## 미리 알고가기

- **SOAR (Security Orchestration, Automation and Response)**: 여러 보안 도구를 연결해 분석·대응 절차를 자동화하는 체계
- **API (Application Programming Interface)**: 시스템 사이에서 조회·차단 명령을 호출하는 연결 규칙
- **SIEM (Security Information and Event Management)**: 여러 시스템의 보안 이벤트를 수집·분석해 경보를 만드는 체계
- **EDR (Endpoint Detection and Response)**: 단말의 위협 행위를 탐지하고 격리·조사하는 체계
- **TIP (Threat Intelligence Platform)**: 위협 정보를 수집·평가·배포하는 플랫폼
- **플레이북**: 경보의 보강·판단·승인·조치·복구 순서를 정의한 실행 절차
- **롤백**: 자동 조치가 잘못됐을 때 차단·설정을 이전 상태로 되돌리는 동작
- **사람 참여 (Human-in-the-Loop)**: 업무 중단 위험이 큰 조치를 담당자가 승인하는 방식
- **오탐**: 정상 활동을 공격으로 잘못 판단한 경보
- **SOAR·SIEM 읽기**: “소어·심”으로 읽으며 보안 대응 자동화와 이벤트 관리 체계의 영문 머리글자임
- **API·EDR·TIP 읽기**: “에이피아이·이디알·팁”으로 읽으며 호출 규칙·단말 대응·위협정보 플랫폼의 영문 머리글자임



## Ⅰ. 개요

- 정의/개념: 보안 도구를 연계해 경보 분석·승인·조치를 실행하는 대응 절차
- **배경/필요성**: 수동 대응의 반복 작업과 도구 전환으로 초기 대응 지연

### 쉽게 이해하기 (학습용)

- 분석가의 반복 조회·차단 업무를 조건과 승인, 되돌리기 기능이 있는 흐름으로 바꿈

## Ⅱ. 특징

- 보안 도구 간 API 표준 연결을 수행한다.
- 경보 맥락에 따라 자동·승인·수동 경로를 분기한다.
- 조건 검증·승인·롤백과 감사 로그로 자동 조치 위험을 통제한다.

### 쉽게 이해하기 (학습용)

- 경보 위험에 따라 자동·승인·수동 대응을 나누고 실패 시 되돌림

## Ⅲ. 아키텍처 및 구성요소

| 설계 요소 | 설명 |
|:---|:---|
| 트리거 | 경보·일정·요청으로 실행 범위를 결정함 |
| 정보 보강 | 자산·사용자·평판 등 문맥 정보를 정규화함 |
| 판단 승인 | 위험 수준에 따라 경로를 분기하고 승인함 |
| 조치 복구 | 차단·계정 보호를 수행하고 롤백을 실행함 |
| 사건 감사 | 입력·결정·API 결과·담당자를 티켓에 남김 |

```text
[SIEM 경보] → [SOAR: 보강·판단]
                    ├─ 저위험 → [EDR·방화벽 자동 조치]
                    ├─ 고위험 → [분석가 승인] → [조치]
                    └─ 실패   → [롤백·수동 대응]
                                   ↓
                              [티켓·감사 로그]
```

### 쉽게 이해하기 (학습용)

- 자동화의 핵심은 버튼을 빨리 누르는 것이 아니라 잘못 누르면 되돌리고 이유를 남기는 것임

## Ⅳ. 원리 및 절차 흐름도

```text
경보 수신 → 자산·위협정보 보강 → 위험 분기·승인 → 조치·롤백 → 결과 기록
```

| 절차 | 설명 |
|:---|:---|
| 선정 | 빈도·영향도로 자동화 대상을 선정함 |
| 설계 | 분기·권한·승인·실패 동작을 정의함 |
| 격리 | 정상·실패·중복 실행을 격리 검증함 |
| 배포 | 관찰·승인·자동 순으로 범위를 확대함 |
| 개선 | 오탐·실패·롤백 지표로 흐름을 개선함 |

### 쉽게 이해하기 (학습용)

- 처음부터 자동 차단하지 않고 관찰과 승인 단계를 거쳐 안전성이 확인된 범위만 확대함

## Ⅴ. 플레이북 실행 방식 비교

| 비교축 | 완전 자동 | 승인 기반 | 수동 지원 |
|:---|:---|:---|:---|
| 적용 기준 | 반복적이고 되돌릴 수 있는 저위험 조치 | 업무 영향이 크지만 신속성이 필요할 때 | 판단이 복잡하거나 자동화가 미성숙할 때 |
| 핵심 특징 | 조건 충족 시 즉시 조치 | 사람이 확인한 뒤 조치 | 정보 보강만 하고 사람이 실행 |
| 한계 | 오탐이 대규모 차단으로 확산 | 승인 지연으로 대응이 늦어짐 | 처리 편차와 분석가 부담 증가 |

> 요약: 대상 위험도와 자동화 성숙도에 따라 선택함

### 쉽게 이해하기 (학습용)

- 확실하고 안전한 일만 자동화하고 업무 중단 위험이 큰 조치는 사람이 마지막으로 확인함

## Ⅵ. 실무 사례

1. 랜섬웨어 단말의 **업무 영향 확인 후 자동 격리**

### 쉽게 이해하기 (학습용)

- 플레이북은 단말의 악성 행위와 업무 중요도를 확인하고 승인 조건을 충족하면 최소 권한 API로 격리하며 실행 결과와 롤백 정보를 기록한다.

## Ⅶ. 결론

- 사고 대응의 지연과 수행 편차를 줄이기 위해 경보 신뢰도·업무 영향·자동화 권한·승인·롤백을 검토하여, 자동·승인·수동 경로가 분리된 플레이북을 운영해야 한다.

### 쉽게 이해하기 (학습용)

- 빠른 자동화보다 잘못된 조치를 멈추고 되돌릴 수 있는 자동화가 중요함
