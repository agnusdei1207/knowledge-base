## Ⅰ. 개요

<details><summary>용어 설명</summary>

- **개인정보 전송요구권(Right to Personal Data Portability / PIPA 제35조의2)**: 정보주체가 개인정보처리자가 보유한 자신에 관한 개인정보를 본인 또는 다른 개인정보처리자(적격 수신자/개인정보관리 전문기관)에게 컴퓨터 등 정보처리장치로 처리 가능한 기계 판독형(Machine-Readable) 형태로 전송해 줄 것을 요구할 수 있는 법적 권리.
- **스크린 스크래핑 및 자격증명 공유 결함(Screen Scraping & Credential Sharing Defect)**: 마이데이터 도입 이전, 핀테크 앱이 사용자의 금융 인증서 비밀번호를 직접 위임받아 금융사 웹사이트에 로그인한 뒤 HTML 텍스트를 파싱하던 방식으로, 패스워드 탈취 위험, 비인가 과도 수집, 시스템 부하 폭증을 유발하던 레거시 수집 결함.

</details>

- 정의/개념: 정보주체가 표준 API로 행사하는 **개인정보 전송요구권**
- 배경/필요성: 과거 금융·통신 등 핀테크 서비스에서 사용자의 인증서 비밀번호를 위임받아 웹 화면을 무차별 파싱하던 레거시 스크린 스크래핑(Screen Scraping) 방식은 패스워드 탈취, 비인가 과잉 수집, 원천사 서버 부하 및 보안 통제 불능의 치명적 결함을 노출함에 따라, 개인정보 보호법 제35조의2(전송요구권) 및 전 산업 마이데이터(MyData) 표준화 정책에 기반하여 OAuth 2.0 인가, mTLS 상호 암호화 터널, JSON 표준 스키마, 멱등키(Idempotency Key) 트랜잭션 제어를 결합하는 표준 API 유통 아키텍처를 도입하여 정보주체의 능동적 데이터 이동권(Data Portability) 보장, 스크래핑 전면 폐지에 따른 자격증명 노출 원천 차단 및 기관 간 안전한 상호운용성을 달성할 필요

#### 한줄 요약
- 스크래핑을 폐지하고 표준 API와 암호화 통신을 통해 본인 및 적격 수신자에게 기계 판독형 데이터를 안전하게 전송한다.

## Ⅱ. 특징

<details><summary>용어 설명</summary>

- **본인 전송 vs 제3자 전송 (Portability to Self vs Third Party)**:
  - **본인 전송**: 정보주체 자신의 개인 스마트폰 디바이스로 구조화된 데이터 파일(CSV, JSON)을 다운로드받는 형태.
  - **제3자 전송**: 정보주체의 지시에 따라 정보전송자 서버에서 인가받은 타 핀테크/전문기관 서버로 표준 API를 통해 직접 전송하는 마이데이터의 핵심 형태.

</details>

- 정보주체의 절대적 자기결정권 및 즉각 철회권: 어떤 데이터(범위)를, 누구(적격 수신자)에게, 언제까지(주기) 보낼지 사용자가 직접 선택하며, 언제든 전송 동의를 즉시 철회 가능
- 표준 API 기반 기계 판독형 데이터 전송: JSON 스키마 기반 구조화된 데이터 규격을 준수하여 수신 시스템이 즉시 연계·가공할 수 있는 상호운용성 보장
- 적격 수신자 인가제 및 책임 분리: 금융위/보호위 인가를 획득한 전문기관 및 안전성 기준을 충족한 적격 수신자에게만 전송을 허용하며, 전송자와 수신자 간의 법적 책임을 명확히 구획

#### 한줄 요약
- 자기결정권 보장, 표준 API 기계 판독형 전송, 적격 수신자 제한 및 전송자-수신자 책임 분리를 제공한다.

## Ⅲ. 구조 및 구성요소

<details><summary>용어 설명</summary>

- **마이데이터 유통 생태계 4대 핵심 주체**:
  1. **정보주체 (Data Subject)**: 데이터 전송 요구 및 철회 명령을 내리는 주체.
  2. **정보전송자 (Data Sender)**: 데이터를 보유하고 있으며 법에 따라 전송 의무를 지는 기관(은행, 통신사 등).
  3. **적격 수신자 및 개인정보관리 전문기관 (Data Recipient)**: 인가를 받아 데이터를 수신·분석하는 사업자.
  4. **마이데이터 종합지원 플랫폼 (Support Platform)**: 중계 라우팅, 기관 적격성 검증, 전송 이력 관리 포털.

</details>

```text
마이데이터 유통 체계
├─ 정보주체 | 전송 범위·수신자 지정과 철회
├─ 정보전송자 | 대상 데이터 선별·송신
├─ 적격 수신자 | 목적 범위 내 수신·활용
├─ 종합지원 플랫폼 | 자격 검증·이력 관리
└─ 보안 전송 게이트웨이 | OAuth 2.0·mTLS·멱등성
```

선의 의미: 정보주체가 인증을 거쳐 전송을 요구하면 종합지원 플랫폼의 적격성 검증을 거쳐 전송자와 수신자 간 안전한 API 파이프라인으로 데이터가 전송되는 구조

| 구성요소 | 핵심 책임 및 기술 통제 | 비고 |
|:---|:---|:---|
| 정보주체 | 전송 목적, 전송 항목, 대상 수신자, 전송 주기(정기/수시)를 지정하고 언제든 철회 | Self-Determination|
| 정보전송자 | 법정 대상 정보를 추출하고, 표준 JSON 변환 후 mTLS API 게이트웨이로 송신 | Sender Core |
| 적격 수신자 | 망분리, DB 암호화 등 엄격한 보안 요건을 충족하고 인가된 목적 범위 내 활용 | Recipient Core |
| 종합지원 플랫폼 | 전송 중계, 수신자 라이선스 디렉터리 관리, 전송 요구 및 철회 내역 중앙 관제 | Directory Hub |
| 보안 전송 게이트웨이| OAuth 2.0 인가, mTLS 상호 인증, 멱등키 기반 재전송 트래픽 중복 방어 | Security Gateway|

#### 한줄 요약
- 정보주체, 정보전송자, 적격 수신자, 종합지원 플랫폼, 보안 전송 게이트웨이가 결합한다.

## Ⅳ. 흐름도

<details><summary>용어 설명</summary>

- **마이데이터 전송 5단계 시퀀스**:
  1. 정보주체 본인확인 및 전송 요구 동의 징구
  2. 수신자의 자격 증명 및 적격성 실시간 검증
  3. 법정 대상 데이터 선별 추출 및 영업비밀 필터링
  4. 표준 JSON 패킹 및 mTLS/OAuth 2.0 보안 전송
  5. 멱등성 검증, 수신 완료 및 전송 이력 원장 기록

</details>

```text
1. [본인확인 및 전송 요구] 사용자가 핀테크 앱에서 본인인증(공동/금융인증서) 후 "통신사 가입 내역 전송" 요청
            │
            ▼
2. [수신자 적격성 검증]
    ├─ 종합지원 플랫폼이 핀테크사의 마이데이터 허가 라이선스 및 유효성 대조
    └─ [적격 판정 시 ➔ 정보전송자(통신사)로 OAuth 2.0 Access Token 전달]
            │
            ▼
3. [대상 정보 추출 및 필터링]
    ├─ 통신사가 법정 대상 정보(가입 요금제, 청구 내역)만 데이터베이스에서 추출
    └─ [영업비밀 알고리즘 및 타인 통화 상대방 정보는 100% 필터링 제외]
            │
            ▼
4. [표준 API 암호화 전송]
    ├─ JSON 표준 스키마로 패킹하고 헤더에 `X-Idempotency-Key` 부여
    └─ [mTLS 1.3 상호 인증 터널을 통해 핀테크사 API 엔드포인트로 안전 송신]
            │
            ▼
5. [멱등성 처리 및 감사 로깅]
    ├─ 핀테크사가 멱등키를 검증하여 네트워크 재시도 시 중복 저장 차단
    └─ [전송 일시, 대상, 건수를 전송 이력 원장에 기록하여 3년간 불변 보존]
```

1. 본인확인 및 전송 요구
2. 수신자 적격성 검증
3. 대상 정보 추출 및 필터링
4. 표준 API 암호화 전송
5. 멱등성 처리 및 감사 로깅

#### 한줄 요약
- 전송자는 API 구축과 트래픽 비용을 지고 편익은 수신자가 가져가는 비대칭이 있으므로, 적격 수신자 제한과 선별 추출이 그 부담을 감당 가능한 범위로 묶는 장치가 된다.

## Ⅴ. 종류 및 비교

<details><summary>용어 설명</summary>

- **데이터 수집 방식 비교**: 레거시 스크린 스크래핑(Screen Scraping) vs 마이데이터 표준 API(MyData API)의 비교.

</details>

| 비교 항목 | 전통적 스크린 스크래핑 (Screen Scraping) | 마이데이터 표준 API (MyData API) |
|:---|:---|:---|
| 데이터 수집 방식 | 사용자 비밀번호로 로그인 후 HTML 화면 텍스트 긁기| OAuth 2.0 토큰 기반 시스템 간 표준 RESTful API 전송|
| 인증 및 자격증명 | 사용자의 공인인증서 비밀번호를 핀테크 서버에 직접 저장| 사용자 비밀번호 미공유 (임시 OAuth 토큰 인가) |
| 데이터 수집 범위 | 화면에 표시되는 불필요한 과다 정보까지 무차별 긁기 | 정보주체가 지정한 법정 필수 항목만 핀셋 선별 전송 |
| 서비스 안정성 | 웹사이트 HTML UI 변경 시 스크래핑 스크립트 즉시 중단| 버전 관리되는 JSON 스키마를 통해 안정적 영구 연동 |
| 보안 및 규제 | 전자금융감독규정 및 PIPA에서 원칙적 금지 폐지| 개인정보 보호법 제35조의2에 따른 합법적 표준 전송 |

#### 한줄 요약
- 스크래핑은 패스워드 공유와 화면 긁기로 보안 취약, 표준 API는 토큰 인가와 정형화된 JSON 전송으로 안전하다.

## Ⅵ. 실무 고려사항 및 대책

<details><summary>용어 설명</summary>

- **개인정보 보호법 시행령 제42조의2~9**: 개인정보 전송요구권의 적용 대상자, 전송 대상 정보의 범위, 전송 거절 사유, 표준 API 규격 및 전송비용 분담 기준.

</details>

| 문제 | 대책 | 효과 |
|:---|:---|:---|
| 핀테크사 요청 시 전송 범위 외의 타인 정보나 기업 영업비밀이 포함되어 개인정보 무단 유출 및 부정경쟁방지법 위반 소송 발생 | 개인정보보호법 시행령 제42조의2 준수, 법정 대상 데이터 선별 추출 엔진 및 영업비밀 자동 마스킹 필터 구축 | 비대상 잉여 정보 및 타인 데이터 유출 100% 원천 차단 |
| 네트워크 불안정으로 인한 API 타임아웃 재전송 시 수신 측 데이터베이스에 동일한 거래 내역이 중복 적재되어 자산 통계가 왜곡되는 장애 | 마이데이터 RESTful API 헤더에 멱등키(Idempotency Key)를 강제하고 수신단 중복 트랜잭션 필터링 구현 | 수십 번의 네트워크 재시도 시에도 데이터 단 1회 정상 적재 보장 및 정합성 완벽 유지 |
| 정보주체가 전송 요구를 철회했으나 전송 시스템과 수신 시스템 간 동기화가 지연되어 철회 후에도 정기 전송이 지속되는 위법 사태 | 종합지원 플랫폼과 연동되는 실시간 전송 철회(Revocation) 이벤트 웹훅 및 즉각 데이터 파이프라인 셧다운 파이프라인 가동 | 철회 즉시 데이터 전송 100% 실시간 중단 및 정보주체 통제권 완벽 보장 |

#### 한줄 요약
- 선별 추출로 영업비밀을 보호하고, 멱등키로 중복 적재를 막으며, 실시간 웹훅으로 철회를 즉각 집행한다.

## Ⅶ. 결론

- 데이터 독점을 해소하고 정보주체가 자신의 데이터를 주도적으로 이동·활용할 수 있도록 보장하는 국가 데이터 경제 및 정보주체 주권 확립(PIPA 제35조의2 / 전 산업 마이데이터)의 핵심 상호연동 아키텍처로 확고히 자리 잡았으며, 금융·공공을 넘어 의료·통신·유통 전 분야로 전면 확산되는 가운데, 실무 마이데이터 송수신 플랫폼 구축 시에는 스크래핑 완전 배제 및 표준 REST API 게이트웨이(OAuth 2.0 토큰 기반) 전환, 전송 구간 mTLS 1.3 암호화 및 비대상 타인 정보/영업비밀 선별 필터링, 네트워크 재시도 시 데이터 중복 적재를 방지하는 멱등키(X-Idempotency-Key) 검증 및 실시간 전송 철회(Revocation) 이벤트 웹훅 체계를 결합하여 완벽한 마이데이터 전송 신뢰성을 완성

#### 한줄 요약
- 표준 RESTful API와 OAuth 2.0/mTLS 및 멱등성 통제를 통해 안전하고 신뢰할 수 있는 마이데이터를 완성한다.
