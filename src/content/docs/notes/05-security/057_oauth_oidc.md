## Ⅰ. 개요

<details><summary>용어 설명</summary>

- **OAuth 2.0 (개방형 권한 위임)**: "내 카카오톡 프로필 사진 좀 배달의민족 앱한테 줄래?" 하고 내 비밀번호를 넘기지 않고 권한만 안전하게 위임하는 오픈 표준 프레임워크다.
- **OIDC (오픈아이디 연결)**: OAuth 2.0 위에 얹어서, "이 사람이 찐 카카오 회원 맞다" 하고 신분증(ID 토큰)을 발급해 주는 로그인(사용자 인증) 전용 확장 표준이다.

</details>

- 정의: 제3자 앱(Client)에게 API 자원 접근 권한을 위임하는 OAuth 2.0과, 사용자 신분증(ID 토큰)을 발급하여 로그인(인증)을 처리하는 OIDC 통합 프레임워크다.
- 배경: 서비스마다 비밀번호를 전부 알려주면 해킹당했을 때 내 모든 사이트가 털리고, 권한(읽기/쓰기)을 쪼개서 통제할 수도 없기 때문이다.

#### 한줄 요약

- 배달 앱이 내 비밀번호를 몰라도, 네이버나 카카오가 보증서(토큰)를 대신 발급해서 로그인시켜주는 거다.

## Ⅱ. 특징

<details><summary>용어 설명</summary>

- **접근 토큰 (Access Token)**: "이 쿠폰(토큰) 있으면 게시판 API 3번 호출할 수 있어요" 하는 권한 위임용 티켓이다. (OAuth 2.0 소관)
- **신원 토큰 (ID Token)**: "이름은 홍길동이고, 카카오가 보증함" 하고 도장 쾅 찍혀서 발급되는 디지털 신분증이다. (OIDC 소관, JWT 형식)
- **PKCE (코드 교환용 증명 키)**: 모바일 앱에서 인가 코드(토큰 교환권)를 해커가 중간에 채가지 못하게, 질문(Challenge)과 답(Verifier)을 맞춰야만 토큰으로 교환해 주는 방어 기술이다.

</details>

- **권한과 신원의 철저한 분리**: 자원에 접근하는 접근 토큰(OAuth 2.0)과 사용자가 누구인지 알려주는 신원 토큰(OIDC)을 구분하여 통제한다.
- **PKCE 및 인가 코드 방어**: 모바일 앱이나 SPA(Single Page App) 환경에서 인가 코드를 가로채는 해킹을 막기 위해 PKCE 챌린지 검증을 강제한다.
- **토큰 회전 및 수명 관리**: 수명이 긴 갱신 토큰(Refresh Token)이 털려도 계속 못 쓰게 만들려고, 갱신할 때마다 기존 토큰을 버리고 새 걸로 교체하는 회전(Rotation)을 적용한다.

#### 한줄 요약

- 권한 티켓(Access)과 신분증(ID Token)을 나눠서 주고, 훔쳐가지 못하게 PKCE 자물쇠를 굳게 채운다.

## Ⅲ. 구조 및 구성요소

<details><summary>용어 설명</summary>

- **자원 소유자 (Resource Owner)**: 자기 데이터를 서드파티 앱(클라이언트)이 쓰도록 허락해 주는 실제 사용자 본인이다.
- **클라이언트 (Client)**: 사용자를 대신해서 "얘 데이터 좀 쓸게요" 하고 인가 서버에 토큰을 구걸하는 서드파티 앱(예: 배달 앱)이다.
- **인가 서버 (Auth Server)**: 사용자한테 "배달 앱이 네 프로필 본다는데 동의함?" 물어보고, 오케이 하면 토큰을 찍어내는 권한/인증 보스다.

</details>

```text
[ OAuth 2.0 및 OIDC 인가/인증 아키텍처 ]

[ 1. 자원 소유자 (사용자) ] ── ("카카오 로그인 버튼 누르고, 프로필 제공에 동의함")
      │
      ▼
[ 2. 클라이언트 (서드파티 앱) ] ── ("카카오한테 '얘 로그인 좀 시켜줘' 하고 요청함")
      │
      ▼
[ 3. 인가 서버 / OIDC 제공자 ] ── ("사용자 비번 확인하고, 클라이언트한테 토큰을 발급함")
      │
      ▼
[ 4. 자원 서버 (API 서버) ] ── ("클라이언트가 토큰 가져오면, '어 정상 토큰이네' 하고 데이터 줌")
      │
      ▼
[ 5. 토큰 및 키 관리 ] ── ("토큰 유효기간(TTL) 통제하고, 위조 못 하게 서명 키(JWKS)를 돌림")
```

| 구성요소 | 직관적 비교 책임 | 비고 |
|:---|:---|:---|
| **자원 소유자 (User)** | 본인 신원을 인증하고 서드파티 앱(클라이언트)의 권한 접근을 **동의함** | Owner |
| **클라이언트 (App)** | 사용자를 대신해 인가 서버에 접속하여 **토큰을 달라고 요청함** | Client |
| **인가 서버 (IdP)** | 사용자 동의를 받고 **인가 코드(Code)와 최종 토큰(Token)을 발급함** | IdP |
| **자원 서버 (API)** | 클라이언트가 들이민 Access Token을 철저한 검증하고 **비즈니스 데이터를 제공함** | Resource |
| **토큰/키 관리** | 만료된 토큰을 즉각 쳐내고(TTL), 공개키(JWKS)를 관리하여 **위조를 원천 차단함** | Key |

#### 한줄 요약

- 사용자가 동의하면 $\to$ 앱이 인가 서버에서 토큰을 받아오고 $\to$ 그 토큰으로 API 서버에서 데이터 빼간다.

## Ⅳ. 흐름도

<details><summary>용어 설명</summary>

- (상단 참조)

</details>

```text
[ OIDC 기반 통합 인증 및 토큰 발급 흐름 ]

┌──────────────────────────────┐
│ 1. [권한/인증 요청 및 Redirect URI 검증]
│ ("클라이언트가 '로그인시켜줘!' 하면, 인가 서버가 '너 등록된 주소 맞어?' 컷!")
└──────────────┬───────────────┘
               ▼
┌──────────────────────────────┐
│ 2. [사용자 로그인 및 동의 승인]
│ ("사용자가 아이디/비번 치고 '프로필 제공 동의' 버튼을 꾹 누름")
└──────────────┬───────────────┘
               ▼
┌──────────────────────────────┐
│ 3. [인가 코드 발급 및 PKCE 결속 검증]
│ ("인가 서버가 임시 코드를 주고, 클라이언트가 PKCE 정답을 제출해 철저한 검증받음")
└──────────────┬───────────────┘
               ▼
┌──────────────────────────────┐
│ 4. [접근 토큰(Access) 및 신원 토큰(ID) 발급]
│ ("검증 통과하면 API 데이터용(Access)과 신분증(ID) 토큰 2개를 쏴줌")
└──────────────┬───────────────┘
               ▼
┌──────────────────────────────┐
│ 5. [토큰 서명 및 만료일 철저한 검증 후 API 응답]
│ ("자원 서버가 토큰 까보고 조작 안 됐으면 데이터 내려줌!")
└──────────────────────────────┘
```

### 동작 원리

1. 사전 검증: 클라이언트 요청 시 사전 등록된 Redirect URI 및 PKCE 조건을 1차로 대조.
2. 동의 획득: 자원 소유자(사용자)가 신원을 인증하고 제공할 범위(Scope)를 승인.
3. 코드 교환: 일회성 권한 코드(Authorization Code) 발급 후 PKCE(code_verifier)를 결속하여 철저한 검증.
4. 토큰 발급: 검증 통과 시 API용 접근 토큰(Access)과 사용자 정보용 신원 토큰(ID)을 동시 발급.
5. 자원 제공: 자원 서버(API)에서 토큰 서명, 발급자(iss), 대상(aud), 만료일(exp) 판정 후 응답.

#### 한줄 요약

- 주소 확인 $\to$ 동의받음 $\to$ 임시 코드 교환(PKCE) $\to$ 토큰 2개 발급 $\to$ API 호출이다.

## Ⅴ. 종류 및 비교

<details><summary>용어 설명</summary>

- (상단 설명 참조)

</details>

| 구분 | **OAuth 2.0 (권한 위임)** | **OIDC (신원 인증)** |
|:---|:---|:---|
| 비유 및 핵심 특징 | **"내 친구한테 내 창고 열쇠(토큰) 좀 주실래요?" (권한 위임)** | **"이 사람 내 친구 홍길동 맞아요!" (주민등록증 발급)** |
| 핵심 목적 | 제3자 앱이 API 서버(자원)에 접근하기 위해 **권한을 안전하게 위임함** | 사용자가 누구인지(Profile)를 **안전하게 인증(SSO)함** |
| 산출물 (토큰) | **Access Token** (이걸로 API 찌름) / **Refresh Token** (토큰 연장용 만능키) | **ID Token** (JWT 형식, 이거 까보면 사용자 이름/이메일 정보 나옴) |
| 핵심 검증 요건 | **Scope(어디까지 허락할 건지), PKCE(모바일에서 가로채기 방어)** | **iss(발급자가 찐인지), aud(내 토큰 맞는지), Nonce(재전송 방지)** |

#### 한줄 요약

- 권한 넘겨줄 땐 **OAuth 2.0**, 네이버 로그인으로 간편 가입할 땐 **OIDC**가 팩트다.

## Ⅵ. 실무 고려사항 및 대책

<details><summary>용어 설명</summary>

- **IETF RFC 9700**: "모바일에서 앱 짤 때, 토큰 가로채기 딱 좋으니까 PKCE 무조건 써라" 하고 못 박은 최신 보안 표준 가이드다.
- **갱신 토큰 회전 (Refresh Token Rotation)**: 만능키(Refresh Token)가 해커한테 털리면 끝장이니까, 한 번 써서 토큰 갱신할 때 이 만능키 자체도 새 걸로 교체해 버리는 방어 기법이다.

</details>

| 장애/위험 요소 | 원인 분석 | 실무 대책 및 해결방안 | 기대 효과 |
|:---|:---|:---|:---|
| 모바일 앱에서 구형 OAuth 썼다가 **인가 코드를 악성 앱에 가로채여 유출 위험** | 모바일 앱은 비밀키(Client Secret)를 숨길 수가 없는데, 방어책 없이 무지성으로 코드를 교환함 | **IETF RFC 9700** 가이드에 따라 모바일/SPA 환경에선 무조건 **PKCE 결속 강제** | 악성 앱의 인가 코드 가로채기(Interception) 공격 구조적 원천 차단 |
| 해커가 남의 ID Token을 복사해서 **로그인 세션을 맘대로 뚫어버림** | ID Token이 위조됐는지, 나한테 발급된 게 맞는지 JWT 서명 검증을 대충 넘어감 | **OIDC Core 1.0** 지침에 따라 발급자(iss), 대상(aud), **Nonce 무결성 검증 강제** | 위조 ID Token 주입 및 사용자 신원 도용(Replay) 공격 소멸 |
| 갱신 토큰(Refresh Token)이 털려서 **해커가 평생 토큰을 계속 재발급받음** | Refresh Token은 수명이 긴데, 유출 시 무효화하거나 재사용을 막는 철저한 방어 로직이 없음 | Access Token 재발급 시 갱신 토큰도 무조건 새 걸로 바꾸는 **갱신 토큰 회전 적용** | Refresh Token 유출 시에도 재사용 불가능 및 권한 영구 남용 철통 억제 |

#### 한줄 요약

- 모바일은 무조건 **PKCE** 걸고, ID 토큰 껍데기 **서명** 까보고, 갱신 토큰은 **회전**시켜서 방어해라.

## Ⅶ. 결론

<details><summary>용어 설명</summary>

- **연동 목적별 표준 선택 기준**: API 데이터만 줄 건지(OAuth), 사용자 신원을 줘서 로그인시킬 건지(OIDC)를 명확히 구별해서 설계하라는 아키텍처 원칙이다.

</details>

- 외부 앱에 데이터를 열어줄 때는 단순 API 접근 통제엔 **OAuth 2.0**을, 사용자 간편 로그인(SSO) 처리엔 **OIDC**를 분리 적용하고, 탈취 위험이 높은 모바일 환경엔 **PKCE**와 **갱신 토큰 회전**을 필수로 강제하는 다층 철저한 방어 기조를 확립함

#### 한줄 요약

- API 권한 통제는 **OAuth 2.0**, 신원 인증은 **OIDC**를 쓰고, **PKCE/토큰 회전**으로 철저한 방어해라.
