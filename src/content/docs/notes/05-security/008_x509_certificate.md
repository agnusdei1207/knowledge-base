## Ⅰ. 개요

<details>
<summary>핵심 용어</summary>

- **X.509 인증서**: 공개키•소유자•용도•유효기간을 인증기관의 전자서명으로 연결하는 표준 전자 문서이다.
- **인증기관(Certificate Authority, CA)**: 공개키와 소유자 신원을 확인하여 인증서에 서명하는 기관이다.
- **소유자•용도 판정 한계**: 공개키 파일만으로 실제 소유자와 허용된 사용 목적을 확인하기 어려운 문제이다.

</details>

- 정의/개념: 공개키•주체•용도•기간을 CA 서명으로 연결한 **X.509 인증서**이다.
- 배경/필요성: 공개키 자체만으로는 소유자의 신원, 허용 도메인 및 구체적인 사용 목적을 증명하기 어렵다.

#### 한줄 요약

- X.509 인증서는 공개키만 담은 파일이 아니라 주인•사용처•유효기간을 적고 발급기관이 위조 방지 서명을 한 디지털 신분증이다.

## Ⅱ. 특징

<details>
<summary>핵심 용어</summary>

- **서명 대상(To Be Signed, TBS) 인증서**: 주체•공개키•유효기간•확장 정보를 담은 인증서 본문이다.
- **주체 대체 이름(Subject Alternative Name, SAN)**: 인증서가 유효한 도메인이나 IP 주소를 나열하는 확장 필드이다.
- **키 용도(Key Usage, KU)**: 인증서 공개키에 허용된 암호 연산을 제한하는 확장 필드이다.
- **확장 키 용도(Extended Key Usage, EKU)**: 인증서의 구체적인 사용 목적을 제한하는 확장 필드이다.

</details>

- **TBS 인증서**에는 공개키•주체 정보를 담되 개인키는 제외한다.
- **CA** 서명으로 TBS 필드 무결성과 발급자를 인증한다.
- **SAN**•**KU**•**EKU**에 따라 이름•키•확장 용도를 제한한다.

#### 한줄 요약

- 인증서 서명이 맞다는 것은 문서가 발급 뒤 바뀌지 않았다는 뜻이고, 그 발급기관을 믿을지는 검증자의 신뢰 저장소가 별도로 결정한다.

## Ⅲ. 구조 및 구성요소

<details>
<summary>핵심 용어</summary>

- **주체**: 인증서가 공개키와 연결하는 소유자이다.
- **발급자**: 인증서에 서명한 CA이다.
- **주체 공개키 정보(Subject Public Key Info, SPKI)**: 공개키 알고리즘과 주체의 공개키 값을 담는 필드이다.
- **인증서 체인**: 주체 인증서에서 중간 CA와 신뢰 기준점까지 서명 관계를 연결한 목록이다.
- **TBS 기본 필드**: 주체•발급자•일련번호•유효기간을 기록하는 인증서 본문 필드이다.
- **확장 필드**: 이름•키•업무 용도와 경로 제약을 추가로 규정하는 필드이다.
- **발급자 서명**: CA가 TBS 인증서 전체의 무결성과 발급 사실을 증명하는 서명이다.
- **인증서 체인•신뢰점**: 상위 CA 서명을 검증자가 신뢰하는 루트까지 연결한 신뢰 근거이다.

</details>

```text
X.509 인증서 구조
├─ TBS 기본 필드
├─ 주체 공개키 정보
├─ 확장 필드
├─ 발급자 서명
└─ 인증서 체인•신뢰점
```

가지의 의미: 인증서 본문•공개키•제약•서명•신뢰 근거를 나눈 구조이다.

| 구성요소 | 책임 |
|:---|:---|
| TBS 기본 필드 | **TBS 기본 필드**가 **주체**•**발급자**•일련번호•기간 기록 |
| 주체 공개키 정보 | **SPKI**가 공개키 알고리즘•매개변수•값 기록 |
| 확장 필드 | **확장 필드**가 SAN•KU•EKU로 이름•용도 제한 |
| 발급자 서명 | **발급자 서명**이 TBS 전체의 발급자•무결성 증명 |
| 인증서 체인•신뢰점 | **인증서 체인•신뢰점**이 상위 CA 서명을 루트까지 연결 |


#### 한줄 요약

- 신분증의 발급 도장을 상위 기관 도장으로 차례로 확인해, 검증자가 미리 믿기로 한 최상위 기관까지 이어지는지 살핀다.

## Ⅳ. 흐름도

<details>
<summary>핵심 용어</summary>

- **인증서 서명 요청(Certificate Signing Request, CSR)**: 공개키•주체 정보와 개인키 보유 증명을 담은 발급 요청이다.
- **경로 검증**: 인증서 서명이 신뢰 기준점까지 유효하게 이어지는지 확인하는 검증이다.
- **이름 검증**: SAN이 검증 대상의 도메인이나 IP 주소와 일치하는지 확인하는 검증이다.
- **용도 검증**: KU•EKU가 검증자가 기대한 사용 목적을 허용하는지 확인하는 검증이다.
- **신원•키 통제권 검증**: 발급 대상의 신원과 공개키에 대응하는 개인키 보유를 확인하는 단계이다.
- **검증된 발급 요청**: 신원과 키 통제권을 확인한 CSR을 CA에 제공하는 단계이다.
- **TBS•확장 서명**: CA가 기본 필드와 확장 필드 전체에 서명하는 단계이다.
- **경로•이름•용도 검증**: 신뢰 경로•기간•SAN•KU•EKU를 함께 확인하는 단계이다.
- **폐지 상태 조회**: 유효기간 전에 인증서 효력이 중단되었는지 확인하는 단계이다.

</details>

```text
CSR 제출
        │
        ▼
1. 신원•키 통제권 검증
        ├─ 실패: 발급 거부
        └─ 성공
             │
             ▼
     2. 검증된 발급 요청
             │
             ▼
     3. TBS•확장 서명
             │
             └── 인증서 체인•소유 증명 제시
                         │
                         ▼
                 4. 경로•이름•용도 검증
                         ├─ 실패: 인증서 거부
                         └─ 성공
                              │
                              ▼
                      5. 폐지 상태 조회
                              │
                              └── 인증서 승인 결과 반환
```

### 동작 원리

1. **신원•키 통제권 검증**: **CSR**의 신원•키 통제권을 검증한다.
2. **검증된 발급 요청**: 확인된 주체•공개키를 **검증된 발급 요청**으로 전달한다.
3. **TBS•확장 서명**: CA가 **TBS•확장 서명**을 수행한다.
4. **경로•이름•용도 검증**: **경로 검증**•**이름 검증**•**용도 검증**을 결합해 **경로•이름•용도 검증**을 수행한다.
5. **폐지 상태 조회**: 유효기간 전 무효화 여부의 **폐지 상태 조회**를 수행한다.


#### 한줄 요약

- SAN이 일치하는 인증서라도 키 용도가 부적합하거나 유효기간이 만료됐거나 신뢰되지 않는 CA가 발급했다면 검증에 실패하므로, SAN 외 모든 검증 조건을 통과해야 한다.

## Ⅴ. 종류 및 비교

<details>
<summary>핵심 용어</summary>

- **전송 계층 보안(Transport Layer Security, TLS)**: 통신 상대 인증과 전송 구간 보호를 제공하는 프로토콜이다.
- **상호 전송 계층 보안(mutual Transport Layer Security, mTLS)**: 양측이 인증서를 교환하여 서로의 신원을 검증하는 방식이다.
- **서버 인증서**: TLS 서버의 도메인과 공개키를 연결하는 인증서이다.
- **클라이언트 인증서**: mTLS 사용자나 장비와 공개키를 연결하는 인증서이다.
- **코드 서명 인증서**: 소프트웨어 배포자와 서명키를 연결하여 산출물의 출처를 검증하는 인증서이다.

</details>

| X.509 인증서 용도 | **서버 인증서** | **클라이언트 인증서** | **코드 서명 인증서** |
|:---|:---|:---|:---|
| 적용 기준 | **TLS** 서버 신원 검증 | **mTLS** 클라이언트 신원 검증 | 소프트웨어 서명 검증 |
| 핵심 특징 | 도메인•서버 키 연결 | 사용자•장비 키 연결 | 배포자•서명키 연결 |
| 한계 | SAN 오검증 시 사칭 허용 | 과다 발급 시 권한 확산 | 빌드 침해 시 악성 코드 서명 |

> 요약: 식별 주체•EKU에 맞는 인증서를 선택한다.

#### 한줄 요약

- 서버용 신분증으로 코드를 승인할 수 없듯, 인증서마다 식별 대상과 EKU가 다르므로 검증자는 기대한 용도인지 확인해야 한다.

## Ⅵ. 실무 고려사항 및 대책

<details>
<summary>핵심 용어</summary>

- **의견 요청 문서(Request for Comments, RFC) 5280**: 인터넷 X.509 v3 인증서•CRL 프로파일과 경로 검증 절차를 규정한 표준이다.
- **국제전기통신연합 전기통신표준화부문(International Telecommunication Union Telecommunication Standardization Sector, ITU-T) X.509**: 인증서와 폐지 목록의 기본 구조를 규정한 표준이다.
- **하드웨어 보안 모듈(Hardware Security Module, HSM)**: 인증서의 개인키를 외부로 노출하지 않고 내부에서 서명 연산을 수행하는 장치이다.

</details>

| 문제 | 대책 | 효과 |
|:---|:---|:---|
| 인증서 프레임워크 불일치 | **ITU-T X.509** 준수 | 필드 의미 일관화 |
| 인터넷 경로 오검증 | **RFC 5280** 적용 | 이름•용도 오용 차단 |
| 개인키•중간 인증서 누락 | **HSM**•체인 자동 배포 | 키 유출•연결 실패 억제 |

#### 한줄 요약

- 서버는 자신의 인증서와 필요한 중간 인증서를 보내지만, 루트 인증서는 클라이언트가 미리 보유한 신뢰 저장소에서 선택해야 한다.

## Ⅶ. 결론

<details>
<summary>핵심 용어</summary>

- **인증서 승인**: 신뢰 경로•SAN•KU•EKU•유효기간과 폐지 상태를 모두 통과했을 때만 내리는 승인이다.

</details>

- **경로•이름•용도 검증**과 **폐지 상태 조회**를 모두 통과한 인증서에만 **인증서 승인**을 내린다.

#### 한줄 요약

- 인증서가 있다는 사실만 믿지 말고, 기대한 루트에서 이어졌는지와 현재 이름•용도•기간•폐지 상태가 모두 맞는지 확인해야 한다.
