## Ⅰ. 개요

<details><summary>용어 설명</summary>

- **OWASP Top 10**: 실제 침해 통계를 기반으로 웹 환경에서 가장 치명적인 상위 10대 보안 위험 범주를 표준화한 참조 모델.
- **OWASP 삼각 체계**: 위험 식별(Top 10), 설계 규격(ASVS), 테스트 검증(WSTG)으로 이어지는 엔드투엔드 시큐어 SDLC.

</details>

- 정의/개념: 상위 10대 보안 위험 범주를 분류하고 **ASVS 설계 규격 및 WSTG 테스트 지침과 결합하여 안전한 소프트웨어를 구축하는 프레임워크**
- 배경/필요성: 조직마다 웹 보안 기준을 각자 만들면 같은 결함을 각자 겪고 각자 학습하는 비용이 반복되므로, 실제 침해 통계로 상위 위험을 추린 공통 참조 계층을 두어 기준 수립 비용을 없애고 설계(ASVS)·검증(WSTG) 규격까지 하나의 축으로 잇을 필요

#### 한줄 요약
- Top 10은 통계로 상위만 추린 목록이라 우선순위를 얻는 대신 조직 고유의 비즈니스 로직 결함은 원리상 담지 못하므로, 이를 단독 기준으로 쓰면 체크리스트를 다 채우고도 침해가 난다.

## Ⅱ. 특징

<details><summary>용어 설명</summary>

- **A01 Broken Access Control (권한 관리 붕괴)**: 타인의 데이터나 비인가 관리자 기능을 직접 URL/API 조작으로 접근할 수 있는 취약점.
- **A04 Insecure Design (안전하지 않은 설계)**: 코딩 오류 이전의 기획/설계 아키텍처 단계에서 위협 모델링 부재로 발생하는 구조적 결함.

</details>

- **위험도 기반 10대 핵심 카테고리화**: 권한 통제 붕괴, **암호화 실패, 인젝션, 안전하지 않은 설계, 보안 설정 오류를 체계적 분류**
- **시큐어 SDLC 삼각 체계(Triad) 연계**: 위험 식별(Top 10) $\rightarrow$ **설계 명세(ASVS) $\rightarrow$ 테스트 검증(WSTG)으로 이어지는 완결된 방법론**
- **아키텍처 설계 중심의 패러다임 전환**: 단순 코딩 버그 수정을 넘어 **위협 모델링(A04 Insecure Design)을 통한 선제적 설계 보안 강조**

#### 한줄 요약
- A04가 설계 결함을 별도 범주로 세운 것은 코딩 단계의 수정으로는 되돌릴 수 없는 결함이 존재함을 인정한 것으로, 설계 시점에 검토 비용을 앞당겨 치르는 편이 나중의 재설계보다 싸다는 판단이다.

## Ⅲ. 구조 및 구성요소

<details><summary>용어 설명</summary>

- **ASVS vs WSTG**: 소프트웨어 보안 요구사항 명세서인 Application Security Verification Standard와 모의 침투 지침인 Web Security Testing Guide.

</details>

```text
OWASP 애플리케이션 보안 체계
|-- 위험 참조
|   `-- OWASP Top 10
|-- 설계 요구사항
|   `-- OWASP ASVS
|-- 안전한 구현
|   `-- 시큐어 코딩·SAST
`-- 검증 지침
    `-- OWASP WSTG
```

선의 의미: Top 10에서 위험을 식별하고 ASVS 명세를 설계에 반영하여 시큐어 코딩을 수행한 후 WSTG 절차에 따라 최종 침투 검증을 완료하는 구조

| 구성요소 | 핵심 엔지니어링 책임 | 주요 특징 |
|:---|:---|:---|
| **OWASP Top 10** | 전 세계 침해 통계를 바탕으로 **상위 10대 위험 범주 및 우선순위 제시** | Risk Awareness |
| **OWASP ASVS** | 애플리케이션 설계에 내재화해야 하는 **3단계 보안 요구사항 명세화** | Architecture |
| **시큐어 코딩 (SAST)** | 소스코드 레벨에서 **인젝션, XSS, 취약 라이브러리 결함 원천 방어** | Implementation |
| **OWASP WSTG** | 배포 전 단계에서 **취약점이 통제되었는지 검증하는 표준 침투 지침** | Verification |
| **위협 모델링** | DFD를 분석하여 **안전하지 않은 설계(A04)를 사전 방지** | Shift-Left |

#### 한줄 요약
- 세 문서는 각각 SDLC의 다른 단계에 끼어들어 앞 단계가 못 막은 결함을 뒤에서 받아 내는 구조이므로, 어느 하나만 도입하면 그 단계 밖의 결함은 그대로 프로덕션까지 통과한다.

## Ⅳ. 흐름도

<details><summary>용어 설명</summary>

- **ASVS Level 1~3**: L1(모든 소프트웨어 기본선), L2(일반 엔터프라이즈 앱/개인정보 처리), L3(금융 코어 뱅킹/군사 최고 등급).

</details>

```text
위험 식별, ASVS 설계 명세, 시큐어 코딩, SAST 검증 및 WSTG 침투 시험 파이프라인
        │
   1. [위험 식별] 서비스 비즈니스 특성을 OWASP Top 10(A01 권한 붕괴, A03 인젝션)에 매핑
        │
   2. [보안 요구 명세화] 설계 단계에서 OWASP ASVS Level 2 세부 항목을 설계서에 반영
        │
   3. [시큐어 코딩 구현] ORM 매핑, 파라미터화 쿼리, 세션 기반 RBAC 접근 통제 코드 구현
        │
   4. [CI/CD 자동 검증] Git Commit 시 SAST/DAST 파이프라인이 구동되어 1차 취약점 자동 필터링
        │
   5. [WSTG 검증 및 배포] 스테이징 침투 검증 후 안전한 빌드 배포
        │
   ├─ [취약점 검출 시] ➔ 배포 파이프라인 차단 및 개발팀에 ASVS 코드 수정 요구
   ▼
       [프로덕션 릴리스]
```

- 1. 위험 식별
- 2. 보안 요구 명세화
- 3. 시큐어 코딩 구현
- 4. CI/CD 자동 검증
- 5. WSTG 검증 및 배포

#### 한줄 요약
- 5단계에서 취약점이 나와 되돌아가는 경로는 설계 문서까지 거슬러 올라가므로, 2단계 ASVS 명세에 들이는 시간이 배포 직전 재작업 비용을 미리 지불하는 셈이 된다.

## Ⅴ. 종류 및 비교

<details><summary>용어 설명</summary>

- **OWASP Top 10 (위험 분류)**: 실제 침해 통계로 상위 10대 위험만 추려 기획 단계의 우선순위와 투자 근거를 제공하는 대신, 개별 구현 방법은 담지 않는 거시적 참조 문서.
- **OWASP ASVS (Application Security Verification Standard)**: 보안 요구사항을 3단계 레벨의 수백 개 항목으로 명세해 설계·구현에 그대로 옮길 수 있게 하는 대신, 어느 레벨을 택할지의 판단을 조직에 남기는 규격 문서.
- **OWASP WSTG (Web Security Testing Guide)**: 각 취약점을 어떤 절차로 공격해 확인할지 표준 테스트 케이스로 규정해 진단 결과의 재현성을 확보하는 대신, 설계 결함 자체를 예방하지는 못하는 검증 문서.

</details>

| 비교 항목 | OWASP Top 10 (위험 분류) | OWASP ASVS (보안 요구 명세) | OWASP WSTG (보안 시험 지침) |
|:---|:---|:---|:---|
| **문서의 핵심 성격** | **최우선 주의 대상 10대 보안 위험 요약서** | **소프트웨어 보안 아키텍처 요구사항 명세서**| **모의 침투 테스트 및 취약점 진단 가이드** |
| **주요 활용 단계** | **기획 및 전략 수립 (Risk Awareness)** | **아키텍처 설계 및 구현 (Secure Design)** | **QA 테스트 및 배포 전 검증 (Verification)**|
| **상세도 및 형식** | 거시적 10대 범주 (개념 및 사례 설명) | **3단계 레벨, 수백 개 세부 기술 요구사항** | **단계별 공격 시나리오 및 진단 체크리스트** |
| **주요 대상 독자** | 경영진, 개발 총괄, 보안 기획자 | **소프트웨어 개발자, 보안 아키텍트** | **모의 침투 테스터, QA 엔지니어, 보안 진단원**|
| **핵심 기여 가치** | **보안 투자 우선순위 선정 및 공감대 형성**| **보안이 내재화된 안전한 소프트웨어 빌드** | **시스템의 실질적 공격 방어 통제력 실증** |

#### 한줄 요약
- Top 10은 위험 인식(What), ASVS는 설계 구현(How to Build), WSTG는 테스트 검증(How to Test)을 담당한다.

## Ⅵ. 실무 고려사항 및 대책

<details><summary>용어 설명</summary>

- **Checklist Syndrome (체크리스트 증후군)**: Top 10의 10개 항목만 단순 체크하고 비즈니스 고유 로직 결함(결제 금액 변조 등) 진단을 누락하는 운영 오류.

</details>

| 문제 | 대책 | 효과 |
|:---|:---|:---|
| Top 10 항목만 단순 체크리스트로 확인하여 **비즈니스 로직 우회 및 API 권한 탈취 사고 발생** | **기획/설계 단계부터 `OWASP ASVS 4.0(Level 2) 보안 아키텍처 요구사항 의무 적용`** | 구조적 보안 결함의 Shift-Left 선제 방어 완성 |
| 모의 침투 테스터의 무차별 공격으로 인한 **테스트 환경 장애 및 재현 불가능한 보고서** | **`OWASP WSTG 4.2 표준 테스트 케이스 기반의 통제된 침투 시험 절차 준수`** 의무화 | 가용성 영향 0% 유지 및 100% 재현 가능한 진단 확보 |
| 과거 룰셋에 머물러 **최신 클라우드 API 권한 붕괴(BOLA) 및 SSRF 공격 방어 실패** | **최신 `OWASP Top 10 및 OWASP API Security Top 10을 전사 표준에 주기적 반영`** | 진화하는 최신 클라우드/API 위협에 선제 대응 |
| 개발자들의 시큐어 코딩 지식 부족으로 인한 소스코드 취약점 재발 | **`IDE 내 실시간 시큐어 코딩 린터(Linter) 플러그인 및 개발자 맞춤 교육`** | 취약 코드 커밋 사전 방지 및 개발 생산성 향상 |

#### 한줄 요약
- 실무 실패는 표준을 안 써서가 아니라 목록을 채우는 것으로 보안을 끝냈다고 판단해서 생기므로, Top 10은 최소 기준선으로만 두고 남는 판단력을 조직 고유 로직 결함에 배분해야 한다.

## Ⅶ. 결론

- 위험 선별은 **Top 10**, 설계는 **ASVS**, 검증은 WSTG로 역할 분리

#### 한줄 요약
- OWASP 프레임워크는 Top 10 위험 식별과 ASVS 설계 규격 및 WSTG 침투 검증을 결합하여 안전한 시큐어 SDLC를 완성하는 표준 체계다.
