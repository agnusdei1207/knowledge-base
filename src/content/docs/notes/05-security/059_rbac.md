## Ⅰ. 개요

<details><summary>용어 설명</summary>

- **RBAC (역할 기반 접근 제어)**: 사원증에 "너 이거이거 해" 하고 권한을 직접 써주는 게 아니라, "넌 대리야!"(직무 역할) 라고만 박아놓고 '대리' 역할에 권한을 매핑해서 관리 편의성을 극대화하는 거다.

</details>

- 정의: 사용자 개인에게 직접 권한을 매핑하지 않고, 조직의 직무(Role) 단위로 권한을 묶어 배정하는 간접 접근 통제 모델이다.
- 배경: 수천 명의 직원에게 개별적으로 권한을 줬다가, 부서 이동이나 퇴사 시 권한 회수가 누락되어 대형 내부 보안 사고가 터지기 때문이다.

#### 한줄 요약

- 홍길동한테 직접 권한을 주지 말고, 홍길동한테 '영업과장' 명찰(역할)을 달아준 뒤 '영업과장' 권한을 줘라.

## Ⅱ. 특징

<details><summary>용어 설명</summary>

- **역할 계층 (Role Hierarchy)**: 과장 역할은 대리와 사원 역할의 모든 권한을 알아서 다 상속받게 구조를 짜는 거다. (RBAC1 모델)
- **정적 직무 분리(SSD)**: "기안자" 역할과 "결재자" 역할을 애초에 한 사람한테 동시에 주지 못하게 부여 단계부터 막아버리는 거다.
- **동적 직무 분리(DSD)**: 기안, 결재 역할을 둘 다 가진 사장님이라도, 한 번 로그인한 세션에선 기안 올리면서 동시에 결재를 못하게 막는 거다.

</details>

- **3계층 간접 맵핑**: 사용자(User)-역할(Role)-권한(Permission)을 분리하여 권한 부여 및 회수의 극대화된 관리 효율성을 제공한다.
- **최소 권한 상속**: 역할 간 계층(Hierarchy) 구조를 통한 공통 권한 상속 및 세션 활성화 기반의 최소 권한 원칙을 적용한다.
- **상충 직무 원천 차단**: 횡령 등 내부자 부정을 예방하기 위해, 권한 부여 자체를 막는 정적 직무 분리(SSD)와 실행을 막는 동적 직무 분리(DSD) 제약조건을 집행한다.

#### 한줄 요약

- 사람-역할-권한으로 분리하고, 직급 높으면 권한 상속해주고, 기안/결재는 동시에 못 하게 찢어놓는다.

## Ⅲ. 구조 및 구성요소

<details><summary>용어 설명</summary>

- **역할 (Role)**: 사용자와 권한 사이에 낀 중간 상자. 여기에 사용자도 넣고 권한도 넣어서 직무를 정의한다.
- **권한 (Permission)**: 데이터베이스 테이블(객체)을 읽거나 지우는(행위) 구체적인 동작들의 바인딩 세트다.

</details>

```text
[ RBAC 접근 제어 구조 ]

[ 1. 사용자 (User) ] ── ("부서 이동 온 김대리")
      │
      ▼
[ 2. 직무 역할 (Role) ] ── ("김대리한테 '결재자' 역할을 배정함")
      │
      ▼
[ 3. 직무 분리 및 계층 검증 ] ── ("어? 김대리는 '기안자'인데 '결재자'도 주면 안 되지! 컷! (SSD)")
      │
      ▼
[ 4. 권한 집합 (Permission) ] ── ("결재자 역할에 연결된 '문서 Read/Write' 티켓을 상속함")
      │
      ▼
[ 5. 자원 및 행위 (Object/Action) ] ── ("최종적으로 DB 테이블이나 파일에 접근하게 허락함")
```

| 구성요소 | 직관적 비교 책임 | 비고 |
|:---|:---|:---|
| **사용자 (User)** | 시스템을 쓰려는 주체로서, 개별 권한이 아니라 **'직무 역할' 단위로 배정받음** | User |
| **역할 (Role)** | 사용자와 권한 사이에 낀 매개체로서, **조직의 직무 단위 권한을 묶어놓은 그룹임** | Role |
| **직무 분리 / 계층** | 횡령 못 하게 **상충되는 역할을 찢어놓거나(SoD), 직급별로 권한을 상속시킴** | Policy |
| **권한 (Permission)** | 특정 자원 객체(Object)에 대해 읽기/쓰기(Action)를 할 수 있는 **실질적인 티켓임** | Permission |
| **자원 객체 (Object)** | 접근 제어를 통해 보호받아야 할 **실제 데이터베이스나 파일, API 엔드포인트 덩어리임** | Resource |

#### 한줄 요약

- 사용자에게 역할을 주고, 역할은 상충되지 않게 관리하며, 역할이 가진 권한 티켓으로 실제 자원을 제어한다.

## Ⅳ. 흐름도

<details><summary>용어 설명</summary>

- (상단 참조)

</details>

```text
[ RBAC 역할 활성화 및 자원 인가 흐름 ]

┌──────────────────────────────┐
│ 1. [로그인 및 사용자-역할 배정 검증]
│ ("김대리가 접속 시, 시스템이 '너 영업팀 과장 역할 맞냐?' 확인함")
└──────────────┬───────────────┘
               ▼
┌──────────────────────────────┐
│ 2. [동적 직무분리(DSD) 상충 검증]
│ ("과장이 결재 역할 켰는데, 기안 역할도 같이 켜려 하네? 즉각 컷!")
└──────────────┬───────────────┘
               ▼
┌──────────────────────────────┐
│ 3. [역할 계층(Hierarchy) 기반 권한 해석]
│ ("과장이니까, 대리랑 사원이 보던 문서 권한까지 다 합쳐서 상속해 줌")
└──────────────┬───────────────┘
               ▼
┌──────────────────────────────┐
│ 4. [최종 자원-행위(Object-Action) 인가 판정]
│ ("최종 권한 묶음을 들고 DB에 지우기(Delete)를 요청 $\to$ 허용!")
└──────────────┬───────────────┘
               ▼
┌──────────────────────────────┐
│ 5. [승인 및 거부 로그 기록 (감사)]
│ ("누가 어떤 역할로 뭘 만졌는지 싹 다 감사 로그로 보존함")
└──────────────────────────────┘
```

### 동작 원리

1. 배정 유효성 검증: 접속 요청 사용자가 할당받은 역할(Role)이 유효한지 대조.
2. DSD 직무분리 검증: 현재 세션에 활성화된 역할 간 상충 여부(동적 직무 분리)를 판정.
3. 역할 계층 해석: 역할 간 상하 구조에 따라 하위 역할의 권한을 롤업(Roll-up) 상속.
4. 자원 인가 판정: 요청 대상 자원 객체(Object) 및 수행 행위(Action)가 권한 내에 있는지 인가.
5. 감사 로깅: 권한 승인 및 거절 내역을 SIEM 등에 보안 감사 로그로 보존.

#### 한줄 요약

- 역할 확인 $\to$ 상충 체크 $\to$ 권한 합침 $\to$ 최종 통과 여부 판정하고 로그 남기기다.

## Ⅴ. 종류 및 비교

<details><summary>용어 설명</summary>

- (상단 설명 참조)

</details>

| RBAC 발전 모델 | **Flat RBAC (기본 RBAC0)** | **Hierarchical RBAC (계층 RBAC1)** | **Constrained RBAC (제약 RBAC2)** |
|:---|:---|:---|:---|
| 비유 및 핵심 특징 | **직원한테 부서 이름표만 딱 달아주고 끝내는 초창기 버전** | **"과장님은 대리들 권한 다 쓸 수 있습니다" 하는 짬짜미 버전** | **"과장님이 기안도 올리고 결재도 하시면 안 되죠!" 하는 철통 방어 버전** |
| 핵심 특징 | 사용자와 권한 사이에 역할(Role)만 도입한 **가장 뼈대만 있는 구조임** | 역할 간 상하 관계(트리 구조)를 도입하여 **상위 역할이 하위 권한을 알아서 상속받음** | 횡령이나 오류 방지를 위해 정적(SSD)/동적(DSD) **직무 분리 제약조건을 추가함** |
| 실무 활용 및 장단점 | 중소기업에선 편하지만, **직급 체계가 복잡해지면 노가다가 증가함** | 권한 재사용성이 엄청 높아지지만, **상하 관계 구조도 짜기가 빡셈** | 내부자 부정을 원천 예방하지만, **역할끼리 제약 조건 충돌(Conflict)이 발생함** |

#### 한줄 요약

- 이름표만 주면 **RBAC0**, 상속받으면 **RBAC1**, 기안/결재 분리하면 **RBAC2**로 진화한다.

## Ⅵ. 실무 고려사항 및 대책

<details><summary>용어 설명</summary>

- **NIST SP 800-53**: 퇴사자 권한 방치 안 하게, 분기별로 권한 재검토(Recertification)를 시키는 보안 표준 가이드라인이다.
- **역할 폭발 (Role Explosion)**: "김대리 얘는 파견직이니까 DB 1번 테이블만 1주일만 보게 해 줘" 자꾸 이런 예외를 쳐내다 보니, 직원 수보다 역할(Role) 개수가 더 많아져서 관리가 개판 나는 현상이다.

</details>

| 장애/위험 요소 | 원인 분석 | 실무 대책 및 해결방안 | 기대 효과 |
|:---|:---|:---|:---|
| 권한 다 몰아줬는데 **퇴사/부서 이동 때 안 빼서 전 부서 정보 탈취됨** | 시스템 도입 때 한 번 권한을 주고, 정기적으로 쓰레기 권한을 청소하는 프로세스가 없음 | **NIST SP 800-53** 기준, 부서장이 분기별로 권한을 검토하는 **정기 권한 재인증(Recertification) 강제** | 좀비 계정 및 과다 잔존 권한을 통한 내부자 정보 유출 및 수평 이동 해킹 사고 원천 차단 |
| 예외 처리 자꾸 해주다 보니 **100명 회사에 역할(Role)이 300개로 폭발함** | RBAC의 한계상 미세한 조건(시간, 접속 위치) 제어를 못 해서 예외 역할만 주구장창 만듦 | 미세 파라미터는 ABAC(속성 기반)로 넘기는 **RBAC-ABAC 하이브리드 접근 제어 적용** | 거시적 직무는 RBAC로, 미시적 통제는 ABAC로 나누어 **역할 폭발(Role Explosion) 방지** |
| 직원이 기안 올리고 지가 결재해서 **법인 카드 대금 10억 횡령함** | 권한을 줄 때 상충되는 직무를 한 사람한테 다 몰아줘도 시스템이 안 막음 | 권한 배정 단계부터 막는 정적(SSD) 및 세션에서 막는 동적(DSD) **철저한 직무 분리(SoD) 집행** | 셀프 결재 및 데이터 무단 훼손 등 내부 통제 붕괴 철저한 방어 |

#### 한줄 요약

- 퇴사자 권한 청소하고(재인증), 예외는 ABAC 섞어서 역할 폭발 막고, 상충되는 역할은 직무분리(SoD)로 원천 차단해라.

## Ⅶ. 결론

<details><summary>용어 설명</summary>

- **최소 권한 원칙 (Principle of Least Privilege)**: 사용자가 딱 지금 업무 할 때 필요한 최소한의 명찰(역할)과 권한만 들고 있게 제한하라는 보안 대원칙이다.

</details>

- 수천 명의 직원을 관리하는 접근 제어의 핵심은, **최소 권한 원칙**에 입각하여 조직 규모에 맞는 **RBAC 모델(RBAC0~3)** 을 선택하고, 내부 부정을 막는 **SoD(직무 분리)** 와 역할 폭발을 제어하는 **하이브리드(ABAC)** 를 병행하는 실무 기조를 확립함

#### 한줄 요약

- 직무별로 권한 주고, 꼬박꼬박 **권한 재검토** 하고, 예외는 **ABAC** 섞어서 관리해라.
