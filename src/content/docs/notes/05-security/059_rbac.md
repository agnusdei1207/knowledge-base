## Ⅰ. 개요

<details><summary>용어 설명</summary>

- **RBAC(Role-Based Access Control, 역할 기반 접근 제어 / ANSI INCITS 359 & NIST)**: 개별 사용자(User)에게 직접 시스템 권한(Permission)을 매핑하지 않고, 조직 내의 업무 직무 및 책임에 대응하는 **역할(Role)** 을 매개체로 정의하여 권한을 할당하고, 사용자는 해당 역할을 부여받음으로써 시스템 자원에 접근하도록 통제하는 간접 인가 모델.
- **직무 분리(SoD: Separation of Duties)**: 내부 통제 붕괴 및 부정 결재(예: 기안자와 승인자의 동일인 지정)를 방지하기 위해, 상호 견제가 필요한 직무 역할을 동일 사용자에게 동시 부여하지 않거나 동시 활성화하지 못하도록 강제하는 보안 원칙.

</details>

- 정의/개념: NIST RBAC 표준에 입각하여 **3계층 간접 매핑(User-Role-Permission)**, **역할 계층(Role Hierarchy)**, **정적/동적 직무 분리(SSD/DSD)** 를 집행함으로써 권한 관리의 복잡성을 낮추고 최소 권한을 보장하는 **엔터프라이즈 인가 거버넌스 아키텍처**
- 배경/필요성: 조직 내 사용자 수가 수만 명으로 증가할 때 개별 ACL(Access Control List) 직접 부여 방식은 잦은 인사이동 시 잔존 권한 방치, 퇴사자 권한 미회수, 과다 권한 부여(Privilege Creep) 문제를 유발하므로 역할 중심의 추상화 통제 요구

#### 한줄 요약
- 사용자-역할-권한의 3계층 간접 매핑과 직무 분리(SoD)를 통해 엔터프라이즈 접근 권한을 체계적으로 통제한다.

## Ⅱ. 특징

<details><summary>용어 설명</summary>

- **NIST RBAC 4단계 표준 모델**:
  - **RBAC0 (Core RBAC)**: 사용자, 역할, 권한의 기본 N:M 매핑 구조.
  - **RBAC1 (Hierarchical RBAC)**: 역할 간 상속(상위 역할이 하위 역할 권한 자동 상속) 트리 지원.
  - **RBAC2 (Constrained RBAC)**: 정적 직무 분리(SSD) 및 동적 직무 분리(DSD) 제약 조건 강제.
  - **RBAC3 (Consolidated RBAC)**: RBAC1(계층)과 RBAC2(제약)를 통합한 엔터프라이즈 완성형 모델.

</details>

- **3계층 간접 매핑에 의한 관리성 극대화**: 사용자가 수천 명이어도 직무 역할 수십 개만 관리하면 되므로 인사이동 시 매핑 교체 1회로 권한 이관 완료
- **역할 계층(Role Hierarchy) 상속**: 직급 및 직무 체계에 맞춰 상위 관리자가 하위 실무자의 권한을 자동으로 상속받도록 구조화
- **정적/동적 직무 분리 (SSD & DSD)**:
  - **SSD (Static SoD)**: 역할 할당(Assignment) 시점에 상충되는 역할(예: 구매 담당 + 대금 지급 담당)의 동시 보유 원천 금지
  - **DSD (Dynamic SoD)**: 세션 런타임 활성화 시점에 상충되는 두 역할을 동일 세션에서 동시 기동 금지

#### 한줄 요약
- 3계층 간접 매핑, 역할 계층 상속(RBAC1), 직무 분리 제약조건(SSD/DSD), 최소 권한 원칙을 제공한다.

## Ⅲ. 구조 및 구성요소

<details><summary>용어 설명</summary>

- **RBAC 핵심 추상화 객체**:
  - **User**: 시스템 자원에 접근하는 주체.
  - **Role**: 조직 내 직무 권한과 책임을 정의하는 집합.
  - **Permission**: 자원(Object)과 연산(Operation/Action)의 결합체.
  - **Session**: 사용자가 특정 시점에 활성화한 역할들의 동적 인스턴스.

</details>

```text
┌─────────────────────────────────────────────────────────────────────────┐
│ [ 1. 사용자 계층 (Users) ]                                              │
│  └─ 김엔지니어, 박팀장, 최관리자 (조직 인사 DB 동기화)                   │
└────────────────────────────────────┬────────────────────────────────────┘
                                     │ (User-to-Role Assignment: N:M 매핑)
                                     ▼
┌─────────────────────────────────────────────────────────────────────────┐
│ [ 2. 역할 및 제약 통제 계층 (Roles & Constraints: RBAC1/RBAC2) ]         │
│  ├─ 역할 계층 (Role Hierarchy): `팀장 Role` ➔ `엔지니어 Role` 권한 상속  │
│  └─ 직무 분리 제약 (SoD): `기안자 Role` ⟷ `결재자 Role` 동시 보유/활성화 차단│
└────────────────────────────────────┬────────────────────────────────────┘
                                     │ (Permission-to-Role Assignment: N:M 매핑)
                                     ▼
┌─────────────────────────────────────────────────────────────────────────┐
│ [ 3. 권한 및 자원 계층 (Permissions & Operations) ]                     │
│  ├─ Permission 1: `DB_Users_Table` ➔ `SELECT`                           │
│  ├─ Permission 2: `Production_Server` ➔ `DEPLOY`                         │
│  └─ [ 세션 활성화(Session) 기반으로 요청 자원에 대한 인가 허용/거절 판정]│
└─────────────────────────────────────────────────────────────────────────┘
```

선의 의미: 사용자가 역할에 매핑되고, 직무 분리와 계층 상속을 거쳐 권한 집합과 연결되어 세션 런타임에 자원 인가를 판정받는 구조

| 구성요소 | 핵심 책임 및 역할 | 비고 |
|:---|:---|:---|
| **사용자 (User)** | 시스템에 로그인하여 자원을 소비하는 식별 가능한 엔터티 | Subject |
| **역할 (Role)** | 직무, 직책, 자격에 따라 권한을 묶어 관리하는 권한의 컨테이너 | Role Group |
| **권한 (Permission)** | 특정 자원 객체(Object)에 대해 허용된 구체적 연산(Read/Write/Execute) 정의 | Operation Bind |
| **역할 계층 (Hierarchy)**| DAG(방향성 비순환 그래프) 구조로 상위 역할이 하위 역할 권한을 자동 집계 상속 | RBAC1 |
| **직무 분리 엔진 (SoD)**| 정적(SSD) 및 동적(DSD) 규칙을 대조하여 권한 집중으로 인한 내부 부정 방지 | RBAC2 |
| **세션 (Session)** | 사용자가 로그인 시 현재 업무에 필요한 최소 역할만 선별 활성화하는 런타임 단위 | Runtime Scope |

#### 한줄 요약
- 사용자, 역할, 권한, 역할 계층(상속), 직무 분리 엔진(SoD), 세션이 결합한다.

## Ⅳ. 흐름도

<details><summary>용어 설명</summary>

- **RBAC 인가 5단계 판정 알고리즘**:
  1. 사용자 인증 및 활성 세션 수립
  2. 세션에 바인딩할 역할 선택 (DSD 검증)
  3. 역할 계층 트리를 순회하여 유효 권한 집합(Permissions) 도출
  4. 요청 자원 및 액션과 권한 집합 대조
  5. 인가 결정(Allow/Deny) 및 감사 로깅

</details>

```text
1. [사용자 로그인] 사용자가 인증 통과 후 세션 생성 ➔ 시스템이 사용자에게 할당된 유효 역할 목록 조회
            │
            ▼
2. [동적 직무분리(DSD) 검증]
    ├─ 사용자가 현재 세션에서 활성화하려는 역할(`결재자 Role`) 선택
    └─ 현재 이미 활성화된 `기안자 Role`과의 동시 기동 금지 규칙(DSD) 대조 ➔ [충돌 시 활성화 거부]
            │
            ▼
3. [역할 계층(Hierarchy) 순회] 선택된 역할(`팀장 Role`)의 상위-하위 상속 관계를 분석하여 전체 상속 권한 집합 구성
            │
            ▼
4. [자원-행위(Object-Action) 인가 대조]
    ├─ 사용자가 `GET /api/v1/financial/reports` 호출
    └─ 상속된 권한 집합에 `Financial_Report:READ`가 포함되어 있는지 대조 ➔ [일치 시 200 OK 승인]
            │
            ▼
5. [감사 로그 보존] 사용자 ID, 활성화된 Role, 접근 대상 Object, 인가 결과를 SIEM에 전송
```

**동작 원리**

1. **간접 권한 획득**: 사용자는 역할에 부여된 권한만을 간접적으로 행사하여 권한 누락/오남용 차단
2. **런타임 상충 통제**: 세션 수준에서 상충 역할을 배타적으로 분리하여 셀프 승인 등 부정행위 억제
3. **계층적 권한 롤업(Roll-Up)**: 조직도의 상하 관계를 모델링하여 중복 권한 설정 작업 최소화
4. **최소 권한 세션 관리**: 사용자가 보유한 모든 권한을 항상 개방하지 않고 세션별 필요 역할만 활성화
5. **폐쇄 루프 권한 감사**: 권한 사용 증적을 실시간 감사 로그로 기록하여 이상 징후 추적

#### 한줄 요약
- 사용자 로그인, DSD 직무 분리 검증, 역할 계층 상속 순회, 자원 인가 대조, 감사 로그 보존 순으로 동작한다.

## Ⅴ. 종류 및 비교

<details><summary>용어 설명</summary>

- **NIST RBAC 4대 모델 비교**: RBAC0(기본), RBAC1(계층), RBAC2(제약), RBAC3(통합)의 비교.

</details>

| 비교 항목 | Core RBAC (RBAC0) | Hierarchical RBAC (RBAC1) | Constrained RBAC (RBAC2) | Consolidated RBAC (RBAC3) |
|:---|:---|:---|:---|:---|
| **핵심 추가 기능** | **사용자-역할-권한 기본 매핑** | **역할 간 상하 상속 계층 (DAG)** | **정적/동적 직무 분리 (SSD/DSD)** | **계층 상속 + 직무 분리 통합** |
| **구조적 복잡도** | 가장 단순 (Flat 구조) | 중간 (트리/그래프 순회 연산) | 중간 (제약조건 유효성 검증) | **높음 (엔터프라이즈 완성형)** |
| **주요 해결 과제** | 권한 직접 매핑의 관리 복잡성 | 상위 직책의 중복 권한 할당 작업| **내부자 횡령 및 권한 집중 부정**| **대규모 복합 조직의 통합 거버넌스**|
| **단독 적용 시 한계** | 직급별 권한 상속 불가 | 상충 직무에 대한 통제 부재 | 직급별 계층 구조 표현 불가 | 구축 및 규칙 설계 난이도 높음 |

#### 한줄 요약
- RBAC0은 기본 Flat 매핑, RBAC1은 계층 상속, RBAC2는 직무 분리 제약, RBAC3은 통합 모델이다.

## Ⅵ. 실무 고려사항 및 대책

<details><summary>용어 설명</summary>

- **역할 폭발(Role Explosion)**: 비즈니스 예외(예: "특정 지점 김대리만 야간에 1번 DB 조회 허용")를 처리하기 위해 매번 새로운 역할을 신설하다가 조직 내 역할 수가 사용자 수보다 많아져 관리가 불가능해지는 RBAC의 구조적 한계 현상.

</details>

| 문제 | 대책 | 효과 |
|:---|:---|:---|
| 인사이동/퇴사 후 이전 부서 권한이 회수되지 않고 누적되어 **퇴사자 계정을 통한 내부 기밀 데이터 유출 사고** | **NIST SP 800-53** 기준, 분기별 부서장 주관 **정기 권한 재인증(Access Recertification) 의무화** | 잔존 과다 권한(Privilege Creep) 및 좀비 권한 100% 원천 회수 |
| 세부적인 예외 접근 요구를 수용하다 **역할(Role) 개수가 사용자 수를 초과하여 관리가 붕괴(Role Explosion)** | **거시적 직무는 RBAC으로 통제하고, 동적 미세 조건(시간/IP/기기)은 ABAC으로 위임하는 하이브리드 모델** 도입 | 역할 개수 80% 이상 감축 및 세분화된 문맥 인식(Context-Aware) 인가 달성 |
| 단일 사용자가 기안과 결재 역할을 동시에 보유하여 **셀프 결재를 통한 횡령 및 비인가 자금 집행 사고** | **역할 부여 시 정적 직무 분리(SSD)를 강제하고, 세션 기동 시 동적 직무 분리(DSD) 교차 검증** | 상충 권한 집중으로 인한 내부 통제 실패 및 부정행위 100% 원천 차단 |

#### 한줄 요약
- 권한 재인증으로 잔존 권한을 회수하고, ABAC을 결합해 역할 폭발을 막으며, SoD로 부정을 방지한다.

## Ⅶ. 결론

- 엔터프라이즈 신원 및 접근 관리의 근간인 **RBAC 아키텍처**는 대규모 조직의 인가 거버넌스를 단순화하고 최소 권한을 보장하는 핵심 모델이며, 실무 구현 시 **NIST RBAC3 표준 기반 계층 상속 및 SSD/DSD 직무 분리 내재화**, **정기적 권한 재인증(Recertification) 체계 확립**, **역할 폭발 방지를 위한 ABAC과의 하이브리드 연계**를 결합하여 견고하고 확장성 높은 엔터프라이즈 접근 통제 프레임워크를 완성

#### 한줄 요약
- 사용자-역할-권한 3계층 매핑과 계층 상속 및 직무 분리(SoD)를 통해 안전한 RBAC 인가를 완성한다.
