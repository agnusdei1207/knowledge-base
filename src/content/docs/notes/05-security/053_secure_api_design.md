## Ⅰ. 개요

<details><summary>용어 설명</summary>

- **보안 API 설계 (Secure API Design)**: 누구나 찔러볼 수 있는 API 서버에 열쇠(인증), 방문증(인가), 출입 제한(Rate Limiting)을 다층으로 달아서, 해커가 남의 데이터를 빼가거나 서버를 팩트로 뻗게 만드는 걸 막는 설계 기법이다.

</details>

- 정의: API 서비스 전 구간에 걸쳐 채널 암호화, 호출자 신원 인증, 토큰 기반 권한 인가, BOLA(객체 탈취) 방지 및 무제한 호출 차단 통제를 설계 구현하는 팩트 보안 기법이다.
- 배경: 단순히 JWT 토큰이 유효한지만 검증하는 1차원적 방어로는, 교묘하게 타인의 객체를 조회하는 BOLA 공격이나 트래픽을 때려 붓는 자원 고갈(DoS) 공격을 팩트로 막아낼 수 없기 때문이다.

#### 한줄 요약

- 토큰 껍데기만 믿지 말고, 진짜 내 데이터가 맞는지(BOLA 방지)와 너무 자주 찌르는지(호출률 제한) 팩트로 따져라.

## Ⅱ. 특징

<details><summary>용어 설명</summary>

- **접근 토큰 (Access Token)**: "나 로그인한 사용자 맞아" 하고 들이미는 JWT 형태의 방문증이다. 위변조가 불가능하게 서명되어 있다.
- **BOLA 방지 (객체 수준 인가)**: 토큰이 정상이라도, "네가 요청한 7번 게시글이 진짜 네 글이 맞아?" 하고 자원 소유권을 매번 백엔드에서 팩트로 재확인하는 깐깐한 문지기다.
- **호출률 제한 (Rate Limiting)**: 해커가 1초에 만 번씩 API를 찔러서 서버를 죽이는 걸 막기 위해, "1분에 60번만 호출해!" 하고 멱살 잡고 팩트로 제어하는 속도 제한기다.

</details>

- **팩트 이중 인가 통제**: 게이트웨이(앞단)에서 호출자 신원을 인증하고, 백엔드(뒷단)에서 객체 소유권(BOLA 방지)과 기능 권한을 분리하여 팩트로 이중 통제한다.
- **팩트 토큰 및 채널 검증**: 접근 토큰(JWT) 내의 범위(Scope), 만료시간, 서명 무결성을 철저히 검증하고 클라이언트와 mTLS로 채널을 팩트 바인딩한다.
- **팩트 트래픽 폭주 차단**: API 게이트웨이 전단에 호출률 제한(Rate Limiting)과 페이로드 크기 제한을 걸어 가용성을 팩트 보호한다.

#### 한줄 요약

- 앞단(게이트웨이)에선 토큰 검사랑 속도 제한을 걸고, 뒷단(백엔드)에선 남의 데이터 훔쳐보는지 팩트로 잡는다.

## Ⅲ. 구조 및 구성요소

<details><summary>용어 설명</summary>

- **API 게이트웨이 (API Gateway)**: 외부 요청이 들어오는 단일 골목길(접점)에 서서, 토큰 껍데기가 맞는지 확인하고 1초에 너무 많이 쏘는 놈들을 팩트로 쳐내는 1차 방어막이다.
- **자원 서버 (Resource Server)**: 실제 데이터(DB)를 들고 있는 녀석으로, "이 데이터 진짜 얘 꺼 맞아?" 하고 BOLA(객체 인가)를 팩트로 2차 검증하는 백엔드다.

</details>

```text
[ API 팩트 방어 아키텍처 ]

[ 1. 클라이언트 요청 ] ── ("앱/웹에서 JWT 토큰 달고 데이터 달라고 팩트 요청함")
      │
      ▼
[ 2. API 게이트웨이 (1차 검증) ] ── ("토큰 위조 안 됐나 확인하고, 1초에 100번 넘으면 팩트 컷!")
      │
      ▼
[ 3. 인증/권한 서버 ] ── ("게이트웨이가 물어보면, '어 그 토큰 내가 발급한 거 맞아' 팩트 확인해줌")
      │
      ▼
[ 4. 자원 서버 (2차 검증 / BOLA) ] ── ("토큰 정상이라도, 남의 글(ID) 조회하려 하면 소유권 검사해서 팩트 컷!")
      │
      ▼
[ 5. 감사 및 로깅 (SIEM) ] ── ("누가 몇 번 API 찔렀는지, 권한 없어 거부당했는지 이력을 다 팩트로 남김")
```

| 구성요소 | 팩트 폭행 책임 | 비고 |
|:---|:---|:---|
| **클라이언트** | API 호출 시 OAuth 2.0 (PKCE) 기반의 **접근 토큰을 HTTP 헤더에 팩트로 달고 옴** | Client |
| **API 게이트웨이** | 단일 접점에서 **토큰 서명 검증 및 호출률 제한(Rate Limiting)을 팩트로 집행함** | Gateway |
| **인증/권한 서버** | 클라이언트 신원을 확인하고 위변조 불가능한 **JWT 토큰을 팩트로 발급함** | Auth |
| **자원 서버 (백엔드)** | 타인의 데이터를 빼가지 못하게 **객체 수준의 소유권(BOLA)을 2차 팩트 검증함** | Resource |
| **로깅 및 감사** | 해커의 비정상적인 호출 및 인가 거부 이력을 **SIEM에 보내서 팩트 추적함** | Audit |

#### 한줄 요약

- 게이트웨이는 방패(호출 제한/토큰 검사) 들고 막고, 자원 서버는 돋보기(객체 소유권 검사) 들고 팩트로 잡는다.

## Ⅳ. 흐름도

</details>

```text
[ 보안 API 호출 및 다층 팩트 통제 흐름 ]

┌──────────────────────────────┐
│ 1. [mTLS 채널 및 JWT 접근 토큰 팩트 접수]
│ ("클라이언트가 암호화된 통신(mTLS)으로 JWT 토큰을 팩트로 제출함")
└──────────────┬───────────────┘
               ▼
┌──────────────────────────────┐
│ 2. [입력 크기 및 호출률 통제 (Rate Limiting)]
│ ("게이트웨이: '너 1초에 100번 넘었네? 페이로드도 너무 커!' 트래픽 팩트 기각!")
└──────────────┬───────────────┘
               ▼
┌──────────────────────────────┐
│ 3. [기능 및 범위(Scope) 인가 팩트 대조]
│ ("읽기 전용 토큰(Read)으로 쓰기(Write) API 엔드포인트 호출 시 팩트 거부!")
└──────────────┬───────────────┘
               ▼
┌──────────────────────────────┐
│ 4. [객체 소유권 팩트 검증 (BOLA 방어)]
│ ("자원 서버: '토큰 주인이랑 네가 요청한 데이터 ID 주인이 다르잖아!' 소유권 팩트 차단!")
└──────────────┬───────────────┘
               ▼
┌──────────────────────────────┐
│ 5. [안전한 API 응답 및 팩트 감사 기록]
│ ("모든 깐깐한 검증을 통과한 찐 요청만 응답해 주고, 기록을 팩트로 남김")
└──────────────────────────────┘
```

### 동작 원리

1. 채널/토큰 검증: mTLS 상호 채널 형성 및 JWT 토큰의 서명 무결성, 만료 시간(exp) 팩트 확인.
2. 호출률 통제: API 게이트웨이에서 페이로드 규격 검증 및 호출률 제한(Throttling) 팩트 적용.
3. 기능 인가: 호출된 API 엔드포인트와 토큰에 부여된 권한 범위(OAuth Scope) 간 팩트 매칭 대조.
4. 객체 인가(BOLA): 자원 서버에서 쿼리 대상 객체 ID와 요청자 세션 간 소유권을 매번 팩트 대조 검증.
5. 로깅 및 감사: 모든 정상/거부 요청 이력과 이상 징후를 SIEM 및 보안 감사 로그로 팩트 보존.

#### 한줄 요약

- 토큰 까보고 $\to$ 너무 많이 쏘면 쳐내고 $\to$ 권한 넘으면 자르고 $\to$ 남의 거 보려 하면 팩트로 패버린다.

## Ⅴ. 종류 및 비교

<details><summary>용어 설명</summary>

- (상단 설명 참조)

</details>

| API 통제 지점 | **권한 위임 (OAuth / PKCE)** | **주장 전달 (JWT 토큰)** | **통신 신원 (mTLS)** |
|:---|:---|:---|:---|
| 팩트 폭행 비유 | **남한테 내 집(데이터) 열쇠 안전하게 깎아주기** | **위조가 불가능한 디지털 출입증(신분증)** | **서로 민증 까고 대화하는 철통 보안 터널** |
| 핵심 방어 방식 | 제3자 앱(카톡 등)이 내 자원에 접근할 수 있게 **표준화된 위임 프로세스로 팩트 통제함** | 서버(DB)를 안 뒤져도 서명(Signature)만 확인하면 **조작 여부를 바로 팩트 판별함 (무상태)** | 클라이언트와 서버 양방향으로 X.509 인증서를 검증하여 **암호화 채널을 팩트로 바인딩함** |
| 장점 및 특징 | 모바일/SPA 환경에서도 PKCE로 인가 코드를 보호하여 **가로채기(탈취)를 팩트로 막아냄** | 세션 관리가 필요 없어서, API 서버가 수백 대로 늘어나도 **확장성이 팩트로 뛰어남** | 단순 비밀번호 노출이나 토큰 탈취만으로는 **API를 팩트로 절대 호출할 수 없음** |
| 한계 및 문제점 | 개발자가 Scope(권한 범위)를 너무 넓게 줘버리면 **권한 오남용 사고가 팩트로 터짐** | 토큰이 한 번 털리면 만료(Exp) 전까지 **서버에서 강제로 죽이기가 팩트로 불가능함** | 인증서 발급, 갱신, 폐기(CRL/OCSP) 등 **PKI 인프라 관리 비용이 팩트로 어마어마함** |

#### 한줄 요약

- 권한 줄 땐 **OAuth**, 신분증은 **JWT**, 통신 터널은 **mTLS**로 팩트 통제하는 게 3대장이다.

## Ⅵ. 실무 고려사항 및 대책

<details><summary>용어 설명</summary>

- **OWASP API Top 10:2023**: 전 세계 API 해킹 사고 원인 탑 10. 그중 부동의 1위가 BOLA(남의 데이터 훔쳐보기)다.
- **BOLA (객체 수준 인가 결함)**: 내 토큰으로 정상 로그인해 놓고, URL 파라미터 숫자만 `user_id=7`에서 `user_id=8`로 살짝 조작해서 남의 개인정보나 영수증을 팩트로 털어가는 얍삽한 최악의 취약점이다.

</details>

| 장애/위험 요소 | 원인 분석 | 실무 대책 및 해결방안 | 기대 효과 |
|:---|:---|:---|:---|
| 토큰 검증 빡세게 했는데 **URL 파라미터 조작으로 남의 데이터가 팩트로 털림** | 인증(토큰)만 확인하고, 요청한 자원(객체)의 진짜 소유자가 맞는지 **인가 검증(BOLA 방어)** 을 팩트로 안 함 | **OWASP API Top 10** 기반, 자원 서버(백엔드)에서 매 요청마다 **객체 인가 소유권 팩트 재검증 강제** | 파라미터 변조를 통한 타인 정보 대량 탈취(BOLA) 취약점 팩트 완벽 소멸 |
| 해커가 자동화 툴로 API를 10만 번 찔러서 **메인 DB 서버가 팩트로 뻗음** | 인증된 사용자라도 단위 시간당 얼마나 호출할 수 있는지 **Rate Limiting 통제**를 팩트로 안 걸어둠 | API 게이트웨이 전단에 IP 및 토큰 주체별 **호출률 제한(Throttling) 및 크기 제한 팩트 적용** | 백엔드 자원 고갈(DoS) 및 무차별 대입(Brute-Force) 스캐닝 공격 팩트 원천 억제 |
| 모바일 앱에서 OAuth 로그인 중 **인가 코드를 악성 앱이 가로채서 팩트로 털림** | 모바일(Public Client) 특성상 Secret 키를 숨길 수 없는데, 옛날 방식의 OAuth를 무지성 팩트 사용함 | **IETF RFC 9700** 지침에 따라, 모바일/SPA 환경에서는 반드시 **OAuth 2.0 PKCE 확장 규격 팩트 강제** | 인가 코드 가로채기(Interception) 공격 무력화 및 토큰 발급 팩트 무결성 보장 |

#### 한줄 요약

- 남의 거 훔쳐보는 놈(BOLA) 막고, 무식하게 찌르는 놈(DoS)은 Rate Limit으로 팩트로 조져라.

## Ⅶ. 결론

<details><summary>용어 설명</summary>

- **API 통제 선택 기준 (API Control Selection Criteria)**: API는 상태가 없는(Stateless) 열린 문이므로, 껍데기만 믿지 말고 다층으로 팩트 검증해야 한다는 핵심 실무 사상.

</details>

- API 서비스는 경계가 모호하고 무상태(Stateless) 통신을 하므로, 외부 권한 위임은 **OAuth 2.0/PKCE**로, 채널 보안은 **mTLS**로, 과부하 차단은 게이트웨이의 **호출률 제한**으로, 데이터 탈취(BOLA) 방어는 백엔드의 철저한 **객체 인가**로 다층 팩트 억제하는 실무 기조를 확립함

#### 한줄 요약

- 외부 위임은 **OAuth/PKCE**, 과부하는 **호출률 제한**, 데이터 탈취는 **BOLA 검증**으로 팩트 컷해라.
