## Ⅰ. 개요

<details><summary>용어 설명</summary>

- **CSRF (교차 사이트 요청 위조)**: 내가 은행에 로그인해 있는 상태에서, 해커가 보낸 스팸 메일(링크)을 무심코 눌렀더니 내 아이디로 돈이 이체되거나 비밀번호가 바뀌는 낚시 해킹이다.

</details>

- 정의: 사용자가 자신의 의지와 무관하게, 공격자가 의도한 비승인 상태 변경(State-changing) 요청을 서버에 전송하도록 유도당하는 취약점이다.
- 배경: 브라우저가 특정 도메인으로 요청을 보낼 때 인증 정보인 '세션 쿠키'를 자동 첨부하는 편리한 맹점을 해커가 악용하여 서버를 속이기 때문이다.

#### 한줄 요약

- 브라우저가 쿠키를 알아서 실어 보내는 걸 악용해서, 해커가 내 권한을 도용해(위조) 명령을 내리는 공격이다.

## Ⅱ. 특징

<details><summary>용어 설명</summary>

- **Anti-CSRF 토큰**: 서버가 "진짜 네가 폼(Form) 버튼 눌러서 보낸 거 맞아?" 하고 확인하기 위해, 폼 안에 몰래 숨겨놓은 일회성 난수 암호다.
- **SameSite 쿠키**: "해커 사이트(남의 동네)에서 출발한 요청엔 우리 은행 쿠키를 실어 보내지 마!" 하고 브라우저한테 명령하는 보안 속성이다.

</details>

- **쿠키 자동 첨부 악용**: 희생자가 로그인된 상태(세션 유지)를 노려, 브라우저의 쿠키 자동 전송 기능을 악용한다. (사용자는 모름)
- **의도 검증 토큰 방어**: 상태 변경 HTTP 메서드(POST, PUT, DELETE) 요청 시, 폼에 숨겨둔 동적 CSRF 토큰(난수)을 서버가 수신하여 일치 여부를 철저한 검증한다.
- **서드파티 통신 차단**: SameSite 쿠키 속성을 (Lax/Strict)로 적용하여, 외부 도메인에서 날아오는 위조 교차 요청(Cross-Site)엔 브라우저가 쿠키를 빼버리게 만든다.

#### 한줄 요약

- 쿠키만 보고 믿지 말고, 일회성 암호(토큰)를 대조하거나 SameSite 속성으로 남의 동네 요청을 컷하는 게 핵심이다.

## Ⅲ. 구조 및 구성요소

<details><summary>용어 설명</summary>

- **Origin / Referer**: HTTP 헤더를 까서 "이 요청이 정상적인 네이버에서 출발한 거야, 아니면 해커 블로그에서 출발한 거야?"를 확인하는 발신처 검증 문지기다.
- **안전 메서드 (Safe Methods)**: GET 방식은 데이터 조회만 해야지, `GET /delete?id=1`처럼 DB 상태를 지우게 만들면 이미지 태그(`<img>`) 하나만으로도 무지성 털리게 된다.

</details>

```text
[ CSRF 철저한 방어 아키텍처 ]

[ 1. 상태 변경 경로 통제 ] ── ("돈 보내거나 비번 바꾸는 기능엔 GET 방식 절대 금지! POST를 강제함")
      │
      ▼
[ 2. 토큰 발행 및 철저한 검증 ] ── ("정상 폼 제출할 때, 일회성 난수(CSRF 토큰)가 맞는지 확인함")
      │
      ▼
[ 3. 출처(Origin) 철저한 검증 ] ── ("헤더 까보고 우리 은행 도메인에서 출발한 정상 요청인지 체크함")
      │
      ▼
[ 4. 쿠키 정책 (SameSite) ] ── ("해커 사이트에서 위조된 요청엔 브라우저가 은행 쿠키를 아예 안 주게 원천 차단!")
      │
      ▼
[ 5. 재인증 (최후의 보루) ] ── ("비번 바꾸거나 거액 송금 땐, OTP나 비밀번호 한 번 더 입력하라고 강제함")
```

| 구성요소 | 직관적 비교 책임 | 비고 |
|:---|:---|:---|
| **상태 변경 경로 통제** | 데이터가 바뀌는 핵심 기능엔 절대 GET을 쓰지 않고 **POST/PUT을 강제함** | Method |
| **Anti-CSRF 토큰** | 사용자의 진짜 의도를 확인하기 위해 **일회성 난수를 폼에 심고 서버가 철저한 검증함** | Token |
| **출처 헤더 (Origin)** | 해커 도메인에서 출발한 위조 요청인지 **HTTP 헤더 발신처를 까보고 컷함** | Origin |
| **SameSite 쿠키 속성** | 외부(타 도메인)에서 온 위조 요청엔 **브라우저가 인증 쿠키를 안 태워 보냄** | SameSite |
| **고위험 업무 재인증** | 토큰이 털려도 막을 수 있게, 치명적 연산엔 **비밀번호를 한 번 더 물어봄** | Re-Auth |

#### 한줄 요약

- 토큰 확인하고 $\to$ 출발지 주소 확인하고 $\to$ 쿠키 막고 $\to$ 불안하면 비밀번호 한 번 더 물어보는 4중 철저한 방어다.

## Ⅳ. 흐름도

<details><summary>용어 설명</summary>

- (상단 참조)

</details>

```text
[ CSRF 위조 요청 발생 및 철저한 방어 흐름 ]

┌──────────────────────────────┐
│ 1. [해커의 위조 폼 및 낚시 링크 배포]
│ ("해커가 '돈 100만 원 송금해라'는 폼을 숨긴 피싱 메일(이미지 링크)을 발송함")
└──────────────┬───────────────┘
               ▼
┌──────────────────────────────┐
│ 2. [희생자 클릭 및 세션 쿠키 자동 첨부]
│ ("은행 로그인된 피해자가 클릭! 브라우저가 은행 인증 쿠키를 자동으로 실어 보냄")
└──────────────┬───────────────┘
               ▼
┌──────────────────────────────┐
│ 3. [서버의 출처 및 토큰 철저한 검증 누락 시 (해킹 성공)]
│ ("서버가 쿠키만 보고 '오! 로그인 고객이네? 송금 승인!' 하고 유출 위험 (CSRF 발생)")
└──────────────┬───────────────┘
               ▼
    ┌──────────────────────────────┐
    │ 4. [방어 1: Anti-CSRF 토큰 불일치 차단]
    │ ("서버: '어? 근데 송금 폼에 난수 토큰이 없네? 해커 짓이구나!' 결제 차단!")
    └──────────────┬───────────────┘
                   ▼
    ┌──────────────────────────────┐
    │ 5. [방어 2: SameSite 속성에 의한 쿠키 누락]
    │ ("브라우저: '해커 사이트에서 은행으로 가는 요청엔 쿠키 안 줘!' 무력화")
    └──────────────────────────────┘
```

### 동작 원리

1. 위조 요청 생성: 해커가 `<iframe>` 또는 `<img>` 태그를 이용해 타깃 사이트의 상태 변경 요청(이체 등)을 조작함.
2. 자동 쿠키 첨부: 희생자가 타깃 도메인에 로그인된(세션이 살아있는) 상태일 때 공격이 구동됨.
3. 검증 누락 및 공격 성공: 서버가 '의도'를 묻지 않고 '쿠키(신분)'만 보고 비승인 요청을 인가 처리함.
4. 토큰 방어: 서버가 수신한 HTTP 요청에서 세션과 매칭되는 CSRF 토큰 난수를 대조하여 기각함.
5. 출처/쿠키 방어: HTTP Origin/Referer 헤더 불일치 및 SameSite 속성으로 외부 유입 요청의 권한을 박탈함.

#### 한줄 요약

- 로그인된 틈을 타서 몰래 버튼을 누르게 만드는 공격이므로, 토큰이나 출처 검사로 위조 여부를 감별해야 한다.

## Ⅴ. 종류 및 비교

<details><summary>용어 설명</summary>

- (상단 설명 참조)

</details>

| CSRF 방어 기법 | **Anti-CSRF 토큰** | **SameSite 쿠키 속성** | **출처(Origin/Referer) 검증** |
|:---|:---|:---|:---|
| 비유 및 핵심 특징 | **은행 창구에서 나눠주는 위조 불가 1회용 대기표** | **"남의 동네에서 온 택배엔 내 신분증(쿠키) 안 빌려줌"** | **"발신자 주소가 우리 동네가 맞는지 택배 송장 확인하기"** |
| 핵심 방어 방식 | 사용자가 정상 폼을 열 때 난수를 발급하고, **제출할 때 일치하는지 서버에서 검증함** | 타 도메인(Cross-Site)에서 발생한 교차 요청엔 **브라우저가 쿠키를 아예 안 실어 차단함** | HTTP 헤더를 까서 **요청이 출발한 발신 도메인이 우리 사이트가 맞는지 체크함** |
| 장점 및 특징 | 토큰이 털리지 않는 한 **가장 확실하게 사용자 본인 의도를 보장함 (정석)** | 서버 소스를 뜯어고칠 필요 없이 **쿠키 설정 한 줄 추가로 꿀가성비 철저한 방어 가능함** | 토큰 로직 구현 없이 **웹 서버(WAF/Proxy) 앞단 네트워크에서 빠르게 컷할 수 있음** |
| 한계 및 문제점 | XSS 방어에 뚫리면 해커가 **토큰값까지 스크립트로 같이 훔쳐 가서 털어버림** | 너무 옛날 구형 브라우저에서는 **SameSite 속성을 이해 못 해서 방어가 안 됨** | 프록시나 방화벽이 개인정보 보호 이유로 **헤더를 지우고 보내버리면 오탐 터짐** |

#### 한줄 요약

- 정석은 **토큰**, 가성비는 **SameSite**, 앞단 차단은 **출처 검사**다. 이 3가지를 섞어 써야 방패가 된다.

## Ⅵ. 실무 고려사항 및 대책

<details><summary>용어 설명</summary>

- **MITRE CWE-352**: 전 세계 취약점 사전에서 "CSRF는 이런 원리니까 토큰으로 막아라" 하고 지정해 둔 가이드다.
- **재인증 (Re-authentication)**: 토큰이고 뭐고 다 뚫렸을 때 최후의 보루로 "돈 보낼 거면 비밀번호 다시 쳐봐" 하는 철저한 방어벽이다.

</details>

| 장애/위험 요소 | 원인 분석 | 실무 대책 및 해결방안 | 기대 효과 |
|:---|:---|:---|:---|
| 세션 쿠키만 빡세게 검증했는데 **돈이 해커 통장으로 송금됨** | "쿠키 = 진짜 사용자"라고 믿어버리고, 진짜 본인 의지로 보낸 건지(의도 검증)를 안 함 | **MITRE CWE-352** 기반, 모든 상태 변경 폼(POST)에 **Anti-CSRF 토큰 철저한 검증 로직 강제** | 쿠키 자동 첨부를 악용한 위조 요청을 난수 토큰 불일치로 원천 차단 |
| 토큰 방어벽 다 쳐놨는데 **게시판 글에 이미지 링크 하나로 유출 위험** | 개발자가 귀찮다고 상태 변경(DB 수정/삭제) 로직을 **GET 메서드(URL 파라미터)** 로 대충 만듦 | 데이터 조회는 GET, 상태 변경은 POST/PUT/DELETE로 엄격히 분리하는 **안전 메서드 원칙 준수** | <img> 태그 하나만으로 무지성 실행되는 GET 방식의 CSRF 취약점 소멸 |
| CSRF 방어 완벽히 했는데 **XSS 취약점 터져서 토큰까지 같이 털림** | XSS로 자바스크립트가 실행되면, 해커가 폼 안의 CSRF 토큰값을 읽어서 위조 요청에 같이 담아버림 | 치명적 권한(송금, 비번 변경 등) 실행 직전 **OTP나 비밀번호 재인증(Re-auth) 강제** | XSS+CSRF 연계 공격을 당해도, 최종 단계의 사용자 본인 개입 요구로 최악의 피해 억제 |

#### 한줄 요약

- 상태 변경은 POST, 방어는 토큰(Token), 최후의 보루는 재인증(비밀번호 다시 묻기)이 팩트다.

## Ⅶ. 결론

<details><summary>용어 설명</summary>

- **사용자 의도 검증 (User Intent Verification)**: "서버야, 쿠키만 보고 인증 끝내지 말고 얘가 진짜 버튼을 누른 게 맞는지 토큰으로 체크 좀 해라" 하는 방어 핵심 사상이다.

</details>

- CSRF는 브라우저 쿠키 인증 세션의 맹점을 노린 공격이므로, 상태 변경 시 무조건 **Anti-CSRF 토큰**으로 사용자 의도를 확정하고, 쿠키 속성(**SameSite**)과 출처 검증(**Origin**)으로 외부 요청을 원천 차단하며, 치명적 연산 시 **재인증(Re-authentication)** 을 적용하는 다층 철저한 방어 기조를 확립함

#### 한줄 요약

- 쿠키만 믿지 말고 **토큰**으로 의도를 검증하고, **SameSite**로 외부 요청 원천 차단해라.
