## 미리 알고가기

- **CSRF (Cross-Site Request Forgery)**: [읽기: 씨에스알에프; 표기 이유: 영문 머리글자] 로그인된 브라우저의 자동 인증정보를 이용해 사용자가 의도하지 않은 요청을 보내는 공격
- **세션 쿠키**: [읽기: 세션 쿠키; 표기 이유: 한국어 통용어 표기] 로그인 상태를 식별하도록 브라우저가 같은 사이트 요청에 자동 첨부하는 값
- **CSRF 토큰**: [읽기: 씨에스알에프; 표기 이유: 영문 머리글자] 서버가 정상 화면에 발급하고 상태 변경 요청에서 일치 여부를 확인하는 예측 불가능한 값
- **Origin**: [읽기: Origin; 표기 이유: 한국어 통용어 표기] 웹 요청을 만든 출처의 프로토콜·호스트·포트 정보
- **Referer**: [읽기: Referer; 표기 이유: 한국어 통용어 표기] 현재 요청을 발생시킨 이전 페이지 주소 정보
- **SameSite**: [읽기: SameSite; 표기 이유: 한국어 통용어 표기] 다른 사이트에서 시작한 요청에 쿠키를 보낼 범위를 제한하는 쿠키 속성
- **안전 메서드**: [읽기: 안전 메서드; 표기 이유: 한국어 통용어 표기] GET·HEAD처럼 서버 상태를 변경하지 않아야 하는 HTTP 메서드
- **XSS (Cross-Site Scripting)**: [읽기: 엑스에스에스; 표기 이유: 영문 머리글자] 공격 스크립트가 대상 사이트의 브라우저 문맥에서 실행되는 취약점


- **흐름 기호(↓·→·X)**: [읽기: 흐름 기호; 표기 이유: 한글명 뒤 영문 원어 병기] 아래로·다음으로·차단으로 읽으며 순서·분기·금지를 나타냄
## Ⅰ. 개요

- **정의/개념**: 자동 인증정보로 상태 변경을 위조함
- **배경/필요성**: 서버는 로그인과 요청 의도를 구분해야 함

### 쉽게 이해하기 (학습용)

- CSRF는 로그인 쿠키가 자동 전송되는 점을 악용하므로 서버가 요청 의도까지 검증해야 한다.

## Ⅱ. 특징

- 브라우저의 자동 인증 전송을 악용해 요청을 위조한다.
- 쿠키로 인증하는 모든 상태 변경 경로가 대상이다.
- 안전 메서드에는 서버 상태 변경을 두지 않는다.
- XSS가 있으면 토큰 등 CSRF 방어를 우회할 수 있다.

### 쉽게 이해하기 (학습용)

- 토큰·출처 검사·SameSite 쿠키를 함께 적용하면 위조 요청이 상태 변경까지 도달하기 어렵다.

## Ⅲ. 구성요소 및 구조

| 설계 요소 | 설명 |
|:---|:---|
| 세션 쿠키 | 자동 첨부된 인증 상태 |
| 상태 변경 경로 | 자금·계정 등 요청 처리 |
| CSRF 토큰 | 요청 의도 검증 값 |
| 출처 정책 | Origin/Referer 검증 |
| 쿠키 정책 | SameSite/안전 메서드 적용 |

```text
[공격 사이트] ─위조 요청─> [사용자 브라우저]
                                │ 세션 쿠키 자동 첨부
                                ↓
                         [상태 변경 서버]
                         토큰·Origin·SameSite 검증
```

### 쉽게 이해하기 (학습용)

- 공격자 페이지가 피해자의 인증 상태를 빌려 요청해도 서버 검증기가 정상 화면에서 발급한 증거가 없으면 거부한다.

## Ⅳ. 원리 및 절차 흐름도

```text
경로식별
   ↓
메서드정리
   ↓
토큰적용
   ↓
출처정책
   ↓
회귀검증
```

| 절차 | 설명 |
|:---|:---|
| 경로식별 | 인증 필요한 상태 변경 경로 식별함 |
| 메서드정리 | 안전 메서드의 상태 변경 제거함 |
| 토큰적용 | 예측 불가능한 토큰 검증함 |
| 출처정책 | SameSite와 출처 정책 적용함 |
| 회귀검증 | 예외 경로 및 보안 정책 검증함 |

> 요약: 상태 변경 경로 식별 후 토큰 및 출처 정책 적용함

### 쉽게 이해하기 (학습용)

- 서버는 상태 변경 요청에서 토큰과 출처를 확인한 뒤에만 업무 처리를 수행한다.

## Ⅴ. 종류 및 비교

| 비교축 | CSRF 토큰 | SameSite 쿠키 | 출처 검증 |
|:---|:---|:---|:---|
| 핵심 특징 | 서버 발급 비밀값으로 요청 의도 확인 | 교차 사이트 요청의 쿠키 전송 제한 | Origin·Referer로 요청 출처 확인 |
| 적용 기준 | 의도 직접 검증 | 쿠키 전송 제한 | 출처 판정 시 |
| 주요 위험 | 토큰 노출·검증 누락·세션 미결합 | 브라우저·업무 호환성과 예외 설정 | 헤더 부재·프록시 처리 오류·허용목록 과다 |

> 요약: 토큰/SameSite/출처 신호로 위조 의도 판정함

### 쉽게 이해하기 (학습용)

- CSRF과 대안의 선택 기준을 비교함

## Ⅵ. 실무 사례

- 상태 변경 API는 미들웨어에서 검증
- 명시적 인증 헤더는 위험 모델 심사
- 교차 출처 요청 시 제한적 허용
- XSS 결함 독립적 제거

### 쉽게 이해하기 (학습용)

- 사례 1은 공통 미들웨어를 사용해 보호가 빠지는 상태 변경 API를 방지한다.
- 사례 2는 사용자 정의 인증 헤더가 브라우저에서 자동 전송되지 않는지 확인한다.
- 사례 3은 필요한 출처와 메서드만 허용해 교차 출처 요청 범위를 줄인다.
- 사례 4는 XSS가 토큰을 훔쳐 CSRF 통제를 우회하지 못하도록 별도로 제거한다.

## Ⅶ. 결론

- 상태 변경은 토큰·출처·쿠키 정책으로 검증함

### 쉽게 이해하기 (학습용)

- CSRF 방어는 토큰·출처 검사·쿠키 정책과 XSS 제거를 함께 운영해야 한다.
