## Ⅰ. 개요

<details><summary>용어 설명</summary>

- **CSRF(Cross-Site Request Forgery / CWE-352)**: 사용자가 특정 웹 서비스(예: 인터넷 뱅킹, 관리자 포털)에 인증되어 세션이 유지된 상태에서, 공격자가 구축한 악의적인 웹 페이지나 이메일 링크를 열람하도록 유도하여, 사용자의 브라우저가 해당 취약 서비스로 공격자가 의도한 비승인 상태 변경 요청(패스워드 변경, 금융 이체, 관리자 계정 생성)을 전송하게 만드는 교차 사이트 요청 위조 취약점.
- **자격증명 자동 전송 맹점(Ambient Authority Defect)**: 브라우저가 타 사이트에서 발생한 교차 출처(Cross-Origin) HTTP 요청이라도 대상 도메인의 유효한 세션 쿠키를 자동으로 헤더에 포함하여 전송함으로써, 서버가 사용자의 '실제 의도(Intent)'와 단순한 '인증 자격증명(Authentication)'을 구분하지 못하는 구조적 결함.

</details>

- 정의/개념: 브라우저의 무조건적 자격증명 자동 첨부 취약성을 차단하기 위해 **동기화 Anti-CSRF 토큰(Synchronizer Token Pattern)**, **SameSite 쿠키 속성(Lax/Strict)**, **Origin/Referer 헤더 출처 검증**, **고위험 작업 재인증(Step-Up Authentication)** 을 적용하는 **요청 무결성 검증 아키텍처**
- 배경/필요성: 비밀번호나 세션 쿠키가 클라이언트 스크립트에 노출되지 않더라도(XSS가 없더라도), 브라우저의 교차 도메인 요청 메커니즘을 악용하여 사용자의 인가된 권한으로 서버의 상태를 강제 변경할 수 있는 취약점을 원천 방어할 요구

#### 한줄 요약
- 동기화 Anti-CSRF 토큰과 SameSite 쿠키 및 출처 검증을 통해 브라우저 자동 자격증명 악용 요청을 차단한다.

## Ⅱ. 특징

<details><summary>용어 설명</summary>

- **Anti-CSRF 토큰(동기화 토큰 패턴 / Synchronizer Token Pattern)**: 사용자 세션 생성 시 서버가 암호학적으로 안전한 의사 난수(PRNG)를 생성하여 세션과 폼(Hidden Field) 또는 커스텀 헤더에 각각 바인딩하고, 상태 변경 요청 수신 시 두 토큰값의 일치 여부를 대조하는 방어 메커니즘 (동일 출처 정책 SOP로 인해 공격자는 토큰 탈취 불가).
- **SameSite 쿠키 속성 (IETF RFC 6265bis)**:
  - `SameSite=Strict`: 타 사이트에서 발생하는 모든 교차 출처 요청(링크 클릭 포함)에 대해 쿠키 전송 완전 차단.
  - `SameSite=Lax`: 안전한 상위 탐색(GET 링크 클릭)만 허용하고, 위험한 POST/PUT 및 서드파티 임베디드 요청에 대해 쿠키 전송 차단 (현대 브라우저 기본값).

</details>

- **인증 신분과 사용자 의도의 엄격한 분리**: 유효한 세션 쿠키가 첨부되었더라도 별도의 의도 증명 토큰이 없으면 요청 즉시 기각
- **안전한 HTTP 메서드(Safe Methods) 규약 강제**: RFC 7231에 따라 상태를 변경하는 모든 요청은 `POST`, `PUT`, `DELETE`로 한정하고 `GET`을 통한 상태 변경 금지
- **심층 방어 계층화**: SameSite 쿠키(브라우저 단독 차단) $\rightarrow$ Anti-CSRF 토큰(서버 로직 검증) $\rightarrow$ 재인증(금융/결제 최종 방어)

#### 한줄 요약
- 신분과 의도 분리, 안전한 HTTP 메서드 강제, Anti-CSRF 토큰, SameSite 쿠키 격리를 제공한다.

## Ⅲ. 구조 및 구성요소

<details><summary>용어 설명</summary>

- **Origin / Referer 헤더 검증**:
  - `Origin`: 요청이 출발한 프로토콜, 도메인, 포트 정보만 전송 (CORS 및 상태 변경 요청 시 기본 포함).
  - `Referer`: 요청이 발생한 전체 URL 경로를 전송.
  - $\rightarrow$ 서버 측에서 해당 헤더가 자사 화이트리스트 도메인과 일치하는지 엄격히 대조.

</details>

```text
[ 공격자 사이트 (attacker.com: 악성 숨은 폼 자동 제출) ]
                        │
                        ▼ (희생자 브라우저에서 target-bank.com으로 위조 요청 전송)
┌─────────────────────────────────────────────────────────────────────────┐
│ [ 1. 브라우저 쿠키 통제 계층 (Browser Cookie Policy) ]                 │
│  └─ `Set-Cookie: ...; SameSite=Lax`: attacker.com에서 온 POST 요청에    │
│     세션 쿠키 자동 첨부를 브라우저 레벨에서 원천 차단 (1차 방어)       │
└────────────────────────────────────┬────────────────────────────────────┘
                                     │ (만일 레거시 브라우저로 인해 통과 시)
                                     ▼
┌─────────────────────────────────────────────────────────────────────────┐
│ [ 2. 네트워크 및 헤더 검증 계층 (Origin / Referer Filter) ]             │
│  └─ `Origin: http://attacker.com` 확인 ➔ [ 화이트리스트 불일치로 즉시 거부 ]│
└────────────────────────────────────┬────────────────────────────────────┘
                                     │
                                     ▼
┌─────────────────────────────────────────────────────────────────────────┐
│ [ 3. 애플리케이션 토큰 검증 계층 (Anti-CSRF Token Interceptor) ]        │
│  ├─ 세션 토큰: `Session["csrf_token"] == "a7F9..."`                      │
│  ├─ 요청 본문: `Request.Form["csrf_token"] == (누락 또는 위조 난수)`    │
│  └─ [ 두 토큰 불일치 ➔ 403 Forbidden 응답 및 비정상 요청 즉각 기각 ]   │
└────────────────────────────────────┬────────────────────────────────────┘
                                     │ (고위험 금융/관리자 트랜잭션의 경우)
                                     ▼
┌─────────────────────────────────────────────────────────────────────────┐
│ [ 4. 고위험 업무 재인증 계층 (Step-Up / MFA Re-Authentication) ]        │
│  └─ OTP / 생체인증 / 비밀번호 재입력 확인 ➔ 최종 상태 변경 승인         │
└─────────────────────────────────────────────────────────────────────────┘
```

선의 의미: 공격자의 위조 요청이 SameSite 쿠키 필터 $\rightarrow$ Origin 헤더 검증 $\rightarrow$ Anti-CSRF 토큰 대조 $\rightarrow$ 단계별 재인증을 거쳐 완벽히 차단되는 심층 방어 구조

| 구성요소 | 핵심 책임 및 역할 | 비고 |
|:---|:---|:---|
| **SameSite 쿠키 엔진** | 타 도메인에서 시작된 크로스 사이트 요청에 대해 인증 쿠키 전송을 브라우저에서 차단 | RFC 6265bis |
| **Origin/Referer 필터** | HTTP 요청 헤더의 발신 도메인이 자사 신뢰 도메인과 일치하는지 네트워크 단에서 검증 | Origin Check |
| **Anti-CSRF 토큰 인터셉터**| 폼 또는 AJAX 헤더(`X-CSRF-Token`)의 일회성 난수와 서버 세션 난수 일치성 검증 | Token Validation|
| **안전 메서드 라우터** | `GET` 요청을 통한 데이터베이스 상태 변경(CUD)을 아키텍처 수준에서 원천 금지 | Safe Methods |
| **Step-Up 재인증기** | 패스워드 변경, 거액 이체 등 핵심 기능 수행 시 OTP 또는 재인증을 강제 | Step-Up Auth |

#### 한줄 요약
- SameSite 쿠키 엔진, Origin 필터, Anti-CSRF 토큰 인터셉터, 안전 메서드 라우터, Step-Up 재인증기가 결합한다.

## Ⅳ. 흐름도

<details><summary>용어 설명</summary>

- **동기화 토큰 패턴(Synchronizer Token)의 정상 vs 위조 요청 처리 과정**:
  1. **정상 요청**: 서버가 렌더링한 폼의 Hidden 토큰과 세션 토큰이 동일하므로 검증 성공.
  2. **위조 요청**: 공격자는 동일 출처 정책(SOP)으로 인해 피해자의 세션 토큰값을 읽을 수 없으므로, 토큰이 누락되거나 틀린 값을 전송하여 검증 실패.

</details>

```text
1. [정상 폼 요청] 사용자가 정상적으로 송금 페이지 접속 ➔ 서버가 암호학적 난수(`csrf_token=x8K9`)를 세션 및 폼에 주입
            │
            ▼
2. [공격자 함정 유입] 사용자가 타 탭에서 공격자의 악성 웹사이트(`attacker.com`)를 로드
            │
            ▼
3. [위조 요청 자동 발생] 악성 스크립트가 은행 URL(`POST /transfer`)로 금액 1,000만 원 이체 요청 전송
            │
            ▼
4. [SameSite 쿠키 차단] 최신 브라우저가 `SameSite=Lax` 정책에 따라 은행 세션 쿠키를 누락하고 전송
            │
            ├─ [쿠키가 첨부되어 서버에 도달한 경우: 2차 방어]
            ▼
5. [서버 토큰 인터셉터 검증]
    ├─ 서버가 세션의 `csrf_token`과 HTTP 요청 본문의 `csrf_token`을 비교
    └─ 공격자는 SOP로 인해 토큰값을 알 수 없으므로 `csrf_token` 누락/불일치 ➔ [403 Forbidden 차단]
            │
            ▼
6. [보안 로그 기록] 위조 요청 이벤트(Origin 불일치, CSRF 토큰 누락)를 SIEM으로 전송하고 트랜잭션 강제 중단
```

**동작 원리**

1. **상태 무결성 보증**: 폼 로드 시점에 일회용 토큰을 암호학적으로 생성하여 세션 저장소에 캐싱
2. **출처 격리 정책 집행**: 서드파티 컨텍스트에서 발행된 요청의 자격증명 자동 포함 거부
3. **토큰 불예측성 활용**: CSPRNG(암호학적 난수 생성기)를 사용하여 토큰 추측(Brute-force) 불가능화
4. **동일 출처 정책(SOP) 신뢰**: 타 도메인의 자바스크립트가 피해자 도메인의 DOM 토큰을 읽을 수 없음을 이용
5. **사전 차단 로깅**: 비정상 토큰 유입 시 즉시 컨트롤러 진입을 차단하고 침해 지표 기록

#### 한줄 요약
- 정상 폼 난수 발급, 악성 위조 요청 전송, SameSite 쿠키 차단, Anti-CSRF 토큰 대조, 403 차단 및 로깅 순으로 동작한다.

## Ⅴ. 종류 및 비교

<details><summary>용어 설명</summary>

- **CSRF 3대 방어 메커니즘 비교**: Anti-CSRF 토큰, SameSite 쿠키, 출처(Origin/Referer) 검증의 비교.

</details>

| 비교 항목 | Anti-CSRF 토큰 (Synchronizer) | SameSite 쿠키 속성 | Origin / Referer 헤더 검증 |
|:---|:---|:---|:---|
| **방어 메커니즘** | **세션 난수와 폼/헤더 토큰 일치성 검증** | **타 도메인 교차 요청 시 쿠키 전송 차단** | **요청 시작 발신 도메인 화이트리스트 대조** |
| **방어 집행 위치** | **웹 애플리케이션 백엔드 서버 로직** | **사용자 웹 브라우저 렌더링 엔진** | **웹 서버, WAF, 리버스 프록시 앞단** |
| **구현 및 운영 복잡도**| 보통~높음 (모든 상태 변경 폼/API 수정)| **매우 낮음 (웹 서버 쿠키 헤더 설정 1줄)**| **낮음 (공통 인터셉터/WAF 규칙 적용)** |
| **XSS 취약점 연계 시** | 취약 (XSS로 토큰 탈취 시 무력화) | **우회 불가 (타 도메인 출발 시 완벽 차단)**| 취약 (동일 출처 XSS 내부 요청 시 통과) |
| **레거시 호환성** | **완벽 (모든 브라우저 및 HTTP 환경 지원)**| 구형 브라우저(IE 등)에서 미지원 가능 | 프록시가 개인정보 보호로 헤더 삭제 시 오탐 |

#### 한줄 요약
- Anti-CSRF 토큰은 서버 로직의 정석, SameSite는 브라우저 단의 고효율 방어, Origin 검증은 앞단 게이트웨이 통제이다.

## Ⅵ. 실무 고려사항 및 대책

<details><summary>용어 설명</summary>

- **Double Submit Cookie 패턴**: 서버 세션에 토큰을 저장하지 않는 Stateless(REST API/JWT) 환경에서, CSRF 난수를 암호화 쿠키와 커스텀 요청 헤더(`X-CSRF-Token`)에 동시에 담아 클라이언트가 전송하게 하고 서버가 두 값의 일치성을 검증하는 아키텍처 패턴.

</details>

| 문제 | 대책 | 효과 |
|:---|:---|:---|
| 세션 쿠키만 검증하고 사용자 의도(Intent)를 검증하지 않아 **사용자 권한으로 비인가 금전 이체 사고 발생** | **MITRE CWE-352** 준수, 모든 상태 변경(POST/PUT)에 **Anti-CSRF 토큰 검증 인터셉터 의무 적용** | 브라우저 쿠키 자동 첨부를 악용한 위조 요청 100% 원천 차단 |
| 개발 편의를 위해 DB 수정/삭제 기능을 **`GET /delete?id=1` 형태로 구현하여 `<img>` 태그 하나로 침해** | **상태 변경 비즈니스 로직에 대해 POST/DELETE 메서드 강제 및 GET 요청 상태 변경 엄격 금지** | 이미지 태그나 링크 클릭을 통한 비인가 상태 변경 공격 경로 완전 소멸 |
| XSS 취약점과 연계되어 스크립트에 의해 **CSRF 토큰까지 함께 탈취되어 위조 요청이 승인되는 사고** | **중요 트랜잭션(비밀번호 변경, 이체) 직전 OTP/재인증(Step-Up Auth) 강제 및 XSS 선제 차단** | 다중 취약점 체이닝 공격 발생 시에도 사용자 본인의 명시적 개입으로 최종 피해 차단 |

#### 한줄 요약
- Anti-CSRF 토큰으로 의도를 검증하고, 안전한 메서드를 강제하며, 고위험 작업은 재인증으로 보호한다.

## Ⅶ. 결론

- 웹 애플리케이션의 신뢰 권한 모델을 악용하는 비승인 요청을 무력화하는 **CSRF 방어 아키텍처**는 트랜잭션 무결성 보호의 필수 요소이며, 실무 구현 시 **SameSite=Lax/Strict 쿠키 정책 전면 적용**, **동기화 Anti-CSRF 토큰 및 Double Submit Cookie 패턴 구현**, **Origin/Referer 헤더 출처 검증**, **고위험 작업에 대한 Step-Up 재인증 체계**를 결합하여 사용자 의도에 기반한 완전무결한 웹 트랜잭션 보안을 완성

#### 한줄 요약
- SameSite 쿠키와 Anti-CSRF 토큰 및 Step-Up 재인증을 결합하여 교차 사이트 요청 위조를 완벽히 차단한다.
