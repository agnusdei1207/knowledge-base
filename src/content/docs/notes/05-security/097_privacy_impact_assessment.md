## Ⅰ. 개요

<details><summary>용어 설명</summary>

- **개인정보 영향평가(Privacy Impact Assessment, PIA / PIPA 제33조)**: 대규모 개인정보파일을 운용하는 정보시스템을 신규 구축, 확장, 또는 변경하기 전에, 데이터의 수집부터 파기에 이르는 전 생애주기 처리 흐름(Data Flow)을 분석하여 정보주체의 프라이버시 침해 위험 요인을 사전에 식별하고, 시스템 오픈 전에 기술적·관리적 개선 대책을 도출·이행하는 법정 사전 예방 평가 제도.
- **사후 땜질식 패치 및 아키텍처 재작업 결함(Post-deployment Redesign Defect)**: 시스템 설계 및 코딩 완료 후 서비스 오픈 시점에 뒤늦게 데이터 암호화 미비, 비인가 제3자 제공, 접근통제 누락 등의 결함이 발견될 경우, 데이터베이스 스키마와 API 아키텍처 전체를 재설계해야 하므로 천문학적인 재개발 비용과 일정 지연이 발생하는 구조적 비효율.
- **Privacy by Design (설계 단계의 프라이버시 보호)**: 개발이 완료된 후 사후에 보안을 덧붙이는 것이 아니라, 기획 및 아키텍처 설계 초기 단계부터 데이터 최소화, 암호화, 접근통제, 가명화 원칙을 시스템 뼈대에 내재화하는 선제적 엔지니어링 방법론.
- **개인정보 흐름도 (Data Flow Diagram, DFD)**: 정보주체로부터 데이터가 수집되어 내부 데이터베이스에 저장되고, 부서 간 이용, 제3자 제공 API 연동, 백업 스토리지 복제, 최종 파기에 이르는 물리적·논리적 이동 경로를 시각적으로 전수 매핑한 도면.

</details>

- 정의/개념: 설계 전에 개인정보 침해 위험을 줄이는 **개인정보 영향평가**
- 배경/필요성: 대규모 개인정보 및 민감정보를 처리하는 정보시스템 구축 완료 후 운영 단계에서 암호화 미비, 비인가 연계, 접근통제 결함이 뒤늦게 발견될 경우, 데이터베이스 스키마와 대외 연계 API 전체를 재설계해야 하므로 천문학적인 재개발 비용과 시스템 납기 지연이 초래되는 구조적 비효율이 발생함에 따라, 개인정보 보호법 제33조 및 시행령 제35조(민감정보 5만 명, 연계 100만 명, 대규모 100만 명 등)에 기반하여 기획·설계 초기 단계부터 데이터 흐름도(DFD) 작성, 정량적 침해요인 도출, 개선계획(CAP) 수립 및 실물 이행 증적을 결속하는 개인정보 영향평가(PIA / Privacy by Design) 아키텍처를 도입하여 **시스템 오픈 전 프라이버시 침해 위험 선제 제거, 아키텍처 재작업 비용 최소화 및 법정 컴플라이언스 무결성**을 달성할 필요

#### 한줄 요약
- 시스템 구축 전 개인정보 흐름을 분석하여 유출 침해 위험을 사전에 식별하고 개선 대책을 이행한다.

## Ⅱ. 특징

<details><summary>용어 설명</summary>

- **개인정보 흐름도 (Data Flow Diagram, DFD)**: 정보주체로부터 데이터가 수집되어 내부 데이터베이스에 저장되고, 부서 간 이용, 제3자 제공 API 연동, 백업 스토리지 복제, 최종 파기에 이르는 물리적·논리적 이동 경로를 시각적으로 전수 매핑한 도면.

</details>

- **사전 예방성 및 비용 절감**: 시스템 릴리즈 이전 설계 단계에서 결함을 조기 발견하여 사후 아키텍처 재작업 비용을 최소화
- **실물 이행 증적 결속 (Actionable Evidence Binding)**: 단순 서류 권고에 그치지 않고, 소스코드 커밋, 방화벽 룰셋 설정, DB 암호화 스키마 등 구체적 실물 이행 증거를 검증
- **운용체계 변경 시 지속적 재평가 루프**: 외부 AI API 연동이나 대규모 테이블 변경 등 아키텍처 변경 발생 시 영향 범위를 재산정하여 잔여 위험을 지속 갱신

#### 한줄 요약
- 사전 예방적 위험 제거, 개인정보 흐름 전수 해부, 실물 이행 증적 결속, 운용 변경 시 지속 재평가를 제공한다.

## Ⅲ. 구조 및 구성요소

<details><summary>용어 설명</summary>

- **PIA 5대 핵심 평가 영역 및 구성요소**:
  1. **Assessment Scope (시행령 제35조)**: 대상 시스템, DB 테이블, 연계 API 경계 확정.
  2. **Data Flow Analyzer**: 수집·저장·이용·제공·파기 전주기 흐름도(DFD) 작성기.
  3. **Risk Scoring Engine**: 발생 가능성 $\times$ 비즈니스 영향도 $\times$ 기존 통제력 산정기.
  4. **Corrective Action Plan (CAP)**: 개선 과제, 담당자, 조치 기한, 완료 증적 명세서.
  5. **Residual Risk Governance**: CPO의 잔여 위험 수용 승인 및 감시 체계.

</details>

```text
┌─────────────────────────────────────────────────────────────────────────┐
│ [ 1. 대상 선정 및 범위 확정 계층 (Scope Definition: PIPA Art. 33) ]    │
│  ├─ 법정 의무 기준 확인: 민감정보 5만 명, 연계 100만 명, 대규모 100만 명 │
│  └─ [ 대상 시스템, 메인 DB 스키마, 외부 연계 API 엔드포인트 경계 확정 ] │
└────────────────────────────────────┬────────────────────────────────────┘
                                     │ (평가 범위 확정)
                                     ▼
┌─────────────────────────────────────────────────────────────────────────┐
│ [ 2. 데이터 흐름 해부 및 위험 분석 (Data Flow & Risk Scoring) ]         │
│  ├─ 개인정보 흐름도(DFD) 작성: 수집 ➔ 저장 ➔ 이용 ➔ 제공 ➔ 백업 ➔ 파기  │
│  ├─ 침해요인 발굴: 암호화 미비, 접근통제 누락, 불필요한 제3자 제공 식별│
│  └─ [ 위험도 산정: $Risk = \text{Threat} \times \text{Vulnerability} \times \text{Impact}$ ]│
└────────────────────────────────────┬────────────────────────────────────┘
                                     │ (고위험 요인 도출)
                                     ▼
┌─────────────────────────────────────────────────────────────────────────┐
│ [ 3. 개선 이행 및 잔여 위험 거버넌스 (Corrective Action & Sign-off) ]   │
│  ├─ 개선계획(CAP) 수립: DB 컬럼 암호화, API mTLS 적용, 파기 배치 구현  │
│  ├─ 실물 증적 검증: 소스코드 커밋, 방화벽 설정 캡처, 테스트 리포트 확인│
│  └─ [ CPO 잔여 위험 수용 서명 결재 ➔ 보호위원회에 최종 평가 보고서 제출]│
└─────────────────────────────────────────────────────────────────────────┘
```

선의 의미: 대상 선정 후 데이터 흐름 분석과 위험도 산정을 거쳐, 개선계획 이행과 실물 증적 확인 및 CPO 최종 승인을 통해 완료되는 구조

| 구성요소 | 핵심 책임 및 역할 | 비고 |
|:---|:---|:---|
| **평가 대상 선정기** | 시행령 제35조 법정 요건(5만/100만) 대조 및 공공·민간 평가 대상 경계 설정 | Scope Filter |
| **데이터 흐름 분석기** | 수집부터 파기까지의 데이터 이동 경로 및 숨겨진 백업/로그 흐름도(DFD) 전수 매핑 | DFD Engine |
| **위험도 산정 엔진** | 침해요인별 발생 가능성, 침해 심각도, 현재 보호 대책을 정량 계산하여 등급화 | Risk Scoring |
| **개선계획(CAP) 명세서** | 지적 사항별 기술적 대책, 조치 담당자, 완료 목표일, 검증 증빙 기준 1:1 매핑 | Action Plan |
| **잔여 위험 관리체계** | 개선 후 잔존하는 위험을 CPO가 최종 승인하고, 아키텍처 변경 시 재평가 가동 | Governance |

#### 한줄 요약
- 대상 선정, 데이터 흐름 분석, 위험도 산정, 개선계획 명세서, 잔여 위험 관리체계가 결합한다.

## Ⅳ. 흐름도

<details><summary>용어 설명</summary>

- **개인정보 영향평가 5단계 수행 절차**:
  1. 사전 준비 및 평가 대상 범위 확정
  2. 개인정보 흐름도(DFD) 작성 및 업무 현황 분석
  3. 침해요인 도출 및 정량적 위험도 평가
  4. 개선계획(CAP) 수립 및 시스템 코드/인프라 개선 이행
  5. 이행 확인, 잔여 위험 CPO 승인 및 결과서 보호위 제출

</details>

```text
1. [사전 준비 및 범위 확정] 신규 차세대 공공 시스템 구축 사업 착수 ➔ 대상 파일 100만 명 초과 확인 및 범위 락킹
            │
            ▼
2. [데이터 흐름도(DFD) 분석]
    ├─ 수집 화면부터 메인 DB, 통계 분석 마트, 백업 스토리지, 외부 연계 API까지 데이터 흐름도 도면화
    └─ [분석 결과: 대외 연계 API 구간에서 주민등록번호 평문 전송 결함 발견]
            │
            ▼
3. [침해요인 도출 및 위험도 평가]
    ├─ 취약점: 평문 전송 시 패킷 스니핑에 의한 대규모 개인정보 유출 가능성 높음
    └─ [위험도 매트릭스: 위험 등급 'High' 판정 ➔ 즉각 개선 과제 지정]
            │
            ▼
4. [개선조치 이행 및 실물 증적 확인]
    ├─ 개발팀이 대외 연계 API를 REST mTLS 1.3 및 AES-256 페이로드 암호화로 코드 수정
    └─ [보안팀이 소스코드 커밋 내역 및 패킷 덤프 암호화 캡처 실물 증거 검증 완료]
            │
            ▼
5. [CPO 승인 및 보호위 제출]
    ├─ 잔여 위험(표준 프로토콜 결함 등) CPO 최종 결재 승인
    └─ [개인정보보호위원회에 PIA 최종 결과 보고서 공식 제출 및 시스템 안전 릴리즈]
```

**동작 원리**

1. **사전 준비 및 범위 확정**
2. **데이터 흐름도(DFD) 분석**
3. **침해요인 도출 및 위험도 평가**
4. **개선조치 이행 및 실물 증적 확인**
5. **CPO 승인 및 보호위 제출**

#### 한줄 요약
- 실제 비용이 드는 구간은 평가 자체가 아니라 개선조치 이행 검증이므로, 설계 일정 안에 이행 기간을 확보하지 못하면 평가 결과는 서류로만 남는다.

## Ⅴ. 종류 및 비교

<details><summary>용어 설명</summary>

- **개인정보 영향평가(PIA) 의무 대상 4대 기준 (시행령 제35조)**:
  - 민감/고유식별정보: 5만 명 이상의 민감정보 또는 고유식별정보 처리 파일.
  - 연계 파일: 타 시스템과 연계하여 100만 명 이상의 정보가 구축·운용되는 파일.
  - 대규모 파일: 100만 명 이상의 정보주체에 관한 개인정보파일.
  - 운용체계 변경: 기존 평가를 받은 시스템의 소프트웨어/하드웨어 뼈대가 대폭 변경된 경우.

</details>

| 법정 의무 대상 유형 | 강제 발동 기준 (시행령 제35조) | 주요 핵심 위험 요인 | 중점 평가 포인트 |
|:---|:---|:---|:---|
| **민감/고유식별정보 파일** | **5만 명 이상**의 민감정보 또는 고유식별정보 | 사생활 침해 극심, 주민번호 도용 | **DB 컬럼 암호화, 접근기록 2년 보존** |
| **연계 및 결합 파일** | 내부/외부 시스템 연계로 **100만 명 이상** 구축 | 프로파일링 식별성 폭증, 권한 오남용 | **연계 구간 TLS 암호화, 목적 외 결합 방지** |
| **대규모 일반 파일** | **100만 명 이상**의 정보주체 개인정보 처리 | 대규모 해킹 유출, 랜섬웨어 파괴 | **망분리, 침입탐지(IPS), 권한 최소화** |
| **운용체계 변경 시스템** | 기존 평가 시스템의 **핵심 아키텍처/API 변경**| 신규 공격 표면 노출, 통제선 붕괴 | **신규 외부 API(AI 등) 연동 구간 검증** |

#### 한줄 요약
- 민감정보 5만 명, 연계 파일 100만 명, 대규모 파일 100만 명, 아키텍처 운용체계 변경 시 법정 의무 평가가 강제된다.

## Ⅵ. 실무 고려사항 및 대책

<details><summary>용어 설명</summary>

- **개인정보 보호법 제33조 및 시행령 제35조**: 공공기관의 장은 고위험 개인정보파일 구축·운용·변경 시 영향평가기관에 의뢰하여 평가를 수행하고 결과를 보호위원회에 제출하도록 명시.

</details>

| 문제 | 대책 | 효과 |
|:---|:---|:---|
| 공공 시스템 개발 사업 완료 후 오픈 직전에 법정 영향평가를 신청하여 **지적 사항 개선을 위한 재개발로 사업 오픈이 수개월 지연되는 사고** | **개인정보보호법 제33조** 준수, **기획 및 아키텍처 설계 초기 단계(Privacy by Design)에 PIA를 착수하여 개발과 개선을 병행** | 서비스 납기 지연 0% 달성 및 아키텍처 재작업 비용 90% 이상 절감 |

#### 한줄 요약
- Privacy by Design으로 지연을 막고, 아키텍처 변경 시 재평가를 수행하며, 실물 이행 증적으로 안전성을 확보한다.

## Ⅶ. 결론

- 시스템 사후 땜질식 보안 패치를 지양하고 기획·설계 초기부터 프라이버시 보호 조치를 뼈대에 내재화하는 **설계 기반 프라이버시(Privacy by Design / PIPA 제33조 / GDPR DPIA)의 최상위 사전 예방 공학 체계**로 확고히 자리 잡았으며, AI 파이프라인 데이터 거버넌스 및 클라우드 아키텍처 지속적 재평가로 진화하는 가운데, 실무 대규모 공공·엔터프라이즈 시스템 구축 시에는 **분석/설계 초기 단계 PIA 조기 착수를 통한 DFD 전주기 흐름 매핑, 민감정보 암호화 및 연계 API mTLS 강제 등 지적사항별 실물 소스코드/인프라 설정 증적 1:1 대조 검증, 외부 AI 모델 연동 및 DB 스키마 변경 시 영향평가 재평가(Change Re-assessment) 파이프라인 운영**을 결합하여 완벽한 개인정보 영향평가 신뢰성을 완성

#### 한줄 요약
- 설계 단계 조기 착수와 데이터 흐름 분석 및 실물 증적 기반 개선 이행을 통해 완벽한 PIA를 수행한다.
