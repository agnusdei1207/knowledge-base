## Ⅰ. 개요

<details><summary>용어 설명</summary>

- **마이크로 세그멘테이션 (Micro-Segmentation)**: 예전엔 외부 방화벽 밖만 막았는데, 이제 사내망 안쪽 서버들(VM, 컨테이너)끼리도 서로 못 믿어서 서버 한 대 한 대마다 방화벽(경계)을 씌우는 차세대 망 분리 기법이다. (데이터센터용 제로 트러스트)
- **측면 이동 (Lateral Movement)**: 해커가 사내망 내의 만만한 서버 하나를 털고 들어와, 같은 망이라는 이유로 다른 핵심 DB 서버까지 도미노처럼 털어먹는 내부 확산 공격이다.

</details>

- 정의: 데이터센터 내부의 서버, 가상 머신(VM), 컨테이너 단위로 네트워크 경계를 잘게 쪼개어, 승인된 1:1 트래픽만 허용하는 보안 통제 기법이다.
- 배경: 낡은 VLAN 망 분리는 같은 구역 안에서는 프리패스로 통신이 뚫려 있어, 서버 하나만 털려도 옆 서버까지 랜섬웨어가 확산(측면 이동)되기 때문이다.

#### 한줄 요약

- 같은 사내망에 있는 우리 편 서버끼리라도 서로 못 믿으니까, 각자 집 문 앞에 도어락 달고 허락된 통신만 해라.

## Ⅱ. 특징

<details><summary>용어 설명</summary>

- **동서 트래픽 (East-West Traffic)**: 외부에서 내부로 들어오는 통신(남북) 말고, 사내망 안에서 서버들끼리 서로 데이터를 주고받는 내부 트래픽이다.
- **기본 거부 (Default Deny)**: 명시적으로 허락한 통신(화이트리스트) 외에, 사내망 안의 우리 편끼리 하는 내부 통신이라도 무조건 다 막아버리는 철칙이다.
- **분산 집행 (Distributed Enforcement)**: 중앙에 큰 방화벽 하나 달랑 두는 게 아니라, 서버 1만 대 각각의 OS(커널) 안에 미니 방화벽을 깔아서 1만 곳에서 동시에 차단하는 거다.

</details>

- **신원 및 라벨 정책**: IP가 휙휙 바뀌는 클라우드 환경에 맞춰, IP 대신 '웹 서버', 'DB 서버' 같은 논리적 메타데이터(라벨) 신원을 기준으로 통제 정책을 부여한다.
- **기본 거부 및 동서 트래픽 제어**: 명시된 화이트리스트 외의 모든 내부 트래픽(동서 트래픽) 통신 시도를 제로 트러스트 관점에서 원천 원천 차단(Default Deny)한다.
- **분산 집행 아키텍처**: 중앙 방화벽에 트래픽 병목이 생기는 걸 막기 위해, 개별 호스트 OS나 프록시 단위에서 직접 패킷을 검사하고 써는 분산 집행을 적용한다.

#### 한줄 요약

- IP 대신 명찰(라벨) 달아주고, 허락된 거 빼곤 다 막아버리고(기본 거부), 중앙 방화벽 대신 각자 알아서 철저한 방어(분산 집행)한다.

## Ⅲ. 구조 및 구성요소

<details><summary>용어 설명</summary>

- **흐름 가시성 (Flow Visibility)**: 무턱대고 막기 전에 "사내 서버 수만 대 중 누가 누구랑 통신하고 있지?" 하고 며칠 동안 트래픽을 관찰해서 지도를 그려주는 기능이다.
- **정책 관리면 (Policy Control Plane)**: 가시성 지도를 보고 정책을 짠 뒤, 1만 대 서버에 깔린 미니 방화벽들에게 "이거대로 통제해라" 하고 지휘하는 중앙 통제탑 근거다.

</details>

```text
[ 마이크로 세그멘테이션 통제 구조 ]

[ 1. 자산 및 흐름 가시성 확보 ] ── ("누가 누구랑 통신하는지 며칠 동안 CCTV로 지도 그림")
      │
      ▼
[ 2. 신원 라벨(Label) 부여 ] ── ("너는 '웹서버', 너는 'DB서버' 명찰을 달아줌")
      │
      ▼
[ 3. 정책 관리면 (중앙 통제) ] ── ("웹서버 $\to$ DB서버 통신만 빼고 싹 다 막아라! 명령 하달")
      │
      ▼
[ 4. 분산 집행점 (개별 호스트) ] ── ("1만 대 서버 OS에서 각자 방화벽 켜서 실시간 원천 차단 중")
      │
      ▼
[ 5. 트래픽 철저한 검증 및 감사 ] ── ("막힌 놈들, 뚫은 놈들 로그 다 모아서 이상 징후 분석")
```

| 구성요소 | 책임 | 비고 |
|:---|:---|:---|
| **자산 / 흐름 가시성** | 차단 정책을 짜기 전에 **실제 서버들 간의 내부 통신 의존성 지도를 그려냄** | Visibility |
| **신원 / 라벨 (Label)** | 클라우드에서 자꾸 바뀌는 IP를 버리고 **'HR 서버', '운영망' 같은 메타데이터 명찰을 담** | Identity |
| **정책 관리면 (Control)** | 지도를 보고 수립한 화이트리스트 통제 룰을 **전체 서버에 중앙 집중적으로 쫙 뿌려줌** | Control Plane |
| **분산 집행점 (Data)** | 호스트 OS 커널(eBPF)이나 프록시 에이전트로 숨어서 **실제 패킷을 분산해서 썰어버림** | Data Plane |
| **워크로드 로그 검증** | 허용되거나 차단된 패킷을 SIEM으로 쏴서 **보안 구멍이나 우회 없는지 재검증함** | Audit |

#### 한줄 요약

- 통신 흐름 CCTV로 파악 $\to$ 명찰(라벨) 달기 $\to$ 중앙에서 룰 배포 $\to$ 서버 각자가 알아서 철저한 방어 시스템이다.

## Ⅳ. 흐름도

<details><summary>용어 설명</summary>

- (상단 참조)

</details>

```text
[ 동서 트래픽 분산 집행 및 통제 흐름 ]

┌──────────────────────────────┐
│ 1. [워크로드 라벨 및 정책 버전 검증]
│ ("통신을 시도하는 두 서버의 명찰(라벨)이 맞는지, 최신 룰이 깔렸는지 확인")
└──────────────┬───────────────┘
               ▼
┌──────────────────────────────┐
│ 2. [최소 흐름(Whitelist) 및 예외 규칙 판정]
│ ("웹 $\to$ DB 통신은 미리 허락된 규칙에 들어있는지 화이트리스트를 대조함")
└──────────────┬───────────────┘
               ▼
┌──────────────────────────────┐
│ 3. [기본 거부(Default Deny) 기반 연결 집행]
│ ("허락된 리스트에 단 1자라도 틀리면 얄짤없이 연결을 드롭(Drop) 시킴")
└──────────────┬───────────────┘
               ▼
┌──────────────────────────────┐
│ 4. [허용/차단 패킷 집행 결과 로그 생성]
│ ("어떤 정책 룰 때문에 막혔는지 IP, 포트, 라벨명까지 싹 다 기록함")
└──────────────┬───────────────┘
               ▼
    ┌──────────────────────────────┐
    │ 5. [과차단(장애) 평가 및 예외 경로 보정]
    │ ("어? 필수 사내 업무망이 막혀서 장애 났네?(과차단) 얼른 정책 다시 수정함")
    └──────────────────────────────┘
```

### 동작 원리

1. 라벨/정책 검증: 정책 관리면에서 동기화된 최신 보안 룰과 출발/도착지의 **라벨** 신원을 대조.
2. 예외 판정: 업무에 필수적인 최소 흐름(Whitelist)과 사전에 등록된 예외 정책 통과 여부를 계산.
3. 연결 집행: 화이트리스트에 없는 100% 모든 미인가 동서 트래픽을 즉각 **기본 거부(Default Deny)** 원천 차단.
4. 로그 생성: 개별 집행점이 허용/차단된 패킷의 맥락(라벨명, 정책 ID, IP)을 모아 감사 로그로 전송.
5. 오탐 보정: 룰 설정 오류로 인한 정상 서비스 차단(과차단) 및 직접 우회 경로를 실시간으로 모니터링 후 수정.

#### 한줄 요약

- 명찰(라벨) 확인 $\to$ 화이트리스트 체크 $\to$ 없으면 무조건 원천 차단 $\to$ 차단 로그 남기고 $\to$ 실수로 막은 건 다시 뚫어줌.

## Ⅴ. 종류 및 비교

<details><summary>용어 설명</summary>

- (상단 설명 참조)

</details>

| 망 분리 계층 | **VLAN / Subnet (기존망 L2/L3)** | **호스트 / 워크로드 정책 (L4)** | **서비스 메시 / Sidecar (L7 앱)** |
|:---|:---|:---|:---|
| 핵심 특징 | **같은 아파트 단지(망) 안이면 앞집 뒷집 문 열고 맘대로 돌아다님** | **각자 집(OS) 문마다 도어락 달아서 남의 집 못 가게 잠가버림** | **방문객한테 딱 화장실 1칸만 지정해주고 문지기(프록시)가 에스코트함** |
| 핵심 특징 | 스위치 장비로 큼지막한 네트워크 **구역 IP 경계를 나눔** | VM이나 서버 OS(커널)에 에이전트를 깔아서 **포트 단위로 1:1 핀포인트 통제함** | 쿠버네티스(k8s) 컨테이너 환경에서 Envoy 프록시 띄워 **API 단위로 통제함** |
| 장단점 / 한계 | 한 구역 뚫리면 그 안의 서버 수백 대가 **측면 이동 공격에 도미노처럼 털림** | 모든 서버에 무거운 에이전트 깔아야 해서 **운영 부하와 통제 사각지대가 생김** | 극강의 제로 트러스트 방어력이지만 설계가 미치도록 복잡하고 **통신 지연이 발생함** |

#### 한줄 요약

- 구역 나누는 **VLAN**, 서버마다 가두는 **호스트(L4)**, 앱끼리 묶는 **서비스 메시(L7)** 순으로 방어력이 상승한다.

## Ⅵ. 실무 고려사항 및 대책

<details><summary>용어 설명</summary>

- **관찰 모드 (Observation / Audit Mode)**: 마이크로 세그멘테이션 솔루션 달자마자 "다 막아!" 해버리면 기존 정상 서비스도 싹 끊겨서 초대형 장애 파티 나니까, 한두 달은 "누가 누구랑 통신하나" CCTV처럼 지켜만 보고 원천 차단은 안 하는 시뮬레이션 모드다.

</details>

| 장애/위험 요소 | 원인 분석 | 실무 대책 및 해결방안 | 기대 효과 |
|:---|:---|:---|:---|
| 클라우드랑 기존 온프레미스를 **어떻게 쪼개야 할지 몰라서 아키텍처가 꼬임** | 레거시 서버와 컨테이너 혼재 환경의 세그멘테이션 표준 레퍼런스 가이드가 없음 | **NIST SP 800-207** 및 **800-125B** 기반의 하이브리드 **데이터센터 제로 트러스트 설계** | 이기종 하이브리드 인프라 전체의 횡적 통제 수준 및 보안 표준화 달성 |
| 보안팀이 룰 켰더니 **사내 핵심 서비스 DB 통신 끊겨서 전사 장애 터짐** | 통신 흐름 가시성 파악도 안 된 상태에서 무식하게 '기본 거부(Default Deny)'부터 질러버림 | 정책 적용 초기엔 무조건 **관찰 모드(Observation)** 우선 적용 및 **단계적 원천 차단(Enforcement) 전환** | 미탐 트래픽 사전 식별 및 과차단(False Positive)으로 인한 서비스 중단(A) 예방 |
| 라벨(태그) 잘못 달아놔서 **내부 DB 서버가 웹에 뻥 뚫리는 보안 구멍 생김** | 관리자가 IP 대신 라벨을 수동으로 달다가 휴먼 에러로 신원 라벨링을 누락함 | 클라우드 자산 관리 툴(CSPM/CMDB) 연동을 통한 **자동 라벨링 및 주기적 감사 스크립트 가동** | 통제 공백 제거 및 휴먼 에러 차단으로 100% 라벨 기반 제어 정확도 확보 |

#### 한줄 요약

- 하이브리드는 **NIST 표준** 기반 묶고, 처음엔 무조건 **관찰 모드** 기반 장애 예방하고, 라벨링은 수작업 금지해라.

## Ⅶ. 결론

<details><summary>용어 설명</summary>

- **침해 도달 범위 (Blast Radius)**: 해커가 운 좋게 서버 1대를 털었을 때, 거기서부터 옆으로 퍼져나가서 망칠 수 있는 '최대 피해 폭발 반경' 근거다.

</details>

- 랜섬웨어의 고질적인 데이터센터 내부 횡적 확산을 끊어내기 위해, 너무 넓은 구역 분리인 **VLAN** 넘어, 서버마다 에이전트를 두는 **L4 호스트 정책** 및 컨테이너 레벨의 **L7 서비스 메시** 활용 혼합 적용하여, 해커의 **침해 도달 범위(Blast Radius)** 를 단일 워크로드로 고립시키는 실무 기조를 확립함

#### 한줄 요약

- 해커 털어도 그 서버 1대에서 끝나게, **L4 호스트 정책**이랑 **L7 서비스 메시** 섞어서 폭발 반경 가둬라.
