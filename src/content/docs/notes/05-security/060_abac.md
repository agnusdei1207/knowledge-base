## Ⅰ. 개요

<details><summary>용어 설명</summary>

- **ABAC (속성 기반 접근 제어)**: "과장님" 같은 직급(RBAC)뿐만 아니라, "지금이 퇴근 시간인가?", "회사 IP로 들어왔는가?", "회사 지급 기기인가?" 등 수많은 조건(속성)을 논리적으로 조합해서 그때그때 동적으로 권한을 팩트로 허락해 주는 모델이다.
- **RBAC (역할 기반 접근 제어)**: "이 사람은 영업팀이다" 하고 역할(명찰) 하나로 권한을 정적으로 팩트 매핑하는 기존 3계층 모델이다.

</details>

- 정의: 주체(Subject), 객체(Object), 행위(Action), 환경(Environment)의 4대 속성을 조건문(Policy)으로 엮어 실시간 동적 인가를 팩트 판정하는 메커니즘이다.
- 배경: 재택근무와 클라우드 시대에 역할(RBAC)만 가지고 통제하면 예외 권한이 수십만 개로 팩트 폭발하고, '위치'나 '시간' 같은 핵심 맥락을 팩트로 통제할 수가 없기 때문이다.

#### 한줄 요약

- 직급 하나만 보지 않고, 누구냐, 어디서냐, 몇 시냐, 무슨 기기냐를 종합적으로 스캔해서 실시간으로 문을 열어주는 팩트 기술이다.

## Ⅱ. 특징

<details><summary>용어 설명</summary>

- **환경 속성 (Environment Attributes)**: 낮 12시인지, 접속 IP가 해외인지 등 접속할 당시의 실시간 맥락을 팩트로 알려주는 정보. (ABAC의 꽃이다)
- **PDP (정책 결정점)**: "해외 IP면 컷, 사내 IP면 통과" 등 정책을 쥐고 있다가, 실제로 통과시킬지 말지 두뇌 역할을 팩트로 하는 결재 엔진이다.
- **PEP (정책 집행점)**: PDP가 "통과" 하면 문 열어주고, "거부" 하면 얄짤없이 사용자 접속을 팩트로 끊어버리는 기도(Gateway) 역할이다.

</details>

- **팩트 4대 속성 조합**: 주체, 객체, 행위, 환경 속성의 논리적 조합(AND/OR 조건문)을 통해 극도로 세밀한(Fine-Grained) 팩트 인가 통제를 구현한다.
- **팩트 표준 아키텍처 분리**: 문지기(PEP), 판사(PDP), 정보원(PIP), 법전(PAP) 등 논리 컴포넌트를 분리하여 아키텍처의 결합도를 팩트로 낮추고 확장성을 보장한다.
- **팩트 실시간 컨텍스트 반영**: 고정된 권한이 아니라 접속 당시의 속성 신선도(Freshness)를 실시간 팩트로 반영하여 제로 트러스트 수준의 동적 인가를 집행한다.

#### 한줄 요약

- 4대 속성을 조합하고, PEP-PDP-PIP 구조를 분리하여, 그때그때 상황에 맞는 제로 트러스트 팩트 통제를 때린다.

## Ⅲ. 구조 및 구성요소

<details><summary>용어 설명</summary>

- **PIP (속성 정보점)**: PDP가 판결을 내릴 수 있게 "이 사람 인사팀 DB 까보니 직급 대리 맞아요" 하고 속성 데이터를 팩트로 물어다 주는 실시간 정보원이다.
- **PAP (정책 저장소)**: 관리자가 "주말엔 시스템 접속 막아라" 같은 정책(법률)을 적어서 보관해 두는 도서관(DB)이다.

</details>

```text
[ ABAC 팩트 정책 평가 아키텍처 ]

[ 1. PEP (정책 집행점) ] ── ("요청 들어옴! 일단 트래픽 막고, PDP한테 허락받고 올게")
      │
      ▼
[ 2. PDP (정책 결정점) ] ── ("판결 내리려면 최신 정보가 필요해. PIP한테 팩트 물어봐야지")
      │
      ▼
[ 3. PIP (속성 정보점) ] ── ("인사 DB랑 MDM 뒤져보니 사내 기기 맞고 부장님 팩트 맞음!")
      │
      ▼
[ 4. PAP (정책 저장소) ] ── ("규칙(법전) 꺼내보니 '사내 기기 + 부장'이면 통과 팩트임!")
      │
      ▼
[ 5. PEP (정책 집행점) ] ── ("PDP가 통과래! API 문 열어준다 (또는 거절 시 접속 즉각 팩트 차단!)")
```

| 구성요소 | 팩트 폭행 책임 | 비고 |
|:---|:---|:---|
| **PEP (정책 집행점)** | 사용자의 접근 요청을 가로채서 PDP에 묻고 **최종 통과/차단 결과를 팩트로 집행함** | Gateway |
| **PDP (정책 결정점)** | 정책 규칙(PAP)과 속성(PIP)을 대조해서 **최종적으로 허용(Permit)/거부(Deny)를 팩트 판결함** | Engine |
| **PIP (속성 정보점)** | HR(인사)이나 MDM(기기관리) 등 권위자로부터 **실시간 속성 데이터를 팩트로 캐싱해 옴** | Data |
| **PAP (정책 저장소)** | 관리자가 XACML 기반으로 작성한 **접근 제어 정책 조건문을 보관하는 팩트 창고임** | Policy |
| **속성 권위자 (Authority)** | 속성의 원천 데이터(인사 발령 정보, 기기 상태)를 쥐고 있는 **진실의 팩트 원천 시스템임** | Source |

#### 한줄 요약

- PEP가 가로채고 $\to$ PDP가 판결하고 $\to$ PIP가 정보 캐오고 $\to$ PAP에서 법률 꺼내서 팩트 확인한다.

## Ⅳ. 흐름도

<details><summary>용어 설명</summary>

- (상단 참조)

</details>

```text
[ ABAC 실시간 속성 팩트 평가 및 인가 흐름 ]

┌──────────────────────────────┐
│ 1. [요청 속성 및 맥락(Context) 팩트 추출]
│ ("PEP가 HTTP 헤더나 IP, 토큰에서 환경/주체/객체/행위 정보를 팩트로 파싱함")
└──────────────┬───────────────┘
               ▼
┌──────────────────────────────┐
│ 2. [적용 정책 및 팩트 충돌 해결 규칙 로드]
│ ("PDP가 PAP 저장소에서 '지금 이 상황에 적용할 법(Policy)'을 꺼내옴")
└──────────────┬───────────────┘
               ▼
┌──────────────────────────────┐
│ 3. [권위자 조회 및 속성 TTL(신선도) 팩트 검증]
│ ("PIP가 인사 DB 찔러서 지금 이 직원이 방금 퇴사하지 않았는지 최신 상태를 팩트 확인함")
└──────────────┬───────────────┘
               ▼
┌──────────────────────────────┐
│ 4. [논리 조건 평가 및 기본 거부(Default Deny) 팩트 판정]
│ ("정책 조건이랑 100% 일치 안 하거나 에러 나면 무조건 다 막아버림 (Default Deny)")
└──────────────┬───────────────┘
               ▼
    ┌──────────────────────────────┐
    │ 5. [결정(Permit) 집행 및 감사 로그 팩트 기록]
    │ ("합격(Permit) 뜨면 PEP가 문 열어주고, 그 내역을 SIEM 등에 팩트로 적어둠")
    └──────────────────────────────┘
```

### 동작 원리

1. 속성 추출: **PEP**에서 들어오는 트래픽(HTTP, API)을 인터셉트하여 4대 속성 파라미터 팩트 구성.
2. 정책 선택: **PDP**가 **PAP**에서 대상 리소스 정책 및 충돌 규칙(Deny-Overrides 등) 팩트 로드.
3. 속성 검증: **PIP**가 외부 시스템(AD, HR)에서 캐싱한 **TTL** 기반 속성의 신선도 및 팩트 무결성 대조.
4. 조건 평가: **PDP**가 논리 수식을 계산하며, 미합치 및 에러 발생 시 즉시 **Default Deny** 팩트 집행.
5. 결과 집행: **PEP**가 결정(Permit/Deny)에 따라 트래픽을 흘려보내고 Audit Log를 팩트 기록.

#### 한줄 요약

- 속성 파싱 $\to$ 정책 꺼냄 $\to$ 실시간 정보 캐옴 $\to$ 평가해서 조금이라도 틀리면 거부 $\to$ 합격만 팩트 통과시킨다.

## Ⅴ. 종류 및 비교

<details><summary>용어 설명</summary>

- (상단 설명 참조)

</details>

| 접근 제어 모델 | **RBAC (역할 기반)** | **ABAC (속성 기반)** | **혼합 모델 (Hybrid RBAC-ABAC)** |
|:---|:---|:---|:---|
| 팩트 폭행 비유 | **"너 과장이야? ㅇㅋ 들어와" (단순 직급 확인)** | **"과장이고, 사내 IP고, 낮 2시고, 백신 켰네? ㅇㅋ" (조건 풀스캔)** | **"과장(RBAC)부터 거르고, 사내 IP(ABAC)인지 한 번 더 팩트 컷!"** |
| 핵심 통제 기준 | 사용자가 가진 **정적 직무(Role)를 기준으로 팩트 통제함** | 주체, 객체, 환경 등 수많은 속성을 **실시간 조건문으로 팩트 통제함** | 거시적인 역할(RBAC)로 1차 필터링하고, 세밀한 조건(ABAC)으로 **2차 팩트 검증함** |
| 장점 및 특징 | 직관적이고 시스템 구현이 쉬워서 **가장 많이 쓰이는 팩트 표준임** | 제로 트러스트 철학처럼 매우 세밀하고 **동적인 권한 통제가 팩트로 가능함** | 예외 권한이 수만 개로 쪼개지는 역할 폭발을 막고 **엔진 부하를 팩트로 줄여줌** |
| 한계 및 문제점 | 예외 권한 만들어주다 보면 **'역할 폭발' 나고 환경/시간 변수 통제가 팩트로 불가능함** | 정책(조건문) 짜는 게 너무 복잡하고, **매번 계산하는 PDP 성능 부하가 팩트로 큼** | 설계 난이도가 가장 높고, 기존 시스템 아키텍처가 매우 **무거워지는 팩트 단점이 있음** |

#### 한줄 요약

- 직무만 보는 **RBAC**, 조건 풀스캔하는 **ABAC**, 두 개를 섞어서 성능과 보안을 잡은 게 **혼합(Hybrid) 모델** 팩트다.

## Ⅵ. 실무 고려사항 및 대책

<details><summary>용어 설명</summary>

- **OASIS XACML 3.0**: ABAC 시스템끼리 통신할 때 서로 말이 통하도록, 정책 조건문(AND/OR)을 적는 표준 XML 문법 팩트 규격이다.
- **기본 거부 (Default Deny)**: 조건이 애매하거나, 판단 엔진(PDP) 에러가 나거나, 통신 불량일 때는 일단 무조건 접속을 팩트로 닫아버리는 철칙이다.

</details>

| 장애/위험 요소 | 원인 분석 | 실무 대책 및 해결방안 | 기대 효과 |
|:---|:---|:---|:---|
| ABAC 솔루션들끼리 말이 안 통해서 **정책 연동하다가 서버가 팩트로 뻗음** | 벤더사마다 정책 조건문(AND/OR)을 표현하는 언어(문법)가 제각각이라 이종 연동이 팩트로 안 됨 | **OASIS XACML 3.0** 및 JSON Profile 표준 문법 준수 및 **PEP-PDP 간 표준 API 팩트 강제** | 벤더 종속성(Lock-in) 탈피 및 상호운용성(Interoperability) 팩트 보장 |
| 직원이 어제 퇴사했는데 **정보 갱신 늦어져서 시스템에 버젓이 팩트 접속함** | PIP가 속성을 캐싱(Caching)해 놓은 시간이 너무 길어서, 옛날 정보(Stale Data)를 들고 팩트 판정함 | 속성 권위자(인사DB 등) 연동 주기 단축, **캐싱 TTL 최소화** 및 **기본 거부(Default Deny) 팩트 적용** | 속성 신선도(Freshness) 100% 확보 및 구형 데이터 인가 오류 팩트 원천 차단 |
| 매번 수많은 조건을 계산(PDP)하느라 **접속할 때마다 로딩이 수십 초씩 팩트로 걸림** | 단순한 접근 요청도 ABAC 엔진이 수백 개 조건을 풀스캔하느라 CPU 팩트 부하 발생 | 자주 쓰는 정책 캐싱(Policy Cache) 적용 및 **혼합 모델(RBAC로 1차 필터 후 ABAC 적용) 팩트 하드닝** | 실시간 인가 결정 시간(Latency) 최소화 및 대용량 트래픽 처리 팩트 성능 확보 |

#### 한줄 요약

- XACML 문법으로 통일하고, 캐싱 주기(TTL) 줄여서 퇴사자 잡고, 부하 심하면 RBAC 섞어서(Hybrid) 팩트로 막아라.

## Ⅶ. 결론

<details><summary>용어 설명</summary>

- **설명 가능성 (Explainability)**: "이 사람 왜 접속 짤렸어?" 물어볼 때, "XACML 3번 조항 때문에 IP가 막혀서 짤렸습니다" 하고 원인을 감사 로그로 명확히 팩트로 증명할 수 있는 성질이다.

</details>

- 제로 트러스트 보안의 핵심인 ABAC는 세밀한 동적 통제가 가능하나 구현 난이도와 성능 부하가 따르므로, **NIST SP 800-162** 가이드에 입각하여 **신뢰 속성** 파이프라인을 구축하고, 실무적으로는 직무(RBAC)와 결합한 **혼합 모델(Hybrid RBAC-ABAC)**을 적용하여 성능과 보안을 동시 팩트 달성하는 기조를 확립함

#### 한줄 요약

- 세밀한 통제는 **ABAC**가 팩트지만, 부하 빡세니까 **혼합(Hybrid) 모델**을 도입하고 **설명 가능성** 챙겨라.
