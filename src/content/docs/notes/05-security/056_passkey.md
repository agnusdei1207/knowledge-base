## Ⅰ. 개요

<details><summary>용어 설명</summary>

- **패스키 (Passkey)**: 털리기 쉬운 비밀번호를 아예 없애고, 내 지문과 애플/구글 클라우드 동기화(E2EE)를 통해 폰을 바꿔도 계속 편하게 쓸 수 있게 만든 차세대 디지털 팩트 열쇠다.
- **WebAuthn (웹 인증)**: 브라우저와 서비스 백엔드(RP 서버) 간에 패스키 자물쇠(공개키)를 주고받고, 지문 서명을 팩트로 검증할 수 있게 해주는 W3C 웹 API 규격이다.

</details>

- 정의: FIDO2/WebAuthn 표준 기반으로 사용자 비밀번호를 대체하며, 종단간 암호화(E2EE)를 통해 클라우드 계정(애플, 구글 등) 간 안전하게 팩트 동기화되는 디지털 자격증명 기술이다.
- 배경: 기존 비밀번호는 피싱이나 크리덴셜 스터핑 공격에 무방비로 팩트 유출되고, 기존 하드웨어 USB 보안키는 분실 시 복구가 너무 빡세서 대중화가 팩트로 실패했기 때문이다.

#### 한줄 요약

- 서비스마다 비밀번호 외울 필요 없이, 내 폰 지문 하나로 애플/구글 계정 타고 다니며 팩트 로그인하는 기술이다.

## Ⅱ. 특징

<details><summary>용어 설명</summary>

- **RP ID (도메인 바인딩)**: 내 패스키는 진짜 'naver.com'에서만 반응하고, 가짜 피싱 사이트인 'naaver.com'에서는 브라우저가 알아채고 아예 지문 창을 안 띄워주는 구조적 팩트 방어막이다.
- **동기화 패스키 (Synced Passkey)**: 아이폰에서 지문으로 패스키 만들면 아이클라우드 타고 내 맥북이나 아이패드에서도 바로 로그인되게 해주는 꿀가성비 팩트 열쇠다.
- **기기 결합 패스키 (Device-bound)**: 폰 밖으로 절대 열쇠를 못 빼가게 보안 칩셋(TPM)에 박아버려서, 편의성은 버려도 보안성은 끝판왕인 기업용 팩트 열쇠다.

</details>

- **팩트 피싱 원천 차단**: RP ID와 브라우저 접속 도메인(Origin) 결속을 통해 중간자 피싱 사이트의 서명 탈취 공격을 구조적으로 팩트 차단한다.
- **팩트 멀티 기기 동기화**: 소비자 편의를 극대화한 동기화 패스키(Apple/Google)와 최고 보안 등급을 요하는 기기 결합 패스키를 서비스 목적에 맞게 팩트 지원한다.
- **팩트 생체/물리 사용자 검증**: 패스키를 쓰려면 스마트폰의 생체인식(UV)이나 PIN 입력 등을 거쳐야만 로컬에서 키 사용을 팩트로 승인해 준다.

#### 한줄 요약

- 피싱 사이트에선 안 먹히고, 폰 바꾸면 클라우드 타고 자동으로 넘어오고, 내 지문 아니면 열쇠를 팩트로 못 돌린다.

## Ⅲ. 구조 및 구성요소

<details><summary>용어 설명</summary>

- **인증자 (Authenticator)**: 내 스마트폰 보안 영역(Secure Enclave/TPM)에서 개인키를 안전하게 보관하고 지문 인증 시 팩트 서명해 주는 하드웨어/소프트웨어 컴포넌트다.
- **복구 경로 (Account Recovery Flow)**: 패스키가 동기화된 폰, 태블릿을 싹 다 잃어버렸을 때, "나 진짜 본인 맞다"고 증명하고 계정을 다시 살려내는 빡센 팩트 절차다.

</details>

```text
[ 패스키(Passkey) 팩트 동작 및 동기화 아키텍처 ]

[ 1. RP 서버 (서비스 백엔드) ] ── ("네이버가 도전값(난수) 주고 공개키 서명해 오라고 브라우저에 팩트 지시함")
      │
      ▼
[ 2. 플랫폼 및 브라우저 ] ── ("가짜 도메인인지 팩트 확인하고, OS한테 패스키 꺼내달라고 호출함")
      │
      ▼
[ 3. 사용자 검증 (지문/얼굴) ] ── ("폰 주인이 맞는지 지문이나 PIN으로 기기 로컬에서 팩트 확인함")
      │
      ▼
[ 4. 인증자 (보안 칩 / 개인키) ] ── ("지문 통과하면 내부 개인키로 서명 생성! (또는 클라우드로 팩트 E2EE 동기화)")
      │
      ▼
[ 5. 동기화 및 복구 체계 ] ── ("새 폰 사서 로그인하면 아이클라우드/구글 타고 패스키 열쇠가 팩트로 따라옴")
```

| 구성요소 | 팩트 폭행 책임 | 비고 |
|:---|:---|:---|
| **RP 서버 (백엔드)** | "가짜 말고 진짜면 서명해와!" 하고 **도전값을 내고 나중에 공개키로 팩트 검증함** | RP |
| **플랫폼 및 브라우저** | 주소창(Origin) 까보고 피싱 컷트하며, 사용자에게 **패스키 선택 창(UI)을 팩트로 띄워줌** | Platform |
| **사용자 검증 (UV)** | 스마트폰 생체인식(Face ID/지문)이나 **PIN 번호를 통해 키 사용을 팩트로 승인함** | UV |
| **인증자 (보안 영역)** | 스마트폰 칩셋 내에서 해커가 못 훔치게 **개인키를 관리하고 전자 서명을 팩트 생성함** | Auth |
| **클라우드 동기화/복구** | 기기를 잃어버리거나 바꿨을 때 **E2EE 암호화 망으로 패스키를 팩트 동기화/복구해 줌** | Sync |

#### 한줄 요약

- 서버가 문제 내면 $\to$ 브라우저가 사이트 짭인지 거르고 $\to$ 폰에 지문 찍어서 서명 제출하고 $\to$ 폰 바꾸면 동기화된다.

## Ⅳ. 흐름도

<details><summary>용어 설명</summary>

- (상단 참조)

</details>

```text
[ 패스키 로그인 및 팩트 서명 대조 흐름 ]

┌──────────────────────────────┐
│ 1. [도전값(Challenge) 및 RP ID 팩트 생성]
│ ("서버가 Replay(재전송) 방어용 일회성 난수를 클라이언트로 팩트 발송함")
└──────────────┬───────────────┘
               ▼
┌──────────────────────────────┐
│ 2. [원본(Origin) 및 도메인(RP ID) 팩트 검증]
│ ("브라우저가 가짜 피싱 주소인지 팩트로 까보고, 맞으면 패스키 목록 UI 띄움")
└──────────────┬───────────────┘
               ▼
┌──────────────────────────────┐
│ 3. [생체/PIN 기반 사용자 검증(UV) 팩트 확인]
│ ("사용자가 화면에 뜬 '로그인하시겠습니까?' 창에 지문을 팩트로 찍음")
└──────────────┬───────────────┘
               ▼
┌──────────────────────────────┐
│ 4. [보안 칩 개인키 전자 서명 팩트 생성]
│ ("지문 통과! 폰 안의 개인키가 도전값을 암호학적으로 팩트 서명함")
└──────────────┬───────────────┘
               ▼
┌──────────────────────────────┐
│ 5. [RP 서버 공개키 기반 서명 팩트 대조 및 승인]
│ ("서버가 DB에 있는 공개키(자물쇠)로 서명을 풀고, 정상이면 로그인 팩트 승인!")
└──────────────────────────────┘
```

### 동작 원리

1. 도전값•RP ID 생성: RP 서버에서 재전송 및 피싱 방지용 Challenge와 허용 RP ID를 팩트 정의.
2. 도메인 바인딩 검증: 브라우저 런타임 상에서 현재 접속 Origin과 RP ID의 동일성을 팩트 대조.
3. 사용자 검증(UV): 디바이스 로컬 상에서 지문/얼굴 등 생체인식이나 PIN 입력을 팩트 집행.
4. 개인키 서명: 디바이스 내부 인증자(개인키)로 Challenge 문맥에 대한 전자서명을 팩트 생성.
5. 공개키 검증: RP 서버에서 등록된 패스키 공개키로 서명의 정당성을 팩트 판정 후 세션 발급.

#### 한줄 요약

- 난수 던짐 $\to$ 피싱 도메인 확인 $\to$ 지문 인식 $\to$ 개인키 서명 $\to$ 서버에서 공개키로 팩트 합격 판정.

## Ⅴ. 종류 및 비교

<details><summary>용어 설명</summary>

- (상단 설명 참조)

</details>

| 패스키 보관 및 팩트 통제 | **동기화 패스키 (Synced Passkey)** | **기기 결합 패스키 (Device-bound)** | **휴대형 보안키 (Hardware Key)** |
|:---|:---|:---|:---|
| 팩트 폭행 비유 | **클라우드 타고 알아서 폰, 태블릿, PC로 복사되는 마법 열쇠** | **이 폰에서 꺼낼 수 없게 칩셋에 순간접착제로 붙여놓은 팩트 열쇠** | **지갑에 넣고 다니다가 USB나 NFC로 찍는 실물 쇳덩어리 팩트 열쇠** |
| 핵심 저장 및 복원 방식 | 구글/애플 클라우드 계정을 통해 종단간 암호화(E2EE) 상태로 **다른 기기들에 자동 팩트 동기화됨** | 특정 기기 내장 보안 칩(TPM 등)에 저장되며 **외부 유출이나 클라우드 동기화가 팩트로 불가능함** | 별도의 USB 장치 안에 물리적으로 보관되며 **다른 기기나 클라우드로 복사/동기화 팩트 불가능함** |
| 장점 및 특징 | 기기를 잃어버려도 새 폰 사서 로그인하면 패스키가 다 살아나서 **소비자 편의성이 팩트로 압도적임** | 폰이 해킹당해서 파일이 통째로 털려도 **이 열쇠만큼은 절대 밖으로 팩트 반출 안 됨 (사내 보안용)** | PC나 폰을 아예 믿을 수 없는 최악의 악성코드 감염 환경에서도 **완벽한 하드웨어 격리로 팩트 안전 보장됨** |
| 한계 및 문제점 | 애플/구글 클라우드 계정 자체가 털리면 **동기화된 내 모든 열쇠가 해커 기기로 팩트 복사됨** | 기기를 잃어버리거나 고장 나면 **새 폰에서 열쇠를 처음부터 빡세게 다시 팩트 등록해야 함** | 사용자가 USB 키를 항상 들고 다녀야 하고 **분실 시 물리적으로 복구가 팩트로 노답임** |

#### 한줄 요약

- 일반인 편의성은 **동기화 패스키**, 사내 철통 보안은 **기기 결합 패스키**, 극한 환경은 **실물 보안키** 쓴다.

## Ⅵ. 실무 고려사항 및 대책

<details><summary>용어 설명</summary>

- **NIST SP 800-63B-4**: 패스키 같은 새로운 디지털 자격증명 관리 시스템을 도입할 때, 안전하게 클라우드 동기화나 계정 복구를 어떻게 해야 하는지 팩트로 가이드하는 글로벌 표준이다.
- **자격 증명 폐기 (Credential Revocation)**: 예전 폰을 당근마켓에 팔아버리거나 잃어버렸을 때, RP 서버에서 "저 폰에 있던 공개키는 이제 팩트 무효야!" 하고 날려버리는 관리 기능이다.

</details>

| 장애/위험 요소 | 원인 분석 | 실무 대책 및 해결방안 | 기대 효과 |
|:---|:---|:---|:---|
| 동기화 패스키 썼는데 **내 구글/애플 클라우드 계정이 해킹돼서 열쇠 싹 다 팩트로 털림** | 구글/애플 계정에 설정된 MFA(2차 인증)가 허술해서, 클라우드 계정 뚫릴 시 패스키 연쇄 동기화 팩트 발생 | **NIST SP 800-63B-4** 지침에 따라 동기화 클라우드 계정 자체의 **강력한 MFA 및 비밀번호 보안 팩트 하드닝** | 패스키 무단 복제(Cloning) 및 해커의 다른 디바이스로 불법 동기화/재전송 공격 팩트 원천 차단 |
| 패스키만 믿고 비밀번호 아예 없앴는데 **폰 하나 달랑 잃어버리니까 로그인을 팩트로 아예 못함** | 유일한 인증 수단(단일 디바이스)만 믿고, 다수 기기 동기화나 안전한 **복구 경로(Recovery)** 를 팩트로 안 만들어둠 | 다수 디바이스(폰, 패드, PC)에 패스키 사전 등록 유도 및 **동등 보증 수준의 안전한 계정 복구 절차 팩트 수립** | 기기 분실로 인한 영구 잠금(Lockout) 방지 및 허술한 복구(Backdoor) 경로 우회 팩트 철통 방어 |
| 직원 퇴사했는데 **퇴사자 개인 폰(동기화 패스키)으로 회사 시스템에 버젓이 팩트 접속함** | 퇴사자 처리 시, 사내 시스템(RP 서버)에 등록된 해당 직원의 패스키 공개키를 무효화(Revocation) 팩트로 안 함 | 퇴사/기기 분실 신고 시 RP 서버(백엔드)에서 해당 **패스키 공개키(자격 증명)를 즉각 팩트 폐기(Revoke) 처리** | 인가되지 않은 구형 기기나 악의적 퇴사자 기기를 통한 내부 시스템 무단 접근 팩트 완벽 차단 |

#### 한줄 요약

- 애플/구글 계정 털리지 않게 2차 인증 빡세게 걸고, 폰 잃어버렸을 때 쓸 복구 수단 만들고, 퇴사자 폰은 팩트 폐기해라.

## Ⅶ. 결론

<details><summary>용어 설명</summary>

- **전환 완성 조건 (Passkey Migration)**: 위험한 비밀번호를 아예 제거하는 동시에, 패스키 등록/복구 경로에 기존 로그인만큼 빡센 본인확인을 동등하게 팩트로 적용하는 보안 가이드라인이다.

</details>

- 비밀번호 없는(Passwordless) 인증 체계로의 완벽한 **전환 완성 조건**에 입각하여, B2C 서비스는 편의성 극대화를 위해 **동기화 패스키**를 적용하고, B2E/B2B 보안 환경은 유출이 불가능한 **기기 결합 패스키**를 채택하되 철저한 **자격 증명 폐기** 및 엄격한 복구 절차를 다층으로 연동하는 팩트 실무 기조를 확립함

#### 한줄 요약

- 대고객은 편한 **동기화 패스키**, 사내망은 빡센 **기기 결합 패스키**로 가고 폰 잃어버리면 팩트로 즉각 폐기해라.
