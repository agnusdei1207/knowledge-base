## Ⅰ. 개요

<details><summary>용어 설명</summary>

- **SABSA(Sherwood Applied Business Security Architecture)**: 사업 위험을 보안 구현•지표까지 추적하는 방법론이다.

</details>

- 정의/개념: 사업 목표와 위험을 보안 구현•운영 지표까지 연결하는 **SABSA**이다.
- 배경/필요성: 제품 중심 설계로는 통제와 사업 가치•위험을 연결할 수 없다.

#### 한줄 요약

- **사업 속성**에서 구현·운영 지표까지 추적

## Ⅱ. 특징

<details><summary>용어 설명</summary>

- **비즈니스 속성**: 보호 목표를 사업 언어와 측정 가능한 성공 기준으로 표현한 속성이다.
- **추적성**: 사업 요구•위험•통제•구성•지표를 양방향으로 연결하는 성질이다.

</details>

- **비즈니스 속성**을 측정 가능한 보호 목표로 만든다.
- 계층•질문으로 누락과 정합성을 점검한다.
- 요구•통제•지표의 **추적성**을 확보한다.

#### 한줄 요약

- 상위 사업 이유가 제품 설정•운영 지표까지 이어지고 아래 결과로 다시 설명돼야 한다.

## Ⅲ. 구조 및 구성요소

<details><summary>용어 설명</summary>

- **SABSA 계층**: 요구를 맥락•개념•논리•물리•운영으로 구체화하는 구조이다.

</details>

```text
SABSA 계층
├─ 맥락•사업 요구
├─ 개념•보안 원칙
├─ 논리•보안 서비스
├─ 물리•컴포넌트 구현
└─ 운영•측정•개선
```

| 구성요소 | 책임 |
|:---|:---|
| 맥락•사업 요구 | 목표•자산•위험•이해관계자 |
| 개념•보안 원칙 | 속성•정책•서비스 모델 |
| 논리•보안 서비스 | 기술 독립 기능•정보 흐름 |
| 물리•컴포넌트 구현 | 표준•제품•구성•배치 |
| 운영•측정•개선 | **SABSA 계층**의 절차•지표 환류 |

#### 한줄 요약

- 사업 요구를 원칙·논리 기능을 거쳐 **구현 구체화**

## Ⅳ. 흐름도

<details><summary>용어 설명</summary>

- **양방향 추적**: 상위 사업 요구를 구현•지표로 내려 연결하고 운영 결과를 다시 사업 위험으로 올려 설명하는 방식이다.
- **사업 속성•목표 임계값 정의**: 보호 가치•측정값•책임을 사업 언어로 정하는 단계이다.
- **위험•보안 요구•추적 관계 도출**: 위협•영향에서 보안 요구와 연결 관계를 만드는 단계이다.
- **논리 서비스•제품 구성 설계**: 기술 독립 보안 기능을 제품•배치로 구체화하는 단계이다.
- **통제 성과•운영 증거 측정**: 절차와 지표로 통제 실효성 자료를 수집하는 단계이다.
- **잔여위험•변경 영향 평가**: 운영 결과에 따라 갱신할 요구•통제•구성을 판정하는 단계이다.

</details>

```text
사업 목표•보호 가치
   │
   ▼
1. 사업 속성·목표 임계값 정의
   │
   ▼
2. 위험·보안 요구·추적 관계 도출
   │
   ▼
3. 논리 서비스·제품 구성 설계
   │
   ▼
4. 통제 성과·운영 증거 측정
   │
   ▼
5. 잔여위험·변경 영향 평가
   ├─ 임계값 미달 ──► 요구•통제•구성 갱신
   └─ 임계값 충족 ──► 운영 유지
```

### 동작 원리

1. 사업 속성·목표 임계값 정의: 보호 가치 설정
2. 위험·보안 요구·추적 관계 도출: 요구 연결
3. 논리 서비스·제품 구성 설계: 기능·구현 연결
4. 통제 성과·운영 증거 측정: 실효성 자료 수집
5. 잔여위험·변경 영향 평가: 갱신 대상 결정

#### 한줄 요약

- 지표 미달 시 **요구·통제·구성 갱신**

## Ⅴ. 종류 및 비교

<details><summary>용어 설명</summary>

- **TOGAF(The Open Group Architecture Framework)**: 전사 아키텍처 전환 프레임워크이다.
- **Zachman 프레임워크**: 관점별 아키텍처 산출물 분류 체계이다.
- **ADM(Architecture Development Method)**: TOGAF의 아키텍처 개발 방법이다.

</details>

| 아키텍처 프레임워크 | SABSA | TOGAF | Zachman |
|:---|:---|:---|:---|
| 적용 기준 | 사업 위험과 보안 구현 연결 | 전사 업무•기술 전환 | 관점별 산출물 분류 |
| 핵심 특징 | **SABSA**의 위험 추적 | **TOGAF**의 **ADM** 변화 관리 | **Zachman 프레임워크**의 관점 분류 |
| 한계 | 문서 과잉 | 보안 위험 깊이 부족 | 실행 절차 연결 약함 |

> 요약: 보안 위험, 전사 전환, 산출물 분류의 초점이 다르다.

#### 한줄 요약

- SABSA는 보안•위험에 깊고 TOGAF와 Zachman은 더 넓은 전사 구조를 다룸이 핵심이다.

## Ⅵ. 실무 고려사항 및 대책

<details><summary>용어 설명</summary>

- **SABSA 매트릭스**: 여섯 계층과 육하원칙으로 산출물을 점검하는 틀이다.
- **ISO(International Organization for Standardization)**: 국제표준화기구이다.
- **IEC(International Electrotechnical Commission)**: 국제전기기술위원회이다.
- **IEEE(Institute of Electrical and Electronics Engineers)**: 전기전자 기술표준을 개발하는 학회이다.
- **ISO/IEC/IEEE 42010**: 아키텍처 관점•뷰•모델 표현 표준이다.
- **전사 전환 연계**: TOGAF ADM으로 보안 설계와 전환 일정을 연결하는 방식이다.

</details>

| 문제 | 대책 | 효과 |
|:---|:---|:---|
| 모든 매트릭스 칸을 채우면 문서만 증가할 수 있음 | **SABSA 매트릭스** 선택 적용 | 속성•통제•지표 정렬 |
| 보안 아키텍처 단독 추진 시 전사 변혁 로드맵과의 정렬 복잡성 | **전사 전환 연계** 적용 | ADM•전환 계획 통합 |
| 이해관계자별 관심사가 섞이면 설명이 모호해짐 | **ISO**•**IEC**•**IEEE**의 **ISO/IEC/IEEE 42010** 적용 | 관점•관심사 명확화 |

#### 한줄 요약

- 금융 서비스 가용성 목표를 비즈니스 속성으로 정하고 보안 서비스•제품 구성•운영 지표까지 연결한다.

## Ⅶ. 결론

<details><summary>용어 설명</summary>

- **사업 가치 입증**: 보안 구현과 운영 성과가 어떤 사업 목표•위험에 기여하는지 연결해 설명하는 활동이다.
- **위험 추적•전사 전환 결합**: SABSA 위험 추적과 TOGAF 전환을 결합하는 방식이다.

</details>

- **사업 가치 입증**을 위해 **위험 추적•전사 전환 결합**을 적용한다.

#### 한줄 요약

- 보안 투자가 어떤 사업 가치를 지키는지 구현과 운영 결과로 계속 증명해야 한다.
