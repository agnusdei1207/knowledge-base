## Ⅰ. 개요

<details><summary>용어 설명</summary>

- **MFA(Multi-Factor Authentication, 다중 인증)**: 사용자의 신원을 증명하기 위해 **지식(Something you know: 패스워드, PIN)**, **소유(Something you have: 스마트폰, 하드웨어 보안키, OTP 토큰)**, **고유 존재(Something you are: 지문, 안면, 홍채 등 생체인식)** 중 서로 다른 2개 이상의 독립적 인증 범주(Factor)를 요구하는 신원 검증 체계.
- **단일 지점 인증 붕괴(Single Factor Failure Defect)**: 지식 기반의 비밀번호 단독 인증 체계는 크리덴셜 스터핑(Credential Stuffing), 키로깅, 피싱, 무차별 대입 공격에 의해 자격증명이 단 한 번만 유출되어도 전체 계정이 장악되는 치명적 보안 취약성을 내포.

</details>

- 정의/개념: NIST SP 800-63B 표준에 입각하여 **인증 보증 레벨(AAL1~3) 정의 $\rightarrow$ 암호학적 기기 등록 바인딩 $\rightarrow$ 독립 요소 교차 검증 $\rightarrow$ 피싱 저항성(FIDO2) 통제 $\rightarrow$ 비상 계정(Break-glass) 거버넌스** 를 집행하는 **신원 및 접근 관리(IAM) 아키텍처**
- 배경/필요성: SMS OTP나 단순 모바일 푸시 승인은 SS7 통신망 가로채기, SIM 스와핑, 역프록시(AitM: Adversary-in-the-Middle) 피싱 도구(Evilginx), 무차별 푸시 스팸을 통한 인증 피로(MFA Fatigue) 공격에 의해 우회되므로 암호학적 피싱 저항성 인증 체계 구축 요구

#### 한줄 요약
- 지식/소유/생체의 독립 2요소 결합과 FIDO2 피싱 저항성 기술을 통해 계정 장악 위협을 근원 차단한다.

## Ⅱ. 특징

<details><summary>용어 설명</summary>

- **피싱 저항성(Phishing-Resistant Authentication)**: 역프록시 중간자 공격자(AitM)가 가짜 피싱 사이트를 구축하여 사용자의 1차/2차 자격증명을 탈취하려 해도, 인증 프로토콜(FIDO2/WebAuthn)이 브라우저와 도메인(Origin) 간의 암호학적 채널 바인딩을 강제하여 가짜 도메인에 대한 서명 생성을 원천 차단하는 성질.
- **인증 피로 공격 방어(MFA Fatigue & Number Matching)**: 공격자가 야간에 수백 번의 푸시 승인을 연속 발송하여 사용자가 무심코 승인하도록 유도하는 공격을 방어하기 위해, PC 로그인 화면에 표시된 2자리 난수를 모바일 앱에 직접 타이핑하도록 요구하는 대책.

</details>

- **요소 간 엄격한 카테고리 독립성 (Factor Independence)**: 동일 카테고리 내 중복(예: 패스워드 + PIN 번호)은 단순 2단계 인증(2-Step)일 뿐 진정한 MFA로 불인정
- **NIST AAL(Authenticator Assurance Level) 체계화**:
  - **AAL1**: 단일 요소 인증 (패스워드 등)
  - **AAL2**: 다중 요소 인증 (소프트웨어 OTP, 푸시 알림)
  - **AAL3**: 하드웨어 기반 암호학적 피싱 저항성 다중 인증 (FIDO2 하드웨어 키)
- **동등 보증 수준의 복구 프로세스**: 인증기 분실 시 헬프데스크 우회(Social Engineering)를 차단하기 위해 초기 등록과 동일한 수준의 엄격한 신원 확인 집행

#### 한줄 요약
- 요소 독립성, NIST AAL3 피싱 저항성, 번호 일치(Number Matching), 동등 수준 복구 거버넌스를 제공한다.

## Ⅲ. 구조 및 구성요소

<details><summary>용어 설명</summary>

- **비상 계정(Break-glass Account)**: MFA 인증 서버 전체 장애나 IdP(Okta, Azure AD) 다운 시에도 클라우드 루트 계정이나 인프라에 접근하여 복구 작업을 수행할 수 있도록, 하드웨어 보안 모듈(HSM) 및 물리적 금고에 봉인 관리되는 최후의 비상 접근 계정.

</details>

```text
[ 사용자 (브라우저 / 클라이언트 앱) ]
                 │ (1. ID / 패스워드 1차 입력 ➔ 지식 요소 검증)
                 ▼
┌─────────────────────────────────────────────────────────────────────────┐
│ [ 1. 신원 공급자 (IdP: Identity Provider / MFA 서버) ]                 │
│  ├─ AAL 요구 레벨 평가 ➔ [ 2차 인증 챌린지(Nonce 난수) 발행 ]           │
│  └─ 도메인 Origin 바인딩 검증 준비 (`rp_id = enterprise.com`)           │
└────────────────────────────────────┬────────────────────────────────────┘
                                     │ (2. 암호학적 챌린지 전송)
                                     ▼
┌─────────────────────────────────────────────────────────────────────────┐
│ [ 2. 하드웨어/모바일 인증기 (FIDO2 Authenticator / TPM / Secure Enclave)]│
│  ├─ 생체인증(지문/FaceID) ➔ 3차 생체 요소(Inherence) 검증                │
│  ├─ 보안칩 내부 비공개키(Private Key)로 챌린지+Origin 데이터 전자서명  │
│  └─ [ 개인키는 하드웨어 외부 유출 불가 ➔ 서명된 Assertion 응답 반환 ]  │
└────────────────────────────────────┬────────────────────────────────────┘
                                     │ (3. 공개키 암호 서명 검증)
                                     ▼
┌─────────────────────────────────────────────────────────────────────────┐
│ [ 3. 인증 완료 및 접근 제어 계층 (Access Control & Session) ]           │
│  ├─ 서명 검증 성공 ➔ AAL3 인증 세션 토큰(JWT) 발급                     │
│  └─ 고위험 트랜잭션 발생 시 ➔ [ Step-Up 재인증 트리거 ]                 │
└─────────────────────────────────────────────────────────────────────────┘
```

선의 의미: 1차 지식 입력 후 IdP의 챌린지를 받아 하드웨어 보안칩에서 생체 검증 및 서명을 거쳐 안전한 AAL3 세션을 발급받는 구조

| 구성요소 | 핵심 책임 및 역할 | 비고 |
|:---|:---|:---|
| **AAL 정책 엔진** | 접속 대상 시스템의 데이터 등급(기밀/일반)에 따라 AAL2/AAL3 인증 요건 강제 | NIST SP 800-63B |
| **인증기 등록 관리기** | 최초 발급 시 사용자의 신원을 대면/eKYC로 확정하고 하드웨어 공개키 바인딩 | Authenticator Reg|
| **MFA 검증 엔진** | 소유 기반 토큰(TOTP) 및 비대칭 전자서명(WebAuthn)을 독립적으로 검증 | Verification |
| **번호 일치 모듈 (Number Matching)**| 푸시 인증 시 콘솔의 2자리 난수 입력을 강제하여 MFA Fatigue 공격 무력화 | Fatigue Defense |
| **비상 계정 (Break-glass)**| IdP 장애 시 업무 연속성을 위해 물리적/암호학적으로 분리 보관되는 비상 접근 키 | Resilience |

#### 한줄 요약
- AAL 정책 엔진, 인증기 등록기, MFA 검증 엔진, 번호 일치 모듈, 비상 계정(Break-glass)이 결합한다.

## Ⅳ. 흐름도

<details><summary>용어 설명</summary>

- **AitM(Adversary-in-the-Middle) 피싱 vs FIDO2 방어 메커니즘**:
  - **AitM 공격**: 사용자가 가짜 도메인(`evil-bank.com`)에 접속하면 공격자가 정상 도메인(`bank.com`)에 대리 접속하여 OTP 번호를 가로챔.
  - **FIDO2 방어**: 브라우저가 실제 접속 도메인(`evil-bank.com`)을 서명 데이터(`ClientDataJSON`)에 강제 포함하므로, `bank.com` 서버가 서명 검증 시 도메인 불일치로 즉각 기각.

</details>

```text
1. [인증 요청] 사용자가 포털에 ID/PW 입력 ➔ IdP가 1차 인증 통과 후 FIDO2 2차 인증 트리거
            │
            ▼
2. [도전값 발행] IdP가 암호학적 1회용 난수(Challenge)와 기대 도메인(`rp_id=company.com`) 클라이언트에 전송
            │
            ▼
3. [생체 검증 및 하드웨어 서명]
    ├─ 스마트폰/보안키가 사용자 생체(지문)를 내부 Secure Enclave에서 검증
    └─ 브라우저가 제공한 실제 접속 도메인과 Challenge 값을 개인키로 디지털 서명
            │
            ▼
4. [IdP 서명 및 도메인 대조]
    ├─ IdP가 등록된 사용자의 공개키로 서명 무결성 검증
    └─ 요청 패킷의 `rp_id`가 `company.com`과 정확히 일치하는지 대조 (AitM 피싱 즉각 기각)
            │
            ▼
5. [안전 세션 인가] 최종 MFA 통과 ➔ 고유 세션 발급 및 관리자 콘솔 접근 허용
```

**동작 원리**

1. **지식 요소 1차 분리**: 1차 패스워드 검증과 2차 하드웨어 챌린지 검증의 독립적 프로세스 수행
2. **비밀키 격리 보장**: 인증 개인키가 네트워크를 타거나 OS 메모리에 노출되지 않고 전용 칩 내부에서만 연산
3. **도메인 결속(Channel Binding)**: 피싱 프록시 서버의 도메인 위장을 암호학적 서명 검증 레벨에서 원천 차단
4. **인간 실수 상쇄**: 사용자 부주의로 가짜 사이트에 접속하더라도 브라우저와 하드웨어가 공격을 자동 무력화
5. **폐쇄 루프 감사 추적**: 인증 실패 횟수 및 비정상 위치 시도를 실시간 SIEM 위험 평가 엔진에 피드백

#### 한줄 요약
- 인증 요청, 도전값 발행, 하드웨어 생체 서명, 도메인 결속 검증, 안전 세션 인가 순으로 동작한다.

## Ⅴ. 종류 및 비교

<details><summary>용어 설명</summary>

- **MFA 3대 인증 방식 비교**: SMS/이메일 OTP(AAL2 레거시), 모바일 푸시 승인(AAL2), FIDO2/WebAuthn(AAL3 피싱 저항성)의 비교.

</details>

| 비교 항목 | SMS / 이메일 OTP (AAL2 레거시) | 모바일 푸시 번호 일치 (AAL2) | FIDO2 / Passkey (AAL3) |
|:---|:---|:---|:---|
| **인증 메커니즘** | 통신망 평문 6자리 난수 전달 | 클라우드 푸시 팝업 + 2자리 난수 타이핑 | **공개키 암호화 기반 하드웨어 비대칭 서명** |
| **피싱 저항성 (Phishing)** | **전혀 없음 (AitM 피싱에 100% 탈취)** | 없음 (피싱 사이트에서 가로채기 가능) | **완벽 보장 (도메인 바인딩 암호학적 차단)** |
| **주요 취약점 및 위협** | **SIM 스와핑, SS7 도청, 이메일 탈취** | 사용자 실수에 의한 오승인 (Number Matching 필요)| 기기 분실 시 복구 프로세스 설계 난이도 |
| **사용자 편의성** | 보통 (문자 확인 후 6자리 수동 입력) | **높음 (스마트폰 화면 숫자 터치)** | **최상 (기기 지문/FaceID 터치 1회로 완료)** |
| **NIST 800-63B 권고** | **중요 시스템 사용 전면 금지 권고** | 일반 엔터프라이즈 환경 허용 | **금융, 인프라, 관리자 계정 필수 권고** |

#### 한줄 요약
- SMS는 피싱에 취약, 푸시는 편의성 중심, FIDO2/Passkey는 완벽한 피싱 저항성을 제공한다.

## Ⅵ. 실무 고려사항 및 대책

<details><summary>용어 설명</summary>

- **SS7(Signaling System No. 7) 도청 취약점**: 이동통신사 간 로밍 및 통화 연결에 사용되는 글로벌 통신 프로토콜의 설계 결함을 악용하여 공격자가 원격에서 SMS 문자 메시지를 가로채는 통신망 취약점.

</details>

| 문제 | 대책 | 효과 |
|:---|:---|:---|
| SMS OTP를 2차 인증으로 사용하다 **통신사 SIM 스와핑 및 SS7 도청 공격에 의해 2차 인증 우회 및 계정 탈취** | **NIST SP 800-63B 지침 준수, 중요 관리자 및 금융 계정의 SMS OTP 폐지 및 FIDO2 보안키 의무화** | 평문 통신망 기반의 자격증명 가로채기(Interception) 위협 100% 원천 제거 |
| 야간에 공격자가 수백 번의 모바일 푸시 알람을 전송하여 **사용자가 무심코 승인 버튼을 누르는 MFA Fatigue 사고** | **단순 승인 버튼 대신 PC 화면의 2자리 난수를 폰에 직접 입력하는 번호 일치(Number Matching) 기능 강제** | 봇넷의 무차별 푸시 스팸 및 사용자 오승인(Human Error) 공격 100% 무력화 |
| 고강도 MFA를 도입했으나 사용자가 폰 분실 시 **헬프데스크 전화 통화만으로 2차 인증을 해제해 주는 우회로 발생** | **인증기 초기화/재등록 시 본인 확인을 초기 등록과 동등 보증 수준(AAL)으로 강화 및 감사 로그 의무화** | 사회공학(Social Engineering) 기법을 통한 백도어 우회 침해 100% 원천 차단 |

#### 한줄 요약
- FIDO2로 SMS 도청을 막고, 번호 일치로 푸시 피로를 방지하며, 동등 수준 복구로 헬프데스크 우회를 차단한다.

## Ⅶ. 결론

- 계정 자격증명 유출 위협을 무력화하는 **MFA 다중 인증 아키텍처**는 제로 트러스트 보안의 가장 필수적인 첫 번째 관문이며, 실무 구현 시 **NIST SP 800-63B AAL3 기준의 FIDO2/Passkey 피싱 저항성 인증 전면 도입**, **번호 일치(Number Matching)를 통한 MFA Fatigue 방어**, **엄격한 인증기 라이프사이클 및 비상 계정(Break-glass) 거버넌스**를 통합 구축하여 신원 기반 무결점 접근 통제를 완성

#### 한줄 요약
- FIDO2 피싱 저항성과 번호 일치 및 엄격한 복구 거버넌스를 결합하여 안전한 다중 인증 체계를 완성한다.
