## Ⅰ. 개요

<details><summary>용어 설명</summary>

- **공개키 기반구조(Public Key Infrastructure, PKI)**: 인터넷과 같은 개방형 네트워크 환경에서 비대칭 공개키(Public Key)가 실제 특정 개인, 기업, 서버의 것임을 암호학적으로 보증하기 위해 디지털 인증서(X.509)의 생성, 발급, 분배, 검증, 폐기 전 생애주기를 관리하는 종합 신뢰 프레임워크.
- **계층적 신뢰 체인(Hierarchical Chain of Trust / RFC 5280)**: 최상위 신뢰점인 루트 인증기관(Root CA)으로부터 중간 인증기관(Intermediate CA)을 거쳐 최종 사용자(End-Entity) 인증서로 이어지는 디지털 서명 검증 경로(Path Validation).

</details>

- 정의/개념: 비대칭 암호의 공개키에 신원 정보와 유효기간을 결합하여 공인 CA의 전자서명으로 공인하는 **X.509 인증서 발급·관리 체계**와, 루트 신뢰점(Trust Anchor) 기반의 **계층적 신뢰 경로 검증 생태계**
- 배경/필요성: 공개키 자체에는 소유자 증명 메커니즘이 없어 공격자가 임의의 공개키로 위장하는 중간자 공격(MITM)을 원천 차단하고, 글로벌 인터넷 상거래 및 보안 통신의 단일 신뢰 기준점을 확립할 요구

#### 한줄 요약
- 신뢰된 CA의 전자서명으로 공개키와 신원을 바인딩하여 계층적 인증서 발급 및 폐기를 관리한다.

## Ⅱ. 특징

<details><summary>용어 설명</summary>

- **소유권 증명(Proof of Possession, PoP / RFC 4210 CMP)**: 인증서 발급 신청자(CSR)가 제출한 공개키에 대응하는 개인키를 실제로 소유하고 통제하고 있음을 서명을 통해 RA/CA에 수학적으로 입증하는 절차.
- **오프라인 루트 CA(Offline Root CA)**: 최상위 신뢰 기준점의 개인키 침해를 방지하기 위해, 네트워크 인터페이스를 물리적으로 분리(Air-Gapped)하고 FIPS 140-3 하드웨어 금고(HSM)에 보관하며 하위 발급 CA 서명 시에만 제한적으로 기동하는 보안 설계.

</details>

- **계층적 서명 위임 및 신뢰 전파**: 최상위 Root CA $\rightarrow$ 중간 Policy/Issuing CA $\rightarrow$ 최종 엔드포인트 단말로 이어지는 신뢰 사슬
- **엄격한 권한 분립 (CA vs RA)**: 신원 검증 및 PoP 심사를 전담하는 **등록기관(RA)** 과 인증서 서명·발급만을 수행하는 **인증기관(CA)** 의 분리
- **실시간 무효화 체계 (CRL & OCSP)**: 키 탈취나 퇴사 등 사고 발생 시 만료일 이전이라도 인증서 효력을 즉시 정지·폐기

#### 한줄 요약
- 계층적 신뢰 체인, RA-CA 권한 분립, 오프라인 Root CA 보호, 실시간 CRL/OCSP 폐기 관리를 제공한다.

## Ⅲ. 구조 및 구성요소

<details><summary>용어 설명</summary>

- **인증서 서명 요청(Certificate Signing Request, CSR / PKCS#10)**: 신청자의 주체명(DN), 도메인(SAN), 공개키 정보 및 개인키로 자체 서명한 PoP 데이터를 담아 CA에 인증서 발급을 요청하는 표준 포맷.

</details>

```text
[ 인증서 신청자 (End-Entity / Server) ]
 ├─ 키 쌍 생성 (공개키 + 개인키)
 └─ CSR (PKCS#10: 공개키 + PoP 자체 서명) 생성
           │
           ▼ (1. CSR 제출 및 도메인 소유권 심사)
┌─────────────────────────────────────────────────────────────────────────┐
│ [ 등록기관 (Registration Authority, RA) ]                               │
│  ├─ 신청자 실명/조직 확인 (EV/OV) 및 도메인 검증 (DNS/HTTP ACME 챌린지)  │
│  └─ PoP 서명 검증 ➔ 승인된 발급 요청 전달                              │
└────────────────────────────────────┬────────────────────────────────────┘
                                     │ (2. 발급 승인)
                                     ▼
┌─────────────────────────────────────────────────────────────────────────┐
│ [ 발급 인증기관 (Issuing CA / Intermediate CA) ]                        │
│  ├─ 온라인 HSM 기반 X.509 v3 인증서 전자서명 및 발급                    │
│  └─ 실시간 폐기 데이터 발행 ──▶ [ 디렉터리 저장소: CRL 배포점 & OCSP 응답기 ]│
└────────────────────────────────────┬────────────────────────────────────┘
                                     │ (3. 상위 신뢰 위임 서명)
                                     ▼
┌─────────────────────────────────────────────────────────────────────────┐
│ [ 오프라인 최상위 루트 기관 (Offline Root CA) ]                         │
│  └─ 네트워크 물리적 단절 (Air-Gapped) + Root CA 자체 서명 인증서 보관    │
└─────────────────────────────────────────────────────────────────────────┘
```

선의 의미: 신청자의 CSR이 RA의 신원 검증을 통과한 후 발급 CA의 HSM 서명을 거쳐 X.509 인증서로 발행되고, 최상위 Root CA가 신뢰의 앵커를 제공하는 구조

| 구성요소 | 핵심 책임 및 역할 | 비고 |
|:---|:---|:---|
| **등록기관 (RA)** | 신청자의 실명·도메인 유효성 심사, CSR의 PoP 서명 검증 및 발급 승인 | ACME / RFC 4210 |
| **발급 인증기관 (CA)** | 승인된 신청자에게 CA 개인키(HSM)로 서명된 X.509 인증서 발행 | RFC 5280 |
| **최상위 루트 CA (Root)**| 전체 PKI의 신뢰 기준점(Trust Anchor)으로 하위 중간 CA 인증서만을 서명 발행 | Offline Air-Gap |
| **인증서 저장소 (Repository)**| 발급된 인증서, CRL(폐기 목록 파일) 및 OCSP 실시간 응답 서비스 제공 | LDAP / HTTP |
| **신뢰 저장소 (Trust Store)** | 클라이언트 OS 및 브라우저에 사전 탑재된 공인 Root CA 인증서 번들 | Windows/NSS |

#### 한줄 요약
- 등록기관(RA), 발급 CA, 최상위 루트 CA, 폐기 저장소(CRL/OCSP), 클라이언트 신뢰 저장소가 결합한다.

## Ⅳ. 흐름도

<details><summary>용어 설명</summary>

- **경로 검증 알고리즘(Certification Path Validation / RFC 5280 Section 6)**: 클라이언트가 수신한 서버 인증서로부터 시작하여 상위 CA 서명을 순차 검증하고, 유효기간, 기본 제약(Basic Constraints), 키 용도(Key Usage), 폐기 상태를 확인하여 Root CA까지의 무결성을 증명하는 알고리즘.

</details>

```text
1. 신청자가 키 쌍을 생성하고 공개키와 신원 정보를 담은 CSR(PKCS#10)을 작성하여 RA에 제출
            │
            ▼
2. RA가 도메인 제어 검증(ACME/DNS) 및 PoP 서명을 심사 ➔ 발급 CA로 인증서 발행 명령 하달
            │
            ▼
3. 발급 CA가 HSM 내부 개인키로 서명하여 X.509 v3 인증서 생성 및 신청자에게 교부
            │
            ▼
4. [통신 시점] 클라이언트(브라우저)가 서버로부터 인증서 체인을 수신하고 신뢰 저장소의 Root CA까지 경로 검증
            │
            ▼
5. OCSP 서버로 실시간 폐기 여부 조회 ➔ [유효 판정] ➔ 서버의 공개키를 신뢰하고 TLS 보안 채널 수립
```

**동작 원리**

1. **CSR 생성 및 PoP**: 신청자가 자신의 개인키로 CSR을 서명하여 개인키 보유 사실 증명
2. **신원 심사 및 인가**: RA가 자동화(ACME) 또는 수동 심사로 주체 정보의 진위 확인
3. **CA 전자서명**: CA가 X.509 표준 필드(Subject, Issuer, Validity, Extensions)를 구성하고 서명
4. **체인 역추적 검증**: 수신자가 Intermediate CA $\rightarrow$ Root CA 서명을 차례로 대조
5. **폐기 및 제약 조건 판정**: CRL/OCSP 상태와 인증서 확장 필드(isCA=False, KeyUsage) 일치 확인

#### 한줄 요약
- CSR 제출, RA 신원 심사, CA 전자서명 발급, 클라이언트 체인 경로 검증, OCSP 폐기 확인 순으로 동작한다.

## Ⅴ. 종류 및 비교

<details><summary>용어 설명</summary>

- **공개 웹 PKI vs 사설 엔터프라이즈 PKI**: 전 세계 웹 브라우저가 기본 신뢰하는 상용 PKI와 기업 내부 인트라넷/mTLS 통신 전용 사설 PKI의 비교.

</details>

| 비교 항목 | 글로벌 공개 웹 PKI (Web PKI) | 사설 엔터프라이즈 PKI (Private PKI) |
|:---|:---|:---|
| **신뢰 기준점 (Trust Anchor)**| **OS/브라우저에 기본 탑재된 상용 Root CA** | **기업 내부에서 자체 생성하여 단말에 배포한 사설 Root CA** |
| **발급 및 운영 비용** | 인증서당 유료 과금 (또는 Let's Encrypt 무료) | **초기 구축 후 무제한 무료 발급** |
| **적용 영역** | **대고객 HTTPS 웹 서비스, 공인 이메일(S/MIME)** | **사내 인트라넷, 마이크로서비스 mTLS, 사내 VPN, IoT** |
| **운영 통제권 및 유연성** | CA/Browser 포럼의 엄격한 규정 준수 (수명 90일 제한) | **인증서 프로파일, 수명, 확장 필드 기업 맞춤형 통제** |
| **외부 접속 호환성** | 전 세계 모든 기기에서 경고창 없이 자동 신뢰 | **사설 Root CA 미설치 외부 단말 접속 시 보안 경고 발생** |

#### 한줄 요약
- 공개 웹 PKI는 글로벌 범용 신뢰용, 사설 PKI는 내부 통제 및 mTLS 마이크로서비스용이다.

## Ⅵ. 실무 고려사항 및 대책

<details><summary>용어 설명</summary>

- **인증서 투명성(Certificate Transparency, CT / RFC 6962)**: CA가 인증서를 발급할 때마다 공개된 불변 분산 로그(Append-Only Log)에 실시간 등록하도록 강제하여, 도메인 소유자 몰래 위조 발급된 부정 인증서를 즉각 탐지하는 감사 프레임워크.

</details>

| 문제 | 대책 | 효과 |
|:---|:---|:---|
| 공인 CA의 시스템 침해 또는 내부자 실수로 인한 **위조/부정 인증서 몰래 발급 사고** | **RFC 6962 인증서 투명성(CT) 로그 모니터링 및 CAA(DNS) 레코드 구성** | 도메인 부정 발급 실시간 탐지 및 미승인 CA 발급 차단 |
| Root CA 개인키 온라인 노출로 인한 **전사 신뢰 기준점 붕괴(Total Compromise)** | **Root CA 오프라인(Air-Gapped) 유지 및 HSM 기반 키 분할 관리(M of N Quorum)** | Root CA 키 탈취 원천 방어 및 단일 장애점(SPOF) 해소 |
| 인증서 만료일 관리 실패로 인한 **전사 서비스 접속 불가 및 대규모 장애 발생** | **ACME 프로토콜(RFC 8555) 기반 인증서 자동 발급·갱신 파이프라인(Cert-Manager)** | 만료 휴먼 에러 0% 달성 및 무중단 인증서 생애주기 자동화 |

#### 한줄 요약
- CT 로그로 오발급을 감시하고, Air-Gap Root CA로 키를 보호하며, ACME 자동화로 만료 장애를 방지한다.

## Ⅶ. 결론

- 초연결 디지털 사회의 모든 보안 통신과 신원 증명의 신뢰 기반인 **PKI(공개키 기반구조)** 는 제로 트러스트(mTLS), 전자서명, 공급망 보안(SBOM 서명)의 핵심 인프라이며, 실무 구현 시 **오프라인 Root CA와 온라인 Issuing CA의 계층적 분리**, **ACME 기반 인증서 자동 갱신 체계**, **CT 로그 모니터링 및 실시간 OCSP Stapling**을 통합 구현하여 완결성 높은 고신뢰 보안 인프라를 완성

#### 한줄 요약
- 계층적 CA 신뢰 체인과 엄격한 수명주기 관리 및 ACME 자동화를 통해 무결점 PKI 환경을 구현한다.
