## 미리 알고가기

- **국가정보원(National Intelligence Service, NIS)**: 영문 머리글자를 딴 표기로 “엔아이에스”로 읽으며, 국가 정보보안 지침과 위임 검토를 담당함
- **제안요청서(Request for Proposal, RFP)**: 영문 머리글자를 딴 표기로 “알에프피”로 읽으며, 발주 전 보안 요구와 검증 기준을 명시함
- **인공지능(Artificial Intelligence, AI)**: 영문 머리글자를 딴 표기로 “에이아이”로 읽으며, 정보화사업의 자동화 판단·분석을 수행함
- **보안성 검토(Security Review)**: 공공 정보화사업의 설계·발주 전 보안대책을 검토하는 절차
- **보안적합성 검증**: 공공기관이 도입하는 보안 제품과 구성이 요구사항에 맞는지 확인하는 절차
- **외부 연계**: 기관 시스템이 클라우드·협력기관·인터넷과 데이터를 주고받는 연결
- **NIS·RFP 읽기**: “엔아이에스·알에프피”로 읽으며 영문 명칭의 머리글자를 묶어 국가정보원과 제안요청서를 나타냄
- **AI 읽기와 표기**: “에이아이”로 읽으며 Artificial Intelligence의 머리글자로 인공지능을 나타냄



## Ⅰ. 개요

- **정의/개념**: 공공 정보화사업의 설계·발주 전 보안대책 검토 절차
- **배경/필요성**: 구축 후 점검만으로 설계·계약에 누락된 보안 요구 보완 곤란

### 쉽게 이해하기 (학습용)

- 시스템 설계 전에 발주 단계에서 보안 요구를 확인함

## Ⅱ. 특징

- 정보화사업 공고 전 보안대책을 검토한다.
- 흐름·망·인증·암호·공급망 대책을 확인한다.
- 국가 지침에 따른 검토 경로와 의견을 RFP·설계에 반영한다.

### 쉽게 이해하기 (학습용)

- 기관이 자체 검토할지 상급기관이나 국가정보원에 의뢰할지는 사업 유형과 위임 기준에 따름

## Ⅲ. 아키텍처 및 구성요소

| 설계 요소 | 설명 |
|:---|:---|
| 사업 범위 | 목적·정보·기술과 검토 대상 여부 |
| 데이터 흐름 | 정보의 저장·처리·전송 및 외부 연계 |
| 망 구성 | 보안 영역·접점·클라우드 접근 경로 |
| 보안 대책 | 인증·암호·로그·개발·공급망·대응 |
| 조치 추적 | 의견을 RFP·설계·검수 항목에 연결 |

```text
[사업 계획·데이터 흐름] ─검토 자료─> [검토 기관]
          ↑                              │ 보완 의견
          └── RFP·설계·계약 반영 ───────┘
                         ↓
                    [구축·검수]
```

### 쉽게 이해하기 (학습용)

- 사업 구조와 정보 흐름을 보여 주고 받은 보완 의견을 발주·설계·검수까지 추적함

## Ⅳ. 원리 및 절차 흐름도

```text
대상경로판단 → 자료대책작성 → 검토의뢰 → 의견반영 → 완료전확인
```

| 절차 | 설명 |
|:---|:---|
| 대상판단 | 위임 기준으로 경로 정함 |
| 자료작성 | 계획·흐름·대책 준비함 |
| 검토의뢰 | 자료 제출함 |
| 의견반영 | 보완 요구를 설계함 |
| 완료확인 | 이행·잔여 사항 확인함 |

> 요약: 검토 의견을 RFP·설계·계약까지 추적함

### 쉽게 이해하기 (학습용)

- 검토 의견을 받은 것으로 끝내지 않고 구축 결과가 의견대로 구현됐는지 확인해야 함

## Ⅴ. 공공 보안 검토 절차 비교

| 비교축 | 보안성 검토 | 보안적합성 검증 |
|:---|:---|:---|
| 적용 기준 | 공고 전 설계·RFP에 보안을 반영할 때 | 제품 적용·운용 전에 구성을 확인할 때 |
| 핵심 특징 | 사업 구조와 보안대책 사전 검토 | 도입 제품·버전·구성의 적합성 검증 |
| 한계 | 검토 의견이 계약·구축에 미반영 | 인증 제품의 설치 설정·버전 불일치 |

### 쉽게 이해하기 (학습용)

- 보안성 검토는 사업 설계, 보안적합성 검증은 실제 도입 제품의 안전성을 확인함

## Ⅵ. 실무 사례

- 사업 분할과 무관하게 전체 연계 구조 제시
- 클라우드·AI 연계의 중요 변경 재판단
- 보안대책서는 통제하고 요구만 계약 전달
- 전자정부 사업은 행정정보·전자문서 보호 요건을 반영함

### 쉽게 이해하기 (학습용)

- 사업을 쪼개도 전체 연계 구조로 검토 대상을 판단함
- 클라우드·AI·외부 연결이 바뀌면 중요 변경 여부를 다시 판단함
- 민감한 보안대책서는 통제하고 사업자에게 필요한 요구만 계약에 반영함
- 전자정부 사업은 행정정보와 전자문서 보호 요건을 설계에 포함함

## Ⅶ. 결론

- 사업 전 보안 요구를 확정하고 설계·검수까지 추적함

### 쉽게 이해하기 (학습용)

- 발주 전에 위험을 찾아 계약에 넣어야 납품 뒤 보안 기능을 추가하는 비용과 공백을 줄일 수 있음
