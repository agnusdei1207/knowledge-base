## Ⅰ. 개요

<details><summary>용어 설명</summary>

- **XSS (Cross-Site Scripting, CWE-79)**: 웹 페이지에 악성 스크립트를 삽입하여 열람 사용자의 브라우저에서 실행되도록 하는 취약점.
- **Context-Aware Encoding (문맥 인식 인코딩)**: 출력 위치(HTML 본문, 속성값, JS 블록)마다 브라우저 파서가 적용하는 문법이 다르다는 점을 이용해, 그 위치를 판별한 뒤 해당 문맥에서만 구문으로 해석될 특수문자를 골라 치환함으로써 단일 이스케이프 규칙의 우회 경로를 없애는 기법.

</details>

- 정의/개념: 비신뢰 입력이 브라우저에서 실행되지 않도록 문맥 인식 인코딩, HTML 정화, CSP 및 HttpOnly로 세션 탈취를 방지하는 보안 기술
- 배경/필요성: 공격자가 웹 게시판, URL 파라미터, DOM 환경을 통해 악성 자바스크립트를 주입하는 크로스 사이트 스크립팅(XSS: Cross-Site Scripting, CWE-79)은 피해자의 브라우저 권한으로 실행되어 세션 토큰 탈취, 비인가 기능 호출, 악성코드 유포 및 화면 위변조를 유발하는 웹의 가장 대표적인 클라이언트 측 취약점임에 따라, 브라우저가 출력 위치(HTML 본문, 태그 속성, JS 블록, CSS)별로 서로 다른 파싱 문법을 적용하는 특성에 맞추어 문맥 인식 출력 인코딩(Context-Aware Encoding)과 DOMPurify 정화를 의무화하고, 스크립트 실행 자체를 억제하는 콘텐츠 보안 정책(CSP) 및 쿠키 탈취를 원천 차단하는 HttpOnly 플래그를 결합하여 출력 문맥별 우회 방지, 클라이언트 세션 토큰 완벽 보호 및 브라우저 네이티브 심층 방어(Defense-in-Depth)를 달성할 필요

#### 한줄 요약
- 문맥 인식 인코딩과 DOMPurify 정화 및 CSP/HttpOnly 다계층 방어로 브라우저 스크립트 주입을 무력화한다.

## Ⅱ. 특징

<details><summary>용어 설명</summary>

- **DOMPurify**: 리치 텍스트 에디터 사용 시 허용된 안전 HTML 태그만 남기고 악성 스크립트 속성을 제거하는 정화 라이브러리.
- **CSP (Content Security Policy)**: 웹 페이지가 로드할 수 있는 스크립트 출처를 제한하여 인라인 악성 코드 실행을 막는 보안 헤더.

</details>

- 출력 위치 기반 문맥 인식 인코딩: HTML Body, 속성(`attribute`), 자바스크립트 변수 영역별 전용 인코딩 규칙을 적용해 우회 차단
- 화이트리스트 기반 HTML 정화(Sanitization): 리치 텍스트 지원 시 DOMPurify를 통해 `onerror`, `onload` 등 악성 이벤트 핸들러 완전 소거
- 브라우저 네이티브 심층 방어(CSP & HttpOnly): 스크립트 주입에 성공하더라도 CSP 차단 및 HttpOnly 쿠키 보호로 세션 토큰 탈취 원천 봉쇄

#### 한줄 요약
- 인코딩 규칙이 문맥마다 갈라지는 이상 누락은 확률적으로 남으므로, 그 누락을 전제로 CSP와 HttpOnly가 실행 허가와 쿠키 접근을 한 번 더 끊는 중복 비용을 감수한다.

## Ⅲ. 구조 및 구성요소

<details><summary>용어 설명</summary>

- **HttpOnly Cookie**: 자바스크립트 `document.cookie` API를 통한 세션 ID 접근을 브라우저 차원에서 차단하는 보안 플래그.

</details>

```text
[XSS 다계층 방어 체계]
├─ 애플리케이션 계층
│  ├─ 문맥 인식 인코더 (출력 위치별 인코딩)
│  └─ HTML 정화기 (DOMPurify 악성 태그 소거)
└─ 브라우저 계층
   ├─ 안전한 DOM API (textContent 활용)
   ├─ CSP 보안 헤더 (스크립트 출처 제한)
   └─ HttpOnly 쿠키 (세션 토큰 탈취 원천 차단)
```

- 선의 의미: 계층 구조 및 상하위 포함 관계를 나타낸다.

| 구성요소 | 책임 |
|:---|:---|
| 문맥 인식 인코더 | HTML Body, Attribute, JS, URL 등 출력 위치별 전용 이스케이프 인코딩 실행 |
| HTML 정화기 (DOMPurify) | 리치 텍스트 허용 시 화이트리스트 안전 태그만 통과시키고 악성 속성 소거 |
| 안전한 DOM 싱크 API | `innerHTML` 대신 `textContent`를 사용하여 입력값이 실행 코드로 승격되는 결함 방지 |
| CSP 보안 헤더 | 인라인 스크립트 실행을 금지하고 사전에 인가된 도메인의 스크립트만 로드 허용 |
| HttpOnly 쿠키 속성 | `document.cookie` 자바스크립트 API를 통한 세션 ID 접근을 브라우저 엔진에서 차단 |

#### 한줄 요약
- 방어가 출력을 만드는 애플리케이션 계층과 그것을 해석하는 브라우저 계층으로 갈라져 있어, 앞 계층이 놓친 스크립트를 뒤 계층이 실행 시점과 쿠키 접근 시점에서 각각 다시 거른다.

## Ⅳ. 흐름도

<details><summary>용어 설명</summary>

- **DOM XSS Source & Sink**: Source(비신뢰 입력 `location.hash` 등) → Sink(실행 함수 `eval()`, `innerHTML` 등).

</details>

```text
악성 입력 유입, 문맥 판별, 문맥 인코딩/정화, DOM 해석 및 CSP 차단 파이프라인
        │
       [비신뢰 입력 유입]
        │
   1. [출력 시 문맥 판별] 서버 렌더링 엔진이 본문 출력 위치를 "HTML Body Context"로 식별
        │
   2. [문맥 인코딩 및 정화]
       ├─ 일반 게시판: `<` ➔ `&lt;`, `>` ➔ `&gt;`, `"` ➔ `&quot;` 로 치환
       └─ 리치 에디터: DOMPurify가 `<img>` 태그의 위험 속성 `onerror`를 정적으로 제거
        │
   3. [브라우저 DOM 해석] 브라우저 파서가 데이터를 실행 스크립트가 아닌 단순 텍스트로 정상 렌더링
        │
   ▼
4. [CSP 및 HttpOnly 차단]
    ├─ CSP 정책에 의해 미인가 인라인 스크립트 실행 즉시 거부
    └─ 스크립트가 실행되더라도 `HttpOnly` 속성으로 인해 세션 토큰 탈취 0% 완벽 방어
```

- 1. 출력 시 문맥 판별
- 2. 문맥 인코딩 및 정화
- 3. 브라우저 DOM 해석
- 4. CSP 및 HttpOnly 차단

#### 한줄 요약
- 인코딩 규칙은 출력 문맥이 정해진 뒤에야 고를 수 있으므로 방어의 자리는 입력 저장 시점이 아니라 출력 시점이며, CSP·HttpOnly는 그 선택이 틀렸을 때만 비용을 치르는 후단 안전망이다.

## Ⅴ. 종류 및 비교

<details><summary>용어 설명</summary>

- **저장형 (Stored)** vs **반사형 (Reflected)** vs **DOM 기반 (DOM-based)**.

</details>

| 비교 항목 | 저장형 XSS (Stored XSS) | 반사형 XSS (Reflected XSS) | DOM 기반 XSS (DOM-based XSS) |
|:---|:---|:---|:---|
| 악성 코드 저장 위치| 백엔드 데이터베이스 (영구 저장) | 웹 서버 로그/URL 파라미터 (미저장) | 클라우드/서버 미저장 (순수 클라이언트)|
| 공격 전달 메커니즘 | 게시판, 프로필, 댓글 등 정상 조회 | 피싱 메일, SNS의 조작된 URL 클릭 유도 | 조작된 URL Hash(`#`) 및 프론트엔드 JS |
| 피해 대상 범위 | 해당 페이지를 열람하는 불특정 다수 | 공격 링크를 직접 클릭한 특정 피해자 | 조작된 DOM 페이지를 로드한 피해자 |
| 서버 개입 여부 | 서버가 DB에서 읽어 응답에 포함 | 서버가 요청 파라미터를 응답에 반사 | 서버 개입 없음 (브라우저 JS 내부 실행) |
| 최우선 기술적 대책 | 저장 전/출력 시 문맥 인코딩 & HTML 정화| 파라미터 출력 인코딩 & WAF 필터링 | 안전한 프론트엔드 API(`textContent`) 사용|

#### 한줄 요약
- 세 유형은 악성 스크립트가 머무는 위치만 다를 뿐 실행은 모두 브라우저에서 일어나므로, 서버가 개입하지 않는 DOM 기반은 서버측 인코딩·WAF의 사정거리 밖이며 프론트엔드 싱크 API에서만 끊을 수 있다.

## Ⅵ. 실무 고려사항 및 대책

<details><summary>용어 설명</summary>

- **Strict CSP Nonce**: 매 요청마다 동적 일회용 난수(`nonce="rAnd0m"`)를 생성하여 일치하는 스크립트만 실행 허용하는 정책.

</details>

| 문제 | 대책 | 효과 |
|:---|:---|:---|
| 단순 HTML 엔티티 치환만 적용하여 자바스크립트 블록 내부 XSS 방어 실패 | 출력 위치 문맥(HTML, Attribute, JS, URL)에 맞는 `맞춤형 문맥 인식 인코딩 라이브러리` 적용 | 렌더링 문맥별 특수문자 실행 우회 경로 100% 차단 |
| 리치 텍스트 에디터 지원 중 `onload`, `onerror` 등 악성 이벤트 핸들러 유입 | `DOMPurify 기반 화이트리스트 정화(Sanitization) 엔진 적용 및 안전 태그 선별 허용` | UI 기능성을 유지하면서 악의적 스크립트 속성만 소거 |
| 소스코드 인코딩 실수로 XSS 발생 시 사용자의 세션 쿠키가 외부로 전면 탈취 | 모든 세션 쿠키에 `HttpOnly; Secure; SameSite=Strict` 적용 및 Strict-CSP 헤더 배포 | XSS 발생 시에도 브라우저 레벨에서 세션 접근 100% 차단 |
| SPA 프론트엔드 프레임워크의 위험 DOM API 사용 | React `dangerouslySetInnerHTML` 사용 금지 및 `textContent` 강제 | 클라이언트 사이드 DOM XSS 취약점 원천 소거 |

#### 한줄 요약
- 문맥 인식 인코딩으로 우회를 막고, DOMPurify로 에디터를 정화하며, HttpOnly/CSP로 세션을 격리한다.

## Ⅶ. 결론

- 웹 및 싱글 페이지 애플리케이션(SPA)의 발전과 함께 사용자 브라우저를 직접 장악하는 가장 치명적이고 빈번한 클라이언트 사이드 취약점이자 웹 프론트엔드 및 백엔드 시큐어 코딩의 가장 핵심적인 통제 대상(CWE-79)으로 확고히 규정되어 있으며, React/Vue의 가상 DOM 자동 이스케이프 및 Trusted Types API로 진화하는 가운데, 실무 웹 애플리케이션 개발 시에는 출력 위치에 따른 문맥 인식 인코딩(Context-Aware Encoding) 엄격 적용, 리치 텍스트 에디터 지원 시 DOMPurify 기반 화이트리스트 정화(Sanitization) 강제, 세션 쿠키에 대한 HttpOnly/Secure/SameSite 플래그 필수 지정 및 논스(Nonce) 기반의 엄격한 콘텐츠 보안 정책(Strict-CSP) 배포를 결합하여 완벽한 클라이언트 보안 격리를 완성

#### 한줄 요약
- XSS 방어는 문맥 인식 인코딩과 DOMPurify 정화 및 CSP/HttpOnly 심층 방어를 결합하여 브라우저 스크립트 주입을 완벽히 통제하는 클라이언트 보안 체계다.
