## Ⅰ. 개요

<details><summary>용어 설명</summary>

- **XSS (교차 사이트 스크립팅)**: 해커가 게시판 글이나 댓글에 악성 자바스크립트 코드를 숨겨놓고, 다른 일반 사용자가 그 글을 읽을 때 브라우저에서 코드가 몰래 실행되어 세션(쿠키)을 털어가는 해킹 기법이다.

</details>

- 정의: 검증되지 않은 비신뢰 클라이언트 입력값이 웹 응답 문서에 포함되어, 희생자의 브라우저에서 악성 자바스크립트 코드로 해석 및 실행되는 취약점이다.
- 배경: 브라우저의 DOM 렌더링 엔진(파서)이 입력값(단순 텍스트 데이터)과 실행 스크립트(Code)의 경계를 구분하지 못하고, 들어오는 족족 다 코드로 실행해버리기 때문이다.

#### 한줄 요약

- 내가 쓴 글(데이터)을 남의 브라우저가 코드(명령어)로 착각해서 실행해버리는, 게시판 테러 해킹이다.

## Ⅱ. 특징

<details><summary>용어 설명</summary>

- **출력 문맥 (Output Context)**: 데이터가 뿌려지는 위치. HTML <body> 태그 안이냐, 자바스크립트 변수 안이냐에 따라 해커의 공격 코드가 다르게 해석된다.
- **출력 인코딩 (Output Encoding)**: 브라우저가 `<script>` 태그를 코드로 실행하지 못하게, `<` 기호를 `&lt;` 같은 무해한 문자(엔티티)로 강제 변환시켜버리는 필수 방어법이다.

</details>

- **DOM 실행 경로 통제**: 데이터가 서버에 저장되었다가 반사되는 것뿐만 아니라, 클라이언트 단에서 DOM을 직접 조작할 때 발생하는 실행 경로(Source to Sink)도 통제해야 한다.
- **문맥 기반 출력 인코딩**: 단순히 다 막는 게 아니라 HTML 태그 안이냐 자바스크립트 안이냐 등 출력 문맥(Context)에 맞춰서 위험한 문자를 안전한 텍스트로 인코딩해야 한다.
- **API 응답 철저한 방어**: AJAX나 REST API로 주고받는 비신뢰 JSON/XML 데이터에 대해서도, 브라우저 렌더링 시 반드시 동일한 방어 룰(인코딩/정화)을 적용한다.

#### 한줄 요약

- 글자가 화면 어디에 찍히는지(문맥) 파악해서, 브라우저가 코드로 해석 못 하게 글자를 깨버리는(인코딩) 게 핵심이다.

## Ⅲ. 구조 및 구성요소

<details><summary>용어 설명</summary>

- **HTML 정화 (Sanitization)**: 네이버 스마트에디터처럼 표나 색깔 태그를 써야 하는 곳에서는 인코딩으로 태그를 다 부수면 안 되니까, 안전한 태그(`<b>`, `<img>`)만 허용목록(Allowlist)으로 살리고 위험한 태그(`<script>`)만 싹 지워주는 영리한 세탁기다.
- **CSP (콘텐츠 보안 정책)**: "우리 사이트는 우리 도메인에서 만든 스크립트만 실행해!" 하고 헤더에 못 박아서, 외부에서 욱여넣은 스크립트 실행을 브라우저 단에서 아예 차단하는 방패다.

</details>

```text
[ XSS 철저한 방어 아키텍처 ]

[ 1. 비신뢰 유입 ] ── ("게시판 폼이나 URL 파라미터로 악성 스크립트가 유입됨")
      │
      ▼
[ 2. 출력 문맥 파악 ] ── ("이 데이터가 HTML 바디에 찍힐지, JS 변수에 들어갈지 구분함")
      │
      ▼
[ 3. 인코딩 및 HTML 정화 ] ── ("일반 글자는 싹 다 치환(인코딩)하고, 에디터 글은 안전 태그만 남기고 세탁함")
      │
      ▼
[ 4. 렌더링 반영 (DOM) ] ── ("안전하게 세탁된 데이터만 코드가 아닌 순수 텍스트로 브라우저 DOM에 반영함")
      │
      ▼
[ 5. 브라우저 통제 (CSP) ] ── ("혹시 인코딩 뚫려도 CSP랑 HttpOnly 쿠키로 세션 탈취를 브라우저에서 최종 컷!")
```

| 구성요소 | 책임 | 비고 |
|:---|:---|:---|
| **비신뢰 유입 통제** | 폼 입력이나 URL에서 들어오는 **모든 외부 데이터는 의심함** | Input |
| **출력 문맥 파악** | 데이터가 화면의 **어느 위치에 찍히는지(HTML, JS, 속성)를 파악함** | Context |
| **인코더 및 정화기** | 일반 텍스트는 **인코딩(치환)** 하고, 웹 에디터 글은 **안전 태그만 살림** | Sanitize |
| **렌더링 반영 (DOM)** | 파서가 오해하지 않게, 코드가 아닌 순수 텍스트로 **DOM에 반영함** | DOM |
| **브라우저 통제 (CSP)** | 뚫리더라도 해커 서버로 쿠키 못 빼가게 **CSP와 HttpOnly 속성으로 막음** | CSP |

#### 한줄 요약

- 들어오는 족족 위치(문맥)에 맞게 글자를 치환(인코딩/정화)하고, 뚫릴 거 대비해서 헤더(CSP)로 브라우저 멱살을 잡는다.

## Ⅳ. 흐름도

<details><summary>용어 설명</summary>

- (상단 참조)

</details>

```text
[ XSS 악성 스크립트 실행 및 방어 흐름 ]

┌──────────────────────────────┐
│ 1. [비신뢰 데이터 저장 및 반사]
│ ("해커가 게시판에 <script>쿠키탈취</script> 악성 글을 남김")
└──────────────┬───────────────┘
               ▼
┌──────────────────────────────┐
│ 2. [취약한 웹 응답 및 DOM 구문 해석]
│ ("일반 사용자가 그 글을 읽을 때, 브라우저가 스크립트 코드로 오해해서 파싱함")
└──────────────┬───────────────┘
               ▼
┌──────────────────────────────┐
│ 3. [피해자 세션 권한으로 스크립트 실행]
│ ("사용자 브라우저 안에서 해커의 악성 코드가 권한을 얻고 구동됨")
└──────────────┬───────────────┘
               ▼
┌──────────────────────────────┐
│ 4. [문서 데이터(쿠키/세션) 접근]
│ ("악성 코드가 document.cookie를 뒤져서 로그인 세션을 탈취함")
└──────────────┬───────────────┘
               ▼
    ┌──────────────────────────────┐
    │ 5. [탈취 및 원격지 서버 전송 (위조 요청)]
    │ ("훔친 쿠키를 해커 서버로 몰래 전송함 (HttpOnly나 CSP 없으면 다 털림)")
    └──────────────────────────────┘
```

### 동작 원리

1. 비신뢰 데이터 저장/반사: 검증되지 않은 악성 스크립트 데이터가 DB에 저장되거나 응답에 결합됨.
2. HTML/DOM 구문 해석: 브라우저 엔진(파서)이 방어되지 않은 텍스트 데이터를 코드로 해석 처리함.
3. 스크립트 실행: 희생자 브라우저의 동일 출처(Same-Origin) 세션 권한을 기반으로 악성 스크립트가 구동됨.
4. 세션 데이터 접근: 구동된 스크립트가 쿠키(Cookie), 로컬 스토리지 등에 접근하여 민감 정보를 긁어감.
5. 유출 및 위조 요청: 탈취한 세션을 해커의 서버로 빼돌리거나 CSRF 위조 요청을 집행함.

#### 한줄 요약

- 글을 남기고 $\to$ 남이 읽으면 코드로 돌아가고 $\to$ 쿠키를 긁어내서 $\to$ 해커 서버로 전송해버리는 악질 흐름이다.

## Ⅴ. 종류 및 비교

<details><summary>용어 설명</summary>

- **저장형 (Stored)**: 게시판 글에 악성 코드를 박아놔서, 이 글을 클릭하는 모든 사람의 쿠키를 털어먹는 파급력 최강의 XSS다.
- **반사형 (Reflected)**: 해커가 만든 링크를 피해자가 클릭하게 유도해서, 클릭하는 순간 서버를 튕겨 나와 브라우저에서 실행되는 단발성 XSS다.
- **DOM 기반 (DOM-based)**: 서버를 안 거치고, 클라이언트 자바스크립트 내에서 `innerHTML` 같은 위험한 함수를 쓸 때 발생하는 XSS다.

</details>

| XSS 공격 유형 | **저장형 (Stored XSS)** | **반사형 (Reflected XSS)** | **DOM 기반 (DOM-based XSS)** |
|:---|:---|:---|:---|
| 핵심 특징 | **지뢰밭(게시판) 만들어 놓고 누가 밟기를 대기하기** | **독 묻은 낚시 링크를 카톡으로 보내서 클릭 유도하기** | **서버 안 거치고, 사용자 브라우저 안에서 혼자 북치고 장구치기** |
| 핵심 탐지 방식 | 악성 스크립트가 DB에 영구 저장된 후, **게시글을 읽을 때 자동 실행됨** | URL 파라미터에 숨긴 코드가 서버를 거쳐 **즉시 응답 페이지로 반사됨** | 서버와 상관없이 클라이언트 JS가 **DOM을 직접 조작하다 런타임에 터짐** |
| 장점 및 특징 | 불특정 다수를 상대로 한 번에 수백 명의 세션을 **동시에 털어버림 (파급력 극대)** | 피싱 이메일이나 메신저를 통해 **특정 타깃을 노리고 단발성으로 공격함** | 서버(WAF)를 안 거치고 브라우저 안에서만 돌아서 **네트워크 방어망을 다 피함** |
| 한계 및 문제점 | 게시판 폼에서 입력/출력 인코딩만 잘하면 **DB에 들어가기도 전에 다 막힘** | 피해자가 의심스러운 낚시 링크를 **직접 클릭해 주지 않으면 아무 일도 없음** | 프론트엔드 개발자가 `innerHTML` 같은 위험한 JS 함수를 안 쓰면 **공격 성립 불가** |

#### 한줄 요약

- 글에 묻혀놓으면 '저장형', 튕겨내면 '반사형', 화면단에서만 놀면 'DOM 기반' XSS다.

## Ⅵ. 실무 고려사항 및 대책

<details><summary>용어 설명</summary>

- **MITRE CWE-79**: 전 세계 모든 취약점 바이블에서 "XSS 방어하려면 인코딩해라" 하고 정해둔 가이드다.
- **HttpOnly**: 자바스크립트 따위가 감히 세션 쿠키에 접근하지 못하도록, 브라우저 단에서 쿠키를 꽉 잠가버리는 가장 강력하고 가성비 좋은 속성이다.

</details>

| 장애/위험 요소 | 원인 분석 | 실무 대책 및 해결방안 | 기대 효과 |
|:---|:---|:---|:---|
| 홑따옴표(') 다 막았는데 **자바스크립트 안에서 XSS가 터짐** | 데이터가 HTML에 찍히는지 JS 변수에 들어가는지 **출력 문맥(Context)** 을 무시하고 무지성 인코딩함 | **MITRE CWE-79** 기반, 출력되는 문맥(HTML, 속성, URL 등)에 맞춘 **맞춤형 인코딩 적용** | 브라우저 파서(해석기)가 코드로 오해하는 근본 원인을 차단하여 우회 공격 원천 방어 |
| 인코딩 빡세게 돌렸더니 **스마트에디터 글씨 색깔이 다 깨짐** | 글꼴이나 표(태그)가 필수적인 에디터 영역에 인코딩을 강제 돌려서 정상 태그까지 부숨 | **OWASP ASVS** 기준, 안전한 태그(`<b>`, `<img>`)만 허용목록으로 남기는 **HTML Sanitizer(정화기) 도입** | 비즈니스 요구사항(풍부한 웹 텍스트 에디터)을 수용하면서 악성 스크립트만 세탁 |
| XSS 뚫린 건 맞는데 **사용자 세션 쿠키가 싹 털려서 대형사고 남** | 브라우저 방어막이 안 쳐져 있어서, 자바스크립트가 쿠키를 마음대로 읽어가게 방치함 | 세션 쿠키 발급 시 **HttpOnly / Secure / SameSite** 속성 적용 및 외부 전송 막는 **CSP 헤더 강제** | XSS에 뚫리더라도, 최악의 사태인 세션(계정) 탈취를 브라우저 단에서 완벽히 무력화 |

#### 한줄 요약

- 화면 위치(문맥)에 맞춰 인코딩하고, 에디터는 정화(Sanitize)하고, 최후의 보루로 HttpOnly와 CSP를 박아라.

## Ⅶ. 결론

<details><summary>용어 설명</summary>

- **XSS 통제 선택 기준 (XSS Control Criteria)**: 단순 문자 필터링 땜빵이 아닌, 문맥별 출력 방어와 브라우저 제어를 다층으로 엮는 시큐어 코딩 원칙.

</details>

- XSS 방어는 단순 문자 필터링이 아닌 출력 문맥에 따른 정확한 해석 차단이 핵심이므로, 일반 데이터 출력은 **출력 인코딩(Contextual Encoding)**, 에디터 기능에는 **HTML 정화(Sanitization)** 를 적용하고, 만약의 사태에 대비해 **CSP** 및 **HttpOnly** 쿠키 속성으로 잔여 위협을 다층 통제하는 실무 기조를 확립함

#### 한줄 요약

- 텍스트는 **인코딩**, 에디터는 **HTML 정화**, 마무리는 **CSP와 HttpOnly** 기반 철저한 방어해라.
