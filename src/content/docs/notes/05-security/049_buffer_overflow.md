## Ⅰ. 개요

<details><summary>용어 설명</summary>

- **Buffer Overflow (버퍼 오버플로우, CWE-120/787)**: 할당된 메모리 버퍼 크기를 초과하여 인접한 복귀 주소(RET) 등을 덮어써 실행 흐름을 장악하는 취약점.
- **Control Flow Hijacking (제어 흐름 탈취)**: 스택에 저장된 함수의 복귀 주소를 변조하여 공격자의 악성 코드나 시스템 함수로 점프시키는 행위.

</details>

- 정의/개념: 메모리 버퍼 경계를 초과 기록하여 RET를 변조하는 공격에 맞서 **안전 함수, 스택 카나리, DEP/NX, ASLR로 제어 흐름을 보호하는 기술**
- 배경/필요성: C/C++와 같은 저수준 시스템 프로그래밍 언어에서 메모리 할당 버퍼의 경계 검사(Bounds Checking)가 누락될 경우, 입력 데이터가 스택이나 힙의 인접 메모리 영역을 침범하여 함수의 복귀 주소(RET) 또는 함수 포인터를 변조함으로써 공격자가 임의의 셸코드를 실행하고 시스템 제어권을 장악하는 치명적 메모리 오염 취약점(CWE-120/787)이 발생함에 따라, 개발 레벨의 안전 함수 사용 및 Rust 등 메모리 안전 언어(Memory-Safe Languages) 전환과 더불어 컴파일러의 스택 카나리(Stack Canary), CPU 하드웨어 MMU 기반의 데이터 실행 방지(DEP/NX), OS 커널의 주소 공간 무작위화(ASLR/PIE)를 다계층으로 결합하여 **메모리 경계 붕괴 방지, 셸코드 주입 실행 차단 및 제어 흐름 탈취(Control Flow Hijacking)의 원천 무력화**를 달성할 필요

#### 한줄 요약
- 스택 카나리, 하드웨어 DEP/NX, OS ASLR의 다계층 결합을 통해 메모리 변조 및 제어 흐름 탈취를 차단한다.

## Ⅱ. 특징

<details><summary>용어 설명</summary>

- **Stack Canary**: 함수 진입 시 스택 버퍼와 RET 사이에 난수를 주입하고, 반환 전 난수 변조 여부를 검사하여 변조 시 즉시 종료시키는 기법.
- **DEP / NX (Data Execution Prevention / No-Execute)**: CPU 하드웨어 MMU를 통해 데이터 영역(스택/힙)에서 코드가 실행되는 것을 원천 차단하는 기술.

</details>

- **컴파일러 레벨의 덮어쓰기 감지(Stack Canary)**: 함수 반환 전 **카나리 난수의 무결성을 검증하여 변조 감지 시 프로세스를 즉시 강제 종료**
- **하드웨어 MMU 기반 실행 권한 박탈(DEP/NX)**: CPU 페이지 테이블의 NX 비트를 설정하여 **스택/힙 데이터 영역에서의 셸코드 실행 원천 차단**
- **가상 메모리 주소 난수화(ASLR / PIE)**: 프로세스 기동 시 **스택, 힙, 라이브러리(libc) 주소를 무작위 셔플링하여 점프 타깃 은닉**

#### 한줄 요약
- 세 기법은 모두 결함 자체를 제거하지 못하고 공격의 성공 조건만 비싸게 만드는 완화책이므로, 근본 해소는 경계 검사 비용을 런타임이 대신 치르는 메모리 안전 언어로의 전환에 있다.

## Ⅲ. 구조 및 구성요소

<details><summary>용어 설명</summary>

- **ASLR / PIE**: 스택, 힙, 공유 라이브러리(ASLR) 및 바이너리 실행 코드 영역(PIE)의 가상 메모리 주소를 난수화하는 메커니즘.

</details>

```text
버퍼 오버플로우 방어 구조
|-- 소스 계층
|   `-- 안전 함수 라이브러리
|-- 컴파일러 계층
|   |-- 스택 카나리
|   `-- PIE·RELRO
`-- OS·하드웨어 계층
    |-- ASLR
    `-- DEP·NX
```

선의 의미: 소스코드 안전 함수 적용에서 시작하여 컴파일러의 카나리 주입을 거쳐 OS/CPU의 ASLR 및 DEP 하드웨어 차단으로 이어지는 구조

| 구성요소 | 핵심 엔지니어링 책임 | 주요 특징 |
|:---|:---|:---|
| **안전 함수 라이브러리**| 입력 버퍼의 크기를 명시적으로 검증하는 **C11 표준 안전 함수(`strncpy_s`) 적용** | Source-Level |
| **스택 카나리 (Canary)** | 스택 덮어쓰기 발생 시 **함수 종료 전 변조를 감지해 프로세스 즉시 종료** | Compiler |
| **위치 독립 실행 (PIE)** | 바이너리의 코드 세그먼트까지 **메모리 상에 무작위 주소로 로드 지원** | PIE Compiler |
| **ASLR (주소 무작위화)** | 기동 시 **스택, 힙, 라이브러리 가상 메모리 베이스 오프셋 무작위화** | OS Kernel |
| **하드웨어 DEP/NX** | 페이지 테이블 수준에서 **데이터 메모리 영역의 코드 실행을 하드웨어 차단** | CPU Hardware |

#### 한줄 요약
- 방어 책임이 소스·컴파일러·커널·CPU로 흩어져 있어 어느 한 계층의 플래그 누락만으로 그 아래 계층이 전제하던 조건이 무너지며, 그래서 배포 시점의 플래그 검증이 방어의 일부가 된다.

## Ⅳ. 흐름도

<details><summary>용어 설명</summary>

- **W^X 원칙 (Write XOR Execute)**: 메모리 페이지는 쓰기(W) 또는 실행(X) 중 하나만 가능해야 하며 둘을 동시에 허용하지 않는 보안 원칙.

</details>

```text
버퍼 초과 쓰기, 카나리 훼손 감지, ASLR 불일치 및 DEP 실행 차단 파이프라인
        │
   1. [취약 함수 호출] 공격자가 128바이트 버퍼에 512바이트 셸코드 및 조작된 복귀 주소 입력
        │
   2. [버퍼 경계 초과 쓰기] 버퍼를 넘어 스택 카나리 영역과 함수 복귀 주소(RET) 영역까지 덮어쓰기 집행
        │
   3. [에필로그 카나리 검증]
       ├─ 컴파일러가 삽입한 `__stack_chk_fail()` 루틴이 스택 카나리 값의 훼손을 실시간 감지
       └─ [변조 감지 즉시 프로세스 강제 크래시(Crash) 유발 ➔ 제어권 탈취 1차 선제 차단]
        │
   ├─ [만일 정보 유출로 카나리를 우회한 경우: 2차/3차 방어]
   ▼
4. [ASLR 주소 난수화 방어] 공격자가 고정된 라이브러리 주소로 점프를 시도하나 주소 불일치(SegFault)
        │
   ▼
5. [하드웨어 DEP/NX 최종 차단] 스택 영역의 셸코드가 실행되려는 순간 CPU가 NX 비트 위반 인터럽트 발생
```

- 1. 취약 함수 호출
- 2. 버퍼 경계 초과 쓰기
- 3. 에필로그 카나리 검증
- 4. ASLR 주소 난수화 방어
- 5. 하드웨어 DEP/NX 최종 차단

#### 한줄 요약
- 세 방어선은 감지·예측 방해·실행 거부라는 서로 다른 성격을 맡으며, 앞의 카나리와 ASLR은 메모리 정보 유출 한 건으로 전제가 무너지는 반면 NX 비트는 유출로 우회되지 않는다.

## Ⅴ. 종류 및 비교

<details><summary>용어 설명</summary>

- **스택 카나리** vs **데이터 실행 방지 (DEP / NX)** vs **주소 공간 무작위화 (ASLR / PIE)**.

</details>

| 비교 항목 | 스택 카나리 (Stack Canary) | 데이터 실행 방지 (DEP / NX) | 주소 공간 무작위화 (ASLR / PIE) |
|:---|:---|:---|:---|
| **보호 메커니즘** | **스택 프레임 내 난수 무결성 검증** | **데이터 메모리 영역의 코드 실행 권한 박탈**| **스택/힙/라이브러리 베이스 주소 난수화** |
| **방어 집행 주체** | **컴파일러 (GCC `-fstack-protector`)** | **CPU 하드웨어 (MMU) + OS 커널** | **운영체제(OS) 가상 메모리 로더** |
| **핵심 방어 목표** | **스택 RET 주소 덮어쓰기 감지 및 차단** | **스택/힙에 주입된 악성 셸코드 실행 차단** | **공격자의 고정된 타깃 점프 주소 예측 방해**|
| **우회 공격 기법** | 카나리 값 메모리 유출(Leak), BSS 덮어쓰기| **ROP (Return-Oriented Programming)** | 메모리 주소 유출(Memory Leak) 취약점 결합 |
| **시스템 오버헤드** | 극히 미미 (함수 시작/종료 시 비교 연산) | **전혀 없음 (하드웨어 MMU 수준 처리)** | 극히 미미 (프로세스 로드 시 1회 연산) |

#### 한줄 요약
- 셋 다 오버헤드는 미미하나 우회 경로가 각각 값 유출·주소 유출·코드 재사용으로 갈라지므로 하나가 다른 하나를 대체할 수 없고 동시 적용이 전제된다.

## Ⅵ. 실무 고려사항 및 대책

<details><summary>용어 설명</summary>

- **Checksec**: 컴파일된 바이너리에 Canary, NX, PIE, RELRO 보호 플래그가 누락 없이 적용되었는지 검사하는 도구.

</details>

| 문제 | 대책 | 효과 |
|:---|:---|:---|
| 레거시 C 함수(`strcpy`, `gets`) 사용으로 인한 **스택 오버플로우 RCE 취약점 발생** | **`C11 표준 안전 함수(strncpy_s) 전환 및 메모리 안전 언어(Rust) 도입`** 의무화 | 메모리 경계 초과 결함 100% 예방 |
| 컴파일 플래그 누락으로 **카나리와 NX가 비활성화된 취약 바이너리가 운영망에 배포** | **CI/CD에 `Checksec 도구 연동 및 -fstack-protector-all, NX 플래그 강제`** | 보호 플래그 누락 바이너리 배포 100% 차단 |
| 스택 카나리만 단독 적용하여 **힙 오버플로우 및 ROP 우회 공격에 시스템 장악** | **`스택 카나리 + Full ASLR + 하드웨어 DEP/NX + Full RELRO 동시 다층 적용`** | 단일 방어선 우회 시에도 하드웨어 방어선에서 최종 차단 |
| 포인터 서명(PAC) 미지원 하드웨어에서의 제어 흐름 변조 | **`ARM PAC 및 Intel CET 하드웨어 제어 흐름 무결성(CFI)` 기술 단계적 도입** | ROP/JOP 코드 재사용 공격 하드웨어 수준 원천 봉쇄 |

#### 한줄 요약
- 안전 함수/Rust로 원인을 제거하고, Checksec으로 플래그를 강제하며, 카나리/DEP/ASLR을 다층 적용한다.

## Ⅶ. 결론

- 운영체제와 임베디드, 고성능 서버의 기반을 위협하는 가장 오래되고 치명적인 시스템 메모리 침해 공격이자 **저수준 바이너리 보안 및 소프트웨어 신뢰성(CWE-120)의 핵심 방어 대상**으로 확고히 규정되어 있으며, 미국 백악관 및 CISA 권고에 따른 메모리 안전 언어(Memory-Safe Languages, Rust/Go)로의 현대적 전환과 하드웨어 제어 흐름 무결성(Intel CET / ARM PAC)으로 진화하는 가운데, 실무 바이너리 개발 및 운영 시에는 **C11 표준 안전 함수(strncpy_s) 적용, 컴파일 파이프라인 내 스택 카나리(-fstack-protector-all) 및 Full RELRO/PIE 플래그 강제, Checksec 정적 바이너리 검증 자동화, 하드웨어 MMU의 DEP/NX와 OS 커널 ASLR의 동시 다층 활성화**를 결합하여 완벽한 시스템 메모리 보안 무결성을 완성

#### 한줄 요약
- 버퍼 오버플로우 방어은 시큐어 코딩과 스택 카나리, 하드웨어 DEP/NX, ASLR의 다층 결합을 통해 메모리 오염 공격을 완벽히 차단하는 저수준 보안 체계다.
