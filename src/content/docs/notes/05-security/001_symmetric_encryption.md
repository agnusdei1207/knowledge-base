## Ⅰ. 개요

<details><summary>용어 설명</summary>

- **대칭키 암호 (Symmetric Key Cryptography)**: 문을 잠글 때 쓴 열쇠(암호화)와 문을 열 때 쓰는 열쇠(복호화)가 완전히 똑같은 암호화 방식이다. 빠르고 효율적이지만, 열쇠를 상대방에게 안전하게 전달해야 하는 숙제가 있다.
- **비밀키 (Secret Key)**: 송신자와 수신자가 공유하는 단 하나의 열쇠로, 외부에 유출되는 순간 암호화된 모든 팩트 데이터가 털리는 대칭키 암호의 핵심 통제값이다.

</details>

- 정의: 송수신자가 동일한 **비밀키** 하나로 기밀성을 확보하고 초고속으로 데이터를 보호하는 **대칭키 암호** 기술이다.
- 배경: 비대칭키(공개키) 암호는 수학 연산이 너무 무거워서, 대규모 데이터를 실시간으로 암호화하려면 **저비용 고속 암호화** 체계가 필수적이었다.

#### 한줄 요약

- 빠르고 가볍게 대용량 파일을 암호화하지만, '단 하나의 열쇠'를 안전하게 전달하고 지켜야 하는 양날의 검이다.

## Ⅱ. 특징

<details><summary>용어 설명</summary>

- **블록 암호 (Block Cipher)**: 고기 썰듯이 데이터를 128비트 단위의 깍둑썰기(블록)로 잘라서 팩트 암호화하는 방식이다.
- **스트림 암호 (Stream Cipher)**: 물 흐르듯이 1비트씩 연속으로 팩트 암호화하는 방식으로, 무선 통신처럼 빠르고 끊기지 않아야 할 때 쓴다.
- **논스 (Nonce)**: 한 번 쓰고 버리는 일회용 난수다. 똑같은 평문을 똑같은 키로 암호화해도 매번 다른 암호문이 나오게 해서, 해커가 암호문의 패턴을 못 읽게 만드는 조미료다.

</details>

- **초고속 대용량 처리**: 복잡한 소수 연산 대신 단일 비밀키 기반의 단순 연산(XOR 등)으로 대규모 데이터를 빛의 속도로 보호한다.
- **블록/스트림 분할**: 데이터 특성 및 가속기 유무에 맞춰 **고정 블록** 단위나 연속된 **키스트림** 단위로 팩트 처리한다.
- **AEAD 결합**: 기밀성(암호화)에 인증 태그(무결성)와 논스를 결합해 위변조까지 한 방에 차단한다.

#### 한줄 요약

- 열쇠 하나로 미친 듯이 빠르게 잠그고, 매번 랜덤한 조미료(논스)를 쳐서 해커가 비밀번호 패턴을 못 외우게 만든다.

## Ⅲ. 구조 및 구성요소

<details><summary>용어 설명</summary>

- **AEAD (인증 기반 암호)**: 암호화만 하는 게 아니라, "이 데이터 변조 안 됐음!"이라는 인증 꼬리표(태그)를 같이 붙여주는 팩트 만능 기능이다.
- **KMS (키 관리 시스템)**: 핵심 비밀키를 소스 코드에 하드코딩하지 않고, 별도의 안전한 금고(HSM 등)에 넣어서 수명주기 전반을 팩트로 통제하는 시스템이다.

</details>

```text
[ 대칭키 암호 및 AEAD 기반 팩트 보호 구조 ]

[ 1. 애플리케이션 (응용) ] ── (DB에 넣을 평문과 정책을 넘김. 키는 직접 안 만짐)
      │
      ▼
[ 2. 키 관리 시스템 (KMS) ] ── (안전한 금고에서 비밀키와 일회용 논스 값을 할당함)
      │
      ▼ (키 핸들 전달)
[ 3. AEAD 암호 모듈 ] ── (평문을 암호문으로 바꾸고, 무결성 팩트용 '인증 태그'를 찍음)
      │
      └─▶ [ 4. 검증 및 복호화 ] ── (수신자가 태그 팩트 체크 통과 후 복호화 수행)
```

| 구성요소 | 팩트 폭행 책임 | 비고 |
|:---|:---|:---|
| **애플리케이션 (응용)** | 평문과 부가 인증 데이터(AAD)를 던져주고 **암호화를 의뢰하는 놈** | Application |
| **KMS (키 관리 시스템)** | 털리면 회사 망하는 **비밀키를 안전하게 보관하고 배급하는 금고** | Key Manager |
| **AEAD 암호 모듈** | 평문을 암호문으로 팩트 변환하고 **조작 방지용 인증 태그를 굽는 엔진** | Crypto Engine |
| **인증 태그 (Tag)** | "이 암호문은 조작되지 않았음"을 **수신자에게 팩트로 증명하는 도장** | Auth Tag |
| **논스 (Nonce)** | 암호문의 패턴을 숨기기 위해 **매번 새롭게 뿌려주는 일회용 조미료** | Nonce |

#### 한줄 요약

- 앱은 키를 보관하지 않고 KMS 금고에 맡기며, 암호 모듈은 암호화와 동시에 조작 방지 씰(태그)을 붙인다.

## Ⅳ. 흐름도

<details><summary>용어 설명</summary>

- **키 핸들 (Key Handle)**: 암호 모듈이 진짜 비밀키 값을 직접 보지 않고도, "그 금고에 있는 1번 키 써서 암호화해!"라고 권한만 팩트로 지시하는 참조값이다.
- **인증 후 복호문 공개**: 해커가 조작한 쓰레기 암호문을 복호화하느라 서버 자원을 낭비하지 않도록, 무조건 '인증 태그'부터 팩트 체크하고 통과해야만 평문을 까주는 철칙이다.

</details>

```text
[ AEAD 기반 대칭키 암호화 및 무결성 십자포화 흐름 ]

┌──────────────────────────────┐
│ 1. [키/논스 할당 및 핸들 전달]
│ (KMS가 일회용 논스를 뽑고, 암호 모듈에 키 사용 권한(핸들) 팩트 부여)
└──────────────┬───────────────┘
               ▼
┌──────────────────────────────┐
│ 2. [AEAD 암호문 및 인증 태그 생성]
│ (평문을 암호화하고, 동시에 조작 방지용 인증 팩트 도장을 쾅 찍음)
└──────────────┬───────────────┘
               ▼
┌──────────────────────────────┐
│ 3. [암호문 전송 및 수신자 검증]
│ (수신자가 암호문을 받고, 가장 먼저 '인증 태그'부터 팩트 체크함)
└──────────────┬───────────────┘
               ▼
┌──────────────────────────────┐
│ 4. [검증 실패 시 폐기 / 성공 시 복호화]
│ (태그 훼손됐으면 해커의 조작이므로 즉각 폐기, 정상이면 복호화 진행)
└──────────────────────────────┘
```

### 동작 원리

1. 키/논스 배정: 동일 평문 방어를 위해 KMS가 키와 유일한 논스(일회용 난수)를 팩트 할당함.
2. 키 핸들 참조: 원문 키 유출을 막기 위해 키 핸들만으로 암호 모듈을 가동함.
3. 태그 동시 생성: 데이터를 섞으면서(암호화) 훼손 검증용 태그를 일괄 생성함.
4. 인증 선행 검증: 암호문을 까보기 전에 태그부터 검사해 쓰레기 데이터 연산을 차단함.

#### 한줄 요약

- 키 유출을 막기 위해 핸들로 지시하고, 암호화할 때 무결성 도장(태그)을 찍어 수신자가 변조 여부를 먼저 확인하게 만든다.

## Ⅴ. 종류 및 비교

<details><summary>용어 설명</summary>

- **AES-GCM**: 서버 등 하드웨어 가속 환경에서 짱먹는 블록 기반 AEAD 암호다.
- **ChaCha20-Poly1305**: 가속기가 없는 똥폰이나 IoT에서 미친 속도를 내는 스트림 기반 AEAD 암호다.
- **AES-XTS**: 디스크 자체를 통째로 잠가버릴 때(BitLocker 등) 쓰는 전용 모드다.

</details>

| 대칭 암호 방식 | **AES-GCM (블록 기반 AEAD)** | **ChaCha20-Poly1305 (스트림)** | **AES-XTS (디스크 암호화)** |
|:---|:---|:---|:---|
| 팩트 폭행 비유 | **성능 빵빵한 PC를 위한 '표준 규격 장갑차'** | **스마트폰/IoT를 위한 '초경량 스포츠카'** | **하드디스크를 통째로 잠그는 '금고 다이얼'** |
| 작동 원리 | 하드웨어 가속(AES-NI)을 받아 **블록 단위로 초고속 병렬 처리** | 하드웨어 가속 없이도 **스트림 단위로 가볍고 미친 듯이 빠르게 팩트 암호화** | 디스크의 물리적 섹터 위치(XTS)를 반영해 **블록 단위 기밀성 유지** |
| 핵심 강점 | 글로벌 표준(NIST)이라 **서버 환경에서 압도적인 호환성과 속도 보장** | 모바일 기기 배터리 소모가 적고 **TLS 1.3 최고 표준으로 채택됨** | 파일 크기 변경 없이 **스토리지 자체 암호화(BitLocker 등)에 찰떡임** |
| 치명적 한계 | 동일한 논스(Nonce) 재사용 시 **기밀성/무결성이 팩트로 다 깨져버림** | AES 전용 가속 칩이 있는 환경에선 **오히려 AES-GCM보다 성능이 떨어짐** | 무결성 인증(AEAD) 기능이 없어서 **해커가 데이터를 뒤섞는 변조에 취약함** |

#### 한줄 요약

- 서버 통신은 AES-GCM, 모바일은 ChaCha20, 하드디스크 암호화는 AES-XTS가 국룰이다.

## Ⅵ. 실무 고려사항 및 대책

<details><summary>용어 설명</summary>

- **논스 재사용 (Nonce Reuse)**: 같은 일회용 난수(논스)를 두 번 쓰면 해커가 XOR 연산으로 암호키를 역산해서 평문을 다 까발릴 수 있는, 대칭키 암호화 최악의 휴먼 에러다.

</details>

| 장애/위험 요소 | 원인 분석 | 실무 대책 및 해결방안 | 기대 효과 |
|:---|:---|:---|:---|
| 동일 암호키 환경에서 **해커가 암호문 패턴을 역산해 냄** | 논스(Nonce)를 고정값으로 쓰거나 재사용해서 암호문이 똑같이 생성됨 | 12바이트 난수 등 **키별 논스 유일성을 강제하고 팩트로 모니터링함** | 논스 재사용으로 인한 암호키 유출 및 평문 노출 원천 차단 |
| 해커가 조작한 쓰레기 암호문 때문에 **서버가 복호화하다 뻗음** | 암호문의 무결성을 검증하기도 전에, 무작정 복호화(Decrypt) 연산부터 들이댐 | 반드시 AEAD 태그를 먼저 검증하는 **'인증 후 복호문 공개' 로직 팩트 적용** | 위조 데이터 처리로 인한 자원 고갈(DoS) 및 패딩 오라클 공격 방어 |
| 비밀키를 **소스 코드(Github)에 하드코딩해서 통째로 털림** | 개발 편의상 DB 비밀번호나 대칭키를 `config.json`이나 소스 코드에 박아 넣음 | 키를 KMS/Vault에 격리하고, 암호 모듈에는 **원문 키 대신 '키 핸들'만 전달함** | 소스 코드 유출/해킹 시에도 핵심 비밀키는 100% 안전하게 보호 |

#### 한줄 요약

- 키는 코드에 박지 말고 KMS에 넣고, 논스는 무조건 한 번만 쓰고 버리며, 수상한 암호문은 태그부터 까보고 버려라.

## Ⅶ. 결론

<details><summary>용어 설명</summary>

- (상단 참조)

</details>

- 대규모 데이터의 초고속 기밀성 보호를 위해, 통신에는 무결성을 동시 보장하는 **AEAD(AES-GCM/ChaCha20)** 를 적용하고 디스크엔 **AES-XTS**를 배치하며, 철저한 **논스 유일성**과 **KMS 키 통제**를 결합한 대칭 암호화 기조 확립함

#### 한줄 요약

- 대칭 암호는 알고리즘 자체보다, 비밀키를 어떻게 배포/보관하고 논스를 겹치지 않게 쓰느냐 하는 '운영 통제'가 생명이다.
