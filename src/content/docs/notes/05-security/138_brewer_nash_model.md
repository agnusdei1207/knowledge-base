## Ⅰ. 개요

<details><summary>용어 설명</summary>

- **Brewer-Nash 모델(만리장성 모델 / Chinese Wall Model / IEEE 1989)**: 금융, 법률, 회계 컨설팅 환경에서 컨설턴트가 특정 기업의 기밀 정보를 열람한 후 경쟁 기업의 기밀 정보를 추가로 열람함으로써 발생할 수 있는 이해충돌(Conflict of Interest)과 내부자 거래를 원천 방지하기 위해, 주체의 과거 접근 이력(Access History)에 따라 경쟁사 데이터에 대한 접근을 실시간 동적으로 차단하는 보안 모델.
- **정적 역할 기반 통제(RBAC)의 이해충돌 방지 한계 결함(Static Privilege vs Dynamic Conflict Defect)**: 전통적인 강제적 접근 통제(MAC)나 역할 기반 통제(RBAC)는 직급이나 부서에 따라 고정된 권한을 부여하므로, 동일한 '기업 분석가' 역할을 가진 직원이 A금융사 데이터를 분석한 직후 경쟁 B금융사 데이터에 접근하여 영업 비밀을 유출하거나 악용하는 동적 이해충돌 시나리오를 방어할 수 없던 구조적 결함.
- **만리장성 모델(Chinese Wall Model)**: 1989년 David Brewer와 Michael Nash가 발표한 상업용 접근 제어 모델로, 금융·투자은행·회계·법률 등에서 컨설턴트나 분석가가 경쟁사 간의 기밀을 동시에 열람하여 발생할 수 있는 이해충돌(Conflict of Interest)과 내부자 거래를 방지하기 위해 고안된 동적 보안 모델.
- **이해충돌 클래스(Conflict of Interest Class, COI)**: 상호 경쟁 관계에 있는 기업들의 데이터셋 집합(예: 석유화학 COI = {A정유, B정유, C정유}).

</details>

- 정의/개념: 상호 경쟁 관계에 있는 기업 데이터의 교차 유출을 방지하기 위해 **객체 3계층 구조화(객체 $\rightarrow$ CD $\rightarrow$ COI) $\rightarrow$ 과거 접근 이력(Access History) 추적 $\rightarrow$ 단순 보안 읽기 규칙(Simple Security Rule) 적용 $\rightarrow$ 별표(*) 쓰기 규칙(Star-Property Rule)을 통한 간접 유출 차단 $\rightarrow$ 정제 데이터(Sanitized Data) 예외 처리**를 집행하는 **동적 정보 흐름 격리 보안 모델**
- 배경/필요성: 전통적인 정적 역할 기반 통제(RBAC)나 강제적 접근 통제(MAC)는 직무나 보안 등급에 따라 권한을 사전에 고정 부여하므로, 동일한 권한을 가진 금융·법률·회계 분석가가 A기업의 기밀을 열람한 후 경쟁 B기업의 기밀을 연속 열람하여 내부자 거래나 영업 비밀 유출을 일으키는 동적 이해충돌(Conflict of Interest)을 방어할 수 없는 구조적 한계가 존재함에 따라, 3계층 객체 구조(객체 $\rightarrow$ 회사 데이터셋 CD $\rightarrow$ 이해충돌 클래스 COI), 주체의 과거 접근 이력(Access History) 추적, 단순 보안 읽기 규칙(Simple Security Rule) 및 간접 전파를 차단하는 별표(*) 쓰기 규칙을 결합하는 Brewer-Nash(만리장성) 동적 보안 모델을 도입하여 **상업적 이해충돌 원천 방지, 다자간 기업 기밀 격리 및 동적 정보 흐름 통제(NIST SP 800-53 AC-4)**를 달성할 필요

#### 한줄 요약
- Brewer-Nash 모델은 과거 접근 이력을 기반으로 경쟁사(COI) 간 데이터 접근을 동적으로 차단한다.

## Ⅱ. 특징

<details><summary>용어 설명</summary>

- **Brewer-Nash 모델 3대 핵심 메커니즘**:
  - **이력 기반 동적 권한 결정 (History-based Dynamic Authorization)**: 주체의 정적 속성이 아닌 '과거에 어떤 회사 데이터를 열람했는가'에 따라 접근 권한이 실시간 재구성.
  - **COI(이해충돌 클래스) 내 배타적 선택 (Exclusive Choice within COI)**: 특정 COI 클래스 내에서 단 하나의 회사 데이터셋(CD)만 선택 접근 가능하며, 선택 시 동일 COI 내 타 경쟁사는 즉각 차단.
  - **양방향 정보 흐름 제어 (Bidirectional Flow Control)**: 직접 읽기 제한뿐만 아니라, 열람한 기밀을 타 기업 공유 공간에 복사하는 간접 유출(쓰기)까지 통제.

</details>

- 첫 객체 열람 후 범위가 줄어드는 **시간 종속 통제**
- 수평적 경쟁 관계를 격리하는 **상업 환경 특화**
- 기업 식별자를 제거한 **정제 데이터** 공유 허용

#### 한줄 요약
- 접근 이력 기반 동적 권한 축소, COI 내 배타적 선택, 읽기/쓰기 양방향 간접 유출 차단을 제공한다.

## Ⅲ. 구조 및 구성요소

<details><summary>용어 설명</summary>

- **Brewer-Nash 3계층 데이터 계층 구조 및 핵심 규칙**:
  1. **Objects (객체/파일)**: 개별 데이터 파일, 테이블 레코드.
  2. **Company Dataset (CD, 회사 데이터셋)**: 특정 단일 기업에 속하는 모든 객체의 집합 (예: 코카콜라 데이터).
  3. **Conflict of Interest Class (COI, 이해충돌 클래스)**: 상호 경쟁 관계에 있는 기업 데이터셋의 집합 (예: 탄산음료 COI = {코카콜라, 펩시}).
  4. **Simple Security Rule (읽기 규칙)**: 주체 $S$가 객체 $O$를 읽기 위해서는 $O$가 속한 CD가 $S$가 과거에 접근했던 CD와 동일하거나, $S$가 해당 COI에 속한 어떤 CD에도 접근한 적이 없어야 함.
  5. **Star Property Rule (*-속성 쓰기 규칙)**: 주체 $S$가 객체 $O$에 쓰기 위해서는 $S$가 읽을 수 있는 모든 비정제 객체들이 $O$와 동일한 CD에 속해야 함.

</details>

```text
[Brewer-Nash 만리장성 모델]
├── [데이터 3계층 분류]
│   └── 이해충돌 클래스 (COI)
│       └── 회사 데이터셋 (CD)
│           └── 개별 객체 (Objects)
├── [비식별 예외 데이터]
│   └── 정제 데이터 (Sanitized Data)
├── [주체 상태 관리]
│   └── 과거 접근 이력 (Access History)
└── [동적 정보 흐름 규칙]
    ├── 단순 읽기 규칙 (이해충돌 열람 차단)
    └── 별표(*) 쓰기 규칙 (간접 정보 유출 방지)
```

- 선의 의미: 계층 구조 및 상하위 포함 관계를 나타낸다.

| 구성요소 | 책임 |
|:---|:---|
| **객체 (Objects)** | 개별 파일이나 데이터베이스 행 단위의 최소 보호 자원 |
| **회사 데이터셋 (CD)** | 특정 단일 기업에 귀속된 객체들의 격리 집합 |
| **이해충돌 클래스 (COI)** | 상호 배타적 경쟁 관계에 있는 기업 데이터셋들의 상위 그룹 |
| **접근 이력 (History)** | 주체가 과거에 열람한 CD 기록을 추적하여 동적 권한 판정 지원 |
| **단순 읽기 규칙** | 과거 접근한 CD와 동일하거나 COI 내 경쟁 이력이 없을 때만 읽기 허용 |
| **별표(*) 쓰기 규칙** | 열람한 비정제 정보가 속한 동일 CD 외 타 객체로의 쓰기를 차단하여 간접 유출 방지 |
| **정제 데이터 (Sanitized)** | 기업 식별자가 제거된 비식별 통계로 COI 제약 없이 전사 공유 허용 |

#### 한줄 요약
- 주체의 접근 이력이 관리자가 미리 정해 둔 권한 목록을 대신해 첫 열람 순간에 권한 경계를 스스로 좁히고, 단순 읽기 규칙이 경쟁사 데이터의 직접 열람을 막는다면 별표 쓰기 규칙은 주체를 매개로 두 CD를 잇는 간접 경로를 막으며, 식별자가 제거된 정제 데이터만 그 제약 밖에 놓인다.

## Ⅳ. 흐름도

<details><summary>용어 설명</summary>

- **Brewer-Nash 동적 접근 통제 5단계 프로세스**:
  1. 주체(Analyst)가 특정 기업 데이터 객체에 읽기 요청
  2. 요청 객체의 소속 CD 및 상위 COI 클래스 식별
  3. 주체의 과거 접근 이력 DB 조회 및 이해충돌 여부 검증
  4. 읽기 규칙 충족 시 접근 허용 및 주체 이력에 해당 CD 원자적(Atomic) 갱신
  5. 쓰기 요청 시 별표(*) 규칙 검증을 통해 타 CD로의 간접 전파 차단

</details>

```text
[분석가] ── 객체 읽기 요청 ──> [접근 통제기]
            │
            ▼
1. [객체 분류 및 메타데이터 조회]
    ├─ 객체 O ➔ 회사 데이터셋: CD_Pepsi
    └─ 상위 이해충돌 클래스: COI_Beverage {CD_Coke, CD_Pepsi}
            │
            ▼
2. [단순 보안 읽기 규칙 검증]
    ├─ 주체 S의 과거 접근 이력 H(S) 조회
    ├─ [시나리오 A: H(S)에 CD_Coke 존재 확인]
    │   └─ ➔ [이해충돌 발생! 만리장성 장벽 작동 ➔ 읽기 즉시 거부 (Access Denied)]
    └─ [시나리오 B: H(S)에 음료 COI 접근 이력 없음 또는 CD_Pepsi만 존재]
            │
            ▼
3. [읽기 허용 및 이력 원자적 갱신]
    ├─ 읽기 권한 승인 (Access Granted)
    └─ [H(S) 이력 테이블에 'CD_Pepsi' 추가 ➔ 트랜잭션 원자적(Atomic) 커밋]
            │
            ▼
4. [쓰기 요청 및 별표 규칙 검사]
    ├─ 분석가 S가 '공용 분석 보고서(CD_Public)'에 내용 작성(Write) 시도
    ├─ S가 CD_Pepsi 비정제 데이터를 읽었으므로 CD_Public 쓰기 검사 수행
    └─ [간접 유출 방지를 위해 CD_Public 쓰기 차단 ➔ 오직 CD_Pepsi 내부에만 쓰기 허용]
```

**동작 원리**

1. **객체 분류 및 메타데이터 조회**: 객체의 CD와 COI 식별
2. **단순 보안 읽기 규칙 검증**: 이력과 경쟁 CD 대조
3. **읽기 허용 및 이력 원자적 갱신**: 승인과 기록 동시 커밋
4. **쓰기 요청 및 별표 규칙 검사**: 다른 CD로의 전파 차단

#### 한줄 요약
- 접근할수록 허용 범위가 줄어드는 구조라 이해충돌은 확실히 막히지만 한 사람이 맡을 수 있는 고객 범위도 함께 좁아지므로, 모델의 대가는 인력 배치의 경직성으로 나타난다.

## Ⅴ. 종류 및 비교

<details><summary>용어 설명</summary>

- **접근 통제 3대 보안 모델 비교**:
  - Brewer-Nash (만리장성): 과거 접근 이력 기반의 동적 상업적 이해충돌 방지 (기밀성 중심).
  - Bell-LaPadula (BLP): 정적 군사 보안 등급(No Read Up, No Write Down) 기반 (기밀성 중심).
  - Biba 모델: 정적 무결성 등급(No Read Down, No Write Up) 기반 (무결성 중심).

</details>

| 비교 항목 | Brewer-Nash (만리장성 모델) | Bell-LaPadula (BLP 모델) | Biba (비바 모델) |
|:---|:---|:---|:---|
| **핵심 목표** | **상업적 이해충돌(Conflict) 방지** | **군사적 기밀 유출 방지** | **데이터 비인가 변조 및 오염 방지**|
| **통제 방식** | **동적 통제 (접근 이력 기반 실시간 변화)**| **정적 통제 (보안 등급 및 인가 레벨)** | 정적 통제 (무결성 등급 기준) |
| **읽기 규칙** | **동일 CD 또는 미접근 COI만 허용** | **단순 보안: No Read Up (하위 등급 금지)**| 단순 무결성: No Read Down |
| **쓰기 규칙** | **별표(*): 읽은 CD 외 타 CD 쓰기 금지** | **별표(*): No Write Down (하위 쓰기 금지)** | 별표(*): No Write Up (상위 쓰기 금지) |
| **적용 환경** | **금융, 투자은행, 법무/회계 컨설팅** | **국방, 군사 정보, 국가 정보기관** | **금융 원장, 시스템 무결성, DB 관리**|

#### 한줄 요약
- Brewer-Nash는 동적 이해충돌 방지, BLP는 정적 기밀성 등급 통제, Biba는 정적 무결성 등급 통제이다.

## Ⅵ. 실무 고려사항 및 대책

<details><summary>용어 설명</summary>

- **NIST SP 800-53 AC-4 (정보 흐름 통제) 및 Brewer-Nash 구현**: 기업 전산망 내 동적 정보 흐름 격리 및 이해충돌 방지 통제 가이드라인.

</details>

| 문제 | 대책 | 효과 |
|:---|:---|:---|
| 컨설팅 포털에서 A사 데이터를 열람한 컨설턴트가 **시스템 재로그인 또는 신규 브라우저 세션을 통해 경쟁 B사 데이터에 접근하여 기밀 유출** | **NIST SP 800-53 AC-4 준수, DB 레벨의 주체-CD 접근 이력 원장을 영구 보존하고 매 세션 생성 시 과거 이력 강제 동기화** | 세션 분리를 악용한 이해충돌 우회 100% 원천 차단 |
| 두 개 이상의 요청이 동시에 인입될 때 레이스 컨디션(Race Condition)으로 인해 **동일 주체에게 경쟁 관계인 A사와 B사의 접근 권한이 동시 발급되는 결함 발생** | **접근 검증과 이력 테이블 갱신을 분리 불가능한 단일 RDBMS 원자적(ACID) 트랜잭션 격리 수준(Serializable)으로 락킹** | 동시성 경합으로 인한 만리장성 무력화 0% 달성 |
| 비식별화된 정제 데이터(Sanitized Data) 내에 미세한 매출 수치가 남아 있어 **타사 데이터를 통해 역추적 재식별(Re-identification)하여 원본 기밀을 복원** | **차분 프라이버시(Differential Privacy) 및 k-익명성(k-Anonymity) 알고리즘을 적용하여 정제 데이터의 비식별화 품질 사전 검증** | 정제 데이터를 통한 우회적 기밀 유출 100% 차단 |

#### 한줄 요약
- 영구 이력 보존으로 세션 우회를 막고, 원자적 트랜잭션으로 경합을 방어하며, 차분 프라이버시로 재식별을 차단한다.

## Ⅶ. 결론

- 과거 접근 이력에 따라 권한 범위를 실시간 재구성하여 상호 경쟁 기업 간 정보 유출과 이해충돌을 차단하는 **동적 상업 보안 및 정보 흐름 격리(Brewer-Nash / Chinese Wall Model / NIST SP 800-53 AC-4)의 핵심 이론적 모델**로 확고히 자리 잡았으며, 멀티테넌트 클라우드 환경 및 법무/금융 SaaS 플랫폼 보안의 핵심 접근제어 로직으로 계승되는 가운데, 실무 엔터프라이즈 시스템 구현 시에는 **접근 검증과 이력 갱신의 직렬화(Serializable) 원자적 트랜잭션 보장, 브라우저 재로그인 및 세션 분리를 통한 우회 차단용 영구 감사 원장 동기화, 정제 데이터(Sanitized Data) 공유 시 차분 프라이버시(Differential Privacy) 기반 재식별 방지**를 결합하여 완벽한 만리장성 격리 신뢰성을 완성

#### 한줄 요약
- Brewer-Nash 모델을 통해 과거 접근 이력 기반의 동적 만리장성을 구축하여 무결점 이해충돌 방지를 완성한다.
