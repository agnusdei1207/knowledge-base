## Ⅰ. 개요

<details><summary>용어 설명</summary>

- **인증서 폐지 (Revocation)**: "이 인증서 아직 유효기간 1년 남았지만, 어제 내 노트북 털려서 비밀번호(개인키) 유출됐으니 당장 무효로 만들어줘!" 하는 긴급 킬 스위치다.
- **CRL (인증서 폐지 목록)**: CA가 주기적으로 "지금까지 잘린 인증서 번호 싹 다 모아서 압축 파일 만들어 줄게" 하고 배포하는 무식하게 큰 블랙리스트다.
- **OCSP (온라인 인증서 상태 프로토콜)**: "목록 전체 다운받기 무거우니까, 내가 이 번호 하나만 찔러볼 테니 지금 짤렸는지 안 짤렸는지 실시간 대답만 해줘" 하는 1:1 질문 시스템이다.

</details>

- 정의: 만료 전 인증서 효력 상실을 확인하는 **CRL(블랙리스트 전체 대조)** 과 **OCSP(실시간 개별 대조)** 철저한 검증 기술이다.
- 배경: 유효기간만 믿고 통신하면 **키 유출•오발급•권한 상실**된 위험한 인증서로 해커가 사기를 치는 걸 막을 수가 없었다.

#### 한줄 요약

- 유효기간이 아무리 많이 남아도, "어제 털렸으니까 오늘부터 쓰지 마!" 하고 전 세계에 선언하는 블랙리스트 시스템이다.

## Ⅱ. 특징

<details><summary>용어 설명</summary>

- **전파 지연 (Propagation Delay)**: 어제 해킹당해서 CA에 폐기 신청했는데, 브라우저가 새 CRL을 다운받는 건 내일이라서, 하루 동안 해커가 마음껏 털어먹는 치명적인 보안 공백이다.
- **소프트 실패 / 하드 실패 (Soft/Hard Fail)**: 브라우저가 OCSP 서버에 물어봤는데 서버가 죽어있을 때, "그냥 안전하겠지" 하고 접속시키는 게 소프트 실패(가용성), "검증 안 되면 무조건 차단!" 하는 게 하드 실패(보안)다.

</details>

- **보안 공백 (전파 지연)**: CRL은 주기적으로 다운받기 때문에, 최신 폐지 정보가 내 PC에 반영되기 전까지의 치명적 공백이 존재한다.
- **응답의 한계 (OCSP Good)**: OCSP가 "정상(Good)"이라고 했다고 인증서 전체가 완벽하다는 뜻이 아니라, 단지 "아직 폐기 목록에 없다"는 팩트만 알려줄 뿐이다.
- **장애 대응 (실패 정책)**: 상태 조회 서버(OCSP)가 뻗었을 때 서비스가 마비되는 걸 막을 건지(소프트 실패), 털릴 바엔 접속을 차단할 건지(하드 실패) 전략을 결정해야 한다.

#### 한줄 요약

- 정보가 늦게 퍼지는 치명적 단점(CRL)과, 묻는 서버가 죽었을 때 어떻게 할 것인지(OCSP)에 대한 철학 싸움이다.

## Ⅲ. 구조 및 구성요소

<details><summary>용어 설명</summary>

- **검증자 정책 및 캐시**: 똑같은 사이트 들어갈 때마다 똑같은 걸 계속 물어보면 네트워크 낭비니까, 한 번 물어본 응답은 메모리(캐시)에 저장해 뒀다가 빼서 쓰는 거다.

</details>

```text
[ 인증서 폐지 철저한 검증 및 응답 구조 ]

[ 1. CA 폐지 상태 DB ] ── (신고 들어온 잘린 인증서 목록을 기록해 둠)
      │
      ├─▶ [ 2. CRL 배포점 (CDP) ] ── (일주일마다 전체 블랙리스트 압축 파일 만들어서 던짐)
      │
      └─▶ [ 3. OCSP 응답 서버 ] ── (브라우저가 찌르면 "이 번호는 살았음/죽었음" 실시간 서명 답변함)
      │
      ▼
[ 4. 검증자 (브라우저) 캐시 ] ── (어제 다운받은 CRL이나 OCSP 응답을 캐시 메모리에 저장해 두고 꺼내 씀)
```

| 구성요소 | 책임 | 비고 |
|:---|:---|:---|
| **CA 폐지 상태 DB** | 신고 접수된 인증서의 **일련번호와 폐기 사유를 저장하는 원본 DB** | CA DB |
| **CRL 배포점 (CDP)** | 무식하게 큰 **전체 폐기 목록을 일괄 서명해서 주기적으로 뿌리는 게시판** | CDP |
| **OCSP 응답 서버** | 브라우저가 번호 하나 물어보면 **실시간으로 살았는지 죽었는지 서명해서 알려줌** | Responder |
| **검증자 정책 및 캐시** | 똑같은 거 또 안 물어보게 **캐시에 저장하고 서버 죽었을 때 정책(Soft/Hard) 결정함** | Relying Party |

#### 한줄 요약

- 통째로 다운받을래(CRL)? 아님 접속할 때마다 하나씩 실시간으로 물어볼래(OCSP)? 둘 중 하나를 고르는 구조다.

## Ⅳ. 흐름도

<details><summary>용어 설명</summary>

- **신선도 검증 (Freshness Check)**: 해커가 어제 정상이었던 OCSP 응답을 가로채서 오늘 쏴줄 수 있으니, "이거 진짜 방금 막 만든 응답 맞아?" 하고 타임스탬프 유효 범위를 따지는 거다.

</details>

```text
[ CRL/OCSP 상태 갱신 및 신선도 검증 십자포화 흐름 ]

┌──────────────────────────────┐
│ 1. [인증서 폐지 접수 및 CA DB 갱신]
│ ("제 키 털렸어요!" 신고받고 CA가 내부 DB에 폐기 처리함)
└──────────────┬───────────────┘
               ▼
┌──────────────────────────────┐
│ 2. [CRL 일괄 배포 및 OCSP 실시간 동기화]
│ (CA가 전체 목록 만들어서 뿌리고, OCSP 서버에 실시간 폐기 정보 넘겨줌)
└──────────────┬───────────────┘
               ▼
┌──────────────────────────────┐
│ 3. [브라우저 질의 및 응답의 신선도/서명 검증]
│ (브라우저가 OCSP 응답을 받았는데, 이거 최신 맞는지(신선도) 서명 체크함)
└──────────────┬───────────────┘
               ▼
┌──────────────────────────────┐
│ 4. [검증 결과 적용 또는 실패 정책(Soft/Hard) 발동]
│ (정상이면 통과. 만약 응답 서버가 죽었으면 미리 정한 정책대로 끊거나 냅둠)
└──────────────────────────────┘
```

### 동작 원리

1. 폐기 접수 및 서명 갱신: CA가 접수된 폐기 목록(일련번호)과 적용 시각을 서명해 CA DB에 게시함.
2. 상태 동기화: 최신 폐기 상태를 CRL 배포점 및 OCSP 응답자에 실시간 동기화함.
3. 신선도 및 서명 검증: 응답 서명과 **thisUpdate/nextUpdate** 유효 기간(신선도)을 깐깐하게 검증함.
4. 실패 정책 적용: 서버 다운 시 보안과 가용성 위험도에 따라 소프트 실패 또는 하드 실패를 강제함.

#### 한줄 요약

- 블랙리스트를 배포하고 $\to$ 접속 시 실시간 확인하고 $\to$ 답변이 없으면 팅길지 말지(실패 정책)를 정한다.

## Ⅴ. 종류 및 비교

<details><summary>용어 설명</summary>

- **OCSP 스테이플링 (Stapling)**: 100만 명이 구글 들어갈 때마다 OCSP 서버를 찌르면 서버가 발생하니까, 아예 구글 서버가 아침에 확인증을 하나 받아놓고, 접속하는 손님들한테 영수증처럼 직접 찍어 보여주는 천재적인 꼼수다. 웹의 국룰이다.

</details>

| 인증서 폐지 확인 | **CRL (무식한 목록)** | **OCSP (실시간 질의)** | **OCSP 스테이플링 (최고 존엄)** |
|:---|:---|:---|:---|
| 핵심 특징 | **전국 범죄자 명부 책자 받아서 하나씩 뒤져봄** | **경찰청에 전화해서 "이놈 범죄자 맞나요?" 물어봄** | **가게 주인이 아침에 뗀 '영업허가 확인증' 직접 보여줌** |
| 핵심 기술 원리 | CA가 주기적으로 발행하는 무거운 블랙리스트 파일을 통째로 다운로드함 | 브라우저가 특정 인증서 하나만 OCSP 서버에 실시간 질의함 | TLS 서버가 미리 받아둔 OCSP 응답을 **사용자 접속 시 알아서 던져줌** |
| 최고 장점 | 오프라인 폐쇄망에서도 **한 번 다운받아두면 검증 가능함** | CRL처럼 파일이 무겁지 않고 **가장 최신의 폐기 상태를 알 수 있음** | 브라우저가 OCSP 접속할 필요 없어서 **접속 지연(Delay)과 개인정보 유출 원천 차단됨** |
| 치명적 한계 | 파일 사이즈가 무지막지하게 크고 **다음 업데이트 전까지 해킹에 노출됨** | 내 브라우저가 어느 사이트 들어가는지 **OCSP 서버가 내 접속 기록(사생활)을 다 털어감** | 서버 관리자가 설정 잘못해서 **확인증 갱신 까먹으면 멀쩡한 사이트 접속이 팅겨버림** |

#### 한줄 요약

- 덩치 큰 CRL은 버리고, 프라이버시 발생하는 OCSP 단점까지 완벽히 보완한 '스테이플링'이 현재 표준이다.

## Ⅵ. 실무 고려사항 및 대책

<details><summary>용어 설명</summary>

- **RFC 6960 (OCSP 표준)**: "이 응답이 해커가 조작한 옛날(재전송) 팩트인지 아닌지"를 깐깐하게 검증하라고 만들어둔 국제 표준 규격이다.

</details>

| 장애/위험 요소 | 원인 분석 | 실무 대책 및 해결방안 | 기대 효과 |
|:---|:---|:---|:---|
| 사이트 들어갈 때마다 **인증서 확인하느라 웹 로딩이 5초씩 걸림** | 브라우저가 OCSP 서버에 질의하고 응답받을 때까지 TLS 통신 접속을 멈추고 멍 때림 | 서버가 인증 응답을 대신 받아 던져주는 **'OCSP 스테이플링(Stapling)' 강제 적용** | 무거운 상태 검증 네트워크 오버헤드 제거 및 통신 지연시간 획기적 단축 |
| 해커가 가로채서 **옛날 정상 응답(Replay)을 전송함** | OCSP 응답이 언제 만들어진 건지(신선도, Freshness) 브라우저가 대충 철저한 검증함 | **RFC 6960 규격** 대상 따라 **thisUpdate와 nextUpdate 유효기간 범위를 강제 검증** | 구형 상태 응답 재전송 공격(Replay Attack)을 통한 위변조 인증 통과 방어 |
| OCSP 서버가 뻗으니 **모든 사용자가 멀쩡한 사이트 접속이 안 됨** | OCSP 응답을 못 받으면 무조건 접속을 끊어버리는 빡센 '하드 실패(Hard-fail)' 적용됨 | 인터넷 웹 브라우저 환경에서는 서비스 가용성을 위한 **'소프트 실패(Soft-fail)' 적용** | 인프라 장애나 방화벽 막힘으로 인한 대규모 서비스 접속 마비 사태 원천 방지 |

#### 한줄 요약

- 속도와 사생활은 스테이플링으로 지키고, OCSP 서버가 죽었을 때 다 팅기게 할지 융통성(소프트 실패) 발휘할지 잘 정해라.

## Ⅶ. 결론

<details><summary>용어 설명</summary>

- (상단 참조)

</details>

- 폐지 정보의 전파 지연과 사용자의 프라이버시 유출을 막기 위해 **OCSP 스테이플링** 웹 통신의 표준으로 삼고, 내부망엔 **CRL** 보완 운영하며, 서비스 장애(SPOF)를 막기 위해 **소프트 실패(Soft-fail)** 정책을 융통성 있게 적용하는 기조 확립함

#### 한줄 요약

- 폐지 검증은 해킹당한 키의 생명줄을 끊는 기술이지만, 검증하다가 서버가 발생하는 딜레마를 항상 주의해야 한다.
