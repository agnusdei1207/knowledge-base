## Ⅰ. 개요

<details>
<summary>핵심 용어</summary>

- **인증서 폐지**는 유효기간 전이라도 개인키 유출·오발급·권한 상실이 발생한 인증서를 신뢰 대상에서 제외하는 조치이다.

</details>

- 정의/개념: **CRL·OCSP**는 인증서가 만료되기 전에 폐지됐는지를 목록 배포 또는 온라인 질의로 검증하게 하는 인증서 상태 확인 방식
- 배경/필요성: 유효기간 검사만으로는 **사고 인증서 차단 불가**

#### 한줄 요약
- 만료일이 남은 신분증도 분실 신고가 되면 사용할 수 없듯, 인증서도 폐지 신고가 검증자에게 전달되면 즉시 거부해야 한다.

## Ⅱ. 특징

<details>
<summary>핵심 용어</summary>

- **폐지 정보 전파 지연**은 CA가 폐지한 시점과 검증자가 최신 상태를 확인하는 시점 사이의 위험 구간이다.
- **소프트 실패와 하드 실패**는 상태 조회가 실패했을 때 각각 인증서 사용을 허용하거나 거부하는 정책이다.
- **OCSP good**은 폐지 기록이 없다는 뜻이며 인증서의 이름·용도·기간까지 보증하지는 않는다.

</details>

- **폐지 정보 전파 지연** 동안 인증서 허용 가능성
- OCSP `good`의 **폐지 기록 없음**에 한정된 의미
- **소프트 실패는 가용성**, 하드 실패는 보안성 우선

#### 한줄 요약

- 폐지 목록에 없다는 것은 분실 신고가 없다는 뜻일 뿐 이름·용도·기간이 맞다는 뜻은 아니므로, 인증서의 다른 조건도 계속 검증해야 한다.

## Ⅲ. 구조 및 구성요소

<details>
<summary>핵심 용어</summary>

- **CRL 배포점**은 CA가 서명한 폐지 인증서 일련번호 목록을 게시한다.
- **OCSP 응답자**는 요청받은 개별 인증서의 상태와 적용 시각을 서명하여 반환한다.
- **검증자 캐시와 정책**은 상태 정보의 신선도와 조회 실패 시 허용 여부를 결정한다.

</details>

```mermaid
block-beta
    columns 3
    C["CA 폐지 상태 저장소"]
    L["CRL 배포점"]
    O["OCSP 응답자"]
    V["검증자 캐시·정책"]
    T["CA·응답자 검증키"]
    C --- L
    C --- O
    L --- V
    O --- V
    V --- T
```

| 구성요소 | 책임 |
|:---|:---|
| CA 폐지 상태 저장소 | **폐지 일련번호·사유·시각** 보관 |
| CRL 배포점 | **서명된 폐지 목록** 게시 |
| OCSP 응답자 | 인증서별 **상태·적용 시각** 서명 |
| 검증자 캐시·정책 | **신선도·조회 실패 처리** 결정 |
| CA·응답자 검증키 | **CRL·OCSP 응답 출처** 검증 |


#### 한줄 요약

- 폐지 정보도 공격자가 바꾸거나 오래된 정상 응답을 다시 보낼 수 있으므로, 검증자는 서명과 갱신 시각을 함께 확인한다.

## Ⅳ. 흐름도

<details>
<summary>핵심 용어</summary>

- **thisUpdate와 nextUpdate**는 상태 정보가 생성된 기준 시각과 다음 정보가 제공되어야 하는 한계 시각이다.
- **서명·신선도 검증**은 폐지 정보의 출처가 CA 또는 위임 응답자인지와 응답이 아직 유효한지 확인한다.

</details>

```mermaid
sequenceDiagram
    participant C as 인증기관
    participant L as CRL 배포점
    participant O as OCSP 응답자
    participant V as 검증자
    participant P as 검증 정책기
    C->>L: 1. 서명 CRL 게시
    C->>O: 2. 인증서 상태 동기화
    V->>L: CRL 조회
    L-->>V: 서명 CRL
    V->>O: 인증서 상태 요청
    O-->>V: 서명 OCSP 응답
    V->>P: 3. 서명·신선도 검증
    P->>P: 4. 실패 정책 적용
    P-->>V: 폐지 판정
```

**동작 원리**

1. **서명 CRL 게시**: 폐지 일련번호·시각 배포
2. **인증서 상태 동기화**: 응답자에 최신 폐지 상태 반영
3. **서명·신선도 검증**: 출처와 thisUpdate·nextUpdate 확인
4. **실패 정책 적용**: 위험에 따라 소프트·하드 실패 선택


#### 한줄 요약

- 상태 서버가 안 보일 때 무조건 허용하면 공격자가 조회를 방해해 폐지 인증서를 계속 쓸 수 있고, 무조건 거부하면 상태 장애가 서비스 중단으로 이어진다.

## Ⅴ. 종류 및 비교

<details>
<summary>핵심 용어</summary>

- **CRL**은 폐지된 인증서의 일련번호와 사유를 CA가 서명하여 주기적으로 배포하는 목록이다.
- **OCSP**는 특정 인증서의 정상·폐지·알 수 없음 상태를 온라인으로 조회한다.
- **OCSP 스테이플링**은 서버가 미리 받은 서명 OCSP 응답을 TLS 연결에 첨부하여 검증자에게 전달한다.

</details>

| 인증서 폐지 확인 | CRL | OCSP | OCSP 스테이플링 |
|:---|:---|:---|:---|
| 적용 기준 | **대량 검증·폐쇄망** | 최신 **개별 상태가 필요한 검증** | TLS의 **조회 지연·노출 완화** |
| 핵심 특징 | **폐지 목록 일괄 검사** | **인증서별 온라인 질의** | **서명 응답 서버 첨부** |
| 한계 | **목록 증가·배포 지연** | **응답 장애·조회 정보 노출** | 서버의 **응답 갱신 누락** |

> 요약: 목록 규모·신선도·조회 경로로 선택

#### 한줄 요약

- CRL은 전체 분실자 명단을 받아 두고 찾으며, OCSP는 신분증 하나씩 물어보고, 스테이플링은 서버가 미리 받은 공식 답변을 함께 내민다.

## Ⅵ. 실무 고려사항 및 대책

<details>
<summary>핵심 용어</summary>

- **RFC 5280**은 인터넷 X.509 인증서와 CRL 프로파일 및 검증 절차를 규정한다.
- **RFC 6960**은 인증서별 현재 상태를 질의하고 응답하는 OCSP를 규정한다.

</details>

| 문제 | 대책 | 효과 |
|:---|:---|:---|
| **CRL 형식·검증 오류** | **IETF RFC 5280 적용** | **목록 상호운용성** 확보 |
| **OCSP 상태·신선도 오류** | **IETF RFC 6960 검증** | **재전송·오판정 억제** |
| **상태 서비스 장애** | **위험별 실패 정책·캐시** | **보안·가용성 균형** |

#### 한줄 요약

- 공개 TLS 서버가 최신 OCSP 응답을 연결에 첨부하면 클라이언트가 인증기관에 직접 질의하지 않고도 폐지 상태를 확인할 수 있다.

## Ⅶ. 결론

<details>
<summary>핵심 용어</summary>

- **폐지 확인 방식 선택**은 목록 규모·필요한 신선도·조회 경로의 가용성과 장애 시 위험을 함께 고려한다.

</details>

- 대량·폐쇄망은 **CRL**, 공개 TLS의 저지연 검증은 **OCSP 스테이플링** 선택

#### 한줄 요약

- 새 폐지 정보의 도착 시점과 조회 실패 때 연결 허용 여부를 서비스 위험에 맞춰 정한다.
