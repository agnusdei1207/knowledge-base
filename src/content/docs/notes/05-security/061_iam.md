## Ⅰ. 개요

<details><summary>용어 설명</summary>

- **IAM(Identity and Access Management, 신원 및 접근 관리)**: 기업 내 모든 디지털 신원(사용자, 서비스 계정, 기기)에 대해 생성(입사), 변경(부서 이동), 검토(재인증), 회수(퇴사)로 이어지는 **신원 생애주기(Identity Lifecycle)** 를 중앙에서 통제하고, 자원에 대한 적절한 인증(AuthN) 및 인가(AuthZ)를 집행하는 통합 보안 거버넌스 체계.
- **권한 축적 및 고아 계정(Privilege Creep & Orphan Account Defect)**: 부서 이동 시 이전 부서의 접근 권한이 회수되지 않고 계속 누적되거나(Privilege Creep), 퇴사자의 계정이 시스템별로 개별 방치(Orphan Account)되어 내부 침해사고 및 데이터 유출의 통로로 악용되는 거버넌스 결함.

</details>

- 정의/개념: 권위 있는 원천(인사 DB/IdP)과 대상 시스템(ERP, 클라우드, 사내망) 간에 **JML(Joiner-Mover-Leaver) 자동 프로비저닝(SCIM) $\rightarrow$ 역할/속성 기반 인가(RBAC/ABAC) $\rightarrow$ 정기 접근 재인증(Recertification) $\rightarrow$ 감사 대조(Reconciliation)** 를 집행하는 **전사 신원 거버넌스 아키텍처**
- 배경/필요성: 온프레미스와 멀티 클라우드(AWS, Azure, SaaS)가 혼재된 하이브리드 인프라에서 수동 계정 관리의 한계를 극복하고, 최소 권한 원칙(Least Privilege)을 자동화하여 계정 도용 및 내부 부정 위험을 원천 차단할 요구

#### 한줄 요약
- 인사 데이터와 연동된 JML 생애주기 자동화, SCIM 프로비저닝, 정기 권한 재인증 및 감사 대조로 신원 무결성을 보장한다.

## Ⅱ. 특징

<details><summary>용어 설명</summary>

- **JML(Joiner-Mover-Leaver) 생애주기 모델**:
  - **Joiner (입사)**: 인사 DB 생성 즉시 직무에 필요한 기본 계정/권한 자동 프로비저닝.
  - **Mover (이동/승진)**: 부서 이동 즉시 이전 부서 권한 자동 회수 및 신규 부서 권한 할당.
  - **Leaver (퇴사)**: 퇴사 처리 즉시 전 시스템 계정 비활성화 및 세션 강제 만료(Deprovisioning).
- **감사 대조(Audit Reconciliation)**: IAM 중앙 저장소의 정책상 승인된 권한 상태와 실제 타깃 시스템(OS, DB, SaaS)에 설정된 계정/권한 상태를 주기적으로 크로스체크하여 불일치(비인가 수동 생성 계정)를 강제 교정하는 절차.

</details>

- **단일 진실 원천(Single Source of Truth) 기반 동기화**: 인사(HR) DB의 신원 변경 이벤트가 전사 대상 시스템으로 실시간 전파
- **SCIM(RFC 7644) 표준 프로비저닝**: 이기종 클라우드 및 온프레미스 애플리케이션 간 계정 프로비저닝 인터페이스 표준화
- **폐쇄 루프 접근 거버넌스 (Closed-Loop Governance)**: 정기 권한 재인증을 통해 불필요한 잔존 권한을 상시 회수하고 감사 증적 보존

#### 한줄 요약
- JML 생애주기 자동화, SCIM 표준 프로비저닝, 정기 접근 재인증, 감사 대조 기반 자동 교정을 제공한다.

## Ⅲ. 구조 및 구성요소

<details><summary>용어 설명</summary>

- **SCIM(System for Cross-domain Identity Management / RFC 7643 & RFC 7644)**: 클라우드 기반 애플리케이션 및 엔터프라이즈 시스템 간에 사용자 신원 데이터(JSON)를 안전하고 표준화되게 생성, 수정, 삭제(CRUD)하기 위한 RESTful API 규격.

</details>

```text
┌─────────────────────────────────────────────────────────────────────────┐
│ [ 1. 권위 있는 신원 원천 (Authoritative Source: HR 인사 시스템) ]       │
│  └─ [ 입사 / 인사이동 / 퇴사 이벤트 발생 ➔ 웹훅(Webhook) 이벤트 발행 ] │
└────────────────────────────────────┬────────────────────────────────────┘
                                     │ (신원 변경 이벤트 수신)
                                     ▼
┌─────────────────────────────────────────────────────────────────────────┐
│ [ 2. IAM / IGA 중앙 거버넌스 엔진 (Identity Governance & Administration)│
│  ├─ 역할/속성 정책 엔진: RBAC / ABAC 기반 권한 자동 산출                │
│  ├─ 워크플로우 관리자: 비즈니스 예외 권한 신청 및 관리자 결재 승인      │
│  └─ 접근 재인증 모듈: 분기별 부서장 대상 권한 재검토 및 미확인 권한 회수│
└────────────────────────────────────┬────────────────────────────────────┘
                                     │ (SCIM 2.0 REST API 프로비저닝 명령)
                                     ▼
┌─────────────────────────────────────────────────────────────────────────┐
│ [ 3. 대상 타깃 시스템 계층 (Target Systems: Cloud / On-Prem / SaaS) ]    │
│  ├─ Enterprise SaaS (Salesforce, Microsoft 365, Slack)                  │
│  ├─ Cloud IaaS (AWS IAM, Azure AD, GCP Cloud IAM)                       │
│  └─ On-Premises (Active Directory, LDAP, RDBMS, ERP)                    │
└────────────────────────────────────┬────────────────────────────────────┘
                                     │ (주기적 감사 텔레메트리 수집)
                                     ▼
┌─────────────────────────────────────────────────────────────────────────┐
│ [ 4. 감사 대조 및 컴플라이언스 엔진 (Audit Reconciliation Engine) ]      │
│  └─ [ 타깃 시스템 실제 권한 vs IAM 정책 상태 비교 ➔ 불일치 시 자동 교정]│
└─────────────────────────────────────────────────────────────────────────┘
```

선의 의미: 인사 시스템의 이벤트가 IAM 엔진을 통해 타깃 시스템으로 SCIM 자동 프로비저닝되고, 감사 대조 엔진을 통해 지속적으로 불일치를 교정하는 구조

| 구성요소 | 핵심 책임 및 역할 | 비고 |
|:---|:---|:---|
| **Authoritative Source** | 직원의 재직 상태, 부서, 직급 등 신원 데이터의 원천 진실(Truth) 제공 | HR System |
| **IAM/IGA 거버넌스 엔진** | JML 생애주기 이벤트 처리, 역할 기반 권한 산출, 권한 승인 워크플로우 통제 | Core Engine |
| **SCIM 프로비저너** | IETF RFC 7644 REST API를 통해 타깃 시스템에 계정 생성/수정/삭제 명령 집행 | SCIM 2.0 |
| **접근 재인증 모듈** | 정기적으로 부서장에게 소속원의 권한 목록을 제시하고 불필요 권한 회수 유도 | Recertification |
| **감사 대조 엔진 (Reconciliation)**| 비인가 수동 생성 계정 및 잔존 권한을 탐지하여 IAM 표준 상태로 강제 롤백 | Compliance |

#### 한줄 요약
- 권위 원천(HR), IAM/IGA 거버넌스 엔진, SCIM 프로비저너, 접근 재인증 모듈, 감사 대조 엔진이 결합한다.

## Ⅳ. 흐름도

<details><summary>용어 설명</summary>

- **JML(Joiner-Mover-Leaver) 프로비저닝 5단계 처리 과정**:
  1. HR 시스템 상태 변경 이벤트 발생
  2. IAM 엔진이 역할 매핑 및 변경 사항 산출
  3. 최소 권한 정책 및 SoD(직무 분리) 검증
  4. SCIM 커넥터를 통한 타깃 시스템 API 동시 호출
  5. 처리 결과 로깅 및 감사 대조

</details>

```text
1. [인사 이동 이벤트 수신] HR DB에서 `김엔지니어(개발팀 ➔ 기획팀)` 발령 정보 수신
            │
            ▼
2. [권한 델타(Delta) 계산]
    ├─ 회수 대상: 개발망 VPN 접근 권한, Git 리포지토리 쓰기 권한, AWS 개발 계정
    └─ 신규 부여: 기획 포털 접근 권한, Confluence 기획 스페이스 읽기/쓰기 권한
            │
            ▼
3. [직무 분리(SoD) 검증] 신규 권한 조합이 조직의 정적 직무 분리(SSD) 정책에 위배되는지 사전 심사
            │
            ▼
4. [SCIM 자동 프로비저닝 집행]
    ├─ AWS, GitHub, SaaS API를 동시 호출하여 기존 권한 즉시 박탈 및 신규 권한 적용
    └─ [퇴사 이벤트인 경우: 전 시스템 계정 즉각 비활성화(Disable) 및 세션 강제 종료]
            │
            ▼
5. [감사 대조 및 증적 보존] 타깃 시스템별 적용 완료 응답을 수집하고 SIEM에 신원 변경 감사 로그 저장
```

**동작 원리**

1. **이벤트 기반 즉각성**: 인사 발령 시점과 IT 시스템 권한 변경 시점 간의 시차(Time Lag)를 0으로 수렴
2. **원자적 권한 교체(Atomic Swap)**: 부서 이동 시 신규 권한 부여와 이전 권한 회수가 단일 트랜잭션으로 완결
3. **표준 인터페이스 일원화**: 프로프라이어터리(Proprietary) 스크립트 대신 SCIM 2.0 표준 규격으로 프로비저닝
4. **그림자 계정(Shadow Account) 색출**: 감사 대조를 통해 관리자가 수동으로 생성한 비인가 백도어 계정 자동 폐쇄
5. **컴플라이언스 준수성**: ISMS-P, SOX, GDPR 등 규제 기관이 요구하는 권한 승인 증적을 자동화

#### 한줄 요약
- 인사 이벤트 수신, 권한 델타 계산, SoD 검증, SCIM 자동 프로비저닝, 감사 대조 및 로깅 순으로 동작한다.

## Ⅴ. 종류 및 비교

<details><summary>용어 설명</summary>

- **신원 관리 3대 아키텍처 비교**: 수동 관리(Legacy), 온프레미스 중앙 IAM, 클라우드 연합 IAM(Federated)의 비교.

</details>

| 비교 항목 | 수동 관리 (Manual Legacy) | 온프레미스 중앙 IAM (Centralized) | 클라우드 연합 IAM (Federated / IDaaS) |
|:---|:---|:---|:---|
| **프로비저닝 방식** | 시스템 관리자의 수작업 CLI/GUI 입력 | **사내 스크립트 및 전용 커넥터 연동** | **SCIM 2.0 기반 클라우드 자동 프로비저닝** |
| **적용 인프라 영역** | 폐쇄형 레거시 시스템 | 온프레미스 사내망 및 AD 도메인 | **하이브리드, 멀티 클라우드, SaaS 전역** |
| **퇴사자 권한 회수율** | **극히 낮음 (고아 계정 및 잔존 권한 다수)**| 높음 (사내망 자원에 한정 회수) | **100% 완벽 (SAML/OIDC/SCIM 통합 즉시 차단)**|
| **표준 프로토콜 활용**| 없음 (독자 수동 절차) | LDAP, Kerberos, AD DS | **SCIM, SAML 2.0, OpenID Connect** |
| **운영 복잡도 및 비용**| **높은 인건비 및 휴먼 에러 위험** | 구축 및 유지보수 비용 높음 | **운영 오버헤드 최소화 (IDaaS 서비스 모델)**|

#### 한줄 요약
- 수동 관리는 오류와 누락 위험, 중앙 IAM은 사내망 통제, 연합 IAM/IDaaS는 하이브리드 전역의 표준화된 자동화이다.

## Ⅵ. 실무 고려사항 및 대책

<details><summary>용어 설명</summary>

- **NIST SP 800-63-3 신원 보증 수준(IAL / AAL / FAL)**:
  - **IAL (Identity Assurance Level)**: 신원 확인 엄격성.
  - **AAL (Authenticator Assurance Level)**: 인증 메커니즘 강도(MFA 등).
  - **FAL (Federation Assurance Level)**: SAML/OIDC 연합 토큰의 암호학적 보호 강도.

</details>

| 문제 | 대책 | 효과 |
|:---|:---|:---|
| 이기종 시스템 및 클라우드 서비스마다 API 규격이 달라 **퇴사자 발생 시 계정 삭제 명령 전달 실패 및 고아 계정 방치** | **IETF RFC 7644** 준수, 전사 시스템 연동 인터페이스로 **SCIM 2.0 표준 RESTful 프로비저닝 강제** | 이기종/SaaS 시스템 간 계정 생애주기 자동화 100% 달성 및 벤더 종속성 탈피 |
| 부서 이동이 잦은 직원의 이전 부서 권한이 회수되지 않아 **과다 권한(Privilege Creep)을 악용한 데이터 유출 발생** | **인사 이동 시 이전 권한 자동 회수(Atomic Deprovisioning) 및 분기별 정기 접근 재인증(Recertification)** | 불필요 잔존 권한 100% 원천 회수 및 직무 권한 최소화 유지 |
| 타깃 시스템에서 관리자가 수동으로 생성한 로컬 계정이 **IAM 통제를 우회하여 백도어로 악용되는 침해 사고** | **타깃 시스템의 실제 계정 상태와 IAM 기준선을 대조하는 감사 대조(Reconciliation) 및 자동 폐쇄** | 비인가 그림자 계정(Shadow Account) 및 관리자 수동 생성 계정 100% 색출 및 제거 |

#### 한줄 요약
- SCIM 표준으로 프로비저닝을 일원화하고, 재인증으로 잔존 권한을 회수하며, 감사 대조로 그림자 계정을 제거한다.

## Ⅶ. 결론

- 엔터프라이즈 제로 트러스트 보안의 최상위 거버넌스 프레임워크인 **IAM 아키텍처**는 모든 접근 제어의 신원 기준선을 확립하는 인프라로서, 실무 구현 시 **NIST SP 800-63 기반 신원/인증 보증 수준 확립**, **SCIM 2.0 기반의 JML 생애주기 자동 프로비저닝**, **정기 접근 재인증(Recertification) 및 지속적 감사 대조(Reconciliation)** 를 결합하여 무결점 신원 수명주기 및 최소 권한 통제를 완성

#### 한줄 요약
- JML 생애주기 자동화와 SCIM 표준 프로비저닝 및 지속적 감사 대조를 통해 완결된 IAM 거버넌스를 완성한다.
