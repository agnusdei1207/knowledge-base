## Ⅰ. 개요

<details><summary>용어 설명</summary>

- **IAM (신원 및 접근 관리)**: 직원이 입사해서 퇴사할 때까지, 어떤 시스템에 접근할 수 있는지 권한을 줬다 뺐었다 하는 전체 생애주기 팩트 관리 시스템이다.
- **디지털 신원 (Digital Identity)**: 사람(직원), 서비스, 장치를 IT 시스템 상에서 식별할 수 있게 해주는 속성 및 계정의 팩트 집합이다.

</details>

- 정의: 디지털 신원과 접근 권한의 생성, 변경, 검토, 회수 등 전체 수명주기(Lifecycle)를 중앙 통제하는 팩트 관리 체계이다.
- 배경: 부서장이 시스템마다 계정을 수동으로 파주다 보니, 퇴사자 계정(고아 계정)이 방치되거나 과다 잔존 권한이 대량으로 팩트 유발되기 때문이다.

#### 한줄 요약

- 사원이 입사, 부서 이동, 퇴사할 때마다 사내 모든 시스템의 계정과 권한을 알아서 팩트로 세팅하고 지워주는 중앙 통제탑이다.

## Ⅱ. 특징

<details><summary>용어 설명</summary>

- **프로비저닝 (Provisioning)**: 인사팀에서 "홍길동 입사"를 찍으면, 사내 메일, ERP, 메신저 계정이 자동으로 팩트 쫙 만들어지는 자동화 처리 기술이다.
- **접근 검토 (Access Review)**: 분기마다 부서장한테 "김대리 아직도 이 DB 권한 필요합니까?" 물어보고, 필요 없다면 즉시 팩트로 회수하는 정기 감사 절차다.

</details>

- **팩트 수명주기 자동화**: 권위 원천(인사 DB)의 신원 상태 변화(입사/퇴사)를 수많은 대상 시스템의 계정 프로비저닝(생성/삭제)으로 팩트 자동 연계한다.
- **팩트 중앙 통제**: 로그인(인증), 권한(인가), 계정 발급(프로비저닝) 정책을 단일 통제 흐름으로 묶어 관리 공백을 팩트로 원천 제거한다.
- **팩트 최소 권한 유지**: 정기적인 접근 검토(Access Review)를 팩트로 강제하여, 쓸데없는 잔존 권한을 걷어내고 오남용 위험을 팩트 차단한다.

#### 한줄 요약

- 인사 데이터랑 묶어서 계정을 자동으로 파주고, 로그인 통제하고, 분기마다 권한 검사해서 팩트로 회수한다.

## Ⅲ. 구조 및 구성요소

<details><summary>용어 설명</summary>

- **권위 원천 (Authoritative Source)**: IAM이 무조건 믿고 따르는 팩트의 근원이다. (보통 회사의 인사팀 데이터베이스가 여기에 해당한다)
- **감사 대조 (Audit Reconciliation)**: "IAM에는 권한 뺐다고 나오는데, 실제 ERP 서버 까보니 아직 권한 있네?" 하고 기준과 실제 상태의 불일치를 팩트로 찾아내서 강제 교정하는 작업이다.

</details>

```text
[ 통합 신원 및 접근 관리(IAM) 팩트 구조 ]

[ 1. 권위 원천 (인사 DB) ] ── ("홍길동 대리, 오늘부로 퇴사 팩트 처리됨")
      │
      ▼
[ 2. IAM 중앙 컨트롤 타워 ] ── ("권위 원천 데이터 수신! 퇴사자 팩트 확인!")
      │
      ▼
[ 3. 수명주기 및 프로비저닝 ] ── ("사내 메일, ERP, 그룹웨어에 '홍길동 계정 당장 닫아라' 팩트 명령 쏨")
      │
      ▼
[ 4. 대상 시스템 및 연합 인증 ] ── ("명령받고 계정 잠금 및 로그인(MFA) 세션 즉각 팩트 강제 종료함")
      │
      ▼
[ 5. 감사 대조 및 거버넌스 ] ── ("실제로 싹 다 잠겼는지 팩트 크로스체크하고 보고서 씀")
```

| 구성요소 | 팩트 폭행 책임 | 비고 |
|:---|:---|:---|
| **권위 원천 (HR DB)** | 입사, 부서 이동, 퇴사 등 **모든 신원 상태의 단일 진실 기준(팩트)을 제공함** | Source |
| **수명주기 / 프로비저닝** | 인사 이동에 맞춰 **타겟 시스템의 계정과 권한을 자동으로 팩트 생성/변경/회수함** | Lifecycle |
| **인증 / 연합 (MFA/SSO)** | 실제 사용자가 로그인할 때 **다중 요소(MFA)나 통합(SSO)으로 신원을 팩트로 검증함** | Auth |
| **권한 거버넌스 (Governance)** | 부서장의 결재나 정기 접근 검토(Review)를 통해 **권한 승인/회수를 팩트로 통제함** | Governance |
| **감사 대조 (Reconciliation)** | 서류상(IAM) 권한과 실제(서버) 권한이 팩트로 일치하는지 **크로스체크하고 자동 교정함** | Audit |

#### 한줄 요약

- 인사팀 DB(권위 원천)를 기준으로, 계정을 파주고(프로비저닝), 결재받고(거버넌스), 똑바로 됐는지 검사(감사 대조)한다.

## Ⅳ. 흐름도

<details><summary>용어 설명</summary>

- (상단 참조)

</details>

```text
[ IAM 신원 수명주기 및 팩트 프로비저닝 흐름 ]

┌──────────────────────────────┐
│ 1. [권위 원천(HR DB) 신원 상태 팩트 검증]
│ ("인사 DB에서 '김과장 영업팀 $\to$ 재무팀 발령' 팩트 접수함")
└──────────────┬───────────────┘
               ▼
┌──────────────────────────────┐
│ 2. [역할/속성 기반 권한 후보 팩트 계산]
│ ("재무팀으로 갔으니, 기존 영업 권한은 뺏고 재무 ERP 권한을 팩트로 산출함")
└──────────────┬───────────────┘
               ▼
┌──────────────────────────────┐
│ 3. [최소 권한 및 만료/회수 팩트 확정]
│ ("이 권한은 언제까지만 쓸 수 있게 할지(유효기간) 팩트로 결정함")
└──────────────┬───────────────┘
               ▼
┌──────────────────────────────┐
│ 4. [프로비저닝(Provisioning) 명령 팩트 생성]
│ ("각 대상 서버 API로 '얘 권한 업데이트해라' 하고 명령을 팩트로 쏨")
└──────────────┬───────────────┘
               ▼
┌──────────────────────────────┐
│ 5. [신원/권한 상태 적용 및 감사 팩트 기록]
│ ("대상 서버가 명령 처리 후 '성공' 응답 주면 IAM에 팩트로 기록함")
└──────────────────────────────┘
```

### 동작 원리

1. 신원 검증: **권위 원천**에서 주체의 소속, 고용 상태(입/퇴사) 변경 이벤트를 팩트 확인.
2. 후보 계산: 정책 및 역할(RBAC)을 기반으로 해당 사용자에게 쥐여줄 권한을 팩트 도출.
3. 권한 확정: 부여할 권한의 범위, 승인 조건, 유효기간(TTL)을 최소 권한 원칙으로 팩트 확정.
4. 명령 생성: 대상 시스템별(ERP, 메일 등) 계정/권한 프로비저닝 타겟 명령을 팩트 생성.
5. 상태 적용: 타겟 시스템이 계정을 잠그거나 권한을 갱신하고, 미반영분은 **감사 대조**로 팩트 적발.

#### 한줄 요약

- 인사 변동 확인 $\to$ 권한 계산 $\to$ 유효기간 세팅 $\to$ 서버로 명령 발송 $\to$ 처리 결과 팩트 로그 기록이다.

## Ⅴ. 종류 및 비교

<details><summary>용어 설명</summary>

- (상단 설명 참조)

</details>

| 신원 권한 관리 방식 | **수동 관리 (Manual)** | **중앙 IAM (Centralized)** | **연합 IAM (Federated / Cloud)** |
|:---|:---|:---|:---|
| 팩트 폭행 비유 | **신입 올 때마다 서버 관리자가 일일이 수작업으로 계정 파주는 생노가다** | **사내 인사 DB랑 연동돼서 클릭 한 번에 사내 시스템 싹 다 세팅되는 팩트 마법** | **우리 회사 사원증(SSO)으로 외부 클라우드(AWS, SaaS)까지 팩트로 뚫는 프리패스** |
| 핵심 특징 | 시스템마다 관리자가 **각각 따로따로 권한을 팩트로 쌩수작업 부여함** | 조직 내 수많은 사내 시스템의 **신원 수명주기를 IAM이 일관되게 중앙 팩트 통제함** | SAML, OIDC 등 표준을 써서 **조직 경계를 넘어 클라우드 서비스까지 팩트 연계함** |
| 한계 및 문제점 | 퇴사자 권한 회수가 100% 누락되고 **고아 계정(Orphan)이 무더기로 팩트 양산됨** | 다양한 사내 구형 시스템들(Legacy)을 **전부 연동시키는 개발/인터페이스 작업이 팩트로 빡셈** | 외부망과 신뢰 설정 맺는 게 복잡하고, **연합 토큰 털리면 클라우드까지 싹 다 팩트로 털림** |

#### 한줄 요약

- 사내 시스템은 묶어서 **중앙 IAM** 돌리고, 외부 SaaS/클라우드는 **연합 IAM**으로 팩트 뚫어버린다.

## Ⅵ. 실무 고려사항 및 대책

<details><summary>용어 설명</summary>

- **SCIM (교차 도메인 신원 관리 체계)**: IAM이 여러 이기종 시스템들한테 "계정 파라", "비번 바꿔라" 하고 명령을 내릴 때 쓰는 글로벌 표준 REST API 팩트 규격이다.
- **NIST SP 800-63**: 사용자한테 암호만 받을 건지, OTP(MFA)까지 받을 건지 등 깐깐한 인증(AAL) 보증 수준을 팩트로 가이드하는 국제 보안 표준이다.

</details>

| 장애/위험 요소 | 원인 분석 | 실무 대책 및 해결방안 | 기대 효과 |
|:---|:---|:---|:---|
| 서버마다 API가 달라서 **퇴사자 계정 잠금 명령을 IAM이 팩트로 못 날림** | 이기종 시스템 간 계정 생성/삭제(프로비저닝) 통신 규격이 파편화되어 연동이 팩트로 끊김 | **IETF RFC 7644** 기반의 **SCIM 표준 REST API 팩트 연동 적용** | 이기종 및 클라우드(SaaS) 시스템 간 프로비저닝 자동화 및 벤더 종속성 팩트 탈피 |
| 인증 대충 해줬다가 **남의 계정으로 로그인해서 IAM 권한 통제가 팩트로 무력화됨** | 신원을 검증하는 보증 수준(비밀번호, MFA 등)이 시스템마다 들쭉날쭉함 | **NIST SP 800-63** 지침에 따라 신원(IAL) 및 인증(AAL) **보증 수준 팩트 하드닝** | 허술한 인증 우회 방지 및 전사적 신원 보증 수준(Assurance Level) 팩트 상향 평준화 |
| IAM에는 권한 뺐다고 뜨는데 **실제 서버 까보니까 권한이 버젓이 팩트로 살아있음** | 프로비저닝 네트워크 에러로 명령이 씹히고(고아 계정 생성), 그걸 팩트로 검사 안 함 | IAM 데이터와 대상 시스템 DB 간 **주기적 감사 대조(Reconciliation) 및 즉시 자동 교정 팩트 집행** | 잔존 권한 방치에 따른 내부자 무단 정보 유출 팩트 원천 차단 |

#### 한줄 요약

- 통신은 **SCIM** 표준 쓰고, 로그인 수준은 **NIST** 기준 맞추고, 에러난 건 **감사 대조**로 팩트 교정해라.

## Ⅶ. 결론

<details><summary>용어 설명</summary>

- **상태 전파 완결성 (State Propagation Completeness)**: "홍길동 퇴사!"라는 이벤트가 발생했을 때, 사내 100개 시스템의 모든 계정, 세션, 토큰이 결함 하나 없이 100% 팩트로 잠겼는지 입증하는 핵심 운영 기준이다.

</details>

- 수천 개의 계정과 클라우드가 혼재하는 엔터프라이즈 환경에서는, 인사 DB(권위 원천) 기반의 **중앙 IAM**과 **연합 IAM(SAML/OIDC)**을 결합하고, **SCIM** 표준 프로비저닝과 철저한 **감사 대조**를 통해 퇴사자 계정 회수의 **상태 전파 완결성**을 무결점 팩트로 입증하는 실무 기조를 확립함

#### 한줄 요약

- 인사DB 연동 팩트 체크하고, 내부는 **중앙 IAM**, 외부는 **연합 IAM**으로 상태 전파 완결성 챙겨라.
