## Ⅰ. 개요

<details><summary>용어 설명</summary>

- **보안 구성 관리(Security Configuration Management, SCM)**: 조직 내 모든 IT 인프라(OS, 서버, 네트워크 장비, 데이터베이스, 클라우드 워크로드)의 설정 상태를 공인된 표준 보안 기준선(Security Baseline)에 부합하도록 정의하고, 배포 전 정적 검증부터 운영 중 런타임 구성 편차(Configuration Drift) 감시 및 자동 원복(Auto-Remediation)까지 전 생애주기에 걸쳐 지속 통제하는 보안 거버넌스 체계.
- **구성 편차(Configuration Drift)**: 최초에 안전하게 배포된 표준 보안 기준선(Baseline) 상태에서, 운영자의 임의 수동 변경, 긴급 장애 조치 후 미원복, 비인가 소프트웨어 설치 등으로 인해 시스템 설정이 목표 보안 상태를 이탈하여 취약점이 발생하는 현상.

</details>

- 정의/개념: NIST SP 800-128 표준에 기반하여 **표준 하드닝 기준선(CIS Benchmarks) 수립 $\rightarrow$ 배포 전 IaC 정적 정책 검사(Policy-as-Code) $\rightarrow$ 런타임 실시간 드리프트(Drift) 탐지 $\rightarrow$ 자동 원복 및 기한부 예외 통제** 를 집행하는 **인프라 무결성 통제 아키텍처**
- 배경/필요성: 소프트웨어 자체의 버그보다 방화벽 규칙 개방, 디폴트 계정 방치, 안전하지 않은 암호화 스위트 허용 등 운영 중 발생하는 설정 오류(Misconfiguration)가 클라우드 및 온프레미스 침해사고의 80% 이상을 차지하는 구조적 취약성을 통제할 요구

#### 한줄 요약
- CIS 벤치마크 기준선 수립, IaC 배포 전 검증, 런타임 편차(Drift) 탐지 및 자동 원복을 통해 인프라 설정을 안전하게 유지한다.

## Ⅱ. 특징

<details><summary>용어 설명</summary>

- **코드 기반 정책 검증(Policy-as-Code / OPA & Rego)**: 인프라를 프로비저닝하기 전, 테라폼(Terraform)이나 쿠버네티스 매니페스트(YAML) 파일 내의 보안 설정 위반(예: S3 버킷 공개 읽기 허용, SSH 22번 포트 전세계 개방)을 CI/CD 파이프라인에서 정적으로 차단하는 Shift-Left 기술.
- **자동 원복(Auto-Remediation) & 기한부 예외(Time-bound Exceptions)**: 런타임에 비인가 구성 편차가 감지되었을 때 에이전트/API를 통해 목표 기준선으로 즉시 강제 원상 복구하며, 비즈니스상 불가피한 예외 요청은 보상 통제 하에 만료 기한(TTL)을 부여하여 시한부로 관리하는 통제 방식.

</details>

- **전사 보안 기준선(Baseline) 표준화**: 자산 유형별(Linux, Windows, Kubernetes, AWS) CIS 벤치마크 기반 하드닝 규격 확립
- **Shift-Left 사전 통제와 런타임 감시 결합**: 빌드/배포 단계의 정적 검증과 운영 단계의 동적 드리프트 탐지를 상호보완적으로 운영
- **불변 인프라(Immutable Infrastructure) 지향**: 운영 중인 서버의 인플레이스(In-place) 수동 수정을 금지하고 코드를 통한 재배포 강제

#### 한줄 요약
- CIS 벤치마크 표준화, IaC Shift-Left 검증, 런타임 드리프트 실시간 탐지, 자동 원복 및 기한부 예외 통제를 제공한다.

## Ⅲ. 구조 및 구성요소

<details><summary>용어 설명</summary>

- **SCM 4대 핵심 통제 계층**:
  1. **기준선 정의 계층**: 자산별 하드닝 규칙(CIS Level 1/2) 수립
  2. **빌드/배포 계층**: CI/CD 파이프라인 정적 IaC 검사 (Checkov, tfsec)
  3. **런타임 감시 계층**: 실시간 드리프트 감지 (CSPM, Host Agent)
  4. **교정 및 거버넌스 계층**: 자동 원복(Ansible, Lambda) 및 예외 만료 추적

</details>

```text
[ 1. 표준 보안 기준선 수립 (CIS Benchmarks / DISA STIG) ]
                             │
                             ▼
┌─────────────────────────────────────────────────────────────────────────┐
│ [ 2. 배포 전 정적 정책 검사 계층 (Pre-Deployment / Policy-as-Code) ]    │
│  ├─ CI/CD 파이프라인 내 IaC 스캔 (Terraform / K8s YAML)                 │
│  └─ OPA (Open Policy Agent) 게이트웨이 ➔ [ 보안 위반 시 빌드 즉시 차단 ]│
└────────────────────────────────────┬────────────────────────────────────┘
                                     │ (검증 완료된 안전한 인프라 배포)
                                     ▼
┌─────────────────────────────────────────────────────────────────────────┐
│ [ 3. 운영 인프라 런타임 감시 계층 (Runtime Drift Detection Layer) ]      │
│  ├─ CSPM / CIEM: 클라우드 리소스 설정 주기적 API 폴링 스캔             │
│  └─ 호스트 SCM 에이전트: OS 레지스트리, 파일 권한, sshd_config 상시 감시 │
└────────────────────────────────────┬────────────────────────────────────┘
                                     │ (비인가 구성 편차(Drift) 발생 감지)
                                     ▼
┌─────────────────────────────────────────────────────────────────────────┐
│ [ 4. 자동 원복 및 예외 거버넌스 계층 (Auto-Remediation & Governance) ]  │
│  ├─ 자동 원복 엔진: AWS Lambda / Ansible ➔ 목표 기준선으로 즉시 강제 복귀│
│  └─ 기한부 예외 관리: 승인된 예외 건에 대해 TTL(30일) 부여 및 만료 시 회수│
└─────────────────────────────────────────────────────────────────────────┘
```

선의 의미: 표준 기준선이 배포 전 IaC 검증을 거쳐 프로덕션에 적용되고, 런타임 드리프트 발생 시 자동 원복 엔진과 기한부 예외 관리로 교정되는 구조

| 구성요소 | 핵심 책임 및 역할 | 비고 |
|:---|:---|:---|
| **기준선 정의 엔진** | OS, 네트워크, DB, 클라우드별 CIS 벤치마크 기반 전사 하드닝 템플릿 수립 | Baseline Scope |
| **IaC 정적 검사기 (Shift-Left)**| 배포 전 테라폼/클라우드포메이션 코드의 보안 설정 결함을 CI/CD에서 차단 | Policy-as-Code |
| **런타임 편차 탐지기** | 운영 중인 호스트 및 클라우드 자산의 실시간 설정과 목표 기준선 간 편차(Drift) 감시 | Drift Detection |
| **자동 교정기 (Remediator)** | 비인가 편차 감지 시 Ansible 플레이북 또는 서버리스 함수를 통해 표준 설정으로 원복 | Auto-Remediation |
| **기한부 예외 관리기** | 업무상 불가피한 보안 예외 요청에 대해 만료 기한을 설정하고 만료 시 자동 원복 | Exception TTL |

#### 한줄 요약
- 기준선 정의기, IaC 정적 검사기, 런타임 편차 탐지기, 자동 교정기, 기한부 예외 관리기가 결합한다.

## Ⅳ. 흐름도

<details><summary>용어 설명</summary>

- **NIST SP 800-128 보안 구성 관리 5단계 수명주기**:
  1. **계획(Planning)**: 정책 및 기준선 정의
  2. **식별(Identifying)**: 대상 구성 요소 식별
  3. **통제(Controlling)**: 변경 관리 및 배포 통제
  4. **모니터링(Monitoring)**: 드리프트 스캔 및 감사
  5. **교정(Remediating)**: 편차 복구 및 예외 회수

</details>

```text
1. [기준선 매핑] 엔터프라이즈 환경에 맞춘 Linux OS CIS Benchmark Level 1 하드닝 템플릿 정의
            │
            ▼
2. [IaC 정적 검증] 개발자가 작성한 Terraform 코드 커밋 ➔ CI/CD 파이프라인에서 OPA 정적 정책 검사
            │
            ├─ [보안 룰 위반 발견 시] ➔ 파이프라인 실패(Fail) 및 개발자에게 피드백 후 수정 요구
            ▼
3. [승인 구성 배포] 검증을 통과한 인프라 코드를 프로덕션 클라우드 환경에 안전하게 프로비저닝
            │
            ▼
4. [런타임 드리프트 감시] CSPM 도구가 1시간 주기로 운영 자산 스캔 ➔ [운영자에 의한 0.0.0.0/0 보안그룹 개방 감지]
            │
            ▼
5. [자동 원복 및 통제]
    ├─ 표준 절차: EventBridge 트리거 ➔ Lambda가 비인가 보안그룹 룰 즉시 삭제 (목표 기준선 복원)
    └─ 기한부 예외: 긴급 점검 사유로 승인된 티켓인 경우 7일간 예외 등록 후 기한 만료 시 자동 회수
```

**동작 원리**

1. **표준화된 설정 주입**: 인프라 프로비저닝 시 골든 이미지(Golden Image)와 표준 템플릿 적용
2. **사전 결함 유입 차단**: 잘못된 설정이 운영망에 배포되기 전 코드 레벨에서 선제 차단
3. **지속적 무결성 감사**: API 폴링 및 에이전트를 통해 실시간 시스템 상태와 기준선 대조
4. **인간 개입 없는 자가 치유**: 비인가된 보안 완화 조치를 무인 스크립트로 밀리초 단위 원복
5. **기술 부채 방지**: 예외 설정을 영구 방치하지 않고 시한부 라이프사이클로 엄격 통제

#### 한줄 요약
- 기준선 매핑, IaC 정적 검증, 승인 배포, 런타임 드리프트 감시, 자동 원복 및 기한부 예외 순으로 동작한다.

## Ⅴ. 종류 및 비교

<details><summary>용어 설명</summary>

- **보안 구성 점검 3대 접근 방식 비교**: 정기 수동 감사, 배포 전 IaC 정적 검사, 런타임 실시간 편차(Drift) 탐지의 비교.

</details>

| 비교 항목 | 정기 수동 점검 (Manual Audit) | 배포 전 정적 검증 (IaC Shift-Left) | 런타임 실시간 편차 탐지 (Drift Detection) |
|:---|:---|:---|:---|
| **점검 시점 및 주기** | **월간 / 분기 단위 배치 점검** | **코드 커밋 및 빌드 시점 (배포 전)** | **24x7x365 상시 실시간 모니터링** |
| **주요 점검 대상** | 시스템 엔지니어의 수동 CLI 스크립트 | **Terraform, CloudFormation, K8s YAML**| **운영 중인 OS 레지스트리, 클라우드 API 상태** |
| **장점 및 특징** | 복잡한 레거시 인프라의 맥락적 평가 가능 | **운영망 배포 전 결함 100% 선제 차단** | **한밤중 발생한 비인가 변경 즉각 적발** |
| **한계 및 문제점** | **점검 주기 사이의 침해 공백기 발생** | 코드로 관리되지 않는 수동 설정 감시 불가 | **자동 원복 실패 시 서비스 가용성 충돌 위험** |
| **자동화 수준** | 낮음 (사람의 수동 확인 의존) | **매우 높음 (CI/CD 파이프라인 자동 통합)** | **매우 높음 (CSPM/에이전트 실시간 감시)** |

#### 한줄 요약
- 수동 점검은 주기적 배치 감사, IaC 검사는 배포 전 원천 차단, 런타임 탐지는 운영 중 실시간 자가 치유이다.

## Ⅵ. 실무 고려사항 및 대책

<details><summary>용어 설명</summary>

- **CIS Benchmarks 테일러링(Tailoring)**: 범용 CIS 벤치마크 표준(예: 300여 개 항목)을 그대로 무조건 적용하지 않고, 조직의 비즈니스 특성 및 레거시 애플리케이션 호환성을 분석하여 필수 항목(Level 1)과 선택 항목(Level 2)을 합리적으로 선별 조정하는 맞춤화 작업.

</details>

| 문제 | 대책 | 효과 |
|:---|:---|:---|
| CIS 벤치마크를 획일적으로 강제 적용하여 **사내 레거시 ERP 및 결제 시스템의 서비스 중단 장애** | **조직 비즈니스 환경을 반영한 보안 기준선 테일러링(Tailoring) 및 개발망 사전 호환성 테스트** | 과도한 하드닝으로 인한 가용성 장애 0% 달성 및 실무 부서 수용성 100% 확보 |
| 긴급 장애 조치 중 변경된 설정에 대해 무조건 자동 원복(Auto-Remediation)하여 **2차 서비스 장애 발생** | **핵심 무중단 자산에 대한 Human-in-the-loop 인적 승인 연계 및 단계적 자동 원복 정책** 수립 | 장애 복구 중인 운영 시스템의 예기치 않은 단절 방지 및 안전한 자가 치유 보장 |
| 비즈니스 요구로 승인해 준 임시 보안 예외(특정 포트 개방 등)가 **수년간 방치되어 침투 경로로 악용** | **예외 승인 시 만료 기한(TTL 30일) 강제 지정 및 만료 시 자동 기준선 원복 시스템** 구축 | 잊혀진 예외 설정(기술 부채) 누적으로 인한 보안 사각지대 100% 영구 제거 |

#### 한줄 요약
- 기준선 테일러링으로 호환성을 보장하고, 인간 승인으로 가용성을 지키며, 기한부 TTL로 예외 방치를 방지한다.

## Ⅶ. 결론

- 인프라 설정 오류로 인한 사이버 침해를 근원적으로 차단하는 **보안 구성 관리(SCM) 아키텍처**는 시스템 하드닝과 제로 트러스트의 핵심 토대이며, 실무 구현 시 **CIS 벤치마크 기반의 기준선 테일러링**, **Policy-as-Code 기반 CI/CD 배포 전 정적 검증**, **CSPM 및 에이전트 기반 실시간 런타임 드리프트 감시**, **기한부 예외 관리 및 안전한 자동 원복(Auto-Remediation)** 을 결합하여 지속 가능하고 완결성 높은 인프라 보안 무결성을 완성

#### 한줄 요약
- CIS 기준선 테일러링, IaC 배포 전 검증, 런타임 드리프트 감시 및 기한부 자동 원복으로 인프라 무결성을 보장한다.
