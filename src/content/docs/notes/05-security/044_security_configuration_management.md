## Ⅰ. 개요

<details><summary>용어 설명</summary>

- **SCM (Security Configuration Management)**: IT 인프라 설정을 표준 보안 기준선에 맞추고 런타임 구성 편차를 감시·원복하는 거버넌스 체계.
- **Configuration Drift (구성 편차)**: 최초 배포된 표준 기준선 상태에서 수동 변경이나 미원복으로 인해 설정이 이탈하여 취약해지는 현상.

</details>

- 정의/개념: 인프라 설정을 CIS 벤치마크 기준선에 맞추고 IaC 배포 전 검증과 런타임 구성 편차(Drift) 감시 및 자동 원복으로 통제하는 기술
- 배경/필요성: 하이브리드 및 멀티 클라우드 인프라가 대규모로 확장됨에 따라 엔지니어의 수동 설정 오류(Misconfiguration)나 디폴트 계정/포트 방치, 긴급 장애 조치 후 원복 누락으로 인해 발생하는 구성 편차(Configuration Drift)가 클라우드 데이터 유출과 랜섬웨어 침투의 주요 원인으로 대두됨에 따라, CIS Benchmarks 및 NIST SP 800-128 표준 기반의 전사 보안 기준선을 수립하고, 배포 전 IaC(Terraform/K8s) 정적 정책 검사(Policy-as-Code)와 런타임 실시간 편차 감시 및 자동 원복(Auto-Remediation)을 통합한 보안 구성 관리(SCM) 체계를 도입하여 설정 오류 기반 침해의 선제 차단, 런타임 보안 무결성 상시 유지 및 기한부 예외 관리를 통한 보안 기술 부채 누적 방지를 달성할 필요

#### 한줄 요약
- 구성 관리의 요체는 좋은 설정을 한 번 만드는 것이 아니라 시간이 지나도 그 상태로 되돌아오게 하는 데 있으므로, 기준선 수립보다 편차를 되돌리는 장치의 유무가 실효성을 가른다.

## Ⅱ. 특징

<details><summary>용어 설명</summary>

- **CIS Benchmarks**: 전 세계 보안 전문가들이 합의한 OS, 데이터베이스, 클라우드 인프라 하드닝 글로벌 보안 기준선.
- **Policy-as-Code (PaC / OPA)**: 보안 정책을 코드로 정의하고 CI/CD 파이프라인에서 배포 전 자동으로 준수 여부를 검사하는 기법.

</details>

- CIS 벤치마크 기반 표준 하드닝: OS, DB, 클라우드 계정의 기본 설정(Default) 취약점을 글로벌 표준 템플릿으로 원천 제거
- IaC 보안 검사(Shift-Left)의 전면 적용: 테라폼, K8s 매니페스트 코드를 배포 전에 정적 검증(OPA)하여 결함 인프라의 생성 자체를 차단
- 런타임 드리프트(Drift) 실시간 자가 치유: 비인가된 보안 완화(0.0.0.0/0 개방 등)를 감지 즉시 표준 상태로 무인 자동 원복

#### 한줄 요약
- 배포 전 검증은 결함 인프라의 생성 자체를 막아 가장 싸게 위험을 없애지만 코드로 관리되지 않는 수동 변경은 잡지 못하므로, 런타임 감시가 그 사각을 더 비싼 값에 메운다.

## Ⅲ. 구조 및 구성요소

<details><summary>용어 설명</summary>

- **Auto-Remediation (자동 원복)**: 런타임 환경에서 표준 기준선을 벗어난 비인가 설정 변경 발견 시 서버리스 함수 등으로 즉각 롤백시키는 엔진.

</details>

```text
[보안 구성 관리 체계]
├─ 기준선 정의 계층
│  └─ 하드닝 템플릿 (CIS 벤치마크 기준선)
├─ 배포 전 검증 계층
│  └─ IaC 정적 검사기 (OPA Policy-as-Code)
├─ 런타임 감시 계층
│  └─ 편차 탐지기 (Configuration Drift 감시)
└─ 교정 및 거버넌스
   ├─ 자동 교정기 (무인 원복 Auto-Remediation)
   └─ 예외 관리기 (기한부 TTL 안전판)
```

- 선의 의미: 계층 구조 및 상하위 포함 관계를 나타낸다.

| 구성요소 | 책임 |
|:---|:---|
| 기준선 정의 엔진 | OS, 네트워크, DB별 CIS 벤치마크 기반 전사 하드닝 템플릿 수립 |
| IaC 정적 검사기 | 배포 전 테라폼/K8s 코드의 보안 설정 결함을 CI/CD에서 사전 차단 (OPA) |
| 런타임 편차 탐지기 | 운영 중인 자산의 실시간 설정과 목표 기준선 간 편차(Drift) 상시 감시 |
| 자동 교정기 | 비인가 편차 감지 시 표준 설정으로 무인 자동 원복(Auto-Remediation) 집행 |
| 기한부 예외 관리기 | 업무상 불가피한 예외에 만료 기한(TTL)을 설정하고 만료 시 자동 원복 |

#### 한줄 요약
- 기한부 예외 관리기는 자동 교정기를 무력화하는 장치처럼 보이지만 실은 예외에 만료 시각을 붙여 영구 부채가 되지 않게 하는 안전판이며, 이것이 없으면 현장은 자동 원복 자체를 꺼 버린다.

## Ⅳ. 흐름도

<details><summary>용어 설명</summary>

- **NIST SP 800-128 5단계**: 1. 계획(Planning) → 2. 식별(Identifying) → 3. 통제(Controlling) → 4. 모니터링(Monitoring) → 5. 교정(Remediating).

</details>

```text
기준선 정의, IaC 정적 검증, 승인 배포, 드리프트 감시 및 자동 원복 파이프라인
        │
   1. [기준선 매핑] 엔터프라이즈 환경에 맞춘 Linux OS CIS Benchmark 하드닝 템플릿 정의
        │
   2. [IaC 정적 검증] 개발자가 작성한 Terraform 코드 커밋 ➔ CI/CD에서 OPA 정적 정책 검사
        │
   ├─ [보안 룰 위반 발견 시] ➔ 파이프라인 실패(Fail) 및 개발자에게 피드백 후 수정 요구
   ▼
3. [승인 구성 배포] 검증을 통과한 인프라 코드를 프로덕션 클라우드 환경에 안전하게 프로비저닝
        │
   4. [런타임 드리프트 감시] CSPM 도구가 운영 자산 스캔 ➔ [0.0.0.0/0 보안그룹 개방 감지]
        │
   ▼
5. [자동 원복 및 통제]
    ├─ 표준 절차: EventBridge 트리거 ➔ Lambda가 비인가 룰 즉시 삭제 (목표 기준선 복원)
    └─ 기한부 예외: 승인된 긴급 티켓인 경우 7일간 예외 등록 후 기한 만료 시 자동 회수
```

- 1. 기준선 매핑
- 2. IaC 정적 검증
- 3. 승인 구성 배포
- 4. 런타임 드리프트 감시
- 5. 자동 원복 및 통제

#### 한줄 요약
- 2단계에서 걸린 위반은 파이프라인 실패라는 개발자 시간만 소모하지만 4단계까지 흘러간 위반은 운영 자산이 실제로 열린 뒤에 잡히므로, 같은 결함이라도 발견 시점이 뒤로 갈수록 비용이 커진다.

## Ⅴ. 종류 및 비교

<details><summary>용어 설명</summary>

- **정기 수동 점검 (Manual Audit)**: 엔지니어가 주기적으로 설정을 직접 확인해 레거시의 맥락까지 판단하는 대신, 점검과 점검 사이의 기간을 통째로 사각지대로 남기는 방식.
- **배포 전 정적 검증 (IaC Shift-Left)**: 인프라 코드를 커밋 시점에 정책으로 검사해 결함 자산의 생성 자체를 막는 대신, 코드 밖에서 이뤄지는 수동 설정 변경은 시야에 넣지 못하는 방식.
- **런타임 실시간 편차 탐지 (Drift Detection)**: 운영 중 자산의 실제 상태를 상시 비교해 비인가 변경을 즉시 잡아내는 대신, 자동 원복이 정당한 긴급 조치까지 되돌려 가용성과 충돌할 위험을 안는 방식.

</details>

| 비교 항목 | 정기 수동 점검 (Manual Audit) | 배포 전 정적 검증 (IaC Shift-Left) | 런타임 실시간 편차 탐지 (Drift Detection) |
|:---|:---|:---|:---|
| 점검 시점 및 주기 | 월간 / 분기 단위 배치 점검 | 코드 커밋 및 빌드 시점 (배포 전) | 24x7x365 상시 실시간 모니터링 |
| 주요 점검 대상 | 시스템 엔지니어의 수동 CLI 스크립트 | Terraform, CloudFormation, K8s YAML| 운영 중인 OS 레지스트리, 클라우드 API 상태 |
| 장점 및 특징 | 복잡한 레거시 인프라의 맥락적 평가 가능 | 운영망 배포 전 결함 100% 선제 차단 | 한밤중 발생한 비인가 변경 즉각 적발 |
| 한계 및 문제점 | 점검 주기 사이의 침해 공백기 발생 | 코드로 관리되지 않는 수동 설정 감시 불가 | 자동 원복 실패 시 서비스 가용성 충돌 위험 |
| 자동화 수준 | 낮음 (사람의 수동 확인 의존) | 매우 높음 (CI/CD 파이프라인 자동 통합) | 매우 높음 (CSPM/에이전트 실시간 감시) |

#### 한줄 요약
- 수동 점검은 주기적 배치 감사, IaC 검사는 배포 전 원천 차단, 런타임 탐지는 운영 중 실시간 자가 치유이다.

## Ⅵ. 실무 고려사항 및 대책

<details><summary>용어 설명</summary>

- **CIS Benchmarks Tailoring**: 범용 표준을 조직 비즈니스 특성과 레거시 호환성에 맞추어 필수 항목(Level 1)과 선택 항목(Level 2)으로 선별 조정하는 맞춤화.

</details>

| 문제 | 대책 | 효과 |
|:---|:---|:---|
| CIS 벤치마크 획일적 적용으로 인한 사내 레거시 결제 시스템의 서비스 중단 장애 | 조직 환경을 반영한 `보안 기준선 테일러링(Tailoring) 및 사전 호환성 테스트` | 과도한 하드닝으로 인한 가용성 장애 0% 달성 |
| 긴급 장애 조치 중 변경된 설정을 무조건 자동 원복하여 **2차 서비스 장애 발생** | 핵심 무중단 자산에 대한 `Human-in-the-loop 인적 승인 연계 및 단계적 원복` | 운영 시스템의 예기치 않은 단절 방지 및 안전한 치유 |
| 승인된 임시 보안 예외(특정 포트 개방 등)가 수년간 방치되어 침투 경로로 악용 | 예외 승인 시 `만료 기한(TTL 30일) 강제 지정 및 만료 시 자동 원복` 시스템 구축 | 기술 부채 누적으로 인한 보안 사각지대 영구 제거 |
| 클라우드 멀티 계정 환경에서 설정 가시성 파편화 | `중앙 집중식 CSPM 플랫폼 도입 및 단일 대시보드 규정 준수율 관리` | 전사 멀티 클라우드 자산 보안 기준선 준수율 98% 달성 |

#### 한줄 요약
- 구성 관리 실무는 표준을 얼마나 강하게 밀어붙일지의 조절 문제이므로, 테일러링과 승인 연계로 가용성을 사는 만큼 기준선의 엄격함은 내려가고 그 간극은 예외의 기한 관리로만 통제된다.

## Ⅶ. 결론

- 소프트웨어 취약점(CVE) 못지않게 치명적인 시스템/클라우드 설정 오류(Misconfiguration)를 개발 파이프라인부터 런타임 운영까지 전 수명주기에 걸쳐 통제하는 엔터프라이즈 인프라 하드닝(Hardening) 및 클라우드 보안 태세 관리(CSPM)의 가장 기초적이고 강력한 방어 프랙티스로 확고히 자리 잡았으며, GitOps 기반의 인프라 상태 동기화 및 AI 기반 비정상 설정 변경 탐지로 진화하는 가운데, 실무 보안 구성 관리 체계 구축 시에는 비즈니스 가용성을 고려한 조직 맞춤형 CIS Benchmarks 테일러링(Tailoring), 배포 전 단계에서 취약한 코드의 프로비저닝을 차단하는 IaC(OPA/Checkov) 정적 검사 강제, 런타임 비인가 설정 이탈 시 즉시 표준으로 복구하는 서버리스 자동 원복(Auto-Remediation) 및 임시 예외 설정의 영구 방치를 차단하는 기한부(TTL) 예외 만료 정책을 결합하여 완벽한 인프라 보안 무결성을 완성

#### 한줄 요약
- 보안 구성 관리는 CIS 기준선 테일러링, IaC 배포 전 검증, 런타임 드리프트 감시 및 기한부 자동 원복으로 인프라 무결성을 보장하는 핵심 체계다.
