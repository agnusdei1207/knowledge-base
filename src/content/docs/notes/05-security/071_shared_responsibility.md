## Ⅰ. 개요

<details><summary>용어 설명</summary>

- **클라우드 공유 책임 모델(Cloud Shared Responsibility Model / ISO/IEC 27017)**: 클라우드 컴퓨팅 환경에서 클라우드 서비스 제공자(CSP)와 이용 고객(Customer) 간에 물리 인프라, 하이퍼바이저, 가상 네트워크, OS, 런타임, 데이터, IAM 계정 관리에 이르는 전체 IT 스택의 보안 통제 소유권(Ownership) 및 책임을 명확히 구분한 보안 거버넌스 프레임워크.
- **클라우드 오설정 및 책임 공백(Accountability Gap & Misconfiguration Defect)**: "클라우드 도입 시 보안 전체를 CSP가 전담해 준다"는 고객의 오인으로 인해, 고객 책임 영역인 S3 스토리지 퍼블릭 오픈, IAM 과다 권한, OS 미패치 등의 오설정이 방치되어 대규모 데이터 유출로 이어지는 거버넌스 결함.

</details>

- 정의/개념: NIST SP 800-145 및 ISO/IEC 27017에 입각하여 **IaaS(OS부터 고객 책임) $\rightarrow$ PaaS(앱/데이터 고객 책임) $\rightarrow$ SaaS(데이터/IAM 고객 책임)** 로 이어지는 서비스 모델별 **Security OF the Cloud(CSP)** 와 **Security IN the Cloud(Customer)** 경계를 구획하고, **RACI Matrix 및 CSPM 자동화** 로 관리 공백을 제거하는 **클라우드 보안 분담 아키텍처**
- 배경/필요성: 클라우드는 물리 인프라 운영 비용을 CSP에 넘긴 대가로 통제 스택을 두 주체가 나눠 갖게 되어 그 경계에 아무도 손대지 않는 통제가 남으므로, 계층별 소유권을 RACI로 문서에 고정하고 고객 몫의 설정 편차는 CSPM이 상시 대조·원복하는 감사 계층을 그 위에 얹을 필요

#### 한줄 요약
- 클라우드로 옮겨 간 것은 운영 부담이지 책임이 아니며, 모델이 고도화될수록 고객이 손댈 범위는 줄어도 데이터와 IAM에 대한 책임은 끝까지 남는다.

## Ⅱ. 특징

<details><summary>용어 설명</summary>

- **Security OF the Cloud vs Security IN the Cloud**:
  - **Security OF the Cloud (CSP 책임)**: 데이터센터 물리 보안, 서버 하드웨어, 스토리지 인프라, 가상화 하이퍼바이저, 물리 네트워크의 가용성 및 무결성 보호.
  - **Security IN the Cloud (고객 책임)**: 게스트 OS 패치, 네트워크 방화벽(보안그룹) 규칙, IAM 자격증명/MFA, 암호화 키 관리, 데이터 분류 및 거버넌스.

</details>

- **서비스 모델별 동적 책임 전이 (Responsibility Shift)**: IaaS $\rightarrow$ PaaS $\rightarrow$ SaaS로 고도화될수록 CSP의 인프라 관리 범위가 확대되나, 데이터와 IAM 통제는 100% 영구적 고객 책임
- **상속 및 공동 통제 (Inherited & Shared Controls)**: 데이터센터 물리 보안은 CSP로부터 상속(SOC 2 보고서로 대체)받고, 패치/구성 관리는 협력하여 이행
- **운영 증적 기반 컴플라이언스**: CSP의 제3자 감사 인증(SOC 1/2/3, ISO 27001)과 고객 측 CSPM 감사 로그를 결합하여 법적 증적 완결

#### 한줄 요약
- CSP에 통제를 넘길수록 직접 관리할 대상은 줄지만 직접 확인할 수단도 함께 사라지므로, 그 구간은 제3자 감사 보고서를 신뢰하는 방식으로 대체된다.

## Ⅲ. 구조 및 구성요소

<details><summary>용어 설명</summary>

- **클라우드 3대 모델별 통제 분담 스택**:
  - **IaaS**: 물리 인프라/가상화는 CSP, OS/미들웨어/앱/데이터/IAM은 고객.
  - **PaaS**: 인프라/OS/DB 엔진은 CSP, 애플리케이션 코드/데이터/IAM은 고객.
  - **SaaS**: 인프라/OS/앱 소프트웨어 전반은 CSP, 데이터 접근/사용자 권한(IAM)은 고객.

</details>

```text
┌─────────────────────────────────────────────────────────────────────────┐
│ [ 클라우드 서비스 모델별 공유 책임 매핑 (Shared Responsibility Stack) ] │
│                                                                         │
│  [ IT 통제 스택 ]      [ IaaS (예: EC2) ]  [ PaaS (예: RDS) ]  [ SaaS (예: M365) ] │
│  ├─ 데이터 분류/암호화 ───▶ [ 고객 (Customer) ]   [ 고객 (Customer) ]   [ 고객 (Customer) ] │
│  ├─ IAM 계정/권한 통제 ───▶ [ 고객 (Customer) ]   [ 고객 (Customer) ]   [ 고객 (Customer) ] │
│  ├─ 애플리케이션 코드  ───▶ [ 고객 (Customer) ]   [ 고객 (Customer) ]   [ 제공자 (CSP) ]    │
│  ├─ 미들웨어 / DB 엔진 ───▶ [ 고객 (Customer) ]   [ 제공자 (CSP) ]      [ 제공자 (CSP) ]    │
│  ├─ 게스트 OS 패치     ───▶ [ 고객 (Customer) ]   [ 제공자 (CSP) ]      [ 제공자 (CSP) ]    │
│  ├─ 하이퍼바이저/가상화───▶ [ 제공자 (CSP) ]      [ 제공자 (CSP) ]      [ 제공자 (CSP) ]    │
│  └─ 물리 데이터센터    ───▶ [ 제공자 (CSP) ]      [ 제공자 (CSP) ]      [ 제공자 (CSP) ]    │
└─────────────────────────────────────────────────────────────────────────┘
```

선의 의미: 데이터와 IAM은 모든 클라우드 모델에서 100% 고객의 책임이며, 하위 인프라 계층으로 내려갈수록 서비스 모델에 따라 책임 주체가 전이되는 구조

| 구성요소 | 핵심 책임 및 역할 | 비고 |
|:---|:---|:---|
| **CSP 제공자 통제** | 데이터센터 물리 보안, 서버 하드웨어, 스토리지 가용성, 하이퍼바이저 격리 보장 | Security OF |
| **고객 자산 통제** | 고객 데이터의 암호화(KMS), 접근 권한(IAM/MFA), 게스트 OS 보안 패치(IaaS) | Security IN |
| **공동 통제 (Shared)** | 네트워크 구성, 패치 주기 관리, 로깅 설정 등 상호 협력을 통해 완결되는 통제 | Shared RACI |
| **상속 통제 (Inherited)**| CSP의 물리적 보안 및 하드웨어 유지보수 결과를 고객 보안 감사 증적으로 수용 | SOC 2 / ISMS |
| **사고 대응 인터페이스** | 침해사고 발생 시 CSP와의 핫라인 소통, 클라우드 트레일 로그 공유 및 포렌식 협력 | Incident SLA |

#### 한줄 요약
- 데이터와 IAM은 어느 모델에서도 고객 쪽에 남으므로, 스택의 어느 높이를 쓰든 침해의 최종 원인은 대체로 고객이 설정한 접근 권한에서 발생한다.

## Ⅳ. 흐름도

<details><summary>용어 설명</summary>

- **공유 책임 거버넌스 5단계 수명주기**:
  1. 클라우드 서비스 계약 체결 및 SLA/SOC 보고서 분석
  2. IaaS/PaaS/SaaS 계층별 통제 소유권 매핑
  3. RACI Matrix 수립 및 고객 책임자 지정
  4. IaC 및 CSPM을 통한 고객 환경 지속 감사
  5. 오설정 발견 시 자동 원복(Remediation) 및 침해 대응

</details>

```text
1. [계약 및 SLA 검토] 약관과 CSP 감사 보고서 확인
            │
            ▼
2. [서비스 모델별 책임 구획]
    ├─ IaaS(EC2): "OS 커널 패치 및 방화벽 인바운드 룰은 고객 전담" 확정
    └─ SaaS(M365): "외부 공유 링크 정책 및 2단계 인증 강제는 고객 전담" 확정
            │
            ▼
3. [RACI 매트릭스 수립] 통제별 책임 주체 지정
            │
            ▼
4. [CSPM 지속적 태세 점검] 고객 영역 설정 스캔
            │
            ▼
5. [오설정 자동 교정 및 피드백]
    ├─ "S3 버킷 Public 오픈" 감지 ➔ [CSPM 정책 기반 즉각 Private 격리 자동 집행]
    └─ 침해 의심 발생 시 ➔ [CSP 지원 센터와 연계하여 침해사고 대응 핫라인 가동]
```

**동작 원리**

1. **계약 및 SLA 검토**: CSP 보증 범위와 고객 의무 확인
2. **서비스 모델별 책임 구획**: 계층별 통제 소유권 확정
3. **RACI 매트릭스 수립**: 통제별 수행·책임 주체 지정
4. **CSPM 지속적 태세 점검**: 고객 영역의 오설정 탐지
5. **오설정 자동 교정 및 피드백**: 정책 위반 설정 원복

#### 한줄 요약
- 책임 구획은 계약 시점에 한 번 끝나지만 설정은 배포마다 바뀌므로, 문서로 정한 경계를 실제 상태와 이어 주는 것은 CSPM의 반복 대조뿐이다.

## Ⅴ. 종류 및 비교

<details><summary>용어 설명</summary>

- **클라우드 3대 모델별 책임 비교**: IaaS(인프라형), PaaS(플랫폼형), SaaS(소프트웨어형)의 비교.

</details>

| 비교 항목 | IaaS (예: AWS EC2, GCP GCE) | PaaS (예: AWS RDS, Azure App) | SaaS (예: M365, Salesforce) |
|:---|:---|:---|:---|
| CSP 관리 영역 | 물리 데이터센터·**하이퍼바이저** | 인프라·OS·**런타임** | 인프라·OS·**애플리케이션** |
| 고객 관리 영역 | 게스트 OS·방화벽·**데이터·IAM** | 소스코드·**데이터·IAM** | **데이터·IAM** |
| 고객 통제권 수준 | OS·네트워크 **전면 제어** | 플랫폼 내 **제한적 설정** | 기능·계정만 **최소 제어** |
| **주요 침해 원인** | OS 취약점 미패치, 방화벽 Any Open | 앱 로직 취약점, 비인가 DB 접근 | **계정 자격증명 탈취, 비인가 외부 파일 공유**|
| **핵심 보안 대책** | 호스트 EDR, 취약점 패치, CSPM | DAST/SAST 정적분석, WAF, DSPM | **CASB(SaaS 보안), IDaaS MFA, DLP** |

#### 한줄 요약
- IaaS는 OS부터 고객 책임, PaaS는 앱/데이터 고객 책임, SaaS는 데이터/IAM만 고객 책임이다.

## Ⅵ. 실무 고려사항 및 대책

<details><summary>용어 설명</summary>

- **CSPM(Cloud Security Posture Management)**: 멀티 클라우드 환경에서 CIS Benchmarks 및 컴플라이언스 기준에 따라 고객 측의 잘못된 구성(오설정), 과다 권한, 미사용 자원을 자동으로 탐지하고 즉시 교정하는 보안 도구.

</details>

| 문제 | 대책 | 효과 |
|:---|:---|:---|
| 클라우드 보안 책임을 CSP가 전담한다는 오인으로 인해 **고객 측 OS 미패치 및 방화벽 0.0.0.0/0 개방으로 인한 침해 사고** | **NIST SP 800-145 및 ISO/IEC 27017** 기준, 전사 클라우드 자산에 대한 **서비스 모델별 RACI 책임 할당 행렬 수립** | CSP와 고객 간의 보안 통제 소유권 명확화 및 책임 공백 100% 원천 해소 |
| 개발자의 수동 인프라 설정 실수로 인해 **S3 오브젝트 스토리지가 퍼블릭으로 완전 노출되어 핵심 DB가 유출되는 결함** | **CSPM(Cloud Security Posture Management) 도구 도입 및 CI/CD IaC 파이프라인 정적 보안 검증 강제** | 고객 책임 영역의 오설정 실시간 자동 탐지 및 100% 즉시 자동 원복(Remediation) |
| 클라우드 침해 사고 발생 시 CSP와 고객 간의 **책임 공방으로 포렌식 로그 확보가 지연되고 2차 피해가 확산되는 장애** | **클라우드 서비스 계약 시 침해사고 대응 인터페이스(Incident SLA) 및 상세 로그 제공 협약 명시** | 사고 발생 시 CSP 핫라인 즉각 가동 및 포렌식 조사 시간 80% 이상 단축 |

#### 한줄 요약
- 세 대책은 모두 사고가 난 뒤 책임 소재를 가리는 비용을 사전 문서화와 상시 점검 비용으로 앞당겨 치르는 선택이다.

## Ⅶ. 결론

- 서비스 모델로 **책임 경계**를 정하고 고객 영역은 **CSPM**으로 검증

#### 한줄 요약
- 서비스 모델의 선택은 곧 어느 통제를 직접 쥘 것인가의 선택이므로, 규제 요구가 강한 자산일수록 통제권이 더 많이 남는 낮은 계층을 고르게 된다.
