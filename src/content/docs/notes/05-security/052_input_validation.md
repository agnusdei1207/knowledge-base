## Ⅰ. 개요

<details><summary>용어 설명</summary>

- **입력값 검증(Input Validation / CWE-20)**: 외부 클라이언트(웹 브라우저, 모바일 앱, 서드파티 API)로부터 유입되는 모든 데이터에 대해 신뢰성을 배제하고, 서버 측에서 데이터의 타입(Type), 길이(Length), 형식(Format), 범위(Range)가 사전 정의된 비즈니스 스키마에 일치하는지 엄격히 심사하는 방어 프로세스.
- **파라미터 바인딩(Parameter Binding)**: 데이터베이스 및 시스템 쿼리 실행 시, 사전 컴파일된 쿼리 구조의 특정 위치 홀더(`?`)에 사용자 입력값을 순수 리터럴 데이터로만 매핑하여, 입력값이 인터프리터에 의해 명령어로 오인 해석되는 것을 원천 차단하는 기술.

</details>

- 정의/개념: 인젝션 및 비정상 입력 공격을 차단하기 위해 **정규화(Canonicalization) $\rightarrow$ 서버 측 화이트리스트(Allowlist) 검증 $\rightarrow$ PreparedStatement 파라미터 바인딩 $\rightarrow$ 동적 식별자 정적 매핑** 을 단계별로 적용하는 **입력 경계 보안 아키텍처**
- 배경/필요성: 클라이언트 측 자바스크립트 검증은 프록시(Burp Suite) 조작에 의해 완전히 우회되며, 특정 악성 문자열만 걸러내는 블랙리스트 방식은 다중 인코딩 및 변종 공격에 취약하므로 서버 측의 강력한 입력 통제와 데이터 격리 요구

#### 한줄 요약
- 정규화 후 서버 측 화이트리스트 검증을 거치고, PreparedStatement 파라미터 바인딩으로 코드와 데이터를 물리적으로 분리한다.

## Ⅱ. 특징

<details><summary>용어 설명</summary>

- **정규화(Normalization / Canonicalization)**: 공격자가 입력 필터링을 우회하기 위해 적용한 URL 인코딩(`%27`), HTML 엔티티, 16진수, 유니코드 변종 문자열을 평가하기 전에 가장 단순하고 표준화된 단일 인코딩 형식(UTF-8)으로 완전히 디코딩하는 전처리 과정.
- **포지티브 검증(Positive Validation / 화이트리스트)**: 거부할 악성 문자열(Blacklist)을 정의하는 대신, 시스템이 허용하는 안전한 문자 집합(예: 정수형 숫자, 알파벳, 이메일 정규표현식)만을 명시하고 그 외의 모든 입력을 기본 거부(Default Deny)하는 원칙.

</details>

- **다중 인코딩 우회 무력화**: 입력값 검증 로직 실행 전 반드시 표준 정규화(Canonicalization)를 선행하여 필터링 우회 차단
- **서버 측 단독 신뢰 원칙 (Server-Side Authoritative)**: 프론트엔드 UI 검증은 사용자 편의용으로만 간주하고, 모든 보안 정책은 백엔드 API 게이트웨이에서 집행
- **바인딩 불가 영역의 정적 매핑**: `ORDER BY`, `TABLE`, `COLUMN` 등 문법적으로 바인딩 변수를 쓸 수 없는 영역에 대해 화이트리스트 맵핑 적용

#### 한줄 요약
- 표준 정규화 선행, 서버 측 화이트리스트 검증, 쿼리-데이터 물리적 격리, 동적 식별자 정적 맵핑을 제공한다.

## Ⅲ. 구조 및 구성요소

<details><summary>용어 설명</summary>

- **동적 식별자(Dynamic Identifiers) 처리 기법**:
  - `SELECT * FROM users ORDER BY ?` (SQL 문법 오류 발생)
  - $\rightarrow$ 해결책: `Map<String, String> sortMap = Map.of("1", "reg_date", "2", "name");` 형태로 클라이언트 입력을 사전에 정의된 정적 키 값과 매핑하여 안전한 SQL 문자열로 치환.

</details>

```text
[ 비신뢰 클라이언트 입력 (예: %2527%20OR%201=1) ]
                        │
                        ▼
┌─────────────────────────────────────────────────────────────────────────┐
│ [ 1. 정규화 계층 (Canonicalization Engine) ]                            │
│  └─ 이중 URL 디코딩 / 유니코드 표준화 ➔ 순수 문자열 `' OR 1=1`로 변환    │
└────────────────────────────────────┬────────────────────────────────────┘
                                     │
                                     ▼
┌─────────────────────────────────────────────────────────────────────────┐
│ [ 2. 서버 측 화이트리스트 검증 계층 (Server-Side Allowlist Validation) ]│
│  ├─ 데이터 타입 검증 (Integer / UUID / ISO-8601 Date)                   │
│  ├─ 정규표현식 매칭 (Regex: `^[a-zA-Z0-9_]{4,20}$`)                     │
│  └─ [ 스키마 불일치 시 ➔ 400 Bad Request 응답 및 즉각 거부 ]            │
└────────────────────────────────────┬────────────────────────────────────┘
                                     │ (검증 통과된 안전한 데이터)
                                     ▼
┌─────────────────────────────────────────────────────────────────────────┐
│ [ 3. 데이터베이스 쿼리 바인딩 계층 (Parameter Binding Layer) ]          │
│  ├─ 일반 조건절: PreparedStatement (`SELECT ... WHERE id = ?`)          │
│  └─ 동적 컬럼/테이블: 정적 화이트리스트 매핑 (`sortMap.get(userInput)`) │
└────────────────────────────────────┬────────────────────────────────────┘
                                     │ (쿼리 구조 고정 ➔ 순수 리터럴 파라미터 전달)
                                     ▼
[ 데이터베이스 엔진 (DBMS) ➔ 쿼리 재파싱 없이 안전한 트랜잭션 실행 ]
```

선의 의미: 입력값이 정규화를 거쳐 서버 측 화이트리스트 검증을 통과한 후, PreparedStatement 바인딩 및 정적 맵핑을 통해 DBMS에서 안전하게 처리되는 구조

| 구성요소 | 핵심 책임 및 역할 | 비고 |
|:---|:---|:---|
| **정규화 모듈 (Canonicalizer)**| 다중 URL 인코딩, Base64, 널 바이트(`%00`)를 단일 표준 문자열로 디코딩 | Normalization |
| **화이트리스트 유효성 검증기** | 비즈니스 스펙에 따라 허용된 형식, 길이, 정규식에 일치하는지 백엔드 검증 | Allowlist Check |
| **PreparedStatement 엔진** | SQL 실행 계획을 사전 컴파일하여 쿼리 문법 구조를 메모리에 불변 고정 | Pre-compile |
| **파라미터 바인더** | 사용자 입력값을 쿼리 제어 코드가 아닌 순수 데이터 리터럴 변수로 바인딩 | Parameter Bind |
| **식별자 매핑기 (Allowlist Map)**| 바인딩이 불가능한 `ORDER BY` 및 테이블명을 서버 내 정적 상수 테이블과 대조 | Identifier Map |

#### 한줄 요약
- 정규화 모듈, 화이트리스트 검증기, PreparedStatement 엔진, 파라미터 바인더, 식별자 매핑기가 결합한다.

## Ⅳ. 흐름도

<details><summary>용어 설명</summary>

- **CWE-20 입력 유효성 검증 4대 원칙**:
  1. **정규화 선행**: 검증 전 표준 문자열로 변환
  2. **화이트리스트 기반**: 허용된 패턴 외 전면 거부
  3. **서버 측 강제**: 클라이언트 검증에 의존 금지
  4. **문맥별 데이터 분리**: 바인딩 및 이스케이프 적용

</details>

```text
1. [클라이언트 요청 유입] REST API 요청 페이로드(`{ "sort": "1", "search": "%27%20OR%201=1" }`) 수신
            │
            ▼
2. [정규화 전처리] 디코딩 라이브러리를 통해 이중 인코딩 및 특수 우회 문자를 표준 UTF-8 문자열로 복원
            │
            ▼
3. [서버 측 화이트리스트 검증]
    ├─ `search` 파라미터: 허용 정규식(`^[a-zA-Z0-9가-힣\s]{1,50}$`) 대조 ➔ [특수문자 포함 시 즉시 기각]
    └─ `sort` 파라미터: 정수형 범위(1~3) 대조 통과
            │
            ▼
4. [쿼리 골격 사전 컴파일] DB 엔진에 `SELECT * FROM items WHERE name LIKE ? ORDER BY ` 쿼리 골격 전달
            │
            ▼
5. [동적 식별자 매핑 및 바인딩]
    ├─ `sort="1"` ➔ 서버 코드 내 매핑 테이블에 의해 `ORDER BY create_date DESC` 로 안전 치환
    └─ `search` 값은 `pstmt.setString(1, "%" + search + "%")` 로 바인딩 변수에 대입
            │
            ▼
6. [안전한 DBMS 실행] DBMS 파서가 입력값을 쿼리 명령어가 아닌 순수 검색 키워드로만 평가하여 실행 완료
```

**동작 원리**

1. **우회 기법 무력화**: 다중 인코딩 및 널 바이트 삽입 패턴을 표준 형태로 사전 변환
2. **엄격한 스키마 준수**: 정규표현식 및 DTO(Data Transfer Object) 검증을 통한 비정상 페이로드 거절
3. **실행 구조의 불변성**: 쿼리 템플릿 컴파일 후에는 외부 입력이 SQL 문법 구조에 개입 불가능
4. **동적 파라미터 안전성**: 바인딩이 불가능한 식별자도 사용자 입력을 직접 결합하지 않고 내부 상수로 치환
5. **다계층 장애 차단**: 입력 검증 실패 시 즉시 트랜잭션을 중단하여 백엔드 DB 부하 및 노출 예방

#### 한줄 요약
- 요청 수신, 정규화 전처리, 서버 측 화이트리스트 검증, 쿼리 사전 컴파일, 파라미터 바인딩 및 안전 실행 순으로 동작한다.

## Ⅴ. 종류 및 비교

<details><summary>용어 설명</summary>

- **입력 통제 3대 단계 비교**: 정규화(Normalization), 화이트리스트 검증(Allowlist), 파라미터 바인딩(Binding)의 비교.

</details>

| 비교 항목 | 1. 정규화 (Normalization) | 2. 화이트리스트 검증 (Allowlist) | 3. 파라미터 바인딩 (Binding) |
|:---|:---|:---|:---|
| **핵심 목적** | **인코딩 우회 기법 해제 및 표준화** | **비정상 입력값 사전 유입 차단** | **구문-데이터 물리적 격리 (인젝션 방지)**|
| **실행 위치** | API 게이트웨이 / 프론트 컨트롤러 | 백엔드 유효성 검증 계층 (DTO/Service) | 데이터 액세스 계층 (DAO / ORM) |
| **방어 메커니즘** | 이중 URL/유니코드 디코딩 | 정규표현식 및 스키마 타입/길이 검증 | **PreparedStatement `?` 홀더 치환** |
| **주요 방어 위협** | **이중 인코딩 우회, 널 바이트 인젝션** | **비정상 비즈니스 입력, DoS 페이로드** | **SQL Injection, NoSQL Injection** |
| **단독 적용 한계** | 검증 자체는 수행하지 않음 (전처리) | 복잡한 텍스트(게시글 등) 정규식 작성 난해| **ORDER BY 등 동적 식별자엔 적용 불가**|

#### 한줄 요약
- 정규화는 우회 해제 전처리, 화이트리스트는 사전 차단 문지기, 파라미터 바인딩은 최종 물리적 격리이다.

## Ⅵ. 실무 고려사항 및 대책

<details><summary>용어 설명</summary>

- **Bean Validation (JSR 380 / Hibernate Validator)**: 자바 엔터프라이즈 환경에서 `@NotNull`, `@Size(min=4, max=20)`, `@Pattern(regexp=...)` 등 어노테이션 기반으로 DTO 입력값을 선언적이고 표준화되게 검증하는 프레임워크.

</details>

| 문제 | 대책 | 효과 |
|:---|:---|:---|
| 클라이언트(JS) 검증만 믿고 서버 측 검증을 생략하여 **프록시 툴을 통한 파라미터 변조 및 권한 탈취 사고** | **MITRE CWE-20** 준수, 모든 API 엔드포인트에 **서버 측 Bean Validation(JSR-380) 화이트리스트 검증 강제** | 프론트엔드 검증 우회 조작 공격을 백엔드 진입점에서 100% 원천 차단 |
| PreparedStatement 바인딩이 지원되지 않는 **`ORDER BY` 및 테이블명 동적 쿼리에서 SQL 인젝션 발생** | **동적 식별자에 대한 정적 화이트리스트 매핑 테이블(Enum / Map) 정의 및 사전 검증** | 바인딩 한계 영역에 대한 사용자 입력 직접 연결 차단 및 2차 인젝션 완벽 방어 |
| 개발자가 직접 문자열 결합(`+`)으로 SQL을 작성하여 **코드베이스 전반에 수백 개의 인젝션 결함 발생** | **Spring Data JPA, Hibernate 등 안전한 ORM 프레임워크 도입 및 정적 분석(SAST) CI 연동** | 개발자의 수작업 코딩 실수(Human Error)를 배제하고 파라미터 바인딩 100% 자동화 |

#### 한줄 요약
- 서버 측 Bean Validation으로 입구를 막고, 정적 매핑으로 동적 쿼리를 보호하며, ORM으로 바인딩을 강제한다.

## Ⅶ. 결론

- 외부 비신뢰 데이터로부터 소프트웨어의 내부 무결성을 보호하는 **입력값 검증 및 파라미터 바인딩 아키텍처**는 모든 애플리케이션 보안의 제1원칙이며, 실무 구현 시 **표준 정규화(Canonicalization) 선행**, **서버 측 화이트리스트(Allowlist) 검증 의무화**, **PreparedStatement 및 ORM 기반 파라미터 바인딩 전면 적용**, **동적 식별자에 대한 정적 매핑 거버넌스**를 통합 구축하여 무결점 소프트웨어 입력 신뢰 경계를 완성

#### 한줄 요약
- 정규화와 서버 측 화이트리스트 검증 및 PreparedStatement 바인딩을 통해 입력값 조작 및 인젝션을 완벽히 차단한다.
