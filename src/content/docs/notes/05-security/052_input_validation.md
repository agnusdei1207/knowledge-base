## Ⅰ. 개요

<details><summary>용어 설명</summary>

- **Input Validation (입력값 검증, CWE-20)**: 외부 클라이언트로부터 유입되는 모든 데이터의 타입, 길이, 형식을 서버 측에서 엄격 심사하는 보안 프로세스.
- **Parameter Binding (파라미터 바인딩)**: 사전 컴파일된 쿼리 구조에 입력값을 순수 리터럴 데이터로만 매핑하여 구문 변조를 막는 기술.

</details>

- 정의/개념: 인젝션 공격을 차단하기 위해 정규화, 서버 측 화이트리스트 검증, PreparedStatement 바인딩으로 데이터-구문을 격리하는 기술
- 배경/필요성: 웹 및 API 환경에서 클라이언트가 전송하는 비신뢰 입력값(Untrusted Input)을 적절한 정규화나 검증 없이 백엔드 로직 및 데이터베이스 쿼리에 직접 결합할 경우, 이중 인코딩 우회, SQL/Command 인젝션, 경로 조작(Directory Traversal) 등 시스템 제어권을 탈취당하는 치명적 결함(**CWE-20**)이 발생함에 따라, 다중 인코딩을 표준 UTF-8로 환원하는 선행 정규화(Canonicalization)와 서버 측 화이트리스트(Allowlist) 유효성 검증을 거치고, 데이터베이스 액세스 계층에서 PreparedStatement **파라미터 바인딩**을 강제하여 비신뢰 입력의 위험 요소 사전 소거, 구문과 데이터의 완전한 물리적 격리 및 바인딩 불가 영역(동적 식별자)에 대한 안전한 정적 매핑 통제를 달성할 필요

#### 한줄 요약
- 정규화와 서버 측 화이트리스트 검증 및 파라미터 바인딩을 통해 비신뢰 입력을 완벽히 격리한다.

## Ⅱ. 특징

<details><summary>용어 설명</summary>

- **Canonicalization (정규화)**: 다중 URL 인코딩이나 유니코드 변형 문자열을 표준 UTF-8 형태로 디코딩하여 우회를 방지하는 전처리.
- **Allowlist Validation (화이트리스트 검증)**: 금지 문자열을 거르는 블랙리스트 대신, 허용된 안전 패턴만 통과시키는 엄격한 검증 방식.

</details>

- 선행 **정규화**(Canonicalization) 기반 우회 무력화: 다중 인코딩, 유니코드 변형, 널 바이트(%00)를 표준 형태로 디코딩 후 검증 집행
- 엄격한 화이트리스트(Allowlist) 검증 정책: 금지 문자 차단(Blacklist)의 한계를 넘어 사전 정의된 형식, 길이, 정규표현식만 통과 허용
- 데이터 액세스 계층의 완전한 물리적 분리: 입력 검증 후에도 PreparedStatement 및 ORM 바인딩을 적용하여 쿼리 문법 변조 원천 봉쇄

#### 한줄 요약
- 화이트리스트는 허용 범위를 좁힐수록 안전해지지만 그만큼 정상 입력의 오기각도 늘어나므로, 좁히기 어려운 자유 텍스트 영역은 바인딩의 문법 격리가 검증 대신 떠맡는다.

## Ⅲ. 구조 및 구성요소

<details><summary>용어 설명</summary>

- **Identifier Mapping (식별자 매핑)**: PreparedStatement 바인딩이 불가능한 `ORDER BY` 등의 동적 컬럼명을 내부 정적 매핑 테이블(Enum)과 대조하는 기법.

</details>

```text
[입력값 검증 및 파라미터 바인딩]
├─ 전처리 계층
│  └─ 정규화 모듈 (URL·유니코드 표준 환원)
├─ 서버 검증 계층
│  └─ 화이트리스트 검증기 (정규식·길이 검사)
├─ 데이터 액세스 계층
│  ├─ PreparedStatement (쿼리 실행 계획 고정)
│  ├─ 파라미터 바인더 (데이터 리터럴 바인딩)
│  └─ 식별자 매핑기 (동적 정렬·Enum 대조)
└─ 저장소 계층
   └─ 데이터베이스 엔진 (안전한 트랜잭션 실행)
```

- 선의 의미: 계층 구조 및 상하위 포함 관계를 나타낸다.

| 구성요소 | 책임 |
|:---|:---|
| 정규화 모듈 (Canonicalizer) | 다중 URL 인코딩, 널 바이트, 변형 유니코드를 단일 표준 문자열(UTF-8)로 디코딩 |
| 화이트리스트 검증기 | 비즈니스 스펙에 따라 허용된 형식, 길이, 정규식 일치성을 백엔드에서 강제 검증 |
| PreparedStatement 엔진 | SQL 실행 계획을 사전에 컴파일하여 쿼리 문법 구조를 메모리에 불변 고정 |
| 파라미터 바인더 | 사용자 입력값을 특수문자 변조 위험 없이 순수 데이터 리터럴 변수로 바인딩 |
| 식별자 매핑기 | 바인딩 불가능한 `ORDER BY` 등의 동적 식별자를 서버 내 정적 Enum 테이블과 대조 |

#### 한줄 요약
- 다섯 요소는 값의 형태를 다루는 앞 계층과 구문의 경계를 다루는 뒤 계층으로 갈리며, 바인딩이 닿지 못하는 동적 식별자 영역만은 정적 매핑이 검증 방식 자체를 바꿔 떠맡는다.

## Ⅳ. 흐름도

<details><summary>용어 설명</summary>

- **CWE-20 4대 원칙**: 1. 정규화 선행, 2. 화이트리스트 기반, 3. 서버 측 강제, 4. 문맥별 데이터 분리.

</details>

```text
요청 수신, 정규화 전처리, 서버 측 검증, 쿼리 컴파일 및 바인딩 파이프라인
        │
   1. [클라이언트 요청 유입] REST API 요청 페이로드(`{ "sort": "1", "search": "%27%20OR%201=1" }`) 수신
        │
   2. [정규화 전처리] 디코딩 라이브러리를 통해 이중 인코딩 및 특수 우회 문자를 표준 문자열로 복원
        │
   3. [서버 측 화이트리스트 검증]
       ├─ `search` 파라미터: 허용 정규식(`^[a-zA-Z0-9가-힣\s]{1,50}$`) 대조 ➔ [특수문자 포함 시 즉시 기각]
       └─ `sort` 파라미터: 정수형 범위(1~3) 대조 통과
        │
   4. [쿼리 골격 사전 컴파일] DB 엔진에 `SELECT * FROM items WHERE name LIKE ? ORDER BY ` 전달
        │
   5. [동적 식별자 매핑 및 바인딩]
       ├─ `sort="1"` ➔ 서버 코드 내 매핑 테이블에 의해 `ORDER BY create_date DESC` 로 안전 치환
       └─ `search` 값은 `pstmt.setString(1, "%" + search + "%")` 로 바인딩 변수에 대입
        │
   ▼
6. [안전한 DBMS 실행] DBMS 파서가 입력값을 순수 검색 키워드로만 평가하여 실행 완료
```

- 1. 클라이언트 요청 유입
- 2. 정규화 전처리
- 3. 서버 측 화이트리스트 검증
- 4. 쿼리 골격 사전 컴파일
- 5. 동적 식별자 매핑 및 바인딩
- 6. 안전한 DBMS 실행

#### 한줄 요약
- 정규화가 검증보다 앞서지 않으면 이중 인코딩된 입력이 검증을 통과한 뒤 원형으로 복원되므로, 방어의 성패는 개별 기법의 강도가 아니라 이들이 놓이는 순서에서 갈린다.

## Ⅴ. 종류 및 비교

<details><summary>용어 설명</summary>

- **1. 정규화 (전처리)** vs **2. 화이트리스트 검증 (문지기)** vs **3. 파라미터 바인딩 (물리적 격리)**.

</details>

| 비교 항목 | 1. 정규화 (Normalization) | 2. 화이트리스트 검증 (Allowlist) | 3. 파라미터 바인딩 (Binding) |
|:---|:---|:---|:---|
| 핵심 목적 | 인코딩 우회 기법 해제 및 표준화 | 비정상 입력값 사전 유입 차단 | 구문-데이터 물리적 격리 (인젝션 방지)|
| 실행 위치 | API 게이트웨이 / 프론트 컨트롤러 | 백엔드 유효성 검증 계층 (DTO/Service) | 데이터 액세스 계층 (DAO / ORM) |
| 방어 메커니즘 | 이중 URL/유니코드 디코딩 | 정규표현식 및 스키마 타입/길이 검증 | PreparedStatement `?` 홀더 치환 |
| 주요 방어 위협 | 이중 인코딩 우회, 널 바이트 인젝션 | 비정상 비즈니스 입력, DoS 페이로드 | SQL Injection, NoSQL Injection |
| 단독 적용 한계 | 검증 자체는 수행하지 않음 (전처리) | 복잡한 텍스트(게시글 등) 정규식 작성 난해| ORDER BY 등 동적 식별자엔 적용 불가|

#### 한줄 요약
- 셋은 같은 비신뢰 입력을 서로 다른 지점에서 다루는 직렬 단계라 대체 관계가 아니며, 앞 단계가 빠지면 뒤 단계의 전제가 무너지고 바인딩만 남기면 동적 식별자가 통째로 사각지대로 남는다.

## Ⅵ. 실무 고려사항 및 대책

<details><summary>용어 설명</summary>

- **Bean Validation (JSR 380)**: 자바 환경에서 `@NotNull`, `@Size`, `@Pattern` 등의 어노테이션으로 DTO 입력값을 선언적으로 검증하는 표준.

</details>

| 문제 | 대책 | 효과 |
|:---|:---|:---|
| 클라이언트(JS) 검증만 믿고 서버 측 검증을 생략하여 파라미터 변조 및 권한 탈취 사고 발생 | 모든 API 엔드포인트에 서버 측 **Bean Validation**(JSR-380) 화이트리스트 검증 강제 | 프론트엔드 검증 우회 조작 공격 100% 차단 |
| PreparedStatement 바인딩 불가 영역인 `ORDER BY` 동적 쿼리에서 SQL 인젝션 발생 | 동적 식별자에 대한 정적 화이트리스트 매핑 테이블(Enum / Map) 정의 및 사전 검증 | 바인딩 한계 영역에 대한 사용자 입력 직접 연결 차단 |
| 문자열 직접 결합(`+`)으로 SQL을 작성하여 코드베이스 전반에 수백 개 인젝션 결함 발생 | Spring Data JPA 등 안전한 ORM 도입 및 정적 분석(SAST) CI 연동 | 개발자 코딩 실수를 배제하고 파라미터 바인딩 자동화 |
| 파일 업로드 시 파일명 경로 조작(Directory Traversal) 취약점 발생 | 파일명 UUID 재생성 및 절대 경로 화이트리스트 검증 적용 | 악의적 경로 조작 및 상위 디렉터리 파일 덮어쓰기 방어 |

#### 한줄 요약
- 서버 측 Bean Validation으로 입구를 막고, 정적 매핑으로 동적 쿼리를 보호하며, ORM으로 바인딩을 강제한다.

## Ⅶ. 결론

- 모든 웹 및 분산 애플리케이션 보안의 출발점이자 외부 비신뢰 데이터로부터 내부 시스템 자산을 보호하는 소프트웨어 개발보안(CWE-20) 및 데이터 무결성 보장의 최우선 방어선으로 확고히 규정되어 있으며, 선언적 DTO 유효성 검증(Bean Validation)과 프레임워크 자동 바인딩으로 표준화되는 가운데, 실무 애플리케이션 구현 시에는 클라이언트 검증에 의존하지 않는 100% 서버 측 화이트리스트(Allowlist) 검증 강제, 이중 인코딩 우회를 무력화하는 입력값 정규화(Canonicalization) 선행, PreparedStatement 매개변수화 바인딩을 통한 쿼리 실행 계획 불변 고정, ORDER BY 등 동적 식별자에 대한 정적 Enum 매핑 통제를 결합하여 완벽한 입력 데이터 보안 신뢰성을 완성

#### 한줄 요약
- 입력값 검증 및 바인딩은 정규화와 서버 측 화이트리스트 검증 및 PreparedStatement 바인딩을 통해 입력값 조작 및 인젝션을 완벽히 차단하는 데이터 보호 체계다.
