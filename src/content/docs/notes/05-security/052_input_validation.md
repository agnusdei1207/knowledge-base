## Ⅰ. 개요

<details><summary>용어 설명</summary>

- **입력값 검증 (Input Validation)**: 클라이언트가 보낸 데이터가 진짜로 '이메일 형식'이 맞는지, 길이는 50자를 안 넘는지 서버(백엔드)에서 깐깐하게 팩트 따져보는 문지기다.
- **파라미터 바인딩 (Parameter Binding)**: DB한테 "내가 보낸 입력값은 단순한 텍스트(데이터)지, 절대 SQL 명령어 코드가 아니야!" 하고 박스에 담아 물리적으로 팩트 격리하는 필수 방어 기술이다.

</details>

- 정의: 외부 클라이언트로부터 유입되는 모든 데이터는 허용목록 기반으로 검증하고, DB나 시스템 명령어 생성 시 입력값을 파라미터로 팩트 격리 처리하는 보안 아키텍처다.
- 배경: 해커가 `<script>`나 `' OR 1=1 --`처럼 복잡한 우회 구문을 섞어 보내면, '욕설 필터링' 같은 단순 차단목록(블랙리스트) 방식으로는 인젝션 공격을 팩트로 다 막아낼 수 없기 때문이다.

#### 한줄 요약

- 들어오는 데이터는 '허용된 것만' 팩트로 받고, DB에 넣을 땐 쿼리문(코드)과 입력값(데이터)을 완전히 격리해라.

## Ⅱ. 특징

<details><summary>용어 설명</summary>

- **허용 목록 (Allowlist / Positive Validation)**: "해킹 코드 빼고 다 들어와"가 아니라, "숫자랑 영어 10글자 이내만 들어와"처럼 안전하다고 100% 확정된 패턴만 수용하고 나머진 다 팩트 거부하는 화이트리스트다.
- **정규화 (Normalization / Canonicalization)**: 해커가 필터링을 피하려고 URL 인코딩(`%27`)이나 유니코드로 문자를 꼬아 보내면, 이걸 다시 알아볼 수 있는 원래 문자(`'`)로 팩트 변환해서 속임수를 깨부수는 사전 작업이다.
- **동적 식별자 (Dynamic Identifier)**: 파라미터 바인딩(물음표 `?`)이 안 먹히는 `ORDER BY 컬럼명` 같은 자리다. 여긴 입력값을 절대 바로 쓰지 않고, `1=name, 2=date`처럼 서버 코드에 매핑해둔 안전한 값만 팩트로 꽂아야 한다.

</details>

- **팩트 정규화 및 허용 목록**: 꼬아 보낸 문자를 정규화로 풀고 나서, 서버 단에서 데이터 형식/길이/범위를 깐깐한 허용 목록 기반으로 팩트 검증한다.
- **팩트 구문과 데이터 격리**: `PreparedStatement`를 사용해 DB 쿼리 실행 구문(Code 뼈대)과 사용자 입력 데이터(Data)를 파라미터 바인딩으로 완전 팩트 물리적 격리한다.
- **팩트 동적 식별자 통제**: 구조적으로 바인딩이 불가능한 동적 식별자(테이블명, 컬럼명)는 입력값을 직접 쓰지 않고 서버에 하드코딩된 변수와 팩트로 안전하게 매핑(Mapping)한다.

#### 한줄 요약

- 꼬인 글자 풀고(정규화) $\to$ 정해진 형식만 받고(허용목록) $\to$ DB 쿼리랑 데이터는 박스 쳐서 팩트 분리(바인딩)한다.

## Ⅲ. 구조 및 구성요소

<details><summary>용어 설명</summary>

- **파서 (Parser)**: HTTP 요청, JSON, XML 등의 텍스트 뭉치를 서버가 이해할 수 있는 객체로 파싱하고 인코딩을 풀어주는 분석기다.
- **안전 실행 API (Secure Execution API)**: 개발자가 직접 `SELECT * FROM users WHERE id = '` + id + `'` 처럼 위험하게 문자열 더하기를 하지 못하게 막아주는, 안전하게 설계된 쿼리 전용 팩트 라이브러리다.

</details>

```text
[ 입력 통제 및 바인딩 팩트 방어 아키텍처 ]

[ 1. 입력 계약 정의 ] ── ("API 스펙에 '나이는 숫자 1~150까지만 받아!'라고 팩트 정의함")
      │
      ▼
[ 2. 정규화 및 파서 ] ── ("해커가 꼬아 보낸 인코딩 문자열을 알아볼 수 있게 단일 포맷으로 팩트 품")
      │
      ▼
[ 3. 허용 목록 검증 ] ── ("정상적인 형식(이메일, 전화번호 등)이 아니면 무조건 팩트 컷!")
      │
      ▼
[ 4. 파라미터 바인딩 ] ── ("DB에 보낼 땐 SQL 뼈대랑 입력 데이터를 박스로 완전히 팩트 분리함")
      │
      ▼
[ 5. 최소 권한 질의 실행 ] ── ("행여나 뚫려도 DB 전체 못 날리게 권한 쪼개서 팩트 실행함")
```

| 구성요소 | 팩트 폭행 책임 | 비고 |
|:---|:---|:---|
| **입력 계약 정의** | API 스키마 상에 형식, 길이, 필수 여부를 **명확하게 팩트로 정의함** | Contract |
| **정규화 및 파서** | 검증을 피하려는 이중 인코딩 꼼수를 **표준 단일 포맷으로 팩트 디코딩함** | Parse |
| **허용 목록 검증** | 프론트엔드 자바스크립트 검사 믿지 말고 **서버(백엔드)에서 무조건 팩트 재검증함** | Allowlist |
| **파라미터 바인딩** | 쿼리 구문과 데이터를 분리하여 **인젝션 공격을 구조적으로 팩트 차단함** | Bind |
| **최소 권한 실행** | 웹 애플리케이션이 DB에 붙을 땐 딱 필요한 테이블만 건드리는 **최소 권한만 팩트로 줌** | Least Priv |

#### 한줄 요약

- 서버가 스펙 정해놓고, 꼼수 풀어서 확인하고, DB 던질 때 데이터만 쏙 분리해서 던지는 팩트 철벽 수비다.

## Ⅳ. 흐름도

<details><summary>용어 설명</summary>

- (상단 참조)

</details>

```text
[ 외부 입력 데이터 검증 및 쿼리 팩트 실행 흐름 ]

┌──────────────────────────────┐
│ 1. [외부 입력 및 팩트 정규화]
│ ("해커가 '%27 OR 1=1' 로 보낸 걸 디코딩해서 원본 텍스트로 팩트 까발림")
└──────────────┬───────────────┘
               ▼
┌──────────────────────────────┐
│ 2. [허용 목록(Allowlist) 팩트 검증]
│ ("아이디 칸에 'OR 1=1' 같은 특수기호가 있네? 허용된 문자가 아니니 팩트 기각!")
└──────────────┬───────────────┘
               ▼
┌──────────────────────────────┐
│ 3. [고정 SQL 구조 팩트 사전 컴파일 (Prepare)]
│ ("검증 통과하면, DB 엔진에 'SELECT * FROM users WHERE id = ?' 뼈대를 먼저 팩트 전송함")
└──────────────┬───────────────┘
               ▼
┌──────────────────────────────┐
│ 4. [입력값 파라미터 팩트 바인딩]
│ ("빈칸(?) 자리에 사용자 입력값을 '명령어 코드'가 아닌 단순 '문자열 데이터'로 팩트 삽입함")
└──────────────┬───────────────┘
               ▼
┌──────────────────────────────┐
│ 5. [최소 권한 기반 팩트 질의 실행]
│ ("혹시 모를 사태에 대비해 제한된 최소 DB 계정 권한으로만 팩트 쿼리 실행!")
└──────────────────────────────┘
```

### 동작 원리

1. 정규화 입력: 검증 회피 목적의 인코딩/난독화 데이터를 팩트 디코딩하여 표준 포맷으로 변환함.
2. 허용 업무 값 검증: 백엔드 서버 단에서 허용 목록(정규식 등)을 기준으로 형식, 길이의 정합성을 팩트 판정함.
3. 사전 컴파일: DB 엔진에 SQL 실행 계획(Execution Plan) 골격 체계를 고정하여 사전 팩트 컴파일함.
4. 파라미터 바인딩: 입력값을 바이트 파라미터 채널로 밀어 넣어 쿼리 구문 변조를 팩트 원천 차단함.
5. 최소 권한 실행: 취약점 연계 확산을 막기 위해 애플리케이션 전용 최소 권한 DB 계정으로 팩트 집행함.

#### 한줄 요약

- 디코딩으로 속임수 풀고, 허용목록으로 나쁜 놈 거르고, 바인딩으로 남은 놈마저 상자에 가둬서 팩트 처리한다.

## Ⅴ. 종류 및 비교

<details><summary>용어 설명</summary>

- (상단 설명 참조)

</details>

| 입력 통제 단계 | **1. 정규화 (Normalization)** | **2. 허용 목록 (Allowlist 검증)** | **3. 파라미터 바인딩 (Binding)** |
|:---|:---|:---|:---|
| 팩트 폭행 비유 | **외국어로 꼬아 쓴 욕설을 한국어로 팩트 번역해놓기** | **클럽 입구에서 '초대장 있는 사람'만 팩트 들여보내기** | **택배 내용물을 편지(명령)로 안 읽고 짐짝(데이터)으로만 팩트 취급하기** |
| 핵심 방어 방식 | URL 인코딩 등 우회 표현을 **표준 형태로 풀어내어 필터링 우회를 팩트 사전 차단함** | 차단 목록(블랙리스트) 대신 정해진 형식과 길이만 수용하고 **나머지는 팩트 거부함** | 쿼리 구문(Code)과 데이터(Value)를 물리적으로 분리하여 **인젝션을 원천 팩트 방어함** |
| 장점 및 특징 | 뒤에서 수행할 검증 로직이 **꼼수에 당하지 않게 확실한 팩트 밑작업을 해줌** | 새로운 해킹 꼼수가 나와도 **내가 허용한 패턴이 아니면 무조건 팩트로 컷트함** | 개발자가 일일이 따옴표를 이스케이프(치환)할 필요 없이 **구조적으로 안전 팩트 보장됨** |
| 한계 및 문제점 | 잘못된 파서(Parser)를 쓰면 **이중 인코딩(Double Encoding) 꼼수에 팩트로 털림** | 비즈니스 로직이 복잡해질수록 **허용 목록 패턴(정규식)을 엄격하게 짜기가 팩트로 빡셈** | 컬럼명이나 테이블명 같은 **동적 식별자 자리(ORDER BY 등)엔 바인딩을 팩트로 못 씀** |

#### 한줄 요약

- 정규화는 **속임수 풀기**, 허용목록은 **입구 컷**, 바인딩은 **실행 컷** 팩트 3단 콤보다.

## Ⅵ. 실무 고려사항 및 대책

<details><summary>용어 설명</summary>

- **MITRE CWE-20**: "사용자가 보낸 값 믿지 말고 서버에서 무조건 빡세게 검사해라" 하고 팩트로 때리는 글로벌 보안 취약점 명세다.
- **ORM (객체 관계 매핑)**: JPA나 MyBatis처럼 쿼리를 문자열로 직접 안 짜고 객체로 맵핑해주면, 프레임워크가 알아서 안전하게 파라미터 바인딩을 팩트로 걸어주는 꿀가성비 기술이다.

</details>

| 장애/위험 요소 | 원인 분석 | 실무 대책 및 해결방안 | 기대 효과 |
|:---|:---|:---|:---|
| 프론트엔드(JS)에서 빡세게 막았는데 **해커가 프록시 툴로 값 변조해서 팩트 털림** | 클라이언트(웹 브라우저) 단 검사만 순진하게 믿고, 정작 서버(백엔드)에서 팩트 재검증을 안 함 | **MITRE CWE-20** 기반, 서버 단에서 반드시 정규식 기반 **허용 목록(Allowlist) 팩트 검증 강제** | 클라이언트단 검증 우회 조작 공격을 서버 백엔드 로직에서 팩트 원천 차단 |
| 파라미터 바인딩 다 썼는데 **ORDER BY (컬럼명) 자리에서 SQL 인젝션 팩트 터짐** | 컬럼명이나 테이블명 같은 식별자는 바인딩(`?`) 처리가 안 되는 구조적 한계를 팩트로 몰랐음 | 파라미터화 불가능한 **동적 식별자**는 사용자 입력을 아예 안 쓰고 **서버 하드코딩 맵핑 변수 팩트 사용** | ORDER BY나 테이블 동적 쿼리 구문에서의 인젝션 취약점 팩트 완벽 소멸 |
| 개발자들이 귀찮다고 문자열 계속 더해서 **취약점 스캐너에 인젝션 천 개 팩트 적발됨** | 생짜 JDBC나 쌩 SQL 텍스트를 쓰면서 개발자 개인의 꼼꼼함과 실력에만 방어를 팩트로 떠넘김 | SQL 구문을 추상화하여 기본적으로 바인딩을 강제하는 **안전한 ORM(JPA 등) 프레임워크 팩트 도입** | 개발자의 Human Error 개입을 차단하고, 파라미터 바인딩 팩트 자동화 달성 |

#### 한줄 요약

- 서버에서 허용목록 검사하고, 바인딩 안 되는 컬럼명은 매핑하고, 웬만하면 직접 쿼리 짜지 말고 ORM 팩트로 써라.

## Ⅶ. 결론

<details><summary>용어 설명</summary>

- **입력 통제 적용 기준 (Input Control Criteria)**: "아무것도 믿지 마라. 정규화하고, 화이트리스트로 검사하고, 바인딩 박스에 가둬서 실행해라" 하는 팩트 방어 철학이다.

</details>

- 외부 입력값은 절대 신뢰할 수 없으므로 데이터 유입 시 반드시 **정규화** 후 **서버 단 허용 목록**으로 검증하고, DB 쿼리 실행 시 **파라미터 바인딩(PreparedStatement)** 으로 구문과 데이터를 격리하며, 바인딩 불가 영역은 **동적 식별자 매핑**으로 방어하는 팩트 실무 기조를 확립함

#### 한줄 요약

- 외부 값은 **허용목록**으로 막고, DB 쿼리는 **바인딩**으로 팩트 격리해라.
