## Ⅰ. 개요

<details><summary>용어 설명</summary>

- **해시 함수 (Hash Function)**: 고기 10kg을 넣든 10g을 넣든 항상 똑같은 크기의 소시지(다이제스트)를 뽑아내는 마법의 분쇄기(단방향 암호)다.
- **다이제스트 (Digest)**: 원본 데이터를 갈아서 만든 고정 길이의 결과값(지문)이다.

</details>

- 정의: 임의 길이의 데이터를 입력받아 고정된 길이의 **다이제스트(지문)** 로 팩트 변환하는 **해시 함수** 기술이다.
- 배경: 대용량 원본 파일 전체를 매번 직접 비교하는 건 **전송•검증 비용 증가** 때문에 팩트로 불가능하므로, 지문(해시값)만 뽑아서 대조할 가벼운 체계가 필요했다.

#### 한줄 요약

- 원본 데이터가 조작되지 않았음을(무결성) 팩트로 증명하기 위해, 데이터를 갈아서 짧은 지문을 뽑아내는 마법이다.

## Ⅱ. 특징

<details><summary>용어 설명</summary>

- **쇄도 효과 (Avalanche Effect)**: 100GB짜리 영화 파일에서 점 하나만 팩트로 바꿔도, 해시값 전체가 100% 딴판으로 뒤집어지는 엄청난 민감성이다.
- **충돌 저항성 (Collision Resistance)**: 해시값이 똑같이 나오는 서로 다른 두 개의 파일(쌍둥이)을 찾는 것이 수학적으로 불가능한 성질이다.
- **역상 저항성 (Pre-image Resistance)**: 소시지(해시)를 보고 원래 어떤 돼지(원본)였는지 절대 팩트로 역산할 수 없는 단방향 성질이다.

</details>

- **팩트 민감성 (쇄도 효과)**: 입력 데이터의 단 1비트만 변경돼도 출력 다이제스트 전체가 완전히 변하는 **쇄도 효과**를 제공한다.
- **단방향 및 무결성 (저항성)**: 원래 데이터로의 역산을 막고(**역상 저항성**), 위조 문서를 만들지 못하게 차단(**충돌 저항성**)한다.
- **팩트 한계 (송신자 인증 불가)**: 비밀키가 필요 없어서 누구나 해시를 돌릴 수 있으므로, "이걸 누가 만들었는지"는 팩트로 증명할 수 없다.

#### 한줄 요약

- 점 하나만 찍혀도 지문이 완전히 바뀌기 때문에 무결성 확인엔 짱이지만, 누가 찍었는지(인증)는 이것만으론 알 수 없다.

## Ⅲ. 구조 및 구성요소

<details><summary>용어 설명</summary>

- **입력 전처리 (Padding)**: 기가바이트 단위의 원본을 한 번에 갈 수 없으니, 믹서기에 넣기 좋게 블록 단위로 썰고 빈 공간은 규격화된 솜(패딩)으로 채우는 단계다.

</details>

```text
[ 해시 함수 기반 다이제스트 팩트 생성 구조 ]

[ 1. 메시지 입력 ] ── (기가바이트급 원본 데이터 투입)
      │
      ▼
[ 2. 입력 전처리 (Padding) ] ── (512비트 블록으로 쪼개고 빈 공간에 규격 패딩을 채움)
      │
      ▼
[ 3. 상태 변환 함수 (압축) ] ── (쪼갠 블록을 하나씩 넣으면서 이전 상태와 함께 믹서기 돌림)
      │
      ▼
[ 4. 다이제스트 출력 ] ── (모든 블록이 끝나면 튀어나오는 고정 길이 팩트 지문 반환)
```

| 구성요소 | 팩트 폭행 책임 | 비고 |
|:---|:---|:---|
| **메시지 입력** | 임의의 크기를 가진 **원본 데이터를 쑤셔 넣는 단계** | Input |
| **입력 전처리 (Padding)** | 데이터를 썰기 좋게 **규격(블록)을 맞추고 쓰레기값을 채우는 단계** | Padding |
| **상태 변환 함수** | 잘라진 블록들을 이전 내부 상태와 섞어서 **믹서기로 팩트 압축하는 엔진** | Compression |
| **다이제스트 출력** | 압축이 모두 끝나고 튀어나온 **최종 고정 길이의 팩트 지문 (예: 256비트)** | Digest |

#### 한줄 요약

- 원본을 규격에 맞게 썰고 $\to$ 믹서기로 계속 압축하고 섞어서 $\to$ 최종적인 짧은 지문 하나를 토해낸다.

## Ⅳ. 흐름도

<details><summary>용어 설명</summary>

- **반복 상태 갱신**: 첫 번째 블록을 갈아 만든 즙(상태)에 두 번째 블록을 넣고 또 가는 식으로, 모든 블록이 팩트로 연쇄적인 영향을 미치게 만드는 루프(Loop)다.

</details>

```text
[ 다이제스트 추출을 위한 단방향 해시 십자포화 흐름 ]

┌──────────────────────────────┐
│ 1. [데이터 인코딩 및 패딩 (전처리)]
│ (파일 크기 정보를 붙이고 512비트 블록으로 예쁘게 팩트 분할함)
└──────────────┬───────────────┘
               ▼
┌──────────────────────────────┐
│ 2. [첫 번째 블록 투입 및 초기 상태 믹싱]
│ (첫 블록을 초기값(IV)과 함께 믹서기(압축 함수)에 넣고 팩트로 돌림)
└──────────────┬───────────────┘
               ▼
┌──────────────────────────────┐
│ 3. [연쇄적인 상태 갱신 (반복 루프)]
│ (이전 믹서기 결과물에 다음 블록을 넣고 계속 섞음. 1비트만 달라도 폭주함)
└──────────────┬───────────────┘
               ▼
┌──────────────────────────────┐
│ 4. [모든 블록 소진 및 최종 다이제스트 추출]
│ (더 이상 넣을 데이터가 없으면 믹서를 끄고 최종 팩트 지문을 뽑아냄)
└──────────────────────────────┘
```

### 동작 원리

1. 전처리 및 패딩: 입력 데이터를 인코딩하고, 정해진 블록 크기에 맞게 끝부분에 팩트 패딩을 덧붙임.
2. 초기 블록 압축: 패딩된 첫 메시지 블록을 상태 변환 함수(믹서기)에 밀어 넣고 초기 상태를 갱신함.
3. 반복 연쇄 압축: 이전 블록의 결과(내부 상태)를 다음 블록과 계속 섞어서 팩트 연쇄 반응을 일으킴.
4. 다이제스트 반환: 마지막 블록까지 다 갈아버린 후, 고정된 길이의 최종 해시값을 반환함.

#### 한줄 요약

- 덩어리를 썰어서 $\to$ 이전 즙이랑 섞어 갈고 $\to$ 또 갈고 $\to$ 마지막에 한 방울의 에센스(해시)를 짠다.

## Ⅴ. 종류 및 비교

<details><summary>용어 설명</summary>

- **SHA-2**: 현재 전 세계 모든 인증서와 시스템에서 국룰로 쓰는 든든한 팩트 표준 해시 알고리즘이다.
- **SHA-3**: 구조를 '스펀지(Sponge)' 형태로 완전히 갈아엎어서, SHA-2가 털리더라도 동반 자살하지 않게 만든 차세대 대안이다.
- **SHA-1**: 구글이 충돌쌍(똑같은 해시를 갖는 가짜 파일)을 찾아내면서 보안용으론 사형 선고를 받은 옛날 해시다.

</details>

| 해시 알고리즘 | **SHA-2 (현재 국룰 표준)** | **SHA-3 (차세대 스펀지)** | **SHA-1 (구형/사망)** |
|:---|:---|:---|:---|
| 팩트 폭행 비유 | **세상 모든 곳에서 쓰는 든든한 '다용도 믹서기'** | **구조를 완전히 갈아엎은 '신형 스펀지 믹서기'** | **모터 고장 나서 해커한테 털리는 '고물 믹서기'** |
| 핵심 기술 원리 | 이전 해시 구조를 업그레이드한 **FIPS 180-4 표준** (SHA-256 등) | 흡수/짜내기(Sponge)라는 완전히 새로운 아키텍처 적용 (**FIPS 202**) | 160비트 출력 크기를 가지는 구형 해시 함수 |
| 최고 장점 | 하드웨어 가속기가 다 깔려 있어서 **팩트로 제일 빠르고 호환성 만렙임** | SHA-2가 털리더라도 **구조가 아예 달라서 동반 자살을 피할 수 있음** | 옛날 시스템에서 가볍게 팩트로 돌아감 |
| 치명적 한계 | 길이 연장 공격(Length Extension)에 취약해 **HMAC 없이 쓰면 털릴 위험 있음** | S/W 연산이 상대적으로 느리고 **하드웨어 가속기 지원이 아직 팩트로 부족함** | 구글이 충돌쌍을 찾아내서 **보안용으로 쓰면 무조건 해킹당함(사형 선고)** |

#### 한줄 요약

- 보안 시스템 만들 땐 무조건 SHA-2 이상을 쓰고, SHA-1은 팩트 쓰레기통에 버려야 한다.

## Ⅵ. 실무 고려사항 및 대책

<details><summary>용어 설명</summary>

- **솔트 (Salt)**: "password" 같은 뻔한 비밀번호를 그냥 해시 돌리면 해커가 다 아니까, 무작위 소금을 팍팍 쳐서 다이제스트를 완전히 꼬아버리는 팩트 조미료다.
- **HMAC (Hash-based MAC)**: 해시만 쓰면 해커가 파일과 해시를 둘 다 조작해 버리니까, "나만 아는 비밀키"를 섞어서 해시를 굽는 팩트 무결성 인증 기술이다.

</details>

| 장애/위험 요소 | 원인 분석 | 실무 대책 및 해결방안 | 기대 효과 |
|:---|:---|:---|:---|
| 뻔한 비밀번호의 해시값이 **레인보우 테이블로 0.1초 만에 털림** | 똑같은 비번은 늘 똑같은 해시가 나옴. 해커가 이미 모든 해시값을 팩트로 다 계산해 둠 | 무작위 난수 **'솔트(Salt)'를 치고, GPU 공격을 막는 'Argon2id' 팩트 적용함** | 오프라인 사전 공격 및 무차별 대입 공격 원천 방어 |
| 해커가 원본 파일과 **해시값을 팩트로 동시에 바꿔치기함** | 해시는 무결성만 증명할 뿐, 비밀키가 없어서 누구나 해시값을 다시 만들 수 있음 | 해시와 대칭키를 섞어서 도장을 찍는 **'HMAC' 또는 비대칭키 '전자서명' 팩트 결합** | 조작된 데이터의 무결성 검증 통과(우회) 위협 원천 봉쇄 |
| 똑같은 파일인데 **서버-클라이언트 간 해시 검증이 자꾸 실패함** | 엔터(CRLF), 공백, 인코딩(UTF-8) 등 미세한 데이터 포맷 차이가 쇄도 효과를 일으킴 | 해시를 굽기 전에 양측의 데이터를 똑같이 맞추는 **'입력 정규화(Normalization)' 팩트 적용** | 이기종 환경에서의 무결성 오탐/미탐으로 인한 서비스 장애 방지 |

#### 한줄 요약

- 해시는 만능이 아니다. 비밀번호엔 소금(Salt) 치고, 파일 검증엔 비밀키(HMAC) 섞고, 입력값은 예쁘게 맞춰라(정규화).

## Ⅶ. 결론

<details><summary>용어 설명</summary>

- **용도 분리 (Context Separation)**: 무결성 검사용(SHA-2)과 패스워드 보호용(Argon2id)은 애초에 요구하는 스펙이 다르므로 절대 팩트로 섞어 쓰면 안 된다는 원칙이다.

</details>

- 대용량 데이터의 무결성 검증 한계를 극복하기 위해, 범용 파일 검증엔 **SHA-2**와 **HMAC**을 결합하고, 비밀번호 저장엔 메모리 경화 해시인 **Argon2id**를 채택하는 **용도 분리** 기조 확립함

#### 한줄 요약

- 해시는 데이터의 팩트 지문이다. 지문 채취할 땐 도장이 진짜인지(HMAC)와 원본 잉크가 섞였는지(솔트)를 팩트로 따져야 한다.
