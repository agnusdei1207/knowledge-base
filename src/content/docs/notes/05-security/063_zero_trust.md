## Ⅰ. 개요

<details><summary>용어 설명</summary>

- **ZTA (제로 트러스트 아키텍처)**: "사내망이니까 안전하겠지"라는 낡은 믿음을 싹 버리고, 접속할 때마다 신원, 기기 상태, 접속 위치를 지속 검증하여 권한을 통제하는 최신 보안 철학이다.
- **묵시적 신뢰 (Implicit Trust)**: 예전엔 VPN 방화벽 한 번 뚫고 사내망(IP)에 들어오면 "우리 편이네" 하고 내부 자원 전체를 프리패스로 열어주던 최악의 결함 방식이다.
- **측면 이동 (Lateral Movement)**: 해커가 보안이 약한 말단 직원 PC 하나를 털고 들어와서, 묵시적 신뢰를 악용해 내부망을 이리저리 휘젓고 다니며 핵심 DB 서버까지 털어먹는 해킹 기법이다.

</details>

- 정의: 네트워크 경계 내부 위치를 전혀 신뢰하지 않고, 모든 자원 접근 시 신원과 기기를 명시적으로 검증하는 아키텍처 모델이다.
- 배경: 기존 경계 방어선의 묵시적 신뢰(Implicit Trust)가 무너지면서, 측면 이동(Lateral Movement)에 의한 대규모 랜섬웨어 피해와 내부 정보 유출이 폭증했기 때문이다.

#### 한줄 요약

- 성벽 방어선 무너졌으니까, 이제 회사 안이든 밖이든 무조건 다 의심하고 로그인할 때마다 검사하는 체계다.

## Ⅱ. 특징

<details><summary>용어 설명</summary>

- **명시적 검증 (Explicit Verification)**: 사내망에 있든 카페에 있든 IP만 믿지 않고 무조건 사용자 신원과 기기 상태(백신 유무)를 깐깐하게 검사하는 원칙이다.
- **지속 평가 (Continuous Evaluation)**: 로그인 한 번 성공했다고 끝이 아니라, 세션이 맺어져 있는 중간에도 기기에 악성코드가 돌면 즉각 연결을 끊어버리는 실시간 런타임 제어다.

</details>

- **절대 의심 및 검증**: 네트워크 위치(내/외부망)와 무관하게 모든 접근 요청에 대해 주체의 신원과 기기 무결성을 매번 엄격하게 명시적 철저한 검증한다.
- **최소 통제 구역 설정**: 업무 수행에 반드시 필요한 딱 그 자원에만 최소 권한을 부여하고 마이크로 세그먼테이션(Micro-Segmentation)으로 물리적/논리적 격리한다.
- **실시간 런타임 제어**: 최초 인증 합격에 만족하지 않고, 세션 진행 중에도 위험도를 지속 평가하여 이상 징후 시 세션을 즉시 폭파시킨다.

#### 한줄 요약

- 누구든 의심하고(검증), 딱 필요한 권한만 주고(최소 권한), 접속 내내 끝까지 감시한다(지속 평가).

## Ⅲ. 구조 및 구성요소

<details><summary>용어 설명</summary>

- **PE (정책 엔진)**: 로그인 시간, 위치, 기기 백신 상태 등 데이터를 쫙 모아서 "이놈 허용할까 말까?"를 계산하고 판결을 내리는 AI 두뇌다.
- **PA (정책 관리자)**: PE의 판결문을 전달받아 "통과시켜", "연결 끊어" 하고 실질적인 세션 제어 명령을 하달하는 컨트롤 타워다.
- **PEP (정책 집행점)**: 보호 자원 바로 앞단에 서서 PA 명령대로 데이터를 열어주거나 닫아버리는 문지기(게이트웨이/에이전트)다.

</details>

```text
[ 제로 트러스트 통제 아키텍처 (NIST SP 800-207) ]

[ 1. 주체 및 기기 ] ── ("나 사내망이고 로그인도 했어! 시스템 문 열어줘")
      │
      ▼
[ 2. PEP (정책 집행점) ] ── ("잠깐 대기. 통과증 없네. PA님, 얘 들여보낼까요?")
      │
      ▼
[ 3. PE (정책 엔진) ] ── ("(두뇌 평가) 백신 꺼져있고 이상한 IP네? 신뢰도 0점! 차단해!")
      │
      ▼
[ 4. PA (정책 관리자) ] ── ("야 PEP! 당장 통신 세션 끊어버려!")
      │
      ▼
[ 5. 보호 자원 ] ── ("PEP가 문을 물리적으로 닫아서 해커 침투 철저한 방어 완료")
```

| 구성요소 | 직관적 비교 책임 | 비고 |
|:---|:---|:---|
| **주체 / 기기** | 자원에 접속하려는 놈의 **신원, IP, 단말 OS 패치 상태 정보를 제공함** | Subject |
| **정책 엔진 (PE)** | 신원과 기기 등 수많은 위협 신호를 종합해서 **접근을 허락할지 말지 최종 판결함** | Brain |
| **정책 관리자 (PA)** | PE의 결정을 넘겨받아 **실제 암호화 데이터 세션을 열거나 끊는 명령을 내림** | Control |
| **정책 집행점 (PEP)** | 자원 앞을 직접 지키면서 **데이터 흐름을 물리적으로 열어주거나 가차 없이 원천 차단함** | Gateway |
| **보호 자원 (Resource)** | ZTA 통제하에 안전하게 보호받는 **회사의 핵심 DB, SaaS 애플리케이션 덩어리임** | Resource |

#### 한줄 요약

- PE가 두뇌 굴려 판결하고 $\to$ PA가 명령 내리고 $\to$ PEP가 문 닫아서 자원을 보호하는 삼각 편대다.

## Ⅳ. 흐름도

<details><summary>용어 설명</summary>

- (상단 참조)

</details>

```text
[ ZTA 동적 세션 및 통제 흐름 ]

┌──────────────────────────────┐
│ 1. [접근 맥락 및 기기 상태(Posture) 추출]
│ ("PEP가 로그인 요청 시 IP, 단말 백신 업데이트 상태 정보를 수집해 PE에 던짐")
└──────────────┬───────────────┘
               ▼
┌──────────────────────────────┐
│ 2. [신뢰 알고리즘 및 정책(Policy) 평가]
│ ("PE(두뇌)가 수집된 정보를 바탕으로 위험 점수를 계산하고 허용/거부 결정함")
└──────────────┬───────────────┘
               ▼
┌──────────────────────────────┐
│ 3. [시간 제한 및 최소 권한 세션 생성]
│ ("PA가 '너 딱 1시간만, 이 DB 서버만 써라' 하고 제한된 통로를 만들어줌")
└──────────────┬───────────────┘
               ▼
┌──────────────────────────────┐
│ 4. [보호 자원 접근 및 정책(PEP) 집행]
│ ("PEP가 문을 열어줘서 사용자가 마침내 보호 자원에 접속함")
└──────────────┬───────────────┘
               ▼
    ┌──────────────────────────────┐
    │ 5. [세션 유지 중 위험 지속 평가 (Continuous Evaluation)]
    │ ("접속 중 기기에 갑자기 악성코드 감지? PE가 재평가 후 즉시 세션 폭파함!")
    └──────────────────────────────┘
```

### 동작 원리

1. 정보 수집: **PEP**가 사용자의 신원, 위치, 단말 보안 상태(Posture) 데이터를 수집.
2. 평가: **PE** 내부의 신뢰 알고리즘이 보안 정책과 대조하여 통과, 거부, 또는 MFA 재인증 결정.
3. 세션 생성: **PA**가 최소 권한 및 유효 시간(TTL)이 적용된 한시적인 데이터 통신 자격을 셋업.
4. 정책 집행: **PEP**가 허가받은 트래픽만 보호 자원으로 흘려보내고 나머지는 모조리 드롭(Drop).
5. 지속 모니터링: 세션 도중 이상행위나 위협 피드가 탐지되면, **PE**가 즉시 권한을 축소하거나 세션을 원천 차단.

#### 한줄 요약

- 기기 검사 $\to$ PE 허락 $\to$ 통로 개설 $\to$ 접근 허용 $\to$ 접속 내내 CCTV로 감시하는 사이클이다.

## Ⅴ. 종류 및 비교

<details><summary>용어 설명</summary>

- (상단 설명 참조)

</details>

| 보안 아키텍처 모델 | **경계 중심 보안 (과거/기존)** | **제로 트러스트 / ZTA (미래)** | **혼합 전환 (Hybrid / 과도기)** |
|:---|:---|:---|:---|
| 비유 및 핵심 특징 | **성벽(방화벽) 하나만 뚫리면 성 안쪽은 완전 무방비인 호구 보안** | **성문 통과해도 건물마다, 방마다 전부 짐수색하고 신분증 검사하는 철통 보안** | **성벽은 냅두고 제일 중요한 방앗간부터 ZTA 자물쇠를 달아가는 과도기** |
| 핵심 통제 기준 | 방화벽이나 VPN 안쪽(내부 사내망 IP)에 들어오면 **모든 자원 접근을 묵시적으로 허용함** | 내부망이든 외부망이든 위치를 안 믿고 **모든 요청마다 신원/기기를 명시적으로 철저한 검증함** | 기존 인프라망을 유지하면서 **핵심 보호 자원(DB/앱)부터 단계적으로 전환함** |
| 장단점 / 한계 | VPN 한 번 털리면 해커가 내부망을 제집처럼 누비는 **측면 이동(Lateral Movement)에 싹 털림** | 내부 해킹 방어에 완벽하지만, **PE/PEP 연동 구조 짜는 게 아키텍처 상 미치도록 빡셈** | 초기 도입 예산 부담은 적지만 **기존 구형 시스템(Legacy)과 보안 정책 충돌이 잦음** |

#### 한줄 요약

- 경계선 방어 다 뚫리니까 무조건 **ZTA**로 가야 하는데, 당장 돈 없으니까 **혼합형**으로 조금씩 전환한다.

## Ⅵ. 실무 고려사항 및 대책

<details><summary>용어 설명</summary>

- **CISA ZTMM 2.0 (성숙도 모델)**: 미국 국토안보부(CISA)에서 "ZTA 한 번에 절대 못 하니까, 신원/기기/네트워크/앱/데이터 5개 기둥을 단계별로 천천히 올려라" 하고 만든 레벨업 가이드라인이다.

</details>

| 장애/위험 요소 | 원인 분석 | 실무 대책 및 해결방안 | 기대 효과 |
|:---|:---|:---|:---|
| ZTA 한다고 솔루션 수십 개 샀는데 **시스템끼리 연동 안 돼서 프로젝트 폭망함** | 벤더사(Cisco, PANW 등)마다 ZTA 개념을 다르게 해석해서 논리 구조(PE/PEP) 호환이 안 됨 | **NIST SP 800-207** 표준의 PE-PA-PEP 논리 아키텍처 기반 **공용 API 및 표준 연동 강제** | 이종 솔루션 간 신호 연동 무결성 100% 확보 및 특정 벤더 종속성(Lock-in) 탈피 |
| 기존 사내망 한 번에 ZTA로 엎으려다 **직원들 접속 튕기고 업무 올스톱 남** | 현재 회사의 보안 수준 파악 없이 빅뱅(Big-Bang) 방식으로 무리하게 전면 도입을 시도함 | **CISA ZTMM 2.0** 성숙도 모델 기반의 **5대 기둥(Pillar) 영역별 단계적 전환(Transition) 로드맵 수립** | 비즈니스 연속성 보장 및 임직원 거부감 없는 안정적 제로 트러스트 연착륙 달성 |
| ZTA 심장인 정책 엔진(PE) 서버 뻗었더니 **전 직원 인증 거부돼서 시스템 전면 마비됨** | 중앙 PE 서버가 단일 장애점(SPOF)인데, 죽었을 때 트래픽을 어쩔지 가용성 대책이 없음 | 정책 엔진 다중화(HA/DR) 및 장애 시 무조건 차단이 아닌 **제한 업무 모드(Fail-Secure) 가동** | 보안 통제 엔진 장애에도 치명적 중단 없는 핵심 비즈니스 생존성 및 복원력(Resilience) 확보 |

#### 한줄 요약

- **NIST** 표준으로 연동하고, **CISA ZTMM**으로 차근차근 올리고, 엔진 죽었을 때 대비한 **Fail-Secure** 챙겨라.

## Ⅶ. 결론

<details><summary>용어 설명</summary>

- **자원별 지속 검증 (Continuous Verification)**: 아침에 로그인 한 번 했다고 믿어주는 게 아니라, 엑셀 파일 열 때마다, 사내 메신저 켤 때마다 지독하게 백그라운드로 검사하는 통제 철칙이다.

</details>

- 클라우드 전환과 재택근무가 일상화된 현대 IT 환경에서 생존하기 위해, 낡은 '경계 중심 방어'를 폐기하고 **NIST SP 800-207** 표준에 입각한 **ZTA(PE-PA-PEP)** 를 도입하여, 치명적 내부 측면 이동을 끊어내는 **명시적 검증**과 **자원별 지속 평가** 기조를 전사적으로 확립함

#### 한줄 요약

- 내부망 맹신 버리고, **NIST 800-207** 기반으로 **명시적 지속 검증**하는 ZTA를 집중 적용하여라.
