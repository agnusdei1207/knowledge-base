## Ⅰ. 개요

<details><summary>용어 설명</summary>

- **SQL 인젝션(SQL Injection / CWE-89)**: 웹 애플리케이션이 클라이언트로부터 입력받은 비신뢰 데이터(Untrusted Input)를 검증 없이 동적 SQL 쿼리 문자열과 단순 결합하여 데이터베이스 엔진으로 전달할 때, 공격자가 악의적으로 삽입한 SQL 제어 구문(따옴표, 주석자, UNION, 서브쿼리)이 쿼리 구조를 변조하여 비인가 데이터 조회, 데이터 위변조, 관리자 권한 획득, OS 명령 실행을 유발하는 코드 인젝션 취약점.
- **코드와 데이터의 혼재(Code-Data Mingling Defect)**: 컴파일러나 인터프리터가 실행해야 할 '명령어 구조(Code)'와 처리해야 할 '값(Data)'이 단일 문자열 스트림으로 섞여 전달됨으로써, 입력 데이터가 명령어로 오인 해석되는 근본적 소프트웨어 결함.

</details>

- 정의/개념: 비신뢰 입력을 쿼리 인터프리터로부터 물리적으로 격리하기 위해 **사전 컴파일된 질의(PreparedStatement)**, **매개변수 바인딩(Parameter Binding)**, **정적 화이트리스트 검증(Allowlist)**, **최소 권한 DB 계정(Least Privilege)** 을 계층적으로 적용하는 **데이터베이스 접근 통제 아키텍처**
- 배경/필요성: WAF 기반의 시그니처 블랙리스트 필터링은 인코딩 우회(URL, Hex, 대소문자 혼합) 및 신종 난독화 공격에 쉽게 무력화되므로, 소스코드 레벨에서 쿼리 구조와 입력 데이터를 원천 분리할 요구

#### 한줄 요약
- PreparedStatement 매개변수 바인딩을 통해 코드와 데이터를 분리하고 최소 권한 DB 계정으로 공격을 원천 차단한다.

## Ⅱ. 특징

<details><summary>용어 설명</summary>

- **준비된 질의(PreparedStatement / Parameterized Query)**: 데이터베이스 엔진이 SQL 쿼리의 문법적 구조(실행 계획)를 사전에 컴파일(Pre-compile)해 둔 상태에서, 사용자 입력값을 오직 리터럴 데이터(Literal Value)로만 바인딩하여 쿼리 구조 변조를 원천 방지하는 프로그래밍 기법.
- **화이트리스트 검증(Allowlist / Parameter Binding 불가 영역)**: `ORDER BY` 절의 컬럼명이나 `TABLE` 명과 같이 PreparedStatement의 매개변수 바인딩(`?`)이 문법적으로 지원되지 않는 동적 영역에 대해, 사전에 정의된 안전한 식별자 목록과 엄격히 대조하는 검증 기법.

</details>

- **구문과 데이터의 원천 분리**: 데이터베이스 쿼리 파서가 사용자 입력을 실행 가능한 SQL 명령어로 재해석하는 경로 원천 차단
- **다양한 공격 추론 벡터 존재**: In-Band(직접 노출), Inferential/Blind(참/거짓 및 시간 지연 기반 추론), Out-of-Band(DNS/HTTP 외부 채널)
- **심층 방어 계층 구조**: 시큐어 코딩(1차) $\rightarrow$ DB 최소 권한 및 에러 은닉(2차) $\rightarrow$ WAF/DASP 인라인 차단(3차)

#### 한줄 요약
- 구문-데이터 원천 분리, 블라인드/OOB 등 다양한 추론 벡터, 시큐어 코딩 및 최소 권한 심층 방어를 제공한다.

## Ⅲ. 구조 및 구성요소

<details><summary>용어 설명</summary>

- **최소 권한 DB 계정(Least Privilege DB Account)**: 웹 애플리케이션 전용 데이터베이스 계정에서 `DROP`, `ALTER`, `xp_cmdshell` 등 치명적인 DDL 및 시스템 프로시저 실행 권한을 박탈하고, 해당 비즈니스에 필요한 특정 테이블의 `SELECT`, `INSERT`, `UPDATE` 권한만 부여하는 방어 원칙.

</details>

```text
[ 비신뢰 사용자 입력 (예: admin' OR '1'='1) ]
                      │
                      ▼
┌─────────────────────────────────────────────────────────────────────────┐
│ [ 1. 입력 검증 계층 (Input Validation Layer) ]                          │
│  ├─ 문자열 타입/길이 검증 및 화이트리스트 필터링                         │
│  └─ ORDER BY / 테이블명 동적 영역: 정적 매핑 테이블(Allowlist) 대조     │
└────────────────────────────────────┬────────────────────────────────────┘
                                     │
                                     ▼
┌─────────────────────────────────────────────────────────────────────────┐
│ [ 2. 애플리케이션 질의 계층 (Application Query Layer) ]                 │
│  ├─ PreparedStatement: `SELECT * FROM users WHERE id = ? AND pw = ?`   │
│  └─ Parameter Binding: 사용자 입력을 데이터베이스 드라이버 바인딩 변수에 대입│
└────────────────────────────────────┬────────────────────────────────────┘
                                     │ (쿼리 구조 컴파일 완료 ➔ 순수 리터럴 값 전달)
                                     ▼
┌─────────────────────────────────────────────────────────────────────────┐
│ [ 3. 데이터베이스 엔진 실행 계층 (DBMS Execution Layer) ]               │
│  ├─ 파서 재평가 없음: 입력값 전체를 단일 문자열 `"admin' OR '1'='1"`로 매칭│
│  ├─ 최소 권한 적용: DDL 실행 차단 및 시스템 테이블 접근 거부            │
│  └─ 에러 은닉(Error Masking): 내부 스택 트레이스 및 DB 구조 정보 반환 차단│
└─────────────────────────────────────────────────────────────────────────┘
```

선의 의미: 사용자 입력이 화이트리스트 검증을 거쳐 PreparedStatement 매개변수로 바인딩되어 DBMS에서 순수 데이터로 안전하게 처리되는 구조

| 구성요소 | 핵심 책임 및 역할 | 비고 |
|:---|:---|:---|
| **입력 검증 모듈** | 정규표현식 및 화이트리스트를 통해 입력 데이터의 타입, 길이, 허용 문자열 검증 | Validation |
| **PreparedStatement** | SQL 쿼리 실행 계획을 사전에 컴파일하여 쿼리 트리 구조를 고정 | Pre-compile |
| **매개변수 바인더** | 사용자 입력을 특수문자 이스케이프 필요 없이 순수 데이터 리터럴로 치환 | Parameter Binding|
| **최소 권한 DB 계정** | 웹 서비스용 계정의 DDL(`DROP`/`ALTER`) 및 시스템 프로시저 실행 권한 박탈 | DB Privileges |
| **에러 마스킹 모듈** | 쿼리 오류 발생 시 상세 SQL 구문 및 스키마 노출을 차단하고 범용 에러 코드 반환 | Error Masking |

#### 한줄 요약
- 입력 검증 모듈, PreparedStatement 컴파일러, 매개변수 바인더, 최소 권한 DB 계정, 에러 마스킹이 결합한다.

## Ⅳ. 흐름도

<details><summary>용어 설명</summary>

- **동적 쿼리(취약) vs 준비된 질의(안전) 실행 메커니즘 비교**:
  - **취약한 동적 쿼리**: `stmt.executeQuery("SELECT * FROM users WHERE id = '" + input + "'")` $\rightarrow$ `input`의 따옴표가 파서에 의해 쿼리 문법으로 재해석됨.
  - **안전한 준비된 질의**: `pstmt = conn.prepareStatement("SELECT * FROM users WHERE id = ?"); pstmt.setString(1, input);` $\rightarrow$ 파서는 구조만 컴파일하고 `input`은 메모리 데이터로만 대조.

</details>

```text
1. [클라이언트 요청] 공격자가 로그인 폼의 아이디 필드에 `' OR '1'='1` 악성 페이로드 입력
            │
            ▼
2. [쿼리 구조 사전 생성] 애플리케이션이 DBMS에 `SELECT * FROM users WHERE id = ?` 구조를 전달하여 사전 컴파일
            │
            ▼
3. [매개변수 바인딩] DB 드라이버가 물음표(`?`) 위치에 입력값 `' OR '1'='1`을 순수 문자열(Data)로 안전하게 바인딩
            │
            ▼
4. [DBMS 실행] DB 쿼리 파서가 재파싱을 수행하지 않고, `id` 컬럼 값이 정확히 `' OR '1'='1`인 행을 단순 조회 ➔ [불일치로 인증 실패]
            │
            ▼
5. [결과 반환 및 에러 은닉] 데이터가 없으므로 "로그인 실패" 정상 응답 반환 (내부 SQL 에러 메시지 노출 0%)
```

**동작 원리**

1. **실행 계획 고정**: 쿼리의 토큰화(Tokenizing)와 구문 분석(Parsing)이 입력값 전달 전에 이미 완결
2. **문맥 오염 차단**: 입력값에 포함된 싱글 쿼트(`'`)나 주석자(`--`)가 SQL 문법 연산자로 동작 불가
3. **타입 안전성 보장**: 정수형 매개변수(`setInt`)는 숫자가 아닌 문자열 유입 시 컴파일/런타임 에러 발생
4. **횡적 확산 방지**: 애플리케이션 계정이 탈취되더라도 타 데이터베이스나 마스터 권한 침해 방지
5. **정보 수집 차단**: 에러 기반 블라인드 인젝션의 단서가 되는 데이터베이스 에러 로그 노출 봉쇄

#### 한줄 요약
- 쿼리 사전 컴파일, 매개변수 바인딩, 리터럴 데이터 조회, 안전한 실패 응답, 에러 은닉 순으로 동작한다.

## Ⅴ. 종류 및 비교

<details><summary>용어 설명</summary>

- **SQL 인젝션 3대 공격 기법 비교**: In-Band(직접 출력), Inferential/Blind(간접 추론), Out-of-Band(외부 채널)의 비교.

</details>

| 비교 항목 | 인밴드 SQL 인젝션 (In-Band SQLi) | 블라인드 SQL 인젝션 (Blind SQLi) | 아웃오브밴드 SQL 인젝션 (OOB SQLi) |
|:---|:---|:---|:---|
| **데이터 탈취 경로** | **동일 웹 요청/응답 화면 (직접 노출)** | **참/거짓 응답 차이 또는 서버 응답 시간 지연**| **DNS 쿼리, HTTP 요청 등 외부 네트워크 채널** |
| **주요 세부 기법** | **UNION 기반 질의, 에러 기반(Error-based)**| **Boolean-based Blind, Time-based Blind** | **`xp_dirtree`(MSSQL), `UTL_HTTP`(Oracle)**|
| **공격 수행 속도** | **매우 빠름 (수 초 내 대량 데이터 탈취)** | 느림 (이진 검색으로 한 글자씩 비트 추론) | 빠름~보통 (대역폭 및 외부 통신 허용 여부 좌우)|
| **화면 출력 차단 시** | 공격 성립 불가 | **화면 출력이 차단되어도 100% 데이터 탈취 가능**| 화면 출력이 차단되어도 외부 채널로 유출 가능 |
| **핵심 네트워크 방어** | WAF 입력값 필터링 및 시큐어 코딩 | 시큐어 코딩 및 WAF 비정상 질의 탐지 | **DB 서버의 아웃바운드(Egress) 인터넷 통신 차단**|

#### 한줄 요약
- In-Band는 화면 직접 노출, Blind는 참/거짓 및 시간차 추론, OOB는 외부 DNS/HTTP 채널 악용이다.

## Ⅵ. 실무 고려사항 및 대책

<details><summary>용어 설명</summary>

- **ORM(Object-Relational Mapping)의 SQLi 취약점**: JPA, Hibernate, MyBatis 등 현대 ORM 프레임워크를 사용하더라도, 개발자가 `createQuery("... " + input)`와 같이 네이티브 SQL을 문자열로 결합하거나 MyBatis의 `${param}`(치환)을 남용하면 SQL 인젝션이 그대로 발생하는 취약점 (반드시 `#{param}` 바인딩 사용 필수).

</details>

| 문제 | 대책 | 효과 |
|:---|:---|:---|
| WAF 블랙리스트 필터링에만 의존하다 **난독화/인코딩 우회 SQL 인젝션 공격에 의해 DB 전체가 유출** | **모든 SQL 쿼리에 PreparedStatement 매개변수화 바인딩 의무화 (MyBatis `#{}` 강제)** | 구문-데이터 물리적 분리를 통해 인코딩 우회 공격 100% 원천 차단 |
| `ORDER BY` 및 테이블명 등 바인딩 불가 영역에 **사용자 입력을 동적 결합하여 발생하는 2차 인젝션** | **동적 식별자에 대한 정적 화이트리스트(Allowlist) 매핑 및 문자열 유효성 엄격 검증** | PreparedStatement 바인딩 한계 영역의 우회 인젝션 공격 100% 방어 |
| SQL 인젝션 공격에 뚫렸을 때 웹 서버 계정이 **`sa` 관리자 권한을 보유하여 전사 DB가 일괄 삭제** | **DB 계정의 최소 권한(Least Privilege) 원칙 적용, DDL 박탈 및 DB 서버 아웃바운드 차단** | 침해 발생 시에도 타 테이블 확산 및 OOB 데이터 유출 피해 99% 차단 |

#### 한줄 요약
- PreparedStatement로 구문을 분리하고, 화이트리스트로 동적 영역을 보호하며, 최소 권한으로 피해를 격리한다.

## Ⅶ. 결론

- 웹 애플리케이션과 백엔드 데이터베이스 간의 신뢰 경계를 수호하는 **SQL 인젝션 방어 아키텍처**는 데이터 무결성과 기밀성 보호의 최우선 핵심 과제이며, 실무 구현 시 **PreparedStatement 및 ORM `#{}` 매개변수화 쿼리 전면 도입**, **바인딩 불가 영역에 대한 정적 화이트리스트(Allowlist) 검증**, **DB 계정의 최소 권한(Least Privilege) 격리**, **상세 DB 에러 메시지 은닉 및 아웃바운드 차단**을 결합하여 무결점 데이터베이스 보호 환경을 완성

#### 한줄 요약
- PreparedStatement 매개변수 바인딩과 화이트리스트 검증 및 최소 권한 계정을 통해 SQL 인젝션을 완벽히 무력화한다.
