## Ⅰ. 개요

<details><summary>용어 설명</summary>

- **SQL 인젝션 (SQL Injection)**: 해커가 로그인 창에 아이디 대신 데이터베이스 파괴 명령(SQL 구문)을 욱여넣어서, 백엔드 DB를 내 맘대로 조종하는 치명적인 웹 해킹 공격이다.

</details>

- 정의: 클라이언트의 조작된 비신뢰 입력값이 백엔드 DB의 쿼리 구문 해석기로 인입되어, 쿼리의 원래 구조와 의미를 무단으로 변조하는 주입 공격이다.
- 배경: 입력값(Data)과 명령어(Code)가 물리적으로 철저히 분리되지 않고 단순히 문자열로 결합(+ 연산자 등)되면, 해커의 조작된 입력값이 진짜 명령어로 오인되어 실행되기 때문이다.

#### 한줄 요약

- 해커가 넣은 텍스트가 단순한 '데이터'가 아니라 '실행 명령어'로 둔갑해서 DB를 털어먹는 공격이다.

## Ⅱ. 특징

<details><summary>용어 설명</summary>

- **준비된 질의 (PreparedStatement)**: DB한테 "내가 앞으로 보낼 명령어 구조는 이거야" 하고 사전에 틀을 못 박아두는 기술이다.
- **값 바인딩 (Parameter Binding)**: 해커가 `DROP TABLE`을 입력해도, 명령어가 아니라 단순한 '문자열 쓰레기 데이터'로 취급하도록 파라미터 변수에 묶어버리는 방어법이다.

</details>

- **구문-데이터 붕괴**: 동적 문자열 연결 시 쿼리 구문 해석 문맥을 상실하여, 해커가 의도한 권한 오용을 유발한다.
- **입력 구조 분리**: 준비된 질의(PreparedStatement)와 값 바인딩(Binding)을 적용하여, 해커의 외부 입력을 무조건 단순 데이터로만 처리한다.
- **다양한 추론 기법**: 인밴드(In-band), 오류 기반(Error), 시간차 기반(Time-based Blind) 등 다양한 우회 추론 기법으로 데이터를 끈질기게 탈취한다.

#### 한줄 요약

- 해커가 뭔 짓을 해도 입력값이 명령어로 작동하지 않도록, 구조(PreparedStatement)와 값(Binding)을 쪼개는 게 핵심이다.

## Ⅲ. 구조 및 구성요소

<details><summary>용어 설명</summary>

- **최소 권한 DB 계정 (Least Privilege Account)**: 웹 서버가 DB에 붙을 때 전지전능한 'sa(최고 관리자)' 계정 말고, 딱 해당 서비스 테이블만 읽을 수 있는 쫄따구 권한 계정만 열어주는 방어법이다.
- **허용목록 (Allowlist)**: 파라미터 바인딩이 안 먹히는 정렬(ORDER BY) 같은 곳엔, 우리가 미리 정해둔 목록(1: 이름순, 2: 날짜순) 외의 입력은 무조건 쳐내는 화이트리스트 검증이다.

</details>

```text
[ SQL 인젝션 철저한 방어 아키텍처 ]

[ 1. 비신뢰 입력 ] ── ("해커가 로그인 창에 'OR 1=1-- 입력함")
      │
      ▼
[ 2. 질의 구조 분리 ] ── ("준비된 질의(PreparedStatement)로 명령어 틀(구조)을 굳힘")
      │
      ▼
[ 3. DB 드라이버 바인딩 ] ── ("해커 입력값을 구문 파싱 없이 단순 문자열(Data)로 바인딩함")
      │
      ▼
[ 4. DB 계정 실행 통제 ] ── ("쫄따구 계정(최소 권한)으로 실행해서 다른 핵심 테이블은 못 봄")
      │
      ▼
[ 5. 오류 통제 및 감사 ] ── ("에러 났다고 친절하게 DB 구조나 테이블명을 화면에 안 보여줌")
```

| 구성요소 | 직관적 비교 책임 | 비고 |
|:---|:---|:---|
| **비신뢰 입력** | 폼, API, HTTP 쿠키 등 **외부에서 들어오는 모든 데이터는 의심함** | Input |
| **질의 구조 사전 생성** | 입력값과 **명령어(Code)가 해석될 쿼리 구조를 사전에 분리함** | Pre-compile |
| **DB 값 바인딩** | 바인딩을 통해 해커의 조작된 입력을 **명령어가 아닌 데이터로 치환함** | Binding |
| **최소 권한 DB 계정** | 만약 뚫려도 DB 전체가 안 날아가게 **딱 필요한 쫄따구 권한만 줌** | Privilege |
| **오류 노출 통제** | 시스템 에러 메시지(테이블명 등)를 **해커에게 절대 친절하게 안 알려줌** | Error |

#### 한줄 요약

- 문자열 더하기 코딩을 금지하고 바인딩(틀)을 강제하며, 뚫려도 덜 다치게 최소 권한만 부여한다.

## Ⅳ. 흐름도

<details><summary>용어 설명</summary>

- (상단 참조)

</details>

```text
[ 시큐어 코딩 기반 SQL 실행 흐름 ]

┌──────────────────────────────┐
│ 1. [명령어 구조 사전 생성 (Pre-compile)]
│ ("SELECT * FROM users WHERE id = ? <- 물음표 자리에만 데이터 들어가게 못 박음!")
└──────────────┬───────────────┘
               ▼
┌──────────────────────────────┐
│ 2. [해커 입력값 바인딩 (Parameter Binding)]
│ ("물음표 자리에 해커가 입력한 'OR 1=1'을 쿼리 구문이 아닌 단순 문자열로 묶어버림!")
└──────────────┬───────────────┘
               ▼
┌──────────────────────────────┐
│ 3. [SQL 쿼리 컴파일 및 처리]
│ ("DB 엔진이 '아이디가 OR 1=1인 사람 찾아'라고 해석해서 아무것도 못 찾음!")
└──────────────┬───────────────┘
               ▼
    ┌──────────────────────────────┐
    │ 4. [최소 권한 DB 계정 실행]
    │ ("해커가 어떻게든 DROP TABLE 치려고 해도, 웹 서버 계정엔 삭제 권한이 없어서 컷!")
    └──────────────┬───────────────┘
                   ▼
    ┌──────────────────────────────┐
    │ 5. [질의 감사 및 에러 메시지 은닉]
    │ ("에러 나더라도 '서버 오류입니다'만 띄우고, DB 종류나 내부 버전 정보는 숨김!")
    └──────────────────────────────┘
```

### 동작 원리

1. 구조 사전 생성: DB에서 SQL 실행계획 및 쿼리 아키텍처(구조)를 사전에 컴파일함.
2. 입력값 바인딩: 외부 입력값을 명령어 구문이 아닌 안전한 매개변수(Parameter)로 전달함.
3. 쿼리 컴파일/처리: 동적 구문 재파싱(문자열 해석) 없이, 고정된 구조 안에서 데이터값만 매치함.
4. 최소 권한 질의 실행: 해당 애플리케이션 전용으로 발급된 최소 권한 계정(Least Privilege)으로 쿼리 집행함.
5. 에러 통제/감사: 상세 시스템 오류(스택 트레이스) 노출 방지 및 이상 질의 로그를 보존함.

#### 한줄 요약

- 물음표(?)로 빈칸을 뚫어두고, 해커가 무슨 짓을 하든 빈칸 안의 텍스트 조각으로만 취급해서 씹어버린다.

## Ⅴ. 종류 및 비교

<details><summary>용어 설명</summary>

- **인밴드 (In-band)**: 해킹한 데이터가 웹사이트 화면(게시판 등)에 그대로 노출되는 가장 고전적인 초보 형태.
- **블라인드 (Blind)**: 화면엔 힌트가 1도 없지만, 로그인 성공/실패 여부(True/False)나 서버 응답 시간 지연(Sleep)을 관찰하며 스무고개 하듯 한 글자씩 팩트를 털어가는 지독한 놈.
- **아웃오브밴드 (Out-of-band, OOB)**: 방화벽이 결과를 막고 있으면, 아예 DB 서버 자체에서 해커 서버로 몰래 DNS 신호를 쏴서 데이터를 빼돌리는 우회 기법.

</details>

| SQL 인젝션 유형 | **인밴드 (In-band SQLi)** | **블라인드 (Blind SQLi)** | **아웃오브밴드 (OOB SQLi)** |
|:---|:---|:---|:---|
| 비유 및 핵심 특징 | **해킹한 결과물이 모니터 화면에 대놓고 출력됨** | **안 보이는 방 안에서 스무고개하며 비밀번호 맞추기** | **방화벽 뚫기 힘드니, DB가 내 해킹 서버로 직접 쏘게 명령함** |
| 핵심 탐지 방식 | 유니온(UNION) 쿼리를 써서 **게시판 화면에 해킹 데이터를 그대로 노출함** | 참/거짓 응답이나 서버 딜레이 시간차(Time-based)를 관찰해 **데이터를 유추하는 기법임** | HTTP, DNS 질의 등 DB 서버가 외부망으로 직접 전송하는 **별도의 네트워크 채널 악용** |
| 장점 및 특징 | 가장 고전적이고 구현이 쉬워 **대량의 데이터를 가장 빠르게 탈취함** | 에러 메시지나 화면 출력이 완벽히 막혀있는 **철통 보안 환경에서도 기어코 뚫어냄** | 웹 응답이 막혀있어도, 아웃바운드 통신망을 통해 **데이터를 외부로 은밀히 빼돌림** |
| 한계 및 문제점 | 에러 메시지나 화면 출력을 막아버리면 **공격 자체가 성립 안 됨** | 한 글자씩 스무고개로 추론해야 하므로 **데이터 탈취 시간이 엄청 오래 걸림** | 내부망 DB 서버가 외부 인터넷과 통신할 수 없게 차단되어 있으면 **공격 불가능함** |

#### 한줄 요약

- 대놓고 빼가면(인밴드), 화면 막히면 스무고개로 빼가고(블라인드), 아예 DB가 밖으로 쏘게(OOB) 만드는 놈들이다.

## Ⅵ. 실무 고려사항 및 대책

<details><summary>용어 설명</summary>

- **MITRE CWE-89**: 전 세계 모든 취약점 바이블에서 "SQL 인젝션은 이렇게 생겼으니 막아라" 하고 정해둔 가이드다.
- **허용목록 (Allowlist)**: 파라미터 바인딩이 안 먹히는 정렬(ORDER BY) 같은 곳엔, 우리가 미리 정해둔 목록(1: 이름순, 2: 날짜순) 외의 입력은 무조건 쳐내는 화이트리스트 검증이다.

</details>

| 장애/위험 요소 | 원인 분석 | 실무 대책 및 해결방안 | 기대 효과 |
|:---|:---|:---|:---|
| 입력값 빡세게 필터링했는데도 **신종 인젝션 기법에 DB가 다 털림** | WAF나 정규식 필터링(블랙리스트) 땜빵만 믿고, 근본적인 쿼리 구조/데이터 분리를 안 함 | **MITRE CWE-89** 준수하여 동적 문자열 쿼리 조합 금지 및 무조건 **PreparedStatement 의무화** | 해커가 무슨 짓을 해도 명령어가 아닌 데이터로 치환되어, 구문 변조 해킹 원천 차단 |
| 바인딩이 안 되는 정렬(ORDER BY) 구문에 **인젝션 갈겨서 데이터 유출됨** | PreparedStatement 지원이 불가능한 동적 테이블명/컬럼명에 사용자 입력을 무지성 허용함 | 바인딩 불가 영역은 사용자 입력을 배제하고, 서버 측 코드가 지정한 **허용목록(Allowlist) 검증 강제** | 개발 프레임워크의 바인딩 한계를 노린 지능적인 우회 인젝션 공격 원천 방어 |
| 인젝션 한 번 당했다고 **회사 DB 전체가 DROP 당해서 폐업함** | 웹 서버가 DB에 접속할 때, 편하다고 'sa(최고 권한)' 공용 계정을 써서 무제한 권한을 부여함 | 각 웹 애플리케이션 목적에 맞는 **최소 권한 DB 계정(Least Privilege)** 발급 및 민감 프로시저 통제 | 인젝션에 뚫리더라도, 해커가 해당 테이블 밖으로 나가지 못하게 폭발 피해 최소화 |

#### 한줄 요약

- 문자열 더하기는 절대 금지(바인딩 필수), 바인딩 안 되면 허용목록만 받고, 뚫릴 거 대비해 DB 권한은 최소로 줘라.

## Ⅶ. 결론

<details><summary>용어 설명</summary>

- **인젝션 방어 원칙 (Injection Defense Principle)**: 단순 문자 필터링(WAF)이라는 땜빵에 의존하지 않고, 구조적 분리를 통해 해커의 코드를 쓰레기 데이터로 치환해버리는 시큐어 코딩 원칙.

</details>

- SQL 인젝션 방어는 단순 필터링(WAF)이 아닌 구조적 원인 해결이 핵심이므로, 사용자 값 입력에는 무조건 **준비된 질의(PreparedStatement)**, 동적 인자에는 **허용목록(Allowlist)** 검증을 적용하고, 만약의 사태에 대비해 **최소 권한 DB 계정**과 **오류 메시지 통제**를 다중 적용하는 실무 기조를 확립함

#### 한줄 요약

- 입력값은 **준비된 질의**, 동적 식별자는 **허용목록**, 만약을 위해 **최소 권한 DB 계정**을 박아라.
