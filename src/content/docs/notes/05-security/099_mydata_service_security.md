## Ⅰ. 개요

<details><summary>용어 설명</summary>

- **마이데이터 서비스 보안(MyData Service Security / FAPI 2.0 & RFC 9700)**: 정보주체의 동의에 기반하여 금융, 공공, 의료 등 이종 산업 간 개인정보를 전송·수신·활용하는 마이데이터 생태계에서, 정보주체의 동의 범위(Consent), OAuth 2.0 인가 토큰(Token Scope), 실제 API 응답 데이터 필드(Response Field)를 1:1로 결속하고 mTLS 및 DPoP 암호화 터널을 통해 토큰 탈취, 중간자 변조(MITM), 재생 공격(Replay Attack)을 원천 방어하는 서비스 전주기 보안 아키텍처.
- **베어러 토큰 탈취 및 재생 공격 결함(Bearer Token Theft & Replay Defect)**: 발급된 OAuth 2.0 Access Token에 클라이언트의 암호학적 신원 바인딩(Sender-Constrained Binding)이 적용되지 않은 일반 베어러(Bearer) 토큰을 사용할 경우, 네트워크 스니핑이나 로그 탈취를 통해 토큰을 획득한 공격자가 정상 핀테크 앱으로 위장하여 금융사 API 서버에 대량의 무단 데이터 조회를 실행할 수 있는 구조적 취약점.

</details>

- 정의/개념: 동의 범위와 API 전송을 결속하는 **마이데이터 서비스 보안**
- 배경/필요성: 금융, 공공, 의료 등 이종 산업 간 실시간 API로 개인정보가 유통되는 마이데이터 환경에서, 기존의 일반 베어러 토큰(Bearer Token)은 네트워크 스니핑이나 로그 유출 시 공격자가 토큰을 재사용(Replay Attack)하여 대량의 민감 정보를 무단 탈취할 수 있고, 리소스 서버의 무분별한 쿼리로 동의 범위를 초과하는 과잉 데이터가 전송되는 결함이 존재함에 따라, FAPI 2.0(Financial-grade API) 및 RFC 9700(OAuth 2.0 Security BCP) 표준에 기반하여 DPoP(RFC 9449) 송신자 지문 결속, mTLS 1.3 상호 인증 터널, JWS 요청 서명, 동의-토큰-응답필드 3각 결속(Consent-Token-Field Binding)을 결합하는 마이데이터 서비스 보안 아키텍처를 도입하여 **토큰 탈취 재사용 원천 무효화, 데이터 최소화 원칙 실시간 집행 및 철회 시 파생 데이터 연쇄 소멸**을 달성할 필요

#### 한줄 요약
- FAPI 2.0 및 DPoP 기반 송신자 결속 토큰과 mTLS 상호 인증을 통해 마이데이터 API 전송을 보호한다.

## Ⅱ. 특징

<details><summary>용어 설명</summary>

- **DPoP (Demonstrating Proof-of-Possession at the Application Layer / RFC 9449)**: 클라이언트가 공개키/개인키 쌍을 생성하고, API 요청 시 개인키로 서명한 DPoP Proof 헤더를 첨부하여, 토큰 문자열이 유출되더라도 개인키를 갖지 않은 제3자가 토큰을 재사용하지 못하도록 강제하는 애플리케이션 계층 송신자 결속(Sender-Constrained) 기술.
- **동의-토큰-응답필드 3각 결속 (Consent-Token-Field Binding)**: 사용자가 UI에서 동의한 항목(Consent Scope), 인가 서버가 발급한 토큰의 권한 범위(Token Scope), 리소스 서버가 반환하는 JSON 응답 데이터 필드(Payload Field)가 완벽히 일치하도록 런타임에 강제하는 데이터 최소화 통제.

</details>

- **송신자 지문 결속 토큰 (Sender-Constrained Token)**: 베어러 토큰의 취약점을 제거하기 위해 DPoP 또는 mTLS Certificate Binding을 적용하여 탈취된 토큰의 비인가 재사용 원천 차단
- **기관 간 상호 PKI 인증 및 요청 서명**: 통신 양단 서버가 mTLS 1.3으로 신원을 상호 검증하고, JSON Web Signature(JWS)를 통해 요청 파라미터의 중간 위변조 방어
- **철회 시 파생 데이터 연쇄 소멸 거버넌스**: 정보주체가 동의를 철회할 경우 신규 API 전송 중단뿐만 아니라 수신 측에 기저장된 원본 및 2차 가공 파생 데이터의 활용 근거를 소급 재판정하여 폐기 유도

#### 한줄 요약
- DPoP 송신자 결속 토큰, mTLS 및 JWS 요청 서명, 동의-토큰-필드 3각 결속, 철회 시 파생 데이터 폐기를 제공한다.

## Ⅲ. 구조 및 구성요소

<details><summary>용어 설명</summary>

- **마이데이터 보안 4대 핵심 컴포넌트**:
  1. **Consent Management Hub**: 4대 동의 항목(목적, 항목, 수신자, 기간) 수명주기 관리 포털.
  2. **OAuth 2.0 / FAPI Authorization Server**: DPoP 송신자 결속 토큰 발급 엔진.
  3. **Mutual TLS & JWS Secure API Gateway**: 상호 인증 터널 및 요청 무결성 검증기.
  4. **Data Minimization & Policy Enforcement Point (PEP)**: 3각 결속 대조 및 응답 필드 마스킹기.

</details>

```text
[마이데이터 서비스 전송 보안 체계]
├─ 동의 관리 및 인가 계층 (Consent Hub)
│  ├─ 4대 동의 항목 수명주기 관리
│  └─ FAPI 2.0 및 DPoP 송신자 결속 토큰 발급
├─ 적격 수신자 요청 계층 (Recipient Client)
│  ├─ 클라이언트 개인키 서명 (DPoP Proof)
│  └─ JWS 요청 본문 서명 및 Nonce 장착
└─ 정보전송자 리소스 계층 (Sender PEP)
   ├─ mTLS 1.3 상호 인증 및 인증서 검증
   ├─ DPoP 서명 대조 (토큰 탈취 재사용 차단)
   ├─ 동의-토큰-필드 3각 결속 (과잉 필드 차단)
   └─ 안전 응답 전송 및 전송 이력 불변 로깅
```

- 선의 의미: 계층 구조 및 상하위 포함 관계를 나타낸다.

| 구성요소 | 책임 |
|:---|:---|
| 동의 관리 허브 (Consent Hub) | 전송 목적, 항목, 수신자, 유효기간 관리 및 실시간 철회(Revocation) 이벤트 전파 |
| FAPI 인가 서버 | RFC 9700/BCP 240 준수, DPoP 키 바인딩 및 최소 권한 스코프(Scoped Token) 발급 |
| mTLS API 게이트웨이 | 클라이언트와 서버 간 PKI 상호 인증 및 전송 구간 TLS 1.3 암호화 터널 유지 |
| JWS 서명 검증기 | 요청 본문의 변조 방지를 위해 비대칭 전자서명 및 재전송 방어용 Nonce 검증 |
| 정책 집행점 (PEP) | 동의 스코프와 응답 필드를 1:1 대조하여 미동의 개인정보 필드 유출 원천 필터링 |

#### 한줄 요약
- 동의 관리 허브, FAPI 인가 서버, mTLS API 게이트웨이, JWS 서명 검증기, 정책 집행점(PEP)이 결합한다.

## Ⅳ. 흐름도

<details><summary>용어 설명</summary>

- **마이데이터 보안 API 트랜잭션 5단계 시퀀스**:
  1. 정보주체의 핀셋 동의 및 DPoP 토큰 발급
  2. 핀테크사의 mTLS 터널 수립 및 JWS 서명 요청 생성
  3. 리소스 서버의 mTLS, DPoP 서명 및 Nonce 무결성 검증
  4. 동의-토큰-응답필드 3각 대조 및 최소 데이터 응답 펌핑
  5. 동의 철회 이벤트 수신 시 파생 데이터 폐기 및 감사 로깅

</details>

```text
1. [동의 및 DPoP 토큰 발급] 고객이 핀테크 앱에서 카드 청구 내역 동의 ➔ 인가 서버가 DPoP 키 결속 토큰 발급
            │
            ▼
2. [보안 API 요청 패킷 생성]
    ├─ 핀테크사가 개인키로 `DPoP: <JWT>` 헤더 생성 및 요청 바디에 `JWS` 전자서명 첨부
    └─ 재사용 공격 방어를 위한 일회성 넌스(Nonce) 및 타임스탬프 결속
            │
            ▼
3. [mTLS 및 토큰 무결성 검증]
    ├─ 카드사 게이트웨이가 핀테크사의 mTLS X.509 인증서 상호 검증
    └─ [DPoP 서명 대조: 요청자의 공개키와 토큰 내 바인딩 키 일치 확인 ➔ 토큰 탈취 재사용 차단]
            │
            ▼
4. [동의-토큰-필드 3각 검증 및 응답]
    ├─ 카드사 PEP가 토큰 스코프와 고객 원본 동의 내역 1:1 대조
    └─ [동의 항목(카드 청구 금액)만 JSON으로 전송하고 미동의 항목(가맹점 상세 주소)은 컬럼 마스킹]
            │
            ▼ (고객이 마이데이터 서비스 탈퇴 및 전송 동의 철회 시)
5. [철회 웹훅 수신 및 파생본 폐기]
    ├─ 카드사가 토큰을 즉시 무효화(Revoke)하여 추가 전송 차단
    └─ [핀테크사는 기저장된 원본 및 2차 가공 파생 프로파일 데이터 영구 파기 집행 및 감사 로깅]
```

**동작 원리**

1. **동의 및 DPoP 토큰 발급**
2. **보안 API 요청 패킷 생성**
3. **mTLS 및 토큰 무결성 검증**
4. **동의-토큰-필드 3각 검증 및 응답**
5. **철회 웹훅 수신 및 파생본 폐기**

#### 한줄 요약
- 요청마다 서명과 검증을 더하는 만큼 지연과 키 관리 부담이 늘지만, 그 대가로 탈취된 토큰이 다른 단말에서 재사용될 경로 자체가 사라진다.

## Ⅴ. 종류 및 비교

<details><summary>용어 설명</summary>

- **마이데이터 API 보안 3단계 생애주기 비교**: 동의 및 인가 단계(Consent & Auth), API 통신 전송 단계(Transport), 수신 보관 및 철회 단계(Storage & Revocation)의 비교.

</details>

| 생애주기 단계 | 핵심 보안 위협 | 표준 방어 아키텍처 및 무기 | 법적 근거 및 표준 |
|:---|:---|:---|:---|
| **1. 동의 및 인가 단계** | 과도한 권한 위임, 사용자 사칭 | **동의 관리 허브, DPoP 결속 최소 스코프 토큰** | **RFC 9700, BCP 240** |
| **2. API 통신 전송 단계**| 중간자 도청, 토큰 재사용, 패킷 변조| **mTLS 1.3 상호 인증, JWS 본문 서명, Nonce** | **FAPI 2.0 Profile** |
| **3. 수신 보관 및 철회** | 목적 외 불법 활용, 철회 후 좀비 보관| **동의-토큰-필드 3각 결속, 파생본 연쇄 파기** | **PIPA 제35조의2** |

#### 한줄 요약
- 1단계는 DPoP 최소 토큰 발급, 2단계는 mTLS/JWS 통신 보안, 3단계는 3각 결속 및 철회 시 파생본 파기이다.

## Ⅵ. 실무 고려사항 및 대책

<details><summary>용어 설명</summary>

- **FAPI 2.0 (Financial-grade API 2.0) & RFC 9700 (OAuth 2.0 Security BCP)**: 고보안 금융·마이데이터 트랜잭션을 위한 상호 TLS(mTLS), DPoP, PKCE, JWS 요청 서명 기술 표준 규격.

</details>

| 문제 | 대책 | 효과 |
|:---|:---|:---|
| 마이데이터 리소스 서버에서 `SELECT *` 쿼리를 사용하여 **정보주체가 동의하지 않은 민감 금융 필드까지 핀테크사로 과다 전송되는 유출 사고** | **개인정보보호법 제35조의2** 준수, **동의-토큰-응답필드 3각 결속 엔진을 PEP에 탑재하여 미동의 컬럼 실시간 인라인 마스킹** | 비동의 잉여 정보 유출 100% 원천 차단 및 데이터 최소화 원칙 완벽 준수 |
| 공격자가 네트워크 패킷 스니핑으로 탈취한 OAuth 2.0 토큰을 재사용하여 **금융사 API 서버로부터 수만 명의 개인정보를 무단 다운로드하는 침해** | **IETF RFC 9700 및 FAPI 2.0** 표준 준수, **DPoP 기반 송신자 결속(Sender-Constrained) 토큰 및 1회용 Nonce 강제** | 탈취된 토큰의 비인가 재사용(Replay Attack) 100% 무효화 및 API 사칭 차단 |
| 정보주체가 마이데이터 전송 동의를 철회했으나 수신 기관이 **과거 원본 데이터로 생성한 2차 가공 파생 데이터를 지속 활용하는 위법 분쟁** | **실시간 철회 웹훅(Webhook) 연동 및 2차 파생 데이터 보유 근거 소급 재판정·완전 삭제 파이프라인 가동** | 철회권의 실효적 보장 및 미인가 파생 데이터 잔존 리스크 100% 해소 |

#### 한줄 요약
- 3각 결속으로 과다 전송을 막고, DPoP/Nonce로 토큰 탈취를 차단하며, 실시간 웹훅으로 파생 데이터를 연쇄 폐기한다.

## Ⅶ. 결론

- 초연결 API를 통해 대규모 금융·공공 마이데이터가 실시간 유통되는 환경에서 토큰 탈취와 무단 과다 전송을 방어하는 **글로벌 금융 수준 API 보안 및 인가 통제(FAPI 2.0 / RFC 9700 / DPoP)의 최상위 기술 표준 체계**로 확고히 자리 잡았으며, 제로 트러스트 API 게이트웨이 및 기밀 컴퓨팅 기반 데이터 처리로 전면 진화하는 가운데, 실무 마이데이터 서비스 구축 시에는 **OAuth 2.0 베어러 토큰 전면 폐지 및 DPoP 기반 송신자 결속(Sender-Constrained) 토큰 의무화, 전송 전구간 mTLS 1.3 상호 인증 및 JWS 요청 서명 검증, 리소스 서버 정책 집행점(PEP)에서의 동의-토큰-응답필드 3각 결속 인라인 마스킹, 전송 철회 시 파생 데이터 자동 삭제 웹훅 파이프라인**을 결합하여 완벽한 마이데이터 API 전주기 보안 무결성을 완성

#### 한줄 요약
- FAPI 2.0과 DPoP 송신자 결속 토큰 및 3각 결속 통제를 통해 안전하고 신뢰할 수 있는 마이데이터 API 보안을 완성한다.
