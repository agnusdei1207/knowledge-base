## Ⅰ. 개요

<details><summary>용어 설명</summary>

- **SAML 2.0 (보안 주장 마크업 언어 2.0)**: 회사 A(본사)와 회사 B(자회사)처럼 완전히 남남인 도메인끼리, "이 직원 우리 회사 사람 맞으니까 로그인시켜줘" 하고 XML 증명서를 주고받는 고전적인 기업 연합 로그인(SSO) 표준이다.
- **XML**: "이름: 홍길동, 부서: 영업팀" 같은 정보를 태그(`<name>`)로 묶고 그 위에 위조 방지용 전자서명을 덮어씌우는, SAML의 핵심 데이터 포맷이다.

</details>

- 정의: 이종 도메인 간 사용자 인증(Authentication) 및 인가(Authorization) 데이터를 XML 기반 보안 주장(Assertion)으로 교환하는 연합 인증 표준이다.
- 배경: 서비스마다 각자 아이디/비번을 따로 만들면, 퇴사자 관리가 안 되고 직원들이 비밀번호를 포스트잇에 적어두다 털리기 때문이다.

#### 한줄 요약

- 직원들이 사이트마다 비번 외울 필요 없이, 본사 서버가 보증서(XML 서명) 하나 끊어주면 자회사들까지 싹 로그인되는 기술이다.

## Ⅱ. 특징

<details><summary>용어 설명</summary>

- **Assertion (보안 주장)**: IdP(본사 서버)가 "내가 얘 신분증 확인했음!" 하고 도장 쾅 찍어서 SP(자회사 서버)한테 보내주는 위조 불가능한 보증서다.
- **재전송 공격 (Replay Attack)**: 해커가 남이 정상적으로 로그인할 때 쓰던 Assertion(보증서)을 몰래 복사해뒀다가, 나중에 그대로 다시 서버에 던져서 로그인(세션 탈취)하는 얍삽한 해킹이다.

</details>

- **신뢰 관계 사전 형성**: IdP(인증 제공자)와 SP(서비스 제공자) 간에 메타데이터(Metadata)와 공개키를 사전 교환하여, 서로만 믿고 대화하는 철통같은 상호 신뢰를 형성한다.
- **무결성 보장**: XML 서명(XML Signature) 기술을 적용하여, 중간에 해커가 직급(사원 $\to$ 사장)이나 부서를 무단 조작하지 못하게 Assertion 무결성을 보장한다.
- **재전송 공격 차단**: InResponseTo(요청 ID)와 Recipient(수신 주소), 유효 시간(NotOnOrAfter)을 SP에서 깐깐하게 검증하여 보증서 재사용(Replay) 공격을 원천 차단한다.

#### 한줄 요약

- 서로 키(인증서) 나눠 갖고, 위조 못 하게 XML에 서명 빡세게 걸고, 한 번 쓴 보증서는 두 번 다시 못 쓰게 막는다.

## Ⅲ. 구조 및 구성요소

<details><summary>용어 설명</summary>

- **IdP (신원 제공자)**: 본사 통합 인증 서버다. 사원증(비번) 검사하고 Assertion 보증서를 찍어내는 공장이다.
- **SP (서비스 제공자)**: 자회사 업무 웹사이트다. IdP가 던져준 보증서를 보고 "어 우리 본사 도장 맞네" 하면 자기네 서비스를 열어주는 놈이다.
- **로컬 세션 (Local Session)**: SP가 SAML 보증서 검사를 끝내고, "ㅇㅋ 통과" 한 뒤에 자기네 서비스 전용 로그인 세션(쿠키)을 구워주는 마지막 단계다.

</details>

```text
[ SAML 2.0 연합 인증 아키텍처 ]

[ 1. 사용자 브라우저 ] ── ("자회사(SP) 접속했더니, 본사(IdP) 로그인 창으로 튕겨줌")
      │
      ▼
[ 2. IdP (인증 서버) ] ── ("본사 사번으로 로그인 성공! 보증서(Assertion) 만들고 서명함")
      │
      ▼
[ 3. SAML Assertion (보증서) ] ── ("이름, 부서 정보가 담긴 위조 불가능한 XML 문서를 전달함")
      │
      ▼
[ 4. SP (서비스 서버) ] ── ("보증서 도장(서명) 확인하고, 내 주소로 온 거 맞는지 체크함")
      │
      ▼
[ 5. 로컬 세션 생성 ] ── ("검증 통과했으니 자회사 서비스 쓸 수 있게 세션을 구워줌")
```

| 구성요소 | 직관적 비교 책임 | 비고 |
|:---|:---|:---|
| **사용자 브라우저** | SP와 IdP 사이를 왔다 갔다 하면서 **SAML 요청서와 보증서를 배달하는 중계기 역할을 함** | Browser |
| **IdP (신원 제공자)** | 사용자가 찐인지 확인하고 **속성(이름/직급)을 담아 XML 서명을 발급함** | IdP |
| **SAML Assertion** | 절대 조작이 불가능하도록 서명(Signature)이 걸린 **사용자 신분 및 인증 보증서(XML)임** | Assertion |
| **SP (서비스 제공자)** | 보증서의 서명 무결성, 수신자(Recipient), 유효시간을 **서버단에서 깐깐하게 검증함** | SP |
| **메타데이터/검증 체계** | 사전에 맺어둔 신뢰 관계(공개키 교환)를 통해 **보증서 위조 여부를 철저히 걸러냄** | Metadata |

#### 한줄 요약

- 브라우저가 배달하고 $\to$ IdP가 서명 찍고 $\to$ SP가 서명 검증하고 로컬 세션 열어주는 티키타카다.

## Ⅳ. 흐름도

<details><summary>용어 설명</summary>

- (상단 참조)

</details>

```text
[ SAML 기반 통합 로그인 처리 흐름 ]

┌──────────────────────────────┐
│ 1. [SAML AuthnRequest 생성]
│ ("SP가 '이 사람 누군지 인증 좀 해줘' 하고 요청서(ID 번호 포함)를 날림")
└──────────────┬───────────────┘
               ▼
┌──────────────────────────────┐
│ 2. [IdP 로그인 및 사용자 신원 인증]
│ ("사용자가 본사 로그인 창에서 아이디/비번 치고 인증함")
└──────────────┬───────────────┘
               ▼
┌──────────────────────────────┐
│ 3. [Assertion XML 서명 및 발급]
│ ("IdP가 '인증 통과!'라는 보증서(Assertion)에 도장 찍어서 발송함")
└──────────────┬───────────────┘
               ▼
┌──────────────────────────────┐
│ 4. [서명 / 대상(Recipient) / 요청(ID) 철저한 검증]
│ ("SP가 서명 확인하고, 자기가 보낸 요청 ID(InResponseTo)에 대한 답이 맞는지 대조함")
└──────────────┬───────────────┘
               ▼
┌──────────────────────────────┐
│ 5. [재전송(Replay) 차단 및 로컬 세션 발급]
│ ("이미 써먹은 보증서면 즉시 컷! 새 거면 정상 로그인 세션 발급!")
└──────────────────────────────┘
```

### 동작 원리

1. 요청서 생성: SP에서 사용자 인증을 요구하는 고유 요청 ID(AuthnRequest)를 생성.
2. 사용자 인증: IdP 로그인 페이지로 브라우저가 리다이렉트되어 사용자 신원을 인증.
3. Assertion 생성: IdP가 사용자 속성(NameID 등)을 담은 Assertion 문서에 XML 디지털 서명을 집행.
4. 결속 검증: SP가 사전 교환된 Metadata 공개키로 서명을 풀고, Recipient 및 InResponseTo를 1:1 철저한 검증.
5. 재전송 차단: 응답 ID 중복 여부(Replay 공격) 확인 후, 최종 승인 시 SP 로컬 세션을 발급.

#### 한줄 요약

- 요청서 쏘고 $\to$ 본사에서 로그인하고 $\to$ 보증서 받아오고 $\to$ 서명이랑 유효시간 철저한 검증해서 통과시킨다.

## Ⅴ. 종류 및 비교

<details><summary>용어 설명</summary>

- (상단 설명 참조)

</details>

| SAML 인증 시작 방식 | **SP 시작 (SP-Initiated SSO)** | **IdP 시작 (IdP-Initiated SSO)** |
|:---|:---|:---|
| 비유 및 핵심 특징 | **식당(SP)에 먼저 갔더니, 입구 컷 당하고 신분증(IdP) 떼오라고 시킴** | **주민센터(IdP)에서 신분증 묶음 들고, 곧바로 식당(SP)으로 밀고 들어감** |
| 핵심 동작 방식 | 사용자가 서비스 웹사이트(SP)에 먼저 접속하면, **SP가 '인증 요청서(AuthnRequest)'를 먼저 쏨** | 사내 포털(IdP)에서 아이콘을 클릭하면, **요청서 없이 IdP가 보증서를 SP로 바로 쏴버림** |
| 장점 및 특징 | SP가 자기가 던진 '요청 ID'랑 '응답 ID'를 1:1로 맞출 수 있어서 **재전송 공격 방어가 완벽함** | 사내 인트라넷 대시보드(포털)처럼 여러 앱을 **한 번의 클릭으로 띄울 때 매우 편리함** |
| 한계 및 문제점 | 브라우저가 SP $\to$ IdP $\to$ SP로 리다이렉션을 여러 번 쳐야 해서 **흐름이 김** | SP 입장에선 자기가 요청하지도 않은 보증서가 뜬금없이 날아온 거라 **재전송(Replay) 공격 막기가 빡셈** |

#### 한줄 요약

- 보안이 중요하면 1:1 대조가 되는 **SP 시작**, 포털 메뉴에서 앱 여러 개 띄울 땐 **IdP 시작**이 팩트다.

## Ⅵ. 실무 고려사항 및 대책

<details><summary>용어 설명</summary>

- **XML 서명 래핑 공격 (XSW)**: 해커가 XML 문서 구조를 교묘하게 꼬아서(Wrapping), 서명 검사하는 로직은 "어 정상 서명이네" 하고 속고, 실제 로그인 처리 로직은 "해커가 관리자(Admin)네!" 하고 속게 만드는 SAML 최악의 공격이다.

</details>

| 장애/위험 요소 | 원인 분석 | 실무 대책 및 해결방안 | 기대 효과 |
|:---|:---|:---|:---|
| A 회사용 보증서(Assertion)를 해커가 훔쳐서 **B 회사 시스템 로그인에 뚫어버림** | "이 보증서는 A 회사(Recipient) 전용입니다"라는 수신자 검증 로직을 SP 개발자가 빼먹음 | **OASIS SAML 2.0 Core** 지침 준수 및 SP에서 수신자(Recipient)와 대상(Audience) **대조 강제** | 가로채기(Interception) 후 다른 타겟 사이트로의 무단 보증서 재사용 공격 원천 차단 |
| 해커가 XML 구조를 꼬아서 찌르니까 **일반 계정이 관리자(Admin) 권한으로 승인됨** | SP의 파싱 로직과 서명 검증 로직이 분리된 틈을 타, 가짜 XML 노드를 끼워 넣는 서명 래핑(XSW) 공격 발생 | **W3C XML Signature 1.1** 기반 하드닝 및 XML 노드 위치(DOM)에 대한 **엄격한 스키마 철저한 검증** | 서명 검증 우회 및 위조 XML 구조 주입(XSW 래핑) 공격 구조적 무력화 |
| 해커가 어제 훔친 100% 정상 보증서를 **오늘 아침에 그대로 전송해서 로그인을 뚫음** | 이미 한 번 사용한 응답(Response ID)을 폐기하지 않고 방치하여, 재전송(Replay) 공격이 먹힘 | Assertion ID를 캐싱하여 중복을 검사하고, 유효시간(NotOnOrAfter)을 **5분 이내 단기로 설정** | 정상 보증서를 훔쳐서 재탕하는 Replay 세션 탈취 공격 원천 억제 |

#### 한줄 요약

- 수신자(Recipient) 확인 똑바로 하고, 래핑 공격(XSW) 안 당하게 파싱 빡세게 하고, 쓴 보증서는 폐기해라.

## Ⅶ. 결론

<details><summary>용어 설명</summary>

- **요청 결속 (Request-Response Binding)**: SP가 보증서를 받을 때 InResponseTo(내가 요청한 거 맞냐), Recipient(나한테 온 거 맞냐), NotOnOrAfter(시간 안 지났냐)를 1:1로 칼같이 대조하라는 핵심 보안 원칙이다.

</details>

- 기업 연합 인증의 핵심인 SAML은 강력한 보안을 위해 가급적 1:1 대조가 가능한 **SP 시작 SSO** 흐름을 채택하고, SP 측에서 InResponseTo, Recipient, NotOnOrAfter를 검증하는 철저한 **요청 결속**과 **XSW 래핑 공격 차단**을 다층 연동하는 실무 기조를 확립함

#### 한줄 요약

- 보안 빡센 **SP 시작 SSO**를 쓰고, **요청 결속(1:1 대조)** 과 **래핑 공격 방어**로 통제해라.
