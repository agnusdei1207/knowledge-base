## Ⅰ. 개요

<details><summary>용어 설명</summary>

- **SOLID 원칙(SOLID Principles)**: '클린 코드' 엉클 밥 형님이 제창한 5가지(SRP, OCP, LSP, ISP, DIP) 객체지향 십계명으로, 수정하기 쉽고 스파게티를 막아주는 설계 국룰이다.
- **유지보수성(Maintainability)**: 기획자가 갑자기 요구사항을 바꿨을 때, 개발자가 샷건 안 치고 기존 코드 손상 없이 안전하고 빠르게 기능을 붙이거나 수정할 수 있는 코드의 맷집이다.
- **결합도와 응집도(Coupling & Cohesion)**: 좋은 코드는 클래스끼리는 남남처럼 느슨하게 연결되고(Low Coupling), 클래스 내부는 끼리끼리 똘똘 뭉쳐(High Cohesion) 있어야 한다는 대원칙이다.

</details>

- 정의: 코드를 짤 때 스파게티를 막고 유지보수성과 확장성을 극대화하기 위해 반드시 지켜야 할 객체지향 5대 설계 원칙인 **SOLID Principles**
- 배경: 아무 생각 없이 깡코딩하면, 나중에 기능 하나 바꿀 때마다 **수십 개의 클래스가 연쇄 폭발하는 유지보수 지옥**이 열리기 때문

#### 한줄 요약

- 코드 짤 때 나중에 뜯어고치기 쉽게 만들기 위해 지켜야 하는 5가지 객체지향 국룰이다.

## Ⅱ. 특징

<details><summary>용어 설명</summary>

- **SRP (단일 책임 원칙)**: 클래스는 단 하나의 목적(이유)으로만 수정되어야 한다. 결제 로직에 이메일 발송 로직까지 짬뽕으로 넣지 말라는 뜻이다.
- **OCP (개방-폐쇄 원칙)**: 기존 코드는 안 고치면서(수정엔 닫힘), 새로운 기능은 인터페이스나 상속으로 쏙쏙 갖다 붙일(확장엔 열림) 수 있어야 한다는 뜻이다.
- **LSP (리스코프 치환 원칙)**: 부모 클래스 자리에 자식 클래스를 껴넣어도 프로그램이 안 뻗어야 한다. 직사각형을 상속받아 정사각형을 만들면 부모 규칙이 깨져서 망한다.
- **ISP (인터페이스 분리 원칙)**: 스마트폰 인터페이스를 전화기, 카메라 등으로 쪼개라. 전화만 거는 애한테 카메라 기능까지 강제로 물려주지 말라는 뜻이다.
- **DIP (의존성 역전 원칙)**: '아반떼' 클래스에 묶이지 말고 추상적인 '자동차' 인터페이스에 의존해라. 그래야 나중에 '소나타'로 바꿀 때 코드를 안 뜯어고친다.

</details>

- 5대 원칙(**SRP, OCP, LSP, ISP, DIP**)으로 역할과 책임을 칼같이 나눔.
- 결합도는 낮추고 응집도를 높여서(**High Cohesion, Loose Coupling**), 코드의 재사용성을 폭발시킴.
- 인터페이스와 다형성을 극한으로 활용해 변경 파급 효과를 차단함.

#### 한줄 요약

- 책임을 쪼개고, 묶이지 않게 떨어뜨려서, 고치기 쉽게 만드는 5가지 콤보 기술이다.

## Ⅲ. 구조 및 구성요소

<details><summary>용어 설명</summary>

- **다형성(Polymorphism)**: "가속해!"라고 명령하면 소나타든 테슬라든 알아서 굴러가는 것처럼, 똑같은 호출에 여러 객체가 각자의 방식대로 움직이는 OCP/DIP의 근본 마법이다.

</details>

```text
[ SOLID 원칙의 십자포화 아키텍처 방어선 ]

    [ SRP ]  ──(클래스를 잘게 찢음)──▶ 응집도 상승
       │
    [ ISP ]  ──(인터페이스를 찢음)──▶ 불필요한 의존성 제거
       │
    [ LSP ]  ──(상속 규칙 준수)───▶ 다형성 기반 마련
       │
    [ OCP ]  ──(기존 코드 보호)───▶ 확장성 열림
       │
    [ DIP ]  ──(추상화에 의존)────▶ 결합도 하락 (스프링 DI의 핵심)
```

| 원칙 | 팩트 폭행 책임 |
|:---|:---|
| **SRP (단일 책임)** | 클래스가 바뀔 이유는 딱 하나여야 함. 잡다한 로직 짬처리 금지 |
| **OCP (개방-폐쇄)** | 새 기능 추가할 때 기존 코드 뜯어고치지 말고, 껍데기(인터페이스) 늘려서 붙여라 |
| **LSP (리스코프 치환)** | 자식은 부모의 규칙을 배신하면 안 됨. 부모 자리에 자식을 껴넣어도 잘 돌아야 함 |
| **ISP (인터페이스 분리)** | 안 쓰는 뚱뚱한 인터페이스 강요하지 말고, 용도별로 날씬하게 쪼개라 |
| **DIP (의존성 역전)** | 변하기 쉬운 구현체(`Impl`)에 매달리지 말고, 안 변하는 추상화(인터페이스)에 의존해라 |

#### 한줄 요약

- 하나의 클래스가 하나의 일을 하고, 뚱뚱한 건 쪼개고, 부모 배신 안 하며, 추상화에 매달린다.

## Ⅳ. 흐름도

<details><summary>용어 설명</summary>

- **의존성 주입(DI, Dependency Injection)**: DIP 원칙을 구현하는 기술. 개발자가 직접 `new`로 객체를 안 만들고, 밖(스프링)에서 "너 이거 써라" 하고 꽂아주는 마법이다.

</details>

```text
[ 코드 스파게티 극복 십자포화 흐름 ]
┌──────────────────────────────┐
│ 1. 스파게티 코드 발견        │
│ (하나 고치면 10개 에러 터짐) │
└──────────────┬───────────────┘
               ▼
┌──────────────────────────────┐
│ 2. SRP 적용 (책임 분리)      │
│ (결제/알림/DB 클래스 찢음)   │
└──────────────┬───────────────┘
               ▼
┌──────────────────────────────┐
│ 3. ISP 적용 (인터페이스 분리)│
│ (뚱뚱한 인터페이스 다이어트) │
└──────────────┬───────────────┘
               ▼
┌──────────────────────────────┐
│ 4. LSP/DIP/OCP 적용          │
│ (추상화에 의존하고 DI 주입)  │
└──────────────┬───────────────┘
               ▼
┌──────────────────────────────┐
│ 5. 유지보수 쌉가능 구조 완성 │
└──────────────────────────────┘
```

### 동작 원리

1. 코드 진단: 떡진 코드에서 변경 이유가 여러 개인 놈을 찾음.
2. SRP 적용: 짬뽕된 책임을 각각의 클래스로 예쁘게 찢어냄.
3. ISP 쪼개기: 필요 없는 메서드까지 구현한 놈들의 인터페이스를 세분화함.
4. OCP/LSP/DIP: `new`를 없애고 인터페이스(추상화)를 도입해 외부(Spring)에서 의존성을 꽂아줌(DI).
5. 구조 완성: 기획자가 추가 요청해도, 기존 코드 안 건드리고 구현체만 띡 추가하는 마법 완성.

#### 한줄 요약

- 떡진 클래스 찢기(SRP) $\to$ 인터페이스 다이어트(ISP) $\to$ `new` 지우고 추상화 주입(DIP) 흐름이다.

## Ⅴ. 종류 및 비교

<details><summary>용어 설명</summary>

- **코드 악취(Code Smell)**: 겉으론 돌아가지만 딱 봐도 구조가 썩어서, 나중에 수정하려면 밤샘 야근 확정인 구린내 나는 코드의 징후이다.

</details>

| 원칙 위반 증상 (Code Smell) | 위반된 원칙 | 대책 패턴 팩폭 |
|:---|:---|:---|
| 클래스 이름이 `Manager`, `Util`이고 1000줄 넘음 | **SRP 위반** | "얘가 대체 무슨 일 하는데?" $\to$ 용도별로 잘게 찢어라 |
| 기능 추가할 때마다 `if/switch` 문 분기를 계속 박음 | **OCP 위반** | **Strategy Pattern(전략 패턴)**으로 구현체로 빼라 |
| 부모 타입 호출했더니 자식이 `NotImplemented` 던짐 | **LSP 위반** | 상속을 끊어버리고 **Composition(합성)**으로 돌려라 |
| 쓸데없는 메서드를 오버라이딩하고 안엔 텅 비워둠 | **ISP 위반** | 뚱뚱한 인터페이스를 용도별로 다이어트시켜라 |
| 클래스 안에 `new KakaoPayImpl()`을 떡하니 박아둠 | **DIP 위반** | `new` 치우고 생성자나 **Spring DI**로 주입받아라 |

#### 한줄 요약

- 코드가 길면 찢고(SRP), `if`가 많으면 패턴 쓰고(OCP), `new`가 보이면 주입받아라(DIP).

## Ⅵ. 실무 고려사항 및 대책

<details><summary>용어 설명</summary>

- **오버 엔지니어링(Over-Engineering)**: 실무에선 바뀌지도 않을 로직인데, SOLID 지키겠다고 인터페이스 쪼개고 추상화 떡칠해서 코드 가독성을 지옥으로 보내버리는 삽질이다.

</details>

| 문제 | 대책 | 효과 |
|:---|:---|:---|
| 원칙에 미쳐서 쓸데없이 인터페이스 폭증 (**오버 엔지니어링**) | 고정 로직은 **YAGNI**(안 필요하니까 짜지 마) 적용 | 코드가 꼬이는 가독성 파탄 방어 |
| 자식 클래스가 부모의 근본(규칙)을 깨서 다형성 박살 남 | 상속 대신 **합성(Composition)** 우대 원칙 적용 | 치명적인 LSP 위반 차단 |
| DIP 적용한다고 `new` 지웠더니 객체 조립을 누가 함? | **Spring IoC Container** 같은 의존성 주입 툴 씀 | 비즈니스 로직과 객체 생성의 분리 |

#### 한줄 요약

- 원칙에 잡아먹혀 쓸데없이 쪼개는 짓(오버 엔지니어링)을 경계하고, 상속보단 합성을 써라.

## Ⅶ. 결론

<details><summary>용어 설명</summary>

- **SOLID 적용 기준(SOLID Adoption Criteria)**: 토이 프로젝트인지, 수십 명이 5년간 건드릴 엔터프라이즈 시스템인지 각 재서 인터페이스를 찢을지 말지 정하는 잣대이다.

</details>

- **SOLID 적용 기준** 원칙에 따라, 요구사항이 자주 바뀌는 핵심 로직은 **SOLID 떡칠**, 스크립트나 고정 배치 로직은 걍 **절차적 깡코딩(YAGNI)** 채택 기조 확립함

#### 한줄 요약

- 대형 프로젝트에선 빛과 소금이지만, 1회용 스크립트 짤 때 쓰면 그냥 시간 낭비다.
