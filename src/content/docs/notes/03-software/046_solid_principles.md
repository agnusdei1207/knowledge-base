## Ⅰ. 개요

<details><summary>용어 설명</summary>

- **객체지향 5대 원칙(SOLID Principles)**: SRP(단일책임), OCP(개방폐쇄), LSP(리스코프치환), ISP(인터페이스분리), DIP(의존역전)로 구성된 클래스/모듈 설계 가이드라인.
- **연쇄적 부수효과(Side-Effect & Fragility)**: 클래스 간 의존성이 지나치게 얽혀 있어 한 곳을 수정하면 무관한 다른 기능들이 연쇄적으로 파괴되는 소프트웨어 노후화 현상.

</details>

- 정의/개념: 소프트웨어 유지보수성과 확장성을 극대화하기 위해 **책임 단일화(SRP), 개방폐쇄(OCP), 치환성(LSP), 인터페이스 분리(ISP), 추상화 의존(DIP)**을 규정한 5대 객체지향 설계 원칙
- 배경/필요성: 강결합 스파게티 코드로 인한 **코드 수정 시 연쇄적 부수효과(Side-Effect) 발생 및 재사용 불가 한계** 직면

#### 한줄 요약

- 책임 분리와 추상화 의존으로 낮은 결합도·높은 응집도를 달성하는 객체지향 5대 설계 원칙

## Ⅱ. 특징

<details><summary>용어 설명</summary>

- **SRP(단일 책임 원칙)**: 클래스는 단 하나의 변경 이유만 가져야 하며 단일 책임에 집중해야 한다는 원칙.
- **OCP(개방-폐쇄 원칙)**: 기존 코드 수정 없이(수정에 닫힘) 새로운 기능을 인터페이스·상속으로 추가(확장에 열림)할 수 있어야 한다는 원칙.
- **LSP(리스코프 치환 원칙)**: 자식 클래스가 부모 클래스를 완전히 대체할 수 있어야 하며 부모의 계약을 위반하지 않아야 한다는 원칙.
- **ISP(인터페이스 분리 원칙)**: 클라이언트가 사용하지 않는 메서드를 강제하는 비대한 인터페이스 대신 역할별로 세분화된 인터페이스를 사용해야 한다는 원칙.
- **DIP(의존성 역전 원칙)**: 구체 구현체가 아닌 추상화(인터페이스·추상 클래스)에 의존하여 변경 가능성이 낮은 추상화에 의존해야 한다는 원칙.

</details>

- **SRP·ISP**로 클래스·인터페이스의 단일 책임 및 역할별 분리로 높은 응집도 확보
- **DIP·OCP**로 추상화 의존과 인터페이스 기반 확장으로 낮은 결합도 달성
- **LSP**로 상속 계층의 다형성을 안전하게 보장

#### 한줄 요약

- SRP·ISP로 높은 응집도를, OCP·DIP로 낮은 결합도를 달성하고 LSP로 다형성 안전성을 보장

## Ⅲ. 구조 및 구성요소

<details><summary>용어 설명</summary>

- **다형성(Polymorphism)**: 동일한 인터페이스 호출에 대해 각 구현체가 고유한 방식으로 동작하는 OCP·LSP·DIP의 핵심 메커니즘.

</details>

```text
[ SOLID 원칙 설계 방어선 ]
SRP ─(클래스 단일 책임 분리)─▶ 높은 응집도
   │
ISP ─(인터페이스 역할별 분리)─▶ 불필요 의존 제거
   │
LSP ─(자식이 부모를 안전 대체)─▶ 다형성 기반 확보
   │
OCP ─(기존 코드 보호·확장 허용)─▶ 변경 파급 차단
   │
DIP ─(추상화 의존·구현체 주입)─▶ 낮은 결합도
```

선의 의미: 각 원칙에서 화살표 우측은 원칙 준수 시 달성하는 설계 품질 속성

| 원칙 | 책임 |
|:---|:---|
| **SRP (단일 책임)** | 클래스의 변경 이유를 단 하나로 제한하여 책임을 분리 |
| **OCP (개방-폐쇄)** | 기존 코드 수정 없이 인터페이스·상속 기반으로 확장 |
| **LSP (리스코프 치환)** | 자식 클래스가 부모의 계약을 위반하지 않고 완전 대체 |
| **ISP (인터페이스 분리)** | 역할별 세분화 인터페이스로 불필요한 의존 관계 제거 |
| **DIP (의존성 역전)** | 구체 구현체 대신 추상화에 의존하여 결합도 최소화 |

#### 한줄 요약

- 단일 책임(SRP)·역할 분리(ISP)·안전 대체(LSP)·확장 열림(OCP)·추상화 의존(DIP)으로 설계 품질 확보

## Ⅳ. 흐름도

<details><summary>용어 설명</summary>

- **의존성 주입(DI, Dependency Injection)**: DIP 원칙을 구현하는 기법으로, 객체가 직접 의존 객체를 생성하지 않고 외부(IoC 컨테이너)에서 주입받아 결합도를 낮추는 패턴.

</details>

```text
1. 다중 책임 클래스 발견 (변경 이유가 복수)
   │
   ▼
2. SRP 적용: 책임별 클래스 분리 (결제·알림·DB 접근 분리)
   │
   ▼
3. ISP 적용: 비대한 인터페이스를 역할별로 세분화
   │
   ▼
4. LSP/OCP/DIP 적용:
   └─ 구체 클래스 의존을 추상화(인터페이스) 의존으로 전환
   └─ DI(의존성 주입)로 구현체를 외부에서 주입
   │
   ▼
5. 기존 코드 수정 없이 구현체 추가만으로 기능 확장 가능
```

**동작 원리**

1. **SRP 적용**: 복수 책임을 가진 클래스를 단일 책임 클래스들로 분리
2. **ISP 적용**: 클라이언트별 필요한 메서드만 포함하는 세분화 인터페이스로 교체
3. **DIP 적용**: `new` 생성자 호출 대신 인터페이스 타입으로 선언하고 Spring DI로 주입
4. **OCP 실현**: 새 구현체 추가 시 기존 코드 수정 없이 인터페이스 구현체만 추가

#### 한줄 요약

- 책임 분리(SRP·ISP) → 추상화 의존(DIP) → 확장 열림(OCP) 순서로 설계를 개선

## Ⅴ. 종류 및 비교

<details><summary>용어 설명</summary>

- **코드 악취(Code Smell)**: 기능은 동작하지만 설계 원칙 위반으로 유지보수·확장이 어려운 구조적 문제의 징후.

</details>

| 위반 증상 | 위반 원칙 | 개선 방향 |
|:---|:---|:---|
| 단일 클래스가 다수의 서로 다른 책임을 보유 | **SRP 위반** | 책임별 클래스 분리 |
| 기능 추가 시 기존 코드에 if/switch 분기 추가 | **OCP 위반** | **전략 패턴(Strategy Pattern)**으로 구현체 분리 |
| 자식 클래스가 부모 계약 위반 예외 발생 | **LSP 위반** | 상속 대신 **합성(Composition)** 전환 |
| 사용하지 않는 메서드 구현 강제 | **ISP 위반** | 역할별 인터페이스 세분화 |
| 클래스 내 구체 구현체 직접 생성(`new`) | **DIP 위반** | 인터페이스 의존·**Spring DI** 주입 전환 |

#### 한줄 요약

- 코드 악취로 SOLID 위반을 조기에 감지하고 전략 패턴·합성·DI로 설계를 개선

## Ⅵ. 실무 고려사항 및 대책

<details><summary>용어 설명</summary>

- **오버 엔지니어링(Over-Engineering)**: 변경 가능성이 낮은 로직에 불필요한 추상화·인터페이스를 과도하게 적용하여 코드 복잡도를 높이는 설계 과잉.

</details>

| 문제 | 대책 | 효과 |
|:---|:---|:---|
| 변경 가능성 낮은 로직에 과도한 인터페이스 분리(**오버 엔지니어링**) | **YAGNI** 원칙 적용으로 실제 변경 요구가 있을 때만 추상화 도입 | 불필요한 복잡도 방지 |
| 자식 클래스가 부모의 불변 조건을 위반하여 다형성 파괴 | 상속 대신 **합성(Composition)** 선호 원칙 적용 | LSP 위반으로 인한 런타임 오류 방지 |
| DIP 적용 시 객체 조립 책임 부재 | **Spring IoC Container** 활용으로 의존성 주입 자동화 | 비즈니스 로직과 객체 생성 관심사 분리 |

#### 한줄 요약

- 변경 불필요 로직은 YAGNI로, LSP 위반은 합성으로, DIP 조립 문제는 Spring DI로 해소

## Ⅶ. 결론

<details><summary>용어 설명</summary>

- **SOLID 적용 기준**: 요구사항 변경 빈도·시스템 규모·팀 규모를 기준으로 SOLID 원칙 적용 수준을 결정하는 판단 기준.

</details>

- 변경이 잦은 핵심 도메인 로직은 **SOLID 전면 적용**, 고정 배치·스크립트 로직은 **YAGNI 기반 절차적 설계** 선택

#### 한줄 요약

- 요구사항 변경 빈도와 시스템 규모에 따라 SOLID 적용 수준을 결정하고 과잉 추상화를 경계
