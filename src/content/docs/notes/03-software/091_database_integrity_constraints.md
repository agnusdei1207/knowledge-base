## Ⅰ. 개요

<details><summary>용어 설명</summary>

- **4대 무결성 제약조건**: 개체 무결성(PK Not Null & Unique), 참조 무결성(FK 유효성), 도메인 무결성(타입 및 Check 범위), 사용자 정의 무결성(트리거/비즈니스 제약).
- **고아 데이터 및 데이터 오염(Orphan Data & Corruption)**: 외래키 제약 부재로 부모 튜플이 삭제되었음에도 자식 테이블에 쓰레기 데이터가 잔존하거나 비정상적인 값이 저장되는 현상.

</details>

- 정의/개념: 데이터베이스에 저장되는 데이터의 유효성과 일관성을 위해 **개체(PK), 참조(FK), 도메인(Check), 사용자정의(Trigger)** 4대 규칙을 강제하는 스키마 제약 체계
- 배경/필요성: 애플리케이션 단독 검증 시 직접 SQL 접근에 따른 **검증 우회, 부모 삭제 후 고아 데이터(Orphan) 발생 및 데이터 오염 위험** 직면

#### 한줄 요약

- 개체, 참조, 도메인, 사용자 정의 무결성을 DBMS 엔진 레벨에서 선언하여 데이터의 신뢰성을 보장

## Ⅱ. 특징

<details><summary>용어 설명</summary>

- **선언적 DDL 강제(Declarative DDL)**: 애플리케이션 코드에 의존하지 않고 `PRIMARY KEY`, `FOREIGN KEY`, `CHECK`, `NOT NULL` 등 DDL로 선언하여 엔진이 직접 검증.
- **런타임 선제적 차단(Pre-Validation & Abort)**: `INSERT/UPDATE/DELETE` 실행 시 제약조건 위반이 감지되면 즉시 에러를 발생시키고 트랜잭션을 롤백.

</details>

- 모든 데이터 변경 작업에 대해 DBMS 엔진 레벨에서 **중앙집중식 규칙 강제**
- DDL 선언을 통한 **선제적 런타임 위반 감지 및 즉각적 트랜잭션 롤백**
- 다중 애플리케이션 및 직접 SQL 배치 접속 환경에서도 **동일한 데이터 무결성 보장** #### 한줄 요약

- 선언적 DDL과 엔진 차원의 중앙 통제로 어떤 우회 경로에서도 데이터 무결성을 절대 방어

## Ⅲ. 구조 및 구성요소

<details><summary>용어 설명</summary>

- **참조 무결성 옵션(Referential Actions)**: RESTRICT/NO ACTION(삭제 차단), CASCADE(연쇄 삭제), SET NULL(외래키 Null 처리), SET DEFAULT(기본값 처리).

</details>

```text
[ 데이터베이스 4대 무결성 제약 구조도 ]

 ┌────────────────────────────────────────────────────────────────────────┐
 │                   데이터베이스 4대 무결성 제약 체계                     │
 ├───────────────────┬───────────────────┬────────────────────────────────┤
 │ 1. 개체 무결성    │ 2. 참조 무결성    │ 3. 도메인 무결성               │
 │   - PRIMARY KEY   │   - FOREIGN KEY   │   - NOT NULL                   │
 │   - UNIQUE        │   - ON DELETE 옵션│   - CHECK (조건식) / DEFAULT   │
 ├───────────────────┴───────────────────┴────────────────────────────────┤
 │ 4. 사용자 정의 무결성 (User-Defined: Trigger, Stored Procedure)        │
 └────────────────────────────────────────────────────────────────────────┘
```

선의 의미: 데이터베이스 엔진이 개체, 참조, 도메인, 사용자 정의 무결성을 결합하여 다층 방어막을 형성하는 구조.

| 구성요소 | 책임 |
|:---|:---|
| 개체 무결성 (Entity) | 행(Tuple)의 유일성을 식별하기 위해 **기본키(PK)의 고유성과 Not Null 강제** |
| 참조 무결성 (Referential) | 부모-자식 간의 관계를 보장하고 **외래키(FK) 값의 유효성 및 고아 데이터 차단** |
| 도메인 무결성 (Domain) | 속성(Column)의 데이터 타입, 자릿수, **Not Null 및 Check 조건 범위 검증** |
| 사용자 정의 무결성 | DDL로 표현 불가한 복잡한 업무 규칙을 **트리거 및 저장 프로시저로 검증** |

#### 한줄 요약

- 개체(행 유일성), 참조(관계 유효성), 도메인(값 범위), 사용자 정의(업무 규칙)로 무결성을 완성

## Ⅳ. 흐름도

<details><summary>용어 설명</summary>

- **참조 무결성 검증 파이프라인**: 부모 행 삭제 시 자식 테이블의 FK 인덱스를 탐색하여 참조 동작(RESTRICT/CASCADE)을 분기 처리하는 과정.

</details>

```text
[ 참조 무결성 삭제 검증 및 분기 처리 파이프라인 ]

 ┌────────────────────────────────────────┐
 │ 1. 부모 테이블 튜플 삭제(DELETE) 요청  │
 └───────────────────┬────────────────────┘
                     │
                     ▼
 ┌────────────────────────────────────────┐
 │ 2. 자식 테이블 FK 참조 레코드 탐색     │
 └───────────────────┬────────────────────┘
                     │ (참조 레코드 존재 시)
                     ▼
 ┌────────────────────────────────────────┐
 │ 3. 삭제 옵션(ON DELETE) 정책 판정      │
 ├───────────────────┬────────────────────┤
 │ RESTRICT / NO ACT │ CASCADE / SET NULL │
 │ (삭제 차단 및 롤백│ (자식 연쇄 삭제/널)│
 └───────────────────┴────────────────────┘
```

### 동작 원리

1. 삭제 요청: 부모 테이블에 대해 `DELETE` SQL이 실행됨.
2. FK 참조 탐색: DBMS 엔진이 자식 테이블의 외래키 인덱스를 조회하여 해당 기본키를 참조하는 행이 있는지 검사.
3. 삭제 정책 판정: 자식 레코드가 존재할 경우 선언된 `ON DELETE` 정책에 따라 동작을 분기.
4. 예외 및 롤백: `RESTRICT`인 경우 즉시 무결성 위반 에러를 반환하고 트랜잭션을 롤백.
5. 연쇄 처리: `CASCADE`인 경우 자식 레코드를 함께 삭제하고, `SET NULL`인 경우 자식 외래키 값을 Null로 갱신.

#### 한줄 요약

- 부모 삭제 $\to$ 자식 FK 탐색 $\to$ 정책 판정 $\to$ RESTRICT(롤백) 또는 CASCADE(연쇄 처리)

## Ⅴ. 종류 및 비교

<details><summary>용어 설명</summary>

- **Application Validation vs DB Constraint**: 비즈니스 친화적이나 우회 가능한 앱 레벨 검증과 절대적이나 스키마 변경이 필요한 DB 레벨 제약.

</details>

| 구분 | Application Level Validation | Database Integrity Constraint |
|:---|:---|:---|
| **적용 기준** | 사용자 친화적 에러 메시지 및 유연한 폼 검증 | 데이터의 절대적 무결성 및 중앙 집중식 규칙 강제 |
| **핵심 특징** | **Spring/Java 코드 수준에서 조건별 가변 검증** | **DBMS 엔진 DDL 선언을 통해 모든 입력 경로 중앙 통제** |
| **한계** | 직접 SQL 배치나 타 시스템 연계 시 우회 위험 | 복잡한 제약조건 추가 시 DB 성능 부하 및 마이그레이션 부담 |

#### 한줄 요약

- 애플리케이션 검증은 사용자 경험을 개선하고, DB 무결성 제약은 최후의 데이터 안전망을 담당

## Ⅵ. 실무 고려사항 및 대책

<details><summary>용어 설명</summary>

- **FK 인덱스 누락 병목(Unindexed FK Bottleneck)**: 자식 테이블의 Foreign Key 컬럼에 인덱스가 없을 때 부모 삭제/수정 시 자식 테이블 전체에 풀 스캔 락(Table Lock)이 걸리는 현상.

</details>

| 문제 | 대책 | 효과 |
|:---|:---|:---|
| Foreign Key 인덱스 부재로 부모 행 삭제 시 Table Lock 발생 | **모든 자식 테이블의 FK 컬럼에 B-Tree 인덱스 필수 생성** | 참조 검사 속도 향상 및 락 경합 방지 |
| `ON DELETE CASCADE` 남용으로 인한 연쇄 대량 데이터 유실 | **실무에서는 `CASCADE` 자제, `RESTRICT` 또는 `SET NULL` 권장** | 실수로 인한 주요 비즈니스 데이터 삭제 원천 방지 |
| 대용량 데이터 배치 적재 시 제약조건 검사로 인한 쓰기 지연 | **적재 중 제약조건 일시 비활성화 $\to$ 적재 완료 후 일괄 검증 활성화** | 대용량 배치 처리 속도 극대화 |

#### 한줄 요약

- FK 인덱스 필수 생성, CASCADE 남용 금지, 배치 적재 시 일괄 검증으로 성능과 안정성을 양립

## Ⅶ. 결론

<details><summary>용어 설명</summary>

- **심층 방어 무결성(Defense in Depth Integrity)**: 프론트엔드 UI 검증, 백엔드 애플리케이션 검증, DBMS 무결성 제약조건의 3중 방어 체계.

</details>

- **데이터베이스 무결성 제약 조건** 시스템이 붕괴되어도 데이터의 신뢰성을 지켜내는 최후의 보루이며, 애플리케이션 유효성 검사와 DB 레벨 선언적 제약을 상호 보완적으로 결합하여 완벽한 데이터 무결성을 달성해야 함

#### 한줄 요약

- 4대 무결성 제약을 엔진 레벨에 선언하고 FK 인덱싱을 병행하여 무결성과 고성능을 동시에 확보
