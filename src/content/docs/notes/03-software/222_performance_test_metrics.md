## Ⅰ. 개요

<details><summary>용어 설명</summary>

- **성능 테스트 지표 (Performance Test Metrics)**: TPS, 응답 시간 백분위수(P95/P99), 동시 사용자, 자원 사용률을 다차원으로 측정하여 시스템 처리 용량과 포화 한계를 판정하는 지표.
- **Little's Law (리틀의 법칙)**: $N = \mathrm{TPS} \times (R + Z)$ 공식으로 동시 사용자($N$), 초당 처리량(TPS), 응답 시간($R$), 생각 시간($Z$) 간의 수학적 관계를 규명.

</details>

- 정의/개념: 시스템의 처리 용량과 한계 병목을 규명하기 위해 **TPS, 응답시간(P95/P99), 동시 사용자 및 자원 사용률을 다차원 계측하는 지표 체계**
- 배경/필요성: 성능 시험 시 산술 평균 응답시간 착시로 인한 **상위 1% 사용자의 치명적 꼬리 지연(Tail Latency) 은폐 및 시스템 처리 한계(Knee Point) 오판 한계**

#### 한줄 요약
- 처리량(TPS)과 꼬리 지연(P99) 및 리틀의 법칙을 결합하여 시스템의 안전 운영 용량을 확정한다.

## Ⅱ. 특징

<details><summary>용어 설명</summary>

- **Response Percentile (응답 백분위수: P95/P99)**: 전체 요청 중 95% 또는 99%가 완료되는 소요 시간으로 평균값의 착시를 제거하는 지표.
- **Think Time (생각 시간)**: 실제 사용자가 화면을 읽고 다음 버튼을 클릭하기까지 대기하는 현실적 시간 간격.

</details>

- 실패 요청을 제외하고 정상 완료된 비즈니스 트랜잭션만을 산정하는 **순수 처리량(TPS)**
- 평균값의 착시를 제거하고 소수 고객의 체감 지연을 추적하는 **P95/P99 꼬리 지연 측정**
- 리틀의 법칙($N = \mathrm{TPS} \times (R + Z)$)을 적용하여 **동시 사용자와 처리량 간 정합성 검증**

#### 한줄 요약
- 순수 TPS, P99 꼬리 지연, 리틀의 법칙 수학적 검증을 통해 성능 병목 지점을 포착한다.

## Ⅲ. 구조 및 구성요소

<details><summary>용어 설명</summary>

- **성능 테스트 4대 계측 계층**: Workload Model(부하 모델), Load Generator(부하 생성기), System Under Test(검증 대상), Analysis Engine(병목 분석기).

</details>

```text
[성능 테스트 구성]
|-- 부하 모델
|-- 부하 생성기
|-- 시험 대상 시스템
|-- 지표 수집기
`-- 포화 분석기
```

선의 의미: 계층 및 부하 모델에 따라 생성기가 SUT에 단계별 부하를 가하고 지표 수집기가 TPS, 지연, 자원을 측정하여 분석기가 포화점을 확정하는 구조

| 구성요소 | 핵심 엔지니어링 책임 | 주요 특징 |
|:---|:---|:---|
| **부하 모델 (Workload)** | 실제 사용자 행동 패턴, **요청 비율, 동시 사용자 수, 생각 시간(Think Time) 정의** | 현실적 시나리오 |
| **부하 생성기 (Generator)** | 마스터-슬레이브 분산 구조로 **목표 가상 사용자(VUser) 및 트래픽 부하 정밀 인가** | JMeter, k6 |
| **시험 대상 시스템 (SUT)** | 프로덕션과 동일한 인프라 배포 환경에서 **인입되는 트랜잭션 실제 분산 처리** | EKS, RDS 클러스터 |
| **지표 수집기 (Collector)** | APM 및 프로메테우스를 통해 **TPS, 응답 백분위수, 오류율, 자원 점유율 동시 수집** | 초단위 정밀 계측 |
| **포화 분석기 (Analyzer)** | 부하 증가 시 TPS가 꺾이고 지연이 급증하는 **Knee Point(포화 변곡점) 자동 판정** | 안전 용량 산출 |

#### 한줄 요약
- 부하 모델이 시험의 현실성을, 포화 분석기가 판정 기준을 맡으므로 결과가 장비 사양이 아니라 운영 가능한 용량이라는 숫자로 환산된다.

## Ⅳ. 흐름도

<details><summary>용어 설명</summary>

- **성능 테스트 5단계**: 단계별 부하 인가 $\to$ 실시간 지표 계측 $\to$ 자원 모니터링 $\to$ 병목 원인 분석 $\to$ 안전 운영 용량 확정.

</details>

```text
단계별 성능 부하 테스트 실행 (Step Load Test)
        │
   1. [단계별 부하 인가] 가상 사용자(VUser)를 100명 단위로 10분 간격 계단식 증합
        │
   2. [실시간 지표 계측] 부하 구간별 TPS, P95/P99 지연시간, HTTP 5xx 에러율 수집
        │
   3. [자원 모니터링] CPU 75%, DB Connection Pool 고갈 여부를 APM으로 동시 관측
   ┌────┴───────────────────────────┐
  SLO 충족 및 자원 여유             SLO 위반 (P99 > 1초 or Error > 1%)
   │                                 │
   • 다음 단계 VUser 부하 증합         • Knee Point(포화 변곡점) 확정
   │                                 │
   └────┬────────────────────────────┘
        ▼
   4. [병목 원인 분석] 슬로우 쿼리 및 락 경합 지점 튜닝 조치
        │
   5. [안전 운영 용량 확정] 피크 부하의 70% 수준을 프로덕션 안전 운영 용량으로 공식 확정
```

#### 한줄 요약
- 부하를 단계적으로 올려야 TPS가 꺾이는 변곡점이 드러나며, 그 지점을 넘어서면 부하를 더해도 처리량 대신 지연과 오류만 늘어난다.

## Ⅴ. 종류 및 비교

<details><summary>용어 설명</summary>

- **TPS vs 응답 시간(Latency) vs 동시 사용자(Concurrent User)**: 처리 속도 용량(TPS), 사용자 체감 지연(Latency), 시스템 부하 유발자(동시 사용자).

</details>

| 비교 항목 | 초당 거래 수 (TPS) | 응답 시간 (Latency / P99) | 동시 사용자 (Concurrent User) |
|:---|:---|:---|:---|
| 핵심 측정 관점 | **시스템의 단위 시간당 일 처리 능력** | **개별 사용자가 느끼는 서비스 체감 속도** | **동일 시점에 시스템을 이용 중인 부하원** |
| 측정 단위 | TPS (Transactions Per Second) | ms (초, 밀리초 단위 P95/P99 분포) | 명 (Active VUser / Inactive VUser) |
| 해석 시 유의점 | 에러 응답(500)이 포함되면 왜곡 발생 | **평균값은 소수 꼬리 지연을 은폐함** | **접속자(Concurrent)와 활동자(Active) 구분**|
| 비즈니스 연계 | 서버 스케일아웃 증설 사이징 기준 | **고객 이탈률 및 결제 성공률 SLO 기준** | 이벤트 동시 접속 마케팅 수용량 기준 |

#### 한줄 요약
- 처리 능력은 TPS, 체감 속도는 P99 지연, 인입 부하는 동시 사용자를 유기적으로 결합하여 분석한다.

## Ⅵ. 실무 고려사항 및 대책

<details><summary>용어 설명</summary>

- **Tail Latency Masking (꼬리 지연 은폐)**: 평균 응답시간은 0.2초로 정상이지만, 1% 고객의 P99 지연이 15초에 달해 결제가 이탈하는 현상.

</details>

| 문제 | 대책 | 효과 |
|:---|:---|:---|
| 평균 응답시간의 왜곡으로 1% 고객의 치명적 꼬리 지연 은폐 | **평균값 대신 `P95, P99 백분위수 및 오류율`을 SLO 기준으로 강제** | 꼬리 지연 100% 가시화 및 방어 |
| Think Time 0초 설정으로 비현실적 디도스 공격형 부하 유발 | **실제 사용자 로그 기반 `Think Time (평균 3~5초)` 가우스 분포 적용** | 실제 운영 환경과 99% 일치 달성 |
| 캐시 웜업(Warm-up) 상태에서만 테스트하여 오픈 직후 콜드 캐시 다운 | **`Cold Cache(캐시 비움)` 상태와 Warm Cache 상태를 분리 시험** | 오픈 당일 캐시 스탬피드 장애 방어 |
| 부하 생성기(JMeter) 자체의 CPU 100% 포화로 인한 측정 왜곡 | **부하 생성기 분산 클러스터링 및 생성기 자원 사용률(50% 이하) 감시** | 테스트 도구에 의한 왜곡 원천 차단 |

#### 한줄 요약
- 네 대책은 시험 조건을 실제 운영 환경 쪽으로 되돌려 얻은 신뢰도이며, 현실성을 높일수록 시험 준비 공수와 소요 시간은 함께 늘어난다.

## Ⅶ. 결론

- 서비스 오픈 전 가용 용량 산정과 SLA/SLO 준수 여부를 검증하는 **가장 핵심적인 성능 엔지니어링 및 사이징 평가 표준 프레임워크**로 확립되었으며, 실무 수행 시에는 **평균의 함정을 배제한 P95/P99 꼬리 지연 및 에러율 기반 통과 기준 수립, 현실적인 Think Time 가우스 분포 적용, 오픈 직후를 대비한 Cold Cache/Warm Cache 분리 시험, 부하 증가에 따라 처리량이 꺾이는 변곡점(Knee Point)의 70% 수준을 상시 안전 용량으로 확정**을 결합하여 무결점 서비스 오픈과 안정적 확장을 완성

#### 한줄 요약
- 성능 테스트 지표는 TPS, P99 지연, 동시 사용자, 자원 점유율의 상관관계를 분석하여 시스템의 포화 한계와 안전 용량을 확정하는 핵심 성능 엔지니어링 기술이다.
