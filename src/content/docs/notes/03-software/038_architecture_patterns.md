## Ⅰ. 개요

<details><summary>용어 설명</summary>

- **아키텍처 패턴(Architecture Pattern)**: 맨땅에 헤딩하지 않도록, 선배 개발자들이 피똥 싸며 만들어놓은 '이럴 땐 이렇게 짜라'는 검증된 소프트웨어 뼈대(청사진) 족보이다.
- **계층형 패턴(Layered Pattern)**: UI(화면), 비즈니스 로직, DB(데이터)를 햄버거 패티처럼 세로로 층층이 쌓아놔서 섞이지 않게 막는 가장 만만한 기본 아키텍처이다.
- **아키텍처 트레이드오프(Trade-off Analysis)**: MSA를 쓰면 확장은 짱짱한데 DB 트랜잭션 헬파티가 열리는 것처럼, 모든 아키텍처엔 장점이 있으면 단점(비용)이 있다는 등가교환 분석이다.

</details>

- 정의: 맨땅 코딩 방지용으로, 선배들이 닦아놓은 구조와 통신 방식 족보를 재활용하는 **Architecture Pattern**
- 배경: 아무 생각 없이 스파게티 코드를 짜면, 나중에 버튼 하나 바꿨는데 **DB가 터지는 대재앙(파급 효과)**이 열리기 때문

#### 한줄 요약

- 선배들이 겪은 피똥의 결과물(패턴)을 가져다 써서 스파게티 코드를 막는 뼈대다.

## Ⅱ. 특징

<details><summary>용어 설명</summary>

- **관심사 분리(Separation of Concerns)**: UI 그리는 놈, 로직 짜는 놈, DB 저장하는 놈을 각방에 가둬서, 한 놈이 사고 쳐도 다른 방으로 불이 번지지 않게 격리하는 룰이다.
- **품질 속성(System Quality Attributes)**: 앱이 안 죽냐(가용성), 빠르냐(성능), 안 털리냐(보안성) 같이 아키텍처를 고를 때 잣대가 되는 비기능적 스펙이다.

</details>

- UI, 로직, DB를 철저하게 각방에 가두는 **관심사 분리(Separation of Concerns)**를 보장함.
- 앱이 얼마나 빠르고 튼튼한지 결정짓는 **품질 속성(Quality Attributes)**의 근간이 됨.
- 성능, 확장성, 복잡도 사이에서 뼈를 내주고 살을 취하는 **트레이드오프(Trade-off)**가 존재함.

#### 한줄 요약

- 역할(관심사)을 확실히 찢고, 성능과 복잡도 사이에서 등가교환(트레이드오프)을 치는 게 핵심이다.

## Ⅲ. 구조 및 구성요소

<details><summary>용어 설명</summary>

- **MVC (Model-View-Controller)**: 화면(View)과 데이터(Model)를 분리하고, 그 사이에서 멱살 잡고 중재하는 컨트롤러(Controller)를 둔 클래식 웹 아키텍처이다.
- **EDA (Event-Driven Architecture)**: "가입했어!"라고 이벤트만 던지고 튀면, 쿠폰 주고 이메일 쏘는 놈들이 알아서 주워 먹는, 결합도를 지하 암반수까지 낮춘 비동기 아키텍처이다.

</details>

```text
[ 아키텍처 패턴 십자포화 진화 트랙 ]

[ 모놀리식 (Monolithic) ]  ➔  [ 마이크로서비스 (MSA) ]  ➔  [ 이벤트 기반 (EDA) ]
     (한 통에 다 때려박음)           (기능별로 쪼개고 찢음)          (메시지만 던지고 튐)

   ex) MVC / Layered               ex) 분산 REST API               ex) Kafka Pub/Sub
```

| 구성요소 | 책임 |
|:---|:---|
| **계층형 / MVC** | 화면, 로직, DB를 층별로 찢어놓은 **가장 만만하고 클래식한 국밥 패턴** |
| **마이크로서비스 (MSA)** | "내 DB는 나만 건드려!" 라며 업무별로 서버와 DB를 갈기갈기 찢어버린 **분산 패턴** |
| **이벤트 주도 (EDA)** | API 호출 기다리지 않고 "나 일 끝남!" 이벤트만 허공에 쏘고 튀는 **비동기 패턴** |
| 헥사고널 (Hexagonal) | 코어 로직을 가운데 박고, 외부 DB나 화면은 언제든 갈아 끼우는 **방어형 패턴** |

#### 한줄 요약

- 층으로 찢으면 MVC, 서버를 찢으면 MSA, 비동기 메시지로 찢으면 EDA다.

## Ⅳ. 흐름도

<details><summary>용어 설명</summary>

- **아키텍처 결정 기록(ADR, Architecture Decision Record)**: "왜 멀쩡한 모놀리스 버리고 굳이 MSA 골라서 헬파티를 열었는가?"를 나중에 변명하려고 적어두는 팩트 기반 설계 일기장이다.

</details>

```text
[ 아키텍처 결정 십자포화 흐름 ]
┌──────────────────────────────┐
│ 1. 시스템 품질(비기능) 목표  │
│ (우리 트래픽 얼마나 터짐?)   │
└──────────────┬───────────────┘
               ▼
┌──────────────────────────────┐
│ 2. 패턴 후보군 픽 (MVC vs MSA)│
│ (국밥 먹을까 분산 치를까?)   │
└──────────────┬───────────────┘
               ▼
┌──────────────────────────────┐
│ 3. 트레이드오프(Trade-off) 팸│
│ (성능 vs 확장성 팩트 폭행)   │
└──────────────┬───────────────┘
               ▼
┌──────────────────────────────┐
│ 4. ADR 작성 및 패턴 픽스     │
│ (결정 이유를 문서로 박제함)  │
└──────────────────────────────┘
```

### 동작 원리

1. 품질 목표 파악: 트래픽이 미어터지는지, 아니면 사내용 인트라넷인지 사이즈를 잼.
2. 패턴 후보 픽: "DB 하나에 다 박는 MVC 갈까, 분산 MSA 갈까?" 후보를 추림.
3. 트레이드오프: "MSA 가면 확장성은 쩌는데, 장애 추적하다 탈모 온다" 팩트로 팸.
4. ADR(결정 기록) 박제: "MSA 쓴 이유는 OOO 때문임" 하고 족보(ADR)를 남기고 코딩 시작함.

#### 한줄 요약

- 목표 잡고 $\to$ 후보 추리고 $\to$ 장단점(트레이드오프) 팩트 체크하고 $\to$ 문서(ADR)로 박제한다.

## Ⅴ. 종류 및 비교

<details><summary>용어 설명</summary>

- **모놀리스 vs 마이크로서비스 vs 이벤트 주도(Monolith vs MSA vs EDA)**: 쪼렙 때는 통짜(Monolith)로 굴리다, 사람 몰리면 쪼개고(MSA), 트래픽이 미쳐 날뛰면 허공에 이벤트 쏘는(EDA) 아키텍처의 진화 테크트리이다.

</details>

| 비교 항목 | **Layered / MVC** (통짜 국밥) | **Microservices (MSA)** (찢기) | **Event-Driven (EDA)** (던지기) |
|:---|:---|:---|:---|
| 데이터베이스 | 멱살 잡고 1개의 거대 DB 공유 | **DB도 갈기갈기 찢음 (Service-per-DB)** | 이벤트 스트림 큐(Kafka) / 비동기 뷰 DB |
| 통신 속도 | 인메모리 함수 호출 (존나 빠름) | REST/gRPC 네트워크 탐 (느리고 뻗음) | **비동기 Pub/Sub (안 기다리고 튐)** |
| 데이터 정합성 | 트랜잭션 묶이면 절대 안 틀림 | 2PC/Saga 쓰다 머리 빠짐 (최종 일관성) | **최종 일관성 (언젠가는 맞겠지)** |
| 찰떡 무대 | 극초기 스타트업, 사내 시스템 | **배민, 토스 같은 초거대 엔터프라이즈** | **실시간 IoT, 금융 거래 피드** |

#### 한줄 요약

- 속도와 정합성은 모놀리스(MVC)가 좋고, 트래픽 확장성은 MSA와 EDA가 압살한다.

## Ⅵ. 실무 고려사항 및 대책

<details><summary>용어 설명</summary>

- **아키텍처 부패(Architectural Degradation)**: 처음엔 MVC로 예쁘게 짰는데, 납기일 쪼달리니까 뷰(View)에서 DB 쿼리(Model)를 바로 때려버리면서 시스템이 썩어 문드러지는 현상이다.

</details>

| 문제 | 대책 | 효과 |
|:---|:---|:---|
| 실력도 없는데 MSA병 걸려서 쓰다가 분산 지옥 터짐 | 깝치지 말고 일단 **모듈리스(Modulith)**로 짜고 커지면 찢음 | 오버엔지니어링 막고 초기 개발 속도 사수 |
| 납기 쪼달린다고 뷰에서 DB 바로 쑤심 (**부패**) | **ArchUnit** 툴로 "계층 어기면 빌드 컷!" 자동화시킴 | 스파게티 코드로 부패하는 걸 강제로 틀어막음 |
| 이벤트 스키마 막 바꿨다가 구독하던 서비스들 다 뻗음 | 카프카에 **Schema Registry** 박아서 하위 호환성 강제함 | 인터페이스 안 맞아서 터지는 런타임 장애 원천 차단 |

#### 한줄 요약

- MSA병 조심하고, 계층 파괴(부패)는 빌드 툴로 막고, 비동기 스키마는 호환성 멱살을 잡아라.

## Ⅶ. 결론

<details><summary>용어 설명</summary>

- **아키텍처 패턴 선택 기준(Architecture Pattern Selection Criteria)**: 우리 팀 실력이 되는지, 트래픽이 얼마나 꽂히는지 각 재서 얌전히 MVC 짤지 MSA로 갈아탈지 가르는 잣대이다.

</details>

- **아키텍처 패턴 선택 기준** 원칙에 따라, 가볍게 짤 땐 **Layered(MVC)**, 팀과 서버를 독립시켜야 할 땐 **MSA**, 미친 트래픽 비동기 처리는 **EDA** 채택 기조 확립함

#### 한줄 요약

- 남들 다 쓴다고 MSA 쓰지 말고, 니네 팀 사이즈와 트래픽(선택 기준)에 맞춰서 패턴을 골라라.
