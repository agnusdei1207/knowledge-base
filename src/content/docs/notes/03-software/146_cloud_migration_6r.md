## Ⅰ. 개요

<details><summary>용어 설명</summary>

- **클라우드 마이그레이션 6R(Cloud Migration 6R)**: 기업의 레거시 시스템을 클라우드로 이관할 때 워크로드의 가치와 제약에 따라 최적의 이전 방식을 결정하는 6대 전략(Rehost, Replatform, Refactor, Repurchase, Retain, Retire).
- **빅뱅 전면 재개발 위험(Big-Bang Failure Risk)**: 모든 레거시 시스템을 무리하게 전면 재개발하려다 프로젝트가 지연되고 예산이 초과되어 비즈니스 연속성이 마비되는 위험.

</details>

- 정의/개념: 온프레미스 레거시 시스템을 클라우드로 이관 시 **Rehost, Replatform, Refactor, Repurchase, Retain, Retire로 분류한 6대 마이그레이션** 전략 프레임워크
- 배경/필요성: 모든 레거시 시스템을 획일적 전면 재개발(Big-Bang)로 추진 시 발생하는 **예산 초과, 프로젝트 지연 및 이관 실패로 인한 비즈니스 마비 위험** 직면

#### 한줄 요약

- 시스템의 비즈니스 가치와 복잡도에 따라 6가지 전략을 최적 조합하여 안전하고 경제적인 클라우드 전환을 완수

## Ⅱ. 특징

<details><summary>용어 설명</summary>

- **Rehost (Lift-and-Shift)**: 코드 변경 없이 기존 VM과 데이터를 클라우드 가상머신(EC2)으로 그대로 이전하는 신속 이관 전략.
- **Replatform (Lift-Shift-and-Tweak)**: 핵심 코드는 유지하면서 DB나 미들웨어만 클라우드 관리형 PaaS(RDS)로 교체하는 부분 현대화 전략.
- **Refactor (Re-architect)**: MSA, 서버리스, 컨테이너 등 클라우드 네이티브 아키텍처로 전면 재설계하는 고부가가치 전략.

</details>

- 신속 이관(Rehost)부터 전면 클라우드 네이티브 현대화(Refactor)까지 **단계별 이전 경로 제공**
- 상용 SaaS 전환(Repurchase), 현행 유지(Retain), 자산 폐기(Retire)를 포함한 **포괄적 자산 최적화**
- 시스템 간 상호 연관 관계를 분석하여 단계별로 이관하는 **마이그레이션 웨이브(Wave) 계획 연계** #### 한줄 요약

- 6가지 이전 방식을 포트폴리오 관점에서 유연하게 적용하여 리스크를 분산하고 클라우드 전환 가치를 극대화

## Ⅲ. 구조 및 구성요소

<details><summary>용어 설명</summary>

- **6R 마이그레이션 전략 구성요소**: Rehost, Replatform, Refactor, Repurchase, Retain, Retire 6대 축.

</details>

```text
[ 클라우드 마이그레이션 6R 프레임워크 아키텍처 ]

 ┌────────────────────────────────────────────────────────────────────────┐
 │                    전사 레거시 워크로드 포트폴리오 평가                 │
 ├─────────────────────┬───────────────────┬──────────────────────────────┤
 │ 1. 기술 이전 영역   │ 2. 현대화 영역    │ 3. 비즈니스 정제 영역        │
 ├─────────────────────┼───────────────────┼──────────────────────────────┤
 │ • Rehost            │ • Refactor        │ • Repurchase                 │
 │   - Lift-and-Shift  │   - Cloud-Native  │   - 상용 SaaS 완제품 도입    │
 │ • Replatform        │   - MSA 재설계    │ • Retain (현행 유지)         │
 │   - 관리형 PaaS 교체│   - Serverless    │ • Retire (불필요 자산 폐기)  │
 └─────────────────────┴───────────────────┴──────────────────────────────┘
```

선의 의미: 전사 레거시 자산을 기술 이전, 현대화, 비즈니스 정제의 3대 영역 6가지 전략으로 분기 배치하는 구조.

| 구성요소 | 책임 |
|:---|:---|
| Rehost (재호스팅) | 애플리케이션 수정 없이 **가상머신(EC2)으로 그대로 이전하여 마이그레이션 속도 극대화** |
| Replatform (재플랫폼) | 코드는 유지하되 **DB를 RDS 등 클라우드 관리형 PaaS로 교체하여 운영 효율 향상** |
| Refactor (재설계) | 핵심 비즈니스 시스템을 **MSA 및 컨테이너(K8s) 기반의 클라우드 네이티브로 전면 재개발** |
| Repurchase (재구매) | 레거시 커스텀 패키지를 **Salesforce, Workday 등 완성형 SaaS 솔루션으로 대체** |
| Retain (유지) | 기술적 제약이나 감가상각이 남은 시스템을 **당분간 온프레미스에 그대로 존치** |
| Retire (폐기) | 더 이상 비즈니스 가치가 없거나 중복된 **레거시 서버 및 소프트웨어 영구 종료** |

#### 한줄 요약

- Rehost, Replatform, Refactor, Repurchase, Retain, Retire가 결합하여 전사 자산 최적화를 달성

## Ⅳ. 흐름도

<details><summary>용어 설명</summary>

- **6R 의사결정 5단계 파이프라인**: 자산 인벤토리 실사 $\to$ 비즈니스 가치 평가 $\to$ 6R 전략 매핑 $\to$ Wave 의존성 그룹핑 $\to$ 컷오버 전환.

</details>

```text
[ 클라우드 마이그레이션 6R 의사결정 파이프라인 ]

 ┌────────────────────────────────────────┐
 │ 1. 전사 IT 자산 인벤토리 및 의존성 실사│
 └───────────────────┬────────────────────┘
                     │
                     ▼
 ┌────────────────────────────────────────┐
 │ 2. 비즈니스 가치 및 기술 노후도 평가   │
 └───────────────────┬────────────────────┘
                     │
                     ▼
 ┌────────────────────────────────────────┐
 │ 3. 시스템별 최적 6R 전략 매핑 확정    │
 └───────────────────┬────────────────────┘
                     │
                     ▼
 ┌────────────────────────────────────────┐
 │ 4. 마이그레이션 Wave 그룹핑 및 일정 수립│
 └───────────────────┬────────────────────┘
                     │
                     ▼
 ┌────────────────────────────────────────┐
 │ 5. 단계적 이관, 데이터 동기화 및 컷오버 │
 └────────────────────────────────────────┘
```

### 동작 원리

1. 자산 실사: AWS Application Discovery Service를 통해 서버 목록, OS 버전, 네트워크 의존성 맵을 자동 수집.
2. 가치 평가: 각 워크로드의 비즈니스 중요도, 변경 빈도, 유지보수 비용, 라이선스 만료 시점을 평가.
3. 전략 매핑: 평가 결과를 바탕으로 미사용 시스템은 Retire, 핵심 차별화 시스템은 Refactor, 단순 이전은 Rehost로 결정.
4. Wave 수립: 데이터베이스와 애플리케이션 간 강한 결합을 가진 서버들을 동일한 Wave(이관 차수)로 묶음.
5. 컷오버 전환: AWS DMS를 활용해 DB 변경분을 실시간 동기화(CDC)한 후 주말 야간에 DNS를 스위칭하여 무중단 컷오버 완료.

#### 한줄 요약

- 자산 실사 $\to$ 가치 평가 $\to$ 전략 매핑 $\to$ Wave 수립 $\to$ 컷오버 전환의 5단계

## Ⅴ. 종류 및 비교

<details><summary>용어 설명</summary>

- **주요 3대 기술 이전 전략 비교**: Rehost(단순 이전), Replatform(부분 개선), Refactor(전면 현대화).

</details>

| 구분 | Rehost (Lift-and-Shift) | Replatform (Lift-and-Tweak) | Refactor (Cloud-Native) |
|:---|:---|:---|:---|
| **적용 기준** | 데이터센터 임대 만료 등 빠른 이관이 최우선 | 핵심 앱 코드는 안정적이나 DB 운영 부담 해소 | 트래픽 폭증 대응 및 고속 기능 배포 필요 |
| **핵심 특징** | **코드 수정 0%, 가장 빠른 이관 속도** | **관리형 DB(RDS) 도입, 중간 수준의 개선** | **MSA/서버리스 전면 재개발, 최대 탄력성** |
| **한계** | 기존 OS 및 레거시 기술 부채 그대로 잔존 | 플랫폼 연동을 위한 일부 설정 수정 필요 | 개발 기간 장기화 및 초기 개발 비용 과다 |

#### 한줄 요약

- 신속성은 Rehost, 운영 효율은 Replatform, 궁극의 확장성은 Refactor를 선택

## Ⅵ. 실무 고려사항 및 대책

<details><summary>용어 설명</summary>

- **CDC 기반 무중단 데이터 동기화**: 레거시 DB 운영 중 변경된 트랜잭션 로그를 클라우드 DB로 실시간 복제하여 컷오버 다운타임을 수 분 이내로 단축하는 기법.

</details>

| 문제 | 대책 | 효과 |
|:---|:---|:---|
| 모든 시스템을 무리하게 MSA로 재개발하려다 예산 초과 | **Rehost로 일단 신속 이관 후 2단계로 Refactor 분할 추진** | 프로젝트 성공률 극대화 및 리스크 분산 |
| 파악되지 않은 레거시 통신 의존성 누락으로 이관 후 장애 | **Discovery Service 기반 정밀 네트워크 의존성 맵 사전 분석** | 숨은 의존성 결함 사전 차단 |
| 대용량 데이터베이스 이관 시 장시간 서비스 다운타임 발생 | **AWS DMS (Data Migration Service) CDC 실시간 동기화 적용** | 컷오버 다운타임 수 분 이내 단축 |

#### 한줄 요약

- 2단계 접근법, 의존성 맵 분석, CDC 실시간 동기화를 통해 마이그레이션 실패 리스크를 제거

## Ⅶ. 결론

<details><summary>용어 설명</summary>

- **클라우드 현대화 로드맵(Modernization Roadmap)**: 6R 마이그레이션 완료 후 지속적으로 시스템을 컨테이너와 서버리스로 진화시키는 장기 엔지니어링 계획.

</details>

- **클라우드 마이그레이션 6R** 성공적인 디지털 전환을 이끄는 실증적 의사결정 프레임워크이며, 시스템별 비즈니스 가치와 복잡도를 정밀 분석하여 단계적이고 안전한 클라우드 현대화를 완수해야 함

#### 한줄 요약

- 6대 이전 전략을 체계적으로 수립하고 CDC 무중단 동기화를 결합하여 엔터프라이즈 클라우드 전환을 완성
