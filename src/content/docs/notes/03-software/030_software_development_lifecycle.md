## Ⅰ. 개요

<details>
<summary>핵심 용어</summary>

- **소프트웨어 개발 생명주기(Software Development Lifecycle, SDLC)**: 요구 식별부터 운영•폐기까지 개발 활동•산출물•승인을 관리하는 체계다.
- **산출물(Artifact)**: 생명주기 단계의 완료와 승인 근거를 담는 결과물이다.
- **추적성(Traceability)**: 요구와 설계•코드•시험 결과 사이의 연결 관계다.

</details>

- 정의/개념: 요구 식별부터 폐기까지 활동•산출물•승인을 통제하는 **SDLC 관리 체계**
- 배경/필요성: 산출물 연결이 없으면 변경 영향과 **재작업 범위 추적 불가**

#### 한줄 요약

- 요구부터 운영•폐기까지 **활동•산출물•승인** 통제

## Ⅱ. 특징

<details>
<summary>핵심 용어</summary>

- **단계 게이트(Stage Gate)**: 산출물과 승인 기준을 검사해 다음 생명주기 단계 진입을 허용하는 통제 지점이다.
- **피드백 루프(Feedback Loop)**: 운영 결과를 새 변경 요구와 개선 작업으로 되돌리는 순환 구조다.

</details>

- **단계 게이트** 로 진입•종료 조건 통제
- **요구 추적성** 으로 변경 영향•검증 범위 연결
- **피드백 루프** 로 운영 결과를 개선 요구에 반영

#### 한줄 요약

- 단계 게이트•추적성•**운영 피드백** 결합

## Ⅲ. 구조 및 구성요소

<details>
<summary>핵심 용어</summary>

- **생명주기 모델**: 요구•설계•구현•검증•운영 단계의 순서와 반복•전이 규칙을 정하는 틀이다.
- **승인 증적**: 단계 게이트를 통과한 근거와 승인 주체•시점을 보존한 기록이다.

</details>

```text
                         [생명주기 모델]
                                |
[산출물•추적성 저장소] -- [단계 게이트] -- [수행 활동]
```

선의 의미: 생명주기 모델은 단계 게이트의 통제 규칙을 정하고, 단계 게이트는 수행 활동과 산출물•추적성 저장소를 기준으로 진입·종료 조건을 관리한다.

| 구성요소 | 책임 |
|:---|:---|
| 생명주기 모델 | **단계 순서•반복•전이 규칙** 정의 |
| 단계 게이트 | **진입•종료•승인 조건** 통제 |
| 수행 활동 | **요구•설계•구현•검증•운영** 수행 |
| 산출물•추적성 저장소 | 결과•요구 연결과 **승인 증적** 보존 |

#### 한줄 요약

- 생명주기 모델•게이트•활동•**추적 저장소** 구조

## Ⅳ. 흐름도

<details>
<summary>핵심 용어</summary>

- **요구•추적 기준선 설정**: 요구와 수용 기준에 식별자를 부여해 후속 산출물 연결을 시작하는 단계다.
- **설계•구현 수행**: 승인 범위에 따라 구조를 설계하고 코드를 작성하는 단계다.
- **검증•증적 생성**: 시험•검토로 수용 기준 충족 여부와 잔여 위험을 입증하는 단계다.
- **단계 게이트 판정**: 기준 충족 시 릴리스하고 미충족 시 재작업 범위를 정하는 단계다.
- **운영 피드백•폐기 판정**: 운영 결과를 개선 요구로 돌리거나 종료 기준에 따라 시스템을 폐기하는 단계다.

</details>

```text
┌──────────────────────────────┐
│ 1. 요구•추적 기준선 설정   │◀──────────────┐
└──────────────┬───────────────┘               │
               ▼                               │
┌──────────────────────────────┐◀──────────┐   │
│ 2. 설계•구현 수행          │           │   │
└──────────────┬───────────────┘           │   │
               ▼                           │   │
┌──────────────────────────────┐           │   │
│ 3. 검증•증적 생성          │           │   │
└──────────────┬───────────────┘           │   │
               ▼                           │   │
┌──────────────────────────────┐           │   │
│ 4. 단계 게이트 판정        │           │   │
└───────┬──────────────────────┘           │   │
        ├─ 미충족 ─▶ [재작업 범위] ────────┘   │
        │ 충족                                  │
        ▼                                       │
     [릴리스•운영]                              │
        │                                       │
        ▼                                       │
┌──────────────────────────────┐               │
│ 5. 운영 피드백•폐기 판정   │               │
└───────┬──────────────────────┘               │
        ├─ 개선 ────────────────────────────────┘
        └─ 종료 ───────────────▶ [안전한 폐기]
```

**동작 원리**

- **1. 요구•추적 기준선 설정**: 요구•수용 기준 연결 시작
- **2. 설계•구현 수행**: 승인 범위의 구조•코드 작성
- **3. 검증•증적 생성**: 수용 기준과 잔여 위험 확인
- **4. 단계 게이트 판정**: 릴리스•재작업 경로 결정
- **5. 운영 피드백•폐기 판정**: 개선 환류•종료 선택

#### 한줄 요약

- 요구부터 운영 피드백•폐기까지 **생명주기 순환**

## Ⅴ. 종류 및 비교

<details>
<summary>핵심 용어</summary>

- **데브옵스(Development and Operations, DevOps)**: 개발•운영 협업과 자동화로 변경을 지속적으로 검증•배포하는 방식이다.
- **자동화 파이프라인(Automation Pipeline)**: 코드 변경을 빌드•시험•배포로 연속 처리하고 결과를 증적으로 남기는 흐름이다.
- **운영 결합도**: 개발 변경과 운영 환경•도구•절차가 서로 의존하는 정도다.

</details>

| 생명주기 운영 방식 | 단계 중심 SDLC | DevOps 연계 SDLC |
|:---|:---|:---|
| 적용 기준 | **규제•계약•감사** 우선 사업 | 빈번한 **변경•운영 피드백** 우선 |
| 핵심 특징 | **단계 게이트•산출물 승인** | **자동화 파이프라인•연속 피드백** |
| 한계 | 긴 **피드백 주기•변경 비용** | **통제 증적 누락•운영 결합도** 증가 |

> 요약: 감사 중심은 단계 통제, 변화 중심은 연속 피드백

#### 한줄 요약

- 감사 중심은 단계 게이트, 변화 중심은 **연속 피드백**

## Ⅵ. 실무 고려사항 및 대책

<details>
<summary>핵심 용어</summary>

- **변경 영향**: 한 요구나 코드 수정이 연결된 설계•시험•운영 대상에 미치는 범위다.
- **감사 증적(Audit Evidence)**: 요구•변경•시험•승인•배포가 정한 절차를 따랐음을 확인하는 기록이다.
- **서비스 수준 목표(Service Level Objective, SLO)**: 응답 시간•가용성 등 서비스 품질에 대해 달성하기로 정한 측정 목표다.
- **관측 데이터(Telemetry)**: 운영 상태를 파악하도록 수집한 로그•지표•추적 정보다.
- **수정 방지 감사 로그(Tamper-evident Audit Log)**: 변경•삭제 흔적을 검증할 수 있게 보호한 감사 기록이다.
- **역할 분리(Segregation of Duties)**: 개발•검토•승인 권한을 서로 다른 주체에 나눠 단독 변경을 제한하는 통제다.
- **개선 백로그(Improvement Backlog)**: 운영 피드백과 결함을 우선순위에 따라 정리한 후속 개선 작업 목록이다.

</details>

| 문제 | 대책 | 효과 |
|:---|:---|:---|
| 문서만 작성하고 요구•코드•시험의 **추적 링크 누락** | 요구•코드•시험 링크와 **변경 영향 자동 수집** | 변경별 **검증 범위 식별** |
| 모든 변경에 같은 단계 게이트를 적용해 **승인 대기 증가** | 위험•규제 등급별 **게이트•자동 검증** 적용 | 통제 강도별 **변경 대기시간** 절감 |
| 자동 배포에서 승인•**감사 증적 누락** | 수정 방지 감사 로그•**역할 분리•승인 보존** | DevOps의 **통제 이행 입증** |
| 운영 데이터가 개선 백로그로 **환류되지 않음** | **SLO•관측 데이터•사용자 영향** 으로 우선순위 결정 | 운영 결과의 **피드백 루프** 연결 |

#### 한줄 요약

- 요구 추적•위험별 게이트•**운영 환류** 적용

## Ⅶ. 결론

<details>
<summary>핵심 용어</summary>

- **연속 피드백**: 변경과 운영 결과를 짧은 주기로 다음 개발 활동에 반영하는 방식이다.

</details>

- 규제•감사 강도가 높으면 **단계 게이트**, 변경•운영 빈도가 높으면 **연속 피드백** 강화

#### 한줄 요약

- 감사 강도와 변화 속도에 맞는 **생명주기 운영 선택**
