## Ⅰ. 개요

<details><summary>용어 설명</summary>

- **SDLC (Software Development Lifecycle)**: 기획부터 뼈대 잡고, 코딩하고, 테스트하고, 유지보수하다가 무덤(폐기) 갈 때까지 소프트웨어의 전 생애를 멱살 잡고 끌고 가는 뼈대 프레임워크이다.
- **추적성(Traceability)**: 기획자가 써놓은 요구사항이 최종 소스코드랑 테스트 결과에 1:1로 잘 박혀 있는지 위아래로 집요하게 추적해서 "이거 안 만들었는데요?"를 막아내는 족보 시스템이다.
- **단계 게이트(Stage Gate)**: 기획 끝났다고 맘대로 개발 넘어가게 두지 않고, "문서 퀄리티 합격임?" 하고 검증한 뒤에 톨게이트를 열어주는 깐깐한 품질 관문이다.

</details>

- 정의: 요구사항부터 무덤(폐기)까지 개발 전 과정을 체계화해서 일정, 비용, 퀄리티 3마리 토끼의 멱살을 잡고 통제하는 **SDLC 프레임워크**
- 배경: 중간 톨게이트(기준선) 없이 주먹구구로 코딩하면, 나중에 **뭐가 누락됐는지도 모르고 책임 떠넘기기** 헬파티가 열리기 때문

#### 한줄 요약

- 기획부터 코딩, 폐기까지의 일정을 통제하고, 단계마다 퀄리티 톨게이트를 세워 버그를 막는 뼈대다.

## Ⅱ. 특징

<details><summary>용어 설명</summary>

- **산출물(Artifact)**: 각 톨게이트를 지날 때마다 "우리 이만큼 했어요" 하고 증거로 뱉어내야 하는 기획서, ERD, 아키텍처 문서, 테스트 결과서 같은 영수증이다.
- **피드백 루프(Feedback Loop)**: 코딩하다 보니까 설계가 개판이라 다시 기획/설계 단계로 빠꾸(Iteration) 쳐서 뜯어고치는 순환 구조이다.

</details>

- 단계별로 **산출물(Artifact)** 을 뱉어내고, **단계 게이트(Stage Gate)** 가 통과시켜 줘야 다음으로 넘어감.
- 요구사항 ➔ 설계 ➔ 코드 ➔ 테스트까지 잃어버린 자식 찾듯 **양방향 추적성(Traceability)** 을 사수함.
- 개발하다 이상하면 즉각 뒤로 빠꾸치는 **피드백 루프(Feedback Loop)** 를 깔고 감.

#### 한줄 요약

- 단계마다 산출물 검사받고, 요구사항이 테스트까지 이어지는 추적성(족보)을 챙기는 게 핵심이다.

## Ⅲ. 구조 및 구성요소

<details><summary>용어 설명</summary>

- **SDLC 모델(SDLC Models)**: 이 생명주기를 어떤 컨셉으로 굴릴지 정하는 뼈대로, 뒤도 안 돌아보는 폭포수(Waterfall)부터 매일 배포하는 애자일(Agile)까지 프로젝트 성격에 맞게 고르는 판이다.

</details>

```text
[ SDLC 산출물 및 추적성 십자포화 아키텍처 ]

[ 요구사항 ] ◀──(추적성)──▶ [ 테스트 케이스 ]
    │                            ▲
    ▼ (게이트 통과)               │
[ 아키텍처 설계 ] ◀─(추적성)─▶ [ 소스 코드 ]
    │                            ▲
    └────▶ [ 산출물 저장소 ] ◀────┘
       (모든 단계의 증거를 영구 보존)
```

| 구성요소 | 책임 |
|:---|:---|
| 생명주기 모델 | 폭포수(Waterfall)로 갈지, 애자일(Agile)로 갈지 프로젝트의 성격과 운명을 결정하는 큰 그림 |
| 수행 활동 | 기획, 설계, 코딩, 테스트, 유지보수 등 실무자들이 피땀 눈물 흘리며 갈아 넣는 태스크 |
| **단계 게이트** | 다음 단계로 넘어가기 전에 산출물 퀄리티를 검사하고 **빠꾸(Rework)** 먹일지 패스시킬지 결정하는 수문장 |
| 산출물·추적성 저장소 | 요구사항이 테스트까지 제대로 이어졌는지(추적성) 증거를 모아두고 나중에 감사(Audit) 때 들이미는 벙커 |

#### 한줄 요약

- SDLC 모델 위에서 코딩하고, 게이트에서 빠꾸먹고, 통과한 증거는 저장소에 영원히 박제된다.

## Ⅳ. 흐름도

<details><summary>용어 설명</summary>

- **V-모델(V-Model)**: "개발한 만큼 빡세게 테스트한다"는 마인드로, 기획엔 인수 테스트, 설계엔 통합 테스트를 1:1로 멱살 잡고 매핑시켜 검증을 극대화한 V자 모양의 FM 모델이다.

</details>

```text
[ SDLC 단계별 게이트 검증 십자포화 흐름 ]
┌──────────────────────────────┐
│ 1. 요구•추적 기준선 설정   │
│ (요구사항 문서화 및 ID 부여) │
└──────────────┬───────────────┘
               ▼ (기획 게이트 패스)
┌──────────────────────────────┐
│ 2. 설계•구현 (코딩) 수행   │
│ (아키텍처 짜고 깡코딩 갈김)  │
└──────────────┬───────────────┘
               ▼ (개발 게이트 패스)
┌──────────────────────────────┐
│ 3. V-Model 기반 대칭 검증  │
│ (단위/통합/시스템 테스트 팸) │
└──────────────┬───────────────┘
               ▼
┌──────────────────────────────┐
│ 4. 최종 단계 게이트 판정   │
│ (결함 컷 넘으면 패스, 아님 빠꾸)│
└───────┬───────────────┬──────┘
        │(기준 미달)    │(합격)
        ▼               ▼
  [재작업 (Rework)]   [5. 운영 및 폐기]
```

### 동작 원리

1. 요구·추적 기준선 설정: 고객 요구사항 다 받아적고, 나중에 추적할 수 있게 ID표(추적 매트릭스)를 땀.
2. 설계·구현 수행: 뼈대(아키텍처) 그리고 개발자들이 카페인 빨면서 깡코딩을 갈김.
3. 검증·증적 생성: 코딩 끝난 거 **V-Model**에 맞춰서 단위/통합/시스템 테스트로 오지게 패면서 버그를 잡음.
4. 단계 게이트 판정: 버그율 합격선 넘으면 라이브 릴리즈 패스, 퀄리티 개판이면 얄짤없이 **빠꾸(Rework)** 시킴.
5. 운영 피드백·폐기 판정: 서비스 오픈 후 피드백 받고, 더 이상 안 쓰면 DB 말소하고 서버 끄면서 장례식(폐기) 치름.

#### 한줄 요약

- 기획 따고 $\to$ 코딩하고 $\to$ 테스트 패고 $\to$ 퀄리티 합격하면 출시하고 늙으면 폐기한다.

## Ⅴ. 종류 및 비교

<details><summary>용어 설명</summary>

- **폭포수 모델(Waterfall Model)**: 폭포수 떨어지듯 앞 단계가 완벽히 끝나야 다음으로 넘어가는 쌍팔년도 FM 방식으로, 중간에 요구사항 바뀌면 피눈물 나는 구조이다.
- **애자일 / 데브옵스(Agile / DevOps)**: 길게 기획 안 하고 2주(Sprint) 단위로 일단 만들고 배포하면서 고객한테 욕먹고 고쳐나가는 현대 IT 씬의 무지성 생존 모델이다.

</details>

| 비교 항목 | **Waterfall Model** (폭포수) | **Spiral Model** (나선형) | **Agile / DevOps** (현대적) |
|:---|:---|:---|:---|
| 중심 철학 | 문서 빡세게 쓰고 완벽하게 계획대로 밀고 나감 | 리스크 터질까 봐 **위험 분석**에 벌벌 떨며 빙글빙글 돎 | **일단 만들어서 배포하고 반응 보면서 뜯어고침** |
| 리스크 관리 | 막판 테스트 때 버그 터지면 플젝 망하고 기도 메타 감 | **매 단계 위험 분석** 쑤셔 넣어서 폭망은 막음 | 2주 단위로 쪼개서 만들어서 망해도 타격 쥐꼬리만함 |
| 변경 수용성 | 설계 다 끝났는데 기획 바꾸면 개발자들 칼 들고 일어남 | 중간 (한 바퀴 돌 때마다 반영 가능) | **언제든 기획 엎어도 쿨하게 다음 2주 차에 반영함** |
| 최고존엄 무대 | 금융 차세대, 방산, 정부 공공기관 (오차 없어야 함) | 조 단위 들어가는 고위험 우주항공/연구개발(R&D) 플젝 | 스타트업, 배민/토스 같은 모바일 앱, 클라우드 |

#### 한줄 요약

- 빠꾸 없이 직진하는 건 폭포수, 리스크 쫄보는 나선형, 빠르고 유연하게 쳐내는 건 애자일이다.

## Ⅵ. 실무 고려사항 및 대책

<details><summary>용어 설명</summary>

- **시프트 레프트 테스팅(Shift-Left Testing)**: 다 만들고 막판에 테스트했다가 보안 털리고 버그 터지면 큰일 나니까, 아예 코딩 시작할 때(좌측)부터 보안/테스트(SAST, Unit Test)를 멱살 잡고 끌고 오는 트렌드이다.

</details>

| 문제 | 대책 | 효과 |
|:---|:---|:---|
| 다 만들고 테스트했더니 아키텍처부터 뜯어고쳐야 하는 재작업(Rework) 폭탄 터짐 | 테스트를 극초반(좌측)으로 땡겨버리는 **시프트 레프트(Shift-Left)** 전략 갈김 | 결함을 싹수부터 잘라서 후반부 디버깅 헬파티 원천 차단 |
| 꼰대들이 일일이 결재 서류 보고 단계 게이트 승인해주느라 배포가 한 세월 걸림 | **CI/CD 파이프라인**에 SonarQube 박아서 테스트 통과하면 **게이트 자동 패스**시킴 | 결재 도장 안 기다리고 하루에 10번씩 빛의 속도로 배포 쌉가능 |
| 기획자가 요구사항 슬쩍 바꿨는데 개발/테스트 어디까지 고쳐야 할지 감도 안 옴 | 엑셀이든 지라(Jira)든 **양방향 추적표(Traceability Matrix)** 멱살 잡고 갱신함 | 기획 하나 바뀌면 소스코드/테스트 케이스 영향도 스캔 1초 컷 |

#### 한줄 요약

- 테스트는 왼쪽(시작)으로 땡기고, 게이트는 CI/CD로 자동화하고, 요구사항은 추적표로 박제해라.

## Ⅶ. 결론

<details><summary>용어 설명</summary>

- **SDLC 프레임워크 선택 기준(SDLC Framework Adoption Criteria)**: 프로젝트가 사람 목숨 달린 규제 덩어리인지, 고객 변덕이 죽 끓듯 하는 스타트업인지 각 재서 폭포수와 애자일을 가르는 잣대이다.

</details>

- **SDLC 프레임워크 선택 기준** 원칙에 따라, 사람 목숨/돈 달린 보수적 인프라는 **Waterfall/V-Model**, 하루가 다르게 엎어지는 스타트업 서비스는 **Agile/DevOps** 채택 기조 확립함

#### 한줄 요약

- 금융/방산처럼 무거운 곳은 폭포수(Waterfall)로 가고, 가볍고 빠른 스타트업은 애자일(Agile)로 가라.
