## Ⅰ. 개요

<details><summary>용어 설명</summary>

- **SDLC(Software Development Life Cycle)**: 소프트웨어의 기획, 요구분석, 설계, 구현, 테스트, 배포, 유지보수, 폐기까지의 전 생애주기를 체계화한 프로세스 프레임워크.
- **단계 게이트(Stage Gate)**: 각 개발 단계의 산출물 품질과 진입/종료 기준(Entry/Exit Criteria)을 공식 심의하여 다음 단계 착수를 승인하는 관문.

</details>

- 정의/개념: 소프트웨어 계획부터 폐기까지 전 과정을 단계별로 정의하고 **단계 게이트(Stage Gate)** 기반으로 품질과 일정을 통제하는 공학 프레임워크
- 배경/필요성: 비정형 개발은 후반 결함 누적으로 **재작업 비용 폭증**

#### 한줄 요약
- 소프트웨어 전 수명주기를 정형화하고 단계 게이트를 통해 품질과 일정을 체계적으로 관리한다.

## Ⅱ. 특징

<details><summary>용어 설명</summary>

- **양방향 추적성(Bidirectional Traceability)**: 요구사항 ID부터 설계서, 소스 코드, 테스트 케이스까지 전후방 연계를 매핑하여 누락과 변경 영향을 파악하는 능력.
- **베이스라인(Baseline)**: 공식 심의를 거쳐 확정되어 이후 변경 시 엄격한 변경 통제 위원회(CCB) 절차를 거쳐야 하는 기준 산출물.

</details>

- 단계별 표준 **산출물(Artifact)** 정의 및 **단계 게이트(Stage Gate)** 승인을 통한 통제된 공정 진행
- 요구사항부터 테스트 케이스까지 **양방향 추적성(Traceability)** 확보를 통한 범위 변동 통제
- 프로젝트 위험도와 요구사항 변동성에 따른 다양한 수명주기 모델(Waterfall, Spiral, Agile) 적용

#### 한줄 요약
- 산출물 기준선 관리와 양방향 추적성 확보를 통해 변경 영향을 통제하고 품질을 보증한다.

## Ⅲ. 구조 및 구성요소

<details><summary>용어 설명</summary>

- **RTM(Requirements Traceability Matrix)**: 요구사항과 설계, 코드, 테스트 케이스 간의 연결성을 테이블 형태로 관리하는 요구사항 추적 매트릭스.

</details>

```text
[SDLC 공학적 수명주기 및 V-Model 구조]
|-- 요구사항 분석 (Requirements) <---------------- (인수 테스트: Acceptance Test)
|   `-- RTM 요구사항 기준선 확정
|-- 시스템/SW 아키텍처 설계 (Architecture) <-------- (시스템 테스트: System Test)
|   `-- 고수준/저수준 인터페이스 명세
|-- 모듈 상세 설계 (Detailed Design) <------------- (통합 테스트: Integration Test)
`-- 소프트웨어 구현 (Implementation) -------------> (단위 테스트: Unit Test)
    `-- 시큐어 코딩 및 정적 코드 분석
```

선의 의미: 계층 및 개발 단계와 테스트 단계 간 대칭적 검증/추적성 구조

| 구성요소 | 책임 |
|:---|:---|
| 프로세스 모델 | 위험·변동성별 **공정 전략 수립** |
| 핵심 엔지니어링 공정 | 분석·설계·구현·검증·릴리즈 수행 |
| 단계 게이트 | 산출물 심의와 **베이스라인 확정** |
| RTM 형상 관리자 | 요구·테스트의 **양방향 추적성 유지** |

#### 한줄 요약
- 개발 공정과 V-Model 대칭 검증, 단계 게이트, RTM 형상 관리가 결합된다.

## Ⅳ. 흐름도

<details><summary>용어 설명</summary>

- **V-Model**: 요구분석-설계-구현과 단위-통합-시스템-인수 테스트를 1:1로 매핑하여 단계별 검증 책임을 명확히 한 SDLC 모델.

</details>

```text
비즈니스 요구사항 분석 및 RTM 기준선 수립
        │
   요구사항 단계 게이트(Stage Gate) 통과 및 승인
        │
   시스템 및 모듈 아키텍처 설계
        │
   설계 단계 게이트 통과 및 인터페이스 확정
        │
   소프트웨어 구현 및 시큐어 코딩 (정적 분석)
        │
   V-Model 기반 계층적 테스트 수행 (단위 -> 통합 -> 시스템 -> 인수 테스트)
        │
   최종 품질 게이트(Quality Gate) 승인 및 운영 배포
```

#### 한줄 요약
- 요구분석 → 설계 → 구현 → V-Model 계층 검증 → 단계 게이트 승인 후 배포 순으로 진행된다.

## Ⅴ. 종류 및 비교

<details><summary>용어 설명</summary>

- **폭포수 vs 나선형 vs 애자일**: 선형 순차적 폭포수, 위험 분석 반복 나선형, 1~4주 반복 점증 배포 애자일.

</details>

| SDLC 모델 | 폭포수 모델 (Waterfall) | 나선형 모델 (Spiral) | 애자일 모델 (Agile/Scrum) |
|:---|:---|:---|:---|
| 요구사항 명확성 | **초기 확정 필수 (변경 통제)** | 점진적 구체화 | **빈번한 변경 수용** |
| 위험 관리 방식 | 후반부 테스트 시 위험 발견 | **반복 주기마다 위험 분석 선행** | 매 스프린트 데모/회고로 위험 제거 |
| 릴리즈 주기 | 프로젝트 종료 시 일괄 배포 | 프로토타입 단계별 배포 | **1~4주 스프린트 단위 점진 릴리즈** |
| 적합한 프로젝트 | 금융 기간계, 국방, 규제 필수 시스템 | 대규모 R&D, 고위험 국책 사업 | 스타트업, 이커머스, 웹/모바일 서비스 |

#### 한줄 요약
- 요구사항이 명확하면 폭포수, 기술 불확실성이 크면 나선형, 시장 출시 속도가 중요하면 애자일을 선택한다.

## Ⅵ. 실무 고려사항 및 대책

<details><summary>용어 설명</summary>

- **Shift-Left(시프트 레프트)**: 테스트 및 보안 검증을 프로젝트 후반부가 아닌 요구분석/설계/구현 초기 단계로 앞당겨 결함을 조기 제거하는 전략.

</details>

| 문제 | 대책 | 효과 |
|:---|:---|:---|
| 개발 후반부 결함 집중으로 인한 납기 지연 및 비용 폭증 | 단위 테스트 자동화 및 TDD 기반 **시프트 레프트(Shift-Left)** | 초기 결함 제거율 80% 달성 및 재작업 비용 절감 |
| 수동 문서 승인으로 인한 배포 병목 | **CI/CD 파이프라인 내 정적 분석 및 자동 품질 게이트** 구축 | 검증 자동화 및 일일 수십 회 무중단 배포 |
| 요구사항 변경 시 영향도 파악 불가로 인한 회귀 결함 | JIRA/Git 기반 **양방향 추적성 매트릭스(RTM)** 자동화 | 변경 영향 범위 정밀 식별 및 누락 0화 |
| 설계와 실제 구현 코드의 불일치(Architecture Erosion) | 아키텍처 적합성 검증 도구(ArchUnit) CI 연동 | 아키텍처 규칙 위반 시 빌드 자동 실패 |

#### 한줄 요약
- 시프트 레프트 조기 검증, CI/CD 품질 게이트 자동화, RTM 추적성 확립으로 품질을 보장한다.

## Ⅶ. 결론

- 규제 시스템은 **폭포수/V-Model**, 신속 배포는 **Agile** 선택

#### 한줄 요약
- SDLC는 프로젝트의 도메인 특성과 위험도에 부합하는 프로세스 모델을 선정하고 지속적 품질 통제를 체계화하는 엔지니어링 표준이다.
