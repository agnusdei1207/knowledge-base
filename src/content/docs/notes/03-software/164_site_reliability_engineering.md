## Ⅰ. 개요

<details><summary>용어 설명</summary>

- **SRE(Site Reliability Engineering)**: 구글이 정립한 모델로, 소프트웨어 엔지니어링 방법론을 대규모 IT 운영에 적용하여 SLI/SLO 및 오류 예산(Error Budget) 기반으로 시스템 신뢰성을 관리하는 실천 체계.
- **개발-운영 이해관계 충돌(Dev vs Ops Conflict)**: 빠른 기능 출시(Feature Velocity)를 추구하는 개발팀과 무중단 안정성(System Stability)을 추구하는 운영팀 간의 갈등 및 정량적 의사결정 기준 부재의 한계.

</details>

- 정의/개념: 소프트웨어 엔지니어링 방법론을 인프라 운영에 적용하여 **SLI/SLO 및 오류 예산(Error Budget) 기반으로 신뢰성을 관리**하는 운영 프레임워크
- 배경/필요성: 개발팀의 빠른 신기능 배포 속도 요구와 운영팀의 시스템 안정성 요구 간의 **이해관계 충돌 및 정량적 의사결정 기준 부재 위험** 직면

#### 한줄 요약

- SLI/SLO 측정과 오류 예산(Error Budget)이라는 수학적 지표를 통해 개발 속도와 시스템 신뢰성의 최적 균형을 달성

## Ⅱ. 특징

<details><summary>용어 설명</summary>

- **토일 감축(Toil Reduction 50% Rule)**: 수작업으로 반복되는 가치 없는 운영 업무(Toil)를 엔지니어 업무의 50% 이하로 제한하고 나머지는 자동화 코드 개발에 투자.
- **비난 없는 사후 회고(Blameless Postmortem)**: 장애 발생 시 담당자를 문책하지 않고 시스템적·절차적 결함을 찾아내어 근본적인 재발 방지 코드를 작성하는 문화.

</details>

- 100% 가용성이 아닌 사용자가 만족하는 수준을 목표로 삼는 **SLI/SLO 기반 정량 관리**
- 오류 예산 잔여량에 따라 신규 기능 배포와 안정화 작업을 조율하는 **Error Budgeting**
- 단순 반복 수작업 운영을 소프트웨어 코드로 대체하는 **운영 업무의 엔지니어링화(Toil 자동화)**

#### 한줄 요약

- 데이터 기반 신뢰성 관리와 비난 없는 사후 분석을 통해 조직의 지속 가능한 고속 성장을 지원

## Ⅲ. 구조 및 구성요소

<details><summary>용어 설명</summary>

- **SRE 5대 핵심 축**: SLI(지표), SLO(목표), Error Budget(오류 예산), Toil Automation(자동화), Blameless Postmortem(문화).

</details>

```text
[ SRE 핵심 프레임워크 및 의사결정 구조도 ]

 1. [ 측정 계층 (Measurement Layer) ]
    • SLI (Service Level Indicator): 사용자 관점의 실제 성공률 (99.95%)
                     │
                     ▼
 2. [ 목표 및 의사결정 계층 (Decision Layer) ]
    • SLO (Service Level Objective): 비즈니스 합의 목표 (99.90%)
    • Error Budget (오류 예산): 100% - SLO = 0.10% (월간 허용 다운타임 43분)
                     │
        ┌────────────┴────────────┐
        ▼ (예산 잔여: 여유)       ▼ (예산 소진: 위험)
 3. [ 신규 기능 배포 허용 ]     [ 배포 동결 및 안정화/Toil 자동화 전환 ]
                     │
                     ▼
 4. [ Blameless Postmortem & Toil Reduction (재발 방지 소프트웨어 개발) ]
```

선의 의미: SLI/SLO 측정을 통해 오류 예산을 산출하고 예산 잔여량에 따라 배포 허용 또는 안정화 작업을 결정하는 구조.

| 구성요소 | 책임 |
|:---|:---|
| 서비스 수준 지표 (SLI) | 사용자 관점에서 서비스가 정상 동작하는지 **가용성, 지연시간, 처리량을 정량 측정** |
| 서비스 수준 목표 (SLO) | 비즈니스 가치와 엔지니어링 비용을 고려하여 **팀 간에 합의한 신뢰성 목표치 설정** |
| 오류 예산 (Error Budget) | `100% - SLO`로 계산되는 허용 가능한 실패 한도로 **개발과 운영의 배포 기준 제공** |
| 토일 자동화 (Toil) | 반복적인 수작업 운영 업무를 **Terraform/Ansible 등 자동화 코드로 개발하여 50% 미만 억제** |
| 비난 없는 회고 (Postmortem)| 장애 원인을 사람의 실수가 아닌 **시스템 결함 관점에서 분석하고 재발 방지 조치 문서화** |

#### 한줄 요약

- SLI, SLO, 오류 예산, 토일 자동화, 비난 없는 회고가 결합하여 SRE 거버넌스를 완성

## Ⅳ. 흐름도

<details><summary>용어 설명</summary>

- **SRE 오류 예산 기반 배포 거버넌스 5단계**: SLI 실시간 측정 $\to$ SLO 대비 예산 계산 $\to$ Burn Rate(소진 속도) 평가 $\to$ 배포/안정화 결정 $\to$ 개선 조치 실행.

</details>

```text
[ SRE 오류 예산 기반 의사결정 파이프라인 ]

 ┌────────────────────────────────────────┐
 │ 1. Prometheus / OTel 기반 SLI 실시간 측정│
 └───────────────────┬────────────────────┘
                     │
                     ▼
 ┌────────────────────────────────────────┐
 │ 2. SLO 대비 잔여 Error Budget 및 Burn Rate 계산
 └───────────────────┬────────────────────┘
                     │
                     ▼
 ┌────────────────────────────────────────┐
 │ 3. 의사결정 분기: Burn Rate 임계치 초과 여부
 ├───────────────────┬────────────────────┤
 │ 정상 (예산 여유)  │ 위험 (예산 급소진) │
 │ 4A. 신규 기능 배포│ 4B. 신규 배포 동결 │
 │     정상 진행     │     안정화 작업 전환
 └───────────────────┴────────────────────┘
                     │
                     ▼
 ┌────────────────────────────────────────┐
 │ 5. Blameless Postmortem 및 Toil 자동화 개발
 └────────────────────────────────────────┘
```

### 동작 원리

1. SLI 측정: API Gateway 및 APM 지표를 통해 성공한 HTTP 200 요청의 비율을 실시간 계산.
2. 예산 계산: 당월 허용된 총 다운타임(43분) 중 잔여 오류 예산과 소진 속도(Burn Rate)를 분석.
3. 분기 판정: Burn Rate가 1배수 이하로 안전하면 정상 배포를 진행하고, 14.4배수 이상 급소진 시 경보를 발령.
4. 조치 실행: 예산이 고갈된 경우 신규 기능 배포를 일시 동결하고 버그 수정, 롤백, 성능 개선에 집중.
5. 시스템 개선: 장애 복구 후 비난 없는 회고 문서를 작성하고 Toil을 제거하는 자동화 스크립트를 작성.

#### 한줄 요약

- SLI 측정 $\to$ 예산/Burn Rate 계산 $\to$ 위험도 분기 $\to$ 배포/안정화 결정 $\to$ Toil 자동화의 5단계

## Ⅴ. 종류 및 비교

<details><summary>용어 설명</summary>

- **DevOps vs SRE**: 문화적 철학과 소통 강조(DevOps)와 이를 수학적 지표(SLO)와 소프트웨어 엔지니어링으로 구체화한 실천 직무(SRE).

</details>

| 구분 | 데브옵스 (DevOps) | 사이트 신뢰성 공학 (SRE) |
|:---|:---|:---|
| **적용 기준** | 개발과 운영의 사일로(Silo)를 허물고 협업 문화를 정착시키려는 조직 | 대규모 분산 시스템에서 수학적 지표 기반으로 신뢰성을 보장하려는 조직 |
| **핵심 특징** | **문화적 철학, CI/CD 자동화 강조, 소통 및 협업** | **DevOps 철학을 구현하는 구체적 엔지니어링 직무 (Class SRE)** |
| **한계** | 신뢰성과 배포 속도 간 갈등 발생 시 정량적 판정 기준 모호 | SLI/SLO 설계 역량 필요 및 고숙련 소프트웨어 엔지니어링 인력 요구 |

#### 한줄 요약

- 철학과 문화는 DevOps, 이를 구체적인 지표(SLO)와 자동화 코드로 구현한 것은 SRE

## Ⅵ. 실무 고려사항 및 대책

<details><summary>용어 설명</summary>

- **경보 피로(Alert Fatigue)**: 사소한 CPU/메모리 스파이크마다 울리는 불필요한 알람으로 인해 온콜 엔지니어가 실제 중요 장애를 놓치는 현상.

</details>

| 문제 | 대책 | 효과 |
|:---|:---|:---|
| 단순 인프라 CPU 알람 폭증으로 온콜 엔지니어 경보 피로 유발 | **SLI/SLO 기반 다중 윈도우 Burn Rate 알람 체계로 전면 전환** | 불필요한 노이즈 알람 90% 차단 |
| 수작업 배포 및 권한 승인 업무(Toil) 과다로 개발 업무 마비 | **SRE 엔지니어링 업무 중 Toil 비중 50% 상한선 엄격 제한** | Toil 자동화 코드 개발 시간 50% 이상 확보 |
| 장애 발생 시 부서 간 책임 전가 및 범인 색출 문화 | **`Blameless Postmortem` 문화 정착 및 재발 방지 액션 아이템 수립** | 조직 심리적 안정감 및 시스템 복원력 확보 |

#### 한줄 요약

- Burn Rate 기반 경보 통합, Toil 50% 상한제, 비난 없는 사후 회고를 통해 SRE 문화를 정착

## Ⅶ. 결론

<details><summary>용어 설명</summary>

- **지속 가능한 신뢰성 엔지니어링(Sustainable Reliability Engineering)**: 시스템 규모가 10배 성장해도 운영 인력은 선형 증가하지 않도록 소프트웨어로 문제를 해결하는 SRE 궁극의 지향점.

</details>

- **사이트 신뢰성 공학(SRE)** 은 현대 클라우드 운영의 표준 엔지니어링 패러다임이며, SLI/SLO와 오류 예산을 통해 개발 속도와 안정성을 수학적으로 양립시키고 Toil 자동화를 지속 실천해야 함

#### 한줄 요약

- SLI/SLO 정량 지표와 오류 예산 거버넌스를 통해 시스템 신뢰성과 개발 생산성을 완성
