## Ⅰ. 개요

<details><summary>용어 설명</summary>

- **UML (Unified Modeling Language)**: 개발자, 기획자, 아키텍트가 서로 딴소리 안 하게 소프트웨어의 뼈대(정적 구조)와 움직임(동적 행위)을 표준화된 기호로 그려내는 국제 공통 설계 도면이다.
- **구조 다이어그램 (Structural Diagrams)**: 건물의 철골 뼈대나 벽면처럼 프로그램이 멈춰 있을 때 클래스와 컴포넌트가 어떻게 생겨먹고 엮여 있는지 보여주는 정적(Static) 설계도이다.
- **행위 다이어그램 (Behavioral Diagrams)**: 건물의 엘리베이터나 사람의 이동선처럼 프로그램이 실행(Run)될 때 객체들이 어떻게 메시지를 주고받고 상태가 변하는지 보여주는 동적(Dynamic) 설계도이다.

</details>

- 정의: 멈춰있는 뼈대(구조)와 살아 숨 쉬는 움직임(행위)을 OMG 국제 표준 기호로 그려내는 객체지향 설계 공통 언어인 **UML(Unified Modeling Language)**
- 배경: 말이나 글로만 기획을 던지면, 찰떡같이 말해도 개떡같이 알아듣는 **설계 해석 불일치** 심각한 결함가 터지기 때문

#### 한줄 요약

- 서로 딴소리 못하게, 객체의 뼈대와 움직임을 전 세계 공통 기호로 그려놓은 설계 표준이다.

## Ⅱ. 특징

<details><summary>용어 설명</summary>

- **OMG (Object Management Group)**: UML 기호를 "화살표는 점선으로 해라, 실선으로 해라"라고 전 세계 룰을 깐깐하게 통제하고 표준을 관리하는 국제 컨소시엄이다.
- **시퀀스 다이어그램 (Sequence Diagram)**: 객체들이 시간 순서대로 위에서 아래로 서로 무슨 메시지(API 호출)를 핑퐁으로 주고받는지 까발려주는 1티어 핵심 행위 다이어그램이다.

</details>

- 크게 뼈대(정적 구조)와 움직임(동적 행위) 2가지 관점에서 **총 14개의 다이어그램 무기** 활용 제공함.
- UML만 잘 그려놓으면 코드로 자동 변환(MDA)까지 노려볼 수 있을 만큼 **정교한 설계 호환성** 자랑함.
- 전 세계 어디서든 **OMG 국제 표준 표기법** 하나로 통하는 압도적 가독성을 제공함.

#### 한줄 요약

- 구조와 행위 2가지 맛으로 총 14개 도면을 제공하며, OMG 룰로 전 세계 어딜 가나 통한다.

## Ⅲ. 구조 및 구성요소

<details><summary>용어 설명</summary>

- **클래스 다이어그램 (Class Diagram)**: 시스템을 구성하는 클래스들이 필드(변수)와 메서드(함수)를 얼마나 갖고 있고, 서로 어떻게 의존/상속하며 얽혀 있는지 보여주는 1티어 핵심 구조 다이어그램이다.

</details>

```text
[ UML 14종 다이어그램 십자포화 트리 구조 ]

                     [ UML 다이어그램 ]
                      /              \
    [ 구조(Structural) 다이어그램 ]     [ 행위(Behavioral) 다이어그램 ]
   (멈춰있는 뼈대: 클래스, 컴포넌트)              │
                                              ▼
                                   [ 상호작용(Interaction) 다이어그램 ]
                                 (객체 간 핑퐁: 시퀀스, 커뮤니케이션)
```

| 구성요소 | 책임 |
|:---|:---|
| **UML 다이어그램** | "네모는 클래스, 화살표는 상속" 등 전 세계 개발자가 끄덕이는 표준 규약의 총집합 |
| **구조 다이어그램** | 멈춰 있는 프로그램의 뼈대(클래스, 패키지, 배포 서버)를 정적(Static)으로 박제함 |
| **행위 다이어그램** | 돌아가는 프로그램의 로직(상태 변화, 유스케이스)을 동적(Dynamic)으로 시각화함 |
| **상호작용 다이어그램** | 행위의 하위 개념으로, 객체끼리 "데이터 내놔", "여기 있어" 메시지 핑퐁을 그림 |

#### 한줄 요약

- 멈춰있는 건 구조 도면으로, 움직이는 건 행위(상호작용) 도면으로 찢어서 그린다.

## Ⅳ. 흐름도

<details><summary>용어 설명</summary>

- **일반화 vs 실체화 (Generalization vs Realization)**: 일반화(실선+빈 화살표)는 부모의 재산을 물려받는 상속(IS-A) 관계고, 실체화(점선+빈 화살표)는 껍데기뿐인 인터페이스를 찐으로 구현(Implementation)하는 관계이다.

</details>

```text
[ UML 설계 및 표기 십자포화 흐름 ]
┌──────────────────────────────┐
│ 1. 정적 vs 동적 관점 판정    │
│ (뼈대 그릴래? 로직 그릴래?)  │
└──────────────┬───────────────┘
               ▼
┌──────────────────────────────┐
│ 2. 구조(Structure) 설계      │
│ (클래스 다이어그램으로 뼈대 그림)│
└──────────────┬───────────────┘
               ▼
┌──────────────────────────────┐
│ 3. 행위(Behavior) 설계       │
│ (시퀀스로 호출 로직과 시간 그림)│
└──────────────┬───────────────┘
               ▼
┌──────────────────────────────┐
│ 4. OMG 표준 화살표 정립      │
│ (상속, 의존 등 깐깐하게 선 그음)│
└──────────────────────────────┘
```

### 동작 원리

1. 정적/동적 판정: DB 구조나 클래스 뼈대(정적)를 그릴지, API 호출 순서(동적)를 그릴지 타겟을 정함.
2. 구조 다이어그램 작성: 클래스의 변수(필드), 함수(메서드)를 네모칸에 박아 넣고 뼈대를 짬.
3. 행위 다이어그램 작성: 시퀀스 위에서 아래로 시간 긋고, 점선과 실선으로 비동기/동기 호출을 날림.
4. 관계 표기법 정립: 포함, 합성, 의존 화살표를 OMG 룰에 맞게 깐깐하게 그려서 오해를 차단함.

#### 한줄 요약

- 뼈대 그릴지 로직 그릴지 정하고 $\to$ 도형 배치하고 $\to$ OMG 화살표 룰에 맞춰 선을 잇는다.

## Ⅴ. 종류 및 비교

<details><summary>용어 설명</summary>

- **합성 vs 집합 (Composition vs Aggregation)**: 합성(검은 마름모)은 건물과 방처럼 부모가 죽으면 자식도 같이 뒈지는 빡센 생명주기 공유 관계고, 집합(빈 마름모)은 회사와 직원처럼 회사가 망해도 직원은 딴 데로 튀는 느슨한 관계이다.

</details>

| 관계 표기법 | 의미 (직관적 비교) | OMG 선 형태 및 화살표 룰 |
|:---|:---|:---|
| **일반화 (Generalization)** | 부모 클래스를 그대로 상속받는 IS-A 관계 | 실선 + 빈 삼각형 화살표 (`──▷`) |
| **실체화 (Realization)** | 빈껍데기 인터페이스를 실체(구현)로 만드는 관계 | 점선 + 빈 삼각형 화살표 (`--▷`) |
| **의존 (Dependency)** | 함수 파라미터 정도로 잠깐 쓰고 버리는 얕은 관계 | 점선 + 일반 화살표 (`-->`) |
| **합성 (Composition)** | 부모 죽으면 자식 메모리도 같이 날아가는 빡센 포함 관계 | 실선 + **검은 마름모** (`──◆`) |
| **집합 (Aggregation)** | 부모가 죽어도 자식은 독립적으로 살아남는 약한 포함 관계 | 실선 + 빈 마름모 (`──◇`) |

#### 한줄 요약

- 실선/점선, 꽉 찬 마름모/빈 마름모 하나 차이로 코드의 생사가 결정되는 빡센 룰이다.

## Ⅵ. 실무 고려사항 및 대책

<details><summary>용어 설명</summary>

- **모델 드리프트 (Model-Implementation Drift)**: 플젝 초반엔 예쁘게 UML 그려놓고, 나중에 코드 바꿀 때 갱신을 안 해서 결국 UML 문서가 예쁜 쓰레기(거짓말)가 되어버리는 설계 부패 현상이다.

</details>

| 문제 | 대책 | 효과 |
|:---|:---|:---|
| 코딩할 시간도 없는데 UML 14개 다 그리라고 강요함 | **애자일 모델링**: 뼈대(클래스)랑 로직(시퀀스) 딱 2개만 최소한으로 그림 | 엑기스만 뽑아내 시간 낭비 방어 |
| 코드는 뜯어고쳤는데 UML은 안 고쳐서 도면이 씹창남 (**모델 드리프트**) | **리버스 엔지니어링(역공학)** 툴 돌려서 코드에서 UML을 역으로 뽑아냄 | 코드와 도면 간 100% 싱크 유지 |
| 마우스로 네모 박스 예쁘게 그리느라 야근함 | **PlantUML, Mermaid** 같은 Diagram-as-Code (텍스트 기반) 툴 떡칠 | 마우스 노가다 없애고 Git 버전 관리 가능 |

#### 한줄 요약

- 14개 다 그리지 말고 꼭 필요한 것만 코드로 짜서(PlantUML) 역공학으로 싱크 맞춰라.

## Ⅶ. 결론

<details><summary>용어 설명</summary>

- **UML 선택 기준(UML Diagram Selection Criteria)**: 시스템의 정적인 뼈대를 설명해야 할 때인지, 아니면 동적인 런타임 이벤트(누가 누굴 호출하는지)를 설명해야 할 때인지 각을 재서 다이어그램을 고르는 잣대이다.

</details>

- **UML 선택 기준** 원칙에 따라, 객체 필드/메서드 뼈대 잡을 땐 **Class Diagram(구조)**, 복잡한 비동기 API 호출 핑퐁을 깔 땐 **Sequence Diagram(행위)** 채택 기조 확립함

#### 한줄 요약

- 뼈대를 보여주고 싶으면 클래스 다이어그램, 핑퐁하는 움직임을 보여주고 싶으면 시퀀스를 깔아라.
