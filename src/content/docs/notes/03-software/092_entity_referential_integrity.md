## Ⅰ. 개요

<details><summary>용어 설명</summary>

- **개체 무결성 및 참조 무결성(Entity & Referential Integrity)**: 릴레이션 내 튜플의 유일한 식별을 보장하는 기본키(PK) 제약과 릴레이션 간의 유효한 관계를 보장하는 외래키(FK) 제약.
- **튜플 식별 불능 및 고아 레코드(Identification Failure & Orphan Record)**: 기본키 중복이나 부모 데이터 삭제 후 자식 테이블에 고립된 데이터가 남아 정합성이 파괴되는 현상.

</details>

- 정의/개념: 관계형 데이터베이스에서 튜플의 유일한 식별을 보장하는 **개체 무결성(PK Not Null & Unique)과 릴레이션 간 연관성을 유지하는 참조 무결성(FK)** 제약 규칙
- 배경/필요성: 기본키 중복 및 유효하지 않은 외래키 참조로 인한 **튜플 식별 불능, 부모 없는 고아 레코드(Orphan) 발생 및 데이터 부정합 위험** 직면

#### 한줄 요약

- 기본키 기반 개체 무결성과 외래키 기반 참조 무결성을 통해 관계형 데이터베이스의 핵심 정합성을 보장

## Ⅱ. 특징

<details><summary>용어 설명</summary>

- **기본키 제약(PK Constraint)**: 개체 무결성의 핵심으로 기본키를 구성하는 속성은 절대 중복될 수 없고 `NULL` 값을 허용하지 않음.
- **참조 유효성(Referential Validity)**: 외래키 값은 참조 대상 부모 테이블의 기본키 값과 정확히 일치하거나 `NULL`이어야 함.

</details>

- 기본키(PK)를 통한 **튜플의 유일성(Uniqueness) 및 Not Null 보장 (개체 무결성)**
- 외래키(FK)를 통한 **부모-자식 간 관계 일관성 및 고아 데이터 방지 (참조 무결성)**
- 부모 데이터 수정/삭제 시 **연쇄 동작(RESTRICT, CASCADE, SET NULL) 제어**

#### 한줄 요약

- 개체 무결성으로 튜플 식별자를 확립하고 참조 무결성으로 테이블 간 연결을 검증

## Ⅲ. 구조 및 구성요소

<details><summary>용어 설명</summary>

- **부모-자식 관계(Parent-Child Relation)**: 기본키를 소유한 부모 릴레이션과 이를 외래키로 참조하는 자식 릴레이션 간의 구조적 바인딩.

</details>

```text
[ 개체 무결성 및 참조 무결성 상호 작용 구조도 ]

  [ 부모 릴레이션: Users ]
  ┌────────────────────────────────────────────────────────┐
  │ 기본키(PK): user_id (1001) ◄── [개체 무결성: Unique & Not Null]
  └───────────▲────────────────────────────────────────────┘
              │ (참조 무결성: FK 값은 부모 PK 존재값 또는 Null)
  [ 자식 릴레이션: Orders ]
  ┌───────────┴────────────────────────────────────────────┐
  │ 기본키(PK): order_id (5001) | 외래키(FK): user_id (1001)│
  └────────────────────────────────────────────────────────┘
```

선의 의미: 부모 테이블의 PK에 개체 무결성이 적용되고, 자식 테이블의 FK가 이를 참조하여 참조 무결성을 유지하는 구조.

| 구성요소 | 책임 |
|:---|:---|
| 기본키 (Primary Key) | 릴레이션 내 튜플의 유일 식별을 위해 **중복 배제 및 Not Null 강제 (개체 무결성)** |
| 외래키 (Foreign Key) | 부모 테이블의 PK를 참조하여 **유효한 값만 허용하고 고아 데이터 방지 (참조 무결성)** |
| 참조 제약 정책 (Actions) | 부모 레코드 삭제/수정 시 **RESTRICT, CASCADE, SET NULL 연쇄 동작 제어** |
| 외래키 인덱스 (FK Index) | 부모 삭제 및 조인 시 빠른 탐색을 위해 **자식 FK 컬럼에 B-Tree 인덱스 생성** |

#### 한줄 요약

- 기본키는 튜플의 고유 식별을, 외래키는 부모-자식 간 연결 정합성을 각각 전담

## Ⅳ. 흐름도

<details><summary>용어 설명</summary>

- **참조 무결성 연쇄 처리 절차**: 부모 레코드 변경 요청 시 자식 테이블의 FK 존재 여부를 확인하고 정책에 따라 삭제 거부 또는 연쇄 변경을 수행하는 흐름.

</details>

```text
[ 부모 데이터 삭제 시 참조 무결성 검증 파이프라인 ]

 ┌────────────────────────────────────────┐
 │ 1. 부모 튜플 삭제(DELETE) 요청 접수    │
 └───────────────────┬────────────────────┘
                     │
                     ▼
 ┌────────────────────────────────────────┐
 │ 2. 자식 테이블 FK 참조 레코드 존재 확인│
 └───────────────────┬────────────────────┘
                     │ (참조 데이터 발견 시)
                     ▼
 ┌────────────────────────────────────────┐
 │ 3. DDL 선언 정책(ON DELETE) 분기 판정  │
 ├───────────────────┬────────────────────┤
 │ RESTRICT (기본값) │ CASCADE / SET NULL │
 │ (삭제 차단 및 롤백│ (자식 연쇄 삭제/널)│
 └───────────────────┴────────────────────┘
```

### 동작 원리

1. 부모 삭제 요청: 부모 테이블의 특정 행을 삭제하려는 DML 쿼리가 실행.
2. 자식 FK 탐색: DBMS 엔진이 자식 테이블의 외래키 인덱스를 조회하여 해당 기본키를 참조하는 자식 레코드가 있는지 검사.
3. 정책 분기 판정: 자식 레코드가 존재할 경우 선언된 `ON DELETE` 옵션에 따라 분기.
4. 예외 차단: `RESTRICT`인 경우 삭제를 거부하고 트랜잭션을 롤백하여 고아 데이터 발생을 차단.
5. 연쇄 반영: `CASCADE`인 경우 자식 레코드를 함께 삭제하고, `SET NULL`인 경우 자식 외래키를 Null로 갱신.

#### 한줄 요약

- 부모 삭제 요청 $\to$ 자식 FK 검사 $\to$ 정책 판정 $\to$ RESTRICT(롤백) 또는 CASCADE(연쇄 처리)

## Ⅴ. 종류 및 비교

<details><summary>용어 설명</summary>

- **개체 무결성 vs 참조 무결성**: 단일 테이블 내부의 행 식별자를 다루는 개체 무결성과 테이블 간의 관계 무결성을 다루는 참조 무결성.

</details>

| 구분 | 개체 무결성 (Entity Integrity) | 참조 무결성 (Referential Integrity) |
|:---|:---|:---|
| **적용 기준** | 단일 릴레이션 내부의 행 식별 기준 확립 | 두 릴레이션 간의 부모-자식 관계 연결 |
| **핵심 특징** | **기본키(PK)에 대한 NOT NULL 및 UNIQUE 강제** | **외래키(FK)의 유효성 검증 및 ON DELETE 연쇄 제어** |
| **한계** | 복합 자연키 사용 시 갱신 오버헤드 발생 | FK 인덱스 부재 시 부모 삭제 시 Table Lock 지연 |

#### 한줄 요약

- 개체 무결성은 테이블 내부 행의 유일성을 지키고, 참조 무결성은 테이블 간의 연결을 지킴

## Ⅵ. 실무 고려사항 및 대책

<details><summary>용어 설명</summary>

- **대리키(Surrogate Key)**: 비즈니스 의미가 있는 자연키(주민번호, 이메일) 대신 Auto-Increment ID나 UUID를 PK로 사용하여 개체 무결성의 불변성을 확보하는 기법.

</details>

| 문제 | 대책 | 효과 |
|:---|:---|:---|
| 자연키(이메일 등) PK 변경 시 개체/참조 무결성 연쇄 파행 | **불변 대리키(Surrogate Key: Auto-Increment/UUID)를 PK로 사용** | 기본키의 불변성 및 식별 안정성 확보 |
| 부모 삭제 시 자식 FK 풀스캔으로 인한 성능 지연 | **자식 테이블의 모든 FK 컬럼에 B-Tree 인덱스 필수 생성** | 참조 검사 속도 $O(\log N)$ 보장 |
| `CASCADE` 설정 오남용으로 인한 전사 데이터 무단 삭제 | **기본 `RESTRICT` 적용 및 필요시 애플리케이션 소프트 삭제(Soft Delete)** | 치명적인 비즈니스 데이터 유실 사고 차단 |

#### 한줄 요약

- 대리키 도입, FK 인덱스 생성, RESTRICT/소프트 삭제를 통해 안전하고 빠른 무결성 구조를 구현

## Ⅶ. 결론

<details><summary>용어 설명</summary>

- **관계형 모델의 2대 기둥(Dual Pillars)**: E.F. Codd의 관계형 데이터 모델을 지탱하는 가장 본질적인 2대 무결성 규칙.

</details>

- **개체 무결성과 참조 무결성** 관계형 데이터베이스의 신뢰성을 지탱하는 근본 기둥이며, 대리키와 FK 인덱스를 표준 설계 지침으로 정착시켜 고성능과 무결성을 동시에 달성해야 함

#### 한줄 요약

- PK의 개체 무결성과 FK의 참조 무결성을 통해 데이터베이스의 식별성과 관계 정합성을 완성
