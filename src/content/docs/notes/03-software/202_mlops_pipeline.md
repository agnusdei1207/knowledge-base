## Ⅰ. 개요

<details><summary>용어 설명</summary>

- **MLOps (Machine Learning Operations)**: DevOps의 원칙(자동화·CI/CD·모니터링)을 ML 모델 개발에 적용하여, 데이터 준비·학습·검증·배포·감시·재학습의 모델 전 생명주기를 코드처럼 관리·자동화하는 운영 체계.
- **Model Lifecycle (모델 생명주기)**: ML 모델의 기획·데이터 수집·특성 공학(Feature Engineering)·학습·검증·배포·운영 모니터링·재학습·폐기에 이르는 전체 단계.
- **Reproducibility (재현성)**: 같은 코드·데이터·환경에서 실험을 반복해도 동일한 모델 성능이 나오는 성질. 수동 노트북 실행 방식에서는 보장하기 어려운 MLOps의 핵심 목표.

</details>

- 정의/개념: Data•학습•검증•배포•관측을 자동화하는 **MLOps 체계**
- 배경/필요성: 수동 학습•배포로 **재현 불가•Drift 방치•품질 저하** 발생

#### 한줄 요약

- 학습 재료·방법·결과를 함께 기록해 같은 모델을 다시 만들고 운영 변화를 감시한다.

## Ⅱ. 특징

<details><summary>용어 설명</summary>

- **Drift (드리프트)**: 모델 배포 후 실세계 데이터가 학습 데이터와 다르게 변화하여 모델 예측 정확도가 저하되는 현상. 크게 데이터 드리프트(입력 분포 변화)와 개념 드리프트(입력-출력 관계 변화)로 구분.

</details>

- **Version Control (버전 관리)**: 코드(Git), 데이터(DVC), 환경(Docker), 모델(Model Registry)을 고유 버전으로 연결하여 어떤 조합에서 현재 모델이 생성됐는지 언제든 재현 가능.
- **Quality Gate (품질 게이트)**: 데이터 품질 검사(결측·이상값·분포), 오프라인 성능(정확도·F1), 배포 전 온라인 검증(A/B Test, Canary)을 각 단계의 관문으로 설정하여 저품질 모델의 승격 차단.
- **Lineage Tracking (계보 추적)**: 배포된 모델이 어느 데이터셋·피처 버전·하이퍼파라미터·학습 코드에서 생성됐는지 추적하는 이력으로, 품질 문제 발생 시 원인 규명에 필수.
- **CT (Continuous Training, 지속 학습)**: 데이터 드리프트 탐지·일정 주기·업무 성과 저하 등을 트리거로 검증된 학습 파이프라인을 자동 실행하여 모델을 최신 데이터에 맞게 유지.

#### 한줄 요약

- 학습 조건과 결과를 기록하고 운영 품질이 떨어질 때 검증된 재학습을 시작한다.

## Ⅲ. 구조 및 구성요소

<details><summary>용어 설명</summary>

- **Feature Store (피처 저장소)**: 학습 시 사용된 피처의 계산 로직·버전·값을 저장하여, 운영 추론 시에도 동일한 피처를 재사용(훈련-서빙 스큐 방지). Offline Store(배치 학습용)와 Online Store(실시간 추론용)로 구성.

</details>

```text
[MLOps Pipeline]
 ├── [Feature Store | Offline•Online Feature]
 ├── [Training Pipeline | 전처리•학습•평가]
 ├── [Model Registry | Version•Lineage•승인]
 ├── [Model Serving | 추론•Canary•Rollback]
 └── [Quality Monitoring | Drift•KPI•CT]
```

| 구성요소 | 책임 |
|---|---|
| Feature Store | 학습•추론의 **Feature 일관성** 보장 |
| Training Pipeline | 전처리•학습•평가•등록 **자동화** |
| Model Registry | 지표•Lineage•Version•**승인 상태** 관리 |
| Model Serving | 승인 Model의 추론•Canary•**Rollback** 수행 |
| Quality Monitoring | Drift•KPI 감시와 **CT Trigger** 수행 |

#### 한줄 요약

- 학습 재료와 결과를 등록한 뒤 승인 모델만 배포하고 품질 저하 시 다시 학습한다.

## Ⅳ. 흐름도

<details><summary>용어 설명</summary>

- **Model Promotion (모델 승격)**: 학습·평가를 완료한 후보 모델의 상태를 Staging → Production으로 올려 실제 운영 추론에 사용하도록 승인하는 절차. 수동 승인(Manual Approval) 또는 자동 승격 정책으로 운영.

</details>

```text
 1. [데이터·피처 품질 검증] ─── 결측·이상값·분포 확인 (품질 게이트)
          │
          ├─(품질 미달)──────► 학습 중단 및 데이터 교정 요청
          │
          └─(통과)───────────────────────────────────────────┐
                                                             ▼
 2. [학습·평가·레지스트리 등록] ── 동일 파이프라인으로 재현, 지표 기록
          │
          ├─(오프라인 기준 미달)──► 승격 거부, 재실험
          │
          └─(기준 통과)──────────► 후보 모델 Staging 승격
                                                  │
                                                  ▼
 3. [배포] ─────────────────── A/B Test 또는 Canary 방식으로 점진 배포
          │
          ▼
 4. [운영 모니터링] ────────── 드리프트·예측 품질·업무 KPI 지속 수집
          │
          ├─(급격한 품질 저하)──► 이전 버전 자동 롤백
          ├─(드리프트 탐지)──────► CT 파이프라인 자동 트리거
          └─(정상)────────────────► 현재 모델 지속 운영
```

### 동작 원리

1. 데이터•피처 품질 검증: 결측•이상•분포 Gate 판정
2. 학습•평가•레지스트리 등록: 지표•Lineage•환경 기록
3. 배포: A/B•Canary로 후보 Model 점진 노출
4. 운영 모니터링: Drift•예측 품질•업무 KPI 감시

#### 한줄 요약

- 운영 입력과 예측 품질이 달라지면 새 후보를 학습해 승인 모델과 다시 비교한다.

## Ⅴ. 종류 및 비교

<details><summary>용어 설명</summary>

- **CI/CD for ML**: 소프트웨어 CI/CD가 코드를 테스트·배포하듯, ML에서는 모델 코드 변경 시 자동으로 데이터 검증→학습→평가→스테이징 배포를 실행하는 자동화 파이프라인.

</details>

| MLOps 성숙도 | Level 0 (수동) | Level 1 (파이프라인) | Level 2 (CI/CD/CT 완전 자동화) |
|:---|:---|:---|:---|
| 학습 방식 | 노트북 수동 실행 | 파이프라인 코드화·재현 가능 | 드리프트/트리거 기반 자동 재학습 |
| 배포 방식 | 수동 모델 파일 교체 | 일관된 배포 절차 자동화 | Canary/A-B 자동 점진 배포 |
| 모니터링 | 없거나 수동 대시보드 | 예측 품질 자동 수집 | 드리프트→CT 자동 연계 |
| 적용 시기 | 초기 실험·PoC 단계 | 반복 배포가 필요한 운영 단계 | 대규모·지속 갱신 필요 서비스 |

#### 한줄 요약

- 실험이 적으면 사람이 실행하고 반복 배포가 늘수록 검증·배포·재학습을 차례로 연결한다.

## Ⅵ. 실무 고려사항 및 대책

<details><summary>용어 설명</summary>

- **Training-Serving Skew (훈련-서빙 스큐)**: 학습 시 사용된 피처 계산 방식과 온라인 추론 시 사용되는 피처 계산 방식이 달라서, 학습 성능과 실제 운영 성능이 괴리되는 현상. Feature Store로 방지.

</details>

| 3대 실무 난제 | 발생 원인 | 실무 대책 및 해결방안 |
|:---|:---|:---|
| 1. 재현 불가 | 데이터·코드·라이브러리 버전이 고정되지 않음 | **DVC로 데이터 버전 고정, Docker로 환경 스냅숏, Git으로 코드 Pin** |
| 2. 훈련-서빙 스큐 | 학습 때와 온라인 추론 때 피처 계산 로직이 다름 | **Feature Store를 통해 학습과 추론에 동일 피처 정의·값 재사용 강제** |
| 3. 드리프트 미탐지로 품질 저하 방치 | 오프라인 정확도만 보고 운영 모니터링 미실시 | **Evidently/Arize로 데이터 드리프트·예측 분포·업무 KPI 자동 감시 구성** |

> 사례: **Google의 TFX(TensorFlow Extended) 기반 유튜브 추천 모델 지속 학습 파이프라인, 네이버·카카오의 MLOps 플랫폼 내재화 및 모델 드리프트 자동 재학습 운영 사례**

#### 한줄 요약

- 추천 입력 분포가 달라지면 후보를 다시 학습하고 기존 모델과 비교한다.

## Ⅶ. 결론

<details><summary>용어 설명</summary>

- **Model Promotion Criteria (모델 승격 기준)**: 오프라인 성능(AUC, F1)과 온라인 A/B Test 업무 KPI(클릭률, 전환율)를 모두 충족해야 운영 대상으로 승인하는 이중 합격 기준.

</details>

- **모델 승격 기준**에 따라 오프라인 성능과 온라인 업무 KPI를 동시 충족한 후보만 승격하고, **드리프트 탐지 시 CT 파이프라인 자동 실행** 원칙 적용

#### 한줄 요약

- 학습 기록과 합격선을 통과한 모델만 운영에 내보내고 품질 저하 때 다시 학습한다.
