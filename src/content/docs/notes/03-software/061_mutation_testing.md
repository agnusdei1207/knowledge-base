## Ⅰ. 개요

<details><summary>용어 설명</summary>

- **뮤테이션 테스트(Mutation Testing, 변이 테스트)**: "네가 짠 테스트 코드가 진짜 버그를 잡을 수 있어?"라고 도발하며, 멀쩡한 코드에 일부러 버그(돌연변이)를 주입해 보고 테스트가 그걸 잡아내는지 팩트 체크하는 화이트박스 기법이다.
- **변이체(Mutant)**: 봇이 소스코드를 뒤져서 `+`를 `-`로, `>`를 `<`로 얍삽하게 바꿔치기해서 만든 '고의적 결함이 심어진 가짜 프로그램'이다.
- **변이 점수(Mutation Score, MS)**: 100마리의 돌연변이(버그)를 풀었을 때 네 테스트 코드가 몇 마리나 죽였는지(Killed) 계산한 킬대스 비율(방어력 성적표)이다.

</details>

- 정의: 원본 코드에 고의로 에러(변이체)를 주입한 뒤, 기존 단위 테스트가 이 에러를 잡아내는지(Kill) 역으로 검증하는 **White-box Testing** 기법
- 배경: 커버리지 100%라고 자랑해 봤자, 정작 `assert(정답)`을 빼먹은 **가짜 테스트(물테스트)면 버그를 못 잡는 맹점**을 타파하기 위함

#### 한줄 요약

- 테스트 코드를 검사하기 위해, 멀쩡한 코드에 일부러 버그를 심어보고 잘 잡나 테스트하는 거다.

## Ⅱ. 특징

<details><summary>용어 설명</summary>

- **사멸(Killed) vs 생존(Survived)**: 버그를 심었는데 테스트가 빨간불을 뿜으며 잡아내면 '사멸(성공)', 테스트가 버그를 못 찾고 초록불로 통과해버리면 '생존(실패)'으로 판정한다.
- **등가 변이체(Equivalent Mutant)**: 봇이 코드를 바꾸긴 했는데, 논리적으로 원본이랑 결과가 똑같아서(예: `i++`나 `++i`) 테스트가 영원히 잡을 수 없는 무적 돌연변이이다.

</details>

- 테스트 코드 자체의 **결함 탐지 능력(Fault Detection Capability)** 을 팩트 폭행하여 검증.
- 결과를 **사멸(Killed), 생존(Survived), 등가 변이체(Equivalent)** 3단계로 무자비하게 분류.
- **변이 점수(MS)** 를 통해 "물테스트"인지 "진짜 테스트"인지 객관적으로 정량 평가.

#### 한줄 요약

- 코드가 아니라 '테스트 코드의 방어력'을 점수(사멸/생존)로 까발리는 게 핵심이다.

## Ⅲ. 구조 및 구성요소

<details><summary>용어 설명</summary>

- **변이 연산자(Mutation Operators)**: 산술 연산자(`+` $\to$ `-`), 관계 연산자(`>` $\to$ `<=`), 논리 연산자(`&&` $\to$ `||`) 등 코드를 어떻게 망가뜨릴지 정해둔 공격 룰셋이다.

</details>

```text
[ 뮤테이션 테스트 십자포화 아키텍처 ]

[ 원본 코드 ] ──(변이 연산자로 공격)──▶ [ 변이체 (Mutant, 버그 심은 코드) ]
                                                    │
                                                    ▼
                                   [ 기존 단위 테스트 (Unit Tests) 실행 ]
                                                    │
[ 생존 (Survived) ◀─ (테스트 통과) ─── [ 판정 ] ──── (테스트 실패) ─▶ 사멸 (Killed) ]
(물테스트 검거!)                                                  (정상 방어!)
```

| 구성요소 | 팩트 폭행 책임 |
|:---|:---|
| **원본 코드** | 멀쩡하게 잘 돌아가고 있는 샌드백 대상 코드 |
| **변이 연산자** | 코드를 어떻게 망가뜨릴지(+, - 바꾸기 등) 정의해 놓은 봇의 공격 패턴 |
| **변이체 (Mutant)** | 공격을 맞고 고의적인 버그가 심어진 복제 프로그램 (수백 개 생성됨) |
| **단위 테스트** | 이 가짜 복제 프로그램들을 상대로 방어력을 뽐내야 하는 나의 테스트 코드 |
| **판정 결과** | 테스트가 버그를 잡아내면 Killed(승리), 못 막고 초록불 뜨면 Survived(패배) |

#### 한줄 요약

- 코드에 버그를 풀고 $\to$ 테스트를 돌려서 $\to$ 버그를 잡으면 패스, 못 잡으면 물테스트로 판정한다.

## Ⅳ. 흐름도

<details><summary>용어 설명</summary>

- **파이테스트(PITest)**: 자바(Java) 진영에서 컴파일된 바이트코드를 직접 헤집어놓으며 돌연변이를 공장장처럼 찍어내는 1티어 뮤테이션 자동화 봇이다.

</details>

```text
[ 변이 테스트 실행 십자포화 흐름 ]
┌──────────────────────────────┐
│ 테스트가 끝난 원본 코드 준비 │
└──────────────┬───────────────┘
               ▼
┌──────────────────────────────┐
│ 1. 변이체 생성 (Mutate)      │
│ (봇이 연산자를 바꿔치기함)   │
└──────────────┬───────────────┘
               ▼
┌──────────────────────────────┐
│ 2. 테스트 냅다 실행 (Run)    │
│ (각 변이체마다 테스트 돌림)  │
└──────────────┬───────────────┘
               ▼
┌──────────────────────────────┐
│ 3. 상태 판정 (Kill/Survive)  │
│ (못 잡으면 물테스트로 박제)  │
└──────────────┬───────────────┘
               ▼
┌──────────────────────────────┐
│ 4. 변이 점수(MS) 산출        │
│ (방어율 계산 후 리포팅)      │
└──────────────────────────────┘
```

### 동작 원리

1. 변이 주입: PIT 봇이 원본 코드의 `A > B`를 `A < B`로 바꿔서 변이체를 찍어냄.
2. 테스트 돌림: 변이체 수백 개를 띄워놓고 내 테스트 코드를 다 던져봄.
3. 판정: 테스트가 에러 뿜고 터지면 버그 잡은 거니까 Killed. 안 터지고 넘어가면 Survived.
4. 점수 계산: (죽인 변이체 수) / (전체 변이체 수 - 등가 변이체 수) * 100.
5. 피드백: 생존한 변이체 로그 보고, 내 테스트 코드에 빠진 `assert(정답확인)`를 채워 넣음.

#### 한줄 요약

- 버그 심기 $\to$ 테스트 돌리기 $\to$ 버그 못 잡은 놈 색출 $\to$ 점수 팩폭의 흐름이다.

## Ⅴ. 종류 및 비교

<details><summary>용어 설명</summary>

- **코드 커버리지 vs 뮤테이션 점수**: 커버리지는 "이 코드를 읽었냐(양)?"만 따져서 껍데기만 핥고 갈 수 있지만, 뮤테이션은 "이 코드가 망가졌을 때 잡아냈냐(질)?"를 팩트 폭행하는 궁극의 잣대이다.

</details>

| 비교 항목 | **Code Coverage (구문 커버리지의 함정)** | **Mutation Score (뮤테이션 팩트 폭행)** |
|:---|:---|:---|
| 측정 대상 | 코드 라인을 한 번이라도 지나갔는가? (양) | **버그가 생겼을 때 확실히 에러를 뿜는가? (질)** |
| 단언문(Assert)| `assert` 한 줄도 안 적어도 커버리지 100% 가능 | **`assert` 대충 짜면 변이체 생존해서 점수 나락 감** |
| 컴퓨팅 비용 | 한 번만 돌리면 끝이라 가벼움 | **변이체 수백 개를 다 돌려야 해서 CPU 터짐** |
| 실무 가치 | "아 이 부분 테스트 아예 안 짰네" 파악용 | **"결제 로직 테스트가 꼼꼼하게 짜여있나?" 검증용** |

#### 한줄 요약

- 커버리지는 테스트를 '했냐 안 했냐'를 묻고, 뮤테이션은 테스트를 '제대로 했냐'를 묻는다.

## Ⅵ. 실무 고려사항 및 대책

<details><summary>용어 설명</summary>

- **등가 변이체 오탐(Equivalent Mutant Problem)**: 점수가 안 나와서 털어봤더니, 봇이 멍청하게 원본이랑 완벽히 똑같이 작동하는 변이체를 만들어놔서 억울하게 점수가 깎이는 뒷목 잡는 현상이다.

</details>

| 문제 | 대책 | 효과 |
|:---|:---|:---|
| 수백 개 테스트하느라 빌드 시간 1시간 넘게 걸림 | 바뀐 코드만 터는 **PITest 델타 스캔** 적용 | 시간 단축하고 CI 파이프라인 숨통 트임 |
| 죽일 수 없는 '등가 변이체' 때문에 점수 억울하게 깎임 | 노가다로 분석해서 **어노테이션(`@Suppress`) 예외 처리** | 점수 왜곡 막고 진짜 빵꾸난 테스트만 공략 |
| 모든 코드에 뮤테이션 돌렸다가 서버 리소스 다 타버림 | 단순 CRUD 빼고 **핵심 도메인(결제/인증)** 에만 선별 적용 | CPU 터지는 거 막고 가성비 챙김 |

#### 한줄 요약

- CPU 낭비 심하니까 억울한 오탐은 예외 처리하고, 돈 되는 핵심 로직에만 돌려라.

## Ⅶ. 결론

<details><summary>용어 설명</summary>

- **뮤테이션 도입 수립 기준(Mutation Adoption Standards)**: 앱이 1원이라도 틀리면 난리 나는 금융권인지, CPU 자원이 남아도는지 각 재서 커버리지의 한계를 넘을지 정하는 잣대이다.

</details>

- **뮤테이션 도입 수립 기준** 원칙에 따라, 핵심 금융 로직은 닥치고 **변이 점수(Mutation)** 로 팩폭하고, 단순 화면은 걍 **코드 커버리지**로 퉁치는 기조 확립함

#### 한줄 요약

- 커버리지 100%라는 개발자의 허세를 박살 내고 테스트의 진짜 '질(Quality)'을 증명하는 끝판왕이다.
