## Ⅰ. 개요

<details><summary>용어 설명</summary>

- **뮤테이션 테스트(Mutation Testing, 변이 테스트)**: 원본 소스 코드에 인위적으로 구문 결함(변이체)을 주입한 후, 기존 단위 테스트 스위트가 해당 결함을 성공적으로 검출(Kill)하는지 측정하여 테스트의 유효성과 결함 탐지력을 정량 평가하는 기법.
- **변이체(Mutant)**: 원본 프로그램의 연산자, 피연산자 또는 제어문을 의도적으로 변경하여 생성한 인위적 결함 포함 프로그램.
- **변이 점수(Mutation Score, MS)**: 생성된 전체 유효 변이체 중 테스트 케이스에 의해 사멸(Killed)된 변이체의 백분율 지표.

</details>

- 정의/개념: 소스 코드에 변이 연산자를 적용하여 인위적 결함을 주입하고 단위 테스트의 결함 식별 능력을 정량 평가하는 **결함 기반(Fault-based) 테스트 검증 기법**
- 배경/필요성: 단순 코드 커버리지(Statement/Branch) 100% 달성 시에도 단언문(Assertion) 누락이나 검증 로직 미비로 실제 결함을 놓치는 형식적 테스트의 한계 극복 요구

#### 한줄 요약
- 원본 코드에 고의적 결함을 주입하여 단위 테스트 스위트의 실제 결함 탐지 능력을 정량 측정한다.

## Ⅱ. 특징

<details><summary>용어 설명</summary>

- **변이체 사멸(Killed Mutant)**: 주입된 변이체에 대해 단위 테스트 실행 결과 실패(Fail/Error)가 발생하여 결함이 올바르게 탐지된 상태.
- **변이체 생존(Survived Mutant)**: 주입된 변이체에 대해 단위 테스트가 모두 통과(Pass)하여 테스트 스위트의 결함 탐지 검증이 누락된 상태.
- **등가 변이체(Equivalent Mutant)**: 문법적 형태는 변경되었으나 프로그램의 의미론적 실행 결과는 원본과 동일하여 어떤 테스트로도 사멸시킬 수 없는 변이체.

</details>

- **결함 탐지 능력(Fault Detection Capability)** 을 직접 측정하여 테스트 케이스의 질적 수준 평가
- 실행 결과를 **사멸(Killed), 생존(Survived), 등가 변이체(Equivalent)** 로 명확히 분류
- **변이 점수 산식**: $\text{Mutation Score} = \frac{\text{Killed Mutants}}{\text{Total Mutants} - \text{Equivalent Mutants}} \times 100$

#### 한줄 요약
- 사멸과 생존 분류를 통해 변이 점수를 산출하고 테스트 단언문의 정밀도를 검증한다.

## Ⅲ. 구조 및 구성요소

<details><summary>용어 설명</summary>

- **변이 연산자(Mutation Operator)**: 산술 연산자 교체(`+` $\leftrightarrow$ `-`), 관계 연산자 교체(`>` $\leftrightarrow$ `<=`), 조건문 반전, 리턴값 변경 등 정형화된 결함 주입 규칙.

</details>

```text
[ 원본 소스 코드 ] ───(변이 연산자 적용)───▶ [ 다중 변이체 생성 (Mutants) ]
                                                     │
                                                     ▼
                                     [ 단위 테스트 스위트 (Unit Tests) 실행 ]
                                                     │
               ┌─────────────────────────────────────┴─────────────────────────────────────┐
               ▼                                                                           ▼
     [ 테스트 통과 (Pass) ]                                                      [ 테스트 실패 (Fail) ]
               │                                                                           │
               ▼                                                                           ▼
      [ 생존 (Survived) ]                                                         [ 사멸 (Killed) ]
  (테스트 단언문 보완 필요)                                                    (결함 탐지 능력 확인)
```

선의 의미: 변이체 생성부터 단위 테스트 실행 및 결과 판정(사멸/생존)으로 이어지는 검증 경로

| 구성요소 | 책임 |
|:---|:---|
| **원본 소스 코드** | 결함 주입의 대상이 되는 기준 프로덕션 코드베이스 |
| **변이 연산자 엔진** | 정적/바이트코드 조작을 통해 표준 결함 패턴을 소스 코드에 주입 |
| **변이체 집합(Mutants)** | 변이 연산자가 적용되어 독립적으로 생성된 결함 포함 바이너리/소스 |
| **단위 테스트 스위트** | 생성된 각 변이체를 실행하여 assertion 실패를 유발해야 하는 검증 대상 |
| **변이 리포터** | 사멸율, 생존 변이체 위치 및 등가 변이체 분석 지표 제공 |

#### 한줄 요약
- 변이 연산자로 변이체를 대량 생성하고, 테스트 실행 결과를 판정하여 사멸률을 리포팅한다.

## Ⅳ. 흐름도

<details><summary>용어 설명</summary>

- **PITest**: 자바 바이트코드를 런타임에 직접 조작하여 고속으로 변이체를 생성하고 테스트를 수행하는 대표적인 뮤테이션 테스트 프레임워크.

</details>

```text
1. 원본 프로그램 대상 단위 테스트 스위트 사전 검증 (모든 테스트 Pass 확인)
            │
            ▼
2. 변이 연산자 적용 및 변이체(Mutant) 생성: 구문 및 조건식 결함 주입
            │
            ▼
3. 변이체별 단위 테스트 병렬 실행: 개별 변이체 격리 실행 및 결과 수집
            │
            ▼
4. 사멸/생존 상태 판정: 테스트 실패 시 Killed, 성공 시 Survived 판정
            │
            ▼
5. 변이 점수(Mutation Score) 산출 및 생존 변이체 대상 단언문 보완
```

**동작 원리**

1. **사전 조건 확인**: 원본 코드가 기존 단위 테스트를 100% 통과하는지 확인
2. **변이체 생성**: AST 또는 바이트코드 수준에서 연산자를 교체하여 수백~수천 개의 변이체 생성
3. **격리 실행**: 각 변이체마다 연관된 단위 테스트를 실행하여 실행 시간 초과(Timeout) 또는 Assertion 실패 감지
4. **결과 분류**: 예외/실패 발생 시 Killed로 기록하고, 정상 통과 시 Survived로 기록
5. **품질 피드백**: Survived 변이체가 발생한 위치를 분석하여 누락된 테스트 케이스 및 단언문(Assert) 보강

#### 한줄 요약
- 사전 검증 후 변이체를 주입 실행하고, 생존 변이체를 분석하여 테스트 단언문을 보강한다.

## Ⅴ. 종류 및 비교

<details><summary>용어 설명</summary>

- **구문 커버리지(Statement Coverage)**: 테스트 실행 중 소스 코드의 개별 명령문이 최소 1회 이상 실행된 비율(양적 지표).
- **변이 점수(Mutation Score)**: 주입된 결함을 테스트가 실제로 식별해 낸 비율(질적 지표).

</details>

| 비교 항목 | 코드 커버리지 (Code Coverage) | 뮤테이션 점수 (Mutation Score) |
|:---|:---|:---|
| **평가 관점** | 테스트가 코드를 얼마나 많이 실행했는가? (양적 평가) | 테스트가 결함을 얼마나 정밀하게 잡아내는가? (질적 평가) |
| **단언문(Assert) 검증** | Assert가 없어도 코드 실행만 되면 100% 달성 가능 | 정밀한 Assert가 없으면 변이체가 생존하여 점수 저하 |
| **실행 오버헤드** | 단 1회 실행으로 측정 완료 (낮은 오버헤드) | 변이체 개수만큼 반복 실행으로 높은 컴퓨팅 자원 소모 |
| **실무 적용 영역** | CI 빌드 파이프라인의 기본 품질 게이트 | 결제, 금융, 의료, 항공 등 고신뢰성 핵심 비즈니스 로직 |

#### 한줄 요약
- 커버리지가 실행 여부의 양적 지표라면, 뮤테이션 점수는 결함 탐지력의 질적 지표다.

## Ⅵ. 실무 고려사항 및 대책

<details><summary>용어 설명</summary>

- **등가 변이체 문제(Equivalent Mutant Problem)**: 등가 변이체 판별이 정지 문제(Halting Problem)와 연관되어 튜링 완전 언어에서 자동으로 완벽히 판별하기 어려운 이론적 한계.

</details>

| 문제 | 대책 | 효과 |
|:---|:---|:---|
| 대량 변이체 실행으로 인한 빌드 시간 및 CPU 오버헤드 폭증 | 변경된 코드만 증분 검증하는 **PITest 델타 스캔** 및 바이트코드 변이 적용 | CI 파이프라인 지연 최소화 및 실행 시간 단축 |
| **등가 변이체(Equivalent Mutant)** 로 인한 점수 왜곡 | 정적 분석 도구 연계 및 `@Suppress` 어노테이션 기반 수동 예외 등록 | 측정 지표 신뢰도 제고 및 불필요한 분석 낭비 제거 |
| 전체 시스템 일괄 적용 시 리소스 한계 도달 | 단순 데이터 전송 객체(DTO/CRUD) 제외 및 **핵심 도메인 영역 선별 적용** | 투입 비용 대비 소프트웨어 신뢰성 극대화 |

#### 한줄 요약
- 증분 델타 스캔, 등가 변이체 예외 처리, 핵심 도메인 선별 적용으로 오버헤드를 통제한다.

## Ⅶ. 결론

- 형식적인 코드 커버리지의 한계를 보완하고 소프트웨어 신뢰성을 보증하기 위해 금융·보안 등 미션 크리티컬 도메인을 중심으로 **뮤테이션 테스트**를 도입하되, PITest 증분 실행 및 등가 변이체 관리 프로세스를 확립하여 비용 효율적인 품질 검증 체계를 운영

#### 한줄 요약
- 결함 주입을 통한 질적 검증으로 형식적 테스트를 탈피하고 핵심 로직의 신뢰성을 보증한다.
