## Ⅰ. 개요

<details><summary>용어 설명</summary>

- **서버리스 컴퓨팅 및 FaaS(Function as a Service)**: 개발자가 서버 인프라 관리 없이 이벤트(HTTP, 메시지 큐, S3 변경) 트리거 시 무상태(Stateless) 함수 코드를 자동 확장 실행하고 사용한 밀리초(ms) 단위 시간만큼만 과금되는 클라우드 실행 모델.
- **인프라 유휴 낭비 및 운영 오버헤드(Idle Waste & Server Maintenance)**: 비정기적으로 호출되는 배치나 API를 위해 24/365 상시 서버를 켜두어 발생하는 비용 낭비와 OS 패치 관리의 비효율.

</details>

- 정의/개념: 서버 인프라 관리 없이 이벤트(Event) 트리거 시 **무상태(Stateless) 함수 코드를 자동 확장 실행하고 사용 시간만큼만 과금**하는 서버리스 컴퓨팅 패러다임
- 배경/필요성: 간헐적·비주기적 워크로드에 대한 상시 서버 운영으로 인한 **인프라 유휴 비용 낭비, 서버 패치 오버헤드 및 수동 스케일링 지연 위험** 직면

#### 한줄 요약

- 서버 인프라 프로비저닝 없이 이벤트 발생 시에만 함수를 탄력 실행하여 비용을 획기적으로 절감하고 개발 생산성을 극대화

## Ⅱ. 특징

<details><summary>용어 설명</summary>

- **콜드 스타트(Cold Start)**: 유휴 상태의 함수 인스턴스를 최초로 초기화하고 런타임을 구동하는 과정에서 발생하는 1~3초의 초기 응답 지연.
- **실행 시간 기반 종량 과금(Pay-per-Execution)**: 서버 대기 비용 없이 실제 함수가 호출되어 실행된 시간(1ms 단위)과 메모리 할당량에 비례하여 과금.

</details>

- 서버 프로비저닝, OS 패치, 용량 계획이 100% 불필요한 **Zero Server Management**
- 이벤트 유입량에 따라 0개에서 수천 개로 즉시 확장되는 **자동 스케일아웃(Auto-Scaling)**
- 함수 호출 횟수와 실행 시간(ms)에만 비례하여 청구되는 **초정밀 종량 과금 체계**

#### 한줄 요약

- 이벤트 기반 무상태 실행과 무한 확장을 통해 인프라 운영 오버헤드를 제로화

## Ⅲ. 구조 및 구성요소

<details><summary>용어 설명</summary>

- **FaaS 아키텍처 계층**: Event Source(트리거), FaaS Control Plane(동시성/배치 제어), Function Runtime(MicroVM 격리 실행), External State(외부 영속 저장소).

</details>

```text
[ 서버리스 FaaS(AWS Lambda) 이벤트 구동 아키텍처 ]

 1. [ 다양한 이벤트 소스 (Event Sources) ]
    • API Gateway (HTTP) / S3 Bucket (객체 업로드) / SQS (메시지 큐)
                              │ (Event Trigger)
                              ▼
 2. [ FaaS 컨트롤 플레인 (FaaS Control Plane) ] ──────────────────┐
    • 동시성(Concurrency) 제어, 라우팅, IAM 권한 및 재시도 검증  │
    └─────────────────────────┬───────────────────────────────────┘
                              │
                              ▼ (Warm 컨테이너 할당 또는 Cold Start 생성)
 3. [ 무상태 함수 런타임 (MicroVM / Firecracker Container) ]
    ┌─────────────────────────────────────────────────────────────┐
    │  [ 사용자 함수 로직 (Python / Node.js / Java 코드) ]         │
    └─────────────────────────┬───────────────────────────────────┘
                              │ (상태 저장 및 데이터 조회)
                              ▼
 4. [ 외부 영속 계층 (External State: DynamoDB / S3 / ElastiCache) ]
```

선의 의미: 이벤트 소스가 FaaS 제어면을 트리거하여 무상태 함수 컨테이너를 가동하고 외부 DB에 결과를 기록하는 구조.

| 구성요소 | 책임 |
|:---|:---|
| 이벤트 소스 (Event Source) | HTTP, S3 객체 생성, 큐 메시지 등 **함수 실행을 유발하는 트리거 신호 제공** |
| FaaS 제어면 (Control Plane)| 인증/인가, 동시성 한도 검사, **컨테이너 웜/콜드 상태 판별 및 스케줄링 총괄** |
| 함수 런타임 (Runtime) | Firecracker MicroVM 기반으로 **격리된 환경에서 사용자 코드를 초고속 실행** |
| 외부 영속 저장소 (State) | 무상태 함수의 한계를 극복하기 위해 **결과 데이터 및 세션 상태를 외부 보존** |

#### 한줄 요약

- 이벤트 소스, FaaS 제어면, 무상태 함수 런타임, 외부 영속 저장소가 결합

## Ⅳ. 흐름도

<details><summary>용어 설명</summary>

- **FaaS 함수 실행 5단계 절차**: 이벤트 감지 $\to$ 권한 검증 $\to$ 웜/콜드 환경 준비 $\to$ 함수 로직 실행 $\to$ 결과 반환 및 자원 회수.

</details>

```text
[ 서버리스 FaaS 이벤트 처리 및 컨테이너 기동 파이프라인 ]

 ┌────────────────────────────────────────┐
 │ 1. 이벤트 소스(S3/APIGW) 신호 도착     │
 └───────────────────┬────────────────────┘
                     │
                     ▼
 ┌────────────────────────────────────────┐
 │ 2. IAM 실행 권한 및 동시성 쿼터 검증   │
 └───────────────────┬────────────────────┘
                     │
                     ▼
 ┌────────────────────────────────────────┐
 │ 3. Warm 인스턴스 탐색 (부재 시 Cold Start 초기화)
 └───────────────────┬────────────────────┘
                     │
                     ▼
 ┌────────────────────────────────────────┐
 │ 4. 사용자 비즈니스 함수 핸들러 로직 실행│
 └───────────────────┬────────────────────┘
                     │
                     ▼
 ┌────────────────────────────────────────┐
 │ 5. 외부 DB 결과 저장 및 런타임 유휴/회수│
 └────────────────────────────────────────┘
```

### 동작 원리

1. 이벤트 도착: S3 이미지 업로드 이벤트가 발생하여 FaaS 제어면으로 알림 페이로드가 전송.
2. 권한 검증: Lambda 실행 역할(IAM Role)과 계정별 동시성(Concurrency) 한도를 검증.
3. 환경 준비: 이미 켜져 있는 Warm 컨테이너를 우선 탐색하고, 없으면 신규 MicroVM을 부팅(Cold Start).
4. 로직 실행: 핸들러 함수가 이미지를 리사이징하는 연산을 밀리초 단위로 수행.
5. 결과 반환: 리사이징된 이미지를 S3에 저장하고 응답을 반환한 뒤 컨테이너는 대기 또는 자동 회수.

#### 한줄 요약

- 이벤트 도착 $\to$ 권한 검증 $\to$ 환경 준비 $\to$ 함수 실행 $\to$ 자원 회수의 5단계

## Ⅴ. 종류 및 비교

<details><summary>용어 설명</summary>

- **전통적 상시 서버(EC2) vs 서버리스 FaaS**: 24/365 고정 과금 및 수동 관리(EC2)와 이벤트 트리거 기반 자동 확장 및 종량 과금(FaaS).

</details>

| 구분 | 상시 서버 가상머신 (EC2 / VM) | 서버리스 FaaS (AWS Lambda) |
|:---|:---|:---|
| **적용 기준** | 24시간 일정한 트래픽, 장시간(15분 이상) 실행 프로세스, 웹소켓 | 간헐적 이벤트, 비정기 배치, 이미지 리사이징, 경량 REST API |
| **핵심 특징** | **OS 커스터마이징, 지속 연결 유지, 고정 인프라 렌탈 과금** | **Zero 인프라 관리, 밀리초 단위 종량 과금, 무제한 스케일아웃** |
| **한계** | 트래픽 유휴 시간에도 100% 비용 발생 및 수동 OS 패치 | 초기 콜드 스타트 지연 및 최대 실행 시간(15분) 제약 |

#### 한줄 요약

- 항시 가동과 지속 연결은 EC2/컨테이너, 이벤트 구동 및 간헐적 처리는 서버리스 FaaS를 선택

## Ⅵ. 실무 고려사항 및 대책

<details><summary>용어 설명</summary>

- **프로비저닝된 동시성(Provisioned Concurrency)**: 콜드 스타트를 원천 차단하기 위해 N개의 함수 인스턴스를 미리 초기화하여 항상 대기시키는 기술.

</details>

| 문제 | 대책 | 효과 |
|:---|:---|:---|
| 자바/스프링 함수 최초 기동 시 수 초의 콜드 스타트 지연 | **AWS Lambda SnapStart 또는 Provisioned Concurrency 사전 적용** | 초기 응답 시간 수십 ms 이내로 단축 |
| 수천 개 함수 동시 실행 시 백엔드 RDBMS 연결 풀 고갈 | **RDS Proxy 도입으로 데이터베이스 커넥션 풀링 및 다중화** | DB 연결 초과 장애 완벽 방지 |
| 대용량 데이터 처리 중 단일 함수 최대 실행 시간(15분) 초과 | **AWS Step Functions 도입으로 워크플로우를 단계별 분할 제어** | 장기 실행 프로세스 무중단 완결 |

#### 한줄 요약

- SnapStart 도입, RDS Proxy 커넥션 풀링, Step Functions 분할 제어를 통해 서버리스 운영 장애를 해결

## Ⅶ. 결론

<details><summary>용어 설명</summary>

- **서버리스 우선주의(Serverless-First Strategy)**: 신규 시스템 설계 시 서버리스 FaaS와 관리형 SaaS를 최우선 고려하여 인프라 운영 TCO를 최소화하는 아키텍처 원칙.

</details>

- **서버리스 FaaS** 기반 이벤트 구동 클라우드 네이티브의 궁극적인 실행 모델이며, 무상태 설계와 콜드 스타트 방어 기법 및 데이터베이스 프록시를 결합하여 비용 효율성과 개발 민첩성을 극대화해야 함

#### 한줄 요약

- 이벤트 구동 무상태 실행과 정밀 종량 과금을 통해 인프라 운영 제로화와 비용 최적화를 완성
