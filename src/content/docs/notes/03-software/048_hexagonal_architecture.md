## Ⅰ. 개요

<details><summary>용어 설명</summary>

- **헥사고날 아키텍처(Hexagonal Architecture)**: 핵심 비즈니스 로직(도메인)이 데이터베이스나 웹 프레임워크 등 외부 기술에 종속되지 않도록 포트와 어댑터 인터페이스로 격리하는 소프트웨어 아키텍처 패턴.
- **포트(Port)**: 도메인 코어가 외부 세계와 상호작용하기 위해 정의한 인터페이스 명세(인바운드 유스케이스 및 아웃바운드 SPI).
- **어댑터(Adapter)**: 외부 인프라 기술(REST API, JPA, 메시지 큐)을 도메인 포트 인터페이스 규격에 맞게 변환 결합하는 구현 모듈.

</details>

- 정의/개념: 핵심 비즈니스 로직을 중심에 두고 외부 프레임워크 및 데이터베이스와의 결합을 **포트(Port)와 어댑터(Adapter)** 인터페이스로 분리 격리하는 소프트웨어 아키텍처
- 배경/필요성: 계층형(Layered) 구조에서 발생하는 데이터베이스 중심 의존성 전파를 차단하고 비즈니스 로직의 독립적 테스트 가능성 및 기술 교체 유연성 확보 필요

#### 한줄 요약

- 도메인 중심 의존성 역전을 통해 외부 인프라 기술 변경에 독립적인 비즈니스 로직을 구축

## Ⅱ. 특징

<details><summary>용어 설명</summary>

- **인바운드/아웃바운드(Inbound/Outbound)**: 외부에서 도메인을 호출하는 유스케이스 진입 방향(Inbound)과 도메인이 외부 인프라를 호출하는 방향(Outbound).
- **의존성 역전 원칙(Dependency Inversion Principle, DIP)**: 상위 수준의 비즈니스 모듈이 하위 수준의 세부 구현에 의존하지 않고 추상화(인터페이스)에 의존하도록 설계하는 원칙.

</details>

- **인바운드/아웃바운드(Inbound/Outbound)** 포트 분리를 통한 도메인 코어의 완전한 기술 독립성
- 어댑터가 도메인 포트를 참조하도록 강제하는 **의존성 역전 원칙(DIP)** 적용
- 외부 인프라(DB, Web) 없이도 모의 객체(Mock) 주입을 통한 **고속 단위 테스트(Unit Test)** 가능

#### 한줄 요약

- 인바운드와 아웃바운드 포트를 통한 의존성 역전으로 도메인 코어의 순수성과 테스트 용이성을 달성

## Ⅲ. 구조 및 구성요소

<details><summary>용어 설명</summary>

- **도메인 코어(Domain Core)**: 프레임워크나 외부 라이브러리 의존성이 배제된 순수 POJO(Plain Old Java Object) 엔티티 및 도메인 서비스.

</details>

```text
[ 인바운드 어댑터 (REST Controller) ] ──► [ 인바운드 포트 (UseCase Interface) ]
                                                   │
                                                   ▼
                [ 애플리케이션 코어 (순수 Domain Core / POJO Entities) ]
                                                   │
                                                   ▼
[ 아웃바운드 어댑터 (JPA/Kafka Adapter) ] ◄── [ 아웃바운드 포트 (SPI Interface) ]
```

선의 의미: 인바운드 요청 진입 및 도메인 코어 내부 실행 후 아웃바운드 SPI 호출 흐름

| 구성요소 | 책임 |
|:---|:---|
| 인바운드 어댑터 (Inbound Adapter) | HTTP/CLI 등 외부 요청을 수신하여 **도메인 입력 커맨드로 변환 후 유스케이스 호출** |
| 인바운드 포트 (Inbound Port) | 애플리케이션 코어가 외부에 노출하는 **유스케이스(UseCase) 진입 인터페이스 정의** |
| 도메인 코어 (Domain Core) | 외부 기술 프레임워크 종속성 없이 **순수 비즈니스 엔티티 및 규칙 연산 수행** |
| 아웃바운드 포트 (Outbound Port) | 도메인이 요구하는 영속성/메시징 기능을 정의한 **서비스 제공자 인터페이스(SPI) 명세** |
| 아웃바운드 어댑터 (Outbound Adapter) | 아웃바운드 포트를 구현하여 **실제 DB 쿼리 실행 또는 외부 메시지 큐 전송** |

#### 한줄 요약

- 외부 어댑터가 인바운드 포트를 통해 도메인으로 진입하고, 도메인은 아웃바운드 포트를 통해 인프라를 호출

## Ⅳ. 흐름도

<details><summary>용어 설명</summary>

- **도메인 모델 매핑(Domain Model Mapping)**: 외부 DTO와 영속성 엔티티를 순수 도메인 객체와 상호 변환하여 계층 간 결합을 차단하는 메커니즘.

</details>

```text
[ 1. 외부 클라이언트의 HTTP 요청 수신 ]
                │
                ▼
[ 2. 인바운드 어댑터: DTO 검증 및 도메인 Command 객체 생성 ]
                │
                ▼
[ 3. 인바운드 포트 경유 도메인 유스케이스 실행 ]
                │
                ▼
[ 4. 아웃바운드 포트(SPI) 인터페이스 호출 ]
                │
                ▼
[ 5. 아웃바운드 어댑터: 영속성 매핑 및 데이터베이스 트랜잭션 커밋 ]
```

**동작 원리** 1. **외부 요청 수신**: 클라이언트가 REST API 또는 메시지 큐 이벤트 전송
2. **인바운드 어댑터 매핑**: HTTP 요청을 파싱하고 유효성 검증 후 도메인 명령(Command) 객체 생성
3. **도메인 유스케이스 실행**: 인바운드 포트를 거쳐 순수 비즈니스 규칙 및 상태 전이 로직 수행
4. **아웃바운드 포트 호출**: 영속화 또는 외부 전송을 위해 도메인 인터페이스(SPI) 호출
5. **아웃바운드 어댑터 저장**: JPA 또는 NoSQL 어댑터가 도메인 엔티티를 DB 테이블 레코드로 변환 저장

#### 한줄 요약

- 요청 수신부터 도메인 실행 및 외부 영속화까지 각 경계에서 포트와 어댑터를 거쳐 격리 수행

## Ⅴ. 종류 및 비교

<details><summary>용어 설명</summary>

- **계층형 아키텍처(Layered Architecture)**: 프레젠테이션, 비즈니스, 데이터 접근 계층이 상위에서 하위로 단방향 의존하는 전통적 구조.

</details>

| 아키텍처 스타일 | 계층형 아키텍처 (Layered) | 헥사고날 아키텍처 (Ports & Adapters) |
|:---|:---|:---|
| 적용 기준 | **단순 CRUD 작업 위주** 및 빠른 초기 납기 요구 시스템 | **도메인 복잡도 과다** 및 장기 유지보수·기술 교체 잦은 시스템 |
| 핵심 특징 | 상위 계층이 하위 데이터베이스 계층에 **직접 종속** | 의존성 역전(DIP)을 통한 **도메인 코어의 인프라 기술 완전 격리** |
| 한계 | DB 변경 시 상위 비즈니스 로직에 **파급 영향 발생** | 포트, 어댑터, 매퍼 분리로 인한 **보일러플레이트 코드 증가** |

#### 한줄 요약

- 단순 CRUD는 계층형이 효율적이며, 복잡한 비즈니스 규칙과 장기 진화에는 헥사고날을 선택

## Ⅵ. 실무 고려사항 및 대책

<details><summary>용어 설명</summary>

- **보일러플레이트 코드(Boilerplate Code)**: 구조적 분리를 위해 반복적으로 작성해야 하는 DTO, Entity 간 매핑 코드 및 인터페이스 선언문.

</details>

| 문제 | 대책 | 효과 |
|:---|:---|:---|
| 영속성 프레임워크(JPA) 어노테이션의 도메인 모델 오염 | **도메인 엔티티와 JPA 영속성 엔티티 분리 및 매핑** | 데이터베이스 스키마 변경 시 도메인 로직 보존 |
| 계층 간 객체 변환으로 인한 **보일러플레이트 코드 증가** | **MapStruct 등 컴파일 타임 매핑 자동화 라이브러리 도입** | 매핑 코드 수작업 오버헤드 최소화 |
| 단순 CRUD 업무에 헥사고날 적용 시 **오버 엔지니어링** | **도메인 복잡도 기준 하이브리드 아키텍처 설계** | 개발 생산성과 유지보수성 간 최적 균형 유지 |

#### 한줄 요약

- 엔티티 분리와 매핑 자동화를 적용하고 도메인 복잡도에 따라 선택적으로 헥사고날을 도입

## Ⅶ. 결론

<details><summary>용어 설명</summary>

- **도메인 주도 설계(Domain-Driven Design, DDD)**: 복잡한 도메인을 유비쿼터스 언어와 바운디드 컨텍스트 중심으로 모델링하는 소프트웨어 개발 접근법.

</details>

- 비즈니스 도메인의 복잡성이 높고 외부 시스템과의 통합 변경이 빈번한 대규모 엔터프라이즈 시스템 구축 시에는 헥사고날 아키텍처를 도입하여 도메인 순수성과 의존성 역전을 확립하고, 단순 데이터 조회 중심 서비스는 계층형 구조를 병행하는 실용적 아키텍처 거버넌스가 필수적

#### 한줄 요약

- 복잡한 도메인은 헥사고날로 격리하고 단순 서비스는 계층형으로 최적화
