## Ⅰ. 개요

<details><summary>용어 설명</summary>

- **헥사고날 아키텍처(Hexagonal Architecture)**: 비즈니스 핵심 로직(도메인)이 DB나 웹 프레임워크 같은 외부 기술에 오염되지 않도록, 중간에 '포트와 어댑터'라는 방어벽을 쳐서 완벽히 격리시키는 육각형 구조의 아키텍처이다.
- **포트(Port)**: 비즈니스 로직(도메인 코어)이 외부와 소통하기 위해 뚫어놓은 구멍(인터페이스)으로, "나는 DB에 저장할 거니까 누군가 이 계약서(인터페이스)대로 구현해 줘"라고 던지는 명세서이다.
- **어댑터(Adapter)**: 110V 돼지코처럼, 바깥 세상의 잡다한 기술(Spring MVC, JPA)을 도메인 포트 규격에 딱 맞게 변환해서 꽂아주는 껍데기 모듈이다.

</details>

- 정의: 핵심 비즈니스 로직(도메인 코어)을 한가운데 두고, 외부 기술(웹, DB)이 침범하지 못하게 **포트(Port)와 어댑터(Adapter)** 로 철벽을 치는 아키텍처인 **Hexagonal Architecture**
- 배경: 쿼리나 웹 기술이 비즈니스 로직과 한 덩어리로 엉키면(계층형), 나중에 **프레임워크나 DB를 바꿀 때 전체 코드를 다 갈아엎어야 하는 대참사**가 터지기 때문

#### 한줄 요약

- 진짜 중요한 '비즈니스 로직'을 한가운데 숨기고, 밖에서 들어오는 요청은 껍데기(어댑터)가 처리하게 만드는 거다.

## Ⅱ. 특징

<details><summary>용어 설명</summary>

- **인바운드/아웃바운드(Inbound/Outbound)**: 밖에서 안으로 들어와 도메인을 찌르는 건 인바운드(Web, API), 도메인이 밖으로 나가서 일 시키는 건 아웃바운드(DB, 외부 API)라고 부르는 트래픽 방향이다.
- **의존성 역전(Dependency Inversion)**: 보통은 '비즈니스 로직 $\to$ DB' 방향으로 의존하지만, 포트를 중간에 껴서 'DB(어댑터) $\to$ 비즈니스 로직(포트)' 방향으로 화살표를 확 꺾어버려 도메인 코어를 짱박는 DIP 원칙의 끝판왕이다.

</details>

- **Inbound/Outbound** 양방향으로 포트와 어댑터를 달아서 도메인 코어를 육각형(Hexagonal)으로 꽁꽁 싸맴.
- 어댑터가 포트를 바라보게 만드는 **의존성 역전(DIP)** 으로, 코어는 바깥세상에 뭐가 있는지 1도 모르게 만듦.
- 바깥에 진짜 DB나 UI가 없어도, 가짜(Mock) 어댑터만 꽂으면 비즈니스 로직만 **초스피드로 단위 테스트** 쌉가능함.

#### 한줄 요약

- 밖에서 안을 향해 찌르는 구조(의존성 역전)로 만들어서, DB가 날아가도 로직은 살릴 수 있다.

## Ⅲ. 구조 및 구성요소

<details><summary>용어 설명</summary>

- **도메인 코어(Domain Core)**: 프레임워크 어노테이션(`@Entity`, `@Service` 등)이 단 1개도 안 묻은, 순수 자바(POJO)로만 짜인 시스템의 심장이자 비즈니스 룰의 성역이다.

</details>

```text
[ 헥사고날 아키텍처 십자포화 아키텍처 ]

[ 인바운드 어댑터 (Web Controller) ] ──▶ [ 인바운드 포트 (UseCase Interface) ]
                                                 │
                                                 ▼
              [ 애플리케이션 핵심 (순수 Domain Core / POJO) ]
                                                 │
                                                 ▼
[ 아웃바운드 어댑터 (JPA Repository) ] ◀── [ 아웃바운드 포트 (Repository Interface) ]
```

| 구성요소 | 직관적 비교 책임 |
|:---|:---|
| **인바운드 어댑터 (Web/API)** | 유저가 쏜 HTTP 요청을 받아 도메인이 알아먹게 명령어로 번역하는 웹 껍데기 |
| **인바운드 포트 (UseCase)** | 도메인이 "내게 일 시킬 거면 이 규격 맞춰서 들어와" 정해둔 출입문 |
| **도메인 코어 (Domain)** | 프레임워크 1도 없이, 오직 돈 계산/주문 처리 찐 비즈니스 룰만 깎는 장인 |
| **아웃바운드 포트 (Repo)** | 도메인이 "DB가 뭐든 상관없고 이대로 저장해"라며 밖으로 던지는 청구서 |
| **아웃바운드 어댑터 (DB)** | 청구서(포트)를 받아 진짜 MySQL 쿼리로 바꾸거나 카프카로 쏴주는 하청업체 |

#### 한줄 요약

- 인바운드 어댑터(Web) $\to$ 인바운드 포트 $\to$ 코어 $\to$ 아웃바운드 포트 $\to$ 아웃바운드 어댑터(DB) 구조다.

## Ⅳ. 흐름도

<details><summary>용어 설명</summary>

- **도메인 매핑(Domain Model Mapping)**: 바깥에서 들어온 흙 묻은 데이터(DTO, JPA Entity)를 순수한 도메인 객체로 변환하거나, 그 반대로 씻겨내는 문지기(어댑터)의 노가다 작업이다.

</details>

```text
[ 헥사고날 요청 십자포화 흐름 ]
┌──────────────────────────────┐
│ 1. 유저의 HTTP REST API 요청 │
└──────────────┬───────────────┘
               ▼
┌──────────────────────────────┐
│ 2. 인바운드 어댑터 매핑      │
│ (JSON을 도메인 명령어로 변환)│
└──────────────┬───────────────┘
               ▼
┌──────────────────────────────┐
│ 3. 도메인 핵심 로직 실행     │
│ (포트 타고 들어와서 룰 검사) │
└──────────────┬───────────────┘
               ▼
┌──────────────────────────────┐
│ 4. 아웃바운드 포트 찌름      │
│ (도메인이 "야 이거 저장해" 함)│
└──────────────┬───────────────┘
               ▼
┌──────────────────────────────┐
│ 5. 아웃바운드 어댑터 DB 저장 │
│ (JPA로 변환해서 진짜 DB에 박음)│
└──────────────────────────────┘
```

### 동작 원리

1. 외부 요청: 유저가 폰으로 버튼을 누름.
2. 인바운드 어댑터: Controller가 받아 불순물 제거하고 깔끔한 데이터로 매핑함.
3. 도메인 진입 및 실행: 인바운드 포트 열고 들어가 순수 비즈니스 로직 돌림.
4. 아웃바운드 포트 호출: 로직 끝내고 아웃바운드 포트(Interface)를 불러 저장 지시함.
5. 아웃바운드 어댑터 저장: 포트를 구현한 JPA 어댑터가 진짜 DB에 쿼리를 쏴서 박음.

#### 한줄 요약

- 외부 요청 $\to$ 껍데기가 번역 $\to$ 알맹이가 처리 $\to$ 껍데기가 다시 번역해서 DB 저장하는 흐름이다.

## Ⅴ. 종류 및 비교

<details><summary>용어 설명</summary>

- **계층형(Layered) vs 헥사고날(Hexagonal)**: 맨 밑에 DB 깔고 위에서 찍어 누르는 뻔한 3단 케이크(계층형)와, 비즈니스를 한가운데 짱박고 DB마저 껍데기 취급하는 양파 구조(헥사고날)의 차이이다.

</details>

| 비교 항목 | **계층형 아키텍처 (Layered)** | **헥사고날 아키텍처 (Ports & Adapters)** |
|:---|:---|:---|
| 의존성 화살표 | Controller $\to$ Service $\to$ **DB (결국 DB가 갑)** | Adapter $\to$ Port $\to$ **Domain (도메인이 갑)** |
| DB 기술 결속력 | 비즈니스 로직이 JPA `@Entity`에 멱살 잡힘 | **Domain은 순수 자바**, 어댑터가 똥 치움(매핑) |
| 테스트 난이도 | 묶여 있어서 가짜 DB 띄우고 테스트해야 됨 | **포트에 Mock 객체만 끼우면 빛의 속도 테스트** |
| 보일러플레이트 | 걍 클래스 3개면 뚝딱 만듦 (초기 생산성 갑) | 포트 뚫고 매퍼 짜느라 **클래스 개수 폭발함** |

#### 한줄 요약

- 계층형은 DB 중심이고 만들기 쉽지만 나중에 망하고, 헥사고날은 도메인 중심이고 어렵지만 안 망한다.

## Ⅵ. 실무 고려사항 및 대책

<details><summary>용어 설명</summary>

- **보일러플레이트 코드(Boilerplate Code)**: 헥사고날에서 도메인 순수성 지키겠다고, 똑같이 생긴 DTO, Domain Entity, JPA Entity 파놓고 데이터 옮겨 담는 의미 없는 노가다 타이핑이다.

</details>

| 문제 | 대책 | 효과 |
|:---|:---|:---|
| 도메인 모델에 JPA 찌꺼기가 묻어서 오염됨 | **영속 Entity와 Domain 철저히 분리** 후 매핑 | DB 오라클로 바꿔도 도메인 코드는 1도 안 바뀜 |
| DTO 변환하느라 클래스 파다가 오열함 (**보일러플레이트**) | **MapStruct** 같은 매핑 자동화 라이브러리 떡칠 | 노가다성 매핑 코드 오버헤드 강력히 완화 |
| 걍 단순 게시판인데 헥사고날 박아서 폴더 구조 지옥 됨 | 닭 잡는 데 소 잡는 칼 쓰지 말고 **계층형** 타협 | 겉멋(오버 엔지니어링)으로 인한 생산성 파탄 차단 |

#### 한줄 요약

- 매핑 노가다는 라이브러리로 풀고, 단순한 앱엔 절대 헥사고날 쓰지 마라.

## Ⅶ. 결론

<details><summary>용어 설명</summary>

- **헥사고날 아키텍처 도입 판정 기준(Hexagonal Architecture Selection Criteria)**: 비즈니스 로직이 복잡해서 10년 유지보수할지, 걍 외부 API 긁어오는 쓰레기 코드인지 각 재서 구조 잡는 잣대이다.

</details>

- **헥사고날 아키텍처 도입 기준** 원칙에 따라, 핵심 도메인 로직이 목숨줄인 시스템은 **Hexagonal (DDD 결합)**, 단순 고정 DB CRUD는 **계층형(Layered)** 채택 기조 확립함

#### 한줄 요약

- 도메인 중심 설계(DDD)와 찰떡궁합인, 크고 복잡한 엔터프라이즈의 종착역 아키텍처다.
