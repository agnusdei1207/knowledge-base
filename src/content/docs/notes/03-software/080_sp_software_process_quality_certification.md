## Ⅰ. 개요

<details><summary>용어 설명</summary>

- **SP Certification (Software Process Quality Certification, 소프트웨어 프로세스 품질인증)**: 정보통신산업진흥원(NIPA)이 주관하여 국내 중소/중견 SW 기업의 프로젝트 수행 역량 및 품질 프로세스 수준을 평가하여 Level 2 또는 Level 3 인증을 부여하는 국내 법정 인증제도 (소프트웨어 진흥법 제21조).
- **NIPA (National IT Industry Promotion Agency)**: 과기정통부 산하 정보통신산업진흥원으로, 국내 SW 개발 기업의 체질 개선을 위해 SP 인증을 심사/발급하는 주관 기관.
- **GS vs SP Certification**: GS(Good Software) 인증은 SW '단품 산출물'의 품질을 인증하는 제도, SP 인증은 SW를 만들어내는 '개발 공정(Process)'의 품질을 인증하는 제도.

</details>

- 정의/개념: 국내 SW 기업의 소프트웨어 개발 프로세스 역량을 개발, 관리, 지원 등 5개 영역으로 심사하여 등급(Level 2~3)을 인증하는 국내 법정 프로세스 인증제도인 **SP (Software Process) Certification**
- 배경/필요성: 프로젝트별 수행 편차는 **납기•품질 재현성** 저하 유발

#### 한줄 요약

- 프로젝트 증적에 기반한 SP 품질인증이 핵심이다.

## Ⅱ. 특징

<details><summary>용어 설명</summary>

- **5개 영역 17개 평가항목**: 개발, 프로젝트 관리, 조직 프로세스 관리, 프로세스 개선, 지원 등 5대 영역.
- **Level 2 (프로젝트 차원)** vs **Level 3 (조직 차원)**: Level 2는 개별 프로젝트 단위의 성공적 완수 역량, Level 3는 전사 차원의 공통 프로세스 자산화 및 정량적 지속 개선 역량.

</details>

- 국내 중소/중견기업 친화적 맞춤형 심사 체계 (**CMMI 대안**)
- 2단계 등급 체계 (**Level 2: 프로젝트 관리 차원 / Level 3: 전사 조직 프로세스 차원**)
- 공공 IT 사업 입찰 참여 시 **가점(마일리지) 혜택** 및 SW 진흥법 법적 인센티브

#### 한줄 요약

- 수행 증적과 현장 수행의 일치성 평가가 핵심이다.

## Ⅲ. 구조 및 구성요소

<details><summary>용어 설명</summary>

- **17개 프랙티스**: 개발(요구사항, 설계, 구현, 테스트), 프로젝트 관리(계획, 진행통제, 위험관리, 협력업체 관리), 지원(형상관리, 품질보증), 조직 프로세스(표준, 훈련), 프로세스 개선(평가, 개선).

</details>

```text
┌─────────────────────────────────────────────────────────────────────────┐
│              SP (Software Process) 인증 5대 평가 영역                    │
├──────────────┬──────────────┬──────────────┬──────────────┬─────────────┤
│ 1. 개발      │ 2. 프로젝트  │ 3. 지원      │ 4. 조직      │ 5. 프로세스 │
│    영향 (Dev)│    관리 (PM) │    (Support) │    프로세스  │    개선     │
├──────────────┼──────────────┼──────────────┼──────────────┼─────────────┤
│ • 요구분석   │ • 사업계획   │ • 형상관리   │ • 전사 표준  │ • 성과 측정 │
│ • 구조설계   │ • 위험관리   │ • 품질보증   │ • 역량 훈련  │ • 공정 개선 │
│ • 코드구현   │ • 진행통제   │ (QA)         │              │             │
│ • 단위/통합  │ • 외주 관리  │              │ (Level 3 전용│ (Level 3 전용│
│   테스트     │              │              │  평가 영역)  │  평가 영역) │
└──────────────┴──────────────┴──────────────┴──────────────┴─────────────┘
```

선의 의미: 5대 평가 영역 중 1~3 영역은 Level 2 평가 범위, 1~5 전체 영역은 Level 3 인증 심사 범위 아키텍처.

| 인증 등급 | 평가 영역 범위 | 주요 특징 및 심사 기준 |
|:---|:---|:---|
| Level 2 (기본) | **1. 개발 + 2. 프로젝트 관리 + 3. 지원 영역 (3개 영역)** | **개별 프로젝트를 성공적으로 이끌 수 있는 프로젝트 단위 관리 능력 입증** |
| Level 3 (고급) | **1 ~ 3 영역 + 4. 조직 프로세스 + 5. 프로세스 개선 (5개 영역 전체)** | **전사 조직 차원의 표준 프로세스가 정립되고 정량적 지속 개선 체계 입증** |

#### 한줄 요약

- 표준 프로세스와 세 영역 및 실제 프로젝트 적용 증적의 구조가 핵심이다.

## Ⅳ. 흐름도

<details><summary>용어 설명</summary>

- **NIPA SP Audit**: 서류 심사 $\rightarrow$ 현장 심사(프로젝트 산출물 및 개발자/PM 인터뷰) $\rightarrow$ 시정 조치 $\rightarrow$ 심의위원회 최종 승인 4단계 절차.

</details>

```text
┌──────────────────────────────┐
│ SP 인증 신청 접수 (NIPA)     │
└──────────────┬───────────────┘
               ▼
┌──────────────────────────────┐
│ 1. 내부 진단•범위 확정       │
│ 2. 신청•증적 제출            │
│ 3. 현장 심사•인터뷰          │
│ 4. 부적합 원인 개선          │
│ 5. 인증심의회 등급 심의      │
└──────────────┬───────────────┘
               ▼
     [SP 인증서 발급 (유효3년)]
```

### 동작 원리

1. 내부 진단•범위 확정: 목표 등급과 평가 프로젝트 선정.
2. 신청•증적 제출: 영역별 절차와 실제 수행 기록 연결.
3. 현장 심사•인터뷰: 문서와 개발•관리 활동의 일치 확인.
4. 부적합 원인 개선: 결함의 근본 원인과 재발 방지 조치 수행.
5. 인증심의회 등급 심의: 증거와 개선 결과로 등급 결정.

#### 한줄 요약

- 내부 진단, 현장 심사, 인증심의회의 등급 심의 흐름이 핵심이다.

## Ⅴ. 종류 및 비교

<details><summary>용어 설명</summary>

- **SP vs CMMI**: SP 인증은 NIPA 주관의 국내 중소기업 맞춤형(비용 저렴, 심사기간 단축), CMMI는 CMU SEI 주관의 해외 대형 글로벌 가이드라인.

</details>

| 비교 항목 | SP (소프트웨어 프로세스 품질인증) | CMMI (Capability Maturity Model Integration) |
|:---|:---|:---|
| 주관 기관 | **과기정통부 / NIPA (대한민국)** | **CMMI Institute / ISACA (미국)** |
| 평가 범위 | **국내 SP 평가 영역과 프로젝트 증적** | **CMMI 실천 영역과 조직 성과 증거** |
| 등급 구조 | **Level 2 (프로젝트), Level 3 (조직)** | **Maturity Level 1 ~ Level 5 (5단계)** |
| 실무 적합성 | **국내 중소/중견 SW 기업 실정에 최적화** | 대기업 및 글로벌 해외 진출용 |
| 법적 혜택 | **공공 SW 사업 입찰 가점 부여** | 해외 국방/항공 IT 입찰 필수 요건 |

#### 한줄 요약

- 결과 품질은 프로젝트 산출물 점검, 반복 역량은 SP 품질인증으로 평가한다.

## Ⅵ. 실무 고려사항 및 대책

<details><summary>용어 설명</summary>

- **Agile/DevOps Tailoring**: 전통적 Waterfall 위주의 SP 심사 항목을 최신 애자일(Scrum) 및 DevOps 파이프라인 산출물(Jira, Git, CI/CD)로 대체 증빙하는 재단 기법.

</details>

| 문제 | 대책 | 효과 |
|:---|:---|:---|
| 심사를 위해 무의미한 페이퍼컴퍼니 문서 양산 | **Jira, Confluence, Git Commit 이력을 자동 증적으로 제출** | 서류 오버헤드 해소 |
| 3년 유효기간 만료 후 프로세스 사장 | **사후 갱신 심사 연동 및 전사 PMO 품질 템플릿 상시 운용** | 지속적 품질 유지 |
| 애자일 수행팀과 SP Waterfall 지침 충돌 | **Agile User Story 및 Sprint Backlog를 SP 요구사항 산출물로 맵핑**| 애자일 조화 달성 |

> 사례: **국내 중소 SW 솔루션 기업의 NIPA SP 인증 Level 2 획득 및 공공 사업 수주 가점 확보**

#### 한줄 요약

- 실제 도구 증적, 재단 기준, 근본 원인 개선이 핵심이다.

## Ⅶ. 결론

<details><summary>용어 설명</summary>

- **SP 인증 수립 기준(SP Certification Standards)**: NIPA SP 인증 기준, 소프트웨어 진흥법 및 기업 성장 단계별(Level 2 $\rightarrow$ Level 3) 이행에 의거한 체계.

</details>

- 프로젝트 역량은 **Level 2**, 조직 표준•개선 역량은 **Level 3** 선택

#### 한줄 요약

- 역량 적용 범위에 맞는 SP 인증 등급 선택 기준이 핵심이다.
