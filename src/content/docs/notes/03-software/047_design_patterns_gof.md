## Ⅰ. 개요

<details><summary>용어 설명</summary>

- **GoF 디자인 패턴(GoF Design Patterns)**: 객체지향 소프트웨어 설계에서 빈번히 발생하는 문제들에 대해 재사용 가능한 해결책을 23가지 형태로 정리한 설계 패턴 카탈로그.
- **생성·구조·행위 패턴(Creational, Structural, Behavioral Patterns)**: 패턴의 목적과 책임 범위에 따라 객체의 인스턴스화, 클래스/객체의 합성, 객체 간 상호작용 및 알고리즘 분배로 구분한 3대 분류 체계.

</details>

- 정의/개념: 객체지향 설계의 재사용성과 유연성을 높이기 위해 검증된 객체 생성, 구조 결합, 행위 위임 전략을 23가지 표준 형태로 정립한 **GoF 디자인 패턴**
- 배경/필요성: 무분별한 결합도 증가 및 하드코딩으로 인한 코드 변경의 파급 효과를 완화하고, SOLID 원칙을 구현하는 표준화된 아키텍처 어휘 요구

#### 한줄 요약
- 객체지향 설계의 반복적 문제를 해결하기 위해 생성, 구조, 행위 관점으로 표준화한 23가지 설계 템플릿이다.

## Ⅱ. 특징

<details><summary>용어 설명</summary>

- **SOLID 원칙**: 단일 책임(SRP), 개방-폐쇄(OCP), 리스코프 치환(LSP), 인터페이스 분리(ISP), 의존역전(DIP)으로 구성된 객체지향 5대 설계 원칙.
- **패턴 과용(Pattern Overengineering)**: 단순한 문제에 불필요하게 복잡한 다중 패턴을 도입하여 시스템 복잡도와 유지보수 비용을 증가시키는 안티패턴.

</details>

- 목적별 3대 분류 체계: **생성 패턴 5종, 구조 패턴 7종, 행위 패턴 11종** 으로 구조화
- 인터페이스 기반 다형성과 객체 합성을 활용하여 **개방-폐쇄 원칙(OCP)** 및 **의존역전 원칙(DIP)** 실현
- 엔지니어 간의 아키텍처 의도 전달을 명확히 하는 **공통 설계 어휘(Common Vocabulary)** 기능 수행

#### 한줄 요약
- 생성, 구조, 행위의 3대 축으로 분류되며, 결합도를 낮추고 공통 설계 어휘를 제공한다.

## Ⅲ. 구조 및 구성요소

<details><summary>용어 설명</summary>

- **생성 패턴(Creational)**: 객체의 생성 메커니즘을 캡슐화하여 인스턴스화 과정의 결합도를 낮추는 패턴.
- **구조 패턴(Structural)**: 클래스나 객체를 조합하여 더 큰 구조를 형성하면서도 유연성을 유지하는 패턴.
- **행위 패턴(Behavioral)**: 객체 간의 책임 분배와 알고리즘 제어 흐름을 정의하는 패턴.

</details>

```text
[ GoF 23종 디자인 패턴 분류 ]
 ├─ 생성 패턴 (5종): Singleton, Factory Method, Abstract Factory, Builder, Prototype
 ├─ 구조 패턴 (7종): Adapter, Bridge, Composite, Decorator, Facade, Flyweight, Proxy
 └─ 행위 패턴 (11종): Chain of Responsibility, Command, Interpreter, Iterator,
                       Mediator, Memento, Observer, State, Strategy, Template Method, Visitor
```

선의 의미: `├─`는 23종 패턴의 목적별 3대 분류 계층

| 구성요소 | 책임 |
|:---|:---|
| **생성 패턴 (5종)** | 객체 생성 과정을 추상화하여 특정 클래스에 종속되지 않는 인스턴스화 제어 |
| **구조 패턴 (7종)** | 인터페이스 변환, 기능 동적 확장 및 복잡한 서브시스템 단순화를 위한 객체 합성 |
| **행위 패턴 (11종)** | 알고리즘 교체, 이벤트 통지 및 상태 전이 책임을 독립 객체로 위임하여 결합도 최소화 |

#### 한줄 요약
- 객체 생성의 유연성, 구조적 합성의 확장성, 행위 위임의 독립성을 담당하는 3개 그룹으로 구성된다.

## Ⅳ. 흐름도

<details><summary>용어 설명</summary>

- **상충관계 평가(Trade-off Analysis)**: 디자인 패턴 도입으로 얻는 유연성 이점과 클래스 증가로 인한 복잡성 비용을 정량/정성적으로 비교 분석하는 과정.

</details>

```text
1. 설계 결함 및 변경 요구 식별 (예: 잦은 알고리즘 변경 요구)
            │
            ▼
2. 문제 성격 분석: 생성, 구조, 행위 중 해결 대상 도메인 영역 판정
            │
            ▼
3. 적합 디자인 패턴 매핑: 요구사항에 부합하는 GoF 패턴 후보군 도출
            │
            ▼
4. 복잡도 대비 유연성 상충관계 평가: 클래스 증가 비용과 확장성 이점 비교
            │
            ▼
5. 패턴 적용 및 리팩토링: 인터페이스 정의 및 구현체 분리 완료
```

**동작 원리**

1. **문제 식별**: 코드 중복, 잦은 조건문 분기(`if-else`), 높은 결합도 등의 설계 냄새(Design Smell) 탐지
2. **도메인 분석**: 인스턴스 생성의 문제인지, 모듈 결합의 문제인지, 제어 흐름의 문제인지 분류
3. **패턴 선정**: GoF 23종 중 의도(Intent)가 일치하는 최적 패턴 매핑(예: 알고리즘 교체 시 Strategy 패턴)
4. **비용 분석**: 패턴 도입에 따른 추상화 계층 증가 오버헤드와 향후 유지보수 편익 평가
5. **리팩토링**: 인터페이스와 위임(Delegation)을 적용하여 기존 코드를 구조화

#### 한줄 요약
- 설계 문제를 분석하여 적합한 패턴을 매핑하고, 복잡도와 유연성의 상충관계를 평가하여 적용한다.

## Ⅴ. 종류 및 비교

<details><summary>용어 설명</summary>

- **전략 패턴(Strategy)**: 동일 계열의 알고리즘들을 캡슐화하여 상호 교환 가능하도록 만드는 행위 패턴.
- **템플릿 메서드 패턴(Template Method)**: 알고리즘의 골격을 상위 클래스에 정의하고 세부 단계를 하위 클래스에서 오버라이드하는 행위 패턴.

</details>

| 핵심 패턴 | 분류 | 주요 의도 및 적용 기준 |
|:---|:---|:---|
| **Singleton** | 생성 | 시스템 전역에서 단 하나의 인스턴스만 유지하고 글로벌 접근점 제공 |
| **Factory Method** | 생성 | 객체 생성을 하위 클래스에 위임하여 인스턴스화 결합도 완화 |
| **Adapter** | 구조 | 호환되지 않는 인터페이스를 클라이언트가 요구하는 인터페이스로 변환 |
| **Decorator** | 구조 | 상속 대신 객체 합성을 통해 런타임에 동적으로 기능 확장 |
| **Proxy** | 구조 | 실제 객체에 대한 접근을 제어하거나 지연 로딩(Lazy Loading), 보안 검증 수행 |
| **Strategy** | 행위 | 런타임에 클라이언트 요구에 따라 알고리즘 군을 동적으로 교체 |
| **Observer** | 행위 | 일대다 객체 의존성을 정의하여 상태 변경 시 모든 구독 객체에 자동 통지 |

#### 한줄 요약
- 생성(Singleton, Factory), 구조(Adapter, Proxy), 행위(Strategy, Observer) 등 목적에 따라 패턴을 선별한다.

## Ⅵ. 실무 고려사항 및 대책

<details><summary>용어 설명</summary>

- **YAGNI(You Aren't Gonna Need It)**: 실제로 요구사항이 발생하기 전까지는 미래를 예측한 불필요한 기능이나 과도한 추상화를 구현하지 않는 소프트웨어 개발 원칙.

</details>

| 문제 | 대책 | 효과 |
|:---|:---|:---|
| 단순 기능에 과도한 패턴 적용으로 인한 가독성 저하 (**패턴 과용**) | **YAGNI** 및 KISS 원칙을 준수하고 실질적 변경 발생 시점에 리팩토링 | 불필요한 추상화 방지 및 코드 단순성 유지 |
| 단순 패턴 적용으로 인한 클래스 수 급증 및 관리 오버헤드 | 최신 언어의 **함수형 인터페이스 / 람다식(Lambda)** 적극 활용 | 보일러플레이트 코드 제거 및 경량화 달성 |
| 패턴 설계 의도 미공유로 인한 유지보수 시 구조 훼손 | 아키텍처 의사결정 기록(**ADR**) 작성 및 클래스 다이어그램 문서화 | 설계 의도 보존 및 후속 개발자의 일관된 확장 지원 |

#### 한줄 요약
- YAGNI 원칙을 통해 과도한 추상화를 경계하고, 함수형 기법과 ADR 문서화로 관리 비용을 최적화한다.

## Ⅶ. 결론

- 변동성과 확장 요구가 명확한 핵심 도메인 영역에 한해 **GoF 디자인 패턴**을 선별 적용하되, 단순한 CRUD 로직에는 **YAGNI** 원칙을 우선하여 불필요한 복잡도 증가를 방지하고 유지보수성을 극대화

#### 한줄 요약
- 비즈니스 변경 가능성과 유지보수 비용을 평가하여 필요한 구간에 한해 디자인 패턴을 적용한다.
