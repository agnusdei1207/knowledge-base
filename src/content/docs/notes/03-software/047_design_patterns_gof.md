## Ⅰ. 개요

<details><summary>용어 설명</summary>

- **GoF 23종 디자인 패턴(GoF Design Patterns)**: Gang of Four(4인방)가 객체지향에서 맨날 터지는 문제들을 모아다가 "이럴 땐 이렇게 짜라"고 족보를 만들어 둔 23가지 코드 설계 복붙 템플릿이다.
- **생성/구조/행위(Creational/Structural/Behavioral)**: 23개 패턴을 목적에 따라 쪼갠 3대장. 객체를 어떻게 찍어낼지(생성), 덩어리를 어떻게 조립할지(구조), 객체끼리 어떻게 핑퐁 칠지(행위)로 나눈다.

</details>

- 정의: 객체지향 소프트웨어 설계에서 반복적으로 나타나는 뻔한 문제들을 풀기 위해, 4인방(GoF)이 정리한 23가지 재사용 가능한 설계 족보 모음집인 **GoF Design Patterns**
- 배경: 코드를 짤 때마다 맨땅에 헤딩하면 **개발자마다 코드 스타일이 달라서 스파게티가 되고**, "야 그거 싱글톤으로 짜" 같은 빠른 커뮤니케이션이 불가능하기 때문

#### 한줄 요약

- 코드 짜다 막힐 때 꺼내 보는, 선배 개발자들이 남겨둔 23가지 모범 답안지(족보)다.

## Ⅱ. 특징

<details><summary>용어 설명</summary>

- **패턴 중독(Patternitis)**: 걍 `if-else` 한 줄이면 끝날 단순한 로직인데, 책에서 배운 거 써먹어 보겠다고 팩토리 만들고 전략 패턴 적용하여 코드를 안드로메다로 보내버리는 극혐 오남용 상태이다.

</details>

- 목적에 따라 **생성 5종, 구조 7종, 행위 11종** 3대 분류로 쪼개놓음.
- 결국은 SOLID 원칙(특히 OCP, DIP)을 잘 지키게 만들어주는 **실전 압축 가이드**임.
- 개발자들끼리 "여기에 싱글톤 박고 어댑터로 빼자"라고 말하면 다 알아듣게 만드는 **공통 언어(Common Language)** 역할을 함.

#### 한줄 요약

- 생성, 구조, 행위로 나뉘며, 개발자들끼리 말이 통하게 해주는 설계 표준어다.

## Ⅲ. 구조 및 구성요소

<details><summary>용어 설명</summary>

- **3대 패턴 분류**: 생성(Creational - 객체를 찰지게 찍어냄), 구조(Structural - 클래스를 예쁘게 합침), 행위(Behavioral - 객체끼리 역할 분담함).

</details>

```text
[ GoF 23종 패턴 십자포화 아키텍처 분류 ]

┌───────────────────────────┬───────────────────────────┬───────────────────────────┐
│ 🏭 생성 패턴 (5종)        │ 🧱 구조 패턴 (7종)        │ 🏃 행위 패턴 (11종)       │
├───────────────────────────┼───────────────────────────┼───────────────────────────┤
│ Singleton, Factory,       │ Adapter, Decorator,       │ Strategy, Observer,       │
│ Builder 등                │ Proxy, Facade 등          │ Template Method 등        │
└───────────────────────────┴───────────────────────────┴───────────────────────────┘
```

| 구성요소 | 직관적 비교 책임 |
|:---|:---|
| **생성 (Creational)** | 객체 만들 때 `new` 아무 데서나 치지 말고, 깔끔하게 공장(Factory) 등에 맡겨서 결합도를 낮춤 |
| **구조 (Structural)** | 짜잘한 클래스들을 레고처럼 조립해서, 더 크고 강력한 구조물(Facade, Decorator)을 찍어냄 |
| **행위 (Behavioral)** | 객체들끼리 어떻게 역할 분담을 하고 대화를 나눌지(Strategy, Observer) 알고리즘을 짬 |

#### 단답 요약

- 어떻게 만들까(생성), 어떻게 합칠까(구조), 어떻게 굴릴까(행위)로 나뉜다.

## Ⅳ. 흐름도

<details><summary>용어 설명</summary>

- **패턴 선택 흐름(Pattern Selection Flow)**: 에러 터지면 무작정 패턴부터 박는 게 아니라, 상황(Context) 파악 $\to$ 생성/구조/행위 중 하나 고르기 $\to$ 최적 패턴 꽂아 넣기의 3단 논리 회로이다.

</details>

```text
[ 디자인 패턴 적용 십자포화 흐름 ]
┌──────────────────────────────┐
│ 1. 꼬여버린 설계 문제 발생   │
│ (ex. 로직 갈아끼우기가 빡셈) │
└──────────────┬───────────────┘
               ▼
┌──────────────────────────────┐
│ 2. 문제 성격 분석 (Context)  │
│ (이건 '행위'를 바꾸는 문제군)│
└──────────────┬───────────────┘
               ▼
┌──────────────────────────────┐
│ 3. 최적의 패턴 매핑          │
│ (행위 교체? ➔ 전략 패턴!)   │
└──────────────┬───────────────┘
               ▼
┌──────────────────────────────┐
│ 4. 상충 관계(Trade-off) 평가 │
│ (클래스 쪼개지는데 감당 됨?) │
└──────────────┬───────────────┘
               ▼
┌──────────────────────────────┐
│ 5. 패턴 적용 및 리팩토링 끝  │
└──────────────────────────────┘
```

### 동작 원리

1. 문제 발생: `if-else`가 100줄을 넘어가거나 클래스가 뚱뚱해짐.
2. 성격 분석: 뼈대를 고칠 거냐(생성), 레고를 합칠 거냐(구조), 톱니를 갈아 끼울 거냐(행위) 판단.
3. 패턴 매핑: 23종 중에서 가장 찰떡인 놈을 골라옴. (ex. "이건 옵저버다!")
4. 상충 관계 평가: 패턴 쓰면 유연해지지만 코드가 복잡해지는 단점을 저울질함.
5. 적용: 떡진 코드를 패턴 족보에 맞춰 예쁘게 분리함.

#### 한줄 요약

- 아프면(문제) $\to$ 진찰하고(분류) $\to$ 약을 고르고(패턴) $\to$ 부작용을 따져서 처방한다.

## Ⅴ. 종류 및 비교

<details><summary>용어 설명</summary>

- **전략(Strategy) vs 템플릿 메서드(Template Method)**: 로직 바꿀 때, 껍데기만 두고 통째로 갈아 끼우면 '전략(Strategy)', 부모가 뼈대 잡고 자식이 빈칸 채우면 '템플릿 메서드'이다.

</details>

| 핵심 패턴 명칭 | 분류 | 패턴 핵심 의도 팩폭 |
|:---|:---|:---|
| **Singleton** (싱글톤) | 생성 | 메모리에 딱 한 놈만 띄워놓고 온 동네가 다 같이 돌려씀 (Spring Bean 국룰) |
| **Factory Method** (팩토리) | 생성 | `new` 안 치고, 객체 찍어내는 전용 공장(공장장)한테 위임함 |
| **Adapter** (어댑터) | 구조 | 110V 코드를 220V 콘센트에 꽂을 수 있게 돼지코 역할로 변환해 줌 |
| **Decorator** (데코레이터)| 구조 | 상속 안 받고 껍데기에 계속 새로운 기능(토핑)을 겹겹이 덧붙임 (Java I/O) |
| **Proxy** (프록시) | 구조 | 찐 객체 앞에 비서 세워두고, 게으른 로딩이나 검문(보안/AOP)을 짬처리함 |
| **Strategy** (전략) | 행위 | 네비 경로 찾기처럼 상황에 따라 알고리즘(전략)을 통째로 슉슉 갈아 끼움 |
| **Observer** (옵저버) | 행위 | 유튜버(Subject)가 영상 올리면 구독자들한테 알람 쫙 뿌림 |

#### 한줄 요약

- 딱 하나만 쓰면 싱글톤, 갈아 끼우면 전략 패턴, 알람 뿌리면 옵저버 패턴이다.

## Ⅵ. 실무 고려사항 및 대책

<details><summary>용어 설명</summary>

- **YAGNI (You Aren't Gonna Need It)**: "미래에 쓸지도 몰라" 하며 오만가지 패턴을 미리 박아두는 설레발을 치지 마라. 어차피 안 쓰니까 제발 심플하게 짜라는 극단적 절제 원칙이다.

</details>

| 문제 | 대책 | 효과 |
|:---|:---|:---|
| 단순 로직에 패턴 적용하여 가독성 멸망함 (**패턴 중독**) | **YAGNI** 원칙 들이대서 제발 무식하고 단순한 코드로 유지 | 코드 스파게티화 및 복잡성 폭주 방어 |
| 패턴 썼더니 꼴랑 한 줄짜리 클래스가 10개씩 무한 증식함 | Java 8+ **람다(Lambda)나 함수형 기능** 기반 대체 | 클래스 폭발 막고 코드 다이어트 성공 |
| 신입이 디자인 패턴 몰라서 코드 보고 어리둥절함 | 주석 빡세게 달고 설계 문서(**ADR**)에 "왜 썼는지" 변명 적어둠 | 유지보수할 때 욕먹는 리스크 해소 |

#### 한줄 요약

- 괜히 아는 척하려고 패턴 쓰다 코드 망치지 말고, 진짜 필요할 때만 써라.

## Ⅶ. 결론

<details><summary>용어 설명</summary>

- **GoF 패턴 채택 기준(GoF Pattern Adoption Criteria)**: 코드가 앞으로 얼마나 자주 바뀔지(확장성), 팀원들이 패턴을 이해할 짬바가 되는지 각을 재서 패턴을 박을지 정하는 잣대이다.

</details>

- **GoF 패턴 채택 기준** 원칙에 따라, 확장 가능성이 열려 있는 핵심 도메인엔 **GoF 패턴** 박고, 단순 CRUD는 제발 **YAGNI** 채택 기조 확립함

#### 한줄 요약

- 디자인 패턴은 만병통치약이 아니다. SOLID 원칙을 지키기 위한 도구일 뿐이다.
