## Ⅰ. 개요

<details><summary>용어 설명</summary>

- **Journaling(저널링)**: 파일 시스템 변경 사항을 실제 스토리지 블록(Home Block)에 반영하기 전, 별도의 로그 영역(Journal)에 선행 기록(WAL)하여 비정상 종료 시 신속한 무결성 복구를 보장하는 기술.
- **fsck(File System Consistency Check)**: 저널링 미적용 파일 시스템에서 비정상 종료 후 전체 디스크 메타데이터 구조를 전수 탐색(Full Scan)하여 불일치를 교정하는 복구 유틸리티.

</details>

- 정의/개념: 파일 시스템 변경 사항을 물리 블록(Home Block)에 기록하기 전 **선행 로그 기록(WAL: Write-Ahead Logging)** 원칙에 따라 저널 영역에 트랜잭션을 커밋하여 장애 일관성을 보장하는 기술
- 배경/필요성: 시스템 비정상 다운 시 발생하는 **메타데이터 불일치 및 대용량 스토리지 전수 검사(fsck)에 따른 장시간 서비스 중단 한계 극복** 필요

#### 한줄 요약

- 선행 로그 기록(WAL)을 통해 장애 발생 시 전체 검사 없이 저널 리플레이만으로 신속한 일관성을 복구하는 기법

## Ⅱ. 특징

<details><summary>용어 설명</summary>

- **WAL(Write-Ahead Logging, 선행 로그 기록)**: 실제 데이터/메타데이터를 원래 디스크 위치에 기록하기 전에 반드시 해당 트랜잭션 로그를 저널 영역에 먼저 커밋해야 한다는 원칙.
- **Checkpoint(체크포인트)**: 저널에 커밋된 트랜잭션 블록들을 실제 파일 시스템 데이터 블록으로 동기화(Flushing)하고 저널 공간을 회수하는 주기적 작업.

</details>

- **선행 로그 기록(WAL)** 원칙 준수를 통한 트랜잭션 원자성 및 장애 복구성 확보
- 전체 디스크 전수 검사(`fsck`)를 배제하고 커밋된 **저널 로그 리플레이(REDO)** 만으로 수 초 내 마운트 복구
- 무결성과 성능의 트레이드오프에 따른 3가지 저널링 모드(**Journal, Ordered, Writeback**) 지원

#### 한줄 요약

- **WAL 원칙 기반 트랜잭션 보장·초고속 저널 리플레이 복구·3단계 저널링 모드(Journal/Ordered/Writeback) 제공** ## Ⅲ. 구조 및 구성요소

<details><summary>용어 설명</summary>

- **Transaction Block(트랜잭션 블록)**: Inode 갱신, 비트맵 수정 등 단일 파일 연산에 수반되는 다수의 메타데이터 변경을 원자적 단위(All-or-Nothing)로 묶어 관리하는 블록.

</details>

```text
[ 파일 시스템 저널링 트랜잭션 및 복구 아키텍처 ]
               [ 파일 I/O 변경 요청 ]
                         │
               [ JBD2 트랜잭션 관리자 ]
           (원자적 트랜잭션 Descriptor 구성)
                         │
                         ▼
        ┌────────────────────────────────┐
        │   저널 영역 (Journal Device)    │
        │ ├─ Descriptor Block (메타 정보) │
        │ ├─ Data/Metadata Payload       │
        │ └─ Commit Block (커밋 완료 마크) │
        └────────────────┬───────────────┘
                         │
          ┌──────────────┴──────────────┐
          ▼                             ▼
   [ 정상 동작 시 ]              [ 장애 재부팅 시 ]
   체크포인트(Checkpoint)        저널 리플레이(REDO)
   실제 Home Block에 반영        커밋된 트랜잭션 복원
          │                             │
          └──────────────┬──────────────┘
                         ▼
             [ 실제 파일 시스템 블록 (Home Block) ]
```

선의 의미: 트랜잭션 관리자가 저널에 선행 기록하고, 정상 시 체크포인트로 실제 블록에 기록하며 장애 시 리플레이로 복구하는 구조.

| 구성요소 | 책임 |
|:---|:---|
| JBD2 트랜잭션 관리자 | 복수의 메타데이터 변경 작업을 단일 원자적 트랜잭션 단위로 그룹화 |
| 저널 영역 (Journal) | 디스크 내 격리된 순환 버퍼로, 트랜잭션 페이로드 및 Commit Block 선행 기록 |
| 체크포인트 처리기 | 저널에 커밋된 트랜잭션 데이터를 실제 Home Block으로 비동기 플러시 후 저널 헤드 갱신 |
| 복구 관리자 (Recovery) | 마운트 시 저널을 스캔하여 Commit Block이 존재하는 유효 트랜잭션만 REDO 복구 |

#### 한줄 요약

- **트랜잭션 관리자·저널 로그 영역(Descriptor/Commit)·체크포인트 플러시·REDO 복구 엔진** ## Ⅳ. 흐름도

<details><summary>용어 설명</summary>

- **Journal Replay(저널 리플레이)**: 비정상 종료 후 재부팅 마운트 시 저널 영역을 스캔하여 커밋 마크가 완료된 트랜잭션을 실제 Home Block에 재적용(REDO)하는 복구 프로세스.

</details>

```text
[ 저널 트랜잭션 라이프사이클 및 복구 시퀀스 ]
 1. 파일 변경 트랜잭션 생성 (Inode, Bitmap 등 갱신)
          │
          ▼
 2. 저널 영역에 Descriptor 및 메타데이터 블록 쓰기
          │
          ▼
 3. 저널 Commit Block 기록 및 캐시 플러시 (트랜잭션 확정)
          │
          ├─────────────────────────────┐
          ▼ (정상 운용 시)              ▼ (전원 차단 등 장애 발생 시)
 4-1. 체크포인트 비동기 수행    4-2. 재부팅 후 파일 시스템 마운트
      (Home Block으로 데이터 반영)     저널 영역 스캔 및 Commit 검증
          │                             │
 5-1. 저널 트랜잭션 해제        5-2. 커밋된 트랜잭션 REDO 리플레이
                                     (미커밋 불완전 트랜잭션 폐기)
```

**동작 원리** 1. **트랜잭션 캡슐화**: 파일 변경에 필요한 Inode, 디렉터리 엔트리, 블록 할당 비트맵 수정을 하나의 트랜잭션으로 구성
2. **저널 선행 기록 (WAL)**: 실제 Home Block을 수정하기 전 저널 영역에 Descriptor와 변경 블록을 순차 기록
3. **Commit Block 기록**: 트랜잭션의 모든 블록이 물리 저널에 기록 완료되면 Commit Block을 기록하여 트랜잭션 완료 확정
4. **체크포인트 동기화**: 백그라운드 데몬이 커밋된 데이터를 실제 Home Block으로 복사하고 저널 버퍼 공간 회수
5. **장애 복구(Recovery)**: 비정상 종료 후 마운트 시 저널을 검사하여 Commit Block이 있는 트랜잭션만 순차 재적용(REDO)

#### 한줄 요약

- **트랜잭션 생성 $\to$ 저널 선행 기록(WAL) $\to$ Commit Block 확정 $\to$ 체크포인트 동기화 / 장애 시 REDO 리플레이** ## Ⅴ. 종류 및 비교

<details><summary>용어 설명</summary>

- **Ordered Mode(순서화 저널링)**: 실제 파일 데이터 블록을 Home Block에 먼저 기록한 후 메타데이터만을 저널에 기록하여 성능과 무결성의 최적 균형을 제공하는 리눅스 기본 모드.

</details>

| 저널링 모드 (ext4) | 동작 메커니즘 | 장단점 및 트레이드오프 | 주 적용 환경 |
|:---|:---|:---|:---|
| **Journal (Full)** | 데이터와 메타데이터 모두를 저널에 먼저 기록 후 Home Block 반영 | **최고 수준 무결성 보장**, 그러나 이중 쓰기로 인한 **I/O 처리량 대폭 저하** | 고신뢰성 금융 트랜잭션 DB |
| **Ordered (기본값)** | 실제 데이터 블록을 Home Block에 먼저 쓴 후 메타데이터만 저널에 기록 | 메타데이터 무결성 보장 및 이전 데이터 노출 방지, **우수한 성능과 안정성 균형** | 일반 리눅스 서버 및 범용 엔터프라이즈 |
| **Writeback** | 메타데이터만 저널에 기록하며 데이터 쓰기 순서를 보장하지 않음 | **최고의 I/O 성능**, 그러나 비정상 종료 시 파일 내 쓰레기 데이터 유입 위험 | 임시 캐시 및 재현 가능한 연산 워크로드 |

#### 한줄 요약

- 완전 무결성은 **Journal 모드**, 범용 최적 표준은 **Ordered 모드**, 극한의 성능은 **Writeback 모드** ## Ⅵ. 실무 고려사항 및 대책

<details><summary>용어 설명</summary>

- **Write Barrier(쓰기 장벽)**: 스토리지 장치의 내부 휘발성 캐시 재정렬로 인해 Commit Block이 실제 데이터보다 먼저 디스크 플래터/NAND에 기록되는 것을 차단하는 하드웨어 플러시 동기화 명령.

</details>

| 문제 | 대책 | 효과 |
|:---|:---|:---|
| 스토리지 캐시 재정렬로 인한 **WAL 커밋 순서 역전 및 저널 손상** | 파일 시스템 마운트 시 **Write Barrier(바리어) 활성화**(`barrier=1`) | 하드웨어 쓰기 순서 강제 및 장애 시 저널 무결성 보장 |
| 전체 저널링(Journal 모드) 사용 시 **SSD 쓰기 증폭(WAF) 급증 및 수명 단축** | 저널링 모드를 **`data=ordered`** 로 구성하여 메타데이터만 로깅 | 불필요한 이중 쓰기 방지 및 SSD 내구성 확보 |
| 잦은 파일 읽기 시 접근 시간(atime) 갱신으로 인한 **지속적 저널 쓰기 부하** | 마운트 옵션에 **`noatime` 또는 `relatime` 적용** | 불필요한 메타데이터 저널 트래픽 차단 및 I/O 성능 향상 |

#### 한줄 요약

- **Write Barrier 기반 WAL 순서 강제·Ordered 모드 기반 SSD 수명 보호·noatime 기반 메타 I/O 절감** ## Ⅶ. 결론

<details><summary>용어 설명</summary>

- **Journaling Mode Selection Strategy**: 데이터의 가치, I/O 성능 요구량, 스토리지 미디어의 쓰기 내구성을 종합적으로 고려하여 최적의 저널링 모드를 구성하는 설계 기준.

</details>

- 리눅스 엔터프라이즈 운영체제는 기본적으로 **`data=ordered` 모드와 Write Barrier 활성화** 활용 표준으로 채택하며, 읽기 집약 환경에서는 **`noatime`** 병행 적용 필수

#### 한줄 요약

- **WAL 기반 저널링과 적정 모드 튜닝** 통해 스토리지 I/O 성능과 시스템 장애 복구 신뢰성 동시 확보
