## Ⅰ. 개요

<details><summary>용어 설명</summary>

- **저널링(Journaling)**: 파일 덮어쓰다 전원 날아가서 하드디스크가 벽돌 되는 걸 막기 위해, 진짜 디스크에 쓰기 전에 저널(비밀 장부)에 먼저 "나 이거 쓸 거임" 하고 1차 기록을 남기는 보험 기술이다.
- **fsck (File System Check)**: 옛날에 저널링 없던 시절, 컴퓨터 뻑나면 수백 기가 하드디스크를 처음부터 끝까지 싹 다 뒤져서(풀스캔) 꼬인 걸 푸느라 부팅에 한세월 걸리게 하던 악명 높은 복구 명령어이다.

</details>

- 정의: 파일 변경 사항을 진짜 블록(Home Block)에 박기 전에 **저널(Journal Log)** 영역에 먼저 커밋(Commit)해서 전원 차단 시 롤백/복구하는 기술
- 배경: 컴퓨터 쓰다 뻑나면 디스크 쓰다 만 찌꺼기 때문에 **메타데이터가 꼬여서** 파일이 통째로 증발해버리기 때문

#### 한줄 요약

- 디스크에 쓰기 전에 장부에 먼저 기록(WAL)해서, 뻑나면 장부만 보고 1초 만에 복구하는 기술이다.

## Ⅱ. 특징

<details><summary>용어 설명</summary>

- **선행 로그 기록(Write-Ahead Logging, WAL)**: 묻지도 따지지도 않고 무조건 디스크(진짜 블록) 갱신보다 저널(장부) 갱신을 먼저 완벽하게 끝내야 한다는 저널링의 제1원칙이다.
- **체크포인트(Checkpoint)**: 저널 장부에 써둔 밀린 일거리(트랜잭션)들을 주기적으로 진짜 하드디스크 빈자리에 쓱싹 이사(동기화)시키고 장부를 비우는 청소 작업이다.

</details>

- **WAL(Write-Ahead Logging)** 원칙으로 장부 먼저 써서, 뻑나면 장부만 보고 초스피드로 복구함.
- 장애 시 풀스캔(fsck) 똥꼬쇼 버리고, 커밋된 **저널 로그(Journal Log)** 만 딱 읽어서 1초 만에 일관성을 살려냄.
- 성능이랑 데이터 보호 중에서 뭘 포기할지에 따라 **Writeback, Ordered, Journal** 모드로 뼈대를 고름.

#### 한줄 요약

- 디스크보다 장부에 먼저 쓰는 WAL 원칙으로 풀스캔(fsck)의 저주를 풀고 빛의 속도로 복구한다.

## Ⅲ. 구조 및 구성요소

<details><summary>용어 설명</summary>

- **트랜잭션 블록(Transaction Block)**: 파일 하나 지울 때 엮여 있는 수많은 장부(Inode, 권한, 블록 맵) 갱신 작업을 "전부 다 하거나 아예 안 하거나(All or Nothing)"로 묶어버리는 논리적 커밋 단위이다.

</details>

```text
[ 파일 시스템 저널링 십자포화 아키텍처 ]
         [ 파일 변경 요청 ]
                 │
        [ 트랜잭션 관리자 ]
  (여러 작업을 All-or-Nothing으로 묶음)
                 │
┌────────────────┴────────────────┐
▼ WAL 기록                        ▼ WAL 기록 안됨
[ 저널 영역 (장부) ]             [ 비정상 종료 (뻑남) ]
(WAL 로그, 커밋 마크)        (장부에 커밋 없으면 걍 버림)
│           └───────────┐
│                       ▼
│ 주기적 동기화       [ 복구기 (Recovery) ]
▼                 (부팅 시 장부 보고 REDO 복구)
[ 체크포인트 처리기 ]
(진짜 하드디스크로 데이터 이송)
```

| 구성요소 | 책임 |
|:---|:---|
| 트랜잭션 관리자 | 파일 수정 작업들을 모아서 "전부 성공 아니면 전부 취소" 단위로 멱살 잡고 묶는 통제관 |
| **저널 영역 (Journal)** | 디스크 구석에 처박아둔 전용 장부로, **WAL 로그**와 커밋 표식을 가장 먼저 때려 박는 임시 대피소 |
| 체크포인트 처리기 | 장부에 커밋 끝난 데이터를 틈틈이 실제 하드디스크(**Home Block**)로 이송하고 장부 지우는 청소부 |
| 복구기 (Recovery) | 컴퓨터 뻑나서 재부팅될 때, 장부만 싹 까보고 커밋된 건 **REDO(재생)**, 안 된 건 가차 없이 버리는 구원자 |

#### 한줄 요약

- 트랜잭션 단위로 묶어서 장부(저널)에 박고, 나중에 체크포인트가 진짜 디스크로 짐을 옮긴다.

## Ⅳ. 흐름도

<details><summary>용어 설명</summary>

- **저널 리플레이(Journal Replay, REDO)**: 컴퓨터가 비정상적으로 꺼진 후 다시 켜질 때, 장부에 커밋 도장(Commit Mark)이 찍혀 있는 데이터만 골라서 진짜 디스크에 다시 덮어써 버리는 구원 작업이다.

</details>

```text
[ WAL 기반 저널 커밋 및 복구 십자포화 흐름 ]
┌──────────────────────────────┐
│ 1. 트랜잭션 패키징           │
│ (파일 쓰기 작업을 묶음)      │
└──────────────┬───────────────┘
               ▼
┌──────────────────────────────┐
│ 2. WAL 로깅 (저널 영역 쓰기) │
│ (실제 디스크 전에 장부에 씀) │
└──────────────┬───────────────┘
               ▼
┌──────────────────────────────┐
│ 3. 커밋(Commit) 마크 찍기    │
│ (여기까지 쓰면 데이터 생존)  │
└───────┬───────────────┬──────┘
        │               │
[4. 체크포인트 핑]  [5. 뻑나서 재부팅 핑]
(정상: 디스크 씀)   (장애: 저널 리플레이)
```

### 동작 원리

1. 트랜잭션 구성: 파일 저장, 이름 변경 같은 작업들을 묶어서 패키징함.
2. 변경 레코드 로깅 (WAL): 진짜 디스크 건드리기 전에 **저널 장부**에 먼저 기록함.
3. 커밋 레코드 지속화: 저널에 데이터 다 썼으면 "나 다 썼다"고 **Commit Block** 도장을 쾅 찍음.
4. 체크포인트 반영 (정상): 시스템이 널널할 때, 커밋된 데이터를 장부에서 꺼내서 진짜 **Home Block**에 써버림.
5. 저널 재생 (장애 복구): 부팅하다 뻑났으면 fsck 안 돌리고 저널 장부만 뒤져서 커밋 도장 있는 놈만 **REDO(리플레이)** 로 수습함.

#### 한줄 요약

- 장부에 커밋 도장 찍히기 전에 죽으면 롤백, 도장 찍히고 죽으면 부팅 시 리플레이(REDO)로 부활시킨다.

## Ⅴ. 종류 및 비교

<details><summary>용어 설명</summary>

- **오더드 모드(Ordered Mode)**: 리눅스(ext4)의 국룰 모드로, 데이터는 진짜 디스크에 먼저 냅다 쓰고 장부에는 껍데기(메타데이터)만 적어서 성능과 안정성을 기가 막히게 줄타기하는 방식이다.

</details>

| 저널링 모드 (ext4) | 동작 메커니즘 (어떻게 쓰나) | 장단점 및 팩트폭력 |
|:---|:---|:---|
| **Journal** (Full) | 데이터랑 메타데이터를 통째로 저널에 썼다가 디스크로 또 옮김 | 가장 완벽하게 복구되지만, 데이터 용량 2배로 갉아먹어서 **I/O 성능 최악** |
| **Ordered** (국룰) | 진짜 데이터는 디스크에 냅다 박고, 족보(메타데이터)만 장부에 적음 | 성능 깎이는 걸 방어하면서 치명적인 꼬임도 막아주는 **황금 밸런스** |
| **Writeback** | 순서 안 지키고 메타데이터만 대충 장부에 씀 | 젤 빠르지만, 뻑나면 남의 파일 내용 튀어나오는(Trash Data) **대형 사고 유발** |

#### 한줄 요약

- 속도와 안정성을 모두 챙기는 Ordered 모드가 현시대 리눅스의 압도적 국룰이다.

## Ⅵ. 실무 고려사항 및 대책

<details><summary>용어 설명</summary>

- **쓰기 장벽(Write Barrier)**: SSD나 하드디스크가 지 맘대로 속도 올리겠다고 쓰는 순서(캐시)를 뒤죽박죽 섞어버리면 장부(WAL) 꼬이니까, "여기부턴 순서 지켜!" 하고 멱살 잡고 캐시를 비우게 만드는 동기화 채찍이다.

</details>

| 문제 | 대책 | 효과 |
|:---|:---|:---|
| SSD가 지 맘대로 순서 바꿔치기해서 저널 장부 쓰기도 전에 디스크에 엎어쳐서 꼬임 | **쓰기 장벽(Write Barrier)** 쳐서 하드웨어 캐시 강제 비움 | 커밋(Commit)이 무조건 디스크보다 먼저 써지도록 WAL 원칙 철통 사수 |
| 저널링 켰더니 SSD 쓰기 증폭(WAF) 터져서 수명 반토막 나고 I/O 성능 개박살남 | 풀 저널(Journal) 버리고 데이터는 걍 쓰는 **Ordered Mode** 튜닝 | 쓸데없는 장부질 줄여서 내구성과 성능의 가성비 타협점 도출 |
| 리눅스에서 읽기만 해도 접근 시간(atime) 갱신하느라 저널을 계속 써서 디스크 혹사시킴 | 마운트 옵션에 **`noatime / nodiratime`** 박아서 읽기 로깅 꺼버림 | 무의미한 메타데이터 저널링을 원천 차단해서 디스크 수명 떡상 |

#### 한줄 요약

- 하드웨어 통수는 Write Barrier로 막고, 수명 단축은 Ordered 모드와 noatime으로 틀어막아라.

## Ⅶ. 결론

<details><summary>용어 설명</summary>

- **저널링 모드 선택 기준(Journaling Mode Selection Criteria)**: 하드디스크 수명 챙길 거냐, 깡성능 챙길 거냐, 무결성이 목숨이냐에 따라 Writeback/Ordered/Journal을 고르는 잣대이다.

</details>

- **저널링 모드 선택 기준** 원칙에 따라, 웬만한 리눅스 서버 국룰은 **Ordered Mode**, 금융권 빡센 무결성은 **Full Journal**, 막 굴리는 캐시는 **Writeback** 채택 기조 확립함

#### 한줄 요약

- 데이터의 목숨값과 디스크의 수명을 저울질해서 알맞은 저널링 모드를 꽂아 넣어라.
