## Ⅰ. 개요

<details><summary>용어 설명</summary>

- **스트랭글러 패턴(Strangler Fig Pattern)**: 거대한 모놀리식 레거시 시스템을 빅뱅(Big-Bang) 방식으로 한 번에 교체하지 않고, API 게이트웨이 파사드(Facade)를 통해 특정 도메인 단위로 트래픽을 신규 마이크로서비스로 점진적으로 우회시켜 레거시를 서서히 도태시키는 차세대 현대화 아키텍처 패턴.
- **빅뱅 재구축 실패 및 비즈니스 중단 위험(Big-Bang Rewrite Failure Risk)**: 수년간 수백억을 들여 전체 시스템을 일시에 오픈하려다 숨겨진 비즈니스 규칙 누락, 데이터 정합성 파괴, 대규모 셧다운 장애로 프로젝트가 좌초되는 위험.

</details>

- 정의/개념: 모놀리식 레거시 시스템을 중단 없이 현대화하기 위해 **API 게이트웨이 파사드를 통해 트래픽을 신규 서비스로 점진 전환**하는 마이그레이션 패턴
- 배경/필요성: 전면 재구축(Big-Bang) 방식의 높은 실패율과 **장기간의 신규 기능 동결, 숨겨진 비즈니스 로직 유실 및 전사 장애 위험** 직면

#### 한줄 요약

- 파사드(Facade) 라우팅, 부패 방지 계층(ACL), 섀도우 트래픽 미러링, CDC 데이터 동기화를 통해 무중단으로 모놀리스를 마이크로서비스로 전환

## Ⅱ. 특징

<details><summary>용어 설명</summary>

- **부패 방지 계층(ACL: Anti-Corruption Layer)**: 레거시의 낙후된 데이터 모델과 모놀리식 스키마가 신규 마이크로서비스의 깨끗한 도메인 주도 설계(DDD)를 오염시키지 않도록 중간에서 변환해 주는 어댑터 계층.
- **섀도우 트래픽 미러링(Shadow Traffic Mirroring)**: 실제 프로덕션 트래픽을 복제하여 신규 마이크로서비스에 무응답(Read-only)으로 흘려보내 응답 정합성과 부하 성능을 실전 검증하는 기법.

</details>

- 클라이언트 변경 없이 신·구 시스템의 물리적 분리를 은닉하는 **파사드(API Gateway) 기반 라우팅**
- 도메인 단위로 데이터 정본(System of Record) 권한을 단계적으로 이양하는 **소유권 점진 이관(Ownership Transfer)**
- 이상 발생 시 라우팅 가중치만 0%로 바꾸어 즉각 롤백할 수 있는 **초저위험 복원력(Instant Rollback)**

#### 한줄 요약

- 파사드 라우팅, ACL 격리, 섀도우 검증, CDC 데이터 동기화를 결합하여 레거시를 안전하게 해체

## Ⅲ. 구조 및 구성요소

<details><summary>용어 설명</summary>

- **스트랭글러 패턴 4대 아키텍처 구성요소**: Routing Facade(API 게이트웨이), Legacy System(모놀리스/구형 DB), New Microservice(신규 도메인 서비스), Anti-Corruption Layer(부패 방지 어댑터).

</details>

```text
[ 스트랭글러 피그 패턴(Strangler Fig Pattern) 점진 전환 아키텍처 ]

 1. [ 단일 진입점 파사드 (Routing Facade: API Gateway) ]
    ┌─────────────────────────────────────────────────────────────┐
    │  • URL / 헤더 기반 트래픽 가중치 분기 (Canary 10% ➔ 100%) │
    └──────────────┬──────────────────────────────┬───────────────┘
                   │ (미전환 도메인: 90%)         │ (전환 완료 도메인: 10%)
                   ▼                              ▼
 2. [ 레거시 모놀리스 시스템 ]      3. [ 신규 마이크로서비스 (MSA) ]
    • 거대 모놀리스 WAS + 단일 DB      • 독립 K8s 파드 + 독립 PostgreSQL
    └──────────────┬──────────────────────────────▲───────────────┘
                   │ (레거시 데이터 참조 필요 시) │
                   ▼                              │
 4. [ 부패 방지 계층 (Anti-Corruption Layer: ACL) ] ──────────────┘
    • 구형 EBCDIC / 비표준 전문 ➔ 표준 JSON 도메인 객체 변환 격리
```

선의 의미: API Gateway가 트래픽을 신·구 시스템으로 분기하고, 신규 서비스가 레거시 데이터를 필요로 할 때 ACL을 거쳐 통신하는 구조.

| 구성요소 | 책임 |
|:---|:---|
| 라우팅 파사드 (Facade) | 클라이언트 진입점에서 **URL 경로 및 트래픽 비율에 따라 신·구 시스템으로 지연 없이 분기** |
| 레거시 시스템 (Legacy) | 아직 전환되지 않은 **잔여 비즈니스 도메인 로직과 구형 데이터베이스 정본(SoR) 유지** |
| 신규 마이크로서비스 (MSA) | 분리 완료된 도메인의 **비즈니스 로직 처리 및 전용 데이터베이스의 완전한 CUD 소유권 확보** |
| 부패 방지 계층 (ACL) | 신규 서비스와 레거시 간 통신 시 **데이터 모델 변환을 전담하여 신규 도메인의 오염 원천 방지** |

#### 한줄 요약

- 라우팅 파사드, 레거시 모놀리스, 신규 마이크로서비스, 부패 방지 계층이 결합하여 스트랭글러를 구현

## Ⅳ. 흐름도

<details><summary>용어 설명</summary>

- **스트랭글러 마이그레이션 5단계 수명주기**: 신규 도메인 서비스 구축 $\to$ 섀도우 트래픽 미러링 $\to$ 응답 정합성 검증 $\to$ 카나리 정식 전환(Cutover) $\to$ 레거시 데드코드 폐기.

</details>

```text
[ 스트랭글러 피그 점진적 도메인 전환 파이프라인 ]

 ┌────────────────────────────────────────┐
 │ 1. 결제 도메인 신규 MSA 및 ACL 구축   │
 └───────────────────┬────────────────────┘
                     │
                     ▼
 ┌────────────────────────────────────────┐
 │ 2. Gateway에서 섀도우 트래픽 복제 미러링
 └───────────────────┬────────────────────┘
                     │
                     ▼
 ┌────────────────────────────────────────┐
 │ 3. 신·구 시스템 응답값 및 성능 정합성 검증
 ├───────────────────┬────────────────────┤
 │ 불일치 (버그 발견)│ 완벽 일치 (합격)   │
 │ • 신규 코드 수정  │ • Cutover 준비     │
 └───────────────────┴────────────────────┘
                     │
                     ▼
 ┌────────────────────────────────────────┐
 │ 4. Canary 10% ➔ 100% 실 트래픽 정식 전환│
 └───────────────────┬────────────────────┘
                     │
                     ▼
 ┌────────────────────────────────────────┐
 │ 5. 모놀리스 내 결제 코드 및 테이블 영구 폐기
 └────────────────────────────────────────┘
```

### 동작 원리

1. 신규 구축: 모놀리스에서 '주문 결제' 도메인을 떼어내어 Spring Boot 기반 신규 마이크로서비스와 ACL을 구축.
2. 섀도우 미러링: API 게이트웨이가 실 결제 요청을 레거시(실제 승인)로 보내는 동시에 신규 서비스로 복제 전송.
3. 정합성 검증: 모니터링 도구로 양쪽의 결제 금액, 세금 계산, 응답 형식이 100% 일치함을 2주간 실증 검증.
4. 카나리 전환: 게이트웨이 라우팅을 10%에서 100%로 점진 전환하고 결제 DB의 쓰기 권한(Mastership)을 신규 서비스로 이양.
5. 레거시 폐기: 모놀리스 내에 방치된 결제 관련 소스코드 10만 라인과 구형 테이블을 안전하게 삭제(Decommission).

#### 한줄 요약

- 신규 구축 $\to$ 섀도우 미러링 $\to$ 정합성 검증 $\to$ 카나리 전환 $\to$ 레거시 폐기의 5단계

## Ⅴ. 종류 및 비교

<details><summary>용어 설명</summary>

- **점진 전환(Strangler) vs 빅뱅 전면 재작성(Big-Bang) vs 내부 리팩터링(In-Place)**: 무중단 점진 전환(Strangler), D-Day 일괄 교체(Big-Bang), 배포 구조 유지 내부 개선(In-Place).

</details>

| 구분 | 점진 전환 (Strangler Fig Pattern) | 전면 재작성 (Big-Bang Rewrite) | 내부 리팩터링 (In-Place Refactoring) |
|:---|:---|:---|:---|
| **적용 기준** | 24x7 무중단 운영 필수, 대규모 복합 엔터프라이즈 시스템 | 시스템 규모가 작거나 기존 비즈니스 로직을 완전히 폐기할 때 | MSA 전환 없이 모놀리스 내부 코드의 가독성과 품질만 개선할 때 |
| **핵심 특징** | **도메인 단위로 트래픽을 점진 분기, 실패 시 즉각 롤백 가능** | **수년간 병렬 개발 후 특정 D-Day에 구 시스템을 일시에 중단 교체** | **배포 단위와 API 명세는 유지한 채 내부 스파게티 코드만 정화** |
| **한계** | 과도기 동안 신·구 시스템 병행 운영 비용 및 CDC 데이터 동기화 복잡성 | 장기간 피드백 부재 및 오픈 당일 대규모 장애 폭발(리스크 집중) | 근본적인 모놀리스 DB 병목 및 프레임워크 노후화 한계 잔존 |

#### 한줄 요약

- 무중단 고가용성 전환은 스트랭글러, 소규모 전면 개편은 빅뱅, 단순 코드 정리는 내부 리팩터링을 채택

## Ⅵ. 실무 고려사항 및 대책

<details><summary>용어 설명</summary>

- **이중 쓰기(Dual Write) 방지와 CDC**: 과도기 동안 양쪽 DB에 동시에 쓸 때 발생하는 정합성 깨짐을 막기 위해 Debezium 기반 CDC(Change Data Capture)로 단방향 비동기 동기화를 구축하는 통제.

</details>

| 문제 | 대책 | 효과 |
|:---|:---|:---|
| 신·구 시스템 간 이중 쓰기(Dual Write) 시 분산 트랜잭션 실패로 데이터 불일치 | **단일 데이터 정본(SoR) 지정 및 `Debezium CDC 기반 비동기 스트리밍` 구축** | 최종 일관성(Eventual Consistency) 100% 보장 |
| 모놀리스 내부의 끈끈한 스파게티 순환 의존성으로 도메인 분리 불가 | **의존성이 가장 적은 `외곽 엣지 도메인(알림/로그인)`부터 점진 분리** | 전환 실패 위험 최소화 및 성공 경험 축적 |
| 병행 운영 기간이 수년간 장기화되어 클라우드 중복 인프라 비용 폭증 | **도메인별 명확한 `일몰(Sunset) 기한` 및 레거시 코드 폐기 기준 강제** | 인프라 비용 누수 및 기술 부채 조기 청산 |

#### 한줄 요약

- CDC 비동기 동기화, 엣지 도메인 우선 분리, 엄격한 일몰 기준 적용을 통해 스트랭글러 전환을 성공

## Ⅶ. 결론

<details><summary>용어 설명</summary>

- **이벤트 기반 스트랭글러 아키텍처(Event-Driven Strangler)**: 카프카(Kafka) 이벤트 스트림을 중심으로 레거시의 모든 변경 사항을 발행하여 신규 서비스들이 비동기로 자립하게 만드는 발전된 전환 기법.

</details>

- **스트랭글러 패턴** 복잡하고 거대한 레거시 시스템을 비즈니스 중단 없이 안전하게 클라우드 네이티브 MSA로 진화시키는 가장 검증된 마이그레이션 전략이며, 파사드 라우팅과 ACL 격리 및 CDC 동기화를 통해 완벽한 무중단 현대화를 완성해야 함

#### 한줄 요약

- 파사드 라우팅과 ACL 및 섀도우 검증을 통해 모놀리스를 안전하게 해체하고 MSA를 완성
