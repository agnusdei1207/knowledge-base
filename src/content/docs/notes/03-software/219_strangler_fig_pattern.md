## Ⅰ. 개요

<details><summary>용어 설명</summary>

- **레거시 시스템의 점진 대체(Incremental Legacy Replacement)**: 빅뱅 방식의 교체 위험을 피하기 위해, 독립적인 업무 경계별로 신규 마이크로서비스를 배치하고 검증된 범위부터 기존 모놀리식 기능을 서서히 제거하는 현대화(Modernization) 원칙.
- **스트랭글러 피그 패턴(Strangler Fig Pattern)**: 나무를 감싸며 자라다가 결국 숙주 나무를 대체하는 교살무화과(Strangler Fig) 나무처럼, 사용자의 트래픽 라우팅을 점진적으로 신규 서비스로 전환하여 레거시를 자연스럽게 도태시키는 아키텍처 패턴.

</details>

- 정의/개념: Domain별 Traffic•소유권을 점진 이전하는 **Strangler Pattern**
- 배경/필요성: Big-Bang 재작성은 **Logic 유실•장애 집중•기능 동결** 유발

#### 한줄 요약

- 낡은 건물을 한 번에 부수지 않고 새로운 건물을 주변에 지으면서 부서별로 조금씩 이사하듯, 트래픽을 신규 시스템으로 점진 우회시켜 시스템 중단 위험을 최소화하는 레거시 마이그레이션 기법.

## Ⅱ. 특징

<details><summary>용어 설명</summary>

- **기능·데이터 소유권 이관(Ownership Transfer)**: 트래픽 분기 및 섀도우 테스트(병행 검증)를 거친 후, 특정 비즈니스 로직 처리와 해당 데이터 테이블의 CUD(생성·수정·삭제) 권한(정본)을 완전히 신규 시스템으로 넘기는 전환 원칙.
- **파사드(Facade, API Gateway)**: 클라이언트 앱(호출자) 앞단에 위치하여 신·구 시스템의 물리적 분리를 추상화하고, 요청 URL이나 헤더에 따라 트래픽을 레거시 또는 신규 서비스로 적절히 라우팅하는 단일 진입점.
- **부패 방지 계층(Anti-Corruption Layer, ACL)**: 레거시의 낡은 데이터 구조와 기술 부채가 신규 마이크로서비스의 깨끗한 도메인 모델(DDD)로 오염되어 전파되는 것을 막기 위해 중간에서 모델을 변환하고 격리하는 어댑터 계층.
- **병행 검증(Parallel Validation/Shadowing)**: 실제 프로덕션 트래픽을 신·구 시스템 양쪽에 동시에 흘려보내(Read-only), 반환되는 응답 값과 처리 결과의 정합성을 비교·검증하여 전환의 신뢰성을 확보하는 기법.

</details>

- 단일 진입점을 통한 투명성 보장: 클라이언트는 내부가 레거시인지 신규 시스템인지 알 필요 없이 **파사드**를 통해서만 통신.
- 도메인 주도 설계(DDD) 기반의 **기능·데이터 소유권 이관**: 트랜잭션 경계를 분리하여, 마이그레이션이 끝난 도메인의 DB 테이블은 신규 서비스만 단독 소유하도록 강제.
- 리스크 통제 및 롤백 용이성: **병행 검증**으로 오류를 사전 탐지하고, 문제 발생 시 파사드의 라우팅 룰만 수정하여 즉시 레거시로 복귀(Rollback) 가능.
- **부패 방지 계층**을 통한 모델 순수성 유지: 신규 서비스가 구형 DB나 API 규격에 종속되지 않도록 인터페이스를 분리.

#### 한줄 요약

- 클라이언트 앞단의 파사드가 트래픽을 나누어 분산하므로 신규 시스템에 장애가 발생해도 라우팅 룰만 변경하면 즉각 레거시로 되돌려 비즈니스 연속성을 방어할 수 있음.

## Ⅲ. 구조 및 구성요소

<details><summary>용어 설명</summary>

- **데이터 정본(System of Record, SoR)**: 특정 도메인 데이터(예: 고객 정보)에 대해 마스터 권한(Mastership)을 가지며, 생성·수정 권한과 최종적인 데이터의 진실(Single Source of Truth)을 소유하는 시스템.
- **신규 서비스(New Service)**: 스트랭글러 패턴을 통해 새롭게 분리 구축되어 클라우드 네이티브 아키텍처(MSA)를 따르고 특정 도메인의 데이터 소유권을 확보한 독립 배포 단위.
- **레거시 시스템(Legacy System)**: 아직 마이그레이션되지 않아 기존의 모놀리식 구조와 거대 DB를 유지하며, 잔여 업무 기능과 해당 데이터 정본을 처리하는 기존 시스템.

</details>

```text
[Strangler Architecture]
 ├── [Facade]
 ├── [Legacy System]
 ├── [New Service]
 └── [Anti-Corruption Layer]
```

| 구성요소 | 책임 |
|:---|:---|
| Facade | URL•Header•Weight로 **신•구 Routing** 수행 |
| Legacy System | 미전환 업무와 잔여 Domain **SoR** 소유 |
| New Service | 전환 Domain Logic•Data **소유권** 확보 |
| Anti-Corruption Layer | Model•Format 변환과 **Legacy 격리** 수행 |

#### 한줄 요약

- 사용자 요청을 파사드가 분석해 전환된 기능은 새 시스템으로, 미전환 기능은 레거시로 보내며, 시스템 간 통신은 ACL이 중재하여 새 시스템이 구형 구조에 오염되지 않게 함.

## Ⅳ. 흐름도

<details><summary>용어 설명</summary>

- **2. 병행 라우팅 설정(Shadowing/Mirroring)**: 파사드(Gateway) 또는 서비스 메시(Istio 등)를 통해 실 트래픽을 신규 시스템으로 복제(미러링)하여, 사용자에게 영향을 주지 않고 내부적으로 결과를 비교하는 단계.
- **3. 결과 정합성 판정(Validation & Verification)**: 섀도우 트래픽으로 발생한 신·구 시스템의 응답 데이터(Payload), 레이턴시, 오류율 차이를 모니터링 툴로 대조하여 전환 허용 기준(Threshold)을 충족하는지 평가하는 단계.
- **4. 신규 소유권 전환(Cutover)**: 정합성이 확보된 기능에 한해 파사드의 실 트래픽 라우팅을 100% 신규 시스템으로 변경하고(Write 권한 포함), 해당 데이터 테이블의 오너십을 분리하는 단계.
- **5. 레거시 기능 폐기(Legacy Decommissioning)**: 완전히 이관되어 더 이상 파사드를 통해 호출되지 않는 레거시 코드 블록과 테이블을 식별(Dead code)하고 안전하게 삭제하여 기술 부채를 청산하는 단계.

</details>

```text
1. 신규 기능 배치 (독립 서비스 및 ACL 구축)
        |
        v
2. 병행 라우팅 설정 (트래픽 미러링 / 섀도우 테스트)
        |
        +-- 레거시 실행 (실제 응답 반환)
        |
        `-- 신규 실행 (응답 폐기, 로그만 기록)
                  |
                  v
         3. 결과 정합성 판정 (응답값 비교)
                  |
                  +-- 불일치 ---- 코드 버그 수정 및 레거시 로직 보완
                  |                    |
                  |                    `-- 병행 검증 반복
                  |
                  `-- 일치 (신뢰성 확보)
                       |
                       v
              4. 신규 소유권 전환 (라우팅 변경 및 Cutover)
                       |
                       +-- 타 기능 의존성 존재 ---- ACL 통한 병행 운영
                       |
                       `-- 잔여 의존성 완전 분리
                                  |
                                  v
                         5. 레거시 기능 폐기 (코드 삭제 및 DB 분리)
```

### 동작 원리

1. 신규 기능 배치: 신규 도메인 모델에 맞춰 서비스를 개발하고, 레거시 통신을 위한 ACL을 구성.
2. 병행 라우팅 설정: 파사드를 통해 실 트래픽의 복제본(Shadow)을 신규 서비스로 전달.
3. 결과 정합성 판정: 양쪽의 비즈니스 처리 결과(응답값, 처리 시간 등)가 일치하는지 모니터링 시스템을 통해 비교.
4. 신규 소유권 전환: 검증 완료 시 파사드의 라우팅을 신규 서비스로 공식 전환(Cutover)하고, DB 쓰기 권한 이관.
5. 레거시 기능 폐기: 전환이 완료되어 사용되지 않는 레거시 코드(Dead code)를 완전히 제거하여 시스템 경량화.

#### 한줄 요약

- 기존 시스템과 똑같이 동작하는지 복제된 트래픽(섀도우)으로 은밀히 테스트한 후, 완벽히 일치할 때 트래픽과 데이터 권한을 공식적으로 넘기고 낡은 코드를 버림.

## Ⅴ. 종류 및 비교

<details><summary>용어 설명</summary>

- **점진 전환(Incremental Migration / Strangler Fig)**: 서비스를 중단하지 않고 비즈니스 도메인 단위로 쪼개어 단계적으로 신·구 시스템을 교체하며, 문제 발생 시 파사드 라우팅으로 즉각 복귀(Rollback)가 가능한 안정적 방식.
- **일괄 재작성(Big-Bang Rewrite)**: 수년 간 새로운 아키텍처로 전체 시스템을 병렬 개발한 뒤, 특정 D-Day(명절 연휴 등)에 구 시스템을 완전히 내리고 신규 시스템으로 일거에 대체하는 고위험 방식.
- **내부 개선(Internal Refactoring)**: 클라이언트가 바라보는 API 계약(Contract)이나 외부 배포 아키텍처는 그대로 둔 채, 레거시 시스템 내부의 스파게티 코드만 디자인 패턴을 적용해 구조적으로 정화하는 방식.

</details>

| 레거시 개선 방식 | **점진 전환** | **일괄 재작성** | **내부 개선** |
|:---|:---|:---|:---|
| 적용 기준 | 24x7 연속 운영 필수, 리스크 최소화 및 부분적 가치 창출이 우선일 때 | 시스템 규모가 작거나 기존 비즈니스 로직을 100% 버리고 재창조할 때 | 외부 의존성을 깨지 않고 유지보수성(가독성)과 테스트 용이성만 개선할 때 |
| 핵심 특징 | 도메인 단위로 하나씩(Strangler) 시스템을 교체하고 트래픽 분기 | D-Day를 정해 기존 시스템을 일시에 중단하고 신규 시스템으로 오픈 | 외부로 드러나는 동작(행위)은 변경하지 않고 내부 코드 아키텍처만 개선 |
| 한계 | 과도기 동안 신·구 시스템 병행 운영 비용 및 데이터 동기화(CDC 등) 복잡성 증가 | 장기간 피드백 부재, 오픈 시 예기치 못한 대규모 장애 발생 위험(리스크 집중) | 근본적인 모놀리식 DB 결합이나 플랫폼(프레임워크) 노후화 제약은 잔존함 |

> 요약: 무중단과 안정성이 최우선이면 **점진 전환**, 전환 범위가 작고 도메인이 완전히 바뀌면 **일괄 재작성**, 내부 코드 품질 향상이 목적이면 **내부 개선**을 선택함.

#### 한줄 요약

- 서비스 중단을 피하면서 안전하게 MSA로 전환하려면 점진 전환(스트랭글러)을, 기능 추가 없이 코드 가독성만 높이려면 내부 개선을, 아예 백지에서 다시 만들려면 빅뱅 재작성을 적용함.

## Ⅵ. 실무 고려사항 및 대책

<details><summary>용어 설명</summary>

- **이중 쓰기(Dual Write) 문제**: 과도기 동안 신·구 시스템이 동일한 개념의 데이터를 각자의 DB에 기록할 경우, 분산 트랜잭션 실패 시 어느 쪽이 진실(SoR)인지 어긋나게 되는 데이터 정합성 파괴 현상.
- **변경 데이터 캡처(Change Data Capture, CDC)**: 레거시 DB의 트랜잭션 로그(Binlog, Redo Log 등)를 비동기로 읽어내어 신규 서비스 DB(또는 카프카)로 스트리밍함으로써 시스템 간 실시간 동기화를 맞추는 데이터 파이프라인 기술.
- **카나리 전환(Canary Cutover)**: 전체 트래픽을 한 번에 신규 시스템으로 넘기지 않고, 특정 지역이나 1~5%의 소수 트래픽만 우선 라우팅하여 시스템 부하와 예외를 모니터링한 뒤 점진적으로 비율을 높이는 배포 전략.
- **완료 기준(Exit Criteria)**: 특정 도메인의 스트랭글러 전환을 최종 완료로 판정하기 위해 필요한 정량적 조건(예: 신규 라우팅 100% 도달, 레거시 DB 의존성 0%, 2주간 크리티컬 장애 없음 등).

</details>

| 실무 문제점 | 해결 대책 | 기대 효과 |
|:---|:---|:---|
| 신·구 시스템의 과도기적 **이중 쓰기** 및 데이터 불일치 | 데이터 정본(SoR) 단일화 지정 및 Kafka/Debezium 기반의 **변경 데이터 캡처** 구축 | 분산 트랜잭션 없이도 최종 일관성(Eventual Consistency) 및 정합성 보장 |
| 파악되지 않은 깊은 레거시 의존성(스파게티 얽힘) 문제 | 서비스 메시(Service Mesh) 기반 호출 추적(Tracing) 및 APM 데이터 흐름 사전 관측 | 의존성이 적은 엣지(Edge) 도메인부터 전환하여 실패 리스크 및 마찰 축소 |
| 병행 운영 기간 장기화에 따른 조직 피로도 및 운영비 상승 | 명확한 도메인별 일몰(Sunset) 계획 수립 및 엄격한 **완료 기준** 강제 | 레거시 폐기 지연 억제 및 클라우드 인프라 중복 비용 조기 회수 |
| 라우팅 일괄 변경(Cutover) 시 트래픽 폭증으로 인한 신규 시스템 장애 | 파사드(API Gateway)를 활용한 가중치 기반 **카나리 전환** 및 롤백 훈련 | 대규모 사용자 영향 차단 및 즉각적인(수 분 내) 레거시 복원력 확보 |

#### 한줄 요약

- 트래픽 전환 시에는 카나리 배포로 안전망을 치고, 데이터 분리 시에는 CDC를 활용하여 양쪽 DB의 동기화를 맞추되, 전환이 끝난 레거시는 과감히 삭제(일몰)하여 복잡성을 줄여야 함.

## Ⅶ. 결론

<details><summary>용어 설명</summary>

- **소유권 이관 기준(Ownership Transition Criteria)**: 독립된 도메인 경계 내에서 섀도우 트래픽 검증을 완벽히 통과한 후, API 호출 진입점과 마스터 데이터(DB)의 제어권을 최종적으로 신규 시스템으로 이양하는 의사결정 기준.

</details>

- 독립 Domain은 **Shadow 검증•Canary Cutover**, Exit 충족 후 Legacy 폐기

#### 한줄 요약

- 함께 변경되지 않는 외곽 비즈니스(Edge Domain)부터 점진적으로 트래픽과 데이터 소유권을 이관하여 마이크로서비스 전환 리스크를 효과적으로 통제하는 스트랭글러 체계 적용 필수.
