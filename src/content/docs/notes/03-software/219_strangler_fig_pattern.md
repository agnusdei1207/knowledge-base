## Ⅰ. 개요

<details><summary>용어 설명</summary>

- **Strangler Fig Pattern (스트랭글러 패턴)**: 거대 모놀리스를 빅뱅으로 한 번에 교체하지 않고, API Gateway 파사드를 통해 특정 도메인부터 신규 MSA로 점진 전환하는 마이그레이션 패턴.
- **Anti-Corruption Layer (ACL, 부패 방지 계층)**: 레거시의 낡은 데이터 모델이 신규 마이크로서비스의 도메인 설계를 오염시키지 않도록 중간에서 변환하는 완충 계층.

</details>

- 정의/개념: 모놀리식 레거시 시스템을 중단 없이 현대화하기 위해 **API 게이트웨이 파사드를 통해 트래픽을 신규 서비스로 점진 전환하는 마이그레이션 패턴**
- 배경/필요성: 전면 재구축(Big-Bang) 시 발생하는 **장기간의 비즈니스 기능 개발 동결, 숨은 규칙 유실 및 오픈 당일 전사 장애 폭발 해결 불가**

#### 한줄 요약
- 파사드 라우팅, 부패 방지 계층(ACL), 섀도우 미러링, CDC 동기화를 통해 무중단 MSA 전환을 달성한다.

## Ⅱ. 특징

<details><summary>용어 설명</summary>

- **Shadow Traffic Mirroring**: 실제 운영 트래픽을 복제하여 신규 마이크로서비스에 무응답(Read-only)으로 흘려보내 정합성과 성능을 검증하는 기법.
- **System of Record (SoR, 데이터 정본)**: 특정 비즈니스 데이터의 유일한 쓰기 권한(Mastership)을 소유한 신뢰할 수 있는 원천 저장소.

</details>

- 클라이언트 변경 없이 신·구 시스템의 분리를 은닉하는 **파사드(API Gateway) 기반 라우팅**
- 도메인 단위로 데이터 정본(SoR) 권한을 단계적으로 이양하는 **소유권 점진 이관(Ownership Transfer)**
- 레거시 데이터 모델의 오염을 차단하는 **부패 방지 계층(ACL) 완충 격리**

#### 한줄 요약
- 파사드 라우팅, 소유권 점진 이관, ACL 완충 격리를 통해 전환 리스크를 최소화한다.

## Ⅲ. 구조 및 구성요소

<details><summary>용어 설명</summary>

- **스트랭글러 4대 아키텍처**: Routing Facade(트래픽 분기), Legacy Monolith(잔여 도메인), New Microservice(신규 도메인), Anti-Corruption Layer(모델 변환 완충).

</details>

```text
[스트랭글러 패턴(Strangler Fig) 점진적 마이그레이션 아키텍처]
|-- 1. Routing Facade Layer (API Gateway / Envoy: URL 경로 및 가중치 기반 트래픽 라우팅)
|   |-- (전환 완료 도메인: `/api/v2/payments`) -> 2. New Payment MSA (신규 마이크로서비스 & 전용 DB)
|   `-- (미전환 도메인: `/api/v1/orders`) -> 3. Legacy Monolith (구형 모놀리스 & 통합 DB)
`-- 4. Anti-Corruption Layer (ACL: 구형 전문/스키마 <-> 표준 JSON 도메인 객체 변환 완충)
`-- 5. Data Synchronization Layer (Debezium CDC + Kafka: 신·구 데이터베이스 비동기 최종 일관성)
```

선의 의미: 계층 및 API Gateway가 트래픽을 신·구 시스템으로 분기하고 신규 서비스가 레거시 데이터를 필요로 할 때 ACL을 거쳐 통신하는 구조

| 구성요소 | 핵심 엔지니어링 책임 | 주요 특징 |
|:---|:---|:---|
| **라우팅 파사드 (Facade)** | 클라이언트 진입점에서 **URL 경로 및 트래픽 비율에 따라 신·구 시스템으로 지연 없이 분기** | API Gateway |
| **레거시 모놀리스 (Legacy)** | 아직 전환되지 않은 **잔여 비즈니스 도메인 로직과 구형 데이터베이스 정본(SoR) 유지** | 기존 시스템 |
| **신규 마이크로서비스 (MSA)**| 분리 완료된 도메인의 **비즈니스 로직 처리 및 전용 데이터베이스의 완전한 CUD 소유권 확보** | 신규 클라우드 앱 |
| **부패 방지 계층 (ACL)** | 신규 서비스와 레거시 간 통신 시 **데이터 모델 변환을 전담하여 신규 도메인의 오염 방지** | 도메인 변환 완충 |
| **데이터 동기화 (CDC)** | 과도기 동안 신·구 DB 간의 **데이터 변경분을 실시간 스트리밍하여 최종 일관성 보장** | Debezium, Kafka |

#### 한줄 요약
- 라우팅 파사드, 레거시 모놀리스, 신규 MSA, 부패 방지 계층, CDC 동기화가 결합된다.

## Ⅳ. 흐름도

<details><summary>용어 설명</summary>

- **스트랭글러 전환 5단계**: 신규 도메인 MSA 구축 $\to$ 섀도우 트래픽 미러링 $\to$ 응답/성능 정합성 검증 $\to$ 카나리 정식 전환 $\to$ 레거시 코드 폐기.

</details>

```text
모놀리스 레거시 시스템 점진적 현대화 가동
        │
   1. [신규 구축] 모놀리스에서 '결제 도메인'을 분리하여 Spring Boot 기반 신규 MSA 및 ACL 구축
        │
   2. [섀도우 미러링] API 게이트웨이가 실제 결제 요청을 레거시와 신규 MSA로 동시 복제 전송
        │
   3. [정합성 검증] 양쪽 시스템의 결제 금액, 세금 계산, 응답 형식이 100% 일치함을 2주간 검증
   ┌────┴───────────────────────────┐
  일치 (검증 통과)                 불일치 (결함 발견)
   │                                 │
4A. [카나리 정식 Cutover]           4B. [신규 로직 디버깅]
   Gateway 라우팅 10% -> 100% 전환      불일치 케이스 수정 후 재검증
   │                                 │
   ▼                                 │
5. 레거시 내 결제 코드 10만 라인 폐기 │
   │                                 │
   └────┬────────────────────────────┘
        ▼
   모놀리스 무중단 해체 및 신규 MSA 자립 완료
```

#### 한줄 요약
- 신규 구축 → 섀도우 미러링 → 정합성 검증 → 카나리 전환 → 레거시 폐기 순으로 진행된다.

## Ⅴ. 종류 및 비교

<details><summary>용어 설명</summary>

- **Strangler Fig vs Big-Bang Rewrite vs In-Place Refactoring**: 점진 전환(Strangler), 일괄 교체(Big-Bang), 배포 단위 유지 내부 개선(In-Place).

</details>

| 비교 항목 | 점진 전환 (Strangler Fig) | 전면 재작성 (Big-Bang Rewrite) | 내부 리팩터링 (In-Place) |
|:---|:---|:---|:---|
| 핵심 전환 방식 | **도메인 단위 트래픽 점진 분기, 실패 시 롤백** | **특정 D-Day에 구 시스템 일시 중단 및 전면 교체**| **배포 단위와 API는 유지하고 내부 코드만 정화**|
| 비즈니스 다운타임 | **전무 (0초 무중단 전환)** | 수 시간 ~ 수일간 전면 다운타임 발생 | 전무 (기존 배포 프로세스 동일) |
| 프로젝트 리스크 | **최소 (도메인별 점진 검증 및 즉각 회귀)** | **최고 (오픈 당일 대규모 장애 폭발 위험)** | 낮음 (기존 아키텍처 한계는 잔존) |
| 주요 관리 난제 | 과도기 동안 신·구 시스템 병행 운영 및 CDC | 장기간 신규 비즈니스 기능 개발 동결 | 모놀리스 DB 병목 및 프레임워크 노후화 잔존 |

#### 한줄 요약
- 무중단 대규모 현대화는 Strangler Fig, 소규모 전면 개편은 Big-Bang, 단순 코드 정리는 In-Place를 선택한다.

## Ⅵ. 실무 고려사항 및 대책

<details><summary>용어 설명</summary>

- **Dual-Write Anti-Pattern (이중 쓰기 안티패턴)**: 애플리케이션 레벨에서 신·구 DB에 동시에 쓸 때 발생하는 네트워크 분할 및 트랜잭션 불일치 장애.

</details>

| 문제 | 대책 | 효과 |
|:---|:---|:---|
| 신·구 DB 간 이중 쓰기(Dual Write) 시 분산 트랜잭션 실패 | **단일 데이터 정본(SoR) 지정 및 `Debezium CDC 기반 비동기 스트리밍` 구축** | 최종 일관성(Eventual Consistency) 보장 |
| 모놀리스 내부의 스파게티 순환 의존성으로 도메인 분리 불가 | **의존성이 가장 적은 `외곽 엣지 도메인(알림/인증)`부터 점진 분리** | 전환 실패 위험 최소화 및 성공 경험 축적 |
| 병행 운영 기간이 장기화되어 클라우드 중복 인프라 비용 폭증 | **도메인별 명확한 `일몰(Sunset) 기한` 및 레거시 코드 폐기 기준 강제** | 인프라 비용 누수 및 기술 부채 조기 청산 |
| 신규 MSA 전환 후 레거시 데이터 조회 시 성능 병목 | **부패 방지 계층(ACL) 내 로컬 캐싱 및 비동기 이벤트 복제 적용** | 레거시 의존성 분리 및 응답 지연 해소 |

#### 한줄 요약
- CDC 비동기 동기화, 엣지 도메인 우선 분리, 엄격한 일몰 기준, ACL 로컬 캐싱으로 운영한다.

## Ⅶ. 결론

- 거대하고 복잡한 레거시 모놀리스를 비즈니스 중단 없이 안전하게 클라우드 네이티브 MSA로 전환하기 위해 **API 게이트웨이 파사드 라우팅과 부패 방지 계층(ACL)을 표준 아키텍처로 수립**하고, **섀도우 트래픽 미러링 검증과 Debezium CDC 기반의 데이터 동기화**를 결합하여 무결점 점진적 현대화 완성

#### 한줄 요약
- 스트랭글러 패턴은 파사드 라우팅과 ACL 및 섀도우 검증을 통해 레거시를 무중단으로 안전하게 해체하고 마이크로서비스로 전환하는 핵심 아키텍처 현대화 기술이다.
