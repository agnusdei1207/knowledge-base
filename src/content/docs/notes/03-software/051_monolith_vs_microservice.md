## Ⅰ. 개요

<details><summary>용어 설명</summary>

- **모놀리식(Monolithic)**: 모든 비즈니스 기능이 단일 배포 단위(jar/war)로 패키징되고 단일 공유 DB를 사용하는 전통적 아키텍처.
- **마이크로서비스(MSA)**: 비즈니스 도메인 단위로 서비스를 분리하여 각 서비스가 전용 DB와 독립 배포 파이프라인을 보유하는 분산 아키텍처.
- **모듈리스(Modulith)**: 단일 배포 단위를 유지하면서 코드 내부에 엄격한 모듈 경계를 적용하여 스파게티 코드를 방지하는 과도기 아키텍처.

</details>

- 정의/개념: 단일 배포 단위로 운영하는 **모놀리식**과 도메인별 독립 서비스로 분리하는 **MSA**의 트레이드오프 비교 및 선택 기준
- 배경/필요성: 도메인 복잡도·팀 규모·트래픽 요구 수준을 무시한 조기 MSA 전환은 분산 운영 복잡도로 인한 프로젝트 실패를 유발하므로, **시스템 성숙도 기반 단계적 아키텍처 선택 필수**

#### 한줄 요약

- 도메인 복잡도·팀 규모·DevOps 역량에 따라 Monolith→Modulith→MSA의 단계적 아키텍처 진화를 결정

## Ⅱ. 특징

<details><summary>용어 설명</summary>

- **결합도와 응집도(Coupling & Cohesion)**: 컴포넌트 간 의존은 낮게(Low Coupling), 내부 요소 간 관련성은 높게(High Cohesion) 유지하는 설계 원칙으로 모놀리식·MSA 공통 적용.
- **분산 오버헤드(Distributed Overhead)**: MSA에서 서비스 간 네트워크 호출·분산 트랜잭션·서비스 디스커버리 등으로 발생하는 추가 복잡도와 지연.

</details>

- **모놀리식**: 단일 프로세스 내 함수 호출로 높은 성능, RDBMS의 ACID 트랜잭션 직접 활용 가능
- **MSA**: Database-per-Service로 서비스 독립 확장, 특정 서비스만 선택적 스케일아웃 가능
- 트랜잭션 단순성·성능(Monolith) vs 독립 확장·장애 격리·배포 자유도(MSA)의 **트레이드오프**

#### 한줄 요약

- 강한 ACID 트랜잭션·고성능 함수 호출은 모놀리식, 독립 확장·장애 격리는 MSA의 장점

## Ⅲ. 구조 및 구성요소

<details><summary>용어 설명</summary>

- **스트랭글러 피그 패턴(Strangler Fig Pattern)**: 레거시 모놀리식을 즉시 전면 교체하지 않고 기능 단위로 점진적으로 마이크로서비스로 분리하여 전환 위험을 최소화하는 마이그레이션 전략.

</details>

```text
[ Monolith vs MSA 구조 비교 ]
모놀리식 (Monolithic)                MSA (Microservice)
┌──────────────────────┐             API Gateway
│ 통합 애플리케이션     │              │
│ (주문+결제+배송 통합) │         ┌───┴───────┐
│           │           │         │           │
│ 단일 공유 DB          │     주문 서버    결제 서버
└──────────────────────┘      주문 DB     결제 DB
```

선의 의미: 모놀리식은 단일 배포 단위 내 직접 호출 관계, MSA의 API Gateway는 라우팅 진입점, 서비스별 전용 DB는 데이터 격리 관계

| 구성요소 | 책임 |
|:---|:---|
| **통합 애플리케이션 (Monolith)** | 단일 배포 단위·공유 DB·인메모리 함수 호출 |
| **API Gateway (MSA)** | 외부 요청 단일 진입점·라우팅·인증 |
| **독립 서비스 (MSA)** | 도메인별 독립 배포·전용 DB 보유·독립 확장 |

#### 한줄 요약

- 모놀리식은 단일 배포·공유 DB, MSA는 API Gateway와 서비스별 독립 배포·전용 DB로 구성

## Ⅳ. 흐름도

<details><summary>용어 설명</summary>

- **아키텍처 전환 임계점(Architecture Migration Threshold)**: 팀 규모·배포 빈도·서비스 독립 확장 필요 등의 지표가 모놀리식의 한계를 초과하여 MSA 전환이 불가피해지는 시점.

</details>

```text
1. 초기 스타트업: 빠른 시장 검증 목적
   └─ 모놀리식으로 신속 구축·배포
   │
   ▼
2. 서비스 성장: 코드베이스·팀 규모 증가
   └─ 모듈리스(Modulith)로 내부 모듈 경계 강화
   │
   ▼
3. 임계점 초과: 특정 서비스 독립 확장·팀 병렬 배포 요구
   │
   ▼
4. MSA 점진 전환: 스트랭글러 피그 패턴으로 기능 단위 분리
   └─ 레거시 모놀리식과 신규 MSA 병행 운영
   │
   ▼
5. MSA 완전 전환: 서비스별 독립 배포·확장 체계 확립
```

**동작 원리**

1. **초기**: 단순 요구사항 및 소규모 팀에서 모놀리식으로 빠른 초기 출시
2. **성장기**: 코드베이스 증가에 따라 Modulith로 내부 모듈 경계를 강화하여 복잡도 관리
3. **임계점**: 특정 도메인 트래픽 급증·팀 규모 확대로 독립 배포·확장 필요 발생
4. **점진 전환**: Strangler Fig 패턴으로 레거시와 병행하며 기능 단위 MSA 전환

#### 한줄 요약

- Monolith→Modulith→MSA의 단계적 진화로 각 성장 단계에 적합한 복잡도 수준을 유지

## Ⅴ. 종류 및 비교

<details><summary>용어 설명</summary>

- **분산 시스템 원칙(First Rule of Distributed Systems)**: 분산 시스템은 단순 시스템 대비 필연적으로 복잡도가 증가하므로 독립 확장의 이득이 분산 비용을 상회할 때만 MSA를 선택해야 한다는 원칙.

</details>

| 아키텍처 | 구현 복잡도 | 운영 오버헤드 | 적합 환경 |
|:---|:---|:---|:---|
| **Monolithic** | 낮음 | 단일 배포 단위로 낮음 | 초기 스타트업·소규모 팀 |
| **Modulith** | 중간 (모듈 경계 설계) | 단일 배포 유지로 낮음 | MSA 전환 전 단계·중규모 |
| **Microservice** | 높음 (분산 제어) | 복수 서비스 모니터링·운영 | 대규모 트래픽·독립 배포 필요 |

#### 한줄 요약

- 조직 규모·트래픽·DevOps 역량에 따라 운영 복잡도와 확장 이득의 균형점에서 아키텍처를 결정

## Ⅵ. 실무 고려사항 및 대책

<details><summary>용어 설명</summary>

- **조기 최적화(Premature Optimization)**: 실제 확장 요구가 발생하기 이전에 MSA를 도입하여 불필요한 분산 복잡도를 증가시키는 과잉 설계.

</details>

| 문제 | 대책 | 효과 |
|:---|:---|:---|
| 불충분한 서비스 규모에서 조기 MSA 도입 (**조기 최적화**) | **모듈리스(Modulith)** 로 시작하여 경계를 선 설계 후 필요 시 분리 | 분산 오버헤드 없이 미래 MSA 분리 준비 |
| 레거시 모놀리식의 빅뱅 방식 전면 재작성으로 리스크 집중 | **Strangler Fig Pattern**으로 기능 단위 점진 마이그레이션 | 전환 실패 리스크 분산 및 단계적 검증 |
| MSA 서비스 간 동기 API 호출 체인으로 장애 전파 | **비동기 이벤트(Kafka) + Circuit Breaker** 적용 | 장애 격리 및 서비스 생존성 확보 |

#### 한줄 요약

- 조기 MSA는 Modulith로 대체하고, 레거시 전환은 Strangler Fig로 점진화하며, API 장애 전파는 비동기 이벤트로 차단

## Ⅶ. 결론

<details><summary>용어 설명</summary>

- **아키텍처 패러다임 선택 기준**: 조직의 DevOps 자동화 역량·도메인 복잡도·팀 규모·독립 확장 필요 수준을 종합하여 Monolith·Modulith·MSA를 결정하는 판단 기준.

</details>

- 초기는 **모놀리식**, 성장기는 **모듈리스**, 대규모 독립 확장 필요 시 **MSA**로 점진 전환

#### 한줄 요약

- MSA는 목적이 아닌 수단으로, 독립 확장의 이득이 분산 복잡도 비용을 상회할 때만 선택
