## Ⅰ. 개요

<details><summary>용어 설명</summary>

- **모놀리식(Monolithic)**: 결제, 주문, 배송 등 모든 기능이 1개의 프로젝트(war/jar)로 묶여서 통짜로 배포되고, 1개의 DB를 쪼개 쓰는 전통적인 뚝배기 아키텍처이다.
- **마이크로서비스(Microservice, MSA)**: 결제 서버, 주문 서버 등 비즈니스 단위로 완전히 찢어져서 각자 자기만의 DB를 갖고 독고다이로 배포/확장되는 쿨한 분산 아키텍처이다.
- **모듈리스(Modulith)**: 모놀리식처럼 통짜로 배포하되, 코드 내부에선 MSA처럼 패키지(모듈) 경계를 엄격하게 쳐놔서 스파게티를 방어하는 쌉가성비 타협안이다.

</details>

- 정의: 통째로 배포해서 개발/운영이 심플한 **Monolithic**과, 잘게 찢어서 독립적으로 서버를 늘리고 배포하는 **MSA(Microservice Architecture)**의 세기의 대결 분석인 **Monolith vs Microservice**
- 배경: 넷플릭스 겉멋 들어서 무지성으로 MSA 도입했다가 **API 호출 지연(Latency)과 분산 트랜잭션 지옥**에 빠져 프로젝트가 터지는 꼴을 막기 위함

#### 한줄 요약

- 통짜로 뭉쳐서 편하게 살 거냐(모놀리식), 잘게 찢어서 독립적으로 빠르게 움직일 거냐(MSA)의 선택이다.

## Ⅱ. 특징

<details><summary>용어 설명</summary>

- **결합도와 응집도(Coupling & Cohesion)**: MSA로 찢든 모놀리식으로 짜든 무조건 지켜야 하는 '남남끼리 느슨하게, 끼리끼리 똘똘 뭉치게' 묶는 아키텍처 절대 진리이다.
- **분산 오버헤드(Distributed Overhead)**: 통짜일 땐 0.1밀리초면 끝나던 함수 호출이, 서버를 찢었더니 네트워크 타고 API 쏘고 장애 나면 롤백(Saga)하느라 피똥 싸는 MSA의 끔찍한 청구서이다.

</details>

- **Monolithic**: DB 1개라서 트랜잭션(`@Transactional`) 묶기 개꿀이고 메모리 함수 호출이라 빛의 속도임.
- **MSA**: 서비스마다 DB 따로 가져감(Database-per-Service). 결제 이벤트 터지면 결제 서버만 무한 스케일아웃 쌉가능.
- 결국 **네트워크 지연/분산 트랜잭션의 헬난이도(MSA)** vs **스파게티 코드와 배포 병목(Monolithic)**의 숨 막히는 트레이드오프임.

#### 한줄 요약

- 뭉치면 트랜잭션이 쉽고 배포가 꼬이며, 찢으면 배포는 자유롭지만 네트워크와 분산 지옥이 열린다.

## Ⅲ. 구조 및 구성요소

<details><summary>용어 설명</summary>

- **스트랭글러 피그 패턴(Strangler Fig Pattern)**: 레거시 통짜 서버를 한 방에 엎는 게 아니라, 덩굴식물(Strangler)이 나무를 덮어 죽이듯 기능 하나씩 MSA로 야금야금 빼내는 안전빵 전환 전략이다.

</details>

```text
[ 통짜(Monolith) vs 찢기(MSA) 십자포화 비교 구조 ]

+-- [ 뚝배기 (Monolith) ] -----------+
│ [ 통짜 애플리케이션 (주문+결제) ]  │
│                │                   │
│ [ 1개의 거대한 공용 DB ]           │
+------------------------------------+

+-- [ 레고 블록 (Microservice) ] ---------------+
│ [ API Gateway (라우터/문지기) ]               │
│        │                       │              │
│ [ 주문 서버 (독립 배포) ]  [ 결제 서버 ]      │
│        │                       │              │
│ [ 주문 전용 DB ]           [ 결제 전용 DB ]   │
+-----------------------------------------------+
```

| 구성요소 | 팩트 폭행 책임 |
|:---|:---|
| **통짜 애플리케이션** | 한 번 배포할 때 결제, 주문 다 같이 죽었다 살아나는 샴쌍둥이 구조 |
| **공용 DB** | 쿼리 조인(JOIN) 한 방이면 데이터 다 뽑아올 수 있는 꿀통이자 병목의 원흉 |
| **API Gateway (MSA)** | 유저 요청 받아서 "주문은 쟤한테, 결제는 얘한테" 토스해 주는 트래픽 경찰 |
| **독립 서비스군 (MSA)** | 남 눈치 안 보고 하루에 100번 배포하고 각자 스케일아웃 하는 독고다이 서버들 |
| **전용 DB (MSA)** | 남의 DB 건들면 철컹철컹. "내 데이터 내놔" 하면 무조건 API나 이벤트로 통신함 |

#### 한줄 요약

- 모놀리식은 통짜 앱과 공용 DB를, MSA는 라우터(Gateway)와 독립 앱/전용 DB를 갖는다.

## Ⅳ. 흐름도

<details><summary>용어 설명</summary>

- **아키텍처 전환 임계점(Architecture Migration Threshold)**: 통짜 서버가 너무 비대해져서, 개발자가 코드 한 줄 고치는 시간보다 깃허브 충돌(Conflict) 해결하고 빌드하는 데 시간이 더 걸려 "아 찢어야겠다"고 빡치는 마지노선이다.

</details>

```text
[ 아키텍처 진화 십자포화 흐름 ]
┌──────────────────────────────┐
│ 1. 스타트업 초기 (단순 기획) │
└──────────────┬───────────────┘
               ▼
┌──────────────────────────────┐
│ 2. Monolithic 구축 (일단 통짜)
│ (빠르게 배포해서 시장 검증)  │
└──────────────┬───────────────┘
               ▼
┌──────────────────────────────┐
│ 3. 덩치가 커짐 (Modulith 전환)
│ (내부 패키지만 빡세게 나눔)  │
└──────────────┬───────────────┘
               ▼
┌──────────────────────────────┐
│ 4. 임계점 돌파 (서버 터짐)   │
│ (결제 트래픽 떡상, 팀 50명)  │
└──────────────┬───────────────┘
               ▼
┌──────────────────────────────┐
│ 5. MSA로 점진적 분리         │
│ (Strangler 패턴으로 야금야금)│
└──────────────────────────────┘
```

### 동작 원리

1. 도입 평가: 이 서비스가 얼마나 크고 팀원이 몇 명인지 사이즈를 잼.
2. 초기 선택(Monolith): 닥치고 모놀리식. 스타트업 초반에 MSA 하면 서버 띄우다 망함.
3. 모듈화 진화(Modulith): 덩치가 커지면 모놀리식 안에서 패키지(모듈) 경계만 빡세게 나눔.
4. 임계점 돌파: 팀원이 수십 명 넘어가고 매일 배포해야 되면 통짜 서버 한계가 옴.
5. 점진적 이행(MSA): 스트랭글러(Strangler) 패턴으로 하나씩 MSA로 찢어내며 진화함.

#### 한줄 요약

- 통짜로 시작해서 $\to$ 모듈 쪼개고 $\to$ 임계점 터지면 $\to$ 하나씩 서버를 찢어내는 테크트리다.

## Ⅴ. 종류 및 비교

<details><summary>용어 설명</summary>

- **분산 시스템 제1원칙(First Rule of Distributed Systems)**: 마틴 파울러 왈, "제발 분산 시스템(MSA) 하지 마라. 진짜 어쩔 수 없이 서버 찢어야만 살 수 있을 때까지 버텨라"라는 뼈 때리는 명언이다.

</details>

| 아키텍처 | 구현 난이도 | 운영 오버헤드 | 팩트 폭행 추천 환경 |
|:---|:---|:---|:---|
| **Monolithic** | 눈 감고도 짬 (최하) | `war` 파일 하나 떨구면 끝 (최하)| 돈 없고 시간 없는 **극초기 스타트업** |
| **Modulith** | 패키지 분리 머리 아픔 | 여전히 1개로 배포함 (하) | MSA 갈 돈은 없는데 스파게티는 피하고 싶을 때 |
| **Microservice**| **헬파티** (분산 제어) | 수십 개 서버 모니터링 (**지옥**)| 쿠팡, 배민처럼 **돈 많고 트래픽 터지는 대기업** |

#### 한줄 요약

- 돈과 사람이 없으면 모놀리식, 넘쳐흐르면 마이크로서비스를 하면 된다.

## Ⅵ. 실무 고려사항 및 대책

<details><summary>용어 설명</summary>

- **조기 최적화(Premature Optimization)**: 장사도 안 되는데 손님 몰릴 거 대비한다고 빚내서 가게 10개 짓는 것처럼, 초반에 유행 따라 무작정 MSA 찢었다가 인프라 비용과 버그에 깔려 죽는 헛짓거리이다.

</details>

| 문제 | 대책 | 효과 |
|:---|:---|:---|
| 유행 따라 오픈 전부터 무지성 MSA 찢었다가 폭망함 (**조기 최적화**) | 일단 **Modulith(모듈화된 통짜)**로 뭉쳐서 경계부터 깎음 | 분산 지옥을 피하면서 미래 MSA 분리 준비 완료 |
| 통짜(레거시) 서버 빅뱅 방식으로 한 방에 엎다가 망함 | **Strangler Fig Pattern**으로 티 안 나게 야금야금 찢어냄 | 빅뱅 방식의 실패 리스크를 제로로 수렴시킴 |
| 서버끼리 API 부르다가 통신 꼬여서 속도 박살 남 | **비동기 이벤트(Kafka)**로 쏘고 회로 차단기(Circuit Breaker) 박음 | 앞서 서버가 죽어도 내 서버는 살아남는 생존성 |

#### 한줄 요약

- MSA 겉멋 들지 말고, 스트랭글러로 천천히 찢으며, API 대신 카프카(비동기)로 대화해라.

## Ⅶ. 결론

<details><summary>용어 설명</summary>

- **아키텍처 패러다임 선택 기준(Architecture Paradigm Selection Criteria)**: 조직이 DevOps 자동화가 되는지, 서버를 안 찢으면 팀원끼리 주먹다짐이 일어날 상황인지 각을 재는 잣대이다.

</details>

- **아키텍처 선택 기준** 원칙에 따라, 유행 쫓는 무지성 MSA를 극혐하고, **스타트업 통짜(Monolith) $\to$ 중견(Modulith) $\to$ 대기업(MSA)** 진화 테크트리 기조 확립함

#### 한줄 요약

- MSA는 목표가 아니라, 통짜 서버가 터지기 직전일 때 어쩔 수 없이 선택하는 '생존 수단'이다.
