## Ⅰ. 개요

<details><summary>용어 설명</summary>

- **모놀리식(Monolithic)**: 모든 비즈니스 로직과 데이터 액세스 계층이 단일 바이너리/프로세스 내에 통합되어 배포되는 아키텍처.
- **마이크로서비스(Microservices)**: 비즈니스 도메인 단위로 독립 배포 가능한 작은 서비스들이 네트워크(REST/gRPC/Kafka)를 통해 협업하는 분산 아키텍처.

</details>

- 정의/개념: 단일 프로세스/공유 DB 기반 통합 배포(Monolith)와 도메인 경계 기반 **독립 배포 및 DB 격리(MSA)** 간의 설계 비교 체계
- 배경/필요성: 무분별한 조기 MSA 전환 시 발생하는 **네트워크 분산 트랜잭션 복잡도 및 인프라 운영비용 폭증 해결 불가**

#### 한줄 요약
- 도메인 복잡도, 팀 규모, DevOps 역량에 따라 Monolith $\to$ Modulith $\to$ MSA의 단계적 진화를 결정한다.

## Ⅱ. 특징

<details><summary>용어 설명</summary>

- **분산 시스템의 제1원칙(First Rule of Distributed Systems)**: "가능하면 분산 시스템을 만들지 마라(Don't distribute)" - 분산 비용이 독립 배포의 이득보다 크면 모놀리스 유지가 유리함.
- **모듈러 모놀리스(Modular Monolith)**: 단일 배포 아티팩트를 유지하되 코드베이스 내부 패키지/모듈 간 캡슐화 경계를 엄격히 통제하는 절충형 모델.

</details>

- **모놀리식**: 인메모리 함수 호출 기반의 **초고성능 및 강력한 단일 RDBMS ACID 트랜잭션** 보장
- **마이크로서비스**: Database-per-Service 기반 **서비스별 독립 배포, 장애 격리 및 선별적 Scale-out**
- 개발 단순성(Monolith)과 독립 확장성/민첩성(MSA) 간의 명확한 **트레이드오프(Trade-off)**

#### 한줄 요약
- 단순성과 ACID 트랜잭션은 모놀리식, 독립 배포와 탄력적 확장은 MSA가 우수하다.

## Ⅲ. 구조 및 구성요소

<details><summary>용어 설명</summary>

- **Strangler Fig 패턴**: 레거시 모놀리스를 한 번에 교체하지 않고 특정 도메인 기능을 하나씩 MSA로 분리하여 점진적으로 교체하는 전략.

</details>

```text
[Monolith vs Modular Monolith vs Microservices 구조]
|-- 모놀리식 (Monolith: 단일 프로세스 & 단일 공유 DB)
|   `-- [UI -> Controller -> Service -> DAO] -> [단일 통합 RDBMS]
|-- 모듈러 모놀리스 (Modular Monolith: 단일 배포 & 내부 모듈 격리)
|   |-- [주문 모듈 (내부 격리)] <--- [내부 이벤트/인터페이스] ---> [결제 모듈]
|   `-- [단일 DB 내 도메인별 스키마 분리]
`-- 마이크로서비스 (MSA: 네트워크 분산 & Database-per-Service)
    |-- API Gateway -> [주문 서비스: 주문 DB] (독립 배포)
    `-- Kafka Event -> [결제 서비스: 결제 DB] (독립 배포)
```

선의 의미: 아키텍처 모델별 프로세스 및 데이터베이스 경계

| 비교 항목 | 모놀리식 (Monolithic) | 모듈러 모놀리스 (Modular Monolith) | 마이크로서비스 (MSA) |
|:---|:---|:---|:---|
| **배포 단위** | **단일 실행 바이너리** | **단일 실행 바이너리** | 서비스별 수십 개 컨테이너 |
| **서비스 간 통신** | 인메모리 메서드 호출 | 인메모리 인터페이스/이벤트 | **네트워크 HTTP, gRPC, Kafka** |
| **데이터베이스** | 단일 통합 DB (공유) | 단일 DB (스키마 논리 분리) | **Database-per-Service (물리 분리)** |
| **트랜잭션** | **ACID (단일 트랜잭션)** | ACID (단일 트랜잭션) | **BASE (Saga 최종 일관성)** |

#### 한줄 요약
- Monolith(단일 통합), Modulith(단일 배포/모듈 격리), MSA(완전 네트워크 분산)로 대비된다.

## Ⅳ. 흐름도

<details><summary>용어 설명</summary>

- **아키텍처 진화 임계점**: 팀 규모가 수십 명으로 늘고 일일 배포 빈도가 수십 회로 증가하여 모놀리스의 빌드/배포 병목이 사업 성장을 가로막는 시점.

</details>

```text
1. 초기 스타트업 단계: 빠른 비즈니스 검증 목표
   └─ 모놀리식(Monolith)으로 신속한 단일 배포 및 시장 출시
        │
   2. 성장기: 개발자 및 코드베이스 증가
   └─ 모듈러 모놀리스(Modular Monolith)로 패키지 간 경계 캡슐화 (ArchUnit 검증)
        │
   3. 분기점: 특정 도메인 트래픽 폭증 및 팀 간 배포 락 발생 (임계점 도달)
   └─ 스트랭글러 피그 패턴(Strangler Fig) 기반 기능 단위 점진 분리
        │
   4. 대규모 성숙기: 서비스별 독립 무중단 CI/CD 및 K8s 오토스케일링 확립 (MSA 완성)
```

#### 한줄 요약
- 초기 모놀리스 → 성장기 모듈리스 → 임계점 도달 시 점진 분리 → MSA 완성 순으로 진화한다.

## Ⅴ. 종류 및 비교

<details><summary>용어 설명</summary>

- **Conway's Law(콘웨이의 법칙)**: 50명 이하의 단일 팀은 모놀리스가 적합하고, 수백 명의 다중 팀은 MSA 구조가 자연스럽게 일치한다는 조직 법칙.

</details>

| 결정 판단 축 | 모놀리식 선택 기준 | 마이크로서비스 선택 기준 |
|:---|:---|:---|
| **팀 규모 및 조직** | 단일 팀, 10~20명 이하 개발 조직 | **수십 개 분산 팀, 50명 이상 대규모 조직** |
| **도메인 복잡도** | 도메인 경계가 모호하고 자주 변경됨 | **도메인 경계(Bounded Context)가 매우 명확함** |
| **DevOps 인프라** | K8s, 분산 추적, 메시 인프라 미보유 | **완전 자동화된 CI/CD 및 관측성 플랫폼 보유** |
| **트래픽 패턴** | 전체 시스템 트래픽이 균일함 | **특정 기능(결제, 검색)만 트래픽 극단적 집중** |

#### 한줄 요약
- 팀 규모가 작고 빠른 검증이 필요하면 모놀리스, 팀 규모가 크고 독립 배포가 필수면 MSA를 선택한다.

## Ⅵ. 실무 고려사항 및 대책

<details><summary>용어 설명</summary>

- **Premature Optimization(조기 최적화)**: 서비스 트래픽도 검증되지 않은 초기에 MSA를 무리하게 도입하여 인프라 비용과 분산 디버깅 지옥을 겪는 안티패턴.

</details>

| 문제 | 대책 | 효과 |
|:---|:---|:---|
| 초기 스타트업에서 무리한 MSA 도입으로 인한 개발 지연 | **모듈러 모놀리스(Modular Monolith)** 로 시작 후 점진 분리 | 분산 복잡도 제거 및 초기 Time-to-Market 단축 |
| 레거시 모놀리스의 위험천만한 빅뱅식 전면 재구축 | **Strangler Fig Pattern** 기반 API 게이트웨이 점진 트래픽 우회 | 서비스 중단 위험 0화 및 단계적 안전 전환 |
| MSA 서비스 간 동기 REST 체인으로 인한 연쇄 장애 | **Kafka 비동기 이벤트 주도 + Resilience4j 서킷 브레이커** | 서비스 간 결합도 제거 및 장애 격리 |
| 분산 환경에서 데이터 추적 및 로깅 곤란 | **OpenTelemetry 기반 분산 추적(Distributed Tracing)** | 전역 요청 흐름 가시성 확보 |

#### 한줄 요약
- 모듈러 모놀리스 시작, Strangler Fig 점진 전환, 비동기 이벤트 격리, OpenTelemetry 추적으로 위험을 통제한다.

## Ⅶ. 결론

- 아키텍처는 기술적 유행이 아닌 비즈니스 성장 단계의 도구이며, **초기 모듈러 모놀리스에서 시작하여 임계점 도달 시 Strangler Fig 패턴을 통해 MSA로 점진 진화**하는 전략이 엔지니어링 최적 표준

#### 한줄 요약
- 모놀리식과 마이크로서비스는 상호 배타적이지 않으며, 시스템의 성장 주기와 조직 규모에 맞춘 점진적 진화가 핵심이다.
