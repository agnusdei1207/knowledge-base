## Ⅰ. 개요

<details><summary>용어 설명</summary>

- **피처 토글(Feature Toggle / Feature Flag)**: 소스코드 배포(Deployment)와 비즈니스 기능의 활성화(Release) 시점을 완전히 분리하여, 런타임에 소스코드 재빌드나 재배포 없이 특정 사용자, 환경, 비율에 따라 기능 실행 경로를 동적으로 켜고 끄는 릴리스 제어 기법.
- **배포-출시 결합 및 롤백 지연 위험(Deployment Coupling & Rollback Lag Risk)**: 코드 배포와 기능 출시가 결합되어 있어 신기능 장애 발생 시 전체 애플리케이션을 롤백 재배포해야 하고, 사용자 세그먼트별 실전 A/B 테스트가 불가능한 위험.

</details>

- 정의/개념: 소스코드 배포와 기능 활성화 시점을 분리하여 **사용자별·비율별로 동적 기능 분기 및 롤백을 제어하는 릴리스 엔지니어링** 기법
- 배경/필요성: 배포와 기능 노출의 강결합으로 인한 **대규모 롤백 부담, 실전 A/B 테스트 불가 및 릴리스 병목 위험** 직면

#### 한줄 요약

- 소스코드 재배포 없이 플래그 제어부(Flag Control Plane)와 결정적 해시(Deterministic Hashing)를 통해 안전한 카나리 출시와 실전 A/B 테스트를 구현

## Ⅱ. 특징

<details><summary>용어 설명</summary>

- **결정적 해시(Deterministic Hashing)**: 사용자 ID와 플래그 키를 결합하여 해시(MD5/MurmurHash)를 계산함으로써 동일 사용자가 세션을 변경해도 항상 동일한 실험군(A/B)에 배정되도록 보장하는 알고리즘.
- **킬 스위치(Kill Switch)**: 신기능 배포 후 서버 CPU 폭증이나 결제 오류 감지 시 0.1초 만에 플래그를 OFF로 전환하여 장애를 즉각 완화하는 긴급 차단 기능.

</details>

- 코드 배포(Deploy)와 기능 개방(Release)을 시공간적으로 분리하는 **배포와 출시의 디커플링**
- 사용자 속성(지역, 버전) 및 비율(Canary 10%)에 따라 동적으로 분기하는 **정밀 타깃팅 제어**
- 프로덕션 장애 발생 시 재배포 없이 즉각 기능을 끄는 **실시간 킬 스위치(Kill Switch)**

#### 한줄 요약

- 배포 분리, 결정적 해시 배정, 실시간 킬 스위치, 노출 로그 추적을 결합하여 릴리스 위험을 최소화

## Ⅲ. 구조 및 구성요소

<details><summary>용어 설명</summary>

- **피처 토글 5대 핵심 아키텍처 계층**: Flag Control Plane(관리 포털), Policy Engine(타깃팅 룰), Evaluation SDK(로컬 평가기), Application Logic(분기 코드), Experiment Analytics(효과 분석기).

</details>

```text
[ 피처 토글 및 실험 플랫폼(LaunchDarkly / Unleash) 구조도 ]

 1. [ 플래그 제어 평면 (Flag Control Plane) ]
    ┌─────────────────────────────────────────────────────────────┐
    │  • 플래그 생성/만료일 설정, 타깃팅 규칙(Rule) 및 킬 스위치  │
    └────────────────────────────┬────────────────────────────────┘
                                 │ (실시간 스트리밍 동기화: SSE / WebSocket)
                                 ▼
 2. [ 로컬 평가 런타임 및 SDK (In-Memory Evaluation SDK) ] ──────┐
    • `if (flagClient.evaluate("new-checkout", userContext))`     │
    • 네트워크 홉(Hop) 없이 1ms 미만 인메모리 결정적 해시 계산  │
    └────────────────────────────┬────────────────────────────────┘
                                 │
                                 ▼
 3. [ 애플리케이션 분기 실행 (Application Execution) ] ──────────┐
    • Control(기존 결제) vs Treatment(신규 간편결제) 분기 실행    │
    └────────────────────────────┬────────────────────────────────┘
                                 │ (노출 이벤트 비동기 스트리밍)
                                 ▼
 4. [ 실험 분석 및 가드레일 (Experiment Analytics & Alert) ] ────┐
    • 노출 로그 + 전환율(CVR) + 오류율 ➔ A/B 테스트 통계적 유의성 판정│
    └─────────────────────────────────────────────────────────────┘
```

선의 의미: 제어 평면의 플래그 룰이 SDK에 실시간 캐시되어 앱이 로컬에서 분기 실행하고 노출 로그를 분석 플랫폼으로 전송하는 구조.

| 구성요소 | 책임 |
|:---|:---|
| 플래그 제어 평면 (Control Plane) | 토글 소유자, **규칙 버전, 노출 비율, 만료일(TTL)을 중앙 관리하고 실시간 전파** |
| 로컬 평가 SDK (Evaluation Engine)| 원격 호출 없이 **인메모리에서 결정적 해시를 계산하여 1ms 이내에 분기 결과 반환** |
| 애플리케이션 (Application) | SDK의 평가 결과에 따라 **기존 로직과 신규 후보 로직을 조건부 실행 및 노출 기록** |
| 실험 분석기 (Analytics) | 노출 로그와 비즈니스 전환 지표를 결합하여 **A/B 테스트 통계적 유의성($p < 0.05$) 검증** |
| 가드레일 모니터 (Guardrail) | 신기능 오류율이 임계치 초과 시 **자동으로 킬 스위치를 작동시켜 플래그 OFF 전환** |

#### 한줄 요약

- 제어 평면, 평가 SDK, 애플리케이션, 실험 분석기, 가드레일 모니터가 결합하여 피처 토글을 완성

## Ⅳ. 흐름도

<details><summary>용어 설명</summary>

- **피처 플래그 수명주기 5단계**: 가설 및 지표 수립 $\to$ 플래그 룰 등록 $\to$ SDK 로컬 평가 및 노출 $\to$ A/B 테스트 통계 검증 $\to$ 100% 출시 및 토글 코드 정리.

</details>

```text
[ 피처 토글 카나리 릴리스 및 실험 라이프사이클 파이프라인 ]

 ┌────────────────────────────────────────┐
 │ 1. 실험 가설 및 전환/가드레일 지표 정의│
 └───────────────────┬────────────────────┘
                     │
                     ▼
 ┌────────────────────────────────────────┐
 │ 2. Control Plane에 10% 카나리 룰 등록   │
 └───────────────────┬────────────────────┘
                     │
                     ▼
 ┌────────────────────────────────────────┐
 │ 3. 앱 SDK: User ID 기반 결정적 해시 평가│
 └───────────────────┬────────────────────┘
                     │
                     ▼
 ┌────────────────────────────────────────┐
 │ 4. 실시간 가드레일 감시 및 통계 분석   │
 ├───────────────────┬────────────────────┤
 │ 에러율 급증 (장애)│ 전환율 유의미 향상 │
 │ • Kill-Switch OFF │ • 100% 점진 확대   │
 └───────────────────┴────────────────────┘
                     │
                     ▼
 ┌────────────────────────────────────────┐
 │ 5. 영구 활성화 후 소스코드 내 토글 삭제│
 └────────────────────────────────────────┘
```

### 동작 원리

1. 가설 정의: "신규 원클릭 결제창을 도입하면 결제 전환율이 15% 상승하고 오류율은 0.1% 미만일 것이다."
2. 룰 등록: 플래그 `fast-checkout-v2`를 생성하고 내부 임직원 100% 및 일반 고객 10% 할당 룰을 등록.
3. SDK 평가: 앱 서버 내부 Unleash SDK가 사용자 UUID를 해싱하여 10% 대상자에게만 신규 결제 UI를 렌더링.
4. 통계 검증: 1주일간 10만 건 노출 결과 결제 완료율이 18% 증가하고 통계적 유의성($p = 0.01$)을 확보.
5. 토글 제거: 기능을 100% 전체 공개로 전환한 후 다음 스프린트에서 `if-else` 토글 분기 코드를 깔끔히 삭제.

#### 한줄 요약

- 가설 정의 $\to$ 룰 등록 $\to$ SDK 평가 $\to$ 통계 검증 $\to$ 코드 정리의 5단계

## Ⅴ. 종류 및 비교

<details><summary>용어 설명</summary>

- **Release vs Experiment vs Operational vs Permission Toggle**: 마틴 파울러의 피처 토글 4대 분류 체계.

</details>

| 구분 | 릴리스 토글 (Release Toggle) | 실험 토글 (Experiment Toggle) | 운영 토글 (Operational Toggle / Kill Switch) |
|:---|:---|:---|:---|
| **적용 기준** | 트렁크 기반 개발 시 미완성 기능을 숨기고 카나리 출시할 때 | A/B 테스트를 통해 어떤 변종이 비즈니스 성과를 내는지 검증할 때 | 트래픽 폭증 시 추천 알고리즘을 끄고 정적 캐시로 대체할 때 |
| **핵심 특징** | **수일~수주 동안 유지되는 단기 토글, 점진적 롤아웃** | **통계적 유의성이 확보될 때까지 유지되는 다중 변종 분기** | **시스템 과부하 시 비핵심 기능을 즉시 차단하는 영구 킬 스위치** |
| **한계** | 출시 완료 후 즉각 코드를 삭제하지 않으면 부채로 누적 | 사용자 편향 및 동시 실험 간의 간섭(Interference) 위험 | 평상시 자주 사용되지 않아 정작 비상시에 미작동 위험 |

#### 한줄 요약

- 점진 배포는 릴리스 토글, 가설 검증은 실험 토글, 비상 장애 차단은 운영 토글을 적용

## Ⅵ. 실무 고려사항 및 대책

<details><summary>용어 설명</summary>

- **토글 부채(Toggle Debt)**: 출시가 끝났음에도 `if-else` 토글 코드를 삭제하지 않고 방치하여 코드 복잡도가 $2^N$으로 증가하고 테스트 조합이 폭증하는 현상.

</details>

| 문제 | 대책 | 효과 |
|:---|:---|:---|
| 사용 완료된 플래그가 소스코드에 방치되어 유지보수성 파괴 (토글 부채) | **플래그 등록 시 `만료일(TTL: 최대 30일)` 지정 및 자동 정리 Jira 티켓 발행** | 죽은 분기 코드 100% 근절 |
| 토글 평가를 위해 매번 원격 API를 호출하여 애플리케이션 응답 지연 | **SDK 내 `인메모리 룰 캐싱 및 SSE 기반 실시간 동기화` 아키텍처 적용** | 토글 평가 오버헤드 1ms 미만 달성 |
| 여러 A/B 테스트가 동시에 진행되면서 실험군 간섭으로 데이터 오염 | **사용자 해시 공간을 분리하는 `직교 레이어(Orthogonal Layering)` 구성** | 실험 간 간섭 왜곡 0건 달성 |

#### 한줄 요약

- 만료일 기반 토글 제거, 인메모리 SDK 평가, 직교 레이어 실험 분리를 통해 피처 토글의 안정성을 보장

## Ⅶ. 결론

<details><summary>용어 설명</summary>

- **트렁크 기반 개발(Trunk-Based Development)의 필수 전제**: 장수 브랜치(Feature Branch)를 만들지 않고 모든 개발자가 메인 브랜치에 매일 커밋할 수 있도록 미완성 기능을 감추는 핵심 도구.

</details>

- **피처 토글 및 실험 플랫폼** 지속적 배포(CD)와 데이터 기반 의사결정을 실현하는 현대 소프트웨어 릴리스의 핵심 인프라 기술이며, 인메모리 평가 SDK와 엄격한 토글 수명주기(TTL) 관리를 통해 안전하고 민첩한 카나리 출시를 완성해야 함

#### 한줄 요약

- 배포와 출시의 분리 및 인메모리 평가와 킬 스위치를 통해 안전한 릴리스와 실전 A/B 테스트를 완성
