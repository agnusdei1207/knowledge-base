## Ⅰ. 개요

<details><summary>용어 설명</summary>

- **화이트박스 테스트(White-box Testing)**: 소스코드 상한선을 열어서 "If문 탔냐? For문 몇 번 돌았냐?" 하면서 돋보기로 내부 로직(제어 흐름)을 다 까보는 시스루(See-through) 테스트 기법이다.
- **블랙박스 테스트(Black-box Testing)**: 코드가 어떻게 생겼든 노관심이고, 자판기처럼 "동전 넣으면(Input) 콜라 잘 나오냐?(Output)"만 쿨하게 체크하는 명세 기반 테스트이다.
- **그레이박스 테스트(Gray-box Testing)**: 겉으론 블랙박스처럼 입출력만 보지만, 사실 내부 DB 구조나 API 작동 원리를 살짝 커닝해서 얍삽하게 엣지 케이스를 찔러보는 융합 기법이다.

</details>

- 정의: 소스코드 내부 제어 구조를 까보는 **White-box Testing** 및, 코드는 안 보고 명세서 기준으로 입출력만 찔러보는 **Black-box Testing** 비교 체계
- 배경: 블랙박스만 하면 **구석에 숨은 버그** 활용 못 잡고, 화이트박스만 하면 **기능 자체를 안 만든 것(기능 누락)** 을 못 찾기 때문

#### 한줄 요약

- 속을 다 까집어보고 검사할지(화이트박스), 겉에서 찔러만 볼지(블랙박스)의 차이다.

## Ⅱ. 특징

<details><summary>용어 설명</summary>

- **제어 흐름 그래프(CFG, Control Flow Graph)**: 복잡한 코드를 동그라미(노드)와 화살표(엣지)로 그려서, "아 여기서 분기가 갈라지는구나" 하고 화이트박스 경로를 찾는 지도이다.
- **명세 기반 기법(Specification-based Technique)**: "요구사항 문서(SRS)에 이렇게 적혀있잖아!"라며 문서를 무기로 삼아 블랙박스 테스트 케이스를 뽑아내는 기법이다.

</details>

- 소스 내부 구조를 들여다봄(**White-box**) 대 외부 요구사항 명세서만 봄(**Black-box**)
- 제어/데이터 흐름 커버리지 측정(**White-box**) 대 입력값 범위/상태 전이 확인(**Black-box**)
- 개발자가 짜는 **Unit Test(단위)** 수준 대 QA가 때려보는 **System/Acceptance(시스템/인수)** 수준 주력 적용.

#### 한줄 요약

- 코드 구조 중심(화이트)이냐, 기획서 명세 중심(블랙)이냐의 관점 차이다.

## Ⅲ. 구조 및 구성요소

<details><summary>용어 설명</summary>

- **커버리지(Coverage)**: 구문(모든 줄 밟았나?), 분기(If문 T/F 다 타봤나?) 등 화이트박스가 얼마나 코드를 들쑤셨는지 보여주는 성적표이다.
- **동등 분할 / 경계값 분석(EP / BVA)**: 귀찮게 1~100 다 안 해보고, 중간값 50(동등 분할)이랑 터지기 좋은 0, 1, 100, 101(경계값)만 얍삽하게 찔러보는 블랙박스 스킬이다.

</details>

```text
[ 테스트 기법 십자포화 아키텍처 ]

[ 블랙박스 (Black-box) ]          [ 화이트박스 (White-box) ]
│ (명세서 기반)                   │ (소스코드 기반)
├─ 동등 분할 (가운데 찌르기)      ├─ 구문 커버리지 (다 밟기)
├─ 경계값 분석 (모서리 찌르기)    ├─ 분기 커버리지 (T/F 다 타기)
└─ 상태 전이 (순서대로 찌르기)    └─ 조건 커버리지 (조건별 타기)
```

| 기법 분류 | 직관적 비교 예시 |
|:---|:---|
| **동등 분할 (블랙박스)** | 1~100점 입력 칸에 중간값인 50점 하나만 넣어보고 퉁침 |
| **경계값 분석 (블랙박스)** | 1~100점 칸에 터지기 딱 좋은 0, 1, 100, 101점만 악랄하게 찔러봄 |
| **구문 커버리지 (화이트박스)**| 작성된 소스코드 100줄을 최소 한 번씩은 다 밟고 지나갔는지 검사 |
| **분기 커버리지 (화이트박스)**| `if`문 만났을 때 `참(True)`으로도 가보고 `거짓(False)`으로도 가봤는지 검사 |

#### 한줄 요약

- 겉에서 경계값을 악랄하게 찌르거나(블랙), 안에서 코드를 구석구석 밟아본다(화이트).

## Ⅳ. 흐름도

<details><summary>용어 설명</summary>

- **기본 경로 테스트(Basis Path Testing)**: McCabe의 순환 복잡도 공식을 써서, 코드가 지저분하게 갈라지는 '독립 경로' 개수를 수학적으로 구하고 거길 다 지나가보는 화이트박스 기법이다.

</details>

```text
[ 양동 작전 테스트 십자포화 흐름 ]
┌──────────────────────────────┐
│ 테스트 대상 분석             │
└──────────────┬───────────────┘
               ▼
┌──────────────────────────────┐
│ 1. 블랙박스 (명세 찌르기)    │
│ (요구사항 문서 보고 테스트)  │
└──────────────┬───────────────┘
               ▼
┌──────────────────────────────┐
│ 2. 화이트박스 (코드 찌르기)  │
│ (커버리지 툴 켜서 빈틈 찾기) │
└──────────────┬───────────────┘
               ▼
┌──────────────────────────────┐
│ 3. 기반 교차 보완       │
│ (블랙박스가 놓친 구석 메우기)│
└──────────────┬───────────────┘
               ▼
┌──────────────────────────────┐
│ 4. 최종 결과 리포팅          │
│ (결함 탐지 완료 및 커버리지) │
└──────────────────────────────┘
```

### 동작 원리

1. 블랙박스 설계: 명세서 보고 동등 분할, 경계값 찔러넣을 케이스를 만듦.
2. 화이트박스 설계: 커버리지 도구 돌려서 안 탄 If문(미실행 경로)이 어딘지 찾음.
3. 교차 실행: 양쪽 관점에서 다 털어봄.
4. 보완: 블랙박스로 찾은 "기능 누락"과 화이트박스로 찾은 "쓸데없는 코드"를 상호 보완함.
5. 완료: 결함 싹 다 지라(Jira)에 올리고 커버리지 리포트 뽑음.

#### 한줄 요약

- 명세서로 기능 누락 잡고, 커버리지 툴로 미실행 코드 잡아서 쌍끌이하는 흐름이다.

## Ⅴ. 종류 및 비교

<details><summary>용어 설명</summary>

- **개발자(White-box) vs QA(Black-box)**: 지가 짠 코드를 지가 들여다보는 게 화이트박스(주로 단위 테스트)고, 코드 1도 모르는 QA나 고객이 겉에서 마우스 딸깍거려 보는 게 블랙박스(시스템 테스트)이다.

</details>

| 구분 | **White-box Testing (개발자 관점)** | **Black-box Testing (QA 관점)** |
|:---|:---|:---|
| 팩폭 무기 (Basis)| 소스코드 제어 구조, If문, Loop문 | 요구사항 명세서, 유스케이스, 매뉴얼 |
| 주력 공격수 | **주로 코딩한 개발자가 직접 털어봄** | **테스트 전문 QA나 최종 사용자 (User)** |
| 테스트 레벨 | **밑바닥 단위 테스트 (Unit Test)** | **시스템/인수 테스트 (System/Acceptance)** |
| 탐지하는 결함 | 절대 안 타는 죽은 코드(Dead Code), 메모리 릭 | 요구사항 쌩까고 미구현, 이상한 에러 팝업 |
| 지식 필요성 | **소스코드 내부 구조 모르면 못 함** | **코드 볼 줄 몰라도 입력값 넣을 줄 알면 됨** |

#### 한줄 요약

- 개발자가 코드 까보면서 하는 게 화이트박스, QA가 기능만 확인하는 게 블랙박스다.

## Ⅵ. 실무 고려사항 및 대책

<details><summary>용어 설명</summary>

- **커버리지의 함정(Coverage Fallacy)**: 개발자가 "제 코드 커버리지 100%인데요?"라며 뻗대지만, 애초에 요구사항 명세서를 빼먹고 안 짰으면 커버리지가 100%든 1000%든 블랙박스 테스트에서 박살 난다는 팩폭이다.

</details>

| 문제 | 대책 | 효과 |
|:---|:---|:---|
| 구문 커버리지 100% 달성 후에도 분기 결함 발생 | **분기(Branch) 및 MC/DC 커버리지** 상향 및 경계값 분석 결합 | 복합 조건 분기 결함 조기 차단 |
| 대규모 레거시 코드 전체 화이트박스 검증 비용 과다 | 핵심 도메인은 **화이트박스**, 외부 인터페이스는 **블랙박스** 차등 적용 | 테스트 투자 비용 대비 검증 효율 극대화 |
| 요구사항 명세 누락 결함을 코드 커버리지로 탐지 불가 | **명세 기반 블랙박스 인수 테스트(Acceptance Test)** 교차 검증 | 명세 일치도 검증 및 커버리지 착시 해소 |

#### 한줄 요약

- 커버리지 100%라고 깝치지 말고, 명세서 잘 읽고 블랙박스 테스트로 체크해라.

## Ⅶ. 결론

<details><summary>용어 설명</summary>

- **테스트 기법 선택 기준(Test Technique Selection Standards)**: 단위 테스트할 땐 화이트박스, 시스템 테스트할 땐 블랙박스라는 국룰에 기반한 잣대이다.

</details>

- **테스트 기법 선택 기준** 원칙에 따라, 내부 로직의 알고리즘 꼬임은 **White-box**, 기획서 빼먹고 안 만든 기능 누락은 **Black-box** 기반 상호 보완 기조 확립함

#### 한줄 요약

- 화이트박스가 '잘못 짠 코드'를 잡는다면, 블랙박스는 '안 짠 기능'을 잡는 완벽한 파트너다.
