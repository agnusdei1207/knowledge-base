## Ⅰ. 개요

<details><summary>용어 설명</summary>

- **화이트박스 테스트(White-box)**: 소스 코드의 내부 제어 흐름, 데이터 흐름, 분기 조건을 직접 보며 테스트 케이스를 도출하는 구조 기반 테스팅.
- **블랙박스 테스트(Black-box)**: 소스 코드를 보지 않고 요구사항 명세서(SRS)의 입력값과 기대 출력값을 기반으로 결함을 검증하는 명세 기반 테스팅.

</details>

- 정의/개념: 내부 로직의 실행 경로를 검증하는 **화이트박스**와 요구사항 명세 충족 여부를 검증하는 **블랙박스** 테스팅 기법의 상호보완 체계
- 배경/필요성: 코드 구조 의존 시의 요구 누락(Omission Fault) 및 **명세 의존 시의 미실행 경로(Dead Code)와 내부 분기 결함 미탐지 한계**

#### 한줄 요약
- 내부 코드 구조 검증(화이트박스)과 외부 명세 기반 검증(블랙박스)을 상호 보완하여 결함 누출을 방지한다.

## Ⅱ. 특징

<details><summary>용어 설명</summary>

- **커버리지(Coverage)**: 소스 코드의 구문(Statement), 분기(Branch), 조건(Condition), MC/DC가 테스트에 의해 실행된 비율.
- **경계값 분석(BVA)**: 입력 유효/무효 동등 클래스의 경계($\pm 1$) 부근에서 결함 발생률이 가장 높다는 원리를 이용한 블랙박스 기법.

</details>

- **화이트박스**: 소스 코드의 구문, 분기, 조건 커버리지 측정을 통한 **내부 논리 결함 식별**
- **블랙박스**: 동등 분할, 경계값 분석, 결정 테이블 기반의 **사용자 기능 및 인터페이스 결함 식별**
- 단위/통합 수준(화이트박스)과 시스템/인수 수준(블랙박스)의 **테스트 레벨별 상호 보완**

#### 한줄 요약
- 코드 커버리지 기반의 구조적 결함 검증과 명세 기반의 기능 누락 검증을 분담한다.

## Ⅲ. 구조 및 구성요소

<details><summary>용어 설명</summary>

- **MC/DC(Modified Condition/Decision Coverage)**: 복합 조건식에서 각 개별 조건이 다른 조건의 영향을 받지 않고 전체 결정 결과에 독립적으로 영향을 미침을 입증하는 최고 수준의 커버리지.

</details>

```text
[소프트웨어 테스트 기법 체계]
  │
  ├─ [화이트박스: 구조 기반]
  │     ├─ [제어 흐름] (구문·분기·조건 커버리지)
  │     ├─ [복합 조건] (MC/DC 무결성 검증)
  │     └─ [데이터 흐름] (Def-Use 체인 이상 탐지)
  │
  └─ [블랙박스: 명세 기반]
        ├─ [동등 분할] (유효/무효 동등 클래스)
        ├─ [경계값 분석] (경계 ±1 극단값 검증)
        ├─ [결정 테이블] (조건·행위 매트릭스)
        └─ [상태 전이] (FSM 이벤트 전이 검증)
```
- 선의 의미: 계층 구조 및 상하위 포함 관계를 나타낸다.

| 구성요소 | 책임 |
|:---|:---|
| 화이트박스 테스트 | **구문·분기·MC/DC·데이터 흐름** 검증 |
| 블랙박스 테스트 | **동등 분할·경계값·결정표·상태 전이** 검증 |

#### 한줄 요약
- 화이트박스는 코드에서 명세로, 블랙박스는 명세에서 코드로 접근하므로, 두 방향이 만나지 않는 영역이 곧 시험이 비어 있는 구간이다.

## Ⅳ. 흐름도

<details><summary>용어 설명</summary>

- **Coverage Illusion(커버리지 착시)**: 코드 커버리지 100%를 달성했더라도, 요구사항 자체가 아예 구현되지 않은 누락 결함(Omission Fault)은 탐지하지 못하는 현상.

</details>

```text
요구사항 명세서 기반 블랙박스 테스트 설계 (동등 분할, 경계값 추출)
        │
   소스 코드 구현 및 제어 흐름 그래프(CFG) 생성
        │
   화이트박스 단위 테스트 설계 (분기 커버리지 80% 이상 목표 수립)
        │
   테스트 실행 및 JaCoCo 커버리지 프로파일러 측정
        │
   커버리지 착시(Coverage Illusion) 검증 (화이트박스 100%라도 요구명세 누락 여부 확인)
        │
   블랙박스 인수 시나리오 교차 실행을 통한 기능 완전성 및 비기능 품질 확정
```

#### 한줄 요약
- 블랙박스를 먼저 설계해야 커버리지 수치가 명세에 없는 코드까지 정당화하는 것을 막을 수 있으므로, 두 기법의 적용 순서 자체가 검증의 의미를 좌우한다.

## Ⅴ. 종류 및 비교

<details><summary>용어 설명</summary>

- **White-box vs Black-box vs Gray-box**: 내부 코드를 완전히 아는 White-box, 코드를 전혀 안 보는 Black-box, DB 스키마나 API 명세 등 일부 내부 구조를 알고 수행하는 Gray-box.

</details>

| 비교 항목 | 화이트박스 테스트 (White-box) | 블랙박스 테스트 (Black-box) |
|:---|:---|:---|
| 테스트 기준 | **소스 코드 구조, 제어/데이터 흐름** | **요구사항 명세서, 유스케이스, API 명세** |
| 수행 주체 | 소프트웨어 개발자 (단위/통합 레벨) | **QA 엔지니어, 최종 사용자 (시스템/인수)** |
| 핵심 탐지 결함 | 논리적 분기 오류, 미실행 코드(Dead Code) | **요구사항 누락(Omission), 인터페이스 결함** |
| 주요 기법 | 구문, 분기, 조건, MC/DC, 기본 경로 | **동등 분할, 경계값 분석, 결정 테이블** |
| 코드 가시성 | **소스 코드 열람 필수 (Internal Visible)** | 소스 코드 불필요 (External View) |

#### 한줄 요약
- 화이트박스는 개발자가 코드 논리와 분기를, 블랙박스는 QA가 요구사항 명세 부합성을 검증한다.

## Ⅵ. 실무 고려사항 및 대책

<details><summary>용어 설명</summary>

- **McCabe 순환 복잡도(Cyclomatic Complexity)**: 제어 흐름 그래프에서 $V(G) = E - N + 2P$ 공식으로 계산되는 독립된 선형 실행 경로의 수.

</details>

| 문제 | 대책 | 효과 |
|:---|:---|:---|
| 구문 커버리지 100% 달성 후에도 복합 조건 결함 잔존 | **분기 커버리지 및 핵심 도메인 MC/DC 커버리지** 강제 | 복합 논리 연산자(`AND/OR`) 결함 완전 탐지 |
| 소스 커버리지 지표에 안주하여 명세 누락 결함 간과(**커버리지 착시**) | **명세 기반 블랙박스 인수 테스트 및 BDD 시나리오 병행** | 요구사항 누락(Omission Fault) 원천 차단 |
| 순환 복잡도가 높은 메서드로 인한 테스트 작성 곤란 | **McCabe 복잡도 10 이하로 메서드 분리 리팩토링** | 테스트 케이스 수 축소 및 유지보수성 향상 |
| 경계 부근에서 1 차이로 발생하는 오프바이원(Off-by-One) 결함 | **3포인트 경계값 분석 (경계점, 바로 아래, 바로 위)** 표준화 | 경계 조건 등호/부등호 오류 100% 적발 |

#### 한줄 요약
- 화이트박스는 커버리지 기준을 높일수록 비용이 급증하고 블랙박스는 내부 경로를 보지 못하므로, MC/DC 같은 강한 기준은 안전 필수 모듈에만 적용하고 나머지는 경계값 분석으로 효율을 취한다.

## Ⅶ. 결론

- 소프트웨어 품질 공학의 **양대 핵심 테스팅 방법론**으로 확립되었으며, 실무 프로젝트에서는 **단위/통합 단계에서 JaCoCo 기반 분기/조건 커버리지 측정과 안전 필수 모듈 대상 MC/DC 적용, 시스템/인수 단계에서 3포인트 경계값 분석(BVA) 및 BDD 시나리오 기반 블랙박스 검증**을 단계별로 연계하여 결함 유출률을 0화

#### 한줄 요약
- 화이트박스와 블랙박스는 상호 대체 관계가 아니며, 개발 생애주기 전반에 걸쳐 유기적으로 결합되어야 하는 필수 테스팅 기법이다.
