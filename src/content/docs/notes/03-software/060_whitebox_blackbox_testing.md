## Ⅰ. 개요

<details><summary>용어 설명</summary>

- **화이트박스 테스트(White-box Testing)**: 소프트웨어의 내부 소스 코드 구조, 제어 흐름 및 데이터 흐름을 직접 분석하여 논리적 경로와 분기 조건을 검증하는 구조 기반(Structural) 테스트 기법.
- **블랙박스 테스트(Black-box Testing)**: 내부 코드 구현을 참조하지 않고 소프트웨어의 요구사항 명세서(SRS)를 기반으로 입력값에 대한 출력 결과의 정확성을 검증하는 명세 기반(Specification-based) 테스트 기법.
- **그레이박스 테스트(Gray-box Testing)**: 내부 데이터 구조 및 아키텍처에 대한 부분적 지식을 활용하여 명세 기반 테스트 케이스의 정밀도를 향상시키는 절충형 테스트 기법.

</details>

- 정의/개념: 내부 로직의 실행 경로를 검증하는 **화이트박스(White-box)** 와 요구사항 명세 충족 여부를 검증하는 **블랙박스(Black-box)** 테스트 기법의 비교 체계
- 배경/필요성: 단일 테스트 관점 적용 시 발생하는 미실행 경로 결함(Dead Code) 누락 또는 요구사항 미구현(Omission) 결함 미탐지 한계 극복 요구

#### 한줄 요약
- 내부 소스 코드의 제어 흐름 검증(화이트박스)과 외부 명세 기반의 입출력 검증(블랙박스)을 상호 보완한다.

## Ⅱ. 특징

<details><summary>용어 설명</summary>

- **제어 흐름 그래프(Control Flow Graph, CFG)**: 프로그램의 실행 흐름을 노드(기본 블록)와 엣지(제어 분기)로 도식화하여 실행 경로를 분석하는 정형 모델.
- **명세 기반 테스트(Specification-based Testing)**: 기능적/비기능적 요구사항 정의서 및 유스케이스로부터 테스트 케이스를 체계적으로 도출하는 방식.

</details>

- **화이트박스**는 소스 코드의 구문, 분기, 조건 커버리지를 측정하여 구조적 결함 식별
- **블랙박스**는 동등 분할, 경계값 분석 등을 활용하여 사용자 관점의 기능 적합성 및 인터페이스 결함 식별
- 적용 레벨: 화이트박스는 단위(Unit) 및 통합(Integration) 수준, 블랙박스는 시스템(System) 및 인수(Acceptance) 수준에 주력 적용

#### 한줄 요약
- 코드 커버리지 기반의 구조적 결함 검증과 명세 기반의 기능 누락 검증을 분담한다.

## Ⅲ. 구조 및 구성요소

<details><summary>용어 설명</summary>

- **동등 분할(Equivalence Partitioning)**: 입력 데이터 영역을 동일한 결과를 유발할 것으로 기대되는 유효/무효 동등 클래스로 분할하여 대표값을 선정하는 기법.
- **경계값 분석(Boundary Value Analysis)**: 동등 클래스의 경계선상에 위치한 값(최소값, 경계값, 최대값 등)에서 결함 발생 확률이 높다는 특성을 이용한 테스트 기법.

</details>

```text
[ 소프트웨어 테스트 기법 분류 ]
 ├─ 화이트박스 테스트 (구조 기반)
 │   ├─ 구문 커버리지 (Statement Coverage)
 │   ├─ 분기 커버리지 (Branch/Decision Coverage)
 │   ├─ 조건 커버리지 (Condition Coverage)
 │   └─ MC/DC (Modified Condition/Decision Coverage)
 └─ 블랙박스 테스트 (명세 기반)
     ├─ 동등 분할 (Equivalence Partitioning)
     ├─ 경계값 분석 (Boundary Value Analysis)
     ├─ 결정 테이블 (Decision Table Testing)
     └─ 상태 전이 테스트 (State Transition Testing)
```

선의 의미: `├─`는 테스트 설계 기준(내부 구조 vs 외부 명세)에 따른 세부 기법 분류

| 구성요소 | 책임 |
|:---|:---|
| **구문/분기 커버리지 (화이트박스)** | 모든 실행 코드 구문과 `True/False` 분기 경로가 최소 1회 이상 실행됨을 보증 |
| **MC/DC (화이트박스)** | 각 조건문이 독립적으로 전체 조건식의 결과에 영향을 미치는지 정밀 검증(안전 필수 도메인) |
| **동등 분할 (블랙박스)** | 유효/무효 클래스별 대표 입력을 선정하여 중복 테스트 케이스 축소 및 효율화 |
| **경계값 분석 (블랙박스)** | 입력 범위 경계값($-1, 0, +1$)을 집중 테스트하여 오프바이원(Off-by-One) 결함 탐지 |

#### 한줄 요약
- 화이트박스는 구문/분기/조건 커버리지를 통제하고, 블랙박스는 동등 분할과 경계값 분석으로 입력을 검증한다.

## Ⅳ. 흐름도

<details><summary>용어 설명</summary>

- **기본 경로 테스트(Basis Path Testing)**: McCabe 순환 복잡도(Cyclomatic Complexity)를 기반으로 독립적인 선형 실행 경로의 집합을 도출하여 100% 분기 커버리지를 설계하는 기법.

</details>

```text
1. 요구사항 명세 분석 및 블랙박스 테스트 설계 (동등 분할, 경계값 추출)
            │
            ▼
2. 소스 코드 정적 분석 및 제어 흐름 그래프(CFG) 생성
            │
            ▼
3. 화이트박스 테스트 설계 (기본 경로 및 커버리지 목표 수립)
            │
            ▼
4. 교차 실행 및 커버리지 측정: 미실행 경로 및 명세 미준수 결함 도출
            │
            ▼
5. 결함 리포팅 및 회귀 테스트: 명세 미구현 및 미사용 코드(Dead Code) 정비
```

**동작 원리**

1. **명세 기반 설계**: 요구사항 문서를 분석하여 정상/예외 시나리오별 입출력 테스트 케이스 생성
2. **코드 구조 분석**: 소스 코드로부터 제어 흐름 그래프를 도출하고 순환 복잡도 산정
3. **구조적 테스트 설계**: 목표 커버리지(분기, 조건 등)를 달성하기 위한 단위 테스트 케이스 보완
4. **통합 실행**: 테스트 스위트를 실행하고 런타임 커버리지 프로파일러를 통해 미실행 경로 확인
5. **상호 보완**: 블랙박스로 발견된 '명세 미구현'과 화이트박스로 발견된 '불필요한 코드'를 상호 정비

#### 한줄 요약
- 명세 분석과 코드 제어 흐름 분석을 병행하여 블랙박스와 화이트박스 케이스를 교차 검증한다.

## Ⅴ. 종류 및 비교

<details><summary>용어 설명</summary>

- **순환 복잡도(Cyclomatic Complexity)**: 제어 흐름 그래프에서 $V(G) = E - N + 2P$ (엣지 수 - 노드 수 + $2 \times$ 연결 성분)로 계산되는 독립 경로 수 지표.

</details>

| 비교 항목 | 화이트박스 테스트 (White-box) | 블랙박스 테스트 (Black-box) |
|:---|:---|:---|
| **테스트 기준 (Basis)** | 내부 소스 코드, 제어 흐름, 데이터 흐름 | 요구사항 명세서, 유스케이스, 인터페이스 정의서 |
| **수행 주체 및 레벨** | 개발자 중심 / 단위 및 통합 테스트 | QA 엔지니어, 최종 사용자 / 시스템 및 인수 테스트 |
| **주요 탐지 결함** | 논리적 제어 오류, 메모리 누수, 미사용 코드(Dead Code) | 요구사항 미구현(Omission), 인터페이스 불일치, 성능 결함 |
| **코드 가시성 요구** | 소스 코드 구조에 대한 완전한 지식 필수 | 소스 코드 열람 없이 입출력 사양만으로 수행 가능 |

#### 한줄 요약
- 화이트박스는 개발자가 코드 논리를 검증하고, 블랙박스는 QA/사용자가 요구사항 부합성을 검증한다.

## Ⅵ. 실무 고려사항 및 대책

<details><summary>용어 설명</summary>

- **커버리지 착시(Coverage Illusion)**: 코드 커버리지 100%를 달성하더라도 요구사항 자체가 누락된 기능(Omission Fault)은 탐지할 수 없는 구조적 한계.

</details>

| 문제 | 대책 | 효과 |
|:---|:---|:---|
| 구문 커버리지 100% 달성 후에도 복합 조건 결함 잔존 | **분기 커버리지** 및 안전 필수 영역에 **MC/DC** 의무화 | 다중 조건식의 개별 평가 결함 완전 탐지 |
| 소스 코드 커버리지 지표에만 의존하여 명세 누락 결함 간과 | **명세 기반 블랙박스 인수 테스트(Acceptance Test)** 교차 수행 | 커버리지 착시 방지 및 요구사항 완전성 보증 |
| 전체 레거시 시스템 대상 화이트박스 적용 시 비용 과다 | 핵심 비즈니스 도메인은 **화이트박스**, 외부 인터페이스는 **블랙박스** 차등 적용 | 테스트 투자 대비 결함 검출 효율성 극대화 |

#### 한줄 요약
- 분기 및 MC/DC 커버리지 적용과 명세 기반 인수 테스트 교차 검증을 통해 커버리지 착시를 극복한다.

## Ⅶ. 결론

- 소프트웨어 품질 확보를 위해 단위/통합 단계에서는 **화이트박스(구문·분기·MC/DC)** 검증을 통해 코드 레벨 무결성을 확보하고, 시스템/인수 단계에서는 **블랙박스(경계값·결정테이블)** 검증을 교차 적용하여 요구사항 준수와 구조적 안정성을 종합적으로 보증

#### 한줄 요약
- 개발 생명주기 단계별로 화이트박스와 블랙박스 기법을 상호 보완적으로 배치하여 결함 누출을 방지한다.
