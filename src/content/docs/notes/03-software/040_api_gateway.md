## Ⅰ. 개요

<details><summary>용어 설명</summary>

- **API 게이트웨이(API Gateway)**: 클라이언트가 수십 개의 마이크로서비스 주소를 일일이 외우지 않게, 맨 앞에서 트래픽을 다 받아주고 인증과 라우팅을 짬처리하는 듬직한 문지기(엣지 서버)이다.
- **리버스 프록시(Reverse Proxy)**: 밖에서 들어오는 요청을 가로채서 안에 있는 진짜 서버들한테 몰래 토스해 주며, 내부망 IP와 구조를 꽁꽁 숨겨버리는 방패막이 역할이다.
- **BFF(Backend For Frontend)**: 모바일 앱용, 웹용 등 화면 사이즈와 용도에 맞게 API 게이트웨이를 여러 개 찢어놓고, 화면에 딱 맞는 데이터만 예쁘게 조합해서 내려주는 커스텀 그릇이다.

</details>

- 정의: 외부 클라이언트가 마이크로서비스를 직접 쑤시지 못하게 막고, 앞단에서 인증/보안/라우팅을 한 번에 처리하는 단일 관문 **API Gateway**
- 배경: 서비스마다 로그인 검사하고 트래픽 룰 짜면 **개발자들 퇴근 못 하고 인증 코드만 복붙**하다 플젝이 망하기 때문

#### 한줄 요약

- MSA에서 밖에서 들어오는 트래픽을 한 놈(문지기)이 받아서 짬처리(인증, 라우팅)하는 구조다.

## Ⅱ. 특징

<details><summary>용어 설명</summary>

- **트래픽 제어(Rate Limiting)**: 매크로나 디도스 공격이 들어올 때 "1초에 100번 넘으면 차단!"이라며 방화벽처럼 트래픽 멱살을 잡고 터지는 걸 막는 조절기이다.
- **SSL 종료(SSL Termination)**: 무거운 HTTPS 암호화 풀기(복호화)를 백엔드 서버들이 각자 하면 뻗으니까, 게이트웨이가 밖에서 깐 다음에 안쪽으론 가벼운 HTTP로 쏴주는 오버헤드 패스 기술이다.

</details>

- 클라이언트의 쏟아지는 요청을 하나로 받는 **단일 진입점**이자, 내부 IP 주소를 숨기는 캡슐화 방패임.
- **인증(JWT 검사), 트래픽 제어(Rate Limiting), SSL 복호화** 같은 노가다성 공통 로직을 싹 다 짬처리함.
- **BFF 패턴**을 적용하면, 프론트가 5개 API 찔러서 짜깁기할 걸 게이트웨이가 한방에 말아서 내려줌.

#### 한줄 요약

- 백엔드 주소 숨겨주고, 인증/보안 다 막아주고, 흩어진 데이터 하나로 예쁘게 말아준다.

## Ⅲ. 구조 및 구성요소

<details><summary>용어 설명</summary>

- **필터 체인(Filter Chain)**: 게이트웨이에 들어온 요청이 백엔드로 가기 전에 인증 필터 $\to$ 로깅 필터 $\to$ 헤더 조작 필터를 차례대로 뚫고 지나가는 컨베이어 벨트이다.

</details>

```text
[ API 게이트웨이 파이프라인 십자포화 아키텍처 ]

        [ 외부 클라이언트 (Web/App) ]
                     │
         [ 1. SSL 해제 및 인증 엔진 ]
         [ 2. 트래픽 제어 (Rate Limit) ]
         [ 3. 필터 체인 (헤더 조작) ]
         [ 4. 라우터 (경로 탐색) ]
              /              \
     [ 주문 서비스 ]      [ 결제 서비스 ]
```

| 구성요소 | 책임 |
|:---|:---|
| 진입 정책 엔진 | 토큰(JWT) 까보고 짭이면 뱉어내고, 초당 호출 횟수 넘으면 차단(Rate Limit)하는 경찰 |
| 경로 라우터 | `/orders`로 오면 주문 서버, `/pay`로 오면 결제 서버로 길 안내하는 내비게이션 |
| 요청/응답 변환기 | 프론트가 읽기 편하도록 백엔드 3군데서 온 데이터를 하나로 말아주는 짬짜면 그릇 |
| 관측 처리기 | 요청마다 Trace ID(꼬리표) 달아서 백엔드 어디서 뻗었는지 CCTV(분산 추적)로 감시함 |

#### 한줄 요약

- 토큰 까보고 $\to$ 트래픽 거르고 $\to$ 헤더 조작해서 $\to$ 맞는 백엔드 서버로 쏴준다.

## Ⅳ. 흐름도

<details><summary>용어 설명</summary>

- **토큰 버킷 알고리즘(Token Bucket Algorithm)**: 바구니에 토큰을 1초에 10개씩 채우고, 요청 들어올 때마다 토큰을 하나씩 쓰게 해서 바구니 비면 차단하는 쌉근본 트래픽 억제 알고리즘이다.

</details>

```text
[ API 게이트웨이 요청 처리 십자포화 흐름 ]
┌──────────────────────────────┐
│ 클라이언트 API 요청 (HTTPS)  │
└──────────────┬───────────────┘
               ▼
┌──────────────────────────────┐
│ 1. TLS 종료 (SSL 껍데기 깜)  │
│ 2. 진입 검증 (JWT 인증)      │
│ 3. L7 라우팅 (길 찾기)       │
│ 4. 백엔드 서비스 호출        │
│ 5. 응답 조합 (JSON 짬짜면)   │
└──────────────┬───────────────┘
               ▼
┌──────────────────────────────┐
│ 클라이언트 최종 응답 반환    │
└──────────────────────────────┘
```

### 동작 원리

1. TLS 종료: 무거운 암호화(HTTPS)를 밖에서 걷어내고 안쪽으론 가벼운 HTTP로 쏨.
2. 진입 검증: 경찰(JWT)과 신호등(Token Bucket)을 거쳐 찌꺼기 트래픽을 거름.
3. L7 라우팅: 디스커버리(Eureka)한테 물어봐서 목적지 IP 주소 찾아냄.
4. 서비스 호출: 백엔드 API를 찔러서 데이터 긁어옴.
5. 응답 조합: 데이터 뭉쳐서(BFF) 프론트한테 예쁘게 던져줌.

#### 한줄 요약

- 암호화 풀고 $\to$ 토큰 검사하고 $\to$ 길 찾아서 찌르고 $\to$ 결과 뭉쳐서 던져준다.

## Ⅴ. 종류 및 비교

<details><summary>용어 설명</summary>

- **Spring Cloud Gateway vs Kong**: Java 개발자들이 환장하는 스프링 찰떡궁합 게이트웨이(SCG)와, Nginx/C 기반으로 미친 속도를 뽐내는 고성능 게이트웨이(Kong)의 양대 산맥이다.

</details>

| 구현체 / 솔루션 | 기반 기술 | 특징 및 장단점 팩트폭행 |
|:---|:---|:---|
| **Kong Gateway** | Nginx / C / Lua | 깡패 같은 속도. 비-자바 진영이나 대규모 트래픽에서 국룰로 씀 |
| **Spring Cloud Gateway** | Java / Spring WebFlux | 자바/스프링 생태계와 찰떡. 비동기 논블로킹(Netty) 지원 |
| **AWS API Gateway** | AWS 관리형 서비스 | 서버 관리 1도 안 해도 됨. 근데 트래픽 폭발하면 요금 폭탄 맞음 |
| **Envoy Proxy** | C++ | 가벼워서 API 게이트웨이보단 K8s 서비스 메시(Service Mesh) 사이드카로 더 씀 |

#### 한줄 요약

- 속도가 깡패면 Kong, 자바 공화국이면 Spring Cloud Gateway, 귀찮으면 AWS를 쓴다.

## Ⅵ. 실무 고려사항 및 대책

<details><summary>용어 설명</summary>

- **단일 장애점(SPOF, Single Point of Failure)**: 백엔드 서버가 100대 살아있어도, 문지기(API 게이트웨이) 하나 죽으면 온 동네 서비스가 올스톱되는 치명적인 아킬레스건이다.

</details>

| 문제 | 대책 | 효과 |
|:---|:---|:---|
| 게이트웨이 하나 뻗었더니 전체 서비스 마비 (**SPOF**) | 앞단에 **L4 로드밸런서(LB)** 박고 인스턴스 무조건 다중화(Scale-out) | 문지기 하나 죽어도 끄떡없는 고가용성 |
| 개발자 놈들이 비즈니스 로직(DB 쿼리 등)을 게이트웨이에 짬처리함 | 게이트웨이엔 **공통 횡단 로직(라우팅, 인증)**만 두고 연산 철저 배제 | 게이트웨이 스파게티화 및 병목 차단 |
| 봇이 1초에 1만 번씩 결제 API 쑤시며 테러함 | 토큰 버킷 기반 **Rate Limiting**과 **Circuit Breaker** 멱살 잡고 적용 | 백엔드 연쇄 폭발 및 트래픽 테러 방어 |

#### 한줄 요약

- 게이트웨이는 무조건 두 대 이상(SPOF 대비) 띄우고, 무거운 로직은 절대 태우지 마라.

## Ⅶ. 결론

<details><summary>용어 설명</summary>

- **API 게이트웨이 도입 기준(API Gateway Adoption Criteria)**: 마이크로서비스가 3개 이상인지, 맞춤형(BFF) 응답이 필요한지, 트래픽 억제기가 필요한지 각 재서 문지기를 세울지 결정하는 잣대이다.

</details>

- **API 게이트웨이 도입 기준** 원칙에 따라, 공통 보안/라우팅이 필요한 분산 환경은 **API Gateway**, 단일 거대 앱은 **직접 호출** 채택 기조 확립함

#### 한줄 요약

- 마이크로서비스가 찢어질수록, 문지기(API 게이트웨이)의 트래픽 경찰 역할은 절대적이다.
