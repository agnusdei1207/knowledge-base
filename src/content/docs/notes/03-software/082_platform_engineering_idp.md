## Ⅰ. 개요

<details>
<summary>핵심 용어</summary>

- **플랫폼 엔지니어링(Platform Engineering)**: 반복 개발•배포•운영 기능을 셀프서비스 플랫폼으로 제공하고 개발자 경험을 내부 제품처럼 개선하는 운영 방식이다.
- **내부 개발자 플랫폼(Internal Developer Platform, IDP)**: 개발자가 환경과 배포를 직접 쓰는 셀프서비스 플랫폼이다.
- **대기시간(Waiting Time)**: 티켓 기반 자원 제공을 기다리는 시간이다.
- **환경 편차(Environment Drift)**: 수동 구성으로 개발 환경이 서로 달라진 상태다.
- **운영 병목(Operational Bottleneck)**: 인프라 요청이 전문팀에 집중된 상태다.

</details>

- 정의/개념: 반복 개발•배포•운영 기능을 셀프서비스 IDP로 제공하고 내부 제품처럼 개선하는 **플랫폼 엔지니어링 기반 개발자 지원 운영 방식**
- 배경/필요성: 티켓 기반 수동 제공은 **대기시간•환경 편차•운영 병목**

#### 한줄 요약

- 개발자는 승인 티켓을 기다리지 않고 검증된 메뉴에서 필요한 환경을 직접 만든다.

## Ⅱ. 특징

<details>
<summary>핵심 용어</summary>

- **포털 추상화(Portal Abstraction)**: 화면 뒤에 복잡한 인프라 세부를 숨기는 경계다.
- **응용 프로그래밍 인터페이스(Application Programming Interface, API)**: 다른 시스템 기능을 호출하는 규칙과 접점이다.
- **정책 코드 가드레일**: 보안•비용•운영 규칙을 실행 가능한 정책으로 자동 판정하는 통제이다.
- **플랫폼 제품 운영**: 개발자 문제와 사용 성과를 근거로 내부 플랫폼을 지속 개선하는 방식이다.

</details>

- **포털•API 추상화** 로 복잡한 인프라 작업 은닉
- **정책 코드 가드레일** 로 보안•비용 기준 자동 적용
- **플랫폼 제품 운영**으로 채택률•실패율•개발자 경험 개선

#### 한줄 요약

- 개발자는 내부 구조를 몰라도 표준 메뉴를 고르고 플랫폼은 허용된 구성만 자동 제공한다.

## Ⅲ. 구조 및 구성요소

<details>
<summary>핵심 용어</summary>

- **개발자 포털(Developer Portal)**: 서비스•문서•셀프서비스 요청의 단일 진입점이다.
- **서비스 카탈로그(Service Catalog)**: 검증된 환경•배포 템플릿과 소유 정보를 모은 목록이다.
- **자동화 워크플로**: 자원 생성•설정•배포 작업을 정해진 순서로 실행하는 흐름이다.
- **정책 가드레일**: 보안•비용•운영 기준의 허용 여부를 자동 판정하는 규칙이다.

</details>

```text
[개발자 포털] -------- [서비스 카탈로그] -------- [자동화 워크플로]
                                                     |
                                                     |
                                               [정책 가드레일]
```

선의 의미: 개발자 포털과 서비스 카탈로그의 선은 셀프서비스 요청과 검증 템플릿 선택 관계, 서비스 카탈로그와 자동화 워크플로의 선은 환경•배포 명세 제공 관계, 자동화 워크플로와 정책 가드레일의 선은 자원 생성•설정•배포에 대한 보안•비용•운영 기준 판정 관계를 뜻한다.

| 구성요소 | 책임 |
|:---|:---|
| 개발자 포털 | **서비스•문서•요청** 의 단일 진입점 |
| 서비스 카탈로그 | 검증된 **환경•배포 템플릿** 제공 |
| 자동화 워크플로 | **자원 생성•설정•배포** 실행 |
| 정책 가드레일 | **보안•비용•운영 기준** 판정 |

#### 한줄 요약

- 포털에서 표준 구성을 고르면 자동화와 정책 검사가 실행된다.

## Ⅳ. 흐름도

<details>
<summary>핵심 용어</summary>

- **템플릿(Template)**: 검증된 환경 구성을 재사용하는 표준 양식이다.
- **매개변수(Parameter)**: 템플릿 실행 시 사용자가 제공하는 값이다.
- **소유 정보(Ownership Metadata)**: 생성 자원을 책임질 팀과 담당자 정보다.
- **자원 명세(Resource Specification)**: 생성할 실행 환경의 선언이다.
- **정책 컨텍스트(Policy Context)**: 가드레일 판정에 필요한 조건이다.
- **승인 자원(Approved Resource)**: 정책 검증을 통과한 실행 환경이다.
- **파이프라인 명세(Pipeline Specification)**: 승인 자원의 전달 경로 선언이다.

</details>

```mermaid
sequenceDiagram
    participant D as 개발자
    participant P as IDP•자동화 워크플로
    participant C as 서비스 카탈로그
    participant G as 정책 가드레일
    participant R as 실행 환경
    D->>P: 카탈로그 템플릿•요청값
    P->>C: 1. 템플릿•매개변수•소유 정보 구체화
    C-->>P: 구체화 결과
    P->>G: 2. 자원 명세•정책 컨텍스트
    G-->>P: 허용•위반•보완 조건
    P->>R: 3. 승인 자원•파이프라인 명세
    R-->>P: 배포•건강 상태
    P-->>D: 운영 접점•소유 정보•피드백 경로
```

**동작 원리**

- **1. 템플릿•매개변수•소유 정보**: 검증된 경로를 실행 가능한 요청으로 구체화
- **2. 자원 명세•정책 컨텍스트**: 보안•비용•운영 기준의 허용 여부 판정
- **3. 승인 자원•파이프라인 명세**: 허용된 표준 실행 환경을 자동 구성

> 요약: 검증된 템플릿을 자동 가드레일 안에서 셀프서비스로 생성하고 사용 피드백으로 개선

#### 한줄 요약

- 표준 메뉴를 선택하면 정책 검사 뒤 환경과 운영 도구가 함께 준비된다.

## Ⅴ. 종류 및 비교

<details>
<summary>핵심 용어</summary>

- **전통적 공용 인프라팀**: 비정형 요청을 운영 담당자가 건별로 수동 처리하는 제공 방식이다.

</details>

| 개발 환경 제공 | 플랫폼 엔지니어링 IDP | 전통적 공용 인프라팀 |
|:---|:---|:---|
| 적용 기준 | 반복 환경의 **신속•표준 배포** | 비정형 **예외 환경 중심** |
| 핵심 특징 | 개발자의 **표준 구성 셀프서비스** | 운영팀의 **요청별 수동 작업** |
| 한계 | 경직된 표준•**현장 요구 불일치** | 요청 병목•**담당자 의존** |

> 요약: 운영팀 티켓을 자동 검사 기반 셀프서비스로 전환함

#### 한줄 요약

- IDP는 반복 요청을 자동화하고 플랫폼팀은 예외와 공통 경로 개선에 집중한다.

## Ⅵ. 실무 고려사항 및 대책

<details>
<summary>핵심 용어</summary>

- **사용자 연구(User Research)**: 개발자의 실제 불편과 요구를 조사하는 활동이다.
- **사용 데이터(Usage Data)**: 플랫폼 사용자의 실제 행동 기록이다.
- **제품 로드맵(Product Roadmap)**: 플랫폼 기능의 개발 순서를 정한 계획이다.
- **승인 예외(Approved Exception)**: 골든 패스 밖의 요구를 제한적으로 허용한 상태다.
- **회수 절차(Revocation Procedure)**: 승인 예외를 종료하고 권한을 거두는 절차다.
- **메타데이터 동기화(Metadata Synchronization)**: 카탈로그 정보를 실제 시스템과 맞추는 활동이다.
- **만료 검증(Expiration Validation)**: 오래된 카탈로그 항목을 확인하는 활동이다.
- **책임 경계(Responsibility Boundary)**: 플랫폼팀과 사용팀의 장애 처리 범위다.
- **진단(Diagnostics)**: 장애 원인을 찾기 위해 하부 상태를 확인하는 활동이다.
- **원시 도구 접근(Raw-tool Access)**: 복구 시 하부 도구를 직접 사용하는 수단이다.
- **처리 시간(Lead Time)**: 셀프서비스 요청부터 완료까지 걸린 시간이다.
- **실패율(Failure Rate)**: 표준 경로 실행 중 실패한 요청 비율이다.
- **우회율(Bypass Rate)**: 사용자가 표준 경로를 쓰지 않은 비율이다.
- **만족도(Satisfaction)**: 개발자가 플랫폼을 유용하다고 평가한 정도다.

</details>

| 문제 | 대책 | 효과 |
|:---|:---|:---|
| 공급자 편의로 기능을 정해 개발자 문제와 불일치 | **사용자 연구•사용 데이터 기반 로드맵** | **개발자 문제•기능 일치** |
| 골든 패스가 예외 요구를 막아 비공식 우회 증가 | **승인 예외•회수 절차** 제공 | **비정형 요구 우회** 감소 |
| 하부 장애가 추상화 밖으로 드러나 원인 진단 지연 | **책임 경계•진단•원시 도구 접근** 제공 | **장애 복구 시간** 단축 |
| 카탈로그 소유•지원 정보가 실제 시스템과 불일치 | **메타데이터 동기화•만료 검증** | **소유•지원 정보 현행화** |
| 채택률만 높여 느린 표준 경로의 강제 사용 은폐 | **시간•실패율•우회율•만족도** 측정 | **개발자 성과 중심 개선** |

> 적용 사례: 표준 포털의 환경 생성시간•채택률•실패율•우회율을 함께 측정

#### 한줄 요약

- 표준 경로가 수동 요청보다 빠르고 편해야 개발자가 우회하지 않는다.

## Ⅶ. 결론

<details>
<summary>핵심 용어</summary>

- **IDP 셀프서비스**: 반복•표준 수요를 개발자가 검증된 경로에서 직접 처리하는 방식이다.
- **전문팀 지원**: 비정형 예외를 전문 지식과 수동 검토로 처리하는 방식이다.

</details>

- 반복•표준 수요는 **IDP 셀프서비스**, 비정형 예외는 **전문팀 지원**

#### 한줄 요약

- IDP는 개발자에게 빠른 셀프서비스를 주고 조직에는 자동 통제를 제공할 때 효과가 난다.
