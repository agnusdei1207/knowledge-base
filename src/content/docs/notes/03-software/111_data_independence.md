## Ⅰ. 개요

<details><summary>용어 설명</summary>

- **데이터 독립성(Data Independence)**: 하위 레벨의 데이터 구조가 변경되더라도 상위 계층이나 응용 프로그램에 영향을 주지 않는 아키텍처 원칙.
- **2단계 사상(Two-Level Mapping)**: 외부-개념 사상(논리적 독립성)과 개념-내부 사상(물리적 독립성)으로 구성된 계층 간 연결 메커니즘.

</details>

- 정의/개념: ANSI/SPARC 3단계 스키마 구조에서 하위 레벨의 데이터 구조 변경이 **상위 스키마 및 응용 프로그램에 영향을 주지 않도록 격리하는 논리·물리 독립성** 설계 원칙
- 배경/필요성: 파일 처리 시스템의 프로그램-데이터 강결합으로 인한 **저장 구조 변경 시 애플리케이션 전면 수정 및 유지보수 비용 급증 해결 불가**

#### 한줄 요약
- 2단계 사상(Mapping)을 통해 비즈니스 모델 변경과 물리 저장 구조 튜닝을 상호 격리한다.

## Ⅱ. 특징

<details><summary>용어 설명</summary>

- **논리적 데이터 독립성**: 개념 스키마(테이블/컬럼)가 변경되어도 외부 스키마(View)와 응용 프로그램이 영향받지 않는 성질.
- **물리적 데이터 독립성**: 내부 스키마(인덱스, 파티션, 스토리지)가 변경되어도 개념 스키마와 응용 프로그램이 영향받지 않는 성질.

</details>

- ANSI/SPARC 표준 3단계 계층의 **외부, 개념, 내부 스키마 분리 구조**
- 뷰(View)와 외부-개념 매핑을 통한 **논리적 데이터 독립성(Logical Independence) 확보**
- 인덱스 및 개념-내부 매핑을 통한 **물리적 데이터 독립성(Physical Independence) 확보**

#### 한줄 요약
- 2단계 사상으로 논리 모델과 물리 저장 변경의 영향을 줄인다.

## Ⅲ. 구조 및 구성요소

<details><summary>용어 설명</summary>

- **3단계 스키마 계층**: 외부 스키마(사용자 뷰), 개념 스키마(통합 엔티티/관계), 내부 스키마(물리 저장 구조).

</details>

```text
[ANSI/SPARC 3단계 스키마 및 2단계 사상 구조]
|-- 외부 스키마 (External Schema: 사용자별 View 1, View 2)
|   `-- [외부-개념 사상]
|-- 개념 스키마 (Conceptual Schema: 통합 엔티티, 속성, 관계, 무결성 제약조건)
|   `-- [개념-내부 사상]
`-- 내부 스키마 (Internal Schema: B+Tree 인덱스, 데이터 파일, 파티션, 디스크 블록)
```

선의 의미: 계층 및 3단계 스키마 사이의 2단계 사상(Mapping)을 통한 변경 전파 차단 구조

| 구성요소 | 책임 |
|:---|:---|
| 외부 스키마 | 사용자별 **뷰·인터페이스** 정의 |
| 외부-개념 사상 | 뷰와 개념 모델의 대응 관계 유지 |
| 개념 스키마 | 엔티티·관계·무결성 제약 정의 |
| 개념-내부 사상 | 논리 모델과 저장 구조의 대응 유지 |
| 내부 스키마 | **인덱스·파일·파티션** 저장 방식 정의 |

#### 한줄 요약
- 외부(뷰), 개념(통합 모델), 내부(물리 저장) 계층과 2단계 매핑이 결합된다.

## Ⅳ. 흐름도

<details><summary>용어 설명</summary>

- **스키마 변경 5단계 파이프라인**: 변경 계층 식별 $\to$ 사상 갱신 $\to$ 인터페이스 보존 $\to$ 호환성 검증 $\to$ 무중단 적용.

</details>

```text
비즈니스 요구 변화에 따른 스키마 변경 요청 발생
        │
   [계층 식별] 물리적 성능 튜닝(내부)인가, 테이블 컬럼 추가(개념)인가 식별
        │
   [사상 갱신] 변경 계층에 따라 개념-내부 사상 또는 외부-개념 사상 메타데이터 수정
        │
   [인터페이스 보존] 응용 프로그램이 바라보는 외부 뷰(View)의 시그니처 불변 유지
        │
   [호환성 검증] 기존 SQL 질의 및 트랜잭션이 에러 없이 동일 결과 반환함을 검증
        │
   [변경 적용] 호환성 검증 결과에 따라 스키마와 사상 활성화
```

#### 한줄 요약
- 계층 식별 → 사상 갱신 → 인터페이스 보존 → 호환성 검증 → 무중단 전환 순으로 진행된다.

## Ⅴ. 종류 및 비교

<details><summary>용어 설명</summary>

- **논리적 vs 물리적 독립성**: 비즈니스 모델 변화에 대응하는 논리적 독립성과 인덱스/스토리지 튜닝에 대응하는 물리적 독립성.

</details>

| 비교 항목 | 논리적 데이터 독립성 (Logical) | 물리적 데이터 독립성 (Physical) |
|:---|:---|:---|
| 변경 대상 계층 | **개념 스키마 (테이블 분할, 신규 컬럼 추가)** | **내부 스키마 (인덱스 추가, 파티셔닝, SSD 교체)**|
| 영향 격리 범위 | **외부 스키마 및 애플리케이션 소스코드 불변** | **개념 스키마 및 외부 스키마/애플리케이션 불변** |
| 매핑 메타데이터 | **외부-개념 사상(External-Conceptual Mapping)**| **개념-내부 사상(Conceptual-Internal Mapping)**|
| 주 변경 목적 | 비즈니스 요구사항 추가 및 도메인 모델 진화 | **쿼리 속도 개선 및 스토리지 입출력 튜닝** |

#### 한줄 요약
- 논리적 독립성은 비즈니스 모델 변경을 격리하고, 물리적 독립성은 성능 튜닝 변경을 격리한다.

## Ⅵ. 실무 고려사항 및 대책

<details><summary>용어 설명</summary>

- **Expand-Contract Pattern**: 컬럼/테이블 변경 시 구버전과 신버전을 병행 유지(Expand)한 뒤 클라이언트 이전 후 구버전을 제거(Contract)하는 무중단 패턴.

</details>

| 문제 | 대책 | 효과 |
|:---|:---|:---|
| 앱의 물리 테이블 직접 참조 | **DB View·Repository 계층** 도입 | 논리 스키마 변경 영향 완화 |
| SQL 쿼리 내 물리적 인덱스 힌트(`/*+ INDEX */`) 하드코딩 남발 | **CBO 옵티마이저 통계 기반 자동 선택에 위임하고 힌트 최소화** | 물리적 데이터 독립성 보존 |
| 컬럼 삭제 시 레거시 런타임 오류 | **Expand-Contract 패턴** 적용 | 구·신 버전의 전환 기간 확보 |
| 대규모 DDL의 테이블 락 | **온라인 DDL 도구** 활용 | 변경 중 잠금과 중단 시간 감소 |

#### 한줄 요약
- 뷰/ORM 추상화, 힌트 최소화, Expand-Contract 패턴, 온라인 DDL로 데이터 독립성을 실현한다.

## Ⅶ. 결론

- 논리 격리는 **외부-개념 사상**, 물리 격리는 **개념-내부** 선택

#### 한줄 요약
- 논리 변경은 외부 사상, 저장 변경은 내부 사상으로 격리한다.
