## Ⅰ. 개요

<details><summary>용어 설명</summary>

- **데이터 독립성(Data Independence)**: 데이터베이스의 3단계 스키마(외부, 개념, 내부) 계층 구조에서 하위 레벨의 데이터 구조가 변경되더라도 상위 계층이나 응용 프로그램에 영향을 주지 않는 아키텍처 특성.
- **프로그램-데이터 결합 및 유지보수 비용(Tight Coupling & Maintenance Cost)**: 과거 파일 시스템처럼 물리적 저장 구조나 컬럼이 바뀔 때마다 모든 소스코드를 재작성해야 하는 구조적 한계.

</details>

- 정의/개념: 3단계 스키마 구조에서 하위 레벨의 데이터 구조 변경이 **상위 스키마 및 응용 프로그램에 영향을 주지 않도록 격리하는 논리·물리 독립성** 설계 원칙
- 배경/필요성: 파일 처리 시스템의 데이터-프로그램 간 강한 결합으로 인한 **저장 구조 변경 시 애플리케이션 전면 재개발 및 유지보수 비용 급증 위험** 직면

#### 한줄 요약

- 외부-개념 매핑(논리적)과 개념-내부 매핑(물리적)을 통해 스키마 변경 시 응용 프로그램의 수정 없이 영속성을 보장

## Ⅱ. 특징

<details><summary>용어 설명</summary>

- **논리적 데이터 독립성(Logical Data Independence)**: 개념 스키마(테이블 컬럼 추가/삭제)가 변경되어도 외부 스키마(View) 및 응용 프로그램이 영향받지 않는 속성.
- **물리적 데이터 독립성(Physical Data Independence)**: 내부 스키마(인덱스 재구성, 파티셔닝, 디스크 파일 레이아웃)가 변경되어도 개념 스키마 및 응용 프로그램이 영향받지 않는 속성.

</details>

- ANSI/SPARC 3단계 스키마 계층의 **외부, 개념, 내부 스키마 분리 구조**
- 뷰(View)와 외부-개념 매핑을 통한 **논리적 데이터 독립성(Logical Independence) 확보**
- 인덱스 및 개념-내부 매핑을 통한 **물리적 데이터 독립성(Physical Independence) 확보**

#### 한줄 요약

- 2단계 사상(Mapping) 구조를 통해 비즈니스 모델 변화와 물리 저장 장치 튜닝을 상호 격리

## Ⅲ. 구조 및 구성요소

<details><summary>용어 설명</summary>

- **2단계 사상(Two-Level Mapping)**: 외부-개념 사상(외부 뷰와 통합 테이블 간 변환)과 개념-내부 사상(통합 테이블과 디스크 블록 간 변환).

</details>

```text
[ ANSI/SPARC 3단계 스키마 및 데이터 독립성 구조도 ]

 ┌────────────────────────────────────────────────────────────────────────┐
 │ [외부 스키마 1 (사용자 뷰)]          [외부 스키마 2 (관리자 뷰)]        │
 └───────────────────▲──────────────────────────────────▲─────────────────┘
                     │ (외부-개념 사상: 논리적 데이터 독립성 보장)
 ┌───────────────────┴──────────────────────────────────┴─────────────────┐
 │ [개념 스키마 (통합 엔티티, 속성, 관계, 무결성 제약조건)]                │
 └───────────────────────────────────▲────────────────────────────────────┘
                                     │ (개념-내부 사상: 물리적 데이터 독립성 보장)
 ┌───────────────────────────────────▼────────────────────────────────────┐
 │ [내부 스키마 (데이터 파일, 인덱스 B+Tree, 디스크 블록, 파티션)]         │
 └────────────────────────────────────────────────────────────────────────┘
```

선의 의미: 외부 스키마와 개념 스키마 사이, 개념 스키마와 내부 스키마 사이의 사상(Mapping)을 통해 변경의 전파를 차단하는 구조.

| 구성요소 | 책임 |
|:---|:---|
| 외부 스키마 (External) | 개별 사용자나 응용 프로그램 관점에서 **필요한 데이터 형태를 뷰(View)로 정의** |
| 외부-개념 사상 (Mapping) | 외부 뷰와 개념 스키마 간 매핑을 유지하여 **논리적 데이터 독립성 보증** |
| 개념 스키마 (Conceptual) | 데이터베이스 전체의 통합적 논리 구조인 **엔티티, 속성, 관계, 무결성 제약 정의** |
| 개념-내부 사상 (Mapping) | 개념 스키마와 물리 저장 구조 간 매핑을 유지하여 **물리적 데이터 독립성 보증** |

#### 한줄 요약

- 외부(뷰), 개념(통합 모델), 내부(물리 저장) 계층과 2단계 매핑이 결합하여 독립성을 달성

## Ⅳ. 흐름도

<details><summary>용어 설명</summary>

- **스키마 진화(Schema Evolution) 5단계 절차**: 변경 계층 식별 $\to$ 영향 매핑 수정 $\to$ 상위 인터페이스 보존 $\to$ 호환성 검증 $\to$ 무중단 전환.

</details>

```text
[ 스키마 변경 시 데이터 독립성 보장 파이프라인 ]

 ┌────────────────────────────────────────┐
 │ 1. 변경 계층 식별: 내부 vs 개념 스키마 │
 └───────────────────┬────────────────────┘
                     │
                     ▼
 ┌────────────────────────────────────────┐
 │ 2. 영향받는 사상(Mapping) 계층 갱신    │
 └───────────────────┬────────────────────┘
                     │
                     ▼
 ┌────────────────────────────────────────┐
 │ 3. 상위 인터페이스(View/계약) 보존     │
 └───────────────────┬────────────────────┘
                     │
                     ▼
 ┌────────────────────────────────────────┐
 │ 4. 쿼리 및 DML 트랜잭션 호환성 검증   │
 └───────────────────┬────────────────────┘
                     │
                     ▼
 ┌────────────────────────────────────────┐
 │ 5. 신규 스키마 및 매핑 무중단 전환    │
 └────────────────────────────────────────┘
```

### 동작 원리

1. 변경 계층 식별: 인덱스 추가(물리)인지 테이블 컬럼 추가(논리)인지 변경 계층을 특정.
2. 매핑 갱신: 물리 변경 시 개념-내부 사상을 수정하고, 논리 변경 시 외부-개념 사상을 수정.
3. 인터페이스 보존: 응용 프로그램이 사용하는 외부 뷰(View)의 시그니처와 데이터 타입을 불변으로 유지.
4. 호환성 검증: 기존 SQL 쿼리가 에러 없이 동일한 결과를 반환하는지 회귀 테스트를 수행.
5. 무중단 전환: 응용 프로그램 소스코드 배포 없이 DBMS 스키마 및 매핑 메타데이터만 즉시 활성화.

#### 한줄 요약

- 계층 식별 $\to$ 사상 갱신 $\to$ 인터페이스 보존 $\to$ 호환성 검증 $\to$ 무중단 전환의 5단계

## Ⅴ. 종류 및 비교

<details><summary>용어 설명</summary>

- **논리적 독립성 vs 물리적 독립성**: 비즈니스 모델 변경에 대응하는 논리적 독립성과 스토리지/인덱스 최적화에 대응하는 물리적 독립성.

</details>

| 구분 | 논리적 데이터 독립성 (Logical) | 물리적 데이터 독립성 (Physical) |
|:---|:---|:---|
| **적용 기준** | 비즈니스 요구 변화로 인한 테이블/컬럼 구조 변경 | 대용량 쿼리 튜닝을 위한 인덱스, 파티셔닝, 스토리지 변경 |
| **핵심 특징** | **개념 스키마가 변경되어도 외부 스키마(View)는 불변** | **내부 스키마가 변경되어도 개념/외부 스키마는 불변** |
| **한계** | 복잡한 컬럼 삭제 시 뷰 재설계 및 매핑 복잡도 증가 | DBMS 엔진의 내부 최적화 지원 범위에 종속 |

#### 한줄 요약

- 논리적 독립성은 비즈니스 모델 변경을 격리하고, 물리적 독립성은 성능 튜닝 변경을 격리

## Ⅵ. 실무 고려사항 및 대책

<details><summary>용어 설명</summary>

- **물리적 강결합 안티패턴(Physical Coupling Trap)**: 애플리케이션 SQL에 특정 인덱스 힌트나 물리적 파일 파티션 정보를 하드코딩하여 물리적 독립성을 파괴하는 현상.

</details>

| 문제 | 대책 | 효과 |
|:---|:---|:---|
| 앱이 DB 물리 테이블을 직접 참조하여 컬럼 변경 시 전면 수정 | **DB View 또는 ORM 엔티티 추상화 계층(Repository) 도입** | 논리적 데이터 독립성 극대화 |
| SQL 쿼리 내 물리적 인덱스 힌트(`/*+ INDEX */`) 하드코딩 남발 | **CBO 옵티마이저 통계 기반 자동 선택에 위임하고 힌트 최소화** | 물리적 데이터 독립성 보존 |
| 컬럼 삭제(Drop Column) 시 레거시 시스템 런타임 에러 발생 | **Expand-Contract 패턴(추가 $\to$ 마이그레이션 $\to$ 유예 $\to$ 삭제)** | 무중단 스키마 진화 달성 |

#### 한줄 요약

- 뷰/ORM 추상화 도입, 힌트 하드코딩 지양, Expand-Contract 패턴으로 데이터 독립성을 완성

## Ⅶ. 결론

<details><summary>용어 설명</summary>

- **현대적 데이터 독립성(Modern Data Independence)**: 마이크로서비스(MSA)와 클라우드 환경에서 API 게이트웨이 및 데이터 계층 추상화로 진화한 데이터 독립성 체계.

</details>

- **데이터 독립성**은 데이터베이스 공학의 가장 근본적인 아키텍처 철학이며, ANSI/SPARC 3단계 계층 모델과 현대 ORM/API 추상화를 결합하여 비즈니스 변화와 기술적 최적화에 유연한 시스템을 구축해야 함

#### 한줄 요약

- 2단계 사상 구조를 통해 논리적·물리적 독립성을 보장하고 소프트웨어의 유지보수성을 극대화
