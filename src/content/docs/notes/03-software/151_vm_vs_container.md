## Ⅰ. 개요

<details><summary>용어 설명</summary>

- **가상머신(VM) vs 컨테이너(Container)**: 하이퍼바이저를 통해 가상 하드웨어 위에 독립된 Guest OS를 통째로 실행하는 가상머신과 호스트 OS 커널을 공유하며 Namespaces/cgroups로 격리 실행하는 경량 컨테이너.
- **격리 강도 대 자원 효율성 상충(Isolation vs Resource Efficiency)**: 완벽한 커널 격리를 제공하지만 무거운 VM과 초경량 고밀도 배치를 제공하지만 커널을 공유하는 컨테이너 간의 아키텍처적 트레이드오프.

</details>

- 정의/개념: 하드웨어 가상화 기반의 **독립 Guest OS를 구동하는 가상머신(VM)과 호스트 커널을 공유하는 경량 격리 컨테이너** 활용 비교한 가상화 패러다임
- 배경/필요성: 시스템의 보안 격리 요구 수준과 고밀도 자원 효율성 및 **신속한 마이크로서비스 배포 속도 간의 상충 관계(Trade-off) 한계** 직면

#### 한줄 요약

- 보안과 커널 격리가 최우선이면 가상머신(VM), 초고속 기동과 고밀도 자원 효율이 최우선이면 컨테이너를 선택

## Ⅱ. 특징

<details><summary>용어 설명</summary>

- **하이퍼바이저(Hypervisor)**: 물리 하드웨어를 가상화하여 복수의 Guest OS를 독립적으로 실행시키는 중계 계층(Type 1: KVM/ESXi, Type 2: VirtualBox).
- **마이크로VM(MicroVM: Firecracker/Kata)**: 컨테이너의 빠른 시작 속도(수 밀리초)와 VM의 독립 커널 격리 보안을 결합한 차세대 하이브리드 기술.

</details>

- 하드웨어 가상화를 통한 **완벽한 Guest OS 및 커널 수준의 보안 격리(VM)**
- 호스트 커널 공유를 통한 **수 밀리초 단위 초고속 부팅 및 고밀도 집적(Container)**
- 워크로드의 신뢰 수준과 오토스케일링 주기에 따른 **명확한 선택 기준 제공**

#### 한줄 요약

- 커널 격리 강도와 인프라 운영 오버헤드 간의 균형을 통해 최적의 가상화 계층을 설계

## Ⅲ. 구조 및 구성요소

<details><summary>용어 설명</summary>

- **가상머신 vs 컨테이너 스택 구조**: 하이퍼바이저+Guest OS 계층(VM) 대 도커 엔진+호스트 커널 공유 계층(컨테이너).

</details>

```text
[ 가상머신(VM) vs 컨테이너(Container) 아키텍처 비교 ]

 1. [ 가상머신 (VM) 구조 ]
    ┌──────────────────────┐  ┌──────────────────────┐
    │ App A + Libraries    │  │ App B + Libraries    │
    ├──────────────────────┤  ├──────────────────────┤
    │ Guest OS (Linux)     │  │ Guest OS (Windows)   │ (수 GB 용량, 수 분 부팅)
    ├──────────────────────┴──┴──────────────────────┤
    │ 하이퍼바이저 (Hypervisor: KVM / ESXi)           │
    ├────────────────────────────────────────────────┤
    │ 물리 하드웨어 인프라 (CPU, RAM, Storage)       │
    └────────────────────────────────────────────────┘

 2. [ Docker 컨테이너 구조 ]
    ┌──────────────────────┐  ┌──────────────────────┐
    │ App A + Libraries    │  │ App B + Libraries    │ (수십 MB, 수 밀리초 기동)
    ├──────────────────────┴──┴──────────────────────┤
    │ 컨테이너 엔진 (containerd / runc)               │
    ├────────────────────────────────────────────────┤
    │ 호스트 OS 커널 (리눅스 cgroups / Namespaces)   │
    ├────────────────────────────────────────────────┤
    │ 물리 하드웨어 인프라 (CPU, RAM, Storage)       │
    └────────────────────────────────────────────────┘
```

선의 의미: Guest OS를 가상화하는 무거운 VM 구조와 호스트 커널을 공유하는 경량 컨테이너 구조의 차이.

| 구성요소 | 책임 |
|:---|:---|
| 가상머신 (VM) | 하이퍼바이저 기반으로 **독립된 Guest OS 커널을 실행하여 완벽한 하드웨어 격리 보장** |
| 컨테이너 (Container) | 호스트 커널을 공유하며 **Namespaces와 cgroups를 통해 격리된 프로세스 환경 제공** |
| 하이퍼바이저 (Hypervisor) | CPU, 메모리, I/O 하드웨어를 가상화하여 **다중 OS 간의 자원 충돌 방지** |
| 컨테이너 런타임 (runc) | OCI 표준 명세에 따라 **리눅스 시스템 콜을 직접 호출하여 격리 프로세스 즉시 생성** |

#### 한줄 요약

- VM(하드웨어 가상화), 컨테이너(OS 커널 격리), 하이퍼바이저, 컨테이너 런타임의 역할 비교

## Ⅳ. 흐름도

<details><summary>용어 설명</summary>

- **가상화 환경 실행 5단계 파이프라인**: 요구 분석 $\to$ 모델 선정 $\to$ 환경 프로비저닝 $\to$ OS 부팅/이미지 마운트 $\to$ 프로세스 실행.

</details>

```text
[ 워크로드 실행 환경 분기 및 기동 파이프라인 ]

 ┌────────────────────────────────────────┐
 │ 1. 격리 요구도 및 OS 호환성 요구 분석 │
 └───────────────────┬────────────────────┘
                     │
                     ▼
 ┌────────────────────────────────────────┐
 │ 2. 실행 모델 분기 (VM vs Container)    │
 ├───────────────────┬────────────────────┤
 │ VM 경로           │ Container 경로     │
 │ 3A. 가상 HW 할당  │ 3B. NS/cgroup 생성 │
 │ 4A. Guest OS 부팅 │ 4B. Image 마운트   │
 └───────────────────┴────────────────────┘
                     │
                     ▼
 ┌────────────────────────────────────────┐
 │ 5. 애플리케이션 비즈니스 프로세스 가동 │
 └────────────────────────────────────────┘
```

### 동작 원리

1. 요구 분석: 다중 고객 멀티테넌트 보안이 필수인지, MSA 초고속 확장이 필요한지 분석.
2. 모델 분기: 커널 분리가 필요하면 VM, 동일 커널 고밀도 배치가 목적이면 컨테이너로 분기.
3. 환경 생성: VM은 하이퍼바이저가 vCPU/vRAM을 생성하고, 컨테이너는 커널 네임스페이스와 cgroups를 할당.
4. 부팅/마운트: VM은 수 기가바이트 Guest OS 커널을 부팅(수 분)하고, 컨테이너는 불변 이미지 레이어를 즉시 마운트(수 밀리초).
5. 프로세스 가동: 애플리케이션 엔트리포인트를 실행하여 정상 서비스를 제공.

#### 한줄 요약

- 요구 분석 $\to$ 모델 분기 $\to$ 자원 할당 $\to$ 부팅/마운트 $\to$ 프로세스 가동의 5단계

## Ⅴ. 종류 및 비교

<details><summary>용어 설명</summary>

- **Pure VM vs Pure Container vs Secure Container**: 전통적 VM, 경량 컨테이너, 둘을 융합한 MicroVM(Firecracker/Kata).

</details>

| 구분 | 순수 가상머신 (Pure VM) | 순수 컨테이너 (Pure Container) | 보안 컨테이너 (Secure Container: MicroVM) |
|:---|:---|:---|:---|
| **적용 기준** | 금융 코어 뱅킹, 이종 OS(Windows), 강력한 격리 | 마이크로서비스(MSA), CI/CD, 대규모 웹 서버 | AWS Lambda 서버리스, 다중 테넌트 SaaS |
| **핵심 특징** | **독립 Guest OS 커널 탑재, 하드웨어 수준 격리** | **호스트 커널 공유, 수 밀리초 기동, 극단적 경량** | **초경량 하이퍼바이저(Firecracker) 기반 독립 커널** |
| **한계** | 수 기가바이트 디스크 낭비 및 느린 부팅 속도 | 동일 커널 공유로 인한 커널 취약점 전파 위험 | 기존 VM 대비 레거시 하드웨어 드라이버 호환성 제약 |

#### 한줄 요약

- 엄격한 격리는 VM, 초고속 배포는 컨테이너, 서버리스 멀티테넌트는 Secure Container(MicroVM)를 선택

## Ⅵ. 실무 고려사항 및 대책

<details><summary>용어 설명</summary>

- **멀티테넌트 SaaS 격리 전략**: 서로 다른 기업 고객의 코드를 단일 서버에서 실행할 때 컨테이너 대신 Kata Containers나 MicroVM을 적용하는 실무 수칙.

</details>

| 문제 | 대책 | 효과 |
|:---|:---|:---|
| 멀티테넌트 환경에서 컨테이너 탈출 해킹으로 타 테넌트 침해 | **테넌트 경계마다 VM 분리 또는 Kata Containers(MicroVM) 적용** | 커널 수준 완전 격리 달성 |
| 수천 개 컨테이너 급증 시 호스트 커널 리소스 고갈 | **Kubernetes Resource Request/Limit 및 cgroups 엄격 통제** | 단일 컨테이너의 호스트 자원 고갈 방지 |
| 리눅스 컨테이너 환경에서 윈도우 기반 레거시 앱 구동 불가 | **Hyper-V 기반 Windows 가상머신(VM) 전용 인스턴스 구축** | OS 아키텍처 호환성 완벽 보장 |

#### 한줄 요약

- 테넌트 커널 격리, K8s 자원 제한 설정, OS 호환성 분리를 통해 최적의 가상화 환경을 운영

## Ⅶ. 결론

<details><summary>용어 설명</summary>

- **하이브리드 가상화 인프라(Hybrid Virtualization)**: 베어메탈 위에 VM을 띄우고 그 위에서 K8s 컨테이너를 구동하는 현대 클라우드 표준 인프라.

</details>

- **가상머신과 컨테이너** 기반 상호 대립하는 기술이 아닌 현대 인프라의 상호 보완재이며, 보안 신뢰 경계는 VM으로 보호하고 그 내부에서 컨테이너의 민첩성과 고밀도 집적을 결합하여 최적의 클라우드 플랫폼을 완성해야 함

#### 한줄 요약

- 커널 격리의 가상머신과 경량 배포의 컨테이너를 융합하여 안전하고 확장성 높은 인프라를 완성
