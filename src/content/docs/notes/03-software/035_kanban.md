## Ⅰ. 개요

<details><summary>용어 설명</summary>

- **칸반 시스템(Kanban System)**: 도요타 공장에서 쓰던 JIT(적시생산) 방식을 가져와서, 포스트잇(카드)을 화이트보드에 붙여놓고 '할 일'이 쌓이는 걸 시각적으로 틀어막는 워크플로우 통제 룰이다.
- **진행 중인 작업(WIP, Work In Progress)**: 일을 시작하긴 했는데 아직 끝내진 못하고 '개발 중', '테스트 중' 칸에 널브러져 있는 골칫덩어리 작업들의 개수이다.
- **당김 시스템(Pull System)**: 위에서 일을 강제로 쑤셔 넣는(Push) 게 아니라, 내 칸에 빈자리가 생길 때만 "다음 일 가져올게!" 하고 당겨오는(Pull) 병목 방지 메커니즘이다.

</details>

- 정의: 화이트보드에 작업을 시각화하고, **WIP Limit(작업 개수 제한)** 을 걸어 일을 당겨오게(Pull) 만들어서 속도를 극한으로 뽑는 **칸반 시스템**
- 배경: 일은 끝내지도 못하면서 계속 새로운 일만 벌리면(무제한 착수), **대기열이 쌓이고 컨텍스트 스위칭 때문에 다 같이 망하기** 때문

#### 한줄 요약

- 일 좀 그만 벌리고(WIP Limit), 하나 끝내면 다음 거 가져오자(Pull)는 시각적 워크플로우 통제법이다.

## Ⅱ. 특징

<details><summary>용어 설명</summary>

- **리틀의 법칙(Little's Law)**: "음식점에 손님(WIP)이 꽉 차 있으면 밥 먹고 나오는 시간(Lead Time)이 무조건 길어진다"는 절대 불변의 수학적 진리이다. ($\text{Lead Time} = \frac{\text{WIP}}{\text{Throughput}}$).
- **누적 흐름도(CFD, Cumulative Flow Diagram)**: '할 일', '진행 중', '완료' 카드 개수가 시간에 따라 어떻게 쌓이는지 색칠공부 차트로 그려서, "아, 테스트 단계가 꽉 막혔네!" 하고 병목을 찾아내는 지도이다.

</details>

![리틀의 법칙에 따른 WIP와 평균 리드타임 관계](/study/diagrams/little-law-wip-lead-time.svg)

> 처리율을 하루 2건으로 고정한 파란 선은 WIP가 10건이면 평균 리드타임이 5일이 되는 리틀의 법칙 예시이며, 안정적인 유입•처리율을 가정한다.

- **WIP Limit**를 빡세게 걸어서 리틀의 법칙에 따라 리드타임을 강제로 줄여버림.
- 스크럼처럼 2주 단위(Sprint)로 끊지 않고, 물 흐르듯 끊임없이 일을 쳐내는 **연속적 가치 흐름(Continuous Flow)** 을 지향함.
- **CFD(누적 흐름도)** 랑 **리드타임(Lead Time)** 을 보면서 어디가 막혔는지 눈에 불을 켜고 감시함.

#### 한줄 요약

- 스프린트 없이 쭉 가되, 한 번에 벌리는 일(WIP) 수를 빡세게 제한해서 리드타임을 줄인다.

## Ⅲ. 구조 및 구성요소

<details><summary>용어 설명</summary>

- **칸반 보드(Kanban Board)**: To Do, In Progress, Done으로 칸을 나누고, 그 위에 티켓(카드)을 옮기면서 현재 팀이 얼마나 구르고 있는지 한눈에 보여주는 현황판이다.

</details>

```text
[ 칸반 보드 WIP Limit 십자포화 아키텍처 ]

 [ 백로그 ]     [ 개발 (WIP: 2) ]     [ QA (WIP: 1) ]     [ 완료 ]
(대기열 무한)      (카드 2장 꽉 참)      (카드 0장 비어있음)
     │                   │                     │
[ 카드 A ] ──(Pull)──▶ [ 카드 A ]                  │
[ 카드 B ]             [ 카드 B ] ──(당겨감)──▶ [ 카드 B ]
[ 카드 C ]                                     (QA로 이동)
```

| 구성요소 | 책임 |
|:---|:---|
| **칸반 보드 (Board)** | 팀의 모든 똥줄 타는 상황(작업 상태)을 발가벗겨 보여주는 시각화 판때기 |
| **작업 카드 (Card)** | 누가, 무슨 일을, 언제부터 쥐고 안 놔주고 있는지(노화 시간) 적힌 포스트잇 |
| **흐름 정책 (Policy)** | "개발 칸에는 포스트잇 2개 이상 절대 못 붙여!" 라고 정해둔 **WIP Limit** 룰 |
| 흐름 지표 | 리드타임과 처리량(Throughput)을 재서 팀 일하는 속도를 팩트 폭행하는 수치 |

#### 한줄 요약

- 보드판에 카드를 붙이고, 칸마다 최대 허용치(WIP Limit)를 걸어서 병목을 막는다.

## Ⅳ. 흐름도

<details><summary>용어 설명</summary>

- **긴급 차선(Expedite Lane)**: "서버 터졌다 비켜라!" 할 때, WIP Limit 다 무시하고 하이패스처럼 1순위로 뚫고 지나가는 VIP 긴급 장애 처리 전용 라인이다.

</details>

```text
[ 칸반 Pull 시스템 십자포화 흐름 ]
┌──────────────────────────────┐
│ 1. 하위 단계 완료 (빈자리 발생)│
│ (QA 칸에 카드 하나 빠짐)     │
└──────────────┬───────────────┘
               ▼
┌──────────────────────────────┐
│ 2. 수용량 및 WIP 한도 확인   │
│ (QA WIP 한도가 남는지 체크)  │
└──────────────┬───────────────┘
               ▼ (당김 허용)
┌──────────────────────────────┐
│ 3. 상위 단계에서 카드 Pull   │
│ (개발 칸에서 QA로 멱살 잡고 끔)│
└──────────────┬───────────────┘
               ▼
┌──────────────────────────────┐
│ 4. 카드 작업 수행 및 이동    │
│ (QA 작업 끝내고 완료로 던짐) │
└──────────────┬───────────────┘
               ▼
┌──────────────────────────────┐
│ 5. 리드타임(Lead Time) 측정  │
│ (이 카드 며칠 걸렸나 팩트체크)│
└──────────────────────────────┘
```

### 동작 원리

1. 빈자리 발생: 내 다음 단계(하류)에서 일을 끝내서 칸에 빈자리가 남.
2. 수용량 확인: 빈자리가 생겼으니 **WIP Limit**에 여유가 생김을 확인함.
3. 카드 당김(Pull): 내 전 단계(상류)에서 끝난 카드를 멱살 잡고 끌고 옴.
4. 작업 수행: 가져온 카드를 죽어라 패서 완료 상태로 만듦.
5. 지표 갱신: 백로그에서 완료까지 총 며칠 걸렸는지 **Lead Time**을 기록함.

#### 한줄 요약

- 내 칸이 비었을 때(Pull), 이전 칸에서 카드를 당겨와 작업하고(WIP), 다 끝나면 리드타임을 잰다.

## Ⅴ. 종류 및 비교

<details><summary>용어 설명</summary>

- **리드타임 vs 사이클타임(Lead Time vs Cycle Time)**: 리드타임은 고객이 접수한 날부터 완성품 받을 때까지 총시간이고, 사이클타임은 개발자가 실제로 그 카드를 쥐고 코딩한 진짜 소요 시간이다.

</details>

| 비교 항목 | **Kanban** (칸반) | **Scrum** (스크럼) |
|:---|:---|:---|
| 일하는 주기 | **연속적 흐름** (스프린트 그딴 거 없음) | **타임박스** (2주 단위 스프린트) |
| 도중에 기획 엎기 | 빈자리(WIP) 나면 **언제든 새 카드 쑤셔 넣음** | 스프린트 도중엔 **절대 기획 못 바꿈** |
| 팀 쪼는 핵심 무기 | **WIP Limit** (한 번에 3개 이상 일 벌리지 마!) | **Timeboxing** (2주 안에 결과 내놔!) |
| 전투력 측정 지표 | **리드타임 (Lead Time), 사이클타임** | 스프린트 속도 (Velocity), 스토리 포인트 |

#### 한줄 요약

- 스크럼은 2주 시간제한으로 쪼고, 칸반은 작업 개수(WIP) 제한으로 쪼는 게 차이다.

## Ⅵ. 실무 고려사항 및 대책

<details><summary>용어 설명</summary>

- **작업 노화(Work Item Aging)**: 작업 카드가 보드에 붙은 채로 며칠째 완료로 안 넘어가고 '개발 중' 칸에서 먼지만 쌓여가며 썩어가는 현상이다.

</details>

| 문제 | 대책 | 효과 |
|:---|:---|:---|
| 상사가 계속 일을 밀어 넣어서(Push) 팀이 터짐 | 보드에 **WIP Limit 3** 써놓고 "못 받습니다" 시전 (**Pull**) | 병목 안 쌓이고, 하나라도 똑바로 끝냄 |
| 카드가 특정 칸에서 먼지 쌓이면서 썩음 (**작업 노화**) | 매일 미팅에서 썩은 카드 칠하고 다 같이 달라붙어 해결 | 병목 뚫고 카드 흐름(Flow) 정상화 |
| 죄다 **긴급 차선(Expedite Lane)** 에 넣어서 보드가 붕괴 | "긴급 차선은 무조건 1개만 허용" 룰을 강제함 | 새치기 막아서 일반 작업 굶어 죽는 것 방지 |

#### 한줄 요약

- WIP 한도로 막고, 썩어가는 카드(노화)는 다 같이 치우며, VIP 하이패스(긴급 차선)는 남용하지 마라.

## Ⅶ. 결론

<details><summary>용어 설명</summary>

- **칸반 도입 선택 기준(Kanban Adoption Criteria)**: 언제 터질지 모르는 유지보수 팀인지, 아니면 2주짜리 계획이 통하는 신규 팀인지 각 재서 스크럼과 칸반을 가르는 잣대이다.

</details>

- **칸반 도입 선택 기준** 원칙에 따라, 서버 터지면 당장 고쳐야 하는 **운영/유지보수(SM) 조직**은 **Kanban**, 2주 단위 기획이 먹히는 신규 서비스는 **Scrum** 채택 기조 확립함

#### 한줄 요약

- 매일매일 무슨 일이 터질지 모르는 유지보수(장애 대응) 팀이라면 칸반이 찰떡이다.
