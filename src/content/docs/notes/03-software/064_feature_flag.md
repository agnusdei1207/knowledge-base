## Ⅰ. 개요

<details><summary>용어 설명</summary>

- **배포-릴리스 분리(Decoupling Deploy from Release)**: 코드가 서버에 반영(Deploy)되는 시점과 사용자에게 기능이 노출(Release)되는 시점을 독립적으로 분리하는 통제 방식.
- **출시 지연 및 롤백 불가(Schedule Delay & Rollback Limit)**: 마케팅 일정에 맞춰 배포를 대기해야 하고 신기능 오류 시 전체 바이너리를 재배포해야 하는 운영 한계.

</details>

- 정의/개념: 소스코드 재배포 없이 런타임에 특정 기능의 활성화 여부(ON/OFF)와 대상 사용자군을 동적 제어하는 **배포와 릴리스 분리(Decoupling)** 기법
- 배경/필요성: 배포와 릴리스의 결합으로 인한 **신규 기능 출시 일정 지연 및 프로덕션 결함 발생 시 긴급 롤백 불가 위험** 직면

#### 한줄 요약

- 재배포 없이 런타임에 기능 ON/OFF·사용자 타겟팅을 동적으로 제어하여 배포와 릴리스를 독립적으로 수행

## Ⅱ. 특징

<details><summary>용어 설명</summary>

- **타겟팅 및 세분화(Targeting & Segmentation)**: 사용자 속성(지역·등급·그룹)에 따라 특정 사용자군에만 기능을 선택적으로 노출하는 정밀 제어 기능.
- **트렁크 기반 개발(Trunk-Based Development)**: 미완성 기능을 플래그로 비활성화한 채로 메인 브랜치에 통합하여 장기 Feature 브랜치 없이 지속적 통합을 가능하게 하는 개발 방식.

</details>

- **배포와 릴리스의 완전 분리** 기반 출시 시점과 대상 사용자를 독립적으로 제어
- 런타임 즉각 제어 기반 **킬 스위치(재배포 없는 기능 비활성화)** 및 **정밀 타겟팅**
- **트렁크 기반 개발** 촉진 및 **A/B 테스트** 기반 점진 검증 지원

#### 한줄 요약

- 배포-릴리스 분리·즉각 킬 스위치·타겟팅으로 안전하고 유연한 기능 제어를 실현

## Ⅲ. 구조 및 구성요소

<details><summary>용어 설명</summary>

- **LaunchDarkly / Unleash**: 피처 플래그를 중앙에서 관리하고 애플리케이션에 실시간으로 배포하는 플래그 관리 플랫폼(SaaS/오픈소스).

</details>

```text
[ 피처 플래그 구조 ]
피처 플래그 콘솔 (LaunchDarkly/Unleash)
   └─ 플래그 ON/OFF 설정·타겟팅 룰·변경 감사 로그 관리
   │ (런타임 실시간 룰 배포)
애플리케이션 서버 내부 플래그 SDK
   └─ 사용자 컨텍스트 기반 플래그 평가
      │
     True(신기능) / False(기존 기능)
```

선의 의미: 콘솔에서 SDK로의 화살표는 실시간 룰셋 배포 관계, SDK에서 분기의 화살표는 평가 결과에 따른 코드 경로 분기 관계

| 구성요소 | 책임 |
|:---|:---|
| **플래그 콘솔** | 기능 ON/OFF·타겟팅 룰 설정·감사 로그 관리 |
| **평가 SDK** | 사용자 컨텍스트 기반 플래그 값 평가·반환 |
| **기능 분기(If-Else)** | 평가 결과에 따라 신기능·기존 기능 경로 분기 |
| **감사 로그** | 플래그 변경 이력 추적 및 장애 원인 분석 |

#### 한줄 요약

- 콘솔에서 룰을 배포하면 SDK가 사용자 컨텍스트로 평가하여 코드 분기를 결정

## Ⅳ. 흐름도

<details><summary>용어 설명</summary>

- **플래그 평가(Flag Evaluation)**: SDK가 사용자 ID·지역·등급 등의 컨텍스트와 플래그 타겟팅 룰을 비교하여 True/False를 반환하는 과정.

</details>

```text
1. HTTP 요청 수신 → 사용자 컨텍스트 추출
   └─ (사용자 ID·지역·등급 등 속성 수집)
   │
   ▼
2. 플래그 SDK 호출 → 타겟팅 룰 평가
   └─ 콘솔 룰("VIP 등급이면 True")과 사용자 속성 비교
   │
   ▼
3. 코드 분기 실행
   ├─ True: 신기능 코드 경로 실행
   └─ False: 기존 기능 코드 경로 실행
   │
   ▼
4. 평가 결과 통계 기록 → 응답 반환
```

**동작 원리** 1. **컨텍스트 추출**: 요청에서 사용자 속성(ID·지역·등급)을 추출
2. **플래그 평가**: SDK가 콘솔 룰셋과 사용자 속성을 비교하여 True/False 반환
3. **안전 기본값**: 콘솔 접속 실패 시 로컬 캐시 또는 기본값(False)을 반환하여 앱 장애 방지
4. **분기 실행**: 평가 결과에 따라 신기능 또는 기존 기능 코드 경로를 실행

#### 한줄 요약

- 컨텍스트 추출→룰 평가→코드 분기→통계 기록의 흐름으로 런타임 기능 제어 실현

## Ⅴ. 종류 및 비교

<details><summary>용어 설명</summary>

- **카나리 배포 vs 피처 플래그**: 카나리는 인프라 라우터 수준에서 무작위 트래픽 비율로 버전을 분리하고, 피처 플래그는 코드 수준에서 사용자 속성 기반 정밀 타겟팅으로 기능을 분리.

</details>

| 구분 | 카나리 배포 | 피처 플래그 |
|:---|:---|:---|
| 제어 계층 | L7 라우터 (인프라) | **애플리케이션 코드 (if문)** |
| 타겟팅 정밀도 | 무작위 트래픽 비율 | **사용자 속성 기반 정밀 타겟팅** |
| 제어 주체 | 인프라 엔지니어 | **개발자·PM·마케터 누구나** |
| 롤백 방법 | 라우팅 비율 변경 | **콘솔 OFF(재배포 불필요)** |

#### 한줄 요약

- 카나리는 인프라 수준 트래픽 분리, 피처 플래그는 코드 수준 사용자 타겟팅 기능 분리

## Ⅵ. 실무 고려사항 및 대책

<details><summary>용어 설명</summary>

- **플래그 오염(Flag Pollution)**: 릴리스 완료 후 코드에서 제거하지 않은 플래그 분기가 누적되어 코드 복잡도와 테스트 경우의 수가 기하급수적으로 증가하는 기술 부채.

</details>

| 문제 | 대책 | 효과 |
|:---|:---|:---|
| 사용 완료 플래그를 제거하지 않아 코드 복잡도 급증(**플래그 오염**) | **플래그 만료일(TTL)** 설정 및 릴리스 완료 후 즉시 코드 제거 | 불필요한 분기 제거로 코드 품질 유지 |
| 플래그 콘솔 장애 시 앱 전체 기능 오류 | **로컬 캐시** 적용 및 장애 시 **기본값(Fallback) 반환** | 콘솔 장애 시에도 앱 정상 동작 보장 |
| 복수 플래그 조합으로 테스트 경우의 수 폭발 | **플래그 간 의존성 결합 금지** 원칙 적용 | 테스트 복잡도 관리 |

#### 한줄 요약

- 완료된 플래그는 TTL 기반 즉시 제거로, 콘솔 장애는 기본값으로, 플래그 의존성은 분리 원칙으로 관리

## Ⅶ. 결론

<details><summary>용어 설명</summary>

- **피처 플래그 관리 기준**: 플래그 생명주기 관리(생성·만료·제거)와 OpenFeature 표준 준수 여부를 기준으로 피처 플래그의 지속 가능한 운영을 판단하는 기준.

</details>

- 임시 릴리스용 플래그는 **만료 후 즉시 코드 제거**, 장애 대응용 킬 스위치는 **영구 유지** 기조로 생명주기 관리

#### 한줄 요약

- 배포-릴리스 분리와 정밀 타겟팅으로 안전한 기능 제어를 실현하고 플래그 생명주기 관리로 기술 부채를 방지
