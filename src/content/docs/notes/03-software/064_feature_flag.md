## Ⅰ. 개요

<details><summary>용어 설명</summary>

- **피처 플래그(Feature Flag / Toggle)**: 소스 코드를 다시 빌드하거나 배포하지 않고, 런타임에 조건부로 특정 기능을 켜거나 끄는(ON/OFF) 소프트웨어 공학 기법.
- **배포(Deploy)와 릴리즈(Release)의 분리**: 코드를 서버에 배포하는 물리적 행위(Deploy)와 사용자에게 기능을 노출하는 비즈니스 행위(Release)를 독립 분리.

</details>

- 정의/개념: 소스코드 재배포 없이 런타임에 특정 기능의 활성화(ON/OFF)와 대상 사용자를 동적 제어하는 **배포와 릴리즈 분리(Decoupling)** 기법
- 배경/필요성: 코드 배포와 기능 릴리즈의 강한 결합으로 인한 **릴리즈 지연, 긴급 롤백 시의 재배포 병목 및 대규모 병합 충돌(Merge Hell) 한계**

#### 한줄 요약
- 재배포 없이 런타임에 기능 ON/OFF와 사용자 타겟팅을 동적 제어하여 배포와 릴리즈를 분리한다.

## Ⅱ. 특징

<details><summary>용어 설명</summary>

- **Kill Switch(킬 스위치)**: 장애 기능을 런타임에 비활성화해 영향을 제한하는 비상 제어.
- **Trunk-Based Development 연계**: 미완성된 기능도 Feature Flag(OFF)로 감싼 채 main 브랜치에 수시로 병합하여 Merge Hell을 방지.

</details>

- **배포와 릴리즈 분리** 기반의 비즈니스 주도 출시 제어
- 장애 발생 시 재배포 없이 즉각 비활성화하는 **킬 스위치(Kill Switch)** 기능
- 사용자 속성(VIP, 지역, 베타 테스터)에 따른 **정밀 타겟팅 및 A/B 테스트** 지원

#### 한줄 요약
- 배포와 릴리즈를 분리하면 공개 시점의 자유를 얻는 대신 조건 분기가 코드에 남으므로, 그 유연성은 관리해야 할 부채로 지불된다.

## Ⅲ. 구조 및 구성요소

<details><summary>용어 설명</summary>

- **Unleash / LaunchDarkly**: 중앙에서 플래그 규칙을 관리하고 애플리케이션 SDK로 실시간 푸시/폴링해주는 피처 관리 플랫폼.

</details>

```text
[피처 플래그 런타임 체계]
  │
  ├─ [중앙 플래그 콘솔] (LaunchDarkly/Unleash)
  │     ├─ [상태 설정] (ON/OFF·카나리 비율 제어)
  │     └─ [타겟팅 룰셋] (사용자 등급·조건 정의)
  │
  ├─ [애플리케이션 SDK]
  │     ├─ [로컬 룰셋 캐시] (초저지연 평가·장애 방어)
  │     └─ [평가 엔진] (사용자 컨텍스트 조건 분기)
  │
  └─ [분석 플랫폼] (전환율 측정 및 감사 로그 추적)
```
- 선의 의미: 계층 구조 및 상하위 포함 관계를 나타낸다.

| 구성요소 | 책임 |
|:---|:---|
| 중앙 플래그 콘솔 | 플래그 상태와 **타겟팅 규칙** 관리 |
| 플래그 평가 SDK | 규칙 캐시와 **사용자 컨텍스트 평가** |
| 코드 분기 로직 | 평가 결과에 따른 **조건부 실행** |
| 감사 로그 및 메트릭 | 플래그 변경 이력 추적 및 기능 노출별 성능/전환율 계측 |

#### 한줄 요약
- 플래그 값은 중앙 콘솔에서 관리되지만 판정은 로컬 캐시에서 이뤄지므로, 평가 지연을 없애는 대신 설정 반영에 시차가 생긴다.

## Ⅳ. 흐름도

<details><summary>용어 설명</summary>

- **Percentage Rollout(점진 롤아웃)**: 사용자 ID 해시를 기반으로 10% $\to$ 30% $\to$ 100% 비율로 점진적으로 기능을 활성화하는 방식.

</details>

```text
사용자 HTTP 요청 수신 (사용자 ID, 디바이스, 등급 컨텍스트 추출)
        │
   애플리케이션 내부 플래그 SDK 호출 (`flagService.isEnabled('dark_mode', context)`)
        │
   로컬 메모리 캐시의 타겟팅 룰셋과 사용자 컨텍스트 대조 평가
        │
   플래그 평가 결과는 무엇인가?
   ┌────┴───────────────────────────┐
[True: 기능 활성화]               [False: 비활성화 또는 콘솔 통신 장애]
신규 다크모드 화면 렌더링           안전한 기본 화이트모드 화면 렌더링
        │                                │
   결과 응답 반환 및 Datadog으로 A/B 테스트 클릭 이벤트 전송
```

#### 한줄 요약
- 판정이 로컬 캐시에서 이뤄지므로 평가는 즉시 끝나지만, 중앙에서 끈 플래그가 실제로 꺼지기까지는 캐시 갱신 주기만큼 시차가 남는다.

## Ⅴ. 종류 및 비교

<details><summary>용어 설명</summary>

- **Canary 배포 vs Feature Flag**: 인프라 레벨의 네트워크 트래픽 분할(Canary)과 코드 레벨의 사용자 속성 조건 분기(Feature Flag).

</details>

| 비교 항목 | 카나리 배포 (Canary Deployment) | 피처 플래그 (Feature Flag) |
|:---|:---|:---|
| 제어 계층 | **인프라 L7 라우터 (Ingress, Service Mesh)** | **애플리케이션 소스 코드 (if-else 조건문)** |
| 제어 주체 | DevOps 엔지니어, 인프라 운영자 | **소프트웨어 개발자, PO, 프로덕트 매니저** |
| 타겟팅 정밀도 | IP, 무작위 트래픽 비율 기반 분할 | **사용자 ID, 회원 등급, 지역 등 정밀 타겟팅** |
| 롤백 방식 | 라우터 트래픽 비율 원복 | **콘솔에서 플래그 비활성화** |

#### 한줄 요약
- 카나리는 인프라 수준 트래픽 분할, 피처 플래그는 애플리케이션 수준의 비즈니스 타겟팅이다.

## Ⅵ. 실무 고려사항 및 대책

<details><summary>용어 설명</summary>

- **Flag Debt(플래그 부채)**: 릴리즈가 100% 완료된 후에도 코드베이스에서 제거되지 않은 죽은 플래그(Dead Flag)가 쌓여 복잡도를 높이는 기술 부채.

</details>

| 문제 | 대책 | 효과 |
|:---|:---|:---|
| 만료 플래그 누적에 따른 **Flag Debt** | 플래그별 **TTL·소유자**와 제거 일정 설정 | 코드 복잡도와 테스트 조합 감소 |
| 플래그 서버 장애에 따른 평가 실패 | **로컬 규칙 캐시·기본값** 설정 | 네트워크 단절 시 기능 저하 범위 제한 |
| 플래그 결합에 따른 예외 조합 증가 | **의존성 제한**과 조합 테스트 적용 | 조합 폭발 위험 관리 |
| 변경 권한 오남용에 따른 운영 사고 | **RBAC·변경 승인** 적용 | 비인가 변경 위험 감소 |

#### 한줄 요약
- 피처 플래그는 배포와 릴리즈를 분리하는 대신 조건 분기를 코드에 부채로 남기므로, TTL로 수거 시점을 강제하고 중첩을 금지해 분리 이득이 복잡도에 잠식되지 않게 한다.

## Ⅶ. 결론

- 현대 지속적 딜리버리(CD) 및 트렁크 기반 개발(Trunk-based Development)의 **핵심 런타임 기능 제어 아키텍처 패턴**으로 확립되었으며, 실무 운영 시에는 **비즈니스 주도의 A/B 테스트 및 점진적 롤아웃 수행, 플래그 서버 장애에 대비한 로컬 캐시 폴백, 출시 완료 후 방치되는 플래그 부채(Flag Debt)를 방지하기 위한 수명주기(TTL) 관리 및 정기 코드 정제 스프린트**를 결합하여 시스템 복잡도와 출시 유연성의 균형을 달성

#### 한줄 요약
- 피처 플래그는 코드 배포와 비즈니스 릴리즈를 분리하여 프로덕션 환경에서의 빠른 검증과 즉각적인 롤백을 가능하게 하는 핵심 딜리버리 패턴이다.
