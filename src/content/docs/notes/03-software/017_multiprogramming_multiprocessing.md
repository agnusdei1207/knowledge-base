## Ⅰ. 개요

<details><summary>용어 설명</summary>

- **다중프로그래밍(Multiprogramming)**: CPU(요리사)는 1명인데, 한 요리가 오븐(I/O)에 들어간 틈을 타서 잽싸게 다른 요리를 썰며(Context Switching) CPU를 1초도 안 쉬게 쥐어짜는 기법이다.
- **다중처리(Multiprocessing)**: 진짜 요리사(물리 CPU 코어)를 여러 명 고용해서, 동시에 여러 개의 요리를 물리적으로 병렬(Parallel) 진행하는 찐 멀티태스킹 기법이다.

</details>

- 정의: 단일 코어 하나로 쉴 틈 없이 교대 연산(Interleaving)을 돌리는 **다중프로그래밍**과 복수 코어로 진짜 동시 연산을 때리는 **다중처리**
- 배경: CPU 하나만 놔두면 놈이 하드디스크(I/O) 읽는 동안 CPU가 멍 때리면서 **연산 자원이 낭비**되기 때문

#### 한줄 요약

- CPU 하나로 쉴 새 없이 돌려 막기 하면 다중프로그래밍, CPU 여러 개로 진짜 동시에 패면 다중처리다.

## Ⅱ. 특징

<details><summary>용어 설명</summary>

- **교대 실행(Interleaving)**: CPU가 눈에 안 보일 정도로 찰나의 시간 동안 이놈 저놈 번갈아 가며 패서, 사용자 눈에는 다 같이 쳐맞는 것처럼 보이게 하는 환술이다.
- **병렬 실행(Parallel Execution)**: 여러 CPU가 각자 놈을 잡고 물리적으로 진짜 동시에 패는 팩트 폭행이다.

</details>

- 단일 CPU에서 I/O 대기 시간을 훔쳐서 교대로 때우는 **다중프로그래밍 (Interleaving)**.
- 여러 CPU/코어를 갈아 넣어서 진짜 동시에 패버리는 **다중처리 (Parallel Execution)**.
- 다중처리는 빠르지만, 지들끼리 데이터 안 맞물리게 락 걸고 캐시 맞추느라 오버헤드가 터질 수 있음.

#### 한줄 요약

- 다중프로그래밍은 시간을 쪼개는 환술이고, 다중처리는 물리적 코어를 늘리는 팩트 폭행이다.

## Ⅲ. 구조 및 구성요소

<details><summary>용어 설명</summary>

- **대칭형 다중처리(Symmetric Multiprocessing, SMP)**: 모든 CPU 코어가 평등하게 하나의 메인 메모리와 버스를 공유하며 으쌰으쌰 일하는 뼈대이다.
- **암달의 법칙(Amdahl's Law)**: 코어를 100개 때려 박아도, 순서대로 해야만 하는 일(직렬 구간)이 있으면 속도 향상에 뼈아픈 한계가 온다는 팩트 폭력 법칙이다.

</details>

```text
[ 다중 연산 처리 십자포화 아키텍처 ]
           [ 작업 집합 ]
                │
           [ 준비 큐 ]
        (CPU 밥 달라고 대기)
                │
           [ 스케줄러 ]
     (니네는 코어1, 니네는 코어2)
                │
        ┌───────┴───────┐
        ▼               ▼
    [ 코어 1 ]      [ 코어 2 ]
 (교대 또는 진짜 병렬로 미친 듯이 연산)
        │               │
        └───────┬───────┘
                ▼
          [ 공유 메모리 ]
     (둘이 싸우지 않게 데이터 공유)
```

| 구성요소 | 책임 |
|:---|:---|
| 작업 집합 | 메모리에 적재돼서 당장이라도 달릴 준비가 끝난 프로세스 무리 |
| 준비 큐 | CPU 할당받으려고 줄 서서 덜덜 떨며 대기하는 벤치 |
| 스케줄러 | 큐에 있는 놈들을 멱살 잡고 **코어**에 꽂아주는 지휘관 |
| 코어 1•2 | 혼자서 번갈아 패거나(다중프로그래밍), 둘이서 동시에 패는(다중처리) 물리 엔진 |
| 공유 메모리 | 코어끼리 데이터 안 맞아서 싸우지 않게(캐시 일관성) 정보를 모아두는 칠판 |

#### 한줄 요약

- 스케줄러가 코어에 일을 꽂아주고, 코어들은 공유 메모리를 바라보며 연산 폭격을 날린다.

## Ⅳ. 흐름도

<details><summary>용어 설명</summary>

- **문맥 전환 오버헤드(Context Switch Overhead)**: 요리사가 A 요리 하다가 B 요리로 바꿀 때, 도마 닦고 레시피 다시 꺼내는 데 버려지는 쌩짜 시간 낭비이다.

</details>

```text
[ 다중프로그래밍 vs 다중처리 흐름 ]

[ 다중프로그래밍 (1코어 환술) ]
┌─────────────────────────────┐
│ 1. 작업 A 실행 중 I/O 대기  │
└──────────────┬──────────────┘
               ▼ (찰나의 문맥 전환)
┌─────────────────────────────┐
│ 2. 작업 B 교대 실행         │
│ (CPU 노는 시간 0%로 쥐어짬) │
└─────────────────────────────┘

[ 다중처리 (멀티코어 팩트 폭행) ]
┌─────────────────────────────┐
│ 3. 병렬 작업 집합 대기      │
└──────────────┬──────────────┘
               ▼
┌──────────────┴──────────────┐
▼                             ▼
[ 4. 코어1: 작업 A 팸 ]  [ 4. 코어2: 작업 B 팸 ]
(물리적 동시 실행)        (물리적 동시 실행)
```

### 동작 원리

1. 대기 발생: 작업 A가 하드디스크 읽느라 멍 때림.
2. 교대 실행(다중프로그래밍): CPU가 그 꼴 못 보고 잽싸게 작업 B로 갈아타서 쉼 없이 일함.
3. 병렬 준비: 독립적으로 쪼갤 수 있는 일거리들을 모음.
4. 코어별 병렬(다중처리): 코어1은 A, 코어2는 B를 붙잡고 진짜 물리적으로 동시에 두들겨 팸.

#### 한줄 요약

- I/O 대기 때 딴 짓 하면 다중프로그래밍, 코어 두 개로 동시에 갈구면 다중처리다.

## Ⅴ. 종류 및 비교

<details><summary>용어 설명</summary>

- **멀티태스킹 vs 멀티스레딩(Multitasking vs Multithreading)**: 멀티태스킹은 OS가 여러 프로그램을 찰나로 쪼개서 동시에 도는 척하는 거고, 멀티스레딩은 프로그램 하나 안에서 일꾼(스레드)을 여러 명 두는 것이다.

</details>

| 비교 항목 | 핵심 실행 특징 | 하드웨어 자원 관계 |
|:---|:---|:---|
| **Multiprogramming** (다중프로그래밍) | 메모리에 여러 놈 올리고 I/O 대기 때 교대 실행 | 단일 CPU 유휴시간(노는 꼴) 소멸시킴 |
| **Multitasking** (멀티태스킹) | 타이머(Time Slice) 박아놓고 미친 속도로 번갈아 때림 | 사용자 입장에선 "오, 동시에 도네" 체감 됨 |
| **Multiprocessing** (다중처리) | 물리적인 여러 CPU 코어에서 진정한 **병렬 동시 실행** | 찐 멀티 코어 칩셋이 물리적으로 필요함 |
| **Multithreading** (멀티스레딩) | 하나의 프로세스 안에서 일꾼 여러 명이 메모리 공유하며 일함 | 덩어리(프로세스) 안의 내부 자원을 알뜰히 나눠 씀 |

#### 한줄 요약

- 시간을 쪼개면 멀티태스킹, 칩을 쪼개면 멀티코어(다중처리), 일을 쪼개면 멀티스레딩이다.

## Ⅵ. 실무 고려사항 및 대책

<details><summary>용어 설명</summary>

- **거짓 공유(False Sharing)**: 두 코어가 전혀 다른 변수를 고치는데, 하필 그 변수들이 같은 64바이트 캐시 라인(묶음)에 들어있어서, 서로 "내 거 건들지마!"라며 무효화 트래픽을 뿜어대 버스가 박살 나는 기막힌 병목 현상이다.

</details>

| 문제 | 대책 | 효과 |
|:---|:---|:---|
| 다중프로그래밍 한답시고 메모리에 너무 많이 쑤셔 넣어서 **스레싱** 터짐 | **수용 제어(Admission Control)** 로 적당히 컷 치고 쫓아냄 | 램 터지는 걸 막아서 시스템 다운을 철통 방어 |
| 코어끼리 캐시 무효화 폭탄을 던지는 **거짓 공유(False Sharing)** 터짐 | 변수 사이에 깡통 데이터(Padding)를 박는 **`@Contended`** 적용 | 변수들을 물리적으로 찢어발겨 캐시 버스 병목 완전 제거 |
| 코어를 100개 샀는데 **암달의 법칙** 때문에 성능이 안 오름 | 순서대로 해야 하는 **직렬 구간(Serial Section)** 을 영혼까지 튜닝함 | 비싼 코어 사놓고 놀리는 일 없이 가속비 끝판왕 달성 |

#### 한줄 요약

- 램 터지는 건 수용 제어로 막고, 캐시 충돌은 변수를 찢어 발겨서 막고, 코어 노는 건 직렬 구간을 튜닝해서 막는다.

## Ⅶ. 결론

<details><summary>용어 설명</summary>

- **실행 아키텍처 선택 기준(Execution Architecture Criteria)**: 코어가 몇 개인지, I/O 대기가 많은지, 락 오버헤드가 큰지 각을 재서 멀티 기법을 고르는 잣대이다.

</details>

- **실행 아키텍처 선택 기준** 원칙에 따라, I/O 잦은 곳엔 **다중프로그래밍**으로 때우고, 연산 빡센 병렬 구간은 무조건 **다중처리** 채택 기조 확립함

#### 한줄 요약

- I/O 대기가 많으면 다중프로그래밍, 빡센 계산이 많으면 다중처리를 박아라.
