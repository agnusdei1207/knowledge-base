## Ⅰ. 개요

<details><summary>용어 설명</summary>

- **CAP 정리 3대 요소**: 일관성(Consistency: 모든 노드가 최신 데이터 조회), 가용성(Availability: 모든 요청에 정상 응답), 분할내성(Partition Tolerance: 네트워크 단절 시에도 시스템 동작 지속).
- **분할 시 일관성-가용성 상충(Partition Trade-off)**: 네트워크 단절(P) 발생 시 최신 데이터를 보장하기 위해 응답을 차단(CP)하거나, 오래된 데이터를 허용하고 무조건 응답(AP)해야 하는 근본적 한계.

</details>

- 정의/개념: 분산 데이터 시스템에서 네트워크 분할 발생 시 **일관성(Consistency), 가용성(Availability), 분할내성(Partition Tolerance)** 중 2가지만 선택 가능하다는 정리
- 배경/필요성: 분산 노드 간 네트워크 단절(Partition) 상황에서 **최신 데이터 동기화와 무중단 성공 응답의 동시 보장 불가 한계** 직면

#### 한줄 요약

- 분할 내성(P)이 필수적인 분산 환경에서 일관성 중심(CP)과 가용성 중심(AP) 간의 불가피한 트레이드오프를 규정

## Ⅱ. 특징

<details><summary>용어 설명</summary>

- **P의 필수성(Partition Tolerance is Mandatory)**: 분산 네트워크에서 통신 단절은 물리적으로 피할 수 없는 장애이므로 실질적 선택은 CP 대 AP의 2지선다로 귀결.
- **PACELC 정리**: 네트워크 분할(P) 시 A와 C의 선택, 정상(Else) 시 지연시간(Latency)과 일관성(Consistency) 간의 절충을 규정한 확장 이론.

</details>

- 분산 네트워크 단절(P)을 전제로 한 **일관성(CP) 대 가용성(AP)의 양자택일**
- 노드 정족수(Quorum) 기반의 **과반수 노드 합의 메커니즘 연계**
- 정상 상태에서의 지연시간(L)과 일관성(C)의 절충을 설명하는 **PACELC 확장 이론과 조화**

#### 한줄 요약

- 네트워크 분할 시 무결성을 위해 응답을 차단(CP)할 것인지, 서비스 지속을 위해 가용성을 우선(AP)할 것인지 결정

## Ⅲ. 구조 및 구성요소

<details><summary>용어 설명</summary>

- **CP vs AP 아키텍처**: 과반수 정족수 미달 시 에러를 반환하는 CP(MongoDB, HBase, Redis)와 Stale 데이터를 허용하며 응답하는 AP(Cassandra, DynamoDB).

</details>

```text
[ CAP 정리 3대 속성 및 CP/AP 분기 구조도 ]

                       [ Partition Tolerance (P) ]
                       (네트워크 단절 발생: 필수 조건)
                                    │
                 ┌──────────────────┴──────────────────┐
                 ▼                                     ▼
        [ CP 시스템 (일관성 선택) ]            [ AP 시스템 (가용성 선택) ]
        - 정족수 미달 시 에러/차단              - 로컬 복제본 기반 무조건 성공
        - 최신 데이터 보장                      - Stale Data 및 최종 일관성
        - MongoDB, HBase, Spanner             - Cassandra, DynamoDB, Couch
```

선의 의미: 네트워크 분할(P) 발생 시 일관성을 보장하는 CP 경로와 가용성을 보장하는 AP 경로로 분기되는 구조.

| 구성요소 | 책임 |
|:---|:---|
| 일관성 (Consistency) | 모든 클라이언트가 어느 노드에 접속하더라도 **가장 최근에 쓰여진 동일한 최신 데이터 반환** |
| 가용성 (Availability) | 일부 분산 노드에 장애가 발생해도 **살아있는 정상 노드가 에러 없이 유한 시간 내 응답** |
| 분할 내성 (Partition) | 노드 간 네트워크 통신이 단절되거나 메시지가 유실되어도 **분산 시스템 전체 동작 유지** |
| 정족수 검증기 (Quorum) | 분할 발생 시 과반수 노드($R + W > N$) 도달 여부를 확인하여 **요청 승인 또는 거부 판정** |

#### 한줄 요약

- 일관성(C), 가용성(A), 분할내성(P)의 상호작용 속에서 정족수 검증을 통해 시스템 동작을 결정

## Ⅳ. 흐름도

<details><summary>용어 설명</summary>

- **분할 시 동작 및 복구 절차**: 분할 감지 $\to$ 정족수 판정 $\to$ CP 거부 또는 AP 응답 $\to$ 네트워크 복구 $\to$ 최종 일관성 수렴.

</details>

```text
[ 네트워크 분할 발생 시 CAP 처리 파이프라인 ]

 ┌────────────────────────────────────────┐
 │ 1. 분산 노드 간 네트워크 분할(P) 감지  │
 └───────────────────┬────────────────────┘
                     │
                     ▼
 ┌────────────────────────────────────────┐
 │ 2. 정족수(Quorum) 과반수 도달 여부 판정│
 ├───────────────────┬────────────────────┤
 │ CP 경로 (정족수 미달)│ AP 경로 (지역 처리) │
 │ - 최신 데이터 불확실│ - 로컬 복제본 응답 │
 │ - 3A. 요청 거부(에러)│ - 3B. 임시 성공 반환│
 └───────────────────┴────────────────────┘
                     │
                     ▼
 ┌────────────────────────────────────────┐
 │ 4. 네트워크 복구 감지 및 힌트 핸드오프  │
 └───────────────────┬────────────────────┘
                     │
                     ▼
 ┌────────────────────────────────────────┐
 │ 5. 데이터 수렴: 최종 일관성 달성       │
 └────────────────────────────────────────┘
```

### 동작 원리

1. 분할 감지: 노드 간 하트비트(Heartbeat) 실패로 네트워크 파티션 발생을 감지.
2. 정족수 판정: 현재 격리된 서브 클러스터가 과반수(Quorum) 이상의 노드를 포함하는지 검사.
3. CP/AP 분기: CP 시스템은 정족수 미달 시 쿼리를 거부하여 불일치를 차단하고, AP 시스템은 로컬 데이터를 즉시 반환.
4. 네트워크 복구: 통신망이 복구되면 Hinted Handoff 및 Read Repair를 통해 변경 이력을 교환.
5. 데이터 수렴: 벡터 시계(Vector Clock) 또는 LWW(Last-Write-Wins)를 적용하여 최종 일관성을 회복.

#### 한줄 요약

- 분할 감지 $\to$ 정족수 검사 $\to$ CP(차단) / AP(응답) $\to$ 복구 및 최종 일관성 수렴의 파이프라인

## Ⅴ. 종류 및 비교

<details><summary>용어 설명</summary>

- **CP vs AP 시스템**: 데이터 정합성이 최우선인 금융/결제용 CP와 24/365 무중단 서비스가 최우선인 쇼핑몰/SNS용 AP.

</details>

| 구분 | CP 시스템 (Consistency & Partition) | AP 시스템 (Availability & Partition) |
|:---|:---|:---|
| **적용 기준** | 금융 계좌 이체, 결제, 재고 차감 등 정합성 필수 | SNS 피드, 장바구니, IoT 센서, 스트리밍 |
| **핵심 특징** | **정족수 미달 시 쓰기/읽기 차단, 최신 데이터 보장** | **네트워크 분할 중에도 무조건 성공 응답, 최종 일관성** |
| **한계** | 네트워크 장애 시 서비스 일시 가동 불가(Downtime) | 분할 기간 중 구버전 데이터(Stale Data) 반환 가능 |

#### 한줄 요약

- 데이터 정확성이 최우선이면 CP, 무중단 고가용성이 최우선이면 AP 시스템을 선택

## Ⅵ. 실무 고려사항 및 대책

<details><summary>용어 설명</summary>

- **가변 일관성(Tunable Consistency)**: Cassandra 등에서 쿼리마다 읽기/쓰기 정족수 레벨(ONE, QUORUM, ALL)을 동적으로 조절하는 기법.

</details>

| 문제 | 대책 | 효과 |
|:---|:---|:---|
| AP 시스템 채택 시 심각한 비즈니스 데이터 불일치 발생 | **Tunable Consistency 설정 ($R + W > N$, Strong Quorum)** | AP 기반 DB에서 강한 일관성 확보 |
| CP 시스템 채택 시 네트워크 단절로 인한 쿼리 타임아웃 | **Circuit Breaker 패턴 연동 및 캐시 기반 Fallback 응답 구성** | 서비스 전면 장애 전파 차단 |
| AP 환경에서 노드 간 동시 쓰기로 인한 충돌(Conflict) | **Vector Clock 및 Last-Write-Wins(LWW) 자동 충돌 해결기 가동** | 충돌 데이터의 원활한 최종 수렴 |

#### 한줄 요약

- 가변 정족수 튜닝, 서킷 브레이커 도입, 충돌 해결 메커니즘을 통해 CAP의 한계를 보완

## Ⅶ. 결론

<details><summary>용어 설명</summary>

- **비즈니스 도메인별 CAP 재단(Domain-Driven CAP)**: 동일 서비스 내에서도 결제는 CP로, 상품 조희는 AP로 분리 설계하는 최신 아키텍처 기법.

</details>

- **CAP 정리**는 분산 컴퓨팅의 절대 불변 법칙이며, 맹목적인 단일 선택 대신 도메인 중요도에 맞추어 결제 모듈은 CP로, 조회 모듈은 AP로 분리하는 하이브리드 아키텍처를 설계해야 함

#### 한줄 요약

- 분할 내성 하에서 비즈니스 요구에 따라 CP와 AP를 균형 있게 배치하여 신뢰성 있는 분산 시스템을 구축
