## Ⅰ. 개요

<details><summary>핵심 용어</summary>

- **DR (Disaster Recovery, 재해 복구)**: 지진, 화재, 사이버 공격 등 예상치 못한 재해로 인해 주 시스템이 완전 불능 상태가 되었을 때, 사전에 구축된 대체 환경에서 서비스를 복원하는 업무 연속성(BCP) 전략.
- **RTO (Recovery Time Objective, 복구 시간 목표)**: "장애 발생 후 최대 몇 시간/분 이내에 서비스가 복구되어야 하는가?"를 정량화한 목표. RTO가 짧을수록 비싼 예비 환경 필요.
- **RPO (Recovery Point Objective, 복구 시점 목표)**: "복구 시, 몇 시간 전 데이터까지는 손실을 허용한다"는 목표. RPO가 0이면 실시간 동기 복제가 필요하고, RPO가 24시간이면 하루 1회 백업으로도 충족.

</details>

- 정의/개념: 업무별 허용 중단 시간(RTO)과 허용 데이터 손실 구간(RPO)을 기준으로, 각 업무의 중요도에 맞는 대체 환경과 데이터 복제 수준을 설계하는 **재해 복구 전략 체계**
- 배경/필요성: 모든 시스템에 동일하게 비싼 복구 수준을 적용하면 비용이 기하급수적으로 증가하므로, BIA(업무 영향 분석) 결과를 바탕으로 업무별 차등 복구 목표를 설정하고 최적의 비용-복구 균형 요구성

#### 한줄 요약

- 가게 문을 다시 여는 시한이 RTO이고 마지막 장부를 어디까지 되살릴지가 RPO이므로 업무마다 다른 복구 준비가 필요하다.

## Ⅱ. 특징 (RTO/RPO 설계의 3대 핵심 개념)

<details><summary>핵심 용어</summary>

- **BIA (Business Impact Analysis, 업무 영향 분석)**: 각 업무가 X시간 동안 중단되었을 때 발생하는 재무적 손실, 법적 제재, 고객 이탈 등의 피해 규모를 정량화하여, RTO/RPO와 복구 투자 우선순위를 결정하는 핵심 분석.

</details>

![RPO 데이터 복구점과 RTO 서비스 복구 시한](/study/diagrams/rto-rpo-recovery-window.svg)

> 장애 시점 왼쪽은 **RPO (허용 데이터 손실 범위)**, 오른쪽은 **RTO (서비스 복구 목표 시간)**를 나타낸다.

- **BIA (업무 영향 분석)**: 업무 중단 1시간당 손실 규모를 금액으로 계산하여 RTO/RPO 목표치를 수치화하는 기반 활동.
- **MTD (Maximum Tolerable Downtime, 최대 허용 중단 시간)**: 조직이나 업무가 서비스를 복구하지 못했을 때 비즈니스 생존이 불가능해지는 한계 시간. **RTO는 항상 MTD보다 짧아야** 함.
- **Failover / Failback (장애 전환/복귀)**: 재해 발생 시 서비스를 DR 사이트로 넘기는 절차(Failover)와, 복구 완료 후 원래 사이트로 되돌리는 절차(Failback).

#### 한줄 요약

- 결제는 수초 안에 예비 환경으로 넘기고 보고서는 백업에서 복원하듯, 중단 피해에 따라 준비 비용과 복구 속도를 달리한다.

## Ⅲ. 구조 및 구성요소 (DR 아키텍처 계층 구조)

<details><summary>핵심 용어</summary>

- **Recovery Tier (복구 등급)**: RTO/RPO와 업무 중요도에 따라 시스템을 그룹화한 등급. Tier 1은 미션 크리티컬(RTO 분 단위), Tier 3은 비핵심(RTO 일 단위). 각 Tier별로 다른 DR 방식(Active-Active, Warm Standby, Backup) 적용.

</details>

```text
┌────────────────────────────────────────────────────────────────────────┐
│                      Disaster Recovery Architecture                    │
├────────────────────────────────────────────────────────────────────────┤
│ [BIA 분석] ──► RTO/RPO 결정 ──► 복구 등급(Tier) 배정                   │
│                                         │                              │
│     Tier 1: RTO분/RPO초 ───────► Active-Active 이중화                  │
│     Tier 2: RTO시/RPO분 ───────► Warm Standby (축소 환경 상시 준비)    │
│     Tier 3: RTO일/RPO시 ───────► Backup Restore (백업에서 재구성)      │
│                                         │                              │
│ [데이터 보호] ── 동기 복제(Tier1) / 비동기 복제(Tier2) / 백업(Tier3)   │
│ [예비 환경] ─── DR 사이트 자원 (컴퓨팅, 스토리지, 네트워크)            │
│ [전환 통제] ─── 재해 선언 → Failover → 복구 확인 → Failback            │
└────────────────────────────────────────────────────────────────────────┘
```

선의 의미: BIA 결과가 RTO/RPO를 결정하고, 이 목표값이 데이터 복제 방식(동기/비동기/백업)과 예비 환경 준비 수준을 결정하는 상위 기반.

| 구성요소 | 핵심 역할 및 기능 | 대표 기술/도구 |
|:---|:---|:---|
| **BIA & 복구 등급** | **업무 피해 분석으로 RTO/RPO 목표치 수치화** | 스프레드시트, CMDB |
| **데이터 보호** | **RPO를 충족하는 복제·백업·스냅숏 구성** | Oracle Data Guard, AWS S3 Replication |
| **예비 환경** | **RTO를 충족하는 대체 컴퓨팅·스토리지 자원** | AWS/Azure DR 리전, Veeam |
| **전환 통제** | **재해 선언·Failover·검증·Failback 단계 통제** | Runbook, SOAR |
| **훈련 증적** | **정기 DR 훈련으로 실제 RTO/RPO 달성 입증** | DR 훈련 보고서 |

#### 한줄 요약

- 복구 등급이 데이터 사본과 예비 환경 수준을 정하고 전환 통제와 훈련 증적이 실제 목표 달성을 확인한다.

## Ⅳ. 흐름도 (DR 선언에서 복귀까지 전체 절차)

<details><summary>핵심 용어</summary>

- **대사 검증 (Reconciliation)**: 재해 발생 후 DR 사이트로 전환하고 나서, 주 사이트와 DR 사이트의 데이터가 정합성(Consistency)을 유지하고 있는지 금액·건수 등을 비교하여 확인하는 작업. 특히 금융권에서 필수.

</details>

```text
 1. [BIA 수행] ─── 업무별 중단 피해 분석 → RTO/RPO 수치 확정
          │
          ▼
 2. [DR 설계] ─── 복구 등급 분류 → 복제 방식·예비 환경 구성
          │
          ▼
 3. [정기 DR 훈련] ─── 전환 후 실제 RTO/RPO 달성 여부 측정·기록
          │
          ├─(목표 미달)──► 복구 등급 상향 또는 예비 자원 증설
          │
          └─(목표 충족)──► 훈련 증적 보존

 ★ 실제 재해 발생 시:
 4. [재해 선언] ─── 승인 권한자가 DR 가동 선언
          ▼
 5. [Failover] ─── DR 사이트로 서비스 전환 (Tier 기준 우선순위)
          ▼
 6. [대사 검증] ─── 데이터 정합성 확인 (트랜잭션·잔액 일치)
          ▼
 7. [Failback] ─── 원 사이트 복구 완료 후 순차 복귀
```

### 동작 원리

1. **BIA → RTO/RPO**: 업무 피해를 금액으로 환산하여 복구 목표를 수치화.
2. **Failover**: 재해 선언 후 복구 등급 순서(Tier 1 먼저)로 DR 환경 전환.
3. **대사 검증 → Failback**: 데이터 정합성을 확인한 후에만 원 사이트로 복귀 (**DR 사이클 완결**).

#### 한줄 요약

- 재해 선언 뒤 대체 환경을 켜고 거래를 확인한 후 원래 환경으로 돌아감이 핵심이다.

## Ⅴ. 종류 및 비교 (DR 방식 1:1 비교)

<details><summary>핵심 용어</summary>

- **Active-Active (액티브-액티브)**: 2개 이상의 데이터센터가 평상시에도 동시에 트래픽을 처리하여, 한 곳이 재해를 당해도 나머지가 즉시 100% 부하를 흡수하는 최고 수준의 DR 방식.

</details>

| 비교 항목 | Backup Restore | Warm Standby | Active-Active |
|:---|:---|:---|:---|
| **RTO / RPO 목표** | **시간~일 / 시간 단위 (긴 목표)** | **분~시간 / 분 단위 (중간 목표)** | **초 / 0~분 단위 (최단 목표)** |
| **예비 환경 상태** | 백업 저장소만 존재 (환경은 재구성) | 축소된 환경이 항상 켜져 있음 (Scale-up) | 전체 용량 환경이 실시간 동시 운영 |
| **비용 수준** | 최저 (백업 스토리지 비용만) | 중간 (축소 운영 비용) | 최고 (2배 이상 인프라 비용) |
| **대표 적용 사례** | 비핵심 배치 시스템, 아카이브 | 내부 업무 시스템, 비금융 서비스 | 결제 시스템, 주요 인터넷 뱅킹 |

#### 한줄 요약

- 백업 복구는 창고에서 장비를 다시 꺼내고 웜 스탠바이는 예비 매장을 데우며 액티브-액티브는 두 매장이 평소에도 함께 영업한다.

## Ⅵ. 실무 고려사항 및 대책 (DR 3대 실무 난제 대책)

<details><summary>핵심 용어</summary>

- **N-1 Load Test (N-1 부하 시험)**: 전체 노드(서버) N개 중 1개가 장애 난 상태(N-1)에서 나머지 노드들이 피크(최대) 트래픽을 소화할 수 있는지 사전에 검증하는 용량 테스트. DR 전환 후 용량 부족 방지.

</details>

| 3대 실무 난제 | 발생 원인 | 실무 대책 및 해결방안 |
|:---|:---|:---|
| **1. 복구 등급 미차등화** | 모든 시스템에 같은 높은 DR 수준 적용 | **BIA 결과 기반 Tier 1/2/3 분류 및 각각 다른 RTO/RPO 목표 적용**|
| **2. DR 훈련 미실시** | 문서화된 Runbook만 있고 실제 훈련 없음 | **반기 1회 이상 실제 Failover 훈련 및 대사 검증 수행 후 증적 보존** |
| **3. 예비 환경 용량 부족** | 평소 50% 수준 자원으로만 DR 사이트 구성 | **N-1 부하 시험으로 피크 트래픽 처리 가능 용량 사전 검증 및 확보** |

> 사례: **국내 금융기관의 재해복구 시스템(DRS) 구축·운영 감독 규정에 따른 RTO 4시간 이내·RPO 1시간 이내 충족 의무화 및 연 2회 DR 훈련 실적 금융감독원 보고 사례**

#### 한줄 요약

- 금융 거래의 원장과 잔액이 다른 시점으로 돌아가면 숫자가 맞지 않으므로 같은 복구점으로 대사해야 한다.

## Ⅶ. 결론

<details><summary>핵심 용어</summary>

- **DR 방식 선택 기준**: 업무의 BIA 피해 규모(RTO/RPO 요구치)와 예산 한도를 교차 분석하여 Active-Active, Warm Standby, Backup Restore 중 최적 방식을 선택하는 경영적 의사결정 기준.

</details>

- **재해 복구 방식 선택 기준**에 따라 BIA 분석 결과를 기반으로 **업무 Tier별 RTO/RPO를 차등 설계하고 정기 DR 훈련으로 목표 달성 입증** 필수 적용

#### 한줄 요약

- 가장 비싼 예비 환경을 모두 쓰는 대신 업무 손실 한도에 맞는 등급을 고르고 훈련에서 거래 복구 성공을 확인한다.
