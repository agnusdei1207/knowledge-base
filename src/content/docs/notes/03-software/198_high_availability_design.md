## Ⅰ. 개요

<details><summary>용어 설명</summary>

- **고가용성 설계(High Availability Design)**: 시스템의 단일 장애점(SPOF)을 제거하고 다운타임을 최소화하기 위해, 인프라와 소프트웨어 자원을 다중화(Active-Active / Active-Standby)하고 자동 헬스체크 및 무중단 장애 전환(Failover)을 구현하는 아키텍처 체계.
- **단일 장애점 및 전사 다운타임 위험(SPOF & Downtime Catastrophe)**: 단일 서버, 데이터베이스, 네트워크 장비의 결함 발생 시 전체 시스템으로 장애가 전파되어 서비스가 전면 중단되는 위험.

</details>

- 정의/개념: 단일 장애점(SPOF)을 제거하고 장애 발생 시 무중단 페일오버를 위해 **Active-Active 및 Active-Standby 구조로 이중화**하는 고가용성 설계 체계
- 배경/필요성: 단일 서버, 데이터베이스, 네트워크 장비의 불의의 장애 발생 시 **전체 서비스 다운타임 초과 및 막대한 비즈니스 금전 손실 위험** 직면

#### 한줄 요약

- 독립된 장애 도메인 분리와 쿼럼 기반 페일오버를 결합하여 Five Nines(99.999%) 수준의 비즈니스 무중단 가용성을 달성

## Ⅱ. 특징

<details><summary>용어 설명</summary>

- **스플릿 브레인(Split-Brain)**: 네트워크 단절 시 양쪽 노드가 서로 상대방이 다운되었다고 오판하여 동시에 Primary 승격을 시도함으로써 데이터 충돌 및 오염이 발생하는 현상.
- **펜싱 및 STONITH(Fencing & STONITH)**: 'Shoot The Other Node In The Head'의 약어로, 페일오버 승격 전 구 Active 노드의 전원/네트워크를 강제 차단하여 이중 쓰기를 원천 봉쇄하는 안전 메커니즘.

</details>

- 모든 컴포넌트를 최소 2개 이상의 독립 경로로 구성하는 **완전 다중화(Full Redundancy)**
- 과반수 노드 투표 합의를 통해 단일 Primary를 선출하는 **쿼럼(Quorum: $N/2 + 1$) 메커니즘**
- 노드 1개가 탈락해도 피크 트래픽을 감당하는 **$N-1$ 여유 용량(Capacity) 확보**

#### 한줄 요약

- 다중화, 펜싱(STONITH), 쿼럼 합의, 헬스체크를 결합하여 스플릿 브레인 없는 안전한 고가용성을 보장

## Ⅲ. 구조 및 구성요소

<details><summary>용어 설명</summary>

- **고가용성 4대 아키텍처 요소**: Traffic Controller(로드밸런서/라우터), Redundant Nodes(Active-Active/Standby), Consensus Engine(Quorum), Fencing Device(STONITH).

</details>

```text
[ 고가용성(HA) 이중화 및 장애 전환(Failover) 아키텍처 구조도 ]

 1. [ 트래픽 제어 계층 (Traffic Controller: GSLB / L4-L7 로드밸런서) ]
    ┌─────────────────────────────────────────────────────────────┐
    │  • 심층 헬스체크(Health Check) ➔ 정상 인스턴스로만 트래픽 분산│
    └────────────────────────────┬────────────────────────────────┘
                                 │
        ┌────────────────────────┴────────────────────────┐
        ▼                                                 ▼
 2. [ 주 노드 (Primary / Active Node) ]       3. [ 대기 노드 (Standby Node) ]
    • 가용영역 1 (AZ-1) 독립 격리 배치           • 가용영역 2 (AZ-2) 독립 격리 배치
    • 실시간 동기/비동기 상태 복제 (Replication) ──► 인메모리 데이터 웜업 대기
        │                                                 │
        └────────────────────────┬────────────────────────┘
                                 │ (하트비트 및 과반수 합의)
                                 ▼
 4. [ 쿼럼 및 펜싱 제어 (Quorum Consensus & Fencing STONITH) ]
    • etcd / Zookeeper 3노드 쿼럼 ➔ 장애 감지 시 구 Active 전원 강제 차단
```

선의 의미: 로드밸런서가 헬스체크를 통해 정상 노드로 라우팅하고, 쿼럼과 펜싱 장치가 단일 Primary를 유지하며 복제를 수행하는 구조.

| 구성요소 | 책임 |
|:---|:---|
| 트래픽 컨트롤러 (LB/GSLB) | 실시간 심층 헬스체크를 수행하여 **비정상 노드를 배제하고 정상 인스턴스로 트래픽 라우팅** |
| 액티브/스탠바이 노드 | 독립된 가용영역(AZ)에 배치되어 **실시간 데이터 복제 및 무중단 업무 처리 제공** |
| 쿼럼 엔진 (Quorum) | 과반수($N/2+1$) 투표 합의를 통해 **네트워크 단절 시에도 단 1개의 Primary 승격 보장** |
| 펜싱 장치 (STONITH) | 페일오버 실행 전 **구 Primary 노드의 전원/네트워크를 강제 차단하여 스플릿 브레인 방어** |

#### 한줄 요약

- 트래픽 컨트롤러, 다중화 노드, 쿼럼 엔진, 펜싱 장치가 결합하여 고가용성 클러스터를 완성

## Ⅳ. 흐름도

<details><summary>용어 설명</summary>

- **자동 장애 전환 5단계 절차**: 헬스체크 장애 감지 $\to$ Fencing(구 노드 격리) $\to$ Quorum 기반 Standby 승격 $\to$ 데이터 정합성 검증 $\to$ 트래픽 전환 완료.

</details>

```text
[ 고가용성 자동 페일오버(Failover) 처리 파이프라인 ]

 ┌────────────────────────────────────────┐
 │ 1. Active 노드 심층 헬스체크 연속 실패 │
 └───────────────────┬────────────────────┘
                     │
                     ▼
 ┌────────────────────────────────────────┐
 │ 2. Fencing 실행: 구 Active 전원 차단(STONITH)
 └───────────────────┬────────────────────┘
                     │
                     ▼
 ┌────────────────────────────────────────┐
 │ 3. Quorum 과반수 합의로 Standby 노드 승격
 └───────────────────┬────────────────────┘
                     │
                     ▼
 ┌────────────────────────────────────────┐
 │ 4. 복제 동기화 지점 확인 및 정합성 검증│
 └───────────────────┬────────────────────┘
                     │
                     ▼
 ┌────────────────────────────────────────┐
 │ 5. 로드밸런서 라우팅 갱신 및 신규 Active 전환
 └────────────────────────────────────────┘
```

### 동작 원리

1. 장애 감지: 로드밸런서와 감시 데몬이 Active 노드의 HTTP 500 에러 및 응답 지연을 3회 연속 감지하여 장애 확정.
2. 펜싱 실행: 스플릿 브레인을 방지하기 위해 IPMI/클라우드 API를 호출하여 기존 Active 노드의 네트워크와 전원을 강제 차단.
3. 쿼럼 승격: 3노드 etcd 클러스터의 과반수 합의(2/3)를 얻어 Standby 노드를 새로운 Primary로 즉시 승격.
4. 정합성 검증: WAL(Write-Ahead Log) 복제 지점을 대조하여 유실된 트랜잭션이 없는지 데이터 무결성을 확인.
5. 트래픽 전환: 로드밸런서의 VIP 및 DNS 라우팅 테이블을 갱신하여 클라이언트의 모든 트래픽을 신규 Active로 즉시 전환.

#### 한줄 요약

- 장애 감지 $\to$ 펜싱 격리 $\to$ 쿼럼 승격 $\to$ 정합성 검증 $\to$ 트래픽 전환의 5단계

## Ⅴ. 종류 및 비교

<details><summary>용어 설명</summary>

- **Active-Active vs Hot Standby vs Warm Standby**: 상시 동시 처리(Active-Active), 즉시 승격 대기(Hot), 기동 시간 소요 대기(Warm).

</details>

| 구분 | 액티브-액티브 (Active-Active) | 핫 스탠바이 (Active-Hot Standby) | 웜 스탠바이 (Active-Warm Standby) |
|:---|:---|:---|:---|
| **적용 기준** | 무중단(RTO $\approx$ 0) 및 대규모 트래픽 분산이 필수적인 웹/앱 계층 | 데이터 쓰기 일관성이 중요한 핵심 RDBMS (Oracle, PostgreSQL) | 비용 절감이 중요한 비핵심 내부 시스템, 개발/스테이징 환경 |
| **핵심 특징** | **모든 노드가 상시 동시 트래픽 처리, Failover 시간 사실상 0초** | **실시간 데이터 동기 복제 유지, 장애 시 수 초 내 자동 승격** | **최소 사양으로 기동 대기하다가 장애 시 스케일업 승격 (수 분 소요)** |
| **한계** | 분산 데이터 쓰기 시 충돌 해결 및 양방향 복제 지연 난이도 | 유휴 장비 유지로 인한 2배의 인프라 비용 발생 | RTO가 수 분 이상 발생하여 금융/미션 크리티컬 시스템 적용 불가 |

#### 한줄 요약

- 웹/앱 계층은 Active-Active, 데이터베이스 계층은 Hot Standby, 비용 절감형 백업은 Warm Standby를 선택

## Ⅵ. 실무 고려사항 및 대책

<details><summary>용어 설명</summary>

- **플래핑(Flapping) 방지**: 일시적인 네트워크 튐 현상으로 인해 Active와 Standby가 서로 주도권을 번갈아 바꾸며 서비스가 마비되는 현상을 방지하는 통제.

</details>

| 문제 | 대책 | 효과 |
|:---|:---|:---|
| 일시적 네트워크 지연으로 불필요한 페일오버 반복 (Flapping) | **헬스체크 다중 임계치(3회 이상 연속 실패) 및 쿨다운 시간 설정** | 오탐 페일오버 사고 0건 달성 |
| 네트워크 단절 시 양쪽 노드가 동시 Primary로 동작 (Split-Brain) | **STONITH 펜싱 강제 및 3노드 이상 홀수 쿼럼(Quorum) 합의 의무화** | 데이터 덮어쓰기 충돌 원천 차단 |
| 페일오버 후 단일 노드가 전체 피크 트래픽을 감당 못해 연쇄 다운 | **$N-1$ 부하 테스트 검증 및 K8s HPA 자동 오토스케일링 연계** | 장애 전환 후 2차 다운 완벽 방어 |

#### 한줄 요약

- 플래핑 방지, STONITH 펜싱, $N-1$ 용량 검증을 통해 고가용성 시스템의 실효성을 보장

## Ⅶ. 결론

<details><summary>용어 설명</summary>

- **카오스 엔지니어링(Chaos Engineering)**: 고가용성 아키텍처가 실제 프로덕션 장애 시 정상 동작하는지 Chaos Monkey 등을 통해 의도적으로 서버를 다운시켜 검증하는 실천 기법.

</details>

- **고가용성 설계** 기반 엔터프라이즈 시스템의 생존을 결정짓는 핵심 아키텍처 원칙이며, Active-Active 및 Hot Standby의 적재적소 배치와 쿼럼/펜싱 기반의 안전한 페일오버를 구축하여 무중단 클라우드 서비스를 완성해야 함
