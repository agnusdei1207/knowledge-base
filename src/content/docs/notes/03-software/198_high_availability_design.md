## Ⅰ. 개요

<details><summary>용어 설명</summary>

- **HA (High Availability, 고가용성)**: 시스템이 특정 기간 동안 정상적으로 서비스를 제공할 수 있는 확률을 의미하며, 일반적으로 연간 가용성 목표를 "몇 나인(9)"으로 표현(예: 99.99% = "포 나인"). 이를 달성하기 위해 자원을 다중화하고 장애 전환 체계를 구축.
- **Failure Domain (장애 도메인)**: 하나의 물리적 장애(전원 단절, 스위치 불량, 랙 화재 등)가 동시에 영향을 미치는 자원의 범위. HA 설계의 핵심은 이 도메인을 최대한 분리하여 하나의 장애가 전체 시스템에 미치는 영향을 최소화하는 것.
- **Five Nines (파이브 나인)**: 99.999% 가용성으로, 연간 다운타임이 약 5.26분 이내. 인터넷 뱅킹 코어 시스템 등 초고가용성이 요구되는 시스템의 목표 수준.

</details>

- 정의/개념: 장애 Domain을 분리하고 정상 자원으로 전환하는 **HA 설계**
- 배경/필요성: 단일 서버•망•전원의 **SPOF가 전체 중단**으로 확산

#### 한줄 요약

- 한 발전기가 멈추면 독립 전원의 예비 발전기로 부하를 넘기듯, 장애 도메인을 나누고 준비된 인스턴스로 요청을 전환한다.

## Ⅱ. 특징

<details><summary>용어 설명</summary>

- **Split Brain (분할 뇌 현상)**: 클러스터 노드들 간의 네트워크가 단절되었을 때, 각 노드가 자신만이 정상 Primary라고 판단하여 동시에 쓰기 작업을 수행하는 데이터 충돌 현상. Quorum과 Fencing으로 방지.

</details>

- **Redundancy (다중화)**: 서버, 네트워크, 전원, 스토리지 등 단일 장애점(SPOF)이 될 수 있는 모든 구성요소를 2개 이상의 독립 경로로 구성.
- **Fencing (펜싱)**: 장애 전환 시 이전 활성 노드(Old Primary)가 스플릿 브레인으로 계속 쓰기를 시도하지 못하도록 강제로 격리(전원 차단, 네트워크 차단)하는 안전 기법.
- **Quorum (쿼럼)**: 클러스터에서 장애 전환 결정 시 반드시 과반수(N/2+1) 노드의 합의를 요구하여, 두 노드가 동시에 Primary로 승격하는 사태를 방지하는 투표 메커니즘.
- **N-1 Capacity (N-1 용량)**: 구성 노드 N개 중 1개가 장애 나더라도, 나머지 N-1개가 최대(Peak) 트래픽을 전부 처리할 수 있는 충분한 용량을 확보하는 설계 원칙.
- **Health Check (헬스 체크)**: 단순 Ping이 아닌, 실제 의존성(DB, 외부 API)까지 포함한 "이 인스턴스가 실제 요청을 정상 처리할 수 있는가?"를 주기적으로 판정하는 심층 검사.

#### 한줄 요약

- 두 매장을 다른 전원과 망에 두고 한쪽이 멈추면 상태 확인과 펜싱 뒤 다른 쪽으로 손님을 보내 동시 장애와 이중 쓰기를 피한다.

## Ⅲ. 구조 및 구성요소

<details><summary>용어 설명</summary>

- **State Replication (상태 복제)**: Active 노드의 메모리 상태, 세션 데이터, 처리 중인 트랜잭션 정보를 Standby 노드에 실시간으로 복제하여, 전환 후에도 진행 중이던 작업을 끊김 없이 이어받는 기술.

</details>

```text
[HA Architecture]
 ├── [Traffic Controller | Health Check•Routing]
 ├── [Active•Standby | 독립 장애 Domain]
 ├── [Quorum | 단일 Primary 선출]
 ├── [Fencing | 장애 노드 격리]
 └── [State Store | 상태 복제]
```

| 구성요소 | 책임 |
|---|---|
| Traffic Controller | Health Check 기반 **정상 경로** Routing |
| Active•Standby | 독립 장애 Domain의 **실행 자원** 제공 |
| Quorum | 과반수 합의로 **단일 Primary** 보장 |
| Fencing | 구 Primary를 격리해 **Split Brain** 방지 |
| State Store | Active 상태의 **복제•정합성** 유지 |

#### 한줄 요약

- 트래픽 제어가 활성·대체 인스턴스를 잇고 쿼럼이 단일 쓰기를 보장하며 상태 저장소가 업무 상태를 대체 노드에 전달한다.

## Ⅳ. 흐름도

<details><summary>용어 설명</summary>

- **STONITH (Shoot The Other Node In The Head)**: 문자 그대로 "상대 노드의 머리를 쏴라"를 의미하는 Fencing 기법. 네트워크 단절 등 이상이 감지된 노드의 전원을 원격으로 강제 차단하여 Split Brain을 방지.

</details>

```text
[Active 인스턴스 이상 신호]
          │
          ▼
 1. [헬스 체크 실패 감지] ─── 단순 Ping이 아닌 실제 의존성 포함 심층 검사
          │
          ├─(일시 오류)──────► 지속 모니터링 (오탐 방지)
          │
          └─(지속 장애 확정)─► Failover 프로세스 시작
                                      │
                                      ▼
 2. [Fencing 실행] ──────── 구 Active 노드 강제 격리 (STONITH)
          │
          ▼
 3. [Quorum 기반 승격] ───── 과반수 합의로 단일 Standby만 Primary로 선출
          │
          ▼
 4. [상태 정합성·용량 검증] ─ 복제 상태 확인 + N-1 용량 처리 가능 여부 점검
          │
          ▼
 5. [트래픽 전환 완료] ────── LB가 신규 Active로 요청 라우팅 변경
```

### 동작 원리

1. **헬스 체크 실패 감지**: 다중 신호로 지속 장애 확정
2. **Fencing 실행**: 구 Active를 격리해 이중 쓰기 차단
3. **Quorum 기반 승격**: 과반수로 단일 Primary 선출
4. **상태 정합성•용량 검증**: 복제 상태와 N-1 용량 확인
5. **트래픽 전환 완료**: 신규 Active로 요청 Routing

#### 한줄 요약

- 활성 노드가 멈추면 쓰기 권한을 먼저 끊고 쿼럼 승인을 받은 대체 노드가 복제 상태를 확인한 뒤 요청을 인계한다.

## Ⅴ. 종류 및 비교

<details><summary>용어 설명</summary>

- **Active-Active (액티브-액티브)**: 모든 인스턴스가 평상시에도 동시에 트래픽을 처리하는 방식. 한 인스턴스에 장애가 발생하면 나머지가 해당 부하를 자연스럽게 흡수하여 전환 시간이 사실상 0.

</details>

| 비교 항목 | Active-Active | Hot Standby (핫 스탠바이) | Warm Standby (웜 스탠바이) |
|:---|:---|:---|:---|
| **평소 상태** | **모든 인스턴스가 동시에 트래픽 처리** | **대기 인스턴스가 상태 복제를 유지하며 즉시 승격 가능**| 대기 인스턴스가 축소/정지 상태로 기동·확장 시간 필요|
| **전환 시간** | 사실상 0 (LB가 즉시 우회) | 초 단위 (승격 절차 후 즉시) | 분 단위 (기동·확장 후 승격) |
| **비용** | 최고 (모든 인스턴스 Full 용량 운영) | 중간 (대기 인스턴스 운영 비용) | 최저 (최소 자원 대기) |
| **주요 적용** | 결제 시스템, 인터넷 뱅킹 | DB Primary-Replica, 금융 거래 | 비핵심 배치 시스템, DR 사이트 |

#### 한줄 요약

- 두 매장이 평소 함께 영업하면 액티브-액티브, 한 매장은 즉시 대기하면 핫 스탠바이, 준비 시간이 필요하면 웜 스탠바이다.

## Ⅵ. 실무 고려사항 및 대책

<details><summary>용어 설명</summary>

- **Chaos Engineering (카오스 엔지니어링)**: Netflix가 창시한 복원력 검증 기법으로, 운영 환경에 의도적으로 서버 장애, 네트워크 단절 등을 주입하여 HA 절차가 실제로 동작하는지 검증하는 실험.

</details>

| 3대 실무 난제 | 발생 원인 | 실무 대책 및 해결방안 |
|:---|:---|:---|
| **1. 오탐 전환(Flapping)** | 순간적 네트워크 지연으로 헬스 체크 실패 → 불필요한 Failover | **다중 신호(헬스 체크 횟수, 지속 시간) 기반 장애 확정 기준 상향** |
| **2. Split Brain 발생** | 네트워크 단절 후 양쪽 노드가 동시에 Primary로 동작 | **반드시 Fencing 선행 후 Quorum 합의 기반 단일 노드만 승격** |
| **3. 전환 후 용량 부족** | 전환 후 잔여 인스턴스가 전체 트래픽을 감당 못 함 | **N-1 Load Test로 최대 트래픽 처리 가능 용량 사전 검증 및 자동 스케일링 구성** |

> 사례: **AWS Multi-AZ RDS 배포로 데이터베이스 Primary 장애 시 60초 이내 Standby 자동 승격 구현, 쿠버네티스 다중 마스터(etcd 쿼럼 기반) 고가용성 구성 사례**

#### 한줄 요약

- 데이터베이스 전환 때 이전 주 노드의 쓰기 권한을 먼저 차단해야 두 계산대가 같은 장부를 동시에 고치지 않는다.

## Ⅶ. 결론

<details><summary>용어 설명</summary>

- **SLO·Error Budget (서비스 수준 목표·오류 예산)**: SLO는 달성해야 할 가용성 목표(예: 99.95%)이고, 오류 예산은 목표 달성을 위해 허용되는 최대 다운타임 시간. 오류 예산이 소진될 위기이면 신규 배포를 멈추고 안정화에 집중.

</details>

- **고가용성 구성 선택 기준**에 따라 목표 가용성(SLO)과 허용 전환 시간·N-1 용량 여부·쓰기 충돌 위험을 종합 평가하여 **Active-Active, Hot/Warm Standby 방식 적용** 결정

#### 한줄 요약

- 두 노드가 동시에 쓸 위험이 크면 하나만 주 노드로 두고, 동시 처리와 남은 용량이 검증되면 둘 다 활성화한다.
