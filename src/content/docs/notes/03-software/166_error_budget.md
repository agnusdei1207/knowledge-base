## Ⅰ. 개요

<details><summary>용어 설명</summary>

- **오류 예산(Error Budget)**: 서비스 가용성 목표(SLO)에서 100%를 뺀 나머지 비율(`100% - SLO`)로, 시스템의 변경과 혁신을 위해 합법적으로 허용된 서비스 중단(불안정성) 허용량.
- **배포 속도 대 시스템 안정성 딜레마(Velocity vs Reliability Dilemma)**: 신속한 기능 출시를 원하는 개발 조직과 다운타임 제로를 요구하는 운영 조직 간의 목표 충돌 및 합리적 절충 기준 부재의 위험.

</details>

- 정의/개념: 가용성 목표(SLO)를 기반으로 **허용 가능한 실패량(100% - SLO)을 산출하여 신규 기능 배포와 안정화의 균형을 통제**하는 SRE 거버넌스 지표
- 배경/필요성: 완벽한 무결점 100% 가용성 추구로 인한 **과도한 인프라 비용 낭비 및 개발팀의 신규 기능 배포 속도 저하 위험** 직면

#### 한줄 요약

- 서비스 수준 목표(SLO)의 잔여 허용치를 오류 예산으로 정의하여 신규 기능 배포와 안정화 작업의 균형을 통제

## Ⅱ. 특징

<details><summary>용어 설명</summary>

- **소진 속도(Burn Rate)**: 오류 예산이 정상 소비 속도(1배수) 대비 얼마나 빠르게 고갈되고 있는지를 나타내어 단기/장기 경보 발령을 결정하는 지표.
- **배포 동결(Code Freeze Policy)**: 오류 예산이 전액 소진되었을 때 신규 기능 배포를 즉시 중단하고 시스템 안정화 및 버그 수정에만 엔지니어링 자원을 집중하는 정책.

</details>

- 완벽주의(100%)를 배제하고 실용적인 신뢰성을 추구하는 **수학적 실패 허용량 산출**
- 예산이 충분하면 빠른 출시를, 예산이 고갈되면 안정화를 강제하는 **배포 통제 밸브(Release Valve)**
- 단기 폭발적 장애와 장기 누적 장애를 모두 감지하는 **다중 윈도우 Burn Rate 경보 체계** #### 한줄 요약

- 정량적 오류 예산 관리를 통해 비즈니스 혁신 속도와 시스템 신뢰성을 동시에 확보

## Ⅲ. 구조 및 구성요소

<details><summary>용어 설명</summary>

- **오류 예산 거버넌스 프레임워크**: SLO(목표), Error Budget(허용량), Burn Rate(소진 속도), Consequence Policy(소진 시 행동 강제).

</details>

```text
[ 오류 예산(Error Budget) 산출 및 배포 거버넌스 구조도 ]

 1. [ 월간 가용성 목표 (SLO: 99.9%) ]
                    │
                    ▼
 2. [ 오류 예산 산출: Error Budget = 100% - 99.9% = 0.1% ]
    • 월 30일 기준 총 허용 다운타임: 약 43.2분 (2,592초)
                    │
        ┌───────────┴───────────┐
        ▼                       ▼
 3. [ 소진율 평가: Burn Rate ] [ 배포 의사결정 정책: Consequence Policy ]
    • 1x 이하: 정상 소진        • 예산 잔여: 신규 기능 지속 배포 (Velocity)
    • 14.4x: 1시간 내 2% 소진   • 예산 고갈: 배포 전면 동결 (Code Freeze)
    • 144x: 1시간 내 20% 전소   • Toil 제거 및 안정화 자동화 전환
```

선의 의미: SLO에서 오류 예산을 산출하고 Burn Rate 소진 속도에 따라 신규 배포 허용 또는 안정화 동결을 결정하는 구조.

| 구성요소 | 책임 |
|:---|:---|
| 가용성 목표 (SLO) | 비즈니스 요구사항과 비용을 반영하여 **팀 간에 합의한 신뢰성 목표치(99.9%) 선언** |
| 오류 예산 (Error Budget) | `100% - SLO`로 계산되는 **월간 허용 다운타임(43.2분) 및 실패 요청 한도 산출** |
| 소진 속도 (Burn Rate) | 현재 장애로 인해 **오류 예산이 기준 대비 몇 배속으로 고갈되는지 실시간 계산** |
| 행동 정책 (Policy) | 예산 소진 상태에 따라 **신규 배포 동결(Code Freeze), 롤백, 테스트 보강 강제** |

#### 한줄 요약

- SLO, 오류 예산, Burn Rate, 행동 정책이 결합하여 개발-운영 간의 배포 거버넌스를 완성

## Ⅳ. 흐름도

<details><summary>용어 설명</summary>

- **오류 예산 기반 배포 제어 5단계**: 실시간 오류율 집계 $\to$ 잔여 예산 계산 $\to$ Burn Rate 평가 $\to$ 배포/동결 판정 $\to$ 안정화 조치 실행.

</details>

```text
[ 오류 예산(Error Budget) 실시간 모니터링 및 배포 통제 파이프라인 ]

 ┌────────────────────────────────────────┐
 │ 1. Prometheus / APM 기반 SLI 오류율 집계│
 └───────────────────┬────────────────────┘
                     │
                     ▼
 ┌────────────────────────────────────────┐
 │ 2. SLO(99.9%) 대비 잔여 오류 예산 산출 │
 └───────────────────┬────────────────────┘
                     │
                     ▼
 ┌────────────────────────────────────────┐
 │ 3. 다중 윈도우 Burn Rate 소진 속도 계산│
 └───────────────────┬────────────────────┘
                     │
                     ▼
 ┌────────────────────────────────────────┐
 │ 4. 의사결정: Burn Rate 초과 시 Pager 발령│
 ├───────────────────┬────────────────────┤
 │ 예산 여유 (정상)  │ 예산 고갈 (위험)   │
 │ • 신규 배포 지속  │ • 신규 배포 동결   │
 └───────────────────┴────────────────────┘
                     │
                     ▼
 ┌────────────────────────────────────────┐
 │ 5. 안정화 작업, 버그 픽스 및 예산 회복 │
 └────────────────────────────────────────┘
```

### 동작 원리

1. 오류율 집계: API Gateway와 서비스 메시에서 발생하는 HTTP 5xx 에러 및 타임아웃 비율을 실시간 수집.
2. 예산 산출: 당월 총 허용 다운타임(43.2분) 중 현재까지 소비된 시간과 잔여 예산을 계산.
3. Burn Rate 계산: 단기(1시간) 및 장기(6시간) 윈도우를 결합하여 예산이 정상 속도보다 몇 배 빠르게 소진되는지 평가.
4. 의사결정: Burn Rate가 14.4x를 초과하면 온콜 엔지니어에게 긴급 Pager를 울리고 CI/CD 배포 파이프라인을 자동 차단.
5. 안정화 조치: 개발팀과 SRE가 협력하여 결함 롤백, 핫픽스, 아키텍처 개선을 수행하고 롤링 윈도우 예산을 회복.

#### 한줄 요약

- 오류율 집계 $\to$ 예산 산출 $\to$ Burn Rate 계산 $\to$ 배포/동결 판정 $\to$ 안정화 조치의 5단계

## Ⅴ. 종류 및 비교

<details><summary>용어 설명</summary>

- **Fast Burn vs Slow Burn**: 수십 분 내로 예산을 전소시키는 치명적 장애(Fast Burn)와 며칠에 걸쳐 서서히 예산을 갉아먹는 미세 장애(Slow Burn).

</details>

| 구분 | 초고속 소진 (Fast Burn: 14.4x / 144x) | 완만 소진 (Slow Burn: 6x / 1x) |
|:---|:---|:---|
| **적용 기준** | 대규모 서비스 장애, DB 전면 다운, 잘못된 배포 | 간헐적 타임아웃, 메모리 누수, 특정 파드 불안정 |
| **핵심 특징** | **1시간 내 예산의 2%~20%가 급소진되는 위급 상황** | **수일에 걸쳐 서서히 예산이 감소하는 잠재적 결함** |
| **한계** | 즉각적인 온콜 Pager 호출 및 즉시 배포 동결 강제 | 즉각 Pager를 울리면 경보 피로 유발 (Jira 티켓 처리) |

#### 한줄 요약

- 긴급 장애는 Fast Burn 알람으로 즉각 대응, 잠재적 누수 장애는 Slow Burn 티켓으로 계획적 조치

## Ⅵ. 실무 고려사항 및 대책

<details><summary>용어 설명</summary>

- **롤링 윈도우(Rolling Window)**: 매월 1일 예산이 리셋되는 달력 윈도우의 꼼수를 방지하기 위해 '최근 30일(Rolling 30 Days)' 이동 구간으로 예산을 산출하는 기법.

</details>

| 문제 | 대책 | 효과 |
|:---|:---|:---|
| 매월 1일 자정 예산 리셋을 노리고 미해결 장애 상태에서 배포 강행 | **달력 기준을 폐지하고 '최근 30일 롤링 윈도우(Rolling Window)' 적용** | 상시 연속적 신뢰성 관리 달성 |
| 경영진의 무조건 100% 무장애 요구로 개발팀 사기 저하 | **100% 달성에 필요한 인프라 비용과 사업적 실익 한계를 데이터로 입증** | 합리적 99.9% SLO 및 오류 예산 확보 |
| 예산 고갈 시 PO/개발팀이 배포 동결 정책(Code Freeze) 거부 | **CTO 및 경영진 주관으로 Error Budget Consequence Policy 공식 협약** | 정책 위반 배포 시도 원천 차단 |

#### 한줄 요약

- 롤링 윈도우 도입, 합리적 SLO 협약, 경영진 승인 배포 동결 정책을 통해 오류 예산의 실효성을 보장

## Ⅶ. 결론

<details><summary>용어 설명</summary>

- **데이터 주도 릴리즈 거버넌스(Data-Driven Release Governance)**: 감정이나 주관적 판단이 아닌 오류 예산 잔여율 데이터를 기반으로 릴리즈 여부를 자동 결정하는 현대적 운영 체계.

</details>

- **오류 예산** 신뢰성과 배포 속도라는 상충되는 두 목표를 조화시키는 SRE의 핵심 나침반이며, 다중 윈도우 Burn Rate 경보와 롤링 윈도우 거버넌스를 결합하여 비즈니스 성장과 시스템 안정성을 완벽히 양립시켜야 함

#### 한줄 요약

- 잔여 오류 예산과 소진 속도(Burn Rate)를 기반으로 기능 출시와 시스템 안정화의 최적 균형을 완성
