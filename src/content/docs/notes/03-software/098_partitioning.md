## Ⅰ. 개요

<details><summary>용어 설명</summary>

- **테이블 파티셔닝(Partitioning)**: 단일 논리 테이블을 물리적으로 여러 개의 독립된 세그먼트 파일로 분할 관리하는 DB 설계 기법.
- **Partition Pruning(파티션 프루닝)**: 조건절의 파티션 키를 분석하여 불필요한 파티션 블록 접근을 원천 배제하는 옵티마이저 최적화.

</details>

- 정의/개념: 대용량 테이블을 파티션 키 기준으로 물리적 독립 파일로 분할하여 **파티션 프루닝으로 I/O를 절감하고 수명주기를 관리**하는 물리 설계 기법
- 배경/필요성: 단일 테이블이 커지면 조건과 무관한 구간까지 함께 스캔해 데이터량에 비례하는 I/O를 치르고 과거 이력 정리도 행 단위 DELETE 비용을 그대로 부담하므로, 파티션 키 경계로 물리 분할해 무관한 구간을 접근 대상에서 빼고 삭제를 파티션 드롭이라는 메타데이터 연산으로 대체할 필요

#### 한줄 요약
- 파티셔닝의 이득은 질의가 파티션 키를 조건에 담을 때만 성립하므로, 키 선택은 저장 구조의 결정이 아니라 어떤 질의를 값싸게 만들고 어떤 질의를 포기할지의 결정이 된다.

## Ⅱ. 특징

<details><summary>용어 설명</summary>

- **Local Index vs Global Index**: 파티션별로 1:1 생성되어 독립 관리되는 로컬 인덱스와 전체 파티션을 아우르는 단일 글로벌 인덱스.
- **Drop Partition**: `DELETE` 대신 파티션 파일 자체를 `ALTER TABLE ... DROP PARTITION`으로 1초 만에 일괄 삭제하여 Undo/Redo 부하를 제거하는 기능.

</details>

- 조건절에 일치하는 파티션 파일만 선별 스캔하는 **파티션 프루닝(Partition Pruning)**
- `DROP/TRUNCATE PARTITION`을 통한 **대용량 이력 데이터 초고속 수명주기 관리**
- 파티션별로 독립적인 B+Tree를 유지하는 **로컬 인덱스(Local Index) 기반 관리 편의성**

#### 한줄 요약
- 파티션 프루닝, 초고속 이력 삭제, 로컬 인덱스 독립 관리가 핵심이다.

## Ⅲ. 구조 및 구성요소

<details><summary>용어 설명</summary>

- **3대 파티셔닝 전략**: Range(연속 범위/날짜), Hash(해시 균등 분산), List(이산 코드값/지역).

</details>

| 파티셔닝 유형 | 분할 기준 키 (Partition Key) | 핵심 특징 및 적용 워크로드 |
|:---|:---|:---|
| Range (범위) | **날짜, 일자, 연도 (`created_at`)** | **시계열 로그, 매출 이력 데이터 (오래된 파티션 Drop 용이)** |
| Hash (해시) | **사용자 ID, 주문 번호 (`user_id`)** | **데이터가 특정 파티션에 치우치지 않고 균등하게 분산 필요 시** |
| List (목록) | **지역 코드, 사업부 코드 (`region`)** | **명확히 구분되는 불연속적 비즈니스 카테고리 분류 시** |
| Composite (복합) | **Range + Hash / Range + List** | 1차 기간 분할 후 2차 해시 분산으로 초대용량 테이블 관리 |

#### 한줄 요약
- 네 전략은 노리는 이득이 달라 Range는 수명주기 관리를, Hash는 부하 균등을, List는 업무 코드별 격리를 얻는 대신 각각 데이터 편향·범위 검색 불리·경계 관리 부담을 대가로 치른다.

## Ⅳ. 흐름도

<details><summary>용어 설명</summary>

- **Pruning 실행 과정**: SQL 조건절 파싱 $\to$ 파티션 메타데이터 대조 $\to$ 불필요 파티션 제외 $\to$ 대상 로컬 인덱스 스캔.

</details>

```text
클라이언트 SQL 질의 인입 (`SELECT * FROM Logs WHERE created_at BETWEEN '2026-08-01' AND '2026-08-31'`)
        │
   [조건절 파싱] 옵티마이저가 WHERE 절의 파티션 키(`created_at`) 조건 추출
        │
   [메타데이터 대조] 테이블의 파티션 경계값(Range: p_202608)과 질의 범위 대조
        │
   [파티션 프루닝] 2026년 8월 외 모든 과거/미래 파티션 세그먼트 물리 스캔 제외 (Pruned!)
        │
   [로컬 인덱스 스캔] `p_202608` 파티션의 로컬 B+Tree 인덱스만 접근하여 데이터 인출
        │
   클라이언트에 결과 반환 (디스크 I/O 95% 절감)
```

#### 한줄 요약
- 프루닝은 조건절에서 파티션 키를 읽어낼 수 있을 때만 작동하므로, 키에 함수를 씌우거나 조건에서 빠뜨리는 순간 분할해 둔 모든 파티션을 훑는 원래 비용으로 되돌아간다.

## Ⅴ. 종류 및 비교

<details><summary>용어 설명</summary>

- **Local Index vs Global Index**: 파티션별 독립 인덱스(Local)와 전체 테이블 통합 인덱스(Global).

</details>

| 비교 항목 | 로컬 파티션 인덱스 (Local Index) | 글로벌 파티션 인덱스 (Global Index) |
|:---|:---|:---|
| 인덱스 저장 구조 | **각 파티션 파일마다 독립적 B+Tree 유지** | 전체 파티션을 통합한 거대 B+Tree 유지 |
| 파티션 삭제(Drop) 시| **영향 없음 (해당 파티션 인덱스만 자동 소멸)**| **글로벌 인덱스 전체가 손상(Unusable)되어 재빌드 필요** |
| 파티션 키 미포함 질의| 모든 로컬 인덱스를 병렬 스캔해야 함 | 단일 인덱스 탐색으로 고속 처리 가능 |
| 실무 권장 표준 | **대부분의 OLTP 파티셔닝에서 표준 적용** | PK 보증 등 불가피한 경우에만 제한적 사용 |

#### 한줄 요약
- 파티션 수명주기 관리와 운영 안정성을 위해 로컬 인덱스를 기본 표준으로 사용한다.

## Ⅵ. 실무 고려사항 및 대책

<details><summary>용어 설명</summary>

- **Data Skew(데이터 편향)**: 특정 파티션 키(이벤트 날짜, 특정 고객 ID)에 데이터가 집중되어 특정 파티션 세그먼트만 비대해지는 현상.

</details>

| 문제 | 대책 | 효과 |
|:---|:---|:---|
| 파티션 키 조건 누락으로 모든 파티션 풀스캔 발생 | **조회 쿼리 WHERE 절에 파티션 키(`created_at`) 조건 강제** | Partition Pruning 100% 활성화 |
| 특정 날짜 트래픽 폭증으로 파티션 용량 편향(**Data Skew**) | **Range + Hash 복합 파티셔닝(Composite) 도입** | 파티션 간 디스크 저장 및 I/O 균등 분산 |
| 파티션 삭제 시 글로벌 인덱스 손상(Unusable) | **인덱스는 로컬 인덱스(Local Index) 생성을 표준 원칙 준수** | 파티션 Drop 시 무중단 서비스 유지 |
| 신규 파티션 사전 생성 누락으로 인한 Insert 에러 | **자동 파티션 증설 배치 또는 `MAXVALUE` 파티션 구성** | 배치 오류 사전 차단 |

#### 한줄 요약
- 파티션 키 조건 필수 포함, 복합 파티셔닝 편향 완화, 로컬 인덱스 표준화, 자동 증설 배치로 관리한다.

## Ⅶ. 결론

- 시계열 이력은 **Range**, 균등 분산은 **Hash 파티셔닝** 선택

#### 한줄 요약
- 테이블 파티셔닝은 단일 인스턴스 내에서 대용량 데이터를 물리적으로 분할하여 프루닝과 고속 수명주기 관리를 달성하는 핵심 물리 설계 기법이다.
