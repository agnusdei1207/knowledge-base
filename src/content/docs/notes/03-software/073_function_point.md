## Ⅰ. 개요

<details><summary>용어 설명</summary>

- **기능점수(Function Point)**: 사용자 관점에서 소프트웨어가 제공하는 논리적 기능의 크기를 측정하는 국제 표준(ISO/IEC 20926) 소프트웨어 규모 산정 기법.
- **5대 기능 유형(IFPUG)**: 데이터 기능 2종(ILF, EIF)과 트랜잭션 기능 3종(EI, EO, EQ).

</details>

- 정의/개념: 프로그래밍 언어와 무관하게 사용자 관점의 기능 요구량을 **데이터(ILF/EIF)와 트랜잭션(EI/EO/EQ)** 5대 유형으로 계량화하는 SW 규모 산정 기법
- 배경/필요성: 코드 라인 수(LOC) 기반 규모 산정의 **언어 종속성, 개발자 코딩 편차 및 구현 전 초기 예산 산정 불가 한계**

#### 한줄 요약
- 사용자 관점의 논리적 요구사항을 5가지 기능 유형으로 분류하여 소프트웨어 규모와 비용을 산정한다.

## Ⅱ. 특징

<details><summary>용어 설명</summary>

- **기술 독립성(Technology Independence)**: Java, Python, C 등 구현 언어에 구애받지 않고 동일한 요구사항에 대해 동일한 기능점수를 산출하는 특성.
- **미조정 기능점수(UFP)**: 5대 기능 유형의 식별된 복잡도 가중치를 합산한 순수 기능적 규모.

</details>

- 프로그래밍 언어 및 프레임워크에 영향을 받지 않는 **기술 독립적(Technology Independent) 측정**
- 데이터 기능(2종)과 트랜잭션 기능(3종)의 **5대 표준 기능 유형(IFPUG) 분류 체계**
- 한국소프트웨어산업협회(KOSA) **SW 사업 대가산정 가이드의 법정 표준 기준**

#### 한줄 요약
- FP는 언어와 기술에 독립적인 규모를 주는 대신 기능 판정과 복잡도 결정에 사람의 시간을 요구하므로, 객관성을 측정 공수로 사들인다.

## Ⅲ. 구조 및 구성요소

<details><summary>용어 설명</summary>

- **ILF vs EIF & EI vs EO vs EQ**: 내부 DB(ILF), 외부 참조 DB(EIF), 등록/수정(EI), 계산 출력(EO), 단순 조회(EQ).

</details>

```text
[기능점수(FP) 5대 기능 유형 아키텍처 구조]
|-- 데이터 기능 (Data Functions: 2종)
|   |-- 내부논리파일 (ILF: 시스템 경계 내부에서 유지·관리하는 DB 엔티티 테이블)
|   `-- 외부연계파일 (EIF: 타 시스템에서 관리되며 본 시스템은 참조만 수행하는 파일)
`-- 트랜잭션 기능 (Transaction Functions: 3종)
    |-- 외부입력 (EI: 외부에서 유입되어 내부 ILF를 추가, 수정, 삭제하는 트랜잭션)
    |-- 외부출력 (EO: 내부 데이터를 가공, 계산, 파생 공식을 거쳐 외부로 전송/출력)
    `-- 외부조회 (EQ: 계산/가공 없이 단순 검색하여 화면에 표시하는 트랜잭션)
```

선의 의미: 계층 및 시스템 경계 내 데이터/트랜잭션 기능 분류

| 구성요소 | 책임 |
|:---|:---|
| 내부논리파일 | 경계 내부의 **데이터 유지·관리** |
| 외부연계파일 | 외부 소유 데이터의 **참조** |
| 외부입력 | 내부 데이터의 **생성·수정·삭제** |
| 외부출력 | 계산·파생 결과의 **외부 출력** |
| 외부조회 | 가공 없는 **단순 조회·전달** |

#### 한줄 요약
- 다섯 기능 유형은 데이터를 보관하는 축과 데이터를 통과시키는 축으로 나뉘므로, 어느 축에 속하는지를 먼저 정해야 복잡도 판정이 일관된다.

## Ⅳ. 흐름도

<details><summary>용어 설명</summary>

- **DET / RET / FTR**: 데이터 요소 수(DET: 필드 수), 레코드 요소 수(RET: 엔티티 테이블 수), 파일 참조 수(FTR: 연관된 ILF/EIF 수).

</details>

```text
애플리케이션 측정 경계(System Boundary) 식별
        │
   요구사항 명세서로부터 데이터 기능(ILF, EIF) 및 트랜잭션 기능(EI, EO, EQ) 도출
        │
   각 기능별 DET, RET, FTR 수를 계수하여 복잡도(단순/보통/복잡) 및 가중치 매핑
        │
   미조정 기능점수(UFP) 합산: $\text{UFP} = \sum (\text{기능 개수} \times \text{가중치})$
        │
   비기능 보정계수(연계 복잡성, 성능, 보안 요구)를 반영하여 최종 보정 FP 및 개발비 산정
```

#### 한줄 요약
- 경계 식별이 잘못되면 이후 기능 도출과 가중치가 모두 어긋나므로, 가장 앞 단계의 판정이 산정 전체의 정확도를 결정한다.

## Ⅴ. 종류 및 비교

<details><summary>용어 설명</summary>

- **간이법 vs 정밀법**: 기획/발주 단계에서 평균 가중치를 쓰는 간이법과 상세 설계 후 DET/RET를 하나하나 세는 정밀법.

</details>

| 비교 항목 | 간이 기능점수 산정법 (Estimated FP) | 정밀 기능점수 산정법 (Detailed FP) |
|:---|:---|:---|
| 적용 단계 | **사업 기획, 예산 수립, 발주 제안 단계** | **상세 설계 완료 후 또는 최종 대금 정산 단계** |
| 복잡도 산정 방식 | **기능 유형별 표준 평균 가중치(Average) 일괄 적용** | **실제 DET, RET, FTR 계수 후 복잡도 매트릭스 대입** |
| 장점 | 상세 설계서 없이 요구사항 목록만으로 신속 산정 | 실제 개발량에 가장 근접한 정확한 대가 산출 |
| 단점 | 상세 명세 부재로 $\pm 10\sim 20\%$ 오차 가능 | 화면설계서, ERD 전수 분석 공수 과다 소요 |

#### 한줄 요약
- 기획 단계에서는 신속한 간이법, 설계 완료 후에는 정밀법으로 정확한 대가를 정산한다.

## Ⅵ. 실무 고려사항 및 대책

<details><summary>용어 설명</summary>

- **KOSA 대가산정 가이드**: 한국소프트웨어산업협회가 매년 고시하는 기능점수당 단가(약 55만 원/FP)와 규모/연계/보안 보정 계수.

</details>

| 문제 | 대책 | 효과 |
|:---|:---|:---|
| 사업 초기 상세 설계서 부재로 정밀 측정 불가 | **기획 단계 간이법(평균 가중치)으로 예산 확보 후 사후 정산** | 공공 예산 편성의 적시성 확보 |
| 산정자 주관에 따른 기능 유형 오분류(EO vs EQ) | **파생/계산 로직 유무 기준(있으면 EO, 없으면 EQ) 명확화** | 산정 결과의 객관성 및 공신력 확보 |
| 비기능적 품질 요구(보안, 성능) 공수 미반영 | **보정계수(품질, 연계, 다중 사이트)를 합성하여 최종 FP 산출** | 개발비 현실화 및 납품 분쟁 예방 |
| 코드 제너레이터(CRUD 자동생성)로 인한 원가 왜곡 | **자동화 도구 적용 영역에 대한 생산성 할인 계수 적용** | 예산 낭비 차단 및 공정 계약 체결 |

#### 한줄 요약
- FP는 언어 독립적 비교를 얻는 대신 측정에 사람의 판정과 시간을 요구하므로, 초기에는 간이법으로 속도를 사고 명세가 확정되면 정밀법으로 정확도를 되사는 2단계 운용이 현실적이다.

## Ⅶ. 결론

- 공공 SW 사업 및 엔터프라이즈 프로젝트 대가 산정의 **국제 표준(ISO/IEC 20926) 및 국가 공인 법정 규모 측정 척도**로 확립되었으며, 실무 운영 시에는 **사업 기획 및 발주 단계에서는 평균 복잡도 기반의 간이법으로 신속하게 예산을 수립하고, 상세 설계 이후에는 DET/RET/FTR 실측 기반의 정밀법으로 사후 정산하며, 비기능 요구사항(연계·성능·보안) 보정계수를 필수 적용**하여 적정 사업 대가를 보장

#### 한줄 요약
- 기능점수(FP)는 개발 언어의 왜곡 없이 사용자 관점의 가치를 기준으로 소프트웨어 규모와 비용을 산정하는 핵심 소프트웨어 공학 척도다.
