## Ⅰ. 개요

<details><summary>용어 설명</summary>

- **데이터 및 트랜잭션 기능(ILF/EIF & EI/EO/EQ)**: 내부 논리 파일(ILF), 외부 연계 파일(EIF)의 데이터 기능과 외부 입력(EI), 외부 출력(EO), 외부 조회(EQ)의 트랜잭션 기능 5대 분류.
- **LOC 왜곡 및 사업 대가 산정 불가(LOC Distortion & Sizing Limit)**: 프로그래밍 언어의 표현력 차이로 인한 코드 라인 수 왜곡과 개발 초기 단계에서 비용 산정이 불가능한 한계.

</details>

- 정의/개념: 프로그래밍 언어와 무관하게 사용자 관점의 논리적 기능 요구량을 **데이터(ILF/EIF)와 트랜잭션(EI/EO/EQ)** 5대 유형으로 계량화하는 SW 규모 산정 기법
- 배경/필요성: 소스코드 라인수(LOC) 기반 산정 시 발생하는 **개발 언어별 왜곡 및 설계 초기 단계 사업 대가 산정 불가 한계** 직면

#### 한줄 요약

- 사용자 관점의 논리적 기능 요구사항을 5가지 기능 유형으로 분류하여 소프트웨어 규모와 사업 대가를 산정

## Ⅱ. 특징

<details><summary>용어 설명</summary>

- **기술 독립성(Technology Independence)**: Java, Python, C 등 사용 언어 및 프레임워크와 무관하게 동일한 기능 명세에 대해 일관된 규모 점수를 산출하는 특성.
- **미조정 기능점수(UFP, Unadjusted Function Point)**: 5대 기능 유형의 개수에 복잡도 가중치를 곱하여 단순 합산한 순수 기능 규모 점수.

</details>

- 개발 언어 및 하드웨어 환경에 영향을 받지 않는 **기술 독립적(Technology Independent) 측정**
- 데이터 기능(2종) 및 트랜잭션 기능(3종)의 **5대 표준 기능 유형(IFPUG) 분류**
- 국가 공공 소프트웨어 사업 대가 산정 가이드의 **법정 표준 규모 산정 기준 적용**

#### 한줄 요약

- 기술 독립적인 5대 기능 유형 분류와 복잡도 가중치 매트릭스를 통해 공학적이고 일관된 규모를 도출

## Ⅲ. 구조 및 구성요소

<details><summary>용어 설명</summary>

- **시스템 측정 경계(Application Boundary)**: 측정 대상 애플리케이션과 외부 사용자/타 시스템을 구분하는 논리적 경계.

</details>

```text
[ 기능점수(FP) 5대 기능 유형 아키텍처 구조도 ]

               ┌──────────────────────────────────────────────┐
               │    시스템 측정 경계 (System Boundary)         │
               │                                              │
  [사용자] ──► │ 1. 외부 입력 (EI: 데이터 등록/수정/삭제)      │ ──► [내부논리파일 (ILF)]
               │ 2. 외부 출력 (EO: 파생/계산 데이터 출력)     │
  [사용자] ◄── │ 3. 외부 조회 (EQ: 단순 데이터 검색 및 표시)  │ ◄── [ILF / EIF]
               │                                              │
               │ 4. 내부 논리 파일 (ILF: 자체 관리 DB 테이블) │
               └──────────────────────┬───────────────────────┘
                                      │ (참조)
                                      ▼
               ┌──────────────────────────────────────────────┐
               │ 5. 외부 연계 파일 (EIF: 타 시스템 참조 파일) │
               └──────────────────────────────────────────────┘
```

선의 의미: 시스템 경계를 기준으로 트랜잭션 기능(EI, EO, EQ)과 데이터 저장소(ILF, EIF) 간의 데이터 흐름 및 참조 관계.

| 구성요소 | 책임 |
|:---|:---|
| 내부 논리 파일 (ILF) | 애플리케이션 경계 내에서 유지·관리되는 **핵심 비즈니스 논리 데이터 저장소** |
| 외부 연계 파일 (EIF) | 타 시스템에서 관리되며 본 시스템은 **참조 목적으로만 활용하는 인터페이스 파일** |
| 외부 입력 (EI) | 경계 외부에서 유입되어 **내부 ILF를 추가, 수정, 삭제하는 트랜잭션 기능** |
| 외부 출력 (EO) | 내부 데이터를 가공, 계산, 파생 알고리즘을 거쳐 **외부로 전송하는 트랜잭션 기능** |
| 외부 조회 (EQ) | 수학적 연산이나 파생 없이 **단순 검색하여 화면에 표시하는 트랜잭션 기능** |

#### 한줄 요약

- 데이터 기능(ILF/EIF)과 트랜잭션 기능(EI/EO/EQ)으로 분리하여 소프트웨어의 논리적 규모를 측정

## Ⅳ. 흐름도

<details><summary>용어 설명</summary>

- **DET, RET, FTR**: 데이터 요소 수(DET: 필드 수), 레코드 요소 수(RET: 서브 엔티티 수), 참조 파일 수(FTR)로 복잡도를 결정하는 3대 인자.

</details>

```text
[ 기능점수(FP) 산정 5단계 파이프라인 ]

 ┌────────────────────────────────────────┐
 │ 1. 경계 식별: 측정 목적 및 범위 확정   │
 └───────────────────┬────────────────────┘
                     │
                     ▼
 ┌────────────────────────────────────────┐
 │ 2. 기능 분류: ILF/EIF 및 EI/EO/EQ 식별 │
 └───────────────────┬────────────────────┘
                     │
                     ▼
 ┌────────────────────────────────────────┐
 │ 3. 복잡도 평가: DET/RET/FTR 가중치 매핑 │
 └───────────────────┬────────────────────┘
                     │
                     ▼
 ┌────────────────────────────────────────┐
 │ 4. UFP 합산: 미조정 기능점수 계산      │
 └───────────────────┬────────────────────┘
                     │
                     ▼
 ┌────────────────────────────────────────┐
 │ 5. 보정 및 대가 산정: 최종 개발비 산출 │
 └────────────────────────────────────────┘
```

### 동작 원리

1. 경계 식별: 측정 대상 시스템의 논리적 범위와 외부 연계 인터페이스 경계를 설정.
2. 기능 분류: 요구사항 명세서로부터 데이터 기능(ILF, EIF)과 트랜잭션 기능(EI, EO, EQ)을 도출.
3. 복잡도 평가: 각 기능별 DET, RET, FTR 개수를 계수하여 단순/보통/복잡 가중치를 부여.
4. UFP 합산: 기능 유형별 개수와 가중치를 곱하여 미조정 기능점수(UFP)를 산출.
5. 보정 및 대가 산정: 비기능 보정계수(품질, 연계, 보안)를 반영하여 최종 보정 기능점수 및 사업 대가를 확정.

#### 한줄 요약

- 경계 식별 $\to$ 기능 분류 $\to$ 복잡도 평가 $\to$ UFP 합산 $\to$ 대가 산정의 5단계 절차로 진행

## Ⅴ. 종류 및 비교

<details><summary>용어 설명</summary>

- **간이법 vs 정밀법(Average Weight vs Detailed FP)**: 기획/발주 단계에서 평균 가중치를 적용하는 간이법과 상세 설계 단계에서 DET/RET를 정밀 계수하는 정밀법.

</details>

| 구분 | 간이 기능점수 산정법 (Estimated FP) | 정밀 기능점수 산정법 (Detailed FP) |
|:---|:---|:---|
| **적용 기준** | 사업 기획, 예산 수립, 발주 공고 단계 | 상세 설계 완료 후 또는 최종 대금 정산 단계 |
| **핵심 특징** | **기능 유형별 표준 평균 가중치(Average Weight) 적용** | **실제 DET, RET, FTR 계수 후 복잡도 매트릭스 대입** |
| **한계** | 상세 명세 부재로 인한 산정 오차 존재 가능 | 상세 설계서 분석에 따른 많은 시간과 공수 소요 |

#### 한줄 요약

- 기획 단계에서는 신속한 간이법으로 예산을 확보하고, 설계 완료 후에는 정밀법으로 정확한 대가를 정산

## Ⅵ. 실무 고려사항 및 대책

<details><summary>용어 설명</summary>

- **SW 대가산정 가이드(KOSA Guide)**: 한국소프트웨어산업협회가 공표하는 기능점수당 단가(FP 단가)와 보정계수 기준.

</details>

| 문제 | 대책 | 효과 |
|:---|:---|:---|
| 프로젝트 초기 상세 설계서 부재로 정밀 측정 불가 | **기획 단계 간이법(평균 가중치)으로 예산 수립 후 사후 정산** | 예산 편성의 적시성 확보 |
| 산정자의 주관적 판단에 따른 기능 유형 분류 왜곡 | **KOSA 표준 가이드라인 준수 및 공인 FP 심사원 교차 검증** | 산정 결과의 객관성 및 공신력 확보 |
| 비기능 요구사항(보안, 성능)의 개발 공수 미반영 | **규모 점수에 비기능 보정계수(연계 복잡성, 성능 요구) 합성** | 개발 비용 현실화 및 납품 분쟁 방지 |

#### 한줄 요약

- 간이법-정밀법 연계, 교차 검증, 비기능 보정계수 적용으로 신뢰성 높은 사업 대가를 산정

## Ⅶ. 결론

<details><summary>용어 설명</summary>

- **소프트웨어 규모 자산화(Software Sizing Asset)**: 축적된 기능점수 데이터를 기반으로 향후 유사 프로젝트의 생산성과 원가를 예측하는 데이터베이스.

</details>

- **기능점수(FP)** 는 공공 및 민간 소프트웨어 사업의 공정한 대가 산정과 생산성 관리의 표준 척도이며, 지속적인 측정 데이터 자산화를 통해 소프트웨어 공학적 원가 관리 체계를 완성해야 함

#### 한줄 요약

- 5대 기능 유형 기반의 정량적 측정을 통해 합리적인 개발 대가를 산정하고 프로젝트 예산을 통제
