## Ⅰ. 개요

<details><summary>핵심 용어</summary>

- **Function Point (FP, 기능점수)**: 개발 언어나 구현 기술에 독립적으로, 최종 사용자가 요구하는 소프트웨어의 논리적 기능 규모(Functional Size)를 5가지 표준 기능 유형으로 분류 및 수치화하여 SW 개발 대가 및 비용을 산정하는 국제 표준(ISO/IEC 14143) 규모 측정 단위.
- **IFPUG (International Function Point Users Group)**: 기능점수 산정 가이드라인(CPM: Counting Practices Manual)을 정립 및 유지 관리하는 세계 최대의 기능점수 국제 표준 단체.
- **Unadjusted Function Point (UFP, 미조정 기능점수)**: 소프트웨어의 5가지 데이터/트랜잭션 기능 유형의 복잡도 가중치를 단순 합산한 순수 기능 규모 점수.

</details>

- 정의/개념: 소프트웨어 개발 언어나 프레임워크와 무관하게 사용자 관점의 논리적 기능 요구사항을 5가지 기능 유형(EI, EO, EQ, ILF, EIF)으로 정량 측정하여 SW 규모를 산정하는 표준 기법인 **Function Point (FP)**
- 배경/필요성: 코드량 기반 규모는 **언어•구현 방식**에 따라 편차 발생

#### 한줄 요약

- 소프트웨어의 사용자 기능 유형과 가중치에 기반한 기능점수 측정이 핵심이다.

## Ⅱ. 특징

<details><summary>핵심 용어</summary>

- **Technology-Independent Metric**: C, Java, Python 등 프로그래밍 언어나 DB 종류에 영위받지 않고 순수 사용자 기능 명세서만으로 획득 가능한 기술 독립적 단위.
- **5 Function Types (5가지 기능 유형)**: 데이터 기능 2가지(ILF, EIF) 및 트랜잭션 기능 3가지(EI, EO, EQ).

</details>

- **Technology-Independent (기술 독립적 사용자 관점 측정)**
- 5가지 표준 기능 유형 (**EI, EO, EQ, ILF, EIF**) 분류
- 한국 소프트웨어 사업 대가 산정 가이드의 규모 산정 방식

#### 한줄 요약

- 기술 독립적 사용자 기능의 다섯 유형이 핵심이다.

## Ⅲ. 구조 및 구성요소

<details><summary>핵심 용어</summary>

- **Data Functions (데이터 기능)**: 시스템 내부/외부에 저장되어 사용자가 참조/관리하는 파일로, ILF와 EIF로 구성.
- **Transactional Functions (트랜잭션 기능)**: 시스템 경계(Boundary)를 넘어 입출력/조회를 수행하는 기능으로, EI, EO, EQ로 구성.

</details>

```text
               ┌──────────────────────────────────────────────┐
               │    System Boundary (시스템 측정 경계)         │
               │                                              │
 [External] ──►│ 1. External Input (EI: 데이터 입력/변경)     │──► [ILF]
               │ 2. External Output (EO: 연산/파생 데이터 출력)│
 [External] ◄──│ 3. External Inquiry (EQ: 단순 조회 및 출력)  │◄── [ILF / EIF]
               │                                              │
               │ 4. Internal Logical File (ILF: 내부 논리파일)│
               └──────────────────────┬───────────────────────┘
                                      │ (참조)
                                      ▼
               ┌──────────────────────────────────────────────┐
               │ 5. External Interface File (EIF: 외부 연계)  │
               └──────────────────────────────────────────────┘
```

선의 의미: 시스템 경계 안에서 트랜잭션 기능(EI, EO, EQ)이 수행되고, 내부 논리 데이터(ILF)와 외부 참조 데이터(EIF)를 읽고 쓰는 입출력 아키텍처.

| 구분 (Category) | 기능 유형 명칭 | 설명 및 기능적 정의 | 가중치 범위 (단순/보통/복잡) |
|:---|:---|:---|:---|
| **Data Functions** | **ILF (Internal Logical File)** | 애플리케이션 내부에서 유지/관리되는 논리적 데이터 그룹 (e.g., 회원 DB 테이블) | **7 / 10 / 15** |
| | **EIF (External Interface File)** | 타 시스템에 존재하며 내 시스템이 '참조'만 하는 논리 파일 (e.g., 타사 카드사 인증 테이블) | **5 / 7 / 10** |
| **Transactional**| **EI (External Input)** | 외부에서 유입된 데이터로 내부 ILF를 추가/수정/삭제하는 입력 기능 | **3 / 4 / 6** |
| | **EO (External Output)** | 내부 데이터를 가공/계산/파생하여 외부로 출력하는 기능 (e.g., 통계 리포트) | **4 / 5 / 7** |
| | **EQ (External Inquiry)** | 수학적 연산/가공 없이 단순히 데이터를 조회하여 보여주는 기능 (e.g., 마이페이지 조회) | **3 / 4 / 6** |

#### 한줄 요약

- 트랜잭션 기능과 데이터 기능으로 나뉘는 다섯 기능 유형 구조가 핵심이다.

## Ⅳ. 흐름도

<details><summary>핵심 용어</summary>

- **DET, RET, FTR (복잡도 측정 요소)**: DET(Data Element Type: 식별 가능한 필드 수), RET(Record Element Type: 서브 데이터 그룹 수), FTR(File Type Referenced: 참조 논리 파일 수).

</details>

```text
┌──────────────────────────────┐
│ 1. 측정 유형 & 경계(Boundary)│
└──────────────┬───────────────┘
               ▼
┌──────────────────────────────┐
│ 2. 데이터 기능 식별 (ILF/EIF) │
│ 3. 트랜잭션 기능 식별(EI/EO/EQ)│
│ 4. DET / RET / FTR 복잡도 산정│
│ 5. 미조정 기능점수 (UFP) 합산 │
│ 6. 규모•비용 산정 근거 기록  │
└──────────────┬───────────────┘
               ▼
     [SW 개발비 산정 완결]
```

### 동작 원리

1. **측정 유형•경계 정의**: 목적과 애플리케이션 경계 확정.
2. **데이터 기능 식별**: ILF•EIF의 논리 데이터 그룹 판정.
3. **트랜잭션 기능 식별**: EI•EO•EQ의 독립 처리 판정.
4. **복잡도•가중치 산정**: DET•RET•FTR로 복잡도 결정.
5. **미조정 기능점수 합산**: 유형별 개수와 가중치 곱 합산.
6. **규모•비용 산정 근거 기록**: 포함•제외와 판정 근거 보관.

#### 한줄 요약

- 경계•유형•복잡도 기반 기능점수 산정 흐름이 핵심이다.

## Ⅴ. 종류 및 비교

<details><summary>핵심 용어</summary>

- **Indicative / Estimated FP (간이법)**: 기획/분석 단계에서 상세 DET/RET/FTR 정보 없이 기능 유형별 평균 가중치(Average Weight)를 적용하여 빠르게 예산을 산정하는 방식.

</details>

| 비교 항목 | 간이 기능점수 산정법 (Indicative / Estimated) | 정밀 기능점수 산정법 (Detailed FP) |
|:---|:---|:---|
| 수행 시점 | **프로젝트 기획, 예산 수립, 제안 단계** | **상세 설계 완결 시점, 최종 대금 정산 시점** |
| 복잡도 측정 | DET, RET, FTR 산정 없이 **평균 가중치 적용** | **실제 DET, RET, FTR 계수 후 복잡도 매트릭스 대입**|
| 소요 시간 | 매우 빠름 | 상대적으로 느림 (상세 명세 분석 필요) |
| 산정 불확실성 | 상세 정보 부족으로 분류 편차 증가 | 상세 기능 근거로 분류 편차 축소 |

#### 한줄 요약

- 구현 전 규모는 기능점수, 구현 후 코드량은 코드 줄 수로 측정한다.

## Ⅵ. 실무 고려사항 및 대책

<details><summary>핵심 용어</summary>

- **SW 대가 산정 가이드**: 한국소프트웨어산업협회(KOSA)에서 매년 개정 발표하는 공공 IT 사업 FP 당 단가(e.g., FP당 약 55만원선) 및 보정계수 지침.

</details>

| 문제 | 대책 | 효과 |
|:---|:---|:---|
| 프로젝트 초기 상세 설계서가 없어 정밀 FP 측정 불가 | **기획 단계에서는 간이 기능점수 산정법으로 예산 확보 후 정산**| 예산 적시성 확보 |
| 개발자의 코딩 스킬이나 프레임워크 오버헤드 반영 불가 | **규모(FP) + 비기능 요구사항 보정계수(보안, 성능) 합성** | 사업 대가 현실화 |
| 측정자(산정인)의 주관에 따라 기능 유형 분류가 왜곡 | **KOSA 표준 가이드라인 및 전문 FP 심사자 검증** | 객관적 산정 공신력 |

> 사례: **공공기관 대형 IT 시스템 구축 사업 RFP 내 기능점수(FP) 기반 대가 산정**

#### 한줄 요약

- 측정 목적, 시스템 경계, 독립 처리에 기반한 편차 통제가 핵심이다.

## Ⅶ. 결론

<details><summary>핵심 용어</summary>

- **기능점수 산정 수립 기준(Function Point Standards)**: KOSA SW 대가 산정 가이드, IFPUG CPM 4.3.1 표준 및 공공사업 계약 법률에 의거한 체계.

</details>

- 초기 예산은 **간이법**, 상세 기능 확정 후 **정밀법**으로 재산정

#### 한줄 요약

- 경계•유형•복잡도 근거 기반 기능점수 확정이 핵심이다.
