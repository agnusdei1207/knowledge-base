## Ⅰ. 개요

<details><summary>용어 설명</summary>

- **VEX(Vulnerability Exploitability eXchange)**: 제품별 취약점 영향 상태와 판단 근거를 기계 판독 문서로 교환하는 체계.
- **Product Status**: Affected, Not Affected, Fixed, Under Investigation 등 제품별 대응 상태.
- **Justification**: 취약 코드 부재, 실행 불가, 완화 적용 등 Not Affected 판단 근거.

</details>

- 정의/개념: 제품별 취약점 영향•조치 상태를 교환하는 **VEX**
- 배경/필요성: SBOM•CVE 일치만으로는 **실행 가능성•제품 영향** 판정 불가

#### 한줄 요약

- 부품표가 취약 후보를 찾으면 VEX가 제품별 실제 영향과 조치 상태를 설명한다.

## Ⅱ. 특징

<details><summary>용어 설명</summary>

- **Reachability Analysis (도달성 분석)**: 취약 함수가 실제 실행 경로에서 호출 가능한지 분석하는 기법.

</details>

- **제품 Version•Digest**에 취약점 상태를 결속
- Not Affected는 **Justification**•**Evidence**를 함께 제공
- 새 분석•Patch•배포에 따라 **상태 수명주기** 갱신

#### 한줄 요약

- 영향 없음은 선언이 아니라 제품 식별자와 도달성 근거가 연결된 검증 가능한 상태다.

## Ⅲ. 구조 및 구성요소

<details><summary>용어 설명</summary>

- **CSAF(Common Security Advisory Framework)**: 보안 권고와 제품별 취약점 상태를 JSON으로 교환하는 OASIS 표준.

</details>

```text
[VEX Document]
 ├── [Product ID]
 ├── [Vulnerability ID]
 ├── [Product Status]
 └── [Justification•Action]
```

| 구성요소 | 책임 |
|---|---|
| Product ID | 제품 Version•Digest의 **판정 대상** 식별 |
| Vulnerability ID | CVE 등 **취약점 기준 Key** 제공 |
| Product Status | **Affected•Not Affected•Fixed** 상태 표현 |
| Justification•Action | 판단 근거와 **완화•Patch 조치** 전달 |

#### 한줄 요약

- 제품과 취약점의 조합마다 상태·근거·조치를 기록해야 자동 정책에 사용할 수 있다.

## Ⅳ. 흐름도

<details><summary>용어 설명</summary>

- **VEX Lifecycle**: 취약점 후보 탐지부터 영향 분석, 문서 발행, 조치와 재평가까지의 상태 관리 절차.

</details>

```text
[취약점 후보 탐지]
      │
      ▼
1. 제품•Component 식별
      │
      ▼
2. 도달성•구성 분석
      │
      ▼
3. Product Status 결정
      │
      ▼
4. VEX 서명•발행
      │
      ▼
5. Patch•완화•재평가
      │
      ▼
[대응 상태 반환]
```

### 동작 원리

1. **제품•Component 식별**: SBOM과 배포 Digest로 대상 확정
2. **도달성•구성 분석**: 취약 코드•호출 경로•완화 상태 검증
3. **Product Status 결정**: 영향•조치 상태와 근거 승인
4. **VEX 서명•발행**: 책임 주체와 무결성 증적 제공
5. **Patch•완화•재평가**: 배포 확인과 새 정보 반영

#### 한줄 요약

- 취약 후보를 제품별로 분석하고 서명된 상태를 배포 확인까지 계속 갱신한다.

## Ⅴ. 종류 및 비교

<details><summary>용어 설명</summary>

- **CycloneDX VEX**: CycloneDX BOM 안팎에서 취약점 분석 상태를 표현하는 방식.

</details>

| 비교 항목 | CSAF VEX | CycloneDX VEX |
|---|---|---|
| 중심 목적 | 보안 권고와 제품 상태 교환 | **BOM•취약점 분석 통합** |
| 문서 관계 | SBOM과 독립 문서 발행 | BOM 내장•외부 BOM 가능 |
| 적용 판단 | 다수 제품 권고 배포 | 개발•AppSec Pipeline 연계 |

#### 한줄 요약

- 권고 유통은 CSAF, BOM 중심 개발 파이프라인은 CycloneDX 연계를 우선 검토한다.

## Ⅵ. 실무 고려사항 및 대책

<details><summary>용어 설명</summary>

- **Trust Evidence (신뢰 증거)**: 상태 판정의 제품 Digest, 분석 결과, 책임자, 시각, 서명을 묶은 감사 자료.

</details>

| 난제 | 원인 | 대책 |
|---|---|---|
| 거짓 Not Affected | 책임 회피성 상태 선언 | **도달성 Evidence•책임자 서명** 요구 |
| 제품 식별 불일치 | 이름만으로 Version Mapping | **purl•Digest•SBOM Serial** 결속 |
| Fixed 배포 누락 | 문서만 갱신하고 운영 미반영 | **배포 자산 Version•재검사** 연계 |

#### 한줄 요약

- 영향 없음과 조치 완료는 서명 문서뿐 아니라 실제 배포 제품의 증거로 다시 확인한다.

## Ⅶ. 결론

<details><summary>용어 설명</summary>

- **Risk Prioritization (위험 우선순위화)**: 제품 영향과 악용 가능성, 노출도, 업무 중요도를 결합해 조치 순서를 정하는 활동.

</details>

- 근거 없는 상태는 **보류**, 서명•Digest•도달성 증거가 있으면 VEX 반영

#### 한줄 요약

- 검증 가능한 VEX만 정책에 반영하고 영향 제품은 패치·완화·배포 확인까지 추적한다.
