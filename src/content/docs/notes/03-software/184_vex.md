## Ⅰ. 개요

<details><summary>핵심 용어</summary>

- **VEX (Vulnerability Exploitability eXchange, 취약점 악용 가능성 교환)**: SBOM을 통해 발견된 취약점(CVE)이 해당 소프트웨어 제품에서 **실제로 악용 가능한지(Exploitable)** 여부와 그 기술적 근거를 기계 판독 가능한 포맷(Machine-Readable)으로 제공하는 보안 권고 명세서.
- **False Positive (오탐지 / 과잉 경보)**: 보안 스캐너가 취약한 라이브러리가 포함되어 있다는 이유만으로 경보를 울렸으나, 실제로는 해당 취약 코드가 호출되지 않아 안전한 상태. VEX가 해결하려는 핵심 문제.
- **NTIA (국가통신정보청)**: 소프트웨어 공급망 보안을 강화하기 위해 SBOM과 더불어 VEX 개념과 최소 요건을 정의하고 업계 도입을 주도한 미국 정부 산하 기관.

</details>

- 정의/개념: "취약한 부품(컴포넌트)을 사용하고 있지만, 우리 제품에서는 그 취약점이 발현되지 않는다"는 것을 기술적으로 증명하여 취약점 관리의 노이즈를 제거하는 **취약점 상태 판별 문서**
- 배경/필요성: 현대 소프트웨어 구성요소 중 취약점이 있는 라이브러리가 포함되더라도, 실제 그 취약 코드가 실행(Reachability)되는 비율은 5% 미만이므로, 보안팀의 피로도(Alert Fatigue)를 줄이고 진짜 위험한 패치에 집중할 우선순위화 기법 요구성

#### 한줄 요약

- SBOM이 문제 부품의 포함 여부를 알려 준다면 VEX는 그 부품의 취약 코드가 이 제품에서 실제 실행되는지 증거와 함께 알려 준다.

## Ⅱ. 특징 (VEX의 4대 핵심 상태값 - Status)

<details><summary>핵심 용어</summary>

- **Not Affected (영향 없음)**: 취약점이 존재하는 라이브러리를 포함하고 있으나, 빌드 옵션, 실행 경로 부재, 인라인 완화 통제 등으로 인해 실제 해커가 악용할 수 없는 가장 중요한 VEX 상태 선언.

</details>

- **Not Affected (영향 없음)**: 해당 제품은 이 CVE의 영향을 받지 않으므로 패치가 불필요함 (개발사가 정당화 사유 필수 기재).
- **Affected (영향 있음)**: 취약점의 조치를 취해야 하며, 악용 가능한 상태이므로 즉각적인 패치나 워크어라운드(Workaround) 권고 필요.
- **Fixed (수정됨)**: 해당 버전에서는 이미 취약점이 패치되어 조치 완료된 상태.
- **Under Investigation (조사 중)**: 아직 해당 취약점이 우리 제품에 영향을 미치는지 분석이 끝나지 않은 대기 상태.

#### 한줄 요약

- 같은 취약 부품이 들어 있어도 빌드 옵션과 실행 경로가 다르면 제품별 영향 상태가 달라지므로 범위와 근거를 함께 기록한다.

## Ⅲ. 구조 및 구성요소 (VEX 문서의 표준 구조)

<details><summary>핵심 용어</summary>

- **Justification (정당화 사유)**: VEX 상태를 `Not Affected`로 선언할 때 반드시 기재해야 하는 기계 판독형 사유 코드. 예: `vulnerable_code_not_present`(취약 코드 미포함), `vulnerable_code_not_in_execute_path`(실행 경로 없음) 등.

</details>

```text
┌────────────────────────────────────────────────────────────────────────┐
│                        VEX Document Structure                          │
├────────────────────────────────────────────────────────────────────────┤
│ 1. [VEX Metadata] (발행자, 타임스탬프, VEX 문서 ID)                    │
│ 2. [Product Identification] (어떤 제품/버전/SBOM에 대한 명세인가?)     │
│ 3. [Vulnerability Identification] (어떤 CVE 취약점에 대한 판정인가?)   │
│ 4. [Status & Justification]                                            │
│      - Status: Not Affected                                            │
│      - Justification: vulnerable_code_not_in_execute_path              │
│      - Detail: "이 라이브러리는 테스트용으로만 컴파일되어 운영 제외됨" │
└────────────────────────────────────────────────────────────────────────┘
```

선의 의미: VEX 문서는 '어떤 제품(Product)'에 있는 '어떤 취약점(CVE)'이 '어떤 상태(Status)'이며, 그 '이유(Justification)'가 무엇인지 기계와 사람이 동시에 읽을 수 있게 연결한 메타데이터 집합체.

| 구성요소 | 핵심 역할 및 기능 | 스펙 및 속성 |
|:---|:---|:---|
| **VEX Metadata** | **문서의 신뢰성을 보장하는 식별 정보** | Author, Timestamp, Version |
| **Product ID** | **판정 대상이 되는 제품의 고유 식별자**| purl, CPE, SBOM 링크 |
| **Vulnerability**| **대상 취약점의 국제 표준 식별 번호** | CVE, GHSA ID |
| **Status / Justification**| **핵심 판정 결과와 기술적 정당화 사유 코드** | Not Affected + 이유 코드 |

#### 한줄 요약

- 제품 부품표와 취약점 목록을 맞춘 뒤 실행 가능성을 분석하고 책임자가 서명한 영향 상태를 운영 도구에 전달한다.

## Ⅳ. 흐름도 (SBOM과 VEX를 결합한 취약점 대응 흐름)

<details><summary>핵심 용어</summary>

- **Reachability Analysis (도달성 분석)**: 정적 분석(SAST) 및 동적 분석 기법을 통해, 클라이언트의 입력값이 취약한 라이브러리의 함수(Sink)까지 실제로 도달(호출)할 수 있는지 수학적/논리적으로 검증하는 과정.

</details>

```text
[소프트웨어 벤더사]                                [고객사 / 보안운영팀]
   │                                                 │
   ├─ 1. [SBOM 발행] ───────────────────────────────►│
   │                                                 ├─ 2. SCA 스캔 (취약점 CVE 100개 탐지)
   │                                                 │
   ├─ 3. [VEX 발행] (95개는 Not Affected, 5개 Affected) ─►│
   │                                                 │
   │                                                 ├─ 4. VEX 파싱 및 CVE 95개 경보 해제
   │                                                 │
   │                                                 ├─ 5. Affected 5개만 긴급 패치 작업(우선순위)
   │◄─ 6. (Affected 5개에 대한 패치 요청) ───────────┤
```

### 동작 원리

1. **탐지**: 고객사는 벤더가 준 SBOM을 스캔하여 `Log4j` 부품을 발견하고 즉각 경보(Alert)를 띄움.
2. **소명**: 벤더사는 자사 제품에서 `Log4j`가 어떻게 쓰이는지 도달성 분석(Reachability) 수행.
3. **VEX 발행**: "우리는 Log4j를 쓰지만, 취약한 `JNDILookup` 클래스는 컴파일 과정에서 제외(Strip)했다"는 정당화 코드를 담아 `Not Affected` 상태의 VEX 발행.
4. **대응**: 고객사의 보안 도구가 VEX를 읽어 경보를 끄고(Silence), 보안팀은 다른 위험한 작업에 집중 (**영향 평가 완결**).

#### 한줄 요약

- 취약 함수가 빌드에 없다는 증거를 책임자가 검토해 Not Affected로 발행하면 소비자는 그 제품만 패치 대기열에서 분리할 수 있다.

## Ⅴ. 종류 및 비교 (VEX 구현 포맷 1:1 비교)

<details><summary>핵심 용어</summary>

- **CSAF (Common Security Advisory Framework)**: OASIS 표준화 기구가 제정한 보안 권고(Advisory) 포맷으로, 사람이 읽던 PDF 보안 패치 안내문을 기계가 읽는 JSON으로 바꾼 범용 프레임워크 (VEX 프로파일을 포함).

</details>

| 비교 항목 | CSAF VEX | CycloneDX VEX |
|:---|:---|:---|
| **설계 목적** | **전통적인 '보안 권고문'의 디지털화 및 표준화**| **SBOM 포맷 내부에 취약점 정보를 통합 관리** |
| **운영 방식** | SBOM 파일과 **독립적인 별개의 문서**로 발행 | SBOM 파일 **내부에 직접 내장(Embedded)** 가능 |
| **주요 주체** | OASIS Open (보안 벤더 및 정부 기관 친화적) | OWASP (개발자 및 AppSec 친화적) |
| **장점** | 광범위한 보안 권고 체계 연동, VEX 특화 | SBOM 파이프라인 하나로 모든 공급망 보안 통제 |

#### 한줄 요약

- SBOM으로 후보 제품을 찾고 VEX로 실제 영향을 좁히며 보안 권고에서 패치와 완화 방법을 확인한다.

## Ⅵ. 실무 고려사항 및 대책 (VEX 실무 도입 3대 난제 대책)

<details><summary>핵심 용어</summary>

- **Trust Issue (신뢰성 문제)**: 벤더사가 패치하기 귀찮아서 임의로 모든 취약점을 `Not Affected`로 선언하는 악용 사례를 막기 위해, VEX 발행 주체의 서명(Signature)과 투명한 도달성 입증 자료를 요구하는 과제.

</details>

| 3대 VEX 실무 난제 | 발생 원인 | 실무 대책 및 해결방안 |
|:---|:---|:---|
| **1. 벤더사의 VEX 발행 거부**| 제조사의 보안 역량 부족 및 책임 회피 | **계약 시 SBOM 및 VEX 제출을 컴플라이언스 의무 조항화**|
| **2. Not Affected 신뢰성** | 거짓 해명으로 인한 보안 사각지대 발생 | **제품 해시 다이제스트 결속 및 정당화 사유(Justification) 강제**|
| **3. 동적 업데이트의 어려움**| 매일 쏟아지는 CVE에 대한 VEX 갱신 지연| **도달성 분석(Reachability Analysis) 툴 도입을 통한 자동화**|

> 사례: **미국 CISA 주도의 VEX 워킹그룹 가이드라인 및 오픈소스 보안 재단(OpenSSF)의 VEX 발행 자동화 파이프라인 도입 권고**

#### 한줄 요약

- Fixed 문서가 있어도 운영 자산이 수정 버전으로 배포됐는지 별도로 확인해야 실제 취약 제품이 남지 않는다.

## Ⅶ. 결론

<details><summary>핵심 용어</summary>

- **Alert Fatigue (경보 피로)**: 수천 개의 무의미한 취약점 경보로 인해 보안 담당자가 정작 중요한 위협을 놓치는 현상으로, VEX는 이를 해결하는 가장 강력한 백신(Vaccine).

</details>

- **VEX 반영 기준**에 따라 SBOM 도입 시 필연적으로 발생하는 오탐지(False Positive) 제거를 위해 **SCA 툴과 VEX 연동 자동화 체계** 필수 적용

#### 한줄 요약

- 영향 없음과 조치 완료는 제품 Digest·검증 증거·책임자 서명·배포 확인이 있을 때만 정책에 반영하고 새 정보가 나오면 재평가해야 한다.
