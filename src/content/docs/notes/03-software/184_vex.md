## Ⅰ. 개요

<details><summary>용어 설명</summary>

- **VEX (Vulnerability Exploitability eXchange)**: SBOM에 명시된 소프트웨어 컴포넌트에 취약점(CVE)이 존재하더라도, 실제 실행 환경에서 해당 코드가 실행될 수 있는지(Reachability) 여부와 악용 가능성 상태(Status)를 기계 판독 문서로 전달하는 보안 표준.
- **오탐 및 패치 피로(False Positive & Alert Fatigue)**: 단순히 취약한 라이브러리가 포함되어 있다는 이유만으로 실제 악용 불가능한 수백 건의 CVE에 대해 불필요한 패치 작업을 수행하느라 개발 생산성이 마비되는 위험.

</details>

- 정의/개념: SBOM에 포함된 오픈소스 컴포넌트의 취약점(CVE)이 **실제 런타임 환경에서 악용 가능한지 영향도와 상태를 명세**하는 보안 교환 규격
- 배경/필요성: 단순 라이브러리 버전 매칭으로 인한 **방대한 거짓 양성(False Positive) 경보 폭증 및 불필요한 패치 공수 낭비 위험** 직면

#### 한줄 요약

- 도달성 분석(Reachability)을 기반으로 CVE 취약점의 실제 악용 가능 여부(Affected / Not Affected)를 명시하여 보안 패치 효율을 극대화

## Ⅱ. 특징

<details><summary>용어 설명</summary>

- **4대 제품 상태(Product Status)**: Affected(실제 영향 있음), Not Affected(영향 없음), Fixed(패치 완료), Under Investigation(조사 중).
- **도달성 분석(Reachability Analysis)**: 정적/동적 호출 그래프(Call Graph)를 분석하여 취약한 함수가 실제 비즈니스 로직의 실행 경로에 포함되어 있는지 검증.

</details>

- 취약점의 실제 영향 여부를 판정하는 **4가지 표준 상태(Affected/Not Affected/Fixed/Investigating)**
- '영향 없음' 판정 시 구체적 이유를 제시하는 **정당화 사유(Justification: 코드 미포함, 완화 조치 등)**
- CSAF 및 CycloneDX 규격을 통한 **기계 판독 자동화 및 DevSecOps CI/CD 연동** #### 한줄 요약

- 취약점의 이론적 존재가 아닌 실제 런타임 악용 가능성을 증명하여 실질적인 위험 대응을 지원

## Ⅲ. 구조 및 구성요소

<details><summary>용어 설명</summary>

- **VEX 4대 핵심 구조**: Product ID(대상 제품), Vulnerability ID(CVE 번호), Product Status(영향 상태), Justification & Evidence(판단 근거).

</details>

```text
[ VEX(Vulnerability Exploitability eXchange) 데이터 모델 구조도 ]

 1. [ 대상 제품 식별자 (Product Identification) ]
    • purl: `pkg:npm/express@4.18.2`, 빌드 해시 Digest, SBOM Serial
                           │
                           ▼
 2. [ 취약점 식별자 (Vulnerability ID) ]
    • CVE-2023-12345, NVD CVSS Score
                           │
                           ▼
 3. [ 제품 상태 판정 (Product Status 4단계) ]
    ┌─────────────────────────────────────────────────────────────┐
    │  • not_affected (영향 없음)   • affected (실제 영향 받음)   │
    │  • fixed (패치 완료)          • under_investigation (조사중)│
    └────────────────────────────┬────────────────────────────────┘
                                 │
                                 ▼
 4. [ 정당화 사유 및 증거 (Justification & Evidence) ]
    • Justification: `code_not_reachable` (취약 함수 미호출)
    • Impact Statement: 네트워크 입력 차단 및 WAF 인라인 방어 증적
```

선의 의미: 제품과 CVE 취약점을 매핑하여 4대 상태 중 하나를 부여하고, Not Affected일 경우 정당화 근거를 첨부하는 구조.

| 구성요소 | 책임 |
|:---|:---|
| 제품 식별자 (Product ID) | VEX 상태가 적용되는 **소프트웨어 버전, 빌드 해시, 패키지 URL(purl) 특정** |
| 취약점 식별자 (Vuln ID) | 대응 대상이 되는 **CVE 번호 및 NVD 취약점 고유 식별자 제공** |
| 제품 상태 (Product Status) | Affected, Not Affected, Fixed, Under Investigation 등 **실제 영향 상태 표현** |
| 정당화 근거 (Justification) | Not Affected 판정 시 **취약 함수 미도달(code_not_reachable) 등 기술적 근거 명시** |

#### 한줄 요약

- 제품 ID, 취약점 ID, 제품 상태, 정당화 근거가 결합하여 VEX 명세서를 구성

## Ⅳ. 흐름도

<details><summary>용어 설명</summary>

- **VEX 발행 및 조치 5단계 수명주기**: 취약점 감지 $\to$ 도달성 분석 $\to$ 상태 판정 $\to$ VEX 문서 서명/발행 $\to$ 배포 및 재평가.

</details>

```text
[ VEX 기반 취약점 도달성 분석 및 조치 파이프라인 ]

 ┌────────────────────────────────────────┐
 │ 1. SBOM 기반 신규 CVE 취약점 후보 탐지│
 └───────────────────┬────────────────────┘
                     │
                     ▼
 ┌────────────────────────────────────────┐
 │ 2. 정적 호출 그래프 기반 도달성 분석 수행│
 └───────────────────┬────────────────────┘
                     │
                     ▼
 ┌────────────────────────────────────────┐
 │ 3. Product Status 및 Justification 확정│
 ├───────────────────┬────────────────────┤
 │ not_affected      │ affected           │
 │ 4A. 근거 문서화   │ 4B. 긴급 핫픽스    │
 │     VEX 발행      │     패치 개발      │
 └───────────────────┴────────────────────┘
                     │
                     ▼
 ┌────────────────────────────────────────┐
 │ 5. VEX 문서 전자서명 및 고객/운영 배포 │
 └────────────────────────────────────────┘
```

### 동작 원리

1. 취약점 감지: 사내 소프트웨어 SBOM에 포함된 라이브러리에서 신규 CVE-2023-XXXX가 탐지됨.
2. 도달성 분석: SAST 도구가 소스코드를 스캔하여 해당 취약 함수(`vulnerableMethod()`)가 실제 호출되는지 검증.
3. 상태 확정: 취약 함수가 호출 경로에 전혀 포함되지 않음을 확인하고 `not_affected` 상태로 판정.
4. 근거 작성: 정당화 사유로 `code_not_reachable`을 기재하고 보안 책임자의 승인 서명을 첨부.
5. VEX 배포: CSAF/CycloneDX JSON VEX 문서를 생성하고 서명하여 고객사 및 내부 운영팀에 배포함으로써 불필요한 패치 중단.

#### 한줄 요약

- 취약점 감지 $\to$ 도달성 분석 $\to$ 상태 판정 $\to$ 근거 작성 $\to$ VEX 배포의 5단계

## Ⅴ. 종류 및 비교

<details><summary>용어 설명</summary>

- **CSAF VEX vs CycloneDX VEX**: 전용 보안 권고 독립 문서 포맷(CSAF)과 SBOM 일체형 경량 포맷(CycloneDX).

</details>

| 구분 | CSAF VEX (OASIS 표준) | CycloneDX VEX (OWASP 표준) |
|:---|:---|:---|
| **적용 기준** | 보안 전담 조직, 글로벌 벤더의 대고객 보안 권고문 발행 | DevSecOps CI/CD 파이프라인, SBOM 통합 취약점 스캐닝 |
| **핵심 특징** | **독립된 JSON 보안 권고(Advisory) 포맷, 다수 제품 포괄** | **SBOM 문서 내에 VEX 데이터를 직접 임베딩하여 일원화** |
| **한계** | SBOM과 별도로 문서를 발행·관리해야 하는 오버헤드 | 복잡한 벤더 법적 권고문 서술에는 상대적으로 간결 |

#### 한줄 요약

- 대고객 권고는 CSAF VEX, 빌드 파이프라인 내장 처리는 CycloneDX VEX를 선택

## Ⅵ. 실무 고려사항 및 대책

<details><summary>용어 설명</summary>

- **증거 기반 VEX(Evidence-based VEX)**: 개발팀의 책임 회피성 '영향 없음' 선언을 방지하기 위해 호출 그래프 스캔 결과와 보안 책임자 전자서명을 의무화하는 통제.

</details>

| 문제 | 대책 | 효과 |
|:---|:---|:---|
| 개발팀의 패치 회피를 위한 무단 `not_affected` 허위 선언 | **도달성 호출 그래프(Call Graph) 증적 및 보안팀 전자서명 의무화** | 허위 판정 원천 차단 |
| 소프트웨어 버전 업데이트 시 이전 VEX 문서가 잘못 적용됨 | **`purl` 및 빌드 SHA-256 해시 기반의 1:1 불변 결속 검증** | 버전 불일치로 인한 보안 누락 방지 |
| `fixed` 상태로 VEX를 발행했으나 실제 릴리즈 배포가 누락됨 | **배포 파이프라인(CD)과 VEX 릴리즈 상태를 자동 동기화** | 미패치 제품 배포 사고 방지 |

#### 한줄 요약

- 증거 기반 판정, 불변 식별자 결속, 배포 상태 자동 동기화를 통해 VEX의 신뢰성을 확보

## Ⅶ. 결론

<details><summary>용어 설명</summary>

- **지능형 공급망 보안 자동화(Automated VEX Pipeline)**: SBOM 생성 즉시 AI와 호출 그래프 분석기가 VEX 문서를 자동 생성하고 패치 우선순위를 도출하는 차세대 체계.

</details>

- **VEX 취약점 악용 가능성 교환** SBOM 도입의 실효성을 완성하는 핵심 보완 장치이며, 도달성 분석과 서명 기반의 정당화 근거를 통해 거짓 양성 알람을 제거하고 실질적인 보안 위협에 집중해야 함

#### 한줄 요약

- 도달성 분석과 4대 표준 상태 명세를 통해 거짓 양성을 제거하고 실효성 있는 취약점 관리를 완성
