## Ⅰ. 개요

<details><summary>용어 설명</summary>

- **정적 보안 분석(SAST, Static Application Security Testing)**: 앱을 켜보지도 않고, 소스코드만 쓱 훑어보면서 "너 여기 SQL 인젝션 터지겠는데?" 하고 보안 구멍을 찾아내는 화이트박스 엑스레이 검사이다.
- **오염 분석(Taint Analysis)**: 해커가 입력한 텍스트(독극물)가 DB 쿼리문까지 흘러가는 핏줄(데이터 흐름)을 집요하게 추적해서 터지기 직전에 잡아내는 기법이다.
- **소스, 싱크, 새니타이저(Source, Sink, Sanitizer)**: 소스(Source)는 독극물 진입점(입력창), 싱크(Sink)는 독극물이 터지는 심장(DB 쿼리), 새니타이저(Sanitizer)는 중간에 독을 해독하는 해독제(입력값 필터링)이다.

</details>

- 정의: 코드를 실행하지 않고 구문 분석과 오염 분석(Taint Analysis)을 통해 코딩/빌드 단계에서 보안 약점을 조기에 팩트 폭행하는 **SAST**
- 배경: 다 짜놓고 배포한 뒤에 해킹당하면 **고치는 비용과 뉴스 타는 수치심**이 수십 배로 뛰기 때문

#### 한줄 요약

- 프로그램 돌려보지도 않고 코드만 쭉 읽어서 보안 빵꾸를 찾아내는 엑스레이 기계다.

## Ⅱ. 특징

<details><summary>용어 설명</summary>

- **오탐 vs 미탐(False Positive vs False Negative)**: 오탐은 정상 코드를 보고 "해킹당했다!"고 헛소리하는 늑대소년이고, 미탐은 진짜 해킹당했는데 "안전합니다~" 하고 넘어가는 돌팔이 의사이다. SAST는 오탐이 꽤 많다.
- **룰셋(Rule Set)**: 봇이 소스코드를 뒤질 때 "이런 패턴 나오면 잡아라" 하고 적어둔 KISA나 OWASP의 팩폭 가이드북이다.

</details>

- 코드를 낱낱이 파헤치는 **White-box Analysis (화이트박스 투시)**.
- 코드 짜자마자 바로 보안 검사 때리는 **Shift-Left Security (좌측 이동)**.
- 실제로 안 돌려보고 예측만 하다 보니 발생하는 짜증 나는 **False Positive (오탐)** 방어 필수.

#### 한줄 요약

- 코딩 즉시 잡아내서 좋긴 한데, 안 돌려보고 눈으로만 찾아서 헛소리(오탐)가 많은 게 단점이다.

## Ⅲ. 구조 및 구성요소

<details><summary>용어 설명</summary>

- **추상 구문 트리(AST, Abstract Syntax Tree)**: 코드를 인간이 읽는 텍스트가 아니라, 봇이 분석하기 쉽게 동그라미와 선(트리 구조)으로 해체해 놓은 뼈대이다.

</details>

```text
[ SAST 십자포화 아키텍처 ]

[ 소스코드 ] ──(AST 뼈대 추출)──▶ [ 코드 파서 ]
                                       │
                                       ▼
      [ 보안 룰셋 (KISA) ] ────▶ [ 오염 분석기 (독극물 추적) ]
                                       │
[ 헛소리 억제 (예외 처리) ] ◀────── [ 결과 판정 (취약점 리포트) ]
```

| 구성요소 | 팩트 폭행 책임 |
|:---|:---|
| **코드 파서 (Parser)** | 소스코드를 봇이 씹고 뜯기 좋게 트리 뼈대(AST)로 발라내는 놈 |
| **오염 분석기 (Taint)** | 외부에서 들어온 독(Source)이 심장(Sink)까지 가는지 피의 흐름을 쫓는 추적자 |
| **규칙 엔진 (Rule Set)** | KISA 가이드북 들고 다니면서 "이거 어겼네!" 하고 빨간 줄 긋는 훈장님 |
| **억제 근거 (Suppress)** | 봇이 헛소리(오탐)할 때 "내가 안전한 거 확인했으니 입 다물어" 하고 재갈 물리는 기능 |

#### 한줄 요약

- 코드를 뼈대로 분해 $\to$ 독극물 추적 $\to$ 룰셋 대조 $\to$ 오탐 입막음의 구조다.

## Ⅳ. 흐름도

<details><summary>용어 설명</summary>

- **KISA 47개 SW 보안약점**: 한국 공공기관 납품할 때 안 지키면 무조건 빠꾸 먹는, "비번 평문 저장 금지" 같은 대한민국 국룰 방어선이다.

</details>

```text
[ SAST 실행 십자포화 흐름 ]
┌──────────────────────────────┐
│ 개발자가 깃허브에 코드 푸시  │
└──────────────┬───────────────┘
               ▼
┌──────────────────────────────┐
│ 1. 코드 파싱 (뼈대 바르기)   │
│ (AST, 제어/데이터 흐름 추출) │
└──────────────┬───────────────┘
               ▼
┌──────────────────────────────┐
│ 2. 독극물(Taint) 경로 추적   │
│ (입력값이 DB로 직행하는가?)  │
└──────────────┬───────────────┘
               ▼
┌──────────────────────────────┐
│ 3. 룰셋 대조 (보안 위반 확인)│
│ (KISA, OWASP 기준 위반 팩폭) │
└──────────────┬───────────────┘
               ▼
┌──────────────────────────────┐
│ 4. 퀄리티 게이트 판정        │
│ (치명적 약점이면 빌드 컷!)   │
└──────────────────────────────┘
```

### 동작 원리

1. 코드 뜯기: 코드를 텍스트가 아니라 구조 트리(AST)로 변환함.
2. 경로 추적: 외부 입력값(Source)이 필터링 없이 쿼리(Sink)로 직행하는지 쫓아감.
3. 필터링 판정: 중간에 해독제(Sanitizer)를 거쳤는지 팩트 체크함.
4. 위반 대조: 발견된 구멍이 OWASP/KISA 룰셋에 걸리는지 확인.
5. 게이트 판정: 위험한 코드면 SonarQube에서 빨간불 띄우고 얄짤없이 빌드 터뜨림.

#### 한줄 요약

- 코드 뼈대 분해 $\to$ 독극물 추적 $\to$ 해독제 팩트 체크 $\to$ 경고 발송의 흐름이다.

## Ⅴ. 종류 및 비교

<details><summary>용어 설명</summary>

- **SAST (정적 분석) vs DAST (동적 분석)**: SAST는 코드 까보고 "너 암 걸릴 거 같은데?" 하는 MRI 검사고, DAST는 실제로 때려보고 "아프지?" 확인하는 샌드백 검사이다.

</details>

| 비교 항목 | **SAST (정적 분석, MRI 검사)** | **DAST (동적 분석, 샌드백 검사)** |
|:---|:---|:---|
| 분석 대상 | **비실행 소스코드 전체 (속살)** | **살아 숨 쉬는 실제 웹 서버 (겉껍질)** |
| 테스트 기법 | **화이트박스 (코드 까봄)** | **블랙박스 (코드 안 보고 찌름)** |
| 취약점 위치 | **"Main.java 45번째 줄 터짐" (정확함)** | **"로그인 URL에서 에러 남" (어딘지 찾아야 함)** |
| 실행 시점 | **개발자가 코딩하자마자 (Shift-Left)** | **서버 배포 다 끝나고 나서 (늦음)** |
| 오탐/미탐 | **안 돌려봐서 헛소리(오탐) 많음** | **실제 터진 것만 잡아서 오탐 적지만, 안 찌른 곳은 미탐** |

#### 한줄 요약

- SAST는 의사가 엑스레이 보며 팩폭하는 거고, DAST는 암행어사가 직접 서버를 털어보는 거다.

## Ⅵ. 실무 고려사항 및 대책

<details><summary>용어 설명</summary>

- **경고 피로(Alert Fatigue)**: SAST 봇이 매일 500개씩 헛소리(오탐) 알림을 보내니까, 개발자가 빡쳐서 알림을 끄고 무시해버리는 늑대소년 대참사이다.

</details>

| 문제 | 대책 | 효과 |
|:---|:---|:---|
| 오탐 때문에 빡친 개발자의 **경고 피로(Fatigue)** 폭발 | 우리 앱에 안 맞는 **룰셋 끄고 예외(Suppress) 처리**로 입막음 | 신뢰성 회복 및 진짜 알림만 집중 |
| 100만 줄 털다가 빌드 30분 걸림 | 바뀐 코드만 터는 **PR 증분 검사** 도입 | CI 피드백 속도 떡상 |
| 내가 안 짠 라이브러리(Spring)까지 털어서 억울함 | **Third-party 폴더 스캔 대상에서 제외(Exclusion)** | 쓸데없는 경고 박멸 |

#### 한줄 요약

- 오탐 너무 많으면 늑대소년 취급받으니까, 입막음(예외 처리) 잘하고 바뀐 코드만 검사해라.

## Ⅶ. 결론

<details><summary>용어 설명</summary>

- **SAST 도입 수립 기준(SAST Adoption Standards)**: 공공기관 납품(KISA 필수)인지, CI 속도를 중시하는지 각 재서 룰셋을 세팅하는 잣대이다.

</details>

- **SAST 도입 수립 기준** 원칙에 따라, 소스코드 구멍은 **SAST**로 미리 털고, 배포 후 실제 해킹 가능성은 **DAST**로 두들겨 패는 상호 보완 기조 확립함

#### 한줄 요약

- SAST 하나로 다 막겠다는 건 허세다. 엑스레이(SAST) 찍고 맷집 테스트(DAST)까지 해야 안전하다.
