## Ⅰ. 개요

<details><summary>용어 설명</summary>

- **SAST**: 실행 없이 소스나 바이트코드를 분석해 보안 약점을 찾는 화이트박스 기법.
- **오염 분석(Taint Analysis)**: 외부 입력값(Source)이 정화(Sanitizer) 없이 데이터베이스 쿼리나 쉘 실행점(Sink)으로 흘러가는 경로를 추적하는 기법.

</details>

- 정의/개념: 소스코드를 실행하지 않고 **추상 구문 트리(AST) 및 오염 분석(Taint Analysis)** 으로 보안 약점을 조기 탐지하는 화이트박스 보안 테스팅
- 배경/필요성: 소프트웨어 배포 후 런타임 환경에서 보안 취약점이 발견될 경우 발생하는 아키텍처 재설계 비용 폭증과 개인정보 유출 및 서비스 중단 피해를 방지하기 위해, 소스코드를 실행하지 않고 추상 구문 트리(AST)와 소스-싱크 오염 분석(Taint Analysis)을 통해 CWE/OWASP/KISA 보안 약점과 비인가 데이터 흐름을 코딩·빌드 단계에서 조기 식별하는 시프트 레프트(Shift-Left) 체계를 구축하여 **보안 결함의 수정 비용을 최소화하고 시큐어 코딩 품질을 원천 확보**할 필요

#### 한줄 요약
- 코드를 실행하지 않고 구문 파싱과 데이터 흐름 추적으로 소스 코드 내 보안 취약점을 조기에 탐지한다.

## Ⅱ. 특징

<details><summary>용어 설명</summary>

- **False Positive(오탐)**: 실제로는 공격이 불가능하거나 안전한 코드임에도 정적 분석 도구가 잠재적 위험으로 잘못 경고하는 현상.
- **Shift-Left Security**: 배포 전 최종 점검이 아닌 개발자 IDE 코딩 및 CI 빌드 단계로 보안 검증을 앞당기는 원칙.

</details>

- 코드 내부 구조를 검사하는 **화이트박스 정적 분석**
- 개발/빌드 단계에서 결함을 즉각 피드백하는 **시프트 레프트(Shift-Left) 보안 내재화**
- 실행 컨텍스트 부재로 인한 **오탐(False Positive) 억제를 위한 룰셋 커스터마이징 필수**

#### 한줄 요약
- 정적 분석은 실행 없이 전체 코드를 훑는 넓은 시야를 얻는 대신 실행 맥락을 몰라 오탐을 감수하므로, 룰셋 조정이 곧 탐지율과 신뢰도의 조절점이 된다.

## Ⅲ. 구조 및 구성요소

<details><summary>용어 설명</summary>

- **Source-Sink-Sanitizer**: 외부 입력(Source: HTTP 요청), 취약점 실행점(Sink: SQL 쿼리), 입력값 검증/치환(Sanitizer) 3요소 모델.

</details>

```text
[SAST 분석 체계]
|-- 소스·바이트코드
|-- 구문 파서
|-- 정적 분석 엔진
|   |-- 규칙 엔진
|   `-- 오염 분석기
`-- 품질 게이트·리포터
```

선의 의미: 가지는 분석 체계의 포함 관계

| 구성요소 | 책임 |
|:---|:---|
| 구문 파서 | **AST·CFG** 생성 |
| 오염 분석기 | Source부터 Sink까지 **미정화 흐름** 추적 |
| 규칙 엔진 | CWE·OWASP 규칙과 코드 패턴 대조 |
| 품질 게이트 | 심각도 정책에 따른 빌드 판정·보고 |

#### 한줄 요약
- Taint 분석이 입력에서 위험 지점까지의 데이터 흐름을 추적하므로, 단순 규칙 매칭으로는 잡히지 않는 경로형 취약점이 이 단계에서 드러난다.

## Ⅳ. 흐름도

<details><summary>용어 설명</summary>

- **KISA 47대 보안약점**: 행정안전부/KISA가 고시한 입력데이터 검증(SQLi, XSS), 보안기능, 시간 및 상태, 에러처리 등 공공 SW 필수 점검 기준.

</details>

```text
개발자가 소스 코드를 Git 저장소에 커밋/푸시
        │
   [파싱 단계] SAST 도구가 소스 코드를 읽어 AST 및 CFG/DFG 그래프 생성
        │
   [오염 추적] HTTP 파라미터(Source)가 `PreparedStatement` 등 정화(Sanitizer) 없이
              `Statement.executeQuery()`(Sink)로 직접 전달되는지 분석
        │
   [룰셋 대조] KISA SQL Injection 취약점(CWE-89) 위반으로 판정 (정확한 소스 라인 특정)
        │
   심각도 기준(Critical 취약점 1건 이상)에 위배되는가?
   ┌────┴─────┐
  예           아니오
   │             │
[CI 빌드 차단]   [품질 게이트 통과]
PR 병합 금지      CD 파이프라인 진행
개발자 즉시 통보
```

#### 한줄 요약
- 오염 추적은 규칙 대조보다 비싸지만 경로를 따라가야만 드러나는 결함을 잡으므로, 빌드 차단 기준을 어디에 두느냐가 정확도와 속도를 맞바꾼다.

## Ⅴ. 종류 및 비교

<details><summary>용어 설명</summary>

- **SAST vs DAST**: 소스 코드를 직접 보는 화이트박스 정적 분석(SAST)과 구동 중인 앱에 외부에서 공격 패킷을 쏘는 블랙박스 동적 분석(DAST).

</details>

| 비교 항목 | 정적 분석 (SAST: SonarQube, Checkmarx) | 동적 분석 (DAST: OWASP ZAP, Burp Suite) |
|:---|:---|:---|
| 분석 대상 | **소스 코드 원문, 컴파일 바이트코드** | **실행 중인 웹 애플리케이션 (HTTP URL)** |
| 테스팅 방식 | **화이트박스 (Whitebox)** | **블랙박스 (Blackbox)** |
| 취약점 위치 특정 | **파일·코드 위치 후보 제공** | 취약 URL과 HTTP 응답 제공 |
| 장점 | 개발 초기 결함 조기 발견 (Shift-Left) | 런타임 인증 오류, 서버 설정 결함 탐지 |
| 주요 한계 | 실행 컨텍스트 부재로 오탐(False Positive) 존재 | 소스 코드 내부의 정확한 수정 위치 미제공 |

#### 한줄 요약
- SAST는 코드 내부 취약 라인을 조기 전수 검사하고, DAST는 실행 환경의 실제 침투 가능성을 검증한다.

## Ⅵ. 실무 고려사항 및 대책

<details><summary>용어 설명</summary>

- **Incremental Scan(증분 스캔)**: 전체 수백만 줄의 코드를 매번 분석하지 않고, 이번 Git PR에서 변경된 파일들만 30초 내로 빠르게 스캔하는 기법.

</details>

| 문제 | 대책 | 효과 |
|:---|:---|:---|
| SAST 오탐에 따른 **경고 피로** | 맞춤 룰셋과 검토된 **오탐 억제** 등록 | 유효 경고의 우선순위 향상 |
| 대규모 저장소의 CI 분석 지연 | **PR 증분 분석·주기적 전체 분석** 분리 | 변경 피드백 시간 단축 |
| 프레임워크 자체 새니타이징(Spring Security)을 미인식 | **도구 설정 파일에 프레임워크 내장 Sanitizer 함수 등록** | 오탐 제거 및 정밀 오염 분석 달성 |
| 서드파티 라이브러리 소스코드까지 분석하여 노이즈 발생 | **자체 개발 소스만 스캔 대상 지정 및 오픈소스는 SCA 도구로 분리** | 자체 비즈니스 로직 취약점 집중 검증 |

#### 한줄 요약
- 정적 분석은 실행 없이 넓게 훑는 대신 오탐을 대량으로 만들므로, 룰셋 정제와 Sanitizer 인식으로 경고 밀도를 낮추고 증분 분석으로 검사 시간을 파이프라인에 맞춘다.

## Ⅶ. 결론

- 데브섹옵스(DevSecOps) 파이프라인 및 시큐어 코딩 거버넌스의 **가장 기초적이고 필수적인 화이트박스 정적 분석 표준 도구**로 확립되었으며, 실무 적용 시에는 **개발자 IDE 플러그인(SonarLint)을 통한 실시간 피드백, 오탐(False Positive) 억제를 위한 조직 맞춤형 룰셋 및 프레임워크 Sanitizer 등록, PR 변경 파일 대상 증분 스캔(Incremental Scan)을 적용**하여 CI 빌드 속도 저하 없이 소스코드 무결성을 사수

#### 한줄 요약
- SAST는 소스 코드를 실행하지 않고 구문 파싱과 오염 분석을 통해 코딩 단계에서 보안 결함을 조기 제거하는 핵심 화이트박스 보안 도구다.
