## Ⅰ. 개요

<details>
<summary>핵심 용어</summary>

- **오픈 테이블 포맷(Open Table Format)**: 객체 스토리지 파일의 버전•스키마•파티션을 여러 엔진이 같은 규칙으로 관리하게 하는 공개 메타데이터 명세이다.

</details>

- 정의/개념: 객체 스토리지 파일을 테이블로 관리하는 **오픈 테이블 포맷**이다.
- 배경/필요성: 디렉터리 기반 파일 표는 부분 커밋•동시 쓰기•구조 진화를 제약한다.

#### 한줄 요약

- 같은 창고 파일을 여러 도구가 동일한 표로 보도록 공개된 장부 규칙을 둔다.

## Ⅱ. 특징

<details>
<summary>핵심 용어</summary>

- **다중 엔진 호환성**: 공개 명세에 따라 여러 처리 엔진이 같은 테이블 스냅숏을 해석하는 특성이다.
- **원자 커밋**: 완성된 파일 집합만 하나의 새 테이블 버전으로 공개하는 특성이다.
- **구조 진화**: 스키마•파티션 정보를 디렉터리 경로와 분리해 열과 배치 규칙을 안전하게 변경하는 특성이다.

</details>

- 완성된 파일 집합만 새 버전으로 공개하는 **원자 커밋**이 핵심이다.
- 공개 명세로 같은 스냅숏을 해석하는 **다중 엔진 호환성**이 핵심이다.
- 스키마•파티션 정보를 경로에서 분리한 **구조 진화**가 핵심이다.

#### 한줄 요약

- 세 포맷 모두 안전한 장부를 제공하지만 현재 파일과 바뀐 행을 찾고 정리하는 방법이 다르다.

## Ⅲ. 구조 및 구성요소

<details>
<summary>핵심 용어</summary>

- **포맷 메타데이터**: 스냅숏•스키마•파티션과 데이터 및 변경 파일 참조를 관리하는 구성요소이다.
- **읽기 엔진**: 공개 명세를 해석해 테이블을 조회하는 실행 도구이다.
- **쓰기 엔진**: 테이블 변경 파일과 새 메타데이터를 커밋하는 실행 도구이다.
- **카탈로그**: 테이블 이름과 현재 메타데이터 위치를 관리하는 구성요소이다.
- **데이터 파일**: 실제 행을 불변 열 지향 형식으로 저장하는 파일이다.
- **삭제 파일**: 데이터 파일을 재작성하지 않고 행 삭제를 표현하는 파일이다.
- **로그 파일**: 행 수준 변경을 순서대로 기록하는 파일이다.

</details>

```text
[오픈 테이블 포맷]
          |
          +-- [카탈로그]
          |
          +-- [포맷 메타데이터]
          |          |
          |          +-- [데이터 파일]
          |          +-- [삭제•로그 파일]
          |
          +-- [읽기•쓰기 엔진]
```

선의 의미: 카탈로그는 현재 포맷 메타데이터의 위치를 제공하고, 읽기•쓰기 엔진은 이 메타데이터를 해석하며, 메타데이터는 유효한 데이터 파일과 삭제•로그 파일을 참조한다.

| 구성요소 | 책임 |
|:---|:---|
| 읽기•쓰기 엔진 | **읽기 엔진**과 **쓰기 엔진**이 공개 명세에 따라 조회•변경•커밋 수행 |
| 카탈로그 | **카탈로그**가 테이블 이름과 현재 메타데이터 위치 제공 |
| 포맷 메타데이터 | **포맷 메타데이터**가 스냅숏•스키마•파티션•파일 참조 관리 |
| 데이터 파일 | **데이터 파일**이 실제 행을 열 지향 파일로 저장 |
| 삭제•로그 파일 | **삭제 파일**과 **로그 파일**이 데이터 파일 재작성 전 행 수준 변경 저장 |

#### 한줄 요약

- 엔진과 파일 사이의 공개 장부가 현재 테이블 상태를 정한다.

## Ⅳ. 흐름도

<details>
<summary>핵심 용어</summary>

- **로그•스트림 연계**: 순차 트랜잭션 로그와 스트리밍 처리의 결합을 우선하는 선택 축이다.
- **대규모 계획•구조 진화**: 많은 파일의 탐색과 스키마•파티션 변경을 우선하는 선택 축이다.
- **레코드 변경•증분 적재**: 키 단위 갱신과 변경분 소비를 우선하는 선택 축이다.
- **운영 적합성 검증**: 엔진 호환성과 쓰기•읽기•정리 비용을 실제 작업으로 확인하는 단계이다.

</details>

```text
가장 중요한 요구사항
        |
        +-- 로그•스트림 연계
        |          |
        |          +-- Delta Lake
        |
        +-- 대규모 계획•구조 진화
        |          |
        |          +-- Apache Iceberg
        |
        +-- 레코드 변경•증분 적재
                   |
                   +-- Apache Hudi

후보 포맷
   |
   +-- 엔진 호환성 시험
   +-- 커밋•읽기•정리 비용 측정
   |
   +-- 운영 적합 포맷 확정
```

- **운영 적합성 검증**은 후보 포맷의 엔진 호환성과 커밋•읽기•정리 비용을 실제 작업으로 확인한다.

#### 한줄 요약

- 새 파일과 목록을 준비하고 현재 장부 위치를 한 번에 바꾼 뒤 독자는 확정된 파일만 읽는다.

## Ⅴ. 종류 및 비교

<details>
<summary>핵심 용어</summary>

- **Apache Hudi**: 타임라인•파일 그룹•인덱스로 레코드 변경과 증분 적재를 관리하는 테이블 포맷이다.
- **Delta Lake**: 순차 트랜잭션 로그와 체크포인트로 파일 집합의 버전을 관리하는 포맷이다.
- **Apache Iceberg**: 스냅숏•매니페스트•필드 식별자(Field Identifier, Field ID)로 대규모 계획과 구조 진화를 지원하는 포맷이다.

</details>

| 오픈 테이블 포맷 | Delta Lake | Apache Iceberg | Apache Hudi |
|:---|:---|:---|:---|
| 적용 기준 | **Delta Lake**: **로그•스트림 연계** | **Apache Iceberg**: **대규모 계획•구조 진화** | **Apache Hudi**: **레코드 변경•증분 적재** |
| 핵심 특징 | 순차 로그•체크포인트 | 스냅숏•매니페스트•Field ID | 타임라인•파일 그룹•인덱스 |
| 한계 | 로그•작은 파일•스냅숏 만료 관리 | 매니페스트•삭제 파일•스냅숏 관리 | 인덱스•파일 병합•이전 파일 정리 관리 |

#### 한줄 요약

- 델타는 거래 로그, 아이스버그는 단계별 파일 목록, 후디는 작업 시간선과 레코드 위치표가 중심이다.

## Ⅵ. 실무 고려사항 및 대책

<details>
<summary>핵심 용어</summary>

- **계획 비용**: 파일과 목록을 분석해 쿼리 태스크를 만드는 비용이다.
- **읽기 비용**: 선택한 데이터 파일을 스캔하고 병합하는 비용이다.
- **호환성 시험**: 엔진•카탈로그 조합의 읽기•쓰기 기능을 확인하는 시험이다.
- **커밋 시험**: 동시 변경의 충돌과 원자 확정을 확인하는 시험이다.
- **키 기반 쓰기 방식**: 레코드 키 분포에 맞춰 갱신 위치를 찾는 방식이다.
- **파티션 기반 쓰기 방식**: 파티션 단위로 변경 파일이나 재작성을 선택하는 방식이다.
- **변경률 기반 쓰기 방식**: 갱신 비율과 파일 재작성 비용을 비교하는 기준이다.
- **파일 병합**: 작은 데이터 파일을 목표 크기로 합치는 처리이다.
- **메타데이터 병합**: 작은 목록 파일을 합쳐 계획 비용을 줄이는 처리이다.
- **수명주기**: 복구 목표와 최대 작업 시간보다 길게 스냅숏과 참조 파일을 보존한 뒤 안전하게 제거하는 정책이다.

</details>

| 문제 | 대책 | 효과 |
|:---|:---|:---|
| 엔진•카탈로그 조합별 기능 차이로 읽기•쓰기 오류 발생 | 조합별 **호환성 시험**•**커밋 시험** 수행 | 미지원 기능의 운영 투입 방지 |
| 변경률과 키 분포가 맞지 않으면 파일 재작성•병합량 증가 | **키 기반 쓰기 방식**•**파티션 기반 쓰기 방식**•**변경률 기반 쓰기 방식** 선택 | 행 수준 변경의 쓰기 증폭 감소 |
| 작은 파일•메타데이터 누적으로 **계획 비용**•**읽기 비용** 증가 | 목표 크기 기반 **파일 병합**•**메타데이터 병합** | 쿼리의 계획•스캔 비용 감소 |
| 보존 기간이 작업 시간보다 짧으면 과거 파일 조기 삭제 | 복구 목표•작업 시간 기반 **수명주기** 설정 | 과거 조회와 저장 비용 균형 |

#### 한줄 요약

- 이름표만 비교하지 말고 실제 주문 변경을 넣어 쓰기•읽기•정리 비용까지 재 본다.

## Ⅶ. 결론

<details>
<summary>핵심 용어</summary>

- **오픈 테이블 포맷 선택 기준**: 로그 연계•구조 진화•레코드 갱신의 우선순위이다.

</details>

- **오픈 테이블 포맷 선택 기준**에 따라 로그 연계는 **Delta Lake**, 구조 진화는 **Apache Iceberg**, 레코드 갱신은 **Apache Hudi**를 선택한다.

#### 한줄 요약

- 같은 안전 장부라도 도구와 변경 방식에 따라 유지비가 달라 실제 작업으로 골라야 한다.
