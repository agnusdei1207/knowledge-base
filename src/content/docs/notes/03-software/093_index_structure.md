## Ⅰ. 개요

<details><summary>용어 설명</summary>

- **B+Tree, 해시, 복합 인덱스(Index Structures)**: 순차 연결 리프 노드로 범위 탐색을 지원하는 B+Tree, 동등 비교에 $O(1)$로 접근하는 해시, 다중 컬럼을 결합한 복합 인덱스 구조.
- **풀 테이블 스캔 및 디스크 I/O 병목(Full Scan & I/O Bottleneck)**: 인덱스 부재로 인해 수백만 건의 데이터 블록 전체를 디스크에서 읽어 발생되는 성능 저하 현상.

</details>

- 정의/개념: 대용량 테이블에서 풀스캔 병목을 해소하고 검색 속도를 향상시키기 위해 **B+Tree, 해시, 복합 인덱스 형태로 키-포인터 쌍을 정렬·관리**하는 검색 가속 자료구조
- 배경/필요성: 데이터량 증가에 따른 풀 테이블 스캔(Full Scan) 강제 시 발생하는 **디스크 I/O 급증, 버퍼 풀 오염 및 쿼리 응답 시간 지연 위험** 직면

#### 한줄 요약

- 선택도가 높은 컬럼에 B+Tree, 해시, 복합 인덱스를 구성하여 디스크 I/O를 최소화하고 질의 속도를 극대화

## Ⅱ. 특징

<details><summary>용어 설명</summary>

- **선택도(Selectivity)**: 고유값 개수 대비 전체 행 수의 비율($\text{Unique Count}/\text{Total Rows}$)로 10~15% 이하로 낮을수록(변별력이 높을수록) 인덱스 효율 극대화.
- **DML 쓰기 오버헤드(Write Overhead)**: `INSERT/UPDATE/DELETE` 발생 시 인덱스 트리 분할(Split) 및 정렬 유지로 인해 추가 I/O가 발생하는 비용.

</details>

- 변별력이 높은 컬럼을 우선 선정하는 **선택도(Selectivity) 중심 설계**
- 범위 검색과 정렬에 최적화된 **B+Tree($O(\log N)$) 및 동등 검색용 Hash($O(1)$) 지원**
- 조회 성능 향상과 DML 쓰기 오버헤드 간의 **명확한 트레이드오프 관리** #### 한줄 요약

- 높은 선택도 컬럼을 중심으로 B+Tree 기반 탐색을 구현하여 조회 속도를 비약적으로 단축

## Ⅲ. 구조 및 구성요소

<details><summary>용어 설명</summary>

- **B+Tree 3단계 노드**: 루트 노드, 브랜치 노드, 실제 데이터 포인터와 양방향 링크드 리스트가 존재하는 리프 노드.

</details>

```text
[ B+Tree 및 대표 인덱스 아키텍처 구조도 ]

 ┌────────────────────────────────────────────────────────────────────────┐
 │                        B+Tree 인덱스 탐색 아키텍처                      │
 ├────────────────────────────────────────────────────────────────────────┤
 │                       [ 루트 노드 (Key: 50) ]                          │
 │                      /                       \                         │
 │          [ 브랜치 노드 (Key: 20) ]         [ 브랜치 노드 (Key: 80) ]    │
 │          /                     \           /                     \     │
 │   [리프: 10, 15] ◄───────────► [리프: 20, 30] ◄───────────► [리프: 80, 90]│
 │   (양방향 연결)               (양방향 연결)               (양방향 연결)│
 └────────────────────────────────────────────────────────────────────────┘
```

선의 의미: 루트에서 리프 노드로 하향 탐색하며, 리프 노드 간 양방향 링크를 통해 범위 스캔(Range Scan)을 고속 수행하는 구조.

| 구성요소 | 책임 |
|:---|:---|
| B+Tree 인덱스 | 루트-브랜치-리프 계층으로 **범위 검색, 정렬(ORDER BY), 동등 조회를 $O(\log N)$으로 처리** |
| 해시 인덱스 (Hash) | 해시 함수 기반 버킷 탐색으로 **동등 비교(`=`) 연산을 $O(1)$ 초고속 처리** |
| 복합 인덱스 (Composite) | 다중 컬럼 결합 시 **선행 컬럼(Leading Column)의 동등 조건 우선 배치로 탐색 보장** |
| 리프 노드 링크 | 리프 블록 간 양방향 연결을 통해 **추가 트리 탐색 없는 순차 범위 스캔 지원** |

#### 한줄 요약

- B+Tree의 계층 구조와 리프 노드 양방향 체인을 통해 동등 검색과 범위 스캔을 모두 최적화

## Ⅳ. 흐름도

<details><summary>용어 설명</summary>

- **옵티마이저 인덱스 스캔 결정**: 조건절 분석 $\to$ 통계 기반 비용 계산(CBO) $\to$ 인덱스 레인지 스캔 vs 풀 테이블 스캔 선택.

</details>

```text
[ 인덱스 기반 쿼리 최적화 및 탐색 파이프라인 ]

 ┌────────────────────────────────────────┐
 │ 1. SQL 질의 접수: 조건절 및 정렬 분석 │
 └───────────────────┬────────────────────┘
                     │
                     ▼
 ┌────────────────────────────────────────┐
 │ 2. 통계 기반 선택도 및 CBO 비용 계산   │
 └───────────────────┬────────────────────┘
                     │ (Index Scan이 유리한 경우)
                     ▼
 ┌────────────────────────────────────────┐
 │ 3. B+Tree 루트 노드 진입 및 이진 탐색  │
 └───────────────────┬────────────────────┘
                     │
                     ▼
 ┌────────────────────────────────────────┐
 │ 4. 리프 노드 도달: ROWID/PK 추출       │
 └───────────────────┬────────────────────┘
                     │
                     ▼
 ┌────────────────────────────────────────┐
 │ 5. 테이블 데이터 블록 랜덤 I/O 인출    │
 └────────────────────────────────────────┘
```

### 동작 원리

1. SQL 질의 접수: WHERE 절의 필터 조건, JOIN 컬럼, ORDER BY 정렬 요구사항을 파악.
2. CBO 비용 계산: 옵티마이저가 인덱스 스캔 비용과 풀 테이블 스캔 비용을 비교하여 실행 계획을 수립.
3. B+Tree 탐색: 루트 노드에서 시작하여 키 값을 비교하며 브랜치 노드를 거쳐 리프 노드로 진입.
4. 리프 노드 스캔: 리프 노드에서 일치하는 키 범위를 양방향 링크로 순차 스캔하고 데이터 행 포인터(ROWID 또는 클러스터 PK)를 획득.
5. 테이블 인출: 추출된 포인터로 실제 데이터 블록에 접근하여 최종 레코드를 반환.

#### 한줄 요약

- 조건 분석 $\to$ CBO 비용 계산 $\to$ B+Tree 탐색 $\to$ 리프 스캔 $\to$ 테이블 랜덤 I/O 인출

## Ⅴ. 종류 및 비교

<details><summary>용어 설명</summary>

- **B+Tree vs Hash vs Composite**: 범용적 범위 조회의 B+Tree, 초고속 동등 조회의 Hash, 복합 다중 조건 최적화의 Composite 인덱스.

</details>

| 구분 | B+Tree 인덱스 | Hash 인덱스 | Composite (복합) 인덱스 |
|:---|:---|:---|:---|
| **적용 기준** | 범위 검색, 부등호, 정렬이 빈번한 일반 컬럼 | 동등 비교(`=`)만 발생하는 고유 키 컬럼 | WHERE 절에 2개 이상 조건이 항상 결합될 때 |
| **핵심 특징** | **$\mathcal{O}(\log N)$ 탐색, 리프 노드 순차 연결** | **$\mathcal{O}(1)$ 해시 버킷 탐색, 최고속도** | **선두 컬럼(Leading Column) 기반 다단계 정렬** |
| **한계** | 대량 데이터 수정 시 노드 분할(Split) 발생 | 범위 검색(`BETWEEN, <, >`) 및 정렬 불가 | 컬럼 순서 설계 오류 시 인덱스 미사용(Skip) |

#### 한줄 요약

- 범위와 정렬은 B+Tree, 단순 동등 비교는 해시, 다중 조건 결합은 선두 컬럼을 고려한 복합 인덱스를 적용

## Ⅵ. 실무 고려사항 및 대책

<details><summary>용어 설명</summary>

- **인덱스 미사용 3대 안티패턴**: 컬럼 좌변 가공, 묵시적 형변환, 부정형 조건 사용 시 옵티마이저가 인덱스를 타지 못하고 풀스캔으로 전락하는 현상.

</details>

| 문제 | 대책 | 효과 |
|:---|:---|:---|
| 컬럼 좌변 가공으로 인덱스 무효화 (`WHERE YEAR(dt)=2026`) | **우변 가공으로 변경 (`WHERE dt >= '2026-01-01' AND..`)** | 인덱스 레인지 스캔 정상 적용 |
| 묵시적 형변환으로 인한 인덱스 풀스캔 전락 | **컬럼 데이터 타입과 조회 파라미터 타입을 정확히 일치화** | 불필요한 전체 형변환 방지 및 인덱스 활용 |
| 테이블당 과도한 인덱스 생성으로 쓰기 성능 급락 | **중복 인덱스 정리 및 핵심 조회 경로 위주 3~5개 이내 제한** | DML 쓰기 오버헤드 최소화 |

#### 한줄 요약

- 좌변 가공 금지, 형변환 일치, 인덱스 개수 통제를 통해 인덱스의 본래 가속 성능을 온전히 유지

## Ⅶ. 결론

<details><summary>용어 설명</summary>

- **인덱스 수명주기 관리(Index Lifecycle Management)**: 미사용 인덱스(Unused Index)를 모니터링하여 주기적으로 삭제하고, 변경된 쿼리 패턴에 맞추어 인덱스를 재정비하는 활동.

</details>

- **데이터베이스 인덱스** 기반 쿼리 성능 튜닝의 가장 강력한 도구이자 양날의 검이며, 선택도 분석과 실행 계획(EXPLAIN) 검증을 거쳐 최소한의 인덱스로 최대의 성능을 이끌어내야 함

#### 한줄 요약

- 높은 선택도 컬럼에 B+Tree와 복합 인덱스를 최적 설계하고 쓰기 오버헤드를 철저히 통제
