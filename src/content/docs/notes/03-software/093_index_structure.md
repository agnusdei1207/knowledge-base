## Ⅰ. 개요

<details><summary>용어 설명</summary>

- **데이터베이스 인덱스(Index)**: 데이터 레코드의 물리적 위치(포인터/PK)를 정렬된 키 형태로 별도 관리하여 $O(\log N)$ 또는 $O(1)$의 빠른 탐색을 지원하는 가속 자료구조.
- **B+Tree vs Hash vs Composite**: 범위 스캔에 최적화된 B+Tree, 단건 동등 조회에 특화된 Hash, 다중 컬럼을 결합한 Composite 인덱스.

</details>

- 정의/개념: 풀 테이블 스캔을 방지하고 조회 속도를 극대화하기 위해 **B+Tree, 해시, 복합 인덱스 형태로 키-포인터 쌍을 정렬·관리**하는 검색 가속 자료구조
- 배경/필요성: 데이터 레코드 수 증가에 따른 **풀 테이블 스캔(Full Table Scan)의 디스크 I/O 병목 및 버퍼 풀 오염으로 인한 질의 처리 지연 한계**

#### 한줄 요약
- 인덱스는 읽기 경로를 줄이는 대신 모든 쓰기에 구조 갱신 비용을 얹으므로, 걸러내는 양이 적은 저선택도 컬럼에서는 인덱스 경유가 풀스캔보다 오히려 비싸진다.

## Ⅱ. 특징

<details><summary>용어 설명</summary>

- **선택도(Selectivity)**: 전체 행 수 대비 고유한 값의 비율로, 선택도가 낮을수록(보통 5~10% 이하, 변별력이 높을수록) 인덱스 스캔 효율 극대화.
- **Index Split(페이지 분할)**: B+Tree 리프 노드가 가득 찬 상태에서 신규 키 삽입 시 노드가 둘로 쪼개지며 I/O 부하가 발생하는 현상.

</details>

- 카디널리티가 크고 변별력이 높은 컬럼을 우선 선정하는 **선택도(Selectivity) 중심 설계**
- 범위 검색과 정렬에 최적화된 **B+Tree($O(\log N)$) 및 동등 검색용 Hash($O(1)$) 지원**
- 조회 성능 향상과 DML(Insert/Update/Delete) 쓰기 오버헤드 간의 **명확한 트레이드오프**

#### 한줄 요약
- 높은 선택도 컬럼 중심의 B+Tree 탐색으로 조회 성능을 극대화하되 쓰기 오버헤드를 통제한다.

## Ⅲ. 구조 및 구성요소

<details><summary>용어 설명</summary>

- **B+Tree 3계층 구조**: Root Node(최상위), Branch Node(인덱스 탐색 경로), Leaf Node(실제 키-ROWID 저장 및 양방향 링크드 리스트).

</details>

| 인덱스 구성요소 | 책임 | 탐색 복잡도 및 특징 |
|:---|:---|:---|
| B+Tree 루트/브랜치 | 키 값을 대조하여 하위 자식 노드로의 **탐색 경로 안내 (라우팅 전용)** | 데이터 없이 자식 포인터만 저장하여 팬아웃(Fan-out) 극대화 |
| B+Tree 리프 노드 | 실제 인덱스 키와 **데이터 행 포인터(ROWID/PK) 저장 및 양방향 체인 연결** | **$O(\log N)$ 단건 탐색 및 $O(K)$ 순차 범위 스캔** |
| 해시 인덱스 (Hash) | 키 값을 해시 함수에 통과시켜 **해시 버킷 메모리 주소로 직접 접근** | **$O(1)$ 초고속 동등(`=`) 조회 (범위/정렬 불가)** |
| 복합 인덱스 (Composite) | 2개 이상의 컬럼을 결합하여 **선두 컬럼(Leading Column) 순서대로 정렬** | 결합 인덱스 컬럼 순서에 따른 탐색 여부 결정 |

#### 한줄 요약
- B+Tree가 값을 리프에만 두고 상위 노드를 경로 안내로만 쓰기에 트리 높이가 낮게 유지되고, 리프끼리 이어진 체인이 범위 조회에서 다시 루트로 되돌아가는 비용을 없앤다.

## Ⅳ. 흐름도

<details><summary>용어 설명</summary>

- **CBO(Cost-Based Optimizer) 선택**: 통계 정보를 분석하여 Index Range Scan 비용이 Table Full Scan 비용보다 저렴할 때만 인덱스 채택.

</details>

```text
클라이언트 SQL 질의 실행 (`SELECT * FROM Orders WHERE user_id = 101 AND created_at >= '2026-08-01'`)
        │
   [비용 계산] CBO 옵티마이저가 인덱스 통계 정보 기반으로 Table Full Scan vs Index Range Scan 비용 비교
        │
   [루트 노드 탐색] B+Tree 루트 페이지에서 `user_id = 101`이 속한 브랜치 노드 포인터 획득
        │
   [리프 노드 스캔] 리프 페이지에 도달하여 '2026-08-01' 이후 키들을 양방향 링크로 순차 스캔
        │
   [테이블 랜덤 I/O] 리프 노드에서 추출한 Clustered PK로 실제 테이블 데이터 블록 인출
        │
   클라이언트에 최종 쿼리 결과 집합 반환
```

#### 한줄 요약
- 리프까지 도달하는 비용은 트리 높이에 묶여 거의 일정한 반면 리프에서 테이블 행을 되찾는 랜덤 I/O는 결과 건수에 비례하므로, 조회 건수가 커지는 지점에서 인덱스 경유가 풀스캔에 역전당한다.

## Ⅴ. 종류 및 비교

<details><summary>용어 설명</summary>

- **B+Tree vs Hash vs Composite**: 범용 범위 조회의 B+Tree, 초고속 단건 조회의 Hash, 다중 조건 결합의 Composite 인덱스.

</details>

| 비교 항목 | B+Tree 인덱스 | Hash 인덱스 | Composite (복합) 인덱스 |
|:---|:---|:---|:---|
| 탐색 시간 복잡도 | **$O(\log N)$** | **$O(1)$** | **$O(\log N)$** |
| 범위 검색/부등호 | **완벽 지원 (리프 노드 체인)** | **절대 불가 (순서 없음)** | **선두 컬럼 일치 시 지원** |
| `ORDER BY` 정렬 | **정렬 연산 생략 가능** | 정렬 지원 불가 | **인덱스 컬럼 순 정렬 생략 가능** |
| 주 활용처 | 대부분의 RDBMS 기본 인덱스 | Memory 엔진, Redis 키 탐색 | 다중 조건 WHERE 절 복합 쿼리 |

#### 한줄 요약
- 범위와 정렬은 B+Tree, 단순 동등 조회는 해시, 다중 조건 결합은 선두 컬럼을 고려한 복합 인덱스를 적용한다.

## Ⅵ. 실무 고려사항 및 대책

<details><summary>용어 설명</summary>

- **인덱스 미사용 안티패턴**: 컬럼 좌변 가공(`WHERE SUBSTR(name,1,3)='홍'`), 묵시적 형변환, 부정형 조건(`!=`, `NOT IN`) 사용 시 풀스캔으로 전락.

</details>

| 문제 | 대책 | 효과 |
|:---|:---|:---|
| 컬럼 좌변 가공으로 인덱스 무효화 (`WHERE YEAR(dt)=2026`) | **우변 가공으로 쿼리 변경 (`WHERE dt >= '2026-01-01' AND ...`)** | 인덱스 레인지 스캔 정상 적용 |
| 문자열 컬럼에 숫자를 대입하여 묵시적 형변환 풀스캔 | **조회 파라미터 타입을 컬럼 데이터 타입(String)과 100% 일치화** | 불필요한 Full Table Scan 방지 |
| 테이블당 과도한 인덱스 생성(10개 이상)으로 쓰기 지연 | **미사용 인덱스 삭제 및 테이블당 필수 인덱스 3~5개로 제한** | Insert/Update 쓰기 성능 3배 개선 |
| 복합 인덱스 선두 컬럼 누락으로 인한 인덱스 스킵 | **복합 인덱스 설계 시 카디널리티 높고 `=` 조건인 컬럼을 맨 앞에 배치** | 인덱스 활용도 극대화 |

#### 한줄 요약
- 좌변 가공 금지, 형변환 일치, 인덱스 개수 제한, 선두 컬럼 최적 배치로 인덱스를 정상 작동시킨다.

## Ⅶ. 결론

- 엔터프라이즈 관계형 데이터베이스 물리 튜닝 및 쿼리 최적화의 **가장 핵심적인 검색 가속 자료구조**로 확립되었으며, 실무 설계 시에는 **범위 검색과 정렬을 지원하는 B+Tree를 기본으로 채택하고, 카디널리티가 높고 `=` 조건으로 자주 쓰이는 컬럼을 복합 인덱스의 선두(Leading)에 배치하며, DML 쓰기 오버헤드와 페이지 분할(Index Split)을 억제하기 위해 테이블당 필수 인덱스를 3~5개 이내로 통제**하여 최적의 읽기/쓰기 균형을 유지

#### 한줄 요약
- 인덱스는 풀 테이블 스캔을 방지하고 조회 성능을 극대화하는 핵심 물리 구조이며, 쓰기 오버헤드와의 균형 있는 설계가 필수적이다.
