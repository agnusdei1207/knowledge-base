## Ⅰ. 개요

<details><summary>용어 설명</summary>

- **소프트웨어 형상 관리(Software Configuration Management, SCM)**: 소프트웨어 생명주기 전반에 걸쳐 소스 코드, 문서, 환경 설정 등 형상 항목(Configuration Item)의 변경 이력을 식별, 통제, 감사 및 기록하는 공학 체계.
- **분산 버전 관리 시스템(Distributed Version Control System, DVCS)**: 중앙 서버뿐만 아니라 모든 클라이언트가 전체 리포지토리 히스토리를 로컬에 복제하여 독립적인 커밋, 브랜칭 및 오프라인 작업을 지원하는 아키텍처(Git 등).
- **브랜치 전략(Branching Strategy)**: 다수 개발자의 동시 협업 환경에서 코드 충돌을 최소화하고 안정적인 릴리즈 기준선을 유지하기 위해 브랜치 생성, 병합 및 배포 흐름을 정형화한 규칙.

</details>

- 정의/개념: 소프트웨어 자산의 변경 이력을 체계적으로 추적·통제(SCM)하고, **Git(분산 버전 관리)** 과 **브랜치 전략** 을 기반으로 병렬 개발 및 지속적 통합을 지원하는 형상 통제 체계
- 배경/필요성: 다중 개발자 환경에서 비정형적 파일 공유로 인한 코드 덮어쓰기(Overwrite), 릴리즈 버전 추적 불가 및 병합 충돌 비용 폭증 문제 해결 요구

#### 한줄 요약
- 소프트웨어 변경 이력을 무결하게 관리하고 브랜치 전략을 통해 안정적인 협업 및 배포를 지원한다.

## Ⅱ. 특징

<details><summary>용어 설명</summary>

- **형상 기준선(Baseline)**: 공식적으로 검토 및 승인되어 이후 변경 시 엄격한 변경 통제 절차(CCB 등)를 거쳐야 하는 특정 시점의 형상 항목 집합.
- **방향성 비순환 그래프(Directed Acyclic Graph, DAG)**: Git 내부에서 개별 커밋 객체들이 이전 부모 커밋을 단방향으로 참조하여 형성하는 순환 없는 버전 트리 구조.

</details>

- 완전한 로컬 복제본 기반의 빠른 브랜치 생성, 전환 및 병렬 개발 지원(**DVCS**)
- **DAG (Directed Acyclic Graph)** 기반의 커밋 그래프 관리 및 SHA-1/SHA-256 암호학적 해시를 통한 무결성 보증
- 형상 식별, 형상 통제, 형상 감사(Audit), 형상 기록의 4대 핵심 활동을 **브랜치 전략** 및 CI/CD 파이프라인과 통합

#### 한줄 요약
- DAG 기반의 무결성 검증과 분산 저장소 구조를 제공하며, 브랜치 전략으로 변경 통제를 수행한다.

## Ⅲ. 구조 및 구성요소

<details><summary>용어 설명</summary>

- **Git 3단계 영역(Three Trees)**: 파일의 변경과 커밋 과정을 격리하기 위해 제공되는 작업 디렉터리(Working Directory), 스테이징 영역(Index), 로컬 저장소(Repository)의 3단계 구조.

</details>

```text
[ 작업 디렉터리 (Working Directory) ]
        │
        ▼ (git add)
[ 스테이징 영역 (Staging Area / Index) ]
        │
        ▼ (git commit)
[ 로컬 저장소 (Local Repository) ]
        │
        ▼ (git push)
[ 원격 저장소 (Remote Repository - GitHub/GitLab) ]
```

선의 의미: 작업 공간에서 스테이징 영역, 로컬 저장소, 원격 저장소로 단계별 전이되는 커밋 생명주기

| 구성요소 | 책임 |
|:---|:---|
| **작업 디렉터리** | 파일 시스템 상에서 실제 소스 코드를 생성 및 수정하는 로컬 작업 영역 |
| **스테이징 영역(Index)** | 다음 커밋에 포함될 파일 변경 스냅샷을 선별하여 준비하는 임시 버퍼 |
| **로컬 저장소** | 로컬 시스템에 완결된 커밋 객체(Commit, Tree, Blob)를 영구 기록하는 저장소 |
| **원격 저장소** | 팀원 간 협업 및 CI/CD 파이프라인 연계를 위해 중앙에서 동기화되는 공유 저장소 |

#### 한줄 요약
- 작업 디렉터리, 스테이징 영역, 로컬 저장소, 원격 저장소의 단계적 격리를 통해 변경 단위를 제어한다.

## Ⅳ. 흐름도

<details><summary>용어 설명</summary>

- **병합(Merge) vs 리베이스(Rebase)**: 'Merge'는 분기된 두 이력을 결합하는 별도 병합 커밋(Merge Commit)을 생성하는 반면, 'Rebase'는 현재 브랜치의 커밋들을 대상 브랜치의 최신 커밋 뒤로 재배치하여 선형적(Linear) 히스토리를 유지하는 기법.

</details>

```text
1. 로컬 기능 개발 (Feature Branch 작업 디렉터리 수정)
            │
            ▼
2. git add & commit: 변경 사항 스테이징 및 로컬 커밋 객체 생성
            │
            ▼
3. git push & Pull Request(PR): 원격 저장소 브랜치 푸시 및 코드 리뷰 요청
            │
            ▼
4. 자동화 CI 빌드·테스트 및 동료 리뷰 검증: 정적 분석 및 테스트 통과 확인
            │
            ▼
5. 메인라인 브랜치 병합(Merge): 승인 완료 후 메인 브랜치로 통합 및 베이스라인 갱신
```

**동작 원리**

1. **기능 브랜치 작업**: 베이스라인으로부터 분기된 브랜치에서 단위 기능 구현
2. **원자적 커밋**: 변경 논리 단위별로 스테이징 영역에 등록하고 명확한 커밋 메시지와 함께 로컬 커밋
3. **PR 생성**: 원격 저장소에 푸시 후 변경 사항 검토를 위한 Pull Request 발행
4. **품질 검증**: CI 파이프라인이 자동 트리거되어 단위 테스트, 린트 검사, 시큐어 코딩 분석을 수행하고 동료 리뷰 진행
5. **메인라인 통합**: 모든 검증 게이트를 통과한 코드를 메인 브랜치에 병합하여 릴리즈 가능한 형상 기준선 확정

#### 한줄 요약
- 로컬 커밋 후 PR을 발행하고 자동화 검증과 코드 리뷰를 거쳐 메인라인 브랜치로 병합한다.

## Ⅴ. 종류 및 비교

<details><summary>용어 설명</summary>

- **GitFlow**: main, develop, feature, release, hotfix 등 역할을 세분화한 다중 브랜치를 운용하는 정형화된 브랜치 전략.
- **트렁크 기반 개발(Trunk-based Development)**: 모든 개발자가 단일 메인 브랜치(Trunk)를 중심으로 하루 1회 이상 단기 브랜치를 자주 병합하는 지속적 배포 지향 전략.

</details>

| 비교 항목 | GitFlow (정형적 확장형) | GitHub Flow (경량 브랜치) | Trunk-based Development (지속 통합형) |
|:---|:---|:---|:---|
| **적용 기준** | 정기 배포 주기가 있고 버전 관리가 엄격한 패키지/금융 SW | 웹 기반 SaaS, 수시 릴리즈 서비스 | 고도화된 CI/CD 및 기능 플래그(Feature Flag) 적용 환경 |
| **브랜치 구조** | main, develop, feature, release, hotfix 등 5개 계층 | main과 단기 feature 브랜치로 단순화 | 단일 main(Trunk)과 초단기(수 시간~1일) 브랜치 |
| **병합 및 배포 주기** | 주기적 릴리즈 브랜치 생성 및 일괄 배포 | PR 승인 시 main 병합 즉시 배포 | 하루 수회 이상 빈번한 main 병합 및 지속 배포 |
| **병합 충돌 위험** | 브랜치 장기 유지로 인한 병합 충돌(Merge Hell) 가능성 | 기능 단위 격리로 중간 수준 | 잦은 통합으로 대규모 충돌 위험 원천 최소화 |

#### 한줄 요약
- 정기 릴리즈 패키지에는 GitFlow를, 수시 배포 SaaS에는 GitHub Flow나 Trunk-based 전략을 적용한다.

## Ⅵ. 실무 고려사항 및 대책

<details><summary>용어 설명</summary>

- **보호 브랜치(Protected Branch)**: 메인라인 브랜치에 대한 직접 푸시(Direct Push)를 차단하고, 반드시 PR 승인과 CI 통과를 거쳐야만 병합을 허용하는 저장소 보안 정책.

</details>

| 문제 | 대책 | 효과 |
|:---|:---|:---|
| 메인 브랜치 직접 푸시로 인한 미검증 코드 배포 위험 | **보호 브랜치(Protected Branch)** 규칙 강제 및 PR 승인 필수화 | 메인라인 안정성 보증 및 비인가 변경 차단 |
| API Key, 인증 비밀번호 등 민감 정보의 저장소 유출 | **Pre-commit Hook(Gitleaks/git-secrets)** 및 GitGuardian 연동 | 커밋/푸시 시점에 민감 정보 노출 원천 차단 |
| 장기 생존 브랜치로 인한 대규모 병합 충돌 발생 | **트렁크 기반 개발** 전환 및 주기적 Rebase/Merge 정책 수립 | 코드 차이 최소화 및 지속적 통합(CI) 원활화 |

#### 한줄 요약
- 보호 브랜치로 직접 변경을 차단하고, Pre-commit 훅으로 기밀 유출을 방지하며, 잦은 통합으로 충돌을 줄인다.

## Ⅶ. 결론

- 지속적 통합/배포(CI/CD)가 성숙한 클라우드 네이티브 환경에는 **트렁크 기반 개발(Trunk-based)** 과 **보호 브랜치** 정책을 적용하고, 버전별 장기 지원이 필수적인 임베디드 및 엔터프라이즈 솔루션에는 **GitFlow** 기반의 정형 릴리즈 브랜치를 운용하여 프로젝트 성격에 최적화된 형상 통제를 수립

#### 한줄 요약
- 릴리즈 주기와 품질 통제 요구수준에 부합하는 Git 브랜치 전략과 보안 게이트를 구축한다.
