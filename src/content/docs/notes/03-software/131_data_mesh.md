## Ⅰ. 개요

<details><summary>용어 설명</summary>

- **데이터 메시 4대 핵심 원칙(Zhamak Dehghani)**: 도메인 중심 소유권(Domain Ownership), 제품으로서의 데이터(Data-as-a-Product), 셀프서비스 인프라 플랫폼(Self-Serve Platform), 연합형 전산 거버넌스(Federated Governance).
- **중앙 데이터팀 병목 및 도메인 지식 부재(Centralized Bottleneck & Domain Gap)**: 중앙 데이터 엔지니어링 조직이 전사 수집·정제를 독점하여 요청이 적체되고 비즈니스 맥락을 이해하지 못해 품질이 저하되는 한계.

</details>

- 정의/개념: 중앙 집중식 데이터 관리 병목을 해소하기 위해 **도메인 중심 소유권, Data-as-a-Product, 셀프서비스 플랫폼, 연합 거버넌스**를 구현하는 탈중앙 데이터 아키텍처
- 배경/필요성: 단일 중앙 데이터팀에 모든 파이프라인 구축이 집중되어 발생하는 **데이터 수집 요청 적체, 도메인 맥락 부재에 따른 품질 저하 및 파이프라인 마비 위험** 직면

#### 한줄 요약

- 데이터의 소유권을 현업 도메인 팀에 분산하고 품질 보증(SLA)이 포함된 제품으로 제공하여 전사 데이터 민주화를 실현

## Ⅱ. 특징

<details><summary>용어 설명</summary>

- **제품으로서의 데이터(Data-as-a-Product)**: 데이터를 단순한 파일 덤프가 아닌 명확한 스키마, 계약(Data Contract), SLO, 문서를 갖춘 독립적 소프트웨어 제품으로 취급.
- **연합형 전산 거버넌스(Federated Computational Governance)**: 전사 공통 보안, 컴플라이언스, 상호운용성 정책을 자동화된 코드(Policy-as-Code)로 분산 노드에 집행.

</details>

- 현업 비즈니스 도메인(주문, 결제, 회원)에 **데이터 소유권과 품질 책임을 부여(Decentralized)**
- 검색성, 신뢰성, 상호운용성을 갖춘 **독립적 데이터 제품(Data-as-a-Product) 서빙**
- 도메인 팀이 인프라를 자급자족 프로비저닝하는 **셀프서비스 데이터 플랫폼 구축**

#### 한줄 요약

- 도메인별 자율성과 연합 거버넌스의 조화를 통해 데이터 파이프라인의 병목을 제거

## Ⅲ. 구조 및 구성요소

<details><summary>용어 설명</summary>

- **Data Product Quantum**: 독립된 데이터 제품 단위로 파이프라인 코드, 스키마 메타데이터, 보안 정책, 서빙 API가 완결된 아키텍처 단위.

</details>

```text
[ 데이터 메시(Data Mesh) 4대 축 아키텍처 구조도 ]

 ┌────────────────────────────────────────────────────────────────────────┐
 │ 1. 도메인 분산 계층 (Domain-Oriented Decentralized Ownership)          │
 │   ┌──────────────────────┐ ┌──────────────────────┐ ┌────────────────┐ │
 │   │ [주문 도메인 Data Prod]│ │ [결제 도메인 Data Prod]│ │ [회원 Data Prod]│ │
 │   └──────────────────────┘ └──────────────────────┘ └────────────────┘ │
 ├────────────────────────────────────────────────────────────────────────┤
 │ 2. 셀프서비스 데이터 플랫폼 (Self-Serve Data Platform: S3, Spark, Glue) │
 │   - 원클릭 인프라 프로비저닝, 공통 수집 템플릿, 데이터 파이프라인 오케스트레이션│
 ├────────────────────────────────────────────────────────────────────────┤
 │ 3. 연합형 전산 거버넌스 (Federated Computational Governance)            │
 │   - Policy-as-Code (자동 권한/암호화), Data Contract 검증, 통합 카탈로그 │
 └────────────────────────────────────────────────────────────────────────┘
```

선의 의미: 각각의 현업 도메인이 Data Product를 생성하고 하단의 셀프서비스 플랫폼 및 연합 거버넌스가 이를 받쳐주는 탈중앙 아키텍처.

| 구성요소 | 책임 |
|:---|:---|
| 도메인 소유권 (Domain) | 주문/결제 등 현업 팀이 **데이터 파이프라인 생성, 품질 검증, 생명주기를 직접 소유** |
| 데이터 제품 (Data Product) | 스키마, SLO, API 문서, 데이터 계약을 완비하여 **소비자에게 신뢰성 있게 서빙** |
| 셀프서비스 플랫폼 | 도메인 팀이 복잡한 인프라 관리 없이 **파이프라인과 스토리지를 자급 생성하도록 지원** |
| 연합 거버넌스 | 전사 데이터 카탈로그, PII 마스킹, 접근 제어 정책을 **코드로 자동 집행(Policy-as-Code)** |

#### 한줄 요약

- 도메인 소유권, 데이터 제품, 셀프서비스 플랫폼, 연합 거버넌스가 결합하여 자율과 통제를 양립

## Ⅳ. 흐름도

<details><summary>용어 설명</summary>

- **데이터 제품 개발 및 배포 5단계 파이프라인**: 도메인 경계 식별 $\to$ 데이터 계약 체결 $\to$ 셀프서비스 파이프라인 배포 $\to$ 거버넌스 자동 검증 $\to$ 카탈로그 공개.

</details>

```text
[ Data Mesh 데이터 제품 개발 및 서빙 파이프라인 ]

 ┌────────────────────────────────────────┐
 │ 1. 도메인 경계 지정 및 소유권 확정    │
 └───────────────────┬────────────────────┘
                     │
                     ▼
 ┌────────────────────────────────────────┐
 │ 2. 생산자-소비자 간 데이터 계약 체결  │
 └───────────────────┬────────────────────┘
                     │
                     ▼
 ┌────────────────────────────────────────┐
 │ 3. 셀프서비스 플랫폼 기반 파이프라인 배포
 └───────────────────┬────────────────────┘
                     │
                     ▼
 ┌────────────────────────────────────────┐
 │ 4. 연합 거버넌스(보안/품질) 자동 검증  │
 └───────────────────┬────────────────────┘
                     │
                     ▼
 ┌────────────────────────────────────────┐
 │ 5. 전사 카탈로그 등록 및 출력 포트 공개│
 └────────────────────────────────────────┘
```

### 동작 원리

1. 도메인 경계 지정: 비즈니스 바운디드 컨텍스트(예: 주문 도메인)를 기준으로 데이터 소유 팀을 확정.
2. 데이터 계약 체결: 소비자가 요구하는 스키마, 데이터 타입, SLA, 갱신 주기를 Data Contract로 공식 정의.
3. 셀프서비스 배포: 플랫폼 팀이 제공하는 표준 IaC 템플릿을 사용하여 S3 버킷 및 Spark 잡을 원클릭 배포.
4. 거버넌스 자동 검증: CI/CD 파이프라인에서 PII 개인정보 마스킹 및 스키마 유효성을 코드로 자동 검증.
5. 카탈로그 공개: OpenMetadata/Glue에 데이터 제품의 메타데이터와 SQL/API 출력 포트를 등록하여 전사 공개.

#### 한줄 요약

- 경계 지정 $\to$ 계약 체결 $\to$ 셀프서비스 배포 $\to$ 거버넌스 검증 $\to$ 카탈로그 공개의 5단계

## Ⅴ. 종류 및 비교

<details><summary>용어 설명</summary>

- **중앙형 데이터 레이크 vs 데이터 메시**: 단일 데이터팀이 모든 수집을 독점하는 중앙형 구조와 도메인 팀이 분산 소유하는 메시 구조.

</details>

| 구분 | 중앙 집중식 데이터 레이크/DW | 데이터 메시 (Data Mesh) |
|:---|:---|:---|
| **적용 기준** | 소규모 조직 및 단순 데이터 분석 환경 | 대규모 조직, 다수 비즈니스 도메인, MSA 환경 |
| **핵심 특징** | **중앙 데이터팀이 전사 수집/가공 총괄 (Monolithic)** | **현업 도메인 팀이 데이터 제품을 직접 소유 (Decentralized)** |
| **한계** | 중앙 팀 병목, 도메인 맥락 부재, 파이프라인 적체 | 도메인 팀의 데이터 엔지니어링 역량 요구 및 거버넌스 난이도 |

#### 한줄 요약

- 소규모는 중앙형 레이크, 복잡한 대규모 조직은 데이터 메시 아키텍처를 선택

## Ⅵ. 실무 고려사항 및 대책

<details><summary>용어 설명</summary>

- **데이터 사일로 위험(Data Silo Risk)**: 거버넌스 통제 없이 도메인 자율권만 부여하여 팀별로 데이터가 고립되고 인프라 비용이 중복 폭증하는 안티패턴.

</details>

| 문제 | 대책 | 효과 |
|:---|:---|:---|
| 도메인별 분산 적재로 인한 데이터 사일로(Data Silo) 고립 | **전사 메타데이터 카탈로그(OpenMetadata/DataHub) 연동 의무화** | 전사 데이터 검색성 및 리니지 확보 |
| 도메인 팀별 중복 인프라 프로비저닝으로 클라우드 비용 폭증 | **셀프서비스 플랫폼에 중앙 FinOps 모니터링 및 쿼터제 적용** | 불필요한 중복 인프라 비용 차단 |
| 도메인 팀의 데이터 품질 무관심으로 인한 왜곡 데이터 유입 | **Data Contract 체결 및 위반 시 파이프라인 자동 중단 훅 설정** | 데이터 품질 SLA 보장 |

#### 한줄 요약

- 전사 카탈로그 연동, FinOps 비용 통제, Data Contract 품질 자동화를 통해 데이터 메시를 성공적으로 정착

## Ⅶ. 결론

<details><summary>용어 설명</summary>

- **조직과 기술의 조화(Socio-Technical Shift)**: 데이터 메시는 단순 기술 아키텍처가 아닌 조직의 책임 구조와 엔지니어링 문화를 혁신하는 사회-기술적 패러다임.

</details>

- **데이터 메시**는 마이크로서비스 사상을 데이터 분석 영역으로 확장한 현대적 패러다임이며, 강력한 셀프서비스 플랫폼과 연합 거버넌스를 토대로 현업 도메인의 데이터 주권을 확립하여 전사 데이터 가치를 극대화해야 함

#### 한줄 요약

- 4대 핵심 원칙을 기반으로 데이터 소유권을 도메인에 분산하고 데이터 제품화를 달성
