## Ⅰ. 개요

<details><summary>용어 설명</summary>

- **서비스 메시(Service Mesh)**: 마이크로서비스들끼리 통신할 때 개발자가 코드에 타임아웃, 인증, 추적 로직을 짤 필요 없이, 인프라 레이어(프록시)가 다 짬처리해 주는 그물망 같은 통신 제어 아키텍처이다.
- **컨트롤 플레인(Control Plane)**: 서비스 메시의 뇌(Brain) 역할로, 라우팅 룰이나 mTLS 인증서를 찍어내서 전방의 행동대장(데이터 플레인)들에게 뿌리고 명령을 내리는 사령부(Istiod)이다.
- **데이터 플레인(Data Plane)**: 사령부의 명령을 받고 실제 앱 컨테이너 옆에 찰싹 붙어서(사이드카), 들어오고 나가는 트래픽을 가로채서 암호화/차단/라우팅을 수행하는 행동대장 프록시(Envoy)이다.

</details>

- 정의: 앱 코드 수정 없이, 옆에 찰싹 붙은 프록시(사이드카)를 통해 서비스 간 통신/보안/관측을 멱살 잡고 통제하는 인프라 아키텍처인 **Service Mesh (Istio)**
- 배경: 100개의 서비스마다 통신 라이브러리(Spring Cloud 등)를 박아두면, 나중에 룰 바꿀 때 **수정 폭탄과 버전 파편화**가 터지기 때문

#### 한줄 요약

- 개발자는 비즈니스 로직만 짜게 냅두고, 복잡한 통신/보안 룰은 인프라(프록시)가 다 해주는 아키텍처다.

## Ⅱ. 특징

<details><summary>용어 설명</summary>

- **사이드카 패턴(Sidecar Pattern)**: 오토바이(앱) 옆에 타는 사이드카(Envoy 프록시)처럼, 동일한 컨테이너(Pod) 안에 프록시를 띄워 트래픽을 모조리 가로채서 대리 처리하는 배치 구조이다.
- **상호 인증(mTLS, Mutual TLS)**: 클라이언트만 서버를 믿는 게 아니라, 서버와 클라이언트 둘 다 서로 신분증(인증서)을 까서 찐인지 확인하고 통신을 암호화하는 영 트러스트(Zero Trust)의 핵심 보안 기술이다.

</details>

- 룰을 찍어내는 **Control Plane(사령부)**과 몸빵 하는 **Data Plane(행동대장)**으로 역할을 분리함.
- 앱 코드는 1도 안 건드리고 **Sidecar 프록시**만 붙여서 블루/그린 배포, 트래픽 쪼개기를 시전함.
- 서비스 통신을 **mTLS**로 강제 암호화해서, 해커가 중간에서 패킷을 털어도 못 읽게 팩트 폭행함.

#### 한줄 요약

- 뇌(사령부)와 몸(행동대장)을 분리하고, 사이드카로 낚아채서, mTLS로 암호화하는 게 핵심이다.

## Ⅲ. 구조 및 구성요소

<details><summary>용어 설명</summary>

- **Envoy Proxy**: Lyft에서 C++로 깎아 만든 미친 속도의 L7 프록시로, 서비스 메시의 행동대장(Data Plane) 역할을 싹쓸이한 표준 무기이다.
- **Istiod**: 뇌(Control Plane) 역할을 하는 단일 바이너리 데몬으로, 예전엔 파일럿, 시타델, 갤리로 찢어져 있던 통제 권한을 하나로 합친 Istio의 독재자이다.

</details>

```text
[ Istio 서비스 메시 십자포화 아키텍처 ]

                [ Istiod (사령부 / Control Plane) ]
                 (룰 세팅, 인증서 발급, xDS 명령)
                              │
     ┌────────────────────────┴────────────────────────┐
     ▼ (명령 하달)                                     ▼ (명령 하달)
[ Envoy 프록시 (데이터 플레인) ] ◀──(mTLS 통신)──▶ [ Envoy 프록시 (데이터 플레인) ]
        │ (트래픽 가로채기)                              │ (트래픽 가로채기)
[ 주문 워크로드 (App) ]                           [ 결제 워크로드 (App) ]
```

| 구성요소 | 책임 |
|:---|:---|
| **Istiod (제어 플레인)** | 룰과 인증서를 만들어서 행동대장(Envoy)들에게 쏘는(xDS) 총사령관 |
| **Envoy (데이터 플레인)** | 앱 옆에 사이드카로 붙어서 통신을 낚아채 라우팅, 암호화를 집행하는 행동대장 |
| 워크로드 (비즈니스 앱) | "난 통신은 모르겠고 로직만 짠다"며 Envoy 등 뒤에 숨어있는 찐 애플리케이션 |
| 텔레메트리 (Jaeger 등) | Envoy들이 보내온 로그와 트레이스를 까보고 병목을 찾는 CCTV |

#### 단답 요약

- Istiod가 명령 내리면, Envoy가 낚아채서 통신하고, Jaeger가 감시한다.

## Ⅳ. 흐름도

<details><summary>용어 설명</summary>

- **xDS 프로토콜(xDS Protocol)**: "야 프록시 재시작 안 해도 되니까 라우팅 룰 당장 이걸로 바꿔!" 라며 사령부(Istiod)가 행동대장(Envoy)에게 실시간으로 룰(RDS, CDS 등)을 때려 박는 gRPC 통신 규약이다.

</details>

```text
[ 서비스 메시 트래픽 가로채기 십자포화 흐름 ]
┌──────────────────────────────┐
│ 1. 정책 동기화 (Istiod ➔ Envoy)│
│ (사령부가 룰을 프록시에 깔아줌)│
└──────────────┬───────────────┘
               ▼
┌──────────────────────────────┐
│ 2. 앱이 요청 보냄 ➔ Envoy 낚아챔│
│ (아웃바운드 트래픽 가로채기) │
└──────────────┬───────────────┘
               ▼
┌──────────────────────────────┐
│ 3. Envoy 간 mTLS 암호화 통신 │
│ (프록시끼리 신분증 까고 보안 통신)│
└──────────────┬───────────────┘
               ▼
┌──────────────────────────────┐
│ 4. 타깃 Envoy의 인바운드 인가│
│ (접근 허용 룰에 맞는지 팩트체크)│
└──────────────┬───────────────┘
               ▼
┌──────────────────────────────┐
│ 5. 최종 목적지(앱)로 딜리버리│
└──────────────────────────────┘
```

### 동작 원리

1. 정책 셋업: Istiod가 "A에서 B로 가는 트래픽 막아" 룰을 xDS로 깔아줌.
2. 아웃바운드 낚아채기: A 앱이 쏘면, A의 사이드카(Envoy)가 삥 뜯듯 가로챔.
3. mTLS 통신: A Envoy가 B Envoy한테 상호 인증(mTLS) 맺고 쏨.
4. 인바운드 검증: B Envoy가 트래픽을 받고 "이거 받아도 돼?" 룰을 검사함.
5. 앱 전달: 룰 패스하면 B 앱한테 넘겨서 비즈니스 로직 태움.

#### 한줄 요약

- 룰 세팅 $\to$ 가로채기 $\to$ mTLS 암호화 $\to$ 인가 검사 $\to$ 앱에 전달하는 흐름이다.

## Ⅴ. 종류 및 비교

<details><summary>용어 설명</summary>

- **앰비언트 메시 (Ambient Mesh)**: 모든 팟(Pod)마다 사이드카를 달면 메모리 잡아먹고 느려지니까, 사이드카를 빼버리고 노드당 1개의 경량 L4 프록시(ztunnel)와 필요할 때만 쓰는 L7 프록시(Waypoint)로 퉁치는 최신 쌉가성비 모드이다.

</details>

| 비교 항목 | **사이드카 모드 (전통적 Istio)** | **앰비언트 모드 (최신 Ambient)** |
|:---|:---|:---|
| 프록시 주입 위치 | **모든 앱(Pod)마다 1:1로 옆에 딱 붙임** | **노드당 1개(ztunnel)** + 옵션 L7(Waypoint) |
| 자원 소모 (메모리) | 프록시가 너무 많아 **자원 낭비 개쩜 (무거움)** | 노드 공유로 **중복 프록시 걷어내서 쌉가벼움** |
| 업데이트 방식 | 프록시 업뎃 시 **앱(Pod)도 껐다 켜야 됨** | 앱 재시작 없이 프록시만 스무스하게 업뎃 가능 |
| 보안 처리 스택 | 처음부터 L4 ~ L7 풀스택으로 무겁게 팸 | 일단 L4(mTLS)만 치고 L7은 필요할 때만 팸 |

#### 한줄 요약

- 무겁고 빡센 사이드카의 단점을 돈(자원) 아끼면서 풀어낸 게 앰비언트 메시(Ambient Mesh)다.

## Ⅵ. 실무 고려사항 및 대책

<details><summary>용어 설명</summary>

- **사이드카 풋프린트(Sidecar Footprint)**: 1000개의 팟(Pod)을 띄웠더니 사이드카 1000개가 메모리와 CPU를 좀먹어서, 배보다 배꼽이 커지는 인프라 오버헤드 현상이다.

</details>

| 문제 | 대책 | 효과 |
|:---|:---|:---|
| 팟마다 사이드카가 붙어 메모리가 터짐 (**풋프린트**) | 가벼운 **Ambient Mesh**로 갈아타거나 억세스 제한 | 무지성 자원 낭비 멱살 잡고 방어 |
| 프록시를 2번 거치면서 통신 속도가 느려 터짐 | 안 쓰는 L7 필터 싹 끄고, 타임아웃 빡세게 설정 | 홉(Hop) 때문에 생기는 레이턴시 병목 억제 |
| Istio 업뎃하다가 룰 꼬여서 전체 통신망 폭파됨 | 카나리아(Canary) 방식으로 **Revision** 달아서 찔끔 적용 | 문제 터지면 옛날 버전으로 1초 컷 롤백 |

#### 한줄 요약

- 자원 낭비(풋프린트)는 앰비언트로 막고, 속도는 필터 다이어트로 살리며, 업뎃은 카나리아로 쳐라.

## Ⅶ. 결론

<details><summary>용어 설명</summary>

- **서비스 메시 도입 기준(Service Mesh Adoption Criteria)**: 마이크로서비스가 50개가 넘어 통제가 안 되고, Zero-Trust(mTLS) 보안이 강제되는지 각 재서 무거운 Istio를 얹을지 결정하는 잣대이다.

</details>

- **서비스 메시 도입 기준** 원칙에 따라, 짬뽕 언어에 강력한 mTLS 통제가 필요하면 **Service Mesh**, 서버가 몇 개 없으면 **라이브러리(Spring Cloud 등)** 채택 기조 확립함

#### 한줄 요약

- 닭 잡는 데 소 잡는 칼 쓰지 말고, 진짜 수십 개 서비스가 난장판일 때만 Istio를 얹어라.
