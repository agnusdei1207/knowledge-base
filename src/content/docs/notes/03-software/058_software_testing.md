## Ⅰ. 개요

<details><summary>용어 설명</summary>

- **소프트웨어 테스트(Software Testing)**: 코드가 내 맘대로 잘 도는지, 유저가 쓰다가 뻗진 않는지 버그(결함)를 찾아내서 출시 전에 박살 내는 일련의 삽질(활동)이다.
- **V-Model 검증 및 확인(V&V)**: Verification(검증)은 "설계서대로 잘 짰냐?"고 개발자 시점에서 따지는 거고, Validation(확인)은 "유저가 원하는 거 맞냐?"고 고객 시점에서 따지는 잣대이다.
- **테스트 피라미드(Test Pyramid)**: UI/E2E 테스트같이 느리고 잘 깨지는 비싼 테스트는 꼭대기에 조금만 두고, 빠르고 싼 단위 테스트(Unit)를 밑바닥에 오지게 깔아두라는 가성비 전략이다.

</details>

- 정의: 코드 짜면서 생긴 버그를 잡고, 설계서(Verification)와 사용자 요구(Validation)를 제대로 만족하는지 털어보는 **Software Testing 4대 단계**
- 배경: 버그를 배포 날 잡으면 개발 때 잡는 것보다 **수정 비용이 100배는 더 깨지고 서버가 터지기** 때문

#### 한줄 요약

- 배포 날 서버 터지고 유저한테 욕먹기 전에, 미리 버그를 잡고 원하는 대로 도는지 검사하는 거다.

## Ⅱ. 특징

<details><summary>용어 설명</summary>

- **테스트 오라클(Test Oracle)**: 테스트 돌렸을 때 "이게 맞는 결과냐, 틀린 결과냐"를 판정하기 위해 미리 적어둔 절대적인 정답지(기대값)이다.
- **회귀 테스트(Regression Testing)**: A 기능 고쳤더니 멀쩡하던 B 기능이 뻗는 대참사(Side Effect)를 막기 위해, 배포할 때마다 옛날 테스트를 다시 돌려보는 짓이다.

</details>

- 개발 단계와 1:1로 매칭되는 **V-Model** 기반의 단위 $\to$ 통합 $\to$ 시스템 $\to$ 인수 테스트 구조.
- 정답지(**Test Oracle**)를 만들어놓고 팩트 기반으로 Pass/Fail 판정.
- 코드 고칠 때마다 **Regression Testing(회귀 테스트)**을 자동화해서 부작용 차단.

#### 한줄 요약

- V모델을 타고 올라가며 검사하고, 정답지(오라클)로 채점하며, 고칠 때마다 다시 검사(회귀)한다.

## Ⅲ. 구조 및 구성요소

<details><summary>용어 설명</summary>

- **4대 테스트 레벨**: 함수 하나만 0.1초 만에 검사하는 '단위', 모듈끼리 통신 꼬이는지 보는 '통합', 실제 서버랑 똑같이 올려놓고 쥐어짜는 '시스템', 고객이 도장 찍어주는 '인수' 테스트이다.

</details>

```text
[ V-Model 4대 테스트 십자포화 아키텍처 ]

[ 요구사항 분석 ] ────────────────────▶ [ 인수 테스트 (고객 OK?) ]
        │                                       ▲
[ 아키텍처 설계 ] ───────────────▶ [ 시스템 테스트 (부하/보안) ]
              │                         ▲
       [ 모듈 설계 ] ────────▶ [ 통합 테스트 (DB/API 연동) ]
                   │              ▲
                   ▼              │
              [ 코딩 (단위 테스트) ]
```

| 구성요소 | 팩트 폭행 책임 |
|:---|:---|
| **단위 테스트 (Unit)** | 함수나 클래스 하나만 고립시켜서 로직이 맞는지 0.1초 만에 검증하는 갓성비 방어막 |
| **통합 테스트 (Integration)** | A 모듈과 B 모듈, 또는 DB/API를 이어 붙였을 때 데이터가 안 꼬이는지 확인 |
| **시스템 테스트 (System)** | 실제 운영 서버랑 똑같은 환경에서 기능은 물론 부하(성능), 보안까지 다 쥐어짜 봄 |
| **인수 테스트 (Acceptance)**| 고객(현업)이 직접 마우스 딸깍거려보고 "이거 결제할게요" 도장 찍어주는 최종 관문 |

#### 한줄 요약

- 코딩할 땐 단위 $\to$ 붙일 땐 통합 $\to$ 띄울 땐 시스템 $\to$ 팔기 전엔 인수 테스트를 거친다.

## Ⅳ. 흐름도

<details><summary>용어 설명</summary>

- **테스트 대역(Test Double)**: 단위 테스트할 때 DB나 외부 API가 없어서 못 한다는 핑계를 막기 위해, 진짜 대신 투입하는 '가짜 객체(Mock, Stub 등)' 묶음이다.

</details>

```text
[ 테스트 실행 십자포화 흐름 ]
┌──────────────────────────────┐
│ 1. 테스트 케이스 & 오라클 짬 │
│ ("1+1 넣으면 2 나와야 함")   │
└──────────────┬───────────────┘
               ▼
┌──────────────────────────────┐
│ 2. 픽스처 & 가짜 객체 세팅   │
│ (DB 대신 Mock 객체 꽂음)     │
└──────────────┬───────────────┘
               ▼
┌──────────────────────────────┐
│ 3. 냅다 테스트 실행          │
│ (JUnit Run 버튼 딸깍)        │
└──────────────┬───────────────┘
               ▼
┌──────────────────────────────┐
│ 4. 정답지(Oracle)와 비교     │
│ (실제 2 나왔네? Pass!)       │
└──────────────┬───────────────┘
               ▼
┌──────────────────────────────┐
│ 5. 버그 수정 및 회귀 테스트  │
│ (Fail 뜨면 고치고 다시 돌림) │
└──────────────────────────────┘
```

### 동작 원리

1. 케이스 설계: "이거 넣으면 저거 나와야 함" 하고 정답지(Oracle)를 미리 씀.
2. 환경/대역 세팅: DB 접속하면 느리니까 Mock(가짜 객체) 꽂아서 격리시킴.
3. 실행: 봇(CI)이 테스트 코드들을 눈썹 휘날리게 돌림.
4. 판정: 정답지랑 실제 결과가 같은지 팩트 체크함.
5. 피드백: 틀리면 지라(Jira)에 버그 등록하고, 고치면 다시 돌림(회귀 테스트).

#### 한줄 요약

- 룰 짜고 $\to$ 가짜 객체 박고 $\to$ 실행해서 $\to$ 정답지랑 맞춰보고 $\to$ 고치는 무한 반복이다.

## Ⅴ. 종류 및 비교

<details><summary>용어 설명</summary>

- **스텁(Stub) vs 목(Mock)**: Stub은 부르면 "미리 적어둔 500원 반환해" 하는 멍청한 로봇이고, Mock은 "어? 너 아까 나 두 번 불렀고 파라미터로 300원 넣었잖아" 하고 행위까지 따지는 감시자이다.

</details>

| Test Double 종류 | 팩트 폭행 정의 |
|:---|:---|
| **Dummy** | 파라미터 자리만 채우고 아무 일도 안 하는 깡통 객체 |
| **Fake** | 진짜 DB 쓰면 느리니까 HashMap(메모리)으로 대충 구라 친 객체 |
| **Stub** | 찌르면 미리 세팅해 둔 하드코딩 값만 앵무새처럼 뱉는 멍청한 객체 |
| **Spy** | Stub처럼 행동하면서, "얘가 나 몇 번 불렀나" 몰래 기록해 두는 쁘락치 |
| **Mock** | 결과값 반환은 물론, "이 순서대로 파라미터 넣어서 호출했냐?" 따지는 깐깐한 객체 |

#### 한줄 요약

- 진짜를 띄우기 버거울 땐 가짜(Test Double)를 박아서 무조건 테스트가 돌아가게 만들어야 한다.

## Ⅵ. 실무 고려사항 및 대책

<details><summary>용어 설명</summary>

- **결함 유입 비용(Defect Inflow Cost)**: 기획할 때 오타 하나 고치면 10원이지만, 배포 끝나고 유저가 그 오타 때문에 결제 실패하면 100만 원 깨진다는 살벌한 가성비의 법칙이다.

</details>

| 문제 | 대책 | 효과 |
|:---|:---|:---|
| 셀레니움(E2E)만 떡칠해서 CI 도는 데 2시간 걸림 | **Test Pyramid** 원칙에 따라 빠른 단위 테스트(Unit) 비중 폭발시킴 | 피드백 1분 컷으로 줄여서 퇴근 시간 보장 |
| DB 연결 안 되면 테스트 못 한다고 개발자가 징징댐 | **Mockito** 같은 **Test Double (Mock/Stub)** 억지로 먹임 | 오프라인에서도 눈썹 휘날리게 빠른 격리 테스트 가능 |
| A 고쳤더니 멀쩡하던 B 기능 터져서 멱살 잡힘 | 파이프라인에 **Automated Regression Test** 박아둠 | 사이드 이펙트 터지기 전에 봇이 멱살 잡고 컷냄 |

#### 한줄 요약

- 무조건 빠르고 싼 단위 테스트를 많이 짜고, DB 없어도 핑계 대지 말고 Mock 박아서 테스트해라.

## Ⅶ. 결론

<details><summary>용어 설명</summary>

- **소프트웨어 테스트 수립 기준(Software Testing Strategy Standards)**: V-Model 검증 레벨을 탔는지, 테스트 피라미드 비율은 황금비율인지, 회귀 테스트는 봇이 돌리는지 각 재는 잣대이다.

</details>

- **소프트웨어 테스트 수립 기준** 원칙에 따라, 내부 로직은 닥치고 **단위 테스트**, 모듈 간 통신은 **통합 테스트**, 고객 확인은 **인수 테스트** 채택 기조 확립함

#### 한줄 요약

- 테스트 코드를 짤 시간이 없는 게 아니라, 테스트를 안 짜니까 버그 잡느라 시간이 없는 거다.
