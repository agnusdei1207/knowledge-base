## Ⅰ. 개요

<details>
<summary>핵심 용어</summary>

- **소프트웨어 테스트(Software Testing)**: 실행 결과와 기대 결과를 비교해 결함을 발견하고 품질 근거를 제공하는 활동이다.
- **검증(Verification)**: 개발 산출물이 명세와 설계에 맞게 만들어졌는지 확인하는 활동이다.
- **확인(Validation)**: 완성된 시스템이 사용자 요구와 사용 목적을 충족하는지 확인하는 활동이다.

</details>

- 정의/개념: 실행 결과를 기대 결과와 비교해 결함과 품질 근거를 도출하는 **소프트웨어 테스트** 활동이다.
- 배경/필요성: 개발자 단독 확인으로 연동 결함과 업무 결함이 누락될 수 있다.
- 품질 판단: 산출물의 명세 적합성은 **검증**, 사용 목적 충족은 **확인**이 핵심이다.

#### 한줄 요약

- **소프트웨어 테스트**로 실제 결과와 **기대 결과**를 비교하는 것이 핵심이다.

## Ⅱ. 특징

<details>
<summary>핵심 용어</summary>

- **기대 결과(Expected Result)**: 입력과 사전 조건에 대해 시스템이 보여야 할 올바른 동작이나 값이다.
- **회귀 테스트(Regression Testing)**: 변경 후 기존 기능이 손상되지 않았는지 이전 테스트를 다시 실행하는 활동이다.

</details>

- 테스트 단계에 따라 검증 대상과 책임을 분리한다.
- **기대 결과**를 기준으로 합격과 실패를 판정한다.
- 변경 후 **회귀 테스트**로 기존 기능 손상을 확인한다.

#### 한줄 요약

- **기대 결과**에 따른 판정과 **회귀 테스트**가 핵심이다.

## Ⅲ. 구조 및 구성요소

<details>
<summary>핵심 용어</summary>

- **테스트 케이스(Test Case)**: 입력•사전 조건•기대 결과와 실행 절차를 묶은 검증 항목이다.
- **테스트 픽스처(Test Fixture)**: 테스트를 같은 조건에서 반복하도록 준비한 데이터•객체•환경 상태이다.
- **테스트 오라클(Test Oracle)**: 시험 결과가 옳은지 판단할 기대 결과•규칙•참조값이다.
- **테스트 근거(Test Basis)**: 테스트 조건과 기대 결과를 도출하는 요구•설계•업무 규칙이다.
- **테스트 실행기(Test Runner)**: 대상 코드를 정한 조건에서 실행하고 실제 결과•시간•오류를 수집하는 도구이다.
- **결과 저장소(Result Repository)**: 통과 증거를 요구와 연결해 보관하는 저장소이다.
- **결함 저장소(Defect Repository)**: 실패 조건과 영향 및 처리 상태를 보관하는 저장소이다.

</details>

```text
      [테스트 근거]
            |
[테스트 케이스] --- [테스트 픽스처]
            |
     [테스트 실행기]
            |
   [결과•결함 저장소]
```

선의 의미: 세로선은 테스트 근거에서 케이스와 실행기를 거쳐 결과•결함 저장소로 이어지는 검증 경로이고, 가로선은 테스트 케이스와 반복 조건인 픽스처의 결합 관계이다.

| 구성요소 | 책임 |
|:---|:---|
| 테스트 근거 | 요구•설계의 검증 조건 제공 |
| 테스트 케이스 | 입력•**기대 결과**와 절차 정의 |
| 테스트 픽스처 | 반복 가능한 데이터•환경 상태 구성 |
| 테스트 실행기 | 대상 실행과 실제 결과 수집 |
| 결과•결함 저장소 | **결과 저장소**와 **결함 저장소**에 증거•재현 조건 추적 |

#### 한줄 요약

- **테스트 근거**, **테스트 케이스**, **테스트 픽스처**, **테스트 실행기**, **결과 저장소**, **결함 저장소**의 연결 구조가 핵심이다.

## Ⅳ. 흐름도

<details>
<summary>핵심 용어</summary>

- **테스트 조건 구성(Test Condition Setup)**: 요구와 설계에서 입력•사전 조건•기대 결과를 도출하는 동작이다.
- **시험 대상 실행(System Under Test Execution)**: 재현 가능한 픽스처에서 대상을 실행해 실제 결과를 수집하는 동작이다.
- **오라클 판정(Oracle Decision)**: 실제 결과와 기대 결과 및 허용 범위를 비교하는 동작이다.
- **통과 증거 기록(Pass Evidence Recording)**: 일치한 결과를 검증한 요구와 연결해 보존하는 동작이다.
- **결함 증거 기록(Defect Evidence Recording)**: 불일치 결과의 조건•영향•재현 정보를 보존하는 동작이다.
- **재현 조건(Reproduction Condition)**: 같은 결함을 다시 발생시키는 입력•데이터•환경•실행 순서이다.

</details>

```text
[요구•설계•업무 규칙]
          |
          v
+-------------------------+
| 1. 테스트 조건 구성     |
+-------------------------+
          |
          v
+-------------------------+
| 2. 시험 대상 실행       |
+-------------------------+
          |
          v
+-------------------------+
| 3. 오라클 판정          |
+-------------------------+
          |
     +----+----+
     | 일치    | 불일치
     v         v
+-------------------+  +-------------------+
| 4. 통과 증거 기록 |  | 5. 결함 증거 기록 |
+-------------------+  +-------------------+
     |                         |
     v                         v
[요구 추적 근거]       [재현•수정•회귀 시험]
```

### 동작 원리

1. **테스트 조건 구성**: 요구에서 입력•기대 결과를 도출한다.
2. **시험 대상 실행**: 재현 가능한 조건에서 결과를 수집한다.
3. **오라클 판정**: 실제•기대 결과의 일치를 비교한다.
4. **통과 증거 기록**: 검증한 요구와 결과를 연결한다.
5. **결함 증거 기록**: 조건•영향•재현 정보를 보존한다.

> 요약: **테스트 조건 구성**과 **시험 대상 실행** 후 **오라클 판정** 결과를 통과 또는 결함 증거로 기록한다.

#### 한줄 요약

- **오라클 판정**에 따른 **통과 증거 기록**과 **결함 증거 기록**이 핵심이다.

## Ⅴ. 종류 및 비교

<details>
<summary>핵심 용어</summary>

- **단위 테스트(Unit Testing)**: 함수•클래스•모듈 등 최소 코드 단위의 내부 동작을 격리해 검증하는 테스트이다.
- **통합 테스트(Integration Testing)**: 결합된 모듈•서비스 사이의 인터페이스와 데이터 흐름을 검증하는 테스트이다.
- **시스템 테스트(System Testing)**: 완성된 전체 시스템의 기능•성능•보안 등 요구사항을 검증하는 테스트이다.
- **인수 테스트(Acceptance Testing)**: 사용자•발주자의 업무•계약 기준 충족 여부를 검증해 수용을 결정하는 테스트이다.
- **종단 시험(End-to-end Test)**: 사용자 진입점부터 실제 하위 구성요소까지 전체 요청 흐름을 검증하는 시스템 시험이다.
- **비기능 요구(Non-functional Requirement)**: 성능•보안•가용성처럼 시스템이 기능을 어떤 품질로 제공해야 하는지 정한 요구이다.

</details>

| 테스트 단계 | 검증 경계 | 발견에 유리한 결함 |
|:---|:---|:---|
| **단위 테스트** | 함수•클래스의 개별 로직 | 분기•경계값•예외 처리 오류 |
| **통합 테스트** | 모듈•서비스의 인터페이스와 데이터 흐름 | 계약•직렬화•연동 오류 |
| **시스템 테스트** | 운영 유사 환경의 **종단 시험**으로 기능•**비기능 요구** 검증 | 전체 흐름•성능•보안 결함 |
| **인수 테스트** | 사용자 업무 시나리오와 계약 기준 | 업무 규칙과 수용 조건 불일치 |

> 요약: 코드에서 사용자 수용까지 검증 범위와 책임을 확대한다.

#### 한줄 요약

- **단위 테스트**, **통합 테스트**, **시스템 테스트**, **인수 테스트** 순으로 검증 경계가 확대된다.

## Ⅵ. 실무 고려사항 및 대책

<details>
<summary>핵심 용어</summary>

- **테스트 더블(Test Double)**: 실제 의존 대상을 대신해 입력•출력•상호작용을 통제하는 대체 객체의 상위 개념이다.
- **위험 기반 테스트(Risk-based Testing)**: 결함 가능성과 영향이 큰 영역에 시험 우선순위와 자원을 배분하는 방식이다.
- **경계값 분석(Boundary Value Analysis)**: 입력 범위의 최소•최대와 그 주변에서 결함이 많다는 점을 이용한 설계 기법이다.
- **허용 범위(Tolerance)**: 측정 오차나 업무 규칙상 기대값에서 벗어나도 합격으로 인정할 수 있는 한계이다.
- **독립 픽스처(Independent Fixture)**: 시험마다 별도 초기 상태를 준비하는 방식이다.
- **격리 데이터(Isolated Data)**: 다른 시험과 공유하지 않는 전용 시험 데이터이다.
- **영향 기반 선별(Impact-based Selection)**: 변경된 코드와 계약으로 회귀 시험을 고르는 방식이다.
- **위험 기반 선별(Risk-based Selection)**: 결함 영향도로 회귀 시험 우선순위를 정하는 방식이다.

</details>

| 문제 | 대책 | 효과 |
|:---|:---|:---|
| 단위 시험에 편중돼 연동•업무 결함이 누락됨 | **위험 기반 테스트**에 따라 **통합 테스트**, **시스템 테스트**, **인수 테스트** 조합 | 연동•업무 결함 탐지 |
| 기대 결과와 허용 오차가 명확하지 않음 | **테스트 오라클**과 **허용 범위** 명시 | 객관적 판정 확보 |
| 실행마다 데이터와 환경 상태가 달라짐 | **독립 픽스처**와 **격리 데이터** 구성 | 시험 재현성 확보 |
| **테스트 더블**만 검증해 실제 계약과 달라짐 | 실제 계약 대상의 핵심 **통합 테스트** 병행 | 구현 불일치 탐지 |
| 변경마다 전체 회귀 시험을 실행해 지연됨 | **영향 기반 선별**과 **위험 기반 선별** 후 전체 회귀 병행 | 피드백 시간 통제 |
| 입력 범위 끝부분의 계산 결함이 누락됨 | **경계값 분석**과 **단위 테스트** 적용 | 경계 결함 탐지 |

#### 한줄 요약

- **위험 기반 테스트**, **경계값 분석**, **독립 픽스처**에 기반한 시험 조합이 핵심이다.

## Ⅶ. 결론

<details>
<summary>핵심 용어</summary>

- **검증 범위(Test Scope)**: 단위 로직부터 연동, 전체 시스템, 업무 수용까지 시험이 다루는 대상의 경계이다.
- **수용 기준(Acceptance Criteria)**: 사용자가 시스템을 받아들일 수 있는지 판단하는 업무•계약 조건이다.
- **테스트 단계 선택 기준**: 결함 대상이 개별 로직•구성요소 연동•전체 비기능•업무 수용 중 어디에 있는지에 따라 검증 단계를 정하는 기준이다.

</details>

- **테스트 단계 선택 기준**에 따라 로직 결함은 **단위 테스트**, 연동은 **통합 테스트**, **비기능 요구**는 **시스템 테스트**, **수용 기준**은 **인수 테스트**로 검증한다.

#### 한줄 요약

- **검증 범위**와 결함 유형에 맞는 **테스트 단계 선택 기준**이 핵심이다.
