## Ⅰ. 개요

<details><summary>용어 설명</summary>

- **V-모델 4단계 및 검증/확인(V-Model & V&V)**: 단위, 통합, 시스템, 인수 단계별로 요구명세 일치성(Verification)과 사용자 의도 충족성(Validation)을 교차 검증하는 구조.
- **수정 비용 지수적 폭증(Boehm Defect Cost Curve)**: 요구분석 단계 결함이 배포 후 운영 단계에서 발견될 경우 수정 비용이 최대 100배 이상 폭증하는 현상.

</details>

- 정의/개념: 소프트웨어 결함을 사전에 식별하고 품질을 보증하기 위해 **V-모델 기반 4단계(단위·통합·시스템·인수) 및 검증/확인(V&V)** 을 수행하는 공학 활동
- 배경/필요성: 개발 후반부 결함 발견 시 발생하는 **수정 비용 지수적 폭증(Boehm 법칙) 및 서비스 장애 위험** 직면

#### 한줄 요약

- V-Model 기반 4단계 테스트로 결함을 조기 탐지하고 수정 비용을 최소화하는 품질 보증 체계

## Ⅱ. 특징

<details><summary>용어 설명</summary>

- **테스트 오라클(Test Oracle)**: 테스트 실행 결과의 정오(Pass/Fail)를 판정하기 위한 사전 정의된 기대값 집합.
- **회귀 테스트(Regression Testing)**: 코드 변경 후 기존 기능의 부작용(Side Effect)을 탐지하기 위해 기존 테스트 케이스를 재실행하는 테스트 활동.

</details>

- V-Model 기반 **단위→통합→시스템→인수** 4단계 계층적 테스트 구조
- **테스트 오라클** 기반 객관적 Pass/Fail 판정 체계
- 코드 변경 시마다 **회귀 테스트 자동화** 기반 부작용 조기 탐지

#### 한줄 요약

- V-Model 4단계·오라클 기반 판정·회귀 자동화로 체계적 결함 탐지 및 품질 보증

## Ⅲ. 구조 및 구성요소

<details><summary>용어 설명</summary>

- **4대 테스트 레벨**: 단위 테스트(함수·클래스 단독 검증)·통합 테스트(모듈 간 인터페이스 검증)·시스템 테스트(전체 시스템 성능·보안·기능 검증)·인수 테스트(사용자 요구 충족 최종 확인).

</details>

```text
[ V-Model 테스트 단계 구조 ]
요구사항 분석 ────────────────────▶ 인수 테스트 (고객 요구 충족 확인)
      │                                  ▲
아키텍처 설계 ─────────────────▶ 시스템 테스트 (성능·보안·기능)
            │                       ▲
       모듈 설계 ──────────▶ 통합 테스트 (모듈·DB·API 인터페이스)
                 │                ▲
                 └────▶ 단위 테스트 (함수·클래스 단독)
```

선의 의미: V-Model의 좌측 하강 화살표는 개발 단계, 우측 상승 화살표는 대응하는 테스트 단계, V의 하단 꼭짓점은 단위 테스트(코딩)

| 구성요소 | 책임 |
|:---|:---|
| **단위 테스트(Unit)** | 함수·클래스 단독 격리 검증, 빠른 피드백 |
| **통합 테스트(Integration)** | 모듈 간 인터페이스·DB·외부 API 연동 검증 |
| **시스템 테스트(System)** | 전체 시스템의 기능·성능·보안·신뢰성 검증 |
| **인수 테스트(Acceptance)** | 사용자 요구사항 충족 여부 최종 확인 및 고객 승인 |

#### 한줄 요약

- 단위→통합→시스템→인수의 V-Model 4단계로 코딩 단계부터 인수 단계까지 결함을 계층적으로 탐지

## Ⅳ. 흐름도

<details><summary>용어 설명</summary>

- **테스트 대역(Test Double)**: 외부 의존성(DB·API)을 대체하여 단위 테스트의 격리 환경을 구성하는 Mock·Stub·Fake 등의 가짜 객체.

</details>

```text
1. 테스트 케이스 설계 및 오라클 정의
   └─ 입력값·기대 출력값·판정 기준 정의
   │
   ▼
2. 테스트 환경 준비 (픽스처·테스트 대역 구성)
   └─ 외부 의존성을 Mock/Stub으로 대체·격리
   │
   ▼
3. 테스트 실행 (CI 자동화)
   │
   ▼
4. 오라클 대비 결과 판정 (Pass/Fail)
   │
   ▼
5. 결함 등록·수정 후 회귀 테스트 재실행
```

**동작 원리** 1. **케이스 설계**: 요구사항 기반으로 테스트 케이스와 오라클(기대값)을 정의
2. **환경 준비**: DB·외부 API를 Test Double(Mock/Stub)로 대체하여 격리 환경 구성
3. **자동 실행**: CI 파이프라인에서 테스트를 자동으로 실행
4. **오라클 판정**: 실제 결과와 기대값을 비교하여 Pass/Fail 판정
5. **회귀 수행**: 결함 수정 후 전체 테스트를 재실행하여 부작용 검증

#### 한줄 요약

- 오라클 정의→환경 격리→자동 실행→판정→수정·회귀의 체계적 테스트 수행 흐름

## Ⅴ. 종류 및 비교

<details><summary>용어 설명</summary>

- **Stub vs Mock**: Stub은 사전 정의된 값만 반환하는 단순 대역, Mock은 호출 횟수·파라미터·순서 등 행위까지 검증하는 스마트 대역.

</details>

| Test Double 종류 | 정의 및 용도 |
|:---|:---|
| **Dummy** | 파라미터 자리만 채우는 값, 실제 동작 없음 |
| **Fake** | 실제 구현의 단순화 버전(인메모리 DB 등) |
| **Stub** | 사전 정의된 고정 응답만 반환 |
| **Spy** | Stub 기능 + 호출 기록 추적 |
| **Mock** | 응답 반환 + 호출 방식(횟수·파라미터·순서) 행위 검증 |

#### 한줄 요약

- 외부 의존성을 Test Double로 대체하여 테스트를 격리하고 신속하게 실행

## Ⅵ. 실무 고려사항 및 대책

<details><summary>용어 설명</summary>

- **결함 발견 비용(Defect Detection Cost)**: 개발 단계에서 발견한 결함 수정 비용은 낮지만, 운영 배포 후 발견 시 비용이 수십~수백 배 이상 증가하는 결함 탐지 시점별 비용 원칙.

</details>

| 문제 | 대책 | 효과 |
|:---|:---|:---|
| UI/E2E 테스트 위주로 CI 실행 시간 과다 발생 | **테스트 피라미드** 원칙에 따라 단위 테스트 비중 확대 | CI 피드백 주기 단축 |
| 외부 DB·API 의존으로 단위 테스트 실행 불가 | **Mockito** 등 Test Double(Mock/Stub) 적용 | 외부 의존성 없는 빠른 격리 테스트 실현 |
| 코드 변경 후 기존 기능 부작용 미탐지 | CI 파이프라인에 **자동화 회귀 테스트** 통합 | 변경 부작용 조기 탐지 |

#### 한줄 요약

- 테스트 피라미드로 속도를 확보하고, Test Double로 격리를 보장하며, 회귀 자동화로 부작용을 탐지

## Ⅶ. 결론

<details><summary>용어 설명</summary>

- **소프트웨어 테스트 전략 수립 기준**: V-Model 단계 적용 여부·테스트 피라미드 비율·회귀 자동화 수준을 기준으로 테스트 전략의 효과성을 평가하는 판단 기준.

</details>

- 단위 테스트 기반 테스트 피라미드로 조기 결함 탐지를 확보하고 V-Model 4단계를 체계적으로 수행하여 품질을 보증

#### 한줄 요약

- 결함 탐지 비용 최소화를 위해 단위 테스트 위주의 조기 검증과 V-Model 기반 단계별 체계적 테스트를 수행
