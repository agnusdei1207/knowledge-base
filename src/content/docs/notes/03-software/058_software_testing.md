## Ⅰ. 개요

<details><summary>용어 설명</summary>

- **소프트웨어 테스팅**: 요구사항 명세와의 일치성(Verification)과 사용자의 실질적 필요 충족(Validation)을 검증하여 결함을 조기에 찾아내는 품질 보증 활동.
- **Boehm의 결함 비용 곡선**: 요구분석 단계의 결함이 배포/운영 단계에서 발견될 경우 수정 비용이 최대 100배 이상 폭증한다는 소프트웨어 공학 법칙.

</details>

- 정의/개념: 결함을 사전에 식별하고 품질을 보증하기 위해 **V-모델 4단계(단위·통합·시스템·인수) 및 V&V(검증/확인)** 를 수행하는 공학 활동
- 배경/필요성: 소프트웨어 개발 후반부나 운영 배포 이후 결함 발견 시 수정 비용이 최대 100배 이상 폭증하는 현상(Boehm의 결함 비용 법칙)과 회귀 결함으로 인한 시스템 불안정성을 극복하고, V-Model 개발 단계와 대칭되는 4대 테스트 레벨(단위·통합·시스템·인수)과 검증/확인(V&V) 및 테스트 오라클 체계를 통해 **결함을 생애주기 초기 단계에서 선제적으로 회수하고 소프트웨어 품질 무결성을 보증**할 필요

#### 한줄 요약
- V-Model 4단계 테스트로 결함을 조기 탐지하고 결함 수정 비용을 극소화한다.

## Ⅱ. 특징

<details><summary>용어 설명</summary>

- **테스트 오라클(Test Oracle)**: 테스트 실행 결과가 참인지 거짓인지 판단하기 위해 사전에 정의된 정답(Expected Result) 기준.
- **회귀 테스트(Regression Testing)**: 소스 코드 수정 후 새로운 결함(Side Effect)이 발생하지 않았음을 입증하기 위해 기존 테스트를 재수행하는 활동.

</details>

- V-Model 기반 **단위 $\to$ 통합 $\to$ 시스템 $\to$ 인수** 4단계 계층적 결함 격리
- 참 오라클, 샘플링 오라클, 일관성 오라클 등 **테스트 오라클** 기반 객관적 Pass/Fail 판정
- 소스 코드 변경 시마다 즉각 실행되는 **자동화된 회귀 테스트(Regression Test)**

#### 한줄 요약
- 시험은 결함을 조기에 회수하는 대신 작성과 유지에 지속적인 공수를 요구하므로, 레벨별 배분이 곧 비용 대비 회수율을 정하는 설계가 된다.

## Ⅲ. 구조 및 구성요소

<details><summary>용어 설명</summary>

- **V-Model 검증/확인**: 요구사항-인수테스트, 기본설계-시스템테스트, 상세설계-통합테스트, 구현-단위테스트의 1:1 대응 구조.

</details>

```text
[V-Model 및 테스트 4단계 계층 구조]
|-- 요구사항 분석 ───────── 인수 테스트
|-- 기본/시스템 설계 ───── 시스템 테스트
|-- 상세 설계 ─────────── 통합 테스트
`-- 소스 구현 ─────────── 단위 테스트
```

선의 의미: 소프트웨어 개발 단계와 테스트 레벨 간의 1:1 V-Model 대응 구조

| 구성요소 | 책임 |
|:---|:---|
| 단위 테스트 | **JUnit·Mockito** 기반 모듈 격리 검증 |
| 통합 테스트 | **Testcontainers** 기반 인터페이스 연동 검증 |
| 시스템 테스트 | **JMeter** 기반 전체 성능·보안 검증 |
| 인수 테스트 | **Cucumber BDD** 기반 요구사항 승인 |

#### 한줄 요약
- 네 레벨은 대상의 크기가 아니라 결함의 출처가 다르므로, 상위 레벨 시험으로 하위 레벨의 누락을 메우려 하면 비용만 커진다.

## Ⅳ. 흐름도

<details><summary>용어 설명</summary>

- **테스트 피라미드(Test Pyramid)**: 비용이 적고 빠른 단위 테스트(Unit)를 70%로 가장 많이 두고, 통합(20%), UI/E2E(10%)로 갈수록 비중을 줄이는 이상적 테스트 구성비.

</details>

```text
요구사항 기반 테스트 케이스(TC) 및 테스트 오라클 정의
        │
   [단위 테스트] Mock 객체를 활용하여 비즈니스 로직 독립 실행 및 커버리지 80% 달성
        │
   [통합 테스트] Testcontainers로 실제 DB/Kafka 컨테이너 띄워 모듈 간 인터페이스 검증
        │
   [시스템 테스트] 스테이징 환경에서 JMeter 부하 테스트 및 보안 취약점 검증
        │
   [인수 테스트] 최종 사용자 및 PO(Product Owner)의 시나리오 검증 및 릴리즈 승인
```

#### 한줄 요약
- 각 레벨은 앞 레벨이 통과됐다는 가정 위에서만 의미가 있으므로, 단위 시험을 건너뛰면 통합 이후 결함의 원인 후보가 급격히 넓어진다.

## Ⅴ. 종류 및 비교

<details><summary>용어 설명</summary>

- **Test Double(테스트 대역)**: 단위 테스트 시 외부 DB, 네트워크 호출을 대체하기 위해 사용하는 모의 객체 5종.

</details>

| Test Double 유형 | 정의 및 핵심 용도 | 실무 예시 |
|:---|:---|:---|
| Dummy | 파라미터 전달용으로만 쓰이며 **실제 사용되지 않는 빈 객체** | 로깅용 파라미터 `new DummyUser()` |
| Fake | 실제 구현체와 동일하게 동작하나 **간이화된 객체** | **In-Memory H2 DB, HashMap 저장소** |
| Stub | 테스트 시 지정된 **고정 응답값만 반환(Hardcoded)** | `when(userRepo.findById(1)).thenReturn(user)` |
| Spy | 실제 객체를 감싸며 **호출된 횟수/파라미터 기록** | `verify(mailSender, times(1)).send()` |
| Mock | 기대 행위(Behavior)를 미리 설정하고 **호출 여부를 검증** | **Mockito 프레임워크 기반 행위 검증** |

#### 한줄 요약
- Dummy(채우기), Fake(간이 구현), Stub(고정 응답), Spy(기록), Mock(행위 검증)으로 역할을 분담한다.

## Ⅵ. 실무 고려사항 및 대책

<details><summary>용어 설명</summary>

- **Testcontainers**: 테스트 실행 시 Docker 컨테이너(PostgreSQL, Redis 등)를 동적으로 기동하여 완벽히 일치하는 환경에서 통합 테스트를 수행하는 도구.

</details>

| 문제 | 대책 | 효과 |
|:---|:---|:---|
| E2E/UI 테스트 비중 과다로 인한 실행 속도 저하(아이스크림 콘 안티패턴) | **마틴 파울러의 테스트 피라미드 (Unit 70%, Integration 20%, E2E 10%)** | CI 피드백 시간 10분 이내 단축 |
| 인메모리 H2 DB와 실제 Oracle/PostgreSQL SQL 문법 차이 | **Testcontainers 라이브러리 기반 실제 DB 도커 통합 테스트** | 배포 후 SQL 문법 런타임 오류 0화 |
| 코드 리팩토링 시 취약한 테스트가 깨지는 현상 | **내부 구현이 아닌 공개 인터페이스의 행위(Behavior) 중심 테스트** | 리팩토링 저항성 확보 및 테스트 유지보수성 향상 |
| 릴리즈 후 미탐지 결함 발견 | **SonarQube 브랜치 커버리지 80% 게이트 강제** | 잠재적 예외 분기 누락 원천 방어 |

#### 한줄 요약
- 시험은 결함 회수 이득과 작성·유지 비용의 균형 문제이므로, 피라미드 형태로 값싼 단위 시험을 두껍게 깔고 통합 시험은 Testcontainers로 실환경 충실도만 선택적으로 사들인다.

## Ⅶ. 결론

- 소프트웨어 공학 전 생애주기 품질 보증 및 지속적 배포(CI/CD)의 **가장 핵심적인 안전망(Safety Net) 표준 활동**으로 확립되었으며, 실무 프로젝트에서는 **테스트 피라미드(단위 70%·통합 20%·E2E 10%) 원칙 준수, Test Double(Mock/Stub/Fake)을 활용한 모듈 격리, Testcontainers 기반 실제 인프라 통합 검증, 공개 행위 중심 테스트 작성을 통한 리팩토링 저항성 확보**를 결합하여 테스트 신뢰도를 극대화

#### 한줄 요약
- 소프트웨어 테스팅은 단순한 오류 적발을 넘어, 개발 초기부터 결함을 차단하고 아키텍처의 리팩토링 안전망을 제공하는 핵심 공학 활동이다.
