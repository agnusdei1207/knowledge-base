## Ⅰ. 개요

<details><summary>용어 설명</summary>

- **CI (지속적 통합, Continuous Integration)**: 개발자들이 코드를 깃허브에 올릴 때마다(Push), 서버가 알아서 코드를 합치고 빌드하고 테스트까지 돌려서 버그를 초장에 박살 내는 자동화 과정이다.
- **CD (지속적 전달/배포, Continuous Delivery/Deployment)**: CI를 통과한 코드를 '배포 대기(Delivery)' 상태로 두거나, 묻고 더블로 실서버(Prod)에 꽂아버리는(Deployment) 자동 배포 과정이다.

</details>

- 정의: 소스 커밋부터 빌드, 테스트, 보안 검사, 그리고 실운영 서버 배포까지의 모든 노가다를 사람 손 안 거치고 자동화한 엔지니어링 고속도로인 **CI/CD Pipeline**
- 배경: "어? 내 PC에선 빌드 되는데 서버에선 왜 안 되지?" 하는 핑계를 없애고, **수동 배포하다가 파일 빼먹고 서버 터트리는 대참사**를 막기 위함

#### 한줄 요약

- 개발자가 코드 짜서 올리기만 하면, 알아서 빌드하고 검사해서 서버에 예쁘게 꽂아주는 봇이다.

## Ⅱ. 특징

<details><summary>용어 설명</summary>

- **파이프라인 애즈 코드(Pipeline as Code, PaC)**: 젠킨스 화면에서 마우스로 클릭해서 세팅하지 말고, `Jenkinsfile`처럼 파이프라인 과정 자체를 코드로 짜서 깃에 박제하는 기술이다.
- **퀄리티 게이트(Quality Gate)**: 테스트 커버리지가 80% 미만이거나 보안 취약점이 하나라도 뜨면, 파이프라인을 가차 없이 멈추고 빌드를 터트려버리는(Fail-Fast) 무자비한 검문소이다.

</details>

- 결함이 있으면 뒷단으로 안 넘기고 즉시 터트리는 **Fail-Fast** 원칙 적용.
- 파이프라인도 코드로 관리하는 **Pipeline as Code (PaC)**로 버전 통제.
- 검문소(**Quality Gate**)를 통과하면 두 번 다시 바뀌지 않는 실행 파일(**Immutable Artifact**)을 구워냄.

#### 한줄 요약

- 코드로 배포 과정을 짜고, 검문소로 똥 코드를 거르고, 한 번 구운 파일은 절대 고치지 않는다.

## Ⅲ. 구조 및 구성요소

<details><summary>용어 설명</summary>

- **아티팩트 저장소(Artifact Repository)**: 빌드 다 끝나고 도커 이미지나 `jar` 파일처럼 당장 서버에 꽂을 수 있는 완성품을 버전별로 예쁘게 모아두는 창고(Nexus, Harbor 등)이다.

</details>

```text
[ CI/CD 파이프라인 십자포화 아키텍처 ]

[ 깃허브 (소스) ] ──(Webhook)──▶ [ Runner (CI 서버) ]
                                         │ (빌드 & 테스트)
                                         ▼
                                [ Quality Gate (코드 품질 검문) ]
                                         │ (Pass)
                                         ▼
[ 운영 서버 (Prod) ] ◀──(CD)─── [ 아티팩트 저장소 (완성품 창고) ]
```

| 구성요소 | 팩트 폭행 책임 |
|:---|:---|
| **소스 저장소 (Git)** | 개발자들이 짠 소스 코드와 파이프라인 설정(PaC) 코드를 쟁여두는 원본 창고 |
| **실행기 (Runner)** | 소스가 올라오면 잽싸게 격리된 방(컨테이너)을 파서 컴파일하고 테스트 돌리는 봇 |
| **품질 게이트** | 커버리지, 보안 취약점 스캔해서 맘에 안 들면 빌드 멱살 잡고 터트리는 문지기 |
| **아티팩트 저장소** | 게이트 통과해서 구워진 실행물(Docker Image)을 버전 달아서 보관하는 창고 |
| **배포 제어기** | 창고에서 완성품 꺼내다가 실제 운영 서버(K8s)에 예쁘게 꽂아주는 배포 담당자 |

#### 한줄 요약

- 소스 푸시 $\to$ 봇이 빌드/테스트 $\to$ 게이트 검문 $\to$ 창고 보관 $\to$ 배포봇이 서버에 꽂는 구조다.

## Ⅳ. 흐름도

<details><summary>용어 설명</summary>

- **불변 아티팩트(Immutable Artifact)**: 한 번 구워진 도커 이미지나 빌드 산출물은 Dev, Staging, Prod 환경을 거치면서 절대 내용물을 수정할 수 없고 환경 변수만 갈아 끼워야 한다는 룰이다.

</details>

```text
[ CI/CD 자동화 십자포화 흐름 ]
┌──────────────────────────────┐
│ 1. Git Push (개발자 커밋)    │
└──────────────┬───────────────┘
               ▼ (Webhook 발동)
┌──────────────────────────────┐
│ 2. CI 빌드 & 단위 테스트     │
│ (에러 나면 여기서 광탈)      │
└──────────────┬───────────────┘
               ▼
┌──────────────────────────────┐
│ 3. Quality Gate 정적 분석    │
│ (코드 냄새나면 여기서 광탈)  │
└──────────────┬───────────────┘
               ▼
┌──────────────────────────────┐
│ 4. 아티팩트 굽고 창고에 박제 │
│ (도커 이미지 빌드 후 Push)   │
└──────────────┬───────────────┘
               ▼
┌──────────────────────────────┐
│ 5. CD 운영 환경 배포 (승격)  │
│ (배포봇이 땡겨서 실서버 띄움)│
└──────────────────────────────┘
```

### 동작 원리

1. 코드 커밋: 개발자가 퇴근 전 `git push`를 때림.
2. CI 빌드/테스트: Runner가 깨어나서 소스 받고 빌드하고 테스트 코드(JUnit) 싹 다 돌림.
3. 품질 검사: SonarQube가 코드 까보고 취약점이나 똥 코드 있으면 가차 없이 빌드 터트림.
4. 아티팩트 생성: 검사 통과하면 불변 도커 이미지로 구워서 레지스트리(Harbor)에 박제함.
5. CD 배포: 배포봇이 새 이미지 뜬 거 보고 실운영 클러스터에 꽂아버림.

#### 한줄 요약

- 코딩 $\to$ 시험 $\to$ 검사 $\to$ 굽기 $\to$ 배포하기의 완벽한 컨베이어 벨트 흐름이다.

## Ⅴ. 종류 및 비교

<details><summary>용어 설명</summary>

- **지속적 전달(Delivery) vs 배포(Deployment)**: 둘 다 CD지만, 운영 서버(Prod)로 쏠 때 팀장님의 수동 '승인(Approve)' 버튼을 누르느냐(Delivery), 아님 봇이 다이렉트로 쏴버리느냐(Deployment)의 차이이다.

</details>

| 비교 항목 | **CI (Continuous Integration)** | **CD (Delivery, 전달)** | **CD (Deployment, 배포)** |
|:---|:---|:---|:---|
| 자동화 범위 | 소스 빌드 $\to$ 테스트 $\to$ 패키징 | **운영 서버 배포 직전까지만 대기** | **묻고 더블로 실운영까지 자동 슛** |
| 수동 개입 | 0% (완전 자동) | **운영 배포 시 팀장 클릭(Approve) 필수** | **0% (사람 손 안 탐)** |
| 팩폭 환경 | 숨 쉬는 모든 프로젝트 | 규제가 빡센 금융권, 엔터프라이즈 | 실패 감당되는 넷플릭스, 웹 프론트 |

#### 한줄 요약

- 빌드/테스트만 하면 CI, 마지막에 사람이 버튼 누르면 Delivery, 로봇이 알아서 다 쏘면 Deployment다.

## Ⅵ. 실무 고려사항 및 대책

<details><summary>용어 설명</summary>

- **플래키 테스트(Flaky Test)**: 코드 결함이 없는데 네트워크나 타이밍 문제로 지 맘대로 '성공-실패'를 와리가리 타서, "아 이거 또 억까네" 하고 걍 재시도 누르게 만드는 CI 파이프라인의 암 덩어리이다.

</details>

| 문제 | 대책 | 효과 |
|:---|:---|:---|
| 파이프라인 도는 데 30분 걸려서 개발자들 커피 마시러 감 | **캐싱(Cache)** 떡칠하고 테스트를 병렬로 찢어서 돌림 | 파이프라인 피드백 시간 단축으로 생산성 폭발 |
| **Flaky Test** 억까 때문에 CI가 맨날 빨간불임 | 불안정한 테스트는 **격리(Quarantine)**시키고 뜯어고침 | 양치기 소년이 되어버린 CI 신뢰도 회복 |
| 액션 코드에 AWS Secret Key 쌩으로 박아둠 | 무조건 **OIDC** 쓰거나 **Vault** 같은 시크릿 매니저 연동 | 깃허브 털려도 AWS 인프라 요금 폭탄 방어 |

#### 한줄 요약

- CI가 너무 느리면 캐시를 붓고, 지 맘대로 터지는 테스트는 빼버리고, 비번은 제발 코드에 박지 마라.

## Ⅶ. 결론

<details><summary>용어 설명</summary>

- **CI/CD 파이프라인 구축 기준(CI/CD Pipeline Build Standards)**: 테스트 코드가 튼튼한지, 장애 났을 때 감당이 되는지 각을 재서 Delivery(수동)로 갈지 Deployment(자동)로 갈지 정하는 잣대이다.

</details>

- **CI/CD 파이프라인 구축 기준** 원칙에 따라, 보수적인 결제망은 **Continuous Delivery(수동 승인)**, 빠른 피드백이 생명인 프론트엔드는 **Continuous Deployment** 채택 기조 확립함

#### 한줄 요약

- 테스트 코드가 허접한데 CD(Deployment)로 자동 배포를 뚫어놓는 건 폭탄 돌리기나 다름없다.
