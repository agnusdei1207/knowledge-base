## Ⅰ. 개요

<details><summary>용어 설명</summary>

- **지속적 통합/배포(CI/CD)**: 코드 병합 시마다 단위/통합 테스트와 정적 분석을 자동 실행(CI)하고, 통과된 불변 이미지를 대상 인프라에 배포(CD)하는 체계.
- **인적 오류 및 릴리스 지연(Human Error & Delivery Delay)**: 수작업 서버 접속 배포 시 환경 설정 실수로 인한 서비스 장애 및 배포 주기 장기화 문제.

</details>

- 정의/개념: 소스 코드 커밋부터 **자동 빌드·테스트(CI) 및 품질 게이트 통과 후 불변 아티팩트 자동 배포(CD)**를 수행하는 지속적 소프트웨어 전달 파이프라인
- 배경/필요성: 수동 빌드·배포 시 발생하는 **인적 오류(Human Error) 및 릴리스 지연과 결함 늑장 발견 위험** 직면

#### 한줄 요약

- 코드 커밋에서 운영 배포까지 전 단계를 자동화하여 신속하고 신뢰성 있는 소프트웨어 전달을 달성

## Ⅱ. 특징

<details><summary>용어 설명</summary>

- **파이프라인 애즈 코드(Pipeline as Code, PaC)**: Jenkinsfile·GitHub Actions YAML 등으로 파이프라인 정의를 소스 코드와 함께 버전 관리하는 방식.
- **품질 게이트(Quality Gate)**: 테스트 커버리지·정적 분석·보안 취약점 기준을 충족하지 못하면 파이프라인을 즉시 중단하는 검증 관문.

</details>

- 결함 발견 즉시 파이프라인을 중단하는 **Fail-Fast** 원칙으로 결함의 하위 단계 유입 방지
- 파이프라인 정의를 코드로 관리하는 **Pipeline as Code**로 버전 추적 및 변경 이력 확보
- **품질 게이트** 통과 후 생성된 **불변 아티팩트(Immutable Artifact)**를 환경별 재사용

#### 한줄 요약

- Fail-Fast·Pipeline as Code·불변 아티팩트로 자동화 파이프라인의 일관성과 신뢰성을 확보

## Ⅲ. 구조 및 구성요소

<details><summary>용어 설명</summary>

- **아티팩트 저장소(Artifact Repository)**: 빌드 완료 후 생성된 컨테이너 이미지·jar 파일 등 배포 가능한 불변 산출물을 버전별로 관리하는 저장소(Nexus·Harbor 등).

</details>

```text
[ CI/CD 파이프라인 구조 ]
소스 저장소 (Git)
   │ Webhook (코드 Push 시 자동 실행)
   ▼
CI 실행기 (Runner/Agent)
   └─ 빌드·단위 테스트·통합 테스트 자동 수행
   │
품질 게이트 (Quality Gate)
   └─ SonarQube: 커버리지·정적 분석·보안 취약점 검증
   │ 통과 시
아티팩트 저장소
   └─ 불변 컨테이너 이미지 생성·버전 태깅·보관
   │
CD 배포 제어기
   └─ K8s 클러스터에 새 이미지 자동 또는 수동 승인 배포
```

선의 의미: 단계 간 화살표는 파이프라인 실행 흐름, 품질 게이트 이후 가지는 통과 시만 다음 단계로 진행하는 조건 관계

| 구성요소 | 책임 |
|:---|:---|
| **소스 저장소(Git)** | 소스 코드·파이프라인 정의(PaC) 버전 관리 |
| **CI 실행기** | 격리 환경에서 빌드·테스트 자동 실행 |
| **품질 게이트** | 커버리지·정적 분석·보안 기준 검증 및 미달 시 파이프라인 중단 |
| **아티팩트 저장소** | 검증 완료 불변 아티팩트 버전별 보관 |
| **CD 배포 제어기** | 아티팩트를 대상 환경에 자동 또는 승인 기반 배포 |

#### 한줄 요약

- Git Push→CI 빌드/테스트→품질 게이트→아티팩트 생성→CD 배포의 자동화 파이프라인 구성

## Ⅳ. 흐름도

<details><summary>용어 설명</summary>

- **불변 아티팩트(Immutable Artifact)**: 한 번 생성된 컨테이너 이미지는 내용 수정 없이 동일한 이미지를 개발·스테이징·운영 환경에 동일하게 배포하여 환경 간 불일치를 방지하는 원칙.

</details>

```text
1. Git Push (개발자 코드 커밋)
   │ Webhook으로 파이프라인 자동 트리거
   ▼
2. CI: 빌드·단위 테스트 실행
   └─ 실패 시 즉시 파이프라인 중단 (Fail-Fast)
   │
   ▼
3. 품질 게이트: 정적 분석·보안 취약점 스캔
   └─ 기준 미달 시 즉시 파이프라인 중단
   │
   ▼
4. 불변 아티팩트 생성 및 저장소 등록
   └─ 컨테이너 이미지 빌드·버전 태깅·레지스트리 Push
   │
   ▼
5. CD: 대상 환경 배포 (Delivery: 수동 승인 / Deployment: 자동)
```

**동작 원리**

1. **트리거**: Git Push 이벤트가 Webhook을 통해 파이프라인을 자동 실행
2. **CI**: 격리 컨테이너에서 빌드·테스트를 실행하고 결함 발생 시 Fail-Fast로 즉시 중단
3. **품질 검증**: SonarQube 등으로 코드 품질·보안 기준 충족 여부 자동 판정
4. **아티팩트**: 검증 완료 후 불변 컨테이너 이미지를 생성하여 아티팩트 저장소에 등록
5. **CD 배포**: Delivery는 수동 승인, Deployment는 배포 제어기가 자동으로 운영 환경에 적용

#### 한줄 요약

- Git Push→빌드/테스트→품질 게이트→불변 아티팩트→CD 배포의 자동화 흐름으로 신속한 소프트웨어 전달

## Ⅴ. 종류 및 비교

<details><summary>용어 설명</summary>

- **지속적 전달(Delivery) vs 배포(Deployment)**: 운영 배포 시 수동 승인 단계를 유지(Delivery)하거나 완전 자동화(Deployment)하는 CD 방식의 차이.

</details>

| 비교 항목 | CI | CD (Delivery) | CD (Deployment) |
|:---|:---|:---|:---|
| 자동화 범위 | 빌드·테스트·패키징 | 운영 배포 직전까지 자동화 | 운영 배포까지 완전 자동화 |
| 수동 개입 | 없음 | **운영 배포 시 수동 승인 필요** | 없음 (완전 자동) |
| 적용 기준 | 모든 프로젝트 기본 | 규제 산업·고위험 배포 환경 | 빠른 피드백 주기·웹 서비스 |

#### 한줄 요약

- 빌드/테스트 자동화는 CI, 수동 승인 배포는 Delivery, 완전 자동 배포는 Deployment

## Ⅵ. 실무 고려사항 및 대책

<details><summary>용어 설명</summary>

- **플래키 테스트(Flaky Test)**: 코드 결함 없이 네트워크 타이밍·환경 의존 등으로 인해 실행 때마다 결과가 변동하는 불안정 테스트로 CI 신뢰도를 저하.

</details>

| 문제 | 대책 | 효과 |
|:---|:---|:---|
| 파이프라인 실행 시간 과다로 개발자 피드백 지연 | **의존성 캐싱** 적용 및 테스트 병렬 실행 | 파이프라인 실행 시간 단축 |
| **플래키 테스트**로 인한 CI 신뢰도 저하 | 불안정 테스트를 **격리(Quarantine)** 후 원인 분석 및 수정 | CI 결과의 신뢰성 회복 |
| 파이프라인 정의에 보안 자격 증명(Secret) 하드코딩 | **OIDC** 또는 **Vault** 기반 시크릿 관리 적용 | 자격 증명 노출로 인한 보안 사고 방지 |

#### 한줄 요약

- 파이프라인 속도는 캐싱·병렬화로, 플래키 테스트는 격리·수정으로, 보안 정보는 시크릿 관리로 개선

## Ⅶ. 결론

<details><summary>용어 설명</summary>

- **CI/CD 구축 기준**: 테스트 자동화 성숙도·배포 위험도·규제 요구사항을 기준으로 Delivery와 Deployment를 선택하는 판단 기준.

</details>

- 규제 요구가 엄격한 환경은 **Continuous Delivery(수동 승인)**, 빠른 피드백이 중요한 서비스는 **Continuous Deployment(완전 자동화)** 선택

#### 한줄 요약

- 테스트 자동화 성숙도와 배포 위험도를 기준으로 Delivery·Deployment를 선택하고 불변 아티팩트로 환경 일관성을 보장
