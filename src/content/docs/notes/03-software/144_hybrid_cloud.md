## Ⅰ. 개요

<details><summary>용어 설명</summary>

- **하이브리드 클라우드(Hybrid Cloud)**: 자체 온프레미스 프라이빗 클라우드(Private IDC)와 공용 퍼블릭 클라우드(AWS, GCP)를 전용회선(Direct Connect) 또는 VPN으로 상호 연계하여 보안과 탄력성을 동시에 확보하는 통합 인프라.
- **데이터 주권 및 확장성 충돌(Data Sovereignty vs Elasticity)**: 핵심 금융/개인정보 데이터는 사내 폐쇄망에 보관해야 하는 규제와 대규모 대외 트래픽 처리를 위한 무제한 확장 요구가 충돌하는 딜레마.

</details>

- 정의/개념: 기업의 온프레미스 프라이빗 클라우드와 **공용 퍼블릭 클라우드를 전용망으로 상호 연계하여 보안과 탄력성을 양립**하는 하이브리드 인프라
- 배경/필요성: 민감 금융·개인정보 데이터의 법적 규제 통제와 **대규모 대외 트래픽에 대응하기 위한 탄력적 자원 확장 요구 간의 충돌 위험** 직면

#### 한줄 요약

- 규제 원장 데이터는 프라이빗에 보존하고 대외 웹 및 분석 서비스는 퍼블릭으로 확장하는 최적의 절충 인프라

## Ⅱ. 특징

<details><summary>용어 설명</summary>

- **워크로드 분할 배치(Workload Partitioning)**: 보안 및 규제 등급에 따라 코어 DB는 프라이빗에, 오토스케일링이 필요한 프론트엔드는 퍼블릭에 분리 배치하는 설계.
- **클라우드 버스팅(Cloud Bursting)**: 평시에는 사내 IDC를 사용하다가 이벤트/피크 시점에만 퍼블릭 클라우드 자원을 동적으로 임차하여 스케일아웃하는 기법.

</details>

- 금융/개인정보 등 핵심 자산을 사내에 격리하는 **강력한 데이터 주권(Data Sovereignty)**
- 피크 타임 트래픽 급증 시 퍼블릭으로 자원을 동적 임차하는 **클라우드 버스팅(Cloud Bursting)**
- Direct Connect 및 IPsec VPN 전용 암호화 통로를 통한 **보안 통신 인프라 완비**

#### 한줄 요약

- 프라이빗의 데이터 통제력과 퍼블릭의 무제한 탄력성을 전용선으로 연결하여 결합

## Ⅲ. 구조 및 구성요소

<details><summary>용어 설명</summary>

- **하이브리드 네트워크 연계망**: 온프레미스 IDC와 퍼블릭 VPC를 BGP 라우팅 전용회선(Direct Connect)과 백업 IPsec VPN으로 묶어 단일 사설망으로 구성.

</details>

```text
[ 하이브리드 클라우드 계층 아키텍처 구조도 ]

 1. [ 온프레미스 프라이빗 클라우드 (Private IDC) ]
    - 코어 뱅킹 원장 DB, 고객 개인정보 (엄격한 폐쇄망 통제)
                          │
                          │ (AWS Direct Connect 전용선 + IPsec VPN 백업)
                          ▼
 2. [ 전송 게이트웨이 (AWS Transit Gateway) ]
                          │
                          ▼
 3. [ 퍼블릭 클라우드 (AWS Public VPC) ]
    - 대외 고객 서빙 API, EKS 컨테이너 (오토스케일링 웹/앱)
    - 퍼블릭 캐시 레이어 (Redis) ➔ 온프레미스 쿼리 부하 차단
```

선의 의미: 프라이빗의 민감 데이터와 퍼블릭의 대외 애플리케이션이 전용망과 게이트웨이를 통해 상호 통신하는 구조.

| 구성요소 | 책임 |
|:---|:---|
| 프라이빗 클라우드 (Private) | 금융 원장, 개인정보 등 **규제 대상 핵심 데이터를 전용 폐쇄망에서 통제** |
| 퍼블릭 클라우드 (Public) | 대외 대고객 서비스 웹/앱 및 **대규모 데이터 분석/AI 워크로드 탄력 처리** |
| 전용회선 및 VPN (Network) | 10Gbps Dedicated Direct Connect 및 **IPsec VPN으로 안전한 사설 경로 제공** |
| 통합 IAM 및 거버넌스 | Okta/Azure AD SSO를 통해 **사내 계정과 클라우드 IAM 권한 정책 단일화** |

#### 한줄 요약

- 프라이빗(코어 통제), 퍼블릭(탄력 서비스), 전용망(암호화 연계), 통합 IAM으로 구성

## Ⅳ. 흐름도

<details><summary>용어 설명</summary>

- **하이브리드 쿼리 처리 5단계 파이프라인**: 요청 접수 $\to$ 퍼블릭 캐시 검사 $\to$ 전용선 데이터 호출 $\to$ 프라이빗 처리 $\to$ 통합 결과 반환.

</details>

```text
[ 하이브리드 클라우드 트래픽 처리 및 연계 파이프라인 ]

 ┌────────────────────────────────────────┐
 │ 1. 대외 사용자 요청 접수 (퍼블릭 웹)  │
 └───────────────────┬────────────────────┘
                     │
                     ▼
 ┌────────────────────────────────────────┐
 │ 2. 퍼블릭 캐시(Redis) 확인 (Hit 시 즉시 반환)
 └───────────────────┬────────────────────┘
                     │ (Miss 시 전용선 경유)
                     ▼
 ┌────────────────────────────────────────┐
 │ 3. Direct Connect 전용선 암호화 호출   │
 └───────────────────┬────────────────────┘
                     │
                     ▼
 ┌────────────────────────────────────────┐
 │ 4. 프라이빗 코어 DB 원장 트랜잭션 수행 │
 └───────────────────┬────────────────────┘
                     │
                     ▼
 ┌────────────────────────────────────────┐
 │ 5. 결과 암호화 응답 및 퍼블릭 캐시 갱신│
 └────────────────────────────────────────┘
```

### 동작 원리

1. 요청 접수: 외부 사용자의 서비스 요청이 퍼블릭 클라우드의 API Gateway/ALB에 도달.
2. 캐시 확인: 퍼블릭 영역의 Redis 캐시를 조회하여 단순 조회 쿼리는 온프레미스로 보내지 않고 즉시 반환.
3. 전용선 호출: 금융 결제 등 원장 갱신 쿼리에 한하여 Direct Connect 전용선을 통해 사설망으로 안전하게 전송.
4. 코어 트랜잭션: 사내 프라이빗 IDC의 코어 DB가 ACID 트랜잭션을 엄격하게 수행.
5. 결과 반환: 암호화된 결과를 퍼블릭 웹 서버로 회신하고 필요한 캐시를 갱신하여 클라이언트에 최종 응답.

#### 한줄 요약

- 퍼블릭 접수 $\to$ 캐시 확인 $\to$ 전용선 전송 $\to$ 프라이빗 트랜잭션 $\to$ 결과 반환의 5단계

## Ⅴ. 종류 및 비교

<details><summary>용어 설명</summary>

- **Public vs Private vs Hybrid**: 완전 공개 임대(Public), 완전 독점 구축(Private), 둘의 전략적 결합(Hybrid).

</details>

| 구분 | 순수 퍼블릭 클라우드 (Pure Public) | 순수 프라이빗 클라우드 (Pure Private) | 하이브리드 클라우드 (Hybrid) |
|:---|:---|:---|:---|
| **적용 기준** | 대외 스타트업, 일반 모바일 앱 | 국방, 정부 행정망, 특수 폐쇄망 | 금융, 엔터프라이즈, 헬스케어 |
| **핵심 특징** | **전체 인프라 CSP 위탁, 무한 스케일아웃** | **사내 전용 자원, 완벽한 물리 보안 통제** | **보안 데이터는 내부, 대외 앱은 외부에 분산** |
| **한계** | 데이터 주권 규제 및 폐쇄망 요구 미충족 | 피크 타임 인프라 증설 한계 및 높은 CapEx | 전용선 단선 위험 및 이종 인프라 관리 복잡도 |

#### 한줄 요약

- 완전 위탁은 퍼블릭, 완전 독점은 프라이빗, 규제와 확장의 공존은 하이브리드를 선택

## Ⅵ. 실무 고려사항 및 대책

<details><summary>용어 설명</summary>

- **스플릿 브레인(Split-Brain Risk)**: 온프레미스와 퍼블릭 간 전용선이 단선되었을 때 양쪽 데이터베이스가 독립적으로 쓰기를 수행하여 정합성이 파괴되는 위험.

</details>

| 문제 | 대책 | 효과 |
|:---|:---|:---|
| Direct Connect 전용선 물리적 단선 사고 발생 | **BGP 라우팅 기반 IPsec VPN 자동 백업 경로(Backup) 이중화** | 네트워크 무중단 자동 절체(Failover) |
| 퍼블릭-프라이빗 간 잦은 네트워크 호출로 레이턴시 급증 | **퍼블릭 영역 캐싱 계층(Redis) 및 Read Replica 배치** | 전용선 왕복 트래픽 80% 이상 절감 |
| 온프레미스 AD와 클라우드 IAM 계정 불일치 | **Azure AD / Okta SSO 기반 SAML/OIDC 계정 연동 단일화** | 통합 접근 통제 및 권한 관리 |

#### 한줄 요약

- 전용선 이중화, 퍼블릭 캐시 계층화, SSO 계정 통합을 통해 하이브리드 클라우드의 연속성을 보장

## Ⅶ. 결론

<details><summary>용어 설명</summary>

- **하이브리드 네이티브 플랫폼(Hybrid-Native Platform)**: Google Anthos, AWS Outposts 등을 활용하여 온프레미스 장비를 퍼블릭 클라우드 콘솔에서 동일하게 제어하는 진화 아키텍처.

</details>

- **하이브리드 클라우드** 기반 엔터프라이즈의 규제 준수와 디지털 혁신을 동시에 만족시키는 가장 현실적이고 강력한 배포 모델이며, 전용선 이중화와 통합 거버넌스를 기반으로 안정적인 하이브리드 네이티브 환경을 구축해야 함

#### 한줄 요약

- 프라이빗의 데이터 통제력과 퍼블릭의 탄력성을 융합하여 엔터프라이즈의 보안과 확장을 양립
