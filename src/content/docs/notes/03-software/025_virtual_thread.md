## Ⅰ. 개요

<details><summary>용어 설명</summary>

- **가상 스레드(Virtual Thread)**: OS 커널 스레드(1:1)와 달리 JVM 사용자 공간에서 M:N으로 다중화되는 수백 바이트 크기의 초경량 스레드 (Java 21 표준).
- **Continuation**: 실행 중인 코드의 호출 스택과 연산 상태를 일시 중단(`yield`)하여 힙 메모리에 저장하고 나중에 복원하는 기제.

</details>

- 정의/개념: JVM 런타임이 콜 스택을 힙에 저장하고 **M:N 다중화(Continuation & ForkJoinPool)** 로 I/O 대기 시 플랫폼 스레드를 양보하는 경량 동시성 기법
- 배경/필요성: OS 스레드와 1:1로 묶인 모델은 스레드마다 고정 스택과 커널 자원을 잡아 동시 연결 수가 메모리에서 먼저 막히므로, JVM이 힙 위에 스택을 두고 캐리어 스레드에 다중화하는 가상 스레드 계층을 OS 스레드 위에 얹을 필요

#### 한줄 요약
- I/O 블로킹 시 캐리어 스레드를 양보하여 수백만 개의 동시 연결을 동기식 코드로 처리한다.

## Ⅱ. 특징

<details><summary>용어 설명</summary>

- **Carrier Thread(캐리어 스레드)**: 가상 스레드가 마운트되어 실제 CPU 명령어를 실행하는 소수의 OS 플랫폼 스레드 풀.
- **Mount / Unmount**: 가상 스레드가 캐리어 스레드에 결합(Mount)되어 실행되다가 I/O 블로킹 발생 시 즉시 분리(Unmount)되는 동작.

</details>

- 스레드 생성 비용이 극소화(수백 바이트)되어 **스레드 풀링 없이 요청당 스레드(Thread-per-Request)** 생성
- I/O 대기 시 **언마운트(Unmount)** 로 캐리어 스레드를 즉시 반납하여 CPU 가동률 극대화
- Reactive WebFlux의 복잡한 콜백 없이 **직관적인 동기식 블로킹 코드 스타일** 그대로 유지

#### 한줄 요약
- 가상 스레드는 스레드당 메모리 상한을 걷어내는 대신 스택 저장·복원을 JVM이 떠안으므로, 이득은 I/O 대기가 길수록 커지고 연산 위주 작업에서는 사라진다.

## Ⅲ. 구조 및 구성요소

<details><summary>용어 설명</summary>

- **ForkJoinPool 스케줄러**: JVM 내부에서 CPU 코어 수만큼의 워커 스레드를 캐리어로 유지하며 가상 스레드를 작업 훔치기(Work-Stealing)로 스케줄링하는 엔진.

</details>

```text
[가상 스레드 M:N 다중화 아키텍처]
|-- 가상 스레드 풀 (수백만 개 VT: JVM 힙 메모리에 스택 저장)
|   |-- VT 1 (비즈니스 로직 실행 중)
|   |-- VT 2 (I/O 대기 중 -> Unmount 상태로 힙에 보관)
|   `-- VT 3 (실행 대기 큐)
|-- JVM 스케줄러 (ForkJoinPool - Work-Stealing)
|   |-- Mount : 유휴 캐리어 스레드에 VT 탑재
|   `-- Unmount : I/O 블로킹 시 Continuation 힙 저장 후 캐리어 반환
`-- 캐리어 스레드 풀 (OS 플랫폼 스레드 = CPU 코어 수만큼 상주)
    `-- CPU 코어 1, 코어 2 ... 코어 N
```

선의 의미: 계층 및 M:N 매핑 구조

| 구성요소 | 책임 |
|:---|:---|
| 가상 스레드 | 비즈니스 로직과 **힙 기반 호출 스택** |
| Continuation 엔진 | 블로킹 시 **스택 저장·복원** |
| JVM 스케줄러 | 가상 스레드의 **M:N 스케줄링** |
| 캐리어 스레드 | CPU에서 명령을 실행하는 **OS 스레드** |

#### 한줄 요약
- Continuation이 스택을 힙에 저장해 대기 중에 캐리어 스레드를 반납할 수 있게 하므로, OS 스레드 수와 무관하게 동시 실행 흐름을 늘릴 수 있다.

## Ⅳ. 흐름도

<details><summary>용어 설명</summary>

- **스레드 피닝(Thread Pinning)**: `synchronized` 블록 내부나 C 라이브러리(JNI) 호출 중에 I/O가 발생하면 가상 스레드가 언마운트되지 못하고 캐리어를 쥔 채 멈추는 결함.

</details>

```text
가상 스레드 생성 후 실행 시작 (Thread.startVirtualThread)
        │
   JVM 스케줄러가 유휴 캐리어 스레드에 가상 스레드를 탑재 (Mount)
        │
   비즈니스 연산 수행 중 소켓 읽기/DB 쿼리 등 I/O 블로킹 발생
        │
   synchronized 블록 또는 네이티브 C JNI 호출 구간인가?
   ┌────┴─────┐
  예           아니오 (일반 순수 자바 I/O)
   │             │
스레드 피닝 발생   Continuation.yield() 호출 -> Unmount 수행
(캐리어 락 점유)  (호출 스택을 힙 메모리에 저장하고 캐리어 즉시 반납)
   │             │
캐리어 스레드     캐리어 스레드는 대기 중인 다른 가상 스레드를 즉시 실행
블로킹 지연      │
   │        네트워크 I/O 완료 이벤트 수신 (epoll/kqueue)
   │             │
   │        스케줄러가 가상 스레드를 캐리어에 재탑재 (Re-Mount) 후 실행 재개
   └────┬────────┘
        │
   가상 스레드 실행 완료 및 소멸
```

#### 한줄 요약
- Unmount 시점에 스택이 힙으로 옮겨지는 것이 이 구조의 비용이자 이득이므로, 블로킹 호출이 캐리어를 붙잡아 Unmount가 일어나지 않으면 이점이 그대로 사라진다.

## Ⅴ. 종류 및 비교

<details><summary>용어 설명</summary>

- **플랫폼 스레드 vs 가상 스레드 vs Reactive WebFlux**: OS 1:1 스레드 풀 모델, JVM 1:N 경량 스레드, 비동기 이벤트 루프 스트림 모델 비교.

</details>

| 비교 항목 | 플랫폼 스레드 (Platform Thread) | 가상 스레드 (Virtual Thread) | 리액티브 (Reactive WebFlux) |
|:---|:---|:---|:---|
| 스레드 매핑 | **OS 커널 스레드 1:1 매핑** | **JVM M:N 다중화 매핑** | 소수 이벤트 루프 스레드 |
| 스택 메모리 크기 | **스레드당 1MB 고정 할당** | **수백 바이트 (동적 힙 확장)** | 힙 객체 체인 |
| 동시 생성 한도 | 수천 개 (메모리 OOM 한계) | **수백만 개 동시 생성 가능** | 수만~수십만 동시 연결 |
| 코드 작성 스타일 | 동기식 블로킹 코드 | **동기식 블로킹 코드 (직관적)** | 비동기 함수형 파이프라인 (복잡) |
| 디버깅/스택트레이스 | 완벽한 호출 스택 보존 | **완벽한 호출 스택 보존** | 스택 트레이스 단절로 추적 난해 |

#### 한줄 요약
- 가상 스레드는 Reactive의 고동시성과 전통 스레드의 직관적 디버깅 편의성을 완벽히 결합한다.

## Ⅵ. 실무 고려사항 및 대책

<details><summary>용어 설명</summary>

- **ReentrantLock**: `synchronized`와 달리 가상 스레드가 락 획득 대기 중에도 캐리어 스레드를 언마운트할 수 있는 Java 표준 동시성 유틸리티.
- **Scoped Values**: 수백만 가상 스레드 환경에서 `ThreadLocal`의 메모리 복사 및 불변성 누수를 방지하는 초경량 컨텍스트 전파 기법.

</details>

| 문제 | 대책 | 효과 |
|:---|:---|:---|
| `synchronized` 사용으로 인한 **스레드 피닝(Thread Pinning)** | `synchronized`를 **`ReentrantLock`** 으로 전면 교체 | I/O 대기 시 정상 언마운트 보장 및 캐리어 고갈 방지 |
| 수백만 가상 스레드 폭증으로 DB 커넥션 풀 고갈 | 가상 스레드를 풀링하지 말고 **DB 접근에 세마포어(Semaphore)** 적용 | 고동시성 유지하면서 하위 백엔드 자원 보호 |
| `ThreadLocal` 남용으로 인한 힙 메모리 과소비 | **Scoped Values (`java.lang.ScopedValue`)** 도입 | 스레드 간 데이터 불변 공유 및 메모리 오버헤드 제거 |
| CPU 바운드 대규모 연산에 가상 스레드 적용 시 성능 저하 | CPU 집약 작업은 기존 **플랫폼 스레드 풀 / ForkJoinPool** 유지 | 불필요한 스케줄링 오버헤드 방지 |

#### 한줄 요약
- 가상 스레드는 동시성 상한을 메모리 제약에서 풀어 주지만 CPU 연산량은 그대로이므로, I/O 대기가 지배적인 구간에만 쓰고 캐리어 스레드를 묶는 고정 락은 ReentrantLock으로 바꿔 이득을 지킨다.

## Ⅶ. 결론

- I/O 처리는 **가상 스레드**, CPU 연산은 **플랫폼 풀** 선택

#### 한줄 요약
- 가상 스레드는 Java 21의 혁신적 경량 동시성 모델이며, 동기식 코드의 단순함으로 수백만 동시성을 실현한다.
