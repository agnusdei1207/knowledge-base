## 미리 알고가기

- **사이드카 패턴(Sidecar Pattern)**: 메인 앱과 보조 프로세스를 같은 배포 단위에 함께 배치함
- **횡단 관심사(Cross-Cutting Concern)**: 여러 서비스에 공통 적용되는 부가 기능임
- **파드(Pod)**: 쿠버네티스(Kubernetes)가 스토리지·네트워크와 생명주기를 공유하도록 묶는 배포 단위임
- **서비스 메쉬 프록시(Service Mesh Proxy)**: 외부 사이드카에서 관측성을 처리함
- **초기화 컨테이너(Init Container)**: 메인 실행 전 준비 작업을 수행함
- **장애 도메인(Failure Domain)**: 장애의 영향 범위를 결정하는 배포 경계임
- **앰배서더 패턴(Ambassador Pattern)**: 외부 시스템 연결 정책을 대행함
- **루프백·소켓**: 루프백은 같은 호스트의 내부 주소이고 소켓은 프로세스 통신 끝점임
- **사이드카 주입**: 배포 시 보조 컨테이너 정의를 파드에 자동으로 추가하는 기능임
- **프로브**: 컨테이너의 생존·준비·기동 상태를 확인하는 쿠버네티스 검사임
- **자원 경합**: 메인 앱과 사이드카가 중앙 처리 장치(Central Processing Unit, CPU)·메모리를 서로 차지해 성능이 낮아지는 현상임


## Ⅰ. 개요

- 정의/개념: 메인 앱과 **보조 프로세스의 동일 단위 배치**
- **배경/필요성**: 횡단 기능의 **코드 중복·결합 한계** 해소

### 쉽게 이해하기 (학습용)
- 메인 서비스와 독립된 프로세스로 부가 기능을 주입함

## Ⅱ. 특징

- 메인 앱과 **네트워크·스토리지 공유**
- 횡단 기능의 **별도 프로세스 격리**
- 메인·보조 프로세스의 **생명주기 결합**

### 쉽게 이해하기 (학습용)
- 메인 코드 수정 없이 부가 기능과 의존성을 업데이트함

## Ⅲ. 아키텍처 및 구성요소

```mermaid
flowchart LR
    A[책임 분리] --> B[통신 구성]
    B --> C[기동 제어]
    C --> D[자원 격리]
```

| 설계 요소 | 설명 |
|:---|:---|
| 책임 분리 | 공통 기능을 메인 앱에서 분리함 |
| 통신 구성 | 루프백·소켓으로 통신 경로를 구성함 |
| 기동 제어 | 생명주기와 주입 호환성을 확인함 |
| 자원 격리 | 자원 상한을 정하고 경합을 줄임 |

> 요약: 동일 파드 내 프로세스 간 정적 공유 구조를 구성함

### 쉽게 이해하기 (학습용)
- 파드 단위 내에서 메인과 사이드카의 자원을 정적으로 배치함

## Ⅳ. 원리 및 절차 흐름도

| 절차 | 설명 |
|:---|:---|
| **식별** | 부가 기능 선정 및 분리함 |
| **설계** | 통신 규약 및 우회 설정함 |
| **격리** | 최소 권한 및 자원 할당함 |
| **검증** | 프로브를 통한 순차 기동 확인함 |
| **개선** | 통신 지연 및 자원 모니터링함 |

> 요약: 자원 격리·프로브 검증으로 연동 오류 격리

### 쉽게 이해하기 (학습용)
- 사이드카 주입 및 기동 순서를 검증하여 적용함

## Ⅴ. 종류 및 비교

| 횡단 기능 배치 | 사이드카 | 임베디드 라이브러리 | 공유 서비스 |
|:---|:---|:---|:---|
| 적용 기준 | 앱별 공통 기능 격리 | 낮은 지연·단순 기능 | 다수 앱의 중앙 공유 |
| 핵심 특징 | 파드 안에서 별도 실행 | 앱 프로세스에 직접 포함 | 원격 공통 서비스 제공 |
| 한계 | 인스턴스별 자원 증가 | 코드 결합·개별 배포 | 네트워크 지연·중앙 장애 |

> 요약: 격리 수준과 자원 비용을 고려함

### 쉽게 이해하기 (학습용)
- 서비스 규모와 자원 오버헤드를 비교해 구조를 선택함

## Ⅵ. 실무 사례

1. 서비스 메쉬의 **통신 정책을 사이드카 분리**

### 쉽게 이해하기 (학습용)
- 메쉬 프록시는 앱 수정 없이 통신 정책을 적용함

## Ⅶ. 결론

- **앱별 독립 배포** 시 컨테이너 자원 한도 확인

### 쉽게 이해하기 (학습용)
- 코드 분리는 쉬워지지만 파드마다 자원이 추가됨
