## Ⅰ. 개요

<details>
<summary>핵심 용어</summary>

- **보조 프로세스**: 사이드카 패턴은 메인 애플리케이션과 보조 프로세스를 같은 배포 단위에 배치해 공통 기능을 분리한다.

</details>

- 정의/개념: **사이드카 패턴**은 로깅·프록시·설정 같은 횡단 기능을 보조 프로세스로 분리하고 메인 애플리케이션과 같은 배포·생명주기 단위에 배치하는 아키텍처 패턴
- 배경/필요성: 서비스별 횡단 기능 내장으로 **코드 중복·버전 결합** 발생

#### 한줄 요약
- 오토바이 옆 보조 좌석처럼 앱 옆 프로세스가 통신·로그를 맡아 앱 코드를 바꾸지 않고 공통 기능을 제공한다

## Ⅱ. 특징

<details>
<summary>핵심 용어</summary>

- **생명주기 결합**: 메인 앱과 사이드카는 배포와 시작·종료 생명주기가 결합되므로 준비 상태와 종료 순서를 함께 조정해야 한다.

</details>

- 메인 앱과 **네트워크·스토리지 공유**
- 횡단 기능의 **별도 프로세스 격리**
- 메인·보조 프로세스의 **생명주기 결합**

#### 한줄 요약
- 앱과 같은 파드에서 네트워크를 공유하되 별도 프로세스로 실행돼 공통 기능만 독립 교체할 수 있다

## Ⅲ. 구조 및 구성요소

<details>
<summary>핵심 용어</summary>

- **사이드카**: 사이드카는 메인 앱과 네트워크·볼륨을 선택적으로 공유하면서 프록시, 로그, 보안 같은 횡단 기능을 별도 실행한다.

</details>

```mermaid
block-beta
    columns 1
    A["메인 애플리케이션"]
    B["사이드카"]
    C["공유 네트워크"]
    D["선택적 공유 볼륨"]
    E["독립 자원·권한 한도"]
    A --- B
    B --- C
    C --- D
    D --- E
```

| 구성요소 | 책임 |
|:---|:---|
| 메인 애플리케이션 | 핵심 **업무 기능 실행** |
| 사이드카 | 프록시·로그·**공통 기능 분리** |
| 공유 네트워크 | 루프백·소켓 **통신 경로** |
| 선택적 공유 볼륨 | 로그·설정 **파일 공유** |
| 독립 자원·권한 한도 | CPU·메모리·**최소 권한 제한** |


#### 한줄 요약
- 한 파드의 메인 앱과 사이드카가 내부 통로와 선택적 파일함을 공유하고 각자 자원·권한 한도를 갖는다

## Ⅳ. 흐름도

<details>
<summary>핵심 용어</summary>

- **2. 루프백 전달**: 사이드카는 인증·라우팅 정책을 적용한 요청을 공유 네트워크의 루프백 주소로 메인 앱에 전달한다.

</details>

```mermaid
sequenceDiagram
    participant C as 호출자
    participant S as 사이드카
    participant M as 메인 앱
    participant O as 관측기
    C->>S: 서비스 요청
    S->>S: 1. 통신 정책 적용
    S->>M: 2. 루프백 전달
    M-->>S: 업무 응답
    S->>O: 3. 텔레메트리 전송
    S-->>C: 서비스 응답
```

**동작 원리**

1. **통신 정책 적용**: 인증·재시도·라우팅 규칙 판정
2. **루프백 전달**: 공유 네트워크로 메인 앱 호출
3. **텔레메트리 전송**: 요청 지연·오류·추적 정보 기록


#### 한줄 요약
- 요청이 옆 프록시를 거쳐 앱으로 들어가고 응답 지연·오류가 관측기로 복사되는 경로다

## Ⅴ. 종류 및 비교

<details>
<summary>핵심 용어</summary>

- **임베디드 라이브러리**: 임베디드 라이브러리는 공통 기능을 앱 프로세스에 직접 포함해 호출 지연과 별도 프로세스 자원 비용을 줄인다.

</details>

| 횡단 기능 배치 | 사이드카 | 임베디드 라이브러리 | 공유 서비스 |
|:---|:---|:---|:---|
| 적용 기준 | 앱별 **공통 기능 격리** | 낮은 지연·**단순 기능** | 다수 앱의 **중앙 공유** |
| 핵심 특징 | 파드 안에서 **별도 실행** | 앱 프로세스에 **직접 포함** | 원격 **공통 서비스** 제공 |
| 한계 | 인스턴스별 **자원 증가** | 코드 결합·**개별 배포** | 네트워크 지연·**중앙 장애** |

> 요약: 기능 격리는 **사이드카**, 저지연은 **임베디드 라이브러리** 선택

#### 한줄 요약
- 앱마다 격리하면 사이드카, 호출 지연이 민감하면 라이브러리, 중앙 공유가 필요하면 원격 서비스를 고른다

## Ⅵ. 실무 고려사항 및 대책

<details>
<summary>핵심 용어</summary>

- **자원 오버헤드**: 자원 오버헤드는 모든 인스턴스에 배치된 사이드카가 CPU와 메모리를 추가 소비해 노드의 배치 밀도를 낮추는 문제다.

</details>

| 문제 | 대책 | 효과 |
|:---|:---|:---|
| 사이드카의 **자원 오버헤드** | 요청량·노드별 **용량 산정** | 밀도 저하 **방지** |
| 메인 앱과 **수명주기 불일치** | 시작·종료·**준비 상태 연결** | 요청 손실 **방지** |
| 인스턴스별 **정책 차이** | 중앙 정책·**버전 동기화** | 통제 일관성 **확보** |
| 사이드카 장애 시 **메인 앱 통신 중단** | 사이드카를 제외한 **직접 통신 우회 경로** | 서비스 영향 **축소** |

#### 한줄 요약
- 메인 앱보다 프록시가 늦게 준비되면 요청이 사라지므로 두 컨테이너의 준비·종료 신호를 연결한다



## Ⅶ. 결론

<details>
<summary>핵심 용어</summary>

- **라이브러리**: 공통 기능의 프로세스 격리 이익이 자원 비용보다 크면 사이드카를 사용하고 낮은 지연이 우선이면 라이브러리를 선택한다.

</details>

- 공통 기능 격리가 자원 비용보다 크면 **사이드카**, 저지연은 **라이브러리** 선택

#### 한줄 요약
- 앱마다 붙는 보조 프로세스의 격리 이익이 파드별 CPU·메모리 비용보다 큰지 보고 적용한다
