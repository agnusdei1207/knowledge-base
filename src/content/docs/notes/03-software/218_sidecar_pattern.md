## Ⅰ. 개요

<details><summary>용어 설명</summary>

- **사이드카 패턴(Sidecar Pattern)**: 메인 애플리케이션 컨테이너를 수정하지 않고, 로깅, 모니터링, 통신 제어(Envoy Proxy), 설정 동기화 등 횡단 관심사(Cross-Cutting Concerns)를 동일한 파드(Pod) 내의 독립된 보조 컨테이너로 분리하여 배포하는 클라우드 네이티브 아키텍처 패턴.
- **공통 라이브러리 결합 및 언어 종속 위험(Library Coupling & Polyglot Barrier Risk)**: 공통 기능(Hystrix, Logback)을 소스코드 내 SDK로 포함할 경우 프레임워크 버전 의존성 충돌, 다국어(Java/Go/Node) 지원 불가 및 라이브러리 패치 시 전사 재배포가 강제되는 위험.

</details>

- 정의/개념: 메인 애플리케이션의 수정 없이 로깅, 모니터링, 통신 제어 등 **공통 횡단 기능을 별도의 보조 컨테이너로 분리 배포하는 아키텍처** 패턴
- 배경/필요성: 공통 라이브러리의 코드 내장으로 인한 **다국어(Polyglot) 지원 한계, 프레임워크 버전 결합 및 재배포 부담 위험** 직면

#### 한줄 요약

- 동일한 K8s 파드 내에서 localhost 네트워크와 볼륨을 공유하는 보조 컨테이너를 통해 비즈니스 로직과 인프라 관심사를 완벽히 분리

## Ⅱ. 특징

<details><summary>용어 설명</summary>

- **동일 파드 생명주기 결합(Pod Lifecycle Coupling)**: 메인 앱과 사이드카가 동일한 노드에 함께 스케줄링되고, 1:1로 스케일 아웃되며, 동일한 IP와 로컬 스토리지를 공유하는 결합 특성.
- **투명한 트래픽 인터셉트(Transparent Interception)**: iptables 룰을 통해 메인 앱의 인/아웃바운드 네트워크 패킷을 사이드카 프록시가 자동으로 가로채 mTLS 암호화 및 서킷 브레이커를 수행하는 기법.

</details>

- 개발 언어(Polyglot)와 무관하게 전사 공통 인프라 기능을 표준화하는 **언어 독립성(Polyglot Agnostic)**
- 메인 앱 코드 한 줄 변경 없이 mTLS 보안과 분산 트레이싱을 주입하는 **비침투적 확장(Non-invasive)**
- 프로세스는 격리되어 상호 크래시 전파를 차단하는 **안전한 장애 격리(Fault Isolation)**

#### 한줄 요약

- 언어 독립성, 비침투적 트래픽 제어, 파드 단위 자원 격리를 통해 마이크로서비스 인프라를 표준화

## Ⅲ. 구조 및 구성요소

<details><summary>용어 설명</summary>

- **사이드카 패턴 5대 핵심 파드 구성요소**: Main Container(비즈니스 앱), Sidecar Container(Envoy/Fluentbit), Shared Network(localhost), Shared Volume(로그/설정 공유), Resource Limits(cgroups 자원 제한).

</details>

```text
[ 쿠버네티스 파드(Pod) 내 사이드카 패턴 아키텍처 구조도 ]

 ┌─ [ Kubernetes Pod (단일 IP 주소: 10.244.1.15) ] ─────────────────────────┐
 │                                                                           │
 │ 1. [ 메인 애플리케이션 컨테이너 ] ── (localhost:8080 루프백 호출) ──┐      │
 │    • 순수 비즈니스 로직, 주문/결제 API 처리 (인프라 무지)          │      │
 │                                                                    │      │
 │ 2. [ 사이드카 프록시 컨테이너 (Envoy / Istio-proxy) ] ◄────────────┘      │
 │    • 인바운드/아웃바운드 트래픽 가로채기 (mTLS, 서킷 브레이커)           │
 │    • 텔레메트리 메트릭/트레이스(OpenTelemetry) 중앙 관측 플랫폼 전송     │
 │                                                                           │
 │ 3. [ 공유 볼륨 (EmptyDir Volume: `/var/log/app`) ] ───────────────────────┤
 │    • 메인 앱이 작성한 로그 파일을 사이드카(Fluentbit)가 실시간 읽어 전송  │
 └───────────────────────────────────────────────────────────────────────────┘
```

선의 의미: 메인 앱과 사이드카가 동일 파드 내에서 localhost와 공유 볼륨을 통해 통신하며 외부 트래픽을 중계하는 구조.

| 구성요소 | 책임 |
|:---|:---|
| 메인 컨테이너 (Main App) | 순수 **비즈니스 도메인 로직 및 데이터 처리를 담당하며 인프라 코드 배제** |
| 사이드카 컨테이너 (Sidecar) | 네트워크 프록시(mTLS/라우팅), **로그 수집, 설정 실시간 동기화, 관측 지표 전송 대행** |
| 공유 네트워크 (Namespace) | 동일한 파드 IP를 공유하여 **메인 앱과 사이드카 간 초저지연 localhost 루프백 통신 제공** |
| 공유 볼륨 (Shared Volume) | EmptyDir 마운트를 통해 **앱이 쓴 로그 파일이나 인증서 파일을 사이드카와 안전 공유** |
| 자원 한도 (Resource Limits) | 사이드카 컨테이너에 **CPU/메모리 상한선을 설정하여 메인 앱의 자원 고갈(Starvation) 방어** |

#### 한줄 요약

- 메인 앱, 사이드카 컨테이너, 공유 네트워크, 공유 볼륨, 자원 한도가 결합하여 파드를 구성

## Ⅳ. 흐름도

<details><summary>용어 설명</summary>

- **사이드카 트래픽 처리 5단계 수명주기**: 외부 요청 인입 $\to$ 사이드카 mTLS 복호화/인증 $\to$ localhost 전달 $\to$ 앱 비즈니스 처리 $\to$ 응답 가로채기 및 텔레메트리 전송.

</details>

```text
[ 사이드카 프록시 트래픽 인터셉트 및 텔레메트리 파이프라인 ]

 ┌────────────────────────────────────────┐
 │ 1. 외부 클라이언트의 HTTPS 서비스 요청 │
 └───────────────────┬────────────────────┘
                     │
                     ▼
 ┌────────────────────────────────────────┐
 │ 2. iptables가 트래픽을 사이드카로 인입 │
 │    (mTLS 상호 인증 + Rate Limit 검사)  │
 └───────────────────┬────────────────────┘
                     │
                     ▼
 ┌────────────────────────────────────────┐
 │ 3. localhost:8080 통해 메인 앱에 전달 │
 └───────────────────┬────────────────────┘
                     │
                     ▼
 ┌────────────────────────────────────────┐
 │ 4. 메인 앱이 순수 비즈니스 로직 응답 생성│
 └───────────────────┬────────────────────┘
                     │
                     ▼
 ┌────────────────────────────────────────┐
 │ 5. 사이드카가 메트릭 전송 및 외부 반환│
 └────────────────────────────────────────┘
```

### 동작 원리

1. 요청 인입: 주문 서비스로 들어오는 외부 gRPC 요청이 파드 IP로 도착.
2. 정책 적용: 파드 내부 iptables 규칙에 의해 사이드카(Envoy)가 트래픽을 가로채 mTLS 인증서 유효성을 검증.
3. 로컬 전달: 검증된 평문 트래픽을 메인 앱의 `localhost:8080` 포트로 0.1ms 만에 전달.
4. 비즈니스 처리: Spring Boot 메인 앱이 결제 트랜잭션을 처리하고 JSON 응답을 반환.
5. 텔레메트리 전송: 사이드카가 응답을 가로채 Prometheus 메트릭과 Jaeger 분산 트레이스를 전송한 후 클라이언트에 최종 응답.

#### 한줄 요약

- 요청 인입 $\to$ 정책 적용 $\to$ 로컬 전달 $\to$ 비즈니스 처리 $\to$ 텔레메트리 전송의 5단계

## Ⅴ. 종류 및 비교

<details><summary>용어 설명</summary>

- **사이드카 패턴 vs 임베디드 라이브러리 vs 공유 API 게이트웨이**: 파드 내 Out-of-Process(사이드카), 프로세스 내 SDK(임베디드), 중앙 집중 원격 노드(게이트웨이).

</details>

| 구분 | 사이드카 패턴 (Sidecar Pattern) | 임베디드 라이브러리 (In-Process SDK) | 공유 중앙 게이트웨이 (API Gateway) |
|:---|:---|:---|:---|
| **적용 기준** | Polyglot 다국어 마이크로서비스, 서비스 메시(Istio) 구축 시 | 극단적 초저지연(마이크로초)이 필요하거나 단일 언어 생태계 | 외부 클라이언트 인그레스(Ingress), 전사 단일 인증 관제 |
| **핵심 특징** | **파드 내 독립 컨테이너, 언어 독립적, 비침투적 투명 제어** | **앱 프로세스 내 함수 호출, 네트워크 오버헤드 0초** | **네트워크 홉(Hop)을 거쳐 중앙에서 일괄 보안/라우팅 통제** |
| **한계** | 파드 개수 증가 시 CPU/메모리 자원 오버헤드 선형 증가 | 라이브러리 패치 시 전사 앱 재컴파일 및 언어별 SDK 유지 부담 | 게이트웨이 장애 시 전사 마비(SPOF) 및 네트워크 지연 발생 |

#### 한줄 요약

- 다국어 서비스 간 통신은 사이드카, 초저지연은 임베디드 라이브러리, 외부 경계 관제는 API 게이트웨이를 채택

## Ⅵ. 실무 고려사항 및 대책

<details><summary>용어 설명</summary>

- **네이티브 사이드카 컨테이너(K8s Native Sidecar)**: K8s v1.28+에 도입되어 메인 앱보다 사이드카가 먼저 켜지고, 메인 앱이 완전히 꺼진 후에 사이드카가 종료되도록 순서를 보장하는 표준 기능.

</details>

| 문제 | 대책 | 효과 |
|:---|:---|:---|
| 파드 기동 시 사이드카(프록시)가 늦게 켜져 메인 앱의 DB 연결 실패 | **쿠버네티스 표준 `initContainers (restartPolicy: Always)` 네이티브 사이드카 적용** | 기동/종료 순서 불일치 패킷 드롭 100% 방지 |
| 수천 개 파드에 사이드카가 복제되어 막대한 클러스터 메모리 낭비 | **`eBPF 기반 사이드카리스(Sidecarless: Cilium Mesh)` 아키텍처 전환** | 노드 메모리 오버헤드 70% 절감 |
| 사이드카 다운 시 메인 앱의 헬스체크까지 함께 실패하여 파드 재시작 무한 루프 | **사이드카 장애 시 직접 통신을 허용하는 `Fail-Open 우회 경로` 구성** | 서비스 가용성 및 장애 격리 보장 |

#### 한줄 요약

- K8s 네이티브 사이드카 순서 제어, eBPF 사이드카리스 전환, Fail-Open 우회를 통해 안정성을 보장

## Ⅶ. 결론

<details><summary>용어 설명</summary>

- **엠비언트 메시(Ambient Mesh)와 eBPF의 진화**: 사이드카의 자원 오버헤드를 극복하기 위해 노드 레벨 eBPF 커널 계층과 L7 전담 웨이포인트(Waypoint) 프록시로 진화하는 차세대 서비스 메시 기술.

</details>

- **사이드카 패턴** 마이크로서비스 아키텍처에서 비즈니스 로직과 인프라 횡단 관심사를 분리하는 표준 설계 원칙이며, K8s 네이티브 라이프사이클 제어와 eBPF 기반 사이드카리스 기술을 결합하여 경량화되고 견고한 분산 플랫폼을 완성해야 함

#### 한줄 요약

- 파드 내 독립 보조 컨테이너를 통해 비즈니스와 인프라를 완벽히 분리하고 클라우드 네이티브 표준을 완성
