## Ⅰ. 개요

<details><summary>용어 설명</summary>

- **ANSI/SPARC 3단계 스키마**: 외부 스키마(External: 개별 사용자 뷰), 개념 스키마(Conceptual: 통합 논리 구조), 내부 스키마(Internal: 물리적 저장 배치)로 구성된 데이터베이스 계층 표준.
- **사용자-저장소 결합 및 권한 노출(Coupling & Security Exposure)**: 단일 스키마 구조에서 사용자 화면과 물리 디스크 배치가 얽혀 권한 통제가 불가능하고 유지보수가 마비되는 문제.

</details>

- 정의/개념: 데이터베이스의 복잡성을 은닉하고 데이터 독립성을 보장하기 위해 **외부 스키마(View), 개념 스키마(통합논리), 내부 스키마(물리저장)** 로 분리 정의한 표준 아키텍처
- 배경/필요성: 사용자 뷰와 물리적 저장 구조의 결합으로 인한 **데이터 중복, 보안 권한 통제 불가 및 스키마 변경 시 전면 수정 위험** 직면

#### 한줄 요약

- 외부(사용자 뷰), 개념(통합 논리), 내부(물리 저장)의 3단계 계층화를 통해 데이터 독립성과 보안성을 확보

## Ⅱ. 특징

<details><summary>용어 설명</summary>

- **N:1 외부 뷰 다중성(View Multiplicity)**: 단 하나의 통합 개념 스키마를 바탕으로 사용자 권한과 직무에 따라 N개의 서로 다른 외부 스키마(View)를 유연하게 제공하는 구조.
- **2단계 사상(Two-Level Mapping)**: 외부-개념 사상(논리 독립성)과 개념-내부 사상(물리 독립성)을 통해 상하위 계층의 변경 전파를 차단하는 원리.

</details>

- 사용자 관점, 조직 전체 관점, 스토리지 관점으로 분리된 **3단계 관심사 분리(SoD)**
- 단일 개념 스키마 위에 다수의 뷰를 생성하는 **N:1 외부 스키마 다중성 제공**
- 2단계 사상(Mapping)을 통한 **완전한 논리적·물리적 데이터 독립성 실현** #### 한줄 요약

- 단일 개념 스키마와 N개 외부 뷰의 3계층 분리를 통해 보안성과 유지보수 유연성을 극대화

## Ⅲ. 구조 및 구성요소

<details><summary>용어 설명</summary>

- **외부-개념 사상 vs 개념-내부 사상**: 사용자 뷰를 공통 테이블로 번역하는 외부-개념 사상과 공통 테이블을 디스크 파일/인덱스로 번역하는 개념-내부 사상.

</details>

```text
[ ANSI/SPARC 3단계 스키마 아키텍처 구조도 ]

 ┌────────────────────────────────────────────────────────────────────────┐
 │ [외부 스키마 1 (사용자 뷰)]          [외부 스키마 2 (관리자 뷰)]        │
 └───────────────────▲──────────────────────────────────▲─────────────────┘
                     │ (외부-개념 사상: 외부 뷰 ➔ 공통 논리 변환)
 ┌───────────────────┴──────────────────────────────────┴─────────────────┐
 │ [통합 개념 스키마 (엔티티, 속성, 관계, 무결성 제약조건)]                │
 └───────────────────────────────────▲────────────────────────────────────┘
                                     │ (개념-내부 사상: 공통 논리 ➔ 디스크 변환)
 ┌───────────────────────────────────▼────────────────────────────────────┐
 │ [내부 스키마 (데이터 파일 블록, B+Tree 인덱스, 파티셔닝, 압축)]         │
 └────────────────────────────────────────────────────────────────────────┘
```

선의 의미: 3개 스키마 계층을 2개 변환 매핑(Mapping)이 중계하여 계층 간 독립성과 투명성을 제공하는 아키텍처.

| 구성요소 | 책임 |
|:---|:---|
| 외부 스키마 (External) | 각 사용자 및 응용 프로그램 관점에서 **필요한 데이터만 선별한 논리적 서브셋(View)** |
| 외부-개념 사상 | 외부 뷰 질의를 개념 스키마 연산으로 변환하여 **논리적 데이터 독립성 보증** |
| 개념 스키마 (Conceptual) | 조직 전체의 관점에서 정의된 **단일 통합 데이터 모델 및 무결성 규칙(SSOT)** |
| 개념-내부 사상 | 개념 스키마 연산을 내부 디스크 I/O로 변환하여 **물리적 데이터 독립성 보증** |
| 내부 스키마 (Internal) | 디스크 상의 데이터 레코드 포맷, **인덱스 구조, 파티셔닝 및 저장 블록 배치** |

#### 한줄 요약

- 외부(개별 뷰), 개념(통합 모델), 내부(물리 저장)와 2단계 매핑이 유기적으로 결합

## Ⅳ. 흐름도

<details><summary>용어 설명</summary>

- **3단계 쿼리 변환 5단계 절차**: 외부 뷰 쿼리 $\to$ 외부-개념 사상 $\to$ 개념-내부 사상 $\to$ 디스크 블록 인출 $\to$ 외부 뷰 투영 반환.

</details>

```text
[ 3단계 스키마 쿼리 처리 및 변환 파이프라인 ]

 ┌────────────────────────────────────────┐
 │ 1. 외부 스키마(View) 질의 요청 접수    │
 └───────────────────┬────────────────────┘
                     │
                     ▼
 ┌────────────────────────────────────────┐
 │ 2. 외부-개념 사상: 통합 논리 쿼리 변환 │
 └───────────────────┬────────────────────┘
                     │
                     ▼
 ┌────────────────────────────────────────┐
 │ 3. 개념-내부 사상: 물리 접근 경로 변환 │
 └───────────────────┬────────────────────┘
                     │
                     ▼
 ┌────────────────────────────────────────┐
 │ 4. 내부 디스크 블록/인덱스 데이터 조회 │
 └───────────────────┬────────────────────┘
                     │
                     ▼
 ┌────────────────────────────────────────┐
 │ 5. 외부 스키마 뷰 형식으로 투영 반환   │
 └────────────────────────────────────────┘
```

### 동작 원리

1. 질의 접수: 클라이언트가 특정 외부 뷰(External View)를 대상으로 SQL 쿼리를 실행.
2. 외부-개념 사상: DBMS 엔진이 외부-개념 매핑 메타데이터를 참조하여 뷰를 개념 스키마의 실제 테이블과 조인 연산으로 변환.
3. 개념-내부 사상: 옵티마이저가 개념-내부 매핑을 참조하여 인덱스 스캔 및 디스크 블록 접근 경로를 생성.
4. 디스크 데이터 조회: 스토리지 엔진이 내부 스키마에 정의된 데이터 파일과 인덱스 블록에서 튜플을 인출.
5. 뷰 투영 반환: 인출된 원본 데이터를 외부 스키마에 정의된 컬럼 구조로 필터링/가공하여 클라이언트에 반환.

#### 한줄 요약

- 외부 뷰 $\to$ 개념 변환 $\to$ 물리 경로 변환 $\to$ 디스크 인출 $\to$ 뷰 투영 반환의 5단계

## Ⅴ. 종류 및 비교

<details><summary>용어 설명</summary>

- **외부 vs 개념 vs 내부 스키마**: 사용자 관점의 서브셋(외부), 조직 전체 관점의 통합 논리(개념), 시스템 관점의 물리 저장(내부).

</details>

| 구분 | 외부 스키마 (External) | 개념 스키마 (Conceptual) | 내부 스키마 (Internal) |
|:---|:---|:---|:---|
| **적용 기준** | 일반 사용자, 프론트엔드/백엔드 개발자 | 데이터 아키텍트(DA), 비즈니스 분석가 | DBA, 시스템 엔지니어 |
| **핵심 특징** | **사용자 직무별 N개의 독립 뷰(View) 존재** | **전체 데이터 구조 및 무결성을 정의하는 단 1개의 모델** | **파일, 인덱스, 블록 배치를 정의하는 단 1개의 스토리지 모델** |
| **한계** | 복잡한 다중 뷰 생성 시 메타데이터 오버헤드 | 비즈니스 변경 시 모델링 정합성 유지 난이도 | 하드웨어 및 OS 스토리지 엔진 제약 종속 |

#### 한줄 요약

- 외부는 사용자별 뷰(N개), 개념은 통합 논리 모델(1개), 내부는 물리 저장 배치(1개)로 정의

## Ⅵ. 실무 고려사항 및 대책

<details><summary>용어 설명</summary>

- **뷰 거버넌스(View Governance)**: 무분별한 뷰 생성을 억제하고 개념 스키마 변경 시 영향받는 외부 뷰를 체계적으로 관리하는 운영 체계.

</details>

| 문제 | 대책 | 효과 |
|:---|:---|:---|
| 개념 스키마 컬럼 변경 시 기존 외부 뷰 파행 에러 | **외부-개념 사상(DB View) 사전 영향도 분석 및 자동 동기화** | 응용 프로그램 수정 없는 무중단 전환 |
| 내부 스토리지 파티셔닝 변경 시 개념 스키마 혼선 | **스토리지 엔진 내부 매핑의 완전한 투명성(Transparency) 유지** | 물리적 튜닝의 논리 모델 전파 차단 |
| 수백 개의 미사용 외부 뷰 누적으로 인한 딕셔너리 부하 | **미사용 외부 뷰 모니터링 및 정기적 라이프사이클 정제** | 데이터 딕셔너리 파싱 성능 최적화 |

#### 한줄 요약

- 뷰 사전 영향도 분석, 스토리지 투명성 유지, 정기 뷰 정제를 통해 3단계 스키마의 안정성을 유지

## Ⅶ. 결론

<details><summary>용어 설명</summary>

- **데이터 계층화의 보편적 가치(Universal Layering)**: ANSI/SPARC의 3단계 스키마 사상은 현대 마이크로서비스 DTO, 도메인 엔티티, 영속성 계층(JPA) 분리의 근간이 됨.

</details>

- **3단계 스키마 아키텍처** 기반 데이터베이스 시스템의 복잡성을 관리하고 지속 가능한 진화를 가능케 하는 핵심 프레임워크이며, 철저한 계층 분리와 2단계 사상을 준수하여 데이터 거버넌스를 확립해야 함

#### 한줄 요약

- 외부, 개념, 내부 스키마의 명확한 분리와 2단계 매핑을 통해 무결성과 데이터 독립성을 완성
