## Ⅰ. 개요

<details><summary>용어 설명</summary>

- **ANSI/SPARC 3단계 스키마**: 데이터베이스 관리의 복잡성을 줄이고 데이터 독립성을 보장하기 위해 외부, 개념, 내부 계층으로 구분한 표준 구조.
- **관심사 분리(Separation of Concerns)**: 개별 사용자 관점(외부), 조직 통합 관점(개념), 시스템 물리 저장 관점(내부)으로 책임을 분리.

</details>

- 정의/개념: 데이터베이스의 복잡성을 은닉하고 데이터 독립성을 보장하기 위해 외부 스키마(사용자 뷰), 개념 스키마(통합 논리), **내부 스키마**(물리 저장) 로 분리 정의한 표준 아키텍처
- 배경/필요성: 사용자별 요구사항을 단일 통합 구조에 직접 결합할 때 발생하는 **보안 권한 통제 난항 및 물리 저장 장치 튜닝 시 응용 프로그램 전체 중단 한계**

#### 한줄 요약
- 3계층 분리는 변경 격리와 권한 통제를 얻는 대신 모든 접근이 두 번의 사상을 거치게 하므로, 이 구조의 이득은 변경이 잦은 환경에서만 그 변환 비용을 넘어선다.

## Ⅱ. 특징

<details><summary>용어 설명</summary>

- **N:1 외부 뷰 다중성**: 단일 개념 스키마를 기반으로 사용자 직무 및 권한에 따라 N개의 서로 다른 외부 뷰를 동적으로 생성.
- **Two-Level Mapping**: 외부-개념·개념-내부 사상으로 계층 간 변경 영향을 줄이는 구조.

</details>

- 사용자 관점, 조직 전체 관점, 스토리지 관점으로 분리된 3단계 **관심사 분리**(SoD)
- 단일 개념 스키마 위에 다수의 뷰를 생성하는 N:1 외부 스키마 다중성 제공
- 2단계 사상으로 논리적·물리적 데이터 독립성 지원

#### 한줄 요약
- 개념 스키마를 하나로 두고 외부 뷰만 여럿 두기에 데이터 정본은 한 곳에 유지되면서 관점별 노출 범위가 갈라지므로, 뷰는 조회 편의 장치인 동시에 권한 경계 그 자체가 된다.

## Ⅲ. 구조 및 구성요소

<details><summary>용어 설명</summary>

- **3단계 스키마 구성요소**: 외부 스키마(N개 뷰), 개념 스키마(1개 통합 모델), 내부 스키마(1개 물리 스토리지 모델).

</details>

```text
[ANSI/SPARC 3단계 스키마 아키텍처]
|-- 외부 스키마 (External Schema: User A View, User B View - N개 존재)
|   `-- [외부-개념 사상]
|-- 개념 스키마 (Conceptual Schema: 통합 엔티티, 속성, 관계, 무결성 규칙 - 1개 존재)
|   `-- [개념-내부 사상]
`-- 내부 스키마 (Internal Schema: B+Tree 인덱스, 파일 블록, 파티셔닝, 압축 - 1개 존재)
```

선의 의미: 계층 및 3개 스키마 계층을 2개 변환 매핑이 중계하여 계층 간 독립성을 제공하는 구조

| 구성요소 | 책임 |
|:---|:---|
| 외부 스키마 | 사용자별 뷰·접근 범위 정의 |
| 외부-개념 사상 | 외부 질의를 개념 모델 연산으로 변환 |
| 개념 스키마 | 통합 엔티티·관계·무결성 제약 정의 |
| 개념-내부 사상 | 개념 연산을 물리 접근 경로로 변환 |
| 내부 스키마 | 인덱스·파티션·블록 배치 정의 |

#### 한줄 요약
- 세 계층은 나란한 병렬 구조가 아니라 개념 스키마를 축으로 위아래 사상이 매달린 형태이므로, 개념 스키마의 변경만이 양쪽 계층 모두에 비용을 전파한다.

## Ⅳ. 흐름도

<details><summary>용어 설명</summary>

- **3단계 질의 변환 파이프라인**: 뷰 쿼리 접수 $\to$ 외부-개념 사상 변환 $\to$ 개념-내부 사상 변환 $\to$ 디스크 블록 인출 $\to$ 뷰 형식 투영 반환.

</details>

```text
클라이언트가 외부 뷰(View)를 대상으로 SQL 질의 실행
        │
   [외부-개념 사상] DBMS 엔진이 뷰 쿼리를 개념 스키마의 실제 테이블 조인 쿼리로 변환
        │
   [개념-내부 사상] CBO 옵티마이저가 인덱스 및 디스크 블록 물리 접근 경로(Execution Plan) 생성
        │
   [물리 블록 I/O] 스토리지 엔진이 내부 스키마에 정의된 데이터 파일/인덱스 블록에서 튜플 인출
        │
   [뷰 투영 반환] 인출된 원본 데이터를 외부 스키마에 정의된 컬럼 포맷으로 필터링하여 응답
```

#### 한줄 요약
- 질의는 뷰에서 물리로 내려가고 결과는 반대로 투영돼 올라오므로 계층마다 변환 비용이 붙지만, 조건을 아래 계층으로 밀어내면 인출량 자체가 줄어 그 비용을 상쇄할 수 있다.

## Ⅴ. 종류 및 비교

<details><summary>용어 설명</summary>

- **외부 vs 개념 vs 내부 스키마**: 사용자 관점 서브셋(외부), 조직 전체 통합 모델(개념), 시스템 물리 저장(내부).

</details>

| 비교 항목 | 외부 스키마 (External) | 개념 스키마 (Conceptual) | 내부 스키마 (Internal) |
|:---|:---|:---|:---|
| 관점 및 대상 | 최종 사용자, 애플리케이션 개발자 | 데이터 아키텍트(DA), DBA | 시스템 엔지니어, 스토리지 DBA |
| 인스턴스 개수 | N개 (업무 역할별 다수 존재) | 1개 (전사 단일 통합 모델) | 1개 (물리 저장소 모델) |
| 핵심 구성요소 | SQL View, 가상 테이블, 화면 DTO | 엔티티(Entity), 관계(Relation), 제약 | B+Tree 인덱스, 블록, 파티션, 압축 |
| 주 달성 목표 | 사용자 편의성 및 데이터 보안 격리 | 전사 데이터 무결성 및 단일 진실 공급원| 디스크 I/O 최적화 및 고속 쿼리 성능 |

#### 한줄 요약
- 세 스키마는 같은 데이터를 누구의 관점에서 기술하느냐로 갈리며, 개수가 N:1:1이라는 사실 자체가 어느 계층이 변경에 자주 노출되고 어느 계층이 정본을 지키는지를 드러낸다.

## Ⅵ. 실무 고려사항 및 대책

<details><summary>용어 설명</summary>

- **View Lifecycle Governance**: 무분별한 뷰 생성을 방지하고 스키마 변경 시 영향받는 외부 뷰를 추적 관리하는 거버넌스.

</details>

| 문제 | 대책 | 효과 |
|:---|:---|:---|
| 개념 스키마 변경에 따른 외부 뷰 오류 | 외부-개념 사상 영향도 분석 | 응용 변경 범위와 호환성 확인 |
| 파티셔닝 변경의 논리 모델 전파 | 개념-내부 사상으로 저장 변경 은닉 | 물리 튜닝의 논리 영향 완화 |
| 미사용 외부 뷰 누적에 따른 관리 부하 | 뷰 사용량 추적·수명주기 정제 | 딕셔너리와 의존성 관리 비용 감소 |
| 뷰를 통한 복합 조인 시 옵티마이저 비효율 발생 | View Merging 및 Predicate Pushdown 힌트 최적화 | 뷰 기반 쿼리 성능 저하 방지 |

#### 한줄 요약
- 뷰 영향도 분석, 스토리지 투명성, 정기 뷰 정제, Predicate Pushdown으로 안정성을 유지한다.

## Ⅶ. 결론

- 현대 관계형 DBMS 및 엔터프라이즈 데이터 아키텍처의 **가장 표준적인 관심사 분리(Separation of Concerns) 계층 모델**로 확립되었으며, 실무 데이터 모델링 시에는 **전사 단일 진실 공급원(SSOT)을 수립하는 3NF 개념 스키마 설계, 역할 기반 접근 제어(RBAC)와 개인정보 마스킹을 결합한 외부 뷰(View) 거버넌스, I/O 성능 극대화를 위한 파티셔닝/인덱스 내부 스키마 튜닝**을 조화롭게 운용하여 시스템 안정성과 확장성을 극대화

#### 한줄 요약
- 사용자 관점은 외부, 통합 모델은 개념, 저장 방식은 내부로 분리한다.
