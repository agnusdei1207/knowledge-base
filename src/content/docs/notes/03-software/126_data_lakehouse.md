## Ⅰ. 개요

<details><summary>용어 설명</summary>

- **데이터 레이크하우스(Data Lakehouse)**: 데이터 레이크(Data Lake)의 저비용 객체 스토리지 수평 확장성과 데이터 웨어하우스(DW)의 100% ACID 트랜잭션 및 고성능 SQL 관리 기능을 단일 계층으로 통합한 차세대 데이터 아키텍처.
- **이중 적재 비용 및 데이터 사일로(Dual Ingestion & Inconsistency)**: 레이크와 DW를 분리 운영하여 발생하는 데이터 중복 복제 비용, 파이프라인 지연 및 엔진 간 지표 불일치 문제.

</details>

- 정의/개념: 데이터 레이크의 유연한 저비용 스토리지와 **데이터 웨어하우스의 ACID 트랜잭션 및 고성능 SQL 관리를 단일 계층으로 융합**한 차세대 데이터 아키텍처
- 배경/필요성: Lake와 DW 이중 인프라 운영 시 발생하는 **데이터 중복 복제 비용, 파이프라인 지연 및 엔진 간 지표 불일치 위험** 직면

#### 한줄 요약

- 저비용 객체 스토리지 위에 오픈 테이블 포맷(Delta/Iceberg)을 결합하여 ACID 트랜잭션과 다중 엔진 SQL 분석을 구현

## Ⅱ. 특징

<details><summary>용어 설명</summary>

- **오픈 테이블 포맷(Open Table Format)**: S3 등의 불변 Parquet 파일 위에서 ACID 트랜잭션, 타임 트래블(Time Travel), 스키마 진화(Schema Evolution)를 제공하는 메타데이터 계층(Delta, Iceberg, Hudi).
- **타임 트래블(Time Travel)**: 스냅샷 메타데이터 이력을 추적하여 과거 특정 시점의 데이터로 쿼리를 실행하거나 롤백하는 기능.

</details>

- 객체 스토리지 기반의 **100% ACID 트랜잭션 및 스냅샷 격리 보장**
- 단일 데이터 원천을 Spark, Presto/Trino, 머신러닝 엔진이 **직접 동시 조회(Direct Access)**
- 스냅샷 이력을 추적하여 과거 시점으로 롤백 가능한 **타임 트래블(Time Travel) 지원** #### 한줄 요약

- 오픈 테이블 포맷을 통해 레이크의 경제성과 DW의 신뢰성을 동시에 달성

## Ⅲ. 구조 및 구성요소

<details><summary>용어 설명</summary>

- **트랜잭션 로그 메타데이터(Transaction Log)**: 데이터 파일의 추가 및 삭제 이력을 JSON/AVRO 스냅샷으로 기록하여 동시성 제어(OCC)를 수행하는 핵심 계층.

</details>

```text
[ 데이터 레이크하우스 통합 계층 아키텍처 구조도 ]

 ┌────────────────────────────────────────────────────────────────────────┐
 │ 1. 다중 분석 엔진 계층 (Diverse Compute Engines)                       │
 │   - [ Spark SQL ]  [ Trino / Presto ]  [ Databricks ]  [ ML Engine ]   │
 ├────────────────────────────────────────────────────────────────────────┤
 │ 2. 오픈 테이블 포맷 계층 (Open Table Format Layer)                     │
 │   - Delta Lake / Apache Iceberg / Apache Hudi                          │
 │   - ACID 트랜잭션 로그 (JSON/AVRO 스냅샷 메타데이터)                   │
 │   - Time Travel, Schema Evolution, Partition Evolution                 │
 ├────────────────────────────────────────────────────────────────────────┤
 │ 3. 스토리지 계층 (Cloud Object Storage)                                │
 │   - AWS S3, Google Cloud Storage, Azure ADLS                           │
 │   - 불변(Immutable) Parquet / ORC 열 지향 데이터 파일                 │
 └────────────────────────────────────────────────────────────────────────┘
```

선의 의미: 다종의 쿼리 엔진이 Open Table Format 메타데이터 레이어를 경유하여 S3의 Parquet 파일에 ACID 및 고성능 SQL 연산을 수행하는 아키텍처.

| 구성요소 | 책임 |
|:---|:---|
| 다중 연산 엔진 (Compute) | Spark, Trino, MLlib 등이 **공통 테이블 포맷을 통해 데이터를 직접 병렬 처리** |
| 오픈 테이블 포맷 (Format) | Delta Lake, Iceberg 등이 **ACID 트랜잭션, 타임 트래블, 스키마 진화 통제** |
| 메타데이터 카탈로그 | 현재 유효한 최신 테이블 스냅샷 포인터 및 **파티션/파일 통계 정보 보관** |
| 객체 스토리지 (Storage) | AWS S3 등에 **불변(Immutable) Parquet 데이터 파일과 변경 로그 영구 저장** |

#### 한줄 요약

- 다중 연산 엔진, 오픈 테이블 포맷, 메타데이터 카탈로그, 객체 스토리지가 결합된 아키텍처

## Ⅳ. 흐름도

<details><summary>용어 설명</summary>

- **낙관적 동시성 제어(OCC) 기반 쓰기 절차**: 스냅샷 조회 $\to$ 불변 파일 쓰기 $\to$ 충돌 검증 $\to$ 메타데이터 생성 $\to$ 원자적 포인터 전환.

</details>

```text
[ 레이크하우스 OCC 기반 원자적 쓰기 파이프라인 ]

 ┌────────────────────────────────────────┐
 │ 1. 현재 테이블 기준 스냅샷(버전 N) 조회│
 └───────────────────┬────────────────────┘
                     │
                     ▼
 ┌────────────────────────────────────────┐
 │ 2. 신규 Parquet 데이터 파일 S3 기록    │
 └───────────────────┬────────────────────┘
                     │
                     ▼
 ┌────────────────────────────────────────┐
 │ 3. 동시 커밋 충돌(Conflict) 여부 검증  │
 └───────────────────┬────────────────────┘
                     │ (충돌 없을 시)
                     ▼
 ┌────────────────────────────────────────┐
 │ 4. 신규 스냅샷 메타데이터(N+1) 생성    │
 └───────────────────┬────────────────────┘
                     │
                     ▼
 ┌────────────────────────────────────────┐
 │ 5. 최신 메타데이터 포인터 원자적 전환  │
 └────────────────────────────────────────┘
```

### 동작 원리

1. 스냅샷 조회: 쓰기 트랜잭션이 현재 테이블의 최신 스냅샷 버전(Version N)을 확인.
2. 파일 기록: 변경된 데이터를 새로운 불변 Parquet 파일로 S3에 기록.
3. 충돌 검증: 쓰기 도중 다른 트랜잭션이 동일한 파티션이나 파일을 수정했는지 낙관적 동시성 제어(OCC)로 검사.
4. 메타데이터 생성: 충돌이 없으면 추가된 파일과 삭제된 파일 목록을 담은 신규 메타데이터(Version N+1)를 작성.
5. 포인터 전환: 카탈로그가 가리키는 현재 메타데이터 포인터를 원자적(Atomic)으로 N+1로 전환하여 새 버전을 즉시 공개.

#### 한줄 요약

- 스냅샷 확인 $\to$ 불변 파일 생성 $\to$ OCC 충돌 검증 $\to$ 메타데이터 작성 $\to$ 원자적 전환의 5단계

## Ⅴ. 종류 및 비교

<details><summary>용어 설명</summary>

- **DW vs Lake vs Lakehouse**: 정형 SQL 전용 DW, 무질서 원본 보관 Lake, 둘의 장점을 융합한 Lakehouse.

</details>

| 구분 | 데이터 웨어하우스 (DW) | 데이터 레이크 (Data Lake) | 데이터 레이크하우스 (Data Lakehouse) |
|:---|:---|:---|:---|
| **적용 기준** | 고성능 정형 BI 및 재무 분석 | 대규모 비정형 데이터 원시 수집 | 전사 통합 BI, 대규모 SQL 및 AI/ML 통합 분석 |
| **핵심 특징** | **전용 엔진 관리, 완벽한 ACID, 정형 전용** | **저비용 객체 스토리지, Schema-on-Read** | **객체 스토리지 + 오픈 테이블 포맷(ACID/SQL)** |
| **한계** | 고비용 스토리지 및 비정형 처리 불가 | 트랜잭션 부재로 인한 정합성 파괴 위험 | 메타데이터 관리 및 파일 컴팩션 튜닝 오버헤드 |

#### 한줄 요약

- DW의 정합성과 Lake의 유연성을 융합하여 단일 스토리지에서 모든 분석을 처리

## Ⅵ. 실무 고려사항 및 대책

<details><summary>용어 설명</summary>

- **컴팩션 및 진공 청소(Optimize & Vacuum)**: 자잘한 파일을 큰 파일로 병합하는 `OPTIMIZE`와 보존 기간이 지난 구버전 파일을 물리 삭제하여 스토리지 비용을 절감하는 `VACUUM`.

</details>

| 문제 | 대책 | 효과 |
|:---|:---|:---|
| 자잘한 파티션 파일 누적으로 인한 쿼리 성능 급락 | **`OPTIMIZE` (Bin-packing) 작업으로 128MB~1GB 파일 병합** | 메타데이터 조회 및 스캔 속도 5배 가속 |
| 타임 트래블 이력 누적으로 S3 스토리지 비용 폭증 | **`VACUUM` 명령을 주기적으로 실행하여 7일 이전 구버전 파일 삭제** | 미사용 스토리지 비용 50% 이상 절감 |
| 원천 데이터 구조 변경으로 인한 스키마 충돌 오류 | **`mergeSchema` 옵션 활성화를 통한 안전한 스키마 진화 허용** | 파이프라인 중단 없는 유연한 스키마 적응 |

#### 한줄 요약

- 파일 컴팩션, 진공 청소(Vacuum), 스키마 진화 옵션을 통해 안정적인 레이크하우스를 운영

## Ⅶ. 결론

<details><summary>용어 설명</summary>

- **단일 진실 공급원 레이크하우스(Unified Lakehouse SSOT)**: BI 분석가, 데이터 엔지니어, AI 연구원이 동일한 오픈 테이블을 실시간 공유하는 최신 엔터프라이즈 표준.

</details>

- **데이터 레이크하우스** 기반 데이터 사일로와 이중 인프라 운영 비용을 근본적으로 제거한 현대 데이터 엔지니어링의 정점이며, 오픈 테이블 포맷과 클라우드 분산 쿼리 엔진을 결합하여 전사 단일 진실 공급원(SSOT) 플랫폼을 구축해야 함

#### 한줄 요약

- 객체 스토리지와 오픈 테이블 포맷을 결합하여 ACID 트랜잭션과 고성능 다중 엔진 분석을 완성
