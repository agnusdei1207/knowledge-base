## Ⅰ. 개요

<details><summary>용어 설명</summary>

- **클라우드 4대 배포 모델**: 자원 공유 퍼블릭(Public), 단독 구축 프라이빗(Private), 온프레미스-퍼블릭 연계 하이브리드(Hybrid), 복수 CSP 활용 멀티(Multi-Cloud).
- **데이터 상주성(Data Residency)**: 개인정보나 금융 거래 데이터를 자국 영토 또는 폐쇄망 내부 데이터센터에만 보관해야 하는 법적 규제.

</details>

- 정의/개념: 인프라의 위치와 점유 독점성 및 연결 방식에 따라 퍼블릭, 프라이빗, 하이브리드, 멀티 클라우드로 분류한 배포 아키텍처
- 배경/필요성: 온프레미스의 확장성 한계 및 퍼블릭 클라우드 단독 도입 시 발생하는 데이터 주권/망분리 규제, 벤더 종속(Lock-in) 및 CSP 리전 장애 위험 한계

#### 한줄 요약
- 배포 모델은 규제 준수와 탄력성 중 무엇을 우선할지의 배치 결정이므로, 여러 모델을 섞을수록 각각의 장점을 얻는 대신 연계망과 통합 인증이라는 새로운 고정 비용이 붙는다.

## Ⅱ. 특징

<details><summary>용어 설명</summary>

- **Cloud Bursting**: 평시에는 온프레미스/프라이빗을 사용하다가 트래픽 폭증 시 퍼블릭 클라우드로 연산을 동적 확장하는 기법.
- **Egress Fee**: 서로 다른 클라우드 또는 온프레미스로 데이터를 전송할 때 발생하는 아웃바운드 네트워크 통신 비용.

</details>

- 멀티테넌시 기반 탄력적 확장을 제공하는 퍼블릭 클라우드의 비용 효율성
- 단일 조직 전용 인프라로 완전한 보안 통제를 보장하는 프라이빗 클라우드의 규제 준수
- 전용선(Direct Connect) 기반 연계를 통한 하이브리드 및 멀티 클라우드의 유연성

#### 한줄 요약
- 퍼블릭의 확장성과 프라이빗의 통제력을 결합하여 고가용성과 비용 효율성을 달성한다.

## Ⅲ. 구조 및 구성요소

<details><summary>용어 설명</summary>

- **하이브리드 연계 컴포넌트**: Private IDC, AWS Direct Connect 전용선, Public Cloud, Multi-Cloud 상호 연동.

</details>

```text
[클라우드 배포 모델 (Deployment)]
├─ [단일 배포 환경]
│  ├─ 퍼블릭 (멀티테넌시·비용효율)
│  └─ 프라이빗 (단독인프라·규제준수)
├─ [복합 배포 환경]
│  ├─ 하이브리드 (IDC-Cloud 전용망 연계)
│  └─ 멀티 클라우드 (복수 CSP·락인방지)
└─ [통합 관리 계층]
   ├─ 연결망 (Direct Connect·IPSec VPN)
   └─ 거버넌스 (통합 IAM·멀티 클러스터 K8s)
```

- 선의 의미: 계층 구조 및 상하위 포함 관계를 나타낸다.

| 구성요소 | 책임 |
|:---|:---|
| 퍼블릭 클라우드 | 공유 인프라의 탄력적 확장 제공 |
| 프라이빗 클라우드 | 전용 인프라의 데이터 주권·보안 통제 |
| 하이브리드 연계 | 전용선 기반 동기화·버스팅 조율 |
| 멀티 클라우드 | 복수 CSP의 락인 방지·재해복구 |

#### 한줄 요약
- 하이브리드 연계망은 프라이빗의 데이터 주권 통제와 퍼블릭의 탄력적 확장 사이에 전용선 계층으로 끼어들어 어느 한쪽 모델만 고르는 선택을 대신하고, 멀티 클라우드는 그 위에서 단일 CSP에 몰린 락인과 재해 위험을 복수 사업자로 나눈다.

## Ⅳ. 흐름도

<details><summary>용어 설명</summary>

- **배포 모델 선정 5단계**: 데이터 민감도 분류 $\to$ 트래픽 탄력성 평가 $\to$ 모델 선정 $\to$ 전용선/IAM 설계 $\to$ Egress/DR 검증.

</details>

```text
기업 신규 워크로드 인프라 아키텍처 설계 요청
        │
   [데이터 분류] 개인정보, 금융 계좌 등 법적 규제 대상 데이터와 일반 서비스 데이터 식별
        │
   [탄력성 평가] 트래픽 급증 시 오토스케일링 필수 여부 및 지연시간(Latency) 요구사항 분석
        │
   [모델 선정] 핵심 원장은 프라이빗, 대외 웹 서비스는 퍼블릭에 배치하는 하이브리드/멀티 선정
        │
   [연계망 및 보안 설계] AWS Direct Connect 전용선 및 OIDC 기반 중앙 통합 IAM 구성
        │
   클라우드 간 데이터 전송 Egress 네트워크 비용 및 리전 장애 시 DR 페일오버 경로 검증
```

#### 한줄 요약
- 모델을 나누는 기준은 시스템이 아니라 데이터의 민감도이므로, 분류가 끝나지 않은 상태에서 배치를 먼저 정하면 이후 재배치 비용이 고스란히 남는다.

## Ⅴ. 종류 및 비교

<details><summary>용어 설명</summary>

- **4대 배포 모델 비교**: Public(탄력성), Private(보안 통제), Hybrid(유연한 절충), Multi-Cloud(DR 및 벤더 독립).

</details>

| 비교 항목 | 퍼블릭 클라우드 (Public) | 프라이빗 클라우드 (Private) | 하이브리드 / 멀티 클라우드 |
|:---|:---|:---|:---|
| 자원 점유 방식 | 멀티테넌시 공유 자원 (임대) | 단일 조직 독점 자원 (자체 구축) | 온프레미스 독점 + 멀티테넌시 결합 |
| 비용 투자 모델 | 운영비용 중심 종량제 (OpEx) | 초기 막대한 자본투자 (CapEx) | CapEx + OpEx 혼합 최적화 |
| 보안 및 규제 준수 | CSP 보안 준수 (데이터 상주 제약) | 완벽한 데이터 주권 및 폐쇄망 통제 | 민감 데이터 격리 및 유연한 규제 대응|
| 확장 탄력성 | 무제한 즉각 오토스케일링 | 물리적 장비 증설 필요로 한계 | 클라우드 버스팅(Bursting) 지원 |

#### 한줄 요약
- 빠른 확장은 퍼블릭, 강력한 통제는 프라이빗, 규제와 탄력성을 절충할 때는 하이브리드/멀티를 선택한다.

## Ⅵ. 실무 고려사항 및 대책

<details><summary>용어 설명</summary>

- **Egress Cost**: 이종 클라우드 또는 온프레미스로 데이터를 아웃바운드 전송할 때 발생하는 기가바이트당 과금.

</details>

| 문제 | 대책 | 효과 |
|:---|:---|:---|
| 이종 클라우드 간 대용량 데이터 전송 시 Egress 비용 폭증 | 데이터 상주 영역 최적화 및 Dedicated Direct Connect 구축 | 네트워크 전송 비용 50% 이상 절감 |
| 클라우드별 IAM 정책 상이로 인한 보안 관리 복잡성 | OIDC 기반 중앙 Identity Provider 및 HashiCorp Vault 연동 | 단일 창구 기반 통합 접근 통제 |
| 프라이빗 클라우드 피크 타임 용량 고갈로 서비스 마비 | K8s 기반 클라우드 버스팅(Cloud Bursting) 자동화 파이프라인 구성 | 피크 트래픽 다운타임 0화 |
| 특정 CSP 장애 시 전사 서비스 중단 리스크 | Multi-Cloud 액티브-스탠바이 DR 및 DNS(Route 53) 헬스체크 전환 | 서비스 가용성 99.999% 달성 |

#### 한줄 요약
- Egress 비용 최적화, 통합 IAM 구축, 클라우드 버스팅, 멀티 클라우드 DR로 안정성을 확보한다.

## Ⅶ. 결론

- 엔터프라이즈 인프라 아키텍처 및 클라우드 네이티브 전환의 핵심 물리/논리 배치 전략 프레임워크로 확립되었으며, 실무 구축 시에는 규제 대상 원장과 핵심 자산은 프라이빗/폐쇄망에 유지하고 대외 대고객 서비스는 퍼블릭에 배치하는 하이브리드 버스팅(Cloud Bursting), 데이터 유출 및 비용 폭증을 방어하는 Direct Connect 전용선 기반 Egress 비용 통제, 이종 인프라를 단일 통제하는 OIDC 중앙 통합 IAM 및 Kubernetes 기반 멀티 클라우드 DR 페일오버 체계를 결합하여 규제 준수와 운영 탄력성을 동시 완성

#### 한줄 요약
- 클라우드 배포 모델은 보안 규제와 확장 탄력성의 균형을 맞추어 최적의 인프라 배치를 결정짓는 엔터프라이즈 아키텍처의 필수 기준이다.
