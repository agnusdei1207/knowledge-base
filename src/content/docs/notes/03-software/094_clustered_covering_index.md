## Ⅰ. 개요

<details><summary>용어 설명</summary>

- **클러스터드 인덱스 및 커버링 인덱스(Clustered & Covering Index)**: 데이터 행 자체가 키 순서로 디스크에 물리 정렬되는 클러스터드 인덱스와 쿼리에 필요한 모든 컬럼을 인덱스에 포함하여 2차 테이블 접근(Key Lookup)을 제거하는 커버링 인덱스.
- **랜덤 I/O 및 쿼리 지연(Random I/O & Latency)**: 비클러스터드 인덱스 조회 후 실제 데이터를 가져오기 위해 디스크 힙 영역을 반복 접근하며 발생하는 I/O 병목 현상.

</details>

- 정의/개념: 테이블 데이터 행을 키 순서대로 디스크에 물리 정렬하는 **클러스터드 인덱스와 Key Lookup 없이 인덱스만으로 질의를 완결하는 커버링 인덱스** 기반 I/O 최적화 기법
- 배경/필요성: 잦은 범위 검색 및 비클러스터드 인덱스의 반복적 Key Lookup으로 인한 **랜덤 I/O 급증 및 쿼리 응답 시간 지연 위험** 직면

#### 한줄 요약

- 데이터 물리 정렬(클러스터드)과 2차 테이블 접근 소멸(커버링)을 통해 데이터베이스 디스크 I/O를 극소화

## Ⅱ. 특징

<details><summary>용어 설명</summary>

- **물리적 정렬 배치(Physical Data Ordering)**: 클러스터드 인덱스의 리프 노드가 곧 실제 데이터 페이지이므로 연속된 범위 검색(Range Scan) 시 순차 I/O를 활용.
- **Using Index(커버링 인덱스 지표)**: 쿼리 실행 계획(EXPLAIN)의 Extra 항목에 `Using index`가 표시되어 테이블 데이터 블록 접근이 완전히 생략되었음을 입증하는 속성.

</details>

- 데이터 페이지 자체가 기본키 순서로 물리 정렬되는 **테이블당 1개의 클러스터드 인덱스**
- 쿼리에 필요한 모든 컬럼을 인덱스 리프에 완비하여 **Key Lookup을 0화하는 커버링 인덱스**
- 대규모 범위 조회(Range Query) 및 초고빈도 단건 조회의 **극적인 디스크 I/O 절감** #### 한줄 요약

- 물리적 순차 I/O 활용과 2차 테이블 룩업 제거를 통해 대용량 조회 성능을 극대화

## Ⅲ. 구조 및 구성요소

<details><summary>용어 설명</summary>

- **Key Lookup(Bookmark Lookup)**: 비클러스터드 인덱스 탐색 후 인덱스에 없는 컬럼을 읽기 위해 PK나 ROWID로 실제 데이터 페이지를 찾아가는 2차 랜덤 I/O.

</details>

```text
[ 클러스터드 인덱스 및 커버링 인덱스 아키텍처 구조도 ]

 1. [ 클러스터드 인덱스 (Clustered Index) ]
    Root ──► Branch ──► Leaf Node (= 실제 테이블 데이터 행 자체 / 테이블당 1개)

 2. [ 커버링 인덱스 (Covering Index) ]
    질의: SELECT user_id, name, email FROM users WHERE age = 30;
    인덱스: Index(age, user_id, name, email)
    Leaf Node ──► [age=30, user_id=1, name='홍길동', email='hong@test.com']
                 (★ Key Lookup 없이 인덱스 리프에서 즉시 결과 반환!)
```

선의 의미: 클러스터드는 리프가 곧 데이터 레코드이며, 커버링은 인덱스 리프 내에 쿼리 요구 컬럼이 모두 존재하여 테이블 접근을 차단하는 구조.

| 구성요소 | 책임 |
|:---|:---|
| 클러스터드 인덱스 | 데이터 행을 키 순서대로 디스크에 저장하여 **연속 범위 검색(Range Scan) 성능 극대화** |
| 커버링 인덱스 | SELECT/WHERE/ORDER BY 컬럼을 인덱스에 포함하여 **2차 Table Access(Key Lookup) 완전 생략** |
| 포함 컬럼 (INCLUDE) | B+Tree 검색 키가 아닌 부가 컬럼을 **리프 노드에만 저장하여 인덱스 크기 최적화** |
| 실행 계획 (Using Index) | 옵티마이저가 테이블 접근 없이 **인덱스 단독으로 질의를 처리함을 증명하는 지표** |

#### 한줄 요약

- 클러스터드는 데이터 물리 정렬을, 커버링은 테이블 접근 제거를 전담하여 디스크 I/O를 최소화

## Ⅳ. 흐름도

<details><summary>용어 설명</summary>

- **커버링 인덱스 판정 파이프라인**: 쿼리 요청 컬럼 분석 $\to$ 인덱스 키/포함 컬럼 대조 $\to$ Key Lookup 생략 여부 결정 $\to$ 인덱스 리프 즉시 반환.

</details>

```text
[ 커버링 인덱스 쿼리 처리 파이프라인 ]

 ┌────────────────────────────────────────┐
 │ 1. SQL 질의 접수: SELECT/WHERE 절 분석 │
 └───────────────────┬────────────────────┘
                     │
                     ▼
 ┌────────────────────────────────────────┐
 │ 2. 인덱스 컬럼 포함 여부 대조          │
 └───────────────────┬────────────────────┘
                     │ (요청 컬럼이 인덱스에 100% 포함 시)
                     ▼
 ┌────────────────────────────────────────┐
 │ 3. 인덱스 레인지 스캔: 리프 노드 접근  │
 └───────────────────┬────────────────────┘
                     │
                     ▼
 ┌────────────────────────────────────────┐
 │ 4. Zero Key Lookup: 테이블 접근 생략   │
 └───────────────────┬────────────────────┘
                     │
                     ▼
 ┌────────────────────────────────────────┐
 │ 5. 인덱스 리프 데이터 즉시 반환        │
 └────────────────────────────────────────┘
```

### 동작 원리

1. SQL 질의 접수: SELECT, WHERE, ORDER BY에 포함된 모든 컬럼 집합을 식별.
2. 컬럼 포함 대조: 사용 가능한 인덱스에 요청된 모든 컬럼이 포함되어 있는지 검사.
3. 인덱스 레인지 스캔: 인덱스 트리를 타고 내려가 조건에 부합하는 리프 노드 블록을 스캔.
4. Zero Key Lookup: 추가적인 힙 테이블 블록이나 PK 클러스터 조회를 완전히 생략.
5. 즉시 반환: 인덱스 리프에 캐시된 컬럼 값들로 결과 셋을 구성하여 클라이언트에 즉시 응답.

#### 한줄 요약

- 질의 분석 $\to$ 인덱스 컬럼 대조 $\to$ 리프 스캔 $\to$ Key Lookup 생략 $\to$ 즉시 반환의 파이프라인

## Ⅴ. 종류 및 비교

<details><summary>용어 설명</summary>

- **Clustered vs Non-Clustered vs Covering**: 물리 저장 구조인 클러스터드/비클러스터드 인덱스와 쿼리 요구 컬럼을 모두 포함하는 상태적 최적화 기법인 커버링 인덱스.

</details>

| 구분 | Clustered Index (클러스터드) | Non-Clustered Index (보조형) | Covering Index (커버링 상태) |
|:---|:---|:---|:---|
| **적용 기준** | 범위 검색 및 순차 정렬 조회가 핵심인 PK | 특정 조건 검색 가속을 위한 보조 인덱스 | 초고빈도 핵심 조회 쿼리의 성능 극대화 |
| **핵심 특징** | **실제 디스크 데이터 행 자체가 키 순 정렬** | **인덱스 키와 데이터 행 포인터(PK/ROWID) 저장** | **쿼리 필요 컬럼이 100% 인덱스에 포함(Using index)** |
| **한계** | 테이블당 1개만 생성 가능, 무작위 삽입 시 Split | 인덱스 외 컬럼 조회 시 Key Lookup 오버헤드 | 컬럼 추가에 따른 인덱스 크기 및 DML 비용 증가 |

#### 한줄 요약

- 클러스터드는 테이블 자체의 물리 정렬, 보조 인덱스는 포인터 기반, 커버링은 테이블 조회를 생략하는 기법

## Ⅵ. 실무 고려사항 및 대책

<details><summary>용어 설명</summary>

- **페이지 분할(Page Split)**: 클러스터드 인덱스 키로 무작위 UUID 등을 사용할 때 중간에 데이터가 삽입되며 디스크 페이지가 쪼개져 성능이 저하되는 현상.

</details>

| 문제 | 대책 | 효과 |
|:---|:---|:---|
| Clustered PK에 무작위 UUID 사용 시 빈번한 Page Split 발생 | **순차 증가하는 Auto-Increment ID 또는 TSID(Time-Sorted) 채택** | 순차 삽입 보장 및 페이지 단편화 방지 |
| 커버링 인덱스를 위해 과도하게 많은 컬럼을 인덱스에 추가 | **INCLUDE 절(PostgreSQL/MSSQL) 활용 및 핵심 Top 5 쿼리 한정 적용** | 인덱스 크기 팽창 억제 및 DML 오버헤드 최소화 |
| 커버링 인덱스 의도했으나 실행 계획에서 Key Lookup 발생 | **`EXPLAIN` 실행 계획 상의 `Using index` 표기 여부 상시 모니터링** | 비효율적 테이블 2차 조회 조기 차단 |

#### 한줄 요약

- 순차 PK 설계, INCLUDE 컬럼 활용, 실행 계획 검증을 통해 커버링 인덱스의 효율을 극대화

## Ⅶ. 결론

<details><summary>용어 설명</summary>

- **I/O 병목 제거 전략(I/O Bottleneck Elimination)**: 디스크 접근 횟수를 줄이는 것이 데이터베이스 성능 튜닝의 핵심이며, 클러스터드와 커버링 인덱스가 최전선 해결책.

</details>

- **클러스터드 인덱스와 커버링 인덱스** 기반 데이터베이스 I/O 병목을 해결하는 가장 강력한 물리 아키텍처 기법이며, 순차적 PK 설계와 선별적 커버링 인덱스 구성을 통해 대규모 트래픽을 지연 없이 처리해야 함

#### 한줄 요약

- 클러스터드 물리 정렬과 커버링 룩업 제거를 통해 데이터베이스 I/O를 최소화하고 질의 성능을 극대화
