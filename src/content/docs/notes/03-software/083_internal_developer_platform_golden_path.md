## Ⅰ. 개요

<details><summary>용어 설명</summary>

- **골든 패스(Golden Path, Paved Road)**: 플랫폼 엔지니어링 팀이 사전 검증한 템플릿, CI/CD 파이프라인, 모니터링 가드레일을 결합하여 개발자가 가장 쉽고 빠르게 프로덕션에 배포할 수 있도록 지원하는 표준 경로.
- **인프라 구성 불일치 및 온보딩 지연(Drift & Onboarding Delay)**: 팀마다 서로 다른 도구와 파편화된 배포 스크립트를 작성하여 환경 불일치와 신규 개발자 온보딩 기간이 장기화되는 문제.

</details>

- 정의/개념: 내부 개발자 플랫폼(IDP)에서 검증된 모범 사례를 기반으로 **소프트웨어 템플릿, 자동화 파이프라인, 보안 가드레일** 제공하는 표준 배포 경로
- 배경/필요성: 팀별 파편화된 인프라 구축으로 인한 **환경 구성 불일치, 보안 취약점 방치 및 신규 서비스 온보딩 지연 위험** 직면

#### 한줄 요약

- 검증된 템플릿과 자동화 파이프라인을 통해 개발자가 가장 안전하고 신속하게 프로덕션에 배포할 수 있는 권장 경로

## Ⅱ. 특징

<details><summary>용어 설명</summary>

- **자발적 채택(Opt-in, Not Forced)**: 개발자에게 표준 사용을 강제하지 않고 압도적인 편의성과 생산성을 통해 자발적인 사용을 유도하는 원칙.
- **사전 검증된 가드레일(Pre-validated Guardrails)**: 보안 규정 준수, 리소스 한도, 로깅 설정이 템플릿에 기본 내장되어 별도의 승인 대기 없이 자동 통과되는 속성.

</details>

- 강제가 아닌 높은 개발자 경험(DX)을 통한 **자발적 채택(Opt-in) 유도**
- 보안, 규정 준수, 비용 최적화가 기본 탑재된 **사전 검증 가드레일 내장**
- 특수 요구사항을 수용할 수 있는 **안전한 우회 통로(Escape Hatch) 제공** #### 한줄 요약

- 자발적 채택, 사전 검증 가드레일, Escape Hatch를 결합하여 표준화와 개발 자율성의 균형을 달성

## Ⅲ. 구조 및 구성요소

<details><summary>용어 설명</summary>

- **소프트웨어 템플릿(Software Templates)**: Spring, Node.js, Go 등 기술 스택별 표준 아키텍처, Dockerfile, Helm Chart, CI/CD 스크립트가 사전 구성된 스타터 템플릿.

</details>

```text
[ 골든 패스(Golden Path) 4대 구성 구조도 ]

 ┌────────────────────────────────────────────────────────────────────────┐
 │                    Golden Path (황금 경로) 프레임워크                   │
 ├───────────────────┬───────────────────┬────────────────────────────────┤
 │ 1. 시작 템플릿    │ 2. 권장 워크플로  │ 3. 보안·비용 가드레일          │
 │   - 표준 코드 구조│   - 자동 CI/CD    │   - OPA 보안 정책 내장         │
 │   - Docker/Helm   │   - 텔레메트리    │   - FinOps 비용 한도           │
 ├───────────────────┴───────────────────┴────────────────────────────────┤
 │ 4. 탈출구 (Escape Hatch): 정당한 사유가 있는 특수 아키텍처 예외 승인 통로│
 └────────────────────────────────────────────────────────────────────────┘
```

선의 의미: 표준 템플릿, 파이프라인, 가드레일을 결합한 골든 패스와 예외 시 Escape Hatch로 우회하는 구조.

| 구성요소 | 책임 |
|:---|:---|
| 시작 템플릿 (Scaffolder) | 표준 디렉터리, 라이브러리, Dockerfile이 포함된 **스타터 레포지토리 자동 생성** |
| 권장 워크플로 (Pipeline) | 빌드, 정적 분석, 테스트, 카나리 배포, 모니터링을 **원클릭 자동 연계** |
| 보안 가드레일 (Policy) | 보안 취약점 점검 및 FinOps 비용 통제를 **코드로 자동 검증** |
| 탈출구 (Escape Hatch) | 골든 패스로 해결 불가능한 특수 워크로드에 대한 **인프라 직접 제어 예외 허용** |

#### 한줄 요약

- 시작 템플릿, 워크플로, 정책 가드레일로 표준을 제공하고 Escape Hatch로 유연성을 확보

## Ⅳ. 흐름도

<details><summary>용어 설명</summary>

- **TTFC(Time-to-First-Commit)**: 개발자가 신규 서비스를 기획하여 최초 프로덕션 배포 커밋까지 도달하는 데 소요되는 시간.

</details>

```text
[ 골든 패스 기반 신규 서비스 배포 파이프라인 ]

 ┌────────────────────────────────────────┐
 │ 1. 템플릿 선택: Backstage 포털 렌더링 │
 └───────────────────┬────────────────────┘
                     │
                     ▼
 ┌────────────────────────────────────────┐
 │ 2. 워크플로 연결: 저장소 및 CI/CD 구성 │
 └───────────────────┬────────────────────┘
                     │
                     ▼
 ┌────────────────────────────────────────┐
 │ 3. 정책 검증: 가드레일 기준 자동 심사  │
 └───────────────────┬────────────────────┘
                     │
                     ▼
 ┌────────────────────────────────────────┐
 │ 4. 환경 생성 및 배포: TTFC 5분 달성    │
 └────────────────────────────────────────┘
```

### 동작 원리

1. 템플릿 선택: 개발자가 포털에서 검증된 골든 패스 템플릿(Java 21 + Spring Boot 3)을 선택.
2. 워크플로 연결: Git 저장소 생성과 동시에 표준 CI/CD 파이프라인과 모니터링 대시보드가 자동 바인딩.
3. 정책 검증: 보안 및 비용 정책(OPA)이 코드와 설정을 자동 검사하여 승인 완료.
4. 환경 생성 및 배포: K8s 네임스페이스에 즉각 배포되어 5분 이내에 첫 배포(TTFC)를 완료.

#### 한줄 요약

- 템플릿 선택 $\to$ 워크플로 연결 $\to$ 정책 검증 $\to$ 자동 배포의 4단계로 개발 생산성을 극대화

## Ⅴ. 종류 및 비교

<details><summary>용어 설명</summary>

- **Golden Path vs Mandated Standard**: 자발적 채택을 유도하는 Golden Path와 강제 규정을 어길 시 빌드를 차단하는 엄격한 강제 표준.

</details>

| 구분 | Golden Path (황금 경로) | Mandated Strict Standard (엄격한 강제 표준) |
|:---|:---|:---|
| **적용 기준** | 자발적 생산성 향상 및 유연한 조직 문화 | 국방, 금융 등 초고위험 법적 규제 준수 시스템 |
| **핵심 특징** | **Opt-in 자발적 채택, Escape Hatch 예외 허용** | **무조건적 준수 강제(Enforced), 예외 불허** |
| **한계** | 템플릿 품질 저하 시 채택률 감소 위험 | 개발자 자율성 훼손 및 개발 병목/반발 초래 |

#### 한줄 요약

- 일반 엔터프라이즈 환경은 골든 패스를 적용하고, 극단적 규제 환경에서는 강제 표준을 적용

## Ⅵ. 실무 고려사항 및 대책

<details><summary>용어 설명</summary>

- **경로 정체(Path Stagnation)**: 골든 패스 템플릿이 최신 버전으로 관리되지 않고 방치되어 또 다른 레거시 기술 부채로 전락하는 안티패턴.

</details>

| 문제 | 대책 | 효과 |
|:---|:---|:---|
| 템플릿 업데이트 지연으로 기술 부채화 (Path Stagnation) | **플랫폼팀 전담 템플릿 유지보수 및 Dependabot 자동 의존성 갱신** | 최신 보안 패치 및 표준 기술 스택 유지 |
| 개발자들의 무분별한 Escape Hatch 남용으로 파편화 | **Escape Hatch 승인 심사 및 사용 사유 피드백을 템플릿 개선에 반영** | 전사 표준성 유지 및 골든 패스 지속 진화 |
| 골든 패스 가이드 문서 부실로 인한 학습 저항 | **Backstage TechDocs 기반 코드 인라인 기술 문서 자동 동기화** | 개발자 온보딩 시간 최소화 |

#### 한줄 요약

- 템플릿 자동 갱신, Escape Hatch 피드백 루프, 문서 자동화로 골든 패스의 생명력을 유지

## Ⅶ. 결론

<details><summary>용어 설명</summary>

- **플랫폼 진화 주기(Platform Evolution Cycle)**: 현업 개발자의 피드백을 수집하여 골든 패스에 새로운 모범 사례를 지속적으로 편입시키는 개선 순환 체계.

</details>

- **골든 패스** 기반 개발자의 자율성을 존중하면서도 조직의 표준성과 보안성을 확보하는 가장 진보된 인프라 전달 방식이며, 지속적인 피드백 루프를 통해 개발자가 가장 선호하는 경로로 유지 발전시켜야 함

#### 한줄 요약

- 자발적 채택 기반의 표준 경로를 제공하여 개발자 인지 부하를 줄이고 소프트웨어 전달 속도를 극대화
