## Ⅰ. 개요

<details><summary>용어 설명</summary>

- **폭포수 모델(Waterfall Model)**: 요구사항 ➔ 설계 ➔ 코딩 ➔ 테스트 순으로, 한 번 폭포에서 물이 떨어지면 절대 위로 거슬러 올라갈 수 없는 빡센 선형 순차적 개발 뼈대이다.
- **애자일 방법론(Agile Methodology)**: 일단 2~4주(Sprint) 단위로 작동하는 거(Working Software)부터 후딱 던져주고, 고객 피드백 받으면서 계속 뜯어고치는 실전 압축형 개발 철학이다.

</details>

- 정의: 기획 다 끝나야 설계하는 **폭포수(Waterfall)**와, 2주마다 일단 만들고 보면서 뜯어고치는 **애자일(Agile)**의 개발 패러다임 비교
- 배경: 초반 기획이 엉망인데 폭포수로 쭉 밀고 나가면, 나중에 테스트할 때 아키텍처부터 뜯어고치는 **재작업(Rework) 폭탄**이 터지기 때문

#### 한줄 요약

- 돌이킬 수 없는 결재 도장 중심의 폭포수와, 2주마다 뜯어고치며 생존하는 애자일의 대결이다.

## Ⅱ. 특징

<details><summary>용어 설명</summary>

- **제품 증분(Product Increment)**: 애자일에서 2주(Sprint)마다 찍어내는, 당장 고객한테 팔아먹거나 테스트할 수 있는 작동 가능한 기능 덩어리이다.
- **범위 확장(Scope Creep)**: 폭포수에서 기획 다 확정하고 코딩 중인데, 기획자나 고객이 "이거 하나만 더 넣어줘" 하다가 일정/비용이 감당 못 할 만큼 터져버리는 멘붕 사태이다.

</details>

- 초기 **기획 고정(Requirements Freeze)**과 단계별 **결재 도장(Stage Gate)**으로 통제하는 게 **폭포수**의 낭만임.
- 일단 **제품 증분(Increment)**부터 던지고, **백로그(Backlog)** 우선순위 바꿔가며 기획 엎는 게 **애자일**의 생존 방식임.
- **애자일**은 일정/돈을 고정하고 범위를 깎아내고, **폭포수**는 범위를 고정하고 일정/돈을 억지로 때려 맞춤.

#### 한줄 요약

- 폭포수는 기획을 픽스하고, 애자일은 기획을 2주마다 엎으면서 완제품(증분)을 뱉어낸다.

## Ⅲ. 구조 및 구성요소

<details><summary>용어 설명</summary>

- **제품 백로그(Product Backlog)**: 애자일에서 만들고 싶은 기능, 고칠 버그들을 중요도 순으로 쭉 나열해 둔 영수증(요구사항 대기열)이다.

</details>

```text
[ 개발 패러다임 십자포화 아키텍처 ]

[ 폭포수 (Waterfall) ]         [ 애자일 (Agile) ]

(기획 고정) ──▶ 설계          [ 제품 백로그 (요구사항) ]
               │                     │
               ▼                     ▼ (2주 단위 Sprint)
              구현               [ 제품 증분 (릴리즈) ]
               │                     │
               ▼                     ▼ (고객 피드백)
(돌이킬 수 없음) 테스트          [ 백로그 재정렬 및 수정 ]
```

| 구성요소 | 책임 |
|:---|:---|
| **요구 기준선 (폭포수)** | "이거 다 못 만들면 집에 못 가"라고 박아둔 절대 불변의 개발 범위 |
| 단계 승인 (폭포수) | 기획서 다 썼는지 검사하고 윗선에서 결재 도장 찍어줘야 다음으로 넘어가는 톨게이트 |
| **제품 백로그 (애자일)** | "언젠간 만들어야지" 하고 모아둔 요구사항 목록으로, 급한 놈부터 수시로 순위를 바꿈 |
| **제품 증분 (애자일)** | 2주마다 찍어내는 "지금 당장 돌아가는" 미니 완제품으로, 피드백을 빨아들이는 스펀지 |

#### 한줄 요약

- 폭포수는 결재 도장과 기준선으로 버티고, 애자일은 백로그와 2주짜리 완제품(증분)으로 승부 본다.

## Ⅳ. 흐름도

<details><summary>용어 설명</summary>

- **재작업 캐스케이드(Rework Cascade)**: 폭포수 막판(테스트 단계)에서 초기 기획 빵꾸를 발견해서, 코딩 ➔ 설계 ➔ 기획까지 도미노처럼 다 뜯어고쳐야 하는 재앙이다.

</details>

```text
[ 방법론 별 생명주기 십자포화 흐름 ]

폭포수 흐름
┌──────────────────────────────┐
│ 1. 요구 기준선(Freeze) 박기  │
└──────────────┬───────────────┘
               ▼ (순차 단계 수행)
┌──────────────────────────────┐
│ 2. 설계 ➔ 구현 ➔ 테스트    │
│ (빠꾸 없이 직진)             │
└──────────────┬───────────────┘
               ▼ (기획 빵꾸나면 좆됨)
┌──────────────────────────────┐
│ 3. 최종 통합 릴리스 (빅뱅)   │
└──────────────────────────────┘

애자일 흐름
┌──────────────────────────────┐
│ 1. 스프린트(2주) 백로그 할당 │
└──────────────┬───────────────┘
               ▼ (초고속 개발)
┌──────────────────────────────┐
│ 2. 제품 증분(Increment) 시연 │
│ (작동하는 기능 바로 던짐)    │
└──────────────┬───────────────┘
               ▼ (욕 먹고 피드백 반영)
┌──────────────────────────────┐
│ 3. 백로그 엎고 재정렬        │
└──────────────────────────────┘
```

### 동작 원리

1. 폭포수 직진: 요구사항 픽스하고, 설계-구현-테스트를 윗선 결재받으며 무지성 직진함.
2. 폭포수 빅뱅 릴리스: 다 끝나면 한 방에 라이브 서버에 올리고 에러 터지면 밤샘.
3. 애자일 증분 개발: 2주치 백로그만 딱 잘라서 미친 듯이 코딩하고 **증분(완성본)**을 뱉어냄.
4. 애자일 피드백 루프: 뱉은 거 시연해서 고객한테 욕 처먹고, 다음 2주 차 백로그 순위를 갈아엎음.

#### 한줄 요약

- 폭포수는 무지성 직진 후 한방 릴리스고, 애자일은 2주마다 릴리스하며 피드백을 빨아먹는다.

## Ⅴ. 종류 및 비교

<details><summary>용어 설명</summary>

- **하이브리드 모델(Hybrid Model)**: 돈 주는 계약서랑 큰 뼈대(아키텍처)는 폭포수로 묶어두고, 안에서 코딩하고 테스트하는 건 애자일(스프린트)로 돌리는 혼종 타협안이다.

</details>

| 비교 항목 | **Waterfall Model** (전통 폭포수) | **Agile / Scrum** (현대 애자일) | **Hybrid Model** (혼종) |
|:---|:---|:---|:---|
| 변화 대응력 | 기획 바꾸면 위약금 물어야 됨 (유연성 0) | 2주마다 기획 엎어도 "오케이 콜" | 큰 틀은 픽스, 세부 기능만 변경 |
| 배포 타이밍 | 1년 내내 개발하고 마지막 날 한 방에 터트림 | 2~4주마다 계속 돌아가는 앱 던짐 | 일정 주기로 마일스톤 배포 |
| 찰떡 무대 | 차세대 금융망, 국방 (단 1원도 틀리면 안 됨) | B2C 모바일 앱, SaaS 스타트업 | 대기업 엔터프라이즈 시스템 개편 |

#### 한줄 요약

- 1원도 틀리면 안 되는 금융권은 폭포수, 트렌드가 생명인 스타트업은 애자일이다.

## Ⅵ. 실무 고려사항 및 대책

<details><summary>용어 설명</summary>

- **완료 정의(Definition of Done, DoD)**: 애자일에서 "이거 다 짰어요"라고 사기 치는 걸 막기 위해, "코드 리뷰, 단위 테스트 80%, QA 통과" 조건을 다 채워야만 끝난 걸로 쳐주는 팩트체크 기준이다.

</details>

| 문제 | 대책 | 효과 |
|:---|:---|:---|
| 폭포수 막판에 테스트했더니 설계 뜯어고치는 재앙 터짐 | **V-Model** 섞고, 초반에 **프로토타입** 던져서 핑프 방지 | 폭망 리스크를 초반으로 땡겨서 기획 엎는 비용 최소화 |
| 애자일 한다고 문서 없이 대충 짰다가 기술 부채 폭발함 | "테스트 안 짜면 완료 아님" **완료 정의(DoD)** 세움 | 스프린트 배포 안정성 확보하고 스파게티 코드 방어 |
| SI 업체랑 1억 고정 계약했는데 기획 엎어서 멱살 잡음 | 애자일에 맞게 기능 단위 **유연 범위 계약**으로 바꿈 | "돈 준 만큼만 짠다"로 깔끔하게 떨어져 멱살잡이 차단 |

#### 한줄 요약

- 폭포수는 프로토타입으로 보험 들고, 애자일은 DoD(완료 정의)로 기술 부채를 틀어막아라.

## Ⅶ. 결론

<details><summary>용어 설명</summary>

- **방법론 선택 기준(Methodology Selection Criteria)**: 기획서가 안 바뀔 확률(불확실성), 규제 빡센 정도, 타임 투 마켓(빨리 안 내면 망하는가)을 각 재서 폭포수/애자일을 가르는 잣대이다.

</details>

- **방법론 선택 기준** 원칙에 따라, 1원이라도 틀리면 쇠고랑 차는 규제 인프라는 **폭포수**, 트렌드가 하루가 다르게 바뀌는 B2C 앱은 **애자일** 채택 기조 확립함

#### 한줄 요약

- 규제 덩어리 인프라는 폭포수, 고객 변덕이 죽 끓듯 하는 서비스는 애자일을 택해라.
