## Ⅰ. 개요

<details><summary>용어 설명</summary>

- **카나리 배포(Canary Deployment)**: 광산의 카나리아 새처럼, 신규 버전을 전체의 1~5% 소수 트래픽에만 먼저 노출하여 실환경 반응을 검증한 후 점진 확대하는 배포 기법.
- **블루-그린 배포(Blue-Green Deployment)**: 기존 운영 환경(Blue)과 동일한 신규 환경(Green)을 병렬 구축해두고 로드밸런서 라우팅을 한 번에 스위칭하는 무중단 배포 기법.

</details>

- 정의/개념: **점진 노출(Canary)** 또는 **이중 환경 전환(Blue-Green)** 전략
- 배경/필요성: 인플레이스 덮어쓰기는 교체 순간 서비스가 끊기고 되돌릴 원본도 남지 않으므로, 구버전 환경을 살려 둔 채 트래픽만 옮기는 블루그린·카나리 계층을 배포 앞단에 두어 롤백을 재배포가 아닌 트래픽 전환으로 바꿀 필요

#### 한줄 요약
- 카나리는 장애 범위를 제한하고 블루-그린은 환경 전환 롤백을 지원한다.

## Ⅱ. 특징

<details><summary>용어 설명</summary>

- **Blast Radius(장애 파급 반경)**: 배포 실패 시 장애의 영향을 받게 되는 사용자 또는 시스템의 물리적/논리적 범위.
- **Router Switching**: DNS 또는 L7 인그레스(Ingress) 라우팅 테이블 변경을 통해 트래픽 대상을 1초 미만으로 전환하는 기법.

</details>

- 카나리: **장애 파급 반경**을 초기 트래픽 비율로 제한
- 블루-그린: 구버전(Blue)과 신버전(Green) 병렬 운용 후 **라우터 스위칭을 통한 즉시 전환**
- 결함 감지 시 라우팅 규칙 원복으로 **빠른 롤백** 지원

#### 한줄 요약
- 카나리는 점진 노출로 위험을 최소화하고, 블루-그린은 병렬 환경으로 즉각 전환/롤백을 지원한다.

## Ⅲ. 구조 및 구성요소

<details><summary>용어 설명</summary>

- **Argo Rollouts**: Kubernetes 환경에서 NGINX/Envoy와 연계하여 가중치 기반 트래픽 분할(Canary)과 메트릭 분석을 수행하는 컨트롤러.

</details>

```text
[배포 제어 체계]
|-- L7 트래픽 라우터
|-- Blue 환경
|-- Canary 환경
|-- Green 환경
`-- 공통 데이터 계층
```

선의 의미: 가지는 배포 제어 체계의 구성 관계

| 구성요소 | 책임 |
|:---|:---|
| L7 트래픽 라우터 | **가중치 분할·엔드포인트 전환** 수행 |
| Blue 환경 | 기존 안정 버전 서비스와 롤백 대기 |
| Canary 환경 | 제한된 트래픽으로 **신버전 지표** 수집 |
| Green 환경 | 전환 전 신버전 검증과 대체 서비스 |
| 공통 데이터 계층 | 세션 외장화와 호환 DB 스키마 제공 |

#### 한줄 요약
- 라우터가 트래픽 비율을 쥐고 있기 때문에 롤백이 재배포가 아닌 가중치 변경이 되며, 관측 시스템이 그 가중치를 바꿀 근거를 공급한다.

## Ⅳ. 흐름도

<details><summary>용어 설명</summary>

- **ACA(Automated Canary Analysis)**: 프로메테우스 메트릭을 분석하여 카나리 Pod의 에러율이 기준치 이하일 때만 다음 가중치로 자동 승격시키는 엔진.

</details>

```text
[카나리 배포 워크플로우]
신버전 컨테이너 기동과 초기 트래픽 할당
        │
   관찰 구간의 에러율과 지연시간 분석
        │
   서비스별 SLO 가드레일을 만족하는가?
   ┌────┴─────┐
  예           아니오 (에러율 급증)
   │             │
가중치 점진 확대         카나리 트래픽 차단과 기존 버전 유지
배포 완료 후 구버전 종료

[블루-그린 배포 워크플로우]
Blue(v1.0 운영 중) 상태에서 독립된 Green(v2.0) 인프라 구축 -> 내부 스모크 테스트 수행
        │
   L7 라우터의 서비스 대상을 Green으로 전환
        │
   이상 감지 시 Blue로 복원, 정상 시 Blue 자원 회수
```

#### 한줄 요약
- 카나리는 소수 사용자를 노출시켜 자원을 아끼고 블루-그린은 자원을 두 배로 써서 노출을 없애므로, 무엇을 대가로 낼지가 두 경로의 유일한 차이다.

## Ⅴ. 종류 및 비교

<details><summary>용어 설명</summary>

- **Rolling vs Blue-Green vs Canary**: 순차 교체(Rolling), 이중 환경 일괄 스위칭(Blue-Green), 점진 가중치 노출(Canary) 3대 무중단 배포 비교.

</details>

| 비교 항목 | 롤링 배포 (Rolling Update) | 블루-그린 배포 (Blue-Green) | 카나리 배포 (Canary) |
|:---|:---|:---|:---|
| 구현 난이도 | **가장 단순 (K8s 기본 지원)** | 중간 (이중 인프라 필요) | 높음 (L7 트래픽 제어 및 ACA 필요) |
| 추가 인프라 비용 | 없음 (최소 오버헤드) | **2배 인프라 비용 발생** | 소폭 추가 (카나리 인스턴스) |
| 장애 파급 반경 | 전체 사용자에 점진 노출 | 전체 사용자에 일괄 노출 | **1~5% 소수 사용자에게만 국소화** |
| 롤백 방식 | 역순 롤링 | **Blue로 라우팅 복원** | **카나리 가중치 회수** |

#### 한줄 요약
- 비용 최소화는 롤링, 빠른 스위칭은 블루-그린, 리스크 극소화는 카나리를 선택한다.

## Ⅵ. 실무 고려사항 및 대책

<details><summary>용어 설명</summary>

- **Expand-Contract 패턴**: 배포 중 신/구버전이 DB를 동시 조회할 때 발생하는 스키마 불일치를 해결하기 위해 컬럼 추가 $\to$ 배포 $\to$ 구컬럼 삭제로 진행하는 기법.

</details>

| 문제 | 대책 | 효과 |
|:---|:---|:---|
| 신·구버전의 DB 스키마 불일치 | **Expand-Contract 마이그레이션** | 전환 중 스키마 호환성 유지 |
| 블루-그린 배포 시 2배 인프라 비용 발생 | 전환 완료 즉시 **구버전(Blue) 인스턴스 자동 정지(Scale-in)** | 클라우드 인프라 비용 낭비 차단 |
| 인스턴스 간 세션 불일치 | 세션을 **외부 저장소**로 분리 | 버전 전환 중 세션 연속성 지원 |
| 카나리 분석 지표의 모호성 | **Prometheus + Argo Rollouts AnalysisTemplate** 지표 정량화 | 무인 자동 승격 및 자동 롤백 실현 |

#### 한줄 요약
- 블루그린은 자원을 두 배로 써 즉시 롤백을 사고 카나리는 일부 사용자 노출을 대가로 자원을 아끼므로, 롤백 속도와 인프라 비용 중 무엇이 더 비싼지로 방식을 고른다.

## Ⅶ. 결론

- 충격 최소화는 **카나리 배포**, 즉각 롤백은 **블루-그린** 선택

#### 한줄 요약
- 점진 위험 검증은 카나리, 환경 단위 복원은 블루-그린을 적용한다.
