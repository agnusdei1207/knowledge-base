## Ⅰ. 개요

<details><summary>용어 설명</summary>

- **데브섹옵스(DevSecOps)**: 배포 직전에 보안팀이 "이거 취약점 있어서 배포 못 함" 하고 엎어버리는 꼴을 막기 위해, 코딩 단계부터 파이프라인 전체에 보안 검사를 떡칠해 놓는 생존 전략이다.
- **시프트 레프트(Shift-Left Security)**: 출시(오른쪽) 다 돼서 보안 검사하지 말고, 코딩/빌드하는 맨 처음(왼쪽)으로 검사를 앞당겨서 개발자가 똥 싸자마자 치우게 만드는 기술이다.
- **정책 코드화(Policy as Code, PaC)**: 문서에 적힌 꼰대식 보안 규정을 코드로 바꿔서, 파이프라인 돌 때 로봇이 알아서 "너 규정 위반! 빌드 폭파!" 하도록 자동화하는 것이다.

</details>

- 정의: DevOps 파이프라인 전 과정(Plan ~ Deploy)에 보안(Security)을 겉절이가 아닌 핵심으로 내재화(Shift-Left)하는 아키텍처 방법론인 **DevSecOps**
- 배경: 릴리스 전날 밤 보안 검사에서 다 털리고 **코드 갈아엎느라 배포 지연되는 끔찍한 병목 현상**을 막기 위함

#### 한줄 요약

- 배포 직전에 보안 검사받고 멘탈 터지지 말고, 코드 짤 때부터 봇이 자동으로 검사하게 하자는 거다.

## Ⅱ. 특징

<details><summary>용어 설명</summary>

- **자동 보안 게이트(Automated Security Gate)**: CI/CD 돌아갈 때 보안 도구가 코드 까보고 치명적 취약점 하나라도 나오면, 사람이 사정해도 얄짤없이 빌드를 파기시키는 무자비한 차단벽이다.
- **보안 공동 책임(Shared Responsibility)**: "보안은 보안팀이 알아서 하겠지"라는 마인드를 박살 내고, 기획자, 개발자, 엔지니어 모두가 내 코드 보안은 내가 챙긴다는 마인드이다.

</details>

- 보안 검사 시기를 맨 앞으로 땡기는 **Shift-Left Security**.
- 보안 규정을 코드로 짜고 로봇이 검사하는 **Policy as Code (PaC)** 및 **Automated Security Gate** 구현.
- 개발-보안-운영 3개 조직이 멱살 안 잡고 같이 짐을 지는 **Shared Security Responsibility (보안 공동 책임)** 문화.

#### 한줄 요약

- 검사를 앞으로 땡기고(시프트 레프트), 룰을 코드로 짜며(PaC), 다 같이 책임지는 게 핵심이다.

## Ⅲ. 구조 및 구성요소

<details><summary>용어 설명</summary>

- **SAST / DAST / SCA**: SAST는 서버 띄우기 전에 코드 텍스트만 스캔하는 정적 분석, DAST는 서버 띄워놓고 모의 해킹 때리는 동적 분석, SCA는 인터넷에서 긁어온 오픈소스 구멍 잡는 툴이다.

</details>

```text
[ DevSecOps 십자포화 파이프라인 ]

[ 1. IDE (개발자) ] ──(비밀번호 평문 금지)──▶ [ 2. Git (Pre-commit) ]
                                                     │
                                                     ▼
 [ 4. 보안 게이트 (통과 못하면 폭파) ] ◀── [ 3. CI 빌드 (SAST / SCA) ]
               │
               ▼ (ArgoCD 배포)
 [ 5. DAST (모의 해킹) ] ──▶ [ 6. 운영 모니터링 (CCTV) ]
```

| 구성요소 | 팩트 폭행 책임 |
|:---|:---|
| **위협 모델링 (Plan)** | 코딩 전부터 "여기 털리면 끝장이다"라고 방어선 미리 그리는 기획 |
| **정적 분석 (SAST/SCA)** | 깃허브에 코드 올리자마자 소스 까보고 라이브러리 구멍 난 곳 잡는 스캐너 |
| **보안 게이트 (Gate)** | 취약점 등급이 'High' 이상이면 냅다 빌드 터트리고 개발자 반성하게 만듦 |
| **동적 분석 (DAST)** | 테스트 서버 띄운 다음 무식하게 해킹 공격 때려 넣어서 뚫리는지 실전 테스트 |
| **보안 관측 (Monitor)** | 실운영 서버 띄우고 나서도 해커가 찌르는지 24시간 감시하는 CCTV |

#### 한줄 요약

- 코딩 전 $\to$ 커밋 직후 $\to$ 배포 전 $\to$ 배포 후 모든 단계에 보안 검문소가 깔려있는 거다.

## Ⅳ. 흐름도

<details><summary>용어 설명</summary>

- **컨테이너 이미지 스캔(Container Image Scanning)**: 도커(Docker) 이미지 구울 때, Base OS나 패키지에 숨어있는 취약점(CVE)을 Trivy 같은 툴로 배포 직전에 탈탈 터는 검사이다.

</details>

```text
[ Shift-Left 보안 검사 십자포화 흐름 ]
┌──────────────────────────────┐
│ 1. Git Commit (Pre-commit)   │
│ (AWS 비번 평문 커밋 차단!)   │
└──────────────┬───────────────┘
               ▼
┌──────────────────────────────┐
│ 2. CI 빌드 및 정적 분석      │
│ (SAST로 XSS, SQLi 잡기)      │
└──────────────┬───────────────┘
               ▼
┌──────────────────────────────┐
│ 3. 도커 굽고 이미지 스캔     │
│ (Trivy로 OS 취약점 털기)     │
└──────────────┬───────────────┘
               ▼
┌──────────────────────────────┐
│ 4. 보안 게이트 최종 판정     │
│ (Critical 뜨면 빌드 폭파!)   │
└──────────────┬───────────────┘
               ▼
┌──────────────────────────────┐
│ 5. 운영 서버 배포 완결       │
│ (무사 통과된 청정 코드만 슛) │
└──────────────────────────────┘
```

### 동작 원리

1. 비밀정보 검사: 로컬에서 커밋 칠 때 AWS API Key 들어있으면 바로 커밋 빠꾸 먹임.
2. 정적/구성요소 분석: CI 봇이 코드 문법이랑 긁어온 오픈소스 취약점 스캔함.
3. 이미지 검사: 도커 컨테이너 구운 다음에 리눅스 패키지 털리는 거 없는지 검사함.
4. 보안 게이트: 스캔 리포트 종합해서 룰(PaC)에 어긋나면 빌드 멱살 잡고 터트림.
5. 검증 배포: 보안 청정 구역 판정받은 도커 이미지만 실서버로 꽂아 넣음.

#### 한줄 요약

- 깃에 올릴 때 잡고, 빌드할 때 잡고, 도커 구울 때 또 잡는 3중 거름망이다.

## Ⅴ. 종류 및 비교

<details><summary>용어 설명</summary>

- **전통적 보안 vs 데브섹옵스(Traditional Security vs DevSecOps)**: 배포 전날 보안팀이 점검하고 다 엎으라고 하는 게 전통적 방식, 코딩할 때마다 봇이 자동으로 검사해 주는 게 데브섹옵스이다.

</details>

| 비교 항목 | **Traditional Security (사후 점검)** | **DevSecOps (지속적 내재화)** |
|:---|:---|:---|
| 검사 시점 | 개발 다 끝나고 배포 전날 밤 수동 모의 해킹 | **개발자 PC에서 타자 치는 순간부터 무한 스캔** |
| 검사 속도 | 보안팀 휴가 가면 배포 한 달 밀림 | **봇이 3분 만에 자동 스캔하고 빌드 컷냄** |
| 담당 주체 | 전담 보안팀(경찰) vs 개발팀(도둑) 구도 | **개발자+보안팀+운영팀의 훈훈한 공동 책임** |
| 피드백 환류| "코드 싹 다 다시 짜오세요" (퇴사각) | **커밋 단위로 즉시 수정 가능해서 타격 제로** |

#### 한줄 요약

- 몰아서 검사받고 욕먹을래, 찔끔찔끔 검사받고 편하게 배포할래의 차이다.

## Ⅵ. 실무 고려사항 및 대책

<details><summary>용어 설명</summary>

- **보안 챔피언(Security Champion)**: 개발팀 안에서 보안 마인드가 좀 있는 에이스를 뽑아서, 꼰대 보안팀 대신 개발팀 내부에서 자체적으로 보안 문화를 전파하게 만드는 전도사이다.

</details>

| 문제 | 대책 | 효과 |
|:---|:---|:---|
| 보안 툴 오탐(False Positive) 때문에 멀쩡한 빌드 터짐 | 룰셋 튜닝하고 억울한 건 **예외 처리(Exclusion)** 허용 | 파이프라인 막히는 스트레스 줄이고 생산성 떡상 |
| 보안 스캔하느라 CI 도는 데 1시간 걸림 | 바뀐 코드만 터는 **증분 검사**랑 야간 딥스캔 분리 | 빠른 피드백 유지하면서 꼼꼼하게 검증함 |
| 개발자들이 꼼수 부려서 파이프라인 우회하려 함 | 팀 내 **Security Champion** 육성 & IDE 플러그인 | 잔소리 없이 자연스럽게 보안 문화 스며듦 |

#### 한줄 요약

- 억울한 오탐은 풀어주고, 검사는 가볍게 쪼개고, 개발팀 안에 쁘락치(보안 챔피언)를 심어라.

## Ⅶ. 결론

<details><summary>용어 설명</summary>

- **데브섹옵스 성숙도 평가(DevSecOps Maturity)**: 툴 몇 개 깔았다고 끝이 아니라, 위협 모델링부터 런타임 방어까지 얼마나 촘촘하게 보안이 파이프라인에 녹아들었는지 팩트 체크하는 잣대이다.

</details>

- **DevSecOps 도입 기준** 원칙에 따라, 코드 결함은 맨 왼쪽으로 땡겨서 **Shift-Left(SAST)**로 막고, 운영 중인 공격은 **런타임 관측(DAST)**으로 막는 양동 작전 기조 확립함

#### 한줄 요약

- 보안은 나중에 붙이는 반창고가 아니라, 처음부터 건물 지을 때 넣는 철근이다.
