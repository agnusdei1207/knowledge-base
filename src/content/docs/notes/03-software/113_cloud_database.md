## 미리 알고가기

- **관리형 데이터베이스(Managed Database)**: 프로비저닝·패치·백업·장애 조치 등의 운영 기능을 공급자가 수행하는 서비스임
- **아마존 웹 서비스(Amazon Web Services, AWS)**: RDS·Aurora·DynamoDB를 제공하는 클라우드 서비스 공급자임
- **아마존 관계형 데이터베이스 서비스(Amazon Relational Database Service, Amazon RDS)**: 여러 관계형 엔진의 배포·백업·패치·장애 조치를 관리하는 서비스임
- **아마존 오로라(Amazon Aurora)**: MySQL·PostgreSQL 호환 엔진과 여러 가용 영역에 걸친 클러스터 볼륨을 사용하는 관계형 데이터베이스임
- **아마존 다이나모DB(Amazon DynamoDB)**: 파티션 키와 선택적 정렬 키로 항목을 분산하는 관리형 키값·문서 데이터베이스임
- **가용 영역(Availability Zone, AZ)**: 한 리전 안에서 다른 영역의 장애와 격리되도록 설계된 인프라 위치임
- **다중 가용 영역(Multi-AZ)**: 여러 가용 영역의 인스턴스나 저장 사본을 이용해 장애 조치를 지원하는 배포 구성임
- **읽기 복제본(Read Replica)**: 원본의 변경을 복제해 읽기 요청을 분산하는 사본임
- **프로비저닝(Provisioning)**: 필요한 인스턴스·저장소·네트워크 자원을 준비하고 설정하는 작업임
- **접속 엔드포인트(Connection Endpoint)**: 응용 프로그램이 데이터베이스에 연결할 때 사용하는 네트워크 주소임
- **복구 시점 목표(Recovery Point Objective, RPO)**: 장애 시 허용할 수 있는 최대 데이터 손실 시간 범위임
- **복구 시간 목표(Recovery Time Objective, RTO)**: 장애 뒤 서비스를 복구해야 하는 목표 시간임

## Ⅰ. 개요

- **정의/개념**: 공급자가 공통 데이터베이스 운영을 관리함
- **배경/필요성**: 반복 운영 작업으로 관리형 데이터베이스 필요

### 쉽게 이해하기 (학습용)
- 설치와 백업 및 장애 조치를 클라우드가 맡고 사용자는 용량을 선택함

## Ⅱ. 특징

- 공급자가 제어 계층을 운영해도 정책은 사용자가 정한다.
- 서비스마다 인스턴스·저장소·파티션 확장 단위가 다르다.
- 복제본으로 읽기를 확장하고 장애 시 가용성을 높인다.
- 관리형도 지연·장애 조치·용량 비용을 검증해야 한다.

### 쉽게 이해하기 (학습용)
- 운영 작업은 줄지만 서비스별 확장 단위·비용·종속성이 다름

## Ⅲ. 아키텍처 및 구성요소

| 구성요소 | 설명 |
|:---|:---|
| 관리 제어 계층 | 패치와 백업 및 장애 조치를 API로 수행함 |
| 접속 엔드포인트 | 인스턴스와 클러스터 및 리전 API로 요청을 수신함 |
| 질의·키 처리 계층 | SQL 실행 계획이나 파티션 키로 처리 대상을 결정함 |
| 컴퓨팅·파티션 계층 | 인스턴스와 파티션이 데이터 연산을 수행함 |
| 저장·복제 계층 | 스토리지와 클러스터 볼륨 및 파티션이 데이터를 보존함 |

```text
  제어접속
      ↓
  질의해석
      ↓
  계산처리
      ↓
  저장복제
```

> 요약: 제어 계층·서비스 구조로 운영 결정

### 쉽게 이해하기 (학습용)
- 관리형이라는 공통점은 같아도 관계형 질의는 인스턴스·클러스터로, 키 기반 요청은 파티션으로 처리됨

## Ⅳ. 원리 및 절차 흐름도

```text
  요구식별
      ↓
  모델선택
      ↓
  복구비용
      ↓
  실측검증
```

| 절차 | 설명 |
|:---|:---|
| **요구 식별** | 조인과 트랜잭션 및 부하 분포를 식별함 |
| **모델 선택** | 데이터 모델과 확장 우선순위를 정함 |
| **복구 비용** | RPO 및 RTO 요구와 과금 모델을 매핑함 |
| **실측 검증** | 커밋 지연과 장애 조치 및 비용으로 검증함 |

> 요약: 모델과 확장 및 복구 목표를 서비스 구조에 매핑해 선택함

### 쉽게 이해하기 (학습용)
- 데이터 모델·질의·거래·확장 단위와 RPO·RTO·비용을 비교해 적합한 서비스를 결정함

## Ⅴ. 종류 및 비교

| 비교축 | RDS | Aurora | DynamoDB |
|:---|:---|:---|:---|
| 핵심 특징 | 선택한 엔진의 관계형을 사용함 | 호환 관계형과 SQL을 사용함 | 키와 값 및 문서형 항목을 사용함 |
| 확장 방식 | 인스턴스와 스토리지 복제본을 확장함 | 공유 클러스터 볼륨을 자동 확장함 | 자동 파티션 관리로 처리량을 확장함 |
| 적용 기준 | 기존 관계형 엔진 호환성이 중요함 | 호환 관계형과 클러스터 저장 구조가 필요함 | 대규모 키 기반 읽기·쓰기 확장이 필요함 |
| 주요 위험 | 엔진 제약·운영 종속 | 비용 변동·호환 차이 | 핫 파티션·질의 제약 |

> 요약: 관계형과 키 기반 분산 모델 비교

### 쉽게 이해하기 (학습용)
- RDS는 일반 관계형 엔진 관리에, Aurora는 호환 관계형 클러스터에, DynamoDB는 키 중심 수평 확장에 맞음

## Ⅵ. 실무 사례

1. 주문 DB는 관리형 구성·지연·장애 조치를 확인함
2. 세션 API는 파티션 키를 분산하고 최대 요청 점유율을 확인함

### 쉽게 이해하기 (학습용)
- 주문 데이터베이스는 관계형 거래를 유지하면서 커밋 지연과 실제 장애 조치 시간이 RTO를 만족하는지 검증함
- 세션 API는 DynamoDB 파티션 키의 요청 점유율을 측정해 특정 키에 부하가 몰리는 핫 파티션을 찾음

## Ⅶ. 결론

- 모델·거래·확장·복구·비용에 맞춰 서비스 선택

### 쉽게 이해하기 (학습용)
- 관리형 서비스도 스키마·키·용량·복구 목표·비용은 사용자가 설계하고 장애 훈련과 지표로 검증해야 함
