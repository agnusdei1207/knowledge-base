## Ⅰ. 개요

<details><summary>핵심 용어</summary>

- **SCI (Software Carbon Intensity, 소프트웨어 탄소 집약도)**: 소프트웨어 실행으로 인해 발생하는 운영 탄소(O)와 하드웨어 생산에서 비롯된 내재 탄소(M)의 합계를, 해당 소프트웨어가 처리한 유용한 기능 단위(R)로 나눈 탄소 효율 지표.
- **Green Software Foundation (그린 소프트웨어 재단)**: SCI 스펙을 정의하고 ISO 표준(ISO 21031) 제정을 추도한 단체로, 마이크로소프트, 구글, 어도비 등이 참여하는 소프트웨어 탄소 중립화 주도 산업 연합.
- **Green Software Engineering (그린 소프트웨어 엔지니어링)**: 소프트웨어를 개발하고 운영하는 전 과정에서 탄소 배출을 최소화하도록 설계·코딩·운영하는 엔지니어링 원칙과 실천 방법론.

</details>

- 정의/개념: 소프트웨어가 기능 단위(트랜잭션, API 호출 등)를 처리할 때 발생시키는 탄소량을 정량화하여, 버전 간·아키텍처 간 탄소 효율을 비교하고 감축 여부를 판단하는 **소프트웨어 탄소 집약도(SCI) 지표**
- 배경/필요성: 단순 총 탄소 배출량 비교는 사용자 수 증가나 워크로드 변화로 인한 증가분과 실제 비효율 코드의 배출량을 구분할 수 없어, 코드 수준의 탄소 개선 효과를 정확히 측정할 표준 지표 요구성

#### 한줄 요약

- 같은 배송 건수마다 트럭 연료와 차량 제조분을 나누듯, 같은 기능 작업량마다 운영·내재 배출량을 계산한다.

## Ⅱ. 특징 (SCI 공식의 4대 구성 변수)

<details><summary>핵심 용어</summary>

- **Carbon Aware Computing (탄소 인식 컴퓨팅)**: 그리드(전력망)의 탄소 집약도(I)가 낮은 시간대(태양광·풍력 발전 비중이 높을 때)나 지역에 컴퓨팅 워크로드를 몰아서 실행하여 같은 전력 소비로 탄소 배출을 줄이는 기법.

</details>

- **O (Operational Emissions, 운영 배출량)**: 소프트웨어가 실행 중 소비하는 전력(E)에 해당 지역·시간대의 탄소 집약도(I)를 곱한 값 → **O = E × I**.
- **M (Embodied Emissions, 내재 배출량)**: 서버, GPU 등 하드웨어를 제조할 때 발생한 탄소 배출량 중, 해당 소프트웨어가 사용하는 기간·비중만큼 할당된 부분.
- **R (Functional Unit, 기능 단위)**: API 호출 1,000회, 사용자 시간 1시간, 거래 1건 등 소프트웨어의 유용한 출력을 나타내는 정규화 기준값.
- **SCI 공식**: $\mathrm{SCI} = (O + M) / R = (E \times I + M) / R$

#### 한줄 요약

- 같은 API 호출 수를 기준으로 실행 전력과 서버 제조분을 합쳐야 버전별 실제 탄소 효율을 비교할 수 있다.

## Ⅲ. 구조 및 구성요소 (SCI 측정 아키텍처)

<details><summary>핵심 용어</summary>

- **Telemetry (텔레메트리)**: 소프트웨어 실행 중 CPU 사용률, 메모리 소비량, 네트워크 I/O 등의 에너지 소비 관련 데이터를 자동으로 수집하고 모니터링하는 체계. SCI 계산의 핵심 원천 데이터.

</details>

```text
┌────────────────────────────────────────────────────────────────────────┐
│                        SCI Measurement Architecture                   │
├────────────────────────────────────────────────────────────────────────┤
│ 1. [측정 경계 정의] ── 측정 대상 서비스, 인프라, 기간 범위 확정          │
│          │                                                             │
│          ▼                                                             │
│ 2. [텔레메트리 수집] ── CPU/GPU 전력, 메모리, 탄소 집약도(I), 하드웨어 수명│
│    (Prometheus, CloudWatch, Carbon Intensity API)                      │
│          │                                                             │
│          ▼                                                             │
│ 3. [SCI 계산기] ── O = E × I, SCI = (O + M) / R                       │
│          │                                                             │
│          ▼                                                             │
│ 4. [기준선 vs 변경안 SCI 비교] ── SCI 감소 여부 + SLO 충족 여부 동시 판정│
└────────────────────────────────────────────────────────────────────────┘
```

선의 의미: 경계가 동일해야만 기준선과 변경안의 SCI를 공정하게 비교할 수 있으며, SLO(품질 목표) 충족 여부까지 함께 검증해야 진정한 탄소 감축으로 인정.

| 구성요소 | 핵심 역할 및 기능 | 데이터 원천 |
|:---|:---|:---|
| **측정 경계 정의** | **비교 대상 서비스·자원·기간 범위를 동일하게 고정** | 아키텍처 다이어그램, 인프라 목록 |
| **텔레메트리 수집** | **전력, 탄소 집약도(I), 기능 단위(R) 데이터 실시간 수집**| Prometheus, ElectricityMaps API |
| **SCI 계산기** | **O=E×I 산출 후 M과 합산, R로 나눠 SCI 도출** | 계산 엔진, 스프레드시트 |
| **비교·보고 체계** | **기준선·변경안 SCI 차이 시각화 및 감축 여부 공식 판정**| Grafana, 탄소 대시보드 |

#### 한줄 요약

- 측정 책임자가 저울 범위와 한 묶음의 크기를 정하면 수집기가 재료를 모으고 계산기와 검토 체계가 같은 기준으로 변경 효과를 비교한다.

## Ⅳ. 흐름도 (SCI 기반 그린 소프트웨어 개선 사이클)

<details><summary>핵심 용어</summary>

- **SLO (Service Level Objective, 서비스 수준 목표)**: 응답 시간 P99 < 200ms, 가용성 99.9% 등 서비스의 최소 품질 요건. SCI를 낮추려다 SLO를 위반하면 해당 최적화 방안은 채택 불가.

</details>

```text
[기존 소프트웨어 (Baseline)]          [최적화 후보 (변경안)]
           │                                   │
           └────────── 동일 측정 경계 ──────────┘
                                │
                                ▼
                      [E·I·M·R 텔레메트리 수집]
                                │
                                ▼
                      [SCI 산출: SCI = (E×I+M)/R]
                                │
                       ┌────────┴────────┐
               SCI 감소?               SLO 충족?
                  예 ◄─────────────────► 예
                                │
                        [변경안 채택 확정]
                                │
              아니오 ◄───────────┘
          (SCI 증가 또는 SLO 위반) → 재설계
```

### 동작 원리

1. **경계 고정**: 비교 대상을 공정하게 만들기 위해 소프트웨어 경계, 측정 기간, 기능 단위 R을 동일하게 설정.
2. **텔레메트리 기반 SCI 산출**: 실제 운영 중 측정된 전력(E), 탄소 집약도(I), 내재 탄소(M), 기능 단위(R)로 공식 계산.
3. **이중 판정**: SCI(탄소 효율)가 낮아졌는지 + SLO(응답속도, 처리량)가 깨지지 않았는지 동시 확인 (**그린 개선 사이클 완결**).

#### 한줄 요약

- 같은 크기의 바구니에 기준 버전과 변경 버전의 배출 자료를 담아 SCI를 계산해야 차이가 코드 변경에서 생겼는지 판단할 수 있다.

## Ⅴ. 종류 및 비교 (탄소 측정 지표 1:1 비교)

<details><summary>핵심 용어</summary>

- **GHG Protocol (온실가스 프로토콜)**: 기업의 온실가스 배출을 범주화(Scope 1/2/3)하여 측정하는 글로벌 회계 표준. SCI는 소프트웨어 영역의 Scope 2·3 일부를 측정하는 특화 지표.

</details>

| 탄소 측정 지표 | SCI (소프트웨어 탄소 집약도) | Total Emissions (총 탄소 배출량) | Energy Consumption (에너지 소비량) |
|:---|:---|:---|:---|
| **목적** | **소프트웨어 버전 간 탄소 효율 비교** | **기업/서비스의 전체 탄소 발자국 공시** | **전력 비용 및 효율 관리** |
| **단위** | gCO₂eq per R (기능 단위당 탄소) | tCO₂eq (절대량) | kWh (절대량) |
| **주요 한계** | 측정 경계와 R 왜곡 시 비교 무의미 | 사용자 수 증가와 실제 비효율 구분 불가 | 전력원의 탄소 차이(I) 반영 안 됨 |

#### 한줄 요약

- 총배출량은 이용자가 늘면 커지지만 SCI는 같은 거래 한 건에 든 탄소를 비교하고 에너지 사용량은 전력원 차이를 놓친다.

## Ⅵ. 실무 고려사항 및 대책 (SCI 측정 3대 실무 난제 대책)

<details><summary>핵심 용어</summary>

- **Carbon Intensity (탄소 집약도, I)**: 특정 시간대·지역에서 생산된 전력 1kWh당 배출되는 이산화탄소 환산량(gCO₂eq/kWh). 태양광·풍력이 많은 낮에는 낮고, 화력발전이 많은 밤에는 높음. 탄소 인식 컴퓨팅의 핵심 변수.

</details>

| 3대 실무 난제 | 발생 원인 | 실무 대책 및 해결방안 |
|:---|:---|:---|
| **1. 측정 경계 불일치** | 기준선과 변경안의 포함 자원 범위 상이 | **SCI 산정 전 서비스 경계(SUT: System Under Test)를 명시적으로 문서화하고 고정**|
| **2. 성능 저하를 탄소 감축으로 오인**| 응답이 느려진 것이 처리량 감소로 이어져 SCI가 낮아진 것처럼 보임 | **SLO(응답 시간, 처리량) 동시 검증 필수 병행** |
| **3. 고정된 탄소 계수 사용** | 지역/시간별 탄소 집약도(I) 차이를 반영하지 않음 | **ElectricityMaps 등 실시간 탄소 집약도 API를 통한 시간대별 I 값 적용**|

> 사례: **Microsoft Azure의 Emissions Impact Dashboard를 통한 클라우드 서비스 SCI 모니터링, Google의 탄소 인식(Carbon-Aware) 스케줄링으로 배치 워크로드를 저탄소 시간대로 자동 이동하는 사례**

#### 한줄 요약

- 야간 저탄소 시간대로 작업을 옮겨도 마감과 SLO를 함께 확인해야 느려진 서비스를 감축 성과로 오인하지 않는다.

## Ⅶ. 결론

<details><summary>핵심 용어</summary>

- **Demand Shaping (수요 조절)**: 에너지 비용이나 탄소 집약도가 낮은 시간대에 사용자의 행동을 유도(예: 업로드는 밤에, 미디어는 낮은 화질로)하여 소프트웨어의 전력 수요와 탄소 배출을 줄이는 그린 소프트웨어 전략.

</details>

- **그린 소프트웨어 개선 기준**에 따라 소프트웨어 최적화 시 **동일 경계와 기능 단위로 SCI를 산출하고 SLO 동시 충족을 확인한 변경안** 채택 원칙 적용

#### 한줄 요약

- 탄소만 줄이고 응답이 느려진 변경은 채택하지 않음이 핵심이다.
