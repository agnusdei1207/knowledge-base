## Ⅰ. 개요

<details><summary>용어 설명</summary>

- **디스크 스케줄링(Disk Scheduling)**: 하드디스크 바늘(헤드)이 이리저리 미친 듯이 튀는 걸 막기 위해, OS가 파일 읽기/쓰기 요청 순서를 엘리베이터처럼 가지런히 정렬해 주는 큐(Queue) 통제 기술이다.
- **탐색 시간(Seek Time)**: HDD의 물리적인 바늘(헤드)이 원하는 데이터가 있는 트랙까지 끽끽거리며 이동하는 데 걸리는, 디스크 성능을 갉아먹는 가장 치명적인 기계적 지연시간이다.

</details>

- 정의: 저장 매체의 물리적 한계를 극복하기 위해, I/O 요청 큐를 멱살 잡고 정렬/병합(Merging)해서 탐색 지연을 박살 내고 스루풋을 극대화하는 **I/O 관리 및 디스크 스케줄링**
- 배경: 앱에서 요청 들어온 순서대로 무식하게 처리하면, 하드디스크 바늘이 양끝을 왕복하느라 **탐색 오버헤드가 폭발**하기 때문

#### 한줄 요약

- 디스크 바늘이 헛돌지 않게 읽기/쓰기 요청을 모으고 줄 세워서 엘리베이터처럼 처리하는 기술이다.

## Ⅱ. 특징

<details><summary>용어 설명</summary>

- **회전 지연시간(Rotational Latency)**: 헤드가 트랙에 도착한 뒤, 원판(플래터)이 왱왱 돌아서 진짜 데이터가 있는 섹터가 헤드 밑으로 올 때까지 멍 때리는 대기시간이다.
- **멀티 큐 블록 I/O(blk-mq)**: 탐색 시간이 0인 NVMe SSD 시대가 오자, 옛날식 1차선 큐를 버리고 코어별로 수만 개의 큐를 뚫어서 초고속 병렬 I/O를 꽂아버리는 현대 리눅스 서브시스템이다.

</details>

- HDD 시절의 가장 큰 적인 **탐색 시간(Seek Time)** 과 **회전 지연(Rotational Latency)** 을 극한으로 쥐어짬.
- 인접한 블록 요청을 하나로 합치고(Merging) 순서를 재정렬해서 헤드의 헛스윙을 막음.
- 기계적 바늘이 없는 현대 NVMe/SSD는 정렬 똥꼬쇼 대신 **blk-mq** 같은 다중 큐로 병렬성에 올인함.

#### 한줄 요약

- HDD는 바늘 탐색 시간 최소화에 목숨을 걸고, SSD/NVMe는 병렬 큐로 깡성능을 쥐어짠다.

## Ⅲ. 구조 및 구성요소

<details><summary>용어 설명</summary>

- **엘리베이터 알고리즘(Elevator Algorithm)**: 엘리베이터가 올라가는 김에 층마다 서듯이, 디스크 헤드가 한 방향으로 훑으면서 경로상에 있는 요청을 싹 다 처리하고 돌아오는 SCAN 계열의 근본 알고리즘이다.

</details>

```text
[ 블록 I/O 서브시스템 십자포화 아키텍처 ]
         [ 파일 시스템 (VFS) ]
        (디스크 좀 읽고 써줘라)
                 │
┌────────────────▼────────────────┐
│       [ I/O 요청 큐 (Queue) ]   │
│  (I/O 스케줄러가 엘리베이터 정렬) │
└────────────────┬────────────────┘
                 ▼
         [ 장치 드라이버 ]
 (컨트롤러가 알아먹게 명령어 번역)
                 │
┌────────────────▼────────────────┐
│     [ 물리 디스크 (HDD/SSD) ]   │
│ (바늘 움직이거나 낸드 플래시 쏨) │
└────────────────┬────────────────┘
                 ▼
         [ 완료 처리기 (IRQ) ]
    (I/O 끝났다고 프로세스 깨움)
```

| 구성요소 | 책임 |
|:---|:---|
| I/O 요청 큐 | 앱들이 던진 읽기/쓰기 요청 쪼가리들을 줄 세우고 합치는(Merging) 대기실 |
| **I/O 스케줄러** | 엘리베이터 알고리즘으로 헤드 이동 동선을 최적화하고 응답 딜레이를 멱살 잡고 조율하는 두뇌 |
| 장치 드라이버 | OS의 논리적 요청을 하드웨어가 알아먹는 깡통 명령어(SATA/NVMe)로 번역하는 통역사 |
| 완료 처리기 | 디스크가 일 다 끝냈다고 하드웨어 인터럽트(IRQ) 날리면, 잠자던 프로세스를 확 깨워버리는 알람시계 |

#### 한줄 요약

- 요청 큐에서 스케줄러가 줄을 세우고, 드라이버가 디스크를 패면, 완료 처리기가 앱을 깨운다.

## Ⅳ. 흐름도

<details><summary>용어 설명</summary>

- **요청 병합 및 정렬(Request Merging & Sorting)**: 스케줄러가 1번, 2번, 3번 블록 요청을 1~3번 통째로 읽는 하나로 합치고(Merging), 헤드 이동 방향에 맞춰 순서를 재배치(Sorting)하는 최적화 예술이다.

</details>

```text
[ 디스크 I/O 스케줄링 십자포화 흐름 ]
┌──────────────────────────────┐
│ 1. 블록 I/O 요청 등록        │
│ (앱 ➔ VFS ➔ 큐 입성)        │
└──────────────┬───────────────┘
               ▼
┌──────────────────────────────┐
│ 2. 요청 병합(Merge) 및 정렬  │
│ (인접 블록 뭉치고, 동선 최적화)│
└──────────────┬───────────────┘
               ▼
┌──────────────────────────────┐
│ 3. 드라이버 디스패치         │
│ (하드웨어 컨트롤러에 꽂음)   │
└──────────────┬───────────────┘
               ▼
┌──────────────────────────────┐
│ 4. 물리적 처리 및 인터럽트   │
│ (플래터 돌리거나 낸드 쓰기)  │
└──────────────┬───────────────┘
               ▼
┌──────────────────────────────┐
│ 5. I/O 완료 및 프로세스 Wake │
│ (대기 풀고 연산 재개)        │
└──────────────────────────────┘
```

### 동작 원리

1. 요청 큐 등록: 프로세스가 VFS를 찔러서 떨어진 블록 I/O 요청(BIO)을 **큐**에 가둠.
2. 병합·제출 대상 선택: 스케줄러가 인접 섹터를 뭉치고(**Merging**), 헤드 동선이 짧아지게 순서를 조작함(**Sorting**).
3. 장치 명령 변환: 정리된 요청을 장치 드라이버가 넘겨받아 컨트롤러 명령어로 디스패치함.
4. 장치 실행·완료 게시: HDD 바늘이 움직이거나 SSD에 전자가 꽂히고, 끝나면 완료 큐(CQ)/인터럽트를 날림.
5. 완료 반영·작업 재개: 메모리 페이지 캐시를 갱신하고 Blocked 상태로 잠자던 프로세스의 멱살을 잡아 깨움.

#### 한줄 요약

- 큐에 넣고 $\to$ 뭉치고 줄 세워서 $\to$ 하드웨어에 쏜 다음 $\to$ 다 되면 깨우는 5단계다.

## Ⅴ. 종류 및 비교

<details><summary>용어 설명</summary>

- **SSTF (Shortest Seek Time First)**: 지금 바늘 위치에서 제일 가까운 놈부터 무지성으로 패는 방식으로, 구석에 있는 요청은 평생 굶어 죽는 기아(Starvation)를 유발한다.
- **SCAN / C-SCAN**: 엘리베이터처럼 바늘이 한쪽 끝까지 쭉 훑고, 다시 반대로 훑거나(SCAN) 아예 처음으로 휙 돌아와서 다시 훑는(C-SCAN) 공평함의 대명사이다.

</details>

| 스케줄링 알고리즘 | 동작 방식 (어떻게 움직이나) | 장단점 및 팩트폭력 |
|:---|:---|:---|
| **FCFS** | 먼저 온 놈부터 무식하게 순서대로 처리 | 탐색 시간 최악, 바늘이 원판 위에서 좌우 반복뛰기함 |
| **SSTF** | 지금 헤드 위치에서 가장 가까운 놈 우선 처리 | 평균 탐색 시간은 떡상하지만, 구석진 트랙은 영원히 처리 안 되는 **기아(Starvation) 발생** |
| **SCAN / C-SCAN** | 끝에서 끝으로 **엘리베이터**처럼 훑으며 처리 | 기아 현상 원천 봉쇄, 응답시간 편차가 안정적이나 양끝 바운드 편향 존재 |
| **LOOK / C-LOOK** | SCAN과 같지만, 끝에 요청 없으면 끝까지 안 가고 턴함 | 디스크 벽치기 하는 멍청한 오버헤드를 컷친 **현실적 HDD 국룰** |
| **Kyber / BFQ** | 다중 큐(blk-mq) 기반으로 타깃 지연시간 보장 및 공정성 조율 | 탐색 시간이 없는 **NVMe/SSD 시대의 최신 스케줄러** |

#### 한줄 요약

- 가까운 놈 먼저 치는 SSTF는 굶어 죽는 놈이 생기고, 한 방향으로 미는 SCAN/LOOK이 국룰이다.

## Ⅵ. 실무 고려사항 및 대책

<details><summary>용어 설명</summary>

- **none / mq-deadline / bfq**: 현대 리눅스의 스케줄러 마운트 옵션으로, SSD는 정렬 똥꼬쇼가 필요 없으니 `none`, 응답시간 보장은 `mq-deadline`, 무거운 HDD는 묵직한 `bfq`를 꽂는 게 정석이다.

</details>

| 문제 | 대책 | 효과 |
|:---|:---|:---|
| SSD 꽂아놓고 HDD용 정렬 알고리즘 돌리느라 CPU 오버헤드 터짐 | 스케줄러를 **`none` (No-op)** 으로 놔서 정렬 패스하고 꽂음 | 바늘이 없는 SSD의 극강 병렬 I/O 성능을 한계치까지 쥐어짬 |
| HDD 쓰는데 디스크 바깥쪽 요청이 안쪽 요청에 밀려서 평생 굶어 죽음(Starvation) | 디스크 끝을 안 찍고 돌아오는 **C-LOOK** 또는 공평성 보장 **BFQ** 적용 | 특정 프로세스가 I/O 렉 걸려서 뻗어버리는 기아 현상 철통 방어 |
| 읽기(Read)는 급한데, 대용량 쓰기(Write) 요청 큐에 꽉 막혀서 앱이 멈춤 | Read 큐의 우선순위를 멱살 잡고 올리고 쓰기 타임아웃 컷을 거는 튜닝 갈김 | 사용자가 체감하는 애플리케이션의 화면 렌더링/응답 속도 사수 |

#### 한줄 요약

- SSD는 `none`으로 정렬을 생까고, 깡통 HDD는 `bfq`나 `C-LOOK`으로 공평하게 줄을 세워라.

## Ⅶ. 결론

<details><summary>용어 설명</summary>

- **디스크 스케줄러 선택 기준(Disk Scheduler Selection Criteria)**: 하드웨어가 깡통 HDD인지 갓 NVMe인지, 응답시간이 생명인지 대역폭이 생명인지 따져서 none/BFQ를 가르는 잣대이다.

</details>

- **디스크 스케줄러 선택 기준** 원칙에 따라, 깡통 HDD는 **C-LOOK/BFQ**, 탐색 시간 제로인 SSD/NVMe는 무조건 **none / mq-deadline** 채택 기조 확립함

#### 한줄 요약

- 하드디스크는 물리적 바늘 헛스윙을 막고, NVMe는 스케줄링을 치워버려서 병렬로 때려 박는다.
