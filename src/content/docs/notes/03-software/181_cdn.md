## Ⅰ. 개요

<details><summary>핵심 용어</summary>

- **CDN (Content Delivery Network)**: 사용자 인접 엣지 서버(Edge Server)에 정적 자산(이미지, 영상, CSS 등)을 캐싱하여, 원본 서버(Origin) 부하 절감 및 로딩 속도를 극대화하는 분산 네트워크 인프라.
- **Origin Server (원본 서버)**: 서비스 주체의 정본 데이터가 존재하는 유일한 근원(Source of Truth) 서버.
- **Edge Node / PoP (Point of Presence)**: 사용자 물리적 인접 위치에서 콘텐츠를 전송(Delivery)하는 CDN 캐시 서버 클러스터.

</details>

- 정의: 원본 트래픽 병목 방지 및 지연(Latency) 최소화를 위해 에지 사본으로 콘텐츠를 전달하는 분산 전송 기법.
- 배경: 단일 데이터 센터와 글로벌 사용자 간 물리적 거리(RTT) 한계 극복.

#### 한줄 요약

- **CDN (Content Delivery Network)**: 사용자 인접 엣지 서버(Edge Server)에 정적 자산을 캐싱하여 원본 부하 절감 및 로딩 속도를 최적화하는 분산 네트워크 인프라.
- **Origin Server (원본 서버)**: 서비스 데이터의 정본이 저장된 유일한 근원 서버.
- **Edge Node / PoP (Point of Presence)**: 사용자 물리적 인접 위치에서 콘텐츠를 전송하는 CDN 캐시 서버 클러스터.

</details>

- 정의: 원본 트래픽 병목 방지 및 지연(Latency) 최소화를 위해 에지 서버로 콘텐츠를 분산 전송하는 기법.
- 배경: 단일 데이터 센터의 물리적 거리(RTT) 한계 극복 및 글로벌 서비스 품질 보장.

#### 한줄 요약

- 오리진 서버의 콘텐츠를 에지 캐시에 복제하여 사용자 인접 노드에서 즉시 응답.

## Ⅱ. 특징 (CDN 3대 핵심 라우팅 메커니즘)

<details><summary>핵심 용어</summary>

- **Anycast (애니캐스트)**: 동일 IP를 공유하는 엣지 서버군 중 BGP를 통해 최적 지연 경로로 요청을 전달하는 라우팅 기법.
- **Geographic Routing (지리적 라우팅)**: 클라이언트 DNS 질의를 기반으로 물리적 최인접 PoP를 동적 반환.
- **Reverse Proxy Caching (리버스 프록시 캐싱)**: 엣지 서버가 요청을 인터셉트하여 캐시 응답, 부재 시 원본 백홀(Backhaul).
- **DDoS Mitigation (DDoS 완화)**: 거대 대역폭의 엣지 서버를 통한 트래픽 흡수 및 원본 보호.

</details>

#### 한줄 요약

- 에지에 사본이 없을 때도 실드가 여러 지역의 같은 미스를 하나로 모아 원본에 몰리는 요청을 줄인다.

## Ⅲ. 구조 및 구성요소 (CDN 다층 계층 구조)

<details><summary>핵심 용어</summary>

- **Shield Cache (쉴드 캐시)**: 원본 앞단 중간 계층 캐시. 다수 엣지 노드의 동시 Cache Miss로 인한 원본 서버의 요청 폭주(Cache Stampede) 방지 방패.

</details>

```text
┌────────────────────────────────────────────────────────────────────────┐
│                        Multi-Tier CDN Architecture                     │
├────────────────────────────────────────────────────────────────────────┤
│ 1. [Client (서울)] ───(DNS 조회 및 Anycast)──► 2. [Edge PoP (서울)]    │
│                                                       │                │
│                                                 (Cache Miss 시)        │
│                                                       ▼                │
│ 4. [Origin Server (미국)] ◄──(Cache Miss 시)── 3. [Shield Cache (도쿄)]│
└────────────────────────────────────────────────────────────────────────┘
```

선의 의미: 클라이언트의 요청이 최전방 에지 서버에서부터 방패 캐시, 원본 서버까지 다단계로 통제되며 단계마다 방어선(Cache Hit)이 작동하는 3-Tier 응답 구조.

| 구성요소 | 핵심 역할 및 기능 | 실무 사례 |
|:---|:---|:---|
| **DNS Server** | **사용자 위치 기반 최적 엣지 서버 IP 반환 (GSLB)** | Route53, Cloudflare DNS |
| **Edge PoP** | **엔드유저에게 가장 빨리 콘텐츠를 던져주는 최전방 서버**| 서울 리전 CDN 엣지 |
| **Shield Cache** | **엣지 서버들의 요청을 모아서 Origin을 보호하는 중간층**| AWS CloudFront Regional |
| **Origin Server** | **캐시가 없을 때만 호출되는 최종 정본 데이터 저장소** | AWS S3, Nginx 서버 |

#### 한줄 요약

- DNS/애니캐스트 라우터가 최적 에지를 선택하고 에지와 리저널 실드가 캐시를 탐색하며 모두 미스일 때만 오리진 서버를 조회한다.

## Ⅳ. 흐름도 (콘텐츠 요청 파이프라인 흐름)

<details><summary>핵심 용어</summary>

- **Cache Hit / Miss Ratio (캐시 적중률/실패율)**: 사용자 요청이 원본(Origin)까지 가지 않고 엣지(Edge)에서 바로 처리된 비율. 이 수치가 높을수록 훌륭한 CDN 설정이며 원본 서버 비용이 절감됨.

</details>

```text
[Client]                            [Edge Node]                     [Origin]
   │                                     │                              │
   ├─ 1. DNS Query (Geo-Routing) ───────►│                              │
   ├─ 2. HTTP GET /image.png ───────────►│                              │
   │                                     ├─ 3. Cache Check (Miss)       │
   │                                     │                              │
   │                                     ├─ 4. HTTP GET /image.png ────►│
   │                                     │                              │
   │                                     │◄─ 5. HTTP 200 (image data) ──┤
   │                                     ├─ 6. Save to Cache (TTL 설정) │
   │◄─ 7. HTTP 200 (image data) ─────────┤                              │
```

### 동작 원리

1. **Routing**: 클라이언트 DNS 질의 시 GSLB가 최인접 Edge IP 반환.
2. **First Request**: 최초 요청 시 Cache Miss 발생.
3. **Fetch & Cache**: Edge가 Origin에서 데이터를 가져와 TTL만큼 캐싱.
4. **Subsequent Request**: 이후 사용자는 Origin 접근 없이 Edge에서 즉시 응답.

#### 한줄 요약

- 첫 이미지 요청만 실드와 원본을 거치고 다음 요청은 TTL 안의 에지 사본으로 응답해 장거리 왕복을 없앤다.

## Ⅴ. 종류 및 비교 (Pull vs Push 방식 1:1 비교)

<details><summary>핵심 용어</summary>

- **Push CDN**: 서비스 배포 시점에 개발자가 미리 콘텐츠를 CDN 엣지에 찔러넣는(Pre-loading) 방식. 대규모 게임 패치나 VOD 영상처럼 용량이 크고 배포 일정이 정해져 있을 때 유리함.

</details>

| 비교 항목 | Pull CDN (일반적 웹 방식) | Push CDN (대용량 배포 방식) |
|:---|:---|:---|
| **동작 원리** | 클라이언트가 요청할 때 비로소 Origin에서 당겨옴 | 배포 시점에 Origin이 엣지로 미리 밀어넣음 |
| **적합한 데이터** | **HTML, JS, 자잘한 이미지 등 일반 웹 리소스**| **대용량 VOD 영상, 수십 GB 게임 클라이언트 패치** |
| **장점** | 설정이 단순하고 서버 용량 효율성이 훌륭함 | 첫 유저(Cache Miss)의 로딩 지연 시간마저 없음 |
| **단점 (문제점)**| 최초 요청 유저는 Cache Miss 지연을 감수해야 함 | 모든 엣지에 밀어넣으므로 스토리지 비용 막대 |

#### 한줄 요약

- 수요를 모르는 웹 자산은 요청 때 채우고 게임 패치처럼 배포 시점과 대상이 정해진 콘텐츠는 에지에 미리 보낸다.

## Ⅵ. 실무 고려사항 및 대책 (CDN 3대 실무 난제 대책)

<details><summary>핵심 용어</summary>

- **Cache Invalidation / Purge (무효화 / 퍼지)**: 원본 데이터가 수정되었음에도 Edge에 예전 데이터(Stale)가 남아 엉뚱한 화면이 나오는 현상을 막기 위해, Edge의 특정 경로(`/*`) 데이터를 강제로 지우는 API 호출.

</details>

| 3대 실무 난제 | 발생 원인 | 실무 대책 및 해결방안 |
|:---|:---|:---|
| **1. Stale Data 갱신 지연** | TTL이 길게 남아 원본 수정이 미반영 | **강제 퍼지(Purge) 수행 또는 URL 버저닝(`app.v2.js`) 적용**|
| **2. 동적 콘텐츠 분배 한계**| 로그인 유저마다 데이터(장바구니)가 다름| **Cache-Control: private 및 API 응답은 CDN 패스(Bypass)**|
| **3. CORS Cross-Origin 에러**| CDN 도메인과 Origin 도메인이 다름 | **Origin 서버와 CDN 엣지 양쪽에 `Access-Control-Allow-Origin` 헤더 설정**|

> 사례: **토스 / 넷플릭스의 정적 에셋(Asset)에 대한 URL 해시화(Hash) 버저닝을 통한 무효화(Purge) 없는 무한(Infinite) TTL 캐싱 전략**

#### 한줄 요약

- 정적 파일명에 내용 해시를 넣으면 긴 TTL을 유지하면서 변경 시 새 주소로 즉시 전환하고 전 세계 퍼지 지연도 피할 수 있다.

## Ⅶ. 결론

<details><summary>핵심 용어</summary>

- **Dynamic Content Delivery (동적 콘텐츠 전송)**: 최신 CDN은 단순 캐시를 넘어, 엣지 라우팅 최적화 및 Edge Computing(AWS Lambda@Edge)을 통해 API 및 동적 콘텐츠까지 가속하는 기술로 진화 중.

</details>

- CDN 캐시 정책 기준, Static Asset의 Edge 분산 및 URL 버저닝 전략 필수 적용.
