## Ⅰ. 개요

<details><summary>용어 설명</summary>

- **CDN(Content Delivery Network)**: 사용자 근접 에지 서버(Edge Server)에 정적 자산을 캐싱하여 원본 서버(Origin Server) 부하를 경감하고 지연 시간(Latency)을 최소화하는 분산 네트워크.
- **오리진 서버(Origin Server)**: 원본 데이터가 저장된 서비스의 최종 정본 저장소.
- **에지 노드/PoP(Edge Node/Point of Presence)**: 사용자 물리적 근접 위치에서 콘텐츠를 고속 전송하는 캐시 서버 군집.

</details>

- 정의/개념: 콘텐츠 사본을 Edge에 배치하는 **CDN**
- 배경/필요성: 원거리 Origin 직접 접근은 **RTT•대역폭•부하** 증가

#### 한줄 요약

- 사용자와 가까운 사본이 응답하고 없을 때만 원본 계층에서 가져온다.

## Ⅱ. 특징

<details><summary>용어 설명</summary>

- **애니캐스트(Anycast)**: 동일 IP를 다수 서버에 할당하여 BGP 경로 탐색을 통해 최단 지연 시간 노드로 유도하는 라우팅 기술.
- **지리적 라우팅(Geo-Routing)**: 클라이언트 IP의 지리적 위치 정보를 기반으로 물리적 근접 PoP(Point of Presence)를 할당하는 기술.
- **리버스 프록시 캐싱(Reverse Proxy Caching)**: 에지 서버가 클라이언트 요청을 가로채어(Intercept) 캐시 데이터를 응답하고, 부재 시 원본과 동기화하는 기법.
- **DDoS 완화(DDoS Mitigation)**: 에지 노드의 대규모 대역폭을 활용하여 공격 트래픽을 분산·흡수하고 원본 서버를 보호하는 보안 기술.

</details>

- **Anycast•Geo Routing**으로 근접 PoP 선택
- **Reverse Proxy Cache**로 Origin 요청•대역폭 절감
- 분산 Edge 용량으로 **Traffic Spike•DDoS** 완화

#### 한줄 요약

- 라우팅은 가까운 지점을 고르고 Cache는 반복 요청을 원본에서 분리한다.

## Ⅲ. 구조 및 구성요소

<details><summary>용어 설명</summary>

- **쉴드 캐시(Shield Cache)**: 다수 에지 노드의 캐시 미스(Cache Miss) 요청을 집약하여 원본 부하를 방지하는 중간 계층 캐시.

</details>

```text
[CDN]
 ├── [DNS•Anycast]
 ├── [Edge PoP]
 ├── [Shield Cache]
 └── [Origin]
```

| 구성요소 | 책임 |
|---|---|
| DNS•Anycast | Client를 **근접•가용 Edge**로 유도 |
| Edge PoP | Cache Hit 응답과 **접속 종료** 처리 |
| Shield Cache | Edge Miss 병합과 **Origin 보호** |
| Origin | 콘텐츠 **정본•권한•원본 응답** 제공 |

#### 한줄 요약

- Edge와 Shield가 사본 계층을 이루고 Origin은 최종 정본만 제공한다.

## Ⅳ. 흐름도

<details><summary>용어 설명</summary>

- **캐시 적중률(Cache Hit Ratio)**: 원본 접근 없이 에지에서 즉시 처리된 요청의 비율.

</details>

```text
[콘텐츠 요청]
      │
      ▼
1. 근접 Edge 선택
      │
      ▼
2. Cache Key•정책 평가
      │
      ▼
3. Edge•Shield 조회
      │
      ▼
4. Miss 시 Origin 조회
      │
      ▼
5. Cache 저장•응답
      │
      ▼
[콘텐츠 반환]
```

### 동작 원리

1. **근접 Edge 선택**: DNS•Anycast로 PoP 결정
2. **Cache Key•정책 평가**: URL•Header•Cookie 기준 확인
3. **Edge•Shield 조회**: Hit면 사본과 Metadata 검증
4. **Miss 시 Origin 조회**: 요청 병합 후 정본 인출
5. **Cache 저장•응답**: TTL•ETag와 저장 후 반환

#### 한줄 요약

- Cache Miss를 Shield에서 병합해 Origin 조회를 줄이고 결과를 Edge에 재사용한다.

## Ⅴ. 종류 및 비교

<details><summary>용어 설명</summary>

- **Push CDN**: 배포 시점에 콘텐츠를 에지로 사전 로딩(Pre-loading)하는 방식.

</details>

| 항목 | Pull CDN (일반 웹) | Push CDN (대용량) |
|:---|:---|:---|
| **동작** | 요청 시 원본에서 인출 | 배포 시점에 에지로 밀어넣음 |
| **데이터** | 일반 웹 리소스 | VOD, 게임 패치 |
| **장점** | 단순 설정, 용량 효율 | 첫 사용자 응답 속도 최적 |

#### 한줄 요약

- 일반 자산은 Pull, 출시 시점의 대용량 자산은 Push 사전 배치를 검토한다.

## Ⅵ. 실무 고려사항 및 대책

<details><summary>용어 설명</summary>

- **퍼지(Purge/Invalidation)**: 에지 캐시 내 노후 데이터(Stale)를 강제 삭제하는 API 호출.

</details>

| 난제 | 원인 | 대책 |
|:---|:---|:---|
| **갱신 지연** | 긴 TTL(Time To Live) | 강제 퍼지, URL 버저닝 |
| **동적 콘텐츠** | 로그인별 데이터 상이 | Cache-Control: private, 패스(Bypass) |
| **CORS 에러** | 도메인 불일치 | 헤더 설정(`Access-Control-Allow-Origin`) |

- 불변 자산은 **Content Hash•긴 TTL**, 동적 응답은 Private•Bypass

#### 한줄 요약

- 변경 가능한 주소에는 짧은 TTL이나 Purge, 불변 주소에는 긴 TTL을 적용한다.

## Ⅶ. 결론

<details><summary>용어 설명</summary>

- **에지 컴퓨팅(Edge Computing)**: 엣지 서버 내 로직 실행(AWS Lambda@Edge)으로 동적 데이터 가속.

</details>

- 불변 정적 자산은 **CDN Cache**, 개인화 응답은 Bypass 선택

#### 한줄 요약

- Cache 가능성·변경 빈도·개인화를 기준으로 Edge 저장과 Origin 직접 처리를 나눈다.
