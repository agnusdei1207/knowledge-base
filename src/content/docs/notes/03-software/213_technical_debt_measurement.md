## Ⅰ. 개요

<details><summary>용어 설명</summary>

- **기술부채(Technical Debt)**: 단기적인 출시 속도나 편의를 위해 최선의 설계 대신 임시방편적인 코드와 구조적 타협을 선택함으로써, 향후 유지보수 시 지속적인 추가 비용과 지연(이자)을 발생시키는 소프트웨어 엔지니어링 개념.
- **원금과 이자(Principal & Interest)**: 결함을 근본적으로 리팩터링하는 데 소요되는 일회성 상환 공수(원금)와, 부채를 방치함으로써 매 스프린트마다 발생하는 개발 지연, 디버깅 공수, 장애 손실(이자).

</details>

- 정의/개념: 소프트웨어 개발 과정의 타협으로 누적된 설계 결함을 **원금과 이자 관점으로 정량화하고 체계적으로 상환하는 소프트웨어 품질 관리** 체계
- 배경/필요성: 보이지 않는 아키텍처 부채와 코드 악취 방치로 인한 **유지보수 비용 폭증, 개발 생산성 급락 및 시스템 붕괴 위험** 직면

#### 한줄 요약

- 소나큐브(SonarQube) 정적 분석과 Git 커밋 핫스팟 분석을 결합하여 기술부채를 화폐/공수 가치로 환산하고 정규 스프린트 백로그에 상환

## Ⅱ. 특징

<details><summary>용어 설명</summary>

- **SQALE 방법론**: 소스코드 품질 측정 표준으로, 발견된 코드 악취 및 결함을 수정하는 데 걸리는 시간(SQALE Debt Rating)을 A~E 등급으로 산출하는 기법.
- **부채 등록부(Debt Register)**: 식별된 부채 항목, 발생 원인, 담당 오너, 예상 원금/이자, 상환 우선순위를 추적하는 백로그 대장.

</details>

- 결함을 수정하는 데 드는 일회성 비용을 정량 산출하는 **상환 원금(Remediation Principal) 측정**
- 수정하지 않고 방치할 때 발생하는 생산성 손실과 장애 리스크를 평가하는 **반복 이자(Recurring Interest) 산정**
- 정규 스프린트 엔지니어링 용량의 20%를 상환에 배정하는 **정규 백로그 상환 거버넌스**

#### 한줄 요약

- 원금과 이자 측정, 부채 등록부 관리, CI 품질 게이트(Quality Gate)를 통해 기술부채의 폭증을 차단

## Ⅲ. 구조 및 구성요소

<details><summary>용어 설명</summary>

- **기술부채 관리 5대 프레임워크 요소**: Debt Register(부채 등록부), Cost Meter(원금/이자 측정기), Risk Assessor(비즈니스 위험 평가), Remediation Backlog(상환 실행), Quality Gate(신규 유입 차단).

</details>

```text
[ 기술부채(Technical Debt) 측정, 우선순위화 및 상환 거버넌스 구조도 ]

 1. [ 부채 탐지 및 등록 계층 (Detection & Debt Register) ]
    ┌─────────────────────────────────────────────────────────────┐
    │  • SonarQube(정적 코드 악취) + Git Hotspot(빈번 변경 파일) │
    │  • APM 성능 결함 + Jira 장애 티켓 이력 ➔ 부채 등록부 등재   │
    └────────────────────────────┬────────────────────────────────┘
                                 │
                                 ▼
 2. [ 재무적/위험 정량화 계층 (Cost Meter & Risk Assessment) ] ───┐
    • 상환 원금(M/D) vs 월간 발생 이자(지연 시간/장애 피해액)     │
    • ROI = (월간 절감 이자 × 잔여 수명) / 상환 원금 산출       │
    └────────────────────────────┬────────────────────────────────┘
                                 │ (고수익 상환 대상 선별)
                                 ▼
 3. [ 상환 실행 및 게이트 계층 (Remediation & Quality Gate) ] ────┐
    • 스프린트 용량의 20%를 '기술부채 상환 백로그'로 우선 배정   │
    • CI 파이프라인 Quality Gate(SonarQube A등급) ➔ 신규 부채 차단│
    └─────────────────────────────────────────────────────────────┘
```

선의 의미: 정적 분석과 핫스팟으로 등록된 부채를 원금/이자 ROI로 평가하여 스프린트 백로그에 투입하고 CI 게이트로 신규 유입을 막는 구조.

| 구성요소 | 책임 |
|:---|:---|
| 부채 등록부 (Debt Register) | 식별된 코드/아키텍처 부채의 **원인, 영향 모듈, 담당자(Owner), 해결 상태 추적** |
| 비용 측정기 (Cost Meter) | 결함 수정을 위한 **상환 원금(공수)과 매달 낭비되는 반복 생산성 손실(이자) 산출** |
| 위험 평가기 (Risk Assessor) | 해당 모듈의 **장애 발생 확률과 비즈니스 파급력(Business Impact) 점수화** |
| 상환 실행기 (Remediation) | 우선순위가 높은 부채를 **정규 스프린트 백로그(20% 할당)에 배치하여 리팩터링** |
| 품질 게이트 (Quality Gate) | 신규 PR 커밋 시 **SQALE 등급 및 테스트 커버리지 기준 미달 코드의 병합 차단** |

#### 한줄 요약

- 부채 등록부, 비용 측정기, 위험 평가기, 상환 실행기, 품질 게이트가 결합하여 기술부채를 통제

## Ⅳ. 흐름도

<details><summary>용어 설명</summary>

- **기술부채 수명주기 5단계**: 부채 식별 및 등록 $\to$ 원금/이자 정량화 $\to$ 상환 우선순위 결정 $\to$ 스프린트 상환 실행 $\to$ 상환 효과 검증.

</details>

```text
[ 기술부채 식별, ROI 평가 및 상환 파이프라인 ]

 ┌────────────────────────────────────────┐
 │ 1. SonarQube 및 Git 핫스팟 기반 부채 식별│
 └───────────────────┬────────────────────┘
                     │
                     ▼
 ┌────────────────────────────────────────┐
 │ 2. 상환 원금(공수) 및 월간 누적 이자 산출│
 └───────────────────┬────────────────────┘
                     │
                     ▼
 ┌────────────────────────────────────────┐
 │ 3. ROI 및 위험 기반 상환 우선순위 매트릭스
 ├───────────────────┬────────────────────┤
 │ 고이자 & 고위험   │ 저이자 & 저위험    │
 │ • 즉시 상환 백로그│ • 위험 수용/모니터링│
 └───────────────────┴────────────────────┘
                     │
                     ▼
 ┌────────────────────────────────────────┐
 │ 4. 정규 스프린트에서 리팩터링 및 아키텍처 개선
 └───────────────────┬────────────────────┘
                     │
                     ▼
 ┌────────────────────────────────────────┐
 │ 5. DORA 리드타임 단축 및 결함률 감소 측정│
 └────────────────────────────────────────┘
```

### 동작 원리

1. 부채 식별: SonarQube 분석 결과 결제 모듈에서 복잡도(Cyclomatic Complexity) 45 이상의 코드 악취와 30일의 부채 기간 검출.
2. 비용 산출: 리팩터링 공수(원금)는 5 M/D, 매달 변경 지연과 버그 수정으로 낭비되는 시간(이자)은 월 3 M/D로 정량화.
3. 우선순위: 2개월 만에 원금을 회수(ROI 300%)할 수 있는 최우선 상환 대상으로 확정.
4. 상환 실행: 다음 스프린트 백로그에 등록하고 메서드 추출과 단위 테스트 보강을 1주간 전담 수행.
5. 효과 측정: 상환 완료 후 해당 모듈의 PR 리드타임이 4일에서 1일로 단축되고 배포 실패율이 0%로 개선됨을 확인.

#### 한줄 요약

- 부채 식별 $\to$ 비용 산출 $\to$ 우선순위 결정 $\to$ 상환 실행 $\to$ 효과 측정의 5단계

## Ⅴ. 종류 및 비교

<details><summary>용어 설명</summary>

- **Code Debt vs Architecture Debt vs Platform/Infrastructure Debt**: 단위 코드 레벨(Code), 모듈 간 결합도(Architecture), 프레임워크/OS 노후화(Platform).

</details>

| 구분 | 코드 부채 (Code Debt) | 아키텍처 부채 (Architecture Debt) | 플랫폼/인프라 부채 (Platform Debt) |
|:---|:---|:---|:---|
| **적용 기준** | 단일 함수, 클래스 내부의 중복 코드, 매개변수 과다, 매직 넘버 | 서비스 간 순환 참조, 모놀리스 강결합, 데이터베이스 공유 | EOL(지원 종료) 임박한 Java/Spring 구버전, 노후 OS |
| **핵심 특징** | **SonarQube 정적 분석으로 즉시 자동 탐지 가능, 국소적 영향** | **시스템 전반의 변경 비용과 장애 파급 반경(Blast Radius) 급증** | **보안 취약점(CVE) 패치 불가 및 클라우드 마이그레이션 차단** |
| **한계** | 코드만 깨끗해지고 시스템 전반의 아키텍처 병목은 미해결 | 상환 시 대규모 인터페이스 변경 및 장기간의 재설계 공수 소요 | 런타임 프레임워크 전면 교체에 따른 대규모 회귀 테스트 부담 |

#### 한줄 요약

- 단위 함수는 코드 부채, 모듈 간 결합은 아키텍처 부채, 노후 프레임워크는 플랫폼 부채로 분류하여 상환

## Ⅵ. 실무 고려사항 및 대책

<details><summary>용어 설명</summary>

- **지표 게임화(Metric Gaming) 방지**: 실제 가독성 개선 없이 소나큐브 룰만 우회(`@SuppressWarnings`)하여 수치만 100점으로 만드는 개발자의 편법을 방지하는 통제.

</details>

| 문제 | 대책 | 효과 |
|:---|:---|:---|
| 툴 점수만 높이고 실질적 변경은 없는 지표 게임화(Metric Gaming) | **정적 분석 점수와 함께 `Git Commit Hotspot(자주 변경되는 파일)` 교차 분석** | 실질적 병목 부채 타겟팅 100% 달성 |
| 폐기 예정이거나 변경이 전혀 없는 레거시 코드를 맹목적 상환 | **시스템 로드맵상 6개월 내 교체 대상은 '위험 수용(Acceptance)' 처리** | 불필요한 엔지니어링 낭비 방지 |
| 경영진이 기능 개발만 요구하여 부채 상환 일정 완전 배제 | **기술부채를 '지연 비용(Cost of Delay)' 화폐 가치로 환산하여 보고** | 정규 스프린트 20% 상환 용량 확보 |

#### 한줄 요약

- 핫스팟 교차 검증, 로드맵 연계, 지연 비용 화폐화를 통해 기술부채 상환의 경영진 지지를 획득

## Ⅶ. 결론

<details><summary>용어 설명</summary>

- **DORA 메트릭스와 기술부채의 상관관계**: 기술부채를 적극 상환할수록 배포 빈도(Deployment Frequency)가 증가하고 변경 리드타임(Lead Time for Changes)이 단축되는 소프트웨어 생산성 법칙.

</details>

- **기술부채 측정 및 관리** 기반 소프트웨어의 지속 가능한 개발 속도를 지켜내는 핵심 엔지니어링 거버넌스이며, 소나큐브 정적 분석과 원금/이자 ROI 평가 및 스프린트 20% 룰을 제도화하여 부채의 눈덩이 효과를 차단해야 함

#### 한줄 요약

- 원금과 이자 정량화 및 정규 스프린트 상환 백로그 할당을 통해 지속 가능한 소프트웨어 생산성을 완성
