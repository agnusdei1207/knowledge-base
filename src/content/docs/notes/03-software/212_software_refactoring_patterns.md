## Ⅰ. 개요

<details><summary>용어 설명</summary>

- **소프트웨어 리팩터링(Software Refactoring)**: 소프트웨어가 제공하는 외부 동작(기능, 인터페이스)은 완벽히 보존하면서, 내부 코드 구조와 설계만을 점진적이고 체계적으로 개선하여 가독성을 높이고 유지보수 비용을 낮추는 개발 기법이다.
- **코드 악취(Code Smell)**: 현재 당장 버그를 일으키지는 않지만, 설계 원칙을 위반하여 코드의 이해를 방해하고 향후 변경 시 높은 유지보수 비용과 잠재적 결함 위험을 강력히 암시하는 구조적 징후(예: 거대한 클래스, 긴 메서드)이다.

</details>

- 정의/개념: 외부 동작을 보존하며 내부 구조를 개선하는 **Refactoring**
- 배경/필요성: Code Smell•기술 부채로 **변경 지연•회귀 위험** 증가

#### 한줄 요약
- 사용자 관점의 외부 기능은 그대로 둔 채, 내부의 복잡하고 얽힌 코드를 규칙에 따라 작게 쪼개고 재배치하여 향후 유지보수를 원활하게 만드는 구조 개선 작업

## Ⅱ. 특징

<details><summary>용어 설명</summary>

- **외부 동작 계약 보존(External Behavior Preservation)**: 리팩터링의 절대 원칙으로, 코드 구조가 아무리 바뀌더라도 동일한 입력에 대해 동일한 출력, 상태 변화, 오류 처리 결과를 보장해야 한다는 약속이다.
- **메서드 추출(Extract Method)**: 코드의 의도와 구현이 뒤섞여 있는 길고 복잡한 함수의 일부분을 분리해, 그 목적을 명확히 설명할 수 있는 이름을 가진 독립된 메서드로 추출하는 가장 기본적이고 핵심적인 리팩터링 패턴이다.
- **함수 이동(Move Function)**: 특정 함수가 자신이 속한 클래스나 모듈보다 다른 모듈의 데이터 요소(필드)를 더 많이 참조할 때, 응집도를 높이고 결합도를 낮추기 위해 해당 데이터가 있는 곳으로 함수를 이사시키는 패턴이다.
- **조건문 다형성 치환(Replace Conditional with Polymorphism)**: 코드 곳곳에 산재한 복잡한 switch나 if-else 분기문(타입 코드에 따른 분기)을 객체 지향의 다형성(오버라이딩)을 활용해 각 하위 클래스로 분산시켜 조건부 로직을 제거하는 패턴이다.

</details>

- **외부 동작 계약 보존**을 절대 전제로 삼아 내부 구조 변경만을 수행하는 것이 핵심 철학이다.
- 대규모 수정 대신 아주 작은 변환 단계를 거치며, 각 단계 직후 즉각적인 회귀 테스트를 수행하여 실패 시 복구 범위를 최소화한다.
- 긴 함수에는 **메서드 추출**을, 책임이 엇나간 함수에는 **함수 이동**을, 복잡한 타입 분기에는 **조건문 다형성 치환** 등 식별된 악취에 정통하게 매핑되는 기법을 적용한다.

#### 한줄 요약
- 한꺼번에 대규모로 코드를 뜯어고치는 것이 아니라, 테스트망의 보호 아래 작은 패턴 단위로 코드를 조각조각 개선하여 언제든 정상 작동 상태를 유지하는 안전한 설계 변경

## Ⅲ. 구조 및 구성요소

<details><summary>용어 설명</summary>

- **동작 계약(Behavior Contract)**: 리팩터링 전후로 절대 변하지 않아야 하는 시스템의 경계 조건으로, 입력 파라미터 제약, 예상 출력값, 발생 가능한 예외(Exception), 상태 변경 순서 등을 포함하는 규약이다.
- **변환 패턴(Refactoring Pattern)**: 마틴 파울러 등이 정립한 카탈로그로, 특정 코드 악취를 해결하기 위한 일련의 안전한 절차적 스텝(예: 변수명 변경, 메서드 인라인화)과 적용 조건이 체계화된 방법론이다.
- **회귀 검증(Regression Verification)**: 구조 변경 작업 이후에도 기존의 비즈니스 로직(동작 계약)이 전혀 깨지지 않고 동일하게 작동하는지를 자동화된 단위 테스트(Unit Test)를 통해 기계적으로 입증하는 활동이다.

</details>

```text
[Refactoring 체계]
 ├── [Code Smell]
 ├── [Behavior Contract]
 ├── [변환 Pattern]
 └── [Regression Verification]
```

| 구성요소 | 책임 |
|:---|:---|
| Code Smell | 가독성•변경성을 해치는 **개선 표적** 제공 |
| Behavior Contract | 보존할 입력•출력•상태•**예외 기준** 정의 |
| 변환 Pattern | Smell별 검증된 **Code 조작 절차** 제공 |
| Regression Verification | 변환 후 **외부 동작 보존** 입증 |

#### 한줄 요약
- 코드의 구조적 문제점(악취)을 찾아내고, 정해진 기법(패턴)으로 이를 해소한 뒤, 이전과 똑같이 작동하는지(동작 계약 보존)를 자동 테스트로 끊임없이 검증하는 무결성 유지 사이클

## Ⅳ. 흐름도

<details><summary>용어 설명</summary>

- **1. 동작 고정(Behavior Pinning)**: 리팩터링 대상 코드의 현재 상태를 블랙박스로 간주하고, 실제 입출력과 엣지 케이스를 모두 포괄하는 특성화 테스트(Characterization Test)를 작성하여 기존 행위를 단단히 고정하는 0단계이다.
- **2. 악취 선택(Smell Selection)**: 정적 분석기나 코드 리뷰를 통해 시스템의 복잡도와 유지보수 비용을 가장 크게 가중시키는 코드 악취(예: 중복 코드, 장황한 메서드) 하나를 타겟으로 콕 집어내는 단계이다.
- **3. 작은 변환(Small Transformation)**: IDE의 리팩터링 도구 등을 활용하여, 선택된 악취에 대응하는 단 하나의 카탈로그 패턴만을 매우 작고 고립된 단계로 적용하여 내부 구조를 뒤트는 단계이다.
- **4. 회귀 검증(Regression Verification)**: 변환 직후 1단계에서 짠 특성화 테스트 스위트를 실행하여, 컴파일 오류나 런타임 비즈니스 로직 훼손(Regression)이 발생했는지 즉각 판별하는 단계이다.
- **5. 변경 확정(Change Commit)**: 테스트 패스(Green) 시 로컬 커밋으로 변경을 확정 짓고, 실패(Red) 시 원인 분석 대신 즉각 롤백(Undo)한 뒤 더 작은 단계로 3단계를 재시도하는 결정 단계이다.

</details>

```text
1. 동작 고정 (Characterization Test)
      |
      v
2. 악취 선택 (Identify Code Smell)
      |
      v
3. 작은 변환 (Apply Single Pattern)
      |
      v
4. 회귀 검증 (Run Tests)
      |
      +-- 계약 불일치(Fail) --> 즉시 롤백(Undo) 후 더 작은 단계로 3단계 재시도
      |
      +-- 계약 일치(Pass)
              |
              v
5. 변경 확정 (Local Commit)
      |
      +-- 잔여 악취 존재 --> 2단계 반복 (Iterative)
```

### 동작 원리

1. 동작 고정: Characterization Test로 현재 Behavior 기록
2. 악취 선택: 변경 비용이 큰 Code Smell 하나 지정
3. 작은 변환: 단일 Refactoring Pattern 적용
4. 회귀 검증: Test로 Behavior Contract 보존 확인
5. 변경 확정: 통과 시 Commit, 실패 시 Undo•단계 축소

#### 한줄 요약
- 기존 로직을 테스트로 꽁꽁 묶어둔 채 코드를 조금씩 썰어내고, 썰 때마다 삐끗하지 않았는지 테스트로 확인하며 한 걸음씩 나아가는 마이크로 스텝 진화 과정

## Ⅴ. 종류 및 비교

<details><summary>용어 설명</summary>

- **리팩터링 적용(Refactoring Application)**: 새로운 기능을 전혀 추가하지 않고, 오직 기존 코드의 가독성과 변경 용이성을 극대화하기 위해 테스트 커버리지 하에서 점진적으로 내부를 정리하는 행위이다.
- **기능 변경(Feature Change)**: 고객의 새로운 요구사항이나 버그 수정을 위해 기존의 외부 동작(인터페이스, 화면, DB 스키마 등)을 의도적으로 추가하거나 변형하는 개발 행위이다.
- **재작성(Rewrite)**: 기존 시스템의 구조가 너무 썩어 부분적 리팩터링으로는 도저히 회생이 불가능할 때, 기존 코드를 전부 폐기하고 새로운 아키텍처와 언어로 처음부터 다시 개발하는 최후의 수단이다.

</details>

| 코드 변경 방식 | **리팩터링 적용** | **기능 변경** | **재작성** |
|:---|:---|:---|:---|
| 적용 기준 | 외부 동작은 온전하며 향후 유지보수 비용을 낮춰야 할 때 | 명확한 비즈니스 신규 요구사항 수용 및 결함(Bug) 수정 시 | 기존 시스템의 기술 부채가 압도적이라 점진 개선이 절대 불가능할 때 |
| 핵심 특징 | 기능 추가 제로, 철저한 내부 구조 및 설계 품질만의 극대화 | 시스템의 외부 관찰 행위(기능) 추가 및 API 명세의 능동적 변경 | 기존 레거시 코드를 완전 폐기하고 스크래치(Scratch)부터 전면 재구축 |
| 한계 | 테스트 코드가 부실할 경우 심각한 회귀(Regression) 리스크 존재 | 무분별한 기능 추가 시 코드 악취 가중 및 기술 부채 누적 유발 | 엄청난 시간과 자본 소요, 전환 기간 중 비즈니스 요구사항 누락 위험 극대화 |

> 요약: 행위를 보존하며 구조만 닦는 것은 **리팩터링**, 행위를 추가하는 것은 **기능 변경**, 뼈대 자체를 갈아엎는 것은 **재작성**이다.

#### 한줄 요약
- 리팩터링 모자를 썼을 때는 기능 추가 유혹을 버리고 구조 정리에만 집중하며, 기능 모자를 썼을 때는 구조를 뒤엎지 말고 요구사항 구현에만 집중하는 '두 개의 모자' 철학

## Ⅵ. 실무 고려사항 및 대책

<details><summary>용어 설명</summary>

- **구조 변경 위험(Structural Change Risk)**: 든든한 테스트 하네스(Harness) 없이 개발자의 직관에만 의존해 무리하게 구조를 뜯어고치다가, 본인도 모르게 숨겨진 비즈니스 로직(엣지 케이스)을 망가뜨려 대형 장애를 유발하는 치명적 리스크이다.
- **특성화 테스트(Characterization Test)**: 사양서나 기획서가 없는 오래된 레거시 시스템에서 현재 코드가 "실제로 어떻게 작동하는가"에 대한 출력 결과 자체를 정답으로 간주하고, 이를 그대로 고정시키기 위해 작성하는 사후 테스트 기법이다.
- **추상화에 의한 분기(Branch by Abstraction)**: 대규모 리팩터링 시 한 번에 코드를 뒤집는 위험을 피하기 위해, 기존 코드와 새 코드를 동시에 감싸는 추상 인터페이스를 먼저 만들고 클라이언트들을 점진적으로 새 구현체로 갈아끼우는 안전한 마이그레이션 기법이다.
- **프로파일링(Profiling)**: 구조 개선을 핑계로 메모리나 CPU를 비효율적으로 사용하는 우아한 코드(예: 과도한 스트림 API 남용)를 작성하다가 성능 병목이 발생하지 않도록, 변경 전후의 리소스 사용량을 정밀하게 프로파일러 툴로 측정하고 벤치마킹하는 통제 수단이다.

</details>

| 문제 | 대책 | 효과 |
|:---|:---|:---|
| 테스트 코드 부재로 인한 심각한 **구조 변경 위험** | 리팩터링 전 **특성화 테스트** 필수 작성 및 마이크로 커밋 원칙 준수 | 조용한 비즈니스 로직 파손(Regression)을 즉각 탐지하여 서비스 장애 원천 차단 |
| 수개월이 걸리는 대규모 일괄(빅뱅) 리팩터링에 따른 통합 지옥 발생 | **추상화에 의한 분기** 적용을 통한 점진적 인터페이스 마이그레이션 | 신규 기능 개발을 중단하지 않으면서도 레거시 코드를 안전하고 조용히 교체 가능 |
| 구조적 우아함만 추구하다가 치명적인 성능 저하 및 응답 지연 발생 | 리팩터링 전후 마이크로 벤치마크 및 정밀한 런타임 **프로파일링** 데이터 비교 분석 | 무분별한 객체 생성이나 루프 분리로 인한 병목을 찾아내 성능과 설계의 균형 유지 |
| 명확한 목표 없는 완벽주의적 리팩터링 패턴의 과도한 남용 | 변경 이유가 명확한 코드(활성 코드)에만 제한적으로 패턴을 적용하고 팀 내 리팩터링 범위 합의 | 비즈니스 가치 창출과 무관한 맹목적 코드 다듬기로 인한 개발 자원 낭비 최소화 |

#### 한줄 요약
- 테스트 없이 코드를 고치는 것은 눈을 감고 수술하는 것과 같으므로, 반드시 특성화 테스트로 환자를 고정하고 추상화 분기로 리스크를 쪼개어 안전하게 수술하는 실무적 방어 체계

## Ⅶ. 결론

<details><summary>용어 설명</summary>

- **리팩터링 우선순위(Refactoring Priority)**: 무작정 눈에 띄는 모든 코드를 고치는 것이 아니라, 신규 기능 추가가 잦아 변경 비용이 지속적으로 발생하는 모듈 내의 고빈도 악취부터 타겟팅하여 투자 대비 효과(ROI)를 극대화하는 실용적 접근 기준이다.
- **점진적 리팩터링(Incremental Refactoring)**: 대규모 개편 프로젝트를 띄우는 대신, 매일의 일상적인 기능 개발 과정(보이스카우트 규칙) 속에서 작은 단위로 변환과 검증을 반복하며 실패 영향을 국소화하는 애자일(Agile)한 구조 개선 철학이다.

</details>
