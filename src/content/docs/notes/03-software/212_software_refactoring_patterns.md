## Ⅰ. 개요

<details><summary>용어 설명</summary>

- **리팩터링 (Refactoring)**: 소프트웨어의 외부 동작(Behavior)은 완벽히 보존하면서 가독성과 유지보수성을 극대화하기 위해 내부 구조를 개선하는 기법.
- **Code Smell (코드 악취)**: 당장 에러는 아니지만 거대 클래스, 긴 매개변수, 중복 코드 등 향후 결함과 기술 부채를 유발하는 나쁜 설계 징후.

</details>

- 정의/개념: 소프트웨어의 외부 동작은 변경하지 않고 **가독성, 유지보수성, 확장성을 높이기 위해 내부 코드 구조를 안전하게 재조정하는 설계 개선 기법**
- 배경/필요성: 코드 악취가 쌓이면 같은 기능을 고치는 데 드는 이해·수정·검증 비용이 변경마다 커지므로, 테스트가 외부 동작을 고정한 상태에서 기능 변경과 분리된 구조 개선 작업을 수행해 앞으로의 변경 단가를 낮출 필요

#### 한줄 요약
- 자동화 단위 테스트의 보호 아래 마이크로 스텝 패턴을 적용하여 외부 동작 보존과 내부 구조 개선을 달성한다.

## Ⅱ. 특징

<details><summary>용어 설명</summary>

- **Two Hats Principle (두 개의 모자)**: 기능 추가 작업과 리팩터링 작업을 동일한 커밋에 섞지 않고 명확히 분리하여 수행하는 원칙.
- **Characterization Test (특성화 테스트)**: 리팩터링 대상 레거시 코드의 현재 동작 상태를 스냅샷처럼 고정하여 회귀 결함을 방어하는 테스트.

</details>

- 기능 추가 모자와 리팩터링 모자를 철저히 분리하는 **2개의 모자(Two Hats) 원칙**
- 코드 악취와 1:1로 매핑되는 마틴 파울러의 **정형화된 변환 패턴 카탈로그 적용**
- 단위 테스트와 CI 파이프라인을 통한 **즉각적인 회귀 결함(Regression) 방어**

#### 한줄 요약
- 두 개의 모자 원칙, 정형 패턴 적용, 단위 테스트 회귀 검증을 통해 시스템 복잡도를 낮춘다.

## Ⅲ. 구조 및 구성요소

<details><summary>용어 설명</summary>

- **리팩터링 4대 핵심 구조**: Code Smell Detection(악취 탐지), Characterization Harness(동작 고정 테스트), Transformation Engine(패턴 변환), Verification(회귀 검증).

</details>

```text
[리팩터링 체계]
|-- 코드 악취
|-- 동작 계약
|-- 변환 패턴
`-- 회귀 검증기
```

선의 의미: 안전한 구조 개선을 이루는 정적 포함 관계

| 구성요소 | 책임 |
|:---|:---|
| **코드 악취** | 중복·강결합 등 개선 대상 식별 |
| **동작 계약** | 입출력·예외·상태 변경 고정 |
| **변환 패턴** | 검증된 **코드 조작 절차** 제공 |
| **회귀 검증기** | 구조 변경 후 **동작 보존** 입증 |

#### 한줄 요약
- 동작 계약을 테스트로 고정한 뒤에야 변환 패턴이 안전해지므로, 회귀 검증기가 없으면 리팩터링과 기능 변경이 결과적으로 구분되지 않는다.

## Ⅳ. 흐름도

<details><summary>용어 설명</summary>

- **리팩터링 5단계**: 특성화 테스트 작성 $\to$ 단일 악취 선택 $\to$ 작은 변환 적용 $\to$ 단위 테스트 회귀 검증 $\to$ 로컬 커밋 및 반복.

</details>

```text
1. 동작 고정
      |
2. 악취 선택
      |
3. 작은 변환
      |
   [테스트]
    /    \
 통과    실패
  |       |
4. 커밋  변환 취소
  |
[다음 악취 반복]
```

- 1. 동작 고정: **특성화 테스트** 작성
- 2. 악취 선택: 단일 **코드 악취** 지정
- 3. 작은 변환: 한 가지 **변환 패턴** 적용
- 4. 커밋: 테스트 통과 변환만 **분리 커밋**

#### 한줄 요약
- 변환 단위를 작게 쪼갤수록 검증 횟수는 늘지만 실패 시 되돌릴 범위가 한 커밋으로 제한되어 전체 위험 비용은 오히려 줄어든다.

## Ⅴ. 종류 및 비교

<details><summary>용어 설명</summary>

- **리팩터링 vs 기능 추가 vs 전면 재작성(Rewrite)**: 내부 구조만 개선(리팩터링), 외부 동작 변경(기능 추가), 스크래치 신규 개발(전면 재작성).

</details>

| 비교 항목 | 리팩터링 (Refactoring) | 기능 추가 및 변경 (Feature Change) | 전면 재작성 (Full Rewrite) |
|:---|:---|:---|:---|
| 핵심 작업 목표 | **외부 동작 보존, 내부 가독성/설계 극대화**| **새로운 API, 화면, 비즈니스 로직 추가** | **레거시를 폐기하고 새로운 아키텍처 구축** |
| 적용 가능 시점 | 상시 (보이스카우트 규칙 일상 실천) | 비즈니스 요구사항 발생 시 | 기술 부채 누적으로 점진 개선이 불가할 때 |
| 주요 위험 요소 | 테스트 부실 시 잠재적 회귀 결함 | 코드 악취 가중 및 기술 부채 누적 | **막대한 일정/비용 소요 및 전환 실패 위험** |
| 최적 적용 기준 | 운영 중인 서비스의 점진적 품질 향상 | 신규 기능 배포 및 버그 수정 | 아키텍처 패러다임 전면 전환 (모놀리스->MSA)|

#### 한줄 요약
- 내부 구조 개선은 리팩터링, 새 요구사항 구현은 기능 추가, 회생 불가 레거시는 전면 재작성을 적용한다.

## Ⅵ. 실무 고려사항 및 대책

<details><summary>용어 설명</summary>

- **Branch by Abstraction**: 대규모 리팩터링 시 빅뱅 배포를 피하기 위해 인터페이스를 먼저 생성하고 구현체를 점진 교체하는 기법.

</details>

| 문제 | 대책 | 효과 |
|:---|:---|:---|
| 테스트 코드 없이 리팩터링하다가 비즈니스 엣지 케이스 파손 | **리팩터링 전 기존 동작을 고정하는 `특성화 테스트` 선행 작성 의무화** | 비즈니스 로직 회귀 결함 100% 방지 |
| 수개월간 별도 브랜치에서 대규모 빅뱅 리팩터링 후 머지 지옥 | **`추상화에 의한 분기(Branch by Abstraction)` 기반 메인 트렁크 점진 배포**| 코드 충돌 및 배포 위험 제거 |
| 구조 개선 과다 추구로 무분별한 객체 생성에 따른 런타임 성능 저하 | **리팩터링 전후 APM 프로파일러 및 마이크로 벤치마크(JMH) 성능 비교** | 설계 품질과 런타임 성능 균형 확보 |
| 리팩터링과 신규 기능 추가가 한 커밋에 뒤섞여 리뷰 불가 | **'2개의 모자' 원칙을 준수하여 리팩터링 전용 PR 분리 제출** | 코드 리뷰 가독성 및 추적성 보장 |

#### 한줄 요약
- 네 대책은 구조 개선의 이득이 회귀 결함이나 성능 저하로 상쇄되지 않도록 검증 비용을 작업 이전으로 앞당겨 치르는 선택이다.

## Ⅶ. 결론

- 동작 계약이 있으면 **점진 리팩터링**, 없으면 특성화 테스트 선행

#### 한줄 요약
- 리팩터링은 외부 동작을 보존하면서 내부 구조를 안전하게 개선하는 핵심 엔지니어링 실천법이다.
