## Ⅰ. 개요

<details><summary>용어 설명</summary>

- **소프트웨어 리팩터링(Software Refactoring)**: 소프트웨어가 제공하는 외부 동작(External Behavior)과 비즈니스 계약은 완벽히 보존하면서, 내부 코드 구조와 설계만을 점진적이고 체계적으로 개선하여 가독성과 유지보수성을 극대화하는 엔지니어링 기법.
- **코드 악취(Code Smell)**: 당장 컴파일 에러나 런타임 버그를 일으키지는 않지만, 거대 클래스(God Class), 긴 매개변수 목록, 중복 로직 등 향후 변경 시 결함과 기술 부채를 가중시키는 나쁜 설계 징후.

</details>

- 정의/개념: 소프트웨어의 외부 동작은 변경하지 않고 **가독성, 유지보수성, 확장성을 높이기 위해 내부 코드 구조를 재조정하는 설계 개선** 기법
- 배경/필요성: 스파게티 코드, 중복 로직, 거대 클래스 등 **코드 악취(Code Smell) 누적으로 인한 기능 추가 지연 및 결함 급증 위험** 직면

#### 한줄 요약

- 자동화된 단위 테스트(Test Harness)의 보호 아래 작은 카탈로그 패턴을 단계적으로 적용하여 외부 동작 보존과 내부 구조 개선을 동시 달성

## Ⅱ. 특징

<details><summary>용어 설명</summary>

- **외부 동작 계약 보존(External Behavior Preservation)**: 입력, 출력, 상태 전이, 예외 처리 등 클라이언트가 관찰 가능한 모든 행위를 100% 동일하게 유지하는 리팩터링의 절대 전제.
- **메서드 추출(Extract Method)**: 하나의 함수에 뒤섞인 복잡한 로직의 일부분을 의도가 명확한 이름을 가진 독립된 메서드로 분리하는 가장 기본적 리팩터링 패턴.

</details>

- 기능 추가 모자와 리팩터링 모자를 철저히 분리하는 **2개의 모자(Two Hats) 원칙**
- 코드 악취(Code Smell)와 1:1로 매핑되는 마틴 파울러의 **정형화된 변환 패턴 카탈로그 적용**
- 단위 테스트와 CI 파이프라인을 통한 **즉각적인 회귀 결함(Regression) 방어** #### 한줄 요약

- 외부 동작 보존, 마이크로 스텝 변환, 단위 테스트 회귀 검증을 통해 시스템 위험 없이 코드 품질을 혁신

## Ⅲ. 구조 및 구성요소

<details><summary>용어 설명</summary>

- **리팩터링 4대 아키텍처 체계**: Code Smell(개선 대상), Behavior Contract(동작 보존 기준), Transformation Catalog(변환 패턴), Regression Harness(단위 테스트 스위트).

</details>

```text
[ 소프트웨어 리팩터링 프레임워크 및 안전망 구조도 ]

 1. [ 코드 악취 식별 계층 (Code Smell Target) ]
    ┌─────────────────────────────────────────────────────────────┐
    │  • Long Method, Large Class, Duplicated Code, Feature Envy │
    └────────────────────────────┬────────────────────────────────┘
                                 │
                                 ▼
 2. [ 동작 계약 고정 계층 (Behavior Contract: Test Harness) ] ───┐
    • 단위 테스트(JUnit), 특성화 테스트(Characterization Test)    │
    └────────────────────────────┬────────────────────────────────┘
                                 │ (안전망 확보 후 변환)
                                 ▼
 3. [ 정형 변환 패턴 계층 (Transformation Catalog) ] ────────────┐
    • 메서드 추출(Extract Method) ➔ 클래스 분리(Extract Class)   │
    • 조건문 다형성 치환(Replace Conditional with Polymorphism)   │
    └────────────────────────────┬────────────────────────────────┘
                                 │ (변환 직후 즉각 실행)
                                 ▼
 4. [ 회귀 검증 및 커밋 계층 (Regression Verification & Commit) ]
    • CI 파이프라인 자동 테스트 Pass ➔ 마이크로 로컬 커밋
```

선의 의미: 코드 악취를 식별하고 특성화 테스트로 동작을 고정한 뒤 변환 패턴을 적용하여 회귀 테스트를 거쳐 커밋하는 구조.

| 구성요소 | 책임 |
|:---|:---|
| 코드 악취 (Code Smell) | 가독성과 유지보수성을 저해하는 **중복, 결합도, 거대 클래스 등 개선 대상 식별** |
| 동작 계약 (Contract) | 리팩터링 전후로 변하지 않아야 하는 **입출력, 예외, 상태 변경 스펙을 명문화** |
| 변환 패턴 (Patterns) | 메서드 추출, 함수 이동, 인터페이스 추출 등 **검증된 안전한 코드 조작 절차 제공** |
| 회귀 검증기 (Harness) | 자동화 단위 테스트를 실행하여 **구조 변경 후에도 비즈니스 로직의 무결성 입증** |

#### 한줄 요약

- 코드 악취, 동작 계약, 변환 패턴, 회귀 검증기가 결합하여 안전한 리팩터링 사이클을 완성

## Ⅳ. 흐름도

<details><summary>용어 설명</summary>

- **리팩터링 5단계 마이크로 수명주기**: 특성화 테스트 고정 $\to$ 악취 선택 $\to$ 단일 패턴 변환 $\to$ 회귀 테스트 실행 $\to$ 로컬 커밋 및 반복.

</details>

```text
[ 점진적 소프트웨어 리팩터링 파이프라인 ]

 ┌────────────────────────────────────────┐
 │ 1. 특성화 테스트 작성으로 현재 동작 고정│
 └───────────────────┬────────────────────┘
                     │
                     ▼
 ┌────────────────────────────────────────┐
 │ 2. 리팩터링할 단일 코드 악취(Smell) 선택│
 └───────────────────┬────────────────────┘
                     │
                     ▼
 ┌────────────────────────────────────────┐
 │ 3. 단일 리팩터링 패턴 적용 (작은 변환) │
 └───────────────────┬────────────────────┘
                     │
                     ▼
 ┌────────────────────────────────────────┐
 │ 4. 자동화 단위 테스트 회귀 검증 실행  │
 ├───────────────────┬────────────────────┤
 │ 테스트 실패 (Red) │ 테스트 통과 (Green)│
 │ • 즉각 롤백(Undo) │ • 다음 단계 진행   │
 └───────────────────┴────────────────────┘
                     │
                     ▼
 ┌────────────────────────────────────────┐
 │ 5. 로컬 커밋 및 잔여 악취 반복 개선   │
 └────────────────────────────────────────┘
```

### 동작 원리

1. 동작 고정: 2,000라인짜리 주문 정산 클래스의 입출력과 엣지 케이스를 검증하는 특성화 테스트 20개를 작성.
2. 악취 선택: 5단계 중첩 if-else문이 포함된 '복잡한 할인 조건문' 악취를 1차 개선 대상으로 지정.
3. 작은 변환: IDE 리팩터링 도구로 할인 계산 로직을 `calculateDiscount()` 독립 메서드로 1차 추출.
4. 회귀 검증: 단위 테스트를 즉시 실행하여 20개 테스트가 0.2초 만에 모두 Green으로 통과함을 확인.
5. 커밋 및 반복: 마이크로 로컬 커밋을 수행한 후, 다음 단계로 Strategy 패턴 기반 다형성 치환을 적용.

#### 한줄 요약

- 동작 고정 $\to$ 악취 선택 $\to$ 작은 변환 $\to$ 회귀 검증 $\to$ 로컬 커밋의 5단계

## Ⅴ. 종류 및 비교

<details><summary>용어 설명</summary>

- **리팩터링 vs 기능 추가 vs 전면 재작성(Rewrite)**: 구조만 개선(리팩터링), 외부 동작 변경(기능 추가), 스크래치 전면 신규 구축(재작성).

</details>

| 구분 | 리팩터링 (Refactoring) | 기능 추가 및 변경 (Feature Change) | 전면 재작성 (Full Rewrite) |
|:---|:---|:---|:---|
| **적용 기준** | 외부 동작은 정상이나 코드 복잡도로 유지보수가 어려울 때 | 새로운 고객 비즈니스 요구사항이나 버그를 수정할 때 | 기술 부채가 압도적이어서 점진적 개선이 불가능할 때 |
| **핵심 특징** | **외부 동작 100% 보존, 내부 코드 구조 및 설계 품질 극대화** | **새로운 API, 화면, 비즈니스 로직 추가 및 기능 명세 변경** | **기존 레거시 코드를 폐기하고 새로운 아키텍처로 스크래치 개발** |
| **한계** | 테스트 코드가 부실할 경우 잠재적 회귀 결함 발생 위험 | 무분별한 추가 시 코드 악취 가중 및 기술 부채 누적 유발 | 막대한 비용·시간 소요 및 전환 기간 중 비즈니스 갭 발생 |

#### 한줄 요약

- 내부 구조만 개선은 리팩터링, 새 요구사항 구현은 기능 추가, 회생 불가 레거시는 전면 재작성을 적용

## Ⅵ. 실무 고려사항 및 대책

<details><summary>용어 설명</summary>

- **추상화에 의한 분기(Branch by Abstraction)**: 대규모 리팩터링 시 빅뱅 배포의 위험을 피하기 위해 기존 컴포넌트와 신규 컴포넌트를 아우르는 인터페이스를 먼저 생성하고 점진 전환하는 기법.

</details>

| 문제 | 대책 | 효과 |
|:---|:---|:---|
| 테스트 코드 없이 리팩터링을 감행하다가 잠재된 비즈니스 엣지 케이스 파손 | **리팩터링 전 기존 동작을 고정하는 `특성화 테스트` 선행 작성 의무화** | 비즈니스 로직 회귀 결함 100% 방지 |
| 수개월간 별도 브랜치에서 대규모 빅뱅 리팩터링을 진행하다가 머지 지옥 | **`추상화에 의한 분기(Branch by Abstraction)` 기반 메인 트렁크 점진 배포** | 코드 충돌 및 배포 위험 제거 |
| 구조 개선을 과도하게 추구하다가 무분별한 객체 생성으로 런타임 성능 저하 | **리팩터링 전후 APM 프로파일러 및 마이크로 벤치마크(JMH) 성능 비교** | 설계 품질과 런타임 성능의 균형 확보 |

#### 한줄 요약

- 특성화 테스트 선행, 추상화 분기 적용, 성능 벤치마크 검증을 통해 리팩터링의 실효성을 보장

## Ⅶ. 결론

<details><summary>용어 설명</summary>

- **보이스카우트 규칙(Boy Scout Rule)**: "캠프장을 떠날 때는 처음 왔을 때보다 더 깨끗하게 치워라"는 격언처럼, 코드를 수정할 때마다 주변의 작은 악취를 조금씩 개선해 나가는 지속적 리팩터링 문화.

</details>

- **소프트웨어 리팩터링** 기술 부채를 통제하고 시스템의 수명을 연장하는 가장 핵심적인 일상 엔지니어링 실천이며, 견고한 테스트 하네스와 보이스카우트 규칙을 팀 문화로 정착시켜 점진적이고 안전한 코드 품질 진화를 완성해야 함

#### 한줄 요약

- 외부 동작 보존 원칙과 테스트 기반 마이크로 스텝 변환을 통해 지속 가능한 클린 코드를 완성
