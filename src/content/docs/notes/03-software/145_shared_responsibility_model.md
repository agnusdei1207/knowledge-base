## Ⅰ. 개요

<details><summary>용어 설명</summary>

- **클라우드 공유 책임 모델(Shared Responsibility Model)**: 클라우드 서비스 제공자(CSP)와 고객(Customer) 간의 보안, 규제 준수, 시스템 운영 영역에 대한 책임 경계를 명확히 정의한 프레임워크.
- **Security OF the Cloud vs Security IN the Cloud**: CSP는 클라우드 자체의 물리 인프라 및 가상화 보안(OF)을 책임지고, 고객은 클라우드 내부의 데이터, 계정(IAM), OS 패치, 방화벽 설정(IN)을 책임지는 핵심 원칙.

</details>

- 정의/개념: 클라우드 환경에서 보안과 거버넌스 공백을 방지하기 위해 **CSP(Cloud 자체의 보안)와 고객(Cloud 내부의 보안)의 책임 한계를 규정**한 운영 프레임워크
- 배경/필요성: 클라우드 도입 시 인프라 관리가 위탁됨에 따라 발생하는 **데이터 보호 및 IAM 권한 설정 책임 주체 오인과 보안 통제 공백 위험** 직면

#### 한줄 요약

- CSP의 인프라 보안과 고객의 데이터/설정 보안 책임을 명확히 구분하여 보안 사각지대를 방지

## Ⅱ. 특징

<details><summary>용어 설명</summary>

- **Security OF the Cloud(CSP 영역)**: 데이터센터 물리 보안, 서버 하드웨어, 스토리지, 전력/공조, 하이퍼바이저 가상화 계층.
- **Security IN the Cloud(고객 영역)**: 고객 데이터 암호화, IAM 계정/MFA, OS 보안 패치, 네트워크 방화벽(Security Group) 설정.

</details>

- 물리 시설과 가상화 계층을 CSP가 전담하는 **Security OF the Cloud 책임**
- 데이터 암호화, 계정 통제, 방화벽을 고객이 전담하는 **Security IN the Cloud 책임**
- IaaS에서 PaaS, SaaS로 갈수록 고객 책임이 CSP로 이관되는 **서비스 모델별 가변 경계**

#### 한줄 요약

- 서비스 모델(IaaS/PaaS/SaaS)에 따라 가변적으로 이동하는 보안 책임 경계를 정밀하게 관리

## Ⅲ. 구조 및 구성요소

<details><summary>용어 설명</summary>

- **공유 책임 매트릭스 계층**: 고객 영역(데이터, IAM, 앱, OS 패치)과 CSP 영역(물리 데이터센터, 하이퍼바이저, 글로벌 인프라).

</details>

```text
[ 클라우드 공유 책임 모델(Shared Responsibility) 구조도 ]

 ┌────────────────────────────────────────────────────────────────────────┐
 │ 1. 고객 책임 (Security IN the Cloud)                                   │
 │   - 고객 데이터 자산 및 암호화 (KMS)                                  │
 │   - 플랫폼 및 IAM 계정 권한 통제 (MFA, 최소 권한)                      │
 │   - 운영체제(OS) 패치, 네트워크 방화벽(Security Group) 설정            │
 ├────────────────────────────────────────────────────────────────────────┤
 │ ────────────── 서비스 모델별 책임 이동 경계선 (IaaS / PaaS / SaaS) ─────│
 ├────────────────────────────────────────────────────────────────────────┤
 │ 2. CSP 책임 (Security OF the Cloud)                                    │
 │   - 컴퓨팅, 스토리지, 데이터베이스 기본 서비스 소프트웨어 관리         │
 │   - Hypervisor 가상화 레이어 및 네트워크 인프라                        │
 │   - AWS/GCP 글로벌 데이터센터 물리 시설, 서버 랙, 전력, 공조 보안      │
 └────────────────────────────────────────────────────────────────────────┘
```

선의 의미: 상단의 고객 통제 영역과 하단의 CSP 인프라 통제 영역을 서비스 모델별로 분계하는 구조.

| 구성요소 | 책임 |
|:---|:---|
| 고객 데이터 및 IAM (IN) | 데이터 암호화, 접근 통제(RBAC/ABAC), **루트 계정 MFA 및 최소 권한 부여 전담** |
| 애플리케이션 및 OS (IN) | IaaS 가상머신의 **OS 보안 패치, 미들웨어 설정 및 애플리케이션 취약점 조치** |
| 가상화 및 플랫폼 (OF) | 하이퍼바이저 격리, 관리형 PaaS 런타임, **스토리지 결함 허용성 및 패치 제공** |
| 물리 데이터센터 (OF) | 전 세계 리전 및 가용 영역(AZ)의 **물리 출입 통제, 전력, 공조, 하드웨어 파기** |

#### 한줄 요약

- 고객 책임(IN)과 CSP 책임(OF)이 서비스 계층 경계를 중심으로 명확히 분리

## Ⅳ. 흐름도

<details><summary>용어 설명</summary>

- **공유 책임 모델 수립 5단계 절차**: 서비스 모델 식별 $\to$ 관리 계층 분해 $\to$ 책임 주체 배정 $\to$ 통제 증적 매핑 $\to$ 책임 공백 점검.

</details>

```text
[ 클라우드 공유 책임 모델 적용 및 검증 파이프라인 ]

 ┌────────────────────────────────────────┐
 │ 1. 클라우드 서비스 모델(I/P/S) 식별    │
 └───────────────────┬────────────────────┘
                     │
                     ▼
 ┌────────────────────────────────────────┐
 │ 2. 인프라 스택 관리 계층별 분해       │
 └───────────────────┬────────────────────┘
                     │
                     ▼
 ┌────────────────────────────────────────┐
 │ 3. 고객 vs CSP 책임 주체 배정 (RACI)   │
 └───────────────────┬────────────────────┘
                     │
                     ▼
 ┌────────────────────────────────────────┐
 │ 4. 보안 통제 도구(CSPM/KMS) 및 증적 연결
 └───────────────────┬────────────────────┘
                     │
                     ▼
 ┌────────────────────────────────────────┐
 │ 5. 책임 공백 및 설정 오류(Misconfig) 점검
 └────────────────────────────────────────┘
```

### 동작 원리

1. 모델 식별: 도입하려는 서비스가 IaaS(EC2)인지, PaaS(RDS)인지, SaaS(Workspace)인지 분류.
2. 계층 분해: 시설, 하드웨어, 가상화, OS, 미들웨어, 데이터 등 스택 계층을 세분화.
3. 주체 배정: 각 계층의 관리 및 패치 주체를 고객 또는 CSP로 명확히 지정(RACI 매트릭스).
4. 도구 연결: 고객 책임 영역에 대해 AWS KMS(암호화), GuardDuty(위협 탐지), CSPM 도구를 연결.
5. 공백 점검: S3 퍼블릭 오픈, 보안 그룹 애니웨어(0.0.0.0/0) 허용 등 책임 공백과 설정 오류를 검사.

#### 한줄 요약

- 모델 식별 $\to$ 계층 분해 $\to$ 주체 배정 $\to$ 도구 연결 $\to$ 공백 점검의 5단계

## Ⅴ. 종류 및 비교

<details><summary>용어 설명</summary>

- **IaaS vs PaaS vs SaaS 책임 비교**: 모델별 고객과 CSP의 관리 책임 이전 범위 비교.

</details>

| 구분 | IaaS (인프라 서비스) | PaaS (플랫폼 서비스) | SaaS (소프트웨어 서비스) |
|:---|:---|:---|:---|
| **적용 기준** | EC2, Compute Engine 가상머신 | RDS, Elastic Beanstalk 관리형 | Salesforce, Microsoft 365 |
| **핵심 특징** | **고객이 OS 패치부터 데이터까지 직접 통제** | **CSP가 OS/런타임 관리, 고객은 코드/데이터 관리** | **CSP가 인프라 전담, 고객은 계정/데이터 관리** |
| **한계** | OS 보안 패치 및 방화벽 설정 오버헤드 과다 | 특정 플랫폼 런타임 제약 및 커스터마이징 한계 | 내부 시스템 세부 보안 감사 증적 직접 확인 불가 |

#### 한줄 요약

- IaaS는 OS부터 고객 책임, PaaS는 코드/데이터만 고객 책임, SaaS는 계정/데이터만 고객 책임

## Ⅵ. 실무 고려사항 및 대책

<details><summary>용어 설명</summary>

- **CSPM (Cloud Security Posture Management)**: 클라우드 환경의 잘못된 보안 설정(S3 Public Open, 과도한 권한)을 실시간 자동 탐지하고 교정하는 보안 도구.

</details>

| 문제 | 대책 | 효과 |
|:---|:---|:---|
| S3 버킷 퍼블릭 오픈 클릭 실수로 인한 대규모 데이터 유출 | **AWS S3 Block Public Access 전사 강제 및 CSPM(Wiz) 실시간 감시** | 설정 오류 기반 데이터 유출 원천 차단 |
| IaaS EC2 인스턴스 OS 보안 패치 누락으로 인한 악성코드 침투 | **AWS Systems Manager (SSM) Patch Manager 정기 자동화 구축** | 무중단 정기 보안 패치 100% 달성 |
| Root 계정 및 AccessKey 유출로 인한 비인가 리소스 생성 | **Root 계정 사용 금지, 전 임직원 MFA 의무화 및 90일 키 회전** | 비인가 크리덴셜 탈취 무력화 |

#### 한줄 요약

- S3 퍼블릭 차단, SSM 자동 패치, MFA 및 키 회전을 통해 고객 책임 영역의 보안을 완벽히 통제

## Ⅶ. 결론

<details><summary>용어 설명</summary>

- **클라우드 보안 거버넌스 프레임워크(Cloud Security Governance)**: CSP의 SOC 1/2/3 인증 보고서와 고객의 CSPM/CIEM 설정을 통합하여 전사 컴플라이언스를 달성하는 체계.

</details>

- **클라우드 공유 책임 모델**은 클라우드 보안의 출발점이자 가장 중요한 기본 원칙이며, 서비스 모델에 따른 책임 분계를 명확히 인식하고 CSPM과 IAM 최소 권한을 통해 고객 영역의 보안 통제력을 확립해야 함

#### 한줄 요약

- 고객 책임(IN)과 CSP 책임(OF)의 경계를 준수하여 클라우드 전반의 보안과 가용성을 완성
