## Ⅰ. 개요

<details><summary>용어 설명</summary>

- **도메인 주도 설계(Domain-Driven Design, DDD)**: 기술이나 DB 스키마 중심이 아니라, 찐 비즈니스 룰(도메인)을 한가운데 짱박아두고 기획자부터 개발자까지 다 똑같은 생각으로 코드를 짜는 철학이다.
- **보편적 언어(Ubiquitous Language)**: 기획자는 '주문취소', 개발자는 `DeleteOrder`라고 따로 노는 환장할 짓을 멈추고, 회의실부터 소스코드 클래스명까지 100% 동일한 단어(ex. `cancelOrder`)를 쓰자는 팩폭 원칙이다.
- **전략적/전술적 설계(Strategic vs Tactical Design)**: '주문', '결제'처럼 덩어리(경계)를 크게 쪼개는 숲을 보는 설계가 전략적(Strategic), 그 안에서 Entity나 VO 같은 객체를 깎는 나무를 보는 설계가 전술적(Tactical) 설계이다.

</details>

- 정의: 기술 겉멋(DB/프레임워크) 다 치우고, 현업의 찐 비즈니스 로직(도메인)을 보편적 언어(Ubiquitous Language)로 깎아서 코드에 그대로 때려 박는 설계 철학인 **DDD (Domain-Driven Design)**
- 배경: 요구사항 문서랑 실제 코드가 다르면, 나중에 기획자가 룰을 바꿨을 때 **개발자가 "그거 구조상 안 되는데요?" 시전하며 프로젝트가 망하기** 때문

#### 한줄 요약

- DB나 프레임워크 핑계 대지 말고, 진짜 비즈니스 룰을 기획자 용어 그대로 코드에 박아 넣는 철학이다.

## Ⅱ. 특징

<details><summary>용어 설명</summary>

- **바운디드 컨텍스트(Bounded Context)**: '상품'이라는 단어가 물류팀엔 '부피/무게'지만 판매팀엔 '가격/할인율'이듯, 같은 단어라도 의미가 달라지는 '동네(문맥)'의 확실한 울타리(경계)이다.
- **컨텍스트 맵(Context Map)**: 바운디드 컨텍스트들끼리 "주문팀이 결제 API를 쓴다" 같은 갑을 관계나 의존성 지도를 그려놓은 전체 조감도이다.

</details>

- 개발자와 기획자가 뇌를 동기화하는 **보편적 언어(Ubiquitous Language)** 수립이 0순위임.
- 도메인을 찢는 **전략적 설계(Strategic)**로 마이크로서비스(MSA)를 나누는 절대적 기준을 제시함.
- 객체를 깎는 **전술적 설계(Tactical)** 패턴(Entity, VO, Aggregate)으로 스파게티 코드를 방어함.

#### 한줄 요약

- 다 같이 같은 말 쓰고(보편적 언어), 구역을 나누고(전략적), 객체를 야무지게 깎는(전술적) 게 핵심이다.

## Ⅲ. 구조 및 구성요소

<details><summary>용어 설명</summary>

- **애그리게이트(Aggregate & Aggregate Root)**: '주문'과 '주문 상세'처럼 생사고락을 함께하는 객체 묶음(Aggregate)과, 밖에서 함부로 내부를 건드리지 못하게 문지기 역할을 하는 대빵 객체(Aggregate Root)이다.
- **엔티티 vs 값 객체(Entity vs Value Object)**: '고객'처럼 이름이 바뀌어도 동일 인물인 식별자(ID)가 있는 놈이 엔티티(Entity), '주소'처럼 글자 하나만 달라도 아예 다른 놈 취급하는 불변 객체가 VO이다.

</details>

```text
[ DDD 십자포화 아키텍처 트리 ]

[ 전사 도메인 ] ──▶ (숲 보기: 전략적 설계)
       │
       ├─ [ 바운디드 컨텍스트 A (주문) ] ◀──(컨텍스트 맵)──▶ [ 바운디드 컨텍스트 B (결제) ]
       │          │
       │          ▼ (나무 보기: 전술적 설계)
       │       [ 애그리게이트 루트 (주문) ] ──▶ [ 엔티티 (주문상세) ]
       │          │                             │
       │          ▼                             ▼
       │       [ 값 객체 (주소 VO) ]         [ 값 객체 (금액 VO) ]
```

| 구성요소 | 팩트 폭행 책임 |
|:---|:---|
| **하위 도메인** | 회사가 돈 버는 핵심(Core), 보조(Supporting), 외부 도메인으로 덩어리 분류 |
| **바운디드 컨텍스트** | 모델과 용어가 꼬이지 않게 울타리(경계)를 쳐서 MSA 서비스 단위를 찢음 |
| **공통 언어 (Ubiquitous)**| 기획자 입에서 나온 용어를 토씨 하나 안 틀리고 소스 코드에 박음 |
| **도메인 모델** | 비즈니스 룰과 상태를 Entity, VO, Aggregate로 캡슐화해서 코드로 번역함 |

#### 단답 요약

- 전략(바운디드 컨텍스트)으로 구역을 나누고, 전술(애그리게이트, 엔티티, VO)로 내부를 깎는다.

## Ⅳ. 흐름도

<details><summary>용어 설명</summary>

- **이벤트 스토밍(Event Storming)**: DDD 하겠다고 다 같이 회의실에 모여, 주황색 포스트잇에 '주문됨', '결제됨' 같은 이벤트를 시간순으로 벽에 미친 듯이 붙이면서 바운디드 컨텍스트를 도출하는 쌉가성비 워크숍이다.

</details>

```text
[ DDD 설계 십자포화 흐름 ]
┌──────────────────────────────┐
│ 1. Event Storming 워크숍     │
│ (포스트잇 벽에 붙이며 룰 찾기)│
└──────────────┬───────────────┘
               ▼
┌──────────────────────────────┐
│ 2. 보편적 언어(Ubiquitous)   │
│ (기획자-개발자 용어 통일)    │
└──────────────┬───────────────┘
               ▼
┌──────────────────────────────┐
│ 3. 전략적 설계 (경계 찢기)   │
│ (바운디드 컨텍스트 도출)     │
└──────────────┬───────────────┘
               ▼
┌──────────────────────────────┐
│ 4. 전술적 설계 (객체 깎기)   │
│ (Entity, VO, Aggregate 코딩) │
└──────────────┬───────────────┘
               ▼
┌──────────────────────────────┐
│ 5. 도메인 모델 구현 완료     │
└──────────────────────────────┘
```

### 동작 원리

1. 도메인 탐색: 이벤트 스토밍으로 벽에 포스트잇을 붙여가며 업무 흐름을 싹 다 털어냄.
2. 언어 통일: 회의하며 나온 용어들을 사전으로 만들어 코드 변수명까지 박제함.
3. 경계 설정(전략): 큰 덩어리를 찢어서 바운디드 컨텍스트(MSA 서비스 단위)를 나눔.
4. 객체 모델링(전술): 찢어놓은 동네 안에서 Aggregate 대빵을 찾고 내부 엔티티를 설계함.
5. 코드 구현: 비즈니스 룰을 품은 리치(Rich)한 도메인 객체를 완성함.

#### 한줄 요약

- 포스트잇(이벤트 스토밍) $\to$ 단어 통일 $\to$ 구역 나누기 $\to$ 객체 코딩 순서로 진행된다.

## Ⅴ. 종류 및 비교

<details><summary>용어 설명</summary>

- **빈혈 도메인 모델(Anemic Domain Model)**: 객체 안에 로직은 1도 없고 `getter/setter`만 덜렁 있는 깡통(DTO)으로 만들어 놓고, 비즈니스 룰은 외부 Service 클래스의 `if-else`에 다 짬처리한 붕괴 상태이다.

</details>

| 비교 항목 | **빈혈 도메인 모델 (Anemic)** | **풍부한 도메인 모델 (Rich/DDD)** |
|:---|:---|:---|
| 상태/행위 | 상태(Data)는 객체에, 행위(Logic)는 Service에 찢어짐 | **상태와 행위를 Entity가 다 품음 (캡슐화)** |
| 비즈니스 유효성| Service 클래스가 `if-else`로 수동 검사함 | **Entity/VO 스스로 검증 로직을 내장함** |
| 객체 변경 안전성| 외부에서 `setter`로 아무나 데이터 조작함 | **`setter` 박살 내고 도메인 메서드로만 바꿈** |

#### 한줄 요약

- 깡통 객체(빈혈) 쓰면 로직이 사방에 흩어지고, 꽉 찬 객체(리치) 쓰면 로직이 예쁘게 뭉친다.

## Ⅵ. 실무 고려사항 및 대책

<details><summary>용어 설명</summary>

- **안티 코럽션 레이어(ACL, Anti-Corruption Layer)**: 남이 짠 쓰레기 레거시 시스템의 오물(구조)이 내 예쁜 도메인으로 넘어오지 못하게, 중간에서 예쁘게 번역/세탁해 주는 짬처리 방파제이다.

</details>

| 문제 | 대책 | 효과 |
|:---|:---|:---|
| 썩은 레거시 API 규격이 내 새삥 도메인을 오염시킴 | 중간에 **안티 코럽션 레이어(ACL)** 번역기 박아둠 | 레거시의 더러운 구조가 전파되는 걸 원천 차단 |
| Entity에 무지성 `setter` 달아서 데이터 멋대로 바뀜 | **`setter` 싹 지우고** 의미 있는 비즈니스 메서드만 개방 | 도메인 불변성(Invariant)과 객체 캡슐화 사수 |
| 단순 게시판 CRUD인데 DDD 박아서 파일만 100개 됨 | 닭 잡는 데 소 잡는 칼 쓰지 말고 걍 **CRUD** 짬 | 겉멋(오버엔지니어링)으로 팀원들 피눈물 흘리기 방지 |

#### 한줄 요약

- 레거시 똥은 ACL로 막고, 객체 `setter`는 다 지워버리며, 단순 게시판엔 절대 DDD 쓰지 마라.

## Ⅶ. 결론

<details><summary>용어 설명</summary>

- **DDD 도입 판정 기준(DDD Adoption Standards)**: 비즈니스 룰이 지독하게 복잡해서(금융, 정산) MSA로 찢어야 할지, 걍 단순 DB 껍데기(CRUD)인지 각 재서 DDD 지옥에 빠질지 정하는 잣대이다.

</details>

- **DDD 도입 판정 기준** 원칙에 따라, 돈 버는 핵심 코어 도메인은 **DDD (풍부한 모델)**, 남들 다 쓰는 일반 도메인은 걍 **단순 CRUD** 채택 기조 확립함

#### 한줄 요약

- 쇼핑몰 정산/결제 같은 '돈 버는 핵심 로직'에만 써야 하는 비싸고 강력한 무기다.
