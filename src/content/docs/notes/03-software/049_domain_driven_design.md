## Ⅰ. 개요

<details><summary>용어 설명</summary>

- **도메인 주도 설계(DDD, Domain-Driven Design)**: 소프트웨어의 복잡성을 비즈니스 도메인 지식을 코드에 명시적으로 반영함으로써 제어하는 설계 철학으로, Eric Evans가 체계화.
- **보편적 언어(Ubiquitous Language)**: 도메인 전문가와 개발자가 동일한 용어를 사용하여 소통하고 해당 용어를 소스 코드의 클래스명·메서드명에도 일관되게 반영하는 언어 통일 원칙.
- **전략적/전술적 설계(Strategic vs Tactical Design)**: 시스템 전체의 도메인 경계를 정의하는 전략적 설계와 경계 내부의 도메인 객체를 설계하는 전술적 설계의 구분.

</details>

- 정의/개념: 비즈니스 도메인 지식을 보편적 언어로 표현하고 코드에 직접 반영하여 시스템 복잡도를 제어하는 **DDD(Domain-Driven Design)**
- 배경/필요성: 요구사항 문서와 코드가 괴리되면 도메인 변경 시 코드 파악이 불가능해지므로, **비즈니스 도메인 중심의 일관된 언어와 모델 체계 필수**

#### 한줄 요약

- 비즈니스 도메인을 보편적 언어로 코드에 반영하고 전략·전술 설계로 복잡도를 체계적으로 제어

## Ⅱ. 특징

<details><summary>용어 설명</summary>

- **바운디드 컨텍스트(Bounded Context)**: 동일 용어가 다른 의미를 갖는 도메인 경계로, 문맥 내에서 모델의 일관성을 보장하는 명시적 경계.
- **컨텍스트 맵(Context Map)**: 바운디드 컨텍스트 간 의존 관계·통합 방식을 시각화하는 전체 시스템 조감도.

</details>

- **보편적 언어** 수립으로 도메인 전문가와 개발자의 언어 괴리 해소
- **전략적 설계**로 바운디드 컨텍스트 경계를 도출하여 MSA 서비스 분리 기준 제공
- **전술적 설계** 패턴(Entity·VO·Aggregate)으로 도메인 모델의 캡슐화 및 불변 조건 보호

#### 한줄 요약

- 보편적 언어로 소통 격차를 해소하고 전략적 경계와 전술적 객체 설계로 도메인 복잡도를 제어

## Ⅲ. 구조 및 구성요소

<details><summary>용어 설명</summary>

- **애그리게이트(Aggregate & Root)**: 생명 주기를 공유하는 도메인 객체 묶음과 외부에서 해당 묶음에 접근하는 단일 진입점(Aggregate Root).
- **엔티티 vs 값 객체(Entity vs Value Object)**: 고유 식별자로 동일성을 판단하는 엔티티와 속성 값의 동등성으로 판단하며 불변인 값 객체(VO)의 구분.

</details>

```text
[ DDD 설계 계층 구조 ]
전사 도메인 (Strategic Design)
├─ 바운디드 컨텍스트 A (주문)
│    │ 컨텍스트 맵 (의존 방향)
│    └─ 바운디드 컨텍스트 B (결제)
│
전술적 설계 (Tactical Design) - 컨텍스트 A 내부
├─ 애그리게이트 루트 (주문)
│    ├─ 엔티티 (주문상세)
│    └─ 값 객체 (금액 VO)
└─ 도메인 서비스·레포지토리
```

선의 의미: 가지(`├─`, `└─`)는 컨텍스트 경계 내부의 객체 소유 관계, 컨텍스트 맵의 화살표는 바운디드 컨텍스트 간 의존 방향

| 구성요소 | 책임 |
|:---|:---|
| **바운디드 컨텍스트** | 모델 일관성 보장 경계·MSA 서비스 분리 단위 |
| **보편적 언어** | 기획자·개발자 공통 용어를 코드에 일관 반영 |
| **애그리게이트·루트** | 도메인 객체 묶음의 단일 접근 진입점·불변 조건 보호 |
| **도메인 모델** | Entity·VO·Aggregate로 비즈니스 로직을 캡슐화한 도메인 객체 |

#### 한줄 요약

- 바운디드 컨텍스트로 경계를 정의하고 Aggregate·Entity·VO로 도메인 모델을 캡슐화

## Ⅳ. 흐름도

<details><summary>용어 설명</summary>

- **이벤트 스토밍(Event Storming)**: 도메인 전문가·개발자가 도메인 이벤트를 시간순으로 시각화하여 바운디드 컨텍스트와 집합체를 도출하는 협업 워크숍 기법.

</details>

```text
1. 이벤트 스토밍 (Event Storming 워크숍)
   └─ 도메인 이벤트를 시간순으로 시각화하여 업무 흐름 탐색
   │
   ▼
2. 보편적 언어 수립
   └─ 회의에서 도출된 용어를 코드 클래스명·메서드명에 반영
   │
   ▼
3. 전략적 설계 (바운디드 컨텍스트 도출)
   └─ 도메인 경계 정의·컨텍스트 맵 작성·MSA 서비스 분리 기준 수립
   │
   ▼
4. 전술적 설계 (도메인 객체 설계)
   └─ Aggregate Root·Entity·VO·도메인 서비스 설계
   │
   ▼
5. 풍부한 도메인 모델 구현 완료
```

**동작 원리**

1. **이벤트 스토밍**: 도메인 전문가·개발자가 참여하여 도메인 이벤트를 시각화하고 경계를 도출
2. **보편적 언어 수립**: 이벤트 스토밍에서 도출된 용어를 소스 코드 식별자에 그대로 반영
3. **전략적 설계**: 바운디드 컨텍스트 경계를 정의하고 컨텍스트 맵으로 의존 관계를 명시
4. **전술적 설계**: Aggregate Root를 식별하고 내부 Entity·VO 및 도메인 비즈니스 로직을 구현

#### 한줄 요약

- 이벤트 스토밍→보편적 언어→전략적 경계→전술적 객체 설계의 순서로 도메인 모델을 구현

## Ⅴ. 종류 및 비교

<details><summary>용어 설명</summary>

- **빈혈 도메인 모델(Anemic Domain Model)**: 도메인 객체에 getter/setter만 존재하고 비즈니스 로직이 외부 서비스 클래스에 분산된 DDD 안티패턴.

</details>

| 비교 항목 | 빈혈 도메인 모델 (Anemic) | 풍부한 도메인 모델 (Rich/DDD) |
|:---|:---|:---|
| 비즈니스 로직 위치 | 외부 서비스 클래스에 분산 | **Entity·VO 내부에 캡슐화** |
| 유효성 검증 방식 | 서비스에서 if-else 수동 검증 | **도메인 객체 내부 자기 검증** |
| 객체 변경 안전성 | setter를 통한 외부 무분별 수정 | 도메인 메서드로만 상태 변경 허용 |

#### 한줄 요약

- 빈혈 모델은 로직이 서비스에 분산되고, 풍부한 도메인 모델은 로직이 객체 내부에 캡슐화

## Ⅵ. 실무 고려사항 및 대책

<details><summary>용어 설명</summary>

- **안티 코럽션 레이어(ACL, Anti-Corruption Layer)**: 레거시 시스템의 구조·용어가 도메인 모델을 오염하지 않도록 경계에서 번역·변환을 수행하는 격리 계층.

</details>

| 문제 | 대책 | 효과 |
|:---|:---|:---|
| 레거시 API 구조가 신규 도메인 모델을 오염 | 경계에 **ACL(안티 코럽션 레이어)** 번역 계층 배치 | 레거시 구조의 도메인 전파 차단 |
| Entity에 setter 공개로 도메인 불변 조건 위반 | **setter 제거**, 의미 있는 도메인 메서드로만 상태 변경 허용 | 도메인 객체 캡슐화·불변 조건 보호 |
| 단순 CRUD 요구사항에 DDD 강제 적용으로 복잡도 급증 | 핵심 도메인에만 DDD 적용, 일반 도메인은 단순 CRUD 유지 | 오버엔지니어링 방지 |

#### 한줄 요약

- 레거시 오염은 ACL로, setter 남용은 도메인 메서드로, 단순 요구사항에는 DDD 적용을 지양

## Ⅶ. 결론

<details><summary>용어 설명</summary>

- **DDD 도입 판정 기준**: 비즈니스 도메인의 복잡도·변경 빈도·팀 역량을 기준으로 핵심 도메인과 일반 도메인을 구분하여 DDD 적용 범위를 결정하는 판단 기준.

</details>

- 복잡한 비즈니스 로직을 가진 핵심 도메인(결제·정산)은 **DDD 풍부한 도메인 모델**, 단순 CRUD 요구는 **절차적 설계** 선택

#### 한줄 요약

- 핵심 코어 도메인의 복잡한 비즈니스 로직에 DDD를 선별 적용하고 단순 도메인은 CRUD로 유지
