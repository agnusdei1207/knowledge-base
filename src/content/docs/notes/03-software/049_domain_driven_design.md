## Ⅰ. 개요

<details>
<summary>핵심 용어</summary>

- **도메인 주도 설계(Domain-Driven Design, DDD)**: 도메인 전문가와 개발자가 업무 지식을 공통 언어•모델•코드로 발전시키는 설계 방법이다.
- **도메인 모델(Domain Model)**: 업무 개념•관계•규칙을 실행 가능한 구조로 표현한 모델이다.
- **공통 언어(Ubiquitous Language)**: 전문가와 개발자가 대화•모델•코드에서 같은 의미로 쓰는 업무 용어다.

</details>

- 정의/개념: **도메인 주도 설계(DDD)**는 전문가와 개발자가 공통 언어와 도메인 모델로 업무 지식을 탐색해 코드에 연결하는 **소프트웨어 설계 방법**이다.
- 배경/필요성: 팀별 용어•규칙 불일치로 **모델 충돌•변경 오류가 증가한다**.

#### 한줄 요약

- 공통 언어•도메인 모델 기반 **업무 지식 정제**가 핵심이다.

## Ⅱ. 특징

<details>
<summary>핵심 용어</summary>

- **도메인 전문가(Domain Expert)**: 실제 업무의 용어•규칙•예외를 설명하고 모델 정확성을 검증하는 현업 전문가다.
- **전략적 설계(Strategic Design)**: 도메인 모델의 경계와 관계를 정하는 설계 층위다.
- **전술적 설계(Tactical Design)**: 경계 안의 업무 규칙을 코드로 구현하는 설계 층위다.
- **불변 조건(Invariant)**: 업무 상태가 변경 전후에도 반드시 참이어야 하는 규칙이다.

</details>

- **도메인 전문가•개발자 협업**으로 공통 언어 형성이 핵심이다.
- **전략적 경계**로 모델 의미•투자 우선순위를 분리한다.
- **전술적 모델**로 업무 규칙•불변 조건 구현이 핵심이다.

#### 한줄 요약

- 전략적 경계와 전술적 모델 기반 **핵심 업무 집중**이 핵심이다.

## Ⅲ. 구조 및 구성요소

<details>
<summary>핵심 용어</summary>

- **하위 도메인(Subdomain)**: 업무 문제를 핵심•지원•일반 영역으로 나눈 단위다.
- **핵심 하위 도메인(Core Subdomain)**: 조직의 차별 경쟁력을 만드는 업무 영역이다.
- **지원 하위 도메인(Supporting Subdomain)**: 핵심 업무를 돕는 조직 고유의 업무 영역이다.
- **일반 하위 도메인(Generic Subdomain)**: 범용 해법을 재사용할 수 있는 업무 영역이다.
- **바운디드 컨텍스트(Bounded Context)**: 한 도메인 모델과 공통 언어의 의미가 일관되는 경계다.
- **컨텍스트 맵(Context Map)**: 바운디드 컨텍스트 사이의 의존•협력•번역 관계를 나타낸 지도다.

</details>

```text
        [하위 도메인]
               |
     [바운디드 컨텍스트] ----- [컨텍스트 맵]
               |
        +------+------+
        |             |
  [공통 언어]    [도메인 모델]
```

선의 의미: 하위 도메인은 바운디드 컨텍스트로 모델 경계를 만들고, 경계 안에서는 공통 언어와 도메인 모델이 결합되며, 컨텍스트 맵은 다른 경계와의 관계를 나타낸다.

| 구성요소 | 책임 |
|:---|:---|
| 하위 도메인 | **핵심•지원•일반** 문제 분류 |
| 바운디드 컨텍스트 | 모델•언어의 **의미 경계** 확정 |
| 공통 언어 | **업무 용어•코드 이름** 연결 |
| 도메인 모델 | **업무 개념•불변 조건** 표현 |
| 컨텍스트 맵 | 경계 간 **의존•통합 방식** 표현 |

#### 한줄 요약

- 하위 도메인•의미 경계•**언어•모델 관계**가 핵심이다.

## Ⅳ. 흐름도

<details>
<summary>핵심 용어</summary>

- **업무 시나리오•예외 탐색**: 실제 사건과 판단 예외를 수집해 모델링할 업무 지식을 찾는 과정이다.
- **용어•규칙 질문**: 모호한 업무 의미와 판단 조건을 전문가와 개발자가 함께 확인하는 과정이다.
- **공통 언어 합의**: 업무 용어와 제약을 대화•모델•코드에서 같은 의미로 확정하는 과정이다.
- **도메인 모델•경계 정제**: 새 지식에 따라 불변 조건과 바운디드 컨텍스트를 고치는 과정이다.
- **모델 기반 코드 구현**: 정제한 업무 규칙과 계약을 실행 가능한 코드에 반영하는 과정이다.
- **업무 피드백**: 실행 결과를 도메인 전문가와 검토해 모델•언어•코드를 다시 정제하는 정보다.

</details>

```text
+--------------------------------------------------+
| 반복 범위: 업무 의미와 모델이 일치할 때까지      |
|                                                  |
| [1. 업무 시나리오•예외 탐색]                    |
|                |                                 |
|                v                                 |
| [2. 용어•규칙 질문]                              |
|                |                                 |
|                v                                 |
| [3. 공통 언어 합의]                              |
|                |                                 |
|                v                                 |
| [4. 도메인 모델•경계 정제]                       |
|                |                                 |
|                v                                 |
| [5. 모델 기반 코드 구현]                         |
|                |                                 |
|                v                                 |
| [실행 결과•업무 피드백] -------------------------+
+--------------------------------------------------+
```

**동작 원리**

1. **업무 시나리오•예외 탐색**: 사건과 판단 규칙을 발견한다.
2. **용어•규칙 질문**: 모호한 의미와 경계 후보를 확인한다.
3. **공통 언어 합의**: 업무 용어와 제약을 한 의미로 확정한다.
4. **도메인 모델•경계 정제**: 컨텍스트•불변 조건을 갱신한다.
5. **모델 기반 코드 구현**: 업무 규칙과 계약을 반영한다.

> 요약: **바운디드 컨텍스트** 안의 언어•모델•코드를 **업무 피드백**으로 정제가 핵심이다.

#### 한줄 요약

- 업무 피드백 기반 **언어•모델•코드 정제 순환**이 핵심이다.

## Ⅴ. 종류 및 비교

<details>
<summary>핵심 용어</summary>

- **트랜잭션 스크립트(Transaction Script)**: 한 업무 요청의 처리 절차를 서비스 함수에 순서대로 작성하는 방식이다.
- **절차 결합**: 규칙이 늘수록 한 서비스 함수의 처리 순서와 조건이 서로 얽히는 상태다.
- **모델 유지 비용**: 공통 언어와 도메인 모델을 업무 변화에 맞춰 검증•수정하고 코드와 동기화하는 데 드는 비용이다.

</details>

| 업무 로직 설계 | DDD | 트랜잭션 스크립트 |
|:---|:---|:---|
| 적용 기준 | 예외•용어 변화 많은 **핵심 업무** | 단순 규칙•**드문 변경** |
| 핵심 특징 | 공통 언어•**도메인 모델•경계** | 서비스 함수의 **처리 순서 나열** |
| 한계 | 지식 탐색•**모델 유지 비용** | 규칙 증가 시 **절차 결합** |

> 요약: **단순 업무**는 스크립트, **복잡한 핵심 업무**는 DDD가 핵심이다.

#### 한줄 요약

- 단순 업무는 스크립트, 복잡한 핵심 업무는 **DDD**가 핵심이다.

## Ⅵ. 실무 고려사항 및 대책

<details>
<summary>핵심 용어</summary>

- **통합 계약(Integration Contract)**: 서로 다른 바운디드 컨텍스트가 교환할 데이터•행위•오류 규칙이다.
- **모델 부패(Model Corruption)**: 다른 경계의 용어•규칙이 섞여 도메인 모델의 의미가 흐려지는 현상이다.
- **애그리게이트(Aggregate)**: 하나의 트랜잭션에서 일관성을 지켜야 하는 객체 묶음이다.
- **애그리게이트 루트(Aggregate Root)**: 애그리게이트 경계 안의 상태 변경과 불변 조건을 통제하는 진입 객체다.
- **번역 계층(Translation Layer)**: 외부 컨텍스트의 데이터•용어를 내부 모델의 의미와 계약으로 변환해 모델 부패를 막는 경계다.
- **전술 패턴(Tactical Pattern)**: 엔티티•값 객체•애그리게이트•도메인 서비스로 경계 안의 업무 규칙을 구현하는 설계 도구다.
- **잠금(Lock)**: 동시 변경을 직렬화하는 제어다.
- **충돌(Conflict)**: 같은 상태의 갱신이 겹쳐 발생하는 처리 실패다.

</details>

| 문제 | 대책 | 효과 |
|:---|:---|:---|
| 팀마다 같은 용어를 다른 의미로 사용 | 업무 능력•언어 차이로 **컨텍스트 분리** | **모델 의미 충돌** 방지 |
| 데이터 구조 중심 모델로 업무 행위 누락 | 전문가와 **행위•규칙 중심 모델** 검증 | **업무 개념** 보존 |
| 단순 지원 영역까지 전술 패턴 적용 | 핵심에 집중하고 단순 영역은 **스크립트 적용** | **설계 비용** 통제 |
| 경계 간 모델 객체를 직접 공유 | **통합 계약•번역 계층**으로 의미 격리 | **모델 부패** 방지 |
| 애그리게이트가 여러 업무 일관성을 포괄 | **애그리게이트 루트**가 단일 트랜잭션 불변 조건 통제 | **잠금•충돌** 감소 |

#### 한줄 요약

- 통합 계약•번역 계층 기반 **모델 의미 격리**가 핵심이다.

## Ⅶ. 결론

<details>
<summary>핵심 용어</summary>

- **업무 복잡도(Business Complexity)**: 업무 예외와 규칙 변화의 정도다.
- **차별성(Differentiation)**: 업무가 조직 경쟁력에 기여하는 정도다.
- **설계 비용**: 지식 탐색과 도메인 모델•경계를 만들고 유지하는 데 드는 비용이다.

</details>

- **업무 복잡도•차별성**이 크면 DDD, 단순 지원 업무는 **트랜잭션 스크립트**를 선택한다.

#### 한줄 요약

- 복잡한 차별 업무에는 DDD, 지원 업무에는 **스크립트**가 핵심이다.
