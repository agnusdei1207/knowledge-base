## Ⅰ. 개요

<details><summary>용어 설명</summary>

- **피처 스토어(Feature Store)**: 머신러닝 모델의 학습에 필요한 대용량 시계열 과거 피처(Offline Store)와 실시간 온라인 추론에 필요한 초저지연 최신 피처(Online Store)의 정의, 변환 로직, 저장, 공유를 일원화하여 관리하는 MLOps 핵심 데이터 플랫폼.
- **훈련-서빙 스큐 및 데이터 누수(Training-Serving Skew & Data Leakage)**: 학습 시 사용한 판다스 전처리 로직과 운영 서빙 시 자바 전처리 로직의 불일치(Skew), 그리고 과거 데이터 학습 시 미래 시점의 피처가 유입되어 성능이 과대평가되는 위험.

</details>

- 정의/개념: 머신러닝 학습 및 실시간 추론에 사용되는 **피처(Feature)의 정의, 계산, 저장, 공유를 일원화하는 MLOps 데이터 관리** 플랫폼
- 배경/필요성: 데이터 과학자와 엔지니어 간 파편화된 파이프라인으로 인한 **훈련-서빙 스큐(Skew), 피처 중복 개발 및 데이터 누수 위험** 직면

#### 한줄 요약

- 단일 피처 레지스트리와 Offline/Online 이중 저장소를 통해 훈련-서빙 스큐를 원천 차단하고 시점 일치 조인(Point-in-Time Join)을 보장

## Ⅱ. 특징

<details><summary>용어 설명</summary>

- **시점 일치 조인(PIT Join: Point-in-Time Correct Join)**: 관측 시점(Event Timestamp) 이전의 피처값만을 정확히 결합하여 미래 데이터가 과거 학습 데이터에 섞이는 데이터 누수(Data Leakage)를 방어하는 기법.
- **Offline / Online 이중 저장소 구조**: 대규모 배치 학습을 위한 분석형 스토리지(Parquet/Iceberg)와 실시간 10ms 이내 추론을 위한 키-값 스토리지(Redis)의 동기화 구조.

</details>

- 피처 정의와 계산 변환 로직을 중앙에서 1회만 선언하는 **단일 계산 정의(Single Source of Truth)**
- 과거 시점의 정확한 스냅샷을 구성하여 데이터 누수를 방지하는 **PIT(Point-in-Time) Join 지원**
- 전사 데이터 과학자 간 피처를 검색하고 재사용할 수 있는 **피처 카탈로그 및 계보(Lineage) 관리**

#### 한줄 요약

- 단일 피처 정의로 온/오프라인 저장소를 동기화하여 모델 개발 속도를 가속하고 추론 데이터 정합성을 사수

## Ⅲ. 구조 및 구성요소

<details><summary>용어 설명</summary>

- **피처 스토어 5대 아키텍처 계층**: Feature Registry(메타데이터/정의), Transformation Engine(변환기), Offline Store(학습용), Online Store(추론용), Monitoring(품질/신선도).

</details>

```text
[ 피처 스토어(Feature Store: Feast 기반) 계층 아키텍처 구조도 ]

 1. [ 피처 등록 및 메타데이터 계층 (Feature Registry) ]
    ┌─────────────────────────────────────────────────────────────┐
    │  • 피처 정의(Schema), 계산식, 소유자(Owner), 버전(v1.0)     │
    └────────────────────────────┬────────────────────────────────┘
                                 │ (단일 변환 로직 동시 파이프라인)
                                 ▼
 2. [ 피처 변환 엔진 (Transformation: Spark / Flink Streaming) ]
    ┌────────────────────────────┴────────────────────────────┐
    │ (배치 적재)                                             │ (실시간 스트리밍)
    ▼                                                         ▼
 3. [ 오프라인 저장소 (Offline Store) ]       4. [ 온라인 저장소 (Online Store) ]
    • Delta Lake / Parquet / BigQuery         • Redis / DynamoDB 인메모리
    • 대용량 과거 시계열 이력 저장            • 초저지연 최신 피처값 (<10ms)
    • PIT Join ➔ 모델 훈련 데이터셋 생성       • 실시간 추론 API 서빙
```

선의 의미: Feature Registry의 정의에 따라 변환 엔진이 Offline(학습용)과 Online(추론용) 저장소에 동일한 피처값을 동기화 공급하는 구조.

| 구성요소 | 책임 |
|:---|:---|
| 피처 레지스트리 (Registry) | 피처의 이름, 데이터 타입, **계산 수식, 버전, 계보(Lineage)를 중앙 메타데이터로 보관** |
| 변환 엔진 (Transformer) | 배치 및 스트리밍 데이터를 받아 **온라인과 오프라인 저장소에 동일한 계산 로직으로 적재** |
| 오프라인 저장소 (Offline) | Parquet/BigQuery 기반으로 **대용량 시계열 과거 이력을 보관하고 PIT Join 학습 데이터셋 생성** |
| 온라인 저장소 (Online) | Redis 기반으로 **실시간 추론 모델에 최신 피처값을 10ms 이내 초저지연으로 제공** |
| 품질 모니터링 (Monitor) | 피처의 결측치 비율, **신선도(Freshness SLA), 온/오프라인 간 드리프트 스큐 실시간 감시** |

#### 한줄 요약

- 레지스트리, 변환기, 오프라인 저장소, 온라인 저장소, 모니터링 모듈이 유기적으로 결합

## Ⅳ. 흐름도

<details><summary>용어 설명</summary>

- **피처 스토어 5단계 수명주기**: 피처 정의 등록 $\to$ 온/오프라인 동시 변환 $\to$ PIT Join 학습셋 생성 $\to$ 실시간 추론 피처 서빙 $\to$ 신선도 및 스큐 감시.

</details>

```text
[ Feature Store 피처 수명주기 및 온/오프라인 서빙 파이프라인 ]

 ┌────────────────────────────────────────┐
 │ 1. 피처 정의(이름, 계산식, TTL) 등록   │
 └───────────────────┬────────────────────┘
                     │
                     ▼
 ┌────────────────────────────────────────┐
 │ 2. Spark/Flink로 원천 데이터 단일 변환 │
 ├───────────────────┬────────────────────┤
 │ 오프라인 적재     │ 온라인 실시간 적재 │
 │ 3A. Delta Lake에  │ 3B. Redis에        │
 │     시계열 이력   │     최신값 갱신    │
 └───────────────────┴────────────────────┘
                     │
                     ▼
 ┌────────────────────────────────────────┐
 │ 4. PIT Join으로 미래 데이터 누수 차단  │
 └───────────────────┬────────────────────┘
                     │
                     ▼
 ┌────────────────────────────────────────┐
 │ 5. 모델 추론 서빙 및 피처 신선도 모니터링
 └────────────────────────────────────────┘
```

### 동작 원리

1. 정의 등록: 데이터 엔지니어가 `user_30d_avg_spend` 피처의 SQL 계산 로직과 버전을 Feast 레지스트리에 선언.
2. 단일 변환: 스트리밍 엔진이 Kafka 로그를 읽어 동일한 변환 로직으로 온/오프라인 양쪽에 동시 적재.
3. 이중 적재: 과거 이력은 오프라인 Delta Lake에 시계열 파티션으로 쌓고, 최신값은 온라인 Redis에 갱신.
4. PIT Join: 모델 학습 시 각 결제 이벤트 타임스탬프 이전 시점의 피처값만 정확히 결합하여 데이터 누수를 완벽 차단.
5. 추론 및 감시: 결제 사기 탐지 API 호출 시 Redis에서 2ms 만에 피처를 조회하고, 피처 신선도(1시간 이내 갱신)를 감시.

#### 한줄 요약

- 정의 등록 $\to$ 단일 변환 $\to$ 이중 적재 $\to$ PIT Join $\to$ 추론 및 감시의 5단계

## Ⅴ. 종류 및 비교

<details><summary>용어 설명</summary>

- **Offline Store vs Online Store**: 대용량 배치 학습 전용 저장소(Offline)와 초저지연 실시간 추론 전용 저장소(Online).

</details>

| 구분 | 오프라인 피처 저장소 (Offline Store) | 온라인 피처 저장소 (Online Store) |
|:---|:---|:---|
| **적용 기준** | 대규모 데이터셋 기반의 모델 훈련, 배치 추론, 백테스팅 | 사용자 요청 즉시 예측값을 반환해야 하는 실시간 온라인 추론 |
| **핵심 특징** | **대용량 시계열 이력 저장(Parquet), 시점 일치 조인(PIT Join)** | **인메모리 Key-Value 스토리지(Redis), 초저지연 조회 (<10ms)** |
| **한계** | 대용량 분산 쿼리로 인해 실시간 밀리초 단위 즉시 조회 불가 | 최신값 위주 보관으로 과거 시계열 학습 데이터셋 생성 불가 |

#### 한줄 요약

- 배치 학습과 시계열 이력 관리는 Offline Store, 실시간 초저지연 추론 서빙은 Online Store를 채택

## Ⅵ. 실무 고려사항 및 대책

<details><summary>용어 설명</summary>

- **데이터 누수(Data Leakage)**: 학습 시점의 피처 테이블에 예측 대상 사건 이후에 발생한 미래 정보가 섞여 들어가 실제 배포 시 성능이 폭망하는 현상.

</details>

| 문제 | 대책 | 효과 |
|:---|:---|:---|
| 단순 DB 조인으로 미래 데이터가 학습에 유입되는 데이터 누수 발생 | **Feature Store의 `Point-in-Time (PIT) Join` 기능 의무화** | 데이터 누수 에러 원천 차단 |
| 학습 전처리 코드와 추론 전처리 코드 불일치로 모델 성능 급락 | **`Feature Store` 단일 계산 로직을 학습/추론 양쪽에 강제 공유** | 훈련-서빙 스큐 제로화 |
| 담당자 퇴사로 인해 수천 개 피처의 정의와 계산 의존성 유실 | **Feature Registry에 소유자(Owner), SLA, 계보(Lineage) 메타데이터 등록** | 전사 피처 재사용성 및 거버넌스 확보 |

#### 한줄 요약

- PIT Join 적용, 단일 계산 로직 공유, 피처 레지스트리 메타데이터 등록을 통해 피처 정합성을 보장

## Ⅶ. 결론

<details><summary>용어 설명</summary>

- **엔터프라이즈 피처 메시(Enterprise Feature Mesh)**: 도메인별 데이터 팀이 생성한 고품질 피처를 전사 레지스트리를 통해 상품처럼 교환·소비하는 차세대 MLOps 아키텍처.

</details>

- **피처 스토어**는 머신러닝 시스템의 데이터 정합성과 재사용성을 보장하는 핵심 인프라 계층이며, PIT Join 기반의 데이터 누수 방지와 온/오프라인 동기화를 통해 훈련-서빙 스큐를 완벽히 해결해야 함

#### 한줄 요약

- 단일 피처 정의와 PIT Join 및 온/오프라인 이중 저장을 통해 훈련-서빙 스큐를 해결하고 모델 품질을 완성
