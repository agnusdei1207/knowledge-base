## Ⅰ. 개요

<details><summary>용어 설명</summary>

- **교착상태(Deadlock)**: 두 프로세스가 서로 멱살을 잡고 "네가 먼저 놔!"라며 평생 기다리다가 시스템 전체가 뻗어버리는 재앙이다.
- **코프만 4대 조건(Coffman Conditions)**: 교착상태가 터지려면 완벽하게 타이밍이 맞아야 하는 4가지 조건(상호배제, 점유대기, 비선점, 환형대기)이다.
- **자원 할당 그래프(Resource Allocation Graph, RAG)**: 누가 뭘 쥐고 있고 뭘 기다리는지 그림으로 쫙 그려서 꼬인 사이클을 찾아내는 엑스레이 도구이다.

</details>

- 정의: 실행 주체들이 서로 상대방의 자원을 무한정 대기하며 시스템이 완전히 정지해 버리는 **교착상태(Deadlock)**
- 배경: 멀티스레드 환경에서 독립적으로 락을 획득하다가 재수 없게 꼬이면 **환형 대기(Circular Wait)**가 완성되기 때문

#### 한줄 요약

- 서로 양보 안 하고 남의 것을 기다리다가 시스템이 멈추는 현상으로, 코프만 4대 조건이 모두 맞을 때 발생한다.

## Ⅱ. 특징

<details><summary>용어 설명</summary>

- **상호 배제(Mutual Exclusion)**: 한 번에 한 놈만 쓸 수 있는 자원이라서 남이 쓰고 있으면 무조건 밖에서 손가락 빨고 기다려야 하는 속성이다.
- **점유 대기(Hold & Wait)**: 자기가 가진 건 하나도 안 놓으면서 남의 것을 내놓으라고 끝까지 버티는 욕심쟁이 속성이다.
- **비선점(No Preemption)**: 남이 쓰고 있는 걸 강제로 빼앗을 수 없어서, 그놈이 알아서 다 쓰고 뱉을 때까지 하염없이 기다려야 하는 속성이다.
- **환형 대기(Circular Wait)**: A는 B를 기다리고, B는 C를, C는 A를 기다리는 식으로 서로 꼬리를 물고 죽음의 원을 그리는 끔찍한 속성이다.

</details>

- **코프만 4대 필요조건**이 4개 다 맞아떨어질 때만 교착상태가 터짐.
- 자원이 하나뿐일 때는 **자원 할당 그래프**에 사이클(원)이 생겼는지로 판정함.
- 예방, 회피, 탐지, 복구 4단계 방어 전략으로 멱살을 잡고 통제함.

#### 한줄 요약

- 상호 배제, 점유 대기, 비선점, 환형 대기가 완성되면 멈추고, 이걸 그래프로 그려서 찾아낸다.

## Ⅲ. 구조 및 구성요소

<details><summary>용어 설명</summary>

- **대기 그래프(Wait-for Graph)**: 자원 할당 그래프에서 자원 껍데기는 다 쳐내고, 프로세스끼리 멱살 잡은 꼬라지만 단순하게 그려놓은 핵심 도면이다.

</details>

```text
[ 교착상태 방어 십자포화 아키텍처 ]
               [ 자원 관리자 ]
               (자원 내놔 통제)
                      │
     ┌────────┬───────┴──────┬────────┐
     ▼        ▼              ▼        ▼
[ 예방 규칙 ] [ 안전성 검사 ] [ 대기 그래프 ]
  (4대 조건   (미리 계산해서    (사이클 포착)
   원천봉쇄)   위험하면 빠꾸)         │
                                      ▼
                               [ 복구 관리자 ]
                               (한 놈 쏴 죽임)
```

| 구성요소 | 책임 |
|:---|:---|
| 자원 관리자 | 프로세스들이 락 달라고 징징대는 걸 다 기록하고 할당해 주는 총괄 매니저 |
| **예방 규칙** | 시스템 설계할 때부터 코프만 4대 조건 중 하나를 박살 내서 싹수를 자르는 통제 룰 |
| 안전성 검사 | 락 주기 전에 시뮬레이션 돌려서 **안전 상태(Safe State)**인지 미리 확인하는 회피꾼 |
| **대기 그래프** | 평소엔 냅두다가 뒤에서 몰래 그래프 그려서 놈들이 동그랗게 꼬였는지 찾아내는 탐지기 |
| 복구 관리자 | 꼬인 거 발견하면 불쌍한 희생자(Victim) 하나 찍어서 강제로 죽이고 롤백시키는 처형자 |

#### 한줄 요약

- 예방하거나, 미리 시뮬레이션 돌려 피하거나, 나중에 그래프 까서 꼬였으면 한 놈을 죽인다.

## Ⅳ. 흐름도

<details><summary>용어 설명</summary>

- **은행가 알고리즘(Banker's Algorithm)**: "얘가 나중에 이만큼 더 달라고 하면 어쩌지?" 하고 최악의 상황까지 계산해서 안전할 때만 락을 내어주는 깐깐한 회피 기법이다.

</details>

```text
[ 교착상태 방어 전략 적용 흐름 ]
┌─────────────────────────────┐
│ 1. 예방할 수 있나? (Prevention) │
└──────────────┬──────────────┘
               ├─ 가능 ─▶ [2. 예방(Lock Ordering) 적용]
               │ 불가
               ▼
┌─────────────────────────────┐
│ 3. 피할 수 있나? (Avoidance)    │
└──────────────┬──────────────┘
               ├─ 가능 ─▶ [4. 회피(은행가 알고리즘) 적용]
               │ 불가 (최대치 예측 불가능)
               ▼
┌─────────────────────────────┐
│ 5. 탐지 및 복구 (Detection)     │
│ (걍 쓰게 냅두고 꼬이면 한 놈 죽임) │
└─────────────────────────────┘
```

### 동작 원리

1. 예방 판정: 코프만 4대 조건을 원천 봉쇄할 수 있는지 각을 잼.
2. 예방 적용: 순서를 정해서 락을 잡게 하는 식(**Lock Ordering**)으로 예방함.
3. 회피 판정: 프로세스가 최대 얼마만큼 자원을 쓸지 예측할 수 있으면 회피로 빠짐.
4. 회피 적용: 깐깐한 **은행가 알고리즘**을 돌려서 안전할 때만 락을 허락함.
5. 탐지 및 복구: 예측도 안 되면 걍 냅두고 주기적으로 대기 그래프 까봐서 꼬여있으면 처형(Kill)함.

#### 한줄 요약

- 예방이 안 되면 회피하고, 회피도 안 되면 그냥 막 쓰게 한 뒤 꼬였을 때 죽여서 복구한다.

## Ⅴ. 종류 및 비교

<details><summary>용어 설명</summary>

- **안전 상태(Safe State)**: 모든 프로세스가 순서대로 락을 먹고 토해내며 아무도 안 뻗고 무사히 퇴근할 수 있는 완벽한 시나리오가 1개 이상 있는 쾌적한 상태이다.

</details>

| 비교 항목 | 예방 (Prevention) | 회피 (Avoidance) | 탐지 및 복구 (Detection & Recovery) |
|:---|:---|:---|:---|
| 접근 방식 | 4대 조건 중 하나를 설계 단에서 박살 냄 | 락 달라고 할 때마다 **안전 상태**인지 미리 계산함 | 그냥 막 퍼주다가 주기적으로 순찰 돌아서 꼬이면 뒤엎음 |
| 구현 기법 | **Lock Ordering** (순서대로만 락 잡아!) | **은행가 알고리즘** (은행원처럼 깐깐하게 빌려줌) | **대기 그래프** 분석 후 꼬인 놈 하나 쏴 죽임 |
| 단점 및 오버헤드 | 코딩이 빡세고 자원을 너무 심하게 제약함 | 락 잡을 때마다 시뮬레이션 돌려대서 속도가 느려 터짐 | 안 꼬이면 제일 빠른데, 꼬여서 롤백 터지면 지옥문 열림 |

#### 한줄 요약

- 예방은 꽉 막혔고, 회피는 느려 터졌으며, 탐지는 빠르지만 사고 나면 수습이 고통스럽다.

## Ⅵ. 실무 고려사항 및 대책

<details><summary>용어 설명</summary>

- **락 오더링(Lock Ordering)**: 락에 번호를 매겨놓고 "무조건 번호 낮은 거부터 순서대로 락 잡아!"라고 강제해서 환형 대기(원)를 원천 차단하는 예방 꼼수이다.
- **트라이락(tryLock / Timeout)**: 락 달라고 3초만 기다려보고 안 주면 "안 해!" 하고 자기가 들고 있던 것까지 뱉어버려서 점유 대기를 끊어내는 기법이다.

</details>

| 문제 | 대책 | 효과 |
|:---|:---|:---|
| 여기저기서 락 잡는 순서가 꼬여서 **환형 대기** 터지고 서버 멈춤 | **락 오더링(Lock Ordering)** 멱살 잡고 강제 적용함 | 사이클 자체가 절대 안 만들어지게 싹수를 잘라 교착상태 예방 |
| 락 하나 얻겠다고 평생 대기 타느라 시스템 전체가 얼어붙음 | 무한 대기 대신 3초 **트라이락(tryLock)** 꽂아서 타임아웃 먹임 | 남의 자원 못 뺏으면 내 것도 뱉게 만들어서 점유 대기 무력화 |
| 분산 서버 환경에서 락이 꼬여서 교착상태 감지도 못 하고 터짐 | **펜싱 토큰(Fencing Token)**이랑 락 임대 시간을 멱살 잡고 박아버림 | 분산 락 환경에서도 죽어버린 락을 뺏어서 사후 해제 및 복구 |

#### 한줄 요약

- 락 순서를 멱살 잡고 강제하고, 타임아웃으로 못 뺏으면 다 뱉게 만들어서 교착상태를 예방하라.

## Ⅶ. 결론

<details><summary>용어 설명</summary>

- **교착상태 대응 선택 기준(Deadlock Trade-off Criteria)**: 락 잡을 때마다 검사해서 느려질지, 아니면 꼬일 때마다 롤백해서 지옥을 볼지 자원 상황을 따지는 기준 잣대이다.

</details>

- **교착상태 대응 선택 기준** 원칙에 따라, 일반 앱 개발엔 **락 오더링 예방**을 꽂고, 롤백이 쉬운 DB 환경은 **탐지/복구 엔진** 채택 기조 확립함

#### 한줄 요약

- 소프트웨어는 락 오더링으로 사전에 예방하고, 데이터베이스는 탐지하고 롤백시키는 게 정배다.
