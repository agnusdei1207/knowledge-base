## Ⅰ. 개요

<details><summary>용어 설명</summary>

- **멀티 클라우드 전략(Multi-Cloud Strategy)**: 단일 벤더 종속(Lock-in)을 방지하고 서비스별 최적 기능 조합(Best-of-Breed) 및 글로벌 재해복구(DR)를 위해 2개 이상의 이종 퍼블릭 클라우드(AWS, GCP, Azure)를 분산 운용하는 아키텍처 전략.
- **단일 CSP 전면 장애 및 가격 협상력 상실(Single CSP Outage & Lock-in Risk)**: 단일 클라우드 사업자에 전적으로 의존할 때 발생하는 전사 서비스 중단 사고와 공급자의 일방적 요금 인상에 대응하지 못하는 위험.

</details>

- 정의/개념: 단일 벤더 종속(Lock-in)을 방지하고 서비스별 최적 조합(Best-of-Breed)을 달성하기 위해 **2개 이상의 퍼블릭 CSP를 분산 운용**하는 클라우드 전략
- 배경/필요성: 특정 클라우드 사업자 독점 사용 시 발생하는 **단일 CSP 전면 장애 전파, 가격 협상력 상실 및 타 플랫폼 이관 불가 위험** 직면

#### 한줄 요약

- 2개 이상의 퍼블릭 클라우드를 조합하여 단일 장애점(SPOF)을 제거하고 비즈니스 연속성과 협상력을 극대화

## Ⅱ. 특징

<details><summary>용어 설명</summary>

- **Best-of-Breed(최적 조합)**: AWS의 범용 인프라/EKS, GCP의 BigQuery/AI 엔진, Azure의 AD 보안 등 각 CSP의 최고 기술만을 선별 결합하는 방식.
- **클라우드 중립적 추상화(Cloud-Agnostic Abstraction)**: Kubernetes(CaaS)와 Terraform(IaC)을 통해 특정 CSP 종속성 없이 이종 클라우드 간 워크로드를 자유롭게 이동시키는 기법.

</details>

- 단일 클라우드 종속을 방지하고 가격 협상력을 확보하는 **벤더 락인(Lock-in) 완화**
- CSP별 특화된 강점 서비스를 결합하는 **최적 기능 조합(Best-of-Breed)**
- CSP 전면 장애 발생 시 타 클라우드로 자동 우회하는 **글로벌 재해복구(DR) 가용성**

#### 한줄 요약

- 컨테이너 및 IaC 기반의 클라우드 비종속 아키텍처를 통해 안정적인 다중 CSP 운영을 달성

## Ⅲ. 구조 및 구성요소

<details><summary>용어 설명</summary>

- **멀티 클라우드 추상화 계층**: Terraform(통합 프로비저닝), Kubernetes(통합 런타임), GSLB(글로벌 트래픽 라우팅), Vault(통합 시크릿/IAM).

</details>

```text
[ 멀티 클라우드 통합 관리 및 추상화 구조도 ]

 ┌────────────────────────────────────────────────────────────────────────┐
 │ 1. 통합 오케스트레이션 및 거버넌스 계층                                │
 │   - [ Terraform (IaC) ]  [ Kubernetes (CaaS) ]  [ HashiCorp Vault (IAM)│
 ├────────────────────────────────────────────────────────────────────────┤
 │ 2. 글로벌 트래픽 분기 계층: GSLB (Global Server Load Balancer)         │
 ├───────────────────────────────────┬────────────────────────────────────┤
 │ 3. Primary CSP: AWS               │ 4. Secondary CSP: GCP              │
 │   • EKS 워크로드 (대외 웹/앱)     │   • BigQuery / Vertex AI (데이터)  │
 │   • RDS / Aurora (주 트랜잭션)    │   • Cloud Storage (DR 백업)        │
 └───────────────────────────────────┴────────────────────────────────────┘
```

선의 의미: 하단의 AWS, GCP 이종 CSP 클라우드를 상단의 Terraform, Kubernetes 추상화 레이어로 묶어 제어하는 아키텍처.

| 구성요소 | 책임 |
|:---|:---|
| 워크로드 배치 (Placement) | 기능 적합성, 데이터 주권, 비용에 따라 **최적의 CSP로 애플리케이션 분산 배정** |
| 인프라 추상화 (IaC/CaaS) | Terraform 및 Kubernetes를 통해 **CSP 간 이식 가능한 공통 배포 환경 제공** |
| 통합 신원 관리 (IAM) | HashiCorp Vault 및 OIDC를 통해 **이종 클라우드 간 통합 계정/시크릿 통제** |
| 글로벌 트래픽 라우터 (GSLB)| 헬스체크 기반으로 **CSP 간 트래픽 분기 및 장애 시 타 CSP로 자동 절체** |
| 통합 관제 및 FinOps | DataDog 등을 통해 **CSP 전반의 성능, SLO, Egress 네트워크 비용 통합 관측** |

#### 한줄 요약

- 워크로드 배치, 인프라 추상화, 통합 IAM, GSLB, FinOps 관제가 결합하여 멀티 클라우드를 제어

## Ⅳ. 흐름도

<details><summary>용어 설명</summary>

- **멀티 클라우드 DR 장애 전환 5단계 절차**: 주 CSP 장애 판정 $\to$ 보조 CSP RPO 확인 $\to$ 보조 CSP 승격 $\to$ GSLB 트래픽 전환 $\to$ 서비스 정합성 검증.

</details>

```text
[ 멀티 클라우드 재해복구(DR) 자동 절체 파이프라인 ]

 ┌────────────────────────────────────────┐
 │ 1. 주(Primary) CSP 리전 전면 장애 감지 │
 └───────────────────┬────────────────────┘
                     │
                     ▼
 ┌────────────────────────────────────────┐
 │ 2. 보조(Secondary) CSP 데이터 RPO 확인 │
 └───────────────────┬────────────────────┘
                     │
                     ▼
 ┌────────────────────────────────────────┐
 │ 3. 보조 CSP 워크로드 활성화 및 승격   │
 └───────────────────┬────────────────────┘
                     │
                     ▼
 ┌────────────────────────────────────────┐
 │ 4. GSLB DNS 라우팅 보조 CSP로 자동 전환│
 └───────────────────┬────────────────────┘
                     │
                     ▼
 ┌────────────────────────────────────────┐
 │ 5. 트랜잭션 정합성 및 오류율 검증 완료 │
 └────────────────────────────────────────┘
```

### 동작 원리

1. 장애 감지: 글로벌 모니터링 시스템이 주 CSP(예: AWS)의 API 타임아웃 및 리전 다운을 판정.
2. RPO 확인: 보조 CSP(예: GCP)로 실시간 복제 중이던 데이터의 복구 시점(RPO) 지연을 확인.
3. 승격: 보조 CSP에 대기 중이던 쿠버네티스 파드(Pod)를 스케일아웃하고 DB 읽기/쓰기를 승격.
4. GSLB 전환: DNS 기반 GSLB가 사용자 트래픽을 보조 CSP의 엔드포인트로 즉시 우회.
5. 정합성 검증: 정상 서비스 재개를 확인하고 트랜잭션 오류율 및 지연시간 메트릭을 점검.

#### 한줄 요약

- 장애 감지 $\to$ RPO 확인 $\to$ 보조 승격 $\to$ GSLB 우회 $\to$ 정합성 검증의 5단계

## Ⅴ. 종류 및 비교

<details><summary>용어 설명</summary>

- **Single Cloud vs Multi-Cloud**: 단일 CSP 전용 구조와 2개 이상의 CSP를 분산 병용하는 멀티 클라우드 구조.

</details>

| 구분 | Single Cloud (단일 CSP 전용) | Multi-Cloud (복수 CSP 병용) |
|:---|:---|:---|
| **적용 기준** | 단일 CSP 생태계에 집중하여 빠른 개발과 단순 운영이 필요한 환경 | 벤더 종속 회피, 무중단 DR 가용성, AI/빅데이터 특화 결합 환경 |
| **핵심 특징** | **단일 콘솔 관리, 최적화된 통합, 낮은 운영 복잡도** | **CSP 수준 장애 우회, Best-of-Breed 조합, 높은 협상력** |
| **한계** | 벤더 종속(Lock-in) 및 CSP 전면 장애 시 대책 부재 | 다중 기술 스택 인력 필요 및 CSP 간 Egress 전송 비용 발생 |

#### 한줄 요약

- 단순 운영은 단일 클라우드, 완벽한 재해복구와 협상력 확보는 멀티 클라우드를 채택

## Ⅵ. 실무 고려사항 및 대책

<details><summary>용어 설명</summary>

- **크로스 클라우드 전송 비용(Cross-Cloud Egress Fee)**: 서로 다른 CSP 간 대량 데이터 복제 시 발생하는 아웃바운드 네트워크 통신 과금.

</details>

| 문제 | 대책 | 효과 |
|:---|:---|:---|
| CSP 간 대용량 데이터 동기화 시 Egress 전송 비용 폭증 | **타깃 CSP 내 로컬 처리 원칙 수립 및 변경분(CDC) 압축 전송** | 네트워크 전송 비용 60% 절감 |
| CSP별 상이한 기술 스택으로 인한 엔지니어링 관리 복잡도 | **Kubernetes(K8s) 및 Terraform 기반 표준화 인프라 단일화** | 클라우드 비종속 단일 운영 체계 구축 |
| CSP별 IAM 권한 체계 상이로 인한 보안 구멍(Security Drift) | **HashiCorp Vault 및 OIDC 기반 중앙 집중형 권한 배포** | 전사 보안 정책 일관성 100% 보장 |

#### 한줄 요약

- Egress 비용 최소화, 컨테이너/IaC 표준화, 중앙 Vault IAM을 통해 멀티 클라우드의 복잡성을 제어

## Ⅶ. 결론

<details><summary>용어 설명</summary>

- **멀티 클라우드 거버넌스 프레임워크(Multi-Cloud Governance)**: 비용(FinOps), 보안(SecOps), 운영(DevOps)을 단일 통합 플랫폼에서 통제하는 차세대 클라우드 거버넌스.

</details>

- **멀티 클라우드 전략** 클라우드 종속을 탈피하고 무중단 비즈니스 영속성을 달성하는 필수 엔터프라이즈 아키텍처이며, 명확한 워크로드 배치 원칙과 표준화된 추상화 계층을 기반으로 운영 효율을 극대화해야 함

#### 한줄 요약

- 컨테이너 추상화와 GSLB 장애 전환을 통해 단일 CSP 한계를 극복하고 최적의 멀티 클라우드를 완성
