## Ⅰ. 개요

<details><summary>용어 설명</summary>

- **자동 페일오버(Auto Failover)**: 시스템 운영자의 수동 개입 없이, 감시 모듈이 주 노드(Primary)의 장애를 감지하고 구 노드의 쓰기 권한을 강제 차단(Fencing)한 후 대기 노드(Standby)를 새로운 Primary로 자동 승격하여 서비스 경로를 재라우팅하는 무중단 복구 메커니즘.
- **수동 전환 지연 및 데이터 충돌 위험(Manual Lag & Split-Brain Risk)**: 엔지니어가 장애를 인지하고 수동으로 명령을 내리기까지 RTO가 수십 분 이상 지연되거나, 펜싱 없이 승격하여 양쪽 노드가 동시 쓰기를 수행해 데이터가 영구 손상되는 위험.

</details>

- 정의/개념: 장애 감지부터 펜싱, 스탠바이 승격, 트래픽 재라우팅까지 **사람의 개입 없이 소프트웨어가 자율 실행하는 무중단 복구** 메커니즘
- 배경/필요성: 야간 및 휴일 장애 시 엔지니어의 수동 전환 개입 지연으로 인한 **RTO 초과, 작업 실수 및 스플릿 브레인 데이터 오염 위험** 직면

#### 한줄 요약

- 다중 하트비트 감시, STONITH 펜싱, 쿼럼 합의 기반 승격을 통해 RTO를 초 단위로 단축하고 데이터 무결성을 보장

## Ⅱ. 특징

<details><summary>용어 설명</summary>

- **히스테리시스(Hysteresis)**: 헬스체크 장애 진입 임계치(3회 연속 실패)와 정상 복귀 임계치(5회 연속 성공)를 다르게 설정하여 플래핑(Flapping) 오탐을 차단하는 제어 기법.
- **Fencing 선행 원칙**: 신규 Primary 승격 명령을 내리기 전에 반드시 구 Primary의 전원/네트워크를 물리적으로 차단(STONITH)하는 절대 안전 수칙.

</details>

- 단순 Ping을 넘어 DB 쿼리 실행 가능 여부를 판정하는 **심층 헬스체크(Deep Health Check)**
- 네트워크 단절 시에도 단일 노드만 승격되도록 통제하는 **과반수 쿼럼(Quorum: $N/2+1$) 합의**
- 로드밸런서 라우팅 및 DNS TTL을 자동으로 갱신하는 **무중단 트래픽 재라우팅**

#### 한줄 요약

- 장애 감지, 펜싱 격리, 쿼럼 승격, 라우팅 갱신의 전 과정을 자동화하여 사람의 실수 없는 초고속 복구를 실현

## Ⅲ. 구조 및 구성요소

<details><summary>용어 설명</summary>

- **자동 페일오버 4대 제어 모듈**: 상태 감지기(Detector), 결정 엔진(Decision Engine), 펜싱 에이전트(Fencing Agent), 전환 컨트롤러(Failover Controller).

</details>

```text
[ 자동 페일오버(Auto Failover) 파이프라인 및 제어 구조도 ]

 1. [ 상태 감지기 (Detector) ] ── (하트비트, 심층 헬스체크, 복제 지연 수집)
              │
              ▼
 2. [ 결정 엔진 (Decision Engine: Patroni / Raft Quorum) ] ──────┐
    • 과반수 합의 + 히스테리시스 검증 ➔ "지속적 치명 장애 확정"  │
    └─────────┬───────────────────────────────────────────────────┘
              │
              ▼
 3. [ 펜싱 에이전트 (Fencing: STONITH / Cloud API) ] ────────────┐
    • 구 Primary 인스턴스 전원 강제 차단 및 스토리지 연결 해제   │
    └─────────┬───────────────────────────────────────────────────┘
              │ (펜싱 성공 확인 후 승격 개시)
              ▼
 4. [ 전환 컨트롤러 (Failover Controller) ] ─────────────────────┐
    • Standby 노드를 신규 Primary로 승격 + VIP 및 DNS 라우팅 갱신│
    └─────────────────────────────────────────────────────────────┘
```

선의 의미: 감지기가 장애를 포착하면 결정 엔진이 쿼럼으로 확정하고, 펜싱 에이전트가 구 노드를 격리한 후 전환 컨트롤러가 Standby를 승격하는 구조.

| 구성요소 | 책임 |
|:---|:---|
| 상태 감지기 (Detector) | 하트비트, TCP 연결성, **복제 지연(Replication Lag)을 실시간 다중 수집** |
| 결정 엔진 (Decision Engine) | 쿼럼($N/2+1$) 투표와 히스테리시스를 통해 **일시적 오류를 배제하고 장애를 최종 확정** |
| 펜싱 에이전트 (Fencing) | 승격 전 **구 Primary 노드의 전원/네트워크를 강제 차단하여 스플릿 브레인 원천 방어** |
| 전환 컨트롤러 (Failover) | Standby를 **Primary로 승격하고 로드밸런서 VIP 및 서비스 디스커버리 라우팅 갱신** |

#### 한줄 요약

- 감지기, 결정 엔진, 펜싱 에이전트, 전환 컨트롤러가 결합하여 무인 자동 페일오버를 완수

## Ⅳ. 흐름도

<details><summary>용어 설명</summary>

- **자동 페일오버 5단계 수명주기**: 상태 감시 $\to$ 장애 확정 판정 $\to$ Fencing 선행 격리 $\to$ Standby 쿼럼 승격 $\to$ 트래픽 라우팅 전환.

</details>

```text
[ 자동 페일오버(Auto Failover) 실행 및 트래픽 전환 파이프라인 ]

 ┌────────────────────────────────────────┐
 │ 1. 하트비트 및 심층 헬스체크 다중 수집│
 └───────────────────┬────────────────────┘
                     │
                     ▼
 ┌────────────────────────────────────────┐
 │ 2. 쿼럼 과반수 합의 기반 장애 최종 판정│
 └───────────────────┬────────────────────┘
                     │
                     ▼
 ┌────────────────────────────────────────┐
 │ 3. Fencing: 구 Primary 전원/네트워크 차단
 ├───────────────────┬────────────────────┤
 │ 펜싱 성공         │ 펜싱 실패          │
 │ • 승격 절차 진행  │ • 자동 승격 중단   │
 │                   │   수동 승인 요구   │
 └───────────────────┴────────────────────┘
                     │
                     ▼
 ┌────────────────────────────────────────┐
 │ 4. Standby 노드를 신규 Primary로 승격  │
 └───────────────────┬────────────────────┘
                     │
                     ▼
 ┌────────────────────────────────────────┐
 │ 5. 로드밸런서 라우팅 및 DNS 갱신 완료  │
 └────────────────────────────────────────┘
```

### 동작 원리

1. 상태 감시: Patroni 데몬이 매 2초마다 Primary 데이터베이스의 하트비트와 복제 지연 시간을 etcd에 보고.
2. 장애 확정: Primary 노드가 3회 연속(10초간) 응답하지 않자 3개 etcd 노드 중 2개 이상의 동의로 장애를 선포.
3. 펜싱 실행: AWS API를 호출하여 응답 없는 구 Primary EC2 인스턴스를 강제 중지(`ec2:StopInstances`)시킴.
4. 신규 승격: WAL 로그가 가장 최신인 Standby 노드를 새로운 Primary로 승격하고 쓰기 모드를 활성화.
5. 트래픽 전환: HAProxy 로드밸런서의 상태 테이블과 DNS 레코드를 갱신하여 애플리케이션의 쿼리를 신규 Primary로 인계.

#### 한줄 요약

- 상태 감시 $\to$ 장애 확정 $\to$ 펜싱 실행 $\to$ 신규 승격 $\to$ 트래픽 전환의 5단계

## Ⅴ. 종류 및 비교

<details><summary>용어 설명</summary>

- **계층별 자동 페일오버**: 클라이언트 레벨, 서비스(웹/앱) 레벨, 데이터베이스(DB) 레벨 페일오버.

</details>

| 구분 | 클라이언트 페일오버 (Client Level) | 서비스 페일오버 (Service Level) | 데이터베이스 페일오버 (Data Level) |
|:---|:---|:---|:---|
| **적용 기준** | 모바일 앱, SDK 내부의 다중 엔드포인트 자동 재시도 | 무상태(Stateless) 웹 서버 및 K8s 파드 장애 전환 | 상태형 RDBMS (PostgreSQL, MySQL, Oracle) |
| **핵심 특징** | **지수 백오프+지터 재시도, 다중 DNS IP 라운드로빈** | **로드밸런서 헬스체크 기반 비정상 파드 즉시 제외** | **STONITH 펜싱 필수 선행, 쿼럼 합의 기반 리더 승격** |
| **한계** | 백엔드 전체 장애 시 클라이언트 단독으로 해결 불가 | 백엔드 데이터베이스 장애는 해결하지 못함 | 복제 지연으로 인한 극미량 데이터 유실(RPO) 위험 |

#### 한줄 요약

- 클라이언트는 재시도 분산, 웹 서비스는 로드밸런서 제외, 데이터베이스는 펜싱 기반 쿼럼 승격을 적용

## Ⅵ. 실무 고려사항 및 대책

<details><summary>용어 설명</summary>

- **지수 백오프와 지터(Exponential Backoff with Jitter)**: 페일오버 완료 직후 수천 개의 클라이언트가 신규 Primary로 동시에 재접속을 시도하여 2차 다운되는 현상(Thundering Herd)을 방어하는 재시도 지연 알고리즘.

</details>

| 문제 | 대책 | 효과 |
|:---|:---|:---|
| 순간적인 네트워크 튐 현상으로 불필요한 페일오버 남발 (Flapping) | **히스테리시스 기반 연속 3회 실패 및 쿨다운 타임(60초) 적용** | 오탐 페일오버 100% 방지 |
| Fencing 실패 상태에서 Standby를 강제 승격하여 이중 쓰기 발생 | **Fencing 실패 시 자동 승격을 즉시 중단하고 온콜 수동 개입 전환** | 데이터 오염 사고 원천 차단 |
| 페일오버 직후 수만 개 클라이언트의 동시 재접속 폭주 (Thundering Herd) | **클라이언트 SDK에 `Exponential Backoff with Jitter` 강제 적용** | 신규 Primary 서버 과부하 보호 |

#### 한줄 요약

- 히스테리시스 오탐 방지, 펜싱 안전 중단, 지수 백오프 지터를 통해 자동 페일오버의 안정성을 보장

## Ⅶ. 결론

<details><summary>용어 설명</summary>

- **카오스 복원력 엔지니어링(Chaos Resilience)**: 정기적으로 운영 환경에 무작위 노드 다운을 유발하여 Auto Failover가 RTO(30초) 이내에 무결하게 완료되는지 증적을 확보하는 활동.

</details>

- **자동 페일오버**는 고가용성 인프라의 최종 완성 단계이며, 속도보다 안전(Safety First)을 최우선으로 하여 STONITH 펜싱과 쿼럼 합의가 검증된 경우에만 자동 승격을 수행하도록 설계해야 함

#### 한줄 요약

- Fencing 선행 격리와 쿼럼 합의 및 트래픽 재라우팅을 통해 안전하고 완벽한 무인 자동 복구를 완성
