## Ⅰ. 개요

<details><summary>핵심 용어</summary>

- **Saga Pattern (사가 패턴)**: 마이크로서비스(MSA) 환경에서 2PC의 성능 저하를 피하기 위해, 긴 분산 트랜잭션을 여러 개의 로컬 트랜잭션으로 쪼개고, 실패 시 완료된 트랜잭션을 역순으로 되돌리는 보상(Compensating) 트랜잭션 패턴.
- **2PC (Two-Phase Commit, 2단계 커밋)**: 분산된 여러 데이터베이스가 모두 커밋할 준비가 되었는지 투표(Prepare)한 후, 만장일치일 때만 일제히 커밋(Commit)하여 강력한 원자성(Atomicity)을 보장하는 전통적 프로토콜.
- **Coordinator (조정자)**: 2PC에서는 모든 노드의 투표를 집계하여 최종 커밋/롤백을 지시하는 중앙 주체이며, Saga(오케스트레이션 방식)에서는 상태 머신을 통해 각 MSA의 트랜잭션과 보상 단계를 중앙 제어하는 주체.

</details>

- 정의/개념: 분산 데이터베이스 환경의 데이터 정합성을 맞추기 위해, 강한 원자성을 띠는 동기식 **2PC** 모델과, 최종 일관성을 지향하는 비동기식 보상 트랜잭션 모델인 **Saga Pattern**의 분산 트랜잭션 관리 전략
- 배경/필요성: 단일 데이터베이스(Monolithic)의 ACID 트랜잭션을 Database per Service(MSA) 환경에 그대로 적용할 수 없어, 성능(가용성)과 데이터 정합성 사이의 트레이드오프를 해결할 아키텍처 패턴 요구성

#### 한줄 요약

- Saga는 끝난 일을 반대 업무로 상쇄하고 2PC는 모든 참여자가 준비될 때까지 잠근 뒤 함께 확정한다.

## Ⅱ. 특징 (원자성 대 최종 일관성 비교)

<details><summary>핵심 용어</summary>

- **Compensating Transaction (보상 트랜잭션)**: 이미 커밋(Commit)되어 물리적으로 되돌릴 수 없는 로컬 트랜잭션의 논리적 효과를 무효화하기 위해, 반대되는 작업(예: 결제 완료 $\rightarrow$ 결제 취소 API 호출)을 수행하는 비즈니스 트랜잭션.

</details>

- **2PC**: Strong Consistency(강한 일관성), Blocking(동기식 차단), Database-Level(인프라 계층), 단일 장애점(Coordinator SPOF) 내재
- **Saga**: Eventual Consistency(최종 일관성), Non-Blocking(비동기 비차단), Application-Level(비즈니스 로직 계층), 보상 복잡도 증가
- **Isolation (고립성) 포기**: Saga 패턴은 트랜잭션 도중 다른 사용자가 중간 상태(예: 임시 예약 상태)를 볼 수 있으므로 ACID 중 'I'를 사실상 포기

#### 한줄 요약

- Saga는 긴 분산 잠금을 없애는 대신 중간 상태와 보상 책임이 생기고 2PC는 원자성을 얻는 대신 준비 상태의 자원 대기가 생긴다.

## Ⅲ. 구조 및 구성요소 (분산 트랜잭션 제어 아키텍처)

<details><summary>핵심 용어</summary>

- **Orchestration (오케스트레이션)**: Saga의 구현 방식 중 하나로, 중앙의 오케스트레이터(Saga Execution Coordinator)가 상태 머신에 따라 각 서비스에게 해야 할 일(Command)을 순차적으로 지시하고 실패 시 보상 트랜잭션까지 통제하는 중앙집중형 구조.
- **Choreography (코레오그래피)**: 중앙 통제 없이, 각 마이크로서비스가 자신이 할 일을 마친 뒤 이벤트를 발행(Publish)하면 다른 서비스가 이를 구독(Subscribe)하여 다음 할 일을 알아서 수행하는 릴레이 구조.

</details>

```text
┌─────────────────────────┐       ┌─────────────────────────┐
│     2PC Architecture    │   VS  │    Saga Architecture    │
├─────────────────────────┤       ├─────────────────────────┤
│ [Transaction Manager]   │       │ [Order Service (시작)]  │
│    │               │    │       │    │ (로컬 DB 커밋)     │
│    ▼ (1. Prepare)  ▼    │       │    ▼ (이벤트 발행)      │
│ [DB 1]           [DB 2] │       │ [Payment Service (결제)]│
│    │ (2. Commit)   │    │       │    │ (로컬 DB 커밋)     │
│    ▼               ▼    │       │    ▼ (이벤트 발행)      │
│ (Lock 해제)     (Lock 해제)│       │ [Stock Service (재고)]  │
└─────────────────────────┘       └─────────────────────────┘
```

선의 의미: 2PC는 매니저가 하위 DB의 락(Lock)을 쥔 채로 일괄 통제하며, Saga는 서비스별로 즉시 커밋 후 비동기 이벤트를 통해 다음 서비스로 릴레이하는 느슨한 구조.

| 구성요소 | 2PC 기반 메커니즘 | Saga 기반 메커니즘 |
|:---|:---|:---|
| **트랜잭션 주체** | **DB나 XA 트랜잭션 매니저 (미들웨어)** | **각 MSA의 애플리케이션 (비즈니스 코드)**|
| **에러 롤백 방식**| **DB 엔진 차원의 물리적 원자적 ROLLBACK** | **애플리케이션 차원의 보상(취소) API 호출**|
| **Lock (잠금)** | 트랜잭션 완료 시까지 **모든 DB Lock 유지** | Lock 없이 **각 서비스 로컬 단위로 즉시 해제**|
| **상태 관리** | 트랜잭션 매니저의 WAL (Write-Ahead Log) | **Saga 상태 저장소 (State Machine DB) 활용**|

#### 한줄 요약

- 호출자는 한 업무를 요청하고 조정자는 Saga라면 단계와 보상을, 2PC라면 준비 투표와 최종 결정을 기록한다.

## Ⅳ. 흐름도 (2PC 장애 시나리오 대 Saga 보상 시나리오)

<details><summary>핵심 용어</summary>

- **Pivot Transaction (피벗 트랜잭션)**: Saga 패턴에서 "이 트랜잭션이 성공하면 전체 Saga는 웬만하면 성공으로 가야 한다"는 분수령 역할을 하는 트랜잭션 (보통 외부 결제 연동이나 변경 불가능한 작업이 피벗이 됨).

</details>

```text
[Saga 실패 및 보상 흐름 (Choreography)]
   1. [주문 MSA] (주문생성 커밋) ──(주문생성 이벤트)──► 
   2. [결제 MSA] (결제성공 커밋) ──(결제완료 이벤트)──►
   3. [재고 MSA] (재고차감 실패) ──(재고부족 이벤트)──► 
   4. [결제 MSA] ◄──(보상 수신) (결제취소 커밋) ──(결제취소 이벤트)──►
   5. [주문 MSA] ◄──(보상 수신) (주문상태 취소 커밋) (Saga 최종 롤백 수렴)

[2PC 정상 흐름 (동기식)]
   1. Coordinator ──(Prepare)──► Node A, Node B
   2. Node A, B ──(Prepared 락 확보 응답)──► Coordinator
   3. Coordinator ──(Commit)──► Node A, Node B (동시 확정 및 락 해제)
```

### 동작 원리

1. **2PC (동기)**: 모든 노드가 `Prepare` 단계에서 데이터를 업데이트하고 커밋만 남겨둔 채 락을 잡고 대기하며, `Commit` 명령이 떨어져야 일제히 확정.
2. **Saga (비동기)**: 재고 차감에서 실패(3번)가 발생하면, 시스템은 이전에 수행되었던 2번(결제)과 1번(주문)의 로컬 커밋을 취소하기 위한 **반대 성격의 보상 API**를 역순으로 호출.
3. **최종 수렴**: 모든 보상 처리가 끝나면 시스템은 처음과 같이 논리적으로 정합성이 맞는 상태로 복귀 (**Saga 복구 완결**).

#### 한줄 요약

- 주문과 재고 예약 뒤 결제가 실패하면 이미 끝난 재고 예약을 반대 거래로 해제하고 주문을 취소 상태로 수렴시킨다.

## Ⅴ. 종류 및 비교 (Saga 코레오그래피 대 오케스트레이션 비교)

<details><summary>핵심 용어</summary>

- **Semantic Lock (의미론적 잠금)**: Saga에서 물리적 DB Lock을 쓸 수 없으므로, 애플리케이션 레벨에서 상태를 `PENDING(진행중)`으로 마킹하여 다른 트랜잭션의 접근을 논리적으로 통제하는 기법.

</details>

| 비교 항목 | Saga (코레오그래피) | Saga (오케스트레이션) |
|:---|:---|:---|
| **제어 주체** | **중앙 통제 없음 (이벤트 퍼블리셔/구독자)** | **단일 오케스트레이터 (상태 머신 서버)** |
| **적합한 규모** | 2~4개 서비스가 엮인 **간단한 트랜잭션** | 5개 이상의 **복잡하고 단계가 긴 트랜잭션** |
| **장점** | 단일 장애점(SPOF) 없음, 결합도 최하 | 전체 흐름 파악 용이, 순환 참조 발생 위험 없음 |
| **단점 (문제점)**| 프로세스 파악이 어려움, 테스트 매우 복잡 | 오케스트레이터 자체가 병목이나 SPOF 우려 |

#### 한줄 요약

- 독립 서비스의 장기 주문 흐름은 Saga를, 같은 관리 범위의 지원 자원에서 모두 함께 확정해야 하는 짧은 거래는 2PC를 검토한다.

## Ⅵ. 실무 고려사항 및 대책 (분산 트랜잭션 3대 실무 난제 대책)

<details><summary>핵심 용어</summary>

- **Idempotency (멱등성)**: 보상 트랜잭션(결제 취소) 요청이 네트워크 오류로 2번 이상 들어오더라도, 이미 취소된 건이라면 추가 환불(사이드 이펙트) 없이 무시되도록 시스템을 설계하는 필수 원칙.

</details>

| 3대 분산 트랜잭션 난제 | 발생 원인 | 실무 대책 및 해결방안 |
|:---|:---|:---|
| **1. 보상 트랜잭션 실패** | 결제 취소 API 호출 시 네트워크 타임아웃 | **메시지 큐(Kafka)를 통한 무한 재시도 및 수동 개입(DLQ) 알람** |
| **2. 보상 멱등성 파괴** | 결제 취소가 재전송되어 이중 환불 발생 | **이벤트 식별자(ID) 기반 DB 멱등성 검사 로직 적용**|
| **3. 동시성 데이터 오염**| 커밋된 중간 상태를 다른 사용자가 읽음 | **Semantic Lock (`PENDING` 상태 플래그)으로 접근 차단**|

> 사례: **배달의민족 결제/배달 연동 시 이벤트(Kafka) 기반 코레오그래피 및 AWS Step Functions 기반 오케스트레이션 혼용 사례**

#### 한줄 요약

- 외부 송금처럼 되돌릴 수 없는 단계는 피벗 뒤에 두고 이후 실패는 취소가 아니라 별도 환불 업무로 보정해야 한다.

## Ⅶ. 결론

<details><summary>핵심 용어</summary>

- **트랜잭션 선택 기준**: 시스템 결합도, 성능(비동기 여부), 물리적 락(Lock) 허용 여부, 롤백 비용에 의거하여 분산 트랜잭션 처리 패턴을 결정하는 기준.

</details>

- **분산 트랜잭션 선택 기준**에 따라 단일 RDBMS 인트라넷 환경은 **2PC/XA**, 클라우드 네이티브 MSA 환경은 **Saga Pattern** 필수 채택

#### 한줄 요약

- 보상 가능한 장기 서비스 흐름은 Saga로, 모든 자원이 지원하고 짧은 원자 확정이 필요한 거래만 2PC로 제한해야 한다.
