## Ⅰ. 개요

<details><summary>용어 설명</summary>

- **12 팩터 앱(The Twelve-Factor App)**: Heroku 엔지니어들이 피똥 싸며 깨달은, "제발 클라우드에서 앱 돌릴 거면 이 12가지 룰은 지켜라"라고 박아놓은 클라우드 네이티브의 십계명(12계명)이다.
- **클라우드 네이티브(Cloud-Native App)**: 옛날 전산실 서버처럼 고이 모시는 게 아니라, K8s 컨테이너 위에서 죽으면 다시 살리고 트래픽 터지면 막 늘어나는(Scale-out) 모던 애플리케이션이다.
- **무상태(Stateless)**: 서버 메모리에 유저 로그인 세션 같은 찌꺼기를 안 남기고, 언제 죽든 딴 서버가 바로 이어받을 수 있게 모든 상태를 외부 DB(Redis 등)로 몰빵하는 클라우드의 핵심 구조이다.

</details>

- 정의: 클라우드(Docker/K8s) 환경에서 서버를 뗐다 붙였다(Scale-out) 맘대로 하기 위해 반드시 지켜야 할 12가지 모던 개발 룰인 **12-Factor App**
- 배경: "내 로컬 피씨에선 되는데요?" 시전하거나 서버 로컬에 상태(세션/파일)를 저장하면, **서버 늘릴 때마다 에러가 터지고 컨테이너가 뻗어버리기** 때문

#### 한줄 요약

- 클라우드에서 서버를 고무줄처럼 맘대로 늘리고 줄이려면 반드시 지켜야 할 12가지 헌법이다.

## Ⅱ. 특징

<details><summary>용어 설명</summary>

- **개발/운영 동등성(Dev/Prod Parity)**: 개발 피씨에선 SQLite 쓰고 실서버엔 Oracle 써놓고 에러 나면 핑계 대지 말고, 개발/테스트/운영 환경의 도구와 DB를 똑같이 맞추라는 팩폭 원칙이다.
- **폐기 가능성(Disposability)**: 컨테이너는 언제든 죽고 새로 뜰 수 있으니, 켤 때 1초 만에 켜지고 죽을 때 하던 일 마무리하고 깔끔하게 죽는(Graceful Shutdown) 쿨한 프로세스를 만들어야 한다.

</details>

- DB 비번 같은 설정(Config)은 코드에 하드코딩하지 말고 무조건 **환경 변수(ENV)**로 찢어버림.
- 앱은 철저히 **무상태(Stateless)**로 짜서, 언제든 죽이고 새로 띄우는 **수평 확장(Scale-out)**을 지원함.
- 개발/운영 환경 격차를 없애고(**Dev/Prod Parity**), 켜고 끄는 게 번개처럼 빠른 프로세스(**Disposability**)를 지향함.

#### 한줄 요약

- 설정은 밖으로 빼고, 로컬에 찌꺼기 안 남기며, 개발 피씨와 실서버를 똑같이 맞추는 게 핵심이다.

## Ⅲ. 구조 및 구성요소

<details><summary>용어 설명</summary>

- **지원 서비스(Backing Services)**: DB, Redis, 카프카, 메일 서버 등 앱이 쓰는 모든 외부 서비스를 언제든 URL만 바꾸면 갈아 끼울 수 있는(탈부착 가능한) 리소스로 취급하라는 룰이다.

</details>

```text
[ 12 팩터 클라우드 네이티브 십자포화 아키텍처 ]

[ 코드베이스 (Git 1개) ] ──▶ [ 빌드(Build) ➔ 릴리스(Release) ➔ 실행(Run) 철저히 분리 ]
                                                 │ (설정 ENV 주입)
                                                 ▼
       (로컬 디스크 쓰지 마!) ◀── [ 프로세스 (Stateless, 맘대로 늘리고 죽임) ]
                                                 │ (주소 바꿔서 탈부착)
                                                 ▼
                                   [ 지원 서비스 (DB, Redis, S3 등) ]
```

| 12 팩터 주요 원칙 | 팩트 폭행 책임 |
|:---|:---|
| 1. **코드베이스 (Codebase)** | 앱 하나당 Git 레포 하나 파라. 여기저기 섞어 쓰지 말고 버전 관리 빡세게 해라 |
| 3. **설정 (Config)** | DB 비번 코드에 하드코딩하지 마라. 무조건 환경 변수(ENV)로 찢어내라 |
| 4. **지원 서비스 (Backing)** | DB나 Redis는 로컬에 깔지 말고 언제든 주소만 바꿔서 탈부착 가능하게 써라 |
| 6. **프로세스 (Processes)** | 서버 메모리에 세션 두지 마라. 무조건 무상태(Stateless)로 짜서 언제든 죽여라 |
| 11. **로그 (Logs)** | 로그 파일로 남기지 마라. 콘솔(stdout)로 쏘면 Datadog이나 ELK가 주워 가게 해라 |

#### 한줄 요약

- 1 Codebase, 환경 변수 주입, 무상태 프로세스, stdout 로그가 12팩터의 엑기스다.

## Ⅳ. 흐름도

<details><summary>용어 설명</summary>

- **빌드-릴리스-실행 분리(Build-Release-Run Pipeline)**: 소스 코드를 컴파일하는 '빌드', 거기에 DB 주소(환경 변수)를 합치는 '릴리스', 실제로 컨테이너를 띄우는 '실행' 단계를 절대 섞지 말고 3단계로 칼같이 끊으라는 룰이다.

</details>

```text
[ 12-Factor 배포 및 실행 십자포화 흐름 ]
┌──────────────────────────────┐
│ 1. Git Codebase (단일 원본)  │
└──────────────┬───────────────┘
               ▼ (코드 컴파일)
┌──────────────────────────────┐
│ 2. 빌드 (Build 단계)         │
│ (바이너리/도커 이미지 굽기)  │
└──────────────┬───────────────┘
               ▼ (환경 변수 ENV 주입)
┌──────────────────────────────┐
│ 3. 릴리스 (Release 단계)     │
│ (빌드본 + 실서버 Config 결합)│
└──────────────┬───────────────┘
               ▼ (컨테이너 띄우기)
┌──────────────────────────────┐
│ 4. 실행 (Run 단계)           │
│ (Stateless 프로세스로 띄움)  │
└──────────────────────────────┘
```

### 동작 원리

1. 코드베이스: Git에서 코드를 땡겨옴.
2. 빌드: 코드를 컴파일하고 의존성을 땡겨와서 불변의 도커(Docker) 이미지로 구워버림.
3. 릴리스: 구워진 이미지에 "운영 DB 주소" 같은 환경 변수(Config)를 주사기로 찔러 넣음.
4. 실행: K8s나 도커가 릴리스 버전을 가져다가 팍팍 띄움. 맘대로 죽이고 늘려도 됨.

#### 한줄 요약

- 코드 굽기(Build) $\to$ 환경 변수 넣기(Release) $\to$ 서버 띄우기(Run) 단계를 절대 섞지 마라.

## Ⅴ. 종류 및 비교

<details><summary>용어 설명</summary>

- **레거시 모놀리스 vs 12 팩터 앱(Legacy Monolith vs 12-Factor App)**: 전산실 서버 안에 세션, 파일, 설정 다 때려 박아서 서버 한 대 죽으면 대참사 나는 레거시와, 언제든 컨테이너 날리고 다시 띄우는 쿨한 12 팩터 앱의 차이이다.

</details>

| 비교 항목 | **레거시 (Traditional App)** | **12 팩터 (Cloud-Native App)** |
|:---|:---|:---|
| 설정 관리 | `application.xml`에 DB 비번 하드코딩함 | **OS 환경 변수(ENV)**로 밖에서 주입함 |
| 상태/세션 | 로컬 서버 메모리에 세션 저장함 (Sticky) | **무상태(Stateless)**. 세션은 Redis로 다 던짐 |
| 로그 처리 | 서버 안 `/var/log`에 파일로 씀 | **표준 출력(stdout)**으로 쏘면 외부에서 주워 감 |
| 스케줄 작업| 서버 안에서 Crontab 돌림 | **K8s CronJob** 같은 일회성 프로세스로 돌림 |

#### 한줄 요약

- 서버를 '반려동물(애지중지)'처럼 키우면 레거시, 언제든 갈아치우는 '가축'처럼 다루면 12 팩터다.

## Ⅵ. 실무 고려사항 및 대책

<details><summary>용어 설명</summary>

- **우아한 종료(Graceful Shutdown)**: K8s가 서버를 죽일 때(SIGTERM 신호), 하던 결제 처리는 마저 끝내고 DB 커넥션도 예쁘게 끊은 뒤에 얌전히 관짝에 들어가는 신사적인 종료 매너이다.

</details>

| 문제 | 대책 | 효과 |
|:---|:---|:---|
| 깃허브 코드에 AWS 키랑 DB 비번 올라가서 해커한테 털림 | 설정을 무조건 코드에서 찢어서 **환경 변수(ENV)**로 주입함 | 깃허브 털려도 보안키 안 털리는 철벽 방어 |
| 서버 재시작할 때 결제 중이던 유저 튕기고 돈 증발함 | SIGTERM 신호 받으면 기존 요청 끝내고 죽는 **Graceful Shutdown** 적용 | 런타임 데이터 유실 0% 멱살 방어 |
| 도커 컨테이너 죽었더니 안에 있던 로그 파일도 싹 날아감 | 로그는 무조건 **표준 출력(stdout)**으로 쏘게 만들어서 밖에서 낚아챔 | 컨테이너가 뒈지든 말든 로그는 안전하게 보관 |

#### 한줄 요약

- 비번은 환경 변수로, 세션은 Redis로, 로그는 stdout으로, 종료는 우아하게(Graceful) 해라.

## Ⅶ. 결론

<details><summary>용어 설명</summary>

- **클라우드 네이티브 도입 기준(Cloud-Native Architecture Standards)**: 회사가 그냥 서버실에 짱박아둘지, AWS/K8s 위에서 트래픽 따라 서버를 고무줄처럼 늘릴지 각을 재는 잣대이다.

</details>

- **클라우드 네이티브 도입 기준** 원칙에 따라, 트래픽 터지고 자동 스케일링(K8s)이 필수인 서비스는 **12-Factor App**, 고정 장비에서 도는 앱은 **일반 아키텍처** 채택 기조 확립함

#### 한줄 요약

- 클라우드(AWS, K8s) 쓰면서 12 팩터 안 지키면, 돈만 비싸게 내고 레거시 똥 치우는 격이다.
