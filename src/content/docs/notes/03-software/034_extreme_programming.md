## Ⅰ. 개요

<details><summary>용어 설명</summary>

- **익스트림 프로그래밍(XP, Extreme Programming)**: 1~2주마다 미친 듯이 소통하고, 좋은 개발 관행(TDD, 페어 코딩 등 12가지 실천법)을 극한(Extreme)까지 끌어올려 소프트웨어 품질을 쥐어짜는 애자일 방법론이다.
- **짝 프로그래밍(Pair Programming)**: 개발자 두 명이 컴퓨터 1대에 붙어서, 한 놈(Driver)은 코딩하고 한 놈(Navigator)은 훈수 두면서 실시간으로 버그를 잡아내는 영혼의 듀오 코딩이다.
- **테스트 주도 개발(TDD, Test-Driven Development)**: 코드부터 짜지 않고 무조건 '실패하는 테스트(Red)'부터 만든 다음, 그걸 통과할 만큼만 최소한으로 코딩(Green)하고, 나중에 예쁘게 다듬는(Refactoring) 역발상 개발법이다.

</details>

- 정의: 12가지 빡센 공학 실천법(TDD, 짝 프로그래밍 등)을 통해 피드백을 극단적으로 당겨서 퀄리티를 올리는 **XP(Extreme Programming)**
- 배경: 코딩 다 끝나고 막판에 테스트하면, 버그 원인 찾느라 밤새우고 **디버깅과 재작업 비용이 폭발**하기 때문

#### 한줄 요약

- 코드 품질을 극한으로 끌어올리기 위해 테스트 먼저 짜고 둘이서 같이 짜는 개발법이다.

## Ⅱ. 특징

<details><summary>용어 설명</summary>

- **5대 핵심 가치(5 Core Values)**: 용기(Courage) 있게 코드를 갈아엎고, 서로 존중(Respect)하며, 미친 듯이 소통(Communication)해서 단순(Simplicity)하고 빠른 피드백(Feedback)을 받자는 XP의 5대 정신이다.
- **공동 코드 소유(Collective Code Ownership)**: "이거 내가 짠 거니까 건들지 마!"를 금지하고, 팀원 누구나 남의 코드를 뜯어고치고 리팩토링할 수 있는 완전 오픈형 소유권이다.

</details>

- XP의 영혼인 **5대 핵심 가치(소통, 단순성, 피드백, 용기, 존중)**를 실천함.
- TDD, 리팩토링, CI(지속적 통합) 등 개발자를 빡세게 굴리는 **공학 실천법**을 숨 쉬듯 씀.
- **짝 프로그래밍(Pair Programming)**으로 혼자 뻘짓을 막고, **공동 코드 소유**로 팀원 전체가 책임짐.

#### 한줄 요약

- 소통과 피드백을 위해 공동 소유, 짝 프로그래밍, TDD 같은 빡센 룰을 무조건 지킨다.

## Ⅲ. 구조 및 구성요소

<details><summary>용어 설명</summary>

- **리팩토링(Refactoring)**: 앱이 겉으로 똑같이 동작하게 냅둔 상태에서, 내부 스파게티 코드를 깔끔하게 청소해서 기술 부채를 갚는 대청소 작업이다.

</details>

```text
[ XP 핵심 실천법 십자포화 아키텍처 ]

        [ TDD (테스트 주도 개발) ]
        (실패 테스트 ➔ 통과 ➔ 리팩토링)
                │
        [ 짝 프로그래밍 (Pair) ]
     (키보드 1대, 개발자 2명의 실시간 리뷰)
                │
       [ 지속적 통합 (CI) ]
    (하루에도 수십 번씩 빌드 서버에 병합)
```

| 구성요소 | 책임 |
|:---|:---|
| **TDD (테스트 주도)** | 코딩 전 무조건 테스트부터 짜서, 버그가 발붙일 틈을 안 주는 안전망 |
| **짝 프로그래밍** | Driver가 깡코딩 갈길 때 Navigator가 아키텍처 훈수 두면서 실시간 코드 리뷰하는 듀오 |
| **리팩토링** | 똥 코드를 그대로 두지 않고 겉은 멀쩡하게, 속은 우아하게 고쳐서 기술 빚 청산 |
| **지속적 통합 (CI)** | 다 짠 코드를 한 달 뒤에 합치지 않고, 하루에도 열 번씩 합쳐서 '통합 지옥'을 방지함 |

#### 한줄 요약

- 테스트 먼저 짜고(TDD), 둘이서 같이 짜고(Pair), 다 짰으면 바로바로 합친다(CI).

## Ⅳ. 흐름도

<details><summary>용어 설명</summary>

- **Red-Green-Refactor 루프**: TDD의 근본 3단계. 에러 뜨는 테스트(Red) $\to$ 무지성 통과(Green) $\to$ 코드 예쁘게 다듬기(Refactor)의 무한 반복 사이클이다.

</details>

```text
[ TDD 기반 개발 십자포화 흐름 (Red-Green-Refactor) ]
┌──────────────────────────────┐
│ 사용자 스토리 ➔ TDD 시작   │
└──────────────┬───────────────┘
               ▼
┌──────────────────────────────┐
│ 1. 실패하는 테스트 작성(Red) │
│ (당연히 안 짰으니 빨간불)    │
└──────────────┬───────────────┘
               ▼
┌──────────────────────────────┐
│ 2. 최소 구현으로 통과(Green) │
│ (돌아가게만 깡코딩해서 통과) │
└──────────────┬───────────────┘
               ▼
┌──────────────────────────────┐
│ 3. 리팩토링 (Refactoring)    │
│ (초록불 유지하며 코드 청소)  │
└──────────────┬───────────────┘
               ▼
┌──────────────────────────────┐
│ 4. CI 서버 병합 (통합)       │
│ (전체 테스트 돌리고 합침)    │
└──────────────────────────────┘
```

### 동작 원리

1. 실패 테스트(Red): 요구사항(스토리)을 바탕으로 무조건 에러가 나는 테스트 코드부터 선빵침.
2. 최소 통과(Green): 하드코딩을 하든 뭘 하든 일단 테스트만 통과하게 최단기로 코딩함.
3. 리팩토링(Refactor): 테스트 통과(안전망)를 믿고, 쓰레기 코드를 중복 없는 예쁜 코드로 청소함.
4. CI 통합: 짝꿍이랑 다 짰으면 당일 퇴근 전에 무조건 메인 브랜치에 합쳐버림.

#### 한줄 요약

- 테스트 실패 $\to$ 어떻게든 통과 $\to$ 예쁘게 청소 $\to$ 서버에 병합하는 무한 루프다.

## Ⅴ. 종류 및 비교

<details><summary>용어 설명</summary>

- **스크럼 vs XP(Scrum vs XP)**: 둘 다 애자일이지만, 스크럼은 "회의는 언제 하고 직책은 뭐다"라는 관리 룰(프레임워크)이고, XP는 "테스트 먼저 짜고 2명이 같이 짜라"는 개발 공학 실천법이다.

</details>

| 비교 항목 | **XP (익스트림 프로그래밍)** | **Scrum (스크럼)** |
|:---|:---|:---|
| 멱살 잡는 포커스 | TDD, Pair 등 **엔지니어링(공학적) 실천법** | PO, SM 등 **조직 관리 및 룰(3-5-3)** |
| 룰의 유연성 | 스프린트 도중에도 긴급 기획 변경 유연하게 받음 | 2주 스프린트 시작되면 웬만해선 안 바꿈 |
| 업무 방식 | 짝지어서 1대의 컴퓨터로 찰싹 붙어 일함 (Pair) | 각자 태스크 가져가서 찢어져서 코딩함 |
| 실무 국룰 조합 | 보통 독자적으로 안 쓰고 **Scrum 팀 안에서 XP를 돌림** | 애자일의 기본 베이스 뼈대로 사용됨 |

#### 한줄 요약

- 스크럼은 조직 관리법이고, XP는 코드를 빡세게 짜는 기술 훈련법이다. (보통 둘을 섞어 쓴다)

## Ⅵ. 실무 고려사항 및 대책

<details><summary>용어 설명</summary>

- **페어 피로도(Pair Fatigue)**: 개발자 두 명이 하루 종일 모니터 하나 보면서 입 털고 코딩하다가, 기 빨리고 체력 방전돼서 집에 가면 쓰러지는 현상이다.

</details>

| 문제 | 대책 | 효과 |
|:---|:---|:---|
| 8시간 내내 짝 코딩했더니 멘탈 털려서 퇴사 말림 (**페어 피로도**) | 쉬운 뷰 짜는 건 혼자 하고, 핵심 코어 로직만 **선택적 페어** 진행 | 검토 효과는 챙기면서 개발자 멘탈과 체력 보존 |
| TDD 한답시고 테스트 짜느라 진도 안 나가서 욕 처먹음 | 당장은 느려도 **장기적 부채 0** 됨을 증명하고 CI 툴 자동화 떡칠 | 나중에 버그 잡느라 밤새는 시간 1/10로 깎음 |
| 상주 고객을 앉혀놓으라는데 고객이 바빠서 안 옴 | 도메인 잘 아는 **PO(제품 책임자)**가 대리인 역할 멱살 잡음 | 요구사항 물어보면 1분 만에 대답해 주는 환경 |

#### 한줄 요약

- 온종일 페어하면 죽어나가니 조절하고, TDD로 당장 느려져도 결국 버그가 줄어 이득이다.

## Ⅶ. 결론

<details><summary>용어 설명</summary>

- **XP 실천법 정착 기준(XP Practices Adoption Criteria)**: 팀이 진짜 TDD를 숨 쉬듯 하는지, 자동화 커버리지가 높은지 각 재서 XP의 도입 수위를 정하는 잣대이다.

</details>

- **XP 실천법 정착 기준** 원칙에 따라, 실무에선 **Scrum(관리 뼈대) + XP(TDD/페어 실천법)**을 스까서 애자일 풀세트로 채택하는 기조 확립함

#### 한줄 요약

- 실무에서는 관리하기 좋은 스크럼에 품질 쥐어짜는 XP(TDD)를 섞어서 쓰는 게 국룰이다.
