## Ⅰ. 개요

<details><summary>용어 설명</summary>

- **TDD 및 짝 프로그래밍(TDD & Pair Programming)**: 테스트 코드를 먼저 작성해 안전망을 구축하고 두 개발자가 실시간으로 코드를 교차 검증하는 XP 실천법.
- **결함 수정 비용 폭증(Exponential Defect Cost)**: 요구분석/설계 오류가 배포 직전에야 발견되어 처음부터 재작업해야 하는 공학적 손실.

</details>

- 정의/개념: 소통·피드백·단순성 5대 가치 하에 **TDD, 짝 프로그래밍, CI/리팩토링** 등 12가지 공학 실천법을 극단적으로 적용하는 개발 방법론
- 배경/필요성: 개발 후반부 결함 발견 시 발생하는 **수정 비용 기하급수적 폭증 및 요구사항 변경 수용 실패** 직면

#### 한줄 요약

- TDD로 테스트를 선행하고 짝 프로그래밍·CI로 조기 피드백을 극대화하여 코드 품질을 향상하는 방법론

## Ⅱ. 특징

<details><summary>용어 설명</summary>

- **5대 핵심 가치**: 소통(Communication)·단순성(Simplicity)·피드백(Feedback)·용기(Courage)·존중(Respect)으로 구성된 XP의 행동 원칙.
- **공동 코드 소유(Collective Code Ownership)**: 팀원 누구나 코드베이스 전체를 수정·리팩토링할 수 있는 소유권 공유 원칙으로 기술 지식 고립 방지.

</details>

- XP의 **5대 핵심 가치**를 실천 기반으로 설정
- TDD·리팩토링·CI 등 공학 실천법을 일상적으로 적용
- **짝 프로그래밍**으로 실시간 코드 리뷰를 수행하고, **공동 코드 소유**로 팀 전체가 코드 품질에 책임

#### 한줄 요약

- 5대 가치 기반으로 TDD·짝 프로그래밍·공동 코드 소유 등의 공학 실천법을 조합하여 품질 향상

## Ⅲ. 구조 및 구성요소

<details><summary>용어 설명</summary>

- **리팩토링(Refactoring)**: 외부 동작을 유지하면서 내부 코드 구조를 개선하여 기술 부채를 감소시키는 체계적 코드 개선 활동.

</details>

```text
[ XP 핵심 실천법 구성 ]
TDD (테스트 주도 개발)
└─ Red → Green → Refactor 사이클로 품질 안전망 형성
짝 프로그래밍 (Pair Programming)
└─ 드라이버(코딩) + 내비게이터(검토)로 실시간 코드 리뷰
지속적 통합 (CI)
└─ 일 단위 코드 병합으로 통합 오류 조기 탐지
공동 코드 소유
└─ 팀원 전체가 코드베이스 전체 수정·개선 권한 보유
```

선의 의미: 가지(`└─`)는 각 XP 실천법의 목적과 효과 관계

| 구성요소 | 책임 |
|:---|:---|
| **TDD** | 테스트 선행 작성으로 버그 발생 방지 및 리팩토링 안전망 제공 |
| **짝 프로그래밍** | 실시간 코드 리뷰·지식 공유·오류 조기 발견 |
| **리팩토링** | 외부 동작 유지 기반 내부 코드 구조 지속 개선 |
| **지속적 통합(CI)** | 빈번한 코드 병합으로 통합 오류 조기 탐지 |

#### 한줄 요약

- TDD가 품질 안전망을 형성하고, 짝 프로그래밍이 실시간 검토를 수행하며, CI가 통합 오류를 조기에 탐지

## Ⅳ. 흐름도

<details><summary>용어 설명</summary>

- **Red-Green-Refactor 루프**: TDD의 핵심 3단계 순환으로, 실패 테스트 작성(Red)→최소 구현 통과(Green)→코드 개선(Refactor)을 반복.

</details>

```text
사용자 스토리 수신
   │
   ▼
1. 실패하는 테스트 작성 (Red)
   └─ 구현 전 요구사항을 검증하는 테스트 코드 작성 (실패 확인)
   │
   ▼
2. 최소 구현으로 테스트 통과 (Green)
   └─ 테스트를 통과하는 최소한의 구현 코드 작성
   │
   ▼
3. 리팩토링 (Refactor)
   └─ 테스트 통과 유지하며 코드 중복 제거·구조 개선
   │
   ▼
4. CI 서버 병합 (지속적 통합)
   └─ 전체 테스트 실행 후 메인 브랜치 병합
   │
   └─ 다음 스토리 → 1단계 반복
```

**동작 원리**

1. **Red**: 미구현 요구사항을 검증하는 실패 테스트를 먼저 작성
2. **Green**: 테스트를 통과하는 최소 구현 코드를 작성
3. **Refactor**: 테스트 통과 상태를 유지하며 중복 제거·구조 개선
4. **CI 통합**: 구현 완료 즉시 CI 서버에 병합하여 전체 테스트 실행

#### 한줄 요약

- Red→Green→Refactor 루프로 버그를 예방하고 CI 통합으로 전체 코드 정합성을 즉시 검증

## Ⅴ. 종류 및 비교

<details><summary>용어 설명</summary>

- **Scrum vs XP**: 스크럼은 역할·이벤트·산출물 기반의 조직 관리 프레임워크이고, XP는 TDD·짝 프로그래밍 등 공학 실천법 중심의 개발 방법론으로 상호 보완적.

</details>

| 비교 항목 | XP (익스트림 프로그래밍) | Scrum (스크럼) |
|:---|:---|:---|
| 적용 기준 | 코드 품질·기술 실천 강화 필요 시 | 팀 협업·역할·일정 관리 체계 필요 시 |
| 핵심 특징 | TDD·짝 프로그래밍 등 **공학 실천법** 중심 | PO·SM·3-5-3 구조 **조직 관리** 중심 |
| 한계 및 위험 | 프로세스 관리 체계 부재로 규모 확장 어려움 | 공학 실천법 미포함으로 코드 품질 보장 없음 |

#### 한줄 요약

- 스크럼은 조직 관리 체계, XP는 코드 품질 공학 실천법으로 실무에서 혼합 사용이 일반적

## Ⅵ. 실무 고려사항 및 대책

<details><summary>용어 설명</summary>

- **짝 피로도(Pair Fatigue)**: 장시간 짝 프로그래밍 수행 시 집중력·생산성 저하로 개발자 피로도가 증가하는 현상.

</details>

| 문제 | 대책 | 효과 |
|:---|:---|:---|
| 전일 짝 프로그래밍으로 **짝 피로도** 발생 | 핵심 비즈니스 로직에만 선택적 짝 프로그래밍 적용 | 검토 효과 유지 및 개발자 지속 가능성 확보 |
| TDD 초기 도입 시 테스트 작성 부담으로 개발 속도 저하 | 자동화 테스트 도구 확충·장기 기술 부채 감소 효과 데이터 제시 | 장기적 버그 수정 비용 절감 |
| 상주 고객 부재로 요구사항 즉시 확인 불가 | **PO(제품 책임자)**가 도메인 전문가 대리인 역할 수행 | 요구사항 불명확으로 인한 재작업 최소화 |

#### 한줄 요약

- 짝 피로도는 선택적 적용으로, TDD 부담은 장기 효과 증명으로, 고객 부재는 PO 대리인으로 해소

## Ⅶ. 결론

<details><summary>용어 설명</summary>

- **XP 실천법 정착 기준**: 자동화 테스트 커버리지·CI 통합 빈도·짝 프로그래밍 적용 범위로 XP 도입 수준을 평가하는 판단 기준.

</details>

- 실무에서는 **Scrum(조직 관리 뼈대) + XP(TDD·짝 프로그래밍 실천법)** 혼합 적용이 표준

#### 한줄 요약

- 스크럼 조직 관리 체계에 XP 공학 실천법을 결합하여 관리성과 코드 품질을 동시에 달성
