## Ⅰ. 개요

<details><summary>용어 설명</summary>

- **데이터베이스 용량 산정(Capacity Planning)**: 데이터 증가 추세, 인덱스/로그 오버헤드, 피크 TPS/IOPS를 예측하여 스토리지, RAM, CPU를 선제 설계하는 공학 절차.
- **4대 자원 축**: Storage(디스크 용량), Memory(Buffer Pool), IOPS(입출력 속도), CPU(처리 능력).

</details>

- 정의/개념: 시스템 가용성을 보장하기 위해 **데이터 증가율, 인덱스·로그 오버헤드, 피크 IOPS/TPS를 분석하여 스토리지와 컴퓨팅 자원을 예측·설계**하는 기법
- 배경/필요성: 정량적 용량 예측 부재 시 발생하는 **디스크 공간 고갈, 메모리 버퍼 부족에 따른 TPS 급락 및 긴급 증설 다운타임 해결 불가**

#### 한줄 요약
- 4대 자원 축과 실측 오버헤드를 분석하여 안정적인 증설 시점을 선제 확보한다.

## Ⅱ. 특징

<details><summary>용어 설명</summary>

- **Safety Margin(안전 여유율)**: 예측하지 못한 비즈니스 이벤트나 데이터 스파이크를 수용하기 위해 기본 산정치에 30~50% 여유를 두는 계수.
- **Lead Time(조달 리드타임)**: 신규 하드웨어 발주, 설치, 데이터 마이그레이션까지 걸리는 총 소요 기간(통상 1~3개월).

</details>

- 단순 디스크 용량뿐만 아니라 **Storage, Memory(Buffer Pool), IOPS, CPU 4대 축 다차원 산정**
- 인덱스, WAL/Redo 로그, 복제본, 안전 여유율(Safety Margin)을 포함한 **실측 오버헤드 계수(1.5~2.5배) 적용**
- 임계치(80%) 도달 전 조달 기간을 고려하여 선제 조치하는 **리드타임(Lead Time) 역산 기반 증설 계획**

#### 한줄 요약
- 4대 자원 축 다차원 산정, 실측 오버헤드 적용, 리드타임 역산 증설이 핵심이다.

## Ⅲ. 구조 및 구성요소

<details><summary>용어 설명</summary>

- **총 저장 용량 산출 공식**: $\text{Total Storage} = (\text{순수 테이블} + \text{인덱스}) \times \text{복제본 수} \times \text{연간증가율} \times \text{안전여유율(1.3)}$.

</details>

```text
[데이터베이스 4대 자원 축 용량 산정 체계]
|-- 1. 스토리지 (Storage: 테이블 레코드 크기 + 인덱스 40% + WAL/Redo 로그 + 백업본)
|-- 2. 메모리 (Memory / RAM: InnoDB Buffer Pool -> 활성 워킹셋 100% 수용, Hit Ratio >= 99%)
|-- 3. 스토리지 대역폭 (IOPS: 피크 타임 읽기/쓰기 IOPS 실측 -> SSD / Provisioned IOPS 산정)
`-- 4. 처리 능력 (CPU: 피크 동시 쿼리 수 * 쿼리당 CPU 시간 -> 피크 사용률 70% 이하 유지 코어 수)
```

선의 의미: 계층 및 4대 핵심 자원 축과 세부 산정 항목 매핑 구조

| 자원 구성요소 | 핵심 엔지니어링 책임 | 산출 공식 및 기준 |
|:---|:---|:---|
| **저장 용량 (Storage)** | 테이블 레코드, 인덱스, WAL/Redo 로그, **백업 및 복제본 오버헤드 합산 산정** | $\text{행 크기} \times \text{행 수} \times \text{오버헤드 계수(2.0)}$ |
| **메모리 (Memory)** | 캐시 적중률(Hit Ratio $\ge 99\%$) 유지를 위한 **InnoDB Buffer Pool 크기 산정** | $\text{전체 활성 핫 데이터(Working Set)} \times 1.25$ |
| **입출력 대역폭 (IOPS)**| 피크 타임 동시 읽기/쓰기 트랜잭션을 위한 **SSD / NVMe IOPS 규격 도출** | $\text{Peak TPS} \times \text{트랜잭션당 I/O 횟수}$ |
| **컴퓨팅 파워 (CPU)** | 동시 쿼리 처리 및 정렬/조인을 위해 **피크 사용률(70% 이하) 충족 코어 수 할당** | $\text{동시 세션 수} \times \text{평균 쿼리 CPU 소모율}$ |

#### 한줄 요약
- 저장 용량, 메모리, IOPS, CPU의 4대 자원 축을 체계적으로 산출한다.

## Ⅳ. 흐름도

<details><summary>용어 설명</summary>

- **용량 산정 5단계**: 비즈니스 지표 수집 $\to$ 오버헤드 계산 $\to$ 피크 처리량 도출 $\to$ 고갈 시점 예측 $\to$ 리드타임 역산 증설.

</details>

```text
1. 비즈니스 성장 지표 수집 (MAU, 일일 주문 수, 데이터 보존 주기)
        │
   2. [저장 오버헤드 산정] 순수 데이터 + 인덱스(40%) + WAL 로그 + Replica 2벌 곱연산
        │
   3. [피크 처리량 도출] 피크 TPS 기반으로 필요 IOPS 및 버퍼 풀 RAM 크기 계산
        │
   4. [임계치 도달 예측] 월별 증가 추세를 분석하여 자원 사용률 80% 도달 시점 계산
        │
   5. [증설 착수일 확정] 하드웨어 조달/마이그레이션 리드타임(3개월)을 역산하여 발주 결정
```

#### 한줄 요약
- 지표 수집 → 오버헤드 산정 → 피크량 계산 → 고갈일 예측 → 증설 착수일 역산 순으로 진행된다.

## Ⅴ. 종류 및 비교

<details><summary>용어 설명</summary>

- **Scale-Up vs Scale-Out 용량 산정**: 단일 고성능 장비 확장을 산정하는 Scale-Up과 노드 분산 및 샤딩 기반 확장을 산정하는 Scale-Out.

</details>

| 비교 항목 | Scale-Up (수직 확장 용량 산정) | Scale-Out (수평 확장 용량 산정) |
|:---|:---|:---|
| 확장 방식 | **단일 서버의 CPU 코어, RAM, SSD 스펙 증설**| **Read Replica 노드 증설 및 샤드 분할** |
| 산정 복잡도 | 비교적 단순 (단일 인스턴스 자원 합산) | **데이터 분산율, 네트워크 대역폭, 샤드 쏠림 고려** |
| 한계/단점 | 단일 머신의 물리적 한계 및 증설 시 다운타임 | 분산 트랜잭션 오버헤드 및 샤드 재배치 비용 |
| 적용 권장 | 초기~중규모 엔터프라이즈 RDBMS | **초대규모 글로벌 서비스, NoSQL, 샤딩 DB** |

#### 한줄 요약
- 단일 인스턴스는 Scale-Up으로 사양을 확장하고, 대규모 분산 환경은 Scale-Out으로 노드를 증설한다.

## Ⅵ. 실무 고려사항 및 대책

<details><summary>용어 설명</summary>

- **Temp & Log Bloat**: 복잡한 정렬 쿼리로 인한 디스크 임시 테이블 생성 및 장기 트랜잭션으로 인한 WAL 로그 폭증 현상.

</details>

| 문제 | 대책 | 효과 |
|:---|:---|:---|
| 인덱스 및 복제본 누락으로 인한 스토리지 조기 고갈 | **실측 오버헤드 계수(최소 2배) 및 보존 주기(TTL) 정책 반영** | 저장 공간 예측 오차 0화 |
| 피크 타임 디스크 I/O 병목으로 인한 쿼리 타임아웃 | **부하 테스트(nJMeter/Locust) 기반 프로비저닝 IOPS(gp3/io2) 확보** | 피크 트래픽 지연 스파이크 해소 |
| 하드웨어 조달 지연 중 디스크 100% 장애 발생 | **사용률 70% 도달 시점 기준 리드타임 역산 선제 증설 프로세스 가동** | 무중단 인프라 증설 완료 |
| 대용량 정렬로 인한 디스크 임시 테이블(Temp) 폭증 | **`tmp_table_size` 메모리 확장 및 정렬 인덱스 사전 구축** | 디스크 풀(Disk Full) 장애 방지 |

#### 한줄 요약
- 실측 오버헤드 반영, 프로비저닝 IOPS 확보, 리드타임 역산 선제 증설로 장애를 예방한다.

## Ⅶ. 결론

- 시스템의 무중단 고가용성을 지탱하기 위해 **Storage, Memory, IOPS, CPU 4대 축을 다차원 산정**하고, **클라우드 Storage Auto-Scaling 및 리드타임 역산 증설 프로세스**를 결합하여 안정적인 데이터 인프라 운영

#### 한줄 요약
- 데이터베이스 용량 산정은 데이터 증가율과 실측 오버헤드를 정량 분석하여 인프라 증설 시점을 선제 확보하는 핵심 엔지니어링 규약이다.
