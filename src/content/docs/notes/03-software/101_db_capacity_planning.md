## Ⅰ. 개요

<details><summary>용어 설명</summary>

- **데이터베이스 용량 산정(Database Capacity Planning)**: 데이터베이스 서비스의 성능과 가용성을 보장하기 위해 데이터 증가율, 인덱스·로그 오버헤드, 피크 IOPS/TPS를 분석하여 스토리지와 컴퓨팅 자원을 예측하는 공학적 자원 계획 기법.
- **디스크 공간 고갈 및 긴급 증설 다운타임(Disk Exhaustion & Downtime)**: 정량적 용량 예측 부재로 인해 디스크가 100% 포화되어 서비스 장애가 발생하고 긴급 증설로 인한 중단이 초래되는 위험.

</details>

- 정의/개념: 데이터베이스 서비스의 성능과 가용성을 보장하기 위해 **데이터 증가율, 인덱스·로그 오버헤드, 피크 IOPS/TPS를 분석하여 스토리지와 컴퓨팅 자원을 예측**하는 공학적 자원 계획 기법
- 배경/필요성: 정량적 용량 예측 부재 시 발생하는 **디스크 공간 고갈, 메모리 버퍼 부족에 따른 TPS 급락 및 긴급 증설 다운타임 위험** 직면

#### 한줄 요약

- 데이터 저장량, 인덱스·로그 오버헤드, 피크 처리량을 종합 분석하여 스토리지와 서버 하드웨어 증설 시점을 선제적으로 확보

## Ⅱ. 특징

<details><summary>용어 설명</summary>

- **4대 자원 축(Storage, RAM, IOPS, CPU)**: 디스크 용량뿐만 아니라 버퍼 풀 메모리, 디스크 입출력 대역폭, 쿼리 처리 CPU를 동시 산정.
- **리드타임 역산(Lead Time Reverse Calculation)**: 자원 고갈 임계치(80%) 도달 시점으로부터 조달 및 마이그레이션 소요 기간을 역산하여 선제 증설에 착수하는 기법.

</details>

- 단순 스토리지 용량뿐만 아니라 **Storage, Memory(Buffer Pool), IOPS, CPU 4대 축 다차원 산정**
- 인덱스, WAL/Redo 로그, 복제본, 안전 여유율(Safety Margin)을 포함한 **실측 오버헤드 계수(1.5~2.5배) 적용**
- 임계치 도달 전 조달 기간을 고려하여 선제 조치하는 **리드타임(Lead Time) 기반 증설 계획**

#### 한줄 요약

- 4대 자원 축 다차원 산정과 실측 오버헤드 반영을 통해 용량 부족으로 인한 장애를 사전에 방지

## Ⅲ. 구조 및 구성요소

<details><summary>용어 설명</summary>

- **총 저장 용량 산식**: 총 스토리지 = (순수 테이블 데이터 + 인덱스 크기) $\times$ 복제본 수 $\times$ 연간 증가율 $\times$ 안전 여유율(1.3).

</details>

```text
[ 데이터베이스 4대 자원 축 용량 산정 구조도 ]

 ┌────────────────────────────────────────────────────────────────────────┐
 │                    Database Capacity Planning 4대 축                   │
 ├─────────────────────┬───────────────────┬──────────────────────────────┤
 │ 1. 저장 용량        │ 2. 메모리 (RAM)   │ 3. I/O 대역폭 & CPU          │
 │   - 순수 테이블 크기│   - Buffer Pool   │   - 피크 타임 IOPS 실측      │
 │   - 인덱스/로그 용량│   - 활성 워킹셋   │   - 쿼리당 CPU 소요 시간     │
 │   - 복제본 및 여유율│   - OS/세션 메모리│   - 목표 CPU 사용률 (≤ 70%)  │
 └─────────────────────┴───────────────────┴──────────────────────────────┘
```

선의 의미: 데이터 저장량, 메모리 버퍼, I/O 및 CPU 처리량을 통합 연계하여 전체 DB 인프라 규격을 결정하는 구조.

| 구성요소 | 책임 |
|:---|:---|
| 저장 용량 (Storage) | 테이블 레코드 크기, 인덱스, WAL/Redo 로그, 백업 및 **복제본 오버헤드 합산 산정** |
| 메모리 (Memory) | 캐시 적중률(Hit Ratio $\ge 99\%$) 유지를 위한 **InnoDB Buffer Pool 및 세션 메모리 산정** |
| 입출력 대역폭 (IOPS) | 피크 타임 읽기/쓰기 트랜잭션 처리를 위한 **SSD/NVMe 스토리지 IOPS 규격 도출** |
| 처리 능력 (CPU) | 동시 쿼리 수와 복잡도를 반영하여 **피크 시 목표 사용률(70% 이하)을 충족하는 코어 수 할당** |

#### 한줄 요약

- 저장 용량, 메모리, IOPS, CPU의 4대 자원 축을 체계적으로 산출하여 안정적인 운영 인프라를 확정

## Ⅳ. 흐름도

<details><summary>용어 설명</summary>

- **용량 산정 및 선제 증설 5단계 절차**: 성장 지표 수집 $\to$ 오버헤드 산정 $\to$ 피크 처리량 계산 $\to$ 임계치 도달 예측 $\to$ 증설 착수일 확정.

</details>

```text
[ 데이터베이스 용량 산정 및 선제 증설 파이프라인 ]

 ┌────────────────────────────────────────┐
 │ 1. 성장 지표 수집: 행 수 및 증가율     │
 └───────────────────┬────────────────────┘
                     │
                     ▼
 ┌────────────────────────────────────────┐
 │ 2. 저장 오버헤드 산정: 인덱스/로그/복제 │
 └───────────────────┬────────────────────┘
                     │
                     ▼
 ┌────────────────────────────────────────┐
 │ 3. 피크 처리량 산정: IOPS/메모리/CPU   │
 └───────────────────┬────────────────────┘
                     │
                     ▼
 ┌────────────────────────────────────────┐
 │ 4. 자원 고갈 시점 예측: 임계치(80%)   │
 └───────────────────┬────────────────────┘
                     │
                     ▼
 ┌────────────────────────────────────────┐
 │ 5. 증설 착수일 결정: 리드타임 역산     │
 └────────────────────────────────────────┘
```

### 동작 원리

1. 성장 지표 수집: 비즈니스 계획에 따른 사용자 수, 일일 트랜잭션 수, 데이터 보존 기간을 수집.
2. 저장 오버헤드 산정: 순수 데이터 크기에 B+Tree 인덱스(약 30~50%), WAL 로그, Replica 복제본을 곱하여 총 스토리지 용량을 산출.
3. 피크 처리량 산정: 최대 피크 시점의 TPS를 기반으로 초당 읽기/쓰기 IOPS와 필요한 버퍼 풀 RAM 크기를 계산.
4. 고갈 시점 예측: 월별 증가 추세를 그래프화하여 스토리지 및 메모리 사용률이 80%에 도달하는 한계일을 도출.
5. 증설 착수일 결정: 하드웨어 발주 및 데이터 마이그레이션 리드타임(예: 3개월)을 역산하여 증설 착수일을 확정.

#### 한줄 요약

- 지표 수집 $\to$ 오버헤드 산정 $\to$ 피크량 계산 $\to$ 고갈일 예측 $\to$ 증설 착수일 역산의 5단계

## Ⅴ. 종류 및 비교

<details><summary>용어 설명</summary>

- **Scale-Up vs Scale-Out 용량 산정**: 단일 고성능 장비의 사양 확장을 산정하는 Scale-Up과 노드 분산 및 샤딩 기반 확장을 산정하는 Scale-Out.

</details>

| 구분 | Scale-Up (수직 확장 용량 산정) | Scale-Out (수평 확장 용량 산정) |
|:---|:---|:---|
| **적용 기준** | 단일 인스턴스 중심의 전통적 RDBMS 환경 | 대규모 트래픽 분산 및 샤딩/NoSQL 환경 |
| **핵심 특징** | **단일 서버의 CPU 코어, RAM, NVMe 스펙 확장** | **Read Replica 증설 또는 샤드 노드 분할 확장** |
| **한계** | 하드웨어 물리적 한계 봉착 및 증설 시 다운타임 | 분산 트랜잭션, 네트워크 대역폭, 샤드 리밸런싱 비용 |

#### 한줄 요약

- 단일 인스턴스는 Scale-Up으로 사양을 확장하고 대규모 분산 환경은 Scale-Out으로 노드를 증설

## Ⅵ. 실무 고려사항 및 대책

<details><summary>용어 설명</summary>

- **임시 테이블 및 WAL 비대화(Temp & Log Bloat)**: 대용량 정렬 쿼리로 인한 디스크 Temp 테이블 생성 및 장기 트랜잭션으로 인한 WAL 로그 폭증 현상.

</details>

| 문제 | 대책 | 효과 |
|:---|:---|:---|
| 인덱스 및 복제본 누락으로 인한 스토리지 조기 고갈 | **실측 오버헤드 계수(최소 2배) 및 보존 주기 정책 반영** | 저장 공간 예측 오차 최소화 |
| 피크 타임 디스크 I/O 병목으로 인한 쿼리 타임아웃 | **부하 테스트(nJMeter/Locust) 기반 프로비저닝 IOPS 스토리지 도입** | 피크 트래픽 지연 스파이크 해소 |
| 하드웨어 조달 지연 중 디스크 임계치 초과 장애 | **사용률 70% 도달 시점 기준 리드타임 역산 선제 증설 프로세스 가동** | 다운타임 없는 안정적 인프라 증설 |

#### 한줄 요약

- 실측 오버헤드 반영, 부하 테스트 기반 IOPS 확보, 리드타임 역산 선제 증설로 장애를 예방

## Ⅶ. 결론

<details><summary>용어 설명</summary>

- **자동 확장 연계(Cloud Auto-Scaling Integration)**: AWS RDS Storage Auto-Scaling 등 클라우드 기능을 결합하여 용량 산정 오차를 자동 보정하는 현대적 운영 체계.

</details>

- **데이터베이스 용량 산정** 시스템의 영속성과 고가용성을 지탱하는 인프라 엔지니어링의 핵심 기반이며, 정밀한 4대 자원 분석과 클라우드 자동 확장 기술을 융합하여 무중단 데이터베이스 서비스를 구현해야 함

#### 한줄 요약

- 4대 자원 축 분석과 리드타임 역산 선제 증설을 통해 무중단 데이터베이스 인프라를 완성
