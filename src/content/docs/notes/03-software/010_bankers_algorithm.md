## Ⅰ. 개요

<details><summary>용어 설명</summary>

- **은행원 알고리즘(Banker's Algorithm)**: 돈 빌려주는 은행원처럼, 프로세스가 자원을 달라고 할 때 "나중에 터지지 않을까?" 하고 최악의 상황을 시뮬레이션 돌려본 뒤 안전할 때만 내어주는 깐깐한 교착상태 회피 기법이다.
- **안전 상태(Safe State)**: 모든 프로세스가 순서대로 자원을 빌려 쓰고 무사히 반납하며 퇴근할 수 있는 완벽한 시나리오(안전 순서)가 1개 이상 존재하는 쾌적한 상태이다.

</details>

- 정의: 프로세스가 추가 자원을 요청할 때, 일단 빌려줬다고 치고(가상 할당) 시스템이 뻗지 않고 **안전 순서(Safe Sequence)** 를 유지할 때만 진짜로 빌려주는 깐깐한 **은행원 알고리즘(Banker's Algorithm)**
- 배경: 닥치는 대로 빌려주다가 나중에 놈들이 한꺼번에 더 달라고 깽판 치면 **안전 순서가 소멸**하면서 교착상태 지옥이 열리기 때문

#### 한줄 요약

- 은행원처럼 대출(자원)을 깐깐하게 심사해서, 무사히 상환(퇴근)할 수 있는 안전한 순서가 나올 때만 빌려준다.

## Ⅱ. 특징

<details><summary>용어 설명</summary>

- **가용 자원(Available Vector)**: 은행 금고에 지금 당장 대출해 줄 수 있는 현금이 얼마나 남아있는지 보여주는 현황판이다.
- **최대 요구량(Max Matrix)**: 프로세스가 태어날 때 "나 죽기 전까지 이만큼은 무조건 쓴다!"라고 배 째고 선언해 둔 한도액 장부이다.
- **할당량(Allocation Matrix)**: 프로세스가 지금까지 금고에서 빼내서 쥐고 있는 대출금 현황판이다.
- **추가 요구량(Need Matrix)**: 앞으로 더 달라고 징징댈 수 있는 남은 대출 한도(최대 - 할당)이다.

</details>

- 프로세스가 태어날 때 무조건 **최대 요구량(Max Claim)** 을 사전에 선언해야 하고, 요청 시 가상으로 할당(Tentative Allocation)해 봄.
- **가용 자원(Available)**, **최대 요구량(Max)**, **할당량(Allocation)**, **추가 요구량(Need)** 4대 장부를 빡세게 관리함.
- 안전성 검사를 돌려서 무사히 퇴근하는 **안전 순서(Safe Sequence)** 가 나올 때만 진짜로 자원(물리 할당)을 내어줌.

#### 한줄 요약

- 4가지 장부를 펴놓고 가상으로 빌려준 뒤, 안전하다는 결론이 나와야만 진짜 자원을 내준다.

## Ⅲ. 구조 및 구성요소

<details><summary>용어 설명</summary>

- **가상 가용 자원(Work Vector)**: 시뮬레이션 돌릴 때, 놈들이 쓰고 반납한 자원까지 합쳐서 지금 금고에 얼마나 남았는지 추적하는 가상의 금고이다.
- **종료 여부(Finish Vector)**: 시뮬레이션 중에 "이놈은 무사히 퇴근했다"라고 체크해 두는 출석부(True/False) 배열이다.

</details>

```text
[ 은행원 알고리즘 십자포화 안전성 검사 아키텍처 ]
            [ 4대 자원 장부 ]
   (가용 자원, 최대 요구, 할당량, 추가 요구)
                   │
                   ▼
          [ 요청 제어기 ]
     (한도 넘는지 1차 입구 컷 치고)
     (가상으로 쥐여줘 봄)
                   │
                   ▼
          [ 안전성 검사기 ]
(가상 금고(Work)랑 출석부(Finish) 돌려봄)
                   │
         ┌─────────┴─────────┐
         ▼                   ▼
[ 안전 순서 나옴 ]     [ 안전 순서 없음 ]
(진짜로 빌려줌)        (거절하고 원상 복구)
```

| 구성요소 | 책임 |
|:---|:---|
| **가용 자원** (Available) | 금고에 남아있는 각 타입별 쌩현금(유휴 자원) 수치 |
| **최대 요구량** (Max) | 프로세스 $P_i$가 언젠가 뜯어갈 최대 한도액 바운더리 |
| **할당량** (Allocation) | 프로세스 $P_i$가 현재 대출받아 쥐고 있는 자원 수량 |
| **추가 요구량** (Need) | 프로세스 $P_i$가 앞으로 더 달라고 깽판 칠 남은 잔액 ($\text{Max} - \text{Allocation}$) |
| 안전성 검사기 | 가상으로 빌려준 뒤 $\text{Need}_i \le \text{Work}$인 놈들 찾아 릴레이로 퇴근시키는 **안전 순서** 시뮬레이터 |

#### 한줄 요약

- 장부를 바탕으로 제어기가 가상 할당을 때리고, 검사기가 안전 순서를 뺑뺑이 돌려 검증한다.

## Ⅳ. 흐름도

<details><summary>용어 설명</summary>

- **안전성 검사 알고리즘(Safety Algorithm)**: 금고 잔액(Work)으로 남은 빚(Need)을 갚아줄 수 있는 놈을 찾아 퇴근시키고, 그놈이 뱉은 자원으로 다음 놈을 퇴근시키는 뺑뺑이 시뮬레이션이다.

</details>

```text
[ 은행원 알고리즘 십자포화 가상 할당 시뮬레이션 흐름 ]
┌──────────────────────────────┐
│ 1. 1차 입구 컷 검사          │
│ (요청 ≤ 잔액, 요청 ≤ 금고현금)│
└───────┬──────────────────────┘
        ├─ 초과 ─▶ [ 얄짤없이 컷 (에러/대기) ]
        │ 통과
        ▼
┌──────────────────────────────┐
│ 2. 가상으로 장부 업데이트    │
│ (금고에서 빼서 쥐여줘 봄)    │
└──────────────┬───────────────┘
               ▼
┌──────────────────────────────┐
│ 3. 시뮬레이션 초기화         │
│ (가상 금고 세팅, 출석부 리셋) │
└──────────────┬───────────────┘
               ▼
╔══════════════════════════════╗
║ 4. 안전 순서 탐색 뺑뺑이     ║
║ (남은 빚 ≤ 가상 금고인 놈 찾음) ║
║ 놈 퇴근 처리 (출석부 True)   ║
║ 놈이 뱉은 자원을 금고에 더함 ║
╚══════════════╤═══════════════╝
               │ (더 이상 조건 맞는 놈 없음)
               ▼
┌──────────────────────────────┐
│ 5. 최종 확정 판정            │
└───────┬──────────────────────┘
        ├─ 전원 퇴근(True) ─▶ [ 안전함! 진짜 할당 ]
        └─ 퇴근 못한 놈 있음 ─▶ [ 위험함! 복구 및 대기 ]
```

### 동작 원리

1. 요청 한도 검사: 달라는 자원이 남은 한도($\text{Need}$)나 금고 현금($\text{Available}$)보다 많으면 뺨 맞고 쫓겨남.
2. 요청 가상 반영: 금고에서 현금을 빼고($\text{Available} - \text{Req}$), 놈한테 쥐여주고($\text{Allocation} + \text{Req}$), 남은 빚을 깜($\text{Need} - \text{Req}$).
3. 시뮬레이션 초기화: 가상 금고(`Work`)를 현금 잔액으로 세팅하고, 출석부(`Finish`)를 전부 False로 리셋함.
4. 안전 순서 탐색: 안 퇴근했고, 남은 빚이 가상 금고로 덮어지는 놈을 찾아 퇴근시키고 자원을 뺏어 가상 금고에 넣음.
5. 확정 판정: 전원이 무사히 출석부에 True를 찍었으면 진짜 자원을 주고, 아니면 롤백하고 컷 침.

#### 한줄 요약

- 장부 끄적여서 줘보고, 퇴근 가능한 놈들 릴레이 돌려서 전원 퇴근하면 성공, 아니면 무효다.

## Ⅴ. 종류 및 비교

<details><summary>용어 설명</summary>

- **불안전 상태(Unsafe State)**: 안전 순서를 못 찾아서 자칫하면 교착상태로 직행할 수 있는 시한폭탄 같은 찝찝한 상태이다. (교착상태 자체는 아님)

</details>

| 비교 항목 | **안전 상태** (Safe State) | **불안전 상태** (Unsafe State) | **교착 상태** (Deadlock) |
|:---|:---|:---|:---|
| 정의 | 모두가 무사히 퇴근할 수 있는 **안전 순서**가 확실히 존재하는 쾌적한 상태 | 안전 순서를 못 찾아서 삐끗하면 다 같이 뒤질 수 있는 위태로운 상태 | 놈들이 서로 멱살 잡고 영구히 얼어붙어서 이미 터져버린 상태 |
| 자원 승인 여부 | 묻고 더블로 감 (안전하니까 시원하게 승인) | 가상 할당을 즉시 취소(롤백)하고 얌전히 대기하라고 컷 침 | 탐지기 돌려서 한 놈 쏴 죽이고 롤백해서 수습해야 함 |
| 시스템 진행성 | 누가 봐도 무조건 끝까지 살아서 완료됨 | 교착상태로 빠질 **가능성**이 농후함 | 이미 멈춰서 아무도 집에 못 감 |

#### 한줄 요약

- 불안전 상태라고 무조건 죽는 건 아니지만, 재수 없으면 교착상태로 가므로 미리 차단하는 것이다.

## Ⅵ. 실무 고려사항 및 대책

<details><summary>용어 설명</summary>

- **최대 요구량 사전 선언(Max Claim Pre-declaration)**: 이 알고리즘을 쓰려면 프로세스가 태어날 때부터 "나 죽을 때까지 얼마나 쓸 거다"라고 정확히 예언하고 문서로 남겨야 하는 빡센 제약이다.

</details>

| 문제 | 대책 | 효과 |
|:---|:---|:---|
| 프로세스가 태어날 때 **최대 요구량**을 뻥튀기하거나 구라 쳐서 예측 오차 터짐 | 계약 기반 상한을 박고 런타임에 뻥치는지 칼같이 검증함 | 구라 치고 자원 빼먹는 놈들 차단해서 시스템 신뢰성 방어 |
| 자원 요청할 때마다 **안전성 시뮬레이션** 뺑뺑이 돌리느라 CPU 오버헤드 폭발 | 자원군을 쪼개고 시뮬레이션 검사 범위를 타이트하게 축소함 | 매번 계산기 두드리는 비용을 줄여서 승인 딜레이 최소화 |
| 프로세스가 생겼다 죽었다를 반복해서 장부(Matrix)가 너덜너덜해짐 | 놈들 들락날락할 때마다 장부를 동적으로 빡세게 재할당함 | 런타임에 장부 빵꾸나는 거 막고 알고리즘 정합성 철통 보장 |

#### 한줄 요약

- 최대 요구량 구라 치는 건 런타임에 잡고, 계산 딜레이는 자원군을 쪼개서 줄여라.

## Ⅶ. 결론

<details><summary>용어 설명</summary>

- **은행원 알고리즘 적용 기준(Banker's Algorithm Adoption Criteria)**: 자원 개수 고정돼 있고, 놈들이 요구량 솔직하게 말하고, 시뮬레이션 딜레이 감당 가능한지 따지는 엄격한 도입 잣대이다.

</details>

- **은행원 알고리즘 적용 기준** 원칙에 따라, 정적인 자원 한도와 사전 선언이 확실한 **미션 크리티컬 인프라(원전 등)** 에 **은행원 알고리즘** 채택 기조 확립함

#### 한줄 요약

- 프로세스 요구량을 확실히 알 수 있고, 검사할 여유가 있는 깐깐한 인프라에만 쓸 수 있다.
