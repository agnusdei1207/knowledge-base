## Ⅰ. 개요

<details><summary>용어 설명</summary>

- **바운디드 컨텍스트(Bounded Context)**: '상품'이라는 단어가 물류팀엔 '재고/무게'지만 판매팀엔 '가격/할인'이듯, 똑같은 단어라도 의미가 달라지는 경계를 명확히 그어놓은 '동네(문맥)의 울타리'이다.
- **컨텍스트 맵(Context Map)**: 동네(컨텍스트)들끼리 어떻게 데이터를 주고받는지(갑을 관계), 어디에 번역기(ACL)를 뒀는지 그려놓은 전체 조감도(지도)이다.
- **보편적 언어 스코프(Ubiquitous Language Scope)**: 하나의 단어가 100% 동일한 의미로만 통용되는 유효 범위이다. 이 울타리를 넘어가면 단어의 의미가 달라져야 정상이다.

</details>

- 정의: 억지로 전사 단일 모델을 만들지 않고, 도메인 모델과 보편적 언어가 일관된 의미를 유지하는 명확한 경계선을 긋는 **Bounded Context**
- 배경: 전사 모든 부서가 똑같은 1개의 대형 `User` 테이블을 공유하면, **부서마다 `User`의 의미가 달라서 컬럼이 수백 개로 증식하고 헬파티가 열리기** 때문

#### 한줄 요약

- 같은 단어도 부서마다 의미가 다르니, 억지로 합치지 말고 동네(경계)를 나누어 각자 살게 하는 거다.

## Ⅱ. 특징

<details><summary>용어 설명</summary>

- **업스트림/다운스트림(Upstream / Downstream)**: 강물이 위에서 아래로 흐르듯, 데이터를 제공하는 갑(Upstream)과 그 데이터를 받아서 쓰는 을(Downstream)의 의존 관계 방향이다.
- **오염 방지 계층(ACL, Anti-Corruption Layer)**: 업스트림(갑)의 구린내 나는 레거시 모델이 내 새삥 도메인(을)으로 스며들지 못하게, 중간에서 내 입맛에 맞게 데이터를 번역해 주는 방파제이다.

</details>

- 경계 내부에서는 **보편적 언어(Ubiquitous Language)**의 의미를 100% 철저하게 수호함.
- 콘웨이의 법칙에 따라 가급적 1개의 **개발 팀**이 1개의 Bounded Context를 독점 소유함.
- 서로 다른 동네끼리 만날 땐 **공유 커널(Shared Kernel), ACL, OHS** 같은 관계 패턴으로 선을 그음.

#### 한줄 요약

- 우리 동네(경계) 안에선 용어 100% 통일, 남의 동네랑 데이터 섞을 땐 번역기(ACL)를 거친다.

## Ⅲ. 구조 및 구성요소

<details><summary>용어 설명</summary>

- **공유 커널(Shared Kernel)**: 두 동네가 완전히 합치긴 싫고, 그렇다고 남남처럼 살기도 애매해서 딱 핵심 도메인 모델 일부만 공용으로 파놓고 같이 관리하는 위험한 결합 방식이다.
- **공개 호스트 서비스(OHS, Open Host Service)**: 업스트림이 "나한테 데이터 받으려면 REST API나 JSON으로 줄 테니 이거 써라"라며 여러 다운스트림에게 쿨하게 열어둔 공용 표준 창구이다.

</details>

```text
[ 컨텍스트 맵(Context Map) 십자포화 아키텍처 ]

[ 업스트림 컨텍스트 (결제) ] ──▶ (OHS: 나 REST API 열었어)
                                   │
                          [ 컨텍스트 맵 경계 ]
                                   │
(내 입맛대로 번역) ◀── [ 오염 방지 계층 (ACL) ]
                                   │
[ 다운스트림 컨텍스트 (주문) ] ◀───┘
```

| 구성요소 | 팩트 폭행 책임 |
|:---|:---|
| **업스트림 (공급자)** | "결제 완료됐음"이라고 이벤트를 쏘거나 API를 제공하는 상류(갑) 동네 |
| **컨텍스트 맵 (지도)** | 어떤 동네가 갑(U)이고 어떤 동네가 을(D)인지, 번역기는 어딨는지 그려놓은 전체 지도 |
| **오염 방지 계층 (ACL)**| 외부의 낯선 용어(결제 ID)를 우리 동네 용어(주문 참조 ID)로 씻겨내는 세탁기 |
| **다운스트림 (소비자)** | 세탁기를 거친 데이터를 받아서 자기만의 보편적 언어로 씹어 먹는 하류(을) 동네 |

#### 한줄 요약

- 위에서(업스트림) 물을 흘려보내면 중간에 필터(ACL)로 거르고 아래(다운스트림)에서 받아 마신다.

## Ⅳ. 흐름도

<details><summary>용어 설명</summary>

- **이벤트 기반 통합(Event-Driven Integration)**: 동네끼리 REST API로 직접 찌르면 결합도가 떡상하니까, "나 일 끝남!" 하고 카프카(Broker)에 이벤트만 던지고 튀는 비동기 쿨거래 방식이다.

</details>

```text
[ 이벤트 기반 컨텍스트 통합 십자포화 흐름 ]
┌──────────────────────────────┐
│ 1. 업스트림 상태 변경        │
│ (결제 완료됨!)               │
└──────────────┬───────────────┘
               ▼
┌──────────────────────────────┐
│ 2. 도메인 이벤트 발행        │
│ (카프카에 'PaymentDone' 쏨)  │
└──────────────┬───────────────┘
               ▼
┌──────────────────────────────┐
│ 3. 다운스트림의 ACL이 수신   │
│ (주문팀 번역기가 메시지 받음)│
└──────────────┬───────────────┘
               ▼
┌──────────────────────────────┐
│ 4. 내부 언어로 번역 (세탁)   │
│ (Payment ➔ OrderStatus 맵핑)│
└──────────────┬───────────────┘
               ▼
┌──────────────────────────────┐
│ 5. 다운스트림 상태 반영      │
│ (주문 상태 '배송준비'로 변경)│
└──────────────────────────────┘
```

### 동작 원리

1. 업스트림 발생: 갑 동네에서 데이터가 바뀜.
2. 이벤트 쏘기: "나 바뀜" 하고 브로커(Kafka)에 이벤트를 쿨하게 쏨.
3. ACL 캐치: 을 동네의 문지기(ACL)가 이벤트를 주워옴.
4. 번역: 갑 동네의 사투리를 을 동네의 표준어로 깔끔하게 번역(매핑)함.
5. 로컬 커밋: 을 동네는 오염되지 않은 순수한 데이터만 자기 DB에 저장함.

#### 한줄 요약

- 갑이 던지고 튀면 $\to$ 번역기(ACL)가 주워서 번역하고 $\to$ 우리 팀 DB에 안전하게 박는다.

## Ⅴ. 종류 및 비교

<details><summary>용어 설명</summary>

- **전사 공유 모델 vs 바운디드 컨텍스트(Single Model vs Bounded Context)**: 모든 팀이 `User` 테이블 1개에 컬럼 300개씩 달아가며 병목 터지는 레거시와, 팀마다 `User`, `Customer`, `Rider`로 작게 쪼개서 각자 사는 MSA의 차이이다.

</details>

| 비교 항목 | **전사 공유 모델 (레거시 통짜 DB)** | **바운디드 컨텍스트 (DDD 쪼개기)** |
|:---|:---|:---|
| 용어 정의 | 전사가 1개 단어를 돌려씀 (의미 오염/충돌) | **동네 안에서만 의미가 일치하면 장땡임** |
| 데이터 소유권| `User` 테이블 건들 때마다 전 부서 허락 맡음 | **우리 동네 DB는 우리 팀만 맘대로 고침** |
| 의존성 및 배포| 한 팀 배포하다 DB 락 걸리면 전사 마비됨 | **API나 이벤트(ACL)로만 통신하고 각자 배포** |
| 복잡도 | 테이블 크기가 갓(God) 클래스가 됨 | 덩어리가 작아져서 인간의 뇌로 유지보수 가능 |

#### 한줄 요약

- 무식하게 하나로 합치면 병목 지옥이고, 의미별로 동네를 쪼개면(Bounded Context) 평화가 온다.

## Ⅵ. 실무 고려사항 및 대책

<details><summary>용어 설명</summary>

- **콘웨이의 법칙(Conway's Law)**: 소프트웨어 구조는 그걸 만드는 조직의 소통 구조를 그대로 따라간다는 팩폭 법칙이다. 부서가 3개면 웬만해선 바운디드 컨텍스트도 3개가 된다.

</details>

| 문제 | 대책 | 효과 |
|:---|:---|:---|
| 기획도 안 끝났는데 개발자가 멋대로 DB부터 쪼갬 | **이벤트 스토밍(Event Storming)**으로 찐 경계 찾음 | 껍데기만 쪼개진 분산 모놀리스 방지 |
| 갑(Upstream)이 API 바꿨다고 우리 코드가 다 터짐 | 중간에 든든한 **오염 방지 계층(ACL)** 번역기를 박음 | 갑의 횡포로부터 순수 도메인 모델 사수 |
| 하나의 컨텍스트 코드를 A팀, B팀이 같이 건드림 | **콘웨이 법칙**에 따라 **1팀 = 1컨텍스트** 강제 | 책임 소재가 명확해지고 의사결정 병목 박살 |

#### 한줄 요약

- 무지성으로 DB 쪼개지 말고 이벤트 스토밍으로 선을 긋고, 팀당 1개씩 나눠주며, ACL로 방어해라.

## Ⅶ. 결론

<details><summary>용어 설명</summary>

- **바운디드 컨텍스트 도출 기준(Bounded Context Boundary Standards)**: 단어의 의미가 바뀌는지, 배포 주기가 다른지, 팀이 나뉘어져 있는지 각을 재서 선을 그을지 정하는 잣대이다.

</details>

- **바운디드 컨텍스트 도출 기준** 원칙에 따라, 의미가 달라지고 소유 팀이 다르면 **Bounded Context 분리**, 남의 코드가 스며드는 게 싫으면 **ACL** 채택 기조 확립함

#### 한줄 요약

- MSA로 시스템을 찢을 때 기술(DB)이 아니라 업무(단어의 의미)를 기준으로 찢는 게 찐이다.
