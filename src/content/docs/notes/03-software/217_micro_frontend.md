## Ⅰ. 개요

<details>
<summary>핵심 용어</summary>

- **독립 배포•화면 조합**: 업무별 웹 앱을 팀이 독립 배포하고 애플리케이션 셸에서 하나의 화면으로 구성하는 아키텍처 원칙이다.
- **마이크로프론트엔드(Micro Frontend)**: 사용자 화면을 업무 경계별 웹 애플리케이션으로 나눠 독립 개발•배포하고 하나의 화면으로 조합하는 아키텍처이다.

</details>

- 정의/개념: 사용자 화면을 업무 경계별 웹 애플리케이션으로 나눠 독립 개발•배포하고 조합하는 **마이크로프론트엔드(Micro Frontend)**이다.
- 배경/필요성: 단일 빌드 구조에서는 팀별 변경을 독립 배포하기 어렵다.

#### 한줄 요약

- 큰 웹 화면을 주문•결제 같은 업무별 작은 앱으로 나눠 각 팀이 따로 배포하되 사용자에게는 한 서비스처럼 보여 준다.

## Ⅱ. 특징

<details>
<summary>핵심 용어</summary>

- **기술 자율성•공통 계약**: 팀별 구현 기술 선택권과 라우팅•이벤트•공유 상태 규약 준수를 함께 보장하는 원칙이다.
- **업무 경계(Business Boundary)**: 함께 변경되는 화면과 규칙을 하나의 팀이 소유하도록 나눈 기능 범위이다.
- **부분 독립 배포(Independent Deployment)**: 전체 프런트엔드를 다시 배포하지 않고 특정 업무 앱만 변경•배포하는 방식이다.

</details>

- **업무 경계(Business Boundary)**와 팀 소유권을 일치시킨다.
- **부분 독립 배포(Independent Deployment)**로 실패 범위를 축소한다.
- **기술 자율성•공통 계약** 기반 화면 조합이 핵심이다.

#### 한줄 요약

- 팀별 변경은 분리되지만 과도한 분할은 기능 중복과 화면 상태•양식 동기화 비용을 늘린다.

## Ⅲ. 구조 및 구성요소

<details>
<summary>핵심 용어</summary>

- **애플리케이션 셸(Application Shell)**: 공통 화면 틀과 라우팅을 제공하고 경로에 맞는 업무별 마이크로 앱을 조합하는 구성요소이다.
- **통합 계약(Integration Contract)**: 업무 앱 사이의 라우팅•이벤트•공유 상태•수명주기 규약이다.
- **디자인 시스템(Design System)**: 공통 화면 구성요소와 디자인 토큰•사용 규칙을 제공하는 체계이다.
- **오류 경계(Error Boundary)**: 부분 앱의 실행 오류를 해당 화면 영역에 격리하고 대체 화면을 제공하는 장치이다.
- **업무별 마이크로 앱(Business Micro App)**: 하나의 업무 경계와 팀이 소유하고 독립 개발•배포하는 화면 단위이다.

</details>

```text
[애플리케이션 셸] ----- [통합 계약] ----- [업무별 마이크로 앱]
                                               /       \
                                      [디자인 시스템] [오류 경계]
```

선의 의미: 애플리케이션 셸과 통합 계약은 업무별 마이크로 앱의 화면 조합 경계에 결합되고, 각 마이크로 앱 아래에는 표현 일관성을 담당하는 디자인 시스템과 부분 실패를 격리하는 오류 경계가 놓이는 정적 프런트엔드 구조를 뜻한다.

| 구성요소 | 책임 |
|:---|:---|
| **애플리케이션 셸(Application Shell)** | 공통 틀•라우팅•화면 조합 담당 |
| **통합 계약(Integration Contract)** | 이동•이벤트•공유 상태 규약 정의 |
| **업무별 마이크로 앱(Business Micro App)** | 업무 경계별 독립 개발•배포 단위 |
| **디자인 시스템(Design System)** | 화면 구성요소와 표현 규칙 공유 |
| **오류 경계(Error Boundary)** | 부분 오류를 해당 화면 영역에 격리 |


#### 한줄 요약

- 셸이 공통 화면 틀을 잡고 계약에 맞춰 업무 앱을 끼워 넣으며 디자인 규칙과 오류 경계가 일관성과 격리를 지킨다.

## Ⅳ. 흐름도

<details>
<summary>핵심 용어</summary>

- **1. 업무 앱 적재**: 현재 경로에 필요한 업무 앱을 선택•적재하는 단계이다.
- **2. 통합 계약 연결**: 라우팅•이벤트•공유 상태 규약을 적용하는 단계이다.
- **3. 부분 오류 격리**: 실패한 앱 영역만 폴백으로 바꾸는 단계이다.

</details>

```text
화면 요청
    |
    v
1. 업무 앱 적재
    |
    v
2. 통합 계약 연결
    |
    +-- 앱 실행 성공 ---- 조합 화면 반환
    |
    `-- 앱 실행 실패
             |
             v
      3. 부분 오류 격리
             |
             `-- 폴백 화면 반환
```

### 동작 원리

1. **업무 앱 적재**: 경로에 맞는 업무 앱을 선택•적재한다.
2. **통합 계약 연결**: 이동•이벤트•공유 상태 규약을 적용한다.
3. **부분 오류 격리**: 실패 앱 영역만 폴백 화면으로 대체한다.


#### 한줄 요약

- 사용자가 메뉴를 열면 셸이 해당 업무 앱을 불러 공통 규칙으로 화면에 붙이고, 실패한 앱의 자리만 오류 화면으로 바꾼다.

## Ⅴ. 종류 및 비교

<details>
<summary>핵심 용어</summary>

- **런타임 조합(Runtime Composition)**: 브라우저가 실행 중에 업무별 앱을 적재해 팀별 독립 배포를 지원하는 방식이다.
- **빌드 시 조합(Build-Time Composition)**: 셸을 빌드할 때 업무 앱을 하나의 배포 산출물로 결합하는 방식이다.
- **엣지 조합(Edge-Side Composition)**: 중계 서버가 요청별 화면 조각을 결합해 브라우저에 전달하는 방식이다.

</details>

| 마이크로프론트엔드 조합 방식 | **빌드 시 조합(Build-Time Composition)** | **런타임 조합(Runtime Composition)** | **엣지 조합(Edge-Side Composition)** |
|:---|:---|:---|:---|
| 적용 기준 | 버전 통제와 단순 운영 우선 | 팀별 독립 배포 필수 | 서버별 화면 개인화 필요 |
| 핵심 특징 | 셸 빌드 때 앱을 하나로 결합 | 브라우저가 실행 중 앱 적재 | 중계 서버가 화면 조각 결합 |
| 한계 | 셸 재배포•버전 충돌 | 초기 지연•중복 의존성 | 중계 지연•조합 실패 |

> 요약: 단일 배포는 **빌드 시 조합(Build-Time Composition)**, 독립 배포는 **런타임 조합(Runtime Composition)**을 선택한다.

#### 한줄 요약

- 한 번에 묶어 배포하면 단순하고, 실행 중 불러오면 팀 독립성이 높으며, 중계 서버에서 합치면 요청별 화면 구성이 쉽다.

## Ⅵ. 실무 고려사항 및 대책

<details>
<summary>핵심 용어</summary>

- **경험 불일치**: 팀별 UI가 디자인 토큰과 통합 계약을 다르게 적용해 사용 방식과 표현이 어긋나는 문제이다.
- **사용자 인터페이스(User Interface, UI)**: 사용자가 서비스 기능을 보고 조작하는 화면 접점이다.
- **디자인 토큰(Design Token)**: 색상•간격•글꼴 등 디자인 결정을 재사용 가능한 값으로 표현한 규칙이다.
- **폴백(Fallback)**: 부분 앱이 실패할 때 전체 중단 대신 표시하는 대체 화면이나 기능이다.

</details>

| 문제 | 대책 | 효과 |
|:---|:---|:---|
| 중복 런타임의 용량 증가 | 공유 의존성•버전 정책 적용 | 초기 적재 절감 |
| **사용자 인터페이스(User Interface, UI)**의 **경험 불일치** | **디자인 토큰(Design Token)**•계약 시험 | 사용자 경험 일관성 |
| 부분 앱의 런타임 장애 | **폴백(Fallback)**•**오류 경계(Error Boundary)** | 전체 화면 보호 |
| 잘못 나눈 팀 경계 | **업무 경계(Business Boundary)**•독립 배포 기준 | 조정 비용 감소 |

#### 한줄 요약

- 상품 팀과 주문 팀이 각자 화면을 배포하면 한쪽의 잦은 변경 때문에 다른 팀의 배포를 기다리지 않아도 된다.



## Ⅶ. 결론

<details>
<summary>핵심 용어</summary>

- **조합 방식 선택 기준**: 팀 독립성•초기 지연•버전 통제•운영 복잡도를 비교해 빌드•런타임•엣지 조합을 고르는 기준이다.

</details>

- **조합 방식 선택 기준**에 따라 업무별 독립 배포는 런타임 조합, 단순 운영은 빌드 시 조합을 선택한다.

#### 한줄 요약

- 화면을 조직도대로 무조건 쪼개지 말고 함께 바뀌는 업무 범위와 필요한 독립 배포 수준을 먼저 정해야 한다.
