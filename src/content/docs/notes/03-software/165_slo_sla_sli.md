## Ⅰ. 개요

<details><summary>용어 설명</summary>

- **SLI / SLO / SLA 삼각 체계**: 사용자 관점의 실제 서비스 측정치인 SLI(Service Level Indicator), 엔지니어링 팀 내부 운영 목표인 SLO(Service Level Objective), 미달성 시 금전적 보상이 수반되는 고객 계약인 SLA(Service Level Agreement).
- **추상적 안정성 및 보상 분쟁(Ambiguous Quality & SLA Dispute)**: 가용성에 대한 모호한 정의로 인해 팀 간 갈등이 발생하고 장애 시 고객과의 책임 소재 및 보상 기준이 불분명해지는 위험.

</details>

- 정의/개념: 서비스 품질을 정량화하기 위해 **실제 측정 지표(SLI), 내부 운영 목표(SLO), 고객 보상 계약(SLA)을 계층화**한 서비스 수준 관리 체계
- 배경/필요성: 시스템 가용성에 대한 모호하고 추상적인 정의로 인한 **개발팀-운영팀 간 갈등 및 고객 장애 보상 분쟁 발생 위험** 직면

#### 한줄 요약

- SLI(실측), SLO(내부 목표), SLA(고객 계약)를 명확히 분리하여 체계적인 품질 거버넌스와 배포 의사결정을 확립

## Ⅱ. 특징

<details><summary>용어 설명</summary>

- **SLO $\geq$ SLA 안전 마진(Safety Margin)**: 외부 계약인 SLA(99.5%)보다 내부 운영 목표인 SLO(99.9%)를 엄격하게 설정하여 계약 위반 전에 선제적으로 대응.
- **오류 예산(Error Budget)**: `100% - SLO`로 산출되며 신규 기능 배포와 시스템 개선에 사용할 수 있는 정량적 실패 허용량.

</details>

- 사용자 경험을 직접 대변하는 정량적 성공 비율 측정인 **SLI 기반의 현실 진단**
- 개발팀과 운영팀이 기능 출시와 안정화의 우선순위를 합의하는 **SLO 기반 내부 통제**
- 비즈니스 약속 미달 시 크레딧 환불 및 법적 구속력을 갖는 **SLA 기반 외부 계약**

#### 한줄 요약

- 실측치(SLI), 내부 목표(SLO), 외부 계약(SLA)의 단계적 연동을 통해 신뢰성과 비즈니스를 완벽히 연결

## Ⅲ. 구조 및 구성요소

<details><summary>용어 설명</summary>

- **서비스 수준 관리(SLM) 3계층 모델**: SLI(지표 수집), SLO(오류 예산 산출), SLA(계약 조건/페널티).

</details>

```text
[ SLI, SLO, SLA 계층 관계 및 안전 마진 구조도 ]

 1. [ 최상위 외부 계약: SLA (Service Level Agreement: 99.5%) ]
    • 고객 약속 미달 시 금전적 보상/크레딧 지급 (위반 시 비즈니스 페널티)
                           │
                           │ (Safety Margin: 0.4% 안전 마진 버퍼)
                           ▼
 2. [ 내부 운영 목표: SLO (Service Level Objective: 99.9%) ]
    • Error Budget (0.10%): 예산 소진 시 신규 기능 배포 동결
                           │
                           │ (정량적 실시간 측정)
                           ▼
 3. [ 실제 시스템 측정치: SLI (Service Level Indicator: 99.95%) ]
    • `성공한 HTTP 200 요청 수 / 유효한 전체 HTTP 요청 수`
```

선의 의미: SLI 실측치를 바탕으로 내부 SLO를 평가하고, SLA 계약선에 도달하기 전 안전 마진 내에서 선제 조치하는 구조.

| 구성요소 | 책임 |
|:---|:---|
| 서비스 수준 지표 (SLI) | 사용자 관점에서 서비스의 **성공률, P99 지연시간, 처리량을 백분율(%)로 정량 산출** |
| 서비스 수준 목표 (SLO) | 엔지니어링 조직이 합의한 **내부 목표치로서 Error Budget 및 신규 배포 통제의 기준 제공** |
| 서비스 수준 계약 (SLA) | 고객과의 비즈니스 계약으로서 **위반 시 요금 할인, 크레딧 보상, 위약금 지급 조건 규정** |
| 안전 마진 (Margin) | SLA 위반 전 장애를 수습할 수 있도록 **SLO와 SLA 사이에 확보하는 완충 격차** |

#### 한줄 요약

- SLI(실측), SLO(내부 목표), SLA(외부 계약), 안전 마진이 유기적으로 결합

## Ⅳ. 흐름도

<details><summary>용어 설명</summary>

- **서비스 수준 관리 5단계 수명주기**: 이벤트 수집 $\to$ SLI 측정 $\to$ SLO 대비 예산 평가 $\to$ 운영 조치 $\to$ SLA 보상 판정.

</details>

```text
[ SLI/SLO/SLA 기반 서비스 수준 운영 및 계약 평가 파이프라인 ]

 ┌────────────────────────────────────────┐
 │ 1. 실시간 트랜잭션 요청 이벤트 수집   │
 └───────────────────┬────────────────────┘
                     │
                     ▼
 ┌────────────────────────────────────────┐
 │ 2. SLI 계산: (성공 요청 수 / 전체 요청 수)
 └───────────────────┬────────────────────┘
                     │
                     ▼
 ┌────────────────────────────────────────┐
 │ 3. SLO 대비 잔여 Error Budget 소진율 평가│
 └───────────────────┬────────────────────┘
                     │
                     ▼
 ┌────────────────────────────────────────┐
 │ 4. 내부 운영 조치: 배포 진행 또는 배포 동결
 └───────────────────┬────────────────────┘
                     │
                     ▼
 ┌────────────────────────────────────────┐
 │ 5. SLA 계약 기준 대조 및 위반 시 고객 보상
 └────────────────────────────────────────┘
```

### 동작 원리

1. 이벤트 수집: API Gateway에서 발생하는 모든 HTTP 호출의 상태 코드와 응답 시간을 로그/메트릭으로 집계.
2. SLI 계산: 유효한 전체 요청 중 정상 응답(HTTP 200~399 및 지연 300ms 이내)의 비율을 산출(예: 99.95%).
3. 예산 평가: 이번 달 SLO 목표치(99.9%)와 비교하여 남은 오류 예산이 충분한지 소진율(Burn Rate)을 계산.
4. 운영 조치: 예산이 남아있으면 기능 배포를 진행하고, 예산이 급소진되면 배포를 멈추고 롤백 및 복구 집중.
5. 계약 대조: 월말 정산 시 정기 점검 시간을 제외한 순수 가용성이 외부 SLA(99.5%)를 하회했는지 판정하여 크레딧 환불.

#### 한줄 요약

- 이벤트 수집 $\to$ SLI 계산 $\to$ SLO 평가 $\to$ 운영 조치 $\to$ SLA 보상 판정의 5단계

## Ⅴ. 종류 및 비교

<details><summary>용어 설명</summary>

- **SLI vs SLO vs SLA**: 주체, 대상, 위반 시 파급 효과에 따른 3대 개념 비교.

</details>

| 구분 | SLI (Service Level Indicator) | SLO (Service Level Objective) | SLA (Service Level Agreement) |
|:---|:---|:---|:---|
| **적용 기준** | 현재 시스템의 실제 품질을 정량적으로 진단 | 개발과 운영의 우선순위 조율 및 배포 통제 | 고객과의 공식 비즈니스 계약 및 신뢰 보장 |
| **핵심 특징** | **성공률 및 응답 지연의 실제 측정치 (%)** | **엔지니어링 내부 합의 목표, Error Budget** | **고객 대상 외부 계약, 법적/금전적 구속력** |
| **한계** | 지표 자체는 목표나 조치 방향을 제시하지 못함 | 너무 과도한 목표(100%) 설정 시 배포 중단 초래 | 너무 보수적 설정 시 고객 신뢰 저하 |

#### 한줄 요약

- SLI는 현재의 실측값, SLO는 내부 운영의 목표선, SLA는 고객과의 비즈니스 약속선

## Ⅵ. 실무 고려사항 및 대책

<details><summary>용어 설명</summary>

- **비현실적 100% SLO 안티패턴(100% SLO Anti-Pattern)**: 결함 없는 100% 가용성을 목표로 잡아 오류 예산을 0으로 만들고 1년 내내 배포를 마비시키는 치명적 실수.

</details>

| 문제 | 대책 | 효과 |
|:---|:---|:---|
| 100% 가용성 목표 설정으로 신규 기능 배포 전면 마비 | **비즈니스 비용과 사용자 체감을 고려한 현실적 99.9% SLO 합의** | 합리적 Error Budget 및 빠른 배포 속도 확보 |
| CPU 사용률을 SLI로 잡아 실제 사용자 장애 체감 누락 | **사용자 관점 지표(HTTP 성공률, P99 응답 지연)로 SLI 재정의** | 사용자 경험 100% 반영한 품질 통제 |
| 정기 점검 시간 장애 포함 여부로 고객과 SLA 보상 분쟁 | **SLA 계약 명세서에 사전 공지된 정기 점검은 제외(Exclude) 명시** | 법적 분쟁 및 불필요한 위약금 방지 |

#### 한줄 요약

- 현실적 목표 설정, 사용자 관점 SLI 정의, 사전 점검 제외 조항 명시를 통해 서비스 수준 관리를 완성

## Ⅶ. 결론

<details><summary>용어 설명</summary>

- **비즈니스 중심 신뢰성 관리(Business-Aligned SLM)**: SLI/SLO/SLA를 통해 엔지니어링의 신뢰성 투자가 기업의 매출과 고객 만족으로 직결되도록 만드는 체계.

</details>

- **SLO, SLA, SLI**는 현대 클라우드 소프트웨어 운영의 핵심 거버넌스 프레임워크이며, 사용자 관점의 SLI를 측정하고 SLA 위반 전 안전 마진 내에서 SLO 기반의 오류 예산을 운영하여 비즈니스 가치를 극대화해야 함

#### 한줄 요약

- SLI 실측, SLO 내부 목표, SLA 외부 계약의 계층적 연동을 통해 안정성과 개발 속도를 양립
