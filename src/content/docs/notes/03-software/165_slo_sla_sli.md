## Ⅰ. 개요

<details><summary>용어 설명</summary>

- **SLI / SLO / SLA 삼각 체계**: 사용자 관점의 실제 서비스 측정치인 SLI(Indicator), 내부 운영 목표인 SLO(Objective), 금전적 보상이 수반되는 고객 계약인 SLA(Agreement).
- **Safety Margin**: 외부 계약선인 SLA(99.5%)보다 내부 운영 목표선인 SLO(99.9%)를 엄격하게 설정하여 계약 위반 전 선제 조치하는 완충 버퍼.

</details>

- 정의/개념: 서비스 품질을 정량화하고 신뢰성을 관리하기 위해 **실제 측정 지표(SLI), 내부 엔지니어링 목표(SLO), 고객 보상 계약(SLA)을 계층화한 프레임워크**
- 배경/필요성: 가용성에 대한 모호하고 추상적인 정의로 인한 **가용성 정의 모호에 따른 고객 보상 기준 분쟁 방지 필요**

#### 한줄 요약
- SLI(실측), SLO(내부 목표), SLA(고객 계약)를 명확히 분리하여 품질 거버넌스와 배포 의사결정을 확립한다.

## Ⅱ. 특징

<details><summary>용어 설명</summary>

- **Error Budget**: `100% - SLO`로 산출되며 신규 기능 배포와 시스템 안정화에 사용할 수 있는 허용 실패량.

</details>

- 사용자 경험을 직접 대변하는 정량적 성공 비율 측정인 **SLI 기반의 현실 진단**
- 개발팀과 운영팀이 기능 출시와 안정화의 우선순위를 합의하는 **SLO 기반 내부 통제**
- 비즈니스 약속 미달 시 크레딧 환불 및 법적 구속력을 갖는 **SLA 기반 외부 계약**

#### 한줄 요약
- 실측치(SLI), 내부 목표(SLO), 외부 계약(SLA)의 단계적 연동을 통해 신뢰성과 비즈니스를 연결한다.

## Ⅲ. 구조 및 구성요소

<details><summary>용어 설명</summary>

- **SLM 3계층 모델**: SLA(고객 계약: 99.5%), Safety Margin(완충 격차), SLO(내부 목표: 99.9%), SLI(실제 측정치: 99.95%).

</details>

```text
[SLI, SLO, SLA 계층 관계 구조]
|-- 서비스 수준 계약 (SLA)
|   `-- 외부 고객 비즈니스 계약 및 보상
|-- 안전 마진 (Margin)
|   `-- SLA 위반 전 선제적 장애 방어 완충 버퍼
|-- 서비스 수준 목표 (SLO)
|   `-- 내부 엔지니어링 배포 통제 기준선
`-- 서비스 수준 지표 (SLI)
    `-- 사용자 관점 서비스 실제 성공률 측정치
선의 의미: 계층 및 SLI 실측치를 바탕으로 내부 SLO를 평가하고, SLA 계약선에 도달하기 전 안전 마진 내에서 선제 조치하는 구조

| 구성요소 | 핵심 엔지니어링 책임 | 주요 특징 |
|:---|:---|:---|
| 서비스 수준 지표 (SLI) | 사용자 관점에서 서비스의 **성공률, P99 지연시간, 처리량을 백분율(%)로 정량 산출** | 실시간 실측 수치 |
| 서비스 수준 목표 (SLO) | 엔지니어링 조직이 합의한 **내부 목표치로서 Error Budget 및 신규 배포 통제의 기준 제공**| 내부 운영 목표선 |
| 서비스 수준 계약 (SLA) | 고객과의 비즈니스 계약으로서 **위반 시 요금 할인, 크레딧 보상, 위약금 지급 조건 규정**| 법적/금전적 구속력 |
| 안전 마진 (Margin) | SLA 위반 전 장애를 수습할 수 있도록 **SLO와 SLA 사이에 확보하는 완충 격차** | 선제적 장애 방어 |

#### 한줄 요약
- SLI(실측), SLO(내부 목표), SLA(외부 계약), 안전 마진이 유기적으로 결합된다.

## Ⅳ. 흐름도

<details><summary>용어 설명</summary>

- **서비스 수준 운영 5단계**: 트랜잭션 이벤트 수집 $\to$ SLI 실측 계산 $\to$ SLO 대비 예산 평가 $\to$ 내부 배포/동결 조치 $\to$ SLA 계약 정산.

</details>

```text
서비스 운영 중 Prometheus 지표 집계
        │
   1. [이벤트 수집] API Gateway에서 모든 HTTP 호출 상태 코드와 응답 시간 수집
        │
   2. [SLI 계산] 전체 요청 중 정상 응답(HTTP 200 및 지연 300ms 이내) 성공 비율 산출
        │
   3. [SLO 예산 평가] 당월 SLO 목표치와 비교하여 남은 오류 예산 및 Burn Rate 분석
        │
   4. [운영 조치] 예산 여유 시 신규 기능 배포, 급소진 시 배포 동결 및 긴급 롤백
        │
   5. [SLA 계약 대조] 월말 정산 시 사전 점검을 제외한 가용성의 외부 SLA 충족 여부 확인
```

#### 한줄 요약
- 이벤트 수집 → SLI 계산 → SLO 예산 평가 → 운영 조치 → SLA 정산 순으로 진행된다.

## Ⅴ. 종류 및 비교

<details><summary>용어 설명</summary>

- **SLI vs SLO vs SLA**: 실측치(SLI), 내부 목표(SLO), 공식 계약(SLA)의 주체, 목적, 위반 시 조치 비교.

</details>

| 비교 항목 | SLI (Service Level Indicator) | SLO (Service Level Objective) | SLA (Service Level Agreement) |
|:---|:---|:---|:---|
| 정의 및 성격 | **현재 시스템의 실제 품질 측정값 (%)** | **엔지니어링 내부 합의 목표치 (%)** | **고객과의 공식 비즈니스 계약 (%)** |
| 주체 및 대상 | **모니터링 시스템 $\rightarrow$ 엔지니어** | **개발팀 $\leftrightarrow$ 운영팀 간 합의** | **기업 $\leftrightarrow$ 고객/사용자 간 계약** |
| 위반 시 파급 효과 | 지표 악화 (단순 수치 변화) | **신규 배포 동결 및 버그 수정 전환** | **이용료 할인, 크레딧 환불, 위약금** |
| 대표적 수치 예시 | **99.95% (실제 측정치)** | **99.90% (내부 운영 목표)** | **99.50% (외부 계약 기준선)** |

#### 한줄 요약
- SLI는 현재의 실측값, SLO는 내부 운영의 목표선, SLA는 고객과의 비즈니스 약속선이다.

## Ⅵ. 실무 고려사항 및 대책

<details><summary>용어 설명</summary>

- **100% SLO Anti-Pattern**: 결함 없는 100% 가용성을 목표로 잡아 오류 예산을 0으로 만들고 1년 내내 배포를 마비시키는 실수.

</details>

| 문제 | 대책 | 효과 |
|:---|:---|:---|
| 100% 가용성 목표 설정으로 신규 기능 배포 전면 마비 | **비즈니스 비용과 사용자 체감을 고려한 현실적 99.9% SLO 합의** | 합리적 Error Budget 및 빠른 배포 속도 확보 |
| CPU 사용률을 SLI로 잡아 실제 사용자 장애 체감 누락 | **사용자 관점 지표(HTTP 성공률, P99 응답 지연)로 SLI 재정의** | 사용자 경험 100% 반영한 품질 통제 |
| 정기 점검 시간 장애 포함 여부로 고객과 SLA 보상 분쟁 | **SLA 계약 명세서에 사전 공지된 정기 점검은 제외(Exclude) 명시** | 법적 분쟁 및 불필요한 위약금 방지 |
| 마이크로서비스 내부 호출 지연의 전파 | **서비스 간 호출 구간마다 개별 서비스별 내부 SLO 체계 수립** | 병목 서비스 조기 식별 및 격리 |

#### 한줄 요약
- 현실적 목표 설정, 사용자 관점 SLI 정의, 사전 점검 제외 조항 명시로 서비스 수준을 관리한다.

## Ⅶ. 결론

- 사용자 서비스 품질 정량화는 **SLI**, 내부 엔지니어링 운영 통제는 **SLO** 기반 선택

#### 한줄 요약
- SLI, SLO, SLA는 실측 지표, 내부 운영 목표, 외부 비즈니스 계약을 유기적으로 연계하여 엔지니어링과 비즈니스 가치를 일치시키는 핵심 서비스 수준 관리 체계다.
