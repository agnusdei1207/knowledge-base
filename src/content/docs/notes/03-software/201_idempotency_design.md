## Ⅰ. 개요

<details>
<summary>핵심 용어</summary>

- **멱등성(Idempotency)**: 같은 요청을 한 번 또는 여러 번 처리해도 최종 업무 결과가 동일하게 유지되는 성질이다.
- **응용 프로그래밍 인터페이스(Application Programming Interface, API)**: 프로그램 사이에서 요청과 응답을 주고받도록 정한 호출 규약이다.

</details>

- 정의/개념: 재시도에도 동일한 최종 업무 효과를 보장하는 **멱등성(Idempotency)**이다.
- 배경/필요성: **응용 프로그래밍 인터페이스(Application Programming Interface, API)** 재시도•중복 전달은 중복 결제를 일으킬 수 있다.

#### 한줄 요약
- 같은 주문이 여러 번 도착해도 한 번만 결제하고 처음 영수증을 다시 보여 준다.

## Ⅱ. 특징

<details>
<summary>핵심 용어</summary>

- **멱등 키(Idempotency Key)**: 같은 업무의 최초 요청과 재시도를 식별하는 고유 값이다.
- **요청 지문(Request Fingerprint)**: 같은 키로 다른 요청 본문이 들어오는 충돌을 검출하는 값이다.
- **원자적 확정(Atomic Commit)**: 처리권과 업무 결과를 모두 반영하거나 모두 반영하지 않아 중간 상태를 남기지 않는 처리 방식이다.
- **응답 재생(Response Replay)**: 중복 요청에 업무를 다시 실행하지 않고 최초 저장 응답을 반환하는 방식이다.
- **보존 기간(Retention Period)**: 재시도에 응답을 재생할 수 있도록 멱등 키와 결과를 유지하는 기간이다.

</details>

- **멱등 키(Idempotency Key)**와 **요청 지문(Request Fingerprint)**으로 동일 요청을 식별한다.
- **원자적 확정(Atomic Commit)**으로 처리권과 업무 결과의 단일 효과를 보장한다.
- **응답 재생(Response Replay)**과 **보존 기간(Retention Period)**으로 재시도를 통제한다.

#### 한줄 요약
- 요청 이름표와 결과를 함께 저장해야 동시에 도착한 복사본도 한 번만 처리할 수 있다.

## Ⅲ. 구조 및 구성요소

<details>
<summary>핵심 용어</summary>

- **처리권 저장소**: 같은 키의 동시 요청 중 하나에만 원자적으로 최초 실행권을 부여하는 저장소이다.
- **멱등성 게이트(Idempotency Gate)**: 멱등 키와 요청 지문을 검사해 최초 요청만 업무 처리기로 전달하는 진입 제어 구성요소이다.
- **결과 저장소(Result Store)**: 멱등 키와 처리 상태•응답을 연결해 중복 요청에 재사용할 결과를 보존하는 저장소이다.

</details>

```text
멱등성 처리 구조
      |
      +-- [요청자]
      |
      +-- 식별•처리권
      |         +-- [멱등성 게이트]
      |         +-- [처리권 저장소]
      |
      +-- 실행•결과
                +-- [업무 처리기]
                +-- [결과 저장소]
```

| 구성요소 | 책임 |
|:---|:---|
| 요청자 | 동일 키•재시도 요청 전송 |
| **멱등성 게이트(Idempotency Gate)** | 키•지문•동일성 판정 |
| **처리권 저장소** | 원자적 최초 실행권 부여 |
| 업무 처리기 | 처리권 요청만 업무 실행 |
| **결과 저장소(Result Store)** | 키•상태•응답 원자 보존 |

> 요약: 게이트가 최초 요청만 실행하고 **응답 재생(Response Replay)**으로 중복 요청을 처리한다.

#### 한줄 요약
- 게이트가 주문 이름표를 확인해 처음 주문만 실행하고 복사본에는 저장한 결과를 돌려준다.

## Ⅳ. 흐름도

<details>
<summary>핵심 용어</summary>

- **2. 처리권 획득**: 멱등성 게이트가 저장소의 조건부 연산으로 최초 실행권을 원자적으로 확보하는 단계이다.
- **1. 키•요청 검증**: 멱등 키의 형식•유효 기간과 요청 지문 일치 여부를 확인하는 단계이다.
- **3. 업무 수행**: 처리권을 획득한 최초 요청에만 실제 상태 변경을 허용하는 단계이다.
- **4. 결과 확정**: 업무 결과와 반환 응답을 멱등 키에 연결해 원자적으로 저장하는 단계이다.

</details>

```text
멱등 키•업무 요청
      |
      v
1. 키•요청 검증
      |
      +-- 형식•기간 오류 --> 요청 거부
      +-- 같은 키•다른 지문 --> 충돌 응답
      |
      +-- 검증 통과
              |
              v
2. 처리권 획득
      |
      +-- 완료 상태 --> 저장 응답 재생
      +-- 처리 중 --> 완료 대기•재조회
      |
      +-- 최초 처리권 획득
              |
              v
3. 업무 수행
      |
      v
4. 결과 확정
      |
      v
저장 응답 반환
```

### 동작 원리

1. **키•요청 검증**: 형식•기간•요청 지문을 확인한다.
2. **처리권 획득**: 최초 실행권을 원자적으로 획득한다.
3. **업무 수행**: 처리권을 얻은 요청만을 실행한다.
4. **결과 확정**: 업무 결과•응답을 함께 저장한다.

> 요약: 최초 요청만 실행하고 중복에는 **응답 재생(Response Replay)**을 수행한다.

#### 한줄 요약
- 같은 이름표로 먼저 온 주문만 처리하고 나머지는 처음 영수증을 받는다.

## Ⅴ. 종류 및 비교

<details>
<summary>핵심 용어</summary>

- **조건부 갱신**: 현재 버전이나 상태가 기대 조건과 일치할 때만 값을 바꿔 동시 수정 충돌을 막는 방식이다.
- **멱등 키 적용**: 자연 멱등이 아닌 요청의 최초 호출과 재시도 식별이다.
- **자연 멱등 연산(Naturally Idempotent Operation)**: 동일 값을 설정하거나 이미 없는 자원을 삭제하는 것처럼 반복해도 결과가 달라지지 않는 연산이다.

</details>

| 멱등 처리 방식 | **멱등 키 적용** | **자연 멱등 연산(Naturally Idempotent Operation)** | **조건부 갱신** |
|:---|:---|:---|:---|
| 적용 기준 | 생성•결제 요청 재시도 | 상태 설정•삭제 요청 | 동시 수정 충돌 방지 |
| 핵심 특징 | 최초 결과 저장•재생 | 동일 값을 반복 설정 | 조건 일치 시 갱신 |
| 한계 | 키 충돌•보존 만료 | 증가 연산 적용 불가 | 버전 충돌 재시도 |

> 요약: 생성은 키, 상태 설정은 자연 멱등, 수정은 조건부가 핵심이다.

#### 한줄 요약
- 새 주문은 이름표를 저장하고 상태 설정은 같은 값을 반복하며 수정은 버전을 확인한다.

## Ⅵ. 실무 고려사항 및 대책

<details>
<summary>핵심 용어</summary>

- **부분 확정**: 업무 결과와 멱등 키•응답 중 일부만 저장되어 재시도 때 업무 효과가 반복되는 문제이다.
- **트랜잭셔널 아웃박스(Transactional Outbox)**: 업무 데이터와 발행할 메시지를 같은 트랜잭션에 기록한 뒤 별도 전달기가 메시지를 발행하는 패턴이다.
- **유효 시간(Time To Live, TTL)**: 멱등 키와 저장 결과를 자동 만료시키기까지 유지하는 시간이다.

</details>

| 문제 | 대책 | 효과 |
|:---|:---|:---|
| 다른 요청의 키 재사용 | 사용자•업무별 **멱등 키(Idempotency Key)** 범위 분리 | 결과 혼선 방지 |
| 같은 키의 본문 변경 | **요청 지문(Request Fingerprint)** 비교•충돌 응답 | 요청 동일성 보장 |
| 업무와 결과의 **부분 확정** | **원자적 확정(Atomic Commit)**•**트랜잭셔널 아웃박스(Transactional Outbox)** | 중복 효과 차단 |
| 짧은 보존 기간 | 재시도 창보다 긴 **유효 시간(Time To Live, TTL)** 설정 | 만료 후 중복 예방 |

#### 한줄 요약
- 결제 요청이 다시 와도 주문 키에 저장한 승인 결과만 반환한다.

## Ⅶ. 결론

<details>
<summary>핵심 용어</summary>

- **멱등 처리 방식 선택 기준**: 생성•결제 재시도에는 멱등 키, 자연 멱등 연산에는 반복 실행, 동시 수정에는 조건부 갱신을 적용하는 기준이다.

</details>

- **멱등 처리 방식 선택 기준**에 따라 생성•결제 재시도는 멱등 키, 동시 갱신은 조건부 갱신을 적용한다.

#### 한줄 요약
- 요청이 어디서 재시도되든 같은 업무 키와 최초 결과를 끝까지 추적해야 한다.
