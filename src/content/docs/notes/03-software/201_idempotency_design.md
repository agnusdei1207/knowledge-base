## Ⅰ. 개요

<details><summary>용어 설명</summary>

- **Idempotency (멱등성)**: 동일한 요청을 1회 또는 수십 번 반복 수행하더라도 서버의 최종 상태가 단 한 번 실행했을 때와 동일하게 유지되는 성질.
- **Idempotency-Key**: 클라이언트가 요청 헤더에 첨부하는 고유 UUID 식별자로 중복 요청을 식별하는 표준 키.

</details>

- 정의/개념: 동일한 요청을 여러 번 반복 실행하더라도 **시스템의 최종 상태가 단 한 번 실행했을 때와 동일하게 유지되도록 보장하는 분산 설계 원칙**
- 배경/필요성: 네트워크 타임아웃 시 클라이언트 재시도나 브로커 재전송(At-Least-Once)으로 인한 **중복 결제, 이중 재고 차감 및 데이터 무결성 파괴 해결 불가**

#### 한줄 요약
- Idempotency-Key와 원자적 상태 관리를 통해 중복 요청에 의한 비즈니스 부작용을 원천 차단한다.

## Ⅱ. 특징

<details><summary>용어 설명</summary>

- **Request Fingerprint (요청 지문)**: 동일 멱등 키에 요청 바디(금액, 수신자)를 위변조하여 재시도하는 것을 탐지하는 SHA-256 해시값.
- **Response Replay (응답 재생)**: 이미 완료된 멱등 키 수신 시 비즈니스 로직을 재실행하지 않고 최초 저장된 HTTP 응답을 즉시 반환하는 기법.

</details>

- 클라이언트가 부여한 UUID를 기반으로 최초 처리 여부를 판별하는 **Idempotency Key 식별**
- 비즈니스 상태 갱신과 멱등 키/응답 저장을 묶는 **원자적 커밋(Atomic Commit)**
- 중복 요청 수신 시 저장된 최초 응답을 그대로 반환하는 **응답 재생(Response Replay)**

#### 한줄 요약
- 고유 키 식별, 원자적 결과 저장, 응답 재생을 통해 중복 처리 비용과 부작용을 방지한다.

## Ⅲ. 구조 및 구성요소

<details><summary>용어 설명</summary>

- **멱등성 처리 4대 핵심 구조**: Idempotency Gate(진입 검증), Execution Lock(SETNX 단일 실행권), Business Processor(비즈니스 실행), Result Store(응답 캐시).

</details>

```text
[분산 멱등성(Idempotency) 처리 게이트 및 저장소 구조]
|-- 1. Idempotency Gate Layer (HTTP Header: `Idempotency-Key: UUID-1234` 검증)
|   |-- Key & Request Fingerprint Validation (요청 바디 SHA-256 해시 대조)
|   `-- State Routing (최초 요청 / 처리 진행 중 / 완료 상태 분기)
`-- 2. Distributed Execution Lock Layer (Redis `SET key val NX EX 30` 단일 실행권 획득)
`-- 3. Business Processor Layer (RDBMS: 결제 승인, 계좌 차감 트랜잭션 실행)
`-- 4. Result & Response Store Layer (성공 응답 JSON 영속화 및 TTL 24시간 보존)
```

선의 의미: 계층 및 게이트가 멱등 키와 지문을 검증하여 최초 요청에만 실행권을 부여하고 완료된 요청에는 저장된 응답을 반환하는 구조

| 구성요소 | 핵심 엔지니어링 책임 | 주요 특징 |
|:---|:---|:---|
| **멱등성 게이트 (Gate)** | 멱등 키 및 요청 지문(Fingerprint)을 대조하여 **최초, 진행 중, 완료 요청 분기 처리** | 진입점 필터 |
| **실행권 저장소 (Lock)** | Redis `SETNX` 분산 락을 통해 **동일 키에 대해 단 하나의 스레드에만 실행권 부여** | 동시성 제어 |
| **비즈니스 처리기 (Logic)**| 실행권을 획득한 요청에 대해 **실제 결제 승인 및 DB 원자적 트랜잭션 수행** | 핵심 비즈니스 |
| **결과 저장소 (Store)** | 완료된 비즈니스 결과와 **HTTP 응답 객체를 키와 결속하여 TTL 동안 영속 보관** | 응답 재생 저장소 |

#### 한줄 요약
- 멱등 게이트, 실행권 락, 비즈니스 처리기, 결과 저장소가 결합된다.

## Ⅳ. 흐름도

<details><summary>용어 설명</summary>

- **멱등성 요청 처리 5단계**: 멱등 키/지문 검증 $\to$ SETNX 실행권 획득 $\to$ 비즈니스 트랜잭션 실행 $\to$ 결과/응답 원자적 저장 $\to$ 응답 재생 및 반환.

</details>

```text
클라이언트의 결제 요청 (Idempotency-Key: UUID-1234)
        │
   1. [키 및 지문 검증] 헤더의 멱등 키 형식과 요청 바디 해시(Fingerprint) 위변조 검사
        │
   2. [실행권 획득 (SETNX)] Redis 분산 락으로 최초 실행권 획득 시도
   ┌────┴───────────────────────────┐
  최초 획득                         이미 완료된 키
   │                                 │
3A. [비즈니스 로직 실행]            3B. [응답 재생 (Replay)]
   DB 결제 승인 및 계좌 차감 커밋       저장소에서 최초 응답(HTTP 200) 즉시 회신
   │                                 │
4. [결과 원자적 저장]               │
   처리 결과와 응답을 DB에 영속화    │
   │                                 │
   └────┬────────────────────────────┘
        ▼
   5. 클라이언트에게 최종 결제 성공 응답 반환 완료
```

#### 한줄 요약
- 키/지문 검증 → 실행권 획득 → 비즈니스 실행 → 결과 저장 → 응답 재생 순으로 진행된다.

## Ⅴ. 종류 및 비교

<details><summary>용어 설명</summary>

- **3대 멱등 처리 메커니즘**: Idempotency Key 패턴, Naturally Idempotent(자연 멱등), Conditional Update(조건부 갱신).

</details>

| 비교 항목 | 멱등 키 패턴 (Idempotency Key) | 자연 멱등 연산 (Naturally Idempotent) | 조건부 갱신 (Conditional Update) |
|:---|:---|:---|:---|
| 핵심 적용 대상 | **POST 결제, 주문 생성 등 비멱등 요청** | **PUT 상태 교체, DELETE 삭제 요청** | **동시성 경합이 있는 UPDATE 잔액 갱신**|
| 핵심 구현 기법 | **고유 UUID 헤더 검증 + 응답 Replay** | **절대값 덮어쓰기 (`SET status='PAID'`)**| **`WHERE version = :v` 낙관적 락** |
| 추가 인프라 부담 | 멱등 키 및 응답 캐시 저장소 필요 | 추가 인프라 불필요 (자연 멱등성) | DB 버전 컬럼 관리 필요 |
| 최적 적용 사례 | **Stripe/토스 결제 API, Kafka 소비자** | 회원 프로필 수정, 파일 삭제 | 재고 수량 차감, 포인트 차감 |

#### 한줄 요약
- 신규 생성 및 결제는 멱등 키 패턴, 단순 상태 변경은 자연 멱등, 동시성 차감은 조건부 갱신을 선택한다.

## Ⅵ. 실무 고려사항 및 대책

<details><summary>용어 설명</summary>

- **Partial Commit (부분 확정)**: 결제 승인은 성공했으나 멱등 키/응답 저장이 실패하여 재시도 시 이중 결제가 발생하는 장애.

</details>

| 문제 | 대책 | 효과 |
|:---|:---|:---|
| 결제 성공 후 멱등 키 저장 실패로 재시도 시 이중 결제 (부분 확정)| **비즈니스 DB 갱신과 멱등 키 저장을 단일 ACID 트랜잭션으로 원자적 커밋** | 결제 중복 사고 원천 차단 |
| 서로 다른 사용자가 우연히 동일한 멱등 키를 사용하여 충돌 | **멱등 키에 `User_ID + Business_Type` 접두어(Namespace) 강제 결합** | 키 충돌 및 타인 응답 노출 방지 |
| 클라이언트 재시도 주기보다 짧은 TTL로 인해 만료 후 중복 실행 | **클라이언트 최대 재시도 기간의 2배 이상(최소 24시간) TTL 보존** | 재시도 창 내 100% 멱등성 보장 |
| 동일 키로 결제 금액을 변조하여 재전송하는 악성 공격 | **요청 바디의 SHA-256 Fingerprint를 대조하여 불일치 시 `409 Conflict`** | 요청 변조 공격 차단 |

#### 한줄 요약
- 원자적 커밋, 네임스페이스 격리, 충분한 TTL 보존, 요청 지문 검증으로 운영한다.

## Ⅶ. 결론

- 분산 네트워크 환경에서 재시도와 비동기 메시지 중복으로 인한 비즈니스 데이터 오염을 방지하기 위해 **모든 핵심 생성/결제 API에 Idempotency-Key 표준 헤더와 원자적 커밋 아키텍처를 의무화**하고, **요청 지문(Fingerprint) 위변조 검증과 응답 재생(Replay)**을 결합하여 완벽한 분산 멱등성 완성

#### 한줄 요약
- 멱등성 설계는 고유 키 식별, 분산 락 실행권 통제, 원자적 결과 영속화를 통해 중복 요청에도 단 한 번의 비즈니스 효과만을 보장하는 핵심 분산 시스템 설계 기술이다.
