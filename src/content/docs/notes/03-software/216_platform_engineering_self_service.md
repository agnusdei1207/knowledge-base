## Ⅰ. 개요

<details><summary>용어 설명</summary>

- **내부 개발자 플랫폼(Internal Developer Platform, IDP)**: 개발팀의 인지 부하를 줄이기 위해 앱 개발·배포·운영 도구를 셀프서비스 형태로 제공하는 사내 표준화된 기술 제품(Product) 체계.
- **플랫폼 엔지니어링(Platform Engineering)**: 개발팀이 일관되고 안전하게 소프트웨어를 전달할 수 있도록 내부 플랫폼을 제품처럼 설계·운영하고 지속 개선하는 기술 조직의 핵심 활동.
- **셀프서비스(Self-Service)**: 사전에 승인된 보안 및 운영 정책 범위(Guardrail) 안에서, 개발팀이 인프라/운영팀의 수동 개입이나 승인 대기 없이 필요한 자원을 직접 요청·생성·관리하는 클라우드 네이티브 운영 방식.

</details>

- 정의/개념: IDP에서 검증된 경로를 Self-Service로 제공하는 **운영 방식**
- 배경/필요성: 수동 자원 할당의 **Ticket 대기•운영 병목•인지 부하** 발생

#### 한줄 요약

- 개발팀이 운영팀의 승인 대기 없이 검증된 카탈로그(메뉴)에서 필요한 클라우드 네이티브 환경을 직접 프로비저닝할 수 있도록 지원하는 내부 기술 서비스 체계.

## Ⅱ. 특징

<details><summary>용어 설명</summary>

- **인지 부하 감소(Cognitive Load Reduction)**: 복잡한 인프라 설정이나 배포 파이프라인 구성 등 공통 기술의 복잡성을 골든 패스와 자동화 뒤로 추상화하여, 개발팀이 비즈니스 로직(업무 기능) 개발에만 온전히 집중하게 만드는 플랫폼의 핵심 효과.
- **골든 패스(Golden Path, 권장 표준 경로)**: 조직의 보안 및 아키텍처 기준을 통과한 검증된 도구·구성·절차를 패키징하여, 대부분의 개발팀이 가장 안전하고 빠르게 제품을 출시할 수 있도록 권장하는 베스트 프랙티스 경로.
- **제품 중심 운영(Product-Oriented Operation)**: 사내 개발자를 플랫폼의 '고객'으로 간주하고, 사용자 경험(UX), 사용성, 채택률, 피드백 사이클을 기반으로 내부 플랫폼을 상용 제품처럼 지속적으로 진화시키는 운영 철학.

</details>

- 정책 가드레일 기반의 자율성: 사전 정의된 규정(보안, 컴플라이언스) 내에서 개발팀이 자원을 직접 제어할 수 있도록 자율성과 통제력을 동시에 보장.
- 공통 기술 추상화와 **인지 부하 감소**: 쿠버네티스, CI/CD, 모니터링 등 기저 인프라의 복잡성을 숨겨 개발자 생산성 극대화.
- 사용자(개발자) 중심의 **제품 중심 운영**: 강제적인 도구 사용이 아닌, 편의성과 가치를 제공함으로써 자발적인 플랫폼 채택(Adoption)을 유도.

#### 한줄 요약

- 플랫폼이 복잡한 공통 인프라 작업을 추상화하여 자동화하되, 개발팀의 필요에 따른 유연한 선택권과 예외 경로를 제공하여 공식 표준 경로의 자발적 채택을 유도.

## Ⅲ. 구조 및 구성요소

<details><summary>용어 설명</summary>

- **제어 평면(Control Plane)**: 카탈로그를 통한 개발자의 자원 요청을 수신하고, 선언적 정책(Policy)을 확인한 뒤 실제 인프라 자원의 프로비저닝·변경·삭제 전체 수명주기를 오케스트레이션하는 백엔드 핵심 엔진.
- **개발자 포털·카탈로그(Developer Portal and Catalog)**: 개발자가 마이크로서비스, 인프라 템플릿, API 등을 통합 검색·요청하고, 전체 서비스의 소유권(Ownership) 및 배포 상태를 단일 화면(Single Pane of Glass)에서 확인하는 사용자 접점(UI).
- **정책 가드레일(Policy Guardrail)**: 접근 권한, 보안 취약점 기준, 클라우드 비용 한도 등을 코드로 정의(Policy-as-Code)하여, 허용 범위 안의 요청만 자동으로 프로비저닝되도록 통제하는 안전 장치.
- **제품 피드백(Product Feedback)**: 플랫폼 이용 현황 데이터(Telemetry)와 개발자의 직접적인 요구사항을 수집·분석하여, 기존 골든 패스를 개선하거나 새로운 기능 로드맵을 수립하는 데 활용하는 순환 체계.

</details>

```text
[Internal Developer Platform]
 ├── [개발자 Portal•Catalog]
 ├── [Golden Path]
 ├── [Control Plane]
 ├── [Policy Guardrail]
 └── [Product Feedback]
```

| 구성요소 | 책임 |
|:---|:---|
| 개발자 Portal•Catalog | Template 검색•요청•Owner•**상태 가시성** 제공 |
| Golden Path | Architecture•보안이 내장된 **표준 Template** 제공 |
| Control Plane | IaC 기반 자원 생성과 **상태 동기화** 수행 |
| Policy Guardrail | 권한•보안•비용 **Policy-as-Code** 검증 |
| Product Feedback | 사용•마찰 지표로 **Platform Roadmap** 개선 |

#### 한줄 요약

- 개발자가 포털 UI에서 검증된 템플릿을 선택하면, 제어 평면이 정책 엔진을 통해 보안을 확인한 후 인프라를 자동 구축하고 이용 데이터를 다시 플랫폼 개선에 활용.

## Ⅳ. 흐름도

<details><summary>용어 설명</summary>

- **2. 정책 자동 검증(Policy Auto-Verification)**: 제어 평면이 Policy-as-Code(예: OPA/Rego)로 작성된 가드레일을 참조하여, 요청된 자원 사양이 조직의 보안/비용 기준에 부합하는지 즉각적으로 심사하는 단계.
- **1. 표준 사양 전달(Standard Spec Transmission)**: 개발자가 포털을 통해 선택한 골든 패스의 템플릿 매개변수와 구성 값을 제어 평면의 API로 선언적으로 전달하는 단계.
- **3. 자원 자동 생성(Automated Resource Provisioning)**: 검증을 통과한 선언적 사양을 바탕으로 Terraform, ArgoCD 등의 자동화 파이프라인을 작동시켜 실제 인프라, Git 저장소, CI/CD 환경을 일괄 구축하는 단계.
- **4. 상태 카탈로그 등록(Status Catalog Registration)**: 프로비저닝이 완료된 자원의 소유권, 엔드포인트 정보, 런타임 상태 데이터를 개발자 카탈로그에 자동 업데이트하여 가시성을 확보하는 단계.

</details>

```text
셀프서비스 요청
      |
      v
1. 표준 사양 전달
      |
      v
2. 정책 자동 검증
      |
      +-- 정책 위반 ---- 사양 수정•예외 승인 (수동 티켓팅 연계)
      |
      `-- 정책 통과
              |
              v
      3. 자원 자동 생성
              |
              v
      4. 상태 카탈로그 등록
              |
              v
          처리 상태 확인
              |
              `-- 이용 데이터•의견 수집 ---- 골든 패스 지속 개선
```

### 동작 원리

1. **표준 사양 전달**: 개발자가 선택한 골든 패스 템플릿과 매개변수를 제어 평면에 API 형태로 전달.
2. **정책 자동 검증**: OPA(Open Policy Agent) 등을 활용하여 요청의 권한, 보안, 비용 제한을 실시간 판정.
3. **자원 자동 생성**: 검증 통과 시 IaC 기반의 자동화 파이프라인을 통해 클라우드 환경 및 저장소를 즉각 구성.
4. **상태 카탈로그 등록**: 생성된 자산 정보를 서비스 카탈로그에 연동하여 단일 가시성(Single Pane of Glass)과 소유권을 확립.

#### 한줄 요약

- 개발자가 포털에서 표준 구성을 선택하여 요청하면, 코드 기반의 정책 검사를 즉시 통과한 인프라가 자동 구축되고, 그 결과와 모니터링 데이터가 서비스 카탈로그에 동기화.

## Ⅴ. 종류 및 비교

<details><summary>용어 설명</summary>

- **가드레일 셀프서비스(Guardrailed Self-Service)**: 반복적이고 표준화된 인프라 수요를 자동 정책 제어(Guardrail) 범위 내에서 개발팀이 대기 없이 직접 프로비저닝하는 이상적인 플랫폼 모델.
- **티켓 기반 제공(Ticket-Based Provisioning)**: 개발팀이 JIRA나 ITSM 도구로 자원을 요청하면, 인프라/운영팀이 건별로 요구사항을 검토하고 수동으로 승인·처리하는 전통적 방식.
- **완전 자율(Full Autonomy, 섀도우 IT 위험)**: 중앙 통제나 공통 플랫폼 없이 개발팀 단위로 도구와 클라우드 정책을 자유롭게 선택하고 직접 인프라를 운영(DevOps Anti-pattern)하여 사일로를 발생시키는 방식.

</details>

| 플랫폼 제공 방식 | **가드레일 셀프서비스** | **티켓 기반 제공** | **완전 자율** |
|:---|:---|:---|:---|
| 적용 기준 | 수요의 반복성과 표준화 가능성이 높은 경우 | 인프라 예외가 많고 보안 심사 및 수동 승인이 필요한 경우 | 스타트업 초기 등 팀별 요구사항이 고유하고 빠르게 변화할 때 |
| 핵심 특징 | 정책 범위 내에서 자동화된 파이프라인으로 즉시 생성 | 운영팀이 요청 내용을 확인 후 인프라를 수동 구성 | 개발팀이 아키텍처와 기술 스택을 독자적으로 판단하여 직접 운영 |
| 한계 | 플랫폼 팀의 초기 구축 및 유지보수 비용 발생, 예외 처리에 경직성 | 리드 타임 증가, 운영팀 병목(Bottleneck) 및 개발자 피로도 가중 | 전사 표준화 실패, 보안 취약점 증가, 중복 기술 투자(섀도우 IT) |

> 요약: 조직 내 반복적인 표준 수요는 **가드레일 셀프서비스**로 처리하여 속도를 높이고, 컴플라이언스가 복잡한 예외 케이스는 **티켓 기반 제공** 방식을 병행하는 하이브리드 전략이 권장됨.

#### 한줄 요약

- 정형화된 공통 작업은 셀프서비스로 즉각 처리하고, 복잡한 인적 판단이 개입되는 예외 작업은 티켓으로, 팀별 특수성이 매우 큰 초기 탐색 단계는 완전 자율로 접근.

## Ⅵ. 실무 고려사항 및 대책

<details><summary>용어 설명</summary>

- **개발자 채택률(Developer Adoption Rate)**: 강제 지시가 아닌 개발자의 자발적 만족도를 기반으로 전체 개발팀 중 사내 공식 플랫폼을 활발히 사용하는 팀의 비중.
- **서비스 수준 목표(Service Level Objective, SLO)**: 플랫폼 조직이 내부 고객(개발자)에게 약속하는 플랫폼 시스템의 가용성, API 응답 시간, 프로비저닝 성공률에 대한 정량적 목표 수치.
- **마찰 지표(Friction Metric)**: 개발자가 코드를 작성하고 배포를 완료하기까지 겪는 승인 대기 시간, 매뉴얼 작업 건수, 파이프라인 실패율 등 개발 경험(DevEx)을 저해하는 장애물 지표.

</details>

| 실무 문제점 | 해결 대책 | 기대 효과 |
|:---|:---|:---|
| 골든 패스의 지나친 경직성 | 기본 경로(Core)와 팀별 확장 지점(Extension) 분리 설계 | 전사 보안 통제와 개발팀의 기술 자율성 간의 균형 유지 |
| 셀프서비스 허용에 따른 보안 사고 | **정책 가드레일** 도입 및 최소 권한(Least Privilege) 원칙 엄격 적용 | 휴먼 에러로 인한 오구성 및 클라우드 비용 폭탄 위험 사전 차단 |
| 내부 플랫폼의 소유자(Owner) 부재 | 전담 프로덕트 매니저(PM) 배정 및 **서비스 수준 목표** 로드맵 운영 | 상용 제품에 준하는 기능 업데이트 및 플랫폼 운영의 영속성 확보 |
| 낮은 **개발자 채택률** | 설문 조사 기반의 사용성 테스트 및 **마찰 지표** 지속 모니터링·개선 | 개발자 경험(DevEx) 향상을 통한 플랫폼 활용 가치 및 ROI 극대화 |

#### 한줄 요약

- 플랫폼 도입 시 강제적 표준화보다는 개발자 경험(DevEx)을 우선시하여 마찰을 줄이고, 점진적으로 플랫폼 채택률을 높이는 제품 관리 방식의 접근 필수.

## Ⅶ. 결론

<details><summary>용어 설명</summary>

- **플랫폼 제공 경로 선택 기준(Platform Provisioning Strategy)**: 인프라 요청의 복잡도, 반복성, 위험도를 종합적으로 평가하여 셀프서비스 자동화 대상과 수동 개입 대상을 분류하는 의사결정 프레임워크.
- **예외 경로(Exception Path, 이스케이프 해치)**: 표준 골든 패스만으로는 처리 불가능한 레거시 연동이나 특수 아키텍처 요구를 수용하기 위해, 가드레일을 벗어난 요청을 운영자가 개별 검토하도록 마련된 우회 승인 절차.

</details>

- 반복•저위험 요청은 **Guardrail Self-Service**, 고위험 예외는 Ticket 심사

#### 한줄 요약
