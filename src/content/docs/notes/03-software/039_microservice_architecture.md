## Ⅰ. 개요

<details><summary>용어 설명</summary>

- **독립 배포 및 DB 격리(Database-per-Service)**: 서비스마다 자체 데이터 저장소를 소유하고 경량 API(REST/gRPC)로만 통신하여 독립적 CI/CD를 수행하는 원칙.
- **단일 실패점 및 전수 재배포(SPOF & Monolithic Bottleneck)**: 코드 한 줄 변경에도 전체 바이너리를 재빌드해야 하고 한 모듈의 메모리 누수가 전체 시스템 다운을 초래하는 한계.

</details>

- 정의/개념: 단일 애플리케이션을 비즈니스 도메인 경계로 분할하여 **독립 배포 단위와 Database-per-Service** 활용 보장하는 분산 서비스 아키텍처
- 배경/필요성: 거대 모놀리스의 단일 실패점(SPOF) 및 부분 변경 시 **전체 시스템 전수 재빌드·재배포 병목과 확장 한계** 직면

#### 한줄 요약

- 비즈니스 도메인 단위 서비스 분리와 Database-per-Service로 독립 배포·확장·장애 격리를 달성하는 분산 아키텍처

## Ⅱ. 특징

<details><summary>용어 설명</summary>

- **장애 격리(Fault Isolation)**: 개별 서비스 장애가 타 서비스로 전파되지 않아 부분 장애 시에도 나머지 서비스가 정상 운영되는 MSA의 복원력 특성.
- **폴리글랏 퍼시스턴스(Polyglot Persistence)**: 서비스별 요구사항에 따라 RDBMS·NoSQL·캐시 등 이기종 데이터 저장소를 혼용하는 MSA의 기술 선택 자유도.

</details>

- **Database-per-Service** 원칙으로 서비스 간 데이터 격리 및 독립 CI/CD 배포 파이프라인 구성
- 서비스별 최적 기술 스택 선택이 가능한 **폴리글랏 아키텍처** 지원
- 개별 서비스 장애의 타 서비스 파급을 차단하는 **장애 격리** 및 개별 수평 확장(Scale-out) 지원

#### 한줄 요약

- DB 격리·폴리글랏 기술 선택·장애 격리가 MSA의 핵심 설계 특성

## Ⅲ. 구조 및 구성요소

<details><summary>용어 설명</summary>

- **API 게이트웨이(API Gateway)**: 클라이언트의 단일 진입점으로 인증·인가·라우팅·Rate Limiting을 처리하는 엣지 서버.
- **서비스 디스커버리(Service Discovery)**: 동적으로 변하는 서비스 인스턴스 위치를 레지스트리(Eureka 등)에서 실시간으로 조회하는 서비스 위치 관리 메커니즘.

</details>

```text
[ MSA 분산 아키텍처 구조 ]
클라이언트 (Web/App)
   │
API 게이트웨이 (인증·라우팅·Rate Limiting)
   │
┌──┴──────────────────────┐
서비스 디스커버리           분산 추적·로그 집계
   │
┌──┴──────────────────────┐
주문 서비스      결제 서비스      배송 서비스
(주문 DB)  ←─Kafka─→  (결제 DB)    (배송 DB)
```

선의 의미: API 게이트웨이에서 내려오는 화살표는 라우팅 경로, 서비스 간 Kafka 화살표는 비동기 이벤트 통신 관계

| 구성요소 | 책임 |
|:---|:---|
| **API 게이트웨이** | 인증·라우팅·Rate Limiting 단일 진입점 |
| **서비스 디스커버리** | 동적 서비스 인스턴스 위치 조회 |
| 독립 마이크로서비스 | 도메인별 비즈니스 로직·전용 DB 보유 |
| **이벤트 브로커(Kafka)** | 서비스 간 비동기 이벤트 전달 |
| 관측 플랫폼 | 분산 추적(Distributed Tracing)·로그 집계 |

#### 한줄 요약

- API 게이트웨이가 단일 진입점을 제공하고 서비스 디스커버리·Kafka·분산 추적이 서비스 간 통신을 지원

## Ⅳ. 흐름도

<details><summary>용어 설명</summary>

- **분산 트랜잭션(Distributed Transaction)**: DB가 서비스별로 분리된 환경에서 여러 서비스에 걸친 데이터 일관성을 유지해야 하는 복잡한 문제.

</details>

```text
1. API 게이트웨이 요청 수신·인증·라우팅
   │
   ▼
2. 주문 서비스: 로컬 트랜잭션 실행
   └─ 주문 DB에 '결제 대기' 상태 저장
   └─ Kafka에 '주문 생성' 이벤트 발행
   │
   ▼
3. 결제 서비스: 이벤트 수신·로컬 트랜잭션 실행
   │
   ▼
4. 결과 처리
├─ 성공: 주문 DB '완료' 업데이트
└─ 실패: Saga 보상 트랜잭션으로 주문 DB '취소' 처리
```

**동작 원리**

1. **요청 진입**: API 게이트웨이가 인증 토큰 검증 후 해당 서비스로 라우팅
2. **로컬 트랜잭션 1**: 주문 서비스가 주문 DB에 저장 후 Kafka에 이벤트를 발행
3. **로컬 트랜잭션 2**: 결제 서비스가 이벤트를 수신하여 결제 DB에서 처리
4. **Saga 보상**: 결제 실패 시 역순으로 보상 트랜잭션을 실행하여 데이터 정합성 복원

#### 한줄 요약

- DB 분리 환경에서 Saga 패턴의 단계별 로컬 트랜잭션과 보상 트랜잭션으로 최종 일관성을 확보

## Ⅴ. 종류 및 비교

<details><summary>용어 설명</summary>

- **분산 모놀리스(Distributed Monolith)**: 서비스를 분리했지만 공유 DB나 강한 동기 호출 의존으로 단일 서비스 장애가 전체 시스템에 파급되는 MSA 안티패턴.

</details>

| 구분 | 모놀리식 | MSA |
|:---|:---|:---|
| 적용 기준 | 초기 스타트업·소규모 시스템 | 독립 확장·팀별 독립 배포 필요 대규모 |
| 핵심 특징 | 단일 배포 단위·강한 ACID 트랜잭션 | 독립 배포·**Database-per-Service**·장애 격리 |
| 한계 | 확장 한계·파급 변경 위험 | 분산 트랜잭션·운영 복잡도·관측 체계 필요 |

#### 한줄 요약

- 독립 배포·확장 이점이 분산 복잡도 비용을 상회하는 규모에서 MSA 전환을 결정

## Ⅵ. 실무 고려사항 및 대책

<details><summary>용어 설명</summary>

- **Saga 패턴(Saga Pattern)**: 분산 환경에서 서비스별 로컬 트랜잭션을 순차 실행하고 실패 시 역순으로 보상 트랜잭션을 실행하여 최종 일관성을 달성하는 분산 트랜잭션 패턴.

</details>

| 문제 | 대책 | 효과 |
|:---|:---|:---|
| DB 분리 환경에서 서비스 간 트랜잭션 원자성 보장 불가 | **Saga 패턴** 기반 보상 트랜잭션으로 최종 일관성 확보 | 분산 DB 환경에서 데이터 정합성 복원 |
| 단일 서비스 장애가 동기 호출 체인으로 전체 시스템에 전파 | **Circuit Breaker** 패턴으로 장애 서비스 호출 차단 | 장애 격리 및 부분 서비스 정상 운영 유지 |
| 수십 개 서비스를 거친 요청의 장애 원인 추적 불가 | **Zipkin·Jaeger** 분산 추적(Trace ID 기반) 적용 | 전체 요청 경로와 지연 병목 추적 가능 |

#### 한줄 요약

- 분산 트랜잭션은 Saga로, 장애 전파는 Circuit Breaker로, 추적 불가는 분산 추적으로 해소

## Ⅶ. 결론

<details><summary>용어 설명</summary>

- **MSA 도입 판정 기준**: 독립 배포 이득·DevOps 역량·도메인 경계 명확성·인프라 투자 여력을 종합하여 MSA·모듈러 모놀리스 중 선택하는 판단 기준.

</details>

- 독립 배포 이득이 분산 운영 복잡도를 상회하는 규모와 DevOps 역량이 갖춰질 때 **MSA**, 그 외에는 **모듈러 모놀리스** 선택

#### 한줄 요약

- 조직 역량·도메인 경계·트래픽 규모가 MSA의 복잡도 비용을 정당화할 때 단계적으로 전환을 적용
