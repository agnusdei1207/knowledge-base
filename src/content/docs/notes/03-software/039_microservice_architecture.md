## Ⅰ. 개요

<details><summary>용어 설명</summary>

- **MSA(Microservices Architecture)**: 대규모 애플리케이션을 비즈니스 도메인 중심의 작고 독립적으로 배포 가능한 서비스들의 집합으로 분할하는 아키텍처 스타일.
- **Database-per-Service**: 각 마이크로서비스가 전용 데이터베이스를 독점 소유하고, 타 서비스는 오직 API/이벤트를 통해서만 데이터를 조회/수정하도록 격리하는 원칙.

</details>

- 정의/개념: 비즈니스 도메인 경계(Bounded Context)로 서비스를 분할하고 **독립 배포와 Database-per-Service**를 보장하는 분산 서비스 아키텍처
- 배경/필요성: 모놀리스는 기능 하나를 바꿔도 전체를 재빌드·재배포하고 확장도 전체 단위로만 가능한 비용을 치르므로, 비즈니스 기능 단위로 배포·확장 경계를 쪼갠 마이크로서비스를 두어 변경과 확장의 단위를 서비스 크기까지 낮출 필요

#### 한줄 요약
- 비즈니스 도메인 단위 분리와 DB 격리로 독립 배포, 독립 확장, 장애 격리를 실현한다.

## Ⅱ. 특징

<details><summary>용어 설명</summary>

- **장애 격리(Fault Isolation)**: 특정 서비스에 장애가 발생해도 서킷 브레이커와 비동기 큐를 통해 타 서비스로의 연쇄 장애(Cascading Failure)를 차단하는 능력.
- **폴리글랏(Polyglot)**: 서비스의 특성에 따라 서로 다른 언어(Java, Go, Python)와 서로 다른 DB(RDBMS, NoSQL, Cache)를 자유롭게 조합하는 방식.

</details>

- **Database-per-Service** 원칙을 통한 서비스 간 데이터 결합도 제거 및 독립적 CI/CD 파이프라인
- 서비스별 워크로드에 최적화된 언어/저장소를 채택하는 **폴리글랏(Polyglot) 아키텍처**
- 특정 서비스 오류가 전역으로 확산되지 않는 **장애 격리(Fault Isolation)** 및 개별 Scale-out

#### 한줄 요약
- 독립 배포와 폴리글랏 자유는 서비스 경계마다 네트워크 호출과 데이터 분산을 감수하고 얻은 것이므로, 자율성이 커질수록 일관성 보장은 약해진다.

## Ⅲ. 구조 및 구성요소

<details><summary>용어 설명</summary>

- **Service Mesh**: 서비스 간 통신(mTLS 보안, 트래픽 라우팅, 관측성)을 애플리케이션 코드 대신 사이드카 프록시(Envoy) 계층에서 전담 처리하는 인프라.

</details>

```text
[마이크로서비스(MSA) 분산 생태계 구조]
|-- API Gateway
|-- 서비스 디스커버리
|-- 독립 마이크로서비스
|-- 이벤트 브로커 (Kafka)
`-- 분산 추적 (Jaeger)
```

선의 의미: 계층 및 MSA 통신/관측성 인프라 파이프라인

| 구성요소 | 책임 |
|:---|:---|
| API Gateway | 클라이언트 단일 진입점, 인증/인가, 라우팅, 로드밸런싱 및 SSL 종단 |
| 서비스 디스커버리 | 컨테이너 오토스케일링에 따른 **동적 서비스 IP/Port 레지스트리** 관리 |
| 독립 마이크로서비스 | 도메인 비즈니스 로직 캡슐화 및 **전용 데이터베이스 독점 관리** |
| 이벤트 브로커 (Kafka) | 서비스 간 결합도를 없애는 비동기 메시지 발행/구독(Pub/Sub) |
| 분산 추적 (Jaeger) | Trace ID / Span ID 기반 서비스 간 호출 경로 및 레이턴시 병목 시각화 |

#### 한줄 요약
- API Gateway는 외부 진입을, Service Mesh는 내부 통신을 맡아 횡단 관심사를 서비스 코드 밖으로 밀어내며, 이벤트 브로커가 서비스 간 시간적 결합까지 끊는다.

## Ⅳ. 흐름도

<details><summary>용어 설명</summary>

- **Saga 패턴**: 분산 DB 환경에서 2PC 대신 각 서비스의 로컬 트랜잭션을 순차 실행하고, 실패 시 보상 트랜잭션(Compensating Transaction)으로 롤백하는 기법.

</details>

```text
클라이언트 주문 요청 인입 -> API Gateway 토큰 검증 및 라우팅
        │
   주문 서비스: 로컬 트랜잭션 실행 (주문 '생성 대기' 저장)
        │
   주문 서비스가 Kafka로 '주문 생성됨' 이벤트 발행
        │
   결제 서비스가 이벤트를 수신하여 로컬 결제 트랜잭션 수행
   ┌────┴───────────────────────────┐
[결제 승인 성공]                  [잔액 부족 등 결제 실패]
결제 서비스가 '결제 완료' 이벤트 발행  결제 서비스가 '결제 실패' 이벤트 발행
        │                                │
주문 서비스가 '주문 확정'으로 갱신    주문 서비스가 수신 후 '주문 취소' 보상 트랜잭션 실행
        │                                │
[최종 일관성(BASE) 달성 완료]       [데이터 정합성 원복 완료]
```

#### 한줄 요약
- 정상 완료와 Saga 보상은 같은 이벤트 경로를 정방향과 역방향으로 쓰므로, 보상을 설계하지 않은 서비스는 실패 시 되돌릴 수단 자체가 없다.

## Ⅴ. 종류 및 비교

<details><summary>용어 설명</summary>

- **분산 모놀리스(Distributed Monolith)**: MSA를 표방했으나 DB를 여전히 공유하거나 서비스 간 강한 동기 RPC 결합으로 모놀리스보다 못한 복잡도만 양산한 안티패턴.

</details>

| 비교 항목 | 모놀리식 아키텍처 (Monolith) | 마이크로서비스 아키텍처 (MSA) |
|:---|:---|:---|
| 배포 및 릴리즈 | **전체 시스템 전수 일괄 배포** | **서비스별 무중단 독립 배포 (CI/CD)** |
| 데이터베이스 | 단일 통합 DB (강력한 ACID 보장) | **Database-per-Service (최종 일관성)** |
| 장애 전파 | 단일 모듈 OOM 시 **전체 시스템 다운** | 서킷 브레이커로 **해당 기능만 장애 격리** |
| 확장성 (Scale) | 전체 애플리케이션 단위 스케일아웃 | **부하가 높은 특정 서비스만 선별 스케일아웃** |
| 운영 복잡도 | 낮음 (단일 모니터링) | **매우 높음 (DevOps, K8s, 분산 추적 필수)** |

#### 한줄 요약
- 모놀리스는 단순성과 ACID 정합성이 우수하며, MSA는 대규모 조직의 빠른 릴리즈와 독립 확장이 우수하다.

## Ⅵ. 실무 고려사항 및 대책

<details><summary>용어 설명</summary>

- **서킷 브레이커(Circuit Breaker)**: 호출 대상 서비스의 장애율이 임계치를 초과하면 호출을 즉시 차단(Open)하고 Fallback 응답을 반환하여 시스템을 보호하는 패턴.

</details>

| 문제 | 대책 | 효과 |
|:---|:---|:---|
| 분산 DB 환경에서 서비스 간 데이터 정합성 파괴 | **Saga 패턴(Choreography / Orchestration)** 적용 | 원자적 2PC 없이 최종 일관성(BASE) 보장 |
| 특정 서비스 지연이 전체 호출 체인으로 전파 | **Resilience4j 기반 서킷 브레이커 및 타임아웃** 강제 | 연쇄 장애 차단 및 Fallback 가용성 유지 |
| 수십 개 서비스 간 호출 경로 파악 불가 | **OpenTelemetry 기반 분산 추적(Distributed Tracing)** | 마이크로초 단위 병목 구간 즉시 식별 |
| DB 공유로 인한 MSA 안티패턴(분산 모놀리스) | **DDD(도메인 주도 설계) Bounded Context 기반 DB 완전 분리** | 서비스 간 진정한 독립 배포성 확보 |

#### 한줄 요약
- 마이크로서비스는 배포 독립성을 네트워크 지연·분산 일관성·관측 비용으로 사므로, Saga로 일관성 수준을 낮추고 서킷 브레이커와 분산 추적으로 그 대가를 관리 가능한 범위에 묶는다.

## Ⅶ. 결론

- 도메인 분리는 **MSA**, 분산 정합성은 **Saga** 선택

#### 한줄 요약
- MSA는 조직의 비즈니스 민첩성과 시스템 확장성을 극대화하지만, 분산 복잡도를 감당할 수 있는 DevOps 및 관측성 인프라가 전제되어야 한다.
