## Ⅰ. 개요

<details><summary>용어 설명</summary>

- **MSA (Microservice Architecture)**: 통짜배기(Monolithic) 시스템을 도메인(주문, 결제, 배송) 단위로 잘근잘근 쪼개서, 각각 독립적으로 배포하고 스케일링할 수 있게 만든 현대 백엔드 아키텍처의 끝판왕이다.
- **서비스별 DB (Database-per-Service)**: "내 데이터는 나만 건드려!" 라며 다른 서비스가 절대 내 DB에 직접 접근하지 못하게 막고, 오직 API로만 통신하게 만드는 빡센 데이터 격리 원칙이다.
- **분해 (Decomposition)**: 무식하게 큰 모놀리스 덩어리를 DDD(도메인 주도 설계)의 '바운디드 컨텍스트' 같은 메스를 써서 예쁘고 독립적인 마이크로서비스로 발라내는 수술 기법이다.

</details>

- 정의: 거대 앱을 독립 배포 가능한 작은 서비스로 찢어발기고, 각각 전용 DB를 들려주는 분산 아키텍처인 **MSA (Microservice Architecture)**
- 배경: 덩치가 커지면 오타 하나 고치고 전체 서버를 껐다 켜야(재배포) 해서 **수정 파급과 확장의 한계**에 부딪히기 때문

#### 한줄 요약

- 앱과 DB를 업무별로 잘근잘근 찢어서, 남 눈치 안 보고 내 것만 배포(확장)하는 아키텍처다.

## Ⅱ. 특징

<details><summary>용어 설명</summary>

- **장애 격리 (Fault Isolation)**: '추천' 서비스 서버가 뻗어도 '결제' 서비스는 멀쩡히 돌아가게 막아서, 배가 구멍 나도 다른 칸은 물이 안 차게 막는 격벽 시스템이다.
- **폴리글랏 퍼시스턴스 (Polyglot Persistence)**: 어떤 서비스는 RDBMS, 어떤 건 NoSQL, 어떤 건 Redis를 쓰는 등 각자 취향과 성능에 맞춰 기술과 DB를 뷔페처럼 골라 쓰는 자유도이다.

</details>

- **Database-per-Service** 원칙으로 DB를 철저히 찢고, 빌드/배포(CI/CD)도 독립시킴.
- 결제는 Java+Oracle, 추천은 Python+MongoDB를 쓰는 **폴리글랏 아키텍처(Polyglot)**가 가능해짐.
- 타 서비스가 죽어도 나한테 불똥 안 튀는 **장애 격리(Fault Isolation)**와 개별 스케일아웃(Scale-out)을 지원함.

#### 한줄 요약

- DB 찢기, 언어(스택) 맘대로 고르기, 장애 전파 틀어막기가 MSA의 3대 무기다.

## Ⅲ. 구조 및 구성요소

<details><summary>용어 설명</summary>

- **API 게이트웨이 (API Gateway)**: 클라이언트(앱/웹)가 수십 개의 마이크로서비스 주소를 외울 필요 없이, 앞단에서 문지기 역할을 하며 라우팅, 인증, 트래픽 제한(Rate Limiting)을 짬처리하는 엣지 서버이다.
- **서비스 디스커버리 (Service Discovery)**: 인스턴스가 떴다 죽었다 하며 IP가 미친 듯이 바뀌는 MSA 환경에서, "결제 서버 지금 몇 번 IP에 살아있냐?"를 실시간으로 찾아주는 전화번호부(Eureka 등)이다.

</details>

```text
[ MSA 통신 및 분산 십자포화 아키텍처 ]

           [ 클라이언트 (Web/App) ]
                     │
             [ API 게이트웨이 ]
             (인증, 라우팅, Rate Limit)
              /             \
[ 서비스 디스커버리 ]       [ 분산 추적 / 로그 ]
(지금 서버 어디 있음?)      (어디서 병목 터짐?)
             │               │
     ┌───────┴───────────────┴────────┐
[ 주문 서비스 ] ──(Kafka 비동기)──▶ [ 결제 서비스 ]
  (주문 DB)                          (결제 DB)
```

| 구성요소 | 책임 |
|:---|:---|
| **API 게이트웨이** | 외부 요청을 한 놈이 받아서 인증 까고, 트래픽 막고, 길(라우팅) 안내해 주는 문지기 |
| **서비스 디스커버리** | IP가 시시각각 변하는 컨테이너 환경에서 각 서비스 위치를 찾아주는 내비게이션 |
| 독립된 마이크로서비스 | 주문, 결제 등 비즈니스 단위로 완전히 찢어져서 자기 DB만 챙기는 서버들 |
| **이벤트 브로커 (Kafka)** | "결제 끝났어 배송 시작해!" 비동기 찌라시(이벤트)를 날리는 우체국 |
| 관측 플랫폼 | 수십 개 서버를 거치는 요청을 추적(Distributed Tracing)해서 범인 찾는 CCTV |

#### 단답 요약

- 문지기(게이트웨이), 전화번호부(디스커버리), 배달부(카프카)가 찢어진 서버들을 엮어준다.

## Ⅳ. 흐름도

<details><summary>용어 설명</summary>

- **분산 트랜잭션 (Distributed Transaction)**: 모놀리스에선 DB가 하나라 `COMMIT` 한방이면 끝났지만, MSA에선 DB가 찢어져 있어서 "주문은 성공했는데 결제가 실패하면 주문 DB를 어떻게 롤백할래?"라는 지옥 같은 문제이다.

</details>

```text
[ MSA 분산 트랜잭션(Saga) 십자포화 흐름 ]
┌──────────────────────────────┐
│ 1. API Gateway 요청 진입     │
│ (클라이언트가 주문 버튼 클릭)│
└──────────────┬───────────────┘
               ▼
┌──────────────────────────────┐
│ 2. 주문 서비스 로컬 트랜잭션 │
│ (주문 DB에 '결제 대기' 저장) │
└──────────────┬───────────────┘
               ▼ (이벤트 발행)
┌──────────────────────────────┐
│ 3. 결제 서비스 비동기 호출   │
│ (결제 DB에서 돈 차감 시도)   │
└───────┬───────────────┬──────┘
        │(성공)         │(잔액 부족으로 실패)
        ▼               ▼
┌────────────────┐ ┌────────────────────────┐
│ 4-1. 최종 완료 │ │ 4-2. Saga 보상 트랜잭션│
│ (주문 '완료'됨)│ │ (주문 DB 다시 '취소'함)│
└────────────────┘ └────────────────────────┘
```

### 동작 원리

1. 요청 진입: 게이트웨이가 토큰 까보고 주문 서버로 라우팅 쏴줌.
2. 로컬 트랜잭션 1: 주문 서버가 자기 DB에 데이터 넣고 Kafka에 이벤트를 던짐.
3. 로컬 트랜잭션 2: 결제 서버가 이벤트 주워 먹고 결제 DB에 트랜잭션 침.
4. 분산 트랜잭션(Saga) 마무리: 성공하면 해피엔딩, 터지면 지나온 길을 거꾸로 취소하는 보상 트랜잭션으로 수습함.

#### 한줄 요약

- DB가 찢어져서 한방 롤백이 안 되니, 이벤트로 넘기고 터지면 역순으로 취소(보상)한다.

## Ⅴ. 종류 및 비교

<details><summary>용어 설명</summary>

- **분산 모놀리스 (Distributed Monolith)**: 서버만 찢어놨지 DB는 하나를 같이 쓰거나, API로 너무 끈적하게 동기 호출을 해대서 하나 죽으면 다 같이 죽는 'MSA 조무사'이자 최악의 아키텍처이다.

</details>

| 비교 항목 | **Monolithic (통짜)** | **MSA (마이크로서비스)** |
|:---|:---|:---|
| 배포 단위 | 전쟁 나가듯 한 달에 한 번 전체 껐다 켬 | 버튼 하나만 고치면 그 서비스만 **1분 만에 독립 배포** |
| 데이터베이스 | 마스터 DB 하나에 모든 테이블 때려 박음 | **개별 독립 DB (Service-per-DB)** 유지 |
| 트랜잭션 처리 | RDBMS가 보장해 주는 강한 일관성 (ACID) | 코드로 똥 닦아야 하는 **사가 패턴 (최종 일관성)** |
| 복잡도 쏠림 | 서버 안에 스파게티 코드가 쌓임 (코드 복잡도) | 서버는 예쁜데 통신망이 스파게티 됨 (인프라 복잡도) |

#### 한줄 요약

- MSA는 배포와 확장엔 무적인 대신, 통신망(인프라)과 트랜잭션 헬파티를 감수해야 한다.

## Ⅵ. 실무 고려사항 및 대책

<details><summary>용어 설명</summary>

- **사가 패턴 (Saga Pattern)**: 찢어진 DB들 사이에서 2PC 같은 구시대 유물을 버리고, 트랜잭션을 쪼개서 순차적으로 밟다가 터지면 역순으로 '취소(보상) 트랜잭션'을 때려서 억지로 수습하는 MSA 트랜잭션 국룰이다.

</details>

| 문제 | 대책 | 효과 |
|:---|:---|:---|
| DB가 찢어져서 주문은 됐는데 결제가 실패해도 롤백이 안 됨 | **Saga Pattern(사가 패턴)**을 도입해 보상(취소) 로직 짜서 덮음 | 구르다 보면 언젠간 데이터가 맞는 **최종 일관성** 획득 |
| 추천 서버 하나 뻗었다고 전체 앱이 뒤짐 | 타임아웃 걸고 **Circuit Breaker(서킷 브레이커)**로 연결 끊음 | 장애가 옆 서버로 번지는 걸 차단 (**Fault Isolation**) |
| 5개 서버 거쳐 에러 터졌는데 어디서 터졌는지 로그를 못 찾음 | Zipkin 같은 **분산 추적(Distributed Tracing)** 툴로 Trace ID 묶음 | 요청이 지나간 모든 서버 경로와 딜레이 병목을 1초 컷 추적 |

#### 한줄 요약

- 트랜잭션은 Saga로 수습하고, 장애는 서킷 브레이커로 끊어내며, 로그는 분산 추적으로 묶어라.

## Ⅶ. 결론

<details><summary>용어 설명</summary>

- **MSA 도입 판정 기준(MSA Adoption Criteria)**: 조직에 돈과 인력이 넘치는지, DevOps(K8s) 역량이 되는지, 비즈니스가 찢어발겨질 만큼 큰지 각 재서 MSA를 할지 말지 정하는 잣대이다.

</details>

- **MSA 도입 판정 기준** 원칙에 따라, 독립 배포 이익이 인프라 비용을 씹어먹을 땐 **MSA**, 운영 쪼렙이거나 도메인 경계가 애매하면 **Modulith(모듈러 모놀리스)** 채택 기조 확립함

#### 한줄 요약

- MSA는 만병통치약이 아니다. 조직 역량(K8s)과 도메인 사이즈가 받쳐줄 때만 써라.
