## Ⅰ. 개요

<details><summary>용어 설명</summary>

- **사가 패턴(Saga Pattern)**: MSA에서 DB가 찢어져 한방 커밋이 안 되니, 순서대로 로컬 커밋을 치다가 중간에 엎어지면 역순으로 환불(보상)을 때려서 수습하는 분산 트랜잭션 국룰이다.
- **보상 트랜잭션(Compensating Transaction)**: 이미 내 DB에 '성공'이라고 도장 찍어버린(Commit) 과거 데이터를 롤백할 수 없으니, 논리적으로 반대되는 행동(환불, 재고 복구)을 새로 쳐서 퉁치는 개념이다.
- **2PC(Two-Phase Commit)**: 옜날에 쓰던 무식한 분산 방식. 한 놈이라도 밍기적거리면 전체 DB에 락(Lock)을 걸어버려서 MSA 성능을 개박살 내는 적폐이다.

</details>

- 정의: 2PC 같은 구닥다리 락(Lock)을 버리고, 로컬 커밋의 릴레이와 실패 시 역순 **보상 트랜잭션**으로 최종 일관성을 맞추는 MSA 분산 트랜잭션 패턴인 **Saga Pattern**
- 배경: DB가 서비스별로 찢어지면 모놀리스 시절처럼 쿼리 한 줄로 **트랜잭션(ACID 원자성) 한방 롤백이 안 돼서** 고아 데이터가 생기기 때문

#### 한줄 요약

- DB가 찢어진 MSA 환경에서 성공하면 릴레이 커밋, 실패하면 역순 환불(보상)로 수습하는 패턴이다.

## Ⅱ. 특징

<details><summary>용어 설명</summary>

- **코레오그래피(Choreography)**: 중앙 통제 없이, 서비스들끼리 "나 주문받음!" 하고 허공에 카프카 이벤트 쏘면 옆에서 주워 먹고 결제 치는 자율적인 눈치 게임 방식이다.
- **오케스트레이션(Orchestration)**: 깐깐한 지휘자(Saga Orchestrator)가 한가운데 서서 "주문 팀 결제해!", "재고 팀 실패했네? 주문 팀 취소해!"라고 멱살 잡고 명령을 내리는 공산당식 중앙 통제 방식이다.

</details>

- DB 전체를 묶어버리는 2PC 전역 락을 찢어버리고, **로컬 커밋 + 보상 트랜잭션** 조합으로 타협을 봄.
- 알아서 눈치껏 던지는 **코레오그래피(Choreography)**와, 중앙에서 지시하는 **오케스트레이션(Orchestration)** 2가지 맛이 있음.
- 중간에 빵꾸난 데이터가 보일 수 있는 **격리성(Isolation) 부재**와 언젠간 맞는 **최종 일관성(Eventual Consistency)**을 감수해야 함.

#### 한줄 요약

- 락(Lock) 안 걸어서 빠르지만, 중간 짬뽕 상태가 노출되고 역순 보상(환불) 로직을 일일이 짜야 한다.

## Ⅲ. 구조 및 구성요소

<details><summary>용어 설명</summary>

- **사가 오케스트레이터(Saga Orchestrator)**: 오케스트레이션 방식에서 "지금 3단계(재고)까지 성공했고 4단계 대기 중임" 같은 진행 상태(State Machine)를 DB에 꼼꼼히 적어두고, 터지면 2단계, 1단계에 역순으로 명령을 내리는 중앙 통제탑이다.

</details>

```text
[ Saga Orchestration 십자포화 아키텍처 ]

                      [ 사가 상태 저장소 ]
                      (어디까지 진행됐는지 엑셀 기록)
                             │
       ┌─────────────────────┴─────────────────────┐
       │             [ 사가 오케스트레이터 ]       │
       ▼                 (흐름 중앙 통제)          ▼
[ 주문 서비스 ] ──(명령/응답)──▶ ◀──(명령/응답)── [ 결제 서비스 ]
  (주문 DB)                                       (결제 DB)
```

| 구성요소 | 책임 |
|:---|:---|
| **사가 오케스트레이터** | "주문 성공했으니 결제해라", "결제 터졌으니 주문 취소해라" 명령하는 중앙 지휘자 |
| **사가 상태 저장소** | 지휘자가 헷갈리지 않게 1단계 끝, 2단계 진행 중 같은 상태(State)를 엑셀에 적어둠 |
| 참여 서비스 (주문, 결제) | 지휘자 명령 떨어지면 내 DB에 로컬 커밋 치고, 취소하라면 취소(보상) 치는 행동대장 |
| 메시지 채널 (Kafka) | 지휘자와 행동대장 사이에서 명령(명령어)과 결과(이벤트)를 나르는 우체부 |

#### 한줄 요약

- 지휘자(오케스트레이터)가 상태를 적어가며 행동대장(서비스)에게 커밋/취소를 지시한다.

## Ⅳ. 흐름도

<details><summary>용어 설명</summary>

- **보상 흐름(Compensating Flow)**: 직진하다가 낭떠러지(실패)를 만나면, 왔던 길을 되돌아가며(결제 취소 $\to$ 주문 취소) 싸질러 놓은 데이터를 다시 치우는 뒤치다꺼리 흐름이다.

</details>

```text
[ Saga 보상 흐름(Compensating Flow) 십자포화 흐름 ]
[ 클라이언트 주문 요청 ]
        │
        ▼ 1. 정방향 1단계
   [ 주문 완료 ]
        │
        ▼ 2. 정방향 2단계
   [ 결제 승인 ]
        │
        ▼ 3. 정방향 3단계
   [ 재고 차감 시도 ]
        ├─ ⭕ 성공 ─▶ [ 사가 최종 완료 해피엔딩 ]
        └─ ❌ 실패 (재고 없음)
                │
                ▼ 4. 역방향 1단계 (보상)
        [ 결제 취소 (환불 펀치) ]
                │
                ▼ 5. 역방향 2단계 (보상)
        [ 주문 취소 (최종 정합성 수습 완료) ]
```

### 동작 원리

1. 정방향 1단계: 주문 서비스가 내 DB에 '주문 완료' 커밋 도장 찍음.
2. 정방향 2단계: 결제 서비스가 내 DB에 '결제 완료' 커밋 도장 찍음.
3. 정방향 3단계: 재고 서비스 갔더니 "물건 없는데요?" 하고 에러(실패) 뱉음.
4. 보상(역방향 1단계): 결제 서비스한테 "아까 받은 돈 다시 뱉어(환불)" 보상 명령 때림.
5. 보상(역방향 2단계): 주문 서비스한테 "방금 주문 무효 처리해" 하고 팩트 폭행하여 최종 수습함.

#### 한줄 요약

- 성공하면 쭉 밀고 나가고(로컬 커밋), 중간에 터지면 역순으로 되돌아가며 치운다(보상 트랜잭션).

## Ⅴ. 종류 및 비교

<details><summary>용어 설명</summary>

- **코레오그래피 vs 오케스트레이션(Choreography vs Orchestration)**: 2~3단계로 짧으면 이벤트 쏘고 튀는 자율형(코레오그래피)이 짱이고, 4단계 넘어가서 취소 로직이 그지 같아지면 무조건 지휘자(오케스트레이션)를 둬야 스파게티를 막는다는 비교이다.

</details>

| 비교 항목 | **Choreography** (눈치 게임/자율형) | **Orchestration** (중앙 통제형) |
|:---|:---|:---|
| 제어 방식 | 지휘자 없이 서비스끼리 **이벤트(Pub/Sub)** 던지고 자율 처리 | **중앙 통제탑(오케스트레이터)**이 멱살 잡음 |
| 시스템 결합도 | **완전 쌉느슨함** (옆 부서가 뭐 하는지 알 필요 없음) | 지휘자가 전 부서 로직을 다 알아야 해서 끈적함 |
| 스파게티 위험도 | 트랜잭션이 길어지면 이벤트가 핑퐁 튀어서 **디버깅 지옥** | 아무리 복잡해도 지휘자 DB 까보면 돼서 **추적 쌉가능** |
| 대표 툴 | Kafka, RabbitMQ | **Temporal**, AWS Step Functions |

#### 한줄 요약

- 짧고 굵은 건 코레오그래피로 자율로 돌리고, 길고 복잡한 건 오케스트레이터가 멱살 잡고 캐리한다.

## Ⅵ. 실무 고려사항 및 대책

<details><summary>용어 설명</summary>

- **격리성 부재(Lack of Isolation)**: 2단계 결제까지만 커밋됐는데, 다른 유저가 조회하면 "결제는 됐는데 재고는 그대로인" 기괴한 중간 짬뽕 상태(Dirty Read)가 대놓고 노출되는 사가의 치명적 약점이다.

</details>

| 문제 | 대책 | 효과 |
|:---|:---|:---|
| 덜 끝난 기괴한 중간 상태가 노출됨 (**격리성 부재**) | **시맨틱 락(Semantic Lock)**으로 DB에 `PENDING` 명시 | 덜 익은 데이터(Dirty Read) 못 읽게 접근 컷 |
| 취소(보상) 날렸는데 서버 뻗어서 환불 안 되고 증발 | 될 때까지 **무한 재시도(Retry)** 및 수동 큐(DLQ) 이송 | 어떻게든 끝까지 추적해서 보상 실패 리스크 박살 |
| 이벤트 2번 와서 돈 2번 빠짐 | **트랜잭셔널 아웃박스 + 멱등성(Idempotency)** 조합 | 재시도 폭격 맞아도 한 번만 처리되게 이중 방어 |

#### 한줄 요약

- 중간 상태 노출은 시맨틱 락으로 막고, 환불 씹히는 건 무한 재시도로 패며, 멱등성으로 2번 환불을 막아라.

## Ⅶ. 결론

<details><summary>용어 설명</summary>

- **분산 트랜잭션 선택 기준(Distributed Transaction Selection Criteria)**: 마이크로서비스 간에 데이터를 일치시킬 때, 2PC 락으로 묶을지 사가 패턴으로 환불 똥꼬쇼를 할지 결정하는 잣대이다.

</details>

- **분산 트랜잭션 선택 기준** 원칙에 따라, 무조건 0.1초 만에 씽크 맞아야 하면 성능 포기하고 **2PC**, 보상(환불) 가능하고 확장이 생명인 MSA에선 **Saga** 채택 기조 확립함

#### 한줄 요약

- 락 걸어서 다 같이 느려지는 2PC 뻘짓 말고, 실패하면 쿨하게 환불해 주는 Saga 패턴이 MSA의 국룰이다.
