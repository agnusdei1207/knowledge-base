## Ⅰ. 개요

<details><summary>용어 설명</summary>

- **APM (Application Performance Management)**: 사용자 요청 진입부터 분산 서비스, 소스코드 메서드, DB 쿼리, 인프라까지 전 구간의 성능과 병목을 실시간 모니터링하고 진단하는 체계.
- **Trace ID & Span**: 분산 환경에서 단일 트랜잭션을 식별하는 고유 ID(Trace ID)와 서비스별 세부 실행 단위(Span).

</details>

- 정의/개념: 사용자 요청부터 분산 서비스 호출, 내부 코드, DB 쿼리까지 **전 구간의 성능 지표와 분산 트레이스를 실시간 계측·진단하는 APM 관리 체계**
- 배경/필요성: 복잡한 마이크로서비스(MSA) 및 클라우드 환경에서 트랜잭션이 수십 개의 서비스와 DB를 거치며 실행됨에 따라, 특정 API 지연이나 오류 발생 시 각 서버의 로그를 개별 수작업으로 대조하느라 원인 규명이 지연되고 MTTR(평균 복구 시간)이 폭증하는 한계를 극복하기 위해, 비침투적 바이트코드 인스트루멘테이션(Instrumentation)과 OpenTelemetry 분산 추적(Trace ID/Span) 및 서비스 토폴로지 맵을 결합한 APM 체계를 도입하여 **전 구간 엔드투엔드 성능 가시화, 슬로우 쿼리/락 경합 코드 라인 레벨 즉각 특정 및 서비스 가용성 극대화**를 달성할 필요

#### 한줄 요약
- 바이트코드 인스트루멘테이션과 분산 추적을 통해 사용자 체감 지연부터 소스코드 라인 레벨까지 병목을 가시화한다.

## Ⅱ. 특징

<details><summary>용어 설명</summary>

- **Bytecode Instrumentation (바이트코드 계측)**: 소스코드 수정 없이 JVM 클래스 로딩 시점에 프로파일링 코드를 동적으로 삽입하여 메서드 수행 시간을 측정하는 기법.
- **RED Metrics**: Rate(요청률), Errors(오류율), Duration(응답 시간)의 3대 핵심 마이크로서비스 관측 지표.

</details>

- 소스코드 수정 없이 런타임에 동적으로 프로파일링 코드를 삽입하는 **바이트코드 계측(Instrumentation)**
- Trace ID와 Span을 통해 서비스 간 호출 경로와 지연시간을 연결하는 **엔드투엔드 분산 추적**
- 요청률(Rate), 오류율(Errors), 지연시간(Duration)을 종합 관측하는 **RED 메트릭 실시간 감시**

#### 한줄 요약
- 바이트코드 계측, 분산 추적, RED 메트릭 감시를 통해 장애 원인을 수 분 내에 규명한다.

## Ⅲ. 구조 및 구성요소

<details><summary>용어 설명</summary>

- **APM 4대 아키텍처**: Instrumentation Agent(신호 수집), Service Topology(의존성 맵), Analysis Engine(병목 분석), Alerting/Runbook(경보 및 런북).

</details>

```text
[APM 구성]
|-- 계측 에이전트
|-- 분산 추적기
|-- 서비스 토폴로지 맵
|-- 분석 엔진
`-- 경보 워크플로
```

선의 의미: 계층 및 에이전트가 바이트코드를 계측하여 수집한 신호를 분석 엔진이 상관 분석하고 토폴로지 맵에 시각화하여 경보를 전달하는 구조

| 구성요소 | 핵심 엔지니어링 책임 | 주요 특징 |
|:---|:---|:---|
| **계측 에이전트 (Agent)** | Java/Go 런타임에 삽입되어 **메서드 실행 시간, SQL 파라미터, 인프라 자원을 비침투적 수집** | Pinpoint Agent |
| **분산 추적기 (Tracing)** | 분산 트랜잭션 전 구간에 **Trace ID를 전파하여 서비스 간 지연 병목 구간을 1:1 매핑** | OpenTelemetry |
| **서비스 토폴로지 맵** | 마이크로서비스 간 **실시간 호출 의존성, 인바운드/아웃바운드 TPS, 에러율 시각화** | 실시간 의존성 맵 |
| **분석 엔진 (Analyzer)** | 정상 베이스라인과 실측 지표를 비교하여 **슬로우 쿼리, 락 경합, 스레드 병목 지점 진단** | 이상 징후 분석 |
| **경보 워크플로 (Alert)** | SLO 위반 시 **온콜 엔지니어에게 장애 원인 구간 및 복구 런북(Runbook) 즉시 전달** | MTTR 단축 |

#### 한줄 요약
- 에이전트가 코드 수정 없이 계측을, 추적기가 구간 연결을, 분석 엔진이 기준선 비교를 맡으므로 원인 규명이 담당자의 추론이 아니라 데이터 조회로 대체된다.

## Ⅳ. 흐름도

<details><summary>용어 설명</summary>

- **APM 장애 진단 5단계**: 관측 신호 수집 $\to$ 분산 추적 상관 분석 $\to$ 토폴로지 병목 식별 $\to$ 원인 코드 특정 및 런북 알람 $\to$ 튜닝 후 정상화 검증.

</details>

```text
서비스 운영 중 결제 API 지연 발생 (SLO 위반)
        │
   1. [관측 신호 수집] APM 에이전트가 트랜잭션별 Trace ID, 응답 시간(Duration), SQL 쿼리 수집
        │
   2. [분산 추적 상관 분석] 결제 요청(3.2초)의 Span 트리를 분석하여 주문 서비스 구간(2.8초) 특정
        │
   3. [토폴로지 병목 식별] 토폴로지 맵에서 주문 서비스 -> 결제 DB 간의 커넥션 풀 100% 포화 감지
        │
   4. [원인 코드 및 런북 전달] `select for update` 락 경합 메서드를 특정하고 당직자에게 런북 전달
        │
   5. [튜닝 및 회귀 검증] 트랜잭션 격리수준 완화 후 P99 응답시간이 150ms로 정상 회복됨을 실시간 확인
```

#### 한줄 요약
- 구간을 좁힌 뒤에야 코드 레벨 프로파일링이 값어치를 가지므로, 상관 분석을 건너뛰면 가장 비싼 계측을 가장 넓은 범위에 거는 낭비가 생긴다.

## Ⅴ. 종류 및 비교

<details><summary>용어 설명</summary>

- **RUM vs 합성 모니터링 vs 분산 추적**: 실사용자 체감 성능(RUM), 가상 시나리오 주기 점검(Synthetic), 백엔드 서비스 간 심층 분석(Distributed Tracing).

</details>

| 비교 항목 | 실사용자 모니터링 (RUM) | 합성 모니터링 (Synthetic) | 분산 추적 (Distributed Tracing) |
|:---|:---|:---|:---|
| 핵심 관측 대상 | **실제 사용자 브라우저/앱 단말 체감 지연**| **핵심 사용자 여정(로그인/결제) 가상 스크립트** | **백엔드 마이크로서비스 간 호출 및 DB 쿼리** |
| 장점 | 실제 고객의 지역/기기별 다양한 체감 측정 | 트래픽이 없는 심야에도 사전 장애 감지 | **서비스별 지연 병목과 에러 원인 코드 1:1 규명**|
| 한계 | 네트워크 편차 영향, 개인정보 마스킹 필요 | 실제 사용자의 복잡한 예외 행동 재현 한계 | 고트래픽 시 샘플링 누락 및 저장소 비용 |
| 최적 적용 사례 | 프론트엔드 성능 최적화, 모바일 앱 분석 | 24x7 서비스 가용성 SLA 사전 점검 | **마이크로서비스 MSA 트러블슈팅 전반** |

#### 한줄 요약
- 프론트 체감은 RUM, 사전 가용성 감시는 합성 모니터링, 백엔드 원인 분석은 분산 추적을 결합한다.

## Ⅵ. 실무 고려사항 및 대책

<details><summary>용어 설명</summary>

- **Tail-Based Sampling (꼬리 기반 샘플링)**: 모든 정상 요청을 다 저장하지 않고, 요청 완료 후 에러가 발생했거나 응답이 느린 트랜잭션만을 선별 저장하여 비용을 절감하는 기법.

</details>

| 문제 | 대책 | 효과 |
|:---|:---|:---|
| APM 에이전트의 과도한 프로파일링으로 인한 서버 CPU 성능 저하 | **프로파일링 주기 조정 및 `에이전트 CPU 사용률 3% 상한선` 강제** | 계측 오버헤드 극소화 |
| 고트래픽 서비스에서 전체 트레이스 저장 시 스토리지 비용 폭증 | **`Tail-Based Sampling` 적용으로 에러 및 P99 지연 트레이스만 선별 저장** | APM 저장소 비용 80% 절감 |
| 수집된 SQL 파라미터 및 트레이스에 개인정보(주민번호/카드) 노출 | **에이전트 단에서 정규식 기반 `개인정보(PII) 자동 마스킹` 강제** | 개인정보보호법 컴플라이언스 준수 |
| 지표 간 분절로 인해 대시보드와 로그를 따로 확인하는 비효율 | **Metrics, Logs, Traces를 Trace ID로 결합하는 `OpenTelemetry 통합`** | 장애 원인 분석 시간(MTTR) 70% 단축 |

#### 한줄 요약
- 네 대책은 관측을 위해 치르는 CPU·저장·개인정보 비용을 상한과 선별 저장으로 되사는 선택이며, 샘플링 비율을 낮출수록 비용과 함께 남는 장애 흔적도 줄어든다.

## Ⅶ. 결론

- 클라우드 네이티브 및 대규모 분산 시스템의 신뢰성과 SLA를 수호하는 **가장 핵심적인 풀스택 옵저버빌리티(Observability) 및 성능 관리 표준 인프라**로 정립되었으며, 실무 구축 시에는 **OpenTelemetry 기반 메트릭·로그·트레이스 3대 기둥 단일화, 바이트코드 비침투적 계측 오버헤드 3% 이하 통제, 스토리지 비용을 절감하는 Tail-Based Sampling, 수집 데이터 내 개인정보(PII) 자동 마스킹 및 실사용자 모니터링(RUM) 연계**를 결합하여 사용자 경험과 백엔드 안정성을 동시에 사수

#### 한줄 요약
- APM은 바이트코드 계측, 분산 추적, 서비스 토폴로지 맵을 통해 병목 구간과 결함 코드를 실시간으로 찾아내는 핵심 애플리케이션 성능 관리 기술이다.
