## Ⅰ. 개요

<details><summary>용어 설명</summary>

- **블랙박스 모의 침투(Black-Box Penetration Testing)**: 소스코드에 대한 사전 지식 없이 외부 공격자 관점에서 웹 애플리케이션의 엔드포인트에 페이로드를 전송하여 반응을 검증하는 방식.
- **액티브 스캐닝(Active Scanning)**: 취약점 유발 페이로드(SQL Injection, XSS, SSRF 등)를 실제 HTTP 요청에 주입하여 서버 응답 상태 및 에러 패턴을 분석하는 동적 진단 기법.

</details>

- 정의/개념: 구동 중인 웹 애플리케이션을 대상으로 **블랙박스 모의 침투 및 액티브 스캐닝(Active Scanning)**을 수행하여 런타임 보안 취약점과 환경 설정 오류를 탐지하는 보안 테스팅 기법
- 배경/필요성: 정적 분석(SAST)만으로는 탐지하기 어려운 **인프라/웹 서버 설정 오류 및 런타임 인증/인가 우회 결함 위험** 직면

#### 한줄 요약

- 실행 중인 애플리케이션에 외부 공격 시뮬레이션을 수행하여 실제 악용 가능한 런타임 보안 취약점을 검증

## Ⅱ. 특징

<details><summary>용어 설명</summary>

- **오탐 최소화(Low False Positive Rate)**: 실제 공격 페이로드 실행에 따른 서버 응답(데이터 유출, 500 에러, 응답 지연 등)을 기반으로 판정하여 오탐이 극히 적은 특성.
- **언어 독립성(Language Agnosticism)**: 백엔드 구현 언어(Java, Python, Go 등)와 무관하게 HTTP/S 통신 인터페이스만으로 보안성을 평가하는 특성.

</details>

- 소스코드 접근이 불필요한 **블랙박스(Black-Box) 기반 외부 공격자 관점 검증**
- 프로그래밍 언어 및 프레임워크에 구애받지 않는 **언어 독립적(Language Agnostic) 스캐닝**
- 실제 공격 성공 시 검출하므로 **오탐(False Positive) 극소화 및 실효적 보안 위협 입증**

#### 한줄 요약

- 소스코드 없이 언어 독립적으로 실제 공격을 시뮬레이션하여 매우 낮은 오탐률로 취약점을 증명

## Ⅲ. 구조 및 구성요소

<details><summary>용어 설명</summary>

- **스파이더/크롤러(Spider/Crawler)**: 대상 웹사이트의 모든 링크, 폼, REST API 엔드포인트를 자동으로 순회하여 공격 표면(Attack Surface)을 수집하는 엔진.

</details>

```text
[ DAST 동적 분석 아키텍처 구조도 ]

  [ 대상 웹/API 엔드포인트 ] ──► [ 스파이더 (URL/Form 탐색) ] ──► [ 공격 표면 목록 ]
                                                                      │
                                                                      ▼
  [ 인증 컨텍스트 (JWT/세션) ] ─────────────────────────► [ 페이로드 주입 엔진 ]
                                                                      │
                                                                      ▼
  [ 취약점 증명 리포트 ] ◄── [ 응답 분석기 (오라클 검증) ] ◄── [ 액티브/패시브 스캐너 ]
```

선의 의미: 공격 대상 URL 탐색, 인증 세션 연계, 공격 페이로드 주입 및 서버 응답 분석 파이프라인.

| 구성요소 | 책임 |
|:---|:---|
| 스파이더 (Spider/Crawler) | 사이트 내 링크, HTML 폼, REST API를 탐색하여 **공격 표면(Attack Surface) 도출** |
| 인증 관리자 (Auth Context) | 로그인 폼 및 OAuth/JWT 토큰을 갱신하여 **인증 세션 유지 및 인가 영역 진입** |
| 페이로드 주입기 (Fuzzer) | OWASP Top 10 기반 SQLi, XSS, 명령 주입 등 **변이 페이로드 전송** |
| 응답 분석기 (Analyzer) | HTTP 상태 코드, 응답 헤더, 시간 지연을 분석하여 **취약점 발현 여부 판정** |

#### 한줄 요약

- 크롤러가 공격 표면을 수집하고 인증 세션을 유지하며 페이로드를 주입하여 응답을 분석

## Ⅳ. 흐름도

<details><summary>용어 설명</summary>

- **패시브 vs 액티브 스캔(Passive vs Active Scan)**: 정상 트래픽을 가로채 보안 헤더 부재를 확인하는 비침습적 분석(Passive)과 악의적 페이로드를 직접 전송하는 침습적 분석(Active).

</details>

```text
[ DAST 진단 및 취약점 증명 파이프라인 ]

 ┌────────────────────────────────────────┐
 │ 1. 타겟 설정: 대상 URL 및 인증 구성   │
 └───────────────────┬────────────────────┘
                     │
                     ▼
 ┌────────────────────────────────────────┐
 │ 2. 공격 표면 탐색: 크롤링 및 파라미터  │
 └───────────────────┬────────────────────┘
                     │
                     ▼
 ┌────────────────────────────────────────┐
 │ 3. 페이로드 주입: OWASP 취약점 공격    │
 └───────────────────┬────────────────────┘
                     │
                     ▼
 ┌────────────────────────────────────────┐
 │ 4. 응답 판정: 실제 악용 가능성 검증   │
 └────────────────────────────────────────┘
```

### 동작 원리

1. 타겟 설정: 진단 대상 스테이징 도메인 및 API 스펙(OpenAPI/Swagger), 로그인 인증 자격증명을 구성.
2. 공격 표면 탐색: 크롤러가 웹 UI와 API 경로를 순회하며 입력 파라미터 목록을 추출.
3. 페이로드 주입: 패시브 스캔으로 보안 헤더를 점검한 후 액티브 스캔으로 조작된 페이로드를 주입.
4. 응답 판정: 서버 에러, 스크립트 실행, DB 응답 패턴을 분석하여 취약점 증빙(PoC) 리포트를 생성.

#### 한줄 요약

- 타겟 설정 $\to$ 표면 탐색 $\to$ 페이로드 주입 $\to$ 응답 판정의 4단계로 실제 보안 취약점을 검증

## Ⅴ. 종류 및 비교

<details><summary>용어 설명</summary>

- **IAST(Interactive Application Security Testing)**: 애플리케이션 내부에 에이전트를 삽입하여 DAST의 외부 공격과 SAST의 코드 실행 경로 추적을 결합한 하이브리드 기법.

</details>

| 구분 | 정적 분석 (SAST) | 동적 분석 (DAST) | 대화형 분석 (IAST) |
|:---|:---|:---|:---|
| **적용 기준** | 소스코드 빌드 단계 | 스테이징 배포 후 런타임 단계 | 테스트 자동화/QA 통합 단계 |
| **핵심 특징** | **코드 전수 검사 및 라인 번호 식별** | **실제 침투 가능성 및 환경설정 검증** | **외부 공격 시 내부 코드 실행 경로 추적** |
| **한계** | 런타임 환경설정 취약점 미탐 | 코드 내부의 정확한 수정 라인 파악 불가 | 에이전트 탑재에 따른 성능 오버헤드 |

#### 한줄 요약

- SAST는 코드 내부를, DAST는 외부 실행 환경을, IAST는 내부 에이전트로 두 장점을 융합하여 분석

## Ⅵ. 실무 고려사항 및 대책

<details><summary>용어 설명</summary>

- **데이터 오염 방지(Data Pollution Prevention)**: DAST의 공격 페이로드 주입으로 인해 데이터베이스 내 실제 데이터가 변조되거나 삭제되는 것을 방지하는 격리 대책.

</details>

| 문제 | 대책 | 효과 |
|:---|:---|:---|
| 운영 DB에 테스트 데이터 오염 및 서비스 장애 유발 | **운영 환경이 아닌 데이터 격리된 Staging 환경에서 진단 수행** | 실제 운영 데이터 손상 방지 및 무중단 유지 |
| SPA(Single Page Application) 동적 렌더링 크롤링 누락 | **헤드리스 브라우저(Puppeteer, Playwright) 기반 크롤러 연동** | JavaScript 렌더링 후 DOM 트리 및 API 공격 표면 확보 |
| 전체 스캔 시간 장기화로 인한 배포 파이프라인 지연 | **핵심 API 대상 Baseline 스캔과 주기적 야간 전수 스캔 분리** | CI/CD 파이프라인 속도 유지 및 정밀 점검 병행 |

#### 한줄 요약

- 스테이징 격리 환경 사용, 헤드리스 크롤러 도입, Baseline/전수 스캔 분리로 안전성과 효율성을 확보

## Ⅶ. 결론

<details><summary>용어 설명</summary>

- **보안 검증 상호 보완(Complementary Security Testing)**: SAST(개발 초기), SCA(오픈소스), DAST(런타임)를 상호 유기적으로 결합하여 다층 방어 체계를 수립하는 전략.

</details>

- **DAST**는 실제 공격자의 시각에서 시스템의 보안성을 검증하는 필수 절차이며, SAST 및 IAST와의 유기적 연계를 통해 빈틈없는 SSDLC 파이프라인을 완성

#### 한줄 요약

- 외부 모의 침투를 통한 실효적 검증으로 SAST의 한계를 보완하고 애플리케이션의 런타임 보안성을 보증
