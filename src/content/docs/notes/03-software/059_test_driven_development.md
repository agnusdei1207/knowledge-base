## Ⅰ. 개요

<details><summary>용어 설명</summary>

- **테스트 주도 개발(Test-Driven Development, TDD)**: 코드를 다 짜놓고 "테스트 어떻게 하지?" 고민하는 게 아니라, 에러 나는 테스트 코드를 먼저 짜놓고 그걸 통과시키려고 실제 코드를 끼워 맞추는 개발 방법론이다.
- **레드-그린-리팩터(Red-Green-Refactor)**: 1단계: 실패하는(Red) 테스트 작성 $\to$ 2단계: 일단 성공(Green)하게 만듦 $\to$ 3단계: 코드를 예쁘게 다듬는(Refactor) TDD의 무한 피드백 루프이다.
- **실행 가능한 명세(Executable Specification)**: 워드에 적어둔 가짜 기획서 말고, 테스트 코드 자체가 "이 앱은 이렇게 돌아가야 함!"을 증명하는 진짜 명세서 역할을 한다는 의미이다.

</details>

- 정의: "실패하는 테스트 작성(Red) $\to$ 통과하는 최소 구현(Green) $\to$ 코드 리팩터링(Refactor)"의 짧은 반복 주기로 피드백을 극대화하는 개발 방법론인 **Test-Driven Development**
- 배경: 나중에 몰아서 테스트하려니 **귀찮아서 빼먹고, 스파게티 코드라 테스트 자체를 못 짜는 참사**를 막기 위함

#### 한줄 요약

- 코드 다 짜고 채점받지 말고, 아예 정답지(테스트)부터 적어놓고 코드를 거기에 끼워 맞추자는 거다.

## Ⅱ. 특징

<details><summary>용어 설명</summary>

- **최소 구현(Minimal Code)**: 완벽한 로직을 짜려고 머리 싸매지 말고, `return 2;`처럼 하드코딩을 해서라도 초록불(Green)부터 보고 시작하라는 게으름뱅이 마인드(Baby Steps)이다.
- **작동하는 깔끔한 코드(Clean Code That Works)**: 버그 없이 돌아가는(Works) 동시에, 다른 사람이 봐도 쾌적한 구조(Clean Code)를 리팩터링으로 만들어내는 TDD의 목표이다.

</details>

- **Red $\to$ Green $\to$ Refactor** 3대 핵심 마이크로 서클.
- 테스트 코드가 아키텍처 설계를 이끄는 **Test-First Development**.
- 코딩이 끝남과 동시에 **Executable Specification** 및 든든한 방탄조끼(**Regression Test Suite**) 자동 구축됨.

#### 한줄 요약

- 일단 깨지게 만들고(Red), 무식하게 고치고(Green), 이쁘게 다듬는(Refactor) 무한 반복이다.

## Ⅲ. 구조 및 구성요소

<details><summary>용어 설명</summary>

- **FIRST 원칙(FIRST Principle)**: TDD 테스트는 1초 만에 끝나고(Fast), 독립적이며(Independent), 반복 가능하고(Repeatable), 자가 검증하며(Self-Validating), 제때 짜야 한다(Timely)는 십계명이다.

</details>

```text
[ TDD 십자포화 아키텍처 ]

[ 요구사항 포스트잇 (To-do) ] ───▶ [ 1. 실패하는 테스트 코드 (Red) ]
                                            │
                                            ▼
 [ 3. 리팩터링 (Refactor) ] ◀── [ 2. 무식하게 통과시키기 (Green) ]
       │ (무한 반복 시)
       ▼
 [ 든든한 회귀 테스트 봇 완성 ]
```

| 구성요소 | 팩트 폭행 책임 |
|:---|:---|
| **테스트 목록 (To-do)** | 오늘 구현해야 할 요구사항이나 예외 케이스들을 뇌에서 끄집어내 적어둔 칠판 |
| **테스트 코드 (Red)** | "나 이거 만들 거임" 하고 선언했지만, 아직 코드가 없어서 시뻘겋게 에러 뿜는 코드 |
| **대상 코드 (Green)** | 뻘건 에러를 끄기 위해, 하드코딩을 하든 어떻게든 억지로 통과만 시킨 걸레짝 코드 |
| **리팩터링 (Refactor)** | 테스트가 통과(초록불)했으니 안심하고 걸레짝 코드를 클린 코드로 다듬는 청소 작업 |
| **회귀 테스트 봇** | 이 짓거리를 수백 번 반복하다 보면 어느새 쌓인 코드들이 날 지켜주는 든든한 방패가 됨 |

#### 한줄 요약

- 목표를 칠판에 적고 $\to$ 빨간불 띄우고 $\to$ 초록불 띄우고 $\to$ 코드 청소하고 $\to$ 방패를 쌓는다.

## Ⅳ. 흐름도

<details><summary>용어 설명</summary>

- **베이비 스텝(Baby Steps)**: 한 번에 거대한 기능을 다 만들려다 망치지 말고, 아기 걸음마처럼 아주 작은 단위의 목표 하나만 잡고 찔끔찔끔 전진하라는 전략이다.

</details>

```text
[ TDD 레드-그린-리팩터 십자포화 흐름 ]
┌──────────────────────────────┐
│ 테스트 목록 (To-do) 작성     │
└──────────────┬───────────────┘
               ▼
┌──────────────────────────────┐
│ 1. Red (실패 시험 작성)      │
│ (에러 나는 빨간불 보기)      │
└──────────────┬───────────────┘
               ▼
┌──────────────────────────────┐
│ 2. Green (최소 구현 통과)    │
│ (하드코딩해서 초록불 만들기) │
└──────────────┬───────────────┘
               ▼
┌──────────────────────────────┐
│ 3. Refactor (구조 개선)      │
│ (초록불 떴으니 맘놓고 청소)  │
└──────────────┬───────────────┘
               ▼
┌──────────────────────────────┐
│ 4. 회귀 시험 무한 반복       │
│ (다음 To-do로 넘어가서 반복) │
└──────────────────────────────┘
```

### 동작 원리

1. Red: To-do에서 기능 하나 꺼내서 컴파일 에러가 나든 말든 테스트 코드부터 갈김.
2. Green: 테스트를 통과시킬 목적으로, 묻지도 따지지도 않고 제일 무식한 코드를 짬.
3. Refactor: 동작 확인했으니 중복 없애고 디자인 패턴 섞으면서 클린 코드로 조각함.
4. 반복 누적: 이 루프를 수백 번 반복하면 어느새 튼튼한 방탄조끼(회귀 테스트)가 완성됨.

#### 한줄 요약

- 빨간불(Red) $\to$ 초록불(Green) $\to$ 코드 세탁(Refactor)의 쫄깃한 3박자 리듬이다.

## Ⅴ. 종류 및 비교

<details><summary>용어 설명</summary>

- **테스트 주도(Test-First) vs 테스트 나중(Test-Last)**: 테스트 먼저 짜면 코드가 테스트하기 좋게 설계(의존성 분리)되지만, 다 짜놓고 나중에 억지로 테스트 끼워 맞추려면 떡진 스파게티라 불가능하다.

</details>

| 비교 항목 | **Traditional (Test-Last 꼰대)** | **TDD (Test-First MZ)** |
|:---|:---|:---|
| 작성 시점 | 기능 다 만들고 배포 직전에 헐레벌떡 | **IDE 켜자마자 테스트 코드부터 냅다 꽂음** |
| 의존성 설계 | 다 엮어놔서 나중에 격리 테스트 불가 | **첨부터 테스트하기 좋게 격리해서 만듦** |
| 리팩터링 깡 | 쫄려서 레거시 코드 한 줄도 못 건드림 | **수백 개 테스트가 지켜주니까 맘대로 갈아엎음** |
| 문서화 | 구석에 박혀있는 3년 전 워드 문서 | **IDE에서 Run 누르면 돌아가는 진짜 명세서** |

#### 한줄 요약

- 코딩 끝나고 테스트 짜려면 안 짜게 되니, 테스트부터 짜서 설계 자체를 깔끔하게 강제하는 거다.

## Ⅵ. 실무 고려사항 및 대책

<details><summary>용어 설명</summary>

- **TDD 병목 현상(TDD Bottleneck)**: TDD 처음 도입하면 평소보다 타자 치는 양이 배로 늘어서 "속도 너무 느린데?" 징징대지만, 버그 찾는 디버깅 시간을 없애줘서 장기적으론 무조건 이득이다.

</details>

| 문제 | 대책 | 효과 |
|:---|:---|:---|
| TDD 처음 하는데 진도 안 나가서 속 터짐 | 단순 화면 말고 **핵심 비즈니스(돈 계산) 로직**에만 선별 적용 | TDD 피로도 줄이고 진짜 중요한 로직만 방어함 |
| Green 띄우려다 완벽한 설계 하느라 시간 날림 | 하드코딩으로 일단 때우는 **Baby Steps(아기 걸음마)** 강제 | TDD의 생명인 짧고 쫄깃한 '리듬' 회복 |
| DB 연결 때문에 단위 테스트 작성이 헬파티임 | **Mockito** 같은 테스트 대역(Mock) 꽂아서 격리시킴 | 통신 기다릴 필요 없이 0.1초 만에 테스트 끝남 |

#### 한줄 요약

- 너무 집착하지 말고 제일 돈 되는 로직에만, 아기 걸음마(Baby Steps)처럼 조금씩 도입해라.

## Ⅶ. 결론

<details><summary>용어 설명</summary>

- **TDD 도입 수립 기준(TDD Adoption Standards)**: 버그 나면 돈 날아가는 복잡한 도메인지, 팀원들이 Mock 객체 쓸 줄 아는지 각 재서 TDD 강제 여부를 정하는 잣대이다.

</details>

- **TDD 도입 수립 기준** 원칙에 따라, 돈이 오가는 핵심 도메인은 무조건 **TDD 강제**, 한 번 쓰고 버릴 UI 스크립트는 **테스트 후행** 채택 기조 확립함

#### 한줄 요약

- TDD는 코딩 속도를 늦추는 게 아니라, 버그 잡느라 야근하는 시간을 아껴주는 가장 훌륭한 투자다.
