## Ⅰ. 개요

<details>
<summary>핵심 용어</summary>

- **테스트 주도 개발(Test-Driven Development, TDD)**: 실패 테스트를 먼저 작성하고 최소 구현과 리팩터링을 반복하는 개발 방식이다.
- **단위 테스트(Unit Test)**: 함수•클래스 등 작은 코드 단위를 격리해 빠르게 검증하는 테스트이다.

</details>

- 정의/개념: 실패 **단위 테스트**를 먼저 작성하고 최소 구현•리팩터링을 반복하는 **테스트 주도 개발** 방식이다.
- 배경/필요성: 구현 후 시험에서 발생하는 요구 누락과 결함 발견 지연을 줄인다.

#### 한줄 요약

- 실패 시험과 최소 구현 및 리팩터링을 반복하는 **테스트 주도 개발**이 핵심이다.

## Ⅱ. 특징

<details>
<summary>핵심 용어</summary>

- **실행 가능한 명세(Executable Specification)**: 요구 동작을 자동 실행하고 통과 여부를 판정할 수 있게 표현한 테스트이다.
- **회귀 테스트(Regression Test)**: 변경 후 기존 동작의 손상 여부를 다시 확인하는 테스트이다.
- **리팩터링(Refactoring)**: 외부 동작을 바꾸지 않고 코드 내부 구조를 개선하는 활동이다.

</details>

- 테스트 우선으로 **실행 가능한 명세**를 작성한다.
- 작은 **단위 테스트**로 결함을 빠르게 피드백한다.
- **회귀 테스트**의 보호 아래 **리팩터링**을 지속한다.

#### 한줄 요약

- **실행 가능한 명세**, **회귀 테스트**, **리팩터링**이 핵심이다.

## Ⅲ. 구조 및 구성요소

<details>
<summary>핵심 용어</summary>

- **테스트 목록(Test List)**: 구현할 작은 동작과 우선순위를 관리하는 작업 목록이다.
- **최소 구현(Minimal Implementation)**: 현재 실패 테스트를 통과하는 데 필요한 만큼만 작성한 코드이다.
- **테스트 실행기(Test Runner)**: 테스트를 자동 실행하고 실패•통과 결과를 즉시 제공하는 도구이다.
- **테스트 코드(Test Code)**: 입력과 기대 동작을 실행 가능한 명세로 표현한 코드이다.
- **대상 코드(Code Under Test)**: 테스트가 요구한 동작을 구현하는 코드이다.
- **회귀 테스트 모음(Regression Suite)**: 기존 동작을 보호하도록 누적해 변경마다 다시 실행하는 자동 테스트 집합이다.

</details>

```text
     [테스트 목록]
           |
     [테스트 코드]
           |
[테스트 실행기] --- [대상 코드]
           |
  [회귀 테스트 모음]
```

선의 의미: 테스트 실행기를 중심으로 테스트 목록, 테스트 코드, 대상 코드와 누적 회귀 테스트 모음이 결합되는 정적 TDD 시험 구조를 뜻한다.

| 구성요소 | 책임 |
|:---|:---|
| 테스트 목록 | 구현할 작은 동작과 우선순위 관리 |
| 테스트 코드 | 입력과 기대 동작을 **실행 가능한 명세**로 표현 |
| 대상 코드 | 현재 시험을 위한 **최소 구현** |
| 테스트 실행기 | 실패와 통과를 즉시 판정 |
| 회귀 테스트 모음 | 기존 동작의 자동 재검증 |

#### 한줄 요약

- **테스트 목록**, **테스트 코드**, **대상 코드**, **테스트 실행기**, **회귀 테스트 모음**의 연결 구조가 핵심이다.

## Ⅳ. 흐름도

<details>
<summary>핵심 용어</summary>

- **레드-그린-리팩터(Red-Green-Refactor)**: 실패 확인, 최소 구현으로 통과, 동작을 유지한 구조 개선의 반복 주기이다.
- **실패 테스트 작성**: 다음 작은 요구 동작을 입력과 기대 결과로 먼저 명세하는 동작이다.
- **레드 확인(Red Check)**: 구현 전 테스트가 의도한 미구현 이유로 실패하는지 확인하는 동작이다.
- **최소 구현 수행**: 현재 실패 테스트를 통과하는 데 필요한 만큼만 코드를 작성하는 동작이다.
- **그린 확인(Green Check)**: 신규 테스트와 기존 회귀 테스트가 모두 통과하는지 확인하는 동작이다.
- **리팩터링 수행**: 모든 테스트를 통과한 상태에서 외부 동작을 유지하며 내부 구조를 개선하는 동작이다.

</details>

```text
+------------------------------------------+
| 반복 범위: 테스트 목록의 다음 작은 동작  |
|                                          |
| [1. 실패 테스트 작성]                   |
|           |                              |
|           v                              |
| [2. 레드 확인] -- 다른 실패 -> [테스트 수정 후 재확인]|
|           | 의도한 실패                           |
|           v                                       |
| [3. 최소 구현 수행]                               |
|           |                              |
|           v                              |
| [4. 그린 확인] -- 실패 -> [구현 수정 후 재확인]   |
|           | 전체 통과                             |
|           v                                       |
| [5. 리팩터링 수행] -- 회귀 실패 -> [변경 복원]    |
|           | 동작 보존                             |
|           +---------------------------------------+
+------------------------------------------+
```

### 동작 원리

1. **실패 테스트 작성**: 다음 작은 동작을 명세한다.
2. **레드 확인**: 구현 전 의도한 이유의 실패를 판정한다.
3. **최소 구현 수행**: 현재 테스트를 통과할 코드를 작성한다.
4. **그린 확인**: 신규•기존 회귀 테스트 통과 판정한다.
5. **리팩터링 수행**: 외부 동작을 유지하며 구조를 개선한다.

> 요약: **레드 확인**, **최소 구현 수행**, **그린 확인**, **리팩터링 수행**을 작은 동작마다 반복한다.

#### 한줄 요약

- **레드-그린-리팩터**의 반복 주기가 핵심이다.

## Ⅴ. 종류 및 비교

<details>
<summary>핵심 용어</summary>

- **결정적 로직(Deterministic Logic)**: 같은 입력과 상태에서 항상 같은 결과를 내는 로직이다.
- **탐색적 구현(Exploratory Implementation)**: 요구나 해법의 불확실성을 줄이기 위해 먼저 만들어 보며 학습하는 구현 방식이다.

</details>

| 개발 방식 | TDD | 구현 후 테스트 |
|:---|:---|:---|
| 적용 기준 | 명확한 **결정적 로직** | **탐색적 구현**과 외부 연동 중심 |
| 핵심 특징 | 테스트가 설계•구현을 선도 | 구현 뒤 검증 항목 도출 |
| 한계 | 테스트 결합과 과도한 단위화 | 결함 발견 지연과 수정 범위 확대 |

> 요약: 결정적 단위 로직은 TDD, 탐색•연동은 보완 시험 활용이 핵심이다.

#### 한줄 요약

- **결정적 로직**에는 **테스트 주도 개발**, 불확실한 해법에는 **탐색적 구현**이 적합하다.

## Ⅵ. 실무 고려사항 및 대책

<details>
<summary>핵심 용어</summary>

- **취약한 테스트(Brittle Test)**: 외부 동작은 같아도 내부 구현 변경만으로 자주 실패하는 테스트이다.
- **목 객체(Mock Object)**: 예상 호출•인자•횟수 등 객체 간 상호작용을 검증하는 테스트 더블이다.
- **스텁(Stub)**: 시험에 필요한 고정 응답을 반환하도록 만든 테스트 더블이다.
- **테스트 가능성(Testability)**: 대상을 격리•제어•관찰해 자동 시험하기 쉬운 정도이다.
- **의도한 실패 이유(Expected Failure Reason)**: 미구현 요구 때문에 테스트가 실패한 원인이다.
- **실패 메시지(Failure Message)**: 테스트 실패 원인을 보여 주는 진단 정보이다.
- **공개 동작(Public Behavior)**: 호출자에게 보이는 입력과 출력 계약이다.
- **리팩터링 내성(Refactoring Resilience)**: 내부 구조 변경에도 불필요하게 실패하지 않는 성질이다.
- **예외 경로(Exception Path)**: 외부 오류•잘못된 입력•시간 초과처럼 정상 처리와 다른 실패 흐름이다.
- **의존성 분리(Dependency Isolation)**: 외부 협력 대상을 교체 가능하게 나누는 설계이다.
- **관찰 가능 출력(Observable Output)**: 결과와 상태 변화를 시험에 드러내는 설계이다.

</details>

| 문제 | 대책 | 효과 |
|:---|:---|:---|
| 실패 원인을 확인하지 않고 구현을 시작함 | **의도한 실패 이유**와 **실패 메시지** 확인 | 잘못된 **레드 확인** 방지 |
| 내부 호출에 결합된 **취약한 테스트**가 누적됨 | **공개 동작** 검증과 내부 호출 검증 축소 | **리팩터링 내성** 확보 |
| 모든 협력 객체를 **테스트 더블**과 **목 객체**로 대체함 | 경계만 **목 객체**와 **스텁**으로 두고 통합 시험 병행 | 실제 협력 동작 검증 |
| 외부 오류 응답의 불확실한 재현 한계 | 경계에 **스텁**의 고정 응답 적용 | **예외 경로** 재현 |
| 대형 객체 격리•제어의 복잡도 증가 | **의존성 분리**와 **관찰 가능 출력** 설계 | **테스트 가능성** 향상 |
| **그린 확인** 뒤 리팩터링을 생략해 중복이 누적됨 | **리팩터링 수행** | 중복과 복잡도 감소 |

#### 한줄 요약

- **공개 동작**, **리팩터링 내성**, **테스트 가능성** 중심의 시험 설계가 핵심이다.

## Ⅶ. 결론

<details>
<summary>핵심 용어</summary>

- **격리 가능한 규칙(Isolatable Rule)**: 외부 시스템 없이 입력과 결과를 독립적으로 검증할 수 있는 업무 로직이다.
- **통합 시험(Integration Test)**: 실제 시스템 경계와 협력 대상 사이의 계약과 상호작용을 검증하는 시험이다.
- **TDD 적용 기준**: 규칙의 결정성•격리 가능성과 요구의 명확성을 평가해 테스트 우선 개발 여부를 정하는 기준이다.

</details>

- **TDD 적용 기준**을 충족하는 **격리 가능한 규칙**에는 **테스트 주도 개발**, 탐색•외부 연동에는 구현 후 **통합 시험**을 선택한다.

#### 한줄 요약

- 규칙의 결정성과 격리 가능성에 따른 **TDD 적용 기준**이 핵심이다.
