## Ⅰ. 개요

<details><summary>용어 설명</summary>

- **비용 기반 옵티마이저(Cost-Based Optimizer, CBO)**: 테이블 통계, 카디널리티, 인덱스 상태를 바탕으로 각 실행 경로의 CPU 및 디스크 I/O 비용을 계산하여 최적 경로를 도출하는 엔진.
- **카디널리티 추정 오류 및 풀스캔(Cardinality Estimation Error & Full Scan)**: 통계 노후화로 인해 실제 데이터양과 다른 잘못된 실행 계획이 선택되어 발생하는 심각한 슬로우 쿼리 병목.

</details>

- 정의/개념: 데이터베이스 옵티마이저가 SQL 질의를 가장 효율적으로 실행하기 위해 **스캔 방식, 조인 알고리즘, 연산 순서를 결정한 물리적 실행 트리** 명세서
- 배경/필요성: 통계 정보 노후화 및 부정확한 카디널리티(Cardinality) 추정으로 인한 **비효율 풀스캔(ALL), 임시 테이블 생성 및 쿼리 병목 위험** 직면

#### 한줄 요약

- CBO 비용 계산과 EXPLAIN 실행 계획 분석을 통해 병목 구간을 진단하고 인덱스 및 쿼리를 최적화

## Ⅱ. 특징

<details><summary>용어 설명</summary>

- **접근 방식 계층(Access Type Hierarchy)**: `const > eq_ref > ref > range > index > ALL(Full Scan)` 순으로 접근 효율이 결정되는 성능 지표.
- **Extra 주요 지표**: `Using index`(커버링 인덱스), `Using filesort`(디스크 정렬 오버헤드), `Using temporary`(임시 테이블 생성 오버헤드).

</details>

- 테이블 통계 기반으로 정량적 CPU/I/O 비용을 계산하는 **비용 기반 최적화(CBO)**
- 파싱, 쿼리 재작성, 경로 탐색, 코드 생성을 거치는 **정형화된 4단계 최적화 파이프라인**
- `EXPLAIN / EXPLAIN ANALYZE`를 통한 **예측 카디널리티와 실제 실행 시간(Actual Time) 대조** #### 한줄 요약

- 통계 기반 비용 산출과 실행 계획 검증을 통해 가장 빠른 데이터 접근 경로를 도출

## Ⅲ. 구조 및 구성요소

<details><summary>용어 설명</summary>

- **MySQL EXPLAIN 필드**: id(연산 순서), select_type(쿼리 유형), table(대상 테이블), type(접근 방식), rows(예상 행 수), Extra(추가 최적화 정보).

</details>

```text
[ MySQL EXPLAIN 실행 계획 트리 구조도 ]

 ┌────────────────────────────────────────────────────────────────────────┐
 │                   MySQL EXPLAIN Query Execution Plan                   │
 ├───────┬─────────────┬───────────┬────────┬────────┬────────────────────┤
 │ id    │ select_type │ table     │ type   │ rows   │ Extra              │
 ├───────┼─────────────┼───────────┼────────┼────────┼────────────────────┤
 │ 1     │ SIMPLE      │ orders    │ ref    │ 150    │ Using index        │
 │ 1     │ SIMPLE      │ users     │ eq_ref │ 1      │ NULL               │
 └───────┴─────────────┴───────────┴────────┴────────┴────────────────────┘
```

선의 의미: `orders` 테이블을 인덱스로 먼저 스캔(ref)한 후 `users` 테이블과 PK 조인(eq_ref)을 수행하는 연산 계층.

| 구성요소 | 책임 |
|:---|:---|
| 접근 방식 (type) | `const, ref, range, ALL` 등 **테이블 블록에 접근하는 스캔 경로 정의** |
| 예상 행 수 (rows) | 옵티마이저가 통계를 기반으로 예측한 **스캔 대상 카디널리티(Cardinality)** |
| 부가 정보 (Extra) | `Using index, Using temporary, Using filesort` 등 **정렬/임시테이블 발생 여부 표시** |
| 조인 방식 (Join Type) | 데이터 스케일에 따라 **Nested Loop, Hash Join, Sort Merge Join 알고리즘 선택** |

#### 한줄 요약

- 접근 방식, 예상 행 수, 조인 알고리즘, 부가 정보로 실행 계획의 효율성을 정량 평가

## Ⅳ. 흐름도

<details><summary>용어 설명</summary>

- **쿼리 재작성(Query Rewrite)**: 서브쿼리 불내포화(Unnesting), 뷰 펴기(View Merging)를 통해 옵티마이저가 최적화하기 쉬운 표준 관계대수식으로 변환하는 절차.

</details>

```text
[ 옵티마이저 4단계 쿼리 최적화 파이프라인 ]

 ┌────────────────────────────────────────┐
 │ 1. 구문 및 의미 분석 (Parsing & Lexing)│
 └───────────────────┬────────────────────┘
                     │
                     ▼
 ┌────────────────────────────────────────┐
 │ 2. 동등 질의 재작성 (Query Rewrite)   │
 └───────────────────┬────────────────────┘
                     │
                     ▼
 ┌────────────────────────────────────────┐
 │ 3. 통계 기반 후보 경로 비용 계산 (CBO) │
 └───────────────────┬────────────────────┘
                     │
                     ▼
 ┌────────────────────────────────────────┐
 │ 4. 최저 비용 물리 실행 계획 생성 및 수행│
 └────────────────────────────────────────┘
```

### 동작 원리

1. 구문 분석: SQL 문법의 유효성을 검증하고 참조된 테이블 및 컬럼 권한을 파싱.
2. 동등 질의 재작성: 복잡한 서브쿼리를 조인으로 변환하거나 불필요한 조건절을 제거하여 표준 대수식으로 변환.
3. CBO 비용 계산: 테이블 크기, 인덱스 높이, 데이터 분포(Histogram)를 바탕으로 후보 실행 경로들의 I/O 비용을 계산.
4. 실행 계획 확정: 가장 비용이 낮은 물리적 실행 트리를 생성하여 쿼리 실행 엔진에 전달.

#### 한줄 요약

- 구문 분석 $\to$ 쿼리 재작성 $\to$ CBO 비용 계산 $\to$ 물리 실행 계획 확정의 4단계 절차

## Ⅴ. 종류 및 비교

<details><summary>용어 설명</summary>

- **RBO vs CBO**: 정해진 15가지 우선순위 규칙에만 의존하던 규칙 기반(RBO)과 실제 데이터 통계 비용을 동적으로 계산하는 비용 기반(CBO).

</details>

| 구분 | RBO (규칙 기반 옵티마이저) | CBO (비용 기반 옵티마이저) |
|:---|:---|:---|
| **적용 기준** | 과거 레거시 DBMS 환경 | 현대 주요 상용/오픈소스 관계형 DBMS 표준 |
| **핵심 특징** | **고정된 우선순위 규칙(15대 Rule)에 따라 정적 결정** | **주기적 `ANALYZE` 통계 기반 CPU/I/O 비용 계산** |
| **한계** | 데이터 규모 및 분포 변화를 반영하지 못함 | 통계 정보 노후화 시 잘못된 비효율 경로 선택 가능 |

#### 한줄 요약

- RBO는 고정 규칙에 의존하나 CBO는 데이터 통계를 바탕으로 최적의 비용 경로를 동적으로 산출

## Ⅵ. 실무 고려사항 및 대책

<details><summary>용어 설명</summary>

- **옵티마이저 힌트(Optimizer Hint)**: 옵티마이저가 통계 오류 등으로 비효율적인 계획을 선택할 때 특정 인덱스나 조인 방식을 강제하는 주석 지시자.

</details>

| 문제 | 대책 | 효과 |
|:---|:---|:---|
| 통계 정보 노후화로 인한 비효율 Full Table Scan(ALL) 선택 | **정기적인 `ANALYZE TABLE` 실행 및 자동 통계 수집 스케줄링** | CBO 카디널리티 산출 정확도 유지 |
| `Using filesort`, `Using temporary` 발생으로 메모리 고갈 | **ORDER BY/GROUP BY 순서에 맞춘 복합 인덱스 설계 및 커버링 적용** | 디스크 I/O 소멸 및 쿼리 처리 속도 향상 |
| 통계 보정 후에도 부적합한 조인 순서(Join Order) 강행 | **`STRAIGHT_JOIN` 또는 Optimizer Hint(`/*+ INDEX() */`) 제한적 사용** | 실행 계획 안정성 확보 |

#### 한줄 요약

- 통계 정보 최신화, 복합 인덱스로 정렬 제거, 필요시 힌트를 적용하여 실행 계획을 최적화

## Ⅶ. 결론

<details><summary>용어 설명</summary>

- **EXPLAIN ANALYZE**: 쿼리를 실제로 실행하여 예측된 카디널리티(rows)와 실제 처리 행 수(actual rows) 및 실행 시간을 단계별로 출력하는 분석 도구.

</details>

- **쿼리 실행 계획 최적화** 기반 데이터베이스 성능을 극대화하는 핵심 분석 기술이며, `EXPLAIN ANALYZE`를 활용한 정밀 진단과 통계 최신화, 적절한 인덱스 설계를 통해 최고 수준의 쿼리 처리량을 달성해야 함

#### 한줄 요약

- CBO 원리를 이해하고 실행 계획 분석을 통해 병목을 진단하여 고성능 쿼리 환경을 완성
