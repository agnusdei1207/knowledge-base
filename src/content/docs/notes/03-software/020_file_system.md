## Ⅰ. 개요

<details><summary>용어 설명</summary>

- **파일 시스템(File System)**: 0과 1의 쓰레기 더미(물리 디스크)에 파일 이름, 확장자, 폴더 구조를 부여해서 인간이 알아먹고 저장하게 해주는 OS의 문서 정리 아키텍처이다.
- **가상 파일 시스템(Virtual File System, VFS)**: 밑에 깔린 파일 시스템이 FAT이든 NTFS든 알 바 없이, 프로그램들한테 똑같은 입출력 버튼(open, read, write)만 눌러서 통일되게 쓰게 해주는 추상화 레이어이다.

</details>

- 정의: 하드디스크 블록 덩어리에 이름표(메타데이터)를 붙여 구조화하고, 전원 나가도 데이터 안 날아가게 강력히 관리하는 **파일 시스템**
- 배경: 그냥 하드디스크 깡통(원시 블록)에 데이터만 냅다 부으면, 이름도 없고 파일이 어디 위치해 있는지도 몰라서 **데이터 보존과 검색**이 불가능하기 때문

#### 한줄 요약

- 디스크 쓰레기 더미에 파일 이름과 폴더 구조를 부여하고, 전원이 뽑혀도 데이터가 꼬이지 않게 장부를 관리하는 시스템이다.

## Ⅱ. 특징

<details><summary>용어 설명</summary>

- **아이노드(Inode)**: 리눅스/유닉스에서 파일의 진짜 이름 빼고 권한, 소유자, 크기, 진짜 디스크 위치를 싹 다 적어둔 영혼(메타데이터) 블록이다.
- **마스터 파일 테이블(MFT)**: 윈도우(NTFS)에서 파일과 디렉터리의 모든 족보와 위치를 단위로 쪼개서 관리하는 절대적인 데이터베이스이다.
- **쓰기 시 복사(Copy-on-Write, COW)**: 파일 덮어쓸 때 원래 있던 자리에 쓰면 뻑날까 봐, 빈자리에 먼저 새 글을 쓰고 연결선만 쏙 바꿔치기하는 무결성(스냅샷) 깡패 기술이다.

</details>

- 앱과 실제 디스크 사이에서 방패막이가 되어주는 **가상 파일 시스템(VFS)**.
- 메타데이터를 어디에 어떻게 적어둘 거냐에 따라 **아이노드(리눅스)**, **MFT(윈도우)** 등 뼈대가 갈림.
- 갑자기 전원 뽑혔을 때 파일 뻑나는 걸 막으려고 **저널링(Journaling)** 이나 **COW** 같은 복구술을 박아넣음.

#### 한줄 요약

- VFS로 공통 입출력을 제공하고, OS별로 고유 장부(Inode, MFT)와 복구술(저널링, COW)을 쓴다.

## Ⅲ. 구조 및 구성요소

<details><summary>용어 설명</summary>

- **익스텐트(Extent)**: 10GB짜리 영화 파일 위치를 4KB 단위로 장부에 수백만 줄 적기 빡세니까, "시작 번호부터 10만 개 연속!"이라고 쿨하게 한 줄로 압축해 버리는 할당 기술이다.

</details>

```text
[ 파일 시스템 처리 십자포화 아키텍처 ]
           [ 애플리케이션 ]
         (파일 좀 열고 써줘!)
                  │
       [ 가상 파일 시스템(VFS) ]
   (알았어 공통 인터페이스로 보내줄게)
                  │
        ┌─────────┴─────────┐
        ▼                   ▼
 [ 파일 메타데이터 ]    [ 블록 할당 관리자 ]
 (이름/권한 까봄)     (디스크 빈칸 찾아서 할당)
        │                   │
        └─────────┬─────────┘
                  ▼
           [ 일관성 관리자 ]
   (전원 뽑혀도 안 죽게 저널링/COW 세팅)
                  │
                  ▼
         [ 물리 블록 디바이스 ]
```

| 구성요소 | 책임 |
|:---|:---|
| 애플리케이션 | "파일 저장해 줘" 하고 VFS에 OS 시스템 콜(open, write)을 찌르는 고객 |
| **가상 파일 시스템** | 밑에 깔린 종류 상관없이 똑같은 얼굴로 고객 응대하는 추상화 안내데스크 |
| 파일 메타데이터 | 파일 이름부터 크기, 권한까지 족보를 관리하는 명부 (**Inode, MFT**) |
| 블록 할당 관리자 | 디스크에서 텅 빈 공간 찾아서 낭비 없이 빈틈없이 할당하는 공간 최적화 기법 (**Extent**) |
| 일관성 관리자 | 쓰다가 뻑나도 복구할 수 있게 기록(저널) 남기거나 **COW** 쳐주는 무결성 수호자 |

#### 한줄 요약

- 앱이 VFS를 찌르면, 메타데이터를 까보고, 블록을 빈자리에 쑤셔 넣고, 일관성 기록을 남긴다.

## Ⅳ. 흐름도

<details><summary>용어 설명</summary>

- **에프싱크(fsync)**: 메모리 캐시에서 깔짝거리던 파일 수정 사항을, 디스크(SSD/HDD)까지 강제로 강력히 쓰게 만들어서 데이터 증발을 막는 안전핀 명령어이다.

</details>

```text
[ 파일 쓰기 일관성 확보 십자포화 흐름 ]
┌──────────────────────────────┐
│ 1. VFS 거쳐서 경로/권한 컷   │
└──────────────┬───────────────┘
               ▼
┌──────────────────────────────┐
│ 2. 디스크 여유 블록 할당     │
└──────────────┬───────────────┘
               ▼
┌──────────────────────────────┐
│ 3. 일관성 복구 모드 선택     │
└───────┬───────────────┬──────┘
        │(기록 남김)    │(새 자리 쓰기)
        ▼               ▼
  [ 저널링 방식 ]    [ COW 방식 ]
        │               │
        └───────┬───────┘
                ▼
┌──────────────────────────────┐
│ 4. 데이터 쓰기 및 장부 갱신  │
│ (fsync()로 디스크 확정)      │
└──────────────────────────────┘
```

### 동작 원리

1. 경로 및 권한 컷: 앱이 VFS 찌르면 권한(Permission) 있는지 입구 컷부터 함.
2. 블록 할당: 저장할 파일 크기만큼 디스크에서 빈자리(Extent)를 영혼까지 끌어모아 잡아줌.
3. 일관성 모드 가동: 전원 차단 대비해서 저널(장부)에 쓸지, 빈자리에 새로 쓸지(COW) 각을 잼.
4. 데이터 기록: 진짜 데이터를 디스크 물리 블록에 집중 배치.
5. 장부 갱신: "나 여기 썼음" 하고 Inode나 메타데이터 포인터를 갱신(**Commit**)해서 파일을 영속화함.

#### 한줄 요약

- 권한 컷 $\to$ 빈칸 확보 $\to$ 저널/COW 모드 켜고 디스크에 꽂아버리는 게 쓰기 흐름이다.

## Ⅴ. 종류 및 비교

<details><summary>용어 설명</summary>

- **공간 공유(Space Sharing)**: APFS 기법으로, 파티션 용량을 미리 쪼개놓지 않고 한 디스크 안의 여러 볼륨이 뷔페처럼 남는 용량을 맘대로 섞어 쓰는 유연성 끝판왕 기술이다.

</details>

| 비교 항목 | **저널링 파일 시스템** (ext4, NTFS) | **COW 파일 시스템** (APFS, ZFS, Btrfs) |
|:---|:---|:---|
| 파일 덮어쓰기 | 원래 있던 자리를 그대로 밀어버리는 **인플레이스(In-Place)** 방식 | 빈자리에 새 글 쓰고 포인터만 쓱 바꾸는 **아웃오브플레이스(Out-of-Place)** |
| 복구/스냅샷 | 장부(Log) 뒤져서 롤백해야 돼서 스냅샷 뜨려면 추가 똥꼬쇼가 필요함 | 블록 포인터 복사만 하면 끝나서 **초당 수천 개 스냅샷**이 가능함 |
| 단편화 방어 | 빈칸 찾아 넣는 최적화(Extent) 알고리즘이 강력히 캐리해야 함 | 덮어쓸 때마다 새 자리를 파서 계속 파편화되므로 가비지 컬렉션이 필수임 |
| 최고존엄 플랫폼 | 리눅스(ext4) 서버 깡성능, 윈도우(NTFS) 대중성 원탑 | 애플(APFS), 솔라리스(ZFS) 급의 엔터프라이즈 데이터 백업 및 관리 끝판왕 |

#### 한줄 요약

- 덮어쓰기 깡성능은 ext4/NTFS, 스냅샷과 백업은 COW 기반의 APFS/ZFS가 짱이다.

## Ⅵ. 실무 고려사항 및 대책

<details><summary>용어 설명</summary>

- **직접 입출력(O_DIRECT)**: OS가 메모리 캐시질하는 거 못 믿겠으니까 다 쌩까고, 데이터베이스가 직접 디스크랑 다이렉트로 쇼부 쳐서 딜레이를 씹어 먹는 상남자 모드이다.
- **트림(TRIM)**: 파일 지울 때 껍데기만 지우지 않고 "이 블록 진짜 비웠으니까 딴 거 써도 돼"라고 SSD한테 귓속말 쳐줘서 SSD 수명과 속도를 떡상시키는 SATA/NVMe 명령어이다.

</details>

| 문제 | 대책 | 효과 |
|:---|:---|:---|
| 파일 쓰다가 전원 뽑히면 메타데이터 장부 꼬여서 하드디스크 날아감 | **저널링(Journaling)** 으로 장부 먼저 쓰고 **fsync()** 로 강력히 밀어 넣음 | 전원 뽑혀도 장부 보고 롤백/복구해서 파일 증발 철통 방어 |
| SSD는 덮어쓰기가 안 돼서 쓰레기 쌓이면 속도 심각히 저하되고 수명 갉아먹음 | 지울 때 OS가 SSD한테 텅 비었다고 알려주는 **TRIM** 명령어 주기적 때림 | 잉여 블록을 선제적으로 확보해서 쓰기 증폭(WAF) 박살 냄 |
| DB 쓰는데 OS가 메모리 캐시질해서 버퍼 두 번 타고 성능 깎아먹음 | 캐시 생까고 하드디스크로 직접 꽂아버리는 **직접 I/O(O_DIRECT)** 갈김 | 이중 버퍼링 낭비 싹 다 죽이고 DB 깡성능 극대화 |

#### 한줄 요약

- 전원 뽑힘은 저널링+fsync, SSD 찌꺼기는 TRIM, DB 이중 버퍼링은 O_DIRECT로 부순다.

## Ⅶ. 결론

<details><summary>용어 설명</summary>

- **파일 시스템 선택 기준(File System Selection Criteria)**: OS가 뭔지, 스냅샷이 필요한지, SSD인지 깡통 HDD인지를 따져서 뼈대를 고르는 잣대이다.

</details>

- **파일 시스템 선택 기준** 원칙에 따라, 리눅스 서버 깡성능은 **ext4**, 윈도우는 **NTFS**, 애플 생태계는 **APFS**, 이리저리 굴리는 USB는 **exFAT** 채택 기조 확립함

#### 한줄 요약

- 리눅스는 ext4, 윈도우는 NTFS, 맥은 APFS, 굴러다니는 USB는 exFAT를 꽂아라.
