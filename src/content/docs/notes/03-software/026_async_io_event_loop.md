## Ⅰ. 개요

<details><summary>용어 설명</summary>

- **다중화 통지(epoll / kqueue)**: 수만 개의 파일 디스크립터(소켓) 상태 변화를 $O(1)$의 이벤트 기반으로 감지하여 통지하는 커널 I/O 멀티플렉싱 API.
- **C10K 한계 및 자원 고갈(C10K & Thread Exhaustion)**: 1:1 스레드 풀 구조에서 10,000개 이상의 동시 연결 발생 시 메모리 부족 및 스케줄링 오버헤드로 서버가 다운되는 문제.

</details>

- 정의/개념: I/O 완료 대기 없이 제어권을 반환하고 OS 커널의 **다중화 통지(epoll/kqueue)** 를 단일 스레드가 순환 디스패치하는 리액터 패턴 비동기 실행 구조
- 배경/필요성: 연결당 1:1 스레드 모델의 C10K 동시 접속 한계 및 블로킹 I/O 대기로 인한 **스레드 자원 고갈과 컨텍스트 전환 오버헤드** 직면

#### 한줄 요약

- 단일 스레드 이벤트 루프가 논블로킹 I/O·OS 이벤트 감시로 수만 개의 동시 연결을 처리하는 고동시성 아키텍처

## Ⅱ. 특징

<details><summary>용어 설명</summary>

- **논블로킹 I/O(Non-blocking I/O)**: I/O 요청 시 데이터 미준비 상태에서도 스레드를 블로킹하지 않고 즉시 반환하여 다른 작업을 계속 수행하는 I/O 방식.
- **리액터 패턴(Reactor Pattern)**: 이벤트 루프가 이벤트를 감지하여 등록된 핸들러에 분배하는 비동기 이벤트 기반 설계 패턴.

</details>

- 대규모 연결에도 스레드 수를 고정하고 **논블로킹 I/O + epoll/kqueue** 조합으로 대응
- **리액터 패턴** 기반 이벤트 루프가 짧은 이벤트를 처리하고 장기 작업은 워커 풀에 위임
- 이벤트 루프 스레드 블로킹 방지가 전체 처리량의 핵심 제약

#### 한줄 요약

- OS 이벤트 감시기와 리액터 패턴으로 단일 스레드가 수만 개의 논블로킹 I/O를 순환 처리

## Ⅲ. 구조 및 구성요소

<details><summary>용어 설명</summary>

- **epoll / kqueue / io_uring**: 리눅스·BSD·최신 리눅스의 고성능 I/O 이벤트 통지 인터페이스로, select 방식 대비 O(1) 복잡도로 대규모 파일 디스크립터 감시 가능.
- **워커 스레드 풀(Worker Thread Pool)**: 이벤트 루프에서 CPU 바운드·블로킹 작업을 오프로드하여 이벤트 루프 블로킹을 방지하는 백그라운드 스레드 집합.

</details>

```text
[ 비동기 이벤트 루프 구조 (Reactor) ]
소켓·파일 I/O 등록
   │
OS 이벤트 감시기 (epoll / kqueue / io_uring)
└─ 완료 이벤트 감지 → 이벤트 큐 큐잉
이벤트 루프 (단일 스레드, 무한 순환)
├─ 이벤트 큐에서 이벤트 추출
├─ 콜백 핸들러 실행 (짧은 작업)
└─ CPU 바운드·블로킹 작업 → 워커 스레드 풀 위임
워커 스레드 풀 (CPU 바운드 작업 처리)
└─ 완료 시 결과를 이벤트 큐에 반환
```

선의 의미: 가지(`├─`, `└─`)는 이벤트 루프의 이벤트 처리·워커 위임 분기 관계

| 구성요소 | 책임 |
|:---|:---|
| I/O 등록 인터페이스 | 감시 대상 파일 디스크립터와 완료 통지 요청을 OS에 등록 |
| **OS 이벤트 감시기** | **epoll** 기반 완료 이벤트 효율적 감지 및 이벤트 큐 전달 |
| 이벤트 큐 | 감지된 완료 이벤트가 콜백 실행을 대기하는 선입선출 큐 |
| **이벤트 루프** | 단일 스레드로 이벤트 큐를 순환 처리하며 콜백 핸들러 실행 |
| 워커 스레드 풀 | CPU 바운드·블로킹 작업을 이벤트 루프로부터 격리 처리 |

#### 한줄 요약

- OS 이벤트 감시기가 완료 이벤트를 큐에 전달하면 이벤트 루프가 콜백을 실행하고 무거운 작업은 워커 풀에 위임

## Ⅳ. 흐름도

<details><summary>용어 설명</summary>

- **이벤트 루프 블로킹(Event Loop Blocking)**: 이벤트 루프 스레드 내에서 CPU 바운드·동기 블로킹 연산이 실행되어 이후 이벤트 처리가 지연되는 현상.

</details>

```text
1. 비동기 I/O 요청 등록 (Non-blocking 설정)
   │ 즉시 제어권 반환 (블로킹 없음)
   ▼
2. 이벤트 루프: 다른 이벤트 계속 처리
   │
   ▼
3. OS I/O 완료 → epoll이 완료 이벤트를 이벤트 큐에 삽입
   │
   ▼
4. 이벤트 루프: 큐에서 완료 이벤트 추출
   │
   ▼
5. 콜백 핸들러 실행 → 후속 비즈니스 로직 처리
   └─ 추가 비동기 I/O 요청 시 1단계 반복
```

**동작 원리**

1. **I/O 등록**: 파일 디스크립터를 논블로킹으로 설정하고 epoll에 완료 통지 등록
2. **즉시 반환**: I/O 완료를 대기하지 않고 이벤트 루프는 다음 이벤트 처리를 계속
3. **완료 이벤트 큐잉**: OS가 I/O 완료를 감지하여 이벤트 큐에 완료 이벤트를 삽입
4. **콜백 디스패치**: 이벤트 루프가 큐에서 완료 이벤트를 추출하여 콜백 핸들러를 실행

#### 한줄 요약

- I/O 요청 즉시 반환 → OS 완료 이벤트 큐잉 → 이벤트 루프 추출 → 콜백 실행의 순환 처리 흐름

## Ⅴ. 종류 및 비교

<details><summary>용어 설명</summary>

- **io_uring**: 커널·유저 공간 공유 링 버퍼(제출 큐·완료 큐)를 통해 시스템 콜 오버헤드 없이 비동기 I/O를 수행하는 리눅스 최신 I/O 인터페이스.

</details>

| 구분 | 동기 블로킹 (Thread-per-request) | 비동기 이벤트 루프 (Async I/O) |
|:---|:---|:---|
| 적용 기준 | 낮은 동시 연결, 단순 비즈니스 로직 | 고동시성 I/O 바운드 서버 |
| 핵심 특징 | 요청당 OS 스레드 1:1, 코드 직관성 높음 | **단일 스레드** 논블로킹 이벤트 순환 처리 |
| 한계 | 대규모 동시 연결 시 스레드·메모리 고갈 | 이벤트 루프 블로킹 시 전체 처리량 급락 |

#### 한줄 요약

- 고동시성 I/O 바운드 서버는 비동기 이벤트 루프, 단순 저동시성 환경은 동기 블로킹 모델 선택

## Ⅵ. 실무 고려사항 및 대책

<details><summary>용어 설명</summary>

- **백프레셔(Backpressure)**: 이벤트 처리 속도가 이벤트 수신 속도를 따라가지 못할 때 이벤트 수신을 일시 제한하여 이벤트 큐 메모리 고갈을 방지하는 흐름 제어 메커니즘.

</details>

| 문제 | 대책 | 효과 |
|:---|:---|:---|
| CPU 바운드 작업의 이벤트 루프 실행으로 **이벤트 루프 블로킹** 발생 | CPU 바운드 작업을 **워커 스레드 풀** 대상 오프로드 | 이벤트 루프 응답성 유지 |
| 콜백 중첩으로 코드 가독성·유지보수성 저하 | **Async/Await·Promise·WebFlux(Reactor)** 적용 | 동기 코드에 준하는 가독성 확보 |
| 이벤트 수신 속도 초과로 이벤트 큐 **메모리 고갈** 발생 | 큐 임계치 초과 시 소켓 읽기 일시 정지(**백프레셔**) 적용 | 이벤트 큐 메모리 한도 내 안정적 운영 |

#### 한줄 요약

- CPU 바운드는 워커 풀로 오프로드, 콜백 복잡성은 Async/Await으로, 큐 폭주는 백프레셔로 제어

## Ⅶ. 결론

<details><summary>용어 설명</summary>

- **비동기 아키텍처 선택 기준**: 동시 연결 수·I/O 바운드 비율·CPU 바운드 비율을 분석하여 동기 블로킹과 비동기 이벤트 루프를 결정하는 판단 기준.

</details>

- 고동시성 I/O 바운드 환경(Node.js·Netty·Nginx)은 **비동기 이벤트 루프**, 단순 비즈니스 로직은 **동기 블로킹** 모델 선택

#### 한줄 요약

- 동시 연결 수가 많고 I/O 바운드 비중이 높은 환경에는 비동기 이벤트 루프, 단순 환경은 동기 모델을 적용
