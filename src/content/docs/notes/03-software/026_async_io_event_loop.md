## Ⅰ. 개요

<details><summary>용어 설명</summary>

- **비동기 I/O(Async I/O)**: 파일이나 네트워크 읽으라고 찔러놓고, 멍 때리며 기다리지 않고 곧바로 딴짓하다가 다 됐다는 콜백 오면 그때 처리하는 논블로킹 깡패 기술이다.
- **이벤트 루프(Event Loop)**: 스레드 딱 하나가 미친 듯이 뺑뺑이 돌면서, OS가 던져주는 수만 개의 완료 이벤트를 낚아채서 콜백 함수로 쏴주는 무한 노동의 굴레이다.
- **I/O 다중화(I/O Multiplexing)**: `epoll`이나 `kqueue` 같은 OS 치트키를 써서, 스레드 하나가 수만 개의 소켓(File Descriptor)을 동시에 감시하는 가성비 끝판왕 기술이다.

</details>

- 정의: 찔러놓고 딴짓하는 **비동기 I/O**와, 완료 이벤트들을 스레드 하나가 뺑뺑이 돌며 콜백으로 쳐내는 **이벤트 루프**
- 배경: 접속자 들어올 때마다 스레드 1개씩 주면(동기 블로킹), 1만 명 들어왔을 때 메모리 터지고 문맥 전환 오버헤드 때문에 **서버가 뻗어버리기 때문**

#### 한줄 요약

- 스레드 하나가 수만 개의 I/O를 논블로킹으로 감시하고, 완료되면 콜백으로 쳐내는 가성비 깡패 구조다.

## Ⅱ. 특징

<details><summary>용어 설명</summary>

- **논블로킹 I/O(Non-blocking I/O)**: I/O 요청했을 때 데이터가 없어도 스레드를 멈추지 않고, "지금 없음(EAGAIN)" 에러를 뱉어서 스레드가 도망가게(딴짓하게) 놔주는 기법이다.
- **리액터 패턴(Reactor Pattern)**: 이벤트 루프가 쏟아지는 이벤트(요청)를 감지해서, 알맞은 콜백 함수(핸들러)한테 멱살 잡고 꽂아주는 비동기 아키텍처의 국룰 패턴이다.

</details>

- 연결이 수만 개여도 스레드를 안 늘리고, **Non-blocking I/O + epoll/kqueue** 조합으로 퉁침.
- **리액터 패턴(Reactor Pattern)**을 써서, 짧은 이벤트는 메인 루프가 다 쳐내고, 오래 걸리는 건 워커 풀에 던짐.
- 루프 스레드는 절대 멈추면 안 되므로, 1초라도 걸리는 깡연산은 무조건 짬처리해야 함.

#### 한줄 요약

- OS 감시기(epoll)로 논블로킹 대기를 하고, 리액터 패턴으로 콜백을 분배하는 게 핵심이다.

## Ⅲ. 구조 및 구성요소

<details><summary>용어 설명</summary>

- **이폴(epoll) / kqueue / io_uring**: "누가 데이터 보냈나" 하고 일일이 확인(select)하는 뻘짓을 버리고, OS가 "얘네 데이터 옴!" 하고 찝어주는 미친 성능의 감시자 인터페이스이다.
- **워커 스레드 풀(Worker Thread Pool)**: 이벤트 루프가 암호화나 파일 쓰기 같은 무거운 작업 하다가 뻗어버리면 서버 전체가 멈추니까, 이런 더러운 일을 짬처리하려고 대기시켜 놓은 백그라운드 일꾼들이다.

</details>

```text
[ 비동기 이벤트 루프 십자포화 아키텍처 (Reactor) ]
  [ I/O 등록 (소켓/파일) ]
            │
┌───────────▼───────────┐
│  [ OS 이벤트 감시기 ] │
│   (epoll / kqueue)    │
└───────────┬───────────┘
            ▼ (이벤트 큐에 꽂힘)
┌───────────────────────┐  짬처리   ┌────────────────┐
│    [ 이벤트 루프 ]    ├────────▶│ 워커 스레드 풀 │
│ (스레드 1개가 무한 뺑뺑이)│        │ (무거운 연산)  │
└───────────┬───────────┘          └────────────────┘
            ▼
     [ 콜백 핸들러 ]
  (결과 받아서 로직 실행)
```

| 구성요소 | 책임 |
|:---|:---|
| I/O 등록 인터페이스 | 감시할 소켓(FD)이랑 "데이터 오면 알려줘"라는 꼬리표를 OS에 등록함 |
| **OS 이벤트 감시기** | **epoll** 켜놓고 수만 개 소켓 중에 진짜 데이터 들어온 놈만 쏙 골라냄 |
| 이벤트 큐 | 감시기가 뱉어낸 이벤트들이 콜백을 기다리며 줄 서 있는 대기실 |
| **이벤트 루프** | 대기실에서 이벤트 뽑아서 쉴 새 없이 콜백 함수에 꽂아주는 메인 심장 (단일 스레드) |
| 완료 처리기 (Callback) | "데이터 왔음" 이벤트 받아서 후속 비즈니스 로직을 돌리는 실무자 |
| 워커 스레드 풀 | 암호화 깡연산 하다가 이벤트 루프 멈출까 봐 따로 짬처리하는 용병 부대 |

#### 한줄 요약

- OS가 이벤트를 큐에 쏴주면, 이벤트 루프가 낚아채서 콜백을 부르고 무거운 건 워커에 던진다.

## Ⅳ. 흐름도

<details><summary>용어 설명</summary>

- **이벤트 루프 블로킹(Event Loop Blocking)**: 단일 스레드로 도는 이벤트 루프 안에서 1초짜리 `while`문을 돌리거나 `Thread.sleep`을 때려서, 뒤에 밀린 수만 명의 접속자를 다 튕기게 만드는 끔찍한 병크 현상이다.

</details>

```text
[ 비동기 I/O 호출 및 콜백 십자포화 흐름 ]
┌──────────────────────────────┐
│ 1. 비동기 I/O 요청 등록      │
│ (Non-blocking 세팅)          │
└──────────────┬───────────────┘
               ▼ (기다리지 않고)
┌──────────────────────────────┐
│ 2. 즉시 제어권 반환 및 딴짓  │
│ (루프는 다음 이벤트 처리)    │
└──────────────┬───────────────┘
               ▼
┌──────────────────────────────┐
│ 3. OS 완료 이벤트 큐잉       │
│ (epoll ➔ Event Queue)        │
└──────────────┬───────────────┘
               ▼
┌──────────────────────────────┐
│ 4. 이벤트 루프가 낚아채기    │
│ (루프가 큐에서 뽑아옴)       │
└──────────────┬───────────────┘
               ▼
┌──────────────────────────────┐
│ 5. 콜백 디스패치 및 후속 처리│
│ (콜백 핸들러에 꽂아서 실행)  │
└──────────────────────────────┘
```

### 동작 원리

1. I/O 요청 등록: 소켓/파일 I/O를 논블로킹으로 세팅하고 커널 **epoll**에 등록함.
2. 제어권 즉시 반환: 블로킹당하지 않고 바로 리턴해서, 루프 스레드는 딴 놈들 요청을 계속 받음.
3. 완료 이벤트 수집: 커널에서 I/O 끝나면 **Event Queue**에 결과 완료 알림을 꽂음.
4. 콜백 디스패치: 뺑뺑이 돌던 **Event Loop**가 큐에서 이벤트를 쏙 빼서 짝지어진 **콜백 핸들러**를 부름.
5. 결과 처리 및 후속: 콜백 로직 돌리고 끝내거나, 또 다른 비동기 I/O 꼬리를 묾.

#### 한줄 요약

- 요청 던지고 $\to$ 딴짓하다가 $\to$ OS가 큐에 완료 이벤트 꽂으면 $\to$ 낚아채서 콜백 부르는 흐름이다.

## Ⅴ. 종류 및 비교

<details><summary>용어 설명</summary>

- **아이오 유링(io_uring)**: epoll조차도 시스템 콜 오버헤드가 크니까, 커널과 유저 공간 사이에 링 버퍼(제출/완료 큐)를 파서 아예 락 없이 비동기 I/O를 초광속으로 꽂아버리는 최신 리눅스 치트키이다.

</details>

| 비교 항목 | **동기 블로킹** (Thread-per-request) | **비동기 이벤트 루프** (Async I/O) |
|:---|:---|:---|
| 스레드 굴리는 법 | 접속자 1명당 OS 스레드 1개씩 통째로 던져줌 (1:1) | **단 1개의 스레드**가 수만 명을 루프 돌며 다 커버 침 |
| 동시성 / 확장성 | 접속자 1만 명 = 스레드 1만 개 ➔ 메모리 터지고 뻗음 | 메모리 쥐꼬리만큼 쓰고 10만 명 접속해도 끄떡없음 |
| 코딩 난이도 | 직관적이고 순서대로 짜서 에러 잡기 개꿀임 | 콜백 지옥, Promise 떡칠로 꼬이면 디버깅 헬파티 옴 |
| 찰떡궁합 툴 | 전통적인 Tomcat, Spring MVC | **Node.js, Netty, Redis, Nginx** (극강의 논블로킹) |

#### 한줄 요약

- 동기는 스레드를 물량으로 때려 박고, 비동기 이벤트 루프는 스레드 하나로 극한의 뽕을 뽑는다.

## Ⅵ. 실무 고려사항 및 대책

<details><summary>용어 설명</summary>

- **백프레셔(Backpressure, 역압력)**: 콜백 처리하는 속도보다 이벤트가 쏟아지는 속도가 너무 빨라서 큐 메모리가 터지려고 할 때, "야 그만 보내!" 하고 소켓 읽기를 틀어막아서 시스템 붕괴를 막는 최후의 방어막이다.

</details>

| 문제 | 대책 | 효과 |
|:---|:---|:---|
| 루프 안에서 무거운 암호화(CPU-bound) 돌리다 서버 멈춤 | 그런 쓰레기 코드는 무조건 **워커 풀(Worker Pool)**로 짬처리 | 루프 스레드 블로킹을 막아 다른 수만 명의 접속자를 살려냄 |
| 콜백 안에 콜백 박다가 **콜백 지옥** 열리고 가독성 멸망함 | **Async/Await, Promise, WebFlux(Reactor)** 패턴으로 섞음 | 동기식처럼 예쁘게 보이게 만들어 개발자 정신병 예방 |
| 1만 개 이벤트 쏟아지는데 처리 못해서 이벤트 큐 OOM 뜸 | 버퍼 꽉 차면 멱살 잡고 소켓 읽기 일시정지 때리는 **백프레셔** | 큐 폭주를 통제해서 메모리 한계치 내에서 서버 생존 사수 |

#### 한줄 요약

- 무거운 작업은 워커 풀에 버리고, 콜백 지옥은 Async/Await로 펴며, 큐 폭주는 백프레셔로 막아라.

## Ⅶ. 결론

<details><summary>용어 설명</summary>

- **비동기 아키텍처 선택 기준(Async I/O Selection Criteria)**: 연결이 만 단위인지, 대기빵(I/O)이 많은지, CPU 깡연산이 많은지 각을 재서 스프링(동기)과 네티(비동기)를 가르는 잣대이다.

</details>

- **비동기 아키텍처 선택 기준** 원칙에 따라, 수만 명 동시 접속 채팅이나 API 게이트웨이는 무조건 **Netty / Node.js (이벤트 루프)**, 무거운 비즈니스 깡연산은 **스레드 풀(동기 블로킹)** 채택 기조 확립함

#### 한줄 요약

- 수만 명 접속하는 I/O 대기빵엔 이벤트 루프를 쓰고, CPU 빡세게 굴리는 연산엔 스레드 풀을 박아라.
