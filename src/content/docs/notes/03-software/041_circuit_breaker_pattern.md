## Ⅰ. 개요

<details><summary>용어 설명</summary>

- **서킷 브레이커 패턴(Circuit Breaker Pattern)**: 두꺼비집(누전 차단기)처럼, 다른 서버 API를 찔렀는데 계속 실패하거나 느리면 아예 선을 끊어버려서(Open) 내 서버까지 죽는 걸 막는 방어 스킬이다.
- **연쇄 장애(Cascading Failure)**: 결제 서버 하나가 느려졌는데, 그거 기다리던 주문 서버 스레드가 다 묶이고, 배달 서버까지 줄줄이 뻗어버리는 MSA 최악의 도미노 붕괴 현상이다.
- **대체 응답(Fallback)**: 차단기가 내려가서 원래 데이터를 못 가져올 때, 에러 화면 대신 "일시적 오류입니다"나 옛날 캐시 데이터라도 던져줘서 유저 빡침을 방어하는 꼼수이다.

</details>

- 정의: 타깃 서비스가 뻗었을 때 두꺼비집(차단기)을 내려서 호출을 끊고, 내 서버까지 뒤지는 연쇄 장애(Cascading Failure)를 막는 방어 패턴인 **Circuit Breaker**
- 배경: 뻗은 서버를 계속 찌르며 기다리다 보면 **내 서버의 스레드 풀(Thread Pool)까지 고갈**되면서 다 같이 사이좋게 망하기 때문

#### 한줄 요약

- 남의 서버 뻗었다고 내 서버까지 같이 뻗는 걸 막기 위해, 선을 끊어버리는(차단) 두꺼비집이다.

## Ⅱ. 특징

<details><summary>용어 설명</summary>

- **Closed (정상 상태)**: 차단기가 닫혀서 전기가 통하는 평화로운 상태. 트래픽이 정상적으로 백엔드를 때리고 통과한다.
- **Open (차단 상태)**: 에러율이 선을 넘어서 차단기가 열린(끊어진) 비상 상태. 백엔드로 아예 요청을 안 보내고 바로 `Fallback`(에러/캐시)을 뱉어낸다.
- **Half-Open (반개방 상태)**: 차단기 내리고 쿨타임 좀 지나서, "이제 좀 살았나?" 하고 찔끔 찔러보는(간 보는) 테스트 상태이다. 성공하면 Closed, 실패하면 다시 Open으로 돌아간다.

</details>

- **Closed $\rightarrow$ Open $\rightarrow$ Half-Open $\rightarrow$ Closed**로 이어지는 3단계 기어 변속(상태 전이) 메커니즘을 굴림.
- "최근 100번 중에 50번 실패하면 차단!" 같은 **슬라이딩 윈도우(Sliding Window)** 룰을 씀.
- 선 끊고 바로 **Fallback(대체 응답)**을 날려서, 500 에러 대신 예쁜 에러 창을 띄워줌.

#### 한줄 요약

- 평소엔 열어두고(Closed), 터지면 끊고(Open), 쿨타임 차면 간 보는(Half-Open) 3단계 시스템이다.

## Ⅲ. 구조 및 구성요소

<details><summary>용어 설명</summary>

- **슬라이딩 윈도우(Sliding Window)**: "최근 10초" 또는 "최근 100번의 호출"이라는 틀(창문)을 만들어놓고, 그 안에서 에러율이나 응답 지연율이 컷트라인을 넘는지 계속 감시하는 모니터링 기법이다.

</details>

```text
[ 서킷 브레이커 방어 십자포화 아키텍처 ]

[ 호출 인터셉터 ] ───(API 찌름)───▶ [ 실패 측정 창(Sliding Window) ]
       │                                 │ (에러율 50% 돌파!)
       ▼                                 ▼
[ 대체 응답(Fallback) ] ◀──(차단)── [ 상태 기계 (Open으로 변신) ]
       │                                 │ (쿨타임 끝남)
       ▼                                 ▼
(캐시 데이터 반환)               [ 복구 제어기 (Half-Open 찔러봄) ]
```

| 구성요소 | 책임 |
|:---|:---|
| **호출 인터셉터** | 외부 API 나가는 길목에 서서 요청을 통과시킬지, 컷할지 멱살 쥐고 있는 문지기 |
| **실패 측정 창** | 최근 N번 호출 중에 몇 번 터졌는지 엑셀에 꼼꼼히 적어두는 서기 |
| **상태 기계** | 에러율 넘으면 차단기 내리고(Open), 복구되면 올리는(Closed) 두꺼비집 컨트롤러 |
| **복구 제어기** | 차단기 내리고 쿨타임 찰 때까지 멍 때리다가 한두 개 찔러보는(Half-Open) 간잽이 |
| **대체 응답 처리기** | 차단기 내려갔을 때 에러 터뜨리는 대신 캐시(Fallback) 던져주는 알바생 |

#### 한줄 요약

- 모니터링 창부가 에러율을 재고, 선 넘으면 컨트롤러가 선을 끊고 땜빵 응답을 던진다.

## Ⅳ. 흐름도

<details><summary>용어 설명</summary>

- **시험 호출(Probe Request)**: 뻗었던 서버가 살아났는지 확인하려고, 1000개 요청 중 한두 개만 쏙 빼서 던져보는(간 보는) 테스트용 정찰병이다.

</details>

```text
[ 서킷 브레이커 상태 전이 십자포화 흐름 ]
┌──────────────────────────────┐
│ 🟢 Closed (정상 영업 중)     │◀────────────────┐
└──────────────┬───────────────┘                 │
               ▼ 1. 임계치 초과 (에러 폭발)      │
       [ 차단기 쾅! 내려감 ]                     │
               ▼                                 │
┌──────────────────────────────┐                 │
│ 🔴 Open (영업 정지 / Fallback)│                 │
└──────────────┬───────────────┘                 │
               ▼ 2. 쿨타임(기다림) 끝남          │
┌──────────────────────────────┐                 │
│ 🟡 Half-Open (간 보는 중)    │                 │
└──────────────┬───────────────┘                 │
               ▼ 3. 시험 호출 (정찰병 투입)      │
       [ 복구 여부 판정 ]                        │
          ├─ ⭕ 성공 (살아남) ───────────────────┘
          └─ ❌ 실패 (여전히 죽음) ─▶ (다시 🔴 Open)
```

### 동작 원리

1. 결과 집계(Closed): 평소엔 잘 찌르면서 에러율을 창부에 꼬박꼬박 적음.
2. 임계치 판정(Open): 에러가 선 넘으면 바로 두꺼비집 내리고 요청 안 보냄.
3. 쿨다운 대기: 세팅해 둔 시간(ex: 10초) 동안 묻지도 따지지도 않고 요청 컷함.
4. 시험 호출(Half-Open): 10초 지나면 반쯤 열어서 한두 개 찔러봄(정찰병).
5. 복구 판정: 정찰병이 성공하면 정상화(Closed)하고, 죽어서 오면 두꺼비집 다시 내림(Open).

#### 한줄 요약

- 평소(Closed) $\to$ 터짐(Open) $\to$ 대기 $\to$ 정찰병(Half-Open) $\to$ 복구(Closed) 루프다.

## Ⅴ. 종류 및 비교

<details><summary>용어 설명</summary>

- **Resilience4j vs Hystrix**: 넷플릭스가 만들었지만 너무 무거워서 버려진 구형(Hystrix)과, 함수형 기반으로 빠르고 가볍게 쪼개 쓸 수 있는 최신 국룰 라이브러리(Resilience4j)의 차이이다.

</details>

| 비교 항목 | **Resilience4j** (요즘 대세) | **Netflix Hystrix** (단종된 유물) |
|:---|:---|:---|
| 기반 기술 | Java 8 함수형 인터페이스, 람다 기반 | 무거운 스레드 풀 격리 중심, 구닥다리 |
| 모듈 쪼개기 | 서킷 브레이커, Rate Limiter 등 골라 씀 | 모놀리식 덩어리라 통째로 박아야 함 |
| 현재 상태 | **스프링 부트 국룰 (Spring Cloud)** | 유지보수 중단(Deprecated). 쓰면 욕먹음 |

#### 한줄 요약

- Hystrix는 역사 속으로 사라졌으니, 무조건 Resilience4j를 쓰면 된다.

## Ⅵ. 실무 고려사항 및 대책

<details><summary>용어 설명</summary>

- **격벽 패턴(Bulkhead Pattern)**: 배 밑바닥에 구멍 나도 배 전체가 가라앉지 않게 칸막이를 치는 것처럼, A API용 스레드 10개, B API용 10개씩 쪼개놔서 한쪽이 뻗어도 남은 쪽은 살리는 패턴이다.

</details>

| 문제 | 대책 | 효과 |
|:---|:---|:---|
| 트래픽 별로 없는데 어쩌다 한 번 난 에러 때문에 차단됨 | 최소 호출 횟수(`minimumNumberOfCalls`) 20회 이상 넉넉히 세팅 | 표본 부족으로 인한 오발탄 차단 방지 |
| 차단기 내려갔다고 화면에 날것의 500 에러를 뱉음 | **Fallback(대체 응답)**으로 캐시 데이터나 기본값 뿌림 | 고객은 장애 난 줄도 모름 (UX 극상 방어) |
| A 서버 뻗었더니 내 스레드 풀이 거기로 쏠려서 나도 뻗음 | **Bulkhead(격벽)** 쳐서 스레드 풀 할당량을 A, B 쪼개둠 | 스레드 고갈 방지 및 **장애 격리 2중 방어** |

#### 한줄 요약

- 최소 표본 세팅으로 오발탄 막고, 뻗으면 Fallback(캐시)으로 때우며, 스레드는 격벽으로 쪼개라.

## Ⅶ. 결론

<details><summary>용어 설명</summary>

- **서킷 브레이커 설계 기준(Circuit Breaker Design Standards)**: MSA 환경에서 장애가 옆 동네로 번지는 걸 막기 위해, 에러율 타겟과 Fallback 퀄리티를 어떻게 맞출지 정하는 잣대이다.

</details>

- **서킷 브레이커 설계 기준** 원칙에 따라, 원격 호출이 잦은 분산 구간은 **Circuit Breaker**, 스레드 털릴 위험이 큰 구간은 **Bulkhead** 결합 기조 확립함

#### 한줄 요약

- 타임아웃과 서킷 브레이커 없는 MSA 호출은 언제 터질지 모르는 시한폭탄이다.
