## Ⅰ. 개요

<details><summary>용어 설명</summary>

- **리팩터링(Refactoring)**: "겉보기 작동은 똑같은데 속은 깨끗하게 뜯어고친다"는 철학으로, 유저 입장에선 바뀐 게 없지만 개발자 입장에선 쓰레기장이 호텔로 바뀌는 마법이다.
- **기술 부채(Technical Debt)**: 당장 내일 배포하려고 똥 코드를 짜서 빚을 냈더니, 나중에 고칠 땐 그 빚이 이자가 되어 개발팀의 목을 조르는 현상이다.
- **코드 악취(Code Smell)**: 천 줄짜리 함수, 여기저기 복붙한 코드처럼 "이거 나중에 무조건 터지겠는데?" 싶은 냄새(결함 징후)를 풍기는 레거시 코드이다.

</details>

- 정의: 당장의 출시를 위해 끌어다 쓴 **Technical Debt(기술 부채)**를 갚기 위해, 외부 동작 결과는 100% 유지하면서 내부 쓰레기 코드를 치우는 **Refactoring**
- 배경: 코드 악취를 방치하면 이자가 눈덩이처럼 불어나 **작은 수정에도 버그가 터지고 야근이 일상이 되는 재앙**을 막기 위함

#### 한줄 요약

- 유저 몰래 쓰레기 코드를 청소해서, 나중에 똥 밟고 야근하는(기술 부채) 걸 막는 작업이다.

## Ⅱ. 특징

<details><summary>용어 설명</summary>

- **외부 행위 보존(Behavior-Preserving)**: 코드를 아무리 뜯어고쳐도 덧셈기에 `1+1`을 넣었을 때 어제처럼 똑같이 `2`가 나와야지 `3`이 나오면 장애라는 절대 원칙이다.
- **회귀 테스트 안전망(Regression Safety Net)**: 코드 고치다가 삐끗해서 기능 날려 먹는 걸 방지하기 위해, 바닥에 촘촘하게 깔아두는 수백 개의 단위 테스트(방패)이다.

</details>

- 기능 추가 금지, 100% **Behavior-Preserving Transformation (외부 행위 보존)**.
- 지독한 **Code Smell 제거** 및 가독성 떡상.
- 안전하게 코드를 뜯기 위해 **Regression Safety Net (테스트 코드 방패)** 필수 장착.

#### 한줄 요약

- 테스트라는 든든한 밧줄(안전망)을 묶고, 결과는 안 바뀌게 속만 깔끔히 파내는 거다.

## Ⅲ. 구조 및 구성요소

<details><summary>용어 설명</summary>

- **리팩터링 기법(Extract Method / Rename Method)**: 천 줄짜리 코드를 잘게 쪼개서 분리하거나, `a`, `b1` 같은 쓰레기 변수명을 `userId`처럼 찰떡같이 바꿔주는 청소 스킬이다.

</details>

```text
[ 리팩터링 및 기술부채 상환 십자포화 아키텍처 ]

[ 코드 스멜 (똥 냄새나는 레거시) ] ──▶ [ 부채 백로그 (빚쟁이 장부 등록) ]
                                                    │
                                                    ▼
     [ 리팩터링 (청소 시작) ] ◀── [ 회귀 테스트 안전망 (방탄조끼 착용) ]
```

| 구성요소 | 팩트 폭행 책임 |
|:---|:---|
| **코드 스멜** | 너무 길거나 중복돼서 냄새 풀풀 나는 쓰레기 코드 (리팩터링 타깃) |
| **부채 백로그** | "이거 나중에 꼭 고쳐야 함" 하고 빚 갚을 목록 적어둔 장부 |
| **회귀 테스트** | 쓰레기 치우려다 기둥까지 뽑아버리지 않게 지켜주는 든든한 테스트 코드 |
| **리팩터링** | 외부 동작은 건드리지 않고, 야금야금 속만 파내서 클린 코드로 조각하는 작업 |

#### 한줄 요약

- 쓰레기 발견 $\to$ 빚장부에 등록 $\to$ 방탄조끼(테스트) 입고 $\to$ 청소하는 구조다.

## Ⅳ. 흐름도

<details><summary>용어 설명</summary>

- **기술 부채 4분면(Technical Debt Quadrant)**: 알면서도 당장 출시하려고 진 '착한 빚'과, 개발자가 멍청해서 자기도 모르게 쌓은 '나쁜 빚' 등 빚을 왜 졌는지 팩폭하는 표이다.

</details>

```text
[ 리팩터링 기술부채 상환 십자포화 흐름 ]
┌──────────────────────────────┐
│ 1. 냄새나는 레거시 코드 발견 │
│ (메서드 길이가 500줄임)      │
└──────────────┬───────────────┘
               ▼
┌──────────────────────────────┐
│ 2. 테스트 방패(안전망) 세팅  │
│ (고치다 터질까 봐 미리 짜둠) │
└──────────────┬───────────────┘
               ▼
┌──────────────────────────────┐
│ 3. 찔끔찔끔 리팩터링 시작    │
│ (함수 쪼개고 변수명 바꿈)    │
└──────────────┬───────────────┘
               ▼
┌──────────────────────────────┐
│ 4. 테스트 돌려서 똑같나 확인 │
│ (어제랑 똑같이 도네? Pass!)  │
└──────────────┬───────────────┘
               ▼
┌──────────────────────────────┐
│ 5. 기술부채 장부 빚 상환     │
│ (스파게티 코드 박멸 완료)    │
└──────────────────────────────┘
```

### 동작 원리

1. 악취 탐지: 정적 분석기가 "여기 복붙 50줄짜리 중복 코드 있음!" 경고 때림.
2. 안전망 확보: 걍 지우지 말고, 기존 코드가 돌아가던 테스트 방패를 세팅함.
3. 구조 개선: `Extract`로 함수 쪼개고 `Rename`으로 변수명 예쁘게 바꿈.
4. 행위 검증: 테스트 돌려서 바뀐 코드도 똑같이 초록불 뿜는지 팩트 체크함.
5. 부채 상환: 장부에서 빚 털어내고 두 다리 쭉 뻗음.

#### 한줄 요약

- 냄새 발견 $\to$ 안전망 확보 $\to$ 청소 $\to$ 테스트 통과 확인 $\to$ 빚 청산의 흐름이다.

## Ⅴ. 종류 및 비교

<details><summary>용어 설명</summary>

- **리팩터링 vs 성능 최적화**: 리팩터링은 사람 보기 좋으라고 코드를 예쁘게 다듬는 거고, 최적화는 컴퓨터 일하기 편하라고 0.1초라도 쥐어짜서(가끔은 더럽게) 만드는 거다.

</details>

| 비교 항목 | **Refactoring (클린 코드 장인)** | **Performance Optimization (속도광)** |
|:---|:---|:---|
| 주 주요 목적 | **코드 예쁘게 짜서 나중에 고치기 쉽게 만듦**| **서버 안 터지게 CPU/메모리 속도 쥐어짬** |
| 외부 행위 변경 | **입출력 결과 100% 똑같아야 함** | 입출력 똑같지만, 응답 시간(0.1초)이 빨라짐 |
| 코드 변화 형태 | 잘게 쪼개져서 파일/함수가 늘어나서 깔끔해짐 | **속도 올리려고 캐싱/하드코딩 떡칠해서 더러워짐** |
| 실행 안전망 | 단위 테스트 코드만 있으면 만사형통 | JMH 같은 성능 벤치마크 툴 필수 장착 |

#### 한줄 요약

- 리팩터링은 사람(개발자)을 위한 청소고, 최적화는 기계(서버)를 위한 도핑이다.

## Ⅵ. 실무 고려사항 및 대책

<details><summary>용어 설명</summary>

- **보이스카우트 원칙(Boy Scout Rule)**: "캠핑장 떠날 땐 쓰레기 하나씩 줍고 가라"는 룰로, 오늘 버그 고치러 들어간 김에 주변에 있던 똥 코드 하나 슬쩍 예쁘게 고치고 나오는 훈훈한 원칙이다.

</details>

| 문제 | 대책 | 효과 |
|:---|:---|:---|
| 테스트도 없이 깝치다가 멀쩡한 기능 다 터짐 | **회귀 테스트(안전망)** 없으면 리팩터링 금지! | 리팩터링하다 퇴사하는 대참사 방지 |
| "한 달 동안 기능 멈추고 리팩터링만 하자" 미친 소리 | **Boy Scout Rule** 적용해 매일 한 줄씩만 고침 | 일정 빵꾸 안 내고 스무스하게 빚 상환 |
| 일정 빡세서 "나중에 고칠게~" 하고 영원히 쨈 | 눈물 흘리며 **기술부채(Tech Debt) 장부**에 박제 | 잊어버리고 튀는 얌체 짓 원천 차단 |

#### 한줄 요약

- 테스트 없인 건들지 말고, 몰아서 하지 말고 매일 줍고(보이스카우트), 안 한 건 장부에 적어라.

## Ⅶ. 결론

<details><summary>용어 설명</summary>

- **기술 부채 관리 기준(Technical Debt Management Standards)**: 코드가 얼마나 썩었는지, 매일 건드려야 하는 앤지 각 재서 먼저 고칠 빚을 정하는 잣대이다.

</details>

- **기술 부채 관리 기준** 원칙에 따라, 매일 건드리는 핵심 코드는 **보이스카우트 원칙**으로 고치고, 다음 달 폐기할 코드는 **현 상태 유지(방치)** 기조 확립함

#### 한줄 요약

- 오늘 게을러서 남겨둔 기술 부채는, 내일 이자까지 쳐서 야근으로 갚아야 한다.
