## Ⅰ. 개요

<details><summary>용어 설명</summary>

- **악취 제거 및 내부 개선(Code Smell & Refactoring)**: 중복 코드, 거대 함수 등 코드 악취를 식별하여 인터페이스 동작 변경 없이 가독성과 결합도를 개선하는 작업.
- **스파게티 누적 및 생산성 마비(Spaghetti Code & Paralysis)**: 단기 출시를 위해 설계 원칙을 무시하여 부채 이자(수정 시간)가 눈덩이처럼 불어나 기능 추가가 불가능해지는 한계.

</details>

- 정의/개념: 외부 동작(Behavior)을 유지한 채 **코드 악취(Code Smell)를 제거하고 내부 구조를 개선**하여 누적된 기술 부채를 상환하는 소프트웨어 유지보수 공학 활동
- 배경/필요성: 무계획적 빠른 출시로 인한 **스파게티 코드 누적 및 변경 수정 비용 기하급수적 증가와 개발 생산성 마비** 직면

#### 한줄 요약

- 기술 부채를 가시화하고 회귀 테스트 보호 하에 외부 동작을 보존하며 코드 구조를 지속적으로 개선

## Ⅱ. 특징

<details><summary>용어 설명</summary>

- **외부 행위 보존(Behavior-Preserving Transformation)**: 리팩터링은 동일한 입력에 대해 동일한 출력을 유지하는 것을 절대 원칙으로 하며, 기능 추가·변경은 리팩터링 범위에서 제외.
- **회귀 테스트 안전망(Regression Safety Net)**: 리팩터링 중 기존 동작이 손상되지 않도록 보호하는 단위 테스트 집합.

</details>

- 기능 추가 없이 100% **외부 행위 보존** 원칙 준수
- **코드 악취 제거**로 가독성·응집도 향상 및 결합도 감소
- 구조 변경의 안전성을 보장하는 **회귀 테스트 안전망** 사전 구비

#### 한줄 요약

- 외부 행위 보존 원칙·코드 악취 제거·회귀 테스트 안전망의 세 원칙으로 안전한 구조 개선 수행

## Ⅲ. 구조 및 구성요소

<details><summary>용어 설명</summary>

- **리팩터링 기법(Extract Method / Rename Method 등)**: 과도하게 긴 메서드를 의미 단위로 분리하거나 비직관적 변수명을 의미 있는 이름으로 변경하는 구체적 리팩터링 적용 기법.

</details>

```text
[ 기술 부채 상환 구조 ]
코드 악취 탐지 (정적 분석 도구·코드 리뷰)
   │ 기술 부채 식별
부채 백로그 (가시화·우선순위화)
   │ 상환 계획 수립
회귀 테스트 안전망 구비
   │ 보호 상태에서
리팩터링 수행 (Extract/Rename/Move 등)
   │ 행위 검증
회귀 테스트 재실행 → 기술 부채 백로그에서 제거
```

선의 의미: 화살표는 기술 부채 상환의 단계 흐름, 회귀 테스트 안전망은 리팩터링 수행의 전제 조건 관계

| 구성요소 | 책임 |
|:---|:---|
| **코드 악취** | 리팩터링 대상 식별 신호 |
| **기술 부채 백로그** | 식별된 부채를 가시화하고 우선순위를 관리하는 목록 |
| **회귀 테스트** | 리팩터링 중 기존 동작 손상 방지 |
| **리팩터링 기법** | 외부 행위 보존 하에 코드 구조를 개선하는 구체적 변환 |

#### 한줄 요약

- 악취 탐지→백로그 등록→안전망 구비→리팩터링→행위 검증→부채 제거의 구조적 상환 흐름

## Ⅳ. 흐름도

<details><summary>용어 설명</summary>

- **기술 부채 4분면(Technical Debt Quadrant)**: Martin Fowler의 기술 부채 분류로, 의도적 무모(Reckless)·신중(Prudent)과 비의도적(Inadvertent) 조합으로 부채의 성격과 대응 전략을 구분.

</details>

```text
1. 코드 악취 탐지 (정적 분석·코드 리뷰)
   └─ 중복 코드·과도한 메서드 길이·높은 결합도 식별
   │
   ▼
2. 회귀 테스트 안전망 구비
   └─ 기존 동작을 검증하는 단위 테스트 작성
   │
   ▼
3. 점진적 리팩터링 수행 (Baby Steps)
   └─ Extract Method·Rename Variable·Move Class 등 기법 적용
   │
   ▼
4. 회귀 테스트 재실행 → 행위 보존 검증 (Pass 확인)
   │
   ▼
5. 부채 백로그에서 항목 제거 → 지속 반복
```

**동작 원리**

1. **악취 탐지**: 정적 분석 도구 또는 코드 리뷰를 통해 코드 악취와 부채를 식별
2. **안전망 구비**: 리팩터링 이전에 기존 동작을 검증하는 회귀 테스트를 작성
3. **점진 수행**: Baby Steps 방식으로 소규모 변환을 반복하여 리스크 최소화
4. **행위 검증**: 매 변환 후 회귀 테스트를 실행하여 외부 행위 보존 확인
5. **부채 상환**: 검증 완료 항목을 백로그에서 제거하고 다음 대상으로 이동

#### 한줄 요약

- 악취 탐지→안전망→점진 리팩터링→행위 검증→부채 상환의 지속적 개선 흐름

## Ⅴ. 종류 및 비교

<details><summary>용어 설명</summary>

- **리팩터링 vs 성능 최적화**: 리팩터링은 코드 구조 개선(가독성·유지보수성)을 목적으로 외부 동작을 완전히 보존하고, 성능 최적화는 실행 효율(속도·메모리) 향상을 목적으로 코드를 변경.

</details>

| 비교 항목 | 리팩터링 | 성능 최적화 |
|:---|:---|:---|
| 주요 목적 | 코드 구조·가독성·유지보수성 향상 | 실행 속도·메모리 효율 향상 |
| 외부 행위 변경 | **완전 보존 필수** | 동일 결과이나 실행 시간 단축 |
| 코드 변화 방향 | 분리·명확화로 코드 복잡도 감소 | 캐싱·최적화 알고리즘으로 복잡도 증가 가능 |
| 검증 도구 | 단위 테스트(회귀) | JMH 등 성능 벤치마크 |

#### 한줄 요약

- 리팩터링은 개발자를 위한 가독성 개선, 성능 최적화는 시스템을 위한 실행 효율 개선

## Ⅵ. 실무 고려사항 및 대책

<details><summary>용어 설명</summary>

- **보이스카우트 원칙(Boy Scout Rule)**: 코드를 수정할 때마다 주변의 코드 악취를 최소 하나 이상 개선하여 전체 코드 품질을 지속적으로 향상하는 원칙.

</details>

| 문제 | 대책 | 효과 |
|:---|:---|:---|
| 회귀 테스트 없이 리팩터링을 수행하다 기존 기능 손상 | 리팩터링 이전 **회귀 테스트 안전망 구비 필수** | 행위 손상 방지 |
| 대규모 리팩터링으로 장기간 기능 개발 중단 | **보이스카우트 원칙**으로 일상 수정 시 점진 개선 | 기능 개발 일정 유지하며 지속적 부채 상환 |
| 기술 부채 방치로 존재 자체가 망각 | **기술 부채 백로그** 작성·가시화·우선순위화 | 부채의 지속적 인식과 체계적 상환 계획 수립 |

#### 한줄 요약

- 안전망 없는 리팩터링 금지·보이스카우트 원칙으로 일상 개선·부채 백로그로 가시화

## Ⅶ. 결론

<details><summary>용어 설명</summary>

- **기술 부채 관리 기준**: 코드 변경 빈도·유지보수 비용·품질 지표를 기반으로 우선 상환 대상 부채를 결정하는 판단 기준.

</details>

- 일상적으로 변경하는 핵심 모듈은 **보이스카우트 원칙**으로 지속 개선하고, 향후 폐기 예정인 코드는 **현 상태 유지**로 자원 낭비를 방지

#### 한줄 요약

- 기술 부채는 회귀 테스트 보호 하에 점진적으로 상환하고 백로그로 가시화하여 품질 저하를 예방
