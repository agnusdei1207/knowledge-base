## Ⅰ. 개요

<details><summary>용어 설명</summary>

- **리팩터링(Refactoring)**: 소프트웨어의 외부 동작(Behavior)은 그대로 유지하면서 내부의 구조, 가독성, 유지보수성을 개선하는 공학 기법.
- **기술 부채(Technical Debt)**: 빠른 출시를 위해 임시방편(Quick & Dirty)으로 작성된 코드가 시간이 지남에 따라 수정 비용과 결함률을 가중시키는 부채 개념.

</details>

- 정의/개념: 외부 동작(Behavior)을 보존하며 **코드 악취(Code Smell)를 제거하고 내부 구조를 개선**하여 누적된 기술 부채를 상환하는 공학 활동
- 배경/필요성: 빠른 출시를 위한 편법 개발로 인한 **스파게티 코드 누적 및 유지보수 비용 기하급수적 폭증 해결 불가**

#### 한줄 요약
- 회귀 테스트 안전망 보호 하에 외부 동작을 보존하며 내부 구조를 지속 개선한다.

## Ⅱ. 특징

<details><summary>용어 설명</summary>

- **외부 행위 보존**: 관찰 가능한 동작을 유지하고 기능·명세 변경을 분리하는 원칙.
- **보이스카우트 원칙(Boy Scout Rule)**: "캠핑장은 떠날 때 처음 왔을 때보다 더 깨끗하게 치워라" - 코드를 만질 때마다 조금씩 리팩토링하는 문화.

</details>

- 신규 기능 추가와 분리해 **외부 행위 보존** 원칙 준수
- 중복 코드(DRY 위반) 및 거대 클래스 등 **코드 악취(Code Smell)의 지속적 제거**
- 리팩터링의 회귀를 탐지하는 **자동화 테스트 안전망** 확보

#### 한줄 요약
- 외부 행위 보존, 코드 악취 제거, 회귀 테스트 안전망 구비가 3대 원칙이다.

## Ⅲ. 구조 및 구성요소

<details><summary>용어 설명</summary>

- **대표 리팩터링 기법**: 메서드 추출(Extract Method), 클래스 추출(Extract Class), 변수 인라인화, 상속을 합성으로 전환.

</details>

```text
[리팩터링 관리 체계]
|-- 코드 악취 지표
|-- 기술 부채 백로그
|-- 회귀 테스트 안전망
`-- 리팩터링 기법 카탈로그
```

선의 의미: 가지는 관리 체계의 구성 관계

| 구성요소 | 책임 |
|:---|:---|
| 코드 악취 지표 | 긴 메서드·중복 코드 등 **개선 후보** 식별 |
| 기술 부채 백로그 | 영향과 상환 비용에 따라 우선순위 관리 |
| 회귀 테스트 안전망 | 변경 전후 **관찰 동작**의 회귀 탐지 |
| 리팩터링 기법 카탈로그 | 메서드 추출 등 재구조화 패턴 제공 |

#### 한줄 요약
- 악취 식별, 부채 백로그, 회귀 테스트 안전망, 정형 리팩터링 기법이 결합된다.

## Ⅳ. 흐름도

<details><summary>용어 설명</summary>

- **Baby Steps(작은 보폭)**: 1~2줄 단위로 작게 코드를 수정하고 즉시 테스트를 실행하여 결함 발생 지점을 즉시 특정하는 리팩토링 방식.

</details>

```text
SonarQube 정적 분석을 통한 코드 악취(Code Smell) 탐지
        │
   해당 모듈의 단위 테스트 존재 여부 확인 (없으면 회귀 테스트 먼저 작성!)
        │
   단위 테스트 실행하여 초록불(Green) 확인 (안전망 확보)
        │
   메서드 추출(Extract Method) 등 작은 단위 리팩토링 수행 (Baby Steps)
        │
   회귀 테스트 즉시 재실행 -> 모든 테스트 통과(Green) 확인
        │
   Git 커밋 (Refactor 태그) 후 부채 백로그 상환 처리
```

#### 한줄 요약
- 악취 탐지 → 회귀 테스트 안전망 확보 → 작은 보폭 리팩토링 → 테스트 재실행 → 커밋 순으로 진행된다.

## Ⅴ. 종류 및 비교

<details><summary>용어 설명</summary>

- **리팩터링 vs 기능 추가 vs 성능 최적화**: 코드 구조 개선(리팩터링), 신규 비즈니스 로직 구현(기능 추가), 속도/메모리 튜닝(성능 최적화).

</details>

| 비교 항목 | 리팩터링 (Refactoring) | 기능 추가 (Feature Addition) | 성능 최적화 (Optimization) |
|:---|:---|:---|:---|
| 핵심 목적 | **코드 가독성, 유지보수성, 결합도 개선** | 신규 비즈니스 가치 제공 | **응답 시간 단축, 메모리 사용량 절감** |
| 외부 행위 변경 | **관찰 동작 유지** | 신규 동작 추가 | 결과 유지·비기능 특성 변경 |
| 코드 복잡도 | **감소 (클린 코드로 단순화)** | 신규 코드 추가로 다소 증가 | 캐싱/병렬화로 복잡도 증가 가능 |
| 1차 수혜자 | **동료 개발자 및 유지보수 엔지니어** | 최종 사용자 (End User) | 시스템 인프라 및 사용자 |

#### 한줄 요약
- 리팩터링은 유지보수성 개선, 기능 추가는 비즈니스 가치 창출, 최적화는 실행 속도 개선이 목적이다.

## Ⅵ. 실무 고려사항 및 대책

<details><summary>용어 설명</summary>

- **Big Bang Refactoring(빅뱅 리팩토링)**: 수만 줄의 코드를 한 번에 갈아엎다가 일정 지연과 대규모 런타임 장애를 유발하는 위험한 안티패턴.

</details>

| 문제 | 대책 | 효과 |
|:---|:---|:---|
| 회귀 테스트 없는 변경으로 기존 기능 파괴 | **특성화 테스트** 작성 후 리팩터링 | 회귀 탐지와 변경 위험 감소 |
| 빅뱅 리팩터링에 따른 일정 지연 | 부채 위험 기반 **상환 용량** 배정 | 기능 개발과 부채 상환 균형 |
| 기술 부채 방치로 개발 생산성 붕괴 | **SonarQube SQALE 기반 부채 지수(Technical Debt Ratio) 가시화** | 경영진 설득 및 계획적 부채 상환 |
| 리팩토링 중 신규 기능 추가가 섞여 디버깅 난항 | **리팩토링 커밋과 기능 추가 커밋을 명확히 물리 분리** | 변경 추적성 및 롤백 용이성 확보 |

#### 한줄 요약
- 테스트·상환 용량·부채 지수·커밋 분리로 위험을 통제한다.

## Ⅶ. 결론

- 구조 개선은 **점진적 리팩터링**, 안전망은 **회귀 테스트** 선택

#### 한줄 요약
- 변경 빈도와 장애 영향이 큰 부채부터 점진적으로 상환한다.
