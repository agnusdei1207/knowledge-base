## Ⅰ. 개요

<details><summary>용어 설명</summary>

- **세이프(SAFe, Scaled Agile Framework)**: 동네 구멍가게 수준의 애자일(Scrum)을 수천 명 규모의 대기업(Enterprise) 덩치에 맞게 뻥튀기시켜서, 임원진의 경영 전략부터 막내 개발자의 코딩까지 한 줄로 묶어버리는 뼈대 프레임워크이다.
- **애자일 릴리스 트레인(ART, Agile Release Train)**: 50~125명의 개발자, 기획자, 디자이너를 하나의 거대한 '기차(Train)'에 태워서, 같은 목표를 향해 다 같이 코딩하고 다 같이 배포하게 만드는 대규모 조직 단위이다.
- **PI(Planning Interval)**: 기차(ART)가 목적지로 가기 위해 8~12주 단위로 끊어서 달리는 큰 사이클(다중 스프린트)이다.

</details>

- 정의: 단일 애자일 팀의 한계를 부수고, 대기업의 경영 전략(Portfolio)부터 개발팀(Team)까지 린-애자일 사상으로 동기화시키는 **확장 애자일 프레임워크**
- 배경: 팀 하나만 애자일로 잘 굴러가 봤자, 옆 팀이랑 스텝이 꼬이거나 임원진 전략이랑 따로 놀면 **의존성 헬파티**가 터지기 때문

#### 한줄 요약

- 스크럼을 대기업 사이즈로 키워서, 100명이 넘는 개발자를 기차(ART)에 태우고 스텝을 맞추는 룰이다.

## Ⅱ. 특징

<details><summary>용어 설명</summary>

- **PI 플래닝(PI Planning)**: 8~12주마다 100명이 넘는 기차(ART) 탑승객 전원을 한방에 모아놓고, 1박 2일 동안 다음 PI 목표와 꼬여있는 의존성을 조율하는 SAFe의 심장이자 거대한 워크숍이다.
- **가치 스트림(Value Stream)**: 아이디어가 떠오른 순간부터 코딩을 거쳐 고객 지갑에서 돈이 나오기까지의 전체 파이프라인(돈줄)이다.

</details>

- 조직 덩치에 따라 **Essential, Large Solution, Portfolio, Full** 4가지 레벨로 맞춤 조립함.
- 100명이 넘는 개발자들이 **ART(기차)**에 타서 한 몸처럼 가치 스트림을 뽑아냄.
- **PI Planning**으로 100명의 스텝을 맞추고, 끝날 땐 **Inspect & Adapt**로 반성회를 가짐.

#### 한줄 요약

- ART(기차)라는 거대 팀을 꾸리고, PI 플래닝으로 100명의 멱살을 잡아 의존성을 푼다.

## Ⅲ. 구조 및 구성요소

<details><summary>용어 설명</summary>

- **RTE(Release Train Engineer)**: 100명이 탄 기차(ART)의 기관장이자 대빵 스크럼 마스터로, 기차가 탈선하지 않게 멱살 잡고 일정과 장애물을 치우는 직책이다.
- **시스템 아키텍트(System Architect)**: 여러 팀이 각자 코딩하다가 아키텍처가 짬뽕되는 걸 막기 위해, 기차 전체의 기술 가이드라인과 큰 뼈대를 통제하는 기술 총괄이다.

</details>

```text
[ SAFe 4계층 십자포화 아키텍처 ]

 [ 포트폴리오 (Portfolio) ] ──▶ (임원진: 돈줄 쥐고 전략 짬)
            ▼
[ 라지 솔루션 (Large Solution) ] ──▶ (수백 명: 거대 시스템 조율)
            ▼
   [ 에센셜 (Essential) ] ──▶ (100명: ART 기차 탑승 및 PI 플래닝)
            ▼
    [ 애자일 팀 (Team) ] ──▶ (10명: 스크럼/칸반으로 깡코딩)
```

| 구성요소 | 책임 |
|:---|:---|
| 린 포트폴리오 관리 (LPM) | 임원진들이 예산(Lean Budget)을 쥐고 회사 전략에 맞는 가치 스트림을 픽스하는 꼭대기 층 |
| 애자일 릴리스 트레인 (ART) | 50~125명이 한 기차에 타서 **PI 플래닝**으로 의존성 풀고 시스템 통합을 멱살 잡는 중간 층 |
| 애자일 팀 (Agile Team) | 밑바닥에서 스크럼/칸반 돌리며 실제로 코딩하고 버그 잡는 실무 노예들 |
| **RTE (기관장)** | ART 전체를 지휘하고 100명의 일정을 조율하는 슈퍼 스크럼 마스터 |

#### 한줄 요약

- 꼭대기에선 임원진이 돈을 풀고, 중간에선 기차(ART)가 구르며, 바닥에선 스크럼 팀이 코딩한다.

## Ⅳ. 흐름도

<details><summary>용어 설명</summary>

- **프로그램 보드(Program Board)**: PI 플래닝 때 벽에 붙여놓는 거대한 판때기로, "우리 팀이 이거 하려면 쟤네 팀 API가 필요해!"라며 팀 간의 꼬인 의존성(빨간 줄)을 시각화한 지뢰밭 지도이다.

</details>

```text
[ SAFe PI 플래닝 및 실행 십자포화 흐름 ]
┌──────────────────────────────┐
│ 1. 전략 및 예산 할당 (LPM)   │
│ (임원진이 돈과 비전 쏨)      │
└──────────────┬───────────────┘
               ▼ (ART 출발)
┌──────────────────────────────┐
│ 2. PI 플래닝 (1박 2일 워크숍)│
│ (100명이 모여 의존성 조율함) │
└──────────────┬───────────────┘
               ▼ (PI 구간 8~12주)
┌──────────────────────────────┐
│ 3. 애자일 팀 반복 개발 (팀)  │
│ (각자 스크럼 돌리며 코딩 팸) │
└──────────────┬───────────────┘
               ▼
┌──────────────────────────────┐
│ 4. 시스템 통합 데모 (ART)    │
│ (팀들 거 합쳐서 시연해 봄)   │
└──────────────┬───────────────┘
               ▼
┌──────────────────────────────┐
│ 5. I&A (Inspect & Adapt)     │
│ (기차 전체 모여서 대반성회)  │
└──────────────────────────────┘
```

### 동작 원리

1. 전략/투자 정렬: LPM에서 이번 분기 돈 쓸 곳과 에픽(Epic)을 정함.
2. PI 플래닝: 100명이 모여서 **프로그램 보드**에 의존성 묶고 목표 합의.
3. 팀 증분 개발: 각 팀이 2주짜리 스프린트 돌리면서 기능 찍어냄.
4. 시스템 통합 데모: 팀들 결과물 다 이어 붙여서 돌아가는지 통합 시연함.
5. I&A 대반성회: PI 구간 끝나면 다 모여서 뼈 때리는 반성하고 프로세스 고침.

#### 한줄 요약

- 돈 내려옴 $\to$ 100명이 모여 계획 짬 $\to$ 각자 코딩함 $\to$ 합쳐서 시연 $\to$ 다 같이 반성의 무한 루프다.

## Ⅴ. 종류 및 비교

<details><summary>용어 설명</summary>

- **IP 이터레이션(Innovation and Planning Iteration)**: PI 마지막 주에 코딩을 멈추고 짱박혀서 해커톤(혁신)을 하거나, 밀린 기술 부채를 갚고, 다음 PI 플래닝을 준비하는 오아시스 같은 휴식기이다.

</details>

| 비교 항목 | **SAFe** (대기업형) | **LeSS** (확장 스크럼) | **Nexus** (중소형 확장) |
|:---|:---|:---|:---|
| 확장 철학 | **하향식(Top-down) 통제 + 상향식 개발**을 섞은 대기업용 설계도 | 룰을 최소화하고 스크럼을 묶는 상향식 | 3~9개 팀을 엮기 위해 '통합 팀'을 둠 |
| 룰(가이드라인) | **숨 막힐 정도로 상세함 (거의 백과사전)** | "알아서 해라" 식의 미니멀리즘 | 스크럼 통합(Integration Team) 위주 |
| 찰떡 무대 | 은행, 자동차, 공공기관 등 수천 명이 엮인 **엔터프라이즈** | 실력파 개발자들이 모인 테크 기업 | 10개 팀 미만의 중소형 개발 조직 |

#### 한줄 요약

- 빡센 통제가 필요한 은행/대기업은 SAFe, 개발자 중심의 자유로운 테크 기업은 LeSS다.

## Ⅵ. 실무 고려사항 및 대책

<details><summary>용어 설명</summary>

- **무늬만 세이프(SAFe in Name Only, SINO)**: 겉으로는 PI 플래닝도 하고 직책도 RTE로 바꿨는데, 실상은 임원진이 옛날 폭포수처럼 문서 검사하고 까라면 까라는 식의 하향식 통제를 버리지 못한 파행적 꼰대 문화이다.

</details>

| 문제 | 대책 | 효과 |
|:---|:---|:---|
| 10개 팀이 남의 API 기다리느라 아무것도 못 하고 뻗음 | PI 플래닝 때 **Program Board(프로그램 보드)** 그려서 시각화 | 블로킹 구간을 미리 파악하고 순서를 재조정해 숨통 틔움 |
| 1년 내내 새 기능만 찍어내느라 스파게티 코드 쌓이고 갈려나감 | PI 마지막 주에 **IP Iteration** 강제 배정해서 코딩 멈춤 | 기술 부채 갚고 다음 PI 준비할 숨돌릴 시간(용량) 확보 |
| 이름만 SAFe고 본부장이 엑셀로 일정 쪼는 **SINO(무늬만 세이프)** | SPC(세이프 코치) 데려와서 임원진 린-애자일 마인드 개조함 | 폭포수 꼰대 문화를 박살 내고 찐 비즈니스 민첩성 획득 |

#### 한줄 요약

- 의존성은 프로그램 보드로 풀고, 지친 팀은 IP 주간으로 쉬게 하며, 꼰대 마인드(SINO)는 박살 내라.

## Ⅶ. 결론

<details><summary>용어 설명</summary>

- **전사 애자일 확장 기준(Enterprise Agile Scaling Criteria)**: 개발자가 몇 명인지, 팀끼리 얼마나 엮여 있는지, 윗선에서 얼마나 통제하고 싶어 하는지 각 재서 SAFe를 쓸지 LeSS를 쓸지 가르는 잣대이다.

</details>

- **전사 애자일 확장 기준** 원칙에 따라, 100명 이상 엮여있고 경영진 통제가 필요한 거대 조직은 **SAFe**, 개발자 중심의 수평적 강소 조직은 **LeSS** 채택 기조 확립함

#### 한줄 요약

- 100명이 넘는 개발자가 한 몸처럼 움직여야 하는 엔터프라이즈라면 묻지도 따지지도 말고 SAFe다.
