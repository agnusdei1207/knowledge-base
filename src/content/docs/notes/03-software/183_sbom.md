## Ⅰ. 개요

<details>
<summary>핵심 용어</summary>

- **소프트웨어 자재 명세서(Software Bill of Materials, SBOM)**: 제품을 이루는 구성요소·정확한 버전·공급자와 직접·전이 의존 관계를 기계 판독 형식으로 기록한 명세이다.

</details>

- 정의/개념: **SBOM**은 소프트웨어 제품에 포함된 구성요소·버전·공급자·의존 관계를 기계 판독 형식으로 기록한 구성 명세
- 배경/필요성: 구성 목록 없이는 숨은 부품의 **취약점·라이선스** 영향 추적 불가

#### 한줄 요약

- 완제품 안에 어떤 부품과 버전이 어떤 관계로 들어갔는지 적어 문제 부품이 발견됐을 때 영향 제품을 바로 찾는 디지털 부품표다.

## Ⅱ. 특징

<details>
<summary>핵심 용어</summary>

- **SPDX·CycloneDX**: SPDX와 CycloneDX는 소프트웨어 구성요소와 관계, 공급망 정보를 표현하고 교환하는 표준이다.
- **소프트웨어 패키지 데이터 교환(Software Package Data Exchange, SPDX)**: 구성요소·라이선스·관계를 표현하는 국제 표준 SBOM 형식이다.
- **사이클론DX(CycloneDX)**: 애플리케이션 보안과 공급망 위험 분석에 필요한 구성요소·서비스·관계를 표현하는 SBOM 표준이다.
- **제품 해시·전자서명**: SBOM을 정확한 산출물 판본과 발행자에게 결속하고 변조 여부를 검증하는 수단이다.

</details>

- **직접·전이 구성요소** 기반 구성 투명성
- **SPDX·CycloneDX** 기반 표준 교환
- **제품 해시·전자서명** 기반 산출물 결속

#### 한줄 요약

- 이름만 적은 목록이 아니라 제품 버전·해시와 부품 관계를 연결해야 다른 빌드의 SBOM을 잘못 적용하지 않는다.

## Ⅲ. 구조 및 구성요소

<details>
<summary>핵심 용어</summary>

- **SBOM Generator**: SBOM Generator는 소스·잠금 파일·빌드 산출물에서 부품과 관계, 표준 식별자를 생성한다.
- **소프트웨어 자재 명세서 생성기(Software Bill of Materials Generator, SBOM Generator)**: 소스·잠금 파일·빌드 산출물에서 부품·관계·식별자를 추출하는 구성요소이다.
- **SBOM 저장소(SBOM Repository)**: 제품·배포 판본별 명세와 서명·출처를 보관하는 구성요소이다.
- **취약점 악용 가능성 교환(Vulnerability Exploitability eXchange, VEX)**: 특정 제품에서 취약점이 실제 영향을 주는지와 근거를 전달하는 상태 정보이다.

</details>

```mermaid
block
    columns 1
    A["소스·빌드 산출물"]
    B["SBOM Generator"]
    C["검증·서명"]
    D["SBOM Repository"]
    E["위험 분석"]
    A --- B
    B --- C
    C --- D
    D --- E
```

| 구성요소 | 책임 |
|:---|:---|
| 소스·빌드 산출물 | 선언·잠금·**실제 구성 입력** |
| SBOM Generator | 부품·관계·**표준 식별자 생성** |
| 검증·서명 | 제품 해시·**발행자·무결성 검증** |
| SBOM Repository | 제품·배포 **버전별 명세 보관** |
| 위험 분석 | 취약점·라이선스·**VEX 영향 판단** |

#### 한줄 요약

- 빌드에서 실제 부품을 뽑아 표준 목록을 만들고 제품 해시와 묶어 서명한 뒤 취약점 목록과 대조한다.

## Ⅳ. 흐름도

<details>
<summary>핵심 용어</summary>

- **4. 구성 그래프**: 구성 그래프는 부품 식별자와 의존 경로를 취약점 정보에 대조해 영향 제품을 찾게 한다.
- **1. 산출물·의존 정보 전달**: 선언 파일·잠금 파일·바이너리의 실제 구성 정보를 생성기에 제공하는 단계이다.
- **2. 소프트웨어 자재 명세서(Software Bill of Materials, SBOM)·제품 해시**: 필수 필드와 산출물 일치 여부를 검증해 명세를 정확한 제품에 연결하는 단계이다.
- **3. 서명 명세**: 발행자와 무결성을 검증한 명세를 제품·버전·배포 단위로 저장하는 단계이다.
- **5. 영향·우선순위**: 취약점 악용 가능성 교환과 실제 배포 자산을 기준으로 대응 순서를 결정한 결과이다.

</details>

```mermaid
sequenceDiagram
    participant B as 빌드 파이프라인
    participant G as SBOM 생성기
    participant V as 검증·서명
    participant R as SBOM 저장소
    participant A as 위험 분석기
    B->>G: 1. 산출물·의존 정보 전달
    G->>V: 2. SBOM·제품 해시
    V-->>R: 3. 서명 명세
    R->>A: 4. 구성 그래프
    A-->>R: 5. 영향·우선순위
```

**동작 원리**

1. **산출물·의존 정보 전달**: 선언·잠금·바이너리 구성 수집
2. **SBOM·제품 해시**: 필수 필드와 산출물 일치 검증
3. **서명 명세**: 제품·버전·배포 단위 연결
4. **구성 그래프**: 식별자·의존 경로·취약점 대조
5. **영향·우선순위**: VEX·배포 자산을 기준으로 대응 순서 결정

#### 한줄 요약

- 새 취약점이 공개되면 부품 식별자와 의존 경로를 따라 실제 배포 중인 제품 버전과 호출 가능성을 확인한다.

## Ⅴ. 종류 및 비교

<details>
<summary>핵심 용어</summary>

- **빌드 시 생성**: 빌드 시 생성 방식은 실제로 해석된 의존성과 산출물을 연결해 자체 제품의 공식 SBOM을 만든다.
- **선언 분석(Manifest Analysis)**: 의존성 선언과 잠금 파일을 읽어 개발 초기 구성요소를 식별하는 방식이다.
- **빌드 시 생성(Build-Time Generation)**: 실제 해석된 의존성과 산출물을 연결해 공식 소프트웨어 자재 명세서를 만드는 방식이다.
- **바이너리 분석(Binary Analysis)**: 완성된 파일·패키지를 사후 스캔해 외부·레거시 산출물의 구성요소를 탐지하는 방식이다.

</details>

| SBOM 생성 방식 | 선언 분석 | 빌드 시 생성 | 바이너리 분석 |
|:---|:---|:---|:---|
| 적용 기준 | 개발 초기 **조기 점검** | 자체 제품 **공식 명세** | 외부·레거시 **보완 분석** |
| 핵심 특징 | Manifest·**Lockfile 입력** | 실제 의존·**산출물 연결** | 파일·패키지 **사후 탐지** |
| 한계 | 동적·삽입 부품 **누락** | 도구 밖 삽입 **누락** | 버전·관계 **오탐** |

#### 한줄 요약

- 선언 파일은 빠르지만 실제 산출물과 다를 수 있어 빌드 시 생성을 정본으로 삼고 바이너리 분석으로 숨은 부품을 보완한다.

## Ⅵ. 실무 고려사항 및 대책

<details>
<summary>핵심 용어</summary>

- **취약점 오매칭**: 취약점 오매칭은 이름만으로 구성요소를 식별해 다른 생태계나 버전의 취약점을 잘못 연결하는 문제다.
- **패키지 통합 자원 위치 지정자(Package Uniform Resource Locator, purl)**: 패키지 생태계·이름·버전을 표준 형식으로 식별하는 주소이다.
- **공통 플랫폼 열거(Common Platform Enumeration, CPE)**: 하드웨어·운영체제·애플리케이션 제품을 취약점 정보와 연결하는 표준 식별 체계이다.
- **제품 다이제스트(Product Digest)**: 완성 산출물 내용으로 계산한 해시값으로 SBOM을 정확한 빌드에 결속하는 식별자이다.

</details>

| 문제 | 대책 | 효과 |
|:---|:---|:---|
| 전이·동적 부품의 **목록 누락** | 소스·빌드·**바이너리 교차 검증** | **구성 완전성** 향상 |
| 이름만 사용한 **취약점 오매칭** | **purl·CPE**와 버전·해시 기록 | **식별 정확성** 향상 |
| 다른 빌드의 **SBOM 연결** | 제품 Digest·**출처·서명 결합** | **산출물 결속** 보장 |
| 포함만으로 **영향 단정** | 호출·설정·**VEX 근거 검토** | **대응 우선순위** 정제 |
| 생성 후 **운영 미연계** | 자산·배포·**티켓·패치 연결** | **사고 대응 시간** 단축 |

#### 한줄 요약

- 취약 라이브러리가 목록에 있어도 실행 경로와 설정상 사용할 수 없는지 VEX 근거를 확인해야 실제 위험 제품부터 고칠 수 있다.

## Ⅶ. 결론

<details>
<summary>핵심 용어</summary>

- **빌드 시 SBOM**: 자체 제품은 빌드 시 SBOM을 제품 해시와 결속해 서명하고 외부 산출물은 바이너리 분석으로 보완해야 한다.

</details>

- 자체 빌드는 **빌드 시 SBOM**을 서명하고 외부 산출물은 바이너리 분석으로 보완

#### 한줄 요약

- 빌드마다 제품 해시와 서명된 SBOM을 만들고 배포 자산·취약점·VEX를 연결해야 부품표가 실제 대응 도구가 된다.
