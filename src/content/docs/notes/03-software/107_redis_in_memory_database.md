## Ⅰ. 개요

<details><summary>용어 설명</summary>

- **Redis 인메모리 데이터베이스**: 모든 데이터를 메인 메모리(RAM)에 상주시켜 서브밀리초(Sub-millisecond) 단위의 초저지연을 제공하고 다양한 내장 자료구조와 영속성을 지원하는 키-값 저장소.
- **디스크 I/O 지연 및 초고속 트래픽 한계(Disk I/O Latency & Throughput Limit)**: 디스크 기반 데이터베이스의 블록 읽기 오버헤드로 인해 실시간 랭킹, 세션 관리 및 초당 수만 건 이상의 트래픽 처리가 지연되는 문제.

</details>

- 정의/개념: 초저지연 데이터 처리를 위해 **모든 데이터를 RAM에 상주시키고 다양한 인메모리 자료구조(ZSet, Hash)와 영속성(RDB/AOF)을 제공**하는 고성능 저장소
- 배경/필요성: 디스크 기반 RDBMS의 I/O 지연으로 인한 **초고속 세션 조회, 실시간 랭킹 산출 및 초당 수만 건 이상의 트래픽 처리 한계** 직면

#### 한줄 요약

- RAM 상주 기반 단일 스레드 이벤트 루프와 풍부한 자료구조를 통해 초저지연 캐싱 및 실시간 데이터 처리를 구현

## Ⅱ. 특징

<details><summary>용어 설명</summary>

- **단일 스레드 이벤트 루프(Single-Threaded Event Loop)**: 복잡한 락(Lock) 경합과 컨텍스트 스위칭 없이 단일 스레드로 명령어를 원자적(Atomic)으로 고속 처리하는 커널 아키텍처.
- **RDB 및 AOF 영속성**: 특정 시점의 메모리 스냅샷을 디스크에 덤프하는 RDB와 모든 쓰기 명령어를 순차 기록하는 AOF(Append-Only File).

</details>

- 메모리 기반 1ms 미만의 **초저지연 응답 속도(Sub-millisecond Latency)**
- Strings, Hashes, Lists, Sets, Sorted Sets(ZSet) 등 **풍부한 내장 자료구조 원자적 지원**
- RDB 스냅샷 및 AOF 변경 로그를 통한 **인메모리 데이터의 디스크 영속성(Persistence) 보장**

#### 한줄 요약

- 단일 스레드 비동기 루프로 동시성 락 경합 없이 원자적 연산을 수행하며 RDB/AOF로 영속성을 보완

## Ⅲ. 구조 및 구성요소

<details><summary>용어 설명</summary>

- **Sorted Set(ZSet)**: 각 멤버에 부동소수점 점수(Score)를 부여하여 $O(\log N)$으로 순위를 정렬·유지하는 스킵리스트 기반 자료구조.

</details>

```text
[ Redis 인메모리 엔진 및 클러스터 아키텍처 구조도 ]

 ┌────────────────────────────────────────────────────────────────────────┐
 │                      Redis 인메모리 코어 아키텍처                      │
 ├────────────────────────────────────────────────────────────────────────┤
 │              [ 단일 스레드 비동기 이벤트 루프 (Event Loop) ]          │
 │                                    │                                   │
 │                 ┌──────────────────┼──────────────────┐                │
 │                 ▼                  ▼                  ▼                │
 │        [ 인메모리 저장소 ]    [ 만료 관리자 ]   [ 영속성 서브시스템 ]   │
 │        - Strings / Hashes     - TTL 타이머      - RDB 스냅샷 (bgsave) │
 │        - ZSet (Sorted Set)    - Maxmemory LRU   - AOF 로그 (appendfsync│
 └─────────────────┬─────────────────────────────────────┬────────────────┘
                   ▼                                     ▼
         [ Redis Sentinel (HA) ]              [ Redis Cluster (16384 슬롯) ]
```

선의 의미: 단일 스레드 이벤트 루프가 메모리 저장소, 만료 관리, 영속성 서브시스템을 통제하고 고가용성/분산 클러스터로 확장되는 구조.

| 구성요소 | 책임 |
|:---|:---|
| 이벤트 루프 (Core) | 다중 클라이언트 요청을 비동기 수신하여 **락 없이 단일 스레드로 원자적 순차 실행** |
| 인메모리 데이터셋 | RAM 상에 다양한 데이터 구조(String, Hash, ZSet)를 **$O(1)\sim O(\log N)$ 속도로 저장/연산** |
| 영속성 엔진 (RDB/AOF) | 비동기 포크(fork)를 통해 **RDB 덤프 및 AOF 로그를 디스크에 기록하여 복구 보장** |
| 만료 관리자 (Eviction) | 키별 TTL 만료를 추적하고 메모리 포화 시 **Maxmemory 정책(LRU/LFU)으로 키 회수** |

#### 한줄 요약

- 이벤트 루프, 메모리 자료구조, 영속성 엔진, 만료 관리자가 결합하여 초고속 인메모리 연산을 수행

## Ⅳ. 흐름도

<details><summary>용어 설명</summary>

- **Maxmemory 회수 및 쓰기 파이프라인**: 요청 수신 $\to$ 메모리 한도 검사 $\to$ LRU/LFU 기반 키 제거 $\to$ 메모리 할당 및 쓰기 완료.

</details>

```text
[ Redis 메모리 할당 및 키 제거(Eviction) 파이프라인 ]

 ┌────────────────────────────────────────┐
 │ 1. 쓰기 요청 접수 (SET, ZADD, HSET)    │
 └───────────────────┬────────────────────┘
                     │
                     ▼
 ┌────────────────────────────────────────┐
 │ 2. Maxmemory 한도 도달 여부 검사       │
 └───────────────────┬────────────────────┘
                     │ (메모리 포화 시)
                     ▼
 ┌────────────────────────────────────────┐
 │ 3. 키 제거 정책(Eviction) 실행 (LRU/LFU)│
 └───────────────────┬────────────────────┘
                     │ (메모리 공간 확보 후)
                     ▼
 ┌────────────────────────────────────────┐
 │ 4. 인메모리 데이터 할당 및 연산 완료    │
 └───────────────────┬────────────────────┘
                     │
                     ▼
 ┌────────────────────────────────────────┐
 │ 5. AOF 버퍼 기록 및 클라이언트 응답    │
 └────────────────────────────────────────┘
```

### 동작 원리

1. 요청 접수: 클라이언트의 쓰기 명령어(SET, ZADD 등)가 이벤트 루프에 도달.
2. 한도 검사: 현재 사용 중인 메모리가 설정된 `maxmemory` 임계치를 초과했는지 확인.
3. 키 제거 정책 실행: 초과 시 설정된 알고리즘(allkeys-lru, volatile-lru 등)에 따라 오래된 키를 즉시 축출(Evict).
4. 메모리 할당: 확보된 RAM 공간에 자료구조를 생성하고 값을 갱신.
5. 영속성 반영: AOF 버퍼에 명령어를 기록하고 1ms 이내로 클라이언트에 성공 응답을 반환.

#### 한줄 요약

- 요청 접수 $\to$ 한도 검사 $\to$ LRU 키 제거 $\to$ 메모리 할당 $\to$ AOF 기록의 5단계

## Ⅴ. 종류 및 비교

<details><summary>용어 설명</summary>

- **Redis vs Memcached**: 다채로운 자료구조와 영속성, 클러스터링을 지원하는 Redis와 단순 Key-Value 멀티스레드 정적 캐시인 Memcached.

</details>

| 구분 | Redis (Remote Dictionary Server) | Memcached (정적 캐시 엔진) |
|:---|:---|:---|
| **적용 기준** | 랭킹 보드, 세션, 메시지 큐, 영속성 필요 캐시 | 단순 HTML/객체 캐싱 및 멀티코어 고속 처리 |
| **핵심 특징** | **Strings, Hashes, ZSets 등 풍부한 자료구조, RDB/AOF 지원** | **단순 String Key-Value 구조, 멀티스레드 고속 연산** |
| **한계** | 대용량 $O(N)$ 명령 실행 시 단일 스레드 블로킹 위험 | 자체 영속성 및 복잡한 자료형/정렬 연산 미지원 |

#### 한줄 요약

- 복합 자료형 계산과 영속성이 필요하면 Redis, 단순 정적 캐싱에는 Memcached를 선택

## Ⅵ. 실무 고려사항 및 대책

<details><summary>용어 설명</summary>

- **$O(N)$ 명령어 블로킹 위협**: 단일 스레드 환경에서 `KEYS *`, `FLUSHALL`, `HGETALL` 등 대량 데이터를 한 번에 조회할 때 전체 서버가 멈추는 현상.

</details>

| 문제 | 대책 | 효과 |
|:---|:---|:---|
| `KEYS *` 실행으로 인한 단일 스레드 전체 서버 락업(Lockup) | **운영 환경 `KEYS` 명령어 비활성화 및 `SCAN` 커서 명령 대체** | 무중단 커서 순회 처리 |
| 대량 캐시 TTL 동시 만료로 DB 다운 (Cache Stampede) | **TTL에 랜덤 지터(Random Jitter) 추가 및 분산 락(Redlock) 선점** | 백엔드 DB 과부하 원천 방지 |
| Big Key(수십만 개 원소를 가진 Hash/ZSet)로 인한 지연 | **해시 태그 기반 키 분할(Sharding) 및 정기적인 Big Key 모니터링** | 메모리 접근 및 직렬화 병목 해소 |

#### 한줄 요약

- SCAN 대체, TTL 지터 부여, Big Key 분할을 통해 단일 스레드 인메모리 데이터베이스를 안전하게 운용

## Ⅶ. 결론

<details><summary>용어 설명</summary>

- **Redis Cluster(16384 Hash Slots)**: 데이터를 16384개의 해시 슬롯으로 분할하여 다중 마스터 노드에 수평 분산하는 표준 클러스터 아키텍처.

</details>

- **Redis**는 현대 웹 서비스의 초고속 성능을 견인하는 핵심 인메모리 데이터 플랫폼이며, 단일 스레드 특성에 맞춘 비차단 명령어 사용과 Redis Cluster 고가용성 구성을 통해 무결점 캐싱 환경을 구축해야 함

#### 한줄 요약

- 단일 스레드 기반 인메모리 자료구조와 RDB/AOF 영속성을 활용하여 서브밀리초 응답 속도를 완성
