## Ⅰ. 개요

<details><summary>용어 설명</summary>

- **Alpha, Beta, Acceptance(UAT)**: 개발사 내부 통제 환경(Alpha), 실사용자 비통제 필드 환경(Beta), 발주자 계약 수용 기준 충족 판정(Acceptance)의 3단계 검증 체계.
- **기기 파편화 및 인수 분쟁(Fragmentation & Dispute)**: 수많은 OS/단말기 환경에서의 오동작 미발견 및 고객 요구사항 불일치로 인한 대금 지급 거절 위험.

</details>

- 정의/개념: 시스템 릴리스 전 **내부 통제(Alpha), 외부 필드(Beta), 계약 인수 기준(Acceptance/UAT)**을 거쳐 실사용자 적합성을 판정하는 검증 프로세스
- 배경/필요성: 개발사 내부 테스트 환경과 사용자 실환경 간의 괴리로 인한 **기기 파편화 결함 누락 및 계약 인수 거부 분쟁** 직면

#### 한줄 요약

- 내부 통제 환경(알파)→외부 실환경(베타)→계약 기준 수용 판정(인수)의 단계적 사용자 검증 체계

## Ⅱ. 특징

<details><summary>용어 설명</summary>

- **통제 환경 vs 비통제 환경**: 알파는 개발자가 실시간으로 로그를 확인할 수 있는 통제된 내부 환경, 베타는 불특정 사용자의 다양한 기기·OS 조합의 비통제 실제 환경.
- **사용자 인수 테스트(UAT, User Acceptance Testing)**: 발주사의 현업 담당자가 실제 업무 시나리오를 기반으로 시스템을 검증하고 수용 기준 충족 여부를 판정하는 인수 테스트.

</details>

- 내부 통제 환경에서 결함을 조기 탐지하는 **알파 테스트**
- 외부 실환경의 기기 파편화·UX 이슈를 수집하는 **베타 테스트**
- 수용 기준(**Acceptance Criteria**) 기반 합격/불합격 판정을 내리는 **인수 테스트**

#### 한줄 요약

- 알파는 내부 통제 환경, 베타는 외부 실환경, 인수는 계약 기준 판정의 단계적 검증 특성

## Ⅲ. 구조 및 구성요소

<details><summary>용어 설명</summary>

- **수용 기준(Acceptance Criteria)**: 발주자와 개발사가 프로젝트 초기에 합의한 시스템 수용 판정 기준으로, 인수 테스트의 판정 근거이자 계약 분쟁 방지 장치.

</details>

```text
[ 사용자 검증 단계 구조 ]
시스템 테스트 완료
   │
알파 테스트 (내부 통제 환경)
   └─ 사내 QA·직원 검증·결함 조기 탐지
   │
베타 테스트 (외부 실환경)
   └─ 제한된 외부 사용자 검증·기기 파편화·UX 피드백 수집
   │
사용자 인수 테스트 (UAT)
   └─ 발주사 현업 담당자가 업무 시나리오 검증·수용 기준 판정
   │
운영 인수 테스트 (OAT)
   └─ 운영팀이 복구·백업·보안 등 인프라 관점 검증
   │
최종 수용 (Sign-off)
   └─ 수용 기준 충족 확인·발주사 승인·계약 완료
```

선의 의미: 단계 간 화살표는 검증 단계 진행 순서, 각 가지(`└─`)는 해당 단계의 검증 수행 내용

| 구성요소 | 책임 |
|:---|:---|
| **알파 테스트** | 내부 통제 환경에서 치명적 결함 조기 탐지 |
| **베타 테스트** | 외부 실환경에서 기기 파편화·UX 이슈 수집 |
| **UAT** | 발주사 현업 담당자의 업무 시나리오 기반 수용 판정 |
| **OAT** | 운영팀의 복구·백업·보안 인프라 관점 검증 |
| **수용 기준** | 인수 테스트 합격/불합격 판정의 계약적 기준 |

#### 한줄 요약

- 알파로 내부 결함 제거→베타로 실환경 검증→UAT·OAT로 계약 기준 수용 판정

## Ⅳ. 흐름도

<details><summary>용어 설명</summary>

- **운영 인수 테스트(OAT, Operational Acceptance Testing)**: 사용자 기능 검증(UAT)과 별개로 운영팀이 모니터링·복구·백업·보안 등 운영 요소를 검증하는 인수 테스트.

</details>

```text
1. 시스템 테스트 완료 → 알파 테스트 실시
   └─ 사내 QA가 통제 환경에서 치명적 결함 탐지·수정
   │
   ▼
2. 베타 테스트 실시
   └─ 외부 사용자에게 배포하여 기기 파편화·UX 피드백 수집
   │
   ▼
3. UAT 실시 (발주사 현업 담당자)
   └─ 업무 시나리오 기반 기능 검증·수용 기준 충족 여부 판정
   │
   ▼
4. OAT 실시 (운영팀)
   └─ 복구·백업·보안 인프라 요소 검증
   │
   ▼
5. 최종 수용 (Sign-off) → 계약 완료·대금 결제
```

**동작 원리**

1. **알파**: 개발사 내부 QA가 통제 환경에서 치명적 버그를 제거
2. **베타**: 외부 얼리어답터에게 공개하여 다양한 기기·OS 환경의 이슈를 수집
3. **UAT**: 발주사 담당자가 수용 기준 대비 시나리오를 검증하고 합격/불합격을 판정
4. **OAT**: 운영팀이 복구·백업·보안 등 운영 요소를 검증
5. **Sign-off**: 수용 기준 충족 확인 후 발주사 승인으로 계약 완료

#### 한줄 요약

- 내부 탐지→외부 검증→업무 기준 수용 판정→운영 검증→최종 승인의 단계적 흐름

## Ⅴ. 종류 및 비교

<details><summary>용어 설명</summary>

- **계약 인수 vs 규정 인수(Contractual vs Regulatory)**: 계약서의 기능 요구사항을 검증하는 계약 인수와 법적 규제(개인정보보호법 등) 준수 여부를 검증하는 규정 인수의 구분.

</details>

| 비교 항목 | 알파 테스트 | 베타 테스트 | 인수 테스트(UAT) |
|:---|:---|:---|:---|
| 테스트 환경 | 내부 통제 환경 | 외부 비통제 실환경 | 합의된 고객사 환경 |
| 수행 주체 | 개발팀·내부 QA | 선발된 외부 사용자 | 발주사 현업 담당자·검수관 |
| 주요 목적 | 내부 결함 조기 탐지 | 실환경 파편화·UX 검증 | 계약 기준 수용 판정 |

#### 한줄 요약

- 알파는 내부 탐지, 베타는 실환경 파편화 검증, UAT는 계약 기준 수용 판정이 핵심 차이

## Ⅵ. 실무 고려사항 및 대책

<details><summary>용어 설명</summary>

- **베타 테스터 피로도(Beta Fatigue)**: 베타 테스터가 자발적 피드백을 제공하지 않는 현상으로, 자동 에러 보고 도구를 통한 강제 수집 체계가 필요.

</details>

| 문제 | 대책 | 효과 |
|:---|:---|:---|
| 사내 알파 테스터가 친분으로 결함을 간과 | **독립적 전문 QA 조직** 구성 및 체크리스트 기반 검증 | 객관적 결함 탐지 |
| 베타 사용자가 결함 발생 후 보고 없이 앱 삭제 | **Crashlytics** 등 자동 에러 보고 도구 적용 | 사용자 피드백 없이도 결함 데이터 자동 수집 |
| 발주사가 주관적 이유로 인수를 거부하여 분쟁 발생 | 프로젝트 초기에 **수용 기준(Acceptance Criteria)** 문서화·합의 | 객관적 기준 기반 판정으로 분쟁 방지 |

#### 한줄 요약

- 알파 객관성은 독립 QA로, 베타 피드백은 자동 수집으로, 인수 분쟁은 수용 기준 사전 합의로 해소

## Ⅶ. 결론

<details><summary>용어 설명</summary>

- **인수 검증 수립 기준**: B2C는 베타 테스트의 실환경 파편화 검증, B2B는 UAT·OAT의 계약 기준 검증을 강화하여 프로젝트 특성에 맞는 사용자 검증 전략을 수립하는 판단 기준.

</details>

- B2C는 **Alpha/Beta**로 실환경 파편화를 검증하고, B2B는 **UAT/OAT**로 계약 기준 수용을 판정하여 성공적 인도·대금 수령

#### 한줄 요약

- 사용자 검증의 목적은 결함 탐지에 머물지 않고 수용 기준 충족을 통한 계약 완료까지 포함
