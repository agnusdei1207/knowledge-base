## Ⅰ. 개요

<details><summary>용어 설명</summary>

- **알파/베타/인수 테스트**: 개발사 통제 환경(알파) $\to$ 불특정 사용자 실환경(베타) $\to$ 발주사 계약 수용 판정(인수/UAT)의 3단계 사용자 관점 검증.
- **수용 기준(Acceptance Criteria)**: 발주자와 개발사가 계약 초기에 합의한 시스템 인수 판정의 객관적 기준.

</details>

- 정의/개념: 시스템 릴리스 전 **내부 통제(Alpha), 외부 필드(Beta), 계약 수용 기준(Acceptance/UAT)** 으로 실환경 적합성을 검증하는 프로세스
- 배경/필요성: 개발사 내부 환경과 사용자 실환경 간 괴리로 인한 **기기 파편화 결함 누락 및 계약 인수 거부 분쟁 해결 불가**

#### 한줄 요약
- 내부 통제 환경(알파) → 외부 실환경(베타) → 계약 기준 수용(인수)의 단계적 사용자 검증 체계다.

## Ⅱ. 특징

<details><summary>용어 설명</summary>

- **통제 환경 vs 비통제 환경**: 개발자가 디버거와 로그를 직접 관찰할 수 있는 사내 통제 환경(알파)과 다양한 단말기/네트워크 조합의 외부 비통제 환경(베타).
- **UAT & OAT**: 사용자 관점의 비즈니스 시나리오 검증(UAT)과 운영 관점의 백업/복구/보안 인프라 검증(OAT).

</details>

- 내부 통제 환경에서 개발자와 함께 치명적 결함을 조기 발견하는 **알파 테스트**
- 외부 실환경의 기기/OS 파편화 및 UX 문제를 수집하는 **베타 테스트**
- 계약서의 **수용 기준(Acceptance Criteria)** 에 따라 합격/불합격을 판정하는 **인수 테스트**

#### 한줄 요약
- 알파(통제 환경), 베타(실환경 파편화), 인수(계약 기준 합격 판정)로 역할을 분담한다.

## Ⅲ. 구조 및 구성요소

<details><summary>용어 설명</summary>

- **Sign-Off(최종 검수 승인)**: 발주사 검수관이 인수 테스트 결과를 확인하고 계약 이행 완료 서명을 날인하는 법적 행위.

</details>

```text
[알파 -> 베타 -> 인수 테스트 계층 구조]
|-- 1. 알파 테스트 (Alpha Test: 개발사 내부 통제 환경)
|   |-- 사내 QA 엔지니어 및 내부 임직원 참여
|   `-- 화이트박스/블랙박스 결합 결함 집중 적발
|-- 2. 베타 테스트 (Beta Test: 외부 실제 사용자 비통제 환경)
|   |-- Closed Beta (선별된 파워 유저 대상) / Open Beta (불특정 다수)
|   `-- 기기 파편화(다양한 스마트폰 기종, OS 버전, 통신망) 검증
`-- 3. 인수 테스트 (Acceptance Test: 발주사/고객 계약 이행 판정)
    |-- UAT (User Acceptance Test: 업무 시나리오 기반 사용자 인수)
    |-- OAT (Operational Acceptance Test: 백업, 재해복구, 성능 운영 인수)
    `-- Sign-Off (최종 검수 완료 및 프로젝트 인도)
```

선의 의미: 계층 및 단계별 사용자 검증 프로세스

| 검증 단계 | 수행 환경 및 주체 | 핵심 검증 책임 |
|:---|:---|:---|
| **알파 테스트 (Alpha)** | **개발사 사내 통제 환경 (내부 QA/개발자)** | 릴리즈 전 치명적 결함 식별 및 **기본 기능 동작 완결성 검증** |
| **베타 테스트 (Beta)** | **실제 사용자 비통제 환경 (외부 테스터)** | **기기 파편화 호환성, 실 네트워크 지연, UX 사용성 피드백** |
| **사용자 인수 (UAT)** | **고객사 업무 환경 (발주사 현업 담당자)** | **비즈니스 요구사항 명세 충족 및 수용 기준 합격 판정** |
| **운영 인수 (OAT)** | **프로덕션 유사 환경 (운영/인프라팀)** | 백업/복구 절차, Failover 재해복구, SLA 가용성 검증 |

#### 한줄 요약
- 사내 알파, 외부 베타, 비즈니스 UAT, 인프라 OAT가 결합된다.

## Ⅳ. 흐름도

<details><summary>용어 설명</summary>

- **Firebase Crashlytics**: 베타 테스터의 스마트폰에서 앱 충돌 발생 시 크래시 로그와 기기 정보를 실시간 자동 수집하는 플랫폼.

</details>

```text
시스템 통합 테스트 완료 (개발 완료)
        │
   1. [알파 테스트] 사내 QA가 통제된 테스트베드에서 치명적 버그 수정
        │
   2. [베타 테스트] TestFlight/구글 플레이 베타로 배포하여 Crashlytics 크래시 수집
        │
   3. [UAT 인수] 발주사 현업이 사전 합의된 업무 시나리오(Happy/Unhappy Path) 검증
        │
   4. [OAT 인수] 운영팀이 DB 백업 복구 훈련 및 부하 장애 조치 검증
        │
   수용 기준(Critical 결함 0건, 성능 기준 충족)을 만족하는가?
   ┌────┴─────┐
  예           아니오
   │             │
[Sign-Off 서명]  [보완 요구 및 결함 재수정]
계약 완료 및 잔금 지급
```

#### 한줄 요약
- 사내 알파 → 외부 베타 크래시 수집 → UAT 시나리오 검증 → OAT 인프라 검증 → Sign-Off 순으로 진행된다.

## Ⅴ. 종류 및 비교

<details><summary>용어 설명</summary>

- **Alpha vs Beta vs UAT**: 개발자가 보는 통제 환경(Alpha), 실사용자의 실환경(Beta), 발주자의 계약 검수(UAT) 비교.

</details>

| 비교 항목 | 알파 테스트 (Alpha) | 베타 테스트 (Beta) | 사용자 인수 테스트 (UAT) |
|:---|:---|:---|:---|
| 테스트 환경 | **개발사 내부 통제 환경** | **외부 실제 비통제 환경** | **고객사 지정 실무 환경** |
| 수행 주체 | 사내 QA 엔지니어, 개발팀 | 선별/불특정 외부 실사용자 | **발주사 현업 담당자, 검수관** |
| 주 목적 | 치명적 기능 결함 조기 적발 | **기기 파편화, UX/시장성 검증** | **계약 이행 판정 (수용/거부)** |
| 결함 수집 방식 | 사내 이슈 트래커(Jira) 등록 | Crashlytics 자동 리포트, 설문 | 공식 검수 결과서(Pass/Fail) |

#### 한줄 요약
- 알파는 내부 안정화, 베타는 실환경 호환성 검증, UAT는 계약상 최종 수용 판정이 목적이다.

## Ⅵ. 실무 고려사항 및 대책

<details><summary>용어 설명</summary>

- **Scope Creep(범위 크립)**: UAT 단계에서 발주자가 계약 외의 새로운 기능을 추가 요구하며 검수 승인을 미루는 현상.

</details>

| 문제 | 대책 | 효과 |
|:---|:---|:---|
| UAT 시 발주자의 주관적 인수 거부 및 범위 크립(Scope Creep) | **프로젝트 착수 시 수용 기준(Acceptance Criteria) 명문화** | 객관적 지표 기반 판정으로 계약 분쟁 원천 차단 |
| 베타 사용자가 결함 발생 시 피드백 없이 이탈 | **Firebase Crashlytics 및 Datadog RUM 자동 계측** | 피드백 없이도 크래시 스택트레이스 100% 자동 수집 |
| 사내 임직원 알파 테스트의 온정주의적 결함 묵인 | **독립적 제3자 전문 QA 조직에 의한 결함 검증** | 객관적 결함 적발 및 프로덕션 결함 유출 방지 |
| 운영 인수(OAT) 누락으로 배포 후 재해복구 불가 | **체크리스트 기반 OAT(백업/복구 모의훈련) 의무화** | 운영 전환 후 99.99% 시스템 가용성 보장 |

#### 한줄 요약
- 수용 기준 명문화, Crashlytics 자동화, 독립 QA 검증, OAT 의무화로 리스크를 통제한다.

## Ⅶ. 결론

- B2C 서비스는 **Alpha/Beta 테스트**로 실환경 기기 파편화와 UX를 검증하고, B2B SI 프로젝트는 **명문화된 수용 기준 기반의 UAT/OAT**를 수행하여 계약 이행 완결성과 릴리즈 신뢰성 확보

#### 한줄 요약
- 알파·베타·인수 테스트는 내부 기술 검증에서 출발하여 외부 시장성 검증과 고객사 계약 승인까지 연결하는 사용자 중심 품질 보증 체계다.
