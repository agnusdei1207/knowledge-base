## Ⅰ. 개요

<details><summary>용어 설명</summary>

- **인수 테스트(Acceptance Testing)**: 개발이 다 끝난 뒤, 발주자(돈 줄 사람)가 "계약서대로 짠 거 맞지?" 하고 마지막으로 딴지 걸며 도장 찍어주는 최종 관문이다.
- **알파 테스트(Alpha Testing)**: 세상에 내보내기 전에 우리 회사 안에서 직원들끼리 옹기종기 모여서 돌려보고 버그를 털어보는 첫 번째 내부 검열이다.
- **베타 테스트(Beta Testing)**: 알파를 통과한 앱을 실제 외부 유저들에게 풀어서, 온갖 파편화된 환경에서 터지는지 간 보는 실전 테스트이다.

</details>

- 정의: 릴리스 전 내부에서 털어보는 검증(Alpha), 외부 실환경에서 굴려보는 검증(Beta), 계약서대로 짰는지 도장 받는 판정(Acceptance)을 수행하는 사용자 검증 체계
- 배경: 개발자 PC에서만 테스트하면 **고객의 폰 환경 차이, 진상 유저의 행동 패턴, 계약 조건 불일치**로 인한 대참사를 막을 수 없기 때문

#### 한줄 요약

- 우리끼리 써보고(알파), 남한테 던져보고(베타), 합격 도장 받고 돈 받는(인수) 과정이다.

## Ⅱ. 특징

<details><summary>용어 설명</summary>

- **통제 환경 vs 비통제 환경**: 알파는 에러 나면 즉시 개발자가 "어 잠깐만요" 하고 고칠 수 있는 온실(통제 환경), 베타는 유저가 지 맘대로 폰 던져버리는 야생(비통제 환경)이다.
- **사용자 인수 테스트(UAT)**: 발주사 현업 담당자가 와서 실제 업무 시나리오대로 딸깍거려 보며 "오 결제 잘 되네요, 인수합시다"라고 결정하는 팩폭 테스트이다.

</details>

- 개발사 내부의 따뜻한 온실 속 환경 검증 (**Alpha Testing**).
- 불특정 다수가 온갖 기기로 쑤셔보는 야생 실환경 검증 (**Beta Testing**).
- 수용 기준(**Acceptance Criteria**) 들이밀며 합격/불합격 판정 내리는 계약적 검증 (**Acceptance Testing**).

#### 한줄 요약

- 알파는 통제된 내부에서, 베타는 통제 안 되는 야생에서, 인수는 계약서 앞에서 진행된다.

## Ⅲ. 구조 및 구성요소

<details><summary>용어 설명</summary>

- **수용 기준(Acceptance Criteria)**: "이러이러하게 작동하면 돈 입금할게"라고 계약서나 기획서에 미리 박아둔, 개발자와 고객 간의 멱살잡이를 막아주는 정량적 평화 협정이다.

</details>

```text
[ 사용자 검증 십자포화 아키텍처 ]

[ 1. 알파 (내부 온실) ] ───▶ [ 2. 베타 (외부 야생) ]
                                        │
                                        ▼
           [ 운영 시스템 릴리스 ] ◀── [ 3. UAT (고객 도장 찍기) ]
```

| 구성요소 | 팩트 폭행 책임 |
|:---|:---|
| **테스트 근거** | 고객이 "이거 안 되면 인수 안 해"라고 선언해 둔 계약서와 수용 기준(Criteria) |
| **알파 테스트** | "일단 우리끼리 버그 다 잡자"며 개발팀과 사내 직원들이 털어보는 내부망 |
| **베타 테스트** | "실제 폰에서 돌아가나 볼까?"라며 한정된 외부 유저에게 앱을 던져보는 필드 |
| **UAT (인수)** | 깐깐한 발주사 담당자가 직접 시나리오 돌려보고 합격/불합격 도장 찍는 심판 |

#### 한줄 요약

- 알파로 버그 잡고 $\to$ 베타로 실전 검증하고 $\to$ UAT로 돈 받을 명분을 챙긴다.

## Ⅳ. 흐름도

<details><summary>용어 설명</summary>

- **운영 인수 테스트(OAT)**: 현업은 기능만 보지만(UAT), 운영팀은 "이거 장애 나면 복구는 됨? 백업은 됨? 보안은?" 하고 인프라 관점에서 딴지 거는 테스트이다.

</details>

```text
[ 수용 판정 십자포화 흐름 ]
┌──────────────────────────────┐
│ 사내 개발 및 시스템 테스트   │
└──────────────┬───────────────┘
               ▼
┌──────────────────────────────┐
│ 1. 알파 테스트 (내부 검열)   │
│ (사내 QA가 버그 싹쓸이함)    │
└──────────────┬───────────────┘
               ▼
┌──────────────────────────────┐
│ 2. 베타 테스트 (필드 방출)   │
│ (얼리버드 유저한테 던짐)     │
└──────────────┬───────────────┘
               ▼
┌──────────────────────────────┐
│ 3. 사용자 인수 테스트 (UAT)  │
│ (발주사가 기능 되는지 확인)  │
└──────────────┬───────────────┘
               ▼
┌──────────────────────────────┐
│ 4. 운영 인수 테스트 (OAT)    │
│ (운영팀이 복구/백업 털어봄)  │
└──────────────┬───────────────┘
               ▼
┌──────────────────────────────┐
│ 5. 최종 수용 (Sign-off)      │
│ (도장 찍고 대금 결제 받음)   │
└──────────────────────────────┘
```

### 동작 원리

1. 알파 시험: 온실 환경에서 사내 직원이 치명적 버그를 잡아냄.
2. 베타 시험: 외부 유저한테 뿌려서 파편화된 기기에서 터지는 걸 수집함.
3. 사용자 인수(UAT): 돈 줄 발주사가 기능 명세서대로 잘 도는지 확인함.
4. 운영 인수(OAT): 서버팀이 이거 인수받고 야근 안 할 수 있는지 인프라 검증함.
5. 최종 판정: 수용 기준 만족하면 계약 완료하고 대금 결제받음.

#### 한줄 요약

- 안에서 치고 $\to$ 밖에서 치고 $\to$ 고객이 기능 치고 $\to$ 운영팀이 인프라 쳐서 $\to$ 끝낸다.

## Ⅴ. 종류 및 비교

<details><summary>용어 설명</summary>

- **계약 인수 vs 규정 인수(Contractual vs Regulatory)**: "계약서대로 짰네"가 계약 인수, "근데 개인정보보호법은 지켰어?" 하고 정부 규제로 털어보는 게 규정 인수이다.

</details>

| 비교 항목 | **Alpha Testing (내부 검열)** | **Beta Testing (외부 방출)** | **Acceptance Testing (고객 갑질)** |
|:---|:---|:---|:---|
| 테스트 장소 | **우리 회사 내부 (온실)** | **불특정 유저의 침대 위 (야생)** | **돈 줄 고객사 환경 (심판대)** |
| 테스트 주체 | 개발자, 사내 QA, 마케팅팀 | 신청받은 외부 얼리버드 유저 | **발주사 현업 담당자, 검수관** |
| 환경 통제성 | **에러 나면 당장 로그 볼 수 있음** | **유저가 폰 끄면 로그 못 봄** | **합의된 고객사 테스트 서버** |
| 주요 목표 | 내부 크래시 버그 조기 척결 | 실환경 기기 파편화 및 UX 피드백 | **"결함 없지? 도장 찍고 돈 줘"** |

#### 한줄 요약

- 통제되는 내부망(알파) $\to$ 통제 불능인 야생(베타) $\to$ 깐깐한 심판대(인수)의 차이다.

## Ⅵ. 실무 고려사항 및 대책

<details><summary>용어 설명</summary>

- **베타 테스터의 피로도(Beta Fatigue)**: "베타 신청해 놓고 귀찮아서 피드백 안 주는 현상"으로, 결국 에러 로그 수집 툴을 깔아서 폰에서 강제로 뽑아먹어야 한다.

</details>

| 문제 | 대책 | 효과 |
|:---|:---|:---|
| 알파 때 사내 직원이라 친하다고 대충 넘어감 | 독립적인 **전문 QA 조직** 만들어서 피도 눈물도 없이 털게 함 | 객관적인 버그 검출 가능 |
| 베타 유저가 버그 나도 리포트 안 쓰고 걍 지움 | **Crashlytics** 같은 툴 박아서 폰에서 에러 나면 몰래 쏘게 함 | 'Beta Fatigue' 극복, 강제 로그 수집 |
| 고객이 "맘에 안 들어"라며 인수 도장 안 찍어줌 | 플젝 시작 때 **수용 기준(Acceptance Criteria)** 문서화 | 딴지 거는 거 원천 차단하고 돈 받아냄 |

#### 한줄 요약

- 베타 유저 피드백은 툴로 강제 수집하고, 고객의 딴지는 수용 기준(계약서)으로 방어해라.

## Ⅶ. 결론

<details><summary>용어 설명</summary>

- **인수 검증 수립 기준(Acceptance Testing Standards)**: 앱 타깃이 일반 유저(B2C)면 베타를 빡세게 하고, 기업 납품(B2B)이면 UAT 계약 검증을 빡세게 하라는 잣대이다.

</details>

- **인수 검증 수립 기준** 원칙에 따라, 폰 파편화 적합성은 **Alpha/Beta**로 퉁치고, 계약서상 돈 받는 조건은 **UAT/OAT**로 칼같이 판정하는 기조 확립함

#### 한줄 요약

- 사용자 검증의 궁극적 목적은 "버그를 잡는 것"이 아니라 "돈을 받기 위한 도장(승인)을 받아내는 것"이다.
