## Ⅰ. 개요

<details><summary>용어 설명</summary>

- **요구공학(Requirements Engineering)**: 고객이 "그냥 알아서 잘 만들어주세요"라고 던진 뜬구름 잡는 소리를 도출하고 쥐어짜서, 개발자가 알아먹을 수 있는 팩트와 숫자로 번역하는 뼈대 작업이다.
- **소프트웨어 요구사항 명세서(SRS, Software Requirements Specification)**: 고객과 개발팀이 서로 딴소리 못하게 "우리 이거 만들기로 합의함" 하고 도장 찍는, 모든 개발의 바이블이자 최종 계약서이다.

</details>

- 정의: 고객의 모호한 니즈를 영혼까지 끌어모아 팩트 기반의 명세서(SRS)로 정제해 내는 **요구사항 분석 및 명세(요구공학)**
- 배경: 처음에 대충 "빠르게 해주세요" 하고 넘어가면, 나중에 "이게 왜 느림?" 하면서 **고객과 개발팀 간 멱살잡이(수용 분쟁)** 가 터지기 때문

#### 한줄 요약

- 고객의 헛소리를 팩트(명세서)로 번역해서 나중에 딴소리 못하게 못 박는 작업이다.

## Ⅱ. 특징

<details><summary>용어 설명</summary>

- **수용 기준(Acceptance Criteria)**: "빠르다" 같은 헛소리 대신 "응답시간 0.5초 이하"처럼, 나중에 테스트할 때 빼박으로 통과/실패를 판정할 수 있는 팩트 체크 기준이다.
- **요구사항 추적 매트릭스(RTM, Requirements Traceability Matrix)**: 기획서 3페이지에 있던 기능이 소스코드 파일 어디에 처박혀 있고, 테스트 케이스 몇 번으로 검증됐는지 위아래로 집요하게 추적하는 족보(매트릭스)이다.

</details>

- 비기능 요구사항(성능, 보안)을 뭉뚱그리지 않고 측정 가능한 **수용 기준(Acceptance Criteria)** 으로 팩트 폭행함.
- 기획서부터 소스코드까지 잃어버린 요구사항 찾기를 막는 **양방향 추적성(RTM)** 을 멱살 잡고 유지함.
- **ISO/IEC/IEEE 29148** 같은 깐깐한 글로벌 국제 표준 가이드를 들이밀어서 품질을 맞춤.

#### 한줄 요약

- 수용 기준(숫자)으로 팩트를 잡고, 추적 매트릭스(RTM)로 기획부터 코드까지 족보를 잇는다.

## Ⅲ. 구조 및 구성요소

<details><summary>용어 설명</summary>

- **기능 vs 비기능 요구사항(Functional vs Non-Functional Requirements)**: 기능(Functional)이 "로그인 버튼을 누르면 메인으로 간다(What)"라면, 비기능(Non-Functional)은 "그 버튼 누르면 1초 안에 넘어간다, 털리지 않게 암호화한다(How well)"를 의미한다.

</details>

```text
[ 요구사항 십자포화 아키텍처 ]

[ 요구 저장소 (고객 니즈 덤프) ]
             │ (정제 및 모델링)
             ▼
[ 분석 모델 (Use Case / DFD) ]
             │ (문서화 및 도장 쾅)
             ▼
   [ 요구 명세서 (SRS) ]
             │ (개발/테스트 맵핑)
             ▼
 [ 요구사항 추적 매트릭스 (RTM) ]
```

| 구성요소 | 책임 |
|:---|:---|
| **요구 저장소** | 고객이 던진 온갖 잡다한 아이디어와 불만 사항을 일단 다 때려 박는 창고 |
| **분석 모델 (Use Case 등)** | 창고에 있는 말들을 꺼내서 다이어그램(그림)으로 뼈대를 잡고 경계를 긋는 설계도 |
| **요구 명세서 (SRS)** | 기능/비기능 요구사항을 텍스트로 박제하고 **수용 기준**을 달아놓은 최종 계약서 |
| **추적 매트릭스 (RTM)** | 기획서 요구 1번이 코드 파일 A, 테스트 1번에 물렸는지 감시하는 거미줄 |

#### 한줄 요약

- 니즈 모으고 $\to$ 그림(모델) 그리고 $\to$ 계약서(SRS) 쓰고 $\to$ 족보(RTM)로 관리한다.

## Ⅳ. 흐름도

<details><summary>용어 설명</summary>

- **요구사항 기준선(Requirements Baseline)**: "여기까지만 해주고 더 이상 기획 안 바꾼다!"라고 서로 도장 찍고 얼려버리는(Freeze) 마지노선 룰이다.

</details>

```text
[ 요구공학 십자포화 흐름 ]
┌──────────────────────────────┐
│ 1. 요구 도출 (Elicitation)   │
│ (고객 멱살 잡고 원하는 거 캠)│
└──────────────┬───────────────┘
               ▼
┌──────────────────────────────┐
│ 2. 요구 분석 (Analysis)      │
│ (말도 안 되는 요구 쳐내고 조율)│
└──────────────┬───────────────┘
               ▼
┌──────────────────────────────┐
│ 3. 요구 명세 (Specification) │
│ (수용 기준 달아서 SRS로 문서화)│
└──────────────┬───────────────┘
               ▼ (사인하고 얼림)
┌──────────────────────────────┐
│ 4. 검토 및 기준선 승인(Baseline)│
└──────────────┬───────────────┘
               ▼ (나중에 딴소리하면)
┌──────────────────────────────┐
│ 5. 변경 통제 및 추적 (CCB)   │
│ (돈 더 내라고 협상하고 RTM 갱신)│
└──────────────────────────────┘
```

### 동작 원리

1. 요구 도출: 인터뷰, 설문 털어서 고객 머릿속에 있는 니즈를 끄집어냄.
2. 요구 분석: 서로 충돌나는 요구사항을 모델링(Use Case) 들이밀면서 타협 봄.
3. 요구 명세: "1초 안에 응답" 같은 팩트 꽂아서 **SRS(명세서)** 씀.
4. 검토 및 기준선 승인: 윗선 불러서 서명받고 **기준선(Baseline)** 그어버림.
5. 변경 통제(CCB): 나중에 바꿔달라 하면 회의 열어서 돈/일정 청구하고 매트릭스 고침.

#### 한줄 요약

- 파내고, 타협하고, 문서 쓰고, 도장 찍고 얼린 뒤, 나중에 바꾸면 돈 더 받는 구조다.

## Ⅴ. 종류 및 비교

<details><summary>용어 설명</summary>

- **구조적 분석 vs 객체지향 분석(Structured vs Object-Oriented Analysis)**: 옛날엔 데이터가 어떻게 흘러가는지 엑셀 파이프처럼 짰다면(구조적 DFD), 지금은 레고 블록(객체)들이 어떻게 대화하는지 그리는(객체지향 UML) 방식의 차이이다.

</details>

| 비교 항목 | **기능 요구사항 (Functional)** | **비기능 요구사항 (Non-Functional)** |
|:---|:---|:---|
| 포커스 (관점) | 앱이 **무엇(What)** 을 해야 하는가? | 앱이 **얼마나 잘(How Well)** 굴러가야 하는가? |
| 판정 기준 | 회원가입 성공/실패 여부 같은 시나리오 | 99.9% 가동률, AES-256 같은 빡센 스펙 |
| 찰떡 예시 | "장바구니에 물건을 담을 수 있어야 한다" | "장바구니 로딩은 0.5초 컷이어야 한다" |

#### 한줄 요약

- 기능은 '무엇을 할지'고, 비기능은 '얼마나 빠르고 안전하게 할지'를 따진다.

## Ⅵ. 실무 고려사항 및 대책

<details><summary>용어 설명</summary>

- **모호성(Ambiguity)**: 기획서에 "유저 친화적으로 예쁘게 만들어주세요" 따위로 써놔서, 개발자랑 디자이너가 싸우게 만드는 최악의 적폐 단어이다.

</details>

| 문제 | 대책 | 효과 |
|:---|:---|:---|
| "빠르게 해주세요" 같은 모호성(Ambiguity) 기획서 | "평균 500ms 이내 응답"처럼 숫자로 때려 박는 **정량화** 시전 | 나중에 고객이 딴지 걸 때 팩트로 방어 가능 |
| 기획서 따로 코드 따로 놀아서 구현 안 된 걸 모름 | 엑셀이든 Jira든 **RTM (추적 매트릭스)** 멱살 잡고 유지함 | 구현 누락을 1초 만에 찾아내고 QA 멘탈 구원 |
| 개발 중간에 기획자가 자꾸 "이거 하나만 더" 시전 | **요구사항 기준선(Baseline)** 긋고 **CCB(변경통제위)** 결재받게 함 | 무지성 기획 엎기로 인한 프로젝트 폭망 원천 차단 |

#### 한줄 요약

- 숫자로 정량화하고(팩트), RTM으로 추적하며(족보), CCB로 무지성 추가(철벽)를 막아라.

## Ⅶ. 결론

<details><summary>용어 설명</summary>

- **요구공학 체계 수립 기준(Requirements Engineering Standards)**: 플젝 사이즈가 동네 구멍가게인지, 사람 목숨 달린 의료/금융 시스템(규제 빡셈)인지 각 재서 SRS 두께와 RTM 빡셈 정도를 조절하는 잣대이다.

</details>

- **요구공학 체계 수립 기준** 원칙에 따라, 무지성 기획 엎기(Scope Creep)를 막고 책임을 묻기 위해 **SRS 정량화 + RTM 추적성 관리** 인가 기조 확립함

#### 한줄 요약

- 기획이 무너지면 코드가 무너지니, 요구사항부터 숫자로 확실히 박고 족보를 남겨라.
