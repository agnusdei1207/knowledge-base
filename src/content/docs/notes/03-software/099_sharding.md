## Ⅰ. 개요

<details><summary>용어 설명</summary>

- **데이터베이스 샤딩(Sharding)**: 단일 DB의 물리적 한계를 극복하기 위해 데이터를 샤드 키 기준으로 여러 독립된 물리 DB 노드에 수평 분산(Scale-Out) 저장하는 기술.
- **Shared-Nothing**: 각 샤드 노드가 CPU, RAM, 디스크를 독립적으로 소유하고 네트워크를 통해서만 협력하는 비공유 분산 아키텍처.

</details>

- 정의/개념: 단일 DB의 용량 및 처리량 한계를 극복하기 위해 **샤드 키(Shard Key)를 기준으로 데이터를 복수의 물리 DB 노드에 수평 분산**하는 아키텍처
- 배경/필요성: 수직 확장은 한 대의 하드웨어 상한에서 멈추고 그 지점에 가까워질수록 같은 성능을 사는 비용이 비선형으로 뛰므로, 샤드 키로 데이터를 나눠 상태를 공유하지 않는 노드에 배치함으로써 용량과 쓰기 처리량을 노드 수에 비례해 늘릴 필요

#### 한줄 요약
- 샤딩은 확장성을 얻는 대신 노드 경계를 넘는 조인과 트랜잭션을 잃으므로, 샤드 키 선택은 성능 튜닝이 아니라 어떤 질의를 포기할지를 확정하는 설계 결정이 된다.

## Ⅱ. 특징

<details><summary>용어 설명</summary>

- **Consistent Hashing(일관된 해싱)**: 노드 증설/삭제 시 전체 데이터 재배치 없이 $1/N$의 데이터만 최소 이동시키는 분산 해싱 알고리즘.
- **Data Skew(데이터 편향)**: 샤드 키 설계 오류로 특정 샤드 노드에만 트래픽과 데이터가 쏠려 핫스팟(Hotspot)이 발생하는 현상.

</details>

- 독립된 물리 서버를 지속 추가하여 무제한 증설 가능한 **Shared-Nothing 기반 수평 확장(Scale-Out)**
- 핫스팟과 편향을 방지하고 균등 분산을 유도하는 **고카디널리티 샤드 키(Shard Key) 설계**
- 노드 증감 시 대규모 데이터 리밸런싱 부하를 억제하는 **일관된 해싱(Consistent Hashing) 적용**

#### 한줄 요약
- Shared-Nothing 수평 확장과 일관된 해싱을 통해 대규모 읽기/쓰기 처리량을 선형 확장한다.

## Ⅲ. 구조 및 구성요소

<details><summary>용어 설명</summary>

- **샤드 라우터(Shard Router)**: 애플리케이션의 SQL 질의를 가로채어 샤드 키를 분석하고 대상 샤드 노드로 라우팅하는 미들웨어 (예: Vitess, ShardingSphere).

</details>

```text
[데이터베이스 샤딩 구성]
|-- 샤드 라우터
|-- 샤드 노드
|-- 메타데이터 카탈로그
`-- 리밸런서
```

선의 의미: 분산 저장·라우팅·재배치를 담당하는 구성

| 구성요소 | 책임 | 주요 특징 |
|:---|:---|:---|
| 샤드 라우터 (Router) | 샤드 키를 파싱하여 **해당 쿼리를 적절한 물리 DB 노드로 전달 (Routing)** | 애플리케이션에 단일 DB 뷰 제공 |
| 샤드 노드 (Shard Node) | 분할된 데이터 조각을 독립 저장하고 **로컬 트랜잭션 및 인덱스 고속 처리** | Shared-Nothing 완전 독립 인스턴스 |
| 메타데이터 카탈로그 | 샤드 노드 토폴로지 및 **일관된 해시 링(Hash Ring) 범위 구성 관리** | Zookeeper, etcd 기반 합의 관리 |
| 리밸런서 (Rebalancer) | 노드 추가/제거 시 **무중단 데이터 마이그레이션 및 파티션 재배치** | 백그라운드 CDC 기반 동기화 |

#### 한줄 요약
- 키를 노드로 바꾸는 매핑을 라우터와 카탈로그에 모아 두기에 애플리케이션은 분산을 몰라도 되지만, 그 매핑이 바뀌는 리밸런싱 순간에는 데이터 이동 비용이 전 노드로 번진다.

## Ⅳ. 흐름도

<details><summary>용어 설명</summary>

- **Scatter-Gather(분산 취합)**: 샤드 키가 조건절에 없을 때 모든 샤드 노드로 쿼리를 브로드캐스팅(Scatter)하고 결과를 모아 정렬(Gather)하는 고비용 패턴.

</details>

```text
클라이언트 SQL 질의 실행 (`SELECT * FROM Orders WHERE user_id = 1500`)
        │
   [샤드 키 추출] 샤드 라우터가 WHERE 절에서 `user_id = 1500` 파싱
        │
   [해시 링 매핑] 메타데이터 카탈로그의 Hash Ring 대조 -> 'Shard-02' 노드 매핑
        │
   [단일 노드 라우팅] Shard-02 물리 DB 인스턴스로만 SQL 직접 전송
        │
   [로컬 실행] Shard-02 노드가 로컬 B+Tree 인덱스로 초고속 조회 (0.5ms)
        │
   클라이언트에 결과 즉시 반환 (타 샤드 노드에는 부하 0)
```

#### 한줄 요약
- 샤드 키가 조건에 있으면 질의가 단일 노드로 좁혀지지만 없으면 모든 노드에 흩뿌린 뒤 결과를 모으는 경로가 되어 응답 시간이 가장 느린 노드에 통째로 묶인다.

## Ⅴ. 종류 및 비교

<details><summary>용어 설명</summary>

- **파티셔닝 vs 샤딩**: 단일 OS/DBMS 내부의 파일 분할(파티셔닝)과 다중 독립 서버 간 네트워크 분산(샤딩).

</details>

| 비교 항목 | 테이블 파티셔닝 (Partitioning) | 데이터베이스 샤딩 (Sharding) |
|:---|:---|:---|
| 분산 인프라 단위 | **단일 DB 서버 인스턴스 내부 파일 분할** | **복수의 독립된 물리/가상 서버 (Shared-Nothing)** |
| 하드웨어 자원 한계 | 단일 서버 CPU, RAM 한계에 종속됨 | **노드를 증설할수록 용량/처리량 선형 확장** |
| 분산 트랜잭션 오버헤드| 단일 DB 엔진 차원에서 ACID 100% 보장 | **2PC 분산 트랜잭션 또는 Saga 패턴 필요** |
| 조인(Join) 연산 | 단일 엔진 내 모든 테이블 간 자유로운 조인 | **교차 샤드 조인(Cross-Shard Join) 성능 급락** |

#### 한줄 요약
- 단일 인스턴스 관리는 파티셔닝, 물리적 한계를 초과하는 대규모 확장은 샤딩을 적용한다.

## Ⅵ. 실무 고려사항 및 대책

<details><summary>용어 설명</summary>

- **Cross-Shard Join**: 서로 다른 물리 DB 노드에 저장된 테이블 간의 조인으로 인해 네트워크 병목과 메모리 버퍼 고갈이 발생하는 문제.

</details>

| 문제 | 대책 | 효과 |
|:---|:---|:---|
| 교차 샤드 조인(Cross-Shard Join)으로 인한 네트워크 병목 | **동일 샤드 키 기준 테이블 코로케이션(Co-location) 및 비정규화** | 단일 노드 로컬 조인으로 전환 |
| 다중 샤드에 걸친 분산 트랜잭션(2PC) 성능 폭락 | **Saga Pattern 기반 보상 트랜잭션 및 아웃박스 이벤트 발행** | 2PC 락 블로킹 해소 및 고가용성 확보 |
| 노드별 Auto-Increment 시퀀스 충돌로 인한 PK 중복 | **Twitter Snowflake, UUID v7, TSID 기반 분산 ID 생성기 도입** | 전역 유일 정렬 ID 완벽 보장 |
| 샤드 키 없는 쿼리로 인한 Scatter-Gather 브로드캐스트 | **글로벌 보조 인덱스(GSI) 테이블을 별도 샤드로 분리 구성** | 불필요한 전체 샤드 스캔 차단 |

#### 한줄 요약
- 테이블 코로케이션, Saga 분산 트랜잭션, 분산 ID 생성기, GSI 분리로 샤딩 난제를 해결한다.

## Ⅶ. 결론

- 수평 확장은 **샤딩 아키텍처**, 편향 방지는 **일관된 해싱** 선택

#### 한줄 요약
- 데이터베이스 샤딩은 단일 인스턴스의 물리적 한계를 극복하고 데이터와 트래픽을 복수 노드로 수평 분산하는 궁극의 분산 영속성 아키텍처다.
