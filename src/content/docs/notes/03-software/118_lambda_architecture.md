## Ⅰ. 개요

<details><summary>용어 설명</summary>

- **람다 아키텍처**: 전체 이력의 정확성을 책임지는 배치 계층(Batch), 최신 데이터의 실시간성을 책임지는 속도 계층(Speed), 두 결과를 통합 서빙하는 계층(Serving)의 3단 구조.
- **Nathan Marz**: 람다 아키텍처를 창안한 엔지니어로, 불변 마스터 데이터셋과 이중 파이프라인 개념을 정립.

</details>

- 정의/개념: **배치·속도·서빙 계층**을 결합해 이력과 최신 데이터를 처리하는 구조
- 배경/필요성: 스트리밍만으로 처리하면 로직이 바뀌거나 지연 이벤트가 들어왔을 때 과거 구간을 다시 계산할 수단이 없어 오차가 그대로 누적되므로, 불변 원천 로그를 남겨 두고 정확성을 맡는 배치 계층과 최신성을 맡는 속도 계층을 나란히 두어 서빙 시점에 합칠 필요

#### 한줄 요약
- 람다는 정확성과 최신성을 동시에 얻는 대신 같은 로직을 두 계층에 중복 구현하게 하므로, 그 이중 유지 비용이 이력 재계산의 가치를 넘어서는 순간 카파로 단순화하는 편이 낫다.

## Ⅱ. 특징

<details><summary>용어 설명</summary>

- **Immutable Master Dataset**: 원본 데이터를 절대 수정하지 않고 Append-Only로 영구 보존하여 언제든 배치 전면 재계산(Recomputation)을 보장.
- **Eventual Exactness**: 속도 계층 결과를 배치 재계산 결과로 대체해 오차를 정정하는 성질.

</details>

- 불변 원천 데이터 기반 **전면 재계산** 지원
- 속도 계층 결과를 배치 계산으로 **사후 정정**
- 배치와 스트리밍의 이중 구축으로 인한 **이중 코드베이스(Code Drift) 관리 부담**

#### 한줄 요약
- 불변 원천 데이터와 이중 연산 계층을 통해 정확성과 실시간성을 동시에 달성한다.

## Ⅲ. 구조 및 구성요소

<details><summary>용어 설명</summary>

- **Batch View & Real-time View**: 배치 계층이 HDFS/Spark로 사전 계산한 불변 뷰와 속도 계층이 Flink/Storm으로 계산한 최신 증분 뷰.

</details>

```text
[람다 아키텍처]
|-- 불변 원천 데이터
|-- 배치 계층
|   `-- 배치 뷰
|-- 속도 계층
|   `-- 실시간 뷰
`-- 서빙 계층
```

선의 의미: 계층 및 데이터가 배치와 속도 계층으로 분기되어 연산된 후 서빙 계층에서 통합되는 구조

| 구성요소 | 책임 |
|:---|:---|
| 불변 원천 데이터 | 재계산 가능한 원시 이벤트 보관 |
| 배치 계층 | 전체 이력으로 **배치 뷰** 생성 |
| 속도 계층 | 배치 미반영 구간의 **실시간 뷰** 생성 |
| 서빙 계층 | 배치·실시간 뷰의 조회 결과 통합 |

#### 한줄 요약
- 원천 데이터를 불변으로 남기는 결정 하나가 배치 재계산을 가능하게 만드는 근거이므로, 다른 계층을 어떻게 바꾸더라도 원천 로그의 불변성이 깨지면 구조 전체가 성립하지 않는다.

## Ⅳ. 흐름도

<details><summary>용어 설명</summary>

- **Time-Boundary Cutoff**: 서비스 계층에서 배치 뷰의 완료 시점(Timestamp)을 기준으로 겹치는 실시간 스트림 데이터를 중복 제거하는 메커니즘.

</details>

```text
새로운 비즈니스 이벤트 발생 및 수집
        │
   [불변 마스터 저장] Kafka를 거쳐 S3/HDFS 불변 로그 스토리지에 Append-Only 기록
        │
   ┌────┴───────────────────────────┐
[배치 계층]                     [속도 계층]
Spark가 전체 이력 일괄 집계     Flink가 최근 미반영 스트림 즉시 증분 집계
(전체 이력 기반 뷰)             (최신 증분 뷰)
        │                               │
   └────┬───────────────────────────┘
        ▼
   [타임스탬프 컷오프] 서비스 계층에서 배치 뷰 완료 시점을 기준으로 중복 구간 제거
        │
   클라이언트 질의에 배치 뷰와 실시간 뷰를 병합해 반환
```

#### 한줄 요약
- 두 계층이 같은 이벤트를 중복 계산하기에 컷오프 시점을 어디로 잡느냐가 중복 집계와 누락을 가르며, 그 경계 관리 비용이 람다 운영 난이도의 대부분을 차지한다.

## Ⅴ. 종류 및 비교

<details><summary>용어 설명</summary>

- **람다 vs 카파 아키텍처**: 배치와 속도의 이중 파이프라인(람다)과 배치 계층을 제거하고 단일 스트림 엔진으로 통일한 카파(Kappa).

</details>

| 비교 항목 | 람다 아키텍처 (Lambda Architecture) | 카파 아키텍처 (Kappa Architecture) |
|:---|:---|:---|
| 파이프라인 구성 | **이중 파이프라인 (Batch Layer + Speed Layer)**| **단일 스트림 파이프라인 (Stream Processing Only)**|
| 과거 데이터 재처리 | 배치 엔진(Spark)을 통해 전체 이력 재계산 | **Kafka 로그 보존 주기를 늘려 스트림 재생(Replay)**|
| 코드 및 운영 복잡도| **이중 코드베이스 작성 및 동기화 부담 큼** | **단일 코드베이스(Flink)로 운영 복잡도 대폭 감소** |
| 적용 분야 | **이력 재계산·최신 뷰 병행** | **로그 재생 기반 단일 스트림 처리** |

#### 한줄 요약
- 이중 계층으로 정확성을 보장하는 람다와 단일 스트림 엔진으로 운영을 단순화한 카파를 비교한다.

## Ⅵ. 실무 고려사항 및 대책

<details><summary>용어 설명</summary>

- **Code Drift**: 배치 로직과 스트림 로직을 서로 다른 언어나 프레임워크로 구현하여 비즈니스 계산 결과가 미세하게 어긋나는 현상.

</details>

| 문제 | 대책 | 효과 |
|:---|:---|:---|
| 배치·스트림 로직의 **Code Drift** | 공통 API·함수로 계산 로직 공유 | 이중 구현의 결과 차이 감소 |
| 배치·실시간 뷰의 중복 합산 | **워터마크·타임스탬프 컷오프** 적용 | 중복 구간 식별과 제외 |
| 배치·스트림 이중 인프라 비용 | **카파·레이크하우스** 전환 검토 | 운영 구성요소 수 감소 |
| 서빙 계층 질의 시 다중 DB 룩업 지연 | **인메모리 캐시(Redis) 계층 전면 배치 및 병렬 서브쿼리 실행** | 사용자 체감 응답 속도 최적화 |

#### 한줄 요약
- 단일 API 공통화, 워터마크 컷오프, 레이크하우스 전환, 서빙 캐시로 람다의 한계를 보완한다.

## Ⅶ. 결론

- 전체 재계산 병행은 **람다**, 단일 재생 흐름은 **카파** 선택

#### 한줄 요약
- 이력 재계산 가치가 이중 파이프라인 비용보다 클 때 람다를 적용한다.
