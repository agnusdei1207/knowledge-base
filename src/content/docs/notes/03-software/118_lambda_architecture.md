## Ⅰ. 개요

<details><summary>용어 설명</summary>

- **람다 아키텍처 3대 계층**: 전체 불변 데이터를 일괄 처리하여 완벽한 정확성을 보장하는 배치 계층(Batch), 최신 스트림을 초저지연 처리하는 속도 계층(Speed), 두 뷰를 통합 쿼리로 병합하는 서비스 계층(Serving).
- **이력 재계산 및 분석 정확성 한계(Historical Recalculation Bottleneck)**: 실시간 스트리밍 단독 처리 시 장애나 버그 발생 시 과거 데이터를 소급 재처리하여 정확성을 맞추기 어려운 한계.

</details>

- 정의/개념: 대규모 데이터 처리에서 **정확성을 보장하는 배치 계층과 초저지연을 보장하는 속도 계층 및 통합 서비스 계층을 이중 구성**하는 빅데이터 아키텍처
- 배경/필요성: 실시간 스트리밍 단독 처리 시 발생하는 **전체 이력 재계산의 어려움, 과거 데이터 소급 정정 불가 및 분석 정확성 저하 위험** 직면

#### 한줄 요약

- 배치 계층의 완벽한 정확성과 속도 계층의 실시간성을 서비스 계층에서 융합하여 무결점 실시간 뷰를 제공

## Ⅱ. 특징

<details><summary>용어 설명</summary>

- **불변 원천 데이터(Immutable Master Dataset)**: 모든 원본 데이터를 절대 수정하지 않고 Append-Only로 영구 보존하여 언제든 전체 재계산이 가능한 기반.
- **이중 파이프라인 트레이드오프(Dual Codebase Overhead)**: 동일한 비즈니스 계산을 배치용(Spark)과 스트림용(Flink)으로 이중 개발·유지보수해야 하는 구조적 부담.

</details>

- 원천 데이터의 불변(Immutable) 보존 및 **전면 재계산(Re-computation) 지원**
- 속도 계층의 임시 계산 오차를 주기적 배치 계산으로 **100% 사후 정정(Eventually Exact)**
- 배치와 스트리밍의 이중 구축으로 인한 **개발 및 운영 오버헤드 존재**

#### 한줄 요약

- 불변 원천 데이터와 이중 연산 계층을 통해 분석의 정확성과 실시간 응답성을 동시에 달성

## Ⅲ. 구조 및 구성요소

<details><summary>용어 설명</summary>

- **Serving Layer 병합 메커니즘**: 클라이언트가 쿼리할 때 이미 생성된 사전 계산 Batch View와 실시간 Real-time View를 타임스탬프 경계 기준으로 합산 응답.

</details>

```text
[ 람다 아키텍처 3대 계층 파이프라인 구조도 ]

 ┌────────────────────────────────────────────────────────────────────────┐
 │                    [ 신규 스트림 데이터 원천 유입 ]                    │
 └───────────────────┬──────────────────────────────────┬─────────────────┘
                     │                                  │
                     ▼                                  ▼
 ┌───────────────────────────────────┐  ┌─────────────────────────────────┐
 │ [ 1. Batch Layer (Hadoop / Spark)]│  │ [ 2. Speed Layer (Flink / Storm)│
 │   - 전체 불변 이력 데이터 일괄 연산 │  │   - 최신 미반영 구간 실시간 연산│
 │   - 완벽한 정확성 (시간 단위 갱신) │  │   - 초저지연 임시 결과 생성    │
 └───────────────────┬───────────────┘  └───────────────┬─────────────────┘
                     │                                  │
                     ▼ (Batch View)                     ▼ (Real-time View)
 ┌───────────────────┴──────────────────────────────────┴─────────────────┐
 │ [ 3. Serving Layer (HBase / Cassandra) ]                               │
 │   - 클라이언트 쿼리 시 Batch View와 Real-time View를 시간 경계 병합 반환│
 └────────────────────────────────────────────────────────────────────────┘
```

선의 의미: 데이터 스트림이 배치 계층과 속도 계층으로 동시 분기되어 연산된 후 서비스 계층에서 통합 병합 조회되는 아키텍처.

| 구성요소 | 책임 |
|:---|:---|
| 원천 데이터셋 (Master) | 원시 이벤트를 불변(Immutable) 상태로 보관하여 **언제든 전면 재계산 보장** |
| 배치 계층 (Batch Layer) | 대규모 전체 이력 데이터를 주기로 일괄 연산하여 **100% 정확한 Batch View 생성** |
| 속도 계층 (Speed Layer) | 배치 처리 지연 구간의 최신 스트림 데이터를 **초저지연으로 즉시 계산하여 View 생성** |
| 서비스 계층 (Serving) | 배치 뷰와 실시간 뷰를 색인하고 **클라이언트 쿼리 시 두 결과를 실시간 병합 반환** |

#### 한줄 요약

- 원천 데이터, 배치 계층, 속도 계층, 서비스 계층이 결합하여 정확성과 최신성을 동시 충족

## Ⅳ. 흐름도

<details><summary>용어 설명</summary>

- **람다 데이터 처리 5단계 파이프라인**: 데이터 적재 $\to$ 전체 배치 연산 $\to$ 최신 증분 연산 $\to$ 시간 경계 컷오프 $\to$ 통합 뷰 서빙.

</details>

```text
[ 람다 아키텍처 5단계 데이터 처리 파이프라인 ]

 ┌────────────────────────────────────────┐
 │ 1. 신규 이벤트 수신 및 불변 저장소 기록│
 └───────────────────┬────────────────────┘
                     │
         ┌───────────┴───────────┐
         ▼                       ▼
 ┌───────────────────────┐ ┌───────────────────────┐
 │ 2. 전체 이력 배치 연산│ │ 3. 최신 실시간 증분   │
 │   (Spark/Hadoop)      │ │    연산 (Flink/Kafka) │
 └───────────┬───────────┘ └───────────┬───────────┘
         │                       │
         └───────────┬───────────┘
                     ▼
 ┌────────────────────────────────────────┐
 │ 4. 타임스탬프 기준 시간 경계 컷오프   │
 └───────────────────┬────────────────────┘
                     │
                     ▼
 ┌────────────────────────────────────────┐
 │ 5. 서비스 계층 통합 뷰 클라이언트 반환 │
 └────────────────────────────────────────┘
```

### 동작 원리

1. 데이터 적재: 유입되는 모든 원시 이벤트를 HDFS나 S3 불변 스토리지에 Append-Only로 영구 기록.
2. 배치 연산: 배치 계층이 전체 이력 데이터를 대상으로 주기적인 집계 연산을 수행하여 Batch View를 생성.
3. 증분 연산: 속도 계층이 최근 배치 실행 이후에 유입된 최신 데이터만 실시간 스트리밍으로 집계.
4. 시간 경계 컷오프: 서비스 계층이 배치 뷰의 최종 완료 시점(Timestamp)을 기준으로 겹치는 실시간 데이터를 중복 제거.
5. 통합 뷰 서빙: 최종 합산된 결과를 대시보드나 클라이언트 쿼리에 즉시 제공.

#### 한줄 요약

- 데이터 적재 $\to$ 배치/스트림 병렬 연산 $\to$ 시간 경계 컷오프 $\to$ 통합 뷰 서빙의 5단계

## Ⅴ. 종류 및 비교

<details><summary>용어 설명</summary>

- **람다 vs 카파 아키텍처**: 배치와 속도의 이중 파이프라인(람다)과 배치 계층을 제거하고 스트림 단일 엔진(카파)으로 통일한 구조.

</details>

| 구분 | 람다 아키텍처 (Lambda Architecture) | 카파 아키텍처 (Kappa Architecture) |
|:---|:---|:---|
| **적용 기준** | 전체 데이터의 완벽한 재계산 정확성이 절대적인 환경 | 빠른 개발 및 단일 스트림 파이프라인 운영 최적화 |
| **핵심 특징** | **이중 파이프라인 (Batch + Speed), 불변 데이터 재계산** | **단일 스트림 파이프라인 (Flink/Kafka Log Replay)** |
| **한계** | 배치와 스트림 로직의 이중 개발 및 유지보수 오버헤드 | 장기 과거 데이터 재생 시 브로커 스토리지 비용 증가 |

#### 한줄 요약

- 이중 계층으로 정확성을 보장하는 람다와 단일 스트림 엔진으로 운영을 단순화한 카파를 비교

## Ⅵ. 실무 고려사항 및 대책

<details><summary>용어 설명</summary>

- **코드 드리프트(Dual Codebase Drift)**: 배치용 코드와 스트림용 코드를 서로 다른 언어나 프레임워크로 작성하여 비즈니스 규칙이 어긋나는 현상.

</details>

| 문제 | 대책 | 효과 |
|:---|:---|:---|
| 배치와 스트림 로직 불일치로 인한 결과 왜곡 (Code Drift) | **Apache Beam 또는 Apache Flink 기반 통합 API 단일 로직 작성** | 이중 개발 방지 및 로직 일관성 보장 |
| 서비스 계층에서 배치 뷰와 실시간 뷰의 중복 합산 | **엄격한 워터마크(Watermark) 및 타임스탬프 컷오프 알고리즘 적용** | 데이터 중복 연산 원천 차단 |
| 하둡 클러스터와 스트리밍 클러스터의 이중 인프라 운영 비용 과다 | **현대적 카파 아키텍처 또는 레이크하우스 스트리밍 엔진으로 전환** | 인프라 운영 복잡도 50% 절감 |

#### 한줄 요약

- 통합 프레임워크 도입, 워터마크 컷오프, 레이크하우스 전환으로 람다의 구조적 한계를 보완

## Ⅶ. 결론

<details><summary>용어 설명</summary>

- **스트리밍 레이크하우스 진화(Streaming Lakehouse Evolution)**: Delta Lake, Apache Iceberg의 실시간 ACID 기능을 활용하여 람다와 카파를 통합하는 현대적 데이터 아키텍처.

</details>

- **람다 아키텍처**는 대규모 데이터 분석에서 정확성과 실시간성을 조화시킨 기념비적인 설계 패턴이며, 최근에는 Flink 단일 스트림 파이프라인(카파) 및 오픈 테이블 포맷 기반의 레이크하우스 아키텍처로 진화 발전하고 있음

#### 한줄 요약

- 배치와 속도 계층의 결합을 통해 빅데이터 분석의 정확성과 실시간성을 성공적으로 융합
