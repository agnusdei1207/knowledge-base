## Ⅰ. 개요

<details><summary>용어 설명</summary>

- **스크럼 프레임워크(Scrum Framework)**: 럭비에서 스크럼 짜듯 다 같이 뭉쳐서, 2~4주(Sprint) 단위로 짧게 치고 빠지면서 소프트웨어를 찍어내는 3-5-3(책무-이벤트-산출물) 국룰 애자일 방법론이다.
- **경험주의(Empiricism)**: "미리 계획 세워봤자 다 틀린다"는 팩트를 인정하고, 일단 만들어보고 눈으로 확인(투명성/점검)하면서 고쳐나가자(적응)는 스크럼의 근본 철학이다.
- **제품 증분(Product Increment)**: 매 스프린트(2주)가 끝날 때마다 당장 고객한테 던져주고 돈 받을 수 있을 만큼 완벽하게 돌아가는 완성품 조각이다.

</details>

- 정의: 완벽한 계획을 버리고, 3-5-3 구조로 짧게 치고 빠지며 매번 돌아가는 완성품(증분)을 찍어내는 **스크럼 프레임워크**
- 배경: 요즘 세상은 어제 기획한 게 오늘 바뀌는데, 옛날처럼 폭포수로 몇 달 치 계획을 세웠다간 **가정 오류 터지고 프로젝트 폭망**하기 때문

#### 한줄 요약

- 계획을 맹신하지 말고(경험주의), 3-5-3 뼈대 위에서 2주마다 완제품을 찍어내라는 실전 철학이다.

## Ⅱ. 특징

<details><summary>용어 설명</summary>

- **타임박싱(Timeboxing)**: 회의 길어지면 입만 털다 끝나니까, "데일리 스크럼 15분!" 하고 알람 울리면 말 허리 끊고 무조건 해산시키는 시간제한 룰이다.
- **교차기능 자율관리 팀(Cross-functional, Self-managing Team)**: 기획자 따로 개발자 따로 노는 게 아니라, 기획+디자인+개발+QA가 한 팀에 모여서 매니저 없이 알아서 굴러가는 드림팀이다.

</details>

- **경험주의 3기둥**(투명성, 점검, 적응)으로 현실을 직시함.
- 시간제한(**타임박싱**)을 걸어서 헛소리할 시간을 차단하고, 매니저 없이 구르는 **자율관리 교차기능 팀**으로 움직임.
- **3대 책무(역할), 5대 이벤트(회의), 3대 산출물(문서)**이라는 3-5-3 뼈대 위에서 돌아감.

#### 한줄 요약

- 시간제한(타임박스) 걸고, 매니저 없이 자율적으로 움직이며, 투명하게 결과를 까고 고친다.

## Ⅲ. 구조 및 구성요소

<details><summary>용어 설명</summary>

- **제품 책임자(Product Owner, PO)**: 고객 요구사항을 수집해서 "이거부터 만들자"라고 백로그 순위를 매기고, 제품의 흥망성쇠를 책임지는 미니 CEO이다.
- **스크럼 마스터(Scrum Master, SM)**: 팀이 딴짓 안 하고 스크럼 룰을 잘 지키는지 감시하고, 윗선에서 들어오는 태클(장애물)을 대신 맞아주는 탱커 겸 코치이다.

</details>

```text
[ 스크럼 3-5-3 십자포화 아키텍처 ]

[ 제품 책임자(PO) ] ──(우선순위 픽)──▶ [ 제품 백로그 ]
    │                                   │
  (코칭/보호)                           ▼
[ 스크럼 마스터(SM) ]            [ 스프린트 백로그 ]
    │                                   │
    ▼                                   ▼ (2주 코딩)
 [ 개발자들 ] ◀──────(증분 제작)──────▶ [ 제품 증분 ]
(기획/개발/QA)                        (고객 시연)
```

| 구성요소 | 역할 및 팩트폭력 |
|:---|:---|
| **제품 책임자 (PO)** | 제품 백로그 순위를 정하는 권력자이자, 결과물이 구리면 욕먹는 **1순위 타겟** |
| **스크럼 마스터 (SM)** | 팀이 헛짓거리 안 하게 룰을 가르치고, 외부 간섭(팀장 등)을 차단하는 **인간 방패** |
| **개발자 (Developers)** | 완료 정의(DoD)를 통과하는 작동 가능한 기능(증분)을 깎아내는 **실무 노예들** |
| **제품/스프린트 백로그** | PO가 관리하는 '전체 소원 수리함'과 개발팀이 이번 2주 동안 뺄 '할 일 목록' |
| **제품 증분 (Increment)** | 이번 스프린트에서 만들어낸, 바로 팔아먹을 수 있는 **완제품 조각** |

#### 한줄 요약

- PO가 일감을 던져주면, SM이 방패 쳐주고, 개발자들이 2주 동안 빡코딩해서 증분을 뱉어낸다.

## Ⅳ. 흐름도

<details><summary>용어 설명</summary>

- **스프린트 회고(Sprint Retrospective)**: 2주간의 개발이 끝나고 다 같이 모여서, "우리 이거 잘못했으니 다음부턴 이러지 말자"고 반성하고 프로세스를 고치는 자기 비판 시간이다.

</details>

```text
[ 스크럼 5대 이벤트 십자포화 흐름 ]
┌──────────────────────────────┐
│ 1. 스프린트 계획(Planning)   │
│ (이번 2주 동안 뭐 할지 픽함) │
└──────────────┬───────────────┘
               ▼ (스프린트 시작)
┌──────────────────────────────┐
│ 2. 일일 스크럼(Daily Scrum)  │
│ (매일 아침 15분 생존 신고)   │
└──────────────┬───────────────┘
               ▼ (스프린트 종료)
┌──────────────────────────────┐
│ 3. 스프린트 리뷰(Review)     │
│ (고객 불러놓고 결과물 시연)  │
└──────────────┬───────────────┘
               ▼
┌──────────────────────────────┐
│ 4. 스프린트 회고(Retro)      │
│ (잘못한 거 반성하고 룰 고침) │
└──────────────────────────────┘
※ 위 모든 과정(1~4)을 감싸는 하나의 큰 타임박스가 바로 [5. 스프린트]
```

### 동작 원리

1. 스프린트 계획: PO가 "이거 하자" 하면, 개발팀이 "어디까지 쳐낼 수 있다" 협상해서 할 일 픽스.
2. 일일 스크럼: 매일 아침 서서 15분 동안 "어제 뭐함? 오늘 뭐함? 막힌 거 있음?" 3가지만 털고 해산.
3. 스프린트 리뷰: 2주 끝났을 때 이해관계자 다 불러놓고 결과물 보여주며 피드백 받음.
4. 스프린트 회고: 회식하면서 "이거 최악이었으니 담주부턴 이렇게 바꾸자"고 룰을 튜닝함.

#### 한줄 요약

- 계획 세우고 $\to$ 매일 15분 회의하고 $\to$ 2주 뒤에 시연하고 $\to$ 반성회 하는 루프의 무한 반복이다.

## Ⅴ. 종류 및 비교

<details><summary>용어 설명</summary>

- **스프린트 속도(Velocity)**: 우리 팀이 2주 동안 기능(스토리 포인트)을 몇 개나 쳐낼 수 있는지 측정하는 전투력 수치이다.

</details>

| 비교 항목 | **Scrum** (스크럼) | **Kanban** (칸반) |
|:---|:---|:---|
| 핵심 마인드 | **타임박스 (무조건 2~4주 단위로 끊어!)** | **흐름 (WIP 제한 걸고 물 흐르듯 가자!)** |
| 중간에 엎기 | 스프린트 도중엔 **절대 못 바꿈** (대기) | 제한된 작업량(WIP) 안 넘치면 **언제든 쑤셔 넣음** |
| 전투력 측정 | **속도 (Velocity)**: 이번 스프린트에 몇 점 태웠나? | **리드 타임 (Lead Time)**: 부탁한 지 며칠 만에 나왔나? |
| 찰떡궁합 | 2주 단위 배포가 가능한 B2C 플랫폼, SaaS | 헬프데스크, 장애 대응, 운영 유지보수(SM) |

#### 한줄 요약

- 스크럼은 2주 단위로 딱 끊어서 박치기하고, 칸반은 한계치(WIP)만 걸어두고 끝없이 쳐낸다.

## Ⅵ. 실무 고려사항 및 대책

<details><summary>용어 설명</summary>

- **워터-스크럼-팔(Water-Scrum-Fall)**: 겉으론 스크럼 한다고 나대는데, 기획은 폭포수로 몇 달 치 짜놓고 배포도 1년에 한 번 하는 전형적인 '무늬만 애자일'의 끔찍한 변종이다.

</details>

| 문제 | 대책 | 효과 |
|:---|:---|:---|
| 일일 스크럼(15분)이 팀장한테 보고하는 지옥의 회의로 변질됨 | SM이 15분 넘으면 마이크 뺏고 **보고가 아닌 동기화(Sync)**로 바꿈 | 팀 자율성을 되찾고 시간 낭비 방지 |
| 코딩은 끝났는데 QA/배포 안 해서 작동하는 증분이 1도 없음 | "테스트 통과 안 하면 끝난 거 아님" 이라는 **완료 정의(DoD)** 멱살 잡음 | 쓰레기 코드를 막고 찐 배포 결과물 획득 |
| PO한테 권한이 없어서 백로그 바꾸는 데 본부장 결재받아 옴 | 조직도 씹고 PO한테 백로그 1순위 독재 권한을 주는 **책무 위임** | 의사결정 병목 뚫고 찐 애자일 속도 체감 |

#### 한줄 요약

- 일일 회의는 보고가 아니고, 테스트 안 하면 완료된 게 아니며, PO는 독재자여야 돌아간다.

## Ⅶ. 결론

<details><summary>용어 설명</summary>

- **스크럼 성숙도 기준(Scrum Maturity Criteria)**: 팀이 진짜 스크럼을 하는 건지 워터스크럼팔인지 가려내는 잣대이다. 3-5-3 룰을 지키는지, DoD를 깐깐하게 보는지 평가한다.

</details>

- **스크럼 성숙도 기준** 원칙에 따라, 2주 단위 배포가 가능한 프로덕트는 **Scrum**, 장애 처리처럼 수시로 일이 터지는 곳은 **Kanban** 채택 기조 확립함

#### 한줄 요약

- 무늬만 애자일 하지 말고, 3-5-3 규칙과 DoD(완료 정의)를 칼같이 지켜라.
