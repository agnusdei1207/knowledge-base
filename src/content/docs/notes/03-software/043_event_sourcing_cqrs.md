## Ⅰ. 개요

<details><summary>용어 설명</summary>

- **이벤트 소싱(Event Sourcing)**: 애플리케이션의 현재 상태를 직접 데이터베이스에 덮어쓰지 않고, 상태를 변화시키는 모든 도메인 사건(Event)을 불변의 순차적 로그로 저장하는 아키텍처 패턴.
- **CQRS(Command Query Responsibility Segregation)**: 시스템의 상태를 변경하는 명령(Command) 모델과 데이터를 조회하는 쿼리(Query) 모델의 책임을 명확히 분리하여 각각 최적화하는 설계 패턴.
- **이벤트 저장소(Event Store)**: 발생한 도메인 이벤트를 시간 순서대로 추가 전용(Append-Only) 방식으로 영속화하는 불변 저장소.

</details>

- 정의/개념: 상태 변화 이력을 불변 로그로 영속화하는 **이벤트 소싱(Event Sourcing)** 과 쓰기·읽기 데이터 모델을 분리하는 **CQRS**를 결합한 분산 데이터 아키텍처
- 배경/필요성: 전통적 CRUD 모델의 과거 이력 추적 한계, 동시성 갱신 충돌 및 읽기/쓰기 트래픽 비대칭으로 인한 단일 DB 병목 현상 해소 요구

#### 한줄 요약
- 상태 변경을 불변의 이벤트 로그로 기록하고, 명령과 조회 모델을 분리하여 확장성과 감사 추적성을 확보한다.

## Ⅱ. 특징

<details><summary>용어 설명</summary>

- **추가 전용 불변 로그(Append-Only Immutable Log)**: 수정(Update)이나 삭제(Delete) 없이 새로운 이벤트만을 추가하여 데이터 무결성을 보장하는 저장 방식.
- **최종 일관성(Eventual Consistency)**: 명령 처리 시점에 즉시 읽기 저장소와 동기화되지 않더라도, 비동기 이벤트 전파를 통해 결과적으로 데이터 정합성이 일치하게 되는 모델.

</details>

- **추가 전용(Append-Only)** 이벤트 저장을 통한 완벽한 감사 추적(Audit Trail) 및 임의 시점 상태 재생(Replay) 지원
- 명령(Command)과 쿼리(Query) 데이터베이스의 물리적 분리를 통한 독립적 수평 확장(Scale-out)
- 비동기 프로젝션에 따른 **최종 일관성(Eventual Consistency)** 수용 및 성능 저하 방지를 위한 **스냅샷(Snapshotting)** 활용

#### 한줄 요약
- 불변 로그를 통한 상태 재구성과 모델 분리를 지원하며, 최종 일관성 기반으로 고성능을 제공한다.

## Ⅲ. 구조 및 구성요소

<details><summary>용어 설명</summary>

- **프로젝션(Projection)**: 이벤트 저장소에 기록된 원시 도메인 이벤트를 구독하여 화면 조회에 최적화된 읽기 전용 뷰(Read Model)로 변환하는 비동기 처리 프로세스.
- **스냅샷(Snapshotting)**: 대량의 이벤트를 처음부터 순차 재생하는 오버헤드를 줄이기 위해 특정 주기마다 애그리게잇의 중간 상태를 저장하는 최적화 기법.

</details>

```text
[ 클라이언트 ] ───(명령 발행)───▶ [ 명령 처리기 (Command Handler) ]
                                          │
                                          ▼ (Append-Only)
                                  [ 이벤트 저장소 (Event Store) ]
                                          │
                                          ▼ (비동기 이벤트 발행)
[ 클라이언트 ] ◀───(조회 수행)─── [ 읽기 전용 뷰 DB (Read Model) ] ◀── [ 프로젝션 엔진 ]
```

선의 의미: 상단은 명령 검증 및 이벤트 저장 흐름, 하단은 비동기 프로젝션을 통한 읽기 뷰 갱신 및 조회 경로

| 구성요소 | 책임 |
|:---|:---|
| **명령(Command) 모델** | 비즈니스 규칙 및 불변식을 검증하고 도메인 상태 변경 이벤트를 생성 |
| **이벤트 저장소(Event Store)** | 생성된 도메인 이벤트를 시간 순서대로 원자적(Append-Only)으로 영속화 |
| **프로젝션(Projection) 엔진** | 이벤트 스트림을 소비하여 조회 요구사항에 최적화된 읽기 모델 갱신 |
| **조회(Query) 모델** | 조인 연산 없이 고속 조회가 가능하도록 비정규화된 읽기 전용 데이터베이스 |

#### 한줄 요약
- 명령 모델이 이벤트를 저장소에 기록하면, 프로젝션 엔진이 비동기로 읽기 뷰를 갱신하여 조회를 처리한다.

## Ⅳ. 흐름도

<details><summary>용어 설명</summary>

- **이벤트 재생(Event Replay)**: 이벤트 저장소에 누적된 과거 이벤트를 순차적으로 재실행하여 애그리게잇 상태를 복원하거나 신규 읽기 뷰를 생성하는 기법.

</details>

```text
1. 상태 변경 명령(Command) 수신 및 유효성 검증
            │
            ▼
2. 도메인 이벤트 생성: 과거형 명사(예: OrderPlaced)로 불변 이벤트 생성
            │
            ▼
3. 이벤트 저장소 영속화: Append-Only 방식으로 이벤트 원자적 커밋
            │
            ▼ (메시지 브로커를 통한 비동기 전파)
4. 프로젝션 엔진 변환: 이벤트를 해석하여 읽기 뷰 스키마에 맞게 비정규화 가공
            │
            ▼
5. 조회 데이터베이스(Query DB) 갱신: 클라이언트가 참조할 최종 뷰 데이터 반영
```

**동작 원리**

1. **명령 수신 및 검증**: 클라이언트의 비즈니스 요청을 수신하여 현재 상태 기반 도메인 유효성 검증
2. **이벤트 생성**: 변경 사실을 나타내는 불변의 도메인 이벤트(Domain Event) 생성
3. **이벤트 저장**: 이벤트 저장소에 순차적 버전 번호와 타임스탬프를 부여하여 영속화
4. **비동기 프로젝션**: 메시지 브로커(Kafka 등)를 통해 전달된 이벤트를 프로젝션 엔진이 구독하여 읽기 스키마로 변환
5. **조회 뷰 갱신**: 읽기 전용 데이터베이스(Redis, RDBMS 등)를 업데이트하여 고속 쿼리 서비스 제공

#### 한줄 요약
- 명령 검증 후 이벤트를 저장소에 기록하고, 비동기 프로젝션을 통해 조회 데이터베이스를 갱신한다.

## Ⅴ. 종류 및 비교

<details><summary>용어 설명</summary>

- **단순 CQRS**: 단일 데이터베이스 내에서 쓰기 모델과 읽기 모델의 코드 계층만 분리하거나, RDBMS 복제본(Read Replica)을 활용하는 형태.
- **이벤트 소싱 결합 CQRS**: 쓰기 데이터베이스 자체를 이벤트 로그 저장소로 구성하고 비동기 프로젝션으로 읽기 모델을 구축하는 완전 분리 형태.

</details>

| 비교 항목 | 전통적 CRUD 아키텍처 | 단순 CQRS 아키텍처 | 이벤트 소싱 + CQRS 아키텍처 |
|:---|:---|:---|:---|
| **적용 기준** | 단순 트랜잭션, 정적 CRUD 업무 | 읽기 트래픽 집중 시스템 | 금융, 결제, 정밀 감사 및 시계열 추적 필요 시스템 |
| **상태 저장 방식** | 현재 상태 값만 덮어쓰기(Overwrite) | 현재 상태 기반 RDBMS/NoSQL 분리 | 모든 상태 변경 이벤트의 불변 누적(Append-Only) |
| **감사 추적성** | 별도 감사 로그 테이블 추가 필요 | 별도 감사 로그 유지 필요 | 이벤트 자체가 완전한 감사 로그로 동작 |
| **데이터 정합성** | 강한 일관성(ACID) 보장 | 복제 지연에 따른 최종 일관성 | 비동기 프로젝션에 따른 **최종 일관성** 수용 |

#### 한줄 요약
- 단순 조회 최적화에는 단순 CQRS를, 완전한 감사 추적과 상태 재구성이 요구될 때는 이벤트 소싱 결합 CQRS를 적용한다.

## Ⅵ. 실무 고려사항 및 대책

<details><summary>용어 설명</summary>

- **업캐스팅(Upcasting)**: 비즈니스 요구 변화로 이벤트 스키마가 변경되었을 때, 런타임에 과거 버전 이벤트를 최신 버전 스키마로 실시간 변환하는 기법.

</details>

| 문제 | 대책 | 효과 |
|:---|:---|:---|
| 누적 이벤트 증가로 인한 상태 복원(Replay) 지연 | 주기적 **스냅샷(Snapshotting)** 저장 및 최신 스냅샷 이후 이벤트만 재생 | 애그리게잇 로딩 속도 최적화 및 복원 시간 단축 |
| 도메인 요구 변경에 따른 이벤트 스키마 불일치 | 스키마 레지스트리 관리 및 변환 계층인 **업캐스터(Upcaster)** 적용 | 과거 이벤트 영속성 유지 및 하위 호환성 보장 |
| 비동기 프로젝션 지연으로 인한 쓰기 직후 조회 불일치 | 클라이언트 낙관적 UI 갱신 또는 **Read-Your-Writes** 토큰 동기화 | 사용자 경험 저하 방지 및 정합성 체감 유지 |

#### 한줄 요약
- 스냅샷을 통한 재생 속도 최적화, 업캐스터를 통한 스키마 호환성 유지, Read-Your-Writes 동기화로 일관성을 보완한다.

## Ⅶ. 결론

- 엄격한 규제 준수와 거래 이력 추적이 필수적인 금융·주문 도메인에는 **이벤트 소싱과 CQRS** 결합 모델을 도입하되, 스냅샷 주기 설정과 이벤트 버저닝 거버넌스를 수립하여 시스템 복잡도와 정합성 오버헤드를 통제

#### 한줄 요약
- 변경 이력의 비즈니스 가치와 트래픽 특성을 평가하여 이벤트 소싱과 CQRS 아키텍처를 선별 적용한다.
