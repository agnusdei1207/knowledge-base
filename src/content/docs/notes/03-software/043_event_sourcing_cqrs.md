## Ⅰ. 개요

<details><summary>용어 설명</summary>

- **이벤트 소싱(Event Sourcing)**: 데이터베이스에 "현재 잔액 5만 원"이라고 덮어쓰는 게 아니라, "10만 원 입금", "5만 원 출금" 같은 '사건(이벤트)'들의 로그를 시간순으로 쌓아서 원본으로 삼는 통장 거래내역 같은 아키텍처이다.
- **CQRS(명령/조회 책임 분리)**: 데이터를 바꾸는(Insert/Update/Delete) 쓰기 모델(Command)과 데이터를 화면에 뿌리는 읽기 모델(Query)을 완전히 갈라치기 해서, 트래픽에 맞게 각각 스케일링하는 설계 패턴이다.
- **이벤트 저장소(Event Store)**: 이벤트 소싱에서 UPDATE나 DELETE 없이, 오직 뒤에 덧붙이기(Append-Only) 방식으로만 로그를 쑤셔 넣는 불변의 이벤트 전용 DB이다.

</details>

- 정의: 상태를 덮어쓰지 않고 변경 이벤트 자체를 차곡차곡 쌓는(Event Sourcing) 동시에, 쓰는 DB와 읽는 DB를 갈라치기(CQRS)하는 백엔드 궁극의 분산 패턴
- 배경: 덮어쓰기(CRUD) 방식은 **"이 데이터가 옛날에 왜 이렇게 바뀌었지?"라는 과거 이력 추적이 불가능**하며, 읽기 트래픽 폭주 시 쓰기 DB까지 같이 터지기 때문

#### 한줄 요약

- 덮어쓰지 않고 변경 내역을 싹 다 쌓아두고(이벤트 소싱), 쓰는 놈과 읽는 놈을 찢어버린다(CQRS).

## Ⅱ. 특징

<details><summary>용어 설명</summary>

- **추가 전용(Append-Only) 불변 이벤트**: 한 번 뱉은 사건은 절대 수정/삭제하지 않고, 만약 취소해야 하면 '취소 이벤트'를 하나 더 뒤에 덧붙여서 보상(Compensating)하는 원칙이다.
- **최종 일관성(Eventual Consistency)**: 쓰기 DB에 이벤트가 쌓이고 읽기 DB로 동기화(복사)되는 데 0.1초 정도 시차가 발생하지만, 언젠간(Eventual) 결과적으로 두 DB 데이터가 같아진다는 타협점이다.

</details>

- UPDATE/DELETE 없이 무조건 **Append-Only** 기반 밀어 넣어서 완벽한 감사(Audit) 추적과 타임머신(상태 재구성)을 지원함.
- 트래픽 90%를 차지하는 읽기(Query) DB만 따로 수평 확장(Scale-out)할 수 있어서 가성비가 지림.
- 데이터 씽크가 바로 안 맞는 **최종 일관성(Eventual Consistency)** 을 감수해야 하며, 너무 쌓이면 성능이 급격한 저하하므로 **스냅샷(Snapshotting)** 을 찍음.

#### 한줄 요약

- 로그만 계속 쌓아서 타임머신이 가능하고, 읽기/쓰기 성능을 따로 올릴 수 있는 대신 씽크(시차)가 안 맞을 수 있다.

## Ⅲ. 구조 및 구성요소

<details><summary>용어 설명</summary>

- **프로젝션(Projection)**: 텍스트로 쌓여있는 이벤트 로그(쓰기 DB)를 쫙 빨아들여서, 유저가 보기 편하게 표나 그래프 형태로 가공한 뒤 읽기 DB(Query)로 밀어 넣는 영사기 같은 작업이다.
- **스냅샷(Snapshotting)**: 이벤트가 100만 개 쌓이면 처음부터 다 읽어서 잔액을 계산하기 빡세니까, "1만 번째 이벤트 시점 잔액: 5만 원"처럼 중간 저장(세이브포인트)을 찍어두는 최적화 꼼수이다.

</details>

```text
[ 이벤트 소싱 + CQRS 십자포화 아키텍처 ]

[ 명령(Command) API ] ──(Create/Update)──▶ [ 이벤트 스토어 (쓰기 전용 DB) ]
                                                │ (Append-Only)
                                                ▼
(메시지 브로커 - Kafka) ◀──(이벤트 동기화)── [ 프로젝션(Projection) 엔진 ]
                                                │ (데이터 가공)
                                                ▼
[ 조회(Query) API ]   ◀──(Read)───────── [ 읽기 전용 뷰 DB (Redis, ES) ]
```

| 구성요소 | 책임 |
|:---|:---|
| **명령(Command) 모델** | 유저가 "물건 사겠다"고 찌르면 검증하고 이벤트를 만들어내는 쓰기 담당 일진 |
| **이벤트 스토어 (DB)** | 생성된 이벤트를 순서대로 시간 도장 찍어서(버전) 영원히 박제하는 창고 |
| **프로젝션 (엔진)** | 박제된 이벤트를 읽어서 "그래서 현재 유저 포인트는 얼만데?"를 계산해 내는 통역사 |
| **조회(Query) 모델** | 화면에 뿌려주기 좋게 비정규화된 상태로 가공된 초고속 읽기 전용 DB |

#### 단답 요약

- 이벤트 스토어(쓰기 전용)에 로그를 쌓으면, 프로젝션이 가공해서 뷰 DB(읽기 전용)로 꽂아준다.

## Ⅳ. 흐름도

<details><summary>용어 설명</summary>

- **이벤트 재생(Replay)**: 신규 기능(통계 화면 등)을 만들어서 새로운 읽기 DB가 필요할 때, 옛날 1번 이벤트부터 지금까지 저장된 모든 이벤트를 다시 쫙 틀어줘서(Replay) 뷰를 순식간에 복원해 내는 타임머신 기술이다.

</details>

```text
[ Event Sourcing & CQRS 십자포화 흐름 ]
┌──────────────────────────────┐
│ 1. 상태 변경 명령 (Command)  │
│ (유저가 5만원 송금 버튼 누름)│
└──────────────┬───────────────┘
               ▼
┌──────────────────────────────┐
│ 2. 유효성 검증 및 이벤트 생성│
│ (통장 잔고 5만원 넘는지 확인)│
└──────────────┬───────────────┘
               ▼
┌──────────────────────────────┐
│ 3. 이벤트 스토어 Append      │
│ (송금 이벤트 박제 완료)      │
└──────────────┬───────────────┘
               ▼ (비동기 전파)
┌──────────────────────────────┐
│ 4. 프로젝션 뷰 변환          │
│ (조회용 DB 포맷으로 가공)    │
└──────────────┬───────────────┘
               ▼
┌──────────────────────────────┐
│ 5. 조회 DB (Query) 반영      │
│ (빠른 조회를 위해 DB 세팅)   │
└──────────────────────────────┘
```

### 동작 원리

1. 명령 및 검증: 변경 요청이 오면 룰을 검사함.
2. 이벤트 생성: "송금됨"이라는 과거형 불변 이벤트를 만듦.
3. 스토어 저장: 이벤트 스토어에 차곡차곡 Append-Only로 쌓음.
4. 비동기 전파 및 프로젝션: 카프카 같은 브로커가 이벤트를 물어다 조회 DB 입맛에 맞게 비벼줌.
5. 조회 DB 갱신: 읽기 트래픽 100만 건이 쏟아져도 끄떡없는 조회 DB에 최종 결과물이 꽂힘.

#### 한줄 요약

- 명령 $\to$ 이벤트 생성/박제 $\to$ 비동기 가공(프로젝션) $\to$ 읽기 DB 반영 흐름이다.

## Ⅴ. 종류 및 비교

<details><summary>용어 설명</summary>

- **순수 CQRS vs 이벤트 소싱 기반 CQRS**: 단순 CQRS는 그냥 쓰기 DB와 읽기 DB만 쪼개서 성능만 올린 거고, 이벤트 소싱 CQRS는 쓰기 DB를 아예 이벤트(과거 내역) 창고로 바꿔서 완벽한 감사(Audit)까지 챙긴 궁극체이다.

</details>

| 구분 | **전통적 CRUD 아키텍처** | **Event Sourcing + CQRS** |
|:---|:---|:---|
| 데이터 저장 상태 | 현재 팩트만 남고 과거는 덮어씌워짐 (휘발성) | **모든 과거 상태 변경 로그가 완벽히 박제됨 (영속성)** |
| 감사(Audit) 추적 | 별도 로그 테이블을 구질구질하게 파야 됨 | 이벤트 자체가 로그라서 **타임머신(Replay) 완전 지원** |
| 확장성 (Scaling) | 읽기와 쓰기가 한 DB에서 강력히 싸움 | 읽기 DB만 100대 띄우는 등 **극한의 독립 확장 가능** |
| 개발/운영 난이도 | 직관적이고 쉬움 (국밥) | **최종 일관성(시차 방어), 버전 관리 등 난이도 극악** |

#### 한줄 요약

- CRUD는 덮어쓰기라 편하지만 과거 이력이 날아가고, 이벤트 소싱은 어렵지만 타임머신이 된다.

## Ⅵ. 실무 고려사항 및 대책

<details><summary>용어 설명</summary>

- **이벤트 버저닝(Event Versioning)**: 작년에 저장한 '회원가입' 이벤트엔 이메일이 없었는데, 올해 바뀐 이벤트엔 이메일이 필수일 때, 옛날 이벤트를 읽어도 뻗지 않게 변환기(Upcaster)를 짜서 땜빵하는 호환성 똥꼬쇼이다.

</details>

| 문제 | 대책 | 효과 |
|:---|:---|:---|
| 이벤트가 수억 개 쌓여서 잔액 재계산(Replay)하면 하루 종일 걸림 | 주기적으로 **스냅샷(Snapshotting)** 찍어서 저장 (세이브포인트) | 상태 복원(부팅) 속도 압도적 단축 |
| 비즈니스 바뀌면서 이벤트 스키마가 변해서 옛날 거 못 읽음 | 낡은 이벤트를 최신으로 강제 형변환하는 **Upcaster** 떡칠 | 낡은 데이터 버릴 필요 없이 **하위 호환성 유지** |
| 방금 돈 썼는데 화면 새로고침하니 시차 때문에 돈이 그대로임 | 프론트에서 먼저 까거나 **Read-your-writes** 꼼수 씀 | 유저가 버그로 착각하는 UX 파탄 방지 |

#### 한줄 요약

- 복원 속도는 스냅샷으로, 낡은 데이터는 업캐스터(Upcaster)로, 씽크 시차는 프론트 단에서 땜빵해라.

## Ⅶ. 결론

<details><summary>용어 설명</summary>

- **이벤트 소싱/CQRS 도입 판정 기준(Event Sourcing CQRS Criteria)**: 변경 이력이 돈과 직결되는지(금융, 결제), 읽기와 쓰기 트래픽 비율이 100:1 이상으로 극단적인지 각을 재서 헬파티(복잡도)를 감수할지 정하는 잣대이다.

</details>

- **이벤트 소싱 CQRS 도입 판정 기준** 원칙에 따라, 과거 이력 감사가 목숨줄인 금융/증권 트랜잭션은 **Event Sourcing + CQRS**, 단순 게시판은 걍 **CRUD** 채택 기조 확립함

#### 한줄 요약

- 트래픽 빡세고 과거 이력이 털리면 철창가는 금융권에서나 쓸법한 복잡한 놈이다. 함부로 쓰지 마라.
