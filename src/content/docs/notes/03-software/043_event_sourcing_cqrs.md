## Ⅰ. 개요

<details><summary>용어 설명</summary>

- **이벤트 소싱(Event Sourcing)**: 현재 상태를 덮어쓰지 않고 발생한 모든 도메인 사건(Event)을 불변의 추가 전용(Append-Only) 로그로 저장하는 패턴.
- **CQRS(Command Query Responsibility Segregation)**: 상태를 변경하는 쓰기(Command) 모델과 데이터를 조회하는 읽기(Query) 모델을 물리적으로 분리하는 설계.

</details>

- 정의/개념: 상태 변화를 불변 이벤트 로그로 저장하는 **이벤트 소싱**과 쓰기·읽기 모델을 분리하는 **CQRS**를 결합한 분산 아키텍처
- 배경/필요성: 전통적 CRUD 덮어쓰기 모델의 **과거 변경 이력 추적 불가 및 대규모 읽기/쓰기 비대칭 트래픽 병목 해결 불가**

#### 한줄 요약
- 상태 변경을 불변 이벤트로 기록하고, 쓰기와 조회를 분리하여 확장성과 완벽한 감사 추적성을 확보한다.

## Ⅱ. 특징

<details><summary>용어 설명</summary>

- **Append-Only 불변 로그**: UPDATE/DELETE 연산 없이 신규 이벤트만을 시간 순서대로 INSERT하여 데이터 무결성을 보장하는 저장 방식.
- **프로젝션(Projection)**: 원시 도메인 이벤트를 비동기로 구독하여 조인 없는 초고속 조회가 가능한 읽기 전용 뷰(Read Model)로 변환하는 과정.

</details>

- **추가 전용(Append-Only)** 이벤트 저장을 통한 100% 감사 추적(Audit Trail) 및 시점 복원(Replay) 지원
- 명령(Command: RDBMS)과 쿼리(Query: NoSQL/Redis)의 **물리적 분리 및 독립적 스케일아웃**
- 비동기 이벤트 전파에 따른 **최종 일관성(Eventual Consistency)** 수용 및 **스냅샷(Snapshotting)** 최적화

#### 한줄 요약
- 불변 로그를 통한 상태 재생과 쓰기/조회 모델 분리로 고성능 최종 일관성을 실현한다.

## Ⅲ. 구조 및 구성요소

<details><summary>용어 설명</summary>

- **스냅샷(Snapshot)**: 수천 개의 이벤트를 매번 처음부터 Replay하는 지연을 없애기 위해 주기적으로 도메인 객체의 현재 상태를 압축 저장하는 기법.

</details>

```text
[이벤트 소싱 & CQRS 아키텍처]
|-- 쓰기 파이프라인 (Command Side)
|   |-- 클라이언트 변경 명령 (Command: CreateOrder)
|   |-- 커맨드 핸들러 (비즈니스 규칙 검증 및 도메인 이벤트 생성)
|   `-- 이벤트 저장소 (Event Store: Append-Only 불변 로그 DB)
|-- 메시지 브로커 & 프로젝션 엔진 (Kafka / RabbitMQ -> 비동기 이벤트 스트리밍)
`-- 읽기 파이프라인 (Query Side)
    |-- 프로젝션 핸들러 (이벤트를 역정규화 뷰 모델로 변환)
    |-- 조회 전용 DB (Read Model: MongoDB, Elasticsearch, Redis)
    `-- 클라이언트 쿼리 요청 (Query: GetOrderDetails -> 초고속 조회)
```

선의 의미: 계층 및 Command-Event-Query 비동기 파이프라인

| 구성요소 | 책임 |
|:---|:---|
| 커맨드 핸들러 (Command) | 비즈니스 불변식을 검증하고 상태 변경을 나타내는 **도메인 이벤트 생성** |
| 이벤트 저장소 (Event Store) | 도메인 이벤트를 시간 순으로 **원자적(Append-Only) 영속화** 및 스냅샷 관리 |
| 프로젝션 엔진 (Projection) | 이벤트 스트림을 구독하여 화면 요구사항에 최적화된 **비정규화 읽기 뷰 갱신** |
| 조회 모델 (Query DB) | 복잡한 RDBMS 조인 없이 $O(1)$로 단건/목록 조회가 가능한 **읽기 전용 NoSQL/캐시** |

#### 한줄 요약
- Command 핸들러, 불변 Event Store, 비동기 프로젝션 엔진, 조회 전용 Query DB가 결합된다.

## Ⅳ. 흐름도

<details><summary>용어 설명</summary>

- **Event Replay(이벤트 재생)**: 누적된 과거 이벤트를 1번부터 차례대로 메모리 객체에 적용하여 특정 시점 또는 최신 상태를 복원하는 과정.

</details>

```text
클라이언트 주문 생성 요청 (Command)
        │
   커맨드 핸들러가 유효성 검증 후 '주문생성됨(OrderCreated)' 도메인 이벤트 생성
        │
   이벤트 저장소(Event Store)에 불변 로그로 Append (쓰기 트랜잭션 커밋 완료)
        │
   Kafka 이벤트 브로커로 '주문생성됨' 이벤트 비동기 발행
        │
   프로젝션 엔진이 이벤트를 수신하여 조회용 Elastic/Redis 스키마로 변환
        │
   조회 DB에 비정규화된 주문 뷰 레코드 저장 (최종 일관성 도달)
        │
   클라이언트가 주문 목록 조회 시 Query DB에서 직접 즉시 반환 (조인 연산 0)
```

#### 한줄 요약
- Command 검증 → 불변 이벤트 커밋 → Kafka 비동기 발행 → 프로젝션 엔진 변환 → Query DB 갱신 순으로 진행된다.

## Ⅴ. 종류 및 비교

<details><summary>용어 설명</summary>

- **전통적 CRUD vs 단순 CQRS vs 이벤트 소싱 결합 CQRS**: 현재 상태 덮어쓰기, 읽기/쓰기 DB만 분리, 이벤트 로그 자체를 원천 데이터로 사용하는 아키텍처.

</details>

| 비교 항목 | 전통적 CRUD 아키텍처 | 단순 CQRS 아키텍처 | 이벤트 소싱 + CQRS 아키텍처 |
|:---|:---|:---|:---|
| 상태 저장 방식 | **현재 상태 덮어쓰기 (Overwrite)** | 현재 상태 기반 RDBMS/NoSQL 분리 | **모든 상태 변경 이벤트의 불변 누적** |
| 감사 추적성 (Audit) | 별도 감사 로그 테이블 수동 개발 | 별도 감사 로그 수동 유지 | **이벤트 자체가 완벽한 감사 로그** |
| 시간 여행 (시점 복원) | 불가능 (백업 복구만 가능) | 불가능 | **특정 시점 상태 완벽 재생(Replay)** |
| 정합성 모델 | 강한 일관성 (ACID) | 복제 지연에 따른 최종 일관성 | **비동기 프로젝션 기반 최종 일관성** |
| 주 적용 분야 | 범용 CRUD 게시판, 관리자 도구 | 대규모 읽기 트래픽 포털/커머스 | **금융 계좌, 결제 원장, 물류 배송 추적** |

#### 한줄 요약
- 단순 조기 확장은 단순 CQRS, 금융/원장 수준의 이력 추적과 고성능 분리는 이벤트 소싱 결합 CQRS를 선택한다.

## Ⅵ. 실무 고려사항 및 대책

<details><summary>용어 설명</summary>

- **Upcasting(업캐스팅)**: 비즈니스 규칙 변경으로 이벤트 스키마가 버전업되었을 때, 런타임에 과거 버전 이벤트를 최신 스키마로 변환하는 기법.
- **Read-Your-Writes**: 사용자가 쓰기를 수행한 직후 조회를 요청했을 때 본인이 변경한 최신 데이터가 보이도록 보장하는 일관성 기법.

</details>

| 문제 | 대책 | 효과 |
|:---|:---|:---|
| 수만 개 이벤트 누적으로 인한 상태 복원(Replay) 지연 | **100개 이벤트마다 주기적 스냅샷(Snapshot)** 저장 | 애그리게잇 로딩 시간 5ms 이내로 단축 |
| 도메인 요구 변경으로 이벤트 스키마 변경 시 역직렬화 오류 | **업캐스터(Upcaster) 변환 계층 및 Schema Registry** 적용 | 과거 이벤트 영속성 유지 및 하위 호환성 100% 보장 |
| 비동기 프로젝션 지연으로 쓰기 직후 화면 조회 불일치 | **Read-Your-Writes 토큰 동기화 및 낙관적 UI 업데이트** | 최종 일관성 지연 은닉 및 사용자 경험 보호 |
| 중복 이벤트 소비로 인한 데이터 왜곡 | **컨슈머 멱등성(Idempotency) 및 이벤트 고유 ID 키** 적용 | 중복 처리 시에도 뷰 정합성 완벽 유지 |

#### 한줄 요약
- 스냅샷 주기 설정, 업캐스터 호환성 보장, Read-Your-Writes 동기화, 멱등성 소비로 안정성을 완성한다.

## Ⅶ. 결론

- 원장 이력 관리는 **이벤트 소싱**, 조회 분리는 **CQRS** 선택

#### 한줄 요약
- 이벤트 소싱과 CQRS는 데이터의 모든 변경 역사를 영구 보존하고 읽기/쓰기 확장성을 극대화하는 최신 분산 데이터 아키텍처다.
