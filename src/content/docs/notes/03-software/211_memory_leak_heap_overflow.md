## Ⅰ. 개요

<details><summary>용어 설명</summary>

- **메모리 누수(Memory Leak)**: 애플리케이션 내에서 더 이상 사용되지 않는 불필요한 객체들이 컬렉션이나 정적 변수 등에 의해 강한 참조(Strong Reference)가 유지됨으로써 가비지 컬렉터(GC)에 의해 메모리가 회수되지 못하고 점유량이 지속적으로 누적되는 치명적 소프트웨어 결함이다.
- **힙 고갈(Heap Exhaustion)**: 장기적인 메모리 누수, 과도하게 큰 데이터 셋업, 혹은 극단적인 동시 트래픽 증가로 인해 자바 가상 머신(JVM)이나 런타임의 가용 힙(Heap) 공간이 절대적으로 부족해져, 새로운 객체에 대한 메모리 할당 요청이 실패하는 한계 상태이다.

</details>

- 정의: 불필요 객체가 GC에 미회수되는 **메모리 누수**와 할당 실패로 이어지는 **힙 고갈** 현상
- 배경: 단순 **OOM** 로그만으로는 누수와 트래픽 폭주 원인 **식별 불가**

#### 한줄 요약
- 숨겨진 참조 고리로 힙 포화 시 객체 할당 불가 및 프로세스 강제 종료

## Ⅱ. 특징

<details><summary>용어 설명</summary>

- **가비지 컬렉션(Garbage Collection, GC)**: 메모리 관리 기법 중 하나로, 런타임 엔진(JVM, V8 등)이 주기적으로 힙 영역을 스캔하여 도달 가능성(Reachability)이 없는 고립된 객체들의 메모리를 자동 식별 및 강제 회수하여 가용 공간을 확보하는 백그라운드 작업이다.
- **메모리 부족(Out Of Memory, OOM)**: 시스템 또는 개별 프로세스에 할당된 메모리 한도(Max Heap)에 도달하여, 운영체제나 런타임이 추가적인 메모리 할당 요청을 수용할 수 없어 애플리케이션 크래시를 유발하는 치명적 예외(Exception) 상태이다.
- **스레드 로컬(ThreadLocal)**: 개별 스레드마다 고유하고 독립적인 상태(값)를 보관할 수 있도록 지원하는 메모리 영역으로, 작업 완료 후 명시적으로 `remove()`를 호출하지 않으면 스레드 풀 환경에서 장수 스레드가 해당 객체를 끝까지 물고 있어 심각한 누수를 유발한다.
- **네이티브 메모리(Native Memory)**: 자바 등 관리형 런타임의 힙(Heap) 영역 바깥에 위치하며, JNI 호출이나 NIO 다이렉트 버퍼 등 운영체제(OS) 수준에서 직접 할당(malloc)하고 명시적으로 해제(free)해야 하는(GC 관리 대상이 아닌) 물리적 메모리 공간이다.
- **힙 덤프(Heap Dump)•도미네이터 경로(Dominator Path)**: **OOM** 발생 시점이나 메모리 고점유 시점의 힙 내 모든 객체 인스턴스와 이들 간의 복잡한 참조 트리를 스냅샷 파일로 기록하고, 특정 객체(도미네이터)가 어떤 하위 객체들의 생명주기를 멱살 잡고 놓지 않는지 그 뿌리 경로를 역추적하는 핵심 진단 수단이다.

</details>

- 진정한 누수는 일시적인 피크가 아니라, 수차례의 전체 **가비지 컬렉션(Garbage Collection, GC)** 수행 이후에도 힙 사용량의 최저 기저선(Baseline)이 톱니바퀴처럼 지속적으로 우상향하는 패턴을 보인다.
- 힙 고갈 현상은 단순 메모리 누수뿐만 아니라 단일 요청이 수 GB의 DB 데이터를 캐싱(큰 작업 집합)하거나 과도한 트래픽이 동시 몰려들 때도 발생할 수 있으므로 원인을 엄격히 분리해야 한다.
- 분석 툴을 이용해 **힙 덤프(Heap Dump)**를 열고 **도미네이터 경로(Dominator Path)**를 분석하여 쓸모없는 객체를 물고 있는 최상위 원흉(Root) 참조 변수를 정확히 찾아낸다.
- 잘못 관리된 정적(Static) 컬렉션, 해제되지 않은 리스너, 찌꺼기가 남은 **스레드 로컬(ThreadLocal)**은 힙 메모리 누수의 3대 주범이다.
- 외부 C/C++ 라이브러리 사용 시 **네이티브 메모리(Native Memory)** 자원에 대한 해제 누락은 관리형 힙 외부의 보이지 않는 치명적 누수를 야기하여 OS 차원의 킬(**OOM** Killer)을 유발한다.

#### 한줄 요약
- 트래픽이 빠져나간 뒤에도 메모리 최저점이 계속 오르고 있다면 애플리케이션 내부의 누수 버그를 의심해야 하며, 단순 피크 시 **OOM**이 터진다면 힙 할당량 설정 최적화 여부도 함께 검토해야 한다.

## Ⅲ. 구조 및 구성요소

<details><summary>용어 설명</summary>

- **참조•점유 분석기(Reference and Retention Analyzer)**: 두 개 이상의 시점에서 추출한 힙 덤프 파일 간의 객체 수량 증감, 보유 크기(Retained Size) 차이, 도미네이터 트리의 변화를 비교 연산하여 누수의 유력한 용의자 객체를 자동 판별하는 심층 진단 도구이다.
- **보유 크기(Retained Size)**: 특정 객체(A) 단일 크기(Shallow Size)뿐만 아니라, A가 소멸될 경우 GC에 의해 동반 회수될 수 있는 하위 종속 객체들의 메모리 크기까지 전부 합산한 실질적인 메모리 해방 기대치이다.
- **도미네이터(Dominator)**: 특정 하위 객체 집합으로 향하는 유일한 길목(참조 경로)에 서 있어서, 그 객체가 살아있는 한 하위 객체들도 절대 GC되지 않도록 생사여탈권을 지배하는 루트(Root) 객체이다.
- **메모리 계측기(Memory Instrumentation)**: 애플리케이션에 부착된 에이전트(JMX, APM 등)를 통해 힙, Non-Heap, 네이티브 메모리 영역의 사용량 추이와 실시간 객체 할당률, GC 소요 시간 등을 모니터링 대시보드에 지속 스트리밍하는 관측 모듈이다.
- **덤프•프로필 수집기(Dump and Profile Collector)**: 관리자가 수동으로 트리거하거나 **OOM** Exception 발생 시점(HeapDumpOnOutOfMemoryError)에 자동으로 당시의 완벽한 힙 메모리 스냅샷 파일(.hprof 등)과 스레드 덤프를 안전하게 생성하고 저장소에 보존하는 백업 컴포넌트이다.
- **운영 제어기(Operational Controller)**: 도출된 메모리 분석 결과 리포트를 바탕으로, 캐시 만료 시간(TTL) 조절, 객체 풀(Pool) 사이즈 조정, 스레드 큐(Queue) 한계치 축소, 혹은 JVM 시작 파라미터(Xmx) 튜닝 등을 결정하고 시스템에 반영하는 통제 모듈이다.

</details>

```text
[Memory 진단 체계]
 ├── [Memory 계측기]
 ├── [Dump•Profile 수집기]
 ├── [참조•점유 분석기]
 └── [운영 제어기]
```

| 구성요소 | 책임 |
|:---|:---|
| Memory 계측기 | Heap•Native•GC•**Allocation Rate** 수집 |
| Dump•Profile 수집기 | 객체•참조•할당 이력 **Snapshot** 보존 |
| 참조•점유 분석기 | Retained Size•**Dominator** 경로 분석 |
| 운영 제어기 | Cache•Pool•Queue•**Heap 설정** 조정 |

#### 한줄 요약
- 단순한 시계열 사용량 그래프와 정적인 거미줄 모양의 힙 참조 트리를 크로스 체크하여, 공간 부족이 인프라 할당량 탓인지 애플리케이션 버그 탓인지 명확히 가려내는 진단 아키텍처

## Ⅳ. 흐름도

<details><summary>용어 설명</summary>

- **1. 반복 부하•GC 후 덤프(Repeated Load•Dump after GC)**: 동일한 비즈니스 트랜잭션 부하를 여러 번 인위적으로 가한 뒤, 명시적으로 GC를 강제(System.gc()) 수행하여 살아남은 찌꺼기 객체들만의 힙 덤프를 다수 시점에서 캡처하는 사전 준비 단계이다.
- **2. 객체•참조 차이 전달(Object•Reference Difference Delivery)**: 시간차가 있는 여러 힙 덤프 파일을 툴(MAT 등)에 밀어넣고, 클래스별 인스턴스 개수와 합산 보유 크기의 델타(Delta) 증가분을 정확히 비교 대조하는 데이터 전처리 단계이다.
- **3. 증가 객체•보유 경로 판정(Increased Object•Retention Path Assessment)**: 2단계에서 지속적으로 몸집을 불리는 객체들을 특정하고, 이들을 가비지 컬렉터의 마수로부터 보호하고 있는 최상위 GC Root 도미네이터가 어떤 놈인지 참조 체인을 따라 역추적하는 핵심 분석 단계이다.
- **4. 누수•정상 고점유•고갈 분류(Leak•Healthy High Utilization•Exhaustion Classification)**: 식별된 힙 점유 양상이 GC 후 정상 회복되는 건강한 부하인지, 찌꺼기가 남아 누적되는 누수인지, 아니면 단순히 객체 생성 속도가 힙 크기를 압도하는 물리적 용량 고갈인지 명확한 경계선으로 원인 영역을 분류하는 진단 단계이다.
- **5. 검증 부하 계측(Verification Load Instrumentation)**: 원흉 참조 코드를 수정 배포하거나 힙 용량을 증설한 이후, 1단계와 동일한 재현 부하 테스트를 실시하여 톱니바퀴 우상향 패턴이 사라지고 **OOM**이 근절되었는지 최종 확인하는 검증 단계이다.

</details>

```text
1. 반복 부하•GC 후 덤프
      |
      v
2. 객체•참조 차이 전달
      |
      v
3. 증가 객체•보유 경로 판정
      |
      v
4. 누수•정상 고점유•고갈 분류
      |
      +-- GC 후 정상적인 기준선(Baseline) 회복 패턴 확인 --> 정상 고점유 상황, 물리적 인프라 용량 확대 검토
      |
      +-- 덤프 간 Retained Size 지속 우상향 패턴 확인 --> 메모리 누수 판정, 도미네이터 소스코드 강제 참조 해제 조치
      |
      +-- 단시간 내 새 할당 실패로 즉각적 크래시 발생 --> 힙 고갈 상태, 코드 누수 여부와 트래픽 부하 폭증 원인 정밀 분리 추적
                               |
                               v
5. 검증 부하 계측
```

### 동작 원리

1. **반복 부하•GC 후 덤프**: 시점별 Heap 기준선 Snapshot 확보
2. **객체•참조 차이 전달**: 객체 수•Retained Size 증가분 비교
3. **증가 객체•보유 경로 판정**: GC Root•Dominator 역추적
4. **누수•정상 고점유•고갈 분류**: 기준선 회복•할당 실패 구분
5. **검증 부하 계측**: 수정 후 동일 부하에서 기준선 안정 확인

#### 한줄 요약
- 펌프질로 부하를 주고 대청소(GC)를 한 뒤에도 바닥에 찌꺼기가 계속 쌓인다면 덤프를 떠서, 수만 개의 실처럼 얽힌 객체 참조 지도를 역추적해 숨은 범인 변수를 찾아내는 과학수사 기법

## Ⅴ. 종류 및 비교

<details><summary>용어 설명</summary>

- **정상 고점유(Healthy High Utilization)**: 수많은 사용자 요청이 몰려 일시적으로 힙 메모리 사용량이 Max 제한선의 80~90%까지 치솟아 아슬아슬하지만, 트래픽이 빠지고 GC가 수행되면 즉시 원래의 평온한 기저선(예: 30%)으로 완벽히 회복되는 탄력적이고 정상적인 시스템 상태이다.
- **메모리 누수 판정 기준(Memory Leak Judgment Criteria)**: 연속적인 트래픽-휴식-GC 사이클을 거쳤음에도 불구하고 힙 사용량의 최저점이 30% -> 35% -> 40% 식으로 미세하지만 멈추지 않고 지속 우상향하여 불필요한 객체와 보유 크기가 계속 축적되고 있음이 증명되는 명확한 이상 지표이다.
- **힙 고갈 판정 기준(Heap Exhaustion Judgment Criteria)**: JVM 내 가용 힙 메모리 공간의 절대적 수량이 부족해져, 운영체제가 `java.lang.OutOfMemoryError: Java heap space` 에러를 뱉어내며 신규 비즈니스 로직 처리를 위한 객체 인스턴스화가 원천 불가능해지는 물리적 붕괴 시점이다.

</details>

| 메모리 상태 | 판별 신호 | 의미 |
|:---|:---|:---|
| **정상 고점유(Healthy High Utilization)** | 대형 작업 종료 및 GC 사이클 통과 후 힙 사용 기저선(Baseline) 원상 회복 | 대량 데이터 조작 등 정상적인 애플리케이션 작업 집합에 따른 일시적 점유 스파이크 현상 |
| **메모리 누수 판정 기준(Memory Leak Judgment Criteria)** | 연속된 강제 GC 수행 뒤에도 힙 내 잔존 객체 수 및 전체 보유 크기가 멈추지 않고 계단식으로 지속 증가 | 컬렉션, 정적 변수 어딘가에 실수로 방치된 불필요 참조가 끈질기게 남아 힙 기저선을 영구적으로 끌어올리는 결함 |
| **힙 고갈 판정 기준(Heap Exhaustion Judgment Criteria)** | 힙 공간 내 단편화(Fragmentation) 극심화 또는 절대 용량 부족으로 신규 메모리 할당(new Object) 즉각 실패 | 켜켜이 쌓인 만성적 누수, 수 기가바이트급 단일 데이터셋 로드 시도, 감당 불가능한 동시 할당 폭주가 빚어낸 시스템 다운 |

> 요약: GC 사이클 이후 베이스라인이 원위치로 돌아오면 **정상 고점유(Healthy)**, 계단식으로 계속 치고 올라가면 **누수(Leak)**, 그 끝에 한계점에 달해 멈춰서면 **힙 고갈(Exhaustion)**이다.

#### 한줄 요약
- 작업이 끝나고 청소차가 지나간 뒤 거리가 깨끗해지면 정상, 쓰레기 더미가 야금야금 쌓여간다면 누수, 결국 산더미 같은 쓰레기 때문에 새 물건을 길가에 내려놓지 못하는 마비 순간이 바로 힙 고갈

## Ⅵ. 실무 고려사항 및 대책

<details><summary>용어 설명</summary>

- **누수 오판(Leak Misjudgment)**: 대량의 파일 업로드나 동시 접속자 폭증 등으로 순간적인 초당 메모리 할당 속도(Allocation Rate)가 가비지 컬렉터의 수거 속도를 압도하여 단기적으로 메모리가 꽉 차는 현상을, 근본적인 소스 코드 내 메모리 누수 버그로 잘못 착각하여 엉뚱한 곳에서 시간을 낭비하는 치명적 분석 오류이다.
- **할당률(Allocation Rate)**: 자바 애플리케이션이 1초당 힙 메모리의 에덴(Eden) 영역에 새롭게 만들어내는 객체들의 메모리 크기(예: 300MB/sec)로, 이 수치가 비정상적으로 높으면 GC 부하를 유발하고 잦은 멈춤(Stop-the-world) 현상을 만든다.
- **힙 덤프 분석(Heap Dump Analysis)**: MAT(Memory Analyzer Tool) 같은 전문 도구를 활용하여 특정 시점에 확보한 수 기가바이트 크기의 힙 스냅샷 파일들을 로드하고, 수백만 개의 객체 인스턴스들이 서로 어떤 값과 생명줄(참조 관계)을 쥐고 있는지 이진(Binary) 레벨에서 해부하는 난이도 높은 작업이다.

</details>

| 문제 | 대책 | 효과 |
|:---|:---|:---|
| 단순 트래픽 폭주에 따른 GC 지연 현상을 심각한 코드 결함으로 착각하는 **누수 오판(Leak Misjudgment)** 위험 | APM을 통한 초당 실시간 **할당률(Allocation Rate)** 추적 및 GC 로그 기반 잔존 객체 패턴 동시 교차 분석 수행 | 불필요한 코드 디버깅 시간 낭비 방지 및 장애 근본 원인(트래픽 vs 버그) 진단 정확성 확보 |
| 운영 시스템 메모리 **힙 덤프 분석(Heap Dump Analysis)** 시 고객의 민감한 비밀번호, PII 데이터 등이 평문으로 노출되는 보안 위협 | 스냅샷 추출 시 중요 메모리 블록 마스킹 툴 적용, 덤프 파일 전송 구간 암호화 및 분석 담당자 접근 통제(RBAC) 엄격 적용 | 개발 및 분석 과정에서의 치명적인 고객 프라이버시 자료 유출 및 컴플라이언스 위반 리스크 원천 방지 |
| 메모리 점유율 알람 울릴 시 단순히 WAS(Tomcat 등)를 재시작하여 일시적으로 회피함으로써 발생 원인을 영구 미궁으로 빠뜨리는 악습 | 재시작 스크립트 가동 전 `jmap` 등을 통한 힙 덤프 및 스레드 덤프, JFR(Java Flight Recorder) 자동 수집 파이프라인 의무화 구축 | 휘발되어 버리는 장애 상황 증거 보존을 통한 끈질긴 근본 원인(Root Cause) 추적성 확보 및 재발 방지 |
| 임계치 95% 도달 시점에 이미 시스템이 프리징되어 손쓸 틈도 없이 **OOM** 크래시로 이어지는 늦은 경보 문제 | 단순히 현재 점유율이 아닌 '우상향 추세선'과 델타 '증가율(Slope)' 기반의 머신러닝 예측 임계치(Predictive Threshold) 조기 경보 세팅 | 사용자가 에러 창을 보기 전, 인프라 팀이 사전에 클러스터를 스케일 아웃(Scale-out)하거나 노드를 제외하는 선제적 장애 완화 가능 |

#### 한줄 요약
- 객체 소멸 시점에 `clear()`·`remove()`로 **참조 고리** 절단 필수

## Ⅶ. 결론

<details><summary>용어 설명</summary>

- **메모리 대응 기준(Memory Response Criteria)**: 서비스의 메모리 문제를 해결하기 위해, GC 이후 바닥선이 지속 상승하는 명확한 누수 패턴일 경우 소스 레벨의 참조 해제 및 코드 픽스를 단행하고, 단기적 피크에 따른 일시적 고점유나 물리적 부족일 경우 캐시 크기 최적화 및 힙 용량 증설(Scale-up) 등 인프라 조치를 분리 적용하는 트러블슈팅 행동 강령이다.
- **기준선 회복(Baseline Recovery)**: 서비스에 가해진 트래픽 부하가 종료되고 JVM의 풀비지 컬렉션(Full GC) 사이클이 한 차례 돈 직후, 힙 메모리 점유율 그래프가 안정적이고 평화로웠던 본래의 최저 수준(평상시의 바닥선)으로 깔끔하게 돌아오는 시스템의 이상적인 건강 지표 현상이다.

</details>

- GC 후 **기준선 회복** 여부로 누수·용량 구분, 누수 시 코드 참조 해제, 일시 고점유 시 **힙 인프라 튜닝**

#### 한줄 요약
- **덤프** 기반 근본 원인 식별 후 누수·용량 분리 대응
