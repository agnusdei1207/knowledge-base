## Ⅰ. 개요

<details><summary>용어 설명</summary>

- **전가상화(Full Virtualization)**: 게스트 OS는 지가 가상 환경인지도 모른 채 쌩 하드웨어인 줄 알고 나대고, 하이퍼바이저가 뒤에서 모든 걸 진짜처럼 사기 쳐주는(흉내 내는) 가장 무거운 가상화이다.
- **반가상화(Paravirtualization)**: 게스트 OS 커널 소스 코드를 뜯어고쳐서, 자기가 가상 환경인 걸 인지하고 하드웨어 대신 하이퍼바이저한테 직접 하이퍼콜(Hypercall)을 때려서 성능을 챙긴 실전 압축 가상화이다.
- **컨테이너 가상화(Container Virtualization)**: 무거운 하이퍼바이저와 게스트 OS를 싹 다 치워버리고, 리눅스 호스트 커널 하나만 놔둔 채 프로세스들만 멱살 잡아 격리(cgroups, namespaces)시켜 돌리는 초경량 가상화이다.

</details>

- 정의: 하드웨어를 어떻게 사기 칠 건지, 게스트 커널을 뜯어고칠 건지, 아니면 아예 커널을 통째로 공유할 건지에 따른 3대 격리 아키텍처 비교인 **전가상화 vs 반가상화 vs 컨테이너 가상화**
- 배경: 무거운 VM만 쓰면 서버에 몇 개 못 올리고(**배치 밀도 최악**), 컨테이너만 쓰면 윈도우 같은 이종 OS를 섞어 쓸 수 없기 때문

#### 한줄 요약

- OS를 통째로 올리면서 속일 건지(전가상화), 고쳐 쓸 건지(반가상화), 아니면 OS 껍데기 버리고 커널만 쉐어할 건지(컨테이너)의 차이다.

## Ⅱ. 특징

<details><summary>용어 설명</summary>

- **하이퍼콜(Hypercall)**: 반가상화에서 뜯어고친 게스트 OS가 하이퍼바이저한테 "형님 이것 좀 대신 해주쇼" 하고 직접 찌르는 VIP 직통 콜(시스템 콜)이다.
- **네임스페이스와 씨그룹(Namespaces & Cgroups)**: 리눅스 커널의 근본 기능으로, 네임스페이스는 "너 혼자 다 쓰는 거야"라고 뷰(View)를 속이고, 씨그룹은 "램 1GB 넘으면 죽인다"라고 멱살 잡고 자원을 통제하는 컨테이너의 핵심이다.

</details>

- 게스트 커널을 하나도 안 건드리고 쌩판 모르게 돌리는 **전가상화**.
- 게스트 커널을 뜯어고치고 **하이퍼콜**을 꽂아서 가상화 트랩 오버헤드를 박살 내버린 **반가상화**.
- 호스트 커널 1개만 공유하면서 깃털처럼 가볍게 시작하고 램을 아끼는 **컨테이너**.

#### 한줄 요약

- 수정 불가면 전가상화, 하이퍼콜 꽂으면 반가상화, 커널 공유 환술이면 컨테이너다.

## Ⅲ. 구조 및 구성요소

<details><summary>용어 설명</summary>

- **버트아이오(virtio)**: 리눅스 KVM 같은 데서 "디스크나 네트워크 I/O 속도 좀 올리자"고 만든 반가상화 전용 드라이버 표준 인터페이스이다.

</details>

```text
[ 3대 가상화 십자포화 아키텍처 경계 ]

[전가상화 / 반가상화]        [ 컨테이너 가상화 ]
┌────────────────┐         ┌───────────────┐
│  워크로드(App) │         │ 워크로드(App) │
├────────────────┤         ├───────────────┤
│    게스트 OS   │         │ (게스트 없음) │
├────────────────┤         │               │
│  하이퍼바이저  │         │               │
├────────────────┴─────────┴───────────────┤
│               호스트 커널                │
│         (cgroups, namespaces)            │
└──────────────────────────────────────────┘
```

| 구성요소 | 책임 |
|:---|:---|
| 워크로드 | 실제로 돌릴 애플리케이션 프로세스 덩어리 |
| 게스트 OS | 전/반가상화에서 지가 짱인 줄 알고 도는 무거운 독립 커널 |
| 하이퍼바이저 | 전/반가상화에서 짭 하드웨어를 만들고 자원을 멱살 잡고 중재하는 중간 보스 |
| 컨테이너 프로세스 | 호스트 커널 위에서 지 혼자 있는 것처럼 환술(**Namespaces**)에 걸린 채 갇혀 있는 앱 |
| 호스트 커널 | 컨테이너들한테 램과 CPU 할당량 캡(**Cgroups**)을 씌우고 통제하는 진짜 주인님 |

#### 한줄 요약

- 가상화는 하이퍼바이저와 게스트 커널이 자원을 뜯어먹고, 컨테이너는 호스트 커널 하나가 다 통제한다.

## Ⅳ. 흐름도

<details><summary>용어 설명</summary>

- **바이너리 변환(Binary Translation)**: 전가상화에서 하드웨어(CPU) 지원이 없을 때, 게스트가 치는 특권 명령어를 하이퍼바이저가 런타임에 동적으로 안전한 코드로 쓱싹 번역해서 돌려막기 하는 구시대 똥꼬쇼 기법이다.

</details>

```text
[ 가상화 아키텍처 선택 십자포화 흐름 ]
┌──────────────────────────────┐
│ 1. 커널 공유가 가능한가?     │
│ (리눅스 앱이고, 보안 빡 안셈?)│
└──────────────┬───────────────┘
               ├─ Yes ──────────▶ [ 컨테이너 가상화 ]
               │ No (윈도우 써야됨, 완벽 격리 필요)
               ▼
┌──────────────────────────────┐
│ 2. 게스트 OS 수정이 가능한가?│
│ (커널 소스 까서 고칠 수 있음?)│
└──────────────┬───────────────┘
               ├─ Yes ──────────▶ [ 반가상화 (Hypercall) ]
               └─ No (소스 못깜) ─▶ [ 전가상화 (Hardware-Assist) ]
```

### 동작 원리

1. 커널 공유 허용 판정: 윈도우 앱인지 리눅스 앱인지, 보안 때문에 무조건 커널 단에서 찢어발겨야 하는지 각을 잼.
2. 컨테이너 선택: 리눅스 앱이고 깃털처럼 가벼워야 되면 **Namespaces & Cgroups**로 묶어버림.
3. 게스트 수정 가능성 판정: 게스트 OS 커널 소스를 까서 **하이퍼콜**을 이식할 수 있는지 봄.
4. 반가상화 선택: 리눅스처럼 소스 깔 수 있으면 뜯어고쳐서 성능 극강인 반가상화 박음.
5. 전가상화 선택: 윈도우처럼 소스 못 까면 하드웨어 칩셋(VT-x) 믿고 쌩으로 전가상화 돌림.

#### 한줄 요약

- 커널을 공유할 수 있으면 컨테이너, 소스 깔 수 있으면 반가상화, 다 안 되면 전가상화를 고른다.

## Ⅴ. 종류 및 비교

<details><summary>용어 설명</summary>

- **카타 컨테이너 / 마이크로 가상머신(Kata Containers / MicroVM)**: "컨테이너는 가벼운데 커널 공유라 보안 털리면 큰일 난다"며, 컨테이너마다 초소형 하이퍼바이저(VM)를 감싸서 보안 격리와 컨테이너의 가벼움을 스까버린 궁극의 혼종이다.

</details>

| 비교 항목 | 전통적 VM (전가상화/반가상화) | **컨테이너** (Docker, Podman) | **마이크로VM** (Kata, Firecracker) |
|:---|:---|:---|:---|
| 격리 메커니즘 | 하이퍼바이저가 하드웨어 단부터 찢어놓음 | 호스트 커널 1개가 **Cgroups/Namespaces**로 논리적 환술을 검 | 컨테이너 하나마다 초경량 하이퍼바이저(VM)를 감싸버림 |
| 메모리/무게 | 덩치 큰 게스트 OS를 띄워야 해서 무거움 | 앱 프로세스만 딱 띄우니까 메모리 낭비가 0에 수렴함 | 린(Lean) 커널 띄워서 일반 VM보단 압도적으로 가벼움 |
| 기동 속도 | 게스트 OS 부팅 다 기다리느라 한세월임 | 프로세스 하나 켜는 수준이라 1초 컷 (ms 단위) | 마이크로 부팅이라 컨테이너급으로 빠름 |
| 최고존엄 용도 | 윈도우/레거시 돌리거나 빡센 클라우드 IaaS | 클라우드 네이티브(MSA), PaaS | 아마존 람다(Serverless FaaS), 멀티테넌트 쿠버네티스 |

#### 한줄 요약

- 묵직한 격리는 VM, 초경량 민첩성은 컨테이너, 둘 다 스깐 놈은 마이크로VM이다.

## Ⅵ. 실무 고려사항 및 대책

<details><summary>용어 설명</summary>

- **커널 공유 취약점 (Kernel Shared Vulnerability)**: 컨테이너는 호스트 커널을 공유하기 때문에, 커널 취약점 하나 터지면 컨테이너 하나 뚫린 게 호스트 전체 탈취로 번지는 대참사 리스크이다.

</details>

| 문제 | 대책 | 효과 |
|:---|:---|:---|
| **컨테이너**는 커널을 공유해서 하나 뚫리면 호스트 통째로 털림(**커널 취약점 파급**) | **seccomp, AppArmor, Rootless** 떡칠로 권한을 뺏어버림 | 시스템 콜을 틀어막아서 커널 공격면을 멱살 잡고 최소화함 |
| 윈도우는 커널을 못 뜯어고쳐서 **반가상화**를 쌩으로는 못 씀 | 윈도우 안에 억지로 **virtio Guest Driver** 패키지를 깔아버림 | 전가상화 환경에서도 I/O 성능만큼은 반가상화급으로 뻥튀기 |
| 클라우드에서 컨테이너 돌리는데 옆 테넌트가 악의적으로 호스트를 해킹하려 함 | **카타 컨테이너(MicroVM)**로 컨테이너마다 껍데기를 씌움 | 가벼움은 유지하면서 하이퍼바이저급 하드웨어 철통 보안 달성 |

#### 한줄 요약

- 컨테이너 보안은 seccomp와 Rootless로 막고, 윈도우 성능은 virtio로 올리며, 빡센 보안은 MicroVM을 씌워라.

## Ⅶ. 결론

<details><summary>용어 설명</summary>

- **가상화 격리 선택 기준 (Virtualization Isolation Criteria)**: OS가 다르냐, 보안 격리가 목숨이냐, 부팅이 1초 컷이어야 하냐를 따져서 VM, 컨테이너, MicroVM을 고르는 잣대이다.

</details>

- **가상화 격리 선택 기준** 원칙에 따라, 가벼운 MSA 생태계는 **컨테이너**, 강력한 보안이 필요한 멀티테넌트 IaaS/서버리스는 **전가상화 / 마이크로VM** 채택 기조 확립함

#### 한줄 요약

- 민첩한 MSA는 컨테이너를, 레거시는 전가상화를, 서버리스는 MicroVM을 박아라.
