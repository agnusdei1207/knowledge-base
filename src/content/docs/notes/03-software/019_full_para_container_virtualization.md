## Ⅰ. 개요

<details><summary>용어 설명</summary>

- **하이퍼콜 및 커널 공유(Hypercall & Kernel Sharing)**: 게스트 OS가 하이퍼바이저를 직접 호출(반가상화)하거나 동일 호스트 커널 위에서 네임스페이스로 격리(컨테이너)하는 기법.
- **VM 오버헤드 및 기동 지연(Overhead & Cold Start)**: 게스트 OS 전체 이미지(수 GB) 적재와 커널 초기화로 인해 수십 초 이상의 기동 시간과 자원 낭비가 발생하는 문제.

</details>

- 정의/개념: 하드웨어 에뮬레이션(전가상화), 커널 수정 하이퍼콜(반가상화), **호스트 커널 공유(Namespaces/Cgroups 컨테이너)** 로 구분되는 가상화 계층 체계
- 배경/필요성: 하이퍼바이저 기반 VM의 자원 오버헤드 및 긴 부팅 지연 극복과 배포 밀도 향상 필요

#### 한줄 요약

- 격리 수준과 성능·경량화 요구에 따라 전가상화·반가상화·컨테이너 중 최적 방식 선택

## Ⅱ. 특징

<details><summary>용어 설명</summary>

- **하이퍼콜(Hypercall)**: 반가상화에서 게스트 OS 커널이 하이퍼바이저에 직접 서비스를 요청하는 API 호출로, VM Exit 기반 에뮬레이션 오버헤드를 제거.
- **Namespaces & Cgroups**: 리눅스 커널의 프로세스 격리(Namespaces)와 자원 사용량 제한(Cgroups)으로 컨테이너 격리를 구현하는 핵심 커널 기능.

</details>

- **전가상화**: 게스트 OS 미수정, 하이퍼바이저 완전 에뮬레이션으로 이종 OS 지원
- **반가상화**: 게스트 OS 커널 수정 + **하이퍼콜** 기반 에뮬레이션 오버헤드 감소
- **컨테이너**: 호스트 커널 공유, **Namespaces·Cgroups** 기반 프로세스 수준 격리

#### 한줄 요약

- 이종 OS 지원이 필요하면 전가상화, 에뮬레이션 오버헤드 최소화는 반가상화, 경량 격리는 컨테이너

## Ⅲ. 구조 및 구성요소

<details><summary>용어 설명</summary>

- **virtio**: 반가상화 I/O 드라이버 표준 인터페이스로, 게스트 OS에 설치된 virtio 드라이버가 하이퍼바이저와 직접 통신하여 디스크·네트워크 I/O 성능을 향상시키는 인터페이스.

</details>

```text
[ 전가상화·반가상화 vs 컨테이너 구조 ]
전가상화 / 반가상화                컨테이너
┌─────────────────┐             ┌─────────────────┐
│  워크로드(App)  │             │  워크로드(App)  │
├─────────────────┤             ├─────────────────┤
│   게스트 OS     │             │  (게스트 OS 없음)│
├─────────────────┤             │                 │
│  하이퍼바이저   │             │                 │
├─────────────────┴─────────────┴─────────────────┤
│              호스트 OS 커널                      │
│           (cgroups, namespaces)                  │
└─────────────────────────────────────────────────┘
```

선의 의미: 계층 구분선은 전가상화·반가상화와 컨테이너의 커널 공유 경계를 나타내며, 컨테이너는 게스트 OS 계층이 없음을 표시

| 구성요소 | 책임 |
|:---|:---|
| 게스트 OS | 전/반가상화에서 독립 커널로 애플리케이션 격리 실행 |
| 하이퍼바이저 | 전/반가상화에서 가상 하드웨어 제공 및 자원 중재 |
| 컨테이너 프로세스 | **Namespaces** 기반 격리된 뷰에서 실행되는 애플리케이션 |
| 호스트 커널 | 컨테이너에 **Cgroups** 기반 자원 한도를 부여하는 공유 커널 |

#### 한줄 요약

- 전/반가상화는 하이퍼바이저와 게스트 커널로 완전 격리하고, 컨테이너는 호스트 커널을 공유하여 프로세스만 격리

## Ⅳ. 흐름도

<details><summary>용어 설명</summary>

- **바이너리 변환(Binary Translation)**: 하드웨어 가상화 지원 없는 전가상화 환경에서 게스트의 특권 명령어를 하이퍼바이저가 런타임에 안전한 코드로 동적 변환하는 기법.

</details>

```text
가상화 방식 선택
   │
   ▼
1. 호스트 커널 공유 가능 여부 판정
├─ 가능 (동일 Linux 워크로드·경량 격리): 컨테이너 선택
└─ 불가 (이종 OS·완전 격리 요구)
      │
      ▼
   2. 게스트 OS 커널 수정 가능 여부 판정
   ├─ 가능 (오픈소스 커널): 반가상화 (하이퍼콜 이식)
   └─ 불가 (비공개 소스): 전가상화 (HW 가상화 지원)
```

**동작 원리** 1. **커널 공유 판정**: 동일 OS 계열·경량 격리 허용 시 컨테이너 선택, 이종 OS·완전 격리 필요 시 VM 방식 선택
2. **커널 수정 가능성 판정**: 게스트 OS 커널 소스 수정 가능 시 **반가상화**(하이퍼콜 이식), 불가 시 **전가상화**(하드웨어 VT-x/AMD-V)
3. **전가상화 동작**: Intel VT-x·AMD-V 기반 VM Exit/Entry 및 EPT로 에뮬레이션 오버헤드 최소화

#### 한줄 요약

- 커널 공유 가능 여부→커널 수정 가능 여부 순서로 컨테이너→반가상화→전가상화를 결정

## Ⅴ. 종류 및 비교

<details><summary>용어 설명</summary>

- **마이크로VM(MicroVM, Kata Containers)**: 컨테이너별로 초경량 하이퍼바이저를 감싸 컨테이너의 경량성과 VM의 하드웨어 수준 격리를 결합한 보안 강화 컨테이너 실행 환경.

</details>

| 구분 | 전통적 VM (전가상화·반가상화) | 컨테이너 (Docker, Podman) | 마이크로VM (Kata, Firecracker) |
|:---|:---|:---|:---|
| 적용 기준 | 이종 OS·레거시·완전 하드웨어 격리 | 동일 OS 계열·경량 마이크로서비스 | 컨테이너 경량성 + VM 수준 보안 격리 |
| 핵심 특징 | 독립 게스트 OS·하이퍼바이저 완전 격리 | 호스트 커널 공유·**Namespaces·Cgroups** 프로세스 격리 | 컨테이너당 초경량 VM 래핑으로 이중 격리 |
| 한계 | 게스트 OS 부팅 시간·메모리 오버헤드 큼 | 커널 공유로 호스트 취약점 파급 위험 | VM 오버헤드 일부 잔존 |

#### 한줄 요약

- 완전 격리는 VM, 경량 민첩성은 컨테이너, 양쪽 균형이 필요하면 마이크로VM 선택

## Ⅵ. 실무 고려사항 및 대책

<details><summary>용어 설명</summary>

- **커널 공유 취약점(Kernel Shared Vulnerability)**: 컨테이너가 호스트 커널을 공유하므로 커널 취약점 악용 시 단일 컨테이너 침해가 호스트 전체로 파급될 수 있는 보안 위험.

</details>

| 문제 | 대책 | 효과 |
|:---|:---|:---|
| 컨테이너 커널 공유로 **커널 공유 취약점** 파급 위험 | **seccomp·AppArmor·Rootless** 컨테이너 적용 | 시스템 콜 제한으로 커널 공격면 최소화 |
| 비공개 소스 게스트 OS에서 전가상화 I/O 성능 저하 | **virtio 드라이버** 패키지 설치로 반가상화급 I/O 적용 | 전가상화 환경에서 I/O 성능 향상 |
| 멀티테넌트 환경에서 컨테이너 간 격리 부족 | **마이크로VM(Kata Containers)** 으로 컨테이너별 VM 래핑 | 하드웨어 수준 격리로 테넌트 간 보안 강화 |

#### 한줄 요약

- 커널 취약점은 seccomp·Rootless로, I/O 성능은 virtio로, 멀티테넌트 격리는 마이크로VM으로 보완

## Ⅶ. 결론

<details><summary>용어 설명</summary>

- **가상화 격리 선택 기준**: 이종 OS 지원 필요성·격리 수준·배포 밀도·시작 시간 요구에 따라 전가상화·반가상화·컨테이너·마이크로VM을 결정하는 판단 기준.

</details>

- 경량 MSA 배포는 **컨테이너**, 이종 OS·레거시 격리는 **전가상화**, 보안 강화 서버리스는 **마이크로VM** 선택

#### 한줄 요약

- 경량·민첩 배포는 컨테이너, 완전 격리는 전가상화, 경량성과 격리 균형이 필요하면 마이크로VM을 적용
