## Ⅰ. 개요

<details>
<summary>핵심 용어</summary>

- **쿠버네티스 아키텍처(Kubernetes Architecture)**: 제어면이 선언한 목표 상태와 관찰한 실제 상태의 차이를 지속 조정하고, 워커 노드가 컨테이너 워크로드를 실행하는 오케스트레이션 구조이다.

</details>

- 정의/개념: 제어면의 지속 조정과 워커 노드의 실행으로 **목표·실제 상태 차이** 를 줄이는 컨테이너 오케스트레이션 구조
- 배경/필요성: 수작업 배치·복구는 워크로드 증가 시 **반복 운영 지연**

#### 한줄 요약

- 운영자가 파드 수만 선언하면 제어면은 빈자리를 찾아 배치하고 장애로 사라진 파드를 다시 만들기 때문에 목표와 현실의 차이를 자동으로 좁힐 수 있다.

## Ⅱ. 특징

<details>
<summary>핵심 용어</summary>

- **지속 조정 루프**: 지속 조정 루프는 상태를 관찰하고 차이를 계산한 뒤 필요한 변경을 반복 수행한다.
- **응용 프로그래밍 인터페이스(Application Programming Interface, API)**: 사용자가 목표 상태를 선언하고 구성요소가 클러스터 상태를 조회·변경하는 접점이다.

</details>

- **선언형 API** 기반 목표 상태 관리
- **지속 조정 루프** 기반 장애 복구
- **제어면·작업 노드 분리** 기반 역할 분담

#### 한줄 요약

- 실행 순서를 일일이 명령하는 대신 원하는 결과를 적어 두면 여러 제어기가 각자 맡은 차이를 계속 바로잡는 방식이다.

## Ⅲ. 구조 및 구성요소

<details>
<summary>핵심 용어</summary>

- **컨트롤러 관리자**: 컨트롤러 관리자는 여러 컨트롤러를 실행해 리소스별 목표 상태를 실제 상태로 수렴시킨다.
- **분산 키값 저장소(etcd)**: 쿠버네티스 객체와 클러스터 상태를 일관되게 보존하는 제어면 저장소이다.
- **큐블릿(kubelet)**: 노드에서 배정된 파드를 실행하고 노드·파드 상태를 제어면에 보고하는 에이전트이다.

</details>

```mermaid
block
    columns 1
    A["API 서버·etcd"]
    B["스케줄러"]
    C["컨트롤러 관리자"]
    D["kubelet"]
    E["컨테이너 런타임"]
    A --- B
    A --- C
    A --- D
    D --- E
```

| 구성요소 | 책임 |
|:---|:---|
| API 서버·etcd | 요청 검증·**API 상태 저장** |
| 스케줄러 | **파드 배치 노드** 선택 |
| 컨트롤러 관리자 | **목표·실제 상태 차이** 조정 |
| kubelet | 파드 실행·**노드 상태 보고** |
| 컨테이너 런타임 | **샌드박스·컨테이너** 실행 |

#### 한줄 요약

- API 서버가 주문을 받고 장부에 기록하면 스케줄러가 작업 장소를 정하고 kubelet과 런타임이 현장에서 파드를 실행한다.

## Ⅳ. 흐름도

<details>
<summary>핵심 용어</summary>

- **2. 파드 생성·노드 배정**: 파드 생성 요청이 저장되면 스케줄러가 조건에 맞는 노드를 선택하고 배정을 기록한다.
- **1. 목표·실제 상태 차이**: 저장된 선언 상태와 관찰된 실행 상태의 편차를 계산한 결과이다.
- **3. 배정 파드 명세**: 선택된 노드에 컨테이너·자원·볼륨 조건을 전달하는 실행 명세이다.
- **4. 파드 실행 명세**: 샌드박스와 컨테이너 생성 조건을 런타임에 전달하는 명세이다.
- **5. 노드·파드 상태**: 실행 결과를 다음 지속 조정 루프의 실제 상태로 갱신하는 정보이다.

</details>

```mermaid
sequenceDiagram
    participant U as 사용자
    participant A as API 서버
    participant C as 컨트롤러·스케줄러
    participant K as kubelet
    participant R as 컨테이너 런타임
    U->>A: 목표 상태 제출
    A-->>U: 객체 승인 결과
    loop 목표 상태 미충족 동안
        A->>C: 1. 목표·실제 상태 차이
        C->>A: 2. 파드 생성·노드 배정
        A->>K: 3. 배정 파드 명세
        K->>R: 4. 파드 실행 명세
        R-->>K: 실행 상태
        K-->>A: 5. 노드·파드 상태
    end
```

**동작 원리**

1. **목표·실제 상태 차이**: 저장된 선언과 관측 상태의 편차 산출
2. **파드 생성·노드 배정**: 부족한 복제본과 실행 위치 결정
3. **배정 파드 명세**: 대상 노드가 실행할 컨테이너·자원 조건 전달
4. **파드 실행 명세**: 샌드박스와 컨테이너 생성 조건 전달
5. **노드·파드 상태**: 다음 조정 루프의 실제 상태 갱신

#### 한줄 요약

- 배포 객체를 제출하면 제어기가 부족한 파드를 만들고 스케줄러가 노드를 정한 뒤 kubelet이 런타임에 실행을 맡기는 한 흐름으로 이어진다.

## Ⅴ. 종류 및 비교

<details>
<summary>핵심 용어</summary>

- **제어면**: 제어면은 API 요청, 상태 저장, 스케줄링, 조정 로직을 담당하는 쿠버네티스 관리 계층이다.
- **작업 노드**: 큐블릿·컨테이너 런타임·네트워크 구성요소로 파드와 컨테이너를 실제 실행하는 계층이다.

</details>

| 쿠버네티스 영역 | 제어면 | 작업 노드 |
|:---|:---|:---|
| 적용 기준 | **클러스터 상태·배치 결정** | **파드·컨테이너 실행** |
| 핵심 특징 | **API·etcd**·스케줄러·컨트롤러 | **kubelet·런타임**·네트워크 |
| 한계 | 장애 시 **관리 기능 저하** | 장애 시 **배치 파드 손실** |

#### 한줄 요약

- 제어면은 어디서 무엇을 실행할지 결정하고 작업 노드는 받은 명세대로 컨테이너를 움직인다는 경계로 구분하면 구성요소가 섞이지 않는다.

## Ⅵ. 실무 고려사항 및 대책

<details>
<summary>핵심 용어</summary>

- **장기 미배치**: 장기 미배치는 자원 부족이나 제약 조건 충돌로 파드가 오랫동안 노드에 할당되지 못하는 문제다.
- **역할 기반 접근 통제(Role-Based Access Control, RBAC)**: 역할에 허용된 권한을 사용자·서비스 계정에 연결하는 접근 통제 방식이다.
- **깃옵스(Git Operations, GitOps)**: Git 저장소의 선언 상태를 기준으로 클러스터 구성을 자동 동기화하는 운영 방식이다.

</details>

| 문제 | 대책 | 효과 |
|:---|:---|:---|
| etcd **장애·상태 손실** | 홀수 멤버·**정기 백업·복원 훈련** | 쿼럼 유지·**복구 시간 단축** |
| API **과도 권한** | **최소 RBAC·입장 제어** 정책 | **비인가 변경 차단** |
| 파드 **장기 미배치** | 요청량·제약·**노드 여유 감시** | **Pending 원인** 조기 제거 |
| 선언 상태 **임의 변경** | **GitOps·소유 필드** 관리 | **변경 추적·되돌리기** 확보 |
| **단일 노드 장애** | 복제본·**분산 배치·상태 점검** | 서비스 **중단 범위 축소** |

#### 한줄 요약

- 제어면만 이중화해도 요청량이 틀리거나 배치 제약이 충돌하면 파드가 멈추므로 상태 저장, 권한, 용량, 배치 조건을 함께 점검해야 한다.

## Ⅶ. 결론

<details>
<summary>핵심 용어</summary>

- **배치 제약**: 배치 제약은 파드가 실행될 노드의 속성, 위치, 관계를 제한하거나 선호하도록 지정하는 조건이다.

</details>

- **복구 목표** 로 제어면 이중화를, **배치 제약** 으로 노드 분산 결정

#### 한줄 요약

- 관리 기능이 멈춰도 기존 파드는 잠시 동작할 수 있지만 새 배치와 복구는 중단되므로 요구 복구 시간에 맞춰 제어면과 노드를 각각 설계해야 한다.
