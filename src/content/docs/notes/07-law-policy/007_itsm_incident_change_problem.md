## Ⅰ. 개요

<details><summary>용어 설명</summary>

- **ITSM 운영 3대 핵심 프랙티스 (인시던트·문제·변경 관리)**: IT 서비스 중단을 최소화하고 안정적인 비즈니스 연속성을 보장하기 위해, 장애 발생 시 최우선으로 서비스를 정상화하는 **인시던트 관리(Incident Management)**, 반복 장애의 근본 원인을 규명하고 영구 제거하는 **문제 관리(Problem Management)**, 서비스 변경 시 발생할 수 있는 위험을 통제하고 안전하게 배포하는 **변경 관리(Change Enablement)** 의 상호보완적 3대 운영 체계.
- **복구와 원인 분석의 혼선 및 통제 없는 긴급 패치 결함(Incident-Problem Confusion & Uncontrolled Patch Defect)**: 대형 서비스 장애가 발생했을 때 우회 조치(Workaround)로 즉시 서비스를 살리는 대신 운영 서버에서 직접 소스코드 디버깅을 하느라 수 시간 동안 대고객 장애를 방치하거나, 검증되지 않은 핫픽스를 임의로 운영 DB에 적용했다가 2차 연쇄 장애를 유발하는 구조적 결함.

</details>

- 정의/개념: 무중단 IT 서비스 운영과 장애 재발 제로화를 달성하기 위해 **서비스 데스크 장애 접수 $\rightarrow$ 우회 조치(Workaround) 기반 인시던트 선 복구(MTTR 단축) $\rightarrow$ 근본 원인 분석(RCA) 및 KEDB 등록(문제 관리) $\rightarrow$ 변경자문위원회(CAB) 위험 심의 및 롤백 계획 수립(변경 관리) $\rightarrow$ CI/CD 배포 및 CMDB 갱신** 을 집행하는 **폐쇄 루프 ITSM 운영 엔지니어링 체계**
- 배경/필요성: 24x7 금융 및 공공 서비스의 가용성(99.99%) 요구 증대와 마이크로서비스 아키텍처(MSA) 도입에 따른 잦은 배포 환경에서, 신속한 복구와 체계적인 변경 통제 프로세스 필수화

#### 한줄 요약
- 인시던트 관리는 신속 복구(MTTR), 문제 관리는 근본 원인 제거(RCA), 변경 관리는 안전한 배포(위험 통제)를 담당한다.

## Ⅱ. 특징

<details><summary>용어 설명</summary>

- **3대 관리 관행의 핵심 역할 분담 (Core Responsibilities)**:
  - **인시던트 관리 (Incident)**: 목표는 **신속한 서비스 복구 (Fast MTTR)**. 근본 원인 규명보다 임시 우회책(Workaround: 서버 재기동, 트래픽 우회)을 우선 실행.
  - **문제 관리 (Problem)**: 목표는 **장애 재발 방지 (Zero Recurrence)**. 5-Whys, 피시본 다이어그램으로 근본 원인(Root Cause)을 찾아 영구 해결책 제시.
  - **변경 관리 (Change)**: 목표는 **안전한 서비스 수정 (Risk Minimization)**. 변경 요청(RFC)을 심의하여 다운타임 없이 신규 기능 및 버그 패치 배포.

</details>

- **선 복구 후 원인 규명의 엄격한 분리(Separation of Recovery and RCA)**: 인시던트 처리 중에는 원인 규명에 시간을 낭비하지 않고 서비스 가동에만 집중하며, 복구 완료 후 비동기로 문제 관리 티켓을 오픈하여 심층 분석
- **알려진 오류 데이터베이스 (KEDB: Known Error Database) 자산화**: 한 번 해결된 장애의 원인과 우회 방법을 KEDB에 영구 저장하여, 동일 장애 발생 시 1선 서비스 데스크가 1분 내 즉각 우회 복구
- **3대 변경 유형의 차등 통제(Risk-based Change Categorization)**: 위험도가 낮은 '표준 변경(Standard)'은 자동 승인 배포하고, 영향도가 큰 '일반 변경(Normal)'은 CAB 심의, 장애 복구를 위한 '긴급 변경(Emergency)'은 ECAB 신속 승인 적용

#### 한줄 요약
- 선 복구 후 원인 규명 분리, KEDB 지식 자산화, 3대 변경(표준/일반/긴급) 차등 심사, CMDB 연계 영향 분석을 제공한다.

## Ⅲ. 구조 및 구성요소

<details><summary>용어 설명</summary>

- **ITSM 삼위일체 상호작용 및 지원 인프라 5대 구성요소**:
  1. **서비스 데스크 (Service Desk)**: 단일 접점(SPOC)으로 인시던트 티켓 접수, 1차 분류 및 우회 조치 실행.
  2. **KEDB (Known Error Database)**: 알려진 오류 및 임시 해결책(Workaround) 저장소.
  3. **RCA 엔진 (Root Cause Analysis)**: 5-Whys, 장애 상관관계 분석을 통한 근본 결함 규명 도구.
  4. **CAB (Change Advisory Board)**: 비즈니스, 개발, 인프라, 보안 리더로 구성된 변경자문위원회.
  5. **CMDB (Configuration Management Database)**: 서버, DB, 애플리케이션 등 구성항목(CI) 간의 의존성 토폴로지 맵.

</details>

```text
┌─────────────────────────────────────────────────────────────────────────┐
│ [ 1. 인시던트 • 문제 • 변경 관리 상호연계 폐쇄 루프 아키텍처 ]          │
│                                                                         │
│  [ 1. 인시던트 관리 ] ──► [ KEDB 조회 ] ──► [ 우회 조치(Workaround) ]    │
│  (서비스 장애 발생)        (기존 해결책)     └─► [ 서비스 즉각 복구 (MTTR) ]│
│       │                                                                 │
│       ▼ (복구 후 티켓 이관)                                             │
│  [ 2. 문제 관리 (Problem) ] ──► [ 근본 원인 분석 (RCA: 5-Whys) ]        │
│  (반복 장애 / 중대 장애)         └─► [ 영구 패치 방안 도출 & KEDB 등록 ] │
│       │                                                                 │
│       ▼ (변경 요청서: RFC 발행)                                         │
│  [ 3. 변경 관리 (Change) ] ──► [ CMDB 의존성 분석 ] ──► [ CAB 심의 승인 ]│
│  (패치 코드 / 인프라 수정)       (영향 범위 파악)         └─► [ 롤백 계획 수립 ]│
│       │                                                                 │
│       ▼ (안전한 프로덕션 배포)                                          │
│  [ 운영 시스템 (Production) ] ──► [ CMDB 최신 형상 갱신 ➔ 완전 종결 ]   │
└─────────────────────────────────────────────────────────────────────────┘
```

선의 의미: 인시던트가 우회 조치로 선 복구된 후 문제 관리에서 RCA를 거쳐 변경 관리(CAB)를 통해 안전하게 영구 패치되는 순환 구조

| 관리 관행 | 최우선 목표 | 핵심 프로세스 및 활동 | 담당 주체 | 핵심 KPI |
|:---|:---|:---|:---|:---|
| **인시던트 관리** | **신속한 서비스 복구** | 티켓 접수, 우선순위화, 우회 조치, 에스컬레이션 | 서비스 데스크, 인시던트 커맨더 | **MTTR, 1차 해결률** |
| **문제 관리** | **근본 원인 제거 및 재발 방지**| 근본 원인 분석(RCA), 알려진 오류(KEDB) 등록, RFC 발행| 문제 관리자, 수석 개발자/DBA | **반복 장애 발생률, KEDB 건수**|
| **변경 관리** | **서비스 변경 위험 극소화** | 변경 요청(RFC), CMDB 영향 분석, CAB 심의, 롤백 계획 | 변경 관리자, CAB 위원회 | **변경 성공률, 변경 유발 장애율**|

#### 한줄 요약
- 인시던트(선 복구), 문제(RCA/KEDB), 변경(CAB/롤백)의 3대 관행과 CMDB 의존성 맵으로 구성된다.

## Ⅳ. 흐름도

<details><summary>용어 설명</summary>

- **장애 발생부터 영구 해결까지의 5단계 실무 라이프사이클**:
  1. 결제 모듈 장애 모니터링 알람 인입 $\rightarrow$ 인시던트 티켓 오픈 및 긴급 워룸(War-Room) 소집
  2. KEDB 조회 후 트래픽을 Standby 결제 게이트웨이로 우회(Failover)시켜 3분 만에 서비스 정상화
  3. 서비스 복구 후 문제 관리 티켓 생성 $\rightarrow$ 덤프 로그 분석을 통해 특정 메모리 누수 코드(RCA) 규명
  4. 메모리 누수 패치 코드를 작성하고 변경 요청서(RFC) 발행 $\rightarrow$ CAB에서 롤백 계획 및 영향도 심의 승인
  5. 정기 배포 시간대에 CI/CD 파이프라인으로 무중단 배포 적용 ➔ CMDB 형상 갱신 및 문제 티켓 최종 Close

</details>

```text
1. [인시던트 발생 및 1단계: 선 복구 (Incident)]
    ├─ [상황]: 대고객 결제 서버 응답 지연(504 Gateway Timeout) 인입
    ├─ 인시던트 커맨더 즉시 발령 ➔ "원인 분석 중단, 가용성 복구 우선" 지시
    ├─ KEDB 검색 ➔ 2번 WAS 노드 메모리 고갈 확인 ➔ 즉각 트래픽 격리 및 프로세스 재시작
    └─ [결과: 장애 발생 4분 만에 결제 서비스 100% 정상화 (MTTR 달성)]
            │
            ▼
2. [2단계: 문제 관리 이관 및 근본 원인 분석 (Problem)]
    ├─ 복구 완료 후 'Problem-2027-042' 티켓 자동 생성
    ├─ 5-Whys 분석: 세션 타임아웃 객체가 힙 메모리에서 해제되지 않는 소프트웨어 버그 규명
    └─ [조치: KEDB에 "메모리 90% 시 재기동" 우회책 등록 + "세션 누수 수정 패치" 개발 착수]
            │
            ▼
3. [3단계: 변경 요청서(RFC) 작성 및 영향 분석 (Change)]
    ├─ 개발팀이 수정된 코드 패치 완성 ➔ 변경 요청서(RFC-889) 발행
    └─ [CMDB 조회: 해당 결제 모듈과 연계된 12개 마이크로서비스 의존성 및 API 영향도 확인]
            │
            ▼
4. [4단계: CAB 심의 및 롤백 계획 수립]
    ├─ 정기 CAB 회의 소집: 비즈니스 영향도 '중간', 기술 위험도 '낮음' 평가
    ├─ [롤백 대책]: 배포 실패 시 30초 내 이전 컨테이너 이미지로 즉시 롤백 런북 승인
    └─ [배포 승인: 트래픽 최저 시간대인 금일 23:00 카나리(Canary) 배포 확정]
            │
            ▼
5. [5단계: 배포 실행 및 폐쇄 루프 종결]
    ├─ 23:00 ArgoCD 배포 파이프라인 가동 ➔ 카나리 10% ➔ 100% 무중단 배포 완료
    ├─ 24시간 모니터링 결과 메모리 누수 0건 검증
    └─ [CMDB 최신 버전 갱신 ➔ 문제 관리 티켓 및 인시던트 티켓 영구 '완료(Closed)' 종결]
```

**동작 원리**

1. **복구와 해결의 분리(Restore vs Resolve)**: 화재가 났을 때(인시던트)는 불을 끄고 사람을 대피시키는 것이 우선이며, 방화 원인 조사와 내화벽 보강(문제 관리)은 불이 꺼진 뒤에 수행하는 원칙
2. **KEDB를 통한 집단 지성 활용**: 수석 엔지니어가 휴가를 가더라도 초급 운영자가 KEDB의 '우회 조치 매뉴얼'을 보고 즉각 조치하여 장애 복구 시간 80% 단축
3. **변경 통제(Change Enablement)의 안전망**: 아무리 급한 버그 패치라도 반드시 '배포 실패 시 어떻게 되돌릴 것인가(Rollback Plan)'가 사전에 마련되지 않으면 배포 승인 거부
4. **CMDB(구성관리DB) 기반 파급 효과 사전 차단**: 단일 DB 컬럼 타입 변경 시 이 컬럼을 참조하는 다른 10개 서비스가 동시에 깨지는 참사를 CMDB 의존성 맵으로 사전 탐지
5. **폐쇄 루프(Closed-Loop)를 통한 학습하는 조직 구축**: 인시던트 $\rightarrow$ 문제 $\rightarrow$ 변경의 사이클이 1회 완결될 때마다 시스템의 기술 부채가 영구적으로 1건씩 소멸

#### 한줄 요약
- 인시던트 선 복구, 문제 관리 RCA 및 KEDB 등록, RFC 발행 및 CMDB 영향 분석, CAB 승인, 배포 및 종결 순으로 동작한다.

## Ⅴ. 종류 및 비교

<details><summary>용어 설명</summary>

- **변경 관리 3대 핵심 유형 비교**:
  - 표준 변경 (Standard Change): 위험도가 낮고 절차가 검증된 사전 승인 변경 (CI/CD 자동 배포).
  - 일반 변경 (Normal Change): 신규 기능, 아키텍처 수정 등 위험도 평가와 CAB 심의가 필수인 변경.
  - 긴급 변경 (Emergency Change): 서비스 다운 중단 복구를 위해 긴급자문위원회(ECAB)가 신속 승인하는 변경.

</details>

| 비교 항목 | 표준 변경 (Standard Change) | 일반 변경 (Normal Change) | 긴급 변경 (Emergency Change) |
|:---|:---|:---|:---|
| **위험도 및 빈도** | **매우 낮음 / 빈번함 (일 수회)** | **중간 ~ 높음 / 주기적 (스프린트 단위)**| **매우 높음 / 비정기적 (긴급 장애 시)**|
| **승인 절차** | **사전 승인 완료 (No CAB 심의)**| **정기 CAB 위원회 정식 심의 승인**| **긴급 ECAB 구두/전자 초단기 승인**|
| **주요 대상 작업** | 정기 OS 보안 패치, K8s 파드 증설| DB 스키마 변경, 신규 비즈니스 API| 상용 P1 장애 복구용 긴급 핫픽스 |
| **배포 방식** | **CI/CD 파이프라인 자동 무중단 배포**| 정기 점검 시간대 카나리/블루그린 배포| 즉시 롤백 런북을 갖춘 수동 배포 |
| **사후 관리** | 로그 자동 기록 | 배포 완료 후 사후 검토(PIR) | **배포 완료 후 익일 정식 RFC 사후 문서화**|

#### 한줄 요약
- 표준 변경은 사전 승인 자동 배포, 일반 변경은 CAB 정식 심의, 긴급 변경은 ECAB 신속 승인 후 사후 문서화이다.

## Ⅶ. 결론

- 디지털 비즈니스의 무중단 가용성과 엔터프라이즈 신뢰성을 기술적으로 담보하는 가장 강력한 3위일체 운영 공학인 **인시던트·문제·변경 관리 체계**는 단순한 장애 대응 절차를 넘어 실패로부터 학습하고 스스로 진화하는 고신뢰성 조직의 핵심 심장이며, 실무 구현 시 **선 복구(인시던트)와 근본 원인 규명(문제 관리)의 철저한 역할 분리**, **KEDB 지식 베이스를 통한 초단기 우회 복구 역량 확보**, **CMDB 의존성 분석과 롤백 계획 기반의 안전한 변경 통제**, **표준 변경 자동화를 통한 DevOps 민첩성 보증**을 완성하여 최고 수준의 가용성(99.99%)과 무결점 IT 서비스 운영 품질을 완성

#### 한줄 요약
- 인시던트 선 복구, 문제 관리 RCA, 위험 기반 변경 통제의 유기적 연계를 통해 무결점 IT 서비스 운영을 완성한다.
