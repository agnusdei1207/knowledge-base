## Ⅰ. 개요

<details><summary>용어 설명</summary>

- **인시던트 관리**: 중단된 서비스를 가능한 빨리 정상화하는 관행.
- **문제 관리**: 인시던트의 근본 원인을 찾아 재발을 줄이는 관행.
- **변경 활성화**: 위험을 평가해 유익한 변경을 안전하게 실행하는 관행.

</details>

- 정의/개념: 선 복구·원인 제거·안전 변경을 연결하는 **ITSM 운영 폐루프**
- 배경/필요성: IT 서비스 운영 중 장애 발생 시 근본 원인 분석과 긴급 서비스 복구의 역할 분담이 명확하지 않을 경우, 장애 상황에서 원인 규명에 매몰되어 복구 시간(MTTR)이 지연되거나 반대로 통제 없는 무분별한 핫픽스 적용으로 2차·3차 연쇄 장애가 초래되는 치명적 운영 결함이 발생함에 따라, 가용성 회복을 위한 선 복구(Workaround) 중심의 인시던트 관리, 근본 원인 분석(RCA)을 통한 재발 방지 중심의 문제 관리, CMDB 영향 분석 및 롤백 계획 기반의 안전한 변경 관리를 유기적으로 결속한 ITSM 3대 핵심 프랙티스 폐루프를 도입하여 **KEDB(알려진 오류 데이터베이스) 기반의 MTTR 최소화, 표준·일반·긴급 변경 유형별 위험 통제 및 변경 후 CMDB 자동 현행화를 통한 고신뢰성 서비스 거버넌스**를 달성할 필요

#### 한줄 요약
- 인시던트·문제·변경 관리는 복구부터 재발 방지까지 연결한다.

## Ⅱ. 특징

- 근본 분석보다 가용성을 우선하는 **인시던트 선 복구**
- 복구 후 RCA로 재발을 줄이는 **문제 관리**
- 우회책·알려진 오류를 재사용하는 **KEDB**
- 구성 의존성으로 영향을 보는 **CMDB**
- 표준·일반·긴급의 **위험 기반 변경 분류**
- 실패 시 원상복구하는 **롤백 계획**

#### 한줄 요약
- 선 복구, RCA, KEDB, CMDB, 변경 분류, 롤백이 핵심이다.

## Ⅲ. 구조 및 구성요소

```text
┌──────────── ITSM 운영 폐루프 ────────────┐
│                                         │
├── [서비스 데스크·인시던트]              │
│   └── [KEDB]                            │
├── [문제 관리·RCA]                       │
├── [변경 활성화·CAB]                     │
│   └── [CMDB·롤백 계획]                  │
└── [운영 시스템·지식 갱신]               │
```

| 구성요소 | 책임 |
|:---|:---|
| **서비스 데스크·인시던트** | 접수·우선화·우회·신속 복구 |
| **KEDB** | 알려진 오류와 우회책 재사용 |
| **문제 관리·RCA** | 원인·영구 해결책·재발 위험 분석 |
| **변경 활성화·CAB** | 위험별 승인·일정·실행 통제 |
| **CMDB·롤백 계획** | 영향 분석과 실패 복구 보장 |

#### 한줄 요약
- 인시던트 계층은 KEDB의 알려진 우회책을 꺼내 근본 원인 규명을 미루고 가용성을 먼저 사며, 미룬 원인은 문제 관리가 RCA로 받고 그 영구 해결책은 CMDB 영향 분석과 롤백 계획을 갖춘 변경 계층을 거쳐야만 운영에 반영된다.

## Ⅳ. 흐름도

```text
[서비스 사용자]
     │
     └──────── 장애 신고
                 │
                 ▼
           [인시던트 관리]
                 │ 1. 접수·영향도 분류
                 │ 2. KEDB 조회·서비스 복구
                 ▼
            [문제 관리]
                 │ 3. RCA·영구 해결책 도출
                 ▼
            [변경 관리]
                 │ 4. 영향·승인·롤백 계획
                 │ 5. 배포·검증·CMDB 갱신
                 └──────── 복구 결과 반환
```

**동작 원리**

1. **접수·영향도 분류**: 사용자·서비스 영향에 따른 우선순위 결정
2. **KEDB 조회·서비스 복구**: 우회·롤백·절체로 MTTR 최소화
3. **RCA·영구 해결책 도출**: 복구 후 원인과 재발 조건 규명
4. **영향·승인·롤백 계획**: CMDB와 위험 등급으로 변경 통제
5. **배포·검증·CMDB 갱신**: 실행 결과와 구성·지식 최신화

#### 한줄 요약
- 접수된 장애가 KEDB에 이미 등록된 오류인지에서 갈래가 갈려, 적중하면 조회 한 번으로 우회 복구가 끝나지만 미적중이면 RCA와 변경 승인·롤백 계획을 모두 거쳐야 하므로 같은 서비스 중단이라도 복구까지의 시간이 자릿수로 벌어진다.

## Ⅴ. 종류 및 비교

| 비교 항목 | 표준 변경 | 일반 변경 | 긴급 변경 |
|:---|:---|:---|:---|
| 위험 특성 | 낮고 반복적 | 영향·위험 평가 필요 | 장애 복구상 즉시 필요 |
| 승인 방식 | **사전 승인** | 권한자·CAB 심의 | ECAB 등 신속 승인 |
| 실행 방식 | 검증 절차의 자동 실행 | 승인된 창구·계획 실행 | 최소 검증 후 즉시 실행 |
| 롤백 | 표준화된 자동 복구 | 변경별 복구 계획 | 즉시 실행 가능한 복구책 |
| 사후 관리 | 자동 기록·정기 검토 | 결과·PIR 검토 | **사후 정식 기록·검토** |

#### 한줄 요약
- 반복 저위험은 표준, 일반 위험은 정식 심의, 장애는 긴급 변경을 쓴다.

## Ⅵ. 실무 고려사항 및 대책

| 문제 | 대책 |
|:---|:---|
| 장애 중 디버깅으로 복구 지연 | 지휘권 명확화와 **선 복구 원칙** |
| 복구 후 문제 티켓 미생성 | 중대 인시던트의 **RCA 자동 연계** |
| KEDB 우회책의 노후화 | 사용 결과 기반 **지식 검증·갱신** |
| 긴급 변경의 승인·롤백 생략 | ECAB·롤백의 **최소 안전 게이트** |
| 배포 후 CMDB 형상 불일치 | 파이프라인 기반 **구성 자동 갱신** |

#### 한줄 요약
- 선 복구, RCA 연계, 지식 갱신, 안전 게이트, 형상 갱신을 적용한다.

## Ⅶ. 결론

- IT 서비스 장애의 신속 복구와 근본 원인 규명 및 무장애 배포를 상호 견제와 협력의 폐루프로 결속하여 서비스 가용성과 무결성을 보증하는 **IT 서비스 운영의 3대 핵심 프랙티스(Incident, Problem, Change Management / ITSM Trinity & KEDB / RCA & CAB)의 최고 운영 공학 표준**으로 확고히 자리 잡았으며, 사이트 신뢰성 공학(SRE) 및 카오스 엔지니어링/AIOps와 결합하여 자율 복구 체계로 발전하는 가운데, 실무 ITSM 운영 시에는 **장애 발생 시 디버깅을 즉각 중단하고 우회책(Workaround) 중심의 선 복구 원칙 철저 이행, 중대 인시던트 복구 후 RCA 기반 문제 티켓 자동 발행 및 KEDB 최신화 강제, 긴급 변경 시에도 비상 CAB(ECAB) 사전 승인과 100% 검증된 롤백(Rollback) 절차 확보**를 결합하여 완벽한 서비스 연속성을 완성

#### 한줄 요약
- 먼저 서비스를 살리고 원인을 분석해 통제된 변경으로 영구 해결한다.
