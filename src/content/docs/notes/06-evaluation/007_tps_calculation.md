## Ⅰ. 개요

<details><summary>핵심 용어(Core Terms)</summary>

- **TPS(Transactions Per Second)**: 1초 동안 오류나 지연 없이 성공적으로 완료한 비즈니스 업무 거래 또는 쿼리 건수.
- **폐쇄형 부하(Closed Workload Model)**: 인간의 반복적 상호작용 행동(요청-응답-생각시간)을 모사한 테스트 부하 모델.
- **처리율 산정(Throughput Estimation)**: 목표 동시 접속 사용자 수와 서버 응답시간, 사용자의 생각시간을 활용하여 초당 처리량을 도출하는 기법.

</details>

- 정의/개념: 동시 사용자·응답·생각시간의 **처리율 산정**
- 배경/필요성: 회원 수만으로는 **실제 TPS 역산 불가**

#### 한줄 요약

- $N$, $R$, $Z$로 **목표 TPS 산정**

## Ⅱ. 특징

<details><summary>핵심 용어(Core Terms)</summary>

- **대화형 응답시간 법칙(Interactive Response Time Law)**: 폐쇄형 큐 네트워크에서 동시 사용자(N)와 처리량(X), 응답시간(R), 생각시간(Z)이 $N=X(R+Z)$ 관계를 유지한다는 용량 검증 원칙.
- **동시 사용자(N, Concurrent Users)**: 서비스 루프를 반복하며 인프라 부하를 유발하는 유효 사용자 수.
- **부하 보정(Load Calibration)**: 이론적 처리량에 피크타임 집중률, 호출 비율 등 실제 환경 요인을 가중치로 반영하는 작업.

</details>

- **대화형 응답시간 법칙**으로 처리량 관계 산출
- 업무 TPS와 내부 API RPS를 분리 측정
- 피크·업무 비율을 **부하 보정**에 반영

#### 한줄 요약

- 생각시간 증가 시 동일 사용자 대비 **요구 TPS 감소**

## Ⅲ. 구조 및 구성요소

<details><summary>핵심 용어(Core Terms)</summary>

- **응답시간(R, Response Time)**: 요청 출발부터 최종 결과값이 화면에 렌더링을 시작하기 전까지의 왕복 지연 시간.
- **생각시간(Z, Think Time)**: 응답 수신 후 다음 요청 전송까지 사용자가 소비하는 휴지 시간.
- **처리량(X, Throughput)**: 특정 기준 시간 동안 오류 없이 성공적으로 방출된 비즈니스 거래 건수.
- **업무 거래 경계(Business Transaction Boundary)**: 단일 비즈니스 의도 달성을 위해 수행되는 여러 API 호출을 하나로 묶은 트랜잭션 판정 기준.

</details>

```text
TPS 산정 구조
├─ 업무 거래 경계
├─ 동시 사용자 N
├─ 응답시간 R
├─ 생각시간 Z
└─ 처리량 X·피크 보정
```

| 구성요소 | 책임 |
|:---|:---|
| 업무 거래 경계 | 거래 TPS와 API RPS 분리 |
| 동시 사용자 N | **동시 사용자** 규모 측정 |
| 응답시간 R | 목표 **응답시간** 설정 |
| 생각시간 Z | 실제 **생각시간** 반영 |
| 처리량 X·피크 보정 | **처리량·피크 계수** 산출 |

#### 한줄 요약

- $X=N/(R+Z)$ 기반 **처리량·피크 용량 산출**

## Ⅳ. 흐름도

<details><summary>용어 설명</summary>

- **사용자 요청 주기**: 요청·응답·생각시간을 합친 반복 구간이다.
- **업무 혼합**: 운영 거래 유형을 실제 비율로 구성한 부하이다.
- **피크 TPS 보정**: 평균 처리량에 집중률을 반영하는 활동이다.
- **N·R·Z 측정 조건 확정**: 거래 경계와 단위를 정하는 단계이다.
- **N·R·Z 표본 수집**: 동시성·응답·생각시간을 모으는 단계이다.
- **X=N/(R+Z) 계산**: 폐쇄형 평균 처리량을 구하는 단계이다.
- **업무 비율·피크 TPS 보정**: 최종 시험 부하를 정하는 단계이다.

</details>

```text
업무 책임자
   │ 거래 경계·피크 비율 전달
   ▼
분석가·측정기
   │ 1. N·R·Z 측정 조건 확정
   │ 2. N·R·Z 표본 수집
   ▼
계산·검증기
   │ 3. X=N/(R+Z) 계산
   │ 4. 업무 비율·피크 TPS 보정
   ▼
목표 TPS·시험 부하 결과
```

### 동작 원리

1. **N·R·Z 측정 조건 확정**: 사용자 요청 주기 정의
2. **N·R·Z 표본 수집**: 동시성·주기 지연 수집
3. **X=N/(R+Z) 계산**: 폐쇄형 평균 TPS 산출
4. **업무 비율·피크 TPS 보정**: 피크 용량 결정

#### 한줄 요약

- 평균 TPS에 **업무 비율·피크 계수 보정**

## Ⅴ. 종류 및 비교

<details><summary>용어 설명</summary>

- **폐쇄형 부하 모델(Closed Workload Model)**: 시스템 내 동시 사용자 수를 고정하고 이전 요청의 응답과 생각시간이 지난 후 다음 요청을 전송하는 부하 모델.
- **개방형 부하 모델(Open Workload Model)**: 시스템 처리 상태나 응답 여부와 무관하게 사전 정의된 도착률에 따라 독립적으로 요청을 주입하는 부하 모델.
- **초당 요청 수(Requests Per Second, RPS)**: 비즈니스 트랜잭션이 아닌 서버 엔드포인트로 유입되는 개별 HTTP/API 호출의 초당 처리 횟수.
- **부하 모델 선택(Load Model Selection)**: 사용자 인터랙션 기반 웹 서비스는 폐쇄형 모델을, 백엔드 API 및 배치 시스템은 개방형 모델을 적용하는 기준.

</details>

| 비교 항목 | 동시 사용자 모델 (폐쇄형 부하) | 요청률 기반 모델 (개방형 부하) |
|:---|:---|:---|
| 적용 기준 | 사람의 웹·앱 화면 조작 | B2B 및 마이크로서비스 간 API 호출 |
| 핵심 특징 | 사용자 생각시간 기반의 순환 주기 모델 | 독립적 도착률 기반의 연속 요청 주입 |
| 한계 | 생각시간 설정 오류 시 처리량 예측 왜곡 | 시스템 포화 시 큐 누적으로 지연시간 급증 |

> 요약: 사용자 행동 기반 서비스에는 폐쇄형 모델을, 시스템 간 연계 통신에는 개방형 모델을 구분 적용.

#### 한줄 요약

- 사람은 폐쇄형, 기계 호출은 **개방형 모델 선택**.

## Ⅵ. 실무 고려사항 및 대책

<details><summary>용어 설명</summary>

- **업무 거래와 내부 요청(Business Transaction vs API Requests)**: 사용자 관점의 단일 비즈니스 트랜잭션과 이를 처리하기 위해 발생하는 복수의 내부 API 호출 간 구분.
- **피크 계수(Peak Factor)**: 일일 평균 처리량 대비 최대 트래픽 집중 시간대의 부하를 방어하기 위해 적용하는 가중치 배수.
- **경계 혼동(Boundary Confusion)**: 비즈니스 단위 TPS와 인프라 단위 API RPS를 혼용하여 발생하는 용량 산정 오류.

</details>

| 문제 | 대책 | 효과 |
|:---|:---|:---|
| 사용자 생각시간 누락으로 인한 용량 과대 산정 | 실제 사용자 행동 기반 **생각시간(Z)** 실측치 반영 | 과잉 TPS 산정 및 인프라 과투자 방지 |
| 비즈니스 거래와 내부 API 단위 혼용 | **업무 거래와 내부 요청** 분리 모델링 | **경계 혼동** 방지 및 정확한 병목 분석 |
| 평균치 적용으로 피크 시간대 지연 열화 | 트래픽 집중도 기반 **피크 계수** 적용 | 최대 부하 시간대 안정적 처리 용량 확보 |

#### 한줄 요약

- 결제 TPS와 내부 API **RPS 분리 계측**.

## Ⅶ. 결론

<details><summary>용어 설명</summary>

- **부하 현실화(Load Realization)**: 실제 운영 로그를 분석하여 동시 사용자 수, 응답시간, 생각시간, 트랜잭션 비율을 테스트 시나리오에 정밀 동기화하는 절차.
- **과부하(System Overload)**: 트래픽 유입률이 시스템 처리 용량을 초과하여 대기열이 누적되고 응답 실패가 발생하는 포화 상태.
- **목표 부하 선정(Target Workload Selection)**: 서비스 아키텍처 특성에 맞춰 적합한 TPS 산정 공식과 부하 테스트 모델을 채택하는 의사결정.

</details>

- 사람은 $N/(R+Z)$, API는 도달률로 목표 부하 산정

#### 한줄 요약

- 운영 로그로 보정해 **과소 용량·과잉 투자 방지**.
