## Ⅰ. 개요

<details><summary>용어 설명</summary>

- **TPS 계산(Transactions Per Second Calculation / Throughput Sizing)**: 시스템 구축 및 용량 산정(Capacity Planning) 시 비즈니스 목표 거래량(일일/월간 거래 건수)과 사용자 행동 특성(동시 접속자 수, 체류/생각 시간, 응답시간)을 수학적 공식(대화형 응답시간 법칙)에 대입하여 초당 필수 처리 용량(TPS)과 피크(Peak) 부하를 정밀 산출하는 성능 공학 프로세스.
- **생각시간 누락 및 일 평균 평탄화에 따른 용량 산정 왜곡 결함(Flattening & Zero Think-Time Defect)**: 사용자의 생각시간($Z$, Think Time)을 0으로 가정하여 실제 필요 용량보다 10배 이상 인프라를 과다 증설(Over-sizing)하거나, 일일 총 거래량을 단순 24시간으로 균등 분할하여 특정 1시간의 피크 트래픽 집중률(Peak Factor 3~5배)을 반영하지 못해 오픈 당일 서버가 다운되는 구조적 결함.

</details>

- 정의/개념: 사용자 주기와 거래량으로 **TPS**를 구하는 처리량 산정 모델
- 배경/필요성: 일평균으로 평탄화한 거래량은 특정 시간대에 배수로 몰리는 **피크 처리량**을 감춰 오픈 당일 긴급 증설 비용을 뒤늦게 치르게 하므로, 사용자 수·응답시간·생각시간을 묶는 산정식 계층을 용량 결정 앞에 두어 피크 계수까지 반영한 목표 TPS로 대체할 필요

#### 한줄 요약
- TPS 계산은 대화형 응답시간 법칙($X=\frac{N}{R+Z}$)과 피크 계수를 기반으로 시스템의 필수 초당 처리 용량을 수학적으로 산출한다.

## Ⅱ. 특징

<details><summary>용어 설명</summary>

- **TPS 계산 4대 핵심 수리 파라미터**:
  - **동시 사용자 수 ($N$, Concurrent Users)**: 시스템에 로그인하여 지속적으로 화면을 조회하고 요청을 발생시키는 활성 사용자 수.
  - **평균 응답 시간 ($R$, Response Time)**: 요청 전송 후 서버로부터 최종 응답을 수신할 때까지의 시스템 지연 시간 (초).
  - **평균 생각 시간 ($Z$, Think Time)**: 응답 화면을 수신한 후 사용자가 내용을 확인하고 다음 버튼을 클릭할 때까지 머무르는 시간 (초).
  - **피크 집중 계수 (Peak Factor, $F_{peak}$)**: 일일 총 트래픽 중 최대 피크 시간대(1시간)에 집중되는 트래픽의 가중치 배수.

</details>

- 폐쇄형 큐에서 성립하는 **대화형 응답시간 법칙**
- 생각시간이 길수록 동일 사용자 수의 **TPS 감소**
- 피크 계수와 **API 호출 배수**를 반영한 인프라 부하 산출

#### 한줄 요약
- 대화형 응답시간 법칙, 생각시간 반비례 반영, 피크 계수 및 API 증폭 배수 결합을 제공한다.

## Ⅲ. 구조 및 구성요소

<details><summary>용어 설명</summary>

- **TPS 산정 3대 핵심 수식 체계**:
  1. **대화형 폐쇄형 TPS 공식**: $TPS_{base} = \frac{N}{R + Z}$.
  2. **일일 거래량 기반 피크 TPS 공식**: $TPS_{peak} = \frac{\text{Daily Total Transactions} \times F_{peak}}{\text{Peak Operating Seconds}}$.
  3. **내부 API 처리량(RPS) 변환 공식**: $RPS = TPS \times M_{api}$ ($M_{api}$: 화면당 API 호출 수).

</details>

```text
[TPS 산정 변수]
|
+-- [사용자 주기]
|   +-- 응답시간 R
|   `-- 생각시간 Z
|
+-- [처리량]
|   +-- 동시 사용자 N
|   `-- 기준 TPS X
|
`-- [보정 계수]
    +-- 피크 계수 F_peak
    `-- API 호출 배수 M_api
```

선의 의미: TPS 산정 변수의 포함 관계

| 산출 변수 | 기호 | 계산 수식 | 실무 적용 의미 |
|:---|:---|:---|:---|
| 사용자 주기 | $T_{cycle}$ | $R + Z$ | 다음 요청까지의 **순환시간** |
| 기준 처리량 | $TPS_{base}$ | $\frac{N}{R + Z}$ | 동시 사용자 기반 **기준 TPS** |
| 피크 처리량 | $TPS_{peak}$ | $TPS_{base} \times F_{peak}$ | 집중 시간대의 **목표 TPS** |
| 인프라 부하 | $RPS_{total}$ | $TPS_{peak} \times M_{api}$ | 내부 API의 **총 RPS** |

#### 한줄 요약
- 기준 TPS는 동시 사용자와 순환시간에서 한 번만 산출되고 그 위에 피크 계수와 API 호출 배수가 차례로 곱해지므로, 어느 한 보정 계수를 빠뜨리면 그 배수만큼의 용량 부족이 집중 시간대의 장애로만 드러난다.

## Ⅳ. 흐름도

<details><summary>용어 설명</summary>

- **실무 TPS 정밀 산출 및 검증 5단계 프로세스**:
  1. 비즈니스 요구사항(동시 접속자 10,000명, 목표 응답시간 0.2초) 정의
  2. 사용자 로그 분석을 통해 평균 생각시간($Z = 4.8\text{초}$) 및 피크 계수($F_{peak} = 2.0$) 도출
  3. 대화형 응답시간 법칙을 적용하여 기준 TPS($X_{base}$) 계산
  4. 피크 계수와 API 증폭 배수($M_{api} = 3$)를 결합하여 최종 목표 Peak RPS 산출
  5. 부하 시험기(JMeter)에 VUser와 Throughput을 입력하고 성능 목표 검증

</details>

```text
1. 사용자 주기 산정
   R + Z
      |
2. 기준 TPS 계산
   N / (R + Z)
      |
3. 피크 TPS 보정
   TPS_base × F_peak
      |
4. 인프라 RPS 변환
   TPS_peak × M_api
      |
5. 부하 시험 검증
```

**동작 원리**

1. **사용자 주기 산정**: 응답시간과 생각시간의 합산
2. **기준 TPS 계산**: 동시 사용자 수를 사용자 주기로 나눈 처리량
3. **피크 TPS 보정**: 기준 TPS에 피크 계수 반영
4. **인프라 RPS 변환**: 피크 TPS에 API 호출 배수 반영
5. **부하 시험 검증**: 목표 처리량과 응답시간 달성 확인

#### 한줄 요약
- 생각시간 4.8초는 사용자 주기를 늘려 기준 TPS를 낮추는 반면 피크 계수 2.0과 API 증폭 배수 3은 그 값을 다시 곱해 올리므로, 업무 단위 TPS를 그대로 인프라 용량으로 쓰면 실제 요구 RPS를 크게 밑돈다.

## Ⅴ. 종류 및 비교

<details><summary>용어 설명</summary>

- **부하 모델링 2대 수리 방식 비교**:
  - 폐쇄형 부하 모델 (Closed Workload Model): 사용자 기반 ($X = \frac{N}{R+Z}$, 응답 지연 시 유입률 감소).
  - 개방형 부하 모델 (Open Workload Model): 도착률 기반 ($\lambda$ 고정, 응답 지연과 무관하게 지속 주입).

</details>

| 비교 항목 | 폐쇄형 부하 모델 | 개방형 부하 모델 |
|:---|:---|:---|
| 적용 기준 | **사용자 순환형** 서비스 | **독립 요청 도착형** 서비스 |
| 산출 공식 | **$X = \frac{N}{R + Z}$** | **$X = \lambda$** |
| 지연 영향 | 응답 지연 시 **유입률 감소** | 응답 지연에도 **유입률 유지** |
| 한계 | 생각시간 오차로 **TPS 왜곡** | 과부하 시 **대기열 적체** |

#### 한줄 요약
- 폐쇄형 모델은 사람의 대화형 서비스에, 개방형 모델은 시스템 간 독립 API 연계 사이징에 특화된다.

## Ⅵ. 실무 고려사항 및 대책

<details><summary>용어 설명</summary>

- **TPS 계산 실무 적용 시 3대 위험 요소와 엔지니어링 대책**:

</details>

| 문제 | 대책 | 효과 |
|:---|:---|:---|
| 생각시간 누락으로 **TPS 과대 산정** | 로그 기반 **생각시간·페이싱** 적용 | **부하 현실성** 확보 |
| 일평균 적용으로 **피크 TPS 과소 산정** | 시간대별 **피크 계수** 반영 | **집중 부하** 수용 |
| TPS와 RPS 동일시로 **백엔드 과부하** | 거래별 **API 호출 배수** 반영 | **백엔드 용량** 확보 |

#### 한줄 요약
- Think Time 설정으로 부하를 현실화하고, 피크 계수로 집중률을 방어하며, API 배수로 백엔드 용량을 산정한다.

## Ⅶ. 결론

- 사용자 순환형은 **응답시간 법칙**, 독립 도착형은 **도착률** 기반 용량 산정

#### 한줄 요약
- 산정 결과는 생각시간과 피크 계수를 얼마나 보수적으로 잡느냐에 따라 배 단위로 갈리므로, 수식 자체보다 가정의 근거를 남기는 것이 재산정 비용을 줄인다.
