## Ⅰ. 개요

<details><summary>용어 설명</summary>

- **TPS 계산(Transactions Per Second Calculation / Throughput Sizing)**: 시스템 구축 및 용량 산정(Capacity Planning) 시 비즈니스 목표 거래량(일일/월간 거래 건수)과 사용자 행동 특성(동시 접속자 수, 체류/생각 시간, 응답시간)을 수학적 공식(대화형 응답시간 법칙)에 대입하여 초당 필수 처리 용량(TPS)과 피크(Peak) 부하를 정밀 산출하는 성능 공학 프로세스.
- **생각시간 누락 및 일 평균 평탄화에 따른 용량 산정 왜곡 결함(Flattening & Zero Think-Time Defect)**: 사용자의 생각시간($Z$, Think Time)을 0으로 가정하여 실제 필요 용량보다 10배 이상 인프라를 과다 증설(Over-sizing)하거나, 일일 총 거래량을 단순 24시간으로 균등 분할하여 특정 1시간의 피크 트래픽 집중률(Peak Factor 3~5배)을 반영하지 못해 오픈 당일 서버가 다운되는 구조적 결함.

</details>

- 정의/개념: 비즈니스 요구사항에 부합하는 최적의 서버 용량을 산정하기 위해 **비즈니스 트랜잭션 경계 확립 $\rightarrow$ 동시 사용자 수($N$), 목표 응답시간($R$), 평균 생각시간($Z$) 측정 $\rightarrow$ 대화형 응답시간 공식($X = \frac{N}{R+Z}$) 기반 기준 TPS 산출 $\rightarrow$ 피크 계수(Peak Factor) 및 API 증폭 배수 반영 $\rightarrow$ 최종 목표 Peak TPS 및 인프라 사이징 확정** 을 집행하는 **수리적 처리량 산정 모델**
- 배경/필요성: 무조건적인 인프라 과투자나 용량 부족에 따른 오픈 장애를 방지하고, 성능 테스트(JMeter)의 입력 파라미터(VUser, Target Throughput)에 대한 수학적 타당성을 제공하기 위해 체계적인 TPS 산정 공식 필요

#### 한줄 요약
- TPS 계산은 대화형 응답시간 법칙($X=\frac{N}{R+Z}$)과 피크 계수를 기반으로 시스템의 필수 초당 처리 용량을 수학적으로 산출한다.

## Ⅱ. 특징

<details><summary>용어 설명</summary>

- **TPS 계산 4대 핵심 수리 파라미터**:
  - **동시 사용자 수 ($N$, Concurrent Users)**: 시스템에 로그인하여 지속적으로 화면을 조회하고 요청을 발생시키는 활성 사용자 수.
  - **평균 응답 시간 ($R$, Response Time)**: 요청 전송 후 서버로부터 최종 응답을 수신할 때까지의 시스템 지연 시간 (초).
  - **평균 생각 시간 ($Z$, Think Time)**: 응답 화면을 수신한 후 사용자가 내용을 확인하고 다음 버튼을 클릭할 때까지 머무르는 시간 (초).
  - **피크 집중 계수 (Peak Factor, $F_{peak}$)**: 일일 총 트래픽 중 최대 피크 시간대(1시간)에 집중되는 트래픽의 가중치 배수.

</details>

- **대화형 응답시간 법칙(Interactive Response Time Law)의 완전성**: 폐쇄형 큐잉 시스템에서 $N = X(R + Z) \iff X = \frac{N}{R + Z}$ 관계가 수학적으로 완벽히 성립
- **생각시간($Z$)과 요구 TPS의 반비례 관계**: 사용자의 체류/생각시간이 길어질수록 동일한 동시 사용자($N$) 규모에서 시스템이 처리해야 하는 초당 트랜잭션 수($X$)는 대폭 감소
- **피크 집중도와 API 호출 배수의 복합 반영**: 단순 일일 평균 TPS에 피크 집중률($F_{peak}$)과 1개 화면 트랜잭션당 유발되는 내부 REST API 호출 수(API Multiplier)를 곱하여 인프라 실부하 도출

#### 한줄 요약
- 대화형 응답시간 법칙, 생각시간 반비례 반영, 피크 계수 및 API 증폭 배수 결합을 제공한다.

## Ⅲ. 구조 및 구성요소

<details><summary>용어 설명</summary>

- **TPS 산정 3대 핵심 수식 체계**:
  1. **대화형 폐쇄형 TPS 공식**: $TPS_{base} = \frac{N}{R + Z}$.
  2. **일일 거래량 기반 피크 TPS 공식**: $TPS_{peak} = \frac{\text{Daily Total Transactions} \times F_{peak}}{\text{Peak Operating Seconds}}$.
  3. **내부 API 처리량(RPS) 변환 공식**: $RPS = TPS \times M_{api}$ ($M_{api}$: 화면당 API 호출 수).

</details>

```text
┌─────────────────────────────────────────────────────────────────────────┐
│ [ 1. 대화형 사용자 트랜잭션 순환 주기 (User Interaction Cycle) ]        │
│                                                                         │
│  ┌───────────────────────────────┐     요청 전송      ┌───────────────┐ │
│  │ 사용자 단말 (Client)          │ ─────────────────► │ 서버 (Server) │ │
│  │ (생각 시간: Think Time Z = 3초)│ ◄───────────────── │ (응답시간 R)  │ │
│  └───────────────────────────────┘     응답 반환      └───────────────┘ │
│  1회 사용자 순환 주기 = 응답시간 (R) + 생각시간 (Z) = 0.2초 + 3.0초 = 3.2초│
│  동시 사용자 N = 1,000명일 때 ➔ 시스템 처리량 X = 1,000 / 3.2 = 312.5 TPS│
└────────────────────────────────────┬────────────────────────────────────┘
                                     │ (피크 집중률 및 API 배수 결합)
                                     ▼
┌─────────────────────────────────────────────────────────────────────────┐
│ [ 2. 실무 피크 TPS 및 인프라 RPS 종합 산출 공식 체계 ]                 │
│                                                                         │
│  ┌───────────────────────────────────────────────────────────────────┐  │
│  │ $\text{Target Peak TPS} = \frac{N}{R + Z} \times F_{peak}$         │  │
│  │ $\text{Total Infrastructure RPS} = \text{Target Peak TPS} \times M_{api}$ │
│  └───────────────────────────────────────────────────────────────────┘  │
│  ├─ N: 동시 접속 사용자 수 (Concurrent Users)                           │
│  ├─ R: 목표 서비스 응답시간 (초)                                        │
│  ├─ Z: 사용자 평균 생각시간 (초)                                        │
│  ├─ $F_{peak}$: 피크 시간대 집중 계수 (일반적으로 1.5 ~ 3.0)            │
│  └─ $M_{api}$: 비즈니스 화면 1회 호출당 발생하는 내부 API 호출 수 (2 ~ 5배)│
└─────────────────────────────────────────────────────────────────────────┘
```

선의 의미: 사용자의 생각시간과 시스템 응답시간의 순환 주기를 기반으로 피크 계수와 API 호출 배수를 결합하여 최종 RPS를 도출하는 구조

| 산출 변수 | 기호 | 계산 수식 | 실무 적용 의미 |
|:---|:---|:---|:---|
| **사용자 주기** | $T_{cycle}$ | $T_{cycle} = R + Z$ | 사용자 1명이 다음 요청을 보낼 때까지의 총 시간 |
| **기준 처리량** | $TPS_{base}$ | $TPS_{base} = \frac{N}{R + Z}$ | 평시 동시 접속자 수 기반의 기본 트랜잭션 처리량 |
| **피크 처리량** | $TPS_{peak}$ | $TPS_{peak} = TPS_{base} \times F_{peak}$ | 특정 피크 시간대(이벤트, 출근 시간) 요구 처리량 |
| **인프라 부하** | $RPS_{total}$| $RPS_{total} = TPS_{peak} \times M_{api}$ | Web/WAS/DB가 실제 처리해야 할 초당 총 API 요청 수 |

#### 한줄 요약
- 사용자 주기($R+Z$), 기준 TPS($\frac{N}{R+Z}$), 피크 TPS($\times F_{peak}$), 인프라 RPS($\times M_{api}$)로 구성된다.

## Ⅳ. 흐름도

<details><summary>용어 설명</summary>

- **실무 TPS 정밀 산출 및 검증 5단계 프로세스**:
  1. 비즈니스 요구사항(동시 접속자 10,000명, 목표 응답시간 0.2초) 정의
  2. 사용자 로그 분석을 통해 평균 생각시간($Z = 4.8\text{초}$) 및 피크 계수($F_{peak} = 2.0$) 도출
  3. 대화형 응답시간 법칙을 적용하여 기준 TPS($X_{base}$) 계산
  4. 피크 계수와 API 증폭 배수($M_{api} = 3$)를 결합하여 최종 목표 Peak RPS 산출
  5. 부하 시험기(JMeter)에 VUser와 Throughput을 입력하고 성능 목표 검증

</details>

```text
1. [비즈니스 요구사항 정의]
    ├─ 동시 접속 활성 사용자 수: $N = 10,000\text{명}$
    ├─ 비즈니스 목표 응답시간: $R = 0.2\text{초}$ (200ms)
    └─ [화면 1회당 내부 REST API 호출 수: $M_{api} = 3\text{회}$]
            │
            ▼
2. [사용자 행동 로그 분석 (Think Time & Peak Factor)]
    ├─ 웹 로그 기반 사용자 클릭 간격 분석: $Z = 4.8\text{초}$
    └─ [피크 시간대(12:00~13:00) 트래픽 집중 계수: $F_{peak} = 2.0$]
            │
            ▼
3. [대화형 응답시간 법칙 적용 (기준 TPS)]
    ├─ 1회 요청 순환 주기: $R + Z = 0.2 + 4.8 = 5.0\text{초}$
    ├─ 기준 TPS 산출: $TPS_{base} = \frac{N}{R + Z} = \frac{10,000}{5.0} = 2,000 \text{ TPS}$
    └─ [평시 시스템은 초당 2,000건의 비즈니스 거래를 처리해야 함]
            │
            ▼
4. [피크 TPS 및 인프라 RPS 확정]
    ├─ 피크 시간대 비즈니스 처리량: $TPS_{peak} = 2,000 \times 2.0 = 4,000 \text{ TPS}$
    ├─ WAS/DB 인프라 요구 처리량: $RPS_{total} = 4,000 \times 3 = 12,000 \text{ RPS}$
    └─ [인프라 사이징 목표: 12,000 RPS를 p99 200ms 이내로 처리하는 서버 스펙 산정]
            │
            ▼
5. [부하 테스트 파라미터 매핑 및 검증]
    ├─ JMeter에 10,000 VUser, Pacing/Think Time 4.8초, Ramp-up 10분 설정
    └─ [실측 결과: 4,000 TPS 및 12,000 RPS 달성 확인 ➔ 용량 산정 정합성 입증]
```

**동작 원리**

1. **폐쇄형 큐의 순환성**: 사용자가 이전 요청의 응답을 받아야만 생각시간($Z$) 후 다음 요청을 전송하므로, 응답시간($R$)이 늘어나면 자연스럽게 유입 속도가 감소하는 자기 조절(Self-throttling) 메커니즘 반영
2. **단위 시간 정합성**: 모든 시간 파라미터($R, Z$)를 초(Seconds) 단위로 통일하여 초당 완료 건수(TPS)와의 수학적 일관성 유지
3. **화면 거래와 API 호출의 괴리 극복**: 사용자가 '주문하기' 버튼 1회를 누를 때 내부적으로 인증, 재고 차감, 결제 승인 등 3개의 API가 호출되는 현상을 $M_{api}$ 계수로 정확히 모델링
4. **피크 트래픽 방어**: 일 평균 데이터에 매몰되지 않고 피크 계수($F_{peak}$)를 곱하여 이벤트 시간대 서버 다운 원천 차단
5. **용량 산정의 투명성 확보**: 직관적 추정이 아닌 수리 공식($X = \frac{N}{R+Z}$)에 입각하여 경영진 및 인프라팀에 명확한 증설 근거 제시

#### 한줄 요약
- 요구사항 정의, Think Time/피크 계수 도출, 대화형 공식 기준 TPS 계산, 피크 RPS 확정, 부하 검증 순으로 동작한다.

## Ⅴ. 종류 및 비교

<details><summary>용어 설명</summary>

- **부하 모델링 2대 수리 방식 비교**:
  - 폐쇄형 부하 모델 (Closed Workload Model): 사용자 기반 ($X = \frac{N}{R+Z}$, 응답 지연 시 유입률 감소).
  - 개방형 부하 모델 (Open Workload Model): 도착률 기반 ($\lambda$ 고정, 응답 지연과 무관하게 지속 주입).

</details>

| 비교 항목 | 폐쇄형 부하 모델 (Closed Model) | 개방형 부하 모델 (Open Model) |
|:---|:---|:---|
| **수리 산출 공식** | $X = \frac{N}{R + Z}$ (대화형 응답시간 법칙)| $X = \lambda$ (포아송 독립 도착률) |
| **주요 적용 대상** | **사람이 조작하는 웹/모바일 대화형 서비스**| **B2B 연계, IoT 센서 데이터 수집, 배치 큐**|
| **응답 지연 시 동작**| **유입률 자동 감소 (Self-throttling)** | **유입률 유지 (대기열 무한 적체 및 붕괴)**|
| **핵심 입력 변수** | **동시 사용자 수($N$), 생각 시간($Z$)** | **초당 유입 요청률($\lambda$)** |
| **실무 적합성** | 쇼핑몰, 인터넷 뱅킹, 사내 포털 사이징 | 메시지 큐(Kafka), 웹훅(Webhook) 처리기 |

#### 한줄 요약
- 폐쇄형 모델은 사람의 대화형 서비스에, 개방형 모델은 시스템 간 독립 API 연계 사이징에 특화된다.

## Ⅵ. 실무 고려사항 및 대책

<details><summary>용어 설명</summary>

- **TPS 계산 실무 적용 시 3대 위험 요소와 엔지니어링 대책**:

</details>

| 문제 | 대책 | 효과 |
|:---|:---|:---|
| 성능 시험 도구(JMeter)에서 Think Time을 0으로 설정하여 **10,000명의 동시 사용자가 50,000 TPS의 비현실적 부하를 유발하며 테스트 시작 10초 만에 서버 다운** | **실제 사용자 로그를 기반으로 Think Time(예: 4.8초)과 Pacing을 엄격히 설정하여 현실적인 2,000 TPS 부하 모델링** | 비현실적 과부하 방지 및 정확한 운영 환경 모사 |
| 1일 총 주문 건수(86,400건)를 86,400초로 단순 분할하여 **평균 1 TPS로 계산했다가 점심 피크 시간대(초당 30 TPS 집중)에 서버 다운 발생** | **피크 시간대(1시간) 집중률(예: 일일 거래의 40%)을 반영하는 피크 계수 공식($TPS_{peak} = \frac{86,400 \times 0.40}{3,600} = 9.6\text{ TPS}$) 적용** | 피크 트래픽 수용 용량 100% 확보 |
| 프론트엔드 비즈니스 트랜잭션(TPS)과 백엔드 마이크로서비스 API 호출량(RPS)을 **동일시하여 백엔드 MSA 서버 및 DB가 3배 과부하로 연쇄 마비** | **화면 트랜잭션당 내부 API 호출 배수($M_{api}$)를 곱한 종합 RPS를 산출하여 백엔드 및 DB 커넥션 풀 사이징** | 마이크로서비스 연쇄 호출에 따른 백엔드 병목 사전 차단 |

#### 한줄 요약
- Think Time 설정으로 부하를 현실화하고, 피크 계수로 집중률을 방어하며, API 배수로 백엔드 용량을 산정한다.

## Ⅶ. 결론

- 비즈니스 요구사항을 기술적 인프라 스펙으로 정확하게 변환하는 성능 공학의 기초 수리 도구인 **TPS 계산 체계**는 인프라 과투자와 오픈 장애를 동시에 방어하는 핵심 방법론이며, 실무 구현 시 **대화형 응답시간 법칙($X = \frac{N}{R+Z}$) 기반의 정밀한 동시성 모델링**, **실제 사용자 행동 로그 기반의 Think Time 실측**, **피크 시간대 집중 계수($F_{peak}$) 반영**, **마이크로서비스 API 증폭 배수($M_{api}$)를 결합한 종합 인프라 RPS 도출**을 완성하여 최고 수준의 비용 효율성과 예측 가능한 시스템 안정성을 완성

#### 한줄 요약
- $X=\frac{N}{R+Z}$ 공식과 피크 계수 및 API 배수 결합을 통해 무결점 TPS 용량 산정을 완성한다.
