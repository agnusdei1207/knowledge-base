## Ⅰ. 개요

<details><summary>핵심 용어</summary>

- **TPS(Transactions Per Second, 초당 처리 트랜잭션 수)**: 시스템이 1초 동안 어떠한 오류나 지연 지시 없이 성공적으로 완료해 낸 비즈니스 업무 거래 또는 쿼리의 건수로, 서버 용량 판단의 최우선 척도.
- **폐쇄형 부하(Closed Workload Model, 반복 사용자 부하 모델)**: 고정된 수의 가상 사용자들이 시스템에 접속해 한 번 요청을 보내고, 응답을 받은 뒤 일정 시간 동안 화면을 살피고(생각시간) 다시 다음 요청을 이어가는 인간의 반복적 상호작용 행동을 모사한 테스트 부하 모델.
- **처리율 산정(Throughput Estimation, 용량 계산법)**: 목표 동시 접속 사용자 수를 서버 응답시간과 사용자의 생각시간을 더한 전체 한 사이클 시간으로 나누어, 시스템이 초당 감당해야 할 논리적인 평균 TPS를 수치로 도출해 내는 핵심 공식($X = N / (R + Z)$).

</details>

- 정의/개념: 인간 사용자의 행동을 본뜬 **폐쇄형 부하** 모델 전제하에서, 시스템에 머무는 동시 사용자와 서버 응답시간 및 사용자 생각시간 변수를 엮어 목표 인프라의 요구 **처리율 산정**을 수학적으로 도출하는 기법.
- 배경/필요성: 시스템에 가입한 누적 회원 수나 단순 일일 방문자 수와 같은 모호한 마케팅 지표만으로는 찰나의 순간에 요청을 대기하는 사용자의 생각시간(Think Time) 텀이 반영된 실제 시스템 인가 **TPS** 부하를 역추산할 수 없기 때문.

#### 한줄 요약

- 시스템 수용 용량을 기획할 때, 동시 접속 유저 규모(N), 서버 처리 대기 시간(R), 사용자의 행동 휴지기인 생각시간(Z) 간의 상관 공식으로 정교한 목표 초당 트랜잭션을 산정하는 로직 수행

## Ⅱ. 특징

<details><summary>핵심 용어</summary>

- **대화형 응답시간 법칙(Interactive Response Time Law)**: 대기열 시스템 이론에 근거하여 폐쇄형 큐 네트워크 내에서 동시 사용자(N) 규모가 전체 처리량(X)과 응답시간(R) 및 생각시간(Z)의 합 간의 수식 $N=X(R+Z)$를 완벽히 만족하며 밸런스를 유지한다는 용량 검증 원칙.
- **동시 사용자($N$, Concurrent Users, 활성 세션 사용자)**: 특정 관측 시점이나 기간 동안 시스템 세션을 맺고 페이지를 둘러보거나 요청을 보내며 서비스 루프(요청-응답-생각) 주기를 반복하고 있는 유효 인프라 부하 유발자 수.
- **부하 보정(Load Calibration, 트래픽 튜닝)**: 수학 공식으로 단순 도출된 평균적인 처리량 데이터에 특정 이벤트 시의 피크타임 집중률(Peak Ratio), 비즈니스별 API 호출 비율, 사용자의 평균 이탈률 등 현실 요인을 추가 가중치로 얹어 요구 용량 산출을 실제 서비스 환경 스펙에 완벽히 맞추는 고도화 작업.

</details>

- 리틀의 법칙에서 파생된 **대화형 응답시간 법칙**을 활용하여 활성 **동시 사용자** 규모와 시스템 처리량 간의 상호 지탱 역학을 정밀 수식화.
- 화면 단의 포괄적인 업무 거래 TPS와, 이면에서 분산 구동되는 다수의 마이크로서비스 내부 요청 RPS를 뚜렷이 분리하여 아키텍처 단위 혼선 회피.
- 도출된 평균 트래픽 수치에 **부하 보정** 프로세스를 필수로 접목하여, 순간 피크 폭주나 업무 비중 편차, 현실적인 생각시간 지연 여유를 튜닝 반영.

#### 한줄 요약

- 사용자가 웹페이지 텍스트를 읽느라 요청을 쉬는 생각시간(Think Time)이 길어지면 인프라 유입 주기가 완화되어 동일 동시 사용자 수 대비 시스템 요구 TPS가 하락하는 원리 활용

## Ⅲ. 구조 및 구성요소

<details><summary>핵심 용어</summary>

- **응답시간($R$, Response Time, 서버 지연시간)**: 사용자의 단말기에서 패킷이 출발한 시점부터 네트워크를 거쳐 서버에서 실행되고 최종 결과값이 화면에 렌더링을 시작하기 전까지 걸린 왕복 딜레이 시간.
- **생각시간($Z$, Think Time, 휴지 시간)**: 시스템으로부터 유효한 응답을 전달받은 사용자가 화면의 내용을 읽고, 다음 클릭이나 입력 액션을 판단하여 재요청을 보내기까지 소비한 무응답 대기 시간.
- **처리량($X$, Throughput, 완료 거래량)**: 시스템이 1초, 혹은 1분 단위 등 특정 기준 시간 동안 에러 없이 온전하게 성공 방출한 비즈니스 거래 건수로 통상 TPS 지표를 지칭.
- **업무 거래 경계(Business Transaction Boundary, 트랜잭션 획정)**: 로그인, 결제 등 사용자의 단일 비즈니스 의도를 완수하기 위해 수반되는 여러 개의 백엔드 API와 DB 호출을 하나로 묶어 '1건의 완전한 TPS'로 판정하는 논리적 구획 기준.

</details>

```text
                         [업무 거래 경계]
                                |
          +---------------------+---------------------+
          |                     |                     |
[동시 사용자 N]          [응답시간 R]          [생각시간 Z]
          |                     |                     |
          +---------------------+---------------------+
                                |
                     [처리량 X•피크 보정]
```

선의 의미: 명확히 선언된 '업무 거래 경계' 안에서, 독립 변수인 동시 사용자, 서버 응답시간, 사용자의 생각시간이 하나의 수학적 관계로 맞물려 최종 종속 변수인 '처리량(TPS)과 피크 집중 용량'을 논리적으로 산출해 내는 정적 역학 구조망.

| 계산 구성요소 | 기능적 산정 역할 및 책임 |
|:---|:---|
| 업무 거래 경계 | 내부 백엔드 API 단건 요건과 비즈니스 화면 처리 요건이 혼용되지 않도록 **업무 거래 경계**를 명확히 분리 정의 |
| 동시 사용자 N | 마케팅 목표 접속자 수나 현행 세션 로그를 바탕으로 유효한 **동시 사용자 N** 규모 계측 |
| 응답시간 R | 사용자가 답답함을 느끼지 않는 비즈니스적 허용 최대 **응답시간 R** 목표(SLO) 타겟 값 확정 |
| 생각시간 Z | 화면 복잡도에 따라 유저가 문서를 읽는 데 소비할 현실적인 **생각시간 Z** 통계치 계측 및 반영 |
| 처리량 X•피크 보정 | 변수 결합식으로 도출한 평균 **처리량 X** 수치에 시간대별 트래픽 **집중률** 계수를 더해 용량 산출 보강 |

#### 한줄 요약

- 서버가 감당해야 할 인프라 처리 요구 건수는 유입되는 활성 동시 접속자 수치와, 서버의 신속한 응답 역량 및 사용자의 화면 관찰 대기 시간에 의해 상호 억제 및 팽창하며 산출

## Ⅳ. 흐름도

<details><summary>핵심 용어</summary>

- **사용자 요청 주기(User Request Cycle, 트랜잭션 1주기)**: 단일 사용자가 1회의 요청 전송, 서버 응답 대기 시간 수용, 화면 확인을 위한 생각시간을 모두 소화한 뒤 다음 신규 요청을 쏘기까지의 총 반복 루프 구간 단위.
- **업무 혼합(Workload Mix, 부하 트랜잭션 믹스)**: 조회형, 등록형, 삭제형 등 다양한 종류의 거래 성격을 라이브 운영 서버의 실제 트래픽 비율(예: 조회 80, 가입 5, 결제 15 등)에 맞게 섞어 구성한 가상 테스트 부하 컴포넌트 세트.
- **피크 TPS 보정(Peak TPS Calibration, 최대 트래픽 가중치 변환)**: 24시간 분산 평균 산술식으로 얻은 너무 밋밋한 맹탕 처리량 수치를 탈피하여, 단시간 트래픽 폭주(출근 시간대 등) 비율 및 업무 복잡도 등을 가중 곱셈하여 인프라 무정지 확보를 위한 최종 피크타임 최대 한계 목표 수치로 치환하는 용량 산출 프로세스.
- **N•R•Z 측정 조건 확정(Parameter Baseline Definition)**: 공식에 대입하기 위한 유효 트랜잭션 경계, 분석 대상 피크타임 구간, 그리고 기초 표본 데이터를 얼마나 광범위하게 수집할지 사전 정의하는 준비 단계.
- **N•R•Z 표본 수집(Data Sampling)**: 웹 로그 및 APM 툴을 사용하여 현재 라이브 세션 접속 유저 수, 지연시간 분포, 세션 간 휴지기(Think Time) 실측 원시 데이터를 대량 긁어모으는 데이터 확보 단계.
- **X=N/(R+Z) 계산(Mathematical Execution)**: 수집된 유효 평균값들을 폐쇄형 사용자 주기 대화형 공식에 직접 치환 대입하여 논리적인 1차 평균 초당 비즈니스 처리량을 도출하는 수학적 연산 단계.
- **업무 비율•피크 TPS 보정(Ratio & Peak Adjustment)**: 도출된 1차 결과에 마케팅 캠페인 집중률(Peak Factor) 및 다중 API 호출 구조를 배수로 반영하여, 하드웨어 구매 스펙 결정에 직결되는 최종 부하량 타겟으로 스케일업하는 튜닝 단계.

</details>

```text
업무 책임자
   │ 거래 경계·피크 비율 전달
   ▼
분석가·측정기
   │ 1. N•R•Z 측정 조건 확정
   │ 2. N•R•Z 표본 수집
   ▼
계산·검증기
   │ 3. X=N/(R+Z) 계산
   │ 4. 업무 비율•피크 TPS 보정
   ▼
목표 TPS·시험 부하 결과
```

### 동작 원리

1. **N•R•Z 측정 조건 확정**: 단건 API 쿼리가 아닌, 덩어리 비즈니스 관점의 **사용자 요청 주기** 범위를 기반으로 깐깐한 **N•R•Z 측정 조건 확정**을 선행 수립한다.
2. **N•R•Z 표본 수집**: 현행 로그 기반 APM이나 트래픽 시뮬레이션 데이터를 통한 **N•R•Z 표본 수집**으로 동시 유저 규모와 사이클 딜레이 데이터 수집.
3. **X=N/(R+Z) 계산**: 추출된 팩트 데이터들을 공식에 대입하는 **X=N/(R+Z) 계산** 과정을 거쳐 폐쇄형 루프 기반의 기초 평균 TPS 인프라 수치 연산.
4. **업무 비율•피크 TPS 보정**: 밋밋한 산술 평균에 트래픽 쏠림과 무거운 **업무 혼합** 비율 가중치를 더하는 **피크 TPS 보정**을 적용하여 무정지 용량 방어선 최종 픽스.

#### 한줄 요약

- 비즈니스 핵심 사용자 시나리오를 설정하고 세션 지표를 도출한 후, 수식을 활용해 목표 인프라 TPS를 역산하고 이를 피크타임 집중률로 다시 재보정하여 용량의 사각지대 해소

## Ⅴ. 종류 및 비교

<details><summary>핵심 용어</summary>

- **폐쇄형 부하 모델(Closed Workload Model, 제어형 유입 모델)**: 시스템 내에 머무는 가상 사용자의 총수를 엄격하게 제한하고 유지시키면서, 앞선 요청의 응답과 생각시간이 지난 후에만 다음 트래픽이 쏟아지는 웹 유저 시뮬레이션 기반 성능 모델.
- **개방형 부하 모델(Open Workload Model, 발산형 유입 모델)**: 대상 시스템의 처리 응답이나 혼잡 여부에 일체 아랑곳하지 않고, 사전에 입력된 초당 도달률(Arrival Rate)에 따라 맹목적으로 무한 트래픽 신규 요청을 쏟아내는 가혹한 인프라 융단폭격 부하 모델.
- **RPS(Requests Per Second, 초당 시스템 호출 빈도)**: 사용자 비즈니스 거래 단위가 아닌, 프론트엔드에서 서버로 쏘는 개별적인 HTTP 스크립트나 API 쿼리 단위의 초당 처리 속도 횟수 지표.
- **API(Application Programming Interface)**: 애플리케이션 간에 데이터를 주고받고 시스템 기능을 제어할 수 있도록 약속된 기술적 연결 호출 통신 규격.
- **모델 선택(Load Model Selection Strategy)**: 시스템의 특성에 맞게, 사람이 화면을 바라보며 조작하는 B2C 서비스는 생각시간을 품은 폐쇄형 모델을 택하고, 기계 간 무한 릴레이 호출이 잦은 B2B API 중계 서버는 무자비한 개방형 모델을 채택하는 아키텍트의 분석 기조.

</details>

| 시뮬레이션 부하 생성 모델 | 동시 사용자 모델 (폐쇄형 부하) | 요청률 기반 모델 (개방형 부하) |
|:---|:---|:---|
| 시스템 적용 기준 타겟 | 웹브라우저/앱을 구동하는 사람 형태의 트래픽 모사 | B2B 모듈 및 서버 간 기계적인 무차별 **API** 호출 통신 |
| 핵심 테스트 메커니즘 차이 | 큐 제어가 가미된 **폐쇄형 부하 모델** 수식 연산(N/R+Z) 도입 | 응답 확인 없이 트래픽을 주입하는 **개방형 부하 모델** 도달률 적용 |
| 성능 검증 시 함정 및 한계 | 무리하게 짧은 생각시간(Z) 입력 시 용량 요구 수치가 기형적으로 폭발하는 왜곡 | 시스템이 지연되어도 봇이 무한 요청을 누적 인가하여 타임아웃 과부하 유발 |

> 요약: 타겟 애플리케이션의 유입 패턴 주체를 인간으로 볼 것인지 기계 통신으로 볼 것인지에 따라 **모델 선택** 전략을 이원화 적용.

#### 한줄 요약

- 유저가 화면을 눈으로 살피고 다음 액션을 기다리는 템포를 고려하는 정교한 연산법과, 외부 시스템이나 매크로가 기계적으로 쿼리를 쏟아붓는 방식의 처리량 계산 모델 비교 운용

## Ⅵ. 실무 고려사항 및 대책

<details><summary>핵심 용어</summary>

- **업무 거래와 내부 요청(Business Transaction vs Internal Calls)**: 유저 입장의 단일 클릭 로그인 트랜잭션 1건(업무 거래)과, 그 1건을 달성하기 위해 뒤에서 발생하는 사용자DB 조회, 세션 Redis 업데이트, 인증 API 호출 등 3~4건의 종속 요청(내부 요청)을 철저히 구분한 성능 설계 단위.
- **피크 계수(Peak Factor, 시간대별 집중 할증률)**: 시스템의 24시간 총 처리량을 86,400초(1일)로 나눈 밋밋한 분당 평균치에 만족하지 않고, 출근길이나 예매 오픈 시간대 등 단시간에 전체 트래픽의 30~50%가 몰리는 폭증 시점의 용량 방어를 위해 곱셈 적용하는 보정 배수(보통 2~5배 이상).
- **경계 혼동(Boundary Confusion, 메트릭 집계 오류)**: 모니터링 툴 대시보드 상에서 비즈니스 트랜잭션 1 TPS와 시스템 내부 API 호출 단위 RPS 지표를 짬뽕시켜, 실제 시스템이 감당 중인 부하 규모를 3~4배 이상 과대 포장하여 과잉 투자를 야기하는 치명적 팩트 분석 오류.

</details>

| 실무 용량 산출 시 범하는 치명적 문제점 | 현장 엔지니어링 대책 및 수식 튜닝 전략 | 용량 최적화 획득 효과 |
|:---|:---|:---|
| 사용자 시나리오상 대기 시간인 생각시간 변수 누락 처리 | 시스템 도메인에 특화된 유저 분석을 통한 **생각시간(Z)** 수식 엄격 적용 | 무한 TPS 폭주 계산 방지로 불필요한 과잉 인프라 투자 사전 차단 |
| 비즈니스 트랜잭션 한 건과 하위 개별 API 호출의 단위 혼용 측정 | **업무 거래와 내부 요청** 호출 레이어를 명확히 분리하여 **경계 혼동** 철벽 방어 | 개발/인프라/기획 조직 간의 소통 오류 종식 및 용량 뻥튀기 오산정 타파 |
| 평균 수치에 매몰되어 폭주 시간에 발생하는 서버 마비 사각지대 은폐 | 로그 트래픽 분산도 분석 기반 합리적인 **피크 계수** 펌핑(Multiplier) 강제 할당 | 오픈 이벤트 집중 시간대의 단기 극단적 과부하 스파이크 무정지 대응력 현실화 |

#### 한줄 요약

- 상품 결제 완료라는 비즈니스 1 TPS를 달성하기 위해 엮여 있는 다수의 마이크로서비스 개별 API 초당 호출 건수(RPS)를 아키텍처 관점에서 엄격히 분리 계측하는 구조 확립

## Ⅶ. 결론

<details><summary>핵심 용어</summary>

- **부하 현실화(Load Realization, 테스트 인프라 정합성 동기화)**: 책상머리에서 도출한 이론 수식에서 벗어나, 현재 운영 중인 시스템 로그 통계 기반의 진짜 동시 유저 규모, 유효 체감 응답시간, 유저별 페이지 체류시간(생각시간), 그리고 트랜잭션 유형 믹스 비율을 테스트 툴에 가미하여 시뮬레이터 신뢰도를 실제 수준으로 끌어올리는 조정 단계.
- **과부하(Overload, 포화 붕괴 상태)**: API 게이트웨이 등으로 쏟아져 들어오는 외부 트래픽 도착률이 시스템 백엔드 큐의 순수 완료 방출 속도 능력을 한참 초과하여, 대기열 메모리가 터져나가고 연쇄 503 오류가 폭증하는 통제 불능 인프라 상태.
- **목표 부하 선택(Target Workload Paradigm Decision)**: 시스템 아키텍처 특성에 입각하여, 프론트웹 사용자 행동 평가는 N/(R+Z) 주기 폐쇄식 공식을, 서버 간 API B2B 통신 부하 검증은 RPS 기준의 개방형 무한 주입식을 양분하여 채택하는 설계적 의사결정 원칙.

</details>

- 시스템 아키텍처 궤도에 걸맞은 정확한 **목표 부하 선택**과 로그 기반 **부하 현실화** 튜닝 과정을 접목하여, 사용자 행동은 Z(생각시간)가 반영된 대화형 처리율로, 무상태 API 기계 호출은 거친 **RPS** 폭격으로 이원화 산출해 돌발 **과부하** 붕괴 한계점 도출 및 스케일업 기준 선별 적용.

#### 한줄 요약

- 단순 공식 계산에 멈추지 않고 시스템 성격(B2C/B2B)과 사용자 행동 휴지기(Think Time)를 현실적으로 조율해 반영함으로써 과소 튜닝과 과잉 투자를 동시에 방어하는 용량 산정 체계 필수 준수
