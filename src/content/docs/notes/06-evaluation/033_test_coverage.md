## Ⅰ. 개요

<details><summary>용어 설명</summary>

- **테스트 커버리지(Test Coverage / 화이트박스 구조적 검증)**: 작성된 테스트 케이스 스위트(Test Suite)가 소스 코드의 제어 흐름 그래프(Control Flow Graph) 상에 존재하는 실행 가능한 문장(Statement), 분기 결정(Branch/Decision), 개별 조건식(Condition), 복합 조건 경로를 얼마나 충실하게 실행(Execution)했는지를 백분율(%)로 정량화한 소프트웨어 테스트 완성도 척도.
- **높은 구문 커버리지의 착시 및 복합 조건 마스킹 결함(Coverage Illusion & Condition Masking Defect)**: 모든 소스코드 줄을 한 번씩 훑었다는 구문 커버리지(Statement Coverage) 100%만 달성하고 안심했으나, `else` 분기가 누락되었거나 `if (A || (B && C))`와 같은 복합 조건문에서 개별 조건의 단독 결함이 상위 조건에 의해 가려지는(Masking) 현상을 놓쳐 상용 배포 후 시스템 크래시가 발생하는 구조적 결함.

</details>

- 정의/개념: 소스코드의 미실행 사각지대와 잠재적 논리 결함을 완전히 색출하기 위해 **소스코드 계측(Instrumentation) $\rightarrow$ 위험도별 커버리지 기준(구문 $C_0$ / 분기 $C_1$ / MC/DC) 선정 $\rightarrow$ $N+1$개 독립 영향 테스트 쌍(Test Pair) 설계 $\rightarrow$ CI/CD 파이프라인 자동 실행 $\rightarrow$ 품질 게이트(Quality Gate) 기반 배포 차단** 을 집행하는 **구조적 테스트 품질 엔지니어링 체계**
- 배경/필요성: 항공기 비행 제어(DO-178C Level A), 자동차 자율주행(ISO 26262 ASIL D), 의료기기 등 인명 안전과 직결된 시스템에서 $2^N$개의 기하급수적 테스트 폭증을 방지하면서도 복합 조건의 완전성을 $N+1$개 케이스로 증명하기 위해 MC/DC 필수화

#### 한줄 요약
- 테스트 커버리지는 소스코드 제어 흐름의 실행 정도를 정량화하며, 미션 크리티컬 환경에서는 MC/DC를 통해 복합 조건의 독립성을 검증한다.

## Ⅱ. 특징

<details><summary>용어 설명</summary>

- **커버리지 포섭 관계 (Subsumption Hierarchy)**:
  - 상위 수준의 커버리지를 100% 만족하면, 하위 수준의 커버리지는 수학적으로 자동 100% 만족되는 포함 관계.
  - $\text{Statement } (C_0) \subset \text{Branch/Decision } (C_1) \subset \text{Condition/Decision} \subset \text{MC/DC} \subset \text{Multiple Condition } (C_2)$.

</details>

- **구조적 사각지대의 가시화**: 테스트 실행 프로브(Probe) 계측을 통해 실행되지 않은 `if-else` 분기, 예외 핸들러(`catch`), 데드 코드(Dead Code)의 정확한 소스 라인 번호 색출
- **MC/DC의 경제적 완전성**: $N$개의 개별 조건식을 가진 복합 조건문에 대해 $2^N$개의 전수 조합(Multiple Condition) 대신 단 $N+1$개의 테스트 케이스만으로 각 조건의 독립적 결과 반전 영향력 100% 입증
- **CI/CD 파이프라인 품질 게이트 연동**: JaCoCo, Coverage.py, gcov 등의 도구를 빌드 파이프라인에 통합하여 목표 커버리지(예: 라인 80%, 분기 75%) 미달 시 자동으로 머지/배포 차단

#### 한줄 요약
- 계층적 포섭 관계, 미실행 사각지대 가시화, MC/DC의 $N+1$ 효율성, CI/CD 품질 게이트 자동 차단을 제공한다.

## Ⅲ. 구조 및 구성요소

<details><summary>용어 설명</summary>

- **주요 4대 테스트 커버리지 기준 및 정의**:
  1. **구문 커버리지 ($C_0$, Statement)**: 전체 실행 가능한 문장 중 테스트된 문장의 비율 ($C_0 = \frac{\text{실행된 문장 수}}{\text{전체 문장 수}} \times 100\%$).
  2. **분기/결정 커버리지 ($C_1$, Branch/Decision)**: 전체 조건문의 True/False 분기 중 테스트된 분기 비율 ($C_1 = \frac{\text{실행된 분기 수}}{\text{전체 분기 수}} \times 100\%$).
  3. **조건 커버리지 (Condition)**: 복합 조건식 내 각 개별 조건의 True/False가 최소 1회씩 실행된 비율.
  4. **수정 조건/결정 커버리지 (MC/DC)**: 다른 모든 조건이 고정된 상태에서, 관심 대상 개별 조건의 참/거짓 변경만으로 전체 결정식의 결과가 반드시 반전됨을 입증하는 테스트 쌍.

</details>

```text
┌─────────────────────────────────────────────────────────────────────────┐
│ [ 1. 테스트 커버리지 계층적 포섭 관계 (Subsumption Hierarchy) ]         │
│                                                                         │
│   [ 복합 조건 커버리지 (Multiple Condition: 2^N) - 비용 극대 ]         │
│                         ▲ (포섭)                                        │
│   [ 수정 조건/결정 커버리지 (MC/DC: N+1) - DO-178C Level A 표준 ]       │
│                         ▲ (포섭)                                        │
│   [ 조건/결정 커버리지 (Condition / Decision Coverage) ]                │
│                         ▲ (포섭)                                        │
│   [ 분기/결정 커버리지 (Branch/Decision Coverage: C1) ]                 │
│                         ▲ (포섭)                                        │
│   [ 구문 커버리지 (Statement Coverage: C0) - 기본 단위 테스트 ]         │
└────────────────────────────────────┬────────────────────────────────────┘
                                     │ (MC/DC 독립 영향 검증 예시)
                                     ▼
┌─────────────────────────────────────────────────────────────────────────┐
│ [ 2. MC/DC 독립 영향 증명 (Decision = A or (B and C) / N=3 ➔ 4개 케이스) ]│
├─────┬───────┬───────┬───────┬────────────┬──────────────────────────────┤
│ No  │ A     │ B     │ C     │ Decision   │ 검증 목적 (독립 영향 증명)   │
├─────┼───────┼───────┼───────┼────────────┼──────────────────────────────┤
│ 1   │ True  │ False │ False │ **True**   │ [테스트 쌍 1-2]: A의 독립 영향 입증│
│ 2   │ False │ False │ False │ **False**  │ (B, C 고정 시 A 반전 ➔ 결과 반전)│
├─────┼───────┼───────┼───────┼────────────┼──────────────────────────────┤
│ 3   │ False │ True  │ True  │ **True**   │ [테스트 쌍 2-3]: B의 독립 영향 입증│
│ 4   │ False │ True  │ False │ **False**  │ [테스트 쌍 3-4]: C의 독립 영향 입증│
└─────┴───────┴───────┴───────┴────────────┴──────────────────────────────┘
```

선의 의미: 하위 구문 커버리지부터 상위 MC/DC로 이어지는 포섭 관계 및 3개 조건에 대해 4개 테스트 케이스로 독립성을 증명하는 구조

| 커버리지 유형 | 수식 및 측정 대상 | 필요 최소 테스트 케이스 수 | 주요 적용 도메인 |
|:---|:---|:---|:---|
| **구문 커버리지 ($C_0$)** | $\frac{\text{실행 문장}}{\text{전체 문장}} \times 100\%$ | 최소 1개 이상 | 일반 웹 서비스, 사내 포털 |
| **분기 커버리지 ($C_1$)** | $\frac{\text{실행 분기 (True/False)}}{\text{전체 분기}} \times 100\%$ | 모든 분기당 2개 | 금융 코어 시스템, 이커머스 |
| **MC/DC 커버리지** | 개별 조건의 독립 영향 증명 쌍 | **$N + 1$개 ($N$: 개별 조건 수)**| **항공기(DO-178C A), 자동차(ASIL D)**|
| **복합 조건 ($C_2$)** | 모든 진리표 조합 전수 실행 | $2^N$개 (조합 폭발 발생) | 극도로 짧은 암호화 알고리즘 |

#### 한줄 요약
- 구문($C_0$), 분기($C_1$), MC/DC($N+1$), 복합 조건($C_2$)의 포섭 계층과 독립 영향 테스트 쌍으로 구성된다.

## Ⅳ. 흐름도

<details><summary>용어 설명</summary>

- **커버리지 기반 품질 통제 5단계 수명주기**:
  1. 소프트웨어 안전성 등급(ASIL, SIL, DAL)에 따른 목표 커버리지(예: ASIL D $\rightarrow$ MC/DC 100%) 확정
  2. 컴파일러 또는 바이트코드 레벨에서 제어 흐름 추적 프로브(Probe) 자동 주입(Instrumentation)
  3. CI 파이프라인에서 단위/통합 테스트 자동 실행 및 실행 트레이스 수집
  4. 커버리지 리포트 생성 및 미도달 분기/조건에 대한 갭 분석(Gap Analysis)
  5. 미도달 경로에 대한 테스트 케이스 추가 작성 또는 도달 불가 코드(Dead Code) 제거 후 배포 승인

</details>

```text
1. [위험도 기반 커버리지 목표 수립]
    ├─ 대상: 자율주행 차량 긴급 제동 제어기 (AEB ECU)
    ├─ 안전성 등급: ISO 26262 ASIL D 등급 판정
    └─ [목표 수립: 구문 100%, 분기 100%, MC/DC 100% 달성 의무화]
            │
            ▼
2. [소스코드 계측 빌드 (Instrumentation)]
    ├─ GCC / LLVM 계측 옵션(`-fprofile-arcs -ftest-coverage`) 활성화
    └─ [모든 if/while 분기 및 복합 조건식에 실행 카운터 프로브 자동 삽입]
            │
            ▼
3. [테스트 스위트 자동 실행]
    ├─ HIL(Hardware-in-the-Loop) 시뮬레이터에서 1,200개 테스트 벡터 인가
    └─ [실행 로그(.gcda) 생성: 실행된 문장 및 참/거짓 분기 히트맵 기록]
            │
            ▼
4. [커버리지 갭 분석 (Gap Analysis)]
    ├─ 측정 결과: 구문 98%, 분기 94%, MC/DC 88% 기록 (품질 게이트 탈락)
    ├─ 미도달 분석: `if (speed > 80 && radar_fail && !driver_override)` 복합 조건에서
    └─ [`driver_override`의 단독 참/거짓 반전 테스트 쌍이 누락되었음을 식별]
            │
            ▼
5. [테스트 보완 및 품질 게이트 통과]
    ├─ 운전자 수동 개입(`driver_override=True`) 시뮬레이션 테스트 케이스 2건 추가
    ├─ 재측정 결과: 구문 100%, 분기 100%, MC/DC 100% 완전 달성
    └─ [CI/CD Quality Gate 자동 통과 ➔ 상용 펌웨어 릴리스 승인]
```

**동작 원리**

1. **프로브 계측의 투명성**: 소스코드의 원본 로직을 변경하지 않고 실행 경로 진입점마다 원자적 메모리 플래그를 세워 실행 여부를 1비트의 누락도 없이 캡처
2. **조건 마스킹(Condition Masking)의 제거**: `A or B`에서 A가 True이면 B의 값에 관계없이 결과가 True가 되므로, B의 결함을 찾으려면 A를 False로 고정하고 B를 변경하는 MC/DC 원리 강제
3. **도달 불가능 코드(Unreachable Code)의 식별**: 물리적으로 실행될 수 없는 방어적 코드가 발견될 경우, 주석 처리하거나 아키텍처 정당성 보고서를 작성하여 예외 승인
4. **테스트 오라클(Test Oracle)과의 결합**: 커버리지는 '코드가 실행되었는가'만 보장하므로, 실행 결과가 정답인지 검증하는 Assert 구문(오라클)이 반드시 동반되어야 함
5. **회귀 테스트 효율화**: 코드 변경 발생 시 변경된 라인의 커버리지 궤적(Trace)과 매핑된 테스트 케이스만 선별 실행(Test Impact Analysis)하여 CI 빌드 시간 80% 단축

#### 한줄 요약
- 위험도 목표 수립, 코드 계측 빌드, 테스트 실행, 갭 분석, 테스트 보완 및 품질 게이트 통과 순으로 동작한다.

## Ⅴ. 종류 및 비교

<details><summary>용어 설명</summary>

- **구조적 테스트 커버리지 3대 기준 상세 비교**:
  - 구문 커버리지 (C0): 모든 라인 1회 실행 (최소 기본 요건).
  - 분기 커버리지 (C1): 모든 조건문 True/False 1회 실행 (표준 상용 시스템).
  - MC/DC 커버리지: 개별 조건의 독립 영향 증명 (미션 크리티컬 안전 필수).

</details>

| 비교 항목 | 구문 커버리지 ($C_0$) | 분기 커버리지 ($C_1$) | MC/DC 커버리지 |
|:---|:---|:---|:---|
| **검증 핵심 관점** | **코드의 모든 문장이 실행되었는가?** | **모든 결정문이 True/False를 겪었는가?**| **개별 조건이 결과에 독립적 영향을 미치는가?**|
| **복합 조건 마스킹**| **전혀 검출 불가** | 검출 불가 | **완벽 검출 (독립 영향 증명)** |
| **필요 테스트 수** | 최소 ($1 \sim M$개) | 중간 ($2 \times$ 분기 수) | **효율적 ($N+1$개 / 결정식당)** |
| **안전 표준 규격** | 비안전 일반 비즈니스 로직 | ISO 26262 ASIL B/C | **DO-178C Level A, ISO 26262 ASIL D**|
| **테스트 설계 난이도**| 매우 쉬움 | 보통 | **높음 (진리표 분석 및 쌍 도출 필요)** |
| **결함 검출 능력** | 낮음 | 중간 | **최고 우수** |

#### 한줄 요약
- 구문(C0)은 기본 라인 검증, 분기(C1)는 참/거짓 검증, MC/DC는 복합 조건의 독립 영향을 보증한다.

## Ⅵ. 실무 고려사항 및 대책

<details><summary>용어 설명</summary>

- **테스트 커버리지 실무 관리 시 3대 위험 요소와 엔지니어링 대책**:

</details>

| 문제 | 대책 | 효과 |
|:---|:---|:---|
| `assert` 검증문 없이 실행만 시키는 깡통 테스트(Empty Test)로 **커버리지 100%를 달성했으나 실제 로직 버그를 전혀 잡지 못하는 허위 통과 발생** | **커버리지 측정과 함께 소스코드에 인위적 결함을 주입하여 테스트가 이를 잡아내는지 검증하는 돌연변이 테스트(Mutation Testing) 병행** | 테스트 오라클 유효성 및 실질 검출력 100% 확보 |
| 하드웨어 장애 대비 방어 코드 등 정상 환경에서 도달 불가능한 코드(Unreachable)로 인해 **커버리지 목표(100%) 미달로 빌드가 차단되는 병목 발생** | **도달 불가 코드에 대한 명확한 사유서와 단위 테스트 제외 어노테이션(`@Generated`, `@CoverageIgnore`) 승인 절차 수립** | 불필요한 테스트 낭비 제거 및 지표 정합성 유지 |
| 복합 조건식이 5개 이상 중첩되어 **MC/DC 테스트 케이스 설계가 불가능할 정도로 복잡도가 폭증하는 코드 스멜 발생** | **복합 조건식을 단일 책임 원칙(SRP)에 따라 작은 서브 함수로 리팩토링하고 순환 복잡도(Cyclomatic Complexity)를 10 이하로 제한** | MC/DC 테스트 설계 간소화 및 가독성 향상 |

#### 한줄 요약
- 돌연변이 테스트로 허위 통과를 막고, 도달 불가 코드를 예외 처리하며, 리팩토링으로 MC/DC 설계를 간소화한다.

## Ⅶ. 결론

- 소프트웨어의 숨겨진 제어 경로와 잠재적 논리 결함을 샅샅이 드러내는 화이트박스 테스트 공학의 핵심 나침반인 **테스트 커버리지 체계**는 단순한 수치 달성을 넘어 소프트웨어의 구조적 신뢰성과 기능안전성을 보증하는 절대적 품질 게이트이며, 실무 구현 시 **시스템 위험도(ASIL/SIL)에 부합하는 커버리지 기준(구문/분기/MC/DC) 차등 수립**, **$N+1$개 테스트 쌍 기반의 엄격한 MC/DC 검증**, **CI/CD 파이프라인 자동화 및 품질 게이트(Quality Gate) 강제**, **돌연변이 테스트를 통한 테스트 오라클 검증**을 완성하여 최고 수준의 소프트웨어 무결점 품질과 시스템 안정성을 완성

#### 한줄 요약
- 위험도 기반 구문/분기/MC/DC 차등화와 CI/CD 품질 게이트를 통해 구조적 소프트웨어 품질을 완성한다.
