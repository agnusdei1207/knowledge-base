## Ⅰ. 개요

<details><summary>용어 설명</summary>

- **APM(Application Performance Management, 애플리케이션 성능 관리)**: 클라이언트의 요청이 복잡한 분산 아키텍처 내부를 관통하는 논리적 호출 경로와 각 노드의 물리적 하드웨어 자원 상태를 실시간 시계열로 연계하여, 응답 지연의 근본 원인을 추적하고 관리하는 종합 모니터링 프레임워크.

</details>

- 정의: 요청 경로와 관측 신호를 잇는 **APM 체계**이다.
- 배경/필요성: 자원 집계만으로는 **지연 호출 원인 식별 불가**

#### 한줄 요약

- 분산 추적·자원 지표로 **구간별 병목 식별**

## Ⅱ. 특징

<details><summary>용어 설명</summary>

- **추적 문맥(Trace Context, 트랜잭션 상관 식별자)**: 단일 요청이 여러 마이크로서비스를 넘나들며 처리될 때, 최초 부여된 유니크한 추적 식별자(Trace ID)와 부모-자식 구간 호출 정보를 HTTP 헤더 등에 실어 서비스 간에 끊김 없이 전달하는 메타데이터 값.
- **표본 추출(Sampling, 샘플링 측정률 조절)**: 수천만 건의 전체 요청 데이터를 모두 수집할 시 발생하는 네트워크 및 스토리지 과부하 오버헤드를 막기 위해, 통계적 유의미성을 잃지 않는 선에서 특정 비율(예: 1~5%)의 핵심 요청만 상세 추적 로그로 저장하는 경량화 정책.
- **오픈텔레메트리(OpenTelemetry, OTel, 표준 관측성 프레임워크)**: 특정 상용 APM 벤더(Datadog, Dynatrace 등)에 종속되지 않고, 클라우드 네이티브 환경에서 추적(Trace), 메트릭(Metric), 로그(Log)의 통합 수집 및 전송 규격을 오픈소스로 표준화한 글로벌 관측성 프로토콜.
- **관측 비용 통제(Observability Cost Control)**: 너무 방대한 추적 데이터 생성으로 인한 모니터링 에이전트의 서버 CPU 점유 오버헤드와 스토리지 보관 비용 폭등을 억제하기 위해 표본률(Sampling Rate)과 계측 심도를 전략적으로 튜닝하는 밸런싱 최적화 관리 활동.

</details>

- **추적 문맥**으로 MSA 종단 호출 관계 재조립
- **오픈텔레메트리**로 추적·메트릭·로그 연계
- **표본 추출·관측 비용 통제**로 오버헤드 제한

#### 한줄 요약

- 메트릭으로 탐지하고 추적으로 **병목 원인 격리**

## Ⅲ. 구조 및 구성요소

<details><summary>용어 설명</summary>

- **추적(Trace, 종단 간 거래 이력)**: 사용자 단말에서 백엔드 DB 서버에 이르기까지, 단일 사용자 요청 1건이 무수한 여러 마이크로서비스 노드와 네트워크 홉(Hop)을 돌파하며 남긴 시계열 호출 궤적의 전체집합 다이어그램.
- **구간(Span, 단위 서비스 논리 블록)**: 거대한 추적(Trace) 덩어리를 구성하는 개별 세부 단위로, 단일 서비스 내 특정 메소드 실행이나 외부 서드파티 API 통신, DB 질의 등이 소요한 단건 시작-종료 시간과 응답 코드를 담은 고유 기록 캡슐.
- **메트릭(Metric, 시계열 집계 지표)**: 1초, 혹은 1분 등 통제된 일정 단위 시간 주기로 인프라에 쌓인 처리량(TPS), 평균 지연시간, 에러율 발생 건수, 시스템 자원(CPU 등) 이용률을 통계적으로 합산하여 수치화한 트렌드 그래프 데이터.
- **로그(Log, 구조화된 이벤트 문자열)**: 런타임 특정 시점에 애플리케이션 내부에서 발생한 상태 변이, 심각한 예외 덤프, 그리고 사용자 비즈니스 오류 메시지를 그 당시의 분산 추적 문맥(Trace ID)과 병합하여 남겨놓은 상세 문자열 팩트 데이터.
- **서비스 지도(Service Map, 분산 토폴로지 시각화 맵)**: 모아진 수백만 개의 수집 구간(Span) 헤더에 박힌 부모-자식 의존 관계 메타데이터를 역추적 조립하여, 시스템 내 마이크로서비스 간의 통신 방향성 트래픽과 병목 지점을 직관적인 노드 다이어그램 형태로 시각화한 모니터링 망.

</details>

```text
                     [계측•추적 문맥]
                              |
                     [Span•Metric•Log]
                              |
                       [수집•처리 계층]
                              |
                    [시계열•추적 저장소] -- [분석•서비스 지도•알림]
```

선의 의미: 최전방 분산 트레이스(추적 문맥) 식별자가 Span/Metric/Log 세 가지 독립된 관측 신호를 하나로 단단히 결속시키고, 수집 서버와 빅데이터 저장소를 관통하여 최종적으로 관제 화면의 서비스 의존성 지도와 장애 알림 트리거로 파생 통합되는 APM 데이터 파이프라인 정적 계층 뷰.

| 관측 구성요소 아키텍처 | 주요 기능적 역할 및 책임 |
|:---|:---|
| 계측•추적 문맥 | Trace ID·부모 관계 전파 |
| Span•Metric•Log | **구간·메트릭·로그** 생성 |
| 수집•처리 계층 | 필터·표본·형식 변환 |
| 시계열•추적 저장소 | **추적·시계열 지표** 저장 |
| 분석•서비스 지도•알림 | **서비스 지도**·병목·알림 제공 |

#### 한줄 요약

- Trace ID로 **함수 지연·오류 경로 재조립**

## Ⅳ. 흐름도

<details><summary>용어 설명</summary>

- **추적 식별자(Trace ID)**: 단일 사용자 트랜잭션이 여러 마이크로서비스를 통과하는 전 과정을 식별하는 전역 고유 식별자.
- **문맥 주입(Context Injection)**: 진입 게이트웨이에서 HTTP 헤더에 Trace ID와 상위 구간 정보를 삽입하는 단계.
- **이상 탐지(Anomaly Detection)**: 수집된 지연시간 통계를 바탕으로 지연 급증 및 슬로우 쿼리 구간을 판정하는 절차.

</details>

```text
클라이언트 요청
      │
      ▼
API 게이트웨이
   │ 1. W3C Trace Context 주입
   ▼
마이크로서비스
   │ 2. 하위 Span·Metric·Log 생성
   ▼
수집기(Collector)
   │ 3. 표본 추출 및 호출 경로 조립
   ▼
분석 엔진
   │ 4. 이상 탐지 및 병목 원인 분석
   ▼
성능 대시보드 및 경보
```

### 동작 원리

1. W3C Trace Context 주입: 진입점에서 전역 Trace ID 및 상위 부모 관계 생성 후 헤더 주입
2. 하위 Span·Metric·Log 생성: 서비스별 비즈니스 로직 및 DB 쿼리 실행 구간 데이터 기록
3. 표본 추출 및 호출 경로 조립: 수집기에서 동일 Trace ID를 매핑하여 종단 간 트리 구성
4. 이상 탐지 및 병목 원인 분석: 슬로우 쿼리 및 지연 유발 컴포넌트의 근본 원인 도출

#### 한줄 요약

- Trace ID와 Span으로 **슬로우 쿼리와 API 지연 원인 추적**.

## Ⅴ. 종류 및 비교

<details><summary>용어 설명</summary>

- **분산 추적(Distributed Traces)**: 개별 트랜잭션의 서비스 간 이동 궤적과 구간별 소요 시간을 심층 분석하는 기법.
- **집계 메트릭(Aggregated Metrics)**: CPU, 메모리, 처리량(TPS), 에러율을 일정 주기 단위로 집계하여 거시적 추세를 모니터링하는 기법.
- **관측 전략(Observability Strategy)**: 메트릭 기반으로 전체 시스템 이상을 조망하고, 추적 데이터로 상세 병목을 좁히는 융합 전략.

</details>

| 비교 항목 | APM 분산 추적 (Traces) | 집계 메트릭 모니터링 (Metrics) |
|:---|:---|:---|
| 핵심 적용 목적 | **상세 병목 원인 진단** 및 개별 트랜잭션 디버깅 | **전체 시스템 이상 탐지** 및 추세 파악 |
| 특징 및 장점 | 호출 경로와 코드 수준의 지연시간 분석 | 리소스 사용량 적음 및 빠른 대시보드 조망 |
| 비용 및 한계 | 데이터 수집·저장 오버헤드 발생 | 개별 호출의 구체적 지연 원인 파악 불가 |

> 요약: 메트릭으로 이상 발생을 먼저 탐지하고, 분산 추적으로 세부 원인 구간을 상세 진단.

#### 한줄 요약

- 메트릭으로 탐지하고 **추적으로 상세 원인 분석**.

## Ⅵ. 실무 고려사항 및 대책

<details><summary>용어 설명</summary>

- **계측 오버헤드(Instrumentation Overhead)**: APM 에이전트 실행으로 인해 애플리케이션 CPU 및 메모리 사용량이 증가하는 현상.
- **OpenTelemetry (OTel)**: 벤더 종속 없이 메트릭, 로그, 추적 데이터를 수집·전송할 수 있는 오픈소스 표준 프레임워크.
- **민감정보 마스킹(Sensitive Data Masking)**: 추적 로그 내 개인정보(PII) 및 인증 토큰을 비식별화 처리하는 보안 기법.

</details>

| 문제 | 대책 | 효과 |
|:---|:---|:---|
| 이종 프레임워크 간 추적 헤더 유실 | **W3C Trace Context** 표준 규격 전파 | **호출 문맥 단절 방지** |
| 특정 상용 APM 솔루션 벤더 종속 | **OpenTelemetry** 표준 수집기 도입 | 백엔드 교체 유연성 확보 |
| 전수 계측으로 인한 성능 저하 및 보안 노출 | **표본 추출(Sampling) 및 민감정보 마스킹** 적용 | 계측 비용 절감 및 정보 보호 |

#### 한줄 요약

- 추적 문맥 보존과 **표본 추출 기반 계측 비용 통제**.

## Ⅶ. 결론

<details><summary>용어 설명</summary>

- **3대 관측성 신호 연계(Telemetry Correlation)**: 메트릭, 로그, 추적 데이터를 단일 Trace ID와 시간 축으로 상호 연계하여 트러블슈팅 시간을 단축하는 체계.

</details>

- 거시적 메트릭 지표로 이상을 감지한 후 **분산 추적과 로그 연계 분석**으로 신속한 원인 규명

#### 한줄 요약

- 이상 메트릭을 **수정 가능한 구체적 호출 원인으로 전환**.
