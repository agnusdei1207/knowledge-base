## Ⅰ. 개요

<details><summary>용어 설명</summary>

- **성능 테스트 4대 핵심 유형(Performance Testing Types)**: 소프트웨어 시스템이 운영 환경에서 직면할 수 있는 다양한 트래픽 조건(정상 피크, 한계 초과, 장시간 가동, 순간 폭주)을 인위적으로 모사하여 처리량(TPS), 응답시간(p99 지연), 파괴점(Break Point), 자원 누수(Memory Leak), 그리고 장애 복원력(Resilience)을 입체적으로 검증하는 성능 엔지니어링 방법론.
- **단일 부하 시험 편향에 따른 잠재 결함 은폐 결함(Single Load Test Blind Spot Defect)**: 1~2시간 동안의 단순 부하 테스트(Load Test)만을 통과한 후 상용 배포했을 때, 며칠 뒤 메모리 누수로 서버가 다운(Soak 미수행)되거나 대규모 이벤트 시 순간 트래픽 폭증으로 오토스케일링이 반응하기도 전에 클러스터 전체가 연쇄 붕괴(Spike/Stress 미수행)되는 구조적 결함.

</details>

- 정의/개념: 시스템의 운영 안정성과 극한의 내구성을 입증하기 위해 **예상 피크 부하 검증(Load Test) $\rightarrow$ 파괴점 한계 탐색(Stress Test) $\rightarrow$ 24~72시간 장기 누수 진단(Soak Test) $\rightarrow$ 계단식 트래픽 급증 및 복원력 측정(Spike Test) $\rightarrow$ 오토스케일링 및 서킷 브레이커 연동 검증** 을 집행하는 **다차원 성능 검증 체계**
- 배경/필요성: 클라우드 네이티브 환경에서 동적 확장성(Elasticity)과 장애 격리 메커니즘이 필수화됨에 따라, 단일 지표 검증을 넘어 부하 프로파일별 다층적 스트레스 내성 평가 필요

#### 한줄 요약
- 성능 테스트는 부하(Load), 스트레스(Stress), 소크(Soak), 스파이크(Spike) 시험을 통해 용량과 복원력을 종합 검증한다.

## Ⅱ. 특징

<details><summary>용어 설명</summary>

- **4대 성능 테스트 핵심 목적 및 부하 프로파일**:
  - **부하 테스트 (Load Testing)**: 예상되는 최대 피크 트래픽 환경에서 SLO(예: 3,000 TPS, p99 < 500ms) 충족 여부 확인.
  - **스트레스 테스트 (Stress Testing)**: 시스템이 견딜 수 있는 최대 한계(Knee Point)와 완전 붕괴(Break Point) 지점 탐색.
  - **소크 테스트 (Soak / Endurance Testing)**: 24시간~72시간 동안 일정 부하를 연속 주입하여 메모리/커넥션 누수 색출.
  - **스파이크 테스트 (Spike Testing)**: 0에서 피크의 3~5배 부하를 수 초 만에 인가하여 서킷 브레이커 및 복구력 검증.

</details>

- **부하 강도와 지속시간의 다차원 조합**: 목표 용량 검증(Load), 한계점 파괴(Stress), 시간 축 내구성(Soak), 순간 변동성(Spike)의 4각 검증
- **무릎점(Knee Point)과 파괴점(Break Point)의 정밀 식별**: 처리량이 선형 증가하다가 꺾이는 최적 용량 지점(Knee)과 에러율이 급증하며 시스템이 멈추는 한계점(Break) 규명
- **장애 복구 탄력성(Elastic Recovery) 실측**: 스파이크 부하가 종료된 후 시스템이 인위적 재기동 없이 스스로 정상 응답시간으로 회귀하는지 계측

#### 한줄 요약
- 부하·스트레스·소크·스파이크의 다각적 조합, 한계 파괴점 식별, 자가 회복력 검증을 제공한다.

## Ⅲ. 구조 및 구성요소

<details><summary>용어 설명</summary>

- **성능 테스트 4대 아키텍처 및 부하 곡선 패턴**:
  1. **Load Test Curve**: 점진적 증가(Ramp-up) $\rightarrow$ 피크 부하 유지(Plateau) $\rightarrow$ 종료.
  2. **Stress Test Curve**: 한계 도달 시까지 지속적 계단식 증가(Step-up) $\rightarrow$ 붕괴 관측.
  3. **Soak Test Curve**: 기준 부하(70~80%)로 장시간(24~72시간) 플랫(Flat) 유지.
  4. **Spike Test Curve**: 평시 부하 $\rightarrow$ 수직 상승(Spike) $\rightarrow$ 급강하 $\rightarrow$ 정상 회복 관측.

</details>

```text
┌─────────────────────────────────────────────────────────────────────────┐
│ [ 4대 성능 테스트 부하 인가 패턴 비교 (Load Profiling Patterns) ]        │
├───────────────────────────────────┬─────────────────────────────────────┤
│ [ 1. 부하 테스트 (Load Testing) ] │ [ 2. 스트레스 테스트 (Stress) ]     │
│   부하│     ┌─────────┐           │   부하│               ┌─── [Break Point]
│   (TPS)│    /           \          │   (TPS)│           ┌───┘                 │
│       └───/             \────     │       └───/───┘                         │
│       시간 ➔ (피크 부하 유지 검증)│       시간 ➔ (파괴점까지 계단식 증가)   │
├───────────────────────────────────┼─────────────────────────────────────┤
│ [ 3. 소크 테스트 (Soak Testing) ] │ [ 4. 스파이크 테스트 (Spike) ]      │
│   부하│ ┌───────────────────────┐ │   부하│     ┌┐        ┌┐                │
│   (TPS)│/                         │ │   (TPS)│     ││        ││                │
│       └─────────────────────────┘ │       └───/  \──────/  \────            │
│       시간 ➔ (24~72시간 누수 검증)│       시간 ➔ (순간 폭주 및 자가 회복력)│
└───────────────────────────────────┴─────────────────────────────────────┘
```

선의 의미: 테스트 유형별로 상이한 부하 인가 패턴(유지, 계단식 증가, 장기 지속, 순간 수직 폭증)을 나타내는 프로파일 구조

| 테스트 유형 | 부하 인가 방식 | 핵심 관측 지표 | 주요 결함 색출 영역 |
|:---|:---|:---|:---|
| **부하 테스트 (Load)** | 예상 피크 부하 (100% 목표) 1~2시간 유지 | TPS, p95/p99 응답시간, CPU/메모리 가동률 | 목표 SLA 달성 여부, 일반 병목 구간 |
| **스트레스 테스트 (Stress)**| 150%~300%까지 계단식 한계 부하 주입 | **Knee Point, Break Point, HTTP 5xx 에러율** | 시스템 최대 처리 한계, 락 경합 붕괴 |
| **소크 테스트 (Soak)** | 안정 부하 (70~80%) 24~72시간 연속 가동 | **JVM Old Gen 메모리 추이, DB Connection 수**| 메모리 누수(Leak), File Descriptor 고갈 |
| **스파이크 테스트 (Spike)**| 0.1초 내 300%~500% 순간 폭주 주입 후 차단 | **큐 대기열 적체량, 정상 회복 소요 시간(MTTR)**| 서킷 브레이커 동작, HPA 확장 지연 |

#### 한줄 요약
- 부하(피크 검증), 스트레스(파괴점 탐색), 소크(장기 누수 진단), 스파이크(순간 복원력)로 구성된다.

## Ⅳ. 흐름도

<details><summary>용어 설명</summary>

- **통합 성능 테스트 5단계 엔지니어링 수명주기**:
  1. 운영 트랜잭션 비율(Transaction Mix) 기반 워크로드 모델링
  2. 1단계: 목표 피크 부하 검증(Load Test) 수행 및 베이스라인 확보
  3. 2단계: 계단식 부하 증설을 통한 스트레스 테스트(Stress Test)로 파괴점 식별
  4. 3단계: 24시간 소크 테스트(Soak Test)로 JVM 힙 메모리 및 자원 누수 검증
  5. 4단계: 스파이크 테스트(Spike Test)로 오토스케일링 및 서킷 브레이커 복원력 최종 검증

</details>

```text
1. [워크로드 모델링 및 환경 격리]
    ├─ 운영 로그 분석: 결제(10%), 조회(70%), 검색(20%) 비율 조합
    └─ [테스트 환경 구축: 운영과 1:1 동일 스펙의 격리된 스테이징 클러스터 준비]
            │
            ▼
2. [1단계: 부하 테스트 (Load Testing)]
    ├─ 목표 3,000 TPS 부하 2시간 인가
    └─ [결과: 평균 45ms, p99 180ms 기록 ➔ SLO 100% 달성 확인]
            │
            ▼
3. [2단계: 스트레스 테스트 (Stress Testing)]
    ├─ 3,000 ➔ 4,000 ➔ 5,000 ➔ 6,000 TPS로 계단식 부하 증가
    ├─ 4,800 TPS(Knee Point)에서 응답시간 급증 시작
    └─ [5,500 TPS(Break Point)에서 DB Connection Pool 고갈로 HTTP 500 에러 폭증 확인]
            │
            ▼
4. [3단계: 소크 테스트 (Soak Testing)]
    ├─ 2,500 TPS(안정 부하)로 48시간 동안 쉬지 않고 부하 지속 주입
    └─ [결과: JVM Old Gen 메모리가 지속 우상향하며 Full GC 발생 주기 단축 ➔ 메모리 누수 색출]
            │
            ▼
5. [4단계: 스파이크 테스트 (Spike Testing)]
    ├─ 평시 1,000 TPS 유지 중 0.5초 만에 5,000 TPS로 수직 스파이크 주입
    ├─ 서킷 브레이커(Resilience4j) 즉시 오픈 ➔ 핵심 결제 보호 및 Fallback 응답 정상 작동
    └─ [스파이크 종료 후 10초 이내에 정상 레이턴시(40ms)로 자력 회복 확인]
```

**동작 원리**

1. **단계적 결함 격리**: 부하 $\rightarrow$ 스트레스 $\rightarrow$ 소크 $\rightarrow$ 스파이크 순으로 시험을 고도화하여 결함의 원인을 단계별로 정확히 규명
2. **소크 테스트의 선형 회귀 분석**: 48시간 동안의 메모리 사용량 데이터를 선형 회귀($y = ax + b$)하여 기울기($a > 0$)가 유의미할 경우 메모리 누수로 확정
3. **그레이스풀 데그라데이션(Graceful Degradation) 검증**: 스트레스 테스트 시 시스템이 완전히 다운되지 않고 일부 비핵심 기능을 차단하며 핵심 기능을 유지하는지 확인
4. **부하 발생기 병목 배제**: 테스트 도중 부하 도구 자체의 CPU/메모리 포화 여부를 동시 감시하여 측정 왜곡 방지
5. **폐쇄 루프 아키텍처 개선**: 식별된 Break Point와 메모리 누수 지점을 코드 레벨에서 수정한 후 재시험을 통해 상용 배포 승인

#### 한줄 요약
- 워크로드 모델링, 부하 검증, 스트레스 한계 탐색, 소크 누수 진단, 스파이크 복원력 평가 순으로 동작한다.

## Ⅴ. 종류 및 비교

<details><summary>용어 설명</summary>

- **성능 테스트 4대 유형 비교**:
  - Load: 목표 SLA 검증 (적합성 확인).
  - Stress: 한계 및 붕괴점 탐색 (강인성 확인).
  - Soak: 장시간 자원 누수 검증 (내구성 확인).
  - Spike: 트래픽 급증 및 복원력 검증 (탄력성 확인).

</details>

| 비교 항목 | 부하 테스트 (Load) | 스트레스 테스트 (Stress) | 소크 테스트 (Soak) | 스파이크 테스트 (Spike) |
|:---|:---|:---|:---|:---|
| **주요 목적** | **목표 성능 SLA 충족 검증** | **파괴점 및 최대 한계 확인** | **메모리/커넥션 누수 탐지**| **순간 폭주 시 복원력 검증**|
| **부하 수준** | **예상 피크 부하 (100%)** | **한계 초과 부하 (150%~300%)**| **정상 안정 부하 (70%~80%)** | **순간 극한 부하 (300%~500%)**|
| **테스트 시간** | 1시간 ~ 2시간 | 30분 ~ 1시간 (계단식) | **24시간 ~ 72시간 (장기)** | 수 초 ~ 수 분 (순간) |
| **핵심 성공 기준**| **p99 지연시간 < 목표치** | **Graceful Shutdown/에러 격리**| **메모리 우상향 0% (수렴)** | **부하 종료 후 자력 복구 시간**|
| **주요 발견 결함**| 일반 병목, DB 인덱스 누락 | 락 경합 붕괴, 스레드 고갈 | 메모리 누수, GC 지연 누적 | 서킷 브레이커 오작동, HPA 지연|

#### 한줄 요약
- 부하는 목표 적합성, 스트레스는 파괴 한계, 소크는 장기 내구성, 스파이크는 순간 복원력을 검증한다.

## Ⅵ. 실무 고려사항 및 대책

<details><summary>용어 설명</summary>

- **성능 테스트 실무 수행 시 3대 위험 요소와 엔지니어링 대책**:

</details>

| 문제 | 대책 | 효과 |
|:---|:---|:---|
| 성능 시험 시 단일 API 호출만 반복하여 **실제 운영 환경의 복합 비즈니스 트랜잭션(조회+결제+검색) 간의 DB Lock 경합 병목 누락** | **실제 운영 액세스 로그를 분석하여 트랜잭션 믹스(Transaction Mix) 비율을 100% 동일하게 부하 시나리오로 구현** | 실제 운영 환경과 완벽히 일치하는 병목 사전 식별 |
| 부하 발생기(JMeter 노드)의 CPU/메모리가 100% 포화되어 **부하 주입이 지연되었음에도 대상 서버의 지연으로 오판하여 불필요한 서버 증설 단행** | **부하 발생기 클러스터에 분산 모니터링 에이전트를 설치하여 부하 도구 자체의 가동률을 50% 이하로 통제** | 부하 도구 병목에 의한 측정 왜곡 100% 차단 |
| 스테이징 환경의 데이터베이스 데이터 건수가 1만 건에 불과하여 **운영 환경(1,000만 건) 배포 후 대규모 Full Table Scan 지연 장애 발생** | **운영 데이터베이스와 동일한 볼륨(Data Volume)의 더미 데이터를 사전에 생성하여 인덱스 및 I/O 성능 정밀 검증** | 데이터 볼륨 차이에 따른 성능 왜곡 원천 제거 |

#### 한줄 요약
- 트랜잭션 믹스로 실 부하를 모사하고, 부하 도구 포화를 방어하며, 운영 동급 데이터 볼륨으로 검증한다.

## Ⅶ. 결론

- 소프트웨어 시스템의 품질과 가용성을 보증하는 최후의 엔지니어링 방패인 **성능 테스트 4대 유형 체계**는 단순한 기능 동작 검증을 넘어 시스템의 한계 용량과 생존성을 입증하는 필수 절차이며, 실무 구현 시 **운영 트랜잭션 믹스 및 데이터 볼륨의 100% 동기화**, **부하(Load) $\rightarrow$ 스트레스(Stress) $\rightarrow$ 소크(Soak) $\rightarrow$ 스파이크(Spike)의 단계별 검증 파이프라인 확립**, **무릎점(Knee Point)과 파괴점(Break Point)의 명확한 수치화**, **서킷 브레이커 및 오토스케일링 자가 복원력 검증**을 완성하여 최고 수준의 시스템 신뢰성과 무결점 서비스 연속성을 완성

#### 한줄 요약
- 부하·스트레스·소크·스파이크 4대 테스트의 체계적 연계를 통해 시스템 한계와 복원력을 완벽히 입증한다.
