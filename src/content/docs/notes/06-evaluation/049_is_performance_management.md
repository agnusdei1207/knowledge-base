## Ⅰ. 개요

<details><summary>용어 설명</summary>

- **정보시스템 성능 관리(IS Performance Management)**: 시스템 응답시간, 처리량, 자원 포화도를 정량 측정·분석하여 병목을 지속 개선하는 체계.
- **SLI/SLO(Service Level Indicator / Objective)**: 서비스 수준을 정량 측정하는 지표(SLI)와 비즈니스가 보장하는 목표치(SLO).

</details>

- 정의/개념: SLI/SLO 목표를 기반으로 애플리케이션, 데이터베이스, 인프라 계층의 트랜잭션 지연과 자원 포화도를 측정·분석·튜닝하는 성능 관리 체계
- 배경/필요성: 단순 평균 CPU 사용률만으로는 **꼬리 지연(p99) 은폐 및 계층 간 병목 이동(Bottleneck Shifting) 식별 불가** #### 한줄 요약

- 사용자 거래 **SLO와 동일 부하** 기반 개선 검증

## Ⅱ. 특징

<details><summary>용어 설명</summary>

- **꼬리 지연(Tail Latency, p95/p99)**: 전체 요청 중 상위 5% 또는 1%에 해당하는 극단적 지연 시간으로, 실제 사용자 체감 품질을 결정.
- **APM(Application Performance Monitoring)**: 트랜잭션 호출 궤적을 엔드투엔드로 추적하여 병목 함수와 SQL을 식별하는 도구.

</details>

- 평균 대신 **p95·p99 지연시간** 관리
- **Trace ID** 기반 WAS·DB·인프라 종단 추적
- 동일 워크로드와 **기준선** 기반 전후 비교

#### 한줄 요약

- 꼬리 지연을 종단 추적하고 **동일 부하 재검증** ## Ⅲ. 구조 및 구성요소

<details><summary>용어 설명</summary>

- **임계 경로(Critical Path)**: 하나의 트랜잭션이 완료되기까지 가장 많은 시간이 소요되는 함수, 네트워크, DB 호출의 연속 체인.
- **병목 이동(Bottleneck Shifting)**: WAS 계층을 튜닝했더니 병목이 DB 락 경합이나 네트워크 대역폭으로 전이되는 현상.

</details>

```text
정보시스템 성능 관리 체계 (구조도)
├─ 성능 목표 수립: 트랜잭션별 SLI/SLO(응답시간 p99, TPS, 에러율)
├─ 관측 계측 체계: APM 에이전트 / Trace ID 분산 추적 / 인프라 메트릭
├─ 계층별 병목 진단: WAS(스레드/GC) ── DB(인덱스/락) ── 인프라(CPU/IO)
└─ 개선 및 회귀 검증: 임계 경로 튜닝 / 동일 부하 재실행 / 병목 이동 검증
```

선의 의미: 목표 설정부터 APM 종단 추적, 계층별 병목 분석 및 동일 부하 회귀 검증으로 이어지는 성능 관리 체계.

| 구성요소 | 책임 |
|:---|:---|
| 목표•워크로드 | SLI·SLO·TPS·데이터 규모 설정 |
| 관측 체계 | **APM·Trace ID** 기반 거래·자원 추적 |
| 응용 계층 | 코드·스레드·외부 API 대기 분석 |
| DB•인프라 계층 | **포화도·Lock·I/O·큐** 분석 |
| 병목 개선•검증 | 임계 경로 수정 후 동일 부하 시험 |

#### 한줄 요약

- **APM 임계 경로**에서 포화·대기 병목 식별

## Ⅳ. 흐름도

<details><summary>용어 설명</summary>

- **부하 테스트(Load & Stress Testing)**: 목표 동시 접속자 수 및 한계 부하를 인가하여 시스템의 임계치와 병목 지점을 도출하는 시험.

</details>

```text
       성능 관리자
              │ 1. 비즈니스 SLO 및 기준 부하 시나리오 확정
              ▼
       기준선(Baseline) 계측
              │ 2. 목표 부하 인가 및 Trace ID 기반 지연시간 측정
              ▼
       병목 원인 분석
              │ 3. WAS 스레드 덤프, GC 정체, Slow Query, Lock 대기 식별
              ▼
       계층별 튜닝
              │ 4. 코드 리팩터링, 인덱스 생성, 커넥션 풀 최적화
              ▼
       회귀 부하 검증
              │ 5. 동일 조건 부하 재인가 및 병목 이동 유무 확인
              ▼
        성능 튜닝 완료 및 운영 배포
```

**동작 원리** 1. **목표 수립**: 주요 업무 트랜잭션별 p99 응답 시간 및 초당 목표 TPS 설정
2. **기준선 계측**: 테스트베드에서 정상 부하를 인가하여 APM으로 초기 성능 프로파일링
3. **병목 진단**: Trace ID 분석을 통해 호출 구간 중 가장 긴 지연(임계 경로)을 유발하는 지점 특정
4. **계층별 개선**: WAS 메모리 누수 조치, 비효율 Full Scan 쿼리 튜닝, DB 커넥션 풀 증설
5. **동일 부하 재검증**: 초기와 동일한 부하 스크립트를 재실행하여 응답시간 단축 및 타 계층으로의 병목 이동 여부 확인

#### 한줄 요약

- 기준선·병목 개선·**동일 부하 회귀검증** 폐루프

## Ⅴ. 종류 및 비교

<details><summary>용어 설명</summary>

- **계층별 성능 튜닝**:
  - Application: 비동기 논블로킹(Non-blocking), 스레드풀, GC 튜닝
  - Database: SQL 실행계획(Explain Plan), 인덱스 설계, Lock 격리수준 최적화
  - Infrastructure: Scale-up/out, 커널 파라미터, 네트워크 버퍼 조정

</details>

| 병목 분석 계층 | 애플리케이션 계층 (Application) | 데이터베이스 계층 (Database) | 인프라 계층 (Infrastructure) |
|:---|:---|:---|:---|
| 적용 기준 | 비즈니스 로직, GC 정체, 외부 API 지연 시 | SQL 쿼리 슬로우, Lock 경합, Disk I/O 병목 시 | CPU 포화, 메모리 부족(OOM), 네트워크 대역폭 부족 시 |
| 핵심 특징 | **코드·스레드·GC 튜닝** | **인덱스·쿼리·락 경합 해소** | **자원 증설·부하 분산 조정** |
| 한계 | 런타임 프로파일링 오버헤드 발생 | 복합 트랜잭션 락 종속성 추적 난이도 | 하드웨어 증설 대비 효율 한계 |

#### 한줄 요약

- 종단 지연을 **응용·DB·인프라 계층** 기반 분해

## Ⅵ. 실무 고려사항 및 대책

<details><summary>용어 설명</summary>

- **계측 오버헤드(Instrumentation Overhead)**: APM 에이전트나 프로파일러가 애플리케이션 CPU와 메모리를 과도하게 점유하는 부작용.

</details>

| 문제 | 대책 | 효과 |
|:---|:---|:---|
| 평균의 꼬리 지연 은폐 | **p95·p99·오류율** 관리 | 체감 지연 가시성 확보 |
| 캐시 뒤 DB 잠금 병목 | Trace ID·쿼리·**인덱스** 개선 | 임계 경로 단축 |
| APM의 **계측 오버헤드** | 대표 거래 샘플링·수집률 조정 | 관측 부하 최소화 |

#### 한줄 요약

- 꼬리 지연·임계 경로·**계측 오버헤드** 동시 관리

## Ⅶ. 결론

<details><summary>용어 설명</summary>

- **지속적 성능 최적화(Continuous Optimization)**: 일회성 튜닝에 그치지 않고 배포 시마다 성능 회귀 테스트를 자동화하여 최적 성능을 유지하는 체계.

</details>

- APM 기반 종단 Trace ID 추적 및 **동일 부하 회귀 시험을 통한 병목 이동 없는 성능 튜닝 완성** #### 한줄 요약

- **SLO·회귀·병목 이동 검증** 후 운영 반영
