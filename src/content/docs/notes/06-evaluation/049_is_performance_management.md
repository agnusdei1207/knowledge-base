## Ⅰ. 개요

<details><summary>핵심 용어</summary>

- **정보시스템 성능 관리**: 핵심 거래의 서비스 수준 목표와 워크로드 기준선을 정하고 병목 개선 효과를 동일 부하에서 반복 검증하는 폐루프 관리이다.
- **서비스 수준 목표(Service Level Objective, SLO)**: 정한 기간에 지연·오류·가용성 같은 서비스 수준 지표(Service Level Indicator, SLI)가 충족해야 하는 목표 수준이다.

</details>

- 정의/개념: **정보시스템 성능 관리** — 핵심 거래의 서비스 수준 목표(Service Level Objective, SLO)·워크로드 기준선을 정하고 병목 개선 효과를 동일 부하에서 검증하는 폐루프 관리
- 배경/필요성: 개별 자원 사용률만으로는 **사용자 거래 지연 원인·병목 이동 식별 불가**

#### 한줄 요약
- 중요한 사용자 거래의 목표를 정하고 느려진 요청이 어느 계층에서 기다리는지 찾아 개선 효과를 같은 부하로 확인함

## Ⅱ. 특징

<details><summary>핵심 용어</summary>

- **기준선**: 개선·변경 전후 성능 차이를 판단하기 위해 고정한 초기 워크로드·지연·처리량·자원 상태이다.
- **워크로드**: 요청 종류·도착 빈도·동시 사용자·데이터 크기를 조합한 시스템 처리 부하이다.
- **p95 지연시간**: 전체 요청의 95%가 해당 값 이하에서 완료되는 응답시간 경계이다.
- **종단 거래 식별자(End-to-End Transaction Identifier, 거래 ID)**: 사용자 요청이 응용·데이터베이스·인프라를 지나는 호출과 대기 기록을 하나로 연결하는 식별자이다.

</details>

- 평균에 가려진 실패를 드러내는 **분위수 지연·오류율**
- 응용·DB·자원 포화를 잇는 **종단 거래 ID**
- 효과와 병목 이동을 확인하는 **동일 워크로드 회귀 시험**

#### 한줄 요약
- CPU가 높다는 사실만 보지 않고 느린 사용자 요청이 어떤 호출과 대기열을 지나 포화됐는지 연결함

## Ⅲ. 구조 및 구성요소

<details><summary>핵심 용어</summary>

- **애플리케이션 성능 모니터링(Application Performance Monitoring, APM)**: 사용자 거래부터 내부 호출·데이터베이스(Database, DB)·자원 사용을 연결하여 추적하는 체계이다.
- **임계 경로**: 종단 요청을 완료하는 데 걸리는 시간을 결정하는 가장 긴 의존 호출 경로이다.
- **포화도**: 중앙처리장치(Central Processing Unit, CPU)·메모리·디스크·네트워크의 처리 여유가 얼마나 소진되었는지 나타내는 정도이다.

</details>

```mermaid
block-beta
  columns 1
  G["목표·워크로드"]
  O["관측 체계"]
  A["응용 계층"]
  D["DB·인프라 계층"]
  V["병목 개선·검증"]
  G --> O --> A
  A --> D --> V
```

| 구성요소 | 책임 |
|:---|:---|
| 목표·워크로드 | 거래별 **SLI·SLO** 와 요청·동시성·데이터 기준선 |
| 관측 체계 | **APM·거래 ID** 로 추적·로그·메트릭 연결 |
| 응용 계층 | **코드·캐시** 와 스레드·외부 호출 대기시간 |
| DB·인프라 계층 | **잠금·자원 포화도** 와 질의·저장장치 상태 제공 |
| 병목 개선·검증 | 동일 워크로드의 **효과·새 병목** 재시험 |

#### 한줄 요약
- 사용자 요청이 응용·DB·인프라를 지나는 동안 같은 거래 ID로 시간을 이어 어느 계층이 전체를 늦추는지 찾음

## Ⅳ. 흐름도

<details><summary>핵심 용어</summary>

- **병목**: 한 구성요소의 처리 한계가 전체 서비스의 처리량이나 지연을 제한하는 상태이다.
- **회귀 검증**: 변경 뒤 성능이 기존보다 나빠지거나 다른 경로에 새 병목이 생기지 않았는지 확인하는 시험이다.
- **동일 워크로드 비교**: 요청 종류·동시성·데이터·부하를 고정해 개선 전후 성능 차이를 공정하게 검증하는 방식이다.

</details>

```mermaid
sequenceDiagram
    participant M as 성능 관리자
    participant S as 대상 시스템
    participant A as 관측 도구
    M->>M: 1. SLO·워크로드 설정
    M->>S: 기준선 부하 실행 요청
    S->>A: 거래·자원 계측
    A-->>M: 기준선 증거
    M->>M: 2. 기준선 분석
    M->>S: 목표·피크 부하 실행 요청
    S->>A: 부하별 거래·자원 계측
    A-->>M: 임계 경로 증거
    M->>M: 3. 병목 원인 분석
    M->>S: 개선·회귀시험 요청
    S->>A: 동일 부하 계측
    A-->>M: 개선 전후 결과
    M->>M: 4. 개선 효과 검증
```

1. **SLO·워크로드 설정**: 핵심 거래의 분위수 지연·오류율 목표와 요청·동시성·데이터 조건 확정
2. **기준선 분석**: 변경 전 지연·오류·포화도와 임계 경로 기록
3. **병목 원인 분석**: 호출·질의·잠금·큐와 자원 포화의 인과 확인
4. **개선 효과 검증**: 동일 부하에서 SLO 개선과 병목 이동 여부 확인

#### 한줄 요약
- 바꾸기 전 상태를 저장하고 같은 요청을 다시 흘려 개선 뒤 빨라졌는지와 병목이 옮겨 가지 않았는지 확인함

## Ⅴ. 종류 및 비교

<details><summary>핵심 용어</summary>

- **애플리케이션 병목**: 코드·스레드·외부 호출이 종단 지연의 임계 경로를 지배하는 상태이다.
- **데이터베이스 병목**: 질의 실행계획·잠금·입출력 대기가 응답시간과 처리량을 제한하는 상태이다.
- **인프라 병목**: 중앙처리장치·메모리·네트워크·큐의 포화가 전체 처리 능력을 제한하는 상태이다.
- **병목 계층 선택**: 거래 추적에서 지연이 집중된 위치를 기준으로 응용·데이터베이스·인프라 중 실제 원인 계층을 정하는 판단이다.

</details>

| 병목 계층 | 판정 증거 | 대표 원인 |
|:---|:---|:---|
| 애플리케이션 | 거래 추적의 **코드·외부 호출 지연** | 스레드 고갈·직렬 처리·캐시 미스 |
| 데이터베이스 | **질의 실행계획·잠금·입출력 대기** | 비효율 질의·경합·인덱스 부재 |
| 인프라 | **중앙처리장치·메모리·네트워크·큐 포화** | 용량 부족·불균형·공유 자원 경합 |

#### 한줄 요약
- 거래 추적에서 시간이 멈춘 위치를 보고 코드·데이터베이스 대기·자원 포화 중 실제 원인이 있는 계층을 고름

## Ⅵ. 실무 고려사항 및 대책

<details><summary>핵심 용어</summary>

- **캐시**: 자주 쓰는 데이터를 빠른 저장공간에 임시 보관하여 원본 조회와 지연을 줄이는 방식이다.
- **인덱스**: 전체 데이터를 읽지 않고 원하는 행의 위치를 빠르게 찾게 하는 검색 구조이다.
- **계측 오버헤드**: 로그·추적·메트릭 수집이 대상 시스템에 추가하는 CPU·메모리·지연 부담이다.
- **응용 프로그래밍 인터페이스(Application Programming Interface, API) 잠금 추적**: 느린 요청의 거래 식별자를 따라 데이터베이스 잠금 대기가 꼬리 지연을 지배하는지 확인하는 분석이다.

</details>

| 문제 | 대책 | 효과 |
|:---|:---|:---|
| 평균에 느린 요청이 가려져 **체감 SLO 미달** | **p95·p99 지연** 과 오류율 관리 | 꼬리 지연의 **가시성 확보** |
| CPU 증설 뒤에도 **DB 잠금 병목 잔존** | **거래 ID·잠금 대기** 를 종단 추적 | 임계 경로의 **원인 분리** |
| 전후 워크로드 차이로 **효과 과대평가** | **동일 부하 회귀시험**으로 전후 비교 | 개선 효과와 **병목 이동 검증** |

#### 한줄 요약
- 주문 응용 프로그램 인터페이스의 느린 5% 요청 추적과 데이터베이스 잠금 대기의 95백분위수 지연 영향 확인

## Ⅶ. 결론

<details><summary>핵심 용어</summary>

- **폐루프 관리**: 목표 설정→측정→병목 분석→개선→동일 부하 재검증→기준선 갱신을 반복하는 관리 방식이다.
- **병목 이동**: 한 병목을 개선한 뒤 다음으로 제한적인 자원·호출 구간이 새 병목이 되는 현상이다.
- **개선안 채택**: 동일 부하에서 서비스 수준 목표의 병목 제거와 부작용 부재가 입증된 변경만 기준선에 반영하는 결정이다.

</details>

- 동일 부하에서 **SLO 병목 제거·부작용 없음** 을 입증한 개선안만 채택

#### 한줄 요약
- 자원 사용률 하나로 판단하지 않고 사용자 거래의 임계 경로를 같은 부하에서 전후 비교해야 함
