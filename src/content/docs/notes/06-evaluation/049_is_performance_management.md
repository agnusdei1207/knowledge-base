## Ⅰ. 개요

<details><summary>핵심 용어</summary>

- **정보시스템 성능 관리(IS Performance Management)**: 서버의 CPU나 메모리 점유율만 쳐다보는 1차원적 관제를 넘어, 사용자가 체감하는 핵심 거래(예: 결제 처리)의 응답 속도와 에러율을 타깃으로 삼아 병목 구간(Bottleneck)을 후벼 파고, 소스를 뜯어고친 뒤 동일한 부하를 다시 때려 진짜로 빨라졌는지 무한 반복 확인하는 지독한 폐루프(Closed-loop) 최적화 체계이다.
- **서비스 수준 목표(Service Level Objective, SLO)**: IT 부서가 "우리 서버 안 죽어요"라고 말로만 하는 게 아니라, "한 달 동안 사용자 결제 요청의 99%는 2초 이내에 성공적으로 응답하겠다"처럼 고객(현업)과 피로 맺은 절대 타협 불가한 정량적 성능 타깃 커트라인이다.
- **서비스 수준 지표(Service Level Indicator, SLI)**: SLO라는 과녁을 맞히기 위해 현재 우리 시스템이 쏘고 있는 화살의 영점, 즉 실시간으로 측정되는 실제 지연시간(Latency), 오류율(Error Rate), 가용성(Availability) 같은 날것의 성능 수치 데이터이다.

</details>

- 정의/개념: 고객 체감 지표인 **SLI**와 절대 타깃인 **SLO**를 잣대로 삼아, 시스템을 갉아먹는 병목(Bottleneck)을 색출하고 개선을 팩트로 검증해 내는 **정보시스템 성능 관리(IS Performance Management)** 체계이다.
- 배경/필요성: "CPU 50%니까 정상입니다"라는 개별 자원 사용률 핑계만으로는, 사용자의 결제창이 왜 10초나 돌고 있는지 그 숨겨진 지연(Latency) 원인과 계층 간 병목 핑퐁(이동) 현상을 절대 찾아내어 박살 낼 수 없기 때문이다.

#### 한줄 요약
- 서버 기계가 안 터진 게 중요한 게 아니라, 고객이 결제 버튼 눌렀을 때 빡치지 않게(3초 이내) 목표를 쾅 박아놓고 느려지는 범인을 찾아내 코드를 고치고 진짜 빨라졌는지 같은 부하로 다시 쏴보는 팩트 체크.

## Ⅱ. 특징

<details><summary>핵심 용어</summary>

- **기준선(Baseline)**: "우리 시스템 빨라졌어요!"라고 우기기 위해 필요한 최초의 거울, 즉 소스 코드를 고치거나 메모리를 늘리기 직전의 처참한 응답시간과 서버 부하 상태를 스냅샷처럼 찰칵 찍어둔 영점 비교 데이터이다.
- **워크로드(Workload)**: 서버를 때리는 주먹의 강도와 콤보, 즉 초당 몇 명이 동시에 들어오고(TPS), 데이터는 몇 메가를 던지며, 조회냐 쓰기냐를 섞어 시스템의 멱살을 잡고 흔드는 융단 폭격 부하량의 총합이다.
- **p95 지연시간(95th Percentile Latency)**: 평균 응답속도 "1초"라는 숫자에 속아, 뒤에서 10초씩 기다리며 빡쳐있는 5%의 꼬리(Tail) 불량 고객을 놓치지 않기 위해, "운 나쁜 하위 5% 빼고 95%의 고객이 이 시간 안에는 무조건 응답을 받았다"고 못 박는 잔인한 체감 지연 잣대이다.
- **종단 거래 식별자(End-to-End Transaction ID / Trace ID)**: 유저가 쏜 요청 하나가 앞단 웹서버 ➝ 중간 WAS ➝ 뒷단 DB까지 흘러가면서 찢어지고 파편화될 때, 그 꼬리표(ID)를 물고 늘어져 "WAS에서 2초, DB 잠금 대기로 5초 까먹었네"라고 핏줄처럼 역추적해 내는 바코드이다.

</details>

- 착시 현상을 일으키는 평균(Average) 뒤에 숨겨진 5%의 진짜 실패를 발라내는 **p95 지연시간(95th Percentile Latency)** 잣대가 핵심이다.
- 응용(WAS)과 **DB**, **CPU** 대기열 사이를 미로처럼 통과하는 유저 요청을 바코드(**거래 ID**) 하나로 끝까지 물고 늘어지는 추적성이 핵심이다.
- 개선(튜닝) 효과를 입증하려면 꼼수 부리지 말고, 튜닝 전후에 100% 동일한 **워크로드(Workload)** 스펙과 **기준선(Baseline)** 스냅샷을 들이대어 맞붙여야 한다.

#### 한줄 요약
- 전체 평균 속도가 빠르다고 자위하지 말고 가장 재수 없이 늦게 처리된 상위 5%(p95)의 느림보 요청을 멱살 잡아, 걔가 WAS에서 놀았는지 DB에서 멈췄는지 바코드(ID) 달아 추적한 뒤 똑같은 부하로 다시 때려보는 튜닝 기법.

## Ⅲ. 구조 및 구성요소

<details><summary>핵심 용어</summary>

- **애플리케이션 성능 모니터링(APM, Application Performance Monitoring)**: 엑스레이 기계처럼 시스템의 배를 갈라, 사용자 클릭부터 내부 자바(Java) 스레드가 꼬인 지점, DB 쿼리가 멈춘 곳, CPU가 불타는 곳을 한 화면에 쫙 뿌려주는 강력한 종단(End-to-End) 추적 레이더망이다.
- **임계 경로(Critical Path)**: 하나의 화면을 띄우기 위해 A 모듈 1초, B 모듈 3초, C 모듈 0.5초가 동시에 돌 때, 무조건 3초짜리 B 모듈이 끝나야만 전체가 끝나는, 즉 멱살 잡고 전체 응답 속도를 질질 끄는 가장 치명적이고 긴 병목 호출 파이프라인이다.
- **포화도(Saturation)**: 고속도로 톨게이트에 차가 얼마나 꽉 찼는지 보여주는 지표로, CPU, 메모리, DB 커넥션 풀(Pool) 등 한정된 자원의 여유 공간(Headroom)이 몇 %나 바닥나서 유저 요청들이 뒤에서 줄을 서서 빡치고 있는지(대기열 큐잉) 나타내는 척도이다.

</details>

```text
성능 관리 체계
├─ 목표•워크로드
├─ 관측 체계
├─ 응용 계층
├─ DB•인프라 계층
└─ 병목 개선•검증
```

선의 의미: 절대 뚫리면 안 되는 방어선(목표/워크로드) 아래 엑스레이망(관측 체계)을 쫙 깔아두고, 유저 요청이 지나가는 소프트웨어(응용)와 하드웨어(DB/인프라) 계층을 샅샅이 훑어, 최종적으로 막힌 똥(병목)을 뚫고 팩트로 다시 쏴보는(검증) 정적 수직 하강 구조를 나타낸다.

| 구성요소 | 책임 및 분석 초점 |
|:---|:---|
| 목표•워크로드 | 절대 양보 못할 체감 속도(SLI/SLO)와, 시스템을 때려 부술 초당 유저 수(TPS), 데이터 덩치(기준선) 강제 세팅 |
| 관측 체계 | 맹인 코끼리 만지기 방지를 위한 **APM** 엑스레이 가동, Trace ID로 로그와 스레드(Thread) 덤프 묶음 추적 |
| 응용 계층 | 엉망으로 짠 스파게티 코드, 남의 API 응답 기다리다 무한 대기 걸린 스레드(Thread) 병목 색출 |
| DB•인프라 계층 | CPU 100% 뻗음(**포화도**), DB Lock(잠금) 걸려 멈춘 악성 쿼리, 꽉 찬 큐(Queue) 폭발 징후 색출 |
| 병목 개선•검증 | 가장 지독한 **임계 경로(Critical Path)**를 뜯어고친 뒤, 100% 동일한 부하를 주입해 튜닝 약효 증명 |

#### 한줄 요약
- 유저 클릭 한 번이 WAS와 DB를 뚫고 지나가는 긴 터널(임계 경로) 속에서, 어디에 차가 막혀 서 있는지(포화도) 엑스레이(APM)로 찍어내어, 그 도로를 확충한 뒤 똑같은 차 1만 대를 다시 부어보는(검증) 인프라 레이싱.

## Ⅳ. 흐름도

<details><summary>핵심 용어</summary>

- **병목(Bottleneck)**: 깔때기의 좁은 주둥이처럼, 다른 곳(CPU/메모리)은 다 텅텅 비어 여유가 넘치는데 오직 DB 디스크 I/O 혼자 100% 폭주해서 전체 서비스의 속도와 트래픽(TPS)을 질식시켜버리는 최악의 교통 체증 구간이다.
- **회귀 검증(Regression Testing)**: A 쿼리를 튜닝해서 1초 만에 나오게 기뻐했는데, 알고 보니 그 나비효과로 B 화면이 뻗어버리거나 DB CPU가 100% 쳐버리는 등 "튜닝 전보다 다른 데가 더 박살 나진 않았는지(풍선효과)" 돌다리를 두드려보는 방어 시험이다.
- **동일 워크로드 비교(Identical Workload Comparison)**: 튜닝 전에는 동시 접속자 1천 명으로 때려놓고, 튜닝 후에는 1백 명으로 때린 뒤 "빨라졌죠?"라고 사기 치는 것을 막기 위해, 1바이트의 오차도 없이 동일한 부하 스크립트(JMeter 등)를 쏴서 공정하게 팩트를 까발리는 실험 원칙이다.

</details>

```text
              [성능 관리자]
                  │ 1. SLO•워크로드 설정
                  │   기준선 부하 실행 요청
                  ▼
              [대상 시스템]
                  │ 거래•자원 계측
                  ▼
              [관측 도구]
                  │ 기준선 증거
                  ▼
              [성능 관리자]
                  │ 2. 기준선 분석
                  │   목표•피크 부하 실행 요청
                  ▼
              [대상 시스템]
                  │ 부하별 거래•자원 계측
                  ▼
              [관측 도구]
                  │ 임계 경로 증거
                  ▼
              [성능 관리자]
                  │ 3. 병목 원인 분석
                  │   개선•회귀시험 요청
                  ▼
              [대상 시스템]
                  │ 동일 부하 계측
                  ▼
              [관측 도구]
                  │ 개선 전후 결과
                  ▼
              [성능 관리자]
                  │ 4. 개선 효과 검증
```

### 동작 원리

1. **SLO•워크로드 설정**: "상위 95%(p95) 유저는 무조건 2초 컷"이라는 독한 타깃(SLO)과 들이부을 유저 수(부하 조건)를 픽스한다.
2. **기준선 분석**: 튜닝 전 구린 소스 코드 상태에서 한 대 맞고, 그때 터져 나가는 지연율과 대기열 큐(포화도), **임계 경로**를 박제(저장)한다.
3. **병목 원인 분석**: APM 바코드를 까 뒤집어, CPU 탓인지 DB 쿼리 탓인지 악성 **병목(Bottleneck)**의 진짜 범인을 멱살 잡아 색출한다.
4. **개선 효과 검증**: 코드를 땜빵한 후 **동일 워크로드 비교** 스팀팩을 맞혀 진짜 빨라졌는지, 풍선효과는 없는지 **회귀 검증(Regression)**한다.

#### 한줄 요약
- 튜닝 전 구린 상태를 스냅샷(기준선) 찍어두고, 엑스레이로 막힌 혈관(병목) 찾아 뚫어준 다음, 처음 맞았던 똑같은 펀치(부하)를 다시 때려봐서 진짜 맷집이 좋아졌고 딴 데가 안 터지는지(회귀) 더블 체크하는 무한 뺑뺑이.

## Ⅴ. 종류 및 비교

<details><summary>핵심 용어</summary>

- **애플리케이션 병목(Application Bottleneck)**: 서버 자원(CPU 등)은 남아도는데 개발자가 짠 자바(Java) 코드가 구려서 쓰레기 수집(GC)에 빠지거나, 쓸데없이 루프를 1만 번 돌거나, 안 오는 외부 API 응답을 하염없이 기다리다 스레드(Thread)가 말라 죽는 소프트웨어적 질식 상태이다.
- **데이터베이스 병목(Database Bottleneck)**: 인덱스(Index) 안 태우고 풀 스캔(Full Scan) 때리는 무식한 악성 쿼리, 혹은 남이 쓰고 있는 로우(Row)를 붙들고 늘어지는 잠금(Lock) 경합 때문에 DB 디스크와 커넥션 풀이 불타오르는 데이터 계층의 암 덩어리이다.
- **인프라 병목(Infrastructure Bottleneck)**: 코드도 좋고 쿼리도 튜닝했는데 애초에 서버 깡통(CPU, 메모리, 1G 랜카드) 덩치가 너무 작거나, 로드밸런서(L4)가 트래픽을 한 놈한테 몰아줘서 뻗어버리는 물리적 하드웨어 한계 상태이다.

</details>

| 병목 혐의자 (계층) | 범인 확정용 판정 증거 (APM 단서) | 멱살 잡아야 할 대표 원인 |
|:---|:---|:---|
| **애플리케이션 병목** | 코드 응답시간 지연, GC(가비지 컬렉터) 멈춤 시간 폭주, 외부 HTTP 호출 대기 | 최악의 동기식 직렬 처리 코드, 스레드 고갈, 메모리 릭(Leak) |
| **데이터베이스 병목** | 플랜 꼬인 악성 쿼리 실행계획, Lock Wait(잠금 대기) 떡상, 스토리지 I/O 100% | 튜닝 안 된 쿼리, 인덱스 부재, 트랜잭션 경합 고립(Deadlock) |
| **인프라 병목** | 서버 **CPU** 100% 뻗음, 메모리 스왑(Swap) 발생, 네트워크 큐(Queue) 꽉 차서 드랍 | 트래픽 융단 폭격(용량 부족), 로드밸런서 L4 불균형 분배 |

- APM 엑스레이를 돌려, 지연시간이 어느 계층에서 파킹(대기)되어 있는지 **병목 계층 선택(Bottleneck Layer Selection)**으로 범인을 좁혀 들어간다.

#### 한줄 요약
- 유저가 10초를 기다렸을 때 그 시간이 WAS 자바 코드에서 깎인 건지(앱 병목), DB 잠금 기다리다 깎인 건지(DB 병목), 서버 CPU가 느려 터져 깎인 건지(인프라 병목)를 분리해 내 엉뚱한 사람 잡지 않게 핀포인트로 조지는 기술.

## Ⅵ. 실무 고려사항 및 대책

<details><summary>핵심 용어</summary>

- **캐시(Cache)**: 무거운 DB까지 매번 땅을 파고 들어가지 않도록, 유저들이 자주 찾는 조회 데이터(예: 메뉴판)를 초고속 메모리(Redis 등)에 복사해 두고 0.01초 만에 툭 던져줘서 DB를 실업자로 만들어버리는 극한의 튜닝 비기이다.
- **인덱스(Index)**: 두꺼운 백과사전에서 1페이지부터 끝까지 다 넘겨보는 바보짓(Full Scan)을 막기 위해, 맨 뒷장 '찾아보기' 색인을 만들어 단 3번의 클릭(B-Tree) 만에 원하는 데이터를 끄집어내는 DB 튜닝의 마스터키이다.
- **계측 오버헤드(Instrumentation Overhead)**: 성능 잡겠다고 APM을 깔고 Trace ID 로그를 미친 듯이 찍어댔더니, 정작 그 로그 기록하는 작업 때문에 서버 CPU가 30%나 더 깎이고 레이턴시가 느려져 배보다 배꼽이 더 커져 버린 자기 파괴적 감시 부하이다.

</details>

| 제기된 실무 문제점 | 현장 적용 대책 | 기대되는 비즈니스 효과 |
|:---|:---|:---|
| 95%는 빠른데 VVIP 5% 고객이 느려서 욕먹음(평균의 함정) | 눈속임 평균치 버리고 **p95•p99 지연시간**과 오류율 멱살 관리 체제로 전환 | 꼬리(Tail) 지연 가시성 100% 확보 및 숨겨진 악성 지연 원인 발본색원 |
| 메모리 **캐시** 떡칠했는데도 결제할 때 디비 잠금(Lock) 대기로 다 뻗어버림 | 거래 ID 꼬리표 붙여 DB 잠금 대기 원인 색출 후 **인덱스** 강제 튜닝 및 쿼리 재설계 | 가짜 성능 개선(캐시)에 속지 않고 찐 **임계 경로(Critical Path)** 튜닝 성공 |
| 잡으라는 병목은 안 잡고 감시(APM) 툴 때문에 서버가 뻗는 **계측 오버헤드** 발생 | 100% 전수 조사 포기하고, 대표 거래 표본(샘플링) 타기팅 및 수집률 다이얼 조정 | 레이더(APM) 부담을 최소 통제하며 시스템 본연의 처리 성능 사수 |

#### 한줄 요약
- 평균 1초라고 속지 말고 느린 상위 5% 고객을 구출(p95)하고, 캐시 발랐다고 안심하다 뚫리는 DB Lock(잠금) 대기를 인덱스로 찢어버리며, 성능 잡겠다고 깐 APM이 서버 잡아먹지 않게 측정 빈도(오버헤드)를 조절하는 게 튜닝의 정석.

## Ⅶ. 결론

<details><summary>핵심 용어</summary>

- **병목 이동(Bottleneck Shift/Balloon Effect)**: WAS의 썩은 코드를 튜닝해 처리량을 2배로 폭발시켰더니, 그 엄청난 트래픽이 고스란히 뒷단 DB로 쏟아져 이번엔 DB 서버가 불타버리는, 풍선 한쪽을 누르면 다른 쪽이 터지는 끔찍한 연쇄 병목 현상이다.
- **개선안 채택(Improvement Adoption Decision)**: 개발자가 "코드 고쳤으니 운영에 배포하시죠" 할 때 덥석 물지 않고, 튜닝 전후 부하 테스트를 십자 대조하여 (1) 타깃(SLO)은 깼는지 (2) 딴 데 불붙는 부작용(병목 이동)은 없는지 두 눈으로 확인한 뒤에야 상용계 릴리즈 도장을 찍어주는 철벽 방어 결정이다.

</details>

- 지독한 **폐루프 관리(Closed-loop)** 사이클을 무한으로 돌려 풍선효과인 **병목 이동(Bottleneck Shift)**을 쫓아가 박살 내고, 팩트가 입증된 것에만 **개선안 채택(Improvement Adoption)**을 승인하는 판단 필수.

#### 한줄 요약
- 앞문 뚫었더니 뒷문 터지는 병목 핑퐁 게임(병목 이동)에 쫄지 말고, 부하 쏘고 튜닝하고 다시 쏘는 도돌이표(폐루프)를 무한 반복해 완벽히 입증된 패치만 운영에 반영(개선 채택)하는 지독한 성능 사냥.
