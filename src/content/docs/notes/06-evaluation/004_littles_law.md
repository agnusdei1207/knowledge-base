## Ⅰ. 개요

<details><summary>용어 설명</summary>

- **리틀의 법칙(Little's Law / John D.C. Little 1961)**: 시스템이 정상적인 안정 상태(Steady State)에 있을 때, 시스템 내부에 머무르는 평균 작업 수($L$, 재공량/동시성)는 작업의 평균 유입·처리율($\lambda$, Throughput)과 작업이 시스템 내에 머무르는 평균 체류 시간($W$, Response Time)의 곱($L = \lambda W$)과 항상 일치한다는 대기행렬 수리 법칙.
- **동시성 및 스레드 풀 과소·과대 사이징 결함(Concurrency Mismatch Defect)**: 목표 TPS와 평균 응답시간 간의 수리적 상관관계를 고려하지 않고 임의의 수치로 WAS 스레드 풀이나 부하 시험 가상 사용자(VUser)를 설정하여, 락(Lock) 경합으로 인한 CPU 낭비 또는 스레드 고갈로 인한 요청 누락을 초래하는 구조적 결함.

</details>

- 정의/개념: 인프라 자원의 최적 동시 처리 용량을 수리적으로 도출하기 위해 **측정 경계 및 안정 상태 검증 $\rightarrow$ 평균 처리율($\lambda$) 및 응답시간($W$) 실측 $\rightarrow$ 수식($L = \lambda W$) 기반 적정 동시 작업 수(WIP) 산출 $\rightarrow$ 생각 시간(Think Time) 반영 가상 사용자(VUser) 역산 $\rightarrow$ WAS 스레드 풀 및 DB 커넥션 풀 최적 사이징** 을 집행하는 **성능 공학 핵심 수리 법칙**
- 배경/필요성: 도착 분포나 서비스 시간 분포(정규/포아송/일반 분포)의 형태와 무관하게 모든 안정 시스템에 보편적으로 성립하는 단순하고 강력한 수학적 불변성을 제공하여 성능 예측의 신뢰성 확보

#### 한줄 요약
- 리틀의 법칙은 안정 상태 시스템에서 평균 작업 수(L)가 처리율(λ)과 체류시간(W)의 곱(L=λW)과 일치함을 규명한다.

## Ⅱ. 특징

<details><summary>용어 설명</summary>

- **리틀의 법칙 3대 핵심 구성 변수**:
  - **평균 재공량 ($L$, Work In Process / Concurrency)**: 시스템 내부에서 대기 중이거나 실제 연산 처리 중인 평균 작업(요청) 수.
  - **평균 처리율 ($\lambda$, Throughput / Arrival Rate)**: 단위 시간(초)당 시스템으로 유입되어 처리를 완료하고 배출되는 평균 트랜잭션 수 (TPS).
  - **평균 체류시간 ($W$, Response Time / Lead Time)**: 요청이 큐에 진입한 순간부터 처리가 완료되어 응답을 반환할 때까지의 총 경과 시간.

</details>

- **분포 비의존적 보편성(Distribution-free Invariance)**: 요청의 도착 간격이나 서비스 처리 시간이 어떤 확률 분포(포아송, 지수, 파레토 등)를 따르든, 서비스 순서(FIFO, LIFO, 우선순위)가 무엇이든 관계없이 항시 성립
- **3대 변수 상호 역산(Bidirectional Derivation)**: 세 변수($L, \lambda, W$) 중 두 값을 측정하면 나머지 하나의 미지수를 수학적으로 오차 없이 정확히 역산 가능
- **성능 테스트 가상 사용자(VUser) 산정의 수학적 근거**: $\text{VUser} = \text{TPS} \times (\text{Response Time} + \text{Think Time})$ 공식을 통해 실무 부하 시나리오의 동시 사용자 수를 정밀 산출

#### 한줄 요약
- 분포 비의존적 성립, 3대 변수 상호 역산, 성능 시험 VUser 및 자원 풀 사이징 근거를 제공한다.

## Ⅲ. 구조 및 구성요소

<details><summary>용어 설명</summary>

- **리틀의 법칙 3대 적용 영역 및 파생 공식**:
  1. **시스템 전체 레벨**: $L_{sys} = \lambda \times W_{sys}$ (큐 대기 작업 + 서버 연산 작업).
  2. **대기열(Queue) 레벨**: $L_q = \lambda \times W_q$ (순수 큐 대기 작업 수와 대기 시간).
  3. **서비스(Server) 레벨**: $L_s = \lambda \times W_s = \frac{\lambda}{\mu} = \rho$ (서버 가동률/비지 상태 서버 수).

</details>

```text
┌─────────────────────────────────────────────────────────────────────────┐
│ [ 1. 리틀의 법칙 측정 경계 및 계층 분해 구조 (Measurement Boundary) ]   │
│                                                                         │
│  유입률 (λ)          [ 1. 대기열 영역 (Queue) ]     [ 2. 서비스 영역 (Server) ] │
│  ──────────► ┌───────────────────────────┐ ──► ┌───────────────────┐ ──► 완료 배출 (λ)
│   (요청 인입) │ [WIP] [WIP] [WIP] ...     │     │ [실행 중 작업]     │    (Throughput)
│              └───────────────────────────┘     └───────────────────┘
│               대기열 재공량: L_q = λ × W_q       서버 재공량: L_s = λ × W_s (ρ)
│              └─────────────────────────────────────────────────────┘
│                     전체 시스템 재공량: L = L_q + L_s = λ × W
└────────────────────────────────────┬────────────────────────────────────┘
                                     │ (실무 가상 사용자 산정 확장)
                                     ▼
┌─────────────────────────────────────────────────────────────────────────┐
│ [ 2. 실무 부하 테스트 가상 사용자(VUser) 산정 공식 체계 ]               │
│                                                                         │
│  ┌───────────────────────────────────────────────────────────────────┐  │
│  │ $\text{VUser} = \text{Target TPS} \times (\text{Response Time} + \text{Think Time})$ │  │
│  └───────────────────────────────────────────────────────────────────┘  │
│  ├─ Target TPS ($\lambda$): 초당 달성해야 하는 비즈니스 목표 처리량      │
│  ├─ Response Time ($W$): 서버 측 왕복 응답 지연 시간 (초)               │
│  └─ Think Time: 사용자가 화면을 읽고 다음 클릭까지 대기하는 시간 (초)    │
└─────────────────────────────────────────────────────────────────────────┘
```

선의 의미: 유입된 요청이 대기열과 서버를 거쳐 배출되는 과정에서 전체 및 부분 계층별로 $L=\lambda W$가 성립하는 구조

| 적용 계층 | 핵심 공식 | 물리적 의미 | 실무 튜닝 활용 |
|:---|:---|:---|:---|
| **전체 시스템 (System)** | $L = \lambda \times W$ | 시스템 내 동시 처리 중인 총 요청 수 | WAS 전체 활성 스레드 수 산정 |
| **대기열 (Queue)** | $L_q = \lambda \times W_q$ | 큐에 쌓여 대기 중인 잔여 요청 수 | 소켓 백로그(Backlog) 큐 크기 설정 |
| **서버 (Server)** | $L_s = \lambda \times W_s = \rho$ | 연산을 수행 중인 활성 CPU/서버 수 | CPU 코어 수 및 병렬 워커 수 산정 |
| **부하 테스트 (Load Test)**| $\text{VUser} = \text{TPS} \times (W + \text{Think})$| 목표 TPS 달성을 위한 동시 접속자 수| 부하 발생기(JMeter) 가상 사용자 설정 |

#### 한줄 요약
- 전체 시스템($L=\lambda W$), 대기열($L_q=\lambda W_q$), 서버($L_s=\lambda W_s$), VUser 산정 공식으로 구성된다.

## Ⅳ. 흐름도

<details><summary>용어 설명</summary>

- **리틀의 법칙 기반 스레드 풀 및 VUser 사이징 5단계 프로세스**:
  1. 비즈니스 목표 처리량($\text{TPS} = 2,000$) 및 예상 응답시간($W = 0.05\text{초}$) 정의
  2. 리틀의 법칙 적용을 위한 시스템 안정 상태(유입량 = 배출량) 확인
  3. 순수 내부 동시 처리 작업 수($L = \lambda W$) 계산
  4. 사용자 생각 시간($\text{Think Time} = 3\text{초}$) 반영 부하 시험 가상 사용자(VUser) 도출
  5. WAS 스레드 풀 및 DB 커넥션 풀에 안전 여유율을 가산하여 최종 인프라 파라미터 확정

</details>

```text
1. [성능 요구사항 및 목표 정의]
    ├─ 목표 비즈니스 처리량: $\text{Target TPS} = 2,000 \text{ req/sec}$
    ├─ 목표 평균 응답시간: $\text{Response Time } (W) = 50\text{ms} = 0.05\text{초}$
    └─ [사용자 평균 체류/생각 시간: $\text{Think Time} = 2.95\text{초}$]
            │
            ▼
2. [시스템 내부 동시성 (WIP) 산출]
    ├─ $L = \lambda \times W = 2,000 \times 0.05 = 100 \text{개}$
    └─ [시스템 내부에서 동시에 실행 및 대기 중인 트랜잭션 수는 정확히 100개임]
            │
            ▼
3. [WAS 스레드 풀 및 DB 커넥션 풀 사이징]
    ├─ 순수 필요 스레드 수: 100개
    ├─ 버스트 스파이크 및 GC 일시 정지 대비 $+50\%$ 여유율 적용
    └─ [최종 확정: 클러스터 전체 활성 스레드 풀 크기 = 150개 (노드당 50개 × 3대)]
            │
            ▼
4. [부하 테스트 가상 사용자 (VUser) 역산]
    ├─ $\text{VUser} = \text{TPS} \times (W + \text{Think Time}) = 2,000 \times (0.05 + 2.95) = 2,000 \times 3.0 = 6,000\text{명}$
    └─ [JMeter에 6,000명의 동시 가상 사용자를 설정해야 2,000 TPS 부하 주입 가능]
            │
            ▼
5. [부하 시험 실행 및 수리 모델 검증]
    ├─ JMeter 6,000 VUser 기동 ➔ 실제 2,000 TPS 측정 및 평균 응답시간 48ms 기록
    └─ [리틀의 법칙 계산치와 실측치 오차 4% 이내로 수리 모델 정합성 입증]
```

**동작 원리**

1. **블랙박스 추론의 힘**: 시스템 내부 아키텍처가 아무리 복잡한 마이크로서비스로 얽혀 있어도 경계 진입점과 종료점의 입출력 데이터만으로 내부 상태를 완벽히 규명
2. **단위 정합성의 엄격성**: 시간 단위를 초(Seconds)로 통일($\lambda$는 req/sec, $W$는 sec)해야만 정확한 차원 분석(Dimensional Analysis: $[\text{Items}] = [\frac{\text{Items}}{\text{Time}}] \times [\text{Time}]$) 성립
3. **과잉 스레드 생성 방지**: $L=100$인 시스템에 관행적으로 1,000개의 스레드를 할당할 경우 Context Switching 부하로 인해 오히려 $W$가 증가하고 TPS가 급감하는 역효과를 수리적으로 차단
4. **안정 상태의 전제**: 유입률이 처리 용량을 초과하여 대기열이 발산하는 비정상 상태(Unsteady State)에서는 리틀의 법칙을 적용할 수 없음을 사전 검증
5. **폐쇄 루프 용량 엔지니어링**: 실측된 $W$의 변화를 실시간 감시하여 $\lambda$ 유지에 필요한 $L$의 동적 확장(Autoscaling) 기준으로 활용

#### 한줄 요약
- 요구사항 정의, 내부 동시성(L) 산출, 스레드 풀 사이징, VUser 역산, 부하 시험 검증 순으로 동작한다.

## Ⅴ. 종류 및 비교

<details><summary>용어 설명</summary>

- **성능 엔지니어링 3대 핵심 수리 법칙 비교**:
  - 리틀의 법칙 (Little's Law): 동시성, 처리율, 체류시간 간의 대기행렬 균형 법칙 ($L = \lambda W$).
  - 암달의 법칙 (Amdahl's Law): 병렬 프로세서 확장에 따른 가속 한계 예측 법칙 ($S(N) = \frac{1}{(1-p) + \frac{p}{N}}$).
  - 유니버설 스케일링 법칙 (USL: Universal Scalability Law): 경합과 일관성 오버헤드를 포함한 확장성 한계 법칙.

</details>

| 비교 항목 | 리틀의 법칙 (Little's Law) | 암달의 법칙 (Amdahl's Law) | 유니버설 스케일링 법칙 (USL) |
|:---|:---|:---|:---|
| **수리 모델 공식**| $L = \lambda \times W$ | $S(N) = \frac{1}{(1-p) + p/N}$ | $X(N) = \frac{\gamma N}{1 + \sigma(N-1) + \kappa N(N-1)}$ |
| **핵심 분석 대상**| **동시 작업 수, 체류 시간, 처리율**| **코어 증설에 따른 병렬 가속비**| **노드 증설 시 경합 및 일관성 한계**|
| **적용 시점** | **스레드 풀/VUser 용량 사이징** | CPU 멀티코어 병렬 알고리즘 설계| 분산 DB/쿠버네티스 클러스터 확장|
| **가정 조건** | **안정 상태 (Steady State)** | 고정 크기 워크로드 (Strong Scaling)| 노드 간 큐 경합($\sigma$) 및 동기화($\kappa$)|
| **주요 한계점** | 큐 발산(비정상 상태) 시 적용 불가 | 통신 및 캐시 동기화 오버헤드 무시 | 파라미터($\sigma, \kappa$) 회귀 추정 필요 |

#### 한줄 요약
- 리틀의 법칙은 대기열 동시성, 암달의 법칙은 병렬 가속 한계, USL은 분산 클러스터 확장 한계를 다룬다.

## Ⅵ. 실무 고려사항 및 대책

<details><summary>용어 설명</summary>

- **리틀의 법칙 실무 적용 시 3대 위험 요소와 대책**:

</details>

| 문제 | 대책 | 효과 |
|:---|:---|:---|
| 성능 시험 시 Think Time을 0으로 설정하여 **실제 6,000명의 동시 사용자를 수용하기 위해 비현실적인 6,000 VUser를 기동하다가 부하 발생기 메모리 고갈(OOM) 마비** | **리틀의 법칙 공식($\text{VUser} = \text{TPS} \times (W + \text{Think})$)에 따라 실제 사용자 행동 로그 기반 Think Time(예: 3초)을 정확히 모델링** | 부하 발생기 리소스 90% 절감 및 실 트래픽 정밀 모사 |
| 피크 트래픽 폭주로 유입량($\lambda_{in}$)이 처리량($\lambda_{out}$)을 초과하는 **비정상 붕괴 상태에서 리틀 공식을 적용하여 잘못된 용량 산정 결과 도출** | **유입과 배출이 평형을 이루는 안정 구간(Steady State)만을 필터링하여 지표를 추출하고, 붕괴 구간은 대기행렬 시뮬레이션으로 전환** | 수리 모델 적용 오류 0% 및 데이터 신뢰성 확보 |
| 초당 처리량(TPS)과 밀리초(ms) 단위의 응답시간을 **단위 환산 없이 직접 곱하여 스레드 풀 크기가 1,000배로 뻥튀기 계산되는 단위 불일치 오류 발생** | **응답시간을 초(Seconds) 단위로 엄격히 변환(예: $50\text{ms} \rightarrow 0.05\text{초}$)하는 차원 정합성 검증 스크립트 강제화** | 용량 산정 계산 착오 원천 배제 |

#### 한줄 요약
- Think Time 모델링으로 부하를 모사하고, 안정 구간 필터링으로 오판을 막으며, 단위 정합성으로 계산 오류를 배제한다.

## Ⅶ. 결론

- 시스템의 동시 처리 역량을 수학적으로 규명하고 스레드 풀 및 부하 시험 가상 사용자 규모를 결정하는 성능 공학의 기초 수리 원리인 **리틀의 법칙 체계**는 단순한 이론을 넘어 엔터프라이즈 용량 설계의 절대적인 불변식이며, 실무 구현 시 **안정 상태(Steady State) 전제 조건 검증**, **시간 단위(초)의 엄격한 차원 정합성 유지**, **Think Time을 결합한 가상 사용자(VUser) 정밀 산출**, **스레드 풀 및 DB 커넥션 풀의 최적화**를 완성하여 자원 낭비 없는 고효율 시스템 아키텍처를 완성

#### 한줄 요약
- $L=\lambda W$ 불변식을 통해 최적의 동시성 및 스레드 풀 규모를 수학적으로 완성한다.
