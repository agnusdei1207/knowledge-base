## Ⅰ. 개요

<details><summary>용어 설명</summary>

- **결함 밀도와 결함 제거율(Defect Density & DRE: Defect Removal Efficiency)**:
  - **결함 밀도 (Defect Density)**: 소프트웨어의 규모(KLOC: 1,000 라인, FP: 기능점수) 대비 발견된 결함(Defect) 건수를 정규화한 지표로, 개별 모듈 및 시스템의 내재적 코드 품질과 결함 집중도를 평가하는 척도 ($\text{Defect Density} = \frac{\text{발견된 총 결함 수}}{\text{소프트웨어 규모 (KLOC 또는 FP)}}$).
  - **결함 제거율 (DRE: Defect Removal Efficiency)**: 전체 결함 중 상용 배포 전(요구분석, 설계, 구현, 테스트 단계)에 선제적으로 발견되어 제거된 결함의 백분율로, QA 테스트 프로세스의 결함 차단력과 품질 통제 역량을 평가하는 척도 ($\text{DRE} = \frac{\text{출시 전 검출 결함 } (D_{\text{pre}})}{\text{출시 전 검출 결함 } (D_{\text{pre}}) + \text{출시 후 유출 결함 } (D_{\text{post}})} \times 100\%$).
- **단순 결함 건수 비교 왜곡 및 유출 결함 은폐 결함(Raw Count Distortion Defect)**: 100줄짜리 모듈의 버그 5건과 10만 줄짜리 모듈의 버그 10건을 단순 건수로만 비교하여 소형 모듈의 극심한 코드 결함을 방치하거나, 출시 직전 테스트에서 버그를 많이 잡았다고 자축했으나 실제 상용 오픈 후 고객에 의해 수백 건의 치명적 결함(Escaped Defects)이 터지는 구조적 결함.

</details>

- 정의/개념: 소프트웨어 코드 품질과 테스트 공정 효율성을 입체적으로 진단하기 위해 **규모 정규화 기반 결함 밀도(Defect Density) 산출 $\rightarrow$ 출시 후 3~6개월 유출 결함(Escaped Defect) 추적 $\rightarrow$ 공정별/종합 결함 제거율(DRE) 계산 $\rightarrow$ $2 \times 2$ 품질 매트릭스 진단 $\rightarrow$ 고밀도 모듈 리팩토링 및 저DRE 테스트 케이스 보강** 을 집행하는 **소프트웨어 품질 정량 평가 체계**
- 배경/필요성: 프로젝트 간 또는 모듈 간의 품질 수준을 공정하게 비교하고, 테스트 조직이 개발 결함을 상용 배포 전에 몇 %나 차단해냈는지 통계적 증거를 확보하기 위해 두 지표의 복합 활용 필수

#### 한줄 요약
- 결함 밀도는 코드 자체의 결함 집중도를 측정하고, DRE는 테스트 공정의 결함 차단 효과성을 평가한다.

## Ⅱ. 특징

<details><summary>용어 설명</summary>

- **결함 관리 2대 핵심 평가 지표의 차별점**:
  - **결함 밀도 (코드 관점)**: "어느 서브시스템의 코드가 가장 위험하고 지저분한가?"를 진단 $\rightarrow$ 개발팀 리팩토링 대상 특정.
  - **결함 제거율 DRE (공정 관점)**: "우리 QA 팀이 버그를 사전에 얼마나 잘 걸러내고 있는가?"를 진단 $\rightarrow$ 테스트 공정 성숙도 특정.

</details>

- **규모 차이에 대한 공정한 정규화(Size Normalization)**: 소스코드 라인 수(KLOC) 또는 기능점수(FP)로 결함 수를 나눔으로써 대형 모듈과 소형 모듈 간의 품질을 동일 선상에서 객관적 비교
- **출시 후 관찰 기간(Observation Window) 의무화**: 출시 후 최소 3개월~6개월 동안 운영 환경에서 사용자가 발견한 유출 결함($D_{\text{post}}$)을 DRE 분모에 정확히 합산
- **단계별 결함 제거율(Phase-wise DRE) 확장**: 요구사항 분석 $\rightarrow$ 아키텍처 설계 $\rightarrow$ 단위 테스트 $\rightarrow$ 통합 테스트 각 단계에서 다음 단계로 결함이 누출되지 않고 해당 단계에서 제거된 비율을 세부 추적

#### 한줄 요약
- 규모 정규화(KLOC/FP), 3~6개월 유출 결함 추적, 단계별 DRE 확장, 2x2 매트릭스 의사결정을 제공한다.

## Ⅲ. 구조 및 구성요소

<details><summary>용어 설명</summary>

- **결함 밀도 및 DRE 정량 수식 체계**:
  1. **결함 밀도 공식**: $\text{Defect Density} = \frac{\text{Total Defects Found}}{\text{Software Size (KLOC / FP)}} \text{ [defects/KLOC]}$.
  2. **종합 결함 제거율 (DRE)**: $\text{DRE} = \frac{D_{\text{pre}}}{D_{\text{pre}} + D_{\text{post}}} \times 100\% = \frac{D_{\text{pre}}}{D_{\text{total}}} \times 100\%$.
  3. **단계별 결함 제거율 ($\text{Phase DRE}_i$)**: $\text{DRE}_i = \frac{E_i}{E_i + E_{i+1}} \times 100\%$ ($E_i$: $i$단계 발견 결함, $E_{i+1}$: $i+1$단계 유출 결함).

</details>

```text
┌─────────────────────────────────────────────────────────────────────────┐
│ [ 1. 결함 밀도 및 결함 제거율(DRE) 시간 축 라이프사이클 ]              │
│                                                                         │
│  [ 1. 개발 및 테스트 단계 (Pre-release) ]     [ 2. 상용 운영 (3~6개월) ]│
│  ├─ 단위/통합/시스템 테스트 결함: D_pre = 900건 ├─ 고객 유출 결함: D_post = 100건 │
│  └─ 소프트웨어 규모: 100 KLOC (100,000 라인)  └─ 총 발생 결함: 1,000건  │
│                                                                         │
│   ├─ [결함 밀도] = 1,000건 / 100 KLOC = 10.0 defects/KLOC (전체 품질)   │
│   └─ [결함 제거율 DRE] = (900 / 1,000) × 100 = 90.0% (테스트 차단 효율) │
└────────────────────────────────────┬────────────────────────────────────┘
                                     │ (2x2 품질 진단 매트릭스)
                                     ▼
┌─────────────────────────────────────────────────────────────────────────┐
│ [ 2. 결함 밀도 vs DRE 2x2 품질 의사결정 매트릭스 ]                      │
├───────────────────┬─────────────────────────────────┬───────────────────┤
│ 구분              │ 낮은 결함 밀도 (Low Density)    │ 높은 결함 밀도 (High Density)│
├───────────────────┼─────────────────────────────────┼───────────────────┤
│ **높은 DRE**      │ **[ 이상적 고품질 (Ideal) ]**   │ **[ 코드 재설계 필요 ]**          │
│ **(High DRE > 90%)**│ ├─ 코드 자체도 견고하고         │ ├─ 코드는 불안정하나              │
│                   │ └─ QA가 결함을 거의 완벽 차단   │ └─ QA가 상용 전 100% 걸러냄 (우수)│
├───────────────────┼─────────────────────────────────┼───────────────────┤
│ **낮은 DRE**      │ **[ 테스트 결함 은폐 (Danger) ]**│ **[ 최악의 재난 상태 (Catastrophe)]│
│ **(Low DRE < 80%)** │ ├─ 테스트가 부실하여 버그를 못 찾음│ ├─ 코드도 엉망이고                │
│                   │ └─ 상용 배포 후 대규모 버그 폭발│ └─ 상용 유출 결함 대규모 발생     │
└───────────────────┴─────────────────────────────────┴───────────────────┘
```

선의 의미: 출시 전/후 결함을 집계하여 결함 밀도와 DRE를 산출하고 2x2 매트릭스로 개발 코드와 QA 공정의 문제를 분리 진단하는 구조

| 산출 지표 | 수학적 산식 | 목표 표준 기준치 | 진단 대상 및 개선 조치 |
|:---|:---|:---|:---|
| **결함 밀도 (KLOC)**| $\frac{\text{총 결함 건수}}{\text{KLOC}}$ | 일반 상용: $< 2.0 \text{ def/KLOC}$ | 소스코드 복잡도, 모듈 리팩토링 |
| **결함 밀도 (FP)** | $\frac{\text{총 결함 건수}}{\text{기능점수(FP)}}$ | 기능 단위: $< 0.1 \text{ def/FP}$ | 비즈니스 로직 및 요구사항 명세 |
| **종합 DRE (%)** | $\frac{D_{\text{pre}}}{D_{\text{pre}} + D_{\text{post}}} \times 100$ | **목표: $\ge 90\% \sim 95\%$** | QA 테스트 케이스 커버리지 보강 |
| **요구단계 DRE** | $\frac{E_{\text{req}}}{E_{\text{req}} + E_{\text{design}}} \times 100$| **목표: $\ge 60\%$** | 요구사항 리뷰 및 정적 인스펙션 |
| **유출 결함수** | $D_{\text{post}}$ (출시 후 3~6개월)| **최소화 ($\downarrow$)** | 핫픽스 패치 및 기술 부채 해소 |

#### 한줄 요약
- 결함 밀도($\frac{\text{Defects}}{\text{KLOC}}$), 종합 DRE($\frac{D_{\text{pre}}}{D_{\text{total}}}$), 단계별 DRE, 2x2 매트릭스로 구성된다.

## Ⅳ. 흐름도

<details><summary>용어 설명</summary>

- **결함 데이터 수집 및 DRE 기반 공정 개선 5단계 프로세스**:
  1. 개발 및 테스트 단계에서 Jira 이슈 트래커를 통해 결함 발생 및 해결 내역 로깅
  2. SonarQube를 통해 모듈별 KLOC 및 IFPUG 기능점수(FP) 정밀 계측
  3. 상용 출시 후 90일(3개월) 동안 운영 환경에서 유입된 고객 CS/장애 티켓 정제
  4. 결함 밀도 및 DRE 공식 연산을 통해 모듈별/단계별 품질 지표 산출
  5. 결함 밀도 상위 10% 모듈 코드 리팩토링 및 DRE 80% 미달 공정 테스트 케이스 보강

</details>

```text
1. [출시 전 테스트 결함 수집 (Pre-release)]
    ├─ 단위/통합/시스템 테스트 3개월 수행
    ├─ 소스코드 규모 계측: 결제 모듈 (20 KLOC), 주문 모듈 (30 KLOC), 포털 모듈 (50 KLOC)
    └─ [테스트 단계 발견 및 제거 결함($D_{pre}$): 결제(180건), 주문(90건), 포털(30건) ➔ 총 300건]
            │
            ▼
2. [상용 릴리스 및 90일 유출 결함 집계 (Post-release)]
    ├─ 상용 오픈 후 3개월간 운영 모니터링 및 버그 리포트 추적
    ├─ 유출 결함($D_{post}$): 결제 모듈(20건), 주문 모듈(10건), 포털 모듈(70건) ➔ 총 100건
    └─ [총 발생 결함($D_{total} = D_{pre} + D_{post}$): 총 400건 확정]
            │
            ▼
3. [결함 밀도 및 DRE 지표 정밀 산출]
    ├─ 결제 모듈: 밀도 = $\frac{200}{20} = 10.0 \text{ def/KLOC}$, $\text{DRE} = \frac{180}{200} = 90.0\%$
    ├─ 주문 모듈: 밀도 = $\frac{100}{30} = 3.3 \text{ def/KLOC}$, $\text{DRE} = \frac{90}{100} = 90.0\%$
    └─ [포털 모듈: 밀도 = $\frac{100}{50} = 2.0 \text{ def/KLOC}$, $\text{DRE} = \frac{30}{100} = 30.0\%$ (심각한 차단 실패)]
            │
            ▼
4. [2x2 매트릭스 원인 분석 및 처방 도출]
    ├─ 결제 모듈: 높은 결함 밀도(10.0) ➔ 코드가 복잡하고 지저분함 ➔ [개발팀 코드 전면 리팩토링 처방]
    └─ [포털 모듈: 극히 낮은 DRE(30.0%) ➔ 테스트가 부실하여 버그를 다 놓침 ➔ [QA 테스트 시나리오 보강 처방]]
            │
            ▼
5. [개선 조치 적용 및 차기 릴리스 재검증]
    ├─ 결제 모듈 리팩토링 후 다음 릴리스 결함 밀도: $10.0 \rightarrow 1.5 \text{ def/KLOC}$로 85% 급감
    ├─ 포털 모듈 E2E 자동화 테스트 보강 후 차기 DRE: $30.0\% \rightarrow 95.0\%$로 대폭 상승
    └─ [전사 품질 거버넌스 성공적 정착 및 시스템 무장애 운영 달성]
```

**동작 원리**

1. **원인 귀속의 분리(Segregation of Accountability)**: 시스템에 버그가 많은 원인이 "개발자가 코드를 못 짰기 때문(결함 밀도 높음)"인지, "QA 팀이 테스트를 부실하게 했기 때문(DRE 낮음)"인지를 명확히 분리
2. **Shift-Left 조기 차단의 경제성**: 요구사항 단계의 DRE가 80% 이상이면 개발/운영 단계로 버그가 넘어가지 않아 전체 프로젝트 수정 비용 70% 절감
3. **유출 결함의 정제(Defect Scrubbing)**: 단순 고객의 사용 미숙이나 신규 추가 요구사항을 유출 결함($D_{\text{post}}$)에서 제외하고, 실제 개발 버그만 선별 집계하여 DRE 왜곡 방지
4. **심각도 가중치 결합 (Weighted Defect Density)**: Critical(가중치 10), Major(가중치 5), Minor(가중치 1)로 가중 결함 밀도를 산출하여 중대 결함 중심 관리
5. **폐쇄 루프 품질 피드백**: 유출 결함이 발생할 때마다 "왜 테스트 단계에서 못 잡았는가?"를 분석하여 회귀 테스트 스위트에 신규 테스트 케이스 즉시 추가

#### 한줄 요약
- 출시 전 결함 수집, 3개월 유출 결함 집계, 결함 밀도/DRE 계산, 2x2 매트릭스 원인 분리, 차기 릴리스 개선 검증 순으로 동작한다.

## Ⅴ. 종류 및 비교

<details><summary>용어 설명</summary>

- **결함 관리 핵심 2대 지표 비교**:
  - 결함 밀도 (Defect Density): 소프트웨어 내부의 본원적 품질 측정 (단위 규모당 결함 수).
  - 결함 제거율 (DRE): 테스트 및 검증 공정의 차단 역량 측정 (사전 제거율 백분율).

</details>

| 비교 항목 | 결함 밀도 (Defect Density) | 결함 제거율 (DRE: Defect Removal Efficiency) |
|:---|:---|:---|
| **수학적 공식** | $\text{Defect Density} = \frac{\text{Total Defects}}{\text{KLOC or FP}}$ | $\text{DRE} = \frac{D_{\text{pre}}}{D_{\text{pre}} + D_{\text{post}}} \times 100\%$ |
| **주요 평가 대상** | **소프트웨어 소스코드, 모듈, 아키텍처** | **QA 테스트 프로세스, 인스펙션 공정, 테스터**|
| **단위 및 척도** | **defects / KLOC 또는 defects / FP** | **백분율 (%)** |
| **목표 지향점** | **최소화 ($\downarrow$)** (낮을수록 코드가 깨끗함) | **최대화 ($\uparrow$)** (높을수록 버그를 잘 잡음)|
| **주요 지표 개선책**| **코드 리팩토링, 디자인 패턴 적용, TDD** | **E2E 테스트 자동화, 회귀 테스트 보강, 인스펙션**|
| **결과 해석 주의점**| 테스트가 부실하면 결함 밀도가 낮게 왜곡됨| 관찰 기간이 짧으면 DRE가 과대평가됨 |

#### 한줄 요약
- 결함 밀도는 코드 자체의 청결도(낮을수록 우수), DRE는 QA 공정의 버그 차단력(높을수록 우수)을 평가한다.

#### 한줄 요약
- 표준 SLOC로 단위를 일원화하고, 90일 관찰 기간을 의무화하며, 심각도 가중치를 부여해 왜곡을 방지한다.

## Ⅶ. 결론

- 소프트웨어의 본질적인 코드 품질과 QA 검증 공정의 효과성을 동시에 입체 진단하는 최고의 정량 품질 나침반인 **결함 밀도와 결함 제거율(DRE) 체계**는 개발팀과 테스트팀의 책임과 역할을 명확히 분리하고 시스템 완성도를 극대화하는 핵심 프레임워크이며, 실무 구현 시 **표준 SLOC 및 기능점수(FP) 기반의 결함 밀도 정규화**, **출시 후 90일 이상 관찰 기간을 반영한 DRE 산출**, **$2 \times 2$ 품질 매트릭스 기반의 리팩토링 및 테스트 보강**, **심각도 가중 결함 관리**를 완성하여 최고 수준의 소프트웨어 무결점 품질과 성숙한 QA 거버넌스를 완성

#### 한줄 요약
- 결함 밀도와 DRE의 2x2 매트릭스 분석을 통해 코드 품질과 테스트 공정 차단력을 완벽히 완성한다.
