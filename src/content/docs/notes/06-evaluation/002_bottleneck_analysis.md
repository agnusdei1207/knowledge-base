## Ⅰ. 개요

<details><summary>핵심 용어</summary>

- **병목(Bottleneck)**: 전체 처리량 제한 및 응답 지연을 유발하는 시스템 내 제약 자원 혹은 구간.
- **임계 경로(Critical Path)**: 최종 사용자 응답시간을 결정짓는 가장 긴 실행 시간의 제약 경로.
- **병목 분석(Bottleneck Analysis)**: 자원 및 경로별 정량 측정을 통해 성능 제약 원인을 식별하는 진단 프로세스.

</details>

- 정의: 처리량과 응답시간을 제약하는 근본 원인 자원 및 실행 경로를 추적하는 분석 프로세스.
- 필요성: 단순 평균 모니터링의 한계를 넘어, 순간적 대기열 급증 및 임계 경로 내 정밀 병목 식별.

#### 한줄 요약

- 트랜잭션이 거치는 다양한 처리 경로 중 가장 포화 상태인 자원이 전체 시스템의 성능 한계를 결정하므로, 이를 최우선으로 식별하고 제거하는 분석 체계 구축

## Ⅱ. 특징

<details><summary>핵심 용어</summary>

- **포화(Saturation, 큐 대기열 적체)**: 서버가 유입되는 요청을 즉시 처리하지 못하고 한계에 부딪혀 대기열(Queue)에 작업이 누적되어 지연이 기하급수적으로 늘어나는 징후.
- **상관 분석(Correlation Analysis)**: 어플리케이션 계층의 요청 지연 발생 시점과 인프라 계층의 자원 포화 시점을 동일한 시계열 그래프상에 겹쳐서 배치하여 인과 관계를 추론하는 분석 기법.
- **병목 이동 검증(Bottleneck Shift Verification)**: 가장 시급한 병목 구간을 튜닝하거나 증설한 직후, 다시 부하 테스트를 수행하여 다음으로 한계에 도달하는 후순위 자원과 전체 시스템 처리량 개선 폭을 확인하는 반복 점검 과정.

</details>

- 상관 분석: 사용자 지연 발생 시점과 인프라 포화 시점의 시계열 연동을 통한 인과관계 규명.
- 교차 진단: 자원 상태와 사용자 관점 서비스 품질의 양방향 진단을 통한 맹점 제거.
- 반복 검증: 병목 이동 확인을 통한 시스템 개선 전후 부하 곡선 객관적 비교.
- 한줄 요약: 상관관계 기반의 다각적 성능 제약 식별 체계 구축.

## Ⅲ. 구조 및 구성요소

<details><summary>핵심 용어</summary>

- **USE(Utilization, Saturation, Errors / 자원 사용 진단)**: 시스템 내부의 물리적/논리적 자원을 대상으로 이용률(Utilization), 대기열 포화도(Saturation), 에러 발생(Errors)을 점검하여 인프라 병목을 진단하는 방법론.
- **RED(Requests, Errors, Duration / 서비스 응답 진단)**: 마이크로서비스 및 API별로 초당 요청률(Requests), 실패율(Errors), 응답시간 지연(Duration)을 관측하여 소프트웨어 및 아키텍처 제약을 분석하는 방법론.

</details>

```text
병목 분석 체계
├─ 업무 부하•기준선
├─ 관측 증거
│  ├─ 서비스 RED 지표
│  ├─ 자원 USE 지표
│  └─ 추적•프로파일 증거
└─ 상관 분석기
```

가지의 의미: 통제된 기준 부하 환경 하에서 수집된 서비스 애플리케이션 로그, 인프라 자원 메트릭, 그리고 런타임 프로파일링 증거가 상관 분석기로 종합되는 정적 구조 매핑.

| 구성요소 | 책임 및 역할 |
|:---|:---|
| 업무 부하•기준선 | 반복 테스트가 가능하도록 고정된 요청률, 동시 접속자 수 및 정상 작동 기준 성능치(Baseline) 확립 |
| 서비스 RED 지표 | 클라이언트 관점에서의 처리량, 지연, 실패 등을 확인할 수 있는 **RED** 지표 정량 수집 |
| 자원 USE 지표 | 서버 CPU, 메모리, 디스크 I/O 등 개별 컴포넌트의 병목 여부를 판단하기 위한 **USE** 지표 산출 |
| 추적•프로파일 증거 | 분산 트레이싱을 통한 **임계 경로** 매핑, 함수별 실행시간 핫스폿(Hotspot) 및 병목 지점 코드 연결 |
| 상관 분석기 | 수집된 다각적 지표(RED, USE, 분산 추적)들을 결합하여 유력한 성능 저하 원인 후보군 도출 |

#### 한줄 요약

- 인프라 관점의 자원 지표(USE)와 애플리케이션 관점의 트랜잭션 추적 데이터(RED)를 융합 분석하여 성능을 제약하는 대기열 원인 규명

## Ⅳ. 흐름도

<details><summary>핵심 용어</summary>

- **재현 조건(Reproducible Conditions, 테스트 통제 변인)**: 병목 개선 작업 전후의 성능 변화를 객관적으로 평가할 수 있도록 트래픽 요청률, 테스트 데이터 셋, 서버 인프라 환경을 동일하게 고정시킨 시험 요건.
- **기준 부하 실행(Baseline Load Execution)**: 철저히 통제된 재현 조건 위에서 사전 정의된 부하를 가하여, 비교의 척도가 될 기준 성능 지표를 생성하는 기초 단계.
- **요청 추적•자원 지표 수집(Telemetry Collection)**: 부하가 발생하는 동안 분산 환경에서의 종단 지연시간과 서버 내 각 자원의 사용률, 포화 큐, 오류 발생 건수를 일제히 수집하는 관측 과정.
- **USE•RED 지표 상관 분석(Metric Correlation Analysis)**: 수집된 개별 지표들을 하나의 시계열 상에 병합하여 서비스 응답 지연의 원인이 인프라 포화에 기인한 것인지 상관성을 파악하는 분석 절차.
- **병목 후보 검증(Bottleneck Candidate Validation)**: 도출된 유력 병목 후보 중 단 하나의 요인만을 수정 적용한 후, 이전과 완전히 동일한 조건으로 부하를 재인가하여 실제 개선 여부를 증명하는 단계.

</details>

```text
분석가
   │ 재현 조건 확정
   ▼
부하 도구
   │ 1. 기준 부하 실행
   ▼
시험 대상·자원 수집기
   │ 2. 요청 추적·자원 지표 수집
   │ 3. USE·RED 지표 상관 분석
   ▼
검증 책임자
   │ 4. 병목 후보 검증
   ▼
개선 전후 처리량·지연 결과
```

### 동작 원리

1. **기준 부하 실행**: 통제된 **재현 조건**을 기반으로 부하 도구를 통해 목표치에 달하는 **기준 부하 실행**을 선행하여 비교 척도를 수립한다.
2. **요청 추적•자원 지표 수집**: 시스템이 임계치에 도달하는 순간 발생하는 징후 포착을 위해 **요청 추적•자원 지표 수집**을 가동해 종단 간 지연 및 USE 상태를 수집한다.
3. **USE•RED 지표 상관 분석**: 수집된 데이터의 시계열 매핑 및 **USE•RED 지표 상관 분석**을 거쳐, 표면적 지연 현상과 기저의 인프라 자원 포화 간의 논리적 고리를 잇는다.
4. **병목 후보 검증**: 가설로 도출된 개선 방안 중 **병목 후보 검증**을 위해 단일 변수 통제 방식으로 패치 후 부하를 다시 주입하여 전체 성능 개선폭을 측정한다.

#### 한줄 요약

- 지연이 극심한 시나리오에 대해 인프라 자원의 한계 임계치를 찾고, 부분 개선 후 반복적인 포화도 재검증을 통해 성능 향상 효과 확인

## Ⅴ. 종류 및 비교

<details><summary>핵심 용어</summary>

- **자원 병목(Resource Bottleneck, 하드웨어 임계 도달)**: 서버 내부의 핵심 인프라인 CPU, 물리 메모리 용량, 디스크 처리량, 네트워크 대역폭 등이 한계치에 달해 작업이 대기하고 전체 속도가 저하되는 상태.
- **DB(Database, 데이터베이스 시스템)**: 다수 동시 요청에 대한 데이터 정합성과 동시성 제어 락(Lock) 경합이 발생하기 쉬운 핵심 백엔드 저장소.
- **구간 병목(Segment Bottleneck, 소프트웨어 경로 지연)**: 특정 마이크로서비스 호출 지연, 서드파티 API 응답 지연, DB의 슬로우 쿼리 등이 전체 비즈니스 트랜잭션의 지연시간을 좌우하는 애플리케이션 레이어의 정체 현상.
- **자원•서비스 연계 분석(Resource-Service Co-analysis)**: 하드웨어 컴포넌트 관점의 USE 프레임워크와 소프트웨어 호출 중심의 RED 프레임워크를 유기적으로 병행하여 장애의 근본 원인을 입체적으로 역추적하는 고도화 진단 기법.

</details>

| 병목 분석 관점 | USE 방법론 (자원 중심) | RED 방법론 (서비스 중심) |
|:---|:---|:---|
| 주 적용 대상 | 서버 시스템 내부의 각종 **자원 병목** 및 포화 여부 진단 | MSA 간 API 호출 및 **DB** 쿼리 등 소프트웨어 **구간 병목** 진단 |
| 핵심 특징 및 지표 | 하드웨어 인프라별 **USE** (이용률, 포화대기열, 에러) 측정 | 서비스 비즈니스 흐름별 **RED** (요청률, 실패율, 응답시간) 수집 |
| 분석의 한계 | 트랜잭션이 거쳐간 소프트웨어 논리 경로와 비즈니스 원인 파악 누락 | 지연을 유발한 근원적인 하드웨어 자원 고갈 상태 및 결함 누락 |

> 요약: 성능 진단의 사각지대를 없애기 위해 USE와 RED를 융합하는 **자원•서비스 연계 분석** 수행 권장.

#### 한줄 요약

- 물리적 컴퓨팅 자원의 고갈을 짚어내는 방법과 사용자 트랜잭션의 소프트웨어 처리 상태를 진단하는 분석 기법을 융합하여 병목의 실체 규명

## Ⅵ. 실무 고려사항 및 대책

<details><summary>핵심 용어</summary>

- **부하곡선(Load Curve, 성능-부하 상관그래프)**: 동시 사용자 등 부하 크기 증가에 비례하여 시스템의 초당 처리량 상승폭, 응답시간 지연, 에러 발생 빈도 및 자원 이용률의 추세를 시각적으로 나란히 나타낸 분석 차트.
- **병목 이동(Bottleneck Shift, 제약점 전이 현상)**: 가장 치명적인 제약 자원을 튜닝하거나 증설하여 해결한 직후, 시스템 전체 처리량이 상승하면서 그동안 드러나지 않던 차순위 자원이나 논리 구간이 한계에 부딪혀 새로운 병목으로 부상하는 현상.

</details>

| 실무상 한계점 | 실질적 대책 및 해결 방안 | 기대 효과 |
|:---|:---|:---|
| 단순 평균 사용률만 주시하여 숨겨진 순간 대기열 포화 누락 | 평균 이용률과 더불어 큐 포화도 및 에러를 함께 점검하는 **USE** 지표 대시보드 구축 | 특정 자원의 순간 포화 및 임계점 조기 식별 |
| 평균 지연시간 위주 모니터링으로 간헐적 악성 호출 경로 은폐 | 꼬리 지연시간 및 오류율 중심의 **RED** 지표를 모니터링 기준에 포함 | 비정상적이거나 극단적으로 느린 애플리케이션 트랜잭션 경로 적발 |
| 하나의 자원 튜닝 후 연쇄적으로 발생하는 **병목 이동** 미인지 | 개선 패치 적용 후 반드시 동일 통제 환경에서 **부하곡선** 변화 재도출 | 차순위 신규 병목 조기 식별 및 시스템의 지속적이고 안정적인 스케일업 달성 |

#### 한줄 요약

- 시스템 자원의 단순 사용 빈도를 넘어, 병목의 실질적 원인이 되는 큐 적체(대기열)와 에러 급증 구간을 선제적으로 찾아내는 점검 체계 확보

## Ⅶ. 결론

<details><summary>핵심 용어</summary>

- **가설 검증(Hypothesis Testing)**: 관측된 다양한 성능 지표와 분석 결과를 바탕으로 가장 유력한 병목 요인을 가설로 수립하고, 다른 변수들을 통제한 채 단일 요인만을 변경해 부하 테스트를 재수행함으로써 개선 전후의 처리량 변화를 과학적으로 비교 입증하는 절차.
- **개선 우선순위(Prioritization of Improvements)**: 다수의 병목 후보 중 가장 비용 효율적이고 즉각적인 전체 시스템 처리량 상향을 가져올 수 있는, 즉 임계 경로 내에서 포화 증거가 뚜렷한 대기열 유발 자원부터 집중적으로 튜닝 및 증설하는 전략적 결정.

</details>

- 관측 기반의 가설 검증을 통한 성능 상한 요소 입증 및 개선 우선순위에 따른 임계 경로 내 포화 자원 해소 전략 적용.

#### 한줄 요약

- 정밀 분석 기반의 병목 원인 규명 및 가용 처리 용량 극대화 체계 적용.
