## Ⅰ. 개요

<details><summary>용어 설명</summary>

- **오류 예산(Error Budget / Google SRE)**: 100% 무결점 시스템을 목표로 하지 않고, 목표 가용성(SLO)을 만족하는 한도 내에서 시스템이 안전하게 감내할 수 있는 불량 이벤트(장애 시간, 5xx 에러 건수)의 총 허용량($\text{Error Budget} = 100\% - \text{SLO}$)을 수치화하여, 개발팀의 신규 기능 배포 속도와 운영팀의 신뢰성 안정화 작업을 객관적으로 통제하는 SRE 핵심 의사결정 거버넌스 도구.
- **개발-운영 간의 감정적 대립 및 무분별한 배포 결함(Dev-Ops Polarization Defect)**: 객관적인 실패 허용 한도가 없어 개발팀은 결함이 존재하는 코드를 무리하게 상용 배포하여 장애를 유발하고, 운영팀은 장애 방지를 명목으로 수개월간 모든 배포를 결재 반려하여 비즈니스 혁신이 마비되는 조직적 결함.

</details>

- 정의/개념: 비즈니스 혁신 속도와 시스템 안정성의 황금 균형을 달성하기 위해 **SLO 기반 총 오류 예산 산출 $\rightarrow$ 실측 SLI 데이터 기반 잔여 예산 추적 $\rightarrow$ 번레이트(Burn Rate) 다중 윈도우 감시 $\rightarrow$ 예산 소진 시 배포 관문(Release Gate) 자동 차단 $\rightarrow$ 신뢰성 개선 스프린트 강제 전환** 을 집행하는 **정량적 릴리스 통제 거버넌스**
- 배경/필요성: 객관적 실패 허용 한도가 없으면 **배포 민첩성·안정성**의 우선순위를 조직 간 힘겨루기로 정하게 되어 무리한 배포와 전면 동결이 번갈아 반복되므로, 목표 가용성을 뺀 나머지 실패량을 예산으로 환산한 통제 계층을 릴리스 관문에 두어 합의를 잔여 예산 소진 여부로 대체할 필요

#### 한줄 요약
- 오류 예산은 $1 - \text{SLO}$로 정의된 실패 허용량과 번레이트를 통해 기능 배포와 시스템 안정성을 통제한다.

## Ⅱ. 특징

<details><summary>용어 설명</summary>

- **오류 예산 3대 핵심 거버넌스 파라미터**:
  - **허용 에러 쿼터 (Error Budget Cap)**: 30일 동안 허용되는 최대 불량 요청 건수 또는 허용 중단 분 (예: 99.9% SLO 시 43.2분).
  - **소진 속도 배수 (Burn Rate)**: 오류 예산이 정상 속도 대비 몇 배 빠르게 소모되고 있는지를 나타내는 가속도 지표 ($\text{Burn Rate} = \frac{\text{실측 에러율}}{\text{허용 에러율}}$).
  - **배포 관문 자동화 (Release Gate Integration)**: 잔여 예산이 0이 되면 CI/CD 배포 파이프라인이 신규 기능 배포를 자동 차단하는 정책.

</details>

- 잔여 예산만큼 위험을 허용하는 **혁신 쿼터**
- 단기·장기 창을 교차하는 **MWMBR 경보**
- 예산 고갈 시 배포를 막는 **오류 예산 정책**

#### 한줄 요약
- 실패의 자산화(혁신 허용), 번레이트 기반 다중 창 경보, 오류 예산 정책 기반 배포 관문 자동화를 제공한다.

## Ⅲ. 구조 및 구성요소

<details><summary>용어 설명</summary>

- **오류 예산 5대 핵심 컴포넌트**:
  1. **총 오류 예산**: SLO에서 산출한 전체 실패 허용량.
  2. **번레이트**: 단위 시간당 예산 소진 속도.
  3. **다중 윈도우 필터**: 단기·장기 창의 임계치 교차 검증.
  4. **배포 관문**: 잔여 예산에 따른 CI/CD 통제.
  5. **신뢰성 스프린트**: 고갈 시 안정화 작업 전환.

</details>

```text
오류 예산 통제 체계
├─ 총 오류 예산
├─ 번레이트
├─ 다중 윈도우 필터
├─ 배포 관문
└─ 신뢰성 스프린트
```

선의 의미: 30일 총 예산에서 발생 에러를 차감하여 잔여량을 계산하고, 번레이트 속도에 따라 즉시 롤백 및 배포 동결을 집행하는 구조

| 컴포넌트 | 핵심 기능 및 수학적 공식 | 동작 기준 | 실무 역할 |
|:---|:---|:---|:---|
| **총 오류 예산** | $\text{Budget} = \text{Total Requests} \times (1 - \text{SLO})$ | 30일 슬라이딩 윈도우 | 전체 실패 허용량 정의 |
| **소진율 (Burn Rate)**| $\text{Burn Rate} = \frac{\text{단위시간 에러수}}{\text{총 예산} / (\text{30일} \times 24\text{시간})}$| $1.0\times$ = 30일 만에 100% 소진 | 장애 소모 속도 측정 |
| **다중 윈도우 필터** | 장기 창(Long-window) AND 단기 창(Short-window) 충족 | 두 윈도우 모두 임계치 초과 시 | 일시적 스파이크 오경보 차단 |
| **배포 관문 (Gate)**| 잔여 예산 비율($\text{Remaining} > 0\%$) 검증 | $\text{Remaining} \le 0\%$ 시 배포 잠금 | CI/CD 파이프라인 제어 |
| **신뢰성 스프린트** | 신규 기능 개발 100% 중단 및 장애 결함 리팩토링 | 예산 고갈 후 복구 시까지 | 기술 부채 집중 해소 |

#### 한줄 요약
- 다중 윈도우 필터가 번레이트와 배포 관문 사이에 끼어들어 단기 스파이크만으로 배포를 잠그는 오경보를 걸러 내므로, 예산을 실제로 소진하지 않은 상황에서 개발 인력이 신뢰성 스프린트로 묶여 노는 낭비를 막는다.

## Ⅳ. 흐름도

<details><summary>용어 설명</summary>

- **오류 예산 기반 릴리스 통제 5단계 엔지니어링 프로세스**:
  1. 30일 이동 창 기반으로 총 오류 예산 10,000건(SLO 99.9%) 확정
  2. 개발팀이 신규 결제 모듈을 프로덕션에 배포
  3. 실시간 트래픽 처리 중 500 에러 발생으로 오류 예산 실시간 차감
  4. 1시간 만에 2,000건 에러 발생 $\rightarrow$ $14.4\times$ Burn Rate 알람 발송 및 자동 롤백
  5. 잔여 예산 0% 도달 시 CI/CD 배포 파이프라인 자동 잠금 및 안정화 스프린트 착수

</details>

```text
1. [오류 예산 초기화 및 배포 승인]
    ├─ 30일 총 요청 1,000만 건, 목표 SLO 99.9% ➔ 오류 예산 = 10,000건 (100% 잔여)
    └─ [CI/CD 파이프라인: 배포 관문(Release Gate) 'Green' 상태 ➔ 신규 결제 기능 배포 승인]
            │
            ▼
2. [결함 발생 및 번레이트 급증]
    ├─ 배포 10분 후 DB 커넥션 누수 버그로 HTTP 500 에러 초당 10건씩 급증
    ├─ 1시간 동안 총 2,500건 에러 발생 ➔ 1시간 만에 월간 예산의 25% 소진
    └─ [번레이트 연산: $\text{Burn Rate} = \frac{2,500 / 1\text{시간}}{10,000 / 720\text{시간}} = 180\times$ (극단적 폭증)]
            │
            ▼
3. [다중 창 경보 발령 및 자동 롤백]
    ├─ 1시간 창($14.4\times$ 초과) AND 5분 창($14.4\times$ 초과) 동시 만족 확인
    ├─ PagerDuty를 통해 당직 SRE 엔지니어에게 최우선(P1) 알람 호출
    └─ [ArgoCD 파이프라인에서 직전 안정 버전으로 1분 내 자동 롤백(Auto-rollback) 집행]
            │
            ▼
4. [배포 관문 자동 잠금 (Release Gate Closed)]
    ├─ 롤백 전까지 누적 에러 10,200건 기록 ➔ 잔여 오류 예산: $-200\text{건}$ (음수 도달, Red 상태)
    └─ [GitHub Actions 배포 파이프라인 잠금: 모든 신규 비즈니스 PR 머지 및 상용 배포 차단]
            │
            ▼
5. [신뢰성 개선 스프린트 및 예산 회복]
    ├─ 개발팀과 SRE팀이 전원 투입되어 DB 커넥션 풀 자동 회수 및 타임아웃 방어 코드 구현
    ├─ 부하 테스트 검증 후 핫픽스 단독 배포 승인
    └─ [30일 슬라이딩 윈도우 진행으로 과거 장애 건수가 창 밖으로 밀려나며 예산 회복 ➔ 정상 배포 재개]
```

**동작 원리**

1. **오류 예산 초기화 및 배포 승인**: 총량과 관문 상태 설정
2. **결함 발생 및 번레이트 급증**: 실시간 소진 속도 산출
3. **다중 창 경보 발령 및 자동 롤백**: 임계치 교차 판정
4. **배포 관문 자동 잠금**: 예산 고갈 시 신규 배포 차단
5. **신뢰성 개선 스프린트 및 예산 회복**: 안정화 후 재개

#### 한줄 요약
- 긴 창 하나만 보면 폭증을 예산이 음수로 떨어진 뒤에야 알아채고 짧은 창 하나만 보면 순간 잡음에도 롤백 비용을 치르므로, 갈래는 1시간과 5분 창이 동시에 임계치를 넘는 지점에서 갈린다.

## Ⅴ. 종류 및 비교

<details><summary>용어 설명</summary>

- **오류 예산 상태 3단계 관리 체계**:
  - Green (여유 상태): 잔여 예산 > 30% $\rightarrow$ 신규 기능 배포 가속, 실험 장려.
  - Yellow (주의 상태): 0% < 잔여 예산 $\le$ 30% $\rightarrow$ 배포 속도 제어, 카나리 정밀 검증.
  - Red (고갈 상태): 잔여 예산 $\le$ 0% $\rightarrow$ 신규 기능 배포 전면 차단, 신뢰성 엔지니어링 집중.

</details>

| 예산 상태 | Green (여유 상태) | Yellow (주의 상태) | Red (고갈 상태) |
|:---|:---|:---|:---|
| **잔여 예산 비율** | **$30\% < \text{Remaining} \le 100\%$**| **$0\% < \text{Remaining} \le 30\%$** | **$\text{Remaining} \le 0\%$ (예산 초과)**|
| **신규 기능 배포** | **정상 배포 및 신속한 릴리스 허용**| **제한적 배포 (추가 승인 필요)** | **신규 기능 배포 전면 동결 (Freeze)**|
| **배포 방식** | 일반 롤링 업데이트, A/B 테스트 | **소규모 카나리 배포 (1% $\rightarrow$ 5%)**| **보안/장애 긴급 핫픽스만 예외 허용**|
| **엔지니어링 리소스**| 신규 비즈니스 기능 개발 80% | 기능 개발 50% + 버그 수정 50% | **안정화 및 기술 부채 해소 100%** |
| **조직 목표** | 비즈니스 시장 출시 속도 극대화 | 신뢰성 경고 및 잠재 결함 격리 | 시스템 고가용성 복원 및 SLA 방어 |

#### 한줄 요약
- Green은 기능 개발 가속, Yellow는 배포 제어 및 카나리 강화, Red는 배포 동결 및 안정화 집중이다.

## Ⅵ. 실무 고려사항 및 대책

<details><summary>용어 설명</summary>

- **오류 예산 실무 운영 시 3대 위험 요소와 엔지니어링 대책**:

</details>

| 문제 | 대책 | 효과 |
|:---|:---|:---|
| 단순 1회성 네트워크 스파이크(1초간 500 에러 발생)로 인해 **밤마다 당직 SRE 엔지니어에게 긴급 호출(Pager)이 발송되어 알람 피로로 사기 저하** | **Google SRE 표준인 다중 윈도우 다중 번레이트(1시간 창 AND 5분 창 동시 충족) 경보 필터링 강제** | 1회성 노이즈 오경보 99% 차단 및 핵심 장애 조기 탐지 |
| 오류 예산이 0%로 고갈되었음에도 개발 부서장이 **사업 일정을 이유로 배포 동결을 무시하고 배포를 강행하여 초대형 서비스 중단 사고 발생** | **오류 예산 고갈 시 CI/CD 배포 파이프라인(GitHub Actions) 머지 권한을 시스템적으로 자동 차단하고 CTO 단독 승인제로 통제** | 무리한 상용 배포 원천 차단 및 시스템 안정성 사수 |
| 인위적인 점검이나 레거시 시스템의 만성 에러로 인해 **오류 예산이 연중 상시 0%로 고갈되어 일 년 내내 기능 배포가 마비되는 경직성 발생** | **레거시 시스템과 신규 시스템의 SLO를 분리하고, 통제 가능한 API 엔드포인트별로 오류 예산을 독립 분할 할당** | 시스템 경직성 해소 및 모듈별 유연한 배포 보장 |

#### 한줄 요약
- 다중 윈도우로 오경보를 막고, CI/CD 자동 잠금으로 강제성을 확보하며, 모듈별 예산 분할로 유연성을 유지한다.

## Ⅶ. 결론

- 잔여 예산이면 **배포**, 고갈이면 **관문 잠금·안정화** 실행

#### 한줄 요약
- 예산이 남았다고 전부 쓰는 것이 최적은 아니며, 소진 속도를 함께 보아야 한 번의 대형 장애와 잦은 소규모 장애를 구분해 다르게 대응할 수 있다.
