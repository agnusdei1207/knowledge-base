## Ⅰ. 개요

<details><summary>핵심 용어</summary>

- **클라우드 서비스 감리(Cloud Service Audit)**: 남의 집(AWS/Azure 등) 컴퓨터를 빌려 쓰는 클라우드 환경에서, 인프라(IaaS), 플랫폼(PaaS), 앱(SaaS) 등 서비스 모델별로 제공자와 고객이 나눠 가진 공유 책임 경계선을 칼같이 가르고, 고객이 설정한 방화벽이나 백업 등 진짜 자기 몫의 보안/통제 의무를 똑바로 이행하고 있는지 증거로 털어보는 제3자 감사 기법이다.
- **공유 책임 모델(Shared Responsibility Model)**: 클라우드 센터 건물이 털리면 AWS 책임(제공자), 하지만 그 안에 올려둔 리눅스 서버 루트(Root) 비밀번호가 털리면 고객 책임(이용자)인 것처럼, 계층별로 누가 해킹 및 장애 복구 독박을 쓸지 명확하게 선을 긋는 클라우드 세계 절대 룰북이다.
- **책임 공백(Responsibility Gap)**: 제공자는 "이용자가 알아서 설정하겠지"하고 버려두고, 이용자는 "클라우드가 알아서 막아주겠지"라며 손을 놓아, 결과적으로 아무도 백업이나 로그 감시를 하지 않아 해커가 유유히 춤을 추고 데이터가 박살 나는 최악의 보안 블라인드 사각지대이다.

</details>

- 정의/개념: 서비스 모델별 공유 책임과 증거를 검증하는 **클라우드 감리**
- 배경/필요성: 제공자 인증만으로는 **이용자 구성·책임 공백 확인 불가**

#### 한줄 요약
- 제공자 인증과 별개로 **이용자 통제 증거** 검증

## Ⅱ. 특징

<details><summary>핵심 용어</summary>

- **코드형 인프라(Infrastructure as Code, IaC)**: 마우스로 콘솔에 들어가 서버를 찍어내는 대신, `Terraform`이나 `YAML` 스크립트 코드 몇 줄로 수백 대의 서버와 방화벽(VPC)을 한 방에 찍어내고, 기획서(코드)와 똑같이 인프라가 배포되었는지 깃허브 이력으로 추적 감시할 수 있는 마법 같은 인프라 관리 기술이다.
- **제어 평면•데이터 평면(Control Plane & Data Plane)**: 제어 평면은 서버를 껐다 켜고 방화벽을 뚫어주는 클라우드 '조종실(API/콘솔)' 영역이고, 데이터 평면은 유저들의 실제 결제 트래픽이나 업무용 엑셀 파일이 굴러가는 '현장 화물칸' 영역으로, 두 평면의 접근 통제를 완벽히 분리해 감시하는 것이 핵심이다.
- **재위탁자(Sub-contractor/Sub-processor)**: 우리가 계약한 A 클라우드 회사가 몰래 뒤에서 B라는 싸구려 외부 백업 솔루션 업체에 우리 데이터를 통째로 넘겨서(하도급) 관리하게 만드는, 최악의 데이터 유출 지뢰밭 리스크 제공자이다.
- **API 상태 대조(API State Reconciliation)**: 서류에는 "DB 접근 막아놨습니다"라고 적어 놨으나 믿을 수 없으니, 감리원이 AWS/GCP의 설정 조회 API를 터미널로 긁어서 실제 런타임 클라우드 서버의 진짜 보안 설정 값과 승인된 서류 값이 100% 일치하는지 때려 맞추는 무자비한 팩트 체크이다.
- **서비스형 인프라(IaaS), 플랫폼(PaaS), 소프트웨어(SaaS)**: 
  - **IaaS(Infrastructure as a Service)**: 제공자는 쇳덩이(서버/네트워크)만 대주고, 이용자가 OS(리눅스)부터 그 위 보안까지 전부 독박 쓰는 모델이다.
  - **PaaS(Platform as a Service)**: 제공자가 OS와 미들웨어(자바 등)까지 깔아주고, 이용자는 앱(소스코드)과 데이터만 신경 쓰면 되는 꿀 모델이다.
  - **SaaS(Software as a Service)**: 제공자가 다 만들어 놓은 소프트웨어(O365 등)를, 이용자는 계정(ID/PW)과 데이터만 밀어 넣고 편하게 쓰는 구독 모델이다.

</details>

- IaaS·PaaS·SaaS별 **공유 책임** 확정
- **API 상태 대조·IaC**로 승인 구성 검증
- **재위탁자**까지 데이터·통제 책임 추적

#### 한줄 요약
- 모델과 무관하게 **계정·데이터는 이용자 책임**

## Ⅲ. 구조 및 구성요소

<details><summary>핵심 용어</summary>

- **신원 및 접근 관리(Identity and Access Management, IAM)**: 클라우드 왕국에 들어오려는 놈이 진짜 퇴사 안 한 김 대리인지 신분을 확인하고, 김 대리에게는 서버 삭제 버튼(권한)은 숨기고 조회 버튼만 딱 열어주는 무적의 클라우드 철통 문지기 시스템이다.
- **테넌트 격리(Tenant Isolation)**: 나(테넌트 A)와 경쟁사(테넌트 B)가 같은 깡통 서버를 나눠 쓰고 있어도, 논리적인 담벼락(VPC, 암호화 키 등)을 겹겹이 쳐서 경쟁사가 내 DB 데이터를 훔쳐보거나 내 CPU 자원을 갉아먹지 못하도록 완벽히 찢어놓는 클라우드 다중 임대 방어막이다.
- **관측 가능성(Observability)**: 서버 수백 대가 클라우드 안에서 살았다 죽었다 하는 마이크로서비스 지옥 속에서, 에러가 터졌을 때 로그(Logs), 성능 지표(Metrics), 분산 추적(Traces)이라는 세 가닥 실마리를 던져 "몇 번째 놈이 죽어서 전체가 멈췄는지" 한눈에 꿰뚫어 보게 만드는 감시 능력이다.
- **서비스 수준 협약(Service Level Agreement, SLA)**: "1년 중 1시간이라도 서버 멈추면 요금 50% 깎아주겠다"처럼 클라우드 제공자가 가용성, 복구 목표 시간(RTO), 고객 지원 품질을 보장하고 삑사리 났을 때 토해낼 배상금을 법적으로 꽝꽝 못 박은 피의 계약서이다.

</details>

```text
                           [책임 경계]
                    /          |          |          \
             [구성 통제] [데이터 통제] [운영 복원력] [계약•출구]
```

선의 의미: 책임 경계 아래 구성·데이터·복원력·출구 통제

| 구성요소 | 책임 및 평가 초점 |
|:---|:---|
| 책임 경계 | 서비스 모델별 제공자·이용자 범위 확정 |
| 구성 통제 | **제어·데이터 평면·IAM** 설정 대조 |
| 데이터 통제 | **테넌트 격리·암호화·백업·삭제** |
| 운영 복원력 | 관측 가능성과 존 장애 복구 훈련 |
| 계약•출구 | **SLA·이식성·잔여 데이터 삭제** |

#### 한줄 요약
- 책임별 **구성·데이터·복구·출구 증거** 검증

## Ⅳ. 흐름도

<details><summary>핵심 용어</summary>

- **승인 구성-실제 상태 대조(Approved vs. Actual State Reconciliation)**: 테라폼(IaC) 스크립트 도면이나 결재 서류에는 "22번 포트 막음"이라 적혀 있는데, 감리원이 런타임 서버를 때려보니 "22번 뻥 뚫려 있음"이 뜨는 등 서류와 진짜 클라우드 현실의 치명적 갭(Gap)을 멱살 잡고 잡아내는 수사 기법이다.
- **출구 전략(Exit Strategy)**: 클라우드 회사(AWS)가 파산하거나 갑자기 요금을 올려서 방을 빼야 할 때, 인질 잡힌 내 수백 테라의 데이터를 다른 클라우드로 안전하게 짐 싸서 이사하고(마이그레이션), 기존 하드디스크에 남은 내 데이터 찌꺼기는 완전 복구 불가로 파쇄(소각)해 달라고 요구하는 치밀한 이혼 합의서이다.
- **증거 소유자(Evidence Owner)**: 클라우드 로그나 설정 증명서를 감리원에게 갖다 바쳐야 할 독박 책임자, 즉 어떤 건 구글(제공자)에게 내놓으라 해야 하고 어떤 건 우리 회사 보안팀(이용자)에게 내놓으라 해야 하는 타깃 주체이다.
- **책임•증거 소유자 확정**: 1단계로 계층 룰에 따라 "이건 네가 내고, 저건 쟤가 내라"며 멱살 잡을 타깃을 배분한다.
- **제공자 통제 검증**: 2단계로 구글/AWS 같은 공룡들에게 "너네 SOC2 인증서, 장애 이력 보고서, 하도급(재위탁) 현황 다 까봐라"며 거시적 장부를 털어본다.
- **이용자 통제 검증**: 3단계로 우리 고객 보안팀 조져서 "네가 세팅한 방화벽, 백업 플랜, 이사 갈 때 짐 쌀 계획(출구) 다 가져와"라며 현미경 디테일(구성 편차)을 털어버린다.
- **책임 공백•조치 판정**: 4단계로 아무도 관리 안 한 빵꾸(미배정 통제)를 색출해 데드라인(기한) 박고 언제까지 땜빵하라고 사형 선고를 내린다.

</details>

```text
              [이용자]
                  │ 클라우드 감리 요청
                  ▼
              [감리인]
                  │ 1. 책임•증거 소유자 확정
                  │   제공자 증거 요청
                  ▼
              [제공자]
                  │ 인증•장애•재위탁 증거
                  ▼
              [감리인]
                  │ 2. 제공자 통제 검증
                  │   이용자 통제 시험 요청
                  ▼
              [이용자]
                  │ 구성•복구•출구 시험 결과
                  ▼
              [감리인]
                  │ 3. 이용자 통제 검증
                  │ 4. 책임 공백•조치 판정
                  │
                  ▼
              [이용자]
```

### 동작 원리

1. **책임•증거 소유자 확정**: 모델별 통제·증거 주체 지정
2. **제공자 통제 검증**: 인증·장애·재위탁·SLA 증거 확인
3. **이용자 통제 검증**: 실제 구성·복구·출구 시험
4. **책임 공백•조치 판정**: 미배정 통제의 책임·기한 지정

#### 한줄 요약
- 제공자·이용자 증거 대조로 **책임 공백** 제거

## Ⅴ. 종류 및 비교

<details><summary>핵심 용어</summary>

- **IaaS 적용 (Infrastructure as a Service Application)**: AWS EC2처럼 깡통 컴퓨터만 빌려 쓰기 때문에, 해커가 뚫고 들어오면 "네가 방화벽(보안그룹) 포트 열어두고 리눅스(OS) 패치 안 한 탓"이라며 99% 이용자가 보안 독박을 써야 하는 극한 직업 환경이다.
- **PaaS 적용 (Platform as a Service Application)**: 구글 앱 엔진(App Engine)처럼 OS 패치나 백신은 클라우드사가 다 해주지만, 내가 짠 발로 만든 소스코드(앱)의 버그나 데이터 탈취 틈새만큼은 철저히 내가 책임져야 하는 반반 무 많이 환경이다.
- **SaaS 적용 (Software as a Service Application)**: 줌(Zoom), 마이크로소프트 365(O365)처럼 완성된 솔루션을 돈 내고 쓰기만 하면 돼 운영 독박은 없지만, 회사 계정 비번을 '1234'로 해두거나 중요 문서를 전체 공개로 퍼나르는 짓(데이터/계정 유출)은 여전히 내 책임인 꿀이지만 위험한 환경이다.
- **운영체제 (Operating System, OS)**: 리눅스, 윈도우처럼 기계 쇳덩이를 돌리는 뇌로, 이 OS 업그레이드와 백신 관리를 고객이 하느냐(IaaS) 클라우드사가 알아서 해주느냐(PaaS/SaaS)가 책임 분기점을 가르는 절대 기준선이다.

</details>

| 클라우드 서비스 계급 | 깡통 인프라 (IaaS) | 개발 플랫폼 (PaaS) | 구독형 완제품 (SaaS) |
|:---|:---|:---|:---|
| 감리 적용 기준 타깃 | OS·네트워크·앱·데이터 | 앱·데이터 | 계정·데이터·접근권한 |
| 가장 뼈 때리는 특징 | 이용자 **OS·보안그룹** 책임 | 제공자 플랫폼·이용자 앱 책임 | 제공자 앱·이용자 계정 책임 |
| 끔찍한 한계 및 부담 | 구성·패치 부담 | 종속성·키 관리 | 격리·통제 가시성 한계 |

#### 한줄 요약
- 상위 모델일수록 제공자 책임 증가, **계정·데이터는 공통**

## Ⅵ. 실무 고려사항 및 대책

<details><summary>핵심 용어</summary>

- **권한 과다(Over-provisioned Privileges)**: 귀찮다고 김 대리 계정에 최고 관리자(AdministratorAccess) 권한을 줘 버렸다가, 김 대리 노트북이 악성코드에 걸리는 순간 회사 클라우드 센터 서버가 통째로 삭제되거나 랜섬웨어에 구워지는 재앙적 계정 남용 상태이다.
- **보안그룹(Security Group)**: 클라우드 인프라(EC2 등)에 딱 달라붙어 외부 놈들의 접속을 튕겨내는 가상 방화벽으로, 포트 22번(SSH)을 '0.0.0.0/0'(전 세계 오픈)으로 뚫어 놓는 순간 1분 만에 중국 해커들 놀이터가 되는 1순위 감리 타깃이다.
- **제공자 인증 의존(Over-reliance on Provider Certification)**: 감리원이 현장 가서 "아마존 ISO 인증서 있네요. 통과!"라고 도장 찍고 퇴근하는 바보 같은 짓으로, 아마존은 튼튼해도 내 방화벽 세팅은 개판일 수 있다는 사실을 망각한 치명적 무능력이다.
- **구성 편차(Configuration Drift)**: 윗선에 보고된 삐까뻔쩍한 서버 구성도(IaC)는 철벽인데, 감리원이 런타임 클라우드 API를 찍어보니 어제 밤에 개발자가 몰래 테스트한다고 보안 포트를 열어둔 채 퇴근하여 서류와 현실의 괴리가 폭발한 아수라장 상태이다.
- **ISO/IEC 27017 & 27018**: 27017은 클라우드 환경에서 클라우드사와 고객이 어떻게 보안 통제를 나눌지 적어둔 정보보호 바이블이고, 27018은 퍼블릭 클라우드에 올라간 주민번호, 카드번호 등 개인정보(PII)가 털리지 않게 막는 프라이버시 바이블이다.

</details>

## Ⅶ. 결론

<details><summary>핵심 용어</summary>

- **잔여 데이터 검증(Residual Data Verification)**: 클라우드 계약을 해지하고 방을 뺄 때, 내 메인 서버 데이터만 지우는 게 아니라, 클라우드사가 여기저기 흩뿌려놓은 스냅샷(백업), 복제본(DR), 심지어 하청(재위탁) 업체에 넘어간 찌꺼기 데이터까지 복구 불가(Wiping/Shredding)하게 파쇄했는지 증명서를 징구하는 잔인한 확인 사살 절차이다.
- **서비스 승인 결정(Service Approval Decision)**: 서류 쪼가리(인증서)만 덜렁 보는 게 아니라, 서비스 모델(IaaS/PaaS/SaaS)별 피 튀기는 책임자와 증거를 교차 확인하고, 실제 살아있는 인프라 구성 스캔, 불났을 때 튀는 복구 훈련, 계약 파기 시 짐 싸는 시험(출구)을 모조리 통과한 녀석에게만 운영 허락 도장을 쾅 찍어주는 최고 권위의 판단이다.

</details>
