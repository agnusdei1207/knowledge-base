## Ⅰ. 개요

<details><summary>용어 설명</summary>

- **클라우드 서비스 감리(Cloud Service Audit / ISO/IEC 27017 & CSA CCM)**: 공공 및 민간 기업이 도입하는 클라우드 환경(IaaS, PaaS, SaaS)에 대해, 클라우드 서비스 제공자(CSP: AWS, Azure, 네이버클라우드 등)와 서비스 이용자(고객사/SI사) 간의 **공동 책임 모델(Shared Responsibility Model)** 을 기준으로 책임 경계를 명확히 분계하고, CSP의 물리적 보안 인증(CSAP, SOC 2) 검증과 더불어 이용자 책임 영역인 IAM 권한 설정, VPC 네트워크 격리, 데이터 암호화(KMS), IaC 형상 일치성, 그리고 계약 종료 시의 출구 전략(Exit Strategy)을 독립 제3자가 종합 점검하는 특수 감리 체계.
- **CSP 인증 맹신에 따른 설정 오류 및 데이터 종속 결함(CSP Blind Faith & Misconfiguration Defect)**: CSP가 글로벌 보안 인증을 획득했다는 사실만 믿고 고객 책임 영역의 보안 설정을 방치하여, 관리자 실수로 S3 스토리지 버킷을 인터넷 전체에 퍼블릭 개방(Public Read)하거나 IAM 계정에 `AdministratorAccess` 와일드카드 권한을 부여하여 대규모 개인정보 유출 사고를 초래하거나, 사업 종료 시 데이터를 회수하지 못해 CSP에 종속(Lock-in)되는 구조적 결함.

</details>

- 정의/개념: 클라우드 도입의 민첩성을 확보하면서 보안 및 가용성 위험을 원천 차단하기 위해 **공동 책임 모델(IaaS/PaaS/SaaS) 경계 확정 $\rightarrow$ CSP 영역 공인 감사보고서(SOC 2/CSAP) 간접 검증 $\rightarrow$ CSPM 도구 기반 이용자 영역(IAM/VPC/KMS) 설정 실사 $\rightarrow$ IaC(Terraform) 코드와 실제 런타임 API 상태 대조 $\rightarrow$ Multi-AZ 장애 복원력 및 암호학적 데이터 영구 삭제(Exit) 검증** 을 집행하는 **클라우드 전문 감리 거버넌스 체계**
- 배경/필요성: 가상화 및 멀티테넌시(Multi-Tenancy) 환경의 확산으로 온프레미스형 물리 실사가 불가능해짐에 따라, API 기반의 지속적 감사와 클라우드 설정 오류(Misconfiguration) 전수 점검 필수화

#### 한줄 요약
- 클라우드 서비스 감리는 공동 책임 모델을 기반으로 CSP 인증 검증과 이용자 영역의 IAM/설정/암호화/출구 전략을 실사한다.

## Ⅱ. 특징

<details><summary>용어 설명</summary>

- **클라우드 감리 4대 핵심 검증 기제**:
  - **공동 책임 분계선 실사 (Shared Responsibility Boundary)**: IaaS, PaaS, SaaS별로 OS 패치, 백업, 네트워크 방화벽의 책임 소재를 계약서에 명문화.
  - **IaC 형상 일치성 (Infrastructure as Code Consistency)**: 승인된 Terraform/CloudFormation 스크립트와 실제 클라우드 인프라 런타임 간의 설정 드리프트(Drift) 제로화 검증.
  - **KMS 고객 관리형 암호화 (Customer Managed Keys, CMK)**: CSP조차 데이터를 열람할 수 없도록 고객이 직접 암호화 키 수명주기를 통제하는 봉투 암호화(Envelope Encryption) 실사.
  - **출구 전략 및 데이터 영구 파기 (Exit Strategy & Crypto-Shredding)**: 계약 해지 시 데이터 이관 포맷의 호환성과 CSP 디스크 상의 잔여 데이터를 암호키 파기로 영구 불능화하는 증명서 확인.

</details>

- **API 기반 실시간 구성 실사(CSPM 연계)**: 수작업 화면 캡처 대신 AWS/Azure API를 직접 호출하여 수천 개의 보안그룹(Security Group), S3 버킷 권한, 미사용 액세스 키를 전수 스캔
- **물리 검사를 대체하는 SOC 보고서 교차 검증**: CSP의 물리 데이터센터 출입이 불가능하므로 공인 회계법인이 발행한 SOC 1/2 Type II 보고서 및 KISA CSAP 인증서의 통제 유효성 검증
- **클라우드 네이티브 복원력(Resilience) 카오스 실증**: 단일 가용영역(AZ) 전체가 단전되는 상황을 시뮬레이션하여 Multi-AZ 오토스케일링 및 DB 페일오버의 100% 정상 작동 확인

#### 한줄 요약
- 공동 책임 분계선, IaC 형상 대조, CSPM 기반 설정 실사, CMK 암호화, 출구 전략 및 데이터 영구 파기를 제공한다.

## Ⅲ. 구조 및 구성요소

<details><summary>용어 설명</summary>

- **클라우드 서비스 감리 4대 통제 계층 (ISO/IEC 27017 & CSA CCM)**:
  1. **책임 경계 및 거버넌스 계층**: IaaS/PaaS/SaaS 모델별 RACI 매트릭스, CSP 공인 인증(CSAP/SOC2), SLA 가용성.
  2. **식별 및 접근 통제 계층 (IAM)**: 루트 계정 잠금, 최소 권한 원칙(Least Privilege), MFA 의무화, 임시 자격증명(STS).

## Ⅳ. 흐름도

<details><summary>용어 설명</summary>

- **클라우드 서비스 감리 실사 5단계 프로세스**:
  1. 클라우드 도입 서비스 모델(IaaS/PaaS/SaaS) 및 공동 책임 매트릭스(RACI) 확정
  2. CSP의 SOC 2 / CSAP 공인 인증 보고서를 검토하여 인프라 물리적 안전성 간접 확인
  3. CSPM 도구 및 API 조회를 통해 이용자 책임 영역(IAM, S3 버킷, 보안그룹) 전수 실사
  4. IaC(Terraform) 코드와 실제 런타임 인프라 간의 설정 드리프트(Configuration Drift) 검증
  5. Multi-AZ 절체 시험 및 계약 종료 시 데이터 반환/암호학적 영구 파기 절차 확인 후 승인

</details>

```text
1. [클라우드 모델 및 공동 책임 경계 확정]
    ├─ 대상: 공공 금융 클라우드 마이그레이션 프로젝트 (AWS IaaS + PaaS 하이브리드)
    └─ [책임 매트릭스 확정: OS/DB/앱/IAM/데이터 암호화는 100% 고객사 책임으로 정의]
            │
            ▼

    └─ [SOC 2 Type II 감사 보고서 내의 물리 데이터센터 접근 통제 적정성 검증]
            │
            ▼

    ├─ [지적 1]: S3 스토리지 버킷 1개가 'All Users (Public Read)'로 개방된 설정 오류 적발
    ├─ [지적 2]: 개발자 IAM 계정 5개에 `AdministratorAccess` 와일드카드 권한 부여 적발
    └─ [조치 요구: S3 퍼블릭 액세스 차단(Block Public Access) 및 최소 권한 Role 재할당]
            │
            ▼

    ├─ Git에 커밋된 Terraform 코드와 AWS 클라우드 실제 리소스 간 드리프트 0건 검증
    └─ [KMS 검증: 모든 RDS 데이터베이스 및 EBS 볼륨이 고객 관리형 키(CMK)로 암호화 확인]
            │
            ▼
5. [Multi-AZ 복원력 및 출구 전략(Exit) 검증]
    ├─ AZ-1 강제 네트워크 차단 시험 ➔ AZ-2 Standby RDS가 4.2초 만에 Primary 승격 (Pass)
    ├─ 계약 종료 시뮬레이션: 표준 RDBMS 덤프 포맷(SQL) 데이터 반환 절차 확인
    └─ [KMS 마스터키 파기를 통한 즉각적인 데이터 판독 불가(Crypto-Shredding) 증명 확인 ➔ 감리 종결]
```

**동작 원리**

1. **설정 오류(Misconfiguration)의 전수 자동화 색출**: 클라우드 보안 사고의 95% 이상은 CSP 결함이 아닌 고객의 잘못된 설정에서 발생하므로, CSPM 도구로 모든 리소스의 권한을 자동 실사
2. **IaC 드리프트(Drift) 방어**: 개발자가 콘솔 화면에서 마우스 클릭으로 임의 변경한 백도어 설정을 방지하기 위해, 모든 인프라 변경이 오직 Git 코드(Terraform)를 통해서만 배포되었는지 검증
3. **봉투 암호화(Envelope Encryption)**: 데이터를 암호화하는 데이터 키(DEK)와 이를 보호하는 마스터 키(KEK)를 분리 관리하여, CSP 엔지니어가 물리 하드디스크를 복사해가더라도 복호화 100% 불가능
4. **암호학적 영구 파기(Crypto-Shredding)**: 클라우드 특성상 수백 대의 분산 스토리지에 흩어진 데이터를 일일이 디스크 와이핑할 수 없으므로, 데이터가 암호화된 상태에서 KMS 마스터키를 영구 삭제하여 1초 만에 판독 불능화
5. **벤더 종속(Lock-in) 방지**: 특정 CSP 전용 독점 API(DynamoDB 등) 사용을 최소화하고 오픈소스 표준 규격(PostgreSQL, Kubernetes)을 채택하여 타 클라우드로의 즉각 이관 가능성 보증

#### 한줄 요약
- 책임 경계 확정, CSP 인증 검토, CSPM 이용자 영역 실사, IaC 드리프트/KMS 검증, Multi-AZ 복원력/출구 전략 승인 순으로 동작한다.

## Ⅴ. 종류 및 비교

<details><summary>용어 설명</summary>

- **클라우드 서비스 모델별 감리 중점 비교**:
  - IaaS 감리: 가상 서버, OS 패치, VPC 네트워크, 방화벽, 스토리지 설정 중심.
  - PaaS 감리: 관리형 DB 파라미터, 컨테이너 오케스트레이션, API 연계 중심.
  - SaaS 감리: 테넌트 데이터 격리, 계정 권한 관리, 데이터 수출/파기 중심.

</details>

| 비교 항목 | IaaS 감리 (인프라 서비스) | PaaS 감리 (플랫폼 서비스) | SaaS 감리 (소프트웨어 서비스) |
|:---|:---|:---|:---|
| **감리 주요 실사 대상**| **가상머신 OS 패치, VPC 네트워크, 보안그룹**| **관리형 DB 설정, K8s 클러스터, 런타임**| **사용자 계정/권한, 테넌트 격리, 데이터**|
| **이용자 책임 범위** | **가장 넓음 (OS부터 앱, 데이터 전체)**| 중간 (앱 소스코드 및 데이터) | **가장 좁음 (계정 및 데이터만 관리)** |
| **주요 설정 결함** | S3 버킷 공개, SSH 포트 개방, OS 취약점| 미흡한 DB 커넥션 풀, API 인증 누락| 과도한 관리자 권한 부여, 로그 미보존|
| **KMS 암호화 적용** | EBS 볼륨, S3 버킷 레벨 고객 키 적용| RDS, 클러스터 스토리지 레벨 암호화 | SaaS 제공사 지원 BYOK(Bring Your Own Key)|
| **출구 전략 난이도** | 쉬움 (가상머신 이미지 및 스토리지 이관)| 중간 (DB 덤프 및 컨테이너 이미지 이전)| **높음 (전용 데이터 포맷 변환 필요)** |

#### 한줄 요약
- IaaS는 OS/네트워크/스토리지 전 영역 실사, PaaS는 플랫폼/런타임 실사, SaaS는 계정/데이터/출구 전략 실사에 집중한다.

## Ⅵ. 실무 고려사항 및 대책

<details><summary>용어 설명</summary>

- **클라우드 감리 실무 수행 시 3대 위험 요소와 엔지니어링 대책**:

</details>

| 문제 | 대책 | 효과 |
|:---|:---|:---|
| CSP의 글로벌 인증(SOC 2)만 믿고 이용자 영역을 보지 않아 **S3 버킷이 전체 공개되어 1,000만 명의 고객 개인정보가 유출되는 참사 발생** | **공동 책임 모델에 기반하여 고객 책임 영역인 S3, IAM, 보안그룹을 CSPM 도구로 전수 스캔하는 기술 실사 강제** | 클라우드 설정 오류에 의한 데이터 유출 100% 원천 차단 |
| 개발자가 AWS 웹 콘솔에서 수동으로 방화벽 포트를 열어두어 **Git의 Terraform 코드와 실제 클라우드 인프라 간의 형상 불일치(Drift) 발생** | **Terraform State와 AWS API를 정기적으로 비교하여 콘솔 수동 변경을 즉각 감지하고 롤백하는 GitOps 파이프라인 실사** | 클라우드 인프라의 완벽한 감사 추적성 확보 |
| 특정 CSP의 독점 데이터베이스에 종속되어 **계약 만료 시 이관 비용이 100억 원 이상 발생하며 서비스를 중단하지 못하는 Lock-in 발생** | **데이터베이스 구축 시 표준 SQL 호환 엔진을 선정하고 감리 단계에서 타 클라우드로의 데이터 덤프/복원 실전 이식 훈련 검증** | 벤더 종속 탈출(Exit Strategy) 및 협상력 확보 |

#### 한줄 요약
- CSPM으로 설정 오류를 잡고, GitOps로 형상 불일치를 막으며, 표준 데이터 포맷으로 Lock-in을 방어한다.

## Ⅶ. 결론

- 클라우드 전환 가속화에 따라 변화된 가상화 및 멀티테넌시 인프라의 위험을 객관적으로 통제하는 최상위 품질 보증 프레임워크인 **클라우드 서비스 감리 체계**는 단순한 문서 확인을 넘어 API 기반의 실증적 보안과 비즈니스 연속성을 보증하는 핵심 기술 감사 공학이며, 실무 구현 시 **IaaS/PaaS/SaaS별 공동 책임 모델의 명확한 분계**, **CSPM 도구 및 IaC 코드 대조를 통한 설정 오류 전수 색출**, **KMS CMK 고객 관리형 암호화 실사**, **Multi-AZ 복원력 및 암호학적 영구 파기 출구 전략(Exit Strategy) 확립**을 완성하여 최고 수준의 클라우드 신뢰성과 무결점 클라우드 네이티브 거버넌스를 완성

#### 한줄 요약
- 공동 책임 모델과 CSPM 기술 실사 및 출구 전략 검증을 통해 무결점 클라우드 서비스 감리를 완성한다.
