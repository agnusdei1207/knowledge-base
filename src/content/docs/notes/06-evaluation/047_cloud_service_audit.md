## Ⅰ. 개요

<details><summary>핵심 용어</summary>

- **클라우드 서비스 감리**: 서비스 모델별 공유 책임 경계를 기준으로 제공자 증거와 이용자의 실제 구성•데이터•복구•출구 통제를 검증하는 감리이다.
- **공유 책임 모델**: 클라우드 제공자와 이용자가 서비스 계층별 보안•운영 책임을 나누는 원칙이다.
- **책임 공백**: 제공자•이용자•재위탁자 중 어느 주체에도 통제와 증거 책임이 배정되지 않은 상태이다.

</details>

- 정의/개념: 서비스 모델별 **공유 책임 경계** 를 기준으로 제공자 증거와 이용자의 실제 구성•데이터•복구•출구 통제를 검증하는 정보시스템 감리
- 배경/필요성: 제공자 인증만으로는 **이용자 설정•재위탁 통제•복구 책임 검증 불가**

#### 한줄 요약
- 제공자 인증만 믿지 않고 제공자와 이용자 중 누가 무엇을 관리하며 실제 설정이 맞는지 확인함

## Ⅱ. 특징

<details><summary>핵심 용어</summary>

- **코드형 인프라(Infrastructure as Code, IaC)**: 클라우드 자원 구성을 코드로 정의하여 반복 배포하고 변경 이력을 남기는 방식이다.
- **제어 평면•데이터 평면**: 자원의 생성•설정•권한을 관리하는 영역과 실제 업무 요청•데이터를 처리하는 영역이다.
- **재위탁자**: 클라우드 제공자가 서비스 일부를 다시 맡긴 외부 사업자이다.
- **응용 프로그래밍 인터페이스(Application Programming Interface, API) 상태 대조**: 승인 구성과 실제 운영 자원의 차이를 API 조회 결과로 확인하는 검증이다.

</details>

- 통제 단위가 되는 서비스 모델별 **공유 책임 모델**
- **API•IaC** 로 워크로드 승인 구성과 실제 자원 대조
- 접근•이전•삭제를 잇는 **테넌트 격리•출구 전략**

#### 한줄 요약
- IaaS에서 SaaS로 갈수록 제공자 책임은 늘지만 계정•데이터•설정에 대한 이용자 책임은 남음

## Ⅲ. 구조 및 구성요소

<details><summary>핵심 용어</summary>

- **신원 및 접근 관리(Identity and Access Management, IAM)**: 사용자•서비스 계정의 신원을 확인하고 자원 접근 권한을 통제하는 체계이다.
- **테넌트 격리**: 여러 고객이 자원을 공유해도 각 고객의 데이터•연산•권한이 섞이지 않게 분리하는 통제이다.
- **관측 가능성**: 로그•메트릭•추적으로 분산 시스템의 내부 상태와 장애 원인을 파악할 수 있는 성질이다.

</details>

```mermaid
block-beta
  columns 1
  R["책임 경계"]
  C["구성 통제"]
  D["데이터 통제"]
  O["운영 복원력"]
  E["계약•출구"]
  R --- C --- D
  D --- O --- E
```

| 구성요소 | 책임 |
|:---|:---|
| 책임 경계 | **IaaS•PaaS•SaaS별 통제 책임** 구분 |
| 구성 통제 | **제어 평면•IAM** 의 승인 구성과 실제 자원 대조 |
| 데이터 통제 | **데이터 평면•지역 제한** 의 접근•백업•삭제 확인 |
| 운영 복원력 | **관측 가능성•복구 시험**으로 장애 전환 관리 |
| 계약•출구 | **SLA•감사권**으로 재위탁•이식•삭제 보장 |

#### 한줄 요약
- 책임표를 시작점으로 실제 설정•데이터•장애 대응과 계약 종료 때의 이전•삭제까지 연결함

## Ⅳ. 흐름도

<details><summary>핵심 용어</summary>

- **승인 구성-실제 상태 대조**: IaC•정책으로 승인한 설정과 API가 반환한 운영 자원 상태의 차이를 찾는 검증이다.
- **출구 전략**: 계약 종료 시 데이터•서비스를 이전하고 제공자•재위탁자의 잔여 데이터를 삭제하는 계획이다.
- **증거 소유자**: 통제의 설계•운영•검증 자료를 제공할 책임이 있는 제공자•이용자•재위탁자이다.

</details>

```mermaid
sequenceDiagram
    participant A as 감리인
    participant C as 이용자
    participant P as 제공자
    C->>A: 클라우드 감리 요청
    A->>A: 1. 책임•증거 소유자 확정
    A->>P: 제공자 증거 요청
    P-->>A: 인증•장애•재위탁 증거
    A->>A: 2. 제공자 통제 검증
    A->>C: 이용자 통제 시험 요청
    C-->>A: 구성•복구•출구 시험 결과
    A->>A: 3. 이용자 통제 검증
    A->>A: 4. 책임 공백•조치 판정
    A-->>C: 감리 결과
```

1. **책임•증거 소유자 확정**: 계층별 통제를 제공자•이용자•재위탁자에 배정
2. **제공자 통제 검증**: 인증 범위•장애 이력•재위탁•SLA 이행 확인
3. **이용자 통제 검증**: IAM•보안그룹•복구•출구 시험과 구성 편차 확인
4. **책임 공백•조치 판정**: 미배정 통제와 잔여 위험의 담당자•기한 확정

#### 한줄 요약
- 제공자가 맡은 부분은 외부 증거로 보고 이용자가 맡은 설정과 복구는 직접 시험해 책임 공백을 찾음

## Ⅴ. 종류 및 비교

<details><summary>핵심 용어</summary>

- **서비스형 인프라(Infrastructure as a Service, IaaS)**: 제공자가 물리•가상 인프라를 관리하고 이용자가 운영체제(Operating System, OS) 이상을 관리하는 모델이다.
- **서비스형 플랫폼(Platform as a Service, PaaS)**: 제공자가 실행 플랫폼까지 관리하고 이용자가 애플리케이션•데이터를 관리하는 모델이다.
- **서비스형 소프트웨어(Software as a Service, SaaS)**: 제공자가 애플리케이션까지 관리하고 이용자가 계정•데이터•설정을 관리하는 모델이다.

</details>

| 클라우드 서비스 모델 | IaaS | PaaS | SaaS |
|:---|:---|:---|:---|
| 적용 기준 | 인프라 **직접 제어** 필요 | 개발 **플랫폼 구성** 필요 | 완성된 **응용 서비스** 이용 |
| 핵심 특징 | OS 이상을 **이용자가 관리** | 앱•데이터를 **이용자가 관리** | 계정•데이터•설정을 **이용자가 관리** |
| 한계 | **권한 과다•관리 포트 노출** | **종속성•비밀정보 노출** | **테넌트 격리•무단 반출** |

#### 한줄 요약
- IaaS는 제어권과 책임이 크고 SaaS는 운영 부담은 작지만 계정•데이터 통제는 이용자에게 남음

## Ⅵ. 실무 고려사항 및 대책

<details><summary>핵심 용어</summary>

- **권한 과다**: 사용자•서비스 계정에 업무상 필요한 범위를 넘는 클라우드 권한이 부여된 상태이다.
- **보안그룹**: 클라우드 자원으로 들어오고 나가는 통신을 허용 규칙으로 제한하는 가상 방화벽이다.
- **제공자 인증 의존**: 제공자 인증서만 확인하고 이용자 설정•복구•재위탁 통제를 직접 검증하지 않는 문제이다.
- **구성 편차**: 승인된 코드형 인프라•정책과 실제 배포된 보안그룹•권한•자원 상태가 다른 문제이다.

</details>

| 문제 | 대책 | 효과 |
|:---|:---|:---|
| 제공자 인증을 이용자 설정까지 해석해 **책임 공백** | **공유 책임표•통제•증거 소유자 명시** | 제공자•이용자의 **통제 누락 방지** |
| 승인 IaC와 실제 보안그룹의 **구성 편차** | **API 실자원과 승인 IaC 지속 대조** | 배포 상태의 **준거 일치 확보** |
| 계약 종료 뒤 **공급자 종속•잔존 데이터** | **이식•복원 시험•삭제 증명 계약화** | 서비스 이전과 **데이터 종결 가능성 확보** |
| 클라우드•개인정보 통제 기준이 다르면 증거가 누락됨 | **ISO/IEC 27017 발행 추적•27018:2025 적용** | 보안•개인정보의 **공통 통제 확보** |

#### 한줄 요약
- IaaS의 승인 IaC와 실제 보안그룹•IAM 설정 및 변경 로그를 대조해 무단 구성 편차를 확인한다.

## Ⅶ. 결론

<details><summary>핵심 용어</summary>

- **서비스 수준 협약(Service Level Agreement, SLA)**: 가용성•지원•복구 등 서비스 목표와 위반 책임을 정한 협약이다.
- **잔여 데이터 검증**: 계약 종료•자원 삭제 후 백업•복제•재위탁 환경에 고객 데이터가 남지 않았는지 증거로 확인하는 절차이다.
- **서비스 승인 결정**: 서비스 모델별 책임자와 증거를 확인하고 실제 구성•복구•출구 시험을 통과한 서비스만 승인하는 판단이다.

</details>

- 서비스 모델별 책임자가 확인되고 **실구성•복구** 와 **출구 시험** 을 통과한 서비스만 승인

#### 한줄 요약
- 제공자 인증은 이용자 설정을 대신하지 않으므로 책임별 증거와 실제 자원 상태를 함께 확인해야 함
