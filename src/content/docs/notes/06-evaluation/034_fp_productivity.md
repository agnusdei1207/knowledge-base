## Ⅰ. 개요

<details><summary>핵심 용어</summary>

- **기능점수 기반 규모•생산성 산정(Function Point based Size and Productivity Estimation)**: 개발자 관점의 물리적 코드 길이가 아닌, 사용자 관점에서 제공되는 논리적 데이터 및 트랜잭션 기능의 복잡성을 계수하여 소프트웨어 고유 규모(FP)를 산출하고, 이를 투입된 공수로 나누어 프로젝트 간 객관적인 생산성을 비교하는 기법이다.
- **생산성(Productivity)**: 인력과 시간이라는 투입 공수(보통 맨먼스, MM) 한 단위가 만들어낸 실질적인 비즈니스 기능 규모를 나타내며, FP/MM 수식으로 도출하여 개발 조직의 역량과 효율성을 평가하는 핵심 지표이다.
- **코드 줄 수(Lines of Code, LOC)**: 구현이 완료된 소스 코드의 줄 수를 기반으로 시스템 규모를 산출하는 전통적 지표로, 측정은 쉽지만 사용 언어나 코딩 스타일에 따라 수치가 극심하게 변동하는 물리적 규모 지표이다.

</details>

- 정의/개념: 기술 종속성을 배제하고 사용자 관점의 비즈니스 기능을 객관적으로 계수하여 소프트웨어 가치를 추정하는 **기능점수(Function Point) 기반 규모•생산성 산정** 방식이다.
- 배경/필요성: 물리적인 **LOC(Lines of Code)** 지표로는 개발 시작 전 단계에서 규모와 예산을 예측하기 불가능하며, 프로젝트 간 **생산성(Productivity)** 벤치마킹 시에도 자바, C 등 구현 언어 차이에 따른 왜곡이 심해 표준화된 규모 척도가 필요했다.

#### 한줄 요약

- 개발 언어가 결정되기도 전인 기획 단계에서 투입 예산을 짜야 하므로, 사용자가 요구한 화면 입력, 데이터베이스 관리, 출력 및 조회 기능을 점수화하여 시스템 규모를 선제적으로 추정하고 완료 후엔 투입 공수 대비 팀의 효율성 비교.

## Ⅱ. 특징

<details><summary>핵심 용어</summary>

- **애플리케이션 경계(Application Boundary)**: 측정 대상이 되는 소프트웨어 시스템과 외부 사용자 또는 연계 타 시스템 간의 한계를 명확히 분리하여, 어느 데이터와 기능을 내부로 계수할지 판정하는 논리적 가상의 선이다.
- **미조정 기능점수(Unadjusted Function Point, UFP)**: 시스템 환경 복잡도(데이터 통신, 분산 처리 등 14개 보정 계수)를 적용하기 전, 순수하게 식별된 5가지 기능 유형별 개수에 각각의 복잡도(Low, Average, High) 가중치만을 곱해 합산한 초기 기본 점수이다.
- **기술 독립성(Technology Independence)**: 최신 클라우드 네이티브 아키텍처든 오래된 코볼 레거시든 구현 기술이나 프로그래밍 언어의 차이에 영향받지 않고 오직 사용자가 체감하는 요구 기능량만을 일관된 잣대로 산출해 내는 기능점수의 고유 성질이다.
- **인월(Man-Month, MM)**: 보통 1명의 개발자가 1개월(통상 22일, 176시간) 동안 프로젝트에 투입되어 수행하는 작업 노력의 총량을 나타내는 표준 투입 공수 단위이다.

</details>

- 논리적인 **애플리케이션 경계(Application Boundary)**를 명확히 설정하여 시스템 내부에서 직접 유지하는 데이터와 외부 타 시스템에서 참조만 해오는 데이터를 철저히 구분한다.
- 데이터 기능과 트랜잭션 기능 유형별로 도출된 개수와 각 기능이 내포한 난이도를 반영한 복잡도 가중치를 곱해 **미조정 기능점수(UFP)**를 우선 산출한다.
- 개발 언어 환경에 흔들리지 않는 **기술 독립성(Technology Independence)**을 바탕으로 규모를 측정하고, 투입 공수를 표준 단위인 **인월(Man-Month, MM)**로 통일하여 객관적 생산성 지표를 얻는다.

#### 한줄 요약

- 똑같은 사용자 로그인 기능이라면 C언어든 파이썬이든 동일한 FP 잣대로 잴 수 있어 공정한 비교가 가능하지만, 시스템의 경계를 잘못 긋거나 기능을 중복 계수하면 엉뚱한 점수가 나오므로 산정자 간 교차 검증 절차 필수.

## Ⅲ. 구조 및 구성요소

<details><summary>핵심 용어</summary>

- **내부 논리 파일(Internal Logical File, ILF)**: 사용자가 식별할 수 있고, 측정 대상 애플리케이션 경계 내부에서 직접 등록, 수정, 삭제되며 관리 주체가 대상 시스템인 논리적 데이터 그룹이다(예: 회원 정보 테이블).
- **외부 연계 파일(External Interface File, EIF)**: 측정 대상 애플리케이션 경계 외부에 존재하며, 다른 시스템이 관리하지만 현재 시스템이 비즈니스 로직을 위해 단순히 참조(Read)만 하는 논리적 데이터 그룹이다(예: 우체국 시스템의 우편번호 테이블).
- **외부 입력(External Input, EI)**: 애플리케이션 경계 밖에서 데이터나 제어 정보를 시스템 내부로 받아들여, 하나 이상의 내부 논리 파일(ILF)을 생성, 수정, 삭제하여 내부 상태를 변경하는 트랜잭션 기능이다.
- **외부 출력(External Output, EO)**: 애플리케이션 경계를 넘어 사용자나 타 시스템으로 정보를 내보낼 때, 단순 조회를 넘어 내부 데이터를 가공, 계산, 요약 처리하여 부가가치를 더해 결과를 제공하는 트랜잭션 기능이다.
- **외부 조회(External Inquiry, EQ)**: 데이터를 가공하거나 내부 ILF 상태를 전혀 변경하지 않고, 주어진 입력 조건에 매칭되는 데이터를 데이터베이스에서 단순히 검색 및 추출하여 그대로 사용자에게 제공하는 트랜잭션 기능이다.

</details>

```text
                       [애플리케이션 경계]
                         /           \
                  [데이터 기능]   [트랜잭션 기능]
                         \           /
                      [복잡도 가중치]
                               |
                         [산정 기준]
```

선의 의미: 최상위 애플리케이션 경계를 기준으로 멈춰있는 데이터 요소(ILF, EIF)와 움직이는 동적 사용자 행위(EI, EO, EQ)를 쪼개어 분류한 뒤, 난이도에 따른 복잡도 가중치를 공통 산정 규칙에 따라 결합해 1차원적 규모 점수를 뽑아내는 계수 구조를 나타낸다.

| 구성요소 | 책임 |
|:---|:---|
| 애플리케이션 경계 | 대상 시스템의 스코프를 정의하여 데이터 생성 및 관리의 책임 주체 소재 확정 |
| 데이터 기능 | 데이터 관리 책임 소재에 따라 내부 유지 파일(**ILF**)과 외부 참조 파일(**EIF**) 논리 식별 |
| 트랜잭션 기능 | 사용자 데이터 흐름 방향과 가공 여부에 따라 입력(**EI**), 가공 출력(**EO**), 단순 조회(**EQ**) 식별 |
| 복잡도 가중치 | 데이터 필드 수(DET)와 레코드 수(RET) 등을 맵핑표에 대조하여 높음, 보통, 낮음으로 치환 뒤 **UFP** 수식 변환 |
| 산정 기준 | 주관적 오류 방지를 위해 공식 매뉴얼(IFPUG 등) 기반 계수 규칙, 판정 사유 기록, 크로스 검토 이력 보존 |

#### 한줄 요약

- 프로젝트 도면 위에 가장 먼저 애플리케이션 경계선을 치고 내 집 데이터와 남의 집 데이터를 식별한 뒤, 그 선을 들락거리는 사용자 조회와 입력 거래를 하나씩 짚어 가중치를 매겨야 누락 없는 정확한 몸집 측정 가능.

## Ⅳ. 흐름도

<details><summary>핵심 용어</summary>

- **기능 식별(Function Identification)**: 요구사항 명세서와 화면 설계서 등을 분석하여 시스템 내외부로 데이터가 이동하는 경로를 따라 데이터 2종(ILF/EIF)과 트랜잭션 3종(EI/EO/EQ)을 중복 없이 발라내는 정밀 계수 과정이다.
- **복잡도 가중치(Complexity Weight)**: 단순한 기능과 복잡한 기능의 노력 차이를 보정하기 위해, 취급하는 데이터 필드 요소(DET), 레코드 요소(RET), 참조 파일(FTR) 개수 매트릭스에 따라 각 기능에 차등 부여하는 점수(Low/Average/High)이다.
- **동료 검토(Peer Review)**: 시스템 경계 설정, 기능 유형 오판, 교묘하게 숨은 기능 중복 산정 등의 주관적 실수를 보정하기 위해, 제3의 산정 전문가가 판정 근거를 크로스 체크하여 견적 편차를 줄이는 품질 보증 절차이다.
- **산정 목적•애플리케이션 경계 확정**: 예산 확보용 간이 산정인지, 대가지급용 상세 산정인지 목적을 세우고 타 시스템 인터페이스 연계 구간 등 측정 물리망을 정하는 출발 단계이다.
- **데이터•트랜잭션 기능 식별**: 정해진 경계를 바탕으로 ILF/EIF 및 EI/EO/EQ의 5대 핵심 유형을 누락이나 뻥튀기 없이 색출해내는 계수 단계이다.
- **복잡도 가중치•FP 산출**: 식별된 각 기능의 데이터 필드 개수 등을 세어 난이도 매트릭스에 대입한 뒤 최종 UFP와 VAF(보정 계수)를 결합하여 수치화하는 계산 단계이다.
- **경계•유형•누락 동료 검토**: 초기 산정자의 편향과 논리적 비약을 방지하기 위해 독립된 외부 또는 내부 심사자가 계수 근거 문서의 정합성을 검증하는 단계이다.
- **확정 FP•투입공수 생산성 산출**: 오차 검증이 끝난 100% 확정 규모 점수를 프로젝트에 소요된 총 투입 인력(MM)으로 나누어 객관적인 조직 생산성(FP/MM)을 산출해 내는 마감 단계이다.

</details>

```text
산정자
   │ 1. 산정 목적•애플리케이션 경계 확정
   ▼
기능목록
   │ 2. 데이터•트랜잭션 기능 식별
   ▼
산정도구
   │ 3. 복잡도 가중치•FP 산출
   ▼
검토자
   │ 4. 경계•유형•누락 동료 검토
   ▼
산정자
   │ 5. 확정 FP•투입공수 생산성 산출
```

### 동작 원리

1. **산정 목적•애플리케이션 경계 확정**: 산정 레벨을 결정하고 대상 시스템의 논리적 **애플리케이션 경계(Application Boundary)**를 고정한다.
2. **데이터•트랜잭션 기능 식별**: 꼼꼼한 **기능 식별(Function Identification)** 절차를 거쳐 ILF, EIF, EI, EO, EQ를 분리 및 매핑한다.
3. **복잡도 가중치•FP 산출**: 각 기능 내부의 세부 항목 수를 기반으로 **복잡도 가중치(Complexity Weight)**를 곱하여 정량 점수를 도출한다.
4. **경계•유형•누락 동료 검토**: 산정 왜곡 방지를 위한 **동료 검토(Peer Review)** 프로세스를 가동해 판정 논리를 투명하게 교정한다.
5. **확정 FP•투입공수 생산성 산출**: 확정된 총 FP를 투입된 전체 인월(MM)로 나누어 프로젝트 수행 역량인 FP/MM 지표를 산출한다.

#### 한줄 요약

- 경계를 치고 안팎의 데이터와 화면 조작 건수를 세어 가중치를 더한 앞의 총점(FP)은 우리가 짜야 할 일감의 크기이고, 이를 사람 투입량으로 나눈 뒤의 수치(FP/MM)는 같은 돈과 시간으로 얼마나 능률적으로 뽑아냈는지 증명하는 효율성 성적표.

## Ⅴ. 종류 및 비교

<details><summary>핵심 용어</summary>

- **FP 적용(Function Point Application)**: 기획 단계에서의 개발 예산 수립, 하도급 업체와의 계약 규모 산정, 혹은 C 언어와 Java 등 서로 다른 아키텍처 환경 간의 순수 개발 조직 생산성을 절대 비교할 때 적용하는 가치 산정 방식이다.
- **LOC 적용(Lines of Code Application)**: 프로젝트 완료 후 작성된 물리적 코드 파일량 분석, 레거시 시스템 마이그레이션 시의 리팩터링 모듈 타깃팅, 자동화 도구 기반의 버그 밀도 산정 시 적용하는 하부 구조 측정 방식이다.
- **MM 적용(Man-Month Application)**: 산정된 시스템 기능 규모(FP)를 소화하기 위해 필요한 소요 인력과 시간을 예측하거나, 반대로 사후 프로젝트 투입 공수 대비 구현 규모를 역산하여 팀의 효율성을 산출하는 시간 및 노동력 기반 측정 방식이다.

</details>

| 소프트웨어 규모 산정 방식 | 기능점수 (FP) | LOC (Lines of Code) | 스토리 포인트 (Story Point) |
|:---|:---|:---|:---|
| 적용 목적 및 기준 | 사용자 관점의 객관적 견적 및 이기종 간 생산성 벤치마킹을 위한 **FP 적용** | 구현 후 컴포넌트별 물리 단위 버그 밀도 및 구조 분석을 위한 **LOC 적용** | 애자일 팀 내부의 백로그 난이도 상대 평가 및 스프린트 계획 수립 |
| 핵심 특징 | 사용자 비즈니스 요구사항 기준 논리적 규모 | 실제 작성된 소스 코드 라인 수 기반 물리적 규모 | 개발 팀 주관의 업무 복잡도 및 노력 기반 상대적 작업량 |
| 한계 및 기회 비용 | 기능 복잡도 및 경계 판정에 전문 지식 요구 및 산정자 간 주관적 오차 발생 여지 | 자동 생성 코드 및 개발자 역량/언어 특성에 따라 수치가 고무줄처럼 변동 | 다른 애자일 팀이나 다른 프로젝트 간의 객관적 비교 잣대로 사용 절대 불가 |

> **생산성(Productivity) 도출 공식** = 프로젝트 총 확정 기능점수 (FP) / 개발 전체 투입 공수 (MM)

**MM 적용(Man-Month Application)** 기법을 혼합하여 도출된 사용자 기능 규모 대비 실제 투입 개발 공수 지표를 통해 소프트웨어 개발사의 고유 역량을 정량화한다.

#### 한줄 요약

- FP는 사용자에게 얼마어치 가치를 주었는지, LOC는 개발자가 키보드를 얼마나 많이 쳤는지, 스토리 포인트는 우리 팀이 이번 달 일감을 얼마나 벅차다고 느꼈는지를 증명하므로, 고객 계약 및 타사 벤치마킹에는 FP/MM 잣대만 써야 팩트 왜곡 불가.

## Ⅵ. 실무 고려사항 및 대책

<details><summary>핵심 용어</summary>

- **경계 오류(Boundary Error)**: 내부에서 자체 생산하고 통제하는 데이터(ILF)와 다른 시스템이 만들어 놓은 것을 그저 읽어오기만 하는 데이터(EIF)를 착각하여 배점을 잘못 적용함으로써, 전체 사업 규모와 예산이 수천만 원씩 요동치는 결정적 오산 문제이다.
- **기능 중복 계수(Double Counting)**: 똑같이 사원 정보를 갱신하는 단일 내부 트랜잭션 로직인데, 웹 화면 UI, 모바일 앱 API, 야간 배치 프로그램 세 곳에서 호출된다고 이를 3개의 분리된 외부 입력(EI)으로 중복 산정해 규모를 불법적으로 뻥튀기하는 문제이다.
- **생산성 비교 조건(Productivity Comparison Condition)**: A 조직과 B 조직의 FP/MM 생산성을 벤치마킹할 때, 개발하는 시스템의 복잡도 도메인, 엄격한 품질 통과 기준 유무, 기성 프레임워크 재사용 비율, 개발자 연차 등의 환경 팩터를 완벽히 동일 선상에 맞춘 상태에서 통계를 돌려야 한다는 전제 조건이다.
- **요구 변경 추적(Requirements Change Tracking)**: 초기 제안 시점과 프로젝트 종료 시점 간의 산출된 FP 차이를 단순한 수치 변동으로 두지 않고, 고객이 추가 요청한 기능 명세서 이력과 일대일로 맵핑하여 무상 개발 방지와 추가 과금의 합법적 근거를 남기는 관리 활동이다.

</details>

| 문제 | 대책 | 효과 |
|:---|:---|:---|
| 미숙한 시스템 **경계 오류**로 인한 내부 데이터 중복 판정 및 누락 | 전문 심사역 기반 크로스 체크와 **기능 중복 계수(Double Counting)** 집중 점검 | 사업 대가 산정의 일관성 확보 및 재무적 분쟁 요소 원천 차단 |
| 상이한 개발 도구, 재사용 컴포넌트 여부를 간과한 생산성 수치 맹신 현상 | 평가 시 엄격한 **생산성 비교 조건(Comparison Condition)** 적용 및 환경 계수 보정 | 성과 평가의 타당성 향상 및 억울한 하위 고과 조직 발생 방지 |
| 개발 중간 단계의 끝없는 요구사항 추가로 인한 초기 규모 및 예산 변동 | 형상 관리 시스템과 연동된 베이스라인별 치밀한 **요구 변경 추적(Change Tracking)** | 스코프 크립(Scope Creep) 차단 및 비용 보전/계약 변경 추적성 확보 |

#### 한줄 요약

- 새로 발주하는 차세대 시스템의 FP가 1,000점으로 나왔을 때, 유사한 과거 금융 사업의 자사 평균 생산성이 1인당 월 10점(FP/MM)이었다면, 즉각적으로 100맨먼스의 예산과 공수가 투입되어야 한다는 수학적 과학적 견적 도출 가능.

## Ⅶ. 결론

<details><summary>핵심 용어</summary>

- **규모와 생산성 구분(Separation of Size and Productivity)**: FP 지표 자체는 비즈니스의 부가가치 덩어리를 재는 객관적 크기 산정에 집중하고, FP/MM 지표는 그 덩어리를 만들어낸 개발 조직의 역량과 비용 효율을 평가하는 데 분리하여 활용하는 실무 원칙이다.
- **비교 기준 통제(Control of Comparison Criteria)**: 타 부서와의 생산성 대결 시, 애플리케이션 경계 설정 방식, IFPUG 표준 계수 규칙 준수, 업무 도메인 난이도 등 베이스 변수를 엄격히 일치시켜 FP/MM 지표의 악의적 통계 왜곡을 막는 원칙이다.
- **견적•성과 결정(Estimation and Performance Decision)**: 선제적 사업 투입 예산은 도출된 기능점수 규모를 조직의 과거 평균 유사 생산성 지수로 나누어 승인하고, 사후 성과 보상은 동일 조건 내에서 쥐어짠 확정 기능점수 대비 최소 투입 인월(MM) 지표로 결정하는 경영적 의사 판단이다.

</details>

- 철저한 **규모와 생산성 구분(Separation of Size and Productivity)** 원칙 하에 객관적인 **비교 기준 통제(Control of Comparison Criteria)**를 거쳐 합리적 **견적•성과 결정(Estimation and Performance Decision)** 프로세스 구축 필수.

#### 한줄 요약

- 경영진에게 정확한 예산을 타내려면 요구사항을 철저히 쪼개 FP 규모를 객관적으로 증명하고, 프로젝트 후 팀의 유능함을 뽐내려면 확정 FP를 실제 사용한 공수로 나누되, 남들과 잴 때는 반드시 동일한 잣대와 계수 룰을 깔아 통계 조작 논란 원천 차단.
