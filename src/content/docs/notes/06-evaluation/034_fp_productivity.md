## 미리 알고가기

- **기능점수(FP, Function Point)**: 사용자가 인식하는 논리 기능을 기준으로 측정한 소프트웨어 규모
- **애플리케이션 경계**: 측정 대상과 외부 사용자·시스템을 나누는 논리적 선
- **ILF(Internal Logical File)**: 측정 대상이 내부에서 유지·관리하는 논리 데이터 집합
- **EIF(External Interface File)**: 외부가 관리하고 측정 대상은 참조만 하는 논리 데이터 집합
- **EI(External Input)**: 경계 밖 입력으로 내부 데이터나 동작을 변경하는 처리
- **EO(External Output)**: 계산이나 가공을 포함해 경계 밖으로 정보를 내보내는 처리
- **EQ(External Inquiry)**: 내부 데이터를 변경하거나 복잡하게 가공하지 않는 조회 처리
- **UFP(Unadjusted Function Point)**: 기능 유형과 복잡도별 가중치를 합산한 미조정 기능점수
- **MM(Man-Month)**: 한 사람이 한 달 동안 투입하는 작업량
- **생산성(Productivity)**: 투입 공수 한 단위로 구현한 기능 규모
- **LOC(Lines of Code)**: 소스 코드 줄 수를 기준으로 측정한 구현 규모

## Ⅰ. 개요

- **정의/개념**: 사용자 기능을 세어 규모와 생산성을 산정한다
- **배경/필요성**: 구현 기술에 덜 종속된 견적·비교 기준을 만든다

### 쉽게 이해하기 (학습용)

- 구현 언어가 정해지기 전에는 코드 줄 수를 알 수 없으므로, 사용자가 요구한 입력·출력·조회·데이터 기능을 점수로 바꾸면 개발 전에도 규모를 추정하고 완료 후에는 투입 공수 대비 생산성을 비교할 수 있다.

## Ⅱ. 특징

- 사용자 관점 기능은 구현 언어별 규모 편차를 줄인다
- 경계 설정은 기능의 중복·누락과 규모 왜곡을 막는다
- 기능 유형·복잡도 가중치는 논리 규모를 수치화한다
- 표준 계수 규칙은 산정자 간 편차를 줄인다
- FP와 공수 결합은 규모와 생산성의 혼동을 막는다

### 쉽게 이해하기 (학습용)

- 같은 요구사항은 구현 언어가 달라도 비슷한 FP를 가지므로 기술에 덜 종속적인 비교가 가능하지만, 경계와 기능을 잘못 나누면 점수가 달라지므로 일관된 규칙과 동료 검토가 필요하다.

## Ⅲ. 아키텍처 및 구성요소

```mermaid
flowchart LR
    A[애플리케이션 경계] --> B[데이터 기능]
    A --> C[트랜잭션 기능]
    B --> D[복잡도 가중치]
    C --> D
    D --> E[산정 기준]
```

| 설계 요소 | 설명 |
|:---|:---|
| 애플리케이션 경계 | 내부와 외부의 논리 범위를 확정 |
| 데이터 기능 | ILF와 EIF를 식별 |
| 트랜잭션 기능 | EI·EO·EQ를 식별 |
| 복잡도 가중치 | 유형별 복잡도를 점수로 변환 |
| 산정 기준 | 규칙·근거·이력을 통제 |

> 요약: 경계 안의 데이터·거래 기능을 가중 합산한다

### 쉽게 이해하기 (학습용)

- 먼저 경계를 그어 데이터의 관리 주체를 구분하고, 그 경계를 드나드는 사용자 거래를 찾은 뒤 복잡도 가중치를 적용해야 같은 기능을 중복 계수하거나 빠뜨리지 않고 규모를 산정할 수 있다.

## Ⅳ. 원리 및 절차 흐름도

```mermaid
sequenceDiagram
    participant E as 산정자
    participant S as 대상시스템
    E->>S: 목적·경계 확정
    E->>S: 데이터 기능 식별
    E->>S: 트랜잭션 기능 식별
    E->>E: 복잡도·점수 계산
    E->>E: 검토·생산성 산정
```

| 절차 | 설명 |
|:---|:---|
| 목적·경계 확정 | 산정 목적과 대상 범위를 고정 |
| 데이터 기능 식별 | ILF와 EIF의 관리 주체를 구분 |
| 트랜잭션 기능 식별 | EI·EO·EQ의 사용자 목적을 구분 |
| 복잡도·점수 계산 | 유형별 가중치를 합산해 FP 산출 |
| 검토·생산성 산정 | 교차 검토 후 FP/MM를 계산 |

> 요약: 기능을 계수하고 검토한 뒤 생산성을 산정한다

### 쉽게 이해하기 (학습용)

- 경계 안팎의 데이터와 사용자 거래를 차례로 세고 가중치를 합산한 뒤 투입 공수로 나누면, 앞의 FP는 만들어야 할 기능 규모를 뒤의 FP/MM는 같은 공수로 얼마나 구현했는지를 뜻한다.

## Ⅴ. 종류 및 비교

| 판단 축 | FP | LOC | 스토리 포인트 |
|:---|:---|:---|:---|
| 핵심 특징 | 사용자 기능의 절대 규모 | 구현 코드의 물리 규모 | 팀이 정한 상대 작업량 |
| 적용 기준 | 견적·계약·생산성 비교 | 구현 후 코드량 분석 | 팀 내부 반복 계획 |
| 주요 위험 | 경계 판정에 편차 발생 | 언어·생성 방식에 종속 | 팀 간 수치 비교가 곤란 |

> 생산성 = 기능점수(FP) / 투입 공수(MM)

> 요약: FP는 규모, LOC는 코드량, 점수는 상대 작업량이다

### 쉽게 이해하기 (학습용)

- FP는 무엇을 제공했는지, LOC는 얼마나 코딩했는지, 스토리 포인트는 팀이 얼마나 어렵다고 보았는지를 나타내므로, 조직 간 생산성은 FP/MM로 비교하고 팀 내부 계획은 스토리 포인트로 관리해야 의미가 섞이지 않는다.

## Ⅵ. 실무 사례

1. 신규와 변경 기능의 범위를 분리해 산정한다
2. 산정자 간 교차 검토로 편차를 조정한다
3. 조직 기준 생산성으로 공수를 추정한다
4. 공공 사업 대가에 표준 FP를 적용한다

### 쉽게 이해하기 (학습용)

- 사례 1은 기존 기능 전체를 다시 세면 변경 사업 규모가 부풀려지므로, 새로 만들거나 수정·삭제하는 기능만 변경 범위로 분리해 견적의 근거를 명확히 한다.
- 사례 2는 산정자마다 경계와 기능 유형 판단이 달라질 수 있으므로, 독립 산정 결과의 차이를 규칙과 요구사항 근거로 조정해 개인 판단의 편차를 줄인다.
- 사례 3은 산정한 FP를 조직의 과거 FP/MM로 나누면 예상 공수가 나오므로, 조직과 기술 여건이 비슷한 실적 자료를 사용해 일정과 인력 계획을 세운다.
- 사례 4는 공공 사업에서는 정한 산정 지침과 기능 유형별 단가를 일관되게 적용하고 근거를 남겨야, 발주자와 수행자가 같은 기능 범위로 대가를 검증할 수 있다.

## Ⅶ. 결론

- 경계를 통일해 FP와 FP/MM를 구분 활용한다.

### 쉽게 이해하기 (학습용)

- 견적이 필요하면 기능을 FP로 산정하고 수행 효율을 비교하려면 FP를 실제 공수로 나누되, 동일한 경계·계수 규칙·실적 조건을 적용해야 수치가 규모와 생산성을 올바르게 설명한다.
