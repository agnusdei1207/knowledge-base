## Ⅰ. 개요

<details><summary>용어 설명</summary>

- **시스템 성능 지표(System Performance Key Performance Indicators, System KPI)**: IT 인프라 및 소프트웨어 시스템이 주어진 워크로드 환경에서 비즈니스 요구사항을 충족하며 안정적으로 동작하는지 평가하기 위해 처리 능력(TPS/처리량), 지연 속도(응답시간/레이턴시), 서비스 연속성(가용성/신뢰성)을 정량화한 핵심 평가 척도.
- **평균값의 함정 및 꼬리 지연 은폐 결함(Flaw of Averages & Tail Latency Defect)**: 대규모 분산 환경에서 평균 응답시간(Average Latency)만을 성능 지표로 관리할 경우, 95% 이상의 정상 트래픽에 가려진 상위 1%~5% 사용자(p95, p99)의 극심한 지연(Tail Latency)과 자원 경합에 의한 포화(Saturation) 현상을 조기에 식별하지 못해 대형 장애로 이어지는 구조적 결함.

</details>

- 정의/개념: 시스템의 처리 용량과 사용자 체감 품질을 종합 검증하기 위해 **초당 트랜잭션 수(TPS) 산출 $\rightarrow$ 백분위수(p95/p99) 기반 응답시간 분포 측정 $\rightarrow$ 네트워크/디스크 대역폭 처리량(Throughput) 검증 $\rightarrow$ MTBF/MTTR 기반 가용성(Availability) 산정 $\rightarrow$ SLI/SLO/SLA 거버넌스 환류** 를 집행하는 **다차원 성능 평가 체계**
- 배경/필요성: 마이크로서비스(MSA)와 클라우드 분산 환경의 확산으로 단일 호출 지연이 연쇄적으로 증폭(Latency Amplification)됨에 따라, 단순 하드웨어 가동률이 아닌 서비스 수준 중심의 정량적 평가 프레임워크 요구

#### 한줄 요약
- 시스템 성능 지표는 TPS, 백분위 응답시간, 처리량, 가용성을 다차원으로 연계하여 성능 병목과 서비스 신뢰성을 평가한다.

## Ⅱ. 특징

<details><summary>용어 설명</summary>

- **성능 평가 4대 핵심 축**:
  - **TPS (Transactions Per Second)**: 단위 시간(1초)당 비즈니스 거래(DB Commit 완료 기준)를 완수한 건수.
  - **응답시간 (Response Time / Latency)**: 클라이언트가 요청을 송신한 시점부터 최종 응답 바이트를 수신할 때까지의 경과 시간.
  - **처리량 (Throughput)**: 단위 시간당 시스템이 처리하여 전송한 총 데이터량(Bytes/sec) 또는 API 요청 수(RPS).
  - **가용성 (Availability)**: 전체 약정 운영 시간 중 정상적인 서비스 처리가 가능했던 시간의 백분율 ($Availability = \frac{MTBF}{MTBF + MTTR} \times 100\%$).

</details>

- **분포 중심의 꼬리 지연(Tail Latency) 측정**: 평균값이 아닌 백분위수(p90, p95, p99, p99.9)를 측정하여 자원 경합(Lock, GC Pause)에 의한 극단적 지연을 정밀 추적
- **업무 거래와 단순 호출의 명확한 분리**: 비즈니스 트랜잭션(TPS)과 네트워크 HTTP 호출(RPS)의 단위를 분리하여 지표 왜곡 방지
- **SLI-SLO-SLA의 계층적 연계**: 측정 관측치(SLI) $\rightarrow$ 내부 관리 목표치(SLO) $\rightarrow$ 고객 계약 및 위약금 보상(SLA)으로 이어지는 폐쇄 루프 거버넌스 확립

#### 한줄 요약
- 백분위 꼬리 지연 분석, TPS/RPS 분리 측정, SLI/SLO/SLA 계층 연계를 제공한다.

## Ⅲ. 구조 및 구성요소

<details><summary>용어 설명</summary>

- **시스템 성능 지표 4대 아키텍처 계층**:
  1. **Workload & Boundary Layer**: 부하 조건 정의 및 측정 대상 업무 경계 설정.
  2. **Execution & Metric Layer**: TPS, RPS, 대기시간(Wait Time), 서비스시간(Service Time) 측정.
  3. **Statistical Aggregation Layer**: 평균, 표준편차, p50/p90/p95/p99 백분위수 계산.
  4. **Governance & Target Layer**: SLI 관측치, SLO 달성률, 에러 예산(Error Budget), SLA 위약 기준.

</details>

```text
┌─────────────────────────────────────────────────────────────────────────┐
│ [ 1. 측정 경계 및 부하 주입 계층 (Measurement Boundary & Workload) ]    │
│  ├─ [ 부하 발생기 (JMeter / Locust) ] ➔ 동시 사용자(VUser), 요청률 주입 │
│  └─ [ 측정 경계 설정 ] ➔ Web ➔ WAS ➔ DB 계층별 End-to-End 트랜잭션 정의 │
└────────────────────────────────────┬────────────────────────────────────┘
                                     │ (요청 및 응답 이벤트 수집)
                                     ▼
┌─────────────────────────────────────────────────────────────────────────┐
│ [ 2. 핵심 성능 지표 수집 계층 (Core Performance Metrics Collection) ]   │
├───────────────────────────────────┬─────────────────────────────────────┤
│ [ 처리 역량 지표 (Capacity) ]     │ [ 사용자 체감 지표 (Latency) ]       │
│ ├─ TPS: 1초당 완수된 비즈니스 거래│ ├─ Service Time: 실제 CPU 연산 시간 │
│ └─ RPS: 1초당 유입/처리된 API 요청│ └─ Wait Time: 큐 대기/Lock 경합 시간│
├───────────────────────────────────┼─────────────────────────────────────┤
│ [ 데이터 전송량 (Throughput) ]    │ [ 서비스 연속성 (Availability) ]     │
│ └─ 네트워크/디스크 초당 I/O 바이트│ └─ 가용성(%): MTBF / (MTBF + MTTR)  │
└───────────────────────────────────┴─────────────────────────────────────┘
                                     │ (통계적 집계 및 분포 분석)
                                     ▼
┌─────────────────────────────────────────────────────────────────────────┐
│ [ 3. 통계 분석 및 거버넌스 계층 (Statistical Distribution & SLA) ]      │
│  ├─ [ 백분위수 분석 ] ➔ p50(중앙값), p95, p99, p99.9 꼬리 지연 산출     │
│  └─ [ SLO / SLA 판정 ] ➔ 에러 예산 소진율 및 SLA 계약 위반 여부 실시간 평가│
└─────────────────────────────────────────────────────────────────────────┘
```

선의 의미: 부하 주입을 통해 처리 역량, 지연, 전송량, 가용성을 수집하고 통계 분석을 거쳐 SLA 목표 달성 여부를 판정하는 구조

| 성능 지표 | 핵심 정의 및 산출 공식 | 주요 측정 대상 | 평가 목적 |
|:---|:---|:---|:---|
| **TPS** | $\text{TPS} = \frac{\text{완료된 트랜잭션 수}}{\text{측정 시간(초)}}$ | 비즈니스 거래 (주문/결제) | 시스템의 최대 비즈니스 처리 용량 산정 |
| **응답시간** | $\text{Response Time} = \text{Wait Time} + \text{Service Time}$ | 클라이언트 왕복 시간 (RTT) | 사용자 체감 속도 및 병목(대기열) 파악 |
| **처리량** | $\text{Throughput} = \frac{\text{전송된 총 바이트 수}}{\text{측정 시간(초)}}$ | 네트워크 대역폭, 디스크 I/O | 인프라 전송 한계 및 I/O 병목 식별 |
| **가용성** | $\text{Availability} = \frac{\text{MTBF}}{\text{MTBF} + \text{MTTR}} \times 100\%$ | 연간/월간 무장애 가동 시간 | 시스템 무중단 신뢰성 및 비즈니스 연속성 평가 |
| **백분위수 지연** | $p99$: 전체 요청의 99%가 완료된 지연시간 임계치 | APM 트레이스 및 분산 추적 | 극단 꼬리 지연(Tail Latency) 및 GC/Lock 색출 |

#### 한줄 요약
- TPS, 응답시간(대기+서비스), 처리량(I/O), 가용성(MTBF/MTTR), 백분위수 지연으로 구성된다.

## Ⅳ. 흐름도

<details><summary>용어 설명</summary>

- **성능 측정 및 서비스 수준 평가 5단계 프로세스**:
  1. 성능 목표 정의 및 측정 기준(비즈니스 트랜잭션 vs API 호출) 확립
  2. 부하 발생기(JMeter)를 활용하여 목표 동시성 및 트래픽 부하 주입
  3. APM 및 모니터링 도구를 통해 처리량, 구간별 응답시간, 오류율 실시간 수집
  4. 수집된 데이터를 바탕으로 평균 및 p95/p99 백분위수 지연 분포 계산
  5. SLO 목표 대비 달성률 판정 및 포화점(Saturation Point) 도달 시 증설 계획 수립

</details>

```text
1. [성능 목표 및 기준 수립]
    ├─ 측정 대상: 쇼핑몰 결제 서비스
    └─ [목표 정의: 피크 시 5,000 TPS 수용, p99 응답시간 500ms 이하, 가용성 99.99%]
            │
            ▼
2. [부하 조건 주입 (Workload Injection)]
    ├─ 부하 발생기(JMeter/Locust)를 통해 가상 사용자(VUser) 10,000명 동시 접속
    └─ [초당 6,000건의 결제 트랜잭션 요청을 단계적(Ramp-up)으로 인입]
            │
            ▼
3. [구간별 지표 측정 및 APM 수집]
    ├─ Web/WAS/DB 계층별 처리 완료 건수 및 오류 건수(HTTP 5xx) 집계
    ├─ 트랜잭션별 네트워크 전송 지연(RTT), WAS 연산 시간, DB 락 대기시간 분리 기록
    └─ [시스템 자원 사용률(CPU, Memory, I/O) 동시 모니터링]
            │
            ▼
4. [통계 분석 및 꼬리 지연 산출]
    ├─ 평균 응답시간: 120ms (정상 수준으로 오판 위험)
    ├─ 백분위수 분석: p50 = 80ms, p95 = 250ms, p99 = 2,400ms (꼬리 지연 발생 확인)
    └─ [원인 분석: DB 커넥션 풀 고갈로 인한 1% 요청의 큐 대기 시간 폭증 식별]
            │
            ▼
5. [SLO 달성 평가 및 용량 증설 조치]
    ├─ [판정] p99 응답시간 기준(500ms) 초과로 SLO 위반 확정
    └─ [대책] DB 커넥션 풀 확장 및 캐시 계층(Redis) 증설 ➔ 재시험을 통해 5,000 TPS 안정화 달성
```

**동작 원리**

1. **리틀의 법칙(Little's Law) 적용**: 시스템 내 체류 작업 수($L$)는 유입률($\lambda$)과 체류 시간($W$)의 곱($L = \lambda W$)으로 결정되며, 처리량이 한계에 도달하면 응답시간이 지수적으로 급증
2. **포화점(Saturation Point) 조기 식별**: CPU 사용률 80% 이상 또는 큐 대기열 발생 시점을 포화점으로 정의하고 처리량 정체 구간 추적
3. **구간 분해(Latency Breakdown)**: 클라이언트 네트워크 지연, 웹서버 큐 대기, WAS 비즈니스 로직 연산, DB 쿼리 실행 시간을 분리 측정하여 병목 구간 국소화
4. **꼬리 지연 증폭 방지**: MSA 환경에서 100개 서비스가 직렬 호출될 때 개별 서비스의 p99 지연이 전체 트랜잭션의 63% 이상을 지연시키는 현상 선제 차단
5. **계약적 거버넌스 완성**: 객관적인 가용성($99.99\% \rightarrow$ 연간 허용 다운타임 52.6분) 수치를 바탕으로 비즈니스 연속성 SLA 준거성 확보

#### 한줄 요약
- 목표 수립, 부하 주입, 지표 수집, 백분위수 꼬리 지연 분석, SLO 판정 및 증설 조치 순으로 동작한다.

## Ⅴ. 종류 및 비교

<details><summary>용어 설명</summary>

- **성능 평가 지표 핵심 유형 비교**:
  - 처리량(Throughput/TPS): 시스템의 최대 용량 및 처리 역량 (시스템 관점).
  - 응답시간(Response Time/Latency): 개별 요청의 처리 지연 속도 (사용자 관점).
  - 가용성(Availability): 중단 없이 정상 서비스를 제공하는 비율 (비즈니스 관점).

</details>

| 비교 항목 | 처리량 / TPS (Capacity) | 응답시간 / 레이턴시 (Speed) | 가용성 / 신뢰성 (Reliability) |
|:---|:---|:---|:---|
| **평가 관점** | **시스템 처리 역량 (System-Centric)** | **사용자 체감 품질 (User-Centric)** | **비즈니스 연속성 (Business-Centric)** |
| **핵심 척도** | **TPS, RPS, bps (Bits per second)** | **평균 지연, p95/p99 백분위수** | **가용률(%), MTBF, MTTR, 결함률** |
| **측정 공식** | $\frac{\text{완료 트랜잭션}}{\text{시간(초)}}$ | $\text{Wait Time} + \text{Service Time}$ | $\frac{\text{MTBF}}{\text{MTBF} + \text{MTTR}} \times 100\%$ |
| **주요 한계점** | 지연 시간 및 오류율 은폐 가능 | **평균값 사용 시 꼬리 지연(p99) 누락**| 단기 측정 시 장기적 신뢰성 왜곡 |
| **병목 징후** | 부하 증가에도 TPS 수치 정체 (포화)| p95/p99 지연시간의 지수적 급증 | **MTTR 증가 및 에러 예산(Budget) 소진**|

#### 한줄 요약
- TPS는 시스템 용량, 응답시간은 사용자 체감 속도, 가용성은 서비스 연속성을 대변한다.

## Ⅵ. 실무 고려사항 및 대책

<details><summary>용어 설명</summary>

- **Google SRE 4대 황금 신호 (Golden Signals)**: 레이턴시(Latency), 트래픽(Traffic), 오류(Errors), 포화도(Saturation).

</details>

| 문제 | 대책 | 효과 |
|:---|:---|:---|
| 성능 시험 시 단순 HTTP API 호출(RPS)을 비즈니스 거래(TPS)와 혼용하여 **실제 DB 트랜잭션 부하를 과소평가하고 운영 배포 후 DB 다운 발생** | **비즈니스 거래(DB Commit 수반)와 단순 정적 리소스 호출(RPS)을 분리 측정하고, 트랜잭션별 가중치를 부여한 종합 TPS 산정** | 실제 운영 환경과 100% 일치하는 정확한 처리 용량 검증 |
| 평균 응답시간 지표만 모니터링하여 **상위 1% VIP 고객이 겪는 3초 이상의 꼬리 지연(Tail Latency)과 JVM GC 멈춤 현상을 감지하지 못함** | **p95, p99, p99.9 백분위수 레이턴시와 에러율을 필수 SLI로 등록하고, APM 분산 추적(Distributed Tracing) 기반 핫스폿 격리** | 상위 1% 극단 꼬리 지연 완벽 식별 및 서비스 품질 개선 |
| 가용성 99.9% 달성에도 불구하고 피크 시간대 특정 10분의 서비스 중단으로 인해 **치명적인 매출 손실 및 고객 이탈 피해 발생** | **연간 단순 평균 가용성 대신 피크 시간대 가중 가용성 및 에러 예산(Error Budget) 소진율 기반의 선제적 릴리스 통제 적용** | 비즈니스 핵심 시간대 무중단 연속성 100% 보장 |

#### 한줄 요약
- TPS/RPS 분리로 용량을 검증하고, 백분위수로 꼬리 지연을 잡으며, 에러 예산으로 가용성을 보장한다.

## Ⅶ. 결론

- 시스템의 기술적 성능과 비즈니스 성공을 보증하는 핵심 나침반인 **시스템 성능 지표 체계**는 단순한 모니터링 수치를 넘어 아키텍처 설계와 용량 증설의 객관적 기준선이며, 실무 구현 시 **비즈니스 트랜잭션(TPS)과 호출(RPS)의 엄격한 분리**, **평균의 함정을 탈피한 p95/p99 백분위수 꼬리 지연 분석**, **Google SRE 4대 황금 신호 기반의 포화도 추적**, **SLI/SLO/SLA 연계를 통한 에러 예산 거버넌스 확립**을 완성하여 최고 수준의 시스템 처리 성능과 무결점 비즈니스 연속성을 완성
