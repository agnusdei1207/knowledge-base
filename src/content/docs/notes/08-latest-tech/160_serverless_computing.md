## Ⅰ. 개요

<details><summary>용어 설명</summary>

- **서버리스 컴퓨팅(Serverless Computing)**: 클라우드 공급자가 서버 인프라 관리, 자동 확장, 용량 할당 및 사용량 계량을 전담하여, 사용자는 인프라 구성 없이 비즈니스 로직만 실행하는 클라우드 모델.
- **종량 과금(Pay-as-you-go)**: 고정 서버 비용이 아닌, 실제 함수 실행 횟수, 실행 시간, 자원 사용량을 기반으로 비용을 산정하는 과금 방식.

</details>

- 정의: 공급자가 인프라•확장•계량을 맡는 **서버리스 컴퓨팅**이다.
- 배경/필요성: 변동 워크로드에 최대치 기준 용량을 상시 확보하면 쓰지 않는 시간까지 **유휴 비용•패치 부담**을 계속 지불하므로, 실행 환경의 확보•축소와 운영 책임을 공급자 계층으로 넘겨 요청이 있는 구간만 과금되게 바꿀 필요

#### 한줄 요약

- 서버리스는 용량 계획과 패치 책임을 공급자에게 넘겨 **사용량 기반 과금**을 얻는 대신 실행 환경의 수명과 위치를 통제할 수 없게 되어, 콜드 스타트와 상태 외부화를 새 비용으로 떠안는다.

## Ⅱ. 특징

<details><summary>용어 설명</summary>

- **콜드 스타트(Cold Start)**: 실행 환경이 유휴 상태이거나 새 요청이 들어왔을 때, 런타임 초기화로 인해 발생하는 초기 지연 현상.
- **자동 회수(Auto-Scaling/Scale-to-Zero)**: 요청량 감소 시 클라우드 공급자가 실행 환경과 할당된 자원을 자동으로 축소하거나 0으로 회수하는 기능.
- **서비스형 함수(Function as a Service, FaaS)**: 특정 이벤트 트리거에 응답하여 사용자 정의 함수 코드를 서버리스 환경에서 실행하는 클라우드 서비스 유형.
- **서비스형 백엔드(Backend as a Service, BaaS)**: 인증, 데이터베이스, 스토리지 등 표준화된 백엔드 기능을 API 형태로 제공하는 서버리스 서비스 유형.

</details>

- 요청량 기반 **자동 할당•회수•계량**
- **FaaS•BaaS•서버리스 컨테이너** 조합
- 콜드 스타트•실행 제한•**공급자 종속**

#### 한줄 요약

- 실행 환경을 언제든 회수 가능하게 만든 대가가 콜드 스타트와 **영속 상태의 외부 저장**이므로, 서버리스의 제약 대부분은 확장 자유를 얻으려 상태 보유를 포기한 결과다.

## Ⅲ. 구조 및 구성요소

<details><summary>용어 설명</summary>

- **이벤트 소스(Event Source)**: HTTP 요청, 메시지 큐, 타이머 등 서버리스 로직의 실행을 트리거하는 입력원.
- **실행 및 확장 계층(Execution & Scaling Layer)**: 요청량을 모니터링하여 격리된 실행 환경을 동적으로 할당, 재사용, 회수하는 공급자 관리 계층.
- **함수 및 코드(Function & Code)**: 이벤트에 대응하여 비즈니스 로직을 수행하는 실행 단위.
- **관리형 서비스 백엔드(Managed Backend Services)**: 클라우드 공급자가 운영하는 인증, 데이터베이스, 스토리지 등의 인프라 서비스.
- **외부 상태 관리(External State Management)**: 인스턴스 생명주기와 분리하여 DB, 객체 스토리지 등에 지속적으로 보관하는 업무 상태 데이터.
- **데이터베이스(Database, DB)**: 구조화된 데이터를 영속적으로 저장하고 쿼리하기 위한 시스템.

</details>

```text
 [이벤트•요청] ----- [실행•확장] ----- [함수•코드]
                                             /      \
                                [서비스 백엔드]   [외부 상태•운영]
```

| 구성요소 | 책임 |
|:---|:---|
| 이벤트•요청 | **웹•메시지•일정 실행** 개시 |
| 실행•확장 | **격리 환경•인스턴스 자동 조정** |
| 함수•코드 | **입력 처리•후속 이벤트** 생성 |
| 서비스 백엔드 | **인증•DB 완성 기능** 제공 |
| 외부 상태•운영 | **영속 상태•사용량 계량** 관리 |

#### 한줄 요약

- 이벤트•실행•함수•백엔드•**외부 상태 운영** 구조

## Ⅳ. 흐름도

<details><summary>용어 설명</summary>

- **실행 환경 재사용**: 이전 호출에서 준비한 런타임과 코드를 다음 요청 처리에 활용하는 방식을 의미한다.
- **관리형 서비스**: 공급자가 배포•패치•확장•가용성을 운영하고 사용자는 응용 프로그래밍 인터페이스로 소비하는 기능을 말한다.
- **응용 프로그래밍 인터페이스(Application Programming Interface, API)**: 소프트웨어 기능을 정해진 요청•응답 규격으로 호출하는 접점이다.

</details>

```text
이벤트 소스 ── 인증된 이벤트 ──▶ 실행•확장 계층
실행•확장 계층 ── 1. 재사용•신규 환경 전달 ──▶ 함수•코드
함수•코드 ── 2. 백엔드 기능 요청 ──▶ 서비스 백엔드
함수•코드 ◀── 관리형 서비스 결과 ─── 서비스 백엔드
함수•코드 ── 3. 외부 상태•사용량 전달 ──▶ 외부 상태•운영
함수•코드 ◀── 저장•계량 결과 ───────── 외부 상태•운영
이벤트 소스 ◀── 응답•후속 이벤트 ───── 함수•코드
```

### 동작 원리

1. 재사용•신규 환경 전달: 준비 환경 선택 또는 **콜드 스타트**
2. 백엔드 기능 요청: 인증•DB **API** 기반 관리형 서비스 호출
3. 외부 상태•사용량 전달: **영속 상태 분리•실행 자원** 계량

#### 한줄 요약

- 실행 환경을 선택하고 **백엔드•외부 상태** 호출

## Ⅴ. 종류 및 비교

<details><summary>용어 설명</summary>

- **서버리스 컨테이너**: 사용자 컨테이너 이미지를 요청이나 작업량에 따라 자동 확장하는 서버리스 유형이다.

</details>

| 서버리스 유형 | 서비스형 함수 | 서비스형 백엔드 | 서버리스 컨테이너 |
|:---|:---|:---|:---|
| 적용 기준 | **짧고 독립적인 이벤트** | **공통 백엔드 기능 활용** | **사용자 런타임•이미지 필요** |
| 핵심 특징 | **함수 단위 실행•자동 확장** | **완성 기능 API 소비** | **컨테이너 단위 자동 확장** |
| 한계 | **실행 시간•환경 제약** | **공급자 기능•정책 종속** | **큰 시작•운영 비용** |

#### 한줄 요약

- 세 방식은 같은 유휴 비용 문제를 공급자에게 넘기는 책임의 크기만 달리해 푸는 것이므로, 위임 범위가 클수록 **관리 단위**는 작아지고 이식성은 함께 나빠진다.

## Ⅵ. 실무 고려사항 및 대책

<details><summary>용어 설명</summary>

- **사전 준비 인스턴스**: 첫 요청 지연을 줄이기 위해 실행 환경을 미리 초기화해 유지한 자원을 의미한다.
- **멱등 처리**: 같은 이벤트가 반복 전달되어도 최종 상태가 한 번 처리한 것과 같도록 만드는 방식이다.

</details>

| 문제 | 대책 | 효과 |
|:---|:---|:---|
| 신규 환경 초기화로 **콜드 스타트 지연** | **사전 준비 인스턴스•패키지 경량화** | 첫 요청 **응답 지연 감소** |
| 함수 내부 상태 의존으로 **확장 정합성** 훼손 | **상태 외부화•멱등 이벤트 처리** | 병렬 실행 **상태 일관성** 확보 |

#### 한줄 요약

- 지연 민감 함수는 사전 준비하고 **상태 외부화•멱등 처리**

## Ⅶ. 결론

<details><summary>용어 설명</summary>

- **변동 워크로드**: 시간에 따라 요청량이 크게 달라져 고정 용량의 유휴나 부족이 발생하는 작업을 의미한다.
- **공급자 종속**: 특정 클라우드의 실행 제약•이벤트•API에 의존해 이전 비용이 커지는 상태로 정의된다.

</details>

- 짧은 이벤트는 **FaaS**, 완성 백엔드는 **BaaS** 선택

#### 한줄 요약

- 서버리스는 유휴 용량 비용을 콜드 스타트 지연과 **공급자 종속**으로 바꾼 거래이므로, 요청 변동 폭이 클수록 이득이 커지고 상시 부하에 가까울수록 전용 용량이 유리해진다.
