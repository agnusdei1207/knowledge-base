## 미리 알고가기

- **사이드카 프록시**: 애플리케이션 옆에서 통신 대행하는 보조 프록시임
- **Service Mesh**: 서비스 메시의 데이터 플레인 기본 단위로 사용함
- **핵심 트레이드오프**: 코드 변경 없는 기능 적용과 자원 오버헤드임



## Ⅰ. 개요

- **정의/개념**: 앱 옆 프록시가 통신 기능을 대행
- **배경/필요성**: 통신 정책을 앱 코드 밖에서 집행

### 쉽게 이해하기 (학습용)

- 앱 옆 보조 프록시가 모든 통신을 대신 처리하는 배치 방식이다.

## Ⅱ. 특징

- 앱·프록시는 네트워크를 공유하고 따로 실행된다
- 로컬 프록시가 검색·보안·재시도·관측을 적용한다
- 제어 평면은 정책, 프록시는 요청을 처리한다
- 프록시 추가는 자원·시작·버전 관리를 늘린다
- 프록시 장애는 앱 통신 경로의 장애로 이어진다

### 쉽게 이해하기 (학습용)

- 앱마다 통신 비서를 두면 정밀하지만 자원과 장애 경로도 늘어난다.

## Ⅲ. 아키텍처 및 구성요소

```text
[제어 평면]
      ↓
[Pod: 앱 ↔ 프록시] → [서비스]
```

| 설계 요소 | 설명 |
|:---|:---|
| 애플리케이션 | 업무 로직·로컬 요청 생성 |
| 프록시 | 통신 중계·정책 집행 |
| 가로채기 | 앱 트래픽을 프록시로 우회 |
| 제어 평면 | 정책·경로·인증서 배포 |
| 수명 관리 | 시작·종료·자원 제한 조정 |
| 수집기 | 지표·로그·추적 수집 |

> 요약: 앱 트래픽을 프록시로 우회해 공통 정책을 집행한다

### 쉽게 이해하기 (학습용)

- 제어 평면이 규칙을 주면 프록시가 통신을 중계하고 기록한다.

## Ⅳ. 원리 및 절차 흐름도

```text
주입배포
    ↓
프록시준비
    ↓
트래픽우회
    ↓
정책집행
```

| 절차 | 설명 |
|:---|:---|
| 주입·배포 | 앱과 같은 Pod에 프록시 배치 |
| 준비 확인 | 설정·인증서·포트 확인 |
| 트래픽 우회 | 인바운드·아웃바운드 가로채기 |
| 정책·전달 | 신원·경로·복원력 정책 적용 |
| 측정·갱신 | 지표 수집·구성 점진 배포 |

> 요약: 프록시 준비 뒤 트래픽을 우회해 정책을 집행한다

### 쉽게 이해하기 (학습용)

- 프록시를 먼저 준비한 뒤 통신을 맡기고 기록과 정책을 갱신한다.

## Ⅴ. 종류 및 비교

| 판단 기준 | 사이드카 프록시 | 노드 공유 프록시 | 내장 통신 라이브러리 |
|:---|:---|:---|:---|
| 배치·수명 | 워크로드별 Pod | 노드별 공용 프로세스 | 앱 빌드·배포 포함 |
| 정책·격리 | 워크로드별 세밀 제어 | 노드 공유 경로 | 호출 코드별 제어 |
| 선택 조건 | 코드 독립·정밀 정책 | 프록시 자원 절감 | 적은 자원·직접 제어 |

> 요약: 격리 정밀도·자원·코드 결합도로 배치 방식을 고른다

### 쉽게 이해하기 (학습용)

- 개인 비서와 공용 안내원, 직접 처리 중 정밀도와 비용으로 고른다.

## Ⅵ. 실무 사례

1. Istio는 Envoy로 서비스 통신을 중계한다
2. 구형 앱에 보안 프록시로 상호 인증을 붙인다

### 쉽게 이해하기 (학습용)

- Envoy가 앱 코드 밖에서 라우팅·보안 정책을 공통 적용한다.
- 구형 앱도 로컬 프록시를 통해 인증서 교체와 상호 인증을 쓴다.

## Ⅶ. 결론

- 정책 정밀도와 프록시 자원 비용을 함께 판단한다.

### 쉽게 이해하기 (학습용)

- 정밀 정책 이득과 프록시 자원·장애 비용을 함께 판단해야 한다.
