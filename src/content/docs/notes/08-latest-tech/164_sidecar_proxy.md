## Ⅰ. 개요

<details><summary>용어 설명</summary>

- **사이드카 프록시(Sidecar Proxy)**: 애플리케이션과 같은 배포 단위에서 인바운드•아웃바운드 통신 정책을 대신 집행하는 보조 프록시을 말한다.
- **사이드카 패턴**: 주 애플리케이션과 수명 주기•배포 경계를 공유하는 보조 프로세스로 공통 기능을 분리하는 패턴이다.

</details>

- 정의: 애플리케이션 옆에서 통신 정책을 집행하는 **사이드카 프록시**
- 배경/필요성: 다국어(Polyglot) 기반 마이크로서비스 환경에서 각 애플리케이션 코드에 mTLS, 서킷브레이커, 로깅/트레이싱 라이브러리를 직접 내장할 경우 언어/프레임워크별 버전 파편화, 비즈니스 로직과 통신 인프라 간의 강한 결합, 인프라 변경 시 전체 애플리케이션 재빌드/재배포가 불가피한 아키텍처 결함에 직면함에 따라, 주 애플리케이션 컨테이너와 동일한 네트워크 네임스페이스(Pod/Localhost)를 공유하는 독립 프로세스 프록시를 동반 배치하여 인바운드/아웃바운드 트래픽을 투명하게 가로채고 통신 정책을 일괄 집행하는 사이드카 프록시(Sidecar Proxy / Envoy Proxy, Linkerd-proxy, iptables/eBPF Traffic Interception, Localhost Shared Network, Independent Lifecycle, Dynamic xDS Configuration) 패턴을 도입하여 **애플리케이션 코드 수정 제로(Zero Code Modification)로 보안(mTLS) 및 트래픽 제어(L7 Routing, Retries, Timeouts) 정책 전사 동기화, 워크로드 단위의 엄격한 자원 격리 및 독립적인 프록시 런타임 업그레이드 지원, 표준화된 분산 추적(Trace Context Propagation) 및 실시간 메트릭 자동 추출**을 달성할 필요

#### 한줄 요약

- 사이드카는 통신 정책을 **별도 프로세스**로 밀어내 언어 종속을 끊는 대신 워크로드마다 프록시를 하나씩 더 띄우므로, 격리를 상시 자원과 추가 홉으로 지불한다.

## Ⅱ. 특징

<details><summary>용어 설명</summary>

- **데이터 평면**: 실제 서비스 요청을 중계하면서 라우팅•보안•관측 정책을 집행하는 계층이다.
- **워크로드 격리**: 각 애플리케이션에 별도 프록시를 배치해 정책•자원•장애 영향을 분리하는 특성로 정의된다.

</details>

- 주 애플리케이션과 배포 경계를 공유하는 **사이드카 패턴**
- 제어 평면 구성을 받아 **데이터 평면 정책 집행**
- 워크로드별 격리와 **자원•기동•장애 경로 증가**

#### 한줄 요약

- 워크로드 단위 격리를 얻은 대가로 **프록시 자원•장애 경로 증가**를 함께 떠안으므로, 인스턴스 수가 많아질수록 격리 이득보다 상시 자원 비용이 먼저 드러난다.

## Ⅲ. 구조 및 구성요소

<details><summary>용어 설명</summary>

- **트래픽 전환 규칙**: 인바운드•아웃바운드 요청을 프록시 경로로 전환하는 네트워크 규칙로 정의된다.
- **제어 평면(Control Plane)**: 라우팅•인증서•보안•복원력 정책을 계산해 각 사이드카 프록시에 배포하는 개념을 의미한다.
- **사이드카 정책 집행**: 애플리케이션 옆에서 서비스 트래픽을 중계하고 통신 정책을 적용하는 개념이다.
- **애플리케이션**: 업무 로직을 수행하고 서비스 요청을 생성하는 주 프로세스이다.
- **관측 파이프라인**: 프록시에서 생성한 지표•로그•추적을 수집•전송•저장하는 처리 경로을 말한다.

</details>

```text
             [제어 평면]
                  |
         [트래픽 전환 규칙]
                  |
           [사이드카 프록시]
                  |
        +---------+---------+
        |                   |
 [애플리케이션]       [관측 파이프라인]
```

선의 의미: 제어 평면과 트래픽 전환 규칙이 사이드카 프록시의 통신 경계를 구성하고, 프록시는 애플리케이션 및 관측 파이프라인과 결합된다.

| 구성요소 | 책임 |
|:---|:---|
| 제어 평면 | **경로•보안•복원력 정책** 배포 |
| 트래픽 전환 규칙 | **인바운드•아웃바운드 요청** 포착 |
| 사이드카 프록시 | **요청 중계•통신 정책** 집행 |
| 애플리케이션 | **업무 로직•요청 생성** 수행 |
| 관측 파이프라인 | **지표•로그•추적** 수집 |

#### 한줄 요약

- 애플리케이션 통신의 **프록시 경유•정책 관측** 구조

## Ⅳ. 흐름도

<details><summary>용어 설명</summary>

- **상호 전송 계층 보안(mutual Transport Layer Security, mTLS)**: 통신 양쪽이 인증서를 검증하고 전송 구간을 암호화하는 방식이다.
- **시간 제한(Timeout)**: 호출이 정한 시간 안에 끝나지 않으면 실패로 중단하는 복원력 정책을 말한다.

</details>

```text
제어 평면 ── 1. 통신 정책 배포 ──▶ 사이드카 프록시
애플리케이션 ── 요청 경로 전환 ──▶ 사이드카 프록시
사이드카 프록시 ── 2. 보안•라우팅 집행 ──▶ 대상 서비스
사이드카 프록시 ◀── 서비스 응답 ───────── 대상 서비스
애플리케이션 ◀── 처리 결과 ───────────── 사이드카 프록시
```

### 동작 원리

1. 통신 정책 배포: **경로•인증•재시도 구성** 전달
2. 보안•라우팅 집행: **mTLS 신원•목적지•시간 제한** 적용

#### 한줄 요약

- 사이드카의 **신원 확인•경로 제어•결과 전달**

## Ⅴ. 종류 및 비교

<details><summary>용어 설명</summary>

- **노드 공유 프록시**: 한 노드의 여러 워크로드가 공통으로 사용하는 통신 프록시로 정의된다.
- **애플리케이션 라이브러리**: 업무 프로세스 안에 포함되어 호출 제어와 보안 기능을 실행하는 코드을 의미한다.

</details>

| 통신 기능 배치 | 사이드카 프록시 | 노드 공유 프록시 | 애플리케이션 라이브러리 |
|:---|:---|:---|:---|
| 적용 기준 | 워크로드별 **세밀한 격리** | 노드 단위 **자원 절감** | **단순•단일 언어** 환경 |
| 핵심 특징 | 파드별 **독립 프록시** | 여러 워크로드의 **프록시 공유** | 업무 프로세스 내부 **호출 제어** |
| 한계 | **자원•기동•장애 경로** 증가 | **공유 장애•격리 제약** | **언어 결합•일관성 부담** |

#### 한줄 요약

- **통신 기능 배치 선택**은 프록시를 프로세스 안•옆•노드 중 어디에 둘지의 문제이며, 애플리케이션에서 멀어질수록 자원 비용은 싸지고 워크로드별 격리는 그만큼 약해진다.

## Ⅵ. 실무 고려사항 및 대책

<details><summary>용어 설명</summary>

- **준비 상태(readiness)**: 프록시가 요청을 안전하게 중계할 준비가 되었는지 나타내는 상태 조건을 의미한다.
- **책임 단일화**: 재시도•시간 제한 같은 정책을 애플리케이션과 프록시 중 한 계층만 맡게 하는 설계로 정의된다.
- **중앙처리장치(Central Processing Unit, CPU)**: 명령 해석과 범용 연산을 수행하는 프로세서을 의미한다.
- **메모리 부족(Out of Memory, OOM)**: 필요한 메모리를 확보하지 못해 할당이나 프로세스 실행이 실패한 상태로 정의된다.

</details>

| 문제 | 대책 | 효과 |
|:---|:---|:---|
| **프록시 준비 전 요청 유입** | 시작•준비•종료 순서와 **준비 상태 연동** | **초기 연결 실패** 방지 |
| **재시도•시간 제한 중복** | 애플리케이션과 프록시의 **책임 단일화** | **요청 증폭•긴 대기** 방지 |
| **사이드카 자원 부족** | 워크로드별 **CPU•메모리•연결 수** 산정 | **지연 증가•OOM** 완화 |

#### 한줄 요약

- 준비 상태 연동과 **재시도 책임 단일화**로 요청 증폭 방지

## Ⅶ. 결론

<details><summary>용어 설명</summary>

- **장애 경로**: 요청 처리 과정에서 실패하거나 지연될 수 있는 추가 구성요소와 연결 단계로 정의된다.
- **자원 오버헤드**: 워크로드마다 프록시를 추가하며 발생하는 중앙처리장치•메모리•연결 비용을 말한다.

</details>

- 마이크로서비스 인프라의 관심사 분리(Separation of Concerns)와 제로 트러스트 데이터 평면을 실현한 **컨테이너 보조 프록시 아키텍처의 핵심 디자인 패턴(Sidecar Proxy Pattern / Envoy Proxy / Localhost Interception via iptables & eBPF / Independent Lifecycle & Failure Domain / L4-L7 Traffic Governance)의 확고한 표준**으로 확고히 자리 잡았으며, 노드당 메모리/CPU 낭비를 줄이기 위한 사이드카리스(Ambient/eBPF) 아키텍처와 상호보완적으로 발전하는 가운데, 실무 사이드카 기반 시스템 운영 시에는 **Pod 기동 시 사이드카 초기화 완료 후 메인 컨테이너가 실행되도록 Startup Probe/InitContainer 라이프사이클을 엄격히 동기화하고, 프록시 전용 CPU/Memory Request-Limit 튜닝 및 애플리케이션-사이드카 간 중복 타임아웃/재시도 정책 단일화**를 결합하여 완벽한 통신 신뢰성과 운영 안정성을 완성

#### 한줄 요약

- 격리 이익이 자원•장애 경로 비용보다 클 때 **사이드카 적용**
