## 미리 알고가기

- **Service Mesh**: 코드 밖 인프라에서 서비스 간 통신 제어
- **트래픽 제어**: 트래픽·보안·관측성을 일관되게 적용함
- **API Gateway**: 동서 트래픽 제어와 남북 트래픽 제어의 구분 필요



## Ⅰ. 개요

- **정의/개념**: 서비스 통신 정책·관측 인프라 계층
- **배경/필요성**: 통신 기능의 코드 분리·일관된 집행

### 쉽게 이해하기 (학습용)

- 공용 도로망이 서비스의 신원·경로·운행 규칙을 통제하는 구조다.

## Ⅱ. 특징

- 프록시가 서비스 검색·부하 분산·연결을 중계한다
- 선언 정책이 라우팅·재시도·차단을 바꾼다
- 워크로드 신원으로 mTLS·인가를 적용한다
- 통신 경로에서 지연·오류·추적을 수집한다
- 업무 보상·정합성은 애플리케이션이 처리한다

### 쉽게 이해하기 (학습용)

- 메시가 통신을 통제해도 업무 보상과 데이터 정합성은 앱이 맡는다.

## Ⅲ. 아키텍처 및 구성요소

```text
[제어 평면] → 정책·인증서
                  ↓
[서비스] ↔ [데이터 평면] ↔ [서비스]
```

| 설계 요소 | 설명 |
|:---|:---|
| 서비스 검색 | 서비스와 엔드포인트 연결 |
| 데이터 평면 | 요청 중계·통신 정책 집행 |
| 제어 평면 | 정책·인증서·구성 배포 |
| 보안 정책 | 인증·인가·암호화 정의 |
| 관측·거버넌스 | 통신 지표·정책 이력 관리 |

> 요약: 제어 평면이 정책을 배포하고 데이터 평면이 집행한다

### 쉽게 이해하기 (학습용)

- 제어 평면은 관제소이고 데이터 평면은 현장의 도로와 신호등이다.

## Ⅳ. 원리 및 절차 흐름도

```text
정책선언
    ↓
구성배포
    ↓
요청집행
    ↓
관측조정
```

| 절차 | 설명 |
|:---|:---|
| 서비스 발견 | 서비스·신원·경계 수집 |
| 정책 선언 | 경로·복원력·보안 규칙 정의 |
| 충돌 검증 | 중복·증폭·인증 불일치 검사 |
| 구성 배포 | 실행 구성·인증서 전달 |
| 요청 집행 | 신원 확인·통신 정책 적용 |
| 관측·조정 | 지표로 정책 조정·복구 |

> 요약: 정책을 검증·배포하고 지표로 조정한다

### 쉽게 이해하기 (학습용)

- 규칙 배포 뒤 실제 흐름과 오류를 보고 정책을 다시 조정한다.

## Ⅴ. 종류 및 비교

| 판단 기준 | 서비스 메시 | API 게이트웨이 | 클라이언트 라이브러리 |
|:---|:---|:---|:---|
| 주 통신 범위 | 서비스 간 동서 트래픽 | 외부 남북 트래픽 | 앱이 시작한 호출 |
| 정책 집행 위치 | 분산 데이터 평면 | 중앙 진입 경계 | 서비스 내부 코드 |
| 적용 기준 | 다언어 공통 통신 정책 | 외부 API 관리 | 소규모 단일 언어 |

> 요약: 메시·게이트웨이·라이브러리는 집행 경계가 다르다

### 쉽게 이해하기 (학습용)

- 게이트웨이는 정문, 메시는 내부 도로, 라이브러리는 차량 규칙이다.

## Ⅵ. 실무 사례

1. 결제 호출에 워크로드 신원 인가를 적용한다
2. 오류율에 따라 카나리 경로를 롤백한다

### 쉽게 이해하기 (학습용)

- 주문 서비스만 결제 승인 경로를 쓰게 하고 거부 지표를 감사한다.
- 신규 버전 비율을 높이다 오류 임계치를 넘으면 기존 경로로 돌린다.

## Ⅶ. 결론

- 공통 정책 이득이 프록시·운영 비용보다 클 때 도입한다.

### 쉽게 이해하기 (학습용)

- 메시 도입 전 정책 책임과 장애 시 복구 기준을 함께 정해야 한다.
