## 미리 알고가기

- **서비스 메시(Service Mesh)**: 애플리케이션 코드 밖의 데이터 평면에서 서비스 간 통신을 제어하는 인프라 계층
- **mTLS(엠티엘에스)**: Mutual TLS의 약자로, 통신 양쪽의 신원을 인증하고 구간을 암호화
- **동서·남북 트래픽**: 내부 서비스 간 흐름은 동서, 외부와 시스템 경계를 오가는 흐름은 남북으로 표기



## Ⅰ. 개요

- 정의/개념: 서비스 간 통신의 라우팅·보안·관측 정책을 인프라 계층에서 집행하는 구조다
- 기존 한계: 각 서비스가 통신 기능을 직접 구현하면 언어·팀별 정책이 달라지고 변경과 감사가 어렵다
- **배경/필요성**: 공통 통신 정책을 애플리케이션 코드와 분리해 일관되게 적용하기 위함이다

### 쉽게 이해하기 (학습용)

- 공용 도로망이 서비스의 신원·경로·운행 규칙을 통제하는 구조다.

## Ⅱ. 특징

- 데이터 평면이 서비스 간 요청의 라우팅·보안 정책을 집행한다
- 제어 평면이 서비스 정보·정책·인증서를 데이터 평면에 배포한다
- 공통 통신 제어를 제공하지만 업무 정합성은 애플리케이션이 담당한다

### 쉽게 이해하기 (학습용)

- 메시가 통신을 통제해도 업무 보상과 데이터 정합성은 앱이 맡는다.

## Ⅲ. 아키텍처 및 구성요소

```text
[제어 평면] → 정책·인증서
                  ↓
[서비스] ↔ [데이터 평면] ↔ [서비스]
```

| 설계 요소 | 설명 |
|:---|:---|
| 서비스 검색 | 서비스와 엔드포인트 연결 |
| 데이터 평면 | 요청 중계·통신 정책 집행 |
| 제어 평면 | 정책·인증서·구성 배포 |
| 보안 정책 | 인증·인가·암호화 정의 |
| 관측·거버넌스 | 통신 지표·정책 이력 관리 |

> 요약: 제어 평면이 정책을 배포하고 데이터 평면이 집행한다

### 쉽게 이해하기 (학습용)

- 제어 평면은 관제소이고 데이터 평면은 현장의 도로와 신호등이다.

## Ⅳ. 원리 및 절차 흐름도

```text
정책선언
    ↓
구성배포
    ↓
요청집행
    ↓
관측조정
```

| 절차 | 설명 |
|:---|:---|
| 서비스 발견 | 서비스·신원·경계 수집 |
| 정책 선언 | 경로·복원력·보안 규칙 정의 |
| 충돌 검증 | 중복·증폭·인증 불일치 검사 |
| 구성 배포 | 실행 구성·인증서 전달 |
| 요청 집행 | 신원 확인·통신 정책 적용 |
| 관측·조정 | 지표로 정책 조정·복구 |

> 요약: 정책을 검증·배포하고 지표로 조정한다

### 쉽게 이해하기 (학습용)

- 규칙 배포 뒤 실제 흐름과 오류를 보고 정책을 다시 조정한다.

## Ⅴ. 종류 및 비교

| 판단 기준 | 서비스 메시 | API 게이트웨이 | 클라이언트 라이브러리 |
|:---|:---|:---|:---|
| 적용 기준 | 내부 서비스 공통 정책 | 외부 API 진입 통제 | 소규모·단일 언어 환경 |
| 핵심 특징 | 분산 데이터 평면에서 집행 | 중앙 경계에서 남북 트래픽 집행 | 애플리케이션 코드에서 호출 제어 |
| 한계 | 프록시 지연과 운영 복잡도 | 내부 동서 트래픽 통제 제한 | 언어 종속과 정책 불일치 |

> 요약: 메시·게이트웨이·라이브러리는 집행 경계가 다르다

### 쉽게 이해하기 (학습용)

- 게이트웨이는 정문, 메시는 내부 도로, 라이브러리는 차량 규칙이다.

## Ⅵ. 실무 사례

1. 결제 호출에 워크로드 신원 인가를 적용한다

### 쉽게 이해하기 (학습용)

- 주문 서비스만 결제 승인 경로를 쓰게 하고 거부 지표를 감사한다.

## Ⅶ. 결론

- 서비스 간 통신 보안과 정책을 일관되게 적용하기 위해 **워크로드 신원·인가·관측·프록시 자원·운영 복잡도**를 검토하고, 공통 정책 편익이 비용보다 클 때 서비스 메시를 도입한다.

### 쉽게 이해하기 (학습용)

- 메시 도입 전 정책 책임과 장애 시 복구 기준을 함께 정해야 한다.
