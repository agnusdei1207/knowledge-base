## 미리 알고가기

- **오픈 테이블 포맷(Open Table Format)**: '오픈 테이블 포맷'으로 읽으며, 객체 저장소의 파일을 논리 테이블로 관리하는 공개 메타데이터 규격
- **스냅샷(Snapshot)**: 특정 시점의 유효한 데이터 파일 집합과 테이블 상태
- **원자성·일관성·격리성·지속성(Atomicity, Consistency, Isolation, Durability, ACID)**: '에이시드'로 읽으며, 트랜잭션이 안전하게 완료되기 위한 성질
- **표기 이유**: '오픈'은 데이터 파일 형식이 아니라 **테이블 메타데이터·커밋 규칙을 여러 엔진에 공개**한다는 의미
- **대표 형식**: Delta Lake, Apache Iceberg, Apache Hudi

## Ⅰ. 개요

- 정의/개념: 객체 저장소의 데이터 파일 위에 **스키마·파티션·스냅샷·원자 커밋 규칙을 제공하는 테이블 계층**
- 배경/필요성: 단순 파일 저장은 동시 쓰기 충돌을 방지하고 일관된 버전 조회와 스키마 변경을 관리하기 어렵다.

### 쉽게 이해하기 (학습용)

- 데이터 파일 자체가 책의 쪽이라면, 오픈 테이블 포맷은 유효한 쪽과 현재 판본을 정하는 공개 목차·개정 규칙이다.

## Ⅱ. 특징

- **1. 스키마·파티션·파일 통계와 유효 파일 집합**: 메타데이터가 스키마·파티션·파일 통계와 유효 파일 집합을 관리한다.
- **2. 일관된 읽기와 동시 쓰기 충돌 검증**: 스냅샷과 원자 커밋으로 일관된 읽기와 동시 쓰기 충돌 검증을 제공한다.
- **3. 형식·버전·기능별 호환성 확인이 필요**: 공개 규격으로 다중 엔진 접근을 지원하지만 형식·버전·기능별 호환성 확인이 필요하다.
### 쉽게 이해하기 (학습용)

- 완성된 판본만 공개해 읽는 도중 내용이 섞이지 않게 하며, 도구마다 지원하는 개정 기능은 따로 확인해야 한다.

## Ⅲ. 구조 및 구성요소

```mermaid
block-beta
  columns 3
  N0["질의·처리 엔진"]
  N1["포맷 커넥터"]
  N2["카탈로그·커밋"]
  N3["스냅샷·테이블 메타데이터"]
  N4["데이터·삭제 파일"]
  N0 --- N1 --- N2
  N2 --- N3 --- N4
```

| 구성요소 | 책임 |
|:---|:---|
| 질의·처리 엔진 | 논리 질의·변경 요청과 결과 처리 |
| 포맷 커넥터 | 형식별 읽기·쓰기·계획 수행 |
| 카탈로그·커밋 | 테이블 식별·새 상태 원자 게시 |
| 스냅샷·테이블 메타데이터 | 스키마·파티션·통계·유효 파일 집합 관리 |
| 데이터·삭제 파일 | **행 데이터와 변경 정보 저장** |

### 쉽게 이해하기 (학습용)

- 처리 엔진은 카탈로그가 가리키는 확정 스냅샷을 읽어 같은 테이블 상태를 본다.

## Ⅳ. 흐름도

```mermaid
sequenceDiagram
  participant E as 처리 엔진
  participant C as 포맷 커넥터
  participant F as 데이터·삭제 파일
  participant M as 테이블 메타데이터
  participant A as 카탈로그·커밋
  E->>C: 1. 기준 스냅샷 읽기
  C->>F: 2. 새 파일 작성
  C->>M: 3. 변경 메타데이터 작성
  M->>A: 4. 충돌 검증·원자 커밋
  A-->>E: 5. 새 스냅샷 공개
```

**동작 원리**

- **1. 기준 스냅샷 읽기**: 현재 버전과 유효 파일 집합 확인
- **2. 새 파일 작성**: 변경 데이터를 불변 파일로 준비
- **3. 변경 메타데이터 작성**: 스키마·파티션·파일 통계와 새 상태 연결
- **4. 충돌 검증·원자 커밋**: 동시 변경을 확인하고 새 포인터 게시
- **5. 새 스냅샷 공개**: 모든 엔진이 확정된 파일 집합 조회

### 쉽게 이해하기 (학습용)

- 새 판본을 완성한 뒤 다른 편집과 충돌하지 않는지 확인하고 공식 판본 번호를 붙인다.

## Ⅴ. 종류 및 비교

| 오픈 테이블 포맷 | Delta Lake | Apache Iceberg | Apache Hudi |
|:---|:---|:---|:---|
| 적용 기준 | 배치·스트림 통합 처리 | 다중 엔진·대규모 분석 | 업서트·증분 처리 중심 |
| 핵심 특징 | 트랜잭션 로그·체크포인트 | 스냅샷·매니페스트 트리 | 타임라인·파일 그룹 |
| 한계 | 기능별 엔진 호환 확인 | 카탈로그·기능 지원 확인 | 테이블 유형 운영 복잡 |

### 쉽게 이해하기 (학습용)

- 모두 공개 테이블 규칙이지만 판본 관리와 변경 처리 구조가 달라 엔진 호환성을 검증해야 한다.

## Ⅵ. 실무 고려사항 및 대책

| 고려사항 | 대책 | 효과 |
|:---|:---|:---|
| 엔진별 포맷 기능 지원 차이 | 읽기·쓰기·삭제·진화 호환 행렬 관리 | 교차 엔진 오류 방지 |
| 카탈로그 장애·원자성 약화 | 고가용 카탈로그·커밋 재시도·감사 | 테이블 포인터 일관성 확보 |
| 스냅샷·작은 파일 누적 | 보존·압축·정리 작업 자동화 | 조회 성능과 저장비 안정화 |

### 쉽게 이해하기 (학습용)

- Spark와 Trino가 같은 테이블을 공유할 때 읽기뿐 아니라 쓰기·삭제·스키마 진화를 교차 검증한다.

## Ⅶ. 결론

- 다중 엔진의 테이블 변경을 일관되게 처리하기 위해 **커밋 원자성·기능 호환성·카탈로그 가용성·스냅샷·파일 유지관리**를 검토해 오픈 테이블 포맷을 선택한다.

### 쉽게 이해하기 (학습용)

- 오픈 테이블 포맷은 공개 규격 여부보다 실제 엔진의 읽기·쓰기 호환성이 중요하다.
