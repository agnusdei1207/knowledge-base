## Ⅰ. 개요

<details>
<summary>핵심 용어</summary>

- **모델 컨텍스트 프로토콜(Model Context Protocol, MCP)**: AI 호스트와 외부 서버 간 도구·리소스·프롬프트 발견 및 교환을 표준화한 연결 프로토콜. 시스템의 자율적 기능 발견과 일관된 상호작용을 매개하는 핵심 아키텍처.

</details>

- 개념: AI 호스트와 서버가 기능을 교환하는 **JSON-RPC 프로토콜**
- 배경: 맞춤 연동은 **기능 발견•메시지 처리 중복** 유발

#### 한줄 요약
- **MCP** 공통 메시지•기능 발견으로 중복 연동 축소

## Ⅱ. 특징

<details>
<summary>핵심 용어</summary>

- **요청 자기기술성(Self-Descriptive Request)**: 요청이 프로토콜 버전·클라이언트 식별·기능 메타데이터를 자체적으로 전달하는 성질.
- **서버 발견(Server Discovery)**: 클라이언트가 호출 전 서버 기능을 선택적으로 조회하는 원격 프로시저 호출 절차.
- **JSON-RPC**: 요청·응답·알림·오류를 JSON 객체로 표현하는 메시지 표준 형식.
- **무상태 축(Stateless Axis)**: 요청마다 필요한 메타데이터를 전달하여 세션 상태 의존성을 제거하는 기능 영역.
- **메시지 축(Message Axis)**: JSON-RPC 기반 도구·리소스·프롬프트를 교환하는 메시지 데이터 교환 영역.
- **책임 축(Responsibility Axis)**: 호스트·클라이언트·서버 간 정책·연결·기능 책임을 명확히 구분하는 아키텍처 영역.

</details>

- **무상태 축**: 2026-07-28 요청별 버전•식별•기능 전달
- **메시지 축**: JSON-RPC로 도구•리소스•프롬프트 교환
- **책임 축**: 호스트•클라이언트•서버 책임 분리

#### 한줄 요약
- **요청 자기기술성•서버 발견**으로 연동 방식 통일

## Ⅲ. 구조 및 구성요소

<details>
<summary>핵심 용어</summary>

- **모델 컨텍스트 프로토콜 호스트(Model Context Protocol Host, MCP Host)**: 사용자 동의•보안 정책과 여러 MCP 클라이언트 연결을 관리하는 인공지능 애플리케이션이며, 이는 구조적 완결성을 높이고 차별화된 성능을 제공하는 기술적 기반이 된다.
- **MCP 클라이언트(MCP Client)**: 서버별 연결과 프로토콜 메시지 교환을 관리하는 호스트 내부 구성요소를 뜻하며, 복잡한 문제 해결과 동적 환경 적응에 필수적인 역할을 수행한다.
- **MCP 서버(MCP Server)**: 도구•리소스•프롬프트 기능을 표준 메시지로 제공하는 외부 구성요소이며, 이는 구조적 완결성을 높이고 차별화된 성능을 제공하는 기술적 기반이 된다.
- **표준 입출력(Standard Input/Output, stdio)**: 로컬 MCP 프로세스가 표준 입력•출력 스트림으로 메시지를 교환하는 전송 방식을 지칭한다.
- **스트리밍 가능 하이퍼텍스트 전송 프로토콜(Streamable Hypertext Transfer Protocol, Streamable HTTP)**: HTTP POST와 요청 라우팅 헤더로 원격 MCP 메시지를 교환하는 방식이며, 이는 구조적 완결성을 높이고 차별화된 성능을 제공하는 기술적 기반이 된다.

</details>

```text
                  [MCP 호스트]
                       |
                [MCP 클라이언트]
                       |
                  [MCP 서버]
                       |
             [JSON-RPC·전송 계층]
```

선의 의미: MCP 호스트 내부의 클라이언트가 MCP 서버와 연결되고, JSON-RPC•전송 계층이 양측 메시지 교환 경계를 제공하는 프로토콜 구조를 나타냄.

| 구성요소 | 책임 |
|:---|:---|
| MCP 호스트 | **MCP Host**가 사용자 동의•정책•복수 서버 연결을 관리함 |
| MCP 클라이언트 | **MCP Client**가 서버별 연결•메시지 교환을 관리함 |
| MCP 서버 | **MCP Server**가 도구•리소스•프롬프트를 제공함 |
| JSON-RPC•전송 계층 | **JSON-RPC**를 **stdio** 또는 **Streamable HTTP**로 전달함 |

#### 한줄 요약
- **MCP Host**가 서버별 연결•보안 경계 관리

## Ⅳ. 흐름도

<details>
<summary>핵심 용어</summary>

- **무상태 코어(Stateless Core)**: 초기화 핸드셰이크와 프로토콜 세션 없이 각 요청이 필요한 메타데이터를 전달하는 구조를 말하며, 실무적 관점에서 안정성과 효율성을 보장하는 주요 기전으로 작용한다.
- **캐시 힌트(Cache Hint)**: 목록•리소스 응답의 유지 시간과 공유 범위를 알려 재조회 비용을 줄이는 정보이며, 이는 구조적 완결성을 높이고 차별화된 성능을 제공하는 기술적 기반이 된다.
- **버전•클라이언트 메타 포함 요청(Request with Meta)**: 요청마다 프로토콜 버전•식별•기능을 전달하는 단계이며, 이는 구조적 완결성을 높이고 차별화된 성능을 제공하는 기술적 기반이 된다.
- **서버 기능 발견 요청(Server Discover Request)**: 필요할 때 서버의 기능 목록과 확장을 조회하는 단계를 의미하며, 시스템의 자율적 판단과 실행을 가능하게 하는 핵심 아키텍처 요소이다.
- **서버 기능 발견 결과 제공(Server Discover Result)**: 사용 가능한 서버 기능과 확장을 클라이언트에 반환하는 단계이며, 이는 구조적 완결성을 높이고 차별화된 성능을 제공하는 기술적 기반이 된다.
- **원시 기능 목록•선택 기능 호출 요청(Call Request)**: 목록을 조회한 뒤 도구 호출•리소스 읽기를 수행하는 단계이며, 이는 구조적 완결성을 높이고 차별화된 성능을 제공하는 기술적 기반이 된다.
- **캐시 힌트•기능 결과 응답(Result Response)**: 유지 시간•공유 범위와 실행 결과•오류를 반환하는 단계를 지칭한다.

</details>

```text
MCP 클라이언트
   │ 1. 버전•클라이언트 메타 포함 요청
   ├──────────────────────┐
   │ 사전 발견이 필요하면 │
   └──────────┬───────────┘
   │ 2. 서버 기능 발견 요청
   ▼
MCP 서버
   │ 3. 서버 기능 발견 결과 제공
   ▼
MCP 클라이언트
   │ 4. 원시 기능 목록•선택 기능 호출 요청
   ▼
MCP 서버
   │ 5. 캐시 힌트•기능 결과 응답
   ▼
MCP 클라이언트
```

### 동작 원리

1. **버전•클라이언트 메타 포함 요청**: 버전•식별•기능 전달
2. **서버 기능 발견 요청**: 필요 시 server/discover 조회
3. **서버 기능 발견 결과 제공**: 기능•확장 반환
4. **원시 기능 목록•선택 기능 호출 요청**: 목록 조회•호출
5. **캐시 힌트•기능 결과 응답**: TTL•결과•오류 반환

#### 한줄 요약
- **요청 메타•선택적 서버 발견** 후 기능 호출


## Ⅴ. 종류 및 비교

<details>
<summary>핵심 용어</summary>

- **개방형 응용 프로그래밍 인터페이스 명세(OpenAPI Specification, OpenAPI)**: 고정된 하이퍼텍스트 전송 프로토콜(Hypertext Transfer Protocol, HTTP) API 계약을 기술하는 명세를 뜻하며, 복잡한 문제 해결과 동적 환경 적응에 필수적인 역할을 수행한다.

</details>

| 판단 기준 | MCP | OpenAPI | 맞춤형 API |
|:---|:---|:---|:---|
| 적용 기준 | **MCP**는 모델의 도구•컨텍스트 선택이 가능함 | **OpenAPI**는 고정 HTTP 계약임 | 맞춤형 API는 단일 시스템 연동임 |
| 핵심 특징 | 기능 발견•호출•컨텍스트 교환을 수행함 | HTTP API 계약을 기술함 | 구현별 직접 연동을 수행함 |
| 한계 | 호스트•서버 보안 구현이 필요함 | 동적 기능 발견 기능이 없음 | 재사용•상호운용성이 부족함 |

> 요약: **MCP**는 기능 발견, **OpenAPI**는 고정 HTTP 계약에 초점을 둠.

#### 한줄 요약
- 기능 발견은 **MCP**, 고정 HTTP 계약은 **OpenAPI**

## Ⅵ. 실무 고려사항 및 대책

<details>
<summary>핵심 용어</summary>

- **신뢰 경계(Trust Boundary)**: 호스트•클라이언트•서버 사이에서 인증•권한•입력 검증 책임이 달라지는 보안 경계를 의미하며, 시스템의 자율적 판단과 실행을 가능하게 하는 핵심 아키텍처 요소이다.
- **전송 계층 보안(Transport Layer Security, TLS)**: 원격 전송 메시지의 기밀성•무결성과 서버 인증을 제공하는 보안 프로토콜이며, 이는 구조적 완결성을 높이고 차별화된 성능을 제공하는 기술적 기반이 된다.

</details>

| 문제 | 대책 | 효과 |
|:---|:---|:---|
| 과도한 기능 공개로 생기는 권한 확산 | **신뢰 경계**별 허용 목록•최소 권한을 적용함 | 서버 간 보안 경계를 유지함 |
| 원격 전송의 인증 토큰 탈취•오용 | **TLS**와 토큰 대상•범위•재사용 탐지를 적용함 | 비인가 요청과 권한 오용을 방지함 |
| 도구 호출의 실제 업무 부작용 | 호스트가 동의•인자•대상•승인을 검증함 | 연결과 실행 권한을 분리함 |

#### 한줄 요약
- 서버별 **신뢰 경계•최소 권한**으로 기능 공개 제한

## Ⅶ. 결론

<details>
<summary>핵심 용어</summary>

- **MCP 적용 구분(MCP Application Division)**: AI 호스트가 모델의 기능 발견•컨텍스트 교환이 필요할 때 MCP를 적용하고, 고정 HTTP 계약만 필요하면 OpenAPI를 적용하는 구분이며, 이는 구조적 완결성을 높이고 차별화된 성능을 제공하는 기술적 기반이 된다.

</details>

- 기능 발견•컨텍스트 교환은 **MCP**, 고정 계약은 **OpenAPI** 선택

#### 한줄 요약
- **기능 발견 필요성•계약 고정성**에 따라 프로토콜 결정
