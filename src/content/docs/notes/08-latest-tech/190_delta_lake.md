## 미리 알고가기

- **Delta Lake(델타 레이크)**: Parquet 데이터 파일과 트랜잭션 로그를 결합한 오픈 테이블 형식
- **`_delta_log`(델타 로그)**: 밑줄은 시스템 관리 경로임을 나타내며, 버전별 파일 추가·제거와 스키마 동작을 기록
- **ACID(에이시드)**: 원자성·일관성·고립성·지속성을 뜻하며 동시 읽기·쓰기의 테이블 정합성을 보장



## Ⅰ. 개요

- 정의/개념: Parquet 파일의 변경을 순차 트랜잭션 로그로 관리해 스냅샷과 ACID를 제공하는 테이블 형식이다
- 기존 한계: 파일만 저장한 데이터 레이크는 동시 쓰기 충돌과 유효 파일·스키마 상태를 일관되게 판단하기 어렵다
- 기존 한계: 객체 저장소의 파일만으로 테이블을 관리하면 동시 쓰기 충돌과 부분 실패가 발생하고 일관된 버전 조회가 어렵다.
### 쉽게 이해하기 (학습용)

- **데이터 관리**: 변경 추적, 스키마 관리, 과거 상태 재현 가능

## Ⅱ. 특징

- 순차 트랜잭션 로그와 체크포인트로 스냅샷을 재구성한다
- 낙관적 동시성 제어로 충돌을 검증한 뒤 새 버전을 커밋한다
- 스키마 관리·시간 여행을 제공하지만 로그·파일 유지관리가 필요하다

### 쉽게 이해하기 (학습용)

- 장부를 요약한 중간 결산표에서 이후 거래만 더하면 빠르게 재고를 알 수 있지만 폐기된 옛 물건까지 되살릴 수는 없음

## Ⅲ. 아키텍처 및 구성요소

```text
[_delta_log checkpoint @ N] + [commit N+1 ... M]
                    │ replay actions
                    ▼
          [Snapshot M: schema + active files]
                    │
                    ▼
              [Parquet Data Files]
```

| 설계 요소 | 설명 |
|:---|:---|
| 데이터 파일 | 행 데이터를 열 지향 파일에 저장함 |
| 순차 로그 | 버전별 프로토콜·데이터 동작 기록 |
| 체크포인트 | 상태 요약으로 전체 로그 재생 방지 |
| 충돌 검증기 | 작업 충돌 여부 검사 후 로그 게시 |
| 프로토콜 | 버전·테이블 기능 호환성 관리 |

> 요약: 체크포인트·로그로 유효 파일과 상태 재구성

### 쉽게 이해하기 (학습용)

- 마지막 결산표와 그 뒤 거래 장부를 합쳐야 현재 재고가 나오며 창고에 남아 있는 상자만 세면 제외된 파일까지 잘못 포함할 수 있음

## Ⅳ. 원리 및 절차 흐름도


```text
기준상태확인
     ↓
데이터파일작성
     ↓
충돌검증
     ↓
로그커밋
     ↓
스냅샷공개
```

| 절차 | 설명 |
|:---|:---|
| 1. 상태확인 | 체크포인트와 로그로 기준 스냅샷 확인함 |
| 2. 파일작성 | 변경된 데이터를 새 데이터 파일로 생성함 |
| 3. 충돌검증 | 동시 변경 작업과 충돌 여부를 검사함 |
| 4. 로그커밋 | 충돌 없으면 새 로그 버전을 원자적 기록 |
| 5. 스냅샷공개 | 커밋 성공 시 새 버전 스냅샷 공개함 |

> 요약: 파일 작성 후 충돌을 검증해 새 로그 버전을 원자적으로 게시한다

### 쉽게 이해하기 (학습용)

- 새 파일을 준비한 뒤 동시 변경과 충돌하지 않을 때만 다음 로그 버전을 확정한다.

## Ⅴ. 종류 및 비교

| 판단 기준 | Delta Lake | Apache Iceberg | Apache Hudi |
|:---|:---|:---|:---|
| 적용 기준 | 로그 중심 배치·스트리밍 통합 | 다중 엔진·대규모 분석 | 증분 처리·업서트 중심 |
| 핵심 특징 | 순차 로그·체크포인트 | 스냅샷·매니페스트 트리 | 타임라인·파일 그룹·테이블 서비스 |
| 한계 | 엔진별 프로토콜 기능 편차 | 메타데이터 유지관리 필요 | 테이블 서비스 운영 복잡도 |

> 요약: 엔진별 Delta 프로토콜·기능 지원 확인

### 쉽게 이해하기 (학습용)

- Delta는 순차 로그, Iceberg는 매니페스트 트리, Hudi는 타임라인과 파일 그룹을 중심으로 관리한다.

## Ⅵ. 실무 사례

1. 주문 정정과 동시 집계를 트랜잭션 로그의 낙관적 충돌 검증으로 처리하고 과거 스냅샷으로 결과를 재현한다.

### 쉽게 이해하기 (학습용)

- 트랜잭션 로그를 이용하면 동시 변경의 충돌을 제어하고 특정 시점의 분석 결과를 다시 확인할 수 있다.

## Ⅶ. 결론

- 데이터 레이크의 배치·스트리밍 정합성을 확보하기 위해 프로토콜 호환성·원자적 커밋·보존 정책을 검토하여 Delta Lake를 선택해야 한다.

### 쉽게 이해하기 (학습용)

- Delta Lake는 사용하는 엔진과 저장소가 트랜잭션 프로토콜을 지원하는지 확인해야 한다.
