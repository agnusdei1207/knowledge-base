## Ⅰ. 개요

<details><summary>용어 설명</summary>

- **대규모 언어 모델 서빙(Large Language Model Serving, LLM Serving)**: 언어 모델 추론을 다중 요청에 제공하며 자원•지연•품질을 통제하는 운영 체계로 정의된다.
- **서비스 목표(Service Objective)**: 요청 처리에서 달성해야 할 품질•지연•처리량•비용 기준을 뜻하며, 복잡한 문제 해결과 동적 환경 적응에 필수적인 역할을 수행한다.
- **GPU(Graphics Processing Unit)**: 모델 추론을 병렬 처리하는 연산 장치이다.

</details>

- 정의: 다중 요청의 자원•지연•품질을 통제하는 **LLM Serving**이다.
- 배경/필요성: 가변 길이•동시 요청은 **GPU 메모리•지연 변동** 일으켜 서비스 목표를 보장하기 어려움.

#### 한줄 요약
- **접수•라우팅•스케줄링•추론•운영 통제** 통합

## Ⅱ. 특징

<details><summary>용어 설명</summary>

- **연속 배치(Continuous Batching)**: 완료 요청을 배치에서 제거하고 새 요청을 실행 중인 배치에 추가하는 방식.
- **프리필(Prefill)**: 입력 전체를 처리해 생성에 필요한 키-값 캐시(Key-Value Cache, KV Cache)를 만드는 단계를 나타낸다.
- **디코드(Decode)**: 저장된 키-값(Key-Value, KV)을 이용해 다음 출력 토큰을 반복 생성하는 단계를 뜻하며, 복잡한 문제 해결과 동적 환경 적응에 필수적인 역할을 수행한다.

</details>

- **연속•동적 배치**: 가변 길이 요청을 실행 중 재편
- **요청 스케줄링**: 프리필•디코드 자원 특성 반영
- **KV Cache 관리**: 양자화•병렬화로 지연•처리량 개선

#### 한줄 요약
- **연속 배치•프리필•디코드** 지연•처리량 결정

## Ⅲ. 구조 및 구성요소

<details><summary>용어 설명</summary>

- **모델 라우터(Model Router)**: 과업과 부하에 따라 사용할 모델과 복제본을 선택하는 구성요소이다.
- **스케줄러(Scheduler)**: 연속 배치와 KV 메모리를 고려하여 실행 순서를 관리하는 모듈로 정의된다.
- **제어 평면(Control Plane)**: 모델 배포•확장•관측•장애 복구 정책을 관리하는 운영 계층.
- **API Gateway(Application Programming Interface Gateway)**: 인증•할당량•스트리밍을 통제하는 요청 경계를 나타낸다.

</details>

```text
                          [제어 평면]
                     /        |        |        \
       [API Gateway] [모델 라우터] [스케줄러] [추론 엔진]
              +------------+------------+------------+
```

선의 의미: 상단 선은 제어 평면의 배포•확장•관측 정책 통제, 하단 선은 네 구성요소의 단일 서빙 경계 귀속을 나타냄.

| 구성요소 | 책임 |
|:---|:---|
| API Gateway | 인증•할당량•스트리밍의 **요청 경계 통제** |
| 모델 라우터 | 과업•부하에 따른 **모델•복제본 선택** |
| 스케줄러 | 연속 배치와 **KV 메모리 기반 실행 순서 관리** |
| 추론 엔진 | 양자화•병렬화 기반 **프리필•디코드 실행** |
| 제어 평면 | 배포•확장•관측•장애 복구의 **운영 정책 관리** |

#### 한줄 요약
- **게이트웨이•라우터•스케줄러•엔진•제어 평면** 구성

## Ⅳ. 흐름도

<details><summary>용어 설명</summary>

- **할당량(Quota)**: 사용자나 서비스가 일정 시간 동안 사용할 수 있는 요청•토큰•자원의 상한을 뜻하며, 복잡한 문제 해결과 동적 환경 적응에 필수적인 역할을 수행한다.
- **복제본(Replica)**: 동일 모델을 독립 실행하여 요청을 분산 처리하는 인스턴스.

</details>

```text
클라이언트 ── 추론 요청 ──▶ 게이트웨이
                              │ 1. 인증•할당량 검증
                              ▼
                           모델 라우터
                              │ 2. 모델•복제본 선택
                              ▼
                           스케줄러
                              │ 3. 연속 배치•KV 할당
                              ▼
                           추론 엔진
                              │ 4. 프리필•KV Cache 생성
                              ▼
┌──────────── 생성 종료 전 반복 ────────────┐
│ 추론 엔진                                 │
│   │ 5. 다음 토큰 디코드                   │
│   └── 토큰 스트리밍 ──▶ 클라이언트        │
└───────────────────────────────────────────┘
```

### 동작 원리

1. 인증•할당량 검증: 권한•토큰 상한•입력 형식을 확인함.
2. 모델•복제본 선택: 과업•부하에 맞는 **모델 인스턴스** 활용 결정함.
3. 연속 배치•KV 할당: 길이•우선순위별 실행 순서와 캐시를 배정함.
4. 프리필•KV 캐시 생성: 입력 어텐션을 계산해 초기 키•값을 저장함.
5. 다음 토큰 디코드: 캐시를 재사용해 토큰을 반복 생성함.

#### 한줄 요약
- **인증•라우팅•배치•프리필•디코드** 수행

## Ⅴ. 종류 및 비교

<details><summary>용어 설명</summary>

- **오프라인 추론(Offline Inference)**: 즉시 응답 없이 대량 데이터를 고정 배치로 처리하여 비용과 처리량을 최적화하는 기법이다.
- **온라인 서빙(Online Serving)**: 대화형 요청을 동적 배치로 처리하여 TTFT와 TPOT을 관리하는 방식으로 정의된다.
- **비동기 배치 응용 프로그래밍 인터페이스(Asynchronous Batch Application Programming Interface, Asynchronous Batch API)**: 완료 시점이 유연한 대량 요청을 작업 큐에 넣고 나중에 결과를 제공하는 구조를 나타낸다.
- **TTFT(Time to First Token)**: 요청부터 첫 출력 토큰까지의 초기 지연을 뜻하며, 복잡한 문제 해결과 동적 환경 적응에 필수적인 역할을 수행한다.
- **TPOT(Time per Output Token)**: 첫 토큰 뒤 출력 토큰당 평균 지연.

</details>

| 구분 | 오프라인 추론 | 온라인 서빙 | 비동기 배치 API |
|:---|:---|:---|:---|
| 적용 기준 | **대량 데이터 일괄 처리** | **대화형 실시간 응답** | **완료 유연 대량 요청** |
| 핵심 특징 | 처리량•비용 중심 **고정 배치** | TTFT•TPOT 중심 **동적 배치** | 작업 큐 기반 **비동기 완료** |
| 한계 | **즉시 응답 불가** | **상시 자원•운영 복잡성** | **결과 대기•상태 관리** |

#### 한줄 요약
- **응답 시급성•처리량** 대상 따라 서빙 방식 선택

## Ⅵ. 실무 고려사항 및 대책

<details><summary>용어 설명</summary>

- **유효 처리량(Goodput)**: 품질•지연 목표를 모두 만족하면서 처리한 유효 요청이나 토큰의 양이다.
- **페이지드 캐시(Paged Cache)**: KV Cache를 고정 크기 비연속 블록으로 나눠 동적 할당•회수하는 방식.
- **회로 차단(Circuit Breaker)**: 장애가 반복되는 복제본의 요청을 일시 중단해 실패 확산을 막는 패턴으로 정의된다.
- **그림자 트래픽•카나리 배포(Shadow Traffic & Canary Deployment)**: 새 모델을 응답에 반영하지 않고 비교한 뒤 일부 요청부터 단계적으로 적용하는 검증 방식을 뜻하며, 복잡한 문제 해결과 동적 환경 적응에 필수적인 역할을 수행한다.
- **SLO(Service Level Objective)**: 지연•품질 등 서비스가 달성해야 하는 운영 목표를 나타낸다.

</details>

| 문제 | 대책 | 효과 |
|:---|:---|:---|
| 요청 길이 편차의 **배치 비효율** | **연속 배치•길이 인지 스케줄링** | GPU 활용률 **향상** |
| KV Cache의 **단편화**•**고갈** | **페이지드 캐시•요청별 길이 상한** | 메모리 부족 **방지** |
| 지연•품질 SLO 미달의 **유효 처리량 감소** | **TTFT•TPOT•품질 공동 계측** | 병목별 **유효 처리량 향상** |
| 반복 장애 복제본의 **실패 확산** | **회로 차단** 기반 장애 복제본 자동 제외 | 연쇄 장애 **방지** |
| 신규 모델의 **품질 회귀** | **그림자 트래픽•카나리 배포** 단계 적용 | 배포 위험 **완화** |

#### 한줄 요약
- **배치•캐시•SLO•회로 차단•카나리** 기반 운영 통제

## Ⅶ. 결론

<details><summary>용어 설명</summary>

- **온라인 동적 배치(Online Dynamic Batching)**: 즉시 스트리밍 응답이 필요한 요청을 지연 목표에 맞춰 실행 중 재편하는 방식이다.
- **비동기 응용 프로그래밍 인터페이스(Asynchronous Application Programming Interface, Asynchronous API)**: 완료 시점이 유연한 대량 요청을 작업 큐로 처리하는 방식.
</details>

- 실시간은 **온라인 동적 배치**, 완료 유연 작업은 **비동기 API**, 대량 처리는 **오프라인 추론** #### 한줄 요약
- **응답 시급성•작업량** 대상 따라 서빙 방식 결정
