## 미리 알고가기

- **레이크하우스(Data Lakehouse)**: 데이터 레이크의 개방형 저장에 웨어하우스의 테이블 관리 기능을 결합한 아키텍처
- **ACID(에이시드)**: Atomicity·Consistency·Isolation·Durability의 머리글자로, 안전한 트랜잭션 성질을 표기
- **오픈 테이블 포맷(Open Table Format)**: 파일 위에 스키마·스냅샷·트랜잭션 메타데이터를 정의해 여러 엔진이 공유



## Ⅰ. 개요

- 정의/개념: 데이터 레이크의 개방형 파일 저장소에 트랜잭션·스키마·카탈로그 계층을 결합한 아키텍처다
- 기존 한계: 레이크는 동시 변경과 정합성 관리가 어렵고 웨어하우스는 저장·엔진 종속과 데이터 복제 비용이 발생한다
- 기존 한계: 데이터 레이크와 웨어하우스를 분리하면 데이터 복제·파이프라인 중복·버전 불일치가 발생해 BI·스트리밍·ML이 동일 데이터를 공유하기 어렵다.
### 쉽게 이해하기 (학습용)

- **워크로드 통합**: BI·스트리밍·ML이 동일 테이블을 공유해 정합성 유지

## Ⅱ. 특징

- 개방형 스토리지와 컴퓨트 엔진을 분리해 엔진 선택권을 제공한다
- 테이블 메타데이터로 ACID·스키마 진화·스냅샷을 관리한다
- 다중 워크로드가 같은 테이블을 공유하지만 파일 최적화가 필요하다

### 쉽게 이해하기 (학습용)

- 여러 엔진이 같은 파일을 공유하되 스냅샷으로 일관된 시점을 읽고 파일·통계를 계속 최적화한다.

## Ⅲ. 아키텍처 및 구성요소

```text
+------------------- Compute Engines -------------------+
| SQL/BI             Batch/Stream              ML       |
+---------------------------+---------------------------+
                            ↓
               Catalog: table → current metadata
                            ↓
        Open Table Format: schema·snapshot·file list
                            ↓
       Object Storage: Parquet/ORC/Avro data files
```

| 설계 요소 | 설명 |
|:---|:---|
| 오브젝트 파일 | 데이터 파일로 실행 기능은 없음 |
| 오픈 테이블 포맷 | 트랜잭션·버전·스키마 정보를 관리함 |
| 카탈로그 | 식별자를 메타데이터 위치와 연결함 |
| 컴퓨트 엔진 | 데이터를 해석하고 읽기·쓰기를 수행함 |
| 운영 거버넌스 | 품질·접근제어 및 성능 최적화 관리 |

> 요약: 카탈로그·테이블 포맷·엔진의 책임을 분리

### 쉽게 이해하기 (학습용)

- 파일 저장소 위의 테이블 포맷과 카탈로그가 상태를 관리하고 각 엔진이 계산을 수행한다.

## Ⅳ. 원리 및 절차 흐름도


```text
변경요청
   ↓
파일생성
   ↓
원자커밋
   ↓
스냅샷공개
   ↓
일관조회
```

| 절차 | 설명 |
|:---|:---|
| 1. 변경요청 | 엔진이 데이터 변경 작업을 수행함 |
| 2. 파일생성 | 새 데이터 파일과 메타데이터를 구성함 |
| 3. 원자커밋 | 카탈로그 위치를 갱신해 스냅샷 확정함 |
| 4. 스냅샷공개 | 변경된 스냅샷을 사용자가 조회 가능함 |
| 5. 일관조회 | 엔진이 확정 스냅샷 기반 데이터를 처리함 |

> 요약: 원자 확정한 스냅샷을 일관되게 조회

### 쉽게 이해하기 (학습용)

- 새 물건과 장부 페이지를 먼저 만든 뒤 최신 장부 표시만 한 번에 바꾸므로 독자는 완성된 이전 장부나 새 장부 중 하나를 일관되게 보게 됨

## Ⅴ. 종류 및 비교

| 판단 기준 | Data Lake | Data Warehouse | Data Lakehouse |
|:---|:---|:---|:---|
| 적용 기준 | 원시·비정형 데이터 대량 저장 | 정형 BI와 고성능 SQL | BI·스트리밍·ML 테이블 통합 |
| 핵심 특징 | 개방형 파일을 저비용 저장 | DBMS가 저장·테이블을 통합 관리 | 파일 위에 테이블 메타데이터 추가 |
| 한계 | 트랜잭션·품질 관리가 어려움 | 저장·엔진 종속과 복제 비용 | 파일 병합·통계 관리 필요 |

> 요약: 레이크 저장소에 테이블 의미를 더해 엔진 공유

### 쉽게 이해하기 (학습용)

- 레이크가 파일 창고이고 웨어하우스가 전용 장부까지 가진 매장이라면, 레이크하우스는 공동 창고에 표준 장부를 붙여 여러 매장이 함께 쓰는 방식임

## Ⅵ. 실무 사례

1. 데이터 플랫폼은 동일한 주문 스냅샷을 SQL 분석과 ML 특징 생성에 공유하고 작은 파일을 주기적으로 병합한다.

### 쉽게 이해하기 (학습용)

- 하나의 스냅샷을 여러 분석 작업이 사용하면 복제에 따른 시차와 중복 저장을 줄일 수 있다.

## Ⅶ. 결론

- 다중 분석 엔진이 일관된 데이터를 공유하도록 하기 위해 트랜잭션·엔진 호환성·파일 최적화를 검토하여 데이터 레이크하우스를 선택해야 한다.

### 쉽게 이해하기 (학습용)

- 데이터 레이크하우스는 테이블 포맷과 카탈로그·파일 유지관리를 함께 운영해야 한다.
