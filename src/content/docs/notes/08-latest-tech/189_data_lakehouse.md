## 미리 알고가기

- **데이터 레이크(Data Lake)**: 저비용 대용량 파일 저장에 유리하지만 정합성 관리가 어려움
- **데이터 웨어하우스(DW)**: 성능과 관리 편의성이 높으나 스토리지 종속성 및 비용 부담 존재
- **레이크하우스(Lakehouse)**: 레이크 저장소에 테이블 메타데이터 계층을 도입해 ACID 결합
- **오픈 테이블 포맷**: 파일 기반 스키마·스냅샷·트랜잭션 정보를 관리하는 핵심 구조
- **컴퓨트 분리**: 데이터 저장을 담당하는 스토리지와 분석 엔진이 독립적으로 동작함
- **최적화**: 파일 병합(Compaction)과 통계 갱신 등을 통한 성능 유지 관리 필수



## Ⅰ. 개요

오픈 파일 저장소에 테이블 관리 계층과 컴퓨트 엔진을 결합한 아키텍처임

- **정의/개념**: 데이터 레이크에 테이블 관리 기능을 결합
- **배경/필요성**: 저비용 저장과 일관된 분석 처리를 통합
### 쉽게 이해하기 (학습용)

- **워크로드 통합**: BI·스트리밍·ML이 동일 테이블을 공유해 정합성 유지

## Ⅱ. 특징

- 저장·컴퓨트 분리가 엔진 선택권을 넓힌다.
- 테이블 포맷이 ACID·스키마 진화를 제공한다.
- 다중 엔진이 같은 스냅샷을 일관되게 사용한다.
- 통계·병합 최적화가 질의 성능을 좌우한다.

### 쉽게 이해하기 (학습용)

- 같은 파일 창고를 여러 작업자가 공유하되 장부가 일관된 시점을 알려 주며, 빠른 조회를 위해 파일 정리와 통계 작성은 계속 수행해야 함

## Ⅲ. 아키텍처 및 구성요소

```text
+------------------- Compute Engines -------------------+
| SQL/BI             Batch/Stream              ML       |
+---------------------------+---------------------------+
                            ↓
               Catalog: table → current metadata
                            ↓
        Open Table Format: schema·snapshot·file list
                            ↓
       Object Storage: Parquet/ORC/Avro data files
```

| 설계 요소 | 설명 |
|:---|:---|
| 오브젝트 파일 | 데이터 파일로 실행 기능은 없음 |
| 오픈 테이블 포맷 | 트랜잭션·버전·스키마 정보를 관리함 |
| 카탈로그 | 식별자를 메타데이터 위치와 연결함 |
| 컴퓨트 엔진 | 데이터를 해석하고 읽기·쓰기를 수행함 |
| 운영 거버넌스 | 품질·접근제어 및 성능 최적화 관리 |

> 요약: 카탈로그·테이블 포맷·엔진의 책임을 분리

### 쉽게 이해하기 (학습용)

- 창고에는 물건 파일이 있고 표준 장부는 재고 시점을 기록하며 목록 서비스는 최신 장부 위치를 알려 주고 각 작업 도구가 실제 계산을 수행함

## Ⅳ. 원리 및 절차 흐름도


```text
변경요청
   ↓
파일생성
   ↓
원자커밋
   ↓
스냅샷공개
   ↓
일관조회
```

| 절차 | 설명 |
|:---|:---|
| 1. 변경요청 | 엔진이 데이터 변경 작업을 수행함 |
| 2. 파일생성 | 새 데이터 파일과 메타데이터를 구성함 |
| 3. 원자커밋 | 카탈로그 위치를 갱신해 스냅샷 확정함 |
| 4. 스냅샷공개 | 변경된 스냅샷을 사용자가 조회 가능함 |
| 5. 일관조회 | 엔진이 확정 스냅샷 기반 데이터를 처리함 |

> 요약: 원자 확정한 스냅샷을 일관되게 조회

### 쉽게 이해하기 (학습용)

- 새 물건과 장부 페이지를 먼저 만든 뒤 최신 장부 표시만 한 번에 바꾸므로 독자는 완성된 이전 장부나 새 장부 중 하나를 일관되게 보게 됨

## Ⅴ. 종류 및 비교

| 판단 기준 | Data Lake | Data Warehouse | Data Lakehouse |
|:---|:---|:---|:---|
| 핵심 특징 | 개방형 파일을 저비용 저장하고 해석을 엔진에 맡김 | DBMS가 내부 테이블·저장 구조를 통합 관리함 | 개방형 파일을 테이블 메타데이터·스냅샷으로 관리함 |
| 적용 기준 | 파일 단위 처리로 동시 변경·조회 최적화가 제한적임 | ACID·인덱스·최적화·캐시가 성숙함 | ACID를 제공하나 통계·병합·엔진 최적화가 필요함 |
| 주요 위험 | 탐색·배치·ML에 유연하나 신뢰 테이블 관리가 약함 | 정형 BI·리포팅에 강하고 엔진 종속성이 큼 | BI·스트리밍·ML이 같은 관리 테이블을 공유함 |

> 요약: 레이크 저장소에 테이블 의미를 더해 엔진 공유

### 쉽게 이해하기 (학습용)

- 레이크가 파일 창고이고 웨어하우스가 전용 장부까지 가진 매장이라면, 레이크하우스는 공동 창고에 표준 장부를 붙여 여러 매장이 함께 쓰는 방식임

## Ⅵ. 실무 사례

1. 대상 환경의 도입 조건과 설계를 검증함
2. 운영 위험과 성과 지표를 검증함

### 쉽게 이해하기 (학습용)

- 데이터 플랫폼은 주문 테이블의 같은 스냅샷을 SQL BI와 ML 특징 생성이 공유하게 해 레이크에서 웨어하우스로 복제할 때 생기던 시차와 중복 저장을 줄임
- 스트리밍 로그 플랫폼은 실시간 엔진이 테이블 스냅샷을 커밋하고 SQL 엔진이 카탈로그를 통해 조회하며 compaction·통계 갱신으로 작은 파일과 스캔 비용을 통제함

## Ⅶ. 결론

- 공통 스냅샷·엔진 호환성으로 레이크하우스 선택

### 쉽게 이해하기 (학습용)

- 공동 파일 창고에 장부만 붙인다고 끝나는 것이 아니라 최신 장부 위치, 실제 계산 도구와 파일 정리 책임을 나눠 계속 운영해야 함
