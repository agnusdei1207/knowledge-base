## 미리 알고가기

- **OpenTelemetry**: 메트릭·로그·추적 수집을 표준화한 관측성 오픈 표준
- **벤더 종속성**: 종속성을 낮추고 계측 방식을 일관화함
- **SDK**: API·Collector·Semantic Conventions의 역할을 구분함



## Ⅰ. 개요

- **정의/개념**: 벤더 중립 텔레메트리 계측·전송 표준
- **배경/필요성**: 언어·백엔드 간 일관된 관측 계약

### 쉽게 이해하기 (학습용)

- OpenTelemetry는 계측·전송 배관이며 저장·시각화 백엔드는 아니다.

## Ⅱ. 특징

- API로 계측하고 SDK로 처리·내보내기를 구성한다
- 자동 계측과 핵심 단계 수동 계측을 결합한다
- 문맥 전파가 서비스 간 요청 흐름을 연결한다
- OTLP·Collector가 신호를 처리·전송한다
- 의미 규칙이 백엔드 속성·질의를 통일한다

### 쉽게 이해하기 (학습용)

- API는 계약, SDK는 구현, OTLP는 운송, Collector는 분류소다.

## Ⅲ. 아키텍처 및 구성요소

```text
앱 → SDK → OTLP → Collector → 백엔드
```

| 설계 요소 | 설명 |
|:---|:---|
| API | 계측 호출·문맥 전파 계약 |
| SDK | 신호 처리·내보내기 구현 |
| OTLP | 텔레메트리 전송 규격 |
| Collector | 수집·처리·라우팅 |
| 의미 규칙 | 공통 속성·명명 규칙 |

> 요약: API·SDK는 계측, OTLP·수집기는 전송을 맡는다.

### 쉽게 이해하기 (학습용)

- Collector까지는 전송 체계이고 저장·질의·화면은 백엔드가 맡는다.

## Ⅳ. 원리 및 절차 흐름도

```text
의미 규칙 → API 계측 → SDK 처리
                         ↓
백엔드 ← Collector ← OTLP 전송
```

| 절차 | 설명 |
|:---|:---|
| 의미 계약 선정 | 신호·속성·규칙 버전 결정 |
| 계측 삽입 | 자동·수동 계측과 문맥 전파 |
| SDK 처리 | 자원·샘플·배치 정책 적용 |
| OTLP 전송 | SDK에서 Collector로 전송 |
| Collector 처리 | 필터·변환·분기·재시도 |
| 백엔드 활용 | 저장·질의 결과로 계측 개선 |

> 요약: 의미 계약부터 계측·처리·전송 흐름을 구성한다

### 쉽게 이해하기 (학습용)

- 질문과 라벨을 정하고 표준 운송과 분류소를 거쳐 백엔드로 보낸다.

## Ⅴ. 종류 및 비교

| 판단 기준 | API | SDK | Collector |
|:---|:---|:---|:---|
| 핵심 책임 | 계측·문맥 계약 | 기록·처리·내보내기 | 수신·처리·분기 |
| 실행 위치 | 앱·계측 라이브러리 | 앱 프로세스 내부 | 에이전트·게이트웨이 |
| 적용 기준 | 구현 독립 호출 | 앱별 계측 정책 | 중앙 통제·다중 전송 |

> 요약: API는 계약, SDK는 구현, 수집기는 외부 처리다.

### 쉽게 이해하기 (학습용)

- 계약·앱 처리·외부 전송을 나누면 백엔드 교체 영향을 줄인다.

## Ⅵ. 실무 사례

1. 공통 의미 규칙으로 다언어 계측을 통일한다
2. Collector에서 민감정보·표본을 통제한다

### 쉽게 이해하기 (학습용)

- 여러 언어가 같은 속성을 쓰고 두 백엔드 전송 결과를 비교한다.
- 중앙 분류소에서 민감 속성을 지우고 필요한 추적만 보존한다.

## Ⅶ. 결론

- 계측 계약과 전송을 분리해 백엔드 선택권을 확보한다.

### 쉽게 이해하기 (학습용)

- 공용 배관과 저장·분석 시스템을 나누고 각 신뢰성을 관리해야 한다.
