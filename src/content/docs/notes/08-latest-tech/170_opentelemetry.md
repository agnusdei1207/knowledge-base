## Ⅰ. 개요

<details><summary>용어 설명</summary>

- **오픈텔레메트리(OpenTelemetry, OTel)**: 텔레메트리를 생성•처리•전송하기 위한 공급자 중립 오픈소스 관찰 가능성 프레임워크이다.
- **공급자 중립**: 특정 관측 백엔드 제품에 종속되지 않는 공통 계측•전송 계약을 제공하는 성질을 말한다.
- **응용 프로그래밍 인터페이스(Application Programming Interface, API)**: 코드가 텔레메트리를 생성할 때 사용하는 계약이다.
- **소프트웨어 개발 키트(Software Development Kit, SDK)**: API 신호를 샘플링•가공•내보내는 구현체을 의미한다.
- **오픈텔레메트리 프로토콜(OpenTelemetry Protocol, OTLP)**: 프로세스와 Collector 사이의 표준 신호 전송 규약을 의미한다.

</details>

- 정의: 공급자 중립 텔레메트리 생성•전송 체계인 **OTel**
- 배경/필요성: 다양한 상용 및 오픈소스 모니터링 벤더(Datadog, Dynatrace, New Relic, Prometheus, Jaeger 등)마다 고유한 전용 에이전트와 비표준 SDK를 제공함에 따라, 모니터링 백엔드를 변경하거나 다중 백엔드를 운영할 때 애플리케이션 코드를 전면 재수정해야 하는 극심한 벤더 락인(Vendor Lock-in)과 다국어 계측 코드 파편화에 직면함에 따라, CNCF 산하에서 OpenTracing과 OpenCensus를 통합하여 단일화된 벤더 중립적 표준 텔레메트리 수집/전송 프레임워크를 제공하는 OpenTelemetry(OTel / Vendor-neutral API & SDK, OTLP Protocol over gRPC/HTTP, OTel Collector: Receiver, Processor, Exporter, W3C Trace Context Propagation, Semantic Conventions, Auto-instrumentation) 아키텍처를 도입하여 **애플리케이션 코드의 단 1회 표준 계측(API)으로 수십 종의 백엔드 APM/시계열 DB로 동시 다중 전송(OTel Collector) 가능한 완전한 벤더 독립성 확보, W3C Trace Context 기반의 완벽한 분산 트레이스 컨텍스트 전파 및 시맨틱 규약 준수, Collector의 중앙 집중식 배치/샘플링/민감정보 마스킹 처리를 통한 텔레메트리 데이터 거버넌스 완성**을 달성할 필요

#### 한줄 요약

- OTel의 이득은 신호 품질이 아니라 **계측•백엔드 분리**에 있어 백엔드 교체 비용을 코드 수정에서 설정 변경으로 낮추는 대신, Collector라는 운영 대상이 새로 생긴다.

## Ⅱ. 특징

<details><summary>용어 설명</summary>

- **맥락 전파**: 서비스 경계를 넘어 추적 식별자와 부가 정보를 전달하는 과정을 말한다.
- **시맨틱 규약**: 서비스•요청•자원 속성의 이름과 의미를 일관되게 정의한 규칙을 의미한다.

</details>

- 계측 생성 계약과 처리 정책을 분리하는 **API•SDK 분리**
- 맥락 전파와 시맨틱 규약 기반 **맥락•의미 표준화**
- OTLP•Collector 기반 **중립 전송 파이프라인**

#### 한줄 요약

- **공급자 중립 표준화**는 계측 코드의 수명을 백엔드 수명에서 떼어 내려고 치르는 규격 준수 비용이므로, 백엔드를 바꿀 일이 없고 언어가 단일한 조직에서는 회수되기 어렵다.

## Ⅲ. 구조 및 구성요소

<details><summary>용어 설명</summary>

- **API 계측 계약**: 언어별 코드가 메트릭•로그•추적을 생성하는 접점을 의미한다.
- **SDK 처리 정책**: 신호의 샘플링•자원 결합•일괄 처리•내보내기를 제어하는 정책로 정의된다.
- **Collector**: 텔레메트리를 수신해 처리하고 하나 이상의 저장•분석 백엔드로 전달하는 독립 구성요소로 정의된다.
- **맥락 전파**: 신호 사이의 요청 관계를 유지하도록 식별자를 전달하는 개념을 의미한다.
- **시맨틱 규약**: 서비스•요청•자원 속성의 이름과 의미를 통일하는 개념이다.

</details>

```text
                    [맥락 전파]   [시맨틱 규약]
                          \       /
                            [API]
                              |
                            [SDK]
                              |
                            [OTLP]
                              |
                         [Collector]
```
선의 의미: 맥락 전파와 시맨틱 규약은 API의 요청 관계와 속성 의미를 표준화하고, SDK는 API 신호의 처리 정책을 구현하며 OTLP는 SDK와 Collector 사이의 공급자 중립 전송 경계를 제공한다.

| 구성요소 | 책임 |
|:---|:---|
| API | 코드의 **스팬•메트릭•로그 생성 계약** 제공 |
| SDK | **샘플링•자원 결합•일괄 처리•내보내기** 실행 |
| 맥락 전파 | 신호 사이의 **요청 상관관계** 유지 |
| 시맨틱 규약 | 신호 속성의 **이름•의미** 통일 |
| OTLP | 프로세스•Collector 간 **표준 신호 전송** |
| Collector | **수신•변환•필터링•라우팅•내보내기** |

#### 한줄 요약

- API•SDK•OTLP•Collector의 **계측 전송 구조**

## Ⅳ. 흐름도

<details><summary>용어 설명</summary>

- **OTLP 전송**: OTel 신호를 프로세스와 Collector 사이에서 표준 형식으로 전달하는 개념을 말한다.
- **내보내기 모듈(Exporter)**: 처리한 텔레메트리를 OTLP나 백엔드별 프로토콜로 전송하는 구성요소이다.

</details>

API 생성 신호의 **SDK 처리•OTLP 전송**

```text
애플리케이션
   │ 1. 신호 생성
   ▼
SDK
   │ 2. 신호 처리
   │ 3. OTLP 표준 전송
   ▼
Collector
   │ 4. 신호 라우팅
   ▼
백엔드
```

### 동작 원리

1. 신호 생성: **API•시맨틱 규약**으로 텔레메트리 생성
2. 신호 처리: SDK의 **자원 결합•샘플링•일괄 처리**
3. OTLP 표준 전송: **Exporter•Collector** 간 신호 전달
4. 신호 라우팅: Collector의 **변환•필터링•백엔드 전송**

#### 한줄 요약

- 공통 계약 신호의 **SDK•Collector 처리•백엔드 전송**

## Ⅴ. 종류 및 비교

<details><summary>용어 설명</summary>

- **계측 코드**: 애플리케이션의 연산•요청•상태에서 텔레메트리를 생성하도록 추가한 코드을 말한다.
- **수집 파이프라인**: 신호를 수신•변환•필터링•라우팅해 백엔드로 전달하는 처리 경로을 말한다.

</details>

API•SDK•Collector의 **신호 생성•처리•수집 분담**

| 구분 | API | SDK | Collector |
|:---|:---|:---|:---|
| 적용 기준 | 애플리케이션 **계측 코드** | 애플리케이션 **실행 프로세스** | 중앙•에이전트형 **수집 파이프라인** |
| 핵심 특징 | 공급자 중립 **신호 생성 계약** | **샘플링•처리•내보내기** 구현 | **수신기•처리기•내보내기** 조합 |
| 한계 | 단독 **신호 처리 불가** | **프로세스 자원•설정** 영향 | 용량 부족 시 **병목•데이터 손실** |

#### 한줄 요약

- 셋은 계측을 변경 빈도가 다른 세 층으로 쪼갠 결과이며, 자주 바뀌는 **처리•수집 책임**을 Collector로 밀어낼수록 애플리케이션에 남는 API **계약**은 더 오래 유지된다.

## Ⅵ. 실무 고려사항 및 대책

<details><summary>용어 설명</summary>

- **카디널리티 예산**: 저장•질의 비용 한도 안에서 허용할 속성 고유 값 수를 정한 기준을 의미한다.
- **영속 버퍼**: Collector 장애나 백엔드 지연에도 신호를 잃지 않도록 디스크 등에 임시 보관하는 큐을 말한다.

</details>

| 문제 | 대책 | 효과 |
|:---|:---|:---|
| 맥락 전파 단절로 **호출 경로 유실** | 전파 형식 통일•경계별 **식별자 전달 시험** | **분산 추적 연속성** 확보 |
| 속성 규약 불일치로 **질의 분산•비용 증가** | 규약 버전•속성 허용 목록•**카디널리티 예산** | **질의 일관성•비용 예측성** 향상 |
| Collector 과부하로 **텔레메트리 손실** | 용량 시험•재시도 큐•**영속 버퍼•신호 우선순위** | **핵심 신호 보존율** 향상 |

#### 한줄 요약

- 속성•추적 맥락 통일과 **Collector 용량 시험**

## Ⅶ. 결론

<details><summary>용어 설명</summary>

- **계측•백엔드 분리**: 애플리케이션의 신호 생성 계약을 유지한 채 저장•분석 제품을 바꿀 수 있게 하는 설계을 말한다.
- **핵심 신호 보존율**: 수집 부하와 장애 상황에서도 우선순위가 높은 텔레메트리가 백엔드에 도달한 비율로 정의된다.

</details>

- 클라우드 네이티브 관찰 가능성(Observability) 생태계의 절대적인 단일 글로벌 사실상 표준(De facto Standard)이자 CNCF 핵심 프로젝트로 확립된 **벤더 중립 텔레메트리 계측 및 파이프라인 프레임워크의 최고 표준(OpenTelemetry: OTel / Universal API-SDK Separation / OTLP gRPC & HTTP / OpenTelemetry Collector Pipelines / W3C TraceContext & Baggage / Semantic Conventions)의 확고한 표준**으로 확고히 자리 잡았으며, 메트릭/트레이스/로그를 넘어 지속적 프로파일링(Profiling)까지 단일 파이프라인으로 통합 발전하는 가운데, 실무 엔터프라이즈 OTel 도입 시에는 **애플리케이션에는 순수 OTel API/SDK만 링크하고, 에이전트형(DaemonSet) 및 중앙 게이트웨이형 Collector 2계층 파이프라인을 구성하며, 테일 기반 샘플링(Tail-based Sampling)과 배치 프로세서(Batch Processor) 튜닝으로 네트워크 대역폭 및 백엔드 라이선스 비용을 극대화**를 결합하여 완벽한 관측 데이터 거버넌스와 비용 최적화를 완성

#### 한줄 요약

- **OTel 적용**은 관측 비용을 줄이는 선택이 아니라 계측 자산의 수명을 특정 백엔드에서 떼어 내는 선택이므로, 백엔드 교체 가능성과 다언어 환경이 있을 때 투자가 회수된다.
