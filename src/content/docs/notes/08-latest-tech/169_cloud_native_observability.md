## Ⅰ. 개요

<details><summary>용어 설명</summary>

- **관찰 가능성(Observability)**: 텔레메트리와 실행 맥락으로 시스템 내부 상태•근본 원인•사용자 영향을 추론할 수 있는 능력을 의미한다.
- **텔레메트리**: 시스템이 생성하는 메트릭•로그•추적•프로파일 자료을 말한다.

</details>

- 정의: 텔레메트리로 내부 상태•원인을 추론하는 **관찰 가능성**
- 배경/필요성: 수천 개의 마이크로서비스, 동적 컨테이너, 서버리스가 유기적으로 얽힌 클라우드 네이티브 환경에서 정적 대시보드와 고정 임계치 기반의 전통적 모니터링(Monitoring)은 '알려진 문제(Known-Unknowns)'만 감지할 수 있어 복합 분산 장애의 근본 원인을 파악하지 못하고 긴 MTTR(평균 복구 시간)을 유발함에 따라, 시스템 외부 출력(텔레메트리 데이터)만으로 내부의 모든 미지의 상태(Unknown-Unknowns)와 근본 원인을 교차 질의로 추론할 수 있는 클라우드 네이티브 관찰 가능성(Cloud-Native Observability / 4 Pillars of Telemetry: Metrics, Logs, Traces, Continuous Profiling / Unified Correlation ID: TraceID/SpanID, Semantic Conventions, SLO/Error Budget Driven, OpenTelemetry Standard, eBPF Auto-instrumentation) 체계를 도입하여 **TraceID 기반으로 메트릭•로그•분산 추적•프로파일을 100% 상호 연결(Correlation)하여 장애 원인 탐색 시간(MTTR)을 수 분 이내로 단축, 기술적 인프라 지표를 넘어 실제 사용자 체감 품질(SLI/SLO) 기반의 능동적 서비스 수준 관리, eBPF 비침습적 수집을 통한 애플리케이션 무중단 제로 오버헤드 계측**을 달성할 필요

#### 한줄 요약

- 관측 가능성은 경보 규칙을 늘리는 대신 신호를 맥락으로 묶어 **근본 원인•사용자 영향**을 사후 질의로 찾게 한 전환이며, 그 대가로 저장량과 카디널리티 비용을 상시 지불한다.

## Ⅱ. 특징

<details><summary>용어 설명</summary>

- **상관 식별자**: 동일 요청이나 자원에서 나온 여러 신호를 연결하는 값을 의미한다.
- **서비스 수준 지표(Service Level Indicator, SLI)**: 사용자 관점의 가용성•지연 등 서비스 수준을 측정하는 지표을 의미한다.
- **서비스 수준 목표(Service Level Objective, SLO)**: SLI가 달성해야 할 목표 수준을 말한다.

</details>

- 시간•요청•자원•배포 버전 식별자의 **다신호 상관성**
- 실행 맥락 교차 질의 기반 **미지의 원인 탐색**
- 기술 신호를 SLI•SLO에 연결하는 **사용자 영향 중심**

#### 한줄 요약

- **사용자 영향 중심 원인 탐색**이 가능한 것은 신호마다 같은 요청•배포 식별자를 붙여 둔 덕분이므로, 관측 품질은 수집한 신호의 양이 아니라 맥락 연결의 보존율이 결정한다.

## Ⅲ. 구조 및 구성요소

<details><summary>용어 설명</summary>

- **실행 맥락**: 요청•서비스•자원•배포 버전이 어떤 관계에서 신호를 만들었는지 나타내는 정보이다.
- **수집 파이프라인**: 텔레메트리를 수신해 정규화•필터링•전달하는 처리 경로이다.
- **계측**: 애플리케이션과 기반 시설에서 텔레메트리를 생성하는 기능을 의미한다.
- **저장소**: 신호 유형과 보존 정책에 따라 텔레메트리를 유지하는 구성요소이다.
- **질의기**: 공통 실행 맥락으로 여러 신호를 연결하여 분석하는 구성요소을 의미한다.
- **SLO 평가기**: SLI를 목표와 비교하여 사용자 영향과 복구 여부를 판단하는 구성요소을 의미한다.
- **대응 체계**: 경보에 따라 원인을 분석하고 복구 조치를 실행하는 운영 구성요소을 말한다.

</details>

실행 맥락 텔레메트리의 **SLO 기반 사용자 영향 판단**

```text
[클라우드 네이티브 관찰 가능성]
├── [수집 및 계측 계층]
│   ├── [계측]
│   └── [수집 파이프라인]
├── [저장 및 상관 계층]
│   ├── [실행 맥락]
│   └── [저장소]
└── [분석 및 대응 계층]
    ├── [질의기]
    ├── [SLO 평가기]
    └── [대응 체계]
```

- 선의 의미: 계층 구조 및 상하위 포함 관계를 나타낸다.

| 구성요소 | 책임 |
|:---|:---|
| 계측 | 애플리케이션•기반 시설의 **텔레메트리 생성** |
| 수집 파이프라인 | **신호 수신•정규화•필터링•전달** |
| 실행 맥락 | **요청•서비스•자원•버전 상관관계** 유지 |
| 저장소 | 신호별 **보존 정책** 집행 |
| 질의기 | 공통 맥락 기반 **교차 분석** 제공 |
| SLO 평가기 | **사용자 영향•복구 여부** 판단 |
| 대응 체계 | **경보•복구 조치** 수행 |

#### 한줄 요약

- 실행 맥락 기반 **교차 분석•SLO 평가•복구 대응** 구조

## Ⅳ. 흐름도

<details><summary>용어 설명</summary>

- **메트릭•로그•추적•프로파일**: 수치 추세•사건 기록•요청 경로•자원 사용 원인을 각각 나타내는 신호로 정의된다.
- **가설 검증**: 사용자 영향에서 출발해 관련 신호를 질의하고 예상 원인과 관측 결과를 대조하는 과정을 의미한다.

</details>

SLI와 SLO로 복구 여부를 검증한다.

```text
애플리케이션
   │ 1. 신호 생성
   ▼
수집 파이프라인
   │ 2. 맥락 연결
   ▼
분석 저장소
   │ 3. 가공 신호 제공
   ▼
운영•SLO 체계
   │ 4. 원인 분석
   └── 5. 복구 검증
```

### 동작 원리

1. 신호 생성: **메트릭•로그•추적•프로파일** 생성
2. 맥락 연결: **상관 식별자•자원•버전**으로 신호 연결
3. 가공 신호 제공: **정규화•필터링•샘플링** 후 보존
4. 원인 분석: 사용자 영향에서 **장애 가설 검증**
5. 복구 검증: 조치 후 **SLI의 SLO 회복** 확인

#### 한줄 요약

- 동일 요청•배포 버전 연결로 **사용자 영향•근본 원인** 추적

## Ⅴ. 종류 및 비교

<details><summary>용어 설명</summary>

- **모니터링**: 알려진 상태와 임계값을 대시보드•규칙 기반 경보로 감시하는 활동이다.
- **교차 질의**: 공통 맥락을 기준으로 서로 다른 텔레메트리 저장소의 신호를 연결해 분석하는 방법이다.

</details>

| 구분 | 텔레메트리 | 모니터링 | 관찰 가능성 |
|:---|:---|:---|:---|
| 적용 기준 | 원시 실행 신호의 **생성•전달** | 알려진 **상태•임계값** 감시 | 미지의 **내부 상태•원인** 탐색 |
| 핵심 특징 | **메트릭•로그•추적•프로파일** 수집 | **대시보드•규칙 기반 경보** | **맥락 기반 교차 질의•가설 검증** |
| 한계 | 신호만으로 **원인 설명 불가** | 미지 장애의 **탐색 취약성** | **비용•카디널리티•분석 역량** 관리 |

#### 한줄 요약

- 세 **분석 수준**은 장애를 미리 알고 있느냐로 갈리며, 알려진 실패는 임계값 감시로 싸게 잡히지만 미지 원인은 맥락 연결을 저장해 둔 만큼만 되짚을 수 있다.

## Ⅵ. 실무 고려사항 및 대책

<details><summary>용어 설명</summary>

- **카디널리티**: 텔레메트리 속성에 존재하는 고유 값의 수로 정의된다.
- **샘플링**: 비용을 통제하기 위해 전체 사건 중 일부를 선택해 저장하는 기법로 정의된다.
- **꼬리 기반 샘플링**: 전체 추적 결과를 본 뒤 오류•고지연 등 보존 가치가 높은 요청을 선택하는 방식이다.

</details>

| 문제 | 대책 | 효과 |
|:---|:---|:---|
| 추적 맥락 단절로 **원인 경로 유실** | 전파 규약 통일•경계별 **식별자 전달 검증** | **원인 경로 추적성** 확보 |
| 카디널리티 폭증으로 **저장•질의 성능 저하** | 속성 허용 목록•**카디널리티 예산•보존 등급** | **저장•질의 비용** 제한 |
| 균일 샘플링의 **희귀 오류 누락** | 오류 우선•**꼬리 기반 샘플링**•원본 로그 연계 | **관측 누락률** 감소 |

#### 한줄 요약

- 맥락 연속성을 보존하는 **카디널리티•샘플링 예산** 관리

## Ⅶ. 결론

<details><summary>용어 설명</summary>

- **카디널리티 예산**: 저장•질의 비용 한도 안에서 허용할 속성 고유 값 수를 정한 운영 기준이다.
- **원인 경로**: 사용자 영향에서 관련 서비스•자원•배포 변경을 거슬러 근본 원인까지 연결한 관계을 말한다.

</details>

- 복합 분산 마이크로서비스 및 AI 인프라의 장애 탐지, 분석, 복구를 자동화하는 **SRE 및 차세대 클라우드 운영 거버넌스의 최고 핵심 기술 표준(Cloud-Native Observability / OpenTelemetry Universal Standard / Unified MELT: Metrics, Events, Logs, Traces, Continuous Profiling / SLO-driven Alerting & Error Budget / AIOps Root Cause Analysis)의 확고한 표준**으로 확고히 자리 잡았으며, 생성형 AI 기반 이상 징후 자동 분석(AIOps)으로 진화하는 가운데, 실무 관찰 가능성 플랫폼 구축 시에는 **OTel 표준 수집 파이프라인을 구축하여 백엔드 종속성을 제거하고, 고카디널리티(High Cardinality) 태그 폭증을 제어하기 위한 카디널리티 예산 수립 및 테일 기반 샘플링(Tail-based Sampling)으로 수집 비용을 최적화하며, 단순 서버 경보가 아닌 SLO 위반(Burn Rate) 기반의 긴급 호출(PagerDuty) 연계**를 결합하여 완벽한 서비스 신뢰성과 효율적인 운영 비용을 완성

#### 한줄 요약

- 관측 가능성의 실제 제약은 수집 기술이 아니라 저장•**카디널리티 예산**이므로, **사용자 SLO**와 **원인 경로**에 기여하는 신호부터 남기고 나머지를 버리는 순서를 정하는 것이 설계의 본질이 된다.
