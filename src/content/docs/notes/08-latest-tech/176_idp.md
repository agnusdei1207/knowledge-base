## 미리 알고가기

- **내부 개발자 플랫폼(Internal Developer Platform, IDP)**: 공통 인프라·배포·운영 기능을 개발자에게 셀프서비스로 제공하는 플랫폼
- **구성 범위**: 포털, API, 자동화, 템플릿 포함
- **Golden path**: 개발자 경험 중심 설계 필요



## Ⅰ. 개요

- 정의/개념: 개발 기능을 셀프서비스로 제공하는 내부 플랫폼
- 기존 한계: 개발팀마다 인프라·배포 도구를 직접 조합하면 인지부하가 커지고 보안·운영 정책의 적용 수준이 달라진다.

### 쉽게 이해하기 (학습용)
- 주문 체계에서 표준 코스를 골라 개발 환경을 받는 내부 서비스

## Ⅱ. 특징

- 플랫폼 API가 포털·CLI의 공통 계약이 된다.
- golden path가 실행 가능한 기본값을 제공한다.
- 내장 정책이 셀프서비스와 통제를 병행한다.
- 사용 지표가 추상화와 기능 개선을 이끈다.

### 쉽게 이해하기 (학습용)
- 표준 코스에 위생 검사를 넣어 주문과 통제를 함께 만드는 방식

## Ⅲ. 아키텍처 및 구성요소

```text
인터페이스 → 제어 계층
            ┌──┴──┐
         카탈로그  자동화
            └──┬──┘
             기반 도구
               ↓
            측정 계층
```

| 설계 요소 | 설명 |
|:---|:---|
| 인터페이스 | 포털·CLI·선언 파일로 요청·상태 확인 제공 |
| 제어 계층 | 공통 계약 및 자원 상태 관리 |
| 카탈로그 | 승인된 템플릿 및 기능 정보 제공 |
| 자동화 | CI/CD·인프라 실행 및 정책 검증 |
| 측정 계층 | 지표 및 의견을 통한 개선 연결 |

> 요약: 공통 API가 셀프서비스·정책·측정을 연결

### 쉽게 이해하기 (학습용)

- 화면이나 명령으로 주문해도 같은 주문 API가 메뉴·주방·위생 규칙을 실행하고, 처리 시간과 실패 이유를 기록해 메뉴를 고치는 구조임

## Ⅳ. 원리 및 절차 흐름도

```text
요청
 ↓
검증
 ↓
선택
 ↓
정책
 ↓
생성
 ↓
갱신
```

| 절차 | 설명 |
|:---|:---|
| 기능 요청 | 인터페이스로 사양 제출함 |
| 계약 검증 | 입력 및 지원 여부 확인함 |
| 경로 선택 | Golden path 구성 결합함 |
| 정책 실행 | 보안 정책 통과 후 생성함 |
| 상태 갱신 | 카탈로그 기록 및 지표 측정함 |

> 요약: 요청 검증 후 golden path 실행·결과 환류

### 쉽게 이해하기 (학습용)

- 주문 방법이 달라도 같은 규칙으로 손님과 메뉴를 확인하고 위생 검사를 통과한 작업만 주방에 보내며 결과를 주문 장부에 남기는 과정임

## Ⅴ. 내부 플랫폼 구성 역할 비교

| 구분 | IDP | 개발자 포털 | 플랫폼 팀 |
|:---|:---|:---|:---|
| 적용 기준 | 전체 플랫폼 제품 | UI 인터페이스 | 로드맵 및 운영 |
| 핵심 특징 | API·템플릿·자동화 제공 | 탐색·요청 진입점 제공 | 플랫폼 제품 설계·운영 |
| 한계 | 통합 복잡성·종속 | 포털만으로 자동화 불가 | 사용자 없는 공급자화 |

> 요약: IDP는 제품, 포털은 화면, 팀은 운영 조직으로 구분함

### 쉽게 이해하기 (학습용)

- 식당 전체 주문·조리 체계가 IDP, 주문 화면이 포털, 메뉴와 주방을 운영하고 개선하는 사람이 플랫폼 팀임

## Ⅵ. 실무 사례

1. 웹 API 템플릿으로 저장소·CI/CD·실행 환경을 셀프서비스 제공

### 쉽게 이해하기 (학습용)

- 개발자는 검증된 템플릿을 선택해 필요한 개발·배포 환경을 직접 구성함

## Ⅶ. 결론
- 개발팀이 검증된 환경을 스스로 생성·운영하도록 하기 위해 **서비스 템플릿·정책 가드레일·확장 지점·지원 부담·채택률**을 검토하고, 반복 가능한 경로를 IDP로 제공해야 한다.

### 쉽게 이해하기 (학습용)

- 보기 좋은 주문 화면만으로는 주방이 아니며 메뉴·조리·검사·기록이 끝까지 연결되어야 실제 내부 플랫폼이 됨
