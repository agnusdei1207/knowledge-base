## Ⅰ. 개요

<details>
<summary>용어 설명</summary>

- **개발•보안•운영(Development, Security and Operations, DevSecOps)**: 개발•보안•운영이 수명주기 전반의 보안 결과를 공동 소유하는 체계을 의미한다.
- **소프트웨어 개발 수명주기(Software Development Life Cycle, SDLC)**: 요구분석부터 설계•개발•시험•배포•운영까지의 과정로 정의된다.
- **공동 소유**: 보안을 별도 심사 조직에 넘기지 않고 개발•보안•운영이 역할별 책임을 함께 지는 원칙을 말한다.

</details>

- 정의/개념: **DevSecOps**는 개발•보안•운영 조직이 **SDLC** 전반의 보안 결과를 공동 소유하고 자동 검증과 운영 피드백을 지속하는 협업•운영 체계임.
- 배경/필요성: 릴리스 직전 수동 심사의 **늦은 취약점 발견•배포 지연•공급망 변경 추적 한계** 개선이 필요하음.

#### 한줄 요약

- 출고 직전에만 검사하지 않고 설계부터 운영까지 보안 확인과 개선을 이어 간다.

## Ⅱ. 특징

<details>
<summary>용어 설명</summary>

- **Shift Left•Right**: 개발 초기의 예방 활동과 운영 단계의 탐지•피드백을 연결하는 보안 접근하는 개념이다.
- **위험도 기반 게이트**: 심각도•노출도•악용 가능성에 따라 변경 차단•승인•예외를 자동 판단하는 통제이다.

</details>

- 위협 모델과 개발 단계 검사의 **Shift Left**가 핵심임.
- 운영 탐지•사고 환류의 **Shift Right**가 핵심임.
- 위험도 기반 **자동 게이트•예외 승인**이 핵심임.
#### 한줄 요약

- 모든 경고를 막는 것이 아니라 위험을 분류해 빠르게 고치고 승인된 예외도 추적한다.

## Ⅲ. 구조 및 구성요소

<details>
<summary>용어 설명</summary>

- **정책 코드화(Policy as Code)**: 보안•준수 판단 규칙을 버전 관리하고 자동 실행 가능한 코드로 표현하는 방식을 말한다.
- **소프트웨어 자재 명세서(Software Bill of Materials, SBOM)**: 소프트웨어에 포함된 구성요소와 버전을 추적하는 명세서이다.
- **정적 애플리케이션 보안 테스트(Static Application Security Testing, SAST)**: 소스•바이트코드를 분석해 보안 결함을 찾는 시험하는 개념을 말한다.
- **소프트웨어 구성 분석(Software Composition Analysis, SCA)**: 오픈소스 의존성의 취약점•라이선스를 분석하는 시험로 정의된다.
- **위협 모델**: 보호 자산•공격자•공격 경로와 위험을 식별한 분석 모델로 정의된다.
- **보안 요구**: 식별한 위험을 예방•탐지•대응하기 위해 구현할 통제 기준을 의미한다.
- **보안 피드백**: 정적 분석•구성요소 분석 등의 결과를 개발 단계에 즉시 돌려주는 활동이다.
- **정책 게이트**: 빌드•배포물이 보안 기준과 공급망 증거를 충족할 때만 다음 단계로 통과시키는 통제로 정의된다.
- **공급망 증거**: 산출물의 구성요소•출처•서명•무결성을 검증하도록 보존한 자료이다.
- **운영 탐지**: 런타임 위협•취약점•이상 행위를 식별하는 활동을 의미한다.
- **보안 환류**: 운영에서 발견한 위험을 개발 요구와 정책에 다시 반영하는 활동을 의미한다.

</details>

개발 보안 피드백은 **SAST•SCA** 결과를 제공하고, 공급망 증거는 **SBOM**으로 구성요소를 추적한다.

```text
                    [위협 모델]
                         |
                    [보안 요구]
                         |
          +--------------+--------------+
          |              |              |
 [개발 보안 피드백] [정책 게이트] [공급망 증거]
                         |              |
                    [운영 탐지]---------+
                         |
                    [보안 환류]
```

선의 의미: 위협 모델과 보안 요구가 개발 검사•정책•공급망 증거의 기준을 제공하고, 운영 탐지와 보안 환류가 발견 위험을 기준에 되돌린다.

| 구성요소 | 책임 |
|:---|:---|
| 위협 모델 | 보호 자산•공격 경로•허용 위험 정의 |
| 보안 요구 | 위험별 예방•탐지•대응 통제 정의 |
| 개발 보안 피드백 | SAST•SCA•비밀 탐지 결과 제공 |
| 정책 게이트 | 위험도별 차단•승인•예외 적용 |
| 공급망 증거 | SBOM•서명•출처•무결성 기록 |
| 운영 탐지 | 런타임 위협•취약점 식별 |
| 보안 환류 | 운영 위험의 요구•정책 반영 |

#### 한줄 요약

- 지킬 대상을 정하고 제작 과정과 부품표를 검사하며 사용 중 문제를 다음 설계에 반영한다.

## Ⅳ. 흐름도

<details>
<summary>용어 설명</summary>

- **기한부 예외**: 차단 기준을 충족한 위험을 소유자•만료일•보완 통제와 함께 일시 허용하는 승인하는 개념로 정의된다.
- **공급망 증거 검증**: 산출물의 구성요소•출처•서명•무결성을 배포 전에 확인하는 활동이다.

</details>

```text
[위협 모델•보안 요구]
         │ 1. 보안 기준 전달
         ▼
[개발 보안 피드백]
         │ 2. 코드•의존성 검사 결과
         ▼
   [정책 게이트]
         │ 3. 위험 판정•예외 승인
         ▼
   [공급망 증거]
         │ 4. SBOM•서명 배포
         ▼
[운영 탐지•환류] ── 5. 사고•취약점 환류 ──▶ [위협 모델•보안 요구]
```

### 동작 원리

1. **보안 기준 전달**: 자산•위협과 차단 임계값 정의
2. **코드•의존성 검사 결과**: 결함 영향•수정 정보 제공
3. **위험 판정•예외 승인**: 위험별 차단 또는 기한부 예외 적용
4. **SBOM•서명 배포**: 산출물과 공급망 증거 전달
5. **사고•취약점 환류**: 사건을 위협 모델•검사 규칙에 반영

#### 한줄 요약

- 검사 결과의 실제 위험을 판정해 출고하고 운영 중 발견한 문제로 검사 규칙을 고친다.

## Ⅴ. 종류 및 비교

<details>
<summary>용어 설명</summary>

- **파이프라인 보안**: 지속적 통합•지속적 배포 과정에서 코드•의존성•비밀•산출물을 규칙 기반으로 자동 검사하는 방식이다.
- **릴리스 보안 심사**: 출시 시점에 고위험 변경을 전문가가 직접 검토하는 방식이다.
- **지속적 통합•지속적 전달(Continuous Integration and Continuous Delivery, CI/CD)**: 코드 변경을 자동 검증하고 배포 가능 상태로 전달하는 방식이다.

</details>

| 보안 적용 방식 | DevSecOps | 파이프라인 보안 | 릴리스 보안 심사 |
|:---|:---|:---|:---|
| 적용 기준 | **전 수명주기 위험 관리** | **CI/CD 자동 검사** 중심 | 고위험 변경의 **전문가 검토** |
| 핵심 특징 | **공동 책임•예방•운영 환류** | 규칙 기반 **자동 게이트** | 출시 시점 **심층 판단** |
| 한계 | **책임•도구•예외 운영** 복잡성 | **설계•런타임 위험** 사각지대 | **늦은 발견•출시 지연** |

#### 한줄 요약

- 자동 검사와 전문가 판단을 연결하되 누가 어떤 위험을 언제 고칠지 책임을 명확히 한다.

## Ⅵ. 실무 고려사항 및 대책

<details>
<summary>용어 설명</summary>

- **오탐(False Positive)**: 실제 취약하지 않거나 악용 가능성이 낮은 대상을 위험으로 잘못 판정한 결과로 정의된다.
- **격리 빌드**: 외부 변경과 비인가 접근을 제한한 환경에서 재현 가능하게 산출물을 생성하는 방식을 의미한다.
- **응용 프로그래밍 인터페이스(Application Programming Interface, API)**: 소프트웨어 기능과 데이터를 호출하기 위한 명세화된 접점을 의미한다.

</details>

| 문제 | 대책 | 효과 |
|:---|:---|:---|
| **오탐 경보**로 개발 흐름 마비 | **노출도•악용 가능성** 기반 우선순위 | **고위험 결함** 집중 |
| **예외 승인 후 영구 방치** | **소유자•만료일•보완 통제**의무화 | **잔여 위험 누적** 방지 |
| **빌드 산출물 변조** | **격리 빌드•서명•배포 전 검증** | **공급망 무결성** 확보 |

#### 한줄 요약

- 결제 **API**는 고위험 비밀•취약점만 병합을 막고 예외에는 소유자와 만료일을 붙인다.

## Ⅶ. 결론

<details>
<summary>용어 설명</summary>

- **잔여 위험**: 보완 통제와 예외 승인을 적용한 뒤에도 조직이 수용하는 보안 위험로 정의된다.
- **공급망 무결성**: 소스부터 빌드•배포까지 산출물이 승인된 구성과 절차에서 변조 없이 만들어졌음을 보장하는 성질을 의미 체계 적용

</details>

- 고위험은 **정책 게이트**로 차단하고 허용 위험은 **소유자•만료일 예외**로 추적함.

#### 한줄 요약

- 검사 수를 늘리는 것이 아니라 중요한 위험을 더 일찍 정확히 알려 안전한 변경을 빠르게 만드는 것이 목표다.
