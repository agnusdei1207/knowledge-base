## 미리 알고가기

- **리액티브 시스템**: 반응성·탄력성·복원력·메시지 구동을 갖춘 설계
- **비동기 프로그래밍**: 개별 구현이나 더 넓은 아키텍처 원칙임
- **Reactive Manifesto**: 구조적 관점에서 네 축을 정의함



## Ⅰ. 개요

- **정의/개념**: 비동기 메시지 기반 반응형 아키텍처
- **배경/필요성**: 지연·장애 전파와 부하 변화 대응

### 쉽게 이해하기 (학습용)

- 한 창구가 멈추면 줄 전체가 서는 조직이 아니라, 업무 쪽지를 독립 창구에 보내고 고장·혼잡 때 대체 창구와 인력을 조정하는 조직임

## Ⅱ. 특징

- 반응성은 일관된 응답 시간을 유지한다
- 복원력은 복제·격리로 장애 영향을 제한한다
- 탄력성은 부하에 따라 자원을 증감한다
- 메시지 구동이 결합도·장애 전파를 낮춘다

### 쉽게 이해하기 (학습용)

- 답을 제때 주고, 한 창구 고장이 옆으로 번지지 않으며, 손님 수에 맞춰 창구를 늘리고, 창구끼리는 직접 붙잡지 않고 쪽지로 협업해야 네 특성이 모두 갖춰짐

## Ⅲ. 구성요소 및 구조

| 설계 요소 | 설명 |
|:---|:---|
| 응답 경계 | 시간 초과로 관리함 |
| 메시지 채널 | 비동기 실행 분리 |
| 격리 컴포넌트 | 전파 범위 제한 |
| 감독 계층 | 실패 컴포넌트 복구 |
| 흐름 제어 | 자원과 유입량 조절 |

```text
요청·이벤트 → 응답 경계 → 비동기 메시지 채널 → 격리 컴포넌트
                 │                  │              │
                 └──── 시간 초과 ───┘         복구·감독 계층
                                    │              │
                                    └── 탄력·흐름 제어 ──┘
```

> 요약: 메시지 경계가 격리하고 복구·흐름 제어가 응답을 유지함

### 쉽게 이해하기 (학습용)

- 접수 기한, 쪽지함, 독립 창구, 고장 대응반, 혼잡에 따른 인력 배치가 연결되어 창구 하나의 문제를 전체 줄과 분리함

## Ⅳ. 원리 및 절차 흐름도

```text
요청·이벤트 → 메시지 발행 → 격리 컴포넌트 처리
                                  ↓
                        부하·장애·기한 상태 판정
                    ┌─────────────┼─────────────┐
                  정상          과부하          장애
                   ↓              ↓              ↓
               결과 메시지   유입 조절·확장   격리·복구·대체
                    └─────────────┼─────────────┘
                                  ↓
                         응답·관측값 피드백
```

| 절차 | 설명 |
|:---|:---|
| 요청 접수 | 응답 기한과 상관 식별자를 부여하고 메시지로 변환함 |
| 비동기 전달 | 주소가 지정된 격리 컴포넌트로 메시지를 전달함 |
| 상태 판정 | 처리 중 지연·대기열·자원 부하·실패 신호를 확인함 |
| 적응 처리 | 과부하는 조절·확장하고 장애는 격리·복구함 |
| 응답·피드백 | 결과·시간 초과·대체 응답을 보내고 관측값을 다음 제어에 반영함 |

> 요약: 메시지를 격리하고 부하·장애에 따라 경로를 나눈다.

### 쉽게 이해하기 (학습용)

- 쪽지를 보낸 뒤 줄 길이·고장·약속 시간을 확인해 평소에는 답하고, 몰리면 창구를 늘리거나 접수를 늦추며, 고장 나면 해당 창구만 막고 대체 창구로 보냄

## Ⅴ. 종류 및 비교

| 판단 기준 | 리액티브 시스템 | 리액티브 프로그래밍 | Reactive Streams |
|:---|:---|:---|:---|
| 적용 범위 | 분산 시스템 전체의 아키텍처 특성임 | 데이터 변화·비동기 흐름을 다루는 구현 패러다임임 | 비동기 스트림 라이브러리 간 상호운용 규약임 |
| 핵심 보장 | 반응성·복원력·탄력성·메시지 구동을 함께 설계함 | 관찰·변환·조합으로 변화 전파 코드를 구성함 | 요청량 기반의 비차단 역압력으로 버퍼를 제한함 |
| 선택 경계 | 장애·부하에도 서비스 응답을 유지해야 할 때 | 컴포넌트 내부의 비동기 데이터 흐름을 표현할 때 | 생산자·소비자 속도 차이를 표준 신호로 조절할 때 |

> 요약: 품질은 시스템, 흐름은 구현, 역압력은 스트림 영역이다.

### 쉽게 이해하기 (학습용)

- 회사 전체가 고장과 혼잡에도 응답하는 방식은 시스템, 한 직원이 변화하는 자료를 처리하는 방법은 프로그래밍, 자료를 받을 양만큼 요청하는 합의는 Streams임

## Ⅵ. 실무 사례

1. 주문 시스템은 결제·재고를 메시지로 격리하고 시간 초과 시 대체 응답을 보내며, 대기열 지연에 따라 소비자 수와 유입량을 조절함
2. 실시간 수집 파이프라인은 내부 구간에 Reactive Streams 역압력을 적용하되 장애 격리·복구와 탄력 확장·응답 기한을 별도로 설계함

### 쉽게 이해하기 (학습용)

- 주문·결제·재고 창구를 쪽지로 분리하고 줄이 길면 인력과 접수 속도를 조절하며, 자료 흐름의 역압력만 만들었다고 회사 전체가 리액티브해지는 것은 아님

## Ⅶ. 결론

- 응답·격리·복구·탄력 제어로 반응성을 검증한다

### 쉽게 이해하기 (학습용)

- 쪽지를 쓴다는 사실보다 고장과 혼잡 속에서도 약속한 시간에 답하도록 조직 전체를 설계했는지가 핵심임
