## Ⅰ. 개요

<details><summary>용어 설명</summary>

- **보안 부팅(Secure Boot)**: 전원 인가 시점부터 OS 로드까지 모든 단계의 소프트웨어 이미지에 대해 전자서명과 해시 무결성을 검증하는 부팅 메커니즘.
- **신뢰 사슬(Chain of Trust)**: 선행 부팅 단계가 차기 부팅 단계의 바이너리를 암호학적으로 검증하고 제어권을 넘기는 연쇄적 신뢰 연결 고리.

</details>

- 정의/개념: 변조 불가능한 시작점에서 출발해 다음 단계를 차례로 검증하며 **신뢰 사슬(Chain of Trust)** 확장하는 **보안 부팅(Secure Boot)**
- 배경/필요성: OS 보안 기능이 켜지기 전에 부트로더가 변조되면 그 이후의 모든 검사와 권한 체계가 함께 무력화됨

#### 한줄 요약
- 이 체계가 성립하는 조건은 사슬의 첫 고리가 물리적으로 바뀔 수 없다는 것 하나뿐이며, 그 전제가 깨지면 나머지 검증은 모두 형식이 된다.

## Ⅱ. 특징

<details><summary>용어 설명</summary>

- **하드웨어 RoT(Root of Trust)**: 물리적으로 수정이나 변조가 불가능하도록 칩 내부에 고정된 마스크 롬(Mask ROM)이나 eFuse 기반의 신뢰 시작점.
- **안티 롤백(Anti-Rollback)**: 서명이 정상이더라도 알려진 보안 취약점이 존재하는 과거 구버전 펌웨어로 다운그레이드되는 것을 차단하는 기법.

</details>

- **하드웨어 RoT(Root of Trust)** 활용 칩 내부에 고정해 변조 불가능한 시작점 확보
- 공개키 암호로 단계마다 서명을 검증하고 이미지 해시 일치를 확인
- 되돌릴 수 없는 버전 카운터로 **안티 롤백(Anti-Rollback)** 강제

#### 한줄 요약
- 서명 검증만으로는 이미 서명된 취약 버전을 막지 못하므로, 버전 카운터가 없으면 정품 펌웨어가 그대로 공격 도구가 된다.

## Ⅲ. 구조 및 구성요소

<details><summary>용어 설명</summary>

- **eFuse(OTP, One-Time Programmable)**: 제조 공정 또는 양산 단계에서 전기적으로 단 한 번만 기록하여 영구히 보존되는 불휘발성 메모리 비트.
- **매니페스트(Manifest)**: 이미지 해시, 암호 서명, 버전 정보, 로딩 주소 등의 보안 메타데이터가 담긴 헤더 구조체.

</details>

```text
[보안 부팅 신뢰 사슬]
├─ 하드웨어 신뢰 뿌리
│  ├─ 칩 내부 마스크 롬 (변경 불가 1차 부트로더)
│  └─ eFuse OTP (루트 공개키 해시·버전 카운터)
├─ 2차 부트로더 (외부 플래시 저장·메모리 초기화)
├─ OS 커널·디바이스 트리 (외부 저장장치)
└─ 시스템 앱·런타임 환경

각 단계는 자신에 첨부된 매니페스트(해시·서명·버전)로 다음 단계를 검증
```

선의 의미: 가지(`├─`)는 실행 순서이자 검증 방향이며, 위 단계가 아래 단계를 검증한 뒤에만 제어권을 넘김

| 구성요소 | 책임 |
|:---|:---|
| 하드웨어 RoT | 최초 실행 코드로서 다음 단계의 서명 검증 수행 |
| **eFuse(OTP, One-Time Programmable)** | 루트 공개키 해시와 롤백 방지 카운터 영구 보관 |
| 2차 부트로더 | 메모리 초기화와 커널 이미지 무결성 검증 |
| **매니페스트(Manifest)** | 해시·서명·버전 등 검증에 필요한 메타데이터 제공 |
| 보안 커널 | 파일시스템 무결성 검증 후 사용자 영역 실행 |

#### 한줄 요약
- 사슬이 길어질수록 검증 지점은 늘지만 신뢰의 총량은 첫 고리를 넘지 못하므로, 보강 투자는 언제나 아래쪽부터 이뤄져야 한다.

## Ⅳ. 흐름도

<details><summary>용어 설명</summary>

- **dm-verity**: 리눅스 커널에서 블록 장치의 해시 트리를 구성하여 파일시스템이 읽힐 때마다 실시간으로 변조를 감지하는 기술.

</details>

```text
전원 인가 → 마스크 롬 실행 후 루트 공개키 해시 획득
        │
   다음 단계 이미지의 서명이 유효한가?
   ┌────┴─────┐
아니오          예
   │             │
부팅 중단·      이미지 보안 버전이 허용 최저 이상인가?
복구 모드 전환   ┌──┴───┐
   │          아니오     예
   │            │        │
   │      롤백으로 판정  제어권 인계 후
   │      부팅 거부      같은 검증을 다음 단계에 반복
   └────┬───────┴────────┘
        │
   모든 단계 통과 시 런타임 진입
```

분기 결과: 서명 검사와 버전 검사가 별개로 걸려 있어 둘 중 하나만 통과해서는 진행되지 않으며, 정품 여부와 최신 여부가 서로 다른 위협을 막음

#### 한줄 요약
- 같은 검증 절차가 단계마다 반복된다는 점이 이 설계의 강점이자 부담이며, 부팅 시간이 늘어나는 대가로 침투 지점이 하나씩 봉쇄된다.

## Ⅴ. 종류 및 비교

| 부팅 보안 방식 | Secure Boot (보안 부팅) | Measured Boot (측정 부팅) | 일반 부팅 (Non-Secure) | Dual Boot (이중 부팅) |
|:---|:---|:---|:---|:---|
| 적용 기준 | 임베디드 기기·스마트폰·차량 전장 | 엔터프라이즈 PC·서버 기밀 증명 | 비보안 저가 가전 및 테스트 장비 | 개발자용 다중 OS 선택 환경 |
| 핵심 특징 | 변조 감지 시 부팅 즉각 차단 | 모든 부팅 단계 해시를 TPM PCR에 누적 | 검증 없이 플래시 코드를 그대로 실행 | 파티션 선택에 따른 다중 OS 로드 |
| 한계 | 개발 단계 서명 키 관리 오버헤드 | 변조 코드가 일단 실행될 수 있음 | 악성 부트킷/루트킷 감염에 무방비 | 부팅 보안 정책 일관성 유지 곤란 |

#### 한줄 요약
- 두 방식은 대립이 아니라 목적이 다른데, 하나는 실행을 막고 다른 하나는 무엇이 실행됐는지 증명하므로 함께 쓸 때 비로소 완결된다.

## Ⅵ. 실무 고려사항 및 대책

<details><summary>용어 설명</summary>

- **글리치 공격(Fault Injection / Glitching)**: 클록이나 전압을 순간적으로 불안정하게 만들어 CPU의 `if(verify == OK)` 검증 분기 명령을 강제로 건너뛰게 하는 물리적 해킹.

</details>

| 문제 | 대책 | 효과 |
|:---|:---|:---|
| 서명 개인키 유출 시 위조 펌웨어가 전면 허용 | 하드웨어 보안 모듈 기반 서명 인프라와 키 철회 체계 | 키 유출 방지와 유출 시 무효화 경로 확보 |
| 취약점이 있는 과거 정품 펌웨어로 되돌리는 공격 | 되돌릴 수 없는 버전 카운터를 하드웨어에서 강제 갱신 | 구버전 펌웨어 적재 차단 |
| **글리치 공격(Fault Injection / Glitching)** 기반 검증 분기 건너뛰기 | 중복 검증·결함 센서·실패 시 차단되는 제어 흐름 적용 | 단일 분기 오류만으로 우회될 가능성 축소 |
| 업데이트 실패로 기기가 부팅 불능 상태 | 이중 파티션과 이전 정상 버전 자동 복귀 구현 | 부팅 연속성 확보와 현장 복구 가능 |

#### 한줄 요약
- 보안을 강하게 걸수록 복구 경로도 함께 막히므로, 실제 설계 난제는 침입을 막는 일이 아니라 정당한 복구만 통과시키는 일이다.

## Ⅶ. 결론

- 비인가 코드의 실행 자체를 막아야 하면 신뢰 뿌리 기반 보안 부팅을, 무엇이 실행됐는지 증명해야 하면 측정 부팅을 함께 적용하고, 업데이트 가능한 제품은 롤백 방지·키 철회·이중 파티션 복구를 처음부터 함께 설계

#### 한줄 요약
- **dm-verity**까지 이어지는 사슬이 실행 시점의 무결성을 지켜 주지만 키 관리 체계가 무너지면 전부 무의미해지므로, 이 기술의 실제 수명은 운영 조직의 키 관리 역량이 정한다.
