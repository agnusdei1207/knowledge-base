## Ⅰ. 개요

<details><summary>용어 설명</summary>

- **마감시간(Deadline)**: 실시간 시스템에서 특정 태스크의 연산 결과가 유효성을 유지하기 위해 완수되어야 하는 엄격한 시간 한계.
- **효용 함수(Utility Function)**: 작업 완료 시점에 따라 시스템에 제공되는 가치(Value)나 유용성의 크기를 나타내는 수학적 모델.

</details>

- 정의/개념: **마감시간(Deadline)**을 넘겼을 때 **효용 함수(Utility Function)**가 어떻게 떨어지는지에 따라 하드·펌·소프트로 나누는 실시간 분류 체계
- 배경/필요성: 모든 지연을 같은 실패로 다루면 안전 태스크는 충분히 보호되지 않고 품질 태스크에는 필요 이상의 자원이 들어감

#### 한줄 요약
- 이 분류의 기준은 얼마나 급한가가 아니라 늦었을 때 결과가 얼마나 쓸모없어지는가이며, 급함과 심각도는 서로 다른 축이다.

## Ⅱ. 특징

<details><summary>용어 설명</summary>

- **하드 마감시간(Hard Deadline)**: 마감시간 위반을 허용하지 않아 설계 단계에서 최악 응답시간 충족을 입증해야 하는 시간 제약.
- **QoS 저하(Graceful Degradation)**: 소프트 실시간 환경에서 지연 발생 시 서비스가 중단되는 대신 화질 저하 등으로 품질을 점진적으로 낮추는 기법.

</details>

- 하드: **하드 마감시간(Hard Deadline)** 위반을 허용하지 않으며 위반 시 위험 상태로 전이
- **펌(Firm)**: 마감시간을 넘긴 결과의 효용 가치는 0이 되어 즉시 폐기되나 시스템 파국은 없음
- 소프트: 초과 후에도 결과가 유효하며 **QoS 저하(Graceful Degradation)**로 완만하게 효용 감소

#### 한줄 요약
- 셋 중 하드만 설계 단계에서 증명을 요구하고 나머지는 운영 중 관측으로 관리되므로, 분류를 잘못하면 검증 비용이 통째로 어긋난다.

## Ⅲ. 구조 및 구성요소

<details><summary>용어 설명</summary>

- **효용 곡선(Time-Utility Curve)**: 시간 경과에 따른 가치 변화를 시각화한 그래프로, Hard는 음의 무한대, Firm은 0으로 수직 낙하, Soft는 점진 감쇄 곡선을 가짐.

</details>

```text
[마감시간 이후 효용 변화]
├─ 마감시간 이전
│  └─ 세 범주 모두 효용 유지
└─ 마감시간 이후
   ├─ 소프트: 효용이 완만하게 감소 (스트리밍·게임)
   ├─ 펌    : 효용이 즉시 0으로 하락 (시세·표적 추적)
   └─ 하드  : 효용이 음수로 전환 (에어백·원전 제어)
```

선의 의미: 가지(`├─`)는 마감시간 전후의 구분이며, 아래로 갈수록 같은 지연이 만드는 피해가 커짐

| 구성요소 | 책임 |
|:---|:---|
| 하드 실시간 | 최악 응답 시간이 마감시간 이내임을 사전 입증 |
| 펌 실시간 | 초과한 결과를 즉시 폐기하고 최신 데이터 획득 우선 |
| 소프트 실시간 | 버퍼링과 품질 조절로 체감 지연 완화 |
| 감시 타이머 | 시작·종료 시각 계측과 위반 시 예외 경로 기동 |
| 안전 상태 전환기 | 하드 위반 감지 시 사전 정의된 안전 정지로 전환 |

#### 한줄 요약
- **효용 곡선(Time-Utility Curve)**의 모양이 곧 설계 요구를 정하므로, 범주 이름을 정하는 일은 이미 대응 전략을 절반 정한 것과 같다.

## Ⅳ. 흐름도

<details><summary>용어 설명</summary>

- **폴백(Fallback)**: 제어 연산 마감시간 초과 시 이전 안전 제어값을 재사용하거나 기본값으로 전환하는 비상 기법.

</details>

```text
이벤트·센서 데이터 수신
        │
   태스크의 마감시간 범주 확인 후 선점 스케줄링
        │
   마감시간 안에 완료됐는가?
   ┌────┴─────┐
  예           아니오
   │             │
정상 출력·      어느 범주인가?
액추에이터 구동  ┌────┼──────┐
   │          하드     펌      소프트
   │           │       │        │
   │      안전 정지  결과 폐기  지연 결과 수용
   │      또는 폴백  후 다음     후 품질 조정
   │       진입      주기 대기      │
   └────┬──────┴───────┴──────────┘
        │
   위반 빈도 기록 후 우선순위·예산 재조정
```

분기 결과: 같은 마감 초과라도 하드는 시스템을 멈추고 펌은 데이터를 버리며 소프트는 그대로 내보내므로, 예외 처리 비용이 범주 사이에서 자릿수 단위로 갈림

#### 한줄 요약
- **폴백(Fallback)** 경로가 설계돼 있느냐가 하드 실시간의 실질이며, 마감을 지키는 코드보다 못 지켰을 때의 코드가 안전을 결정한다.

## Ⅴ. 종류 및 비교

| 실시간 시스템 범주 | 하드 실시간 (Hard RT) | 펌 실시간 (Firm RT) | 소프트 실시간 (Soft RT) | 비실시간 (Non RT) |
|:---|:---|:---|:---|:---|
| 적용 기준 | 차량 ABS, 에어백, 원전 제어, 항공 항법 | 초단타 주식 거래, 레이더 타깃 추적 | 동영상 스트리밍, 온라인 게임, 웹 서버 | 배치 데이터 분석, 컴파일러, 문서 편집 |
| 핵심 특징 | 마감시간 미스 시 시스템 전체 붕괴 및 인명 사고 | 마감 초과 결과는 효용 0 (즉시 폐기) | 마감 초과 시 품질 저하(QoS), 동작 유지 | 마감시간 개념 부재, 총 처리량(Throughput) 중심 |
| 한계 | WCET 입증 및 정적 분석 난이도 극상 | 잦은 데이터 드롭 시 제어 연속성 저하 | 사용자 경험(UX) 불만족 및 지연 누적 | 응답 시간 예측 불가 및 실시간 제어 불가 |

#### 한줄 요약
- 네 범주는 시간 제약의 강도가 아니라 늦은 결과를 어떻게 처리할지의 규칙이며, 그 규칙이 없으면 어떤 범주로 부르든 실시간이 아니다.

## Ⅵ. 실무 고려사항 및 대책

<details><summary>용어 설명</summary>

- **지터(Jitter)**: 주기적 태스크의 실행 시작 또는 완료 시각이 기준 주기에서 벗어나는 시간적 변동 편차.

</details>

| 문제 | 대책 | 효과 |
|:---|:---|:---|
| 하드 태스크의 최악 응답 시간이 마감을 초과 | 실행 시간·블로킹·간섭과 **지터(Jitter)**를 포함한 응답 분석 | 미충족 경로를 배포 전에 식별 |
| 펌 태스크에서 지연이 누적돼 큐가 계속 밀림 | 지연 프레임 즉시 폐기 후 최신 기준점으로 동기화 | 최신성 복원과 누적 지연 해소 |
| 소프트 태스크가 네트워크 지연으로 끊김 발생 | 적응형 비트레이트와 동적 버퍼 확대 적용 | 연속성 유지와 체감 품질 개선 |
| 하드와 소프트 태스크가 자원을 공유해 간섭 | 시간·메모리·대역폭 예약과 우선순위 상한 적용 | 안전 태스크 간섭 상한 확보와 예산 분리 |

#### 한줄 요약
- 대책이 범주마다 정반대 방향인데, 하드는 지연을 막고 펌은 지연된 것을 버리며 소프트는 지연을 받아들이므로 한 정책으로 묶는 순간 셋 다 실패한다.

## Ⅶ. 결론

- 마감 위반이 곧 안전 실패면 하드, 늦은 결과가 무가치하면 펌, 품질만 낮아지면 소프트로 분류하되, 분류명이 아니라 최악 응답 시간과 오버런 대책·안전 상태 정의까지 함께 검증

#### 한줄 요약
- 실무에서 가장 잦은 실패는 스케줄링이 아니라 분류 자체가 틀린 경우이며, 소프트로 다뤄 온 태스크가 사실 하드였다는 사실은 대개 사고로 드러난다.
