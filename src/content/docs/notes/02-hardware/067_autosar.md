## Ⅰ. 개요

<details><summary>용어 설명</summary>

- **AUTOSAR(AUTomotive Open System ARchitecture)**: 글로벌 자동차 제조사(OEM)와 부품사(Tier-1)가 공동 개발한 개방형 자동차 전장 소프트웨어 표준 플랫폼.
- **RTE(Runtime Environment)**: 애플리케이션 소프트웨어 컴포넌트(SWC)와 하부 기본 소프트웨어(BSW) 간의 통신을 중계하는 미들웨어 계층.

</details>

- 정의/개념: 차량 전장 소프트웨어의 재사용성과 이식성을 높이기 위해 **계층형 아키텍처(Application-RTE-BSW-MCAL)** 를 표준화한 글로벌 개방형 자동차 전장 플랫폼
- 배경/필요성: ECU·공급사·차종별 인터페이스와 기반 소프트웨어가 달라지면 통합 검증과 기능 재사용 비용 반복

#### 한줄 요약
- 차량 기능의 인터페이스와 기반 계층을 표준화해 ECU·공급사 사이의 교환과 재사용 범위를 넓힌다.

## Ⅱ. 특징

<details><summary>용어 설명</summary>

- **VFB(Virtual Function Bus)**: 하드웨어 배치와 무관하게 소프트웨어 컴포넌트 간 통신을 가상화하여 설계하는 추상화 버스.
- **ARXML(AUTOSAR XML)**: 시스템 토폴로지, 통신 매트릭스, 소프트웨어 컴포넌트 인터페이스 설정을 기술하는 표준 교환 포맷.

</details>

- RTE·BSW·MCAL 계층으로 **SWC의 하드웨어 의존성**을 제한
- 실시간 딥 제어용 **Classic Platform**과 고성능 서비스 기반 **Adaptive Platform** 이원화
- **ARXML 표준 기술서** 기반의 모델 주도 개발(MDD) 및 자동 코드 생성 툴체인 지원

#### 한줄 요약
- 제어용 칩에는 Classic, 고성능 자율주행 컴퓨터에는 Adaptive를 적용하며, 표준 XML 명세로 자동 코딩을 지원한다.

## Ⅲ. 구조 및 구성요소

<details><summary>용어 설명</summary>

- **SWC(Software Component)**: 차량의 특정 제어 기능을 구현한 최상위 독립 소프트웨어 모듈.
- **BSW(Basic Software)**: OS, 메모리 관리, CAN/LIN 통신 스택, 진단(UDS) 등 공통 필수 서비스를 제공하는 계층.
- **MCAL(Microcontroller Abstraction Layer)**: 특정 반도체 칩의 레지스터를 직접 제어하는 최하위 하드웨어 드라이버 계층.

</details>

```text
┌─────────────────────────────────────────────────────────────┐
│ AUTOSAR Classic Platform 계층 구조                          │
│                                                             │
│  [ 응용 소프트웨어 컴포넌트 계층 (Application SWC Layer) ]  │
│  ┌──────────────┐    ┌──────────────┐    ┌──────────────┐   │
│  │ 엔진 제어 SWC│    │ 브레이크 SWC │    │ 램프 제어 SWC│   │
│  └──────┬───────┘    └──────┬───────┘    └──────┬───────┘   │
│         │ (Port / Interface)│                   │           │
│  ┌──────▼───────────────────▼───────────────────▼─────────┐ │
│  │ 런타임 환경 (Runtime Environment, RTE) - 가상 버스 매핑 │ │
│  └──────────────────────────┬─────────────────────────────┘ │
│                             ▼                               │
│  ┌────────────────────────────────────────────────────────┐ │
│  │ 기본 소프트웨어 (Basic Software, BSW)                   │ │
│  │  ┌──────────────────┐ ┌──────────────────┐ ┌────────┐  │ │
│  │  │ 서비스 (OS/진단) │ │ 통신 (CAN/Ethernet)│ │ 메모리 │  │ │
│  │  ├──────────────────┴─┴──────────────────┴─┴────────┤  │ │
│  │  │ ECU 추상화 & 복합 드라이버 (ECU Abstraction / CDD)│  │ │
│  │  ├───────────────────────────────────────────────────┤  │ │
│  │  │ 마이크로컨트롤러 추상화 계층 (MCAL)               │  │ │
│  │  └───────────────────────────────────────────────────┘  │ │
│  └──────────────────────────┬─────────────────────────────┘ │
│                             ▼                               │
│  [ 하드웨어 마이크로컨트롤러 (Microcontroller Hardware) ]   │
└─────────────────────────────────────────────────────────────┘
```

선의 의미: 상위 SWC가 RTE를 통해 BSW 및 MCAL 드라이버를 거쳐 물리 하드웨어 마이크로컨트롤러로 하향 통신

| 구성요소 | 책임 |
|:---|:---|
| 애플리케이션 SWC | 포트와 인터페이스로 정의된 차량 기능 로직 수행 |
| 런타임 환경 (RTE) | SWC 간 내부 통신 및 BSW 서비스 호출을 중계하는 자동 생성 미들웨어 |
| 서비스 계층 (Services) | OSEK/VDX 기반 실시간 OS, 통신 네트워크 매니저, 진단(UDS/DEM) 서비스 제공 |
| ECU 추상화 계층 | 상위 BSW에 외부 칩(트랜시버, 외장 플래시 등)을 포함한 통합 인터페이스 제공 |
| MCAL 드라이버 계층 | 마이크로컨트롤러 내부의 타이머, ADC, CAN, PWM 레지스터 직접 제어 |

#### 한줄 요약
- 응용 SWC, 통신 중계 RTE, 공통 서비스 BSW, 칩 종속 MCAL이 4단계 수직 분리 구조를 형성한다.

## Ⅳ. 흐름도

<details><summary>용어 설명</summary>

- **Runnable**: 특정 이벤트(주기 타이머, 데이터 수신 등)에 의해 RTE에 의해 트리거되어 실행되는 SWC 내부의 최소 함수 단위.

</details>

```text
시스템 요구사항 및 통신 매트릭스 정의
      │
      ▼
1. 모델링
      │
      ▼
2. BSW 파라미터 튜닝
      │
      ▼
3. 코드 자동 생성
      │
      ▼
4. 통합 빌드
      │
      ▼
5. 실시간 런타임 구동
```

**동작 원리**

1. **모델링**: 아키텍트가 ARXML 표준 형식으로 SWC 간 연결 관계와 CAN 통신 시그널 매핑
2. **BSW 파라미터 튜닝**: 타깃 마이크로컨트롤러 클록, 통신 보드레이트, 메모리 섹션 설정
3. **코드 자동 생성**: AUTOSAR 생성기가 튜닝된 파라미터를 기반으로 RTE 및 BSW C 코드를 자동 합성
4. **통합 빌드**: 개발자가 작성한 순수 알고리즘 C 코드와 자동 생성된 프레임워크를 링커로 결합
5. **실시간 런타임 구동**: OS 타이머 틱에 따라 RTE가 SWC의 Runnable 함수를 정확한 주기로 호출

#### 한줄 요약
- ARXML 모델링 → 툴체인 설정 → RTE/BSW 자동 코드 생성 → 통합 빌드 → RTE 런타임 구동 순으로 완성된다.

## Ⅴ. 종류 및 비교

| AUTOSAR 플랫폼 범주 | AUTOSAR Classic | AUTOSAR Adaptive | Non-AUTOSAR 레거시 | ROS 2 / AP-Linux |
|:---|:---|:---|:---|:---|
| 적용 기준 | 제동·조향·엔진 등 실시간 결정론적 ECU | 자율주행·인포테인먼트·도메인 제어기 | 초저가 단일 목적 단순 센서 노드 | 자율주행 로보틱스 연구 및 시제품 |
| 핵심 특징 | 정적 구성과 신호·서비스 기반 ECU 통신 | POSIX 기반 서비스 지향 애플리케이션 | 제품별 최소 전용 구성 | DDS 기반 노드·토픽 통신 |
| 한계 | 동적 서비스와 고성능 애플리케이션에 제약 | 복잡한 배포·서비스 관리와 큰 자원 요구 | 표준 인터페이스·도구 재사용 범위 제한 | 차량 양산 플랫폼 통합·안전 증거 별도 필요 |

#### 한줄 요약
- 실시간 섀시 제어는 Classic, 고성능 AI 도메인은 Adaptive, 단순 센서는 레거시, 시제품은 ROS 2를 쓴다.

## Ⅵ. 실무 고려사항 및 대책

<details><summary>용어 설명</summary>

- **E2E(End-to-End) 보호**: 차량 네트워크 통신 중 데이터 변조, 유실, 순서 바뀜을 감지하기 위해 CRC와 카운터를 붙이는 기능 안전 프로토콜.

</details>

| 문제 | 대책 | 효과 |
|:---|:---|:---|
| 툴체인·ARXML 스키마 버전 불일치에 따른 **통합 오류** | 메타모델 버전 고정과 ARXML 유효성·참조 CI 검증 | 설정 충돌을 생성·통합 전에 탐지 |
| BSW 계층 오버헤드로 인한 **ECU 메모리(Flash/RAM) 부족** | 미사용 BSW 모듈 비활성화 및 복합 드라이버(CDD)로 긴급 I/O 직결 | 바이너리 풋프린트 축소 및 마진 확보 |
| 통신 데이터의 유실·순서 오류·위조 위험 | **E2E 보호**로 전송 오류를, SecOC로 진위·신선도를 검증 | 기능 안전 오류와 보안 위조의 검출 목적 분리 |
| SDV의 **무선 소프트웨어 업데이트** 실패 | Adaptive UCM 또는 플랫폼별 업데이트 관리와 A/B 롤백 적용 | 손상 이미지 활성화 방지와 이전 버전 복구 |

#### 한줄 요약
- ARXML CI 검증으로 오류를 막고, E2E/SecOC로 기능 안전을 확보하며, UCM으로 안전한 OTA를 구현한다.

## Ⅶ. 결론

- 정적 제어와 작은 ECU는 **Classic**, 동적 서비스·고성능 컴퓨팅은 Adaptive 선택
- SDV는 두 플랫폼을 E2E·SecOC·게이트웨이 정책으로 연계하되 기능·안전 경계를 명확히 분리

#### 한줄 요약
- 표준화된 계층 분리와 ARXML 툴체인을 통해 차량 소프트웨어의 품질과 재사용성을 극대화해야 한다.
