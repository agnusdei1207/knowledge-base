## Ⅰ. 개요

<details><summary>용어 설명</summary>

- **하드웨어 지원 가상화(Hardware-Assisted Virtualization)**: CPU 명령어 세트 수준에서 가상화 전용 실행 모드(Intel VT-x / AMD-V)를 지원하여 게스트 OS를 수정 없이 물리 CPU에서 직접 실행하는 기술.
- **EPT(Extended Page Tables)**: 게스트 물리 주소(GPA)를 호스트 물리 주소(HPA)로 CPU 하드웨어 MMU가 2단계로 직접 변환해 주는 중첩 페이징 기술(AMD는 NPT).

</details>

- 정의/개념: CPU에 가상화 전용 실행 모드와 **EPT(Extended Page Tables)** 2단계 주소 변환을 넣어 수정 없는 게스트 OS를 직접 실행시키는 **하드웨어 지원 가상화(Hardware-Assisted Virtualization)**
- 배경/필요성: 특권 명령을 소프트웨어로 가로채 변환하는 방식은 오버헤드가 커서, 명령어 수준의 하드웨어 지원 없이는 실용적 성능이 나오지 않음

#### 한줄 요약
- 가상화가 널리 퍼진 계기는 소프트웨어 기법의 발전이 아니라 CPU가 이 문제를 자기 일로 받아들인 것이며, 그 시점에 클라우드의 전제 조건이 갖춰졌다.

## Ⅱ. 특징

<details><summary>용어 설명</summary>

- **VMX Root / Non-Root 모드**: 하이퍼바이저가 제어권을 갖는 특권 영역(Root)과 게스트 OS 및 앱이 격리 구동되는 비특권 가상화 영역(Non-Root).
- **VMCS(Virtual Machine Control Structure)**: 게스트/호스트 레지스터 상태와 VM-Exit 트랩 조건을 하드웨어적으로 저장하는 4KB 물리 메모리 블록(AMD는 VMCB).

</details>

- **VMX Root / Non-Root 모드** 기반 하이퍼바이저와 게스트의 실행 권한을 하드웨어에서 구분
- **VMCS(Virtual Machine Control Structure)**는 문맥과 전환 조건을 하드웨어 수준에서 보관
- 2단계 중첩 페이징으로 소프트웨어 섀도 페이지 테이블 관리 부담 제거

#### 한줄 요약
- 세 기능이 모두 하이퍼바이저가 하던 일을 CPU로 옮긴 것이므로, 가상화 성능 향상의 역사는 소프트웨어가 손을 떼 온 과정과 같다.

## Ⅲ. 구조 및 구성요소

<details><summary>용어 설명</summary>

- **VM-Exit & VM-Entry**: 하이퍼바이저에서 게스트로 진입하는 동작(VM-Entry)과 게스트의 특권 명령 실행 시 하이퍼바이저로 트랩되는 동작(VM-Exit).
- **VT-d(Intel Virtualization Technology for Directed I/O)**: PCIe 디바이스(NIC, GPU)를 게스트 VM에 1:1 패스스루 직결할 때 하드웨어 DMA 주소 변환 및 인터럽트 격리를 제공하는 기술.

</details>

```text
[하드웨어 지원 가상화 구조]
├─ 게스트 계층 (Non-Root 모드)
│  └─ 수정 없는 게스트 OS와 응용
├─ CPU 가상화 엔진
│  ├─ VMCS 제어 블록 (게스트·호스트 상태·트랩 조건)
│  ├─ 중첩 페이징 MMU (게스트 물리 → 호스트 물리 변환)
│  └─ 입출력 주소 변환기 (장치 직결 시 DMA·인터럽트 격리)
└─ 하이퍼바이저 계층 (Root 모드)
   └─ 가상 CPU 스케줄링과 자원 통제
```

선의 의미: 가지(`├─`)는 소유 관계이며, 게스트와 하이퍼바이저는 직접 호출하지 않고 CPU 가상화 엔진을 통해서만 오감

| 구성요소 | 책임 |
|:---|:---|
| 게스트 VM | 수정 없는 표준 OS가 물리 CPU에서 직접 실행 |
| 하이퍼바이저 | 가상 CPU 스케줄링과 시스템 자원 통제 |
| VMCS 제어 블록 | 양측 레지스터 상태와 트랩 발생 원인 기록 |
| 중첩 페이징 MMU | **GPA to HPA 변환**을 하드웨어에서 2단계로 수행 |
| **VT-d(Intel Virtualization Technology for Directed I/O)** | 장치 직결 시 DMA 주소 변환과 인터럽트 격리 |

#### 한줄 요약
- 격리가 소프트웨어 규약이 아니라 CPU 모드로 구현돼 있어 게스트가 하이퍼바이저 코드를 장악해도 모드 경계 자체는 넘지 못한다.

## Ⅳ. 흐름도

<details><summary>용어 설명</summary>

- **GPA to HPA 변환**: 게스트 OS가 인식하는 물리 주소(Guest Physical Address)를 실제 호스트 머신의 물리 메모리 주소(Host Physical Address)로 매핑하는 과정.

</details>

```text
하이퍼바이저가 제어 블록에 게스트 초기 상태 기록
        │
   게스트 모드로 진입해 실행 시작
        │
   실행 중인 명령이 트랩 조건에 해당하는가?
   ┌────┴─────┐
아니오          예
   │             │
물리 CPU에서    상태를 제어 블록에 저장하고
그대로 실행     하이퍼바이저 모드로 탈출
   │             │
   │        요청 종류를 판별해 소프트웨어로 대행
   │             │
   │        처리 완료 후 게스트로 재진입
   └────┬────────┘
        │
   게스트 실행 계속
```

분기 결과: 왼쪽 경로는 비용이 0에 가깝고 오른쪽 경로만 수천 사이클을 소모하므로, 가상화 성능은 전환 비용이 아니라 전환 빈도가 결정

#### 한줄 요약
- **VM-Exit & VM-Entry** 횟수가 성능 지표가 되는 이유가 여기에 있으며, CPU 사용률이 낮아도 전환이 잦으면 체감 성능은 무너진다.

## Ⅴ. 종류 및 비교

| CPU 가상화 기술 | 하드웨어 지원 가상화 (VT-x) | 바이너리 변환 전가상화 | 준가상화 (Para-Virt) | OS 컨테이너 가상화 |
|:---|:---|:---|:---|:---|
| 적용 기준 | 현대 클라우드/엔터프라이즈 가상화 | 레거시 하드웨어 전가상화 | 고성능 전용 리눅스 환경 | 경량 마이크로서비스 배포 환경 |
| 핵심 특징 | CPU VMX 모드 및 EPT 하드웨어 가속 | 소프트웨어가 특권 명령 실시간 패치 | 게스트 OS 커널 수정(Hypercall) | 단일 호스트 커널 공유(cgroups/ns) |
| 한계 | 빈번한 VM-Exit 발생 시 전환 오버헤드 | 소프트웨어 바이너리 변환 오버헤드 극심 | Windows 등 상용 비공개 OS 수정 불가 | 호스트 커널 공유로 인한 보안 격리 취약 |

#### 한줄 요약
- 네 방식은 격리 강도와 자원 밀도를 맞바꾼 눈금이며, 커널을 공유할수록 가벼워지지만 한 커널의 결함이 전체로 번질 여지도 함께 커진다.

## Ⅵ. 실무 고려사항 및 대책

<details><summary>용어 설명</summary>

- **SR-IOV(Single Root I/O Virtualization)**: 단일 물리 PCIe 장치를 다수의 독립된 가상 기능(VF)으로 분할하여 VM에 하이퍼바이저 경유 없이 직결하는 기술.
- **휴지 페이지(Huge Pages, 2MB/1GB)**: 기본 4KB 대신 대용량 페이지를 사용하여 EPT 2단계 주소 변환 시 TLB 캐시 미스(Miss)를 대폭 줄이는 기법.

</details>

| 문제 | 대책 | 효과 |
|:---|:---|:---|
| 빈번한 입출력으로 모드 전환 비용 누적 | **SR-IOV(Single Root I/O Virtualization)** 또는 반가상 드라이버 적용 | 제어 유연성과 데이터 경로 비용의 절충 |
| 2단계 변환으로 페이지 워크 비용 증가 | **휴지 페이지(Huge Pages, 2MB/1GB)** 및 페이지 배치 최적화 | 변환 캐시 도달 범위 확대와 워크 감소 |
| 가상 CPU와 메모리가 다른 노드에 배치돼 지연 | 가상 CPU·메모리·입출력을 같은 노드에 고정 | 원격 접근 트래픽 감소 |
| 코어·캐시 공유로 인한 사이드채널 노출 | 완화 기능과 코어 스케줄링 격리를 위협 모델에 맞춰 적용 | 성능 비용과 테넌트 간 정보 노출 위험 절충 |

#### 한줄 요약
- 네 대책 모두 가상화 계층을 우회하는 방향인데, 우회할수록 빨라지지만 마이그레이션과 관측 같은 가상화의 원래 이점도 함께 사라진다.

## Ⅶ. 결론

- 서로 다른 커널과 강한 격리가 필요하면 하드웨어 가상화 기반 가상 머신을, 같은 커널로 밀도를 높여야 하면 컨테이너를 선택하고, 장치 직결은 저지연 입출력이 마이그레이션·관측성 제약보다 중요할 때만 선별 적용

#### 한줄 요약
- 가상화 오버헤드는 CPU 사용률에 나타나지 않고 전환 횟수와 메모리 경로에 숨어 있으므로, 일반 성능 지표만 보면 원인을 끝내 찾지 못한다.
