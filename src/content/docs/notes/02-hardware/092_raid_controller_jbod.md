## Ⅰ. 개요

<details><summary>용어 설명</summary>

- **레이드 컨트롤러(RAID Controller)**: 하드디스크 여러 개를 한 덩어리로 묶고, 에러 나면 스스로 고쳐주는 비싸고 똑똑한 하드웨어 전용 카드이다.
- **제이보드(Just a Bunch of Disks, JBOD)**: "난 묶는 거 몰라" 하고 깡통 디스크들을 그냥 낱개로 무식하게 냅다 던져버리는 방식이다.
- **소프트웨어 정의 스토리지(Software Defined Storage, SDS)**: 비싼 레이드 카드 다 버리고, 싸구려 깡통 디스크(JBOD)들을 수백 개 깔아서 소프트웨어로 알아서 복제하고 관리하는 클라우드식 저장 마법이다.

</details>

- 정의: 하드디스크가 뻗었을 때 살려내는(복구) 책임을 비싼 하드웨어 카드(**RAID 컨트롤러**)한테 떠넘길지, 아니면 깡통 디스크들을 깔아놓고 소프트웨어(**JBOD**)가 알아서 복제하게 놔둘지 가르는 스토리지 2대 진영
- 배경: 옛날엔 서버 한 대 안 죽게 하려고 비싼 레이드 카드를 달았지만, 요새는 클라우드 서버 만 대를 깔아놓고 디스크 뻗으면 소프트웨어가 옆 노드로 복제해 버리는 무식한 방식이 판을 치기 때문

#### 한줄 요약

- 하드웨어 칩이 알아서 디스크를 묶고 보호하면 RAID이고, 낱개로 까놓고 소프트웨어가 관리하면 JBOD이다.

## Ⅱ. 특징

<details><summary>용어 설명</summary>

- **비비유/플래시 백업 유닛(BBU/Flash Backup Unit)**: 정전 나서 서버가 꺼져도, 배터리 힘으로 저장 중이던 데이터를 꽉 쥐고 버티는 생명줄 장치이다.
- **에이치비에이 패스스루 모드(HBA Passthrough Mode)**: 레이드 카드의 오지랖(묶기)을 강제로 끄고, 깡통 디스크 100개를 운영체제에 낱개 그대로 직통으로 꽂아주는 모드이다.
- **리빌드 페널티(Rebuild Penalty)**: 레이드로 묶인 디스크가 하나 고장 났을 때, 새 디스크 끼우고 데이터 복구하느라 며칠 동안 서버가 멈추다시피 헐떡대는 지옥의 패널티이다.

</details>

- 비싼 레이드 카드에 배터리(**BBU**)랑 캐시를 달아서 정전 나도 데이터를 지켜내고 10배 빨리 저장함(RAID).
- 레이드 카드 다 떼버리고, 생짜 디스크 100개를 소프트웨어한테 다이렉트로 던져주는 **에이치비에이 패스스루 모드** 시전(JBOD).
- 레이드로 묶어놓으면 디스크 고장 났을 때 복구하느라 며칠 동안 서버가 멈추다시피 헐떡댐(**리빌드 페널티**).

#### 한줄 요약

- RAID는 배터리 캐시와 하드웨어 복구를 앞세우고, JBOD는 하드웨어 간섭 없이 디스크 상태를 날것으로 까발린다.

## Ⅲ. 구조 및 구성요소

<details><summary>용어 설명</summary>

- **레이드 엔진(RAID Engine, XOR/P+Q Engine)**: 하드디스크 10개를 1개처럼 묶고, 디스크 하나 죽었을 때 복구하기 위한 수학 계산(패리티)을 미친 듯이 돌려대는 하드웨어 가속기이다.
- **패스스루 컨트롤러(Passthrough Controller)**: 디스크들을 묶지 않고 제이보드(JBOD)처럼 1:1로 통과시켜 주는 깡통 커넥터이다.

</details>

```text
[ 스토리지 이중화 십자포화 프레임워크 ]
                          [ 호스트 서버 ]
                          /             \
            (돈 바른 RAID 길)          (무식한 JBOD 길)
                    ▼                       ▼
           [ 보호 쓰기 캐시 (BBU) ]    [ 패스스루 컨트롤러 ]
                    │                       │
      [ 레이드 엔진 (패리티 빡계산) ]           │
                    \                       /
                     [ 물리 디스크 (HDD/SSD) ]
```

| 구성요소 | 책임 |
|:---|:---|
| 호스트 | "이 데이터 안전하게 저장해!" 하고 디스크 덩어리(LUN)나 개별 디스크에 냅다 명령을 갈기는 메인 서버 |
| 보호 쓰기 캐시 | **비비유(BBU)** 배터리 등에 업고서, 전원이 뽑혀도 저장 중이던 데이터를 꽉 쥐고 버티는 생명줄 캐시 |
| **레이드 엔진** | 하드디스크 10개를 1개처럼 묶고, 에러 복구용 수학 계산(XOR 패리티)을 미친 듯이 돌려대는 하드웨어 가속기 |
| **패스스루 컨트롤러** | "난 묶는 거 몰라" 하면서 디스크 10개를 OS에 낱개 10개로 쿨하게 던져버리는 **제이보드(JBOD)** 커넥터 |
| 물리 디스크 | 실제로 데이터를 짱박아두고 뻑나면 S.M.A.R.T 진단값으로 "나 죽어간다"고 비명 지르는 하드/SSD |

#### 한줄 요약

- RAID는 캐시와 엔진을 거쳐 안전하게 묶어 저장하고, 패스스루(JBOD)는 그냥 디스크를 다이렉트로 통과시킨다.

## Ⅳ. 흐름도

<details><summary>용어 설명</summary>

- **라이트 백 vs 라이트 스루(Write-Back vs Write-Through)**: 메모리(캐시)에만 쓱 적어놓고 "다 썼다!" 하고 사기 치는 고속 방식(라이트 백)과, 진짜 디스크에 박힐 때까지 굼벵이처럼 기다리는 안전 방식(라이트 스루)이다.

</details>

```text
[ 하드웨어 레이드 및 소프트웨어 정의 디스크 십자포화 분기 흐름 ]
                                 │
                                 ▼
    [ 1. 사상 검증: 돈 발라서 RAID로 갈지, 소프트웨어 SDS(JBOD)로 갈지 노선 정함 ]
                                 │
                 ┌───────────────┴───────────────┐
             ( RAID 노선 )                   ( JBOD 노선 )
                 ▼                               ▼
 [ 2. 캐시 버티기: 배터리 달린 캐시에 저장 ]  [ 4. 낱개 던지기: 디스크를 낱개로 줌 ]
                 │                               │
                 ▼                               ▼
 [ 3. 하드웨어 짬처리: 레이드 카드가 알아서 ]  [ 5. 소프트웨어 복제: 클라우드 SW가 ]
 [ 쪼개고 복구용 패리티 박아서 저장함 ]       [ 옆 서버에 2~3개씩 무식하게 복사함 ]
                 │                               │
                 └───────────────┬───────────────┘
                                 ▼
                         [ 쓰기 완료 보고 ]
```

### 동작 원리

1. 사상 검증: 하드웨어 **RAID 컨트롤러**로 묶을지, 까놓고 **제이보드(JBOD) & SDS** 소프트웨어 분산으로 돌릴지 노선을 정함.
2. 캐시 버티기(RAID): 배터리 달린 **라이트 백** 캐시에 데이터를 쑤셔 박고 "저장 끝!" 하고 사기 쳐서 속도를 뻥튀기함.
3. 하드웨어 짬처리: 레이드 카드(**레이드 엔진**)가 알아서 패리티 쪼개고 여러 디스크에 흩뿌려서 저장함.
4. 낱개 던지기(JBOD): 패스스루 컨트롤러로 디스크를 낱개로 OS에 냅다 던져버림.
5. 소프트웨어 복제: 클라우드 소프트웨어(**SDS**)가 뻑날 걸 대비해서 옆 서버 디스크에 2~3개씩 무자비하게 복사해 둠.

#### 한줄 요약

- 하드웨어가 캐시 쓰고 알아서 복제해 주는 게 RAID고, 날것으로 넘겨줘서 소프트웨어가 복제하게 냅두는 게 JBOD 경로다.

## Ⅴ. 종류 및 비교

<details><summary>용어 설명</summary>

- **스마트(S.M.A.R.T)**: 디스크가 지 혼자 열 재고, 배드섹터 세면서 "나 내일 죽을 것 같아" 하고 OS한테 징징대는 자가 진단 기술이다.

</details>

| 비교 항목 | **하드웨어 레이드 컨트롤러** (HW RAID) | **제이보드 패스스루** (JBOD / SDS) |
|:---|:---|:---|
| 시스템 적용 최적 기준 | 비싼 DB 서버 한 대를 절대로 뻗지 않게 겹겹이 철통 방어해야 할 시 | 값싼 서버 100대 깔아놓고 죽으면 옆 서버로 퉁치는 클라우드 인프라 구축 시 |
| 아키텍처 핵심 구현 특징 | 전용 하드웨어 카드(비쌈) 꽂아서 디스크를 묶고 배터리 캐시로 속도 뻥튀기함 | 무식하게 생짜 디스크 꽂아놓고 소프트웨어(Ceph 등)가 알아서 복제하고 관리하게 냅둠 |
| 극복해야 할 태생적 한계점 | 비싼 레이드 카드 자체가 뻗어버리면 안에 묶인 디스크 데이터 다 같이 증발하는 대형사고 발생 | 디스크 **스마트(S.M.A.R.T)** 상태는 훤히 보이지만, 레이드 카드 캐시 버프가 없어서 저장 속도 곤두박질 |

#### 한줄 요약

- 돈 발라서 하드웨어로 한 땀 한 땀 지키는 게 RAID고, 물량으로 밀어붙여서 복사본으로 버티는 게 JBOD(SDS)다.

## Ⅵ. 실무 고려사항 및 대책

<details><summary>용어 설명</summary>

- **듀얼 레이드 컨트롤러(Dual RAID Controller)**: 비싼 레이드 카드가 죽을까 봐 똑같은 놈을 2개 꽂아놓고, 하나 죽으면 바로 옆놈이 깨어나는 극한의 좀비 시스템이다.

</details>

| 문제 | 대책 | 효과 |
|:---|:---|:---|
| **제이보드** 쓰면서 소프트웨어로만 복제하려니 속도가 구토 나올 정도로 느려 터짐 | 속도 미친 비싼 캐시 디스크(NVMe) 꽂아서 거기다 먼저 박고 천천히 복제하는 꼼수 시전 | 캐시 없는 생짜 디스크의 미친 지연시간(Latency)을 씹어먹고 쓸만한 성능 방어 |
| 레이드 카드 고장 났더니 디스크 20개 묶인 게 통째로 날아가는 기적의 동반 자살 사태 | 돈 두 배로 발라서 똑같은 레이드 카드를 2개 꽂아놓는 **듀얼 레이드 컨트롤러** 떡칠 | 카드 하나 뻗어도 옆 카드가 멱살 잡고 살려내서 서버 단일 장애점(SPOF) 완벽 파괴 |
| 최신 클라우드 소프트웨어(**SDS**) 썼는데 레이드 카드가 몰래 묶어버려서 디스크 관리가 다 꼬임 | 쓸데없이 묶는 짓거리 막아버리고 무조건 **패스스루 모드**(JBOD)로 낱개로 까발려버림 | 하드웨어랑 소프트웨어가 겹쳐서 싸우는 뻘짓을 막고 소프트웨어에 절대 권력 위임 |

#### 한줄 요약

- JBOD는 캐시 디스크로 속도를 때우고, RAID는 듀얼 컨트롤러로 생존율을 올리며, SDS에는 무조건 패스스루를 먹여라.

## Ⅶ. 결론

<details><summary>용어 설명</summary>

- **스토리지 토폴로지 선택 기준(Storage Topology Selection Criteria)**: 이 서버가 혼자서 끝장을 봐야 하는 놈인지(RAID), 천 대 깔아놓고 떼거지로 버틸 놈인지(JBOD) 견적을 내보는 잣대이다.

</details>

- **스토리지 토폴로지 선택 기준** 원칙에 따라, 단일 DB 서버 부트/데이터 볼륨은 닥치고 **HW RAID**, 대규모 클라우드 인프라는 **JBOD & SDS** 채택 기조 확립함

#### 한줄 요약

- 단일 장비 방어력 몰빵은 레이드를 박고, 구름떼처럼 깔아서 복제할 거면 제이보드를 써라.
