## Ⅰ. 개요

<details><summary>용어 설명</summary>

- **하이퍼바이저(Hypervisor, VMM)**: 단일 물리 서버의 하드웨어 자원을 논리적으로 분할하여 다수의 독립된 가상 머신(VM)을 생성·통제하는 가상화 계층.
- **베어메탈(Bare-Metal)**: 호스트 운영체제(Windows/Linux)의 개입 없이 물리 하드웨어 실리콘 위에 하이퍼바이저가 직접 설치되는 네이티브 실행 환경.

</details>

- 정의/개념: 서버 하드웨어 상의 계층 배치 구조에 따라 물리 베어메탈 직결 **Type 1(네이티브)** 과 호스트 OS 기반 **Type 2(호스티드)** 로 분류하는 서버 가상화 체계
- 배경/필요성: 여러 VM을 같은 서버에서 운영할 때 하이퍼바이저 배치에 따라 장치 경로·장애 범위·운영 편의성이 달라짐

#### 한줄 요약
- 하드웨어 위에 직접 올라가는 고성능 기업용 Type 1(ESXi/KVM)과, 윈도우/맥 앱처럼 깔리는 개인용 Type 2(VirtualBox)로 나뉜다.

## Ⅱ. 특징

<details><summary>용어 설명</summary>

- **장애 도메인(Failure Domain)**: 시스템 내부의 특정 소프트웨어가 고장 났을 때 그 여파로 인해 함께 중단되는 서비스의 물리적·논리적 영향 범위.
- **이중 스케줄링(Double Scheduling)**: Type 2 환경에서 게스트 OS 스케줄러와 호스트 OS 스케줄러가 2중으로 CPU 사이클을 조율하여 발생하는 지연.

</details>

- **Type 1 (Bare-Metal)**: 하이퍼바이저가 하드웨어 제어 계층을 맡아 서버 가상화·운영 기능 제공
- **Type 2 (Hosted)**: 범용 OS 위에서 응용 프로그램 형태로 설치되어 개발 및 테스트 환경 구성 용이
- **장애 도메인 차이**: Type 2는 호스트 OS 장애·업데이트가 모든 게스트에 직접 영향

#### 한줄 요약
- Type 1은 호스트 OS가 없어 빠르고 안전하며, Type 2는 기존 컴퓨터에 앱처럼 깔아 쓰기 편하다.

## Ⅲ. 구조 및 구성요소

<details><summary>용어 설명</summary>

- **게스트 VM(Guest Virtual Machine)**: 하이퍼바이저가 할당한 vCPU, vRAM, vDisk를 기반으로 독립 실행되는 가상 운영체제 인스턴스.
- **호스트 OS(Host Operating System)**: Type 2 환경에서 물리 하드웨어를 직접 제어하며 하이퍼바이저 앱에 프로세스 자원을 공급하는 기본 OS.

</details>

```text
┌─────────────────────────────────────────────────────────────┐
│ Type 1 베어메탈 vs Type 2 호스티드 하이퍼바이저 구조 비교  │
│                                                             │
│  [ Type 1 : 베어메탈 네이티브 가상화 ]                      │
│  ┌──────────────────────────┬────────────────────────────┐  │
│  │ 게스트 VM 1 (Linux)      │ 게스트 VM 2 (Windows)      │  │
│  ├──────────────────────────┴────────────────────────────┤  │
│  │ Type 1 하이퍼바이저 (VMware ESXi, KVM, Hyper-V, Xen)  │  │
│  ├───────────────────────────────────────────────────────┤  │
│  │ 물리 베어메탈 하드웨어 (CPU VT-x, DRAM, NVMe, NIC)    │  │
│  └───────────────────────────────────────────────────────┘  │
│                                                             │
│  [ Type 2 : 호스티드 애플리케이션 가상화 ]                  │
│  ┌──────────────────────────┬────────────────────────────┐  │
│  │ 게스트 VM 1 (Linux)      │ 게스트 VM 2 (Windows)      │  │
│  ├──────────────────────────┴────────────────────────────┤  │
│  │ Type 2 하이퍼바이저 앱 (VirtualBox, VMware Workstation)│  │
│  ├───────────────────────────────────────────────────────┤  │
│  │ 범용 호스트 운영체제 (Host OS : Windows 11, macOS)    │  │
│  ├───────────────────────────────────────────────────────┤  │
│  │ 물리 베어메탈 하드웨어 (CPU, Memory, Storage, NIC)    │  │
│  └───────────────────────────────────────────────────────┘  │
└─────────────────────────────────────────────────────────────┘
```

선의 의미: Type 1은 하이퍼바이저가 하드웨어를 직접 제어하며, Type 2는 호스트 OS의 시스템 콜과 드라이버를 거쳐 간접 제어

| 구성요소 | 책임 |
|:---|:---|
| 물리 하드웨어 계층 | CPU 가상화(VT-x/AMD-V), EPT 메모리 및 IOMMU 장치 가상화 하드웨어 자원 제공 |
| Type 1 하이퍼바이저 | 물리 하드웨어에 직접 상주하며 가상 vCPU 스케줄링 및 초저지연 직접 I/O 제어 |
| 호스트 운영체제 (Host OS) | Type 2 환경에서 물리 장치 드라이버를 전담하고 하이퍼바이저 프로세스에 자원 할당 |
| Type 2 하이퍼바이저 앱 | 호스트 OS 위에서 게스트 요청을 시스템 콜(System Call)로 변환 중계하는 가상화 런타임 |
| 게스트 가상 머신 (Guest VM)| 독립된 가상화 환경에서 상위 애플리케이션 및 서비스를 구동하는 사용자 인스턴스 |

#### 한줄 요약
- 물리 하드웨어, Type 1 VMM(직결), 호스트 OS, Type 2 VMM(앱), 게스트 VM이 2대 가상화 모델을 형성한다.

## Ⅳ. 흐름도

<details><summary>용어 설명</summary>

- **가상 I/O 패스(Virtual I/O Path)**: 게스트 VM 내부 디바이스 드라이버가 발행한 쓰기/읽기 요청이 물리 스토리지 컨트롤러에 도달하기까지의 계층별 처리 경로.

</details>

```text
게스트 VM 애플리케이션 I/O 발생
      │
      ▼
1. I/O 발행
      │                              │
      ├──────────────────────────────┬──────────────────────────────┐
      ▼                              ▼                              │
[ Type 1 경로 ]                  [ Type 2 경로 ]                    │
2. VMM 장치 중개                 2. 가상화 앱 장치 중개             │
      │                              │
      │                              ▼
      │                           3. 호스트 OS 전달                 │
      │                              │
      └──────────────────────────────┴──────────────────────────────┘
                                     ▼
                         4. 하드웨어 완료
                                     │
                                     ▼
                         5. 가상 인터럽트 주입
```

**동작 원리**

1. **I/O 발행**: 게스트 VM 커널이 가상 디바이스 레지스터에 데이터 쓰기 명령 인가
2. **Type 1 직결**: Type 1 VMM이 내장 네이티브 드라이버로 물리 PCIe 버스에 직접 I/O 커밋
3. **Type 2 간접 전달**: Type 2 VMM이 게스트 요청을 호스트 OS의 시스템 콜로 변환하여 2중 전달
4. **하드웨어 완료**: 물리 SSD나 NIC이 패킷 처리를 끝내고 하드웨어 인터럽트 회수
5. **가상 인터럽트 주입**: 하이퍼바이저가 게스트 vCPU로 완료 인터럽트를 주입하여 작업 종결

#### 한줄 요약
- I/O 요청 발생 → Type 1(네이티브 직결) vs Type 2(호스트 시스템 콜 중계) → 물리 HW 처리 → 완료 인터럽트 순으로 진행된다.

## Ⅴ. 종류 및 비교

| 서버 가상화 하이퍼바이저 | Type 1 (Bare-Metal) | Type 2 (Hosted) | OS 컨테이너 (Docker/K8s) | 마이크로VM (Firecracker) |
|:---|:---|:---|:---|:---|
| 적용 기준 | 엔터프라이즈 클라우드 및 상용 IDC | 개인 PC 개발, 테스트, 교육 환경 | 초경량 마이크로서비스(MSA) 배포 | 서버리스(Serverless) 초고속 기동 환경 |
| 핵심 특징 | 하드웨어 제어 계층에서 VM 자원 관리 | 호스트 OS 위 애플리케이션으로 실행 | 단일 호스트 커널과 네임스페이스 공유 | KVM 기반 최소 장치 모델과 작은 VM |
| 한계 | 전용 하드웨어 호환성(HCL) 검증 필요 | 호스트 OS 다운 시 전체 VM 동반 크래시 | 호스트 커널 공유로 인한 보안 격리 한계 | 최소한의 가상 디바이스만 제공(GUI 불가) |

#### 한줄 요약
- 대규모 IDC는 Type 1, 개인 테스트는 Type 2, 클라우드 MSA는 컨테이너, 서버리스는 마이크로VM을 쓴다.

## Ⅵ. 실무 고려사항 및 대책

<details><summary>용어 설명</summary>

- **vCPU 오버커밋(vCPU Overcommit)**: 물리 코어 수보다 더 많은 가상 vCPU를 VM들에 할당하여 서버 집적도를 극대화하는 기법.
- **CPU 레디 타임(CPU Ready Time)**: vCPU가 실행 준비를 마쳤으나 물리 CPU 코어를 점유하지 못하고 대기열에서 지연되는 시간 백분율.

</details>

| 문제 | 대책 | 효과 |
|:---|:---|:---|
| Type 2의 **호스트 OS 장애·재부팅 영향** | 상시 운영은 Type 1 클러스터와 라이브 마이그레이션·HA 적용 | 개발 호스트와 서비스 장애 도메인 분리 |
| 무분별한 vCPU 초과 할당에 따른 **CPU Ready 지연** | 워크로드별 Ready Time·공동 정지 시간을 보고 오버커밋 조정 | 스케줄링 대기와 불필요한 대형 vCPU 축소 |
| 가상 디스크 I/O 병목에 따른 **스토리지 지연 증가** | virtio·vhost, 큐 깊이·NUMA 조정 후 필요 시 패스스루 | 공유성·마이그레이션과 직접 I/O 성능 절충 |
| 다중 테넌트의 **CPU 캐시 사이드채널** | 마이크로코드·하이퍼바이저 패치와 코어 스케줄링·테넌트 분리 | 완화 성능 비용과 잔여 정보 노출 위험 관리 |

#### 한줄 요약
- 상용 서버는 Type 1으로 구축하고, CPU Ready를 감시하며, NVMe-oF와 코어 스케줄링으로 성능과 보안을 지킨다.

## Ⅶ. 결론

- 상시 서비스·다중 테넌트는 **Type 1**, 개인 개발·데스크톱 통합은 Type 2 선택
- 더 높은 밀도는 컨테이너, 빠른 기동과 별도 커널 경계가 함께 필요하면 마이크로VM 비교

#### 한줄 요약
- 성능 오버헤드, 장애 격리성, 운영 편의성을 다각도로 검토하여 서비스 성격에 최적화된 하이퍼바이저 아키텍처를 선정해야 한다.
