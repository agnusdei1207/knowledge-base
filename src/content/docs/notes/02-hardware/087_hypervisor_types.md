## Ⅰ. 개요

<details><summary>용어 설명</summary>

- **하이퍼바이저(Hypervisor / VMM)**: 단일 물리 서버의 하드웨어 컴퓨팅 자원(CPU, 메모리, 스토리지, 네트워크)을 가상화하여 다수의 독립된 가상 머신(VM)을 생성, 스케줄링, 격리 통제하는 가상화 관리 계층.
- **베어메탈(Bare-Metal)**: 호스트 운영체제(Windows, Linux)의 개입 없이 물리 서버 하드웨어 실리콘 위에 하이퍼바이저가 직접 설치되어 하드웨어를 직접 제어하는 실행 환경.

</details>

- 정의/개념: 하이퍼바이저의 물리 하드웨어 상주 위치와 호스트 OS 유무에 따라 **베어메탈형(Type 1)과 호스티드형(Type 2)**으로 분류하는 **가상 머신 모니터(VMM) 아키텍처 체계**
- 배경/필요성: 단일 물리 서버에 단일 OS만 운영하던 전통 구조의 **낮은 하드웨어 자원 활용률(10~15%) 극복 및 멀티테넌트 독립 격리 환경 구축 필요**

#### 한줄 요약
- 하드웨어 직결형 Type 1(베어메탈)과 호스트 OS 기반 Type 2(호스티드)로 구분되어 엔터프라이즈 성능과 데스크톱 편의성을 차별화한다.

## Ⅱ. 특징

<details><summary>용어 설명</summary>

- **장애 도메인(Failure Domain)**: 특정 소프트웨어 계층(호스트 OS 또는 단일 VM)에서 장애가 발생했을 때 그 영향이 시스템 전체로 파급되는 물리적·논리적 범위.
- **이중 스케줄링(Double Scheduling)**: Type 2 환경에서 게스트 OS 스케줄러와 호스트 OS 커널 스케줄러가 2중으로 CPU 타임슬라이스를 중복 조율하여 발생하는 지연.

</details>

- Type 1 (Bare-Metal): 하이퍼바이저가 하드웨어에 직접 상주하여 **호스트 OS 오버헤드가 전무하며 네이티브 대비 95~99% 초고성능 제공**
- Type 2 (Hosted): Windows/macOS 등 범용 OS 상에서 일반 응용 프로그램 형태로 동작하여 설치가 간편하나 **이중 스케줄링 및 3단계 I/O 오버헤드** 발생
- **장애 도메인(Failure Domain)** 격리: Type 1은 특정 VM 크래시가 타 VM에 영향이 없으나, Type 2는 호스트 OS 다운 시 모든 게스트 VM이 동시 중단

#### 한줄 요약
- Type 1은 중간 OS 없이 하드웨어에 직결되어 엔터프라이즈급 성능을 내며, Type 2는 호스트 OS 위에서 동작하여 개발 편의성을 제공한다.

## Ⅲ. 구조 및 구성요소

<details><summary>용어 설명</summary>

- **게스트 VM(Guest Virtual Machine)**: 하이퍼바이저가 할당한 vCPU, vRAM, vDisk를 기반으로 독립 실행되는 가상 운영체제 인스턴스.
- **호스트 OS(Host Operating System)**: Type 2 환경에서 물리 하드웨어를 직접 제어하며 하이퍼바이저 프로세스에 CPU/메모리 자원을 할당하는 기저 OS.

</details>

```text
[하이퍼바이저 Type 1 vs Type 2 아키텍처 비교]
 ┌─ [Type 1: 베어메탈 하이퍼바이저 (Bare-Metal)]     ┌─ [Type 2: 호스티드 하이퍼바이저 (Hosted)]
 │   ┌──────────────┐   ┌──────────────┐             │   ┌──────────────┐   ┌──────────────┐
 │   │ 게스트 VM 1  │   │ 게스트 VM N  │             │   │ 게스트 VM 1  │   │ 게스트 VM 2  │
 │   └──────┬───────┘   └──────┬───────┘             │   └──────┬───────┘   └──────┬───────┘
 │          └─────────┬────────┘                     │          └─────────┬────────┘
 │   ┌────────────────▼────────────────┐             │   ┌────────────────▼────────────────┐
 │   │ [Type 1 하이퍼바이저] (ESXi/KVM) │             │   │ [Type 2 하이퍼바이저] (VMware/VB)│
 │   └────────────────┬────────────────┘             │   └────────────────┬────────────────┘
 │                    │ (하드웨어 직접 제어)          │   ┌────────────────▼────────────────┐
 │                    │                              │   │ [범용 호스트 OS] (Windows/Linux) │
 │                    │                              │   └────────────────┬────────────────┘
 │   ┌────────────────▼────────────────┐             │   ┌────────────────▼────────────────┐
 │   │ [물리 서버 하드웨어] (CPU/RAM/IO) │             │   │ [물리 서버 하드웨어] (CPU/RAM/IO) │
 │   └─────────────────────────────────┘             │   └─────────────────────────────────┘
```

선의 의미: 가지(`├─`, `└─`)는 하드웨어 소속 및 계층 관계; Type 1은 호스트 OS 없이 하드웨어에 직결되며, Type 2는 호스트 OS를 거쳐 물리 하드웨어를 제어함

| 비교 항목 | Type 1 (Bare-Metal) 책임 | Type 2 (Hosted) 책임 |
|:---|:---|:---|
| **상주 위치** | **물리 서버 하드웨어 실리콘에 직접 상주** | **범용 호스트 OS(Windows/Linux) 상단에 앱으로 상주** |
| **호스트 OS 유무** | **부재 (호스트 OS 없음)** | 필수 존재 (호스트 OS 커널 위에서 동작) |
| **I/O 드라이버 경로** | 하이퍼바이저가 물리 드라이버를 직접 구동 (1단계 직결) | 게스트 ➔ 하이퍼바이저 ➔ 호스트 OS ➔ 물리 장치 (3단계 경유) |
| **장애 격리성** | 단일 VM 장애가 타 VM에 영향 없음 (**엄격한 결함 격리**) | 호스트 OS 블루스크린 시 **모든 게스트 VM 전면 셧다운** |
| **대표 제품** | **VMware ESXi, KVM, Xen, Hyper-V Core** | **VMware Workstation, Oracle VirtualBox, Parallels** |

#### 한줄 요약
- Type 1은 중간 OS 없이 물리 서버에 직결되고, Type 2는 범용 호스트 OS 위에서 프로세스 형태로 중계 실행된다.

## Ⅳ. 흐름도

<details><summary>용어 설명</summary>

- **가상 I/O 패스(Virtual I/O Path)**: 게스트 VM 내부 드라이버가 발생시킨 읽기/쓰기 명령이 물리 스토리지 컨트롤러에 도달하기까지의 계층별 처리 경로.

</details>

```text
1. 게스트 VM 애플리케이션: 디스크 I/O 쓰기 요청 발생 ➔ 게스트 OS 커널 전달
                      │
                      ▼
2. 하이퍼바이저 유형별 I/O 스택 처리 분기
   ┌──────────────────┴──────────────────┐
[ Type 1 베어메탈 (ESXi / KVM) ]       [ Type 2 호스티드 (Workstation) ]
   │                                     │
   ▼                                     ▼
3. 하이퍼바이저 스토리지 스택이          3. 가상 I/O 요청을 호스트 OS 시스템 콜(API)로 변환
   물리 디스크 컨트롤러로 직접 커밋       │
   (1단계 초저지연 직결 I/O)             ▼
   │                                  4. 호스트 OS 파일시스템 드라이버가 물리 디스크에 전달
   │                                     (3단계 중계 오버헤드 발생)
   │                                     │
   └──────────────────┬──────────────────┘
                      │
                      ▼
5. 물리 하드웨어 처리 완료 ➔ 하이퍼바이저를 통해 게스트로 가상 인터럽트 주입 완료
```

분기 결과: **Type 1은** 1단계 직결 I/O로 베어메탈급 성능을 내며, **Type 2는** 호스트 OS를 거치는 3단계 중계로 인해 지연이 발생함

#### 한줄 요약
- I/O 발생 ➔ Type 1 직결 처리 또는 Type 2 호스트 OS 중계 변환 ➔ 물리 디스크 기록 ➔ 가상 인터럽트 반환 순으로 동작한다.

## Ⅴ. 종류 및 비교

<details><summary>용어 설명</summary>

- **마이크로VM(MicroVM)**: AWS Firecracker처럼 서버리스 FaaS 환경을 위해 불필요한 레거시 디바이스 모델을 제거하고 5ms 이내로 초고속 기동하는 경량 VM.

</details>

| 가상화 아키텍처 | Type 1 (Bare-Metal) | Type 2 (Hosted) | OS 컨테이너 (Docker) | 마이크로VM (MicroVM) |
|:---|:---|:---|:---|:---|
| 가상화 계층 수준 | **하드웨어 레벨 (하드웨어 가상화)** | **OS 상단 애플리케이션 레벨** | OS 커널 공유 (cgroups/ns) | **초경량 하드웨어 하이퍼바이저** |
| 가상화 실효 성능 | **네이티브 대비 95~99% (초고성능)** | 70~85% (호스트 OS 오버헤드) | **99%+ (프로세스 수준 격리)** | **98%+ (5ms 초고속 부팅)** |
| 부팅 및 기동 속도 | 수십 초 ~ 수 분 (OS 전체 부팅) | 수십 초 | **수백 밀리초 (초고속)** | **5 ~ 10ms (극초고속)** |
| 보안 격리성 수준 | **최고 (하드웨어 CPU 격리)** | 중간 (호스트 OS 종속) | 낮음 (호스트 커널 취약점 공유) | **최고 (KVM 기반 하드웨어 격리)** |
| 주요 적용 분야 | **엔터프라이즈 IaaS 클라우드** | PC 개발/테스트, 교육 환경 | 마이크로서비스(MSA), CI/CD | **서버리스 (AWS Lambda), FaaS** |

#### 한줄 요약
- 엔터프라이즈 IaaS는 Type 1, PC 개발은 Type 2, 클라우드 네이티브 MSA는 컨테이너, 서버리스 FaaS는 MicroVM을 적용한다.

## Ⅵ. 실무 고려사항 및 대책

<details><summary>용어 설명</summary>

- **CPU 레디 타임(CPU Ready Time, %RDY)**: vCPU가 실행 준비를 마쳤으나 하이퍼바이저로부터 물리 CPU 코어를 할당받지 못하고 대기열에서 지연되는 시간 비율(권장 5% 미만).

</details>

| 문제 | 대책 | 효과 |
|:---|:---|:---|
| 과도한 vCPU 오버커밋으로 인한 VM 성능 저하 | **CPU 레디 타임(%RDY < 5%) 상시 모니터링 및 vCPU 할당 축소** | 스케줄러 대기열 정체 해소 및 성능 균일화 |
| Type 1 스토리지/네트워크 I/O 집중 시 레이턴시 증가 | **Virtio 반가상화 드라이버 및 SR-IOV 하드웨어 패스스루** | VM-Exit 트랩 90% 제거 및 100GbE 네이티브 성능 달성 |
| 물리 서버 하드웨어 장애 시 단일 서버 내 다수 VM 동반 다운 | **하이퍼바이저 클러스터 HA(High Availability) 자동 페일오버** | 1분 이내 타 물리 노드로 무중단 자동 재기동 |

#### 한줄 요약
- 실무에서는 %RDY 모니터링으로 CPU를 관리하고, SR-IOV로 I/O를 가속하며, 클러스터 HA로 물리 장애를 방어한다.

## Ⅶ. 결론

- 대규모 엔터프라이즈 클라우드 및 미션 크리티컬 인프라는 **Type 1 베어메탈 하이퍼바이저(ESXi/KVM)를 표준 구축**하고, 개인 개발 및 테스트 환경에는 **Type 2 호스티드 가상화**를 적용하며, 차세대 서버리스 및 클라우드 네이티브 환경에서는 **Type 1 기반 MicroVM(Firecracker)과 컨테이너를 융합**하는 다계층 가상화 아키텍처 확립

#### 한줄 요약
- 하이퍼바이저는 엔터프라이즈 성능과 보안을 위한 Type 1과 개발 편의성을 위한 Type 2로 명확히 구분하여 설계해야 한다.
