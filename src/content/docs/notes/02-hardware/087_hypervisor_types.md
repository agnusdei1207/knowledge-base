## Ⅰ. 개요

<details><summary>용어 설명</summary>

- **하이퍼바이저(Hypervisor, VMM)**: 단일 물리 서버의 하드웨어 자원을 논리적으로 분할하여 다수의 독립된 가상 머신(VM)을 생성·통제하는 가상화 계층.
- **베어메탈(Bare-Metal)**: 호스트 운영체제(Windows/Linux)의 개입 없이 물리 하드웨어 실리콘 위에 하이퍼바이저가 직접 설치되는 네이티브 실행 환경.

</details>

- 정의/개념: **하이퍼바이저(Hypervisor, VMM)** **베어메탈(Bare-Metal)** 위에 직접 올라가는지 범용 OS 위에 얹히는지로 갈리는 두 가지 가상화 배치 방식
- 배경/필요성: 같은 가상화 기능이라도 계층을 어디에 두느냐에 따라 장치 접근 경로와 장애 파급 범위, 운영 방식이 전부 달라짐

#### 한줄 요약
- 하이퍼바이저가 베어메탈 하드웨어에 직접 상주하는지 또는 호스트 OS 위에서 동작하는지에 따라 아키텍처가 구분된다.

## Ⅱ. 특징

<details><summary>용어 설명</summary>

- **장애 도메인(Failure Domain)**: 시스템 내부의 특정 소프트웨어가 고장 났을 때 그 여파로 인해 함께 중단되는 서비스의 물리적·논리적 영향 범위.
- **이중 스케줄링(Double Scheduling)**: Type 2 환경에서 게스트 OS 스케줄러와 호스트 OS 스케줄러가 2중으로 CPU 사이클을 조율하여 발생하는 지연.

</details>

- Type 1은 하이퍼바이저가 하드웨어 제어 계층을 직접 맡아 중간 단계가 없음
- Type 2는 범용 OS 위 응용 프로그램으로 설치돼 도입이 쉬움
- **장애 도메인(Failure Domain)** 갈려, Type 2는 호스트 OS의 장애와 재부팅이 모든 게스트에 직접 전파

#### 한줄 요약
- Type 1은 하드웨어 직결 제어로 고성능을 제공하며, Type 2는 범용 OS 기반으로 편리하나 호스트 장애 전파 위험이 있다.

## Ⅲ. 구조 및 구성요소

<details><summary>용어 설명</summary>

- **게스트 VM(Guest Virtual Machine)**: 하이퍼바이저가 할당한 vCPU, vRAM, vDisk를 기반으로 독립 실행되는 가상 운영체제 인스턴스.
- **호스트 OS(Host Operating System)**: Type 2 환경에서 물리 하드웨어를 직접 제어하며 하이퍼바이저 앱에 프로세스 자원을 공급하는 기본 OS.

</details>

```text
[Type 1 배치]
├─ 게스트 VM (여러 개)
├─ Type 1 하이퍼바이저 (하드웨어 직접 제어)
└─ 물리 하드웨어 (CPU 가상화 기능·메모리·저장장치·네트워크)

[Type 2 배치]
├─ 게스트 VM (여러 개)
├─ Type 2 하이퍼바이저 (호스트 OS 위 응용 프로그램)
├─ 범용 호스트 OS (물리 장치 드라이버 전담)
└─ 물리 하드웨어
```

선의 의미: 가지(`├─`)는 위에서 아래로 쌓인 계층 순서이며, 두 배치의 차이는 하이퍼바이저 아래에 한 층이 더 있느냐 하나뿐

| 구성요소 | 책임 |
|:---|:---|
| 물리 하드웨어 | CPU·메모리·장치 가상화 기능 제공 |
| Type 1 하이퍼바이저 | 하드웨어에 직접 상주해 자원 스케줄링과 입출력 제어 |
| **호스트 OS(Host Operating System)** | 물리 장치 드라이버 전담과 하이퍼바이저에 자원 할당 |
| Type 2 하이퍼바이저 | 게스트 요청을 호스트 OS 호출로 변환 중계 |
| **게스트 VM(Guest Virtual Machine)** | 할당받은 가상 자원 위에서 독립 OS 구동 |

#### 한줄 요약
- 하이퍼바이저의 계층 위치에 따라 장치 드라이버 제어와 자원 할당 경로가 분기된다.

## Ⅳ. 흐름도

<details><summary>용어 설명</summary>

- **가상 I/O 패스(Virtual I/O Path)**: 게스트 VM 내부 디바이스 드라이버가 발행한 쓰기/읽기 요청이 물리 스토리지 컨트롤러에 도달하기까지의 계층별 처리 경로.

</details>

```text
게스트 VM 응용이 입출력 발생
        │
   게스트 커널이 가상 장치에 요청 기록
        │
   하이퍼바이저가 어디에 있는가?
   ┌────┴─────┐
하드웨어 직접   호스트 OS 위
   │             │
내장 드라이버로  요청을 호스트 OS
물리 버스에 직접  호출로 변환해 전달
커밋             │
   │        호스트 드라이버가 물리 장치에 전달
   └────┬────────┘
        │
   물리 장치 처리 완료 후 인터럽트 회수
        │
   하이퍼바이저가 게스트에 가상 인터럽트 주입
```

분기 결과: 오른쪽 경로는 요청마다 호스트 OS 계층을 한 번 더 통과하므로 지연이 더해질 뿐 아니라, 게스트와 호스트 스케줄러가 겹치는 **이중 스케줄링(Double Scheduling)**에도 함께 묶임

#### 한줄 요약
- Type 1은 물리 장치에 직접 I/O를 전달하고, Type 2는 호스트 OS 계층을 거쳐 I/O를 중계한다.

## Ⅴ. 종류 및 비교

| 서버 가상화 하이퍼바이저 | Type 1 (Bare-Metal) | Type 2 (Hosted) | OS 컨테이너 (Docker/K8s) | 마이크로VM (Firecracker) |
|:---|:---|:---|:---|:---|
| 적용 기준 | 엔터프라이즈 클라우드 및 상용 IDC | 개인 PC 개발, 테스트, 교육 환경 | 초경량 마이크로서비스(MSA) 배포 | 서버리스(Serverless) 초고속 기동 환경 |
| 핵심 특징 | 하드웨어 제어 계층에서 VM 자원 관리 | 호스트 OS 위 애플리케이션으로 실행 | 단일 호스트 커널과 네임스페이스 공유 | KVM 기반 최소 장치 모델과 작은 VM |
| 한계 | 전용 하드웨어 호환성(HCL) 검증 필요 | 호스트 OS 다운 시 전체 VM 동반 크래시 | 호스트 커널 공유로 인한 보안 격리 한계 | 최소한의 가상 디바이스만 제공(GUI 불가) |

#### 한줄 요약
- 격리 수준과 기동 속도, 운영 환경에 따라 적합한 가상화 기술을 선별하여 적용한다.

## Ⅵ. 실무 고려사항 및 대책

<details><summary>용어 설명</summary>

- **vCPU 오버커밋(vCPU Overcommit)**: 물리 코어 수보다 더 많은 가상 vCPU를 VM들에 할당하여 서버 집적도를 극대화하는 기법.
- **CPU 레디 타임(CPU Ready Time)**: vCPU가 실행 준비를 마쳤으나 물리 CPU 코어를 점유하지 못하고 대기열에서 지연되는 시간 백분율.

</details>

| 문제 | 대책 | 효과 |
|:---|:---|:---|
| 호스트 OS 장애·재부팅이 모든 게스트에 전파 | 상시 운영은 Type 1 클러스터와 이전·이중화 적용 | 개발 환경과 서비스의 장애 도메인 분리 |
| 과도한 **vCPU 오버커밋(vCPU Overcommit)** 기반 대기 증가 | **CPU 레디 타임(CPU Ready Time)** 보고 할당 비율 조정 | 스케줄링 대기와 불필요한 대형 인스턴스 축소 |
| 가상 디스크 경로 병목으로 저장장치 지연 증가 | 반가상 드라이버와 큐 깊이·노드 배치 조정 후 직결 검토 | 공유성·이전 가능성과 직접 성능의 절충 |
| 다중 테넌트 환경의 캐시 사이드채널 노출 | 완화 패치와 코어 스케줄링·테넌트 분리 적용 | 완화 비용과 잔여 노출 위험의 관리 |

#### 한줄 요약
- CPU 레디 타임과 스토리지 I/O 병목을 모니터링하여 오버커밋 비율과 드라이버 경로를 최적화한다.

## Ⅶ. 결론

- 상시 서비스와 다중 테넌트 환경은 Type 1 배치를, 개인 개발이나 데스크톱 통합은 Type 2를 선택하고, 더 높은 밀도가 필요하면 컨테이너를, 빠른 기동과 별도 커널 경계가 함께 요구되면 마이크로VM을 비교

#### 한줄 요약
- 서비스의 가용성 요구수준과 장애 격리 범위, 오버헤드를 기준으로 적합한 가상화 계층을 결정한다.
