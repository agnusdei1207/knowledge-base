## Ⅰ. 개요

<details><summary>용어 설명</summary>

- **Hypervisor(하이퍼바이저, VMM)**: 단일 물리 서버의 하드웨어 자원을 추상화하여 복수의 독립된 가상 머신(VM)을 생성, 실행, 관리하는 가상화 통제 계층.
- **Type 1 Hypervisor(Bare-Metal)**: 호스트 운영체제 없이 물리 베어메탈 하드웨어 위에 직접 설치되어 하드웨어를 직접 제어하는 네이티브 가상화 계층.
- **Type 2 Hypervisor(Hosted)**: Windows, Linux, macOS 등 범용 호스트 운영체제 상에서 하나의 응용 프로그램 형태로 구동되는 가상화 계층.

</details>

- 정의/개념: 서버 하드웨어 상의 실행 계층 구조에 따라 물리 베어메탈(Bare-Metal) 하드웨어에 직접 상주하는 Type 1(네이티브)과, 범용 호스트 운영체제(Host OS) 상에서 애플리케이션 형태로 구동되는 Type 2(호스티드)의 서버 가상화 하이퍼바이저 분류 체계
- 배경/필요성: 엔터프라이즈 데이터센터의 고밀도 서버 통합, 성능 오버헤드 최소화, 장애 격리성(Fault Isolation) 및 개발·테스트 환경 편의성 간의 **가상화 아키텍처 선정 기준 수립 필수**

#### 한줄 요약

- 물리 하드웨어 직결의 **Type 1(베어메탈)**과 호스트 OS 기반 애플리케이션 형태의 **Type 2(호스티드)** 하이퍼바이저 비교

## Ⅱ. 특징

<details><summary>용어 설명</summary>

- **Bare-Metal Execution**: 중간 OS 레이어 없이 하이퍼바이저가 CPU의 최고 권한 모드(Ring 0 / VMX Root)를 직접 점유하여 하드웨어를 제어하는 구조.
- **Hosted Execution**: 게스트 VM의 I/O 및 자원 요청을 호스트 OS의 시스템 콜(System Call)과 드라이버를 통해 간접적으로 전달하는 구조.

</details>

- 호스트 OS 없이 하드웨어 위에 직접 구동되어 오버헤드가 극소화되고 성능이 뛰어난 **타입 1 (Type 1 : Bare-Metal)**
- 기존 범용 호스트 OS 위에서 간편하게 설치 및 구동되나 이중 스케줄링 오버헤드가 발생하는 **타입 2 (Type 2 : Hosted)**
- 타입 1은 호스트 OS 장애 취약점이 없어 엔터프라이즈 고가용성에 적합하며, 타입 2는 호스트 OS 크래시 시 전체 VM이 동반 중단되는 **장애 경계성(Failure Domain) 차이**

#### 한줄 요약

- **베어메탈 직접 제어(Type 1)·호스트 OS 레이어 간접 실행(Type 2)·오버헤드 및 장애 전파 격리성 차이**

## Ⅲ. 구조 및 구성요소

<details><summary>용어 설명</summary>

- **Guest VM**: 하이퍼바이저가 할당한 가상 vCPU, vRAM, vNIC 자원을 기반으로 독립 구동되는 가상 운영체제 인스턴스.
- **Host OS**: Type 2 환경에서 물리 하드웨어 위에 설치되어 하이퍼바이저 프로세스에 메모리와 스케줄링을 제공하는 기본 운영체제.

</details>

```text
[ Type 1 베어메탈 vs Type 2 호스티드 하이퍼바이저 아키텍처 비교 ]
 
 [ 1. Type 1 (Bare-Metal) ]          [ 2. Type 2 (Hosted) ]
┌──────────────────────────────┐    ┌──────────────────────────────┐
│ 게스트 VM 1  │ 게스트 VM 2   │    │ 게스트 VM 1  │ 게스트 VM 2   │
├──────────────────────────────┤    ├──────────────────────────────┤
│ 하이퍼바이저 (Type 1 VMM)    │    │ 하이퍼바이저 (Type 2 VMM 앱) │
│ (VMware ESXi, KVM, Hyper-V)  │    ├──────────────────────────────┤
├──────────────────────────────┤    │ 호스트 OS (Windows, Linux)   │
│ 물리 하드웨어 (Bare-Metal)   │    ├──────────────────────────────┤
│ (CPU, Memory, Storage, NIC)  │    │ 물리 하드웨어 (Host HW)      │
└──────────────────────────────┘    └──────────────────────────────┘
```

선의 의미: Type 1(게스트 VM $\leftrightarrow$ 하이퍼바이저 $\leftrightarrow$ 베어메탈 HW) vs Type 2(게스트 VM $\leftrightarrow$ 하이퍼바이저 $\leftrightarrow$ 호스트 OS $\leftrightarrow$ HW) 계층 구조도.

| 구성요소 | 책임 |
|:---|:---|
| 물리 하드웨어 | 가짜 윈도우(VM)들이 빨대 꽂고 파먹을 CPU(VT-x/AMD-V)와 메모리, 랜카드 같은 깡통 자원 |
| 호스트 운영체제 | (Type 2 한정) 자기가 원래 주인인 줄 아는 윈도우/맥OS로, 가상 머신의 똥 닦아주는(드라이버) 역할을 떠맡음 |
| 하이퍼바이저 제어부 | 세입자(VM)들한테 CPU 쪼가리를 배급해 주고 서로 메모리 못 훔쳐보게 멱살 잡고 격리하는 건물주 |
| 게스트 가상 머신 | 건물주한테 자원 구걸해서 돌아가면서, 지가 진짜 컴퓨터인 줄 아는 눈치 없는 가짜 운영체제 |

#### 한줄 요약

- **물리 하드웨어(CPU/RAM)·호스트 OS(Type 2 전용)·하이퍼바이저 제어부(VMM)·게스트 가상 머신(Guest VM)**

## Ⅳ. 흐름도

<details><summary>용어 설명</summary>

- **Virtual I/O Path**: 게스트 OS 내부의 I/O 디바이스 드라이버에서부터 물리 하드웨어 스토리지/네트워크 컨트롤러까지의 트랜잭션 전달 경로.

</details>

```text
[ 하이퍼바이저 유형별 게스트 I/O 처리 흐름 ]
                         │
                         ▼
   [ 1. 게스트 VM 내부에서 디스크/네트워크 쓰기(I/O) 요청 발행 ]
                         │
        +────────────────┴────────────────────────+
        │             [ 하이퍼바이저 유형 판별 ]  │
        │             /                         \ │
        │     [ Type 1 하이퍼바이저 ]         [ Type 2 하이퍼바이저 ]
        │            │                                │
        │ 2. VMM 내장 디바이스 드라이버   3. Type 2 하이퍼바이저 앱이
        │    가 물리 하드웨어(PCIe)로        호스트 OS 시스템 콜 호출 ──>
        │    직접 초저지연 I/O 커밋          호스트 OS 드라이버 경유 전달
        +────────────────┬────────────────────────+
                         │
                         ▼
   [ 4. 물리 하드웨어 디스크/네트워크 처리 완료 및 인터럽트 반환 ]
```

**동작 원리**

1. **I/O 발행**: 게스트 VM 커널 드라이버가 가상 디바이스 레지스터에 쓰기 명령 인가
2. **Type 1 직결 처리**: Type 1 하이퍼바이저는 내장된 네이티브 드라이버를 통해 물리 SAS/NVMe 컨트롤러로 직접 패킷 전달
3. **Type 2 이중 변환**: Type 2 하이퍼바이저는 게스트 요청을 호스트 OS의 파일 I/O 시스템 콜로 변환하여 호스트 커널 스케줄러로 위임
4. **I/O 완료**: 물리 장치가 작업을 완료하면 하이퍼바이저가 가상 인터럽트를 주입하여 게스트 OS에 완료 통보

#### 한줄 요약

- 게스트 VM I/O 요청 $\to$ **Type 1(하이퍼바이저 드라이버 물리 HW 직접 구동) vs Type 2(호스트 OS 시스템 콜 짬처리 번역) $\to$ 물리 디스크/네트워크 I/O 완료**

## Ⅴ. 종류 및 비교

<details><summary>용어 설명</summary>

- **Type 1 vs Type 2 Hypervisor**:
  - Type 1: 베어메탈 직결, 오버헤드 $1\sim 3\%$, 호스트 OS 없음, 고가용성/엔터프라이즈 (ESXi, KVM)
  - Type 2: 호스트 OS 위 앱 형태, 오버헤드 $10\sim 30\%$, 호스트 종속, 개발/테스트 (VirtualBox)

</details>

| 비교 항목 | Type 1 하이퍼바이저 (Bare-Metal / Native) | Type 2 하이퍼바이저 (Hosted) |
|:---|:---|:---|
| 아키텍처 및 구현 계층 | 물리 베어메탈 하드웨어 위 직접 상주 (No Host OS) | 호스트 OS(Windows, macOS, Linux) 상의 앱 형태 |
| 성능 및 I/O 오버헤드 | 네이티브 하드웨어 직접 제어 (극소 오버헤드: $1\sim 3\%$) | 호스트 OS 이중 변환으로 인한 추가 오버헤드 ($10\sim 30\%$) |
| 장애 격리 및 대표 제품 | 호스트 OS 장애 종속 없음 (ESXi, KVM, Hyper-V, Xen) | 호스트 OS 장애 시 전체 VM 동반 다운 (VirtualBox, Workstation) |

#### 한줄 요약

- 엔터프라이즈 데이터센터는 **Type 1(ESXi, KVM)**, 개인 개발·테스트는 **Type 2(VirtualBox)**

## Ⅵ. 실무 고려사항 및 대책

<details><summary>용어 설명</summary>

- **vCPU Overcommit**: 물리 CPU 코어 수 대비 더 많은 가상 vCPU를 VM에 할당하는 기술로 과도할 경우 CPU Ready 지연 발생.
- **CPU Ready Time**: vCPU가 실행 준비(Ready)를 마쳤으나 물리 CPU 코어를 선점하지 못하고 큐에서 대기하는 시간.

</details>

| 문제 | 대책 | 효과 |
|:---|:---|:---|
| **타입 2** 쓰다가 메인 윈도우가 뻗어서 안에 있던 DB 가상 머신 10대가 다 같이 저세상 가는 대참사 | 돈지랄해서 상시 운영 서버는 무조건 깡통에 직접 박는 **타입 1**(베어메탈)로 싹 다 갈아엎음 | 빌어먹을 호스트 OS 붕괴로 인한 동반 자살(장애 경계) 원천 차단 |
| 가짜 CPU를 너무 많이 뻥튀기(**가상 시피유 초과 할당**)해서 VM들이 "내 차례 언제 와!" 하고 줄 서다 시스템이 멈춤 | CPU Ready 지연 시간을 칼같이 감시하고 뻥튀기(오버커밋) 비율에 무자비한 상한선 가이드라인 떡칠 | 가상 머신들이 버벅대고 멈추는 끔찍한 반응 지연(Latency) 완벽 억제 |
| 가상 머신들이 랜카드 쓸 때마다 하이퍼바이저가 통역해 주느라 서버 CPU가 100% 치솟고 터지려 함 | 물리 랜카드 하나를 가짜 수십 개로 찢어서 VM에 직빵으로 꽂아주는 **단일 루트 입출력 가상화(SR-IOV)** 장착 | 통역하느라 낭비되던 CPU 부하를 씹어먹고 랜카드 속도를 극한으로 쥐어짬 |

#### 한줄 요약

- **엔터프라이즈 상시 서비스 Type 1 전환·vCPU Overcommit(CPU Ready) 임계치 관리·SR-IOV 및 Virtio 패스스루 가속**

## Ⅶ. 결론

<details><summary>용어 설명</summary>

- **마이크로VM 및 경량 하이퍼바이저 진화**: AWS Firecracker, Cloud Hypervisor처럼 서버리스(Serverless)와 컨테이너를 위해 수 밀리초 만에 기동되는 경량 KVM 기반 Type 1 하이퍼바이저의 확산.

</details>

- 클라우드 인프라(IaaS) 및 대규모 데이터센터에서 **KVM/ESXi 기반 Type 1 하이퍼바이저 표준 채택 및 DPDK/SR-IOV 결합 가속**

#### 한줄 요약

- **성능 극대화와 무중단 고가용성**을 위한 Type 1 베어메탈 하이퍼바이저 인프라 구축
