## Ⅰ. 개요

<details><summary>용어 설명</summary>

- **하이퍼바이저(Hypervisor / VMM)**: 단일 물리 서버의 하드웨어 컴퓨팅 자원(CPU, 메모리, 스토리지, 네트워크)을 가상화하여 다수의 독립된 가상 머신(VM)을 생성, 스케줄링, 격리 통제하는 가상화 관리 계층.
- **베어메탈(Bare-Metal)**: 호스트 운영체제(Windows, Linux)의 개입 없이 물리 서버 하드웨어 실리콘 위에 하이퍼바이저가 직접 설치되어 하드웨어를 직접 제어하는 실행 환경.

</details>

- 정의/개념: 물리 하드웨어 상주 위치와 호스트 OS 유무에 따라 **Type 1(베어메탈)**과 **Type 2(호스티드)**로 분류하는 가상 머신 모니터 체계
- 배경/필요성: 전통 단일 OS의 **하드웨어 자원 낭비** 한계에 따른 인프라 **구축 비용 증가** 및 멀티테넌트 격리 제한 해소

#### 한줄 요약
- 하드웨어 직결형 Type 1(베어메탈)과 호스트 OS 기반 Type 2(호스티드)로 구분되어 엔터프라이즈 성능과 데스크톱 편의성을 차별화한다.

## Ⅱ. 특징

<details><summary>용어 설명</summary>

- **장애 도메인(Failure Domain)**: 특정 소프트웨어 계층(호스트 OS 또는 단일 VM)에서 장애가 발생했을 때 그 영향이 시스템 전체로 파급되는 물리적·논리적 범위.
- **이중 스케줄링(Double Scheduling)**: Type 2 환경에서 게스트 OS 스케줄러와 호스트 OS 커널 스케줄러가 2중으로 CPU 타임슬라이스를 중복 조율하여 발생하는 지연.

</details>

- Type 1 (Bare-Metal): 하이퍼바이저가 하드웨어에 직접 상주하여 호스트 OS 오버헤드 없이 **네이티브 95~99%** 성능 제공
- Type 2 (Hosted): 범용 OS 상에서 응용 프로그램으로 동작하여 편의성이 높으나 **이중 스케줄링** 및 다단계 I/O 오버헤드 수반
- **장애 도메인** 격리: Type 1은 단일 VM 장애가 격리되나, Type 2는 호스트 OS 장애 시 전체 게스트 VM이 중단

#### 한줄 요약
- Type 1은 중간 OS 없이 하드웨어에 직결되어 엔터프라이즈급 성능을 내며, Type 2는 호스트 OS 위에서 동작하여 개발 편의성을 제공한다.

## Ⅲ. 구조 및 구성요소

<details><summary>용어 설명</summary>

- **게스트 VM(Guest Virtual Machine)**: 하이퍼바이저가 할당한 vCPU, vRAM, vDisk를 기반으로 독립 실행되는 가상 운영체제 인스턴스.
- **호스트 OS(Host Operating System)**: Type 2 환경에서 물리 하드웨어를 직접 제어하며 하이퍼바이저 프로세스에 CPU/메모리 자원을 할당하는 기저 OS.

</details>

```text
[하이퍼바이저 유형별 계층 구조 비교]
 ├── Type 1 (Bare-Metal)
 │    ├── 게스트 가상 머신 (VM 1 ~ VM N)
 │    ├── Type 1 하이퍼바이저 (ESXi / KVM, 하드웨어 직접 제어)
 │    └── 물리 서버 하드웨어 (CPU / RAM / I/O)
 └── Type 2 (Hosted)
      ├── 게스트 가상 머신 (VM 1 ~ VM N)
      ├── Type 2 하이퍼바이저 (Workstation / VirtualBox, 호스트 앱)
      ├── 범용 호스트 OS (Windows / Linux)
      └── 물리 서버 하드웨어 (CPU / RAM / I/O)
```

선의 의미: 가지(`├──`, `└──`)는 하드웨어 소속 및 가상화 계층 관계를 나타냄

| 비교 항목 | Type 1 (Bare-Metal) 책임 | Type 2 (Hosted) 책임 |
|:---|:---|:---|
| 상주 위치 | 물리 서버 하드웨어 실리콘에 직접 상주 | 범용 호스트 OS 상단에 **애플리케이션으로 상주** |
| 호스트 OS 유무 | **호스트 OS 없음 (부재)** | 호스트 OS 커널 위에서 동작 (필수) |
| I/O 드라이버 경로 | 하이퍼바이저가 물리 드라이버 직접 구동 (**1단계 직결**) | 게스트 ➔ 하이퍼바이저 ➔ 호스트 OS ➔ 물리 장치 (**3단계 경유**) |
| 장애 격리성 | 단일 VM 장애가 타 VM에 영향 없음 (**엄격한 결함 격리**) | 호스트 OS 다운 시 **전체 게스트 VM 동시 중단** |
| 대표 제품 | **VMware ESXi**, KVM, Xen, Hyper-V | **VMware Workstation**, Oracle VirtualBox |

#### 한줄 요약
- Type 1은 중간 OS 없이 물리 서버에 직결되고, Type 2는 범용 호스트 OS 위에서 프로세스 형태로 중계 실행된다.

## Ⅳ. 흐름도

<details><summary>용어 설명</summary>

- **가상 I/O 패스(Virtual I/O Path)**: 게스트 VM 내부 드라이버가 발생시킨 읽기/쓰기 명령이 물리 스토리지 컨트롤러에 도달하기까지의 계층별 처리 경로.

</details>

```text
[게스트 애플리케이션 I/O 쓰기 요청 인입]
           │
           ▼
1. 게스트 OS I/O 발행: 가상 디스크 드라이버를 통해 I/O 요청 전달
           │
           ▼
2. 하이퍼바이저 유형별 I/O 스택 분기:
   ┌──────────────────┴──────────────────┐
[ Type 1 베어메탈 (ESXi / KVM) ]       [ Type 2 호스티드 (Workstation) ]
   │                                     │
   │                                  a. 가상 I/O를 호스트 OS 시스템 콜로 변환
   │                                     │
   │                                  b. 호스트 OS 파일시스템 드라이버 전달
   └──────────────────┬──────────────────┘
                      │
                      ▼
3. 물리 컨트롤러 커밋: 물리 디스크 컨트롤러에 데이터 쓰기 명령 수행
                      │
                      ▼
4. 가상 인터럽트 주입: 하이퍼바이저가 게스트 OS로 I/O 완료 인터럽트 전달
                      │
                      ▼
[I/O 쓰기 트랜잭션 완료]
```

분기 결과: Type 1은 **1단계 직결 I/O**로 고성능을 제공하며, Type 2는 **호스트 OS 중계**로 지연이 발생함

#### 한줄 요약
- 게스트 OS I/O 발행 ➔ 하이퍼바이저 유형별 I/O 스택 분기 ➔ 물리 컨트롤러 커밋 ➔ 가상 인터럽트 주입 순으로 동작한다.

## Ⅴ. 종류 및 비교

<details><summary>용어 설명</summary>

- **마이크로VM(MicroVM)**: AWS Firecracker처럼 서버리스 FaaS 환경을 위해 불필요한 레거시 디바이스 모델을 제거하고 5ms 이내로 초고속 기동하는 경량 VM.

</details>

| 가상화 아키텍처 | Type 1 (Bare-Metal) | Type 2 (Hosted) | OS 컨테이너 (Docker) | 마이크로VM (MicroVM) |
|:---|:---|:---|:---|:---|
| 가상화 계층 수준 | **하드웨어 가상화** 계층 | 호스트 OS 상단 **애플리케이션** | OS 커널 공유 (**cgroups/ns**) | 초경량 **하드웨어 가상화** |
| 가상화 실효 성능 | **네이티브 95~99%** | 70~85% (OS 오버헤드) | **99% 이상** (프로세스 격리) | **98% 이상** |
| 부팅 및 기동 속도 | 수십 초 ~ 수 분 | 수십 초 | **수백 밀리초 (ms)** | **5~10ms (초고속)** |
| 보안 격리성 수준 | 최고 (**하드웨어 격리**) | 중간 (호스트 OS 종속) | 낮음 (호스트 커널 공유) | 최고 (**KVM 하드웨어 격리**) |
| 주요 적용 분야 | **엔터프라이즈 IaaS** | 개발 및 테스트 환경 | **클라우드 네이티브 (MSA)** | **서버리스 (FaaS)** |

#### 한줄 요약
- 엔터프라이즈 IaaS는 Type 1, PC 개발은 Type 2, 클라우드 네이티브 MSA는 컨테이너, 서버리스 FaaS는 MicroVM을 적용한다.

## Ⅵ. 실무 고려사항 및 대책

<details><summary>용어 설명</summary>

- **CPU 레디 타임(CPU Ready Time, %RDY)**: vCPU가 실행 준비를 마쳤으나 하이퍼바이저로부터 물리 CPU 코어를 할당받지 못하고 대기열에서 지연되는 시간 비율(권장 5% 미만).

</details>

| 문제 | 대책 | 효과 |
|:---|:---|:---|
| 과도한 vCPU 오버커밋으로 인한 성능 저하 | **CPU 레디 타임(%RDY < 5%)** 모니터링 및 할당 조정 | 스케줄러 대기열 정체 해소 및 성능 균일화 |
| Type 1 스토리지/네트워크 I/O 병목 발생 | **SR-IOV** 패스스루 및 **Virtio** 드라이버 적용 | 하이퍼바이저 오버헤드 90% 제거 및 I/O 가속 |
| 물리 서버 하드웨어 장애 시 전체 VM 동시 중단 | 하이퍼바이저 **클러스터 HA** 자동 페일오버 구성 | 장애 시 타 물리 노드로 무중단 자동 재기동 |

#### 한줄 요약
- 실무에서는 %RDY 모니터링으로 CPU를 관리하고, SR-IOV로 I/O를 가속하며, 클러스터 HA로 물리 장애를 방어한다.

## Ⅶ. 결론

- 엔터프라이즈 운영은 **Type 1**, 개인 개발·시험은 **Type 2** 선택

#### 한줄 요약
- 하이퍼바이저는 엔터프라이즈 성능과 보안을 위한 Type 1과 개발 편의성을 위한 Type 2로 명확히 구분하여 설계해야 한다.
