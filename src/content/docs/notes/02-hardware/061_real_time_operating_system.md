## Ⅰ. 개요

<details><summary>용어 설명</summary>

- **RTOS(Real-Time Operating System)**: 우선순위·시간 제약 기반 스케줄링과 지연 상한 분석 수단을 제공하는 실시간 시스템용 운영체제.
- **결정론적(Deterministic)**: 동일한 조건에서 시스템의 처리 지연시간과 응답 순서가 예측 가능하고 상한선(Bounded Time)이 존재하는 특성.

</details>

- 정의/개념: 태스크의 시간 제약을 분석·충족할 수 있도록 우선순위 스케줄링과 **결정론적(Deterministic)** 커널 서비스를 제공하는 **RTOS(Real-Time Operating System)**
- 배경/필요성: 처리량과 공정성을 좇는 범용 OS는 지연의 상한을 제시하지 못해, 평균은 빨라도 마감시간을 보장할 수 없음

#### 한줄 요약
- 실시간이란 빠르다는 뜻이 아니라 늦지 않는다는 보장이며, 그래서 평균 성능을 희생해서라도 최악값을 좁히는 쪽이 옳은 선택이 된다.

## Ⅱ. 특징

<details><summary>용어 설명</summary>

- **선점형 우선순위 스케줄링(Preemptive Priority Scheduling)**: 더 높은 우선순위 태스크가 준비되면 현재 실행 중인 저순위 태스크를 즉시 중단시키고 CPU를 차지하는 방식.
- **최악 응답 시간(WCRT, Worst-Case Response Time)**: 인터럽트 지연, 문맥 교환, 락 블로킹 등을 모두 포함해 태스크 완료까지 걸릴 수 있는 최악의 시간.

</details>

- **선점형 우선순위 스케줄링(Preemptive Priority Scheduling)**으로 상위 태스크가 즉시 CPU 확보
- 인터럽트 지연과 문맥 교환 시간이 상한을 갖도록 커널 임계구역을 짧게 유지
- 제품에 따라 작은 모놀리식 커널이나 마이크로커널로 기능·격리·메모리를 절충

#### 한줄 요약
- **최악 응답 시간(WCRT, Worst-Case Response Time)**은 측정으로 얻는 값이 아니라 증명해야 하는 값이며, 시험에서 한 번도 안 나온 지연이 현장에서 처음 나타나는 일이 흔하다.

## Ⅲ. 구조 및 구성요소

<details><summary>용어 설명</summary>

- **TCB(Task Control Block)**: 태스크의 실행 상태(Ready/Blocked), 레지스터 스택 포인터, 우선순위 정보를 담고 있는 커널 제어 블록.
- **IPC(Inter-Process Communication)**: 태스크 간에 큐(Queue), 세마포어(Semaphore), 뮤텍스(Mutex), 이벤트 플래그로 데이터를 동기화하는 기법.

</details>

```text
[RTOS 커널 구조]
├─ 인터럽트·타이머 틱 (외부 이벤트 진입점)
├─ 커널
│  ├─ 선점형 스케줄러 (우선순위 준비 큐)
│  ├─ 동기화·IPC (뮤텍스·세마포어·메시지 큐)
│  ├─ TCB 관리자·문맥 교환 엔진
│  ├─ 타이머·지연 관리자
│  └─ 고정 크기 메모리 풀 관리자
└─ 태스크
   ├─ 긴급 제어 태스크 (높은 우선순위)
   ├─ 통신 처리 태스크
   └─ 배경 로깅 태스크 (낮은 우선순위)
```

선의 의미: 가지(`├─`)는 소유 관계이며, 태스크 사이에는 직접 연결이 없고 모든 상호작용이 커널의 동기화 모듈을 거침

| 구성요소 | 책임 |
|:---|:---|
| 선점형 스케줄러 | Ready 큐에서 가장 높은 우선순위 태스크를 선택해 CPU 실행권 부여 |
| **TCB(Task Control Block)** 관리자 | 실행 상태·스택 포인터·우선순위 보관과 문맥 저장·복원 |
| **IPC(Inter-Process Communication)** 모듈 | 큐·세마포어·뮤텍스로 태스크 간 데이터 교환 |
| 타이머·지연 관리자 | 주기적 틱으로 지연과 타임아웃 관리 |
| 메모리 풀 관리자 | 고정 크기 블록 할당으로 단편화와 불확정 지연 차단 |

#### 한줄 요약
- 커널이 제공하는 편의 기능이 적을수록 최악 지연을 계산하기 쉬워지므로, 실시간 커널의 작은 크기는 절약이 아니라 증명 가능성의 조건이다.

## Ⅳ. 흐름도

<details><summary>용어 설명</summary>

- **상태 전이(State Transition)**: 태스크가 Ready(준비), Running(실행), Blocked(대기/지연), Suspended 상태 간을 오가는 과정.

</details>

```text
외부 인터럽트 발생 → ISR이 이벤트 통지
        │
   깨어난 태스크가 현재보다 높은 우선순위인가?
   ┌────┴─────┐
아니오          예
   │             │
준비 큐에서     현재 태스크 문맥을 TCB에 저장 후 선점
대기 유지         │
   │        긴급 태스크가 필요한 공유 자원을 쓰는가?
   │        ┌────┴─────┐
   │      아니오          예
   │        │             │
   │     즉시 실행     자원 보유 태스크의
   │        │          우선순위 임시 승격 후 대기
   │        └────┬────────┘
   │             │
   │        마감시간 안에 출력 완료
   └────┬────────┘
        │
   문맥 복원 후 이전 태스크 재개
```

분기 결과: 선점만으로는 응답이 보장되지 않고 공유 자원을 만나는 순간 대기가 발생하므로, **상태 전이(State Transition)** 분석에서 실제 상한을 정하는 것은 실행 시간이 아니라 블로킹 시간

#### 한줄 요약
- 우선순위를 아무리 높게 줘도 자원을 쥔 하위 태스크 앞에서는 기다려야 하므로, 실시간 설계의 난점은 스케줄링이 아니라 공유 자원 관리에 있다.

## Ⅴ. 종류 및 비교

| 운영체제 아키텍처 | RTOS (실시간 OS) | GPOS (범용 OS) | 베어메탈 (No OS) | 임베디드 리눅스 |
|:---|:---|:---|:---|:---|
| 적용 기준 | 미션 크리티컬 차량·항공·의료 제어 | PC·스마트폰 멀티미디어·사무용 | 극소형 초저가 가전 센서 노드 | 스마트 게이트웨이·복잡한 통신 장비 |
| 핵심 특징 | 선점형 우선순위 스케줄링 및 결정론적 응답 | 공정성(Fairness) 기반 시분할 및 높은 처리율 | OS 없이 메인 무한 루프 직접 폴링 | 광범위한 드라이버 지원 및 오픈소스 |
| 한계 | 지원 라이브러리 및 복잡한 GUI 부재 | 비결정적 지연(지연시간 예측 불가) | 코드 복잡도 증가 시 유지보수 한계 | 실시간성 보장 불가(PREEMPT_RT 필요) |

#### 한줄 요약
- 네 선택지는 편의 기능과 예측 가능성을 맞바꾼 눈금이며, 기능이 늘수록 최악 지연을 증명할 수 있는 범위는 좁아진다.

## Ⅵ. 실무 고려사항 및 대책

<details><summary>용어 설명</summary>

- **우선순위 역전(Priority Inversion)**: 중간 순위 태스크가 실행되면서 자원을 쥐고 있는 저순위 태스크를 가로채 고순위 태스크가 무한정 대기하는 버그.
- **우선순위 상속(Priority Inheritance)**: 공유 자원을 획득한 저순위 태스크의 우선순위를 자원을 기다리는 고순위 태스크 수준으로 임시 승격시키는 기법.

</details>

| 문제 | 대책 | 효과 |
|:---|:---|:---|
| 공유 자원 점유로 **우선순위 역전(Priority Inversion)** 발생 | **우선순위 상속(Priority Inheritance)**과 임계구역 상한 설정 | 상위 태스크의 블로킹 시간에 상한 부여 |
| 잦은 문맥 교환으로 실효 처리 시간 감소 | ISR 축소와 태스크 주기·우선순위 재조정 | 불필요한 선점과 캐시 손실 감소 |
| 태스크 스택 부족으로 인접 메모리 침범 | 스택 사용 최고치 감시와 하드웨어 보호 영역 설정 | 침범 차단과 즉각 예외 발생 |
| 동적 할당이 단편화와 불확정 지연 유발 | 고정 크기 메모리 풀을 초기화 시점에 확보 | 할당 경로의 최악 지연 분석 가능 |

#### 한줄 요약
- 네 대책이 모두 최악값을 좁히는 방향이지 평균을 개선하는 방향이 아니듯, 실시간 시스템의 최적화는 빠르게가 아니라 예측 가능하게를 목표로 한다.

## Ⅶ. 결론

- 마감시간 위반이 곧 위험으로 이어지면 실시간 커널과 최악 응답 시간 분석을 함께 도입하고, 태스크가 하나뿐인 단순 제어는 베어메탈 루프로 남겨 분석 대상 자체를 줄임
- 안전 필수 분야는 제품명이 아니라 인증 산출물·격리 수준·도구 체인과 전체 시스템 증거로 결정

#### 한줄 요약
- 실시간 커널을 쓴다고 실시간성이 생기는 것이 아니라 최악 응답 시간을 계산할 수 있게 될 뿐이며, 그 계산을 하지 않으면 도입 효과는 없다.
