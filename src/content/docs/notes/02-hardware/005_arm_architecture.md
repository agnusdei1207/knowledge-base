## Ⅰ. 개요

<details><summary>용어 설명</summary>

- **Arm 아키텍처(Arm Architecture)**: 로드·스토어(Load-Store) 기반 RISC 구조로, 프로파일별로 시스템 기능과 실행 권한 계층을 최적화한 범용 프로세서 아키텍처.
- **프로파일(Profile)**: 응용 분야별 요구사항에 맞춰 기능 집합과 하드웨어 구조를 특화한 Arm 아키텍처 분류(A/R/M-Profile).
- **실행 상태(Execution State)**: 레지스터 너비, 주소 공간 크기, 명령어 세트 규격을 정의하는 프로세서 동작 모드(AArch64/AArch32).

</details>

- 정의/개념: 메모리 접근을 로드·스토어 명령어로만 한정하고, 응용 분야를 프로파일로 갈라 기능 범위를 다르게 규정한 **Arm 아키텍처**
- 배경/필요성: 범용 OS·실시간 제어·초저전력 장치는 요구하는 권한 계층과 메모리 모델이 달라 하나의 기능 집합으로 덮을 수 없음

#### 한줄 요약
- 프로파일 분리는 기능을 더하기 위한 장치가 아니라 쓰지 않을 기능을 명세 단계에서 잘라 내기 위한 장치이며, 그래서 상위 프로파일의 코드는 하위에서 돌지 않는다.

## Ⅱ. 특징

<details><summary>용어 설명</summary>

- **예외 수준(Exception Level, EL)**: 사용자 애플리케이션(EL0), OS 커널(EL1), 하이퍼바이저(EL2), 시큐어 모니터/펌웨어(EL3)로 실행 권한을 계층화한 Armv8/v9 실행 모델.
- **TrustZone**: 단일 물리 코어를 하드웨어 수준에서 일반 영역(Normal World)과 보안 영역(Secure World)으로 완벽히 격리하는 Arm 보안 확장 기술.
- **벡터 확장(Vector Extension)**: NEON, SVE(Scalable Vector Extension) 등 단일 명령어로 다중 데이터를 병렬 처리하는 SIMD 확장 기술.

</details>

- 로드·스토어로만 메모리에 접근해 파이프라인 설계 단순화
- EL0~EL3 **예외 수준**으로 소프트웨어 권한 계층 분리
- 프로파일별 **TrustZone**·벡터·가상화 기능 범위로 응용 분야 구분

#### 한줄 요약
- 로드·스토어 제약은 프로그래머에게는 불편이지만 파이프라인 설계자에게는 메모리 접근 지점을 한 단계로 못 박아 주는 이득이다.

## Ⅲ. 구조 및 구성요소

<details><summary>용어 설명</summary>

- **A-profile(Application Profile)**: 가상 메모리(MMU)와 풍부한 OS 기능, 멀티코어 가상화를 지원하는 고성능 컴퓨팅용 프로파일.
- **R-profile(Real-Time Profile)**: MPU 기반으로 예측 가능하고 결정론적인(Deterministic) 초저지연 응답을 보장하는 실시간 임베디드 제어용 프로파일.
- **M-profile(Microcontroller Profile)**: 초저전력 및 빠른 하드웨어 인터럽트 처리에 최적화된 마이크로컨트롤러 전용 프로파일(Cortex-M).
- **AArch64**: 64비트 범용 레지스터 31개와 64비트 가상 주소 공간, A64 명령어 세트를 제공하는 64비트 실행 상태.

</details>

```text
[Arm 아키텍처]
├─ 프로파일
│  ├─ A-profile  (범용 OS·가상화)
│  ├─ R-profile  (실시간 제어)
│  └─ M-profile  (저전력 임베디드)
├─ 실행 상태
│  └─ AArch64 / AArch32
├─ 권한 모델
│  └─ 예외 수준 (EL0~EL3)
└─ 선택 확장
   ├─ TrustZone
   └─ 벡터 확장
```

선의 의미: 가지(`├─`)는 소유 관계; 선택 확장(`└─`)은 프로파일에 따라 지원 여부가 다름

| 구성요소 | 책임 |
|:---|:---|
| 프로파일 | 응용 분야별 시스템 기능·메모리 모델 범위 결정 |
| 실행 상태 | 레지스터 폭·명령어 규칙으로 소프트웨어 이진 형식 결정 |
| **예외 수준** | 앱·OS·가상화·보안 펌웨어의 권한 계층 분리 |
| **TrustZone** | 보안·비보안 자원의 물리 접근 경계 분리 |
| 벡터 확장 | SIMD·ML 워크로드의 데이터 병렬 처리 |

#### 한줄 요약
- 프로파일이 먼저 정해지고 나머지가 따라오므로, 제품 중간에 프로파일을 바꾸는 결정은 확장 몇 개를 바꾸는 일이 아니라 소프트웨어 스택 전체를 바꾸는 일이 된다.

## Ⅳ. 흐름도

<details><summary>용어 설명</summary>

- **예외(Exception)**: 인터럽트, 시스템 호출(SVC/HVC/SMC), 메모리 폴트 등 현재 실행 흐름을 중단하고 상위 특권 처리기로 제어를 전환시키는 하드웨어 사건.
- **벡터 테이블(Vector Table)**: 각 예외 유형별 인터럽트 서비스 루틴(ISR)의 진입점 주소를 저장하는 메모리 테이블(VBAR_ELx로 기준 주소 지정).
- **예외 복귀(Exception Return)**: ERET 명령어를 통해 SPSR과 ELR에 보관된 프로세서 상태와 복귀 주소를 복원하고 이전 실행 수준으로 복귀하는 동작.

</details>

```text
실행 중 예외 발생 (인터럽트·시스템 호출·오류)
        │
   예외를 어느 EL이 받는가?
 ┌──────┼──────────┐
같은 EL 유지  상위 EL로 승격   EL3 라우팅
 │        │            │
 │   현재 EL 컨텍스트   보안 상태 전환
 │     보존 필요        선행
 └────┬───┘            │
      │                │
  복귀 주소·PSTATE를 대상 EL 전용 레지스터에 저장
      │
  VBAR_ELx + 예외 종류 오프셋으로 벡터 테이블 진입
      │
   처리기 완료 후 ERET 실행
      │
   예외 복귀: PSTATE 복원 후 이전 EL 재개
```

분기 결과: 예외 원인과 라우팅 설정이 대상 EL을 정하고, EL이 올라갈수록 저장해야 할 컨텍스트와 전환 비용이 늘어남

#### 한줄 요약
- 예외 처리 비용은 처리기 코드의 길이가 아니라 몇 단계의 EL을 건너뛰었는지가 결정하며, 실시간 응답 설계가 EL 배치부터 따지는 이유가 여기에 있다.

## Ⅴ. 종류 및 비교

| Arm 프로파일 | A-profile | R-profile | M-profile |
|:---|:---|:---|:---|
| 적용 기준 | 범용 OS·가상화·고성능 처리 요구 | 결정적 실시간 응답 필수 | 저전력·소형 제어 장치 |
| 핵심 특징 | **예외 수준** EL0~EL3·MMU·가상화 지원 | 결정적 응답 시간·MPU 기반 보호 | 단순화된 예외 모델·**TrustZone** 선택 지원 |
| 한계 | 전력·면적·소프트웨어 스택 복잡도 | 범용 OS·가상화 기능 제약 | 고성능·가상화 기능 제약 |

#### 한줄 요약
- 세 프로파일은 성능 등급이 아니라 최악 응답 시간을 보장하는 방식의 차이이며, A-profile이 R-profile보다 빠르지만 늦을 때 얼마나 늦을지는 알 수 없다.

## Ⅵ. 실무 고려사항 및 대책

<details><summary>용어 설명</summary>

- **런타임 기능 탐지(Runtime Feature Detection)**: CPUID 및 시스템 레지스터를 조회하여 런타임에 프로세서가 지원하는 확장 기능(AES, FP, SVE 등)을 동적으로 판별하는 기법.
- **동적 전압·주파수 조절(Dynamic Voltage and Frequency Scaling, DVFS)**: 시스템 부하 및 발열 상태에 따라 동작 전압과 클록 주파수를 동적으로 조절하여 전력 소모를 최적화하는 기법.
- **최소 권한 원칙(Principle of Least Privilege)**: 각 소프트웨어 모듈이 임무 수행에 필요한 최소한의 예외 수준(EL)과 하드웨어 자원 접근 권한만 부여받도록 강제하는 보안 설계 원칙.

</details>

| 문제 | 대책 | 효과 |
|:---|:---|:---|
| 지원 확장 없는 장치에서 명령어 실행 실패 | **런타임 기능 탐지**·대체 코드 경로 제공 | 장치별 실행 호환성 확보 |
| 특권 코드가 과도한 EL로 자원 접근 | **최소 권한 원칙**·EL 경계 검증 | 취약점 영향 범위 축소 |
| 고부하·고온에서 전력·성능 한계 충돌 | **DVFS** 정책·열 설계 시험 | 전력 한도 내 안정 동작 확보 |
| 프로파일과 OS 기능 요구 불일치 | 프로파일별 예외·메모리 기능 사전 검증 | 제품 요구와 ISA 기능 정합성 확보 |

#### 한줄 요약
- 같은 아키텍처 이름을 달아도 지원 확장이 장치마다 다르므로, 컴파일 시점의 가정이 아니라 실행 시점의 확인이 이식성의 실제 근거가 된다.

## Ⅶ. 결론

- OS·응답 시간·전력 한도로 프로파일 경계를 먼저 정해 범용 OS는 **A-profile**, 결정적 제어는 **R-profile**, 소형 제어는 M-profile 선택

#### 한줄 요약
- 코어 이름을 고르는 일은 마지막 단계이며, 그 앞에 OS를 올릴지·응답 시한을 보장할지·전력 예산이 얼마인지가 이미 프로파일을 정해 놓는다.
