## Ⅰ. 개요

<details>
<summary>핵심 용어</summary>

- **Arm 아키텍처**: 로드•스토어 구조에 실행 상태•권한•명령 확장을 결합한 ISA
- **명령어 집합 아키텍처(Instruction Set Architecture, ISA)**: 프로세서의 명령어•레지스터•데이터 형식 규격
- **실행 상태**: 사용할 명령어 집합과 레지스터 폭을 정하는 상태
- **예외 수준(Exception Level, EL)**: 실행 주체의 권한을 단계별로 격리하는 체계
- **선택 명령 확장**: 용도에 따라 선택적으로 구현하는 추가 명령 집합

</details>

- 정의/개념: **Arm 아키텍처** 는 로드•스토어 구조에 실행 상태•예외 수준•선택 명령 확장을 결합한 **ISA 계열**
- 배경/필요성: 임베디드부터 서버까지 서로 다른 권한 격리•연산 폭•벡터 처리 요구를 **공통 아키텍처로 지원할 필요**

#### 한줄 요약
- Arm은 실행 상태•권한•확장을 조합해 임베디드부터 서버까지 서로 다른 요구를 지원한다.

## Ⅱ. 특징

<details>
<summary>핵심 용어</summary>

- **로드•스토어 구조** 는 메모리 접근을 전용 명령으로 처리하고 일반 연산은 레지스터 사이에서 수행한다.
- **코어 지식재산권(Core Intellectual Property, 코어 IP)**: 검증된 프로세서 설계를 재사용하도록 제공하는 설계 블록
- **마이크로아키텍처** 는 같은 ISA를 파이프라인•캐시•실행 장치 등으로 실제 구현한 내부 구조이다.

</details>

- **로드•스토어 구조** 로 메모리 접근과 레지스터 연산 분리
- **실행 상태•예외 수준** 조합으로 용도별 코어 분화
- ISA 규격과 **코어 IP** 구현의 분리 공급

#### 한줄 요약
- 동일 Arm ISA도 코어 마이크로아키텍처와 지원 확장에 따라 성능•전력 특성이 달라진다.

## Ⅲ. 구조 및 구성요소

<details>
<summary>핵심 용어</summary>

- **AArch64**: A64 명령어를 실행하는 Arm의 64비트 실행 상태
- **AArch32**: A32•T32 명령어를 실행하는 Arm의 32비트 실행 상태
- **Neon**: 고정 길이 벡터로 여러 데이터 원소를 처리하는 명령 확장
- **확장 가능 벡터 확장(Scalable Vector Extension, SVE)**: 구현별 벡터 길이를 지원하는 명령 확장
- **레지스터 집합** 은 연산 데이터•주소•상태를 CPU 내부에 고속으로 보관하는 저장 공간이다.
- **EL 격리** 는 AArch64의 예외 수준별로 실행 권한과 접근 가능한 자원을 분리하는 방식이다.

</details>

```text
                      [동작 모드]
                           |
                           |
[예외 수준] -- [실행 상태] -- [레지스터 집합]
                           |
                           |
                       [확장 명령]
```

선의 의미: 실행 상태를 중심으로 AArch32 동작 모드, AArch64 예외 수준, 레지스터 집합, 선택 확장이 결합된 정적 ISA 구성이다.

| 구성요소 | 책임 |
|:---|:---|
| 실행 상태 | 명령 집합•레지스터 폭•**실행 환경** 규정 |
| 동작 모드 | AArch32의 **실행 모드** 규정 |
| 예외 수준 | AArch64의 **EL 격리** 규정 |
| 레지스터 집합 | 연산 데이터•주소•상태 **고속 보관** |
| 확장 명령 | **NEON•SVE** 벡터 연산 제공 |

#### 한줄 요약
- 실행 상태가 명령과 레지스터 폭을 정하고 예외 수준과 확장 명령이 권한과 병렬 연산을 제공한다.

## Ⅳ. 흐름도

<details>
<summary>핵심 용어</summary>

- **트랩** 은 시스템 호출이나 오류를 현재 실행 주체보다 높은 예외 수준의 처리기로 넘기는 제어 전환이다.
- **예외 라우팅** 은 예외 원인과 설정된 규칙에 따라 예외를 처리할 EL을 선택하는 과정이다.
- **ELR_ELx** 는 예외 처리 후 복귀할 프로그램 카운터를 보관하는 레지스터이다.
- **SPSR_ELx** 는 예외 발생 전 PSTATE를 보관하는 저장 프로그램 상태 레지스터이다.
- **VBAR_ELx** 는 예외 처리 루틴을 선택할 벡터 테이블 기준 주소를 보관하는 레지스터이다.
- **ELx 예외 처리기** 는 해당 예외 수준에서 원인을 판독하고 필요한 서비스를 수행하는 루틴이다.
- **ERET** 은 SPSR_ELx와 ELR_ELx를 이용해 이전 실행 상태로 복귀하는 명령이다.

</details>

```text
┌──────────────────────────────┐
│ 현재 소프트웨어 실행         │
└──────────────┬───────────────┘
               │ 예외·인터럽트·트랩 발생
               ▼
┌──────────────────────────────┐
│ 1. 대상 EL 판정              │
│ 원인·현재 EL·라우팅 설정     │
└──────────────┬───────────────┘
               ▼
┌──────────────────────────────┐
│ 2. 복귀 상태 저장            │
│ ELR_ELx ← PC, SPSR_ELx ← 상태│
└──────────────┬───────────────┘
               ▼
┌──────────────────────────────┐
│ 3. 벡터 엔트리 계산          │
│ VBAR_ELx + 예외별 오프셋     │
└──────────────┬───────────────┘
               ▼
┌──────────────────────────────┐
│ 4. ELx 예외 처리             │
│ 원인 판독·서비스·상태 정리   │
└──────────────┬───────────────┘
               │ ERET
               ▼
┌──────────────────────────────┐
│ 5. 실행 상태 복원            │
│ PC ← ELR_ELx, 상태 ← SPSR_ELx│
└──────────────┬───────────────┘
               ▼
┌──────────────────────────────┐
│ 원래 소프트웨어 실행 재개    │
└──────────────────────────────┘
```

**동작 원리**

- **1. 대상 EL 판정**: 원인•현재 EL•라우팅 설정 확인
- **2. 복귀 상태 저장**: PC•PSTATE를 ELR_ELx•SPSR_ELx에 보관
- **3. 벡터 엔트리 계산**: VBAR_ELx에 예외별 오프셋 적용
- **4. ELx 예외 처리**: 원인 판독•서비스•복귀 조건 정리
- **5. 실행 상태 복원**: ERET로 PSTATE•PC 복원

#### 한줄 요약
- EL 판정•상태 저장•벡터 진입•ERET의 **예외 제어 흐름**

## Ⅴ. 종류 및 비교

<details>
<summary>핵심 용어</summary>

- **시스템 온 칩(System on Chip, SoC)**: 프로세서•메모리 제어기•주변장치를 통합한 반도체
- **Arm** 은 로드•스토어 구조와 정형화된 명령 인코딩을 기반으로 하는 ISA 계열이다.
- **x86-64** 는 기존 x86 프로그램과의 호환성을 유지하면서 주소와 레지스터를 64비트로 확장한 ISA이다.
- **레거시 부담** 은 이전 세대 명령과 소프트웨어의 호환성을 유지하기 위해 해독 회로와 설계가 복잡해지는 비용이다.
- **응용 프로그램 이진 인터페이스(Application Binary Interface, ABI)**: 호출 규약•레지스터•바이너리 형식 규격
- **가변 길이 명령•호환 모드** 는 명령마다 바이트 길이가 다르고 이전 실행 환경을 함께 지원하는 x86-64의 특성이다.

</details>

| 명령어 집합 구조 | Arm | x86-64 |
|:---|:---|:---|
| 적용 기준 | 전력 제약•**SoC 통합** | 기존 **x86 바이너리** 호환 |
| 핵심 특징 | **로드•스토어**•정형 인코딩 | **가변 길이 명령**•호환 모드 |
| 한계 | 대상 **ISA•ABI**별 재빌드 | 해독 회로•**레거시** 부담 |

> 요약: 전력•통합성과 기존 바이너리 호환성 비교

#### 한줄 요약
- Arm은 SoC 통합과 전력 효율에, x86-64는 기존 바이너리 호환에 강점이 있다.

## Ⅵ. 실무 고려사항 및 대책

<details>
<summary>핵심 용어</summary>

- **네이티브 라이브러리** 는 특정 ISA와 ABI의 기계어로 컴파일되므로 다른 구조로 이식할 때 다시 빌드해야 한다.
- **런타임 기능 탐지** 는 실행 중인 코어가 NEON•SVE 등의 확장을 지원하는지 확인하여 적합한 코드 경로를 선택한다.
- **최소 권한**: 각 EL에 작업 수행에 필요한 권한만 부여하는 원칙
- **트랩 경로**: 예외가 지정된 처리 수준으로 전달되는 제어 경로
- **대체 코드** 는 특정 명령 확장을 지원하지 않는 코어에서도 같은 기능을 수행하도록 마련한 일반 명령 경로이다.
- **SoC 벤치마크**: 실제 칩에서 성능과 전력 소비를 측정하는 시험
- **부하별 벤치마크**: 작업 조건별 성능과 전력 소비를 비교하는 시험

</details>

| 문제 | 대책 | 효과 |
|:---|:---|:---|
| 이식 후 **네이티브 라이브러리** 실행 실패 | 대상 **ISA•ABI 재빌드** 와 의존성 목록화 | **바이너리 호환 문제** 예방 |
| **예외 수준** 설정 오류로 권한 침범 | EL별 **최소 권한•트랩 경로** 검증 | **커널•가상화 격리** 유지 |
| 배포 장비의 **NEON•SVE** 기능 누락 | **런타임 기능 탐지•대체 코드** 제공 | 다양한 코어의 **실행 호환성** 보장 |
| 기대한 **전력 효율** 미달 | 실제 **SoC•부하별 벤치마크** | **코어•가속기 구성** 최적화 |

#### 한줄 요약
- ISA•ABI 호환성, 예외 수준 격리, 확장 지원과 실제 전력 효율을 함께 검증해야 ARM 이식 위험을 줄일 수 있다.

## Ⅶ. 결론

<details>
<summary>핵심 용어</summary>

- **전력 효율** 은 같은 작업을 처리하는 데 소비하는 에너지를 기준으로 평가하며 실제 SoC와 부하에서 측정해야 한다.
- **네이티브 라이브러리 재빌드** 는 대상 Arm ISA와 ABI에 맞춰 기존 기계어 라이브러리를 다시 컴파일하는 작업이다.

</details>

- 전력•SoC 통합은 **Arm**, 기존 바이너리는 **x86-64** 선택

#### 한줄 요약
- 전력•SoC 통합이 중요하면 Arm을 검토하고 네이티브 라이브러리 재빌드 비용을 함께 산정한다.
