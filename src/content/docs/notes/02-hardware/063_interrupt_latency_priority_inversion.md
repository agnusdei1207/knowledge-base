## Ⅰ. 개요

<details><summary>용어 설명</summary>

- **인터럽트 레이턴시(Interrupt Latency)**: 하드웨어 인터럽트 신호가 발생한 시점부터 CPU가 해당 인터럽트 서비스 루틴(ISR)의 첫 명령어를 실행하기까지 걸리는 시간.
- **우선순위 역전(Priority Inversion)**: 고순위 태스크가 저순위 태스크가 점유한 자원을 기다리면서 실행 순서가 우선순위와 반대로 되는 현상.

</details>

- 정의/개념: 이벤트 발생부터 처리 시작까지의 **인터럽트 레이턴시(Interrupt Latency)**와 공유 자원 경합이 만드는 **우선순위 역전(Priority Inversion)**이라는 두 실시간 병목
- 배경/필요성: 두 지연은 코드 실행 시간과 무관하게 발생하므로, 알고리즘을 아무리 최적화해도 마감시간 위반이 남음

#### 한줄 요약
- 두 현상 모두 코드를 빠르게 만들어도 사라지지 않고 시스템 구조에서만 해소되므로, 실시간 문제의 원인은 대개 알고리즘 바깥에 있다.

## Ⅱ. 특징

<details><summary>용어 설명</summary>

- **우선순위 상속 프로토콜(Priority Inheritance Protocol, PIP)**: 공유 뮤텍스를 쥔 저순위 태스크의 우선순위를 자원을 기다리는 고순위 태스크의 우선순위로 임시 승격시키는 기법.
- **우선순위 천장 프로토콜(Priority Ceiling Protocol, PCP)**: 뮤텍스마다 접근 가능한 최고 우선순위(Ceiling)를 부여하여 교착상태(Deadlock)와 연쇄 블로킹을 사전 차단하는 기법.

</details>

- 인터럽트 레이턴시는 파이프라인 정리·문맥 저장·마스킹 구간의 합으로 결정
- 우선순위 역전은 중간 순위 태스크가 자원 보유자를 선점할 때 블로킹이 무한정 늘어남
- 대응책은 **Top-Half / Bottom-Half** 분리와 **우선순위 상속 프로토콜(Priority Inheritance Protocol, PIP)**·**우선순위 천장 프로토콜(Priority Ceiling Protocol, PCP)** 적용

#### 한줄 요약
- 앞의 지연은 상한이 하드웨어로 정해지지만 뒤의 지연은 프로토콜이 없으면 상한 자체가 존재하지 않으므로, 위험의 성격이 전혀 다르다.

## Ⅲ. 구조 및 구성요소

<details><summary>용어 설명</summary>

- **Top-Half / Bottom-Half**: 인터럽트 직후 즉각 처리해야 하는 최소 하드웨어 작업(Top-Half)과 지연 처리 가능한 본 작업(Bottom-Half)으로 나누는 기법.

</details>

```text
[실시간 지연 통제 구조]
├─ 하드웨어 경로
│  ├─ 인터럽트 컨트롤러 (우선순위 판별·벡터 전달)
│  └─ Top-Half 핸들러 (최소 확인 후 즉시 복귀)
├─ 지연 처리 경로
│  └─ Bottom-Half 핸들러 (긴 후속 처리를 태스크 문맥으로 위임)
└─ 자원 보호 경로
   ├─ 우선순위 상속 뮤텍스 (보유자 우선순위 임시 승격)
   └─ 우선순위 천장 뮤텍스 (획득 시 천장 우선순위 즉시 부여)
```

선의 의미: 가지(`├─`)는 소유 관계이며, 위 두 경로는 지연의 길이를 줄이고 아래 경로는 지연의 상한을 만들어 냄

| 구성요소 | 책임 |
|:---|:---|
| 인터럽트 컨트롤러 | 신호 우선순위 판별과 CPU로 벡터 전달 |
| Top-Half 핸들러 | 인터럽트 확인과 최소 데이터 취득 후 즉시 복귀 |
| Bottom-Half 핸들러 | 긴 후속 처리를 태스크 문맥으로 위임 |
| 우선순위 상속 뮤텍스 | 자원 보유 태스크를 임시 승격해 중간 선점 차단 |
| 우선순위 천장 뮤텍스 | 자원별 천장 값과 획득 규칙으로 블로킹·교착 제한 |

#### 한줄 요약
- 자원 보호 경로만이 커널 정책에 속하므로 하드웨어를 바꾸지 않고도 최악 지연을 바꿀 수 있으며, 실시간 개선의 여지는 대개 이쪽에 남아 있다.

## Ⅳ. 흐름도

<details><summary>용어 설명</summary>

- **임계 구역(Critical Section)**: 공유 자원의 무결성을 위해 한 번에 하나의 태스크만 접근해야 하는 코드 영역.

</details>

```text
저순위 태스크가 임계 구역에서 락 보유 중
        │
   고순위 태스크가 같은 자원을 요청
        │
   보호 프로토콜이 적용돼 있는가?
   ┌────┴─────┐
아니오          예
   │             │
중간 순위       보유 태스크 우선순위를 즉시 승격
태스크가 선점      │
   │        중간 순위 태스크 선점 불가
블로킹 시간       │
무한정 증가     임계 구역 신속 완료 후 락 해제
   │             │
   │        우선순위 원복 → 고순위 태스크 실행
   └────┬────────┘
        │
   응답 시간 상한 확보 여부가 갈림
```

분기 결과: 프로토콜이 없으면 블로킹 시간이 중간 순위 태스크의 개수와 실행 시간에 좌우되어 상한을 계산할 수 없고, 있으면 임계 구역 길이 하나로 상한이 결정

#### 한줄 요약
- 프로토콜이 하는 일은 블로킹을 없애는 것이 아니라 계산 가능한 크기로 묶는 것이며, **임계 구역(Critical Section)**을 짧게 유지해야 그 값이 쓸모 있어진다.

## Ⅴ. 종류 및 비교

| 실시간 응답 지연 요인 | 인터럽트 레이턴시 | 비제한적 우선순위 역전 | 우선순위 상속 (PIP) | 우선순위 천장 (PCP) |
|:---|:---|:---|:---|:---|
| 적용 기준 | 하드웨어 이벤트 즉각 수신 단계 | 단순 뮤텍스 사용 임베디드 시스템 | 다중 스레드 공유 자원 경합 완화 | 엄격한 다중 락 교착상태 방지 시스템 |
| 핵심 특징 | 하드웨어 인터럽트 진입 지연시간 | 중간 태스크의 무한 선점으로 지연 폭증 | 락을 쥔 저순위 태스크 우선순위 임시 승격 | 락 획득 시 Ceiling 우선순위 즉각 부여 |
| 한계 | 인터럽트 비활성화 구간에 종속 | 화성 탐사선(Mars Pathfinder) 마비 사고 유발 | 다중 자원 시 연쇄 블로킹 및 데드락 가능 | 구현 복잡도 및 과도한 락 상한 오버헤드 |

#### 한줄 요약
- 두 프로토콜의 차이는 언제 승격하느냐이며, 상속은 문제가 생긴 뒤 반응하고 천장은 미리 올려 두어 교착 가능성 자체를 없앤다.

## Ⅵ. 실무 고려사항 및 대책

<details><summary>용어 설명</summary>

- **화성 패스파인더 사건(Mars Pathfinder Incident)**: 1997년 화성 탐사선에서 정보 버스 뮤텍스 경합으로 비제한적 우선순위 역전이 발생해 시스템 리셋이 반복되었던 사건.

</details>

| 문제 | 대책 | 효과 |
|:---|:---|:---|
| 긴 처리 루틴이 후속 인터럽트를 막음 | 최소 확인·데이터 포착 후 나머지를 지연 처리로 위임 | 마스킹 구간과 점유 시간 감소 |
| 임계 구역 안의 입출력으로 블로킹 상한 소멸 | 자원별 상속 뮤텍스와 임계 구역 길이 상한 적용 | 중간 순위 선점 차단과 상한 확보 |
| 중첩 락 순서가 어긋나 순환 대기 발생 | 천장 프로토콜 또는 일관된 락 순서와 정적 분석 | 순환 대기와 연쇄 블로킹 차단 |
| 전역 인터럽트 비활성화 남용으로 무반응 구간 확대 | 세분화된 락과 락 프리 자료구조 적용 | 무반응 구간 축소와 응답 상한 개선 |

#### 한줄 요약
- **화성 패스파인더 사건(Mars Pathfinder Incident)**이 보여 주듯 이 결함은 시험에서 거의 재현되지 않으므로, 관측이 아니라 설계 시점의 프로토콜 선택으로만 막을 수 있다.

## Ⅶ. 결론

- 마감시간을 인터럽트 처리 지연이 지배하면 지연 처리 분리를, 공유 자원 블로킹이 지배하면 상속·천장 프로토콜을 선택하되, 모든 락에 일괄 적용하지 말고 마스킹 구간·임계 구역·중첩 락의 최악 상한을 함께 분석

#### 한줄 요약
- 프로토콜을 모든 락에 무조건 걸면 오버헤드만 늘고 상한은 개선되지 않으므로, 적용 대상은 최악 경로에 실제로 등장하는 자원으로 좁혀야 한다.
