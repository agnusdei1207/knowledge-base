## Ⅰ. 개요

<details><summary>용어 설명</summary>

- **RISC-V**: 오픈소스 라이선스(BSD 등) 기반으로 기본 정수 명령어 세트(Base ISA)와 모듈형 표준/커스텀 확장을 제공하는 개방형 명령어 집합 구조.
- **개방형 ISA(Open ISA)**: 로열티나 라이선스 제약 없이 누구나 자유롭게 하드웨어를 구현하고 기능을 확장할 수 있도록 공개된 명령어 세트 표준 규격.
- **명세 기반 호환성(Specification-Based Compatibility)**: 마이크로아키텍처 구현 방식과 무관하게 표준 ISA 명세 규격을 충족하여 동일 바이너리의 상호 운용성을 보장하는 특성.

</details>

- 정의/개념: 공개된 최소 공통 규격과 모듈형 확장을 조합해 제품마다 다른 명령어 구성을 만들 수 있는 **개방형 ISA**
- 배경/필요성: 독점 ISA는 라이선스가 구현 주체를 제한하고 맞춤형 명령어 추가를 막아, 도메인 특화 가속기를 만들 자율성이 없음

#### 한줄 요약
- 개방의 실익은 라이선스 비용 절감이 아니라 명령어를 직접 추가할 권한이며, 그 권한을 쓰는 순간 호환성 관리 책임도 같이 넘어온다.

## Ⅱ. 특징

<details><summary>용어 설명</summary>

- **기본 ISA(Base ISA)**: 정수 연산 및 기본 제어 흐름을 정의하여 모든 하드웨어 구현체가 반드시 준수해야 하는 필수 최소 명령어 세트(RV32I/RV64I).
- **표준 확장(Standard Extension)**: RISC-V International 표준 위원회의 승인을 통해 공식 Opcode 인코딩이 지정된 부동소수점(F/D), 벡터(V), 원자적 연산(A) 등의 모듈형 확장 세트.
- **사용자 정의 확장(Custom Extension)**: 표준 Opcode 공간과 충돌을 방지하도록 비워둔 예약 영역을 활용해 도메인 특화 연산을 구현하는 사용자 정의 명령어 확장.

</details>

- **기본 ISA** 대상 필요한 **표준 확장** 한정 골라 붙이므로 쓰지 않는 기능의 회로 면적과 누설 전력을 처음부터 제거
- **사용자 정의 확장** 표준이 비워 둔 인코딩 공간을 쓰기 때문에 이후 표준이 확장돼도 충돌하지 않음
- 구현 방식과 무관하게 **명세 기반 호환성** 유지해 컴파일러·OS·라이브러리 생태계를 공유

#### 한줄 요약
- 모듈형 조합의 이득은 기능을 더하는 자유가 아니라 빼는 자유이며, 임베디드에서 RISC-V가 먼저 자리 잡은 이유가 여기에 있다.

## Ⅲ. 구조 및 구성요소

<details><summary>용어 설명</summary>

- **권한 아키텍처(Privileged Architecture)**: User(U), Supervisor(S), Machine(M) 모드 등 실행 권한 계층과 시스템 예외·인터럽트 제어 메커니즘을 정의한 시스템 아키텍처 명세.
- **제어 및 상태 레지스터(Control and Status Register, CSR)**: 프로세서 동작 모드, 예외 처리 상태, 가상 메모리 설정, 성능 카운터를 제어하고 모니터링하는 시스템 전용 레지스터.
- **ISA 프로파일(ISA Profile)**: 특정 소프트웨어 플랫폼(Linux, Android 등) 실행에 필요한 기본 ISA 및 필수 표준 확장의 조합을 표준화한 호환성 규격(RVA, RVE 등).

</details>

```text
[RISC-V 명세]
├─ 기본 ISA (RV32I / RV64I)
│  └─ 정수 레지스터·기본 명령어
├─ 표준 확장 (M·A·F·D·V 등)
├─ 사용자 정의 확장
├─ 권한 아키텍처
│  └─ CSR
└─ ISA 프로파일
```

선의 의미: 가지(`├─`)는 명세 계층의 소유 관계이며, ISA 프로파일만이 위 항목들을 가로질러 조합을 고정

| 구성요소 | 책임 |
|:---|:---|
| **기본 ISA** | 공통 명령어·레지스터 동작 규정으로 최소 호환 기준 제공 |
| **표준 확장** | 합의된 인코딩으로 도구·바이너리 공유 기반 형성 |
| **사용자 정의 확장** | 도메인 특화 연산을 표준과 충돌 없이 추가 |
| **권한 아키텍처** | 예외·인터럽트·**CSR** 동작 고정으로 OS 이식성 보장 |
| **ISA 프로파일** | 확장 조합 고정으로 배포 대상 범위 확정 |

#### 한줄 요약
- 확장은 자유롭게 늘릴 수 있지만 프로파일이 그 자유를 다시 묶어 주며, 이 두 층이 없으면 개방형 ISA는 곧바로 파편화된다.

## Ⅳ. 흐름도

<details><summary>용어 설명</summary>

- **레지스터 전송 수준(Register-Transfer Level, RTL)**: 하드웨어 기술 언어(HDL)를 통해 플립플롭 간 신호 전달 및 조합 논리 동작을 표현하는 디지털 회로 설계 수준.
- **적합성 시험(Compliance Test)**: 하드웨어 구현체가 공식 ISA 표준 명세의 명령어 동작, 예외 처리 및 레지스터 상태 변화를 정확히 준수하는지 검증하는 테스트 스위트.
- **차등 시험(Differential Testing)**: 공식 골든 참조 모델(Spike 등)과 실제 RTL 구현체에 동일한 테스트 벡터를 주입하여 출력 상태의 불일치를 탐지하는 비교 검증 기법.

</details>

```text
요구 분석: OS·성능·전력 조건 확정
        │
   확장 범위를 어떻게 정하는가?
   ┌────┴────────────┐
표준 확장만 조합      사용자 정의 확장 포함
   │                    │
   │             예약 인코딩 회피 확인
   └────┬───────────────┘
        │
   RTL 구현: 명령어·권한 상태·예외 동작 반영
        │
   적합성·차등 시험 결과는?
   ┌────┴────┐
 불일치      일치
   │           │
RTL 수정 후   프로파일 선언 후
  재시험      생태계 연동
```

분기 결과: 표준 확장만 쓰면 검증 범위가 명세 시험으로 끝나지만, 사용자 정의 확장을 넣는 순간 인코딩 충돌 확인과 도구 체인 대응이 추가로 발생

#### 한줄 요약
- 개방형 ISA에서 어려운 일은 회로를 만드는 것이 아니라 내 구현이 명세와 같다는 것을 증명하는 일이며, 검증 비용이 확장 선택을 실제로 제한한다.

## Ⅴ. 종류 및 비교

| 확장 유형 | 표준 확장 | 사용자 정의 확장 |
|:---|:---|:---|
| 적용 기준 | 여러 구현·제품이 공통으로 쓸 기능 | 특정 제품에서만 필요한 특화 연산 |
| 핵심 특징 | 인코딩·도구·바이너리를 생태계와 공유 | 데이터 경로와 연산을 독립적으로 추가 |
| 한계 | 기능 추가·변경에 명세 위원회 합의 필요 | 이식성 상실과 **적합성 시험**·도구 지원 부담 |

#### 한줄 요약
- 두 확장의 갈림길은 기술이 아니라 유지 주체이며, 나 혼자 유지할 각오가 없다면 사용자 정의 확장은 부채로 남는다.

## Ⅵ. 실무 고려사항 및 대책

<details><summary>용어 설명</summary>

- **응용 프로그램 이진 인터페이스(Application Binary Interface, ABI)**: 컴파일된 기계어 프로그램 간 함수 호출 규약(Calling Convention), 레지스터 할당 규칙 및 데이터 메모리 정렬 방식을 정의한 저수준 인터페이스.
- **예약 인코딩(Reserved Encoding)**: 향후 표준 확장을 위해 사전에 할당을 유보해 둔 명령어 Opcode 비트 패턴 영역.
- **기능 탐지(Feature Discovery)**: 소프트웨어가 런타임에 CSR 또는 디바이스 트리를 조회하여 프로세서가 지원하는 ISA 확장 기능을 동적으로 판별하는 기법.

</details>

| 문제 | 대책 | 효과 |
|:---|:---|:---|
| 구현별 확장 차이로 같은 바이너리가 실행 실패 | **ISA 프로파일** 및 **ABI** 고정 후 **기능 탐지** 적용 | 배포 대상과 실행 조건 명확화 |
| 사용자 정의 명령이 향후 표준과 인코딩 충돌 | 지정된 사용자 정의 공간 사용·**예약 인코딩** 회피 | 표준 확장 도입 시 재설계 방지 |
| **권한 아키텍처** 구현이 명세와 미묘하게 불일치 | **적합성 시험** 및 **차등 시험** 자동화 | OS 이식 단계가 아닌 설계 단계에서 결함 발견 |
| 확장용 컴파일러 지원 범위가 버전마다 상이 | 도구 버전 고정과 빌드 회귀 시험 상시화 | 개발 환경 재현성 확보 |

#### 한줄 요약
- 확장을 고르는 비용보다 그 확장을 아는 도구와 OS를 계속 유지하는 비용이 크며, 개방형 ISA 도입 실패는 대부분 이 지점에서 발생한다.

## Ⅶ. 결론

- 자체 구현 권한이나 도메인 특화 명령이 필요하면 **RISC-V** 활용 선택하되, 범용 소프트웨어를 배포할 계획이면 **ISA 프로파일** 기반 확장 조합을 먼저 제한

#### 한줄 요약
- RISC-V는 명세가 열려 있다는 이유로 고르는 것이 아니라, 확장을 직접 정의하고 그 확장을 검증·유지할 체계를 갖췄을 때 고른다.
