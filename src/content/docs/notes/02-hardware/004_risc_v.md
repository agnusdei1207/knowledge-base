## Ⅰ. 개요

<details><summary>용어 설명</summary>

- **RISC-V**: 명세를 공개해 누구나 구현할 수 있게 하고, 최소 공통 규격 위에 필요한 기능만 확장으로 얹도록 설계된 명령어 집합 구조.
- **개방형 ISA(Open ISA)**: 명세 문서를 공개해 라이선스 협상 없이 여러 주체가 서로 호환되는 구현을 만들 수 있게 하는 ISA 운영 방식.
- **명세 기반 호환성(Specification-Based Compatibility)**: 내부 구현이 달라도 명세가 규정한 관찰 결과만 같으면 동일한 바이너리가 동작하도록 보장하는 성질.

</details>

- 정의/개념: 공개된 최소 공통 규격과 모듈형 확장을 조합해 제품마다 다른 명령어 구성을 만들 수 있는 **개방형 ISA**
- 배경/필요성: 독점 ISA는 라이선스가 구현 주체를 제한하고 맞춤형 명령어 추가를 막아, 도메인 특화 가속기를 만들 자율성이 없음

#### 한줄 요약
- 개방의 실익은 라이선스 비용 절감이 아니라 명령어를 직접 추가할 권한이며, 그 권한을 쓰는 순간 호환성 관리 책임도 같이 넘어온다.

## Ⅱ. 특징

<details><summary>용어 설명</summary>

- **기본 ISA(Base ISA)**: 정수 레지스터와 최소 명령어 동작만 규정해 어떤 구현이든 반드시 지켜야 하는 공통 규격(RV32I·RV64I 등).
- **표준 확장(Standard Extension)**: 곱셈(M)·원자 연산(A)·부동소수점(F/D)·벡터(V)처럼 명세 위원회 합의를 거쳐 인코딩까지 고정한 추가 기능.
- **사용자 정의 확장(Custom Extension)**: 표준이 쓰지 않기로 남겨 둔 인코딩 공간에 제품 특화 연산을 얹어, 표준 확장과 충돌하지 않게 하는 확장.

</details>

- **기본 ISA**에 필요한 **표준 확장**만 골라 붙이므로 쓰지 않는 기능의 회로 면적과 누설 전력을 처음부터 제거
- **사용자 정의 확장**은 표준이 비워 둔 인코딩 공간을 쓰기 때문에 이후 표준이 확장돼도 충돌하지 않음
- 구현 방식과 무관하게 **명세 기반 호환성**을 유지해 컴파일러·OS·라이브러리 생태계를 공유

#### 한줄 요약
- 모듈형 조합의 이득은 기능을 더하는 자유가 아니라 빼는 자유이며, 임베디드에서 RISC-V가 먼저 자리 잡은 이유가 여기에 있다.

## Ⅲ. 구조 및 구성요소

<details><summary>용어 설명</summary>

- **권한 아키텍처(Privileged Architecture)**: 예외·인터럽트·보호 모드의 동작을 규정해 운영체제가 구현마다 다시 이식되지 않도록 고정한 규격.
- **제어 및 상태 레지스터(Control and Status Register, CSR)**: 권한 상태·예외 원인·타이머 같은 시스템 값을 담아 권한 아키텍처의 동작을 소프트웨어에 노출하는 레지스터.
- **ISA 프로파일(ISA Profile)**: 특정 운영체제나 생태계가 전제해도 되는 확장 조합을 한 묶음으로 고정해, 배포자가 검사할 대상을 줄여 주는 호환 기준.

</details>

```text
[RISC-V 명세]
├─ 기본 ISA (RV32I / RV64I)
│  └─ 정수 레지스터·기본 명령어
├─ 표준 확장 (M·A·F·D·V 등)
├─ 사용자 정의 확장
├─ 권한 아키텍처
│  └─ CSR
└─ ISA 프로파일
```

선의 의미: 가지(`├─`)는 명세 계층의 소유 관계이며, ISA 프로파일만이 위 항목들을 가로질러 조합을 고정

| 구성요소 | 책임 |
|:---|:---|
| **기본 ISA** | 공통 명령어·레지스터 동작 규정으로 최소 호환 기준 제공 |
| **표준 확장** | 합의된 인코딩으로 도구·바이너리 공유 기반 형성 |
| **사용자 정의 확장** | 도메인 특화 연산을 표준과 충돌 없이 추가 |
| **권한 아키텍처** | 예외·인터럽트·**CSR** 동작 고정으로 OS 이식성 보장 |
| **ISA 프로파일** | 확장 조합 고정으로 배포 대상 범위 확정 |

#### 한줄 요약
- 확장은 자유롭게 늘릴 수 있지만 프로파일이 그 자유를 다시 묶어 주며, 이 두 층이 없으면 개방형 ISA는 곧바로 파편화된다.

## Ⅳ. 흐름도

<details><summary>용어 설명</summary>

- **레지스터 전송 수준(Register-Transfer Level, RTL)**: 레지스터 간 데이터 이동과 조합 논리로 회로를 기술하는 설계 추상 수준으로, 명세를 실제 게이트로 옮기기 직전 단계.
- **적합성 시험(Compliance Test)**: 구현이 명세가 규정한 명령어 동작과 예외 처리를 빠짐없이 지키는지 확인하는 시험.
- **차등 시험(Differential Testing)**: 참조 구현과 대상 구현에 같은 입력을 넣고 결과가 갈리는 지점을 찾아, 명세 해석 차이를 드러내는 검증 기법.

</details>

```text
요구 분석: OS·성능·전력 조건 확정
        │
   확장 범위를 어떻게 정하는가?
   ┌────┴────────────┐
표준 확장만 조합      사용자 정의 확장 포함
   │                    │
   │             예약 인코딩 회피 확인
   └────┬───────────────┘
        │
   RTL 구현: 명령어·권한 상태·예외 동작 반영
        │
   적합성·차등 시험 결과는?
   ┌────┴────┐
 불일치      일치
   │           │
RTL 수정 후   프로파일 선언 후
  재시험      생태계 연동
```

분기 결과: 표준 확장만 쓰면 검증 범위가 명세 시험으로 끝나지만, 사용자 정의 확장을 넣는 순간 인코딩 충돌 확인과 도구 체인 대응이 추가로 발생

#### 한줄 요약
- 개방형 ISA에서 어려운 일은 회로를 만드는 것이 아니라 내 구현이 명세와 같다는 것을 증명하는 일이며, 검증 비용이 확장 선택을 실제로 제한한다.

## Ⅴ. 종류 및 비교

| 확장 유형 | 표준 확장 | 사용자 정의 확장 |
|:---|:---|:---|
| 적용 기준 | 여러 구현·제품이 공통으로 쓸 기능 | 특정 제품에서만 필요한 특화 연산 |
| 핵심 특징 | 인코딩·도구·바이너리를 생태계와 공유 | 데이터 경로와 연산을 독립적으로 추가 |
| 한계 | 기능 추가·변경에 명세 위원회 합의 필요 | 이식성 상실과 **적합성 시험**·도구 지원 부담 |

#### 한줄 요약
- 두 확장의 갈림길은 기술이 아니라 유지 주체이며, 나 혼자 유지할 각오가 없다면 사용자 정의 확장은 부채로 남는다.

## Ⅵ. 실무 고려사항 및 대책

<details><summary>용어 설명</summary>

- **응용 프로그램 이진 인터페이스(Application Binary Interface, ABI)**: 컴파일된 코드가 인자 전달·레지스터 용도·데이터 정렬을 어떻게 처리할지 정한 규약으로, 어긋나면 컴파일은 되어도 실행이 깨짐.
- **예약 인코딩(Reserved Encoding)**: 향후 표준화를 위해 비워 둔 명령어 비트 패턴으로, 여기에 사용자 정의 명령을 넣으면 나중에 표준 확장과 충돌.
- **기능 탐지(Feature Discovery)**: 실행 시점에 지원 확장을 조회해 코드 경로를 고르는 방식으로, 하나의 바이너리가 여러 구현에서 동작하게 하는 수단.

</details>

| 문제 | 대책 | 효과 |
|:---|:---|:---|
| 구현별 확장 차이로 같은 바이너리가 실행 실패 | **ISA 프로파일**과 **ABI** 고정 후 **기능 탐지** 적용 | 배포 대상과 실행 조건 명확화 |
| 사용자 정의 명령이 향후 표준과 인코딩 충돌 | 지정된 사용자 정의 공간 사용·**예약 인코딩** 회피 | 표준 확장 도입 시 재설계 방지 |
| **권한 아키텍처** 구현이 명세와 미묘하게 불일치 | **적합성 시험**과 **차등 시험** 자동화 | OS 이식 단계가 아닌 설계 단계에서 결함 발견 |
| 확장용 컴파일러 지원 범위가 버전마다 상이 | 도구 버전 고정과 빌드 회귀 시험 상시화 | 개발 환경 재현성 확보 |

#### 한줄 요약
- 확장을 고르는 비용보다 그 확장을 아는 도구와 OS를 계속 유지하는 비용이 크며, 개방형 ISA 도입 실패는 대부분 이 지점에서 발생한다.

## Ⅶ. 결론

- 자체 구현 권한이나 도메인 특화 명령이 필요하면 **RISC-V**를 선택하되, 범용 소프트웨어를 배포할 계획이면 **ISA 프로파일**로 확장 조합을 먼저 제한

#### 한줄 요약
- RISC-V는 명세가 열려 있다는 이유로 고르는 것이 아니라, 확장을 직접 정의하고 그 확장을 검증·유지할 체계를 갖췄을 때 고른다.
