## Ⅰ. 개요

**데이터플로 실행(dataflow execution)** 은 연산에 필요한 입력이 준비되었을 때 그 연산을 실행 가능 상태로 만드는 계산 모델이다. 전통적인 제어 흐름 프로그램은 프로그램 카운터와 분기·호출에 따라 명령 순서를 정하지만, 데이터플로 그래프는 연산 노드와 데이터 의존성을 중심으로 준비된 작업을 찾는다.

데이터플로 컴퓨터는 이 모델을 하드웨어 수준에서 직접 구현하려는 아키텍처를 뜻할 수 있고, 현대에는 컴파일러의 의존성 그래프, 작업 런타임, GPU·AI 가속기·CGRA의 스케줄링에도 데이터플로 개념이 사용된다. 이런 시스템이 프로그램 카운터나 제어 흐름을 완전히 제거하는 것은 아니며, 분기·상태·메모리·예외 처리는 별도 제어가 필요하다.

#### 한줄 요약

- 데이터플로는 입력 의존성이 충족된 연산을 실행하는 모델이며, 실제 시스템은 제어 흐름과 메모리 제어를 함께 사용한다.

## Ⅱ. 특징

- **발화 규칙(firing rule)**: 노드의 필요한 입력과 제어 조건이 충족되면 실행 후보가 된다.
- **토큰(token)**: 값, 목적지, 포트, 반복·문맥 식별자 같은 정보를 가진 전달 단위로 모델링할 수 있다.
- **암묵적 병렬성**: 서로 의존하지 않는 노드는 동시에 준비될 수 있지만, 실제 병렬도는 실행 자원·메모리·통신에 제한된다.
- **태그(tag)**: 루프·재귀·여러 실행 인스턴스에서 같은 노드의 서로 다른 입력을 섞지 않도록 식별 정보를 제공할 수 있다.

데이터 의존 그래프는 루프를 펼치지 않으면 항상 DAG가 아니다. 순환 의존, 상태 갱신, I/O 순서, 예외는 토큰·반복 제어·스케줄러가 별도로 다뤄야 한다.

#### 한줄 요약

- 준비된 독립 노드는 병렬화할 수 있지만, 태그·상태·메모리·자원 관리가 실제 데이터플로 실행의 핵심 비용이다.

## Ⅲ. 구조 및 구성요소

```text
프로그램·그래프 표현
        │
토큰 생성·라우팅 ──> 매칭/대기 저장소 ──> 준비 작업 큐
                                      │
                           처리 요소(PE)·메모리 접근
                                      │
                        결과 토큰·분기·반복 제어
                                      └──> 후속 노드
```

| 구성요소 | 역할 |
|:---|:---|
| 그래프·명령 표현 | 연산, 입력 포트, 의존성, 라우팅·제어 정보를 표현한다. |
| 토큰 저장소 | 아직 짝이 맞지 않은 입력과 문맥을 보관한다. |
| 매칭 유닛 | 목적지·포트·태그가 맞는 입력을 찾아 실행 가능한 작업을 만든다. |
| 준비 작업 큐 | 준비된 작업을 처리 요소와 메모리 자원에 배정한다. |
| 처리 요소 | 산술·논리·특수 연산을 수행하고 결과 토큰을 만든다. |
| 메모리·통신 경로 | 주소 의존성, 일관성, 대역폭, 지연을 관리한다. |

매칭 저장소의 연관 검색, 토큰 라우팅, 태그 저장 공간은 데이터플로 시스템의 성능·전력·확장성에 큰 영향을 준다.

#### 한줄 요약

- 데이터플로 하드웨어의 중심은 연산기 자체보다 입력 토큰을 저장·매칭·라우팅하는 구조다.

## Ⅳ. 동작 흐름

```text
입력 또는 선행 노드 결과가 토큰으로 도착
        ↓
목적지·포트·태그 기준으로 대기 입력과 매칭
        ↓
필요 조건을 만족하면 준비 작업 생성
        ↓
스케줄러가 처리 요소·메모리 자원에 배정
        ↓
연산 결과와 제어 결과를 후속 토큰으로 라우팅
        ↓
큐 포화 시 흐름 제어·백프레셔로 입력 조절
```

모든 입력이 있어도 실행 자원이 없거나 메모리 의존성이 해결되지 않으면 즉시 실행되지 않는다. 반대로 작업이 독립적이어도 토큰 전달·매칭 비용이 연산보다 크면 세밀한 데이터플로 방식은 비효율적일 수 있다.

#### 한줄 요약

- 노드 발화는 입력 준비의 시작점이며, 실제 실행 시점은 큐·처리 요소·메모리·통신 상태까지 고려해 정한다.

## Ⅴ. 비교

| 비교 항목 | 데이터플로 모델 | 제어 흐름 모델 |
|:---|:---|:---|
| 주된 실행 기준 | 데이터·의존성의 준비 상태 | 명령 순서, 분기, 호출, 스케줄링 |
| 병렬성 표현 | 그래프의 독립 노드가 자연스럽게 드러남 | 스레드·벡터화·OoO·태스크 등으로 추출 |
| 상태·분기 처리 | 토큰·태그·제어 노드로 명시적 관리 필요 | PC·스택·분기 예측·예외 처리와 결합 |
| 주요 비용 | 매칭, 태그, 토큰 저장·통신 | 명령 인출·제어 의존·동기화 |
| 적합한 경우 | 규칙적인 그래프·스트림·데이터 병렬 작업 | 복잡한 분기·불규칙 상태·범용 프로그램 |

현대 CPU의 out-of-order 실행도 데이터 의존성을 이용해 준비된 명령을 실행하지만, 전통적인 데이터플로 머신과 동일한 모델은 아니다. GPU, TPU, CGRA도 각자 다른 스케줄·메모리·프로그램 모델을 사용한다.

#### 한줄 요약

- 데이터플로와 제어 흐름은 대립만 하는 방식이 아니라, 현대 프로세서에서 서로 다른 수준으로 결합될 수 있다.

## Ⅵ. 실무 고려사항 및 대책

| Problem | Countermeasure | Effect |
|:---|:---|:---|
| 세밀한 토큰 처리 비용이 실제 연산보다 큼 | 블록·타일·텐서처럼 적절한 입도로 묶고 컴파일러·런타임 오버헤드를 계측 | 매칭·라우팅 비용 대비 계산량 개선 |
| 루프·재귀·분기에서 태그와 토큰이 증가 | 문맥 수 제한, 반복 제어 설계, 토큰 수명·누수 검사 적용 | 저장소 포화와 잘못된 매칭 위험 완화 |
| 생산자가 소비자보다 빨라 큐가 포화 | 크레딧·백프레셔·큐 크기·드롭/재시도 정책을 설계 | 메모리 고갈과 지연 전파 관리 |
| 메모리 접근이 불규칙하고 공유 충돌이 큼 | 데이터 지역성 배치, 타일링, 주소 의존성·일관성 정책, NoC 관찰 적용 | 통신 병목과 순서 오류 감소 |

#### 한줄 요약

- 데이터플로 성능은 그래프 병렬도보다 토큰 입도, 저장소 압력, 메모리·통신 지역성을 먼저 검증해야 한다.

## Ⅶ. 결론

데이터 의존성이 명확하고 같은 연산 패턴이 반복되는 스트림·그래프·텐서 작업에서는 데이터플로식 스케줄링이 병렬성을 드러내는 데 유용하다. 분기·상태·불규칙 메모리 접근이 큰 범용 작업에서는 전통 제어 흐름과 하이브리드로 구성하는 편이 실용적일 수 있다. 도입 판단은 “자동 병렬화”라는 기대보다 토큰 매칭·통신 비용과 실제 워크로드의 준비 작업 분포를 측정해 내린다.

#### 한줄 요약

- 데이터플로 아키텍처는 준비 연산이 많은 작업에 적합하지만, 토큰·상태·통신 비용을 포함한 실측으로 선택해야 한다.
