## Ⅰ. 개요

<details><summary>용어 설명</summary>

- **퍼시스턴트 메모리(Persistent Memory, PMEM)**: 램(DRAM)처럼 빛의 속도로 접근하면서도, 전원 플러그를 뽑아도 데이터가 하드디스크처럼 살아남는 무시무시한 돌연변이 메모리이다.
- **바이트 주소 지정(Byte-Addressability)**: 하드디스크처럼 덩어리(블록) 단위로 퍼오는 멍청한 짓 안 하고, CPU가 핀셋으로 집듯이 1바이트씩 다이렉트로 찔러 넣는 극강의 속도이다.
- **재시작 지연(Restart Latency)**: 정전으로 서버가 꺼졌을 때, 느려 터진 하드에서 램으로 데이터를 다시 퍼올리느라 서비스 복구에 수십 분씩 걸리는 빡치는 대기 시간이다.

</details>

- 정의: 바이트 주소 **직접 접근**과 전원 차단 시 **비휘발성**을 결합한 하이브리드 영속 메모리(**PMEM**) 아키텍처
- 배경: 램에 올려둔 데이터가 정전 한 번에 싹 날아가고, 하드(블록 I/O)에서 다시 퍼올리느라 서버 켜지는 데 한 세월 걸리는 **재시작 지연**을 멱살 잡고 단축하기 위함

#### 한줄 요약

- 램의 속도와 하드디스크의 비휘발성을 합쳐서, 전기가 나가도 데이터가 안 날아가고 켜자마자 바로 복구되는 사기 템이다.

## Ⅱ. 특징

<details><summary>용어 설명</summary>

- **다이렉트 억세스(Direct Access, DAX)**: 느려 터진 운영체제 파일시스템과 캐시 껍데기를 통째로 무시하고, CPU가 메모리에 다이렉트로 직빵을 꽂아버리는 초저지연 기술이다.
- **캐시 라인 플러시(clflush/clwb)**: CPU가 지만 보려고 꿍쳐둔 캐시 메모리를 멱살 잡고 털어서, 억지로 비휘발성 영속 메모리로 뱉어내게 만드는 강제 덤프 명령어이다.
- **에스펜스(Store Fence, sfence)**: CPU한테 "야! 아까 뱉으라고 한 거 다 뱉을 때까지 멈춰!" 하고 순서를 엄격하게 통제하는 경찰관 같은 명령어이다.
- **장애 정합성(Crash Consistency)**: 전기가 갑자기 팍 나가도 쓰다 만 데이터가 꼬이지 않고, 다시 켰을 때 멀쩡하게 복구되는 완벽한 안전장치이다.

</details>

- 운영체제의 쓸데없는 캐시나 블록 I/O 껍데기를 통째로 패스하고 데이터에 다이렉트로 꽂히는 초저지연 **다이렉트 억세스(DAX)** 구동 방식을 씀.
- CPU가 멍청하게 캐시에만 데이터를 들고 있다가 날려 먹지 않게, **clwb**와 **sfence** 명령어로 멱살을 잡아 메모리에 강제로 쑤셔 넣음.
- 전기가 나가도 데이터가 안 깨지고(**장애 정합성**), 부팅하자마자 메모리에 데이터가 그대로 살아있어 **재시작 지연**이 0에 수렴함.

#### 한줄 요약

- OS 캐시를 무시하고 직통으로 꽂으며(DAX), 강제로 뱉어내게(clwb) 해서 정전이 나도 데이터가 무결하게 살아남는다.

## Ⅲ. 구조 및 구성요소

<details><summary>용어 설명</summary>

- **비동기 디램 리프레시(Asynchronous DRAM Refresh, ADR)**: 정전 터지는 최후의 순간, 캐퍼시터(배터리) 남은 전력을 쥐어짜서 캐시에 있는 데이터를 메모리로 피난시키는 미친 생존 회로이다.
- **피엠디케이(Persistent Memory Development Kit, PMDK)**: "전기 나가도 안 깨지게 코딩하는 법"을 싹 다 모아놓은 인텔의 치명적인 오픈소스 라이브러리 세트이다.

</details>

```text
[ 묻지마 정전 대비 불멸의 영속 데이터 십자포화 프레임워크 ]
[ 영속 자료구조 (PMDK 뼈대) ] ── [ 다이렉트 억세스(DAX) 매핑 (직통 고속도로) ]
                                          │
                                          ▼
[ 캐시•영속 제어 (clwb 강제 이송단) ] ── [ 영속성 영역 (PMEM + ADR 피난처) ]
```

| 구성요소 | 책임 |
|:---|:---|
| 영속 자료구조 | 데이터가 중간에 박살 나지 않게 **피엠디케이(PMDK)** 라이브러리로 뼈대를 세운 불멸의 자료구조 |
| **다이렉트 억세스(DAX)** 매핑 | 커널의 구질구질한 파일시스템(블록 변환)을 무시하고 사용자 프로그램과 메모리를 직통으로 연결하는 고속도로 |
| 캐시•영속 제어 | CPU한테 "**clwb** 뱉어! **sfence** 멈춰!" 하고 호통쳐서 캐시 찌꺼기를 영속 메모리로 강제 이송시키는 지휘관 |
| 영속성 영역 | 전기가 나가는 최후의 순간에도 남은 전력을 쥐어짜서 데이터를 피난시키는 **ADR** 회로와 **퍼시스턴트 메모리** 본체 |

#### 한줄 요약

- PMDK로 뼈대를 짜고, DAX로 고속도로를 뚫은 뒤, clwb로 캐시를 털어 ADR 피난처에 박아 넣는다.

## Ⅳ. 흐름도

<details><summary>용어 설명</summary>

- **순서 보존 쓰기(Ordered Persistence)**: 일기장 적고 ➞ 본편 적고 ➞ 도장 찍는 순서를 무조건 지켜서, 중간에 불 꺼져도 데이터가 오염되지 않게 하는 철칙이다.

</details>

```text
[ 묻지마 정전 대비 불멸의 데이터 기록 십자포화 흐름 ]
                                 │
                                 ▼
          [ 1. 일기장 쓰기: "뭐 바꿀 거임" 하고 복구용 일기장(WAL) 씀 ]
                                 │
                                 ▼
   [ 2. 멱살 잡고 강제 덤프: clwb랑 sfence로 일기장 내용을 영속 메모리에 쑤셔 박음 ]
                                 │
                                 ▼
      [ 3. 진짜 데이터 쓰기: 찐 데이터 기록하고 또 clwb 갈겨서 뱉어내게 만듦 ]
                                 │
                                 ▼
       [ 4. 도장 쾅쾅: "끝!" 도장 찍고 sfence로 굳혀버림 (순서 보존 쓰기) ]
                                 │
                 ┌───────────────┴───────────────┐
             ( 꿀잠 완료 )                   ( 정전으로 사망 )
                 ▼                               ▼
          [ 5. 작업 종료 반환 ]       [ 도장 유무 보고 살릴지 버릴지 얄짤없이 판정 ]
```

### 동작 원리

1. 복구 로그 기록: "나 지금부터 뭐 쓴다" 하고 복구용 일기장(WAL)에 먼저 비휘발 작성을 해둠.
2. 로그 플러시·펜스: **clwb**와 **sfence**로 CPU 멱살을 잡아 일기장 내용을 플랫폼 영속 영역에 강제로 쑤셔 박음.
3. 본 데이터 기록·플러시: 찐 데이터를 메모리에 쓰고 다시 한번 **clwb**를 갈겨서 뱉어내게 만듦.
4. 커밋 표식 영속: 다 썼으면 "끝!" 하고 커밋 도장(Flag)을 찍고 **sfence**로 완료를 확정하는 **순서 보존 쓰기** 시전함.
5. 복구 상태 판정: 전기가 나갔다 들어오면 커밋 도장 유무를 보고 쓸지 버릴지 얄짤없이 결정해 복구함.

#### 한줄 요약

- 로그부터 쓰고, 멱살 잡고 뱉어내게(clwb/sfence) 한 뒤, 도장까지 찍어야 전기가 나가도 살아남는다.

## Ⅴ. 종류 및 비교

<details><summary>용어 설명</summary>

- **엔브이디아이엠엠(Non-Volatile DIMM, NVDIMM)**: 일반 램 스틱에 플래시 메모리랑 쪼만한 배터리를 붙여서, 정전 나면 배터리 힘으로 램 데이터를 플래시에 구워버리는 혼종 램이다.

</details>

| 비교 항목 | **퍼시스턴트 메모리** (PMEM) | **디램** (DRAM) | **엔브이엠이 에스에스디** (NVMe SSD) |
|:---|:---|:---|:---|
| 시스템 적용 최적 기준 | DB 켜지자마자 1초 만에 서비스 시작해야 하거나 전원 나가도 절대 날아가면 안 되는 인메모리 핵심 캐시 돌릴 시 | 그냥 전원 끄면 싹 다 날아가도 상관없는 일회성 작업이나 존나게 빠른 연산 버퍼로 쓸 시 | 용량이 깡패라서 덩치 큰 파일이나 아카이브 데이터를 싼값에 차곡차곡 쌓아둘 시 |
| 아키텍처 핵심 구현 특징 | 램처럼 CPU가 바이트(Byte) 단위로 바늘 꽂듯 접근하는데, 전기 끊어져도 데이터가 화석처럼 굳어서 살아있음 (**DAX** 지원) | 빛의 속도로 빠르지만, 전원 플러그 뽑는 순간 뇌가 포맷되는 극강의 휘발성(Volatile) 메모리 | 램(Byte)이랑 달리 덩어리(Block) 단위로 쑤셔 넣어야 해서 I/O 오버헤드가 덕지덕지 붙어있는 비휘발성 저장소 |
| 극복해야 할 태생적 한계점 | 램보다 미세하게 느리고, 코딩할 때 CPU 캐시에 낀 데이터 강제로 빼내는(플러시) 똥꼬쇼가 필수임 | 전기 나가면 다 날아가니까, 서비스 살리려면 느려 터진 SSD에서 다시 퍼올려야 하는 지옥의 재시작 지연 | 플래시 메모리 특성상 쓸 때마다 수명이 갉아 먹히고 램이랑은 비교도 안 되게 느려 터짐 |

#### 한줄 요약

- 램의 바이트 접근 속도와 SSD의 비휘발성 생존력을 합친 것이 바로 퍼시스턴트 메모리이다.

## Ⅵ. 실무 고려사항 및 대책

<details><summary>용어 설명</summary>

- **파워 페일루어 인젝션(Power-Failure Injection)**: "진짜 안 날아가나 보자" 하고, 프로그램 도는 와중에 일부러 전원선을 무식하게 뽑아버리며 맷집(정합성)을 테스트하는 기법이다.

</details>

| 문제 | 대책 | 효과 |
|:---|:---|:---|
| CPU 캐시에만 데이터 적어놓고 영속 메모리로 안 보냈는데 갑자기 정전돼서 데이터가 공중분해 되는 대참사 | **clwb**랑 **sfence** 명령어를 순서대로 때려 박고 **ADR** 회로 떡칠해서 전원 꺼지기 직전까지 캐시 멱살 잡고 덤프함 | 영속 완료됐다고 구라 치는 걸 막아내고 전원 사고 시 데이터 유실 없는 무결성 절대 사수 |
| 메모리에 하드코딩된 절대 주소를 적어놨는데 재부팅했더니 OS가 주소(ASLR)를 섞어버려 포인터가 쓰레기 값이 됨 | 시작점에서 얼마나 떨어졌는지(Offset)만 기록하는 상대 포인터 매핑으로 뼈 깎는 코드 리팩토링 강행 | 시스템 껐다 켜서 메모리 방 번호가 다 바뀌어도 포인터가 완벽하게 복원되어 데이터 부활 |
| 비휘발 메모리 쓴답시고 코딩 대충 했더니 전원 나갔다 오면 DB 순서가 다 꼬여서 정합성이 와해되는 지옥문 개방 | 검증된 **PMDK** 라이브러리 떡칠하고 전원선 강제로 뽑아보는 **파워 페일루어 인젝션**으로 극한 테스팅 | 미친 듯이 껐다 켜도 데이터 순서가 절대 꼬이지 않는 불멸의 **장애 정합성** 완성 |

#### 한줄 요약

- clwb로 멱살 잡고 덤프하고, 상대 포인터로 주소 꼬임을 막으며, 전원 뽑기 테스트로 맷집을 검증해라.

## Ⅶ. 결론

<details><summary>용어 설명</summary>

- **퍼시스턴트 메모리 선택 기준(PMEM Adoption Criteria)**: 데이터가 빛의 속도로 필요하면서 동시에 절대 날아가면 안 되는 인메모리 DB 같은 귀족급 아키텍처에 돈지랄을 할지 결정하는 잣대이다.

</details>

- **퍼시스턴트 메모리 선택 기준** 원칙에 따라, 바이트 단위 영속 상태 보존은 **PMEM**, 휘발성 초고속 작업은 **DRAM**, 대용량 깡패 보관은 **NVMe SSD** 채택 기조 확립함

#### 한줄 요약

- 돈 많고 재부팅 지연 빡치면 PMEM, 싼 맛에 쓰다 날려도 되면 DRAM, 용량이 중요하면 SSD를 써라.
