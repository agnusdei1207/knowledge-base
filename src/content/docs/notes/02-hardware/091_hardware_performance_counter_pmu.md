## Ⅰ. 개요

<details><summary>용어 설명</summary>

- **성능 모니터링 유닛(Performance Monitoring Unit, PMU)**: CPU 안에서 명령어들이 꼬이는지, 캐시를 헛스윙했는지 미세한 하드웨어 사건들을 몰래 훔쳐보는 감시 카메라 칩이다.
- **하드웨어 성능 카운터(Hardware Performance Counter, HPC)**: PMU 안에서 특정 사건이 터질 때마다 "하나, 둘, 셋" 하고 무자비하게 횟수를 기록하는 전용 카운터 레지스터이다.
- **클록 당 명령어 처리 수(Instructions Per Cycle, IPC)**: CPU가 한 클록 뛸 때마다 몇 개의 명령어를 끝장냈는지 보여주는, 아키텍처 전투력 측정의 절대 지표이다.

</details>

- 정의: CPU 파이프라인에서 명령어가 씹히는지, 캐시를 헛스윙했는지(Miss), 분기 예측이 빗나갔는지 등의 미세한 하드웨어 사건을 소프트웨어 개입 없이 칼같이 세어주는 **PMU & 하드웨어 성능 카운터**
- 배경: 프로그램이 느려 터졌을 때 단순히 "10초 걸렸다"는 시계 시간만으로는, CPU가 놀고 있는지 메모리가 막혔는지 진짜 원인(병목)을 절대 알 수 없기 때문

#### 한줄 요약

- 시계만 보고는 왜 느린지 모르니, CPU 칩 안에 감시 카메라(PMU)를 달아 캐시 헛스윙 같은 걸 직접 세는 기술이다.

## Ⅱ. 특징

<details><summary>용어 설명</summary>

- **정밀 이벤트 기반 샘플링(Precise Event-Based Sampling, PEBS/SPE)**: 에러가 터졌을 때 대충 넘어가지 않고, 정확히 어느 코드 줄에서 사고가 났는지 멱살 잡고 잡아내는 정밀 저격 샘플링이다.
- **다중화(Multiplexing)**: 카운터 개수는 4개뿐인데 잴 건 10개라서, 시간을 쪼개서 번갈아 가며 재고 나중에 곱하기해서 뻥튀기하는 측정 꼼수이다.

</details>

![PMU 다중화 실행 비율에 따른 보정 배율 차트](/study/diagrams/pmu-multiplex-scale.svg)

- 프로그램 실행을 방해하지 않고(낮은 간섭), 칩셋 안에 박힌 하드웨어가 다이렉트로 사건을 훔쳐보는 **하드웨어 수집** 기법임.
- **클록 당 명령어 처리 수(IPC)**나 캐시 미스율 같은 살벌한 지표를 뽑아내서 코드의 병목을 뼛속까지 진단함.
- 정확히 어느 코드 줄에서 사고가 터졌는지 찝어내는 **정밀 샘플링(PEBS/SPE)**과, 적은 카운터 칩으로 여러 이벤트를 쪼개서 재는 **다중화** 꼼수를 시전함.

#### 한줄 요약

- 간섭 없이 하드웨어로 직접 사건을 세서, IPC와 미스율을 뽑아내고 꼼수(다중화)로 카운터 부족을 때운다.

## Ⅲ. 구조 및 구성요소

<details><summary>용어 설명</summary>

- **이벤트 선택기(Event Selector MSR)**: 수백 개의 하드웨어 사건 중에서 "이번엔 캐시 미스만 잡아내!" 하고 타깃을 콕 집어주는 저격수 레지스터이다.
- **성능 카운터 레지스터(Performance Counter MSR)**: 저격수가 잡아낸 사건이 터질 때마다 1씩 숫자를 미친 듯이 올리는 무식한 셈틀이다.

</details>

```text
[ PMU 하드웨어 십자포화 계측 프레임워크 ]
[ 이벤트 원천 (연산기, 캐시) ] ── [ 이벤트 선택기 (타깃 필터) ]
                                          │
                                          ▼
 [ 수집•분석 도구 (Perf/VTune) ] ── [ 성능 카운터 (사건 횟수 누적) ]
```

| 구성요소 | 책임 |
|:---|:---|
| 이벤트 원천 | 연산기(ALU), 캐시 등 CPU 내부 장치들이 뿜어내는 "나 캐시 헛스윙했어!" 같은 날것의 하드웨어 사건들 |
| **이벤트 선택기 (MSR)** | "지금부터 캐시 미스랑 분기 실패만 잡아내!" 하고 계측할 타깃을 콕 집어서 필터링하는 저격수 레지스터 |
| **성능 카운터 (PMC)** | 저격수가 잡아낸 사건이 터질 때마다 1씩 숫자를 미친 듯이 올리고, 꽉 차면 삐용삐용(인터럽트) 울리는 카운터 |
| 수집•분석 도구 | 리눅스(Perf)나 인텔(VTune) 도구를 써서, 카운터에 쌓인 숫자를 빼와서 예쁜 그래프로 까발리는 소프트웨어 |

#### 한줄 요약

- 타깃을 고르고(선택기), 숫자를 세서(성능 카운터), 분석 툴로 넘기는 하드웨어 감시 구조이다.

## Ⅳ. 흐름도

<details><summary>용어 설명</summary>

- **성능 모니터 인터럽트(Performance Monitor Interrupt, PMI)**: 카운터 숫자가 꽉 차서 터지면, OS한테 "비상! 빨리 샘플링 버퍼 비워라!" 하고 소리 지르는 하드웨어 비상벨이다.

</details>

```text
[ 하드웨어 병목 프로파일링 십자포화 분석 흐름 ]
                                 │
                                 ▼
   [ 1. 사냥감 세팅: "캐시 미스 잡자" 하고 이벤트 선택기 빡세게 세팅 ]
                                 │
                                 ▼
       [ 2. 작업 뺑뺑이: 똑같은 프로그램 계속 돌리며 카운터 팽팽 돌림 ]
                                 │
                                 ▼
[ 3. 멱살 수집: 숫자 터지면 비상벨(PMI) 울려서 범인(코드 라인) 샘플링으로 털어냄 ]
                                 │
                                 ▼
     [ 4. 지표 뻥튀기(보정): 다중화로 쪼개서 잰 거 100% 기준으로 환산함 ]
                                 │
                                 ▼
    [ 5. 범인 색출: 핫스팟 코드랑 지표 엮어서 "메모리가 막혔네!" 하고 확정함 ]
```

### 동작 원리

1. 사냥감 세팅: 캐시 미스 잡을지, IPC 잡을지 정하고 **이벤트 선택기**를 빡세게 세팅함.
2. 작업 뺑뺑이: 똑같은 프로그램을 미친 듯이 반복 실행하면서 CPU 내부 하드웨어 카운터를 팽팽 돌림.
3. 멱살 수집: 카운터 숫자가 터질 때마다 **성능 모니터 인터럽트(PMI)**를 쏴서 범인(코드 줄 번호)을 샘플링 덤프로 털어냄.
4. 지표 뻥튀기(보정): 쪼개서 측정한 시간(**다중화**)을 100% 기준으로 보정하고 IPC나 미스율 수치를 뽑아냄.
5. 범인 색출: 병목 터진 코드 라인(Hotspot)이랑 하드웨어 카운터 수치를 엮어서 "니가 범인이다" 하고 십자포화 검증함.

#### 한줄 요약

- 타깃을 세팅하고 미친 듯이 돌리면서, 숫자가 터질 때마다 범인 코드를 잡아내 보정 후 십자포화 분석한다.

## Ⅴ. 종류 및 비교

<details><summary>용어 설명</summary>

- **소프트웨어 프로파일링(Software Profiling)**: 코드 중간중간에 "여기서 타이머 켜라" 하고 억지로 측정 코드를 쑤셔 박아서 함수 시간을 재는 클래식한 방식이다.

</details>

| 비교 항목 | **PMU 하드웨어 계측** | **소프트웨어 프로파일링** |
|:---|:---|:---|
| 시스템 적용 최적 기준 | CPU 클록, 캐시 헛스윙, 파이프라인 붕괴 같은 하드웨어 뼛속의 찐 병목을 탈탈 털어낼 시 | 함수 호출이 얼마나 걸렸는지, 메모리를 얼마나 잡아먹었는지 프로그램 표면적인 흐름을 볼 시 |
| 아키텍처 핵심 구현 특징 | CPU 안에 박힌 전용 하드웨어 레지스터(**PMC**)가 몰래카메라처럼 조용하고 정확하게 사건을 셈 | 개발자가 소스 코드 군데군데 "여기 시간 재라" 하고 측정 코드(Instrumentation)를 억지로 쑤셔 박음 |
| 극복해야 할 태생적 한계점 | 인텔 꺼 다르고 AMD 꺼 달라서, CPU 칩셋 매뉴얼 안 보면 카운터 숫자가 뭔 소린지 해독 불가능함 | 코드를 쑤셔 박아서 재는 거라 프로그램 본래 속도가 느려지고 측정 자체가 오염될 위험 폭발 |

#### 한줄 요약

- 하드웨어 뼛속을 몰래 훔쳐보는 게 PMU고, 코드에 억지로 타이머를 박아 넣는 게 소프트웨어 프로파일링이다.

## Ⅵ. 실무 고려사항 및 대책

<details><summary>용어 설명</summary>

- **시피유 피닝(CPU Pinning)**: 분석할 스레드가 1번 CPU에서 2번 CPU로 도망 못 가게 멱살 잡고 묶어버려서 카운터 오염을 막는 통제술이다.

</details>

| 문제 | 대책 | 효과 |
|:---|:---|:---|
| 카운터 개수는 4갠데 잡아야 할 이벤트가 10개라 동시에 측정을 못 해서 분석이 박살 남 | 시간을 잘게 쪼개서 이 카운터 저 카운터 번갈아 가며 재는 **다중화(Multiplexing)** 꼼수 시전 | 물리 카운터 한계를 씹어먹고 수십 개의 이벤트를 동시에 추정 측정하는 기적 달성 |
| 스레드가 1번 CPU에서 2번 CPU로 멋대로 도망 다녀서 카운터 데이터가 쓰레기로 오염됨 | 분석할 스레드를 특정 CPU에 멱살 잡고 묶어버리는 **시피유 피닝(CPU Pinning)** 강제 발동 | 코어 이동으로 인한 카운터 데이터 붕괴를 막고 비교 실험의 미친듯한 일관성 사수 |
| 샘플링 빈도를 너무 촘촘하게 잡았더니 **인터럽트(PMI)**가 폭주해서 시스템 전체가 뻗어버림 | 하드웨어가 알아서 버퍼에 짱박아주는 **PEBS**를 켜고, 샘플링 주기를 적절히 타협해서 조절함 | 측정기(프로파일러) 자체가 시스템을 갉아먹는 오버헤드 간섭을 극한까지 억제 |

#### 한줄 요약

- 카운터 모자라면 다중화 꼼수 쓰고, 도망가면 CPU 피닝으로 묶고, 인터럽트 폭주하면 PEBS로 버퍼에 짱박아라.

## Ⅶ. 결론

<details><summary>용어 설명</summary>

- **PMU 분석 선택 기준(PMU Performance Profiling Criteria)**: 뼛속 원인을 캘 건지 겉핥기 함수 시간만 볼 건지 따져보고 PMU를 켤지 말지 정하는 잣대이다.

</details>

- **PMU 분석 선택 기준** 원칙에 따라, 뼛속 하드웨어 헛스윙(캐시/분기) 진단은 **PMU**, 겉핥기 함수 논리 시간 추적은 **소프트웨어 프로파일링** 채택 기조 확립함

#### 한줄 요약

- 진짜 뼛속 병목을 잡고 싶으면 닥치고 PMU를 켜라.
