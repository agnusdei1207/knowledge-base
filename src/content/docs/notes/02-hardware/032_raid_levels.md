## Ⅰ. 개요

<details><summary>용어 설명</summary>

- **RAID(Redundant Array of Independent Disks)**: 복수 드라이브를 논리 어레이로 묶어 스트라이핑·미러링·패리티로 성능과 장애 허용성을 조정하는 스토리지 기술.
- **고가용성(High Availability)**: 시스템 물리적 고장 발생 시에도 서비스 중단이나 데이터 유실 없이 정상 입출력을 유지하는 능력.

</details>

- 정의/개념: 복수 드라이브를 논리 어레이로 묶고 분산·복제·잉여 계산을 조합해 성능과 장애 허용성을 조절하는 **RAID(Redundant Array of Independent Disks)**
- 배경/필요성: 단일 드라이브는 대역폭이 한 대에 묶이고 고장 시 곧바로 데이터 접근이 끊겨 **고가용성**을 제공할 수 없음

#### 한줄 요약
- RAID가 늘리는 것은 가용성이지 내구성이 아니며, 삭제·손상·재해는 그대로 전파되므로 백업을 대체할 수 없다.

## Ⅱ. 특징

<details><summary>용어 설명</summary>

- **스트라이핑(Striping)**: 데이터를 여러 디스크에 블록 단위로 분산 기록해 I/O 대역폭을 높이는 방식.
- **미러링(Mirroring)**: 동일한 데이터를 두 개 이상의 드라이브에 완전 복제해 무결성을 유지하는 기법.
- **패리티(Parity)**: XOR 연산으로 에러 검출·복구용 잉여 데이터를 생성해 저장 공간 효율을 높이는 방식.

</details>

- **스트라이핑**으로 다중 드라이브에 I/O를 분산해 순차·병렬 처리량 확대
- **미러링**으로 동일 데이터 사본을 유지해 드라이브 장애 시 대체 읽기 제공
- **패리티**로 데이터 사본보다 적은 중복 용량을 사용해 고장 데이터 재구성

#### 한줄 요약
- **미러링**은 용량을 절반 내주고 **패리티**는 쓰기 성능을 내주므로, 보호 비용을 공간으로 낼지 시간으로 낼지가 레벨 선택의 본질이다.

## Ⅲ. 구조 및 구성요소

<details><summary>용어 설명</summary>

- **RAID 컨트롤러(RAID Controller)**: 호스트 입출력 요청을 받아 스트라이프 매핑 및 패리티 연산을 총괄하는 제어기.
- **BBU(Battery Backup Unit)**: 정전 시 컨트롤러 캐시 데이터를 보존하는 배터리 백업 장치.

</details>

```text
[RAID 시스템]
├─ 호스트 인터페이스 (PCIe·SAS)
├─ RAID 컨트롤러
│  ├─ 스트라이프 매퍼 (LBA → 디스크·오프셋)
│  ├─ 패리티 가속 엔진 (XOR·리드솔로몬)
│  └─ 쓰기 캐시
│     └─ BBU (정전 시 캐시 보존)
└─ 물리 디스크 어레이 (디스크 1 ~ N)
```

선의 의미: 가지(`├─`)는 소유 관계이며, 스트라이프 매퍼를 지난 뒤에야 요청이 개별 물리 디스크로 갈라짐

| 구성요소 | 책임 |
|:---|:---|
| **RAID 컨트롤러** | 어레이 상태 감시와 전체 I/O 제어 |
| 스트라이프 매퍼 | 논리 주소를 다중 물리 디스크 번호와 오프셋으로 변환 |
| 패리티 가속 엔진 | XOR 및 리드솔로몬 연산으로 패리티 생성·복구 |
| **BBU(Battery Backup Unit)** | 정전 시 미완료 쓰기 데이터를 캐시에 보존 |

#### 한줄 요약
- 컨트롤러가 단일 지점에 모든 매핑과 패리티 상태를 쥐고 있으므로, 디스크를 아무리 늘려도 컨트롤러 자체는 여전히 단일 장애점으로 남는다.

## Ⅳ. 흐름도

<details><summary>용어 설명</summary>

- **RMW(Read-Modify-Write)**: RAID 5/6에서 부분 쓰기 시 기존 데이터와 패리티를 읽고 새 패리티를 계산해 쓰는 과정.

</details>

```text
호스트 쓰기 요청 도달
        │
   스트라이프 전체를 덮는 쓰기인가?
   ┌────┴─────┐
  예           아니오 (부분 쓰기)
   │             │
새 패리티를      기존 데이터·패리티 읽기 (2 Reads)
곧바로 계산       │
   │        P_new = D_old ⊕ D_new ⊕ P_old
   │             │
   │        새 데이터·패리티 쓰기 (2 Writes)
   └────┬────────┘
        │
   호스트에 완료 응답
```

분기 결과: 전체 스트라이프 쓰기는 읽기가 필요 없지만 부분 쓰기는 **RMW(Read-Modify-Write)** 때문에 디스크 I/O가 4회로 늘어, 같은 데이터양이라도 요청 크기에 따라 비용이 몇 배 갈림

#### 한줄 요약
- 쓰기 페널티는 패리티 계산이 아니라 계산에 필요한 기존 값을 읽어 오는 데서 나오므로, 요청을 스트라이프 크기에 맞추는 것만으로 상당 부분 사라진다.

## Ⅴ. 종류 및 비교

<details><summary>용어 설명</summary>

- **RAID 5**: 패리티를 전 드라이브에 분산 배치해 N-1 용량으로 단일 드라이브 장애를 견디는 구성.
- **RAID 6**: 서로 다른 두 패리티를 분산 배치해 N-2 용량으로 두 드라이브 동시 장애까지 견디는 구성.
- **RAID 10**: 미러 쌍을 만든 뒤 그 위에 스트라이핑을 얹어, 패리티 계산 없이 성능과 장애 허용을 동시에 얻는 구성.

</details>

| RAID 레벨 | RAID 0 | RAID 1 | RAID 5 | RAID 6 | RAID 10 |
|:---|:---|:---|:---|:---|:---|
| 적용 기준 | 장애 허용 없이 처리량·용량 우선 | 단순 복구·낮은 읽기 지연 우선 | 단일 장애 허용·용량 효율 우선 | 이중 장애 허용·용량 효율 우선 | 임의 쓰기 성능·복구 속도 우선 |
| 핵심 특징 | 스트라이핑 전용·100% 용량 | 1:1 미러 복제·50% 용량 | 단일 분산 패리티·N-1 용량 | 이중 분산 패리티·N-2 용량 | 미러링 위 스트라이핑 결합 |
| 한계 | 디스크 1개 장애 시 전체 손실 | 저장 효율 50%로 비용 상승 | RMW 오버헤드·재구축 부담 | 2중 패리티 연산 지연 증가 | 고비용·최소 4개 디스크 필요 |

#### 한줄 요약
- 디스크 용량이 커질수록 재구축 시간이 길어져 그동안의 추가 장애 확률이 올라가므로, 대용량 시대에는 RAID 5의 단일 패리티가 사실상 부족해졌다.

## Ⅵ. 실무 고려사항 및 대책

<details><summary>용어 설명</summary>

- **핫 스페어(Hot Spare)**: 디스크 장애 시 자동으로 투입되어 즉시 재구축을 시작하는 대기 드라이브.
- **패트롤 리드(Patrol Read)**: 유휴 시간에 전체 디스크를 주기적으로 검사해 잠재적 배드 섹터를 예방 복구하는 기능.
- **쓰기 구멍(Write Hole)**: 정전·장애로 데이터와 패리티 중 일부만 기록돼 서로 불일치하는 상태.

</details>

| 문제 | 대책 | 효과 |
|:---|:---|:---|
| 대용량 드라이브 재구축 중 추가 장애 발생 | **RAID 6** 또는 **RAID 10** 구성에 **핫 스페어** 연동 | 이중 장애 허용 및 재구축 대기 단축 |
| 불시 정전 시 **쓰기 구멍**으로 데이터·패리티 불일치 | **BBU(Battery Backup Unit)** 캐시와 저널링 적용 | 미완료 쓰기 복구·패리티 정합성 유지 |
| **RAID 5** 부분 쓰기 집중 시 성능 저하 | 패리티 연산이 없는 RAID 10 구조로 전환 | 쓰기 페널티 제거 및 입출력 지연 안정화 |
| 재구축 중 잠재적 읽기 오류 발생 | 정기적인 **패트롤 리드**·불량 블록 치환 | 배드 섹터 조기 감지·재구축 실패 위험 감소 |

#### 한줄 요약
- 네 대책이 겨누는 것은 장애 자체가 아니라 재구축이라는 취약 구간이며, RAID의 실제 위험은 디스크가 고장 난 순간이 아니라 그 뒤 복구 기간에 있다.

## Ⅶ. 결론

- 임의 쓰기·빠른 재구축은 **RAID 10**, 용량 효율과 이중 장애 허용은 **RAID 6**을 선택하되, 장애 도메인·재구축 시간을 검증하고 RAID를 백업 대체 수단으로 사용하지 않음

#### 한줄 요약
- 레벨 선택은 정상 운영 성능이 아니라 한 대가 빠진 상태에서 얼마나 버티고 얼마나 빨리 복구되는지로 판단해야 한다.
