## Ⅰ. 개요

<details><summary>용어 설명</summary>

- **CUDA(Compute Unified Device Architecture)**: NVIDIA가 개발한 GPU 범용 병렬 컴퓨팅 플랫폼이자 C/C++ 기반 프로그래밍 모델.
- **호스트-디바이스(Host-Device)**: CPU와 메인 메모리를 호스트(Host), GPU와 비디오 메모리를 디바이스(Device)로 분리하여 협업하는 구조.

</details>

- 정의/개념: **호스트-디바이스** 경계를 명시적으로 다루면서 스레드 계층과 메모리를 프로그래머가 직접 제어하는 **CUDA** 플랫폼
- 배경/필요성: GPU 하드웨어의 병렬성을 쓰려면 스레드 배치와 메모리 계층을 코드에 드러내야 하는데, 기존 CPU 언어에는 그 표현 수단이 없음

#### 한줄 요약
- CUDA는 하드웨어를 감추는 대신 드러내는 쪽을 택한 모델이며, 성능을 얻는 대가로 이식성과 학습 난도를 함께 지불한다.

## Ⅱ. 특징

<details><summary>용어 설명</summary>

- **스레드 계층(Grid-Block-Thread)**: 스레드를 블록으로 묶고, 블록들을 그리드로 구성하여 대규모 병렬성을 계층적으로 관리하는 모델.
- **CUDA 스트림(CUDA Stream)**: 호스트가 디바이스에 내리는 비동기 작업(복사, 커널 실행) 큐로, 다중 스트림 시 전송과 연산이 중첩 실행됨.

</details>

- **스레드 계층**으로 수백만 스레드를 하드웨어 자원에 계층적으로 사상
- 계층형 메모리(글로벌·공유·레지스터)를 통한 수동적 메모리 최적화
- **CUDA 스트림**으로 전송과 연산을 비동기 중첩 실행

#### 한줄 요약
- 세 계층 중 블록만이 하드웨어 SM에 대응하므로, 블록 크기 선택은 코드 구조 문제가 아니라 자원 배분 문제다.

## Ⅲ. 구조 및 구성요소

<details><summary>용어 설명</summary>

- **커널 함수(Kernel Function)**: `__global__` 키워드로 선언되어 GPU의 수많은 스레드에서 동시에 실행되는 C/C++ 함수.
- **공유 메모리(Shared Memory)**: `__shared__` 키워드로 선언되어 동일 블록 내 스레드들이 초고속으로 공유하는 온칩 SRAM.

</details>

```text
[CUDA 실행 모델]
├─ 호스트 (CPU·시스템 메모리)
│  ├─ CUDA 런타임 API (할당·스트림·커널 런칭)
│  └─ 고정 메모리 버퍼
├─ 인터커넥트 (PCIe·NVLink)
└─ 디바이스 (GPU·VRAM)
   ├─ 글로벌 메모리·L2 캐시
   └─ 그리드
      └─ 스레드 블록
         ├─ 공유 메모리
         └─ 32스레드 워프
```

선의 의미: 가지(`├─`)는 소유 관계이며, 인터커넥트가 호스트와 디바이스를 가르는 유일한 경계

| 구성요소 | 책임 |
|:---|:---|
| 호스트 런타임 드라이버 | GPU 메모리 할당, 비동기 스트림 스케줄링 및 커널 런칭 총괄 |
| 그리드·스레드 블록 | 스레드를 계층으로 묶어 하드웨어 SM에 사상 |
| 글로벌 메모리 (Global Mem) | GPU 전체 스레드가 접근 가능한 대용량 DRAM 공간 |
| **공유 메모리** | 블록 내 스레드 간 데이터 교환용 사용자 제어 SRAM |
| CUDA 스트림 | 전송과 **커널 함수** 실행을 비동기 파이프라인으로 중첩 |

#### 한줄 요약
- 메모리 계층이 자동 캐시가 아니라 프로그래머가 명시적으로 옮겨야 하는 공간이라는 점이 CUDA 최적화 난도의 대부분을 차지한다.

## Ⅳ. 흐름도

<details><summary>용어 설명</summary>

- **cudaMemcpyAsync**: CPU를 멈추지 않고 백그라운드 DMA를 통해 호스트와 디바이스 간 데이터를 복사하는 비동기 함수.

</details>

```text
호스트 프로그램 시작 → 디바이스 메모리 할당
        │
   스트림을 여러 개 쓰는가?
   ┌────┴──────────┐
아니오               예
   │                  │
동기 전송 후         전송·커널·회수를 스트림별로 겹침
커널 실행 후 회수      │
(전송 동안 연산기 유휴) │
   │             전송 지연이 다른 스트림 연산에 가려짐
   └────┬─────────────┘
        │
   완료 동기화 후 디바이스 메모리 해제
```

분기 결과: 단일 스트림에서는 전송 시간이 그대로 총 실행 시간에 더해지지만, 다중 스트림에서는 전송과 연산이 겹쳐 둘 중 긴 쪽만 남으므로 전송량이 많을수록 격차가 커짐

#### 한줄 요약
- **cudaMemcpyAsync**가 비동기인 것은 CPU 기준일 뿐 대역폭은 그대로이므로, 전송을 없애는 것이 아니라 가릴 연산이 있을 때만 이득이 된다.

## Ⅴ. 종류 및 비교

| 이기종 병렬 프로그래밍 프레임워크 | CUDA | OpenCL | SYCL | OpenMP |
|:---|:---|:---|:---|:---|
| 적용 기준 | NVIDIA GPU 기반 고성능 AI/HPC | 다양한 벤더(AMD/Intel) 이종 가속기 | 모던 C++ 기반 크로스 플랫폼 가속 | 기존 C/Fortran CPU 코드 점진적 가속 |
| 핵심 특징 | NVIDIA 하드웨어 최적화·방대한 생태계 | 이기종 벤더 독립적 개방형 표준 API | 단일 소스 모던 C++ 템플릿 기반 추상화 | 컴파일러 지시어(#pragma) 기반 간편 적용 |
| 한계 | NVIDIA 전용 하드웨어 종속성(Lock-in) | 코드가 길고 저수준 API로 생산성 저하 | 벤더별 런타임 성숙도 편차 존재 | 세밀한 GPU 하드웨어 제어 및 최적화 한계 |

#### 한줄 요약
- 네 프레임워크는 성능과 이식성을 맞바꾼 눈금이며, CUDA가 앞서는 이유는 언어가 아니라 라이브러리와 도구가 쌓인 시간이다.

## Ⅵ. 실무 고려사항 및 대책

<details><summary>용어 설명</summary>

- **고정 메모리(Pinned Memory)**: 페이지 아웃되지 않도록 고정해 DMA가 직접 접근할 수 있게 한 호스트 메모리.
- **커널 퓨전(Kernel Fusion)**: 연속된 작은 커널을 합쳐 런칭과 중간 메모리 접근을 줄이는 최적화.

</details>

| 문제 | 대책 | 효과 |
|:---|:---|:---|
| 인터커넥트 대역폭 한계로 전송이 병목 | **고정 메모리**와 다중 스트림으로 중첩 | 전송 대기가 연산에 가려지는 비율 증가 |
| 소규모 커널의 잦은 호출에 따른 런칭 오버헤드 | **커널 퓨전** 및 CUDA Graphs 적용 | 런칭 횟수와 중간 메모리 접근 감소 |
| 비연속 메모리 접근에 따른 DRAM 대역폭 낭비 | 공유 메모리 타일링(Tiling) 및 구조체 배열(SoA) 전환 | 메모리 병합(Coalescing) 달성 및 처리 속도 향상 |
| 스레드 간 데이터 동기화 경합 지연 | `__syncthreads()` 최소화 및 워프 레벨 프리미티브(`__shfl_sync`) 활용 | 동기화 대기 시간 단축 및 레지스터 직접 교환 |

#### 한줄 요약
- 네 문제 중 연산량이 원인인 것은 하나도 없으며, GPU 성능 작업이 사실상 데이터 이동 관리라는 점이 여기서 드러난다.

## Ⅶ. 결론

- NVIDIA GPU 기반 고성능 딥러닝·HPC는 **CUDA**를 선택하고, 멀티 벤더 이종 환경이 요구되면 SYCL·OpenCL로 이식성을 확보한 뒤 성능 격차를 실측으로 판단

#### 한줄 요약
- 프레임워크를 바꿔 얻는 이득보다 병목을 잘못 짚어 잃는 시간이 크므로, 선택보다 측정이 먼저 와야 한다.
