## Ⅰ. 개요

<details><summary>용어 설명</summary>

- **인터럽트 처리(Interrupt Handling)**: CPU가 명령을 실행하는 도중 주변 장치나 내부 예외가 발생했을 때, 현재 문맥을 보존하고 전용 ISR을 실행한 후 복귀하는 제어 메커니즘.
- **인터럽트 요청(Interrupt Request, IRQ)**: 주변 장치가 하드웨어 라인이나 메시지(MSI)를 통해 CPU에 즉각적인 처리를 요청하는 전기적 신호.
- **인터럽트 서비스 루틴(Interrupt Service Routine, ISR)**: 해당 인터럽트를 전담하여 장치의 I/O 데이터를 인출하고 상태를 처리하는 커널 함수.

</details>

- 정의/개념: 비동기 이벤트가 오면 현재 실행 상태를 보존하고 **인터럽트 서비스 루틴** 기반 분기했다가 되돌아오는 **인터럽트 처리** 기법
- 배경/필요성: 반복 폴링은 이벤트가 없어도 CPU를 소모하고, 여러 **인터럽트 요청** 겹치면 순서 규칙 없이는 긴급 장치가 뒤로 밀림

#### 한줄 요약
- 인터럽트가 절약하는 것은 CPU 시간이지 응답 지연이 아니며, 문맥 저장과 복원이라는 고정 비용 때문에 이벤트가 잦아지면 폴링보다 느려진다.

## Ⅱ. 특징

<details><summary>용어 설명</summary>

- **문맥 보존(Context Save)**: 현재 실행 중인 프로그램 카운터(PC)와 상태 레지스터(PSR)를 스택에 임시 저장하는 동작.
- **벡터 인터럽트(Vectored Interrupt)**: 장치가 제공하는 번호(Vector)로 시작 주소를 즉시 찾아 분기하는 방식.
- **데이지체인(Daisy Chain)**: 직렬 우선순위 승인 신호(INTA)를 연결해 가장 가까운 장치부터 선점하는 구조.

</details>

- **문맥 보존** 및 복원으로 ISR 종료 후 중단 지점의 실행 상태 회복
- **벡터 인터럽트** 기반 번호에 대응하는 ISR 주소를 조회해 소스 판별 시간 단축
- **데이지체인** 승인 신호를 직렬로 흘려 우선순위를 결선만으로 결정

#### 한줄 요약
- **벡터 인터럽트** 기반 소스 판별을 하드웨어로 옮겨 지연을 줄이는 대신 신호선을 요구하므로, 속도와 배선이 정면으로 교환된다.

## Ⅲ. 구조 및 구성요소

<details><summary>용어 설명</summary>

- **인터럽트 벡터 테이블(IVT)**: 인터럽트 번호별 ISR 시작 주소를 배열 형태로 저장하는 메모리 테이블.
- **APIC(Advanced Programmable Interrupt Controller)**: 다중 코어 환경에서 인터럽트를 분산 라우팅하는 고도화된 제어기.

</details>

```text
[벡터 인터럽트]
주변장치 군 ─ 인터럽트 제어기 ─ 벡터 번호 ─ CPU·IVT
                 ├─ 요청 레지스터
                 ├─ 우선순위 판별기
                 └─ 서비스 레지스터

[데이지체인]
CPU 승인선 ─ 최우선 장치 ─ 다음 장치 ─ 마지막 장치
```

선의 의미: 벡터 경로는 번호 기반 ISR 식별, 데이지체인 경로는 직렬 승인 순서에 따른 우선순위

| 구성요소 | 책임 |
|:---|:---|
| 인터럽트 제어기·**APIC** | 다중 IRQ 수신·우선순위 판정·코어 라우팅 |
| **인터럽트 벡터 테이블(IVT)** | 인터럽트 번호를 ISR 시작 주소로 사상 |
| **ISR** | 장치 상태 판독·플래그 초기화·I/O 데이터 처리 |
| 문맥 스택 메모리 | 인터럽트 진입 전 PC, 범용 레지스터, 플래그 안전 보존 |

#### 한줄 요약
- 우선순위 판정이 CPU 밖 제어기에서 끝나야 CPU가 판정 시간만큼 멈추지 않으므로, 인터럽트 성능의 상당 부분은 CPU가 아니라 제어기 설계에서 결정된다.

## Ⅳ. 흐름도

<details><summary>용어 설명</summary>

- **IRET(Interrupt Return)**: 스택에 저장된 PC와 플래그를 복원하여 인터럽트 발생 전 명령어로 복귀하는 명령어.

</details>

```text
주변장치 인터럽트 요청 (IRQ)
        │
   현재 우선순위보다 높은가?
   ┌────┴─────┐
아니오          예
   │             │
요청 보류·      현재 명령 완료 후
대기열 유지      PC·PSR 스택 저장
   │             │
   │        IVT 조회 후 ISR 진입
   │             │
   │      ISR 실행 중 상위 인터럽트 발생?
   │        ┌────┴────┐
   │      아니오       예
   │        │          │
   │     ISR 완료   중첩 진입 후 복귀
   │        └────┬─────┘
   └────┬────────┘
        │
   IRET로 문맥 복원·중단 지점 재개
```

분기 결과: 우선순위 비교가 진입 전에 한 번, ISR 실행 중에 다시 한 번 일어나므로 중첩을 허용할수록 응답은 빨라지고 스택 사용량과 최악 지연 예측은 어려워짐

#### 한줄 요약
- **IRET** 복원하는 것은 레지스터뿐이고 캐시·TLB 상태는 되돌아오지 않으므로, 인터럽트는 끝난 뒤에도 원래 코드의 속도에 흔적을 남긴다.

## Ⅴ. 종류 및 비교

| 인터럽트 판별 방식 | 벡터 인터럽트 (Vectored) | 비벡터 인터럽트 (Non-Vectored) | 데이지체인 (Daisy Chain) | 소프트웨어 폴링 (Polling) |
|:---|:---|:---|:---|:---|
| 적용 기준 | 다수 소스의 빠른 ISR 식별 | 소수 소스·고정 ISR 진입점 | 배선 최소화·고정 하드웨어 순위 | 이벤트 빈도가 낮고 CPU 점유 허용 |
| 핵심 특징 | 벡터 번호로 ISR 주소 선택 | 고정 주소 진입 후 소프트웨어 소스 판별 | 직렬 승인 신호로 하드웨어 우선순위 결정 | CPU가 장치 상태를 반복 조회 |
| 한계 | 버스 신호선 및 전용 하드웨어 비용 | 다중 인터럽트 시 지연시간 증가 | 뒤쪽 장치의 기아(Starvation) 위험 | 장치 수 증가 시 폴링 지연 선형 증가 |

#### 한줄 요약
- 네 방식은 소스를 누가 판별하느냐로 갈리며, 하드웨어가 판별할수록 빠르지만 장치 구성을 바꿀 때 회로까지 손대야 하는 경직성을 얻는다.

## Ⅵ. 실무 고려사항 및 대책

<details><summary>용어 설명</summary>

- **Top-half / Bottom-half**: 긴급한 하드웨어 처리는 상반부(Top-half)에서 즉시 끝내고, 무거운 후속 작업은 하반부(Bottom-half)로 지연 처리하는 기법.
- **인터럽트 네스팅(Interrupt Nesting)**: ISR 실행 중 더 높은 우선순위의 인터럽트가 오면 현재 ISR을 중단하고 새 ISR을 우선 실행하는 구조.

</details>

| 문제 | 대책 | 효과 |
|:---|:---|:---|
| ISR 내부 처리 지연으로 다른 인터럽트 차단 | **Top-half / Bottom-half** 분리 구조 적용 | 인터럽트 응답성 확보 및 지연 최소화 |
| 고우선순위 장치 집중으로 저우선순위 기아 | 회전 우선순위(Rotating Priority) 스케줄링 | 모든 장치에 공평한 처리 기회 보장 |
| 동일 IRQ 선로를 복수 장치가 공유 시 충돌 | 공통 ISR 체이닝 및 상태 레지스터 신속 검사 | 공유 인터럽트 오동작 방지 |
| **인터럽트 네스팅** 누적으로 스택 고갈 | 중첩 깊이 제한과 전용 인터럽트 스택 할당 | 스택 오버플로 차단·커널 안정성 확보 |

#### 한줄 요약
- **Top-half / Bottom-half** 분리가 통하는 이유는 급한 일과 무거운 일이 대개 다르기 때문이며, 이 둘이 분리되지 않는 작업에서는 어떤 기법도 ISR을 짧게 만들지 못한다.

## Ⅶ. 결론

- 다중 코어·다수 장치 환경은 코어 라우팅이 가능한 **벡터 인터럽트** 활용 기본으로 하고, 데이지체인은 고정 우선순위와 배선 단순성이 더 중요한 소규모 장치로 한정

#### 한줄 요약
- 판별 방식 선택의 실제 기준은 평균 응답 시간이 아니라 최악의 경우 몇 개의 인터럽트가 앞에 설 수 있느냐이며, 실시간 시스템은 이 상한만 본다.
