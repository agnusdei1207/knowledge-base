## Ⅰ. 개요

<details><summary>용어 설명</summary>

- **서브네팅(Subnetting)**: 통째로 받은 큰 IP 땅덩어리(네트워크)를 부서별 규모에 맞춰 쪼개서 낭비 없이 노나 쓰는 기술이다.
- **CIDR(Classless Inter-Domain Routing)**: A/B/C 클래스라는 낡은 계급장을 떼버리고, `/24`처럼 슬래시를 써서 IP를 필요한 만큼만 잘라 쓰거나 합치는 기술이다.

</details>

- 정의: 주소 낭비를 막고 라우팅 테이블 덩치를 줄이기 위한 **IP 주소 분할 및 경로 집약 체계**
- 배경: 옛날의 고정된 클래스 주소 방식으로는 **IP 낭비가 심하고 라우팅 경로 집약이 불가능했기 때문**

#### 한줄 요약

- IP를 부서 크기대로 낭비 없이 잘라 쓰고(서브네팅), 라우터에 알릴 땐 한 줄로 퉁치는(CIDR) 기술이다.

## Ⅱ. 특징

<details><summary>용어 설명</summary>

- **프리픽스 길이(Prefix Length)**: `/24`처럼 IP 주소에서 "여기까지가 우리 동네(네트워크) 번호야" 하고 끊어주는 비트 수이다.
- **VLSM(Variable Length Subnet Mask)**: 100명 있는 부서엔 큰 대역을, 10명 있는 부서엔 작은 대역을 고무줄처럼 유도리 있게 잘라주는 가변 마스크 기법이다.
- **경로 집약(Route Aggregation)**: "논현동, 역삼동, 대치동.."을 그냥 "강남구" 하나로 퉁쳐서 코어 라우터 메모리를 아끼는 기술이다.

</details>

- **프리픽스 길이** 길어질수록(예: `/24` $\to$ `/26`) 동네(서브넷) 개수는 늘어나지만 한 동네에 사는 집(호스트) 수는 줄어듦.
- 부서 규모에 맞춰 서브넷 마스크 크기를 고무줄처럼 늘리고 줄이는 **VLSM** 지원.
- 연속된 IP 대역을 하나로 퉁쳐서 코어 라우터의 부하를 획기적으로 줄이는 **경로 집약** 적용.

#### 한줄 요약

- 필요한 만큼만 잘라 쓰는 VLSM과, 잘게 쪼갠 걸 다시 묶어주는 경로 집약이 핵심이다.

## Ⅲ. 구조 및 구성요소

<details><summary>용어 설명</summary>

- **서브넷 마스크(Subnet Mask)**: "어디까지가 동네 번호(1)고 어디서부터가 컴퓨터 번호(0)인지"를 가려내는 거름망이다.
- **네트워크 프리픽스(Network Prefix)**: 마스크로 걸러낸 동네 번호로, 라우터가 길을 찾을 때 쓰는 핵심 이정표이다.
- **호스트 비트(Host Bits)**: 동네 안에서 "1번, 2번 컴퓨터" 하고 기기마다 번호를 매길 수 있는 잉여 자리이다.

</details>

```text
[ CIDR 기반 직관적 비교 주소 분할 구조 ]

[ 192.168.1.0/26 (서브넷 마스크 255.255.255.192) ]
┌───────────────────────────────────┬────────────────────┐
│ 네트워크 프리픽스 (앞 26비트)     │ 호스트 (뒤 6비트)  │
│ 11000000.10101000.00000001.00     │ 000000 (~ 111111)  │
└───────────────────────────────────┴────────────────────┘
 - 네트워크 ID : 192.168.1.0 (동네 대표 주소, 사용 불가)
 - 브로드캐스트: 192.168.1.63 (동네 전체 방송, 사용 불가)
 - 쓸 수 있는 IP: 192.168.1.1 ~ 192.168.1.62 (총 62개)
```

| 구성요소 | 직관적 비교 책임 | 계산 공식 및 특징 |
|:---|:---|:---|
| **네트워크 프리픽스** | 라우터가 "아, 이 대역이구나" 하고 길을 찾는 기준 | **N비트 (CIDR /N)**. 이게 길수록 최장 일치(LPM)에 걸림 |
| **호스트 비트** | 부서 안에서 PC랑 스마트폰에 노나줄 수 있는 자리표 | **$H = 32 - N$** 비트 |
| **유효 호스트 주소** | 대빵(네트워크ID)과 방송국(Broadcast) 빼고 진짜 쓸 수 있는 IP 개수 | **$2^H - 2$** 개 주소 |
| **경로 집약 (Supernetting)**| 잘게 쪼개진 대역들을 공통 비트로 묶어서 라우터 부담을 줄여주는 퉁치기 | 집약할 주소들이 반드시 **연속(Contiguous)** 되어야 함 |

#### 한줄 요약

- 앞의 N비트는 동네를 식별하고, 남은 비트에서 두 개 빼고 나머지를 컴퓨터에 나눠준다.

## Ⅳ. 흐름도

<details><summary>용어 설명</summary>

- **수요 내림차순 정렬(Descending Demand Sorting)**: IP 쪼갤 때, 제일 큰 부서부터 땅을 먼저 떼줘야 짜투리 땅(파편화)이 안 남는다는 설계 원칙이다.
- **집약 경로 생성(Aggregate Route Generation)**: 잘게 쪼개 쓴 연속 서브넷들의 공통 분모(상위 비트)만 뽑아서 한 줄짜리 경로로 요약하는 절차이다.

</details>

```text
[ VLSM 할당 및 CIDR 경로 집약 십자포화 흐름 ]
┌──────────────────────────────┐
│ 1. IP 필요 개수 조사         │
│ (영업부 100개, 인사부 20개)  │
└──────────────┬───────────────┘
               ▼
┌──────────────────────────────┐
│ 2. 수요 내림차순 정렬        │
│ (제일 큰 놈부터 땅을 떼어줌) │
└──────────────┬───────────────┘
               ▼
┌──────────────────────────────┐
│ 3. 프리픽스 산정 및 할당     │
│ (100개면 128개짜리 /25 할당) │
└──────────────┬───────────────┘
               ▼
┌──────────────────────────────┐
│ 4. 공통 비트 추출 (경로 집약)│
│ (잘게 쪼갠 땅을 상위 비트로 묶음)│
└──────────────┬───────────────┘
               ▼
┌──────────────────────────────┐
│ 5. 라우팅 테이블 축약 등록   │
│ (라우터에 "통째로 여기로 와" 광고)│
└──────────────────────────────┘
```

### 동작 원리

1. 수요 조사: 부서별로 "호스트 개수 + 2"에 맞는 비트 크기($2^H$)를 계산함.
2. 내림차순 정렬: 파편화를 막기 위해 IP가 가장 많이 필요한 큰 부서부터 정렬함.
3. 프리픽스 할당: $2^H$ 배수 경계에 맞춰 낭비 없이 네트워크 ID를 자름.
4. 경로 집약: 광고할 땐 연속된 서브넷의 공통 비트만 묶어서 짧은 /M으로 합쳐버림.
5. 축약 광고: 코어 라우터에는 축약된 경로 하나만 광고해서 메모리를 아낌.

#### 한줄 요약

- 큰 덩어리부터 잘라주고(VLSM), 나중에 코어 라우터에 알릴 땐 한 줄로 묶어서(CIDR) 보낸다.

## Ⅴ. 종류 및 비교

<details><summary>용어 설명</summary>

- **서브네팅 vs 경로 집약(Supernetting)**: 서브네팅이 큰 피자를 작게 조각내서 나눠 먹는 거라면, 경로 집약은 조각난 피자를 장부에 1판으로 묶어 적는 기술이다.

</details>

| 구분 | **서브네팅 (쪼개기)** | **CIDR 경로 집약 / Supernetting (합치기)** |
|:---|:---|:---|
| 핵심 목적 | 너무 큰 주소 덩어리를 낭비 없이 **부서별로 잘게 분할함** | 잘게 쪼개진 주소들을 **큰 덩어리로 하나로 묶어버림** |
| 적용 위치 | 사내망, 데이터센터 등 **브로드캐스트 도메인을 쪼갤 때** | ISP 백본망 등 **인터넷 코어 라우팅 테이블 줄일 때** |
| 프리픽스 길이 | 갈수록 비트 길이가 길어짐 (예: `/24` $\to$ `/27`) |  묶을수록 비트 길이가 짧아짐 (예: 두 개의 `/24` $\to$ `/23`) |
| 주요 효과 | IP 낭비 방지 및 불필요한 사내 트래픽 전파 격리 | 라우팅 연산 부하 떡락 및 인터넷 백본 속도 향상 |

#### 한줄 요약

- 사내에선 서브네팅으로 쪼개서 쓰고, 밖으로 나갈 땐 CIDR로 다시 묶어서 나간다.

## Ⅵ. 실무 고려사항 및 대책

<details><summary>용어 설명</summary>

- **브로드캐스트 도메인(Broadcast Domain)**: "누구 계세요!" 하고 소리치면 다 들리는 범위로, 서브넷을 안 쪼개고 너무 크게 잡으면 쓸데없는 소음(트래픽)으로 스위치가 뻗는다.
- **주소 재설계(Address Redesign)**: 처음 쪼갤 때 빡빡하게 잘랐다가 나중에 직원 늘어나서 IP 모자라면 망 전체를 갈아엎어야 하는 대참사이다.

</details>

| 문제 | 대책 | 효과 |
|:---|:---|:---|
| 서브넷을 크게 줬더니 브로드캐스트 패킷 폭풍 불어서 스위치 뻗음 | **브로드캐스트 도메인** VLAN이나 `/24` 이하 서브넷으로 쪼갬 | L2 대역폭 낭비 방지 및 네트워크 안정성 확보 |
| 딱 맞춰서 IP 줬다가 나중에 확장 안 돼서 IP 고갈됨 (파편화 발생) | 향후 30% 확장을 고려한 **IP 주소 수요 산정(Capacity Planning)** | 눈물겨운 전체망 **주소 재설계** 사태 예방 |
| 부서별로 IP를 듬성듬성 중구난방으로 줘서 경로 집약(CIDR)이 안 됨 | IPAM 솔루션 써서 주소를 반드시 **연속(Contiguous)되게 할당** | 코어 라우터 메모리 절감 및 라우팅 속도 향상 |

#### 한줄 요약

- 브로드캐스트 터지기 전에 쪼개고, 확장을 대비해 넉넉하고 연속적으로 주소를 줘라.

## Ⅶ. 결론

<details><summary>용어 설명</summary>

- **연속 VLSM 블록(Contiguous VLSM Block)**: IP를 쪼개줄 때 빈 공간 없이 다닥다닥 붙여서 연속으로 잘라줘야 나중에 라우터에서 한방에 퉁칠(집약) 수 있다는 설계 원칙이다.

</details>

- **연속 VLSM 블록** 할당 원칙에 따라, 쪼갤 땐 확장성을 고려해 내림차순으로 자르고, 광고할 땐 연속 주소를 묶어서 경로 집약하는 기조 확립함

#### 한줄 요약

- IP를 쪼갤 때는 나중에 합칠 것(CIDR 집약)까지 생각해서 빈틈없이 연속으로 붙여라.
