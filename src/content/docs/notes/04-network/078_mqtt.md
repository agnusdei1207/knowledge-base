## Ⅰ. 개요

<details><summary>용어 설명</summary>

- **MQTT (Message Queuing Telemetry Transport)**: 센서랑 서버가 1:1로 빡세게 직통 연결하는 게 아니라, 중간에 브로커(우체국) 하나 두고 가볍게 '토픽(게시판 주제)' 단위로 쪽지를 주고받는 초경량 단톡방 프로토콜이다.

</details>

- 정의: **MQTT** 기반 중앙 브로커(Broker)가 토픽(Topic)을 기준으로 메시지를 릴레이 해주는(Pub/Sub), 배터리가 적고 인터넷이 툭툭 끊기는 열악한 IoT 환경에 특화된 초경량 통신 프로토콜이다.
- 배경: 산꼭대기 센서나 달리는 자동차는 인터넷이 자주 끊기고 배터리도 조루인데, **무겁고 복잡한 기존 HTTP(REST) 방식으로는 버틸 수가 없어서 가볍고 끊겨도 찰떡같이 전달되는 놈이 필요했다.** #### 한줄 요약

- 서로 IP 주소 몰라도 "강남 날씨"라는 게시판에 글 남기면 알아서 뿌려주는, IoT 세계의 가벼운 단톡방 프로토콜이다.

## Ⅱ. 특징

<details><summary>용어 설명</summary>

- **Pub/Sub (발행/구독) 구조**: 내가 쏘는 쪽지가 누구한테 갈지(목적지 IP) 몰라도 되고, 그냥 특정 토픽(Topic)으로 툭 던지면 브로커가 명단 보고 알아서 구독자한테 쫙 뿌려주는 쿨한 디커플링 방식이다.
- **QoS 상충 (Trade-off)**: "메시지 무조건 도착하게 해줘!"(QoS 2)라고 배달 확인을 빡세게 걸면, 그만큼 확인 패킷 핑퐁이 늘어나서 배터리가 줄줄 새는 딜레마다.

</details>

- **주소 없는 블라인드 미팅 (Pub/Sub)**: 센서(발행자)랑 서버(구독자)는 서로 쌩얼(IP)을 몰라도, 중간 브로커가 강력히 토픽(Topic) 매칭시켜서 메시지를 던져준다.
- **배터리 아끼는 극한의 다이어트**: 헤더 크기가 꼴랑 2바이트밖에 안 돼서, 툭하면 끊기는 3G/LTE-M 통신망이나 저전력 기기에서도 기가 막히게 살아남는다.
- **내 맘대로 배송 수준 (QoS)**: 대충 던져도 되면 QoS 0, 꼭 가야 하면 QoS 1, 두 번 가면 ㅈ되는 결제 명령이면 QoS 2로 상황에 맞게 골라 쓴다.

#### 한줄 요약

- IP 주소 몰라도 통신되고, 헤더 크기는 쥐꼬리만 하며, 배달 퀄리티를 내 맘대로 조절할 수 있는 게 깡패다.

## Ⅲ. 구조 및 구성요소

<details><summary>용어 설명</summary>

- **브로커 (Broker)**: 전 세계 센서 수백만 대가 던지는 메시지를 토픽별로 싹 다 긁어모아서, 구독자들한테 교통정리 해서 뿌려주는 거대한 중앙 전송 계층 신뢰성 제어 엔진이다.
- **세션/전달 저장소**: 구독자가 통신이 끊겨서 오프라인 상태일 때, 메시지를 버리지 않고 캐비닛에 안전하게 보관했다가 재접속하면 쏟아내 주는 우체통이다.

</details>

```text
[ MQTT 발행/구독 직관적 비교 구조 ]

[ 1. 발행자 (Publisher) ] ── ("온도/강남" 토픽으로 35도 데이터 툭 던짐)
      │
      ▼
[ 2. 브로커 (Broker) ] ── (수십만 개 토픽 분류하고 구독자 명단 체크함)
      │
      ├─► [ 3-A. 토픽/구독 엔진 ] ── ("온도/강남" 구독한 놈 어딨냐? 찾아서 라우팅함)
      └─► [ 3-B. 세션/전달 저장소 ] ── (구독자 오프라인이면 킵(Keep) 해둠)
      │
      ▼
[ 4. 구독자 (Subscriber) ] ── ("온도/강남" 데이터 편하게 입 벌리고 받아먹음)
```

| 구성요소 | 책임 | 비고 |
|:---|:---|:---|
| **발행자 (Publisher)** | 목적지 IP 그딴 거 모르고 **그냥 토픽 달아서 브로커한테 던지는 놈** | Publisher |
| **브로커 (Broker)** | 누구한테 보낼지 룰 정하고 **중간에서 강력히 싹 다 릴레이 해주는 전송 계층 신뢰성 제어 엔진** | MQTT Broker |
| **토픽/구독 엔진** | "이 토픽 누가 구독했어?" **구독 명단 까보고 수신자 정확히 매칭시키는 놈** | Routing Engine |
| **세션 저장소** | 수신자가 **통신 끊겨서 안 받을 때 메시지 버리지 않고 보관함에 킵(Keep)해둠** | Session Store |
| **구독자 (Subscriber)** | 브로커한테 "나 강남 날씨 구독할래" 신청하고 **입 벌리고 받아먹는 놈** | Subscriber |

#### 한줄 요약

- 발행자가 던지면 $\to$ 브로커가 받아서 교통정리 하고 $\to$ 구독자가 받아먹는 철저한 중간자(Broker) 중심 아키텍처다.

## Ⅳ. 흐름도

<details><summary>용어 설명</summary>

- **토픽 라우팅 (Topic Routing)**: URL 경로처럼 슬래시(/)로 만든 `센서/온도/강남` 토픽을 보고, 브로커가 이거 누가 받을지 교통정리 해주는 거다.
- **ACL (접근 제어 목록)**: 짬도 안 되는 비인가 작업자이 관리자용 공장 제어 토픽에 명령 쏘는 걸 막기 위해, 브로커가 권한(토픽 필터)을 칼같이 컷트하는 블랙리스트다.

</details>

```text
[ MQTT 십자포화 메시징 흐름 ]

┌──────────────────────────────┐
│ 1. [세션 연결 및 구독 신청]  │
│ (구독자: 브로커야 나 '날씨/#'(전국 날씨) 토픽 구독할게)
└──────────────┬───────────────┘
               ▼
┌──────────────────────────────┐
│ 2. [메시지 발행 (Pub)]       │
│ (발행자: '날씨/강남' 토픽으로 30도 데이터 쏜다!)
└──────────────┬───────────────┘
               ▼
┌──────────────────────────────┐
│ 3. [ACL 권한 검증 및 토픽 라우팅]
│ (브로커: '날씨/강남' 쏜 놈 권한 맞네. 구독자 명단 털어보자)
└──────────────┬───────────────┘
               ▼
┌──────────────────────────────┐
│ 4. [QoS 등급에 따른 배달]    │
│ (브로커: 얘는 QoS 1이니까, 받았다고 ACK 올 때까지 쪼아라)
└──────────────┬───────────────┘
               ▼
┌──────────────────────────────┐
│ 5. [메시지 배달 완료 및 저장]│
│ (수신: 강남 날씨 30도 수신 완료!)
└──────────────────────────────┘
```

### 동작 원리

1. 세션 연결/구독: 클라이언트가 브로커에 접속해 인증을 마치고 원하는 토픽(예: `sensor/+/temp`)을 구독함.
2. 메시지 발행: 센서가 자기 역할에 맞는 토픽과 데이터(Payload), 그리고 QoS 등급을 담아 브로커에 던짐.
3. 토픽 라우팅 검증: 브로커가 **ACL** 권한을 체크하고, 이 토픽을 구독한 놈들을 내부 라우팅 엔진에서 싸그리 찾아냄.
4. QoS 배달 집행: 브로커가 구독자들에게 메시지를 뿌리며, QoS 1, 2일 경우 도착 확인 응답(ACK)이 올 때까지 캐비닛(저장소)에 넣고 쪼아댐.

#### 한줄 요약

- 토픽 구독해 놓으면, 발행자가 그 토픽으로 쐈을 때 브로커가 알아서 쏙쏙 배달해 주는 흐름이다.

## Ⅴ. 종류 및 비교

<details><summary>용어 설명</summary>

- **QoS 0**: 대충 쏴보고 받으면 좋고 아니면 마는 쿨한 방식이다. (최대 1번 전달)
- **QoS 1**: 받았다고 대답할 때까지 계속 쏴대는 독촉 방식이다. 중복될 수 있다. (최소 1번 전달)
- **QoS 2**: 확인 사살 핑퐁을 4번이나 해서, 중복 없이 완벽하게 한 번만 꽂히게 만드는 비싼 방식이다. (정확히 1번 전달)

</details>

| MQTT QoS 등급 | **QoS 0 (한 번 툭 던짐)** | **QoS 1 (적어도 한 번은 감)** | **QoS 2 (정확히 딱 한 번만 감)** |
|:---|:---|:---|:---|
| 핵심 특징 | **전단지 알바** (가든 말든 난 몰라) | **등기 우편** (도착 확인할 때까지 계속 쏨) | **대통령 친서** (무조건 1번만 정확히 전달됨) |
| 동작 원리 | 쏠게. 끝. (Fire and Forget) | 쏠게 $\to$ 받았냐? $\to$ 어! |  쏠게 $\to$ 받았어 $\to$ 그럼 지울게 $\to$ 알았어 (4-way Handshake) |
| 치명적 한계 | 패킷 중간에 증발하면 **데이터 영원히 날아감** | 재전송하다가 **똑같은 데이터 2개 꽂혀서 중복 에러 남** | 패킷이 너무 많이 오가서 **배터리 급격한 자원 소모하고 느려터짐** |
| 주력 활용 | 1분에 한 번씩 보내는 **흔한 온도 센서** | 중복돼도 덮어쓰면 땡인 **알람 통보 / 상태값 갱신** | 두 번 결제되면 ㅈ되는 **요금 부과, 장비 On/Off 제어** |

#### 한줄 요약

- 배터리 아끼려면 무조건 QoS 0, 잃어버리면 안 되면 QoS 1, 중복되면 대형사고 터질 땐 어쩔 수 없이 QoS 2 쓴다.

## Ⅵ. 실무 고려사항 및 대책

<details><summary>용어 설명</summary>

- **LWT (유언장 메시지, Last Will and Testament)**: 센서가 배터리 방전돼서 갑자기 뻗어버릴 때, 브로커가 대신 "나 죽었어ㅠㅠ" 하고 유언장 메시지를 구독자(관제 서버)한테 쏴주는 눈물겨운 기능이다.
- **와일드카드 권한 (Wildcard Privilege)**: 해커가 `/#` (모든 토픽 구독) 와일드카드를 뚫어서 남의 집 센서값부터 보일러 제어권까지 다 빨아먹는 대규모 네트워크 장애다.

</details>

| 장애/위험 요소 | 원인 분석 | 실무 대책 및 해결방안 | 기대 효과 |
|:---|:---|:---|:---|
| 아무 데이터나 QoS 2 걸었더니 **센서 배터리 급격한 소모** | 1초마다 쏘는 온도 데이터에 QoS 2(4번 왕복)를 걸어서 통신칩이 쉬질 못함 | 데이터 성격 분석해서 **주기적 텔레메트리는 QoS 0 적용으로 경량화** | 무선 구간 통신량 줄이고 통신 전력 절감 및 배터리 수명 연장 |
| 센서 뻗었는데 **관제 서버의 센서 비정상 단절 미인지** | 통신이 예고 없이 뚝 끊기면 서버(구독자)는 그냥 데이터가 늦게 오는 줄 암 | 처음에 접속할 때 **LWT(Last Will and Testament) 메시지 설정으로 비정상 종료 시 즉시 공지** | 예고 없는 통신 단절(장애) 즉각 파악하고 장비 복구 투입 |
| 권한 잘못 뚫려서 **비인가 제어 명령 전송으로 인한 오동작** | `/#` 와일드카드 권한을 아무한테나 줘서 타겟팅 안 된 시스템 제어권까지 넘어감 | **최소 권한의 법칙(ACL)** 빡세게 먹여서 자기 부서 토픽만 건드리게 컷트함 | 어이없는 오조작 막고 통신 보안(TLS) 1차 방어 |

#### 한줄 요약

- 중요한 명령만 QoS 2 주고, 갑자기 뻗을 때 대비해 유언장(LWT) 써두고, `/#` 와일드카드 권한 아무나 주지 마라.

## Ⅶ. 결론

<details><summary>용어 설명</summary>

- (상단 참조)

</details>

- 저대역폭과 열악한 통신 환경에서 배터리를 아끼면서 대규모 장비를 연결하기 위해, **Pub/Sub 구조** 및 상황에 맞는 **세 가지 QoS 레벨**, **LWT(유언장)** 를 결합한 초경량 MQTT 메시징 기조 확립함

#### 한줄 요약

- MQTT는 인터넷 툭툭 끊기는 산꼭대기 센서들도 IP 몰라도 서로 단톡방처럼 소통하게 만들어주는 IoT 시대의 구세주다.
