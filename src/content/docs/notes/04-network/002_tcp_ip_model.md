## Ⅰ. 개요

<details><summary>용어 설명</summary>

- **TCP/IP 4계층 모델(TCP/IP 4-Layer Model)**: OSI 7계층이 학자들이 만든 이상적인 교과서라면, TCP/IP는 공학자들이 실제 인터넷을 굴려 먹으려고 4개 층으로 압축한 실전 프로토콜 아키텍처이다.
- **전송 제어 프로토콜(TCP)**: 데이터가 가다가 유실되면 다시 보내달라고 멱살 잡고 확실하게 배달해 주는(신뢰성) 우체국장이다.
- **인터넷 프로토콜(IP)**: "데이터가 잘 갔는지는 난 모르겠고, 일단 최선을 다해서 제일 빠른 길로 던져줄게" 하는 최선형(Best-Effort) 내비게이션이다.

</details>

- 정의: 인터넷 통신 기능을 IP(인터넷 프로토콜) 중심으로 4계층으로 실용 구조화한 **TCP/IP 4-Layer Model**
- 배경: 벤더별 프로토콜 난립 시대에, 전 세계 컴퓨터를 하나로 묶는 **개방형 인터넷 상호연동**이 절실했기 때문

#### 한줄 요약

- 복잡한 7계층을 버리고, 지금 우리가 쓰는 실제 인터넷을 4층으로 압축한 실전 규격이다.

## Ⅱ. 특징

<details><summary>용어 설명</summary>

- **얇은 허리 구조(Thin-Waist Architecture)**: 위로는 HTTP, FTP 등 수많은 앱이 있고 아래로는 5G, Wi-Fi 등 매체가 있지만, 중간은 오직 IP 하나(얇은 허리)로 묶어버린 모래시계 구조이다.
- **최선형 전달(Best-Effort Delivery)**: IP 계층이 "최선은 다해서 배달하겠는데, 가다가 터지거나 순서 꼬이는 건 내 알 빠 아님" 하고 무책임하지만 매우 빠르게 패킷을 던지는 방식이다.
- **종단 간 원칙(End-to-End Principle)**: 중간에 있는 라우터들은 멍청하게 길만 찾아주고, 데이터가 똑바로 왔는지 검사하는 복잡한 일은 양 끝단의 PC(종단)가 알아서 하자는 철학이다.

</details>

- 상하위 기술 의존성을 완전히 끊어버린 **Thin-Waist (얇은 허리, IP 중심)** 구조.
- 네트워크 뼈대는 가볍게 유지하고, 상태는 양 끝단의 호스트가 책임지는 **End-to-End (종단 간 원칙)**.
- 중간 라우터의 부하를 없애기 위해 신뢰성을 포기한 **Best-Effort (최선형 전달)** 라우팅.

#### 한줄 요약

- 중간 길잡이(IP)는 단순 무식하게 길만 뚫어주고, 복잡한 검사(TCP)는 양 끝단 피씨가 알아서 하는 철학이다.

## Ⅲ. 구조 및 구성요소

<details><summary>용어 설명</summary>

- **포트(Port)**: PC에 도착한 데이터가 웹 브라우저(80번)로 갈지 카톡(443번)으로 갈지 구별해 주는 방 번호이다.
- **MAC 주소(MAC Address)**: 공유기나 랜카드에 공장 출고 때부터 박혀 나오는, 물리적으로 절대 안 바뀌는 하드웨어 일련번호이다.

</details>

```text
[ TCP/IP 모래시계 아키텍처 ]

[ 4. 응용 계층 ] ────── (HTTP, SSH) ───────▶ 사용자 프로그램
                            │
[ 3. 전송 계층 ] ──────── (TCP, UDP) ───────▶ 포트 번호 (신뢰성)
                            ▼ (얇은 허리)
[ 2. 인터넷 계층 ] ───────── (IP) ──────────▶ IP 주소 (길 찾기)
                            │
[ 1. 네트워크 접근 계층 ] (Ethernet, Wi-Fi) ▶ MAC 주소 (물리 전송)
```

| 구성요소 | 팩트 폭행 책임 |
|:---|:---|
| **L4 응용 계층 (Application)** | OSI 5~7계층을 합쳐서, 유저가 쓰는 프로그램(HTTP, DNS) 화면을 바로 띄워줌 |
| **L3 전송 계층 (Transport)** | 포트 번호로 방을 찾아주고, TCP(안전)냐 UDP(빠름)냐 선택해서 배달함 |
| **L2 인터넷 계층 (Internet)** | 얇은 허리의 핵심(IP). 논리적 IP 주소만 보고 목적지까지 최적의 길을 뚫어줌 |
| **L1 네트워크 접근 (Network Access)**| OSI 1~2계층 통합. 랜선이나 Wi-Fi를 타고 MAC 주소 기반으로 데이터를 쏴버림 |

#### 한줄 요약

- 쓸데없이 잘게 쪼개지 않고 앱(L4), 배달(L3), 길 찾기(L2), 랜선(L1)으로 실용적으로 뭉쳤다.

## Ⅳ. 흐름도

<details><summary>용어 설명</summary>

- **캡슐화/역캡슐화(Encapsulation/Decapsulation)**: 캡슐화는 앱 데이터에 포트(L3), IP(L2), MAC(L1) 헤더를 차곡차곡 덧붙여 포장하는 거고, 역캡슐화는 받을 때 껍질을 까는 과정이다.

</details>

```text
[ TCP/IP 송수신 십자포화 흐름 ]
┌──────────────────────────────┐
│ 송신자 응용 계층               │
│ (웹 브라우저에서 데이터 생성)│
└──────────────┬───────────────┘
               ▼ (캡슐화 시작)
┌──────────────────────────────┐
│ [L3] 포트 번호 부착 (세그먼트) │
└──────────────┬───────────────┘
               ▼
┌──────────────────────────────┐
│ [L2] IP 주소 부착 (패킷)       │
└──────────────┬───────────────┘
               ▼
┌──────────────────────────────┐
│ [L1] MAC 주소 부착 후 전송     │
├──────────────┬───────────────┤
│              ▼ (인터넷 통과)  │
└──────────────────────────────┘
(수신자는 역순으로 L1부터 L4까지 포장을 벗겨서 데이터를 읽음)
```

### 동작 원리

1. 데이터 생성 (L4): 웹 브라우저가 보낼 메시지를 만듦.
2. 세그먼트 조각 (L3): 덩어리를 쪼개고 목적지 포트 번호(TCP/UDP)를 발라줌.
3. 패킷 생성 (L2): 목적지 IP 주소와 최선형 라우팅 딱지를 붙임.
4. 프레임 전송 (L1): 바로 옆 장비의 MAC 주소를 붙이고 전기/무선 신호로 쏨.
5. 수신 복원: 수신자가 도착한 짐을 역순으로 껍질 까서 원본 확인.

#### 한줄 요약

- 보낼 땐 덧포장해서 쏘고, 받을 땐 껍질을 차례대로 까서 알맹이를 확인한다.

## Ⅴ. 종류 및 비교

<details><summary>용어 설명</summary>

- **TCP/IP vs OSI 7계층**: OSI는 어떻게 만들어야 한다는 이상향(법전)이고, TCP/IP는 실제로 시장을 평정한 현실의 규칙(실전 매뉴얼)이다.

</details>

| 비교 항목 | **TCP/IP 4계층 (실전 압축 근육)** | **OSI 7계층 (이론적 교과서)** |
|:---|:---|:---|
| 성격 | 전 세계를 장악한 **실무 디팩토(De facto) 표준** | 학자들이 정리한 **학술적 참조 모델** |
| 계층 수 | **4개 계층** (L4, L3, L2, L1) | **7개 계층** (엄격하게 쪼갬) |
| 세션/표현 계층 | 쓸데없이 안 나누고 **응용 계층에 짬처리** | 세션(5), 표현(6) 계층으로 명확히 구분 |
| 데이터링크/물리 | **네트워크 접근 계층** 하나로 합침 | 데이터링크(2), 물리(1) 계층 분리 |
| 신뢰성 제어 | 중간 노드는 손 떼고 **종단 호스트(TCP)가 다 함** | 각 계층이 각자 조금씩 신뢰성을 책임지려 함 |

#### 한줄 요약

- OSI는 시험 볼 때나 고장 고칠 때 쓰는 지침서고, TCP/IP는 진짜 돌아가는 인터넷 그 자체다.

## Ⅵ. 실무 고려사항 및 대책

<details><summary>용어 설명</summary>

- **사용자 데이터그램 프로토콜(UDP)**: "가다가 유실돼도 좋으니 묻고 더블로 가!" 하며 유튜브 실시간 스트리밍처럼 속도에 몰빵한 프로토콜이다.
- **최대 전송 단위(MTU, Maximum Transmission Unit)**: 택배 트럭에 한 번에 실을 수 있는 최대 짐 크기(보통 1500바이트)로, 이보다 크면 상자를 쪼개느라 속도가 느려진다.

</details>

| 문제 | 대책 | 효과 |
|:---|:---|:---|
| 실시간 방송인데 TCP 썼다가 렉 걸리고 난리남 | 신뢰성 버리고 속도 올린 **UDP**나 QUIC 프로토콜 투입 | 딜레이 없는 라이브 스트리밍 |
| VPN 껍질이 덧붙어서 트럭 제한(MTU) 초과로 터짐 | 장비의 **MTU 튜닝 및 TCP MSS 클램핑** 설정 | 짐 쪼개짐(단편화) 버그 예방 |
| 인터넷 안 되는데 무지성으로 서버만 재부팅함 | 1층(랜선)$\to$2층(IP)$\to$3층(포트) 올라가는 **상향식 진단** | 헛다리 짚는 시간(MTTR) 단축 |

#### 한줄 요약

- 속도가 생명이면 TCP 대신 UDP 쓰고, 짐이 커서 터지면 MTU 사이즈를 조절해라.

## Ⅶ. 결론

<details><summary>용어 설명</summary>

- **모델 적용 기준(Model Application Criteria)**: 기계 만들고 코드 짤 땐 TCP/IP를 쓰고, 서버 터져서 범인 잡을 땐 OSI 7계층을 잣대로 들이미는 실무 요령이다.

</details>

- **모델 적용 기준** 원칙에 따라, 실제 프로토콜 구현과 운영은 **TCP/IP**를 따르고, 장애 진단과 문서화는 **OSI 계층**에 매핑하는 기조 확립함

#### 한줄 요약

- 구현은 TCP/IP로 가볍게 치고, 장애 나면 OSI 7계층 도면 펼치고 범인을 잡아라.
