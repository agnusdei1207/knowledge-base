## Ⅰ. 개요

<details><summary>용어 설명</summary>

- **TCP(Transmission Control Protocol)**: "느려도 무조건 확실하게!" 분실물 생기면 강력히 다시 받아내는 깐깐한 배달부다.
- **UDP(User Datagram Protocol)**: "어? 잃어버렸어? 내 알 빠 아님" 하고 미친 속도로 패킷만 냅다 던지고 도망가는 폭주족 배달부다.
- **SCTP(Stream Control Transmission Protocol)**: TCP의 깐깐함과 UDP의 속도를 합치고, 길(랜선) 끊어지면 1초 만에 다른 길로 우회하는 차세대 멀티 배달부다.

</details>

- 정의: 4계층(전송 계층)에서 애플리케이션의 요구(신뢰성, 속도, 다중 경로)에 따라 선택해 쓰는 **3대 핵심 전송 프로토콜**
- 배경: 단일 프로토콜만으로는 서비스별 극단적 요구사항(웹 서핑의 꼼꼼함 vs 영상 통화의 신속함)을 **동시에 만족시킬 수 없었기 때문**

#### 한줄 요약

- 데이터 하나도 잃어버리면 안 될 땐 TCP, 끊겨도 무조건 빨라야 할 땐 UDP, 통신사처럼 무조건 안 죽어야 할 땐 SCTP를 쓴다.

## Ⅱ. 특징

<details><summary>용어 설명</summary>

- **바이트 스트림(Byte Stream)**: 내용물 구분 안 하고 그냥 끝없는 컨베이어 벨트(TCP)에 바이트 덩어리를 쏟아붓는 방식이다.
- **데이터그램(Datagram)**: "이거 한 건, 저거 한 건" 편지 봉투 단위(UDP)로 딱딱 잘라서 던지는 방식이다.
- **메시지 경계(Message Boundary)**: 내가 보낸 100바이트와 200바이트를 짬뽕시키지 않고(SCTP/UDP), 보낸 그대로 구분해 주는 선이다.

</details>

- **TCP** 기반 순서와 재전송을 100% 보장하는 **바이트 스트림** 모델로 파일 전송/웹에 적합함.
- **UDP** 기반 수신 확인 절차 없이 **데이터그램** 한정 냅다 던져서, 일부 끊겨도 빠른 실시간 게임/영상에 적합함.
- **SCTP** 기반 TCP처럼 꼼꼼하되, 짐칸(스트림)을 여러 개로 쪼개고 **메시지 경계**까지 완벽히 보존함.

#### 한줄 요약

- TCP는 짬뽕해서 순서대로 밀어 넣고, UDP는 봉투째로 막 던지며, SCTP는 봉투째로 차선 나눠서 꼼꼼하게 보낸다.

## Ⅲ. 구조 및 구성요소

<details><summary>용어 설명</summary>

- **SCTP 연관(Association)**: TCP의 '연결(Connection)'에 대응하는 말로, 랜선(IP)을 여러 개 묶어서 하나의 끈끈한 관계를 맺는 SCTP만의 사기 개념이다.
- **SCTP 4-Way Handshake**: TCP의 3-Way가 해커(SYN Flood)한테 너무 잘 털리니까, 쿠키(Cookie)를 강제 도입해 4번 핑퐁하며 철벽 방어하는 초기 연결 방식이다.

</details>

```text
[ 직관적 비교 L4 전송 프로토콜 구조 ]

[ 애플리케이션 (HTTP, 영상, 통신망 제어) ]
       │          │          │
       ▼          ▼          ▼
   [ TCP ]    [ UDP ]    [ SCTP ]
   (꼼꼼함)   (개빠름)   (다중경로)
       │          │          │
       ▼          ▼          ▼
[ IP 계층 (L3 라우터가 길 찾음) ]
```

| 구성요소 | 직관적 비교 책임 | 비고 |
|:---|:---|:---|
| **TCP (바이트 스트림)** | 잃어버리면 다시 찾고, 순서 꼬이면 **번호표대로 다시 줄 세우는 강박증** | 연결형 (Connection) |
| **UDP (데이터그램)** | 대답 안 기다리고 냅다 던진 다음 **수신자 생사 여부 1도 신경 안 씀** | 비연결형 (Connectionless) |
| **SCTP (멀티스트림)** | 패킷 꼬이면 걔만 대기시키고 **나머지는 안 멈추고 계속 보냄** | 연관형 (Association) |
| **SCTP (멀티호밍)** | 메인 랜선 뽑혀도 **예비 랜선(IP)으로 1초 만에 갈아타서 쏨** | 고가용성 끝판왕 |

#### 한줄 요약

- TCP는 연결(Connection) 하나에 의존하고, SCTP는 여러 길(IP)을 묶은 연관(Association)으로 생존율을 극대화한다.

## Ⅳ. 흐름도

<details><summary>용어 설명</summary>

- **전송 프로토콜 선택(Transport Selection)**: "웹은 TCP, 유튜브 라이브는 UDP, 5G 통신망은 SCTP"처럼 서비스 입맛에 딱 맞게 배달부를 고르는 아키텍트의 결정이다.

</details>

```text
[ 전송 프로토콜 직관적 비교 선택 흐름 ]

[ 전송 요구사항 분석 ]
        │
        ├── (Q: 속도가 짱인가? 중간에 끊겨도 됨?)
        │    └── Yes ──▶ [ UDP 채택 ] (DNS, VoIP, 유튜브 라이브)
        │
        ├── (Q: 랜선 두 개 꽂아서 끊겨도 바로 우회해야 함?)
        │    └── Yes ──▶ [ SCTP 채택 ] (통신사 5G/LTE 신호 제어)
        │
        └── (Q: 속도보다 1바이트도 안 잃어버리는 게 핵심임?)
             └── Yes ──▶ [ TCP 채택 ] (웹, 파일 전송, 이메일)
```

### 동작 원리

- 손실보다 낮은 지연 및 독립 메시지 우선 $\to$ **UDP**
- 종단 간 완벽한 신뢰성 (연속 바이트/단일 경로) $\to$ **TCP**
- 완벽한 신뢰성 + 다중 스트림/경로 (장애 극복) $\to$ **SCTP**

#### 한줄 요약

- 속도 무새는 UDP, 꼼꼼 무새는 TCP, 통신사급 무정지 강박증은 SCTP를 선택한다.

## Ⅴ. 종류 및 비교

<details><summary>용어 설명</summary>

- **멀티호밍(Multihoming)**: 서버에 IP 주소를 여러 개 묶어놔서, 1번 랜선 불타도 2번 랜선으로 안 끊기고 계속 통신하는 SCTP의 사기 스킬이다.
- **멀티스트리밍(Multistreaming)**: 한 파이프 안을 여러 차선으로 쪼개서, 1차선 놈 사고 나도 2, 3차선 놈들은 쌩쌩 달리게 만드는 스킬이다.
- **선두 차단(Head-of-Line Blocking)**: TCP에서 맨 앞에 가던 1번 패킷 잃어버리면, 뒤에 멀쩡히 도착한 패킷들도 1번 올 때까지 꼼짝 못 하고 대기 타는 최악의 병목 현상이다.

</details>

| 전송 프로토콜 | **TCP (모범생)** | **UDP (폭주족)** | **SCTP (엘리트)** |
|:---|:---|:---|:---|
| 연결 방식 | 1:1 단일 연결 (3-Way) | 비연결 (그냥 던짐) | 1:多 **멀티호밍** 연관 (4-Way) |
| 전송 단위 | 뭉뚱그려진 짬뽕 바이트 스트림 | 독립적인 메시지(데이터그램) | 메시지 경계 보존 + **멀티스트리밍** |
| 신뢰성 보장 | 완벽 보장 (재전송, 순서 빡셈) | 알 빠 아님 (응용 앱에서 알아서) | 완벽 보장 + **선두 차단(HoL) 회피** |
| 단점 및 한계 | 하나 잃어버리면 올스톱 **(선두 차단 병목)** | 잃어버려도 절대 복구 안 해줌 | 중간 방화벽/NAT가 SCTP 패킷 다 버림 |

#### 한줄 요약

- TCP는 1등이 안 오면 2등 3등도 못 들어가고 기다리지만(선두 차단), SCTP는 차선을 나눠 2등 3등을 먼저 들여보낸다.

## Ⅵ. 실무 고려사항 및 대책

<details><summary>용어 설명</summary>

- **NAT(Network Address Translation)**: 사설 IP를 공인 IP로 바꿔주는 공유기 기능인데, 옛날 공유기나 방화벽들은 TCP/UDP만 알고 SCTP는 외계어인 줄 알고 다 찢어버린다.

</details>

| 장애/위험 요소 | 원인 분석 | 실무 대책 및 해결방안 | 기대 효과 |
|:---|:---|:---|:---|
| 실시간 방송에 **TCP 썼더니 화면 계속 버퍼링 걸림** | TCP의 깐깐한 재전송/순서 맞추기 | 손실돼도 쌩까고 계속 쏘는 **UDP (RTP/QUIC)** 도입 | 실시간성 확보 및 버퍼링 떡락 |
| 파일 전송에 UDP 썼더니 **다운받은 파일 다 깨짐** | UDP는 재전송과 순서 보장 안 함 | 무조건 100% 무결성을 보장하는 **TCP** 기반 원복 | 파일 무결성 보장 및 앱 복구 로직 덜어냄 |
| TCP 쓰는데 **앞 패킷 하나 날아갔다고 전체 다 멈춤** | TCP 고질병인 **선두 차단(HoL Blocking)** | 차선을 여러 개로 쪼개는 **SCTP (멀티스트림)** 도입 | 패킷 로스에도 다른 스트림 지연 방지 |
| SCTP 썼는데 **방화벽/공유기 통과를 못 하고 뻗음** | 레거시 장비의 **SCTP 포트/NAT 지원 불가** | UDP 기반의 QUIC 도입이나 TCP 터널링 캡슐화 우회 | 구형 인프라 구간 통과 및 호환성 해결 |

#### 한줄 요약

- SCTP가 기술적으론 짱이지만, 중간에 있는 싸구려 공유기들이 패킷을 다 버려버리니 실무에선 조심해서 써야 한다.

## Ⅶ. 결론

<details><summary>용어 설명</summary>

- **전송 프로토콜 결정**: 닭 잡는 데 소 잡는 칼 쓰지 말고, 요구사항(지연 vs 신뢰성)에 딱 맞는 프로토콜을 고르는 아키텍처 진리다.

</details>

- **전송 프로토콜 결정** 원칙에 따라 무결성은 **TCP**, 실시간성은 **UDP**, 다중 경로 고가용성(멀티호밍)은 **SCTP** 활용 적용하는 최적화 기조 확립함

#### 한줄 요약

- 이 세상에 무조건 좋은 프로토콜은 없다. 꼼꼼함(TCP)과 빠름(UDP) 사이에서 최적의 타협점을 찾는 것이 네트워크 엔지니어의 일이다.
