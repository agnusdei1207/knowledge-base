## Ⅰ. 개요

<details><summary>용어 설명</summary>

- **TIME_WAIT**: TCP 연결을 먼저 끊자고 한 쪽이 혹시 모를 오버헤드 패킷을 치우기 위해, 방을 바로 빼지 않고 1~2분 정도 존버하는 잉여 대기 상태다.

</details>

- 정의: TCP 4-Way Handshake에서 **능동 종료(Active Close)** 측이 최종 ACK를 보낸 후, 연결 정보를 **2MSL** 동안 유지하는 소켓 상태
- 배경: 마지막에 보낸 확인 응답(ACK) 유실을 방어하고, 네트워크에 떠도는 **이전 연결의 지연 패킷(Ghost Packet)이 새 연결에 섞이는 대규모 네트워크 장애를 막기 위함** #### 한줄 요약

- 통화를 끊은 뒤 늦게 도착한 옛날 음성이 새 통화에 섞이지 않도록, 방을 바로 빼지 않고 2MSL 동안 오버헤드를 치우며 버티는 시간이다.

## Ⅱ. 특징

<details><summary>용어 설명</summary>

- **능동 종료(Active Close)**: 먼저 "우리 통신 끝내자(FIN)"고 선빵을 날린 쪽이다. 똥 치우는(TIME_WAIT) 독박을 쓴다.
- **2MSL(Twice the Maximum Segment Lifetime)**: 패킷이 네트워크 상에서 살아남을 수 있는 최대 수명(MSL)의 딱 2배 시간이다. 이 시간이 지나면 좀비 패킷이 완벽히 뒤졌다고 확신한다.

</details>

- 상대방이 보낸 **FIN** 대상 대해 최종 ACK를 보냈으나, 이게 유실될 경우를 대비해 **재응답 대기** 활용 탐.
- 연결에 사용된 **4-튜플(출발/목적지 IP와 포트)** 의 즉각적인 재사용을 막아 지연 패킷을 완벽히 격리함.
- 짧은 통신(Short-lived)을 무한 반복하는 서버에서 **TIME_WAIT** 수만 개씩 쌓이면 임시 포트가 고갈되어 서버가 뻗음.

#### 한줄 요약

- TIME_WAIT 자체는 에러가 아니라 오버헤드 패킷을 쳐내는 필수 안전장치다. 포트가 모자랄 때만 문제가 된다.

## Ⅲ. 구조 및 구성요소

<details><summary>용어 설명</summary>

- **4-튜플(4-Tuple)**: 양쪽 IP와 포트 번호 4가지를 합친 식별자다. 소켓 통신의 민증이다.
- **지연 중복 세그먼트(Delayed Duplicate Segment)**: 길 잃고 우주 미아가 됐다가 엉뚱한 타이밍에 뒤늦게 튀어나와 통신을 꼬이게 만드는 오버헤드 패킷이다.

</details>

```text
[ TCP TIME_WAIT 직관적 비교 구조 ]

[ TIME_WAIT 상태 (능동 종료 측) ]
├── [ 4-튜플 식별자 ] (나랑 쟤랑 썼던 포트 번호 기억)
└── [ 2MSL 타이머 ] (타이머 도는 동안은 이 포트 재사용 절대 금지)
         │
         ├── (지연 패킷 도착) ─▶ 걍 무시하고 버림 (격리 성공)
         │
         └── (상대방 FIN 재도착) ─▶ "아까 대답 못 들었냐?" 하고 ACK 다시 쏴줌
```

| 구성요소 | 책임 | 비고 |
|:---|:---|:---|
| **TIME_WAIT 상태** | 먼저 끊자고 한 놈이 **뒷정리 독박 쓰고 버티는 잉여 시간** | 능동 종료자 |
| **2MSL 타이머** | 우주 미아가 된 오버헤드 패킷들이 **뒈질 때까지 기다리는 시한대량 부하** | 보통 1~2분 |
| **4-튜플 식별자** | "이 포트는 당분간 재사용 금지!" 하고 **격리해 둔 민증 번호** | 식별 정보 |

#### 한줄 요약

- 4-튜플 민증을 들고 2MSL 동안 버티면서, 상대방 징징거림(FIN) 받아주고 오버헤드 패킷(지연 세그먼트)을 쳐낸다.

## Ⅳ. 흐름도

<details><summary>용어 설명</summary>

- **LAST_ACK**: 수동 종료(서버) 측이 자기 짐 다 챙겨서 마지막 FIN 보내고, 상대의 최종 ACK를 목 빠지게 기다리는 상태다.

</details>

```text
[ TIME_WAIT 생성 및 십자포화 대처 흐름 ]

[ 능동 종료 측 (먼저 끊음) ]                   [ 수동 종료 측 ]

      (FIN_WAIT_2)                             (LAST_ACK)
           │                                       │
           │◀────── (나도 볼일 다 봄: FIN) ────────┤
           │                                       │
┌──────────────────────────────┐                   │
│ 1. [최종 ACK 전송]           │                   │
│ (ㅇㅋ 알겠음. 수고!)         ├──────────────────▶│ (CLOSED로 정상 방 뺌)
└──────────────┬───────────────┘
               ▼
┌──────────────────────────────┐ (만약 ACK 잃어버리면 상대방이 FIN 또 보냄)
│ 2. [TIME_WAIT 진입]          │◀────── (야 나 FIN 보냈다고!)
│ (2MSL 타이머 시작)           │
└──────────────┬───────────────┘──────────────────▶ (다시 ACK 쏴줌)
               ▼
┌──────────────────────────────┐
│ 3. [연결 상태 제거 (CLOSED)] │
│ (타이머 끝남. 이제 진짜 방 뺌)
└──────────────────────────────┘
```

### 동작 원리

1. 최종 ACK 전송: 상대방 FIN에 응답하며 상대의 깔끔한 종료(LAST_ACK)를 유도.
2. 2MSL 타이머 시작: 오버헤드 패킷 소멸을 대기하며 포트 점유 시작.
3. ACK 재응답: 재전송된 상대 FIN 패킷에 빡치지 않고 최종 확인 반복 수행.
4. 연결 상태 제거: 2MSL 끝나면 4-튜플 해제하고 진정한 자유(CLOSED)를 얻음.

#### 한줄 요약

- ACK 던지고 바로 런(RUN) 치는 게 아니라, 상대가 못 들었을까 봐 2MSL 동안 서성이면서 애프터 서비스(A/S)를 해준다.

## Ⅴ. 종류 및 비교

<details><summary>용어 설명</summary>

- **FIN_WAIT_2**: "헤어지자"고 통보하고 ACK는 받았는데, 상대가 지 짐 챙기느라(FIN) 한참 걸려서 똥줄 타게 기다리는 상태다.
- **CLOSE_WAIT**: 헤어지자고 통보받고 앱한테 "방 빼자"고 했는데, 앱이 병신같이 일 안 해서 무한정 멈춰있는 극혐 상태다.

</details>

| 종료 대기 상태 | **TIME_WAIT (타이머 대기)** | **CLOSE_WAIT (앱 대기)** | **FIN_WAIT_2 (상대 대기)** |
|:---|:---|:---|:---|
| 발생 조건 | 최종 ACK 송신 직후 **(능동 종료)** | 상대 FIN 수신 직후 **(수동 종료)** | 내가 보낸 FIN의 ACK 수신 직후 |
| 직관적 비교 상황 | 똥 치우느라 **2MSL 동안 방 안 빼고 존버함** | 앱이 병신이라 `close()` 안 때려서 **서버가 방을 못 뺌** | 상대가 FIN 안 줘서 **하염없이 기다림** |
| 운영상 리스크 | 많이 쌓이면 **임시 포트 고갈돼서 서버 뻗음** | 닥치고 쌓이면 **FD 고갈로 서버 재부팅해야 됨 (최악)** | 잉여 커넥션 점유 (보통 OS 타임아웃이 쳐냄) |

#### 한줄 요약

- TIME_WAIT은 타이머가 알아서 빼주는 착한 대기실이지만, CLOSE_WAIT은 개발자가 직접 빼기 전까진 영원히 갇혀있는 지옥이다.

## Ⅵ. 실무 고려사항 및 대책

<details><summary>용어 설명</summary>

- **임시 포트(Ephemeral Port)**: 클라이언트가 통신하려고 잠깐 빌려 쓰는 포트. TIME_WAIT가 이거 다 물고 있으면 더 이상 연결 못 맺고 서버 뻗음.
- **TCP 타임스탬프(TCP Timestamp)**: 포트 재사용 꼼수 쓸 때, 오버헤드 패킷(과거)과 진짜 패킷(현재)을 시간으로 구별하려고 도장 찍어놓는 옵션이다.

</details>

| 장애/위험 요소 | 원인 분석 | 실무 대책 및 해결방안 | 기대 효과 |
|:---|:---|:---|:---|
| NGINX 같은 프록시에 **TIME_WAIT가 수만 개 쌓여 뻗음** | 백엔드랑 짧게 연결 맺고 프록시가 먼저 끊음(능동 종료) | Keep-Alive 켜서 세션 재사용하고, 능동 종료 짬 때림 | 프록시 서버의 임시 포트 고갈 원천 차단 |
| TIME_WAIT 꽉 차서 **새로운 접속자가 다 팅김** | TIME_WAIT 상태 포트를 OS가 2MSL 동안 놔주질 않음 | 커널에서 `tcp_tw_reuse` 켜고 **TCP 타임스탬프** 튜닝 | 패킷 안 섞이고 잉여 포트 즉시 재활용 |
| 튜닝한답시고 무지성으로 **TIME_WAIT 타이머를 0으로 쳐버림** | 2MSL 대기 시간을 강제로 없앰 (과도한 부하) | 오버헤드 섞여서 통신 깨지니 절대 건들지 말 것 | 비정상 패킷 난입(RST 발생) 대규모 네트워크 장애 방어 |
| 서버에 **CLOSE_WAIT** 쌓여서 뻗었는데 TIME_WAIT 탓함 | 혼동하기 쉬운 종료 상태에 대한 무지성 오해 | 팩트는 **앱 개발자가 코드 병신같이 짠 거니** 앱 수정 | 인프라 튜닝 삽질 방지 및 근본 원인 해결 |

#### 한줄 요약

- 포트 모자라다고 TIME_WAIT 없애려 들지 말고, `tcp_tw_reuse` 옵션과 타임스탬프로 안전하게 재활용해라.

## Ⅶ. 결론

<details><summary>용어 설명</summary>

- (상단 참조)

</details>

- **TIME_WAIT** 오류가 아닌 안전장치(지연 세그먼트 격리, 최종 ACK 재전송)이며, 대규모 트래픽 환경에서는 무작정 타이머를 줄이는 대신 **TCP 타임스탬프 기반 재사용(Reuse)** 과 **연결 풀링(Keep-Alive)** 으로 포트 고갈을 방어하는 아키텍처 기조 확립함

#### 한줄 요약

- TCP의 깐깐함이 정점을 찍는 상태로, 끝날 때까지 끝난 게 아니라는 철학을 실현하는 필수 불가결한 잉여 시간이다.
