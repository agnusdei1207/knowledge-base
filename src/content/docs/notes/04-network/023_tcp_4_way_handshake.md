## Ⅰ. 개요

<details><summary>용어 설명</summary>

- **TCP 4-Way Handshake(4방향 핸드셰이크)**: 연결을 끊을 때 "나 끊을게", "잠깐만", "나 다 보냄", "ㅇㅋ 잘 가" 하고 4번에 걸쳐 양방향 합의하에 헤어지는 절차다.

</details>

- 정의: 통신을 마친 종단이 서로 FIN과 ACK 플래그를 교환하여 양방향 송신 채널을 독립적으로 닫는 **TCP 연결 해제 절차**
- 배경: 한쪽이 보낼 게 끝났다고 무작정 통신을 끊어버리면, 반대쪽에서 아직 보내지 못한 **남은 데이터가 중간에 날아가는 대참사가 발생하기 때문**

#### 한줄 요약

- 만날 때는 3번 만에 빨리 합의(3-Way)하지만, 헤어질 때는 서로 남은 짐(데이터) 챙기느라 4번(4-Way) 걸린다.

## Ⅱ. 특징

<details><summary>용어 설명</summary>

- **능동 종료(Active Close)**: 먼저 "헤어지자(FIN)" 하고 이별을 통보하는 쪽이다. (주로 클라이언트)
- **수동 종료(Passive Close)**: 차이고 나서 "잠깐만 내 짐 좀 챙길게(데이터 전송)" 하고 나중에 FIN을 보내는 쪽이다. (주로 서버)
- **반쪽 종료(Half-Close)**: 한쪽은 송신 끝났다고 닫았는데, 다른 쪽은 아직 쏠 게 남아서 한쪽 길만 열려있는 애매한 상태다.
- **FIN(Finish)**: "나 이제 보낼 데이터 1도 없음"을 알리는 플래그다.
- **TIME_WAIT**: 먼저 헤어지자고 한 놈이, 나중에 길 잃고 늦게 도착하는 패킷 받을까 봐 찝찝해서 한참 동안 방 안 빼고 존버하는 잉여 상태다.

</details>

- **FIN** 순서 번호를 통해 마지막까지 손실과 재전송을 깐깐하게 추적함.
- **반쪽 종료** 상태를 유지해, 남은 데이터를 끝까지 전송할 수 있게 보장함.
- 먼저 끊은 쪽(능동 종료)은 **TIME_WAIT** 상태에 빠져, 늦게 오는 패킷 섞임을 막고 최종 ACK 유실에 대비함.

#### 한줄 요약

- 남은 데이터를 보낼 수 있게 '반쪽 종료' 상태를 만들고, 마지막 찌꺼기 패킷을 쳐내려고 'TIME_WAIT'로 버틴다.

## Ⅲ. 구조 및 구성요소

<details><summary>용어 설명</summary>

- **FIN_WAIT**: "헤어지자"고 통보하고 나서 상대방 대답 기다리며 속 끓이는 상태다.
- **CLOSE_WAIT**: 통보받고 나서 애플리케이션한테 "우린 끝났대, 짐 싸라" 하고 소켓 닫히기를 기다리는 상태다.
- **LAST_ACK**: 짐 다 싸고 "나도 갈게(FIN)" 보낸 다음, 상대방의 마지막 확인(ACK)을 기다리는 상태다.

</details>

```text
[ TCP 4-Way Handshake 팩트 폭행 상태 변화 구조 ]

[ 클라이언트 (먼저 끊는 놈) ]            [ 서 버 (차이는 놈) ]

ESTABLISHED                           ESTABLISHED
     │                                     │
FIN_WAIT_1 ──(1. 헤어지자: FIN) ─────────▶ │
     │                                     │
FIN_WAIT_2 ◀──(2. 잠시만: ACK) ──────── CLOSE_WAIT (앱 종료 대기)
     │                                     │
     │     ◀──(3. 나도 간다: FIN) ─────── LAST_ACK (마지막 대답 대기)
     │                                     │
TIME_WAIT  ──(4. ㅇㅋ 잘가: ACK) ────────▶ CLOSED
(2MSL 대기)                                │
     │                                     ▼
  CLOSED                                (완전 종료)
```

| 구성요소 | 팩트 폭행 책임 | 비고 |
|:---|:---|:---|
| **능동 종료 측** | 먼저 이별 통보(FIN) 하고, 나중에 **TIME_WAIT로 똥 치우며 기다리는 놈** | 주로 Client |
| **수동 종료 측** | 통보받고 **CLOSE_WAIT** 상태로 남은 짐 다 챙기고(FIN) 방 빼는 놈 | 주로 Server |
| **반쪽 종료** | 한 놈은 송신을 끝냈지만, 다른 놈은 보낼 게 남아서 **반만 닫힌 상태** | Half-Close |
| **TIME_WAIT** | 다음 연결이랑 패킷 섞일까 봐 **일정 시간(2MSL) 동안 방 안 빼고 버팀** | 포트 점유 |

#### 한줄 요약

- 먼저 끊은 쪽은 FIN_WAIT 하다가 TIME_WAIT로 남고, 늦게 끊는 쪽은 CLOSE_WAIT 하다가 LAST_ACK로 끝낸다.

## Ⅳ. 흐름도

<details><summary>용어 설명</summary>

- **2MSL(Twice the Maximum Segment Lifetime)**: 네트워크 상에서 패킷이 끈질기게 살아남을 수 있는 최대 시간(MSL)의 딱 2배만큼, 미련 버리고 완벽히 소켓을 죽일 때까지 기다리는 쿨타임(보통 1~2분)이다.

</details>

```text
[ TCP 4-Way Handshake 십자포화 흐름 ]

능동 종단: 1. [능동 FIN 전송] 
          (나 보낼 거 다 끝났음)
             |
             v
수동 종단: 2. [ACK 전송 및 반쪽 종료]
          (ㅇㅋ 알겠음. 나 남은 거 마저 보낼게)
             |
             `-- (남은 데이터 싹 다 전송 중...)
                        |
                        v
수동 종단: 3. [수동 FIN 전송]
          (나도 다 보냈음. 이제 진짜 끊자)
             |
             v
능동 종단: 4. [최종 ACK 전송]
          (ㅇㅋ 수고!)
             |
             v
능동 종단: 5. [2MSL (TIME_WAIT) 대기]
          (혹시 패킷 늦게 올까 봐 좀 더 버팀)
             |
             `-- TIME_WAIT 끝나면 방 뺌 (CLOSED)
```

### 동작 원리

1. 능동 FIN 전송: 능동 종단(주로 클라)이 자기 데이터 끝났다고 FIN 날림.
2. ACK 전송 및 반쪽 종료: 수동 종단(주로 서버)이 알았다고 ACK 보내고 CLOSE_WAIT 진입 (반쪽 종료).
3. 수동 FIN 전송: 수동 종단도 남은 데이터 마저 털어내고 소켓 닫으며 FIN 날림.
4. 최종 ACK 전송: 능동 종단이 "진짜 끝"이라고 마지막 ACK 날려줌.
5. 2MSL 대기 (TIME_WAIT): 능동 종단이 지연 패킷 섞이는 거 막으려고 2MSL 동안 존버타다 죽음.

#### 한줄 요약

- FIN 던지고 $\to$ ACK 받고 (반쪽 종료) $\to$ 남은 거 다 보내면 다시 FIN 던지고 $\to$ ACK 받고 (TIME_WAIT) 끝난다.

## Ⅴ. 종류 및 비교

<details><summary>용어 설명</summary>

- **임시 포트(Ephemeral Port)**: 클라이언트가 서버랑 연결할 때 OS가 1024번 이상부터 남는 번호 아무거나 던져주는 일회용 출발지 포트다.

</details>

| 종료 역할 | 핵심 상태 전이 | 운영상 빡치는 위험 요소 |
|:---|:---|:---|
| **능동 종료 (먼저 끊음)** | `FIN_WAIT_1/2` $\to$ **TIME_WAIT** $\to$ `CLOSED` | 짧은 세션 많으면 **TIME_WAIT 포트 고갈 현상** 발생 |
| **수동 종료 (나중에 끊음)**| `CLOSE_WAIT` $\to$ `LAST_ACK` $\to$ `CLOSED` | 개발자 코딩 븅신같이 하면 **CLOSE_WAIT** 쌓여서 서버 뻗음 |

#### 한줄 요약

- 먼저 끊은 놈(클라)은 TIME_WAIT가 쌓여서 골치고, 늦게 끊는 놈(서버)은 CLOSE_WAIT가 쌓여서 골치다.

## Ⅵ. 실무 고려사항 및 대책

<details><summary>용어 설명</summary>

- **SO_REUSEADDR**: 포트가 TIME_WAIT 상태로 묶여있어도, "아 몰라 그냥 새로 연결할 때 이 포트 다시 쓸래!" 하고 억지로 재사용하게 해주는 튜닝 옵션이다.

</details>

| 장애/위험 요소 | 원인 분석 | 실무 대책 및 해결방안 | 기대 효과 |
|:---|:---|:---|:---|
| 서버에 **CLOSE_WAIT** 상태가 수만 개 쌓여 뻗음 | 개발자가 소켓 `close()` 코드 안 짬 (어플리케이션 버그) | 소켓 닫는 코드(Exception 처리 포함) 빡세게 점검/수정 | 파일 서술자(FD) 및 소켓 자원 누수 완벽 방지 |
| 로드 밸런서/프록시에 **TIME_WAIT** 꽉 차서 마비됨 | 짧은 연결(Short-lived) 대량 발생 시 임시 포트 고갈 | **SO_REUSEADDR** 옵션 등 TIME_WAIT 포트 재사용 튜닝 | 신규 접속 불가(포트 고갈) 대참사 해결 |
| 마지막 보낸 ACK가 유실돼서 **상대가 FIN 계속 보냄** | 4단계 최종 ACK 유실 | **2MSL (TIME_WAIT)** 시간 동안 존버하면서 ACK 재전송 | 상대방(LAST_ACK)의 깔끔한 종료(CLOSED) 유도 |
| 데이터 덜 보냈는데 상대가 냅다 **RST** 날리고 도망감 | 비정상적 강제 종료(Abort) | 정상적인 4-Way 타도록 **반쪽 종료(Half-Close)** 원칙 활용 | 중간에 짤려서 데이터 날아가는 대참사 방지 |

#### 한줄 요약

- 서버가 뻗으면 CLOSE_WAIT(개발자 잘못)인지, TIME_WAIT(인프라 포트 고갈)인지부터 팩트 체크해라.

## Ⅶ. 결론

<details><summary>용어 설명</summary>

- (상단 참고)

</details>

- 반대 방향 데이터가 남으면 **반쪽 종료(Half-Close)**를 사용하고, 비정상 패킷 충돌을 막기 위해 최종 ACK 후 **TIME_WAIT(2MSL)** 동안 **임시 포트**를 유지하는 아키텍처 기조 확립함

#### 한줄 요약

- 4-Way Handshake는 남은 데이터를 끝까지 보장하고, 찌꺼기 패킷을 안전하게 치우기 위한 배려의 프로토콜이다.
