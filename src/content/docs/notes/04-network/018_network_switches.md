## Ⅰ. 개요

<details><summary>용어 설명</summary>

- **스위칭 계층**: 택배(패킷)를 분류할 때 동네 이름(L2)만 볼지, 시/도 주소(L3)를 볼지, 내용물(L7)까지 싹 다 까볼지를 결정하는 스위칭 판단 기준이다.
- **L2 스위치(Layer 2 Switch)**: MAC 주소(주민번호)만 보고 같은 동네(VLAN) 안에서 1차원적으로 기계적 스위칭을 하는 단순 배달 장비다.
- **L3 스위치(Layer 3 Switch)**: IP 주소를 까보고 다른 동네(서브넷)로 쏴주는 라우터 역할을 겸비한 똑똑한 스위치다.
- **L4 스위치(Layer 4 Switch)**: 포트 번호(TCP/UDP)를 보고 "얘는 웹이니까 A서버, 얘는 DB니까 B서버" 하고 부하 분산(SLB)을 해주는 교통경찰이다.
- **L7 스위치(Layer 7 Switch)**: 앱 데이터(URL, 쿠키, 헤더)까지 다 까보고 "모바일 접속이네? 전용 서버로 가" 하고 깐깐하게 분기하는 끝판왕이다.

</details>

- 정의: 캡슐화된 패킷의 어느 깊이(계층)까지 까보고 포워딩할지 결정하는 **계층별 네트워크 장비 분류 기준**
- 배경: MAC이나 IP 주소만 보는 구식 스위칭만으로는 폭증하는 웹 트래픽의 **부하 분산(SLB)과 콘텐츠 기반 정밀 통제를 처리할 수 없었기 때문**

#### 한줄 요약

- 겉봉투만 보고 던질지(L2/L3), 내용물까지 샅샅이 까보고 던질지(L4/L7)에 따라 장비 급이 나뉜다.

## Ⅱ. 특징

<details><summary>용어 설명</summary>

- **MAC(Media Access Control)**: 같은 링크의 기기를 식별하는 48비트 물리적 주소다.
- **IP(Internet Protocol)**: 서브넷을 넘나들며 길을 찾게 해주는 32비트 논리적 주소다.
- **URL(Uniform Resource Locator)**: L7에서 까보는 최종 목적지 정보로, 웹 자원의 위치와 접근 방식을 나타낸다.

</details>

- L2/L3 스위치는 겉면의 **MAC/IP 주소**만 무지성으로 읽고 포트나 다음 홉을 빠르게 결정(빠르지만 멍청함).
- L4 스위치는 IP+포트 조합인 **5-튜플(Tuple)**을 분석해 트래픽을 서버 여러 대에 골고루 분산(SLB).
- L7 스위치는 OSI 7계층 끝까지 다 까서 **URL, 헤더, 쿠키** 값을 보고 앱 레벨에서 정밀하게 분기(똑똑하지만 CPU 터짐).

#### 한줄 요약

- 계층이 올라갈수록 더 똑똑하게 트래픽을 찢어줄 수 있지만, 그만큼 장비가 해야 할 노가다(검사/상태 유지)가 많아진다.

## Ⅲ. 구조 및 구성요소

<details><summary>용어 설명</summary>

- **포워딩 정보 베이스(FIB)**: L3 스위치가 라우팅 테이블을 하드웨어 칩(ASIC)에 구워놓고 쳐다보는 초고속 컨닝 페이퍼다.
- **5-튜플(Five-tuple)**: "출발지 IP, 출발지 포트, 목적지 IP, 목적지 포트, 프로토콜" 이 5개 조합으로 통신 세션을 완벽히 식별하는 지문이다.

</details>

```text
[ OSI 7계층별 스위치 팩트 폭행 구조 ]

[ L7 스위치 ] ── (URL/쿠키/헤더 까봄: "이미지는 캐시 서버로 가라")
     │
[ L4 스위치 ] ── (IP+포트 까봄: "웹 트래픽이네? 1,2,3번 서버에 번갈아 뿌려")
     │
[ L3 스위치 ] ── (IP 까봄: "192.168.20.0 대역이네? 저쪽 라우터로 넘겨")
     │
[ L2 스위치 ] ── (MAC 까봄: "AA:BB:CC:DD 목적지네? 3번 포트로 쏴")
```

| 구성요소 | 팩트 폭행 책임 | 판단 기준 |
|:---|:---|:---|
| **L2 스위치** | MAC 테이블 보고 **같은 동네(VLAN) 안에서 스위칭** | 48비트 MAC 주소 |
| **L3 스위치** | 라우팅 테이블(FIB) 보고 **다른 동네(서브넷)로 넘겨줌** | 32비트 IP 주소 |
| **L4 스위치** | TCP/UDP 포트 보고 **여러 서버로 부하 분산(SLB)** | **5-튜플**, 세션 상태 |
| **L7 스위치** | 앱 내용 싹 다 까보고 **콘텐츠별로 서비스 정밀 분기** | URL, 쿠키, 헤더, 페이로드 |

#### 한줄 요약

- L2/L3는 주소만 보고 배달하고, L4/L7은 포트랑 내용물 보고 어디로 보낼지 통제한다.

## Ⅳ. 흐름도

<details><summary>용어 설명</summary>

- **최소 계층 선택(Minimum Required Layer Selection)**: "단순 배달은 L2 쓰고, 복잡한 분기는 L7 써라"처럼 목적에 맞게 가성비(처리 속도)가 제일 좋은 장비를 고르는 설계 원칙이다.

</details>

```text
[ 목적에 따른 스위칭 계층 선택 알고리즘 ]

[ 스위치 도입 목적 분석 ]
            │
            ▼
    (단순히 사내 PC들 연결할 건가?)
    ├── Yes ──▶ [ L2 스위치 도입 ] (MAC 기반 스위칭)
    │
    ▼ No
    (부서 간(VLAN 간) 라우팅이 필요한가?)
    ├── Yes ──▶ [ L3 스위치 도입 ] (IP 기반 하드웨어 라우팅)
    │
    ▼ No
    (웹 서버 트래픽 부하 분산(SLB)이 필요한가?)
    ├── Yes ──▶ [ L4 스위치 도입 ] (포트 기반 로드 밸런싱)
    │
    ▼ No
    (PC/모바일 구분하고 URL별로 찢을 건가?)
    └── Yes ──▶ [ L7 스위치 도입 ] (애플리케이션 페이로드 분석)
```

### 동작 원리

- MAC 주소•같은 링크 $\to$ **L2 스위치**
- IP 프리픽스•서브넷 경로 $\to$ **L3 스위치**
- 포트•5-튜플•서버 연결 $\to$ **L4 스위치**
- URL•헤더•응용 내용 $\to$ **L7 스위치**

#### 한줄 요약

- 필요한 통제 수준(주소, 포트, 페이로드)에 맞춰 **최소 계층 선택** 원칙을 적용해 장비를 깐다.

## Ⅴ. 종류 및 비교

<details><summary>용어 설명</summary>

- **TLS 종료(TLS Termination)**: L7 스위치가 HTTPS 암호화 패킷을 직접 풀고(복호화) 내용물을 까본 다음, 다시 암호화해서 서버로 보내주는 개고생 작업이다.

</details>

| 스위칭 계층 | **L2 / L3 스위치 (단순 배달부)** | **L4 스위치 (교통경찰)** | **L7 스위치 (보안 검색대)** |
|:---|:---|:---|:---|
| 적용 기준 | 같은 망/다른 망 **단순 경로 전달** | 트래픽 쏠림 막는 **서버 부하 분산** | 콘텐츠 기반 **정밀 응용 서비스 분기** |
| 핵심 특징 | 패킷 겉면(MAC/IP)만 보고 바로 던짐 | 5-튜플, 포트 상태 유지하며 로드밸런싱 | 짐칸 다 까보고(URL/Header) 조작함 |
| 한계/단점 | 정밀한 트래픽 분산 절대 불가 | 애플리케이션 계층(페이로드) 조작 불가 | **TLS 종료(복호화)** 등 CPU/메모리 부하 극심 |

#### 한줄 요약

- 주소만 볼 거면 L2/L3, 포트로 찢을 거면 L4, 내용물 뜯어보고 SSL/TLS까지 풀어헤칠 거면 L7을 쓴다.

## Ⅵ. 실무 고려사항 및 대책

<details><summary>용어 설명</summary>

- **상태 확인(Health Check)**: L4/L7 스위치가 서버들한테 "살아있냐?" 하고 주기적으로 핑이나 HTTP 요청을 때려서, 죽은 서버한텐 트래픽 안 보내고 빼버리는 모니터링 기술이다.
- **상태 동기화(State Synchronization)**: L4 스위치 두 대를 이중화했을 때, 1번 장비가 죽으면 2번 장비가 세션을 바로 이어받게 실시간으로 세션표를 복사해두는 짓이다.

</details>

| 장애/위험 요소 | 원인 분석 | 실무 대책 및 해결방안 | 기대 효과 |
|:---|:---|:---|:---|
| L4에 물려있는 **서버가 죽었는데 계속 접속 넘겨줌** | 서버 생사 확인 안 함 | L4/L7 스위치에 정기적 **상태 확인(Health Check)** 활성화 | 죽은 서버 즉시 배제 및 무중단 서비스 |
| 메인 L4 장비 뻗자마자 **유저들 로그인 세션 다 날아감** | 이중화 장비 간 세션 테이블 비동기 | Active-Standby 장비 간 **상태 동기화(Session Sync)** 필수 | 절체 시에도 로그인/결제 끊김 방지 |
| HTTPS 암호화 트래픽이라 **L7 스위치가 내용을 못 까봄** | 페이로드 암호화 | L7 스위치에 인증서 올리고 **TLS 종료(Termination)** 구성 | 암호화 트래픽 정밀 분석 및 분기 가능 |
| 이벤트 터져서 봇 몰리자 L4 **세션 테이블(메모리) 꽉 차서 뻗음** | 세션(5-튜플) 허용치 초과 | 세션 한도(Limit) 및 Idle Timeout(만료시간) 짧게 튜닝 | 비정상 세션 칼같이 자르고 장비 보호 |

#### 한줄 요약

- L4/L7 쓸 땐 반드시 헬스 체크로 죽은 서버 걸러내고, 장비 이중화할 땐 세션 동기화로 빡세게 묶어라.

## Ⅶ. 결론

<details><summary>용어 설명</summary>

- **스위칭 계층 결정**: 닭 잡는 데 소 잡는 칼 안 쓰듯이, 트래픽 분기 목적에 맞춰 가성비(처리 속도 vs 분석 깊이)가 제일 좋은 스위치를 고르는 설계 진리다.

</details>

- **스위칭 계층 결정**은 필요한 분기 정보와 상태 유지 비용을 철저히 계산하여 **최소 계층 선택** 원칙을 적용하는 아키텍처 설계 기조 확립함

#### 한줄 요약

- 무작정 비싼 L7 산다고 좋은 게 아니다. 목적에 딱 맞는 최소 계층 장비를 골라야 돈과 CPU를 아낀다.
