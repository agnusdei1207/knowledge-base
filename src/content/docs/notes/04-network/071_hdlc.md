## Ⅰ. 개요

<details><summary>용어 설명</summary>

- **HDLC (고급 데이터 링크 제어)**: 데이터에 앞뒤 꼬리표(플래그)를 붙여서 프레임 단위로 묶고, 에러 나면 몇 번부터 다시 보낼지(흐름/오류 제어) 강력히 통제하는 데이터 링크 계층의 조상님 프로토콜이다.
- **비트 지향 프로토콜**: 글자(문자) 단위가 아니라, 0과 1의 연속된 '비트 패턴' 자체를 인식해서 프레임의 시작과 끝을 칼같이 끊어 읽는 방식이다.

</details>

- 정의: **HDLC** 기반 동기 회선에서 끊임없이 날아오는 비트 스트림을 프레임으로 자르고, 전송 순서와 에러를 깐깐하게 통제하는 **비트 지향 프로토콜**이다.
- 배경: 0과 1이 쉬지 않고 날아오면 수신자가 "어디서부터 읽어야 돼?" 하고 장애 혼선에 빠지니까, **01111110 이라는 특수 패턴(플래그)을 앞뒤로 박아서 경계를 명확히 나누려고 등장했다.** #### 한줄 요약

- 끝없이 쏟아지는 0과 1의 늪에서 꼬리표(플래그)를 달아 데이터를 자르고, 번호표를 붙여 에러 없이 나르는 통신 규칙이다.

## Ⅱ. 특징

<details><summary>용어 설명</summary>

- **경계 투명성 (Bit Stuffing)**: 원본 데이터에 우연히 플래그(01111110)랑 똑같은 패턴이 있으면 수신자가 프레임이 끝난 줄 알고 착각하니까, 송신자가 1이 다섯 번 나오면 강제로 0을 쑤셔 넣어서 패턴을 망가뜨리는 꼼수(비트 채움)다.
- **I / S / U 프레임**: I-프레임은 사용자 짐(데이터) 나르는 용, S-프레임은 "잘 받았다/다시 보내라" 훈수용, U-프레임은 처음 연결 맺고 끊는 관리용 프레임이다.
- **FCS (프레임 검사 순서)**: 프레임 꼬리에 달아놓은 암호 코드(CRC)로, 도착했을 때 비트 하나라도 깨졌으면 귀신같이 찾아내서 폐기해 버리는 에러 검문소다.

</details>

- **비트 채움(Bit Stuffing) 신공**: 진짜 플래그 말고는 절대 플래그 패턴이 안 나오도록, 데이터 속에 1이 5번 나오면 무조건 0을 끼워 넣어 혼선을 차단한다 (**경계 투명성** 확보).
- **프레임 역할 분리**: 데이터 싣는 놈(**I-프레임**), 에러 훈수 두는 놈(**S-프레임**), 링크 관리하는 놈(**U-프레임**) 세 종류로 나눠서 통신 룰을 체계화했다.
- **FCS 에러 철벽 방어**: 프레임 꼬리표에 다항식 연산 결과(**FCS**)를 달아서, 1비트라도 깨지면 엄격한 통제없이 폐기하고 순서 번호로 재전송을 때린다.

#### 한줄 요약

- 비트 끼워 넣기로 꼬리표 착각을 막고, 프레임을 3가지 용도로 쪼개며, 꼬리표(FCS)로 에러를 잡는 지능적인 프로토콜이다.

## Ⅲ. 구조 및 구성요소

<details><summary>용어 설명</summary>

- **Control (제어) 필드**: 이 프레임이 I인지 S인지 U인지 정체성을 밝히고, 송신 번호랑 수신 번호표를 달아서 데이터 순서가 꼬이지 않게 멱살 잡는 핵심 헤더다.

</details>

```text
[ HDLC 프레임 직관적 비교 구조 ]

[ 1. 시작 플래그 (01111110) ] ── (수신자야 여기서부터 프레임 시작이다. 주목!)
      │
      ▼
[ 2. 주소부 & 제어부 (Address & Control) ] ── (이거 3번 단말기로 가는 거고, 데이터 싣는 I-프레임이다)
      │
      ▼
[ 3. 정보부 (Information) ] ── (진짜 알맹이 사용자 데이터 덩어리)
      │
      ▼
[ 4. FCS & 종료 플래그 (01111110) ] ── (에러 검사 끝! 여기서 프레임 닫는다)
```

| 구성요소 | 책임 | 비고 |
|:---|:---|:---|
| **시작 Flag** | 01111110 고정 패턴으로 **"여기서부터 프레임 시작이다" 하고 알람 울려줌** | Flag |
| **Address** | 1:N 통신할 때 **"이거 어느 단말기한테 가는 거냐" 하고 번호표 붙임** | Address |
| **Control** | 프레임 성격(I/S/U) 정하고 **순서 번호 매겨서 순서 안 꼬이게 멱살 잡음** | Control |
| **Information**| 파일, 메시지 등 **실제 사용자가 꽉꽉 눌러 담은 알맹이 데이터** | Payload |
| **FCS & 종료 Flag**| 오류 오버헤드 점검하고 **01111110 패턴으로 "프레임 무사히 끝났다" 선언함** | FCS / Flag |

#### 한줄 요약

- 01111110 깃발로 앞뒤 묶고, 가운데에 목적지(주소), 성격(제어), 알맹이(정보), 검문소(FCS)를 차례로 줄 세운 구조다.

## Ⅳ. 흐름도

<details><summary>용어 설명</summary>

- **ACK (확인 응답)**: 수신자가 "방금 거 에러 없이 잘 받았고, 다음번엔 3번 프레임 보내라" 하고 쿨하게 확인 도장 찍어주는 거다.
- **REJ (거부/재전송 요구)**: 수신자가 "야! 2번 프레임 깨졌다, 2번부터 싹 다 다시 보내!" 하고 빠꾸 먹이는 강력한 피드백이다.

</details>

```text
[ HDLC 에러 통제 십자포화 흐름 ]

┌──────────────────────────────┐
│ 1. [U-프레임 링크 수립]      │
│ (통신 시작: U-프레임 보내서 야 통신 모드(ABM 등) 켜라! 세팅함)
└──────────────┬───────────────┘
               ▼
┌──────────────────────────────┐
│ 2. [I-프레임 데이터 전송]    │
│ (송신: 비트 채움 꼼수 켜고 FCS 달아서 진짜 데이터 빵 쏨)
└──────────────┬───────────────┘
               ▼
┌──────────────────────────────┐
│ 3. [비트 제거 및 프레임 추출]│
│ (수신: 강제로 채워 넣은 0비트 뽑아내고 원본 복구함)
└──────────────┬───────────────┘
               ▼
┌──────────────────────────────┐
│ 4. [FCS 검사 (체크)]    │
│ (수신: FCS 다항식 돌려서 에러 한 개라도 있는지 빡세게 뒤져봄)
└──────────────┬───────────────┘
               ▼
┌──────────────────────────────┐
│ 5. [S-프레임 피드백 (ACK/REJ)]
│ (수신: 멀쩡하면 ACK! 에러 났으면 REJ 때려서 재전송 요구)
└──────────────────────────────┘
```

### 동작 원리

1. U-Frame 링크 설정: 통신 시작 전에 **U-Frame** 주고받아 동작 모드(NRM/ABM)와 순서 번호를 초기화함.
2. 프레임·FCS 전송: 송신자가 데이터(I-Frame)에 비트 채움을 먹이고 **FCS** 꼬리표를 달아 전송함.
3. 수신 프레임 전달: 수신 측이 프레임을 받아 강제로 끼워진 0비트를 뽑아내고(비트 제거) 원본을 풂.
4. FCS 검사: 프레임 꼬리의 **FCS** 활용 뜯어서 에러가 났는지 칼같이 검사함.
5. ACK/REJ 피드백: 정상이면 다음 번호를 달아 **ACK** 활용 쏘고, 에러면 **REJ** 활용 쏴서 해당 번호부터 재전송시킴.

#### 한줄 요약

- 통신 모드 세팅 $\to$ 데이터 쏘기 $\to$ 수신자가 에러 검사 후 $\to$ 정상이면 패스, 에러 나면 빠꾸 먹이는 흐름이다.

## Ⅴ. 종류 및 비교

<details><summary>용어 설명</summary>

- **NRM (정규 응답 모드)**: 왕(주국)이 "야 너 말해" 하고 허락해야만 쫄따구(종국)가 데이터를 보낼 수 있는 씹선비 갑을 모드다.
- **ARM (비동기 응답 모드)**: 여전히 갑을 관계지만, 쫄따구가 급할 땐 굳이 허락 안 받고 먼저 데이터를 날릴 수 있게 약간 풀어준 모드다.
- **ABM (비동기 균형 모드)**: 주국/종국 계급장 떼고, 양쪽 다 대등하게 눈치 안 보고 데이터를 막 쏘는 현대식 1:1 자유 민주주의 모드다.

</details>

| 구분 | **NRM (정규 응답 모드)** | **ARM (비동기 응답 모드)** | **ABM (비동기 균형 모드)** |
|:---|:---|:---|:---|
| 핵심 특징 | 허락받아야 말하는 **군대식 갑을 통신** | 허락 없이 찔러볼 순 있는 **반항아 통신** | 계급장 떼고 맞짱 뜨는 **1:1 민주주의 통신** |
| 적용 기준 (통제권) | **주국(Master)** 이 강력히 전체 통제함 | 여전히 주국이 짱이지만 쪼끔 풀어줌 | 주국/종국 구분 없이 **대등하게 양방향(Full-Duplex) 쏨** |
| 종국 전송 권한 | 주국이 **폴링(허락)** 해야만 전송 가능 | 주국 허가 없이 **자발적 전송 완전 지원** | 서로 눈치 안 보고 아무 때나 맘대로 보냄 |
| 치명적 한계 | 주국 장애 나면 통신망 전체가 다 뻗음 | 주국과 종국 간 책임 소재가 꼬임 | 1:1 통신 전용이라 1:N 중앙 통제는 불가능 |

#### 한줄 요약

- 꼰대식 NRM, 반항아 ARM을 거쳐 현대 인터넷의 조상격인 계급장 뗀 1:1 통신(ABM)으로 진화했다.

## Ⅵ. 실무 고려사항 및 대책

<details><summary>용어 설명</summary>

- **순서 상태 불일치**: 송신자는 3번 보냈다고 우기는데 수신자는 2번 기다리고 있어서 상호 메시지 교환이 엇갈려, 재전송 범위가 완전히 꼬여버리는 치명적 에러다.

</details>

| 장애/위험 요소 | 원인 분석 | 실무 대책 및 해결방안 | 기대 효과 |
|:---|:---|:---|:---|
| 링크 수립 실패하고 **통신 연결 엄격한 통제없이 거부당함** | 송신자는 ABM 모드 쏘는데 수신자는 NRM 모드 켜놔서 양단 프로토콜 핀트가 어긋남 | 장비 설정 들어가서 **NRM, ARM, ABM 모드 양단 똑같이 억지로 세팅해 줌** | 엉뚱한 모드 충돌로 인한 상호 메시지 교환 에러 막고 링크 수립 성공 |
| 데이터 안에 01111110 껴서 **프레임이 강제로 뚝 끊김** | 사용자 데이터 안에 우연히 플래그(01111110)랑 똑같은 패턴이 들어가서 수신자가 프레임 끝난 줄 착각함 | 송신단 칩셋에서 무조건 1 다섯 개 뒤에 0 박아 넣는 **비트 채움(Bit Stuffing) 켬** | 프레임 경계 보장하고 어이없이 데이터 끊기는 사고 원천 차단 |
| 양단이 서로 **보낸 번호랑 받는 번호가 달라서 꼬임** | ACK/REJ 피드백이 중간에 유실돼서 '확인 응답 순서 상태'가 꼬여버림 (순서 상태 불일치) | 타임아웃 걸고 응답 없으면 제어 필드(Control) 까보고 **해당 번호부터 강제 재전송 때림** | 꼬인 순서 풀고 데이터 무손실 전달 및 복구 확보 |

#### 한줄 요약

- 플래그 착각 방지용 비트 채움 확실히 켜고, 모드 양쪽 똑같이 맞추고, 번호 꼬이면 타임아웃으로 강제 재전송해라.

## Ⅶ. 결론

<details><summary>용어 설명</summary>

- (상단 참조)

</details>

- 연속 비트열의 경계를 명확히 구분하고 에러를 통제하기 위해, **플래그 기반 비트 채움** 및 **Control 필드 재전송(ACK/REJ)** 을 결합한 HDLC 프로토콜 기조 확립함

#### 한줄 요약

- HDLC는 비트의 바다 속에서 깃발(플래그)을 꽂아 질서를 만들고, 에러 나면 강력히 재전송시키는 데이터 링크 계층의 헌법이다.
