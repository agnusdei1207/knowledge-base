## Ⅰ. 개요

<details><summary>용어 설명</summary>

- **소프트웨어 정의 네트워킹(Software-Defined Networking, SDN)**: 네트워크 장비의 제어 평면(Control Plane)과 데이터 평면(Data Plane)을 물리적/논리적으로 분리하고, 개방형 표준 API를 통해 중앙 집중식 소프트웨어 컨트롤러로 네트워크 전체 트래픽 흐름을 프로그래밍 제어하는 네트워크 아키텍처.
- **제어 평면(Control Plane)과 데이터 평면(Data Plane)**: 라우팅 경로 결정, 토폴로지 학습, 정책 수립을 담당하는 제어 계층과, 확정된 흐름 규칙(Flow Rule)에 따라 패킷을 고속 스위칭하는 포워딩 계층의 분리 구조.

</details>

- 정의/개념: 기존 네트워크 장비 내부의 경로 제어 로직을 중앙 소프트웨어(**SDN Controller**)로 집중화하고, 하드웨어 스위치는 표준 사우스바운드 API(**OpenFlow/P4**)를 통해 전달 기능만을 전담하도록 추상화한 **개방형 네트워크 가상화 기술**
- 배경/필요성: 장비별 개별 CLI 수동 설정 방식의 운영 비효율을 극복하고, 클라우드 데이터센터의 대규모 멀티 테넌트 트래픽을 전역적 시야(Global View)에서 동적 자동화 제어할 요구

#### 한줄 요약
- 제어 평면과 데이터 평면을 분리하여 중앙 컨트롤러의 소프트웨어 프로그래밍으로 네트워크를 통합 제어한다.

## Ⅱ. 특징

<details><summary>용어 설명</summary>

- **전역 토폴로지 가시성(Global Network Visibility)**: 중앙 컨트롤러가 분산된 모든 스위치의 링크 상태, 포트 통계, 트래픽 부하 지표를 실시간 수집하여 전체 네트워크 지도를 단일 뷰로 파악하는 능력.
- **사우스바운드 / 노스바운드 API(SBI / NBI)**: 상위 비즈니스 응용 프로그램과 컨트롤러 간 인터페이스(NBI: RESTful) 및 컨트롤러와 하위 물리/가상 스위치 간 제어 인터페이스(SBI: OpenFlow, NETCONF, gNMI).

</details>

- **제어와 전달의 물리적 디커플링(Decoupling)**: 스위치는 단순화된 화이트박스 하드웨어로 전환되고, 라우팅 인텔리전스는 중앙 컨트롤러 소프트웨어로 격상
- **전역 최적화 트래픽 엔지니어링(Global TE)**: 국소적 홉별 라우팅의 한계를 탈피하여 전역 네트워크 혼잡도를 반영한 최적의 우회 경로 및 QoS 동적 주입
- **소프트웨어 기반 프로그래머블 자동화(NetDevOps)**: NBI API 및 코드를 통해 방화벽, QoS, 로드 밸런싱 정책을 전체 인프라에 실시간 무중단 배포

#### 한줄 요약
- 평면 분리, 전역 가시성 기반 트래픽 최적화, 개방형 API를 통한 프로그래머블 자동화를 제공한다.

## Ⅲ. 구조 및 구성요소

<details><summary>용어 설명</summary>

- **SDN 컨트롤러(SDN Controller)**: 네트워크의 운영체제(Network OS) 역할을 수행하며, 전역 상태 데이터베이스(Topology DB)를 유지하고 스위치에 흐름 테이블(Flow Table)을 프로그래밍하는 핵심 두뇌.
- **OpenFlow(오픈플로우)**: ONF 표준 사우스바운드 프로토콜로, 패킷의 12~40개 헤더 필드(MAC, IP, Port 등)를 매칭하여 포워딩/수정/폐기 액션을 지시하는 인터페이스.

</details>

```text
[ 1. 응용 계층 (Application Layer) ] ──▶ (네트워크 가상화, 보안 방화벽, 전역 QoS 앱)
                  │
                  ▼ (노스바운드 API - NBI: RESTful, gRPC)
[ 2. 제어 계층 (SDN Controller) ] ────▶ (전역 토폴로지 맵, 경로 계산 엔진, 정책 오케스트레이터)
                  │
                  ▼ (사우스바운드 API - SBI: OpenFlow, P4, NETCONF, OVSDB)
[ 3. 인프라 계층 (Data Plane Switches) ] ─▶ (Flow Table 기반 라인 레이트 고속 패킷 포워딩)
```

선의 의미: 상위 비즈니스 앱의 요구사항이 NBI를 거쳐 제어 계층으로 전달되고, 계산된 흐름 규칙이 SBI를 통해 인프라 스위치로 하향 주입되는 3계층 아키텍처

| 계층 | 주요 구성요소 | 핵심 책임 및 역할 |
|:---|:---|:---|
| **응용 계층 (Application)** | 트래픽 엔지니어링, 보안 모니터링, L4~L7 가상 서비스 | 비즈니스 SLA 정책 정의 및 NBI 호출 |
| **노스바운드 API (NBI)** | RESTful API, gRPC, Java SDK | 응용 프로그램과 제어 평면 간의 추상화된 제어 인터페이스 제공 |
| **제어 계층 (Controller)** | ONOS, OpenDaylight, Ryu, 클라우드 컨트롤러 | 전역 토폴로지 관리, 최적 경로 연산, 흐름 규칙 생성 |
| **사우스바운드 API (SBI)** | OpenFlow 1.3/1.5, P4 Runtime, NETCONF, gNMI | 컨트롤러의 흐름 규칙을 스위치 하드웨어(TCAM)에 프로그래밍 |
| **인프라 계층 (Data Plane)** | Open vSwitch(OVS), 화이트박스 하드웨어 스위치 | 흐름 테이블(Flow Table) 매칭에 따른 패킷 스위칭 전담 |

#### 한줄 요약
- 응용 계층(NBI), 제어 계층(컨트롤러), 인프라 계층(SBI/스위치)의 3계층 구조로 동작한다.

## Ⅳ. 흐름도

<details><summary>용어 설명</summary>

- **패킷 인(Packet-In) / 패킷 아웃(Packet-Out)**: 스위치에 일치하는 흐름 규칙이 없을 때 컨트롤러로 첫 패킷을 전송하여 처리 방법을 문의(Packet-In)하고, 컨트롤러가 액션과 함께 패킷을 반환(Packet-Out)하는 절차.

</details>

```text
1. 신규 패킷이 인프라 스위치 포트로 인입 ➔ 스위치 하드웨어 Flow Table 검색
            │
            ▼ (Table-Miss 발생: 일치하는 규칙 없음)
2. 스위치가 패킷 헤더를 캡슐화하여 사우스바운드(OpenFlow)로 컨트롤러에 Packet-In 전송
            │
            ▼
3. SDN 컨트롤러가 전역 토폴로지 및 보안 정책을 조회하여 최적 포워딩 경로 연산
            │
            ▼
4. 컨트롤러가 스위치로 Flow-Mod(규칙 하향 설치) 및 Packet-Out(패킷 송출 명령) 하달
            │
            ▼
5. 스위치 하드웨어 TCAM에 규칙이 적재되어 후속 패킷부터는 제어 평면 개입 없이 라인 레이트 포워딩
```

**동작 원리**

1. **테이블 룩업**: 스위치가 수신 패킷을 L2~L4 헤더 필드 기반으로 Flow Table과 대조
2. **반응형(Reactive) 룰 요청**: 미등록 트래픽 발생 시 중앙 컨트롤러로 Packet-In 보고
3. **중앙 경로 판정**: 컨트롤러가 다익스트라 또는 제약 기반 라우팅(CSPF)으로 엔드투엔드 경로 산출
4. **하드웨어 캐싱**: 경로상의 모든 스위치에 `Flow-Mod` 메시지를 송출하여 TCAM에 엔트리 등록
5. **고속 전달**: 이후 동일 플로우의 패킷은 컨트롤러 왕복 없이 스위치 단독으로 나노초 단위 전송

#### 한줄 요약
- Flow Table 매칭, Table-Miss 시 Packet-In 보고, 컨트롤러 경로 연산, Flow-Mod 설치 및 라인 레이트 포워딩 순으로 처리된다.

## Ⅴ. 종류 및 비교

<details><summary>용어 설명</summary>

- **화이트박스 스위치(Whitebox Switch)**: 특정 벤더의 독점 소프트웨어 없이 상용 ASIC(Broadcom 등)과 개방형 리눅스 OS(SONiC, ONIE)를 탑재한 범용 고성능 스위치.

</details>

| 비교 항목 | 소프트웨어 정의 네트워킹 (SDN) | 전통적 분산 IP 네트워크 |
|:---|:---|:---|
| **제어 아키텍처** | **논리적 중앙 집중형 (Centralized Control)** | **노드별 완전 분산형 (Distributed Control)** |
| **장비 기능 구성** | 제어/데이터 평면 분리 (스위치는 전달 전담) | 개별 라우터마다 제어 및 데이터 평면 통합 탑재 |
| **망 관리 및 변경** | **중앙 NBI API 및 자동화 코드로 일괄 적용** | 장비별 개별 CLI 콘솔 접속 수동 구성 |
| **트래픽 경로 최적화** | **전역 토폴로지 맵 기반 실시간 TE 최적화** | 홉별(Hop-by-Hop) 국소적 최단 경로(SPF) 종속 |
| **장비 종속성** | **개방형 화이트박스 스위치 활용 (CapEx 절감)** | 특정 네트워크 벤더의 독점 어플라이언스 종속 |

#### 한줄 요약
- SDN은 논리적 중앙 집중 제어, 전역 트래픽 최적화, 개방형 하드웨어를 통한 자동화를 제공한다.

## Ⅵ. 실무 고려사항 및 대책

<details><summary>용어 설명</summary>

- **컨트롤러 클러스터링(Controller Clustering)**: 단일 컨트롤러 장애로 인한 전체 네트워크 마비를 방지하기 위해 Raft 등 분산 합의 알고리즘 기반으로 복수의 컨트롤러를 액티브-스탠바이 또는 액티브-액티브로 동기화하는 기법.
- **P4 언어**: 고정된 OpenFlow 헤더 매칭의 한계를 넘어, 패킷 파서와 파이프라인 구조 자체를 소프트웨어로 정의할 수 있는 데이터 평면 프로그래밍 언어.

</details>

| 문제 | 대책 | 효과 |
|:---|:---|:---|
| 중앙 SDN 컨트롤러 단일 장애 시 전체 네트워크 제어 마비(SPOF) | **Raft 분산 합의 기반 컨트롤러 클러스터링(ONOS/ODL)** 구축 | 단일 장애점 제거 및 무중단 제어 평면 고가용성 보장 |
| 대규모 미등록 트래픽 폭증 시 Packet-In 폭풍으로 인한 컨트롤러 CPU 과부하 | 선제적(Proactive) 흐름 규칙 사전 주입 및 **P4 기반 엣지 필터링** | Packet-In 발생률 95% 감소 및 제어 평면 안정성 확보 |
| 스위치 TCAM 하드웨어 용량 한계로 인한 Flow Table 오버플로우 | 흐름 규칙 수명 관리(**Idle/Hard Timeout**) 및 와일드카드 집약 적용 | 미사용 엔트리 자동 회수 및 TCAM 메모리 자원 고갈 차단 |

#### 한줄 요약
- Raft 클러스터링으로 고가용성을 확보하고, 선제적 룰 주입으로 Packet-In을 억제하며, Timeout으로 TCAM을 최적화한다.

## Ⅶ. 결론

- 대규모 데이터센터 및 클라우드 네트워크의 유연성과 자동화를 달성하기 위해 **SDN 아키텍처**를 전면 도입하되, 제어 평면의 신뢰성을 보장하기 위해 **Raft 분산 컨트롤러 클러스터**와 **P4 프로그래머블 데이터 평면**, **AI 기반 텔레메트리 폐루프(Closed-Loop)** 를 통합 구축하여 자율 운영 인프라(AIOps)를 완성

#### 한줄 요약
- 제어/데이터 평면 분리와 분산 컨트롤러 클러스터링을 결합하여 고신뢰 프로그래머블 네트워크를 실현한다.
