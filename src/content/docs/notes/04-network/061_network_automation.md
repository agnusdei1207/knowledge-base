## Ⅰ. 개요

<details><summary>핵심 용어</summary>

- **네트워크 자동화(Network Automation)**: 목표 네트워크 상태를 모델과 코드로 정의하고 반복 가능한 절차로 검증•배포•복구하는 운영 체계이다.
- **진실의 원천(Source of Truth)**: 주소•토폴로지•정책의 의도 상태를 유일한 기준으로 관리하는 저장소이다.
- **명령줄 인터페이스(Command-Line Interface, CLI)**: 텍스트 명령과 비구조 출력을 사용하는 조작 방식이다.
- **응용 프로그래밍 인터페이스(Application Programming Interface, API)**: 구조화된 요청으로 설정과 상태를 다루는 호출 규격이다.

</details>

- 정의/개념: **네트워크 자동화**는 **진실의 원천**에 선언한 목표 망 상태를 모델•코드로 검증•배포•복구하는 운영 체계이다.
- 배경/필요성: 장비별 수동 **CLI**는 설정 편차와 감사 누락을 유발하므로 구조화된 **API**가 필요하다.

#### 한줄 요약

- 사람이 장비마다 명령을 입력하는 대신 원하는 상태를 코드로 정의해 같은 절차로 검사하고 적용하는 것이 핵심이다.

## Ⅱ. 특징

<details><summary>핵심 용어</summary>

- **설정 드리프트(Configuration Drift)**: 장비의 실제 설정이 진실의 원천에 선언된 목표 상태와 달라진 현상이다.
- **멱등성(Idempotency)**: 같은 자동화 작업을 반복해도 목표 상태와 결과가 달라지지 않는 성질이다.
- **지속적 통합(Continuous Integration, CI)**: 변경마다 구문•스키마•정책 검사를 자동 실행하는 개발 방식이다.
- **YANG 모델**: 네트워크 설정•상태 데이터의 계층•자료형•제약을 정의하는 모델이다.

</details>

- **설정 드리프트**는 실제 설정과 진실의 원천 사이의 차이를 드러낸다.
- **YANG 모델**과 **CI**로 구문•스키마•정책을 변경 전에 검사한다.
- **멱등성**을 보장해 같은 자동화 작업을 반복해도 목표 상태를 유지한다.

#### 한줄 요약

- 자동화 도구만 도입하고 화면 문자열을 계속 파싱하면 장비 출력이 바뀔 때 작업이 쉽게 깨짐이 핵심이다.

## Ⅲ. 구조 및 구성요소

<details><summary>핵심 용어</summary>

- **네트워크 설정 프로토콜(Network Configuration Protocol, NETCONF)**: YANG 데이터를 RPC로 조회•변경하는 관리 프로토콜이다.
- **원격 프로시저 호출(Remote Procedure Call, RPC)**: 원격 시스템의 기능을 호출하는 통신 방식이다.
- **REST 설정 프로토콜(REST Configuration Protocol, RESTCONF)**: HTTP와 JSON•XML로 YANG 데이터를 다루는 프로토콜이다.
- **하이퍼텍스트 전송 프로토콜(Hypertext Transfer Protocol, HTTP)**: 웹 자원을 요청•응답으로 전달하는 프로토콜이다.
- **자바스크립트 객체 표기법(JavaScript Object Notation, JSON)**: 키와 값으로 구조화 데이터를 표현하는 형식이다.
- **확장성 마크업 언어(Extensible Markup Language, XML)**: 태그로 구조화 데이터를 표현하는 언어이다.
- **앤서블(Ansible)**: 인벤토리와 선언형 작업 파일로 여러 장비의 설정 작업을 조율하는 자동화 도구이다.

</details>

- **NETCONF**는 **RPC**와 **XML**로 YANG 데이터를 다루고, **RESTCONF**는 **HTTP**와 **JSON**•XML로 같은 모델을 다룬다.
- **Ansible**은 인벤토리와 선언형 작업 파일로 여러 장비의 적용 범위와 순서를 조율한다.

```text
네트워크 자동화
├─ 진실의 원천
├─ Git•CI 파이프라인
├─ Ansible
├─ YANG•관리 API
└─ 네트워크 장비
```

가지의 의미: 자동화 경계에 속한 정본•검증•배포•실행 기능을 뜻한다.

| 구성요소 | 책임 |
|:---|:---|
| 진실의 원천 | 주소•토폴로지•목표 정책 정본 저장 |
| Git•CI 파이프라인 | 변경 검토•검사•승인과 감사 기록 |
| Ansible | 인벤토리•배포 범위와 의존성 조율 |
| YANG•관리 API | YANG 제약 기반 설정 조회•변경 |
| 네트워크 장비 | 승인 설정•운용 상태 제공 |

#### 한줄 요약

- 진실의 원천와 실제 장비 상태의 차이를 찾아야 자동화 코드가 오래된 설정을 다시 덮어쓰지 않음이 핵심이다.

## Ⅳ. 흐름도

<details><summary>핵심 용어</summary>

- **후보 설정(Candidate Configuration)**: 실행 설정에 반영하기 전에 변경을 검증하는 NETCONF 저장소이다.
- **기능 광고(Capability Advertisement)**: 장비가 지원하는 NETCONF 기능을 관리 체계에 알리는 절차이다.
- **롤백(Rollback)**: 실패한 변경을 이전의 정상 설정으로 되돌리는 복구 작업이다.
- **깃(Git)**: 설정 코드의 변경•리뷰•승인 이력을 관리하는 버전 관리 도구이다.
- **사전 검증**: 설정 변경의 구문•YANG 제약•정책•도달성을 배포 전에 검사하는 단계이다.
- **승인 변경 전달**: 리뷰와 승인을 통과한 변경만 자동화 실행기에 보내는 단계이다.
- **설정 차이 배포**: 목표 상태와 실제 상태의 차이만 후보 설정에 적용하는 단계이다.
- **실제 상태 보고**: 배포 뒤 장비의 적용 설정과 운용 상태를 수집하는 단계이다.
- **검증 실패 시 롤백**: 도달성•정책 검증 실패나 시간 초과가 발생하면 이전 정상 설정으로 복구하는 단계이다.

</details>

```text
목표 상태 변경 요청
        │
        ▼
1. 사전 검증
        ├─ 실패: 변경 차단
        └─ 통과
            │
            ▼
2. 승인 변경 전달
            │
            ▼
3. 설정 차이 배포
            │
            ▼
4. 실제 상태 보고
            ├─ 검증 성공: 배포 결과 반환
            └─ 검증 실패: 5. 검증 실패 시 롤백
                              │
                              ▼
                         이전 정상 설정 복구
```

### 동작 원리

1. **사전 검증**: **사전 검증** 단계에서 **기능 광고**를 확인하고 구문•YANG•정책•도달성을 검사한다.
2. **승인 변경 전달**: **승인 변경 전달** 단계에서 **Git** 리뷰를 통과한 작업만 실행기에 보낸다.
3. **설정 차이 배포**: **설정 차이 배포** 단계에서 현재 상태와 다른 항목만 **후보 설정**에 적용한다.
4. **실제 상태 보고**: **실제 상태 보고** 단계에서 적용 설정과 운용 상태를 수집한다.
5. **검증 실패 시 롤백**: **검증 실패 시 롤백** 단계에서 실패나 시간 초과를 감지하면 **롤백**을 실행한다.

#### 한줄 요약

- API 성공 응답만 보지 말고 경로와 정책이 실제 트래픽에 반영됐는지 확인해야 변경이 끝남이 핵심이다.

## Ⅴ. 종류 및 비교

| 판단 기준 | NETCONF | RESTCONF | CLI 자동화 |
|:---|:---|:---|:---|
| 적용 기준 | **NETCONF**는 잠금•검증•커밋이 필요할 때 | **RESTCONF**는 웹 응용•포털 API와 연계할 때 | **CLI**는 구조화 API를 지원하지 않는 장비에 적용 |
| 핵심 특징 | **RPC**•**XML**•**YANG 모델** 저장소 | **HTTP**•**JSON**•XML•YANG 자원 | 명령•비구조 출력 파싱 |
| 한계 | 장비별 **기능 광고** 차이 | 트랜잭션 지원 차이 | 출력 변경•부분 실패 |

> 요약: 트랜잭션은 NETCONF, 웹 연계는 RESTCONF다.

#### 한줄 요약

- NETCONF의 후보 설정•검증 기능은 장비가 지원 기능을 알릴 때만 사용할 수 있다.

## Ⅵ. 실무 고려사항 및 대책

<details><summary>핵심 용어</summary>

- **템플릿(Template)**: 변수와 공통 형식으로 장비별 설정을 생성하는 코드이다.
- **도달성(Reachability)**: 출발지에서 목적지까지 패킷이 전달될 수 있는 상태이다.
- **텔레메트리(Telemetry)**: 장비의 상태•성능 데이터를 지속 수집해 관리 체계에 전달하는 기능이다.

</details>

| 문제 | 대책 | 효과 |
|:---|:---|:---|
| 정본과 실제 설정 차이로 변경 충돌 | 배포 전 **설정 드리프트** 탐지와 승인 | 오래된 설정 덮어쓰기 방지 |
| 일괄 변경 실패가 전체 망으로 확산 | **템플릿**으로 소수 장비부터 단계 배포 | 실패 범위 제한 |
| CLI 출력 변경으로 파싱 실패 | YANG•구조화 API 우선 | 파싱 오류 감소 |
| 배포 후 **도달성** 저하가 지속 | **텔레메트리** 기반 검증 실패•시간 초과 롤백 | 장애 복구 시간 단축 |

#### 한줄 요약

- 일부 스위치에서 먼저 설정을 검증하고 트래픽 경로가 유지될 때 나머지에 적용한다.

## Ⅶ. 결론

<details><summary>핵심 용어</summary>

- **자동화 배포 범위**: 변경 영향과 검증•복구 능력을 기준으로 한 번에 설정을 적용할 장비 집합을 정한 범위이다.

</details>

- **자동화 배포 범위**는 소수 장비부터 단계적으로 넓히고 복구 목표를 초과하면 **롤백**한다.

#### 한줄 요약

- 실패를 중단하고 실제 경로를 검증해 되돌릴 수 있는 범위까지만 자동화해야 한다.
