## Ⅰ. 개요

<details><summary>용어 설명</summary>

- **SOME/IP (인터넷 프로토콜 기반 확장형 서비스 지향 미들웨어)**: 예전처럼 "A 컴퓨터야 B 컴퓨터로 데이터 쏴라"가 아니라, 스마트폰 앱스토어처럼 "나 브레이크 기능(서비스) 필요한데 누가 해줄래?" 하고 찾아서 쓰는(SOA) 첨단 차량용 이더넷 미들웨어다.
- **AUTOSAR**: 자동차 소프트웨어 짤 때 벤더마다 제각각이던 걸 싹 다 통일시킨 '차량용 안드로이드' 같은 글로벌 표준 아키텍처다.

</details>

- 정의: **SOME/IP** 기반 **AUTOSAR** 기반 차량용 이더넷 통신망에서, 하드웨어 주소(IP) 몰라도 "기능(서비스)" 이름만 알면 찾아서 호출하고 구독하게 해주는 **서비스 지향 아키텍처(SOA) 미들웨어**다.
- 배경: 자율주행(SDV) 때문에 차에 들어가는 기능이 수백 개로 늘어나는데, 옛날처럼 하드웨어 주소로 1:1 하드코딩해 놓으면 센서 하나 바꿀 때마다 코드를 다 뜯어고쳐야 하니까 **유연하게 서비스 단위로 쪼개버렸다.**

#### 한줄 요약

- 자동차 안의 수많은 컴퓨터(ECU)들이 IP 주소 몰라도 "카메라 기능 가진 놈 나와라" 하면 알아서 연결해 주는 똑똑한 통신 규약이다.

## Ⅱ. 특징

<details><summary>용어 설명</summary>

- **SOME/IP-SD (Service Discovery)**: "나 카메라 기능 제공할 수 있어!"(광고)라거나 "카메라 기능 가진 놈 어딨어?"(탐색) 하고 브로드캐스트로 묻고 답하며 짝을 맞춰주는 자동 탐색 기술이다.
- **서비스 계약 (Service Contract)**: "내가 주는 온도 데이터는 섭씨고, 버전은 2.0이다"라고 데이터 규격을 맞춰보는 일종의 인터페이스 명세서(API) 체크다.
- **TTL (생존 시간)**: "내 카메라 기능은 앞으로 5분(TTL) 동안만 유효해!"라고 알려주는 서비스 수명 시간이다.

</details>

- **알아서 찾아줌 (SOME/IP-SD)**: 제공자가 자기를 동네방네 광고(Offer)하고 소비자가 조건에 맞게 탐색(Find)해서 알아서 짝을 맞춘다.
- **체크 (서비스 계약)**: 이름만 같다고 덜컥 연결하면 시스템이 뻗으니까, 인터페이스 버전이랑 데이터 타입(자료형)이 100% 일치하는지 먼저 깐깐하게 검증한다.
- **시한부 계약 (TTL 관리)**: 서비스 연결은 영원하지 않고, 정해진 시간(TTL) 내에 계속 "나 살아있어"라고 갱신(Alive) 안 해주면 얄짤없이 연결을 컷트한다.

#### 한줄 요약

- 제공자가 기능을 띄우면 호환성(버전) 체크 후 연결하고, 유효기간(TTL) 끝나기 전에 계속 갱신해야 하는 구조다.

## Ⅲ. 구조 및 구성요소

<details><summary>용어 설명</summary>

- **서비스 소비자 / 제공자**: 필요한 기능을 호출하는 놈(Client)과 기능을 실행해 주는 놈(Server)이다.
- **E2E 보호 (End-to-End Protection)**: 메시지가 중간에 깨지거나, 해커가 복사해서 두 번 보내는(재전송) 짓거리를 막기 위해 순서 번호(Sequence)와 체크섬(CRC)을 빡세게 말아 넣는 무결성 기술이다.

</details>

```text
[ SOME/IP 서비스 지향 직관적 비교 구조 ]

[ 1. 서비스 소비자 (Client) ] ── ("자율주행용 전방 카메라 기능 찾아요!")
      │
      ▼ (3. SOME/IP-SD 로 탐색 및 짝짓기)
====================================== (4. 서비스 인터페이스 / E2E 보호)
      ▲ (여기 카메라 영상 데이터 쏜다! 데이터 깨졌나 E2E 보호로 체크함)
      │
[ 2. 서비스 제공자 (Server) ] ── ("나 카메라 기능 있어. 가져다 써!")
```

| 구성요소 | 직관적 비교 책임 | 비고 |
|:---|:---|:---|
| **서비스 소비자** | 필요한 기능(서비스) **찾아서(Find) 호출하거나 구독하는 놈** | Client ECU |
| **서비스 제공자** | 자기 기능 쓸 사람 찾으려고 **광고(Offer)하고 데이터 쏴주는 놈** | Server ECU |
| **SOME/IP-SD** | 소비자랑 제공자가 서로 **짝지을 수 있게 위치(IP) 찾아주는 중개 브로커** | Service Discovery |
| **서비스 인터페이스**| 서로 말 통하게 **버전, 데이터 규격(ID) 맞춰놓은 API 계약서** | Interface Contract |
| **E2E 보호** | 데이터 중간에 깨지거나 조작되지 않게 **무결성 체크하는 철벽 보호막** | End-to-End |

#### 한줄 요약

- 소비자가 탐색(SD)해서 제공자를 찾으면, 계약서(인터페이스) 맞춰보고 E2E 보호막 씌워서 통신을 시작한다.

## Ⅳ. 흐름도

<details><summary>용어 설명</summary>

- **이벤트 그룹 (Event Group)**: 소비자가 "속도, RPM, 연료량 다 따로따로 받기 귀찮으니까 묶어서 세트로 보내줘" 하고 구독하는 혜자 구독 패키지 상품이다.
- **OfferService / FindService**: 제공자가 자기를 광고(Offer)하고, 소비자가 필요한 놈을 찾는(Find) 핵심 탐색 룰이다.

</details>

```text
[ SOME/IP-SD 탐색 및 서비스 교환 십자포화 흐름 ]

┌──────────────────────────────┐
│ 1. [OfferService 광고]       │
│ (제공자: 나 후방 카메라 2.0 버전 지원함. 5분(TTL)간 유지!)
└──────────────┬───────────────┘
               ▼
┌──────────────────────────────┐
│ 2. [FindService 탐색 및 체크]
│ (소비자: 나 카메라 기능 필요한데.. 어! 버전 2.0 딱 맞네)
└──────────────┬───────────────┘
               ▼
┌──────────────────────────────┐
│ 3. [이벤트 그룹 구독 (Subscribe)]
│ (소비자: 나 영상 데이터 스트리밍(이벤트 그룹) 구독할게)
└──────────────┬───────────────┘
               ▼
┌──────────────────────────────┐
│ 4. [서비스 메시지 교환 (통신)]│
│ (제공자: ㅇㅋ 영상 쏜다. E2E 보호 씌워서 안전하게 보냄)
└──────────────┬───────────────┘
               ▼
┌──────────────────────────────┐
│ 5. [Offer/Subscribe 갱신]    │
│ (제공자: TTL 끝나가네. 나 아직 살아있어 갱신할게!)
└──────────────────────────────┘
```

### 동작 원리

1. OfferService 광고: 제공자가 동네방네 "나 카메라 기능(ID, 버전, IP) 된다"고 방송하며 TTL(생명줄)을 줌.
2. FindService 탐색: 소비자가 광고 듣고, 자기가 필요한 버전이랑 100% 호환되는지 체크함.
3. 이벤트 그룹 구독: 조건 맞으면 "나 네 데이터 세트로 계속 받을래" 하고 구독 신청함.
4. 서비스 메시지 교환: 실제로 함수를 호출(메서드)하거나 데이터(이벤트)를 E2E 보호 씌워 안전하게 주고받음.
5. OfferService 갱신: TTL 시간 만료되기 전에 "나 계속 서비스한다"고 갱신 안 하면, 소비자가 손절하고 다른 놈 찾으러 떠남.

#### 한줄 요약

- 광고 듣고 $\to$ 버전 맞는지 간 보고 $\to$ 구독해서 빼먹다가 $\to$ 갱신 안 되면 버리는 냉혹한 통신 흐름이다.

## Ⅴ. 종류 및 비교

<details><summary>용어 설명</summary>

- **요청-응답 (Req/Res)**: 결과가 중요해서 호출하고 대답 올 때까지 기다리는 깐깐한 방식이다.
- **무응답 요청 (Fire & Forget)**: 툭 던지고 대답 안 기다리고 쿨하게 갈 길 가는 방식이다.
- **이벤트 통지 (Event)**: 유튜버 구독처럼 상태가 바뀌면 알아서 싹 다 배포해 주는 방식이다.

</details>

| SOME/IP 통신 방식 | **요청-응답 (Req/Res)** | **무응답 요청 (Fire & Forget)** | **이벤트 통지 (Event)** |
|:---|:---|:---|:---|
| 비유 및 핵심 특징 | **질문하고 대답 기다리기** | **툭 던지고 쿨하게 갈 길 가기** | **유튜버 구독 (알아서 날아옴)** |
| 동작 원리 | 클라이언트가 호출하면 **무조건 결과(ACK/응답)를 반환함** | 호출만 때리고 **결과 안 기다리고 그냥 쌩깜** | 상태 바뀌면 **구독자들한테 자동으로 싹 다 뿌림** |
| 치명적 한계 | 응답 올 때까지 기다려야 해서 **딜레이 생김** | 명령이 씹혔는지 체크가 절대 안 됨 | 구독자 너무 많으면 **트래픽 폭주(네트워크 터짐)** |
| 주력 활용 | 에어컨 켜기 (켜졌는지 확인 필수) | 깜빡이 켜기 (안 켜지면 0.1초 뒤 다시 쏘면 됨) | 현재 주행 속도, 엔진 RPM 실시간 방송 |

#### 한줄 요약

- 대답이 필요하면 요청-응답, 대충 보내도 되면 무응답 요청, 여러 명한테 쏠 땐 이벤트 통지(구독)를 쓴다.

## Ⅵ. 실무 고려사항 및 대책

<details><summary>용어 설명</summary>

- **계약 테스트 (Contract Test)**: 서비스 소비자와 제공자의 ID, 버전, 자료형(직렬화)이 100% 호환되는지 차 뽑기 전에 미리 빡세게 검증하는 시험이다.
- **TTL 튜닝 (Time to Live Tuning)**: 1초마다 나 살아있다고 방송하면 망이 터지니까, 탐색 부하랑 장애 감지 시간 간의 밸런스를 잡는 기가 막힌 튜닝 작업이다.

</details>

| 장애/위험 요소 | 원인 분석 | 실무 대책 및 해결방안 | 기대 효과 |
|:---|:---|:---|:---|
| 카메라 ECU 바꿨더니 **네비게이션이 영상을 못 받아먹음** | 카메라가 뱉는 데이터 규격(버전)이랑 네비가 요구하는 규격이 핀트가 어긋남 | 출시 전에 **계약 테스트(Contract Test)로 버전이랑 자료형 100% 호환되는지 빡세게 검증함** | 오호출 및 직렬화 뻑나는 에러 원천 차단 |
| SD 광고 트래픽 폭주해서 **차량 이더넷망 대역폭 박살남** | 모든 ECU가 나 살아있다고 브로드캐스트로 동네방네 떠들어댐 | **TTL 튜닝** 빡세게 해서, 꼭 필요할 때만 탐색하고 평소엔 입 다물게 만듦 | 무의미한 탐색 부하 싹 줄이고 망 쾌적성 확보 |
| 제어 데이터가 **해커 공격받아서 재전송(Replay) 됨** | 해커가 옛날 브레이크 패킷 복사해 뒀다가 다시 쏴서 차를 강제로 세워버림 | 패킷에 카운터(순서)랑 **CRC(체크섬) 달아서 검증하는 E2E 보호 방어막 켬** | 데이터 조작, 누락, 반복 재전송 등 치명적 보안 에러 컷트 |

#### 한줄 요약

- 버전 다르면 통신 뻗으니 계약 테스트 무조건 하고, 탐색 방송 너무 자주 하지 말고, 해커 막으려면 E2E 보호 켜라.

## Ⅶ. 결론

<details><summary>용어 설명</summary>

- (상단 참조)

</details>

- 자동차 소프트웨어의 극단적 복잡성(SDV)을 해결하기 위해, IP 주소 하드코딩을 버리고 **SOME/IP-SD 탐색**, **서비스 계약 및 TTL 관리**, **E2E 보호** 활용 결합한 차량 이더넷 기반 서비스 지향 아키텍처(SOA) 통신 기조 확립함

#### 한줄 요약

- SOME/IP는 하드웨어 주소에 얽매이던 옛날 자동차 통신을 버리고, 스마트폰 앱처럼 필요한 기능만 쏙쏙 골라 쓰는 자율주행차(SDV) 시대의 핵심 신경망이다.
