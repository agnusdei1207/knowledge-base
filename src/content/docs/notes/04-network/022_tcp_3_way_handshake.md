## Ⅰ. 개요

<details><summary>용어 설명</summary>

- **TCP 3-Way Handshake(3방향 핸드셰이크)**: 통신하기 전에 "내 말 들려?", "어 들려. 내 말도 들려?", "어 들려!" 하고 3번에 걸쳐 서로 살아있는지 확인하는 TCP의 기본 의식이다.

</details>

- 정의: SYN, SYN-ACK, ACK 3단계 메시지 교환을 통해 양방향 도달성을 검증하고 초기 순서 번호(ISN)를 동기화하는 **TCP 연결 설정 절차**
- 배경: 무지성으로 데이터를 던지는 UDP와 달리, 연결 전 상대방의 생사 여부와 데이터 수신 능력을 **미리 확인하여 신뢰성을 확보해야 했기 때문**

#### 한줄 요약

- 데이터 던지기 전에 "살아있냐?" 하고 세 번 찔러보며 통신 룰(ISN, MSS)을 맞추는 확인 작업이다.

## Ⅱ. 특징

<details><summary>용어 설명</summary>

- **SYN(Synchronize)**: "나랑 통신하자!" 하고 찌르는 첫인사 플래그다.
- **ACK(Acknowledgment)**: "응 알았어, 잘 받았어!" 하고 대답해 주는 확인 도장이다.
- **초기 순서 번호(ISN)**: 해커가 번호표 위조 못 하게 서로 랜덤하게 뽑아서 교환하는 패킷 일련번호의 시작점이다.
- **MSS(Maximum Segment Size)**: "나는 한 번에 이만큼 받을 수 있어" 하고 서로 덩치를 맞춰보는 캡슐화된 PDU 데이터 최대 크기 합의다.

</details>

- 독립적인 **초기 순서 번호(ISN)** 를 교환하여 꼬이지 않게 양방향 순서 기준을 정함.
- 첫 **SYN** 패킷의 옵션 필드에서 **MSS**나 윈도 스케일 같은 통신 스펙을 서로 합의함.
- 마지막 **ACK** 기반 상대방 ISN을 확실히 받았다고 도장을 찍어야만 찐 통신이 시작됨.

#### 한줄 요약

- SYN으로 인사하고, ISN으로 랜덤 번호표를 뽑고, MSS로 캡슐화된 PDU 데이터 크기를 맞춰서 꼬이지 않게 한다.

## Ⅲ. 구조 및 구성요소

<details><summary>용어 설명</summary>

- **리슨 소켓(Listen Socket)**: 서버가 "손님 받습니다" 하고 문 열어놓고 기다리는 포트 대기열이다.
- **SYN 큐(SYN Queue)**: 클라이언트가 인사(SYN)만 하고 아직 찐 대답(ACK)을 안 해서, 반쪽짜리 연결 상태로 기다리는 대기실이다.
- **Accept 큐(Accept Queue)**: 3번의 인사가 다 끝나고 "자 이제 통신 시작!" 하고 애플리케이션에 넘겨지기 전 대기하는 완전한 연결 방이다.

</details>

```text
[ 서버 측 TCP 연결 상태 관리 직관적 비교 구조 ]

[ 클라이언트 ]                     [ 서 버 ]

  (SYN) ────────────▶ [ 리슨 소켓 ] (어, 손님 왔네?)
                             │
                             ▼
                      [ SYN 큐 ] (대답 올 때까지 여기 있어)
  (ACK) ────────────▶        │
                             ▼
                      [ Accept 큐 ] (문 열렸음, 통신 시작!)
                             │
                             ▼
                    [ 애플리케이션 ] (웹 서버가 데이터 처리)
```

| 구성요소 | 책임 | 비고 |
|:---|:---|:---|
| **리슨 소켓** | 열린 포트(예: 80, 443)에서 멍때리며 **새 연결(SYN) 받아먹음** | 수신 대기 |
| **SYN 큐** | 인사(SYN)만 받고 대답(ACK) 안 온 **반쪽짜리 놈들 가둬두는 곳** | 반쪽 연결 |
| **Accept 큐** | 인사 다 끝나서 **앱으로 넘겨지기 직전인 놈들 대기실** | 완료 연결 |
| **연결 소켓** | 이제 진짜 통신 시작하려고 **서로 주소랑 ISN 킵해둔 장부** | ESTABLISHED |

#### 한줄 요약

- 리슨 소켓에서 손님을 받고, 대답 안 한 놈은 SYN 큐에 가두고, 인사가 끝나면 Accept 큐로 넘긴다.

## Ⅳ. 흐름도

<details><summary>용어 설명</summary>

- **반쪽 연결 상태(Half-Open)**: 서버가 SYN 받고 대답(SYN-ACK)은 했는데 클라이언트가 입 꾹 닫고 있어서 연결이 될랑 말랑한 애매한 상태(SYN_RCVD)다.
- **SYN-ACK**: "네 인사 받았고, 나도 인사할게!" 하고 두 개 플래그를 합쳐서 효율적으로 보내는 패킷이다.
- **완료 연결 상태(ESTABLISHED)**: 3단계 인사가 다 끝나서 이제 진짜 쌍방향으로 데이터를 직관적 비교할 수 있는 상태다.

</details>

```text
[ TCP 3-Way Handshake 십자포화 흐름 ]

[ 클라이언트 ]                                [ 서 버 ]
   (CLOSED)                                  (LISTEN)
      │                                         │
      ├─────── 1. SYN (나 통신할래!) ─────────▶│
      │         [Seq = x]                       │ (SYN 큐에 쑤셔 넣음)
(SYN_SENT)                                  (SYN_RCVD : 반쪽 연결)
      │                                         │
      │◀── 2. SYN-ACK (ㅇㅋ 들림! 넌 들림?) ─────┤
      │       [Seq = y, Ack = x+1]              │
      │                                         │
(ESTABLISHED)                                   │
      ├─────── 3. ACK (ㅇㅇ 나도 들림!) ───────▶│
      │         [Seq = x+1, Ack = y+1]          │ (Accept 큐로 패스)
      │                                         │
      ▼                                         ▼
  [ 통신 시작 ]                             [ 통신 시작 (ESTABLISHED) ]
```

### 동작 원리

1. SYN 전송: 클라이언트가 "나 너랑 통신하고 싶어" 하고 랜덤 번호(x) 던짐.
2. SYN-ACK 전송: 서버가 "콜, 나도 통신할게" 하고 자기 번호(y) 던지면서 응답함(반쪽 연결).
3. 최종 ACK 전송: 클라이언트가 "ㅇㅋ" 하고 대답하며 양방향 생사 확인 끝.
4. 완료 연결 상태: 양쪽 다 ESTABLISHED 되며 찐 통신 시작.

#### 한줄 요약

- 클라이언트가 찌르고(SYN) $\to$ 서버가 맞받아치고(SYN-ACK) $\to$ 클라이언트가 확인 도장(ACK) 찍으면 뚫린다.

## Ⅴ. 종류 및 비교

<details><summary>용어 설명</summary>

- **TCP 연결 설정(3-Way Handshake)**: 만날 때는 서로 목적이 같으니까 "나도!" 하고 3번 만에 쿨하게 합의 보는 과정이다.
- **TCP 연결 종료(4-Way Handshake)**: 헤어질 때는 남은 미련(데이터)이 다를 수 있어서, "나 끊을게" "잠깐만!" "나 다 보냄" "ㅇㅋ 잘 가" 하고 4번에 걸쳐 구질구질하게 헤어진다.

</details>

| 연결 절차 | **연결 설정 (3-Way Handshake)** | **연결 종료 (4-Way Handshake)** |
|:---|:---|:---|
| 목적 | 통신 시작 전 **양방향 도달성 및 스펙 합의** | 통신 다 끝나고 **깔끔하게 세션 방 빼기** |
| 제어 플래그 | **SYN**, **ACK** 사용 | **FIN**, **ACK** 사용 |
| 교환 횟수 | **3번** (서버의 응답과 요청을 합침) | **4번** (미련 남은 데이터를 처리하느라 분리됨) |
| 핵심 상태 | `CLOSED` $\to$ `SYN_SENT` $\to$ `ESTABLISHED` |  `ESTABLISHED` $\to$ `FIN_WAIT` $\to$ `CLOSED` |

#### 한줄 요약

- 만날 때는 쿨하게 3번 만에 합의하고, 헤어질 때는 남은 짐(데이터) 빼느라 4번 걸린다.

## Ⅵ. 실무 고려사항 및 대책

<details><summary>용어 설명</summary>

- **SYN Flood 공격**: 해커가 인사(SYN)만 수만 번 던지고 도망가서 서버의 대기실(SYN 큐)을 꽉 차게 만들어 서버를 터트리는 악질 DDoS 공격이다.
- **SYN Cookie**: SYN 큐가 꽉 차면 "아 몰라, 쿠키 하나 줄 테니까 일단 들고 있어!" 하고 상태 저장을 안 하면서 해커 공격을 방어하는 꼼수 기술이다.
- **경로 MTU(Path MTU)**: 가는 길목 라우터들이 소화할 수 있는 가장 좁은 파이프 크기로, 처음에 MSS 합의할 때 이걸 안 맞추면 패킷 데이터가 중간에 다 터진다.

</details>

| 장애/위험 요소 | 원인 분석 | 실무 대책 및 해결방안 | 기대 효과 |
|:---|:---|:---|:---|
| 좀비 PC들이 **SYN만 날려서 SYN 큐가 꽉 차 뻗음** | 해커의 **SYN Flood** 대량 공격 | 서버에 **SYN Cookie** 켜고 방화벽 임계치 설정 | SYN 큐 고갈 안 되고 정상 유저 접속 보호 |
| 덩치 큰 패킷 보냈는데 **중간 라우터에서 깨짐** | 합의한 **MSS** 라우터 **MTU**보다 큼 | 3-Way 때 **경로 MTU** 대상 맞춰서 MSS 작게 협상 | 패킷 쪼개짐이나 드롭(블랙홀) 원천 방지 |
| 폰 들고 터널 들어가서 **마지막 ACK가 서버로 안 옴** | 무선망 단절로 인한 3-Way 실패 | 반쪽 연결 큐(SYN_RCVD) 타임아웃 줄여서 쳐냄 | 잉여 커넥션 짜르고 메모리 낭비 막음 |
| 중간 방화벽이 **윈도 스케일 옵션을 지워버려서 속도 급격한 저하** | 보안 장비의 비정상 헤더 훼손 | 양쪽 끝에서 패킷 덤프 떠서 옵션 날아가는지 팩트체크 | 비정상적인 전송 속도 저하 원인 규명 |

#### 한줄 요약

- 해커가 SYN만 쏘면 쿠키(SYN Cookie) 줘서 돌려보내고, 파이프 좁으면 MSS 줄여서 패킷 발생하는 걸 막아라.

## Ⅶ. 결론

<details><summary>용어 설명</summary>

- **경로 MTU 블랙홀(Path MTU Black Hole)**: 캡슐화된 PDU 데이터가 너무 커서 라우터가 버려버렸는데, "상자 줄여라!"라는 에러(ICMP)마저 방화벽이 막아서 영원히 통신이 멈춰버리는 빡치는 현상이다.

</details>

- 양방향 **ISN** 동기화와 **MSS** 협상을 통해 신뢰성을 확보하고, 대량 접속 시 **SYN Cookie** 기반 자원을 방어하는 TCP 세션 통제 기조 확립함

#### 한줄 요약

- TCP의 3-Way는 무지성 전송을 막기 위한 최소한의 안전장치이며, MSS와 옵션 협상의 가장 중요한 골든타임이다.
