## Ⅰ. 개요

<details><summary>용어 설명</summary>

- **로드 밸런서(Load Balancer)**: 트래픽이 급격히 몰릴 때 혼자 다 맞고 뻗지 않도록, 여러 대의 서버에 트래픽을 골고루 찢어주는 총알받이 장비다.
- **가상 IP 주소(VIP, Virtual IP Address)**: 유저들한테는 "이게 진짜 서버야" 하고 구라를 치는 로드 밸런서의 대표 주소(IP)로, 뒤에 숨은 진짜 서버들의 방패막이다.

</details>

- 정의: **VIP**를 통해 클라이언트 요청을 받아 뒤에 숨은 여러 대의 실제 서버(백엔드)로 분산시켜 주는 **트래픽 분배기**
- 배경: 단일 서버의 스펙을 올리는(Scale-Up) 것만으로는 폭증하는 트래픽을 버틸 수 없어 **서버를 여러 대 늘리는(Scale-Out) 가용성 아키텍처가 필수였기 때문**

#### 한줄 요약

- 혼자서 감당 못 할 트래픽을 대표 주소(VIP)로 일단 받은 다음, 뒤에 있는 여러 놈한테 골고루 노가다를 분배한다.

## Ⅱ. 특징

<details><summary>용어 설명</summary>

- **L4 로드 밸런서**: IP와 포트 번호(TCP/UDP)만 쓱 보고 "웹이네? 1번 서버로, DB네? 2번 서버로" 하고 빠르게 넘겨버리는 기계적인 교통경찰이다.
- **L7 로드 밸런서**: 앱 데이터(URL, 헤더, 쿠키)까지 싹 다 까보고 "동영상이네? 캐시 서버로!" 하고 정밀하게 찢어주는 깐깐한 심사관이다.
- **URL(Uniform Resource Locator)**: L7 로드 밸런서가 까보는 핵심 정보로, 유저가 진짜 원하는 콘텐츠가 뭔지 알려주는 주소다.

</details>

- **VIP**를 앞세워 유저와 실제 서버 간의 직접적인 연결을 단절하고 네트워크 보안성을 확보.
- 주기적으로 서버 생사를 확인해서, 죽은 서버는 분산 대상에서 칼같이 제외(Health Check).
- **L4 로드 밸런서**는 포트 정보를, **L7 로드 밸런서**는 **URL**과 헤더 같은 내용물을 기준으로 트래픽을 찢어줌.

#### 한줄 요약

- 죽은 놈은 빼버리고(헬스 체크), 포트만 보고 찢으면 L4, 내용물까지 다 까보고 찢으면 L7이다.

## Ⅲ. 구조 및 구성요소

<details><summary>용어 설명</summary>

- **리스너(Listener)**: VIP와 특정 포트(예: 80, 443)를 열어놓고 "여기서 트래픽 받습니다" 하고 대기 타는 입구다.
- **서버 풀(Server Pool)**: 똑같은 일을 하는 복제된 서버들을 한데 묶어놓은 전담자(백엔드) 집합소다.
- **스케줄러(Scheduler)**: "이번엔 누가 덜 바쁘냐?" 하고 라운드 로빈 같은 규칙에 따라 트래픽을 던져줄 서버를 고르는 분배기다.
- **세션 고정(Sticky Session)**: 한 번 1번 서버에 배정받은 유저는 로그인 풀릴 때까지 계속 1번 서버만 쓰도록 묶어두는 꼼수다.

</details>

```text
[ 로드 밸런서 직관적 비교 분산 구조 ]

[ 클라이언트 ] ── (VIP 접속) ──▶ [ 로드 밸런서 ]
                                     │
             ┌───────────────────────┼────────────────────────┐
             ▼ (리스너 대기)         ▼ (스케줄러 분배)        ▼ (상태 확인)
      [ 80 포트 리스너 ]      [ 알고리즘: 라운드 로빈 ]  [ 죽었나 살았나 핑 ]
             │                       │                        │
             └───────────────────────┼────────────────────────┘
                                     ▼ (서버 풀)
                             [ 1번 웹 서버 (정상) ] ──▶ (트래픽 받음)
                             [ 2번 웹 서버 (정상) ] ──▶ (트래픽 받음)
                             [ 3번 웹 서버 (장애!) ] ──▶ (트래픽 차단!)
```

| 구성요소 | 직관적 비교 책임 | 비고 |
|:---|:---|:---|
| **VIP / 리스너** | 유저들한테 대표 주소(VIP) 까고 **트래픽 빨아들이는 입구** | 프론트엔드 |
| **스케줄러** | 라운드 로빈 등 룰에 따라 **트래픽 던져줄 서버 고름** | LB 알고리즘 |
| **서버 풀** | 트래픽 찢어 받을 **불쌍한 백엔드 서버들 모임** | 타겟 그룹 |
| **상태 확인 (Health Check)**| 핑 때려서 **죽은 서버 찾아내고 리스트에서 짤라버림** | 장애 격리 |
| **세션 고정 (Sticky Session)**| 장바구니 안 날아가게 **한 놈만 계속 같은 서버로 꽂아줌** | 세션 유지 꼼수 |

#### 한줄 요약

- 리스너로 빨아들여서, 상태 확인으로 죽은 놈 거르고, 스케줄러가 남은 놈들한테 트래픽을 던져준다.

## Ⅳ. 흐름도

<details><summary>용어 설명</summary>

- **상태 확인(Health Check)**: LB가 서버들한테 "죽었냐 살았냐?" 하고 쉴 새 없이 찔러보는 모니터링이다.
- **상태 탐사(Probe)**: 헬스 체크할 때 핑만 때리는 게 아니라, 웹 서버면 `/health` 페이지까지 찔러보는 깐깐한 검사다.
- **백엔드 선택(Backend Selection)**: 살아남은 정상 서버들 중에서 스케줄러 룰을 따져 최종 타겟을 고르는 작업이다.

</details>

```text
[ 로드 밸런싱 및 상태 확인 십자포화 흐름 ]

[ 1단계: 죽은 서버 솎아내기 ]
┌──────────────────────────────┐
│ 1. [탐사] 서버 풀 헬스 체크  │
│ (Ping, TCP 80, HTTP GET 등)  │
└──────────────┬───────────────┘
               ▼
┌──────────────────────────────┐
│ 2. [갱신] 정상 서버만 남김   │
│ (죽은 서버는 스케줄링 제외)  │
└──────────────────────────────┘

[ 2단계: 유저 트래픽 분산하기 ]
┌──────────────────────────────┐
│ 3. [유입] 유저가 VIP로 접속  │
│ (나 트래픽 줘!)              │
└──────────────┬───────────────┘
               ▼
┌──────────────────────────────┐
│ 4. [선택] 스케줄러가 서버 고름│
│ (가장 널널한 2번 서버 당첨)  │
└──────────────┬───────────────┘
               ▼
┌──────────────────────────────┐
│ 5. [전달] 실제 서버로 토스   │
│ (2번 서버야 일해라)          │
└──────────────────────────────┘
```

### 동작 원리

1. 상태 탐사: 포트 연결이나 웹 페이지 응답을 주기적으로 찔러봄.
2. 정상 집합 갱신: 탐사를 통과한 쌩쌩한 놈들만 리스트에 남김.
3. 백엔드 선택: 룰에 맞춰 가장 만만한 정상 서버 하나 고름.
4. 요청 전달: 선택한 서버로 유저 트래픽 넘겨줌.

#### 한줄 요약

- 뒤에서 계속 서버 생사 확인(Health Check) 하다가, 유저 오면 살아있는 놈 중에 골라서 던져준다.

## Ⅴ. 종류 및 비교

<details><summary>용어 설명</summary>

- **5-튜플(Five-tuple)**: "출발지 IP/포트, 목적지 IP/포트, 프로토콜" 5개로 통신을 식별하는 L4 지문이다.
- **역방향 프록시(Reverse Proxy)**: L7 LB가 유저랑 먼저 짝짜꿍하고 내용물 다 본 다음, 뒤에 서버랑 새 판을 짜서 넘겨주는 중계 방식이다.
- **TLS 종료(TLS Termination)**: HTTPS 암호화 트래픽을 L7 LB가 자기 인증서로 까서(복호화) 내용물 보고, 서버론 쌩얼(HTTP)로 보내는 고된 노동이다.

</details>

| 비교 항목 | **L4 로드 밸런서 (교통경찰)** | **L7 로드 밸런서 (보안 검색대)** |
|:---|:---|:---|
| 적용 기준 | 묻지도 따지지도 않는 **고속 세션 분산** | 내용물 까보고 판단하는 **콘텐츠 정밀 분기** |
| 핵심 특징 | **5-튜플(IP+포트)** 만 보고 무지성으로 던짐 | **역방향 프록시**로 패킷 다 뜯어봄 (URL, 쿠키 등) |
| 장점/단점 | 속도 존나 빠름 / 서버 애플리케이션 죽은 건 모름 | 존나 똑똑함 / **TLS 종료(복호화)** 하느라 CPU 터짐 |

#### 한줄 요약

- 속도전엔 안 까보고 던지는 L4 쓰고, 내용물 까서 깐깐하게 라우팅 할 땐 L7 쓴다.

## Ⅵ. 실무 고려사항 및 대책

<details><summary>용어 설명</summary>

- **상태 외부화(State Externalization)**: 서버 메모리에 세션 저장하면 죽을 때 다 날아가니까, 아예 Redis 같은 별도 DB에 저장해 세션 고정 족쇄를 푸는 아키텍처다.
- **다중 영역(Multi-AZ)**: 로드 밸런서랑 서버를 데이터센터 여러 곳에 찢어놔서, 센터 하나 불타도 안 뻗게 만드는 생존 전략이다.
- **L7 검사(Layer 7 Inspection)**: 로드 밸런서가 페이로드(HTTP 헤더 등)까지 싹 뜯어보고 라우팅 룰을 적용하는 빡센 검사 과정이다.

</details>

| 장애/위험 요소 | 원인 분석 | 실무 대책 및 해결방안 | 기대 효과 |
|:---|:---|:---|:---|
| L4가 핑만 때려서 **DB 죽은 웹서버로 계속 트래픽 쏨** | 멍청한 L4 헬스 체크의 한계 | HTTP `/health` 경로까지 찔러보는 **응용 계층 상태 확인** 튜닝 | 반쪽짜리 좀비 서버 완벽 격리 |
| 세션 고정(Sticky) 썼더니 **특정 서버만 트래픽 몰려 터짐** | 세션 고정 불균형 | Redis 등으로 **상태 외부화**하여 세션 고정 의존 탈피 | 서버 부하의 완벽한 라운드 로빈 달성 |
| HTTPS 트래픽이라 **L7 로드 밸런서가 내용을 못 까봄** | 페이로드 암호화 | L7 LB에 SSL 인증서 박고 **TLS 종료(Termination)** 처리 | **L7 검사(Inspection)** 기반 정밀 라우팅 가능 |
| 로드 밸런서 장비 자체가 뻗어서 **서비스 전체 마비됨** | 단일 장애점(SPOF) 발생 | 로드 밸런서 자체를 **다중 영역(Multi-AZ) Active-Standby** 구성 | 인프라 붕괴 대참사 방지 (고가용성) |

#### 한줄 요약

- 헬스 체크 깐깐하게 하고, 세션은 Redis로 빼서 Sticky 풀고, LB 장비 자체도 무조건 이중화해라.

## Ⅶ. 결론

<details><summary>용어 설명</summary>

- **정상 집합(Healthy Backend Set)**: 헬스 체크라는 지옥 훈련을 통과해서 "지금 당장 트래픽 받아도 안 뻗습니다!" 하고 검증된 살아있는 서버들의 명단이다.

</details>

- **정상 집합**을 철저히 유지하면서 속도가 우선이면 **L4 로드 밸런서**, 콘텐츠 기반 깐깐한 분기가 필요하면 **L7 로드 밸런서**를 선택하는 아키텍처 기조 확립함

#### 한줄 요약

- 부하 분산의 핵심은 "무조건 살아있는 놈한테만 던진다"는 정상 집합 유지에 있다.
