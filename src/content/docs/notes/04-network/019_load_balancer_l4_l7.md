## Ⅰ. 개요

<details><summary>용어 설명</summary>

- **로드 밸런서(Load Balancer)**: 단일 가상 IP(VIP)로 인입되는 대량의 클라이언트 트래픽을 백엔드의 여러 서버 인스턴스로 분산시켜 시스템의 처리량과 가용성을 향상시키는 네트워크 장비/소프트웨어.
- **가상 IP 주소(Virtual IP Address, VIP)**: 클라이언트가 서비스에 접근하는 단일 공용 대표 IP 주소로, 실제 백엔드 서버들의 물리적 IP를 은닉.

</details>

- 정의/개념: 단일 **가상 IP(VIP)** 를 통해 인입되는 트래픽을 사전에 정의된 알고리즘과 헬스 체크에 따라 다중 백엔드 서버 풀로 분산하는 **부하 분산 시스템**
- 배경/필요성: 단일 서버 수직 확장(Scale-Up)의 물리적 한계 극복, 수평 확장(Scale-Out)을 통한 고가용성(HA) 확보 및 서버 장애 시 무중단 서비스 제공 요구

#### 한줄 요약
- 단일 VIP로 인입되는 트래픽을 다중 백엔드 서버로 분산하여 시스템 가용성과 처리량을 극대화한다.

## Ⅱ. 특징

<details><summary>용어 설명</summary>

- **L4 로드 밸런서**: 전송 계층의 5-튜플(IP/Port/프로토콜) 정보만을 참조하여 TCP 연결을 중계하는 고속 로드 밸런서.
- **L7 로드 밸런서**: 애플리케이션 계층의 HTTP/HTTPS 헤더, URI, 쿠키 정보를 파싱하여 요청 내용 기반으로 전달 대상을 결정하는 역방향 프록시(Reverse Proxy) 기반 로드 밸런서.

</details>

- **VIP 기반 프런트엔드 은닉** 을 통해 백엔드 인프라 보안성 강화 및 단일 접근점 제공
- 주기적 **헬스 체크(Health Check)** 를 통해 장애 인스턴스를 서비스 풀에서 즉각 제외하는 결함 격리
- **L4의 고속 패킷 스위칭** 과 **L7의 콘텐츠 기반 지능형 라우팅** 으로 용도별 차등 배포

#### 한줄 요약
- VIP로 백엔드를 추상화하고, 주기적 헬스 체크와 L4(전송)/L7(응용) 계층별 분산 알고리즘을 적용한다.

## Ⅲ. 구조 및 구성요소

<details><summary>용어 설명</summary>

- **리스너(Listener)**: VIP와 특정 프로토콜/포트(예: HTTP 80, HTTPS 443)에서 클라이언트 요청을 수신 대기하는 컴포넌트.
- **백엔드 서버 풀(Target Group / Pool)**: 실제 비즈니스 로직을 처리하는 동일 목적의 백엔드 서버 인스턴스들의 집합.
- **세션 지속성(Sticky Session / Session Affinity)**: 동일 클라이언트의 연속된 요청을 최초 연결된 동일 백엔드 서버로 고정 전달하는 기능.

</details>

```text
[ 클라이언트 ] ───(VIP:443 요청)───▶ [ 로드 밸런서 (VIP 리스너) ]
                                             │
                       ┌─────────────────────┼─────────────────────┐
                       ▼ (헬스 체크 탐사)    ▼ (스케줄러 분산)     ▼ (세션 어피니티)
               [ 헬스 체크 엔진 ]      [ 라운드 로빈 / 최소 연결 ]  [ 쿠키/IP 매핑 테이블 ]
                       │                     │                     │
                       └─────────────────────┼─────────────────────┘
                                             ▼
                             ┌───────────────────────────────┐
                             │ 백엔드 서버 풀 (Server Pool)   │
                             ├─ [ 1번 서버 (정상 / 트래픽 전달) ]│
                             ├─ [ 2번 서버 (정상 / 트래픽 전달) ]│
                             └─ [ 3번 서버 (장애 / 트래픽 차단) ]│
                             └───────────────────────────────┘
```

선의 의미: VIP 리스너 수신부터 헬스 체크, 스케줄링 알고리즘, 세션 지속성을 거쳐 정상 백엔드 서버로 분산되는 구조

| 구성요소 | 책임 | 비고 |
|:---|:---|:---|
| **VIP / 리스너** | 클라이언트 트래픽을 수신하고 SSL/TLS 암복호화 및 포트별 세션 인입 관리 | 프런트엔드 |
| **스케줄러 엔진** | 라운드 로빈(RR), 최소 연결(Least Connection), 가중치 기반 분산 결정 | LB 알고리즘 |
| **백엔드 서버 풀** | 분산된 트래픽을 실질적으로 처리하는 복수 개의 워크로드 인스턴스 집합 | 타겟 그룹 |
| **상태 확인 엔진 (Health Check)** | L3(ICMP), L4(TCP SYN), L7(HTTP 200 OK) 상태를 주기적으로 계측하여 장애 서버 격리 | 결함 탐지 |
| **세션 지속성 모듈 (Sticky Session)** | 클라이언트 IP 해시 또는 쿠키(Cookie)를 기반으로 동일 서버 연결 바인딩 유지 | 세션 관리 |

#### 한줄 요약
- VIP 리스너, 스케줄러, 헬스 체크 엔진, 백엔드 풀의 유기적 결합으로 안정적 트래픽 분산을 수행한다.

## Ⅳ. 흐름도

<details><summary>용어 설명</summary>

- **상태 탐사(Health Probe)**: 백엔드 서버의 정상 동작 여부를 확인하기 위해 주기적으로 전송하는 검증 요청(HTTP GET `/health` 등).

</details>

```text
[ 1단계: 백엔드 가용성 평가 ]
1. 헬스 체크 탐사(Health Probe) 전송 (TCP Handshake / HTTP GET)
            │
            ▼
2. 응답 판정: 정상 응답 서버만 'Active Pool'에 유지, 장애 서버는 제외

[ 2단계: 클라이언트 요청 분산 ]
3. 클라이언트의 VIP 접속 요청 인입
            │
            ▼
4. 스케줄러 알고리즘(Least Connection 등) 및 세션 지속성 여부 판정
            │
            ▼
5. 선택된 정상 백엔드 서버로 트래픽 전달 (L4 NAT/DSR 또는 L7 Proxy)
```

**동작 원리**

1. **지속적 상태 검증**: 헬스 체크 모듈이 백엔드 인스턴스들의 포트 및 애플리케이션 응답 코드를 주기적으로 검증
2. **풀 갱신**: 정상 응답을 반환하는 서버들만 활성 스케줄링 대상 풀에 등록
3. **요청 인입**: 클라이언트가 VIP로 TCP 연결 또는 HTTP 요청 전송
4. **알고리즘 산출**: 기존 세션 쿠키 유무를 확인하고, 신규 요청에 대해 부하 분산 알고리즘 적용
5. **트래픽 중계**: L4 레벨에서 IP/Port 변환(NAT) 또는 L7 레벨에서 백엔드 HTTP 재전송 수행

#### 한줄 요약
- 지속적인 헬스 체크로 활성 풀을 갱신하고, 인입 요청을 알고리즘에 따라 정상 서버로 전달한다.

## Ⅴ. 종류 및 비교

<details><summary>용어 설명</summary>

- **직접 서버 반환(Direct Server Return, DSR)**: 요청 트래픽만 로드 밸런서를 거치고, 응답 트래픽은 백엔드 서버가 클라이언트로 직접 전송하여 로드 밸런서의 대역폭 병목을 해소하는 L4 아키텍처.
- **역방향 프록시(Reverse Proxy)**: L7 로드 밸런서가 클라이언트와 TCP 연결을 맺고(SSL 복호화 포함), 백엔드 서버와 별도의 TCP 연결을 수립하여 요청을 전달하는 방식.

</details>

| 비교 항목 | L4 로드 밸런서 (NLB 등) | L7 로드 밸런서 (ALB 등) |
|:---|:---|:---|
| **동작 계층 및 기준** | 전송 계층 (TCP/UDP 포트, **5-튜플**) | 애플리케이션 계층 (**HTTP URI, Header, Cookie**) |
| **중계 방식** | 패킷 레벨 포워딩 (NAT / DSR) | 양방향 완전 중계 (**Reverse Proxy**) |
| **SSL/TLS 처리** | 단순 패스스루(TCP 통과) 또는 L4 종단 | **TLS 종료(Offloading)** 및 인증서 중앙 관리 |
| **처리 성능 및 지연** | **초고속, 극소 지연 (마이크로초)**, 대규모 세션 | HTTP 파싱 및 버퍼링으로 상대적 지연 존재 |
| **적용 영역** | 대규모 TCP 스트리밍, 게임 서버, DNS | 웹 애플리케이션, 마이크로서비스(MSA), API 게이트웨이 |

#### 한줄 요약
- L4는 5-튜플 기반의 초고속 전송에 적합하고, L7은 URL/쿠키 기반의 지능형 애플리케이션 라우팅에 적합하다.

## Ⅵ. 실무 고려사항 및 대책

<details><summary>용어 설명</summary>

- **상태 외부화(State Externalization)**: 세션 데이터를 개별 웹 서버 메모리가 아닌 Redis 등의 분산 인메모리 저장소에 보관하여 무상태(Stateless) 아키텍처를 구현하는 기법.

</details>

| 문제 | 대책 | 효과 |
|:---|:---|:---|
| L4 단순 TCP 헬스 체크 시 웹 서버 내부 DB 장애 미탐지 | HTTP `/health` 경로 및 DB 연동을 검증하는 **L7 심층 헬스 체크** 적용 | 결함 서버의 완전한 트래픽 차단 및 가용성 보증 |
| 세션 고정(Sticky Session)으로 인한 특정 서버 트래픽 편중 | **Redis/Memcached 기반 세션 상태 외부화** 및 무상태(Stateless)화 | 서버 간 완전한 부하 균등 분산 및 자유로운 Auto-Scaling |
| 로드 밸런서 자체 장애로 인한 전체 시스템 단일 장애점(SPOF) | **다중 AZ(Multi-AZ) Active-Standby/Active-Active 이중화** 및 DNS 연동 | 로드 밸런서 장애 시 무중단 자동 절체(Failover) 보증 |

#### 한줄 요약
- L7 심층 헬스 체크로 결함 서버를 격리하고, Redis 상태 외부화로 부하 균등화를 달성하며, Multi-AZ 이중화로 SPOF를 제거한다.

## Ⅶ. 결론

- 엔터프라이즈 트래픽 아키텍처 수립 시 단순 대용량 트래픽 인입 구간에는 **L4 로드 밸런서(DSR/NLB)** 를 배치하고, 마이크로서비스 경로 분기와 TLS 오프로딩이 요구되는 웹 애플리케이션 구간에는 **L7 로드 밸런서(ALB)** 를 결합하는 2단계(Tiered) 계층 설계를 적용하며, Redis 상태 외부화를 통해 고가용성과 수평 확장성을 동시에 확보

#### 한줄 요약
- L4/L7 계층별 특성에 맞춘 다계층 부하 분산과 상태 외부화를 통해 고가용성 인프라를 완성한다.
