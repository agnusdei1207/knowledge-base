## Ⅰ. 개요

<details><summary>용어 설명</summary>

- **흐름 제어(Flow Control)**: 수신자 버퍼 발생하지 않게 남은 공간 눈치 보며 속도 조절해 주는 배려다.
- **혼잡 제어(Congestion Control)**: 중간 길(네트워크) 꽉 막혀서 다 뒤지지 않게 알아서 기어가는 송신자의 생존 본능이다.

</details>

- 정의: TCP가 데이터를 쏠 때, **흐름 제어(rwnd)** 와 **혼잡 제어(cwnd)** 중 더 빡센(작은) 기준을 골라 송신량을 칼같이 제한하는 **이중 안전장치 메커니즘**
- 배경: 무지성으로 데이터를 쏘면 **수신자 핵심 제어 메커니즘가 발생하거나(버퍼 초과), 중간 네트워크가 마비(혼잡)되어 인터넷 전체가 멈춰버리기 때문** #### 한줄 요약

- 수신자 발생하는 거 막는 '흐름 제어'와 네트워크 뻗는 거 막는 '혼잡 제어'를 동시에 돌려 안전하게 쏜다.

## Ⅱ. 특징

<details><summary>용어 설명</summary>

- **rwnd(Receive Window, 수신 윈도우)**: 수신자가 "나 이만큼 받을 공간 있어" 하고 알려주는 물리적 버퍼 여유 공간 지표다.
- **cwnd(Congestion Window, 혼잡 윈도우)**: 송신자가 "길이 얼마나 막히나?" 찔러보면서 스스로 조절하는 가상의 속도 제한창이다.
- **실제 윈도우(Effective Window)**: rwnd와 cwnd 둘 다 띄워놓고 더 작은 놈(MIN)을 찐으로 적용하는 제한선이다.
- **ssthresh(Slow Start Threshold)**: "여기까진 급격히 속도 올려도 됨" 하고 정해놓은 1차 한계선이다. 이거 넘으면 사리면서 올린다.

</details>

- **rwnd** 기반 수신 버퍼 여유를, **cwnd** 기반 네트워크 라우터 큐(대기열) 여유를 대변함.
- TCP는 항상 **MIN(rwnd, cwnd)** 값을 **실제 윈도우** 기반 삼아 깐깐하게 전송량을 통제함.
- 느린 시작(Slow Start) 단계에서는 **cwnd를 지수적(2배씩)** 으로 급격히 늘리다, **ssthresh** 대상 닿으면 쫄아서 선형적(1개씩)으로 올림.

#### 한줄 요약

- 받는 놈 여유(rwnd)와 도로 사정(cwnd) 중 좁은 쪽에 무조건 맞춰서 사고를 방지한다.

## Ⅲ. 구조 및 구성요소

<details><summary>용어 설명</summary>

- **슬라이딩 윈도우(Sliding Window)**: 대답 안 기다리고 한 번에 냅다 쏠 수 있는 창문(윈도우) 크기 단위의 고속 전송 꼼수다.
- **ECN(Explicit Congestion Notification)**: 라우터가 패킷 버리기 직전에 "나 지금 매우 힘드니까 쫌만 천천히 쏴라" 하고 패킷에 빨간불 켜서 알려주는 매너 기능이다.

</details>

```text
[ TCP 송수신 이중 통제 직관적 비교 구조 ]

[ 송신 TCP ]
│  (혼잡 제어기: cwnd 계산)
│  (송신 버퍼: min(rwnd, cwnd) 만큼 대기 없이 냅다 쏨)
│       │
│       ▼ (슬라이딩 윈도우로 뭉텅이 십자포화 전송)
│       │
│       ▼
[ 수신 TCP ]
   (수신 버퍼: 남은 공간 rwnd 체크해서 ACK에 껴서 반송)
```

| 구성요소 | 책임 | 비고 |
|:---|:---|:---|
| **송신 TCP** | rwnd랑 cwnd 눈치 보면서 **제일 좁은 폭으로 창문 크기 칼같이 조절함** | 송신 주체 |
| **혼잡 제어기**| 패킷 잃어버리거나(Loss) **ECN** 오면 쫄아서 cwnd 반토막 내는 쫄보 AI | 혼잡 제어 |
| **수신 TCP** | 데이터 받을 때마다 "나 이만큼 비었음" 하고 **rwnd 전달함** | 흐름 제어 |

#### 한줄 요약

- 수신자는 rwnd를 실시간으로 던져주고, 송신자는 cwnd를 자체 계산해서 둘 중 작은 값으로 쏜다.

## Ⅳ. 흐름도

<details><summary>용어 설명</summary>

- **느린 시작(Slow Start)**: 쫄아서 1개 보내보고, 대답 오면 2개, 4개, 8개씩 지수배로 속도 올리는 부스터 모드다.
- **혼잡 회피(Congestion Avoidance)**: ssthresh 넘어가면 "아 이제 막히겠는데?" 하고 1개씩(선형)만 늘리며 눈치 보는 찌질 모드다.

</details>

```text
[ TCP 흐름/혼잡 제어 십자포화 흐름 ]

[ 전송량 결정 ]
(실제 윈도우 = min(rwnd, cwnd) 크기만큼 쏨)
       │
       ▼
[ 수신자 ACK 응답 ] 
(수신 여유 rwnd + 혼잡 신호 ECN/Loss 포함)
       │
       ├── (패킷 날아감 / ECN 빨간불 켜짐)
       │    └──▶ cwnd 반토막 내고 ssthresh 깎음 (쫄보 모드)
       │
       └── (ACK 잘 옴)
            ├── cwnd < ssthresh : 2배씩 뻥튀기 (느린 시작)
            └── cwnd >= ssthresh: 1개씩 찔끔찔끔 증가 (혼잡 회피)
```

### 동작 원리

1. 실제 윈도우 산출: rwnd와 cwnd 중 더 작은 값으로 전송 허용량을 잡음.
2. ACK 수신: 수신자가 rwnd를 업데이트해서 ACK와 함께 던져줌.
3. 혼잡 감지: ACK가 잘 오면 cwnd 늘리고, 빵꾸(Loss)나면 쫄아서 cwnd 확 줄임.
4. 반복: 망이 버틸 때까지 느린 시작 $\to$ 혼잡 회피 $\to$ 축소를 반복하며 윈도우 줄타기.

#### 한줄 요약

- 대답 잘 오면 속도 급격히 올리다, 한 번이라도 패킷 잃어버리면 화들짝 놀라 반토막 내고 눈치 보며 올린다.

## Ⅴ. 종류 및 비교

<details><summary>용어 설명</summary>

- **수신자 병목(Receiver Bottleneck)**: 망은 뻥 뚫렸는데, 수신자 폰(앱)이 구져서 버퍼(rwnd)를 못 비워 속도 안 나오는 답답한 상태다.
- **네트워크 병목(Network Bottleneck)**: 수신자는 빵빵한데 중간 통신사 망이 꽉 막혀서 패킷 떨어지고 cwnd가 급격한 저하하는 상태다.

</details>

| 구분 | **흐름 제어 (수신자 병목 대응)** | **혼잡 제어 (네트워크 병목 대응)** |
|:---|:---|:---|
| 핵심 주체 | **수신자** 남은 버퍼 크기(rwnd) 알려줌 | **송신자** 눈치(cwnd) 보고 스스로 조절 |
| 작동 원리 | 수신자가 부른 rwnd 크기만큼 안 기다리고 쏨 | Slow Start $\to$ 혼잡 회피로 눈치 보며 탐색 |
| 주요 지표 | **rwnd** (Receive Window) | **cwnd** (Congestion Window), ssthresh |
| 한계점 | 앱 처리 속도 느리면 계속 병목 (Zero Window) | 버퍼블로트(Bufferbloat)로 인해 핑(지연) 폭증 가능 |

#### 한줄 요약

- 수신자 핵심 제어 메커니즘 깨지는 걸 막는 게 흐름 제어, 라우터 핵심 제어 메커니즘 깨지는 걸 막는 게 혼잡 제어다.

## Ⅵ. 실무 고려사항 및 대책

<details><summary>용어 설명</summary>

- **버퍼블로트(Bufferbloat)**: 중간 라우터 큐가 너무 빵빵해서 패킷을 쳐 버리지 않고 무식하게 다 머금고 있다가 핑(지연 시간)만 수십 배 튀는 환장할 현상이다.
- **BDP(Bandwidth-Delay Product)**: 파이프 굵기(대역폭) × 파이프 길이(RTT)로, 파이프 안에 꽉 채울 수 있는 데이터 최대량이다.

</details>

| 장애/위험 요소 | 원인 분석 | 실무 대책 및 해결방안 | 기대 효과 |
|:---|:---|:---|:---|
| 속도 안 나오는데 **수신자 탓인지 망 탓인지 구분을 못 함** | rwnd랑 cwnd 짬뽕해서 무지성 분석함 | 서버에서 **rwnd 0** 떨어지는지, **패킷 유실(재전송)** 뜨는지 로그 분리 관측 | 정확한 병목(수신자 vs 망) 원인 체크 |
| 무선망에서 잠깐 끊겼는데 **속도 완전 반토막 남** | 송신자가 단순 무선 손실을 **망 혼잡** 기반 오해해서 cwnd 쳐냄 | **BBR** 혼잡 제어 알고리즘 도입 및 ECN/RTT 종합 분석 | 억울하게 속도 급격한 저하하는 TCP 고질병 방어 |
| 중간 망 대역폭 빵빵한데 **핑(지연)이 급격히 튐** | 라우터 큐가 너무 커서 딜레이 쩌는 **버퍼블로트(Bufferbloat)** | AQM(능동 큐 관리) 켜고 큐 사이즈 적정선으로 쳐냄 | 쓸데없는 버퍼 대기 막고 실시간 응답성(RTT) 회복 |
| 10기가 랜선 꽂았는데 **다운 속도가 쥐똥만큼 나옴** | 수신 버퍼가 **BDP**보다 너무 작게 옹졸하게 세팅됨 | 수신 버퍼(Socket Buffer) 늘리고 TCP Window Scale 켬 | 기가비트망 대역폭(BDP) 풀로 뽑아먹음 |

#### 한줄 요약

- 속도 안 나오면 수신자 rwnd가 0 떴는지(앱 장애), 아니면 패킷 날아가서 cwnd가 깎였는지(망 장애)부터 까봐라.

## Ⅶ. 결론

<details><summary>용어 설명</summary>

- **제로 윈도우(Zero Window)**: 수신자 핵심 제어 메커니즘가 다 차서 "나 더 이상 못 받아!" 하고 rwnd=0을 외치며 통신을 강제 셧다운시킨 상태다.

</details>

- **제로 윈도우(rwnd=0)** 가 뜨면 앱 서버(수신자) 처리 로직을 뜯어고치고, 속도는 안 나는데 rwnd가 넉넉하면 망(cwnd) 탓이므로 혼잡 제어 파라미터를 튜닝해 병목부터 조지는 아키텍처 기조 확립함

#### 한줄 요약

- TCP는 겉으론 완벽해 보이지만, 병목이 어디서 났는지 분리해서 보지 못하면 실무에서 삽질만 하게 되는 예민한 프로토콜이다.
