## Ⅰ. 개요

<details><summary>용어 설명</summary>

- **상호 전송 계층 보안(mTLS, Mutual TLS)**: 클라이언트가 서버 멱살 잡고 신분증 요구하듯, 서버도 클라이언트한테 "너도 민증 까봐" 하고 서로 쌍방향으로 검증하는 깐깐한 암호화 프로토콜이다.
- **전송 계층 보안(TLS)**: 기존 HTTPS에서 쓰던 걸로, 클라이언트가 서버 신원(인증서)만 일방적으로 확인하고 통신하는 단방향 보안 기술이다.

</details>

- 정의: 클라이언트와 서버가 서로의 X.509 디지털 인증서와 개인키 서명을 주고받아 양방향 기계 신원(Machine Identity)을 확인하는 **TLS 확장 보안 프로토콜**
- 배경: 기존의 단방향 TLS로는 접속하려는 **클라이언트(기계/서버)가 해커인지 정상 서버인지 신원을 알 수가 없었기 때문** (Zero Trust 도입의 핵심 배경)

#### 한줄 요약

- 너만 나를 검증하는 게 아니라, 나도 너를 검증해서 서로 기계 신분증(인증서)을 까봐야만 통신을 허락하는 기술이다.

## Ⅱ. 특징

<details><summary>용어 설명</summary>

- **인증서 체인(Certificate Chain)**: "이 인증서 진짜임!" 하고 보증 서주는 기관(CA)들의 족보(Root CA $\to$ 중간 CA $\to$ 엔드)다. 족보 꼬이면 짤없이 검증 컷 당한다.
- **세션 키(Session Key)**: 상호 신분 확인이 끝나면, 진짜 통신 데이터를 빠르고 안전하게 암호화하려고 임시로 맞춰보는 쌍둥이 비밀번호(대칭키)다.

</details>

- **양방향 신원 검증**: 서버 및 클라이언트의 인증서 족보(체인)를 동시에 까봐서, 허가되지 않은 기계의 위장 접속을 원천 차단함.
- **비대칭키 기반 서명 증명**: "이 인증서 내 거 맞음"을 증명하려고, 개인키 노출 없이 전자서명만 만들어서 상대에게 소유권을 증명함.
- **인증과 인가 분리**: mTLS로 "네가 00서버구나(Authentication)" 신원 팩트 체크만 하고, "이 API 호출해도 되나?(Authorization)"는 RBAC 같은 정책으로 별도 제어함.

#### 한줄 요약

- 서로 족보(체인)와 서명 까보고 신분 확인한 뒤에야, 임시 비밀번호(세션 키) 파서 암호화 통신을 시작한다.

## Ⅲ. 구조 및 구성요소

<details><summary>용어 설명</summary>

- **인증기관(CA, Certificate Authority)**: 인증서 발급해주고, 불량자(폐기 목록) 관리하며 양쪽이 서로를 믿게 해주는 절대 권력의 신뢰점(Trust Anchor)이다.
- **신뢰 저장소(Trust Store)**: "나는 이 CA가 찍어준 인증서만 믿을 거야" 하고 등록해 놓은 허락 목록(보안 창고)이다. 여기에 상대방 CA가 없으면 얄짤없이 팅긴다.

</details>

```text
[ mTLS 상호 신뢰 팩트 폭행 구조 ]

[ 클라이언트 (A 서비스) ]                       [ 서 버 (B 서비스) ]

(신뢰 저장소)                                   (신뢰 저장소)
[ Root CA ] ◀────────(공통 신뢰)─────────▶ [ Root CA ]
     │                                              │
     ▼ (인증서 제시)                  (인증서 제시) ▼
[ 내 인증서 + 서명 ] ─────────────▶◀───────── [ 네 인증서 + 서명 ]
(이게 나임, 검증해봐)                           (ㅇㅇ 나도 검증해봐)
            │                               │
            ▼ (양쪽 다 통과 시)             ▼
            └──────── [ 대칭 세션 키 ] ───────┘ (암호화 통신 시작)
```

| 구성요소 | 팩트 폭행 책임 | 비고 |
|:---|:---|:---|
| **인증기관 (CA)** | 인증서 발급해주고 양쪽이 서로 믿게 해주는 **최상위 보증인** | Trust Anchor |
| **클라이언트 인증서/키** | 클라이언트가 "나 해커 아니고 정상 서버임" 하고 **서명해서 들이미는 민증** | 신원 증명 |
| **서버 인증서/키** | 서버가 "나 가짜 사이트 아님" 하고 **서명해서 들이미는 민증** | 신원 증명 |
| **양측 신뢰 저장소**| 들이민 민증이 **내가 허락한 보증인(CA)이 발급해 준 건지 팩트 체크하는 명부**| Trust Store |
| **대칭 세션 키** | 신분 확인 끝났으니 통신 훔쳐보지 못하게 빡세게 **암호화하는 임시 자물쇠** | 고속 암호화 |

#### 한줄 요약

- 공통으로 믿는 보증인(Root CA)을 신뢰 저장소에 박아두고, 서로 민증(인증서)과 지문(서명)을 대조해 팩트 체크한다.

## Ⅳ. 흐름도

<details><summary>용어 설명</summary>

- **클라이언트 인증 요청(Certificate Request)**: 서버가 지 인증서만 주지 않고, "이제 네 민증도 내놔라(그리고 이 CA에서 발급한 것만 취급함)" 하고 당당하게 요구하는 mTLS의 핵심 절차다.
- **클라이언트 인증 증명(Certificate Verify)**: 클라이언트가 쫄지 않고 자기 인증서 들이밀면서 "내 개인키로 서명했으니 확인해 봐라" 하고 맞불 놓는 절차다.

</details>

```text
[ mTLS 상호 인증 십자포화 흐름 ]

[ 클라이언트 (A 서버) ]                       [ 서 버 (B 서버) ]
        │                                         │
        ├──────── (1. Client Hello: 안녕?) ──────▶│
        │                                         │
        │◀─────── (2. Server Hello + 서버 인증서) ┤
(서버 인증서 팩트체크)                            │
        │◀─────── (3. 클라이언트 인증 요청) ──────┤ (너도 민증 까라)
        │                                         │
        ├──────── (4. 클라이언트 인증서 + 서명) ─▶│
        │                                         │ (클라이언트 인증서 팩트체크)
        │                                         │
(양쪽 다 검증 끝)                               (양쪽 다 검증 끝)
        ├──────── (5. 대칭 세션 키로 통신) ───────▶│
```

### 동작 원리

1. 클라이언트가 인사(Hello)하면 서버가 자기 인증서를 던져줌.
2. 클라이언트가 서버 인증서 족보(체인)와 만료일 팩트 체크함.
3. 서버가 역으로 **클라이언트 인증 요청(Certificate Request)**을 때림.
4. 클라이언트가 자기 인증서와 찐 서명(**Certificate Verify**)을 제출함.
5. 서버가 클라이언트 인증서 팩트 체크 성공하면, 임시 자물쇠(세션 키) 교환하고 통신 뚫림.

#### 한줄 요약

- 서버 먼저 까보고 이상 없으면 클라이언트 까보고, 양쪽 다 깔끔해야 통신을 열어주는 상호 멱살잡이 절차다.

## Ⅴ. 종류 및 비교

<details><summary>용어 설명</summary>

- **단방향 TLS (One-Way TLS)**: 우리가 흔히 아는 HTTPS. 클라이언트(웹 브라우저)는 묻지도 따지지도 않고 서버 민증만 보고 믿어주는, 서버 입장에서는 접속자가 누군지 개나 소나 다 받는 방식이다.

</details>

| TLS 인증 방식 | **mTLS (상호 TLS)** | **단방향 TLS (일반 HTTPS)** |
|:---|:---|:---|
| 적용 기준 | 내가 누군지 빡세게 가려야 하는 **제로 트러스트(Zero Trust), 서비스 간(M2M) 통신** | 개나 소나 다 들어와도 되는 **대국민 공개 웹 서비스** |
| 팩트 폭행 주체 | **서버와 클라이언트 둘 다** 서로 멱살 잡고 인증서 팩트 체크함 | **클라이언트만** 서버 인증서 확인하고, 서버는 걍 다 받아줌 |
| 단점 및 한계 | 클라이언트마다 인증서 발급해주고 만료일 관리(Rotation)하느라 **운영 빡셈** | 클라이언트가 기계인지 해커인지 **신원 확인 자체가 원천 불가** |

#### 한줄 요약

- 네이버 접속할 땐 단방향 TLS를 쓰고, 백엔드 서버끼리 API 주고받을 땐 해커 막으려고 mTLS를 쓴다.

## Ⅵ. 실무 고려사항 및 대책

<details><summary>용어 설명</summary>

- **인증서 폐기 목록(CRL/OCSP)**: 유효기간 안 지났어도 해킹당해서 "이 새끼 인증서 무효 처리요!" 하고 CA가 실시간으로 뿌리는 블랙리스트다.
- **서비스 메쉬(Service Mesh)**: 수백 개 서버(파드)들의 mTLS 인증서 발급, 갱신, 검증을 지들이 알아서 투명하게 짬 처리해 주는 인프라 컨트롤러(Istio 등)다.
- **SPIFFE/SPIRE**: 기계(컨테이너)마다 "너는 DB용, 너는 웹용" 하고 빡세게 신분증 발급해 주고 mTLS 돌리게 해주는 기계 신원 표준이다.

</details>

| 장애/위험 요소 | 원인 분석 | 실무 대책 및 해결방안 | 기대 효과 |
|:---|:---|:---|:---|
| 클라이언트 인증서 만료돼서 **새벽에 API 통신 다 뻗음** | 인증서 만료(Expiration) 관리 수동 처리 (휴먼 에러) | **ACME** 봇이나 **서비스 메쉬** 연동으로 인증서 자동 회전(Auto-Rotation) | 끔찍한 만료 장애 원천 방어 |
| 해커가 클라이언트 서버 털어서 **인증서 탈취해 위장 접속함** | 인증서 탈취 및 검증 로직 부재 | **단기 인증서(Short-Lived)** 도입 및 실시간 **CRL/OCSP** 폐기 검증 튜닝 | 해커 위장 접속 즉시 차단 (Zero Trust) |
| 서버끼리 서로 **인증서 못 믿겠다고 팅김(Handshake Failure)**| 양쪽 서버의 **신뢰 저장소(Trust Store)** 버전 불일치 | 서비스 메쉬(Service Mesh) 기반으로 중앙에서 **Root CA 일괄 배포** 및 동기화 | 어이없는 인증 실패 장애 해결 |
| mTLS 통과했다고 **DB 삭제 API까지 프리패스로 다 뚫림** | 신원 확인(인증)과 권한 승인(인가)을 짬뽕시킴 | mTLS로 1차 팩트 체크 후, **RBAC/ABAC**로 "얘가 이 API 호출해도 되나?" 2차 통제 | 최소 권한 원칙(PoLP) 사수 |

#### 한줄 요약

- 인증서 수동으로 갱신하다 좆되지 말고 서비스 메쉬로 자동화하고, 털린 인증서는 CRL로 바로바로 쳐내라.

## Ⅶ. 결론

<details><summary>용어 설명</summary>

- **인증과 인가 분리(Authentication/Authorization Separation)**: "너 우리 회사 직원 맞네(mTLS 인증)"와 "근데 너 사장 방에 들어갈 권한 있어?(RBAC 인가)"를 철저하게 쪼개서 관리하는 보안의 근본 원칙이다.

</details>

- 기계 간 신원 확인은 **mTLS(SPIFFE/SPIRE)**로 강제하고, 접근 권한은 **RBAC/ABAC**로 통제하는 **인증과 인가 분리** 중심의 제로 트러스트 아키텍처 기조 확립함

#### 한줄 요약

- mTLS는 제로 트러스트의 심장으로, 인증서라는 절대적인 신분증 없이는 그 어떤 기계도 대화에 낄 수 없게 만드는 무자비한 문지기다.
