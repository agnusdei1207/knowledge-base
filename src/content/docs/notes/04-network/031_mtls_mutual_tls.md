## Ⅰ. 개요

<details><summary>용어 설명</summary>

- **상호 전송 계층 보안(Mutual Transport Layer Security, mTLS)**: 클라이언트만 서버의 인증서를 검증하는 기존 단방향 TLS와 달리, 서버도 클라이언트의 X.509 디지털 인증서를 요구하여 양방향 기계 신원(Machine Identity)을 상호 검증하고 암호화 채널을 수립하는 프로토콜.
- **기계 신원(Machine Identity)**: 서비스, 컨테이너, 워크로드 간 통신에서 X.509 인증서 및 개인키 서명을 통해 증명되는 디지털 신원.

</details>

- 정의/개념: 클라이언트와 서버가 서로의 X.509 디지털 인증서와 전자서명을 상호 교환하여 양방향 신원을 검증하고 전송 구간을 암호화하는 **양방향 TLS 인증 프로토콜**
- 배경/필요성: 마이크로서비스(MSA), API 게이트웨이 및 제로 트러스트(Zero Trust) 아키텍처 환경에서 비인가 서비스의 내부망 위장 접속 방지 및 전송 기밀성 확보 요구

#### 한줄 요약
- 양방향 X.509 인증서 교환을 통해 클라이언트와 서버의 기계 신원을 상호 검증하고 통신을 암호화한다.

## Ⅱ. 특징

<details><summary>용어 설명</summary>

- **인증서 체인(Certificate Chain)**: 엔드포인트 인증서가 중간 인증기관(Intermediate CA)을 거쳐 신뢰할 수 있는 최상위 루트 인증기관(Root CA)에 의해 서명되었음을 증명하는 계층적 신뢰 경로.
- **인증과 인가의 분리(AuthN vs AuthZ)**: mTLS를 통해 통신 주체의 신원을 확인(Authentication)하고, 해당 주체의 API 실행 권한(Authorization)은 RBAC/ABAC 정책 엔진으로 분리 제어하는 원칙.

</details>

- **양방향 X.509 신원 검증**: 서버와 클라이언트 모두 사전에 정의된 신뢰 저장소(Trust Store)의 CA 서명을 상호 검증
- **비대칭키 기반 소유권 증명**: Certificate Verify 메시지를 통해 개인키 노출 없이 암호학적 전자서명으로 인증서 소유권 입증
- **세션 키 기반 고속 암호화**: 신원 검증 완료 후 대칭키(AES-GCM, ChaCha20) 세션 키를 생성하여 데이터 기밀성 및 무결성 보장

#### 한줄 요약
- 양방향 인증서 체인 검증과 비대칭키 서명으로 신원을 증명하고, 대칭 세션 키로 암호화 통신을 수행한다.

## Ⅲ. 구조 및 구성요소

<details><summary>용어 설명</summary>

- **인증기관(Certificate Authority, CA)**: 공개키 인증서를 발급, 서명, 갱신 및 폐기 관리하는 신뢰 앵커(Trust Anchor).
- **신뢰 저장소(Trust Store)**: 호스트가 신뢰하기로 사전에 등록한 루트 CA 및 중간 CA의 공개키 인증서 모음.

</details>

```text
[ 클라이언트 (Service A) ]                       [ 서버 (Service B) ]
 ┌──────────────────────┐                        ┌──────────────────────┐
 │ Trust Store (Root CA)│ ◀──── 공통 신뢰 앵커 ────▶ │ Trust Store (Root CA)│
 └──────────┬───────────┘                        └──────────┬───────────┘
            │                                               │
            ▼ (클라이언트 인증서 제시)        (서버 인증서 제시) ▼
 ┌──────────────────────┐                        ┌──────────────────────┐
 │ Client Cert + 서명   │ ────────▶            ◀────────│ Server Cert + 서명   │
 └──────────────────────┘                                └──────────────────────┘
            │                                               │
            └─────────────── [ 상호 검증 성공 ] ──────────────┘
                                    │
                                    ▼
                 [ AES-GCM 대칭 세션 키 암호화 통신 ]
```

선의 의미: 공통 Root CA를 신뢰하는 양 엔드포인트 간 인증서 및 서명 교환을 거쳐 대칭 세션 키로 암호화 채널을 수립하는 구조

| 구성요소 | 책임 | 비고 |
|:---|:---|:---|
| **인증기관 (CA)** | 사설 PKI 또는 SPIFFE 기반으로 워크로드 인증서를 발급 및 생명주기 관리 | Trust Anchor |
| **클라이언트 인증서/개인키** | 클라이언트 워크로드의 신원을 나타내는 X.509 인증서와 소유권 증명용 개인키 | 클라이언트 신원 |
| **서버 인증서/개인키** | 서버 도메인/서비스 신원을 나타내는 X.509 인증서와 키 교환용 개인키 | 서버 신원 |
| **신뢰 저장소 (Trust Store)** | 상대방 인증서 체인의 유효성을 검증하기 위해 로컬에 저장된 신뢰 CA 인증서 목록 | 검증 기준 |
| **대칭 세션 키** | 상호 인증 완료 후 키 교환(ECDHE)을 통해 생성된 전송 구간 고속 암호화 키 | 기밀성/무결성 |

#### 한줄 요약
- CA, 클라이언트/서버 인증서 및 개인키, 신뢰 저장소, 대칭 세션 키가 결합하여 상호 인증을 완성한다.

## Ⅳ. 흐름도

<details><summary>용어 설명</summary>

- **CertificateRequest**: 서버가 클라이언트에게 신원 증명을 요구하며 허용 가능한 CA 목록을 전달하는 TLS 제어 메시지.
- **CertificateVerify**: 클라이언트가 핸드셰이크 메시지들의 해시값을 자신의 개인키로 서명하여 인증서 소유권을 증명하는 메시지.

</details>

```text
1. ClientHello: 클라이언트 암호 스위트 및 지원 TLS 버전 전송
            │
            ▼
2. ServerHello + Certificate + CertificateRequest: 서버 인증서 제시 및 클라이언트 인증 요구
            │
            ▼
3. 클라이언트의 서버 인증서 검증: 체인 유효성, 만료일, CRL/OCSP 상태 확인
            │
            ▼
4. Certificate + CertificateVerify + Finished: 클라이언트 인증서 및 개인키 전자서명 전송
            │
            ▼
5. 서버의 클라이언트 서명 검증 ➔ 상호 인증 완료 후 대칭 세션 키 기반 보안 통신 개시
```

**동작 원리**

1. **연결 시작**: 클라이언트가 서버로 ClientHello 전송
2. **서버 응답 및 요구**: 서버가 ServerHello와 함께 자신의 인증서를 전달하고 `CertificateRequest`를 송신하여 클라이언트 인증 요구
3. **서버 검증**: 클라이언트가 로컬 Trust Store를 참조하여 서버 인증서 체인을 검증
4. **클라이언트 증명**: 클라이언트가 자신의 X.509 인증서와 `CertificateVerify`(개인키 서명)를 서버로 전송
5. **서버 검증 및 완료**: 서버가 클라이언트 인증서와 서명을 검증한 후 세션 키를 유도하여 mTLS 암호화 통신 개시

#### 한줄 요약
- ClientHello, ServerHello/CertRequest, 클라이언트 인증서 검증, CertificateVerify 전송 및 서버 검증 순으로 수립된다.

## Ⅴ. 종류 및 비교

<details><summary>용어 설명</summary>

- **단방향 TLS(One-Way TLS)**: 일반 웹 브라우징(HTTPS)과 같이 클라이언트만 서버 인증서를 확인하고 서버는 클라이언트를 익명으로 수용하는 방식.

</details>

| 비교 항목 | mTLS (Mutual TLS) | 단방향 TLS (One-Way TLS) |
|:---|:---|:---|
| **인증 방향** | **양방향 상호 검증** (클라이언트 $\leftrightarrow$ 서버) | **단방향 검증** (클라이언트 $\rightarrow$ 서버 단독) |
| **적용 영역** | **M2M, 마이크로서비스(Service Mesh), 금융 API, 제로 트러스트** | **일반 대고객 웹 서비스(HTTPS)** |
| **클라이언트 신원** | 암호학적 X.509 인증서 기반 강한 기계 신원 보증 | 인증서 없음 (애플리케이션 계층 ID/PW 또는 토큰 의존) |
| **인증서 관리 부담** | 높음 (모든 클라이언트 단말/노드에 인증서 발급·갱신 필요) | 낮음 (서버 단일 인증서만 관리) |

#### 한줄 요약
- mTLS는 M2M 및 제로 트러스트 통신을 위한 양방향 검증을 제공하고, 단방향 TLS는 일반 대고객 웹 서비스에 적합하다.

## Ⅵ. 실무 고려사항 및 대책

<details><summary>용어 설명</summary>

- **SPIFFE/SPIRE**: 분산 이종 환경에서 워크로드에 표준화된 기계 신원(SPIFFE ID)과 단기 X.509 인증서(SVID)를 자동 발급하는 오픈소스 프레임워크.
- **서비스 메시(Service Mesh)**: 사이드카 프록시(Envoy 등)를 통해 애플리케이션 수정 없이 mTLS 암호화 및 인증서 로테이션을 인프라 계층에서 투명하게 처리하는 아키텍처.

</details>

| 문제 | 대책 | 효과 |
|:---|:---|:---|
| 수많은 마이크로서비스 간 인증서 만료로 인한 서비스 통신 장애 | **서비스 메시(Istio/Linkerd)** 및 **SPIFFE/SPIRE 기반 자동 로테이션** | 인증서 만료 사고 원천 차단 및 운영 오버헤드 최소화 |
| 유출된 클라이언트 인증서를 악용한 비인가 기계의 위장 접속 | **단기 유효 인증서(Short-Lived Cert)** 발행 및 실시간 **OCSP Stapling** | 인증서 탈취 시 피해 지속 시간 최소화 및 무효화 보증 |
| mTLS 인증 완료 후 모든 내부 API에 무제한 접근하는 권한 남용 | mTLS 신원(인증)과 **OPA/RBAC 기반 세부 인가(Authorization)** 분리 | 최소 권한 원칙(Least Privilege) 구현 및 내부 횡적 이동 차단 |

#### 한줄 요약
- 서비스 메시 기반 인증서 자동 로테이션, 단기 인증서 운용, mTLS와 RBAC 인가 분리를 통해 제로 트러스트를 달성한다.

## Ⅶ. 결론

- 클라우드 네이티브 및 제로 트러스트 환경에서 서비스 간 안전한 통신을 위해 **mTLS**를 표준 전송 보안 계층으로 채택하되, 인증서 수명 관리 복잡성을 해결하기 위해 **서비스 메시(Istio/Envoy)** 와 **SPIRE**를 도입하여 인증서 자동 발급·교체를 구성하고, **인증과 인가 분리** 원칙에 따른 세부 접근 제어 정책을 병행 수립

#### 한줄 요약
- mTLS와 서비스 메시 자동화를 결합하여 신뢰할 수 있는 제로 트러스트 M2M 보안 인프라를 구축한다.
