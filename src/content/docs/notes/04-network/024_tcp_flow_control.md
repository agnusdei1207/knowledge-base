## Ⅰ. 개요

<details><summary>용어 설명</summary>

- **TCP 흐름 제어(Flow Control)**: 송신 측과 수신 측 간의 처리 속도 차이로 인해 수신 버퍼 오버플로우(Buffer Overflow) 및 패킷 손실이 발생하는 것을 방지하기 위해 송신 데이터 전송량을 동적으로 제어하는 종단 간(End-to-End) 메커니즘.
- **수신 윈도우(Receive Window, rwnd)**: 수신 측이 현재 수신 버퍼의 가용 바이트 크기를 측정하여 송신 측에 통보(Advertise)하는 윈도우 크기.

</details>

- 정의/개념: 수신 측이 TCP 헤더의 Window 필드로 광고하는 가용 버퍼 크기(**rwnd**)에 맞춰 송신 측의 미확인 데이터 전송량을 제어하는 **종단 간 속도 조절 기제**
- 배경/필요성: 고속 송신자가 저속 수신자의 처리 용량을 초과하여 전송할 때 발생하는 수신 큐 고갈, 패킷 드롭 및 불필요한 재전송 오버헤드 해소 요구

#### 한줄 요약
- 수신 측의 가용 버퍼 크기(rwnd)에 맞추어 송신 데이터 전송량을 동적으로 조절한다.

## Ⅱ. 특징

<details><summary>용어 설명</summary>

- **혼잡 윈도우(Congestion Window, cwnd)**: 네트워크 망 내부의 혼잡 상태를 반영하여 송신 측이 결정하는 전송 상한 윈도우 크기.
- **유효 윈도우(Effective Window)**: 송신 측이 실제로 전송 가능한 바이트 크기로, $\min(\text{rwnd}, \text{cwnd}) - (\text{전송 후 미확인 바이트})$로 산출.

</details>

- 수신 측은 매 **ACK 패킷** 회신 시 가용 수신 버퍼 크기인 **rwnd** 값을 헤더에 명시하여 동적 피드백 제공
- 송신 측은 수신자 여유(**rwnd**)와 네트워크 혼잡도(**cwnd**) 중 **최솟값인 $\min(\text{rwnd}, \text{cwnd})$** 을 상한으로 송신
- **슬라이딩 윈도우(Sliding Window)** 알고리즘을 통해 매 패킷마다 개별 ACK를 대기하지 않고 연속 전송을 지원하여 링크 효율 극대화

#### 한줄 요약
- rwnd와 cwnd의 최솟값을 기준으로 슬라이딩 윈도우를 전진시키며 연속 전송을 수행한다.

## Ⅲ. 구조 및 구성요소

<details><summary>용어 설명</summary>

- **슬라이딩 윈도우(Sliding Window)**: ACK를 수신할 때마다 윈도우의 좌측 경계가 우측으로 이동(Slide)하면서 새로운 데이터를 추가 전송할 수 있도록 허용하는 전송 제어 구조.
- **지속 타이머(Persist Timer)**: 제로 윈도우(rwnd=0) 상황에서 수신 측의 윈도우 갱신(Update) ACK 유실 시 발생할 수 있는 교착 상태(Deadlock)를 방지하기 위해 주기적으로 윈도우 탐사 패킷을 전송하는 타이머.

</details>

```text
[ 송신 윈도우 구조 ]

 ┌──────────────────┬──────────────────────┬──────────────────────┬──────────────────┐
 │ 1. 전송 및 ACK 완료 │ 2. 전송 완료 / ACK 미수신 │ 3. 미전송 / 전송 가능 범위 │ 4. 미전송 / 전송 불가   │
 └──────────────────┴──────────────────────┴──────────────────────┴──────────────────┘
                    │ ◀──────────── 유효 송신 윈도우 (rwnd) ────────────▶ │
                    └─▶ ACK 수신 시 우측으로 윈도우 슬라이딩 (전진)
```

선의 의미: 수신 측의 ACK 수신에 따라 송신 윈도우가 좌에서 우로 이동하며 전송 가능 범위를 갱신하는 구조

| 구성요소 | 책임 | 비고 |
|:---|:---|:---|
| **송신 윈도우 관리기** | 광고된 rwnd 크기 내에서 미확인 데이터를 파이프라인으로 전송하고 ACK 수신 시 슬라이딩 | 송신 측 제어 |
| **수신 윈도우 관리기** | 수신 버퍼에서 애플리케이션이 데이터를 읽어간 후 가용 공간(rwnd)을 재계산하여 통보 | 수신 측 피드백 |
| **지속 타이머(Persist Timer)** | rwnd=0 도달 시 교착 상태를 방지하기 위해 주기적으로 1바이트 윈도우 프로브(Probe) 전송 | 데드락 방어 |
| **윈도우 확장 옵션(WSOPT)** | 기본 16비트(64KB) 헤더 한계를 극복하여 최대 1GB까지 윈도우 크기를 확장(RFC 7323) | BDP 극복 옵션 |

#### 한줄 요약
- 송수신 윈도우, 지속 타이머, 윈도우 스케일 옵션이 결합하여 수신 버퍼 오버플로우를 차단한다.

## Ⅳ. 흐름도

<details><summary>용어 설명</summary>

- **제로 윈도우(Zero Window)**: 수신 애플리케이션의 처리 지연으로 수신 버퍼가 완전히 고갈되어 `rwnd=0`을 통보한 상태.

</details>

```text
1. 수신 측이 수신 버퍼 잔여 용량 계산 ➔ TCP ACK 헤더의 Window 필드(rwnd) 통보
            │
            ▼
2. 송신 측이 min(rwnd, cwnd) 크기 계산 및 유효 윈도우 산출
            │
            ├─ [rwnd = 0 (제로 윈도우)] ──▶ 지속 타이머 가동 ➔ 1바이트 Window Probe 전송
            └─ [rwnd > 0 (정상 전송)]
                    │
                    ▼
3. 슬라이딩 윈도우 기반 연속 전송 (ACK 수신 대기 없이 윈도우 크기만큼 일괄 송출)
            │
            ▼
4. 수신 측 데이터 적재 및 ACK 회신 ➔ 윈도우 좌측 경계 우측 전진(Sliding)
```

**동작 원리**

1. **윈도우 통보**: 수신 측이 소켓 버퍼 상태를 계측하여 ACK 세그먼트에 `Window=rwnd` 기록 후 전송
2. **송신량 결정**: 송신 측이 수신자의 `rwnd`와 네트워크 `cwnd`를 비교하여 전송 한도 산출
3. **파이프라인 전송**: 허용된 윈도우 바이트 한도 내에서 세그먼트들을 연속 전송
4. **수신 및 슬라이딩**: 수신자가 패킷을 정상 수신하고 애플리케이션이 버퍼를 비우면 새로운 rwnd를 포함한 ACK 전송
5. **교착 방지**: `rwnd=0` 수신 시 송신을 중단하고 지속 타이머를 가동하여 윈도우 갱신 ACK 유실에 대응

#### 한줄 요약
- rwnd 통보, 유효 윈도우 연속 전송, ACK 수신 시 윈도우 전진, 제로 윈도우 시 프로브 전송으로 제어한다.

## Ⅴ. 종류 및 비교

<details><summary>용어 설명</summary>

- **정지-대기(Stop-and-Wait)**: 1개의 패킷을 전송한 후 수신 측의 ACK가 도착할 때까지 다음 패킷 전송을 멈추고 대기하는 방식.
- **슬라이딩 윈도우(Sliding Window)**: 윈도우 크기만큼의 복수 패킷을 ACK 수신 없이 연속 전송하고 윈도우를 이동시키는 방식.

</details>

| 비교 항목 | 슬라이딩 윈도우 (Sliding Window) | 정지-대기 (Stop-and-Wait) |
|:---|:---|:---|
| **전송 방식** | 허용된 윈도우(rwnd) 내에서 **ACK 대기 없이 연속 전송** | 단 1개의 세그먼트 전송 후 **반드시 ACK 수신 대기** |
| **대역폭 활용률(BDP)** | **높음** (네트워크 파이프라인 연속 활용) | **극히 낮음** (RTT 동안 링크가 유휴 상태로 방치) |
| **구현 복잡도** | 시퀀스 번호 추적, 재전송 큐, 버퍼 슬라이딩 관리 필요 | 단순 타이머 기반으로 구조가 매우 단순 |
| **적용 영역** | **현대 고속 TCP/IP 네트워크의 표준 흐름 제어** | TFTP, 초소형 임베디드 통신 등 제한적 환경 |

#### 한줄 요약
- 정지-대기 방식의 심각한 대역폭 낭비를 슬라이딩 윈도우의 연속 파이프라인 전송으로 극복한다.

## Ⅵ. 실무 고려사항 및 대책

<details><summary>용어 설명</summary>

- **대역폭-지연 곱(Bandwidth-Delay Product, BDP)**: 대역폭($\text{bps}$)과 왕복 시간($\text{RTT}$)의 곱으로, 파이프라인을 최대로 채우기 위해 요구되는 윈도우 크기($\text{BDP} = \text{Bandwidth} \times \text{RTT}$).
- **어리석은 윈도우 신드롬(Silly Window Syndrome, SWS)**: 수신 버퍼가 1바이트 비워질 때마다 작은 윈도우를 광고하고, 송신자도 작은 패킷을 전송하여 헤더 오버헤드가 폭증하는 비효율 현상(Clark 알고리즘 및 Nagle 알고리즘으로 해결).

</details>

| 문제 | 대책 | 효과 |
|:---|:---|:---|
| 수신 측 윈도우 갱신 ACK 유실로 인한 영구 송신 대기(**교착 상태**) | 송신 측 커널의 **지속 타이머(Persist Timer)** 및 Window Probe 활성화 | 윈도우 상태 자동 재동기화 및 데드락 해소 |
| 고속 광대역망(10Gbps 이상)에서 기본 64KB 윈도우 한계로 인한 속도 저하 | TCP 3-Way Handshake 시 **윈도우 스케일(Window Scale, RFC 7323)** 협상 | BDP에 부합하는 최대 1GB 윈도우 지원으로 전송률 극대화 |
| 작은 바이트 단위 전송으로 헤더 오버헤드가 급증하는 **SWS 현상** | 수신 측 **Clark 알고리즘**(MSS 이상 회복 시 통보) 및 송신 측 **Nagle** 결합 | 미세 패킷 전송 억제 및 네트워크 대역폭 효율 최적화 |

#### 한줄 요약
- 지속 타이머로 데드락을 방지하고, 윈도우 스케일로 BDP를 충족하며, Clark/Nagle로 SWS를 방어한다.

## Ⅶ. 결론

- 고속 네트워크 환경에서 수신 버퍼의 안정성을 유지하고 회선 처리량을 극대화하기 위해 **슬라이딩 윈도우** 메커니즘을 기반으로 **윈도우 스케일(Window Scaling)** 옵션을 필수 적용하되, SWS 방지 알고리즘과 지속 타이머를 결합하여 종단 간 전송 효율을 최적화

#### 한줄 요약
- 슬라이딩 윈도우와 윈도우 스케일 튜닝을 통해 고성능·무결점 흐름 제어를 완성한다.
