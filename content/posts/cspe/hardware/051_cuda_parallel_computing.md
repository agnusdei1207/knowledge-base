## Ⅰ. 개요
- **정의**: GPU(050 참조)의 수천 개 코어를 C/C++ 확장으로 범용 병렬 연산에 활용하는 프로그래밍 모델
- **배경/필요성**: 단일 CPU 코어의 클록 한계로 대규모 데이터 병렬 처리가 어려워, GPU의 SIMT 구조를 범용 연산에 개방할 프로그래밍 인터페이스가 필요함
- **비유**: CPU가 숙련 요리사 1명이라면, CUDA는 수천 명의 보조 요리사에게 동시에 같은 레시피를 나눠 맡기는 주방 관리 시스템임

| 출제 의도 | 반드시 짚을 핵심 | 감점 회피 포인트 |
|:---|:---|:---|
| GPU 병렬 프로그래밍 이해도 | 커널-스레드 블록-그리드 3계층 구조 | 메모리 계층별 접근 지연 차이를 수치로 구분할 것 |

> 요약: CUDA는 GPU의 대규모 병렬 코어를 범용 연산에 활용하기 위한 C/C++ 확장 프로그래밍 모델임

## Ⅱ. 구성요소
```text
Host(CPU) --> Kernel Launch --> Grid
                                 |
                    +------------+------------+
                    |            |            |
               Block(0,0)  Block(1,0)  Block(n,0)
                    |
          +---------+---------+
          |         |         |
      Thread(0) Thread(1) Thread(m)
          |         |         |
       Register  Register  Register
          |         |         |
          +--Shared Memory---+
                    |
              Global Memory (Device DRAM)
```

| 구성요소 | 설명 | 비유 |
|:---|:---|:---|
| 커널(Kernel) | GPU에서 실행되는 함수, 호출 시 수천 스레드가 동시 인스턴스화됨 | 전체 작업자에게 배포되는 작업 지시서 |
| 스레드(Thread) | 커널의 최소 실행 단위, 고유 `threadIdx`로 데이터 분할 담당 | 개별 작업자 1명 |
| 블록(Block) | 최대 1024개 스레드 묶음, Shared Memory를 공유하며 동기화 가능 | 한 테이블에서 협업하는 작업 조 |
| 그리드(Grid) | 블록들의 집합, 커널 1회 호출의 전체 실행 범위 | 공장 전체 작업 현장 |
| 레지스터(Register) | 스레드 전용, 접근 지연 약 1 사이클 | 작업자 손에 든 도구 |
| Shared Memory | 블록 내 공유, 접근 지연 약 5 사이클, 용량 48~100 KB | 같은 조가 쓰는 공용 작업대 |
| Global Memory | 전체 스레드 접근 가능, 접근 지연 약 400~600 사이클 | 중앙 창고 |

> 요약: 커널-블록-스레드 실행 계층과 레지스터-Shared-Global 메모리 계층이 CUDA의 핵심 구조임

## Ⅲ. 절차
```text
CPU 데이터 준비 --> GPU 메모리 할당(cudaMalloc)
    --> Host-to-Device 전송(cudaMemcpy)
        --> 커널 실행(<<<grid, block>>>)
            --> Device-to-Host 결과 회수
```
- 1단계: CPU에서 입력 데이터를 준비하고, `cudaMalloc`으로 GPU 메모리를 확보함
- 2단계: `cudaMemcpy`로 Host 데이터를 Device(GPU)로 전송함
- 3단계: `<<<gridDim, blockDim>>>` 구문으로 커널을 실행하여 수천 스레드가 병렬 연산을 수행함
- 4단계: 연산 완료 후 `cudaMemcpy`로 결과를 Host로 회수하고, `cudaFree`로 메모리를 해제함

> 요약: 메모리 할당-전송-커널 실행-결과 회수의 4단계로 CPU-GPU 간 협업이 이루어짐

## Ⅳ. 문제점
- Host-Device 전송 병목: PCIe 대역폭(최대 64 GB/s)이 GPU 연산 처리량(수 TB/s)에 비해 낮아 데이터 이동 시간이 전체 성능을 제한함
- Warp 분기 손실: 32개 스레드로 구성된 Warp 내 조건 분기 시 양쪽 경로를 순차 실행하여 처리량이 최대 50% 감소함
- 메모리 용량 한계: GPU VRAM(16~80 GB)이 시스템 메모리보다 작아 대규모 데이터셋 처리 시 분할 전송이 필요함

> 요약: 전송 병목, Warp 분기 손실, 메모리 용량 제약이 CUDA 활용의 주요 제한 요소임

## Ⅴ. 개선방안
1. 단기: CUDA 스트림과 비동기 전송으로 연산과 데이터 이동을 중첩(overlap)하여 전송 병목을 완화함
2. 중기: 분기 최소화 알고리즘 설계 및 Warp-level 프리미티브(`__shfl_sync`) 활용으로 분기 손실을 저감함
3. 장기: Unified Memory와 NVLink/CXL 기반 메모리 풀링으로 GPU 메모리 용량 제약을 해소함

> 요약: 비동기 전송, 분기 최소화, 통합 메모리 기술로 CUDA의 구조적 한계를 단계적으로 해소함

## Ⅵ. 전망
- 발전 방향: Multi-GPU 클러스터와 NVLink 기반 GPU-to-GPU 직접 통신으로 단일 노드 병렬 처리 규모가 수만 코어로 확장됨
- 기술사적 판단: AI/HPC 워크로드 증가로 CUDA 생태계의 중요성이 지속 확대되나, 벤더 종속 문제에 대한 대안(OpenCL, SYCL) 검토가 필요함
- 기술사 제언: CUDA 최적화 역량과 함께 하드웨어 독립적 병렬 프레임워크 전환 전략을 병행 수립할 필요가 있음
