# ✍️ Decap CMS는 정확히 무엇인가

Decap CMS는 정적 사이트용 웹 편집기입니다. 더 정확히 말하면, **Git 저장소를 백엔드로 사용하는 오픈소스 CMS**입니다.

관련 문서:
- [[hermes-architecture]]
- [[hermes-pipeline]]
- [[quartz-deployment]]

---

## 1. 한 줄 정의

Decap CMS는 **브라우저에서 문서를 수정하면, 그 결과를 별도 DB가 아니라 Git 저장소에 커밋 또는 PR로 반영하는 웹 편집 UI**입니다.

즉, Notion처럼 자기 DB를 중심으로 돌아가는 SaaS형 CMS가 아닙니다.

---

## 2. 기술적으로는 무엇인가

공식 문서 기준으로 Decap CMS는 다음 성격을 가집니다.

- 오픈소스 프로젝트
- Git 워크플로우를 감싸는 React 앱
- GitHub, GitLab, Bitbucket, Gitea/Forgejo 같은 Git 백엔드와 연동 가능
- 정적 사이트에 `admin/` 경로를 추가해 붙이는 방식

구성도 단순합니다.

- `admin/index.html`
- `admin/config.yml`

이 두 파일이 핵심입니다.

즉, 무거운 서버 애플리케이션을 새로 올리는 느낌보다는,

**정적 사이트 안에 웹 편집 콘솔을 하나 붙이는 방식**에 가깝습니다.

---

## 3. Quartz와의 관계

Decap CMS는 Quartz를 대체하는 기술이 아닙니다.

역할이 다릅니다.

- Quartz: Markdown을 읽기 좋은 웹사이트와 그래프 뷰로 렌더링
- Decap CMS: 브라우저에서 Markdown을 수정하고 Git에 반영

그래서 함께 쓰는 그림이 자연스럽습니다.

직원 입장에서는:

- `/` 또는 문서 URL에서 읽기
- `/admin/`에서 수정하기

이런 구조가 됩니다.

---

## 4. 왜 검토할 가치가 있는가

현재 구조의 약점은 "비개발자가 웹에서 수정하기 어렵다"는 점입니다.

Decap CMS를 붙이면:

- 브라우저에서 수정 가능
- 필드 기반 입력 폼 제공 가능
- 실시간 미리보기 가능
- 초안/리뷰/발행 흐름 사용 가능
- 결국 Git에 기록이 남음

즉, 사용성은 높이되 원본 소유권은 유지할 수 있습니다.

---

## 5. 저장 방식은 어떻게 되나

중요한 포인트는 여기입니다.

Decap CMS는 자체 DB를 주 저장소로 두지 않습니다.

대신:
- GitHub API 같은 백엔드 API로 파일을 읽고
- 수정 결과를 Git 커밋이나 PR로 저장하고
- 필요하면 draft/ready-to-review 워크플로우를 사용합니다

따라서 저장소 원본이 계속 중심입니다.

---

## 6. 장점

- 원본이 Git에 남는다
- Markdown 기반 구조를 유지할 수 있다
- 비개발자에게 웹 편집 UI를 줄 수 있다
- 승인 흐름을 PR 기반으로 가져갈 수 있다
- 정적 사이트와 궁합이 좋다

---

## 7. 한계

- Git 백엔드와 인증 구성이 필요하다
- 완전한 엔터프라이즈 문서관리시스템처럼 세밀한 권한 모델은 별도 포지 정책에 기대게 된다
- 실시간 협업 문서 편집기는 아니다
- 검색엔진 역할은 하지 않는다

즉, Decap CMS 하나로 모든 걸 해결하려 하면 안 됩니다.

---

## 8. 우리 구조에서의 적합성

우리 목표는 아래와 같습니다.

- 원본은 Markdown
- Quartz 그래프 뷰 유지
- AI도 같은 원본을 사용
- 운영 복잡도는 낮게

이 기준에서 Decap CMS는 꽤 잘 맞습니다.

왜냐하면:

- 기존 Git 구조를 버리지 않아도 되고
- Quartz 앞단에 `admin/`만 추가하면 되고
- 문서 승인 흐름을 GitHub PR과 자연스럽게 연결할 수 있기 때문입니다

---

## 9. 그래서 결론은 무엇인가

Decap CMS는 "웹에서 문서를 쉽게 고치게 해주는 Git 기반 편집 계층"입니다.

정리하면:

- Quartz 단독: 읽기/탐색은 강함
- Decap CMS 추가: 수정/승인 UX 보강
- 검색 고도화는 별도 인덱스 계층이 담당
- 에이전트 접속 표준화는 Hermes MCP가 담당

따라서 현재 구조를 해치지 않으면서 현실적으로 붙일 수 있는 첫 번째 확장 카드로 볼 수 있습니다.
