## 핵심 인사이트 (3줄 요약)

> 1. **본질**: 클라우드는 "물리 자원의 가상화·추상화 → API 기반 셀프서비스 → 탄력적 과금"으로, 가상화(VM)→컨테이너→쿠버네티스(K8s)→서버리스로 추상화 수준이 올라갈수록 운영 책임은 CSP로 이전된다.
> 2. **가치**: 확장성(Scale-out)·복원력(Resilience)·민첩성(CI/CD)을 동시에 얻되, 그 대가로 벤더 종속(Lock-in)·비용 통제(FinOps)·보안 경계 재정의(제로 트러스트)라는 트레이드오프를 감수한다.
> 3. **판단 포인트**: 기술사 답안은 "정의 암기"가 아니라 **왜 이 구조를 택하고(필요성), 무엇을 희생하며(트레이드오프), 어떻게 운영·통제하는가**(거버넌스)를 비교형·의사결정형으로 전개해야 고득점한다.

## Ⅰ. 과목 개요

- **기준**: 컴퓨터시스템응용기술사(컴시응) 관점, 과목 13 클라우드 아키텍처
- **과목 총 노트 수**: 372개 (스터디노트 기준)
- **과목 정의**: 물리 인프라(컴퓨팅·스토리지·네트워크)를 가상화·소프트웨어 정의 기술로 추상화하여, 주문형 셀프서비스와 탄력적 확장이 가능한 분산 시스템을 설계·운영하는 아키텍처 영역.
- **출제 경향**:
  - 단순 IaaS/PaaS/SaaS 비교를 넘어 **가상화 ↔ 컨테이너 ↔ 쿠버네티스 ↔ MSA ↔ 서버리스**의 연결 구조와 선택 기준을 묻는다.
  - 확장성·가용성·복원력·비용·보안·운영복잡도를 **동시에 저울질하는 의사결정형** 문제가 핵심.
  - 최신 동향: 클라우드 네이티브(CNCF), 서비스 메시, GitOps, 플랫폼 엔지니어링, 소버린 클라우드, FinOps.
- **약어 표기 원칙**: 최초 1회 풀네임 병기 — 예: MSA(Microservices Architecture, 마이크로서비스 아키텍처).

## Ⅱ. 1교시 단답형 핵심 (앞단위)

> **1교시 답안 공식 (1줄)**: `정의 1문장 → 핵심 3포인트(원리/효과/한계) → ASCII 도해 3줄 → 미니 표 3행 → 적용·비교 1줄`. 13문제 중 10문제, 각 10점, 문제당 약 10분.

| 키워드 | 한줄 정의 | 핵심 3포인트 |
|:---|:---|:---|
| **IaaS / PaaS / SaaS** | 클라우드 서비스 3계층 모델로 추상화 수준에 따라 책임 경계가 달라짐 | ①IaaS=VM·스토리지·네트워크 제공(EC2) ②PaaS=런타임·미들웨어까지(Beanstalk) ③SaaS=완제품 SW(Salesforce) |
| **FaaS / 서버리스** | 서버 프로비저닝 없이 함수 코드 단위로 배포, 이벤트 호출 시 밀리초 과금 | ①관리 부담 0·자동 확장 ②상태 비저장(Stateless) 제약 ③콜드 스타트(Cold Start) 지연·벤더 락인 |
| **가상화 vs 컨테이너** | VM은 Guest OS 전체 격리, 컨테이너는 호스트 커널 공유 프로세스 격리 | ①VM=강한 격리·무거움 ②컨테이너=경량·밀리초 기동 ③컨테이너 보안 취약(Container Escape) |
| **하이퍼바이저** | VM을 생성·스케줄링하는 가상화 커널 SW(VMM) | ①Type1 베어메탈(ESXi,KVM) 고성능 ②Type2 호스트형(VirtualBox) ③전가상화 vs 반가상화 |
| **컨테이너(Docker)** | 앱+의존성을 불변 이미지로 묶어 커널 공유로 격리하는 경량 가상화 | ①Namespace=자원 격리 ②cgroups=자원 상한 ③이미지 레이어(UnionFS)·OCI 표준 |
| **쿠버네티스(K8s)** | 컨테이너를 자동 배치·확장·복구하는 오케스트레이션 사실상 표준 | ①Control Plane(API/etcd/Scheduler) ②Worker(Kubelet/Pod) ③선언적(Declarative) 상태 관리 |
| **Pod / 워크로드** | K8s 최소 배포 단위(Pod)와 상위 컨트롤러 | ①ReplicaSet=개수 보장·Self-healing ②Deployment=롤링·롤백 ③StatefulSet=상태·PV 유지 |
| **K8s 서비스/Ingress** | 동적 Pod IP를 고정 진입점·도메인으로 추상화하는 네트워킹 | ①ClusterIP(내부)/NodePort/LoadBalancer ②Ingress=L7 경로 라우팅 ③kube-proxy 규칙 |
| **오토스케일링** | 임계치 기반 자원 자동 증감으로 탄력성 확보 | ①HPA=Pod 수평 증설 ②VPA=Pod 리소스 수직 ③CA(Cluster Autoscaler)=노드 증설 |
| **IaC** | 인프라를 코드로 정의·버전관리(Terraform, Ansible) | ①멱등성(Idempotency) ②선언형 vs 명령형 ③불변 인프라·구성편류(Drift) 방지 |
| **멀티/하이브리드 클라우드** | 2개 이상 퍼블릭(멀티) 또는 퍼블릭+프라이빗(하이브리드) 혼용 | ①벤더 락인 회피·가용성 ②망연계(VPN/전용선) ③데이터 그래비티·운영 복잡도 ↑ |
| **소버린 클라우드** | 데이터 주권·법규(개인정보·국가안보) 준수를 보장하는 격리 클라우드 | ①데이터 거주성(Residency) ②운영·관할권 자국 통제 ③EU GDPR·공공 부문 수요 |
| **FinOps** | 클라우드 비용을 가시화·최적화하는 재무 운영 문화 | ①Inform(태깅·가시성) ②Optimize(RI·스팟·Rightsizing) ③Operate(지속 셧다운·거버넌스) |
| **서비스 메시** | MSA 통신 관리를 인프라 계층 프록시로 분리(Istio, Linkerd) | ①사이드카(Envoy) 프록시 ②mTLS 보안·관측성 ③Control/Data Plane 분리 |
| **MSA** | 도메인 단위 독립 서비스로 분해, 자율 개발·독립 배포 | ①느슨한 결합·폴리글랏 DB ②API 게이트웨이 단일 진입 ③분산 트랜잭션(Saga) 복잡 |
| **서킷 브레이커** | 장애 서비스 호출을 차단해 연쇄 장애(Cascading) 전파 방지 | ①Open 시 호출 차단 ②폴백(Fallback) 대체 응답 ③벌크헤드와 함께 복원력 확보 |
| **클라우드 네이티브 / CNCF** | 컨테이너·MSA·선언형 API 기반 확장·탄력·관측 극대화 철학 | ①12-Factor App ②CNCF=K8s·Prometheus 등 표준 재단 ③GitOps·옵저버빌리티 결합 |
| **GitOps** | Git을 단일 진실원천(SSOT)으로 선언적 인프라 상태를 자동 동기화 | ①Pull 기반 배포(ArgoCD) ②선언형 YAML ③감사 추적·자동 롤백 |

## Ⅲ. 2~4교시 서술형 확장 (심화)

> 서술형: 6문제 중 4문제, 각 25점, 문제당 약 22~24분, 3~3.5쪽. 전개 골격 = Ⅰ.개요 → Ⅱ.구조/원리(도식) → Ⅲ.특징/비교(표) → Ⅳ.적용/방안 → Ⅴ.결론.

### 1. 쿠버네티스(Kubernetes) 아키텍처

- **정의**: 구글 보그(Borg)에서 유래한, 컨테이너의 배포·확장·네트워킹·자가복구(Self-healing)를 선언적으로 자동화하는 컨테이너 오케스트레이션 사실상 표준.

**Ⅰ. 개요·필요성**: 컨테이너가 수백~수만 개로 늘면 수동 관리가 불가능 → 원하는 상태(Desired State)를 선언하면 컨트롤러가 현재 상태를 지속 일치시키는 자동화 필요.

**Ⅱ. 구조 (구조도)**
```text
            [ kubectl / CI·CD / GitOps ]
                      │ REST
   ┌──────────────────▼───────────────────┐
   │        Control Plane (마스터)          │
   │  API Server ─ etcd(상태저장 KV)        │
   │  Scheduler(배치) ─ Controller Manager  │
   └───────┬───────────────────┬───────────┘
           │ 명령              │ 명령
   ┌───────▼──────┐    ┌───────▼──────┐
   │ Worker Node1 │    │ Worker Node2 │
   │ Kubelet      │    │ Kubelet      │
   │ kube-proxy   │    │ kube-proxy   │
   │ [Pod][Pod]   │    │ [Pod][Pod]   │
   │ Container RT │    │ Container RT │
   └──────────────┘    └──────────────┘
```

**Ⅲ. 핵심 컴포넌트**

| 구분 | 구성요소 | 역할 |
|:---|:---|:---|
| 마스터 | API Server | 모든 명령 수신·중계 허브 |
| 마스터 | etcd | 클러스터 상태·메타데이터 분산 KV 저장 |
| 마스터 | Scheduler | Pod를 적합한 노드에 배치 결정 |
| 마스터 | Controller Manager | Desired=Current 상태 일치 제어 루프 |
| 워커 | Kubelet | Pod 생성·헬스체크·보고 에이전트 |
| 워커 | kube-proxy | 서비스 라우팅·로드밸런싱 규칙(iptables/IPVS) |

**Ⅳ. 적용·운영 방안**: ①워크로드 — Deployment(무중단 롤링)/StatefulSet(DB)/DaemonSet(로그) 선택 ②오토스케일링 — HPA(Pod)+CA(노드) 조합 ③스토리지 — PV/PVC·CSI 표준 ④프로브(Liveness/Readiness)로 생명주기 관리 ⑤Helm·ArgoCD로 배포 자동화.

**Ⅴ. 결론**: K8s는 클라우드 네이티브의 운영 표준이나, 인지 부하가 커 플랫폼 엔지니어링(IDP)·관리형 서비스(EKS/GKE)로 운영 복잡도를 흡수하는 방향이 바람직하다.

### 2. 클라우드 서비스 모델 & 책임 공유 모델

- **정의**: 추상화 수준에 따라 IaaS/PaaS/SaaS로 구분되며, CSP와 사용자가 보안·운영 책임을 계층별로 분담하는 모델.

**Ⅱ. 책임 분담 구조 (비교표)**

| 계층 (관리 주체) | On-Premise | IaaS | PaaS | SaaS |
|:---|:---:|:---:|:---:|:---:|
| 애플리케이션 | 사용자 | 사용자 | 사용자 | **CSP** |
| 데이터 | 사용자 | 사용자 | 사용자 | 사용자 |
| 런타임·미들웨어 | 사용자 | 사용자 | **CSP** | **CSP** |
| OS | 사용자 | 사용자 | **CSP** | **CSP** |
| 가상화·서버·스토리지 | 사용자 | **CSP** | **CSP** | **CSP** |
| 네트워크·물리 | 사용자 | **CSP** | **CSP** | **CSP** |
| 대표 예시 | 자체 DC | EC2, S3 | Beanstalk | Salesforce |

**Ⅲ. 핵심 특징·트레이드오프**

| 구분 | IaaS | PaaS | SaaS |
|:---|:---|:---|:---|
| 자유도/제어 | 높음 | 중간 | 낮음 |
| 운영 부담 | 큼 | 중간 | 거의 없음 |
| 락인 위험 | 낮음 | 높음 | 높음 |
| 적합 | 레거시 이관·커스텀 | 앱 개발 집중 | 표준 업무 SW |

**Ⅳ. 적용 방안 (마이그레이션 6R)**: Rehost(Lift&Shift)→Replatform→Refactor→Repurchase→Retire→Retain. 핵심은 "데이터 그래비티·락인·비용"을 함께 평가하여 단계적 전환.

**Ⅴ. 결론**: 책임 공유 모델은 보안 사고 책임 경계의 기준선이며, "사용자 책임 영역(데이터·접근통제)"을 명확히 인식하는 것이 클라우드 보안의 출발점이다.

### 3. 마이크로서비스 아키텍처(MSA)와 분산 트랜잭션

- **정의**: 애플리케이션을 비즈니스 도메인 단위의 작고 독립적인 서비스로 분해(느슨한 결합)하여 자율 개발·독립 배포하는 아키텍처.

**Ⅱ. 구조 (구조도)**
```text
        [ Client (Web/Mobile) ]
                 │
        ┌────────▼────────┐
        │  API Gateway    │ 인증·라우팅·스로틀링
        └───┬────┬────┬───┘
            ▼    ▼    ▼
       [주문] [결제] [배송]   ← 각 서비스 독립 DB
         │DB    │DB   │DB
            ↘   │   ↙  비동기 이벤트
        [ Message Broker (Kafka) ]
            (Saga / 보상 트랜잭션)
```

**Ⅲ. 모놀리식 vs MSA (비교표)**

| 구분 | 모놀리식 | MSA |
|:---|:---|:---|
| 결합도 | 강결합 단일 코드 | 느슨한 결합 분산 |
| 배포 | 전체 재배포 | 서비스별 독립 배포 |
| 확장 | 전체 Scale | 필요 서비스만 Scale |
| 기술스택 | 단일 종속 | 폴리글랏 자유 |
| 트랜잭션 | ACID 단순 | 분산·결과적 일관성 |
| 단점 | 빌드 지연·종속 | 운영·통신 복잡도 ↑ |

**Ⅳ. 핵심 패턴**: ①API 게이트웨이(단일 진입·인증) ②서비스 디스커버리(동적 IP) ③서킷 브레이커+폴백(연쇄 장애 차단) ④**Saga 패턴**(2PC 대안, 로컬 트랜잭션+보상 트랜잭션으로 논리적 롤백) ⑤CQRS·이벤트 소싱(읽기/쓰기 분리) ⑥스트랭글러 피그(레거시 점진 이관).

**Ⅴ. 결론**: MSA는 만능이 아니며, 도메인 주도 설계(DDD)의 바운디드 컨텍스트로 분해 기준을 잡고, 조직 성숙도·운영 자동화(DevOps) 역량이 갖춰질 때 도입해야 한다.

### 4. 클라우드 네이티브 & DevOps/관측성

- **정의**: 컨테이너·MSA·선언형 API·CI/CD를 결합해 확장성·탄력성·관측성을 극대화하는 12-Factor 기반 개발·운영 패러다임.

**Ⅱ. 파이프라인 흐름 (흐름도)**
```text
[Code/Git] →[CI 빌드·테스트]→[이미지·SAST/SCA]
     │                              │
     ▼                              ▼
[GitOps(ArgoCD) Pull 동기화] → [K8s 배포]
     │                              │
     └──[Observability: MELT]◄──────┘
        (Metric/Log/Trace → 자동복구·SRE)
```

**Ⅲ. 무중단 배포·관측 (비교표)**

| 배포 전략 | 방식 | 장점 | 단점 |
|:---|:---|:---|:---|
| 롤링 | 점진 교체 | 자원 효율 | 구·신 공존 혼선 |
| 블루-그린 | 환경 복제 스위칭 | 즉시 롤백 | 자원 2배 |
| 카나리 | 소수 트래픽 점증 | 리스크 최소 | 모니터링 부담 |

**Ⅳ. 핵심 운영 개념**: ①IaC·불변 인프라(구성편류 방지) ②DevSecOps(Shift-Left 보안) ③SRE — SLI/SLO/SLA·에러 예산·토일(Toil) 축소 ④옵저버빌리티 3요소(메트릭=Prometheus, 로그=ELK, 분산추적=OpenTelemetry/Jaeger)+4 골든 시그널 ⑤카오스 엔지니어링으로 복원력 검증.

**Ⅴ. 결론**: 클라우드 네이티브는 도구 도입이 아닌 문화(CALMS)·자동화·측정의 결합이며, 플랫폼 엔지니어링으로 개발자 셀프서비스를 제공해 인지 부하를 줄이는 것이 성숙 단계의 과제다.

---

### 5. 멀티/하이브리드 클라우드 & FinOps 전략

- **정의**: 벤더 종속 회피·가용성·규제 대응을 위해 2개 이상 퍼블릭(멀티) 또는 퍼블릭+프라이빗(하이브리드)을 혼용하고, 그 비용을 가시화·최적화(FinOps)하는 운영 전략.

**Ⅲ. 멀티 vs 하이브리드 (비교표)**

| 구분 | 멀티 클라우드 | 하이브리드 클라우드 |
|:---|:---|:---|
| 구성 | AWS+Azure+GCP | 퍼블릭+프라이빗/레거시 |
| 목적 | 락인 회피·가용성 | 민감정보 내부+탄력성 외부 |
| 연계 | 추상화 계층·K8s | VPN·전용선 망연계 |
| 난점 | 운영 표준화·관제 | 데이터 그래비티·지연 |

**Ⅳ. FinOps 라이프사이클 & 적용 방안**: ①**Inform** — 태깅으로 비용 가시화·부서별 할당 ②**Optimize** — RI(예약)·스팟 인스턴스·Rightsizing·오버프로비저닝 제거 ③**Operate** — 미사용 자원 스케줄 셧다운·지속 거버넌스. 추가로 소버린 클라우드(데이터 주권), 분산 클라우드(엣지 통제)로 규제·저지연 요구에 대응.

**Ⅴ. 결론**: 멀티 클라우드는 락인을 줄이지만 운영 복잡도·비용 통제 부담을 키우므로, FinOps·표준화(K8s·IaC)·관측성 통합이 전제될 때 실효적이다.

## Ⅳ. 출제 포인트 & 함정

| 출제유형 | 1교시 단답 포인트 | 2~4교시 서술 포인트 |
|:---|:---|:---|
| 가상화·컨테이너 | Type1/2, Namespace·cgroups | VM vs 컨테이너 격리·성능 트레이드오프 비교 |
| 쿠버네티스 | API Server·etcd·Kubelet 역할 | 구조도+자가복구·오토스케일링 설계 |
| 서비스 모델 | IaaS/PaaS/SaaS·FaaS 정의 | 책임 공유 모델·마이그레이션 6R 의사결정 |
| MSA·서버리스 | 서킷 브레이커·Saga·콜드 스타트 | 모놀리식→MSA 분해 기준·분산 트랜잭션 |
| DevOps·SRE | HPA, GitOps, SLI/SLO/에러예산 | CI/CD·무중단 배포·관측성 통합 운영 |
| 멀티 클라우드 | 락인·데이터 그래비티·FinOps | 멀티/하이브리드 운영모델·비용 최적화 |

**함정 (감점 포인트)**
- **HPA vs VPA vs CA 혼동**: HPA=Pod 수평 증설, VPA=Pod 리소스 수직, CA=노드 증설. 셋을 구분 못 하면 감점.
- **Pod ≠ 컨테이너**: Pod는 1개 이상 컨테이너의 최소 배포 단위(사이드카 포함 가능).
- **2PC를 클라우드 분산 트랜잭션 정답으로 쓰기**: MSA에서는 블로킹 병목으로 배제 → Saga·결과적 일관성이 정답.
- **서버리스를 만능으로 서술**: 상태 비저장·콜드 스타트·벤더 락인 한계를 반드시 병기.
- **멀티 클라우드 = 무조건 좋음**: 운영 복잡도·표준화 비용 트레이드오프를 누락하면 통찰 부족.
- **책임 공유 모델에서 데이터 책임**: 데이터·접근통제는 SaaS에서도 사용자 책임임을 명시.
- **약어 풀네임 누락**: MSA, IaC, HPA, mTLS, CNCF 등 최초 1회 풀네임 병기 필수.
