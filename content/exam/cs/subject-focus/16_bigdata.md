## 핵심 인사이트 (3줄 요약)

> 1. **본질**: 빅데이터는 3V/5V로 정의되는 대용량·고속·다양한 데이터를 **분산 저장(HDFS)·분산 처리(MapReduce/Spark)·분석·서비스**로 연결하는 시스템 체계다.
> 2. **가치**: 배치(Hadoop)→인메모리(Spark)→실시간 스트리밍(Kafka/Flink)으로 진화하며, 저장은 데이터 레이크하우스(Delta/Iceberg)와 벡터 DB로 수렴 중이다.
> 3. **판단 포인트**: 답안은 단순 플랫폼 나열이 아닌 **아키텍처 선택 근거(성능·확장성·비용·정합성·운영복잡도 트레이드오프) + 거버넌스 + AI 연계**를 통합 서술해야 고득점.

## Ⅰ. 과목 개요

- **과목 성격**: 빅데이터는 대규모 분산 저장·처리·분석 시스템을 다루므로, 컴퓨터시스템응용기술사에서 **분산 아키텍처 설계 역량**과 **데이터 활용 가치**를 동시에 평가하는 과목이다.
- **과목 총 노트 수**: 262개 (studynote 기준) / 본 트랙은 그중 **진짜 핵심 12키워드 + 서술 3주제**로 압축.
- **출제 흐름**: 하둡(Hadoop)·스파크(Spark)·스트리밍·NoSQL(Not Only SQL) 기반 → 최근 **레이크하우스, 실시간 OLAP(Online Analytical Processing), 벡터 데이터베이스, AI 연계 분석 플랫폼**으로 관점 이동.
- **학습 전략**: 저장 구조(HDFS/Parquet) → 처리 엔진(MapReduce/Spark/Flink) → 데이터 품질·거버넌스 → 서비스 활용까지 **하나의 파이프라인으로 연결**해 서술하는 훈련이 핵심.

## Ⅱ. 1교시 단답형 핵심 (앞단위)

> 단답형: 13문제 중 10문제, 각 10점, 약 10분/문제. 약어는 최초 1회 풀네임 병기.

| 키워드 | 한줄 정의 | 핵심 3포인트 |
|:---|:---|:---|
| 빅데이터 3V/5V | Volume·Velocity·Variety(+Veracity·Value)로 규정하는 대용량 데이터 특성 (Laney, 2001) | ① 3V=양/속도/다양성 ② 5V=정확성·가치 추가 ③ 정형<20%, 비정형>80% |
| Hadoop | 분산 저장(HDFS)+분산 처리(MapReduce)+자원관리(YARN) 오픈소스 프레임워크 | ① 범용 서버 수평 확장 ② 배치 처리 중심 ③ 에코시스템(Hive·HBase·Sqoop) |
| HDFS (Hadoop Distributed File System) | 블록 단위 분산 저장 파일시스템 | ① 블록 128MB·3중 복제 ② NameNode(메타)/DataNode(블록) ③ Rack Awareness 장애복구 |
| MapReduce | Map→Shuffle&Sort→Reduce 3단계 분산 처리 모델 | ① Map: (K,V) 출력 ② Reduce: 동일 K 집계 ③ Shuffle 네트워크 병목 |
| Spark | RDD 기반 인메모리 분산 처리 엔진 (MapReduce 대비 최대 100배) | ① Lazy Evaluation(변환 지연) ② Catalyst·Tungsten 최적화 ③ SQL·MLlib·Streaming 통합 |
| RDD (Resilient Distributed Dataset) | 불변·분산·결함허용 데이터 추상화 | ① Lineage 기반 복구 ② Transformation/Action 구분 ③ DataFrame/Dataset로 진화 |
| 람다 아키텍처 | 배치(Batch)+속도(Speed)+서빙(Serving) 3계층 통합 처리 | ① 정확성(배치)+실시간(스트림) ② 이중 코드베이스 부담 ③ Serving Layer 병합 |
| 카파 아키텍처 | 스트리밍 단일 경로로 단순화한 아키텍처 | ① Kafka+Flink ② 코드 단일화 ③ 재처리=로그 리플레이 |
| NoSQL (Not Only SQL) | RDBMS 수평확장 한계 극복용 비관계형 DB군 | ① BASE 원칙 ② 키값/문서/컬럼/그래프 4유형 ③ CAP 정리 트레이드오프 |
| 분산처리 (CAP 정리) | 일관성·가용성·분할내성 중 2개만 동시 보장 | ① C+A / C+P / A+P 선택 ② PACELC 확장(지연 vs 일관성) ③ 튜닝 가능한 일관성 |
| 데이터마이닝 | 대용량 데이터에서 패턴·규칙·지식 추출 | ① 분류·군집·연관·예측 ② 연관규칙(Apriori/FP-Growth) ③ 지지도·신뢰도·향상도 |
| 벡터 DB (Vector Database) | 고차원 임베딩 벡터의 유사도 검색 특화 DB | ① ANN(근사최근접) 인덱스 ② RAG·생성형 AI 검색 ③ Pinecone/Milvus/pgvector |

> **1교시 답안 공식 (1줄)**: `정의 1줄 → 핵심 특징 3개(번호) → ASCII 도해 3줄 → 미니 표 3행(목적/장점/한계) → 적용·비교 1줄`.

## Ⅲ. 2~4교시 서술형 확장 (심화)

> 서술형: 교시별 6문제 중 4문제, 각 25점, 약 22~24분/문제. 전개: Ⅰ개요 → Ⅱ구조/원리 → Ⅲ특징/비교 → Ⅳ적용/방안 → Ⅴ결론.

### 주제 1. 하둡(Hadoop) vs 스파크(Spark) 분산 처리 비교

**정의**: 하둡은 디스크 기반 배치 분산 처리 프레임워크, 스파크는 RDD 기반 인메모리 분산 처리 엔진이다.

- **Ⅰ. 개요**: 데이터 폭증(제타바이트 시대)으로 단일 서버 RDBMS 한계 → 수평 확장형 분산 처리 필요성 대두.
- **Ⅱ. 구조 및 원리**

```text
[입력 데이터 / HDFS]
        ↓
 ┌──────────────┐        ┌──────────────┐
 │  MapReduce   │        │    Spark     │
 │ Map→Shuffle  │  vs    │ RDD(메모리)  │
 │   →Reduce    │        │ DAG 스케줄러 │
 │ (디스크 I/O) │        │ Catalyst 최적│
 └──────┬───────┘        └──────┬───────┘
        ↓                       ↓
   [YARN 자원관리]        [Driver/Executor]
        ↓
   [결과 저장 / 서빙]
```

- **Ⅲ. 특징 비교**

| 구분 | Hadoop MapReduce | Spark |
|:---|:---|:---|
| 처리 방식 | 디스크 기반 배치 | 인메모리(최대 100배) |
| 지연 시간 | 높음(분 단위) | 낮음(초~ms) |
| 추상화 | 저수준 Java 코드 | RDD/DataFrame 고수준 API |
| 실시간 | 미지원(배치) | Structured Streaming 지원 |
| 결함 복구 | 데이터 재복제 | Lineage 재계산 |
| 적합 워크로드 | 대용량 일괄 ETL | 반복 ML·대화형 분석·실시간 |

- **Ⅳ. 적용 방안**: ① 대용량 야간 배치·아카이빙 → Hadoop, ② 반복 머신러닝·대화형 쿼리·스트리밍 → Spark, ③ 혼합 시 HDFS 저장 + Spark 처리 조합, ④ 클라우드는 EMR/Dataproc 관리형으로 운영 부담 절감.
- **Ⅴ. 결론**: 스파크가 사실상 표준 처리 엔진으로 자리잡았으나, 저장 계층(HDFS/오브젝트 스토리지)과 자원관리(YARN/K8s)는 여전히 하둡 생태계와 연계되므로 **워크로드 특성별 선택**이 기술사적 판단이다.

### 주제 2. 람다(Lambda) vs 카파(Kappa) 아키텍처

**정의**: 람다는 배치+스트리밍 이중 경로로 정확성과 실시간성을 모두 추구하는 아키텍처, 카파는 스트리밍 단일 경로로 단순화한 아키텍처다.

- **Ⅰ. 개요**: 실시간 이상 감지·즉각 대응 의사결정 수요 증가 → 배치만으로는 지연 한계 → 실시간/배치 통합 아키텍처 등장.
- **Ⅱ. 구조 및 원리**

```text
[람다]                         [카파]
[데이터 소스]                  [데이터 소스]
   ├──→ [Batch Layer]            └──→ [Kafka 로그]
   │     (정확·전체 재계산)             ↓
   └──→ [Speed Layer]            [Stream(Flink)]
         (실시간 근사)                   ↓
        ↓        ↓                 [Serving]
      [Serving Layer 병합]        (재처리=리플레이)
```

- **Ⅲ. 특징 비교**

| 구분 | 람다(Lambda) | 카파(Kappa) |
|:---|:---|:---|
| 처리 경로 | 배치+스트리밍 2중 | 스트리밍 단일 |
| 정확성 | 배치로 보정(높음) | 스트림 일관 처리 |
| 코드 복잡도 | 이중 코드베이스(높음) | 단일 코드(낮음) |
| 재처리 | 배치 재실행 | 로그 리플레이 |
| 대표 스택 | Hadoop+Storm/Spark | Kafka+Flink |
| 적합 상황 | 정합성 critical·과거 보정 | 실시간 우선·운영 단순화 |

- **Ⅳ. 적용 방안**: ① 금융 정산·규제 보고처럼 정확성 critical → 람다, ② 실시간 추천·IoT 모니터링 → 카파, ③ Exactly-Once 보장 위해 2PC+Idempotent Sink·Watermark 적용, ④ 최근 스트리밍 엔진 성숙으로 **카파 우선** 추세.
- **Ⅴ. 결론**: 스트리밍 처리의 정확성·상태관리(Flink Checkpoint)가 성숙하며 카파로 단순화되는 흐름이나, 대규모 과거 데이터 보정이 필요한 도메인은 람다가 유효하다.

### 주제 3. 데이터 레이크하우스(Data Lakehouse) 아키텍처

**정의**: 데이터 레이크의 유연성(저비용·원시 데이터)과 데이터 웨어하우스의 성능·ACID를 결합한 통합 저장 아키텍처다.

- **Ⅰ. 개요**: 레이크는 거버넌스 부재 시 데이터 스왐프(Swamp)로 변질, DW는 비정형·비용 한계 → 오픈 테이블 포맷(Delta/Iceberg/Hudi) 기반 레이크하우스 등장.
- **Ⅱ. 구조 및 원리 (Medallion 3계층)**

```text
[원시 소스: 로그/IoT/RDBMS]
        ↓ (ELT 수집)
 ┌────────────────────────────┐
 │ Bronze(원시) → Silver(정제)│
 │           → Gold(집계)      │
 │  Delta/Iceberg 테이블 포맷  │
 │  ACID·타임트래블·스키마강제 │
 └────────────┬───────────────┘
              ↓
   [BI·ML·벡터검색 서빙 + Unity Catalog 거버넌스]
```

- **Ⅲ. 특징 비교**

| 구분 | 데이터 레이크 | 데이터 웨어하우스 | 레이크하우스 |
|:---|:---|:---|:---|
| 스키마 | Schema-on-Read | Schema-on-Write | 둘 다 지원 |
| 데이터 | 원시·비정형 | 정형 | 통합 |
| ACID | 미지원 | 지원 | 지원(Delta) |
| 비용 | 저비용 | 고비용 | 저비용+성능 |
| AI/ML | 직접 접근 | 제한적 | 네이티브 |

- **Ⅳ. 적용 방안**: ① 컬럼 포맷(Parquet/ORC) + 오픈 테이블 포맷으로 표준화, ② Medallion 3계층으로 품질 단계화, ③ Unity Catalog/Data Catalog로 계보(Lineage)·거버넌스 통합, ④ 벡터 DB 연계로 RAG·생성형 AI 데이터 공급체계 확장.
- **Ⅴ. 결론**: 레이크하우스는 저장·분석·AI를 단일 플랫폼으로 통합하는 모던 데이터 스택의 중심이며, **오픈 포맷 + 거버넌스 + 컴퓨트-스토리지 분리**가 성공 요건이다.

## Ⅳ. 출제 포인트 & 함정

| 출제유형 | 1교시 단답 포인트 | 2~4교시 서술 포인트 |
|:---|:---|:---|
| 분산 저장 | HDFS 블록 128MB·3중 복제·NameNode SPOF | HDFS vs 오브젝트 스토리지, 컴퓨트-스토리지 분리 설계 |
| 분산 처리 | MapReduce 3단계, Spark Lazy Evaluation·RDD | Hadoop vs Spark 비교, 워크로드별 엔진 선택 근거 |
| 실시간 처리 | Kafka·Flink·Watermark·Exactly-Once | 람다 vs 카파, 스트리밍 정합성 보장 방안 |
| 저장 아키텍처 | 레이크 vs DW vs 레이크하우스, Delta/Iceberg | Medallion 3계층, 데이터 메시·거버넌스 통합 |
| NoSQL/일관성 | CAP·PACELC·BASE, 4유형 DB | 일관성 수준 선택과 트레이드오프 설계 |
| AI 연계 | 벡터 DB·RAG·임베딩 | 빅데이터를 AI 학습·추론 데이터 공급체계로 확장 |

**함정 정리**:
- **람다 vs 카파 역전**: 람다=배치+스트림 이중, 카파=스트림 단일. Batch Layer가 람다에만 존재 (혼동 주의).
- **NameNode SPOF**: NameNode는 단일 장애점 → HA NameNode/Secondary NameNode로 보완해야 함. DataNode와 역할 혼동 금지.
- **Spark가 Hadoop 대체?**: Spark는 처리 엔진일 뿐, 저장(HDFS)·자원관리(YARN)는 여전히 필요. "Spark가 하둡을 완전 대체"는 오답.
- **Schema-on-Read vs Write**: 레이크=Read, DW=Write. 레이크하우스는 둘 다.
- **CAP 정리**: 3개 중 2개만 — "3개 모두 보장"은 함정. 분산 환경에선 P 필수라 실질 C vs A 선택.
- **약어 병기 누락**: HDFS·RDD·YARN·NoSQL·OLAP 등 최초 1회 풀네임 병기 안 하면 감점.

## Ⅴ. 결론 및 회독 포인트

- **회독 핵심**: ① 저장(HDFS/Parquet/Delta) → 처리(MapReduce/Spark/Flink) → 서빙을 **하나의 파이프라인**으로 암기, ② 비교축 5개(성능·확장성·비용·정합성·운영복잡도)를 모든 서술형 답안에 삽입, ③ 람다/카파·하둡/스파크·레이크/DW/레이크하우스 3대 비교표는 암기 필수.
- **마무리 문장**: "빅데이터 플랫폼은 단순 도입보다 워크로드 특성·정합성·비용·거버넌스의 균형 속에서 AI 데이터 공급체계로 확장할 때 실효성이 높다."
