## 핵심 인사이트 (3줄 요약)

> 1. 본질: DevOps는 개발(Dev)과 운영(Ops)의 사일로를 허물어 배포 속도와 안정성을 동시에 높이는 문화·자동화 패러다임이며, SRE(Site Reliability Engineering, 사이트 신뢰성 공학)는 이를 SLO·에러버짓이라는 정량 지표로 공학화한 운영 방법론이다.
> 2. 가치: CI/CD(지속적 통합/지속적 배포)·IaC(Infrastructure as Code, 코드형 인프라)·GitOps·옵저버빌리티·DevSecOps를 하나의 파이프라인으로 연결해 "빠르고 안전한 배포"와 "측정 가능한 신뢰성"을 달성한다.
> 3. 판단 포인트: 도구명 나열이 아니라 속도·안정성·보안·비용·인지부하(Cognitive Load) 간 트레이드오프를 에러버짓·DORA 지표로 설명할 수 있어야 기술사 답안이 된다.

## Ⅰ. 과목 개요

- 기준: 컴퓨터시스템응용기술사(컴시응) 관점, 과목 총 노트 수 400개 기반 핵심 압축.
- 과목 성격: DevOps/SRE는 클라우드 네이티브·MSA(Microservice Architecture) 운영의 표준 방법론으로, 5과목(소프트웨어 공학)·9과목(보안)·13과목(클라우드)과 교차 출제된다.
- 출제 경향: 단답형은 CI/CD·GitOps·SLI/SLO/SLA·배포 전략 정의 구분, 서술형은 배포 자동화 체계·SRE 지표 체계·DevSecOps 통합을 구조도+비교표로 전개하는 문제가 반복된다.
- 답안 원칙: 약어는 최초 1회 풀네임 병기, 정의를 첫 줄에, 도식 1개·표 1개 이상 필수, 마지막은 발전 방향(플랫폼 엔지니어링·AIOps).

## Ⅱ. 1교시 단답형 핵심 (앞단위)

> 약어 최초 1회 풀네임 병기. 13문제 중 10문제 선택, 각 10점, 약 10분.

| 키워드 | 한줄 정의 | 핵심 3포인트 |
|:---|:---|:---|
| CI/CD | 코드 통합·테스트·배포를 자동화하는 파이프라인 (Continuous Integration / Continuous Delivery·Deployment) | ①CI=수시 병합+자동 빌드/테스트로 통합오류 조기발견 ②CDelivery=배포 준비, 운영배포는 수동승인 ③CDeployment=수동승인 생략 전자동 |
| IaC | 인프라를 선언적 코드(HCL/YAML)로 정의·버전관리·프로비저닝 (Infrastructure as Code) | ①멱등성(Idempotency)으로 동일결과 보장 ②구성편류(Drift) 방지 ③Terraform/CloudFormation, Git 형상관리 |
| GitOps | 목표상태(Desired State)를 Git에 선언하고 클러스터 에이전트가 동기화하는 CD 방식 | ①Pull기반=클러스터 내부 에이전트가 Git 폴링(보안↑) ②단일진실원천(SSOT) ③ArgoCD/FluxCD |
| 컨테이너 오케스트레이션 | 다수 컨테이너의 배포·스케일·복구를 자동화 (대표: Kubernetes) | ①선언적 제어루프(목표≈현재) ②Pod/ReplicaSet/Deployment ③HPA(수평파드오토스케일러)/Self-Healing |
| 옵저버빌리티 | 텔레메트리만으로 분산시스템 내부 근본원인을 추론하는 역량 (Observability/관측성) | ①3대 기둥=메트릭·로그·트레이스 ②Unknown-Unknowns 탐색 ③모니터링(기지문제)과 구분 |
| OpenTelemetry | 메트릭·로그·트레이스 계측 SDK와 API를 통합한 CNCF 관측성 표준 (OTel) | ①벤더 파편화 해소 ②Instrumentation 표준명세 ③Collector로 백엔드(Jaeger/Prometheus) 전송 |
| SLI/SLO/SLA | 신뢰성 측정·목표·계약의 3계층 (Indicator/Objective/Agreement) | ①SLI=실측치(5xx 에러율) ②SLO=내부목표(99.9%) ③SLA=고객계약+위약금(SLO보다 느슨) |
| 에러버짓 | 100%-SLO로 허용된 장애예산 (Error Budget) | ①99.9% SLO→0.1% 예산 ②소진 시 신규배포 동결 ③속도-안정성 균형 의사결정 도구 |
| 카오스 엔지니어링 | 고의로 장애를 주입해 회복탄력성을 사전 검증 (Chaos Engineering) | ①정상상태(Steady State) 가설 ②장애반경(Blast Radius) 최소화 ③Chaos Monkey/Mesh, 넷플릭스 기원 |
| 블루그린 배포 | 동일규모 신·구 환경 병행 후 LB 라우팅 일괄 전환 (Blue/Green) | ①롤백 1초(스위치복귀) ②자원 일시 2배 ③무중단·운영검증 용이 |
| 카나리 배포 | 트래픽을 1%→10%→100% 점진 확대하며 메트릭 검증 (Canary) | ①에러율 이상시 자동롤백 ②리스크 최소화 ③Kayenta 통계분석 |
| 롤링 업데이트 | 인스턴스를 하나씩 순차 교체 (Rolling, K8s 기본) | ①추가자원 최소 ②배포중 신·구 혼재 ③롤백 느림 |
| DORA 메트릭스 | 개발·운영 성과 4대 지표 (DevOps Research & Assessment) | ①배포빈도 ②변경리드타임 ③변경실패율 ④MTTR(평균복구시간) |
| 토일(Toil) | 반복적·자동화 가능한 무가치 수작업 | ①SRE는 50% 미만 억제 ②엔지니어링 시간 확보 ③자동화로 제거 |
| DevSecOps | CI/CD에 보안검증을 자동 내재화 (시프트 레프트) | ①SAST(정적)/DAST(동적)/SCA(구성분석) ②SBOM 공급망보안 ③품질게이트로 배포차단 |
| 플랫폼 엔지니어링/IDP | 셀프서비스 내부 개발자 포털로 인지부하 감소 (Internal Developer Platform) | ①골든패스(Golden Path) 표준경로 ②Backstage 등 IDP ③개발자경험(DX) 향상 |

- 1교시 답안 공식 1줄: `정의 1줄 → 핵심 3포인트(원리·효과·비교) → ASCII 도해 3줄 → 미니표(목적·장점·한계) → 적용/비교 1줄`.

## Ⅲ. 2~4교시 서술형 확장 (심화)

> 6문제 중 4문제 선택, 각 25점, 약 22~24분. Ⅰ개요·Ⅱ구조/원리·Ⅲ특징/비교·Ⅳ적용/방안·Ⅴ결론.

### 주제 1. CI/CD 파이프라인 (배포 자동화 체계)

- 정의: 소스코드 커밋부터 빌드·테스트·보안검증·배포까지를 자동화하여 변경 리드타임을 단축하고 배포 품질을 보장하는 파이프라인.

```text
[개발자 커밋/PR]
   ↓
Ⅰ. CI ─ [빌드(Maven/Gradle)] → [단위테스트] → [SAST/SCA 정적분석] → [품질게이트]
   ↓
[아티팩트 빌드(Docker Image)] → [이미지 스캐닝(Trivy)] → [레지스트리(ECR) 푸시]
   ↓
Ⅱ. CD ─ [스테이징 배포] → [DAST/통합·E2E 테스트] → [승인게이트]
   ↓
[운영 배포(Canary/Blue-Green)] → [옵저버빌리티 모니터링] → [이상시 자동롤백]
   ↓
(GitOps: ArgoCD가 Git 목표상태와 클러스터 지속 동기화)
```

- Ⅲ 특징: Pipeline as Code(Jenkinsfile/YAML)로 재현성 확보, 시프트 레프트로 결함 조기탐지, 일회성(Ephemeral) 러너로 격리.
- Ⅳ 적용: 빌드캐싱·분산빌드로 병목 단축, 시크릿 매니저(Vault)로 자격증명 분리, SBOM 추출 의무화로 공급망 보안.
- Ⅴ 결론: 파이프라인은 속도뿐 아니라 보안·관측성을 내재한 "신뢰의 자동화"로 설계해야 한다.

### 주제 2. SRE 신뢰성 지표 체계 (SLI/SLO/에러버짓)

- 정의: 100% 가용성의 비현실성을 인정하고, 실측 SLI와 목표 SLO, 그 차이인 에러버짓으로 속도와 안정성을 정량 관리하는 운영 공학.

| 구분 | SLI | SLO | SLA | 에러버짓 |
|:---|:---|:---|:---|:---|
| 정의 | 실측 지표 | 내부 목표치 | 고객 계약 | 허용 장애한도 |
| 예시 | 5xx 에러율 0.05% | 월 99.9% | 99.5%+위약금 | 100%-SLO=0.1% |
| 주체 | 모니터링 시스템 | SRE/개발팀 | 영업/법무 | SRE 의사결정 |
| 용도 | 측정 | 운영 기준 | 대외 책임 | 배포 동결 판단 |

- Ⅱ 4대 골든 시그널: 트래픽(Traffic)·지연(Latency)·에러(Errors)·포화도(Saturation)로 서비스 건강도 측정 (인프라는 USE, 서비스는 RED 메서드).
- Ⅳ 적용: 에러버짓 소진 시 신기능 동결·안정화 전환, 토일 50% 억제로 자동화 투자, 무비난 포스트모템(Blameless Postmortem)으로 시스템 개선.
- Ⅴ 결론: SRE는 "신뢰성을 협상 가능한 비용"으로 다루는 데이터 기반 운영 문화다.

### 주제 3. 무중단 배포 전략 (블루그린 vs 카나리 vs 롤링)

- 정의: 서비스 중단 없이 신버전을 출시하는 전략으로, 자원·롤백속도·리스크 통제 수준에서 차이가 있다.

| 구분 | 블루그린 | 카나리 | 롤링 |
|:---|:---|:---|:---|
| 방식 | 신·구 환경 병행 후 일괄 전환 | 트래픽 점진 확대(1→100%) | 인스턴스 순차 교체 |
| 추가 자원 | 일시적 2배 | 소량(카나리분) | 최소 |
| 롤백 속도 | 즉시(스위치 복귀) | 빠름(트래픽 회수) | 느림(역순 교체) |
| 신·구 혼재 | 없음 | 일부 혼재 | 배포중 혼재 |
| 리스크 통제 | 전체 일괄(위험집중) | 점진 검증(최소) | 중간 |
| 적용 | 자원 여유·즉시롤백 필요 | 메트릭 기반 정밀검증 | 기본·자원 제약 |

- Ⅳ 보완 기법: 피처 플래그(Feature Flag)로 코드재배포 없이 기능 토글, 다크 론칭(Dark Launching)으로 백그라운드 사전검증, 트래픽 섀도잉으로 프로덕션 미러링 테스트.
- Ⅴ 결론: 단일 정답은 없으며 자원·SLO·롤백요건에 따라 선택하되, 카나리+자동분석(Kayenta)이 클라우드 네이티브의 표준으로 수렴 중이다.

### 주제 4. 옵저버빌리티 & DevSecOps 통합

- 정의: 분산시스템의 텔레메트리(메트릭·로그·트레이스)로 근본원인을 추론하고, 보안검증을 파이프라인에 내재화하여 신뢰성과 보안을 동시 확보하는 체계.

```text
[애플리케이션/인프라]
   ↓ (OpenTelemetry 계측)
[메트릭(Prometheus)] [로그(EFK)] [트레이스(Jaeger)]
   ↓                    ↓             ↓
[Collector] ──→ [Grafana 통합 대시보드/알람]
   ↓
[DevSecOps: SAST·DAST·SCA·이미지스캐닝·SBOM·OPA 정책검증]
   ↓
[AIOps 이상탐지 → 자동롤백/자동치유(Self-Healing)]
```

- Ⅲ 특징: 옵저버빌리티는 Unknown-Unknowns 탐색(모니터링과 차별), DevSecOps는 시프트 레프트로 보안비용 절감, eBPF로 사이드카 없는 커널레벨 관측.
- Ⅳ 적용: 분산추적의 컨텍스트 전파(Trace ID 헤더 주입), 정책 애즈 코드(OPA/Gatekeeper Rego)로 비인가 파드 차단, SBOM(CycloneDX)로 공급망 공격 방어.
- Ⅴ 결론: 관측성과 보안은 사후 도구가 아니라 설계 단계부터 내재된 "신뢰성의 기둥"이다.

## Ⅳ. 출제 포인트 & 함정

| 출제유형 | 1교시 단답 포인트 | 2~4교시 서술 포인트 |
|:---|:---|:---|
| 배포 전략 | 블루그린·카나리·롤링 정의 1줄 구분 | 3종 비교표+자원/롤백/리스크 선택기준 |
| SRE 지표 | SLI/SLO/SLA/에러버짓 계층 구분 | 골든시그널+에러버짓 기반 배포동결 의사결정 |
| GitOps/IaC | Pull vs Push, 멱등성, 구성편류 | ArgoCD 동기화 구조도+선언적 운영모델 |
| 옵저버빌리티 | 3대 기둥, OpenTelemetry 표준 | 메트릭·로그·트레이스 통합+근본원인 추론 |
| DevSecOps | SAST/DAST/IAST/SCA/SBOM 구분 | 파이프라인 내 보안검증 내재화+공급망 |
| 플랫폼 엔지니어링 | IDP·골든패스·인지부하 정의 | 셀프서비스 체계+개발자경험 향상 방안 |

- 함정 1: CDelivery(배포 준비, 수동승인)와 CDeployment(전자동)를 혼동 — 약어 D 구분 필수.
- 함정 2: SLA를 SLO보다 엄격하게 설정하면 오답 — SLA는 위약금 방어 위해 SLO보다 느슨해야 한다.
- 함정 3: GitOps를 단순 "Git+CI"로 답하면 감점 — 핵심은 Pull기반 선언적 동기화와 클러스터 내부 에이전트.
- 함정 4: 옵저버빌리티를 모니터링과 동일시 — 모니터링은 기지문제, 옵저버빌리티는 미지문제 탐색.
- 함정 5: 에러버짓을 "장애 허용"으로만 답하면 부족 — 속도-안정성 균형의 정량적 의사결정 도구임을 명시.
- 함정 6: 카나리/블루그린 비교 시 "자원 2배=블루그린"만 외우고 롤백속도·혼재 여부를 빠뜨리는 경우.

## Ⅴ. 결론 및 회독 포인트

- DevOps/SRE 답안의 핵심은 "도구명 나열"이 아니라 속도·안정성·보안·비용·인지부하의 트레이드오프를 DORA 지표·에러버짓·골든시그널로 정량 설명하는 것이다.
- 회독 우선순위: ①배포 3종 비교표 ②SLI/SLO/SLA/에러버짓 계층 ③CI/CD+GitOps 구조도 ④옵저버빌리티 3대 기둥 ⑤DevSecOps 시프트 레프트 — 이 5개만 손글씨로 즉시 그릴 수 있으면 1·2교시 모두 대응 가능.
- 발전 방향: 플랫폼 엔지니어링(IDP)·AIOps 자동치유·정책형 보안으로 "운영 자동화의 수준"과 "개발자 경험"이 최신 출제 축으로 확장 중이다.
