## 핵심 인사이트 (3줄 요약)

> 1. **본질**: 소프트웨어공학은 요구사항-설계-구현-검증-운영 전 과정을 구조화해 품질·일정·유지보수성을 통제하는 과목이다.
> 2. **가치**: 애자일·도메인 주도 설계(DDD)·마이크로서비스 아키텍처(MSA)·테스트·형상관리를 하나의 생명주기 축으로 연결해야 고득점형 답안이 된다.
> 3. **판단 포인트**: 인공지능(AI) 기반 개발, 데브섹옵스(DevSecOps), 소프트웨어 공급망 보안(SBOM)을 함께 엮어 최신 동향을 입혀야 한다.

## Ⅱ. 1교시 단답형 핵심 (앞단위)

> 약어는 최초 1회 풀네임 병기, 정의 1문장 + 핵심 3포인트로 압축한다.

| 키워드 | 한줄 정의 | 핵심 3포인트 |
|:---|:---|:---|
| 애자일(Agile) | 짧은 반복(Iteration)으로 고객 가치를 점진 전달하는 경량 방법론 | ① 4가치 12원칙 ② 스프린트·백로그·회고 ③ 변화 수용·자기조직화 |
| 스크럼(Scrum) | 역할·이벤트·산출물로 구성된 대표 애자일 프레임워크 | ① PO/SM/개발팀 ② 스프린트(1~4주) ③ 번다운 차트로 가시화 |
| DDD(Domain-Driven Design) | 도메인 모델 중심으로 복잡성을 다루는 설계 기법 | ① 유비쿼터스 언어 ② 바운디드 컨텍스트 ③ 애그리게이트·MSA 식별 기준 |
| MSA(Microservices Architecture) | 독립 배포 가능한 작은 서비스로 시스템을 분해한 아키텍처 | ① 서비스별 DB ② API 게이트웨이·서비스 디스커버리 ③ 사가(Saga)로 분산 트랜잭션 |
| 응집도/결합도(Cohesion/Coupling) | 모듈 내부 연관도(高 선호)와 모듈 간 의존도(低 선호) 지표 | ① 응집도 7단계(우연~기능) ② 결합도 5단계(내용~자료) ③ 좋은 설계=고응집·저결합 |
| SOLID 원칙 | 객체지향 설계 5대 원칙(SRP/OCP/LSP/ISP/DIP) | ① 단일책임·개방폐쇄 ② 리스코프 치환 ③ 인터페이스 분리·의존 역전 |
| GoF 디자인 패턴 | 생성·구조·행위 23가지 재사용 설계 해법 | ① 싱글톤·팩토리(생성) ② 어댑터·퍼사드(구조) ③ 옵저버·전략(행위) |
| 품질속성(Quality Attributes) | ISO/IEC 25010 기반 비기능 요구사항(-ility) | ① 가용성·성능·보안 ② 변경용이성·시험용이성 ③ 시나리오 6요소·ATAM 평가 |
| 소프트웨어 테스트 | 결함 발견을 통해 품질을 확인하는 활동(V&V) | ① 블랙박스(동등분할·경계값) ② 화이트박스(구문·분기·MC/DC) ③ 단위→통합→시스템→인수 |
| TDD(Test Driven Development) | 실패 테스트 우선 작성 후 구현하는 개발 기법 | ① Red-Green-Refactor ② 회귀안정성 ③ 설계 품질 향상 |
| 형상관리(SCM, Software Configuration Management) | 산출물 변경을 식별·통제·감사하는 활동 | ① 식별·통제·감사·기록 ② 기준선(Baseline)·CCB ③ Git 분산 버전관리 |
| 기술부채(Technical Debt) | 단기 편의가 누적해 장기 비용으로 전이되는 부채 | ① 파울러 사분면 ② 이자=유지보수 비용 ③ 리팩토링으로 상환 |
| CI/CD | 지속적 통합·배포로 빌드·검증·릴리즈를 자동화 | ① 잦은 머지·자동 빌드 ② 파이프라인 자동 테스트 ③ 카나리·블루그린 배포 |
| DevOps | 개발과 운영을 통합한 문화·자동화·측정·공유 | ① CALMS ② IaC·관측가능성(Observability) ③ 배포 빈도·MTTR 개선 |
| DevSecOps | 보안을 파이프라인 초기로 당기는 시프트-레프트 보안 | ① SAST/DAST/SCA ② 위협 모델링(STRIDE) ③ 컴플라이언스 애즈 코드 |
| SBOM(Software Bill of Materials) | SW 구성요소 명세서로 공급망 투명성 확보 | ① SPDX·CycloneDX 포맷 ② OSS 취약점·라이선스 추적 ③ 서명·무결성 검증 |
| 폭포수/V-모델 | 순차·문서 중심 개발과 V&V 대응 검증 모델 | ① 단계별 게이트 ② 요구-인수, 코딩-단위 매핑 ③ 변경 비용 후반 급증 |
| 아키텍처 평가(ATAM) | 품질속성 간 상충(Trade-off)을 분석하는 평가 기법 | ① 시나리오 도출 ② 민감점·트레이드오프점 ③ 위험·비위험 식별 |

- **1교시 답안 공식 1줄**: `정의 1문장 → 핵심 3포인트(원리/효과/한계) → 미니 도해 3줄 → 미니 표(목적·강점·한계) → 적용·비교 1줄`.

## Ⅲ. 2~4교시 서술형 확장 (심화)

### 1. 마이크로서비스 아키텍처(MSA) vs 모놀리식

- **정의**: MSA는 비즈니스 능력 단위로 독립 배포 가능한 작은 서비스로 시스템을 분해한 아키텍처다.

**Ⅰ. 개요** — 모놀리식의 배포 단위 비대화·확장 한계를 극복하기 위해 등장. 서비스별 독립 개발·배포·확장이 핵심 가치.

**Ⅱ. 구조 및 원리**
```text
[클라이언트/BFF]
   ↓
[API 게이트웨이] ── 인증·라우팅·집계
   ↓        ↓        ↓
[서비스 A] [서비스 B] [서비스 C]   ← 서비스별 DB(Database per Service)
   ↘        ↓        ↙
[메시지 브로커(Kafka)] ── 비동기 이벤트
   ↓
[서비스 디스커버리 · 서비스 메시(Istio)] ── 관측·트래픽 제어
```

**Ⅲ. 특징/비교**

| 구분 | 모놀리식(Monolith) | MSA |
|:---|:---|:---|
| 배포 단위 | 단일 산출물 일괄 배포 | 서비스별 독립 배포 |
| 확장성 | 전체 스케일아웃 | 필요 서비스만 선택 확장 |
| 데이터 | 단일 공유 DB | 서비스별 DB·결과적 일관성 |
| 트랜잭션 | 로컬 ACID | 사가(Saga)·보상 트랜잭션 |
| 장애 영향 | 전체 전파 위험 | 서킷 브레이커·벌크헤드로 격리 |
| 적합 상황 | 소규모·초기 제품 | 대규모·팀 자율·잦은 배포 |

**Ⅳ. 적용/방안** — ① DDD 바운디드 컨텍스트로 서비스 경계 도출 ② 스트랭글러 피그(Strangler Fig)로 레거시 점진 전환 ③ 분산 트랜잭션은 사가(오케스트레이션/코레오그래피) ④ 분산 추적(OpenTelemetry)·서비스 메시로 운영 통제. **안티패턴 경계**: 분산 모놀리스.

**Ⅴ. 결론** — MSA는 단순 도입보다 조직 성숙도·운영 복잡도·비용을 함께 고려한 단계적 적용이 중요하다.

---

### 2. 애자일(스크럼) vs 폭포수

- **정의**: 애자일은 짧은 반복으로 동작하는 제품을 점진 전달하며 변화에 적응하는 경량 방법론이다.

**Ⅰ. 개요** — 요구 변동성·시장 불확실성 대응을 위해 문서 중심 폭포수의 경직성을 보완.

**Ⅱ. 구조 및 원리**
```text
[제품 백로그] → [스프린트 계획] → [스프린트(1~4주)]
                                     ↓ 데일리 스크럼
                            [잠재적 출시 가능 증분]
                                     ↓
                       [스프린트 리뷰] → [회고] → (반복)
```

**Ⅲ. 특징/비교**

| 구분 | 폭포수(Waterfall) | 애자일(Scrum) |
|:---|:---|:---|
| 진행 | 순차·단계 게이트 | 반복·점진 |
| 요구 변경 | 후반 변경 비용 급증 | 매 스프린트 수용 |
| 산출물 | 문서 중심 | 동작 SW 중심 |
| 고객 참여 | 초기·말기 | 전 주기 지속 |
| 리스크 | 후반 발견 | 조기·반복 노출 |
| 적합 | 요구 명확·규제 | 불확실·혁신 제품 |

**Ⅳ. 적용/방안** — ① 대규모는 SAFe·LeSS로 확장 ② 워터스크럼폴 안티패턴 회피 ③ INVEST 사용자 스토리·플래닝 포커 산정 ④ CI/CD와 결합해 배포 자동화.

**Ⅴ. 결론** — 방법론은 테일러링이 핵심이며, 조직·제품 특성에 맞춘 하이브리드 적용이 실효성을 높인다.

### 3. 소프트웨어 품질속성과 아키텍처 평가(ATAM)

- **정의**: 품질속성은 ISO/IEC 25010이 정의한 비기능 요구사항이며, ATAM은 속성 간 상충을 분석하는 아키텍처 평가 기법이다.

**Ⅰ. 개요** — 기능 충족만으로는 운영 실패를 막지 못하므로 가용성·성능·보안 등 -ility를 시나리오로 정량화.

**Ⅱ. 구조 및 원리** — 품질 시나리오 6요소: `자극원 → 자극 → 환경 → 대상 → 응답 → 응답 척도`.
```text
[비즈니스 목표]
   ↓
[품질속성 시나리오] → [아키텍처 접근법]
   ↓
[민감점/트레이드오프점 식별]
   ↓
[위험·비위험 도출 → 개선]
```

**Ⅲ. 특징/비교**

| 평가기법 | 관점 | 특징 |
|:---|:---|:---|
| SAAM | 변경용이성 | 최초의 시나리오 기반 평가 |
| ATAM | 품질속성 상충 | 민감점·트레이드오프점 분석 |
| CBAM | 경제성 | 비용-효익(ROI) 관점 |

**Ⅳ. 적용/방안** — ① 가용성=결함 탐지·복구·예방 전술 ② 성능=자원 관리·스케줄링 ③ 보안=탐지·방어·복구 ④ ADR(Architecture Decision Record)로 결정 근거 문서화.

**Ⅴ. 결론** — 품질은 사후 측정이 아니라 아키텍처 설계 시점에 전술로 내재화해야 한다.

---

### 4. DevSecOps와 소프트웨어 공급망 보안(SBOM)

- **정의**: DevSecOps는 보안을 개발 파이프라인 초기로 당기는 시프트-레프트 보안 문화이며, SBOM은 SW 구성요소 명세서다.

**Ⅰ. 개요** — 오픈소스 의존성 폭증·공급망 공격(예: 의존성 변조) 대응을 위해 보안 자동화가 필수.

**Ⅱ. 구조 및 원리**
```text
[계획·위협모델링(STRIDE)]
   ↓
[코딩→SAST] → [빌드→SCA/SBOM 생성] → [테스트→DAST/IAST]
   ↓
[배포→이미지 스캔·서명] → [운영→RASP·관측]
   ↓
[피드백 → 보안 백로그 반영(반복)]
```

**Ⅲ. 특징/비교**

| 도구 | 시점 | 방식 |
|:---|:---|:---|
| SAST | 코드 | 정적 분석(소스) |
| DAST | 실행 | 동적 페이로드 주입(블랙박스) |
| IAST | 실행 | 에이전트 내부 흐름 분석 |
| SCA | 빌드 | OSS 취약점·라이선스 스캔 |

**Ⅳ. 적용/방안** — ① SBOM은 SPDX·CycloneDX 포맷으로 생성·관리 ② CVE/CVSS로 취약점 우선순위화 ③ 서명된 커밋·CI 파이프라인 보호 ④ VEX로 영향 여부 명시.

**Ⅴ. 결론** — 향후 SW 공급망 보안은 규제 의무화(SBOM)와 결합해 DevSecOps의 핵심 통제 요소로 자리잡을 것이다.

## Ⅳ. 출제 포인트 & 함정

| 출제유형 | 1교시 단답 포인트 | 2~4교시 서술 포인트 |
|:---|:---|:---|
| 방법론 | 애자일 4가치, 스크럼 역할·이벤트 | 폭포수 vs 애자일 비교 + 테일러링 방안 |
| 설계 | 응집도/결합도, SOLID, GoF 패턴 | DDD 기반 서비스 경계 도출 + 클린/헥사고날 아키텍처 |
| 아키텍처 | MSA 구성요소, 사가·서킷브레이커 | Monolith vs MSA 비교 + 전환 전략(스트랭글러 피그) |
| 품질/테스트 | ISO 25010, 블랙/화이트박스, MC/DC | 품질속성 시나리오 + ATAM 평가 절차 |
| 형상/운영 | 기준선·CCB, CI/CD 단계 | DevSecOps 파이프라인 + SBOM 공급망 보안 |

**함정 정리**
- **응집도·결합도 방향 혼동**: 응집도는 높을수록, 결합도는 낮을수록 좋다(역방향 주의).
- **분산 모놀리스**: MSA로 쪼갰으나 강결합·동기 의존으로 독립 배포 불가 → 사실상 안티패턴.
- **검증(Verification) vs 확인(Validation)**: "올바르게 만들고 있는가"(과정) vs "올바른 것을 만들었는가"(결과).
- **MC/DC ↔ 다중조건 커버리지 혼동**: MC/DC는 각 조건의 독립적 영향 증명(항공 DO-178C 표준).
- **골드 플래팅·범위 크리프**: 요구에 없는 기능 추가/무분별한 확장은 감점 포인트.
- **2PC를 MSA에 그대로 적용**: 가용성 저하로 부적합 → 사가·결과적 일관성으로 대체.

## Ⅴ. 최신 기술 동향 + 공부 노트 연결

- **개발 방식**: 생성형 AI 코딩 보조(GitHub Copilot, Cursor), 프롬프트 엔지니어링, AI 기반 테스트 자동화 — 산출물 라이선스·할루시네이션 버그 검증 필수.
- **운영 품질**: 데브섹옵스(DevSecOps), 소프트웨어 공급망 보안(SBOM/VEX/SLSA), 지속적 테스팅(Continuous Testing).
- **아키텍처**: 클라우드 네이티브(12-Factor App), 서비스 메시(Service Mesh), 이벤트 주도 아키텍처(EDA), 모듈러 모놀리스.
- **관리 체계**: 플랫폼 엔지니어링, 내부 개발자 플랫폼(IDP), 가치 흐름 관리(Value Stream Management), SRE 에러 예산.
- **신뢰성**: 카오스 엔지니어링, 관측가능성(Metrics/Logs/Traces), 회복력 패턴(서킷 브레이커·벌크헤드).
