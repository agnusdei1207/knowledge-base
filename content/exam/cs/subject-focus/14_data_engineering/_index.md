## 핵심 인사이트 (3줄 요약)

> 1. **본질**: 데이터 엔지니어링은 시스템이 생성한 원시 데이터를 수집·정제·적재·서빙하는 파이프라인을 분산 시스템·저장 구조·운영 자동화로 묶어 설계하는 과목이다.
> 2. **가치**: 저장 계층(레이크/웨어하우스/레이크하우스)·처리 방식(배치/스트리밍)·이관 기술(ETL/ELT/CDC)·거버넌스(품질·계보·메타데이터)를 한 답안에 구조적으로 연결할 때 고득점한다.
> 3. **판단 포인트**: 정합성·지연시간·장애복구·비용·거버넌스의 트레이드오프를 함께 제시하고, 데이터 메시·레이크하우스·MLOps 같은 최신 사상으로 마무리하는 것이 기술사 답안답다.

---

## Ⅰ. 과목 개요

- **정의**: 데이터 엔지니어링(Data Engineering)은 정형·반정형·비정형 데이터를 안정적으로 수집·정제·저장·제공하기 위한 파이프라인과 플랫폼을 분산 처리·저장·운영 자동화 관점에서 설계·구축·운영하는 공학 영역이다.
- **컴퓨터시스템응용기술사 관점 출제 축**:
  - 저장 아키텍처: 데이터 레이크 vs 웨어하우스 vs 레이크하우스, 데이터 메시
  - 처리 아키텍처: 배치 vs 스트리밍, 람다 vs 카파
  - 데이터 이동: ETL vs ELT, CDC(Change Data Capture)
  - 운영·품질: 데이터 거버넌스, 데이터 품질, 계보(Lineage), DataOps/MLOps
- **약어 표기 원칙**: 최초 1회 풀네임 병기 — ETL(Extract, Transform, Load), CDC(Change Data Capture), DW(Data Warehouse) 등.
- **출제 빈도가 높은 결합형**: "실시간 데이터 플랫폼 설계", "배치+스트리밍 통합", "레이크하우스 도입 방안", "데이터 품질·거버넌스 체계" 형태로 결합 출제.

## Ⅱ. 1교시 단답형 핵심 (앞단위)

| 키워드 | 한줄 정의 | 핵심 3포인트 |
|:---|:---|:---|
| **데이터 레이크 (Data Lake)** | 원시(Raw) 형태의 모든 정형·비정형 데이터를 저비용 스토리지에 무한 저장 | ① Schema-on-Read ② S3/HDFS 기반 저비용 ③ 거버넌스 약하면 Data Swamp化 |
| **데이터 웨어하우스 (Data Warehouse)** | BI 위한 통합·주제별·시계열 정제 데이터 저장소(Inmon) | ① Schema-on-Write ② ACID·SQL 성능 ③ 정형 위주·고비용·유연성↓ |
| **데이터 레이크하우스 (Lakehouse)** | 레이크의 저비용·유연성 + DW의 ACID·SQL을 단일 계층 결합 | ① 오픈 테이블 포맷(Iceberg/Delta/Hudi) ② 컴퓨팅·스토리지 분리 ③ Time Travel·스키마 에볼루션 |
| **데이터 메시 (Data Mesh)** | 중앙 집중 데이터팀을 탈피, 도메인이 분산 오너십으로 데이터를 '프로덕트'로 제공 | ① 도메인 소유권 ② Data as a Product ③ 셀프서비스 플랫폼·연합 거버넌스 |
| **데이터 패브릭 (Data Fabric)** | 흩어진 멀티클라우드 사일로를 메타데이터 가상화로 연결한 단일 뷰 | ① 데이터 가상화 ② AI 메타데이터 ③ 이동 없이 연방 쿼리 |
| **ETL vs ELT** | ETL은 외부 변환 후 적재, ELT는 적재 후 DW 연산력으로 변환 | ① ETL=정제 후 적재(병목) ② ELT=클라우드 DW 내부 변환(대세) ③ 대용량·반정형은 ELT 유리 |
| **배치 vs 스트리밍** | 배치는 일정 주기 일괄 처리, 스트리밍은 이벤트 발생 즉시 처리 | ① 배치=고처리량·고지연 ② 스트리밍=저지연·실시간 ③ 정확성 vs 신선도 트레이드오프 |
| **CDC (Change Data Capture)** | 운영 DB의 트랜잭션 로그(Binlog/Redo)를 읽어 부하 없이 변경분만 실시간 전파 | ① 로그 기반 무부하 ② Debezium·Kafka 연계 ③ 실시간 동기화·복제 |
| **데이터 파이프라인 (Pipeline)** | 수집→정제→적재→서빙으로 데이터를 흐르게 하는 자동화 워크플로 | ① DAG 의존성(Airflow) ② 멱등성(Idempotency)·재처리 ③ 모니터링·SLA |
| **데이터 거버넌스 (Governance)** | 데이터의 품질·보안·메타데이터·소유권을 통제하는 정책·조직 체계 | ① 카탈로그·리니지 ② 접근통제·마스킹 ③ 규제 준수(개인정보) |
| **데이터 품질 (Data Quality)** | 정확성·완전성·일관성·적시성·유효성을 보장하는 관리 활동 | ① 6대 차원 ② 프로파일링·검증 룰(dbt test) ③ 이상 자동 탐지 |
| **데이터 카탈로그·계보 (Catalog/Lineage)** | 메타데이터 통합 검색(Discovery) + 출처~타겟 흐름 추적 | ① 데이터 탐색·태깅 ② 영향도 분석 ③ 감사·규제 대응 |
| **람다 vs 카파 아키텍처** | 람다=배치+스트림 이중 계층, 카파=스트림 단일 계층 통합 | ① 람다=정확+실시간(복잡) ② 카파=Kafka 단일화 ③ Event Replay로 재처리 |
| **오픈 테이블 포맷 (Open Table Format)** | Parquet 위에 ACID·스냅샷·스키마 진화를 부여(Iceberg/Delta/Hudi) | ① 레이크하우스 핵심 ② Time Travel ③ 동시성·트랜잭션 제어 |

> **1교시 답안 공식 (1줄)**: `정의 1줄 → 특징 3줄(원리/장점/한계) → 도해 3줄(입력→처리→효과) → 미니표 3행(목적/장점/한계) → 비교·적용 1줄`

## Ⅲ. 2~4교시 서술형 확장 (심화)

### 1. 데이터 레이크하우스 아키텍처

- **정의**: 레이크하우스(Lakehouse)는 데이터 레이크의 저비용·유연성과 데이터 웨어하우스의 ACID 트랜잭션·SQL 성능을 오픈 테이블 포맷 기반 단일 계층에 결합한 현대 데이터 아키텍처이다.

**Ⅰ. 개요** — 레이크는 거버넌스 부재 시 Data Swamp, DW는 비정형·비용 한계. 두 약점을 단일 플랫폼으로 통합할 필요성에서 등장.

**Ⅱ. 구조** (메달리온 아키텍처)
```text
[소스: DB/로그/IoT/CDC]
        ↓
[Bronze: 원시 적재] → [Silver: 정제·정합] → [Gold: 집계·분석용]
        ↓                                          ↓
[오픈 테이블 포맷: Iceberg/Delta/Hudi (ACID, Time Travel)]
        ↓
[컴퓨팅 엔진(Spark/Trino) — 스토리지(S3)와 분리]
        ↓
[BI / ML / Ad-hoc SQL 서빙]
```

**Ⅲ. 핵심 특징**

| 구분 | 내용 | 판단 포인트 |
|:---|:---|:---|
| 트랜잭션 | 오픈 테이블 포맷이 ACID 보장 | 동시 쓰기·정합성 확보 |
| 컴퓨팅/스토리지 분리 | 독립 스케일링 | 비용 최적·탄력성 |
| 스키마 에볼루션 | 컬럼 추가·변경 무중단 | 운영 유연성 |
| Time Travel | 스냅샷 롤백·감사 | 장애복구·재현성 |

**Ⅳ. 적용 방안** — ① 레거시 DW의 분석 워크로드를 Gold 계층으로 점진 이관, ② CDC로 운영 DB 변경분을 Bronze 실시간 적재, ③ 데이터 카탈로그·리니지로 거버넌스 결합.

**Ⅴ. 결론** — 레이크하우스는 단일 진실 원천(Single Source of Truth)으로 BI와 AI를 통합하나, 오픈 테이블 포맷 선택·소형 파일 컴팩션·메타데이터 운영 역량이 성패를 좌우한다.

### 2. 실시간 데이터 파이프라인 (배치+스트리밍 통합)

- **정의**: 실시간 데이터 파이프라인은 이벤트 발생 즉시 수집·처리·적재하여 저지연 분석을 제공하면서, 배치 처리의 정확성과 결합하는 데이터 처리 아키텍처이다.

**Ⅰ. 개요** — 배치만으로는 신선도 부족, 스트리밍만으로는 정확성·재처리 한계. 람다/카파로 양자를 결합.

**Ⅱ. 구조** (카파 기반 스트리밍 파이프라인 구조도)
```text
[소스 DB] --CDC(Debezium)--┐
[IoT/로그/클릭스트림] ──────┤
                            ▼
                     [Kafka 토픽/파티션]  ← 단일 로그 백본
                            ▼
              [Flink/Spark Streaming]  ← Window·Watermark 상태처리
                            ▼
              ┌─────────────┴─────────────┐
              ▼                           ▼
        [실시간 뷰/대시보드]        [레이크하우스 적재(Gold)]
              │                           │
              └──── Event Replay 재처리 ───┘
```

**Ⅲ. 특징** — 멱등성(Idempotency)으로 중복 제거, 워터마크로 지연 이벤트 처리, Exactly-once 시맨틱 보장.

**Ⅳ. 람다 vs 카파 비교**

| 구분 | 람다 아키텍처 | 카파 아키텍처 |
|:---|:---|:---|
| 계층 | 배치 + 스피드 이중 | 스트림 단일 |
| 정확성 | 배치 레이어 재계산 | Event Replay 재처리 |
| 복잡도 | 높음(코드 이중화) | 낮음(단일화) |
| 적용 | 정확성 최우선 | 실시간·운영 단순화 |

**Ⅴ. 결론** — 운영 복잡도를 줄이려면 카파가 유리하나, 정확성·과거 대용량 재처리가 중요하면 람다가 적합하며, 최근은 레이크하우스 스트리밍으로 양자가 수렴 중이다.

### 3. 데이터 거버넌스 및 데이터 품질 체계

- **정의**: 데이터 거버넌스(Data Governance)는 데이터의 품질·보안·메타데이터·소유권을 정책·조직·기술로 통제하여 신뢰할 수 있는 데이터 활용을 보장하는 관리 체계이다.

**Ⅰ. 개요** — 데이터 양 폭증·규제 강화·AI 학습 데이터 신뢰성 요구로 거버넌스가 필수.

**Ⅱ. 구조** (데이터 품질 통제 폐루프)
```text
[데이터 프로파일링]
        ↓
[품질 룰 검증(dbt test/Great Expectations)] → [이상 탐지] → [알림/격리]
        ↓                                                      │
[카탈로그·리니지 등록]                                          │
        ↓                                                      │
[활용/서빙] ←──────────── 피드백·개선 ──────────────────────────┘
```

**Ⅲ. 데이터 품질 6대 차원**

| 차원 | 의미 | 검증 예 |
|:---|:---|:---|
| 정확성 | 실제값과 일치 | 도메인 검증 |
| 완전성 | 결측 없음 | Null 비율 |
| 일관성 | 상호 모순 없음 | 참조 무결성 |
| 적시성 | 최신성 | 지연 SLA |
| 유효성 | 형식 준수 | 패턴/범위 |
| 유일성 | 중복 없음 | PK 중복 |

**Ⅳ. 적용 방안** — ① 데이터 카탈로그로 탐색·소유권 명시, ② 리니지로 영향도·감사 추적, ③ 마스킹·K-익명성으로 개인정보 보호, ④ DataOps의 CI/CD로 품질 테스트 자동화.

**Ⅴ. 결론** — 거버넌스는 통제가 아니라 신뢰 기반 데이터 활용의 인프라이며, 데이터 메시 환경에서는 중앙 통제 대신 '연합 거버넌스(Federated Governance)'로 진화한다.

### 4. ETL vs ELT 및 데이터 통합 전략

- **정의**: 데이터 통합은 분산된 소스의 데이터를 추출·변환·적재하여 분석용 저장소로 모으는 활동으로, 변환 위치에 따라 ETL과 ELT로 구분된다.

**Ⅰ. 개요** — 온프레미스 시대 ETL이 주류였으나, 클라우드 DW의 무한 연산력 등장으로 ELT가 대세화.

**Ⅱ. 구조** (ELT 흐름도)
```text
[운영 DB/SaaS/로그]
        ↓ Extract (CDC/배치 추출)
[클라우드 DW·레이크하우스 Raw 영역]
        ↓ Load (즉시 적재)
[DW 내부 SQL 변환(dbt) — Transform]
        ↓
[정제 테이블 → BI/ML 서빙]
```

**Ⅲ. ETL vs ELT 비교**

| 구분 | ETL | ELT |
|:---|:---|:---|
| 변환 위치 | 별도 변환 서버 | 적재 후 DW 내부 |
| 적재 데이터 | 정제된 데이터 | 원시 데이터 |
| 처리량 | 변환 서버 병목 | DW 스케일 활용 |
| 유연성 | 사전 스키마 고정 | 원시 보존·재변환 용이 |
| 적합 환경 | 정형·소규모·온프레 | 대용량·반정형·클라우드 |

**Ⅳ. 적용 방안** — ① CDC로 변경분만 증분 추출해 부하 최소화, ② Airflow DAG로 의존성·재처리(멱등성) 관리, ③ dbt로 변환을 코드화(DataOps)하여 버전·테스트 관리.

**Ⅴ. 결론** — 클라우드·대용량·AI 학습 데이터 환경에서는 원시 보존·재변환이 유리한 ELT가 우세하나, 강한 정합성·사전 정제가 필요한 영역에서는 ETL이 여전히 유효하며 양자 혼용이 현실적이다.

## Ⅳ. 출제 포인트 & 함정

| 출제유형 | 1교시 단답 포인트 | 2~4교시 서술 포인트 |
|:---|:---|:---|
| 저장 아키텍처 | 레이크/DW/레이크하우스 한줄 차이(Schema-on-Read/Write) | 레이크하우스 메달리온 구조 + 3자 비교표 + 도입 방안 |
| 처리 아키텍처 | 배치 vs 스트리밍, 람다 vs 카파 | 실시간 파이프라인 구조도 + Exactly-once/Watermark |
| 데이터 이동 | ETL vs ELT, CDC 원리(로그 기반) | 통합 전략 + 증분 추출 + 멱등성 재처리 |
| 거버넌스/품질 | 품질 6대 차원, 카탈로그·리니지 | 품질 폐루프 + 연합 거버넌스 + 개인정보 마스킹 |
| 조직·사상 | 데이터 메시, 데이터 패브릭 | 도메인 오너십·Data as a Product 전개 |

**함정 정리**
- **레이크 ≠ 레이크하우스**: 레이크는 ACID 없음, 레이크하우스는 오픈 테이블 포맷으로 ACID 보장 — 혼동 시 감점.
- **ETL/ELT 변환 위치**: ELT의 핵심은 '적재 후 DW 내부 변환' — "ELT는 변환을 안 한다"가 아님.
- **CDC는 부하 유발이 아니라 회피 기술**: 트랜잭션 로그를 읽어 운영 DB에 부하를 주지 않는 것이 핵심.
- **람다=복잡, 카파=단순**: 람다의 단점(코드 이중화)을 빠뜨리면 비교가 약해짐.
- **데이터 메시는 기술이 아니라 조직론**: 도메인 소유권·연합 거버넌스가 본질, 도구로만 설명하면 감점.
- **약어 풀네임 병기 누락**: ETL/ELT/CDC/DW 최초 1회 풀네임 미표기는 1교시 금지 패턴.

## Ⅴ. 결론 및 회독 포인트

- **회독 1순위**: 레이크/DW/레이크하우스 3자 비교표 → ETL vs ELT → CDC → 배치 vs 스트리밍(람다/카파) → 거버넌스·품질 6대 차원 순으로 암기.
- **답안 골격 고정**: 정의 1줄 → 구조도 → 비교표 2개 → 방안 3개 → 결론 2줄. 구조도는 메달리온·스트리밍 파이프라인 2종을 손에 익힐 것.
- **기술사적 마무리**: "데이터 엔지니어링은 정합성·지연·비용·거버넌스의 트레이드오프를 균형 있게 설계할 때 실효성이 높다"로 통찰 제시.
