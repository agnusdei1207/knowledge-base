> 본 문서는 컴퓨터시스템응용기술사 기출·출제동향 기준의 **답안 작성 전용** 트랙이다. 정의 한 문장, 비교표, 답안 골격을 그대로 옮겨 쓰는 데 초점을 둔다.

## 핵심 인사이트 (3줄 요약)
1. **본질**: 엔터프라이즈 시스템은 "업무 프로세스(ERP·SCM·CRM)" + "통합 아키텍처(EAI·ESB·MSA)" + "데이터·거버넌스(EA·BPM)"를 한 축으로 묶어 묻는 과목이다.
2. **가치**: 제품 나열이 아니라 **통합 방식의 진화(P2P → Hub&Spoke → Bus → MSA/Service Mesh)** 와 **전환 전략(빅뱅 vs 점진, 스트랭글러)** 을 설명할 때 변별력이 난다.
3. **판단 포인트**: 모든 답안은 "기술 요소 + 업무 프로세스 + 조직/데이터 표준 + 실패요인·대책"을 세트로 써야 고득점한다.

## Ⅰ. 과목 개요
- 엔터프라이즈 시스템은 기업 전반의 자원·고객·공급망·프로세스를 **통합 관리**하고, 분산된 애플리케이션을 **느슨하게 결합**하여 민첩성과 일관성을 동시에 확보하는 정보시스템 체계이다.
- 출제 축: ① 경영/거버넌스(EA, ISP, BPR) ② 기업 애플리케이션(ERP, SCM, CRM, MES, PLM) ③ 통합 아키텍처(EAI, ESB, SOA, MSA, Service Mesh) ④ 프로세스/데이터(BPM, DW, MDM).
- 답안 전략: ERP-SCM-MES, EAI-ESB-MSA, DW-BI-거버넌스처럼 **상호 연계 축**을 잡고, 레거시 전환·벤더 종속·데이터 품질 같은 **리스크와 대책**을 함께 제시한다.

## Ⅱ. 1교시 단답형 핵심 (앞단위)
> 작성 공식 = **정의 1문장 + 핵심 3포인트 + (도해/미니표 1개)**, 약어는 최초 1회 풀네임 병기.

| 키워드 | 한줄 정의 | 핵심 3포인트 |
|:---|:---|:---|
| ERP (Enterprise Resource Planning) | 재무·인사·생산·영업 등 전사 업무 프로세스를 통합 DB로 연동하는 전사적 자원관리 시스템 | ① Best Practice 내재화 ② 통합 단일 DB ③ 빅뱅 vs 점진 전환 / 커스터마이징 리스크 |
| SCM (Supply Chain Management) | 원자재 조달~최종 소비자까지 물류·정보·자금 흐름을 네트워크 관점에서 최적화 | ① 채찍효과(Bullwhip) 억제 ② 실시간 정보공유(POS) ③ SCP/SCE, S&OP |
| CRM (Customer Relationship Management) | 신규 획득·기존 유지로 고객가치(LTV)를 극대화하는 마케팅·세일즈·서비스 통합 전략 | ① 운영/분석/협업 CRM ② LTV>CAC ③ CDP·퍼스트파티 데이터 진화 |
| EA (Enterprise Architecture) | 비즈니스·데이터·애플리케이션·기술 인프라를 구조화한 전사 청사진 | ① BA·DA·AA·TA(+SA) ② Zachman/TOGAF(ADM) ③ AS-IS→TO-BE 정렬 |
| EAI (Enterprise Application Integration) | 미들웨어 허브로 전사 애플리케이션을 통합하는 중앙 집중 통합 방식 | ① Hub&Spoke 중앙제어 ② 포맷변환·라우팅 ③ 허브 SPOF·벤더 종속 |
| ESB (Enterprise Service Bus) | 표준 웹서비스 기반 메시지 버스로 라우팅·변환·보안을 추상화하는 SOA 백본 | ① 분산 버스(개방형) ② 표준 인터페이스 ③ EAI 대비 확장·재사용 우수 |
| SOA (Service Oriented Architecture) | 비즈니스 단위 서비스를 느슨하게 결합·재사용하는 서비스 지향 아키텍처 | ① Provider/Requester/Registry ② WSDL·UDDI·SOAP ③ ESB 중앙 파이프 |
| MSA (Microservices Architecture) | 모놀리식을 독립 배포·확장 가능한 작은 서비스(DB 분리)로 분할한 아키텍처 | ① 독립 배포·자율 팀 ② Database per Service ③ 분산 트랜잭션(사가) 복잡 |
| API Gateway | 클라이언트 단일 진입점에서 라우팅·인증·스로틀링·응답통합을 담당하는 모듈 | ① 단일 진입점 ② 인증/인가·Throttling ③ BFF 패턴 확장 |
| 서비스 메시 (Service Mesh) | 사이드카 프록시로 서비스 간 트래픽·보안을 인프라 계층에서 통제 | ① 비즈/네트워크 코드 분리 ② Sidecar(Envoy) ③ Istio·Linkerd |
| 서킷 브레이커 (Circuit Breaker) | 대상 장애 시 호출을 조기 차단해 연쇄 장애를 막는 내결함성 패턴 | ① Open/Half-Open/Close ② Cascading Failure 방지 ③ Fallback 연계 |
| 사가 (Saga Pattern) | 로컬 트랜잭션 연쇄 + 보상 트랜잭션으로 MSA 분산 일관성을 보장 | ① 2PC 배제 대안 ② 코레오그래피/오케스트레이션 ③ Eventual Consistency |
| BPM (Business Process Management) | 프로세스를 설계·실행·모니터링·최적화하는 순환적 프로세스 관리 체계 | ① BPMN 표기 ② 프로세스 마이닝(로그분석) ③ RPA·워크플로우 연계 |
| MES (Manufacturing Execution System) | 공장 작업지시·자재·품질을 실시간 추적 제어하는 제조 실행 시스템 | ① ERP-설비 사이 미들웨어 ② POP 현장 데이터 ③ 스마트팩토리 4단계 |

**1교시 답안 공식 (1줄)**: `정의 1문장 → 숫자로 핵심 3 → ASCII 도해 1개 → 미니표(목적·장점·한계) → 비교/실무 포인트 1줄`.

## Ⅲ. 2~4교시 서술형 확장 (심화)
> 각 주제: 정의 + Ⅰ~Ⅴ 전개 골격 + 비교표/구조도. 22~24분, 3~3.5쪽 기준.

### 1) EAI vs ESB vs 서비스 메시 — 애플리케이션 통합의 진화
- **정의**: 분산된 엔터프라이즈 애플리케이션 간 데이터·기능을 표준화된 방식으로 연계·통제하는 통합 아키텍처.
- **Ⅰ. 개요**: P2P(Point-to-Point) 통합의 스파게티 구조(N(N-1)/2 링크) 한계 → 중앙 통합 미들웨어 필요성.
- **Ⅱ. 구조/원리**:
```text
[App A] [App B] [App C]
   \      |      /
   ┌──────────────┐   (EAI: 중앙 허브 변환·라우팅)
   │  Hub/ESB Bus │ → 표준 메시지·프로토콜 변환
   └──────────────┘
        │ (MSA: 서비스마다 Sidecar 프록시)
   [Svc]─[Proxy]…[Proxy]─[Svc]  ← Service Mesh 제어면(Control Plane)
```
- **Ⅲ. 특징/비교**: 아래 비교표.
- **Ⅳ. 적용/방안**: 레거시 EAI → ESB 표준화 → MSA 전환 시 **스트랭글러 피그 패턴**으로 점진 교체, **부패방지계층(ACL)** 으로 모델 오염 차단.
- **Ⅴ. 결론**: 중앙집중(통제 용이) ↔ 분산(민첩성)의 트레이드오프를 운영 성숙도에 맞춰 단계적으로 적용.

| 구분 | EAI | ESB | 서비스 메시 |
|:---|:---|:---|:---|
| 구조 | Hub & Spoke(중앙 허브) | 분산 메시지 버스 | Sidecar 프록시(인프라 계층) |
| 표준 | 벤더 종속 어댑터 | 웹서비스 표준(SOAP/WSDL) | L7 프록시(Envoy) |
| 결합도 | 중앙 집중 강결합 | 느슨한 결합 | 비즈/네트워크 완전 분리 |
| 장점 | 빠른 통합 | 재사용·확장성 | 트래픽·보안·관측 통합 통제 |
| 단점 | 허브 SPOF, 확장 한계 | 버스 병목 가능 | 운영 복잡도·프록시 오버헤드 |
| 적용 | 소수 레거시 통합 | SOA 전사 통합 | 클라우드 네이티브 MSA |

### 2) 모놀리식 vs MSA — 차세대 엔터프라이즈 전환
- **정의**: MSA는 단일 코드베이스·단일 DB의 모놀리식을 독립 배포·확장 가능한 다수 서비스로 분할한 아키텍처.
- **Ⅰ. 개요**: 빌드 지연, 부분 배포 불가, 장애 전파 등 모놀리식 한계 → 클라우드 확장·민첩성 요구.
- **Ⅱ. 구조/원리**: API Gateway → 서비스 디스커버리(Eureka/Consul) → 서비스별 독립 DB(Database per Service) → 이벤트 브로커(Kafka) 비동기 연계.
- **Ⅲ. 특징/비교**: 아래 비교표.
- **Ⅳ. 적용/방안**: 분산 트랜잭션은 **2PC 배제 → 사가 패턴 + 트랜잭셔널 아웃박스**, 조회 한계는 **CQRS + 이벤트 소싱**, 장애 격리는 **서킷 브레이커·폴백**.
- **Ⅴ. 결론**: MSA는 만능이 아니며, 조직 규모·도메인 분리·운영 자동화(DevOps) 역량이 전제될 때 효과적.

| 구분 | 모놀리식 | MSA |
|:---|:---|:---|
| 배포 단위 | 전체 일괄 | 서비스 독립 배포 |
| 데이터 | 단일 공유 DB | Database per Service |
| 확장 | 전체 스케일업 | 서비스별 스케일아웃 |
| 장애 | 전체 전파 위험 | 격리(서킷 브레이커) |
| 트랜잭션 | ACID 단순 | 사가/결과적 일관성 |
| 적합 | 소규모·단순 도메인 | 대규모·빠른 변경 |

### 3) ERP 도입 — 빅뱅 vs 점진 전환 전략
- **정의**: ERP는 전사 경영활동을 통합 DB로 연동하는 자원관리 시스템으로, 도입 시 **업무를 시스템에 맞출지(BPR 선행)·시스템을 업무에 맞출지(커스터마이징)** 가 핵심 의사결정.
- **Ⅰ. 개요**: 패키지 선정 → 커스터마이징/CBO → 데이터 이관 → 오픈의 생명주기.
- **Ⅱ. 구조/원리**: 코어 ERP + 부문별 SaaS(HR·CRM)를 느슨히 결합하는 **포스트모던/컴포저블 ERP(API 중심)** 로 진화.
- **Ⅲ. 특징/비교**: 빅뱅(일괄 전환·단기·고위험) vs 점진(모듈 단계 전환·저위험·장기·병행 운영 비용).
- **Ⅳ. 적용/방안**: 컷오버 시 **롤백 시나리오(Plan B)**, 데이터 정제·MDM 선행, 변화관리(교육·CAB) 병행.
- **Ⅴ. 결론**: 클라우드 ERP(2-Tier)·AI 내재화(이상탐지·수요예측)로 차세대 ERP 전환 가속.

| 구분 | 빅뱅 전환 | 점진(단계) 전환 |
|:---|:---|:---|
| 방식 | 전 모듈 일시 오픈 | 모듈/지사 순차 오픈 |
| 기간/비용 | 단기·집중 | 장기·병행 운영비 발생 |
| 리스크 | 높음(전면 장애) | 낮음(국소 영향) |
| 적합 | 단순·소규모 조직 | 대규모·복잡 조직 |

### 4) 데이터 통합·거버넌스 — DW/ETL·MDM 중심
- **정의**: 분산 운영시스템 데이터를 주제별·통합·시계열·비휘발성으로 모아 의사결정을 지원하는 DW(Data Warehouse)와, 전사 기준정보를 단일화하는 MDM(Master Data Management)이 핵심.
- **Ⅰ. 개요**: 사일로·데이터 품질 저하 → 단일 진실 공급원(Single Source of Truth) 필요.
- **Ⅱ. 구조/원리**:
```text
[운영시스템] → ETL/ELT → [DW/Lake] → [OLAP/BI]
                  │
              [MDM·데이터 거버넌스(품질·표준·오너십)]
```
- **Ⅲ. 특징/비교**: ETL(적재 전 변환·배치 병목) vs ELT(적재 후 DW 내부 변환·클라우드 표준), 스타 스키마(조회 빠름) vs 스노우플레이크(중복 제거·조인 복잡).
- **Ⅳ. 적용/방안**: 데이터 카탈로그·리니지로 가시성 확보, 데이터 레이크하우스로 비정형+ACID 결합, 데이터 메시로 도메인 분산 오너십.
- **Ⅴ. 결론**: 데이터 거버넌스 3요소(원칙·조직·프로세스/IT)를 함께 갖춰야 BI 신뢰성이 확보된다.

| 구분 | ETL | ELT |
|:---|:---|:---|
| 변환 위치 | 적재 전(별도 엔진) | 적재 후(DW 내부) |
| 처리 | 배치·병목 | DW 컴퓨팅 활용 |
| 적합 | 온프레미스 정형 | 클라우드 DW 대용량 |

## Ⅳ. 출제 포인트 & 함정

| 출제유형 | 1교시 단답 포인트 | 2~4교시 서술 포인트 |
|:---|:---|:---|
| 통합 아키텍처 | EAI/ESB/SOA/MSA 정의·1줄 차이 | 통합 진화(P2P→Hub→Bus→Mesh) + 비교표 + 전환전략 |
| 기업 애플리케이션 | ERP/SCM/CRM/MES/PLM 정의 | ERP 도입 방법론·BPR 연계·전환 리스크/대책 |
| MSA 패턴 | 서킷브레이커·사가·CQRS·디스커버리 | 분산 트랜잭션·장애 격리·점진 전환(스트랭글러) |
| 데이터/BI | DW/ETL/ELT/MDM/스타스키마 | DW-BI-거버넌스 연계 + ETL vs ELT 비교 |
| 거버넌스 | EA/ISP/COBIT/SLA/ITIL | EA 정렬(AS-IS→TO-BE) + 성과지표(ROI/TCO) |

**함정 정리**
- EAI vs ESB를 단순 동의어로 쓰면 감점 → **중앙 허브(벤더 종속)** vs **분산 버스(표준 개방)** 로 구분.
- SOA vs MSA 혼동 → SOA는 ESB 중앙 파이프(Smart Pipe), MSA는 Dumb Pipe·Smart Endpoint·독립 배포.
- MSA를 만능으로 서술 금지 → 분산 트랜잭션·운영 복잡도·조직 역량 전제를 반드시 단점으로 명시.
- ERP를 "패키지 도입"으로만 쓰면 약함 → **BPR 선행 vs 커스터마이징** 의사결정과 전환 리스크를 함께.
- 약어 최초 1회 풀네임 병기 누락(ERP, MSA, ESB, MDM 등)은 기본 감점 요인.

## Ⅴ. 결론 및 회독 포인트
- 통합 방식의 **진화 축**과 ERP·SCM·CRM의 **연계 축**을 비교표로 고정하면 어떤 변형 문제도 대응 가능하다.
- 모든 답안은 "기술 + 업무 + 데이터/조직 + 리스크·대책"의 4요소를 세트로 구성한다.
