## Ⅰ. 출제 관점 및 1교시 답안 포인트
> 기술부채(Technical Debt)는 빠른 개발을 위해 미흡한 설계·코드를 선택했을 때 향후 추가로 지불해야 하는 유지보수 비용(이자)을 부채에 비유한 개념이다. 방치 시 품질·생산성이 복리로 악화된다.

| 답안 축 | 정리 포인트 |
|:---|:---|
| 출제 맥락 | 생명주기, 프로세스 성숙도, 형상/품질/원가/일정/위험 관리의 통합 판단 |
| 1교시 기본 골격 | 정의 -> 목적 -> 핵심 요소/절차 -> 장단점/지표 -> 적용 판단 |
| 함께 묶을 논점 | SDLC, 프로세스 모델, CMMI, 형상관리, 원가·일정·리스크 |
| 2~4교시 확장 방향 | 도입 배경과 관리 필요성, 핵심 절차·지표·산출물, 성숙도/방법론 비교, 프로젝트 통제와 조직 적용 |


- 답안 포인트
  - `기술부채 (Technical Debt)`가 해결하려는 문제와 목적을 첫 문장에 압축
  - 핵심 구성요소·절차·지표는 3~5개 축으로 정리
  - 비교 개념과 실무 적용 조건을 함께 적시해 확장성 확보

## Ⅱ. 핵심 구조 및 메커니즘
- 원금(Principal): 결함·미흡 설계를 바로잡는 데 드는 비용
- 이자(Interest): 부채를 안고 개발할 때 누적되는 추가 비용
- 의도적 부채: 일정 압박으로 의식적 선택(전략적)
- 비의도적 부채: 역량 부족·요구 변화로 발생(우발적)
- 측정 지표: SQALE 등급, 코드 복잡도, 정적분석 위반 수

## Ⅲ. 비교·구조·지표 정리
```text
[빠른 구현] → [부채 발생]
   → [이자 누적: 결함·지연↑]
   → [리팩터링 상환] or [방치→파산(재작성)]
```

| 구분 | 내용 |
|:---|:---|
| 목적 | 단기 납기와 장기 품질의 트레이드오프 가시화·관리 |
| 장점 | 의사결정 투명화, 상환 우선순위 산정 가능 |
| 한계 | 정량 측정 난이도, 이해관계자 합의·투자 확보 어려움 |

## Ⅳ. 실무 적용 및 기술사 판단
- 정적분석(SonarQube)·리팩터링·코드리뷰로 상환 체계화
- 기술부채 백로그 관리로 애자일 스프린트에 상환 작업 반영

- 답안 포인트
  - 도입 전제, 운영 리스크, 기대 효과를 한 세트로 기술
  - 조직·프로세스·아키텍처 관점의 판단 기준을 함께 제시

## Ⅴ. 2~4교시 확장 프레임
| 확장 문단 | 서술 포인트 |
|:---|:---|
| 서론 | 도입 배경과 관리 필요성 |
| 본론 1 | 핵심 절차·지표·산출물 |
| 본론 2 | 성숙도/방법론 비교 |
| 본론 3 | 프로젝트 통제와 조직 적용 |
| 결론 | 기대효과와 한계 |


- 전개 순서
  1. 문제 배경과 필요성 제시
  2. 핵심 원리·구성요소·절차 설명
  3. 대안 구조 또는 유사 개념과 비교
  4. 도입 효과, 리스크, 기술사 판단 정리
  5. 확장 방향과 결론으로 마무리
