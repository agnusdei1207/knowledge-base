## Ⅰ. 출제 관점 및 1교시 답안 포인트
> 액터와 시스템 간 상호작용을 사용자 관점의 기능 단위(유스케이스)로 표현하는 UML 행위 다이어그램.

| 답안 축 | 정리 포인트 |
|:---|:---|
| 출제 맥락 | 요구 도출부터 우선순위, 명세, 추적성까지 품질 좋은 요구를 만드는 분석 출제축 |
| 1교시 기본 골격 | 정의 -> 목적 -> 핵심 요소/절차 -> 장단점/지표 -> 적용 판단 |
| 함께 묶을 논점 | 요구공학, SRS, RTM, 유스케이스, DFD, QFD, MoSCoW, 스토리맵 |
| 2~4교시 확장 방향 | 문제 상황과 이해관계자 관점, 도출·분석·명세 절차, 도구/기법 비교, 변경 통제와 검증 적용 |


- 답안 포인트
  - `유스케이스 다이어그램 (Use Case Diagram)`가 해결하려는 문제와 목적을 첫 문장에 압축
  - 핵심 구성요소·절차·지표는 3~5개 축으로 정리
  - 비교 개념과 실무 적용 조건을 함께 적시해 확장성 확보

## Ⅱ. 핵심 구조 및 메커니즘
- 액터(Actor): 시스템과 상호작용하는 사용자·외부시스템
- 유스케이스(Use Case): 사용자가 얻는 가치 있는 기능 단위
- 관계: 연관(Association), 포함(include), 확장(extend), 일반화
- include: 공통 기능을 필수로 재사용(예: 결제→로그인 포함)
- extend: 선택적·조건부 기능 확장(예: 결제←쿠폰적용)

## Ⅲ. 비교·구조·지표 정리
```text
        ┌──── 시스템 ────┐
[고객]──│  (주문하기)    │
        │     ▲include   │
        │  (로그인검증)  │
        │  (쿠폰적용)←extend
        └────────────────┘
```

| 구분 | 내용 |
|:---|:---|
| 목적 | 시스템 범위·기능을 사용자 관점에서 가시화 |
| 장점 | 비전문가 소통 용이, 범위 합의 도구 |
| 한계 | 내부 로직·순서 표현 불가(시퀀스로 보완) |

## Ⅳ. 실무 적용 및 기술사 판단
- include는 필수 공통화, extend는 선택적 분기로 구분
- 유스케이스 명세(Use Case Specification)로 상세 시나리오 보강
- 요구사항 도출·범위 정의 단계의 핵심 산출물

- 답안 포인트
  - 도입 전제, 운영 리스크, 기대 효과를 한 세트로 기술
  - 조직·프로세스·아키텍처 관점의 판단 기준을 함께 제시

## Ⅴ. 2~4교시 확장 프레임
| 확장 문단 | 서술 포인트 |
|:---|:---|
| 서론 | 문제 상황과 이해관계자 관점 |
| 본론 1 | 도출·분석·명세 절차 |
| 본론 2 | 도구/기법 비교 |
| 본론 3 | 변경 통제와 검증 적용 |
| 결론 | 실패 예방 효과 |


- 전개 순서
  1. 문제 배경과 필요성 제시
  2. 핵심 원리·구성요소·절차 설명
  3. 대안 구조 또는 유사 개념과 비교
  4. 도입 효과, 리스크, 기술사 판단 정리
  5. 확장 방향과 결론으로 마무리
