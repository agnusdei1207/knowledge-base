## Ⅰ. 출제 관점 및 1교시 답안 포인트
> 서비스 메시는 MSA 서비스 간 통신(트래픽 제어·보안·관측)을 애플리케이션 코드와 분리해 인프라 계층에서 처리하는 전용 네트워크 계층이다.

| 답안 축 | 정리 포인트 |
|:---|:---|
| 출제 맥락 | 컨테이너, 서비스 메시, 분산 트랜잭션, 관측성과 복원력을 포함한 운영형 아키텍처 축 |
| 1교시 기본 골격 | 정의 -> 목적 -> 핵심 요소/절차 -> 장단점/지표 -> 적용 판단 |
| 함께 묶을 논점 | Kubernetes, Service Mesh, API Gateway/BFF, Saga, CQRS, Serverless, MSA 전환 |
| 2~4교시 확장 방향 | 클라우드 네이티브 전환 배경, 런타임 구조와 통신 메커니즘, 모놀리스/분산구조 비교, 운영 복잡도와 대응 패턴 |


- 답안 포인트
  - `서비스 메시 (Service Mesh)`가 해결하려는 문제와 목적을 첫 문장에 압축
  - 핵심 구성요소·절차·지표는 3~5개 축으로 정리
  - 비교 개념과 실무 적용 조건을 함께 적시해 확장성 확보

## Ⅱ. 핵심 구조 및 메커니즘
- Data Plane: 각 Pod에 주입된 사이드카(Sidecar) 프록시(Envoy)가 트래픽 중계
- Control Plane: Istiod가 정책·라우팅·인증서를 사이드카에 배포
- mTLS: 서비스 간 상호 TLS 암호화로 제로트러스트 통신 구현
- 트래픽 관리: 카나리·A/B·트래픽 미러링·재시도·타임아웃
- 관측성: 메트릭·분산추적·로그 자동 수집

## Ⅲ. 비교·구조·지표 정리
```text
        ┌── Control Plane (Istiod) ──┐
        │ 정책/라우팅/인증서 배포     │
        └──────┬──────────┬──────────┘
   [Svc A | Sidecar] ←mTLS→ [Svc B | Sidecar]
        (Data Plane: Envoy 프록시)
```

| 구분 | 내용 |
|:---|:---|
| 목적 | 서비스 간 통신의 횡단관심사 인프라 위임 |
| 장점 | 코드 무변경, mTLS·관측성·트래픽 제어 일관 적용 |
| 한계 | 사이드카 리소스 오버헤드·지연·운영 복잡도 |

## Ⅳ. 실무 적용 및 기술사 판단
- API 게이트웨이(남북 트래픽) vs 서비스 메시(동서 트래픽) 역할 구분
- 사이드카 부담 완화 위해 Ambient Mesh(사이드카리스) 등장
- 제로트러스트 아키텍처의 서비스 간 인증 실현 수단

- 답안 포인트
  - 도입 전제, 운영 리스크, 기대 효과를 한 세트로 기술
  - 조직·프로세스·아키텍처 관점의 판단 기준을 함께 제시

## Ⅴ. 2~4교시 확장 프레임
| 확장 문단 | 서술 포인트 |
|:---|:---|
| 서론 | 클라우드 네이티브 전환 배경 |
| 본론 1 | 런타임 구조와 통신 메커니즘 |
| 본론 2 | 모놀리스/분산구조 비교 |
| 본론 3 | 운영 복잡도와 대응 패턴 |
| 결론 | 확장성·회복탄력성 결론 |


- 전개 순서
  1. 문제 배경과 필요성 제시
  2. 핵심 원리·구성요소·절차 설명
  3. 대안 구조 또는 유사 개념과 비교
  4. 도입 효과, 리스크, 기술사 판단 정리
  5. 확장 방향과 결론으로 마무리
