## Ⅰ. 출제 관점 및 1교시 답안 포인트
> 서비스 디스커버리는 동적으로 생성·소멸하는 서비스 인스턴스의 네트워크 위치(IP·Port)를 레지스트리에 등록·조회하여 호출 가능하게 하는 메커니즘이다.

| 답안 축 | 정리 포인트 |
|:---|:---|
| 출제 맥락 | 컨테이너, 서비스 메시, 분산 트랜잭션, 관측성과 복원력을 포함한 운영형 아키텍처 축 |
| 1교시 기본 골격 | 정의 -> 목적 -> 핵심 요소/절차 -> 장단점/지표 -> 적용 판단 |
| 함께 묶을 논점 | Kubernetes, Service Mesh, API Gateway/BFF, Saga, CQRS, Serverless, MSA 전환 |
| 2~4교시 확장 방향 | 클라우드 네이티브 전환 배경, 런타임 구조와 통신 메커니즘, 모놀리스/분산구조 비교, 운영 복잡도와 대응 패턴 |


- 답안 포인트
  - `서비스 디스커버리 (Service Discovery)`가 해결하려는 문제와 목적을 첫 문장에 압축
  - 핵심 구성요소·절차·지표는 3~5개 축으로 정리
  - 비교 개념과 실무 적용 조건을 함께 적시해 확장성 확보

## Ⅱ. 핵심 구조 및 메커니즘
- Service Registry: 인스턴스 위치를 저장하는 저장소(Consul·Eureka·etcd)
- 등록: 인스턴스 기동 시 자가 등록 또는 외부 등록자가 등록
- 헬스체크: 비정상 인스턴스를 레지스트리에서 자동 제거
- 클라이언트 사이드: 클라이언트가 레지스트리 조회 후 직접 LB(Ribbon)
- 서버 사이드: LB/프록시가 레지스트리 조회 후 라우팅(K8s Service)

## Ⅲ. 비교·구조·지표 정리
```text
[클라이언트 사이드]          [서버 사이드]
Client→Registry→IP목록      Client→LB/Proxy→Registry
   └──직접 호출──→Instance       └→ Instance (LB가 라우팅)
```

| 구분 | 내용 |
|:---|:---|
| 목적 | 동적 인스턴스 위치를 자동 추적·라우팅 |
| 장점 | 오토스케일·장애 인스턴스 자동 배제·하드코딩 제거 |
| 한계 | 레지스트리 SPOF·일관성 문제, 클라이언트 사이드는 언어 종속 |

## Ⅳ. 실무 적용 및 기술사 판단
- 클라이언트 사이드: 네트워크 홉 적으나 LB 로직이 클라이언트에 분산
- 서버 사이드: 클라이언트 단순화, K8s는 DNS+kube-proxy로 내장 제공
- 서비스 메시 도입 시 사이드카가 디스커버리·LB를 투명 처리

- 답안 포인트
  - 도입 전제, 운영 리스크, 기대 효과를 한 세트로 기술
  - 조직·프로세스·아키텍처 관점의 판단 기준을 함께 제시

## Ⅴ. 2~4교시 확장 프레임
| 확장 문단 | 서술 포인트 |
|:---|:---|
| 서론 | 클라우드 네이티브 전환 배경 |
| 본론 1 | 런타임 구조와 통신 메커니즘 |
| 본론 2 | 모놀리스/분산구조 비교 |
| 본론 3 | 운영 복잡도와 대응 패턴 |
| 결론 | 확장성·회복탄력성 결론 |


- 전개 순서
  1. 문제 배경과 필요성 제시
  2. 핵심 원리·구성요소·절차 설명
  3. 대안 구조 또는 유사 개념과 비교
  4. 도입 효과, 리스크, 기술사 판단 정리
  5. 확장 방향과 결론으로 마무리
