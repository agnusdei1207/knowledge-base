## Ⅰ. 출제 관점 및 1교시 답안 포인트
> 행위주도개발(Behavior-Driven Development, BDD)은 TDD를 확장한 기법으로, 비즈니스가 이해하는 자연어로 시스템 행위를 명세하여 개발자·기획·QA가 공통 언어로 협업하고 그 명세를 실행 가능한 테스트로 자동화하는 방법이다.

| 답안 축 | 정리 포인트 |
|:---|:---|
| 출제 맥락 | 애자일 실행체계와 DevOps 기반 전달 자동화, 운영 피드백까지 연결하는 출제축 |
| 1교시 기본 골격 | 정의 -> 목적 -> 핵심 요소/절차 -> 장단점/지표 -> 적용 판단 |
| 함께 묶을 논점 | 스크럼, XP, 칸반, MVP, SAFe/LeSS, DevOps, IaC, SRE, GitOps |
| 2~4교시 확장 방향 | 민첩성 요구와 도입 배경, 역할·이벤트·파이프라인 구조, 전통 방식 대비 차이, 지표 기반 운영과 확장 전략 |


- 답안 포인트
  - `행위주도개발 (BDD)`가 해결하려는 문제와 목적을 첫 문장에 압축
  - 핵심 구성요소·절차·지표는 3~5개 축으로 정리
  - 비교 개념과 실무 적용 조건을 함께 적시해 확장성 확보

## Ⅱ. 핵심 구조 및 메커니즘
- 공통 언어(Ubiquitous Language): 도메인 용어로 시나리오를 기술해 의사소통 간극 제거
- Given-When-Then 구조: Given(전제 상황)–When(행위·이벤트)–Then(기대 결과)
- 실행 가능 명세: 시나리오가 곧 인수 테스트(Acceptance Test)로 자동 실행
- 도구: Cucumber·Gherkin 문법, SpecFlow 등
- 아웃사이드-인(Outside-In): 사용자 관점 행위에서 내부 구현으로 전개

## Ⅲ. 비교·구조·지표 정리
```text
 사용자 스토리 ─> 시나리오(Gherkin)
   Given 로그인 상태
   When  결제 버튼 클릭   ─자동화→ Acceptance Test ─> Pass/Fail
   Then  주문 완료 표시        │
        ↑ 비즈니스·개발·QA 공통 언어 협업
```

| 구분 | 내용 |
|:---|:---|
| 목적 | 행위를 공통 언어로 명세해 협업·검증·문서화를 일원화 |
| 장점 | 요구 누락 감소, 살아있는 문서, 인수 기준 명확, 회귀 안정성 |
| 한계 | 시나리오 유지보수 비용, 과도한 추상화·문법 학습 부담 |

## Ⅳ. 실무 적용 및 기술사 판단
- TDD(단위)+BDD(행위·인수)로 품질 계층화, ATDD와 함께 인수 기준 자동화
- CI 파이프라인에서 인수 테스트 게이트로 활용, 애자일 요구관리와 연계

- 답안 포인트
  - 도입 전제, 운영 리스크, 기대 효과를 한 세트로 기술
  - 조직·프로세스·아키텍처 관점의 판단 기준을 함께 제시

## Ⅴ. 2~4교시 확장 프레임
| 확장 문단 | 서술 포인트 |
|:---|:---|
| 서론 | 민첩성 요구와 도입 배경 |
| 본론 1 | 역할·이벤트·파이프라인 구조 |
| 본론 2 | 전통 방식 대비 차이 |
| 본론 3 | 지표 기반 운영과 확장 전략 |
| 결론 | 조직 문화 정착 포인트 |


- 전개 순서
  1. 문제 배경과 필요성 제시
  2. 핵심 원리·구성요소·절차 설명
  3. 대안 구조 또는 유사 개념과 비교
  4. 도입 효과, 리스크, 기술사 판단 정리
  5. 확장 방향과 결론으로 마무리
