## Ⅰ. 출제 관점 및 1교시 답안 포인트
> GoF(Gang of Four) 구조(Structural) 패턴으로, 복잡한 서브시스템(Subsystem)의 다수 인터페이스를 감싸는 통합된 상위 인터페이스를 제공하여 사용을 단순화하는 패턴.

| 답안 축 | 정리 포인트 |
|:---|:---|
| 출제 맥락 | 모듈 경계, 아키텍처 스타일, 설계 원칙, 패턴, 품질속성까지 설계 판단을 묻는 축 |
| 1교시 기본 골격 | 정의 -> 목적 -> 핵심 요소/절차 -> 장단점/지표 -> 적용 판단 |
| 함께 묶을 논점 | 응집도/결합도, 아키텍처 뷰, MVC, MSA, DDD, SOLID, DI, 코드 품질 메트릭 |
| 2~4교시 확장 방향 | 설계 목표와 품질속성, 구성요소·패턴·원리, 대안 구조 비교, 적용 조건과 안티패턴 |


- 답안 포인트
  - `퍼사드 패턴 (Facade)`가 해결하려는 문제와 목적을 첫 문장에 압축
  - 핵심 구성요소·절차·지표는 3~5개 축으로 정리
  - 비교 개념과 실무 적용 조건을 함께 적시해 확장성 확보

## Ⅱ. 핵심 구조 및 메커니즘
- **Facade**: 서브시스템 기능을 묶은 단순·통합 진입점 제공
- **Subsystem 클래스들**: 실제 세부 기능을 수행하는 다수의 내부 클래스
- **Client**: Facade만 호출, 내부 복잡도·의존을 알 필요 없음
- **원리**: 최소지식 원칙(LoD, Law of Demeter)으로 결합도 완화, 캡슐화

## Ⅲ. 비교·구조·지표 정리
```text
                ┌──> SubsystemA
Client → Facade ┼──> SubsystemB
                └──> SubsystemC
   단일 호출 → Facade가 내부 호출 순서·조합 조율
```

| 구분 | 내용 |
|:---|:---|
| 목적 | 서브시스템 통합 단순 인터페이스 제공 |
| 장점 | 사용 편의↑, 결합도↓, 내부 변경 영향 격리 |
| 한계 | 만능 객체화 위험, 세밀 제어 시 서브시스템 직접 접근 필요 |

## Ⅳ. 실무 적용 및 기술사 판단
- 계층형 아키텍처의 Service Facade, 복잡 API의 SDK 진입점에 활용
- 마이크로서비스의 API Gateway·BFF가 Facade 개념의 확장 적용
- Adapter와 비교: Facade는 단순화(다대일), Adapter는 인터페이스 변환(일대일)

- 답안 포인트
  - 도입 전제, 운영 리스크, 기대 효과를 한 세트로 기술
  - 조직·프로세스·아키텍처 관점의 판단 기준을 함께 제시

## Ⅴ. 2~4교시 확장 프레임
| 확장 문단 | 서술 포인트 |
|:---|:---|
| 서론 | 설계 목표와 품질속성 |
| 본론 1 | 구성요소·패턴·원리 |
| 본론 2 | 대안 구조 비교 |
| 본론 3 | 적용 조건과 안티패턴 |
| 결론 | 유지보수성과 확장성 결론 |


- 전개 순서
  1. 문제 배경과 필요성 제시
  2. 핵심 원리·구성요소·절차 설명
  3. 대안 구조 또는 유사 개념과 비교
  4. 도입 효과, 리스크, 기술사 판단 정리
  5. 확장 방향과 결론으로 마무리
