## Ⅰ. 출제 관점 및 1교시 답안 포인트
> 요구사항 명세서(SRS, Software Requirements Specification)는 시스템의 기능·비기능 요구사항을 합의·검증 가능하도록 체계적으로 문서화한 공식 산출물.

| 답안 축 | 정리 포인트 |
|:---|:---|
| 출제 맥락 | 요구 도출부터 우선순위, 명세, 추적성까지 품질 좋은 요구를 만드는 분석 출제축 |
| 1교시 기본 골격 | 정의 -> 목적 -> 핵심 요소/절차 -> 장단점/지표 -> 적용 판단 |
| 함께 묶을 논점 | 요구공학, SRS, RTM, 유스케이스, DFD, QFD, MoSCoW, 스토리맵 |
| 2~4교시 확장 방향 | 문제 상황과 이해관계자 관점, 도출·분석·명세 절차, 도구/기법 비교, 변경 통제와 검증 적용 |


- 답안 포인트
  - `요구사항 명세서 (SRS)`가 해결하려는 문제와 목적을 첫 문장에 압축
  - 핵심 구성요소·절차·지표는 3~5개 축으로 정리
  - 비교 개념과 실무 적용 조건을 함께 적시해 확장성 확보

## Ⅱ. 핵심 구조 및 메커니즘
- 개요: 목적, 범위, 정의·약어, 참조
- 전체 설명: 제품 관점, 사용자 특성, 제약·가정
- 상세 요구사항: 기능·비기능·인터페이스 요구사항
- 검증기준: 각 요구사항의 수용·테스트 기준
- 부록: 추적성 매트릭스(RTM), 용어집

## Ⅲ. 비교·구조·지표 정리
```text
SRS
 ├ 1 개요(목적/범위/용어)
 ├ 2 전체설명(제약/가정)
 ├ 3 상세요구(FR/NFR/IF)
 └ 4 부록(RTM/용어집)
```

| 구분 | 내용 |
|:---|:---|
| 목적 | 이해관계자 합의·계약·설계의 기준선(Baseline) 제공 |
| 장점 | 추적성·검증성 확보, 분쟁 시 기준 문서 |
| 한계 | 작성·유지 비용, 변경 시 문서 동기화 부담 |

## Ⅳ. 실무 적용 및 기술사 판단
- 좋은 SRS의 8특성: 완전·일관·검증가능·명확·수정가능·추적가능 등(IEEE 830/29148)
- 명세 언어: 자연어+표+모델(UML) 혼용으로 모호성 저감
- 형상관리로 기준선 통제, 변경통제위원회(CCB) 연계

- 답안 포인트
  - 도입 전제, 운영 리스크, 기대 효과를 한 세트로 기술
  - 조직·프로세스·아키텍처 관점의 판단 기준을 함께 제시

## Ⅴ. 2~4교시 확장 프레임
| 확장 문단 | 서술 포인트 |
|:---|:---|
| 서론 | 문제 상황과 이해관계자 관점 |
| 본론 1 | 도출·분석·명세 절차 |
| 본론 2 | 도구/기법 비교 |
| 본론 3 | 변경 통제와 검증 적용 |
| 결론 | 실패 예방 효과 |


- 전개 순서
  1. 문제 배경과 필요성 제시
  2. 핵심 원리·구성요소·절차 설명
  3. 대안 구조 또는 유사 개념과 비교
  4. 도입 효과, 리스크, 기술사 판단 정리
  5. 확장 방향과 결론으로 마무리
