## Ⅰ. 출제 관점 및 1교시 답안 포인트
> API 게이트웨이는 클라이언트 요청의 단일 진입점으로 라우팅·인증·집계를 담당하며, BFF(Backend for Frontend)는 웹·모바일 등 클라이언트 유형별로 특화된 백엔드 게이트웨이를 두는 패턴이다.

| 답안 축 | 정리 포인트 |
|:---|:---|
| 출제 맥락 | 컨테이너, 서비스 메시, 분산 트랜잭션, 관측성과 복원력을 포함한 운영형 아키텍처 축 |
| 1교시 기본 골격 | 정의 -> 목적 -> 핵심 요소/절차 -> 장단점/지표 -> 적용 판단 |
| 함께 묶을 논점 | Kubernetes, Service Mesh, API Gateway/BFF, Saga, CQRS, Serverless, MSA 전환 |
| 2~4교시 확장 방향 | 클라우드 네이티브 전환 배경, 런타임 구조와 통신 메커니즘, 모놀리스/분산구조 비교, 운영 복잡도와 대응 패턴 |


- 답안 포인트
  - `API 게이트웨이·BFF (API Gateway·Backend for Frontend)`가 해결하려는 문제와 목적을 첫 문장에 압축
  - 핵심 구성요소·절차·지표는 3~5개 축으로 정리
  - 비교 개념과 실무 적용 조건을 함께 적시해 확장성 확보

## Ⅱ. 핵심 구조 및 메커니즘
- 라우팅: 요청을 해당 마이크로서비스로 전달·집계(Aggregation)
- 횡단관심사: 인증·인가·Rate Limit·캐싱·로깅 일괄 처리
- 프로토콜 변환: REST↔gRPC, 응답 형식 변환
- BFF: 채널별(Web/Mobile/IoT) 최적화 API 제공으로 과대·과소 패칭 해소
- 보안: 백엔드 직접 노출 차단, 토큰 검증 중앙화

## Ⅲ. 비교·구조·지표 정리
```text
[Web]  → BFF-Web  ┐
[App]  → BFF-App  ┤→ API Gateway →┬→ Svc A
[IoT]  → BFF-IoT  ┘ (인증/Rate)   ├→ Svc B
                                  └→ Svc C
```

| 구분 | 내용 |
|:---|:---|
| 목적 | 진입점 단일화·횡단관심사 집중·클라이언트별 최적화 |
| 장점 | 보안 중앙화·결합도 완화·채널별 응답 최적화 |
| 한계 | SPOF·병목 위험, BFF 수 증가 시 중복·관리 부담 |

## Ⅳ. 실무 적용 및 기술사 판단
- 게이트웨이는 남북(North-South) 트래픽, 서비스 메시는 동서 트래픽 담당
- HA 구성·오토스케일로 SPOF 완화, Kong·Spring Cloud Gateway 활용
- BFF는 마이크로프론트엔드와 결합 시 채널 독립 배포 강화

- 답안 포인트
  - 도입 전제, 운영 리스크, 기대 효과를 한 세트로 기술
  - 조직·프로세스·아키텍처 관점의 판단 기준을 함께 제시
