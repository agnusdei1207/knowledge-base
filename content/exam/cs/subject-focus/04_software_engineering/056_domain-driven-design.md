## Ⅰ. 출제 관점 및 1교시 답안 포인트
> 도메인 주도 설계(DDD, Domain-Driven Design)는 복잡한 업무 도메인을 중심에 두고, 도메인 전문가와 개발자가 유비쿼터스 언어(공통 언어)로 모델을 정제하여 소프트웨어 구조에 반영하는 설계 방법론이다.

| 답안 축 | 정리 포인트 |
|:---|:---|
| 출제 맥락 | 모듈 경계, 아키텍처 스타일, 설계 원칙, 패턴, 품질속성까지 설계 판단을 묻는 축 |
| 1교시 기본 골격 | 정의 -> 목적 -> 핵심 요소/절차 -> 장단점/지표 -> 적용 판단 |
| 함께 묶을 논점 | 응집도/결합도, 아키텍처 뷰, MVC, MSA, DDD, SOLID, DI, 코드 품질 메트릭 |
| 2~4교시 확장 방향 | 설계 목표와 품질속성, 구성요소·패턴·원리, 대안 구조 비교, 적용 조건과 안티패턴 |


- 답안 포인트
  - `도메인 주도 설계 (DDD)`가 해결하려는 문제와 목적을 첫 문장에 압축
  - 핵심 구성요소·절차·지표는 3~5개 축으로 정리
  - 비교 개념과 실무 적용 조건을 함께 적시해 확장성 확보

## Ⅱ. 핵심 구조 및 메커니즘
- 바운디드 컨텍스트(Bounded Context): 모델이 유효한 경계, 컨텍스트 맵으로 관계 정의
- 애그리게이트(Aggregate): 일관성 단위, 루트(Aggregate Root)를 통해서만 접근
- 엔티티·값 객체(Entity·Value Object): 식별성 유무로 구분
- 유비쿼터스 언어(Ubiquitous Language): 도메인-코드 공통 어휘
- 전략적 설계(컨텍스트)·전술적 설계(애그리게이트·리포지토리·도메인 이벤트)

## Ⅲ. 비교·구조·지표 정리
```text
[도메인 전문가] ─유비쿼터스 언어─ [개발자]
        │ (모델 정제)
   [Bounded Context A] ── 컨텍스트 맵 ── [Bounded Context B]
        │
   [Aggregate Root] → [Entity / Value Object]
```

| 구분 | 내용 |
|:---|:---|
| 목적 | 복잡 도메인의 정확한 모델링과 의사소통 일치 |
| 장점 | 업무-코드 정합, 명확한 경계, 변경 국소화 |
| 한계 | 학습 곡선 높음, 단순 도메인엔 과도, 전문가 협업 필수 |

## Ⅳ. 실무 적용 및 기술사 판단
- 바운디드 컨텍스트를 MSA 서비스 경계 도출 기준으로 활용
- 도메인 이벤트는 EDA·이벤트 소싱과 연계, 헥사고날 아키텍처로 도메인 보호

- 답안 포인트
  - 도입 전제, 운영 리스크, 기대 효과를 한 세트로 기술
  - 조직·프로세스·아키텍처 관점의 판단 기준을 함께 제시

## Ⅴ. 2~4교시 확장 프레임
| 확장 문단 | 서술 포인트 |
|:---|:---|
| 서론 | 설계 목표와 품질속성 |
| 본론 1 | 구성요소·패턴·원리 |
| 본론 2 | 대안 구조 비교 |
| 본론 3 | 적용 조건과 안티패턴 |
| 결론 | 유지보수성과 확장성 결론 |


- 전개 순서
  1. 문제 배경과 필요성 제시
  2. 핵심 원리·구성요소·절차 설명
  3. 대안 구조 또는 유사 개념과 비교
  4. 도입 효과, 리스크, 기술사 판단 정리
  5. 확장 방향과 결론으로 마무리
