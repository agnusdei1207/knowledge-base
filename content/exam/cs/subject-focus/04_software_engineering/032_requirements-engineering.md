## Ⅰ. 출제 관점 및 1교시 답안 포인트
> 이해관계자의 요구를 체계적으로 도출·분석·명세·확인·관리하여 검증 가능한 요구사항으로 정제하는 소프트웨어공학 활동.

| 답안 축 | 정리 포인트 |
|:---|:---|
| 출제 맥락 | 요구 도출부터 우선순위, 명세, 추적성까지 품질 좋은 요구를 만드는 분석 출제축 |
| 1교시 기본 골격 | 정의 -> 목적 -> 핵심 요소/절차 -> 장단점/지표 -> 적용 판단 |
| 함께 묶을 논점 | 요구공학, SRS, RTM, 유스케이스, DFD, QFD, MoSCoW, 스토리맵 |
| 2~4교시 확장 방향 | 문제 상황과 이해관계자 관점, 도출·분석·명세 절차, 도구/기법 비교, 변경 통제와 검증 적용 |


- 답안 포인트
  - `요구공학 (Requirements Engineering)`가 해결하려는 문제와 목적을 첫 문장에 압축
  - 핵심 구성요소·절차·지표는 3~5개 축으로 정리
  - 비교 개념과 실무 적용 조건을 함께 적시해 확장성 확보

## Ⅱ. 핵심 구조 및 메커니즘
- 도출(Elicitation): 인터뷰·워크숍·관찰·프로토타입으로 요구 수집
- 분석(Analysis): 충돌·중복·모호성 해소 및 우선순위화
- 명세(Specification): SRS(Software Requirements Specification)로 문서화
- 확인(Validation): 리뷰·프로토타입으로 정확성·완전성 검증
- 관리(Management): 변경통제·추적성(RTM) 유지

## Ⅲ. 비교·구조·지표 정리
```text
[이해관계자] → 도출 → 분석 → 명세(SRS) → 확인
                  ↑________ 관리(변경/추적) ________↓
```

| 구분 | 내용 |
|:---|:---|
| 목적 | 정확·완전·검증가능한 요구사항 확보로 프로젝트 실패 예방 |
| 장점 | 재작업·범위혼란 감소, 추적성 확보 |
| 한계 | 암묵적 요구·변화하는 요구 포착 어려움 |

## Ⅳ. 실무 적용 및 기술사 판단
- 5단계는 단방향이 아닌 반복·점증적(Iterative) 수행
- 애자일에서는 백로그·유저스토리로 경량화하여 적용
- ISO/IEC/IEEE 29148 표준과 연계

- 답안 포인트
  - 도입 전제, 운영 리스크, 기대 효과를 한 세트로 기술
  - 조직·프로세스·아키텍처 관점의 판단 기준을 함께 제시

## Ⅴ. 2~4교시 확장 프레임
| 확장 문단 | 서술 포인트 |
|:---|:---|
| 서론 | 문제 상황과 이해관계자 관점 |
| 본론 1 | 도출·분석·명세 절차 |
| 본론 2 | 도구/기법 비교 |
| 본론 3 | 변경 통제와 검증 적용 |
| 결론 | 실패 예방 효과 |


- 전개 순서
  1. 문제 배경과 필요성 제시
  2. 핵심 원리·구성요소·절차 설명
  3. 대안 구조 또는 유사 개념과 비교
  4. 도입 효과, 리스크, 기술사 판단 정리
  5. 확장 방향과 결론으로 마무리
