# CSPE 답안 작성법 단일 정본

> 이 문서가 CSPE 키워드 노트 작성법의 **유일 정본**이다. `model-answer.md`, `master-template.md`, `AGENTS.md`는 이 문서를 참조할 뿐 별도 작성법을 만들지 않는다.

## 0. 최상위 논리

기술사는 단순히 개념을 설명하는 사람이 아니라, 요구사항을 구조로 바꾸고 기술을 선택해 구현·운영·개선까지 책임지는 사람이다. 따라서 모든 2~4교시 답안은 개요로 시작하더라도 아래 흐름을 잃지 않아야 한다.

```text
+----------+   +----------+   +----------+   +----------+   +----------+   +----------+
| 요구사항 | -> | 구조설계 | -> | 기술선정 | -> | 구현전략 | -> | 운영관리 | -> | 개선     |
+----------+   +----------+   +----------+   +----------+   +----------+   +----------+
```

- **요구사항**: 문제 신호어와 출제 의도에서 무엇을 해결해야 하는지 정의함
- **구조설계**: 요구사항을 구성요소·관계·데이터 흐름으로 전개함
- **기술선정**: 특징/비교를 통해 왜 이 기술·방식이 맞는지 판단함
- **구현전략**: 절차·알고리즘·적용 단계를 구체화함
- **운영관리**: 실제 적용 시 깨지는 지점과 관리 지표를 제시함
- **개선**: 문제 원인별 대응 방안과 발전 방향으로 마무리함

> 요약: 개요는 시작점일 뿐이며, 전체 답안은 요구사항에서 개선까지 전진해야 함.

### 통찰이 보여야 한다

모든 노트는 개념을 순서대로 나열하는 백과사전(위키)이 아니다. 읽는 사람이 마지막 문장까지 읽었을 때 `그래서 이 기술을 언제·어떻게 선택하고 무엇을 통제해야 하는가`라는 통찰 하나를 손에 쥐고 나가야 하는 글이다. 정의·특징·비교·구조·절차·사례 각각이 기술적으로 정확해도, 그 전체를 관통하는 통찰이 없으면 그 노트는 실패로 판정한다.

- 이 통찰은 절 하나에 숨어 있지 않고, 개요의 문제의식에서 시작해 특징·비교의 판단 근거를 거쳐 결론의 선택으로 끝까지 관통해야 함
- 통찰을 검증 가능한 산출물로 강제하는 장치가 1-2절의 `방향성`(작성 근거 최상단 문장)과 `위키형 실패 판정`이며, 모든 절은 이 통찰 하나를 향해 쌓여야 함
- 통찰이 없다는 신호: 결론을 가리고 특징·비교·구조만 읽었을 때 `그래서 뭘 어떻게 하라는 건데`라는 질문에 답이 안 나오면, 사실은 쌓였지만 통찰은 없는 것임

> 요약: 모든 절은 사실 나열이 아니라 하나의 통찰로 수렴해야 하며, 그 통찰은 방향성 문장으로 명시하고 결론에서 회수함.

## 0-1. 작성 방식: 반복 다듬기

노트는 한 번의 작성으로 완성되지 않는다. 초안은 완료가 아니라 깎아나갈 시작점이며, 모든 노트는 1-1의 검수 게이트를 수정 사항이 없는 상태로 통과할 때까지 반복해 다듬는다. 회차 수·검사 순서·통과 기준은 1-1이 정본이다. 문장을 줄일 때는 핵심을 삭제하는 것이 아니라 채점자가 이해하도록 `대상 + 판단 기준 + 필요한 이유`만 남긴다.

**부자연스러운 문장은 가장 위험한 실패로 판정한다.** 기술적으로 맞고 핵심어가 들어 있어도 조사, 수식어 위치, 단어 순서, 목적어와 동사 결합이 어색하면 답안 문장으로 사용하지 않는다. 문장을 줄이거나 전문용어로 바꾼 뒤에는 소리 내어 읽듯 다시 읽고, 평소 한국어 문장으로 자연스럽게 말할 수 있는 형태인지 확인한다.

전수 검토는 수정 개수를 만드는 작업이 아니다. 기술적 오류, 오해 가능성, 비교축 불일치, 템플릿 위반, 채점 판단을 흐리는 장황함이 없으면 **수정 사항 0건으로 통과**시키고, 의미가 같은 동의어 치환, 작성자 취향의 문체 변경, 이미 읽기 쉬운 문장의 재배열은 하지 않는다. 수정할 때는 걸린 단어·조사·배치·논리와 교정 이유를 설명할 수 있어야 하며, 이유를 설명하지 못하는 변경은 하지 않는다.

교정 과정에서 새로운 실패 유형이나 더 나은 문장이 확인되면 [CSPE 답안 작성 예시집](@/exam/cs/writing-examples.md)에 `문제 유형·권장 배치·판정 이유·대체 문장`을 추가한다. 예시집은 고정된 부록이 아니라 이후 작성 판단에 재사용하는 누적 데이터로 관리한다.

절 제목이 이미 역할을 밝히므로 본문과 작성 근거에서 `실무 사례는`, `특징은`, `Ⅵ 사례 선정`처럼 절 이름을 다시 주어로 쓰지 않는다. `서비스 호출 그래프와 음수 비용은...`처럼 선정한 대상과 판단 이유로 시작한다.

### 대표 핵심 선정 게이트

대표성·핵심성·출제 의도 적합성은 Ⅵ의 사례에만 적용하는 기준이 아니라 제목, 미리 알고가기, 작성 근거, Ⅰ~Ⅶ의 모든 문장, 표 헤더·셀, 도식, 요약에 공통 적용한다. 각 항목은 `이 문제에서 왜 이 내용을 써야 하는가`에 한 문장으로 답할 수 있어야 하며, 답하지 못하면 삭제한다.

- **대표성**: 해당 개념을 설명할 때 일반적으로 인정되는 구조·기법·사례인가
- **핵심성**: 정의, 고유 특성, 선택 조건, 구조 원리, 실패 조건, 검증 기준 중 하나를 직접 설명하는가
- **출제 의도 적합성**: 문제의 핵심어와 요구사항을 회수하고 채점자가 기술 선택·비교·적용 판단을 확인하게 하는가
- **절 간 기여**: 앞 절을 표현만 바꿔 반복하지 않고 새로운 판단을 한 단계 추가하는가
- **삭제 대상**: 드문 예외, 제품 홍보, 역사·배경 지식, 개수 채우기용 항목, 문제 논지와 무관한 최신 용어, 측정할 수 없는 효과
- **주제 경계 준수**: 제목의 개념·원리·가치·적용 판단을 직접 설명하지 않는 수식, 주변 개념, 비교 대상의 세부 문제는 기술적으로 맞아도 삭제함
- **핵심 부분 보존**: 정의·특징·구조·사례 중 주제를 정확히 관통해 이미 잘 잡힌 부분은 교정 과정에서도 유지함. 한 문장의 오류를 이유로 검증된 핵심 문장까지 전면 재작성하지 않음

실무 사례는 널리 쓰이는 대표 업무·시스템에서 본문의 구조나 선택 기준이 실제로 드러나는 경우만 쓴다. `적용 대상 -> 기술 고유 조치`만으로 적용 방식이 분명하면 그 문장에서 끝낸다. 검증 지표·실패 조건은 기술 선택이나 설정을 실제로 바꾸는 경우에만 정확한 대상과 기준을 추가한다.

## 1. 답안 품질 3박자와 논리 흐름성

- **직관성**: 채점자가 5초 안에 구조를 파악해야 함. 불친절한 압축을 피하고, 특징/비교, 간결한 텍스트 도식, 표 요약으로 핵심을 먼저 보임
- **이해성**: 학습자와 작성자가 이 파일만 읽고도 개념·용어·동작 원리를 이해할 수 있어야 함. 하나하나 떠먹이는 설명이 아니라, 필요한 연결고리를 생략하지 않는 설명이어야 함
- **핵심포함성**: 긴 설명이 아니라 개념·대상·판단 기준·적용 조건만 남기고 배경·역사·수식 과시를 제거함
- **시간 제한성**: 1교시는 배정 시간 안에 10문제를, 2~4교시는 문제당 3쪽 내외를 손으로 써야 함. 그 분량·시간을 넘는 문장·표·사례는 먼저 삭제하고, 남길 내용은 더 짧고 효율적인 표현으로 바꿈
- **논리 흐름성**: 개요의 문제의식이 특징/비교의 선택 기준으로 이어지고, 구성요소/구조가 그 선택 기준을 설명하며, 실무 사례가 앞 절의 판단을 다시 검증해야 함. 앞 절에서 제시하지 않은 기준이 뒤 절에서 갑자기 등장하거나 뒤 절의 문제점이 앞의 구조·조건과 무관하면 실패임
- **방향성**: 답안은 한 문단씩 새로운 판단을 전진시켜야 하며, 개요에서 잡은 핵심 축이 끝까지 흔들리지 않아야 함. 개요의 핵심 문제, 비교의 판단 기준, 구조의 원리, 결론의 대응이 같은 축을 바라봐야 함
- **인사이트 가시성**: 단순 정의 나열이 아니라 왜 이 기술을 선택하거나 버려야 하는지, 어디서 병목이 생기고 무엇을 통제해야 하는지가 필요한 절에 드러나야 함. 모든 절에 지표·병목·실패 조건을 의무적으로 하나씩 넣지 않으며, 주제의 핵심 판단을 실제로 바꿀 때만 추가함
- **중복 억제**: 앞 절에서 이미 한 말을 표현만 바꿔 반복하지 않음. `빠르다`, `효율적이다`를 반복하는 대신 무엇이 왜 빨라지는지, 어떤 조건에서 깨지는지 다음 절로 전개해야 함

- 1교시는 13문제 중 10문제를 쓰므로 `정의 1~2줄 + 특징 3개 + 미니 도식 + 표/비교 + 적용 1줄`로 압축함
- 2~4교시는 4문제를 각 3쪽 내외로 쓰므로 `개요 -> 특징/비교 -> 구조/원리 -> 실무 사례 -> 결론` 흐름을 끝까지 밀어붙임
- 키워드 노트는 작성 지침이나 체크리스트처럼 쓰지 말고, 해당 키워드에 대한 실제 기술사 모범 답안 본문처럼 작성함
- "답안에서는 ~해야 함", "기술사 관점에서는 ~" 같은 메타 표현은 최소화하고, 개념·구조·비교·실무 판단·결론을 직접 서술함
- 핵심 판단 요소와 비교축 선정은 7절의 단일 게이트를 적용함
- **문장 밀도**: `무엇을`, `무엇 기준으로`, `왜 판단하는지`가 보이도록 쓰되 본문 불릿은 보통 35자 안팎, 최대 50자로 제한함. 수식어·중복 목적어·당위어부터 삭제함
- **답안지 문체**: `~할 수 있음`, `~하는 것이 중요함`, `~측면에서 필요함`보다 `~함`, `~필요`, `~적합`처럼 짧게 끝냄
- **한 문장 한 역할**: 정의는 정의만, 배경은 필요성만, 특징은 성질만, 유의점은 적용·주의·검증만 담음

## 1-0. 실전 답안지 문장 규칙

공개 답안 작성 조언과 답안지 양식은 공통적으로 가독성, 충분한 분량, 그림·표·간글, 문제 요구사항 회수를 강조한다. 디지털 노트도 이를 따르되, 장황한 설명으로 분량을 채우지 않는다.

- **문제 회수**: 문제의 핵심어, 비교 대상, 제약조건을 정의·표·결론에 반복 반영함
- **정의 밀도**: 정의는 1문장으로 쓰며 `대상 + 기준 + 목적`만 남김
- **짧은 간글**: 도식과 표 아래에는 1문장 요약을 붙이되, 새 설명을 늘리지 않음
- **표 중심 압축**: 긴 비교 문장은 표로 보내고, 표의 좌측 축을 `대상`, `기준`, `병목`, `검증`처럼 구체화함
- **문장 삭제 우선**: 문장이 길면 다듬기보다 먼저 삭제 가능한 단어를 찾음. 판단 기준과 필요한 이유는 남기되, 반복해서 읽었을 때 더 직관적인 답안 문장이 되어야 함
- **답안지 가독성**: 한 줄에 핵심어가 보여야 하므로, 주어와 판단어를 앞쪽에 배치함
- **키워드 욱여넣기 금지**: 전문용어·처리 방식·검증 지표를 한 문장에 억지로 연결하지 않음. 조치와 검증이 각각 독립된 판단이면 두 문장으로 나누고, 문장마다 하나의 주어와 핵심 서술어를 유지함

장문 치환 예:

| 장황한 문장 | 답안 문장 |
|:---|:---|
| 입력 데이터 크기 $n$이 증가함에 따라 연산 횟수와 메모리 점유량이 변하는 추이를 수학적 함수로 표현해 알고리즘의 효율성을 판단하는 척도임 | 입력 크기별 시간·메모리 증가율임 |
| 동일한 기능을 수행하더라도 입력 규모가 커지면 지연 시간과 메모리 사용량이 급증할 수 있으므로 확장 한계를 예측할 기준이 필요함 | 입력 규모에 따른 연산량·메모리 사용량 증가율 분석이 필요함 |
| 특정 하드웨어의 성능이나 프로그래밍 언어의 처리 속도에 의존하지 않고 알고리즘 구조 자체의 효율성을 객관적으로 비교할 수 있음 | HW·언어와 분리해 알고리즘 구조를 비교함 |
| 시간과 공간 사이의 상충 관계를 분석하여 시스템의 가용 자원 조건에 맞는 알고리즘 선택 기준을 제공함 | 시간·공간 트레이드오프 선택 기준을 제공함 |
| 문자열 유사도 서비스는 상향식 DP에서 두 행만 저장하고 전체 테이블과의 거리값 일치·최대 메모리를 확인함 | 문자열 유사도 서비스는 공간 최적화를 위해 이전 행과 현재 행만 유지함. 전체 DP 테이블과 거리값을 대조하고 최대 메모리 사용량을 확인함 |
| 몬테카를로 방법은 난수 표본을 반복 생성하고 결과 통계량으로 해를 근사하는 수치 계산 기법임 | 몬테카를로 방법은 난수 표본을 반복 생성하고 통계 결과로 근삿값을 구하는 수치 계산 기법임 |

> 요약: 실전 답안 문장은 짧아야 하며, 짧아도 기준과 판단이 보여야 함.

## 1-1. 순차 반복 검수 강제

초안 작성 후 아래 6단계를 순서대로 수행한다. 검색 결과나 수정한 주변 문장만 보는 표본 검사는 전수 검수로 인정하지 않는다.

**교정 제외:** frontmatter의 `extra.review_status`가 `"사용자 확정"`인 파일은 파일 전체를 건너뛴다. 오류가 의심되어도 사용자가 잠금 해제나 재수정을 명시하기 전에는 열람에 따른 교정, 표현 통일, 날짜 변경을 하지 않는다.

1. **범위·역할 검사**: 제목부터 결론까지 빈 줄을 제외한 모든 줄을 순서대로 읽는다. frontmatter, `미리 알고가기`, `작성 근거`, 본문, 각 절의 `쉽게 이해하기(학습용)`, 표의 모든 셀, 도식 레이블, 수식, 요약도 포함한다. 각 문장·셀은 정의·특징·비교·구조·절차·사례·결론 중 하나의 역할과 주제에 대한 채점 기여를 가져야 한다.
2. **토큰 검사**: 각 문장을 명사, 동사, 수식어, 조사, 수량어, 영문명·약어, 수식 기호로 나눠 다음을 확인한다.
   - **실재성·정확성**: 기술 용어·번역어·약어·수식이 실제 표준·원 논문·공식 문서·전공 교재의 의미와 일치하는가. 확인하지 못한 임시 용어는 삭제하거나 일반 설명으로 바꾼다.
   - **소유권·결합**: 각 토큰이 설명 대상의 실제 역할인가. 수식어와 피수식어, 목적어와 동사, `A·B` 각각과 공통 서술어가 모두 성립하는가. 목적 함수에 선택 함수의 역할을 쓰는 식의 책임 전가는 실패다.
   - **범위·강도**: `전체`, `항상`, `최적`, `보장`, `동시`, `독립`, `최대`에 필요한 조건과 반례가 확인되는가. 판단을 바꾸지 않는 한정어는 삭제한다.
   - **필요성**: 토큰을 가려도 기술적 의미와 판단이 같으면 장식어·중복어로 판정해 삭제한다.
   - **돌발 명사 삽입**: `함수값의 평균으로 기댓값을 근사함`처럼 미리 알고가기나 앞 문장에서 도입하지 않은 전문 명사가 문장 중간에 갑자기 끼어들면, 기술적으로 틀리지 않아도 독해 흐름을 끊는 실패로 판정한다. 그 개념이 핵심 판단에 꼭 필요하면 미리 알고가기에 먼저 정의하고, 없어도 의미가 같으면 삭제해 상위 표현만 남긴다(예: `함수값의 평균으로 기댓값을 근사함` → `평균으로 기댓값을 근사함`).
   - **동사 압축**: `~는지 확인한다`, `~여부를 판정한다`, `~인지 검증한다`처럼 술어가 두 단어 이상이면 의미가 같은 한 단어 동사(`검출`, `판정`, `검증`, `식별`, `파악`, `탐지`)로 줄일 수 있는지 검토함. 통계·논리 술어(`판정`, `검증`)와 자료 처리 술어(`검출`, `식별`)의 의미 차이가 유지되는 경우에만 치환하고, 의미가 흐려지면 원문을 유지함.
   - **복합명사 어순**: `결과 통계량`처럼 두 명사를 그대로 붙인 복합명사가 어순을 바꾸면(`통계 결과`) 더 짧고 자연스러워지는지 검토함. 개요·정의처럼 전달력이 우선인 문장은 자연스러운 어순으로 바꾸되, 특징·구성요소처럼 정밀한 통계·기술 용어(`통계량`)가 판단 근거로 쓰이는 절에서는 정밀 표현을 그대로 유지함.
3. **문장·표 재결합 검사**: 토큰을 다시 합쳐 주어·조건·판단 기준·목적어·서술어가 자연스러운 한 의미로 닫히는지 확인한다. 표는 `[좌측 요소]는/은 [우측 설명]이다`로 가로로 읽고, 앞뒤 문장은 같은 판단을 표현만 바꿔 반복하지 않는지 확인한다.
4. **절 간 논리 검사**: 개요의 핵심 명제와 특징·비교축·구조·절차·사례·결론이 같은 판단 방향으로 이어지는지 대조한다. `작성 근거`의 핵심어·축·배치 이유는 본문에서 실제 문구와 역할로 확인되어야 하며, 뒤 절에 새 기준이나 새 결론을 갑자기 추가하지 않는다. `작성 근거`의 `방향성` 문장이 Ⅱ 특징의 근거로 뒷받침되고 Ⅶ 결론에서 판단으로 실제로 회수되는지 확인하며, 방향성 없이 사실만 나열된 노트는 위키형 실패로 판정한다.
5. **답안 적합성 검사**: 표 헤더·도식·결론만 읽어도 핵심이 보이는지, 처음 읽는 사람이 선행 용어를 이해하는지, 문장이 자연스럽고 손으로 쓸 수 있는 분량인지 확인한다. 50자를 넘는 문장은 불필요한 말부터 삭제하고, 서로 다른 판단이면 분리한다. 단순 상식·추상 구호·채점에 기여하지 않는 주변 지식은 삭제한다.
6. **무수정 반복 통과**: 한 파일을 처음부터 끝까지 최소 5회 완독한다. 한 토큰이라도 수정하면 해당 문장을 처음부터 다시 검사하고, 파일 검수도 1단계·1회차부터 다시 시작한다. 수정 없는 전체 완독 5회를 통과해야 완료로 선언한다.

> 요약: 모든 줄을 역할→토큰→문장·표→절 간 논리→답안 적합성 순으로 검사하고, 수정 없는 전체 완독 5회를 통과해야 완료함.

상세한 수정 전·후 문장은 [CSPE 답안 작성 예시집](@/exam/cs/writing-examples.md)의 문장 정밀화 예시를 참조함.

## 1-2. 내용 선별과 균형, 근거 병기

문장을 다듬기 전에 `0-1. 대표 핵심 선정 게이트`로 존재 이유부터 판단한다. 잘 쓴 문장도 핵심이 아니면 삭제하며, 비교 대상의 공유 값은 차이가 갈리는 이유로 바꾸고 뜻·판단 없는 값 나열은 제거한다.

### 개념 균형과 주제 이탈 경계

- 한 개념을 꺼내면 반대 개념이 따라붙는지 점검함. 예: `희소 그래프`를 쓰면 `밀집 그래프`는 왜 안 쓰는지 자문함
- 다만 반대 개념을 넣는 순간 주제에서 벗어날 수 있으므로, `이 대비가 이 키워드의 판단에 필요한가`를 먼저 물음
- 필요하면 한 줄 대비로 균형을 맞추고, 불필요하면 언급 자체를 지워 초점을 지킴
- **핵심 일관성 게이트**: 개요에서 이 문서가 끝까지 밀고 갈 핵심 명제와 판단축을 한 문장으로 고정함. 이후 모든 특징·비교 행·구성요소·절차 단계·사례·결론은 그 명제를 설명하거나 검증해야 함
- **위키형 실패 판정**: 핵심 명제는 정의를 다시 말한 요약이 아니라 `이 키워드가 결국 어떤 선택·트레이드오프로 귀결되는가`에 답하는 문장이어야 함. `표준오차는 표본 수 제곱근에 반비례함`은 사실이지 명제가 아니고, `그래서 적당히 정확한 근사는 싸지만 극도로 정밀한 값은 비용이 기하급수적으로 늘어나므로 표본 수와 비용의 타협점을 먼저 정해야 함`처럼 판단·선택으로 이어져야 명제로 인정함. 각 절이 사실만 나열하고 결론이 이 명제로 수렴하지 않으면 백과사전형(위키형) 실패로 판정하고 개요의 핵심 명제부터 다시 정한 뒤 결론까지 함께 고침
- 관련 개념이라는 이유만으로 새 기술·반대 개념·파생 이론을 추가하지 않음. 현재 핵심의 원인, 동작, 선택, 실패, 검증 중 어느 역할인지 답하지 못하면 생판 다른 내용으로 판정해 삭제함
- 앞 절에서 정의하지 않은 개념이 중간 절에 처음 등장하면 `핵심을 설명하는 데 반드시 필요한가`, `미리 알고가기나 개요에서 전제했는가`, `뒤 절에서 회수되는가`를 확인함. 하나라도 충족하지 못하면 새 개념을 들고 오지 않음
- 절마다 핵심 대상을 바꾸지 않음. 예를 들어 개요는 알고리즘 선택을 말하면서 특징은 구현 역사, 비교는 무관한 성능 수식, 절차는 일반 운영 흐름, 결론은 보안 통제로 끝내면 핵심 불일치로 판정함
- 핵심을 넓혀야 할 때는 기존 문장 사이에 끼워 넣지 말고 개요의 핵심 명제부터 다시 정한 뒤 모든 절을 함께 수정함

개념 균형 판단 과정은 [CSPE 답안 작성 예시집](@/exam/cs/writing-examples.md)의 내용 선별 예시를 참조함.

> 요약: 개념을 하나 꺼내면 반대 개념의 포함 여부를 매번 판단하되, 균형과 초점 중 답안에 유리한 쪽을 택함.

### 키워드·방향·전개 설계

최적의 답안은 최적의 키워드·방향·논리 흐름·전개에서 나온다. 쓰기 전에 아래를 먼저 고민한다.

- **핵심 키워드 선정**: 이 주제의 판단을 가르는 키워드를 고르고, `왜 다른 후보가 아니라 이 키워드가 핵심인가`를 판단함
- **방향**: 개요에서 잡을 핵심 축을 정하고, 모든 절이 그 축 하나를 향하게 함
- **논리 흐름**: 개요 -> 특징 -> 비교 -> 구조 -> 절차 -> 유의점 -> 결론이 앞 절의 판단을 뒤 절이 이어받도록 배치함
- **전개**: 각 문단이 새 판단을 전진시키는지, 앞 문단의 재진술이 아닌지 확인함
- 이 고민이 있어야 불필요한 요소가 사라지고 필요한 요소가 자리를 잡음

> 요약: 키워드·방향·흐름·전개를 먼저 설계하고, 그 설계 자체를 근거로 남김.

### 쉽게 이해하기 (학습용, 필수)

`Ⅰ. 개요`부터 `Ⅶ. 결론`까지 각 로마숫자 절은 본문(정의·표·절차·사례 등)이 끝나는 지점에 `### 쉽게 이해하기 (학습용)` 소절을 **반드시** 포함한다. 해당 절이 `> 요약:` 블록으로 끝나면 그 블록 바로 다음에 둔다. 전공 용어를 모르는 사람도 **그 절**의 핵심을 짐작할 수 있도록 일상 비유나 쉬운 설명을 최대 3줄로 쓴다.

- **절별 개별 작성**: 키워드 전체가 아니라 그 로마숫자 절이 다루는 내용(정의, 특징, 비교, 구조, 절차, 사례, 결론)만 비유로 풀어씀. 다른 절 내용을 끌어오지 않음
- **학습용 표시**: 제목에 `(학습용)`을 반드시 병기해 답안에 쓰는 문장이 아님을 명시함. 답안 작성 시에는 이 소절을 옮겨 쓰지 않음
- 전문용어 대신 일상 비유·상황으로 그 절의 핵심 동작이나 판단을 감 잡게 함
- 기술적으로 틀린 단순화는 금지하며, 정확성을 해치지 않는 선에서만 쉽게 풀어씀
- 해당 절의 문장을 그대로 반복하지 않고, 다른 표현으로 풀어씀
- 최대 3줄(불릿 또는 짧은 문장)로 제한하며, 넘치면 삭제하고 다시 압축함

> 요약: 쉽게 이해하기(학습용)는 Ⅰ~Ⅶ 각 절 끝마다 두는 3줄 이내 비유이며, 그 절만 다루고 답안에는 옮기지 않음.

### 근거·사유 병기 (필수)

모든 노트는 `미리 알고가기` 바로 다음, `Ⅰ. 개요` 앞에 `## 작성 근거(검토용)` 블록을 **반드시** 포함한다. 이 블록이 없거나 결론 뒤에 있으면 작성 미완료다. 답안을 읽기 전에 핵심 키워드·판단축·전개 근거를 먼저 확인해야 이후 본문의 방향을 잡을 수 있기 때문이다.

- **방향성(필수, 최상단 배치)**: 이 키워드가 결국 어떤 판단·트레이드오프로 귀결되는지 한 문장으로 먼저 명시함. `1-2. 개념 균형과 주제 이탈 경계`의 위키형 실패 판정을 통과해야 하며, 정의를 되풀이하거나 사실만 나열하면 방향성으로 인정하지 않음. 이 문장은 Ⅱ 특징에서 그 원인이 되는 근거로 뒷받침되고 Ⅶ 결론에서 다시 판단으로 회수되어야 함
- 각 절을 왜 이렇게 구성했는지, 핵심 문장을 왜 넣었는지, 주요 단어·어휘를 왜 골랐는지를 근거로 적음
- **키워드 근거**: 핵심 키워드가 왜 이것인지, 왜 다른 후보가 아닌지를 설명함
- **배치·전개 근거**: 문단·문장을 왜 이 순서로 배치하고 이 흐름으로 전개했는지, 앞 절과 뒤 절이 어떻게 이어지는지를 설명함
- 근거는 `기술이 그래서`가 아니라 `이 키워드의 판단·비교·선택에 왜 필요한지`로 씀
- 근거를 댈 수 없는 문장·단어는 존재 이유가 없으므로 삭제함
- 근거가 `일반적으로 중요하므로`, `기본이므로`처럼 뭉뚱그려지면 그 요소도 아무말이므로 다시 판단함
- **근거-본문 일치 의무**: 근거에서 핵심 키워드·판단축으로 지목한 단어는 본문(Ⅰ~Ⅶ) 어딘가에 실제로 등장해야 함. 근거만 그럴듯하고 본문에 그 축이 없으면 근거를 지어낸 것이므로, 본문을 고치거나 근거를 실제 본문에 맞게 다시 씀
- 이 블록은 검토자가 타당성을 확정하기 전에는 제거하지 않음

> 요약: 근거 블록은 선택이 아니라 필수 산출물이며, 각 문장·단어는 근거로 방어하지 못하면 지움.

### 2-1. 기존 노트 전수 다듬기 절차

기존 노트를 다시 다듬을 때는 개요만 수정하지 않고 파일의 첫 줄부터 마지막 줄까지 아래 순서로 확인한다. 일부 절만 확인한 파일은 완료로 표시하지 않는다.

1. **정본 확인**: `_keywords.md`와 제목·영문명·번호·가중치·기출 메타데이터를 대조함
2. **교정 제외 확인**: `extra.review_status: "사용자 확정"` 파일을 먼저 제외하고 기존 사용자 변경을 구분함
3. **선행 블록 확인**: 4절에 따라 `미리 알고가기`를 보강하고 `작성 근거`를 그 다음에 배치함
4. **절별 교정**: 5~11절을 순서대로 적용함. 비교는 7절, 구성요소는 8절의 전용 게이트를 생략하지 않음
5. **전수 검수**: 1-1의 역할·토큰·문장·절 간 논리·답안 적합성 검사를 수행하고 수정 없는 전체 완독 5회를 통과함
6. **일관성 확인**: 같은 개념의 한국어·영문명·약어·기호가 표·도식·절차·결론에서 흔들리지 않는지 대조함
7. **배치 검증**: 10개 파일마다 구조 검사와 `git diff --check`, `zola build`를 통과한 뒤 해당 파일만 커밋·푸시함

#### 교정 작업의 공통 실행 원칙

사용자가 별도 세션 정보 없이 `작성법에 따라 교정`을 요청해도 아래 원칙을 기본 계약으로 적용한다. 작업 진행 번호나 이전 대화에 의존하지 않고 저장소의 현재 파일과 `_keywords.md`를 근거로 범위와 정본을 판단한다.

- **정본 선확인**: 과목별 `_keywords.md`의 번호·한글 제목·영문명을 실제 파일의 `title`, `weight`, `extra.question_no`와 대조한 뒤 해당 키워드와 일치하는 파일만 교정함
- **중복 번호 보호**: 같은 번호의 과거 파일은 사용자 승인 없이 삭제·병합·이름 변경·내용 이전하지 않으며, 번호가 같다는 이유만으로 정본으로 선택하지 않음
- **현재 상태 우선**: 기억·이전 대화·진행표보다 현재 작업 트리와 실제 파일 내용을 우선하고, 기존 수정과 미추적 파일을 확인한 뒤 사용자 변경을 보존함
- **검수 적용**: 맞춤법 교정에 그치지 않고 1-1을 적용하되, 이미 정확하고 자연스러운 내용은 동의어 치환이나 취향 변경 없이 0건으로 통과시킴
- **직접 작성 원칙**: 키워드 노트는 파일별 핵심 논리를 직접 작성·교정하며, 스크립트나 공통 문구 치환으로 여러 문서를 일괄 생성하지 않음. 스크립트는 번호·메타데이터·절·금지 표현·빌드 상태를 검사하는 용도로만 사용함
- **완료 근거**: 모든 대상 파일을 1-1의 순서로 반복 완독하고 구조 검사·`git diff --check`·사이트 빌드를 통과한 경우에만 교정 완료로 판정함

> 요약: 교정은 `_keywords.md`와 현재 파일에서 정본을 확정한 뒤 사용자 변경과 중복 파일을 보존하며, 문장별 기술·논리·자연스러움을 직접 검증하는 작업임.

## 3. 수식 및 기호 표기 (LaTeX)

- **수식 필요성 선별**: 수식이 정의·산출 방식·복잡도·임계값 판단을 직접 설명할 때만 사용하며, 개념과 인과관계를 문장으로 충분히 설명할 수 있으면 수식을 넣지 않음
- **특징·비교·결론의 개념 설명 우선**: 수식보다 동작 원리, 오차 변화, 선택 조건이 먼저 읽혀야 하며, 수식을 제거해도 판단이 유지되면 문장으로 바꿈
- 수식 사용이 필요한 경우 모든 수학적 수식, 알고리즘 복잡도, 기호, 통계량은 **LaTeX($...$)** 형식으로 표기함
- **수식을 사용할 때 LaTeX 필수 적용 대상**:
  - **복잡도**: $O(n \log n)$, $O(V+E)$, $\Omega(n)$
  - **수식**: $y = \gamma \cdot \hat{x} + \beta$, $P(A|B) = \frac{P(B|A)P(A)}{P(B)}$
  - **기호**: $\alpha$, $\beta$, $\mu$, $\sigma^2$, $\Delta$
  - **비교축**: 성능/지연 시간(Latency), 처리량(Throughput)처럼 영문 전문용어는 일반 텍스트로 병기함
- 단순 텍스트(`n log n`)나 코드 블록 내의 평문 표기를 지양하고, 본문과 표 안의 모든 수식은 LaTeX로 감싸 시각적 가독성을 확보함
- 영문 용어 자체는 수식이 아니므로 LaTeX로 감싸지 않음. 특히 `Top-down`, `Hold-out`, `Mini-batch`의 하이픈이 수학식의 뺄셈 기호로 렌더링되지 않도록 일반 텍스트로 작성함
- 수식은 문장 성분으로 억지로 붙이지 않음. `두 방식 모두 $O(V+E)$이지만`보다 `두 방식의 시간복잡도는 모두 $O(V+E)$임. 다만 ...`처럼 한글 문장으로 풀어씀

## 4. 미리 알고가기

`미리 알고가기`는 시험 답안에 쓰지 않는 노트용 선행 이해 블록이다. 본문 표·도식·활용·유의점에서 처음 등장하는 용어, 기호, 전제조건 때문에 본문 이해가 끊길 때 둔다.

- **위치**: frontmatter 바로 아래, `개요` 위
- **분량**: 기본 4~8개 불릿이며, 복합 키워드나 알고리즘 비교형은 최대 10개까지 허용함
- **내용**: 용어 뜻, 약어, 수식 기호, 전제조건, 표·비교축·주요 활용의 선행 용어
- **역추적 보강**: 본문을 쓴 뒤 Ⅱ~Ⅵ의 표·도식·활용·유의점을 훑어 처음 등장하는 전문용어를 `미리 알고가기`에 추가함
- **필수 선공개**: `무가중치 최단 경로`, `위상 정렬`, `DAG`, `안정 정렬`, `선택적 공개`처럼 독자가 멈출 수 있는 용어는 본문보다 먼저 1문장으로 풀어씀
- **기호 선공개**: $O(V+E)$처럼 변수 포함 복잡도를 쓰면 `V는 노드 수`, `E는 간선 수`처럼 기호 뜻을 `미리 알고가기`에 먼저 남김
- **문장 규칙**: 각 불릿은 `용어: 의미·판단 기준·본문 연결점`을 한 문장으로 쓰고, 두 문장으로 쪼개지 않음
- **쉬운 설명 우선**: `한글 용어(영문): 쉬운 한 문장 설명` 형식으로 쓰며, 해당 용어를 모르는 사람도 문장만 읽고 뜻을 이해할 수 있어야 함. 전문용어를 다른 전문용어로 바꾸거나 정의 대상과 같은 말을 반복해 풀이하지 않음
- **모호한 참조 금지**: `같은 방법`, `이 방식`, `이를`, `적절한`, `효율적인`처럼 대상·기준을 다시 찾아야 하는 표현을 쓰지 않음. 실제 동작, 참조 대상, 판단 기준을 해당 문장 안에 직접 밝힘
- **금지**: 역사, 발명자, 논문명, 본문 핵심 논증, 실무 사례 선공개
- **금지 예시**: BFS·DFS처럼 절차가 핵심인 문맥에서 `선택 기준은 속도가 아니라 보장 결과임`처럼 엉뚱한 추상 명사로 끝내지 않음. 문맥이 요구하는 단어가 `절차`면 반드시 `절차`라고 씀

```markdown
## 미리 알고가기

- 용어 A: [본문 표·활용에서 처음 나오는 용어를 1문장으로 설명]
- 표기 B: [수식·기호의 의미와 판단 기준을 1문장으로 설명]
- 전제조건: [이 키워드의 동작 조건 또는 적용 범위를 1문장으로 설명]
```

좋은 예: `최적 부분 구조(Optimal Substructure): 큰 문제의 최적해를 작은 문제들의 최적해로 구성할 수 있는 성질임`

## 5. Ⅰ. 개요

개요는 답안의 첫 판단 문장이다. 정의/개념과 배경/필요성을 포함하되, 표·불릿·짧은 문단 중 키워드에 맞는 형식을 자유롭게 선택한다.

- **정의/개념**: 핵심 개념은 `무엇을`, `무엇 기준으로`, `무엇을 판단·통제하는지`가 보이게 1문장으로 정의함
- **배경/필요성**: 해결할 목적을 `~을 위해`로 먼저 제시하고, 필요한 개념·기준·구조를 `~필요함`으로 끝내는 1문장으로 작성함
- **금지**: 역사, 발명자, 논문명, 수상 이력, 출제 의도표를 위한 출제 의도표

```markdown
- **정의/개념**: [개념의 대상·판단 기준·통제 대상]
- **배경/필요성**: [해결 목적]을 위해 [필요한 개념·기준·구조]가 필요함
```

- 정의에 피정의어를 반복하는 순환 정의 금지
- 정의를 명사구처럼 과도하게 줄이지 않음. 학습자가 처음 읽어도 개념의 대상·측정 기준·통제 대상이 잡혀야 함
- 복합 키워드나 묶음형 제목은 하위 예시를 바로 나열하지 말고, 먼저 상위 개념 자체가 무엇인지 정의한 뒤 대표 유형이나 예시를 이어서 설명함
- 정의/개념과 배경/필요성 안에서 마침표로 두 문장을 나누지 않고 원인과 필요성은 `~하므로`, `~때문에`, `~위해`로 연결해 한 문장으로 압축함
- 대표 용도, 적용 예시, 상세 동작, 장단점은 정의에 붙이지 않고 뒤 절로 보냄
- **정의와 배경의 역할 분리**: 정의는 기법이 성립하는 문제 조건과 무엇을 하는 기법인지를 담고, 배경은 그 기법이 없을 때의 실패·비용을 담음. 배경이 문제 상황을, 정의가 해법을 맡아야 두 문장이 문제 -> 해법으로 이어지고 중복이 사라짐
- 정의를 저장·재사용, 캐싱 같은 구현 메커니즘 서술로만 채우지 않음. 처리 방식의 세부는 특징·구성요소 절에서 설명함
- 배경/필요성은 해법의 동작을 미리 서술하지 않음. 정의와 배경이 같은 서술어로 끝나면 한쪽이 다른 쪽을 반복하고 있다는 신호이므로 역할을 다시 가름
- 배경에 연도·인명·논문·수상 이력 나열 금지
- 배경/필요성은 해결 목적(`~을 위해`) 또는 대안의 실패 원인(`~하므로`)을 앞에 두고 `~필요함`으로 닫음. 예: `라우팅 비용 절감을 위해 거리·비용·시간 지연이 가장 작은 경로가 필요함`
- `그래프 탐색은 정점을 방문하는 알고리즘이므로 필요함`처럼 정의를 반복하는 배경, `라우팅·물류·경로 계획은 연결 여부보다 총 비용이 작아야 하므로 가중치 기반 경로 선택 기준이 필요함`처럼 적용 분야 나열과 긴 명사구를 붙인 배경은 실패임

좋은 정의 기준:

| 나쁜 과압축 | 좋은 정의 |
|:---|:---|
| 입력 증가에 따른 실행시간·메모리 증가율 분석임 | 알고리즘이 입력 크기 `n` 증가에 따라 기본 연산을 얼마나 더 수행하고 추가 메모리를 얼마나 더 쓰는지 함수로 표현해 확장성을 판단하는 분석 기준임 |
| 데이터를 기준 순서로 재배열하는 알고리즘 군임 | 정렬은 원소를 키 기준 순서로 재배열해 탐색·병합·집계 같은 후속 연산을 가능하게 하는 알고리즘 군임 |
| 동적 계획법은 동일한 부분 문제의 답을 한 번만 계산·저장한 뒤 재사용하는 기법임 | 동적 계획법은 중복 부분 문제를 상태로 정의하고 최적 부분 구조에 따라 점화식을 세워 상태값을 저장·재사용하는 기법임 |

> 요약: 정의는 짧은 표어가 아니라 채점자와 학습자가 같은 개념을 떠올리게 하는 첫 판단 문장임.

## 6. Ⅱ. 특징

특징은 비교 없이 본 키워드 자체의 고유한 구조적·성능적·운영적 차별점을 서술하는 절이다.

- **특징 1**: 이 기술의 핵심 동작 원리에서 비롯되는 구조적 차이
- **특징 2**: 성능·품질·보안·운영 관점의 채점 포인트
- **특징 3**: 적용 조건·선택 기준·트레이드오프
- 3~4개 불릿으로 구성하며, 비교는 다음 절(Ⅲ)에서 수행함
- 특징은 뒤의 구성요소·구조·절차에서 확인 가능한 구조·동작 근거를 가져야 함
- 특징을 3개 이상 쓸 때는 0-1의 대표 핵심 선정 게이트를 적용해 각 특징이 핵심인지, 특히 네 번째부터는 지엽·중복이 아닌지 확인함

## 7. Ⅲ. 종류 및 비교

종류 및 비교는 복합 키워드의 개별 설명과 비교표, 또는 단일 키워드의 대안 기술 비교를 수행하는 절이다.

- **복합 키워드**: 개별 키워드의 핵심 설명을 별도 문단으로 서술한 뒤 비교표로 정리함
- **단일 키워드**: 관련 대안·기존 기술과의 비교표 또는 유형 분류표를 둠
- 비교 대상이 2개 이상이고 핵심 비교축 3개가 모두 실질적일 때만 표를 씀
- 비교표의 판단 기준은 정확히 3개로 제한함. 세 축으로 선택 차이를 설명할 수 없으면 비슷한 행을 늘리지 말고 더 핵심적인 축으로 교체함
비교표는 아래 5단계 게이트를 통과해야 한다.

1. **대상 동등성**: 각 열이 같은 추상 수준의 독립된 기술·유형·상태인가. 상위 개념과 하위 기능, 기술과 사례를 같은 열에 놓지 않음
2. **축 핵심성**: 각 축이 고유 원리·적용 조건·선택·실패 판단 중 하나를 직접 설명하고 실제 선택 차이를 만드는가. 뒤 절에서 회수되지 않는 부수 기준은 교체함
3. **축 독립성**: `선택 방식`과 `탐색 범위`처럼 같은 동작을 다른 이름으로 반복하지 않는가. 겹치면 합치고 빠진 핵심 판단을 넣음
4. **행·셀 대응**: 행 제목을 질문으로 읽었을 때 모든 셀이 같은 문법·분석 수준에서 한 가지 판단으로 답하는가. 원리와 장점, 수치와 평가어를 대칭처럼 배치하지 않음
5. **삭제 검사**: 행을 가려도 선택·원리 이해가 같거나 표를 문장으로 바꿔도 정보 손실이 없으면 행 또는 표를 삭제함. 세 축을 채우려고 유사 기준을 만들지 않음
- 핵심 비교축은 `동작 메커니즘`, `계산·처리 범위`, `실무 부작용·리스크`를 기본으로 하며 주제 선택에 더 직접적인 축이 있을 때만 한 축을 교체함
- **적용 기준 필수화**: 비교 대상이 `언제 A를 쓰고 언제 B를 쓰는가`를 가르는 관계라면(Ⅲ절 비교표 대부분이 이에 해당) 세 축 중 하나는 반드시 `적용 기준`이어야 함. 그 값은 표 아래 요약 문장에만 남기지 않고 저차원/고차원, 데이터 규모, 갱신 빈도, 음수 가중치 유무처럼 구체적인 분기 조건으로 셀에 직접 씀. 원리·리스크 두 축만 채우고 적용 기준을 요약 문장에만 미루면 표가 선택 판단에 기여하지 못하는 결함으로 판정함
- 시간복잡도는 알고리즘의 성능 차이가 실제 선택을 가를 때만 비교축으로 사용함. 두 대상의 값이 같거나 구조·적용 사례가 주제의 핵심이면 시간복잡도를 관성적으로 넣지 않고 입력 형태, 선택 절차, 적용 사례, 실패 조건으로 교체함
- 셀은 명사구나 한 줄 핵심 구절 하나로 쓰고, 본문·절차의 수식과 설명을 반복하지 않는다.
- 축명은 `주요 활용`, `얻는 결과`, `적합 조건`처럼 질문이 분명한 말로 쓴다. `대표 적용 사례`와 `적합 조건`처럼 역할이 다른 기준을 섞지 않는다.
- 전문용어는 `미리 알고가기`에서 먼저 설명하고 문서 전체에서 같은 이름으로 유지한다. 어휘·문장 압축은 1-1과 13~14절을 적용한다.

| 판단 기준 | [대상 A] | [대상 B] |
|:---|:---|:---|
| [비교축 1] | [A의 성질] | [B의 성질] |
| [비교축 2] | [A의 특성] | [B의 특성] |
| [비교축 3] | [A의 리스크] | [B의 리스크] |

비교표와 최단 경로 문장 교정 사례는 [CSPE 답안 작성 예시집](@/exam/cs/writing-examples.md)의 비교표·요약문 예시를 참조함.

## 8. Ⅳ. 설계 요소 및 구조

설계 요소는 **무엇이 존재하고 각 요소가 무슨 책임을 맡는지** 설명하는 정적 구조다. 실행 순서·반복·분기·종료는 Ⅴ절의 책임이므로 Ⅳ절에서 절차처럼 나열하지 않는다. 순서가 없는 관계만 표·구조도로 표현한다.

구성표는 대표 요소 3~5개만 남기고, 각 행을 아래 순서로 판정한다. 하나라도 실패하면 요소명·설명을 고치거나 행을 삭제한다.

1. **실재성**: 실제 전산학·표준·원 논문에서 인정되는 구성요소·설계 변수·판정 함수인가. 설명용 임시 명칭, 구현 예, 효과를 요소처럼 만들지 않음
2. **필요성·채점 기여**: 삭제하면 주제의 성립·동작·선택·실패 원리 중 무엇이 빠지는가. 답하지 못하는 주변 개념과 개수 채우기 항목은 삭제함
3. **역할 대응**: `[요소명]은/는 [설명]이다`로 읽었을 때 설명이 그 요소의 표준 책임을 직접 말하는가. 목적 함수에 선택 함수의 역할을 쓰는 등 다른 요소의 책임을 침범하지 않음
4. **중복·추상 수준**: 다른 행의 책임을 표현만 바꿔 반복하지 않고, 시스템 요소·세부 파라미터·운영 지표·사례를 같은 수준에 섞지 않았는가
5. **연결성**: 각 요소의 입력·출력·상태·제어·의존 관계가 표·도식·요약에서 일관되게 이어지는가. 관계는 요약에서 처음 만들지 말고 표 셀이나 도식에 먼저 드러냄
6. **절차 중복 검사**: Ⅳ절의 행·도식이 Ⅴ절의 단계와 같은 동사·순서로 대응하면 정적 구조와 동적 절차가 중복된 것임. Ⅳ에는 요소명·책임·정적 관계만 남기고 실행 순서는 Ⅴ로 옮김

요소는 입력·핵심 처리·상태/저장·통제/검증·산출 중 해당 주제에 필요한 책임 순으로 배치한다. 모든 항목을 억지로 채우지 않으며, 설명은 시험장에서 옮겨 쓸 수 있는 명사구나 한 줄 완결문으로 쓴다.

```text
입력·요구 → 핵심 구성 → 산출물
               ↓
            통제·검증
```

| 설계 요소 | 설명 |
|:---|:---|
| 구성 A | 입력을 핵심 처리 단위로 변환하는 요소 |
| 구성 B | 처리 결과를 다음 요소에 전달하는 연결 구조 |
| 구성 C | 결과를 저장·검증하는 통제 요소 |

> 요약: 설계 요소가 요구사항을 어떤 구조로 해결하는지 1문장으로 정리함.

- 표는 `설계 요소 | 설명` 두 열을 기본으로 하고, 설명에는 사전식 정의가 아니라 해당 구조의 책임·정적 관계를 쓴다. 표만으로 관계가 충분하면 도식을 추가하지 않으며, 도식은 계층·소유·연결처럼 시간 순서가 아닌 관계를 보여줄 때만 사용한다.
- 시간 순서가 핵심이면 9절의 흐름도 규칙을 적용하고, 구조도와 절차가 같은 내용을 반복하면 하나만 남긴다. 분기는 `├─`, `└─`, 이동은 `→`, `↓`처럼 짧게 표시한다.

## 9. Ⅴ. 원리 및 절차 흐름도

원리 및 절차는 **어떤 상태에서 무엇을 수행하고, 어떤 조건으로 다음 동작을 선택하며, 언제 반복·종료하는지** 설명하는 동적 흐름이다. 알고리즘·프로토콜처럼 순서가 핵심인 키워드에서만 독립 절로 작성하고, 순서가 핵심이 아니면 Ⅳ와 합친다.

- **Ⅴ절 존재 타당성 검사**: `순서가 바뀌면 결과가 달라지는가`, `상태·데이터·제어권이 단계마다 실제로 변하는가`, `이 흐름이 해당 주제의 핵심 원리를 설명하는가`를 모두 확인함. 어느 질문에도 답하지 못하면 독립 Ⅴ절을 만들지 않음
- **단계 필요성 검사**: 각 단계는 고유한 입력·처리·판정·산출 중 하나를 가져야 함. 한 단계를 삭제하거나 앞뒤 단계와 합쳐도 원리가 그대로면 불필요한 단계로 판정함
- **전이 근거 검사**: 화살표마다 앞 단계의 산출물이 다음 단계의 입력 또는 조건이 되어야 함. 단순 나열, 생명주기 순서, 작성자가 임의로 붙인 업무 순서는 원리 흐름으로 인정하지 않음
- **주제 고유성 검사**: 단계명을 다른 키워드에 그대로 붙일 수 있으면 일반 템플릿 문구임. `입력 식별 -> 핵심 처리 -> 검증 -> 결과 반환`을 내용 없이 복사하지 말고 실제 연산·상태·메시지·판정명을 사용함
- **Ⅳ·Ⅴ 책임 분리 검사**: Ⅳ는 `요소명·책임·정적 관계`, Ⅴ는 `동작 순서·분기 조건·상태 변화·반복·종료`만 담당함. 두 절에서 같은 내용을 동사만 바꿔 반복하면 Ⅳ의 절차 표현을 제거하고 Ⅴ에 동작을 모음
- **도식·단계 설명 분리 검사**: 도식은 전체 경로와 분기를 한눈에 보여주고, 번호 단계는 도식에 없는 선택 기준·상태 변화·예외만 보완함. 도식 문구를 문장으로 그대로 반복하지 않음
- **핵심성 우선**: 모든 문서에 Ⅴ절을 채우는 것보다 핵심 원리가 없는 흐름도를 생략하는 것이 우선임. 분류·비교·정의가 중심인 주제는 비교표와 구조 설명만으로 완결할 수 있음
- **전수 교정 방식**: 과목 단위 점검에서는 표본 문서만 보지 않고 001번부터 마지막 번호까지 모든 Ⅴ절을 순서대로 읽어 `유지·교정·Ⅳ절 통합·삭제` 중 하나로 판정함. 자연스럽다는 이유만으로 유지하지 않고 위 타당성 검사를 통과한 경우에만 그대로 둠
- **복합 주제 검사**: 여러 알고리즘·기술을 다루는 문서에서 실제 반복 기준과 상태가 다르면 하나의 공통 흐름으로 뭉개지 않음. 알고리즘별 고유 흐름을 나누거나 비교표만 남김
- **교정 완료 조건**: 도식의 단계명, 번호 단계의 설명, 요약문이 같은 원리를 가리키고 예외·종료 조건까지 모순이 없어야 해당 문서의 Ⅴ절 점검을 완료함

흐름도는 큰 상자를 가로로 길게 늘어놓지 않는다. 직선 단계는 `단계 → 단계`로 짧게 연결하고, 판정 이후는 세로 분기로 내려 반복·종료 지점을 드러낸다. 가로 단계가 3개를 넘으면 다음 줄로 꺾는다.

```text
후보 선택 → 후보 제거 → 타당성 판정
                      ├─ 가능 → 부분해 추가 ┐
                      └─ 불가 → 제외        │
                                           ↓
                                    완성 여부 판정
                      ├─ 미완성 → 후보 선택으로 복귀
                      └─ 완성 → 결과 반환
```

위 도식은 배치 방식의 예시다. 실제 답안에서는 `후보 선택`, `타당성 판정` 같은 문구를 모든 주제에 복사하지 않고 해당 기술의 실제 연산·메시지·상태·판정명으로 바꾼다.

> 요약: 입력이 어떤 처리·검증을 거쳐 결과가 되는지 1문장으로 정리함.

- 가로 폭을 채우려고 상자·선·공백을 늘리지 않으며, 장식보다 분기 조건과 되돌아가는 지점을 우선함
- 흐름도가 순서를 이미 보여주므로 단계 설명은 같은 문구를 반복하지 않고 판정 근거·상태 변화만 보완함
- 단계 수를 4개로 맞추지 않음. 핵심 전이가 3개면 3개만 쓰고, 예외·응답까지 5개가 필요하면 5개를 사용함
- 구현 세부는 필요한 만큼만 쓰고, 주변 기술 나열로 흐름을 흐리지 않음

## 10. Ⅵ. 실무 사례

실무 사례는 실제 적용 대상과 기술 고유 동작을 보여주는 절이다. `적용 대상 -> 기술 고유 조치`만으로 적용 방식이 완결되면 즉시 끝낸다. 지표·실패 조건·후속 조치는 실제 선택 판단을 추가할 때만 붙인다.

실무 사례는 개념을 설명하는 예제가 아니라 **기술사가 시스템에 적용해 설계·운영 판단을 내리는 장면**이다. 거스름돈·교과서식 작업 스케줄링·정렬 숫자 배열처럼 알고리즘 동작을 보여주는 문제 예시는 Ⅰ~Ⅴ절에 두며, 실제 시스템·업무 대상과 운영 판단이 없으면 Ⅵ절에 쓰지 않는다.

```markdown
1. [적용 대상 + 기술 고유 조치]
2. [필요할 때만 1개 더 추가]
```

> 요약: 대표 시스템에서 기술이 실제로 수행하는 동작을 1문장으로 정리함.

- "운영 어려움", "보안 취약", "성능 저하"처럼 모든 기술에 붙는 일반론 금지
- **교과서 예제 배제**: 거스름돈·배낭·구간 선택처럼 알고리즘 설명용으로 널리 쓰이는 문제를 실제 운영 대상처럼 적지 않음. 실제 시스템과 기술 고유 동작이 드러날 때만 실무 사례로 인정함
- **실무자 적용 능력 게이트**: 각 사례는 `어떤 시스템인가`, `그 기술의 어떤 동작을 적용했는가`에 반드시 답해야 함. 선택·튜닝이 핵심인 사례만 `무엇을 측정해 어떤 결정을 바꾸는가`를 추가함
- **이름만 실무인 사례 금지**: `작업 스케줄링에 적용`, `추천 시스템에 활용`처럼 업무 이름만 붙이고 기술 고유 조치와 운영 판단을 생략하지 않음. 후보·상태·제약·배치·동시성·장애 처리 중 실제 설계 대상을 문장에 드러냄
- **지표 강제 금지**: 적용 대상과 고유 동작이 이미 명확하면 지표를 붙이지 않음. 지표를 추가할 때는 `성능`, `품질`, `운영 지표` 같은 일반어가 아니라 측정 대상·비교 기준·바뀌는 결정을 직접 씀
- **문장 강제 종료 규칙**: `시스템 + 기술 고유 동작`을 읽고 적용 장면을 설명할 수 있으면 마침표를 찍음. 뒤 문구를 지워도 적용 방식이 같으면 그 문구는 무조건 삭제함
- **`그래서 무엇을 하는가` 검사**: 지표 뒤에 선택·중단·전환·용량 결정 중 어느 행동이 달라지는지 한 문장으로 답하지 못하면 지표와 후속 문구를 모두 삭제함
- **만능 꼬리 금지**: `p95·p99 지연`, `정확도`, `사용률 편차`, `가중치 조정`, `성능 검증`을 사례 완성용으로 붙이지 않음. 해당 지표가 주제의 고유 판단이고 임계값·비교 대상·변경 행동까지 특정될 때만 사용함
- **장황성 실패 판정**: 핵심 동작 뒤에 지표 2개와 조정 동작을 연달아 붙인 문장은 기술적으로 맞아도 실패임. 하나의 사례는 하나의 적용 동작 또는 하나의 선택 판단만 전달함
- 항목은 구성요소·절차·적용 조건에서 논리적으로 도출돼야 함
- CSPE 키워드 노트의 실무 사례는 보통 **1~2개**면 충분하며, 한 사례로 적용 판단이 완결되면 개수를 채우려고 늘리지 않음
- `문제:`와 `해결방안:`을 따로 나누지 않음. 같은 내용이 반복되기 쉬우므로 한 문장으로 합침
- 상세한 실무 사례 교정은 [CSPE 답안 작성 예시집](@/exam/cs/writing-examples.md)의 실무 사례 예시를 참조함
- 제품명·회사명 홍보가 아니라 도메인, 시스템 유형, 운영 조건을 기준으로 씀
- **CSPE 직무 적합성**: 컴퓨터시스템응용기술사 답안이므로 서버·CPU·메모리·스토리지·클러스터·데이터센터·운영체제·미들웨어·데이터베이스·소프트웨어·응용 플랫폼의 설계·운영 사례를 우선함
- 통신사업자의 회선 구축, 이동통신 커버리지, 도로·배관·전력 인프라 설계처럼 다른 기술사 직무가 중심인 사례는 해당 개념의 유일한 대표 사례가 아니면 사용하지 않음. 필요하면 클러스터 연결, 시스템 의존성, 스토리지 경로, 응용 처리 사례로 바꿈
- **짧은 사례 문장**: `적용 대상 -> 핵심 조치`만 남기며, 이것으로 의미가 닫히면 더 쓰지 않음. 배경·장점·지표·후속 조치를 한 문장에 의무적으로 채우지 않음
- 분류와 예측, 신규 구축과 증설처럼 적용 조건·평가 지표가 다른 대상을 한 사례에 묶지 않음. 사례 하나에는 하나의 적용 대상과 하나의 판단 맥락만 두고 필요하면 두 사례로 분리함
- 지표가 선택 판단에 꼭 필요하면 가장 직접적인 지표 하나를 우선함. 두 지표가 서로 다른 판단을 만들면 사례를 분리하거나 덜 중요한 지표를 삭제함
- 사례 문장을 읽은 뒤 기술 이름을 다른 것으로 바꿔도 그대로 성립하면 일반론으로 판정함. 해당 기술의 구조·선택 기준이 조치나 지표에 직접 나타나야 함
- 비교표의 모든 대상을 다시 나열하지 않고, 가장 대표적인 1~2개만 남김
- `대규모`, `고성능`, `효율적`처럼 판단에 영향을 주지 않는 강조어는 삭제하고, 입력 규모·처리량·메모리 한계처럼 선택 기준이 달라질 때만 구체적 조건으로 씀

## 11. Ⅶ. 결론

결론은 **2개 불릿, 각 1문장**으로 작성한다. 첫 문장은 본문 전체를 관통하는 원리·가치·핵심 고려사항을 회수하고, 두 번째 문장은 기술사로서 적용 범위·선택 기준·운영 통제·대안 전환 중 하나에 대한 판단을 제시한다.

두 번째 문장의 `인사이트`는 개인 감상이나 미래 예측이 아니다. 앞 절의 구조·제약·실무 사례에서 도출한 근거로 `어디에 우선 적용할지`, `어떤 조건에서 배제할지`, `무엇을 측정해 설정이나 구조를 바꿀지`를 밝히는 공학적 견해다. `중요하다고 생각함`, `적극 활용해야 함`처럼 근거 없는 1인칭·당위 표현은 쓰지 않는다.

- 당위만 있는 도덕적 문장 금지
- **방향성 회수 의무**: 첫 문장은 `작성 근거`의 `방향성` 문장이 가리킨 판단·트레이드오프를 실제로 완성함. 결론이 방향성과 다른 이야기를 하거나 정의만 반복하면 그 노트는 위키형 실패이므로 개요의 핵심 명제부터 다시 잡음
- 첫 문장은 앞 절의 특징과 핵심 판단을 한 줄로 회수함
- 두 번째 문장은 첫 문장을 반복하지 않고 적용 우선순위·실패 경계·운영 조정·대안 선택 중 하나를 추가함
- **`실무·현업` 도입어 금지**: Ⅵ절이 이미 실제 적용을 담당하므로 결론을 `실무에서는`, `현업에서는`으로 시작하지 않음. 적용 조건이나 선택 판단을 주어로 바로 제시함
- **추상 판단어 금지**: `적용 범위를 통제함`, `종합적으로 고려함`, `품질을 확보함`처럼 실제 행동이 보이지 않는 말로 끝내지 않음. 비교 대상·허용 조건·설정 변경·대안 전환을 직접 씀
- **직관성 재진술 검사**: 처음 읽는 사람이 한 번에 뜻을 설명하지 못하면 전문어를 쉬운 조건과 행동으로 바꿈. 예를 들어 `적용 범위를 통제함`은 `소규모 최적해와 비교해 허용 품질을 충족할 때만 사용함`으로 구체화함
- 기술 이름을 다른 것으로 바꿔도 성립하는 `품질과 성능을 함께 고려해야 함` 같은 일반론은 인사이트로 인정하지 않음
- 재귀 깊이·호출당 저장량처럼 본문에서 이미 설명한 세부 변수를 결론에 욱여넣지 않음
- 정의를 그대로 반복하지 않고 기술의 핵심 가치와 적용 시 상충 관계를 연결함
- 결론만 읽어도 해당 기술의 쓰임과 판단 기준이 쉬운 말로 와닿아야 함
- 새 문제를 결론에서 갑자기 만들지 않음
- 공허한 미래 예측과 세 번째 문장 추가를 금지함

| 구분 | 문장 | 판정 |
|:---|:---|:---|
| 나쁜 예 | 분할 정복은 같은 구조의 작은 문제를 재귀적으로 해결하며, 시간은 부분 문제 수·크기와 분할·결합 비용으로, 공간은 재귀 깊이·호출당 보조 공간으로 판단함 | 세부 분석 변수를 나열해 기술의 가치와 핵심 판단이 와닿지 않음 |
| 좋은 예 1 | 분할 정복은 큰 문제를 작은 문제로 나누어 해결하여 동시성·병렬성을 확보하는 기법이며, 분할 및 결합 비용을 고려해야 함 | 문제 분해의 원리, 동시성·병렬성의 가치, 추가 비용을 회수함 |
| 좋은 예 2 | 부분 문제가 독립적이고 작업 크기가 병렬 실행 비용보다 클 때 적용하며, 작은 작업은 순차 처리로 전환해야 함 | 적용 조건과 대안 전환 기준을 기술사 인사이트로 제시함 |

`content/cspe/01_basic_theory/014_divide_and_conquer.md`는 위 결론 원칙을 적용하는 **작성법 모범 사례**다. 다른 노트의 결론은 이 문장의 표현을 복사하지 말고, 해당 주제의 본질과 적용 판단을 같은 추상 수준으로 설명한다.

## 12. 표와 불릿 판단

표의 선택·내용 규칙은 다음 세 가지다. 구성요소 표는 이 절과 8절을 함께 적용한다.

1. **형식 선택**: 대상 2개 이상을 정확히 3개 축으로 대조할 때는 비교표, 요소와 설명을 대응할 때는 2열 표, 순서·인과가 핵심일 때는 도식을 사용한다. 단순 나열은 불릿으로 쓴다.
2. **머리글·셀 대응**: 각 셀은 행·열 머리글이 묻는 한 가지 내용에 직접 답해야 한다. `설명`에는 의미·역할을, `판단 기준`에는 판별 속성·임계값을 쓴다. 구성요소 행은 8절의 역할 대응 검사를 통과해야 한다.
3. **작성자 행위 금지**: 요소의 의미를 써야 할 셀을 `분석함`, `정의함`, `확인함` 같은 작성자 행위로 끝내지 않는다. 성질·역할·조건·비용 자체를 직접 쓴다.

좋은 예시는 다음과 같다.

| 설계 요소 | 설명 |
|:---|:---|
| 부분 문제 독립성 | 부분 문제 해결 과정의 상호 비의존성 |
| 분할 균형도 | 분할된 부분 문제들의 입력 크기가 서로 비슷한 정도 |
| 종료 조건 | 입력이 직접 답을 구할 수 있는 최소 처리 단위에 도달하면 분할과 함수 호출을 종료함 |
| 결합 비용 | 부분 해를 전체 해로 합치는 과정에서 추가로 소요되는 실행 시간과 저장 공간 |

나쁜 예시인 `결합 비용 | 추가 시간·공간 비용을 분석함`은 비용 자체가 아니라 작성자의 분석 행위를 설명한다. `결합 비용 | 부분 해를 전체 해로 합치는 과정에서 추가로 소요되는 실행 시간과 저장 공간`처럼 비용의 발생 지점과 비용 대상을 직접 써야 한다.

`부분 문제 독립성`을 `각 부분 문제의 계산 결과가 서로 독립적인 성질`로 쓰면 결합 단계에서 함께 사용되는 부분 해가 독립적이라는 뜻으로 오해할 수 있다. 분할 정복의 적용 조건은 한 부분 문제를 해결할 때 다른 부분 문제의 중간 계산이나 해를 요구하지 않는 것이므로 `부분 문제 해결 과정의 상호 비의존성`으로 쓴다. 이 셀은 판별 방법이 아니라 설계 요소의 의미 설명이므로 열 머리글도 `판단 기준`이 아닌 `설명`으로 둔다.

- 불릿도 `보장 결과`, `핵심 효과`, `운영 가치` 같은 넓은 명사로 끝내지 않고 절차·구조·조건·비용·검증 지표 중 실제 역할을 밝힌다.
- **표 요약**: 표 바로 아래 빈 줄 1개 뒤 `> 요약:`을 붙이며, 실제 답안의 간글로 옮길 수 있는 완결 문장으로 작성함
- **요약 문장 품질**: 표의 핵심 대상을 주어로 두고 `요소 관계·동작 메커니즘 -> 산출 결과·효과`를 한 문장으로 연결함. 셀을 순서 없이 나열하거나 `효율성을 극대화함`처럼 근거 없는 효과로 끝내지 않음
- **요약 선행 근거 검사**: 요약은 실제 답안에 쓰는 간글이지만 누락된 핵심을 보충하는 자리가 아님. 요약의 각 주장·선택 기준·원리·제약은 바로 위 본문·표·도식에 먼저 명시되어야 함
- **요약 삭제 검사**: 모든 `> 요약:`을 가린 상태로 문서를 읽어도 핵심 선택과 기술 원리가 그대로 보여야 함. 요약을 지웠을 때 핵심이 사라지면 요약이 좋은 것이 아니라 상단 본문이 미완성인 것임
- 상단 요소가 핵심을 은근히 암시하고 요약에서만 직접 말하는 구성을 금지함. 표 셀도 `전체 간선 정렬 후 사이클 없는 간선 선택`, `현재 트리와 외부 노드를 잇는 최소 간선으로 확장`처럼 동작과 조건을 직접 씀
- 요약에 처음 등장한 단어·판단·예외는 위 절로 올리고, 이미 위에서 충분히 드러난 내용만 짧게 재진술함. 요약을 근거로 본문 누락을 정당화하지 않음
- **표 남발 금지**: 한 파일의 표는 대개 `출제 의도`, `Ⅱ 특징/비교`, `Ⅲ 구성요소` 정도면 충분함

## 13. 표현 금지와 치환

| 금지 표현 | 답안 표현 |
|:---|:---|
| 성능이 좋다 / 빠르다 | 색인으로 탐색 범위 축소, 중복 연산 제거, 독립 작업 동시 처리 |
| 안정적이다 | 장애 영역 격리, 상태 복제, 실패 노드 자동 전환 |
| 보안이 강화된다 | mTLS, RBAC, AES-256, 감사 로그, 취약점 스캔 |
| 효율적이다 | 캐시 재사용, 배치 처리, CPU·메모리 한도에 맞는 구조 선택 |
| 확장성이 있다 | 수평 확장, 샤딩, 오토스케일링, 파티셔닝 |
| 품질이 향상된다 | 결함 유형에 맞는 정적 분석 규칙·테스트·복구 절차 적용 |
| 막다 / 막음 | 오류·위반은 방지, 공격·패킷은 차단, 경쟁·확산은 억제, 영향은 완화, 권한·범위는 제한, 상태는 검증 |

- 수치가 없으면 표준명·기술명·구체 메커니즘으로 특정함
- 억지 수치화도 금지함. 기준은 "수치 여부"가 아니라 "구체적이고 검증 가능한가"임
- 실무 사례의 지표 사용은 10절의 `지표 강제 금지`와 `그래서 무엇을 하는가 검사`를 적용함
- `막다`는 물리적 차단처럼 의미가 분명한 경우가 아니면 쓰지 않음. 대상과 메커니즘을 확인해 `방지`, `차단`, `억제`, `완화`, `격리`, `통제`, `제한`, `검증` 중 하나로 좁힘

전수 어휘 검수 절차와 판별표는 [CSPE 답안 작성 예시집](@/exam/cs/writing-examples.md)의 어휘 검수 예시를 참조함.

## 14. 모호 표현 금지

- 주어·목적어·동사를 명시함
- 모든 명사·동사·형용사·부사·수식어는 기술 정의, 비교 기준, 측정 지표, 인과관계, 절차 순서 중 하나로 근거를 제시할 수 있어야 함
- 근거 없는 평가·강조를 만드는 수식어와 형용사는 문장 의미를 부드럽게 보이게 하더라도 사용하지 않음
- `A·B 제거`처럼 제거 대상이 모호한 압축 표현 금지
- `인증·인가 통제`처럼 역할이 다른 용어를 한 동사에 묶지 않음
- `무엇을 막음`처럼 목적어와 제어 방식이 뭉개진 문장 금지
- 감점 회피 포인트는 이중 부정 대신 명사형으로 씀

모호 표현의 구체적인 교정표는 [CSPE 답안 작성 예시집](@/exam/cs/writing-examples.md)의 모호 표현 예시를 참조함.

## 15. 키워드 유형별 해석

절 제목은 키워드 성격에 맞게 바꿀 수 있다. 다만 개요, 특징/비교, 구조/원리, 실무 사례, 결론의 역할은 유지한다. 유형은 폴더가 아니라 키워드 성격으로 판단한다.

| 유형 | 해당 예 | 판단 기준 |
|:---|:---|:---|
| 기술형 (기본) | 알고리즘, 프로토콜, 아키텍처, 신기술 | 아래 해석 없이 본 문서 5~11절 그대로 적용함 |
| 법·제도·정책형 | 07 영역 대부분, 개인정보보호법, ISMS-P | 법률·고시·인증제도·정책 자체가 키워드임 |
| 평가·지표형 | 06 영역 대부분, BMT, TPC, 신뢰성 지표 | 평가 방법·지표·산식이 키워드임 |
| 비교형 | "A vs B" 형태 제목 | 두 대상을 어떤 기준으로 나눠 판단해야 하는지 보여주는 유형임 |

**법·제도·정책형 해석:**

- **특징/비교**: 이전 제도, 유사 제도, 해외 제도 대비 차별점과 적용 범위 차이를 씀
- **구성요소/구조**: 조문 나열이 아니라 적용 대상, 의무 주체, 추진·감독 체계, 인증·심사 체계를 구조로 씀
- **절차/동작 원리**: 기술 동작이 아니라 신고·인증·심사·이행점검 등 제도 이행 절차를 씀
- **실무 사례**: 적용 범위 공백, 실무 이행 부담, 중복 규제, 판단 기준 모호성 같은 제도 운영상 한계와 기업·기관의 이행 절차, 인증·신고·감사 대응, 운영 문서화 사례를 함께 연결함
- **결론**: 개정 동향, 국제 규제·표준과의 정합성, 실무 대응 우선순위를 씀
- 금지: 조문 전문 인용, 제정·개정 연혁 나열, 법령 명칭만 바꾼 일반론

**평가·지표형 해석:**

- **특징/비교**: 대안 평가 방법·지표 대비 측정 대상과 신뢰 수준 차이를 씀
- **구성요소/구조**: 평가 항목, 지표 정의, 산식, 측정 환경 요건을 구조로 씀
- **절차/동작 원리**: 평가 계획 -> 환경 구성 -> 측정 수행 -> 분석·판정 흐름으로 씀
- **실무 사례**: 지표 왜곡 가능성, 측정 환경 편차, 재현성 부족 같은 한계와 벤치마크, 인증, 용량 산정, 운영 모니터링에서 무엇을 확인하는지 함께 씀

**비교형 해석:**

- **특징/비교**: 이 절이 답안의 중심이어도 판단 기준은 핵심 비교축 3개로 제한하고 세부 근거는 특징·구조·절차로 분산함
- **구성요소/구조 또는 절차**: 두 대상의 구조·동작 차이가 드러나는 지점 중심으로 씀. 각각을 전부 나열하지 않음
- **실무 사례**: 잘못된 선택·오적용 시나리오와 상황별 선택 기준, 하이브리드 적용 방안, 대표 업무·시스템 조건을 함께 씀

## 16. 출력 직전 체크

- **표 좌우 대응 필수 검사**: 모든 표를 가로 한 행씩 읽어 우측 셀이 좌측 요소의 정의·조건·역할·판단 기준에 직접 답하는지 확인했는가. 하나라도 불일치하면 해당 파일은 미완료이며 출력·완료 처리하지 않음
- **내용 선정**: 0-1의 대표 핵심 선정 게이트를 모든 문장·표 셀·도식에 적용했는가
- **절 구성**: 5~11절의 역할과 형식을 충족하고 절마다 새로운 판단을 추가했는가
