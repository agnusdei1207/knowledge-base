# CSPE 답안 작성법 단일 정본

> 이 문서가 CSPE 키워드 노트 작성법의 **유일 정본**이다. `model-answer.md`, `master-template.md`, `AGENTS.md`는 이 문서를 참조할 뿐 별도 작성법을 만들지 않는다.

## 0. 최상위 논리

기술사는 단순히 개념을 설명하는 사람이 아니라, 요구사항을 구조로 바꾸고 기술을 선택해 구현·운영·개선까지 책임지는 사람이다. 따라서 모든 2~4교시 답안은 개요로 시작하더라도 아래 흐름을 잃지 않아야 한다.

```text
+----------+   +----------+   +----------+   +----------+   +----------+   +----------+
| 요구사항 | -> | 구조설계 | -> | 기술선정 | -> | 구현전략 | -> | 운영관리 | -> | 개선     |
+----------+   +----------+   +----------+   +----------+   +----------+   +----------+
```

- **요구사항**: 문제 신호어와 출제 의도에서 무엇을 해결해야 하는지 정의함
- **구조설계**: 요구사항을 구성요소·관계·데이터 흐름으로 전개함
- **기술선정**: 특징/비교를 통해 왜 이 기술·방식이 맞는지 판단함
- **구현전략**: 절차·알고리즘·적용 단계를 구체화함
- **운영관리**: 실제 적용 시 깨지는 지점과 관리 지표를 제시함
- **개선**: 문제 원인별 대응 방안과 발전 방향으로 마무리함

> 요약: 개요는 시작점일 뿐이며, 전체 답안은 요구사항에서 개선까지 전진해야 함.

## 0-1. 작성 방식: 반복 다듬기

노트는 한 번의 작성으로 완성되지 않는다. 초안은 완료가 아니라 깎아나갈 시작점이며, 모든 노트는 1-1의 검수 게이트를 수정 사항이 없는 상태로 통과할 때까지 반복해 다듬는다. 회차 수·검사 순서·통과 기준은 1-1이 정본이다. 문장을 줄일 때는 핵심을 삭제하는 것이 아니라 채점자가 이해하도록 `대상 + 판단 기준 + 필요한 이유`만 남긴다.

**부자연스러운 문장은 가장 위험한 실패로 판정한다.** 기술적으로 맞고 핵심어가 들어 있어도 조사, 수식어 위치, 단어 순서, 목적어와 동사 결합이 어색하면 답안 문장으로 사용하지 않는다. 문장을 줄이거나 전문용어로 바꾼 뒤에는 소리 내어 읽듯 다시 읽고, 평소 한국어 문장으로 자연스럽게 말할 수 있는 형태인지 확인한다.

전수 검토는 수정 개수를 만드는 작업이 아니다. 기술적 오류, 오해 가능성, 비교축 불일치, 템플릿 위반, 채점 판단을 흐리는 장황함이 없으면 **수정 사항 0건으로 통과**시키고, 의미가 같은 동의어 치환, 작성자 취향의 문체 변경, 이미 읽기 쉬운 문장의 재배열은 하지 않는다. 수정할 때는 걸린 단어·조사·배치·논리와 교정 이유를 설명할 수 있어야 하며, 이유를 설명하지 못하는 변경은 하지 않는다.

교정 과정에서 새로운 실패 유형이나 더 나은 문장이 확인되면 [CSPE 답안 작성 예시집](@/exam/cs/writing-examples.md)에 `문제 유형·권장 배치·판정 이유·대체 문장`을 추가한다. 예시집은 고정된 부록이 아니라 이후 작성 판단에 재사용하는 누적 데이터로 관리한다.

절 제목이 이미 역할을 밝히므로 본문과 작성 근거에서 `실무 사례는`, `특징은`, `Ⅵ 사례 선정`처럼 절 이름을 다시 주어로 쓰지 않는다. `서비스 호출 그래프와 음수 비용은...`처럼 선정한 대상과 판단 이유로 시작한다.

### 대표 핵심 선정 게이트

대표성·핵심성·출제 의도 적합성은 Ⅵ의 사례에만 적용하는 기준이 아니라 제목, 미리 알고가기, 작성 근거, Ⅰ~Ⅶ의 모든 문장, 표 헤더·셀, 도식, 요약에 공통 적용한다. 각 항목은 `이 문제에서 왜 이 내용을 써야 하는가`에 한 문장으로 답할 수 있어야 하며, 답하지 못하면 삭제한다.

- **대표성**: 해당 개념을 설명할 때 일반적으로 인정되는 구조·기법·사례인가
- **핵심성**: 정의, 고유 특성, 선택 조건, 구조 원리, 실패 조건, 검증 기준 중 하나를 직접 설명하는가
- **출제 의도 적합성**: 문제의 핵심어와 요구사항을 회수하고 채점자가 기술 선택·비교·적용 판단을 확인하게 하는가
- **절 간 기여**: 앞 절을 표현만 바꿔 반복하지 않고 새로운 판단을 한 단계 추가하는가
- **삭제 대상**: 드문 예외, 제품 홍보, 역사·배경 지식, 개수 채우기용 항목, 문제 논지와 무관한 최신 용어, 측정할 수 없는 효과

실무 사례는 널리 쓰이는 대표 업무·시스템에서 본문의 구조나 선택 기준이 실제로 드러나는 경우만 쓴다. 사례 이름만 붙이지 말고 `적용 대상 -> 기술 고유 조치 -> 검증 지표 1~2개`가 본문 논지와 같은 축으로 이어져야 하며, 실패 조건은 기술 선택을 바꿀 때만 한 개를 추가한다. 특이하지만 비대표적인 사례, 기술 이름을 바꿔도 그대로 성립하는 일반론, 출제 키워드의 원리를 검증하지 못하는 운영 문장은 제외한다.

## 1. 답안 품질 3박자와 논리 흐름성

- **직관성**: 채점자가 5초 안에 구조를 파악해야 함. 불친절한 압축을 피하고, 특징/비교, ASCII 도식, 표 요약으로 핵심을 먼저 보임
- **이해성**: 학습자와 작성자가 이 파일만 읽고도 개념·용어·동작 원리를 이해할 수 있어야 함. 하나하나 떠먹이는 설명이 아니라, 필요한 연결고리를 생략하지 않는 설명이어야 함
- **핵심포함성**: 긴 설명이 아니라 개념·대상·판단 기준·적용 조건만 남기고 배경·역사·수식 과시를 제거함
- **논리 흐름성**: 개요의 문제의식이 특징/비교의 선택 기준으로 이어지고, 구성요소/구조가 그 선택 기준을 설명하며, 실무 사례가 앞 절의 판단을 다시 검증해야 함. 앞 절에서 제시하지 않은 기준이 뒤 절에서 갑자기 등장하거나 뒤 절의 문제점이 앞의 구조·조건과 무관하면 실패임
- **방향성**: 답안은 한 문단씩 새로운 판단을 전진시켜야 하며, 개요에서 잡은 핵심 축이 끝까지 흔들리지 않아야 함. 개요의 핵심 문제, 비교의 판단 기준, 구조의 원리, 결론의 대응이 같은 축을 바라봐야 함
- **인사이트 가시성**: 단순 정의 나열이 아니라 왜 이 기술을 선택하거나 버려야 하는지, 어디서 병목이 생기고 무엇을 통제해야 하는지가 문장 안에 드러나야 함. 각 절에는 `어떤 입력 분포에서 퇴화하는지`, `어떤 지표로 검증하는지` 같은 실질적 인사이트가 최소 1개 있어야 함
- **중복 억제**: 앞 절에서 이미 한 말을 표현만 바꿔 반복하지 않음. `빠르다`, `효율적이다`를 반복하는 대신 무엇이 왜 빨라지는지, 어떤 조건에서 깨지는지 다음 절로 전개해야 함

- 1교시는 13문제 중 10문제를 쓰므로 `정의 1~2줄 + 특징 3개 + 미니 도식 + 표/비교 + 적용 1줄`로 압축함
- 2~4교시는 4문제를 각 3쪽 내외로 쓰므로 `개요 -> 특징/비교 -> 구조/원리 -> 실무 사례 -> 결론` 흐름을 끝까지 밀어붙임
- 키워드 노트는 작성 지침이나 체크리스트처럼 쓰지 말고, 해당 키워드에 대한 실제 기술사 모범 답안 본문처럼 작성함
- "답안에서는 ~해야 함", "기술사 관점에서는 ~" 같은 메타 표현은 최소화하고, 개념·구조·비교·실무 판단·결론을 직접 서술함
- 기술사 답안은 먼저 문제가 실제로 묻는 핵심 판단 요소를 2~3개로 좁힘. 예를 들어 스택·큐·덱은 `처리 순서`, `접근 위치`, `적용 업무`가 핵심 판단 요소임
- 비교형 답안의 판단 기준은 기술사 시험 작성 시간을 고려해 **핵심 비교축 3개**로 제한함
- 세 축은 `동작 메커니즘`, `계산·처리 범위`, `실무 부작용·리스크`를 우선하며, 주제에 맞지 않는 축만 더 직접적인 공학적 판단 기준으로 교체함
- 비교축은 개수를 채우기 위해 늘리지 않음. 각 축이 출제 의도와 기술 선택에 직접 기여해야 하며, 주변 지식이나 공유 값은 더 핵심적인 축으로 교체함
- 비교에서 선정한 핵심축은 표에서 끝내지 않고 구성요소·절차·실무 사례·결론까지 같은 용어와 판단 방향으로 이어감
- 장황성·반복·빈 추상 표현은 이해 부족으로 보이므로 삭제함
- **과압축 금지**: "입력 증가에 따른 실행시간·메모리 증가율 분석"처럼 말은 맞지만 처음 읽는 사람이 대상·방법·목적을 잡기 어려운 문장은 실패임
- 좋은 압축은 `무엇을`, `무엇 기준으로`, `왜 판단하는지`가 보이는 문장임
- **장문 금지**: 10~15자로 끝나는 판단을 40~60자로 늘리지 않음. 수식어, 중복 목적어, 당위어를 제거함
- **문장 길이 기준**: 본문 불릿은 보통 1문장 35자 안팎, 길어도 50자를 넘기지 않으며 개요의 정의/개념과 배경/필요성은 각각 1문장으로 쓰고 추가 판단은 뒤 절이나 표로 보냄
- **답안지 문체**: `~할 수 있음`, `~하는 것이 중요함`, `~측면에서 필요함`보다 `~함`, `~필요`, `~적합`처럼 짧게 끝냄
- **한 문장 한 역할**: 정의는 정의만, 배경은 필요성만, 특징은 성질만, 유의점은 적용·주의·검증만 담음

## 1-0. 실전 답안지 문장 규칙

공개 답안 작성 조언과 답안지 양식은 공통적으로 가독성, 충분한 분량, 그림·표·간글, 문제 요구사항 회수를 강조한다. 디지털 노트도 이를 따르되, 장황한 설명으로 분량을 채우지 않는다.

- **문제 회수**: 문제의 핵심어, 비교 대상, 제약조건을 정의·표·결론에 반복 반영함
- **정의 밀도**: 정의는 1문장으로 쓰며 `대상 + 기준 + 목적`만 남김
- **짧은 간글**: 도식과 표 아래에는 1문장 요약을 붙이되, 새 설명을 늘리지 않음
- **표 중심 압축**: 긴 비교 문장은 표로 보내고, 표의 좌측 축을 `대상`, `기준`, `병목`, `검증`처럼 구체화함
- **문장 삭제 우선**: 문장이 길면 다듬기보다 먼저 삭제 가능한 단어를 찾음. 판단 기준과 필요한 이유는 남기되, 반복해서 읽었을 때 더 직관적인 답안 문장이 되어야 함
- **답안지 가독성**: 한 줄에 핵심어가 보여야 하므로, 주어와 판단어를 앞쪽에 배치함

장문 치환 예:

| 장황한 문장 | 답안 문장 |
|:---|:---|
| 입력 데이터 크기 $n$이 증가함에 따라 연산 횟수와 메모리 점유량이 변하는 추이를 수학적 함수로 표현해 알고리즘의 효율성을 판단하는 척도임 | 입력 크기별 시간·메모리 증가율임 |
| 동일한 기능을 수행하더라도 입력 규모가 커지면 지연 시간과 메모리 사용량이 급증할 수 있으므로 확장 한계를 예측할 기준이 필요함 | 입력 규모에 따른 연산량·메모리 사용량 증가율 분석이 필요함 |
| 특정 하드웨어의 성능이나 프로그래밍 언어의 처리 속도에 의존하지 않고 알고리즘 구조 자체의 효율성을 객관적으로 비교할 수 있음 | HW·언어와 분리해 알고리즘 구조를 비교함 |
| 시간과 공간 사이의 상충 관계를 분석하여 시스템의 가용 자원 조건에 맞는 알고리즘 선택 기준을 제공함 | 시간·공간 트레이드오프 선택 기준을 제공함 |

> 요약: 실전 답안 문장은 짧아야 하며, 짧아도 기준과 판단이 보여야 함.

## 1-1. 순차 반복 검수 강제

글은 한 번에 완성되지 않는다. 조각가가 한 번의 끌질로 형상을 끝내지 않듯, 초안은 완료가 아니라 깎아나갈 시작점이다. 문장과 단어를 여러 차례 반복해 깎고 다듬어야 완성된 답안이 나오며, 한 번의 작성으로 끝내려는 시도 자체가 실패 원인이다. 한 파일을 끝까지 작성한 뒤에도 아래 검수 게이트를 **순서대로** 통과해야 하며, 어느 단계에서든 수정이 발생하면 다시 1단계부터 반복한다. 한 번 읽고 끝내지 말고, 문장과 단어가 더 고칠 부분이 없을 때까지 수차례 다듬는다.

작성 완료를 선언하기 전에는 한 파일당 최소 5회 파일 전체를 처음부터 끝까지 다시 읽어 어휘, 단어, 문장, 문단 흐름, 개연성, 시험 답안 적합성, 범위 이탈, 과잉·누락 여부를 확인해야 한다. 5회 모두 본문, 표 셀, 요약문, 결론, 작성 근거를 빠짐없이 보는 전수 검수여야 하며, 어느 회차에서든 단어 하나라도 고치면 다시 1단계·1회차부터 반복한다. 검색 결과에 걸린 줄이나 눈에 띄는 일부 문장만 고치는 방식은 검수로 인정하지 않는다.

검수 대상에서 제외되는 문장은 없다. 짧은 표 셀, 익숙한 결론 문장, 선행 작성 근거, 반복되는 안내 문장도 모두 한국어 문장으로 자연스러운지, 기술적으로 맞는지, 더 짧고 직관적으로 줄일 수 있는지 확인해야 한다. 한 문장이라도 건너뛰었다면 해당 파일의 5회 검수는 무효이며 다시 처음부터 읽는다.

각 회차는 제목 첫 줄부터 결론 마지막 줄까지 순서대로 완독해야 한다. `작성 근거(검토용)`도 `미리 알고가기` 다음 위치에서 반드시 확인하며, 검색 결과·수정한 주변 줄·긴 문장만 보는 회차는 5회 검수에 포함하지 않는다.

검수는 단어 하나까지 본다. 최종 통과 기준은 **기술 정확성, 문맥 적합성, 논리성, 일관성, 직관성, 가독성, 이해성, 모범답안 적합성**이며, 하나라도 흔들리면 다시 쓴다.

각 문장 작성 직후 아래 자기점검 질문을 반드시 통과해야 한다. 하나라도 답하지 못하면 그 문장은 할루시네이션 후보로 보고 삭제하거나 다시 쓴다.

- 이 단어가 앞뒤 문맥에서 요구하는 정확한 단어인가
- 이 문장이 기술적으로 참이며 반례가 없는가
- 이 문장이 정의, 특징, 비교, 구조, 절차, 유의점 중 어느 역할을 하는가
- 이 문장을 채점 답안에 그대로 넣어도 기술사 수준인가
- 반복해서 읽었을 때 한국어 문장으로 자연스럽고 처음 읽는 사람이 핵심을 파악할 수 있는가
- 줄일 수 있는 문장인데 수식어, 명사 나열, 어색한 비교 구조로 길게 쓴 것은 아닌가
- 더 정확한 단어가 있는데 추상어로 뭉갠 것은 아닌가
- `막다`, `좋다`, `높이다`, `강화`, `향상`처럼 넓은 동사로 사고를 멈춘 것은 아닌가
- 같은 말을 앞 절에서 이미 했는데 표현만 바꾼 것은 아닌가
- 수식이나 공통값을 썼다면 그래서 무엇을 판단해야 하는지 말했는가
- `작성 근거`가 핵심 키워드·판단축으로 내세운 단어가 본문(Ⅰ~Ⅶ)에 실제로 나오는가, 근거만 있고 본문은 다른 말을 하고 있지는 않은가

1. **기술 정확성 검사**: 용어, 수식, 절차, 비교가 전산학적으로 맞는지 확인함. 정확성을 설명하지 못하면 문장을 쓰지 않음
2. **문맥 적합성 검사**: 지금 필요한 기준이 속도인지, 절차인지, 결과인지, 구조인지 확인함. 문맥이 요구하지 않는 단어를 넣으면 실패임
3. **문장 역할 검사**: 모든 문장과 표의 모든 셀을 하나씩 읽고, 정의·배경·특징·비교·구조·절차·실무 적용·유의점·결론 중 어떤 역할인지 확인함. 역할이 모호하면 삭제하거나 다시 씀
4. **단어 검사**: `선택`, `전략`, `체계`, `관점`, `핵심`, `중요`, `효율적`, `보장 결과`, `막다` 같은 추상어가 실제 의미를 좁히는지 확인함. 의미 없이 들어간 단어는 제거하고, 전문용어는 `미리 알고가기`에서 먼저 설명함
   - 모든 단어는 기술 정의, 비교 대상, 측정값, 인과관계, 절차 순서 중 하나로 존재 이유를 설명할 수 있어야 함
   - 형용사·부사·수량어·강조어는 무엇과 비교하는지 또는 어떤 지표·순서를 뜻하는지 근거가 있을 때만 사용함
   - `바로`는 `바로 앞 노드`, `바로 다음 절`처럼 실제 위치·순서를 뜻할 때만 사용함. 비교 기준 없이 빠름·쉬움·즉시성을 강조하는 `바로·빠르게·쉽게·크게`는 삭제함
   - 해당 단어를 삭제해도 문장의 기술적 의미와 판단이 같으면 불필요한 단어로 판정함
   - **근거 없는 수식어·형용사·부사 사용은 절대 금지함.** 문장의 모든 단어는 왜 필요한지 설명할 수 있어야 하며, 설명할 수 없는 단어가 하나라도 있으면 해당 문장을 다시 씀
5. **논리 검사**: 앞 절의 문제의식이 뒤 절의 비교축, 구조, 문제점, 결론으로 자연스럽게 이어지는지 확인함. 앞에서 근거를 제시하지 않은 기준이 뒤에서 갑자기 나오면 실패임
   - 문장 하나도 `대상 -> 관련 조건 -> 판단 기준 -> 결론 동작` 순서로 전개되어야 함
   - 같은 상위 개념에 속한 단어는 붙여 배치함. `음수 가중치`와 `음수 사이클` 사이에 다른 축을 끼워 넣지 않음
   - 앞에서 사용한 용어를 뒤에서 더 정확한 말로 바꾸려면 처음부터 정확한 용어를 사용함. 최단 경로에서는 `계산 범위`보다 출발·도착 대상의 범위를 뜻하는 `접근 범위`를 사용함
   - 마지막 서술어는 문장의 핵심 목적어와 자연스럽게 결합해야 함. 알고리즘은 `선택`하지만 검증 절차는 설계·수행하므로 두 대상을 `선택해야 함`에 함께 묶지 않음
   - 결론 문장은 앞의 조건을 기준으로 무엇을 판단·선택·검증하는지 한 동작으로 회수함. 새 대상이나 관련 없는 동작을 문장 끝에 추가하지 않음
6. **자연스러움·단어 배치 검사**: 이 검사를 통과하지 못하면 기술적으로 맞아도 문장을 폐기함. 한국어 문장으로 읽었을 때 조사, 접속, 종결어미와 단어 순서가 자연스러운지 확인함. 수식어는 꾸미는 대상 가까이에 두고, 주어·목적어·서술어의 관계와 병렬 단어의 순서를 확인함. 수식이나 영어 뒤에 조사를 억지로 붙이지 않고, `O(V+E)이지만` 대신 `시간복잡도는 $O(V+E)$임. 다만 ...`처럼 문장을 나눠 씀
   - **문장 완결성**: 주어 또는 대상, 조건 또는 판단 기준, 목적어, 서술어가 하나의 의미로 닫혀야 함. 명사만 나열하거나 마지막 서술어가 앞의 목적어를 받지 못하면 미완성 문장으로 판정함
   - 문장 끝을 읽었을 때 `무엇이`, `어떤 조건에서`, `무엇을`, `어떻게 하는지` 중 문맥에 필요한 요소가 남지 않아야 함
   - 결론형 문장은 조건을 나열하는 데서 끝나지 않고 그 조건으로 내릴 선택·판단을 서술어로 완성함
7. **이해성 검사**: 처음 읽는 사람이 용어와 전제를 따라올 수 있는지 확인함. `무가중치 최단 경로`, `위상 정렬`, `안정 정렬`처럼 멈칫할 수 있는 용어는 본문 전에 풀어씀
8. **직관성 검사**: 표 헤더, 비교축, 도식, 결론만 읽어도 의미를 설명할 수 있는지 확인함. `직접 해결 문제`, `상수 비용이 달라짐`처럼 말은 되지만 직관이 약한 표현은 `주요 활용`, `목록은 실제 연결만 따라가고 행렬은 간선 존재 여부를 확인함`처럼 풀어씀
9. **가독성 검사**: 한 문장이 너무 길거나 두 판단을 억지로 붙였는지 확인함. 50자를 넘는 문장은 먼저 삭제하고, 그래도 길면 표·도식·별도 문장으로 분리함
10. **모범답안 적합성 검사**: 문장이 시험 답안에 들어갔을 때 채점자가 근거 있는 판단으로 볼지 확인함. 단순 상식, 추상 구호, 그럴듯한 말은 삭제함
11. **근거-본문 정합성 검사**: `작성 근거`에 적은 핵심 키워드·판단축·배치 이유를 하나씩 본문에서 찾아 대조함. 근거가 주장한 단어나 축이 본문 어디에도 없으면 근거가 거짓 근거이므로, 본문에 그 축을 실제로 반영하거나 근거를 사실대로 다시 씀
12. **문장별 전수 읽기 검사**: 금지어 검색이나 표본 확인으로 끝내지 않고, 파일의 모든 문장, 표 셀, 요약문, 결론, 작성 근거를 한 줄씩 소리 내어 읽듯 확인함. 특히 `A·B 동사`처럼 두 명사를 하나의 동사로 묶은 자리는 각 명사가 그 동사와 개별적으로 자연스럽게 짝지어지는지 따로 검사함. `경로·순환 판단`처럼 `순환`은 판단의 대상이지만 `경로`는 분석·추적의 대상이라 같은 동사에 묶이지 않는 경우가 대표적 실패이며, 금지어 목록에 없어 grep으로는 잡히지 않으므로 반드시 눈으로 읽어야 함
13. **누락 방지 검사**: 빈 줄을 제외한 모든 줄을 위에서 아래로 확인하고, 표는 행이 아니라 셀 단위로 끊어 읽음. 한 줄이라도 확인하지 않았거나 확인 여부를 설명하지 못하면 검수는 무효이며, 해당 파일은 미완료로 되돌림
14. **재검수**: 1~13단계 중 하나라도 수정했으면 다시 1단계·1회차부터 반복함. 최소 5회의 전체 완독 전수 검수까지 포함해 수정이 없는 상태로 다섯 바퀴를 통과해야 작성 완료로 인정함

> 요약: 작성 완료는 초안 완성이 아니라 기술 정확성, 문맥 적합성, 문장 역할, 단어, 논리, 자연스러움, 이해성, 직관성, 가독성, 모범답안 적합성, 근거-본문 정합성, 문장별 전수 읽기, 누락 방지 검사를 한 파일당 최소 5회 반복해 수정 사항이 더 나오지 않는 상태를 의미함.

## 1-2. 내용 선별과 균형, 근거 병기

문장을 다듬기 전에 `0-1. 대표 핵심 선정 게이트`로 존재 이유부터 판단한다. 잘 쓴 문장도 핵심이 아니면 삭제하며, 비교 대상의 공유 값은 차이가 갈리는 이유로 바꾸고 뜻·판단 없는 값 나열은 제거한다.

### 개념 균형과 주제 이탈 경계

- 한 개념을 꺼내면 반대 개념이 따라붙는지 점검함. 예: `희소 그래프`를 쓰면 `밀집 그래프`는 왜 안 쓰는지 자문함
- 다만 반대 개념을 넣는 순간 주제에서 벗어날 수 있으므로, `이 대비가 이 키워드의 판단에 필요한가`를 먼저 물음
- 필요하면 한 줄 대비로 균형을 맞추고, 불필요하면 언급 자체를 지워 초점을 지킴
- **핵심 일관성 게이트**: 개요에서 이 문서가 끝까지 밀고 갈 핵심 명제와 판단축을 한 문장으로 고정함. 이후 모든 특징·비교 행·구성요소·절차 단계·사례·결론은 그 명제를 설명하거나 검증해야 함
- 관련 개념이라는 이유만으로 새 기술·반대 개념·파생 이론을 추가하지 않음. 현재 핵심의 원인, 동작, 선택, 실패, 검증 중 어느 역할인지 답하지 못하면 생판 다른 내용으로 판정해 삭제함
- 앞 절에서 정의하지 않은 개념이 중간 절에 처음 등장하면 `핵심을 설명하는 데 반드시 필요한가`, `미리 알고가기나 개요에서 전제했는가`, `뒤 절에서 회수되는가`를 확인함. 하나라도 충족하지 못하면 새 개념을 들고 오지 않음
- 절마다 핵심 대상을 바꾸지 않음. 예를 들어 개요는 알고리즘 선택을 말하면서 특징은 구현 역사, 비교는 무관한 성능 수식, 절차는 일반 운영 흐름, 결론은 보안 통제로 끝내면 핵심 불일치로 판정함
- 핵심을 넓혀야 할 때는 기존 문장 사이에 끼워 넣지 말고 개요의 핵심 명제부터 다시 정한 뒤 모든 절을 함께 수정함

개념 균형 판단 과정은 [CSPE 답안 작성 예시집](@/exam/cs/writing-examples.md)의 내용 선별 예시를 참조함.

> 요약: 개념을 하나 꺼내면 반대 개념의 포함 여부를 매번 판단하되, 균형과 초점 중 답안에 유리한 쪽을 택함.

### 키워드·방향·전개 설계

최적의 답안은 최적의 키워드·방향·논리 흐름·전개에서 나온다. 쓰기 전에 아래를 먼저 고민한다.

- **핵심 키워드 선정**: 이 주제의 판단을 가르는 키워드를 고르고, `왜 다른 후보가 아니라 이 키워드가 핵심인가`를 판단함
- **방향**: 개요에서 잡을 핵심 축을 정하고, 모든 절이 그 축 하나를 향하게 함
- **논리 흐름**: 개요 -> 특징 -> 비교 -> 구조 -> 절차 -> 유의점 -> 결론이 앞 절의 판단을 뒤 절이 이어받도록 배치함
- **전개**: 각 문단이 새 판단을 전진시키는지, 앞 문단의 재진술이 아닌지 확인함
- 이 고민이 있어야 불필요한 요소가 사라지고 필요한 요소가 자리를 잡음

> 요약: 키워드·방향·흐름·전개를 먼저 설계하고, 그 설계 자체를 근거로 남김.

### 근거·사유 병기 (필수)

모든 노트는 `미리 알고가기` 바로 다음, `Ⅰ. 개요` 앞에 `## 작성 근거(검토용)` 블록을 **반드시** 포함한다. 이 블록이 없거나 결론 뒤에 있으면 작성 미완료다. 답안을 읽기 전에 핵심 키워드·판단축·전개 근거를 먼저 확인해야 이후 본문의 방향을 잡을 수 있기 때문이다.

- 각 절을 왜 이렇게 구성했는지, 핵심 문장을 왜 넣었는지, 주요 단어·어휘를 왜 골랐는지를 근거로 적음
- **키워드 근거**: 핵심 키워드가 왜 이것인지, 왜 다른 후보가 아닌지를 설명함
- **배치·전개 근거**: 문단·문장을 왜 이 순서로 배치하고 이 흐름으로 전개했는지, 앞 절과 뒤 절이 어떻게 이어지는지를 설명함
- 근거는 `기술이 그래서`가 아니라 `이 키워드의 판단·비교·선택에 왜 필요한지`로 씀
- 근거를 댈 수 없는 문장·단어는 존재 이유가 없으므로 삭제함
- 근거가 `일반적으로 중요하므로`, `기본이므로`처럼 뭉뚱그려지면 그 요소도 아무말이므로 다시 판단함
- **근거-본문 일치 의무**: 근거에서 핵심 키워드·판단축으로 지목한 단어는 본문(Ⅰ~Ⅶ) 어딘가에 실제로 등장해야 함. 근거만 그럴듯하고 본문에 그 축이 없으면 근거를 지어낸 것이므로, 본문을 고치거나 근거를 실제 본문에 맞게 다시 씀
- 이 블록은 검토자가 타당성을 확정하기 전에는 제거하지 않음

> 요약: 근거 블록은 선택이 아니라 필수 산출물이며, 각 문장·단어는 근거로 방어하지 못하면 지움.

## 2. 유연 골격

```markdown
---
title: "키워드명 (English Name)"
date: "YYYY-MM-DD"
tags:
  - "cspe-{area-key}"
weight: N
extra:
  question_no: "NNN"
  exam_status: "기출|미출제"
  exam_history: "123회, 128회"
  exam_note: "전망"
---

## 미리 알고가기
- [본문 이해를 방해하는 용어/기호/전제/비교표 용어 4~8개 불릿]

## 작성 근거(검토용)
- [핵심 키워드 선정 이유(왜 이 키워드인지), 절 구성·문단 배치·전개 흐름 이유, 핵심 문장·주요 단어 선택 이유를 근거로 병기 — 필수 블록]
- [문장별 5회 전수 검수 근거: 제목, frontmatter, 미리 알고가기, 작성 근거, 본문, 표 헤더·셀, 요약, 결론을 한 줄도 빠뜨리지 않고 확인했으며 어색한 단어·조사·동사 결합·장황한 명사구를 교정했음을 병기 — 필수]

## Ⅰ. 개요
- **정의/개념**: [통합 정의 1문장]
- **배경/필요성**: [왜 필요한지 1문장]

## Ⅱ. 특징
- [본 키워드 고유의 핵심 특성 3~4개 불릿]
- 비교가 아닌, 이 기술 자체의 구조적·성능적·운영적 차별점을 서술함

## Ⅲ. 종류 및 비교
- **복합 키워드**: 개별 키워드의 핵심 설명을 별도 문단 또는 불릿으로 서술 후 비교표로 정리
- **단일 키워드**: 관련 대안·기존 기술과의 비교표 또는 유형 분류표

## Ⅳ. 구성요소 및 구조
- [정적 요소, 역할, 관계를 표 또는 불릿으로]
- [요소 관계를 ASCII로 더 직관적으로 보여줄 수 있으면 표 아래에 보조 구조 도식을 추가]

## Ⅴ. 원리 및 절차 흐름도
- [알고리즘·프로토콜·처리 절차의 순서를 ASCII 흐름도 + 단계 설명]

## Ⅵ. 실무 사례
1. [적용 대상, 기술 고유 조치, 검증 지표 1~2개를 한 문장으로 합쳐 씀]
2. [필요할 때만 1개 더 추가하며, 비슷한 사례 반복은 하지 않음]

## Ⅶ. 결론
- [1문장: 핵심 선택 기준과 기술사적 판단을 회수]

```

- 위 골격과 절 순서는 유지하되 세부 작성 규칙은 본 문서 5~11절을 따름
- 상세 페이지 메타는 `extra.question_no`, `extra.exam_status`, `extra.exam_history`, `extra.exam_note`에 기록함
- `작성 근거(검토용)`는 `미리 알고가기` 바로 다음, `Ⅰ. 개요` 앞에 둠
- 예를 들어 `문제: DFS 재귀가 깊이 한계를 넘어...`와 `적용 사례: 의존성 검사는 DFS를 씀...`처럼 나누지 말고 `깊은 소프트웨어 의존 그래프는 반복 DFS로 순환을 탐지하고 최대 탐색 깊이를 확인함`처럼 합쳐 씀
- 규모가 알고리즘 선택·복잡도·용량 한계의 실제 조건이면 `대규모`를 유지하고, 단순 강조이면 삭제함. 예: `음수 가중치가 없는 대규모 그래프`가 아니라 `음수 가중치가 없는 그래프`로 씀
- 파일 분량을 줄 수로 맞추지 않음. 핵심 판단축과 필수 근거가 완결되는 데 필요한 만큼만 쓰고, 개수·분량을 채우는 표·흐름·사례는 삭제한 뒤 1-1의 반복 검수를 수행함

### 2-1. 기존 노트 전수 다듬기·인계 절차

기존 노트를 다시 다듬을 때는 개요만 수정하지 않고 파일의 첫 줄부터 마지막 줄까지 아래 순서로 확인한다. 다음 작업자나 다른 모델도 이 순서를 그대로 이어받으며, 일부 절만 확인한 파일은 완료로 표시하지 않는다.

1. **제목·frontmatter**: 제목·영문명·번호·가중치·기출 메타데이터가 파일과 일치하는지 확인함
2. **미리 알고가기**: Ⅱ~Ⅵ에서 처음 나오는 전문용어·약어·수식·전제조건이 먼저 설명되는지 확인함
3. **작성 근거 선배치**: 기존 하단 근거를 `미리 알고가기` 다음으로 옮기고, 핵심 키워드·판단축·절 전개가 실제 본문과 일치하는지 대조함
4. **Ⅰ. 개요**: 정의는 성립 조건과 기법이 하는 일을 문장으로 완결하고, 필요성은 해결 목적(`~을 위해`) 또는 대안의 실패 원인(`~하므로`)을 앞에 두고 `~필요함`으로 닫으며 해법의 동작을 미리 서술하지 않음
5. **Ⅱ. 특징**: 다른 기술과의 비교를 섞지 않고 본 키워드의 고유 특성만 3~4개로 압축함
6. **Ⅲ. 종류 및 비교**: 비교 대상·비교축·각 표 셀을 하나씩 읽고, 같은 기준에서 대조되는지와 선택 판단이 가능한지 확인함
7. **Ⅳ. 구성요소 및 구조**: 구성요소 이름·역할·관계가 정확한지 확인하고, 영문 전용 레이블·불필요한 슬래시·쉼표 나열을 한국어 중심으로 정리함
8. **Ⅴ. 원리 및 절차**: 도식·단계명·설명이 같은 순서인지 확인하고, 입력→처리→판단→출력 흐름이 끊기지 않게 함
9. **Ⅵ. 실무 사례**: 적용 대상·기술 고유 조치·검증 지표 1~2개를 한 문장에 담고, 핵심일 때만 실패 조건 하나를 추가함. 과장된 보장 표현이나 측정 불가능한 추상어는 제거함
10. **Ⅶ. 결론**: 새 내용을 추가하지 않고 앞 절의 핵심 선택 기준과 적용 조건을 1문장으로 회수함
11. **전체 용어 통일**: 개요에서 한국어로 정리한 용어가 표·도식·절차·결론에서 다시 영문으로 흔들리지 않는지 검색하고 직접 읽어 확인함
12. **배치 검증**: 10개 파일마다 필수 절·정의·필요성·근거 위치를 검사하고 `zola build` 후 해당 10개만 커밋·푸시함

인계 시에는 마지막으로 완료·푸시한 번호와 다음 시작 번호를 남긴다. 중복 번호 파일은 사용자 승인 없이 삭제·병합·이름 변경하지 않으며, 정식 파일 선택 기록을 유지한다.

## 3. 수식 및 기호 표기 (LaTeX)

- 모든 수학적 수식, 알고리즘 복잡도, 기호, 통계량은 **LaTeX($...$)** 형식을 사용하여 표기함
- **필수 적용 대상**:
  - **복잡도**: $O(n \log n)$, $O(V+E)$, $\Omega(n)$
  - **수식**: $y = \gamma \cdot \hat{x} + \beta$, $P(A|B) = \frac{P(B|A)P(A)}{P(B)}$
  - **기호**: $\alpha$, $\beta$, $\mu$, $\sigma^2$, $\Delta$
  - **비교축**: 성능/지연 시간($Latency$), 처리량($Throughput$) 등 전문 용어 병기 시 LaTeX 권장
- 단순 텍스트(`n log n`)나 코드 블록 내의 평문 표기를 지양하고, 본문과 표 안의 모든 수식은 LaTeX로 감싸 시각적 가독성을 확보함
- 수식은 문장 성분으로 억지로 붙이지 않음. `두 방식 모두 $O(V+E)$이지만`보다 `두 방식의 시간복잡도는 모두 $O(V+E)$임. 다만 ...`처럼 한글 문장으로 풀어씀

## 4. 미리 알고가기

`미리 알고가기`는 시험 답안에 쓰지 않는 노트용 선행 이해 블록이다. 본문 표·도식·활용·유의점에서 처음 등장하는 용어, 기호, 전제조건 때문에 본문 이해가 끊길 때 둔다.

- **위치**: frontmatter 바로 아래, `개요` 위
- **분량**: 기본 4~8개 불릿이며, 복합 키워드나 알고리즘 비교형은 최대 10개까지 허용함
- **내용**: 용어 뜻, 약어, 수식 기호, 전제조건, 표·비교축·주요 활용의 선행 용어
- **역추적 보강**: 본문을 쓴 뒤 Ⅱ~Ⅵ의 표·도식·활용·유의점을 훑어 처음 등장하는 전문용어를 `미리 알고가기`에 추가함
- **필수 선공개**: `무가중치 최단 경로`, `위상 정렬`, `DAG`, `안정 정렬`, `선택적 공개`처럼 독자가 멈출 수 있는 용어는 본문보다 먼저 1문장으로 풀어씀
- **기호 선공개**: $O(V+E)$처럼 변수 포함 복잡도를 쓰면 `V는 노드 수`, `E는 간선 수`처럼 기호 뜻을 `미리 알고가기`에 먼저 남김
- **문장 규칙**: 각 불릿은 `용어: 의미·판단 기준·본문 연결점`을 한 문장으로 쓰고, 두 문장으로 쪼개지 않음
- **금지**: 역사, 발명자, 논문명, 본문 핵심 논증, 실무 사례 선공개
- **금지 예시**: BFS·DFS처럼 절차가 핵심인 문맥에서 `선택 기준은 속도가 아니라 보장 결과임`처럼 엉뚱한 추상 명사로 끝내지 않음. 문맥이 요구하는 단어가 `절차`면 반드시 `절차`라고 씀

```markdown
## 미리 알고가기

- 용어 A: [본문 표·활용에서 처음 나오는 용어를 1문장으로 설명]
- 표기 B: [수식·기호의 의미와 판단 기준을 1문장으로 설명]
- 전제조건: [이 키워드의 동작 조건 또는 적용 범위를 1문장으로 설명]
```

## 5. Ⅰ. 개요

개요는 답안의 첫 판단 문장이다. 정의/개념과 배경/필요성을 포함하되, 표·불릿·짧은 문단 중 키워드에 맞는 형식을 자유롭게 선택한다.

- **정의/개념**: 핵심 개념은 `무엇을`, `무엇 기준으로`, `무엇을 판단·통제하는지`가 보이게 1문장으로 정의함
- **배경/필요성**: 해결할 목적을 `~을 위해`로 먼저 제시하고, 필요한 개념·기준·구조를 `~필요함`으로 끝내는 1문장으로 작성함
- **금지**: 역사, 발명자, 논문명, 수상 이력, 출제 의도표를 위한 출제 의도표

```markdown
- **정의/개념**: [개념의 대상·판단 기준·통제 대상]
- **배경/필요성**: [해결 목적]을 위해 [필요한 개념·기준·구조]가 필요함
```

- 정의에 피정의어를 반복하는 순환 정의 금지
- 정의를 명사구처럼 과도하게 줄이지 않음. 학습자가 처음 읽어도 개념의 대상·측정 기준·통제 대상이 잡혀야 함
- 복합 키워드나 묶음형 제목은 하위 예시를 바로 나열하지 말고, 먼저 상위 개념 자체가 무엇인지 정의한 뒤 대표 유형이나 예시를 이어서 설명함
- 정의/개념과 배경/필요성 안에서 마침표로 두 문장을 나누지 않고 원인과 필요성은 `~하므로`, `~때문에`, `~위해`로 연결해 한 문장으로 압축함
- 대표 용도, 적용 예시, 상세 동작, 장단점은 정의에 붙이지 않고 뒤 절로 보냄
- **정의와 배경의 역할 분리**: 정의는 기법이 성립하는 문제 조건과 무엇을 하는 기법인지를 담고, 배경은 그 기법이 없을 때의 실패·비용을 담음. 배경이 문제 상황을, 정의가 해법을 맡아야 두 문장이 문제 -> 해법으로 이어지고 중복이 사라짐
- 정의를 저장·재사용, 캐싱 같은 구현 메커니즘 서술로만 채우지 않음. 처리 방식의 세부는 특징·구성요소 절에서 설명함
- 배경/필요성은 해법의 동작을 미리 서술하지 않음. 정의와 배경이 같은 서술어로 끝나면 한쪽이 다른 쪽을 반복하고 있다는 신호이므로 역할을 다시 가름
- 배경에 연도·인명·논문·수상 이력 나열 금지
- 배경/필요성은 해결 목적(`~을 위해`) 또는 대안의 실패 원인(`~하므로`)을 앞에 두고 `~필요함`으로 닫음. 예: `라우팅 비용 절감을 위해 거리·비용·시간 지연이 가장 작은 경로가 필요함`
- `그래프 탐색은 정점을 방문하는 알고리즘이므로 필요함`처럼 정의를 반복하는 배경, `라우팅·물류·경로 계획은 연결 여부보다 총 비용이 작아야 하므로 가중치 기반 경로 선택 기준이 필요함`처럼 적용 분야 나열과 긴 명사구를 붙인 배경은 실패임

좋은 정의 기준:

| 나쁜 과압축 | 좋은 정의 |
|:---|:---|
| 입력 증가에 따른 실행시간·메모리 증가율 분석임 | 알고리즘이 입력 크기 `n` 증가에 따라 기본 연산을 얼마나 더 수행하고 추가 메모리를 얼마나 더 쓰는지 함수로 표현해 확장성을 판단하는 분석 기준임 |
| 데이터를 기준 순서로 재배열하는 알고리즘 군임 | 정렬은 원소를 키 기준 순서로 재배열해 탐색·병합·집계 같은 후속 연산을 가능하게 하는 알고리즘 군임 |
| 동적 계획법은 동일한 부분 문제의 답을 한 번만 계산·저장한 뒤 재사용하는 기법임 | 동적 계획법은 중복 부분 문제를 상태로 정의하고 최적 부분 구조에 따라 점화식을 세워 상태값을 저장·재사용하는 기법임 |

> 요약: 정의는 짧은 표어가 아니라 채점자와 학습자가 같은 개념을 떠올리게 하는 첫 판단 문장임.

## 6. Ⅱ. 특징

특징은 비교 없이 본 키워드 자체의 고유한 구조적·성능적·운영적 차별점을 서술하는 절이다.

- **특징 1**: 이 기술의 핵심 동작 원리에서 비롯되는 구조적 차이
- **특징 2**: 성능·품질·보안·운영 관점의 채점 포인트
- **특징 3**: 적용 조건·선택 기준·트레이드오프
- 3~4개 불릿으로 구성하며, 비교는 다음 절(Ⅲ)에서 수행함
- 특징은 뒤의 구성요소·구조·절차에서 확인 가능한 구조·동작 근거를 가져야 함
- 특징을 3개 이상 쓸 때는 0-1의 대표 핵심 선정 게이트를 적용해 각 특징이 핵심인지, 특히 네 번째부터는 지엽·중복이 아닌지 확인함

## 7. Ⅲ. 종류 및 비교

종류 및 비교는 복합 키워드의 개별 설명과 비교표, 또는 단일 키워드의 대안 기술 비교를 수행하는 절이다.

- **복합 키워드**: 개별 키워드의 핵심 설명을 별도 문단으로 서술한 뒤 비교표로 정리함
- **단일 키워드**: 관련 대안·기존 기술과의 비교표 또는 유형 분류표를 둠
- 비교 대상이 2개 이상이고 핵심 비교축 3개가 모두 실질적일 때만 표를 씀
- 비교표의 판단 기준은 정확히 3개로 제한함. 세 축으로 선택 차이를 설명할 수 없으면 비슷한 행을 늘리지 말고 더 핵심적인 축으로 교체함
- **시험 답안 압축**: 본문·절차에서 이미 설명한 세부 차이를 표에 반복하지 않음. 셀은 명사구 또는 한 줄짜리 핵심 구절로 쓰며 두 문장 이상의 서술을 금지함
- **한 셀 한 판단**: 각 셀에는 대표 핵심어 또는 짧은 구절 하나만 쓰며 여러 원인·결과·리스크를 가운데점으로 나열하지 않음
- **공학적 채점 키워드**: 정의·장점 같은 일반론보다 `동작 메커니즘`, `계산·처리 범위`, `실무 부작용·리스크`가 직접 대비되도록 세 축을 배치함
- **리스크 직접 인과성**: CPU·메모리·스택·보안 같은 시스템 리스크는 기술의 동작 메커니즘과 직접 인과관계가 있을 때만 사용함. 시스템 관점을 강조하려고 Context Switching·메모리 파편화 같은 무관한 용어를 넣지 않으며, 일반 애플리케이션 재귀의 호출 스택을 커널 스택으로 표현하지 않음
- **행·열 타당성 강제 검사**: 표를 완성한 뒤 모든 행과 열에 대해 `왜 이 주제에 필요한가`, `대상 선택이나 원리 이해에 어떤 차이를 주는가`, `뒤 절에서 무엇으로 회수되는가`를 답해야 함. 세 질문 중 하나도 답하지 못하면 해당 행·열을 삭제하거나 핵심 축으로 교체함
- **행 검사**: 각 행은 비교 대상 사이의 의미 있는 차이를 하나만 보여야 함. 두 셀의 내용이 같거나, 축명만 바꾸면 다른 주제에도 그대로 붙는 일반론이거나, 이미 다른 행에 포함된 내용이면 중복 행으로 판정함
- **중복 행 통합·삭제 검사**: 두 행이 같은 상위 질문에 답하거나 한 행이 다른 행의 세부 항목이면 먼저 하나로 통합함. 통합 셀이 길어져 판단이 흐려지면 더 핵심인 행만 남기고 나머지를 삭제함. 기준 수를 유지하려고 유사 행을 별도로 두지 않음
- 예를 들어 `주요 자료구조`와 `그래프 입력 형태`가 모두 구현 입력을 설명하면 `입력·자료구조`로 합침. 반대로 `선택 방식`과 중복되는 `선택 조건`은 새 판단을 추가하지 않으므로 삭제함
- **행 제목-셀 질문 일치 검사**: 행 제목을 질문으로 바꿔 읽었을 때 모든 셀이 그 질문에 직접 답해야 함. `선택 조건` 행에 `시작 노드에서 연결 범위를 확장할 때`처럼 동작 방식을 넣거나, `처리 비용` 행에 적용 사례를 넣으면 분석 축이 불일치함
- 행 제목이 틀렸다고 이름만 바꿔 기존 내용을 살리지 않음. 셀이 다른 행의 선택 방식·구조·사례를 반복하면 중복 행을 삭제하고, 주제 선택에 빠진 핵심 축이 있을 때만 교체함
- **열 검사**: 각 열은 독립된 기술·유형·상태를 나타내야 함. 상위 개념과 하위 기능, 원인과 결과, 기술과 적용 사례처럼 비교 수준이 다른 대상을 같은 열에 놓지 않음
- **셀 검사**: 같은 행의 셀은 동일한 문법과 분석 수준으로 대응해야 함. 한쪽은 원리이고 다른 쪽은 장점이거나, 한쪽은 수치이고 다른 쪽은 평가어이면 비교가 성립하지 않음
- **핵심 누락 검사**: 행 수가 충분해도 주제의 선택을 가르는 구조·원리·결과·적용·제약 중 필요한 축이 빠졌으면 표를 미완성으로 판정함. 기존 행을 유지한 채 개수만 늘리지 말고 우선순위가 낮은 행과 교체함
- **최소 행 원칙**: 각 행을 가리고 읽어도 선택·원리 이해가 그대로면 삭제 후보임. 남은 행끼리 상호 배타적인 질문을 만들 때까지 통합·삭제를 반복함
- **표 삭제 검사**: 표를 문장 두세 개로 바꿔도 정보 손실이 없거나 비교 대상·축이 실질적으로 하나뿐이면 표 자체를 삭제함
- 핵심 비교축은 `동작 메커니즘`, `계산·처리 범위`, `실무 부작용·리스크`를 기본으로 하며 주제 선택에 더 직접적인 축이 있을 때만 한 축을 교체함
- 시간복잡도는 알고리즘의 성능 차이가 실제 선택을 가를 때만 비교축으로 사용함. 두 대상의 값이 같거나 구조·적용 사례가 주제의 핵심이면 시간복잡도를 관성적으로 넣지 않고 입력 형태, 선택 절차, 적용 사례, 실패 조건으로 교체함
- 수식이 이미 특징이나 절차에서 충분히 설명됐으면 비교표에 반복하지 않음. 비교표의 행은 수식 전시가 아니라 대상 선택에 필요한 차이를 보여야 함
- 표의 각 축은 이후 구조·절차·실무 사례·결론 중 적어도 한 곳에서 근거·적용·검증으로 다시 이어져야 함. 뒤 절과 연결되지 않는 비교축은 개수 채우기 항목으로 판정함
- 표 헤더에 "비교 축" 같은 메타 단어를 그대로 쓰지 않음
- 비교축은 의미를 오해하지 않는 말로 씀. `직접 해결 문제`처럼 어색한 축명보다 `주요 활용`, `얻는 결과`, `적합 조건`처럼 자연스러운 표현을 사용함
- 기술·유형별 실제 쓰임이 이해를 돕는 경우 `대표 적용 사례`를 비교축으로 두고, 각 셀은 제품명 나열보다 업무·시스템·문제 유형이 드러나는 명사구나 짧은 문장으로 씀
- 선택 전제는 `맞는 상황`, `적합 상황`보다 `적합 조건`으로 쓰고, 실제 쓰임을 설명하는 `대표 적용 사례`와 혼합하지 않음
- 표준 용어가 읽기 어려우면 첫 등장에 `노드(Node, 정점)`처럼 표준어를 함께 밝힌 뒤 익숙한 용어로 통일하되, 의미가 다른 용어로 바꾸지 않음
- 표준 정의에 자주 쓰이는 말이라도 핵심 정확성에 필요하지 않고 이해만 어렵게 하면 더 직접적인 설명으로 바꿈. `부분 트리·부분 그래프`처럼 포함 관계를 강조하는 용어는 원래 그래프와의 관계가 쟁점일 때만 쓰고, MST 정의에서는 `그래프의 모든 노드를 사이클 없이 이은 트리`처럼 대상과 조건을 직접 서술함
- 용어를 뺄 때는 의미 손실을 확인함. 삭제한 단어가 나타내던 범위·관계·조건이 필요하면 쉬운 문장으로 풀어 쓰고, 뒤 절에서 이미 충분히 설명되면 반복하지 않음
- **공통 접사 묶기**: 병렬 명사의 접두사·접미사가 반복되면 의미가 모호해지지 않는 범위에서 한 번만 씀. `통신망·전력망·도로망`보다 `통신·전력·도로망`처럼 공통 접미사를 마지막 항목에 묶어 글자와 호흡을 줄임
- **서술 군더더기 축약**: `설치 비용을 최소화하기 위해`처럼 동작을 길게 풀어도 판단이 늘지 않으면 `설치 비용 최소화를 위해`로 줄임. 다만 행위 주체·시점·인과관계가 사라지면 명사화하지 않음
- **핵심 대상 용어 일관성**: 같은 문서에서 동일한 그래프 대상을 `노드`로 정했으면 `지점·정점·객체`로 임의 교체하지 않음. 첫 등장에 표준어를 병기한 뒤 정의·표·도식·절차·사례·결론에서 한 용어를 유지함
- **동일 개념 용어 일관성**: 같은 대상을 `기저 상태`로 정했으면 `기저 사례`로 바꾸지 않으며, `상태·상태값`처럼 관련 있지만 다른 개념은 관계를 먼저 정의하고 각각의 용어를 유지함
- 병렬 표현을 줄인 뒤에도 조사와 수식 범위가 모든 항목에 동일하게 적용되는지 읽어 봄. 묶은 표현이 한 항목만 꾸미는 것처럼 보이면 반복을 유지하거나 문장을 다시 배치함
- `도달 불가`처럼 서술어를 억지로 줄인 명사형 축약은 쓰지 않음. 이 문서처럼 뜻을 먼저 정의한 `단절 노드`를 사용하거나 자연스러운 문장으로 풀어 씀
- 표 안의 용어가 미리 알고가기에 없으면 표 작성 후 다시 올라가 보강함
- 최종 검수에서는 표의 헤더부터 마지막 셀까지 소리 내어 읽듯 순서대로 확인하고, 자연스러운 셀도 위 타당성 질문을 통과해야 유지함

| 판단 기준 | [대상 A] | [대상 B] |
|:---|:---|:---|
| [비교축 1] | [A의 성질] | [B의 성질] |
| [비교축 2] | [A의 특성] | [B의 특성] |
| [비교축 3] | [A의 리스크] | [B의 리스크] |

비교표와 최단 경로 문장 교정 사례는 [CSPE 답안 작성 예시집](@/exam/cs/writing-examples.md)의 비교표·요약문 예시를 참조함.

## 8. Ⅳ. 구성요소 및 구조

구성요소는 구조설계에 해당한다. 요구사항을 어떤 요소와 관계로 풀었는지 보여주되, 표·도식·불릿 중 가장 직관적인 형식을 선택한다. 순서·상태 전이·메시지 교환이 핵심인 키워드는 같은 절 안에 원리/흐름도를 함께 둔다.

- **핵심 요소 3~5개**: 실전 답안용 구성표는 개념이 성립하고 동작하는 데 필요한 대표 요소 3~5개만 남김. 개수를 맞추려고 보조 속성·구현 예를 독립 요소로 늘리지 않음
- **중복 요소 삭제**: 한 요소의 정의나 동작에 이미 포함된 항목은 별도 행으로 반복하지 않음. 예를 들어 DP의 계산 순서는 점화식의 의존 관계에 포함되므로 상태·상태값·점화식·기저 상태·저장소와 같은 필수 구조만 남김
- **명사구 한 줄 설명**: 각 셀은 시험장에서 옮겨 쓸 수 있는 명사구 또는 한 줄 핵심 구절로 쓰고, `무엇을 식별·계산·저장하는가`가 드러나는 공학 용어를 사용함
- **요소 관계는 간글로 회수**: 표 셀을 장문으로 늘리지 않고 표 아래 한 문장으로 요소의 동작 순서·관계·결과를 연결함. 이 간글은 실제 답안에 쓰는 문장이므로 주어·목적어·서술어가 완결되어야 함

```text
+----------+      +----------+      +----------+
| 입력/요구 | ---> | 핵심 구성 | ---> | 산출물   |
+----------+      +----------+      +----------+
                        |
                        v
                  +----------+
                  | 통제/검증 |
                  +----------+
```

| 구성요소 | 설명 |
|:---|:---|
| 구성 A | 입력을 핵심 처리 단위로 변환하는 요소 |
| 구성 B | 처리 결과를 다음 요소에 전달하는 연결 구조 |
| 구성 C | 결과를 저장·검증하는 통제 요소 |

> 요약: 구성요소가 요구사항을 어떤 구조로 해결하는지 1문장으로 정리함.

- 구성요소 표의 열 구성은 자유롭게 정하되 역할, 원리, 판단 기준이 보여야 하며 `핵심 포인트`를 별도 열로 기계적으로 분리하지 않음
- 설명 칸은 사전식 정의를 반복하지 않고 해당 구조에서 맡는 역할을 명사구나 한 줄 구절로 밝힘
- 구성요소 간 상하 관계, 데이터 흐름, 제어 지점을 ASCII로 그리면 이해가 빨라지는 키워드는 표 아래에 3~5블록 수준의 간단한 구조 도식을 함께 둠
- 프로토콜, 보안 핸드셰이크, 트랜잭션, 스케줄링, 데이터 파이프라인처럼 시간 순서가 답안 이해를 좌우하면 `원리/흐름도`를 둠
- 개념 분류, 성질 비교, 난이도 분류처럼 흐름으로 설명하면 오히려 억지스러운 키워드는 흐름도를 생략함
- 흐름도는 4~6단계 안에서 요청, 검증, 상태 전이, 응답, 예외 지점이 보이게 작성함
- 흐름도가 순서를 이미 설명하면 같은 내용을 단계 표로 반복하지 않음
- 비유는 필요할 때만 사용함
- 유니코드 박스 문자 금지, `+`, `-`, `|`, `v`, `>` 등 ASCII만 사용함

## 9. Ⅴ. 원리 및 절차 흐름도

원리 및 절차는 알고리즘·프로토콜·처리 절차처럼 순서가 핵심인 키워드에서 독립 절로 작성한다. 순서가 핵심이 아닌 키워드는 Ⅳ와 합칠 수 있다.

- **Ⅴ절 존재 타당성 검사**: `순서가 바뀌면 결과가 달라지는가`, `상태·데이터·제어권이 단계마다 실제로 변하는가`, `이 흐름이 해당 주제의 핵심 원리를 설명하는가`를 모두 확인함. 어느 질문에도 답하지 못하면 독립 Ⅴ절을 만들지 않음
- **단계 필요성 검사**: 각 단계는 고유한 입력·처리·판정·산출 중 하나를 가져야 함. 한 단계를 삭제하거나 앞뒤 단계와 합쳐도 원리가 그대로면 불필요한 단계로 판정함
- **전이 근거 검사**: 화살표마다 앞 단계의 산출물이 다음 단계의 입력 또는 조건이 되어야 함. 단순 나열, 생명주기 순서, 작성자가 임의로 붙인 업무 순서는 원리 흐름으로 인정하지 않음
- **주제 고유성 검사**: 단계명을 다른 키워드에 그대로 붙일 수 있으면 일반 템플릿 문구임. `입력 식별 -> 핵심 처리 -> 검증 -> 결과 반환`을 내용 없이 복사하지 말고 실제 연산·상태·메시지·판정명을 사용함
- **중복 검사**: Ⅳ의 구조 도식이나 구성요소 설명과 같은 관계를 반복하면 Ⅴ절을 삭제하거나 Ⅳ에 통합함. 흐름도와 번호 단계도 동일 문장을 반복하지 않고, 도식은 관계를 보여주고 단계 설명은 판정 조건과 상태 변화를 보완함
- **핵심성 우선**: 모든 문서에 Ⅴ절을 채우는 것보다 핵심 원리가 없는 흐름도를 생략하는 것이 우선임. 분류·비교·정의가 중심인 주제는 비교표와 구조 설명만으로 완결할 수 있음
- **전수 교정 방식**: 과목 단위 점검에서는 표본 문서만 보지 않고 001번부터 마지막 번호까지 모든 Ⅴ절을 순서대로 읽어 `유지·교정·Ⅳ절 통합·삭제` 중 하나로 판정함. 자연스럽다는 이유만으로 유지하지 않고 위 타당성 검사를 통과한 경우에만 그대로 둠
- **복합 주제 검사**: 여러 알고리즘·기술을 다루는 문서에서 실제 반복 기준과 상태가 다르면 하나의 공통 흐름으로 뭉개지 않음. 알고리즘별 고유 흐름을 나누거나 비교표만 남김
- **교정 완료 조건**: 도식의 단계명, 번호 단계의 설명, 요약문이 같은 원리를 가리키고 예외·종료 조건까지 모순이 없어야 해당 문서의 Ⅴ절 점검을 완료함

```text
+----------+      +----------+      +----------+      +----------+
| 입력식별 | ---> | 핵심처리 | ---> | 검증/통제 | ---> | 결과반환 |
+----------+      +----------+      +----------+      +----------+
```

위 도식은 형식 설명용이며 실제 답안에 단계명 그대로 복사하지 않음. 각 칸은 해당 주제의 실제 연산·메시지·상태·판정으로 바꿔야 함.

> 요약: 입력이 어떤 처리·검증을 거쳐 결과가 되는지 1문장으로 정리함.

- 흐름도가 순서를 이미 보여주므로 단계 표를 반복하지 않음
- 단계 수를 4개로 맞추지 않음. 핵심 전이가 3개면 3개만 쓰고, 예외·응답까지 5개가 필요하면 5개를 사용함
- 구현 세부는 필요한 만큼만 쓰고, 주변 기술 나열로 흐름을 흐리지 않음

## 10. Ⅵ. 실무 사례

실무 사례는 실제 적용 대상을 중심으로 예전의 `문제점 및 해결방안`과 `적용 사례`를 합친 절이다. `적용 대상 -> 기술 고유 조치 -> 검증 지표 1~2개` 순서로 쓰고, 실패 조건이 기술 선택을 바꿀 때만 한 개를 추가한다.

```markdown
1. [적용 대상 + 기술 고유 조치 + 검증 지표 1~2개]
2. [필요할 때만 1개 더 추가]
```

> 요약: 현장 적용 대상과 검증 포인트를 1문장으로 정리함.

- "운영 어려움", "보안 취약", "성능 저하"처럼 모든 기술에 붙는 일반론 금지
- 항목은 구성요소·절차·적용 조건에서 논리적으로 도출돼야 함
- CSPE 키워드 노트의 실무 사례는 보통 **1~2개**면 충분하며, 한 사례로 적용 판단이 완결되면 개수를 채우려고 늘리지 않음
- `문제:`와 `해결방안:`을 따로 나누지 않음. 같은 내용이 반복되기 쉬우므로 한 문장으로 합침
- 상세한 실무 사례 교정은 [CSPE 답안 작성 예시집](@/exam/cs/writing-examples.md)의 실무 사례 예시를 참조함
- 제품명·회사명 홍보가 아니라 도메인, 시스템 유형, 운영 조건을 기준으로 씀
- **CSPE 직무 적합성**: 컴퓨터시스템응용기술사 답안이므로 서버·CPU·메모리·스토리지·클러스터·데이터센터·운영체제·미들웨어·데이터베이스·소프트웨어·응용 플랫폼의 설계·운영 사례를 우선함
- 통신사업자의 회선 구축, 이동통신 커버리지, 도로·배관·전력 인프라 설계처럼 다른 기술사 직무가 중심인 사례는 해당 개념의 유일한 대표 사례가 아니면 사용하지 않음. 필요하면 클러스터 연결, 시스템 의존성, 스토리지 경로, 응용 처리 사례로 바꿈
- **짧은 사례 문장**: `적용 대상 -> 핵심 조치 -> 검증 지표`만 남김. 실패 조건이 핵심일 때만 한 개를 추가하며 배경 설명, 장황한 원인, 여러 대응을 한 문장에 모두 넣지 않음
- 분류와 예측, 신규 구축과 증설처럼 적용 조건·평가 지표가 다른 대상을 한 사례에 묶지 않음. 사례 하나에는 하나의 적용 대상과 하나의 판단 맥락만 두고 필요하면 두 사례로 분리함
- 한 사례에 지표를 나열하지 않음. 핵심 효과를 직접 확인하는 1~2개 지표를 우선하고, 서로 다른 검증 목적이면 사례를 분리하거나 덜 중요한 지표를 삭제함
- 사례 문장을 읽은 뒤 기술 이름을 다른 것으로 바꿔도 그대로 성립하면 일반론으로 판정함. 해당 기술의 구조·선택 기준이 조치나 지표에 직접 나타나야 함
- 비교표의 모든 대상을 다시 나열하지 않고, 가장 대표적인 1~2개만 남김
- `대규모`, `고성능`, `효율적`처럼 판단에 영향을 주지 않는 강조어는 삭제하고, 입력 규모·처리량·메모리 한계처럼 선택 기준이 달라질 때만 구체적 조건으로 씀

## 11. Ⅶ. 결론

결론은 **1문장**으로 핵심 선택 기준과 기술사적 판단을 회수한다.

- 당위만 있는 도덕적 문장 금지
- 앞 절의 특징과 실무 판단을 한 줄로 회수함
- 새 문제를 결론에서 갑자기 만들지 않음
- 공허한 미래 예측, 장황한 2~4문장 금지

## 12. 표와 불릿 판단

- **비교표 사용**: 2개 이상 대상 × 정확히 3개 비교축이 있을 때
- **불릿 사용**: 정의, 배경, 특징 3개, 절차 단계, 실무 사례, 결론
- **불릿 금지**: `보장 결과`, `핵심 효과`, `운영 가치`처럼 뜻이 넓은 명사로 판단을 끝내지 않음. 문맥상 `절차`, `구조`, `조건`, `비용`, `검증 지표` 중 무엇인지 자기점검 후 씀
- **표 요약**: 표 바로 아래 빈 줄 1개 뒤 `> 요약:`을 붙이며, 실제 답안의 간글로 옮길 수 있는 완결 문장으로 작성함
- **요약 문장 품질**: 표의 핵심 대상을 주어로 두고 `요소 관계·동작 메커니즘 -> 산출 결과·효과`를 한 문장으로 연결함. 셀을 순서 없이 나열하거나 `효율성을 극대화함`처럼 근거 없는 효과로 끝내지 않음
- **요약 선행 근거 검사**: 요약은 실제 답안에 쓰는 간글이지만 누락된 핵심을 보충하는 자리가 아님. 요약의 각 주장·선택 기준·원리·제약은 바로 위 본문·표·도식에 먼저 명시되어야 함
- **요약 삭제 검사**: 모든 `> 요약:`을 가린 상태로 문서를 읽어도 핵심 선택과 기술 원리가 그대로 보여야 함. 요약을 지웠을 때 핵심이 사라지면 요약이 좋은 것이 아니라 상단 본문이 미완성인 것임
- 상단 요소가 핵심을 은근히 암시하고 요약에서만 직접 말하는 구성을 금지함. 표 셀도 `전체 간선 정렬 후 사이클 없는 간선 선택`, `현재 트리와 외부 노드를 잇는 최소 간선으로 확장`처럼 동작과 조건을 직접 씀
- 요약에 처음 등장한 단어·판단·예외는 위 절로 올리고, 이미 위에서 충분히 드러난 내용만 짧게 재진술함. 요약을 근거로 본문 누락을 정당화하지 않음
- **표 남발 금지**: 한 파일의 표는 대개 `출제 의도`, `Ⅱ 특징/비교`, `Ⅲ 구성요소` 정도면 충분함

## 13. 표현 금지와 치환

| 금지 표현 | 답안 표현 |
|:---|:---|
| 성능이 좋다 / 빠르다 | p95/p99 지연, 처리량, 병목 제거, 복잡도 감소 |
| 안정적이다 | 장애 격리, 자동 복구, RTO/RPO, MTTR |
| 보안이 강화된다 | mTLS, RBAC, AES-256, 감사 로그, 취약점 스캔 |
| 효율적이다 | 자동화, 표준화, 배포 시간, CPU/메모리 사용량 |
| 확장성이 있다 | 수평 확장, 샤딩, 오토스케일링, 파티셔닝 |
| 품질이 향상된다 | 결함밀도, 테스트 커버리지, 정적 분석, 리뷰 기준 |
| 막다 / 막음 | 오류·위반은 방지, 공격·패킷은 차단, 경쟁·확산은 억제, 영향은 완화, 권한·범위는 제한, 상태는 검증 |

- 수치가 없으면 표준명·기술명·구체 메커니즘으로 특정함
- 억지 수치화도 금지함. 기준은 "수치 여부"가 아니라 "구체적이고 검증 가능한가"임
- `막다`는 물리적 차단처럼 의미가 분명한 경우가 아니면 쓰지 않음. 대상과 메커니즘을 확인해 `방지`, `차단`, `억제`, `완화`, `격리`, `통제`, `제한`, `검증` 중 하나로 좁힘

전수 어휘 검수 절차와 판별표는 [CSPE 답안 작성 예시집](@/exam/cs/writing-examples.md)의 어휘 검수 예시를 참조함.

## 14. 모호 표현 금지

- 주어·목적어·동사를 명시함
- 모든 명사·동사·형용사·부사·수식어는 기술 정의, 비교 기준, 측정 지표, 인과관계, 절차 순서 중 하나로 근거를 제시할 수 있어야 함
- 근거 없는 평가·강조를 만드는 수식어와 형용사는 문장 의미를 부드럽게 보이게 하더라도 사용하지 않음
- `A·B 제거`처럼 제거 대상이 모호한 압축 표현 금지
- `인증·인가 통제`처럼 역할이 다른 용어를 한 동사에 묶지 않음
- `무엇을 막음`처럼 목적어와 제어 방식이 뭉개진 문장 금지
- 감점 회피 포인트는 이중 부정 대신 명사형으로 씀

모호 표현의 구체적인 교정표는 [CSPE 답안 작성 예시집](@/exam/cs/writing-examples.md)의 모호 표현 예시를 참조함.

## 15. 키워드 유형별 해석

절 제목은 키워드 성격에 맞게 바꿀 수 있다. 다만 개요, 특징/비교, 구조/원리, 실무 사례, 결론의 역할은 유지한다. 유형은 폴더가 아니라 키워드 성격으로 판단한다.

| 유형 | 해당 예 | 판단 기준 |
|:---|:---|:---|
| 기술형 (기본) | 알고리즘, 프로토콜, 아키텍처, 신기술 | 아래 해석 없이 본 문서 5~11절 그대로 적용함 |
| 법·제도·정책형 | 07 영역 대부분, 개인정보보호법, ISMS-P | 법률·고시·인증제도·정책 자체가 키워드임 |
| 평가·지표형 | 06 영역 대부분, BMT, TPC, 신뢰성 지표 | 평가 방법·지표·산식이 키워드임 |
| 비교형 | "A vs B" 형태 제목 | 두 대상을 어떤 기준으로 나눠 판단해야 하는지 보여주는 유형임 |

**법·제도·정책형 해석:**

- **특징/비교**: 이전 제도, 유사 제도, 해외 제도 대비 차별점과 적용 범위 차이를 씀
- **구성요소/구조**: 조문 나열이 아니라 적용 대상, 의무 주체, 추진·감독 체계, 인증·심사 체계를 구조로 씀
- **절차/동작 원리**: 기술 동작이 아니라 신고·인증·심사·이행점검 등 제도 이행 절차를 씀
- **실무 사례**: 적용 범위 공백, 실무 이행 부담, 중복 규제, 판단 기준 모호성 같은 제도 운영상 한계와 기업·기관의 이행 절차, 인증·신고·감사 대응, 운영 문서화 사례를 함께 연결함
- **결론**: 개정 동향, 국제 규제·표준과의 정합성, 실무 대응 우선순위를 씀
- 금지: 조문 전문 인용, 제정·개정 연혁 나열, 법령 명칭만 바꾼 일반론

**평가·지표형 해석:**

- **특징/비교**: 대안 평가 방법·지표 대비 측정 대상과 신뢰 수준 차이를 씀
- **구성요소/구조**: 평가 항목, 지표 정의, 산식, 측정 환경 요건을 구조로 씀
- **절차/동작 원리**: 평가 계획 -> 환경 구성 -> 측정 수행 -> 분석·판정 흐름으로 씀
- **실무 사례**: 지표 왜곡 가능성, 측정 환경 편차, 재현성 부족 같은 한계와 벤치마크, 인증, 용량 산정, 운영 모니터링에서 무엇을 확인하는지 함께 씀

**비교형 해석:**

- **특징/비교**: 이 절이 답안의 중심이어도 판단 기준은 핵심 비교축 3개로 제한하고 세부 근거는 특징·구조·절차로 분산함
- **구성요소/구조 또는 절차**: 두 대상의 구조·동작 차이가 드러나는 지점 중심으로 씀. 각각을 전부 나열하지 않음
- **실무 사례**: 잘못된 선택·오적용 시나리오와 상황별 선택 기준, 하이브리드 적용 방안, 대표 업무·시스템 조건을 함께 씀
