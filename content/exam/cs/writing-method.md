# 합격후기 기반 답안 작성법

컴퓨터시스템응용기술사는 지식량보다 **출제자 의도에 맞는 핵심을 선별하고, 400분 동안 채점자가 읽을 수 있는 구조를 반복 생산하는 능력**이 더 중요하다. 공개 합격후기와 기술사 답안 작성법을 종합하면, 합격권 답안의 공통점은 다음 다섯 가지다.

1. 출제기준과 기출을 먼저 큰 가지로 잡는다.
2. 문제 신호어에서 출제 의도·반드시 짚을 핵심·감점 회피 포인트를 먼저 고정한다.
3. 같은 답안을 1교시는 `Ⅰ~Ⅲ`에서 멈추고, 2~4교시는 `Ⅳ~Ⅵ`까지 밀어붙인다.
4. 2~4교시는 3쪽 내외를 끝까지 채우는 훈련을 한다.
5. 실전 답안은 표와 짧은 단계 흐름을 기본으로 하고, 깨지는 박스형 ASCII 대신 선형 텍스트 도식을 사용한다.

## 0. 대전제 — 이 시험은 논리 시험이다 (템플릿은 틀이 아니라 흐름의 뼈대)

> **템플릿(Ⅰ~Ⅵ)은 큰 흐름을 잡아주는 뼈대일 뿐, 모든 칸을 빠짐없이 채우라는 틀이 아니다.** 주제와 문제가 요구하는 만큼만 쓰고, 요구하지 않는 칸은 비운다. 이 대전제를 어기면 세부 규칙(Ⅰ~Ⅶ)을 다 지켜도 심사위원 의도에 안 맞는 답안이 된다.

- **논리의 연속**: 답안은 정보 모음이 아니라 하나로 이어지는 논리다. 문제 제기 → 전개 → 핵심 판단 → 결론이 자연스럽게 흐르고, 읽는 심사위원을 **설득**해야 한다.
- **핵심만, 장황성 0**: 주제의 핵심이 드러나야 한다. 곁가지·배경 나열로 분량을 늘리지 않는다.
- **반복 0**: 앞에서 한 말을 문구만 바꿔 되풀이하지 않는다. 각 문장·각 절은 새 정보를 더한다.
- **심사위원 의도 기준**: "이 문제가 무엇을 묻는가"에 답한다. 문제가 묻지 않은 것을 아무리 깊이 써도 점수가 아니다.
- **주제·문제가 깊이를 정한다**: 문제가 요구하는 깊이까지만 판다. 문맥상 불필요한데 미친 듯이 딥한 세부(내부 알고리즘, 극단 수치, 주변 기술)를 꺼내 답안 복잡도를 올리지 않는다.
- **수치는 필요할 때만**: p95·TPS 같은 지표는 문맥상 실제로 필요할 때만 쓴다. 전문성 과시용으로 억지로 끼워 넣으면(오버) 오히려 감점이다. → `Ⅳ` 참조.

## Ⅰ. 취득 후기에서 뽑은 실전 원칙

| 후기/작성법 공통점 | 시험 문서 반영 방식 |
|:---|:---|
| 암기 중심에서 이해·작성·커버리지 중심으로 전환해야 점수가 오른다 | 키워드를 외우는 문서와 서술형 답안 템플릿을 분리 |
| 기출을 출제기준 기간 단위로 묶어 경향을 본다 | 2023~2026 출제기준 축에 AI, 보안, 클라우드, SW, DB를 재배치 |
| 정보를 많이 나열하는 답안은 합격 답안이 아니다 | 답안 초반에 출제 의도·핵심 포인트·감점 회피 포인트 표를 배치 |
| 1교시 10문제와 2교시 4문제 분량을 실제 답안지로 채우는 훈련이 필요하다 | 1교시는 `Ⅰ. 개요 + 핵심 3포인트 + 미니 도식 + 적용 1줄` 기준의 `2/3~1쪽`, 2~4교시는 3쪽 내외 템플릿으로 고정 |
| 답안은 서론-본론-결론이 아니라 채점용 목차·표·도식으로 읽혀야 한다 | Ⅰ~Ⅵ 목차, 선형 구조도 1개, 선형 흐름도 1개, 심화 판단 표(대조 축이 있는 곳만, 기본 2~3개·하한 아님), 결론 2줄을 기본값으로 설정 |
| 포괄형 문제와 요구사항 명시형 문제는 목차 구성이 달라야 한다 | 문제 유형별 치환표를 사용 |

## Ⅱ. 단일 답안 모델

| 1교시 단답 요소 | 2~4교시에서 쓰는 위치 | 예시 |
|:---|:---|:---|
| 개요 1문장 | Ⅰ. 개요 첫 줄 | "RAG는 검색 결과를 생성형 AI 프롬프트에 결합하는 아키텍처이다" |
| 구성요소 3개 | Ⅱ. 구조 및 구성요소 표 | Retriever, Vector DB, Generator |
| 동작 흐름 | Ⅲ. 동작원리 및 흐름도 | 문서 적재 -> 검색 -> 프롬프트 보강 -> 생성 |
| 장점·한계 | Ⅳ. 특징 표 | 최신성 확보 vs 검색 품질 의존 |
| 적용 포인트 | Ⅵ. 실무 적용 방안 | 권한 필터링, 평가 자동화, Guardrail |
| 향후 방향 | Ⅵ. 결론 | Agentic RAG, 기업 지식 거버넌스 |

즉 1교시는 `Ⅰ. 개요 + Ⅱ. 구조 및 구성요소 + Ⅲ. 동작원리 및 흐름도`까지만 쓴 압축판이고, 2~4교시는 그 답안을 `Ⅳ. 특징`, `Ⅴ. 심화 비교 및 적용 판단`, `Ⅵ. 실무 적용 및 결론`까지 확장한 형태다. 차이는 답안 종류가 아니라, 같은 답안을 어디까지 쓰느냐에 있다.

2~4교시 정본 골격은 [모범답안 템플릿](@/exam/cs/model-answer.md)의 `Ⅰ. 개요 / Ⅱ. 구조 및 구성요소 / Ⅲ. 동작원리 및 흐름도 / Ⅳ. 특징 / Ⅴ. 심화 비교 및 적용 판단 / Ⅵ. 실무 적용 및 결론`을 따른다.

## Ⅲ. 2~4교시 페이지 구성

| 쪽 | 쓰는 내용 | 실제 행동 |
|:---|:---|:---|
| 1쪽 | Ⅰ 개요 + Ⅱ 구조 및 구성요소 | 개요 불렛 후 선형 구조도 + 구성요소 표 작성 |
| 2쪽 | Ⅲ 동작원리·흐름도 + Ⅳ 특징 | 흐름도·단계 표와 특징(비교) 표로 채점 포인트를 보이게 함 |
| 3쪽 | Ⅴ 심화 판단 + Ⅵ 실무 적용·결론 | 비교·리스크·지표 판단 후 단계별 방안과 조건부 결론으로 마무리 |

### 25분 운용

| 시간 | 작업 |
|:---:|:---|
| 0~2분 | 6문제 중 쓸 4문제 선택, 목차 키워드만 적기 |
| 2~5분 | Ⅰ 개요와 구조도 뼈대 작성 |
| 5~11분 | Ⅱ 구조·구성요소 표 작성 |
| 11~16분 | Ⅲ 동작원리·흐름도·단계 표 작성 |
| 16~19분 | Ⅳ 특징(비교) 작성 |
| 19~23분 | Ⅴ 심화 판단(비교·리스크·지표) 작성 |
| 23~25분 | Ⅵ 적용 방안·결론, 빠진 요구사항 보완 |

구조도는 `Ⅰ. 개요` 직후에 핵심 요소 3~5개 뼈대만 먼저 그리고(손답안에서는 박스 도형 가능, 노트에서는 선형 텍스트), 자세한 설명은 `Ⅱ. 구조` 표와 `Ⅲ. 동작원리` 단계 표에서 채운다.

## Ⅳ. 추상 표현을 줄이는 치환 규칙

> 이 표가 추상 표현 치환의 **유일 원본**이다. 다른 문서(AGENTS.md·model-answer.md)는 이 표를 링크로 참조하고 사본을 두지 않는다.

| 추상 표현 | 시험 답안 표현 |
|:---|:---|
| 성능이 좋다 / 빠르다 | p99 지연 50ms 이하, 처리량 10,000 TPS, 캐시 적중률 95%, 병목 제거 |
| 안정성이 높다 / 신뢰성이 높다 | 장애 격리, 자동 복구, RTO 4분·RPO 15분, 가용성 99.9%, MTTR 10분 |
| 보안이 강화된다 | AES-256, mTLS, RBAC 접근통제, 로깅·감사, CVE 스캔 자동화 |
| 보안 위협을 대응한다 | MITRE ATT&CK TTP 매핑, 탐지 규칙 ID, 대응 플레이북 |
| 운영이 편하다 / 효율적이다 | 자동화, 표준화, 관측성, 배포 롤백, CPU 70%→40%, 배포 45분→8분 |
| 확장성이 있다 | 수평 스케일아웃, HPA min2/max20, 오토스케일링 30초 반응 |
| 비용을 줄인다 | 리소스 우측정, 오토스케일링, 예약/스팟, FinOps 태깅 |
| 품질이 향상된다 | 결함밀도 2.1→0.8/KLOC, 테스트 커버리지 40%→80% |
| 최신 기술이다 | 기존 방식의 한계 + 신기술이 해결하는 수치를 함께 명시 |

**규칙: 막아야 할 것은 *빈 추상 표현*이지, *비수치 서술*이 아니다.**

- **금지**: 검증 불가능한 공허한 형용사·부사("성능이 좋다", "안정적이다", "효율적이다") — 무엇이·얼마나·어떤 조건에서인지 없는 문장.
- **대체는 상황에 맞게**: ① 실측 지표가 있으면 수치(p95, TPS, RTO), ② 지표가 없으면 표준명·기술명·구체 메커니즘·구조적 성질로 특정한다.
- **모든 문장을 수치로 강제하지 않는다**: 정량화가 불가능하거나 무의미한 내용(설계 원칙, 트레이드오프 방향, 동작 원리, 구조적 특성)은 **구체적·검증 가능한 서술**이면 충분하다. 예: "결합도를 낮춰 독립 배포가 가능함", "장애를 서비스 단위로 격리함" — 숫자가 없어도 검증 가능한 기술적 사실이다.
- **판단 기준**: "수치인가"가 아니라 **"구체적이고 검증 가능한가"**. 억지 수치화는 빈 추상만큼 감점이다.

## Ⅴ. 의미 반전·모호 표현 방지 규칙

시험장에서 피로한 상태로 읽을 때, **반대 의미로 오독될 수 있는 압축 표현**은 오답보다 위험하다. 아래 패턴을 감지하면 즉시 풀어 쓴다.

### 원칙: 주어·목적어·동사를 명시한다

| 금지 패턴 | 위험 | 수정 방식 |
|:---|:---|:---|
| `A·B 제거` | A를 제거하는 건지, B를 제거하는 건지, 둘 다 제거하는 건지 불명 | **제거 대상**과 **잔존 대상**을 분리해 쓴다 |
| `A·B 생성/처리/변환` | A가 주체인지 대상인지 불명 | 주어를 명시한다: "A가 B를 생성" |
| `A 기반 B` | A 위에 B를 올린 건지, A를 B로 바꾼 건지 불명 | 관계를 풀어 쓴다: "A를 입력으로 B를 산출" |
| `A와 B로 통제/관리/처리` (역할이 다른 명사 나열) | A(수단)와 B(기록·결과물)를 동급 수단처럼 묶어 어색함 | 각자의 동사를 살려 분리: "A로 검증하고 B로 기록" |

### 실제 오류 사례와 교정

| 원문 (오독 가능) | 오독 방향 | 교정문 |
|:---|:---|:---|
| 최고차항·상수 제거 | "최고차항을 제거한다" (실제는 반대) | 하위 항·계수 제거, 최고차항만 잔존 |
| 암호화·복호화 처리 | 둘 다 하는 건지, 하나만 하는 건지 불명 | 평문을 암호화하여 전송, 수신 측이 복호화 |
| 인증·인가 통제 | 인증이 통제하는 건지, 인증을 통제하는 건지 | 인증으로 신원 확인 후 인가로 권한 부여 |
| 정책과 로그로 통제함 | 로그(기록)를 정책(통제 수단)과 같은 층위로 묶어 어색함 — 로그는 통제 수단이 아니라 결과 기록 | 정책 검증을 거치고 결과를 로그로 남김 |

### 이중 부정 금지 — "피해야 할 것"은 명사형으로

- 감점 회피 포인트처럼 **"피해야 할 실수"를 적는 칸은 실수 자체를 명사형으로** 쓴다: "비용 동인 누락", "단 수 증가를 성능 향상으로 단정".
- **"~하지 않음" 형태 금지**: "비용 동인을 누락하지 않음"은 피로한 상태에서 "누락함"으로 오독되고, 칸의 의미(실수인지 지침인지)도 모호해진다.

### 자가 검증 질문 (문장 작성 후 반드시 확인)

1. **이 문장에서 주어는 무엇인가?** -> 주어가 없으면 추가한다.
2. **'제거/생성/변환'의 대상은 무엇인가?** -> 목적어가 없으면 추가한다.
3. **반대로 읽어도 문법적으로 성립하는가?** -> 성립하면 모호한 것이므로 풀어 쓴다.
4. **피로한 상태에서 3초 안에 뜻이 하나로 확정되는가?** -> 아니면 재작성한다.

## Ⅵ. 답안 품질 절대 규칙 — 채점자 오해 0건

> **이 섹션은 모든 CSPE 키워드 노트·답안 템플릿에 적용되는 최상위 규칙이다.**
> 채점자가 "이 사람 이해를 못 한 것 같은데?"라고 느끼는 순간 감점이다. 내용에 흠이 있어서는 안 된다.

### 기술적 정확성

- **사실 오류 0건** — 프로토콜명·알고리즘 복잡도·표준 번호·수치가 틀리면 즉시 감점이다. 불확실하면 쓰지 않는다.
- **인과 방향** — "A가 B를 야기한다"를 반대로 쓰면 이해 자체를 의심받는다. 원인->결과 방향을 반드시 검증한다.
- **범위 한정** — "모든", "항상", "반드시"는 반례 하나로 무너진다. "일반적으로", "N 이상일 때" 등 조건을 명시한다.
- **용어 혼동** — 유사 용어(인증/인가, throughput/latency, 단위 행렬/유니터리 행렬)를 섞으면 이해도를 의심받는다.
- **순환 정의 금지** — "AI 워터마킹은 AI 생성물 식별을 위한 워터마킹 기술이다"처럼 정의에 피정의어를 되풀이하면 이해 없이 베낀 인상을 준다. 정의 1문장에는 **메커니즘(어떻게)과 차별점(무엇과 다른가)**을 담는다.

### 핵심 집중 — 채점 근거 없는 문장 삭제

> **심사위원은 "이 문제가 왜 출제됐고, 무엇을 확인하려는가"를 기준으로 채점한다.** 출제 의도와 무관하게 배경지식을 나열하거나, 같은 말을 다른 표현으로 반복하는 문장은 분량만 늘릴 뿐 점수에 기여하지 않는다 — 오히려 "핵심을 못 짚었다"는 인상을 준다.

- **문장 자가검증**: 각 불렛을 쓴 뒤 "이 문장이 없으면 채점 포인트(정의·수치·비교 기준·리스크·판단 근거)가 하나라도 빠지는가?"를 묻는다. 아니라면 삭제한다.
- **일반론 금지**: "~이 중요하다", "~에 활용된다", "~을 고려해야 한다"처럼 수치·기준·조건이 없는 문장은 감점 대상이다. 반드시 무엇을·얼마나·어떤 조건에서인지 채운다.
- **동어반복 금지**: 정의·배경·필요성이 같은 내용을 단어만 바꿔 반복하면 안 된다. 정의=본질 1문장, 배경=이 개념이 필요해진 원인/한계, 필요성=적용 시 수치·기준으로 각각 다른 정보를 담는다.
- **분량보다 밀도**: 불렛 개수를 늘리는 것이 목표가 아니다. 각 불렛은 서로 다른 채점 포인트(정의/구조/비교/리스크/적용)를 담당해야 하며, 같은 포인트를 여러 불렛으로 쪼개 분량만 채우면 안 된다.

### 논리 전개 — 기승전결, 위키식 나열 금지

> **답안은 사실을 병렬로 쌓는 위키가 아니다.** 문제 제기에서 시작해 판단으로 끝나는 하나의 논리 흐름(기승전결)이 있어야 점수가 된다.

- **흐름 강제**: 개요(문제 제기, 기) → 구조·원리(전개, 승) → 비교·심화 판단(핵심 논점, 전) → 적용·결론(판단, 결). 각 절은 **앞 절을 딛고 다음 판단으로 전진**한다. 사실을 순서 없이 나열하지 않는다.
- **절마다 전진**: 각 절은 앞 절에 **없던 정보를 더한다.** 앞 절에서 한 정의·서술을 문구만 바꿔 다음 절에서 반복하면 감점이다.
- **같은 정의 재등장 금지**: [핵심 인사이트 본질]·[Ⅰ 정의]·[Ⅱ 구성요소]·[Ⅳ]에 같은 정의 문장이 되풀이되지 않게 한다. 각 자리는 서로 다른 관점(본질/개요/구성/특징)을 담는다.
- **중복 허용 예외**: ⓐ 표 아래 `> 요약:` 한 줄, ⓑ 명시적으로 다른 축·관점에서 재조명하는 문장, ⓒ 결론의 판단 요약. 이 셋 외의 반복은 삭제한다.
- **암기용↔답안용은 예외**: 두 블록은 목적(이해 vs 시험 양식)이 달라 같은 개념을 다뤄도 된다. 단 답안용 **Ⅰ~Ⅵ 내부**에서는 반복을 금지한다.

### 문체·포맷 규칙 — 불렛 포인트 필수

> **답안용 모든 서술은 문장 단위 `- 불렛`으로 쓴다.** 줄글 문단 금지.
> 시험 답안지에 옮겨 쓸 때도 불렛 단위로 빠르게 쓸 수 있어야 한다.

> **판정 기준: 한 문단(또는 한 항목 설명)에 문장이 2개 이상 이어지면 무조건 불렛으로 쪼갠다.** 줄 수·글자 수가 아니라 "문장이 몇 개 연속되는가"로 판단한다. 개요뿐 아니라 구성요소·특징·비교·적용방안 등 모든 서술 항목에 동일하게 적용한다.

| 금지 | 필수 |
|:---|:---|
| 줄글 문단으로 개요·배경·필요성·특징·적용방안 서술 | 문장 단위 `- 불렛`으로 분리 |
| 한 항목 설명에 문장이 2개 이상 연속 | 문장 수만큼 불렛을 나눈다 (2문장 -> 불렛 2개) |
| 접속사(`~하며`, `~하고`, `~때문에`)로 여러 문장을 이어 붙인 복합문 | 접속사를 끊어 한 불렛 = 한 문장 = 한 가지 사실로 분리 |
| 한 파일 안에서 종결어미 혼용 ("~함"과 "~한다" 혼재) | 답안용은 **개조식 명사형 종결(~함/~임/~필요)로 파일 내 통일** |

**✅ 올바른 예 (Ⅰ 개요):**
```
- 개요: 입력 n에 따른 자원 증가율
- 선택 기준: 기능 동일 시 n 증가에 따른 연산량·메모리 증가율 차이로 결정
- 필요성: O(n^2) 설계는 n=10^6에서 SLA p95 200ms 초과 -> 사전 복잡도 분석 필수
```

**❌ 금지 예 (Ⅰ 개요):**
```
입력 n에 따른 자원 증가율이다. 알고리즘 선택은 기능 동일성보다 n 증가 시
연산량·메모리 증가율 차이가 좌우한다. 대용량 로그·추천·검색 시스템에서는
O(n^2) 설계가 SLA p95 200ms를 초과할 수 있어 사전 복잡도 분석 필요.
```

### Ⅰ. 개요 작성법 (구체)

```markdown
## Ⅰ. 개요 및 필요성

- 개요: [본질 1문장, 30자 내외]
- 배경: [기존 한계 또는 등장 이유]
- 필요성: [이 기술이 해결하는 문제 + 수치/기준]
```

- 개요 전체 3~4줄(불렛 3~4개)
- 개요 1문장(정의)은 30자 내외 — 정의는 짧게, 부연은 별도 불렛으로 (순환 정의 금지: "X는 X를 위한 기술" 식 동어반복 대신 메커니즘·차별점을 담는다)
- 배경·필요성도 각 1줄씩 불렛으로
- **줄글 문단으로 쓰지 않는다**

## Ⅶ. 표·불릿·구성 판단 규칙

> **답안 구성은 정해진 개수를 채우는 것이 아니라, 내용에 맞는 형식을 고르는 것이다.** 표를 남발하면 가독성·직관성이 떨어져 오히려 감점 요인이 된다. "표 N개 이상" 같은 하한선은 두지 않는다.

### 표 vs 불릿 판단 기준

> **의심되면 불릿이 기본이다.** 표는 "여러 대상을 여러 축으로 나란히 비교"할 때만 가독성을 높인다. 그 외에는 대부분 표가 오히려 핵심을 흩뜨린다.

- **표를 쓴다**: 2개 이상의 **대상**을 2개 이상의 **축**으로 대조할 때. 행과 열이 **둘 다** 실질 의미를 가질 때다(예: 비교축 × 2개 이상 대상, 구성요소 × 속성).
- **불릿을 쓴다(기본)**: 단일 축 나열, 순차 설명(순서·단계), 항목 3개 이하, 정의·배경·필요성·적용 방안·결론 같은 서술.
- **금지**: 개수를 채우려고 억지 열을 만드는 것(특히 값이 대부분 비슷해지는 '확인 지표' 열), 순서·나열이면 충분한 내용을 표로 부풀리는 것.

### 표 헤더는 메타 단어 금지 — "비교 축"을 헤더로 그대로 쓰지 않는다

> **실제 사고 사례**: [model-answer.md](@/exam/cs/model-answer.md) Ⅴ 템플릿의 예시 헤더가 `비교 축 | 기존/대안 | 본 키워드`였는데, 대괄호 `[ ]`로 감싸지 않아 "채워야 할 예시"가 아니라 "그대로 베낄 문구"처럼 보였다. 그 결과 저장소 전역 1,300여 개 파일이 첫 칸에 "비교 축"이라는 의미 없는 메타 단어를 그대로 박아 넣었다. 표가 "무엇과 무엇을, 무슨 기준으로 비교하는지" 제목만 봐도 안 보이면 독자는 표를 이해하지 못한다.

- **금지**: 표 헤더에 "비교 축", "구분 항목", "판단 요소"처럼 **표의 역할 자체를 설명하는 메타 단어**를 그대로 쓰는 것. 이런 단어는 "여기에 실제 비교 기준 이름을 넣으라"는 placeholder이지 완성된 헤더가 아니다.
- **필수**: 첫 칸 헤더는 그 행들이 실제로 나열하는 **판단 기준의 이름**이어야 한다. 예: 정렬 알고리즘 비교라면 "판단 기준"이 아니라 이미 각 행에 쓴 값의 상위 범주(예: "시간복잡도·공간복잡도·안정성" 3행을 아우르는 "성능 지표")로 쓰거나, 행이 서로 다른 개별 항목이면 관용적으로 "구분"을 쓴다.
- **자가 검증**: 표 제목 행만 가리고 헤더 셀만 읽었을 때, "이게 뭘 비교하는 표인지" 감이 오는가? "비교 축"이라는 단어에서는 아무 정보도 안 나온다 — 이러면 실패다.
- **템플릿 사용 규칙**: model-answer.md·master-template.md의 표 예시에서 대괄호 `[ ]`로 감싸진 셀은 반드시 실제 내용으로 교체한다. 대괄호가 없는 고정 라벨(예: "선택 기준")만 그대로 재사용 가능하다.

### 표를 쓰면 안 되는 대표 자리 (실제 남용 사례 — 기본은 불릿)

> 이 저장소에서 표가 실제로 남발돼 가독성을 떨어뜨린 자리다. **아래 자리는 기본이 불릿**이며, 표는 괄호 안 예외 조건을 만족할 때만 쓴다. 파일당 표는 대개 "출제 의도 + Ⅱ 구성요소 + 비교 1개" 수준이면 충분하다.

- **Ⅲ 동작원리의 "단계 표"**: 순차 과정이고, 바로 위 **흐름도가 이미 순서를 보여줘 중복**이다. → 흐름도 + 번호 불릿(단계당 1줄)로 쓴다. (예외: 각 단계에 '입력·처리·검증'처럼 2개 이상 축의 값이 실제로 모두 채워질 때만 표)
- **Ⅴ 리스크**: 리스크 나열은 단일 축이고 '확인 지표' 열이 대개 빈칸 채우기가 된다. → "리스크 — 원인 — 대응" 불릿으로 쓴다. (예외: 리스크 3개 이상 + 원인·대응·지표가 모두 실질 정보일 때만 표)
- **Ⅴ 지표·점검**: 항목이 2~3개면 표의 행·열 이점이 없다. → 불릿. (예외: 측정 항목이 많고 기준·방법이 항목마다 다를 때만 표)
- **정의·배경·필요성·적용 방안·결론**: 서술이라 대조 축이 없다. → 항상 불릿(표 금지).

- **표가 적합한 자리(유지)**: ① 출제 의도 표(의도·핵심·감점 3축) ② Ⅱ 구성요소 표(요소·역할·특이사항) ③ Ⅳ/Ⅴ의 대상 간 비교 표(비교축 × 2개 이상 대상). 이 자리는 행·열이 둘 다 실질 의미를 가져 표가 가독성을 높인다.

> **⚠️ 위 표 최소화 규칙은 답안용(Ⅰ~Ⅵ)에만 적용된다.** 【암기용】 블록에서 하위 용어를 `용어 │ 의미 │ 비유`로 정리하는 명료화 표는 오히려 권장된다 — 상세는 아래 **Ⅷ. 【암기용】 블록 작성 원칙**을 따른다.

### Ⅳ. 특징 슬롯 판단

- Ⅳ 기본 제목은 "특징"이되, **고유한 특징이 없는 주제**(분석기법·지표·도구형)는 "비교"·"트레이드오프" 등으로 제목을 바꾸거나 절을 생략한다.
- 판단 기준: **"이 절을 지우면 답안 논리가 무너지는가?"** 안 무너지면 뺀다. 억지 특징 4줄보다 비교·트레이드오프가 변별력이 높다.
- Ⅳ에 표를 절대 쓰지 않는다(무조건 불릿 작성). 단 "핵심특징" 표기는 금지, "특징"만 쓴다.

### 표 요약(`> 요약:`) 규칙

- 표를 쓸 때는 바로 아래 `> 요약:` 한 줄을 단다(채점 포인트 고정).
- **표와 `> 요약:` 사이에 빈 줄 1개 필수** — 빈 줄 없이 표 마지막 행에 붙이면 웹 렌더링이 깨진다.
- 불릿에는 `> 요약:`을 강제하지 않는다.

### 절 생략·번호 규칙 (Ⅰ~Ⅵ 골격)

- **생략 가능한 절은 Ⅳ(특징)뿐이다.** Ⅴ(심화 비교 및 적용 판단)와 Ⅵ(실무 적용 및 결론)은 2~4교시 확장의 핵심이므로 생략 금지.
- **번호는 고정이다.** Ⅳ나 Ⅴ를 생략해도 결론은 항상 `Ⅵ. 실무 적용 및 결론`으로 쓴다 — 결론을 `Ⅴ.`로 당겨 붙이는 번호 밀림 금지.
- 문제 유형별 목차 전환 표의 열 제목은 `Ⅱ·Ⅲ 강조`와 `Ⅴ·Ⅵ 강조`로 쓴다. 구버전 `Ⅲ 강조/Ⅳ 강조`(5단 구골격 잔재)는 Ⅲ=동작원리, Ⅳ=특징인 현행 골격과 어긋나므로 금지.

## Ⅷ. 【암기용】 블록 작성 원칙 — 답안 전에 '이해'부터 시킨다

> **【암기용】 블록의 유일한 임무: 이 개념을 처음 보는 사람이, 답안 템플릿을 손대기 전에 개념과 그 안에 등장하는 모든 내부 용어를 완전히 이해하게 만드는 것이다.** 읽고도 "답안 쓰기도 전에 이해가 안 된다"면 암기용은 실패한 것이다. 이 저장소에서 실제로 나온 가장 큰 불만이므로 최우선으로 지킨다.

### 0. 깊이 기준 — 개인 CS 스터디노트(`content/studynote/`) 수준으로 쓴다

- **목표 깊이**: 암기용은 `content/studynote/`에 아카이빙된 개인 CS 학습 노트 수준의 **깊이**로 쓴다. 얕은 요약이 아니라, **이 파일 하나만 읽고도 개념을 처음부터 제대로 학습**할 수 있어야 한다. 답안용은 지금의 시험 압축 수준을 유지하고, 암기용은 그 위에 이 학습 깊이를 더한다.
- **구체적으로 담을 것**:
  - 메커니즘을 문장으로 충분히 풀어 설명(어떻게 동작하는가 + 왜 그렇게 되는가)
  - **구체 수치 예시**: 예) N이 10→100일 때 등급별 연산량 변화, log₂(10⁶)≈20, O(N²)→O(N log N)이 100만 건에서 약 5,000배 차이
  - 각 하위 개념을 **실제 알고리즘·패턴·사례**와 연결(예: O(log n) ↔ 이진 탐색·B-Tree)
  - **판별·선택 원리**: 등급·기법을 어떻게 판정하고 언제 무엇을 쓰는지
  - 직관적 비유 1개 이상, 필요하면 등장 배경·역사
- **단, 형식·품질은 CSPE 규칙을 따른다 — 스터디노트의 결함은 베끼지 않는다**:
  - 박스 문자 ASCII 아트(`┌ ─ ┐ │ └ ┘`) 금지 → 선형 텍스트 도식만(Ⅶ·model-answer 규칙)
  - 깨진 글자·오타·외국어(중국어·일본어) 금지, 정확한 한국어로
  - **패딩·군더더기·동어반복 금지** — 깊이는 정보 밀도이지 분량 늘리기가 아니다(대전제 0)
- **분량**: 이 깊이를 확보하기 위해 **암기용은 답안용의 170줄 상한에 얽매이지 않는다.** 답안용(Ⅰ~Ⅵ)은 3쪽 압축을 지키되, 암기용은 이해에 필요한 만큼 쓴다(패딩 없이).

### 1. 핵심 키워드부터 세우고, 내부 용어는 빠짐없이 설명한다

**(1) 개요는 핵심 키워드로 정체성부터 세운다**
- 암기용 개요의 **첫 문장**에 이 개념의 정체성을 이루는 **핵심 키워드**(상위 개념·본질 용어)를 반드시 넣는다. 설명을 시작하기 전에 "이게 무엇에 관한 것인가"를 핵심 단어로 못 박는다.
- **나쁜 예(실제 사례)**: 빅오 표기법 개요를 "연산량이 넘지 않는 상한을 나타내는 표기법"으로만 시작 → 정작 **시간 복잡도**라는 핵심 단어가 빠져, 독자가 "이게 시간 복잡도를 표현하는 것"임을 연결하지 못한다.
- **좋은 예**: "빅오는 **시간 복잡도**(및 공간 복잡도)를 나타내는 대표적 **점근적 표기법**이다." → 첫 문장에 핵심 키워드(시간 복잡도·점근적 표기법)가 선다.
- 자가 점검: "이 개념을 한 단어로 검색한다면 무슨 단어인가? 그 단어가 개요 첫 문장에 있는가?"

**(2) 내부에 등장하는 용어·표기·계산식은 하나도 빠짐없이 설명한다**
- 주제 안에 등장하는 **하위 용어·표기·구성요소·계산 방식**(예: Big-O의 O/Ω/Θ·c·n₀, 해시의 버킷·충돌·체이닝, 암호화 알고리즘의 복잡도 계산법 등)을 독자가 모른 채 넘어가게 두지 않는다.
- 각 용어·표기·공식은 **뜻/의도 1줄 + 비유(또는 구체적 계산 예시) 1개**로 설명한다. 정의만 나열하면 이해가 안 된다.
- **핵심 용어 정리 표에는 내부 하위 용어뿐 아니라, 이 개념이 소속·직결되는 상위 핵심 키워드도 (표 맨 위에) 포함한다** — 빅오라면 '시간 복잡도', '점근적 표기법'을 맨 위에 둔다.
- 새로운 개념이나 어려운 수식이 등장하면, **암기용 블록 최상단**에서 이를 직관적으로 먼저 풀어 설명하여 진입 장벽을 낮춘다.

### 2. 병렬 항목은 '용어 │ 의미 │ 비유' 표로 — 최소 기준은 아래 수준
- O/Ω/Θ, 정렬 종류, 충돌 해결 기법처럼 **병렬 항목이 2개 이상**이면 명료화 표로 정리한다.
- **최소 기준**은 아래 예시 수준이다. 이보다 얕으면(뜻만 있고 비유 없음, 항목 누락) 안 된다:

| 표기 | 의미 | 비유 |
|:---|:---|:---|
| O (빅 오) | 상한 (최악의 경우) | "최대 이만큼 걸린다" |
| Ω (빅 오메가) | 하한 (최선의 경우) | "최소 이만큼 걸린다" |
| Θ (빅 세타) | 정확한 차수 (상한 = 하한) | "딱 이만큼 걸린다" |

### 3. 이 명료화 표는 Ⅶ '표 최소화'의 예외다
- Ⅶ의 표 최소화는 **답안용(Ⅰ~Ⅵ)** 규칙이다. **암기용에서 이해를 돕는 표는 적극 권장**한다 — 남용이 아니다.
- 암기용은 시험 답안 양식이 아니라 이해를 위한 글이므로, 표·비유·예시를 아끼지 않는다.

### 4. 판정 기준: 길이가 아니라 '이 파일만 읽고 이해됐는가'
- 암기용은 분량으로 채점하지 않는다. **"처음 보는 사람이 이 블록만 읽고 개념과 내부 용어를 이해했는가"**가 유일한 기준이다.
- 이해에 필요한 건 다 넣되(내부 용어·비유·예), 답안용에서 다시 할 시험 양식·수치 나열은 넣지 않는다(역할 분리 — 암기용=이해, 답안용=시험 양식).

### 5. 골드 스탠다드 예시 — 암기용을 쓸 땐 이 파일을 참고한다
- **참고 정본**: `content/cspe/01_basic_theory/002_big_o_notation.md`의 【암기용】 블록. 위 0~4 원칙(스터디노트 깊이·핵심 키워드 우선·내부 용어 전수 설명·명료화 표·수치 예시)을 모두 충족하는 예시다.
- 새 암기용을 쓰거나 재작성할 때 이 파일의 구성(개요가 핵심 키워드로 시작 → 핵심 용어 정리 표 → 깊이 이해의 소제목별 서술 + 구체 수치·워크드 예시)을 그대로 본떠 맞춘다.

## Ⅸ. 인접 키워드 간 서사 중복 방지 (연쇄 학습 원칙)

> **같은 영역 폴더 안의 파일들은 독립된 백과사전 항목이 아니라, 번호순으로 이어지는 하나의 학습 곡선이다.** 뒤 번호 키워드가 앞 번호 키워드의 배경지식을 처음부터 다시 가르치면, 답안 개수는 늘어도 학습자의 이해는 늘지 않는다 — 이것이 "방향성 없음"으로 읽히는 핵심 원인이다.

### 문제 패턴 (실제 사례: `001_time_space_complexity.md` ↔ `002_big_o_notation.md`)

- 002(Big-O)는 001(시간/공간 복잡도)의 **하위 개념**인데도, 001이 이미 다룬 "최고차항만 남기고 상수·하위항 제거", "O/Ω/Θ 비교"를 처음부터 다시 완전한 설명으로 반복했다.
- 결과: 두 파일의 【암기용】 배경·원리 문단과 답안용 Ⅰ~Ⅳ가 표현만 바뀐 채 같은 내용을 두 번 가르친다. 학습자는 002를 읽어도 001 대비 새로 얻는 게 적다.

### 규칙

1. **작성 전 선행 키워드 확인**: 새 키워드를 쓰기 전, 같은 영역 폴더에서 번호가 빠른 인접 파일(특히 상위 개념·선행 개념에 해당하는 파일)을 먼저 읽는다. 이 개념이 앞 파일의 **특수화·심화·응용**이라면, 앞 파일이 이미 완전히 설명한 원리를 처음부터 다시 풀어 쓰지 않는다.
2. **참조 후 위임(delta-only)**: 공유 배경지식은 "(001 시간복잡도 참조)"처럼 1줄로 위임하고, 이 키워드에서만 성립하는 **차별점·심화·수학적 정식화·새 트레이드오프**로 바로 들어간다. 답안용 Ⅰ 개요에서도 "X의 상위/하위 개념" 관계를 1줄로 명시해 위치를 잡아준다.
3. **암기용 배경·원리도 동일 규칙 적용**: 답안용뿐 아니라 【암기용】 "배경·문제의식"·"작동 원리"도 앞 파일과 동일한 도입부(예: "환경에 종속되지 않는 객관적 지표가 필요하다")를 반복하지 않는다. 이 개념이 실제로 새로 여는 질문에서 시작한다.
4. **다른 점을 표로 못 박는다**: 상위/하위 관계인 두 키워드는 Ⅴ(심화 비교)에서 "이 파일 vs 그 상위/하위 파일"을 하나의 비교 축으로 다루면 중복이 아니라 관계 설명이 된다(예: "Big-O 단독 사용 vs 시간-공간 복잡도 통합 판단").
5. **점검 범위**: 폴더 내 앞뒤 2~3개 번호는 항상 대조한다. 상위개념(예: 001 복잡도 전체)처럼 관계가 먼 번호라도 이름이 유사하거나 명백한 포함관계면 대조 대상에 넣는다.
6. **적용 시점**: 신규 작성뿐 아니라 §7 재작성 트래커의 "파일당 점검 8항목"(AGENTS.md)에도 이 규칙을 9번째 항목으로 반영해 재작성 시 함께 확인한다.

> 이 규칙은 AGENTS.md 파일당 점검 8항목의 8번("Ⅳ/Ⅴ 비교 대상 실질 중복 금지")과 다르다 — 8번은 같은 배치 내 **비교 축**의 중복을, 본 규칙은 **인접 파일의 배경 설명·원리 서술** 중복을 막는다. 둘 다 확인해야 한다.
