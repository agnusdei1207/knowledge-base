# 컴퓨터시스템응용기술사 2~4교시 통합 답안 템플릿

이 문서는 `1교시 단답형 모음`이 아니라, **2~4교시 서술형 답안 안에 1교시 단답형 앞단위를 포함시키는 템플릿**이다.
1교시 키워드는 독립 암기 대상이면서 동시에 서술형의 Ⅰ·Ⅱ 단락 재료가 된다.

---

## Ⅰ. 답안 작성 원칙

| 원칙 | 적용 방법 | 피해야 할 형태 |
|:---|:---|:---|
| 문제 요구사항 우선 | 문제 문장의 동사(설명, 비교, 설계, 방안, 문제점)를 목차로 바꾼다 | 외운 목차를 문제와 무관하게 붙임 |
| 1교시는 앞단위 | 정의·구성요소·장단점 3줄을 2~4교시의 Ⅰ·Ⅱ에 삽입한다 | 단답형 답안을 길게 늘여 서술형으로 착각 |
| 2~4교시는 판단 | 구조도, 비교표, 적용 기준, 한계, 운영 방안을 반드시 넣는다 | 개념 설명만 반복 |
| 과목 균형 | 01 컴퓨터구조뿐 아니라 OS, 네트워크, SW, DB, 보안, AI, 클라우드, 경영까지 선택지를 확보한다 | 1과목 지식으로 모든 문제를 해결하려 함 |
| 손글씨 시간 | 25분 안에 3쪽 내외 완성 가능한 목차로 고정한다 | 목차 구상에 시간을 과다 사용 |

## Ⅱ. 2~4교시 기본 골격

2~4교시 골격은 [모범답안 템플릿](@/exam/cs/model-answer.md)의 `2~4교시 서술형 템플릿`을 정본으로 따른다.

| 정본 반영 원칙 | 적용 메모 |
|:---|:---|
| Ⅰ 개요 / Ⅱ 구조·동작원리 / Ⅲ 핵심특징·비교 / Ⅳ 적용방안·리스크 / Ⅴ 결론 | 과목별 적용 시 제목과 표 축만 바꾸고 골격은 유지 |
| 1교시 단답형은 2~4교시 앞단위 | 정의·구성요소·장단점·적용 포인트를 Ⅰ~Ⅳ에 흡수 |
| 구조도 1개 필수 | `Ⅰ. 개요` 직후 10~15초 안에 박스 3~5개로 뼈대를 먼저 그림 |

## Ⅳ. 문제 유형별 치환 템플릿

| 문제 유형 | Ⅰ | Ⅱ | Ⅲ | Ⅳ | Ⅴ |
|:---|:---|:---|:---|:---|:---|
| 설명형 | 정의·필요성 | 구성요소·원리 | 특징표 | 적용 사례 | 발전 방향 |
| 비교형 | 비교 배경 | 공통 구조 | 차이표 | 선택 기준 | 조건별 결론 |
| 설계형 | 요구사항 | 목표 아키텍처 | 구성요소 역할 | 구축 절차·운영 기준 | 확장 방향 |
| 방안형 | 문제 현황 | 원인 구조 | 문제-원인표 | 단·중·장기 대책 | 기대효과 |
| 운영형 | 운영 목표 | 운영 프로세스 | 지표표 | 자동화·통제 | 지속 개선 |
| 보안형 | 위협 정의 | 공격면·자산 | 통제 매핑 | 탐지·대응·복구 | 제로트러스트/규제 |

### 실제 치환 예시 1: MSA 장애 대응

| 단락 | 바로 쓸 내용 |
|:---|:---|
| Ⅰ | MSA는 서비스를 도메인 단위로 분리해 독립 배포하는 구조이나, 네트워크 지연·장애 전파·데이터 정합성 문제가 생긴다 |
| Ⅱ | API Gateway → Service → DB per Service → Message Broker → Observability |
| Ⅲ | Monolith vs MSA 비교: 배포, 확장, 장애격리, 운영복잡도 |
| Ⅳ | Circuit Breaker, Retry/Timeout, Bulkhead, Saga, Distributed Tracing |
| Ⅴ | MSA는 분해보다 운영 자동화와 관측성 확보가 성공 조건 |

손답안 구조도는 아래처럼 먼저 그린다.

```text
┌────────────┐   ┌────────────┐   ┌────────────┐
│ API Gateway│──▶│ Service A  │──▶│ DB per Svc │
└────────────┘   └─────┬──────┘   └────────────┘
                       │
                       ▼
                 ┌────────────┐
                 │ Message Bus│
                 └─────┬──────┘
                       ▼
                 ┌────────────┐
                 │Observability│
                 └────────────┘
```

구조도는 `Ⅰ. 개요` 다음에 10~15초 안에 뼈대만 그리고, 설명은 `Ⅱ. 구조·동작원리` 표에서 채운다.

### 실제 치환 예시 2: RAG 도입

| 단락 | 바로 쓸 내용 |
|:---|:---|
| Ⅰ | RAG는 외부 지식 검색 결과를 LLM 프롬프트에 결합해 최신성·근거성을 높이는 생성형 AI 아키텍처 |
| Ⅱ | Document → Chunking → Embedding → Vector DB → Retrieval → Prompt Augmentation → LLM |
| Ⅲ | Fine-tuning vs RAG 비교: 목적, 비용, 최신성, 보안, 운영 난이도 |
| Ⅳ | 문서 품질관리, 권한 필터링, Hybrid Search, Evaluation, Hallucination Guardrail |
| Ⅴ | 기업 RAG는 모델보다 데이터 거버넌스와 검색 품질이 성패를 좌우 |

손답안 구조도는 아래처럼 먼저 그린다.

```text
┌──────────┐   ┌──────────┐   ┌──────────┐
│ Document │──▶│ Chunking │──▶│Embedding │
└──────────┘   └──────────┘   └────┬─────┘
                                   ▼
┌──────────┐   ┌──────────┐   ┌──────────┐
│Retriever │◀──│Vector DB │   │   LLM    │
└────┬─────┘   └──────────┘   └────┬─────┘
     └────────▶ Prompt Augmentation ────▶ Answer
```

구조도는 박스를 예쁘게 그리는 것이 아니라, **입력-저장-검색-생성**의 흐름을 한 번에 보이게 만드는 것이 목적이다.
