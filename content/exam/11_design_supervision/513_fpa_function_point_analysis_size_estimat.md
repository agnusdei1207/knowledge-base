## 핵심 인사이트 (3줄 요약)

> 1. **본질**: FPA(기능점 분석)는 Allan J. Albrecht가 1979년 IBM에서 고안한 후 IFPUG(International Function Point Users Group) CPM 4.3.1~4.3.2로 표준화된 **사용자 관점의 기능 단위 SW 규모 측정 기법**으로, 5개 기능 컴포넌트(EI, EO, EQ, ILF, EIF)와 14개 일반 시스템 특성(GSC)을 통해 `UFP × VAF = AFP(조정 기능점)`로 절대 규모를 산정합니다.
> 2. **가치**: 프로그래밍 언어·플랫폼·DBMS에 **무관**하게 동일 기능을 일관되게 측정 가능하며, 국내에서는 행정안전부 「SW사업 대가산정 가이드」와 정보통신산업진흥원 NIPA의 **표준 기능점수 산정 절차**에 따라 공공 SW사업 발주·계약의 법정 기준 단위로 활용되어, 통상 1FP ≈ 8시간~10.5시간(난이도별) 또는 1FP ≈ 155~176 LOC(평균)이라는 환산식으로 비용·기간·생산성 벤치마킹의 기준선이 됩니다.
> 3. **판단 포인트**: **컴포넌트 분류의 경계(EI vs EO vs EQ, ILF vs EIF)**, **복잡도 매트릭스 적용 시 DET·RET·FTR 카운팅 정확도**, **VAF 14개 GSC의 주관성 통제(0~5점 척도)** 가 산정 신뢰도(±10~20% 오차)의 핵심 변동 요인이며, 기술사 논술에서는 "현업 사용 기능 vs 공유 참조 파일"의 EIF 판정, "1차원 vs 2차원 자료구조"의 복잡도 판정 논리를 반드시 정당화해야 합니다.

---

## Ⅰ. 개요 및 필요성

기능점수(Function Point, FP) 분석은 **SW의 "기능(function)"이 사용자에게 제공하는 가치**를 정량화하여 규모(size)를 산정하는 기법입니다. 전통적 SW 규모 측정 단위인 LOC(Line of Code, 원시 코드 라인 수)는 절차형 언어(COBOL, C)와 비교적 잘 맞았으나, 4세대 언어(4GL), 객체지향, 라이브러리·프레임워크·저코드(Low-code)·SaaS·API 호출 기반 시스템이 주류를 이루는 현대 환경에서는 **언어·기술 스택에 따라 LOC가 5~50배 차이**가 나 동일 기능을 측정함에 있어 일관성이 결여되는 근본 한계가 있습니다. 또한 프로젝트 후반(코딩 완료 후)이나 테스트 단계에서야 측정이 가능하여, 사업 초기의 의사결정과 발주 계약에 활용하기 어렵습니다.

FPA는 **"사용자 관점에서 시스템이 무엇을 하는가"** 를 묻는 5가지 기능 유형과, 시스템 품질에 영향을 미치는 14개 일반 시스템 특성(General System Characteristics, GSC)을 결합하여 기술 중립적이면서도 사업 초기(요구사항 정의 단계, RFP 작성 시점)부터 적용 가능한 규모 산정 체계를 제공합니다. IFPUG은 ISO/IEC 20926(EIFPUG), ISO/IEC 29881(COSMIC-FFP)과 함께 SW 규모 측정 국제 표준으로 자리매김하였고, 한국에서는 한국정보통신기술협회(TTA)의 `TTA.KO-10.0230` 기능점수 측정 표준, 행정안전부 「SW사업 대가산정 가이드라인(2024년 개정)」에서 공공부문 SW사업의 **법정 대가(비용) 산정 단위**로 강제 사용됩니다.

```text
[ FPA 등장 배경 및 패러다임 전환 ]

   <- 이전 (1970s)              -> 현재 (FPA, COSMIC-FFP) ----->
  +-----------------+        +------------------------------+
  |  LOC(원시라인수)  |        |  기능점수(FP) — 사용자 관점    |
  | --------------- |   ->    | ---------------------------- |
  | • 기술 종속적     |        | • 기술·언어 중립(Java/Cobol/   |
  |   (C vs SQL vs   |        |   Python/SaaS 동일 측정 가능)  |
  |   Assembly)      |        | • 측정 시점이 앞당겨짐          |
  | • 코딩 완료 후    |        |   (요구사항/설계 단계부터)      |
  |   산정 가능       |        | • 기능·데이터·제약·품질 동시   |
  | • 생산자 관점     |        |   고려(14 GSC 반영)            |
  |   (개발자)        |        | • 사용자 관점(사용자 가치)     |
  +-----------------+        +------------------------------+
          |                              |
          v                              v
  동일 기능 100건 측정 시      동일 기능 100건 측정 시
  Java  : 25,000 LOC          ->  1,200 FP (일관)
  COBOL : 12,000 LOC          ->  1,200 FP (일관)
  C     :  8,000 LOC          ->  1,200 FP (일관)
  -> 비용·기간 비교·벤치마킹 불가    -> 발주·계약·생산성 비교 가능
```

- **📢 섹션 요약 비유**: **부동산 감정평가**와 같습니다. 아파트 시세를 "벽돌 개수"로 평가하지 않고 "방 수·욕실 수·남향·역세권" 같은 **사용자가 가치 있게 여기는 기능 단위(면적, 채광, 학군)** 로 평가해야 공정한 거래가 가능하듯, FPA는 SW를 "코드 라인수"가 아닌 **사용자가 쓰는 기능과 데이터의 가치 단위**로 측정합니다.

## Ⅱ. 아키텍처 및 핵심 원리

FPA의 핵심 메커니즘은 **① 경계(Boundary) 식별 -> ② 5개 기능 컴포넌트 분류·카운팅 -> ③ 복잡도(Complexity) 판정 -> ④ GSC 평가 -> ⑤ AFP 산정** 의 5단계 파이프라인으로 구성됩니다. 각 단계는 결정론적 매트릭스(IFPUG CPM의 DET/RET/FTR 표)와 GSC 0~5점 척도를 통해 진행자의 주관성을 통제합니다.

```text
[ IFPUG FPA 측정 파이프라인 (5단계) ]

  +--------------------------------------------------------------+
  | Stage 1. 시스템 경계(Boundary) 식별                           |
  |   • 사용자 요구사항 도메인 정의 (내부/외부 사용자 기준)         |
  |   • 외부 시스템과의 인터페이스 경계 확정                        |
  +--------------+-----------------------------------------------+
                 v
  +--------------------------------------------------------------+
  | Stage 2. 기능 컴포넌트 식별 (5유형 카운팅)                    |
  |  +-------------+  +-------------+  +-------------+          |
  |  | EI (입력)    |  | EO (출력)    |  | EQ (조회)    |          |
  |  | 외부->내부    |  | 내부->외부    |  | 내부->외부    |          |
  |  | 데이터처리   |  | 파생데이터   |  | 단순 인출   |          |
  |  +-------------+  +-------------+  +-------------+          |
  |  +-------------+  +-------------+                            |
  |  | ILF (내부    |  | EIF (외부    |  -> DET·RET·FTR 집계       |
  |  |  유지파일)   |  |  참조파일)   |                            |
  |  +-------------+  +-------------+                            |
  +--------------+-----------------------------------------------+
                 v
  +--------------------------------------------------------------+
  | Stage 3. 복잡도(Complexity) 판정 — Low/Avg/High              |
  |  • EI/EO : FTR × DET 매트릭스 적용                           |
  |  • EQ    : FTR × DET 매트릭스 적용                           |
  |  • ILF/EIF: RET × DET 매트릭스 적용                          |
  +--------------+-----------------------------------------------+
                 v
  +--------------------------------------------------------------+
  | Stage 4. GSC 14개 항목 평가 (0~5점, 14개)                    |
  |  • 자료통신·분산처리·성능·사용자·처리율·온라인입력·효율성·  |
  |    최종사용자·온라인갱신·복잡처리·재사용성·설치 편의성·      |
  |    다중사이트·변경 촉진                                     |
  |  • ΣFi (i=1..14) 계산 -> VAF 산정                             |
  +--------------+-----------------------------------------------+
                 v
  +--------------------------------------------------------------+
  | Stage 5. AFP 산정                                            |
  |   UFP = Σ(컴포넌트별 수량 × 가중치)                           |
  |   VAF = 0.65 + 0.01 × ΣFi                                   |
  |   AFP = UFP × VAF                                            |
  +--------------------------------------------------------------+
```

| 구성 요소 | 역할 | 핵심 기술 및 동작 방식 |
| :--- | :--- | :--- |
| **경계(Boundary)** | 측정 대상 외곽 정의 | 사용자 관점(외부 사용자가 인식하는 단위 시스템)으로 확정. 동일 DB를 공유하더라도 사용자 도메인이 다르면 별개 시스템으로 산정. Microservices·MSA 환경에서는 **Bounded Context** 단위와 매핑 |
| **5개 기능 컴포넌트** | 카운팅 단위 | **EI(External Input)**: 외부->내부 데이터 처리(Insert/Update/Delete 트리거). **EO(External Output)**: 파생 데이터 산출(집계·계산·포맷팅 결과). **EQ(External Inquiry)**: 단순 조회(원본 데이터 직접 인출, 계산 없음). **ILF(Internal Logical File)**: 측정 대상 시스템 내부에서 유지·관리되는 논리적 데이터 그룹. **EIF(External Interface File)**: 다른 응용시스템이 유지·관리하며 본 시스템이 **참조만** 하는 데이터 그룹 |
| **DET / RET / FTR** | 복잡도 결정 변수 | **DET**(Data Element Type): 사용자가 인식 가능한 유일 필드 수(예: 고객-주소, 고객-전화). **RET**(Record Element Type): ILF/EIF 내 논리적 부분집합 수(예: 고객-개인정보, 고객-신용정보 = 2 RET). **FTR**(File Type Referenced): EI/EO/EQ가 참조하는 ILF/EIF 수 |
| **가중치 매트릭스** | Low/Avg/High -> 3/4/6 등 환산 | IFPUG CPM 4.3.x 표준 표 사용. 예) EI: FTR 0~1 & DET 1~4 -> Low(3), FTR 0~1 & DET 5~15 -> Avg(4), FTR 0~1 & DET 16+ -> High(6). EO: FTR 0~1 & DET 1~5 -> Low(4), … High(7). EQ: Low(3) ~ High(6). ILF/EIF: RET 1 & DET 1~19 -> Low(7), High(15) |
| **14개 GSC + VAF** | 시스템 품질 반영 | VAF = **0.65 + 0.01 × ΣFi** (Fi는 0~5점). ΣFi 범위: 0~70, VAF 범위: 0.65~1.35. 행정안전부 가이드라인은 VAF를 대가산정에 직접 적용하지 않고 **노력율 환산 시점에 별도 보정계수**로 사용하기도 함 |
| **UFP / DFP / AFP** | 최종 규모 산정 | **UFP**(Unadjusted Function Point): 가중치 적용 전 정수점. **DFP**(Development Function Point): 신규 개발 규모(설계·구축 단계 적용). **AFP**(Adjusted FP) = UFP × VAF. 유지보수 단계에서는 **EFP(Enhanced FP)** = (AFP_added + AFP_modified + AFP_deleted - AFP_reused) 활용 |

### 핵심 산정 공식 및 예시

**Step A) 컴포넌트별 가중치 적용 (예시: 단일 기능)**

```
  [ 사례: 고객정보 등록 화면 (Web Form) ]
  - 화면 필드 12개 (ID, 이름, 주소1, 주소2, 우편번호, 전화, 이메일, ...)
  - 고객 ILF 1개 (RET=2 : 기본정보/연락정보) 와 주문 EIF 1개 참조
  - 분류: EI (Insert 트리거), FTR=1, DET=12 -> "High (6점)"
  - 가중치: 1건 × 6 = 6 UFP
```

**Step B) GSC 점수표 예시**

```
  GSC14항목                  점수(0~5)
  1. 자료통신                4
  2. 분산데이터처리          3
  3. 성능                    3
  4. 사용자의 용이성         4
  5. 처리율(Throughput)      3
  6. 온라인 데이터 입력      4
  7. 최종사용자 효율성       4
  8. 온라인 갱신             3
  9. 복잡한 처리 로직        3
  10. 재사용성               2
  11. 설치 편의성            3
  12. 다중 사이트 지원       2
  13. 변경 촉진              3
  14. 다국어/특수 처리       1
  -----------------------------
  ΣFi = 42
  VAF = 0.65 + 0.01 × 42 = 1.07
  AFP = 6 × 1.07 = 6.42 FP
```

**Step C) 실무 환산 (행정안전부 가이드라인 기준)**

```
  기능점수(AFP)   ->   투입공수(M/M)   ->   SW 사업대가
  -------------      ----------------     -------------
  1 FP           ≈   0.13 M/M (약 22일)  (보정계수 적용 시)
  공공 SW사업    =    AFP × 역환산계수    ×  4단계 직접노무비
  (2024 가이드)       (5개 보정계수)         × 간접비·이윤
```
