## Ⅰ. 개요
- **정의**: API 키·비밀번호·인증서 등 민감 정보를 중앙에서 저장·접근제어·갱신하는 관리 체계
- **배경/필요성**: 소스코드·설정파일에 하드코딩된 비밀이 유출되는 사고가 빈발하여, 동적 비밀 발급과 접근 감사 체계가 필요함
- **비유**: 금고 관리인이 요청 시마다 일회용 열쇠를 발급하고 사용 기록을 남기는 것

| 출제 의도 | 반드시 짚을 핵심 | 감점 회피 포인트 |
|:---|:---|:---|
| 클라우드/DevOps 비밀 관리 | Dynamic Secret과 Lease 갱신 개념 | Vault는 도구명, Secrets Management는 범용 개념 |

> 요약: 비밀 관리는 민감 정보의 동적 발급·자동 폐기·접근 감사를 중앙에서 수행하는 체계임

## Ⅱ. 구성요소
```text
Client --> Auth Method --> Vault Core --> Secret Engine
                              |
                              v
                        Audit Backend
```

| 구성요소 | 설명 | 비유 |
|:---|:---|:---|
| Secret Engine | DB 자격증명·PKI·KV 등 비밀 유형별 생성·관리 모듈 | 금고 내 칸막이별 보관함 |
| Auth Method | AppRole·OIDC·K8s SA 등 요청자 신원 확인 수단 | 금고실 출입 신분증 |
| Audit Backend | 모든 비밀 접근 요청·응답을 로그로 기록하는 감사 장치 | CCTV 녹화 장치 |

> 요약: 인증-비밀 엔진-감사 로그 3계층으로 비밀의 발급·사용·추적을 관리함

## Ⅲ. 절차
```text
Authenticate --> Request --> Issue --> Revoke
```
- 1단계: Authenticate — 클라이언트가 Auth Method로 신원을 증명하고 토큰을 발급받음
- 2단계: Request — 토큰과 함께 필요한 비밀 경로에 접근을 요청함
- 3단계: Issue — Secret Engine이 동적 비밀을 생성하고 TTL(유효기간)을 부여함
- 4단계: Revoke — TTL 만료 시 자동 폐기하거나 명시적으로 비밀을 회수함

> 요약: 인증 → 요청 → 동적 발급 → 자동 폐기의 수명주기로 비밀을 관리함

## Ⅳ. 문제점
- Vault 단일 장애점: 비밀 관리 서버 장애 시 전체 서비스가 자격증명을 취득하지 못함
- 초기 봉인 해제: Unseal Key 관리가 복잡하고 분실 시 모든 비밀에 접근 불가능함
- 비밀 스프롤: 팀별로 별도 비밀 저장소를 운영하면 중앙 관리 목적이 무력화됨

> 요약: 가용성, 봉인 키 관리, 분산 저장소 난립이 운영상 주요 문제임

## Ⅴ. 개선방안
1. 단기: Vault 클러스터를 Active-Standby HA로 구성하여 가용성을 확보함
2. 중기: Auto Unseal(Cloud KMS 연동)을 적용하여 봉인 해제 절차를 자동화함
3. 장기: 조직 전체 비밀 관리 정책을 수립하고 단일 플랫폼으로 비밀 저장소를 통합함

> 요약: HA 구성 → 자동 봉인 해제 → 조직 단일 플랫폼 통합 순으로 개선함

## Ⅵ. 전망
- 발전 방향: Kubernetes CSI Driver 연동으로 Pod에 비밀을 파일 마운트하는 클라우드 네이티브 패턴이 확산 중
- 기술사적 판단: Zero Trust(105 참조) 환경에서 동적 비밀 발급이 정적 자격증명을 대체할 것임
- 기술사 제언: SBOM·SLSA(131 참조)와 연계하여 빌드 시점 비밀 주입 경로도 감사 대상에 포함할 필요
