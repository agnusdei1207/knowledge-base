## Ⅰ. 개요
| 항목 | 내용 |
|---|---|
| **정의** | 가변 길이의 평문을 비트 또는 바이트 단위로 순차적으로 암호화하는 스트림 암호의 현대적 표준 알고리즘임 |
| **배경/필요성** | 기존 RC4 알고리즘의 취약점이 발견되고, IoT 등 하드웨어 자원이 부족한 환경에서 AES(블록암호)를 대체할 빠르고 가벼운 암호 필요 |
| **출제 의도** | 블록 암호(AES)와 스트림 암호(ChaCha20)의 구조적 차이 및 소프트웨어 환경에서의 연산 효율성 평가 |

## Ⅱ. 구성요소
```text
+-------------------+      +-------------------+      +-------------------+
|  Key, Nonce, Ctr  |      |  ChaCha20 Core    |      |  Keystream Block  |
| (비밀키, 난수, 카운터)+----->| (ARX 연산 매트릭스)+----->| (유사 난수 스트림) |
+-------------------+      +-------------------+      +-------------------+
```
| 구성요소 | 설명 | 비유 |
|---|---|---|
| **입력 상태 (State)** | 256비트 키, 96비트 난수(Nonce), 32비트 카운터, 상수로 구성된 4x4(16단어) 매트릭스임 | 비밀 재료들을 담은 16칸짜리 상자 |
| **ARX 연산 엔진** | 덧셈(Add), 회전(Rotate), XOR의 단순한 연산만으로 구성된 코어 혼합 알고리즘임 | 재료를 단순한 동작으로 미친듯이 섞는 믹서기 |
| **키 스트림 (Keystream)**| 평문과 결합할 목적으로 ARX 연산을 거쳐 생성된 끝없는 유사 난수 비트 열임 | 믹서기에서 끝없이 뿜어져 나오는 물감 |

> 요약: 복잡한 S-Box(AES) 대신 단순 덧셈과 비트 회전을 통해 소프트웨어 상에서 극도로 빠르게 난수를 쏟아내는 암호임.

## Ⅲ. 절차
```text
+----------------+   +----------------+   +----------------+   +----------------+
| 1. 상태 초기화 |-->| 2. ARX 라운드  |-->| 3. 키 스트림 도출|-->| 4. XOR 암호화  |
| (행렬에 값 배치)|   | (20회 혼합 연산)|   | (난수 블록 생성)|   | (평문과 비트연산)|
+----------------+   +----------------+   +----------------+   +----------------+
```
1. **상태 초기화**: 4x4 행렬에 고정 상수값, 256비트 비밀키, 카운터, 그리고 일회성 난수(Nonce)를 차례로 채움
2. **ARX 라운드 반복**: 행렬의 열 단위와 대각선 단위로 덧셈, XOR, 회전 연산을 총 20회(ChaCha20) 반복하여 원본 값을 철저히 뒤섞음
3. **키 스트림 블록 도출**: 섞인 결과에 초기 상태값을 더하여 역산이 불가능한 512비트(64바이트)의 무작위 키 스트림 블록을 추출함
4. **XOR 암호화**: 도출된 키 스트림과 실제 평문 데이터를 비트 단위로 단순 XOR 연산하여 최종 암호문을 생성함

> 요약: 상태 행렬을 20번 섞어 만든 예측 불가 난수 열(Keystream)과 평문을 단순 부딪혀(XOR) 암호화함.

## Ⅳ. 문제점
* **Nonce(난수) 재사용 시 치명적 결함**: 동일한 키와 동일한 Nonce가 두 번 사용되면 키 스트림이 동일해져, 암호문 2개를 통해 평문이 즉시 노출됨
* **무결성(인증) 보장 기능 부재**: 스트림 암호 자체는 데이터 조작 여부를 확인할 수 없어 비트 플립(Bit-flip) 공격에 의해 암호문이 임의로 조작될 위험
* **하드웨어 가속 부재 시 CPU 점유율**: AES-NI와 같은 하드웨어 명령어가 없는 구형 모바일 환경에서는 빠르지만, 전용 칩이 있는 최신 PC 환경에서는 오히려 AES보다 효율이 떨어짐

## Ⅴ. 개선방안
* **단기 방안 (엄격한 Nonce 관리)**: 시스템 설계 시 Nonce 값을 단순 순차 증가 카운터로 관리하거나 동기화하여 절대 중복 사용되지 않도록 강제 적용
* **중기 방안 (Poly1305 결합)**: 기밀성만 제공하는 ChaCha20에 일회성 메시지 인증 코드(MAC)인 Poly1305를 결합(AEAD 모드)하여 무결성 검증 추가
* **장기 방안 (기기별 동적 스위칭 알고리즘)**: 클라이언트 환경을 동적으로 감지하여 AES 가속 칩이 있으면 AES-GCM을, 저사양 모바일 기기면 ChaCha20-Poly1305를 사용하도록 자동 협상

## Ⅵ. 전망
* 구글의 주도로 TLS 1.3의 핵심 암호 제품군(Cipher Suite)으로 채택되어 AES를 완벽히 대체/보완하는 현대적 표준으로 등극함
* IoT 기기, 저사양 스마트폰, 그리고 WireGuard VPN 등 고속 소프트웨어 암호화가 요구되는 경량 네트워크 환경의 사실상(De-facto) 표준임
