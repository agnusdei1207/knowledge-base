## Ⅰ. 개요
- **정의**: 인증은 주체의 신원을 검증하는 과정이고, 인가는 검증된 주체에 자원 접근 권한을 부여하는 과정임
- **배경/필요성**: 접근제어(002 참조)의 실행을 위해 "누구인지"와 "무엇을 할 수 있는지"를 분리·검증할 필요가 있음
- **비유**: 신분증 확인(인증) 후 출입 가능 구역을 안내(인가)하는 것과 유사함

| 출제 의도 | 반드시 짚을 핵심 | 감점 회피 포인트 |
|:---|:---|:---|
| 인증·인가 개념 구분과 구현 기술 | 인증 팩터 3종(지식·소유·생체)과 인가 프로토콜 | 인증과 인가를 동일 개념으로 혼용하지 않을 것 |

> 요약: 인증은 신원 확인, 인가는 권한 부여이며 두 과정은 순차적으로 수행됨

## Ⅱ. 구성요소
```text
사용자 --> [인증(AuthN)] --> 신원확인 --> [인가(AuthZ)] --> 권한부여
              |                              |
              v                              v
         인증 팩터                       정책 엔진
     (지식/소유/생체)               (RBAC/ABAC/정책)
```

| 구성요소 | 설명 | 비유 |
|:---|:---|:---|
| 인증 팩터 | 지식(패스워드)·소유(OTP토큰)·생체(지문)로 신원을 검증함 | 열쇠·카드·지문 중 하나로 문 열기 |
| MFA(다중 인증) | 2개 이상 팩터를 조합하여 인증 강도를 높임 | 비밀번호 + 문자 인증 코드 |
| 인가 프로토콜 | OAuth 2.0·SAML 등으로 권한 범위(Scope)를 정의·전달함 | 위임장에 적힌 권한 범위 |

> 요약: 인증 팩터로 신원을 확인한 뒤 정책 엔진이 권한 범위를 결정함

## Ⅲ. 절차
```text
자격제출 --> 신원검증 --> 권한조회 --> 접근토큰발급
```
- 1단계: **자격제출** — 사용자가 ID·패스워드·OTP 등 인증 자격을 제출함
- 2단계: **신원검증** — 인증 서버가 자격 정보를 검증하여 신원을 확인함
- 3단계: **권한조회** — 인가 서버가 해당 주체의 역할·속성에 따른 권한을 조회함
- 4단계: **접근토큰발급** — 권한 범위가 포함된 토큰(JWT 등)을 발급하여 자원 접근을 허용함

> 요약: 자격 제출 → 신원 검증 → 권한 조회 → 토큰 발급의 4단계로 접근이 통제됨

## Ⅳ. 문제점
- 패스워드 취약: 지식 기반 단일 팩터는 피싱·무차별 대입 공격에 노출됨
- 토큰 탈취: 발급된 토큰이 유출될 경우 세션 하이재킹이 발생함
- 권한 과다 부여: 최소 권한 원칙 미적용 시 인가 범위가 과도하게 설정됨

> 요약: 단일 팩터 의존·토큰 유출·과다 권한이 인증·인가의 주요 위협임

## Ⅴ. 개선방안
1. 단기: MFA 의무화로 단일 팩터 의존도를 낮춤
2. 중기: 토큰 만료 시간 단축 + 토큰 바인딩으로 탈취 영향 범위를 축소함
3. 장기: 최소 권한 원칙 기반 동적 인가(Just-In-Time Access)를 적용함

> 요약: MFA·토큰 보호·동적 인가로 인증·인가 취약점을 단계적으로 보완함

## Ⅵ. 전망
- 발전 방향: 패스워드리스 인증(FIDO2·Passkey)과 지속적 인증(Continuous AuthN)이 확산됨
- 기술사적 판단: 인증·인가는 IAM(004 참조)과 제로트러스트(007 참조)의 핵심 구성 요소임
- 기술사 제언: 패스워드리스 전환 로드맵 수립과 MFA 적용 범위 확대를 권고함
