## Ⅰ. 개요
- **정의**: 주체가 객체에 접근할 때 역할 또는 속성 기반으로 허가를 판단하는 접근 제어 모델
- **배경/필요성**: 조직 규모 확대와 클라우드 환경에서 정적 역할만으로 세밀한 권한 제어가 곤란해 속성 기반 모델이 필요함
- **비유**: RBAC은 직급별 출입 카드, ABAC은 시간·장소·목적까지 확인하는 스마트 게이트

| 출제 의도 | 반드시 짚을 핵심 | 감점 회피 포인트 |
|:---|:---|:---|
| 두 모델의 차이와 적용 기준 | RBAC 역할 할당 vs ABAC 정책 평가 엔진 | RBAC을 ABAC의 하위 집합으로 설명 가능함 |

> 요약: RBAC은 역할, ABAC은 속성 조합으로 접근 권한을 결정하는 제어 모델임

## Ⅱ. 구성요소
```text
[주체] --요청--> [정책 결정점(PDP)] --판단--> [정책 시행점(PEP)] --> [객체]
                      |
              [정책 저장소(PAP)]
```

| 구성요소 | 설명 | 비유 |
|:---|:---|:---|
| PDP (Policy Decision Point) | 접근 요청에 대해 정책을 평가하여 허가·거부를 결정함 | 심판 |
| PEP (Policy Enforcement Point) | PDP의 결정을 실제로 적용하여 접근을 허용·차단함 | 경비원 |
| PAP (Policy Administration Point) | 접근 정책을 작성·관리하는 관리 인터페이스 | 규칙 편집기 |
| PIP (Policy Information Point) | 주체·객체·환경 속성 정보를 PDP에 제공함 | 신분증 조회기 |

> 요약: PDP가 정책을 판단하고 PEP가 이를 시행하는 XACML 기반 구조임

## Ⅲ. 절차
```text
접근 요청 --> 속성 수집 --> 정책 평가 --> 허가/거부 시행
```
- 1단계: 주체가 객체에 대한 접근을 요청하면 PEP가 이를 가로챔
- 2단계: PIP에서 주체·객체·환경 속성(역할, 부서, 시간대 등)을 수집함
- 3단계: PDP가 PAP에 정의된 정책과 수집된 속성을 대조하여 허가·거부를 결정함
- 4단계: PEP가 결정 결과를 시행하고 감사 로그를 기록함

> 요약: 요청 가로채기 → 속성 수집 → 정책 평가 → 시행의 4단계로 접근을 제어함

## Ⅳ. 문제점
- 역할 폭증(Role Explosion): RBAC에서 세분화 요구가 커지면 역할 수가 기하급수적으로 증가하여 관리 비용이 상승함
- 정책 복잡성: ABAC 정책이 다수의 속성 조합을 포함하면 충돌·누락 검증이 어려워짐
- 성능 부하: 요청마다 다수 속성을 실시간 수집·평가하면 인가 응답 지연이 발생함

> 요약: 역할 폭증, 정책 충돌, 실시간 평가 성능이 주요 과제임

## Ⅴ. 개선방안
1. 단기: 역할 그룹핑과 계층화로 RBAC 역할 수를 축소하여 관리 부담을 줄임
2. 중기: 정책 시뮬레이션·충돌 탐지 도구를 도입하여 ABAC 정책 정합성을 검증함
3. 장기: 속성 캐싱과 PDP 분산 배치로 실시간 평가 지연을 최소화함

> 요약: 역할 계층화 → 정책 검증 도구 → 분산 PDP로 단계적 개선이 필요함

## Ⅵ. 전망
- 발전 방향: RBAC+ABAC 하이브리드 모델로 역할 기반 기본 제어에 속성 기반 세분화를 결합하는 추세임
- 기술사적 판단: 제로 트러스트 환경에서 컨텍스트 기반 동적 인가가 표준이 되어감
- 기술사 제언: 기존 RBAC 체계를 유지하면서 ABAC 정책 엔진을 점진적으로 통합하는 전략이 필요함
