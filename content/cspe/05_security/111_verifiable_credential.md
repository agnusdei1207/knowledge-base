# 📖 【암기용】 개념 완전 이해

> 목적: Verifiable Credential을 디지털 증명서 파일이 아니라 발급자 서명으로 위변조를 검증하는 자격 증명 모델로 이해하게 만든다. 시험 답안 양식이 아니라, 이해를 위한 친절한 설명이다.

## 한눈에
- **개요**: 발급자가 특정 속성이나 자격을 전자서명해 보유자가 검증자에게 제시하는 기계 판독형 증명
- **왜 필요한가**: 서비스마다 신분증 사본, 재직증명서, 자격증 원본을 보관하면 개인정보 노출면과 위변조 확인 비용이 커진다. VC는 필요한 속성만 제시하고 서명으로 진위를 확인한다.
- **핵심 직관**: 종이 증명서의 기관 직인을 공개키 서명으로 바꾸고, 사용자는 필요한 증명만 지갑에서 꺼내 제출하는 구조임

## 깊이 이해
- **배경·문제의식**: 기존 증명은 원본 스캔, API 실시간 조회, 중앙 DB 확인에 의존한다. 기관 간 연동이 늘수록 개인정보 복제본이 증가하고, 원본 여부 확인도 기관별로 달라진다.
- **작동 원리**: Issuer가 Holder의 속성을 VC로 서명한다. Holder는 제출 목적에 맞춰 VC 또는 Verifiable Presentation을 만든다. Verifier는 발급자 공개키, proof, 만료일, 폐기 상태를 확인한다.
- **비유**: 대학이 졸업증명서를 봉인해 주고, 회사는 대학에 매번 전화하지 않고 봉인과 폐기 여부만 확인하는 방식과 유사함
- **구체 예시**: 은행 KYC 완료 VC는 `credentialSubject`에 "본인확인 완료", "만 19세 이상"만 포함하고, 쇼핑몰은 주민번호·주소를 저장하지 않고 1회 검증 결과만 보관한다.
- **흔한 오해·주의점**: VC는 DID나 블록체인과 동일어가 아니다. DID 없이도 X.509, HTTPS DID, trust registry로 발급자 신뢰를 구성할 수 있으며, 폐기·만료·재발급 정책이 필수이다.

## 연결 개념
- DID Document — 발급자와 보유자의 공개키, 서비스 엔드포인트 확인
- OID4VCI/OID4VP — VC 발급·제시 프로토콜
- 선택적 공개 — SD-JWT, BBS 서명, ZKP로 불필요 속성 제거
- 개인정보 영향평가 — 저장 속성, 목적, 보유기간 통제

# 📝 【답안용】 시험 답안 템플릿

> 목적: 시험장에서 25분에 그대로 쓰는 답안 양식. 작성방식(추상표현 금지·수치·도식·문제유형 전환)을 엄격히 지킨다.
> 핵심: VC는 디지털 파일 보관이 아니라 Issuer, Holder, Verifier 간 서명 검증과 선택적 공개로 신원 증명 복제본을 줄이는 구조임.

## 핵심 인사이트 (3줄 요약)

> 1. **본질**: Verifiable Credential은 발급자가 주장(claim)을 전자서명해 보유자가 검증자에게 제시하는 W3C 표준 자격 증명 데이터 모델이다.
> 2. **가치**: 공개키 검증, proof, 만료, 폐기 상태 확인으로 원본 API 조회 없이 자격 위변조를 판정하고 개인정보 저장 속성을 줄인다.
> 3. **판단 포인트**: 발급자 신뢰, 지갑 키 보호, 폐기 반영, 선택적 공개, 감사 로그, W3C VC 2.0·JOSE/COSE 호환성을 함께 봐야 한다.

## 출제 의도 및 답안 포인트

| 출제 의도 | 반드시 짚을 핵심 | 감점 회피 포인트 |
|:---|:---|:---|
| VC 신뢰 구조 이해 확인 | Issuer, Holder, Verifier, VC, VP, proof | 전자문서 저장소로만 설명 |
| 개인정보 최소 수집 판단 확인 | 선택적 공개, 만료, 폐기, purpose binding | 주민번호·주소 전체 저장 전제 |
| 실무 적용 통제 확인 | trust registry, OID4VCI/OID4VP, 검증 로그 | DID·블록체인 필수로 단정 |
> 요약: 이 문제는 VC 데이터 모델보다 발급자 신뢰와 검증 절차를 개인정보 최소화 관점으로 연결해야 한다.

## Ⅰ. 개요 및 필요성

VC는 서명 기반 디지털 자격 증명이다.
기관 간 자격 확인은 원본 스캔, API 조회, 중앙 DB 보관에 의존해 개인정보 복제본과 위변조 확인 비용을 만든다. VC는 발급자가 서명한 증명을 사용자가 보유하고, 검증자는 공개키·폐기 상태·만료일로 진위를 판단한다.

---

## Ⅱ. 구조 및 구성요소

```text
Issuer -> Verifiable Credential -> Holder Wallet -> Verifiable Presentation -> Verifier
           +-> Proof / Signature
           +-> Status / Expiration / Schema
```

| 구성요소 | 역할 | 특이사항 |
|:---|:---|:---|
| Issuer | 자격·속성 claim을 VC로 발급 | 은행, 학교, 공공기관, 기업 |
| Holder | VC 보관, 제출 목적별 VP 생성 | 모바일 지갑, 키 백업 필요 |
| Verifier | VP 서명·상태·발급자 신뢰 검증 | 서비스 접근 승인·거절 |
| Proof | VC 무결성·발급자 확인 | Data Integrity, JOSE, COSE |
| Credential Status | 폐기·정지 여부 표시 | status list, revocation registry |
> 요약: VC 구조는 발급자 서명, 보유자 지갑, 검증자 확인, 폐기 상태가 결합된 3자 신뢰 모델이다.

---

## Ⅲ. 동작원리 및 흐름도

```text
자격 확인 요청 -> VC 발급 -> 지갑 저장 -> VP 생성
-> 서명/스키마/폐기 상태 검증 -> 서비스 승인 / 거절
```

| 단계 | 처리 내용 | 검증 기준 |
|:---:|:---|:---|
| 1 | 발급자가 subject claim과 schema 확정 | W3C VC 2.0 context, type, issuer |
| 2 | proof 생성 후 Holder 지갑에 발급 | 서명 알고리즘, kid, 만료일 |
| 3 | Holder가 목적별 VP와 nonce 생성 | 재사용 공격 방지, 선택 속성 |
| 4 | Verifier가 proof·schema·status 확인 | 공개키 검증, 폐기 미해당, issuer 신뢰 |
| 5 | 검증 결과와 최소 감사 로그 저장 | 속성 저장 3개 이하, 로그 보존 1년 |
> 요약: VC는 발급 시 서명하고 제시 시 nonce와 폐기 상태를 검증해 위조·재사용·만료 증명을 차단한다.

## Ⅳ. 특징

| 구분 | 기존 증명 방식 | VC 방식 | 정량·기술 포인트 |
|:---|:---|:---|:---|
| 검증 | 원본 스캔, 기관 API 조회 | 공개키 proof 검증 | VP 검증 p95 500ms 이하 |
| 개인정보 | 전체 문서 사본 저장 | 필요한 claim만 제시 | 불필요 속성 0개 저장 |
| 상호운용 | 기관별 양식 | W3C VC 2.0, JOSE/COSE | schema 호환 테스트 100% |
| 운영 리스크 | 원본 위조, DB 유출 | 지갑 탈취, 폐기 누락 | 폐기 반영 TTL 10분 이하 |
> 요약: VC는 문서 원본 보관을 서명 검증으로 대체하지만 폐기 상태와 지갑 키 보호를 운영 지표로 관리해야 한다.

## Ⅴ. 심화 비교 및 적용 판단

| 비교 축 | 기존/대안 | VC | 선택 기준 |
|:---|:---|:---|:---|
| 구조 | 중앙 DB 조회, PDF 제출 | Issuer-Holder-Verifier 증명 교환 | 다기관 자격 확인, 개인정보 최소 수집 |
| 비용/성능 | API 연동 기관별 개발 | 지갑·검증 API·status list 구축 | 검증 p95 500ms, 실패율 1% 이하 |
| 운영/위험 | 원본 위조, DB 침해 | 키 분실, 폐기 지연, schema 불일치 | 복구 절차, trust registry, 표준 프로파일 |
> 요약: VC는 다기관 증명 재사용과 최소 속성 제출이 필요한 업무에 적합하고, 내부 단일 권한 관리는 IAM 속성 관리가 적합하다.

| 리스크 | 원인 | 대응 방안 | 확인 지표 |
|:---|:---|:---|:---|
| 위조 VC 수용 | 발급자 공개키·schema 미검증 | trust registry, schema whitelist | 미등록 issuer 차단율 100% |
| 폐기 누락 | status list 미조회, 캐시 과다 | 검증 시 status 확인, 캐시 TTL 10분 | 폐기 반영 10분 이하 |
| 지갑 탈취 | 단말 분실, 개인키 노출 | FIDO2, TEE, 원격 폐기, 백업 키 | 탈취 신고 후 정지 30분 이하 |
> 요약: VC 운영 리스크는 발급자 등록, 폐기 반영, 지갑 보호를 SLA와 로그로 통제한다.

| 점검 항목 | 목표 기준 | 측정 방법 |
|:---|:---|:---|
| 검증 처리 | VP 검증 p95 500ms, 오류율 1% 이하 | 검증 API 로그, APM |
| 개인정보 최소화 | 저장 claim 3개 이하, 원본 문서 0건 | DPIA, 데이터맵 |
| 신뢰 운영 | issuer 인증서 만료 0건, status 조회율 100% | trust registry, revocation log |
> 요약: VC 도입 성과는 검증 지연, 저장 속성 수, 발급자 신뢰 상태, 폐기 조회율로 판단한다.

## Ⅵ. 실무 적용 및 결론

**적용 방안 3개:**
1. 표준 프로파일: W3C VC 2.0, Data Integrity 또는 JOSE/COSE, OID4VCI/OID4VP, schema registry를 업무별로 고정
2. 신뢰 운영: issuer 심사, 공개키 회전 주기 90일, status list TTL 10분, 감사 로그 보존 1년 적용
3. 개인정보 통제: 목적별 VP 템플릿, SD-JWT 선택적 공개, 저장 claim 3개 이하, DPIA 사전 수행

**결론 (2줄):**
- 기술사 판단: 다기관 자격 증명과 개인정보 최소 제출이 필요하면 VC를 적용하고, 단일 서비스 세션 관리는 OIDC·SAML을 유지한다.
- 향후 방향: VC 2.0, OID4VC, 모바일 신분증 지갑과 결합해 API 조회형 신원 확인을 증명 교환형 구조로 전환한다.
