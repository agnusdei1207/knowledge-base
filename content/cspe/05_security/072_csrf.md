## Ⅰ. 개요
- **정의**: 인증된 사용자의 브라우저를 이용해 의도하지 않은 요청을 서버에 전송시키는 공격
- **배경/필요성**: 브라우저가 쿠키를 자동 첨부하는 특성을 악용하여 사용자 모르게 상태 변경 요청이 실행됨
- **비유**: 피해자의 도장이 찍힌 백지 위임장을 악용하는 것과 같음

| 출제 의도 | 반드시 짚을 핵심 | 감점 회피 포인트 |
|:---|:---|:---|
| XSS와 CSRF 차이 이해 | CSRF는 서버가 요청 출처를 검증하지 못하는 문제 | XSS(스크립트 실행)와 혼동 금지 |

> 요약: CSRF는 브라우저의 자동 인증 정보 첨부를 악용하여 피해자 권한으로 위조 요청을 실행함

## Ⅱ. 구성요소
```text
피해자 브라우저 --쿠키 자동첨부--> 대상 서버
      ^                              |
      |                              v
악성 사이트 --위조 요청 유도-->  상태 변경 처리
```

| 구성요소 | 설명 | 비유 |
|:---|:---|:---|
| 세션 쿠키 | 브라우저가 요청마다 자동 첨부하는 인증 토큰 | 자동 날인 도장 |
| 위조 요청 | 공격자가 구성한 폼/이미지/링크로 트리거되는 HTTP 요청 | 위조 서류 |
| CSRF Token | 서버가 발행하고 폼에 삽입하는 1회용 검증 값 | 대조용 시리얼 번호 |

> 요약: 세션 쿠키의 자동 첨부, 위조 요청, CSRF Token이 공격과 방어의 핵심 요소임

## Ⅲ. 절차
```text
악성 페이지 로딩 --> 위조 요청 생성 --> 쿠키 자동 첨부/전송 --> 서버 상태 변경
```
- 1단계: 악성 페이지 로딩 — 피해자가 공격자가 제어하는 페이지를 방문함
- 2단계: 위조 요청 생성 — 숨겨진 폼이나 이미지 태그로 대상 서버 API 호출을 구성함
- 3단계: 쿠키 자동 첨부 — 브라우저가 대상 도메인의 쿠키를 요청에 포함하여 전송함
- 4단계: 서버 상태 변경 — 서버가 정상 요청으로 판단하여 송금, 비밀번호 변경 등을 처리함

> 요약: 악성 페이지에서 유도된 요청이 쿠키와 함께 전송되어 서버가 정상 요청으로 처리함

## Ⅳ. 문제점
- 출처 미검증: 서버가 요청의 Origin/Referer를 확인하지 않아 위조 요청을 수용함
- 쿠키 자동 전송: SameSite 속성 미설정 시 크로스 사이트 요청에도 쿠키가 첨부됨
- GET 상태변경: GET 요청으로 상태 변경을 허용하면 이미지 태그만으로 공격이 가능함

> 요약: 출처 미검증, 쿠키 정책 미흡, GET 상태변경이 CSRF 성공의 원인임

## Ⅴ. 개선방안
1. 단기: CSRF Token을 폼에 삽입하고 서버에서 매 요청 검증함
2. 중기: 쿠키에 `SameSite=Lax` 이상 설정하여 크로스 사이트 자동 전송을 차단함
3. 장기: 상태 변경 API를 POST/PUT/DELETE로 한정하고 Origin 헤더 검증을 표준화함

> 요약: CSRF Token, SameSite 쿠키, HTTP 메서드 제한으로 단계적으로 방어함

## Ⅵ. 전망
- 발전 방향: SameSite 쿠키 기본값이 Lax로 변경되면서 기존 CSRF 공격 벡터가 감소 추세
- 기술사적 판단: SPA에서는 JWT Bearer 토큰 사용으로 쿠키 기반 CSRF 위협이 줄지만, 하이브리드 인증 환경에서는 여전히 유효함
- 기술사 제언: 쿠키 기반 인증 사용 시 CSRF Token과 SameSite를 병행 적용해야 함
