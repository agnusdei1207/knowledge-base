# 📖 【암기용】 개념 완전 이해

> 목적: CSRF를 처음 봐도 완벽히 이해하게 만든다. 시험 답안 양식이 아니라, 이해를 위한 친절한 설명이다.

## 한눈에
- **개요**: 로그인 사용자의 브라우저가 원치 않는 상태 변경 요청을 보내게 하는 공격
- **왜 필요한가**: 브라우저는 대상 사이트 쿠키를 자동 첨부하므로, 사용자가 공격 페이지를 열기만 해도 송금, 비밀번호 변경, 관리자 설정 변경 요청이 인증된 요청처럼 도착할 수 있다.
- **핵심 직관**: 공격자는 쿠키를 훔치지 않고, 이미 로그인된 브라우저를 원격 조종해 요청만 대신 보낸다.

## 깊이 이해
- **배경·문제의식**: 쿠키 기반 세션은 사용자가 직접 만든 요청과 외부 사이트가 유도한 요청을 쿠키만으로 구분하지 못한다. 특히 GET으로 상태를 변경하거나 토큰 없는 POST를 허용하면 요청 출처 검증이 빠진다.
- **작동 원리**: 피해자가 로그인 상태에서 공격 페이지를 방문하면 브라우저가 대상 사이트로 요청을 전송한다. 서버가 CSRF token, Origin/Referer, SameSite, 재인증을 확인하지 않으면 상태 변경이 수행된다.
- **비유**: 도장이 찍힌 빈 위임장을 사용자가 들고 있는데, 공격자가 옆에서 다른 신청서를 끼워 넣어 창구에 제출하게 만드는 상황임.
- **구체 예시**: 관리자 콘솔의 `/user/delete`가 토큰 없는 POST와 세션 쿠키만 확인하면, 외부 페이지의 자동 제출 form으로 계정 삭제 요청이 발생할 수 있다.
- **흔한 오해·주의점**: CORS 차단은 CSRF 방어가 아니다. 브라우저가 응답을 공격자에게 읽게 하지 못할 뿐, 요청 전송 자체는 발생할 수 있다.

## 연결 개념
- SameSite 쿠키 — cross-site 요청에서 쿠키 첨부 여부 제한
- CSRF Token — 사용자 세션과 요청 본문을 결합한 예측 불가 값
- Idempotency — GET은 조회, POST/PUT/DELETE는 상태 변경으로 분리

# 📝 【답안용】 시험 답안 템플릿

> 목적: 시험장에서 25분에 그대로 쓰는 답안 양식. 작성방식(추상표현 금지·수치·도식·문제유형 전환)을 엄격히 지킨다.
> 핵심: CSRF 답안은 공격 payload가 아니라 세션 쿠키 자동 첨부, 상태 변경 API, 요청 출처 검증 부재를 연결해야 한다.

## 핵심 인사이트 (3줄 요약)

> 1. **본질**: CSRF는 인증된 브라우저를 이용해 사용자의 의도와 다른 상태 변경 요청을 서버에 제출하는 취약점이다.
> 2. **가치**: SameSite, CSRF token, Origin/Referer 검증, 재인증을 조합하면 요청 의도와 출처를 검증할 수 있다.
> 3. **판단 포인트**: GET 상태 변경 제거, 토큰 검증 실패 로그, 고위험 기능 재인증을 API 설계 단계에서 반영해야 한다.

## 출제 의도 및 답안 포인트

| 출제 의도 | 반드시 짚을 핵심 | 감점 회피 포인트 |
|:---|:---|:---|
| 세션 기반 웹 공격 이해 확인 | 쿠키 자동 첨부와 사용자 의도 검증 부재 | XSS와 혼동해 스크립트 실행만 설명 |
| 방어 기법 선택 역량 확인 | SameSite, CSRF token, Origin/Referer, 재인증 | CORS를 CSRF 방어의 주 수단으로 서술 |
| API 설계 관점 확인 | 상태 변경 메서드, idempotency, 로그·재검증 | GET 상태 변경 문제와 토큰 실패 지표 누락 |

> 요약: CSRF는 세션 쿠키가 아니라 요청 의도를 검증하는 문제이며, 상태 변경 API 설계가 채점 포인트이다.

## Ⅰ. 개요 및 필요성

- 개요: 로그인 세션 위조 요청 공격
- 배경: 브라우저가 세션 쿠키를 자동 첨부하므로 서버는 외부 사이트가 유도한 요청과 사용자가 의도한 요청을 구분해야 함.
- 필요성: OWASP ASVS 기준으로 CSRF token, SameSite=Lax/Strict, Origin·Referer 검증을 적용해 금융·관리자·개인정보 변경 요청을 보호해야 함.

---

## Ⅱ. 구조 및 구성요소

```text
Victim Browser -> Auth Cookie -> Target State-Changing API
Attack Site -> Hidden Form/Image/Fetch Attempt -> Browser Request
Defense -> SameSite Cookie -> CSRF Token -> Origin Check -> Audit Log
```

| 구성요소 | 역할 | 특이사항 |
|:---|:---|:---|
| 피해 브라우저 | 로그인 세션 쿠키 자동 첨부 | 공격자가 쿠키 값을 몰라도 요청 가능 |
| 상태 변경 API | 송금, 삭제, 설정 변경 처리 | GET 상태 변경 금지 필요 |
| 검증 토큰 | 세션과 요청을 결합하는 난수 | 예측 불가, 요청별 또는 세션별 관리 |
| 출처 검증 | Origin, Referer, SameSite 확인 | 프록시·모바일 앱 예외 정책 필요 |

> 요약: CSRF 구조는 인증 쿠키, 상태 변경 API, 요청 의도 검증 요소의 결합으로 분석한다.

## Ⅲ. 동작원리 및 흐름도

```text
로그인 세션 생성 -> 공격 페이지 방문 -> 브라우저가 대상 API로 요청 전송
-> 쿠키 자동 첨부 -> 서버 검증 누락 -> 상태 변경 수행 -> 감사로그 확인
```

| 단계 | 처리 내용 | 검증 기준 |
|:---:|:---|:---|
| 1 | 사용자가 대상 사이트에 로그인 | 세션 쿠키 `Secure HttpOnly SameSite` 확인 |
| 2 | 외부 사이트가 상태 변경 요청을 유도 | cross-site 요청 여부 기록 |
| 3 | 서버가 CSRF token과 Origin을 검증 | 토큰 누락·불일치 시 403 |
| 4 | 고위험 기능에 재인증 또는 2FA 요구 | 송금·권한 변경 재인증 로그 |

> 요약: CSRF는 로그인 세션, 외부 유도 요청, 검증 누락, 상태 변경의 순서로 발생한다.

## Ⅵ. 실무 적용 및 결론

**적용 방안 3개 (필수 — 단계별 또는 항목별):**
1. API 설계: GET 상태 변경 제거, POST/PUT/DELETE 변경 요청에 CSRF middleware와 idempotency key 적용
2. 브라우저 정책: 인증 쿠키에 `Secure`, `HttpOnly`, `SameSite=Lax` 기본 적용, 외부 IdP 연동은 `None; Secure` 예외 등록
3. 운영 검증: Origin/Referer 실패, token mismatch, 재인증 실패를 403 코드와 사용자·IP·UA로 감사로그 수집

**결론 (2줄):**
- 기술사 판단: 일반 업무 변경 API는 SameSite+토큰 검증, 금융·관리자 기능은 재인증과 MFA step-up까지 적용함
- 향후 방향: SPA와 OAuth 연동 환경에서는 SameSite 예외를 최소화하고 BFF 패턴으로 토큰 노출면을 줄임
