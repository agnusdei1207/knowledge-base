## 미리 알고가기

- CSRF는 공격자가 직접 로그인하지 않아도 피해자 브라우저의 인증 상태를 이용해 요청을 보내게 만드는 공격임
- 브라우저가 쿠키를 자동 첨부하고 서버가 요청 출처를 충분히 검증하지 않으면 성립함
- 방어의 핵심은 CSRF 토큰과 SameSite 쿠키와 서버 측 출처 검증을 함께 쓰는 데 있음

## Ⅰ. 개요

- **정의/개념**: CSRF는 피해자 브라우저가 로그인 상태로 공격자가 의도한 상태 변경 요청을 전송하게 만드는 공격임
- **배경/필요성**: 세션 쿠키 기반 서비스는 브라우저가 인증 정보를 자동 첨부함. 출처 검증이 없으면 결제와 권한 변경이 악용됨

## Ⅱ. 특징

- 공격 코드는 브라우저에서 실행되지만 목적은 스크립트 실행이 아니라 요청 위조임
- GET 요청 남용, CSRF 토큰 부재, SameSite 미설정이 대표 원인임
- 서버가 세션만 보고 요청을 신뢰하면 사용자 의도 여부를 구분하지 못함
- JSON API나 SPA라도 쿠키 기반 세션이면 CSRF 위험이 남음

## Ⅲ. 종류 및 비교

| 판단 기준 | 토큰 없는 세션 기반 요청 | 토큰 검증이 있는 요청 |
|:---|:---|:---|
| 인증 정보 | 브라우저가 쿠키를 자동 첨부함 | 쿠키 첨부와 함께 별도 토큰 검증 수행 |
| 위조 가능성 | 외부 페이지에서 요청 유도가 쉬움 | 공격자가 토큰을 모르므로 위조가 어려움 |
| 서버 판단 기준 | 세션 존재 여부만 확인 | 세션 + 출처/토큰 일치 여부 확인 |
| 운영 주의점 | GET 상태 변경, SameSite 미설정에 취약 | 토큰 누락 화면과 예외 API를 점검해야 함 |

## Ⅳ. 구성요소 및 구조

| 구성요소 | 설명 |
|:---|:---|
| 인증 상태 | 브라우저가 유지 중인 세션 쿠키나 자동 인증 정보임 |
| 위조 요청 유도점 | 외부 사이트의 폼, 링크, 이미지, 스크립트 등이 사용됨 |
| 상태 변경 엔드포인트 | 송금, 비밀번호 변경, 게시물 수정 같은 기능임 |
| 방어 통제 | CSRF 토큰, SameSite, Origin/Referer 검증, 메서드 제한이 포함됨 |

```text
피해자 로그인 상태 -> 악성 페이지 방문 -> 브라우저가 요청 전송 -> 서버가 정상 요청으로 처리
```

## Ⅴ. 원리 및 절차 흐름도

```text
세션 유지 -> 악성 요청 유도 -> 쿠키 자동 첨부 -> 출처 미검증 -> 상태 변경 수행
```

1. **세션 유지**: 사용자가 대상 서비스에 로그인해 세션을 보유함
2. **악성 요청 유도**: 공격자가 외부 페이지나 메일 링크로 요청을 만들게 함
3. **쿠키 자동 첨부**: 브라우저가 대상 서비스 쿠키를 함께 전송함
4. **출처 미검증**: 서버가 토큰이나 Origin 없이 요청을 승인함
5. **상태 변경 발생**: 사용자 의도와 무관한 작업이 완료됨

## Ⅵ. 실무 적용 및 유의점

1. 세션 쿠키 기반 서비스는 상태 변경 요청에 CSRF 토큰과 SameSite를 적용하고 토큰 누락 재현 실패·Origin 검증으로 확인함
2. 레거시 화면·신규 API 혼재 환경은 공통 미들웨어로 강제하고 예외 엔드포인트 최신성·위조 요청 차단 여부로 확인함

## Ⅶ. 결론

- CSRF는 인증보다 요청 의도 검증 문제이므로 세션 존재가 아니라 토큰과 출처 검증으로 승인 기준을 바꿔야 함
