# 📖 【암기용】 개념 완전 이해

> 목적: DID와 SSI를 중앙 로그인 계정이 아닌 사용자 주권형 신원 모델로 이해하게 만든다. 시험 답안 양식이 아니라, 이해를 위한 친절한 설명이다.

## 한눈에
- **개요**: 사용자가 자신의 식별자와 증명서를 지갑에 보관하고 필요한 속성만 제출하는 디지털 신원 체계
- **왜 필요한가**: 중앙 IdP가 모든 개인정보를 보관하면 유출·추적·사업자 종속 위험이 생긴다. DID·SSI는 검증 가능한 증명과 선택적 공개로 개인정보 노출을 줄인다.
- **핵심 직관**: 주민등록증 사본을 매번 제출하는 대신, "성인임" 같은 필요한 사실만 공인 도장으로 증명하는 방식임

## 깊이 이해
- **배경·문제의식**: 기존 로그인은 이메일, 휴대폰, IdP 계정에 의존한다. 서비스마다 개인정보를 저장하면 유출면이 커지고 사용자는 어떤 속성이 어디에 보관되는지 알기 어렵다.
- **작동 원리**: 발급자가 사용자 지갑에 Verifiable Credential을 발급한다. 사용자는 검증자에게 필요한 속성만 Verifiable Presentation으로 제출한다. 검증자는 DID Document의 공개키와 서명을 확인해 위변조 여부를 판정한다.
- **비유**: 대학이 졸업증명서를 봉인해 주면 사용자가 회사에 제출하고, 회사는 대학 도장과 문서 무결성만 확인하는 구조와 유사함
- **구체 예시**: 금융 앱은 실명 전체와 주소를 저장하지 않고, 은행이 발급한 KYC VC에서 "본인확인 완료", "만 19세 이상" 속성만 받아 1회 검증한다.
- **흔한 오해·주의점**: DID가 반드시 블록체인을 의미하지는 않는다. DID Method, 키 복구, 지갑 분실, 발급자 신뢰, 개인정보 규제 적합성이 함께 설계되어야 한다.

## 연결 개념
- Verifiable Credential — 발급자가 서명한 검증 가능 속성 증명
- Zero-Knowledge Proof — 필요한 사실만 증명하는 선택적 공개 기술
- eIDAS 2.0/EUDI Wallet — 유럽 디지털 신원 지갑 정책 흐름
- 패스키 — 지갑 접근과 사용자 인증을 피싱 저항 키 기반으로 보호

# 📝 【답안용】 시험 답안 템플릿

> 목적: 시험장에서 25분에 그대로 쓰는 답안 양식. 작성방식(추상표현 금지·수치·도식·문제유형 전환)을 엄격히 지킨다.
> 핵심: DID·SSI는 중앙 계정 로그인 대체가 아니라 발급자, 보유자, 검증자 간 검증 가능한 증명 교환과 개인정보 최소 공개 체계임.

## 핵심 인사이트 (3줄 요약)

> 1. **본질**: DID(Decentralized Identifier)와 SSI(Self-Sovereign Identity)는 사용자가 신원 증명을 보유하고 필요한 속성만 검증자에게 제출하는 디지털 신원 모델이다.
> 2. **가치**: 공개키 기반 DID Document, Verifiable Credential, 선택적 공개로 중앙 DB 유출면과 불필요한 개인정보 저장을 줄인다.
> 3. **판단 포인트**: 신뢰 앵커, 키 복구, 폐기 목록, 지갑 보안, 법적 효력, 상호운용 표준을 함께 검토해야 한다.

## 출제 의도 및 답안 포인트

| 출제 의도 | 반드시 짚을 핵심 | 감점 회피 포인트 |
|:---|:---|:---|
| DID·SSI 구성 이해 확인 | Issuer, Holder, Verifier, DID Document, VC/VP | 블록체인 지갑으로만 설명 |
| 개인정보 최소 공개 판단 확인 | 선택적 공개, ZKP, 속성 기반 검증 | 개인정보를 새 저장소로 옮기는 답안 |
| 실무 적용 리스크 확인 | 키 분실 복구, 폐기, 발급자 신뢰, 표준 호환 | 법·감사·상호운용성 누락 |
> 요약: 이 문제는 분산 식별자와 검증 가능 증명의 신뢰 구조를 개인정보 최소 공개 관점에서 설명해야 한다.

## Ⅰ. 개요 및 필요성

- 개요: 사용자 주권형 신원 모델
- 배경: 중앙 IdP와 서비스별 계정 저장은 개인정보 유출면, 서비스 간 추적 가능성, 사업자 종속을 만든다.
- 필요성: W3C DID·VC 표준으로 발급자 서명 증명을 사용자가 보유하고 필요한 속성만 검증자에게 제시해야 한다.

---

## Ⅱ. 구조 및 구성요소

```text
Issuer -> Verifiable Credential -> Holder Wallet -> Verifiable Presentation -> Verifier
           +-> DID Document/Public Key
           +-> Revocation Registry
```

| 구성요소 | 역할 | 특이사항 |
|:---|:---|:---|
| Issuer | 신원·자격 속성을 VC로 발급 | 은행, 학교, 공공기관 |
| Holder Wallet | VC 보관, VP 생성, 키 관리 | 모바일 지갑, HSM, 백업 |
| Verifier | VP 서명·상태·발급자 신뢰 확인 | 서비스 사업자, 기관 |
| DID Document | 공개키, 서비스 엔드포인트, 인증 메서드 제공 | DID Method별 저장소 상이 |
| Revocation Registry | 폐기·정지 상태 확인 | 개인정보 노출 없는 상태 확인 필요 |
> 요약: DID·SSI는 발급자, 보유자, 검증자, DID 문서, 폐기 목록이 결합된 증명 교환 구조이다.

---

## Ⅲ. 동작원리 및 흐름도

```text
DID 생성 -> VC 발급 -> 지갑 보관 -> VP 생성
-> 서명/폐기 상태 검증 -> 서비스 접근 / 거절
```

| 단계 | 처리 내용 | 검증 기준 |
|:---:|:---|:---|
| 1 | 사용자가 DID와 키쌍 생성 | 개인키 지갑 보관, 공개키 DID Document 등록 |
| 2 | 발급자가 VC 서명 발급 | W3C VC Data Model, JSON-LD 또는 JWT |
| 3 | 사용자가 VP 생성 | 필요한 속성만 선택, nonce 포함 |
| 4 | 검증자가 서명·발급자·폐기 상태 확인 | 공개키 검증, revocation status valid |
| 5 | 서비스 접근 및 감사 기록 | 최소 속성 저장, 검증 로그 보관 |
> 요약: DID·SSI는 공개키 서명과 폐기 상태 확인으로 중앙 조회 없이 증명 위변조를 검증한다.

## Ⅳ. 특징

| 구분 | 중앙 IdP 모델 | DID·SSI | 정량·기술 포인트 |
|:---|:---|:---|:---|
| 신원 보관 | 사업자 DB 중심 | 사용자 지갑 중심 | VC 원본 서버 저장 최소화 |
| 검증 방식 | IdP 실시간 질의 | 서명 검증, 폐기 상태 확인 | W3C DID/VC, OIDC4VC |
| 개인정보 | 서비스별 속성 저장 | 선택적 공개, ZKP | 불필요 속성 0개 저장 목표 |
| 운영 리스크 | IdP 장애·유출 | 키 분실·지갑 보안 | 복구 절차 성공률 99% |
> 요약: DID·SSI는 중앙 저장소 의존을 줄이지만 키 관리와 폐기 검증 체계를 반드시 설계해야 한다.

## Ⅴ. 심화 비교 및 적용 판단

| 구분 | 기존/대안 | DID·SSI | 선택 기준 |
|:---|:---|:---|:---|
| 구조 | SSO, 중앙 IdP, 계정 DB | Issuer-Holder-Verifier, VC/VP | 다기관 증명 교환, 개인정보 최소화 요구 |
| 비용/성능 | IdP 연동 단순 | 지갑, 발급, 검증, 폐기 인프라 필요 | 검증 p95 500ms 이하 |
| 운영/위험 | 중앙 장애·유출 | 키 분실, 지갑 탈취, 표준 호환 | 복구·폐기 SLA 24시간 이내 |
> 요약: 다기관 자격 증명과 개인정보 최소 공개가 핵심이면 DID·SSI가 적합하고 단일 기업 로그인은 SSO가 적합하다.

| 리스크 | 원인 | 대응 방안 | 확인 지표 |
|:---|:---|:---|:---|
| 키 분실 | 사용자 지갑 삭제, 단말 교체 | 사회적 복구, 백업 키, HSM 연계 | 복구 성공률 99% |
| 증명 폐기 누락 | revocation registry 미조회 | 상태 검증 의무화, 캐시 TTL 10분 | 폐기 반영 10분 이하 |
| 상호운용 실패 | DID Method·VC 포맷 불일치 | W3C DID/VC, OIDC4VC, DIF 프로파일 | 호환 테스트 100% |
> 요약: DID·SSI 리스크는 키 복구, 폐기 반영, 표준 호환성을 운영 지표로 통제한다.

| 점검 항목 | 목표 기준 | 측정 방법 |
|:---|:---|:---|
| 개인정보 최소화 | 서비스 저장 속성 3개 이하, 불필요 속성 0개 | DPIA, 데이터맵 |
| 검증 품질 | VP 검증 p95 500ms, 실패율 1% 이하 | 검증 API 로그 |
| 신뢰 운영 | 발급자 인증서 만료 0건, 폐기 반영 10분 이하 | Trust registry, revocation log |
> 요약: 도입 성과는 저장 속성 수, 검증 지연, 폐기 반영, 발급자 신뢰 상태로 판단한다.

## Ⅵ. 실무 적용 및 결론

**적용 방안 3개:**
1. 유스케이스 선정: 성인 여부, 재직 증명, 자격 증명처럼 속성 선택 공개가 가능한 업무부터 적용
2. 신뢰 체계 구축: Issuer 심사, DID Method 선정, W3C VC·OIDC4VC 프로파일, revocation registry 운영
3. 지갑 보안 운영: 생체 인증, Secure Enclave/TEE, 백업 키, 분실 복구 절차, 감사 로그 보존 1년 적용

**결론 (2줄):**
- 기술사 판단: 다기관 증명 교환과 개인정보 최소화가 필요하면 DID·SSI를 적용하고, 단일 조직 내부 로그인은 SAML/OIDC SSO를 유지한다.
- 향후 방향: 모바일 신분증, EUDI Wallet, 패스키와 결합해 신원 증명의 선택적 공개와 상호운용성이 확대된다.
