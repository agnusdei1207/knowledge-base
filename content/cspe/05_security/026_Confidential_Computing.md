## Ⅰ. 개요
| 항목 | 내용 |
|---|---|
| **정의** | 클라우드 환경에서 '사용 중(In Use)'인 데이터와 코드를 하드웨어 기반의 TEE에 격리하여 클라우드 사업자조차 접근하지 못하게 보호하는 클라우드 보안 아키텍처임 |
| **배경/필요성** | 저장(At Rest) 및 전송(In Transit) 중인 데이터는 암호화로 보호되나, 메모리에 올라가 연산되는 순간의 취약점(In Use) 해결 필요 |
| **출제 의도** | TEE 기술의 클라우드 확장 모델인 기밀 컴퓨팅의 개념 및 CCC(Confidential Computing Consortium) 주도의 데이터 완전 제어권 확보 전략 이해 |

## Ⅱ. 구성요소
```text
+-------------------+      +-------------------+      +-------------------+
| Secure Enclave    |      | Remote Attestation|      | Cloud Provider    |
| (클라우드 내 격리)+----->| (원격 무결성 증명)+----->| (접근 권한 박탈)  |
+-------------------+      +-------------------+      +-------------------+
```
| 구성요소 | 설명 | 비유 |
|---|---|---|
| **보안 엔클레이브 (Enclave)** | 클라우드 서버 메모리 내에 생성되는 접근 통제 및 암호화된 하드웨어 기반 실행 공간임 | 빌딩(클라우드) 내 세입자 전용 특수 금고 |
| **원격 증명 (Attestation)** | 클라이언트가 클라우드 상의 엔클레이브가 변조되지 않았음을 암호학적으로 검증하는 절차임 | 금고가 정품인지 원격으로 확인하는 스캐너 |
| **클라우드 하이퍼바이저** | 인프라를 제공하지만, 기밀 컴퓨팅 환경에서는 엔클레이브 내부에 논리적/물리적으로 접근 불가능함 | 열쇠가 없어 금고를 열지 못하는 건물 관리인 |

> 요약: 클라우드 인프라는 빌려 쓰되, 내부 데이터는 클라우드 관리자도 훔쳐볼 수 없게 원천 봉쇄하는 컴퓨팅 패러다임임.

## Ⅲ. 절차
```text
+----------------+   +----------------+   +----------------+   +----------------+
| 1. Enclave 생성|-->| 2. 원격 증명   |-->| 3. 키/데이터 주입|-->| 4. 기밀 연산   |
| (하드웨어 할당)|   | (무결성 검증)  |   | (암호화 전송)  |   | (메모리 보호)  |
+----------------+   +----------------+   +----------------+   +----------------+
```
1. **엔클레이브 생성**: 클라이언트 요청에 따라 클라우드 하드웨어(CPU)가 메모리에 암호화된 독립 공간(Enclave)을 할당함
2. **원격 증명 수행**: 클라이언트가 해당 엔클레이브의 하드웨어 서명과 해시값을 받아 올바른 TEE 환경인지 원격으로 검증함
3. **비밀 데이터 주입**: 검증이 완료되면 클라이언트가 암호화된 채널로 민감한 데이터와 암호키를 엔클레이브 내부로 전송함
4. **기밀 연산 수행**: 엔클레이브 내부에서 복호화 및 데이터 연산(AI 학습 등)이 수행되며, 이때 메모리 덤프나 하이퍼바이저 접근은 완벽히 차단됨

> 요약: 안전한 방을 만들고 진짜인지 검증한 뒤, 그 방 안에 데이터와 열쇠를 던져넣고 연산시키는 과정임.

## Ⅳ. 문제점
* **기존 앱의 수정(Refactoring) 부담**: Intel SGX 등 일부 아키텍처는 엔클레이브 내에서 실행하기 위해 애플리케이션 코드를 분리/수정해야 하는 막대한 개발 부담 초래
* **하드웨어 종속성 심화**: 특정 CPU 벤더(Intel, AMD)의 고유 명령어 셋과 하드웨어 스펙에 강력히 종속되어 멀티 클라우드 간 이식성 저하
* **부채널 및 하드웨어 결함 노출**: 멜트다운(Meltdown)이나 폴트 인젝션 등 CPU 자체의 하드웨어 결함이 발견되면 기밀 컴퓨팅 모델의 근간이 흔들림

## Ⅴ. 개선방안
* **단기 방안 (Lift & Shift 지원)**: 코드 수정 없이 전체 가상머신(VM) 자체를 통째로 기밀 보호하는 기술(AMD SEV-SNP, Intel TDX)을 우선 적용
* **중기 방안 (CCC 프레임워크 표준화)**: 리눅스 재단 산하 CCC가 주도하는 오픈소스 API(Open Enclave 등)를 채택하여 벤더 종속성을 완화
* **장기 방안 (오픈 하드웨어 설계 도입)**: RISC-V와 같은 오픈소스 명령어 세트 기반의 투명한 보안 하드웨어 설계를 도입해 미지의 칩셋 취약점 최소화

## Ⅵ. 전망
* 개인정보 결합 기반의 AI 연합 학습, 금융 기관의 클라우드 마이그레이션 등 데이터 보호 규제가 극심한 산업군의 클라우드 전환을 위한 필수 마스터키임
* 단순 서버(IaaS) 보호를 넘어 쿠버네티스 기밀 컨테이너(Confidential Containers) 등 클라우드 네이티브 환경 전반으로 적용 범위가 급속히 확장 중임
