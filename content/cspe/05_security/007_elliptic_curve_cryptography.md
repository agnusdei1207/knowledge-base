# 📖 【암기용】 개념 완전 이해

## 한눈에
- **개요**: **ECC는 타원곡선 위 점의 스칼라 곱을 역산하기 어렵다는 난제(ECDLP)를 안전성의 근거로 삼는 공개키 암호 계열**임. 비대칭 암호의 기본 개념(키쌍·공개키/개인키 역할)은 (002 참조), 키 교환 원리는 (006 DH 참조).
- **왜 필요한가**: 같은 128비트 보안 강도를 RSA는 3072비트 키로, ECC는 256비트 곡선(P-256)으로 달성함. 키·서명·인증서가 작아 모바일·IoT·TLS 핸드셰이크처럼 대역폭과 연산이 제약된 환경에 적합함.
- **핵심 직관**: 기준점 G를 k번 더해 Q를 만드는 계산은 빠르지만, G와 Q만으로 k를 되찾는 것은 사실상 불가능하다는 일방향성이 ECC의 안전성 근거임.

## 핵심 용어 정리 (내부에 등장하는 것들)

ECC 답안에 등장하는 표기·알고리즘을 먼저 직관적으로 풀어 둠. 상위 핵심 키워드는 **ECDLP(타원곡선 이산대수 문제)** 이며, 여기서 모든 안전성이 파생됨.

| 용어/표기 | 의미 | 비유·예 |
|:---|:---|:---|
| ECDLP | Q=dG에서 G·Q를 알아도 d를 못 구하는 타원곡선 이산대수 난제 | 도착점만 보고 몇 걸음 걸었는지 역산 불가 |
| 점 덧셈 / 스칼라 곱 | 곡선 위 두 점을 더하는 규칙 / 점을 정수배(dG) 하는 반복 덧셈 | 정해진 규칙으로 지도 위를 이동 |
| 개인키 d / 공개키 Q | d는 비밀 난수 정수, Q=dG는 곡선 위 점 | d=도장 원판, Q=공개된 도장 자국 |
| G(기준점) / 곡선 파라미터 | 모두가 공유하는 시작점과 유한체·곡선식 | 공동 지도와 출발 지점 |
| P-256 / P-384 | NIST 표준 소수체 곡선, 각각 약 128·192비트 강도 | 국가표준 규격 지도 |
| Curve25519 / X25519 | 몽고메리 곡선과 그 위 ECDH 키 교환 방식 | 구현 실수에 강한 신형 지도 |
| ECDH / ECDHE | 곡선 기반 키 교환 / E는 매 세션 임시키(PFS) | 매번 새 자물쇠로 비밀 합의 |
| ECDSA / EdDSA(Ed25519) | 곡선 기반 서명 / 결정적 난수를 쓰는 개선형 서명 | 지문에 개인 도장 날인 |
| nonce k | 서명 때 매번 새로 뽑는 일회성 난수 | 재사용 1회면 개인키가 통째로 노출 |
| invalid curve 공격 | 곡선 위에 없는 조작된 공개키를 넣어 비밀을 캐는 공격 | 위조 지도로 상대를 유인 |
| KDF / PFS | 공유점에서 세션키를 뽑는 함수 / 과거 세션키 안전성 | 원재료를 실제 열쇠로 가공 |
| Shor 알고리즘 | 양자컴퓨터가 이산대수·소인수분해를 깨는 알고리즘 | ECDLP 난제 자체를 무력화 |
| ML-KEM / ML-DSA | 양자내성 표준 키캡슐화 / 서명(FIPS 203/204) | ECC 다음 세대 대체·병행재 |

## 깊이 이해
- **배경·문제의식**: 공개키 암호는 인증·키 교환·서명에 필수지만 RSA는 보안 강도를 올릴수록 키 길이가 급증함(128b→3072b, 192b→7680b). 인증서 크기·서명 검증 비용·핸드셰이크 트래픽이 함께 커져 모바일·IoT에 부담이 됨. ECC는 훨씬 짧은 키로 동일 강도를 제공해 이 문제를 완화함.
- **작동 원리(어떻게+왜)**: 개인키 d는 난수 정수, 공개키 Q=dG는 스칼라 곱 결과 점임. 곱셈은 빠르나 역연산(ECDLP)은 준지수 시간 알고리즘이 없어 지수적으로 어려움 — 이 비대칭성이 안전성의 핵심임. 같은 키쌍으로 ECDH(공유점 계산→KDF)와 ECDSA/EdDSA(해시+개인키 서명)를 모두 수행함.
- **비유**: 공동 지도에서 출발점 G를 정하고 같은 규칙으로 여러 번 이동해 도착점 Q를 만드는 것은 쉽지만, 도착점만 보고 이동 횟수를 역산하는 것은 사실상 불가능함.
- **구체 예시**: NIST SP 800-57 기준 RSA 3072b·ECC P-256은 모두 약 128비트 강도로 취급됨. TLS 1.3은 X25519·P-256 ECDHE로 세션키를 합의하고, 다수 X.509 인증서가 ECDSA P-256 서명을 사용함.
- **흔한 오해·주의점**: (1) ECC는 곧 암호화가 아님 — 키 교환(ECDH), 서명(ECDSA/EdDSA), 암호화 응용(ECIES)로 용도가 갈림. (2) 짧은 키가 곧 안전은 아님 — nonce 재사용·invalid curve·사이드채널 등 구현 결함이 실제 사고 원인임. (3) ECC도 Shor 알고리즘에는 RSA와 똑같이 취약함.

## 연결 개념
- ECDHE — TLS 1.3 세션키 합의와 전방향 안전성(PFS) 제공
- ECDSA·EdDSA — 곡선 기반 전자서명 (008 참조)
- PQC(ML-KEM/ML-DSA) — Shor 알고리즘 대비 양자내성 대체·병행 기술

# 📝 【답안용】 시험 답안 템플릿

## 핵심 인사이트 (3줄 요약)

> 1. **본질**: ECC는 타원곡선 이산대수 난제(ECDLP)를 근거로 키 교환·전자서명을 제공하는 공개키 암호 계열임.
> 2. **가치**: P-256 256비트 키가 RSA 3072비트와 동일한 128비트 강도를 제공해 인증서·핸드셰이크 트래픽을 축소함.
> 3. **판단 포인트**: 곡선 선택·난수 품질·공개키 검증·사이드채널 대응·PQC 전환을 함께 판단해야 함.

## 출제 의도 및 답안 포인트

| 출제 의도 | 반드시 짚을 핵심 | 감점 회피 포인트 |
|:---|:---|:---|
| 공개키 원리 이해 확인 | ECDLP, 개인키 d, 공개키 Q=dG, 스칼라 곱 | 타원 "방정식" 소개에만 머무름 |
| 적용 기준 판단 확인 | ECDH/ECDHE, ECDSA/EdDSA, P-256/X25519 | 키 교환·서명 용도 혼동 |
| 운영 통제 역량 확인 | nonce 재사용, invalid curve, 사이드채널, 키 검증 | "키가 작다"만 쓰고 운영 위험 누락 |

> 요약: ECC 답안은 작은 키의 장점보다 곡선·난수·검증·용도 구분을 채점 축으로 삼아야 함.

## Ⅰ. 개요 및 필요성

- 개요: 타원곡선 난제 기반 공개키 암호 계열임.
- 배경: RSA는 보안 강도 상승 시 키 길이가 급증(128b에 3072b)해 인증서 크기·연산량·트래픽이 함께 커짐.
- 필요성: ECC P-256은 256비트 키로 약 128비트 강도를 제공해 TLS·모바일·IoT·블록체인 서명의 키 크기와 연산 부담을 줄임.
- 전제: 비대칭 키쌍·공개키 배포 신뢰는 (002 비대칭·006 DH 참조)로 위임하고 곡선 고유 논점에 집중함.

---

## Ⅱ. 구조 및 구성요소

```text
곡선 파라미터 -> 기준점 G -> 개인키 d -> 공개키 Q=dG
  / ECDH(E): 상대 Q에 d 곱 -> 공유점 -> KDF -> 세션키
  / ECDSA/EdDSA: 해시 -> 서명(r,s) -> 공개키로 검증
```

| 구성요소 | 역할 | 특이사항 |
|:---|:---|:---|
| 곡선 파라미터 | 유한체·곡선식·기준점 G·차수 정의 | P-256/P-384/Curve25519 표준 사용 |
| 개인키 d | 비밀 스칼라 난수 | CSPRNG 생성, HSM/KMS 보관 |
| 공개키 Q=dG | 스칼라 곱 결과 점 | 수신 시 point-on-curve 검증 필수 |
| ECDH/ECDHE | 세션키 합의 | ECDHE는 임시키로 PFS 제공 |
| ECDSA/EdDSA | 서명 생성·검증 | nonce k 재사용 시 개인키 노출 |

> 요약: ECC 구성은 곡선 파라미터·키쌍·용도별 알고리즘으로 나뉘며 공개키 검증이 필수 통제임.

---

## Ⅲ. 동작원리 및 흐름도

```text
곡선 선택 -> 개인키 d 생성 -> 공개키 Q=dG 계산 -> 용도 분기
  / ECDHE: 상대 Q 검증 -> 공유점 계산 -> KDF -> 세션키
  / ECDSA: 해시·nonce 생성 -> 서명 -> 상대가 공개키로 검증
```

1. 조직 암호정책과 TLS 지원 그룹에 맞춰 사용자가 P-256·P-384·X25519 곡선을 선택함.
2. 사용자가 CSPRNG로 개인키 d와 서명용 nonce를 생성하고, nonce 재사용 0건을 보장함.
3. 사용자가 공개키 Q=dG를 산출해 X.509 인증서에 등록하고, 검증자는 수신 공개키의 곡선 소속을 확인함.
4. 통신 주체가 ECDHE 키 교환 또는 ECDSA/Ed25519 서명을 수행하고, 키 검증·회전·감사로그로 마감함.

> 요약: ECC는 점 연산 자체보다 곡선 선택·난수 생성·공개키 검증 절차가 실제 보안 수준을 결정함.

---

## Ⅳ. 특징

- 키 효율: P-256(256b)이 RSA 3072b와 동일한 128비트 강도를 제공해 인증서·핸드셰이크 바이트를 축소함.
- 용도 분리: 동일 키쌍이 아니라 목적별로 ECDH(키 교환)·ECDSA/EdDSA(서명)로 알고리즘이 명확히 구분됨.
- 난수 민감성: ECDSA는 nonce k가 1회만 재사용돼도 개인키가 산출식으로 노출되는 강한 의존성을 가짐.
- 곡선 신뢰: 자체 곡선 금지, NIST·CFRG 표준 곡선과 point-on-curve·subgroup 검증이 안전성의 전제임.
- 양자 취약: RSA와 동일하게 Shor 알고리즘에 취약하여 PQC 하이브리드 전환 대상임.

## Ⅴ. 심화 비교 및 적용 판단

RSA와 ECC를 키·용도·위험 축으로 비교함(다대상×다축이므로 표 사용).

| 구분 | RSA 2048/3072 | ECC P-256 · X25519 | 선택 기준 |
|:---|:---|:---|:---|
| 키·인증서 크기 | 3072b, 큰 서명·인증서 | 256b, 작은 서명·인증서 | 모바일·TLS는 ECC, 레거시 호환은 RSA 병행 |
| 용도 | 암호화·서명·키 운반 겸용 | ECDH/ECDSA/EdDSA로 분리 | 키 교환·서명 알고리즘 명확 구분 |
| 대표 취약점 | padding·소인수분해 | nonce 재사용·invalid curve | 검증된 표준 라이브러리 사용 여부 |

> 요약: ECC 선택은 키 크기보다 표준 곡선·검증 구현·레거시 호환성을 함께 고려해야 함.

리스크 관리는 불릿으로 정리함.
- 리스크: 개인키 노출 — 원인: ECDSA nonce 재사용 — 대응: RFC 6979 결정적 k, EdDSA 채택, 중복 r 값 0건 점검.
- 리스크: invalid curve 공격 — 원인: 수신 공개키 검증 누락 — 대응: point-on-curve·subgroup check, 실패 시 차단 로그.
- 리스크: 사이드채널 — 원인: 스칼라 곱의 시간·전력 패턴 — 대응: constant-time 구현, HSM 사용, 취약 CVE 0건.

지표 관리도 불릿으로 정리함.
- 지표: 허용 곡선 준수 — 목표: P-256/P-384/X25519만 허용, 취약 곡선 0건 — 측정: TLS 스캔·의존성 점검.
- 지표: 키 보관 — 목표: 개인키 HSM/KMS 보관, 회전주기 1년 이하 — 측정: KMS 감사로그·인증서 만료 리포트.
- 지표: 이상 탐지 — 목표: nonce 재사용·인증서 오발급 탐지 — 측정: CT 로그·SIEM 룰·취약점 스캔.

## Ⅵ. 실무 적용 및 결론

**적용 방안 3개 (필수 — 단계별 또는 항목별):**
1. 표준 곡선 정책: TLS는 X25519/P-256 우선, 서명은 ECDSA P-256 또는 Ed25519 채택, 자체 곡선 금지.
2. 구현 통제: OpenSSL/BoringSSL 등 검증 라이브러리 사용, constant-time 옵션과 public key validation 활성화.
3. 전환 관리: 대외 서비스는 ECC 인증서 적용, 장기 보관 데이터는 ECC+ML-KEM, ECDSA+ML-DSA 하이브리드 로드맵 수립.

**결론 (2줄):**
- 기술사 판단: 키 크기·트래픽 제약이 큰 TLS·IoT면 ECC 우선 적용하되, 난수·곡선 검증 체계를 선행해야 함.
- 향후 방향: 양자 위협 대비 ECC 단독에서 PQC 하이브리드로 단계 전환이 필요함.
