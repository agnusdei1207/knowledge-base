# 📖 【암기용】 개념 완전 이해

> 목적: ECC를 처음 봐도 완전하게 이해하게 만든다. 시험 답안 양식이 아니라, 이해를 위한 설명이다.

## 한눈에
- **개요**: 타원곡선 위 점 연산의 난해성을 이용한 공개키 암호 기술
- **왜 필요한가**: RSA는 128비트 보안 강도에 3072비트 키가 필요하지만, ECC는 P-256 같은 256비트 곡선으로 같은 보안 강도를 제공한다. 모바일·IoT·TLS처럼 키 크기와 핸드셰이크 비용이 중요한 환경에 적합하다.
- **핵심 직관**: 점 G를 k번 더해 Q를 만드는 것은 쉽지만, G와 Q만 보고 k를 찾는 것은 ECDLP 난제에 해당한다.

## 깊이 이해
- **배경·문제의식**: 공개키 암호는 인증·키 교환·전자서명에 필요하지만 RSA 키 길이 증가가 인증서 크기, 서명 검증 비용, 핸드셰이크 트래픽을 키운다. ECC는 작은 키로 공개키 기능을 제공한다.
- **작동 원리**: 개인키 d는 난수 정수, 공개키 Q=dG는 곡선 위 점이다. ECDH는 상대 공개키에 자기 개인키를 곱해 공유점을 만들고, ECDSA/EdDSA는 해시값과 개인키로 서명을 만든다.
- **비유**: 지도 위에서 출발점 G를 정해 같은 규칙으로 256번 움직여 도착점 Q를 만드는 것은 쉽지만, 도착점만 보고 몇 번 움직였는지 역산하기 어렵다.
- **구체 예시**: NIST 기준 RSA 3072비트와 ECC P-256은 약 128비트 보안 강도로 취급되며, X.509 인증서와 TLS ECDHE에서 흔히 사용된다.
- **흔한 오해·주의점**: ECC는 암호화만 뜻하지 않는다. ECDH는 키 교환, ECDSA/EdDSA는 서명, ECIES는 암호화 응용으로 구분해야 한다.

## 연결 개념
- ECDHE — TLS 세션키 합의
- ECDSA·EdDSA — 전자서명 알고리즘
- PQC — 양자 컴퓨터의 Shor 알고리즘에 대한 대체 기술

# 📝 【답안용】 시험 답안 템플릿

> 목적: 시험장에서 25분에 그대로 쓰는 답안 양식. 작성방식(추상표현 금지·수치·도식·문제유형 전환)을 엄격히 지킨다.

## 핵심 인사이트 (3줄 요약)

> 1. **본질**: ECC는 타원곡선 이산로그 문제(ECDLP)를 기반으로 키 교환·전자서명·공개키 암호 기능을 제공하는 공개키 암호 체계임.
> 2. **가치**: P-256은 RSA 3072비트 수준의 128비트 보안 강도를 256비트 키로 제공하여 인증서·핸드셰이크 트래픽을 줄임.
> 3. **판단 포인트**: 곡선 선택, 난수 품질, 공개키 검증, 사이드채널 대응, PQC 전환 계획을 함께 판단해야 함.

## 출제 의도 및 답안 포인트

| 출제 의도 | 반드시 짚을 핵심 | 감점 회피 포인트 |
|:---|:---|:---|
| 공개키 암호 원리 이해 확인 | ECDLP, 개인키 d, 공개키 Q=dG, 점 덧셈·스칼라 곱 | ECC를 타원 "방정식" 설명에만 머무름 금지 |
| 암호 적용 기준 판단 확인 | ECDH/ECDHE, ECDSA/EdDSA, P-256/X25519 | 키 교환·서명·암호화 용도 혼동 금지 |
| 보안형 통제 역량 확인 | 난수 재사용, invalid curve, side-channel, key validation | "키가 작다"만 쓰고 운영 위험 누락 금지 |

> 요약: ECC 답안은 작은 키의 장점보다 곡선·난수·검증·용도 구분을 채점 축으로 삼아야 함.

## Ⅰ. 개요 및 필요성

ECC는 타원곡선 기반 공개키 암호이다.  
공개키 암호는 인증·서명·키 교환에 필요하나 RSA 키 길이 증가는 인증서 크기와 연산 비용을 키운다.  
ECC는 256비트 곡선으로 128비트 보안 강도를 제공하여 TLS, 모바일, IoT, 블록체인 서명에 사용된다.

---

## Ⅱ. 구조 및 구성요소

```text
곡선 파라미터 -> 기준점 G -> 개인키 d -> 공개키 Q=dG
  / ECDH: 공유 비밀 생성 -> KDF -> 세션키
  / ECDSA/EdDSA: 해시 -> 서명 -> 검증
```

| 구성요소 | 역할 | 특이사항 |
|:---|:---|:---|
| 곡선 파라미터 | 유한체, 곡선식, 기준점, 차수 제공 | NIST P-256, Curve25519 등 표준 곡선 |
| 개인키 d | 비밀 스칼라 값 | CSPRNG 생성, HSM/KMS 보관 |
| 공개키 Q | dG 점 연산 결과 | 수신 시 곡선 포함 여부 검증 |
| ECDH/ECDHE | 세션키 합의 | TLS 1.3 PFS 제공 |
| ECDSA/EdDSA | 전자서명 생성·검증 | nonce 재사용 시 개인키 노출 |

> 요약: ECC 구성은 곡선 파라미터, 키쌍, 용도별 알고리즘으로 나뉘며 공개키 검증이 필수 통제임.

---

## Ⅲ. 동작원리 및 흐름도

```text
곡선 선택 -> 개인키 생성 -> 공개키 계산 -> 용도 선택
  / ECDHE: 상대 공개키 검증 -> 공유점 계산 -> KDF
  / ECDSA: 해시·nonce 생성 -> 서명 -> 공개키 검증
```

| 단계 | 처리 내용 | 검증 기준 |
|:---:|:---|:---|
| 1 | P-256, P-384, X25519 등 곡선 선택 | 조직 암호정책, TLS 지원 그룹 |
| 2 | 개인키와 nonce 생성 | CSPRNG, nonce 재사용 0건 |
| 3 | 공개키 산출 및 인증서 등록 | Q=dG, X.509 public key algorithm 확인 |
| 4 | 키 교환 또는 서명 수행 | ECDHE, ECDSA, Ed25519 용도 구분 |
| 5 | 검증·폐기·교체 | key validation, rotation, 감사로그 |

> 요약: ECC는 점 연산 자체보다 곡선 선택, 난수 생성, 공개키 검증 절차가 실제 보안 수준을 결정함.

## Ⅳ. 특징

| 구분 | RSA 기반 | ECC 기반 | 판단 포인트 |
|:---|:---|:---|:---|
| 키 길이 | RSA 3072비트 약 128비트 보안 강도 | P-256 약 128비트 보안 강도 | 인증서 크기·핸드셰이크 바이트 감소 |
| 용도 | 암호화·서명·키 운반 | ECDH/ECDSA/EdDSA로 용도 분리 | 키 교환과 서명 알고리즘 구분 |
| 운영 위험 | 큰 키 관리 부담 | nonce·curve validation 민감 | ECDSA nonce 재사용 1회도 개인키 노출 |
| 양자 내성 | Shor 알고리즘에 취약 | Shor 알고리즘에 취약 | PQC 하이브리드 전환 필요 |

> 요약: ECC는 작은 키의 이점이 있으나 난수·검증 오류와 양자 위협에 대한 별도 통제가 필요함.

## Ⅴ. 심화 비교 및 적용 판단

| 비교 축 | 기존/대안 | 본 키워드 | 선택 기준 |
|:---|:---|:---|:---|
| 구조 | RSA 2048/3072 | ECC P-256/P-384, X25519 | 모바일·TLS는 ECC, 레거시 호환은 RSA 병행 |
| 비용/성능 | 큰 공개키·서명 크기 | 작은 키·인증서 크기 | 핸드셰이크 트래픽, CPU 사용률 측정 |
| 운영/위험 | RSA padding 취약점 | nonce·invalid curve 취약점 | 라이브러리 표준 구현 사용 여부 |

> 요약: ECC 선택은 키 크기보다 표준 곡선, 검증 구현, 레거시 호환성을 함께 고려해야 함.

| 리스크 | 원인 | 대응 방안 | 확인 지표 |
|:---|:---|:---|:---|
| 개인키 노출 | ECDSA nonce 재사용 | RFC 6979 deterministic k, CSPRNG 점검 | 중복 r 값 0건 |
| invalid curve 공격 | 수신 공개키 검증 누락 | point-on-curve, subgroup check | key validation 실패 차단 로그 |
| 사이드채널 | 스칼라 곱 시간·전력 패턴 | constant-time 구현, HSM 사용 | 취약 라이브러리 CVE 0건 |

> 요약: ECC 위험은 수학 난제보다 구현·난수·검증 실패에서 발생하므로 표준 라이브러리와 로그 점검으로 통제함.

| 점검 항목 | 목표 기준 | 측정 방법 |
|:---|:---|:---|
| 암호정책 | P-256/P-384/X25519 허용, 취약 곡선 금지 | TLS 스캔, 코드 의존성 점검 |
| 키 관리 | 개인키 HSM/KMS 보관, 회전주기 1년 이하 | KMS 감사로그, 인증서 만료 리포트 |
| 탐지·복구 | nonce 재사용, 인증서 오발급 탐지 | CT 로그, SIEM 룰, 취약점 스캔 |

> 요약: ECC 운영 성숙도는 허용 곡선, 키 보관, nonce·인증서 이상 이벤트로 측정함.

## Ⅵ. 실무 적용 및 결론

**적용 방안 3개 (필수 — 단계별 또는 항목별):**
1. 표준 곡선 정책: TLS는 X25519/P-256 우선, 전자서명은 ECDSA P-256 또는 Ed25519 사용, 자체 곡선 금지.
2. 구현 통제: OpenSSL/BoringSSL 등 검증된 라이브러리 사용, constant-time 옵션과 public key validation 활성화.
3. 전환 관리: 외부 공개 서비스는 ECC 인증서 적용, 장기 보관 데이터와 인증 체계는 PQC 하이브리드 로드맵 수립.

**결론 (2줄):**
- 기술사 판단: 키 크기·트래픽 제약이 있는 TLS·IoT는 ECC를 우선 적용하되 난수·곡선 검증 체계를 선행해야 함.
- 향후 방향: 양자 위협 대응을 위해 ECC 단독에서 ECC+ML-KEM, ECDSA+ML-DSA 하이브리드로 단계 전환 필요.
