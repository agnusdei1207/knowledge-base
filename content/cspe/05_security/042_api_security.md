## Ⅰ. 개요
- **정의**: API 호출 과정에서 인증·인가·데이터 보호를 보장하는 보안 체계
- **배경/필요성**: 마이크로서비스 확산으로 API 노출면이 증가하여 전용 보안 대책이 필요함
- **비유**: 건물 출입구가 늘어날수록 각 문에 별도 잠금장치가 필요한 것과 동일

| 출제 의도 | 반드시 짚을 핵심 | 감점 회피 포인트 |
|:---|:---|:---|
| API 공격 유형과 방어 체계 설계 | 인증·인가·Rate Limiting·입력 검증 | OWASP API Top 10과 연계 서술 필요 |

> 요약: API 노출면 확대에 따른 체계적 보안 설계가 핵심 과제임

## Ⅱ. 구성요소
```text
Client -> API Gateway -> Auth Server
              |
              v
         Rate Limiter -> Backend Service -> DB
              |
              v
         Logging / Monitoring
```

| 구성요소 | 설명 | 비유 |
|:---|:---|:---|
| API Gateway | 인증·라우팅·트래픽 제어의 단일 진입점 | 건물 안내 데스크 |
| Rate Limiter | 단위 시간당 요청 수를 제한하여 남용 방지 | 놀이공원 입장 인원 제한 |
| OAuth 2.0 / JWT | 토큰 기반 인증·인가 프로토콜 | 출입 카드와 권한 등급 |

> 요약: Gateway·Rate Limiter·토큰 인증을 조합하여 다층 방어를 구성함

## Ⅲ. 절차
```text
요청 수신 -> 인증/인가 -> 입력 검증 -> 응답 필터링
```
- 1단계: 클라이언트 요청을 API Gateway에서 수신
- 2단계: OAuth/JWT 토큰 검증으로 인증·인가 수행
- 3단계: 요청 파라미터에 대한 스키마 기반 입력 검증 실행
- 4단계: 응답 데이터에서 민감 필드를 마스킹·필터링하여 반환

> 요약: 수신-인증-검증-필터링의 4단계로 API 요청 생명주기를 보호함

## Ⅳ. 문제점
- BOLA 취약점: 객체 수준 인가 미흡 — 타 사용자 데이터에 무단 접근 가능
- 과다 데이터 노출: 응답에 불필요한 필드 포함 — 민감 정보 유출 위험 존재
- 섀도우 API: 문서화되지 않은 API 엔드포인트 — 보안 정책 적용 범위에서 누락됨

> 요약: 인가 미흡·과다 노출·비관리 API가 주요 공격 표면을 형성함

## Ⅴ. 개선방안
1. 단기: 객체 수준 인가 검증 로직을 모든 엔드포인트에 적용
2. 중기: API 스키마 기반 응답 필터링으로 최소 데이터만 반환하도록 강제
3. 장기: API 자동 탐지·인벤토리 도구를 도입하여 섀도우 API를 제거

> 요약: 인가 강화·응답 최소화·API 인벤토리 관리로 공격면을 축소함

## Ⅵ. 전망
- 발전 방향: API 보안 전용 플랫폼과 AI 기반 이상 탐지가 확산될 것임
- 기술사적 판단: Zero Trust 아키텍처에서 API 보안은 핵심 구성 요소임
- 기술사 제언: API 설계 단계부터 보안 요구사항을 명세에 포함할 것을 제언함
