## 1. 한눈에 이해하기 (Core Intuition)
- **정의**: 한 번의 로그인(아이디/패스워드 입력)만으로 그룹웨어, 인사 시스템, 이메일, 외부 클라우드 등 **수십 개의 서로 다른 업무 시스템을 재로그인 없이 프리패스로 넘나들 수 있게 해주는 통합 인증 솔루션**입니다.
- **필요성**: 회사원이 하루에 접속해야 하는 시스템이 10개가 넘습니다. 각 시스템마다 요구하는 비밀번호 규칙(특수문자 포함 등)이 다르면, 직원들은 기억하지 못하고 모니터에 포스트잇으로 비밀번호를 적어 붙여놓습니다(치명적 보안 홀). "아이디를 외우기 힘든 것 자체가 최대의 보안 위협"이 되므로, 딱 한 번만 빡세게 로그인하면 나머지는 시스템이 알아서 인증을 대신해 주는 환경이 필요해졌습니다.
- **핵심 직관**: **"놀이공원(에버랜드)의 자유이용권 팔찌"**. 
  - 과거: 롤러코스터(메일 서버), 바이킹(결재 서버) 탈 때마다 지갑 꺼내서 매번 입장권(비밀번호)을 사야 함. (귀찮고 분실 위험).
  - **SSO**: 아침에 정문 매표소(SSO 통합 인증 서버)에서 빡세게 신분증(지문+비밀번호)을 한 번 검사받으면 손목에 **'자유이용권(토큰)'** 을 채워줍니다. 이제 공원 안의 어떤 놀이기구를 타든 팔찌만 보여주면 0.1초 만에 하이패스로 통과!

## 2. 왜 중요한가? (Background & Value)
- **등장 배경**: 시스템이 쪼개지고 외부 클라우드(SaaS) 도입이 폭발적으로 늘면서, IT 부서는 하루 종일 "비밀번호 까먹었어요, 초기화해주세요(Password Reset)"라는 직원들의 헬프데스크 전화만 받다가 업무가 마비되었습니다. IT 운영 비용 절감과 사용자 편의성을 동시에 잡기 위해 기업 인프라의 필수 0순위 과제로 대두되었습니다.
- **가치**: "편의성이 곧 보안 강화다." 직원들은 10개의 외우기 쉬운 허접한 비밀번호 대신, 단 1개의 '매우 복잡하고 긴 패스워드 + 지문(MFA)' 조합만을 쓰게 됩니다. 보안 수준은 극적으로 올라가고, 퇴사 시 이 1개의 마스터 스위치만 끄면 모든 시스템에서 즉각 쫓겨나므로 계정 관리(IAM)가 완벽해집니다.

## 3. 어떻게 작동하는가? (Mechanism)
핵심은 사용자에게 비밀번호를 묻지 않고, 시스템들끼리 '신임장(토큰)'을 주고받는 것입니다.

1. **최초 로그인 요청 (정문 매표소 도착)**
   - 직원이 사내 그룹웨어(앱 A)에 접속하려 합니다. 앱 A는 "나 너 누군지 몰라, 인증 서버(SSO/IdP) 가서 증명서 받아와!"라며 튕겨냅니다.
2. **SSO 서버에서 강력한 인증 (자유이용권 발급)**
   - 직원이 SSO 전용 화면에서 ID/PW를 치고 휴대폰 지문(MFA)까지 찍습니다. 
   - SSO 서버는 100% 본인이 맞음을 확인하고, 브라우저(쿠키)에 위조 불가능한 **'인증 토큰(티켓)'** 을 발급해 줍니다.
3. **다른 시스템 무혈입성 (놀이기구 하이패스)**
   - 직원이 이메일(앱 B)에 접속합니다. 이메일 시스템은 비밀번호 창을 띄우지 않고, 방금 SSO 서버가 발급해 준 브라우저의 '티켓'을 확인합니다.
   - "SSO 형님이 보증한 사람이군. 통과!" $\rightarrow$ 사용자는 로그인 창을 보지도 못하고 바로 메일함에 들어갑니다.

## 4. 실전 활용 및 예시 (Real-world Application)
- **구체적 사례**: 
  - 구글(Google) 아이디 하나로 접속해 두면, YouTube, Gmail, 구글 드라이브를 넘나들 때 계속 로그인 상태가 유지되는 것이 완벽한 SSO의 일상적 예시입니다. 기업 환경에서는 Okta(옥타), Microsoft Entra ID가 SSO 서버 역할을 하며 수천 개의 외부 클라우드 서비스(줌, 슬랙 등)와 토큰을 주고받습니다.
- **주의점 및 흔한 오해**: 
  - **SPOF (단일 장애점)의 저주**: 자유이용권 매표소(SSO 서버)가 고장 나거나 해커 디도스에 맞아 죽어버리면? 직원들은 이메일, 결재, 메신저 등 회사의 단 1개 시스템에도 로그인하지 못하고 전사 업무가 100% 올스톱되는 대참사가 발생합니다. 그래서 SSO 서버는 인프라 설계 시 무조건 2중, 3중으로 살려두는 고가용성(HA/이중화) 아키텍처가 필수입니다.

## 5. 핵심 비교 및 연결 개념 (Relation)
- **IAM vs SSO vs EAM**:
  - **IAM**: 계정 관리의 가장 큰 개념. (아이디 만들고 지우는 중앙 관리청).
  - **SSO**: IAM의 세부 기능 중 '로그인 편의성(토큰 발행)'을 담당하는 문지기.
  - **EAM (Enterprise Access Management)**: 단순 로그인을 넘어, 시스템 안에서 "이 메뉴는 과장 이상만 볼 수 있다"는 세부 권한 통제까지 합친 종합 접근 제어. (현대적으론 IAM 범주에 다 흡수됨).

# ✍️ 단답형 / 서술형 시험장 출격 준비

### Ⅰ. 핵심 인사이트
- **본질**: 분산된 다수의 애플리케이션 및 시스템 환경에서, 사용자가 단일 인증 서버(Identity Provider, IdP)에 최초 1회의 자격 증명(Credential)만 수행하면, 인증 세션(Token/Ticket)을 맺은 이후에는 다른 타겟 시스템 서비스(Service Provider, SP)들에 추가적인 인증 과정 없이 투명하게 접근할 수 있도록 인가하는 통합 인증 프레임워크.
- **가치**: 다수 계정 운영에 따른 패스워드 피로(Password Fatigue) 및 취약한 패스워드 재사용(Reuse) 리스크를 원천 제거함. IT Helpdesk의 패스워드 리셋(Reset) 비용 절감과 함께, 전사적/중앙집중화된 인증 통제(퇴사자 즉시 권한 차단)를 가능케 하는 IAM 거버넌스의 핵심 기반임.
- **판단 포인트**: SSO는 인증의 편의성(Convenience)을 극대화하지만, 그 이면에 존재하는 **'단일 실패점(SPOF, Single Point of Failure)'** 리스크(SSO 장비 장애 시 전사 업무 중단)와 **'마스터키 탈취 위험(Single Point of Compromise)'** 을 반드시 고도화된 이중화(HA) 아키텍처와 MFA(다중 인증) 결합으로 상쇄시켜야 합니다.

### Ⅱ. SSO를 구현하는 3대 주요 아키텍처/프로토콜
환경(웹, 모바일, 인트라넷, B2B 클라우드)에 따라 다른 기술을 매핑하여 사용.
1. **Kerberos (커버로스) 기반 (사내망/인트라넷 온프레미스 표준)**
   - 메커니즘: 대칭키 암호화 기반. 사용자가 KDC(Key Distribution Center / MS Active Directory)에 인증을 요청하면, KDC가 타겟 서버 접근용 **TGT(티켓 발급 티켓)** 와 서비스 티켓(Service Ticket)을 발급해 주는 중앙 집중형 구조.
   - 특징: 윈도우(Windows) 도메인 환경의 기본 SSO 메커니즘. 강력한 보안성을 지니나 클라우드나 외부망으로 확장하기 매우 어려움.
2. **SAML (Security Assertion Markup Language) 기반 (B2B / 클라우드 표준)**
   - 메커니즘: XML 포맷을 이용해 "이 사용자는 우리 회사 직원이 맞고, 방금 인증을 통과했다"는 보증 수표(Assertion)를 IdP(인증 서버)가 SP(서비스 제공자, 예: Salesforce)에게 암호화 서명하여 던져주는 방식.
   - 특징: 현재 기업용 SaaS(웹 애플리케이션) 연동 시장의 압도적 표준.
3. **OAuth 2.0 / OIDC 기반 (B2C / 모던 앱 & 모바일 표준)**
   - 메커니즘: JSON 포맷과 RESTful API를 활용. ID/PW를 넘기지 않고 특정 데이터 접근 '권한(Access Token)'만 위임(OAuth)하거나, '사용자 신원 증명서(ID Token)'를 발급(OIDC). (예: "카카오 계정으로 로그인하기").

### Ⅲ. SSO 아키텍처 토폴로지 (대리 로그인 방식의 분류)
오래된 레거시 시스템(사내 자체 개발 앱)은 표준 프로토콜(SAML 등)을 이해하지 못하므로 다음 우회 기법이 쓰임.
- **Agent 기반 방식 (플러그인 삽입)**
  - 사내망의 각 웹 서버(App A, B) 모듈에 SSO 요원(Agent)을 심어둠. 사용자가 접속하면 Agent가 낚아채어 SSO 중앙 서버에 질의(Query)한 후 결과를 받아 브라우저 세션을 허락함.
- **Reverse Proxy 기반 (게이트웨이 방식)**
  - App 서버에 아무것도 설치하지 않음. 사용자와 수십 개의 서버 사이에 톨게이트(프록시 서버)를 하나 세워둠. 트래픽이 무조건 이 게이트웨이를 거쳐 가며, 프록시가 인증 쿠키를 까보고 없으면 로그인 창으로 돌려보냄(네트워크 병목 리스크 존재).
- **Form-fill 기반 (비밀번호 대리 입력)**
  - 표준 프로토콜 개조가 불가능한 아주 오래된 화면(ActiveX 등)일 때, SSO 브라우저 플러그인(또는 앱)이 사용자의 ID/PW를 암호화된 금고에 기억해 두었다가, 로그인 창이 뜨면 사람 대신 자동으로 타이핑(Inject)해 주는 무식하지만 확실한 편법. (Enterprise Password Vault 활용).

### Ⅳ. 제로 트러스트 하에서의 SSO 발전 (Adaptive SSO)
- **적응형 인증 (Adaptive / Context-Aware SSO)**
  - 기존 SSO의 치명적 단점: 해커가 내 PC(SSO 쿠키가 구워진 브라우저)를 장악하면 무혈입성 가능.
  - $\rightarrow$ 진화: SSO 서버가 '단 한 번' 인증해 주고 끝나는 게 아니라, 접속 위치나 행위(Context)가 바뀌면 **동적으로 재인증(Step-up Authentication)을 요구**함.
  - 예: "아침 출근해서 메일 볼 때는 하이패스 통과(SSO 유지), 하지만 오후에 갑자기 인사팀 급여 DB에 접속을 시도하면 기존 SSO 쿠키를 무시하고 폰으로 OTP 인증(MFA)을 띄움."

### Ⅴ. 결론 및 실무적 판단 포인트
- 인프라 보안 아키텍트는 분산된 앱들을 통합하기 위해 "어떤 프로토콜(SAML vs OIDC)을 지원하는 IdP 플랫폼을 도입할 것인가?"를 최우선으로 설계해야 합니다. 내부 폐쇄망(인트라넷) 전용의 오래된 벤더 종속적 SSO 솔루션을 버리고, **클라우드 확장이 자유로운 IDaaS (Identity as a Service, 예: Okta/Entra ID)** 기반의 개방형 프로토콜 융합 아키텍처로 넘어가야 기술 부채(Tech Debt)를 없앨 수 있습니다.

### 💡 문제 유형별 목차 전환 포인트
- **[복수 시스템 환경에서의 효율적 통합 인증 아키텍처 구축 방안]**: Ⅰ번과 Ⅱ번(프로토콜 구분)을 중심으로 구성. 패스워드 피로도 문제를 제기하고, 온프레미스(Kerberos)와 클라우드(SAML/OIDC) 환경에 각각 맞는 기술을 매핑하여 솔루션 제시.
- **[SSO의 치명적 보안 취약점(SPOF/계정 탈취) 극복 및 접근 통제 고도화]**: SSO의 어두운 면(단일 실패점)을 짚고, 이를 이중화(HA)와 Ⅳ번 적응형 인증(Adaptive SSO, MFA 결합)으로 방어하는 제로 트러스트 성숙도 제고 측면 서술.
