## 1. 한눈에 이해하기 (Core Intuition)
- **정의**: 애플리케이션의 취약점을 찾아내고 방어하기 위해 소프트웨어 생명주기(SDLC)의 각 단계(코드 작성 $\rightarrow$ 테스트 $\rightarrow$ 운영)에 맞춰 적용하는 4가지 핵심 보안 테스팅 및 방어 기술입니다.
- **필요성**: 코드를 안 보고 겉에서 해킹만 해보면 어디를 고쳐야 할지 모르고(DAST의 한계), 코드만 들여다보면 실제 환경에서 해킹이 먹히는지 알 수 없습니다(SAST의 한계). 따라서 소스코드, 동작 상태, 서버 내부, 런타임 방어까지 입체적으로 엮어야 완벽한 웹/앱 보안이 완성됩니다.
- **핵심 직관**: **"자동차 안전을 검증하는 4단계 테스트"**
  - **SAST**: 자동차 설계도를 보고 나사 빠진 곳 찾기 (정적 분석)
  - **DAST**: 완성된 자동차를 벽에 직접 박아보고 찌그러지는지 확인하기 (동적 분석/모의 해킹)
  - **IAST**: 더미 인형 몸에 수십 개의 센서를 달아놓고 충돌 테스트하여 실시간 데이터 뽑기 (내부 계측 분석)
  - **RASP**: 실제 도로를 주행할 때 낭떠러지를 감지하면 스스로 브레이크를 밟는 기능 (런타임 자가 방어)

## 2. 깊이 이해하기 (In-Depth Comprehension)
- **SAST (Static Application Security Testing / White-box)**
  - **특징**: 소스코드(.java)나 바이너리를 실행하지 않고 정적으로 분석하여 SQL Injection 등의 패턴을 찾습니다.
  - **장점/단점**: 개발 초기(IDE, 깃허브 PR)에 즉각 피드백이 가능하고 취약한 코드의 '몇 번째 줄'인지 정확히 짚어줍니다. 하지만 오탐(False Positive)이 많고, 런타임 환경의 취약점은 찾지 못합니다.
- **DAST (Dynamic Application Security Testing / Black-box)**
  - **특징**: 코드를 보지 않고, 실행 중인 웹 서비스에 해커처럼 무수한 악성 HTTP 요청(Payload)을 던져 응답을 분석합니다.
  - **장점/단점**: 실제 해킹 가능성(실행 환경)을 검증하므로 오탐이 적습니다. 하지만 "어느 코드를 고쳐라"라고 알려주지 못하며, 로그인(인증) 뒷단의 페이지를 스캔하기 어렵습니다.
- **IAST (Interactive Application Security Testing / Glass-box)**
  - **특징**: SAST와 DAST의 장점을 합친 3세대 기술. WAS(웹 서버) 내부에 에이전트를 심어놓고, 외부에서 DAST처럼 공격을 때릴 때 앱 내부의 데이터 흐름(Data Flow)을 실시간으로 추적합니다.
  - **장점/단점**: 취약점의 실제 발현 여부와 코드 라인을 동시에 짚어내는 압도적 정확도를 자랑합니다. 단, 에이전트 설치로 인한 서버 부하(Overhead)와 언어 종속성(Java, C# 등)이 존재합니다.
- **RASP (Runtime Application Self-Protection)**
  - **특징**: 테스팅 도구가 아닌 **운영 환경(Production)의 방어 도구**입니다. 앱 내부에 탑재되어, 실행 시점에 앱으로 들어오는 악성 페이로드(예: Log4j 공격)를 앱 스스로 감지하고 세션을 차단합니다.
  - **차별점 (vs WAF)**: WAF는 네트워크 앞단에서 패킷 패턴만 보고 차단하므로 오탐이 잦지만, RASP는 페이로드가 앱 내부의 DB 쿼리나 함수에 도달할 때의 문맥(Context)을 보고 차단하므로 오탐이 거의 0에 가깝습니다.

## 3. 연결 개념 (Related Concepts)
- **DevSecOps**: 이 4가지 도구(SAST $\rightarrow$ DAST/IAST $\rightarrow$ RASP)를 CI/CD 파이프라인의 각 파트에 맞물려 톱니바퀴처럼 자동화하는 프로세스.
- **WAF (Web Application Firewall)**: RASP와 방어 목적은 같으나 동작 위치가 다름. (WAF는 네트워크 경계, RASP는 앱 메모리 내부).
- **OWASP Top 10**: 이 도구들이 기본적으로 탐지하고 방어해야 할 10대 웹 취약점 표준.

# ✍️ 답안용 골격 (Exam Preparation)

### Ⅰ. 핵심 인사이트
- **본질**: 애플리케이션 보안 테스팅(AST) 모델의 진화 과정으로, 개발 초기 소스코드 패턴을 분석하는 **SAST**, 실행 환경에서 블랙박스 침투를 수행하는 **DAST**, 런타임 계측(Instrumentation)을 통해 두 기술의 장점을 융합한 **IAST**, 그리고 운영 단계에서 앱 스스로 위협을 탐지/차단하는 **RASP**의 유기적 프레임워크.
- **가치**: 단일 테스팅 도구의 한계(SAST의 높은 오탐률, DAST의 낮은 코드 가시성)를 상호 보완하여, 결함 조치 시간(MTTR)을 단축하고 제로데이(0-Day) 공격에 대한 런타임 회복 탄력성(Resilience)을 보장함.
- **판단 포인트**: DevSecOps 아키텍처 수립 시, 이 4가지 기술을 단순히 나열하는 것이 아니라 CI/CD 파이프라인의 각 단계(Commit $\rightarrow$ Build $\rightarrow$ Test $\rightarrow$ Run)에 마찰(Friction) 없이 적재적소에 배치하고, RASP의 에이전트 부하(Performance Overhead)를 어떻게 모니터링할 것인지가 핵심 설계 요건임.

### Ⅱ. AST 4대 기술의 메커니즘과 장단점 비교
```text
┌───────────────┬───────────────────┬───────────────────┬────────────────┐
│ 특성          │ SAST (White-Box)  │ DAST (Black-Box)  │ IAST (Glass-Box)│
├───────────────┼───────────────────┼───────────────────┼────────────────┤
│ 분석 대상     │ 소스코드, 바이너리│ 실행 중인 앱(HTTP) │ 실행 앱 + 내부 코드│
│ 테스팅 환경   │ 코딩, 빌드(CI)    │ QA, Staging       │ QA, Staging    │
│ 취약점 위치   │ 라인 단위 정확히 짚음│ 취약 URL 파라미터만 │ 라인 단위 정확히 짚음│
│ 오탐률(FP)    │ 매우 높음 (실행 검증X)│ 낮음              │ 매우 낮음      │
│ 분석 속도     │ 빠름 (IDE 플러그인)│ 느림 (크롤링, 페이로드)│ 빠름 (실시간 모니터링)│
└───────────────┴───────────────────┴───────────────────┴────────────────┘
```

### Ⅲ. IAST와 RASP의 내부 계측(Instrumentation) 원리
기존 기술의 맹점을 깨는 차세대 런타임 분석 기술.
- **동작 원리**: Java의 JVM이나 .NET의 CLR 등 애플리케이션 구동 엔진 내부에 에이전트(Agent)를 삽입하여, 소스코드를 수정하지 않고도 메모리 상의 데이터 흐름(Taint Analysis)을 가로채어 추적함.
- **IAST (테스트 환경)**: 외부에서 DAST 툴이나 자동화 UI 테스트 스크립트가 요청을 보낼 때, IAST 에이전트가 "이 악성 페이로드가 앱 내부의 DB 쿼리 함수(Sink)까지 안전하게 필터링되어 들어갔는지"를 실시간으로 스니핑하여 취약 여부 확정.
- **RASP (운영 환경)**: IAST와 동일한 계측 원리를 사용하되, 테스트가 아닌 실제 고객 서비스 환경에 적용. 만약 악성 페이로드가 SQL 쿼리를 변조하려는 찰나를 감지하면, 앱이 죽기 전에 해당 스레드(Session)의 실행을 강제 종료(Block)시킴.

### Ⅳ. DevSecOps 파이프라인 내 툴 체인 매핑 전략
1. **Plan & Code (IDE / PR)**: **SAST** 구동. 개발자가 타이핑하는 즉시 시큐어 코딩 위반 여부 경고 및 Commit 차단 (Quality Gate).
2. **Build & Test (CI)**: **IAST / DAST** 구동. 테스트 자동화 스크립트(Selenium 등) 구동 시 IAST가 백그라운드에서 취약점 정밀 스캔.
3. **Deploy & Operate (CD)**: 운영망 배포 시 **RASP** 활성화. 레거시 WAF와 연동하여 WAF를 우회한 제로데이(Log4Shell 등) 공격을 메모리 단에서 최종 방어.

### Ⅴ. 결론 및 실무적 판단 포인트
- 앱 보안 테스팅을 구축하는 아키텍트는 "모든 도구를 다 도입하면 완벽하다"는 착각을 버려야 합니다. IAST와 RASP는 압도적인 정확도를 제공하지만, 대상 애플리케이션의 언어(Node.js, Go 등)를 에이전트가 지원해야만 쓸 수 있다는 '언어 종속성'의 치명적 한계가 있습니다.
- 따라서 CISO는 자사의 기술 스택을 분석하여, Java/C# 기반의 핵심 모놀리식 앱에는 IAST/RASP를 딥 다이브(Deep-dive) 적용하고, 다양한 언어가 섞인 마이크로서비스(MSA)와 API 기반 서버리스 환경에서는 SAST와 DAST를 주력으로 배치하는 혼합형(Hybrid) AST 거버넌스를 설계해야 합니다. 또한 운영망 RASP 도입 시에는 반드시 2주간의 '모니터링 모드'를 거쳐 서비스 지연(Latency) p95 지표가 5% 이내인지 검증한 후 차단(Blocking) 모드로 전환하는 안정성 우선 정책이 필수적입니다.

### 💡 문제 유형별 목차 전환 포인트
- **[웹/애플리케이션 보안 진단 방법론 및 취약점 최소화 전략]**: Ⅰ과 Ⅱ(SAST/DAST/IAST 비교)를 전면에 세워, 단일 테스팅 도구의 오탐(FP)/미탐(FN) 한계를 어떻게 IAST의 글래스박스(Glass-Box) 접근법으로 상호 보완하는지 논리 증명.
- **[제로데이 위협 방어를 위한 DevSecOps 및 런타임 보안(RASP) 설계]**: Ⅲ(내부 계측 원리)을 메인으로 다루며 Ⅳ(CI/CD 매핑)를 엮어, "기존 WAF(네트워크 경계 방어)가 우회되는 상황에서, RASP가 어떻게 앱의 메모리 문맥(Context)을 읽어내어 오탐 없이 스스로 방어(Self-Protection)하는가"에 대한 심화 엔지니어링 해법 전개.
