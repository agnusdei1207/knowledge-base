# 📖 【암기용】 개념 완전 이해

> 목적: SAST·DAST·IAST·RASP를 처음 보는 사람도 완벽히 이해하게 만든다. 시험 답안 양식이 아니라, 이해를 위한 친절한 설명이다.

## 한눈에
- **개요**: 애플리케이션 취약점을 코드, 실행 중 외부 요청, 내부 계측, 런타임 차단 관점에서 탐지·대응하는 4가지 방식
- **왜 필요한가**: 한 가지 검사만으로는 코드 결함, 실행 경로, 인증 후 취약점, 실제 공격 차단을 모두 다루기 어렵다. 개발·테스트·운영 단계별 조합이 필요하다.
- **핵심 직관**: SAST는 설계도 검사, DAST는 완성품 외부 침투 테스트, IAST는 내부 센서를 단 테스트, RASP는 운행 중 자동 브레이크이다.

## 깊이 이해
- **배경·문제의식**: 웹·API 서비스는 릴리스 속도가 빨라지고 공격면도 넓어졌다. SQL Injection, XSS, SSRF, 인증 우회 같은 취약점은 코드와 실행 환경을 함께 봐야 정확도가 올라간다.
- **작동 원리**: SAST는 소스코드와 데이터 흐름을 정적으로 분석한다. DAST는 실행 중인 애플리케이션에 HTTP 요청을 보내 응답을 관찰한다. IAST는 애플리케이션 내부 Agent가 코드 실행 경로와 외부 요청을 함께 분석한다. RASP는 런타임에서 공격 행위를 탐지해 요청 차단·세션 종료를 수행한다.
- **비유**: 자동차를 만들 때 SAST는 도면 오류 확인, DAST는 주행 테스트, IAST는 엔진 센서 데이터 분석, RASP는 충돌 직전 자동 제동 장치이다.
- **구체 예시**: PR 단계에서 SAST가 SQL Injection sink를 탐지하고, 테스트 환경 DAST가 인증 후 XSS를 찾으며, 운영 RASP가 악성 파라미터 요청을 403으로 차단한다.
- **흔한 오해·주의점**: DAST가 있으면 SAST가 필요 없다는 생각은 틀렸다. SAST는 개발 초기에 많은 코드 경로를 보지만 실행 가능성을 놓칠 수 있고, DAST는 실제 실행 기반이지만 코드 위치를 정확히 주지 못한다.

## 연결 개념
- DevSecOps - CI/CD 단계별 보안 검사를 자동화하는 운영 방식이다.
- OWASP Top 10 - 네 가지 검사 방식의 주요 탐지 기준이다.
- RASP/WAF - RASP는 애플리케이션 내부 문맥, WAF는 네트워크 경계 요청 패턴을 본다.

# 📝 【답안용】 시험 답안 템플릿

> 목적: 시험장에서 25분에 그대로 쓰는 답안 양식. 작성방식(추상표현 금지·수치·도식·문제유형 전환)을 엄격히 지킨다.
> 핵심: 네 방식의 이름 암기가 아니라 적용 단계, 탐지 범위, 오탐·누락, CI/CD 배치와 운영 차단까지 비교해야 한다.

## 핵심 인사이트 (3줄 요약)

> 1. **본질**: SAST·DAST·IAST·RASP는 애플리케이션 보안을 정적 코드, 동적 외부 테스트, 내부 계측, 런타임 방어 관점에서 나눈 검사·대응 방식이다.
> 2. **가치**: 개발 초기 결함 발견, 테스트 환경 검증, 실행 경로 기반 정확도 보정, 운영 공격 차단을 단계별로 결합한다.
> 3. **판단 포인트**: 적용 단계, 코드 접근 필요 여부, 인증 처리, 오탐률, 런타임 부하, CI/CD Gate 기준을 함께 판단한다.

## 출제 의도 및 답안 포인트

| 출제 의도 | 반드시 짚을 핵심 | 감점 회피 포인트 |
|:---|:---|:---|
| 애플리케이션 보안 검사 방식 비교 확인 | SAST·DAST·IAST·RASP 적용 단계와 탐지 범위 | 네 방식 이름만 나열 |
| DevSecOps 배치 판단 확인 | PR, CI, Test, Staging, Production 위치 | 운영 RASP와 개발 SAST 역할 혼동 |
| 오탐·누락·부하 리스크 확인 | False Positive, False Negative, Agent overhead | 한 도구로 모든 취약점 탐지 가능하다고 단정 |

> 요약: 이 문제는 검사 방식별 강점보다 단계별 조합과 리스크 통제를 평가한다.

## Ⅰ. 개요 및 필요성

- 개요: 앱 보안 검사·런타임 방어 조합
- 배경: 코드 결함, 실행 취약점, 인증 후 취약점, 운영 공격은 관측 위치가 달라 SAST 또는 DAST 단독으로 전체 경로를 검증하기 어려움
- 필요성: SAST·DAST·IAST·RASP를 PR, Test, Staging, Production에 배치하고 Critical 0건, 주요 API 80% 스캔, RASP p95 지연 증가 5% 이하 기준으로 운영해야 함

---

## Ⅱ. 구조 및 구성요소

```text
Source Code -> SAST -> Pull Request Gate
Running App -> DAST -> Test/Staging Gate
Running App + Agent -> IAST -> Verified Finding
Production Runtime -> RASP -> Detect/Block -> SIEM
```

| 구성요소 | 역할 | 특이사항 |
|:---|:---|:---|
| SAST | 소스코드·바이트코드 정적 분석 | 코드 접근 필요, 데이터 흐름 분석 |
| DAST | 실행 앱에 외부 요청 기반 취약점 테스트 | 코드 접근 불필요, 인증 시나리오 필요 |
| IAST | 내부 Agent로 실행 경로와 요청을 함께 분석 | 테스트 커버리지 의존, 위치 추적 가능 |
| RASP | 운영 런타임에서 공격 요청 탐지·차단 | Agent 부하, 차단 정책 튜닝 |
| CI/CD Gate | 결과를 merge·배포 기준으로 사용 | Critical 차단, High SLA 관리 |

> 요약: 네 방식은 코드-테스트-운영 단계별 관측 위치가 달라 상호 보완 조합으로 배치한다.

---

## Ⅲ. 동작원리 및 흐름도

```text
개발 코드 -> SAST 분석 -> PR 수정
테스트 배포 -> DAST/IAST 실행 -> 취약점 검증
운영 배포 -> RASP 탐지/차단 -> SIEM 경보 -> 백로그 환류
```

| 단계 | 처리 내용 | 검증 기준 |
|:---:|:---|:---|
| 1 | SAST가 코드 경로와 sink/source 분석 | OWASP Top 10, CWE 매핑 |
| 2 | DAST가 HTTP 요청과 응답을 기반으로 탐지 | 인증 세션, API 스펙, 크롤링 범위 |
| 3 | IAST가 실행 경로와 데이터 흐름을 Agent로 확인 | 테스트 커버리지 70% 이상 |
| 4 | RASP가 운영 요청을 런타임 문맥으로 판정 | 차단 정책, p95 부하 5% 이하 |
| 5 | 결과를 티켓과 Gate 정책에 반영 | Critical 0건, High 7일 SLA |

> 요약: SAST는 빠른 개발 피드백, DAST/IAST는 실행 검증, RASP는 운영 차단과 환류를 담당한다.

## Ⅳ. 특징

| 구분 | SAST | DAST | IAST/RASP |
|:---|:---|:---|:---|
| 적용 단계 | 코딩·PR | 테스트·스테이징 | 테스트·운영 |
| 관측 방식 | 코드 정적 분석 | 외부 요청·응답 | 내부 Agent·런타임 문맥 |
| 장점 | 코드 위치 제시, 초기 발견 | 실제 실행 취약점 확인 | 오탐 보정, 운영 차단 |
| 한계 | 오탐, 실행 가능성 판단 한계 | 코드 위치 부정확, 인증 필요 | Agent 부하, 언어 지원 제약 |
| 수치 기준 | PR 피드백 10분 이하 | 스캔 윈도 1시간 이하 | p95 부하 5% 이하 |

> 요약: SAST는 초기 발견, DAST는 외부 검증, IAST는 정확도 보정, RASP는 운영 차단 역할로 구분한다.

| RASP 부하 | Agent 계측과 차단 로직 | 고위험 룰 우선, 모니터링 모드 검증 | p95 지연 증가 5% 이하 |

> 요약: 검사 리스크는 오탐·누락·부하이며 룰 튜닝, API 명세, 모니터링 모드로 통제한다.

| 점검 항목 | 목표 기준 | 측정 방법 |
|:---|:---|:---|
| 탐지 품질 | Critical 0건, High 7일 SLA | 취약점 관리 대시보드 |
| 커버리지 | SAST 대상 저장소 100%, DAST 주요 API 80% | CI 로그, OpenAPI 매핑 |
| 운영 영향 | RASP p95 지연 증가 5% 이하, 차단 오탐 1% 이하 | APM, SIEM, 차단 로그 |

> 요약: 도입 성과는 취약점 잔존 수, 검사 커버리지, RASP 운영 영향으로 평가한다.

## Ⅵ. 실무 적용 및 결론

**적용 방안 3개 (필수 - 단계별 또는 항목별):**
1. PR 단계에 SAST를 배치해 CWE Top 25와 OWASP Top 10 Critical finding은 merge 차단하고, 피드백 시간을 10분 이하로 관리함
2. 테스트 환경에 DAST와 IAST를 배치하고 OpenAPI 명세·인증 스크립트로 주요 API 80% 이상을 스캔 범위에 포함함
3. 운영에는 RASP를 모니터링 모드 2주 후 차단 모드로 전환하고, p95 지연 증가 5% 이하와 차단 오탐 1% 이하를 기준으로 운영함

**결론 (2줄):**
- 기술사 판단: 개발 초기 결함은 SAST, 실행 취약점은 DAST/IAST, 운영 공격 차단은 RASP로 역할을 분리해 CI/CD에 배치해야 함
- 향후 방향: SAST·DAST·IAST·RASP 결과는 SBOM, SCA, SIEM과 연계되어 애플리케이션 보안 상태 관리(ASPM)로 통합됨
