# 📖 【암기용】 개념 완전 이해

## 한눈에
- **개요**: 하이브리드 암호는 **비대칭 암호로 세션키를 합의**하고 **대칭 암호로 본문을 암호화**하는 결합 방식이다. (대칭 원리는 001, 비대칭 원리는 002 참조)
- **왜 필요한가**: 비대칭(002)은 키 분배엔 강하나 느리고, 대칭(001)은 빠르나 키 분배가 어렵다 → 서로의 단점을 상대의 장점으로 덮어 **역할을 분리**한다.
- **핵심 직관**: 금고 열쇠(세션키)는 상대의 공개 우편함(비대칭)으로 안전히 전달하고, 무거운 짐(본문)은 그 열쇠로 여는 튼튼한 금고(대칭)에 넣어 보낸다.

## 핵심 용어 정리 (내부에 등장하는 것들)

001·002에서 설명한 대칭키·공개키·개인키는 반복하지 않고, 하이브리드에서 **새로 등장하는 용어**만 정리한다.

| 용어/표기 | 의미 | 비유·예 |
|:---|:---|:---|
| 세션키(Session Key) | 한 연결에서만 쓰고 버리는 임시 대칭키 | 이번 통화에만 쓰는 일회용 암호 |
| 키 분배 문제 | 대칭키를 안전히 나눠 갖기 어려운 문제(하이브리드가 해결) | 열쇠를 택배로 보내면 도중에 복사당함 |
| 키 캡슐화(KEM) | 공개키로 세션키를 감싸 전달하는 방식 | 열쇠를 상대 공개 우편함에 넣어 보냄(RSA-KEM·ML-KEM) |
| 키 합의(ECDHE) | 양쪽이 각자 값을 교환해 같은 세션키를 계산 | 서로 퍼즐 조각을 주고받아 같은 그림을 완성 |
| KDF/HKDF | 공유 비밀에서 실제 세션키를 안전하게 도출 | 원재료를 정제해 규격 열쇠로 깎아냄(HKDF-SHA-256) |
| 전방향 안전성(PFS) | 장기키가 유출돼도 과거 세션은 안전(ECDHE) | 매 통화마다 새 열쇠를 만들고 폐기 |
| AEAD | 대칭 구간에서 기밀성+무결성을 함께 제공 | 내용을 숨기며 봉인 훼손까지 확인(AES-GCM) |
| 재키잉(Rekeying) | 세션 중 주기적으로 세션키를 교체 | 장시간 통화 중 암호를 갈아 끼움 |
| Envelope Encryption | 데이터키를 상위 키로 감싸 저장(KMS 패턴) | 편지를 잠근 뒤 그 열쇠를 다시 봉투에 봉인 |
| PQC 하이브리드 | 기존 ECDHE + 양자내성 ML-KEM 병행 | 자물쇠 두 개를 동시에 채워 하나가 뚫려도 방어 |

## 깊이 이해
- **배경·문제의식**: 인터넷 통신은 처음 만나는 상대와도 즉시 암호화해야 하는데, 사전 공유키(001의 한계)를 만들 수 없다 → 공개키 절차(002)로 세션키를 만들고, 이후 데이터는 대칭 암호로 처리해 이 모순을 푼다.
- **작동 원리(어떻게+왜)**:
  - 서버 인증서를 검증한 뒤(신원 확인), ECDHE로 **공유 비밀**을 계산하거나 KEM으로 세션키를 캡슐화한다.
  - HKDF로 공유 비밀에서 실제 세션키(traffic secret)를 도출한다 — 원시 공유값을 그대로 키로 쓰면 편향이 남기 때문이다.
  - 이후 본문은 AEAD(AES-GCM·ChaCha20-Poly1305)로 암호화해 기밀성·무결성·인증을 함께 제공한다.
  - 왜 이렇게 나누나 — 공개키로 GB 본문을 직접 암호화하면 수백 배 느리고 입력 크기 제한도 걸리기 때문이다.
- **비유**: 낯선 사람에게 금고 열쇠를 직접 건네지 않고, 상대 공개 우편함에 넣거나(KEM) 양쪽이 퍼즐을 풀어 같은 열쇠를 만든 뒤(ECDHE) 그 열쇠로 무거운 짐을 금고에 넣어 보낸다.
- **구체 예시**: TLS 1.3은 ECDHE로 키를 합의하고 HKDF-SHA-256으로 traffic secret을 도출한 뒤 AES-128-GCM 또는 ChaCha20-Poly1305로 레코드를 암호화한다. PGP·S/MIME·클라우드 KMS의 Envelope Encryption도 같은 패턴이다.
- **흔한 오해·주의점**: 하이브리드 암호는 "특정 알고리즘 하나"가 아니다. **인증서 검증 → 키 교환 → KDF → 대칭 암호 → 재키잉**까지 아우르는 **프로토콜 설계 패턴**이다.

## 연결 개념
- 대칭 암호(001)·비대칭 암호(002) — 하이브리드가 결합하는 두 축
- TLS 1.3 — 하이브리드 암호의 대표 구현(1-RTT 핸드셰이크)
- PQC 하이브리드 — ECDHE와 ML-KEM을 결합해 양자내성 전환 리스크 축소

# 📝 【답안용】 시험 답안 템플릿

## 핵심 인사이트 (3줄 요약)

> 1. **본질**: 하이브리드 암호는 비대칭의 키 분배 능력과 대칭의 대량 처리 능력을 결합한 프로토콜 구조임.
> 2. **가치**: TLS·PGP·모바일 메신저·클라우드 KMS가 인증·키 합의·본문 암호화를 역할별로 분리 수행함.
> 3. **판단 포인트**: 인증서 검증·키 합의·KDF·AEAD 선택·재키잉 주기를 하나의 설계로 함께 다뤄야 함.

## 출제 의도 및 답안 포인트

| 출제 의도 | 반드시 짚을 핵심 | 감점 회피 포인트 |
|:---|:---|:---|
| 도청·중간자·세션키 노출 위협을 키 교환·본문 암호화 분리 설계로 통제하는 역량 확인 | TLS 1.3, ECDHE·KEM, HKDF-SHA-256, AES-GCM·ChaCha20-Poly1305, 세션키 수명 | 단일 알고리즘으로 설명, RSA 본문 암호화 오해, 인증서·AEAD 태그 검증 누락 |

> 요약: 하이브리드 답안은 키 교환과 본문 암호화를 분리하고 각 구간의 통제 지표를 제시해야 함.

---

## Ⅰ. 개요 및 필요성

- 개요: 비대칭 키 교환과 대칭 본문 암호화를 결합한 프로토콜 패턴
- 배경: 공개망은 사전 공유키가 불가하고(001 한계), 공개키만으로 대용량 본문을 처리하면 경로 비용이 급증함(002 한계)
- 필요성: 키 교환은 RSA/ECDHE/KEM, 본문은 AES-GCM·ChaCha20-Poly1305로 분리해 TLS·VPN 세션 암호화를 구성함

---

## Ⅱ. 구조 및 구성요소

```text
클라이언트 -> 서버 인증서 검증 -> 키 교환(ECDHE/KEM) -> 공유 비밀
-> HKDF로 세션키 도출 -> AEAD 본문 암호화 -> 암호문+태그 -> 재키잉/세션 만료
```

| 구성요소 | 역할 | 특이사항 |
|:---|:---|:---|
| 인증서·공개키 | 상대 신원 확인 | X.509·SAN·CA chain 검증(002) |
| 키 교환 | 공유 비밀 생성 | ECDHE, RSA-KEM, ML-KEM |
| KDF | 세션키 도출 | HKDF-SHA-256, context 바인딩 |
| 대칭 암호(AEAD) | 본문 암호화 | AES-GCM, ChaCha20-Poly1305(001) |

> 요약: 하이브리드 암호는 인증서·키 교환·KDF·AEAD가 순차 결합된 프로토콜 구조임.

---

## Ⅲ. 동작원리 및 흐름도

```text
인증서 수신 -> 체인·폐지 검증 -> 임시 키 교환 -> 공유 비밀 계산
-> HKDF 세션키 도출 -> AEAD로 본문 암호화 -> 태그 검증 -> 세션 종료·키 폐기
```

1. 서버 인증서와 지원 암호군을 확인함(TLS 1.3, SHA-256 이상)
2. ECDHE 또는 KEM으로 공유 비밀을 생성함(전방향 안전성 또는 KEM 보안)
3. HKDF로 공유 비밀에서 traffic key를 도출함(salt·context 분리)
4. 송신 측이 AES-GCM 등 AEAD로 본문을 암호화해 전송하고, 수신 측이 태그를 검증해 실패 시 세션을 폐기함

---

## Ⅳ. 특징

- 키 분배와 본문 암호화의 역할 분리 — 느린 공개키는 세션키에만, 빠른 대칭은 본문에만 사용
- TLS 1.3 기준 1-RTT 핸드셰이크 — 한 번의 왕복으로 키 합의·인증을 완료
- 전방향 안전성 확보 가능 — ECDHE 임시키로 장기키 유출 시에도 과거 세션 보호
- 단일 알고리즘이 아닌 프로토콜 패턴 — 인증서·KDF·AEAD 설정 오류가 실제 취약점의 대부분
- PQC 전환에 유리 — 기존 ECDHE에 ML-KEM을 병행해 호환성과 양자내성을 동시 확보

---

## Ⅴ. 심화 비교 및 적용 판단

- 순수 대칭·순수 비대칭·하이브리드는 키 분배와 처리량 특성이 달라, 공개망에서는 하이브리드가 표준 선택임.

| 구분 | 순수 대칭(001) | 순수 비대칭(002) | 하이브리드 |
|:---|:---|:---|:---|
| 키 분배 | 사전 공유 필요 | 공개키로 용이 | 비대칭이 세션키 전달 |
| 본문 처리량 | 고속(대량 적합) | 느림(대량 부적합) | 대칭으로 고속 처리 |
| 대표 적용 | 폐쇄망 PSK | 서명·인증서 | TLS 1.3·PGP·KMS |

> 요약: 외부 공개망은 하이브리드, 폐쇄망 소수 장비는 PSK와 키 회전 정책을 비교함.

- 리스크 — 중간자 공격: 인증서 검증 누락이 원인 → CA chain·SAN·OCSP 검증으로 대응
- 리스크 — 세션키 노출: 장기키 재사용이 원인 → ECDHE 임시키·재키잉 주기 제한으로 대응
- 리스크 — 암호군 약화: TLS 1.0·3DES 허용이 원인 → TLS 1.3 우선·CBC·RC4 차단으로 대응

---

## Ⅵ. 실무 적용 및 결론

**적용 방안 3개:**
1. 웹 서비스: TLS 1.3에서 ECDHE·AES-128-GCM·ChaCha20-Poly1305만 허용하고 TLS 1.0/1.1·RC4·3DES를 차단함
2. 데이터 암호화: KMS 공개키 또는 KEM으로 데이터키를 감싸고 본문은 AES-256-GCM으로 Envelope Encryption을 구성함
3. PQC 전환: ECDHE+ML-KEM 하이브리드 키 교환 PoC를 수행하고 핸드셰이크 크기·p95 지연 증가율을 측정함

**결론:**
- 조건부 판단: 공개망 데이터 보호는 하이브리드를 기본으로 하고, 폐쇄망 PSK는 키 배포 대상이 10개 이하일 때만 검토함
- 향후 방향: PQC 전환기에는 ECDHE와 ML-KEM을 병행해 호환성과 양자내성 리스크를 함께 관리해야 함
