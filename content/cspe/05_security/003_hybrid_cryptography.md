# 📖 【암기용】 개념 완전 이해

> 목적: 하이브리드 암호를 처음 보는 사람도 완전하게 이해하게 만든다. 시험 답안 양식이 아니라, 이해를 위한 설명이다.

## 한눈에
- **개요**: 비대칭 암호로 세션키를 안전하게 합의하고, 대칭 암호로 실제 데이터를 암호화하는 결합 방식
- **왜 필요한가**: 공개키 암호는 키 분배에 유리하지만 대량 데이터 처리에 부적합하고, 대칭 암호는 처리량은 충분하지만 키 전달이 어렵다. 두 방식을 결합해 역할을 분리함.
- **핵심 직관**: 금고 열쇠를 특수 보안 봉투로 전달한 뒤, 실제 물건은 그 열쇠로 여는 금고에 넣어 보내는 방식임

## 깊이 이해
- **배경·문제의식**: 인터넷 통신은 처음 만나는 상대와도 암호화해야 한다. 사전 공유키를 만들 수 없으므로 RSA/ECDHE 같은 공개키 절차로 세션키를 만들고, 이후 데이터는 AES-GCM·ChaCha20-Poly1305로 암호화함.
- **작동 원리**: 서버 인증서 검증 후 ECDHE로 공유 비밀을 계산하고 HKDF로 세션키를 도출한다. 이후 애플리케이션 데이터는 AEAD 모드로 암호화되어 기밀성·무결성·인증성을 함께 제공함.
- **비유**: 낯선 사람에게 금고 열쇠를 직접 주지 않고, 상대의 공개 우편함에 열쇠를 넣거나 양쪽이 퍼즐을 풀어 같은 열쇠를 만든 뒤 금고를 사용함.
- **구체 예시**: TLS 1.3은 ECDHE로 키를 합의하고 HKDF-SHA-256으로 traffic secret을 도출한 뒤 AES-128-GCM 또는 ChaCha20-Poly1305로 레코드를 암호화함.
- **흔한 오해·주의점**: 하이브리드 암호는 "암호 알고리즘 하나"가 아니다. 키 교환, 인증서 검증, 키 도출, 대칭 암호, 재키잉까지 포함하는 프로토콜 설계 패턴임.

## 연결 개념
- TLS 1.3 — 하이브리드 암호의 대표 구현
- AEAD — 대칭 암호 구간에서 인증 태그 제공
- PQC 하이브리드 — ECDHE와 ML-KEM을 결합해 전환 리스크 축소

# 📝 【답안용】 시험 답안 템플릿

> 목적: 시험장에서 25분에 그대로 쓰는 답안 양식. 수치·표준명·기술명 중심으로 작성한다.

## 핵심 인사이트 (3줄 요약)

> 1. **본질**: 하이브리드 암호는 비대칭 암호의 키 분배 능력과 대칭 암호의 대량 데이터 처리 능력을 결합한 구조이다.
> 2. **가치**: TLS, PGP, 모바일 메신저, 클라우드 KMS에서 인증·키 합의·본문 암호화를 역할별로 분리함.
> 3. **판단 포인트**: 세션키 생성, 인증서 검증, KDF, AEAD 선택, 키 재협상 주기를 함께 설계해야 함.

## 출제 의도 및 답안 포인트

| 출제 의도 | 반드시 짚을 핵심 | 감점 회피 포인트 |
|:---|:---|:---|
| 도청·중간자·세션키 노출 위협을 인증서 검증, 키 합의, 본문 암호화, 탐지·복구 절차로 분리하는 보안 설계 역량 확인 | TLS 1.3, ECDHE·KEM, HKDF-SHA-256, AES-GCM·ChaCha20-Poly1305, 세션키 수명, 암호군 스캔 | 단일 암호 알고리즘으로 설명, RSA 본문 암호화 오해, 인증서 검증·AEAD 태그 검증 누락 |

> 요약: 하이브리드 암호 답안은 키 교환과 본문 암호화를 분리하고 각 구간의 통제 지표를 제시해야 한다.

---

## Ⅰ. 개요 및 필요성

- 개요: 공개키와 대칭키 결합 구조
- 배경: 공개망은 비밀키 사전 공유가 어렵고, 공개키 암호만으로 대용량 본문을 처리하면 핸드셰이크 이후 데이터 경로 비용이 커짐.
- 필요성: 키 교환은 RSA/ECDHE/PQC로 수행하고 본문은 AES-GCM·ChaCha20-Poly1305로 처리해 TLS·VPN 세션 암호화를 구성함.

---

## Ⅱ. 구조 및 구성요소

```text
Client -> Server Certificate Verify -> Key Exchange
       -> KDF -> Session Key -> AEAD Encryption -> Ciphertext/Tag
       -> Rekey/Session Expire -> Audit
```

| 구성요소 | 역할 | 특이사항 |
|:---|:---|:---|
| 인증서·공개키 | 상대 신원 확인 | X.509, SAN, CA chain 검증 |
| 키 교환 | 공유 비밀 생성 | ECDHE, RSA-KEM, ML-KEM |
| KDF | 세션키 도출 | HKDF-SHA-256, context binding |
| 대칭 암호 | 본문 암호화 | AES-GCM, ChaCha20-Poly1305 |

> 요약: 하이브리드 암호는 인증서, 키 교환, KDF, AEAD 대칭 암호가 순차 결합된 프로토콜 구조이다.

---

## Ⅲ. 동작원리 및 흐름도

```text
인증서 수신 -> 체인/폐지 검증 -> 임시 키 교환
-> 공유 비밀 계산 -> HKDF 세션키 도출 -> AEAD 본문 암호화
-> 태그 검증 -> 세션 종료/키 폐기
```

| 단계 | 처리 내용 | 검증 기준 |
|:---:|:---|:---|
| 1 | 서버 인증서와 지원 암호군 확인 | TLS 1.3, SHA-256 이상 |
| 2 | ECDHE·KEM으로 공유 비밀 생성 | 전방향 안전성 또는 KEM 보안 |
| 3 | HKDF로 traffic key 도출 | salt·context 분리 |
| 4 | AES-GCM 등 AEAD로 데이터 처리 | tag 검증 실패 시 세션 폐기 |

> 요약: 하이브리드 암호는 신원 검증 후 세션키를 만들고, AEAD로 본문을 처리하며, 실패 시 키와 세션을 폐기한다.

---

## Ⅳ. 특징

| 구분 | 내용 | 판단 포인트 |
|:---|:---|:---|
| 장점 | 키 분배와 본문 암호화 역할 분리 | TLS 1.3 기준 1-RTT 핸드셰이크 |
| 한계 | 인증서·KDF·AEAD 설정 오류 가능 | 암호군 정책과 자동 스캔 필요 |
| 비교 대상 | 순수 대칭·순수 비대칭 | 사전 공유망은 PSK, 공개망은 하이브리드 |

> 요약: 하이브리드 암호는 공개망 대량 암호화의 표준 패턴이며, 프로토콜 구성요소별 오설정 점검이 핵심이다.

## Ⅴ. 심화 비교 및 적용 판단

| 비교 축 | 기존/대안 | 본 키워드 | 선택 기준 |
|:---|:---|:---|:---|
| 구조 | PSK 단독 | 공개키 키교환 + 대칭 본문 | 외부 사용자·인터넷 서비스 |
| 비용/성능 | RSA 본문 암호화 | AES-GCM 본문 처리 | 본문 크기 1KB 초과 시 대칭 처리 |
| 운영/위험 | 고정 장기키 | 임시 세션키·재키잉 | 전방향 안전성 필요 시 ECDHE |

> 요약: 외부 공개망에서는 하이브리드 구조를 선택하고, 폐쇄망 소수 장비는 PSK와 키 회전 정책을 비교한다.

| 리스크 | 원인 | 대응 방안 | 확인 지표 |
|:---|:---|:---|:---|
| 중간자 공격 | 인증서 검증 누락 | CA chain·SAN·OCSP 검증 | 인증서 오류 허용 0건 |
| 세션키 노출 | 장기키 재사용 | ECDHE, 키 수명 제한 | 재키잉 주기 24시간 이하 |
| 암호군 약화 | TLS 1.0·3DES 허용 | TLS 1.2 이상, CBC·RC4 차단 | 약한 cipher 0건 |

> 요약: 하이브리드 암호 위험은 인증서 검증, 임시 키 사용, 암호군 정책으로 통제한다.

| 점검 항목 | 목표 기준 | 측정 방법 |
|:---|:---|:---|
| 프로토콜 | TLS 1.2 이상, TLS 1.3 우선 | SSL/TLS 스캐너 |
| 키 교환 | ECDHE 또는 KEM, RSA key exchange 제외 | cipher suite 점검 |
| 본문 암호 | AES-GCM 또는 ChaCha20-Poly1305 | 트래픽 캡처·서버 설정 |

> 요약: 도입 품질은 프로토콜 버전, 키 교환 방식, AEAD 암호군 허용 정책으로 판단한다.

## Ⅵ. 실무 적용 및 결론

**적용 방안 3개 (필수 — 단계별 또는 항목별):**
1. 웹 서비스: TLS 1.3, ECDHE, AES-128-GCM/ChaCha20-Poly1305만 허용하고 TLS 1.0·1.1·RC4·3DES 차단
2. 데이터 암호화: KMS 공개키 또는 KEM으로 Data Encryption Key를 감싸고, 본문은 AES-256-GCM으로 Envelope Encryption 구성
3. PQC 전환: ECDHE+ML-KEM 하이브리드 키 교환 PoC 수행, 핸드셰이크 크기와 p95 지연 증가율 측정

**결론 (2줄):**
- 기술사 판단: 공개망 데이터 보호는 하이브리드 암호를 기본으로 하고, 폐쇄망 PSK는 키 배포 대상이 10개 이하일 때만 검토함
- 향후 방향: PQC 전환기에는 기존 ECDHE와 ML-KEM을 병행해 호환성과 양자내성 리스크를 함께 관리해야 함
