## Ⅰ. 개요
| 항목 | 내용 |
|---|---|
| **정의** | 사용자·디바이스의 신원과 컨텍스트를 검증한 후, 특정 애플리케이션에만 최소 접근을 허용하는 제로 트러스트 기반 원격 접근 솔루션임 |
| **배경/필요성** | VPN은 인증 후 전체 네트워크에 접근을 허용하여 측면 이동에 취약하며, 애플리케이션 단위의 세밀한 접근 제어가 필요함 |
| **출제 의도** | ZTNA의 VPN 대비 장점과 SDP·SASE와의 관계를 이해하는지 평가함 |

## Ⅱ. 구성요소
```
+----------+     +----------+     +----------+
| 커넥터   | --> | 브로커   | --> | 클라이언트|
| (App측)  |     | (정책)   |     | (에이전트)|
+----------+     +----------+     +----------+
```

| 구성요소 | 설명 | 비유 |
|---|---|---|
| 커넥터 | 앱 앞단에 설치되어 인증된 트래픽만 전달하고, 앱을 인터넷에서 은닉함 | 비공개 뒷문 안내원 |
| 브로커 | 사용자 신원·디바이스 상태·정책을 평가하여 접근 허가를 결정하는 클라우드 서비스임 | 출입 승인 본부 |
| 클라이언트 에이전트 | 디바이스에 설치되어 신원 인증·보안 상태 보고를 수행함 | 전자 출입증 |

> 요약: 클라이언트(신원 제시) → 브로커(정책 결정) → 커넥터(앱 연결)로 앱 단위 접근을 제어함.

## Ⅲ. 절차
```
+------------+     +------------+
| 접근요청   | --> | 브로커     |
| (에이전트) |     | 신원·장치검증|
+------------+     +------------+
                        |
+------------+     +----+-------+
| 앱접근     | <-- | 터널생성   |
| (최소범위) |     | (커넥터연결)|
+------------+     +------------+
```

1. 접근 요청: 사용자 에이전트가 브로커에 접근을 요청함(앱 주소를 직접 알 수 없음)
2. 신원·장치 검증: 브로커가 IdP 인증·MDM 디바이스 상태·정책 조건을 검증함
3. 마이크로 터널 생성: 검증 통과 시 커넥터와 에이전트 간 암호화된 1:1 터널을 생성함
4. 앱 단위 접근: 승인된 특정 앱에만 접근을 허용하고, 네트워크 나머지는 접근 불가함

> 요약: 요청 → 검증 → 터널 → 앱 접근으로 VPN 대비 측면 이동 불가한 세밀한 접근을 제공함.

## Ⅳ. 문제점
- 에이전트 의존: 에이전트 미설치 BYOD·IoT 디바이스에 적용이 어려움
- 에이전트리스 한계: 브라우저 기반 ZTNA는 기능이 제한되어 RDP·SSH 등 프로토콜 지원이 미흡함
- 벤더 종속: ZTNA 솔루션 간 상호운용성이 부족하여 멀티벤더 구성이 어려움

## Ⅴ. 개선방안
- (단기) 하이브리드 ZTNA: 에이전트·에이전트리스를 병행하여 BYOD를 수용함
- (중기) SASE 통합: ZTNA를 SWG·CASB·FWaaS와 함께 SASE 플랫폼에 통합함
- (장기) 유니버설 ZTNA: 온프레미스·클라우드·SaaS 전체에 단일 ZTNA 정책을 적용함

## Ⅵ. 전망
- Gartner 예측에 따라 2027년까지 신규 원격 접근의 70%가 VPN 대신 ZTNA로 전환되며, SASE/SSE 통합 플랫폼의 핵심 구성요소로 자리잡을 전망임
