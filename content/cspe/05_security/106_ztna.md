# 📖 【암기용】 개념 완전 이해

> 목적: ZTNA를 처음 보는 사람도 VPN과 차이를 이해하게 만든다. 시험 답안 양식이 아니라, 이해를 위한 친절한 설명이다.

## 한눈에
- **개요**: 사용자와 단말을 계속 검증해 애플리케이션 단위로 접근을 허용하는 보안 접근 모델
- **왜 필요한가**: VPN은 접속 후 내부망을 넓게 노출한다. 원격근무·SaaS·클라우드 환경에서는 위치보다 신원, 단말 상태, 세션 위험을 기준으로 접근을 쪼개야 한다.
- **핵심 직관**: 회사 건물 출입증이 아니라 회의실마다 신분증, 예약 여부, 보안 등급을 다시 확인하는 방식임

## 깊이 이해
- **배경·문제의식**: 경계 방어는 사내망을 신뢰 구역으로 본다. 피싱 계정 1개가 VPN에 접속하면 파일서버·업무시스템 탐색이 가능해져 lateral movement가 발생한다.
- **작동 원리**: 사용자가 앱 접속을 요청하면 IdP가 MFA로 신원을 확인하고, 단말 보안 상태, 위치, 시간, 위험 점수를 정책 엔진이 평가한다. 허용 시 브로커가 특정 앱에만 세션을 열고 내부 IP는 노출하지 않는다.
- **비유**: 백화점 전체 입장권이 아니라 매장별 예약 QR을 검사하는 구조임. 장난감 매장 예약자는 보석 매장 창고 문을 볼 수 없다.
- **구체 예시**: 개발자가 GitLab에 접속할 때 FIDO2 MFA, EDR 정상, 디스크 암호화, 국가 코드 KR, 위험 점수 30점 이하이면 8시간 세션을 허용하고, 점수 70점 이상이면 재인증 또는 차단함.
- **흔한 오해·주의점**: ZTNA는 VPN 장비 교체만이 아니다. 애플리케이션 목록화, 사용자 그룹 정리, 단말 posture 수집, 로그 연계가 없으면 정책이 IP ACL 수준에 머문다.

## 연결 개념
- 제로 트러스트 아키텍처 — 지속 검증, 최소 권한, 침해 가정 원칙의 상위 개념
- SASE/SSE — ZTNA, SWG, CASB, FWaaS를 클라우드 보안 엣지로 통합
- 마이크로 세그멘테이션 — 네트워크 내부 이동을 워크로드 단위로 차단
- 연속 인증 — 세션 중 위험 점수 변화에 따라 ZTNA 정책을 재평가

# 📝 【답안용】 시험 답안 템플릿

> 목적: 시험장에서 25분에 그대로 쓰는 답안 양식. 작성방식(추상표현 금지·수치·도식·문제유형 전환)을 엄격히 지킨다.
> 핵심: ZTNA는 "VPN 대체"가 아니라 신원·단말·상황 기반으로 애플리케이션 접근면을 줄이는 제로 트러스트 실행 구조임.

## 핵심 인사이트 (3줄 요약)

> 1. **본질**: ZTNA(Zero Trust Network Access)는 네트워크 접속 권한이 아니라 특정 애플리케이션 세션 권한을 동적으로 부여하는 접근 제어 모델이다.
> 2. **가치**: 내부 IP 비노출, MFA, 단말 posture, 최소 권한 정책으로 계정 탈취 후 lateral movement 범위를 앱 1개 단위로 제한한다.
> 3. **판단 포인트**: 성공 기준은 제품 도입보다 앱 목록화 100%, 정책 적중률, 재인증 빈도, 차단 이벤트 오탐률로 판단해야 한다.

## 출제 의도 및 답안 포인트

| 출제 의도 | 반드시 짚을 핵심 | 감점 회피 포인트 |
|:---|:---|:---|
| VPN 한계와 ZTNA 구조 구분 역량 확인 | 네트워크 접속 vs 애플리케이션 세션, SDP 브로커, IdP, 정책 엔진 | "사내망에 안전하게 접속" 수준의 설명 |
| 제로 트러스트 원칙 적용 능력 확인 | 지속 검증, 최소 권한, 침해 가정, 단말 posture | MFA만 쓰면 ZTNA라고 단정 |
| 운영 지표 기반 도입 판단 확인 | 앱 커버리지, 정책 미스, p95 접속 지연, 차단 오탐률 | 제품명 나열 후 리스크·지표 누락 |
> 요약: 이 문제는 ZTNA를 VPN 교체 기술이 아니라 동적 접근 정책 체계로 설명하는지를 본다.

---

## Ⅰ. 개요 및 필요성

- 개요: 신원 기반 앱 접근 제어
- 배경: 원격근무, SaaS, 멀티클라우드 확산으로 내부망 전체를 신뢰하는 VPN 모델의 공격면이 증가했다.
- 필요성: ZTNA는 NIST SP 800-207 원칙에 맞춰 사용자·단말·위험 점수를 매 접속 평가하고 허용된 애플리케이션에만 세션을 제공해야 한다.

---

## Ⅱ. 구조 및 구성요소

```text
User/Device -> IdP/MFA -> Policy Engine -> ZTNA Broker -> Application Connector -> Private App
                    +-> Device Posture/EDR
                    +-> SIEM/SOAR Logging
```

| 구성요소 | 역할 | 특이사항 |
|:---|:---|:---|
| IdP/MFA | SAML/OIDC 기반 사용자 인증, FIDO2·OTP 확인 | 사용자 그룹·위험 점수 연계 |
| Policy Engine | 사용자, 단말, 위치, 시간, 앱 민감도 평가 | NIST SP 800-207 원칙 반영 |
| ZTNA Broker | 허용 세션 중개, 내부 IP 은닉 | 인바운드 포트 노출 최소화 |
| App Connector | 사설 앱과 브로커 간 아웃바운드 터널 구성 | 데이터센터·VPC별 배치 |
| Observability | 접속 로그, 차단 사유, 세션 지표 수집 | SIEM, UEBA, SOAR 연계 |
> 요약: ZTNA는 IdP, 정책 엔진, 브로커, 커넥터, 로그 체계가 결합되어 앱 단위 접근을 판정한다.

---

## Ⅲ. 동작원리 및 흐름도

```text
접속 요청 -> 신원 인증 -> 단말 posture 확인 -> 정책 평가
-> 앱별 세션 발급 / 차단 -> 로그 전송 -> 위험 변화 시 재평가
```

| 단계 | 처리 내용 | 검증 기준 |
|:---:|:---|:---|
| 1 | 사용자 로그인 및 MFA 수행 | FIDO2 또는 OTP 성공, IdP 토큰 유효 |
| 2 | 단말 posture 수집 | EDR 정상, 디스크 암호화, OS 패치 30일 이내 |
| 3 | 정책 엔진 평가 | 사용자 그룹, 앱 등급, 위치, 위험 점수 50점 이하 |
| 4 | 브로커 세션 생성 | 앱 FQDN 단위 접근, 내부 IP 비노출 |
| 5 | 세션 관측 및 재평가 | 8시간 만료, 위험 점수 70점 이상 재인증 |
> 요약: ZTNA는 최초 인증 후 방치하지 않고 세션 중 위험 변화까지 반영해 허용·차단을 반복한다.

## Ⅳ. 특징

| 구분 | 기존 VPN | ZTNA | 정량·기술 포인트 |
|:---|:---|:---|:---|
| 접근 단위 | 서브넷·IP 대역 | 애플리케이션·사용자 그룹 | 앱 목록화 100%, 권한 매핑 |
| 신뢰 기준 | 접속 위치·터널 성립 | 신원, 단말, 상황, 위험 점수 | SAML/OIDC, FIDO2, EDR |
| 공격면 | VPN 게이트웨이와 내부 라우팅 노출 | 사설 앱 IP 비노출 | 인바운드 포트 0개 목표 |
| 운영 부담 | 네트워크 ACL 중심 | 정책 수명주기 관리 | 정책 미사용 90일 이상 폐기 |
> 요약: ZTNA는 네트워크 터널이 아니라 정책 기반 앱 세션으로 접근 단위를 줄인다.

## Ⅴ. 심화 비교 및 적용 판단

| 비교 축 | 기존/대안 | ZTNA | 선택 기준 |
|:---|:---|:---|:---|
| 구조 | VPN + 방화벽 ACL | IdP + Policy Engine + Broker | 원격 사용자 30% 이상, SaaS·VPC 혼재 |
| 비용/성능 | 장비 증설과 터널 백홀 | 클라우드 PoP, 앱 커넥터 | p95 접속 지연 300ms 이하 |
| 운영/위험 | 내부망 접속 후 탐색 가능 | 앱 단위 접근과 세션 로그 | 특권 앱은 MFA 재인증 주기 4시간 |
> 요약: 원격·클라우드 앱 비중이 높고 내부망 노출을 줄여야 할 때 ZTNA가 VPN보다 적합하다.

| 리스크 | 원인 | 대응 방안 | 확인 지표 |
|:---|:---|:---|:---|
| 정책 과다 허용 | 그룹 권한 정리 없이 이관 | RBAC/ABAC 재분류, 권한 리뷰 월 1회 | 미사용 권한 90일 이상 0건 |
| 접속 지연 | 브로커 PoP 원거리, 인증 연계 지연 | 지역 PoP 선택, IdP 응답 p95 200ms 관리 | 로그인 p95 1초 이하 |
| 우회 경로 | 기존 VPN·직접 IP 접속 잔존 | 방화벽 인바운드 차단, DNS/FQDN 통제 | 비인가 경로 접속 0건 |
> 요약: ZTNA 도입 리스크는 정책 품질, 인증 지연, 우회 경로이며 월간 지표로 통제한다.

| 점검 항목 | 목표 기준 | 측정 방법 |
|:---|:---|:---|
| 앱 커버리지 | 사설 업무 앱 100% 등록 | CMDB, DNS, 방화벽 로그 대조 |
| 접근 품질 | p95 접속 지연 300ms 이하, 실패율 1% 이하 | ZTNA 로그, APM |
| 보안 통제 | MFA 적용률 100%, 차단 오탐률 3% 이하 | IdP 로그, SOC 티켓 |
> 요약: 성공 여부는 앱 커버리지, 지연시간, MFA 적용률, 오탐률을 함께 측정해야 한다.

## Ⅵ. 실무 적용 및 결론

**적용 방안 3개:**
1. 자산 식별: CMDB·DNS·방화벽 로그로 사설 앱 목록을 만들고 중요도 High 앱부터 ZTNA 정책 적용
2. 정책 설계: SAML/OIDC IdP, FIDO2 MFA, EDR posture, 사용자 그룹, 위치 조건을 조합한 ABAC 정책 구성
3. 전환 통제: 기존 VPN은 60일 병행 후 앱별 차단 로그 0건 확인 시 폐기, SIEM에 ZTNA 로그 100% 연계

**결론 (2줄):**
- 기술사 판단: 인터넷 노출 앱과 원격 사용자가 많으면 ZTNA를 우선 적용하고, 레거시 L3 관리망은 VPN+PAM으로 분리한다.
- 향후 방향: SASE, UEBA, Continuous Authentication과 결합해 세션 중 위험 변화까지 반영하는 접근 통제로 발전한다.
