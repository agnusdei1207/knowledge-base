## 미리 알고가기

- ZTNA는 사용자가 네트워크 전체에 들어오게 하는 대신 필요한 애플리케이션에만 접근시키는 방식임
- VPN은 로그인 뒤 넓은 내부망 접근이 가능한 경우가 많지만, ZTNA는 애플리케이션 단위 최소 접근을 지향함
- 제로 트러스트 전체 아키텍처 중 원격 접속과 앱 접근을 구현하는 대표 수단으로 이해하면 됨

## Ⅰ. 개요

- **정의/개념**: ZTNA는 사용자와 기기 상태를 검증한 뒤 특정 애플리케이션에만 최소 범위 연결을 허용해 내부망 노출과 측면 이동을 줄이는 접근 방식임
- **배경/필요성**: 원격 근무가 늘면서 VPN 중심 접근은 인증 후 내부망 범위가 넓어짐. 계정 탈취와 단말 감염 피해 확산을 줄일 앱 단위 통제가 필요함

## Ⅱ. 특징

- 내부 애플리케이션을 인터넷에 직접 노출하지 않고 중개 경로로 연결함
- 사용자 신원, 디바이스 상태, 정책 조건을 함께 평가함
- 승인 앱 외 네트워크 자산은 기본적으로 보이지 않음
- 에이전트 방식과 브라우저 방식은 지원 범위와 운영 부담이 다름

## Ⅲ. 종류 및 비교

| 판단 기준 | VPN | ZTNA |
|:---|:---|:---|
| 접근 범위 | 내부 네트워크 단위 | 애플리케이션 단위 |
| 기본 노출 | 인증 후 내부 자산이 넓게 보일 수 있음 | 승인된 앱만 노출 |
| 장점 | 레거시 프로토콜 지원이 쉬울 수 있음 | 측면 이동 억제와 세밀한 통제에 유리함 |
| 한계 | 탈취 세션 피해 범위가 큼 | 에이전트/브라우저 지원 차이가 있음 |

## Ⅳ. 구성요소 및 구조

| 구성요소 | 설명 |
|:---|:---|
| Client or Browser | 사용자가 접근 요청을 보내는 단말임 |
| Policy Broker | 신원과 단말과 정책을 평가함 |
| Connector | 내부 애플리케이션 앞에서 승인된 연결만 전달함 |
| Identity and Device Signals | SSO, MFA, EDR, MDM 정보를 평가에 제공함 |

```text
접근 요청 -> 신원/단말 검증 -> 정책 결정 -> 커넥터 연결 -> 특정 앱만 접근 허용
```

## Ⅴ. 원리 및 절차 흐름도

```text
앱 요청 -> 브로커 평가 -> MFA/단말 상태 확인 -> 단기 연결 생성 -> 앱 사용 -> 세션 재평가
```

1. **앱 요청**: 사용자가 특정 업무 애플리케이션 접근을 요청함
2. **브로커 평가**: 신원과 기기와 위치와 정책을 확인함
3. **단기 연결 생성**: 통과 시 앱 전용 연결을 열어 줌
4. **앱 사용**: 허용된 서비스만 사용할 수 있음
5. **세션 재평가**: 위험 신호가 생기면 추가 인증이나 차단을 수행함

## Ⅵ. 실무 적용 및 유의점

1. 원격 근무·협력사 접속은 VPN 대체 구간부터 ZTNA를 적용하고 내부망 비인가 스캔 차단 여부와 승인 앱 외 접근 불가 재현으로 확인함
2. BYOD·레거시 프로토콜 환경은 에이전트 기반과 브라우저 기반을 구분하고 지원 앱 범위, 사용자 마찰, 예외 접속 경로 축소로 확인함

## Ⅶ. 결론

- ZTNA는 원격 접속을 네트워크 연결이 아니라 필요한 애플리케이션 단위 연결로 바꾸는 제로 트러스트 구현 수단임
