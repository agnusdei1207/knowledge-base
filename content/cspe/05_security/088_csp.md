## 미리 알고가기

- CSP는 브라우저가 어떤 스크립트와 스타일과 이미지 출처를 허용할지 서버가 헤더로 선언하는 정책임
- 목적은 XSS를 완전히 대신 막는 것이 아니라 브라우저가 위험한 스크립트 실행을 줄이게 만드는 데 있음
- `unsafe-inline`을 남기면 효과가 크게 줄어들므로 nonce나 hash 방식이 중요함

## Ⅰ. 개요

- **정의/개념**: CSP는 서버가 HTTP 응답 헤더로 허용된 리소스 출처와 스크립트 실행 정책을 브라우저에 전달해 XSS와 데이터 주입 위험을 줄이는 브라우저 측 보안 정책임
- **배경/필요성**: 서버의 필터링과 프레임워크 자동 이스케이프만으로 모든 스크립트 실행 경로를 막기 어려워, 실제 실행 환경인 브라우저에서 한 번 더 허용 범위를 제한할 필요가 있음

## Ⅱ. 특징

- 스크립트와 스타일과 프레임과 네트워크 요청 등 리소스 유형별로 허용 출처를 나눌 수 있음
- 위반 보고 기능으로 차단된 실행 시도를 수집할 수 있음
- 잘못된 예외나 `unsafe-inline` 사용은 정책 효과를 약화시킴
- Report-Only 모드로 서비스 영향 없이 정책을 먼저 점검할 수 있음

## Ⅲ. 종류 및 비교

| 판단 기준 | 출처 허용 목록 중심 CSP | nonce/hash 기반 CSP |
|:---|:---|:---|
| 주된 방식 | 특정 도메인 출처를 허용함 | 허용된 스크립트 자체를 식별함 |
| 장점 | 구조가 단순함 | 인라인 스크립트 제어에 유리함 |
| 한계 | 허용 도메인 내 위험 스크립트까지 통과할 수 있음 | 빌드와 템플릿 연계가 필요함 |
| 적합 환경 | 외부 리소스가 적은 서비스 | 현대 프런트엔드와 보안 요구가 높은 서비스 |

## Ⅳ. 구성요소 및 구조

| 구성요소 | 설명 |
|:---|:---|
| 정책 헤더 | `Content-Security-Policy`로 규칙을 전달함 |
| 디렉티브 | `script-src`, `style-src`, `connect-src` 같은 세부 규칙임 |
| 검증과 차단 | 브라우저가 리소스 요청 시 허용 여부를 판단함 |
| 위반 보고 | 차단된 시도를 수집해 정책을 조정함 |

```text
서버가 정책 헤더 전송 -> 브라우저가 규칙 해석 -> 리소스 요청 검증 -> 허용/차단 -> 위반 보고
```

## Ⅴ. 원리 및 절차 흐름도

```text
정책 설계 -> Report-Only 배포 -> 위반 로그 분석 -> 강제 모드 전환 -> 예외 정리
```

1. **정책 설계**: 필요한 리소스 출처와 실행 방식을 정리함
2. **Report-Only 배포**: 실제 차단 전 위반 로그를 수집함
3. **위반 분석**: 필요한 예외와 불필요한 인라인 스크립트를 구분함
4. **강제 모드 전환**: 허용 범위를 확정해 차단을 시작함
5. **지속 점검**: 변경된 프런트엔드 코드에 맞춰 정책을 갱신함

## Ⅵ. 실무 적용 및 유의점

1. 사용자 입력을 많이 렌더링하는 웹 서비스는 CSP를 XSS 보완 통제로 두고 `unsafe-inline`을 없애면서 nonce 기반 정책으로 바꾼 뒤 대표 XSS 페이로드 실행 여부와 위반 보고 감소와 인라인 스크립트 잔존 여부로 확인함
2. 대규모 프런트엔드 환경은 곧바로 강제 모드로 전환하면 장애가 날 수 있으므로 Report-Only로 먼저 점검하고 필요한 출처만 남았는지와 신규 배포 뒤 정책 위반이 급증하지 않는지로 확인함

## Ⅶ. 결론

- CSP는 브라우저가 실행 가능한 스크립트 범위를 줄이는 마지막 보완선이므로 예외를 최소화한 실행 정책으로 운영해야 효과가 남음
