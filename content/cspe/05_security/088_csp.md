## Ⅰ. 개요
| 항목 | 내용 |
|---|---|
| **정의** | 웹 브라우저에 허용된 리소스 출처를 HTTP 응답 헤더로 선언하여 XSS·데이터 인젝션 공격을 차단하는 W3C 보안 정책임 |
| **배경/필요성** | 인라인 스크립트 실행을 통한 XSS 공격이 지속 발생하며, 서버측 필터링 외에 브라우저 레벨 방어가 필요함 |
| **출제 의도** | CSP 디렉티브의 종류와 XSS 방어 메커니즘을 이해하는지 평가함 |

## Ⅱ. 구성요소
```
+----------+     +----------+     +----------+
| 디렉티브  | --> | 소스리스트| --> | 위반보고  |
| (지시자)  |     | (출처목록)|     | (Report) |
+----------+     +----------+     +----------+
```

| 구성요소 | 설명 | 비유 |
|---|---|---|
| 디렉티브 | `script-src`, `style-src` 등 리소스 유형별 로딩 정책을 지정하는 키워드임 | 구역별 출입 규칙 |
| 소스 리스트 | `'self'`, `https://cdn.example.com` 등 허용된 출처 목록임 | 승인된 방문자 명단 |
| 위반 보고 | `report-uri`/`report-to`로 정책 위반 시 서버에 JSON 리포트를 전송함 | CCTV 녹화·알림 |

> 요약: 디렉티브로 리소스 유형별 허용 출처를 선언하고, 위반 시 보고하여 XSS를 차단함.

## Ⅲ. 절차
```
+------------+     +------------+
| 서버응답   | --> | 브라우저   |
| CSP헤더    |     | 정책파싱   |
+------------+     +------------+
                        |
+------------+     +----+-------+
| 위반보고   | <-- | 리소스    |
| 전송       |     | 출처검증   |
+------------+     +------------+
```

1. CSP 헤더 전송: 서버가 `Content-Security-Policy` 응답 헤더에 정책을 포함하여 전송함
2. 정책 파싱: 브라우저가 디렉티브·소스 리스트를 파싱하여 리소스 로딩 규칙을 설정함
3. 출처 검증: 페이지 내 스크립트·스타일·이미지 로딩 시 허용 출처 여부를 실시간 검증함
4. 위반 차단·보고: 미허용 출처의 리소스를 차단하고, 위반 내역을 `report-to` 엔드포인트에 전송함

> 요약: 헤더 전송 → 정책 파싱 → 출처 검증 → 위반 차단·보고로 XSS를 브라우저 레벨에서 방어함.

## Ⅳ. 문제점
- `unsafe-inline` 남용: 레거시 인라인 스크립트 호환을 위해 `unsafe-inline`을 허용하면 CSP 효과가 무력화됨
- 정책 복잡성: 대규모 웹앱에서 수십 개 외부 출처를 정밀 관리하는 데 운영 부담이 큼
- 우회 기법: `script-src`에 CDN을 허용하면 CDN 내 JSONP 엔드포인트를 악용한 우회가 가능함

## Ⅴ. 개선방안
- (단기) nonce/hash 적용: 인라인 스크립트에 일회성 nonce 또는 SHA-256 해시를 부여하여 `unsafe-inline`을 제거함
- (중기) `strict-dynamic`: 신뢰된 스크립트가 로드하는 하위 스크립트를 자동 허용하여 CDN 우회를 차단함
- (장기) Report-Only 모니터링: 신규 정책을 `Content-Security-Policy-Report-Only`로 먼저 배포하여 영향을 사전 평가함

## Ⅵ. 전망
- CSP Level 3 표준의 `strict-dynamic`·`Trusted Types` 조합이 XSS 방어의 사실상 표준이 되며, 브라우저 네이티브 보안 강화가 가속화될 전망임
