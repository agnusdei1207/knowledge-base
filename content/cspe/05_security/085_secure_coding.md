## 미리 알고가기

- 시큐어 코딩은 개발자가 보안 취약점이 생기지 않도록 코드 작성 규칙과 점검 기준을 지키는 활동임
- 핵심은 취약점 발생 후 수정하는 것보다 입력 처리와 권한 검증과 오류 처리를 처음부터 안전하게 만드는 데 있음
- 가이드는 문서만 있어서는 효과가 없고 리뷰와 테스트와 배포 기준에 연결돼야 함

## Ⅰ. 개요

- **정의/개념**: 시큐어 코딩 가이드는 인젝션, 인증 오류, 정보 노출, 메모리 오염을 줄이기 위한 코드 작성 원칙과 검증 절차임
- **배경/필요성**: 운영 단계 취약점 수정은 비용과 영향 범위가 큼. 개발 단계에서 반복 실수를 줄일 공통 규칙이 필요함

## Ⅱ. 특징

- 입력 처리, 권한 검증, 오류 처리처럼 반복되는 공통 위험을 규칙화함
- 개발자 교육뿐 아니라 코드 리뷰, SAST, 테스트 기준과 연결돼야 함
- 언어와 프레임워크에 따라 금지 함수와 권장 API가 달라짐
- 예외 허용 기준이 없으면 실무에서 규칙이 쉽게 무력화됨

## Ⅲ. 종류 및 비교

| 판단 기준 | 사후 수정 중심 개발 | 시큐어 코딩 적용 개발 |
|:---|:---|:---|
| 취약점 발견 시점 | 테스트 후반이나 운영 이후 | 구현과 리뷰와 CI 단계 |
| 개발 비용 | 수정 비용과 영향 범위가 큼 | 초기 규칙 설계 비용은 있으나 재작업이 줄어듦 |
| 품질 관리 | 개발자 숙련도 의존이 큼 | 공통 규칙과 자동 점검으로 표준화 가능 |
| 반복 결함 | 같은 패턴이 재발하기 쉬움 | 금지 패턴과 샘플 코드로 재발을 줄임 |

## Ⅳ. 구성요소 및 구조

| 구성요소 | 설명 |
|:---|:---|
| 코딩 규칙 | 입력 검증, 인증, 오류 처리, 암호화, 자원 관리 기준을 정의함 |
| 금지 패턴 | 위험 함수와 취약한 구현 예시를 명시함 |
| 검토 체계 | 코드 리뷰, 정적 분석, 보안 테스트로 준수 여부를 확인함 |
| 예외와 개선 | 불가피한 예외 사유를 관리하고 재발 항목을 반영함 |

```text
규칙 정의 -> 개발 적용 -> 리뷰/자동 점검 -> 수정 -> 배포 기준 반영
```

## Ⅴ. 원리 및 절차 흐름도

```text
보안 요구 도출 -> 코딩 규칙 작성 -> 구현/리뷰 -> 자동 분석 -> 취약 패턴 수정 -> 표준 갱신
```

1. **보안 요구 도출**: 서비스 특성에 맞는 핵심 위험을 정함
2. **코딩 규칙 작성**: 허용 방식과 금지 패턴과 예외 기준을 정함
3. **구현과 리뷰**: 개발자가 규칙에 맞춰 작성하고 동료 검토를 받음
4. **자동 분석**: 정적 분석과 테스트로 반복 결함을 잡음
5. **표준 갱신**: 실제 사고와 취약점 결과를 가이드에 반영함

## Ⅵ. 실무 적용 및 유의점

1. 공공·금융 조직은 시큐어 코딩을 리뷰 체크리스트와 SAST 규칙에 연결하고 반복 취약점 감소율·미해결 이슈 잔존 여부로 확인함
2. 다언어 조직은 언어별 예시와 금지 API를 제공하고 팀별 준수율·예외 승인 건수·재발 패턴 감소 여부로 확인함

## Ⅶ. 결론

- 시큐어 코딩 가이드는 선언적 문서가 아니라 개발, 리뷰, 배포 기준을 바꿔 반복 취약점을 줄이는 실행 규칙이어야 함
