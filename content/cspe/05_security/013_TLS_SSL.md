## Ⅰ. 개요
| 항목 | 내용 |
|---|---|
| **정의** | 전송 계층과 응용 계층 사이에서 기밀성, 무결성, 상호 인증을 제공하는 암호화 통신 표준 프로토콜임 |
| **배경/필요성** | 평문 통신인 HTTP(웹), FTP 등 응용 프로토콜의 스니핑 및 조작 위협을 방어하기 위한 보안 채널 필요 |
| **출제 의도** | 핸드셰이크, 레코드, 경고 프로토콜 등 하위 아키텍처와 제공하는 3대 보안 서비스 이해 |

## Ⅱ. 구성요소
```text
+-------------------+      +-------------------+      +-------------------+
|  Handshake Prot.  |      |   Record Prot.    |      |  Alert/Change Prot|
| (인증 및 키 교환) +----->| (데이터 암호/단편)+----->| (오류 통보/상태)  |
+-------------------+      +-------------------+      +-------------------+
```
| 구성요소 | 설명 | 비유 |
|---|---|---|
| **Handshake (핸드셰이크)** | 통신 시작 전 상호 인증, 암호 알고리즘 협상 및 세션키를 교환하는 과정임 | 양국 정상회담의 사전 의전 협의 |
| **Record (레코드)** | 응용 계층의 데이터를 단편화(분할), 압축, MAC 추가, 암호화하여 전송하는 엔진임 | 실제 합의문을 봉인하여 우편 송달 |
| **Alert / Change Cipher Spec** | 통신 오류나 경고를 알리고, 협상된 암호 체계로의 전환을 통보하는 프로토콜임 | 비상 연락망 및 새로운 통신 규약 선포 |

> 요약: 연결 수립 계층(Handshake)과 실제 데이터 보호 전송 계층(Record)이 결합된 종합 보안 스택임.

## Ⅲ. 절차
```text
+----------------+   +----------------+   +----------------+   +----------------+
| 1. 알고리즘 협상|-->| 2. 서버 인증   |-->| 3. 세션키 교환 |-->| 4. 데이터 전송 |
| (Client Hello) |   | (인증서 전달)  |   | (Pre-Master)   |   | (Record 암호화)|
+----------------+   +----------------+   +----------------+   +----------------+
```
1. **알고리즘 협상**: 클라이언트가 지원하는 암호 제품군(Cipher Suite)과 난수를 보내면 서버가 하나를 선택해 응답함
2. **서버 인증 및 공개키 전달**: 서버가 자신의 X.509 인증서를 보내 클라이언트가 유효성(CA 서명 등)을 검증함
3. **세션키 교환**: 인증서의 공개키로 예비 마스터 키(Pre-Master Secret)를 암호화해 전송하고, 이를 통해 대칭 세션키를 도출함
4. **보안 데이터 전송**: 도출된 세션키를 이용해 레코드 프로토콜에서 모든 응용 데이터를 대칭 암호화하여 송수신함

> 요약: 비대칭키로 인증 및 세션키를 안전하게 교환하고, 도출된 세션키로 대용량 데이터를 고속 암호화함.

## Ⅳ. 문제점
* **구버전 취약점 누적**: SSLv3, TLS 1.0, 1.1 등 구버전에 POODLE, BEAST 등 다양한 설계 결함 및 암호학적 공격 기법 노출
* **핸드셰이크 오버헤드**: 연결 초기 설정 과정에 다수의 왕복 시간(RTT)과 비대칭 암호 연산이 필요해 접속 지연 유발
* **정적 RSA 키 교환의 한계**: 서버 개인키가 유출될 경우 과거에 수집된 모든 암호화된 트래픽이 사후에 해독될 위험성(PFS 부재)

## Ⅴ. 개선방안
* **단기 방안 (강력한 Cipher Suite)**: 취약한 알고리즘(RC4, MD5 등)을 비활성화하고 AES-GCM 및 SHA-256 이상만 지원토록 설정 변경
* **중기 방안 (PFS 필수화)**: 정적 RSA 키 교환을 금지하고, 세션마다 독립적 키를 생성하는 ECDHE 기반 키 교환으로 전환하여 완전 순방향 비밀성 보장
* **장기 방안 (TLS 1.3 전환)**: 불필요한 구형 알고리즘을 모두 삭제하고 1-RTT/0-RTT 등 핸드셰이크 구조를 전면 개편한 TLS 1.3 표준으로 마이그레이션

## Ⅵ. 전망
* 레거시 버전(TLS 1.1 이하)은 글로벌 표준 기구와 브라우저에서 완전 퇴출되었으며, 1.2와 1.3만이 유일한 안전한 규격으로 인정받고 있음
* 향후 양자 컴퓨터 공격에 대비하여 KEM 알고리즘 기반의 하이브리드 양자내성암호가 결합된 새로운 TLS 표준 확장이 진행될 예정임
