## 미리 알고가기

- PSIRT는 제품 취약점 제보를 접수하고 분석하고 고객 공지와 패치까지 연결하는 제품 보안 전담 조직임
- SOC나 CSIRT가 조직의 침해 사고를 다룬다면, PSIRT는 제품 결함과 고객 영향과 공개 조율을 다룸
- 효과적인 PSIRT는 접수 창구보다 트리아지, 개발 연계, 공지 품질, 공개 일정 관리가 중요함

## Ⅰ. 개요

- **정의/개념**: PSIRT는 제품 취약점을 접수·분석하고 수정본, 완화책, 보안 권고를 고객에게 제공하는 제품 보안 대응 조직임
- **배경/필요성**: 제품 취약점은 고객 환경과 공급망에 연쇄 영향을 줌. 재현, 공개 일정, 고객 안내를 묶는 단일 책임 조직이 필요함

## Ⅱ. 특징

- 취약점 접수, 트리아지, 개발 수정, 공개 커뮤니케이션을 하나의 흐름으로 관리함
- CVE 할당, CVSS 산정, 보안 권고 작성처럼 외부 표준과 연결됨
- 공개 시점과 고객 패치 준비 시점을 조율해야 하므로 법무·지원 협력이 중요함
- SLA 없이 운영하면 접수 지연과 고객 신뢰 저하가 빠르게 발생함

## Ⅲ. 종류 및 비교

| 판단 기준 | PSIRT | CSIRT/SOC |
|:---|:---|:---|
| 주요 대상 | 제품 취약점과 고객 영향 | 조직 내부 침해 사고와 보안 이벤트 |
| 핵심 산출물 | 패치, 완화책, advisory, CVE 정보 | 탐지, 격리, 포렌식, 복구 |
| 협업 축 | 개발, QA, 고객지원, 법무 | 운영, 인프라, 관제, IR |
| 성공 기준 | 고객 영향 최소화와 공개 품질 | 침해 탐지 속도와 피해 억제 |

## Ⅳ. 구성요소 및 구조

| 구성요소 | 설명 |
|:---|:---|
| Intake Channel | 연구자와 고객이 안전하게 제보할 창구를 제공함 |
| Triage and Reproduction | 유효성, 중복 여부, 영향 범위를 검증함 |
| Remediation Coordination | 개발과 QA와 함께 수정본과 완화책을 준비함 |
| Advisory and Disclosure | CVE, CVSS, 권고문, 공개 일정과 고객 공지를 관리함 |

```text
제보 접수 -> 트리아지/재현 -> 심각도 산정 -> 수정/완화책 준비 -> advisory 공개 -> 사후 개선
```

## Ⅴ. 원리 및 절차 흐름도

```text
접수 확인 -> 영향 분석 -> 개발 연계 -> 패치/완화책 검증 -> 고객 공지 -> 재발 방지 반영
```

1. **접수 확인**: 제보자를 식별하고 기본 증적과 범위를 확인함
2. **영향 분석**: 취약점 재현과 영향 제품 버전과 심각도를 판단함
3. **개발 연계**: 수정 일정과 우회책과 테스트 범위를 합의함
4. **공지 준비**: CVE, CVSS, 고객 영향과 대응 방법을 문서화함
5. **재발 방지**: Secure SDLC와 테스트 케이스에 결함 원인을 반영함

## Ⅵ. 실무 적용 및 유의점

1. 외부 고객 제품 조직은 개발·법무·고객지원의 공개 일정과 메시지를 합의하고 접수 응답 시간·패치 제공 시간·공지 정확도로 확인함
2. 외부 제보 조직은 트리아지 SLA와 공개 정책을 두고 유효 제보 처리율·영향 자산 식별 누락 여부·재발 방지 반영률로 확인함

## Ⅶ. 결론

- PSIRT는 제품 취약점을 기술 수정과 고객 커뮤니케이션까지 연결하는 조직이므로 트리아지, 공지, 개발 연계가 견고해야 함
