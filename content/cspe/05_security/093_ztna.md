## Ⅰ. 개요
- **정의**: 네트워크 위치와 무관하게 사용자·기기·컨텍스트를 매 요청마다 검증하여 접근을 허가하는 보안 모델
- **배경/필요성**: 원격 근무·클라우드 확산으로 네트워크 경계가 사라져 VPN 기반 경계 보안이 한계에 도달함
- **비유**: 건물 출입증이 아닌 방문할 때마다 신분·목적·건강 상태를 확인하는 호텔 체크인

| 출제 의도 | 반드시 짚을 핵심 | 감점 회피 포인트 |
|:---|:---|:---|
| VPN 대비 ZTNA 차이 이해 | 세션 단위 인증·최소 권한·암묵적 신뢰 배제 | ZTNA는 아키텍처가 아닌 접근 방식(105 참조) |

> 요약: ZTNA는 매 접근마다 신뢰를 검증하여 네트워크 경계 없이 보안을 유지하는 모델임

## Ⅱ. 구성요소
```text
[사용자/기기] --> [ZTNA Broker] --> [Policy Engine] --> [애플리케이션]
                      |                  |
               신원 확인/기기 상태    정책 평가/세션 제어
```

| 구성요소 | 설명 | 비유 |
|:---|:---|:---|
| ZTNA Broker | 사용자 요청을 수신하고 정책 엔진에 인가를 위임하는 중계점 | 접수 창구 |
| Policy Engine | 사용자·기기·컨텍스트 속성으로 접근 허가를 결정함 | 심사관 |
| Trust Agent | 기기의 보안 상태(패치·EDR·암호화)를 수집·보고함 | 건강검진표 |
| SDP Gateway | 인가된 세션에 한해 앱으로의 네트워크 경로를 개방함 | 비밀 통로 |

> 요약: Broker가 요청을 접수하고 Policy Engine이 판단하여 SDP Gateway가 경로를 열어주는 구조임

## Ⅲ. 절차
```text
접근 요청 --> 신원/기기 검증 --> 정책 평가 --> 마이크로터널 생성
```
- 1단계: 사용자가 앱 접근을 요청하면 ZTNA Broker가 수신함
- 2단계: IdP 연동으로 신원을 확인하고 Trust Agent가 기기 보안 상태를 수집함
- 3단계: Policy Engine이 사용자·기기·위치·시간 속성으로 접근 허가를 결정함
- 4단계: 허가된 세션에 한해 앱까지 암호화된 마이크로터널을 생성하고 세션을 모니터링함

> 요약: 신원·기기 검증 후 정책 기반으로 최소 범위의 터널만 허용하는 흐름임

## Ⅳ. 문제점
- 지연 증가: 매 요청마다 다중 속성 평가를 수행하면 접근 응답 시간이 늘어남
- 레거시 통합 난이도: 에이전트 설치가 불가한 구형 시스템은 ZTNA 적용이 곤란함
- 정책 관리 부담: 앱·사용자·기기 조합이 많아지면 정책 수가 폭증하여 운영 복잡도가 상승함

> 요약: 인가 지연, 레거시 호환, 정책 폭증이 도입 시 과제임

## Ⅴ. 개선방안
1. 단기: 정책 평가 결과를 세션 단위로 캐싱하여 반복 검증 지연을 줄임
2. 중기: 에이전트리스 ZTNA 모드를 제공하여 레거시 시스템도 브라우저 기반으로 접근을 지원함
3. 장기: AI 기반 정책 자동 추천·정리로 정책 수를 최적화하고 이상 탐지를 자동화함

> 요약: 캐싱 → 에이전트리스 → AI 정책 최적화로 단계적으로 해소함

## Ⅵ. 전망
- 발전 방향: SASE 프레임워크와 통합되어 네트워크·보안을 단일 서비스로 제공하는 추세임
- 기술사적 판단: VPN 대체가 아닌 보완 단계이며 하이브리드 운영이 당분간 지속될 전망임
- 기술사 제언: ZTNA 도입 시 기존 VPN 병행 로드맵과 정책 거버넌스 체계를 함께 수립할 필요가 있음
