# 📖 【암기용】 개념 완전 이해

## 한눈에
- **개요**: **TLS(SSL의 후속)는 TCP 위에서 서버 인증·기밀성·무결성을 제공하는 전송계층 보안 프로토콜로, 레코드 계층과 핸드셰이크 계층으로 나뉘며 SSL은 취약해 전면 폐기됨**. 대칭·해시·인증서 원리는 (001~012 참조).
- **왜 필요한가**: 평문 TCP는 도청·변조·서버 위장에 무방비임. TLS는 인증서로 서버를 인증하고 세션키를 안전 합의해 응용 데이터를 암호화·무결성 보호함으로써 HTTPS·메일·VPN의 기반이 됨.
- **핵심 직관**: 택배 배송 전 "본인 확인(인증서) → 봉인 상자와 열쇠 합의(핸드셰이크) → 밀봉 운송(레코드 암호화)"의 절차와 같음. SSL은 낡은 봉인이라 뜯기므로 TLS로 교체함.

## 핵심 용어 정리 (내부에 등장하는 것들)

답안에 등장하는 계층·서브프로토콜·버전·공격을 먼저 풀어 둠. 상위 핵심 키워드는 **전송계층 보안(TLS)** 으로, 응용 프로토콜과 무관하게 TCP 스트림을 통째로 보호하는 계층임.

| 용어/표기 | 의미 | 비유·예 |
|:---|:---|:---|
| SSL / TLS | Netscape의 원조 보안 프로토콜 / IETF 표준 후속 | 구형 봉인 / 현행 봉인 |
| 레코드 계층(Record) | 상위 메시지를 조각·암호화·MAC해 전송하는 하부 계층 | 밀봉·운송 담당 |
| 핸드셰이크(Handshake) | 버전·암호 협상·인증·키 합의 서브프로토콜 | 거래 전 신원·열쇠 협의 |
| Change Cipher Spec | 이후 암호 적용 전환 신호(1.3서 사실상 제거) | "지금부터 밀봉" 구령 |
| Alert | 오류·종료를 알리는 서브프로토콜 | 경고·종료 통지 |
| Cipher Suite | 키교환·인증·암호·해시 조합 명세 | "TLS_AES_128_GCM_SHA256" |
| 대칭키(세션키) | 합의 후 데이터 암호화에 쓰는 공유키 | 상자 여닫는 공용 열쇠 |
| AEAD | 암호화+무결성을 한 번에 하는 방식(GCM 등) | 봉인과 훼손감지 일체형 |
| PFS(전방향비밀성) | 장기키 유출돼도 과거 세션 안전(ECDHE) | 매번 버리는 임시 열쇠 |
| MITM | 중간자 가로채기 공격 | 배송 중간 바꿔치기 |
| 다운그레이드 공격 | 약한 구버전으로 강제 유도 | "낡은 봉인 써라" 강요 |
| POODLE/BEAST | SSL 3.0·CBC 취약점 공격 이름 | 구형 봉인의 뜯는 수법 |

## 깊이 이해
- **배경·문제의식**: 1994년 Netscape가 SSL을 만들었으나 SSL 2.0은 다운그레이드·MITM에, SSL 3.0은 POODLE(CBC 패딩)에 뚫림. IETF가 이를 넘겨받아 TLS 1.0(1999)로 표준화했고, 이후 CBC·RC4·RSA 키교환의 구조적 약점을 순차 제거하며 TLS 1.3(2018)까지 발전함. SSL 2.0/3.0과 TLS 1.0/1.1은 현재 모두 폐기(RFC 8996)됨.
- **작동 원리(어떻게+왜)**: 핸드셰이크에서 버전·Cipher Suite를 협상하고 서버 인증서를 검증한 뒤 (EC)DHE로 세션키를 합의함. 이후 레코드 계층이 응용 데이터를 세션키로 AEAD 암호화해 조각 단위로 전송함. 인증은 비대칭(인증서·서명), 대량 암호화는 대칭(세션키)으로 나눠 성능과 보안을 동시에 얻는 하이브리드 구조임(003 참조).
- **비유**: 은행 거래와 같음. 먼저 창구에서 신분증(인증서)으로 상대를 확인하고 일회용 금고 열쇠(세션키)를 나눈 뒤, 이후 모든 서류를 그 금고에 넣어 주고받음.
- **구체 예시**: HTTPS는 443 포트에서 TLS를 두름. 브라우저가 ClientHello로 지원 버전·Cipher Suite를 제시하면 서버가 하나를 선택하고 인증서를 제시함. 협상 결과가 `TLS_AES_128_GCM_SHA256`이면 AES-128-GCM(AEAD)로 데이터를 보호함.
- **흔한 오해·주의점**: (1) "SSL 인증서"는 관용어일 뿐 실제 프로토콜은 TLS임 — SSL 자체는 써선 안 됨. (2) TLS는 특정 응용에 종속되지 않고 TCP 스트림을 보호함(HTTP·SMTP·IMAP 공용). (3) 암호화만으로는 부족하며 서버 인증서 검증(체인·SAN·폐지, 010~012)이 없으면 MITM에 뚫림.

## 연결 개념
- 하이브리드 암호 — 비대칭 인증·키합의 + 대칭 대량암호화 구조 (003 참조)
- X.509·PKI — 서버 인증에 쓰는 인증서와 신뢰 체인 (009·010 참조)
- TLS 1.3 핸드셰이크 — 본 프로토콜의 최신 핸드셰이크 심화 (014 참조)

# 📝 【답안용】 시험 답안 템플릿

## 핵심 인사이트 (3줄 요약)

> 1. **본질**: TLS는 TCP 위에서 서버 인증·기밀성·무결성을 제공하는 전송계층 보안 프로토콜로, 레코드·핸드셰이크 두 계층으로 구성됨.
> 2. **가치**: 인증서 인증과 세션키 합의로 HTTPS·메일·VPN을 도청·변조·위장으로부터 보호하는 인터넷 신뢰의 기반임.
> 3. **판단 포인트**: SSL·TLS 1.0/1.1은 폐기 대상이며, 다운그레이드 차단·AEAD·PFS 적용과 최신 버전 강제가 실효 관건임.

## 출제 의도 및 답안 포인트

| 출제 의도 | 반드시 짚을 핵심 | 감점 회피 포인트 |
|:---|:---|:---|
| 계층 구조 이해 확인 | 레코드·핸드셰이크 계층 분리 | TLS를 단일 절차로 뭉뚱그려 단정 |
| SSL·TLS 관계 이해 | 버전 역사·SSL 폐기 사유 | SSL과 TLS를 동일시 |
| 보안 요건 이해 | 서버 인증·PFS·다운그레이드 방어 | 암호화만 되면 안전하다고 단정 |

> 요약: TLS 답안은 두 계층 구조·버전 역사와 SSL 폐기·인증서 검증과 PFS·다운그레이드 방어를 함께 써야 함.

## Ⅰ. 개요 및 필요성

- 개요: TCP 위에서 서버 인증·기밀성·무결성을 제공하는 전송계층 보안 프로토콜임.
- 배경: 평문 TCP는 도청·변조·서버 위장에 무방비이며 SSL은 구조적 취약점으로 폐기됨.
- 필요성: 인증서 인증과 세션키 합의로 응용 데이터를 보호해 HTTPS·메일·VPN의 신뢰 기반을 제공함.
- 전제: 대칭·해시·인증서·PKI는 (001~012 참조)로 위임하고 프로토콜 계층·버전·협상에 집중함.

---

## Ⅱ. 구조 및 구성요소

```text
Application (HTTP/SMTP/IMAP)
  -> TLS Handshake 계층
       / Handshake: 버전·CipherSuite 협상, 인증서 검증, (EC)DHE 키합의
       / Alert: 오류·종료 통지  / Change Cipher Spec: 암호 전환(1.3 제거)
  -> TLS Record 계층: 조각화 -> AEAD 암호화·MAC -> 순서번호
  -> TCP -> IP
```

| 구성요소 | 역할 | 특이사항 |
|:---|:---|:---|
| 핸드셰이크 | 협상·인증·키 합의 | 세션키·버전·CipherSuite 결정 |
| 레코드 계층 | 데이터 조각화·암호화·무결성 | AEAD로 기밀+무결성 일체화 |
| Cipher Suite | 키교환·인증·암호·해시 조합 | 1.3서 AEAD·해시만 남김 |
| Alert | 오류·종료 신호 | close_notify로 정상 종료 |
| 세션 재개 | 재접속 시 핸드셰이크 단축 | Session ID·Ticket·PSK |

> 요약: TLS는 협상·인증·키합의를 담당하는 핸드셰이크 계층과 데이터를 암호화·보호하는 레코드 계층으로 구성됨.

---

## Ⅲ. 동작원리 및 흐름도

```text
클라이언트 ClientHello(버전·CipherSuite·키공유) -> 서버
서버: 버전·CipherSuite 선택 + 인증서 + 키공유 -> 클라이언트
클라이언트: 인증서 검증(체인·SAN·폐지) -> 공유 세션키 산출
양측: Finished 교환 -> 레코드 계층에서 AEAD 암호화 통신
```

1. 클라이언트가 ClientHello로 지원 버전·Cipher Suite·키공유 재료를 제시함.
2. 서버가 최고 공통 버전·Cipher Suite를 선택하고 인증서와 자신의 키공유를 제시함.
3. 클라이언트가 서버 인증서 체인·SAN·폐지(010~012)를 검증하고 (EC)DHE로 세션키를 산출함.
4. 양측이 Finished로 협상 무결성을 확인한 뒤 레코드 계층이 세션키로 응용 데이터를 AEAD 암호화·전송함.

> 요약: 협상·인증·키합의를 마친 뒤 세션키로 레코드를 암호화하며, Finished가 협상 조작·다운그레이드를 검출함.

---

## Ⅳ. 특징

- 계층 분리: 핸드셰이크(협상·인증·키합의)와 레코드(암호화·무결성)를 분리해 응용 프로토콜과 독립적으로 동작함.
- 하이브리드 구조: 비대칭으로 인증·키합의, 대칭으로 대량 암호화해 보안과 성능을 양립함(003).
- 전방향비밀성: (EC)DHE 채택 시 장기키가 유출돼도 과거 세션이 안전함.
- 버전 협상: 다운그레이드 공격 방어를 위해 Finished 해시·downgrade sentinel로 협상 조작을 검출함.
- 폐기 이력: SSL 2.0/3.0·TLS 1.0/1.1은 POODLE·BEAST 등으로 폐기(RFC 8996), 현행은 TLS 1.2/1.3임.

## Ⅴ. 심화 비교 및 적용 판단

SSL·TLS 주요 버전을 인증·암호·취약점 축으로 비교함(다대상×다축이므로 표 사용).

| 구분 | SSL 3.0 | TLS 1.2 | TLS 1.3 |
|:---|:---|:---|:---|
| 상태 | 폐기(POODLE) | 유지·광범위 사용 | 현행 권장 |
| 암호 방식 | CBC·RC4 등 | CBC·AEAD 혼재 | AEAD 전용 |
| 키 교환 | RSA·정적 DH | RSA·(EC)DHE 선택 | (EC)DHE 강제(PFS) |
| 핸드셰이크 | 2-RTT | 2-RTT | 1-RTT(0-RTT 재개) |

> 요약: 신규·성능 중시 서비스는 TLS 1.3, 레거시 호환이 필요하면 TLS 1.2까지 허용하되 SSL·TLS 1.0/1.1은 전면 차단함.

리스크 관리는 불릿으로 정리함.
- 리스크: 다운그레이드 강제 — 원인: 구버전·약한 Cipher Suite 허용 — 대응: TLS 1.2↑ 강제·downgrade 방어, 약한 스위트 0건.
- 리스크: 인증서 미검증 MITM — 원인: 체인·SAN·폐지 확인 생략 — 대응: 엄격 검증·HSTS·pinning, 검증 우회 0건.
- 리스크: 취약 암호 사용 — 원인: RC4·3DES·CBC·SHA-1 잔존 — 대응: AEAD·ECDHE만 허용, 취약 스위트 스캔.

지표 관리도 불릿으로 정리함.
- 지표: 버전 준수율 — 목표: TLS 1.2/1.3만 활성 — 측정: SSL Labs·내부 TLS 스캔.
- 지표: PFS 적용률 — 목표: ECDHE 스위트 100% — 측정: 핸드셰이크 로그·스캐너.
- 지표: 인증서 위생 — 목표: SAN·폐지·만료 정상 — 측정: 인증서 인벤토리 감사.

## Ⅵ. 실무 적용 및 결론

**적용 방안 3개 (필수 — 단계별 또는 항목별):**
1. 버전·스위트 정책: TLS 1.3 우선, TLS 1.2까지 허용, SSL·TLS 1.0/1.1 차단, AEAD·ECDHE만 활성화.
2. 인증서·검증: SAN·체인·폐지(012) 엄격 검증에 HSTS·인증서 pinning을 더해 MITM·다운그레이드를 차단.
3. 운영 자동화: 인증서 ACME 자동 갱신, TLS 스캐너 정기 점검, PQC 대비 하이브리드 키교환(015·019) 준비.

**결론 (2줄):**
- 기술사 판단: 신규·대외 서비스는 TLS 1.3+ECDHE, 레거시 연동 구간만 TLS 1.2를 한시 허용하고 조기 정리함.
- 향후 방향: 짧은 수명 인증서·자동 갱신과 PQC 하이브리드 전환으로 암호 민첩성을 확보하는 것이 필요함.
