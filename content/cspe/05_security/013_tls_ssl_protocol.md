## 1. 한눈에 이해하기 (Core Intuition)
- **정의**: 인터넷을 통해 데이터를 주고받을 때 누군가 훔쳐보거나 조작하지 못하도록, 통신 파이프라인 전체를 강력한 암호로 감싸는 네트워크 보안 프로토콜입니다. (HTTPS의 'S'를 담당)
- **필요성**: HTTP나 TCP/IP는 데이터를 엽서처럼 겉면에 다 드러낸 채로 전송합니다. 카페의 무료 Wi-Fi를 쓸 때 해커가 내 비밀번호를 평문으로 엿보는 것을 막기 위해 반드시 필요합니다.
- **핵심 직관**: **"무적의 디지털 장갑차"**. 맨몸으로 고속도로(인터넷)를 달리는 데이터(HTTP)를, 문을 꼭 잠그고 누구도 열 수 없는 장갑차(TLS)에 태워 보내는 것과 같습니다. 장갑차를 타기 전 운전수(서버)가 진짜 직원이 맞는지 신분증(인증서)을 확인하고, 문을 잠글 유일한 열쇠(세션키)를 나눠 갖는 과정이 핵심입니다.

## 2. 왜 중요한가? (Background & Value)
- **등장 배경**: 1995년 넷스케이프 사가 웹 브라우저 보안을 위해 SSL(Secure Sockets Layer) 2.0을 만들었고, 이후 표준화 기구(IETF)로 이관되면서 이름이 TLS로 바뀌었습니다. (현재 SSL은 보안 취약점으로 모두 폐기되었으나, 관습적으로 혼용해서 부릅니다).
- **가치**: 현대 인터넷 전자상거래와 프라이버시 보호의 근간입니다. 웹(HTTPS)뿐만 아니라 메일(SMTPS), 파일 전송(FTPS), VPN 통신 등 거의 모든 애플리케이션 보안의 밑바탕이 됩니다.

## 3. 어떻게 작동하는가? (Mechanism)
- **3대 보안 기능**:
  1. **기밀성 (대칭키 암호)**: 제3자가 내용을 볼 수 없게 암호화 (AES 사용)
  2. **무결성 (MAC / 해시)**: 전송 중 데이터가 한 글자라도 변조되지 않음 보장 (HMAC 사용)
  3. **인증 (공개키/인증서)**: 내가 접속한 서버가 진짜 네이버/구글이 맞는지 확인 (RSA/ECC, X.509 사용)

- **작동 원리 (TLS Handshake)**: 우리가 전화를 걸 때 "여보세요, 누구신가요?" 하고 대화의 규칙을 맞추는 것처럼, 클라이언트와 서버가 본격적인 암호화 데이터를 주고받기 전 **'준비 운동(Handshake)'** 을 합니다.
  1. **Client Hello**: "나는 TLS 1.2를 쓸 수 있고, AES 알고리즘을 지원해. 내 임시 난수는 123이야."
  2. **Server Hello & Certificate**: "그래, AES로 통신하자. 내 난수는 456이고, 내 신분증(인증서)과 내 공개키 여기 있어."
  3. **Key Exchange (비밀키 생성)**: 클라이언트는 인증서가 진짜인지 브라우저를 통해 확인합니다. 맞다면, 안전한 수학(Diffie-Hellman이나 RSA)을 이용해 서버와 나만 아는 '마스터 세션키(Master Secret)'를 만들어 냅니다.
  4. **Finished**: "이제부터 모든 말은 이 세션키로 암호화해서 할게!" (안전한 터널 완성)

## 4. 실전 활용 및 예시 (Real-world Application)
- **구체적 사례**: 
  - **웹 브라우저**: 주소창의 자물쇠 아이콘을 클릭하면 "연결이 안전합니다"와 함께 사용 중인 TLS 버전(보통 TLS 1.2 또는 1.3)을 확인할 수 있습니다.
  - **Cipher Suite (암호 스위트)**: TLS는 단일 암호가 아니라 종합 세트입니다. 예: `TLS_ECDHE_RSA_WITH_AES_256_GCM_SHA384` 
    (해석: 키 교환은 ECDHE, 서버 인증은 RSA, 데이터 암호화는 AES-256 GCM 모드, 무결성은 SHA-384를 쓴다는 뜻).
- **주의점 및 흔한 오해**: 
  - TLS는 데이터가 전송되는 '구간(파이프)'을 보호할 뿐, 서버의 데이터베이스가 털리는 것까지 막아주진 않습니다.
  - SSL 2.0, SSL 3.0, TLS 1.0, TLS 1.1은 치명적인 취약점(POODLE, BEAST 등)으로 인해 전 세계적으로 사용이 **전면 금지(Deprecated)** 되었습니다. 최소 TLS 1.2 이상을 써야 합니다.

## 5. 핵심 비교 및 연결 개념 (Relation)
- **OSI 7계층**: TCP(4계층) 위, Application(HTTP, 7계층) 아래에서 투명하게 동작하여 응용 프로그램의 수정 없이 보안을 제공합니다.
- **연결 개념**: 
  - **mTLS (Mutual TLS)**: 보통 서버만 신분증을 내지만, 제로 트러스트나 마이크로서비스(MSA) 환경에서는 클라이언트도 인증서를 제출해 **쌍방향**으로 검증하는 기술.

# ✍️ 단답형 / 서술형 시험장 출격 준비

### Ⅰ. 핵심 인사이트
- **본질**: TCP/IP 네트워크의 전송 계층(Transport Layer) 상위에서 하이브리드 암호 체계를 이용하여 종단 간(End-to-End) 기밀성, 무결성, 인증을 제공하는 IETF 표준 프로토콜.
- **가치**: HTTP 등 평문 프로토콜의 보안 취약점을 응용 계층의 구조 변경 없이 투명하게 해결하며, 현대 인터넷 보안의 사실상 단일 표준(De facto standard)으로 작용.
- **판단 포인트**: 레거시 취약점(POODLE, Heartbleed)을 제거하기 위해 TLS 1.2 미만 버전은 전면 차단해야 하며, 보안 강화를 위해 암호 스위트에 완전 순방향 안전성(PFS) 및 AEAD 지원 모드를 강제하는 아키텍처 설계가 필수적임.

### Ⅱ. TLS 프로토콜 스택 아키텍처
TLS는 단일 프로토콜이 아닌 2계층의 프로토콜 스위트로 구성됨.

**1. 하위 계층 (Record Layer)**
- **TLS Record Protocol**: 상위 프로토콜의 메시지를 단편화(Fragmentation), 압축, MAC 추가(무결성), 대칭키 암호화(기밀성)하여 TCP 계층으로 전달.

**2. 상위 계층 (Handshake, Change Cipher Spec, Alert, Application Data)**
- **Handshake Protocol**: 통신 양단 간 암호 알고리즘(Cipher Suite) 협상, 인증서 교환, 세션키(Master Secret) 생성을 수행하는 핵심 통신 규약.
- **Change Cipher Spec Protocol**: "이후부터 전송되는 모든 메시지는 협상된 암호 스위트와 세션키로 암호화함"을 알리는 1바이트 플래그 메시지. (TLS 1.3부터 Record Layer로 흡수/단순화됨).
- **Alert Protocol**: 세션 종료, 인증서 오류, 해독 실패 등 오류/경고 상태를 상대방에게 통보 (Fatal 발생 시 즉각 연결 종료).

### Ⅲ. TLS 1.2 Handshake 메커니즘 (Full Handshake)
- **Step 1 (협상)**: 
  - `Client Hello`: 클라이언트 난수, 지원하는 Cipher Suite 목록 전달.
  - `Server Hello`: 서버 난수, 선택된 Cipher Suite 반환.
- **Step 2 (서버 인증 및 키 교환 준비)**:
  - `Certificate`: 서버의 X.509 인증서(공개키 포함) 전송.
  - `Server Key Exchange` (선택적): DH 키 교환 시 서버 파라미터 전송.
  - `Server Hello Done`: 서버 메시지 전송 완료 통보.
- **Step 3 (클라이언트 인증 및 세션키 생성)**:
  - 클라이언트는 서버 인증서 검증(PKI 체인).
  - `Client Key Exchange`: Pre-Master Secret을 생성하여 서버 공개키로 암호화 후 전송 (또는 DH 파라미터 교환).
  - [ 양측 모두 `난수 2개 + Pre-Master Secret`을 이용해 최종 **Master Secret(세션키)** 도출 ]
- **Step 4 (암호화 통신 시작)**:
  - `Change Cipher Spec` & `Finished`: 양측 모두 "이제부터 암호화한다"고 선언 후 핸드셰이크 종료.

### Ⅳ. 주요 보안 위협과 레거시 버전의 취약점
1. **다운그레이드 공격 (Downgrade Attack)**: 해커가 Handshake 메시지를 변조하여 강제로 취약한 옛날 버전(SSL 3.0 / Export 암호)을 쓰도록 유도하는 공격. (방어: `TLS_FALLBACK_SCSV` 신호 사용).
2. **Heartbleed (하트블리드)**: OpenSSL 라이브러리 버그. 서버에 Heartbeat 확장 메시지 전송 시 길이(Length) 검증 누락으로, 서버 메모리(개인키, 비밀번호 등)가 줄줄 새어 나오는 역사상 최악의 취약점.
3. **POODLE / BEAST Attack**: SSL 3.0, TLS 1.0/1.1의 CBC 모드 블록 암호화의 패딩 취약점을 이용해 평문을 해독하는 공격. $\rightarrow$ 이로 인해 구버전 TLS 전면 폐기 및 AEAD(GCM 모드) 도입 가속화.

### Ⅴ. 실무적 정책 판단 포인트 (암호 스위트 설계 가이드)
- **보안 설정 권고**: 웹 서버(Nginx, Apache) 구축 시 **반드시 TLS 1.2 및 TLS 1.3만 활성화**해야 함.
- **PFS (Perfect Forward Secrecy) 강제**: 암호 스위트 설정 시 `RSA` 키 교환을 배제하고, 반드시 `ECDHE`(타원곡선 디피-헬만 일회용 키 교환)를 우선순위 최상단에 배치하여 서버 키 유출 시 과거 트래픽 복호화를 방지.
- **AEAD 강제**: MAC-then-Encrypt 구조의 취약성을 막기 위해, 데이터 암호화는 `AES-GCM` 또는 `ChaCha20-Poly1305` 등 인증 결합 모드만 허용.

### 💡 문제 유형별 목차 전환 포인트
- **[TLS 핸드셰이크 절차 및 세션키 도출 원리]**: Ⅲ번을 중심으로 Pre-Master Secret이 교환되고 난수(Client/Server Random)와 결합하여 실제 사용할 대칭키가 도출되는 과정을 상세 시퀀스 다이어그램 형태로 서술.
- **[SSL/TLS 취약점 및 대응 방안]**: Ⅳ번과 Ⅴ번을 묶어, 왜 TLS 1.2 미만 버전이 사장되었고(POODLE 등) 현재 어떻게 암호 스위트를 설정(PFS, AEAD)해야 하는지 실무적 보안 정책 관점에서 전개.
