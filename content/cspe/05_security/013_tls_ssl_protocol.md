## 미리 알고가기

- TLS: TCP 기반 통신에 기밀성, 무결성, 서버 인증을 제공하는 보안 프로토콜임
- SSL: TLS 이전 명칭의 구버전 프로토콜이며 SSL 2.0·3.0은 사용하지 않음
- Cipher Suite: 키 교환, 인증, 대칭 암호, 해시 조합을 나타내는 설정임
- Handshake: 알고리즘 협상, 인증서 검증, 세션키 도출 절차임
- Record Protocol: 애플리케이션 데이터를 암호화·분할·검증하는 계층임

## Ⅰ. 개요

- **정의/개념**: TLS는 핸드셰이크로 상대를 인증하고 세션키를 도출한 뒤 레코드 계층에서 데이터를 보호하는 프로토콜임
- **배경/필요성**: 인터넷 통신은 도청, 변조, 서버 위장 위험이 있으므로 애플리케이션 데이터 전송 전에 보안 채널을 구성해야 함

## Ⅱ. 특징

- 인증서 체인 검증으로 서버 공개키와 도메인을 확인함
- 세션키는 핸드셰이크에서 도출하고 데이터 암호화는 대칭 암호로 수행함
- 무결성 검증은 MAC 또는 AEAD 태그로 처리함
- SSL과 TLS 1.0·1.1은 취약점과 정책 사유로 신규 사용에서 제외함

## Ⅲ. 종류 및 비교

| 구분 | SSL 3.0 | TLS 1.2 | TLS 1.3 |
|:---|:---|:---|:---|
| 상태 | 사용 금지 | 제한적 사용 가능 | 신규 권장 |
| 키 교환 | 취약한 조합 존재 | RSA, DHE, ECDHE 등 선택 | 임시 DH 계열 중심 |
| 암호 모드 | CBC 등 취약 조합 | CBC·GCM 등 혼재 | AEAD 중심 |
| 핸드셰이크 | 레거시 구조 | 보통 2-RTT | 보통 1-RTT |
| 적용 판단 | 차단 | 호환성 필요 시 정책 제한 | 기본 적용 대상 |

> 요약: TLS 버전 선택은 이름이 아니라 허용 암호군, PFS, 핸드셰이크 절차로 판단함.

## Ⅳ. 구성요소 및 구조

| 구성요소 | 역할 |
|:---|:---|
| ClientHello | 지원 버전, 암호군, 난수, 확장 제안 |
| ServerHello | 선택한 버전·암호군과 서버 난수 전달 |
| Certificate | 서버 공개키와 도메인 신원 제시 |
| Key Exchange | 공유 비밀 또는 키 재료 생성 |
| Record Protocol | 애플리케이션 데이터 암호화와 검증 |

```text
ClientHello -> ServerHello/Certificate -> Key Exchange -> Finished -> Encrypted Records
```

## Ⅴ. 원리 및 절차 흐름도

1. **협상 시작**: 클라이언트가 지원 버전과 암호군을 제안함
2. **서버 선택**: 서버가 버전, 암호군, 인증서를 제시함
3. **인증서 검증**: 클라이언트가 체인, 도메인, 기간, 폐지 상태를 확인함
4. **키 도출**: 키 교환 결과와 난수로 세션키를 생성함
5. **데이터 보호**: 레코드 계층에서 암호화와 무결성 검증을 수행함

## Ⅵ. 실무 적용 및 유의점

- 서버 설정은 TLS 1.2 이상, 가능하면 TLS 1.3을 기본으로 둠
- 인증서 만료와 체인 누락은 보안 장애보다 먼저 서비스 장애로 나타남
- 약한 암호군과 압축 기능은 다운그레이드·오라클 공격 위험을 키움
- 기업 내부 복호화 장비는 TLS 1.3의 PFS와 ECH 확장을 고려해야 함
- mTLS는 클라이언트 인증서를 추가 검증해 양방향 인증을 구성함

## Ⅶ. 결론

- TLS는 공개키 인증, 키 교환, 대칭 암호화를 결합한 전송 보안 프로토콜임
- 답안에서는 SSL/TLS 명칭보다 핸드셰이크, 인증서 검증, 레코드 보호 절차를 써야 함

## 작성 근거(검토용)

- TLS를 “인터넷 보안 표준”으로만 표현하지 않고 절차와 계층으로 분해함
- 버전 비교는 새 버전 여부보다 허용 암호군과 핸드셰이크 차이를 기준으로 삼음
- 014 TLS 1.3 문서와 중복되지 않도록 기본 구조와 운영 유의점에 집중함
