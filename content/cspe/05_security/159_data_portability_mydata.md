# 📖 【암기용】 개념 완전 이해

> 목적: 전송 요구권과 마이데이터를 처음 보는 사람도 이해하게 만든다. 시험 답안 양식이 아니라, 이해를 위한 설명이다.

## 한눈에
- **개요**: 정보주체가 자신의 개인정보를 본인 또는 제3자에게 전송하도록 요구하는 권리와 서비스 체계
- **왜 필요한가**: 개인정보가 기관별로 흩어지면 개인은 서비스 전환 때 같은 서류를 반복 제출하고, 기업은 폐쇄된 데이터 때문에 맞춤 서비스를 설계하기 어렵다. 전송요구권은 본인 통제 하에 데이터를 이동시키는 장치임.
- **핵심 직관**: 마이데이터는 "기업이 데이터를 나누어 주는 사업"이 아니라 "본인이 지정한 목적지로 본인 데이터를 옮기는 권리 행사"임.

## 깊이 이해
- **배경·문제의식**: 금융 마이데이터 이후 의료·통신·유통 등 전 분야 데이터 이동 수요가 커졌다. 개인정보보호법 제35조의2는 전송 대상, 전송자, 수신자, 제외 정보를 정해 무분별한 복사를 막음.
- **작동 원리**: 정보주체가 전송 요구를 하면 정보전송자는 본인확인, 대상 데이터 확인, 수신자 검증, API 전송, 전송내역 기록을 수행한다. 2026.6 PIPC 안내서는 전 분야 마이데이터 제도 운영 기준을 최신 안내서로 제시함.
- **비유**: 병원 진료기록을 직접 들고 다니는 대신, 본인이 승인한 앱으로 필요한 항목만 안전하게 보내는 구조와 같음.
- **구체 예시**: 통신 이용내역, 건강검진 기록, 쇼핑 구매내역을 본인이 지정한 마이데이터 서비스로 전송하면 맞춤 요금제·건강관리·소비분석에 활용 가능함. 단, 사업자가 분석해 새로 만든 신용점수 같은 생성정보는 전송 대상에서 제외될 수 있음.
- **흔한 오해·주의점**: 전송요구권은 열람권과 다르다. 열람은 확인이 목적이고 전송은 기계판독 가능한 방식으로 본인 또는 제3자에게 이동시키는 것이 목적임.

## 연결 개념
- GDPR 데이터 이동권: 동의·계약 기반 자동처리 데이터의 구조화된 전송 권리
- OAuth 2.0·mTLS: 전송 API 인증·권한 범위 통제
- 개인정보관리 전문기관: 전송 생태계의 중계·관리 역할

> 2. **가치**: 데이터 사일로를 줄이되 본인확인, 수신자 검증, 전송로그, 철회 절차로 오남용을 통제한다.

## Ⅰ. 개요 및 필요성

전송요구권은 개인정보 이동권의 국내 법제이다. 정보주체는 일정 요건의 개인정보처리자에게 본인 또는 제3자 전송을 요구할 수 있음. 전 분야 마이데이터는 의료·통신·유통 등 기관별 데이터를 본인 통제 하에 이동시켜 서비스 전환 비용과 반복 제출을 줄이는 제도임.

---

## Ⅱ. 구조 및 구성요소

```text
정보주체 -> 전송 요구 접수 -> 정보전송자 -> 전송 API -> 본인/전문기관/수신자
            +-> 본인확인/동의 범위
            +-> 전송로그/철회/사고 대응
```

| 구성요소 | 역할 | 특이사항 |
|:---|:---|:---|
| 정보주체 | 본인 또는 제3자 전송 요구, 변경·철회 행사 | 요청 채널은 수집 절차보다 어렵지 않아야 함 |
| 정보전송자 | 대상 데이터 확인, 본인확인, 전송 수행 | 대규모 처리자·공공시스템 등 시행령 기준 적용 |
| 수신자·전문기관 | 전송받은 데이터 활용·관리 | 개인정보관리 전문기관은 지정·심사 대상 |
| 전송지원체계 | API, 인증, 로그, 장애 대응 | mTLS, OAuth 2.0, 전송내역 보관 필요 |

> 요약: 마이데이터 구조는 정보주체 권리 요청을 정보전송자와 수신자가 API와 로그로 이행하는 체계임.

---

## Ⅲ. 동작원리 및 흐름도

```text
요구 접수 -> 본인확인 -> 대상 데이터·수신자 검증 -> 전송 범위 산정 -> API 전송 -> 결과 통지 -> 변경/철회 관리
```

| 단계 | 처리 내용 | 검증 기준 |
|:---:|:---|:---|
| 1 | 정보주체 전송 요구 접수 및 본인확인 | FIDO2, CI, 휴대폰 본인확인 로그 |
| 2 | 전송 대상 데이터와 제외 정보 판정 | 본인 데이터, 자동처리 데이터, 생성정보 제외 목록 |
| 3 | 수신자·전문기관 검증 후 API 전송 | mTLS 인증서, OAuth scope, API 응답코드 |
| 4 | 전송 결과 통지, 정기전송 변경·철회 처리 | 전송내역, 철회 SLA 24시간, 오류 재처리 대장 |

> 요약: 전송요구권은 접수부터 철회까지 본인확인, 대상성 판단, 수신자 검증, 전송로그가 끊기면 안 됨.

> 요약: 주요 리스크는 과다 전송, 수신자 오남용, API 장애이며 scope와 전송로그로 통제함.

> 요약: 마이데이터 운영은 권리 추적성, API 보안 설정률, 스키마 오류율로 성공 여부를 판단함.

## Ⅵ. 실무 적용 및 결론

**적용 방안 3개 (필수 — 단계별 또는 항목별):**
1. 전송 대상 카탈로그 구축: 데이터 항목별 법적 근거, 생성정보 제외 여부, 민감·고유식별정보 표시, 보유기간 등록
2. API 보안 설계: OAuth 2.0 authorization code, mTLS, JWS 서명, rate limit 100 TPS, trace ID 기반 로그 보관
3. 운영 프로세스 수립: 전송 실패 통지, 정기전송 철회 SLA 24시간, 수신자 보안점검 반기 1회, 사고 72시간 신고 훈련

**결론 (2줄):**
- 기술사 판단: 단순 본인 사본 제공이면 다운로드, 제3자 정기전송이면 표준 API와 전문기관 검증 구조를 선택함
- 향후 방향: 전 분야 마이데이터는 법적 권리, API 표준, 개인정보관리 전문기관, 데이터 품질관리를 통합하는 방향으로 운영 필요
