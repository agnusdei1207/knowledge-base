## 1. 한눈에 이해하기 (Core Intuition)
- **정의**: 내 정보(개인정보)의 진짜 주인은 기업이 아니라 '나(정보 주체)'이므로, 내가 원할 때 언제든지 **"내 데이터를 A 기업에서 B 기업으로 즉시, 안전하게, 컴퓨터가 읽을 수 있는 형태로 전송해 줘!"라고 당당하게 요구할 수 있는 권리(전송 요구권)와, 이 데이터를 긁어모아 나에게 딱 맞는 서비스를 제공하는 산업(마이데이터)** 입니다.
- **필요성**: 옛날에는 내가 A 통신사를 10년 쓰다가 B 통신사로 옮기려 할 때, A 통신사에 "내 10년 치 통화 습관 데이터 좀 파일로 뽑아줘"라고 하면 "안 됩니다, 이건 우리 회사의 소중한 영업 자산입니다"라며 주지 않았습니다. 이 때문에 거대 플랫폼(네이버, 카카오, 대형 은행)이 데이터를 독점하게 되었고, 정부는 이 독점을 깨고 데이터의 진짜 주인을 찾아주기 위해 2023년 개인정보보호법 개정을 통해 이 권리를 사회 전 분야에 강제하게 되었습니다.
- **핵심 직관**: **"은행 통장 쪼개 쓰기에서 '토스(Toss)' 한 방울"**. 
  - 과거 (데이터 사일로): 국민은행 잔고는 국민은행 앱에서, 신한은행 잔고는 신한은행 앱에서만 봐야 했습니다. (벽이 쳐짐).
  - **전송 요구권(마이데이터)**: 내가 토스 앱에 들어가 "국민, 신한, 농협은행아! 내 잔고 데이터 지금 당장 토스 서버로 다 보내!(전송 요구권)"라고 명령합니다. 은행들은 울며 겨자 먹기로 토스에게 데이터를 API로 쏴줍니다. 토스는 그 데이터(마이데이터)를 예쁘게 분석해 "이번 달 식비 너무 많이 쓰셨네요"라고 알려줍니다.

## 2. 왜 중요한가? (Background & Value)
- **등장 배경**: 유럽의 GDPR(개인정보보호규정)에서 '개인정보 이동권(Right to Data Portability)'을 선포한 것이 시초입니다. 한국은 먼저 금융권(오픈뱅킹, 신용정보법)에서 대성공을 거둔 마이데이터를 의료(MyHealthway), 공공(내문서함)으로 실험하다가, 마침내 2023년 개인정보보호법 개정으로 통신, 유통, 교육 등 **'전 산업 분야'** 로 그 범위를 폭발적으로 넓혔습니다.
- **가치**: "데이터 경제(Data Economy)의 고속도로 개통". 기업들은 더 이상 자사가 가진 데이터를 무기 삼아 고객을 가두는 락인(Lock-in) 전략을 쓰기 힘들어졌습니다. 스타트업도 기발한 분석 아이디어만 있으면 대기업 고객의 데이터를 (고객 동의하에) 합법적으로 넘겨받아 혁신적인 비즈니스를 창출할 수 있는 생태계가 열렸습니다.

## 3. 어떻게 작동하는가? (Mechanism)
마이데이터는 철저하게 규격화된 '표준 API'를 통해 기계 대 기계로 전송됩니다.

1. **정보 주체의 요구 (Request)**
   - 내가 헬스케어 스타트업 앱(마이데이터 사업자)에 가입한 뒤, 버튼을 누릅니다. "나의 10년간 국민건강보험공단 진료 기록을 이 스타트업으로 전송해 줘."
2. **보유자(기존 기업)의 의무적 전송 (Data Transfer via API)**
   - 건강보험공단(데이터 보유자)은 거부할 수 없습니다. 서류를 팩스로 보내주는 게 아니라, 스타트업 서버가 쉽게 읽고 분석할 수 있는 **'기계 판독 가능한 표준화된 형식(JSON, XML)'** 의 API 통신을 통해 데이터를 안전하게 쏴줍니다.
3. **마이데이터(PDS) 사업자의 통합 분석 및 서비스 (Aggregation)**
   - 스타트업은 넘겨받은 진료 기록 데이터를 분석하여 나에게 "고객님은 당뇨 위험이 30% 증가했으니 이 맞춤형 영양제를 드세요"라는 새로운 부가가치 서비스를 제공합니다.
4. **전송 중단 및 파기 (Revocation & Destruction)**
   - 내가 "이제 영양제 추천 서비스 안 쓸래. 내 데이터 다 지워"라고 전송 철회 버튼을 누르면, 데이터의 흐름은 즉시 차단되고 스타트업은 받아갔던 내 데이터를 흔적 없이 파기해야 합니다.

## 4. 실전 활용 및 예시 (Real-world Application)
- **구체적 사례 (의료 마이데이터 '마이헬스웨이')**: 
  - 과거에는 삼성서울병원에서 찍은 MRI나 피검사 결과를 서울대병원으로 가져가려면, 환자가 직접 창구에 가서 돈을 내고 CD를 구워서(물리적 저장 매체) 들고 다녀야 했습니다. (불편함 극도).
  - 현재는 '나의건강기록' 앱(마이데이터 플랫폼)을 열고 전송 버튼 하나만 누르면, 삼성병원 서버에서 서울대병원 서버로 내 진료 기록이 API를 통해 즉시 꽂혀서 의사가 바로 모니터로 확인할 수 있습니다.
- **주의점 및 흔한 오해**: 
  - "내 카카오톡 대화 내용이나 블로그 쓴 글도 경쟁사로 옮겨달라고 요구할 수 있나요?" $\rightarrow$ **아닙니다.** 전송 요구권의 대상이 되는 정보는 이름, 결제 내역, 진료 기록처럼 객관적인 팩트(Fact) 정보입니다. 기업의 독창적인 노하우가 섞인 분석 데이터(예: 이 고객의 VIP 등급 예측치)나 타인의 프라이버시가 섞인 카톡 대화 내용 등은 '전송 의무 대상'에서 제외되어 기업의 영업 비밀을 보호해 줍니다.

## 5. 핵심 비교 및 연결 개념 (Relation)
| 구분 | 열람 청구권 (기존 권리) | 전송 요구권 (마이데이터의 핵심 권리) |
|---|---|---|
| **목적** | "내 정보 뭐뭐 갖고 있는지 내 눈으로 보자" | **"내 정보를 나, 또는 저 회사(C)로 즉시 쏴라"** |
| **데이터 형태** | 화면 출력, 종이 문서 복사본, PDF 등 | **컴퓨터가 즉시 읽어 들일 수 있는 형태 (Open API, JSON)** |
| **비즈니스 효과**| 개인의 궁금증 해소 및 오류 정정 | **이종 산업 간 데이터 결합을 통한 신규 비즈니스 창출** |

# ✍️ 단답형 / 서술형 시험장 출격 준비

### Ⅰ. 핵심 인사이트
- **본질**: 정보 주체(개인)가 개인정보처리자(기업/기관)에 대하여 자신의 개인정보를 본인, 혹은 본인이 지정하는 제3자(마이데이터 사업자, 개인정보 관리 전문기관 등)에게 **기계 판독 가능한(Machine-readable) 형태의 표준화된 API(Application Programming Interface)로 즉각 전송해 줄 것을 요구할 수 있는 데이터 주권(Data Sovereignty)의 핵심 권리.** (2023년 개인정보보호법 개정으로 신설).
- **가치**: 기존 프라이버시 보호가 "내 정보를 함부로 쓰지 마라"는 수동적/방어적 통제(Data Protection)였다면, 전송 요구권은 **"내 데이터를 가장 이익이 되는 곳에 적극적으로 활용하겠다"는 능동적/적극적 통제(Data Utilization)** 로 패러다임을 바꿈. 거대 플랫폼의 데이터 독점(Silo) 현상을 타파하고, 이기종 산업 간 데이터 결합(Mash-up)을 통해 핀테크/디지털 헬스케어 등 초개인화된(Hyper-personalized) 데이터 경제(Data Economy) 생태계를 촉발하는 기폭제.
- **판단 포인트**: IT 설계자 입장에서 전송 요구권은 극강의 아키텍처 도전 과제입니다. 기존에는 폐쇄망(Intranet) 안에서 DB를 꽁꽁 싸매면 끝이었지만, 이제는 외부 스타트업의 서버가 우리 회사 고객 DB에 안전하게 빨대를 꽂아 데이터를 퍼가도록 **'Open API 게이트웨이'를 합법적이고 안전하게 열어주어야(OAuth 2.0 인가 기반)** 하므로, API Security와 자격 증명(Identity) 관리가 보안의 최전선이 됩니다.

### Ⅱ. 마이데이터 플랫폼의 3대 핵심 아키텍처 요소
안전한 데이터 전송을 담보하는 기술 인프라.
1. **표준화된 Open API 및 데이터 규격 (Interoperability)**
   - 수천 개의 기업이 데이터를 주고받으려면 언어가 통일되어야 함. 
   - 스크래핑(Scraping: 남의 웹 화면을 로봇이 강제로 긁어가는 비정상적 기술)은 보안상 전면 금지됨. 
   - 반드시 정부가 규정한 JSON/RESTful 기반의 '표준 API' 규격에 맞춰 시스템 간 상호 연동성(Interoperability)을 확보해야 함.
2. **강력한 인증 및 인가 체계 (OAuth 2.0 / OIDC)**
   - 내 데이터를 A은행에서 토스(Toss)로 넘길 때, A은행은 "데이터를 요청하는 토스가 진짜 토스가 맞는지(Client Authentication)", 그리고 "데이터를 넘기라고 허락한 사람이 진짜 고객 본인이 맞는지(User Authorization)"를 다중 인증(MFA)과 OAuth 2.0 프로토콜을 통해 검증(Access Token 발급)해야 함.
3. **PDS (Personal Data Store, 개인정보 관리 전문기관)**
   - 개인이 자신의 데이터를 다운로드받아 안전하게 보관하고, 여러 기업에 전송 내역(영수증)을 통합 관리/통제할 수 있는 일종의 '데이터 지갑(Data Wallet) 및 허브(Hub)' 인프라. 전 산업 마이데이터의 관제탑 역할을 수행.

### Ⅲ. 전송 요구의 대상 범위 (Data Scope)
무엇을 전송 요구할 수 있고, 무엇은 안 되는가?
- **포함 대상**: 컴퓨터 등 정보처리장치로 처리된 정보(DB 데이터), 고객의 활동으로 인해 생성된 팩트 데이터(결제 내역, 통화 기록, 심박수 등).
- **제외 대상 (기업 방어권)**: 
  - 기업이 상당한 시간/비용/노력을 들여 팩트 데이터를 가공하여 만들어낸 **독자적인 분석/추론 데이터(예: VIP 예측 점수, 딥러닝 기반 신용 평가 등)** 는 기업의 지적 재산(영업 비밀)이므로 전송 의무에서 면제됨.
  - 타인의 생명/신체/재산에 부당한 침해가 발생할 우려가 있는 데이터 (예: 나와 남이 섞여 있는 카카오톡 단톡방 대화 내용).

### Ⅳ. 마이데이터 환경의 신종 보안 위협 및 방어(Mitigation) 전략
데이터 유동성 폭발에 따른 섀도우 위협.
1. **API 취약점 타협 (BOLA / Broken Object Level Authorization)**
   - 위협: 해커가 토스의 마이데이터 API 쿼리 파라미터에서 `user_id=100`을 `user_id=101`로 살짝 조작하여 호출(BOLA). API 게이트웨이가 접근 제어를 소홀히 하면 타인(101번)의 금융 데이터를 통째로 탈취당함.
   - 방어: API 호출 시 토큰(Token)에 묶인 사용자 식별자와 쿼리의 대상 식별자가 일치하는지 백엔드에서 2중 체크(Validation) 강제, OWASP API Top 10 방어 체계 내재화.
2. **마이데이터 사업자의 보안 수준 차이 (Supply Chain Risk)**
   - 위협: 대형 은행(철통 보안)의 데이터가 신생 헬스케어 스타트업(허술한 보안)으로 전송된 후, 스타트업이 해킹당해 결국 은행 고객 데이터가 유출되는 '도미노 타협'.
   - 방어: 마이데이터 사업 허가(License) 심사 시 엄격한 ISMS-P 및 클라우드 보안 인증(CSAP) 요구. 지속적인 수탁자/제3자 연동 보안 점검(Third-party Audit).

### Ⅴ. 결론 및 실무적 판단 포인트
- 인프라 및 보안 아키텍트는 마이데이터 시대의 보안 패러다임을 '방화벽 치기'에서 **'안전한 통로(API) 열어주기'** 로 전환해야 합니다. 레거시(Legacy) 시스템의 모놀리식(Monolithic) DB 구조로는 수백만 건의 실시간 전송 요구 API 트래픽(TPS)을 감당할 수 없습니다. 따라서 마이데이터 전송 전용의 별도 **읽기 전용 복제 DB(Read-Replica)를 DMZ 구간에 분리 구축**하고, 그 위에 MSA(마이크로서비스) 기반의 API 게이트웨이와 OAuth 2.0 인가 서버(Auth Server)를 올려 백엔드 핵심망(Core)과 물리적으로 단절(Decoupling)시키는 인프라 현대화가 마이데이터 생존의 핵심 전략입니다.

### 💡 문제 유형별 목차 전환 포인트
- **[개인정보보호법 개정에 따른 '데이터 전송 요구권'의 의미와 산업 생태계 변화]**: Ⅰ과 Ⅲ번(전송 대상의 범위 및 면제 조항)을 중심으로 서술. GDPR 기반의 데이터 포터빌리티(Data Portability)가 수동적 열람권(기존)을 넘어 데이터 경제 창출의 능동적 도구로 어떻게 기능하는지 법적/비즈니스적 시각으로 증명.
- **[마이데이터(MyData) 인프라 구축을 위한 Open API 보안 아키텍처 설계]**: Ⅱ번(표준 API 및 OAuth 2.0 인프라)과 Ⅳ번(BOLA 등 API 특화 위협 및 방어)을 결합하여, 기업이 외부로 데이터를 안전하게 퍼주기 위해 갖춰야 할 실무적 망분리 및 API 게이트웨이 보안 설계 역량 과시.
