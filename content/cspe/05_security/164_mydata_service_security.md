## 1. 한눈에 이해하기 (Core Intuition)
- **정의**: 내 모든 통장 잔고, 진료 기록, 카드 내역(초민감 정보)이 '토스' 같은 하나의 마이데이터 앱으로 미친 듯이 쏟아져 들어올 때, **그 앱(마이데이터 플랫폼)이 해킹당하거나 직원이 몰래 데이터를 빼돌리지 못하도록 겹겹이 쳐두는 인증, 암호화, API 통제 등의 통합 보안 인프라**입니다.
- **필요성**: 마이데이터 이전에는 내 정보가 은행별로 뿔뿔이 흩어져 있어서 해커가 털기도 힘들었습니다(사일로 효과). 하지만 마이데이터 시대에는 내 인생의 모든 데이터가 **'단 하나의 앱(단일 장애점, SPOF)'** 으로 완벽하게 모입니다. 해커 입장에서는 이 앱 하나만 털면 국민 수천만 명의 전 재산과 병력을 통째로 가져갈 수 있는 역대급 뷔페(꿀통)가 열린 셈입니다. 이 거대한 꿀통을 지키는 국가급 방어벽이 필수적입니다.
- **핵심 직관**: **"모든 집 열쇠가 걸려 있는 아파트 경비실의 보안 강화"**. 
  - 과거 (개별 보관): 도둑이 A집 털고, B집 털고 일일이 다녀야 했음.
  - **마이데이터 보안**: 이제 모든 집의 열쇠와 현금(데이터)이 '경비실(마이데이터 사업자)' 한 곳에 모여 있습니다. 도둑이 경비실만 노릴 게 뻔하므로, 경비실 창문을 방탄유리로 바꾸고, 경비원(API 게이트웨이)은 방문객의 얼굴과 신분증(OAuth 토큰)을 2중으로 확인하며, 금고(DB)는 암호화(양방향/단방향)하여 철통같이 지키는 작업입니다.

## 2. 왜 중요한가? (Background & Value)
- **등장 배경**: 2022년 금융 마이데이터가 전면 시행되면서, 정부는 "보안이 허술한 벤처기업이나 스타트업은 절대 국민의 마이데이터를 다루지 마라!"라며 극도로 까다로운 보안 심사(라이선스)를 내걸었습니다. 특히 남의 웹사이트를 불법적으로 긁어오는 '스크래핑(Scraping)' 기술을 전면 금지하고, 100% 안전한 '표준 API' 통신만 허용하는 역사적인 룰이 적용되었습니다.
- **가치**: "안전한 데이터 경제의 전제 조건". 마이데이터 앱에서 한 번이라도 대규모 해킹이 터지면, 국민들의 신뢰가 붕괴하여 수조 원짜리 국가 데이터 경제 생태계 전체가 하루아침에 셧다운됩니다. 마이데이터 보안은 단일 기업의 방어를 넘어 국가 인프라의 신뢰를 담보하는 대들보입니다.

## 3. 어떻게 작동하는가? (Mechanism)
정보 제공자(은행) $\rightarrow$ 마이데이터 사업자(토스) $\rightarrow$ 정보 주체(고객)를 잇는 3각 보안 체계.

1. **표준 API 및 스크래핑 금지 (Network Security)**
   - **과거**: 토스 로봇이 내 ID/PW를 들고 국민은행 홈페이지에 몰래 접속해 화면을 긁어옴(스크래핑). 해킹 위험 100%.
   - **현재**: 무조건 금융보안원이 지정한 **'TLS(HTTPS) 기반의 암호화된 표준 API'** 로만 데이터를 주고받아야 함. 전송 구간의 스니핑(훔쳐보기) 완벽 차단.
2. **강력한 사용자 인증 체계 (Identity & Authorization)**
   - 토스가 국민은행에 "홍길동 데이터 줘!"라고 할 때, 국민은행은 그냥 주지 않습니다.
   - 반드시 **'통합 인증'** 또는 **'개별 인증(다중 인증, MFA)'** 을 거쳐, 홍길동 본인이 내 핸드폰(기기 인증)으로 지문/얼굴(생체 인증)을 찍어 **"토스한테 내 데이터 줘도 돼(동의)"라는 접근 토큰(OAuth 2.0 Access Token)** 을 발급받아야만 API가 열립니다.
3. **앱/서버 내부 방어 (Data Rest Security)**
   - 마이데이터 사업자(토스) 서버 안에서는 철통같은 방어가 필요합니다.
   - **DB 암호화**: 긁어온 주민번호는 복호화가 안 되게 뭉개고(단방향), 카드번호는 강력한 키로 잠금(양방향).
   - **망분리**: 고객 데이터가 있는 서버(내부망)와 직원들이 인터넷 하는 PC(외부망)를 물리적/논리적으로 싹둑 끊어버림(망분리 의무).
   - **앱 위변조 방지**: 해커가 가짜 토스 앱을 배포하는 걸 막기 위해 앱(APK/IPA)에 백신과 난독화 기술(Obfuscation) 강제 탑재.

## 4. 실전 활용 및 예시 (Real-world Application)
- **구체적 사례 (네이버페이 타인 정보 노출 사고)**: 
  - 마이데이터 서비스 초창기에 네이버페이(마이데이터 사업자)에서 황당한 버그가 터졌습니다. 사용자가 "내 자산 불러오기"를 눌렀는데, 내 잔고가 아니라 **생판 모르는 남의 계좌 번호와 카드 결제 내역 100여 건이 내 화면에 떠버린 것**입니다. 해킹이 아니라 트래픽 폭주 상황에서 API 캐시(Cache) 서버가 유저 세션(ID) 매핑을 헷갈려서 남의 토큰 정보를 뿌려버린 전형적인 'BOLA(인가 오류)' 취약점 사고였습니다. 마이데이터 환경에서 API 보안 설계가 얼마나 중요한지 보여준 아찔한 사례입니다.
- **주의점 및 흔한 오해**: 
  - "마이데이터 회사들은 어차피 정부가 다 관리하니까 보안 수준이 똑같겠죠?" $\rightarrow$ 아닙니다. 클라우드 인프라(AWS 등) 위에 올라간 마이데이터 시스템은 설정 하나(S3 버킷 퍼블릭 오픈 등)만 삐끗해도 대형 사고가 터집니다. 그래서 정부는 마이데이터 허가를 받으려면 매년 무조건 **'금융보안원 취약점 점검'** 과 **'개인정보보호 배상책임보험(최소 10억~50억 이상 가입)'** 을 의무화하고 있습니다.

## 5. 핵심 비교 및 연결 개념 (Relation)
| 구분 | 과거 (스크래핑 방식) | 마이데이터 (표준 API 방식) |
|---|---|---|
| **통신 주체** | 화면을 긁어가는 로봇 (웹 크롤러) | **규격화된 컴퓨터 간 통신 (API/JSON)** |
| **인증 정보 보관**| 내 은행 ID/PW를 토스 서버에 저장 (극도 위험) | **토스에 PW 안 줌 (토큰(Token) 발급 방식)** |
| **데이터 범위** | 화면에 보이는 모든 텍스트 무차별 수집 | **고객이 허락한 항목만 정밀하게 전송** |

# ✍️ 단답형 / 서술형 시험장 출격 준비

### Ⅰ. 핵심 인사이트
- **본질**: 정보 주체의 전송 요구권에 의해 다수의 정보 제공자(금융/공공/의료)로부터 막대한 민감 정보가 단일 마이데이터 플랫폼(수집자)으로 집중(Aggregation)됨에 따라 발생하는 단일 장애점(SPOF) 및 대규모 유출 리스크를 원천 차단하기 위해, **① 화면 스크래핑(Scraping) 전면 금지 및 표준 API 의무화, ② OAuth 2.0 기반의 강력한 토큰 인가 체계, ③ 망분리 및 금융권 수준의 컴플라이언스(ISMS-P, 취약점 점검)를 강제하는 엔드-투-엔드(End-to-End) 초융합 보안 아키텍처.**
- **가치**: 마이데이터 산업은 보안(Security)이 서비스의 보조재가 아니라 '진입 장벽(License)' 그 자체로 작용하는 대표적 규제 산업임. 고객이 ID/PW를 핀테크 업체에 넘겨주던 레거시 크레덴셜 셰어링(Credential Sharing) 관행을 종식시키고, 제로 트러스트(ZTA) 철학에 기반한 위임 인가(Delegated Authorization) 생태계를 대한민국 IT 전반에 강제 이식한 거버넌스의 결정체입니다.
- **판단 포인트**: IT 아키텍트는 마이데이터 보안이 단순히 '방화벽과 DB 암호화'에 그치지 않음을 깨달아야 합니다. 핵심 챌린지는 **"초당 수만 건의 API 콜(API Gateway TPS)이 쏟아지는 환경에서, 각 쿼리에 묻어있는 Access Token이 진짜 정보 주체의 것이 맞는지(BOLA 취약점 차단), 그리고 고객이 어제 철회한 동의 범위(Scope)를 실시간으로 반영하여 응답을 필터링하고 있는지"** 를 제어하는 동적 접근 제어(Dynamic Access Control) 파이프라인의 설계 역량에 달려 있습니다.

### Ⅱ. 마이데이터 보안 아키텍처 4대 영역 (Threat Modeling)
앱 단말부터 백엔드 망분리까지 아우르는 국방 수준의 방어선.
1. **API 게이트웨이 및 네트워크 구간 보안 (Transit Security)**
   - **표준 API 강제**: 스크래핑 전면 금지. 모든 트래픽은 mTLS(상호 TLS)를 적용하여 클라이언트(핀테크)와 서버(은행) 양방향 인증을 수행, 중간자 공격(MITM) 및 스니핑을 원천 차단.
   - **API 방어 (OWASP API Top 10)**: BOLA(수직/수평적 권한 상승) 방어를 위해 JWT 토큰 내의 `user_id`와 요청 페이로드의 `account_id` 일치 여부를 매 트랜잭션마다 하드 체크. 과도한 호출(DDoS/Scraping 시도)을 막는 엄격한 Rate Limiting 적용.
2. **인증 및 인가 파이프라인 (Authentication & Authorization)**
   - **OAuth 2.0 및 OIDC(OpenID Connect)**: 마이데이터 사업자에게 절대 평문 패스워드를 주지 않음. 정보 제공자(은행)의 인증 창을 띄워 고객이 직접 본인인증(FIDO, PKI 등)을 한 뒤, 단기 소멸성 'Access Token'만 사업자에게 발급하여 스코프(Scope: 예-계좌조회 권한만)를 극도로 통제.
3. **서비스 백엔드 데이터 보안 (Data at Rest)**
   - **DB 암호화**: 수집된 마이데이터(계좌, 병력 등 민감 정보)는 ARIA, AES-256 등 국정원 권고 알고리즘으로 양방향 암호화. 비밀번호 등 크레덴셜은 SHA-256 이상 일방향 해시(Salt 첨가).
   - **파기 및 잊힐 권리**: 정보 주체가 전송 요구를 철회하거나 회원 탈퇴 시, 백업 DB 및 캐시(Redis) 인스턴스에 남은 찌꺼기 데이터까지 완전 영구 삭제(Hard Delete)하는 스케줄링 배치(Batch) 필수 가동.
4. **인프라 망분리 및 클라우드 보안 (Infrastructure)**
   - **물리적/논리적 망분리**: 인터넷이 연결된 외부망(웹 서버)과 고객 데이터가 저장된 내부망(WAS/DB)을 방화벽으로 철저히 단절. 
   - 개발자/운영자의 내부망 접근 시 VDI(데스크톱 가상화) 등 논리적 망분리와 2-Factor 인증(MFA) 강제 적용.

### Ⅲ. 신종 보안 쟁점: 클라우드 기반 마이데이터의 취약성
스타트업들의 퍼블릭 클라우드(AWS, Azure) 사용 증가에 따른 설정 오류(Misconfiguration) 위협.
- **CSPM (클라우드 보안 형상 관리) 부재**: 마이데이터 수집 람다(Lambda) 함수의 IAM 권한이 과도하게 뚫려 있거나, S3 버킷 리소스가 퍼블릭으로 열려 수백만 건의 JSON 데이터가 인터넷에 크롤링되는 치명적 사고 리스크.
- 방어 대책: IaC(Terraform) 배포 전 보안 검수 파이프라인(DevSecOps) 내재화 및 매년 금융보안원이 주관하는 클라우드 사업자 정기 취약점 평가(Pen-testing) 수검 의무.

### Ⅳ. 컴플라이언스 및 거버넌스 체계 (Compliance)
단순 기술을 넘어선 생존형 컴플라이언스 3종 세트.
1. **ISMS-P 인증 의무 취득**: 정보보호 및 개인정보보호 관리체계 인증을 받지 않으면 본허가 심사 통과 불가.
2. **기능 적합성 심사 및 보안 취약점 점검**: API 연동 과정의 규격 적합성을 테스트하고, 화이트해커를 동원해 앱(APK/IPA 위변조 방지) 및 서버를 털어보는 사전 관문.
3. **손해배상 책임보험 (사후 대책)**: 유출 사고 시 고객 보상을 위한 최소 수십억 원 한도의 보험/공제 가입 의무화.

### Ⅴ. 결론 및 실무적 판단 포인트
- CISO와 핀테크 아키텍트는 마이데이터 시스템 오픈을 "일회성 프로젝트"로 치부해선 안 됩니다. 사업 인가를 받는 순간, 기업은 **매일 금융보안원의 관제를 받고 매년 외부 감사를 견뎌야 하는 '유사 금융 기관' 급의 인프라 체력**을 요구받게 됩니다. 트래픽 폭증에 대비하는 MSA(마이크로서비스 아키텍처) 기반의 API 게이트웨이 유연성을 확보하면서도, 그 수많은 마이크로서비스 간 통신에 **제로 트러스트 기반의 상호 인증(mTLS)과 세밀한 토큰(Token) 인가 로직**을 톱니바퀴처럼 물려놓는 것만이 E-DoS(비용 고갈)와 BOLA(인가 우회)를 방어하는 유일한 길입니다.

### 💡 문제 유형별 목차 전환 포인트
- **[마이데이터 생태계의 보안 취약점 및 정보 보호 아키텍처 (OWASP API Top 10 연계)]**: Ⅰ과 Ⅱ번(망분리, API 보안, OAuth 체계)을 메인으로 다루며, 레거시 스크래핑 방식의 종말과 표준 API가 가져온 인프라적 패러다임 시프트 증명.
- **[안전한 클라우드 네이티브 기반 핀테크(Fintech) 서비스 구축 및 데브섹옵스(DevSecOps) 전략]**: Ⅲ번(클라우드 설정 오류 위협)을 비판적으로 짚은 후, Ⅳ번의 컴플라이언스 3종 세트(ISMS-P 등)를 통해 "기술적 아키텍처를 넘어선 엔터프라이즈 거버넌스" 중심의 해법 제시.
