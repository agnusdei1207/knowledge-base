# 📖 【암기용】 개념 완전 이해

> 목적: 마이데이터 서비스 보안을 처음 봐도 완벽히 이해하게 만든다. 시험 답안 양식이 아니라, 이해를 위한 친절한 설명이다.

## 한눈에
- **개요**: 정보주체 전송요구권 기반 데이터 이동을 인증·인가·API·감사로 통제하는 보안체계
- **왜 필요한가**: 마이데이터는 은행·카드·보험·공공 등 여러 기관의 개인신용정보·개인정보를 한 서비스로 모은다. 전송요구, 본인인증, API 전송, 저장, 철회가 틀어지면 대규모 정보유출과 부정조회로 이어짐.
- **핵심 직관**: 금고 여러 개의 열쇠를 한 앱에서 관리하는 구조라서, 열쇠 발급·사용·회수 기록을 모두 남겨야 함.

## 깊이 이해
- **배경·문제의식**: 금융 마이데이터는 스크래핑 대신 표준 API와 본인 직접인증을 사용하도록 설계됐다. 2026년에는 개인정보 전송요구권 제도가 전 분야로 확대되어 금융 외 영역도 동일한 권리·전송·보안 기준이 필요함.
- **작동 원리**: 이용자는 정보제공자, 수신자, 항목, 기간을 선택해 전송을 요구한다. 인증 API로 본인을 확인하고, 정보제공 API로 데이터를 전송하며, 수신자는 이용내역·철회·삭제·접근통제를 관리함.
- **비유**: 택배 전송 요청서와 같다. 누가, 어떤 물건을, 어느 택배사로, 언제까지 보낼지 지정하고 배송 추적과 반송 권한을 남김.
- **구체 예시**: 사용자가 카드 이용내역 12개월을 자산관리 앱에 전송 요구하면 인증 API로 본인확인, 정보제공 API로 TLS 기반 전송, 앱은 접근토큰 만료·재동의·삭제 요청을 처리함.
- **흔한 오해·주의점**: 마이데이터 보안은 API 암호화만이 아니다. 동의 UX, 전송범위 최소화, 토큰 권한, 이상조회 탐지, 탈퇴 시 완전삭제가 함께 필요함.

## 연결 개념
- 개인정보 전송요구권 - 정보주체가 본인정보 전송을 요구하는 권리
- OAuth 2.0/OIDC - 위임 인증·인가와 토큰 관리
- API 보안 - mTLS, JWT, Rate Limit, FAPI 기반 통제

## 암기 포인트
- 전송요구는 수신자·항목·기간·목적을 정보주체가 지정하는 구조임.
- 스크래핑 대비 표준 API의 차이는 계정정보 위탁 제거와 scope 통제임.
- 답안은 동의·토큰·전송·철회·삭제 로그까지 이어서 써야 함.

# 📝 【답안용】 시험 답안 템플릿

> 목적: 시험장에서 25분에 그대로 쓰는 답안 양식. 작성방식(추상표현 금지·수치·도식·문제유형 전환)을 엄격히 지킨다.
> 핵심: 마이데이터 보안은 전송요구권, 표준 API, 본인인증, 동의·철회, 삭제·감사 지표를 하나의 흐름으로 제시해야 한다.

## 핵심 인사이트 (3줄 요약)

> 1. **본질**: 마이데이터 서비스 보안은 정보주체의 전송요구를 표준 API로 처리하면서 인증·인가·전송·저장·철회를 통제하는 보안 아키텍처이다.
> 2. **가치**: 스크래핑의 계정정보 노출을 줄이고, 항목·기간·수신자 단위 전송과 로그 기반 감사로 정보주권을 구현함.
> 3. **판단 포인트**: API 규격, 본인인증, 토큰 범위, 전송내역 기록, 탈퇴·철회 시 삭제, 이상행위 탐지를 반드시 포함해야 함.

## 출제 의도 및 답안 포인트

| 출제 의도 | 반드시 짚을 핵심 | 감점 회피 포인트 |
|:---|:---|:---|
| 제도·기술 결합 이해 | 개인정보 전송요구권, 금융 표준 API, 인증·지원·정보제공 API | 단순 데이터 중개 서비스로 설명 |
| API 보안 설계 역량 | mTLS, OAuth 2.0/OIDC, JWT, scope, nonce, rate limit | TLS만 쓰고 동의·토큰 범위 누락 |
| 운영 통제 판단 | 전송내역 기록, 철회, 삭제, 금융보안원 점검, 이상조회 탐지 | 가입 이후 사후통제 미작성 |
> 요약: 마이데이터 보안 답안은 권리행사 절차와 API 보안, 운영감사를 연결해야 함.

## Ⅰ. 개요 및 필요성

- 개요: 전송요구권 보호체계
- 배경: 이용자 동의로 여러 기관의 개인정보가 수신기관에 집중되므로 인증·인가 오류와 과다수집이 침해 사고로 연결될 수 있다.
- 필요성: 표준 API, 토큰 scope, 감사로그, 철회·삭제 절차를 운영 기준으로 두어 수신기관의 책임 범위를 검증해야 한다.

---

## Ⅱ. 구조 및 구성요소

```text
정보주체 -> 마이데이터 앱 -> 인증 API -> 정보제공자
         +-> 지원 API/종합포털 -> 정보제공 API -> 수신/저장/삭제
```

| 구성요소 | 역할 | 특이사항 |
|:---|:---|:---|
| 정보주체 | 전송요구·동의·철회 주체 | 대상정보, 수신자, 기간 선택 |
| 마이데이터 사업자 | 수신·분석·서비스 제공 | 접근권한, 저장암호화, 삭제 의무 |
| 정보제공자 | 보유정보를 API로 전송 | 은행, 카드, 보험, 공공기관 |
| 인증 API | 본인확인·전송요구 인증 | 통합인증, OIDC, nonce |
| 정보제공 API | 개인신용정보·개인정보 전송 | 업권별 API, scope, rate limit |
> 요약: 마이데이터 구조는 정보주체 요구를 인증 API로 확인하고 정보제공 API로 제한된 데이터를 전송하는 구조임.

---

## Ⅲ. 동작원리 및 흐름도

```text
전송요구 선택 -> 본인인증 -> 동의/권한 발급
-> API 호출/전송 -> 수신저장/이용 -> 내역조회/철회/삭제
```

| 단계 | 처리 내용 | 검증 기준 |
|:---:|:---|:---|
| 1 | 수신자·항목·기간·목적 선택 | 최소수집, 쉬운 용어, 철회 가능 |
| 2 | 본인인증과 전송요구 확인 | OIDC, MFA, nonce, 인증로그 |
| 3 | 토큰 발급·API 호출 | OAuth scope, 만료시간, mTLS |
| 4 | 데이터 전송·저장 | TLS 1.2 이상, AES-256, DB 접근통제 |
| 5 | 이용내역·철회·삭제·감사 | 전송내역 기록, 삭제증적, 이상조회 탐지 |
> 요약: 마이데이터는 동의에서 삭제까지 토큰 범위와 감사로그로 전송권 행사를 검증함.

## Ⅳ. 특징

| 구분 | 스크래핑 방식 | 표준 API 마이데이터 | 수치·통제 포인트 |
|:---|:---|:---|:---|
| 인증 | 이용자 계정정보 위탁 | 본인 직접인증·전송요구 | 인증 API, MFA |
| 권한 | 사이트 전체 접근 가능 | 항목·기간·목적별 scope | 최소권한 토큰 |
| 전송 | 화면 파싱·오류 가능 | 규격화된 정보제공 API | 업권별 표준 API |
| 운영감사 | 조회 행위 추적 곤란 | 전송내역·철회·삭제 로그 | 로그 1년 이상 보관 권장 |
> 요약: 표준 API 방식은 계정정보 위탁을 제거하고 scope·로그·철회로 데이터 이동을 통제함.

## Ⅴ. 심화 비교 및 적용 판단

| 비교 축 | 기존/대안 | 본 키워드 | 선택 기준 |
|:---|:---|:---|:---|
| 데이터 수집 | 스크래핑 | 표준 API 기반 전송 | 전송요구권과 항목별 권한 필요 시 |
| 인증·인가 | ID/PW 저장 | OIDC, OAuth 2.0, mTLS | 계정정보 보관 금지와 토큰 추적성 |
| 운영 리스크 | 과다조회 탐지 제한 | 이상조회, 전송내역, 철회·삭제 | 규제점검과 고객권리 대응 |
> 요약: 금융·공공 개인정보 이동은 스크래핑보다 표준 API와 토큰 기반 위임권한 구조를 선택해야 함.

| 리스크 | 원인 | 대응 방안 | 확인 지표 |
|:---|:---|:---|:---|
| 과다수집 | scope 설계가 포괄적 | 항목·기간별 scope, 동의 화면 분리 | 불필요 항목 0건 |
| 토큰 탈취 | 모바일 앱·API 키 노출 | mTLS, PKCE, 토큰 만료 90일 이하 | 비정상 API 호출 탐지율 |
| 철회 미반영 | 수신기관 삭제 지연 | 철회 이벤트, 삭제 배치, 삭제증명 | 철회 후 삭제 SLA 24시간 |
> 요약: 핵심 리스크는 과다수집·토큰탈취·철회 미반영이며 scope와 삭제 SLA로 통제함.

| 점검 항목 | 목표 기준 | 측정 방법 |
|:---|:---|:---|
| 인증·인가 | MFA 적용, scope 최소권한 100% | 인증로그, 토큰 클레임 점검 |
| API 보안 | TLS 1.2 이상, mTLS, rate limit | API Gateway 정책, 침투테스트 |
| 권리보장 | 철회·삭제 SLA 24시간 이내 | 고객 요청대장, 삭제증적, 감사로그 |
> 요약: 마이데이터 보안 수준은 인증·인가, API 보안, 권리보장 지표로 판단함.

## Ⅵ. 실무 적용 및 결론

**적용 방안 3개 (필수 - 단계별 또는 항목별):**
1. 설계 단계: 인증 API, 지원 API, 정보제공 API를 분리하고 OAuth 2.0/OIDC, PKCE, mTLS, JWT audience·scope 검증을 API Gateway에 적용
2. 운영 단계: 전송요구 화면에 수신자·항목·기간·목적을 분리 표시하고 토큰 만료 90일 이하, rate limit, 이상조회 룰을 설정
3. 감사 단계: 전송내역·접근로그·철회·삭제증적을 1년 이상 보관하고 탈퇴 시 저장정보 완전삭제 및 금융보안원 점검 항목 대응

**결론 (2줄):**
- 기술사 판단: 마이데이터는 표준 API만으로 완성되지 않으며, 동의·토큰·전송·저장·삭제 전 구간을 감사 가능한 권리보장 체계로 설계해야 함
- 향후 방향: 전 분야 전송요구권 확대로 금융권 FAPI 수준 통제를 공공·의료·통신 API 보안 기준과 연계해야 함
