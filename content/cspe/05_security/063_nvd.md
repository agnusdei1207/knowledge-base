# 📖 【암기용】 개념 완전 이해

> 목적: NVD를 처음 봐도 완벽히 이해하게 만든다. 시험 답안 양식이 아니라, 이해를 위한 친절한 설명이다.

## 한눈에
- **개요**: CVE 취약점에 점수, 제품, 약점 분류를 붙인 공개 데이터베이스
- **왜 필요한가**: CVE ID만으로는 어떤 제품과 버전이 영향을 받는지, 점수가 얼마인지, 어떤 유형의 약점인지 알기 어렵다. NVD는 CPE, CWE, CVSS, JSON feed로 자동화 입력을 제공한다.
- **핵심 직관**: CVE가 사건 번호라면 NVD는 사건 번호에 피해 물품, 원인 유형, 위험 점수, 참고 문서를 붙인 사건 대장임.

## 깊이 이해
- **배경·문제의식**: 취약점 관리는 사람이 웹 페이지를 읽어 처리할 수 없는 규모로 증가했다. NVD는 구조화된 feed와 API를 제공해 스캐너, SCA, SIEM, ITSM이 같은 데이터를 사용하게 한다.
- **작동 원리**: CVE가 공개되면 NVD는 분석을 통해 CPE 제품 매칭, CWE 약점 분류, CVSS vector, reference를 추가한다. 조직은 이 데이터를 SBOM, CMDB, 패치 대장과 결합한다.
- **비유**: 도서 ISBN만 있으면 책을 식별할 수 있지만 도서관 운영에는 저자, 분류, 위치, 대출 상태가 필요하다. NVD는 취약점 운영에 필요한 부가 메타데이터를 제공한다.
- **구체 예시**: `CVE-2021-44228`은 NVD에서 CVSS 10.0, 관련 CPE, CWE, reference를 확인하고, 조직은 Log4j SBOM 매칭과 인터넷 노출 서비스 패치를 우선 수행함.
- **흔한 오해·주의점**: NVD는 자동 조치 시스템이 아니다. CPE 매칭 오류, delayed analysis, vendor backport, 환경별 영향 차이를 내부 검증으로 보완해야 함.

## 연결 개념
- CVE/CVSS - NVD가 확장해 제공하는 식별자와 점수
- CPE/CWE - 영향 제품과 약점 유형 분류 체계
- SBOM/VEX - 제품 구성요소와 실제 영향 여부 판단 보완

# 📝 【답안용】 시험 답안 템플릿

> 목적: 시험장에서 25분에 그대로 쓰는 답안 양식. 작성방식(추상표현 금지·수치·도식·문제유형 전환)을 엄격히 지킨다.
> 핵심: NVD 답안은 DB 소개가 아니라 CPE/CWE/CVSS/JSON feed를 자산·패치·재검증 자동화로 연결해야 함.

## 핵심 인사이트 (3줄 요약)

> 1. **본질**: NVD는 CVE에 CPE, CWE, CVSS, reference를 결합해 취약점 관리를 자동화할 수 있는 공개 취약점 DB임.
> 2. **가치**: 스캐너, SCA, SBOM, ITSM이 같은 feed를 사용해 영향 자산 식별과 패치 SLA를 표준화함.
> 3. **판단 포인트**: NVD JSON feed, CPE 매칭, CVSS 보정, KEV/EPSS 보완, delayed analysis 리스크를 함께 써야 함.

## 출제 의도 및 답안 포인트

| 출제 의도 | 반드시 짚을 핵심 | 감점 회피 포인트 |
|:---|:---|:---|
| NVD 구성 데이터 이해 확인 | CVE, CPE, CWE, CVSS, reference, JSON feed/API | CVE 목록 사이트로만 설명 |
| 취약점 운영 자동화 판단 확인 | SBOM/CMDB 매핑, 스캐너 플러그인, ITSM 티켓 | 데이터 조회와 실제 조치 연결 누락 |
| 한계와 보완책 확인 | CPE 부정확, 분석 지연, KEV/EPSS·벤더 권고 보완 | NVD 점수를 최종 위험으로 단정 |

> 요약: NVD 문제는 공개 취약점 메타데이터를 조직 자산과 조치 프로세스로 변환하는 능력을 요구함.

## Ⅰ. 개요 및 필요성

- 개요: 구조화된 취약점 DB
- 배경: CVE ID만으로는 영향 제품, 약점 유형, 심각도, 참고자료가 부족해 자산별 조치 대상을 자동 판별하기 어려움.
- 필요성: NVD JSON 2.0 feed의 CPE, CWE, CVSS, reference를 CMDB·SCA와 매핑해 취약점 식별부터 패치 재검증까지 운영 기준으로 삼아야 함.

---

## Ⅱ. 구조 및 구성요소

```text
CVE Record -> NVD Analysis -> CPE/CWE/CVSS -> JSON Feed/API -> Scanner/ITSM
  / reference, vendor advisory
  / SBOM, CMDB, patch catalog
```

| 구성요소 | 역할 | 특이사항 |
|:---|:---|:---|
| CVE Record | 취약점 식별자와 기본 설명 제공 | CNA 공개 정보 기반 |
| CPE Match | 영향 제품과 버전 범위 표현 | 제품명 정규화 오류 검증 필요 |
| CWE Mapping | 취약점 원인 유형 분류 | secure coding 개선 입력 |
| CVSS Vector | 심각도와 공격 조건 점수화 | 조직 환경 점수 보정 필요 |
| JSON Feed/API | 자동 수집과 도구 연동 제공 | 동기화 주기와 rate limit 관리 |

> 요약: NVD는 CVE를 CPE, CWE, CVSS, feed로 확장해 자동화 가능한 취약점 운영 데이터를 제공함.

---

## Ⅲ. 동작원리 및 흐름도

```text
NVD feed 수집 -> CVE/CPE 파싱 -> SBOM/CMDB 매칭
  / 제품명, 버전, 패키지
CVSS/KEV/EPSS 보정 -> 티켓 발행 -> 패치/예외 -> 재스캔
```

| 단계 | 처리 내용 | 검증 기준 |
|:---:|:---|:---|
| 1 | NVD JSON feed/API를 주기 수집 | feed lag 24시간 이하 |
| 2 | CVE, CPE, CWE, CVSS vector를 파싱 | 파싱 오류 1% 이하 |
| 3 | CPE와 SBOM/CMDB 자산을 매칭 | 영향 자산 매칭률 95% 이상 |
| 4 | KEV, EPSS, 인터넷 노출, 자산 등급으로 보정 | critical SLA 7일 |
| 5 | 패치, 예외 승인, 재검증 결과를 ITSM에 기록 | retest pass 95% |

> 요약: NVD는 feed 수집 후 자산 매핑과 위험 보정을 거쳐 조치 티켓과 재검증으로 이어질 때 운영 가치가 있음.

## Ⅳ. 특징

| 구분 | CVE 원본 | NVD | 수치·판단 포인트 |
|:---|:---|:---|:---|
| 데이터 범위 | ID와 설명 중심 | CPE, CWE, CVSS, reference 포함 | 자동 매핑 가능 |
| 제공 방식 | CNA·벤더 공개 | 웹, JSON feed, API | feed lag 24시간 목표 |
| 활용 | 식별·공지 | 스캔, SCA, ITSM, KPI | SLA 7/30/90일 |
| 한계 | 메타데이터 부족 | 분석 지연, CPE 오매칭 | 벤더·KEV 보완 |

> 요약: NVD는 CVE 운영을 자동화하지만 CPE 매칭과 분석 지연 때문에 내부 자산 검증이 필요함.

## Ⅴ. 심화 비교 및 적용 판단

| 구분 | 기존/대안 | 본 키워드 | 선택 기준 |
|:---|:---|:---|:---|
| 구조 | 벤더 권고 수동 확인 | NVD feed 기반 통합 수집 | 다수 벤더·오픈소스 사용 조직 |
| 비용/성과 | 수작업 영향 분석 | CPE/SBOM 자동 매칭 | 일일 CVE 100건 이상 처리 |
| 운영/위험 | 점검자 경험 의존 | feed, API, ITSM workflow | 데이터 품질과 지연 모니터링 필요 |

> 요약: NVD는 취약점 데이터 규모가 클 때 자동화 기준으로 적합하나 최종 판단은 조직 자산 맥락으로 보정해야 함.

| 리스크 | 원인 | 대응 방안 | 확인 지표 |
|:---|:---|:---|:---|
| CPE 오매칭 | 제품명·버전 표기 차이 | SBOM purl, vendor advisory, 패키지 증거 대조 | false match 5% 이하 |
| 분석 지연 | NVD enrichment 지연 | 벤더 RSS, KEV, CTI feed 병행 | critical feed lag 12시간 이하 |
| 우선순위 왜곡 | CVSS 단독 사용 | EPSS, KEV, 자산 등급, 인터넷 노출 결합 | KEV 미조치 0건 |

> 요약: NVD 운영 리스크는 데이터 지연과 매칭 오류이며, 다중 feed와 내부 증거 대조로 줄여야 함.

| 점검 항목 | 목표 기준 | 측정 방법 |
|:---|:---|:---|
| 수집 품질 | feed 동기화 24시간 이하 | API 로그, 수집 배치 모니터링 |
| 매칭 품질 | 영향 자산 매칭률 95% | SBOM, CMDB, 스캐너 비교 |
| 조치 품질 | critical 7일, high 30일 SLA | ITSM, 재스캔, 예외 대장 |

> 요약: NVD 활용 성과는 feed 수집, 자산 매칭, SLA 조치가 모두 지표로 관리될 때 확인됨.

## Ⅵ. 실무 적용 및 결론

**적용 방안 3개 (필수 — 단계별 또는 항목별):**
1. 데이터 파이프라인: NVD JSON feed/API를 24시간 주기로 수집하고 CVE, CPE, CWE, CVSS vector를 취약점 데이터 lake에 적재함.
2. 자산 매핑: CPE를 SBOM purl, OS 패키지명, CMDB 제품명과 교차 매핑하고 false match는 vendor advisory로 검증함.
3. 조치 연계: NVD 점수에 KEV, EPSS, 인터넷 노출, 자산 등급을 결합해 ITSM 티켓과 재스캔 종료 조건을 자동 생성함.

**결론 (2줄):**
- 기술사 판단: NVD는 취약점 운영의 기준 데이터로 쓰되, CPE 오매칭과 분석 지연은 SBOM·벤더 권고·KEV로 보완해야 함.
- 향후 방향: NVD feed, SBOM, VEX, EPSS를 결합해 "영향 있음" 취약점만 조치하는 risk-based vulnerability management로 발전해야 함.
