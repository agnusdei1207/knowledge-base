## 미리 알고가기

- 비밀은 비밀번호, API 키, 인증서, 토큰처럼 외부 노출 시 즉시 위험해지는 인증 정보를 말함
- 동적 비밀은 필요할 때 잠시 발급했다가 만료되면 자동 폐기하는 자격증명임
- 회전은 같은 비밀을 오래 쓰지 않도록 주기적으로 새 값으로 바꾸는 운영 절차임

## Ⅰ. 개요

- **정의/개념**: 비밀 관리는 애플리케이션과 운영자가 쓰는 인증 정보를 중앙에서 저장, 발급, 회전, 폐기, 감사하는 보안 운영 체계이며 Vault와 AWS Secrets Manager가 대표 수단임
- **배경/필요성**: 비밀이 소스코드, 이미지, 환경변수, 로그에 남으면 유출 뒤 피해가 빠르게 커지므로 저장 위치와 사용 수명을 모두 통제할 필요가 있음

## Ⅱ. 특징

- 하드코딩 대신 실행 시점 발급으로 비밀 노출 면적을 줄임
- 접근 주체와 조회 이력을 남겨 사후 추적이 쉬움
- 자동 회전과 짧은 수명 정책으로 장기 유출 위험을 줄임
- 중앙화만 하고 권한 분리가 약하면 단일 고위험 지점이 되므로 접근 정책이 중요함

## Ⅲ. 종류 및 비교

| 판단 기준 | HashiCorp Vault | AWS Secrets Manager |
|:---|:---|:---|
| 강점 | 동적 비밀과 다양한 백엔드 연동이 강함 | AWS 서비스 연동과 운영 편의성이 좋음 |
| 권한 모델 | 정책과 인증 방식 조합이 유연함 | IAM 중심으로 일관되게 관리함 |
| 운영 방식 | 직접 운영과 고가용성 설계가 필요함 | 관리형 서비스로 운영 부담이 낮음 |
| 적합 환경 | 멀티 클라우드와 복잡한 비밀 발급 | AWS 중심 서비스 환경 |

## Ⅳ. 구성요소 및 구조

| 구성요소 | 설명 |
|:---|:---|
| 인증 수단 | 애플리케이션이나 사용자가 어떤 신원으로 접속하는지 확인함 |
| 비밀 저장·발급 | 정적 비밀 저장과 동적 비밀 생성을 담당함 |
| 권한 정책 | 누가 어떤 비밀을 어떤 범위에서 읽고 갱신할지 정함 |
| 회전 엔진 | 만료 주기에 맞춰 값을 바꾸고 이전 값을 폐기함 |
| 감사 로그 | 조회, 발급, 실패, 갱신 이력을 남김 |

```text
애플리케이션 인증 -> 비밀 요청 -> 정책 확인 -> 비밀 발급/조회 -> 사용 후 회전·폐기 -> 감사 기록
```

## Ⅴ. 원리 및 절차 흐름도

```text
신원 확인 -> 권한 검사 -> 비밀 발급 또는 조회 -> 애플리케이션 사용 -> 만료·회전 -> 기록 보관
```

1. **신원 확인**: 애플리케이션이나 사용자의 접속 주체를 확인함
2. **권한 검사**: 요청한 비밀에 접근 가능한지 판단함
3. **비밀 발급**: 정적 비밀을 읽어 주거나 동적 비밀을 새로 만듦
4. **애플리케이션 사용**: 일정 시간 동안만 비밀을 사용함
5. **만료와 회전**: 수명이 끝나면 폐기하거나 새 값으로 바꿈

## Ⅵ. 실무 적용 및 유의점

1. 애플리케이션 비밀번호와 API 키는 코드와 이미지에 넣지 말고 실행 시점에 받아 쓰게 해야 하며 하드코딩 비밀 탐지 건수와 자동 회전 성공률로 확인함
2. 중앙 비밀 저장소 장애가 곧 서비스 장애가 되지 않게 캐시와 비상 절차를 준비하고 만료된 비밀 사용 건수와 비상 접근 승인 건수로 점검함

## Ⅶ. 결론

- 비밀 관리는 저장 위치만 바꾸는 일이 아니라 발급 수명과 접근 이력까지 통제하는 일이므로 중앙화와 자동 회전을 함께 설계해야 함
