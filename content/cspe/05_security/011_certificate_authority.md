# 📖 【암기용】 개념 완전 이해

## 한눈에
- **개요**: **CA는 신원을 검증한 뒤 CSR을 받아 X.509 인증서에 서명·발급하는 신뢰 앵커로, Root/Intermediate 계층과 DV·OV·EV 검증 등급으로 운영되는 발급 주체**임. PKI 신뢰 체계 전반은 (009 참조), 인증서 필드 구조는 (010 X.509 참조).
- **왜 필요한가**: 공개키를 누가 보증하느냐가 신뢰의 출발점임. CA는 신원을 확인하고 서명을 찍어 "이 공개키는 이 주체 것"을 보증하며, 이 서명 계보(체인)가 검증의 근거가 됨.
- **핵심 직관**: 여권 발급 관청과 같음. 서류(CSR)를 받아 본인 확인(신원 검증)을 하고, 관인(개인키 서명)을 찍어 발급하며, 최상위 발급권(Root)은 금고에 봉인해 둠.

## 핵심 용어 정리 (내부에 등장하는 것들)

답안에 등장하는 발급 주체·절차·검증 등급을 먼저 풀어 둠. 상위 핵심 키워드는 **신뢰 앵커(trust anchor)** 로, Root CA가 여기에 해당함.

| 용어/표기 | 의미 | 비유·예 |
|:---|:---|:---|
| Root CA | 자기서명 최상위 CA, 신뢰 저장소에 사전 등록 | 국가 발급 최상위 관청 |
| Intermediate CA | Root가 서명한 실제 발급용 하위 CA | 지역 발급소 |
| Trust Store | OS·브라우저가 신뢰하는 Root 목록 | 미리 인정된 관청 명단 |
| RA(등록기관) | 발급 전 신원·도메인 검증 담당 | 창구 본인확인 담당 |
| CSR(PKCS#10) | 공개키+주체정보를 개인키로 자기서명한 발급 요청 | 서명 넣은 발급 신청서 |
| 소유 증명(PoP) | CSR 자기서명으로 개인키 보유를 증명 | "이 도장 내 것" 실인 확인 |
| DV / OV / EV | 도메인 / 조직 / 확장 검증 등급 | 소유확인 / 법인확인 / 엄격심사 |
| CP / CPS | 인증서 정책 / 인증업무 준칙 | 발급 규정 / 운영 매뉴얼 |
| CA/Browser Forum | CA·브라우저 공동 발급 기준 제정체 | 발급 업계 표준 위원회 |
| Baseline Requirements | CA/B Forum의 최소 발급 요건 | 발급소 필수 준수 규정 |
| CT(인증서 투명성) | 발급 인증서를 공개 로그에 기록 | 오발급 감시 공개 장부 |
| CAA 레코드 | 어느 CA가 발급 가능한지 DNS 지정 | "이 관청만 발급 허용" 표찰 |
| ACME | 발급·갱신을 자동화하는 프로토콜 | 무인 발급 자판기 |
| pathLen | 하위 CA를 몇 단계까지 둘지 제한 | 재발급 위임 깊이 제한 |

## 깊이 이해
- **배경·문제의식**: 검증자가 모든 주체 공개키를 직접 알 수는 없음. 소수의 Root만 신뢰 저장소에 미리 심어두고, Root가 서명한 계층으로 신뢰를 확장하는 것이 CA 모델임. Root 개인키 유출은 전체 신뢰 붕괴로 이어져 오프라인·HSM 보관이 필수임.
- **작동 원리(어떻게+왜)**: 주체가 키쌍을 만들고 공개키·DN을 담은 CSR을 개인키로 자기서명(소유 증명)해 제출함. RA가 DV/OV/EV 등급에 맞게 신원을 검증하고, 발급용 Intermediate CA가 X.509에 서명함. Root는 평소 오프라인이라 유출 표면을 최소화하고, 실제 발급은 Intermediate가 담당해 사고 시 해당 Intermediate만 교체함.
- **비유**: 최상위 인장(Root)은 금고에 넣고, 실무 인장(Intermediate)으로만 매일 발급하는 관청과 같음. 실무 인장이 유출되면 그 인장만 폐기·교체하면 됨.
- **구체 예시**: Let's Encrypt는 ACME로 도메인 소유(HTTP-01/DNS-01 챌린지)를 자동 검증하는 DV CA로, ISRG Root X1 아래 Intermediate가 서버 인증서를 발급하고 모든 발급분을 CT 로그에 기록함.
- **흔한 오해·주의점**: (1) EV라도 암호 강도가 높아지는 것이 아니라 신원 검증 엄격도만 다름 — 브라우저 주소창 회사명 표시는 대부분 폐지됨. (2) Root가 직접 서버 인증서를 발급하지 않고 Intermediate가 발급함(계층 분리). (3) CA는 개인키를 받지 않으며 CSR의 공개키만 서명함.

## 연결 개념
- PKI·신뢰 체인 — CA가 구성하는 상위 신뢰 운영 체계 (009 참조)
- X.509 인증서 — CA가 서명·발급하는 결과물 (010 참조)
- CRL·OCSP — CA가 발급 후 폐지 상태를 게시하는 채널 (012 참조)

# 📝 【답안용】 시험 답안 템플릿

## 핵심 인사이트 (3줄 요약)

> 1. **본질**: CA는 신원 검증 후 CSR에 서명해 X.509를 발급하는 신뢰 앵커로, Root/Intermediate 계층으로 운영됨.
> 2. **가치**: DV·OV·EV 등급과 CP/CPS·CT로 발급 신뢰도를 표준화해 TLS·코드서명 생태계를 지탱함.
> 3. **판단 포인트**: Root 개인키 보호와 오발급 통제(CT·CAA·Baseline Requirements)가 CA 운영 품질을 결정함.

## 출제 의도 및 답안 포인트

| 출제 의도 | 반드시 짚을 핵심 | 감점 회피 포인트 |
|:---|:---|:---|
| 발급 절차 이해 확인 | CSR·RA 검증·서명·CT 등록 흐름 | 키쌍·CSR을 CA가 만든다고 단정 |
| CA 계층 이해 확인 | Root 오프라인·Intermediate 발급 분리 | Root가 직접 서버 인증서 발급 서술 |
| 검증 등급·통제 확인 | DV/OV/EV, CAA·CT·Baseline Requirements | EV가 암호 강도를 높인다고 오인 |

> 요약: CA 답안은 발급 절차·계층 분리·검증 등급·오발급 통제를 함께 써야 함.

---

## Ⅰ. 개요 및 필요성

- 개요: 신원 검증 후 X.509를 서명·발급하는 신뢰 기관임.
- 배경: 검증자가 모든 주체 공개키를 직접 알 수 없어 소수 Root를 신뢰 앵커로 삼아야 함.
- 필요성: CA는 CSR 검증·서명·CT 등록으로 공개키 보증을 제공하며, 계층 분리로 사고 영향을 국소화함.
- 전제: PKI 신뢰 체계·인증서 필드는 (009·010 참조)로 위임하고 발급 절차·계층·검증 등급에 집중함.

---

## Ⅱ. 구조 및 구성요소

```text
Root CA (자기서명·오프라인·HSM)
  -> Intermediate CA (발급 담당)
      -> End-entity 인증서 (서버·코드·개인)
발급 경로: 주체 키쌍·CSR -> RA(DV/OV/EV 검증) -> CA 서명 -> CT 로그 등록 -> 배포
```

| 구성요소 | 역할 | 특이사항 |
|:---|:---|:---|
| Root CA | 최상위 신뢰 앵커 | 자기서명, 오프라인 보관, HSM |
| Intermediate CA | 실제 발급 담당 | pathLen·용도 분리, 사고 시 교체 |
| RA | 신원·도메인 검증 | DV/OV/EV 등급별 증빙 확인 |
| CSR(PKCS#10) | 발급 요청·소유 증명 | 공개키+DN 자기서명 |
| CP / CPS | 정책·운영 준칙 | 감사·법적 근거 |
| CT 로그 | 발급 공개 기록 | 오발급 탐지, SCT 포함 |

> 요약: CA는 오프라인 Root·발급용 Intermediate·검증 RA·정책(CP/CPS)·투명성(CT)으로 구성된 발급 체계임.

---

## Ⅲ. 동작원리 및 흐름도

```text
주체 키쌍 생성 -> CSR 자기서명 제출 -> RA 신원·도메인 검증(DV/OV/EV)
  -> Intermediate CA 서명·발급 -> CT 로그 등록(SCT) -> 인증서 배포·설치
```

1. 주체가 키쌍을 생성하고 공개키·DN을 담은 CSR을 개인키로 자기서명해 소유를 증명하며 제출함.
2. RA가 등급에 맞게 도메인 소유(DV, ACME 챌린지)·조직 실체(OV)·엄격 심사(EV)를 검증함.
3. Intermediate CA가 CP/CPS·Baseline Requirements에 따라 SAN·EKU·유효기간을 담아 인증서에 서명함.
4. CA가 발급분을 CT 로그에 등록해 SCT를 포함하고, 주체가 인증서와 중간 CA 체인을 함께 설치함.

> 요약: 발급은 CSR 소유 증명 -> RA 신원 검증 -> Intermediate 서명 -> CT 등록의 순서로 진행됨.

---

## Ⅳ. 특징

- 계층 분리: Root는 오프라인 신뢰 앵커, Intermediate가 실제 발급을 맡아 유출 표면과 사고 영향을 최소화함.
- 검증 등급화: DV·OV·EV로 신원 검증 강도만 차등하며 암호 강도와는 무관함.
- 표준 통제: CA/B Forum Baseline Requirements·CP/CPS로 발급 요건과 감사 기준을 강제함.
- 투명성: CT 로그 필수 등록으로 오발급을 공개적으로 탐지 가능하게 함.
- 자동화: ACME로 도메인 검증·발급·갱신을 무인화해 대규모 인증서 운영을 지원함.

---

## Ⅴ. 심화 비교 및 적용 판단

발급 검증 등급(DV·OV·EV)을 검증 대상·소요·용도 축으로 비교함(다대상×다축이므로 표 사용).

| 구분 | DV(도메인 검증) | OV(조직 검증) | EV(확장 검증) |
|:---|:---|:---|:---|
| 검증 대상 | 도메인 소유만 | 도메인+법인 실체 | 도메인+엄격한 법적 실체 |
| 발급 소요 | 수분(ACME 자동) | 수시간~수일 | 수일(수동 심사) |
| 주 용도 | 일반 웹·API·자동화 | 기업·기관 대외 서비스 | 금융·전자상거래 고신뢰 |

> 요약: 자동화·대량 발급이 우선이면 DV+ACME, 조직 실체 표기가 필요하면 OV, 고신뢰 금융 서비스는 EV를 선택함.

리스크 관리는 불릿으로 정리함.
- 리스크: Root 키 유출 — 원인: 온라인 Root·HSM 미사용 — 대응: Root 오프라인·HSM·2인 통제, Root key export 0건.
- 리스크: 인증서 오발급 — 원인: RA 검증 실패·DNS 탈취 — 대응: CAA 레코드·CT 모니터링·다중 관점 검증, 탐지 1시간 이하.
- 리스크: Intermediate 침해 — 원인: 발급 CA 키 노출 — 대응: 용도별 분리·즉시 교체·상위 폐지, 재발급 24시간 이내.

지표 관리도 불릿으로 정리함.
- 지표: 발급 적합성 — 목표: Baseline Requirements·SAN·EKU 준수 — 측정: zlint·발급 전 lint 게이트.
- 지표: 운영 보안 — 목표: HSM·MFA·2인 승인·CP/CPS 준수 — 측정: 정기 WebTrust 감사.
- 지표: 오발급 탐지 — 목표: CT 모니터링·CAA 준수 100% — 측정: CT 알림·CAA 조회 로그.

## Ⅵ. 실무 적용 및 결론

**적용 방안 3개 (필수 — 단계별 또는 항목별):**
1. 계층 설계: Root CA 오프라인·HSM(FIPS 140-2/140-3) 보관, 용도별 Intermediate 분리, pathLen 제약 설정.
2. 발급 자동화·통제: DV는 ACME 자동 발급, 발급 전 zlint 게이트와 CAA·CT 등록을 파이프라인에 필수화.
3. 사고 대응: Intermediate 침해 시 상위 폐지·교체 절차와 오발급 24시간 내 폐지·재발급 런북 운영.

**결론 (2줄):**
- 기술사 판단: 대량·자동화 환경은 DV+ACME 사설/공인 CA, 조직 신뢰 표기가 필요하면 OV/EV를 선택함.
- 향후 방향: 인증서 수명 단축과 발급 자동화 확대에 대비해 CA 운영 자동화와 CT·CAA 통제 강화가 필요함.
