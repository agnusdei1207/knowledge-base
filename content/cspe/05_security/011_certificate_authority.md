## 미리 알고가기

- CA: 공개키와 주체 정보를 확인하고 인증서에 서명하는 기관임
- Root CA: 신뢰 저장소에 포함되는 최상위 CA임
- Intermediate CA: 루트 CA로부터 발급 권한을 위임받은 CA임
- CSR: 인증서 발급을 요청하기 위해 공개키와 주체 정보를 담은 요청임
- CA/B Forum: 공개 TLS 인증서 발급 기준을 정하는 산업 협의체임

## Ⅰ. 개요

- **정의/개념**: CA는 인증서 발급 전 주체를 확인하고 공개키와 주체 정보를 전자서명으로 연결하는 인증기관임
- **배경/필요성**: 공개키를 신뢰하려면 발급 전 확인, 발급 후 폐지, 감사 추적을 수행할 운영 주체가 필요함

## Ⅱ. 특징

- 루트 CA는 신뢰의 시작점이므로 오프라인 보관과 엄격한 키 통제가 필요함
- 중간 CA는 발급 업무를 분산하고 루트 키 사용 빈도를 줄임
- CA의 실수나 키 유출은 다수 인증서 신뢰에 영향을 줌
- 발급 절차는 신원 확인 수준에 따라 DV, OV, EV 등으로 나뉨

## Ⅲ. 종류 및 비교

| 구분 | Root CA | Intermediate CA | Issuing CA |
|:---|:---|:---|:---|
| 위치 | 신뢰 계층 최상위 | 루트 하위 | 최종 인증서 발급 지점 |
| 키 사용 | 제한적 서명 | 위임 서명 | 대량 발급 |
| 운영 방식 | 오프라인 중심 | 정책별 분리 | 자동화·감사 |
| 주요 위험 | 루트 신뢰 붕괴 | 체인 영향 확대 | 오발급·권한 남용 |

> 요약: CA 운영은 인증서 서명 행위보다 키 보호와 발급 권한 통제를 먼저 확인해야 함.

## Ⅳ. 구성요소 및 구조

| 구성요소 | 역할 |
|:---|:---|
| CPS·CP | 인증서 정책과 운영 절차 정의 |
| RA | 가입자 신원과 도메인 통제권 확인 |
| CA 서명키 | 인증서 서명에 사용하는 고권한 키 |
| 발급 시스템 | CSR 접수, 검증, 인증서 생성 |
| 감사 로그 | 발급·폐지·관리 행위 추적 |

```text
신청자 CSR -> RA 검증 -> CA 서명 -> 인증서 발급 -> CT/저장소 공개 -> 폐지 관리
```

## Ⅴ. 원리 및 절차 흐름도

1. **요청 접수**: 신청자가 CSR을 제출함
2. **신원 검증**: 도메인 통제권 또는 조직 정보를 확인함
3. **정책 확인**: 키 용도, 유효기간, 확장 필드를 검토함
4. **인증서 발급**: CA 서명키로 인증서 본문에 서명함
5. **공개·관리**: 인증서 투명성 로그, 폐지 목록, 감사 로그를 관리함

## Ⅵ. 실무 적용 및 유의점

- CA 키는 HSM과 다중 승인 절차로 보호함
- 오발급 발견 시 인증서 폐지와 브라우저 생태계 통지가 필요함
- 자동 발급 환경은 도메인 검증 권한 탈취를 방지해야 함
- 내부 CA는 신뢰 저장소 배포와 루트 교체 절차를 문서화함
- CA 교체는 인증서 체인, 클라이언트 호환성, 서비스 만료 일정을 함께 봄

## Ⅶ. 결론

- CA는 공개키 신뢰를 만드는 서명 주체이자 인증서 수명주기 운영 주체임
- 답안에서는 발급 절차, 키 보호, 오발급 대응, 폐지 관리를 함께 써야 함

## 작성 근거(검토용)

- “CA가 보증한다”는 표현만으로 끝내지 않고 검증·서명·감사·폐지 역할로 쪼갬
- Root와 Intermediate의 차이를 운영 위험 중심으로 배치함
- 009 PKI의 전체 구조와 겹치지 않게 발급 주체와 절차에 집중함
