# 📖 【암기용】 개념 완전 이해

> 목적: CA 인증 기관을 처음 봐도 인증서가 왜 신뢰되는지 이해하게 만든다. 시험 답안 양식이 아니라, 이해를 위한 친절한 설명이다.

## 한눈에
- **개요**: CA는 공개키와 주체 신원을 X.509 인증서로 묶어 서명하는 신뢰 기관
- **왜 필요한가**: 브라우저가 서버 공개키를 직접 알 수 없으므로, OS·브라우저 루트 저장소에 등록된 CA 서명으로 서버 신원을 검증함
- **핵심 직관**: CA는 인터넷 신분증 발급소이며, 인증서는 공개키에 붙은 위조 방지 도장임

## 깊이 이해
- **배경·문제의식**: 공개키 암호만으로는 "이 공개키가 진짜 example.com 것인가"를 보장하지 못함. 중간자 공격자는 자신의 공개키를 서버 공개키처럼 제시할 수 있음
- **작동 원리**: 가입자는 키쌍을 만들고 CSR(Certificate Signing Request)을 제출함. RA 또는 CA가 도메인·조직·확장 필드를 검증한 뒤 CA 개인키로 인증서에 서명함. 클라이언트는 루트 CA부터 서버 인증서까지 체인을 검증함
- **비유**: 여권 사무소가 본인 확인 후 여권을 발급하고, 입국 심사관은 여권의 관인과 유효기간을 확인하는 구조와 같음
- **구체 예시**: 공개 TLS 서버 인증서는 CA/B Forum 기준으로 SAN에 도메인을 넣고, 2026-03-15 이후 공개 신뢰 인증서 유효기간은 200일 이하 정책을 적용함
- **흔한 오해·주의점**: CA가 데이터를 암호화하는 것이 아니라, 공개키와 신원 연결을 서명함. 실제 암호화는 TLS 세션 키(AES-128-GCM·AES-256-GCM·ChaCha20-Poly1305)가 수행함

## 연결 개념
- PKI 공개키 기반구조 - CA·RA·Repository·CRL·OCSP를 포함하는 전체 신뢰 체계
- X.509 인증서 - Subject, Issuer, SAN, KeyUsage, ExtendedKeyUsage를 담는 인증서 형식
- TLS·SSL 프로토콜 - 서버 인증서 검증 후 대칭키를 협상하는 통신 보안 프로토콜

# 📝 【답안용】 시험 답안 템플릿

> 목적: 시험장에서 25분에 그대로 쓰는 답안 양식. 작성방식(추상표현 금지·수치·도식·문제유형 전환)을 엄격히 지킨다.
> 핵심: CA 문제는 암호 알고리즘 설명이 아니라 신뢰사슬, 발급 통제, 폐지 검증, 감사 기준을 연결해야 득점함.

## 핵심 인사이트 (3줄 요약)

> 1. **본질**: CA(Certificate Authority)는 공개키와 신원 정보를 X.509 인증서에 결합하고 CA 개인키로 전자서명하는 신뢰 앵커임.
> 2. **가치**: 브라우저·OS 루트 저장소 기반 신뢰사슬 검증으로 서버 인증, 무결성, 부인방지 근거를 제공함.
> 3. **판단 포인트**: 발급 정확성, CA 개인키 보호, 인증서 폐지(CRL·OCSP), CT 로그, WebTrust/ETSI 감사가 핵심 채점축임.

## 출제 의도 및 답안 포인트

| 출제 의도 | 반드시 짚을 핵심 | 감점 회피 포인트 |
|:---|:---|:---|
| PKI 신뢰모델 이해 확인 | Root CA -> Intermediate CA -> End Entity 체인, X.509, CSR, 서명 검증 | CA가 암호화 수행이라는 오답 금지 |
| 발급 절차와 통제 설명 | 키쌍 생성, CSR, 도메인·조직 검증, CA 서명, 배포, 폐지 | RA·Repository·OCSP 누락 금지 |
| 운영 보안 판단 | HSM FIPS 140-2/3, 오프라인 Root, CT 로그, 감사 | 개인키 유출 시 재발급만 쓰는 답안 금지 |

> 요약: CA 답안은 신뢰사슬과 발급 통제, 개인키 보호, 폐지 검증을 하나의 인증서 생명주기로 제시해야 함.

## Ⅰ. 개요 및 필요성

- 개요: 공개키 신원 보증 기관
- 배경: 공개키 암호는 키 소유자 식별 문제가 남으므로 제3자 신뢰점이 인증서 체인으로 신뢰를 전달해야 함.
- 필요성: CA는 X.509 인증서 서명·폐지·감사를 수행하고 TLS, 전자서명, 코드서명, mTLS의 인증 근거를 제공함.

---

## Ⅱ. 구조 및 구성요소

```text
가입자 키쌍/CSR -> RA 신원확인 -> CA 서명 발급 -> Repository 배포 -> 클라이언트 체인검증
                         +-> 감사로그/CT 로그
                         +-> CRL/OCSP 폐지상태
```

| 구성요소 | 역할 | 특이사항 |
|:---|:---|:---|
| Root CA | 최상위 신뢰 앵커 | 오프라인 보관, 자체서명 인증서, 루트 저장소 등재 |
| Intermediate CA | 하위 인증서 발급 | Root 노출 최소화, 경로 길이 제한, CA KeyUsage |
| RA | 가입자 신원·도메인 검증 | DV·OV·EV 검증, CAA·DNS·HTTP 검증 |
| Repository | 인증서·CRL·OCSP 정보 제공 | AIA, CDP, OCSP Responder URL |
| Subscriber | 키쌍 보유와 CSR 제출 | 개인키 비공개, SAN·KeyUsage 요청 |

> 요약: CA 구조는 Root 신뢰를 Intermediate 발급권한으로 위임하고, RA·Repository·폐지 서비스가 발급 정확성과 사후 검증을 보조함.

---

## Ⅲ. 동작원리 및 흐름도

```text
키쌍 생성 -> CSR 제출 -> 도메인/조직 검증 -> CA 개인키 서명 -> 인증서 설치
-> TLS 접속 -> 체인/유효기간/SAN/폐지상태 검증 -> 세션키 협상
```

| 단계 | 처리 내용 | 검증 기준 |
|:---:|:---|:---|
| 1 | 가입자 RSA/ECDSA 키쌍 생성 후 CSR 제출 | 개인키 외부 전송 금지, SAN 도메인 일치 |
| 2 | RA가 도메인·조직·CAA 레코드 확인 | DNS-01, HTTP-01, 이메일 검증 |
| 3 | CA가 X.509 v3 인증서 서명 | SHA-256 이상, KeyUsage·EKU 설정 |
| 4 | 클라이언트가 체인 검증 | Root 신뢰, Issuer 서명, 유효기간, hostname |
| 5 | 폐지상태와 로그 확인 | CRL·OCSP, Certificate Transparency SCT |

> 요약: 인증서 발급은 CSR 검증 후 CA 서명으로 끝나지 않고, 클라이언트의 체인·폐지·호스트명 검증까지 포함함.

## Ⅳ. 특징

| 구분 | 기존/대안 | CA 기반 인증 | 수치·표준 판단 |
|:---|:---|:---|:---|
| 신뢰 방식 | 사전 공유키·TOFU | 루트 저장소 기반 신뢰사슬 | X.509 v3, RFC 5280 |
| 인증 범위 | 채널 암호화 위주 | 서버·클라이언트·코드·문서 신원 확인 | TLS ServerAuth EKU, CodeSigning EKU |
| 운영 통제 | 수동 키 배포 | 발급·갱신·폐지 생명주기 | 공개 TLS 200일 이하, CT 로그 |
| 위험 지점 | 키 분실 | CA 개인키 유출·오발급 | HSM, 2인 승인, WebTrust/ETSI 감사 |

> 요약: CA 기반 인증은 대규모 신뢰 배포에는 유리하나, 오발급과 CA 개인키 유출은 CT·폐지·감사로 통제해야 함.

## Ⅴ. 심화 비교 및 적용 판단

| 비교 축 | 기존/대안 | CA 인증서 | 선택 기준 |
|:---|:---|:---|:---|
| 신뢰 배포 | Self-signed 수동 등록 | 공인 Root 기반 자동 검증 | 인터넷 공개 서비스는 공인 CA, 내부망은 Private CA |
| 비용/운영 | 장기 수동 갱신 | ACME 자동 갱신 | 90일 이하 인증서는 자동화 필수 |
| 보안 통제 | 키 파일 보관 | HSM/KMS, RBAC, 감사로그 | CA 개인키는 HSM, 서버키는 KMS 또는 TPM |

> 요약: 공개 웹은 공인 CA와 ACME 자동화를, 내부 mTLS는 Private CA와 짧은 수명 인증서를 선택함.

| 리스크 | 원인 | 대응 방안 | 확인 지표 |
|:---|:---|:---|:---|
| 오발급 | 도메인 검증 오류, RA 절차 누락 | CAA 확인, CT 모니터링, 2인 승인 | CT 알림 5분 이내, 오발급 0건 |
| CA 키 유출 | HSM 미사용, 관리자 권한 과다 | FIPS 140-2/3 HSM, 오프라인 Root, M of N 승인 | 키 접근 감사로그 100% |
| 만료 장애 | 갱신 일정 누락 | ACME 자동화, 만료 30일 전 경보 | 만료 14일 이하 인증서 0개 |

> 요약: CA 운영 리스크는 오발급·키 유출·만료 장애이며, CT·HSM·자동 갱신으로 통제함.

| 점검 항목 | 목표 기준 | 측정 방법 |
|:---|:---|:---|
| 발급 정확도 | SAN·EKU·KeyUsage 오류 0건 | 발급 전 lint, zlint, CA/B Forum BR 점검 |
| 키 보호 | CA 개인키 HSM 저장률 100% | HSM 정책, 접근 로그, 분리 보관 점검 |
| 폐지 대응 | 폐지 요청 후 CRL/OCSP 반영 SLA 24시간 이내 | OCSP 응답, CRL thisUpdate/nextUpdate 확인 |

> 요약: CA 품질은 인증서 프로파일, 키 보호, 폐지 반영 SLA로 측정해야 함.

## Ⅵ. 실무 적용 및 결론

**적용 방안 3개 (필수 - 단계별 또는 항목별):**
1. 공인 TLS: CA/B Forum BR 준수, SAN 기반 인증서, ACME 자동 갱신, CT 로그 모니터링 적용
2. 내부 mTLS: Private CA, SPIFFE ID 또는 SAN URI, 인증서 수명 24시간~90일, RBAC 기반 발급권한 분리
3. CA 보호: Root CA 오프라인, Intermediate CA HSM 보관, 관리자 M of N 승인, CRL·OCSP 이중화 구성

**결론 (2줄):**
- 기술사 판단: 공개 서비스는 공인 CA와 CT를 선택하고, 내부 서비스 간 인증은 Private CA 기반 mTLS와 짧은 수명 인증서를 선택함
- 향후 방향: ACME 자동화, Certificate Transparency, PQC 인증서 전환을 포함한 Crypto-Agility 체계로 확장 필요
