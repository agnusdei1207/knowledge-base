# 📖 【암기용】 개념 완전 이해

> 목적: HSM·KMS 기반 키 관리를 처음 봐도 완벽히 이해하게 만든다. 시험 답안 양식이 아니라, 이해를 위한 친절한 설명이다.

## 한눈에
- **개요**: 암호키의 생성·보관·사용·회전·폐기를 통제하는 보안 체계
- **왜 필요한가**: AES-256이나 RSA-3072를 써도 키가 노출되면 암호화는 무력화됨. 키는 데이터보다 권한 집중도가 크므로 HSM, KMS, 감사, 분리 권한이 필요함.
- **핵심 직관**: 보안의 핵심은 금고의 강도만이 아니라 열쇠를 누가 만들고, 어디에 보관하고, 언제 바꾸고, 누가 사용했는지 기록하는 것임.

## 깊이 이해
- **배경·문제의식**: 애플리케이션 설정 파일, 소스코드, 환경변수에 키를 저장하면 침해 시 대량 데이터 복호화가 가능함. 중앙 KMS와 HSM은 키 접근을 API·정책·감사로 통제함.
- **작동 원리**: HSM은 FIPS 140-3 검증 경계 안에서 마스터 키를 생성·보관함. KMS는 IAM·정책·로그를 제공하고 envelope encryption으로 데이터 키(DEK)를 감싸 관리함.
- **비유**: 문서마다 작은 열쇠(DEK)를 쓰고, 작은 열쇠를 다시 중앙 금고의 마스터 열쇠(KEK)로 봉인하는 구조임.
- **구체 예시**: 10TB 객체 저장소는 객체별 DEK로 암호화하고 DEK는 KMS KEK로 wrap함. 키 회전 주기는 90일 또는 1년, 키 사용 로그는 SIEM에 전송함.
- **흔한 오해·주의점**: KMS는 키를 안전하게 두는 서비스만이 아니라 접근정책, rotation, 감사, 비상 폐기까지 포함한 운영 체계임.

## 연결 개념
- Envelope Encryption - DEK와 KEK를 분리하는 대용량 데이터 암호화 방식
- HSM - 키 생성·서명·복호화를 검증된 하드웨어 경계에서 수행
- IAM/RBAC - 키 사용 권한을 최소 권한으로 제한하는 통제

# 📝 【답안용】 시험 답안 템플릿

> 목적: 시험장에서 25분에 그대로 쓰는 답안 양식. 작성방식(추상표현 금지·수치·도식·문제유형 전환)을 엄격히 지킨다.
> 핵심: 키 관리는 암호 알고리즘 보조 기능이 아니라 생성-보관-사용-회전-폐기 전 생명주기 통제 문제임.

## 핵심 인사이트 (3줄 요약)

> 1. **본질**: HSM·KMS 키 관리는 암호키 생명주기를 FIPS 140-3, IAM, 감사로그, envelope encryption으로 통제하는 체계임.
> 2. **가치**: 키를 데이터·애플리케이션과 분리해 대량 복호화, 내부자 오남용, 규제 감사 실패 위험을 축소함.
> 3. **판단 포인트**: KEK/DEK 분리, rotation 주기, 권한 분리, 키 사용 로그 100%, 비상 revoke 절차가 핵심임.

## 출제 의도 및 답안 포인트

| 출제 의도 | 반드시 짚을 핵심 | 감점 회피 포인트 |
|:---|:---|:---|
| 키 생명주기 이해 확인 | 생성·보관·사용·회전·폐기 단계 | 암호화 알고리즘만 설명 |
| HSM과 KMS 역할 구분 | HSM은 하드웨어 보안 경계, KMS는 정책·API·감사 | HSM과 KMS를 동일 장비로 처리 |
| 운영 통제 역량 확인 | FIPS 140-3, envelope encryption, RBAC, audit | 키를 소스코드·환경변수에 저장 |

> 요약: 키 관리 답안은 암호 세기보다 키 생명주기, 권한, 감사 지표를 중심으로 구성해야 함.

---

## Ⅰ. 개요 및 필요성

- 개요: 암호키 생명주기 통제 체계
- 배경: 키가 노출되면 AES-256 적용 데이터도 복호화될 수 있어 알고리즘 선택만으로는 데이터 기밀성을 보장할 수 없음.
- 필요성: HSM/KMS, 권한 분리, 키 회전, 감사로그를 적용해 클라우드·금융·개인정보 시스템의 키 생성·보관·폐기를 통제함.

---

## Ⅱ. 구조 및 구성요소

```text
Root Key(HSM) -> KEK(KMS) -> DEK 생성 -> 데이터 암호화
IAM/RBAC -> KMS API 호출 -> Audit Log -> SIEM
Rotation Policy -> Key Versioning -> Re-encryption / Lazy Rotation
```

| 구성요소 | 역할 | 특이사항 |
|:---|:---|:---|
| HSM | 루트 키 생성·보관·서명·복호화 | FIPS 140-3 Level 3 기준 검토 |
| KMS | 키 정책, API, 버전, 감사 제공 | CMK/KEK 관리, IAM 연동 |
| DEK/KEK | 데이터 키와 키 암호화 키 분리 | envelope encryption |
| 감사·모니터링 | 키 사용·실패·권한 변경 기록 | SIEM 전송, 보존 1년 이상 |

> 요약: HSM은 신뢰 경계, KMS는 정책·운영 평면, DEK/KEK 분리는 대용량 암호화의 기본 구조임.

---

## Ⅲ. 동작원리 및 흐름도

```text
키 정책 수립 -> HSM 루트 키 생성 -> KMS KEK 생성 -> DEK 발급
-> 데이터 암호화 -> DEK wrap 저장 -> 사용 시 unwrap -> 로그 감사 -> 회전/폐기
```

| 단계 | 처리 내용 | 검증 기준 |
|:---:|:---|:---|
| 1 | 키 등급·소유자·사용 목적 정의 | 데이터 등급 매핑 100% |
| 2 | HSM/KMS에서 KEK 생성 | FIPS 140-3, dual control |
| 3 | 애플리케이션이 DEK로 데이터 암호화 | DEK 평문 저장 0건 |
| 4 | KEK로 DEK wrap 후 저장 | envelope encryption 적용 |
| 5 | rotation·revoke·audit 수행 | 키 사용 로그 100%, 주기 준수 |

> 요약: 키 관리는 DEK 평문을 저장하지 않고 KEK로 감싸며 모든 사용 이벤트를 감사하는 흐름임.

## Ⅳ. 특징

| 구분 | 로컬 키 저장 | HSM/KMS 키 관리 | 수치·표준 포인트 |
|:---|:---|:---|:---|
| 보관 | 파일·환경변수 | HSM 보안 경계·KMS 정책 | FIPS 140-3 |

| 감사 | 로그 누락 가능 | 키 사용·실패·정책변경 로그 | 로그 수집 100% |

> 요약: HSM/KMS는 키를 애플리케이션에서 분리하고 권한·회전·감사를 정책으로 집행함.

## Ⅴ. 심화 비교 및 적용 판단

| 구분 | 기존/대안 | 본 키워드 | 선택 기준 |

| 비용/성능 | 로컬 암복호화 | envelope encryption | KMS API p95 100ms 이하 |
| 운영/규제 | 수동 키 관리 | rotation·audit 자동화 | PCI DSS, ISMS-P, 개인정보 감사 |

> 요약: 고위험 데이터는 HSM-backed KMS를, 대용량 데이터는 envelope encryption으로 API 호출 비용을 제어함.

| 리스크 | 원인 | 대응 방안 | 확인 지표 |
|:---|:---|:---|:---|
| 키 노출 | 소스코드·로그·환경변수 저장 | secret scan, KMS 참조 방식 | 평문 키 탐지 0건 |
| 권한 오남용 | 관리자 단독 복호화 | RBAC, dual control, break-glass | 고위험 키 2인 승인 100% |
| 회전 실패 | 레거시 암호문 재암호화 지연 | key versioning, lazy rotation | 만료 키 사용 0건 |

> 요약: 키 관리 리스크는 노출, 오남용, 회전 실패이며 탐지 지표와 승인 절차로 통제함.

| 점검 항목 | 목표 기준 | 측정 방법 |
|:---|:---|:---|
| 키 수명 | KEK rotation 90일 또는 1년 | KMS 정책 점검 |
| 접근통제 | 최소권한, MFA, 2인 승인 | IAM 리뷰, SoD 점검 |
| 감사/복구 | 키 사용 로그 100%, 백업 키 RTO 4시간 | SIEM, DR 리허설 |

> 요약: 운영 성숙도는 rotation 준수, 최소권한, 감사로그 완전성, 복구 시간으로 판단함.

## Ⅵ. 실무 적용 및 결론

**적용 방안 3개 (필수 — 단계별 또는 항목별):**
1. 키 계층 설계: HSM root key, KMS KEK, 서비스별 DEK를 분리하고 envelope encryption을 기본 패턴으로 적용함.
2. 접근·감사 통제: RBAC/ABAC, MFA, dual control, 키 사용 로그 100% SIEM 전송을 운영 기준으로 둠.
3. 생명주기 자동화: KEK rotation 90일 또는 1년, 비상 revoke 15분 이내, 만료 키 사용 0건을 점검함.

**결론 (2줄):**
- 기술사 판단: 규제·금융·개인정보 키는 HSM-backed KMS를 적용하고, 일반 대용량 데이터는 envelope encryption으로 성능과 감사 요구를 함께 충족함.
- 향후 방향: 멀티클라우드 KMS, BYOK/HYOK, confidential computing attestation 연계로 키 릴리스 조건이 세분화됨.
