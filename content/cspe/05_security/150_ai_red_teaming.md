# 📖 【암기용】 개념 완전 이해

> 목적: AI 레드팀을 일반 침투테스트와 구분해 모델·애플리케이션·인프라·운영 전 범위의 적대적 검증으로 이해하게 만든다. 시험 답안 양식이 아니라, 이해를 위한 친절한 설명이다.

## 한눈에
- **개요**: AI 시스템을 공격자 관점에서 테스트해 프롬프트 인젝션, 정보 노출, 편향, 환각, 도구 오남용을 사전에 발견하는 검증 활동
- **왜 필요한가**: 생성형 AI는 자연어 입력, 확률적 출력, RAG, Agent, 플러그인으로 구성되어 기존 취약점 스캐너만으로 위험을 식별하기 어렵다.
- **핵심 직관**: AI 레드팀은 모델에게 "틀린 답을 하게 만들기"가 아니라, 시스템이 실패해도 피해가 제한되는지 확인하는 안전성·보안 훈련이다.

## 깊이 이해
- **배경·문제의식**: LLM 서비스는 출시 후 사용자와 공격자가 새로운 프롬프트, 문서, 도구 조합을 계속 발견한다. 학습 데이터와 모델 내부를 완전히 설명하기 어렵기 때문에 배포 전·후 적대적 검증이 필요함.
- **작동 원리**: 범위 정의, 위협 모델링, 공격 시나리오 작성, 수동·자동 테스트, 위험 등급화, 재현 절차 기록, 완화 조치, 회귀 테스트 순서로 진행한다.
- **비유**: 건물 준공 전 소방 훈련과 침입 테스트를 동시에 수행해, 문이 열리는지보다 화재·침입 시 피해 확산이 어디서 멈추는지 확인하는 과정과 같다.
- **구체 예시**: 사내 HR Agent를 대상으로 간접 프롬프트 인젝션, 권한 없는 인사 문서 검색, 퇴사자 메일 발송 tool call, 민감 정보 로그 저장을 50개 시나리오로 검증함.
- **흔한 오해·주의점**: 일회성 이벤트로 끝내면 배포 후 모델·프롬프트·RAG 문서 변경을 반영하지 못한다. CI 회귀 테스트와 운영 모니터링으로 이어져야 함.

## 연결 개념
- OWASP GenAI Red Teaming Guide — 모델 평가, 구현 테스트, 인프라 평가, 런타임 행동 분석
- NIST AI RMF — Govern, Map, Measure, Manage 위험관리 흐름
- OWASP LLM Top 10 — LLM01~LLM10 공격 시나리오의 테스트 기준

# 📝 【답안용】 시험 답안 템플릿

> 목적: 시험장에서 25분에 그대로 쓰는 답안 양식. 작성방식(추상표현 금지·수치·도식·문제유형 전환)을 엄격히 지킨다.
> 핵심: AI 레드팀은 모델 단독 시험이 아니라 모델·프롬프트·RAG·Agent·인프라·운영 로그를 대상으로 한 위험 기반 검증 체계이다.

## 핵심 인사이트 (3줄 요약)

> 1. **본질**: AI Red Teaming은 생성형 AI 시스템을 공격자 관점에서 평가해 보안·안전·프라이버시·운영 실패 경로를 식별하는 적대적 검증 활동이다.
> 2. **가치**: 배포 전 취약점 제거와 배포 후 회귀 테스트를 연결하면 prompt injection, data leakage, excessive agency를 재현 가능한 결함으로 관리함.
> 3. **판단 포인트**: 테스트 범위를 모델 출력이 아니라 데이터, RAG, 도구, 권한, 로깅, 사용자 피해까지 확장했는지가 채점 포인트임.

## 출제 의도 및 답안 포인트

| 출제 의도 | 반드시 짚을 핵심 | 감점 회피 포인트 |
|:---|:---|:---|
| AI 보안 검증 체계 이해 확인 | threat modeling, attack scenario, evidence, remediation, regression | 단순 jailbreak 테스트로 축소하지 않음 |
| 표준·가이드 연계 확인 | OWASP LLM Top 10, OWASP GenAI Red Teaming, NIST AI RMF | 특정 도구 목록만 나열하지 않음 |
| 운영 내재화 판단 확인 | CI 테스트, 위험 등급, 재현 로그, 책임자 지정 | 일회성 이벤트로 작성하지 않음 |

> 요약: 이 문제는 AI 시스템 위험을 공격 시나리오로 재현하고, 완화·회귀 검증까지 연결하는 체계를 요구한다.

---

## Ⅰ. 개요 및 필요성

AI 레드팀은 AI 시스템을 공격자 관점에서 검증하는 보안·안전성 평가 활동이다. 생성형 AI는 확률적 출력, 자연어 공격면, RAG, Agent, tool call로 인해 기존 점검표만으로 위험을 찾기 어렵다. 출시 전후 반복 검증을 통해 취약점 재현성, 피해 범위, 완화 효과를 수치로 확인해야 함.

---

## Ⅱ. 구조 및 구성요소

```text
Scope Definition -> Threat Model -> Test Scenario -> Execution
                 +-> Model / App / Infra / Runtime
Finding -> Risk Rating -> Remediation -> Regression Test -> Report
```

| 구성요소 | 역할 | 통제 포인트 |
|:---|:---|:---|
| 범위 정의 | 대상 모델·앱·데이터·도구 확정 | production mirror, test account, 법무 승인 |
| 위협 모델 | 자산·공격자·피해 경로 식별 | OWASP LLM Top 10, STRIDE, MITRE ATLAS |
| 테스트 실행 | 수동·자동 공격 시나리오 수행 | prompt set, RAG poisoning, tool abuse |
| 위험 등급화 | 영향도·가능성·재현성 평가 | CVSS 유사 점수, business impact |
| 회귀 검증 | 완화 조치 후 재발 확인 | CI prompt regression, evidence 저장 |

> 요약: AI 레드팀은 범위-위협-실행-등급-완화-회귀 검증으로 이어지는 폐루프 구조이다.

---

## Ⅲ. 동작원리 및 흐름도

```text
자산 식별 -> 위협 시나리오 작성 -> 공격 실행
-> 증거 수집 -> 위험 등급 산정 -> 완화 조치 -> 재시험/운영 모니터링
```

| 단계 | 처리 내용 | 검증 기준 |
|:---:|:---|:---|
| 1 | 대상 AI 시스템과 데이터 흐름 파악 | model, prompt, RAG, tool, log 목록화 |
| 2 | 공격 시나리오와 성공 조건 정의 | leakage, policy bypass, tool misuse 기준 |
| 3 | 수동·자동 테스트 실행 | 100개 이상 prompt set, multi-turn test |
| 4 | 증거와 위험 등급 기록 | reproduction step, screenshot/log, severity |
| 5 | 완화 조치 후 회귀 테스트 수행 | pass/fail, residual risk, owner sign-off |

> 요약: AI 레드팀은 공격 성공 여부보다 재현 가능한 증거와 완화 후 잔여 위험을 남기는 것이 핵심이다.

## Ⅳ. 특징

| 구분 | 일반 침투테스트 | AI 레드팀 | 수치·기술 포인트 |
|:---|:---|:---|:---|
| 대상 | 서버, 네트워크, 웹 취약점 | 모델, 프롬프트, RAG, Agent, tool, 로그 | OWASP LLM Top 10 |
| 입력 | 패킷, URL, payload | 자연어, 문서, 이미지, multi-turn 대화 | prompt set 100개 이상 |
| 결과 | CVE, 권한 상승 | 정책 우회, 데이터 노출, 유해 출력, 도구 오남용 | attack success rate |
| 주기 | 릴리스 전 점검 | 배포 전·후 지속 회귀 검증 | CI regression, runtime monitor |

> 요약: AI 레드팀은 전통 침투테스트에 모델 행동 평가와 운영 회귀 테스트를 결합한 AI 전용 검증 활동이다.

## Ⅴ. 심화 비교 및 적용 판단

| 비교 축 | 기존/대안 | 본 키워드 | 선택 기준 |
|:---|:---|:---|:---|
| 구조 | 보안 스캐너 중심 | 수동 공격+자동 prompt regression | LLM/RAG/Agent 포함 서비스는 AI 레드팀 적용 |
| 범위 | 인프라·웹 취약점 | 모델 평가, 구현 테스트, 인프라 평가, 런타임 분석 | OWASP GenAI Red Teaming 4영역 |
| 운영 | 연 1회 점검 | 릴리스별 테스트+운영 탐지 | 모델·프롬프트·도구 변경 시 재시험 |

> 요약: AI 레드팀은 모델·데이터·도구 변경 시마다 반복하고, 단발성 점검 대신 회귀 테스트와 운영 탐지 지표로 관리해야 한다.

| 리스크 | 원인 | 대응 방안 | 확인 지표 |
|:---|:---|:---|:---|
| 테스트 범위 누락 | 모델만 평가 | RAG·tool·log 포함 scope checklist | scope coverage 100% |
| 재현 불가 결함 | 증거 기록 부족 | prompt, seed, model version, trace ID 저장 | reproduction rate 95% 이상 |
| 완화 미검증 | 조치 후 재시험 누락 | CI regression gate, owner sign-off | reopened finding 0건 |

> 요약: 레드팀 품질은 결함 수보다 범위 커버리지, 재현율, 완화 후 재발 건수로 판단한다.

| 점검 항목 | 목표 기준 | 측정 방법 |
|:---|:---|:---|
| 공격 성공률 | 고위험 시나리오 ASR 5% 이하 | red team prompt set, multi-turn replay |
| 결함 처리 | Critical 7일, High 14일 내 조치 | ticket SLA, risk register |
| 운영 내재화 | 모델·프롬프트 변경 100% 회귀 테스트 | CI job, model registry webhook |

> 요약: AI 레드팀 성과는 ASR, 조치 SLA, 변경 시 회귀 테스트 실행률로 측정한다.

## Ⅵ. 실무 적용 및 결론

**적용 방안 3개 (필수 — 단계별 또는 항목별):**
1. 범위·위협 모델링: OWASP LLM Top 10 기준으로 프롬프트 인젝션, 정보 노출, 과도한 에이전시, 무제한 소비 시나리오를 우선 선정
2. 실행·증거화: 수동 공격과 자동 도구(garak, promptfoo 등)를 결합하고 prompt, model version, trace ID, 결과 로그를 결함 티켓에 첨부
3. 운영 내재화: 모델·프롬프트·RAG 문서·tool registry 변경 시 CI 회귀 테스트를 실행하고 Critical 7일, High 14일 SLA 적용

**결론 (2줄):**
- 기술사 판단: 단순 모델 API 사용은 표준 공격 세트 검증으로 시작하고, Agent·RAG 업무 시스템은 정기 AI 레드팀과 운영 회귀 테스트를 필수화함
- 향후 방향: AI 시스템이 자율 실행과 외부 도구를 포함하면서 AI 레드팀은 보안 테스트, 품질 평가, 거버넌스 감사의 공통 절차로 발전함
