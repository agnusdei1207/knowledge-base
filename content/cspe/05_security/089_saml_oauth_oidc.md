## 1. 한눈에 이해하기 (Core Intuition)
- **정의**: 내가 '네이버 아이디'나 '회사 사원증' 하나만으로 수많은 외부 쇼핑몰이나 글로벌 클라우드 업무 사이트(SaaS)에 **비밀번호를 넘겨주지 않고도 "안전하게 내 신분과 권한을 증명해 주는" 3대장 표준 대화 규약(프로토콜)** 입니다.
- **필요성**: 작은 스타트업(배달 앱)이 회원 가입을 받으려니, 고객들이 "듣보잡 앱에 내 비밀번호 치기 불안하다"며 가입을 안 합니다. 그래서 "네이버/카카오 아이디로 로그인하기" 버튼을 만듭니다. 이때 스타트업이 네이버에게 어떻게 안전하게 "이 사람 누군지 인증해 줘"라고 부탁할지에 대한 전 세계 공통의 약속(언어)이 필요했습니다.
- **핵심 직관**: **"술집 앞 민증 검사 (세 가지 방법)"**.
  - **SAML (출입증 발급)**: B2B 기업용. 회사가 "이 사람은 우리 회사 홍길동 대리가 맞고, 이메일은 홍길동@회사.com 이다"라고 빡빡한 XML(공문서) 증명서를 써주면, 클라우드 술집이 그걸 믿고 프리패스 통과시켜 줍니다. (기업 SSO의 핵심).
  - **OAuth 2.0 (심부름 열쇠 발급)**: 앱 권한용. 배달 앱이 "홍길동님, 카카오톡 친구 목록 좀 가져다 써도 돼요?"라고 물어보고 승인하면, 카카오가 홍길동의 비번을 넘기지 않고 배달 앱에게 **'친구 목록만 조회할 수 있는 임시 열쇠(Access Token)'** 를 던져줍니다.
  - **OIDC (최신형 디지털 민증)**: B2C 최신용. OAuth라는 심부름 열쇠 배달 기술을 뼈대 삼아, 그 위에 가벼운 JSON 명함(ID Token)을 하나 더 얹어 "얘는 홍길동 맞음"을 증명해 주는 가장 트렌디한 인증 방식.

## 2. 왜 중요한가? (Background & Value)
- **등장 배경**: 옛날 인트라넷 시절에는 마이크로소프트의 커버로스(Kerberos)라는 통신 규약 하나면 끝났습니다. 하지만 회사가 세일즈포스(Salesforce), 줌(Zoom), M365 같은 웹 기반 외부 클라우드(SaaS)를 쓰기 시작하면서 방화벽 밖으로 나갈 수 있는 범용적인 '웹 친화적' 인증 규약이 필수 불가결해졌습니다.
- **가치**: "비밀번호 노출 리스크 0%". 수십 개의 타사 앱(3rd Party)을 쓰면서도 내 진짜 아이디와 비밀번호를 그 허접한 앱의 DB에 저장하지 않아도 됩니다(개인정보 보호 종결자). 또한 마우스 클릭 3번만으로 수천 개의 글로벌 클라우드 앱을 회사 계정과 연동(SSO)시킬 수 있는 마법의 연결고리입니다.

## 3. 어떻게 작동하는가? (Mechanism)

**1. SAML 2.0 (Security Assertion Markup Language)**
- **목적**: '인증(Authentication, 이 사람 누구야?)'. 기업 간 B2B 연동 90% 이상 점유.
- **방식**: 브라우저 기반 리다이렉트 통신.
- **과정**: 직원이 줌(Zoom) 사이트에 감 $\rightarrow$ 줌이 "너네 회사 Okta(인증 서버) 가서 인증받아와!"라고 튕겨냄 $\rightarrow$ Okta에서 로그인 $\rightarrow$ Okta가 엄청 길고 무거운 **XML(문서) 형식의 보증서(Assertion)** 에 전자 서명 도장을 쾅 찍어서 직원 브라우저에 쥐여줌 $\rightarrow$ 직원이 줌에 제출하면 로그인 끝.

**2. OAuth 2.0 (Open Authorization)**
- **목적**: '인가(Authorization, 내 데이터 가져다 써!)'. 인증 기술이 아닙니다!
- **방식**: 모바일 앱과 REST API 호출에 최적화. 
- **과정**: 네이버 캘린더 앱이 구글 캘린더 일정을 긁어오려 함. 내가 "동의"를 누름 $\rightarrow$ 구글은 네이버에게 내 비번을 주지 않고, **'액세스 토큰(Access Token)'** 이라는 입장권(토큰)만 줌. 네이버는 이 토큰을 들고 구글 API에 가서 내 일정을 빼옴. (토큰에는 "이 사람 신분이 누군지"에 대한 정보는 안 들어있고, 오직 "이거 긁어갈 권한 있음"만 들어있음).

**3. OIDC (OpenID Connect)**
- **목적**: '인증(Who)' + '인가(What)' 통합. 최신형 SSO 트렌드.
- **방식**: OAuth 2.0 프로토콜 위에 인증 기능을 추가(업바인딩)한 형태. 무거운 XML(SAML) 대신 가벼운 **JWT(JSON 웹 토큰)** 사용.
- **과정**: 배달 앱에서 "카카오로 로그인" 클릭 $\rightarrow$ 카카오가 배달 앱에 '권한 심부름 토큰(Access Token)'도 주면서, 덤으로 **'ID 토큰(JWT)'** 이라는 명함(이름, 이메일 정보)도 같이 넘겨줌 $\rightarrow$ 배달 앱은 이 명함을 까보고 "아하, 홍길동이구나!" 하고 가입/로그인시킴. 모바일 앱과 최신 아키텍처(MSA)의 압도적 대세.

## 4. 실전 활용 및 예시 (Real-world Application)
- **구체적 사례 (어떤 걸 써야 하나요?)**: 
  - 회사에서 산 외국 클라우드 솔루션(HR, ERP)을 사내 포털 로그인 버튼 하나로 붙이려 한다 $\rightarrow$ 십중팔구 **SAML**을 지원하므로 이걸 씁니다. 
  - 회사가 B2C 게임/앱을 새로 개발했는데, 회원 가입 받기 귀찮아서 구글/애플 로그인을 붙이려 한다 $\rightarrow$ 무조건 가벼운 **OIDC (OAuth 기반)** 를 씁니다. 
- **주의점 및 흔한 오해**: 
  - 개발자들이 가장 많이 하는 실수: "OAuth를 로그인(인증) 용도로 썼다"고 말하는 것. OAuth는 본질적으로 '권한 위임(인가)' 프로토콜이라 그 자체로 사용자 검증(인증) 기능이 없습니다. 인증을 하려면 반드시 OIDC(OpenID Connect)를 써야 합니다. (이 둘을 혼동하면 해킹 취약점이 뻥뻥 뚫립니다).

## 5. 핵심 비교 및 연결 개념 (Relation)
| 구분 | SAML 2.0 | OAuth 2.0 | OIDC (OpenID Connect) |
|---|---|---|---|
| **목적 (핵심)** | **인증** (SSO용) | **인가** (API 권한 위임용) | **인증** (+ OAuth 인가 기반) |
| **데이터 포맷** | XML (길고 무거움) | JSON (액세스 토큰) | JWT (가벼운 JSON 토큰) |
| **주사용 환경** | 엔터프라이즈 B2B (웹) | API 연동, IoT, 모바일 앱 | B2C, 모바일, 최신 클라우드 앱 |
| **핵심 산출물** | Assertion (보증 수표) | Access Token (심부름 열쇠) | ID Token (신분증명 명함) |

# ✍️ 단답형 / 서술형 시험장 출격 준비

### Ⅰ. 핵심 인사이트
- **본질**: 클라우드/SaaS 생태계와 모바일 앱(API 중심) 환경에서, 분산된 시스템 간에 사용자의 크리덴셜(ID/PW)을 직접 노출하지 않고도 안전하게 **인증(Authentication, 신원 확인)** 과 **인가(Authorization, 권한 위임)** 를 처리할 수 있도록 IETF/OASIS에서 제정한 3대 개방형 연합(Federation) 프로토콜.
- **가치**: 레거시(온프레미스) 환경의 Kerberos 통신 규약이 방화벽 밖의 인터넷(HTTP/REST) 환경에서 무용지물화되는 문제를 해결함. 서드파티(3rd-party) 애플리케이션의 무결성을 신뢰하지 않고도 데이터 침해 위험(Credential Theft)을 방어하는 제로 트러스트 통합 접근 제어의 뼈대.
- **판단 포인트**: IT 아키텍트는 구축할 서비스의 특성(B2B 레거시 웹 vs B2C 모바일 API)에 따라 프로토콜을 선별해야 합니다. SAML은 무거운 XML 특성상 모바일 네이티브 앱 구현이 어려워 OIDC로 패러다임 전환이 일어나고 있으며, "OAuth는 인가 프로토콜이지 인증 프로토콜이 아니다"라는 근본적 오해(Pseudo-Authentication Risk)를 타파하는 것이 설계의 핵심입니다.

### Ⅱ. SAML (Security Assertion Markup Language) 아키텍처
엔터프라이즈 연합 SSO(Federated SSO)의 B2B 절대 표준.
- **3자 구성 요소**: 
  - **Principal** (사용자/웹 브라우저)
  - **IdP (Identity Provider, 인증 제공자)**: 사내 인증 서버(예: AD FS, Okta).
  - **SP (Service Provider, 서비스 제공자)**: 접속 타겟 클라우드(예: M365, AWS).
- **메커니즘 (SP-Initiated Flow 기준)**: 
  1. 사용자가 SP에 접근. 
  2. SP는 브라우저를 IdP로 리다이렉트(Redirect)시킴. 
  3. 사용자가 IdP에 인증 완료. 
  4. IdP는 "이 사용자는 누구누구이며, 인증 시간은 언제임"을 기록한 **SAML Assertion(XML 문서)** 을 암호화 서명하여 발행함. 
  5. 브라우저를 통해 Assertion이 SP로 전달되어 SSO 완료.
- **한계점**: XML 파싱의 오버헤드가 크고, 웹 브라우저 리다이렉트(POST)에 의존하므로 SPA(Single Page App)나 백엔드 REST API 통신 환경에서는 구축이 매우 까다로움.

### Ⅲ. OAuth 2.0 (Open Authorization) 인가 메커니즘
서드파티 애플리케이션에 대한 안전한 '제한적 권한 위임(Delegation)' 프레임워크.
- **4자 구성 요소**:
  - **Resource Owner (자원 소유자)**: 사용자 본인.
  - **Client (클라이언트)**: 권한을 요청하는 서드파티 앱.
  - **Authorization Server (인가 서버)**: 동의(Consent)를 받고 토큰을 발행하는 주체(Google, Kakao 등).
  - **Resource Server (자원 서버)**: 실제 데이터(연락처/사진)가 저장된 API 서버.
- **핵심 메커니즘**:
  - Client가 사용자 크리덴셜을 알지 못한 상태로, 인가 서버로부터 수명이 짧은 **액세스 토큰(Access Token, 무기명 Bearer Token)** 과 **리프레시 토큰(Refresh Token)** 을 발급받아 Resource Server의 API를 호출(Call)함.
- **보안 리스크 (인증 프로토콜로의 오용)**: 
  - 액세스 토큰은 신분증이 아니라 '호텔 방 키(Key)'입니다. 키를 주웠다고 그 사람이 예약자가 맞는지(인증) 확인할 수 없습니다. OAuth를 인증에 오용할 경우 계정 탈취(Account Takeover) 취약점 발생.

### Ⅳ. OIDC (OpenID Connect) 인증 아키텍처 (현대 API 표준)
OAuth 2.0의 프레임워크 뼈대(인가) 위에, 얹어 쓸 수 있는 얇은 '인증(Identity)' 레이어를 추가한 하이브리드 표준 프로토콜.
- **메커니즘 혁신 (ID Token 도입)**:
  - OAuth 2.0 플로우를 그대로 따라 인가 서버(IdP)에 다녀옴.
  - 리턴 값으로 무기명인 '액세스 토큰'뿐만 아니라, **ID Token(아이디 토큰)** 이라는 추가 결과물을 함께 발급해 줌.
  - ID Token은 서명 구조가 완벽한 **JWT(JSON Web Token)** 포맷으로 묶여 있으며, 까보면 그 안에 사용자의 이메일, 프로필(Claims), 발급자 서명, 만료 시간 등 완벽한 '신원 정보'가 들어 있어 완벽한 분산 환경 인증(SSO)이 성립됨.
- **장점**: SAML의 XML 대비 압도적으로 가벼운 JSON 포맷을 사용하여 모바일 네이티브 환경(iOS/Android)과 마이크로서비스(MSA) 백엔드 간 통신에서 최고의 성능을 발휘. (B2C 소셜 로그인의 100% 점유율).

### Ⅴ. 결론 및 실무적 판단 포인트
- 인프라 보안 아키텍트는 기업의 통합 계정 체계를 클라우드로 확장할 때, 기존 레거시 앱의 전환 비용을 고려해야 합니다. "사내망에 국한된 커버로스(Kerberos) $\rightarrow$ 클라우드 B2B 연동용 SAML 2.0 $\rightarrow$ 차세대 모바일 및 마이크로서비스 확장을 위한 OIDC"라는 순차적 브릿지(Bridge) 아키텍처를 설계하여 점진적으로 개방형 API 규약(OIDC/OAuth) 기반의 제로 트러스트 생태계로 진입해야 합니다.

### 💡 문제 유형별 목차 전환 포인트
- **[SAML, OAuth, OIDC 프로토콜의 개념 및 활용(연합 인증) 차이 비교]**: Ⅰ번과 Ⅴ번을 활용하여 3대 규약의 태생적 목적(인증 vs 인가)과 데이터 포맷(XML vs JSON)의 트레이드오프 차이점을 표/도식으로 명확히 비교 서술.
- **[서드파티 API 통제 및 모바일 환경에 적합한 인가/인증 모델 구축]**: 무거운 SAML의 Ⅱ번 한계를 지적하고, 이를 극복하는 Ⅲ번 OAuth의 '권한 위임' 개념과 Ⅳ번 OIDC의 'JWT 신분증명 결합' 메커니즘을 상세히 조명하여 최신 아키텍처 역량 과시.
