# 📖 【암기용】 개념 완전 이해

> 목적: SDP를 처음 보는 사람도 완벽히 이해하게 만든다. 시험 답안 양식이 아니라, 이해를 위한 친절한 설명이다.

## 한눈에
- **개요**: 인증 전에는 서비스를 보이지 않게 숨기고, 인증 후 최소 권한 경로만 여는 접속 보안 구조
- **왜 필요한가**: VPN은 접속 후 내부망 전체가 스캔 대상이 되기 쉽다. SDP는 사용자·단말 상태를 먼저 검증하고 허용된 애플리케이션만 노출한다.
- **핵심 직관**: 건물 정문을 열어 주는 방식이 아니라, 신원 확인 후 목적지 방으로 가는 전용 문만 잠깐 여는 방식이다.

## 깊이 이해
- **배경·문제의식**: 원격근무·SaaS·클라우드 확대로 경계 기반 방화벽만으로 내부 자산을 보호하기 어렵다. VPN 계정 탈취 시 내부 IP 대역 스캔, 횡이동, 미패치 서버 접근이 가능해진다.
- **작동 원리**: SDP Client가 SPA(Single Packet Authorization)로 Gateway 존재를 확인하고, Controller가 사용자 신원·MFA·단말 보안 상태·위치·시간을 평가한다. 조건을 만족하면 Gateway가 특정 애플리케이션으로 향하는 mTLS 세션과 정책을 생성한다.
- **비유**: 공항 라운지처럼 티켓·여권·탑승권을 확인한 뒤 해당 게이트만 열어 준다. 공항 전체 도면을 보여 주지 않고 필요한 통로만 안내한다.
- **구체 예시**: 개발자가 Git 서버에 접속할 때 IdP MFA, EDR 실행, 디스크 암호화, OS 패치 14일 이내 조건을 통과해야 TCP 443 경로가 8시간 동안 열린다.
- **흔한 오해·주의점**: SDP는 VPN 장비를 이름만 바꾼 제품이 아니다. 네트워크 접속 허용보다 애플리케이션 단위 접근, 선인증, 지속 검증, 기본 비노출이 핵심이다.

## 연결 개념
- ZTNA - SDP는 ZTNA 구현 패턴 중 하나이며, 신원 기반 최소 권한 접속을 제공한다.
- Zero Trust - 신뢰된 내부망 가정을 없애고 매 요청을 검증한다.
- SPA - Gateway를 인터넷 스캔에서 숨기는 선인증 패킷 기법이다.

# 📝 【답안용】 시험 답안 템플릿

> 목적: 시험장에서 25분에 그대로 쓰는 답안 양식. 작성방식(추상표현 금지·수치·도식·문제유형 전환)을 엄격히 지킨다.
> 핵심: SDP는 장비 기능 나열이 아니라 VPN 대비 공격면 축소, 신원·단말 상태 기반 접속 통제, ZTNA 적용 판단으로 답안을 구성한다.

## 핵심 인사이트 (3줄 요약)

> 1. **본질**: SDP는 인증 전 서비스 비노출, 인증 후 애플리케이션 단위 최소 권한 경로를 여는 Zero Trust 접속 아키텍처이다.
> 2. **가치**: 인터넷 스캔 노출면을 0개에 가깝게 줄이고, 계정 탈취 시에도 허용 앱 외 내부 IP 접근을 차단한다.
> 3. **판단 포인트**: Controller 정책, Gateway 배치, Client 단말 상태 수집, SPA·mTLS 적용 여부가 VPN 대체 가능성을 결정한다.

## 출제 의도 및 답안 포인트

| 출제 의도 | 반드시 짚을 핵심 | 감점 회피 포인트 |
|:---|:---|:---|
| 원격접속 보안 구조 이해 확인 | Controller, Gateway, Client, SPA, mTLS, IdP 연계 | VPN과 SDP를 단순 암호 터널로 동일시 |
| Zero Trust 적용 판단 확인 | 사용자 신원·단말 상태·애플리케이션 단위 권한 | 내부망 전체 접속 허용 구조 누락 |
| 운영 리스크 통제 확인 | 정책 실패, 단말 상태 오판, Gateway 병목, 로그 감사 | 인증만 쓰고 지속 검증·세션 만료 누락 |

> 요약: 이 문제는 SDP 구성요소 암기가 아니라 VPN 대비 공격면 축소와 ZTNA 운영 지표를 연결하는 판단을 요구한다.

## Ⅰ. 개요 및 필요성

- 개요: 인증 후 앱별 경로 개방 구조
- 배경: 원격근무와 클라우드 업무가 늘면서 내부망 전체를 여는 VPN은 계정 탈취 시 스캔·횡이동 경로가 됨
- 필요성: SDP는 SPA, Controller, Gateway, mTLS로 승인 앱만 노출하고 미인증 포트 응답 0개, 세션 TTL 8시간 이하 기준으로 운영해야 함

---

## Ⅱ. 구조 및 구성요소

```text
User/Device -> SDP Client -> Controller Policy Decision
                         +-> IdP/MFA + Device Posture
Controller -> Gateway Policy Push -> Private App Access -> Audit Log
```

| 구성요소 | 역할 | 특이사항 |
|:---|:---|:---|
| SDP Client | 사용자 인증 요청, 단말 상태 수집, mTLS 세션 생성 | EDR, OS 패치, 디스크 암호화 상태 전송 |
| Controller | 신원·단말·위치·시간 기반 정책 결정 | IdP, MFA, SIEM, CMDB 연계 |
| Gateway | 승인된 앱 경로만 프록시·중계 | 인터넷 스캔 차단, SPA 응답 |
| Policy Store | 역할·속성·위험 점수 기반 권한 저장 | RBAC, ABAC, 세션 TTL |
| Audit Log | 접속 승인·거부·세션 종료 기록 | SIEM 탐지, 감사 증적 |

> 요약: SDP는 Client가 상태를 제출하고 Controller가 정책을 결정하며 Gateway가 허용 앱만 노출하는 3계층 접속 구조이다.

---

## Ⅲ. 동작원리 및 흐름도

```text
접속 요청 -> SPA 전송 -> 신원/MFA 확인 -> 단말 상태 평가
-> 정책 결정 -> Gateway 경로 생성 -> 앱 접속 -> 로그/재평가
```

| 단계 | 처리 내용 | 검증 기준 |
|:---:|:---|:---|
| 1 | Client가 SPA 패킷으로 Gateway 존재 확인 | 미인증 패킷 무응답, 포트 비노출 |
| 2 | IdP·MFA로 사용자 신원 확인 | OIDC/SAML, FIDO2, MFA 성공 |
| 3 | 단말 상태와 위험 점수 평가 | EDR 실행, 패치 14일 이내, 루팅 미탐지 |
| 4 | Controller가 앱 단위 정책 결정 | RBAC/ABAC, 세션 TTL 4~8시간 |
| 5 | Gateway가 mTLS 경로 생성 후 로그 전송 | TLS 1.3, 접속 로그 1년 보관 |

> 요약: SDP는 선인증, 상태 평가, 정책 결정, 경로 생성, 로그 감사 순서로 접속을 통제한다.

## Ⅳ. 특징

| 구분 | VPN 중심 원격접속 | SDP 방식 | 수치·판단 포인트 |
|:---|:---|:---|:---|
| 노출 범위 | 접속 후 내부 대역 접근 가능 | 승인 앱만 노출 | 포트 스캔 응답 0개 목표 |
| 인증 기준 | 계정·비밀번호·MFA 중심 | 신원+단말 상태+위험 점수 | EDR, 패치, 위치 조건 |
| 권한 단위 | 네트워크 세그먼트 | 애플리케이션·API | 앱별 RBAC/ABAC |
| 운영 로그 | VPN 접속 성공/실패 중심 | 앱 세션·정책 판단 로그 | 사용자-앱-단말 3축 감사 |

> 요약: SDP는 네트워크 입장권을 주는 VPN과 달리 앱별 세션을 짧게 열고 지속 검증하는 구조이다.

## Ⅴ. 심화 비교 및 적용 판단

| 구분 | 기존/대안 | 본 키워드 | 선택 기준 |
|:---|:---|:---|:---|
| 구조 | VPN concentrator 중심 | Controller+Gateway 분리 | 앱별 접근통제와 멀티클라우드 연결 필요 시 |
| 비용/성능 | 전체 트래픽 터널링 | 앱 프록시·분산 Gateway | p95 접속 지연 300ms 이하, Gateway CPU 70% 이하 |
| 운영/위험 | 내부망 신뢰 전제 | 매 세션 정책 재평가 | 계정 탈취·단말 감염 대응 필요 시 |

> 요약: SDP는 내부망 접속보다 애플리케이션 접속을 보호해야 하는 원격·클라우드 환경에서 우선 검토한다.

| 리스크 | 원인 | 대응 방안 | 확인 지표 |
|:---|:---|:---|:---|
| 정책 오탐 | 단말 상태 수집 실패 | 예외 승인 워크플로, 24시간 임시 권한 | 거부율 3% 이하, 예외 건수 |
| Gateway 병목 | 특정 리전 집중 접속 | 리전별 Gateway 이중화, 헬스체크 | p95 지연 300ms 이하 |
| 우회 접속 | 직접 IP 노출 또는 Shadow IT | 방화벽 allowlist, DNS 통제, CASB 연계 | 미승인 접속 차단 로그 |

> 요약: SDP 운영 리스크는 정책 오탐, Gateway 병목, 직접 접속 우회이며 예외·이중화·노출면 점검으로 통제한다.

| 점검 항목 | 목표 기준 | 측정 방법 |
|:---|:---|:---|
| 접근통제 | 앱별 최소 권한, 세션 TTL 8시간 이하 | 정책 리뷰, IAM 로그 |
| 노출면 | 미인증 포트 응답 0개 | 외부 ASM, nmap 점검 |
| 운영 보안 | 접속 로그 1년 보관, MFA 적용률 100% | SIEM, 감사 리포트 |

> 요약: SDP 도입 성과는 포트 비노출, 앱별 최소 권한, 접속 감사로그 완전성으로 판단한다.

## Ⅵ. 실무 적용 및 결론

**적용 방안 3개 (필수 - 단계별 또는 항목별):**
1. IdP(OIDC/SAML)+MFA(FIDO2)+EDR 상태 수집을 Controller 정책에 묶고, 관리자 계정은 세션 TTL 4시간 이하로 설정함
2. Gateway를 업무 앱 리전별로 2대 이상 배치하고, 인터넷 직접 접근은 WAF·방화벽 allowlist로 차단함
3. SIEM에 사용자-단말-앱 로그를 수집해 실패율 3% 초과, 해외 IP, 비관리 단말 접속을 탐지 룰로 등록함

**결론 (2줄):**
- 기술사 판단: 내부망 전체 접속이 필요한 레거시 운영은 VPN 병행, SaaS·클라우드 앱 중심 업무는 SDP/ZTNA 우선 적용이 타당함
- 향후 방향: SDP는 SASE, CASB, EDR 신호와 결합해 신원·단말·행위 기반 접속 통제로 발전함
