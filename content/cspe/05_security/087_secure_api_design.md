## Ⅰ. 개요
| 항목 | 내용 |
|---|---|
| **정의** | API 통신의 인증·인가·무결성을 보장하기 위해 JWT 토큰, OAuth 2.0 위임, mTLS 상호 인증을 적용하는 설계 원칙임 |
| **배경/필요성** | 마이크로서비스 확산으로 API가 핵심 공격면이 되며, OWASP API Security Top 10 기준의 체계적 방어가 필요함 |
| **출제 의도** | JWT·OAuth·mTLS 각각의 역할과 조합 설계 능력을 평가함 |

## Ⅱ. 구성요소
```
+----------+     +----------+     +----------+
|   JWT    | --> |  OAuth   | --> |  mTLS    |
| (토큰)   |     | (인가위임)|     | (상호인증)|
+----------+     +----------+     +----------+
```

| 구성요소 | 설명 | 비유 |
|---|---|---|
| JWT | Header.Payload.Signature 구조의 자체 포함 토큰으로 무상태 인증을 제공함 | 신분증에 직인이 찍힌 통행증 |
| OAuth 2.0 | 리소스 소유자의 자격증명 노출 없이 제3자 앱에 제한된 접근 권한을 위임함 | 발렛파킹 전용 키 |
| mTLS | 클라이언트·서버 양측이 X.509 인증서로 상호 신원을 검증하는 TLS 확장임 | 양측 모두 신분증 제시 |

> 요약: JWT(토큰 기반 인증), OAuth(권한 위임), mTLS(상호 인증)를 조합하여 API를 보호함.

## Ⅲ. 절차
```
+------------+     +------------+
| 클라이언트  | --> | 인증서버   |
| 자격증명   |     | 토큰발급   |
+------------+     +------------+
                        |
+------------+     +----+-------+
| 리소스     | <-- | JWT검증   |
| 응답반환   |     | 권한확인   |
+------------+     +------------+
```

1. 인증 요청: 클라이언트가 자격증명(ID/PW 또는 Client Cert)으로 인증 서버에 토큰을 요청함
2. 토큰 발급: 인증 서버가 OAuth 흐름을 거쳐 Access Token(JWT)을 발급함
3. API 호출: 클라이언트가 `Authorization: Bearer <JWT>` 헤더와 함께 API를 호출함
4. 검증·응답: API 게이트웨이가 JWT 서명·만료·스코프를 검증한 후 리소스를 반환함

> 요약: 자격증명 → 토큰 발급 → Bearer 전송 → 검증·응답으로 무상태 API 인증이 수행됨.

## Ⅳ. 문제점
- JWT 탈취 위험: 토큰이 유출되면 만료 시까지 무효화가 어려움(무상태 특성)
- OAuth 설정 오류: Redirect URI 미검증·PKCE 미적용 시 Authorization Code 탈취 가능함
- 인증서 관리 부담: mTLS 환경에서 클라이언트 인증서의 발급·갱신·폐기 관리가 복잡함

## Ⅴ. 개선방안
- (단기) 짧은 만료·Refresh Token: Access Token 수명을 15분 이내로 제한하고 Refresh Token으로 갱신함
- (중기) PKCE 필수 적용: OAuth 공개 클라이언트에 PKCE(Proof Key for Code Exchange)를 강제함
- (장기) SPIFFE/SPIRE 자동화: 서비스 신원 프레임워크로 mTLS 인증서 생명주기를 자동 관리함

## Ⅵ. 전망
- API 게이트웨이에 AI 기반 이상 요청 탐지가 통합되고, SPIFFE 표준 기반 서비스 메시 인증이 제로 트러스트 API 보안의 핵심 축이 될 전망임
