## 미리 알고가기

- JWT는 API가 요청 주체를 확인할 때 쓰는 서명된 토큰 형식이고, OAuth 2.0은 권한 위임 절차이며, mTLS는 통신 양쪽이 인증서를 확인하는 방식임
- 세 기술은 경쟁 관계가 아니라 API 인증과 권한과 통신 신뢰를 서로 다른 층에서 보완함
- 안전한 API 설계는 토큰 도입보다 권한 범위와 만료와 서비스 간 신뢰 기준을 분명히 하는 데서 시작함

## Ⅰ. 개요

- **정의/개념**: 보안 API 설계는 호출 주체 확인, 권한 범위 제한, 전송 경로 보호, 서비스 간 신뢰를 함께 설계하는 방식임
- **배경/필요성**: API가 핵심 공격면이 되면서 단순 토큰 검증만으로는 과다 권한, 토큰 탈취, 내부 서비스 위조를 막기 어려움

## Ⅱ. 특징

- JWT는 무상태 검증에 유리하지만 탈취 시 만료 전 재사용 위험이 있음
- OAuth 2.0은 사용자 자격 증명 공유 없이 위임 범위를 제어함
- mTLS는 서비스 간 통신 신원을 강하게 보장하지만 인증서 운영이 필요함
- 안전한 설계는 토큰 형식보다 권한 범위, 회전, 폐기, 로그 추적에 좌우됨

## Ⅲ. 종류 및 비교

| 판단 기준 | JWT | OAuth 2.0 | mTLS |
|:---|:---|:---|
| 주된 역할 | 토큰 기반 요청자 식별 | 권한 위임과 토큰 발급 절차 | 통신 주체 상호 인증 |
| 적용 구간 | API 요청 헤더 | 사용자·클라이언트 권한 부여 흐름 | 서비스 간 또는 민감 API 채널 |
| 강점 | 검증이 빠르고 분산 환경에 적합 | 세밀한 권한 범위와 위임 관리 가능 | 강한 기기·서비스 신뢰 확보 |
| 유의점 | 만료, 재발급, 서명키 관리 필요 | 리디렉션과 스코프 설정 오류 주의 | 인증서 발급·갱신·폐기 체계 필요 |

## Ⅳ. 구성요소 및 구조

| 구성요소 | 설명 |
|:---|:---|
| 인증 서버 | 토큰 발급과 클라이언트 검증을 담당함 |
| 토큰과 스코프 | 요청 주체와 권한 범위를 담음 |
| API 자원 서버 | 토큰과 권한을 검증해 요청을 허용함 |
| 서비스 간 신뢰 | mTLS나 서비스 신원 체계로 내부 호출을 검증함 |

```text
주체 인증 -> 토큰 발급/위임 -> API 요청 -> 토큰/권한 검증 -> 필요 시 mTLS로 상호 인증
```

## Ⅴ. 원리 및 절차 흐름도

```text
클라이언트 등록 -> 인증/위임 -> 토큰 수령 -> API 호출 -> 토큰/스코프/mTLS 검증 -> 응답
```

1. **클라이언트 등록**: 누가 어떤 API를 쓸지 식별자를 부여함
2. **인증과 위임**: 사용자나 서비스가 필요한 권한을 승인받음
3. **토큰 수령**: 제한된 범위와 만료 시간을 가진 토큰을 받음
4. **API 호출**: 토큰과 필요 시 인증서로 요청을 보냄
5. **검증과 기록**: 서명과 스코프와 상호 인증 상태를 확인하고 로그를 남김

## Ⅵ. 실무 적용 및 유의점

1. 외부 공개 API는 OAuth 2.0 위임과 짧은 JWT를 기본으로 두고 과다 권한 토큰 부재·만료·폐기 정책 준수 여부로 확인함
2. 내부 API는 mTLS나 서비스 신원 체계로 상호 인증하고 비인가 서비스 호출 차단 여부·인증서 수명 관리 자동화로 확인함

## Ⅶ. 결론

- 보안 API 설계는 JWT 도입이 아니라 권한 위임, 토큰 운영, 서비스 신뢰를 역할별로 나눠 설계하는 문제임
