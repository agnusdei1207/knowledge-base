## 미리 알고가기

- 입력값 검증은 들어온 값이 형식과 길이와 범위에 맞는지 확인하는 절차임
- 파라미터 바인딩은 SQL이나 명령 문자열 안에 값을 직접 붙이지 않고 데이터로 분리해 전달하는 방식임
- 검증은 허용 범위를 줄이고, 바인딩은 해석 구조를 분리하므로 둘은 역할이 다르지만 함께 써야 함

## Ⅰ. 개요

- **정의/개념**: 입력값 검증·파라미터 바인딩은 외부 입력을 허용된 형식으로 제한하고, SQL이나 명령 실행 시 구문과 데이터를 분리해 인젝션과 로직 우회를 막는 기본 방어 원칙임
- **배경/필요성**: 웹과 API는 모든 기능이 외부 입력에서 시작되므로 잘못된 값이 그대로 해석되면 SQL 인젝션, 명령어 인젝션, 경로 조작, 과도한 조회가 쉽게 발생해 서버 측 기준이 필요함

## Ⅱ. 특징

- 클라이언트 검증은 편의 기능일 뿐 최종 판단은 서버가 해야 함
- 허용 목록 기반 검증이 금지 목록보다 안정적임
- 파라미터 바인딩은 SQL 구조 변조를 막는 핵심 수단이지만 동적 컬럼명이나 정렬 조건은 별도 통제가 필요함
- ORM을 써도 raw query나 문자열 결합이 남아 있으면 취약점이 재발함

## Ⅲ. 종류 및 비교

| 판단 기준 | 입력값 검증 | 파라미터 바인딩 |
|:---|:---|:---|
| 목적 | 값의 형식과 범위를 제한 | 구문과 데이터를 분리 |
| 적용 위치 | API 입력, 폼, 헤더, 파일명 등 | SQL, 명령 실행, 검색 조건 등 |
| 막는 대표 문제 | 잘못된 형식, 우회 입력, 과도한 길이 | SQL 인젝션, 명령어 조작 |
| 한계 | 구조 변조를 완전히 막지 못함 | 값 자체의 업무 규칙 적합성은 따로 검증해야 함 |

## Ⅳ. 구성요소 및 구조

| 구성요소 | 설명 |
|:---|:---|
| 허용 규칙 | 타입, 길이, 범위, 패턴 기준을 정함 |
| 서버 측 검증 | 요청 본문과 파라미터와 헤더를 검사함 |
| 안전 실행 인터페이스 | Prepared Statement, Query Builder 같은 바인딩 API를 사용함 |
| 예외와 로깅 | 차단된 입력과 예외 처리 결과를 남겨 재발을 확인함 |

```text
외부 입력 -> 서버 검증 -> 안전한 실행 인터페이스 사용 -> 결과 반환 -> 차단 로그 확인
```

## Ⅴ. 원리 및 절차 흐름도

```text
입력 수신 -> 형식/범위 검증 -> 정규화 -> 파라미터 바인딩 -> 실행 -> 재검증
```

1. **입력 수신**: 파라미터와 본문과 헤더 값을 받음
2. **형식 검증**: 길이와 타입과 허용 패턴을 확인함
3. **정규화**: 인코딩과 공백과 케이스를 일관되게 맞춤
4. **바인딩 실행**: SQL이나 명령 구문과 데이터를 분리해 실행함
5. **재검증**: 우회 입력이 더 이상 구조를 바꾸지 못하는지 확인함

## Ⅵ. 실무 적용 및 유의점

1. 웹과 API 서비스는 서버 측 허용 목록 검증과 Prepared Statement를 기본 규칙으로 묶고, 문자열 결합 쿼리 제거와 공통 검증 모듈 적용을 함께 진행한 뒤 대표 인젝션 페이로드 재현 여부와 문자열 결합 쿼리 제거 상태로 확인함
2. 검색과 정렬 기능이 많은 서비스는 바인딩만으로 안전하다고 보지 말고 컬럼명과 정렬 방향도 허용 목록으로 제한한 뒤 비허용 필드 차단 여부와 회귀 테스트 결과로 확인함

## Ⅶ. 결론

- 입력값 검증과 파라미터 바인딩은 같은 방어가 아니라 서로 다른 실패 지점을 막는 기본 통제이므로 둘을 함께 적용해야 인젝션과 우회 입력을 줄일 수 있음
