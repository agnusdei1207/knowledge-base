## Ⅰ. 개요
| 항목 | 내용 |
|---|---|
| **정의** | 외부 입력 데이터의 유효성을 서버측에서 검증하고, SQL·명령어 실행 시 파라미터 바인딩으로 인젝션을 원천 차단하는 방어 기법임 |
| **배경/필요성** | OWASP Top 10 1위(인젝션)의 근본 원인이 입력값 미검증이며, 파라미터 바인딩은 SQL 인젝션의 완전한 방어책임 |
| **출제 의도** | 화이트리스트 검증과 Prepared Statement의 동작 원리를 이해하는지 평가함 |

## Ⅱ. 구성요소
```
+----------+     +----------+     +----------+
| 입력검증  | --> | 정규화   | --> | 파라미터  |
| (Validate)|     | (Sanitize)|    | 바인딩   |
+----------+     +----------+     +----------+
```

| 구성요소 | 설명 | 비유 |
|---|---|---|
| 입력 검증 | 화이트리스트 기반으로 허용된 문자·길이·형식만 통과시킴 | 출입문 신분증 대조 |
| 정규화 | 입력값의 인코딩 통일(UTF-8)·특수문자 이스케이프를 수행함 | 여권 번역 공증 |
| 파라미터 바인딩 | SQL 구문과 데이터를 분리하여 Prepared Statement로 실행함 | 주문서 양식과 기입 내용 분리 |

> 요약: 검증(필터) → 정규화(통일) → 바인딩(구문·데이터 분리)으로 인젝션을 차단함.

## Ⅲ. 절차
```
+------------+     +------------+
| 클라이언트  | --> | 서버측     |
| 입력전송   |     | 검증수행   |
+------------+     +------------+
                        |
+------------+     +----+-------+
| 안전한     | <-- | Prepared  |
| 쿼리실행   |     | Statement |
+------------+     +------------+
```

1. 입력 수신: 클라이언트로부터 HTTP 파라미터·헤더·쿠키 등 외부 데이터를 수신함
2. 서버측 검증: 화이트리스트(허용 패턴) 기반으로 타입·길이·범위를 서버에서 검증함
3. 정규화 처리: 멀티바이트 인코딩·HTML 엔티티·URL 인코딩을 통일하여 우회를 방지함
4. 바인딩 실행: Prepared Statement의 플레이스홀더(`?`)에 검증된 값을 바인딩하여 쿼리를 실행함

> 요약: 수신 → 서버 검증 → 정규화 → 바인딩 실행으로 입력 기반 공격을 차단함.

## Ⅳ. 문제점
- 클라이언트 검증 의존: JavaScript 검증만 수행하고 서버측 검증을 누락하는 사례가 빈발함
- 블랙리스트 한계: 금지 패턴 기반 필터는 인코딩 우회(더블 URL 인코딩 등)에 취약함
- ORM 오용: ORM 사용 시에도 Raw Query를 혼용하면 인젝션 취약점이 재발함

## Ⅴ. 개선방안
- (단기) 서버측 화이트리스트 강제: 클라이언트 검증과 무관하게 서버에서 독립 검증을 수행함
- (중기) ORM 전환: Raw SQL을 제거하고 ORM의 Query Builder만 사용하도록 코딩 가이드를 적용함
- (장기) WAF·RASP 연동: 런타임 레벨에서 비정상 쿼리 패턴을 실시간 탐지·차단함

## Ⅵ. 전망
- Prepared Statement 기본 사용이 프레임워크 표준으로 정착되며, RASP(Runtime Application Self-Protection)가 최후 방어선으로 확산될 전망임
