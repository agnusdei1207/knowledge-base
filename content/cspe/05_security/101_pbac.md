## Ⅰ. 개요
| 항목 | 내용 |
|---|---|
| **정의** | 조직의 비즈니스 규칙을 선언적 정책 언어(Rego·Cedar 등)로 정의하고, 정책 엔진이 런타임에 접근 허가를 동적 결정하는 접근 제어 모델임 |
| **배경/필요성** | RBAC의 정적 역할·ABAC의 정책 복잡성을 통합 관리하기 위해 코드로 정의 가능한 정책 엔진 기반 접근 제어가 필요함 |
| **출제 의도** | PBAC의 정책 엔진(OPA) 아키텍처와 RBAC·ABAC과의 관계를 이해하는지 평가함 |

## Ⅱ. 구성요소
```
+----------+     +----------+     +----------+
|   PAP    | --> |   PDP    | --> |   PEP    |
| (정책관리)|     | (정책엔진)|     | (집행점) |
+----------+     +----------+     +----------+
```

| 구성요소 | 설명 | 비유 |
|---|---|---|
| PAP | 정책을 작성·배포·버전 관리하는 관리 포인트임 | 법률 제정 기관 |
| PDP(정책 엔진) | OPA·Cedar 등이 정책 규칙을 평가하여 Permit/Deny를 반환함 | 재판관(판결) |
| PEP | API 게이트웨이·미들웨어에서 PDP 결정을 강제 적용함 | 경찰(판결 집행) |

> 요약: PAP(정책 정의) → PDP(평가·결정) → PEP(집행)으로 선언적 정책 기반 접근 제어를 수행함.

## Ⅲ. 절차
```
+------------+     +------------+
| 정책작성   | --> | 정책배포   |
| (Rego코드) |     | (번들배포) |
+------------+     +------------+
                        |
+------------+     +----+-------+
| PEP집행   | <-- | PDP평가   |
| 허가/거부  |     | (런타임)  |
+------------+     +------------+
```

1. 정책 작성: 보안팀이 Rego·Cedar 등 선언적 언어로 접근 제어 규칙을 코드로 작성함
2. 정책 배포: Git 기반 버전 관리를 거쳐 OPA 에이전트에 번들 형태로 배포함
3. PDP 런타임 평가: 접근 요청 시 PDP가 주체·객체·환경 속성과 정책을 대조하여 결정함
4. PEP 결정 집행: 사이드카·미들웨어가 PDP 결정을 적용하여 요청을 허가·거부함

> 요약: 코드로 작성 → 번들 배포 → 런타임 평가 → 집행으로 Policy as Code를 구현함.

## Ⅳ. 문제점
- 정책 학습 곡선: Rego·Cedar 등 전용 언어의 학습이 필요하여 도입 초기 부담이 큼
- 성능 오버헤드: 복잡한 정책 평가 시 마이크로초 단위의 지연이 누적될 수 있음
- 정책 테스트 부족: 정책 변경의 영향을 사전 검증하는 테스트 프레임워크가 미성숙함

## Ⅴ. 개선방안
- (단기) 정책 템플릿: 자주 사용되는 패턴을 템플릿화하여 학습 부담을 줄임
- (중기) 부분 평가 캐싱: OPA의 Partial Evaluation으로 불변 조건을 사전 컴파일하여 평가 속도를 개선함
- (장기) 정책 CI/CD: 정책 변경에 대한 자동 테스트·시뮬레이션·롤백 파이프라인을 구축함

## Ⅵ. 전망
- Kubernetes·서비스 메시 환경에서 OPA/Gatekeeper가 사실상 표준이 되며, Policy as Code가 DevSecOps의 핵심 실천으로 자리잡을 전망임
