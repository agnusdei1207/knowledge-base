## 미리 알고가기

- PBAC는 접근 규칙을 코드나 선언형 정책 문서로 만들어 중앙 정책 엔진이 평가하게 하는 방식임
- RBAC나 ABAC의 개념을 버리는 것이 아니라, 그 규칙을 정책으로 분리해 일관되게 운영하려는 모델에 가깝다
- 핵심은 애플리케이션 안에 흩어진 권한 로직을 정책 계층으로 끌어내는 데 있음

## Ⅰ. 개요

- **정의/개념**: PBAC는 접근 제어 규칙을 애플리케이션 코드와 분리된 정책으로 정의하고, 정책 엔진이 요청 시점에 이를 평가해 허가와 거부를 결정하는 접근 제어 방식임
- **배경/필요성**: 서비스 수가 늘수록 각 애플리케이션에 권한 로직이 흩어져 일관성과 감사 가능성이 떨어지므로, 정책을 중앙에서 관리하고 재사용할 구조가 필요함

## Ⅱ. 특징

- 정책 변경을 코드 수정 없이 별도로 관리할 수 있음
- RBAC와 ABAC 규칙을 같은 엔진 아래 통합하기 쉬움
- 버전 관리와 테스트와 배포 절차를 갖추면 감사와 변경 추적성이 좋아짐
- 정책 표현이 강력한 만큼 복잡해지기 쉬워 테스트 자동화가 필수임

## Ⅲ. 종류 및 비교

| 판단 기준 | 애플리케이션 내 하드코딩 권한 | PBAC |
|:---|:---|:---|
| 정책 위치 | 서비스 코드 내부 | 외부 정책 엔진/정책 저장소 |
| 장점 | 단순한 서비스는 구현이 빠름 | 중앙 일관성, 재사용, 감사가 쉬움 |
| 한계 | 서비스마다 규칙이 달라지기 쉬움 | 정책 언어와 배포 체계 학습이 필요함 |
| 적합 환경 | 소규모 단일 서비스 | 마이크로서비스, API 플랫폼, 클라우드 환경 |

## Ⅳ. 구성요소 및 구조

| 구성요소 | 설명 |
|:---|:---|
| Policy Administration Point | 정책 작성과 승인과 버전 관리를 담당함 |
| Policy Decision Point | 요청을 받아 정책을 평가하고 허가 여부를 결정함 |
| Policy Enforcement Point | 결정 결과를 실제 요청에 집행함 |
| Attributes and Context | 사용자와 자원과 환경 정보를 정책 평가에 제공함 |

```text
정책 작성/배포 -> 요청 수신 -> 속성 조회 -> 정책 평가 -> 허가/거부 집행
```

## Ⅴ. 원리 및 절차 흐름도

```text
정책 정의 -> 저장소 배포 -> 요청 인터셉트 -> 엔진 평가 -> 결과 집행 -> 로그와 테스트 갱신
```

1. **정책 정의**: 허용 규칙과 금지 규칙과 예외 기준을 작성함
2. **정책 배포**: 승인된 정책을 엔진에 배포함
3. **요청 인터셉트**: 게이트웨이나 미들웨어가 요청을 가로챔
4. **엔진 평가**: 속성과 정책을 비교해 결과를 만듦
5. **집행과 기록**: 결과를 적용하고 추후 감사용 로그를 남김

## Ⅵ. 실무 적용 및 유의점

1. 마이크로서비스와 쿠버네티스 환경은 권한 로직을 서비스마다 복제하지 말고 PBAC로 중앙화하고 정책 테스트와 롤백 절차를 함께 운영한 뒤 서비스별 권한 편차 감소와 정책 배포 후 장애·오탐 건수로 확인함
2. PBAC 도입 초기에 모든 규칙을 한 번에 옮기면 복잡성만 커지므로 고위험 API부터 전환하고 코드 내부 권한 로직 축소 여부와 정책 변경 추적 가능성으로 확인함

## Ⅶ. 결론

- PBAC는 권한 규칙을 정책 계층으로 분리해 일관성과 감사 가능성을 높이는 방식이므로 정책 테스트와 배포 체계를 함께 가져가야 함
