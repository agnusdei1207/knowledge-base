## Ⅰ. 개요
- **정의**: 공격자 관점에서 시스템의 취약점을 실제 공격 기법으로 검증하는 보안 테스트
- **배경/필요성**: 자동 스캔만으로는 발견할 수 없는 논리적 취약점과 공격 체인을 검증할 수단이 필요함
- **비유**: 도둑 역할을 고용하여 실제로 건물 침입을 시도해 보안 허점을 찾는 것

| 출제 의도 | 반드시 짚을 핵심 | 감점 회피 포인트 |
|:---|:---|:---|
| 테스트 절차·유형·산출물 | Black/White/Gray Box 구분, 공격 체인 | 스캐닝과의 차이, 법적 근거 언급 필요 |

> 요약: 실제 공격을 모사하여 방어 체계의 실효성을 검증하는 테스트임

## Ⅱ. 구성요소
```text
+-----------+     +----------+     +---------+     +--------+
| Scope     | --> | Recon    | --> | Exploit | --> | Report |
| Definition|     | & Enum   |     | & Post  |     |        |
+-----------+     +----------+     +---------+     +--------+
```

| 구성요소 | 설명 | 비유 |
|:---|:---|:---|
| 범위 정의(Scope) | 테스트 대상·제약 조건을 사전 합의 | 훈련 구역 지정 |
| 정찰·열거(Recon) | 대상 시스템의 정보 수집 및 공격면 파악 | 건물 외부 답사 |
| 익스플로잇(Exploit) | 취약점을 실제 공격하여 침투 가능 여부 검증 | 잠금장치 해제 시도 |

> 요약: 범위 합의-정찰-공격-보고의 구성요소로 테스트를 체계화함

## Ⅲ. 절차
```text
범위 합의 -> 정보 수집 -> 취약점 공격 -> 보고서 작성
```
- 1단계: 고객과 테스트 범위·규칙·일정을 합의(RoE 수립)
- 2단계: OSINT·포트 스캔·서비스 열거로 대상 정보 수집
- 3단계: 발견된 취약점에 대해 익스플로잇 실행 및 권한 상승 시도
- 4단계: 발견 사항·증거·위험도·개선 권고를 포함한 보고서 작성

> 요약: RoE 수립부터 보고서까지 4단계로 구성된 공격 모사 절차임

## Ⅳ. 문제점
- 시점 한정성: 특정 시점의 스냅샷 — 이후 발생하는 취약점은 탐지 불가
- 범위 제약: RoE로 제한된 범위 — 실제 공격자의 무제한 접근과 차이 존재
- 인력 의존성: 테스터 역량에 결과 품질이 좌우 — 일관성 확보 어려움

> 요약: 시점 한정·범위 제약·인력 의존이 테스트 결과의 완전성을 제한함

## Ⅴ. 개선방안
1. 단기: 정기 테스트 주기를 단축하고 주요 변경 시 추가 테스트 수행
2. 중기: 자동화 공격 시뮬레이션(BAS) 도구를 병행하여 범위 확장
3. 장기: 상시 레드팀 운영으로 지속적 공격 검증 체계 구축

> 요약: 주기 단축·BAS 병행·상시 레드팀으로 테스트 한계를 보완함

## Ⅵ. 전망
- 발전 방향: AI 기반 자동 침투 도구와 상시 침투 테스트 체계가 확산될 것임
- 기술사적 판단: 컴플라이언스와 실효적 보안 검증의 교차점에서 중요성이 지속됨
- 기술사 제언: BAS와 수동 침투 테스트를 결합한 하이브리드 검증 체계 수립을 제언함
