## 1. 한눈에 이해하기 (Core Intuition)
- **정의**: 두 사용자가 안전하지 않은 공개 통신망을 통해 안전하게 '대칭키(비밀키)'를 공유할 수 있게 해주는 암호학적 키 교환 알고리즘입니다.
- **필요성**: 만나서 열쇠를 건네주지 않고도, 인터넷상에서 각자의 정보를 조금씩 주고받아 둘만 아는 완벽히 똑같은 열쇠를 조립해 내기 위해 필요합니다.
- **핵심 직관**: **"물감 섞기 비유"**. 
  1. 노란색(공통 색)을 앨리스와 밥이 공유합니다.
  2. 각자 자신만의 비밀 색(빨강, 파랑)을 섞어 주황색, 초록색을 만듭니다.
  3. 주황색과 초록색을 서로 교환합니다. (해커가 중간에 가로채도, 섞인 색에서 비밀 색을 분리해 낼 수 없습니다.)
  4. 받은 색에 다시 자신의 비밀 색을 섞으면, 둘 다 **'노랑+빨강+파랑'이 섞인 동일한 갈색(비밀키)** 을 얻게 됩니다.

## 2. 왜 중요한가? (Background & Value)
- **등장 배경**: 1976년, 휘트필드 디피와 마틴 헬만이 발표하여 **최초로 '키 분배(Key Distribution) 문제'를 해결**한 암호학 역사상 가장 위대한 논문("New Directions in Cryptography")의 결과물입니다. 
- **가치**: 이 기술 덕분에 인류는 택배로 열쇠를 보내지 않고도, 웹 브라우저 접속 즉시 안전한 HTTPS 통신 세션을 맺을 수 있게 되었습니다. 

## 3. 어떻게 작동하는가? (Mechanism)
- **수학적 난제**: **이산대수 문제 (Discrete Logarithm Problem)**. $y = g^x \pmod p$ 에서 $g, x, p$를 알면 $y$를 구하기는 쉽지만, 반대로 $y, g, p$만 주어졌을 때 지수 $x$를 알아내는 것은 계산적으로 불가능하다는 성질을 이용합니다.
- **작동 원리 (Step-by-Step)**:
  1. 앨리스와 밥은 소수 $p$와 생성자 $g$를 공개적으로 합의합니다. (해커도 앎)
  2. 앨리스는 자신만의 비밀 숫자 $a$를 고르고, $A = g^a \pmod p$를 계산해 밥에게 보냅니다.
  3. 밥도 자신만의 비밀 숫자 $b$를 고르고, $B = g^b \pmod p$를 계산해 앨리스에게 보냅니다.
  4. 앨리스는 밥에게 받은 $B$에 자신의 비밀 $a$를 제곱합니다: $K = B^a \pmod p$
  5. 밥도 앨리스에게 받은 $A$에 자신의 비밀 $b$를 제곱합니다: $K = A^b \pmod p$
  6. 결과적으로 둘 다 $K = g^{ab} \pmod p$ 라는 동일한 비밀키를 획득합니다. 해커는 $A, B, p, g$를 모두 가로챘지만, $a$나 $b$를 모르기 때문에 $K$를 계산할 수 없습니다.

## 4. 실전 활용 및 예시 (Real-world Application)
- **구체적 사례**: 
  - **TLS/HTTPS (DHE, ECDHE)**: 우리가 웹사이트에 접속할 때마다 보이지 않는 곳에서 브라우저와 서버가 서로 난수를 생성하여 Diffie-Hellman 수학 연산을 수행해 세션키를 만듭니다.
  - **IPsec VPN (IKE 프로토콜)**: 인터넷 구간을 통해 가상 사설망을 연결할 때, 터널 암호화에 사용할 키를 교환하는 표준 방식입니다.
- **주의점 및 흔한 오해**: 
  - DH 알고리즘은 **'인증(Authentication)' 기능이 없습니다**. 즉, 상대방이 정말 앨리스인지 밥인지 신원을 확인하지 않습니다. 따라서 신분 위장을 통한 **중간자 공격(MITM)** 에 완전히 취약합니다. 이를 막기 위해 반드시 RSA/ECDSA 전자서명(인증서)과 결합하여 사용해야 합니다.

## 5. 핵심 비교 및 연결 개념 (Relation)
- **VS RSA**: RSA는 공개키로 암호화해서 전달하는 '키 전달(Key Transport)' 방식이고, DH는 서로 연산하여 키를 '합의(Key Agreement)'하는 방식입니다.
- **연결 개념**: 
  - **PFS (Perfect Forward Secrecy, 완전 순방향 안전성)**: 키 교환을 할 때마다 매번 새로운 $a, b$ 난수를 쓰는 방식(DHE, Ephemeral DH). 서버의 고정키가 털려도 과거의 통신 내역은 안전합니다.

# ✍️ 단답형 / 서술형 시험장 출격 준비

### Ⅰ. 핵심 인사이트
- **본질**: 이산대수 문제(DLP)의 연산 비대칭성을 활용하여, 안전하지 않은 채널에서 대칭키를 공동 생성(Key Agreement)하는 암호학적 프로토콜.
- **가치**: 대칭키 암호의 고질적 한계였던 O(N²) 키 분배 문제를 해결하고, 공개키 암호학(Public-Key Cryptography)의 시대를 연 최초의 실용적 알고리즘.
- **판단 포인트**: 중간자 공격(MITM)에 근본적으로 취약하므로 단독 사용은 금지되며, 반드시 인증(Authentication)이 결합된 프로토콜(TLS, IKE 등) 내에서 운용되어야 함.

### Ⅱ. DH 알고리즘의 수학적 원리 및 도식화
**1. 기본 파라미터 합의**
- $p$: 매우 큰 소수 (Prime Number)
- $g$: 소수 $p$에 대한 원시근 (Primitive Root, Generator)
- $p, g$는 평문으로 네트워크에 공개됨 (공격자 도청 가능).

**2. 키 교환 메커니즘 (Key Exchange)**
```ascii
      [ Alice ]                                [ Bob ]
  비밀 난수 a 생성                         비밀 난수 b 생성
         │                                       │
  A = g^a mod p                           B = g^b mod p
         │               공개 채널               │
         ├───────────────── A ──────────────────▶│
         │◀──────────────── B ──────────────────┤
         │                                       │
  K = B^a mod p                           K = A^b mod p
  (= (g^b)^a mod p)                       (= (g^a)^b mod p)
         │                                       │
         ▼                                       ▼
    Shared Secret (K)                       Shared Secret (K)
```

### Ⅲ. DH 알고리즘의 발전 형태 및 PFS 체계
**1. Static DH (고정 DH)**
- 서버나 사용자가 고정된 비밀키 $a$나 $b$를 인증서에 박아두고 계속 재사용하는 방식.
- 서버의 비밀키가 유출되면 과거에 캡처해둔 트래픽도 모두 복호화되는 치명적 단점 존재.

**2. Ephemeral DH (DHE, 일회성 DH)**
- 통신 세션을 맺을 때마다 새로운 난수 $a, b$를 생성하여 키 합의를 수행하고 즉시 폐기.
- **완전 순방향 안전성 (PFS, Perfect Forward Secrecy)** 보장: 미래에 장기 키가 유출되어도 과거의 세션키 $K$를 역산할 수 없음.
- TLS 1.2의 주요 암호 스위트로 채택됨 (예: `TLS_DHE_RSA_WITH_AES_256_GCM_SHA384`).

**3. Elliptic Curve DH (ECDH, 타원곡선 DH)**
- DH 알고리즘의 기반을 이산대수(DLP)에서 타원곡선 이산대수(ECDLP)로 변경.
- 더 짧은 키(256bit)로 RSA 3072bit 수준의 강력한 보안과 빠른 연산 속도 제공.
- 현재 TLS 1.3에서 **ECDHE**가 사실상 유일한 표준 키 교환 방식으로 강제됨.

### Ⅳ. 취약점 및 보안 대응 방안
1. **중간자 공격 (Man-In-The-Middle, MITM) 취약성**
   - **이슈**: 공격자(Mallory)가 중간에 개입하여 앨리스와 밥 각각에게 자신과 통신하도록 속여 각각 다른 $K_1, K_2$를 합의하게 만듦 (앨리스 ↔ $K_1$ ↔ 공격자 ↔ $K_2$ ↔ 밥). 상대방 인증 부재가 원인.
   - **대응**: **STS (Station-to-Station) 프로토콜** 적용. 교환하는 $A, B$ 값에 대해 자신의 RSA 또는 ECDSA 개인키로 **전자서명(Digital Signature)** 을 첨부하여 상대방 신원 인증.
2. **Logjam 공격 / Downgrade Attack**
   - **이슈**: 서버가 약한 512비트 수준의 소수 $p$를 허용하도록 유도한 뒤, 사전 계산(Precomputation)을 통해 실시간으로 이산대수를 풀어 세션키를 탈취하는 공격.
   - **대응**: $p$의 크기를 최소 2048비트 이상으로 강제. 안전성이 입증된 타원곡선 기반의 ECDHE로 전환.

### Ⅴ. 실무 아키텍처 적용 (TLS 1.3 관점)
- TLS 1.3은 RSA를 이용한 '키 전달(Key Transport)'을 완전히 폐지하고, 오직 **(EC)DHE를 통한 키 합의(Key Agreement)** 만을 강제함.
- 그 이유는 오로지 'PFS(완전 순방향 안전성)'를 아키텍처 수준에서 강제하기 위함임.
- 암호 스위트 구성 시 키 교환 영역(ECDHE), 서명 인증 영역(RSA/ECDSA), 대칭키 암호 영역(AES-GCM/ChaCha20)을 역할에 맞게 완벽히 분리 적용.

### 💡 문제 유형별 목차 전환 포인트
- **[TLS 1.3 및 PFS 관련 문제]**: Ⅲ번의 Ephemeral DH(DHE) 특성을 Ⅴ번의 TLS 1.3 아키텍처와 결합하여, 왜 RSA 키 교환이 폐지되고 DHE가 표준이 되었는지 서술.
- **[중간자 공격 및 인증 결여 취약점]**: Ⅳ번 항목을 강조하며, STS 프로토콜이나 PKI 기반 전자서명(인증서)과의 결합 필수성을 구조도로 명확히 제시.
