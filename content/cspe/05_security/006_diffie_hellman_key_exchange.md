# 📖 【암기용】 개념 완전 이해

> 목적: 디피-헬만 키 교환을 처음 봐도 완전하게 이해하게 만든다. 시험 답안 양식이 아니라, 이해를 위한 설명이다.

## 한눈에
- **개요**: 공개 채널에서 두 당사자가 동일한 세션키를 만드는 키 합의 방식
- **왜 필요한가**: 암호화 통신은 양쪽이 같은 대칭키를 알아야 하지만, 네트워크로 키를 그대로 보내면 도청자가 키를 얻는다. DH는 비밀값을 직접 보내지 않고도 공통 비밀을 계산하게 한다.
- **핵심 직관**: 각자 비밀 색을 공개 색에 섞어 보내고, 상대 결과에 자기 비밀을 다시 섞으면 양쪽만 같은 최종 색을 얻는 구조이다.

## 깊이 이해
- **배경·문제의식**: 대칭키는 AES-256처럼 대량 데이터 암호화에 적합하지만, 최초 키 전달 문제가 있다. DH는 이산로그 문제의 계산 난이도를 이용해 키 전달 없이 세션키를 합의한다.
- **작동 원리**: 공개 파라미터 p, g를 공유하고 Alice는 비밀 a로 A=g^a mod p, Bob은 비밀 b로 B=g^b mod p를 만든다. Alice는 B^a mod p, Bob은 A^b mod p를 계산하며 결과는 g^(ab) mod p로 동일하다.
- **비유**: 공개 금고에 각자 자물쇠를 걸어 주고받은 뒤, 마지막에 자기 자물쇠만 풀면 같은 물건을 얻는 절차와 유사하다.
- **구체 예시**: TLS에서 ECDHE를 쓰면 서버 장기 개인키가 유출되어도 과거 세션키는 복구되지 않는 PFS(Perfect Forward Secrecy)를 제공한다.
- **흔한 오해·주의점**: DH 자체는 상대 신원을 인증하지 않는다. 인증서, 전자서명, PSK가 없으면 MITM 공격자가 양쪽과 각각 DH를 수행할 수 있다.

## 연결 개념
- TLS 1.3 Handshake — ECDHE 기반 세션키 합의
- PKI·X.509 — DH 교환 상대의 신원 검증
- PQC KEM — 양자 공격 대비 키 합의 대안

# 📝 【답안용】 시험 답안 템플릿

> 목적: 시험장에서 25분에 그대로 쓰는 답안 양식. 작성방식(추상표현 금지·수치·도식·문제유형 전환)을 엄격히 지킨다.

## 핵심 인사이트 (3줄 요약)

> 1. **본질**: 디피-헬만 키 교환은 비밀키를 전송하지 않고 공개값 교환만으로 동일한 세션키를 합의하는 공개키 기반 키 합의 프로토콜임.
> 2. **가치**: ECDHE 적용 시 서버 장기키 유출 이후에도 과거 TLS 세션키 복구를 차단하는 PFS 제공.
> 3. **판단 포인트**: 키 교환은 인증 기능이 아니므로 MITM 차단을 위해 X.509 인증서, 전자서명, PSK와 결합 필요.

## 출제 의도 및 답안 포인트

| 출제 의도 | 반드시 짚을 핵심 | 감점 회피 포인트 |
|:---|:---|:---|
| 키 교환과 암호화를 구분하는 역량 확인 | p·g 공개 파라미터, 개인 난수, 공개값, 공유 비밀, KDF | DH를 대칭키 암호화 알고리즘으로 설명 금지 |
| 보안형 관점의 위협·통제 판단 확인 | MITM 위협, 인증서 서명 검증, PFS, 파라미터 검증 | "도청 방지"만 쓰고 인증·무결성 누락 금지 |
| 적용 기준 판단 확인 | FFDHE 2048비트 이상, ECDHE P-256/X25519, TLS 1.3 | 고정 DH와 임시 DH 차이 누락 금지 |

> 요약: DH 답안은 "키 합의는 하되 인증은 별도"라는 판단과 PFS 적용 조건을 함께 써야 함.

## Ⅰ. 개요 및 필요성

- 개요: 공개 채널 키 합의 방식
- 배경: 대칭키 암호는 안전한 키 전달 문제가 있고, 공개키 암호만으로 대량 트래픽을 처리하면 본문 암호화 비용이 커짐.
- 필요성: DH/ECDHE는 공개값 교환 후 KDF로 세션키를 생성해 TLS·VPN·메신저에서 채널별 임시 키와 PFS를 제공함.

---

## Ⅱ. 구조 및 구성요소

```text
공개 파라미터 p,g 또는 Curve -> 개인 난수 a,b -> 공개값 A,B
  / A,B 교환 -> 공유 비밀 Z -> KDF -> 세션키
  / 인증서·서명 검증 -> MITM 차단
```

| 구성요소 | 역할 | 특이사항 |
|:---|:---|:---|
| 공개 파라미터 | 소수 p·생성원 g 또는 타원곡선 그룹 제공 | FFDHE 2048비트 이상, P-256·X25519 사용 |
| 개인 난수 | a,b 비밀 지수 생성 | 세션마다 재생성, RNG 품질 필수 |
| 공개값 | A=g^a, B=g^b 또는 ECC 점 연산 결과 교환 | 수신 공개키 그룹 검증 필요 |
| KDF | 공유 비밀 Z를 AES·ChaCha20 키로 변환 | HKDF-SHA-256 등 사용 |
| 인증 수단 | 상대 신원 검증 | X.509 서명, PSK, 인증된 공개키 |

> 요약: DH 구조는 공개값 교환과 공유 비밀 계산이 중심이며, 인증 수단을 결합해야 MITM을 차단함.

---

## Ⅲ. 동작원리 및 흐름도

```text
파라미터 합의 -> 개인 난수 생성 -> 공개값 계산 -> 공개값 교환
  -> 공개값 검증 -> 공유 비밀 계산 -> HKDF -> 세션키 적용
```

| 단계 | 처리 내용 | 검증 기준 |
|:---:|:---|:---|
| 1 | p,g 또는 Curve, cipher suite 협상 | TLS 1.3 지원 그룹, 금지 그룹 배제 |
| 2 | 세션별 개인 난수 생성 | CSPRNG, 재사용 0건 |
| 3 | 공개값 교환 및 인증 | 인증서 체인·서명 검증 성공 |
| 4 | 공유 비밀 계산 후 KDF 적용 | HKDF-SHA-256, 키 분리 |
| 5 | 대칭키로 통신 암호화 | AES-128/256-GCM 또는 ChaCha20-Poly1305 |

> 요약: DH는 공개값 교환 후 공유 비밀을 직접 암호키로 쓰지 않고 KDF로 세션키를 분리해 사용함.

---

## Ⅳ. 특징

| 구분 | 기존 키 전달 방식 | DH/ECDHE 방식 | 판단 포인트 |
|:---|:---|:---|:---|
| 키 노출 영향 | 전달 키 탈취 시 세션 즉시 복호화 | 비밀 지수 미전송, 공유 비밀 계산 | 네트워크 도청자에게 키 미노출 |
| 장기키 유출 | RSA key exchange는 과거 세션 복호화 가능 | ECDHE는 PFS 제공 | TLS 1.3은 RSA key exchange 제거 |
| 인증 범위 | 별도 인증 없으면 상대 불명 | 인증서·서명 결합 시 신원 확인 | 키 합의와 인증 구분 |
| 연산 기준 | FFDHE 2048비트 이상 | P-256·X25519로 128비트 보안 강도 | 모바일·웹은 ECDHE 우선 |

> 요약: DH의 채점 포인트는 공유 비밀 계산보다 인증 결합과 PFS 제공 여부 판단임.

## Ⅴ. 심화 비교 및 적용 판단

| 비교 축 | 기존/대안 | 본 키워드 | 선택 기준 |
|:---|:---|:---|:---|
| 구조 | RSA key exchange | ECDHE key agreement | TLS 1.3, PFS 요구 시 ECDHE |
| 비용/성능 | FFDHE 3072비트 | ECDHE P-256/X25519 | 128비트 보안 강도와 핸드셰이크 지연 동시 고려 |
| 운영/위험 | 고정 DH 파라미터 | 임시 키 ECDHE | 세션별 난수, 키 재사용 0건 |

> 요약: 웹·API 통신은 ECDHE+X.509 조합을 기본으로 두고, 레거시 FFDHE는 호환 구간에 제한 적용함.

| 리스크 | 원인 | 대응 방안 | 확인 지표 |
|:---|:---|:---|:---|
| MITM | DH 자체 인증 부재 | 인증서 체인, 서명, 핀닝 검증 | 인증 실패 차단률 100% |
| 약한 그룹 | 1024비트 FFDHE, 작은 부분군 공격 | 2048비트 이상, safe prime, public key validation | 금지 cipher suite 0건 |
| 난수 재사용 | CSPRNG 장애, 세션키 반복 | DRBG 상태 점검, 세션별 ephemeral key | 중복 공개값 탐지 0건 |

> 요약: DH 운영 리스크는 인증 부재, 약한 그룹, 난수 재사용이며 스캐너와 핸드셰이크 로그로 검증함.

| 점검 항목 | 목표 기준 | 측정 방법 |
|:---|:---|:---|
| 암호 적용 | TLS 1.3, ECDHE, AES-GCM/ChaCha20 | SSL Labs, testssl.sh |
| 키 관리 | ephemeral key 세션별 생성, 장기키 HSM 보관 | HSM 감사로그, 키 재사용 탐지 |
| 탐지·복구 | MITM 의심 인증서, cipher downgrade 차단 | SIEM 룰, 인증서 투명성 로그 |

> 요약: 도입 후에는 cipher suite, 키 재사용, 인증서 검증 실패 이벤트로 성공 여부를 판단함.

## Ⅵ. 실무 적용 및 결론

**적용 방안 3개 (필수 — 단계별 또는 항목별):**
1. TLS 정책: TLS 1.3 우선, TLS 1.2는 ECDHE_ECDSA/ECDHE_RSA와 AES-GCM 또는 ChaCha20-Poly1305만 허용.
2. 키 관리: 서버 개인키는 HSM/KMS에 보관하고, DH 개인 지수는 세션별 CSPRNG로 생성 후 즉시 폐기.
3. 탐지·복구: testssl.sh 정기 점검, 약한 DH 그룹 탐지 시 cipher suite 제거와 인증서 재발급 절차 수행.

**결론 (2줄):**
- 기술사 판단: 인터넷 공개 서비스는 ECDHE+X.509, 폐쇄망 장비 호환은 FFDHE 2048비트 이상으로 제한 적용.
- 향후 방향: 양자 위협 구간에서는 ECDHE와 ML-KEM을 결합한 하이브리드 키 교환으로 전환 필요.
