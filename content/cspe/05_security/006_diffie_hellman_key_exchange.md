# 📖 【암기용】 개념 완전 이해

## 한눈에
- **개요**: 디피-헬만(DH)은 **공개 채널에서 비밀키를 직접 전송하지 않고 공유 비밀(shared secret)을 생성**하는 최초의 공개키 기반 **키 교환** 프로토콜이다.
- **왜 필요한가**: 대칭 암호(001)는 같은 키를 미리 나눠 가져야 하는데, 도청 가능한 인터넷에서 키를 그대로 보내면 새어 나간다 — DH는 각자 비밀을 숨긴 채 계산만으로 같은 키에 도달하게 한다.
- **핵심 직관**: 두 사람이 각자 비밀 색 물감을 공개 물감에 섞어 교환한 뒤, 자기 비밀 물감을 한 번 더 섞으면 둘 다 똑같은 색이 되지만, 중간에서 본 사람은 그 색을 못 만든다.

## 핵심 용어 정리 (내부에 등장하는 것들)

아래는 답안에 등장하는 모든 내부 용어를, 처음 보는 사람이 이해하도록 비유와 함께 먼저 정리한 것이다. 맨 위는 이 개념의 상위 핵심 키워드다. 공개키 암호의 일반 원리(공개키·개인키·소인수분해)는 002에서 세웠으므로 위임하고, 여기서는 DH 고유 요소를 세운다.

| 용어/표기 | 의미 | 비유·예 |
|:---|:---|:---|
| 키 교환(Key Exchange, 상위 키워드) | 공개망에서 공유 대칭키를 합의하는 절차 | 두 사람이 같은 자물쇠 열쇠에 도달 |
| 이산대수 문제 | g^x mod p에서 지수 x를 역산하기 어려움 | 시계 바늘 위치는 보여도 몇 바퀴 돌았는지 모름 |
| 공개 파라미터(p, g) | 소수 p와 생성원 g, 양쪽이 공유 | 모두에게 공개된 공용 물감통 |
| 생성원(Generator, g) | 곱셈군을 고루 만들어내는 밑수 | 여러 색을 다 만들 수 있는 원색 |
| 개인 지수(a, b) | 각자 비밀로 고른 지수 | 남에게 안 알리는 나만의 비밀 색 |
| 공개값(g^a, g^b mod p) | 개인 지수로 만들어 교환하는 값 | 섞어서 남에게 보여주는 중간 색 |
| 공유 비밀(g^ab mod p) | 양쪽이 도달하는 동일 비밀값 | 최종적으로 같아지는 색 |
| CDH 가정 | g^a, g^b만으로 g^ab 계산은 어렵다는 전제 | 두 중간 색을 봐도 최종 색은 못 냄 |
| 중간자 공격(MITM) | 공격자가 양쪽과 각각 키 교환해 가로챔 | 두 사람 사이에서 각자와 딴 색을 합의 |
| 전방향 안전성(PFS) | 장기키 유출돼도 과거 세션은 안전 | 매 대화마다 색을 새로 만들고 버림 |
| 임시키(Ephemeral) | 세션마다 새로 만들어 폐기하는 키 | 한 번 쓰고 버리는 일회용 열쇠 |
| ECDHE | 타원곡선 기반 임시 DH | 짧은 키로 같은 강도(X25519·P-256) |
| Logjam | 취약 소수·512비트 파라미터 강등 공격 | 낡고 약한 자물쇠로 갈아치우기 |

## 깊이 이해
- **배경·문제의식**: 1976년 이전엔 대칭키를 안전하게 나눌 유일한 방법이 사람이 직접 전달하는 것이었다(키 분배 문제). DH는 "도청자가 오가는 값을 다 봐도 최종 키는 못 만든다"는, 공개 채널만으로 비밀을 합의하는 최초의 해법을 제시했다 — 공개키 암호(002)의 출발점이다.
- **작동 원리(어떻게+왜)**:
  - 공개 파라미터로 소수 `p`와 생성원 `g`를 정한다. 앨리스는 비밀 `a`를 골라 `A=g^a mod p`를, 밥은 비밀 `b`를 골라 `B=g^b mod p`를 계산해 서로 **공개값만 교환**한다.
  - 앨리스는 받은 `B`에 자기 `a`를 올려 `B^a=g^ba`를, 밥은 `A`에 자기 `b`를 올려 `A^b=g^ab`를 계산한다. 지수 법칙으로 `g^ab = g^ba`가 되어 **양쪽이 같은 공유 비밀**에 도달한다.
  - **왜 안전한가**: 도청자는 `g`, `p`, `A`, `B`를 모두 보지만, `A`에서 `a`를 역산하려면 **이산대수 문제**를 풀어야 하고, `A·B`만으로 `g^ab`를 직접 구하는 것도 어렵다(CDH 가정). 그래서 개인 지수를 모르면 공유 비밀을 못 만든다.
- **비유**: 물감 섞기. 공용 노란색(g)에 각자 비밀 색을 섞어 교환하고, 받은 혼합색에 자기 비밀 색을 한 번 더 섞으면 둘 다 같은 최종색이 된다. 중간에서 혼합색 두 개를 본 사람은 비밀 색을 분리할 수 없어 최종색을 못 만든다.
- **구체 예시**: TLS 1.3은 정적 RSA 키 교환을 **제거하고 (EC)DHE만 허용**해, 세션마다 임시키로 전방향 안전성을 강제한다. 유한체 DH는 2048비트 이상 소수를, ECDHE는 X25519·P-256을 쓴다. 2015년 Logjam은 512비트 취약 소수로 강등시켜 세션을 깬 사례다.
- **흔한 오해·주의점**: ① DH는 **암호화도 서명도 아니다** — 오직 '공유 키 합의'만 하며, 실제 데이터는 그 키로 AES-GCM(001) 암호화한다. ② DH 자체는 **인증이 없어 중간자 공격에 취약**하다 — 공격자가 양쪽과 각각 키를 맺을 수 있으므로, 공개값을 전자서명·인증서(008·010)로 인증해야 안전한 '인증된 DH'가 된다. ③ 정적 키를 재사용하면 PFS가 깨지므로 **임시키(Ephemeral)** 사용이 원칙이다.

## 연결 개념
- 비대칭 암호(002) — DH는 공개키 암호의 효시, 이산대수 난제를 공유
- 대칭 암호(001) — DH가 합의한 공유 비밀을 세션키로 삼아 본문을 암호화
- TLS 1.3 핸드셰이크(014) — ECDHE로 전방향 안전성을 확보하는 실제 적용
- 전자서명·인증서(008·010) — 공개값을 인증해 중간자 공격을 차단

# 📝 【답안용】 시험 답안 템플릿

## 핵심 인사이트 (3줄 요약)

> 1. **본질**: DH는 공개 채널에서 개인 지수를 숨긴 채 g^ab를 양쪽이 동일하게 산출하는, 이산대수 난제 기반 키 교환임.
> 2. **가치**: 키를 전송하지 않고 공유 비밀을 합의해 대칭 세션키를 안전히 확보하며, ECDHE로 전방향 안전성을 제공함.
> 3. **판단 포인트**: 인증이 없어 중간자에 취약하므로 서명·인증서와 결합하고, 임시키로 PFS를 강제해야 함.

## 출제 의도 및 답안 포인트

| 출제 의도 | 반드시 짚을 핵심 | 감점 회피 포인트 |
|:---|:---|:---|
| 공개망 키 합의 원리와 인증 결합 필요성 확인 | 이산대수 난제, g^ab 공유, 중간자 취약성, ECDHE·PFS | DH를 암호화·서명으로 오인, 인증 자동 제공 가정, 정적키 PFS 혼동 |

> 요약: DH 답안은 공유 비밀 산출 메커니즘과, 인증 부재로 인한 중간자 취약성 및 임시키 PFS를 함께 짚어야 함.

## Ⅰ. 개요 및 필요성

- 개요: 공개 채널에서 공유 비밀을 합의하는 이산대수 기반 키 교환 프로토콜임
- 배경: (002 공개키 암호의 효시) 대칭 암호는 사전 키 공유가 필요하나 도청망에서 키 직접 전송이 불가함
- 필요성: 개인 지수를 숨긴 채 g^ab를 양쪽이 산출해 대칭 세션키를 확보하고, ECDHE로 전방향 안전성을 제공함

## Ⅱ. 구조 및 구성요소

선형 구조도:

```text
공개: 소수 p, 생성원 g
앨리스: a(비밀) -> A=g^a mod p --전송--> 밥
밥:    b(비밀) -> B=g^b mod p --전송--> 앨리스
공유 비밀: 앨리스 B^a = 밥 A^b = g^ab mod p
```

| 구성요소 | 역할 | 특이사항 |
|:---|:---|:---|
| 공개 파라미터(p, g) | 연산의 공용 기반 | 유한체 2048b 이상·검증된 곡선 |
| 개인 지수(a, b) | 각자 비밀, 미전송 | 세션마다 새로 생성(임시키) |
| 공개값(g^a, g^b) | 교환 대상 | 도청돼도 이산대수로 역산 불가 |
| 공유 비밀(g^ab) | 세션키 유도 입력 | KDF로 대칭키 파생 후 사용 |

> 요약: DH는 공개 파라미터 위에서 개인 지수는 숨기고 공개값만 교환해 동일한 g^ab에 도달함.

## Ⅲ. 동작원리 및 흐름도

선형 흐름도:

```text
파라미터 합의 -> 각자 개인 지수 선택 -> 공개값 계산·교환 -> 상대 공개값에 자기 지수 적용 -> g^ab 공유 -> KDF로 세션키 유도
```

1. 양측이 공개 파라미터 소수 p와 생성원 g를 합의함
2. 앨리스와 밥이 각자 비밀 지수 a, b를 고르고 공개값 A=g^a, B=g^b를 계산해 교환함
3. 앨리스가 B^a를, 밥이 A^b를 계산해 동일한 공유 비밀 g^ab에 도달함
4. 양측이 공유 비밀을 KDF로 대칭 세션키로 유도해 이후 본문을 AES-GCM으로 암호화함

## Ⅳ. 특징

- 비전송 키 합의 — 키를 직접 보내지 않고 공개값 교환만으로 공유 비밀을 산출함
- 이산대수 기반 안전성 — 공개값에서 개인 지수 역산이 계산상 불가능해 도청에 강함
- 전방향 안전성 — 임시키(ECDHE) 사용 시 장기키 유출에도 과거 세션이 보호됨
- 인증 부재 한계 — 자체 인증이 없어 중간자 공격에 취약하므로 서명·인증서 결합이 필수임
- 키 합의 전용 — 암호화·서명 기능은 없어 대칭 암호·전자서명과 조합해 사용함

## Ⅴ. 심화 비교 및 적용 판단

- 유한체 DH와 타원곡선 ECDHE는 안전 근거는 유사하나 키 길이·성능·현행 표준 채택에서 갈림.

| 구분 | 유한체 DH(FFDHE) | ECDHE |
|:---|:---|:---|
| 수학적 근거 | 유한체 이산대수 | 타원곡선 이산대수 |
| 동등 강도 키 | 3072비트 | 256비트(X25519·P-256) |
| 성능 | 상대적으로 무거움 | 짧은 키로 빠름 |
| 표준 채택 | 레거시 호환 | TLS 1.3 기본 |

> 요약: 신규·경량 환경은 ECDHE(X25519), 레거시 호환이 필요하면 2048b 이상 FFDHE를 선택함.

- 리스크 — 중간자 공격: 공개값 인증 부재가 원인 → 인증서·전자서명으로 공개값 서명 검증으로 대응
- 리스크 — 파라미터 강등(Logjam): 512b 취약 소수가 원인 → 2048b 이상·검증된 곡선 강제로 대응
- 리스크 — PFS 상실: 정적 키 재사용이 원인 → 세션별 임시키(ECDHE) 강제로 대응

## Ⅵ. 실무 적용 및 결론

**적용 방안 3개:**
1. TLS 1.3 적용: 정적 RSA 키 교환을 제거하고 ECDHE(X25519·P-256)만 허용해 전방향 안전성을 강제함
2. 인증 결합: 서버가 공개값을 인증서 개인키로 서명하고 클라이언트가 검증해 중간자 공격을 차단함
3. 파라미터 강화: FFDHE는 2048비트 이상 표준 그룹을 쓰고 512·1024비트 취약 파라미터를 차단함

**결론:**
- 조건부 판단: DH는 공유 키 합의 전용이므로 반드시 인증(서명·인증서)과 대칭 암호를 결합해 배치해야 함
- 향후 방향: 양자컴퓨터의 이산대수 해독 위협에 대비해 ML-KEM(016)과 ECDHE를 병행하는 하이브리드 키 교환으로 전환 필요
