## 미리 알고가기

- 이 문맥의 웹 서비스는 SOAP 기반 XML 메시지를 주고받는 전통적 기업 연계 서비스를 뜻함
- WS-Security는 SOAP 메시지 안에 서명과 암호화와 토큰을 넣어 메시지 자체를 보호하는 표준임
- SAML은 사용자나 시스템의 인증·속성 정보를 담는 서명된 주장 문서로, SSO와 연계 인증에 자주 쓰임

## Ⅰ. 개요

- **정의/개념**: 웹 서비스 보안은 SOAP 기반 연계 환경에서 메시지 무결성과 기밀성과 발신자 신뢰를 보장하기 위해 WS-Security와 SAML 같은 메시지 수준 보안 표준을 적용하는 방식임
- **배경/필요성**: 단순 TLS는 전송 구간은 보호하지만 중간 노드 경유나 저장 후 재전송 상황에서는 메시지 자체의 위변조와 발신자 확인을 보장하지 못해 별도 메시지 보안이 필요함

## Ⅱ. 특징

- 메시지 본문과 일부 헤더를 서명하거나 암호화해 중간 경로에서도 무결성을 유지할 수 있음
- SAML 토큰으로 사용자나 시스템의 인증 상태를 전달할 수 있음
- XML 파싱과 서명 검증 부담으로 REST 기반 API보다 구현과 운영이 복잡함
- XML 보안 설정이 약하면 XXE나 서명 검증 우회 같은 추가 위험이 생길 수 있음

## Ⅲ. 종류 및 비교

| 판단 기준 | TLS 중심 전송 보호 | WS-Security 메시지 보호 |
|:---|:---|:---|
| 보호 범위 | 통신 구간 | 메시지 자체 |
| 강점 | 구현이 단순하고 성능 부담이 상대적으로 적음 | 중간 노드 경유나 저장 후 검증에 유리함 |
| 한계 | 종료 지점 이후 무결성 보장이 약함 | XML 처리 복잡성과 오버헤드가 큼 |
| 적합 환경 | 일반 REST API | 레거시 SOAP, B2B, 기업 간 연계 |

## Ⅳ. 구성요소 및 구조

| 구성요소 | 설명 |
|:---|:---|
| SOAP 메시지 | XML 기반 요청과 응답 본문을 담음 |
| WS-Security 헤더 | 서명, 암호화, 토큰 정보를 담음 |
| SAML Assertion | 신원과 속성과 인증 상태를 전달함 |
| 수신 검증 로직 | 서명, 만료, 토큰 발급자, 복호화를 확인함 |

```text
메시지 생성 -> WS-Security 헤더 추가 -> 서명/암호화 -> 전송 -> 수신 측 검증 -> 처리
```

## Ⅴ. 원리 및 절차 흐름도

```text
SOAP 요청 작성 -> SAML/서명 추가 -> 암호화 -> 중간 노드 경유 -> 수신 측 검증 -> 업무 처리
```

1. **메시지 작성**: SOAP 본문과 필요한 보안 헤더를 구성함
2. **토큰과 서명 추가**: SAML과 서명 정보로 발신자와 무결성을 보강함
3. **암호화와 전송**: 필요한 요소를 암호화해 보냄
4. **수신 측 검증**: 서명과 시간과 발급자와 권한을 확인함
5. **처리와 감사**: 검증 성공 시 처리하고 증적을 남김

## Ⅵ. 실무 적용 및 유의점

1. 금융·공공처럼 SOAP 기반 B2B 연계가 남아 있는 환경은 TLS만으로 끝내지 말고 메시지 서명과 토큰 검증을 함께 적용하고 서명 검증 실패 차단 여부와 토큰 만료·발급자 검사 정확도로 확인함
2. XML 파서를 쓰는 서비스는 기능 구현보다 보안 설정이 더 중요하므로 XXE 차단과 인증서 관리와 시간 동기화를 함께 챙기고 악성 XML 재현 여부와 서명 검증 오류 로그와 인증서 만료 관리 상태로 확인함

## Ⅶ. 결론

- 웹 서비스 보안은 전송 구간 보호를 넘어 메시지 자체의 무결성과 신원을 보장해야 하므로 SOAP 연계 환경에서는 WS-Security와 SAML 검증이 핵심임
