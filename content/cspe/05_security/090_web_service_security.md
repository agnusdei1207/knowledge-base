## Ⅰ. 개요
| 항목 | 내용 |
|---|---|
| **정의** | SOAP 기반 웹 서비스의 메시지 수준 보안을 위해 WS-Security 표준으로 XML 서명·암호화·토큰 전달을 수행하는 체계임 |
| **배경/필요성** | 전송 계층(TLS)만으로는 중간 노드 경유 시 메시지 무결성·기밀성을 보장할 수 없어 메시지 수준 보안이 필요함 |
| **출제 의도** | WS-Security와 SAML 토큰의 역할 및 REST 보안과의 차이를 이해하는지 평가함 |

## Ⅱ. 구성요소
```
+----------+     +----------+     +----------+
| XML서명   | --> | XML암호화 | --> | 보안토큰  |
| (Sign)   |     | (Encrypt)|     | (SAML)   |
+----------+     +----------+     +----------+
```

| 구성요소 | 설명 | 비유 |
|---|---|---|
| XML 서명 | SOAP 메시지 본문에 전자서명을 적용하여 무결성·부인방지를 보장함 | 계약서의 공증 도장 |
| XML 암호화 | 메시지의 민감 요소를 부분 암호화하여 기밀성을 확보함 | 봉투 안의 보안 내용물 |
| SAML 토큰 | 인증·속성 정보를 XML Assertion으로 전달하여 SSO 및 연합 인증을 지원함 | 공인된 기관의 신분 확인서 |

> 요약: XML 서명(무결성), XML 암호화(기밀성), SAML 토큰(인증)으로 메시지 수준 보안을 구현함.

## Ⅲ. 절차
```
+------------+     +------------+
| SOAP메시지  | --> | WS-Security|
| 생성       |     | 헤더삽입   |
+------------+     +------------+
                        |
+------------+     +----+-------+
| 서비스     | <-- | 서명·토큰 |
| 검증·처리  |     | 검증      |
+------------+     +------------+
```

1. SOAP 메시지 생성: 클라이언트가 요청 데이터를 XML SOAP 형식으로 구성함
2. WS-Security 헤더 삽입: SOAP Header에 XML 서명, 암호화 블록, SAML 토큰을 추가함
3. 메시지 전송: 중간 노드(ESB)를 경유하더라도 메시지 수준 보안이 유지됨
4. 수신측 검증: 서비스가 서명 검증, 복호화, SAML Assertion 유효성을 확인한 후 요청을 처리함

> 요약: 메시지 생성 → 보안 헤더 삽입 → 전송 → 수신측 검증으로 종단 간 메시지 보안을 달성함.

## Ⅳ. 문제점
- XML 파싱 오버헤드: XML 서명·암호화 처리로 REST 대비 성능이 저하됨
- XXE 취약점: XML 파서의 외부 엔티티 처리 설정이 미흡하면 XXE 공격에 노출됨
- 표준 복잡성: WS-Security·WS-Trust·WS-Federation 등 관련 표준이 다수로 구현 난이도가 높음

## Ⅴ. 개선방안
- (단기) XXE 방어: XML 파서의 외부 엔티티·DTD 처리를 비활성화함
- (중기) REST 전환: 신규 서비스는 OAuth 2.0 + JWT 기반 REST API로 전환하여 복잡성을 감소함
- (장기) API 게이트웨이 통합: SOAP·REST 혼합 환경에서 게이트웨이가 프로토콜 변환·보안 정책을 중앙 관리함

## Ⅵ. 전망
- 레거시 SOAP 서비스는 API 게이트웨이를 통해 REST로 점진 전환되며, 신규 시스템에서는 OAuth 2.0/OIDC 기반 보안이 사실상 표준으로 자리잡을 전망임
