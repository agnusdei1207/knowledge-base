## 1. 한눈에 이해하기 (Core Intuition)
- **정의**: 서로 다른 시스템이나 외부 클라우드 서비스 간에, **"이 사람은 우리 회사 직원이 맞고, 이런 권한을 가졌습니다"라는 신원 보증서(Assertion)를 암호화된 문서(XML)** 형태로 주고받아 로그인(SSO)을 한 번에 처리하게 해주는 B2B 엔터프라이즈 인증 표준입니다.
- **필요성**: 삼성전자 직원이 사내 로그인(AD)을 한 뒤, 외부에 있는 Salesforce.com(고객관리 클라우드)에 접속하려 합니다. Salesforce는 이 사람이 삼성 직원인지 모릅니다. 삼성이 "우리 직원 맞다"는 증명서를 찍어 보내줘야 하는데, 이 증명서를 어떤 양식과 규칙으로 만들고 읽을 것인지 통일된 글로벌 규격(언어)이 필요했습니다.
- **핵심 직관**: **"대사관이 발급한 밀봉된 외교 신임장"**. 
  - 내가 외국 기관(외부 서비스, SP)에 들어갈 때 직접 신분을 구구절절 해명하지 않습니다. 
  - 본국 대사관(인증 기관, IDP)에서 "이 자는 우리 국민 홍길동이며 직급은 과장이다"라고 두꺼운 양피지 문서에 쓴 뒤 대사관의 공식 도장(전자서명)을 찍어 줍니다.
  - 이걸 외국 기관에 제출하면, 도장을 확인한 뒤 1초 만에 귀빈 대접(로그인 성공)을 해줍니다. 이 양피지 문서의 양식이 바로 SAML 형식(XML 기반)입니다.

## 2. 왜 중요한가? (Background & Value)
- **등장 배경**: 2005년에 제정(OASIS 표준)되어 거의 20년 가까이 된 오래된 기술입니다. 하지만 보안성이 극도로 엄격하고, 기존 기업들의 온프레미스(사내) 시스템과 찰떡같이 연동되어 오랜 기간 업계를 지배해 왔습니다.
- **가치**: B2B(기업 대 기업) 및 엔터프라이즈 환경에서 연합 인증(Federation SSO)을 구현하는 **부동의 인프라 뼈대**입니다. B2C 소셜 로그인이 가벼운 OIDC(JSON)를 쓴다면, 무거운 기업용 ERP, 인트라넷, 클라우드 워크스페이스는 여전히 SAML 2.0이 표준입니다.

## 3. 어떻게 작동하는가? (Mechanism)
SAML 통신의 3대 주체: **사용자(웹 브라우저)**, **IDP(신원 제공자, 사내 인증 서버)**, **SP(서비스 제공자, 외부 클라우드)**.
모든 통신은 무거운 XML 파일로 이루어집니다.

- **작동 원리 (SP-Initiated Flow, 서비스 먼저 접속 시)**:
  1. 사용자가 브라우저로 Salesforce(SP) 사이트에 접속합니다.
  2. Salesforce는 "누구신지? 일단 삼성 로그인 서버(IDP)에 가서 증명서 받아와" 라며, 브라우저를 튕겨냅니다 (SAML AuthnRequest 생성).
  3. 사용자는 삼성 사내 인증 서버(IDP) 화면에서 ID/PW를 입력해 로그인합니다.
  4. IDP는 로그인 성공 확인 후, **"SAML 어설션(Assertion)"** 이라는 두꺼운 XML 문서를 만듭니다. 이 안에는 "이름: 홍길동, 부서: 영업팀" 정보가 들어있고, 위조 방지를 위해 IDP의 개인키로 강력한 '전자 서명'을 찍습니다.
  5. 사용자의 브라우저는 이 XML 문서를 들고 다시 Salesforce(SP)로 날아갑니다.
  6. Salesforce는 삼성이 준 공개키(사전에 교환 완료)로 도장이 진짜인지 확인하고 로그인(세션 발급)을 허락합니다.

## 4. 실전 활용 및 예시 (Real-world Application)
- **구체적 사례**: 
  - **대기업의 O365 / AWS 로그인**: 임직원이 회사 밖에서 Office 365 포털에 이메일 주소를 치면, 마이크로소프트 서버는 비밀번호를 묻지 않고 곧바로 회사의 Okta나 Azure AD 로그인 창으로 화면을 전환시킵니다. 여기서 인증을 마치면 SAML 토큰을 쥐고 자동으로 O365에 로딩됩니다.
- **주의점 및 흔한 오해**: 
  - SAML의 치명적 단점은 **"크고 무겁고 모바일에 안 맞는다"** 는 점입니다. 복잡한 XML 텍스트 뭉치라서 덩치가 크기 때문에, 모바일 앱 환경이나 REST API 백엔드 통신용으로는 성능 저하가 커서 거의 쓰지 못합니다. (이때 OIDC가 쓰입니다).

## 5. 핵심 비교 및 연결 개념 (Relation)
- **SAML 2.0 vs OIDC (OpenID Connect)**:
  - **SAML 2.0**: 무거운 양피지 증명서(XML). 브라우저 기반 B2B 엔터프라이즈 환경(ERP, 클라우드 SSO) 최적화. 보안과 통제력이 극강.
  - **OIDC**: 얇은 플라스틱 신분증(JWT/JSON 포맷). B2C 모바일 앱, REST API 등 가볍고 빠른 현대적 아키텍처 환경에 최적화. (현재 신규 서비스 아키텍처는 대부분 OIDC로 쏠리는 추세).

# ✍️ 단답형 / 서술형 시험장 출격 준비

### Ⅰ. 핵심 인사이트
- **본질**: 독립된 두 도메인(IDP와 SP) 간에, 인증(Authentication) 및 인가(Authorization) 데이터를 XML 포맷의 **어설션(Assertion)** 형태로 브라우저를 매개하여 안전하게 전달함으로써 연합(Federated) SSO를 구현하는 OASIS 국제 표준 규격.
- **가치**: 기존 온프레미스의 Active Directory(AD) 인증 신뢰(Trust) 체계를 외부 SaaS 및 B2B 파트너 포털 인프라까지 경계 없이 수평 확장(Extend)하는 엔터프라이즈 클라우드 인프라의 마더보드(Motherboard).
- **판단 포인트**: XML 기반의 데이터 페이로드가 커서 모바일 및 마이크로서비스(API) 아키텍처에는 부적합하며, XXE(XML External Entity) 인젝션 취약점 등 파서(Parser) 구현 시 보안 홀이 발생하지 않도록 시큐어 코딩 및 XML 서명 무결성 검증이 시스템 아키텍처의 핵심임.

### Ⅱ. SAML 2.0의 3대 핵심 구성 요소
1. **주체 (Principal)**: 로그인을 시도하는 사용자 브라우저 주체 (User).
2. **신원 제공자 (IDP, Identity Provider)**: 사내 인증 서버(예: ADFS, Okta). 주체의 자격 증명(ID/PW, OTP)을 검증하고, 그 결과를 보증하는 **SAML 어설션(XML)** 을 생성 및 전자서명(Sign)하여 발급하는 권위 있는 기관.
3. **서비스 제공자 (SP, Service Provider)**: 사용자가 이용하고자 하는 타겟 애플리케이션(예: Slack, AWS, Salesforce). IDP로부터 받은 어설션의 서명을 검증하고, 그 안의 클레임(Claim) 정보를 파싱하여 자체 세션을 수립하는 기관.

### Ⅲ. 신뢰 관계 (Trust Relationship) 및 통신 메커니즘
- **사전 신뢰 (Metadata Exchange)**: SAML이 작동하기 위해서는 사전에 IDP와 SP가 서로의 정보(Entity ID, 엔드포인트 URL, Public Key/인증서)가 담긴 XML 메타데이터 파일을 교환하여 단단한 1:1 신뢰 고리를 맺어두어야 함.
- **바인딩 (Binding)**: 어설션(XML 문서)을 어떻게 운반할 것인가에 대한 프로토콜 맵핑.
  - **HTTP POST Binding (가장 많이 쓰임)**: 어설션을 Base64로 인코딩하여 HTML Form 숨김 필드(Hidden input)에 담아 브라우저가 자동 POST 전송(Auto-submit)하도록 넘기는 방식.
  - **HTTP Redirect Binding**: 파라미터로 URL 길이에 맞춰 넘기는 방식(주로 짧은 `AuthnRequest` 요청 시 사용).

### Ⅳ. SAML 어설션 (Assertion)의 구조 및 취약점 방어
SAML의 핵심 결과물인 XML 문서 덩어리. 이 문서 하나에 모든 정보가 담겨 있음.
- **구조**:
  - `Subject`: 누구인가? (NameID: 홍길동의 이메일).
  - `Conditions`: 유효기간(NotBefore, NotOnOrAfter) 명시. (재전송 공격 방어용 타임스탬프).
  - `AuthnStatement`: 인증 명세 (언제, 패스워드로 로그인했음).
  - `AttributeStatement`: 속성 명세 (부서: 인사팀, 직급: 과장 등 권한 인가용 데이터).
  - **`<Signature>` (가장 중요)**: XMLDsig 포맷으로, 문서 전체가 조작되지 않았음을 보증하는 IDP의 강력한 디지털 서명.

- **주요 보안 아키텍처 위협 방어**:
  - **XML Signature Wrapping (XSW) 공격**: 해커가 원본 XML 서명은 그대로 둔 채, 악의적인 `Subject` 노드를 몰래 끼워 넣어 파서(Parser)를 속이는 공격. $\rightarrow$ 방어: SAML 파서 개발 시 검증 로직이 서명된 노드와 실제 애플리케이션이 읽는 노드의 위치(XPath)를 엄격하게 동일성 검증하도록 아키텍처 구현.
  - **Replay Attack (재전송)**: 가로챈 어설션으로 며칠 뒤 로그인. $\rightarrow$ 방어: 어설션 내에 일회용 ID(`ID="id123..."`) 생성 및 짧은 수명(Validity 1~3분) 세팅 강제.

### Ⅴ. 결론 및 실무적 판단 포인트
- 기업의 신규 B2C 앱/서비스를 개발하는 아키텍트라면 가볍고 확장성이 좋은 **OIDC(OpenID Connect)** 기반 인증을 표준으로 삼아야 합니다.
- 그러나 이미 레거시 사내 AD(Active Directory)와 연동된 수십 개의 B2B 협력사 시스템망이 존재하거나, 높은 수준의 보안 감사(Audit) 및 속성 통제(Attribute-based)가 필수인 금융/공공 인프라를 클라우드로 이관할 때는 **SAML 2.0 인프라 유지**가 가장 리스크가 적은 안정적 아키텍처 선택입니다.

### 💡 문제 유형별 목차 전환 포인트
- **[엔터프라이즈 B2B 환경의 클라우드 인증(SSO) 아키텍처]**: Ⅱ번 구성요소와 Ⅲ번 사전 Trust 교환 메커니즘을 전면에 내세워, 외부 클라우드 사업자에게 사내 DB 비밀번호를 주지 않고도 인증을 연합(Federated)하는 거버넌스 가치를 집중 기술.
- **[SAML 프로토콜의 작동 원리 및 XSW 취약점]**: Ⅳ번 항목을 도식화하여 XML 어설션(Assertion)의 `Subject/Signature` 구조를 까발리고, 무결성이 붕괴되는 파서 취약점(Signature Wrapping Attack) 원리와 방어 시큐어 코딩 대책을 논증.
