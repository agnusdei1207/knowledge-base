## 미리 알고가기

- 시스템 콜은 프로세스가 파일 접근, 네트워크 연결, 프로세스 생성처럼 커널에 요청하는 기본 동작임
- 강제 접근 통제는 파일 주인 의사와 별개로 시스템 정책이 접근 허용 여부를 정하는 방식임
- 레이블은 프로세스와 파일에 붙는 보안 속성이며 SELinux는 이 레이블 관계로 접근을 판단함

## Ⅰ. 개요

- **정의/개념**: Seccomp, AppArmor, SELinux는 리눅스에서 프로세스가 할 수 있는 시스템 콜, 파일 접근, 자원 사용 범위를 좁혀 침해 후 확산을 막는 커널 수준 격리 기술임
- **배경/필요성**: 애플리케이션이 해킹되더라도 곧바로 호스트 장악으로 이어지지 않게 하려면 컨테이너 바깥의 보안 장비보다 운영체제 안쪽 통제가 먼저 단단해야 함

## Ⅱ. 특징

- 침해를 완전히 막는 기술이 아니라 침해 뒤 피해 범위를 줄이는 기술임
- 커널이 직접 허용 여부를 판단하므로 애플리케이션 우회가 쉽지 않음
- 세 기술이 막는 대상이 달라 함께 쓸수록 격리 강도가 높아짐
- 정책을 너무 촘촘하게 잡으면 정상 애플리케이션도 막히므로 단계적 적용이 필요함

## Ⅲ. 종류 및 비교

| 판단 기준 | Seccomp | AppArmor | SELinux |
|:---|:---|:---|:---|
| 통제 대상 | 시스템 콜 종류 | 파일 경로와 기능 프로파일 | 레이블 기반 객체 접근 |
| 강점 | 불필요한 커널 호출을 직접 차단함 | 애플리케이션별 정책 작성이 비교적 단순함 | 가장 세밀한 권한 분리가 가능함 |
| 대표 용도 | 컨테이너의 위험한 시스템 콜 제한 | 특정 서비스의 파일·네트워크 권한 제한 | 고강도 격리와 다중 테넌트 보호 |
| 운영 부담 | 비교적 낮음 | 중간 | 상대적으로 높음 |

## Ⅳ. 구성요소 및 구조

| 구성요소 | 설명 |
|:---|:---|
| 시스템 콜 필터 | Seccomp 프로파일로 허용된 호출만 남김 |
| 애플리케이션 프로파일 | AppArmor로 경로, 실행, 네트워크 권한을 제한함 |
| 보안 레이블 정책 | SELinux로 프로세스와 파일의 허용 관계를 정함 |
| 감사 로그 | 거부된 행위를 기록해 정책 조정에 활용함 |

```text
프로세스 요청 -> Seccomp 시스템 콜 검사 -> AppArmor 프로파일 검사 -> SELinux 레이블 검사 -> 허용/거부
```

## Ⅴ. 원리 및 절차 흐름도

```text
프로세스 실행 -> 커널 호출 발생 -> 시스템 콜 필터 확인 -> 경로·레이블 정책 확인 -> 허용 또는 차단 -> 감사 기록
```

1. **프로세스 실행**: 애플리케이션이 파일 접근이나 네트워크 요청을 시도함
2. **시스템 콜 필터 확인**: Seccomp가 허용되지 않은 호출을 막음
3. **프로파일 확인**: AppArmor가 경로와 기능 권한을 검사함
4. **레이블 확인**: SELinux가 객체 간 허용 관계를 판단함
5. **감사 기록**: 거부된 요청을 남겨 정책을 다듬음

## Ⅵ. 실무 적용 및 유의점

1. 공용 쿠버네티스 노드는 위험한 시스템 콜과 호스트 파일 접근을 먼저 줄여야 하며 거부된 고위험 시스템 콜 수와 특권 컨테이너 수와 SELinux 위반 로그로 확인함
2. 정책을 한 번에 강하게 올리면 서비스 기동이 깨질 수 있으므로 감사 로그로 정상 행위를 먼저 학습하고 예외 정책 수와 배포 후 기동 실패 건수로 점검함

## Ⅶ. 결론

- Seccomp, AppArmor, SELinux는 같은 이름의 보안 기능이 아니라 서로 다른 통제 면을 막는 커널 격리 수단이므로 중첩 적용과 로그 기반 조정이 핵심임
