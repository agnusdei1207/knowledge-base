## 1. 한눈에 이해하기 (Core Intuition)
- **정의**: 서버 안에서 돌아가는 프로그램(컨테이너나 프로세스)이 해킹당해 좀비로 변하더라도, **운영체제(OS)의 심장(커널)을 부수거나 시스템을 파괴하지 못하도록, 프로그램의 "행동반경과 손발(권한)"을 시스템 밑바닥에서 원천적으로 포박(격리)해버리는 리눅스 강력 통제 기술 3대장**입니다.
- **필요성**: 도커(컨테이너)는 가벼운 대신 치명적인 단점이 있습니다. 1대의 물리 서버 안에 있는 100개의 컨테이너가 '리눅스 OS 심장(커널)' 1개를 쉐어하우스처럼 같이 쓴다는 점입니다. 컨테이너 1개가 해커에게 장악당해 OS 심장부에 "야! 서버 전체 데이터 다 지워!"라고 명령(System Call)을 내리면 서버가 펑 터집니다. 컨테이너가 감히 엉뚱한 명령을 못 내리게 입에 재갈을 물려야 했습니다.
- **핵심 직관**: **"교도소 죄수복의 특수 수갑과 발찌"**. 
  - 과거: 죄수(프로그램)를 교도소(리눅스)에 가둬놨지만 수갑을 안 채웠습니다. 죄수가 갑자기 간수(커널)의 권총(루트 권한)을 뺏어 쏠 수 있습니다.
  - **Seccomp / AppArmor / SELinux**: 죄수가 밥 먹기, 산책하기(정상 명령)는 할 수 있게 풀어주되, 손을 머리 위로 올리거나(이상 통신), 간수의 무기고 근처(중요 파일)로 다가가면 특수 수갑과 발찌가 즉시 록(Lock)을 걸어 죄수를 굳어버리게 만듭니다.

## 2. 왜 중요한가? (Background & Value)
- **등장 배경**: 컨테이너의 보안 취약점 1순위는 바로 '컨테이너 이스케이프(Container Escape, 컨테이너 탈옥)'입니다. 해커가 컨테이너를 뚫은 뒤, 얇은 가상화 벽을 깨부수고 나와서 호스트 OS(노드) 전체를 지배해 버리는 재앙입니다. 이를 막으려면 컨테이너 바깥(쿠버네티스)의 방어뿐만 아니라, 컨테이너가 딛고 서 있는 '리눅스 바닥' 자체의 방탄조끼가 필수적입니다.
- **가치**: "Assume Breach(이미 뚫렸다고 가정하라)의 구현체". 애플리케이션에 취약점(버그)이 있어서 해커가 접속에 성공하더라도, 해커가 칠 수 있는 명령어가 `mkdir`(폴더 만들기)이나 `chmod`(권한 변경) 같은 악의적 명령이면 리눅스 OS가 아예 씹어버려서 피해를 무효화시킵니다.

## 3. 어떻게 작동하는가? (Mechanism)
이 3대장은 역할이 조금씩 다르며, 중첩해서 사용(심층 방어)합니다.

1. **Seccomp (Secure Computing Mode) - "말문(System Call) 막기"**
   - 프로세스(컨테이너)가 커널에 부탁하는 명령어(시스템 콜)의 **종류**를 제한합니다.
   - 리눅스에는 약 330개의 시스템 콜이 있습니다. 웹 서버는 사실 40~50개만 쓰면 돌아갑니다.
   - Seccomp 프로파일(블랙리스트/화이트리스트)을 걸면: "이 컨테이너는 남의 프로세스를 추적하는 `ptrace` 명령어나, 권한을 바꾸는 `chmod` 명령어를 입 밖으로 내뱉는 순간 즉각 사살(Kill)한다!"
2. **AppArmor (Application Armor) - "행동 반경(Path) 막기"**
   - 시스템 콜 종류가 아니라, 특정 프로그램이 **어떤 파일(경로)이나 네트워크 포트를 건드릴 수 있는지** 제한합니다. (MAC, 강제 접근 통제).
   - "nginx(웹 서버) 프로그램은 오직 `/var/www/` 폴더 안의 파일만 읽을 수 있다. 만약 nginx가 `/etc/shadow`(패스워드 파일) 경로로 접근하려 하면 읽기(Read) 거부!" (경로 중심의 직관적 방어).
3. **SELinux (Security-Enhanced Linux) - "신분증(Label) 막기"**
   - 미 국가안보국(NSA)이 만든 초강력(가장 복잡한) 방어 시스템.
   - 모든 파일과 프로세스에 복잡한 보안 '라벨(보안 등급)'을 붙입니다.
   - "A라는 주체(웹 서버 라벨)는 B라는 객체(DB 폴더 라벨)에 접근할 규칙이 없으므로 무조건 접근 불가!" (경로가 아니라 라벨 중심의 군대식 철통 방어).

## 4. 실전 활용 및 예시 (Real-world Application)
- **구체적 사례**: 
  - 쿠버네티스(Docker)를 설치하면 기본적으로 **Seccomp의 디폴트 프로파일(Default Profile)** 이 자동으로 켜집니다. 이 디폴트 세팅만으로도 330개의 시스템 콜 중 악용되기 쉬운 44개의 치명적 명령어를 차단하여 컨테이너 이스케이프의 80%를 막아줍니다.
  - 우분투(Ubuntu) OS에서는 AppArmor가 디폴트로, 레드햇(CentOS/RHEL) OS에서는 SELinux가 디폴트로 커널을 보호하고 있습니다.
- **주의점 및 흔한 오해**: 
  - "이 좋은 걸 왜 끄고 쓰나요?" $\rightarrow$ 개발자들이 가장 싫어하는 보안 기능 1위가 SELinux/AppArmor입니다. 개발자가 새로 짠 앱이 갑자기 디스크를 읽어야 하는데 정책에 안 적혀 있으면 "Permission Denied" 에러를 뱉으며 앱이 뻗어버립니다. 빡친 개발자는 이 강력한 방탄조끼를 `setenforce 0` 명령어로 아예 꺼버리고 작업하는 치명적 실수를 자주 저지릅니다(보안 사고의 단골 원인).

## 5. 핵심 비교 및 연결 개념 (Relation)
| 구분 | 통제 방식 | 특징 및 장단점 |
|---|---|---|
| **Seccomp** | 시스템 콜(명령어 종류) 차단 | 매우 가벼움. 가장 로우(Low) 레벨 통제. Docker/K8s 기본 탑재. |
| **AppArmor** | 파일 경로(Path) 기반 접근 차단 | 프로파일 작성이 직관적이고 쉬움. (우분투 계열 표준). |
| **SELinux** | 보안 라벨(Label/Context) 기반 차단 | 방어력은 가장 완벽하나 설정이 미치도록 복잡함. (레드햇 계열 표준). |

# ✍️ 단답형 / 서술형 시험장 출격 준비

### Ⅰ. 핵심 인사이트
- **본질**: 컨테이너와 호스트 OS(리눅스 커널) 사이의 얇은 격리 수준을 보완하기 위해, 유저 공간(User Space)의 프로세스가 커널 공간(Kernel Space) 리소스에 접근하는 행위를 **시스템 콜 필터링(Seccomp)과 강제 접근 통제(MAC: AppArmor, SELinux) 방식을 통해 제한하는 커널 레벨의 런타임 샌드박싱 기술.**
- **가치**: 취약점이나 제로데이(Zero-day) 공격으로 인해 애플리케이션 계층이 타협(Compromised)되더라도, 공격자가 악의적인 권한 상승(Privilege Escalation), 컨테이너 탈옥(Escape), 무단 파일 시스템 변조를 시도하는 것을 인프라 바닥층에서 원천 무효화(Deny)하여 **공격의 폭발 반경(Blast Radius)을 컨테이너 내부로 영구 격리**함.
- **판단 포인트**: IT 아키텍트는 쿠버네티스 워크로드 보안을 위해 3가지를 상호 배타적으로 선택하는 것이 아님을 숙지해야 합니다. "이 프로세스는 `mount`나 `ptrace` 시스템 콜을 아예 못 쓰게 한다(Seccomp)"는 제한과 "이 프로세스는 특정 폴더만 읽을 수 있다(AppArmor)"는 접근 통제는 **독립된 방어 계층으로서 쿠버네티스 파드 보안 컨텍스트(SecurityContext) 내에 중첩 적용(Defense in Depth)** 되어야 합니다.

### Ⅱ. Seccomp (Secure Computing Mode) 핵심 아키텍처
가장 근원적인 리눅스 커널 방어 매커니즘.
- **원리**: BPF(Berkeley Packet Filter) 룰을 사용하여, 프로세스가 호출할 수 있는 시스템 콜(System Call)의 블랙리스트/화이트리스트를 정의.
- **Docker/K8s의 Default Profile**: 도커 엔진은 기본적으로 약 330여 개의 리눅스 시스템 콜 중 컨테이너 실행에 불필요하고 위험한 44개(예: `reboot`, `settimeofday`, `mount`, 클럭 변조 등)를 차단하는 프로파일을 자동 적용함.
- **도입 이슈**: 개발자가 특이한 라이브러리를 사용할 때 필요한 시스템 콜이 막히면 앱이 크래시(Crash)됨. 도입 시 반드시 Audit(감사) 모드로 먼저 구동하여 앱이 호출하는 시스템 콜 목록을 프로파일링(Profiling)한 후 화이트리스트(Strict) 모드로 전환해야 함.

### Ⅲ. 강제 접근 통제(MAC, Mandatory Access Control) 체계
기존 리눅스의 허술한 임의 접근 통제(DAC, User/Group 기반 rwx)를 극복하기 위해 등장. 해커가 루트(root) 권한을 탈취해도 파일 접근을 막는 강력한 통제권.
- **AppArmor (경로 중심)**:
  - 데비안/우분투(Debian/Ubuntu) 환경의 기본 MAC.
  - 경로 기반(Path-based) 정책을 사용해 "어떤 프로그램 실행 파일(`/usr/sbin/nginx`)이 어떤 파일 시스템 경로(`/etc/*`)에 읽기/쓰기/실행 권한을 가지는지" 정의.
  - 프로파일이 텍스트 형태로 읽기 쉬워 학습 곡선이 낮음.
- **SELinux (라벨 중심)**:
  - RHEL/CentOS 환경의 기본 MAC.
  - 주체(프로세스)와 객체(파일/포트) 모두에 `Type Enforcement (TE)` 보안 컨텍스트 라벨(예: `httpd_sys_content_t`)을 부여.
  - 룰 엔진이 주체 라벨과 객체 라벨 사이의 허용 정책(Policy) 유무를 검사. 방어 입도(Granularity)는 최고 수준이나 설정이 극도로 난해하여 유지보수 오버헤드가 큼.

### Ⅳ. 쿠버네티스 환경에서의 통합 적용 방안 (Pod Security)
과거 PSP(Pod Security Policy)의 기능이 Pod Security Admission(PSA)으로 개편됨에 따라 커널 레벨 보안 프로파일의 명시적 선언이 중요해짐.
- **파드 스펙(YAML) 내 SecurityContext 선언**:
  ```yaml
  securityContext:
    seccompProfile:
      type: RuntimeDefault  # 컨테이너 런타임의 기본 Seccomp 룰 강제 적용
  ```
- **OPA Gatekeeper와의 연동**: K8s 클러스터 내에 배포되는 모든 파드가 `RuntimeDefault` 이상의 Seccomp 프로파일과 AppArmor 프로파일을 강제로 탑재하도록 OPA 제약 조건(Constraint)을 걸어 배포 파이프라인에서 검증.

### Ⅴ. 결론 및 실무적 판단 포인트
- 인프라 운영 조직의 보안 담당자는 서버 트러블슈팅 시 개발자가 흔히 요구하는 "SELinux 끄고 할게요(`setenforce 0`)"라는 요청을 단호히 거절해야 합니다. 컨테이너 런타임(containerd, CRI-O) 자체의 취약점(예: runc 탈옥 버그)이 발생했을 때, 클러스터의 전멸을 막아주는 유일한 최후의 보루는 커널 레벨의 MAC(AppArmor/SELinux)과 Seccomp뿐입니다. Audit 로그 기반의 자동 프로파일 생성 도구(예: oci-seccomp-bpf-hook)를 데브옵스 파이프라인에 통합하여 **"마찰 없는(Frictionless) 커널 샌드박싱"** 을 구현해야 합니다.

### 💡 문제 유형별 목차 전환 포인트
- **[컨테이너 취약점(탈옥/Escape) 위협과 리눅스 커널 레벨 보안 격리 방안]**: Ⅰ번과 Ⅱ번(Seccomp 시스템 콜 차단 원리)을 중심으로 서술. 컨테이너가 가상 머신(VM)과 달리 커널을 공유하여 겪는 태생적 취약점을 어떻게 샌드박싱하여 방어하는지 기술.
- **[리눅스 접근 통제 모델(DAC vs MAC) 비교 및 클라우드 네이티브 환경 적용 방안]**: Ⅲ번(AppArmor와 SELinux의 차이점)을 전면에 내세워 MAC 모델의 루트 권한 통제 메커니즘을 증명하고, Ⅳ번(K8s SecurityContext 적용)으로 마무리하여 실무적 배포 아키텍처 제시.
