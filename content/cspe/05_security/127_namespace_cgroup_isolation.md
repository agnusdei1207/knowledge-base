## 1. 한눈에 이해하기 (Core Intuition)
- **정의**: 도커(Docker) 같은 **'컨테이너' 기술이 마법처럼 1대의 컴퓨터를 수십 대처럼 쪼개 쓸 수 있게 만들어주는 리눅스의 가장 밑바닥 핵심 뼈대 기술 2가지**입니다.
- **필요성**: 1대의 서버에 네이버 앱과 카카오 앱을 같이 깔면, 둘 다 "내가 80포트를 쓸래!" 하고 싸우거나, 악성코드가 걸린 A 앱이 서버 CPU 메모리를 100% 독식해서 B 앱까지 다 죽여버립니다. 서로 못 보게 눈을 가리고(Namespace), 각자 쓸 수 있는 컴퓨터 자원의 양(밥그릇)을 엄격하게 제한(cgroup)하는 완벽한 가벽(칸막이)이 필요했습니다.
- **핵심 직관**: **"쉐어하우스의 방음벽과 식권 배급"**. 
  - 과거 (통짜 서버): 거실 하나에 10명이 삽니다. 한 명이 TV를 크게 틀거나 냉장고 음식을 다 먹어치우면 9명이 굶어 죽습니다.
  - **Namespace (방음벽/시야 차단)**: 10명에게 각자의 방을 주고 두꺼운 벽을 칩니다. A방 사람은 자기가 혼자 이 집을 다 쓴다고 착각합니다. 옆방에 누가 있는지(프로세스), 옆방 구조가 어떤지(네트워크) 아예 볼 수가 없습니다.
  - **cgroup (식권 배급/자원 제한)**: "A방 사람은 하루에 물 1리터(RAM)와 전기 100W(CPU)만 쓸 수 있어!"라고 목줄을 채웁니다. A방 사람이 발악해도 절대 B방 사람의 물을 뺏어 먹을 수 없습니다.

## 2. 왜 중요한가? (Background & Value)
- **등장 배경**: 과거에는 서로 격리하기 위해 크고 무거운 가상 머신(VM, VMWare 등)을 썼습니다. VM은 컴퓨터 안에 또 '운영체제(OS 윈도우)'를 통째로 까는 짓이라 부팅만 1분이 걸리고 너무 무거웠습니다. 리눅스 진영에서 "OS는 1개만 쓰고, 프로세스(앱)들 사이에 얇은 가벽만 쳐주자!"라고 발명한 기술이 Namespace와 cgroup이며, 이 두 기술이 융합되어 오늘날의 '도커(Docker)'와 클라우드 혁명을 탄생시켰습니다.
- **가치**: "초경량 독립 왕국의 완성". 컨테이너 100개를 1초 만에 띄울 수 있는 미친 속도의 원천이자, 서로가 서로를 해킹하거나 자원을 갉아먹지 못하게(Noisy Neighbor 방어) 만드는 클라우드 네이티브 보안의 가장 근본적인 토대입니다.

## 3. 어떻게 작동하는가? (Mechanism)

1. **Namespace (네임스페이스) - "너는 이 우주에 너 혼자야" (가시성 격리)**
   - 리눅스 커널이 각 컨테이너에게 "거짓말(환상)"을 보여주는 기술입니다. 대표적인 6가지 벽이 있습니다.
   - **PID (프로세스 ID)**: 원래 컴퓨터엔 1,000개의 프로그램이 돌지만, 컨테이너 안에서 `ps`를 치면 자기 자신(PID 1) 딱 하나만 보입니다.
   - **NET (네트워크)**: 각 컨테이너에게 자기만의 IP 주소와 랜카드(eth0)가 있는 것처럼 환상을 줍니다.
   - **MNT (마운트)**: 자기 방에 있는 하드디스크 폴더만 보이고, 옆방의 파일은 아예 없는 것처럼 가려버립니다.
   - **IPC, UTS, USER**: 메모리 통신, 서버 이름, 사용자(root) 계정을 철저히 남들과 분리합니다.

2. **cgroup (Control Groups) - "너의 밥그릇은 여기까지야" (자원 격리)**
   - 구글(Google)의 엔지니어들이 리눅스에 기증한 핵심 기술입니다.
   - 아무리 덩치가 큰 컨테이너(DB)라도, cgroup으로 "CPU 2코어, 메모리 4GB 한도!"를 걸어두면 그 이상 절대 자원을 끌어다 쓸 수 없습니다.
   - 해커가 접속해 메모리 폭탄 코드를 돌려도(DDoS), 딱 그 4GB까지만 차오르고 그 컨테이너만 조용히 픽 죽어버리며 호스트 전체(클러스터)는 평온을 유지합니다.

## 4. 실전 활용 및 예시 (Real-world Application)
- **구체적 사례**: 
  - 개발자가 도커(Docker)로 파이썬 서버를 띄울 때 `docker run -m 512m --cpus=1 my_app` 명령어를 칩니다. 이 명령어 한 줄이 뒤에서는 "리눅스 **cgroup**아, 이 앱은 메모리 512MB, CPU 1개로 제한해 줘!"라고 번역되어 실행되는 것입니다.
  - 또, 컨테이너에 들어가면 자기가 최상위 마스터 권한(root)인 줄 알지만, 이것은 **USER Namespace**가 보여주는 환상일 뿐입니다. 진짜 서버(호스트) 입장에서는 그냥 권한 없는 쪼랩 유저 번호(1001번)로 돌아가고 있습니다.
- **주의점 및 흔한 오해**: 
  - "이 2개로 완벽히 격리되나요?" $\rightarrow$ 아닙니다. 두꺼운 벽(VM)이 아니라 얇은 가벽(컨테이너)이므로, 해커가 이 벽의 틈새(커널 취약점)를 비집고 나와 호스트를 털어버리는 기술(컨테이너 탈옥)이 존재합니다. 그래서 앞서 배운 Seccomp, AppArmor 같은 커널 보안 3대장을 덧발라 벽을 철근 콘크리트로 보강해야 하는 것입니다.

## 5. 핵심 비교 및 연결 개념 (Relation)
| 구분 | 하이퍼바이저 기반 VM (가상 머신) | 컨테이너 (Namespace + cgroup) |
|---|---|---|
| **격리 수준** | 하드웨어 칩(CPU/RAM) 수준의 **물리적 완벽 격리**. (보안성 최고) | 리눅스 커널(OS) 단의 **논리적 얇은 격리**. (보안성 보통) |
| **무게/속도** | OS를 매번 깔아야 해서 기가바이트(GB) 단위. 부팅 분 단위. | 앱 껍데기만 있어서 메가바이트(MB) 단위. 부팅 초 단위. |

# ✍️ 단답형 / 서술형 시험장 출격 준비

### Ⅰ. 핵심 인사이트
- **본질**: 하이퍼바이저(Hypervisor)를 통한 무거운 가상화(Hardware-level Virtualization) 대신, 단일 리눅스 커널 위에서 **프로세스들의 가시성(Visibility)을 논리적으로 분리하는 Namespace(네임스페이스)와 컴퓨팅 리소스(CPU/Mem) 사용량을 물리적으로 제한하는 cgroup(컨트롤 그룹)을 결합하여 구현한 OS 레벨 경량 가상화(OS-level Virtualization)의 2대 코어 기술.**
- **가치**: 클라우드 네이티브 환경(Docker, Kubernetes)이 탄생할 수 있었던 기술적 근간. 동일한 호스트 내에서 실행되는 수백 개의 멀티 테넌트(Multi-tenant) 워크로드 간의 상호 간섭(Interference)을 차단하고, 특정 파드가 자원을 독식하는 시끄러운 이웃(Noisy Neighbor) 현상과 자원 고갈(Resource Exhaustion) 기반의 DDoS 공격을 원천적으로 억제함.
- **판단 포인트**: IT 인프라 설계 시, 컨테이너의 이 얇은 격리(Soft Isolation)는 본질적으로 '커널을 공유'한다는 태생적 보안 취약점(단일 장애점, SPOF)을 지닙니다. 따라서 멀티 테넌시 보안(서로 다른 고객의 앱 구동)이 극도로 중요한 금융/퍼블릭 클라우드에서는, 컨테이너의 민첩성을 유지하면서도 VM의 하드웨어 격리를 제공하는 **경량 가상 머신(MicroVM, 예: AWS Firecracker, Kata Containers)** 이라는 차세대 아키텍처로 진화하고 있음을 이해해야 합니다.

### Ⅱ. Namespace (네임스페이스)의 6대 핵심 격리 영역
리눅스 커널이 프로세스 그룹에 제공하는 독립된 뷰(View)와 식별자.
1. **PID (Process ID)**: 컨테이너 내부 프로세스는 격리된 트리 구조를 가져 자신이 PID 1번(init)인 것으로 인식. 호스트의 다른 프로세스 모니터링 불가.
2. **NET (Network)**: 독립적인 네트워크 스택(IP, 포트, 라우팅 테이블, iptables) 제공. 동일 호스트 내 컨테이너끼리 동일한 포트(80) 충돌 방지.
3. **MNT (Mount)**: 파일 시스템의 마운트 포인트 격리. 호스트의 디렉토리 구조를 보지 못하고, 자신에게 할당된 루트 파일 시스템(Rootfs) 내부만 열람 가능.
4. **IPC (Inter-Process Communication)**: 컨테이너 간의 공유 메모리(Shared Memory)나 메시지 큐 통신이 섞이지 않도록 차단.
5. **UTS (UNIX Timesharing System)**: 독립적인 호스트네임(Hostname)과 도메인 이름 할당.
6. **USER (User ID)**: ★보안의 핵심. 컨테이너 내부에서는 자신이 루트(UID 0)로 보이지만, 호스트 OS 관점에서는 권한이 없는 일반 사용자(예: UID 1000)로 매핑(User Namespace Remapping)하여, 탈옥 시 피해를 최소화함.

### Ⅲ. cgroup (Control Groups)의 자원 통제 메커니즘
서브시스템(Subsystems)을 통한 하드웨어 리소스 할당 및 감사(Accounting).
- **CPU 제한 (cpu, cpuset)**: 컨테이너가 사용할 수 있는 CPU 코어 점유율 시간(Quota)을 강제. 특정 코어 핀셋 할당(Pinning) 가능.
- **메모리 제한 (memory)**: 최대 RAM 사용량을 바이트 단위로 캡핑(Capping). 한도를 초과하면 리눅스 커널의 OOM(Out Of Memory) Killer가 개입하여 해당 컨테이너 프로세스를 강제 사살(Kill)하여 호스트 메모리 패닉 방지.
- **디스크 I/O (blkio)**: 초당 블록 디바이스 읽기/쓰기 대역폭(Bandwidth) 및 IOPS를 제한.
- **디바이스 접근 (devices)**: 컨테이너가 접근할 수 있는 물리적 장치(예: `/dev/null`, GPU 장치 등)의 화이트리스트를 관리.

### Ⅳ. 격리 우회 위협(Container Escape)과 아키텍처 방어책
- **위협 시나리오**: 해커가 컨테이너 내부의 취약점(예: runc 버그)을 익스플로잇(Exploit)하여 Namespace 장막을 찢고 호스트 커널의 메모리 영역에 침투하거나, 특권(Privileged) 모드로 실행된 컨테이너가 호스트의 디바이스(cgroup devices 우회)를 직접 마운트하여 장악.
- **방어 아키텍처**:
  1. **User Namespace Remapping 활용**: 반드시 컨테이너 엔진 설정에서 유저 네임스페이스 매핑을 활성화하여 Rootless 컨테이너 환경 구축.
  2. **SecurityContext 통제**: K8s 배포 시 `hostNetwork: true` (NET 네임스페이스 공유)나 `hostPID: true` 옵션을 OPA Gatekeeper로 원천 거절(Deny).
  3. **Kata Containers 등 마이크로 VM 결합**: 하드웨어 가상화 계층(Hypervisor)을 컨테이너 하단에 추가하여 격리벽을 철근 콘크리트로 강화.

### Ⅴ. 결론 및 실무적 판단 포인트
- 인프라 운영자는 쿠버네티스 파드 배포 시 리소스(Requests/Limits) 설정을 선택이 아닌 **강제(Mandatory) 보안 컴플라이언스**로 다루어야 합니다. Limit 설정(cgroup 제어)이 누락된 단 1개의 애플리케이션에 메모리 누수(Memory Leak)가 발생하면, 동일 노드(Node)에 떠 있는 다른 정상적인 결재 파드와 인증 파드까지 연쇄적으로 OOM(Out of Memory)으로 추락하는 아키텍처 전체의 연쇄 붕괴를 초래하기 때문입니다.

### 💡 문제 유형별 목차 전환 포인트
- **[클라우드 네이티브 기반 기술 및 컨테이너 가상화 아키텍처 비교(VM vs Container)]**: Ⅰ번을 중심으로 기존 하이퍼바이저 방식과 OS 레벨 가상화의 구조적 차이를 서술하고, Ⅱ번(Namespace)과 Ⅲ번(cgroup)이 이 가벼운 혁신을 어떻게 지탱하는지 핵심 요소 증명.
- **[마이크로서비스 환경(MSA)의 자원 고갈 위협(DDoS) 및 멀티 테넌시 보안 격리 방안]**: Ⅲ번(cgroup의 OOM 통제)과 Ⅳ번(컨테이너 탈옥/Escape 대응책)을 전면에 세워, 논리적 가벽의 한계를 인정하고 어떻게 보안 컨텍스트(SecurityContext) 튜닝으로 심층 격리를 이뤄내는지 논리 전개.
