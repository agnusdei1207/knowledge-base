# 📖 【암기용】 개념 완전 이해

> 목적: STRIDE·DREAD 위협 모델링을 처음 봐도 완벽히 이해하게 만든다. 시험 답안 양식이 아니라, 이해를 위한 친절한 설명이다.

## 한눈에
- **개요**: 시스템 설계 단계에서 위협 유형과 위험 우선순위를 체계적으로 찾는 방법
- **왜 필요한가**: 침투테스트는 완성된 시스템을 공격하지만, 위협 모델링은 설계도에서 인증·권한·데이터 흐름의 취약 지점을 먼저 찾는다.
- **핵심 직관**: 데이터 흐름도 위에 공격자가 신분 위장, 데이터 변조, 부인, 정보 노출, 서비스 거부, 권한 상승을 시도하는 지점을 표시하는 활동이다.

## 깊이 이해
- **배경·문제의식**: 클라우드·API·마이크로서비스 환경에서는 경계가 많아져 단일 방화벽 기준으로 위험을 설명하기 어렵다. 설계 단계에서 신뢰 경계와 데이터 흐름을 그려야 위협을 누락하지 않는다.
- **작동 원리**: 먼저 DFD(Data Flow Diagram)에 프로세스, 데이터 저장소, 외부 엔터티, 데이터 흐름, 신뢰 경계를 표시한다. 각 요소에 STRIDE 6개 위협을 대입하고, DREAD 또는 CVSS·위험 매트릭스로 우선순위를 정한다.
- **비유**: 건물 도면에 출입문, 금고, 엘리베이터, 외부 통로를 표시한 뒤 침입자가 어떤 방식으로 들어올지 미리 표시하는 보안 설계 검토와 같다.
- **구체 예시**: 로그인 API에서 `사용자 -> API Gateway -> Auth Service -> Session Store` 흐름을 그리면 Spoofing은 MFA·OIDC, Tampering은 TLS·서명, Repudiation은 감사로그 통제로 연결된다.
- **흔한 오해·주의점**: DREAD 점수는 팀마다 편차가 크다. 정량 위험으로 단정하지 말고 CVSS, 자산가치, 규제 영향, 사고 이력으로 보완해야 한다.

## 연결 개념
- DFD — 위협을 빠뜨리지 않기 위한 데이터 흐름 표현
- STRIDE — 위협 유형을 6개 범주로 분류하는 체계
- CVSS·Risk Matrix — DREAD 한계를 보완하는 위험 우선순위 방법

# 📝 【답안용】 시험 답안 템플릿

> 목적: 시험장에서 25분에 그대로 쓰는 답안 양식. 작성방식(추상표현 금지·수치·도식·문제유형 전환)을 엄격히 지킨다.
> 핵심: STRIDE 명칭 암기가 아니라, DFD 신뢰 경계별 위협 식별과 완화 통제를 연결해야 한다.

## 핵심 인사이트 (3줄 요약)

> 1. **본질**: STRIDE 위협 모델링은 DFD의 요소별로 Spoofing, Tampering, Repudiation, Information Disclosure, DoS, Elevation 위협을 식별하는 설계 보안 기법이다.
> 2. **가치**: 개발 전 단계에서 인증·무결성·감사·기밀성·가용성·권한 통제를 도출해 재설계 비용을 줄인다.
> 3. **판단 포인트**: DREAD 점수는 주관 편차가 있으므로 CVSS, 자산 중요도, 규제 영향, 사고 가능성으로 보정해야 한다.

## 출제 의도 및 답안 포인트

| 출제 의도 | 반드시 짚을 핵심 | 감점 회피 포인트 |
|:---|:---|:---|
| 설계 보안 분석 역량 확인 | DFD, 신뢰 경계, STRIDE 6종, 완화 통제 | STRIDE 약어만 쓰고 DFD를 누락 |
| 위험 우선순위 판단 확인 | DREAD Damage/Reproducibility/Exploitability/Affected/Discoverability | DREAD를 객관 점수로 단정 |
| 보안 요구사항 도출 확인 | MFA, 서명, 감사로그, 암호화, rate limit, RBAC | 통제가 위협 유형과 매핑되지 않음 |

> 요약: 이 문제는 위협 목록이 아니라 설계 구성요소별 위협과 대응 통제를 추적하는 능력을 요구한다.

---

## Ⅰ. 개요 및 필요성

- 개요: 설계 단계 위협 식별 방법
- 배경: 시스템이 API, 데이터베이스, 외부 연동, 사용자 권한으로 분산되면 코드 완성 후 인증·인가·데이터흐름 결함을 고치는 비용이 커짐
- 필요성: DFD 신뢰 경계에 STRIDE 6종을 적용하고 High 위협 30일 내 조치, DFD 요소 누락 5% 이하 기준으로 보안 요구사항을 backlog에 연결해야 함

---

## Ⅱ. 구조 및 구성요소

```text
자산/범위 -> DFD 작성 -> 신뢰 경계 표시
          -> STRIDE 위협 대입 -> DREAD/CVSS 우선순위
          -> 완화 통제 -> 보안 요구사항
```

| 구성요소 | 역할 | 특이사항 |
|:---|:---|:---|
| DFD | 외부 엔터티·프로세스·저장소·흐름 표현 | 신뢰 경계 표시 필수 |
| STRIDE | 위협 유형 6개로 누락 방지 | 요소별 적용 범위 상이 |
| DREAD | 위험 점수 산정 보조 | 주관 편차, CVSS 보완 필요 |
| 완화 통제 | 요구사항·설계 변경으로 전환 | 인증, 무결성, 감사, 암호화 |

> 요약: STRIDE 위협 모델링은 DFD로 분석 대상을 고정하고 위협 유형별 통제를 보안 요구사항으로 전환한다.

---

## Ⅲ. 동작원리 및 흐름도

```text
시스템 범위 확정 -> DFD 작성 -> 요소별 STRIDE 질문
                -> 위협 시나리오 기록 -> DREAD/CVSS 평가
                -> 통제 설계 -> backlog 반영 -> 재검토
```

| 단계 | 처리 내용 | 검증 기준 |
|:---:|:---|:---|
| 1 | 자산, 사용자, 외부 시스템, 데이터 분류 | 개인정보, 결제정보, 관리자 권한 |
| 2 | DFD와 신뢰 경계 작성 | 모든 외부 입력과 저장소 표시 |
| 3 | STRIDE 6종 위협 대입 | 위협별 공격 시나리오 1개 이상 |
| 4 | DREAD/CVSS로 우선순위 산정 | High 이상 backlog 등록 |
| 5 | 통제·테스트·재검토 수행 | 보안 요구사항 완료 기준 |

> 요약: 흐름은 범위와 DFD를 먼저 고정한 뒤 STRIDE 질문으로 위협을 찾고 위험 점수에 따라 구현 작업으로 전환한다.

---

## Ⅳ. 특징

| 구분 | STRIDE | DREAD | 수치·기준 |
|:---|:---|:---|:---|
| 목적 | 위협 유형 분류 | 위험 우선순위 산정 | 6개 위협, 5개 점수축 |
| 장점 | 누락 방지 질문 체계 | backlog 정렬 근거 | High/Medium/Low 분류 |
| 한계 | 위험 크기 산정 부족 | 평가자 주관 편차 | CVSS v4.0, risk matrix 보완 |
| 산출물 | 위협 목록·통제 매핑 | 위험 점수·조치 순위 | threat ID, owner, due date |

> 요약: STRIDE는 위협을 찾는 도구이고 DREAD는 조치 순서를 잡는 보조 도구이므로 역할을 구분해야 한다.

## Ⅴ. 심화 비교 및 적용 판단

| 구분 | 기존/대안 | 본 키워드 | 선택 기준 |
|:---|:---|:---|:---|
| 분석 시점 | 침투테스트 후반 | 설계·스프린트 초반 | 아키텍처 변경 비용이 큰 시스템 |
| 분석 단위 | 취약점 단품 | 데이터 흐름·신뢰 경계 | API·권한·외부 연동 다수 |
| 점수 방식 | CVSS 단독 | DREAD+CVSS+자산가치 | 정성·정량 혼합 평가 필요 |

> 요약: 설계 변경 영향이 큰 서비스는 침투테스트 이전에 STRIDE로 위협을 선별해야 한다.

| 리스크 | 원인 | 대응 방안 | 확인 지표 |
|:---|:---|:---|:---|
| DFD 누락 | 비공식 API·배치·관리자 기능 미표시 | API inventory, cloud asset scan | DFD 커버리지 95% 이상 |
| 점수 편차 | DREAD 평가자 경험 차이 | 기준표, 2인 검토, CVSS 보정 | 점수 재현성 표본 감사 |
| 통제 미이행 | 위협이 backlog로 연결되지 않음 | owner, due date, acceptance criteria | High 위협 조치율 100% |

> 요약: 위협 모델링 실패는 모델 누락, 점수 편차, 이행 단절에서 발생하므로 산출물 추적 체계가 필요하다.

| 점검 항목 | 목표 기준 | 측정 방법 |
|:---|:---|:---|
| 모델 완성도 | DFD 요소 누락 5% 이하 | 아키텍처 문서·API 목록 대조 |
| 위험 조치 | High 위험 30일 내 조치 | backlog 상태, 보안 승인 기록 |
| 재검토 주기 | 주요 릴리스·권한 변경 시 수행 | release checklist, change review |

> 요약: 성과는 위협 식별 개수보다 DFD 커버리지, High 조치율, 변경 시 재검토 수행률로 판단한다.

## Ⅵ. 실무 적용 및 결론

**적용 방안 3개:**
1. 신규 서비스 설계 리뷰에서 DFD, 신뢰 경계, STRIDE 6종 질문표를 60분 워크숍으로 수행하고 위협 ID를 부여함
2. DREAD는 1~10 점수 대신 High/Medium/Low와 CVSS v4.0, 개인정보·결제 규제 영향으로 보정함
3. High 위협은 Jira backlog에 owner, due date, acceptance criteria를 등록하고 배포 전 보안 승인 조건으로 둠

**결론 (2줄):**
- 기술사 판단: API·클라우드·권한 경계가 복잡한 시스템은 STRIDE를 설계 게이트로 두고 DREAD는 우선순위 보조 지표로 제한한다
- 향후 방향: IaC, API inventory, SBOM 데이터를 DFD와 연결해 지속형 위협 모델링으로 전환한다
