# 📖 【암기용】 개념 완전 이해

## 한눈에
- **개요**: 비대칭 암호화는 **공개키·개인키 한 쌍**으로 암호화·복호화 또는 **전자서명**을 수행하는 공개키 암호 방식이다.
- **왜 필요한가**: 대칭 암호(001)는 통신 전 같은 비밀키를 미리 나눠 가져야 하는 **키 분배 문제**가 있다 — 공개키는 아무에게나 뿌리고 개인키만 숨겨 이 문제를 푼다.
- **핵심 직관**: 우편함 투입구(공개키)는 누구나 편지를 넣을 수 있게 공개하되, 우편함을 여는 열쇠(개인키)는 주인만 갖는 구조다.

## 핵심 용어 정리 (내부에 등장하는 것들)

아래는 답안에 등장하는 모든 내부 용어를, 처음 보는 사람이 이해하도록 비유와 함께 먼저 정리한 것이다.

| 용어/표기 | 의미 | 비유·예 |
|:---|:---|:---|
| 공개키(Public Key) | 누구에게나 배포하는 키 — 암호화·서명 검증에 사용 | 누구나 편지를 넣는 우편함 투입구 |
| 개인키(Private Key) | 소유자만 보관 — 복호화·서명 생성에 사용 | 우편함을 여는 단 하나의 열쇠 |
| 키 쌍(Key Pair) | 수학적으로 짝을 이루는 공개키+개인키 | 한 자물쇠에 대응하는 투입구와 열쇠 |
| 소인수분해 난이도 | 큰 합성수를 소수 곱으로 되돌리기 어려움(RSA 근거) | 두 소수를 곱하긴 쉬워도 다시 쪼개긴 매우 어려움 |
| 이산대수·타원곡선 이산로그 | 곱셈 결과에서 지수를 역산하기 어려움(ECC 근거) | 시계 바늘 위치는 보이나 몇 바퀴 돌았는지 모름 |
| 전자서명 | 개인키로 서명해 위·변조·부인을 막음 | 본인만 가능한 인감 날인 |
| 서명 검증 | 공개키로 서명의 진위를 확인 | 인감 대조로 진짜인지 확인 |
| 인증서(X.509) | "이 공개키가 누구 것인지" CA가 보증한 문서 | 공인기관이 발급한 신분증 |
| CA(인증기관) | 인증서를 발급·서명하는 신뢰 주체 | 신분증을 발급하는 정부기관 |
| 인증서 체인 | 루트 CA→중간 CA→서버로 이어지는 신뢰 사슬 | 상급 기관이 하급 기관을 보증하는 계층 |
| CRL/OCSP | 폐지된 인증서 목록(CRL)·실시간 조회(OCSP) | 분실 신고된 신분증 블랙리스트 조회 |
| 전방향 안전성(PFS) | 장기키가 유출돼도 과거 세션은 안전(ECDHE) | 매번 새 임시 열쇠를 만들어 쓰고 버림 |
| RSA | 소인수분해 기반 공개키 알고리즘 | 대표적 전자서명·키 캡슐화 표준(RSA-2048) |
| ECC/ECDSA | 타원곡선 기반 암호(ECC)·서명(ECDSA) | 짧은 키로 같은 강도(P-256) |

## 깊이 이해
- **배경·문제의식**: 인터넷에서는 처음 만나는 서버와도 안전히 통신해야 하는데, 대칭 암호는 사전에 비밀키를 공유할 방법이 없다 → 수학적으로 연결된 키 쌍으로 공개 채널에서도 키 전달·신원 확인을 가능하게 함.
- **작동 원리(어떻게+왜)**:
  - RSA는 "두 큰 소수를 곱하긴 쉬워도 그 곱을 다시 소인수분해하긴 어렵다"는 비대칭성을 이용한다.
  - ECC는 타원곡선 위 점의 곱셈은 쉬워도 역산(이산로그)은 어렵다는 성질을 이용해, RSA보다 짧은 키로 같은 강도를 낸다(P-256 ≈ RSA-3072).
  - 암호화·키 캡슐화는 수신자 **공개키**로, 복호화는 수신자 **개인키**로 수행함. 서명은 반대로 서명자 **개인키**로 생성하고 **공개키**로 검증함.
- **비유**: 잠금 우편함이다. 투입구 위치(공개키)는 온 동네에 알려도, 우편함 문을 여는 열쇠(개인키)는 주인만 갖는다.
- **구체 예시**: TLS 1.2는 RSA 키 교환을 썼으나, TLS 1.3은 이를 제거하고 ECDHE로 전방향 안전성을 제공한다. 서버 인증서는 RSA-2048 또는 ECDSA P-256을 사용한다.
- **흔한 오해·주의점**: 공개키 암호는 본문 전체를 암호화하는 수단이 **아니다**. 연산이 무겁고 입력 크기 제한이 있어, **세션키 교환·서명·키 캡슐화**에만 쓰고 본문은 AES-GCM(001)으로 암호화한다 → 이 결합이 003 하이브리드다.

## 연결 개념
- 대칭 암호(001) — 공개키가 못 푸는 대량 본문 암호화를 담당
- 하이브리드 암호(003) — 비대칭으로 대칭 세션키를 안전하게 전달
- PKI·전자서명 — 공개키의 소유자 신뢰를 인증서로 보증, 개인키로 서명·공개키로 검증

# 📝 【답안용】 시험 답안 템플릿

## 핵심 인사이트 (3줄 요약)

> 1. **본질**: 비대칭 암호화는 공개키·개인키를 분리해 키 분배·인증·전자서명 문제를 해결하는 공개키 체계임.
> 2. **가치**: RSA·ECC가 TLS·PKI·코드서명에서 신원 확인과 세션키 보호를 담당함.
> 3. **판단 포인트**: 본문 암호화가 아니라 키 교환·서명·인증에 배치하고, 키 길이와 인증서 수명·폐지 상태를 함께 관리해야 함.

## 출제 의도 및 답안 포인트

| 출제 의도 | 반드시 짚을 핵심 | 감점 회피 포인트 |
|:---|:---|:---|
| 공개망 위장·중간자·부인 위협을 PKI 통제와 연결하는 역량 확인 | 공개키·개인키 역할, RSA-2048·ECC P-256, X.509, CA chain, CRL/OCSP, 전자서명 부인방지 | 공개키로 본문 전체 암호화 가정, 인증서 폐지 누락, 암호화·서명 목적 혼동 |

> 요약: 비대칭 암호 답안은 키 쌍 구조를 넘어 인증서 신뢰와 개인키 통제까지 확장해야 함.

---

## Ⅰ. 개요 및 필요성

- 개요: 공개키·개인키 쌍 기반 공개키 암호
- 배경: 공개망은 통신 전 비밀키 공유가 불가하고, 서버 신원 확인 없이는 중간자(MITM)에 노출됨
- 필요성: RSA-2048·ECC P-256·ECDHE를 키 교환·전자서명·인증서 검증에 적용해 웹·클라우드 신뢰 체계를 구성함

---

## Ⅱ. 구조 및 구성요소

```text
키 쌍 생성 -> 공개키를 X.509 인증서로 바인딩 -> CA 서명
공개키: 암호화·서명 검증  |  개인키: 복호화·서명 생성(HSM 보관)
신뢰 검증: 인증서 체인 확인 -> CRL/OCSP 폐지 조회
```

| 구성요소 | 역할 | 특이사항 |
|:---|:---|:---|
| 공개키 | 암호화·서명 검증 | 인증서로 소유자 바인딩 필요 |
| 개인키 | 복호화·서명 생성 | HSM·TPM·파일 권한으로 보호 |
| 알고리즘 | RSA·ECC·ECDHE | RSA-2048 이상, ECC P-256 이상 권장 |
| 인증서 | 공개키 소유자 증명 | X.509, CA 서명, CRL/OCSP 폐지 확인 |

> 요약: 비대칭 암호는 키 쌍·알고리즘·인증서·폐지 검증이 함께 동작할 때 신뢰 가능한 공개키 사용이 됨.

---

## Ⅲ. 동작원리 및 흐름도

```text
키 쌍 생성 -> CA가 공개키 인증서 발급 -> 상대 인증서 체인·폐지 검증
-> 공개키로 세션키 캡슐화 또는 서명 검증 -> 개인키로 복호화 또는 서명 생성
```

1. RSA/ECC 키 쌍을 생성함(RSA-2048 이상, ECDSA P-256 이상)
2. CA가 Subject·SAN·KeyUsage를 담은 X.509 인증서를 발급함
3. 검증 측이 인증서 체인·만료·CRL/OCSP 폐지 상태를 확인한 뒤, 송신자 공개키로 세션키를 캡슐화하거나 서명을 검증함
4. 개인키 보유자가 개인키로 복호화하거나 서명을 생성하며, 개인키는 HSM 정책으로 보호함

---

## Ⅳ. 특징

- 사전 비밀키 공유 없이 신뢰 연결 — PKI·CA·OCSP 기반으로 초면 상대의 신원을 검증
- 대량 본문 암호화에는 부적합 — 연산이 무겁고 RSA는 입력 크기 제한이 있어 본문은 대칭 암호로 위임
- 전자서명으로 무결성·인증·부인방지 제공 — 개인키 서명은 본인만 가능해 사후 부인을 차단
- ECC는 RSA보다 짧은 키로 동일 강도 — P-256 ≈ RSA-3072, 모바일·IoT에 유리
- 신뢰의 뿌리는 개인키 보호와 인증서 수명 관리 — 개인키 유출·인증서 폐지 실패 시 체계 전체가 무너짐

---

## Ⅴ. 심화 비교 및 적용 판단

- RSA와 ECC는 보안 강도가 유사하나 키 길이·용도가 달라, 환경에 맞춰 선택하는 것이 핵심 판단임.

| 구분 | RSA | ECC(ECDSA) |
|:---|:---|:---|
| 수학적 근거 | 소인수분해 난이도 | 타원곡선 이산로그 난이도 |
| 동일 강도 키 길이 | RSA-3072 | P-256(약 1/12 길이) |
| 적합 환경 | 레거시 호환·범용 서버 | 모바일·IoT·저대역 |

> 요약: 신규·경량 환경은 ECC P-256, 레거시 호환이 필요하면 RSA-2048 이상을 선택함.

- 리스크 — 개인키 유출: 파일 저장·과다 권한이 원인 → HSM/TPM 보관·키 내보내기 금지로 대응
- 리스크 — 인증서 오용: CN/SAN 불일치·만료가 원인 → 자동 갱신·OCSP Stapling으로 대응
- 리스크 — 알고리즘 노후: RSA-1024·SHA-1 사용이 원인 → RSA-2048·SHA-256 이상 강제로 대응

---

## Ⅵ. 실무 적용 및 결론

**적용 방안 3개:**
1. TLS 서버 인증서: RSA-2048 이상 또는 ECDSA P-256 인증서를 사용하고 SAN 검증·OCSP Stapling을 적용함
2. 개인키 보호: HSM·TPM에 개인키를 저장하고 관리자 2인 승인·키 내보내기 차단 정책을 적용함
3. 알고리즘 관리: SHA-1·RSA-1024 인증서를 차단하고 398일 이하 인증서 수명과 자동 갱신 파이프라인을 운영함

**결론:**
- 조건부 판단: 비대칭 암호는 공개망 신뢰·키 교환에 배치하고, 본문 암호화는 AES-GCM(001)과 결합해야 함
- 향후 방향: 양자컴퓨팅 리스크에 대비해 RSA/ECC 의존 구간을 식별하고 ML-KEM·ML-DSA 전환 계획 수립 필요
