## Ⅰ. 개요
| 항목 | 내용 |
|---|---|
| **정의** | 송신자의 개인키로 메시지의 해시값을 암호화하여 전자 문서의 무결성, 인증, 부인 방지를 보장하는 기술임 |
| **배경/필요성** | 종이 문서의 수기 서명이나 인감을 대체하여 온라인상에서 행위자의 신원과 문서 위변조 여부를 확증할 수단 필요 |
| **출제 의도** | 공개키 암호 방식을 역으로 활용하는 서명/검증의 원리와 제공하는 3대 보안 요건 파악 |

## Ⅱ. 구성요소
```text
+-------------------+      +-------------------+      +-------------------+
|  Original Message |      |   Hash Function   |      | Signature Value   |
| (서명할 원본 문서)+----->|  (메시지 다이제스트)+----->| (개인키로 암호화) |
+-------------------+      +-------------------+      +-------------------+
```
| 구성요소 | 설명 | 비유 |
|---|---|---|
| **원본 문서 (Message)** | 서명자가 보증하고자 하는 전자 형태의 데이터임 | 결재 서류 |
| **해시값 (Digest)** | 원본 문서의 무결성을 증명하기 위해 추출한 고유 압축값임 | 서류의 요약본 |
| **서명값 (Signature)** | 추출한 해시값을 서명자의 개인키로 암호화한 데이터 덩어리임 | 인감 도장 및 인영 |

> 요약: 메시지 축약본에 개인키로 도장을 찍어, 공개키를 가진 누구나 검증할 수 있게 하는 체계임.

## Ⅲ. 절차
```text
+----------------+   +----------------+   +----------------+   +----------------+
| 1. 해시 추출   |-->| 2. 서명 생성   |-->| 3. 서명 전송   |-->| 4. 서명 검증   |
| (송신자 수행)  |   | (개인키 암호화)|   | (원본+서명값)  |   | (공개키 복호화)|
+----------------+   +----------------+   +----------------+   +----------------+
```
1. **해시 추출**: 송신자가 원본 문서(메시지)를 해시 함수에 통과시켜 다이제스트(해시값)를 생성함
2. **서명 생성**: 생성된 다이제스트를 송신자 자신의 개인키로 암호화하여 전자서명 값을 만듦
3. **서명 전송**: 원본 문서에 생성된 전자서명 값을 첨부하여 수신자에게 전송함
4. **서명 검증**: 수신자는 송신자의 공개키로 서명값을 복호화하여 얻은 해시값과, 직접 메시지를 해싱한 값을 비교해 일치 여부 확인

> 요약: 송신자의 개인키 암호화(생성)와 수신자의 공개키 복호화(검증)를 통해 문서의 진위성을 확정함.

## Ⅳ. 문제점
* **공개키의 신뢰성 부재**: 서명 검증에 사용하는 공개키 자체가 가짜(위장 공격)인지 확인할 자체적 방법이 없음
* **개인키 유출 시 치명적**: 서명용 개인키가 해킹 등으로 유출되면 타인이 언제든 완벽한 위조 서명을 생성할 수 있음
* **대용량 데이터의 서명 지연**: 비대칭 암호 연산을 직접 원본 데이터 전체에 적용하면 속도 저하가 심각하게 발생함

## Ⅴ. 개선방안
* **단기 방안 (해시 기반 서명)**: 원본 전체 대신 단방향 해시값만을 비대칭 암호화하여 서명 속도 및 효율성 최적화
* **중기 방안 (안전한 키 보관)**: 하드웨어 보안 모듈(HSM)이나 보안 토큰을 사용하여 개인키의 외부 유출 원천 차단
* **장기 방안 (PKI 연동)**: 공인된 인증 기관(CA)에서 발급한 인증서(PKI)를 기반으로 공개키의 신원과 유효성을 제3자가 보증

## Ⅵ. 전망
* 핀테크, 전자계약 등 비대면 서비스의 핵심 근간 기술로서 블록체인의 스마트 컨트랙트 서명 등으로 활용 범위가 대폭 확장됨
* 양자 컴퓨터 시대에 대응하여 다항식 및 격자 기반 알고리즘 등을 활용한 양자내성 전자서명(PQC) 체계로의 전환이 요구됨
