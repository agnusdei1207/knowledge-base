## 1. 한눈에 이해하기 (Core Intuition)
- **정의**: 개발자가 코드를 짜서 서버에 자동 배포(업데이트)될 때까지 거치는 '소프트웨어 자동화 공장(CI/CD 파이프라인)' 그 자체가 **해커의 먹잇감이 되지 않도록 조립 라인 시스템과 인증키, 저장소(GitHub, Jenkins 등)를 철통같이 보호하는 보안 기술**입니다.
- **필요성**: 해커가 게임 서버를 하나하나 해킹하기는 어렵습니다. 하지만 게임 코드를 찍어내는 '공장(CI/CD 서버)' 하나만 해킹하면, 정상적인 업데이트 파일에 악성코드를 몰래 섞어서 수십만 명의 유저 PC에 자동으로 악성코드를 배포(서플라이 체인 공격)할 수 있습니다. 
- **핵심 직관**: **"수도 정수장(수원지) 독극물 테러 방어"**. 
  - 과거: 집집마다 정수기(백신, 방화벽)를 달아서 물을 깨끗하게 마셨습니다.
  - 현대 해커: 집집마다 털지 않고, 도시 전체로 물을 보내는 **중앙 상수도 펌프장(CI/CD 젠킨스 서버)** 에 독(악성코드)을 탑니다. 이 펌프장이 털리면 아무리 좋은 코드를 개발해도 배포되는 순간 쓰레기가 되므로, 펌프장 자체의 출입 통제와 시스템 보안을 지키는 것이 CI/CD 파이프라인 보안입니다.

## 2. 왜 중요한가? (Background & Value)
- **등장 배경**: 대표적으로 2020년 전 세계를 강타한 **'솔라윈즈(SolarWinds) 사태'** 가 있습니다. 솔라윈즈 회사의 CI/CD 배포 시스템(오리온)이 털리는 바람에, 미국 펜타곤(국방부)을 포함한 전 세계 수만 개 대기업 고객사 네트워크에 악성 업데이트가 합법적(?)으로 설치된 최악의 공급망 공격 사건입니다.
- **가치**: 회사의 '심장부'를 지킵니다. 아무리 DevSecOps를 잘해서 소스코드의 버그를 잡았더라도, 코드를 서버로 옮겨주는 '배달원(Jenkins, GitLab CI)'이 해킹당하면 시스템 권한, DB 패스워드, 클라우드 접근 키(AWS Key)가 통째로 털리는 재앙을 막아줍니다.

## 3. 어떻게 작동하는가? (Mechanism)
CI/CD 보안은 크게 4가지 통제 구역으로 나뉩니다.

1. **소스코드 저장소 보호 (Source Control / SCM)**
   - GitHub, GitLab 같은 코드 보관소입니다.
   - 해커가 퇴사자의 아이디로 로그인해 악성 코드를 몰래 끼워 넣는 것을 막기 위해 **다중 인증(MFA)** 을 강제하고, 개발자 한 명이 짠 코드는 무조건 다른 책임자가 확인해야만 합쳐지도록 **코드 리뷰(Branch Protection) 승인 결재**를 설정합니다.
2. **시크릿 키(Secrets) 관리**
   - 개발자들이 급하다고 소스코드 안에 AWS 클라우드 비밀번호나 DB 암호를 그냥 적어놓는(하드코딩) 경우가 많습니다. 
   - 파이프라인 보안은 **HashiCorp Vault나 AWS Secrets Manager** 같은 '안전 금고'를 두고, 코드가 실행될 때만 금고에서 임시 비밀번호를 빌려오도록 아키텍처를 분리합니다. (코드에는 비밀번호가 안 보임).
3. **빌드 서버(CI) 보안 (Jenkins 등)**
   - 빌드 서버(Jenkins)는 회사의 모든 서버에 접속할 수 있는 '슈퍼 권한'을 가집니다.
   - 해커가 이 권한을 탈취하지 못하게 Jenkins 관리자 페이지를 인터넷(외부)에서 아예 접속 못 하게 막고, 권한을 최소화(PoLP)합니다.
4. **무결성 검증 및 서명 (Artifact Signing)**
   - 코드가 다 만들어져 배포 파일(도커 이미지 등)이 완성되면, 그 즉시 암호학적 도장(전자 서명)을 찍습니다.
   - 운영 서버에 올라갈 때 "이 도장 찍힌 파일만 정상이다. 중간에 해커가 가로채서 1바이트라도 위조한 파일이면 절대 실행하지 마라!"라고 차단(Admission Control)합니다.

## 4. 실전 활용 및 예시 (Real-world Application)
- **구체적 사례**: 
  - **시크릿 스캐닝(Secret Scanning)**: 개발자가 실수로 깃허브 오픈소스 저장소에 사내 DB 비밀번호가 적힌 코드를 올리는 순간, 깃허브의 백그라운드 봇이 이를 1초 만에 스캔하여 즉시 비밀번호를 무효화(Revoke)시키고 보안팀에 알람을 보냅니다.
- **주의점 및 흔한 오해**: 
  - "DevSecOps"와 "CI/CD 보안"은 비슷한 듯 다릅니다. 
    - **DevSecOps**: 파이프라인 위를 굴러가는 **'앱(코드) 자체의 보안'** (SAST, DAST 적용).
    - **CI/CD 보안**: 그 앱을 굴려주는 **'컨베이어 벨트(파이프라인 인프라) 자체의 보안'** (Jenkins 서버 방어, 권한 통제).

## 5. 핵심 비교 및 연결 개념 (Relation)
- **공급망 공격(Supply Chain Attack) vs 파이프라인 보안**:
  - 해커는 타깃 기업을 직접 공격하기 너무 힘드니, 그 기업에 소프트웨어를 납품하는 **하청 업체의 CI/CD(배포 서버)** 를 공격 타깃으로 삼습니다. 
  - 따라서 파이프라인을 철저히 지키는 것은 자사뿐만 아니라 내 소프트웨어를 사서 쓰는 수만 명의 고객을 공급망 공격으로부터 지키는 국가적 의무가 되었습니다.

# ✍️ 단답형 / 서술형 시험장 출격 준비

### Ⅰ. 핵심 인사이트
- **본질**: 소스코드가 빌드, 테스트, 배포되는 자동화된 경로(Pipeline) 인프라 자체를 공격자의 변조 및 권한 탈취로부터 방어하기 위해 식별, 접근 통제, 시크릿(Secrets) 관리, 무결성 검증을 포괄적으로 수행하는 시스템 보안 아키텍처.
- **가치**: SolarWinds 사태와 같은 대규모 **소프트웨어 공급망 공격(Software Supply Chain Attack)** 의 핵심 타깃인 CI/CD 플랫폼의 권한 남용을 방어하고, 악의적 페이로드가 Production(운영망) 환경에 주입되는 경로를 원천 차단함.
- **판단 포인트**: 현대의 파이프라인 시스템(Jenkins, GitHub Actions, GitLab CI)은 인프라 제어(IaC) 권한과 인증서를 모두 들고 있는 '신뢰의 단일 장애점(Single Point of Compromise)'이므로, 무결성을 보증할 수 있는 서명 체계(Code Signing)와 격리된 환경(Zero Trust) 구축이 아키텍처의 필수 선결 요건임.

### Ⅱ. 파이프라인 각 단계별 보안 통제 프레임워크 (Top 4 Threats & Defenses)
1. **SCM (소스코드 저장소) 오염 방어**
   - 위협: 계정 탈취를 통한 악의적 코드 커밋(Commit).
   - 통제: 전 개발자 MFA(다중 인증) 의무화. Master/Main 브랜치에 직접 푸시(Push) 금지 및 최소 2명 이상의 동료 검토(Peer Code Review)를 강제하는 **Branch Protection Rules** 적용.
2. **Secrets (크레덴셜/인증서) 하드코딩 및 유출 방어**
   - 위협: 소스코드나 환경 설정 파일에 AWS Secret Key, DB 패스워드가 평문으로 박혀 깃허브에 노출.
   - 통제: 소스코드 내 시크릿 자동 탐지(Secret Scanning) 차단. HashiCorp Vault, AWS Secrets Manager 등 **비밀 정보 관리 전용 외부 저장소(Vault)** 와의 API 연동을 통한 동적 시크릿 주입(Just-in-Time Access).
3. **CI 빌드 서버(Build Server) 침해 방어**
   - 위협: 외부에 노출된 Jenkins 관리자 콘솔을 브루트포스(RCE 취약점)로 탈취.
   - 통제: 빌드 서버를 외부 인터넷과 차단된 프라이빗 망에 격리. 임시 컨테이너 기반(Ephemeral)의 1회용 빌드 러너(Runner)를 사용하여 빌드 종료 시 환경 파괴(잔존 악성코드 제거).
4. **아티팩트 무결성(Artifact Integrity) 및 배포 통제**
   - 위협: 빌드가 끝난 정상 도커(Docker) 이미지를 중간 저장소(Registry)에서 악의적 이미지로 바꿔치기(Poisoning).
   - 통제: 빌드 직후 산출물(Artifact)에 **전자 서명(Cosign, Notary)** 을 부여. 배포(CD) 단계에서 쿠버네티스의 Admission Controller가 서명 해시값을 대조하여 일치하는 무결한 이미지만 클러스터에 배포 승인.

### Ⅲ. 파이프라인 보안 아키텍처 핵심 모델: SBOM 적용
- **SBOM (Software Bill of Materials, 소프트웨어 자재 명세서)**:
  - CI 파이프라인 빌드 과정에서, 이 소프트웨어를 만드는 데 사용된 오픈소스 라이브러리(버전 정보, 출처 등)의 목록을 기계 가독형 파일(SPDX, CycloneDX)로 자동 추출.
  - 목적: 훗날 Log4j 같은 제로데이 사태 발생 시, 사내에 배포된 수만 개의 앱 중 어디에 해당 라이브러리가 숨어있는지 1분 안에 추적하여 패치할 수 있는 공급망 가시성(Visibility) 확보.

### Ⅳ. 환경 분리 (Environment Segregation) 거버넌스
- **운영(Production) 환경과의 권한 분리**: 
  - 개발자가 자신의 노트북이나 CI 서버에서 곧바로 운영 서버 인프라를 직접 조작할 권한(AWS Admin 등)을 갖지 못하도록 해야 함.
  - **GitOps 모델 도입**: 배포 파이프라인을 분리하여, 운영망 안쪽에 위치한 에이전트(ArgoCD 등)가 깃허브의 변경 사항(Desired State)을 감지하고 내부망에서 외부의 코드를 '끌어오는(Pull-based 배포)' 안전한 아키텍처를 구성하여 인바운드 방화벽 오픈을 최소화함.

### Ⅴ. 결론 및 실무적 판단 포인트
- CISO와 아키텍트는 데브옵스(DevOps)의 속도를 찬양하기 이전에, **"우리 회사의 빌드 서버가 해킹당하면 고객에게 악성코드를 강제 배포하게 되는가?"** 라는 리스크를 점검해야 합니다. CI/CD 파이프라인은 인프라 구성의 편의성을 위해 과도한 권한이 집약된 상태이므로, '최소 권한의 원칙(PoLP)'과 '직무 분리(SoD)'를 파이프라인 워크플로우 로직에 코드로 하드 캡슐화(Encapsulation)해야 합니다.

### 💡 문제 유형별 목차 전환 포인트
- **[소프트웨어 공급망 공격(Supply Chain Attack) 위협 대응 방안]**: Ⅰ번 솔라윈즈 사태 등 공급망 오염의 파급력을 짚고, 이를 방어하기 위한 Ⅱ번 4대 통제 방안(시크릿/서명)과 Ⅲ번 SBOM을 통한 자재 명세 추적성을 논증.
- **[데브섹옵스 환경 하의 CI/CD 인프라 보호 및 시크릿(Secrets) 관리 전략]**: Ⅱ번을 전면에 내세워 개발 편의성(하드코딩)과 보안 통제(Vault 외부 연동 및 MFA)의 균형을 맞추는 아키텍처 설계와, 무결성 서명 기반의 배포 통제 모델을 상세히 서술.
