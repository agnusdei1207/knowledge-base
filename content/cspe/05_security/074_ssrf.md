## 미리 알고가기

- SSRF는 서버가 대신 요청을 보내는 기능을 악용해 내부망이나 신뢰된 자원에 접근하게 만드는 공격임
- 브라우저가 아니라 서버가 요청 주체가 되므로 외부에서 직접 닿지 않는 자원도 위험해질 수 있음
- 차단의 핵심은 URL 허용 범위 제한, DNS·IP 재검증, 서버 아웃바운드 통제임

## Ⅰ. 개요

- **정의/개념**: SSRF는 이미지 가져오기, 웹훅 호출, URL 미리보기 같은 기능에서 사용자 입력 URL을 서버가 직접 요청하도록 만들어 내부 시스템, 메타데이터 서비스, 관리 포트 등에 접근하게 하는 공격임
- **배경/필요성**: 클라우드 메타데이터, 내부 API, 관리 콘솔처럼 서버만 접근 가능한 자원이 많아지면서 서버 측 요청 기능이 새로운 우회 통로가 되어 별도 통제가 필요함

## Ⅱ. 특징

- 공격자는 직접 내부망에 접근하지 않고 서버의 신뢰된 네트워크 위치를 빌려 우회함
- 응답을 바로 보는 기본 SSRF와 결과를 직접 못 보더라도 요청만 유도하는 Blind SSRF가 있음
- 단순 문자열 차단은 우회 인코딩과 DNS 리바인딩에 취약함
- 애플리케이션 입력 검증과 함께 네트워크 계층의 아웃바운드 제한이 중요함

## Ⅲ. 종류 및 비교

| 판단 기준 | Basic SSRF | Blind SSRF |
|:---|:---|:---|
| 응답 확인 | 응답 내용이 공격자에게 반환됨 | 직접 응답은 보이지 않음 |
| 주요 피해 | 메타데이터 자격증명, 내부 API 응답 유출 | 내부 서비스 호출, 포트 스캔, 비동기 연계 악용 |
| 탐지 포인트 | 비정상 응답 본문과 요청 로그 | 외부 콜백, DNS 로그, 내부망 요청 흔적 |
| 공통 대응 | 허용 목록, DNS/IP 재검증, egress 통제 | 허용 목록, DNS/IP 재검증, egress 통제 |

## Ⅳ. 구성요소 및 구조

| 구성요소 | 설명 |
|:---|:---|
| URL 입력 기능 | 외부 URL을 받아 서버가 요청하는 기능임 |
| 서버 요청 클라이언트 | HTTP 라이브러리, 프록시, 이미지 처리 모듈 등이 포함됨 |
| 내부 대상 자원 | 메타데이터, 내부 API, 로컬호스트, 관리 포트 등임 |
| 방어 통제 | URL 허용 목록, DNS/IP 검증, 리다이렉트 제한, egress 정책이 포함됨 |

```text
사용자 입력 URL -> 서버가 대신 요청 -> 내부/신뢰 자원 접근 -> 응답 노출 또는 부작용 발생
```

## Ⅴ. 원리 및 절차 흐름도

```text
URL 조작 -> 서버 요청 발생 -> 내부망/메타데이터 접근 -> 응답 또는 부작용 발생 -> 탐지/차단
```

1. **URL 조작**: 공격자가 내부 IP나 메타데이터 주소를 입력함
2. **서버 요청 발생**: 애플리케이션이 검증 없이 해당 URL을 요청함
3. **내부 자원 접근**: 외부에서 직접 접근 불가한 자원에 도달함
4. **결과 발생**: 자격 증명 유출이나 내부 서비스 호출이 일어남
5. **탐지와 차단**: 요청 로그, DNS 로그, 네트워크 정책으로 이상을 확인함

## Ⅵ. 실무 적용 및 유의점

1. URL 프리뷰나 웹훅 기능을 제공하는 서비스는 도메인 허용 목록과 DNS 재조회와 내부 대역 차단을 함께 적용해야 하며 메타데이터 주소와 사설 IP 대상 재현 실패와 리다이렉트 우회 차단 여부로 확인함
2. 클라우드 워크로드는 애플리케이션 검증만으로 부족하므로 메타데이터 보호 기능과 egress 방화벽 정책을 함께 써야 하며 내부망 비인가 요청 로그 차단과 자격 증명 유출 경로 제거 여부로 확인함

## Ⅶ. 결론

- SSRF는 서버의 위치와 권한을 빌리는 공격이므로 입력값 검증과 네트워크 아웃바운드 통제를 함께 설계해야 실질적으로 막을 수 있음
