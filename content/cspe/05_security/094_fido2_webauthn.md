## Ⅰ. 개요
| 항목 | 내용 |
|---|---|
| **정의** | 공개키 암호 기반으로 패스워드 없이 생체·보안키로 인증하는 FIDO Alliance의 차세대 인증 표준임 |
| **배경/필요성** | 패스워드 기반 인증의 피싱·재사용·유출 문제를 근본적으로 제거하기 위해 비대칭키 기반 인증이 필요함 |
| **출제 의도** | FIDO2의 공개키 등록·인증 흐름과 피싱 저항 메커니즘을 이해하는지 평가함 |

## Ⅱ. 구성요소
```
+----------+     +----------+     +----------+
| 인증자   | --> | 클라이언트| --> | 서버(RP) |
|(Authenticator)| | (Browser)|     | (의존자)  |
+----------+     +----------+     +----------+
```

| 구성요소 | 설명 | 비유 |
|---|---|---|
| 인증자 | 보안키(YubiKey)·플랫폼 인증자(지문·Face ID)로 개인키를 안전 보관하고 서명을 생성함 | 개인 금고 속 직인 |
| 클라이언트(브라우저) | WebAuthn API를 통해 인증자와 서버 간 통신을 중계함 | 우체부 |
| 의존자(RP) | 등록 시 공개키를 저장하고, 인증 시 챌린지를 발급하여 서명을 검증함 | 은행 창구 직원 |

> 요약: 인증자(개인키 보관·서명) → 브라우저(중계) → 서버(공개키 검증) 구조로 패스워드를 제거함.

## Ⅲ. 절차
```
+------------+     +------------+
| 등록요청   | --> | 챌린지발급  |
| (사용자)   |     | (서버→브라우저)|
+------------+     +------------+
                        |
+------------+     +----+-------+
| 공개키저장  | <-- | 키쌍생성   |
| (서버)     |     | 개인키보관  |
+------------+     +------------+
```

1. 등록 요청: 사용자가 서비스에 FIDO2 인증자 등록을 요청함
2. 챌린지 발급: 서버(RP)가 랜덤 챌린지와 RP ID(도메인)를 브라우저에 전달함
3. 키쌍 생성: 인증자가 RP ID에 바인딩된 공개키·개인키 쌍을 생성하고, 개인키는 인증자 내부에 보관함
4. 공개키 등록: 서명된 공개키를 서버에 전송하여 등록하고, 이후 인증 시 챌린지 서명 검증으로 신원을 확인함

> 요약: 등록(키쌍 생성·공개키 전달) → 인증(챌린지 서명·검증)으로 패스워드 없는 인증을 수행함.

## Ⅳ. 문제점
- 기기 종속성: 개인키가 특정 인증자에 저장되어 기기 분실·교체 시 복구가 어려움
- 레거시 호환: FIDO2 미지원 구형 브라우저·OS에서 사용이 불가함
- 사용자 인식 부족: 패스키 개념에 익숙하지 않은 사용자의 채택 저항이 존재함

## Ⅴ. 개선방안
- (단기) 패스키 동기화: iCloud Keychain·Google Password Manager를 통해 패스키를 클라우드 동기화함
- (중기) 다중 인증자 등록: 복수의 보안키·플랫폼 인증자를 등록하여 단일 기기 의존을 제거함
- (장기) 크로스 디바이스 인증: 하이브리드 전송(caBLE)으로 스마트폰 인증자가 PC 브라우저를 대리 인증함

## Ⅵ. 전망
- Apple·Google·MS의 패스키 기본 탑재로 2027년까지 주요 서비스의 패스워드 제거가 가속화되며, FIDO2가 인증의 사실상 글로벌 표준이 될 전망임
