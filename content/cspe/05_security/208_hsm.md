# 📖 【암기용】 개념 완전 이해

> 목적: HSM을 처음 봐도 완벽히 이해하게 만든다. 시험 답안 양식이 아니라, 이해를 위한 친절한 설명이다.

## 한눈에
- **개요**: 암호키를 장치 밖으로 내보내지 않고 생성·보관·서명·암복호화를 수행하는 전용 보안 장비
- **왜 필요한가**: 인증서 개인키, 결제 키, 전자서명 키, 루트 CA 키가 서버 파일로 저장되면 관리자 계정 탈취 한 번으로 전체 신뢰 체계가 무너진다. HSM은 키 원문을 장비 내부에 묶어 둔다.
- **핵심 직관**: 금고 안에서 도장을 찍어 주되 도장 자체는 금고 밖으로 꺼내지 않는 방식이다.

## 깊이 이해
- **배경·문제의식**: 금융, 인증, 클라우드 KMS, 코드서명은 키 노출 사고가 서비스 신뢰 붕괴로 이어진다. 일반 서버는 메모리 dump, root 권한, 백업 파일로 키가 노출될 수 있어 전용 장비 격리가 필요하다.
- **작동 원리**: HSM은 내부 TRNG로 키를 생성하고, 키는 export 불가 속성으로 저장된다. 애플리케이션은 PKCS#11, JCE, CNG, KMIP API로 서명 또는 암복호화 명령만 요청한다.
- **비유**: 은행 금고 직원에게 봉투를 주면 금고 안 도장으로 날인해 돌려주지만, 도장과 원장은 금고 밖으로 나오지 않는다.
- **구체 예시**: 루트 CA 개인키를 FIPS 140-3 Level 3 HSM에 보관하고, 인증서 서명은 quorum 2 of 3 승인 후 PKCS#11 `C_Sign`으로 수행한다.
- **흔한 오해·주의점**: HSM은 키 유출 통제 장비이지 모든 API 오남용을 막는 장비가 아니다. 권한 정책, 감사로그, rate limit, dual control이 함께 필요하다.

## 연결 개념
- FIPS 140-3 - 암호모듈 보안 요구사항과 검증 레벨
- PKCS#11/KMIP - HSM 접근과 키 관리 표준 API
- Secure Boot/Code Signing - 서명키 보호 사용처

# 📝 【답안용】 시험 답안 템플릿

> 목적: 시험장에서 25분에 그대로 쓰는 답안 양식. 작성방식(추상표현 금지·수치·도식·문제유형 전환)을 엄격히 지킨다.
> 핵심: HSM은 키 생성·보관·사용·백업·감사를 FIPS 140-3, PKCS#11, KMIP 기준으로 설명한다.

## 핵심 인사이트 (3줄 요약)

> 1. **본질**: HSM은 암호키 원문을 장비 내부에 보관하고 애플리케이션에는 서명·암복호화 결과만 제공하는 전용 암호모듈이다.
> 2. **가치**: FIPS 140-3 검증, tamper response, dual control, 감사로그로 루트키·결제키·코드서명키 노출 범위를 제한한다.
> 3. **판단 포인트**: 성능 TPS, HA 클러스터, 백업키 분산, API 표준, 감사·권한 정책을 업무별로 선택해야 한다.

## 출제 의도 및 답안 포인트

| 출제 의도 | 반드시 짚을 핵심 | 감점 회피 포인트 |
|:---|:---|:---|
| 키 관리 구조 이해 확인 | 키 생성, 저장, 사용, export control, tamper response | HSM을 단순 암호 가속기로만 설명 |
| 표준·연동 판단 확인 | FIPS 140-3, PKCS#11, KMIP, JCE, CNG | API 표준과 인증 레벨 누락 |
| 운영 리스크 판단 확인 | HA cluster, backup, quorum, audit log, DR | 단일 HSM 장애와 백업 절차 제외 |
> 요약: 이 문제는 HSM 기능 나열이 아니라 키 생명주기와 운영 통제를 함께 요구한다.

## Ⅰ. 개요 및 필요성

- 개요: 전용 하드웨어 암호키 보호 모듈
- 배경: 루트 CA, 결제, 전자서명, 코드서명 키는 유출 시 인증서·거래·배포 신뢰가 동시에 훼손된다.
- 필요성: FIPS 140-3 검증 장비와 PKCS#11/KMIP 연동으로 키 생성, 보관, 사용, 감사 추적을 분리한다.

---

## Ⅱ. 구조 및 구성요소

```text
Application -> PKCS#11 / KMIP / JCE API -> HSM Partition
HSM Partition -> Key Store / Crypto Engine / Policy Engine
Operation Control -> M of N Quorum / Audit Log / Backup Token
HA Path -> HSM Cluster -> DR HSM -> Secure Backup
```

| 구성요소 | 역할 | 특이사항 |
|:---|:---|:---|
| Crypto Engine | 키 생성·서명·암복호화 수행 | RSA, ECC, AES, HMAC, TRNG |
| Key Store | export 불가 키와 속성 보관 | label, usage, wrap policy |
| Policy Engine | 접근권한·quorum·rate limit 적용 | M of N, role separation |
| Audit/HA | 감사로그, 클러스터, 백업 | syslog, NTP, secure backup |
> 요약: HSM은 암호 연산 장치와 정책·감사·가용성 기능이 결합된 키 관리 플랫폼이다.

---

## Ⅲ. 동작원리 및 흐름도

```text
관리자 승인 -> HSM 내부 키 생성 -> key handle 반환
애플리케이션 요청 -> API 인증 -> 권한·정책 검사
HSM 내부 연산 -> 서명값 또는 암호문 반환 -> 감사로그 기록
장애 발생 -> HA failover -> 백업키 복구 -> 감사 검증
```

| 단계 | 처리 내용 | 검증 기준 |
|:---:|:---|:---|
| 1 | TRNG로 키 생성, export 금지 속성 부여 | key extract attempt 0회 |
| 2 | API 클라이언트 인증과 partition 권한 확인 | mTLS, role policy |
| 3 | 서명·암복호화 요청에 usage policy 적용 | sign/decrypt allowlist |
| 4 | 결과만 반환하고 키 원문은 내부 유지 | plaintext key outside 0건 |
| 5 | 감사로그와 HA 상태 기록 | log loss 0건, failover test |
> 요약: HSM은 키 handle 기반으로 요청을 처리하며 키 원문은 장비 경계 밖으로 이동하지 않는다.

## Ⅳ. 특징

| 구분 | 소프트웨어 키 저장 | HSM 기반 키 저장 | 판단 포인트 |
|:---|:---|:---|:---|
| 키 노출 | 파일·메모리 dump 가능 | export 금지, tamper response | 루트키·서명키는 HSM 우선 |
| 인증 기준 | 내부 통제 중심 | FIPS 140-3 Level 2/3/4 | 규제 요구 레벨 확인 |
| 연동 | SDK 또는 파일 경로 | PKCS#11, KMIP, JCE, CNG | 벤더 종속성과 표준 API 비교 |
| 운영 | 서버 백업으로 복구 | M of N backup, cluster, DR | RTO 30분 이하 목표 |
> 요약: HSM은 키 유출 통제와 감사 근거를 제공하지만, 성능과 HA 설계가 업무 연속성 조건이 된다.

## Ⅴ. 심화 비교 및 적용 판단

| 구분 | 기존/대안 | 본 키워드 | 선택 기준 |
|:---|:---|:---|:---|
| 배포 방식 | 서버 파일 키, KMS software | 온프레미스/클라우드 HSM | root CA, 결제, 규제 키는 HSM |
| API | REST KMS | PKCS#11, KMIP, JCE | 레거시 CA·DB TDE 연동 시 PKCS#11 |
| 성능 | CPU crypto | HSM TPS 제한 | 서명 5,000 TPS 이상이면 cluster 검토 |
> 요약: HSM 선택은 보안 레벨뿐 아니라 API 호환성, TPS, DR 요구를 동시에 비교해야 한다.

| 리스크 | 원인 | 대응 방안 | 확인 지표 |
|:---|:---|:---|:---|
| 단일 장애 | HSM 1대 구성 | active-active cluster, DR HSM | failover RTO 30분 이하 |
| 키 복구 실패 | 백업 토큰·quorum 분실 | M of N key ceremony, 봉인 보관 | restore drill 분기 1회 |
| API 오남용 | 과도한 sign 권한 | least privilege, rate limit, approval | abnormal signing alert 5분 이내 |
> 요약: HSM 운영 리스크는 장애, 복구, 오남용이며 정기 복구 훈련과 감사 탐지로 통제한다.

| 점검 항목 | 목표 기준 | 측정 방법 |
|:---|:---|:---|
| 인증 | FIPS 140-3 Level 3 이상 | 인증서, 보안 정책 문서 |
| 가용성 | cluster 가용성 99.9% 이상 | HA test, monitoring |
| 감사 | 관리자·키 사용 로그 100% 기록 | syslog, SIEM correlation |
| 성능 | 업무 peak TPS의 2배 용량 | load test, queue depth |
> 요약: HSM 도입 효과는 인증 레벨, 가용성, 감사로그 완전성, peak TPS 여유로 검증한다.

## Ⅵ. 실무 적용 및 결론

**적용 방안 3개 (필수 - 단계별 또는 항목별):**
1. 설계 단계: 키 등급을 root CA, intermediate, service key로 분류하고 HSM partition과 usage policy를 매핑함
2. 구축 단계: FIPS 140-3 Level 3 HSM, PKCS#11/KMIP 연동, active-active cluster, NTP·syslog를 구성함
3. 운영 단계: M of N key ceremony, 분기별 restore drill, SIEM 감사, abnormal signing rate 탐지를 수행함

**결론 (2줄):**
- 기술사 판단: 유출 시 전체 신뢰가 무너지는 루트키·결제키·코드서명키는 HSM과 dual control을 기본으로 선택함
- 향후 방향: HSM은 클라우드 KMS, confidential computing, PQC 키 전환과 결합해 엔터프라이즈 키 거버넌스 중심이 됨
