## 미리 알고가기

- DID는 `did:method:identifier` 형태의 식별자이고, DID Document는 그 식별자에 연결된 공개키와 서비스 정보를 담는 문서임
- W3C DID 표준은 식별자 형식과 해석 구조를 정한 것이지 하나의 블록체인 제품을 뜻하지 않음
- 실제 도입에서는 어떤 DID method를 쓸지와 키 회전과 해석 방식이 중요함

## Ⅰ. 개요

- **정의/개념**: W3C DID 표준은 중앙 기관 없이 사용자가 제어 가능한 식별자를 만들고 공개키·서비스 엔드포인트를 표준 방식으로 해석하게 하는 규격임
- **배경/필요성**: 이메일·플랫폼 계정 식별자는 중앙 종속성과 낮은 이동성이 큼. SSI와 VC 생태계의 기반 식별 체계가 필요함

## Ⅱ. 특징

- 식별자와 검증용 공개키 정보를 분리된 문서 구조로 관리함
- 특정 사업자 계정에 종속되지 않는 식별자 체계를 만들 수 있음
- VC와 전자서명 검증의 기반 식별자로 활용되기 좋음
- DID method가 많아 상호운용과 운영 단순화가 과제가 됨

## Ⅲ. 종류 및 비교

| 판단 기준 | 중앙 식별자 | W3C DID |
|:---|:---|:---|
| 발급/관리 주체 | 서비스 제공자 | 사용자/조직이 직접 제어 가능 |
| 공개키 연계 | 별도 시스템 의존 | DID Document에 직접 포함 가능 |
| 이동성 | 제공자 종속 | 상호운용 설계 시 높아질 수 있음 |
| 주요 과제 | 플랫폼 종속 | method 선택, 해석, 키 복구 |

## Ⅳ. 구성요소 및 구조

| 구성요소 | 설명 |
|:---|:---|
| DID | 분산 식별자 문자열 자체임 |
| DID Document | 공개키, 인증 방식, 서비스 엔드포인트를 담음 |
| DID Method | DID를 생성하고 해석하는 규칙 집합임 |
| Resolver and Registry | DID를 실제 Document로 해석해 검증자가 사용하게 함 |

```text
DID 생성 -> DID Document 게시 -> Resolver 해석 -> 공개키/서비스 정보 확인 -> 검증 사용
```

## Ⅴ. 원리 및 절차 흐름도

```text
키 생성 -> DID 작성 -> Document 게시 -> DID 해석 -> 서명 검증 -> 키 회전/갱신
```

1. **키 생성**: 사용자나 조직이 키 쌍을 만듦
2. **DID 작성**: method 규칙에 따라 식별자를 생성함
3. **Document 게시**: 공개키와 메타정보를 연결함
4. **DID 해석**: 검증자가 DID를 Document로 조회함
5. **갱신과 회전**: 키 변경과 서비스 정보 갱신을 수행함

## Ⅵ. 실무 적용 및 유의점

1. DID 도입은 블록체인 여부보다 method 선택과 운영 단순화를 우선 검토하고 해석 성공률과 키 회전 검증 결과로 확인함
2. VC 연계 환경은 resolver 안정성과 공개키 갱신 후 영향 여부와 DID Document 무결성으로 확인함

## Ⅶ. 결론

- W3C DID 표준은 탈중앙 신원의 기초 식별 체계이므로 기술 선택보다 해석과 키 운영과 상호운용 설계를 명확히 하는 것이 중요함
