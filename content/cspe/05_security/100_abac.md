## 미리 알고가기

- 속성은 사용자 부서, 데이터 등급, 접속 위치, 기기 상태처럼 접근 판단에 쓰는 조건값임
- ABAC는 역할 하나만 보는 대신 주체·객체·환경 속성을 조합해 허가 여부를 결정함
- RBAC가 정적 권한 관리에 강하다면 ABAC는 상황별 세밀한 판단에 강함

## Ⅰ. 개요

- **정의/개념**: ABAC는 사용자, 데이터, 장치, 위치, 시간 같은 다양한 속성을 정책 규칙에 대입해 접근 허용 여부를 동적으로 결정하는 접근 제어 모델임
- **배경/필요성**: 원격 근무와 클라우드 환경에서는 같은 사용자라도 위치와 기기와 데이터 민감도에 따라 허용 조건이 달라지므로 역할만으로는 세밀한 제어가 부족함

## Ⅱ. 특징

- 요청 시점의 맥락을 반영해 동적으로 권한을 판단할 수 있음
- 역할 수를 과도하게 늘리지 않고도 세밀한 정책을 표현할 수 있음
- 필요한 속성 품질이 낮거나 실시간 조회가 불안정하면 정책 품질이 흔들림
- 규칙이 많아지면 정책 이해와 감사가 어려워질 수 있음

## Ⅲ. 종류 및 비교

| 판단 기준 | RBAC | ABAC |
|:---|:---|:---|
| 기준 정보 | 역할 중심 | 역할 + 속성 + 환경 |
| 장점 | 단순하고 운영이 쉬움 | 세밀하고 동적인 판단이 가능함 |
| 한계 | 상황별 예외 표현이 제한됨 | 정책과 데이터 품질 관리가 복잡함 |
| 적합 환경 | 고정형 조직 권한 | 원격 근무, 민감 데이터, API 기반 서비스 |

## Ⅳ. 구성요소 및 구조

| 구성요소 | 설명 |
|:---|:---|
| Subject Attributes | 사용자 부서, 역할, 인증 수준 같은 속성임 |
| Object Attributes | 데이터 등급, 소유자, 서비스 종류 같은 속성임 |
| Environment Attributes | 시간, 위치, 기기 상태, 네트워크 같은 속성임 |
| Policy Decision Logic | 속성을 평가해 허가 또는 거부를 결정하는 규칙임 |

```text
접근 요청 -> 주체/객체/환경 속성 수집 -> 정책 평가 -> 허가/거부 결정
```

## Ⅴ. 원리 및 절차 흐름도

```text
요청 수신 -> 속성 조회 -> 정책 엔진 평가 -> 결정 반환 -> 집행과 로그 기록
```

1. **요청 수신**: 사용자가 데이터나 API 접근을 요청함
2. **속성 조회**: 계정, 자원, 장치, 위치 정보를 모음
3. **정책 평가**: 규칙에 따라 속성을 비교함
4. **결정 반환**: 허가 또는 거부를 판단함
5. **집행과 기록**: 결과를 적용하고 근거를 로그로 남김

## Ⅵ. 실무 적용 및 유의점

1. 민감 데이터와 원격 접속이 많은 조직은 ABAC로 위치와 기기와 데이터 등급을 함께 보고 속성 출처를 표준화한 뒤 고위험 상황 차단 성공률과 정책 예외 감소 여부로 확인함
2. 정책이 복잡한 환경은 무리하게 전면 전환하기보다 RBAC 위에 필요한 속성만 덧붙여 성능 지연 허용 범위와 정책 충돌·오탐 건수로 확인함

## Ⅶ. 결론

- ABAC는 접근을 더 세밀하게 만드는 모델이지만 속성 품질과 정책 관리 체계를 함께 갖춰야 운영 가능한 수준이 됨
