## Ⅰ. 개요
| 항목 | 내용 |
|---|---|
| **정의** | 주체·객체·환경의 속성(Attribute)을 조합한 정책 규칙으로 접근 허가를 동적으로 결정하는 접근 제어 모델임 |
| **배경/필요성** | RBAC의 역할 폭발·정적 권한 한계를 해결하기 위해 컨텍스트 기반의 세밀한 동적 접근 제어가 필요함 |
| **출제 의도** | ABAC의 XACML 아키텍처(PEP·PDP·PIP·PAP)와 RBAC 대비 장단점을 이해하는지 평가함 |

## Ⅱ. 구성요소
```
+----------+     +----------+     +----------+
|   PEP    | --> |   PDP    | --> |   PIP    |
| (실행점) |     | (결정점) |     | (정보점) |
+----------+     +----------+     +----------+
```

| 구성요소 | 설명 | 비유 |
|---|---|---|
| PEP | 접근 요청을 가로채고 PDP의 결정을 강제 집행하는 실행 지점임 | 건물 출입문 게이트 |
| PDP | 정책 규칙과 속성을 평가하여 허가·거부를 결정하는 엔진임 | 보안 통제실 판단관 |
| PIP | 주체·객체·환경의 속성 정보를 PDP에 제공하는 정보 수집 지점임 | 신원 조회 데이터베이스 |

> 요약: PEP(요청 가로채기) → PDP(정책 평가·결정) → PIP(속성 조회)로 동적 접근 제어를 수행함.

## Ⅲ. 절차
```
+------------+     +------------+
| 접근요청   | --> | PEP가     |
| 발생       |     | 요청가로챔 |
+------------+     +------------+
                        |
+------------+     +----+-------+
| PEP가     | <-- | PDP가     |
| 결정집행   |     | 정책평가   |
+------------+     +------------+
```

1. 접근 요청: 주체(사용자·서비스)가 객체(파일·API)에 접근을 요청함
2. PEP 가로채기: PEP가 요청을 인터셉트하여 주체·객체·환경 속성과 함께 PDP에 전달함
3. PDP 정책 평가: PDP가 PIP에서 속성을 조회하고 PAP의 정책 규칙과 대조하여 허가·거부를 결정함
4. PEP 결정 집행: PDP의 결정(Permit/Deny)을 PEP가 집행하여 접근을 허용·차단함

> 요약: 요청 → PEP 가로채기 → PDP 정책 평가 → PEP 집행으로 속성 기반 동적 결정을 수행함.

## Ⅳ. 문제점
- 정책 복잡성: 속성 조합이 증가하면 정책 규칙이 복잡해져 관리·감사가 어려움
- 성능 부담: 매 요청마다 다수 속성을 조회·평가하므로 응답 지연이 발생할 수 있음
- 정책 충돌: 복수 정책 간 충돌(Permit+Deny) 시 해결 알고리즘의 설계가 복잡함

## Ⅴ. 개선방안
- (단기) 정책 시뮬레이터: 배포 전 정책 변경의 영향을 시뮬레이션하여 충돌·의도치 않은 접근을 사전 검증함
- (중기) 속성 캐싱: PIP 조회 결과를 TTL 기반으로 캐싱하여 평가 성능을 개선함
- (장기) AI 기반 정책 추천: 접근 로그를 ML로 분석하여 최적 정책 규칙을 자동 생성·추천함

## Ⅵ. 전망
- 제로 트러스트 아키텍처에서 ABAC이 핵심 접근 제어 모델로 채택되며, OPA(Open Policy Agent)·Cedar 등 선언적 정책 엔진이 클라우드 네이티브 환경의 표준이 될 전망임
