# 📖 【암기용】 개념 완전 이해

> 목적: 민감 데이터 노출을 처음 봐도 완벽히 이해하게 만든다. 시험 답안 양식이 아니라, 이해를 위한 친절한 설명이다.

## 한눈에
- **개요**: 개인정보·인증정보·영업비밀이 암호화·마스킹·접근통제 없이 노출되는 보안 사고
- **왜 필요한가**: 시스템은 기능이 정상이어도 로그, 백업, API 응답, 스토리지 권한에서 주민번호·토큰·카드정보가 새어 나갈 수 있음.
- **핵심 직관**: 금고에 보관할 문서를 책상 위, 복사본, 택배 송장, CCTV 화면에 흘려두면 금고 잠금과 무관하게 유출됨.

## 깊이 이해
- **배경·문제의식**: 민감 데이터는 저장 데이터, 전송 데이터, 처리 중 데이터, 로그·백업 데이터로 흩어진다. OWASP 2021에서는 단순 노출보다 암호 실패(Cryptographic Failures) 관점으로 다룬다.
- **작동 원리**: 데이터 분류로 보호 대상을 정하고, TLS 1.3, AES-256, KMS/HSM, 토큰화, 마스킹, 접근제어, DLP 로그 탐지로 데이터 생명주기 전체를 통제함.
- **비유**: 병원 차트는 진료실 보관뿐 아니라 접수 화면, 문자 알림, 폐기 문서, 백업 테이프까지 같은 환자정보로 취급해야 함.
- **구체 예시**: API가 `email`, `phone`, `access_token`을 과다 응답하면 TLS를 써도 클라이언트 로그에 저장됨. 응답 필드 allowlist와 토큰 TTL 15분, refresh token KMS 암호화가 필요함.
- **흔한 오해·주의점**: "HTTPS 적용"만으로 충분하지 않다. 서버 로그, DB dump, S3 public bucket, analytics event, 운영자 화면의 평문 표시까지 통제해야 함.

## 연결 개념
- 데이터 분류(Data Classification) - 보호 수준과 암호화 기준을 정하는 출발점
- KMS/HSM - 키 생성·회전·접근 감사를 담당하는 핵심 통제
- 개인정보보호법·PCI DSS - 주민번호, 카드정보, 결제정보 보호 기준

# 📝 【답안용】 시험 답안 템플릿

> 목적: 시험장에서 25분에 그대로 쓰는 답안 양식. 작성방식(추상표현 금지·수치·도식·문제유형 전환)을 엄격히 지킨다.
> 핵심: 민감 데이터 노출 답안은 암호화 나열이 아니라 데이터 식별, 통제 위치, 탐지 로그, 재검증 지표를 생명주기로 연결해야 함.

## 핵심 인사이트 (3줄 요약)

> 1. **본질**: Sensitive Data Exposure는 민감 데이터가 저장·전송·로그·백업·API 응답에서 보호조치 없이 노출되는 취약점임.
> 2. **가치**: 데이터 분류, TLS 1.3, AES-256, KMS, 마스킹, DLP를 결합해 평문 노출 지점을 제거함.
> 3. **판단 포인트**: "어떤 데이터가 어디서 새는가"를 자산, 통제 위치, 탐지 로그, 재검증 지표로 좁혀 써야 함.

## 출제 의도 및 답안 포인트

| 출제 의도 | 반드시 짚을 핵심 | 감점 회피 포인트 |
|:---|:---|:---|
| 민감 데이터 식별 역량 확인 | 개인정보, 인증정보, 금융정보, 영업비밀 분류 | HTTPS만 쓰고 데이터 분류 누락 |
| 보호 통제 설계 확인 | TLS 1.3, AES-256-GCM, KMS, 토큰화, 마스킹 | 암호 알고리즘명·키관리 없이 "암호화"만 기재 |
| 운영 검증 역량 확인 | 로그 redaction, DLP 탐지, 접근 감사, 재스캔 | 로그·백업·API 응답 통제 누락 |

> 요약: 이 문제는 암호화 지식보다 데이터가 이동하는 지점별 통제와 검증 지표를 묻는 보안 설계 문제임.

---

## Ⅰ. 개요 및 필요성

- 개요: 보호 대상 데이터 평문 유출
- 배경: 개인정보, 토큰, 결제정보는 DB뿐 아니라 로그, 백업, 캐시, API 응답, 객체 스토리지에 복제되어 통제 누락 지점이 생김.
- 필요성: 개인정보보호법, PCI DSS, AES-256 저장 암호화, TLS 1.2 이상 전송 암호화, 마스킹, 접근감사를 데이터 생명주기에 적용해야 함.

---

## Ⅱ. 구조 및 구성요소

```text
데이터 분류 -> 저장/전송/처리 위치 식별 -> 암호화/마스킹/접근통제 -> 로그 탐지 -> 재검증
  / DB, Object Storage, Cache, Backup
  / API, Browser, Mobile, Admin Console
```

| 구성요소 | 역할 | 특이사항 |
|:---|:---|:---|
| Data Classification | PII, credential, payment, secret 등급화 | 주민번호, access token, API key 별도 라벨 |
| Crypto Control | 저장·전송 암호화 적용 | TLS 1.3, AES-256-GCM, KMS envelope encryption |
| Exposure Surface | API 응답, 로그, 백업, 객체 스토리지 통제 | field allowlist, S3 Block Public Access |
| Detection/Audit | DLP, SIEM, 접근 로그로 노출 확인 | 평문 패턴 탐지, 관리자 조회 감사 |

> 요약: 민감 데이터 통제는 데이터 분류, 암호화, 노출면 통제, 탐지·감사 네 요소가 결합되어야 함.

---

## Ⅲ. 동작원리 및 흐름도

```text
자산/데이터 식별 -> 민감도 라벨링 -> 저장/전송 경로 매핑
  / DB, 로그, 백업, API, 운영자 화면
통제 적용 -> 접근/노출 로그 수집 -> DLP 탐지 -> 재검증
```

| 단계 | 처리 내용 | 검증 기준 |
|:---:|:---|:---|
| 1 | 민감 데이터 필드와 보관 위치 식별 | 분류 누락률 5% 이하 |
| 2 | 저장·전송·처리 경로별 통제 선택 | TLS 1.3, AES-256, masking 적용률 95% 이상 |
| 3 | 로그 redaction, 토큰화, 최소 응답 필드 적용 | secret scan 0건, API 과다응답 0건 |
| 4 | DLP·SIEM 탐지와 접근 감사 수행 | 미승인 조회 0건, 경보 처리 SLA 4시간 |

> 요약: 데이터 식별 후 저장·전송·로그·API 위치별 통제를 적용하고 탐지 지표로 재검증하는 흐름임.

## Ⅳ. 특징

| 구분 | 단순 암호화 접근 | 생명주기 통제 접근 | 수치·판단 포인트 |
|:---|:---|:---|:---|
| 보호 범위 | DB 컬럼 중심 | DB, 로그, 백업, API, 스토리지 | 저장소 coverage 95% 이상 |
| 키 관리 | 코드·설정 파일 보관 | KMS/HSM, rotation, audit | 키 회전 90일, 접근 감사 |
| 노출 탐지 | 사고 후 수동 확인 | DLP, SIEM, secret scanning | 평문 secret 0건 |
| 운영 기준 | 개발자 재량 | data owner, retention, masking policy | 보존기간, 파기일, 승인 이력 |

> 요약: 민감 데이터 노출 방지는 암호 알고리즘보다 보호 범위와 키관리, 탐지 지표를 운영 절차로 묶는 것이 핵심임.

## Ⅴ. 심화 비교 및 적용 판단

| 비교 축 | 기존/대안 | 본 키워드 | 선택 기준 |
|:---|:---|:---|:---|
| 구조 | 네트워크 구간 TLS 중심 | 데이터 생명주기 통제 | DB dump, 로그, 백업 유출 가능성 |
| 비용/성능 | 전체 필드 암호화 | 필드 등급별 암호화·토큰화 | 검색 필요 필드는 토큰화, 고위험 필드는 암호화 |
| 운영/위험 | 평문 로그 허용 | redaction, DLP, SIEM 경보 | 개인정보·secret 패턴 발견 시 배포 차단 |

> 요약: 보호 수준은 데이터 등급과 사용 목적에 따라 암호화, 토큰화, 마스킹을 구분해 선택해야 함.

| 리스크 | 원인 | 대응 방안 | 확인 지표 |
|:---|:---|:---|:---|
| 평문 로그 유출 | request/response 전체 로깅 | log redaction, allowlist logging | secret scan 0건 |
| 키 유출 | 코드 저장소·환경변수 노출 | KMS, secret manager, rotation 90일 | hardcoded secret 0건 |
| 과다 응답 | API DTO 재사용 | field allowlist, schema test | 민감 필드 응답 0건 |

> 요약: 주요 리스크는 로그, 키, API 응답이며 CI secret scan과 런타임 DLP로 통제함.

| 점검 항목 | 목표 기준 | 측정 방법 |
|:---|:---|:---|
| 암호화 | 민감 저장소 AES-256 적용률 95% 이상 | DB schema scan, KMS audit |
| 전송 보호 | 외부 API TLS 1.3, 약한 cipher 0건 | TLS scanner, config audit |
| 탐지·감사 | DLP 경보 4시간 이내 조치 | SIEM ticket, 접근 로그 |

> 요약: 도입 효과는 암호화 적용률, TLS 설정, DLP 경보 처리 시간으로 판단함.

## Ⅵ. 실무 적용 및 결론

**적용 방안 3개 (필수 — 단계별 또는 항목별):**
1. 데이터 분류: PII, credential, payment, secret 필드를 data catalog에 등록하고 owner, 보존기간, 암호화 수준을 매핑함.
2. 통제 적용: TLS 1.3, AES-256-GCM, KMS envelope encryption, 화면 마스킹, 로그 redaction을 저장·전송·표시 위치별로 적용함.
3. SDLC 검증: CI secret scan, API schema test, DLP 룰, KMS audit를 배포 게이트에 연결하고 평문 secret 0건을 release 기준으로 둠.

**결론 (2줄):**
- 기술사 판단: 규제 데이터와 인증정보는 암호화·마스킹·감사로그를 필수 통제로 두고, 일반 업무 데이터는 등급별 보존·접근 기준을 적용함.
- 향후 방향: 민감 데이터 보호는 정적 암호화에서 data lineage, DSPM, 자동 분류 기반 지속 점검으로 전환되어야 함.
