# 📖 【암기용】 개념 완전 이해

> 목적: 랜덤 오라클 모델을 처음 봐도 완벽히 이해하게 만든다. 시험 답안 양식이 아니라, 이해를 위한 친절한 설명이다.

## 한눈에
- **개요**: 해시 함수를 완전 무작위 함수처럼 가정하는 보안 증명 모델
- **왜 필요한가**: RSA-OAEP, Fiat-Shamir 변환, 서명 스킴은 해시가 예측 불가하다는 가정 아래 보안성을 증명함. 실제 해시는 SHA-256 같은 결정적 알고리즘이므로 증명 가정과 구현 사이의 차이를 이해해야 함.
- **핵심 직관**: 질문한 입력마다 일관된 무작위 답을 주는 이상적인 해시 상담원을 두고 공격자 성공 확률을 계산하는 방식임.

## 깊이 이해
- **배경·문제의식**: 표준 모델에서 모든 암호 프로토콜을 증명하면 조건이 복잡하고 비용이 증가함. ROM은 해시를 이상화해 증명을 단순화하지만 구현에서는 실제 해시 함수가 사용됨.
- **작동 원리**: 오라클은 같은 입력에는 같은 출력, 새로운 입력에는 균등 무작위 값을 반환함. 증명자는 공격자의 오라클 질의를 관찰·프로그래밍하며 환원 증명(reduction)을 구성함.
- **비유**: 무한한 난수 장부가 있어 처음 보는 이름에는 새 난수를 붙이고, 같은 이름을 다시 물으면 이전 난수를 그대로 알려주는 방식임.
- **구체 예시**: 256비트 랜덤 오라클에서 특정 출력 충돌을 찾는 비용은 생일 공격 기준 약 $2^{128}$ 질의임. SHA-256은 이를 모사하지만 완전 무작위 함수는 아님.
- **흔한 오해·주의점**: ROM에서 증명되었다고 실제 구현이 자동으로 안전하다는 뜻은 아님. 도메인 분리, 해시 길이, 표준 파라미터, 구현 취약점 검증이 별도 필요함.

## 연결 개념
- 해시 함수(SHA-256, SHA-3) - ROM을 실제로 대체하는 구현 대상
- Fiat-Shamir 변환 - 상호작용 증명을 비상호작용 증명으로 바꾸는 대표 사례
- 표준 모델(Standard Model) - 이상 오라클 없이 가정을 명시하는 증명 방식

# 📝 【답안용】 시험 답안 템플릿

> 목적: 시험장에서 25분에 그대로 쓰는 답안 양식. 작성방식(추상표현 금지·수치·도식·문제유형 전환)을 엄격히 지킨다.
> 핵심: ROM은 해시 함수 설명 문제가 아니라 보안 증명 가정과 실제 구현 한계를 구분하는 문제임.

## 핵심 인사이트 (3줄 요약)

> 1. **본질**: 랜덤 오라클 모델은 해시를 균등 무작위 응답 함수로 이상화해 암호 프로토콜 보안성을 증명하는 모델임.
> 2. **가치**: RSA-OAEP, PSS, Fiat-Shamir 계열 증명에서 공격자 성공확률을 오라클 질의 수와 출력 길이로 제한함.
> 3. **판단 포인트**: ROM 증명은 설계 신뢰 근거이나 실제 SHA-256/SHA-3 구현의 충돌·도메인 분리·파라미터 검증이 필요함.

## 출제 의도 및 답안 포인트

| 출제 의도 | 반드시 짚을 핵심 | 감점 회피 포인트 |
|:---|:---|:---|
| 보안 증명 모델 이해 확인 | 이상 해시, 오라클 질의, 환원 증명 | 난수 생성기나 해시 알고리즘으로만 설명 |
| ROM과 표준 모델 비교 판단 | 증명 단순성 vs 구현 괴리 | ROM 증명만으로 실제 안전을 단정 |
| 구현 적용 통제 확인 | SHA-256/SHA-3, domain separation, 128비트 이상 보안강도 | 출력 길이·라벨 분리 누락 |

> 요약: ROM 답안은 해시 이상화의 장점과 실제 구현 괴리를 동시에 제시해야 채점 포인트를 충족함.

---

## Ⅰ. 개요 및 필요성

- 개요: 이상적 해시 보안 증명 모델
- 배경: 암호 프로토콜은 해시의 예측 불가성과 충돌 저항성에 의존하지만 실제 해시 함수 전체를 수학적으로 다루기 어려움.
- 필요성: 랜덤 오라클 모델은 이상적 무작위 함수 가정으로 증명을 단순화하되, 구현 시 SHA-256·SHA-3 대체와 모델 한계를 함께 검토함.

---

## Ⅱ. 구조 및 구성요소

```text
프로토콜 설계 -> 해시 호출 H(x) -> 랜덤 오라클 질의 -> 무작위 응답 y
공격자 질의 기록 -> 증명자 시뮬레이션 -> 성공확률 상한 계산
```

| 구성요소 | 역할 | 특이사항 |
|:---|:---|:---|
| 랜덤 오라클 | 입력별 균등 무작위 출력 반환 | 같은 입력에는 같은 출력 |
| 공격자 모델 | 오라클 질의 후 위조·복호화 시도 | 질의 수 q로 성공확률 제한 |
| 증명자/시뮬레이터 | 공격자를 이용해 원문제 해법 구성 | oracle programming 사용 |
| 실제 해시 | ROM을 구현에서 대체 | SHA-256, SHA-3, domain separation |

> 요약: ROM 구조는 이상 오라클, 공격자 질의, 증명자 시뮬레이션, 실제 해시 대체의 네 축으로 설명함.

---

## Ⅲ. 동작원리 및 흐름도

```text
입력 x 수신 -> 질의 테이블 조회 -> 기존 y 반환 / 신규 y 무작위 생성
-> 공격자 질의 추적 -> 보안 게임 실행 -> 위조 성공확률 산정
```

| 단계 | 처리 내용 | 검증 기준 |
|:---:|:---|:---|
| 1 | 공격자가 H(x)를 질의 | 중복 입력은 동일 출력 |
| 2 | 오라클이 n비트 균등값 반환 | 출력 공간 2^n |
| 3 | 공격자가 서명 위조·복호화 시도 | 성공 사건 정의 |
| 4 | 증명자가 성공 사건을 난제 해법으로 환원 | RSA, DL, LWE 등 가정 |
| 5 | q회 질의 기준 성공확률 상한 도출 | 128비트 이상 보안강도 |

> 요약: ROM은 공격자 질의를 모두 관찰하는 보안 게임을 통해 성공확률을 수식으로 제한하는 방식임.

## Ⅳ. 특징

| 구분 | 표준 모델 | 랜덤 오라클 모델 | 수치·표준 포인트 |
|:---|:---|:---|:---|
| 가정 | 난제와 프로토콜만 사용 | 해시를 이상 함수로 가정 | q/2^n, birthday 2^(n/2) |
| 증명 복잡도 | 보통 증가 | 증명 구조 단순화 | RSA-OAEP, RSA-PSS |
| 구현 괴리 | 가정과 구현 근접 | 실제 해시 대체 필요 | SHA-256, SHA3-256 |
| 위험 | 설계 비용 증가 | ROM 안전이나 실제 취약 가능 | 도메인 분리 필수 |

> 요약: ROM은 증명 편의와 실무 채택성이 있으나 실제 해시로 인스턴스화할 때 별도 검증이 필요함.

## Ⅴ. 심화 비교 및 적용 판단

| 구분 | 기존/대안 | 본 키워드 | 선택 기준 |
|:---|:---|:---|:---|
| 증명 방식 | 표준 모델 | ROM 증명 | 표준 모델 비용이 과도하고 검증된 스킴 사용 시 |
| 구현 | 임의 해시 사용 | SHA-256/SHA-3 + 라벨 분리 | 최소 128비트 보안강도 |
| 운영/위험 | 증명 부재 스킴 | ROM 기반 표준 스킴 | NIST, RFC, ISO 채택 여부 |

> 요약: 실무에서는 직접 설계보다 ROM 증명을 가진 표준 스킴을 선택하고 해시 파라미터를 검증함.

| 리스크 | 원인 | 대응 방안 | 확인 지표 |
|:---|:---|:---|:---|
| 모델 괴리 | 실제 해시가 완전 무작위가 아님 | SHA-2/SHA-3 표준 사용, 암호 분석 확인 | 알려진 collision/preimage 공격 0건 |
| 도메인 충돌 | 서로 다른 용도에 같은 H 입력 사용 | domain separation label 적용 | 라벨 누락 테스트 0건 |
| 보안강도 부족 | 출력 길이 짧음 | 256비트 해시, 128비트 이상 목표 | 보안강도 산정표 승인 |

> 요약: ROM 적용 위험은 모델 자체보다 실제 해시 선택, 라벨 분리, 출력 길이 관리에서 발생함.

| 점검 항목 | 목표 기준 | 측정 방법 |
|:---|:---|:---|
| 증명 근거 | ROM 또는 표준 모델 논문·RFC 명시 | 설계 문서 리뷰 |
| 파라미터 | 해시 출력 256비트 이상 | 암호정책 점검표 |
| 구현 품질 | KAT 통과 100%, fuzz 결함 0건 | NIST CAVP, CI 테스트 |

> 요약: ROM 기반 설계의 성공 여부는 증명 근거, 256비트 해시, 구현 검증 결과로 판단함.

## Ⅵ. 실무 적용 및 결론

**적용 방안 3개 (필수 — 단계별 또는 항목별):**
1. 표준 스킴 선택: RSA-OAEP, RSA-PSS, EdDSA/Fiat-Shamir 계열 등 공개 분석된 스킴을 우선 적용함.
2. 해시 인스턴스화: SHA-256 또는 SHA3-256 이상을 사용하고 용도별 domain separation label을 입력에 포함함.
3. 검증 체계 운영: Known Answer Test 100%, fuzz test, 코드 리뷰로 해시 호출 순서와 길이 인코딩을 검증함.

**결론 (2줄):**
- 기술사 판단: 새 프로토콜 설계는 표준 모델 증명을 우선 검토하고, ROM 기반이면 표준화·분석 이력·인스턴스화 규칙을 조건으로 채택함.
- 향후 방향: ZKP·PQC·블록체인 서명에서 ROM과 Quantum ROM(QROM) 구분이 중요해져 보안 증명 가정 명시가 필수화됨.
