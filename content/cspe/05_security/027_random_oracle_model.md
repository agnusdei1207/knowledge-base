# 📖 【암기용】 개념 완전 이해

## 한눈에
- **개요**: 랜덤 오라클 모델(ROM)은 **암호학적 보안 증명**에서 해시 함수를 완전 무작위 함수처럼 이상화하여 프로토콜의 안전성을 수학적으로 증명하는 모델임.
- **왜 필요한가**: RSA-OAEP, Fiat-Shamir 변환, EdDSA 같은 암호 스킴은 해시가 예측 불가하다는 가정 아래 보안 증명을 함. 실제 해시(SHA-256)는 결정적 알고리즘이므로 증명 가정과 구현 사이의 괴리를 이해해야 함.
- **핵심 직관**: 질문한 입력마다 일관된 무작위 답을 주는 "이상적 해시 상담원"을 두고, 공격자가 이 상담원을 이용해도 스킴을 깰 수 없음을 보이는 방식임.

## 핵심 용어 정리 (내부에 등장하는 것들)

| 용어/표기 | 의미 | 비유·예 |
|:---|:---|:---|
| 보안 증명 (상위 키워드) | 암호 프로토콜이 특정 가정 하에서 안전함을 수학적으로 보이는 것 | 프로토콜의 안전 보증서 |
| 랜덤 오라클 | 같은 입력→같은 출력, 새 입력→균등 무작위 출력을 반환하는 이상적 함수 | 무한 난수 장부 |
| 질의(Query) | 공격자가 오라클에 입력을 보내 출력을 받는 행위 | 상담원에게 질문하기 |
| 환원 증명(Reduction) | 공격자의 성공을 난제(RSA·DL·LWE) 풀이로 변환하는 증명 기법 | "스킴을 깨면 RSA도 깬다"는 논증 |
| Oracle Programming | 증명자가 오라클 응답을 통제하며 시뮬레이션하는 기법 | 상담원 대본을 조작해 테스트 |
| 표준 모델 (Standard Model) | 이상 오라클 없이 수학적 가정만으로 증명하는 방식 | 상담원 없이 직접 증명 |
| 도메인 분리 (Domain Separation) | 서로 다른 용도의 해시 입력에 고유 라벨을 붙여 충돌을 방지 | 봉투 색깔로 용도 구분 |
| 인스턴스화 (Instantiation) | ROM의 이상 오라클을 실제 해시(SHA-256 등)로 대체하는 것 | 이상적 상담원을 실제 알고리즘으로 교체 |
| QROM | Quantum Random Oracle Model — 양자 공격자가 오라클에 중첩 질의하는 확장 모델 | 양자 상담원 |

## 깊이 이해
- **배경·문제의식**: 표준 모델에서 모든 암호 프로토콜을 증명하면 조건이 복잡하고 증명 비용이 증가함. ROM은 해시를 이상화해 증명을 단순화하지만, 실제 해시는 완전 무작위 함수가 아니므로 "ROM에서 증명 = 실제 안전"이 자동 성립하지 않음 — 이 괴리를 이해하는 것이 핵심임.
- **작동 원리**: (1) 보안 게임을 정의함 — 공격자가 오라클 질의를 최대 q회 수행하고 서명 위조·복호화를 시도함. (2) 오라클은 새 입력에 n비트 균등 무작위 값을 반환하고, 같은 입력에는 같은 값을 반환함. (3) 증명자(시뮬레이터)가 공격자의 오라클 질의를 관찰·프로그래밍하며, 공격 성공을 RSA·DL·LWE 등 난제 풀이로 환원함. (4) 결론: 난제가 어려우면 공격 성공확률이 q/2^n 이하임을 보임.
- **비유**: 무한한 난수 장부가 있어 처음 보는 이름에는 새 난수를 붙이고, 같은 이름을 다시 물으면 이전 난수를 그대로 알려줌. 이 장부를 이용해도 금고(RSA)를 열 수 없다면, 실제 해시(SHA-256)를 써도 어렵다는 논증임.
- **구체 예시**: 256비트 랜덤 오라클에서 충돌을 찾는 비용은 생일 공격 기준 약 2^128 질의임. RSA-OAEP는 ROM에서 IND-CCA2 안전, RSA-PSS는 ROM에서 EUF-CMA 안전이 증명됨. Fiat-Shamir 변환은 대화형 ZKP를 비대화형으로 바꾸는 대표적 ROM 활용 사례임.
- **흔한 오해·주의점**: (1) ROM에서 증명됐다고 실제 구현이 자동 안전하지 않음 — SHA-256이 완전 무작위가 아닐 수 있음. (2) 도메인 분리 없이 같은 해시를 여러 용도에 쓰면 입력 충돌이 발생할 수 있음. (3) PQC·ZKP에서는 양자 공격자가 오라클에 중첩 질의하는 QROM이 필요해짐.

## 연결 개념
- **해시 알고리즘 SHA-256·SHA-3(004)**: ROM의 이상 오라클을 실제로 대체하는 구현 대상
- **전자 서명(008)**: RSA-PSS·EdDSA 등 ROM 증명 기반 서명 스킴
- **영지식 증명 ZKP(022)**: Fiat-Shamir 변환으로 비대화형 ZKP를 만드는 ROM 활용 사례

# 📝 【답안용】 시험 답안 템플릿

## 핵심 인사이트 (3줄 요약)

> 1. **본질**: ROM은 해시를 균등 무작위 응답 함수로 이상화해 암호 프로토콜의 보안성을 증명하는 모델임.
> 2. **가치**: RSA-OAEP·PSS·Fiat-Shamir 계열 증명에서 공격자 성공확률을 오라클 질의 수(q)와 출력 길이(n)로 제한함.
> 3. **판단 포인트**: ROM 증명은 설계 신뢰 근거이나 실제 SHA-256/SHA-3 인스턴스화의 도메인 분리·파라미터 검증이 필수임.

## 출제 의도 및 답안 포인트

| 출제 의도 | 반드시 짚을 핵심 | 감점 회피 포인트 |
|:---|:---|:---|
| 보안 증명 모델 이해 | 이상 해시·오라클 질의·환원 증명 | 난수 생성기나 해시 알고리즘 자체로만 설명 |
| ROM vs 표준 모델 비교 | 증명 단순성 vs 구현 괴리(인스턴스화) | ROM 증명만으로 실제 안전을 단정 |
| 구현 적용 통제 | SHA-256/SHA-3·domain separation·128비트 이상 보안강도 | 출력 길이·라벨 분리 누락 |

> 요약: ROM 답안은 해시 이상화의 증명 편의와 실제 구현 괴리(인스턴스화 한계)를 동시에 제시해야 함.

---

## Ⅰ. 개요 및 필요성

- 개요: 해시를 완전 무작위 함수로 이상화해 암호 프로토콜 보안성을 증명하는 모델임.
- 배경: 암호 프로토콜은 해시의 예측 불가성·충돌 저항성에 의존하지만, 실제 해시 함수 전체를 수학적으로 다루기 어려움.
- 필요성: ROM은 이상적 무작위 함수 가정으로 증명을 단순화하되, 구현 시 SHA-256/SHA-3 인스턴스화와 모델 한계를 함께 검토함.

---

## Ⅱ. 구조 및 구성요소

```text
프로토콜 설계 -> 해시 호출 H(x) -> 랜덤 오라클 질의 -> 무작위 응답 y
공격자 질의 기록 -> 증명자 시뮬레이션(oracle programming) -> 성공확률 상한 계산
  / 실제 구현: SHA-256/SHA-3 + Domain Separation Label
```

| 구성요소 | 역할 | 특이사항 |
|:---|:---|:---|
| 랜덤 오라클 | 입력별 n비트 균등 무작위 출력 반환 | 같은 입력→같은 출력(결정적) |
| 공격자 모델 | 오라클에 최대 q회 질의 후 위조·복호화 시도 | 질의 수 q로 성공확률 제한 |
| 증명자/시뮬레이터 | 공격 성공을 난제(RSA·DL·LWE) 풀이로 환원 | oracle programming 사용 |
| 실제 해시 | ROM을 구현에서 대체(인스턴스화) | SHA-256·SHA-3·domain separation |

> 요약: ROM 구조는 이상 오라클·공격자 질의·증명자 환원·실제 해시 인스턴스화의 네 축으로 구성됨.

---

## Ⅲ. 동작원리 및 흐름도

```text
입력 x 수신 -> 질의 테이블 조회 -> 기존 y 반환 / 신규 y 무작위 생성
  -> 공격자 질의 추적 -> 보안 게임 실행(위조/복호화 시도)
  -> 증명자 환원(난제 풀이) -> 성공확률 상한 q/2^n 도출
```

1. 오라클 질의: 공격자가 H(x)를 질의하면 오라클이 n비트 균등 무작위 값을 반환함 — 중복 입력에는 동일 출력을 보장함.
2. 보안 게임: 공격자가 서명 위조·암호문 복호화를 시도하고, 증명자가 공격자의 모든 오라클 질의를 관찰·기록함.
3. 환원 증명: 증명자가 공격 성공 사건을 RSA·DL·LWE 등 난제 해법으로 변환해 "스킴을 깨면 난제도 풀린다"를 보임.
4. 확률 제한: q회 질의 기준으로 공격 성공확률 상한을 q/2^n 이하로 도출함 — 128비트 이상 보안강도를 목표로 설정함.

> 요약: ROM은 공격자 질의를 모두 관찰하는 보안 게임을 통해 성공확률을 수식으로 제한하는 증명 방식임.

---

## Ⅳ. 특징

- 증명 단순화: 표준 모델 대비 증명 구조가 단순해 RSA-OAEP·PSS·EdDSA·Fiat-Shamir 등 광범위한 스킴에서 채택됨.
- 구현 괴리: 실제 해시(SHA-256)는 완전 무작위가 아니므로 ROM 안전이 자동으로 실제 안전을 보장하지 않음 — 인스턴스화 검증이 필수임.
- 도메인 분리 필수: 서로 다른 용도에 같은 해시를 라벨 없이 사용하면 입력 충돌이 발생할 수 있어 domain separation label을 반드시 적용함.
- QROM 확장: PQC·ZKP에서 양자 공격자가 중첩 질의하는 Quantum ROM이 필요해져 보안 증명 가정 명시가 중요해짐.
- 채택 기준: NIST·RFC·ISO에 채택된 ROM 증명 스킴을 우선 사용하고, 자체 설계 시 표준 모델 증명을 먼저 검토함.

---

## Ⅴ. 심화 비교 및 적용 판단

ROM(이상 해시 가정)과 표준 모델(난제만 가정)을 증명 방식·구현·채택 축으로 비교함.

| 구분 | 표준 모델 | ROM | 선택 기준 |
|:---|:---|:---|:---|
| 가정 | 난제와 프로토콜만 사용 | 해시를 이상 함수로 추가 가정 | 증명 비용 vs 모델 괴리 허용 |
| 증명 복잡도 | 높음(조건 정밀) | 낮음(구조 단순) | 설계·검증 리소스 |
| 구현 괴리 | 가정과 구현 근접 | 실제 해시 인스턴스화 필요 | SHA-256/SHA-3 분석 이력 |
| 대표 스킴 | DHIES, Cramer-Shoup | RSA-OAEP, RSA-PSS, EdDSA | NIST/RFC 채택 여부 |

> 요약: 실무에서는 직접 설계보다 ROM 증명이 있는 표준 스킴(NIST/RFC)을 선택하고, 해시 인스턴스화 규칙을 검증함.

**리스크·대응:**
- 모델 괴리: 실제 해시가 완전 무작위가 아니어서 ROM 증명이 무효화될 가능성 → SHA-2/SHA-3 표준 사용·알려진 공격 분석 확인 (지표: collision/preimage 공격 0건)
- 도메인 충돌: 서로 다른 용도에 같은 H 입력 사용 → domain separation label 적용 (지표: 라벨 누락 테스트 0건)
- 보안강도 부족: 출력 길이가 짧아 brute-force 가능 → 256비트 해시·128비트 이상 보안강도 목표 (지표: 보안강도 산정표 승인)

**도입 후 점검 지표:**
- 증명 근거: ROM 또는 표준 모델 논문·RFC 명시 — 설계 문서 리뷰
- 파라미터: 해시 출력 256비트 이상·domain separation 적용 — 암호정책 점검표
- 구현 품질: KAT 100% 통과·fuzz 결함 0건 — NIST CAVP·CI 테스트

---

## Ⅵ. 실무 적용 및 결론

**적용 방안:**
1. 표준 스킴 선택: RSA-OAEP·RSA-PSS·EdDSA/Fiat-Shamir 계열 등 NIST/RFC에 채택된 ROM 증명 스킴을 우선 적용함.
2. 해시 인스턴스화: SHA-256 또는 SHA3-256 이상을 사용하고 용도별 domain separation label을 입력에 포함함.
3. 검증 체계 운영: Known Answer Test 100%·fuzz test·코드 리뷰로 해시 호출 순서와 길이 인코딩을 검증함.

**결론:**
- 기술사 판단: 새 프로토콜 설계는 표준 모델 증명을 우선 검토하고, ROM 기반이면 표준화·분석 이력·인스턴스화 규칙을 조건으로 채택함.
- 향후 방향: ZKP·PQC·블록체인 서명에서 ROM과 QROM 구분이 중요해져 보안 증명 가정 명시가 필수화됨.
