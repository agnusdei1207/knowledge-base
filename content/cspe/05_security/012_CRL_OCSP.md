## Ⅰ. 개요
| 항목 | 내용 |
|---|---|
| **정의** | 개인키 유출, 퇴사 등의 사유로 유효기간 만료 전에 인증서를 강제로 무효화하고 이를 통보하는 메커니즘임 |
| **배경/필요성** | 유출된 인증서를 통한 위장 공격을 차단하기 위해 인증서의 현재 상태(유효, 폐지)를 신속히 검증할 수단 필요 |
| **출제 의도** | 정적 목록 다운로드(CRL)와 실시간 온라인 질의(OCSP) 방식의 차이점 및 네트워크 오버헤드 이해 |

## Ⅱ. 구성요소
```text
+-------------------+      +-------------------+      +-------------------+
|   Revoked Certs   |      |    CRL System     |      |  OCSP Responder   |
| (폐기 사유 발생)  +----->| (주기적 목록 배포)+----->| (실시간 상태 질의)|
+-------------------+      +-------------------+      +-------------------+
```
| 구성요소 | 설명 | 비유 |
|---|---|---|
| **CRL (인증서 폐지 목록)** | CA가 주기적으로 발행하는, 유효기간 전 폐기된 인증서의 일련번호 목록(블랙리스트) 파일임 | 은행의 분실 수표 번호 책자 |
| **OCSP (온라인 상태 프로토콜)** | 특정 인증서 하나만의 유효성 상태(Good, Revoked, Unknown)를 실시간으로 질의/응답하는 프로토콜임 | 은행 ARS 분실수표 실시간 조회 |
| **OCSP Stapling** | 클라이언트 대신 서버가 자신의 OCSP 응답을 주기적으로 캐싱하여 클라이언트에 제공하는 방식임 | 매장이 수표 유효 증명서를 대리 발급 |

> 요약: 전체 목록을 다운로드하는 기존 CRL 방식의 단점을 실시간 단일 질의 응답 구조(OCSP)로 보완한 체계임.

## Ⅲ. 절차
```text
+----------------+   +----------------+   +----------------+   +----------------+
| 1. 폐기 사유   |-->| 2. 목록 등록   |-->| 3. OCSP 질의   |-->| 4. 상태 응답   |
| (키 유출 발생) |   | (CA 데이터베이스)|   | (클라이언트)   |   | (유효성 판단)  |
+----------------+   +----------------+   +----------------+   +----------------+
```
1. **폐기 사유 발생**: 개인키 분실 또는 도메인 변경 등으로 사용자가 CA에 인증서 폐기를 정식 요청함
2. **목록 등록**: CA가 해당 인증서 일련번호를 폐기 데이터베이스에 기록하고 CRL 파일을 업데이트함
3. **OCSP 질의**: 클라이언트가 통신 대상 웹 서버 인증서의 상태를 확인하기 위해 CA의 OCSP 응답기(Responder)에 질의 전송
4. **상태 응답**: OCSP 응답기는 해당 인증서의 현재 상태를 확인 후 서명된 응답 메시지를 클라이언트로 반환함

> 요약: 폐기 정보가 CA에 등록되면 클라이언트가 접속 전 이를 조회하여 신뢰 여부를 실시간 확정함.

## Ⅳ. 문제점
* **CRL의 갱신 지연 및 크기 문제**: 배포 주기(예: 1일) 동안의 시간차로 인해 취약 상태에 노출되며, 파일 크기 비대화로 네트워크 대역폭 낭비
* **OCSP의 개인정보 침해**: 클라이언트가 질의할 때마다 어떤 사이트에 방문하는지 CA(OCSP 서버)가 모두 추적할 수 있음
* **OCSP 통신 오버헤드 지연**: 접속 시마다 CA 응답 서버와 통신해야 하므로 초기 접속 지연(Latency)과 단일 장애(서버 폭주) 유발

## Ⅴ. 개선방안
* **단기 방안 (CRL 배포 분산)**: CDN이나 분산 저장소를 활용하여 대용량 CRL의 다운로드 부하와 지연을 분산 최소화
* **중기 방안 (OCSP Stapling 도입)**: 웹 서버가 사전에 CA로부터 서명된 OCSP 응답을 받아 캐싱해 두고 클라이언트의 핸드셰이크 시점에 함께 제공하여 프라이버시와 지연 문제 동시 해결
* **장기 방안 (단기 인증서 전환)**: 유효기간이 수일에 불과한 단기 인증서 체계로 완전히 전환하여 별도의 폐기 검증 메커니즘 불필요화

## Ⅵ. 전망
* 브라우저 벤더(Chrome, Firefox)들은 네트워크 부하를 줄이기 위해 OCSP 질의 대신 자체적인 경량화된 폐기 목록(CRLFite 등) 배포 방식으로 선회 중임
* 궁극적으로 유효기간 축소(90일 이하) 추세가 강화됨에 따라 CRL과 OCSP 시스템의 의존도는 점진적으로 감소할 전망임
