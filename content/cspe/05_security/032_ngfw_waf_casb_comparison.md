## 1. 한눈에 이해하기 (Core Intuition)
- **정의**: 단순 포트/IP 차단을 넘어서는 목적별 심층 보안 장비들입니다. **NGFW**(회사 전체망의 똑똑한 통합 경비원), **WAF**(웹 서비스 전용 호위무사), **CASB**(클라우드 SaaS 전용 감시관)로 역할이 나뉩니다.
- **필요성**: 해커들이 80(HTTP), 443(HTTPS) 포트같이 '정상적으로 열려 있는 문'을 통해 악성 행위를 하기 때문에, 겉봉투(포트)만 보는 구형 방화벽으로는 막을 수 없어 '속 내용'까지 뜯어보는 특수 장비들이 필요해졌습니다.
- **핵심 직관**: **"보안 검색대 비유"**. 
  - 구형 방화벽: "비행기 티켓(IP/Port) 있네? 통과!"
  - **NGFW (Next-Gen Firewall)**: X-레이를 찍어서 가방 속에 폭탄(악성코드/앱)이 있는지까지 싹 다 검사하는 최신형 종합 검색대.
  - **WAF (Web App Firewall)**: 특정 식당(웹 서버) 앞에서 진상 손님(SQL 인젝션, XSS 공격)만 기가 막히게 쫓아내는 전담 가드.
  - **CASB (Cloud Access Security Broker)**: 직원들이 밖에서 구글 드라이브나 슬랙(클라우드)을 쓸 때 회사 기밀 파일을 올리지 못하도록 모니터링하는 현장 파견 감시 요원.

## 2. 왜 중요한가? (Background & Value)
- **등장 배경**: 과거에는 회사 안에 서버가 다 있었고 1차 방화벽 하나로 충분했습니다. 하지만 공격이 웹(Web) 취약점을 노리는 형태로 정교해지고, 회사의 업무가 구글 워크스페이스 같은 클라우드(SaaS)로 넘어가자 경계선 보안(Perimeter Security)이 무너졌습니다.
- **가치**: 뚫는 자의 '공격 벡터'가 다양해진 만큼 막는 자도 '방어 벡터'를 세분화한 것입니다. 각자의 특화된 위치(네트워크 게이트웨이, 웹 서버 앞단, 클라우드 API 연동)에서 톱니바퀴처럼 맞물려 **심층 방어(Defense in Depth)** 를 완성합니다.

## 3. 어떻게 작동하는가? (Mechanism)

**1. NGFW (차세대 방화벽)**
- **특징**: 기존 방화벽 + IPS(침입방지) + 안티바이러스 + 샌드박스를 한 통에 담은 '올인원(UTM의 진화형)' 장비입니다.
- **원리 (App-ID, User-ID)**: 단순히 80번 포트를 연다가 아니라, "포트는 80이지만 패킷을 뜯어보니 카카오톡 파일 전송 기능이네? 인사팀 직원(User)만 허용하고 영업팀은 차단!"처럼 사람과 앱의 행동 단위로 통제합니다.

**2. WAF (웹 방화벽)**
- **특징**: 웹(HTTP/HTTPS) 프로토콜의 취약점 공격 방어에만 '올인'한 녀석입니다.
- **원리 (L7 Payload 분석)**: 웹 게시판에 글을 쓸 때 `<script>해킹</script>` 같은 특수 문자가 들어오거나, 로그인 창에 `' OR 1=1 --` 같은 이상한 DB 명령어가 들어오면 찰떡같이 알아보고 잘라버립니다 (OWASP Top 10 완벽 방어).

**3. CASB (클라우드 접근 보안 브로커)**
- **특징**: 직원 기기와 외부 퍼블릭 클라우드(Office 365, Salesforce 등) 사이에 낀 브로커입니다.
- **원리**: 직원이 회사 밖 카페에서 O365에 접속해 "내부 고객 명단.xlsx"를 개인 구글 드라이브로 복사하려 할 때, CASB가 클라우드 API를 통해 이를 감지하고 파일 유출(DLP)을 차단해 버립니다 (Shadow IT 색출).

## 4. 실전 활용 및 예시 (Real-world Application)
- **구체적 사례**: 
  - **망 설계 구성**: 회사의 인터넷 출입구 제일 앞단에는 **NGFW**를 세워 1차 트래픽을 거르고, 고객에게 서비스하는 쇼핑몰 웹 서버 바로 앞에는 **WAF**를 세워 해킹을 막습니다.
- **주의점 및 흔한 오해**: 
  - WAF나 NGFW가 패킷의 내용(Payload)을 뜯어보려면, **암호화된 트래픽(HTTPS)을 중간에서 복호화**해야 합니다(SSL Decryption). 이를 위해 기업 내부망에 별도의 Root CA 인증서를 깔아 합법적인 '중간자 공격(MITM)' 인프라를 세팅해야만 이 장비들이 제값을 할 수 있습니다.

## 5. 핵심 비교 요약
| 구분 | 방어 위치 (주 무대) | 막아내는 주적 (Target) | 판단 기준 |
|---|---|---|---|
| **NGFW** | 회사망 입구 (경계선) | 악성코드, 토렌트, 불법 앱 통신 | 어플리케이션(App-ID), 사용자 식별 |
| **WAF** | 웹 서버 바로 앞 (DMZ) | SQL 인젝션, XSS, 웹 스크래핑 | HTTP/HTTPS 페이로드의 웹 취약점 패턴 |
| **CASB** | 클라우드 서비스 경계 | 데이터 유출(DLP), 비인가 SaaS(섀도우 IT) | 클라우드 API 통신, 계정 탈취 여부 |

# ✍️ 단답형 / 서술형 시험장 출격 준비

### Ⅰ. 핵심 인사이트
- **본질**: 경계형 보안(Perimeter Security)의 한계를 극복하기 위해, L7(애플리케이션 계층) 가시성 확보와 상황 인지(Context-awareness) 능력을 고도화한 목적별 심층 보안 솔루션 체계.
- **가치**: 포트 기반의 맹목적 허용 정책을 악용하는 정교화된 웹 애플리케이션 위협과, 기업 통제권 밖에 존재하는 섀도우 IT(Shadow IT)의 클라우드 데이터 유출 리스크를 원천적으로 통제함.
- **판단 포인트**: 이 세 솔루션은 상호 경쟁/대체 관계가 아닌 보완재(Complementary)임. NGFW는 통합적 인프라 관문, WAF는 웹 서비스 공격 방어의 최종 방어선, CASB는 SaaS 가시성 확보로 각각 특화 영역에 배치해야 함.

### Ⅱ. NGFW (Next-Generation Firewall) 아키텍처
**1. 주요 차별화 기능 (vs 전통적 방화벽)**
- **App-ID (애플리케이션 인지)**: 비표준 포트를 사용하거나 80/443 포트에 숨어 들어오는 트래픽(Skype, BitTorrent 등)을 시그니처 및 휴리스틱 분석으로 정확히 식별.
- **User-ID (사용자 인지)**: IP 주소 기반 통제에서 탈피, Active Directory 등과 연동하여 특정 "그룹(사용자)" 기반의 룰셋(ACL) 적용.
- **IPS 기능 통합**: 별도의 IPS 장비를 거치지 않고 단일 패스(Single-pass) 엔진에서 악성코드/취약점 시그니처를 동시 검사하여 성능 지연 최소화.
- **SSL/TLS 복호화**: 암호화된 트래픽을 In-Line으로 복호화(SSL Decryption)하여 L7 Payload 검사 후 재암호화 전송.

### Ⅲ. WAF (Web Application Firewall) 아키텍처
**1. 주요 차별화 기능 (vs NGFW/IPS)**
- NGFW나 IPS가 네트워크 전반의 광범위한 위협을 탐지한다면, WAF는 **HTTP/HTTPS 프로토콜의 규격과 웹 로직 구조를 깊이 이해**하여 집중 분석함.
- **OWASP Top 10 완벽 방어**: SQL Injection, XSS, SSRF, 디렉토리 트래버셜 등 웹 애플리케이션의 로직/입력값 취약점을 악용한 공격 차단.
- **Positive/Negative Security 모델 동시 적용**: 
  - Negative: 블랙리스트 기반 알려진 공격 패턴 차단.
  - Positive: 화이트리스트 기반 (예: 주민번호 칸에는 13자리 숫자만 허용, 이외 입력 시 차단).

**2. 배치 모드**
- **In-Line (Reverse Proxy)**: 트래픽이 반드시 WAF를 거치도록 하여 차단(Block)에 최적화. (가장 대중적).
- **Out-of-Band (Sniffing/Mirroring)**: 원본 트래픽 흐름에 영향 없이 모니터링만 수행 (초기 도입 시 오탐 테스트용).

### Ⅳ. CASB (Cloud Access Security Broker) 아키텍처
**1. 등장 배경 및 해결 과제**
- **Shadow IT 통제**: IT 부서 모르게 임직원들이 개별적으로 도입/사용하는 SaaS(Dropbox, Trello 등)의 가시성 맹점 극복.
- **Data-in-Motion / Data-at-Rest 제어**: 회사의 중요 자산이 퍼블릭 클라우드에 무단 복사되거나 공유되는 현상(DLP, Data Loss Prevention) 방지.

**2. 아키텍처 (적용 방식 3가지)**
- **API 연동 (API-based)**: 클라우드 사업자(O365, G-Suite)가 제공하는 API를 이용해 클라우드 내에 이미 올라가 있는 파일의 권한 설정, 텍스트 마이닝, 민감정보 여부(Data-at-Rest)를 비동기적으로 스캐닝. (성능 저하 없음).
- **정방향 프록시 (Forward Proxy)**: 사내망과 인터넷의 중간 병목 지점에 설치. 직원의 모든 트래픽을 가로채어 미인가 클라우드 접속이나 민감 데이터 업로드(Data-in-Motion)를 실시간 차단.
- **역방향 프록시 (Reverse Proxy)**: 회사 관리 클라우드로 들어오는 요청 통제. 에이전트(Agent) 설치가 불가능한 비인가 기기(개인 스마트폰 등)에서의 접속 제어.

### Ⅴ. 결론 및 실무적 판단 포인트
- **아키텍처 융합 동향 (SASE의 부상)**: 최근 네트워크 보안 인프라는 방화벽 장비를 지사에 물리적으로 설치하는 대신, NGFW, WAF, CASB, ZTNA 기능을 모두 클라우드 엣지 기반의 단일 통합 플랫폼인 **SASE (Secure Access Service Edge)** 로 넘기는 추세임. 보안 담당자는 개별 솔루션 도입보다는 SASE 기반의 통합 도입 로드맵을 검토해야 함.
- **WAF의 진화 (WAAP)**: 전통적인 WAF는 봇 트래픽(Botnet)이나 API 취약점을 방어하는 데 한계가 있어, 최근에는 웹 + API + 봇 방어 + DDoS 방어를 모두 합친 **WAAP (Web Application and API Protection)** 형태의 클라우드형 서비스(Cloudflare, AWS WAF 등) 도입이 주류를 이루고 있음.

### 💡 문제 유형별 목차 전환 포인트
- **[웹 서비스 보안 고도화 및 WAF 원리]**: Ⅲ번 항목의 L7 이해도와 Positive/Negative 모델을 집중적으로 부각하고, 왜 IPS 장비로는 웹 해킹(SQLi 등)을 정밀하게 잡을 수 없는지(오탐/미탐 한계) 논리적으로 비교 서술.
- **[클라우드 환경의 Shadow IT 통제 및 데이터 보호]**: Ⅳ번 항목의 CASB 3대 아키텍처(API, Forward/Reverse Proxy)를 클라우드 보안 거버넌스(DLP 관점)와 연계하여 서술.
