# 📖 【암기용】 개념 완전 이해

> 목적: X.509 인증서를 처음 봐도 완전하게 이해하게 만든다. 시험 답안 양식이 아니라, 이해를 위한 설명이다.

## 한눈에
- **개요**: 주체 신원과 공개키를 CA 서명으로 묶은 표준 인증서 형식
- **왜 필요한가**: TLS 서버가 공개키를 보내도 그 키가 실제 도메인의 것인지 확인해야 한다. X.509는 도메인명, 공개키, 유효기간, 발급자, 용도, 서명값을 담아 검증 가능한 신뢰 정보를 제공한다.
- **핵심 직관**: 공개키에 이름표와 만료일, 사용 용도, 발급기관 도장을 붙인 디지털 신분증이다.

## 깊이 이해
- **배경·문제의식**: PKI는 신뢰 구조이고, X.509는 그 구조에서 주고받는 인증서 데이터 형식이다. 인증서가 없으면 공개키 소유자 확인이 어렵고, 인증서 검증이 부실하면 MITM 공격을 허용한다.
- **작동 원리**: 인증서에는 Subject, Issuer, Serial Number, Validity, Subject Public Key Info, SAN, KeyUsage, EKU, Signature가 포함된다. 검증자는 체인, 서명, 이름, 기간, 폐지 상태를 확인한다.
- **비유**: 출입증에 이름, 사진, 발급기관, 유효기간, 출입 가능 구역이 적혀 있고 위조 방지 도장이 찍힌 것과 같다.
- **구체 예시**: `www.example.com` HTTPS 인증서는 SAN에 `www.example.com`이 있어야 하며, CN만 맞고 SAN이 없으면 현대 브라우저 검증에서 실패한다.
- **흔한 오해·주의점**: 인증서가 있다고 통신 내용이 자동으로 암호화되는 것은 아니다. TLS 핸드셰이크에서 인증서 검증 후 세션키 합의와 대칭키 암호화가 이어져야 한다.

## 연결 개념
- PKI — X.509 인증서를 발급·검증·폐지하는 신뢰 구조
- TLS — 서버 인증서 검증 후 보안 채널 수립
- CRL·OCSP — X.509 인증서 폐지 상태 확인

# 📝 【답안용】 시험 답안 템플릿

> 목적: 시험장에서 25분에 그대로 쓰는 답안 양식. 작성방식(추상표현 금지·수치·도식·문제유형 전환)을 엄격히 지킨다.

## 핵심 인사이트 (3줄 요약)

> 1. **본질**: X.509 인증서는 주체 식별정보와 공개키를 CA 전자서명으로 결합한 PKI 표준 데이터 구조임.
> 2. **가치**: TLS, S/MIME, 코드서명, 클라이언트 인증에서 신원 확인과 공개키 신뢰 근거를 제공함.
> 3. **판단 포인트**: 검증은 서명만이 아니라 체인·SAN·유효기간·KeyUsage/EKU·폐지 상태를 모두 확인해야 함.

## 출제 의도 및 답안 포인트

| 출제 의도 | 반드시 짚을 핵심 | 감점 회피 포인트 |
|:---|:---|:---|
| 인증서 구조 이해 확인 | Subject, Issuer, Serial, Validity, SPKI, SAN, KeyUsage, Signature | CN만으로 도메인 검증한다고 서술 금지 |
| 검증 절차 판단 확인 | Chain, Signature, SAN, Validity, Revocation | 서명 검증만 쓰고 폐지·용도 검증 누락 금지 |
| 보안 운영 역량 확인 | OCSP/CRL, CT 로그, 만료 관리, 개인키 보호 | 인증서와 암호화 채널을 동일시 금지 |

> 요약: X.509 답안은 필드 구조와 검증 체크리스트를 연결해 MITM 차단 관점으로 작성해야 함.

---

## Ⅰ. 개요 및 필요성

- 개요: 표준 공개키 인증서 형식
- 배경: 공개키만 전달하면 키 소유자·도메인·사용 용도를 확인할 수 없어 위장 서버와 MITM 공격에 노출됨.
- 필요성: X.509는 공개키·주체·발급자·유효기간·KeyUsage·CA 서명을 포함해 TLS와 PKI의 검증 단위를 제공함.

---

## Ⅱ. 구조 및 구성요소

```text
Subject·SAN -> Subject Public Key Info -> Validity·Usage
  / Issuer·Serial -> CA Signature -> Certificate Chain
  / CRL DP·AIA -> OCSP/CRL 검증
```

| 구성요소 | 역할 | 특이사항 |
|:---|:---|:---|
| Subject·SAN | 주체 식별과 도메인명 제공 | TLS 도메인 검증은 SAN 기준 |
| SPKI | 공개키 알고리즘과 공개키 값 포함 | RSA, ECDSA, Ed25519 등 |
| Validity | notBefore/notAfter 기간 제시 | 공개 TLS 인증서 최대 398일 관행 |
| KeyUsage·EKU | 인증서 사용 목적 제한 | serverAuth, clientAuth, codeSigning |
| Signature | CA가 인증서 TBS 영역에 서명 | 상위 CA 공개키로 검증 |

> 요약: X.509는 공개키뿐 아니라 이름·기간·용도·발급자 서명을 함께 담아 검증 범위를 구조화함.

---

## Ⅲ. 동작원리 및 흐름도

```text
인증서 수신 -> 체인 구성 -> CA 서명 검증 -> SAN 이름 검증
  -> 기간 확인 -> KeyUsage/EKU 확인 -> OCSP/CRL 확인 -> 신뢰 결정
```

| 단계 | 처리 내용 | 검증 기준 |
|:---:|:---|:---|
| 1 | 서버·클라이언트 인증서 수신 | PEM/DER 파싱, 체인 순서 |
| 2 | 루트까지 체인 검증 | trust store, basicConstraints |
| 3 | 이름·기간·용도 확인 | SAN 일치, notAfter 미경과, EKU |
| 4 | 폐지 상태 확인 | OCSP good, CRL 미등재 |
| 5 | 핸드셰이크 계속 또는 차단 | 검증 실패 시 연결 중단 |

> 요약: X.509 검증은 체인, 이름, 기간, 용도, 폐지 상태를 순차 확인하고 실패 시 연결을 차단함.

## Ⅳ. 특징

| 구분 | 공개키 단독 | X.509 인증서 | 판단 포인트 |
|:---|:---|:---|:---|
| 신원 검증 | 키 소유자 확인 곤란 | Subject/SAN과 CA 서명 제공 | SAN 기반 도메인 검증 |
| 사용 범위 | 용도 제한 없음 | KeyUsage/EKU로 제한 | serverAuth와 codeSigning 구분 |
| 수명 관리 | 수동 교체 | Validity, Serial, 폐지 정보 | 만료·폐지 자동 감시 |
| 감사·탐지 | 배포 이력 추적 곤란 | CT 로그와 CA 감사 가능 | 오발급 탐지 |

> 요약: X.509는 공개키에 신원·용도·기간·감사 정보를 결합하여 검증 가능한 신뢰 단위를 제공함.

## Ⅴ. 심화 비교 및 적용 판단

| 구분 | 기존/대안 | 본 키워드 | 선택 기준 |
|:---|:---|:---|:---|
| 구조 | self-signed 인증서 | CA 서명 X.509 | 브라우저·외부 고객 접속은 공인 CA |
| 비용/성능 | 장기 인증서 수동 관리 | 단기 인증서 자동 갱신 | 인증서 수 100개 이상이면 ACME |
| 운영/위험 | CN 검증, 폐지 미확인 | SAN·EKU·OCSP 검증 | MITM 차단과 감사 요구 수준 |

> 요약: 외부 공개 서비스는 CA 서명 X.509와 자동 갱신, 내부 서비스는 사설 CA+mTLS를 선택함.

| 리스크 | 원인 | 대응 방안 | 확인 지표 |
|:---|:---|:---|:---|
| 인증서 만료 | 수동 갱신, 인벤토리 누락 | ACME 자동화, 만료 30일 전 알림 | 만료 장애 0건 |
| 잘못된 이름 검증 | CN만 확인, SAN 누락 | SAN 필수 검증, wildcard 제한 | hostname mismatch 차단률 100% |
| 폐지 무시 | OCSP 장애, CRL 미동기화 | OCSP stapling, CRL 캐시 갱신 | 폐지 인증서 허용 0건 |

> 요약: X.509 운영 위험은 만료, 이름 검증 오류, 폐지 확인 누락이며 자동화와 검증 로그로 통제함.

| 점검 항목 | 목표 기준 | 측정 방법 |
|:---|:---|:---|
| 필드 품질 | SAN, EKU, KeyUsage, basicConstraints 적합 | zlint, OpenSSL verify |
| 검증 정책 | 체인·이름·기간·폐지 4종 검사 | 애플리케이션 TLS 테스트 |
| 탐지·복구 | CT 모니터링, 만료 알림, 재발급 절차 | CT 알림, 인증서 인벤토리 |

> 요약: X.509 도입 효과는 인증서 필드 품질과 검증 실패 차단 로그로 판단함.

## Ⅵ. 실무 적용 및 결론

**적용 방안 3개 (필수 — 단계별 또는 항목별):**
1. 발급 정책: SAN 필수, EKU(serverAuth/clientAuth/codeSigning) 분리, RSA 2048 이상 또는 ECDSA P-256 적용.
2. 자동화 운영: ACME 기반 발급·갱신, 인증서 인벤토리 구축, 만료 30·7·1일 알림 설정.
3. 검증·탐지: OCSP/CRL 확인, CT 로그 모니터링, hostname mismatch와 weak signature 탐지 룰 적용.

**결론 (2줄):**
- 기술사 판단: X.509는 인증서 파일이 아니라 체인·이름·기간·용도·폐지를 검증하는 운영 절차까지 포함해 적용해야 함.
- 향후 방향: 단기 인증서와 자동 갱신, PQC 인증서 확장 대응을 위해 인증서 생명주기 자동화가 필요.
