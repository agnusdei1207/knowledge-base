# 📖 【암기용】 개념 완전 이해

## 한눈에
- **개요**: **X.509 인증서는 공개키와 주체 신원을 CA 서명으로 묶는 ITU-T 표준 데이터 형식으로, ASN.1로 구조화되고 확장 필드를 갖는 v3가 현행**임. 신뢰 체인·CA 운영 전반은 (009 PKI 참조), 발급 절차·계층은 (011 CA 참조).
- **왜 필요한가**: 공개키 값만 주고받으면 그것이 누구 것인지 표준적으로 표현할 방법이 없음. X.509는 소유자·용도·유효기간·발급자를 한 형식에 담아 어떤 브라우저·OS·라이브러리든 동일하게 파싱·검증하게 함.
- **핵심 직관**: 신분증의 규격 양식과 같음. 이름·사진(공개키)·발급기관·만료일·용도 제한이 정해진 칸에 들어가고, 맨 아래 발급기관 서명이 위조를 막음.

## 핵심 용어 정리 (내부에 등장하는 것들)

답안에 등장하는 필드·확장·인코딩을 먼저 풀어 둠. 상위 핵심 키워드는 **v3 확장(extensions)** 으로, 이 확장 필드가 현대 인증서 검증의 핵심임.

| 용어/표기 | 의미 | 비유·예 |
|:---|:---|:---|
| ASN.1 | 데이터 구조를 언어 독립적으로 기술하는 표기 규칙 | 양식의 "칸 배치 설계도" |
| DER / PEM | ASN.1의 이진 인코딩 / 그 Base64 텍스트형 | 원본 바이트 / 메일로 보낼 텍스트 |
| tbsCertificate | 실제 서명 대상이 되는 인증서 본문 | 서명 전 신분증 내용 전체 |
| version(v1/v2/v3) | 인증서 형식 세대, v3에서 확장 추가 | 양식 개정판 번호 |
| serialNumber | CA가 발급 인증서마다 부여하는 고유 번호 | 신분증 발급 일련번호 |
| issuer / subject | 발급 CA 이름 / 인증서 주체 이름(DN) | 발급기관 / 소지자 |
| validity(notBefore/notAfter) | 유효 시작·만료 시각 | 발급일·만료일 |
| subjectPublicKeyInfo | 주체 공개키와 알고리즘 식별자 | 신분증에 박힌 본인 정보 |
| SAN(주체 대체 이름) | 인증서가 커버하는 도메인·IP 목록 | "이 신분증 유효 이름들" |
| KeyUsage / EKU | 키 허용 용도 / 확장 용도(서버인증 등) | "서명 전용" / "TLS 서버용" |
| BasicConstraints | CA 여부·하위 발급 깊이(pathLen) | "이 주체가 재발급 가능한가" |
| AKI / SKI | 상위 키 식별자 / 본 인증서 키 식별자 | 발급자 도장 번호 / 내 도장 번호 |
| CDP / AIA | CRL 배포지점 / OCSP·상위CA 위치 | 폐지목록 주소 / 상태조회 주소 |
| DN(Distinguished Name) | CN·O·OU 등으로 구성한 계층 이름 | "CN=example.com, O=회사" |

## 깊이 이해
- **배경·문제의식**: 1988년 X.500 디렉터리의 개체 인증용으로 시작해 인터넷 PKI(RFC 5280 프로파일)로 정착함. 초기 v1은 issuer·subject만 있어 "한 인증서=한 이름·용도 제한 불가"의 한계가 있었고, v3 확장으로 다중 도메인(SAN)·용도 제한(EKU)·폐지 위치(CDP/AIA)를 담게 됨.
- **작동 원리(어떻게+왜)**: 인증서는 tbsCertificate(본문) + signatureAlgorithm + signatureValue의 3부 구조임. CA는 tbsCertificate를 해시·서명하고, 검증자는 같은 본문을 재해시해 상위 공개키로 서명을 확인함. 본문 한 바이트만 바뀌어도 서명이 깨지므로 필드 위조가 불가함.
- **비유**: 여권과 같음. 정해진 칸(필드)에 정보가 들어가고, 발급국 인장(CA 서명)이 전체를 봉인하며, 유효기간·용도(비자=EKU)가 명시됨.
- **구체 예시**: `openssl x509 -text`로 보면 Version: 3, Serial Number, Signature Algorithm: sha256WithRSAEncryption, Issuer: CN=중간CA, Validity notAfter, Subject: CN=example.com, X509v3 Subject Alternative Name: DNS:example.com, DNS:www.example.com 순으로 표시됨.
- **흔한 오해·주의점**: (1) 현대 브라우저는 CN이 아니라 SAN으로 도메인을 검증함 — SAN 없는 인증서는 신뢰되지 않음. (2) 인증서는 비밀이 아니라 공개 데이터임(개인키만 비밀). (3) PEM은 그저 DER의 Base64 텍스트 포장일 뿐 다른 인증서가 아님.

## 연결 개념
- PKI·신뢰 체인 — X.509를 CA 계층으로 검증하는 운영 체계 (009 참조)
- CA·CSR — X.509를 발급하는 주체와 발급 요청 형식 (011 참조)
- CRL·OCSP — CDP/AIA 확장이 가리키는 폐지 확인 채널 (012 참조)

# 📝 【답안용】 시험 답안 템플릿

## 핵심 인사이트 (3줄 요약)

> 1. **본질**: X.509는 공개키-신원 바인딩을 ASN.1로 구조화한 ITU-T 표준 인증서 형식으로, v3 확장이 핵심임.
> 2. **가치**: TLS·코드서명·S/MIME·mTLS에서 소유자·용도·유효기간·폐지 위치를 표준 파싱 가능하게 함.
> 3. **판단 포인트**: 검증 품질은 SAN·EKU·BasicConstraints·유효기간 확인 여부가 좌우하며 CN 기반 판단은 폐기됨.

## 출제 의도 및 답안 포인트

| 출제 의도 | 반드시 짚을 핵심 | 감점 회피 포인트 |
|:---|:---|:---|
| 인증서 구조 이해 확인 | tbsCertificate·서명 3부 구조, v3 확장 | 필드 나열만 하고 서명 대상 구분 누락 |
| 확장 필드 이해 확인 | SAN·KeyUsage·EKU·BasicConstraints | CN으로 도메인 검증한다고 단정 |
| 운영 기준 확인 | 유효기간 단축·SAN 필수·인코딩(DER/PEM) | 유효기간·SAN 요건 누락 |

> 요약: X.509 답안은 3부 서명 구조·v3 확장의 검증 역할·유효기간 정책을 함께 써야 함.

---

## Ⅰ. 개요 및 필요성

- 개요: 공개키와 신원을 CA 서명으로 결합한 표준 인증서 형식임.
- 배경: 공개키 원값만으로는 소유자·용도·유효기간을 표준 표현할 수 없어 상호운용이 불가함.
- 필요성: X.509 v3는 SAN·EKU 등 확장으로 다중 도메인·용도 제한을 표현해 TLS·코드서명 검증 기준을 제공함.
- 전제: CA 신뢰 체인·발급 절차는 (009·011 참조)로 위임하고 인증서 자체의 구조·필드·확장에 집중함.

---

## Ⅱ. 구조 및 구성요소

```text
X.509 Certificate
  tbsCertificate (서명 대상 본문)
    -> version(v3) / serialNumber / signature(alg)
    -> issuer(DN) / validity(notBefore·notAfter) / subject(DN)
    -> subjectPublicKeyInfo
    -> extensions: SAN / KeyUsage / EKU / BasicConstraints / AKI·SKI / CDP·AIA
  signatureAlgorithm
  signatureValue (CA가 tbsCertificate에 서명)
```

| 구성요소 | 역할 | 특이사항 |
|:---|:---|:---|
| serialNumber | 발급 인증서 고유 식별 | CA 내 유일, 폐지 시 CRL 키로 사용 |
| validity | 유효기간 | TLS 서버 최대 398일, 단계적 단축 추세 |
| subjectPublicKeyInfo | 주체 공개키·알고리즘 | RSA-2048↑·ECDSA P-256·향후 PQC |
| SAN | 유효 도메인·IP 목록 | 현행 도메인 검증 기준(CN 대체) |
| KeyUsage / EKU | 키·확장 용도 제한 | digitalSignature, serverAuth 등 |
| BasicConstraints | CA 여부·pathLen | CA:FALSE면 하위 발급 불가 |

> 요약: X.509는 서명 대상 본문(tbsCertificate)과 CA 서명값으로 나뉘며, v3 확장이 도메인·용도·폐지 위치를 규정함.

---

## Ⅲ. 동작원리 및 흐름도

```text
CA: tbsCertificate 구성 -> 해시 -> 상위 개인키로 서명 -> 인증서 생성
  -> 배포(PEM/DER) -> 검증자: 본문 재해시 -> 상위 공개키로 서명 검증
  -> SAN·EKU·유효기간·BasicConstraints 확인 -> 폐지 확인(012)
```

1. CA가 주체 공개키·DN·유효기간·확장을 tbsCertificate로 조립하고 상위 CA 개인키로 서명함.
2. 서버·주체가 인증서를 PEM/DER로 보관하며, TLS 핸드셰이크 등에서 검증자에게 전달함.
3. 검증자가 tbsCertificate를 재해시해 상위 공개키로 signatureValue를 검증해 위조 여부를 판정함.
4. 검증자가 접속 도메인과 SAN 일치·EKU serverAuth·유효기간·CA 플래그를 확인하고 폐지 상태(012)까지 확인함.

> 요약: 발급은 본문 서명, 검증은 서명 확인 + 확장 필드(SAN·EKU·기간) 대조 + 폐지 확인의 다단계로 이뤄짐.

---

## Ⅳ. 특징

- 표준·상호운용: ITU-T X.509 + IETF RFC 5280 프로파일로 브라우저·OS·라이브러리가 동일 파싱함.
- 확장 중심: v3 extensions가 SAN·EKU·BasicConstraints로 용도·범위를 제약해 오남용을 차단함.
- 서명 무결성: tbsCertificate 한 바이트 변경도 서명을 깨뜨려 필드 위조가 원천 불가함.
- 공개 데이터: 인증서 자체는 비밀이 아니며, 보호 대상은 대응하는 개인키뿐임.
- 유효기간 축소 추세: 상호운용 유지하면서 폐지 지연 리스크를 줄이려 만료를 짧게 가는 방향임.

## Ⅴ. 심화 비교 및 적용 판단

인증서 커버리지 방식(단일·와일드카드·SAN 다중)을 관리·보안 축으로 비교함(다대상×다축이므로 표 사용).

| 구분 | 단일 도메인 | 와일드카드(*.example.com) | SAN 다중 도메인 |
|:---|:---|:---|:---|
| 커버 범위 | 정확히 한 FQDN | 한 단계 하위 서브도메인 전체 | 명시한 여러 FQDN·도메인 |
| 보안 영향 | 유출 시 영향 1개 | 유출 시 전 서브도메인 위험 | 유출 시 나열 도메인만 위험 |
| 운영 편의 | 도메인마다 발급 | 서브도메인 추가 무발급 | 도메인군 1장 관리, 변경 시 재발급 |

> 요약: 노출 폭 최소화가 우선이면 단일·SAN 명시, 서브도메인 동적 증가가 크면 와일드카드를 택하되 개인키 격리를 강화함.

리스크 관리는 불릿으로 정리함.
- 리스크: SAN 누락·오설정 — 원인: CN만 설정·다중 도메인 미기재 — 대응: SAN 필수화·발급 후 zlint 검사, SAN 미검증 0건.
- 리스크: 과도한 유효기간 — 원인: 장기 인증서 발급 — 대응: 398일 이하·자동 갱신 도입, 만료 초과 발급 0건.
- 리스크: 약한 키·알고리즘 — 원인: RSA-1024·SHA-1 서명 — 대응: RSA-2048↑·ECDSA P-256·SHA-256↑, 취약 인증서 0건.

지표 관리도 불릿으로 정리함.
- 지표: 프로파일 준수 — 목표: SAN·EKU·BasicConstraints 정상, RFC 5280 적합 — 측정: zlint·certlint.
- 지표: 유효기간 — 목표: TLS 398일 이하·만료 30일 전 갱신 — 측정: 인증서 인벤토리 스캔.
- 지표: 암호 강도 — 목표: 키·서명 알고리즘 정책 준수 — 측정: 정기 인증서 감사.

## Ⅵ. 실무 적용 및 결론

**적용 방안 3개 (필수 — 단계별 또는 항목별):**
1. 발급 프로파일 표준화: SAN 필수, EKU serverAuth 명시, BasicConstraints CA:FALSE 강제, DER/PEM 관리 규칙 정의.
2. 유효기간·갱신: TLS 서버 인증서 398일 이하로 제한하고 ACME 자동 갱신으로 만료 30일 전 교체.
3. 검증 파이프라인: 서명·SAN 일치·EKU·유효기간·BasicConstraints·폐지(012)를 코드로 강제해 예외 승인만 허용.

**결론 (2줄):**
- 기술사 판단: 서브도메인이 동적으로 증가하면 와일드카드+키 격리, 노출 폭 최소화가 우선이면 SAN 명시 인증서를 선택함.
- 향후 방향: 유효기간 단축·자동화와 PQC 공개키 알고리즘 전환에 대비한 암호 민첩성 프로파일이 필요함.
