# 📖 【암기용】 개념 완전 이해

> 목적: 제로 트러스트 아키텍처를 처음 보는 사람도 완벽히 이해하게 만든다. 시험 답안 양식이 아니라, 이해를 위한 친절한 설명이다.

## 한눈에
- **개요**: 제로 트러스트는 내부망도 신뢰하지 않고 모든 접근 요청을 지속적으로 검증하는 보안 아키텍처임
- **왜 필요한가**: VPN과 경계 방화벽 중심 모델은 한 번 내부망에 들어오면 횡적 이동이 쉬웠다. 클라우드·원격근무·SaaS 환경에서는 네트워크 위치만으로 신뢰를 판단할 수 없다.
- **핵심 직관**: 회사 건물에 들어왔다고 모든 사무실·서버실·금고 출입을 허용하지 않고, 문마다 신원·권한·상황을 다시 확인하는 방식임

## 깊이 이해
- **배경·문제의식**: 기존 경계 보안은 내부망을 신뢰 영역으로 전제했다. 그러나 피싱, 단말 감염, VPN 계정 탈취가 발생하면 공격자는 내부망에서 AD, 파일서버, DB로 이동할 수 있다.
- **작동 원리**: 사용자가 자원 접근을 요청할 때 Policy Engine이 신원, 단말 상태, 위치, 위험 점수, 자원 민감도를 평가한다. Policy Enforcement Point는 허용·차단·MFA 요구·읽기 전용 같은 결정을 집행한다.
- **비유**: 공항 보안처럼 항공권 확인 뒤에도 출국 심사, 탑승구 확인, 기내 수하물 점검이 이어지는 다단계 검증임
- **구체 예시**: 관리자 콘솔 접근은 회사 단말, EDR 정상, FIDO2 MFA, 위험 점수 30 이하, 근무 국가 접속일 때만 1시간 세션으로 허용함
- **흔한 오해·주의점**: 제로 트러스트는 특정 제품이 아니다. IAM, 단말 보안, 네트워크 분할, 정책 엔진, 로그 분석을 조합하는 목표 아키텍처임

## 연결 개념
- NIST SP 800-207 — 제로 트러스트 아키텍처 참조 모델
- SASE/ZTNA — 원격 접속과 SaaS 접근 집행 방식
- PBAC — 매 요청 정책 판단을 구현하는 접근 제어 방식

# 📝 【답안용】 시험 답안 템플릿

> 목적: 시험장에서 25분에 그대로 쓰는 답안 양식. 작성방식(추상표현 금지·수치·도식·문제유형 전환)을 엄격히 지킨다.
> 핵심: 제로 트러스트는 "신뢰하지 말라" 구호가 아니라 신원·단말·정책·세분화·관측을 결합한 아키텍처로 써야 한다.

## 핵심 인사이트 (3줄 요약)

> 1. **본질**: 제로 트러스트 아키텍처는 네트워크 위치 신뢰를 제거하고 모든 접근을 명시적으로 검증하는 보안 모델이다.
> 2. **가치**: 계정 탈취·단말 감염 후에도 세션 단위 정책 평가와 마이크로 세그멘테이션으로 횡적 이동 범위를 줄인다.
> 3. **판단 포인트**: Identity, Device, Policy Engine, PEP, Telemetry, Continuous Evaluation을 단계적으로 구축해야 한다.

## 출제 의도 및 답안 포인트

| 출제 의도 | 반드시 짚을 핵심 | 감점 회피 포인트 |
|:---|:---|:---|
| 경계 보안 한계 이해 확인 | 내부망 신뢰 제거, 명시적 검증, 최소 권한 | VPN 대체 제품으로만 설명 |
| 아키텍처 구성 역량 확인 | Policy Engine, Policy Administrator, PEP, Telemetry | NIST SP 800-207 구조 누락 |
| 구축·운영 판단 확인 | IAM, MFA, 단말 상태, ZTNA, 세그멘테이션, SIEM | 전면 도입만 주장하고 단계 계획 부재 |

> 요약: 제로 트러스트 답안은 기존 경계 보안 한계와 정책 기반 지속 검증 구조를 연결해야 한다.

---

## Ⅰ. 개요 및 필요성

- 개요: 모든 접근의 지속 검증
- 배경: 클라우드, SaaS, 원격근무 확산으로 내부망과 외부망의 경계가 약해졌고 VPN 계정 탈취 후 횡적 이동 위험이 커졌다.
- 필요성: NIST SP 800-207 기준으로 사용자·단말·자원·행위·위험을 매 요청 평가하고 최소 권한으로 접근을 제한해야 한다.

---

## Ⅱ. 구조 및 구성요소

```text
User/Device -> PEP/ZTNA -> Policy Engine -> Resource
                  |             |
                  +-> Telemetry
                                +-> IdP/EDR/SIEM/CMDB
```

| 구성요소 | 역할 | 특이사항 |
|:---|:---|:---|
| Identity Provider | 사용자·서비스 신원 인증과 MFA 수행 | OIDC, SAML, FIDO2 |
| Device Posture | 단말 보안 상태 평가 | EDR 정상, 디스크 암호화, 패치 수준 |
| Policy Engine | 신원·단말·위험·자원 속성 평가 | NIST SP 800-207 Policy Engine |
| PEP/ZTNA | 접근 집행과 세션 제어 | 앱 단위 접근, VPN 대체 또는 보완 |
| Telemetry/SIEM | 로그 수집, 위험 점수, 이상 징후 분석 | UEBA, XDR, SOAR 연계 |

> 요약: 제로 트러스트는 신원·단말·정책 판단·집행·관측 데이터를 결합해 매 요청을 검증한다.

---

## Ⅲ. 동작원리 및 흐름도

```text
Access Request -> Identity Verify -> Device Posture Check
-> Risk/Policy Evaluation -> Allow/Deny/Step-up MFA
-> Session Monitor -> Re-evaluate
```

| 단계 | 처리 내용 | 검증 기준 |
|:---:|:---|:---|
| 1 | 사용자·서비스 신원 인증 | MFA 적용률 98% 이상, FIDO2 우선 |
| 2 | 단말 보안 상태 확인 | EDR 정상, 패치 30일 이내, MDM 등록 |
| 3 | 정책 엔진이 자원 민감도와 위험 점수 평가 | 위험 점수 70 이상 차단 또는 Step-up MFA |
| 4 | PEP가 앱·API·세션 단위로 접근 집행 | 세션 TTL 1시간, 권한 범위 최소화 |
| 5 | 로그 분석 후 정책 재평가 | SIEM 이벤트 5분 이내 수집 |

> 요약: 제로 트러스트는 최초 인증 후에도 단말 상태와 위험 변화를 반영해 세션을 계속 재평가한다.

## Ⅳ. 특징

| 구분 | 경계 보안 모델 | 제로 트러스트 | 수치·판단 포인트 |
|:---|:---|:---|:---|
| 신뢰 기준 | 내부망 접속 여부 | 신원·단말·위험·자원 속성 | 매 요청 정책 평가 |
| 접속 방식 | VPN으로 네트워크 접속 | ZTNA로 앱 단위 접속 | 관리 포트 직접 노출 0개 |
| 권한 범위 | 네트워크 대역 접근 | 최소 권한·세션 TTL | 세션 1시간, 관리자 30분 |
| 탐지 | 경계 로그 중심 | IdP, EDR, PEP, SIEM 통합 | 이벤트 수집 5분 이내 |

> 요약: 제로 트러스트는 네트워크 위치 신뢰를 제거하고 앱·세션·정책 단위로 접근 범위를 줄인다.

## Ⅴ. 심화 비교 및 적용 판단

| 구분 | 기존/대안 | 본 키워드 | 선택 기준 |
|:---|:---|:---|:---|
| 구조 | VPN+방화벽 경계 | IdP+Device+Policy Engine+PEP | 원격근무·SaaS 비중 50% 이상 |
| 비용/운영 | 네트워크 중심 통제 | 신원·단말·로그 통합 운영 | IdP, EDR, SIEM 선행 필요 |
| 통제 | 내부망 신뢰 | 명시적 검증·최소 권한 | 관리자·개인정보 시스템부터 적용 |

> 요약: 제로 트러스트는 기존 VPN을 한 번에 폐기하기보다 고위험 앱부터 ZTNA와 정책 평가를 적용하는 단계 접근이 적합하다.

| 리스크 | 원인 | 대응 방안 | 확인 지표 |
|:---|:---|:---|:---|
| 사용자 업무 중단 | 과도한 정책 차단 | 모니터링 모드, 예외 정책, 단계 배포 | 차단 오탐률 1% 이하 |
| 정책 사일로 | IdP·EDR·ZTNA 정책 분리 | 중앙 Policy Engine, 공통 속성 모델 | 중복 정책 0건 |
| 관측 부족 | 로그 수집 지연 | PEP·IdP·EDR 로그 SIEM 통합 | 로그 수집 지연 p95 5분 이하 |

> 요약: 제로 트러스트 실패 원인은 제품 부재가 아니라 정책 사일로와 관측 부족인 경우가 많다.

| 점검 항목 | 목표 기준 | 측정 방법 |
|:---|:---|:---|
| 신원 검증 | MFA 98% 이상, Legacy Auth 0건 | IdP 리포트 |
| 접근 축소 | 앱 단위 접속 전환률 80% 이상 | ZTNA 정책 현황 |
| 침해 대응 | 위험 이벤트 탐지 후 정책 반영 15분 이내 | SIEM/SOAR 플레이북 |

> 요약: 제로 트러스트는 MFA, 앱 단위 접근, 정책 반영 시간으로 성숙도를 측정한다.

---

## Ⅵ. 실무 적용 및 결론

**적용 방안 3개:**
1. 1단계로 IdP 통합, MFA 98% 이상, Legacy Auth 0건을 달성하고 관리자 계정부터 FIDO2 적용
2. 2단계로 운영 콘솔·개인정보 시스템·SaaS 관리 페이지를 ZTNA 앱 단위 접근으로 전환
3. 3단계로 IdP, EDR, PEP, SIEM 로그를 통합해 위험 점수 70 이상 세션은 차단 또는 Step-up MFA 처리

**결론 (2줄):**
- 기술사 판단: 자산 식별과 신원 통합이 선행되지 않으면 제로 트러스트는 정책 사일로로 끝나므로 IdP·EDR·SIEM 순서로 기반을 다짐
- 향후 방향: 사용자 중심 접근에서 워크로드, API, 서비스 메시, 데이터 접근까지 지속 검증 범위가 확대됨
