## Ⅰ. 개요
| 항목 | 내용 |
|---|---|
| **정의** | 암호키의 전체 생명주기(생성, 보관, 분배, 교체, 폐기)를 체계적으로 보호하고 중앙 집중적으로 관리하는 시스템 체계임 |
| **배경/필요성** | 가장 강력한 암호 알고리즘이라 할지라도 암호키가 소프트웨어의 메모리나 설정 파일에 방치되어 탈취되면 무용지물이 됨 |
| **출제 의도** | 암호키의 생명주기 통제 원리 및 논리적 관리(KMS)와 물리적 보호(HSM) 장비의 상호보완적 역할 파악 |

## Ⅱ. 구성요소
```text
+-------------------+      +-------------------+      +-------------------+
|  KMS (Software)   |      |  Key Lifecycle    |      |  HSM (Hardware)   |
| (키 수명주기/정책)+----->| (생성->사용->폐기)+----->| (물리적 칩 보호)  |
+-------------------+      +-------------------+      +-------------------+
```
| 구성요소 | 설명 | 비유 |
|---|---|---|
| **KMS (Key Management Sys)** | 암호키의 접근 제어, 자동 갱신(Rotation), 폐기 정책 등을 소프트웨어적으로 통제하는 중앙 관리 플랫폼임 | 열쇠 대여 대장 및 자동 타이머 시스템 |
| **HSM (Hardware Security)**| 암호키를 칩 내부에 물리적으로 저장하고 암복호화 연산 자체도 장비 내부에서만 수행하는 전용 어플라이언스임 | 폭파 방지 장치가 달린 티타늄 1급 금고 |
| **마스터 키 (Master Key)** | 수많은 일반 데이터 암호화 키(DEK)들을 보호하기 위해 사용되는 최상위 키 암호화 키(KEK)임 | 모든 금고를 제어하는 마스터 열쇠 |

> 요약: 관리자(KMS)가 규칙을 정하고 배포하며, 절대 유출되면 안 되는 핵심 마스터 키는 강철 금고(HSM)에 봉인함.

## Ⅲ. 절차
```text
+----------------+   +----------------+   +----------------+   +----------------+
| 1. 키 생성/저장|-->| 2. 암호화 요청 |-->| 3. 데이터 키 교부|-->| 4. 갱신 및 폐기|
| (HSM 내 마스터)|   | (앱 -> KMS)    |   | (봉투 암호화)  |   | (주기적 순환)  |
+----------------+   +----------------+   +----------------+   +----------------+
```
1. **키 생성 및 저장**: 난수 발생기(TRNG)가 내장된 물리적 HSM 내부에서 최상위 마스터 키를 안전하게 생성하고 저장함
2. **암호화 요청 및 정책 적용**: 애플리케이션 데이터 암호화가 필요할 때 KMS에 요청하며, KMS는 접근 권한(IAM) 및 정책을 검증함
3. **봉투 암호화(Envelope) 교부**: KMS가 데이터 암호화키(DEK)를 생성해 평문으로 데이터와 함께 앱에 주고, 마스터키로 암호화된 DEK를 저장용으로 제공함
4. **키 갱신(Rotation) 및 폐기**: 규제 요건에 따라 일정 주기(예: 1년)마다 마스터 키를 자동 갱신하고 유출된 키는 즉시 폐기(Revoke) 처리함

> 요약: 봉투 암호화 방식을 통해 수많은 데이터 키를 효율적으로 분배하고, 마스터 키는 절대 밖으로 꺼내지 않음.

## Ⅳ. 문제점
* **단일 장애점(SPOF) 위험**: 중앙 KMS 서버나 HSM 장비가 장애로 다운되면, 연동된 모든 엔터프라이즈 시스템의 암/복호화가 전면 중단됨
* **클라우드 락인(Lock-in)과 주권 상실**: AWS KMS 등 클라우드 제공자의 키 관리에 전적으로 의존하면, 데이터 통제 주권을 상실하고 클라우드 종속 심화
* **고가의 구축 비용과 관리 복잡성**: 하드웨어 FIPS 140-2 Level 3 이상의 인증을 받은 HSM 장비 구축 비용이 수억 원에 달하고 숙련된 운영 인력 부족

## Ⅴ. 개선방안
* **단기 방안 (이중화 및 재해복구)**: KMS 서버의 로드밸런싱 다중화 및 HSM 장비 간 실시간 동기화(Active-Active)를 통해 고가용성 인프라 구축
* **중기 방안 (BYOK / HYOK 도입)**: 클라우드 종속성 탈피를 위해 고객이 직접 키를 생성해 주입하는 BYOK(Bring Your Own Key)나 고객 온프레미스 HSM에 키를 두는 HYOK 전략 채택
* **장기 방안 (CloudHSM 및 서비스형 전환)**: 고가의 물리적 도입 대신 멀티 테넌시가 분리된 클라우드 기반 관리형 CloudHSM 서비스를 활용하여 비용 효율성과 유연성 달성

## Ⅵ. 전망
* 제로 트러스트 보안 모델과 융합되어 인프라, 애플리케이션, 컨테이너 전반에 걸친 '모든 암호키의 라이프사이클 중앙 통제'가 의무화되는 추세임
* 향후 양자내성암호(PQC)로의 전환 시 기존 암호키 체계를 전면 재설정해야 하므로, 암호 민첩성을 지원하는 차세대 KMS 플랫폼 도입이 필수 기업 생존 과제가 됨
