## 1. 한눈에 이해하기 (Core Intuition)
- **정의**: OWASP AI 보안 가이드에서 가장 빈번하게 발생하는 사고 중 하나로, 챗봇이 사용자와 대화하던 중에 **자신이 과거에 학습했던 '다른 사람의 주민번호'나 회사의 '1급 영업 비밀(코드, API 키)'을 엉겁결에 입 밖으로 술술 불어버리는 심각한 기밀 유출 현상**입니다.
- **필요성**: 직원들이 업무 효율을 높이려고 사내 문서를 챗봇에 업로드하거나 RAG(사내 데이터 검색)를 연동하는 기업이 많아졌습니다. 문제는 AI 챗봇이 "이 정보는 1급 기밀이니까 임원한테만 말해주고, 저건 평사원한테도 말해줘도 돼"라는 접근 권한(눈치)이 전혀 없다는 것입니다. 해커나 권한 없는 직원이 살살 구슬리면, AI는 너무나 해맑게 사장님의 연봉 테이블이나 핵심 소스코드를 채팅창에 출력해 버립니다.
- **핵심 직관**: **"보안 서약서를 까먹은 과잉 친절한 도서관 사서"**. 
  - 과거 (DB 보안): 일반 직원은 '임원 전용 폴더'에 클릭 자체가 막혀서 들어갈 수 없습니다. (명확한 권한 통제).
  - **LLM 정보 노출**: 챗봇 사서(AI)는 도서관의 모든 책(기밀 포함)을 다 읽어서 뇌 속에 섞어뒀습니다. 신입사원이 사서에게 "우리 회사에서 젤 중요한 극비 프로젝트 내용 좀 요약해 줄래?"라고 묻자, 친절한 사서는 권한 확인도 안 하고 자기가 아는 모든 기밀을 1초 만에 읊어줍니다.

## 2. 왜 중요한가? (Background & Value)
- **등장 배경**: 삼성전자 직원들이 ChatGPT에 반도체 소스코드의 버그를 찾아달라고 복사-붙여넣기 했다가, 그 코드가 고스란히 OpenAI 서버로 넘어가 전 세계 해커들에게 노출될 뻔한 사태(Data Leakage)가 발생했습니다. AI는 먹어 치운 데이터를 분리해서 기억하지 않고 '확률적인 덩어리'로 기억하기 때문에, 한 번 기밀 정보가 모델 뱃속으로 넘어가면 그걸 다시 지우는 것(Unlearning)은 수학적으로 불가능에 가깝습니다.
- **가치**: "엔터프라이즈 AI 도입의 가장 큰 허들". 기업의 CISO(보안책임자)가 임직원들의 챗GPT 사용을 전면 차단하는 1순위 이유가 바로 이 '민감 정보 노출' 때문입니다. 이 문제를 해결하기 위한 사내 전용 LLM, RAG 접근 제어, 프롬프트 마스킹(DLP) 기술이 현재 보안 시장의 최대 캐시카우로 떠오르고 있습니다.

## 3. 어떻게 작동하는가? (Mechanism)
정보 노출은 크게 3가지 경로(학습, 대화, 검색)에서 발생합니다.

1. **학습 데이터 암기 (Memorization of Training Data)**
   - 모델을 훈련시킬 때 실수로 깃허브(GitHub) 퍼블릭 코드를 긁어 왔는데, 그 안에 하드코딩된 'AWS 비밀번호'나 '환자 의료 기록'이 섞여 있었습니다.
   - 모델은 이걸 그냥 텍스트로 달달 외워버립니다. 해커가 "AWS 패스워드를 자동완성해 봐"라고 유도하면 뇌 속에 박혀있던 진짜 패스워드가 튀어나옵니다 (모델 역전 공격 등).
2. **프롬프트 대화 유출 (User Conversation Leakage)**
   - 사용자가 챗봇 창에 주민번호나 회사 기밀을 입력합니다.
   - 퍼블릭 챗봇(무료 챗GPT 등)은 사용자의 대화를 **'모델 재학습(Re-training)' 데이터**로 가져갑니다. 내일 당장 다른 나라의 경쟁사 직원이 챗GPT에게 질문했을 때, 내가 어제 입력했던 기밀 코드가 답변으로 튀어나옵니다.
3. **RAG (검색 증강) 권한 붕괴 (Broken Access Control)**
   - 기업이 사내 문서를 챗봇에 연결했습니다. 일반 직원이 "사장님 전용 폴더에 있는 이번 달 구조조정 명단 요약해 줘"라고 칩니다.
   - 챗봇은 문서 접근 시 직원의 ID/비밀번호(RBAC)를 꼼꼼히 확인하지 않고 통째로 DB에서 긁어와 요약해 버립니다 (권한 우회).

## 4. 실전 활용 및 예시 (Real-world Application)
- **구체적 사례 (이탈리아 ChatGPT 접속 차단 사태)**: 
  - 2023년 이탈리아 데이터보호청이 전 세계 최초로 자국 내 ChatGPT 접속을 강제 차단했습니다. 이유가 바로 개인정보 노출 때문이었습니다. 챗GPT가 학습 데이터 수집 시 사용자 동의를 받지 않았고, 사용자들의 개인정보가 대화 중 무분별하게 노출된다며 GDPR(유럽 개인정보보호법) 위반을 때려버린 것입니다. 오픈AI는 황급히 "대화 기록 학습 끄기(Opt-out)" 버튼을 신설해야만 했습니다.
- **주의점 및 흔한 오해**: 
  - "오픈소스 LLM(Llama 등)을 회사 서버(On-premise)에 깔면 100% 안전하죠?" $\rightarrow$ **반만 맞습니다.** 외부(오픈AI)로 데이터가 날아가는 것은 막을 수 있습니다. 하지만 사내 망에 깔았다 하더라도, 내부 직원들끼리 직급에 안 맞는 기밀 정보(인사/연봉 데이터)를 챗봇을 통해 캐내는 '내부자 정보 노출(RAG 권한 붕괴)' 위협은 그대로 남아있으므로 철저한 문서별 권한 매핑이 필수입니다.

## 5. 핵심 비교 및 연결 개념 (Relation)
| 구분 | 기존 웹 정보 노출 (OWASP Web) | LLM 정보 노출 (OWASP LLM) |
|---|---|---|
| **유출 원인** | 개발자 코딩 실수, 서버 에러 메시지 노출 | **AI의 과도한 친절함, 학습 데이터의 통째 암기** |
| **방어 포인트** | 소스코드 리뷰, 에러 페이지 숨기기 | **입력 데이터 마스킹(DLP), 모델 출력 필터링** |
| **복구 가능성** | 코드 고치면 1분 만에 완벽 방어 | **이미 학습된 데이터는 지우는 것(Unlearning)이 거의 불가능** |

# ✍️ 단답형 / 서술형 시험장 출격 준비

### Ⅰ. 핵심 인사이트
- **본질**: OWASP LLM 위협 리스트의 핵심 항목으로, 대형 언어 모델(LLM)이 사용자(공격자)와의 대화 과정에서 **훈련 데이터(Training Data)에 포함된 PII(개인식별정보)나 영업 비밀을 암기하여 노출하거나, 불충분한 접근 제어(Broken Access Control)로 인해 권한 밖의 사내 기밀 문서를 RAG(검색 증강) 기반으로 요약·출력해 버리는 기밀성(Confidentiality) 침해 사고.**
- **가치**: 엔터프라이즈 환경에서 임직원들이 섀도우 AI(Shadow AI: 회사 몰래 퍼블릭 LLM을 업무에 사용하는 행위)를 통해 회사의 핵심 지적 재산(IP)이나 소스코드를 프롬프트 창에 복사-붙여넣기 할 때 발생하는 막대한 컴플라이언스(GDPR, PIPA) 리스크와 3rd Party 데이터 타협(Third-party Data Compromise) 위협의 근원을 폭로함.
- **판단 포인트**: IT 보안 책임자는 LLM의 기억 구조가 RDBMS와 완전히 다름을 인지해야 합니다. DB는 특정 행(Row)을 지우면 그만이지만, LLM은 신경망의 수십억 개 가중치(Weights)에 확률적으로 데이터를 융합(Memorization)해 버리므로 특정 데이터만 외과 수술하듯 삭제(Machine Unlearning)하는 기술은 상용화 초기 단계에 불과합니다. 따라서 **"애초에 모델 내부로 기밀 데이터가 들어가지 못하게 입구를 막는 전처리(Pre-processing) 격리"** 가 유일한 해법입니다.

### Ⅱ. 민감 정보 노출을 유발하는 3대 아키텍처적 결함
LLM 파이프라인의 어느 단계에서 정보가 뚫리는가의 분류.
1. **사전 학습 및 미세 조정(Fine-tuning) 데이터의 오염**
   - 기업이 자체 LLM을 구축할 때, 데이터 파이프라인에서 주민등록번호, AWS API Key 등을 정제(Sanitization/Masking)하지 않고 그대로 코퍼스(Corpus)에 부어버린 경우. (모델 역전 공격 등에 의해 100% 털림).
2. **퍼블릭 LLM의 무단 재학습 (Opt-out 실패)**
   - 직원이 업무 편의를 위해 ChatGPT, Claude 등에 올린 사내 문서 데이터가, 해당 빅테크 기업의 다음 세대 모델 훈련 데이터로 무단 편입되어 타사 사용자에게 유출되는 서드파티 종속성 위협.
3. **RAG (Retrieval-Augmented Generation) 인가(Authorization) 누락**
   - 사내 위키(Confluence/Jira)를 연동한 LLM 시스템에서, 사용자의 질의에 따라 벡터 DB(Vector DB)에서 문서를 검색할 때, 사용자의 직급/롤(RBAC)을 검사하지 않고 최고 관리자 권한으로 문서를 당겨와 요약해 버리는 권한 우회(Privilege Escalation) 위협.

### Ⅲ. 파급 효과 (Impact) 및 컴플라이언스 붕괴
- **개인정보보호법(PIPA) 및 GDPR 위반**: 사용자 동의 없이 긁어모은 데이터가 LLM을 통해 제3자에게 노출될 경우, '정보 주체의 삭제 요구권(잊혀질 권리)'을 시스템적으로 이행할 수 없어 천문학적 과징금 부과 대상이 됨.
- **지적 재산(IP) 유출**: 소스코드, 독점적 비즈니스 로직, 임원진 회의록 유출을 통한 경제적 타격.

### Ⅳ. 아키텍처적 방어 및 완화(Mitigation) 전략 (데이터 생명주기 통제)
"Never trust the model(모델을 절대 믿지 마라)" 원칙 기반의 데이터 샌드박싱.
1. **프롬프트 입력 마스킹 (Input DLP - Data Loss Prevention)**
   - 직원과 퍼블릭 LLM 사이에 리버스 프록시(Reverse Proxy) 또는 사내 전용 챗봇 포털 구축.
   - 직원이 프롬프트에 주민번호나 사내 소스코드를 입력하면, 앞단의 DLP(데이터 유출 방지) 엔진이 정규표현식이나 소형 NLP 모델을 돌려 `[MASKED_PII]`, `[MASKED_CODE]` 형태로 자동 비식별화/치환한 뒤 외부 LLM으로 전송.
2. **RAG 파이프라인의 메타데이터 기반 접근 제어 (Row-Level Security)**
   - 벡터 DB에 문서를 청크(Chunk) 단위로 쪼개어 넣을 때, 문서마다 `allowed_roles: ["HR", "Executive"]` 같은 메타데이터 태그를 반드시 부착.
   - 검색(Retrieval) 시, 질의를 날린 사용자의 JWT 토큰(Identity)과 문서 메타데이터를 대조(Vector DB Filtering)하여 권한이 있는 청크만 LLM의 컨텍스트로 전달.
3. **퍼블릭 LLM 사용 정책 및 엔터프라이즈 계약 (Enterprise Agreement)**
   - OpenAI 등의 퍼블릭 API를 사용할 때, **"사용자의 입력 프롬프트를 모델 재학습(Training)에 사용하지 않는다"** 는 Zero Data Retention 또는 Opt-out 조항이 포함된 엔터프라이즈 B2B 계약 체결 필수.

### Ⅴ. 결론 및 실무적 판단 포인트
- 기업의 인프라 책임자는 클라우드 네이티브 환경에 AI를 접목할 때 **Zero Trust(제로 트러스트)** 패러다임을 RAG 벡터 데이터베이스 영역까지 확장해야 합니다. LLM 자체는 사용자별 권한(IAM)을 인식할 능력이 없는 멍청한 확률 기계입니다. 따라서 모델이 문서를 읽기(Read) 직전, 백엔드 검색기(Retriever) 계층에서 **사용자의 식별자(Identity)를 바탕으로 데이터 열람 권한을 강제 차단하는 ABAC(속성 기반 접근 제어) 아키텍처 구현**이야말로 내부자 기밀 유출을 막는 유일하고 절대적인 방어선입니다.

### 💡 문제 유형별 목차 전환 포인트
- **[엔터프라이즈 환경의 생성형 AI 도입 리스크(Shadow AI) 및 방어 대책]**: Ⅰ번과 Ⅱ번(3대 유출 경로: 사전 학습, 재학습, RAG 누락)을 메인으로 서술. 섀도우 AI가 초래하는 치명적 영업 비밀 노출 시나리오(삼성전자 사례 등)의 경각심을 논증.
- **[안전한 RAG(검색 증강 생성) 아키텍처 설계 및 데이터 프라이버시(DLP) 방안]**: Ⅲ번(개인정보보호법 컴플라이언스)을 짚은 후, Ⅳ번의 방어책(프록시 기반 프롬프트 마스킹 설계 및 벡터 DB의 메타데이터 접근 제어)을 기술적 돌파구로 제시하여 실제 인프라 보안 구현 역량 증명.
