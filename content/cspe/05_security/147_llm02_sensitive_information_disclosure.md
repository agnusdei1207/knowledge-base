# 📖 【암기용】 개념 완전 이해

> 목적: LLM02 민감 정보 노출을 데이터 흐름과 통제 관점에서 이해하게 만든다. 시험 답안 양식이 아니라, 이해를 위한 친절한 설명이다.

## 한눈에
- **개요**: LLM이 학습·프롬프트·RAG·로그에 포함된 개인정보, 영업비밀, 자격증명을 응답이나 도구 호출로 노출하는 취약점
- **왜 필요한가**: LLM 서비스는 사용자가 입력한 데이터, 검색된 내부 문서, 시스템 프롬프트, API 응답을 한 번에 처리하므로 노출 경로가 애플리케이션 전 계층으로 확장된다.
- **핵심 직관**: 민감 정보 노출은 모델의 "기억" 문제만이 아니라 입력, 검색, 출력, 로그, 학습 재사용까지 이어지는 데이터 거버넌스 문제이다.

## 깊이 이해
- **배경·문제의식**: 기업은 LLM에 상담 기록, 코드, 계약서, 고객 정보, 보안 로그를 넣는다. 이 데이터가 마스킹 없이 컨텍스트에 포함되면 다른 사용자 응답, 디버그 로그, 분석 저장소로 전파될 수 있다.
- **작동 원리**: 사용자가 비밀 값을 직접 입력하거나, RAG가 권한 없는 문서를 검색하거나, 모델이 학습 중 본 문자열을 재현하거나, 출력 로그가 장기 보관되면서 노출이 발생한다.
- **비유**: 회의실 화이트보드에 비밀번호와 고객 정보를 써 놓고, 다음 회의 참가자가 그 내용을 사진으로 가져가는 상황과 같다.
- **구체 예시**: 고객상담 챗봇이 주민등록번호 13자리와 카드번호 16자리를 원문 로그로 저장하면, 운영자 검색·분석 대시보드·모델 개선 데이터셋을 통해 2차 노출이 발생함.
- **흔한 오해·주의점**: "모델이 외부로 학습하지 않으면 문제 없음"은 불충분함. 프롬프트 로그, vector DB, trace, APM, 평가 데이터에도 동일한 DLP 통제가 필요함.

## 연결 개념
- OWASP LLM Top 10 2025 — LLM02 Sensitive Information Disclosure로 분류
- 개인정보보호법·GDPR — 최소 수집, 목적 제한, 보관 기간과 연결
- RAG 권한 필터링 — 문서 ACL과 사용자 세션 권한 매칭 필요

# 📝 【답안용】 시험 답안 템플릿

> 목적: 시험장에서 25분에 그대로 쓰는 답안 양식. 작성방식(추상표현 금지·수치·도식·문제유형 전환)을 엄격히 지킨다.
> 핵심: 민감 정보 노출은 출력 차단만으로 끝나지 않으며, 수집·검색·생성·로그·재학습 전 단계의 데이터 분류와 DLP가 답안 중심이다.

## 핵심 인사이트 (3줄 요약)

> 1. **본질**: LLM02는 LLM 애플리케이션이 개인정보, 비밀키, 영업비밀, 시스템 프롬프트를 권한 없는 사용자나 저장소에 노출하는 데이터 보호 취약점이다.
> 2. **가치**: 데이터 분류, 토큰화, 권한 기반 검색, 출력 마스킹, 로그 보존 정책을 적용하면 노출 경로를 감사 가능하게 축소함.
> 3. **판단 포인트**: 모델 파라미터보다 프롬프트 로그, RAG 저장소, 평가 데이터셋, 도구 응답의 민감도 분류 여부를 먼저 확인해야 함.

## 출제 의도 및 답안 포인트

| 출제 의도 | 반드시 짚을 핵심 | 감점 회피 포인트 |
|:---|:---|:---|
| LLM 데이터 흐름 보안 이해 확인 | 입력·검색·출력·로그·학습 재사용 경로 | 출력 필터만 쓰고 로그·RAG 저장소 누락 금지 |
| 개인정보·비밀정보 통제 설계 확인 | DLP, masking, tokenization, RBAC, retention | "암호화 적용" 한 줄로 끝내지 않음 |
| 운영 감사 역량 확인 | 민감도 분류, 접근 로그, 삭제 요청, 보존 기간 | 규제·감사 대응 지표 미제시 금지 |

> 요약: 이 문제는 모델 보안보다 LLM 데이터 생명주기에서 민감 정보가 어디서 생성·저장·전파되는지 찾는 역량을 요구한다.

## Ⅰ. 개요 및 필요성

- 개요: LLM02 보호 데이터 노출
- 배경: LLM 서비스는 고객 입력, 내부 문서, 도구 응답, 운영 로그를 결합하므로 데이터 이동 경로가 길어짐.
- 필요성: OWASP LLM02와 개인정보보호법 기준으로 데이터 분류, 최소 보관, 마스킹, 검색 권한 필터링을 운영해야 함.

---

## Ⅱ. 구조 및 구성요소

```text
User Data -> PII Detector -> Prompt Store -> LLM
Internal Docs -> ACL Filter -> Vector DB -> Retriever
LLM Output -> DLP Masking -> Response / Log Store / Evaluation Dataset
```

| 구성요소 | 역할 | 통제 포인트 |
|:---|:---|:---|
| PII/Secret Detector | 주민번호·카드번호·API Key 탐지 | regex, entropy scan, secret scanner |
| ACL Filter | RAG 문서 접근 권한 검증 | user group, document label, ABAC |
| Prompt/Log Store | 입력·출력·trace 저장 | AES-256, KMS, retention 30~90일 |
| Output DLP | 응답 직전 민감 정보 마스킹 | token masking, deny response, ticket 생성 |
| 학습/평가 데이터셋 | 모델 개선·품질 평가 자료 | 비식별화, opt-out, data lineage |

> 요약: LLM02 대응은 입력 차단, 권한 검색, 출력 마스킹, 로그 보존, 재학습 제외를 하나의 데이터 통제로 연결해야 한다.

---

## Ⅲ. 동작원리 및 흐름도

```text
데이터 수집 -> 민감도 분류 -> 권한 기반 검색 -> LLM 생성
-> 출력 DLP 검사 -> 마스킹/차단 -> 암호화 저장/보존 기간 만료 삭제
```

| 단계 | 처리 내용 | 검증 기준 |
|:---:|:---|:---|
| 1 | 입력·문서·도구 응답 수집 | data classification label 존재 |
| 2 | PII·secret·IP 패턴 탐지 | 주민번호 13자리, API key entropy, 코드 secret scan |
| 3 | 사용자 권한으로 RAG 검색 제한 | ACL match rate, unauthorized hit 0건 |
| 4 | LLM 응답 생성 후 DLP 후처리 | masking 적용, deny policy |
| 5 | 로그 저장·삭제·재학습 제외 처리 | retention, deletion SLA, lineage ID |

> 요약: 민감 정보 노출은 생성 이후가 아니라 수집 시점부터 라벨링하고, 응답 직전 DLP와 저장 정책으로 재확인한다.

## Ⅳ. 특징

| 구분 | 기존 데이터 유출 | LLM02 민감 정보 노출 | 수치·기술 포인트 |
|:---|:---|:---|:---|
| 유출 경로 | DB dump, 파일 다운로드 | 프롬프트, RAG 검색, 응답, trace, 재학습 | prompt log, vector DB, eval set |
| 통제 단위 | 테이블·파일 ACL | 토큰·청크·문서·세션 권한 | chunk ACL, ABAC, DLP |
| 탐지 방식 | DLP, SIEM | DLP+LLM output scan+secret scan | entropy threshold, regex, semantic classifier |
| 감사 기준 | 접근 로그 | 입력·출력·검색 근거·도구 응답 로그 | trace ID 100% 연결 |

> 요약: LLM02는 DB 접근 제어를 넘어 프롬프트와 검색 청크 단위의 데이터 라벨과 보존 정책이 핵심이다.

## Ⅴ. 심화 비교 및 적용 판단

| 구분 | 기존/대안 | 본 키워드 | 선택 기준 |
|:---|:---|:---|:---|
| 구조 | 일반 DLP 게이트웨이 | LLM 입력·RAG·출력·로그 DLP | 내부 문서 기반 RAG면 chunk ACL 필수 |
| 비용/통제 | 전체 마스킹 | 민감도별 masking/tokenization | 업무 정확도와 규제 요구를 함께 판단 |
| 운영/감사 | 웹 접근 로그 | prompt/output/retrieval lineage | 개인정보 삭제 요청 30일 이내 처리 필요 시 적용 |

> 요약: 민감 정보 보호는 응답 마스킹만이 아니라 검색 청크와 로그의 lineage를 보존할 때 감사 대응이 가능하다.

| 리스크 | 원인 | 대응 방안 | 확인 지표 |
|:---|:---|:---|:---|
| 개인정보 응답 노출 | 출력 DLP 부재 | PII masking, deny template, 상담원 승인 | PII leakage 0건 |
| 비밀키 저장 | 개발자가 key를 프롬프트 입력 | secret scanner, vault 참조, 로그 redaction | secret detection MTTR 10분 |
| 권한 없는 RAG 검색 | vector DB가 문서 ACL 미반영 | metadata ACL, ABAC filter, query-time check | unauthorized chunk 0건 |

> 요약: 주요 리스크는 응답보다 저장소와 검색 권한에서 발생하며, 탐지 시간과 무권한 청크 수로 통제한다.

| 점검 항목 | 목표 기준 | 측정 방법 |
|:---|:---|:---|
| 민감 정보 탐지 | PII/secret recall 95% 이상 | 샘플 데이터셋 1,000건 DLP 테스트 |
| 권한 검색 | unauthorized retrieval 0건 | 사용자 그룹별 RAG 회귀 테스트 |
| 보존·삭제 | 로그 보존 30~90일, 삭제 SLA 30일 | KMS 로그, deletion job, lineage 대조 |

> 요약: LLM02 성공 기준은 탐지율, 무권한 검색 0건, 보존·삭제 SLA 준수로 판단한다.

## Ⅵ. 실무 적용 및 결론

**적용 방안 3개 (필수 — 단계별 또는 항목별):**
1. 데이터 분류: 입력·문서·도구 응답에 `public/internal/confidential/restricted` 라벨을 부여하고 restricted 데이터는 기본 응답 차단
2. RAG 권한 통제: vector DB metadata에 user group, document owner, retention date를 저장하고 query-time ABAC 필터 적용
3. 로그·재학습 통제: 프롬프트 로그 AES-256 암호화, KMS 키 분리, 보존 30~90일, 모델 개선 데이터셋은 PII 비식별화 후 사용

**결론 (2줄):**
- 기술사 판단: 공개 FAQ 챗봇이면 출력 DLP 중심, 내부 지식 RAG이면 문서 ACL·lineage·삭제 SLA를 필수 통제로 선택함
- 향후 방향: Agent와 업무 시스템 연동이 늘수록 tool response와 trace 로그까지 포함한 end-to-end DLP 체계가 필요함
