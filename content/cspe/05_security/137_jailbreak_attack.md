# 📖 【암기용】 개념 완전 이해

> 목적: 탈옥 Jailbreak 공격을 처음 보는 사람도 완벽히 이해하게 만든다. 시험 답안 양식이 아니라, 이해를 위한 친절한 설명이다.

## 한눈에
- **개요**: LLM의 안전 정책과 거부 규칙을 우회하도록 역할극·인코딩·다단계 지시를 넣는 공격
- **왜 필요한가**: 생성형 AI 서비스는 유해 콘텐츠, 개인정보, 악성 코드 생성을 제한한다. 공격자는 정책 문구의 빈틈과 모델의 지시 추종 성향을 이용해 제한을 풀려고 한다.
- **핵심 직관**: 출입금지 규칙이 있는 건물에서 "나는 점검자 역할이다"라고 말하며 출입 절차를 속이는 사회공학과 유사하다.

## 깊이 이해
- **배경·문제의식**: LLM은 system prompt, safety policy, user prompt의 우선순위를 학습했지만 자연어의 모호성과 긴 대화 맥락 때문에 항상 동일하게 거부하지 않는다.
- **작동 원리**: 공격자는 "이전 지시 무시", "가상 시나리오", "토큰을 거꾸로 출력", "단계별로 생각" 같은 우회 지시를 조합한다. 모델은 표면상 합법적 요청으로 해석하고 금지 정보를 일부 출력할 수 있다.
- **비유**: 보안 교육을 받은 직원에게 금지 자료를 직접 달라고 하면 거부하지만, "교육용 모의훈련 문서"라고 포장해 조금씩 요청하는 방식이다.
- **구체 예시**: 악성 코드 생성 요청이 차단되자 Base64 인코딩, 역할극, 조각 출력 요청을 결합해 최종 스크립트를 재조립하게 하는 방식이 대표적이다.
- **흔한 오해·주의점**: "시스템 프롬프트에 금지 문구를 추가하면 끝"은 틀렸다. 모델·정책·입력 필터·출력 검사·레드팀 평가가 같이 동작해야 우회 성공률을 낮출 수 있다.

## 연결 개념
- Prompt Injection: 탈옥은 사용자 직접 입력, 간접 인젝션은 외부 콘텐츠 경유 공격
- AI Red Teaming: 우회 프롬프트 집합으로 정책 실패 지점을 반복 평가
- Content Safety: 분류기, 정책 엔진, 출력 필터로 유해 응답을 통제

# 📝 【답안용】 시험 답안 템플릿

> 목적: 시험장에서 25분에 그대로 쓰는 답안 양식. 작성방식(추상표현 금지·수치·도식·문제유형 전환)을 엄격히 지킨다.
> 핵심: Jailbreak는 단일 금칙어 차단 문제가 아니라 정책 우선순위, 대화 맥락, 출력 검증, 평가 체계가 결합된 LLM 안전성 문제이다.

## 핵심 인사이트 (3줄 요약)

> 1. **본질**: 탈옥 Jailbreak 공격은 LLM의 안전 정책을 역할극·난독화·다단계 지시로 우회해 금지 응답을 생성시키는 공격이다.
> 2. **가치**: 방어 목표는 모든 문장을 차단하는 것이 아니라 정책 위반 응답률, 우회 성공률, 재시도 성공률을 지표로 낮추는 것이다.
> 3. **판단 포인트**: 모델 정렬, 입력 분류, 출력 정책, 사용자 위험도, 레드팀 평가를 묶어 운영해야 한다.

## 출제 의도 및 답안 포인트

| 출제 의도 | 반드시 짚을 핵심 | 감점 회피 포인트 |
|:---|:---|:---|
| LLM 안전 정책 우회 원리 확인 | 역할극, 난독화, 다단계 분해, 인코딩, 맥락 오염 | 단순 금칙어 필터로 설명 |
| 방어 체계 설계 역량 확인 | system policy, classifier, output moderation, rate limit | 모델 교체만으로 해결된다고 단정 |
| 운영 평가 지표 확인 | jailbreak success rate, refusal precision, false refusal rate | 유해 차단과 정상 응답 거부의 균형 누락 |

> 요약: 이 문제는 공격 유형 나열보다 정책 우회 경로와 정량 평가 지표를 연결한 안전성 설계를 요구한다.

---

## Ⅰ. 개요 및 필요성

- 개요: LLM 안전 정책 우회 공격
- 배경: 생성형 AI가 상담, 개발, 검색, 업무 자동화에 사용되면서 유해 정보, 개인정보, 악성 자동화 지시 노출 위험이 증가함.
- 필요성: OWASP LLM Top 10과 NIST AI RMF 기준으로 정책 위반률, 재현 프롬프트, 감사 로그를 평가 지표로 운영해야 함.

---

## Ⅱ. 구조 및 구성요소

```text
Attacker Prompt -> Obfuscation/Roleplay -> LLM Context -> Safety Policy
                                      +-> Multi-turn Coercion
Policy Engine -> Output Moderation -> Response / Refusal -> Evaluation Log
```

| 구성요소 | 역할 | 통제 포인트 |
|:---|:---|:---|
| 공격 프롬프트 | 금지 요청을 우회 표현으로 변형 | 패턴 분류, 언어·인코딩 정규화 |
| 대화 맥락 | 이전 발화와 역할 지시 누적 | context window 정책, 세션 리셋 |
| 안전 정책 | 허용·제한·거부 기준 정의 | policy versioning, priority order |
| 출력 검사 | 응답의 위반 여부 최종 판단 | content classifier, DLP, code scanning |
| 평가 로그 | 우회 시도와 거부 사유 축적 | red-team corpus, audit trail |

> 요약: Jailbreak 방어는 입력·맥락·정책·출력·평가가 연결된 파이프라인이며, 한 단계 누락 시 우회 성공률이 증가한다.

---

## Ⅲ. 동작원리 및 흐름도

```text
금지 요청 작성 -> 역할극/인코딩/분해로 변형
-> 모델이 합법 요청처럼 해석 -> 금지 정보 일부 생성
-> 출력 검사에서 위반 판정 -> 거부/수정 응답 -> 평가셋 반영
```

| 단계 | 처리 내용 | 검증 기준 |
|:---:|:---|:---|
| 1 | 공격자가 금지 요청을 우회 표현으로 변환 | jailbreak pattern 탐지 |
| 2 | 세션 맥락에 권한·역할 변경 지시 누적 | system priority 유지 여부 |
| 3 | LLM이 답변 후보 생성 | policy violation score |
| 4 | 출력 분류기가 유해·개인정보·악성 코드 판단 | moderation threshold 0.8 이상 |
| 5 | 결과를 거부·안전 대안·로그로 처리 | attack success rate 1% 이하 |

> 요약: 공격은 입력 변형으로 시작하지만 방어는 응답 생성 이후의 정책 판정과 평가 피드백까지 이어져야 한다.

## Ⅳ. 특징

| 구분 | 일반 프롬프트 오류 | Jailbreak 공격 | 수치·판단 기준 |
|:---|:---|:---|:---|
| 의도 | 모호한 질문으로 오답 발생 | 정책 우회 목적의 적대적 지시 | 우회 프롬프트 성공률 |
| 기법 | 정보 부족, 문맥 누락 | 역할극, DAN류, Base64, 다국어 변환 | 변형 유형별 커버리지 |
| 피해 | 부정확한 답변 | 유해 정보·악성 코드·개인정보 출력 | policy violation rate |
| 방어 | 프롬프트 개선 | 정책 엔진+분류기+레드팀 | false refusal rate 5% 이하 |

> 요약: Jailbreak는 품질 문제가 아니라 의도적 정책 우회이며, 차단률과 정상 요청 거부율을 함께 관리해야 한다.

## Ⅴ. 심화 비교 및 적용 판단

| 비교 축 | 기존/대안 | 본 키워드 | 선택 기준 |
|:---|:---|:---|:---|
| 구조 | 키워드 차단 | 의미 기반 분류+정책 우선순위 | 다국어·인코딩 우회가 많은 서비스 |
| 비용/성능 | 모든 요청 수동 검토 | 위험 점수 기반 자동 차단 | 일 10만 요청 이상 API |
| 운영/위험 | 모델 응답만 확인 | 입력·출력·세션·사용자 위험도 통합 | 미성년자·의료·금융 영역 포함 시 |

> 요약: 단순 필터는 낮은 비용으로 시작 가능하나, 공개 서비스는 의미 기반 분류와 레드팀 평가가 필수이다.

| 리스크 | 원인 | 대응 방안 | 확인 지표 |
|:---|:---|:---|:---|
| 유해 응답 생성 | 역할극·난독화로 정책 우회 | safety classifier, output moderation | violation rate 0.5% 이하 |
| 정상 응답 과차단 | 정책 임계값 과도 설정 | category별 threshold 조정 | false refusal rate 5% 이하 |
| 반복 공격 자동화 | 봇이 변형 프롬프트 대량 제출 | rate limit, abuse score, CAPTCHA | 동일 계정 재시도 10회 이하 |

> 요약: 운영 리스크는 유해 출력과 과차단이 동시에 존재하므로, 위반률과 정상 거부율을 같이 측정해야 한다.

| 점검 항목 | 목표 기준 | 측정 방법 |
|:---|:---|:---|
| 우회 차단 | jailbreak success rate 1% 이하 | red-team prompt 1,000건 회귀 테스트 |
| 정상 응답 유지 | false refusal rate 5% 이하 | 정상 요청 라벨셋 A/B 평가 |
| 감사 추적 | 정책 버전·판정 사유 100% 기록 | prompt log, moderation log |

> 요약: Jailbreak 대응 성과는 차단률 하나가 아니라 우회 성공률, 정상 거부율, 감사 추적률의 조합으로 판단한다.

## Ⅵ. 실무 적용 및 결론

**적용 방안 3개 (필수 — 단계별 또는 항목별):**
1. 입력 단계: 언어 감지, Base64·URL 인코딩 정규화, 역할극·권한 상승 문구 분류기로 위험 점수 0~1 산정
2. 출력 단계: 유해 콘텐츠·개인정보·악성 코드 분류기와 DLP를 병렬 적용하고 threshold 0.8 이상은 거부 응답 처리
3. 운영 단계: red-team prompt 1,000건 이상 회귀 테스트, 정책 버전별 우회 성공률·정상 거부율 대시보드 운영

**결론 (2줄):**
- 기술사 판단: 내부 업무용은 접근통제와 로그 중심, 공개 API는 rate limit·abuse score·출력 moderation을 포함한 다층 방어가 필요함
- 향후 방향: 멀티모달·에이전트 환경에서는 텍스트뿐 아니라 이미지 OCR, 음성 전사, 도구 호출까지 Jailbreak 평가 범위를 확장해야 함
