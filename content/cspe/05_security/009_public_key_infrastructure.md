# 📖 【암기용】 개념 완전 이해

> 목적: PKI를 처음 봐도 완전하게 이해하게 만든다. 시험 답안 양식이 아니라, 이해를 위한 설명이다.

## 한눈에
- **개요**: 공개키와 실체 신원을 인증서로 묶고 신뢰 체인으로 검증하는 기반구조
- **왜 필요한가**: 공개키만 있으면 그 키가 누구의 것인지 알 수 없다. PKI는 CA가 신원 확인 후 인증서를 발급하고, 사용자는 루트 CA부터 서버 인증서까지 서명 체인을 검증한다.
- **핵심 직관**: 주민등록증처럼 "이 공개키는 이 사람·서버의 것"이라는 보증서를 신뢰기관이 발급하고, 검증자는 발급기관 도장을 따라가며 신뢰를 확인한다.

## 깊이 이해
- **배경·문제의식**: 공개키 암호는 키 소유자 확인 없이는 MITM에 취약하다. PKI는 등록, 발급, 배포, 검증, 폐지, 감사 절차를 묶어 공개키 신뢰 문제를 해결한다.
- **작동 원리**: 주체는 키쌍과 CSR을 만들고 RA가 신원을 검증한다. CA는 X.509 인증서에 서명하고, 클라이언트는 인증서 체인·도메인명·유효기간·폐지 상태를 검증한다.
- **비유**: 회사 출입증 발급과 유사하다. 인사팀이 신원을 확인하고 출입증을 발급하며, 경비 시스템은 발급자·만료일·분실 신고 여부를 확인한다.
- **구체 예시**: 브라우저가 HTTPS 접속 시 서버 인증서의 SAN 도메인, 중간 CA 서명, 루트 신뢰 저장소, OCSP 상태를 검증한 뒤 TLS 세션을 시작한다.
- **흔한 오해·주의점**: PKI는 암호 알고리즘 하나가 아니다. 인증서 정책, CA 운영, 키 관리, 폐지 배포, 감사가 포함된 신뢰 운영 체계이다.

## 연결 개념
- X.509 인증서 — PKI의 공개키·신원 바인딩 데이터 형식
- CA·RA — 인증서 발급과 신원 확인 주체
- CRL·OCSP — 인증서 폐지 상태 확인

# 📝 【답안용】 시험 답안 템플릿

> 목적: 시험장에서 25분에 그대로 쓰는 답안 양식. 작성방식(추상표현 금지·수치·도식·문제유형 전환)을 엄격히 지킨다.

## 핵심 인사이트 (3줄 요약)

> 1. **본질**: PKI는 공개키와 주체 신원을 X.509 인증서로 결합하고 CA 신뢰 체인으로 검증하는 보안 기반구조임.
> 2. **가치**: TLS, 전자서명, 코드서명, S/MIME에서 인증·무결성·부인방지와 키 분배 신뢰를 제공함.
> 3. **판단 포인트**: 발급보다 검증·폐지·키 보호·감사 체계가 PKI 운영 품질을 결정함.

## 출제 의도 및 답안 포인트

| 출제 의도 | 반드시 짚을 핵심 | 감점 회피 포인트 |
|:---|:---|:---|
| 신뢰 체계 이해 확인 | Root CA, Intermediate CA, RA, Repository, CRL/OCSP | PKI를 단순 인증서 저장소로 설명 금지 |
| 보안형 위협·통제 판단 확인 | MITM, CA 키 유출, 오발급, 폐지 지연 | 위협-통제-탐지-복구 연결 누락 금지 |
| 실무 운영 기준 확인 | CP/CPS, HSM, CT 로그, 키 회전, 감사 | 인증서 발급 절차만 나열 금지 |

> 요약: PKI 답안은 인증서 생명주기와 신뢰 체인 검증, 폐지·감사 운영을 함께 써야 함.

---

## Ⅰ. 개요 및 필요성

PKI는 공개키 신뢰 기반구조이다.  
공개키 암호는 키 소유자 확인이 없으면 MITM 공격을 막지 못한다.  
PKI는 인증서 발급·검증·폐지·감사를 통해 TLS, 전자서명, 코드서명의 신뢰 기준을 제공한다.

---

## Ⅱ. 구조 및 구성요소

```text
주체 키쌍·CSR -> RA 신원확인 -> CA 서명·발급 -> Repository 배포
  / Client 검증 -> Chain·SAN·Validity·Revocation 확인
  / Audit·CT Log -> 오발급 탐지
```

| 구성요소 | 역할 | 특이사항 |
|:---|:---|:---|
| Root CA | 최상위 신뢰 앵커 | 오프라인 보관, HSM, 장기 유효기간 |
| Intermediate CA | 실제 인증서 발급 | 용도별 분리, pathLen 제약 |
| RA | 가입자 신원 확인 | 도메인·조직·개인 검증 |
| Repository | 인증서·CRL 배포 | LDAP/HTTP, 가용성 관리 |
| 검증 주체 | 체인·폐지·정책 확인 | 브라우저, OS, 애플리케이션 |

> 요약: PKI는 CA 계층, 신원 확인, 저장소, 검증 주체가 함께 동작하는 신뢰 운영 체계임.

---

## Ⅲ. 동작원리 및 흐름도

```text
키쌍 생성 -> CSR 제출 -> RA 검증 -> CA 서명 -> 인증서 배포
  -> 클라이언트 체인 검증 -> 폐지 확인 -> 세션·서명 신뢰 판단
```

| 단계 | 처리 내용 | 검증 기준 |
|:---:|:---|:---|
| 1 | 가입자 키쌍·CSR 생성 | 개인키 export 금지, CSR 서명 검증 |
| 2 | RA 신원·도메인 검증 | CA/B Forum 요구사항, 조직 증빙 |
| 3 | CA 인증서 서명·발급 | CP/CPS, serial number, EKU |
| 4 | 클라이언트 인증서 검증 | Chain, SAN, Validity, Signature |
| 5 | 폐지·감사 확인 | OCSP/CRL, CT Log, 감사로그 |

> 요약: PKI는 발급 절차와 검증 절차가 분리되며, 검증자는 체인·이름·기간·폐지 상태를 모두 확인함.

---

## Ⅳ. 특징

| 구분 | 자체 공개키 배포 | PKI | 판단 포인트 |
|:---|:---|:---|:---|
| 신뢰 모델 | 사전 공유·수동 등록 | CA 계층 기반 신뢰 체인 | 대규모 인터넷 서비스에 적합 |
| 검증 범위 | 키 일치 여부 | 신원, 서명, 기간, 폐지, 정책 | SAN·EKU 검증 필수 |
| 운영 통제 | 키 목록 관리 | CP/CPS, HSM, CRL/OCSP, 감사 | CA 키 보호가 최상위 통제 |
| 장애 영향 | 개별 키 영향 | CA 오발급·키 유출 시 광역 영향 | CT 로그와 긴급 폐지 절차 필요 |

> 요약: PKI는 확장된 신뢰 검증을 제공하지만 CA 운영 실패 시 영향 범위가 커서 감사·폐지 체계가 필수임.

## Ⅴ. 심화 비교 및 적용 판단

| 비교 축 | 기존/대안 | 본 키워드 | 선택 기준 |
|:---|:---|:---|:---|
| 구조 | PSK, self-signed | CA 기반 PKI | 외부 사용자·브라우저 신뢰 필요 시 PKI |
| 비용/성능 | 수동 배포 | 자동 발급·갱신 ACME | 인증서 수 100개 이상이면 자동화 |
| 운영/위험 | 개별 키 탈취 | CA 키 유출·오발급 | HSM, CT, 감사 요구 수준 |

> 요약: 폐쇄망 소수 장비는 PSK·사설 CA, 인터넷 공개 서비스는 공인 PKI와 자동 갱신을 선택함.

| 리스크 | 원인 | 대응 방안 | 확인 지표 |
|:---|:---|:---|:---|
| CA 키 유출 | 온라인 Root CA, HSM 미사용 | Root 오프라인, HSM, 2인 통제 | CA key export 0건 |
| 인증서 오발급 | RA 검증 실패, DNS 탈취 | CT 모니터링, CAA 레코드, 승인 절차 | CT 오발급 탐지 시간 1시간 이하 |
| 폐지 지연 | CRL 배포 실패, OCSP 장애 | OCSP responder 이중화, CRL 주기 단축 | OCSP 가용성 99.9%, CRL 지연 15분 이하 |

> 요약: PKI 리스크는 CA 키·오발급·폐지 지연이며 예방과 탐지 지표를 분리해 관리함.

| 점검 항목 | 목표 기준 | 측정 방법 |
|:---|:---|:---|
| 인증서 품질 | SAN, EKU, KeyUsage, 유효기간 398일 이하 | zlint, certlint |
| 운영 보안 | HSM, MFA, 2인 승인, CP/CPS 준수 | 감사로그, 정기 감사 |
| 탐지·복구 | CT 모니터링, OCSP/CRL 상태 | CT 알림, OCSP 헬스체크 |

> 요약: PKI 성공 여부는 인증서 발급량이 아니라 검증 오류, 폐지 지연, 오발급 탐지 시간으로 판단함.

## Ⅵ. 실무 적용 및 결론

**적용 방안 3개 (필수 — 단계별 또는 항목별):**
1. CA 구조 설계: Root CA 오프라인 보관, Intermediate CA 용도별 분리, HSM FIPS 140-2/140-3 적용.
2. 생명주기 자동화: ACME 기반 발급·갱신, 만료 30일 전 알림, 인증서 인벤토리 100% 등록.
3. 탐지·복구 체계: CT 로그 모니터링, CAA 레코드 설정, 오발급 시 24시간 내 폐지·재발급 절차 운영.

**결론 (2줄):**
- 기술사 판단: 대외 서비스는 공인 PKI, 내부 마이크로서비스는 사설 CA+mTLS로 분리하여 신뢰 범위를 제한해야 함.
- 향후 방향: 인증서 수명 단축과 PQC 인증서 전환에 대비해 자동화·암호 민첩성 체계 필요.
