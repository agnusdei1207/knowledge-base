# 📖 【암기용】 개념 완전 이해

## 한눈에
- **개요**: **PKI는 공개키와 실체 신원을 X.509 인증서로 묶고 CA 신뢰 체인으로 검증·폐지·감사하는 보안 기반구조**임. 서명 생성/검증 원리는 (008 전자서명 참조), 인증서 데이터 형식은 (010 X.509 참조).
- **왜 필요한가**: 공개키만으로는 그 키가 누구의 것인지 알 수 없어 MITM에 취약함. PKI는 CA가 신원 확인 후 인증서를 발급하고, 검증자는 루트 CA부터 서버 인증서까지 서명 체인을 따라 신뢰를 확인함.
- **핵심 직관**: 주민등록증처럼 "이 공개키는 이 주체의 것"이라는 보증서를 신뢰기관(CA)이 발급하고, 검증자는 발급기관 도장을 거슬러 올라가며 신뢰를 확인함.

## 핵심 용어 정리 (내부에 등장하는 것들)

답안에 등장하는 주체·구성요소·운영 통제를 먼저 풀어 둠. 상위 핵심 키워드는 **신뢰 체인(certificate chain)** 으로, 여기서 인증·인가·부인방지를 혼동하지 않는 것이 중요함.

| 용어/표기 | 의미 | 비유·예 |
|:---|:---|:---|
| CA(인증기관) | 인증서에 서명해 공개키-신원을 보증하는 주체 | 신분증 발급 기관 |
| Root / Intermediate CA | 최상위 신뢰 앵커 / 실제 발급용 하위 CA | 본청 / 지역 발급소 |
| RA(등록기관) | 발급 전 가입자 신원·도메인을 검증 | 창구의 본인 확인 담당 |
| Repository | 인증서·CRL을 배포하는 저장소 | 신분증·분실목록 게시판 |
| CSR | 가입자가 제출하는 공개키·정보 서명 요청서 | 발급 신청서 |
| 신뢰 체인 | 루트→중간→종단 인증서 서명 연결 | 발급 계보를 따라가는 검증 |
| 인증 vs 인가 | 신원 확인 vs 권한 부여 | 누구인지 vs 무엇을 해도 되는지 |
| 부인방지 | 서명 주체가 사후 부인 불가 (008 참조) | 개인키 단독 보유로 발뺌 차단 |
| SAN / EKU | 인증서 대상 도메인 / 허용 용도 | "이 신분증은 이 이름·이 용도" |
| CRL / OCSP | 폐지 목록 / 실시간 폐지 상태 조회 | 분실 신고 대장 / 즉시 조회 창구 |
| CP / CPS | 인증서 정책 / 인증업무 준칙 | 발급 규정과 운영 매뉴얼 |
| CT 로그 | 발급된 인증서를 공개 기록하는 투명성 로그 | 오발급을 감시하는 공개 장부 |
| CAA 레코드 | 어느 CA가 도메인 인증서를 발급할지 DNS 지정 | "이 CA만 발급 허용" 표찰 |
| HSM / mTLS | 키 보호 장치 / 상호 인증 TLS | CA 키 금고 / 양방향 신분 확인 |
| ACME | 인증서 자동 발급·갱신 프로토콜 | 자동 발급 자판기 |

## 깊이 이해
- **배경·문제의식**: 공개키 암호는 키 소유자 확인 없이는 MITM에 취약함. PKI는 등록·발급·배포·검증·폐지·감사를 하나의 절차로 묶어 공개키 신뢰 문제를 해결함.
- **작동 원리(어떻게+왜)**: 주체가 키쌍·CSR을 만들고 RA가 신원을 검증함. CA가 X.509 인증서에 서명하며, 검증자는 인증서 체인·도메인명(SAN)·유효기간·폐지 상태를 모두 확인함. 발급과 검증이 분리되어 각 단계에서 위조를 걸러냄.
- **비유**: 회사 출입증 발급과 유사함. 인사팀(RA)이 신원을 확인하고 출입증(CA)을 발급하며, 경비 시스템(검증자)은 발급자·만료일·분실 신고 여부를 확인함.
- **구체 예시**: 브라우저가 HTTPS 접속 시 서버 인증서의 SAN 도메인·중간 CA 서명·루트 신뢰 저장소·OCSP 상태를 검증한 뒤 TLS 세션을 시작함.
- **흔한 오해·주의점**: (1) PKI는 알고리즘 하나가 아니라 인증서 정책·CA 운영·키 관리·폐지 배포·감사를 포함한 신뢰 운영 체계임. (2) 인증(신원 확인)과 인가(권한 부여)는 별개 — PKI는 인증·무결성·부인방지를 제공하지 접근 권한을 부여하지 않음. (3) 검증에서 서명 확인만 하고 폐지·이름·기간을 빼면 위조 인증서를 수용하게 됨.

## 연결 개념
- X.509 인증서 — PKI의 공개키·신원 바인딩 데이터 형식 (010 참조)
- 전자 서명 — CA의 인증서 발급과 검증이 서명에 기반 (008 참조)
- CRL·OCSP — 인증서 폐지 상태 확인

# 📝 【답안용】 시험 답안 템플릿

## 핵심 인사이트 (3줄 요약)

> 1. **본질**: PKI는 공개키와 주체 신원을 X.509 인증서로 결합하고 CA 신뢰 체인으로 검증하는 보안 기반구조임.
> 2. **가치**: TLS·전자서명·코드서명·S/MIME에서 인증·무결성·부인방지와 키 분배 신뢰를 제공함.
> 3. **판단 포인트**: 발급보다 검증·폐지·키 보호·감사 체계가 PKI 운영 품질을 결정함.

## 출제 의도 및 답안 포인트

| 출제 의도 | 반드시 짚을 핵심 | 감점 회피 포인트 |
|:---|:---|:---|
| 신뢰 체계 이해 확인 | Root/Intermediate CA, RA, Repository, CRL/OCSP | PKI를 단순 인증서 저장소로 설명 |
| 위협·통제 판단 확인 | MITM, CA 키 유출, 오발급, 폐지 지연 | 위협-통제-탐지-복구 연결 누락 |
| 실무 운영 기준 확인 | CP/CPS, HSM, CT 로그, 키 회전, 감사 | 인증서 발급 절차만 나열 |

> 요약: PKI 답안은 인증서 생명주기·신뢰 체인 검증·폐지·감사 운영을 함께 써야 함.

---

## Ⅰ. 개요 및 필요성

- 개요: 공개키 신뢰를 관리하는 인증서 기반구조임.
- 배경: 공개키 값만으로는 소유자·용도를 확인할 수 없어 위조 인증서와 MITM을 구분하기 어려움.
- 필요성: PKI는 X.509 인증서 발급·검증·폐지·감사로 TLS·전자서명·코드서명의 신뢰 기준을 제공함.
- 전제: 서명 검증 원리와 인증서 형식은 (008·010 참조)로 위임하고 CA·인증서 체인·신뢰모델에 집중함.

---

## Ⅱ. 구조 및 구성요소

```text
주체 키쌍·CSR -> RA 신원확인 -> CA 서명·발급 -> Repository 배포
  / 검증자: Chain·SAN·Validity·Revocation 확인
  / Audit·CT Log -> 오발급 탐지
```

| 구성요소 | 역할 | 특이사항 |
|:---|:---|:---|
| Root CA | 최상위 신뢰 앵커 | 오프라인 보관, HSM, 장기 유효기간 |
| Intermediate CA | 실제 인증서 발급 | 용도별 분리, pathLen 제약 |
| RA | 가입자 신원 확인 | 도메인·조직·개인 검증 |
| Repository | 인증서·CRL 배포 | LDAP/HTTP, 가용성 관리 |
| 검증 주체 | 체인·폐지·정책 확인 | 브라우저, OS, 애플리케이션 |

> 요약: PKI는 CA 계층·신원 확인·저장소·검증 주체가 함께 동작하는 신뢰 운영 체계임.

---

## Ⅲ. 동작원리 및 흐름도

```text
키쌍 생성 -> CSR 제출 -> RA 검증 -> CA 서명 -> 인증서 배포
  -> 검증자 체인 검증 -> 폐지 확인 -> 세션·서명 신뢰 판단
```

1. 가입자가 키쌍·CSR을 생성하며, 개인키 export를 금지하고 CSR 자체 서명을 검증함.
2. RA가 CA/B Forum 요구사항과 조직 증빙으로 가입자 신원·도메인을 검증함.
3. CA가 CP/CPS에 따라 serial number·EKU를 담아 인증서에 서명·발급함.
4. 검증자가 Chain·SAN·Validity·Signature를 확인하고, OCSP/CRL·CT 로그·감사로그로 폐지·오발급까지 확인함.

> 요약: PKI는 발급 절차와 검증 절차가 분리되며, 검증자는 체인·이름·기간·폐지 상태를 모두 확인함.

---

## Ⅳ. 특징

- 신뢰 모델: 사전 공유·수동 등록이 아니라 CA 계층 서명 체인으로 대규모 인터넷 서비스까지 확장 가능함.
- 검증 범위: 키 일치만이 아니라 신원·서명·유효기간·폐지·정책(SAN·EKU)을 모두 확인함.
- 역할 분리: 인증(신원 확인)과 인가(권한 부여)를 구분하며, PKI는 인증·무결성·부인방지를 담당함.
- 운영 통제: CP/CPS·HSM·CRL/OCSP·감사가 결합되며, CA 개인키 보호가 최상위 통제 지점임.
- 장애 영향: CA 오발급·키 유출 시 광역 영향을 미쳐 CT 로그와 긴급 폐지 절차가 필수임.

---

## Ⅴ. 심화 비교 및 적용 판단

self-signed/사설 신뢰와 공인 PKI를 신뢰 모델·운영 축으로 비교함(다대상×다축이므로 표 사용).

| 구분 | self-signed · PSK | 공인 PKI(CA 기반) | 선택 기준 |
|:---|:---|:---|:---|
| 신뢰 모델 | 사전 공유·수동 등록 | CA 계층 신뢰 체인 | 외부 사용자·브라우저 신뢰 필요 시 PKI |
| 검증 범위 | 키 일치 여부 | 신원·서명·기간·폐지·정책 | SAN·EKU 검증 필요 시 PKI |
| 운영 부담 | 수동 배포·개별 키 관리 | ACME 자동 발급·갱신, CT·감사 | 인증서 100개 이상이면 자동화 PKI |

> 요약: 폐쇄망 소수 장비는 PSK·사설 CA, 인터넷 공개 서비스는 공인 PKI와 자동 갱신을 선택함.

리스크 관리는 불릿으로 정리함.
- 리스크: CA 키 유출 — 원인: 온라인 Root CA·HSM 미사용 — 대응: Root 오프라인·HSM·2인 통제, CA key export 0건.
- 리스크: 인증서 오발급 — 원인: RA 검증 실패·DNS 탈취 — 대응: CT 모니터링·CAA 레코드·승인 절차, 탐지 1시간 이하.
- 리스크: 폐지 지연 — 원인: CRL 배포 실패·OCSP 장애 — 대응: OCSP 이중화·CRL 주기 단축, OCSP 가용성 99.9%.

지표 관리도 불릿으로 정리함.
- 지표: 인증서 품질 — 목표: SAN·EKU·KeyUsage 준수, 유효기간 398일 이하 — 측정: zlint·certlint.
- 지표: 운영 보안 — 목표: HSM·MFA·2인 승인·CP/CPS 준수 — 측정: 감사로그·정기 감사.
- 지표: 탐지·복구 — 목표: CT 모니터링·OCSP/CRL 상태 정상 — 측정: CT 알림·OCSP 헬스체크.

## Ⅵ. 실무 적용 및 결론

**적용 방안 3개 (필수 — 단계별 또는 항목별):**
1. CA 구조 설계: Root CA 오프라인 보관, Intermediate CA 용도별 분리, HSM FIPS 140-2/140-3 적용.
2. 생명주기 자동화: ACME 기반 발급·갱신, 만료 30일 전 알림, 인증서 인벤토리 100% 등록.
3. 탐지·복구 체계: CT 로그 모니터링, CAA 레코드 설정, 오발급 시 24시간 내 폐지·재발급 절차 운영.

**결론 (2줄):**
- 기술사 판단: 대외 서비스는 공인 PKI, 내부 마이크로서비스는 사설 CA+mTLS로 분리해 신뢰 범위를 제한해야 함.
- 향후 방향: 인증서 수명 단축과 PQC 인증서 전환에 대비해 자동화·암호 민첩성 체계가 필요함.
