# 📖 【암기용】 개념 완전 이해

> 목적: PBAC를 처음 보는 사람도 완벽히 이해하게 만든다. 시험 답안 양식이 아니라, 이해를 위한 친절한 설명이다.

## 한눈에
- **개요**: PBAC는 접근 허용 여부를 사용자·자원·행위·환경 조건을 조합한 정책으로 결정하는 접근 제어 방식임
- **왜 필요한가**: RBAC는 역할 수가 수백 개로 늘면 권한 관리가 복잡해진다. PBAC는 시간, 위치, 단말 상태, 데이터 민감도 같은 조건을 정책으로 묶어 예외 처리를 줄인다.
- **핵심 직관**: 출입증 이름만 보는 방식이 아니라, "누가, 무엇을, 언제, 어떤 단말로, 어떤 목적에서" 들어오려는지 종합 심사하는 방식임

## 깊이 이해
- **배경·문제의식**: 클라우드·SaaS·원격근무 환경에서는 동일 직무라도 접속 위치, MFA 여부, 자산 등급에 따라 허용 범위가 달라진다. 고정 역할 중심 RBAC만으로는 동적 조건을 표현하기 어렵다.
- **작동 원리**: 요청 주체가 자원 접근을 요청하면 PEP가 요청을 가로채고, PDP가 정책 저장소와 속성 정보를 조회해 Permit/Deny/Obligation을 결정한다. 정책은 XACML, OPA/Rego, IAM Condition 같은 선언 규칙으로 관리한다.
- **비유**: 도서관 대출 규칙처럼 학생증만 확인하지 않고, 대출 권한, 도서 등급, 연체 여부, 열람실 시간, 지도교수 승인 여부를 함께 보는 방식임
- **구체 예시**: "개발자는 근무시간 09:00~18:00, 회사 MDM 등록 단말, MFA 완료, 개인정보 테이블은 SELECT만 허용"처럼 5개 조건을 정책 1개로 묶음
- **흔한 오해·주의점**: PBAC는 RBAC를 버리는 기술이 아니다. 역할은 기본 권한 경계로 쓰고, 정책은 조건·예외·위험 수준을 제어하는 보조 판단층으로 설계해야 함

## 연결 개념
- ABAC (Attribute-Based Access Control) — PBAC 정책 판단에 필요한 사용자·자원·환경 속성 제공
- IAM — 신원 수명주기, 인증, 권한 부여의 운영 기반
- Zero Trust — 매 요청을 정책 기반으로 검증하는 보안 아키텍처

# 📝 【답안용】 시험 답안 템플릿

> 목적: 시험장에서 25분에 그대로 쓰는 답안 양식. 작성방식(추상표현 금지·수치·도식·문제유형 전환)을 엄격히 지킨다.
> 핵심: PBAC는 접근 제어 모델 나열 문제가 아니라, RBAC 한계와 동적 정책 판단 구조를 연결해 설명해야 한다.

## 핵심 인사이트 (3줄 요약)

> 1. **본질**: PBAC는 사용자·자원·행위·환경 속성을 정책 조건으로 평가해 접근 결정을 내리는 접근 제어 모델이다.
> 2. **가치**: 역할 폭증을 줄이고, 시간·위치·MFA·단말 상태·데이터 등급을 정책 1곳에서 감사 가능하게 관리한다.
> 3. **판단 포인트**: PDP/PEP 분리, 정책 충돌 해소, 정책 테스트, 감사 로그를 함께 설계해야 운영 리스크를 낮출 수 있다.

## 출제 의도 및 답안 포인트

| 출제 의도 | 반드시 짚을 핵심 | 감점 회피 포인트 |
|:---|:---|:---|
| 접근 제어 모델 비교 역량 확인 | DAC·MAC·RBAC·ABAC·PBAC 차이와 선택 기준 | PBAC를 RBAC의 단순 확장으로만 설명 |
| 정책 엔진 구조 이해 확인 | PEP, PDP, PIP, PAP, 정책 저장소, 감사 로그 | 정책 언어와 집행 지점을 누락 |
| 실무 적용 판단 확인 | OPA/Rego, XACML, IAM Condition, 정책 테스트 | 권한 허용만 쓰고 Deny 우선·충돌 해소 미제시 |

> 요약: PBAC 답안은 정책 판단 구조와 운영 통제를 연결해야 채점 포인트가 살아난다.

---

## Ⅰ. 개요 및 필요성

- 개요: 정책 조건 기반 접근 결정
- 배경: 클라우드·SaaS·원격근무 환경에서는 동일 역할이라도 접속 위치, MFA, 단말 보안 상태, 자원 민감도에 따라 허용 범위가 달라진다.
- 필요성: 정책 엔진이 XACML·OPA 같은 정책 언어로 조건을 평가하고 역할 기반 권한을 요청 단위로 보정해야 한다.

---

## Ⅱ. 구조 및 구성요소

```text
Subject/Device -> PEP -> PDP -> Policy Store -> Decision
                    |       |
                    +-> Audit Log
                            +-> PIP Attribute Source
```

| 구성요소 | 역할 | 특이사항 |
|:---|:---|:---|
| PEP (Policy Enforcement Point) | API Gateway, DB Proxy, Service Mesh에서 요청 차단·허용 집행 | Envoy ext_authz, Kubernetes Admission 적용 |
| PDP (Policy Decision Point) | 정책과 속성을 평가해 Permit/Deny 결정 | OPA, XACML PDP, IAM Policy Engine |
| PIP (Policy Information Point) | 사용자·단말·자원·위험 점수 속성 제공 | IdP, CMDB, EDR, DLP 연계 |
| PAP (Policy Administration Point) | 정책 작성·승인·배포 관리 | GitOps, 2인 승인, 정책 버전 관리 |

> 요약: PBAC는 정책 작성(PAP), 속성 조회(PIP), 판단(PDP), 집행(PEP)을 분리해 권한 결정을 감사 가능한 절차로 만든다.

---

## Ⅲ. 동작원리 및 흐름도

```text
Access Request -> PEP Intercept -> Attribute Collect
-> PDP Policy Evaluation -> Permit/Deny/Obligation
-> Resource Access or Block -> Audit Log
```

| 단계 | 처리 내용 | 검증 기준 |
|:---:|:---|:---|
| 1 | 사용자·서비스·단말의 접근 요청 수신 | 신원 식별자, 세션 ID, 요청 행위 기록 |
| 2 | PEP가 요청을 중단하고 속성 수집 | MFA, 위치, 단말 준수율, 자원 등급 |
| 3 | PDP가 정책 우선순위와 Deny 우선 원칙 평가 | 정책 충돌 0건, 테스트 케이스 통과 |
| 4 | Permit/Deny와 Obligation 반환 | 마스킹, 사유 코드, TTL 포함 |
| 5 | 접근 집행 후 SIEM 감사 로그 전송 | 실패율, 정책 ID, 결정 시간 p95 30ms |

> 요약: PBAC는 요청 시점의 속성을 모아 정책 엔진에서 판단하고, 집행 결과를 감사 로그로 남기는 흐름이다.

---

## Ⅳ. 특징

| 구분 | 기존 RBAC | PBAC | 수치·판단 포인트 |
|:---|:---|:---|:---|
| 권한 단위 | 역할 중심 | 정책 조건 중심 | 역할 500개 이상이면 Role Explosion 발생 |
| 조건 표현 | 부서·직무 위주 | 시간, 위치, MFA, 단말, 데이터 등급 | 5개 이상 속성 조합 가능 |
| 변경 관리 | 역할 수정 후 배포 | 정책 파일 버전 관리 | Git PR, 2인 승인, 회귀 테스트 |
| 감사 | 사용자-역할 매핑 확인 | 정책 ID와 결정 사유 확인 | SIEM 보존 1년 이상 권장 |

> 요약: PBAC는 고정 역할로 표현하기 어려운 동적 접근 조건을 정책으로 분리해 변경·감사 단위를 명확히 한다.

## Ⅴ. 심화 비교 및 적용 판단

| 구분 | 기존/대안 | 본 키워드 | 선택 기준 |
|:---|:---|:---|:---|
| 구조 | RBAC Role-Permission 매핑 | PBAC 정책 엔진+속성 저장소 | 권한 예외가 월 20건 이상이면 PBAC 검토 |
| 비용/운영 | 역할 추가로 처리 | 정책 테스트·배포 파이프라인 필요 | 정책 p95 결정시간 30ms 이하 목표 |
| 통제 | 정기 권한 검토 중심 | 실시간 조건 평가+감사 | 개인정보·계좌·의료 데이터 접근에 적합 |

> 요약: PBAC는 예외 권한이 반복되는 조직에서 RBAC 위에 조건 판단층을 추가할 때 효과가 크다.

| 리스크 | 원인 | 대응 방안 | 확인 지표 |
|:---|:---|:---|:---|
| 정책 충돌 | Allow/Deny 규칙 중복 | Deny 우선, 우선순위, 정책 Lint | 충돌 탐지 0건 |
| 속성 오류 | HR·CMDB·EDR 정보 지연 | 속성 TTL, 동기화 재시도, 결측 시 Deny | 속성 동기화 지연 p95 5분 이하 |
| 우회 접근 | PEP 미적용 경로 존재 | API Gateway, DB Proxy, Sidecar 강제 | 미보호 엔드포인트 0개 |

> 요약: PBAC 리스크는 정책 자체보다 충돌·속성 품질·집행 누락에서 발생하므로 자동 점검으로 통제해야 한다.

| 점검 항목 | 목표 기준 | 측정 방법 |
|:---|:---|:---|
| 정책 품질 | 정책 단위 테스트 커버리지 90% 이상 | OPA test, XACML test suite |
| 결정 지연 | PDP p95 30ms 이하, 오류율 0.1% 이하 | APM, Gateway metric |
| 감사 추적 | 정책 ID·결정 사유·속성 스냅샷 100% 기록 | SIEM, 감사 샘플링 |

> 요약: PBAC 도입 성공은 정책 품질, 결정 지연, 감사 추적 3개 지표로 판정한다.

---

## Ⅵ. 실무 적용 및 결론

**적용 방안 3개:**
1. RBAC 기본 역할을 유지하고 개인정보·관리자 API·계좌 조회에 OPA/Rego 정책을 우선 적용
2. PAP를 GitOps로 구성하고 정책 변경 시 PR, 2인 승인, 단위 테스트 90% 이상을 배포 조건으로 설정
3. PEP를 API Gateway, Service Mesh, DB Proxy에 배치하고 결정 로그를 SIEM에 1년 이상 보관

**결론 (2줄):**
- 기술사 판단: 역할 수가 작고 조건이 단순하면 RBAC, 예외 조건과 감사 요구가 크면 RBAC+PBAC 조합을 선택함
- 향후 방향: Zero Trust와 SaaS 권한 관리를 위해 정책 코드화, 자동 검증, 지속 감사 체계로 발전함
