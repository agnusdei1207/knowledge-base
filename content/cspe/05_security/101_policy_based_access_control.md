## 1. 한눈에 이해하기 (Core Intuition)
- **정의**: 시스템에 접근할 때 단순히 "직급(역할)이 뭐냐?"를 따지는 것을 넘어, 기업의 다양한 보안 규정과 컴플라이언스를 코드로 번역한 **'중앙 정책(Policy)' 엔진을 통과해야만 접근을 허락하는 차세대 접근 제어 모델**입니다.
- **필요성**: 클라우드 시대에는 수백 개의 마이크로서비스(API)가 서로 통신합니다. 이 수많은 서비스마다 각자 권한 설정을 코딩해 두면, 회사 보안 규정이 바뀔 때마다 모든 개발자가 야근하며 소스코드를 수정해야 합니다(유지보수 지옥). 권한 검사 로직을 개별 앱에서 뜯어내어, **"정책만 담당하는 중앙 판사(Policy Engine)"** 에게 맡기기 위해 탄생했습니다.
- **핵심 직관**: **"회사 건물의 중앙 AI 보안 심사대"**. 
  - 과거: 각 부서 사무실(앱) 문마다 경비원이 서서 각자의 수첩을 보고 "너 들어와, 너 안 돼"를 결정했습니다. (수첩 업데이트 힘듦).
  - **PBAC**: 각 사무실 문에는 경비원이 없습니다. 대신 문고리가 중앙 AI 서버와 연결되어 있습니다. 직원이 문을 열려 하면 중앙 AI가 회사 전체의 **정책 문서(코드로 작성됨)** 를 0.1초 만에 스캔하여 "이 직원은 현재 근무 시간이 아니므로 규정에 따라 거부!"라고 즉각 판결을 내려 문을 잠급니다. 정책이 바뀌면 중앙 AI의 텍스트 코드 한 줄만 바꾸면 전사에 즉시 적용됩니다.

## 2. 왜 중요한가? (Background & Value)
- **등장 배경**: ABAC(속성 기반)가 훌륭하긴 했지만, 이것 역시 구현이 너무 복잡했습니다. 최근 쿠버네티스(Kubernetes)나 클라우드 네이티브 환경이 대세가 되면서, 인프라 자체가 코드로 관리(IaC)되기 시작했습니다. 이에 발맞춰 **"보안 권한도 코드로 쓰자 (Policy-as-Code)"** 라는 움직임이 일어났고, 이를 완벽하게 구현한 OPA(Open Policy Agent) 같은 솔루션이 등장하며 PBAC가 업계 표준으로 급부상했습니다.
- **가치**: "개발자와 보안팀의 완벽한 분리". 개발자는 비즈니스 로직(앱 기능)만 개발하고, 보안/접근 제어 로직은 보안팀이 중앙 정책 서버에 코드로 짜서 올려놓으면 알아서 통제됩니다. (민첩성과 거버넌스 동시 확보).

## 3. 어떻게 작동하는가? (Mechanism)
PBAC는 정책을 결정하는 뇌(PDP)와 집행하는 손발(PEP)이 철저히 분리된 아키텍처입니다.

1. **정책 작성 (Policy as Code)**
   - 보안 관리자가 사람이 읽을 수 있는 선언적 언어(예: Rego 언어)로 정책을 짭니다.
   - `규칙 1: 오직 인사팀만 '/salary' API를 호출할 수 있다.`
   - `규칙 2: 주말에는 모든 DB 접근을 차단한다.`
2. **정책 시행 지점 (PEP, Policy Enforcement Point)**
   - 직원이 사내 시스템(API)을 호출합니다.
   - 앱 앞단에 있는 프록시(손발)가 이 요청을 딱 잡고, 중앙 엔진에 "얘 들여보내요?"라고 물어봅니다.
3. **정책 결정 지점 (PDP, Policy Decision Point)**
   - 중앙 엔진(뇌)이 미리 입력된 정책 코드를 촥 돌려봅니다.
   - "오늘 일요일이네? 규칙 2번 위반. 거부(Deny)!" 라고 결론을 내어 프록시에 전달합니다.
4. **집행**
   - 프록시가 요청을 끊고 직원 화면에 "주말 접근 불가" 에러를 띄웁니다. 앱 서버는 애초에 이 요청을 구경도 못 해보고 안전하게 보호됩니다.

## 4. 실전 활용 및 예시 (Real-world Application)
- **구체적 사례**: 
  - 최근 클라우드 네이티브 환경의 절대 강자인 **OPA (Open Policy Agent)** 가 PBAC의 대표적 구현체입니다. 넷플릭스, 핀터레스트 등 수천 개의 마이크로서비스를 굴리는 기업들은 모든 API 통신 권한을 OPA의 정책 코드로 관리합니다. OPA 엔진이 중앙에서 각 서비스 옆에 붙어 0.001초 만에 권한을 심사해 줍니다.
- **주의점 및 흔한 오해**: 
  - "PBAC은 ABAC이랑 똑같은 거 아닌가요?" $\rightarrow$ **매우 비슷하지만 철학이 다릅니다.** 
    - ABAC은 "속성(시간, 장소, 부서)을 조합해서 통제하자"는 **'조건'** 에 방점이 찍혀 있습니다.
    - PBAC은 ABAC의 방식을 포함하되, "이 모든 것을 기업의 규정(컴플라이언스)과 맵핑하여 **'중앙집중화된 코드(Policy)'** 로 관리하자"는 **'아키텍처 및 거버넌스'** 에 방점이 찍힌 한 단계 더 진화한 개념입니다.

## 5. 핵심 비교 및 연결 개념 (Relation)
접근 제어 모델 진화 트리:
- **RBAC**: 부서/역할별로 문을 열어줌. (정적, 딱딱함).
- **ABAC**: 부서 + 환경(시간/기기) 속성을 보고 문을 열어줌. (동적, 유연함).
- **PBAC**: 이 모든 통제 로직을 각 앱에서 뜯어내, 중앙의 **'정책 엔진'** 에 코드로 몰아넣고 자동 심사함. (클라우드 최적화, Policy-as-Code).

# ✍️ 단답형 / 서술형 시험장 출격 준비

### Ⅰ. 핵심 인사이트
- **본질**: 접근 제어 로직을 애플리케이션 소스코드에서 완전히 분리(Decoupling)하여, 중앙 집중화된 **정책 결정 엔진(Policy Engine)** 이 선언적 코드(Policy-as-Code) 형태의 룰셋을 기반으로 사용자 및 시스템의 접근 권한을 동적으로 인가(Authorization)하는 보안 프레임워크.
- **가치**: 마이크로서비스(MSA) 및 클라우드 인프라에서 수만 개의 API 엔드포인트에 대한 접근 통제를 일관되게(Consistent) 강제할 수 있음. 보안/감사 부서는 앱 소스코드를 까볼 필요 없이, 중앙의 정책 리포지토리(Git)만 리뷰하면 전사 컴플라이언스 준수 여부를 즉시 검증(Audit)할 수 있음.
- **판단 포인트**: PBAC는 ABAC의 상위 집합(Superset) 성격을 띱니다. 단순한 속성(Attribute) 계산을 넘어, "GDPR 규정에 의해 유럽 사용자의 데이터는 미국 서버로 전송 불가"라는 비즈니스/법적 요구사항을 기계가 실행 가능한 코드(Machine-executable Code)로 전환했다는 점이 아키텍처적 패러다임 시프트의 핵심입니다.

### Ⅱ. PBAC 아키텍처의 3대 핵심 컴포넌트 (XACML/OPA 모델)
정책의 작성, 결정, 집행을 철저히 분리하여 유연성을 극대화.
1. **PAP (Policy Administration Point, 정책 관리 지점)**
   - 보안 관리자가 정책을 작성(Authoring), 수정, 배포하는 중앙 관리 저장소. (요즘은 Git 저장소와 CI/CD 파이프라인을 연동하여 GitOps 형태로 관리함).
2. **PDP (Policy Decision Point, 정책 결정 지점)**
   - 가장 핵심적인 **'판사(Judge)'** 역할의 정책 엔진 (예: OPA). 
   - PEP로부터 인가 요청을 받으면, PAP에서 내려받은 정책(Policy)과 외부 속성 데이터(JSON)를 대조하여 "Allow(허용)" 또는 "Deny(거부)" 판결을 도출.
3. **PEP (Policy Enforcement Point, 정책 집행 지점)**
   - **'경찰(Police)'** 역할. 사용자의 요청 길목(API Gateway, Service Mesh의 Envoy 프록시 등)에 위치.
   - 요청을 가로채어 PDP에 질의하고, 그 결과에 따라 트래픽을 통과시키거나 차단(Drop)함. 애플리케이션은 PEP 뒤에 숨어 있어 접근 제어 로직을 알 필요가 없음.

### Ⅲ. Policy-as-Code (PaC) 패러다임과 OPA (Open Policy Agent)
PBAC를 현대 클라우드 네이티브 생태계에 정착시킨 일등 공신.
- **개념**: 보안 정책을 클릭(GUI)으로 설정하는 것이 아니라, S/W 개발처럼 코드(Code)로 작성하여 버전 관리, 테스트, 배포 파이프라인(CI/CD)을 태우는 프랙티스.
- **OPA (Open Policy Agent)**:
  - CNCF(클라우드 네이티브 컴퓨팅 재단) 졸업 프로젝트로, 클라우드 인프라 전반에 걸친 범용 정책 엔진.
  - **Rego(레고)** 라는 논리 쿼리 언어를 사용하여 수십 줄의 코드로 복잡한 ABAC/PBAC 룰을 우아하게 선언함.
  - API Gateway뿐만 아니라 Kubernetes의 Admission Controller(파드 생성 제어), CI/CD 파이프라인 테스팅, Terraform 인프라 배포 등 모든 레이어의 정책 통제를 OPA 하나로 싹 다 통일(Unified)하는 아키텍처 구현 가능.

### Ⅳ. PBAC 도입 시 아키텍처적 고려사항 및 트레이드오프
- **지연 시간(Latency) 이슈**:
  - 수천 개의 마이크로서비스가 통신할 때마다 중앙의 PDP(정책 엔진)를 네트워크로 호출하면 핑(Ping) 지연으로 인해 전체 서비스가 느려지는 병목 발생.
  - $\rightarrow$ **아키텍처 대안 (Sidecar Pattern)**: PDP 엔진을 중앙 서버 1대에 두는 것이 아니라, 가벼운 OPA 컨테이너를 각 애플리케이션 파드(Pod) 안에 **사이드카(Sidecar)** 형태로 바짝 붙여 배포함. 이를 통해 네트워크 홉(Hop) 없이 로컬호스트 통신(0.001초 이내)으로 초고속 정책 평가 수행.

### Ⅴ. 결론 및 실무적 판단 포인트
- 엔터프라이즈 아키텍트는 "개발자가 비즈니스 로직(Java) 코드 안에 `if (user.role == 'admin')` 같은 하드코딩된 권한 로직을 넣는 행위"를 강력히 금지해야 합니다. 인증(AuthN)을 OIDC 등 중앙 IdP로 분리했듯, 인가(AuthZ) 영역 또한 OPA 기반의 PBAC 아키텍처로 외부화(Externalization)해야만 거대한 클라우드 시스템의 제로 트러스트(ZTA) 마이크로 세그멘테이션 통제가 완성됩니다.

### 💡 문제 유형별 목차 전환 포인트
- **[클라우드 네이티브(Cloud-Native) 환경의 최적 접근 제어 아키텍처 및 권한 외부화]**: Ⅰ번과 Ⅱ번 아키텍처(PDP와 PEP의 분리)를 핵심으로 서술. 로직의 하드코딩으로 인한 관리 부채를 지적하고, 중앙 판결 엔진이 제공하는 민첩성(Agility) 논증.
- **[Policy-as-Code의 개념과 OPA(Open Policy Agent) 적용 방안]**: Ⅲ번을 집중 조명하여, 인프라를 코드로 관리(IaC)하는 트렌드에 맞춰 보안 정책 역시 코드로 변환됨으로써 얻는 감사(Audit) 편의성과 Ⅳ번의 사이드카 배포를 통한 성능 극복 방안 서술.
