# 📖 【암기용】 개념 완전 이해

> 목적: 임베디드 시스템 보안 취약점을 처음 봐도 완벽히 이해하게 만든다. 시험 답안 양식이 아니라, 이해를 위한 친절한 설명이다.

## 한눈에
- **개요**: 기기 내부의 계정·포트·펌웨어·메모리 보호 실패로 공격자가 장치를 장악하는 취약 조건
- **왜 필요한가**: 임베디드 장치는 자동차, 의료기기, CCTV, 산업 제어기에 들어가며 한 번 배포되면 5~15년 운용된다. 초기 취약점이 현장 장비 전체의 원격 명령 실행과 서비스 중단으로 이어진다.
- **핵심 직관**: 작은 장치도 운영체제, 네트워크, 업데이트, 디버그 포트를 가진 컴퓨터이며, 공격자는 가장 덜 잠긴 입구부터 찾는다.

## 깊이 이해
- **배경·문제의식**: 임베디드 개발은 원가·전력·납기 제약으로 기본 계정, UART/JTAG, 암호화되지 않은 OTA, ASLR 미적용 펌웨어가 남기 쉽다. 현장 교체 비용이 서버 패치보다 크므로 취약점 수명이 길다.
- **작동 원리**: 공격자는 장치 식별 후 웹 관리 페이지, Telnet/SSH 기본 계정, UART 콘솔, JTAG, OTA 패키지, 플래시 덤프를 순서대로 확인한다. 이후 CWE-798, CWE-119, CWE-306 같은 취약점으로 권한을 획득한다.
- **비유**: 공장 설비에 앞문 잠금은 있지만 정비용 뒷문 비밀번호가 출고값이면, 침입자는 앞문 대신 정비문으로 들어간다.
- **구체 예시**: 하드코딩 계정 `admin/admin`과 열린 UART 115200bps 콘솔이 함께 남으면 5분 내 root shell 획득, NVRAM Wi-Fi 키 추출, 봇넷 악용 가능.
- **흔한 오해·주의점**: 네트워크가 사설망이면 충분하다는 판단은 틀림. 현장 노트북, 유지보수 VPN, 공급망 업데이트 서버가 우회 경로가 된다.

## 연결 개념
- Firmware Security - 이미지 서명, SBOM, OTA 검증과 직접 연결
- Secure Boot - 부팅 시 변조 펌웨어 실행 차단
- IEC 62443 - 산업 제어 장비의 보안 수준과 개발 생명주기 기준

# 📝 【답안용】 시험 답안 템플릿

> 목적: 시험장에서 25분에 그대로 쓰는 답안 양식. 작성방식(추상표현 금지·수치·도식·문제유형 전환)을 엄격히 지킨다.
> 핵심: 취약점 이름 나열이 아니라, 공격면-취약점-통제-검증 지표를 연결해 임베디드 보안 설계 판단을 제시한다.

## 핵심 인사이트 (3줄 요약)

> 1. **본질**: 임베디드 보안 취약점은 제한된 장치 환경에서 계정·디버그 포트·펌웨어·메모리 보호가 누락되어 장치 제어권이 외부로 넘어가는 조건이다.
> 2. **가치**: IEC 62443 SDL, OWASP Embedded, CVE/CWE 기반 점검으로 출고 전 취약점 잔존율과 현장 패치 비용을 줄인다.
> 3. **판단 포인트**: 하드코딩 계정, UART/JTAG, OTA 검증, 메모리 보호, 로그·감사 기능을 장치 수명주기 전체에서 점검해야 한다.

## 출제 의도 및 답안 포인트

| 출제 의도 | 반드시 짚을 핵심 | 감점 회피 포인트 |
|:---|:---|:---|
| 임베디드 공격면 식별 역량 확인 | 네트워크, 물리 포트, 펌웨어, 공급망, 유지보수 채널 | 웹 취약점만 쓰고 UART/JTAG·OTA 누락 |
| 취약점 분류와 표준 연결 확인 | CWE-798, CWE-119, CVE, OWASP Embedded, IEC 62443 | 취약점 명칭만 나열하고 통제 기준 누락 |
| 제품 수명주기 보안 판단 확인 | 설계 SDL, 생산 키 주입, 현장 OTA, 폐기 데이터 삭제 | 개발 단계 점검만 쓰고 운영·폐기 단계 제외 |
> 요약: 이 문제는 장치 공격면별 취약점과 수명주기 통제를 연결하는 답안을 요구한다.

---

## Ⅰ. 개요 및 필요성

임베디드 보안 취약점은 장치 내부의 계정·포트·펌웨어·메모리 통제 실패 조건이다.
IoT·자동차·의료·산업 장비는 현장 배포 후 교체 주기가 5~15년으로 길어 취약점 노출 기간이 서버보다 길다.
CVE/CWE 기반 취약점 관리와 IEC 62443 개발 프로세스가 제품 출시 전부터 적용되어야 한다.

---

## Ⅱ. 구조 및 구성요소

```text
External Actor -> Network Service / Web UI / OTA Channel
External Actor -> UART/JTAG / Flash Dump / Debug Console
Device Asset -> Credential / Firmware / Key / Sensor Data
Control -> Secure Config / Memory Protection / Audit Log
```

| 구성요소 | 역할 | 특이사항 |
|:---|:---|:---|
| 하드코딩 계정 | 출고·유지보수 접근 경로 | CWE-798, 기본 비밀번호 대량 악용 |
| 디버그 인터페이스 | UART/JTAG/SWD로 콘솔·메모리 접근 | 생산 후 fuse disable 또는 인증 필요 |
| OTA 채널 | 펌웨어 업데이트 배포 | 서명 검증, 버전 검증, TLS 1.3 필요 |
| 메모리 보호 | 코드 실행·권한 상승 차단 | MPU/MMU, NX, ASLR, stack canary |
> 요약: 임베디드 취약점은 네트워크 서비스보다 물리·펌웨어·유지보수 경로까지 포함한 장치 전체 공격면으로 봐야 한다.

---

## Ⅲ. 동작원리 및 흐름도

```text
장치 식별 -> 서비스 스캔 -> 기본 계정 시도
장치 식별 -> UART/JTAG 연결 -> 콘솔 또는 플래시 덤프
펌웨어 획득 -> binwalk 분석 -> 비밀값 추출 -> 취약점 악용
침해 후 -> C2 등록 / 데이터 탈취 / OTA 변조
```

| 단계 | 처리 내용 | 검증 기준 |
|:---:|:---|:---|
| 1 | 장치 모델, 펌웨어 버전, 열린 포트 식별 | Nmap, banner, CVE 매핑 |
| 2 | 기본 계정·인증 우회 확인 | CWE-798, CWE-306 0건 |
| 3 | UART/JTAG, 플래시 덤프, 펌웨어 unpack 분석 | 디버그 잠금, secret 0건 |
| 4 | OTA 서명·rollback·TLS 검증 | 서명 실패 이미지 부팅 0회 |
| 5 | 침해 지표 수집과 로그 검토 | auth fail, boot fail 감사로그 보존 180일 |
> 요약: 공격 흐름은 식별-접근-분석-악용-지속화 순서이며, 각 단계에 계정·포트·펌웨어·로그 통제가 대응된다.

## Ⅳ. 특징

| 구분 | 일반 서버 취약점 | 임베디드 취약점 | 판단 포인트 |
|:---|:---|:---|:---|
| 배포 환경 | 데이터센터·클라우드 | 현장 장비·폐쇄망·차량·공장 | 물리 접근과 유지보수 채널 포함 |
| 패치 주기 | 주 단위 패치 가능 | 인증·현장 방문으로 월~년 단위 | OTA 실패율 0.1% 이하 목표 |
| 공격면 | OS·웹·API 중심 | UART/JTAG, 펌웨어, 센서, 버스 포함 | OWASP Embedded 10개 영역 점검 |

> 요약: 임베디드 취약점은 긴 수명과 물리 공격면 때문에 출고 전 보안 설계와 OTA 복구 설계가 함께 필요하다.

## Ⅴ. 심화 비교 및 적용 판단

| 비교 축 | 기존/대안 | 본 키워드 | 선택 기준 |
|:---|:---|:---|:---|
| 점검 방식 | 기능 테스트 중심 | CVE/CWE, SBOM, fuzzing, HW 포트 점검 | 출시 전 critical CVE 0건 |
| 통제 위치 | 서버 게이트웨이 | 장치 내부 secure config와 secure boot | 오프라인 운용 장비는 장치 통제 우선 |
| 운영 방식 | 수동 펌웨어 교체 | 서명 OTA, staged rollout, rollback | 1%, 10%, 100% 단계 배포 |
> 요약: 네트워크 격리만으로는 부족하며, 장치 내부 통제와 업데이트 검증을 선택 기준에 포함해야 한다.

| 리스크 | 원인 | 대응 방안 | 확인 지표 |
|:---|:---|:---|:---|
| 기본 계정 악용 | 출고 계정·비밀번호 재사용 | 최초 부팅 강제 변경, per-device secret | 동일 credential 0건 |
| 디버그 포트 침해 | UART/JTAG 생산 후 미차단 | fuse lock, 인증 디버그, epoxy | debug access pass rate 0% |
| OTA 변조 | 서명·버전 검증 누락 | Ed25519/ECDSA 서명, rollback counter | unsigned image boot 0회 |
> 요약: 주요 리스크는 계정·디버그·OTA이며, 생산 검사와 현장 업데이트 지표로 통제해야 한다.

| 점검 항목 | 목표 기준 | 측정 방법 |
|:---|:---|:---|
| 취약점 | Critical/High CVE 0건 | SBOM, SCA, CVE scan |
| 메모리 보호 | NX, stack canary, ASLR 적용률 100% | compiler flag, ELF hardening check |
| 디버그 통제 | 양산품 UART/JTAG 인증 없이는 접근 0회 | board test, boundary scan |
| 운영 감사 | 보안 이벤트 보존 180일 이상 | syslog, secure storage, SIEM 연계 |
> 요약: 성공 여부는 CVE 잔존, hardening flag, 디버그 차단, 감사로그 보존 기간으로 판단한다.

## Ⅵ. 실무 적용 및 결론

**적용 방안 3개 (필수 - 단계별 또는 항목별):**
1. 개발 단계: threat modeling, OWASP Embedded checklist, AFL++ fuzzing, CWE-798 secret scan을 CI에 연결함
2. 생산 단계: per-device key 주입, UART/JTAG fuse lock, secure boot key hash를 ROM 또는 OTP에 저장함
3. 운영 단계: signed OTA, phased rollout 1%/10%/100%, 실패 시 A/B partition rollback과 CVE 모니터링 수행함

**결론 (2줄):**
- 기술사 판단: 현장 장비 수명 5년 이상이면 네트워크 격리보다 secure boot, signed OTA, debug lock을 기본 통제로 선택함
- 향후 방향: IEC 62443 SDL과 SBOM 기반 취약점 추적으로 제조사 책임과 현장 복구 시간을 함께 관리함
