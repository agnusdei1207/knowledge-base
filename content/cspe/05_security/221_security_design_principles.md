# 📖 【암기용】 개념 완전 이해

> 목적: 보안 설계 원칙을 처음 봐도 완벽히 이해하게 만든다. 시험 답안 양식이 아니라, 이해를 위한 친절한 설명이다.

## 한눈에
- **개요**: 시스템을 만들 때 침해 가능성을 낮추도록 기본 구조에 심는 설계 규칙
- **왜 필요한가**: 보안은 운영 단계에서 장비를 붙이는 방식만으로는 누락 지점이 생긴다. 설계 단계에서 권한, 기본값, 검증, 사용성까지 통제해야 변경 비용을 낮출 수 있다.
- **핵심 직관**: 집을 지은 뒤 자물쇠를 다는 것이 아니라, 출입구 수·잠금 방향·비상 차단 방식을 도면에 먼저 반영하는 접근이다.

## 깊이 이해
- **배경·문제의식**: 취약점은 암호 알고리즘보다 과도한 권한, 예외 허용 기본값, 검증 생략, 복잡한 코드 경로에서 자주 발생한다. 보안 설계 원칙은 이런 반복 결함을 설계 언어로 줄이는 방법이다.
- **작동 원리**: 접근은 기본 거부(fail-safe defaults)로 두고, 업무에 필요한 최소 권한만 부여하며, 모든 객체 접근을 매번 확인한다. 내부 설계를 숨기는 방식보다 공개 검증(open design)을 택하고, 공용 메커니즘을 줄여 침해 전파 범위를 제한한다.
- **비유**: 병원 약품 보관함에서 모든 직원에게 마스터키를 주지 않고, 처방 역할·근무 시간·약품 종류별로 접근을 분리하는 것과 같다.
- **구체 예시**: 관리자 API는 RBAC에서 `admin:write` 권한을 별도 분리하고, 기본 계정 비활성화, mTLS, 감사로그 1년 보관, 세션 15분 만료를 설계 기준으로 둔다.
- **흔한 오해·주의점**: 보안 설계 원칙은 체크리스트 암기가 아니다. 인증 장비 도입보다 어떤 기본값과 권한 경계가 침해 범위를 줄이는지 설명해야 한다.

## 연결 개념
- Zero Trust Architecture — 기본 불신과 지속 검증을 네트워크·ID·단말로 확장
- Secure SDLC — 설계 원칙을 요구사항, 위협 모델링, 코드 리뷰, 배포 게이트에 반영
- Privacy by Design — 최소 수집, 목적 제한, 보관 기간 통제로 개인정보 노출면 축소

# 📝 【답안용】 시험 답안 템플릿

> 목적: 시험장에서 25분에 그대로 쓰는 답안 양식. 작성방식(추상표현 금지·수치·도식·문제유형 전환)을 엄격히 지킨다.
> 핵심: 원칙 명칭 나열이 아니라, 설계 결함이 침해로 이어지는 경로와 원칙별 통제 지점을 연결해 답안을 구성한다.

## 핵심 인사이트 (3줄 요약)

> 1. **본질**: 보안 설계 원칙은 기본 거부, 최소 권한, 완전 중재, 단순 구조, 공개 검증을 통해 침해 가능성과 피해 범위를 줄이는 설계 기준이다.
> 2. **가치**: 운영 단계 보안 장비 의존을 줄이고, 요구사항 단계부터 RBAC, mTLS, 감사로그, 암호화, 기본값 통제를 내장한다.
> 3. **판단 포인트**: fail-safe defaults와 secure by default는 기본 상태를 거부로 두고, least privilege와 complete mediation은 접근 경로마다 권한을 검증한다.

## 출제 의도 및 답안 포인트

| 출제 의도 | 반드시 짚을 핵심 | 감점 회피 포인트 |
|:---|:---|:---|
| 보안 내재화 설계 역량 확인 | fail-safe defaults, least privilege, complete mediation, open design | 원칙 명칭만 쓰고 적용 지점을 빠뜨림 |
| 침해 범위 축소 판단 확인 | 최소 노출, least common mechanism, secure by default, 감사로그 | 방화벽·백신 등 운영 도구 나열로 흐름 이탈 |
| 사용성과 통제 균형 확인 | psychological acceptability, MFA UX, 권한 요청 승인 흐름 | 사용성을 이유로 기본 허용을 정당화 |

> 요약: 이 문제는 보안 원칙을 시스템 설계 의사결정과 권한·기본값·검증·감사 지표로 연결하는 능력을 묻는다.

---

## Ⅰ. 개요 및 필요성

- 개요: 침해 경로를 줄이는 설계 기준
- 배경: 인증·암호화 기능을 뒤늦게 추가해도 기본 허용, 과도 권한, 미검증 접근, 오류 시 우회 같은 설계 결함은 남음
- 필요성: fail-safe defaults, least privilege, complete mediation을 요구사항 단계에 반영하고 관리자 권한 30일 재승인, 외부 공개 관리 포트 0개 기준으로 검증해야 함

---

## Ⅱ. 구조 및 구성요소

```text
요구사항 -> 위협 모델 -> 설계 원칙 매핑 -> 통제 구현 -> 검증/감사
              / 권한
              / 기본값
              / 노출면
```

| 구성요소 | 역할 | 특이사항 |
|:---|:---|:---|
| Fail-safe defaults | 권한 미부여 상태는 접근 거부 | 기본 계정 잠금, allowlist |
| Least privilege | 업무 수행 최소 권한만 부여 | RBAC/ABAC, JIT 권한 |
| Complete mediation | 모든 접근마다 권한 재검증 | 캐시된 권한 TTL 5분 이하 |
| Economy of mechanism | 설계·코드 경로 단순화 | 인증 모듈 단일화 |
| Open design | 비밀 설계 의존 제거 | 표준 알고리즘, 공개 검증 |
| Psychological acceptability | 사용자가 통제를 우회하지 않도록 UX 설계 | MFA 푸시 제한, 오류 메시지 표준화 |

> 요약: 보안 설계 원칙은 기본 거부, 최소 권한, 매 접근 검증, 단순 구조, 공개 검증, 사용자 수용성으로 구성된다.

---

## Ⅲ. 동작원리 및 흐름도

```text
자산 식별 -> 위협 시나리오 작성 -> 원칙 선택 -> 설계 통제 반영
-> 보안 테스트 -> 감사로그/지표 확인 -> 예외 권한 회수
```

| 단계 | 처리 내용 | 검증 기준 |
|:---:|:---|:---|
| 1 | 데이터·API·계정·관리 포트 자산 식별 | 자산 목록 100% 소유자 지정 |
| 2 | STRIDE 기반 위협 시나리오 작성 | 인증 우회, 권한 상승, 정보 노출 포함 |
| 3 | 원칙별 통제 설계 | RBAC, mTLS, 암호화, 기본 거부 매핑 |
| 4 | 구현·검증 | SAST/DAST, 권한 테스트, 감사로그 샘플링 |
| 5 | 운영 피드백 | 예외 권한 30일 단위 재승인 |

> 요약: 보안 설계는 자산과 위협을 먼저 고정한 뒤 원칙을 통제 항목으로 바꾸고, 테스트와 감사 지표로 확인한다.

---

## Ⅳ. 특징

| 구분 | 기존 사후 보안 | 보안 설계 원칙 | 수치·판단 포인트 |
|:---|:---|:---|:---|
| 적용 시점 | 구축 후 장비·정책 추가 | 요구사항·아키텍처 단계 반영 | 설계 리뷰 1회 이상, 배포 전 보안 게이트 |
| 접근통제 | 기본 허용 후 차단 | 기본 거부 후 명시 허용 | RBAC 권한 90일 재검토 |
| 검증 방식 | 경계 방어 중심 | 모든 객체 접근 완전 중재 | 권한 캐시 TTL, 감사로그 누락률 0% |
| 실패 처리 | 예외 상황에서 우회 허용 | 오류 시 차단·로그 기록 | fail-close, 오류 로그 1년 보관 |

> 요약: 보안 설계 원칙은 운영 장비 추가보다 기본값·권한·검증 경계를 먼저 고정하여 침해 경로를 줄인다.

## Ⅴ. 심화 비교 및 적용 판단

| 비교 축 | 기존/대안 | 본 키워드 | 선택 기준 |
|:---|:---|:---|:---|
| 구조 | perimeter security 중심 | secure by default + Zero Trust 연계 | 외부·내부 구분이 모호한 SaaS/API 환경 |
| 비용/성능 | 사후 진단·패치 반복 | 설계 리뷰·자동 보안 테스트 | 결함 수정 비용 요구사항 1배, 운영 단계 30배 |
| 운영/위험 | 예외 권한 누적 | JIT 권한, 30일 재승인 | 관리자 계정 5개 이상 시스템 |

> 요약: 기본 허용 구조와 예외 권한이 누적되는 환경에서는 설계 단계 통제가 사후 패치보다 결함 수정 비용을 낮춘다.

| 리스크 | 원인 | 대응 방안 | 확인 지표 |
|:---|:---|:---|:---|
| 과도 권한 | 역할 설계 없이 계정 복제 | RBAC/ABAC, JIT 권한 | 권한 사용률 80% 미만 계정 회수 |
| 기본값 노출 | 샘플 계정·디버그 포트 유지 | secure baseline, CIS Benchmark | 공개 포트 0건, 기본 계정 0건 |
| 우회 사용 | MFA 피로, 복잡한 승인 | 단계별 인증, UX 테스트 | MFA 거절률, 헬프데스크 티켓 |

> 요약: 주요 리스크는 권한 누적, 기본값 노출, 사용자 우회이며 권한 사용률·공개 포트·MFA 지표로 통제한다.

| 점검 항목 | 목표 기준 | 측정 방법 |
|:---|:---|:---|
| 권한 통제 | 관리자 권한 30일 재승인, JIT 4시간 만료 | IAM 리포트, 접근권한 검토 |
| 노출면 관리 | 외부 공개 관리 포트 0개, TLS 1.3 적용 | CSPM, 포트 스캔, 설정 점검 |
| 감사·검증 | 인증·인가 이벤트 100% 로깅 | SIEM, 로그 샘플링, DAST |

> 요약: 도입 성과는 권한 재승인, 공개 포트, 인증·인가 로그 누락률 같은 검증 가능한 지표로 판단한다.

## Ⅵ. 실무 적용 및 결론

**적용 방안 3개 (필수 — 단계별 또는 항목별):**
1. 설계 단계: STRIDE 위협 모델링과 원칙 매핑표를 작성하고, fail-close 오류 처리와 기본 거부 정책을 아키텍처 결정 기록에 반영
2. 구현 단계: RBAC/ABAC, mTLS, secrets vault, TLS 1.3, 감사로그 스키마를 공통 플랫폼으로 제공
3. 운영 단계: CIS Benchmark, SAST/DAST, IAM 권한 검토를 CI/CD 게이트에 연결하고 예외 권한은 30일 재승인

**결론 (2줄):**
- 기술사 판단: 인터넷 노출·개인정보·관리자 권한이 있는 시스템은 secure by default와 least privilege를 기본 설계 기준으로 채택함
- 향후 방향: Zero Trust, SBOM, 정책 코드화(OPA/Rego)로 설계 원칙을 배포 파이프라인에서 자동 검증함
