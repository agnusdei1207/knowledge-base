## 1. 한눈에 이해하기 (Core Intuition)
- **정의**: 개발자가 코드를 작성하여 병합(Merge)하기 전(PR 단계), 소스코드에 존재하는 보안 취약점, 비즈니스 로직 결함, 시큐어 코딩 원칙 위반 사항을 식별하고 수정하도록 강제하는 예방적 통제 활동입니다.
- **필요성**: 자동화된 스캐닝 도구(SAST)는 "코드의 문법적 결함(SQLi, XSS)"은 잘 찾지만, "결제 금액을 클라이언트에서 조작할 수 있는지", "A 사용자가 B 사용자의 게시글을 삭제할 수 있는지(권한 우회)"와 같은 **'비즈니스 로직과 컨텍스트의 결함'**은 절대 찾지 못합니다. 이는 반드시 인간(보안 전문가/시니어 개발자)의 눈으로 리뷰해야 합니다.
- **핵심 직관**: **"자동 번역기(SAST)와 전문 통역사(수동 리뷰)의 결합"**
  - 맞춤법 검사나 뻔한 문법 오류는 자동 번역기가 1초 만에 잡아냅니다.
  - 하지만 "이 문장이 현지 문화(비즈니스 로직)에 맞는지, 무례한 표현(권한 우회)은 없는지"는 인간 통역사가 문맥(Context)을 읽고 판단해야 합니다.

## 2. 깊이 이해하기 (In-Depth Comprehension)
- **배경**: 애자일 배포 환경에서 보안 검사를 사후(모의해킹)에 하면 수정 비용이 너무 큽니다. 가장 저렴한 방어는 "코드가 메인 브랜치에 합쳐지기 전(Pull Request)"에 막는 것입니다.
- **작동 원리 (자동화 + 수동 검토)**:
  - **1차 (기계)**: 개발자가 코드를 올리면 CI가 SAST, Secret Scan(하드코딩된 비밀번호 탐지), SCA(취약한 라이브러리 탐지)를 돌려 명백한 패턴 결함을 걸러냅니다.
  - **2차 (인간)**: 기계를 통과한 코드 중 '고위험 모듈(인증, 결제, 파일 업로드)'에 한해, 보안 리뷰어가 **OWASP ASVS**나 사내 시큐어 코딩 가이드라인을 체크리스트 삼아 데이터 흐름(Data Flow)과 권한 검증 로직을 추적합니다.
- **비유**: 공항 검색대에서 1차로 엑스레이(SAST)를 통과시키고, 엑스레이가 잡지 못하는 마약이나 수상한 목적의 여행객은 요원이 직접 심층 인터뷰(수동 리뷰)를 하는 것과 같습니다.
- **흔한 오해/주의점**: "모든 코드를 사람이 다 봐야 하나요?" $\rightarrow$ 절대 불가능하며 개발 속도를 완전히 마비시킵니다. 일반적인 CRUD(게시판 읽기/쓰기) 코드는 자동 도구에 맡기고, 인간의 리뷰 역량은 **"인증, 인가, 결제, 암호화 로직"**에 100% 집중(선택과 집중)해야 합니다.

## 3. 연결 개념 (Related Concepts)
- **OWASP ASVS (Application Security Verification Standard)**: 앱 보안 요구사항 검증 표준. "비밀번호는 최소 8자리인가?", "세션 타임아웃이 있는가?" 등 수동 리뷰 시 바이블이 되는 체크리스트.
- **SAST (Static Application Security Testing)**: 보안 코드 리뷰의 1차 관문 역할을 하는 자동화 도구.
- **시큐어 코딩 (Secure Coding)**: 시큐어 코딩이 '어떻게 안전하게 짤 것인가(Rule)'라면, 보안 코드 리뷰는 '그 룰을 제대로 지켰는지 검사하는 프로세스(Process)'입니다.

# ✍️ 답안용 골격 (Exam Preparation)

### Ⅰ. 핵심 인사이트
- **본질**: 배포 전 소스코드의 변경분(Diff)을 대상으로, 자동화된 정적 분석 도구(SAST)가 포착하지 못하는 **인증/인가 우회, 비즈니스 로직 결함, 데이터 흐름 취약점**을 OWASP ASVS 등 검증 표준을 기반으로 식별하는 예방적 통제(Preventive Control) 활동.
- **가치**: "결함 수정 비용(Rework Cost)의 획기적 절감과 로직 결함 방어". 출시 후 침투테스트(DAST/Pen-test)에서 발견된 취약점을 수정하는 비용 대비, 코드 리뷰 단계에서 논리적 결함을 차단하는 것이 비용/시간 측면에서 압도적으로 효율적입니다.
- **판단 포인트**: 보안 코드 리뷰의 성패는 "개발자 피로도(Friction)와 리뷰 병목의 해결"에 있습니다. 전체 코드를 리뷰하려는 과욕을 버리고, 위험도 기반(Risk-based)으로 '인증/결제/외부 API' 등 고위험 모듈(Crown Jewel)만 수동 리뷰로 딥 다이브(Deep-dive)하는 **선택적 리뷰 거버넌스**와 **보안 챔피언(Security Champion)** 제도의 운영이 필수적입니다.

### Ⅱ. 보안 코드 리뷰 아키텍처 (기계와 인간의 분업 체계)
```text
┌─────────────────────────────────────────────────────────────┐
│                 [ GitHub / GitLab Pull Request ]            │
├────────────────────────────┬────────────────────────────────┤
│ 1차: Automated Gate (기계)  │ 2차: Manual Review (인간)       │
├────────────────────────────┼────────────────────────────────┤
│ - SAST (SQLi, XSS 패턴)     │ - 비즈니스 로직 무결성 검토       │
│ - Secret Scan (API 키 노출)  │ - 인증(AuthN) / 인가(AuthZ) 맹점│
│ - SCA (취약 라이브러리 탐지) │ - 암호화 알고리즘 구현 적절성     │
│ 👉 기계적 차단 (Hard Block) │ 👉 OWASP ASVS 기반 체크리스트    │
└────────────────────────────┴────────────────────────────────┘
```

### Ⅲ. 수동 리뷰의 4대 핵심 검토 영역 (자동화 도구의 블라인드 스팟)
1. **인증 및 인가 (Authentication & Authorization)**:
   - "IDOR(안전하지 않은 직접 객체 참조) 방어 여부": A 사용자가 파라미터(`id=2`)를 변조해 B 사용자의 데이터를 볼 수 있는가?
   - "수직적/수평적 권한 상승 통제": 일반 유저가 `/admin` API를 호출할 때 서버 단에서 2차 권한 검증을 수행하는가?
2. **비즈니스 로직 및 상태(State) 무결성**:
   - 쇼핑몰 장바구니에서 수량을 음수(-1)로 변조하여 총 결제 금액을 마이너스로 만들 수 있는가?
3. **입출력 데이터 유효성 검증 (Data Validation)**:
   - 클라이언트(프론트엔드) 검증에만 의존하지 않고, 서버(백엔드) 단에서 정규표현식/화이트리스트 기반 검증을 수행하는가?
4. **민감 데이터 보호 (Data Protection)**:
   - 로깅할 때 주민번호, 비밀번호, 카드번호 등 PII(개인식별정보)가 평문으로 로그 파일에 남지 않도록 마스킹(Masking) 처리했는가?

### Ⅳ. 기존 코드 리뷰와의 차이별 비교
| 비교 지표 | 일반 코드 리뷰 (Peer Review) | **보안 코드 리뷰 (Security Review)** |
|---|---|---|
| **검토 목적** | 가독성, 클린 코드, 유지보수성 | **취약점 제거, 권한 우회 차단, 보안 컴플라이언스 준수** |
| **기준 체계** | 사내 코딩 컨벤션, 디자인 패턴 | **OWASP ASVS, CWE, CERT 시큐어 코딩 표준** |
| **선별 대상** | 모든 커밋(Commit) 대상 균등 배분 | **고위험 모듈(인증/결제) 우선의 위험 기반(Risk-based) 접근** |
| **조치 결과** | 리팩토링 코멘트 및 병합 승인 | **CVSS 스코어링, 취약점 조치 후 재검증(Re-review) 필수** |

### Ⅴ. 결론 및 실무적 판단 포인트
- CISO는 코드 리뷰 프로세스를 설계할 때, 보안팀이 모든 리뷰의 최종 승인자(Bottleneck)가 되는 구조를 절대적으로 피해야 합니다. 이는 개발 부서와의 영원한 마찰을 낳습니다.
- 해법은 개발팀 내부에 보안 교육을 이수한 **'보안 챔피언(Security Champion)'**을 육성하여 권한을 위임하는 것입니다. 일상적인 로직의 보안 검토는 보안 챔피언이 수행하고, 보안팀은 '결제 코어 엔진'이나 '암호화 모듈' 같은 크리티컬 패스(Critical Path)에만 개입하는 RACI 매트릭스 설계가 성숙한 DevSecOps를 완성합니다.

### 💡 문제 유형별 목차 전환 포인트
- **[DevSecOps 환경에서의 애플리케이션 보안 내재화 방안]**: Ⅰ과 Ⅱ(기계-인간 분업)를 전면에 세워, 배포 전 단계(Shift-Left)에서 자동화 도구와 수동 리뷰를 파이프라인(PR Gate)에 어떻게 조화롭게 통합할 것인지 아키텍처 논리 증명.
- **[비즈니스 로직 취약점(Business Logic Flaws) 방어 및 시큐어 코딩 검증 거버넌스 수립]**: Ⅲ(4대 핵심 영역)을 뼈대로 삼고 Ⅳ(일반 리뷰와의 차이점)를 엮어, "SAST/DAST가 잡아내지 못하는 인가(AuthZ) 우회 및 로직 결함을 인간의 컨텍스트(Context) 인지 능력과 OWASP ASVS 표준을 통해 어떻게 근본적으로 솎아낼 것인가"에 대한 심화 엔지니어링 해법 전개.
