## 1. 한눈에 이해하기 (Core Intuition)
- **정의**: 쿠버네티스(Kubernetes)라는 거대한 컨테이너 조종 센터에서, 개발자가 컨테이너(앱)를 띄워달라고 요청할 때마다 **"이게 우리 회사 보안 규칙에 맞는지"를 깐깐하게 검사해서 통과(Allow)시키거나 거절(Deny)하는 클라우드 네이티브 깐깐한 수문장(Gatekeeper) 소프트웨어**입니다.
- **필요성**: 개발자가 실수로 외부 해커가 접속할 수 있는 '슈퍼 마스터 권한(특권 모드)'을 가진 컨테이너를 실행해달라고 쿠버네티스에 요청(YAML 파일 제출)했습니다. 쿠버네티스는 본래 매우 친절해서 개발자가 하라는 대로 다 실행해 주다 보니 클러스터 전체가 털리게 됩니다. "이 컨테이너는 권한이 너무 세서 안 돼!", "이 이미지는 공식 보관소에서 가져온 게 아니니 안 돼!"라고 중간에서 서류 심사를 하고 쳐낼 자동화된 정책 검사관이 필요해졌습니다.
- **핵심 직관**: **"공항 출입국 관리소의 깐깐한 여권 심사대"**. 
  - 과거: 비행기(컨테이너 이미지)가 공항(클러스터)에 도착하면 입국 심사 없이 승객(앱)들이 막 돌아다닙니다.
  - **OPA Gatekeeper**: 승객이 공항(쿠버네티스) 안으로 발을 들이기 직전(Admission Control), 여권 심사관(Gatekeeper)이 앞을 턱 막아섭니다. "여권(YAML 설정 파일) 봅시다. 어라? 신원 불명 보관소에서 출발했네? 게다가 체류 권한(특권 모드)이 너무 크잖아? 너 입국 거절(Deny)! 돌아가!" 하고 컨테이너 생성 자체를 원천 봉쇄합니다.

## 2. 왜 중요한가? (Background & Value)
- **등장 배경**: 과거에는 쿠버네티스 보안을 위해 Pod Security Policy(PSP)라는 내장 기능을 썼는데, 너무 불편하고 복잡해서 CNCF(클라우드 재단)가 아예 PSP 기능을 삭제해버렸습니다. 그 빈자리를 완벽하게 대체하며 "쿠버네티스 정책 통제의 글로벌 표준"으로 왕좌에 오른 것이 바로 OPA(Open Policy Agent) 기술을 쿠버네티스 전용으로 만든 Gatekeeper입니다.
- **가치**: "보안 정책의 코드화(Policy-as-Code)". 엑셀 파일이나 한글 문서에 "위험한 컨테이너 띄우지 마세요"라고 적어두는 멍청한 짓을 끝냅니다. 회사의 보안 규정을 코드로 짠 뒤 쿠버네티스에 박아 넣으면, 수백 명의 개발자가 하루에 1만 번을 배포하더라도 사람이 개입할 필요 없이 100% 자동화된 철벽 방어가 이뤄집니다.

## 3. 어떻게 작동하는가? (Mechanism)
핵심은 쿠버네티스의 결재 라인(Admission Controller) 중간에 OPA가 딱 끼어들어 가로채는 것입니다.

1. **개발자의 배포 요청 (API Request)**
   - 개발자가 "도커 컨테이너 1대 띄워줘!"라며 `kubectl apply -f app.yaml` 명령을 칩니다.
2. **웹훅 낚아채기 (Validating Admission Webhook)**
   - 쿠버네티스 마스터가 이 요청을 바로 실행하지 않고, Gatekeeper에게 "야, 이 서류(YAML) 결재해도 되는 거냐?" 하고 토스해 버립니다.
3. **OPA 엔진의 정책 평가 (Rego 언어 기반)**
   - Gatekeeper의 뇌(OPA) 안에는 보안팀이 미리 짜둔 규칙들(Rego 언어로 작성됨)이 들어 있습니다.
   - 정책 1: "이미지는 반드시 우리 회사 공식 레지스트리(`myregistry.com/*`)에서만 가져올 것."
   - 정책 2: "특권(Privileged=true) 권한을 요구하면 절대 안 됨."
4. **허가 또는 거절 (Allow / Deny)**
   - 개발자의 서류를 규칙과 대조해 본 결과 통과면 쿠버네티스에게 "결재 진행시켜!" (Allow).
   - 정책 위반 시 "결재 반려! 사유: 사설 레지스트리 이미지 사용 불가!"라는 에러 메시지를 개발자의 터미널 화면에 뱉어내고 튕겨냅니다 (Deny).

## 4. 실전 활용 및 예시 (Real-world Application)
- **구체적 사례**: 
  - 클라우드 네이티브 보안 4C 중 **Cluster 방어**의 핵심입니다. 
  - 개발자가 이미지 스캔(Trivy) 단계에서 자꾸 에러가 나자 귀찮아서 스캔 우회 꼼수를 씁니다. 하지만 마지막 관문인 쿠버네티스 배포 단계에서 OPA Gatekeeper가 떡하니 버티고 있습니다. OPA Gatekeeper는 "어라? 이 이미지(Container)는 어제 엑스레이 스캔을 무사히 통과했다는 서명(Signature)이 없네? 너 꼼수 썼지? 쿠버네티스 진입 금지!" 하고 막아내어, 완벽한 CI/CD 보안 파이프라인의 종착역 역할을 해냅니다.
- **주의점 및 흔한 오해**: 
  - "OPA가 백신인가요?" $\rightarrow$ 아닙니다. 바이러스를 잡거나 런타임 악성 행위를 감시하는 게 아닙니다. 오직 **"설정 파일(YAML)에 적힌 조건(인텐트)이 회사의 룰에 맞는가?"** 만 논리적으로 따지는 **JSON 데이터 평가 수학 엔진(거름망)** 일 뿐입니다. (바이러스는 Falco나 CWPP가 잡습니다).

## 5. 핵심 비교 및 연결 개념 (Relation)
- **RBAC (역할 기반 제어)**: "너(개발자 A)는 DB 삭제를 할 **자격(Identity)** 이 있어?" $\rightarrow$ **사람의 신분**을 검사함.
- **OPA Gatekeeper**: "네가 띄워달라고 가져온 이 컨테이너 **설정(Config)** 이 안전해?" $\rightarrow$ **배포 요청의 내용물(행위와 설정)** 을 검사함.
- 두 가지가 합쳐져야 쿠버네티스의 완벽한 접근 제어가 완성됩니다.

# ✍️ 단답형 / 서술형 시험장 출격 준비

### Ⅰ. 핵심 인사이트
- **본질**: 클라우드 네이티브 컴퓨팅 파운데이션(CNCF)의 졸업(Graduated) 프로젝트인 OPA(Open Policy Agent) 엔진을 쿠버네티스의 **동적 어드미션 컨트롤러(Validating Admission Webhook)에 통합하여, 선언적(Declarative) 보안 정책을 컨테이너 배포 시점에 강제 집행(Enforcement)하는 클러스터 제어 아키텍처.**
- **가치**: 기존 K8s 내장 보안 기능이었던 PSP(Pod Security Policy)의 Deprecation(폐기)에 따른 공백을 완벽히 메우며, 데브섹옵스 파이프라인에서 휴먼 에러(개발자의 설정 실수, 과다 특권 컨테이너 배포 등)가 런타임(운영) 환경으로 유입되는 것을 원천 차단(Block)하는 파이프라인의 최종 문지기(Gatekeeper) 역할을 수행.
- **판단 포인트**: OPA의 가장 위대한 아키텍처적 사상은 **"정책(Policy)과 애플리케이션 로직의 완전한 분리(Decoupling)"** 입니다. 개발자는 비즈니스 로직(App)만 짜고, 보안팀은 룰(Rego 언어)만 짜면, OPA라는 독립된 평가 엔진이 중간에서 JSON 데이터를 인풋 받아 Allow/Deny를 판결하는 우아한 데이터 평가 엔진 구조를 갖습니다.

### Ⅱ. 쿠버네티스 어드미션 컨트롤러(Admission Controller) 작동 구조
API 서버 요청 처리의 3단계 흐름 속 Gatekeeper의 개입 위치.
1. **Authentication / Authorization (인증 및 인가)**
   - 클라이언트(kubectl)의 요청 $\rightarrow$ 1차 인증(TLS/토큰) 통과 $\rightarrow$ 2차 인가(RBAC: 해당 네임스페이스에 파드 생성 권한이 있는가?) 통과.
2. **Mutating Admission (변형 어드미션)**
   - API 요청 내용을 강제로 변경(예: 사이드카 프록시 자동 삽입).
3. **Validating Admission (검증 어드미션) ★ OPA Gatekeeper의 위치**
   - API 요청이 etcd(데이터 저장소)에 기록되기 직전, 마지막으로 **요청의 내용물(YAML 스펙)** 을 검사.
   - OPA Gatekeeper 웹훅이 API 서버로부터 요청 객체(JSON)를 가로채어 정책 평가 후 `AdmissionReview` (허가 또는 거부) 응답을 API 서버로 반환. 거부 시 파드(Pod) 생성이 원천 무산됨.

### Ⅲ. OPA Gatekeeper의 3대 핵심 아키텍처 컴포넌트
Rego라는 특수 언어와 CRD(사용자 정의 리소스)를 활용한 확장형 구조.
1. **Rego 언어 (정책 정의 언어)**
   - OPA 엔진이 해석하는 특수한 Policy-as-Code 언어. 복잡한 중첩 JSON 데이터를 순회(Iteration)하며 위반 조건(Violation)을 찾아내는데 극도로 최적화됨.
2. **ConstraintTemplate (제약 조건 템플릿)**
   - "모든 컨테이너는 특정 라벨(Label)을 가져야 한다"라는 핵심 **로직(Rego 코드)** 을 담아두는 붕어빵 틀. 
   - 재사용성을 극대화하기 위해 매개변수(Parameter)를 받을 수 있도록 설계됨.
3. **Constraint (제약 조건 인스턴스)**
   - 템플릿(틀)에 실제 값(앙꼬)을 채워 넣은 실행 규칙.
   - 예: "아까 그 템플릿을 써서, `production` 네임스페이스에는 반드시 `billing-team`이라는 라벨을 강제하라"고 구체적인 룰을 쿠버네티스 클러스터에 배포함.

### Ⅳ. OPA Gatekeeper가 방어하는 4대 필수 킬러 정책 (Best Practices)
엔터프라이즈 환경에서 무조건 강제해야 하는 보안 룰.
1. **특권 컨테이너 차단 (Prevent Privileged Containers)**
   - `securityContext.privileged: true` 설정을 금지하여, 해커가 컨테이너에서 이스케이프(Escape)하여 호스트 노드를 장악하는 것을 방어.
2. **사설 레지스트리 강제 (Trusted Image Registry)**
   - `image` 속성이 퍼블릭 도커 허브(docker.io) 등 검증되지 않은 외부 출처인 경우 차단. 사내 ECR/Harbor 이미지 풀링만 허용. (공급망 공격 방어).
3. **루트 사용자 실행 금지 (Require Non-Root User)**
   - 컨테이너 내부의 프로세스가 관리자 권한(`runAsUser: 0`)으로 실행되지 못하게 막아 권한 탈취 피해 최소화.
4. **리소스 쿼터 강제 (Enforce Resource Limits)**
   - CPU/Memory의 Limit 속성 지정을 강제하여, 특정 불량 파드가 노드 자원을 독식해 클러스터 전체를 마비시키는 Noisy Neighbor 및 자원 고갈(DDoS) 위협 차단.

### Ⅴ. 결론 및 실무적 판단 포인트
- 인프라 리더는 클라우드 네이티브 보안을 완성하기 위해 **Policy-as-Code(코드형 정책)** 체계를 반드시 확립해야 합니다. 인프라가 1만 개의 파드로 팽창할 때, 보안팀이 수동으로 YAML을 검토하는 것은 불가능합니다. 깃허브에 Rego 보안 코드를 관리(GitOps)하고, OPA Gatekeeper를 클러스터에 상주시켜 파이프라인의 최종 관문(Guardrail)으로 삼아야만, 개발 속도를 저해하지 않으면서도 보안 컴플라이언스 이탈률 0%를 달성할 수 있습니다.

### 💡 문제 유형별 목차 전환 포인트
- **[쿠버네티스(K8s) 클러스터 환경의 보안 위협 분석 및 방어 아키텍처 설계]**: Ⅰ과 Ⅱ번(어드미션 컨트롤러 가로채기 원리)을 중심으로 서술하여, PSP(Pod Security Policy) 폐기 대안이자 클러스터 심층 방어(Cluster 단계)의 핵심 엔진으로서 OPA의 당위성을 제시.
- **[데브섹옵스(DevSecOps) 내 Policy-as-Code (코드형 정책) 구현 및 규정 준수 자동화]**: Ⅲ번(템플릿과 제약조건 구조)의 유연성과 Ⅳ번(4대 필수 정책)의 실무적 방어 효과를 조명하여, 개발 파이프라인 배포 시점에 휴먼 에러를 통제하는 자동화된 보안 거버넌스 프레임워크 기술.
