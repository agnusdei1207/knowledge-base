## 미리 알고가기

- Admission 제어는 쿠버네티스가 리소스를 생성·수정하기 직전에 허용 여부를 판단하는 단계임
- OPA는 정책을 코드로 작성해 자동 평가하는 오픈 정책 엔진임
- Rego는 OPA가 정책을 기술할 때 쓰는 선언형 규칙 언어임

## Ⅰ. 개요

- **정의/개념**: OPA Gatekeeper는 쿠버네티스 Admission 제어 지점에서 보안 정책을 코드로 평가해 위험한 매니페스트 배포를 막는 정책 엔진임
- **배경/필요성**: 클러스터가 커지면 매니페스트 검토를 사람에게만 맡기기 어려움. 팀별 배포 습관 차이는 위험한 설정 유입으로 이어짐

## Ⅱ. 특징

- 정책을 코드로 관리해 버전 추적과 재사용이 쉬움
- 생성 시점 차단과 배포 후 감사 기능을 함께 제공함
- 네임스페이스, 이미지 출처, 권한 상승, 라벨 규칙을 한 틀에서 다룸
- 너무 많은 정책을 한 번에 강제하면 배포 실패가 늘 수 있어 감사 모드에서 단계적으로 올리는 편이 안정적임

## Ⅲ. 종류 및 비교

| 판단 기준 | Pod Security Admission | OPA Gatekeeper |
|:---|:---|:---|
| 정책 범위 | 미리 정해진 보안 수준 중심 | 조직 맞춤 정책까지 폭넓게 정의 가능 |
| 표현력 | 단순하고 빠름 | 세밀한 조건과 예외를 코드로 작성 가능 |
| 운영 난이도 | 상대적으로 낮음 | 정책 설계와 테스트가 더 필요함 |
| 적합 환경 | 공통 보안 기준을 빠르게 맞출 때 | 세부 규칙을 조직별로 강제할 때 |

## Ⅳ. 구성요소 및 구조

| 구성요소 | 설명 |
|:---|:---|
| Admission Webhook | 리소스 생성·수정 요청을 가로채 정책 평가를 요청함 |
| Constraint Template | Rego 규칙과 입력 형식을 템플릿으로 정의함 |
| Constraint | 실제 허용 기준과 예외 범위를 선언함 |
| Audit Controller | 이미 배포된 리소스도 주기적으로 다시 점검함 |
| 정책 저장소 | Git 기반으로 정책 변경 이력을 관리함 |

```text
매니페스트 요청 -> Admission Webhook -> Constraint 평가 -> 허용/거부
                                            |
                                            +-> Audit로 기존 리소스 재점검
```

## Ⅴ. 원리 및 절차 흐름도

```text
정책 정의 -> 템플릿 배포 -> 제약 조건 생성 -> 매니페스트 요청 평가 -> 허용 또는 거부 -> 감사 재점검
```

1. **정책 정의**: 조직이 금지할 조건과 허용 예외를 정함
2. **템플릿 배포**: Rego 기반 템플릿을 클러스터에 배포함
3. **제약 조건 생성**: 네임스페이스와 리소스별 적용 범위를 지정함
4. **요청 평가**: 새 매니페스트가 들어오면 정책 위반 여부를 판단함
5. **감사 재점검**: 이미 떠 있는 리소스도 주기적으로 다시 검사함

## Ⅵ. 실무 적용 및 유의점

1. 공용 쿠버네티스 클러스터는 특권 컨테이너, 최신 태그, 미승인 레지스트리를 먼저 막고 거부된 위험 매니페스트 수로 확인함
2. 정책을 한꺼번에 강제하면 배포가 멈출 수 있으므로 감사 모드로 시작하고 예외 만료 초과 건수와 배포 실패율로 점검함

## Ⅶ. 결론

- OPA Gatekeeper는 쿠버네티스 보안 규칙을 문서가 아니라 실행되는 정책으로 바꾸는 도구이므로 표현력보다도 단계적 적용과 예외 관리가 중요함
