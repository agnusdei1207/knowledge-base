## Ⅰ. 개요
- **정의**: 사람과 봇을 구별하기 위해 기계가 풀기 어려운 과제를 제시하는 자동화 방지 기술임
- **배경/필요성**: 웹 서비스에 대한 자동화 봇 공격(계정 탈취, 스팸 등록, 매크로 매점)이 증가하여 사람 여부 검증이 필요함
- **비유**: 놀이공원 입구에서 "사람만 통과"라는 간단한 퀴즈를 내는 것과 유사함

| 출제 의도 | 반드시 짚을 핵심 | 감점 회피 포인트 |
|:---|:---|:---|
| 봇 방지 기술 진화와 접근성 균형 | reCAPTCHA v3의 점수 기반 판별 방식 | 접근성(시각장애인) 고려 |

> 요약: CAPTCHA는 과제 기반으로 사람과 봇을 구별하는 자동화 방지 기술임

## Ⅱ. 구성요소
```text
Client --> Challenge 요청 --> CAPTCHA Server
  |                               |
  +-- 사용자 응답 ------>  판별 엔진
                               |
                        결과(pass/fail) --> Web Server
```

| 구성요소 | 설명 | 비유 |
|:---|:---|:---|
| Challenge Generator | 텍스트 왜곡, 이미지 선택, 행동 분석 등 과제를 생성하는 모듈 | 시험 문제 출제기 |
| 판별 엔진 | 사용자 응답 또는 행동 패턴을 분석하여 사람/봇을 판정하는 엔진 | 채점관 |
| Risk Score (v3) | 마우스 움직임, 브라우저 지문 등을 종합한 0.0~1.0 신뢰 점수 | 수상한 행동 점수표 |
| Token | 판별 결과를 서버에 전달하는 일회성 검증 토큰 | 통과 도장 |

> 요약: Challenge 생성, 판별, 점수화, 토큰 전달로 사람/봇 구별 프로세스를 구성함

## Ⅲ. 절차
```text
페이지 로드 -> Challenge 제시 -> 응답 분석 -> 토큰 검증
```
- 1단계: 사용자가 보호 대상 페이지에 접근하면 CAPTCHA 위젯이 로드됨
- 2단계: v2는 이미지 선택 과제를 제시하고, v3는 백그라운드 행동 분석을 자동 수행함
- 3단계: 판별 엔진이 응답 정확도 또는 행동 점수를 산출하여 사람/봇을 판정함
- 4단계: 서버가 CAPTCHA 서버에 토큰을 전송하여 최종 검증 결과를 수신하고 요청을 허용/차단함

> 요약: 위젯 로드, 과제/행동분석, 판정, 토큰 검증 4단계로 자동화 봇을 차단함

## Ⅳ. 문제점
- 사용자 경험 저하: 이미지 선택 과제가 반복되면 이탈률이 증가함
- 접근성 배제: 시각·인지 장애 사용자가 과제를 수행하기 어려움
- AI 우회 공격: OCR·이미지 인식 AI가 발달하여 전통적 CAPTCHA의 판별력이 약화됨

> 요약: UX 저하, 접근성 배제, AI 우회가 CAPTCHA의 핵심 과제임

## Ⅴ. 개선방안
1. 단기: reCAPTCHA v3 점수 기반 방식을 도입하여 사용자 개입 없이 봇을 탐지함
2. 중기: WCAG 가이드라인에 따른 오디오 대안 및 다중 감각 과제를 제공하여 접근성을 확보함
3. 장기: 디바이스 증명(Passkey, Private Access Token) 기반 봇 방지로 CAPTCHA 의존을 탈피함

> 요약: 점수 기반 탐지, 접근성 대안, 디바이스 증명 방식으로 봇 방지 체계를 고도화해야 함

## Ⅵ. 전망
- 발전 방향: Invisible CAPTCHA와 디바이스 증명 기반 방식이 CAPTCHA를 대체할 전망임
- 기술사적 판단: 사람/봇 구별 문제는 AI 발전에 따라 암호학적 디바이스 증명으로 수렴할 것임
- 기술사 제언: 서비스 설계 시 봇 방지와 접근성을 동시에 충족하는 다계층 방어를 구현해야 함
