## Ⅰ. 개요
- **정의**: 소프트웨어 공급망 무결성을 보장하기 위한 단계별 보안 성숙도 프레임워크
- **배경/필요성**: 빌드·배포 파이프라인 어디서든 아티팩트가 변조될 수 있어, 출처 증명과 빌드 재현성을 체계적으로 검증할 구조가 필요함
- **비유**: 식품 이력 추적 시스템처럼, 코드가 어디서 왔고 누가 빌드했는지 증명서를 붙이는 것

| 출제 의도 | 반드시 짚을 핵심 | 감점 회피 포인트 |
|:---|:---|:---|
| 공급망 보안 성숙도 평가 | Level 0~3 단계별 요구사항 차이 | Provenance 자동 생성과 빌드 격리 구분 |

> 요약: SLSA는 소프트웨어 아티팩트의 출처 증명과 빌드 무결성을 단계별로 보장하는 프레임워크임

## Ⅱ. 구성요소
```text
Source --> Build System --> Artifact --> Consumer
  |           |               |            |
  v           v               v            v
Version    Provenance     Signature    Verification
Control    Generation     Attachment   Policy
```

| 구성요소 | 설명 | 비유 |
|:---|:---|:---|
| Provenance | 빌드 입력·환경·출력을 기록한 메타데이터 | 제품 원산지 증명서 |
| Build Level | L0(없음)~L3(격리빌드) 성숙도 등급 | 식품안전 등급(HACCP 수준) |
| Verification | 소비자 측에서 Provenance 검증하는 절차 | 수입 통관 시 서류 대조 |

> 요약: 소스-빌드-아티팩트-소비 전 과정에 출처 증명과 검증 체계를 적용함

## Ⅲ. 절차
```text
Commit --> Build --> Attest --> Verify
```
- 1단계: Commit — 소스코드를 버전 관리 시스템에 커밋하고 변경 이력을 기록함
- 2단계: Build — 격리된 빌드 환경에서 아티팩트를 생성하고 빌드 로그를 보존함
- 3단계: Attest — Provenance 문서를 자동 생성하고 서명을 첨부함
- 4단계: Verify — 소비자가 Provenance 서명과 빌드 출처를 검증 후 배포함

> 요약: 커밋부터 검증까지 4단계를 거쳐 아티팩트의 변조 여부를 추적함

## Ⅳ. 문제점
- 도입 복잡성: 기존 CI/CD 파이프라인 전면 수정 필요 — 레거시 빌드 시스템 전환 비용이 큼
- Provenance 위조: 빌드 시스템 자체가 침해되면 증명서도 조작 가능 — 신뢰 기반이 훼손됨
- 생태계 파편화: 언어·패키지 관리자별 Provenance 포맷이 상이 — 통합 검증이 곤란함

> 요약: 도입 비용, 빌드 시스템 신뢰, 포맷 비호환이 주요 장벽임

## Ⅴ. 개선방안
1. 단기: GitHub Actions 등 주요 CI 플랫폼의 SLSA 빌더를 활용하여 점진적 적용
2. 중기: 빌드 시스템을 TEE(신뢰실행환경)에서 격리 실행하여 Provenance 위조 방지
3. 장기: in-toto, SLSA, SBOM 포맷을 표준화하여 크로스 생태계 상호운용 달성

> 요약: 플랫폼 내장 빌더 활용 → 빌드 격리 강화 → 표준 통합으로 성숙도를 높여야 함

## Ⅵ. 전망
- 발전 방향: SLSA v1.0 이후 Source Track 추가로 소스 무결성까지 포괄하는 방향으로 확장 중
- 기술사적 판단: 공급망 공격이 증가하며 SLSA 준수가 조달·규제 요건으로 의무화될 가능성이 높음
- 기술사 제언: SBOM(130 참조)과 연계하여 빌드 출처 증명을 SW 조달 기준에 포함할 필요
