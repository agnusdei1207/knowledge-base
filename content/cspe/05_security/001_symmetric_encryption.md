# 📖 【암기용】 개념 완전 이해

## 한눈에
- **개요**: 대칭 암호화는 **하나의 비밀키(대칭키)**로 평문을 암호화하고 같은 키로 복호화하는 **블록/스트림 암호** 방식이다.
- **왜 필요한가**: 디스크·DB·VPN·TLS 세션처럼 GB 단위 대량 데이터를 실시간으로 보호하려면, 공개키 연산보다 수백~수천 배 빠른 대칭 암호가 필요하다.
- **핵심 직관**: 같은 열쇠를 복사해 양쪽이 나눠 갖는 자물쇠와 같다 — 자물쇠(알고리즘)가 튼튼해도 열쇠(키)를 어떻게 전달·보관하느냐가 실제 보안을 좌우한다.

## 핵심 용어 정리 (내부에 등장하는 것들)

아래는 답안에 등장하는 모든 내부 용어를, 처음 보는 사람이 이해하도록 비유와 함께 먼저 정리한 것이다.

| 용어/표기 | 의미 | 비유·예 |
|:---|:---|:---|
| 대칭키(비밀키) | 암호화·복호화에 **똑같이 쓰는 하나의 키** | 집 현관 자물쇠 열쇠를 복사해 가족이 나눠 갖는 것 |
| 블록 암호 | 평문을 고정 크기(예: 128-bit) 덩어리로 잘라 암호화 | 화물을 규격 컨테이너 단위로 나눠 싣는 것 (AES) |
| 스트림 암호 | 평문을 1비트/1바이트 흐름으로 키스트림과 XOR | 물줄기에 색소를 흘려 섞는 것 (ChaCha20) |
| 라운드(Round) | 치환·순열을 여러 번 반복하는 한 회차 | 반죽을 여러 번 접고 눌러 고르게 섞는 것 (AES-128은 10라운드) |
| 치환·순열 | 바이트 값을 바꾸고(치환) 자리를 섞음(순열) | 글자를 다른 글자로 바꾸고 순서를 뒤섞는 암호 놀이 |
| 키 확장(키 스케줄) | 하나의 키에서 라운드별 키를 파생 | 마스터키 하나로 여러 방 열쇠를 깎아내는 것 |
| 운용 모드 | 블록 암호를 실제 메시지에 적용하는 규칙(ECB·CBC·CTR·GCM) | 컨테이너를 어떤 순서·연결로 쌓을지 정하는 적재 규칙 |
| IV/Nonce | 매번 다른 초기값으로 같은 평문도 다른 암호문이 되게 함 | 같은 편지도 매번 다른 봉인 스탬프를 찍는 것 |
| AEAD | 기밀성 + 무결성·인증을 한 번에 제공(GCM) | 내용을 숨기면서 봉인 훼손 여부까지 확인하는 봉투 |
| 인증 태그(Tag) | 암호문 변조 여부를 검증하는 짧은 값 | 택배 봉인 스티커 — 뜯기면 티가 남 (GCM 128-bit) |
| 키 분배 | 통신 전 양쪽이 같은 비밀키를 안전하게 나눠 갖는 문제 | 열쇠를 택배로 보내다 도중에 복사당하면 끝 |
| 키 회전 | 키를 주기적으로 새 키로 교체 | 비밀번호를 90일마다 바꾸는 것 |
| KMS/HSM | 키를 안전하게 생성·보관·통제하는 서비스(KMS)·전용 하드웨어(HSM) | 열쇠를 금고(HSM)에 넣고 출입기록(KMS)을 남기는 것 |

## 깊이 이해
- **배경·문제의식**:
  - DES는 56-bit 키를 써서 오늘날 전수조사(Brute-force)로 하루 안에 뚫린다 — 키 공간이 2^56으로 너무 작다.
  - 3DES는 DES를 3번 겹쳐 112-bit 수준 보안을 얻었지만, 64-bit 블록과 3배 연산 비용 때문에 신규 사용이 중단(NIST, 2023) 됐다.
  - AES는 128-bit 블록과 128/192/256-bit 키를 제공해 이 한계를 넘고 현대 표준(FIPS 197)이 됐다.
- **작동 원리(어떻게+왜)**:
  - 평문 블록을 키 스케줄이 만든 라운드 키와 함께 **치환(SubBytes)·행이동(ShiftRows)·열섞기(MixColumns)·키합성(AddRoundKey)** 을 여러 라운드 반복해 통계적 규칙성을 없앤다.
  - 라운드를 반복하는 이유는, 한 번의 섞기만으로는 평문-암호문 사이 패턴이 남아 분석당하기 때문이다(확산·혼돈 원리).
  - 복호화는 같은 비밀키로 각 단계를 역순으로 되돌린다.
- **비유**: 같은 자물쇠 열쇠를 복사해 나눠 갖는 구조다. 자물쇠가 아무리 튼튼해도, 열쇠를 택배로 보내다 중간에 복사당하면 금고 전체가 열린다 → 이것이 **키 분배 문제**이며 002 비대칭·003 하이브리드가 푸는 핵심이다.
- **구체 예시**: AES-256-GCM은 256-bit 키 + 96-bit nonce를 쓰고, 암호문과 함께 128-bit 인증 태그를 만들어 기밀성과 무결성을 동시에 제공한다 → TLS 1.3·디스크 암호화의 기본값이다.
- **흔한 오해·주의점**: "AES-256이면 끝"이 아니다. **ECB 모드**는 같은 평문 블록이 같은 암호문으로 드러나 이미지 윤곽이 그대로 보인다. 반드시 CBC·CTR·GCM 같은 운용 모드와 **nonce 유일성**(GCM에서 nonce 재사용 시 키 노출)을 지켜야 한다.

## 연결 개념
- 비대칭 암호(002) — 대칭키의 키 분배 문제를 공개키로 해결
- 하이브리드 암호(003) — 비대칭으로 세션키 교환 + 대칭으로 본문 암호화
- 키 관리(KMS·HSM), HMAC·AEAD — 대칭키의 생성·보관·무결성 보완

# 📝 【답안용】 시험 답안 템플릿

## 핵심 인사이트 (3줄 요약)

> 1. **본질**: 대칭 암호화는 송·수신자가 동일한 비밀키를 공유해 대량 데이터의 기밀성을 고속으로 제공하는 방식임.
> 2. **가치**: AES-GCM·ChaCha20-Poly1305가 TLS·VPN·DB·디스크 암호화의 본문 보호를 담당함.
> 3. **판단 포인트**: 알고리즘 강도보다 키 분배·nonce 유일성·운용 모드·키 회전이 실제 보안 수준을 결정함.

## 출제 의도 및 답안 포인트

| 출제 의도 | 반드시 짚을 핵심 | 감점 회피 포인트 |
|:---|:---|:---|
| 데이터 노출 위협을 암호 통제·키 관리와 연결하는 설계 역량 확인 | AES-GCM·ChaCha20-Poly1305, KMS/HSM, 96-bit nonce 유일성, 키 회전, ECB 금지 | AES 키 길이만 나열, 운용 모드 누락, 기밀성·무결성 역할 혼동 |

> 요약: 대칭 암호 답안은 기밀성 제공 범위와 키·nonce 운영 통제를 함께 제시해야 함.

---

## Ⅰ. 개요 및 필요성

- 개요: 동일 비밀키로 암복호화하는 블록/스트림 암호
- 배경: DES 56-bit는 전수조사로 무력화, 3DES는 64-bit 블록·3배 비용 한계로 신규 사용 중단(2023)
- 필요성: GB 단위 본문을 실시간 보호하려면 공개키보다 수백 배 빠른 AES-128/256(FIPS 197) 필요

---

## Ⅱ. 구조 및 구성요소

```text
평문 -> [운용 모드(ECB/CBC/CTR/GCM)] -> [AES 코어(라운드 반복)] -> 암호문 + 인증 태그
          ↑ IV/Nonce         ↑ 비밀키 -> 키 스케줄 -> 라운드 키
암호문 -> [태그 검증] -> [역변환 복호화] -> 평문
```

| 구성요소 | 역할 | 특이사항 |
|:---|:---|:---|
| 비밀키 | 암·복호화 공통 입력 | AES-128/192/256-bit, KMS·HSM 보관 |
| 블록 암호 코어 | 평문 블록을 라운드 반복 변환 | AES 128-bit 블록, DES 64-bit 블록 |
| 운용 모드 | 블록을 메시지 단위로 연결 | CBC·CTR·GCM 권장, ECB 금지 |
| IV/Nonce | 같은 평문의 반복 패턴 은닉 | GCM 96-bit nonce, 재사용 금지 |
| 인증 태그 | 암호문 변조 탐지 | AEAD(GCM) 128-bit tag |

> 요약: 대칭 암호는 비밀키·블록 코어·운용 모드·IV/Nonce·인증 태그가 결합해 기밀성과 무결성을 제공함.

---

## Ⅲ. 동작원리 및 흐름도

```text
키 생성 -> 키 보관·배포 -> IV/Nonce 생성 -> 평문을 암호화 -> 암호문·태그 전송/저장
-> 수신 측이 태그 검증 -> 태그 유효 시 복호화 -> 평문 복원 -> 주기적 키 회전·폐기
```

1. CSPRNG(NIST SP 800-90A)로 128-bit 이상 비밀키를 생성함
2. AES-GCM 등 AEAD 모드를 선택하고 유일한 96-bit nonce를 생성함
3. 송신 측이 평문을 암호화해 암호문과 128-bit 인증 태그를 전송, 수신 측이 태그를 검증한 뒤 복호화해 평문을 복원함
4. 정책 주기(90~365일)에 따라 키를 회전·폐기함

---

## Ⅳ. 특징

- 대량 본문 암호화에 최적 — AES-NI 하드웨어 가속 시 CPU 오버헤드가 한 자릿수 %에 그침
- 키 분배가 최대 약점 — 사용자 N명이 개별 쌍키를 쓰면 N(N-1)/2개 키가 필요해 관리 폭증
- AEAD(GCM)는 기밀성과 무결성·인증을 한 번에 제공 — 별도 MAC 없이 변조 탐지 가능
- 운용 모드 오류에 취약 — ECB 노출·고정 IV·nonce 재사용이 알고리즘 강도와 무관하게 보안을 무너뜨림
- 알고리즘 수명주기 — DES 금지, 3DES 신규 사용 중단, AES-256 우선 적용

---

## Ⅴ. 심화 비교 및 적용 판단

- 대칭키와 공개키(002)는 역할이 달라, 데이터 본문은 대칭·키 교환은 공개키로 분리하는 것이 핵심 판단임.

| 구분 | 대칭키 암호 | 공개키 암호(002) |
|:---|:---|:---|
| 키 관리 | 하나의 비밀키 공유(키 분배 문제) | 공개키·개인키 분리(분배 용이) |
| 속도 | AES-NI로 고속, 대량 처리 적합 | 연산 무거워 대량 본문 부적합 |
| 용도 | 본문 대량 암호화(TLS 레코드·TDE) | 키 교환·전자서명·인증 |

> 요약: 본문은 대칭, 키 교환은 공개키로 분리할 때 처리량과 키 관리 요구를 동시에 만족함.

| 구분 | DES | 3DES | AES |
|:---|:---|:---|:---|
| 키 길이 | 56-bit(취약) | 112-bit 수준 | 128/192/256-bit |
| 블록 크기 | 64-bit | 64-bit | 128-bit |
| 현행 상태 | 사용 금지 | 신규 사용 중단(2023) | 표준(FIPS 197) |

> 요약: 신규 설계는 AES-256을 기본으로 하고 DES·3DES는 제외함.

- 리스크 — 키 유출: 파일·환경변수 평문 저장이 원인 → HSM/KMS 보관·키 암호화 키 분리로 대응
- 리스크 — nonce 재사용: GCM 카운터 충돌이 원인 → 96-bit nonce 유일성 검증으로 대응
- 리스크 — 모드 오류: ECB·고정 IV 사용이 원인 → AES-GCM·랜덤 IV 표준화와 SAST 점검으로 대응

---

## Ⅵ. 실무 적용 및 결론

**적용 방안 3개:**
1. 데이터 저장: DB TDE·파일 암호화에 AES-256-GCM 적용, 키는 KMS CMK 기반 Envelope Encryption으로 보호함
2. 통신 구간: TLS 1.3에서 AES-128-GCM 또는 ChaCha20-Poly1305만 허용하고 CBC·RC4·3DES 스위트를 차단함
3. 운영 통제: 키 소유자 분리, 90~365일 회전, KMS 접근 로그 1년 이상 보관, nonce 중복 탐지를 자동화함

**결론:**
- 조건부 판단: 대량 본문은 AES-GCM, 키 교환은 RSA/ECC·DH와 결합하는 하이브리드(003) 구조가 적합함
- 향후 방향: PQC 전환기에도 세션 데이터는 AES-256 유지, 키 교환부만 ML-KEM 하이브리드로 교체 필요
