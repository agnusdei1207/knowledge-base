## 미리 알고가기

- API 게이트웨이는 클라이언트 요청을 받아 적절한 백엔드로 보내는 진입점이고, API 보안 게이트웨이는 여기에 인증과 권한과 위협 차단 정책을 더한 형태임
- WAF가 웹 공격 패턴을 넓게 막는다면 API 보안 게이트웨이는 토큰 검증과 요청 스키마와 호출량 통제를 더 세밀하게 다룸
- 효과는 장비 도입보다 모든 API가 게이트웨이를 반드시 통과하도록 구조를 잡느냐에 달려 있음

## Ⅰ. 개요

- **정의/개념**: API 보안 게이트웨이는 API 호출의 인증·인가·속도 제한·요청 검증·감사를 중앙에서 수행해 API 트래픽을 통제하는 보안 제어 지점임
- **배경/필요성**: 서비스 수와 API 수가 늘면 각 서비스가 보안 로직을 따로 구현해 정책이 흩어지기 쉬우므로 호출 기준과 위협 차단을 한 곳에서 일관되게 적용할 필요가 커짐

## Ⅱ. 특징

- 토큰 검증과 스키마 검사와 호출량 제한을 공통 정책으로 적용할 수 있음
- 감사 로그와 실패 요청을 중앙에서 수집해 가시성을 높일 수 있음
- 게이트웨이를 우회하는 섀도 API가 있으면 효과가 급격히 떨어짐
- 모든 요청이 모이는 구조라 가용성과 지연 시간 관리가 중요함

## Ⅲ. 종류 및 비교

| 판단 기준 | WAF | API 보안 게이트웨이 |
|:---|:---|:---|
| 주된 초점 | 일반 웹 공격 패턴 차단 | API 인증, 권한, 스키마, 속도 제한 |
| 이해 단위 | URL과 요청 패턴 | 엔드포인트, 토큰, 스코프, JSON 구조 |
| 강점 | 빠른 외부 차단 | API별 정책 일관성과 가시성 |
| 한계 | 비즈니스 권한 흐름 이해가 제한적임 | 우회 API와 내부 호출 통제가 과제가 됨 |

## Ⅳ. 구성요소 및 구조

| 구성요소 | 설명 |
|:---|:---|
| 인증·인가 계층 | JWT, OAuth, API Key, 스코프를 검증함 |
| 요청 정책 계층 | Rate limit, 허용 IP, 요청 크기, 스키마를 검사함 |
| 위협 분석 계층 | BOLA, 인젝션, 비정상 사용 패턴을 탐지함 |
| 라우팅 및 감사 | 정상 요청만 백엔드에 전달하고 로그를 남김 |

```text
API 요청 수신 -> 인증/권한 검증 -> 정책/스키마 검사 -> 위협 분석 -> 백엔드 전달 -> 감사 기록
```

## Ⅴ. 원리 및 절차 흐름도

```text
API 등록 -> 정책 정의 -> 요청 인입 -> 검증/차단 -> 백엔드 전달 -> 로그 분석/튜닝
```

1. **API 등록**: 어떤 API를 관리할지 자산 목록을 정함
2. **정책 정의**: 인증 방식과 스코프와 요청 제한 기준을 설정함
3. **요청 검증**: 토큰과 스키마와 호출 빈도를 확인함
4. **차단 또는 전달**: 위반 요청은 막고 정상 요청만 백엔드로 보냄
5. **로그 분석과 튜닝**: 오탐과 누락 정책을 조정함

## Ⅵ. 실무 적용 및 유의점

1. 외부 파트너와 모바일 앱에 API를 제공하는 조직은 인증과 속도 제한과 스키마 검증을 게이트웨이에서 공통화하고, 섀도 API 탐지와 이중화 구성을 함께 운영한 뒤 우회 API 감소와 미인가 요청 차단률과 응답 지연 허용 범위로 확인함
2. 내부 마이크로서비스 환경도 신뢰 구역으로 두지 말고 서비스별 권한과 감사 기준을 게이트웨이나 메시에 명확히 넣어 서비스 간 과다 권한 호출 감소와 정책 변경 추적 가능 여부로 확인함

## Ⅶ. 결론

- API 보안 게이트웨이는 API 보안을 모아 주는 장비가 아니라 호출 신뢰 기준을 중앙에서 강제하는 통제 지점이어야 효과가 있음
