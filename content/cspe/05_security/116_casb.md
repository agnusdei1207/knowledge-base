## 1. 한눈에 이해하기 (Core Intuition)
- **정의**: 직원들이 회사 몰래, 혹은 공식적으로 사용하는 수백 개의 외부 클라우드 서비스(구글 드라이브, 마이크로소프트 365, 슬랙, 드롭박스 등)와 회사 네트워크 **중간에 딱 버티고 서서, 트래픽을 감시하고 기밀 데이터 유출을 차단하는 '클라우드 전용 보안 검문소(브로커)'** 입니다.
- **필요성**: 직원이 사내 PC에서 고객 주민번호 1만 개가 든 엑셀 파일을 개인 구글 드라이브나 섀도우 IT(회사 몰래 쓰는 앱, 예: 무료 PDF 변환 사이트)에 올려버리면, 회사 방화벽은 이게 정상적인 인터넷 웹서핑(HTTPS)인 줄 알고 멍청하게 다 통과시켜버립니다. 클라우드(SaaS)로 빠져나가는 트래픽의 내용물(데이터)을 뜯어보고 차단할 전용 감시자가 필요했습니다.
- **핵심 직관**: **"공항의 수하물 X-ray 검사대"**. 
  - 과거 (방화벽): "출국장에 들어갈 자격(IP)이 있네? 통과!" (가방 안에 폭탄이 있는지 없는지는 모름).
  - **CASB**: 비행기(클라우드)에 타기 직전, 직원의 짐가방(업로드되는 파일)을 X-ray로 싹 다 뜯어봅니다. 만약 가방 안에 회사의 '1급 기밀 설계도'나 '주민번호'가 발견되면? 즉시 가방을 압수하고 보안팀에 경고 사이렌을 울립니다(DLP 기능). 또한 회사가 허락하지 않은 불법 전세기(섀도우 IT 클라우드)에는 아예 탑승 자체를 막아버립니다.

## 2. 왜 중요한가? (Background & Value)
- **등장 배경**: 과거에는 회사의 모든 서버가 전산실(온프레미스) 안에 있었지만, SaaS 시대가 열리며 회사 데이터의 50% 이상이 외부 클라우드에 저장되기 시작했습니다. 통계에 따르면 일반 기업 직원은 IT 부서가 모르는 수십 개의 섀도우 IT(미승인 클라우드 앱)를 씁니다. 방화벽이 보지 못하는 이 맹점을 방어하기 위해 탄생했습니다.
- **가치**: 통제권 상실의 회복. 데이터가 회사의 물리적 울타리를 벗어나 남의 서버(구글/MS)에 저장되어 있더라도, 그 데이터가 누구에게 공유되고 있는지, 암호화는 되어 있는지를 100% 모니터링하고 제어할 수 있는 가시성(Visibility)을 되찾아 줍니다.

## 3. 어떻게 작동하는가? (Mechanism)
CASB는 크게 두 가지 방식으로 클라우드와 직원 사이를 통제합니다.

1. **프록시 방식 (Proxy Mode - 실시간 차단)**
   - **Forward Proxy**: 직원 PC에 에이전트를 깔거나 사내망 길목에 설치. 직원이 파일을 구글 드라이브에 **올리는 순간(In-Line)** 중간에서 낚아채어 검사하고, 기밀문서면 업로드 자체를 실시간 차단합니다.
   - **Reverse Proxy**: 외부(카페, 집)에서 개인 스마트폰으로 회사 MS 365(클라우드)에 접속할 때, 트래픽을 억지로 CASB를 거치게(우회) 만듭니다. "개인 폰에서는 기밀문서 다운로드 불가!" 등 세밀한 기기 통제가 가능합니다.
2. **API 방식 (API Mode - 사후 검사 및 권한 통제)**
   - 통신 중간에 끼어들지 않습니다. 대신 구글(Google Workspace) 관리자 API와 CASB를 연동해 둡니다.
   - 직원이 밤 11시에 구글 드라이브에 있던 '고객명단.xls' 파일의 **공유 설정 버튼을 '전체 공개(Public)'로 실수로 바꾸는 순간**, CASB가 API를 통해 이를 감지하고 1초 만에 강제로 '비공개'로 되돌려놓습니다(자동 조치).

## 4. 실전 활용 및 예시 (Real-world Application)
- **구체적 사례**: 
  - 영업팀 직원이 퇴사하기 직전, 회사 고객 DB 10만 건을 개인용 Dropbox(섀도우 IT)로 업로드하려 시도합니다. 사내 방화벽은 HTTPS 암호화 트래픽이라 무사통과시키지만, 길목에 있던 **CASB(예: Netskope, McAfee, Zscaler)** 가 이 트래픽을 복호화(뜯어봄)하여 파일 내용에 '주민번호/이메일 패턴'이 가득한 것을 발견합니다. CASB는 즉시 "중요 정보 유출 시도 차단" 메시지를 띄우고 파일을 삭제한 뒤 CISO(보안책임자)에게 알람을 보냅니다.
- **주의점 및 흔한 오해**: 
  - "프록시 방식이 무조건 좋네요?" $\rightarrow$ 아닙니다. 프록시는 모든 트래픽을 중간에서 검사하므로 **속도 저하(Latency)** 가 발생하고, 직원이 폰(LTE)으로 우회 접속하면 못 막습니다. 따라서 완벽한 CASB는 **프록시(실시간 차단) + API(사후 설정/권한 감사)** 두 방식을 하이브리드로 결합하여 빈틈을 없애는 것이 핵심입니다.

## 5. 핵심 비교 및 연결 개념 (Relation)
클라우드 보안 삼형제 (CSPM / CWPP / CASB):
- **CSPM**: 인프라 보안. "우리 클라우드(AWS) 설정 제대로 했어? 포트 안 열어놨지?"
- **CWPP**: 서버 보안. "클라우드 안에 있는 리눅스 서버(VM)에 바이러스 안 먹었지?"
- **CASB**: SaaS 데이터 보안. "직원들이 구글 드라이브에 기밀문서 안 흘리고 있지?"

# ✍️ 단답형 / 서술형 시험장 출격 준비

### Ⅰ. 핵심 인사이트
- **본질**: 온프레미스 네트워크와 퍼블릭 클라우드 서비스(주로 SaaS) 사이에 위치하여, 기업의 보안 정책(Policy)을 모니터링하고 강제 집행(Enforcement)하는 클라우드 특화 보안 게이트웨이 및 API 미들웨어 아키텍처.
- **가치**: 클라우드 시대 보안의 최대 사각지대인 **섀도우 IT(Shadow IT, IT 부서 비승인 클라우드 사용)** 에 대한 100% 가시성을 제공하고, 회사 경계를 벗어난 데이터에 대해 실시간 DLP(데이터 유출 방지) 및 세션 통제를 수행하여 데이터 주권을 회복함.
- **판단 포인트**: IT 보안 설계자는 기존 L4/L7 방화벽이나 웹 프록시(SWG)가 CASB를 완벽히 대체할 수 있다는 벤더의 환상을 경계해야 합니다. CASB의 진정한 힘은 네트워크 패킷 검사를 넘어, O365나 Salesforce 같은 **특정 SaaS 앱의 고유한 컨텍스트(예: "다운로드는 허용하되, 공유 버튼 클릭은 차단")를 L7 레벨에서 정밀하게 파싱하고 제어하는 애플리케이션 친화적 아키텍처**에 있습니다.

### Ⅱ. CASB의 4대 핵심 기능 (Gartner 정의 Pillar)
1. **가시성 (Visibility) 및 섀도우 IT 통제**
   - 사내 방화벽 로그를 수집/분석하여, 임직원이 몰래 사용하는 수천 개의 비인가 클라우드 서비스(PDF 압축 사이트, 개인 드라이브) 현황과 위험도(Risk Score)를 시각화.
2. **데이터 보안 (Data Security / Cloud DLP)**
   - 파일 업로드/다운로드 트래픽 내용물(Payload)을 실시간 분석하여 신용카드, PII(개인정보), 소스코드 등 민감 데이터 패턴 매칭 시 즉각 차단(Block) 또는 암호화(Encryption).
3. **위협 방어 (Threat Protection)**
   - 비정상적인 대량 다운로드, 불가능한 위치(한국/미국 동시 접속)에서의 로그인 시도 등 클라우드 계정 침해(Account Hijacking) 징후를 UEBA(사용자 행위 분석)를 통해 탐지하고 세션 탈취/악성코드 전파 차단.
4. **컴플라이언스 (Compliance)**
   - 클라우드 내에 저장된 데이터가 PCI-DSS, HIPAA, ISMS-P 등 산업별 보안 규제를 준수하도록 지속적으로 감사(Audit)하고 보고서 자동 생성.

### Ⅲ. CASB 구축 아키텍처 (Proxy vs API) 트레이드오프
완벽한 통제를 위해 두 아키텍처의 멀티모달(Multi-modal) 결합이 필수적임.
1. **Forward Proxy (포워드 프록시)**
   - 트래픽 길목 통제. 회사 디바이스(에이전트)나 사내망 라우팅을 통해 모든 사용자 트래픽을 CASB로 우회시킴.
   - 장점: **실시간(In-Line) 데이터 유출 차단(DLP)** 가능. 알려지지 않은 섀도우 IT 완벽 통제.
   - 단점: 임직원 개인 단말(BYOD)이나 사외망(LTE)에서 직접 SaaS에 접속하는 트래픽은 통제 불가(에이전트 미설치 시).
2. **Reverse Proxy (리버스 프록시)**
   - SaaS 애플리케이션(예: M365) 앞단에 CASB가 IDP(인증서버)와 연동되어 위치함.
   - 장점: 회사 에이전트가 안 깔린 **개인 PC(BYOD)가 클라우드에 접속할 때도 완벽히 통제 가능**.
   - 단점: 회사가 공식 승인한 SaaS(Sanctioned App) 트래픽만 제어 가능. 직원이 몰래 켜는 섀도우 IT는 막을 수 없음.
3. **API (Out-of-Band)**
   - SaaS 제공자의 개방형 API(Graph API 등)를 호출하여 이미 클라우드에 저장된 데이터(Data-at-rest)를 후행 스캐닝함.
   - 장점: 네트워크 속도 저하(Latency)가 전혀 없으며, 과거에 이미 올라가 있던 기밀 데이터나 공유 권한 설정 오류까지 일괄 교정(Remediation) 가능.
   - 단점: 실시간 업로드 찰나에 발생하는 유출은 막을 수 없음(API Polling 주기 지연).

### Ⅳ. 클라우드 보안 프레임워크의 융합 트렌드 (SASE & SSE)
- CASB 단일 장비 시장은 현재 소멸 중입니다. 
- 임직원이 재택근무를 하며 발생하는 트래픽을 보호하기 위해, 기존의 **SWG(웹 게이트웨이) + CASB(클라우드 보안) + ZTNA(원격 접속 보안)** 기능이 하나의 클라우드 엣지 서비스로 통폐합된 **SSE (Security Service Edge)** 가 대세로 자리 잡았습니다. (예: Zscaler Internet Access, Netskope Security Cloud). 

### Ⅴ. 결론 및 실무적 판단 포인트
- 보안 아키텍트는 "사내 망분리"만 믿고 있는 임원진에게 CASB 도입의 필요성을 증명해야 합니다. 사내 PC망이 분리되어 있더라도, 협력업체와 업무를 위해 예외로 뚫어준 M365나 구글 드라이브(SaaS) 포트를 통해 사내 기밀문서가 합법적인 HTTPS 트래픽으로 둔갑하여 무제한 유출되고 있는 것이 현실입니다. 클라우드 시대의 종단 간(End-to-End) 정보 유출 방어(DLP)는 CASB 없이는 절대 아키텍처적으로 성립할 수 없습니다.

### 💡 문제 유형별 목차 전환 포인트
- **[클라우드 환경의 데이터 유출 방지(DLP) 및 섀도우 IT 통제 방안]**: Ⅰ번과 Ⅱ번 기능(4대 Pillar)을 중심으로 전개. 사내 방화벽의 가시성 맹점을 지적하고, 이를 CASB가 어떻게 애플리케이션 레벨 통제로 극복하는지 서술.
- **[클라우드 보안 접근 통제 아키텍처 (Proxy vs API 방식) 비교]**: Ⅲ번 항목을 집중 조명하여, 실시간 차단(In-Line)이 강점인 Proxy 방식과, BYOD/Data-at-rest 스캔이 강점인 API 방식의 상호 보완적(Multi-modal) 하이브리드 아키텍처의 필수성 논증.
