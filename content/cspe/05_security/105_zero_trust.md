## 미리 알고가기

- 제로 트러스트는 내부망이면 안전하다고 가정하지 않고 모든 접근을 계속 검증하는 보안 모델임
- 핵심은 `절대 신뢰하지 말고 항상 검증하라`가 아니라, 접근 요청마다 신원과 기기와 맥락을 근거로 허용 범위를 다시 판단하는 데 있음
- VPN 하나를 대체하는 단일 제품이 아니라 인증, 단말 보안, 네트워크, 정책 엔진을 묶는 아키텍처 개념임

## Ⅰ. 개요

- **정의/개념**: 제로 트러스트 아키텍처는 네트워크 위치를 기본 신뢰하지 않고 모든 접근 요청을 지속 검증해 최소 권한 세션만 허용하는 구조임
- **배경/필요성**: 원격 근무, 클라우드, SaaS 확산으로 경계 기반 보안만으로는 내부 침해, 계정 탈취, 측면 이동을 막기 어려움

## Ⅱ. 특징

- 내부와 외부를 같은 기준으로 보며 요청 시점마다 검증함
- 신원, 기기 상태, 자원 민감도, 행위 맥락을 함께 판단함
- 한 번 로그인했다고 세션 전체를 신뢰하지 않고 재평가함
- 전환 범위가 넓어 단계적 도입과 자산 식별이 중요함

## Ⅲ. 종류 및 비교

| 판단 기준 | 경계 기반 보안 | 제로 트러스트 |
|:---|:---|:---|
| 기본 가정 | 내부망은 상대적으로 신뢰 | 위치와 무관하게 기본 신뢰 없음 |
| 접근 기준 | 네트워크 진입 후 넓은 접근 | 요청별 최소 권한 허용 |
| 장점 | 구조가 단순함 | 계정 탈취와 측면 이동 억제에 유리함 |
| 한계 | 내부 침투 후 확산에 취약 | 도입 범위가 넓고 운영 성숙도가 필요함 |

## Ⅳ. 구성요소 및 구조

| 구성요소 | 설명 |
|:---|:---|
| Identity and Authentication | SSO, MFA, 패스키 등으로 주체를 확인함 |
| Device and Posture | 단말 보안 상태와 관리 여부를 확인함 |
| Policy Engine and Enforcement | 정책 평가와 접근 집행을 담당함 |
| Telemetry and Continuous Monitoring | 로그와 행위와 위협 정보를 수집해 재평가함 |

```text
요청 발생 -> 신원/기기 검증 -> 정책 평가 -> 최소 권한 세션 허용 -> 지속 모니터링과 재평가
```

## Ⅴ. 원리 및 절차 흐름도

```text
자산 분류 -> 정책 정의 -> 요청별 검증 -> 세션 허용/거부 -> 행위 모니터링 -> 필요 시 추가 인증
```

1. **자산 분류**: 중요한 서비스와 데이터와 계정을 식별함
2. **정책 정의**: 누가 어떤 조건에서 접근할 수 있는지 정함
3. **요청별 검증**: 사용자와 기기와 위치와 위험도를 확인함
4. **최소 권한 허용**: 필요한 자원에 한정해 세션을 줌
5. **지속 재평가**: 이상 행위 시 재인증이나 차단을 수행함

## Ⅵ. 실무 적용 및 유의점

1. 제로 트러스트 전환은 중요 데이터와 관리자 계정부터 단계 적용하고 고위험 자산 보호 범위·측면 이동 차단 재현 여부로 확인함
2. 정책 선언만으로는 부족하므로 자산 식별과 로그 연계를 갖추고 정책 적용 자산 비율·추가 인증 작동 여부로 확인함

## Ⅶ. 결론

- 제로 트러스트는 내부망 신뢰 대신 요청 단위 최소 권한을 판단하는 아키텍처이므로 인증, 단말, 정책, 모니터링이 함께 움직여야 함
