## 1. 한눈에 이해하기 (Core Intuition)
- **정의**: 클라우드 환경에서 하드웨어 기반의 **신뢰 실행 환경(TEE)** 을 활용하여, 데이터가 컴퓨터 메모리(RAM)에서 처리되는 '사용 중(In-Use)' 상태일 때조차 암호화를 유지하여 완벽히 보호하는 기술 체계입니다.
- **필요성**: 클라우드에 민감한 데이터(의료, 금융, 개인정보)를 올리려면 "AWS/Azure 관리자가 내 데이터를 몰래 훔쳐보지 않을까?" 하는 근본적 불신을 해결해야 합니다. 
- **핵심 직관**: **"투명 망토를 두른 수술실"**. 환자(데이터)가 구급차(네트워크 전송)를 탈 때나 병실(스토리지)에 누워 있을 때는 커튼으로 가려 보호했습니다(기존 암호화). 하지만 수술(연산)을 하려면 커튼을 쳐내야 했죠. 컨피덴셜 컴퓨팅은 수술실 자체에 투명 망토를 씌워서, 수술하는 의사(클라우드 서버 CPU) 외에는 병원장(클라우드 관리자)조차도 안을 들여다볼 수 없게 만듭니다.

## 2. 왜 중요한가? (Background & Value)
- **등장 배경**: 과거에는 저장 중인 데이터(Data-at-Rest, 디스크 암호화)와 전송 중인 데이터(Data-in-Transit, TLS) 보호에만 집중했습니다. 하지만 메모리 상의 평문 데이터를 덤프 뜨는 해킹이나 내부자 위협이 늘어나면서, **Data-in-Use(사용 중 데이터)** 보호가 클라우드 전환의 마지막 퍼즐로 대두되었습니다.
- **가치**: 퍼블릭 클라우드 컴퓨팅의 패러다임을 **"신뢰할 수 없는 환경에서의 절대 보안"** 으로 끌어올립니다. 은행이나 국방부도 안심하고 아마존이나 마이크로소프트 서버에 데이터를 맡기고 AI 분석을 돌릴 수 있게 되었습니다.

## 3. 어떻게 작동하는가? (Mechanism)
- **핵심 기술 (Hardware-based TEE)**:
  - 컨피덴셜 컴퓨팅은 순수 소프트웨어가 아니라 **CPU 하드웨어 레벨의 암호화 기능**에 절대적으로 의존합니다.
  - 대표적으로 **Intel SGX**, **AMD SEV**, **ARM TrustZone** 같은 기술이 사용됩니다.
- **작동 원리 (Enclave / Secure VM)**:
  1. 클라이언트가 암호화된 데이터를 클라우드 서버의 특정 구역(Enclave, 보안 구역)으로 보냅니다.
  2. 이 보안 구역은 CPU가 하드웨어적으로 할당하고 암호화 키를 통제합니다.
  3. 클라우드 서버의 OS나 하이퍼바이저(VMWare 등)가 해킹당하거나, 악의적인 관리자가 메모리 카드를 물리적으로 빼내어 읽어보려고 시도해도, 보안 구역 내부의 데이터는 100% 암호화된 쓰레기 값으로만 보입니다.
  4. 오직 보안 구역(Enclave) 내부에서 코드가 실행되는 찰나의 순간에만 CPU 캐시 내부에서 복호화되어 연산이 수행되고 다시 암호화됩니다.

## 4. 실전 활용 및 예시 (Real-world Application)
- **구체적 사례**: 
  - **AWS Nitro Enclaves**: 일반 EC2 인스턴스와 완전히 분리된 별도의 격리된 가상 머신(네트워크 접근도 불가능)을 띄워, 그 안에서만 개인키 서명이나 결제 정보 처리 같은 초민감 연산을 수행합니다.
  - **다자간 데이터 결합 (Clean Room)**: 경쟁사인 A은행과 B은행이 고객 데이터를 Azure의 Confidential VM에 올립니다. MS 관리자도, A은행도, B은행도 서로의 원본 데이터를 볼 수 없지만, 합쳐진 통계 모델 결과만 쏙 뽑아갈 수 있습니다.
- **주의점 및 흔한 오해**: 
  - 앱 코드를 처음부터 SGX 같은 TEE 전용 환경에 맞게 뜯어고쳐야 하는 방식(Application Enclave)과, 뜯어고칠 필요 없이 가상 머신 전체를 감싸버리는 방식(Confidential VM)으로 나뉩니다. 목적과 난이도에 따라 선택해야 합니다.

## 5. 핵심 비교 및 연결 개념 (Relation)
- **데이터 생명주기 3단계 보안**: 
  1. **Data-in-Transit (전송 중)**: TLS/IPsec
  2. **Data-at-Rest (저장 중)**: AES, 디스크/DB 암호화
  3. **Data-in-Use (사용 중)**: **Confidential Computing**, FHE, SMPC
- **VS 동형 암호 (FHE)**: 둘 다 Data-in-Use를 보호하지만, FHE는 순수 수학적(소프트웨어) 암호화라 무지하게 느리고, 컨피덴셜 컴퓨팅은 하드웨어(CPU) 기반이라 거의 평문과 같은 **초고속 퍼포먼스**를 자랑합니다.

# ✍️ 단답형 / 서술형 시험장 출격 준비

### Ⅰ. 핵심 인사이트
- **본질**: 하드웨어 기반의 신뢰 실행 환경(TEE)을 클라우드 데이터센터 규모로 확장하여, 연산 처리 중인 데이터(Data-in-Use)의 기밀성과 코드 무결성을 암호학적으로 보장하는 차세대 클라우드 보안 아키텍처.
- **가치**: 클라우드 서비스 제공자(CSP)의 OS, 하이퍼바이저, 물리적 인프라 관리 권한으로부터 사용자 워크로드를 완벽히 격리(Decoupling)함으로써, 제로 트러스트 기반의 궁극적 퍼블릭 클라우드 이관(Migration)을 가능케 함.
- **판단 포인트**: 완전 동형 암호(FHE)의 연산 오버헤드 한계를 하드웨어(CPU) 가속으로 극복하는 실용주의적 대안이며, Application 레벨의 SGX 방식과 VM 레벨의 SEV/TDX 방식 간의 격리 수준/호환성 트레이드오프 분석이 아키텍처 설계의 핵심임.

### Ⅱ. 컨피덴셜 컴퓨팅 컨소시엄 (CCC) 및 개념적 목표
- 리눅스 파운데이션 산하 CCC(구글, MS, 인텔, AMD, AWS 등 참여)가 주도하는 기술 이니셔티브.
- **주요 보안 목표 (Threat Model)**
  - CSP 내부자 위협 방어: 클라우드 관리자가 물리적 메모리 버스를 스누핑(Snooping)하거나 하이퍼바이저 권한으로 덤프하는 행위 차단.
  - 클라우드 테넌트 간 분리: 동일 물리 서버를 쓰는 다른 악성 VM의 공격 방어.
  - 서드파티 소프트웨어 취약점 격리.

### Ⅲ. 핵심 하드웨어 아키텍처 모델 비교 (SGX vs SEV)
**1. Process/Application Level Enclave (Intel SGX 등)**
- **구조**: 일반 앱 내부에서 특정 핵심 연산(예: 암호키 처리, 머신러닝 추론) 부분만 도려내어 Enclave(EPC 메모리 영역)라는 격리 공간에서 실행.
- **장점**: TCB(Trusted Computing Base, 신뢰 대상 코드 크기)가 매우 작아 보안성이 극도로 높음.
- **단점**: 기존 앱 코드를 Enclave API(SDK)에 맞춰 전면 재작성(Refactoring)해야 하므로 도입 허들이 높음.

**2. Virtual Machine Level Enclave (AMD SEV, Intel TDX)**
- **구조**: 하이퍼바이저가 VM을 띄울 때, VM에 할당된 전체 메모리 영역을 하드웨어(메모리 컨트롤러) 레벨에서 고유 키로 통째로 암호화함.
- **장점**: 기존 앱 코드를 1줄도 수정할 필요 없이 그대로(Lift-and-Shift) 보안 가상 머신에 올려 실행할 수 있어 도입이 매우 쉬움.
- **단점**: 전체 OS 커널이 TCB에 포함되므로, OS 자체에 취약점이 있으면 해킹 가능성이 높아짐 (보안성 상대적 감소).

### Ⅳ. 아키텍처 필수 요소: Remote Attestation (원격 증명)
컨피덴셜 컴퓨팅에서 가장 핵심적인 검증 절차입니다.
- **문제**: "내가 데이터를 보내려는 저 클라우드 서버가 진짜 하드웨어 TEE(Enclave)가 맞는지, 코드가 조작되진 않았는지 어떻게 믿는가?"
- **해결 (원격 증명)**:
  1. 클라우드 CPU 내부의 마이크로코드가 현재 실행 중인 Enclave의 상태(코드 해시값)와 CPU의 고유 시그니처를 서명하여 클라이언트(또는 제3의 증명 서버)로 보냄.
  2. 클라이언트는 이 서명을 제조사(인텔/AMD 등)의 공개키로 검증하여 "진짜 인텔 CPU의 정상적인 Enclave"임을 확신한 후, 비로소 데이터 복호화 키를 Enclave 안으로 쏴줌.

### Ⅴ. 적용 아키텍처 및 산업/보안 이슈
- **Confidential AI / LLM**: 프라이빗 데이터로 거대한 언어 모델을 파인튜닝하거나 프롬프트를 날릴 때, 클라우드 제공자가 데이터를 훔쳐 학습 모델에 무단 사용하는 것을 원천 차단하는 인프라로 급부상 중.
- **부채널 공격 (Side-channel Attack)**: CPU의 캐시(L1/L2)나 분기 예측기를 공유하는 하드웨어적 구조 탓에, Spectre/Meltdown의 변종(SGAxe, Plundervolt 등)을 통한 타이밍 공격으로 Enclave 내부 비밀이 유출될 수 있는 지속적인 보안 리스크 존재 $\rightarrow$ 하드웨어 패치 및 Constant-time 코딩 지속 요구.

### Ⅵ. 결론 및 실무적 판단 포인트
- 엔터프라이즈 환경에서 데이터 3법(마이데이터, 가명결합 등) 컴플라이언스를 충족하며 클라우드 전환을 추진할 때, **기밀 컴퓨팅(CVM, Nitro Enclaves) 아키텍처 도입은 필수불가결한 선택**이 되었습니다.
- 보안 아키텍트는 서비스 특성에 따라 레거시 전환이 쉬운 **VM 레벨(AMD SEV)** 과 높은 보안을 요하는 **App 레벨(Intel SGX)** 간의 하이브리드 배치 전략을 수립해야 합니다.

### 💡 문제 유형별 목차 전환 포인트
- **[클라우드 데이터 보안 / Data-in-Use 해결책 묻는 유형]**: Ⅰ과 Ⅱ번을 중심으로 클라우드 관리자의 권한으로부터 사용자 데이터를 분리(Decoupling)하는 TEE의 아키텍처적 가치를 집중 서술.
- **[컨피덴셜 컴퓨팅 구현 기술 비교 (SGX vs SEV)]**: Ⅲ번을 메인으로 끌어올려, TCB(Trusted Computing Base) 크기와 개발 호환성(Refactoring 필요 여부) 관점에서의 정량적 비교 및 도식화를 구성.
