# 📖 【암기용】 개념 완전 이해

> 목적: 기밀 컴퓨팅을 처음 봐도 완벽히 이해하게 만든다. 시험 답안 양식이 아니라, 이해를 위한 친절한 설명이다.

## 한눈에
- **개요**: 실행 중 데이터까지 TEE 안에서 보호하는 컴퓨팅 모델
- **왜 필요한가**: 기존 암호화는 저장·전송 구간을 보호하지만 CPU가 연산할 때는 평문이 메모리에 존재함. 클라우드 운영자·하이퍼바이저·관리자 권한까지 신뢰하지 않는 구조가 필요함.
- **핵심 직관**: 금고 안에 문서를 넣어 보관하는 수준을 넘어, 금고 안에서 문서 작업까지 끝내는 방식임.

## 깊이 이해
- **배경·문제의식**: 멀티테넌트 클라우드는 물리 서버·하이퍼바이저·운영자 권한을 공유함. 금융·의료 데이터는 저장 시 AES-256, 전송 시 TLS 1.3을 적용해도 연산 시점의 메모리 노출 위험이 남음.
- **작동 원리**: CPU가 격리 실행 영역(Enclave, VM TEE)을 만들고 메모리를 하드웨어 키로 암호화함. 원격 검증(Remote Attestation)으로 측정값(MRENCLAVE, TCB 버전)을 확인한 뒤 키를 주입함.
- **비유**: 외부 직원에게 공장을 빌리되, 핵심 공정은 봉인된 작업실에서만 수행하고 작업실의 봉인 상태를 원격으로 검사한 후 재료를 넣는 방식임.
- **구체 예시**: Intel SGX는 애플리케이션 enclave, AMD SEV-SNP는 VM 단위 메모리 암호화와 무결성 검증을 제공함. 민감 데이터는 attestation 성공 후에만 KMS에서 데이터 키를 복호화함.
- **흔한 오해·주의점**: TEE는 data-in-use 보호 기술이지 전체 보안 면책 기술이 아님. 사이드채널, 취약한 enclave 코드, attestation 검증 누락은 별도 통제 필요함.

## 연결 개념
- 신뢰 실행 환경(TEE) - 기밀 컴퓨팅의 하드웨어 실행 기반
- 원격 검증(Remote Attestation) - 실행 환경 신뢰를 증명하는 절차
- 키 관리(HSM/KMS) - 검증된 TEE에만 키를 주입하는 통제점

# 📝 【답안용】 시험 답안 템플릿

> 목적: 시험장에서 25분에 그대로 쓰는 답안 양식. 작성방식(추상표현 금지·수치·도식·문제유형 전환)을 엄격히 지킨다.
> 핵심: data-in-use 보호를 단순 암호화로 설명하지 않고, 위협 모델·TEE·원격 검증·키 주입·감사까지 연결한다.

## 핵심 인사이트 (3줄 요약)

> 1. **본질**: 기밀 컴퓨팅은 CPU 하드웨어 기반 TEE로 실행 중 데이터(data-in-use)를 격리·암호화하는 클라우드 보안 모델임.
> 2. **가치**: 저장 AES-256, 전송 TLS 1.3 이후 남는 운영자·하이퍼바이저·메모리 덤프 위협을 축소함.
> 3. **판단 포인트**: remote attestation 성공, TCB 패치, KMS 키 릴리스 정책, 사이드채널 통제가 채점 포인트임.

## 출제 의도 및 답안 포인트

| 출제 의도 | 반드시 짚을 핵심 | 감점 회피 포인트 |
|:---|:---|:---|
| data-in-use 보호 범위 이해 확인 | 저장·전송·사용 중 데이터 구분, TEE 격리 | 단순 디스크 암호화로 설명 |
| 클라우드 신뢰 경계 판단 확인 | 하이퍼바이저·관리자 권한을 비신뢰 주체로 설정 | 클라우드 사업자를 전면 신뢰한다고 가정 |
| 운영 통제 역량 확인 | Remote Attestation, KMS 조건부 키 릴리스, 감사로그 | enclave 생성 후 키를 무조건 주입 |

> 요약: 기밀 컴퓨팅 답안은 TEE 기능보다 위협 모델, 검증, 키 릴리스 조건을 함께 제시해야 한다.

---

## Ⅰ. 개요 및 필요성

- 개요: 실행 중 데이터 보호 체계
- 배경: 기존 암호화는 data-at-rest와 data-in-transit 보호에 집중했으나 연산 시점에는 평문이 CPU·메모리에 존재함.
- 필요성: 기밀 컴퓨팅은 TEE와 원격 증명으로 하이퍼바이저·운영자 권한을 제한해 멀티테넌트 클라우드와 규제 데이터 처리를 지원함.

---

## Ⅱ. 구조 및 구성요소

```text
민감 워크로드 -> TEE 생성 -> 측정값 생성 -> Attestation 검증 -> KMS 키 릴리스 -> 암호화 연산
                           +-> TCB 버전 확인
                           +-> 감사로그 적재
```

| 구성요소 | 역할 | 특이사항 |
|:---|:---|:---|
| TEE/Enclave | 코드·데이터 실행 영역 격리 | Intel SGX, AMD SEV-SNP, Arm CCA |
| Attestation Service | 측정값·서명·TCB 버전 검증 | nonce로 재전송 공격 차단 |
| KMS/HSM | 검증된 환경에만 데이터 키 릴리스 | 조건부 정책, 키 사용 로그 |
| 보안 관측 | 실행·검증·키 사용 이벤트 수집 | SIEM 연계, 감사 보존 1년 이상 |

> 요약: 구조의 핵심은 TEE 자체가 아니라 attestation 결과를 KMS 키 릴리스 조건으로 묶는 통제 체계임.

---

## Ⅲ. 동작원리 및 흐름도

```text
워크로드 배포 -> TEE 측정값 산출 -> 원격 검증 요청 -> 정책 판정
-> KMS 데이터 키 복호화 -> TEE 내부 처리 -> 결과 암호화 저장 -> 로그 감사
```

| 단계 | 처리 내용 | 검증 기준 |
|:---:|:---|:---|
| 1 | enclave 또는 confidential VM 생성 | 이미지 해시, TCB 버전 일치 |
| 2 | attestation evidence 제출 | 서명 검증, nonce 확인 |
| 3 | KMS 키 릴리스 정책 평가 | workload identity, mTLS, RBAC |
| 4 | TEE 내부 데이터 복호화·연산 | 평문 외부 반출 차단, 메모리 암호화 |
| 5 | 결과 암호화·로그 전송 | 키 사용 로그 100%, 실패 이벤트 경보 |

> 요약: 실행 신뢰는 배포 시 선언이 아니라 측정값 검증 후 키를 주입하는 절차로 확보함.

## Ⅳ. 특징

| 구분 | 기존 암호화 | 기밀 컴퓨팅 | 수치·표준 포인트 |
|:---|:---|:---|:---|
| 보호 범위 | 저장·전송 중심 | 실행 중 메모리·CPU 경계 보호 | AES-256, TLS 1.3, TEE |
| 신뢰 경계 | OS·하이퍼바이저 신뢰 | OS·하이퍼바이저 비신뢰 | SGX enclave, SEV-SNP VM |
| 키 통제 | 애플리케이션 권한 기반 | attestation 기반 조건부 릴리스 | KMS policy, mTLS, RBAC |
| 한계 | 메모리 평문 노출 가능 | 사이드채널·취약 코드 잔존 | TCB 패치 SLA 30일 |

> 요약: 기밀 컴퓨팅은 기존 암호화의 빈 구간인 data-in-use를 보완하지만 사이드채널과 코드 취약점 통제가 별도로 필요함.

## Ⅴ. 심화 비교 및 적용 판단

| 비교 축 | 기존/대안 | 본 키워드 | 선택 기준 |
|:---|:---|:---|:---|
| 보호 모델 | 디스크·네트워크 암호화 | TEE 기반 실행 격리 | 클라우드 운영자 비신뢰 요구 |
| 비용/성능 | 일반 VM | confidential VM/enclave | p95 지연 증가 10% 이내, CPU 암호화 지원 |
| 운영/위험 | OS 보안 중심 | attestation·KMS 연동 중심 | 키 릴리스 실패율 0.1% 이하 |

> 요약: 규제 데이터 공동 분석처럼 운영자 신뢰를 줄여야 하는 경우 TEE와 KMS 연동을 선택함.

| 리스크 | 원인 | 대응 방안 | 확인 지표 |
|:---|:---|:---|:---|
| 사이드채널 | 캐시·분기·페이지 접근 패턴 | constant-time 코드, 패치, 민감 분기 최소화 | TCB 패치 30일 이내 |
| 검증 우회 | attestation 검증 누락 | KMS 정책에 측정값·TCB 버전 조건 추가 | 미검증 키 릴리스 0건 |
| 운영 불가 | CPU·클라우드 리전 미지원 | 호환성 매트릭스, fallback 워크로드 분리 | 지원 리전 2개 이상 |

> 요약: 주요 위험은 TEE 부재보다 검증 우회와 TCB 미패치이며 키 릴리스 로그로 통제함.

| 점검 항목 | 목표 기준 | 측정 방법 |
|:---|:---|:---|
| 기밀성 | 평문 반출 경로 0건 | DLP, 메모리 덤프 테스트 |
| 검증 | attestation 성공률 99.9%, 실패 경보 5분 이내 | KMS·attestation 로그 |
| 운영/보안 | 키 사용 로그 100%, 관리자 접근 승인 2인 | SIEM, IAM 감사 |

> 요약: 도입 효과는 평문 노출 차단, attestation 성공률, 키 사용 감사 완전성으로 판단함.

## Ⅵ. 실무 적용 및 결론

**적용 방안 3개 (필수 — 단계별 또는 항목별):**
1. 위협 모델 설정: data-at-rest, data-in-transit, data-in-use를 분리하고 하이퍼바이저·관리자를 비신뢰 주체로 명시함.
2. 키 릴리스 통제: attestation 측정값, TCB 버전, workload identity, mTLS를 KMS 정책 조건으로 설정함.
3. 운영 검증: TCB 패치 SLA 30일, 키 사용 로그 100%, attestation 실패 5분 이내 SIEM 경보를 운영 기준으로 둠.

**결론 (2줄):**
- 기술사 판단: 규제 데이터의 클라우드 처리·공동 분석이면 TEE+KMS 조건부 키 릴리스를 적용하고, 일반 공개 데이터 처리에는 저장·전송 암호화 우선 적용.
- 향후 방향: confidential VM, confidential container, confidential AI inference로 확장되며 attestation 표준화와 키 거버넌스가 핵심 통제점임.
