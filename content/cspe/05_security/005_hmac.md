## 1. 한눈에 이해하기 (Core Intuition)
- **정의**: 해시 함수와 **'비밀키(Secret Key)'** 를 결합하여 생성한 메시지 인증 코드(MAC)입니다.
- **필요성**: 단순 해시(Hash)만으로는 데이터가 변조되었는지(무결성)는 알 수 있지만, "정말로 그 사람이 보낸 것인지(인증, 출처 확인)"는 알 수 없기 때문에 필요합니다.
- **핵심 직관**: **"우리끼리만 아는 암구호가 섞인 지문"**. 일반 지문(해시)은 누구나 찍을 수 있어서 해커가 파일을 바꾸고 지문도 새로 찍어치우면 그만입니다. 하지만 HMAC은 우리 둘만 아는 '비밀번호(비밀키)'를 데이터와 섞어서 반죽한 뒤 지문을 찍습니다. 해커는 비밀번호를 모르니 가짜 지문을 찍어낼 수 없습니다.

## 2. 왜 중요한가? (Background & Value)
- **등장 배경**: 일반적인 해시(예: MD5, SHA-256)는 누구나 계산할 수 있어, 중간자 공격(MITM) 시 해커가 원본과 해시값을 통째로 조작해버리면 수신자는 속을 수밖에 없습니다. 이를 막기 위해 송/수신자만 아는 키를 섞는 MAC 개념이 등장했고, 그 중 구현이 가장 빠르고 안전한 해시 기반의 HMAC이 산업 표준이 되었습니다.
- **가치**: API 통신, JWT 토큰 서명, 결제 시스템 등 현대 애플리케이션의 인증과 데이터 무결성을 빠르고 가볍게 검증하는 데 필수적인 기술입니다.

## 3. 어떻게 작동하는가? (Mechanism)
- **작동 원리 (Step-by-Step)**:
  1. **사전 준비**: 클라이언트와 서버는 사전에 '비밀키(Secret Key)'를 안전하게 공유하고 있습니다.
  2. **HMAC 생성 (송신자)**: 보낼 데이터(메시지)와 비밀키를 내부적인 패딩 규칙(ipad, opad)에 따라 섞은 후, 해시 함수(예: SHA-256)에 통과시켜 HMAC 값을 만듭니다.
  3. **전송**: 원본 데이터와 생성된 HMAC 값을 함께 서버로 전송합니다.
  4. **HMAC 검증 (수신자)**: 서버는 받은 원본 데이터를 자신이 보관하던 동일한 비밀키와 섞어 똑같이 HMAC을 계산해 봅니다.
  5. **비교**: 내가 계산한 HMAC과 클라이언트가 보낸 HMAC이 일치하면, "내용이 변조되지 않았고, 비밀키를 아는 정당한 사용자가 보낸 것"으로 확신합니다.

- **안전성을 위한 구조 (RFC 2104)**: 단순히 `Hash(Key + Message)`로 만들면 길이 연장 공격(Length Extension Attack)에 뚫릴 수 있습니다. 따라서 HMAC은 해시를 두 번(Inner Hash, Outer Hash) 감싸는 안전한 구조를 사용합니다.

```ascii
[ 메시지 ] & [ 공유된 비밀키 ]
      │             │
      ▼             ▼
┌─────────────────────────┐
│     HMAC 생성 알고리즘    │ (내부적으로 해시 두 번 적용)
└───────────┬─────────────┘
            │
            ▼
      [ HMAC 결괏값 ]
            │
   (메시지와 함께 네트워크 전송)
```

## 4. 실전 활용 및 예시 (Real-world Application)
- **구체적 사례**: 
  - **JWT (JSON Web Token)**: 헤더와 페이로드를 Base64로 인코딩한 뒤, 서버의 비밀키를 이용해 `HMAC-SHA256`으로 서명(Signature)을 만듭니다. (알고리즘 명칭: HS256). 서버는 세션을 유지하지 않아도 토큰의 무결성/인증을 검증할 수 있습니다.
  - **AWS API Gateway 인증**: 클라이언트가 AWS API를 호출할 때, Access Key(식별자)와 Secret Key(비밀키)를 이용해 요청 본문에 대한 HMAC을 계산하여 헤더에 싣습니다(AWS Signature V4).
- **주의점 및 흔한 오해**: 
  - HMAC은 데이터 자체를 암호화(가리기)하지 않습니다. 비밀 데이터를 보내려면 별도의 대칭키 암호화가 필요합니다.
  - 대칭키 기반이므로, 서명자가 "나는 서명하지 않았다"고 우기는 **부인방지(Non-repudiation)는 제공하지 못합니다**. 부인방지가 필요하면 공개키 기반의 전자서명(RSA/ECDSA)을 써야 합니다.

## 5. 핵심 비교 및 연결 개념 (Relation)
- **VS 일반 해시**: 일반 해시 = 무결성. HMAC = 무결성 + 인증.
- **VS 전자서명(Digital Signature)**: HMAC은 대칭키 기반(빠름, 부인방지 불가). 전자서명은 비대칭키/공개키 기반(느림, 부인방지 가능).
- **연결 개념**: 
  - **AEAD (Authenticated Encryption with Associated Data)**: 암호화와 MAC 검증을 동시에 수행하는 최신 기법 (예: AES-GCM).

# ✍️ 단답형 / 서술형 시험장 출격 준비

### Ⅰ. 핵심 인사이트
- **본질**: 암호학적 해시 함수와 대칭키를 결합하여, 메시지의 무결성(Integrity)과 송신자의 인증(Authentication)을 동시에 보장하는 메커니즘 (RFC 2104).
- **가치**: 비대칭키 기반의 전자서명 대비 연산 속도가 압도적으로 빨라, 트래픽이 많은 API 인증, JWT 서명, IPsec 등에서 경량 인증 수단으로 널리 사용됨.
- **판단 포인트**: 단순히 $H(Key || Message)$ 형태로 구현할 경우 길이 연장 공격(Length Extension Attack)에 취약하므로, 반드시 패딩 기반의 중첩 해시 구조(HMAC)를 사용해야 함.

### Ⅱ. 개념 및 아키텍처
**1. 개념**
- 송·수신자가 사전에 공유한 비밀키(Shared Secret Key)를 해시 함수 입력에 포함시켜, 키를 아는 자만이 올바른 다이제스트를 생성/검증할 수 있게 하는 메시지 인증 코드.

**2. 수학적 원리와 수식**
- $HMAC(K, M) = H((K' \oplus opad) || H((K' \oplus ipad) || M))$
  - $H$: 암호학적 해시 함수 (SHA-256 등)
  - $K$: 공유된 비밀키 / $K'$: 블록 크기에 맞게 조정(패딩 또는 해싱)된 키
  - $M$: 전송할 메시지 본문
  - $ipad$: Inner pad (0x36 반복) / $opad$: Outer pad (0x5C 반복)
  - $||$: 연쇄 (Concatenation) 기호

**3. 아키텍처 도식**
```ascii
 ┌────────────────────────────────────────────────────────┐
 │                      Outer Hash                        │
 │        ┌──────────────────────────────────────┐        │
 │        │             Inner Hash               │        │
 │        │                                      │        │
 │  K' ⊕ ipad   ||   Message (M) ────▶ Hash()  │        │
 │                                         │     │        │
 └─────────────────────────────────────────┼─────┘        │
        │                                  ▼              │
  K' ⊕ opad     ||                    Inner Result ─▶ Hash() ─▶ [ HMAC 출력 ]
```

### Ⅲ. 일반 해시 및 전자서명과의 비교 분석
| 특성 | 일반 Hash (SHA-256) | HMAC | 전자서명 (RSA/ECDSA) |
|---|---|---|---|
| **입력값** | 메시지 ($M$) | 메시지 ($M$) + **비밀키 ($K$)** | 메시지 ($M$) + **개인키 ($PR_A$)** |
| **무결성 보장** | ○ | ○ | ○ |
| **인증 (출처 확인)** | ❌ (조작 가능) | **○ (키 소유자 확인)** | ○ (공개키 검증) |
| **부인방지** | ❌ | **❌ (키를 둘이 공유하므로)** | **○ (개인키는 한 명만 소유)** |
| **연산 속도** | 매우 빠름 | 매우 빠름 | 느림 (공개키 연산) |

### Ⅳ. 적용 및 구현 방안
1. **웹/모바일 API 인증 (JWT)**: JWT의 Signature 영역은 `HMAC SHA-256 (HS256)` 알고리즘을 사용하여 서버가 발급/검증 수행. (세션 DB 없이 무상태성 유지).
2. **클라우드 API 서명 (AWS SigV4)**: 요청 파라미터와 타임스탬프를 조합하여 HMAC을 생성해 헤더에 포함, 재전송 공격(Replay Attack) 방어 및 인증 수행.
3. **네트워크 프로토콜 (IPsec, TLS)**: 패킷의 변조를 막기 위해 페이로드에 대해 HMAC-SHA256 등 결합. (과거 MAC-then-Encrypt 방식에서 현재는 AEAD로 진화 중).

### Ⅴ. 주요 보안 위협 및 해결 방안
- **길이 연장 공격 (Length Extension Attack)**
  - 위협: Merkle-Damgård 구조의 해시 함수에서 $MAC = Hash(Key || M)$ 구조 사용 시, 공격자가 $Key$를 몰라도 임의의 데이터 확장이 가능한 취약점.
  - 방어: HMAC의 중첩 설계(Inner/Outer 패딩 구조) 자체가 이 공격을 수학적으로 무력화하도록 설계됨.
- **키 유출 (Key Compromise)**
  - 위협: 대칭키 기반이므로, 검증 서버가 해킹되어 비밀키가 유출되면 해커가 마음대로 인증 토큰(HMAC)을 위조할 수 있음.
  - 방어: 비밀키를 하드코딩하지 않고 AWS KMS, HashiCorp Vault 등의 시크릿 관리 저장소에서 동적으로 주입하여 사용하며 주기적으로 로테이션 실시.

### Ⅵ. 결론 및 실무적 판단 포인트
- **아키텍처 설계 시 선택 기준**:
  - 클라이언트와 서버가 1:1로 통신하거나 단일 시스템(예: 세션 토큰 검증)인 경우, 속도가 빠르고 구현이 쉬운 **HMAC** 채택.
  - 다수의 불특정 수신자에게 배포하거나 제3자 감사, 부인방지가 법적으로 요구되는 경우(예: 전자계약, 공동인증서) 반드시 **공개키 기반 전자서명** 채택.
- 시스템 현대화 관점에서는 별도의 MAC 연산 대신 암호화와 인증을 동시에 처리해 오버헤드를 줄이는 **AEAD(AES-GCM)** 모드 도입을 적극 검토해야 함.

### 💡 문제 유형별 목차 전환 포인트
- **[HMAC 원리와 취약점 방어 묻는 유형]**: Ⅱ번의 수학적 수식(ipad, opad)과 Ⅴ번의 길이 연장 공격 방어 원리를 결합하여 깊이 있게 서술.
- **[인증/무결성 확보 방안 비교 (Hash vs MAC vs 서명)]**: Ⅲ번의 비교표를 전면에 내세우고, 요구사항(부인방지 필요 여부, 속도 제약)에 따른 아키텍처 선택 가이드(Ⅵ)를 강조.
