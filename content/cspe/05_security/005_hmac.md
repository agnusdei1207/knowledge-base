# 📖 【암기용】 개념 완전 이해

## 한눈에
- **개요**: HMAC은 **비밀키를 해시 함수에 결합**해 만드는 **메시지 인증 코드(MAC)**로, 데이터의 무결성과 송신자 인증을 동시에 보장한다.
- **왜 필요한가**: 순수 해시(004)는 무결성만 검증할 뿐, 공격자가 데이터와 해시를 함께 바꾸면 탐지하지 못한다 — 공격자가 모르는 **비밀키**를 넣어야 "정당한 상대가 보냈음(인증)"까지 증명된다.
- **핵심 직관**: 편지 봉투에 두 사람만 아는 비밀 문양의 왁스 인장을 찍는 것과 같다 — 내용이 그대로이고(무결성), 인장을 찍을 수 있는 사람이 보냈음(인증)을 함께 보인다.

## 핵심 용어 정리 (내부에 등장하는 것들)

아래는 답안에 등장하는 모든 내부 용어를, 처음 보는 사람이 이해하도록 비유와 함께 먼저 정리한 것이다. 맨 위는 이 개념의 상위 핵심 키워드다. 해시 함수 자체의 원리(일방향·충돌저항·머클담가드)는 004에서 세웠으므로 여기서는 위임한다.

| 용어/표기 | 의미 | 비유·예 |
|:---|:---|:---|
| 메시지 인증 코드(MAC, 상위 키워드) | 키로 만든 짧은 태그로 무결성+인증을 보증 | 두 사람만 아는 비밀 인장 |
| 무결성(Integrity) | 데이터가 변조되지 않았음 | 봉투 내용물이 그대로임 |
| 인증(Authentication) | 정당한 상대가 보냈음 | 이 인장은 그 사람만 찍을 수 있음 |
| 부인방지(Non-repudiation) | "내가 안 보냈다"를 반박(HMAC은 불가) | 공유 인장은 둘 다 찍을 수 있어 못 가림 |
| 공유 비밀키 | 송·수신자가 사전에 나눠 가진 대칭키 | 두 사람만 아는 인장 도장 |
| ipad·opad | 키에 XOR하는 내·외부 패딩 상수 | 안쪽·바깥쪽 두 겹으로 봉인 |
| 이중(중첩) 해시 | 내부 해시 결과를 다시 해시하는 구조 | 봉투를 봉투로 한 번 더 감쌈 |
| 길이 확장 공격 | 머클담가드 해시에 데이터를 이어 붙이는 공격 | 뒤에 위조 내용을 덧대기 |
| 재전송 공격(Replay) | 유효한 메시지를 가로채 그대로 재전송 | 진짜 인장 편지를 복사해 다시 보냄 |
| 타이밍 공격 | 태그 비교 시간차로 값을 유추 | 자물쇠 돌리는 소리로 번호 추측 |
| HMAC-SHA256 | SHA-256 기반 HMAC(태그 256비트) | 대표 표준 조합 |
| HKDF | HMAC 기반 키 유도 함수 | 하나의 씨앗키로 여러 키를 파생 |

## 깊이 이해
- **배경·문제의식**: 순수 해시(004)를 그대로 무결성 태그로 쓰면, 중간자가 `데이터`를 바꾸고 `해시`도 새로 계산해 붙이면 수신자는 변조를 알 수 없다. 또 단순히 `H(키‖메시지)`로 키를 앞에 붙이면, 머클담가드 구조의 **길이 확장 공격**으로 키를 몰라도 뒤에 내용을 덧붙인 위조 태그를 만들 수 있다. HMAC은 이 두 문제를 동시에 푼다.
- **작동 원리(어떻게+왜)**:
  - 정의: `HMAC(K,m) = H((K⊕opad) ‖ H((K⊕ipad) ‖ m))`. 키를 ipad(0x36 반복)와 XOR해 메시지 앞에 붙여 1차 해시하고, 그 결과를 다시 키를 opad(0x5c 반복)와 XOR한 값 뒤에 붙여 2차 해시한다.
  - **왜 이중 해시인가**: 바깥 해시가 안쪽 해시 결과를 한 번 더 감싸므로, 공격자가 중간 상태를 이어받는 **길이 확장 공격이 원천 차단**된다. 이것이 `H(키‖메시지)` 단순 결합 대비 HMAC의 핵심 안전성이다.
  - **왜 인증이 되는가**: 공격자는 공유 비밀키를 모르므로 올바른 태그를 계산할 수 없다. 따라서 태그가 맞으면 "키를 가진 정당한 상대가 보냈고(인증) 내용도 안 바뀌었음(무결성)"이 동시에 증명된다.
- **비유**: 두 사람만 아는 특수 잉크로 편지 끝에 서명하는 것. 내용을 고치면 잉크 서명과 안 맞고(무결성), 그 잉크는 두 사람만 가지므로 제3자가 위조할 수 없다(인증).
- **구체 예시**: HMAC-SHA256의 태그는 256비트다. TLS 1.2 레코드 무결성, IPsec, JWT의 HS256 서명, AWS 서명 v4의 요청 인증이 모두 HMAC이다. 안전성은 기반 해시가 아니라 **키 비밀성**에 의존하므로, SHA-1이 충돌에 뚫려도 HMAC-SHA1은 상대적으로 오래 버텼다.
- **흔한 오해·주의점**: ① HMAC은 **부인방지를 못 한다** — 키를 송·수신 양쪽이 공유하므로 어느 쪽이 만들었는지 못 가린다. 부인방지는 개인키로 서명하는 전자서명(008)의 몫이다. ② HMAC은 **재전송을 막지 못한다** — 유효한 (메시지+태그)를 그대로 다시 보내면 검증을 통과하므로, 논스·타임스탬프·시퀀스를 메시지에 포함해야 한다. ③ 태그 비교는 **상수 시간 비교**로 해야 타이밍 공격을 막는다.

## 연결 개념
- 해시 알고리즘(004) — HMAC의 내부 엔진, 일방향·충돌저항 성질을 위임받음
- 전자서명(008) — 부인방지가 필요할 때 HMAC 대신 개인키 서명으로 대체
- AEAD·GCM(001·029) — 암호화+무결성을 한 번에 처리하는 상위 대안(GMAC 내장)

# 📝 【답안용】 시험 답안 템플릿

## 핵심 인사이트 (3줄 요약)

> 1. **본질**: HMAC은 공유 비밀키를 해시에 이중으로 결합해 무결성과 송신자 인증을 동시에 제공하는 MAC임.
> 2. **가치**: `H(키‖메시지)`의 길이 확장 취약점을 이중 해시로 차단하며, TLS·IPsec·JWT·API 서명의 표준 인증 수단임.
> 3. **판단 포인트**: 부인방지·재전송 방어는 HMAC 범위 밖이므로 전자서명·논스와 조합하고, 키 관리와 상수 시간 비교가 안전성의 핵심임.

## 출제 의도 및 답안 포인트

| 출제 의도 | 반드시 짚을 핵심 | 감점 회피 포인트 |
|:---|:---|:---|
| MAC의 무결성+인증 원리와 순수 해시 대비 차별점 확인 | 이중 해시 구조(ipad·opad), 길이 확장 방어, 공유 비밀키, HMAC-SHA256 | 부인방지 가능으로 오기, 무결성·인증·기밀성 혼동, 재전송 방어 자동 가정 |

> 요약: HMAC 답안은 이중 해시로 길이 확장을 막는 원리와, 부인방지·재전송은 범위 밖임을 함께 짚어야 함.

## Ⅰ. 개요 및 필요성

- 개요: 공유 비밀키를 해시에 결합해 무결성+인증을 보증하는 메시지 인증 코드임
- 배경: 순수 해시(004)는 무결성만 보장하고, 단순 `H(키‖메시지)`는 머클담가드 길이 확장 공격에 취약함
- 필요성: 이중 해시로 길이 확장을 차단해 TLS·IPsec·JWT·API 요청의 위·변조와 위장 송신을 방어함

## Ⅱ. 구조 및 구성요소

선형 구조도:

```text
키(K) -> [K⊕ipad ‖ 메시지] -> H(내부) -> [K⊕opad ‖ 내부해시] -> H(외부) -> MAC 태그
```

| 구성요소 | 역할 | 특이사항 |
|:---|:---|:---|
| 공유 비밀키(K) | 인증의 근거, 송·수신 사전 공유 | KMS·HSM 보관, 주기적 로테이션 |
| 해시 함수 H | 확산·일방향 엔진 | SHA-256 이상 권장(004 참조) |
| ipad·opad | 키를 내·외부로 분리하는 패딩 상수 | 0x36·0x5c 반복, 이중 해시 유도 |
| MAC 태그 | 검증용 고정 길이 출력 | HMAC-SHA256=256b, 상수 시간 비교 |

> 요약: HMAC은 키를 ipad·opad로 나눠 내부·외부 해시로 중첩함으로써 길이 확장을 막고 인증 태그를 생성함.

## Ⅲ. 동작원리 및 흐름도

선형 흐름도:

```text
송신자: 키+메시지로 HMAC 계산 -> (메시지+태그) 전송
수신자: 받은 메시지로 HMAC 재계산 -> 태그 상수시간 비교 -> 일치 시 승인
```

1. 송신자가 공유 비밀키를 ipad와 XOR해 메시지 앞에 붙여 내부 해시를 계산함
2. 그 내부 해시 결과를 키⊕opad 뒤에 붙여 외부 해시를 계산해 최종 MAC 태그를 산출함
3. 송신자가 메시지와 태그를 함께 전송하고, 수신자가 같은 키로 태그를 재계산함
4. 수신자가 재계산 태그와 수신 태그를 상수 시간으로 비교해 일치하면 무결성·인증을 승인함

## Ⅳ. 특징

- 무결성+인증 동시 보장 — 키를 모르는 제3자는 유효 태그를 만들 수 없어 위장 송신을 차단함
- 길이 확장 공격 방어 — 이중(중첩) 해시로 머클담가드의 상태 이어받기를 원천 차단함
- 기반 해시 독립성 — 안전성이 키 비밀성에 의존해 기반 해시 약화에 상대적으로 견고함
- 대칭키 기반 경량성 — 전자서명 대비 연산이 가벼워 고빈도 트래픽 인증에 적합함
- 부인방지 불가 — 키를 양쪽이 공유하므로 생성 주체를 특정할 수 없어 서명과 역할이 다름

## Ⅴ. 심화 비교 및 적용 판단

- 무결성·인증·부인방지 요구가 어디까지인지에 따라 순수 해시·HMAC·전자서명 중 배치가 갈림.

| 구분 | 순수 해시(004) | HMAC | 전자서명(008) |
|:---|:---|:---|:---|
| 키 방식 | 키 없음 | 공유 대칭키 | 개인키·공개키 쌍 |
| 보장 범위 | 무결성 | 무결성+인증 | 무결성+인증+부인방지 |
| 연산 비용 | 최저 | 낮음 | 높음 |
| 대표 용도 | 체크섬·다이제스트 | TLS·JWT HS256·API 서명 | 코드서명·계약 문서 |

> 요약: 위·변조만 보면 해시, 상호 인증엔 HMAC, 제3자 대상 부인방지엔 전자서명을 선택함.

- 리스크 — 키 유출: 소스·환경변수 노출이 원인 → KMS·HSM 보관·정기 로테이션으로 대응
- 리스크 — 재전송 공격: 논스·타임스탬프 부재가 원인 → 메시지에 논스·유효시간 포함으로 대응
- 리스크 — 타이밍 공격: 조기 종료 비교가 원인 → 상수 시간 비교 함수 사용으로 대응

## Ⅵ. 실무 적용 및 결론

**적용 방안 3개:**
1. API 요청 인증: 요청 본문+타임스탬프+논스에 HMAC-SHA256 서명을 붙이고 서버가 상수 시간 검증함
2. 토큰 무결성: JWT는 HS256(HMAC) 또는 부인방지 필요 시 RS256(서명)으로 서명하고 키를 KMS로 관리함
3. 키 파생: 단일 마스터키에서 HKDF(HMAC 기반)로 용도별 키를 파생해 키 재사용을 차단함

**결론:**
- 조건부 판단: 상호 신뢰 양자 간 무결성·인증은 HMAC이 최적이나, 제3자 검증·부인방지가 필요하면 전자서명으로 전환해야 함
- 향후 방향: 재전송·세션 방어를 위해 논스·시퀀스를 병행하고, 신규 설계는 HMAC-SHA256 이상과 AEAD(GCM) 통합을 지향함
