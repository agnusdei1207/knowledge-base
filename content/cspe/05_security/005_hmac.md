# 📖 【암기용】 개념 완전 이해

## 한눈에
- **개요**: **해시 함수**와 **비밀키**를 결합하여 데이터의 **무결성(Integrity)**과 **인증(Authentication)**을 동시에 제공하는 메커니즘.
- **왜 필요한가**: 일반 해시는 누구나 계산할 수 있어 위·변조와 해시값 재계산에 취약함. HMAC은 비밀키를 가진 자만이 유효한 태그를 생성할 수 있게 하여 송신자의 신원을 증명함.
- **핵심 직관**: **"비밀 도장이 찍힌 지문"**. 지문(Hash)만 있는 것이 아니라, 두 사람만 아는 비밀 인장(Key)이 함께 찍혀 있어 제3자가 위조할 수 없음.

## 핵심 용어 정리

| 용어 | 의미 | 비유 |
|:---|:---|:---|
| **MAC** | Message Authentication Code. 메시지 인증 코드 | 편지 봉투의 밀봉 씰(Seal) |
| **I-Pad** | Inner Padding. 내부 해시를 위한 패딩 (0x36 반복) | 편지지를 감싸는 속 봉투 |
| **O-Pad** | Outer Padding. 외부 해시를 위한 패딩 (0x5c 반복) | 속 봉투를 다시 담는 겉 봉투 |
| **이중 해시** | 해시 함수를 두 번 중첩하여 계산하는 구조 | 보안을 위해 금고 안에 또 다른 금고를 넣는 방식 |
| **길이 확장 공격** | 메시지 뒤에 추가 데이터를 붙여 새로운 해시를 유도하는 공격 | 이미 봉인된 편지 하단에 몰래 글을 덧붙이는 행위 |

## 깊이 이해
- **수학적 공식**:
  $$HMAC(K, m) = H((K \oplus opad) \ || \ H((K \oplus ipad) \ || \ m))$$
  - 여기서 $H$는 SHA-256과 같은 해시 함수, $K$는 비밀키, $m$은 메시지임.
- **왜 중첩 해시를 쓰는가?**:
  - 단순히 $H(K \ || \ m)$으로 키를 앞에 붙이면, 머클-담가드 구조의 취약점으로 인해 키를 몰라도 $H(K \ || \ m \ || \ m')$을 유도할 수 있는 **길이 확장 공격(Length Extension Attack)**에 노출됨.
  - HMAC은 내부 해시 결과를 다시 외부 해시로 감쌈으로써 공격자가 내부 상태를 가로채지 못하게 원천 차단함.
- **보안의 근거**:
  - HMAC의 안전성은 기반이 되는 해시 함수의 충돌 저항성보다는 **비밀키의 기밀성**에 더 크게 의존함.
  - 따라서 기반 해시(예: SHA-1)에서 충돌이 발견되어도 HMAC-SHA1은 상대적으로 더 오래 안전성을 유지할 수 있었음 (현재는 SHA-256 권고).

## 연결 개념
- **004 해시 알고리즘**: HMAC의 엔진 역할을 수행.
- **008 전자서명**: 비대칭 키를 사용하여 부인방지까지 제공하는 기술.
- **096 OAuth 2.0**: API 요청 시 HMAC을 이용한 서명(Signature) 검증 활용.

# 📝 【답안용】 시험 답안 템플릿

## 핵심 인사이트 (3줄 요약)
> 1. **본질**: 공유 비밀키와 해시 함수를 중첩 결합하여 데이터 변조 방지 및 **송신자 인증**을 보장하는 대칭키 기반 기술임.
> 2. **가치**: 머클-담가드 구조의 **길이 확장 공격(LEA)**을 원천 차단하며, TLS·JWT·API 보안의 표준 인증 수단으로 활용됨.
> 3. **판단 포인트**: 부인방지 기능이 없음을 인지하고, 필요 시 전자서명으로 전환하거나 **재전송 공격(Replay Attack)** 방지를 위해 논스(Nonce)와 병행해야 함.

## 출제 의도 및 답안 포인트
- **출제 의도**: 단순 해시와의 차이점(인증 여부)과 이중 해시 구조를 통한 공격 방어 원리 이해도 확인.
- **감점 회피**: **I-Pad, O-Pad**를 활용한 수식을 기술하고, **상수 시간 비교(Constant-time Comparison)**를 통한 타이밍 공격 방어를 언급할 것.

---

## Ⅰ. 무결성과 인증의 결합, HMAC의 개요
### 1. 정의 및 개념
- RFC 2104에 정의된, 키가 있는 해시 함수를 이용한 메시지 인증 코드
- 데이터 기밀성이 아닌 **데이터의 진위(Authenticity)** 확인이 목적

### 2. 순수 해시(Hash) vs HMAC 비교
| 구분 | 해시 (Hash) | HMAC |
|:---|:---|:---|
| **키 사용** | 사용 안 함 | **공유 비밀키** 사용 |
| **보장 범위** | 무결성 (Integrity) | 무결성 + **인증 (Authentication)** |
| **공격 내성** | 위·변조 후 재해싱에 취약 | 키 없이는 유효한 태그 생성 불가 |
| **비유** | 데이터의 지문 | 비밀 인장이 찍힌 지문 |

---

## Ⅱ. HMAC의 구조 및 동작 원리
### 1. 이중 해시 메커니즘 (Two-pass Hash)
- **Step 1 (Inner Pass)**: 키 $K$를 $ipad$와 XOR 하여 메시지 앞에 붙이고 해싱 $\rightarrow$ 내부 결과 도출.
- **Step 2 (Outer Pass)**: 키 $K$를 $opad$와 XOR 하여 내부 결과 앞에 붙이고 다시 해싱 $\rightarrow$ 최종 HMAC 값.
- **효과**: 메시지 끝에 데이터를 추가해도 외부 해시 과정 때문에 전체 값이 완전히 달라져 LEA 공격 무력화.

### 2. 핵심 구성 요소
- **비밀키 ($K$)**: 송/수신자만 아는 대칭키. 길이는 해시 블록 크기와 맞추는 것이 권장됨.
- **I-Pad / O-Pad**: 키를 변형시켜 두 단계의 독립적인 해싱 과정을 유도하는 상수 (0x36 / 0x5c).
- **해시 엔진**: SHA-2, SHA-3 등 표준 해시 함수.

---

## Ⅲ. HMAC의 보안 위협 및 방어 전략
### 1. 길이 확장 공격 (Length Extension Attack) 방어
- 일반적인 $H(K \ || \ M)$ 방식은 공격자가 $H(K \ || \ M \ || \ M')$을 쉽게 생성 가능하나, HMAC은 중첩 구조를 통해 내부 해시의 상태 값을 노출하지 않음.

### 2. 타이밍 공격 (Timing Attack)
- **위협**: 서버가 HMAC 값을 비교할 때, 앞에서부터 틀린 부분이 나오면 즉시 리턴하는 시간 차를 이용해 한 바이트씩 알아내는 공격.
- **대응**: 전체 문자열을 끝까지 비교하는 **상수 시간 비교(Constant-time Comparison)** 로직 구현.

---

## Ⅳ. 주요 활용 분야 및 사례
### 1. API 요청 서명 (API Request Signing)
- AWS, Naver Cloud 등 클라우드 서비스의 REST API 호출 시 Access Key/Secret Key 기반의 인증 태그 생성.

### 2. JWT (JSON Web Token) - HS256
- 토큰의 페이로드(Payload)가 변조되지 않았음을 증명하기 위해 HMAC-SHA256 서명 사용.

### 3. HKDF (HMAC-based Key Derivation Function)
- 하나의 마스터 키로부터 여러 개의 용도별 키(암호화용, 인증용)를 안전하게 파생할 때 HMAC을 기반으로 사용.

---

## Ⅴ. HMAC vs 전자서명 (Digital Signature)
| 구분 | HMAC | 전자서명 |
|:---|:---|:---|
| **알고리즘** | 대칭키 기반 (AES/SHA) | 비대칭키 기반 (RSA/ECC) |
| **성능** | 매우 빠름 (고속 처리) | 상대적으로 느림 (연산 부하) |
| **부인방지** | **불가능** (공유키 방식) | **가능** (개인키 방식) |
| **적합 분야** | 세션 인증, 고속 API | 전자 계약, 공인 인증, 법적 효력 |

---

## Ⅵ. 실무적 적용 방안 및 결론
### 1. 안전한 HMAC 운영 가이드
- **키 관리**: 키는 HSM 또는 KMS에 보관하고 소스 코드 내 하드코딩 금지.
- **알고리즘**: SHA-1 기반 HMAC은 지양하고 **HMAC-SHA256** 이상을 표준으로 채택.
- **재전송 방지**: 메시지에 **Timestamp** 또는 **Nonce**를 포함하여 탈취된 요청의 재사용 방지.

### 2. 결론
- HMAC은 가볍고 강력한 인증 수단임. 부인방지가 필요 없는 대다수의 통신 구간에서 최적의 선택이며, **상수 시간 비교**와 **키 로테이션**을 통해 운영 보안을 완성해야 함.

### 🔀 문제 유형별 목차 전환
| 유형 | Ⅱ·Ⅲ 강조 (원리 중심) | Ⅴ·Ⅵ 강조 (전략 중심) |
|:---|:---|:---|
| **메커니즘 분석** | I-Pad/O-Pad 상세 수식, LEA 방어 논리 | 알고리즘 성능 벤치마크, 키 유도 함수(HKDF) 연계 |
| **시스템 보안 설계** | API 서명 프로세스 다이어그램 | JWT 보안 설정, 재전송 공격 차단 설계 |
