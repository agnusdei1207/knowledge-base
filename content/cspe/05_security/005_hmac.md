# 📖 【암기용】 개념 완전 이해

> 목적: HMAC을 처음 보는 사람도 완전하게 이해하게 만든다. 시험 답안 양식이 아니라, 이해를 위한 설명이다.

## 한눈에
- **개요**: 비밀키와 해시 함수를 결합해 메시지 무결성과 송신자 인증을 확인하는 코드
- **왜 필요한가**: 단순 해시는 누구나 계산할 수 있어 공격자가 메시지를 바꾸고 해시도 다시 만들 수 있다. HMAC은 비밀키를 모르면 올바른 태그를 만들 수 없게 함.
- **핵심 직관**: 문서 지문에 비밀 도장을 찍는 방식이다. 문서가 같아도 비밀 도장을 모르면 검증 가능한 표식을 만들 수 없음

## 깊이 이해
- **배경·문제의식**: API 요청, 웹훅, 쿠키, 메시지 큐는 변조 여부와 송신자 식별이 필요하다. 암호화는 기밀성을 제공하지만, HMAC은 평문 또는 암호문에 인증 태그를 붙여 무결성과 인증성을 제공함.
- **작동 원리**: 키를 블록 크기에 맞추고 ipad/opad와 XOR한 뒤 내부 해시와 외부 해시를 두 번 계산한다. 이 구조는 단순 `hash(key || message)`의 길이 확장 공격을 피하도록 설계됨.
- **비유**: 계약서 사본마다 담당자만 아는 인장 패턴을 찍어두는 방식이다. 글자가 바뀌거나 인장 패턴이 틀리면 접수자가 즉시 거부함.
- **구체 예시**: AWS Signature Version 4는 HMAC-SHA-256을 사용해 날짜·리전·서비스·요청 문자열에 대한 서명을 계산하고 API 요청 위조를 차단함.
- **흔한 오해·주의점**: HMAC은 암호화가 아니다. 메시지 내용은 그대로 보일 수 있으므로 기밀성이 필요하면 TLS 또는 AES-GCM과 함께 사용해야 함.

## 연결 개념
- 해시 알고리즘 — HMAC의 내부 압축 함수
- API 인증 — 요청 본문·timestamp·nonce에 대한 HMAC 검증
- AEAD — 암호화와 인증 태그를 하나의 모드에서 함께 제공

# 📝 【답안용】 시험 답안 템플릿

> 목적: 시험장에서 25분에 그대로 쓰는 답안 양식. 수치·표준명·기술명 중심으로 작성한다.

## 핵심 인사이트 (3줄 요약)

> 1. **본질**: HMAC은 비밀키와 해시 함수를 조합해 메시지 위변조와 송신자 보유 키를 검증하는 MAC 방식이다.
> 2. **가치**: API 서명, 웹훅 검증, 쿠키 무결성, 로그 체인에서 HMAC-SHA-256이 실무 표준으로 사용됨.
> 3. **판단 포인트**: 키 길이, timestamp·nonce, 상수시간 비교, SHA-256 이상 사용 여부가 안전한 구현의 기준임.

## 출제 의도 및 답안 포인트

| 출제 의도 | 반드시 짚을 핵심 | 감점 회피 포인트 |
|:---|:---|:---|
| API 위조·재전송·메시지 변조 위협을 공유키 통제, 태그 검증, 탐지 로그, 키 회전 복구와 연결하는 역량 확인 | HMAC-SHA-256, canonical request, timestamp 5분, nonce 1회 사용, constant-time compare, KMS 키 회전 | HMAC을 암호화로 설명, 부인방지 제공으로 오인, timestamp·nonce·상수시간 비교 누락 |

> 요약: HMAC 답안은 무결성과 송신자 인증을 제공하되 부인방지는 전자서명 영역임을 구분해야 한다.

---

## Ⅰ. 개요 및 필요성

- 개요: 비밀키 기반 메시지 인증
- 배경: 단순 해시는 누구나 재계산할 수 있어 메시지 변조 여부는 보여도 송신자 보유 키 검증은 제공하지 못함.
- 필요성: API·웹훅·메시지 큐는 HMAC-SHA-256 태그와 타임스탬프 검증으로 변조 요청·재전송 요청을 탐지함.

---

## Ⅱ. 구조 및 구성요소

```text
Secret Key -> Key Normalize -> ipad/opad
Message -> Inner Hash -> Outer Hash -> HMAC Tag
Receiver -> Recompute Tag -> Constant-Time Compare -> Accept/Reject
```

| 구성요소 | 역할 | 특이사항 |
|:---|:---|:---|
| 비밀키 | 송수신자 공유 인증 재료 | 128-bit 이상, KMS 보관 |
| 해시 함수 | 내부·외부 다이제스트 생성 | SHA-256 이상 권장 |
| 메시지 | 검증 대상 데이터 | method, path, body, timestamp 포함 |
| 인증 태그 | 위변조 판정값 | 상수시간 비교 필요 |

> 요약: HMAC은 비밀키를 해시 입력에 구조적으로 결합해 태그를 만들고, 수신자가 동일 계산으로 검증한다.

---

## Ⅲ. 동작원리 및 흐름도

```text
요청 생성 -> timestamp/nonce 추가 -> HMAC-SHA-256 태그 계산
-> 메시지와 태그 전송 -> 수신자 재계산 -> 상수시간 비교
-> timestamp/nonce 재사용 검사 -> 수락 또는 거부
```

| 단계 | 처리 내용 | 검증 기준 |
|:---:|:---|:---|
| 1 | 공유 비밀키 생성·배포 | 128-bit 이상 CSPRNG |
| 2 | canonical message 구성 | method·path·body hash 포함 |
| 3 | HMAC-SHA-256 계산 | SHA-1 제외, 태그 길이 256-bit |
| 4 | 태그·시간·nonce 검증 | 허용 시간창 5분, 재사용 0건 |

> 요약: HMAC 검증은 태그 재계산뿐 아니라 canonicalization, 시간창, nonce 중복 차단까지 포함해야 한다.

---

## Ⅳ. 특징

| 구분 | 내용 | 판단 포인트 |
|:---|:---|:---|
| 장점 | 무결성과 송신자 키 보유 검증 | API 요청 위조 탐지 |
| 한계 | 기밀성 제공 안 함 | TLS·AES와 병행 필요 |
| 비교 대상 | 단순 해시·전자서명 | 공유키 내부 시스템은 HMAC, 제3자 검증은 전자서명 |

> 요약: HMAC은 공유키 기반 인증에는 적합하나, 공개 검증과 부인방지는 전자서명이 담당한다.

## Ⅴ. 심화 비교 및 적용 판단

| 구분 | 기존/대안 | 본 키워드 | 선택 기준 |
|:---|:---|:---|:---|
| 구조 | `hash(message)` | `HMAC(key, message)` | 송신자 인증 필요 시 HMAC |
| 비용/성능 | 전자서명 | HMAC-SHA-256 | 내부 API, 초당 요청 수 1,000건 이상 |
| 운영/위험 | 공유키 수동 배포 | KMS·키 ID·회전 정책 | 서비스 간 키 분리 필요 |

> 요약: 내부 시스템과 웹훅 검증은 HMAC, 외부 공개 검증과 부인방지는 전자서명을 선택한다.

| 리스크 | 원인 | 대응 방안 | 확인 지표 |
|:---|:---|:---|:---|
| 재전송 공격 | timestamp·nonce 누락 | 5분 시간창, nonce 저장 | nonce 재사용 0건 |
| 비교 우회 | 일반 문자열 비교 | constant-time compare | timing leak 테스트 통과 |
| 키 유출 | 소스코드·환경변수 노출 | KMS, 키 ID, 90일 회전 | secret scan 탐지 0건 |

> 요약: HMAC 운영 리스크는 재전송, timing leak, 키 노출이며 시간창·상수시간 비교·KMS로 통제한다.

| 점검 항목 | 목표 기준 | 측정 방법 |
|:---|:---|:---|
| 알고리즘 | HMAC-SHA-256 이상, SHA-1 제외 | 코드·API 게이트웨이 설정 |
| 요청 검증 | timestamp 5분 이내, nonce 1회 사용 | Redis·DB nonce 로그 |
| 키 관리 | 키 90일 회전, 서비스별 분리 | KMS 정책·감사로그 |

> 요약: 적용 성공 여부는 SHA-256 사용, 재전송 차단, 키 회전과 서비스별 키 분리로 판단한다.

## Ⅵ. 실무 적용 및 결론

**적용 방안 3개 (필수 — 단계별 또는 항목별):**
1. API 서명: method, path, query, body hash, timestamp, nonce를 canonical string으로 만들고 HMAC-SHA-256 태그 생성
2. 검증 로직: 수신자는 동일 canonical string으로 태그 재계산, constant-time compare 사용, timestamp 5분 초과 요청 거부
3. 키 운영: 서비스별 secret key 분리, key ID로 회전 지원, KMS 보관과 90일 회전 정책 적용

**결론 (2줄):**
- 기술사 판단: 내부 API·웹훅은 HMAC-SHA-256, 제3자 공개 검증과 부인방지는 ECDSA·RSA 서명을 선택해야 함
- 향후 방향: API Gateway와 Service Mesh에서 HMAC 검증, mTLS, OAuth 2.0 sender-constrained token을 요구 수준별로 조합해야 함
