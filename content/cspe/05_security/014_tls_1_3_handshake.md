## 1. 한눈에 이해하기 (Core Intuition)
- **정의**: 기존 TLS 1.2의 불필요한 기능과 오래된 암호 방식을 전부 덜어내고, **'속도(성능)'와 '안전성(보안)'** 이라는 두 마리 토끼를 완벽하게 잡아낸 최신 네트워크 보안 표준(RFC 8446, 2018년 제정)입니다.
- **필요성**: 기존 TLS 1.2는 모바일 환경에서 통신을 시작할 때 주고받는 횟수(왕복 지연, RTT)가 많아 로딩이 느렸고, 해커들에게 털릴 여지가 있는 낡은 암호화 방식들을 너무 많이 지원하고 있었습니다.
- **핵심 직관**: **"다이어트와 스피드업"**. TLS 1.2가 온갖 무기와 짐(레거시 암호)을 주렁주렁 매단 무거운 장갑차였다면, TLS 1.3은 낡고 위험한 무기는 싹 다 버리고(보안 강화), 시동 걸 때 걸리던 복잡한 확인 절차를 한 번으로 줄인(1-RTT) 최첨단 스텔스 스포츠카입니다.

## 2. 왜 중요한가? (Background & Value)
- **등장 배경**: 구글, 클라우드플레어 등 인터넷 공룡들이 모바일 웹 로딩 속도를 밀리초 단위로 단축하기 위해 10년 만에 프로토콜을 통째로 뜯어고쳤습니다.
- **가치**: 모바일 환경에서 눈에 띄게 웹사이트 로딩이 빨라집니다. 동시에, 서버가 해킹당해 개인키가 털려도 과거의 통신 내역은 절대 해독할 수 없는 완벽한 방어막(PFS)을 강제합니다. 현존하는 가장 안전하고 효율적인 인터넷 인프라의 최종 완성형입니다.

## 3. 어떻게 작동하는가? (Mechanism)
- **핵심 변화 1: 1-RTT 핸드셰이크 (속도 혁명)**
  - 기존 1.2는 "어떤 암호 쓸까?"(왕복 1번) $\rightarrow$ "내 인증서와 키 받을 준비 해"(왕복 1번) 등 총 **2번의 왕복(2-RTT)** 후에야 실제 데이터 전송이 시작되었습니다.
  - TLS 1.3은 "어떤 암호 쓸지 몰라서 최신 유행 키 교환 값(Key Share)을 인사할 때 아예 미리 보내버려!" 방식을 씁니다. 단 **1번의 왕복(1-RTT)** 만에 즉시 암호화 데이터를 주고받습니다. (연결 시간 50% 단축)
  - 심지어 한 번 방문했던 사이트면 인사조차 생략하고 바로 데이터를 암호화해 쏘는 **0-RTT (Zero Round Trip Time)** 기능도 생겼습니다.

- **핵심 변화 2: 레거시 퇴출과 PFS 강제 (보안 혁명)**
  - 구식 암호들(MD5, SHA-1, RC4, DES)과 취약한 모드(CBC 모드)를 싹 다 금지했습니다. 오직 최고로 안전한 AEAD 암호 모드(AES-GCM, ChaCha20 등)만 남겼습니다.
  - 특히, **RSA 키 교환을 완전히 퇴출**시켰습니다. 무조건 '매번 새로운 난수 키를 생성하는' **(EC)DHE 키 교환**만 사용하도록 강제하여, 서버 개인키가 털려도 과거 데이터가 해독되지 않는 **PFS(완전 순방향 안전성)** 를 달성했습니다.

```ascii
[ TLS 1.2 (2-RTT) ]                    [ TLS 1.3 (1-RTT) ]
Client            Server               Client            Server
  │─── Client Hello ─▶│                  │── Client Hello ─▶│ (인사 + 키교환값 미리 던짐)
  │◀── Server Hello ──│                  │◀─ Server Hello ──│ (인사 + 내 키교환값 + 인증서)
  │                   │                  │   (Handshake 완료)
  │── Key Exchange ──▶│                  │                  │
  │◀── Change Cipher ─│                  │◀── Application ──│
  │   (Handshake 완료)                   │    Data 전송      │
  │                   │
  │── Application ───▶│                  ※ 절반의 시간으로 초고속 연결 성립!
      Data 전송
```

## 4. 실전 활용 및 예시 (Real-world Application)
- **구체적 사례**: 
  - 현재 크롬, 엣지, 사파리 등 모든 모던 브라우저와 클라우드플레어, AWS, 네이버 등 주요 인프라는 전부 TLS 1.3을 기본으로 통신하고 있습니다.
  - IoT 기기 환경에서도 연결 오버헤드가 극적으로 줄어들어 배터리 소모가 크게 절약됩니다.
- **주의점 및 흔한 오해**: 
  - 보안 감사를 수행하는 기업의 보안 장비(IPS/IDS, 패킷 감청 장비) 입장에서는 비상입니다. TLS 1.2까지는 회사 서버의 RSA 개인키만 장비에 넣어두면 임직원들의 트래픽을 풀어볼 수 있었으나, TLS 1.3은 키 교환이 DHE로 이루어져 트래픽 해독(Out-of-Band 복호화)이 불가능해집니다. 별도의 프록시 해독(MITM) 아키텍처 재설계가 필요합니다.

## 5. 핵심 비교 및 연결 개념 (Relation)
- **TLS 1.2 vs 1.3**: 1.2는 "옵션이 너무 많은 뷔페(보안 구멍 많음)", 1.3은 "검증된 메뉴만 파는 단일 메뉴 맛집(안전하고 빠름)".
- **연결 개념**: 
  - **SNI 암호화 (ESNI / ECH)**: TLS 1.3에서 새롭게 도입 중인 기술로, 핸드셰이크 첫 단계에서 서버 이름(도메인)이 평문으로 노출되던 것마저 암호화하여 ISP(통신사)가 사용자의 접속 사이트를 엿볼 수 없게 만드는 궁극의 프라이버시 기술.

# ✍️ 단답형 / 서술형 시험장 출격 준비

### Ⅰ. 핵심 인사이트
- **본질**: 암호 스위트의 대폭적인 간소화(다이어트)와 `Key Share` 확장을 통한 1-RTT 핸드셰이크를 구현한 차세대 전송 계층 보안 프로토콜.
- **가치**: 모바일 환경의 지연 시간(Latency) 최소화와 함께, 취약한 레거시 암호를 제거하고 PFS(Perfect Forward Secrecy)를 프로토콜 아키텍처 레벨에서 강제함으로써 궁극의 안전성을 달성.
- **판단 포인트**: 기존 RSA 정적 키를 이용한 네트워크 보안 장비의 OOB(Out-of-Band) 패킷 감청 기능이 무력화되므로, 엔터프라이즈 환경 도입 시 Forward Proxy 기반의 가시성 확보 아키텍처 재검토가 수반되어야 함.

### Ⅱ. TLS 1.3의 3대 핵심 아키텍처 변화
**1. 성능 혁신: 1-RTT 및 0-RTT 핸드셰이크**
- **1-RTT**: `Client Hello` 단계에서 클라이언트가 지원하는 키 교환 매개변수(Diffie-Hellman Key Share)를 추측하여 미리 함께 전송함. 서버가 이를 수락하면 즉시 `Server Hello`와 함께 세션키가 도출되어, 단 한 번의 왕복으로 핸드셰이크가 종료됨.
- **0-RTT (Early Data)**: 이전 세션에서 서버가 발급해 준 PSK(Pre-Shared Key) 티켓을 클라이언트가 보유하고 있다면, 최초의 `Client Hello`에 바로 암호화된 애플리케이션 데이터를 실어 보내는 무지연 통신 기술. (단, Replay Attack에 취약할 수 있어 멱등성 있는 GET 요청에만 제한적 사용 권장).

**2. 보안 혁신: 레거시 제거 및 암호 스위트 간소화**
- **취약한 알고리즘 완전 폐기**: MD5, SHA-1, RC4, DES, 3DES 등 폐기.
- **취약한 운영 모드 폐기**: MAC-then-Encrypt 방식 및 CBC 모드 전면 금지. **오직 AEAD (AES-GCM, ChaCha20-Poly1305, AES-CCM)만 허용.**
- **암호 스위트 표현 단순화**: 기존 `TLS_키교환_서명_WITH_암호화_해시` 구조에서 키교환/서명이 독립적으로 협상되므로, `TLS_AES_256_GCM_SHA384` 형태로 대폭 단순화됨 (현재 총 5개 스위트만 표준 정의).

**3. 아키텍처 혁신: PFS 의무화 (RSA 키 교환 퇴출)**
- 기존 TLS 1.2까지 널리 쓰이던 서버 인증서의 RSA 개인키를 이용한 세션키 암호화(Key Transport) 방식을 완전히 금지.
- 매 세션마다 임시 난수를 사용하는 **(EC)DHE (Ephemeral Diffie-Hellman) 키 교환 방식만을 강제**하여, 완벽한 순방향 안전성(Perfect Forward Secrecy) 보장.

### Ⅲ. 프라이버시 강화: 핸드셰이크 메시지 암호화 및 ECH
- 기존 TLS 1.2는 `Server Hello` 이후의 인증서(Certificate) 전달 단계가 평문으로 전송되어 도청 시 서버 신원이 노출됨. TLS 1.3은 `Server Hello` 직후 세션키가 도출되므로, **인증서 교환 등 나머지 모든 핸드셰이크 과정을 암호화**하여 전송.
- **ECH (Encrypted Client Hello, 구 ESNI)**: 1.3의 핵심 확장. 클라이언트가 접속하려는 호스트 이름(SNI)은 `Client Hello`에 평문으로 담겨 통신사가 차단(예: 불법 사이트 차단)이나 감시를 할 수 있었으나, ECH는 DNS를 통해 서버의 퍼블릭 키를 알아내어 이 SNI 정보까지 완전히 암호화(Inner Client Hello)해버리는 궁극의 프라이버시 보호 기술.

### Ⅳ. 엔터프라이즈 환경 도입 시 문제점과 해결 방안
- **이슈 (가시성 상실)**: 기업 망 내에 설치된 IDS/IPS나 WAF, DLP 같은 수동적(Passive) 네트워크 감청 장비들은 그동안 서버의 RSA 개인키를 복사해두고 트래픽을 훔쳐보는 Out-of-Band(OOB) 방식으로 작동했음. TLS 1.3의 PFS 강제화로 인해 이 방식이 완전히 무력화됨.
- **해결 방안 (In-Line Proxy 아키텍처 전환)**: 
  - 트래픽 경로 중간에 **SSL/TLS Forward Proxy(또는 NGFW)** 를 인라인(In-Line)으로 배치.
  - Proxy가 클라이언트와 서버 사이에서 2개의 개별 TLS 세션을 맺는 중간자(MITM) 역할을 합법적으로 수행(기업 내부 Root CA 배포 필요)하여 평문 페이로드를 검사 후 재암호화하는 아키텍처로 전면 개편.

### Ⅵ. 결론 및 향후 전망 (실무적 판단 포인트)
- 구글과 주요 클라우드 사업자의 드라이브로 TLS 1.3 마이그레이션이 이미 주류로 정착함. IT 시스템 설계 시, 레거시 클라이언트 호환성을 핑계로 RSA 키 교환을 남겨두는 것은 기술 부채이자 심각한 보안 리스크임.
- **양자 컴퓨터 대응 로드맵**: TLS 1.3 아키텍처는 이미 PQC(양자 내성 암호) 도입을 위한 확장성을 염두에 두고 설계되었으며, 현재 Google 등은 ML-KEM(Kyber)과 기존 X25519(ECC)를 결합한 **PQC 하이브리드 키 교환(X25519Kyber768Draft00)** 을 TLS 1.3 상에서 실서비스에 적용 테스트 중.

### 💡 문제 유형별 목차 전환 포인트
- **[TLS 1.2와 TLS 1.3 비교 중심 유형]**: Ⅱ번의 1-RTT와 PFS 강제화를 전면에 내세우고, 연결 속도 향상과 보안(제거된 기능 목록) 관점에서 표 형식으로 극적인 대비를 이끌어냄.
- **[네트워크 가시성/보안 장비 무력화 대응]**: Ⅳ번 항목을 강조하여, "보안이 강화되어 역설적으로 기업의 보안 감시가 불가능해지는 문제"와 해결책(In-Line SSL Decryption)을 심층 논의.
