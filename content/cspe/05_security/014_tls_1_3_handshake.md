## 미리 알고가기

- 1-RTT: 클라이언트와 서버가 한 번 왕복한 뒤 애플리케이션 데이터를 보낼 수 있는 절차임
- 0-RTT: 이전 세션 정보를 이용해 첫 메시지에 조기 데이터를 싣는 방식임
- PFS: 장기 개인키 유출 후에도 과거 세션키 복구를 어렵게 하는 성질임
- AEAD: 암호화와 무결성 태그를 함께 제공하는 대칭 암호 모드임
- PSK: 이전 세션이나 사전 공유 정보로 재개 핸드셰이크에 쓰는 키 재료임

## Ⅰ. 개요

- **정의/개념**: TLS 1.3 핸드셰이크는 레거시 암호군을 줄이고 임시 키 교환과 AEAD 중심으로 세션키를 도출하는 절차임
- **배경/필요성**: TLS 1.2의 선택지가 많을수록 취약 조합과 설정 오류가 늘어남. 협상 절차와 암호군을 단순화할 필요가 있음

## Ⅱ. 특징

- 보통 1-RTT로 서버 인증과 키 교환을 완료함
- RSA 키 교환과 CBC 계열 조합을 제거함
- ECDHE 등 임시 키 교환으로 PFS를 기본 절차에 포함함
- 0-RTT는 재전송 공격 위험 때문에 멱등 요청 중심으로 제한함

## Ⅲ. 종류 및 비교

| 구분 | TLS 1.2 | TLS 1.3 |
|:---|:---|:---|
| 기본 RTT | 보통 2-RTT | 보통 1-RTT |
| 키 교환 | RSA, DHE, ECDHE 등 선택 | 임시 DH 계열 중심 |
| 암호 모드 | CBC와 AEAD 혼재 | AEAD 중심 |
| PFS | 암호군 선택에 의존 | 기본 핸드셰이크에 포함 |
| 조기 데이터 | 없음 | 0-RTT 가능, 재전송 위험 관리 필요 |

> 요약: TLS 1.3의 판단 기준은 “빠름”이 아니라 왕복 절차 축소와 취약 암호군 제거임.

## Ⅳ. 구성요소 및 구조

| 메시지 | 역할 |
|:---|:---|
| ClientHello | 지원 그룹, 키 공유값, 확장, PSK 제안 |
| ServerHello | 선택 그룹과 서버 키 공유값 전달 |
| EncryptedExtensions | 협상된 확장 정보를 암호화해 전달 |
| Certificate·CertificateVerify | 서버 인증서와 서명 검증 정보 |
| Finished | 핸드셰이크 무결성 확인 |

```text
ClientHello(+key_share) ->
<- ServerHello(+key_share), EncryptedExtensions, Certificate, Finished
Finished ->
<====== Application Data ======>
```

## Ⅴ. 원리 및 절차 흐름도

1. **ClientHello**: 클라이언트가 키 공유값과 지원 파라미터를 보냄
2. **ServerHello**: 서버가 그룹을 선택하고 키 공유값을 반환함
3. **키 도출**: 양측이 공유 비밀과 transcript hash로 트래픽 키를 만듦
4. **서버 인증**: 인증서와 CertificateVerify로 서버 신원을 확인함
5. **Finished 검증**: 핸드셰이크 메시지 변경 여부를 확인하고 데이터 전송을 시작함

## Ⅵ. 실무 적용 및 유의점

- 0-RTT 데이터는 재전송 가능성이 있어 결제·상태 변경 요청에 쓰지 않음
- 중간 장비의 패시브 복호화 방식은 PFS 때문에 TLS 1.3에서 동작하지 않음
- 인증서, SNI, ALPN, ECH 지원 여부가 배포 호환성에 영향을 줌
- TLS 1.2 병행 운영 시 취약 암호군을 명시적으로 제외해야 함
- 세션 티켓 키는 재개 연결 보안에 영향을 주므로 주기적으로 교체함

## Ⅶ. 결론

- TLS 1.3은 핸드셰이크 절차와 암호군 선택지를 줄여 설정 오류와 왕복 지연을 줄인 버전임
- 답안에서는 버전 수식어가 아니라 1-RTT, PFS, AEAD, 0-RTT 위험을 기준으로 설명해야 함

## 작성 근거(검토용)

- 기존 문서의 과장된 비유와 단정 표현을 제거하고 RFC 절차 중심으로 재작성함
- 속도 표현은 1-RTT라는 절차 변화로 바꿔 문맥에 맞는 단어를 사용함
- 0-RTT는 장점만 쓰지 않고 재전송 공격 조건을 함께 배치함
