# 📖 【암기용】 개념 완전 이해

> 목적: XSS를 처음 봐도 완벽히 이해하게 만든다. 시험 답안 양식이 아니라, 이해를 위한 친절한 설명이다.

## 한눈에
- **개요**: 사용자의 브라우저에서 공격자 스크립트가 실행되는 웹 취약점
- **왜 필요한가**: 브라우저는 같은 출처의 스크립트를 신뢰하므로, 게시글·검색어·URL 조각에 삽입된 스크립트가 세션 쿠키, 화면 DOM, 사용자 행위를 악용할 수 있다.
- **핵심 직관**: 서버가 사용자 입력을 "글자"로 다루지 않고 "실행할 코드"로 브라우저에 건네는 순간 발생함.

## 깊이 이해
- **배경·문제의식**: 웹 화면은 HTML, CSS, JavaScript가 섞여 렌더링된다. 입력값을 HTML 본문, 속성, URL, JavaScript 문자열에 그대로 넣으면 브라우저는 이를 데이터가 아니라 코드 문맥으로 해석한다.
- **작동 원리**: Stored XSS는 DB에 저장된 입력이 여러 사용자에게 재생되고, Reflected XSS는 요청 파라미터가 즉시 응답에 반사되며, DOM XSS는 서버 응답 없이 클라이언트 JavaScript가 `location`, `innerHTML` 같은 sink에 값을 넣을 때 발생한다.
- **비유**: 안내문 게시판에 종이를 붙여야 하는데, 누군가 방송실 마이크 명령서를 붙여두면 안내문을 읽는 사람이 아니라 방송 설비가 명령을 실행하는 상황임.
- **구체 예시**: 댓글 1건에 삽입된 스크립트가 관리자 브라우저에서 실행되면 `HttpOnly` 미적용 쿠키, CSRF 토큰 DOM 값, 관리자 전용 API 호출이 노출될 수 있다.
- **흔한 오해·주의점**: 입력 필터링만으로 끝나지 않는다. HTML 본문·속성·URL·JavaScript 문맥별 출력 인코딩과 CSP, 쿠키 속성, DOM sink 제거가 함께 필요하다.

## 연결 개념
- CSP(Content Security Policy) — 스크립트 실행 출처와 인라인 실행을 제한
- 쿠키 보안 속성 — `HttpOnly`, `Secure`, `SameSite`로 세션 탈취와 요청 남용 범위 축소
- DOM 기반 취약점 — 클라이언트 코드의 sink 관리가 핵심

# 📝 【답안용】 시험 답안 템플릿

> 목적: 시험장에서 25분에 그대로 쓰는 답안 양식. 작성방식(추상표현 금지·수치·도식·문제유형 전환)을 엄격히 지킨다.
> 핵심: XSS 답안은 payload 나열이 아니라, 입력이 어느 출력 문맥에서 코드화되는지와 방어 코딩 위치를 연결해야 한다.

## 핵심 인사이트 (3줄 요약)

> 1. **본질**: XSS는 신뢰되지 않은 입력이 브라우저 실행 문맥으로 삽입되어 사용자 세션·DOM·권한을 악용하는 취약점이다.
> 2. **가치**: Stored, Reflected, DOM 유형을 구분하면 저장소·응답 생성부·클라이언트 sink 중 방어 위치를 특정할 수 있다.
> 3. **판단 포인트**: 문맥별 출력 인코딩, CSP, `HttpOnly/SameSite` 쿠키, 위험 sink 제거를 함께 설계해야 재현 테스트와 로그 검증이 가능하다.

## 출제 의도 및 답안 포인트

| 출제 의도 | 반드시 짚을 핵심 | 감점 회피 포인트 |
|:---|:---|:---|
| 웹 취약점 분류 역량 확인 | Stored, Reflected, DOM XSS와 발생 위치 구분 | alert payload 예시만 나열하고 취약 위치를 빠뜨림 |
| 방어 코딩 판단 확인 | HTML·속성·URL·JavaScript 문맥별 출력 인코딩 | 입력 필터링 하나로 방어 가능하다고 단정 |
| 운영 통제 연결 확인 | CSP report-uri, 쿠키 `HttpOnly/SameSite`, WAF 탐지 로그 | 세션 경계와 탐지 지표 누락 |

> 요약: XSS는 스크립트 문자열 문제가 아니라 출력 문맥, 세션 경계, 브라우저 정책을 함께 묻는 문제이다.

## Ⅰ. 개요 및 필요성

- 개요: 브라우저 스크립트 실행 취약점
- 배경: 사용자 입력이 HTML 응답이나 DOM sink에 검증 없이 삽입되면 동일 출처 권한으로 JavaScript가 실행되어 세션·화면·요청 흐름이 변조될 수 있음.
- 필요성: OWASP ASVS, context-aware output encoding, HttpOnly·SameSite 쿠키, CSP를 적용해 저장형·반사형·DOM XSS를 출력 단계에서 통제해야 함.

---

## Ⅱ. 구조 및 구성요소

```text
User Input -> Storage/Response/DOM Source -> Output Context -> Browser Execution
              / Stored DB
              / Reflected Parameter
              / DOM Source to Sink
Defense -> Context Encoding -> CSP -> Cookie Attribute -> Log Review
```

| 구성요소 | 역할 | 특이사항 |
|:---|:---|:---|
| 입력 지점 | 댓글, 검색어, URL fragment, HTTP header 수신 | 신뢰 경계 밖 데이터 |
| 출력 문맥 | HTML 본문, 속성, URL, JavaScript 문자열 | 문맥별 인코딩 규칙 상이 |
| 실행 환경 | 브라우저 DOM과 동일 출처 권한 | 세션 쿠키와 API 호출 권한 보유 |
| 방어 정책 | OWASP Encoder, CSP, 쿠키 속성 | 코드 위치와 브라우저 정책 병행 |

> 요약: XSS 구조는 입력 자체보다 출력 문맥과 브라우저 실행 권한을 함께 봐야 취약 위치가 식별된다.

## Ⅲ. 동작원리 및 흐름도

```text
입력 수신 -> 저장 또는 응답 반사 -> 문맥 미분리 출력 -> 브라우저 코드 실행
-> 세션/DOM 접근 -> API 요청 또는 화면 위변조 -> CSP/WAF/감사로그 확인
```

| 단계 | 처리 내용 | 검증 기준 |
|:---:|:---|:---|
| 1 | 입력값이 서버 저장소, 응답 템플릿, DOM source에 유입 | 입력 지점 목록 100% 식별 |
| 2 | 템플릿 엔진 또는 JavaScript가 값을 출력 | HTML·속성·URL·JS 문맥 분류 |
| 3 | 브라우저가 문자열을 스크립트로 해석 | CSP violation report 발생 여부 |
| 4 | 세션 쿠키, DOM 토큰, 사용자 권한 API가 악용 | `HttpOnly`, `SameSite=Lax/Strict`, 감사로그 확인 |

> 요약: XSS 흐름은 유입, 출력 문맥, 브라우저 실행, 세션 악용 순서로 분석한다.

|:---|:---|:---|:---|

| 세션 경계 | 일반 쿠키 | `HttpOnly`, `Secure`, `SameSite=Lax/Strict` | 쿠키 탈취·자동 요청 범위 축소 |

> 요약: XSS 대응은 필터링이 아니라 출력 인코딩, CSP, 쿠키 속성, DOM sink 제거의 조합이다.

## Ⅴ. 심화 비교 및 적용 판단

| 구분 | 기존/대안 | 본 키워드 | 선택 기준 |
|:---|:---|:---|:---|
| 취약 위치 | 서버 입력 검증 중심 | 저장소·응답·DOM sink별 분석 | Stored는 DB, Reflected는 응답, DOM은 클라이언트 코드 점검 |
| 비용/성능 | WAF 규칙 의존 | 템플릿 자동 escape와 CSP 병행 | false positive 5% 이하, CSP report 추적 |
| 운영/위험 | 배포 후 수동 점검 | SAST, DAST, CSP report 자동 수집 | 릴리스마다 XSS 회귀 테스트 수행 |

> 요약: XSS는 WAF보다 코드 문맥별 인코딩과 자동 회귀 테스트를 우선 적용한다.

| 리스크 | 원인 | 대응 방안 | 확인 지표 |
|:---|:---|:---|:---|
| Stored XSS | 게시글·프로필 값 DB 저장 후 재노출 | 저장값 출력 시 OWASP Java Encoder 적용 | 취약 URL 재검증 0건 |
| DOM XSS | `innerHTML`, `document.write` 사용 | `textContent`, 안전 템플릿 API로 교체 | 위험 sink 사용 건수 0건 |
| CSP 우회 | 인라인 스크립트와 외부 CDN 허용 | nonce 기반 CSP, allowlist 최소화 | CSP violation 월별 추세 |

> 요약: 주요 리스크는 저장형 재노출, DOM sink, CSP 예외 확대이며 코드 위치별 지표로 통제한다.

| 점검 항목 | 목표 기준 | 측정 방법 |
|:---|:---|:---|
| 출력 인코딩 | 템플릿 출력 지점 100% 자동 escape | SAST rule, 코드 리뷰 체크리스트 |
| 브라우저 정책 | CSP report critical 0건 | CSP report endpoint, SIEM 연계 |
| 세션 보호 | 인증 쿠키 `HttpOnly Secure SameSite` 100% 적용 | Set-Cookie 헤더 스캔 |

> 요약: 도입 후 성공 여부는 출력 지점, CSP 위반, 쿠키 속성 적용률로 확인한다.

## Ⅵ. 실무 적용 및 결론

**적용 방안 3개 (필수 — 단계별 또는 항목별):**
1. 서버 렌더링: HTML 본문·속성·URL·JavaScript 문맥별 encoder 적용, 템플릿 자동 escape 기본값 유지
2. 클라이언트 코드: `innerHTML`, `outerHTML`, `document.write` 제거, DOMPurify 적용 시 allowlist 정책과 버전 CVE 점검
3. 운영 통제: CSP nonce, `HttpOnly/SameSite` 쿠키, DAST 회귀 테스트, CSP report와 WAF 로그를 SIEM에 연계

**결론 (2줄):**
- 기술사 판단: 서버 렌더링 화면은 출력 인코딩 우선, SPA는 DOM sink 제거와 CSP nonce를 우선 적용함
- 향후 방향: 브라우저 보안 정책과 프레임워크 자동 escape를 전제로, 릴리스 파이프라인에서 XSS 재현 테스트를 자동화함
