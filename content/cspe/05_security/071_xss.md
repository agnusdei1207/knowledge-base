## 미리 알고가기

- XSS는 악성 스크립트가 서버가 아닌 사용자 브라우저에서 실행되게 만드는 공격임
- 원인은 사용자 입력이나 외부 데이터가 적절한 인코딩 없이 HTML이나 DOM에 삽입되는 데 있음
- 방어의 핵심은 입력 필터보다 출력 위치에 맞는 인코딩과 안전한 DOM 조작 방식임

## Ⅰ. 개요

- **정의/개념**: XSS는 웹 애플리케이션이 신뢰할 수 없는 데이터를 HTML, 스크립트, 속성, DOM에 그대로 반영해 사용자 브라우저에서 공격자 스크립트가 실행되게 만드는 클라이언트 측 공격임
- **배경/필요성**: 브라우저 세션과 사용자 입력이 웹 서비스의 핵심이기 때문에 스크립트 실행이 허용되면 세션 탈취, 피싱, 화면 변조, 악성 요청 전송으로 바로 이어질 수 있음

## Ⅱ. 특징

- 서버 저장형과 반사형과 DOM 기반처럼 발생 지점이 다를 수 있음
- 피해는 서버 직접 침해보다 사용자의 세션과 화면 신뢰를 깨는 쪽에 집중됨
- 입력 검증만으로는 HTML 문맥과 자바스크립트 문맥 차이를 모두 막기 어려움
- CSP와 HttpOnly 쿠키는 피해 축소에 도움을 주지만 출력 인코딩 실패 자체를 대신하지 못함

## Ⅲ. 종류 및 비교

| 판단 기준 | Stored XSS | Reflected XSS |
|:---|:---|:---|
| 삽입 위치 | DB나 게시물처럼 서버에 저장됨 | 요청 파라미터나 URL에 포함됨 |
| 피해 범위 | 다수 사용자에게 반복 노출 가능 | 특정 링크를 연 사용자 중심 |
| 탐지 포인트 | 저장 데이터와 렌더링 결과 점검 | 요청-응답 반영 구간 점검 |
| 공통 대응 | 출력 인코딩, 안전한 템플릿, CSP 적용 | 출력 인코딩, 안전한 템플릿, CSP 적용 |

## Ⅳ. 구성요소 및 구조

| 구성요소 | 설명 |
|:---|:---|
| 입력 또는 외부 데이터 | 사용자 글, URL 파라미터, API 응답 등 신뢰할 수 없는 데이터임 |
| 렌더링 지점 | HTML 본문, 속성, 스크립트 블록, DOM 조작 코드가 포함됨 |
| 브라우저 실행 환경 | 세션 쿠키, 사용자 권한, 화면 컨텍스트를 가진 실제 실행 위치임 |
| 방어 통제 | 출력 인코딩, DOM sanitization, CSP, HttpOnly가 포함됨 |

```text
비신뢰 입력 -> 페이지/DOM 반영 -> 브라우저 렌더링 -> 스크립트 실행 -> 세션/화면 악용
```

## Ⅴ. 원리 및 절차 흐름도

```text
악성 입력 삽입 -> 서버 또는 DOM 반영 -> 사용자 브라우저 로드 -> 스크립트 실행 -> 피해 발생
```

1. **악성 입력 삽입**: 공격자가 스크립트나 이벤트 핸들러를 포함한 값을 전달함
2. **반영 지점 통과**: 애플리케이션이 인코딩 없이 값을 HTML이나 DOM에 넣음
3. **브라우저 로드**: 피해자 브라우저가 응답이나 클라이언트 코드를 해석함
4. **스크립트 실행**: 세션 탈취, 화면 변조, 피싱 유도, 악성 요청 발생이 이뤄짐
5. **후속 대응**: 로그와 재현으로 반영 지점을 찾고 수정함

## Ⅵ. 실무 적용 및 유의점

1. 게시판과 관리자 화면처럼 사용자 입력이 다시 렌더링되는 서비스는 템플릿 자동 이스케이프와 출력 문맥별 인코딩을 기본값으로 강제해야 하며 저장형 페이로드 재현 실패와 CSP 위반 로그 감소와 주요 쿠키의 HttpOnly 적용 여부로 확인함
2. 프런트엔드에서 `innerHTML` 같은 직접 DOM 삽입이 남아 있는 환경은 서버 필터만으로 막기 어려우므로 안전한 DOM API와 sanitization 라이브러리로 전환해야 하며 DOM 기반 재현 차단과 정적 분석 경고 제거 여부로 확인함

## Ⅶ. 결론

- XSS는 브라우저 실행 문맥이 깨지는 문제이므로 입력값을 의심하는 수준을 넘어 출력 위치와 DOM 조작 방식 자체를 안전하게 바꿔야 함
