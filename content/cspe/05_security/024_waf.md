## Ⅰ. 개요
- **정의**: HTTP/HTTPS 트래픽을 검사하여 웹 애플리케이션 계층 공격을 탐지·차단하는 보안 시스템임
- **배경/필요성**: 네트워크 방화벽(021 참조)은 L3/L4만 검사하므로 SQL Injection·XSS 등 L7 웹 공격 차단이 불가하여 별도 계층이 필요함
- **비유**: 식당 입구에서 음식 재료의 위생 상태까지 검사하는 검역관과 유사함

| 출제 의도 | 반드시 짚을 핵심 | 감점 회피 포인트 |
|:---|:---|:---|
| WAF와 일반 방화벽·IPS 차별점 | HTTP 프로토콜 파싱·OWASP Top 10 방어 | WAF가 모든 웹 취약점을 방어한다는 오해 주의 |

> 요약: HTTP 요청·응답을 정밀 파싱하여 웹 공격을 차단하는 L7 전용 방화벽임

## Ⅱ. 구성요소
```text
Client --> [ Reverse Proxy / WAF ] --> Web Server
                   |
          +--------+--------+
          |        |        |
       Rule Set  Parser  Learning
```

| 구성요소 | 설명 | 비유 |
|:---|:---|:---|
| HTTP Parser | HTTP 헤더·파라미터·바디를 구조적으로 분해·정규화함 | 편지 내용을 낱장별로 펼쳐 검사 |
| Rule Set | SQLi·XSS·CSRF 등 공격 패턴을 정의한 탐지 규칙 집합임 | 유해물질 검출 기준표 |
| Learning Engine | 정상 트래픽 패턴을 학습하여 화이트리스트 모델을 생성함 | 단골 고객 행동 패턴 기억 |
| Reverse Proxy | 클라이언트-서버 사이에 위치하여 요청을 중계·검사함 | 우편물 대리 수령 창구 |

> 요약: HTTP 파싱·규칙 매칭·학습 엔진이 리버스 프록시 구조에서 동작함

## Ⅲ. 절차
```text
HTTP 요청 수신 --> 요청 파싱 --> 규칙 매칭/학습 모델 비교 --> 허용/차단
```
- 1단계: 리버스 프록시가 클라이언트 HTTP 요청을 수신하고 SSL을 종단함
- 2단계: HTTP Parser가 URI·헤더·파라미터·바디를 정규화·디코딩함
- 3단계: Rule Set 매칭과 Learning Engine 편차 분석으로 공격 여부를 판정함
- 4단계: 정상 요청은 백엔드 서버로 전달하고 공격 요청은 차단·로그 기록함

> 요약: HTTP 요청을 파싱·정규화한 후 규칙·학습 모델로 공격을 판정함

## Ⅳ. 문제점
- 오탐으로 인한 서비스 장애: 정상 요청을 공격으로 오판하여 서비스 가용성이 저하됨
- 우회 공격 취약: 인코딩 변환·페이로드 분할 기법으로 규칙을 우회하는 공격이 존재함
- API 트래픽 미지원: REST/GraphQL 등 비전통 HTTP 트래픽에 대한 검사 규칙이 부족함

> 요약: 오탐·우회 공격·API 미지원이 WAF의 주요 한계임

## Ⅴ. 개선방안
1. 단기: 학습 모드 운영 후 규칙 튜닝으로 오탐률을 감소시킴
2. 중기: 다중 디코딩·재귀 정규화 엔진을 적용하여 우회 공격 방어력을 강화함
3. 장기: API Gateway·WAAP(Web App & API Protection)으로 확장하여 API 트래픽을 보호함

> 요약: 규칙 튜닝, 정규화 강화, WAAP 확장으로 보호 범위를 넓힘

## Ⅵ. 전망
- 발전 방향: 클라우드 네이티브 WAF와 Bot 관리·API 보호가 통합된 WAAP로 진화 중임
- 기술사적 판단: DevSecOps 파이프라인에 WAF 정책을 코드화(Policy-as-Code)하는 방식이 확산됨
- 기술사 제언: WAF 단독 의존이 아닌 시큐어 코딩·취약점 스캔과 병행하는 다층 방어가 필요함
