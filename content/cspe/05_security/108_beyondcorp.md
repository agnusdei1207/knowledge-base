# 📖 【암기용】 개념 완전 이해

> 목적: BeyondCorp를 특정 제품이 아니라 기업 접근 모델로 이해하게 만든다. 시험 답안 양식이 아니라, 이해를 위한 친절한 설명이다.

## 한눈에
- **개요**: 사내망 위치 신뢰를 제거하고 사용자·단말·앱 정책으로 업무 접근을 제공하는 제로 트러스트 모델
- **왜 필요한가**: 사무실 안이라는 이유로 권한을 주면 협력사, 재택, 클라우드, 모바일 단말을 같은 기준으로 관리하기 어렵다.
- **핵심 직관**: 회사 건물 안팎을 구분하지 않고 모든 업무 앱 앞에 동일한 신분 확인 창구를 세우는 방식임

## 깊이 이해
- **배경·문제의식**: 전통 보안은 사내망 내부를 상대적으로 신뢰한다. 그러나 피싱, 악성 단말, VPN 계정 탈취가 발생하면 내부망 위치 자체가 신뢰 근거가 되지 못한다.
- **작동 원리**: 사용자는 인터넷에서 업무 앱 URL에 접근한다. Access Proxy가 요청을 받아 IdP 인증, 단말 인증서, 인벤토리 상태, 사용자 권한, 앱 정책을 조회한 뒤 허용 또는 차단한다.
- **비유**: 임직원 통로를 없애고 고객·직원·협력사 모두 같은 출입 심사대를 통과하게 하는 공항 보안 모델과 유사함
- **구체 예시**: HR 시스템은 사내·외 위치와 무관하게 사용자 그룹 HR, 관리 단말 인증서, 패치 14일 이내, FIDO2 MFA 충족 시 접속 허용. 개인 PC는 조회 권한만 부여하거나 차단함.
- **흔한 오해·주의점**: BeyondCorp는 VPN 제거 선언이 아니다. 기기 인벤토리 품질, 앱 프록시 전환, 레거시 프로토콜 처리, 사용자 경험 지표를 함께 관리해야 한다.

## 연결 개념
- ZTNA — BeyondCorp 원칙을 상용 접근 서비스로 구현한 형태
- Device Inventory — 단말 신뢰 평가의 기반 데이터
- Access Proxy — 인터넷에서 사설 앱 접근을 중개하는 정책 집행 지점

# 📝 【답안용】 시험 답안 템플릿

> 목적: 시험장에서 25분에 그대로 쓰는 답안 양식. 작성방식(추상표현 금지·수치·도식·문제유형 전환)을 엄격히 지킨다.
> 핵심: BeyondCorp는 경계망 위치 신뢰를 폐기하고 모든 앱 접근을 사용자·단말·정책으로 판정하는 기업 보안 운영 모델임.

## 핵심 인사이트 (3줄 요약)

> 1. **본질**: BeyondCorp는 내부망 여부와 무관하게 사용자, 단말, 애플리케이션 정책으로 접근을 결정하는 제로 트러스트 참조 모델이다.
> 2. **가치**: VPN 의존을 줄이고 Access Proxy, IdP, Device Inventory로 업무 앱 접근을 동일한 정책 경로에 수렴시킨다.
> 3. **판단 포인트**: 앱 프록시 전환율, 관리 단말 비율, 정책 결정 지연, 사용자 실패율을 지표로 전환 성숙도를 판단한다.

## 출제 의도 및 답안 포인트

| 출제 의도 | 반드시 짚을 핵심 | 감점 회피 포인트 |
|:---|:---|:---|
| BeyondCorp 개념 이해 확인 | 위치 기반 신뢰 제거, Access Proxy, 단말 인벤토리 | Google 제품명 또는 VPN 폐지만 언급 |
| 제로 트러스트 구현 절차 확인 | 사용자 인증, 기기 신뢰, 앱별 정책, 로그 | 정책 엔진 없이 MFA만 설명 |
| 레거시 전환 판단 확인 | 웹 앱 우선, 비HTTP 프로토콜 분리, 단계 전환 | 모든 업무를 즉시 인터넷 공개로 오해 |
> 요약: 이 문제는 BeyondCorp를 사내망 제거가 아니라 접근 정책 체계 전환으로 설명해야 한다.

---

## Ⅰ. 개요 및 필요성

BeyondCorp는 위치 독립 접근 모델이다.
클라우드·재택·협력사 업무가 증가하면서 사내망 내부라는 조건은 신뢰 기준이 되지 못한다. BeyondCorp는 모든 업무 앱을 Access Proxy 뒤에 두고 사용자·단말·앱 정책으로 접근을 판정한다. 이를 통해 경계망 중심 운영에서 앱 중심 접근 통제로 전환한다.

---

## Ⅱ. 구조 및 구성요소

```text
User Browser -> Access Proxy -> Policy Engine -> Enterprise App
                         +-> IdP/MFA
                         +-> Device Inventory/Certificate
                         +-> Log Pipeline/SIEM
```

| 구성요소 | 역할 | 특이사항 |
|:---|:---|:---|
| Access Proxy | 모든 앱 요청의 정책 집행 지점 | HTTP 앱 우선 적용 |
| IdP/MFA | 사용자 신원과 인증 강도 확인 | SAML/OIDC, FIDO2 |
| Device Inventory | 단말 소유, 패치, 인증서, EDR 상태 제공 | MDM·EDR 데이터 품질 필요 |
| Policy Engine | 사용자·단말·앱 민감도 기반 허용 판단 | 조건부 접근 정책 |
| Log Pipeline | 접속, 차단, 정책 사유 기록 | SIEM, UEBA 분석 |
> 요약: BeyondCorp는 Access Proxy를 중심으로 IdP, 단말 인벤토리, 정책 엔진, 로그가 결합된 구조이다.

---

## Ⅲ. 동작원리 및 흐름도

```text
앱 URL 요청 -> Access Proxy 수신 -> 사용자 인증 -> 단말 신뢰 조회
-> 정책 결정 -> 앱 세션 전달 / 차단 -> 로그 분석
```

| 단계 | 처리 내용 | 검증 기준 |
|:---:|:---|:---|
| 1 | 사용자가 인터넷에서 업무 앱 URL 접속 | 사내·외 동일 경로 |
| 2 | Access Proxy가 IdP 인증 요청 | FIDO2 MFA 성공률 98% 이상 |
| 3 | 단말 인벤토리와 인증서 상태 확인 | 관리 단말, 패치 14일 이내 |
| 4 | 앱 민감도별 정책 평가 | HR·재무 앱은 관리 단말만 허용 |
| 5 | 세션 제공 및 로그 전송 | 정책 결정 p95 200ms 이하 |
> 요약: BeyondCorp는 접근 위치가 아니라 사용자·단말·앱 조건의 조합으로 매 요청을 판정한다.

## Ⅳ. 특징

| 구분 | 경계망/VPN 모델 | BeyondCorp 모델 | 정량·기술 포인트 |
|:---|:---|:---|:---|
| 신뢰 기준 | 사내망 IP, VPN 터널 | 사용자 신원, 단말 상태, 앱 정책 | 관리 단말 비율 95% 이상 |
| 접근 경로 | VPN 접속 후 내부 라우팅 | Access Proxy 통한 앱 접속 | 프록시 전환 앱 80% 이상 |
| 단말 통제 | 접속 시점 검사 중심 | 인벤토리·인증서 기반 지속 조회 | 패치 14일 SLA |
| 사용자 경험 | 위치별 접속 방식 상이 | 사내·외 동일 URL | 로그인 실패율 2% 이하 |
> 요약: BeyondCorp는 위치별 보안 운영을 단일 앱 접근 경로와 단말 신뢰 데이터로 통합한다.

## Ⅴ. 심화 비교 및 적용 판단

| 비교 축 | 기존/대안 | BeyondCorp | 선택 기준 |
|:---|:---|:---|:---|
| 구조 | VPN Concentrator + 내부망 ACL | Access Proxy + Policy Engine | 웹 기반 업무 앱 비율 60% 이상 |
| 비용/성능 | VPN 백홀·장비 증설 | 프록시 PoP·IdP 연계 | 정책 결정 p95 200ms 이하 |
| 운영/위험 | 네트워크 위치별 예외 | 단말 인벤토리 품질 의존 | MDM 등록률 95% 이상 |
> 요약: 웹 앱과 관리 단말 비율이 높을수록 BeyondCorp 전환 효과를 검증하기 쉽다.

| 리스크 | 원인 | 대응 방안 | 확인 지표 |
|:---|:---|:---|:---|
| 단말 신뢰 오류 | MDM·EDR 데이터 지연 | 인벤토리 동기화 15분 이하, 상태 TTL 적용 | unknown device 1% 이하 |
| 레거시 앱 미전환 | 비HTTP, 고정 IP 의존 | TCP 프록시, VPN 격리, 앱 현대화 로드맵 | 프록시 전환율 월 10% 증가 |
| 사용자 마찰 | MFA 과다, 정책 설명 부족 | 위험 기반 MFA, 오류 메시지 표준화 | 로그인 실패율 2% 이하 |
> 요약: BeyondCorp 전환 리스크는 단말 데이터 품질, 레거시 프로토콜, 사용자 실패율로 관리한다.

| 점검 항목 | 목표 기준 | 측정 방법 |
|:---|:---|:---|
| 전환 범위 | Tier-1 웹 앱 100%, 전체 앱 80% 프록시화 | 앱 카탈로그, 프록시 로그 |
| 단말 신뢰 | MDM 등록률 95%, EDR 정상 98% | MDM, EDR, 인증서 로그 |
| 접근 품질 | 정책 결정 p95 200ms, 접속 실패율 2% 이하 | Proxy metric, IdP 로그 |
> 요약: 성숙도는 앱 프록시화, 단말 신뢰 데이터, 정책 지연, 실패율을 함께 측정한다.

## Ⅵ. 실무 적용 및 결론

**적용 방안 3개:**
1. 앱 전환: HR·그룹웨어·개발도구 등 웹 앱부터 Access Proxy 뒤로 이전하고 비HTTP 앱은 별도 게이트웨이로 격리
2. 단말 기반: MDM 등록, 단말 인증서, EDR 상태, 패치 14일 SLA를 정책 조건으로 사용
3. 운영 관측: 프록시 로그, IdP 로그, 단말 상태를 SIEM에 연계하고 실패율 2% 초과 시 정책 리뷰 수행

**결론 (2줄):**
- 기술사 판단: 관리 단말과 웹 앱 중심 조직은 BeyondCorp 모델을 우선 적용하고, 제조 제어망·레거시 TCP 업무는 분리망과 PAM을 병행한다.
- 향후 방향: ZTNA, SASE, 연속 인증과 결합해 요청 단위 위험 기반 접근 모델로 확장된다.
