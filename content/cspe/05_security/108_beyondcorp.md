## 미리 알고가기

- BeyondCorp는 구글이 내부망 신뢰를 없애고 사용자와 기기 상태를 기준으로 사내 앱 접근을 통제한 제로 트러스트 운영 모델임
- ZTNA 제품 하나를 뜻한다기보다 신원, 단말 상태, 프록시 기반 접근을 결합한 참조 아키텍처에 가까움
- 핵심은 `사내망에 있느냐`가 아니라 `누구이며 어떤 기기 상태냐`로 접근을 결정한다는 점임

## Ⅰ. 개요

- **정의/개념**: BeyondCorp는 내부·외부를 구분하지 않고 사용자 신원, 디바이스 상태, 정책 평가로 기업 앱 접근을 허용하는 제로 트러스트 모델임
- **배경/필요성**: 경계 기반 VPN은 내부 침해와 원격 근무 확산에 취약함. 신뢰 가능한 사용자·단말에만 앱 단위 접근을 줘야 함

## Ⅱ. 특징

- 네트워크 위치보다 신원과 단말 보안 상태를 더 중요하게 봄
- 모든 사내 앱 접근을 프록시 계층으로 수렴시켜 정책을 집행함
- 단말 인벤토리와 인증 체계 품질이 낮으면 모델 전체가 약해짐
- 완전 전환보다는 고위험 앱부터 단계 적용하는 방식이 현실적임

## Ⅲ. 종류 및 비교

| 판단 기준 | VPN 중심 내부망 접근 | BeyondCorp 모델 |
|:---|:---|:---|
| 접근 판단 기준 | 내부망 진입 여부 | 사용자 신원 + 단말 상태 + 정책 |
| 자산 노출 | 네트워크 단위 노출 가능 | 승인된 앱만 프록시 경유 노출 |
| 강점 | 기존 구조와 친숙함 | 원격 근무와 내부 침해 대응에 유리함 |
| 한계 | 내부 확산에 취약 | 단말 가시성과 정책 체계가 필수임 |

## Ⅳ. 구성요소 및 구조

| 구성요소 | 설명 |
|:---|:---|
| Identity Layer | 사용자 인증과 MFA와 역할 정보를 제공함 |
| Device Inventory and Posture | 단말 등록 상태와 패치와 보안 상태를 관리함 |
| Access Proxy | 애플리케이션 접근을 중개하고 정책을 강제함 |
| Policy Decision Logic | 사용자, 단말, 자원 조건을 평가해 허용 여부를 판단함 |

```text
사용자 요청 -> 신원 확인 -> 단말 상태 확인 -> 프록시 정책 평가 -> 승인된 앱만 접근
```

## Ⅴ. 원리 및 절차 흐름도

```text
단말 등록 -> 사용자 인증 -> 앱 접근 요청 -> 정책 평가 -> 프록시 전달 -> 지속 재평가
```

1. **단말 등록**: 관리 대상 기기 상태를 수집함
2. **사용자 인증**: SSO와 MFA로 신원을 확인함
3. **앱 접근 요청**: 사용자가 특정 사내 앱을 요청함
4. **정책 평가**: 사용자와 기기와 앱 민감도를 함께 평가함
5. **프록시 전달**: 승인된 요청만 앱으로 전달함

## Ⅵ. 실무 적용 및 유의점

1. 재택근무·SaaS 혼합 환경은 EDR·MDM 연계와 프록시 강제를 두고 등록 단말 커버리지와 비인가 단말 차단 여부로 확인함
2. 레거시 앱은 중요 앱부터 전환하고 VPN 예외 감소, 앱별 정책 전환율, 사용자 마찰 수준으로 확인함

## Ⅶ. 결론

- BeyondCorp는 내부망 신뢰를 없애고 사용자와 단말 상태를 기준으로 앱 접근을 통제하는 제로 트러스트 운영 모델의 대표 사례임
