## Ⅰ. 개요
| 항목 | 내용 |
|---|---|
| **정의** | Google이 구현한 제로 트러스트 엔터프라이즈 보안 모델로, VPN 없이 신원·디바이스 신뢰도만으로 사내 앱 접근을 제어하는 아키텍처임 |
| **배경/필요성** | Google이 오로라 작전(Operation Aurora) APT 공격을 겪은 후, 경계 기반 보안의 한계를 인식하고 내부·외부 구분을 제거한 모델을 구축함 |
| **출제 의도** | BeyondCorp의 핵심 원칙과 기존 VPN 기반 접근 방식과의 차이를 이해하는지 평가함 |

## Ⅱ. 구성요소
```
+----------+     +----------+     +----------+
| 디바이스  | --> | 접근프록시| --> | 접근엔진  |
| 인벤토리 |     | (AP)     |     | (AE)     |
+----------+     +----------+     +----------+
```

| 구성요소 | 설명 | 비유 |
|---|---|---|
| 디바이스 인벤토리 | 모든 기업 디바이스의 보안 상태(패치·암호화·인증서)를 추적·관리하는 DB임 | 전 직원 건강검진 기록부 |
| 접근 프록시(AP) | 모든 앱 접근을 중개하여 인증·권한·디바이스 상태를 검증하는 리버스 프록시임 | 건물 출입구 보안 게이트 |
| 접근 엔진(AE) | 사용자·디바이스·리소스의 신뢰 수준을 실시간 평가하여 접근 허가를 결정함 | 보안 통제실 |

> 요약: 디바이스 인벤토리(상태 추적) + 접근 프록시(중개) + 접근 엔진(판단)으로 VPN 없는 접근을 구현함.

## Ⅲ. 절차
```
+------------+     +------------+
| 디바이스   | --> | 사용자인증  |
| 상태확인   |     | (SSO/MFA)  |
+------------+     +------------+
                        |
+------------+     +----+-------+
| 앱접근허가  | <-- | 접근엔진  |
| (프록시경유)|     | 신뢰평가   |
+------------+     +------------+
```

1. 디바이스 상태 확인: 인벤토리 DB에서 디바이스의 패치·암호화·인증서 상태를 조회함
2. 사용자 인증: SSO·MFA를 통해 사용자 신원을 검증함
3. 신뢰 수준 평가: 접근 엔진이 디바이스 상태·사용자 역할·접속 컨텍스트를 종합하여 Trust Level을 산출함
4. 접근 프록시 허가: Trust Level이 앱 요구 수준 이상이면 프록시를 통해 앱 접근을 허용함

> 요약: 디바이스 상태 → 사용자 인증 → 신뢰 평가 → 프록시 허가로 위치 무관 접근을 제어함.

## Ⅳ. 문제점
- 구현 난이도: Google 규모의 인프라·기술력이 필요하여 중소기업 적용이 어려움
- 디바이스 인벤토리 정확성: 모든 디바이스의 실시간 상태를 정확히 추적하는 데 높은 운영 비용이 소요됨
- 레거시 앱 호환: HTTP 기반이 아닌 레거시 프로토콜의 프록시 경유가 어려움

## Ⅴ. 개선방안
- (단기) BeyondCorp Enterprise(GCP) 활용: Google의 상용 제품을 통해 구현 복잡성을 줄임
- (중기) EDR·MDM 연동: 디바이스 인벤토리를 EDR·MDM과 실시간 연동하여 정확성을 확보함
- (장기) 범용 ZTNA 전환: BeyondCorp 원칙을 벤더 중립적 ZTNA 아키텍처로 표준화함

## Ⅵ. 전망
- BeyondCorp 모델이 NIST SP 800-207 ZTA의 실증 참조 구현으로 인용되며, 산업 전반의 제로 트러스트 전환을 견인하는 사실상 참조 아키텍처 역할을 할 전망임
