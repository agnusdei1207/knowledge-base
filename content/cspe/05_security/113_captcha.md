## 미리 알고가기

- CAPTCHA는 사람과 자동화 프로그램을 구분하기 위한 추가 검증 장치임
- 전통형은 문자나 이미지 문제를 풀게 하고, 최신형은 행동 패턴과 위험 점수를 활용함
- 로그인 보안 전체를 해결하는 기술이 아니라 봇과 대량 자동화를 줄이는 보조 통제로 봐야 함

## Ⅰ. 개요

- **정의/개념**: CAPTCHA·reCAPTCHA는 계정 생성, 로그인, 폼 제출 등에서 사람 사용자인지 자동화된 봇인지 구분해 대량 공격과 스팸과 크리덴셜 스터핑을 줄이기 위한 사용자 검증 기술임
- **배경/필요성**: 봇이 대규모로 계정을 만들고 비밀번호를 대입하고 스팸을 뿌리는 공격이 늘면서, 인증 정보만으로는 구분하기 어려운 자동화를 추가로 차단할 필요가 생김

## Ⅱ. 특징

- 로그인과 가입과 문의 폼 같은 공개 진입점에서 주로 사용됨
- 문제형, 체크형, 점수형처럼 사용자 마찰 수준이 다름
- 단독 방어보다는 속도 제한과 계정 보호와 함께 쓸 때 효과가 큼
- 접근성과 프라이버시와 오탐 문제를 함께 고려해야 함

## Ⅲ. 종류 및 비교

| 판단 기준 | 문제형 CAPTCHA | 점수형 reCAPTCHA |
|:---|:---|:---|
| 사용자 경험 | 직접 문제를 풀어야 함 | 눈에 보이는 도전이 없을 수 있음 |
| 장점 | 작동 원리가 단순함 | 사용자 마찰을 줄일 수 있음 |
| 한계 | 접근성 저하와 AI 우회 위험 | 점수 기준과 프라이버시 의존성이 큼 |
| 적합 환경 | 명확한 추가 검증이 필요한 화면 | 대량 트래픽 분석이 가능한 서비스 |

## Ⅳ. 구성요소 및 구조

| 구성요소 | 설명 |
|:---|:---|
| Client Script or Challenge | 사용자 화면에서 문제 제시나 행동 수집을 담당함 |
| Verification Token | 검증 결과를 서버에 전달하는 토큰임 |
| Risk Evaluation | 문제 정답이나 행동 패턴을 평가함 |
| Server Decision | 허용, 추가 검증, 차단 여부를 결정함 |

```text
사용자 요청 -> CAPTCHA 토큰/문제 생성 -> 응답 또는 행동 수집 -> 서버 검증 -> 허용/차단
```

## Ⅴ. 원리 및 절차 흐름도

```text
폼 접근 -> 챌린지 또는 행동 수집 -> 토큰 생성 -> 서버 검증 -> 임계값 비교 -> 허용/추가 인증/차단
```

1. **폼 접근**: 가입이나 로그인 화면이 열림
2. **챌린지 또는 행동 수집**: 문제를 내거나 행동 패턴을 수집함
3. **토큰 생성**: 검증 결과를 담은 토큰을 만듦
4. **서버 검증**: 토큰과 점수를 확인함
5. **결정**: 허용하거나 추가 인증이나 차단을 수행함

## Ⅵ. 실무 적용 및 유의점

1. 공개 로그인과 회원가입 화면은 CAPTCHA를 속도 제한과 함께 쓰고 실패 임계값과 우회 시나리오를 조정해 봇 성공률 감소와 정상 사용자 이탈 증가 여부로 확인함
2. 이미지 기반 방식은 접근성과 프라이버시 문제가 커질 수 있으므로 음성 대안이나 다른 검증 수단을 함께 제공하고 장애 사용자 지원 가능 여부와 개인정보 전송 범위 적정성으로 확인함

## Ⅶ. 결론

- CAPTCHA는 사람과 봇을 구분하는 보조 통제이므로 로그인 보호 전체를 대신하지 못하며 접근성·프라이버시와 함께 설계해야 함
