# 📖 【암기용】 개념 완전 이해

## 한눈에
- **개요**: **전자 서명은 개인키로 데이터 해시를 서명하고 공개키로 검증하여 인증·무결성·부인방지를 제공하는 공개키 응용 기술**임. 비대칭 키쌍의 기본 동작은 (002 참조), 서명 대상인 해시의 성질은 (004 해시 참조).
- **왜 필요한가**: 네트워크의 문서·코드·인증서는 복제·변조가 쉬움. 전자 서명은 "누가 만들었는가(인증)", "내용이 바뀌지 않았는가(무결성)", "나중에 부인할 수 없는가(부인방지)"를 검증 가능하게 함.
- **핵심 직관**: 원문 지문(해시)에 개인 도장을 찍고, 누구나 공개된 도장 확인 도구(공개키)로 진위를 검사하는 구조임.

## 핵심 용어 정리 (내부에 등장하는 것들)

답안에 등장하는 보안 속성·알고리즘·운영 요소를 먼저 풀어 둠. 상위 핵심 키워드는 **부인방지(non-repudiation)** 로, 인증·무결성과 구분해서 이해해야 함.

| 용어/표기 | 의미 | 비유·예 |
|:---|:---|:---|
| 인증 / 무결성 | 서명자 신원 확인 / 원문 미변조 확인 | 도장 주인 확인 / 지문 일치 확인 |
| 부인방지 | 서명자가 나중에 "안 했다"고 못 하게 함 | 개인키는 본인만 가지므로 발뺌 불가 |
| 기밀성 미제공 | 서명은 내용을 숨기지 않음 | 도장은 봉인이 아니라 확인 표식 |
| 해시(SHA-256) | 원문을 고정 길이 지문으로 압축 | 1비트만 달라도 지문이 완전히 바뀜 |
| Sign / Verify | 개인키로 서명값 생성 / 공개키로 검증 | 날인 / 대조 확인 |
| RSA-PSS | 안전한 패딩을 쓰는 RSA 서명 방식 | 구식 PKCS#1 v1.5의 개선형 |
| ECDSA / EdDSA(Ed25519) | 곡선 기반 서명 / 결정적 난수 개선형 (007 참조) | 작은 서명·빠른 검증 |
| ML-DSA | 양자내성 표준 서명(FIPS 204) | ECC/RSA 서명의 차세대 대체재 |
| X.509 인증서 / 체인 | 공개키-신원 바인딩과 상위 CA 서명 연결 | 도장 주인 신분증과 발급 계보 |
| EKU(확장 키 용도) | 인증서가 허용하는 용도(코드서명 등) | "이 도장은 계약용" 표기 |
| CRL / OCSP | 폐지 목록 / 실시간 폐지 상태 조회 | 분실 신고된 도장 대조 (009 참조) |
| TSA / RFC 3161 | 신뢰 타임스탬프 기관과 그 표준 | "언제 찍었는지" 공증 |
| HSM / KMS | 개인키를 뽑아내지 못하게 보관·서명하는 장치 | 도장을 금고 안에서만 사용 |

## 깊이 이해
- **배경·문제의식**: 암호화는 기밀성을 주지만 작성자 신원과 무결성을 직접 증명하지 않음. 전자 서명은 해시와 공개키 암호를 결합해 인증·무결성·부인방지를 제공함.
- **작동 원리(어떻게+왜)**: 원문 전체가 아니라 SHA-256 해시값을 개인키로 서명함(성능·안전성). 검증자는 원문을 다시 해시해 서명 검증 결과와 대조하고, 인증서 체인으로 공개키 소유자를 확인함. 개인키는 서명자만 보유하므로 부인방지가 성립함.
- **비유**: 계약서 전체를 봉투에 넣는 것이 아니라 계약서 지문을 만든 뒤 인감으로 날인하는 방식임. 지문이 1비트라도 다르면 검증이 실패함.
- **구체 예시**: 소프트웨어 배포에서 코드 서명 인증서로 실행파일에 서명하면, OS는 실행 전 서명값·인증서 체인·폐지 상태를 검증함.
- **흔한 오해·주의점**: (1) 전자 서명은 데이터를 숨기지 않음 — 기밀성이 필요하면 AES-GCM·TLS를 별도 적용함. (2) 원문 전체를 개인키로 "암호화"하는 것이 아니라 해시를 서명함. (3) 서명 검증 성공만으로 끝이 아니라 인증서 유효·폐지·시각 검증까지 통과해야 신뢰됨.

## 연결 개념
- 해시 알고리즘 — 서명 대상 데이터의 지문 생성 (004 참조)
- PKI·X.509 — 공개키 소유자와 신뢰 체인 제공 (009 참조)
- HSM/KMS — 개인키 보호와 서명 감사로그 제공

# 📝 【답안용】 시험 답안 템플릿

## 핵심 인사이트 (3줄 요약)

> 1. **본질**: 전자 서명은 해시값을 개인키로 서명하고 공개키로 검증해 인증·무결성·부인방지를 제공하는 공개키 응용임.
> 2. **가치**: 계약·코드 서명·인증서·API 요청에서 변조 탐지와 서명자 식별을 제공함.
> 3. **판단 포인트**: 기밀성은 제공하지 않으므로 암호화와 구분하고, 개인키 보호·인증서 검증·폐지 확인을 포함해야 함.

## 출제 의도 및 답안 포인트

| 출제 의도 | 반드시 짚을 핵심 | 감점 회피 포인트 |
|:---|:---|:---|
| 보안 속성 구분 확인 | 인증·무결성·부인방지, 기밀성 미제공 | 전자 서명을 암호화로 설명 |
| 알고리즘·절차 이해 확인 | 해시 -> 개인키 서명 -> 공개키 검증 | 원문 전체를 개인키로 암호화한다고 서술 |
| 운영 통제 판단 확인 | HSM, 인증서 체인, CRL/OCSP, 타임스탬프 | 키 관리·폐지 확인 누락 |

> 요약: 전자 서명 답안은 암호화와의 차이·해시 기반 절차·PKI 운영 통제를 동시에 제시해야 함.

## Ⅰ. 개요 및 필요성

- 개요: 공개키로 검증하는 해시 기반 서명 기술임.
- 배경: 디지털 문서·코드·트랜잭션은 복제·변조가 쉬워 작성자 신원과 원문 변경 여부를 별도 검증해야 함.
- 필요성: RSA-PSS·ECDSA·EdDSA·ML-DSA 서명은 해시값과 개인키 서명을 결합해 무결성·인증·부인방지를 제공함.
- 전제: 비대칭 키쌍과 해시 성질은 (002·004 참조)로 위임하고 서명 생성/검증·부인방지에 집중함.

---

## Ⅱ. 구조 및 구성요소

```text
원문 -> 해시 SHA-256 -> 개인키 서명 -> 서명값
  / 원문·서명값·인증서 전달
  / 공개키 검증 -> 인증서 체인·폐지 확인 -> 신뢰 판단
```

| 구성요소 | 역할 | 특이사항 |
|:---|:---|:---|
| 원문·해시 | 서명 대상과 고정 길이 지문 생성 | SHA-256/SHA-3, 충돌 저항성 필요 |
| 개인키 | 서명값 생성 | HSM/KMS 보관, 접근권한 최소화 |
| 공개키·인증서 | 서명 검증과 소유자 확인 | X.509 체인·EKU 확인 |
| 서명 알고리즘 | RSA-PSS, ECDSA, EdDSA | PKCS#1 v1.5 신규 적용 지양 |
| 폐지·시각 증명 | 인증서 유효성·서명 시점 확인 | OCSP, CRL, TSA(RFC 3161) |

> 요약: 전자 서명 구조는 해시·개인키 서명·공개키 검증·인증서 신뢰 확인으로 구성됨.

---

## Ⅲ. 동작원리 및 흐름도

```text
원문 작성 -> 해시 계산 -> 개인키 서명 -> 원문·서명 배포
  -> 검증자 인증서 검증 -> 해시 재계산 -> 서명 검증 -> 폐지·시각 확인
```

1. 서명자가 원문을 SHA-256 이상으로 해시하며, 문서형은 canonicalization으로 표현 차이를 제거함.
2. 서명자가 HSM 서명 정책·승인 워크플로 하에서 개인키로 서명값을 생성함.
3. 서명자가 원문·서명값·인증서(체인·알고리즘 식별 포함)를 검증자에게 전달함.
4. 검증자가 원문을 재해시해 공개키로 서명을 검증하고, OCSP good·TSA 시각까지 확인한 뒤 결과를 기록함.

> 요약: 전자 서명 검증은 수학적 서명 확인과 인증서 유효성 확인을 모두 통과해야 완료됨.

---

## Ⅳ. 특징

- 보안 속성: 기밀성이 아니라 인증·무결성·부인방지를 제공하여 "숨김"이 아닌 "증명" 기능임.
- 키 방향: 서명자 개인키로 서명하고 공개키로 검증하여, 수신자 공개키로 암호화하는 방향과 반대임.
- 서명 대상: 대용량 파일도 본문 전체가 아니라 해시값을 서명해 성능·안전성을 확보함.
- 부인방지: 개인키는 서명자만 보유하므로 사후 부인이 불가하며, 이는 MAC/HMAC과의 결정적 차이임.
- 운영 의존성: 개인키 HSM 보호·인증서 폐지 확인·감사로그가 있어야 서명이 법적·기술적 신뢰를 가짐.

---

## Ⅴ. 심화 비교 및 적용 판단

HMAC과 전자 서명을 검증 주체·부인방지 축으로 비교함(다대상×다축이므로 표 사용).

| 구분 | HMAC | 전자 서명 | 선택 기준 |
|:---|:---|:---|:---|
| 키 모델 | 대칭 공유키 | 개인키 서명·공개키 검증 | 다자 검증 필요 시 서명 |
| 부인방지 | 미제공(공유키라 발뺌 가능) | 제공 | 제3자 증명·법적 효력 필요 시 서명 |
| 대표 용도 | 내부 메시지 무결성 | 코드 서명·문서 서명·인증서 | 배포 경로 신뢰·감사 추적 필요 시 서명 |

> 요약: 단일 조직 내부 무결성은 HMAC, 외부 제3자 검증과 부인방지는 전자 서명을 선택함.

리스크 관리는 불릿으로 정리함.
- 리스크: 개인키 유출 — 원인: 파일 기반 저장·과도 권한 — 대응: HSM/KMS·MFA·승인 기반 서명, 개인키 export 0건.
- 리스크: 위조 서명 수용 — 원인: 인증서 폐지 미확인 — 대응: OCSP stapling·CRL 동기화, 폐지 인증서 허용 0건.
- 리스크: 알고리즘 노후화 — 원인: SHA-1·RSA-1024 사용 — 대응: SHA-256↑·RSA-2048/3072·ECDSA P-256, 취약 알고리즘 0건.

지표 관리도 불릿으로 정리함.
- 지표: 키 보호 — 목표: HSM FIPS 140-2/140-3, 키 export 금지 — 측정: HSM 정책·KMS 감사로그.
- 지표: 검증 품질 — 목표: 서명·체인·폐지·시각 4종 검증 — 측정: 검증 로그·OCSP 응답률.
- 지표: 복구 시간 — 목표: 키 유출 시 24시간 내 폐지·재서명 — 측정: 사고훈련·CRL 반영 시간.

---

## Ⅵ. 실무 적용 및 결론

**적용 방안 3개 (필수 — 단계별 또는 항목별):**
1. 알고리즘 정책: 신규 시스템은 SHA-256 이상, RSA-PSS 2048/3072 또는 ECDSA P-256/Ed25519 적용.
2. 키 관리: 서명 개인키는 HSM/KMS 보관, 운영자 직접 export 금지와 2인 승인 서명 절차 적용.
3. 검증 체계: 인증서 체인·EKU·OCSP/CRL·RFC 3161 타임스탬프를 검증 파이프라인에 포함.

**결론 (2줄):**
- 기술사 판단: 외부 제3자 검증·부인방지가 필요하면 전자 서명, 내부 메시지 무결성만 필요하면 HMAC을 선택함.
- 향후 방향: 장기 보관 문서·코드 서명은 ML-DSA 등 PQC 서명 전환과 타임스탬프 보존 정책이 필요함.
