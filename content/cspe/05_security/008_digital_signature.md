# 📖 【암기용】 개념 완전 이해

> 목적: 전자 서명을 처음 봐도 완전하게 이해하게 만든다. 시험 답안 양식이 아니라, 이해를 위한 설명이다.

## 한눈에
- **개요**: 개인키로 서명하고 공개키로 검증하여 신원·무결성·부인방지를 제공하는 기술
- **왜 필요한가**: 네트워크 문서·코드·인증서는 복사와 변조가 쉽다. 전자 서명은 "누가 만들었는지", "내용이 바뀌지 않았는지", "나중에 부인할 수 있는지"를 검증하게 한다.
- **핵심 직관**: 문서 지문(해시)에 개인 도장을 찍고, 누구나 공개된 도장 확인 도구로 맞는지 검사하는 구조이다.

## 깊이 이해
- **배경·문제의식**: 암호화는 기밀성을 제공하지만 작성자 신원과 무결성을 직접 증명하지 않는다. 전자 서명은 해시와 공개키 암호를 결합하여 인증·무결성·부인방지를 제공한다.
- **작동 원리**: 원문을 SHA-256 등으로 해시한 뒤 개인키로 서명값을 만든다. 검증자는 원문 해시와 공개키 검증 결과를 비교하고, 인증서 체인으로 공개키 소유자를 확인한다.
- **비유**: 계약서 전체를 봉투에 넣지 않고 계약서 지문을 만든 뒤 인감으로 날인하는 방식이다. 지문이 1비트라도 달라지면 검증이 실패한다.
- **구체 예시**: 소프트웨어 배포에서 코드 서명 인증서로 실행파일에 서명하면, OS는 실행 전 서명값·인증서 체인·폐지 상태를 검증한다.
- **흔한 오해·주의점**: 전자 서명은 데이터를 숨기지 않는다. 기밀성이 필요하면 AES-GCM, TLS 같은 암호화를 별도로 적용해야 한다.

## 연결 개념
- 해시 알고리즘 — 서명 대상 데이터의 지문 생성
- PKI·X.509 — 공개키 소유자와 신뢰 체인 제공
- HSM/KMS — 개인키 보호와 서명 감사로그 제공

# 📝 【답안용】 시험 답안 템플릿

> 목적: 시험장에서 25분에 그대로 쓰는 답안 양식. 작성방식(추상표현 금지·수치·도식·문제유형 전환)을 엄격히 지킨다.

## 핵심 인사이트 (3줄 요약)

> 1. **본질**: 전자 서명은 해시값을 개인키로 서명하고 공개키로 검증하여 인증·무결성·부인방지를 제공하는 공개키 응용 기술임.
> 2. **가치**: 계약, 코드 서명, 인증서, API 요청에서 변조 탐지와 서명자 식별을 제공함.
> 3. **판단 포인트**: 기밀성은 제공하지 않으므로 암호화와 구분하고, 개인키 보호·인증서 검증·폐지 확인을 포함해야 함.

## 출제 의도 및 답안 포인트

| 출제 의도 | 반드시 짚을 핵심 | 감점 회피 포인트 |
|:---|:---|:---|
| 보안 속성 구분 역량 확인 | 인증, 무결성, 부인방지, 기밀성 미제공 | 전자 서명을 암호화로 설명 금지 |
| 알고리즘·절차 이해 확인 | Hash -> Sign with Private Key -> Verify with Public Key | 원문 전체를 개인키로 암호화한다고 서술 금지 |
| 운영 통제 판단 확인 | HSM, 인증서 체인, CRL/OCSP, 타임스탬프 | 키 관리와 폐지 확인 누락 금지 |

> 요약: 전자 서명 답안은 암호화와의 차이, 해시 기반 절차, PKI 운영 통제를 동시에 제시해야 함.

---

## Ⅰ. 개요 및 필요성

전자 서명은 공개키 기반 검증 기술이다.  
디지털 문서·코드·트랜잭션은 복제와 변조가 쉬워 작성자 확인과 변경 여부 검증이 필요하다.  
전자 서명은 개인키와 공개키를 분리하여 서명자 인증, 원문 무결성, 사후 부인방지를 제공한다.

---

## Ⅱ. 구조 및 구성요소

```text
원문 -> 해시 SHA-256 -> 개인키 서명 -> 서명값
  / 원문·서명값·인증서 전달
  / 공개키 검증 -> 인증서 체인·폐지 확인 -> 신뢰 판단
```

| 구성요소 | 역할 | 특이사항 |
|:---|:---|:---|
| 원문·해시 | 서명 대상과 고정 길이 지문 생성 | SHA-256/SHA-3 사용, 충돌 저항성 필요 |
| 개인키 | 서명값 생성 | HSM/KMS 보관, 접근권한 최소화 |
| 공개키·인증서 | 서명 검증과 소유자 확인 | X.509 체인, EKU 확인 |
| 서명 알고리즘 | RSA-PSS, ECDSA, EdDSA | RSA PKCS#1 v1.5 신규 적용 지양 |
| 폐지·시각 증명 | 인증서 유효성·서명 시점 확인 | OCSP, CRL, TSA |

> 요약: 전자 서명 구조는 해시, 개인키 서명, 공개키 검증, 인증서 신뢰 확인으로 구성됨.

---

## Ⅲ. 동작원리 및 흐름도

```text
원문 작성 -> 해시 계산 -> 개인키 서명 -> 원문·서명 배포
  -> 공개키 인증서 검증 -> 해시 재계산 -> 서명 검증 -> 결과 기록
```

| 단계 | 처리 내용 | 검증 기준 |
|:---:|:---|:---|
| 1 | 원문 해시 계산 | SHA-256 이상, canonicalization 확인 |
| 2 | 개인키로 서명값 생성 | HSM 서명 정책, 승인 워크플로 |
| 3 | 원문·서명·인증서 전달 | 인증서 체인 포함, 알고리즘 식별 |
| 4 | 공개키로 서명 검증 | 해시 일치, 서명 알고리즘 일치 |
| 5 | 폐지·타임스탬프 확인 | OCSP good, TSA 시각 검증 |

> 요약: 전자 서명 검증은 수학적 서명 확인과 인증서 유효성 확인을 모두 통과해야 완료됨.

## Ⅳ. 특징

| 구분 | 암호화 | 전자 서명 | 판단 포인트 |
|:---|:---|:---|:---|
| 보안 속성 | 기밀성 중심 | 인증·무결성·부인방지 | 숨김과 증명 기능 구분 |
| 키 사용 | 수신자 공개키로 암호화, 수신자 개인키로 복호화 | 서명자 개인키로 서명, 공개키로 검증 | 키 방향 반대 |
| 적용 대상 | 데이터 본문 | 본문 해시값 | 대용량 파일도 해시 후 서명 |
| 운영 기준 | 키 분배, 복호화 권한 | 개인키 보호, 폐지 확인, 감사로그 | HSM·OCSP 필수 |

> 요약: 전자 서명은 기밀성이 아니라 신원·무결성·부인방지를 제공하며 키 사용 방향이 암호화와 다름.

## Ⅴ. 심화 비교 및 적용 판단

| 비교 축 | 기존/대안 | 본 키워드 | 선택 기준 |
|:---|:---|:---|:---|
| 구조 | MAC/HMAC | Digital Signature | 다자 검증·부인방지 필요 시 서명 |
| 비용/성능 | RSA-PSS | ECDSA/EdDSA | 인증서 호환, 서명 크기, 검증 처리량 |
| 운영/위험 | 파일 해시 게시 | 코드 서명·문서 서명 | 배포 경로 신뢰와 감사 추적 필요 시 적용 |

> 요약: 단일 조직 내부 무결성은 HMAC, 외부 제3자 검증과 부인방지는 전자 서명을 선택함.

| 리스크 | 원인 | 대응 방안 | 확인 지표 |
|:---|:---|:---|:---|
| 개인키 유출 | 파일 기반 키 저장, 과도한 권한 | HSM/KMS, MFA, 승인 기반 서명 | 개인키 export 0건, 감사로그 100% |
| 서명 위조 수용 | 인증서 폐지 미확인 | OCSP stapling, CRL 동기화 | 폐지 인증서 허용 0건 |
| 알고리즘 노후화 | SHA-1, RSA 1024 사용 | SHA-256 이상, RSA 2048/3072, ECDSA P-256 | 취약 알고리즘 탐지 0건 |

> 요약: 전자 서명 위험은 개인키 보호, 폐지 확인, 알고리즘 수명 관리로 통제해야 함.

| 점검 항목 | 목표 기준 | 측정 방법 |
|:---|:---|:---|
| 키 보호 | HSM FIPS 140-2/140-3, 키 export 금지 | HSM 정책, KMS 감사로그 |
| 검증 품질 | 서명·체인·폐지·시각 4종 검증 | 검증 로그, OCSP 응답률 |
| 복구 절차 | 키 유출 시 24시간 내 폐지·재서명 | 사고훈련, CRL 반영 시간 |

> 요약: 전자 서명 운영은 서명 생성보다 검증 로그와 키 유출 복구 시간을 지표로 관리함.

## Ⅵ. 실무 적용 및 결론

**적용 방안 3개 (필수 — 단계별 또는 항목별):**
1. 알고리즘 정책: 신규 시스템은 SHA-256 이상, RSA-PSS 2048/3072 또는 ECDSA P-256/Ed25519 적용.
2. 키 관리: 서명 개인키는 HSM/KMS에 보관하고, 운영자 직접 export 금지와 2인 승인 서명 절차 적용.
3. 검증 체계: 인증서 체인, EKU, OCSP/CRL, RFC 3161 타임스탬프를 검증 파이프라인에 포함.

**결론 (2줄):**
- 기술사 판단: 외부 제3자 검증과 부인방지가 필요하면 전자 서명, 내부 메시지 무결성만 필요하면 HMAC 선택.
- 향후 방향: 장기 보관 문서와 코드 서명은 ML-DSA 등 PQC 서명 전환 계획과 타임스탬프 보존 정책 필요.
