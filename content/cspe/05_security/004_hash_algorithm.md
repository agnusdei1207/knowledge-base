# 📖 【암기용】 개념 완전 이해

> 목적: 해시 알고리즘을 처음 보는 사람도 완전하게 이해하게 만든다. 시험 답안 양식이 아니라, 이해를 위한 설명이다.

## 한눈에
- **개요**: 임의 길이 입력을 고정 길이 다이제스트로 변환하는 단방향 함수
- **왜 필요한가**: 파일 변조 확인, 비밀번호 저장, 전자서명 전 처리, 블록체인 무결성 검증처럼 원문 전체를 매번 비교하지 않고도 동일성·무결성을 판단해야 한다.
- **핵심 직관**: 문서의 지문을 만드는 기능이다. 지문만 보고 원문을 복원할 수 없어야 하고, 서로 다른 문서가 같은 지문을 갖기 어려워야 함

## 깊이 이해
- **배경·문제의식**: MD5·SHA-1은 충돌 공격이 실증되어 전자서명과 인증서에서 제외되었다. SHA-256·SHA-3는 충돌 저항성과 표준성을 제공해 무결성 검증의 기본 도구로 사용됨.
- **작동 원리**: 입력을 패딩하고 블록 단위로 압축 함수를 반복해 고정 길이 값을 만든다. 작은 입력 변화가 출력 전체를 바꾸는 avalanche effect를 갖도록 설계됨.
- **비유**: 책 전체 내용을 한 장의 바코드로 요약하는 방식이다. 책 한 글자만 바뀌어도 바코드가 달라져야 하며, 바코드에서 책 원문을 되돌릴 수 없어야 함.
- **구체 예시**: SHA-256은 256-bit 다이제스트를 생성하고, 파일 배포 시 `sha256sum` 값 비교로 다운로드 변조를 확인한다. SHA-3는 Keccak sponge 구조를 사용함.
- **흔한 오해·주의점**: 해시는 암호화가 아니다. 복호화 키가 없고 원문 복원이 목적이 아니며, 인증이 필요하면 HMAC처럼 비밀키를 결합해야 함.

## 연결 개념
- HMAC — 비밀키를 결합해 메시지 인증 코드 생성
- 전자서명 — 원문 대신 해시값에 서명해 처리량과 무결성 확보
- 비밀번호 해싱 — salt·stretching·Argon2/bcrypt로 사전 공격 비용 증가

# 📝 【답안용】 시험 답안 템플릿

> 목적: 시험장에서 25분에 그대로 쓰는 답안 양식. 수치·표준명·기술명 중심으로 작성한다.

## 핵심 인사이트 (3줄 요약)

> 1. **본질**: 해시 알고리즘은 임의 길이 데이터를 고정 길이 다이제스트로 압축하는 단방향 무결성 함수이다.
> 2. **가치**: SHA-256·SHA-3는 파일 검증, 전자서명, 블록체인, 감사로그에서 변조 탐지 기준값을 제공함.
> 3. **판단 포인트**: 충돌 저항성, 역상 저항성, salt·HMAC 사용 여부, MD5·SHA-1 제거가 핵심 판단 기준임.

## 출제 의도 및 답안 포인트

| 출제 의도 | 반드시 짚을 핵심 | 감점 회피 포인트 |
|:---|:---|:---|
| 변조 탐지와 무결성 검증을 인증·부인방지·비밀번호 저장 통제와 구분하는 보안 판단 역량 확인 | SHA-256·SHA-3, 충돌·역상 저항성, MD5/SHA-1 제거, HMAC 결합, 전자서명, Argon2id·bcrypt salt | 해시를 암호화로 설명, 단순 해시를 인증으로 오인, 비밀번호에 SHA-256 단독 적용 |

> 요약: 해시 답안은 무결성 탐지 기능을 중심으로 인증은 HMAC, 부인방지는 전자서명으로 분리해야 한다.

---

## Ⅰ. 개요 및 필요성

- 개요: 입력의 고정 길이 지문
- 배경: 원문 전체 비교만으로는 대용량 파일·인증서·배포 패키지의 변조 확인과 무결성 추적이 어려움.
- 필요성: SHA-256·SHA-3 같은 충돌 저항 해시를 적용하고 MD5·SHA-1을 제거해 전자서명·소프트웨어 배포 무결성을 검증함.

---

## Ⅱ. 구조 및 구성요소

```text
Message -> Padding -> Block Split -> Compression/Sponge
        -> Digest -> Compare/Sign/Store
Salt/Key -> Password Hash or HMAC
```

| 구성요소 | 역할 | 특이사항 |
|:---|:---|:---|
| 입력 메시지 | 파일·로그·문서 원문 | 임의 길이 데이터 |
| 패딩·블록화 | 압축 함수 입력 정렬 | SHA-256은 512-bit 블록 |
| 압축·스폰지 함수 | 내부 상태 갱신 | SHA-2 Merkle-Damgard, SHA-3 Keccak |
| 다이제스트 | 비교·서명 대상 | SHA-256은 256-bit 출력 |

> 요약: 해시는 입력을 블록으로 나누어 내부 상태를 반복 갱신하고 고정 길이 다이제스트를 산출한다.

---

## Ⅲ. 동작원리 및 흐름도

```text
입력 수집 -> 패딩 -> 블록별 해시 계산 -> 다이제스트 생성
-> 기준 다이제스트와 비교 -> 일치/불일치 판정
```

| 단계 | 처리 내용 | 검증 기준 |
|:---:|:---|:---|
| 1 | 입력 데이터와 알고리즘 선택 | SHA-256 이상, MD5·SHA-1 제외 |
| 2 | 패딩 후 블록 단위 처리 | 표준 구현 사용 |
| 3 | 다이제스트 생성·저장 | 256-bit 이상 출력 |
| 4 | 기준값과 상수시간 비교 | 변조 탐지, timing leak 방지 |

> 요약: 해시는 표준 알고리즘으로 다이제스트를 만들고 기준값과 비교해 무결성 위반을 판단한다.

---

## Ⅳ. 특징

| 구분 | 내용 | 판단 포인트 |
|:---|:---|:---|
| 장점 | 고정 길이 지문으로 무결성 확인 | 파일 크기와 무관하게 256-bit 비교 |
| 한계 | 기밀성·송신자 인증 제공 안 함 | 인증 필요 시 HMAC·전자서명 결합 |
| 비교 대상 | MD5·SHA-1·SHA-256·SHA-3 | MD5/SHA-1 충돌 취약, SHA-256 이상 사용 |

> 요약: 해시는 무결성 검증 도구이며, 인증성과 기밀성이 필요하면 HMAC·서명·암호화를 추가해야 한다.

---

## Ⅴ. 심화 비교 및 적용 판단

| 구분 | 기존/대안 | 본 키워드 | 선택 기준 |
|:---|:---|:---|:---|
| 구조 | 암호화 | 해시 다이제스트 | 원문 복원 불필요, 변조 확인 목적 |
| 비용/성능 | 원문 전체 비교 | 256-bit 다이제스트 비교 | 대용량 파일 배포·로그 검증 |
| 운영/위험 | MD5·SHA-1 | SHA-256·SHA-3 | 충돌 저항성 요구 시 SHA-2 이상 |

> 요약: 무결성 판단에는 해시를 선택하고, 인증이 필요한 메시지는 HMAC 또는 전자서명을 결합한다.

| 리스크 | 원인 | 대응 방안 | 확인 지표 |
|:---|:---|:---|:---|
| 충돌 공격 | MD5·SHA-1 사용 | SHA-256·SHA-3 전환 | 약한 해시 사용 0건 |
| 비밀번호 탈취 | salt 없는 단순 SHA-256 | Argon2id·bcrypt·PBKDF2 적용 | 계정별 128-bit salt |
| 길이 확장 공격 | Merkle-Damgard 직접 MAC | HMAC-SHA-256 사용 | raw hash MAC 0건 |

> 요약: 해시 리스크는 노후 알고리즘, 비밀번호 저장 오용, MAC 설계 오류에서 발생한다.

| 점검 항목 | 목표 기준 | 측정 방법 |
|:---|:---|:---|
| 알고리즘 | SHA-256 이상, MD5/SHA-1 0건 | SAST·SBOM 스캔 |
| 비밀번호 저장 | Argon2id 또는 bcrypt, salt 128-bit | 계정 DB 샘플 점검 |
| 무결성 검증 | 배포 파일 해시 공개·검증 100% | CI/CD 검증 로그 |

> 요약: 적용 품질은 약한 해시 제거, salt 적용, 배포 무결성 검증률로 판단한다.

---

## Ⅵ. 실무 적용 및 결론

**적용 방안 3개 (필수 — 단계별 또는 항목별):**
1. 파일·소프트웨어 배포: SHA-256 체크섬과 전자서명 동시 제공, CI에서 다운로드 후 해시 검증 자동화
2. 비밀번호 저장: SHA-256 단독 저장 금지, Argon2id 또는 bcrypt에 128-bit salt와 비용 파라미터 적용
3. 메시지 인증: API 요청 검증은 raw hash가 아니라 HMAC-SHA-256 사용, nonce·timestamp로 재전송 차단

**결론 (2줄):**
- 기술사 판단: 무결성 검증은 SHA-256 이상, 인증은 HMAC·전자서명, 비밀번호는 전용 KDF로 분리해야 함
- 향후 방향: SHA-3·BLAKE3 등 대안은 규제·상호운용 요구를 검토해 단계 적용 필요
