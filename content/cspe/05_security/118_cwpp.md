# 📖 【암기용】 개념 완전 이해

> 목적: CWPP를 처음 보는 사람도 VM, 컨테이너, 서버리스 워크로드 보호 범위를 이해하게 만든다. 시험 답안 양식이 아니라, 이해를 위한 친절한 설명이다.

## 한눈에
- **개요**: CWPP는 클라우드에서 실행되는 워크로드의 취약점, 런타임 행위, 침입 징후를 보호하는 보안 체계임
- **왜 필요한가**: 클라우드 워크로드는 VM, 컨테이너, Kubernetes, 서버리스로 계속 생성·폐기된다. 이미지 취약점, 런타임 권한 상승, 비정상 프로세스, 비인가 네트워크 연결을 실행 환경에서 탐지해야 한다.
- **핵심 직관**: 건물 설계도 점검이 CSPM이라면, 실제 입주한 사람과 장비가 이상 행동을 하는지 감시하는 보안요원이 CWPP임

## 깊이 이해
- **배경·문제의식**: 클라우드 보안 사고는 설정 오류만으로 끝나지 않는다. 취약 이미지 배포, 컨테이너 탈출, 웹셸 실행, 암호화폐 채굴 프로세스, 권한 상승 같은 런타임 위협이 발생한다.
- **작동 원리**: CWPP는 에이전트, eBPF, DaemonSet, 이미지 스캐너, 서버리스 센서를 사용해 파일, 프로세스, 네트워크, 시스템콜, 취약점 정보를 수집한다. 기준 행위와 다른 프로세스 실행, 민감 파일 접근, 외부 C2 통신을 탐지하고 차단 또는 격리한다.
- **비유**: 공장 설비가 정상 도면대로 설치됐는지 확인한 뒤에도, 가동 중 온도, 진동, 소음, 출입자를 계속 측정해 고장과 침입을 잡는 방식임
- **구체 예시**: Kubernetes Pod에서 `crypto-miner` 프로세스가 실행되고 외부 3333 포트로 연결되면 CWPP가 1분 이내 알림, 네트워크 격리, Pod 삭제 정책을 실행함
- **흔한 오해·주의점**: CWPP는 CSPM과 다르다. CSPM은 제어면 설정, CWPP는 데이터면에서 실행되는 워크로드와 런타임 행위 보호가 중심임

## 연결 개념
- 컨테이너 이미지 스캔 — 배포 전 CVE와 Secret 점검
- Falco/eBPF — 런타임 시스템콜 기반 탐지
- Kubernetes 보안 — Pod Security, NetworkPolicy, RBAC와 연계

# 📝 【답안용】 시험 답안 템플릿

> 목적: 시험장에서 25분에 그대로 쓰는 답안 양식. 작성방식(추상표현 금지·수치·도식·문제유형 전환)을 엄격히 지킨다.
> 핵심: CWPP는 클라우드 설정 점검이 아니라 워크로드 생명주기와 런타임 행위를 보호하는 체계로, 이미지·호스트·컨테이너·서버리스 축을 구분해야 한다.

## 핵심 인사이트 (3줄 요약)

> 1. **본질**: CWPP(Cloud Workload Protection Platform)는 VM, 컨테이너, Kubernetes, 서버리스 워크로드의 취약점과 런타임 위협을 보호하는 보안 플랫폼이다.
> 2. **가치**: 배포 전 이미지 취약점, 실행 중 비정상 프로세스, 권한 상승, C2 통신을 워크로드 단위로 탐지·차단한다.
> 3. **판단 포인트**: CSPM은 설정, CWPP는 실행 환경 보호이며 에이전트 방식, eBPF 방식, 서버리스 센서의 적용 범위를 구분해야 한다.

## 출제 의도 및 답안 포인트

| 출제 의도 | 반드시 짚을 핵심 | 감점 회피 포인트 |
|:---|:---|:---|
| 클라우드 워크로드 위협 이해 확인 | VM, 컨테이너, Kubernetes, 서버리스 런타임 보호 | CSPM과 동일한 형상 점검으로 설명 |
| 생명주기 통제 설계 확인 | 이미지 스캔, 배포 정책, 런타임 탐지, 격리 | 배포 전 점검만 쓰고 런타임 대응 누락 |
| 운영 지표 제시 확인 | Critical CVE 조치, 탐지시간, 격리시간, 커버리지 | 제품 기능 나열 후 지표 부재 |

> 요약: CWPP 문제는 워크로드 실행 중 위협을 생명주기 기준으로 탐지·대응하는 역량을 본다.

## Ⅰ. 개요 및 필요성

CWPP는 클라우드 워크로드 런타임 보호 체계이다.
VM, 컨테이너, 서버리스는 배포 속도가 높고 수명이 짧아 취약 이미지, 권한 상승, C2 통신을 사후 수작업으로 추적하기 어렵다.
따라서 이미지 단계부터 실행 단계까지 워크로드 단위 관측과 대응이 필요함.

---

## Ⅱ. 구조 및 구성요소

```text
CI/CD Image -> Registry Scan -> Admission Control -> Runtime Sensor
  / VM Agent
  / K8s DaemonSet/eBPF
  / Serverless Sensor
Runtime Sensor -> Detection Policy -> Alert/Block/Quarantine -> SIEM/SOAR
```

| 구성요소 | 역할 | 특이사항 |
|:---|:---|:---|
| Image Scanner | CVE, Secret, 악성 패키지 탐지 | Critical CVE 배포 차단 |
| Admission Control | Kubernetes 배포 전 정책 집행 | 서명 이미지, Root 금지, 권한 제한 |
| Runtime Sensor | 프로세스, 파일, 네트워크, 시스템콜 관측 | 에이전트, eBPF, DaemonSet 방식 |
| Threat Policy | 비정상 행위와 기준선 비교 | Cryptomining, Reverse Shell, Privilege Escalation |
| Response Integration | 격리, Pod 삭제, 티켓, SIEM 전송 | SOAR 플레이북 연계 |

> 요약: CWPP는 이미지 검사, 배포 제어, 런타임 센서, 위협 정책, 대응 연계를 통해 워크로드를 보호한다.

---

## Ⅲ. 동작원리 및 흐름도

```text
이미지 빌드 -> CVE/Secret 스캔 -> 배포 정책 확인
-> 런타임 행위 수집 -> 이상행위 탐지 -> 격리/차단
-> 사고 분석/재발 방지
```

| 단계 | 처리 내용 | 검증 기준 |
|:---:|:---|:---|
| 1 | 이미지와 패키지 취약점 스캔 | Critical CVE 0건, SBOM 생성 |
| 2 | 배포 전 정책 검사 | 서명 이미지 100%, Privileged Pod 0건 |
| 3 | 실행 중 프로세스·파일·네트워크 관측 | 센서 커버리지 95% 이상 |
| 4 | 기준선 위반과 IOC 탐지 | 탐지시간 5분 이내, 오탐률 5% 이하 |
| 5 | 격리, 종료, 티켓, 포렌식 증적 보존 | 격리 10분 이내, 로그 1년 보존 |

> 요약: CWPP는 배포 전 취약점 차단과 실행 중 행위 탐지를 연결해 워크로드 침해 시간을 줄인다.

## Ⅳ. 특징

| 구분 | 전통 EDR/백신 | CWPP | 수치·판단 포인트 |
|:---|:---|:---|:---|
| 대상 | 고정 서버·단말 | VM, 컨테이너, K8s, 서버리스 | 워크로드 커버리지 95% 이상 |
| 시점 | 파일·프로세스 탐지 중심 | 이미지, 배포, 런타임 전 단계 | Critical CVE 배포 0건 |
| 배치 | 호스트 에이전트 | Agent, eBPF, DaemonSet, API | 컨테이너 수명 분 단위 대응 |
| 대응 | 알림·격리 | Pod 삭제, 네트워크 격리, 함수 차단 | 격리 10분 이내 |

> 요약: CWPP는 클라우드 워크로드의 짧은 수명과 다양한 실행 환경을 고려한 런타임 보호 체계이다.

## Ⅴ. 심화 비교 및 적용 판단

| 비교 축 | 기존/대안 | 본 키워드 | 선택 기준 |
|:---|:---|:---|:---|
| 구조 | 서버 EDR 중심 | VM+컨테이너+서버리스 통합 보호 | Kubernetes 클러스터 3개 이상, 컨테이너 비중 증가 |
| 비용/운영 | 호스트별 에이전트 | eBPF/DaemonSet/서버리스 센서 조합 | 성능 오버헤드 CPU 5% 이하 관리 |
| 위험 | 배포 후 수동 조치 | CI/CD 차단과 런타임 격리 | Critical CVE와 권한 상승 위험 우선 |

> 요약: 컨테이너와 서버리스 비중이 높으면 EDR 단독보다 CWPP 기반 워크로드 보호가 적합하다.

| 리스크 | 원인 | 대응 방안 | 확인 지표 |
|:---|:---|:---|:---|
| 센서 사각지대 | 신규 노드, 서버리스 미연동 | 클러스터 자동 등록, 함수 계정 연동 | 센서 커버리지 95% 이상 |
| 운영 영향 | 과도한 런타임 차단 | 탐지 모드, 예외 승인, 단계 차단 | 차단 오탐률 3% 이하 |
| 취약 이미지 배포 | CI/CD 정책 우회 | Registry 서명, Admission Control | 미서명 이미지 0건 |

> 요약: CWPP 리스크는 커버리지, 오탐, CI/CD 우회이며 자동 등록과 단계 정책으로 통제한다.

| 점검 항목 | 목표 기준 | 측정 방법 |
|:---|:---|:---|
| 취약점 통제 | Critical CVE 0건, High 7일 이내 | 이미지 스캔, SBOM |
| 런타임 탐지 | 위협 탐지 5분 이내, 격리 10분 이내 | CWPP 로그, SOAR |
| 정책 준수 | Privileged Pod 0건, Root 실행 0건 | Admission Controller, K8s API |

> 요약: CWPP 성과는 취약 이미지 차단, 런타임 탐지시간, Kubernetes 정책 준수율로 판단한다.

## Ⅵ. 실무 적용 및 결론

**적용 방안 3개:**
1. CI/CD에 이미지 스캔과 SBOM 생성을 넣고 Critical CVE, Secret 포함, 미서명 이미지는 배포 차단함
2. Kubernetes에는 DaemonSet 또는 eBPF 센서를 배치하고 Privileged Pod 0건, Root 실행 0건, NetworkPolicy 적용률 90% 이상을 기준화함
3. Cryptomining, Reverse Shell, 비인가 파일 접근 탐지 시 10분 이내 격리하고 SIEM/SOAR에 포렌식 증적을 보존함

**결론 (2줄):**
- 기술사 판단: 설정 오류 중심이면 CSPM, 실행 중 워크로드 위협이면 CWPP를 우선 적용하고 컨테이너 환경은 두 통제를 병행해야 함
- 향후 방향: CWPP는 CNAPP에 통합되어 이미지, 런타임, 권한, 형상 위험을 단일 위험 그래프로 분석함
