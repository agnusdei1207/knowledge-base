## Ⅰ. 개요
- **정의**: 서버가 공격자가 지정한 내부/외부 URL로 요청을 대신 수행하게 만드는 취약점
- **배경/필요성**: 클라우드 메타데이터 API 등 내부 자원 접근 경로가 증가하여 SSRF 위험이 높아짐
- **비유**: 회사 직원에게 사내 금고 열쇠를 빌려 외부인이 금고를 여는 것과 유사

| 출제 의도 | 반드시 짚을 핵심 | 감점 회피 포인트 |
|:---|:---|:---|
| SSRF 공격 원리와 방어 기법 | 내부 네트워크 접근·메타데이터 탈취 경로 | Blind SSRF와 일반 SSRF 구분 필요 |

> 요약: 서버의 신뢰된 네트워크 위치를 악용하여 내부 자원에 접근하는 공격임

## Ⅱ. 구성요소
```text
Attacker -> Vulnerable Server -> Internal Network
                |                     |
                v                     v
           URL Parameter       Metadata API / DB
```

| 구성요소 | 설명 | 비유 |
|:---|:---|:---|
| URL 입력 파라미터 | 서버가 외부 입력 URL로 요청을 생성하는 진입점 | 대리 주문서의 배달 주소란 |
| 내부 네트워크 자원 | 메타데이터 API·DB 등 외부 차단된 자원 | 사내 전용 서류함 |
| 응답 데이터 유출 경로 | 서버 응답을 통해 내부 정보가 공격자에게 전달되는 채널 | 내부 메모가 외부 팩스로 전송됨 |

> 요약: URL 파라미터를 통해 서버가 내부 자원에 접근하고 결과를 유출하는 구조임

## Ⅲ. 절차
```text
URL 삽입 -> 서버 요청 생성 -> 내부 자원 접근 -> 응답 탈취
```
- 1단계: 공격자가 요청 파라미터에 내부 IP·메타데이터 URL을 삽입
- 2단계: 서버가 해당 URL로 HTTP 요청을 생성하여 전송
- 3단계: 내부 네트워크의 메타데이터 API·관리 콘솔 등에 접근
- 4단계: 서버 응답에 포함된 내부 정보를 공격자가 수신·탈취

> 요약: 외부 입력 URL을 서버가 신뢰하여 내부 요청을 대행하는 4단계 공격 흐름임

## Ⅳ. 문제점
- 입력 검증 부재: URL 파라미터 화이트리스트 미적용 — 임의 주소로 요청 가능
- 네트워크 격리 미흡: 서버와 메타데이터 API 간 접근 제어 없음 — 내부 자원 노출
- Blind SSRF 탐지 어려움: 응답이 직접 반환되지 않아 — 공격 여부 판별이 지연됨

> 요약: 입력 검증·네트워크 격리·탐지 역량 부족이 SSRF를 가능하게 함

## Ⅴ. 개선방안
1. 단기: 허용 URL 화이트리스트 적용 및 내부 IP 대역 차단 필터 구현
2. 중기: 메타데이터 API에 IMDSv2 등 토큰 기반 접근 제어 적용
3. 장기: 아웃바운드 트래픽 모니터링으로 비정상 내부 요청을 실시간 탐지

> 요약: 화이트리스트·접근제어·모니터링을 조합하여 SSRF 공격면을 차단함

## Ⅵ. 전망
- 발전 방향: 클라우드 네이티브 환경에서 SSRF 방어가 인프라 수준으로 내재화될 것임
- 기술사적 판단: OWASP Top 10 A10에 포함될 만큼 중요도가 높은 위협임
- 기술사 제언: 서버 아웃바운드 요청에 대한 제로 트러스트 정책 수립을 제언함
