## 미리 알고가기

- 소프트웨어 공급망은 소스코드, 오픈소스 의존성, 빌드 서버, 패키지 저장소, 배포 산출물을 모두 포함함
- SBOM은 어떤 구성요소와 버전이 제품 안에 들어 있는지 적은 소프트웨어 성분표임
- VEX는 알려진 취약점이 내 제품에 실제 영향이 있는지 없는지를 설명하는 문서임

## Ⅰ. 개요

- **정의/개념**: 소프트웨어 공급망 보안은 개발부터 빌드와 배포까지 이어지는 경로에서 위변조와 취약 구성요소 유입을 막는 체계이며 SBOM과 VEX는 그 상태를 설명하는 핵심 문서임
- **배경/필요성**: 현대 소프트웨어는 수많은 오픈소스와 자동화 도구 위에서 만들어지므로 한 구성요소 침해가 여러 제품과 고객으로 빠르게 번질 수 있음

## Ⅱ. 특징

- 코드 자체뿐 아니라 의존성, 빌드 경로, 배포 산출물까지 관리 범위에 넣음
- 무엇이 들어 있는지 보여주는 SBOM과 실제 영향 여부를 알려주는 VEX를 함께 써야 함
- 취약점 수집보다 출처 검증과 변경 추적이 더 중요해짐
- 문서만 만들고 서명과 검증을 붙이지 않으면 신뢰하기 어려움

## Ⅲ. 종류 및 비교

| 판단 기준 | SBOM | VEX |
|:---|:---|:---|
| 알려 주는 것 | 제품에 포함된 구성요소와 버전 | 특정 취약점이 실제 영향이 있는지 여부 |
| 주된 목적 | 구성요소 가시성 확보 | 불필요한 경보와 잘못된 패치 우선순위 축소 |
| 쓰는 시점 | 빌드와 배포 시점 | 취약점 공개 후 영향 판단 시점 |
| 함께 필요한 이유 | 무엇이 들어 있는지 알아야 함 | 그중 무엇이 진짜 위험한지 알아야 함 |

## Ⅳ. 구성요소 및 구조

| 구성요소 | 설명 |
|:---|:---|
| 소스와 의존성 | 개발자가 가져오는 외부 라이브러리와 패키지 원천임 |
| 빌드 파이프라인 | 코드를 산출물로 바꾸는 자동화 경로이며 변조 표적이 되기 쉬움 |
| 아티팩트 저장소 | 이미지와 패키지를 보관하고 배포하는 지점임 |
| SBOM 생성기 | 빌드 시점에 포함 구성요소와 버전을 기록함 |
| VEX 발행 체계 | 특정 취약점의 실제 영향 상태와 대응 상태를 전달함 |

```text
소스/의존성 -> 빌드 -> 산출물 생성 -> SBOM 작성 -> 취약점 매칭 -> VEX 발행 -> 배포 판단
```

## Ⅴ. 원리 및 절차 흐름도

```text
의존성 수집 -> 빌드 수행 -> SBOM 생성 -> 취약점 대조 -> 영향 판단 -> VEX 배포 -> 수정 우선순위 결정
```

1. **의존성 수집**: 빌드에 포함된 라이브러리와 패키지를 확인함
2. **빌드 수행**: 산출물을 만들고 해시와 출처 정보를 기록함
3. **SBOM 생성**: 구성요소 목록과 버전을 문서화함
4. **취약점 대조**: 공개 취약점과 SBOM을 연결함
5. **영향 판단**: 실제 노출 여부를 VEX로 정리하고 조치 순서를 정함

## Ⅵ. 실무 적용 및 유의점

1. 오픈소스 의존성이 많은 서비스는 빌드마다 SBOM을 만들고 영향 있는 취약점만 빠르게 추려야 하며 SBOM 생성률과 미해결 실제 영향 취약점 수로 확인함
2. 패키지 이름과 버전 매핑이 틀리면 잘못된 경보가 늘어나므로 식별자 품질과 VEX 최신 상태를 함께 관리하고 오탐 판정 비율과 오래된 VEX 문서 수로 점검함

## Ⅶ. 결론

- 공급망 보안은 취약점 목록을 더 길게 만드는 일이 아니라 무엇이 들어왔고 실제로 무엇이 위험한지 끝까지 추적하는 일이므로 SBOM과 VEX를 운영 흐름에 붙여야 함
