# 📖 【암기용】 개념 완전 이해

> 목적: 소프트웨어 공급망 보안과 SBOM·VEX를 처음 봐도 이해하게 만든다. 시험 답안 양식이 아니라, 이해를 위한 설명이다.

## 한눈에
- **개요**: 공급망 보안은 코드, 오픈소스, 빌드, 배포, 운영 전 과정에서 위변조와 취약 구성요소를 관리하는 보안 체계이다.
- **왜 필요한가**: 현대 소프트웨어는 수백 개 라이브러리와 CI/CD 도구에 의존하므로 한 구성요소 침해가 다수 서비스로 확산된다.
- **핵심 직관**: SBOM은 제품 성분표, VEX는 성분 중 어떤 취약점이 실제 제품에서 exploitable인지 알려주는 판정서임.

## 깊이 이해
- **배경·문제의식**: SolarWinds, Log4j, xz Utils 사례처럼 개발자 PC, 빌드 서버, 패키지 저장소, 의존성 중 하나가 변조되면 정상 업데이트 경로로 악성 코드가 배포될 수 있다.
- **작동 원리**: SBOM은 구성요소명, 버전, 공급자, 해시, 라이선스, 의존관계를 기계 판독 형식으로 기록한다. VEX는 특정 CVE가 제품에 영향 있음, 영향 없음, 조사 중, 수정됨 같은 상태를 제공한다.
- **비유**: 식품 알레르기 관리에서 원재료표가 SBOM이고, 특정 성분이 실제로 포함되어 위험한지 제조사가 판정해 알리는 문서가 VEX이다.
- **구체 예시**: CycloneDX 또는 SPDX SBOM을 빌드 시 생성하고, Log4j CVE가 발견되면 VEX로 "해당 컴포넌트 미사용 경로라 exploitable 아님" 또는 "버전 2.17.1로 수정됨"을 배포한다.
- **흔한 오해·주의점**: SBOM은 취약점 자동 제거 도구가 아니다. SBOM 품질, 패키지 식별자(PURL/CPE), VEX 신뢰도, 패치 SLA가 함께 있어야 운영 가치가 생긴다.

## 연결 개념
- SLSA: 빌드 출처, 무결성, provenance 성숙도 모델
- 코드 서명·Sigstore: 산출물 위변조 검증
- 취약점 관리: CVE, CVSS, EPSS, KEV와 SBOM 매칭

# 📝 【답안용】 시험 답안 템플릿

> 목적: 시험장에서 25분에 그대로 쓰는 답안 양식. 공급망 공격면, SBOM·VEX 역할, CI/CD 통제를 연결한다.
> 핵심: 구성요소 목록만 만드는 답안이 아니라 취약점 우선순위와 빌드 무결성 검증까지 포함한다.

## 핵심 인사이트 (3줄 요약)

> 1. **본질**: 소프트웨어 공급망 보안은 코드 작성부터 배포까지 의존성, 빌드, 아티팩트, 배포 경로의 무결성과 취약점을 통제하는 체계이다.
> 2. **가치**: SBOM은 구성요소 가시성을 제공하고, VEX는 CVE 영향 여부를 판정해 취약점 대응 대상을 실제 exploitable 항목으로 좁힌다.
> 3. **판단 포인트**: CycloneDX·SPDX 형식, PURL/CPE 식별, 서명·provenance, CVE 매칭, VEX 상태값, 패치 SLA를 함께 설계해야 한다.

## Ⅰ. 개요 및 필요성

- 개요: SW 산출물 무결성 통제
- 배경: 오픈소스 의존성, CI/CD, 패키지 저장소, 컨테이너 이미지가 연결되면서 취약점과 위변조가 정상 배포 경로로 확산될 수 있음.
- 필요성: SPDX·CycloneDX SBOM과 CSAF VEX로 구성요소 식별, 영향 판정, 패치 우선순위를 증적화해야 함.

---

## Ⅱ. 구조 및 구성요소

```text
Source Code -> Dependency -> Build Pipeline -> Artifact Registry -> Deployment
      |             |              |                    |
      +-> SBOM      +-> CVE Match  +-> Provenance       +-> VEX Status
```

| 구성요소 | 역할 | 특이사항 |
|:---|:---|:---|
| SBOM | 구성요소명, 버전, 공급자, 해시, 의존관계 기록 | CycloneDX, SPDX, PURL, CPE |
| VEX | CVE별 제품 영향 상태와 조치 상태 제공 | affected, not affected, under investigation, fixed |
| Provenance | 누가·어디서·어떤 소스로 빌드했는지 증명 | SLSA, in-toto, Sigstore |
| Policy Gate | 취약점·서명·라이선스 기준으로 배포 차단 | critical CVE, unsigned artifact, forbidden license |

> 요약: 공급망 보안은 SBOM으로 구성요소를 식별하고, VEX와 provenance로 취약점 영향과 빌드 출처를 검증한다.

## Ⅲ. 동작원리 및 흐름도

```text
코드 커밋 -> 의존성 해석 -> SBOM 생성 -> 취약점 매칭
-> VEX 영향 판정 -> 서명·provenance 검증
-> 정책 게이트 통과 -> 배포·운영 모니터링
```

| 단계 | 처리 내용 | 검증 기준 |
|:---:|:---|:---|
| 1 | 빌드 시 SBOM 생성·서명 | CycloneDX/SPDX, SHA-256, Sigstore |
| 2 | SBOM을 CVE·KEV·EPSS와 매칭 | critical CVE, KEV 포함 여부 |
| 3 | VEX로 영향 여부·조치 상태 판정 | affected, not affected, fixed 상태 |
| 4 | 정책 게이트로 배포 허용·차단 | critical affected CVE 0건, 서명 검증 100% |

> 요약: SBOM은 구성요소를 만들고 VEX는 취약점 영향을 판정하며, 정책 게이트는 배포 가능 여부를 결정한다.

## Ⅵ. 실무 적용 및 결론

**적용 방안 3개 (필수 - 단계별 또는 항목별):**
1. CI 단계에서 CycloneDX 또는 SPDX SBOM을 생성하고 이미지 digest, PURL, SHA-256, 라이선스 정보를 artifact로 보관함
2. CVE·KEV·EPSS 매칭 후 VEX 상태를 등록해 `affected critical`은 배포 차단, `not affected`는 근거와 만료일을 기록함
3. Sigstore·in-toto로 이미지 서명과 provenance를 검증하고 SLSA L3 수준의 격리된 빌드·검증 가능한 출처를 목표로 함

**결론 (2줄):**
- 기술사 판단: 규제·대외 납품 제품은 SBOM 제출을 기본값으로 두고, 운영 서비스는 VEX와 정책 게이트까지 연결해야 함
- 향후 방향: SBOM은 정적 목록에서 벗어나 런타임 사용 여부, VEX 상태, 서명 검증을 포함한 지속적 공급망 위험 점수로 확장되어야 함
