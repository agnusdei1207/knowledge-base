## 미리 알고가기

- 에이전트는 모델이 도구를 골라 외부 시스템에 실제 작업을 수행하는 구조임
- 최소 권한은 꼭 필요한 기능과 권한만 주는 보안 원칙임
- 사람 승인 절차는 삭제, 송금, 발송 같은 큰 행동을 실행 전에 다시 확인하는 통제임

## Ⅰ. 개요

- **정의/개념**: LLM06 과도한 에이전시는 에이전트가 필요 이상으로 많은 기능, 권한, 자율성을 받아 예상 밖의 위험 행동을 실행하는 취약점임
- **배경/필요성**: 생성형 AI가 읽기와 요약을 넘어 메일 발송, 결제, 파일 수정까지 맡기 시작하면서 잘못된 판단 한 번이 바로 실제 피해로 이어질 수 있음

## Ⅱ. 특징

- 모델 출력 오류가 실제 시스템 조작으로 이어질 때 피해가 커짐
- 문제의 핵심은 모델 성능보다 도구 범위와 권한 범위가 너무 넓다는 데 있음
- 과도한 기능, 과도한 권한, 과도한 자율성이 함께 나타나는 경우가 많음
- 프롬프트 인젝션이 없어도 환각이나 애매한 질문만으로 사고가 날 수 있음

## Ⅲ. 종류 및 비교

| 판단 기준 | 최소 권한 에이전트 | 과도한 에이전시 |
|:---|:---|:---|
| 도구 범위 | 필요한 기능만 노출함 | 읽기용 업무에도 삭제·전송 기능까지 노출함 |
| 권한 범위 | 사용자별 최소 권한 토큰을 씀 | 공용 고권한 계정을 넓게 씀 |
| 실행 방식 | 고위험 작업 전 승인 절차가 있음 | 모델 판단만으로 바로 실행함 |
| 운영 위험 | 피해 반경이 제한됨 | 한 번의 오판이 대규모 피해로 번짐 |

## Ⅳ. 구성요소 및 구조

| 구성요소 | 설명 |
|:---|:---|
| 사용자 요청 | 에이전트가 수행할 업무를 시작하는 입력임 |
| 계획기 | 어떤 도구를 어떤 순서로 쓸지 결정함 |
| 도구 목록 | 검색, 수정, 삭제, 전송처럼 실제 기능을 제공함 |
| 권한 문맥 | 어떤 사용자 권한으로 실행할지 정함 |
| 승인 게이트 | 영향이 큰 작업은 다시 확인해 막는 계층임 |

```text
사용자 요청 -> 에이전트 계획 -> 도구 선택 -> 권한 확인 -> 실행 또는 승인 요청
```

## Ⅴ. 원리 및 절차 흐름도

```text
요청 입력 -> 에이전트가 과한 도구 선택 -> 넓은 권한으로 실행 -> 승인 없이 변경 발생 -> 실제 피해 발생
```

1. **요청 입력**: 사용자가 요약이나 조회 같은 작업을 요청함
2. **과한 도구 선택**: 에이전트가 필요 이상으로 강한 기능을 가진 도구를 고름
3. **넓은 권한 실행**: 사용자별 권한 대신 공용 고권한 계정으로 접속함
4. **승인 없는 변경**: 삭제, 전송, 수정 같은 작업을 바로 수행함
5. **실제 피해 발생**: 데이터 훼손이나 잘못된 외부 발송이 일어남

## Ⅵ. 실무 적용 및 유의점

1. 메일, 파일, 결제를 다루는 에이전트는 읽기 전용을 기본값으로 두고 고위험 작업은 사람 승인을 거치게 해야 하며 자동 승인된 고영향 작업 수와 모의 공격 성공률로 점검함
2. 외부 플러그인과 서드파티 도구를 붙일 때는 쓰지 않는 기능과 권한을 먼저 제거하고 남은 고권한 도구 수와 사용자 문맥 미적용 실행 건수로 확인함

## Ⅶ. 결론

- LLM06은 모델이 똑똑한가보다 도구와 권한을 얼마나 좁혔는가가 더 중요한 위험 항목임
