## 1. 한눈에 이해하기 (Core Intuition)
- **정의**: 컨테이너(도커)를 실행할 때 서버의 **'최고 관리자 권한(Root)'을 뺏어버리고, 권한이 1도 없는 '일반 사용자(쪼랩) 권한'만으로도 컨테이너가 정상적으로 돌아가게 만드는 최신 보안 실행 방식**입니다.
- **필요성**: 기본적으로 도커 엔진은 리눅스의 '신'이라고 불리는 Root(관리자) 권한으로 돌아갑니다. 해커가 컨테이너 하나를 해킹해서 얇은 가벽(네임스페이스)을 찢고 밖(호스트 서버)으로 탈출하면? 해커가 그 즉시 서버 전체를 지배하는 '신(Root)'이 되어버리는 대재앙이 벌어집니다. 이 "컨테이너 탈옥(Escape) = 즉각적인 서버 장악"이라는 최악의 공식을 끊어내기 위해 등장했습니다.
- **핵심 직관**: **"무기 없는 교도소 간수와 가짜 왕관"**. 
  - 과거 (Rootful 도커): 교도소 간수(도커 엔진)가 실탄이 장전된 기관총(Root 권한)을 메고 감방(컨테이너) 안으로 들어가서 밥을 줍니다. 죄수가 간수를 기절시키고 총을 뺏으면 즉시 교도소 전체를 점령합니다.
  - **Rootless 컨테이너**: 간수는 감방에 들어갈 때 모든 무기를 밖에 두고 비무장 상태(일반 사용자 권한)로 들어갑니다. 감방 안에서 죄수(앱)는 자기가 기관총을 든 왕(가짜 Root)인 줄 알고 으스대며 놀지만, 만약 벽을 뚫고 밖(호스트)으로 나오더라도 그의 손에는 기관총이 아예 없습니다(진짜 쪼랩 유저). 해커는 당황하며 아무것도 부수지 못합니다.

## 2. 왜 중요한가? (Background & Value)
- **등장 배경**: 컨테이너가 해킹당하는 가장 흔한 루트가 컨테이너를 관리자(Root)로 돌리기 때문이라는 사실이 뼈저리게 증명되었습니다. 하지만 기존에는 도커 엔진 자체가 워낙 시스템 깊숙한 곳을 건드려야 해서 무조건 Root 권한이 필요했습니다. 리눅스 커널 기술(User Namespace 매핑 등)이 발전하면서, 2019년경부터 "엔진 자체를 쪼랩으로 돌리자!"는 패러다임이 Podman(포드맨) 등 차세대 엔진을 중심으로 폭발적으로 확산되었습니다.
- **가치**: "피해의 완벽한 억제(Containment)". 해커가 수백억짜리 제로데이 취약점을 써서 컨테이너 밖으로 기어 나와도, 할 수 있는 건 자기 폴더 안의 텍스트 파일 몇 개 지우는 것뿐입니다. 서버 포맷, 방화벽 해제, 딴 사용자 패스워드 훔치기 등 치명적인 타격이 100% 원천 불가능해집니다.

## 3. 어떻게 작동하는가? (Mechanism)
Rootless의 마법은 리눅스의 '사용자 이름표 바꿔치기(User Namespace Remapping)' 기술로 구현됩니다.

1. **컨테이너 안에서의 환상 (가짜 신)**
   - 컨테이너 안의 앱(예: 웹 서버)은 "나는 포트 80번(관리자 전용 포트)도 열고 파일 시스템도 다 부술 수 있는 위대하신 Root(번호 0번) 님이시다!"라고 굳게 믿으며 돌아갑니다. 앱 작동에 전혀 에러가 안 납니다.
2. **환전소의 이름표 바꿔치기 (User Namespace)**
   - 앱이 "나 Root(0번)인데 폴더 하나 만들어줘"라고 진짜 서버(호스트 리눅스 커널)에 요청합니다.
   - 중간에 있는 통역기(User Namespace)가 이 요청의 이름표를 몰래 바꿔버립니다. **"호스트님, 이 컨테이너는 자기가 0번인 줄 아는데, 사실 우리 서버 기준으로는 제일 힘없는 '100000번' 쪼랩 사용자입니다. 100000번 권한으로 폴더 하나만 만들어주세요."**
3. **완벽한 권한 강등 방어**
   - 만약 해커가 밖으로 탈출해서 "나 Root 0번이야! 서버 다 포맷해!"라고 명령을 날립니다.
   - 호스트 커널은 콧방귀를 뀝니다. "뭔 소리야, 네 진짜 번호표는 100000번 쪼랩이잖아. 권한 없음(Permission Denied)! 넌 아무것도 못 지워!"

## 4. 실전 활용 및 예시 (Real-world Application)
- **구체적 사례**: 
  - 과거의 왕좌였던 도커(Docker) 데몬은 Root가 필수였지만, 레드햇(Red Hat)이 만든 최신 컨테이너 엔진인 **Podman(포드맨)** 은 아예 설계부터 Rootless를 기본 철학으로 달고 나왔습니다. 데몬(상주 프로그램) 없이 사용자(1000번)가 명령을 치면 그 권한 그대로 컨테이너가 뜹니다. 보안이 생명인 글로벌 금융사나 핀테크 기업들은 개발 표준 엔진을 아예 Docker에서 Podman으로 전면 교체(Migration)하는 추세입니다.
- **주의점 및 흔한 오해**: 
  - "이거 무조건 쓰면 되겠네요?" $\rightarrow$ 단점도 있습니다. Rootless로 돌리면, 일반 쪼랩 권한이기 때문에 **1번부터 1024번까지의 포트(예: HTTP 80번 포트)를 열지 못합니다.** (리눅스 보안 규정상 1024번 이하 포트는 진짜 Root만 열 수 있음). 그래서 포트를 8080번 같은 걸로 바꿔서 써야 하고, 네트워크 설정이 조금 더 까다로워지는 운영상의 귀찮음(Friction)이 존재합니다.

## 5. 핵심 비교 및 연결 개념 (Relation)
- **Rootful 컨테이너 (기존 Docker)**: 빠르고 설정이 쉽지만, 벽 하나만 부수면 서버 전체가 해커의 손에 넘어감 (고위험).
- **Rootless 컨테이너 (Podman, Rootless Docker)**: 포트 번호 등을 조금 번거롭게 설정해야 하지만, 벽을 뚫고 나와봤자 쪼랩이라 서버가 절대 털리지 않음 (최고 방어).

# ✍️ 단답형 / 서술형 시험장 출격 준비

### Ⅰ. 핵심 인사이트
- **본질**: 컨테이너 런타임(데몬)과 컨테이너 내부의 프로세스를 호스트 머신의 Root(UID 0) 권한이 아닌 비특권 일반 사용자(Non-root, Unprivileged User) 권한으로 실행하도록 리눅스 커널의 **User Namespace 매핑 기능을 극대화하여 구성한 컨테이너 격리 및 실행 아키텍처.**
- **가치**: 클라우드 네이티브 환경 최악의 위협인 **'컨테이너 이스케이프(Container Escape)'를 통한 호스트 장악(Host Takeover) 시나리오의 폭발 반경(Blast Radius)을 수학적으로 소멸**시킴. 취약점을 통해 탈주에 성공하더라도 공격자는 호스트 커널의 주요 파일 수정, 커널 모듈 적재(eBPF 악용 등) 및 다른 사용자 프로세스 간섭에 철저히 실패(Permission Denied)하게 됨.
- **판단 포인트**: IT 설계자는 Rootless 아키텍처 도입 시 필연적으로 수반되는 **기능적 제약(Functional Trade-offs)** 을 인지해야 합니다. 특권 포트(Privileged Ports: 1~1024) 바인딩 불가, 특정 Cgroup(v1) 제어의 한계, 호스트 네트워크 인터페이스(Overlay Network) 제어 권한 부족 등의 이슈가 발생하므로, 인프라의 네트워크 라우팅 레이어(Ingress/Service) 재설계가 병행되어야만 무중단 롤아웃이 가능합니다.

### Ⅱ. User Namespace Remapping 작동 메커니즘
Rootless 보안의 핵심이 되는 리눅스 커널 변환 계층.
1. **컨테이너 내부 뷰 (Container View)**
   - 프로세스는 자신이 UID 0 (root)로 실행된다고 착각(Illusion)함. 
   - `apt-get install` 같은 패키지 설치나 컨테이너 내부 루트 파일 시스템 쓰기가 정상적으로 동작함.
2. **ID 매핑 테이블 (`/etc/subuid`, `/etc/subgid`)**
   - 호스트 OS는 매핑 테이블을 통해 "이 특정 컨테이너 안의 UID 0~65535는, 호스트의 UID 100000~165535 구간으로 번역한다"고 선언함.
3. **호스트 OS 뷰 (Host View)**
   - 컨테이너 내부의 프로세스(UID 0)가 커널로 시스템 콜을 던지면, 커널 공간에서 권한 평가 시 UID 100000 (권한 없는 일반 계정)으로 취급됨.
   - 따라서 호스트의 `/etc/shadow`나 커널 메모리에 대한 접근 시도는 철저히 차단(Drop)됨.

### Ⅲ. Rootful vs Rootless 아키텍처 비교 트레이드오프
| 구분 | Rootful (기존 Docker Daemon) | Rootless (Podman / Rootlesskit) |
|---|---|---|
| **데몬(Daemon) 실행 권한** | 호스트의 루트(Root) 권한 | 데몬리스(Daemonless) 또는 일반 유저 권한 |
| **탈주(Escape) 시 위협 파급력** | 시스템 전체(Node) 완벽 장악 (Critical) | 해당 일반 유저 공간으로 한정 (Low Risk) |
| **네트워크 포트 바인딩** | 80/443 등 Well-known 특권 포트 직결 가능 | 1024번 이상(Unprivileged Port)만 매핑 가능 (8080 등) |
| **도입 허들 및 운영 호환성** | 100% 완벽한 레거시 호환 및 손쉬운 구성 | cgroup v2 필수, 특정 스토리지 드라이버 및 네트워크 플러그인(CNI) 호환성 제약 발생 |

### Ⅳ. 쿠버네티스(K8s) 보안 컨텍스트(SecurityContext) 연동 아키텍처
Rootless 패러다임을 K8s 파드(Pod) 배포 파이프라인에 강제하는 3가지 핵심 설정.
- 개발자가 작성하는 배포 YAML에 다음 명세를 강제(OPA Gatekeeper 연동).
  1. `runAsNonRoot: true` 
     - 컨테이너의 진입 프로세스가 root(UID 0)로 시작하는 것 자체를 어드미션 단계에서 차단.
  2. `runAsUser: 1000` 
     - 컨테이너를 특정 비특권 식별자(UID 1000)로 콕 찍어서 강제 실행.
  3. `allowPrivilegeEscalation: false` 
     - 컨테이너 내부 프로세스가 `sudo`나 `setuid` 비트를 사용하여 부모 프로세스보다 더 높은 권한을 얻는 것을 커널 레벨에서 금지.

### Ⅴ. 결론 및 실무적 판단 포인트
- 인프라 혁신(DevOps) 리더는 차세대 컨테이너 플랫폼 선정 시 아키텍처 종속성을 타파해야 합니다. Docker 데몬은 중앙 집중형 루트 권한을 요구하는 치명적 단일 장애점(SPOF)을 지니고 있습니다. 데몬 자체가 아예 존재하지 않는 포크/실행(Fork/Exec) 모델의 **Podman (Red Hat)** 과, OCI 표준 규격을 따르는 **CRI-O / containerd 런타임**의 조합을 차세대 표준 인프라 아키텍처(Target Architecture)로 채택하여 근원적인 권한 상승 킬 체인(Kill Chain)을 박살내야 합니다.

### 💡 문제 유형별 목차 전환 포인트
- **[클라우드 네이티브 워크로드 위협(컨테이너 탈옥/Escape)의 구조적 원인과 아키텍처 완화 방안]**: Ⅰ과 Ⅱ번(User Namespace 매핑 원리)을 중심으로 서술하여, 커널을 공유하는 가벼운 가상화의 태생적 취약점을 Rootless 매커니즘이 어떻게 권한 분리(Separation of Duty)로 커버하는지 증명.
- **[쿠버네티스(K8s) 파드 보안 설계 및 데브섹옵스 파이프라인(SecurityContext) 적용 방안]**: Ⅲ번(기능적 트레이드오프)을 냉정히 짚고, Ⅳ번의 SecurityContext YAML 설정과 OPA 정책 집행을 연계하여 실무 현장에서 강제(Enforcement)할 수 있는 인프라 보안 통제 모델로 답변 전개.
