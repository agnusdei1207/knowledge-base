# 📖 【암기용】 개념 완전 이해

> 목적: Brewer-Nash 모델을 처음 봐도 완벽히 이해하게 만든다. 시험 답안 양식이 아니라, 이해를 위한 친절한 설명이다.

## 한눈에
- **개요**: 이해상충이 있는 조직 간 정보 접근을 사용 이력에 따라 동적으로 제한하는 보안 모델
- **왜 필요한가**: 컨설팅·회계·금융기관은 경쟁 고객의 민감 정보를 동시에 다루면 내부자가 의도와 무관하게 정보를 섞을 수 있다. 정적 등급만으로는 고객 간 이해상충을 막기 어렵다.
- **핵심 직관**: 한 컨설턴트가 A은행 자료를 열람한 순간, 같은 이해상충 집합의 B은행 자료에는 벽이 생기는 구조다.

## 깊이 이해
- **배경·문제의식**: Bell-LaPadula는 군사 기밀처럼 상하 등급 중심이다. 금융·컨설팅 환경은 같은 등급의 고객 자료라도 경쟁 관계이면 동시 접근이 문제다.
- **작동 원리**: 객체를 회사 데이터셋(Company Dataset)과 이해상충 클래스(Conflict of Interest Class)로 묶는다. 사용자가 한 회사 자료를 읽으면 동일 이해상충 클래스의 다른 회사 자료 접근이 차단된다.
- **비유**: 변호사가 A사 인수 자문을 맡으면 같은 업종 경쟁사 B사의 인수 자료를 볼 수 없도록 사무실 안에 보이지 않는 벽을 세우는 방식이다.
- **구체 예시**: `COI=은행`에 A은행·B은행·C은행 자료가 있을 때, 사용자가 A은행 문서를 읽으면 B·C 은행의 비공개 문서는 거부하고, 공시자료는 접근 허용한다.
- **흔한 오해·주의점**: 이 모델은 단순 RBAC가 아니다. 접근 가능 여부가 역할뿐 아니라 이전 열람 이력에 따라 바뀌는 동적 접근통제이다.

## 연결 개념
- Chinese Wall Policy — 이해상충 차단 정책의 별칭
- Mandatory Access Control — 조직 정책 기반 접근통제라는 점에서 비교 가능
- Data Loss Prevention — 고객 간 정보 혼입과 반출 탐지로 보완

# 📝 【답안용】 시험 답안 템플릿

> 목적: 시험장에서 25분에 그대로 쓰는 답안 양식. 작성방식(추상표현 금지·수치·도식·문제유형 전환)을 엄격히 지킨다.
> 핵심: 고객 데이터 분류, 이해상충 클래스, 열람 이력 기반 동적 차단을 Bell-LaPadula와 구분해 서술한다.

## 핵심 인사이트 (3줄 요약)

> 1. **본질**: Brewer-Nash Model은 이해상충 클래스 내에서 한 고객 자료를 열람하면 경쟁 고객 자료 접근을 동적으로 제한하는 정보흐름 통제 모델이다.
> 2. **가치**: 금융, 회계, 법무, 컨설팅 조직에서 내부자에 의한 고객 간 정보 혼입을 접근 이력 기반으로 차단한다.
> 3. **판단 포인트**: Bell-LaPadula가 기밀 등급의 상하 흐름을 통제한다면, Brewer-Nash는 동등 등급 고객 간 이해상충을 통제한다.

## 출제 의도 및 답안 포인트

| 출제 의도 | 반드시 짚을 핵심 | 감점 회피 포인트 |
|:---|:---|:---|
| 이해상충 기반 접근통제 이해 확인 | COI class, company dataset, sanitized data, access history | 단순 기밀 등급 모델로 설명 |
| 동적 접근통제 판단 확인 | 최초 접근 이후 같은 COI 내 경쟁 고객 차단 | RBAC 역할 목록만 나열 |
| Bell-LaPadula와 비교 역량 확인 | 수평 이해상충 vs 수직 보안등급 차이 | no read up/no write down을 Brewer-Nash 규칙으로 혼동 |

> 요약: 이 문제는 고객 간 이해상충을 데이터 분류와 접근 이력으로 통제하는 동적 모델 설명을 요구한다.

---

## Ⅰ. 개요 및 필요성

- 개요: 이해상충 기반 동적 접근통제
- 배경: 동일 산업 경쟁 고객의 비공개 자료를 한 사용자가 동시에 다루면 정보 혼입, 내부자 오용, 법적 책임이 발생함
- 필요성: Company Dataset, COI Class, Access History를 메타데이터로 기록하고 경쟁 고객 비공개 문서 차단률 100%, 로그 보관 1년 이상 기준으로 운영해야 함

---

## Ⅱ. 구조 및 구성요소

```text
Subject -> Access History -> COI Class 확인 -> Company Dataset 선택
                                    / 동일 회사 허용
                                    / 경쟁 회사 비공개 데이터 차단
                                    / Sanitized Data 허용
```

| 구성요소 | 역할 | 특이사항 |
|:---|:---|:---|
| Subject | 문서에 접근하는 사용자·프로세스 | 컨설턴트, 애널리스트, 감사인 |
| Company Dataset | 특정 고객 회사의 데이터 묶음 | A은행 계약서, B은행 재무자료 |
| COI Class | 이해상충이 발생하는 회사 집합 | 은행, 보험, 반도체 등 산업군 |
| Access History | 사용자의 과거 열람 기록 | 동적 접근 판단 핵심 |
| Sanitized Data | 민감 식별자가 제거된 공개 가능 자료 | 공시자료, 익명 통계 |

> 요약: Brewer-Nash는 사용자, 고객 데이터셋, 이해상충 클래스, 접근 이력, 정제 데이터를 조합해 고객 간 정보흐름을 통제한다.

---

## Ⅲ. 동작원리 및 흐름도

```text
접근 요청 -> 객체의 Company Dataset 확인 -> COI Class 확인
-> 사용자 Access History 조회 -> 허용/거부 결정 -> 로그 기록
```

| 단계 | 처리 내용 | 검증 기준 |
|:---:|:---|:---|
| 1 | 사용자가 고객 문서 접근 요청 | Subject, Object, 목적 기록 |
| 2 | 문서의 Company Dataset과 COI Class 식별 | 메타데이터 누락률 0% |
| 3 | 사용자의 Access History 조회 | 같은 COI 내 기존 고객 여부 확인 |
| 4 | 동일 고객 또는 정제 데이터면 허용 | 경쟁 고객 비공개 자료 거부 |
| 5 | 허용·거부 사유 감사로그 저장 | 로그 보관 1년 이상 |

> 요약: 접근 결정은 현재 요청만 보지 않고 같은 이해상충 클래스에서 과거에 어떤 고객 자료를 봤는지 함께 판단한다.

---

## Ⅳ. 특징

| 구분 | Bell-LaPadula | Brewer-Nash | 수치·판단 포인트 |
|:---|:---|:---|:---|
| 보호 목표 | 기밀 등급 간 정보 누출 방지 | 경쟁 고객 간 정보 혼입 방지 | 군사/정부 vs 금융/컨설팅 |
| 통제 기준 | Subject/Object 보안등급 | COI Class와 Access History | 고객 메타데이터 100% 분류 |
| 접근 성격 | 정적 등급 중심 | 동적 이력 중심 | 최초 접근 후 권한 상태 변경 |
| 허용 예외 | 등급 정책 | Sanitized Data 접근 | 비식별·공개자료 구분 필요 |

> 요약: Brewer-Nash는 수직 등급이 아니라 수평 이해상충을 동적으로 차단한다는 점에서 Bell-LaPadula와 다르다.

## Ⅴ. 심화 비교 및 적용 판단

| 구분 | 기존/대안 | 본 키워드 | 선택 기준 |
|:---|:---|:---|:---|
| 구조 | RBAC 역할 기반 | COI+열람 이력 기반 | 고객 간 경쟁 관계가 접근 조건인 업무 |
| 비용/성능 | 권한 테이블 단순 조회 | 요청마다 이력·메타데이터 조회 | 접근 요청 p95 100ms 이하 설계 |
| 운영/위험 | 프로젝트별 수동 격리 | 자동 COI 차단 정책 | 고객사 50개 이상 컨설팅 조직 |

> 요약: 고객 경쟁 관계가 보안 판단의 중심이면 RBAC 단독보다 COI 클래스와 이력 기반 통제가 적합하다.

| 리스크 | 원인 | 대응 방안 | 확인 지표 |
|:---|:---|:---|:---|
| 메타데이터 누락 | 문서에 고객·COI 태그 미부여 | DLP 분류, 업로드 게이트 | 미분류 문서 0건 |
| 업무 지연 | 과도한 COI 묶음 | 예외 승인, sanitized data 분리 | 접근 거부 재심 비율 |
| 이력 우회 | 계정 공유·외부 저장소 사용 | MFA, 계정 공유 탐지, CASB | 동시 로그인 이상 건수 |

> 요약: 분류 누락과 계정 우회가 모델의 실효성을 낮추므로 문서 태깅, MFA, CASB 지표로 보완한다.

| 점검 항목 | 목표 기준 | 측정 방법 |
|:---|:---|:---|
| 분류 완전성 | Company Dataset·COI 태그 100% | DLP 스캔, 문서 메타데이터 검사 |
| 접근 결정 | 경쟁 고객 비공개 문서 차단률 100% | 정책 테스트, 감사로그 분석 |
| 운영 통제 | 예외 승인 7일 만료, 로그 1년 보관 | IAM 워크플로, SIEM 리포트 |

> 요약: 적용 성과는 문서 분류율, 차단 정책 테스트, 예외 승인 만료와 로그 보관으로 확인한다.

## Ⅵ. 실무 적용 및 결론

**적용 방안 3개 (필수 — 단계별 또는 항목별):**
1. 데이터 분류: 고객사 ID, 산업군, COI Class, 공개/비공개 여부를 문서 메타데이터로 강제하고 업로드 시 미분류 차단
2. 접근 엔진: ABAC 정책에 Access History 조건을 추가하고, 최초 고객 접근 후 같은 COI 경쟁 고객 비공개 문서 자동 거부
3. 운영 감사: 예외 승인은 법무·보안 공동 승인으로 7일 만료, 모든 허용·거부 이벤트를 SIEM에 전송

**결론 (2줄):**
- 기술사 판단: 경쟁 고객 자료를 동시에 다루는 금융·컨설팅 업무는 RBAC만으로 부족하므로 Brewer-Nash 기반 동적 통제를 채택함
- 향후 방향: DLP, CASB, 데이터 카탈로그와 연동해 COI 태깅과 접근 이력 검증을 자동화함
