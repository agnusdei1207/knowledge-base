## Ⅰ. 개요
- **정의**: 비밀번호 없이 공개키 기반으로 사용자를 인증하는 국제 표준 프로토콜
- **배경/필요성**: 비밀번호 재사용·피싱·크리덴셜 스터핑으로 인한 인증 사고가 지속되어 비밀번호 의존도를 낮출 수단이 필요함
- **비유**: 열쇠(개인키)는 사용자가 보관하고, 자물쇠(공개키)만 서버에 등록하는 구조

| 출제 의도 | 반드시 짚을 핵심 | 감점 회피 포인트 |
|:---|:---|:---|
| 비밀번호 없는 인증 원리 이해 | 공개키 등록-챌린지-서명 흐름 | UAF/U2F/FIDO2 차이 혼동 주의 |

> 요약: FIDO는 공개키 암호 기반으로 비밀번호 없이 안전한 인증을 제공하는 국제 표준임

## Ⅱ. 구성요소
```text
[사용자] --> [Authenticator] --> [FIDO Client] --> [RP Server]
               |                     |                 |
          개인키 저장           프로토콜 중계       공개키 저장
```

| 구성요소 | 설명 | 비유 |
|:---|:---|:---|
| Authenticator | 개인키를 생성·저장하고 서명을 수행하는 장치 | 인감도장 보관함 |
| FIDO Client | 브라우저·OS에서 인증기와 서버 간 메시지를 중계함 | 우체부 |
| RP Server | 공개키를 등록·저장하고 챌린지를 발행하는 서비스 서버 | 은행 창구 |
| 메타데이터 서비스 | 인증기의 신뢰성·인증 수준 정보를 제공함 | 인감증명 발급소 |

> 요약: 인증기가 개인키로 서명하고 서버가 공개키로 검증하는 분리 구조임

## Ⅲ. 절차
```text
등록 요청 --> 키쌍 생성 --> 공개키 전송 --> 인증 챌린지/응답
```
- 1단계: 사용자가 RP 서버에 등록을 요청하면 서버가 챌린지를 발행함
- 2단계: 인증기가 생체·PIN으로 사용자를 확인 후 공개키-개인키 쌍을 생성함
- 3단계: 공개키와 인증기 정보를 RP 서버에 전송·등록함
- 4단계: 로그인 시 서버 챌린지에 대해 개인키로 서명하여 인증을 완료함

> 요약: 등록 시 키쌍을 생성하고 로그인 시 챌린지-서명으로 본인을 증명하는 흐름임

## Ⅳ. 문제점
- 기기 종속성: 개인키가 특정 장치에 바인딩되어 기기 분실·교체 시 재등록이 필요함
- 호환성 격차: 레거시 시스템·구형 브라우저에서 FIDO API 미지원으로 전면 적용이 곤란함
- 계정 복구 난이도: 비밀번호 재설정 같은 대체 수단이 없어 복구 절차가 복잡함

> 요약: 기기 종속·레거시 호환·계정 복구가 도입 장벽으로 작용함

## Ⅴ. 개선방안
1. 단기: Passkey 도입으로 클라우드 동기화를 통해 기기 종속 문제를 해소함
2. 중기: FIDO2/WebAuthn 표준 채택을 확대하여 브라우저·OS 호환 범위를 넓힘
3. 장기: 분산 신원(DID)과 결합하여 플랫폼 독립적 복구·이동 체계를 구축함

> 요약: Passkey 동기화 → 표준 확산 → DID 연계 순으로 기기·호환·복구 문제를 해결함

## Ⅵ. 전망
- 발전 방향: Passkey 확산으로 비밀번호 없는 인증이 소비자·기업 양쪽에서 표준화되는 추세임
- 기술사적 판단: 피싱 저항성과 사용 편의성을 동시에 달성하는 인증 기술로 전환기에 해당함
- 기술사 제언: 레거시 시스템 병행 기간 동안 FIDO+MFA 하이브리드 전략 수립이 필요함
