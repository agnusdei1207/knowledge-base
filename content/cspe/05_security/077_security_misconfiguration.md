## 미리 알고가기

- 보안 오설정은 기본 계정, 디버그 모드, 공개 스토리지, 과다 권한처럼 설정값 때문에 생기는 취약 상태를 뜻함
- 코드 취약점이 없어도 설정 한 줄이 잘못되면 외부 노출과 권한 우회가 바로 발생할 수 있음
- 핵심은 최초 설정보다 운영 중 생기는 구성 편차를 계속 줄이는 데 있음

## Ⅰ. 개요

- **정의/개념**: 보안 오설정은 운영 환경의 설정값이 보안 기준선과 다르게 남아 시스템, 미들웨어, 클라우드 자산의 공격 표면을 넓히는 취약 상태임
- **배경/필요성**: 자산 종류와 배포 빈도가 늘면서 수동 변경과 예외 설정이 누적되기 쉬워졌고, 작은 설정 오류 하나가 데이터 유출과 관리 권한 노출로 이어지므로 기준선 기반 통제가 필요함

## Ⅱ. 특징

- 애플리케이션, 운영체제, 웹서버, DB, 클라우드, 컨테이너 모두 대상이 됨
- 설치 직후 기본값 방치와 운영 중 원복 누락이 대표 원인임
- 취약점 스캔만으로 다 잡기 어려워 IaC와 정책 자동화가 효과적임
- 예외 승인과 만료일 관리가 없으면 임시 허용 설정이 상시화됨

## Ⅲ. 종류 및 비교

| 판단 기준 | 설치 초기 오설정 | 운영 중 편차 오설정 |
|:---|:---|:---|
| 대표 사례 | 기본 계정, 디버그 모드, 관리 포트 공개 | 임시 방화벽 허용, 공개 버킷, 권한 원복 누락 |
| 발생 시점 | 도입 직후 | 변경 작업 이후 누적 |
| 탐지 방식 | 하드닝 점검, 베이스라인 검사 | 드리프트 탐지, CSPM, 정책 비교 |
| 기본 대응 | 보안 기본값 강제 | 변경 관리와 자동 시정 연계 |

## Ⅳ. 구성요소 및 구조

| 구성요소 | 설명 |
|:---|:---|
| 기준선 정의 | OS, WAS, DB, 클라우드, 컨테이너별 보안 기준을 정함 |
| 배포 전 검증 | IaC와 설정 파일을 배포 전에 검사함 |
| 운영 상태 수집 | 실제 자산의 설정값과 권한 상태를 수집함 |
| 시정과 예외 관리 | 편차를 수정하고 필요한 예외는 만료일과 함께 관리함 |

```text
기준선 수립 -> 배포 전 검사 -> 운영 상태 수집 -> 편차 탐지 -> 시정/예외 관리
```

## Ⅴ. 원리 및 절차 흐름도

```text
보안 기준 작성 -> 설정 배포 -> 실제 상태 비교 -> 위반 탐지 -> 수정 또는 예외 승인 -> 재확인
```

1. **보안 기준 작성**: 자산별 하드닝과 권한 기준을 정의함
2. **설정 배포**: 코드 또는 운영 변경으로 실제 환경에 반영함
3. **실제 상태 비교**: 배포된 결과를 기준선과 대조함
4. **위반 탐지와 수정**: 공개 노출과 과다 권한과 디버그 옵션을 바로잡음
5. **재확인**: 수정 후 동일 편차가 해소됐는지 다시 점검함

## Ⅵ. 실무 적용 및 유의점

1. 클라우드와 쿠버네티스를 함께 운영하는 조직은 공개 스토리지와 과다 IAM 권한과 무인증 관리 포트를 기준선으로 막고, IaC 정책 검사와 운영 드리프트 탐지를 묶어 위반 배포 차단율과 운영 편차 감소율로 확인함
2. 레거시 서버가 많은 환경은 모든 설정을 한 번에 바꾸기보다 고위험 설정부터 표준화하고 기본 계정 제거 여부와 불필요 포트 차단 결과와 예외 만료 준수율로 확인함

## Ⅶ. 결론

- 보안 오설정은 코드 밖에서 생기는 즉시형 위험이므로 기준선과 운영 상태의 차이를 지속적으로 줄이는 체계가 핵심임
