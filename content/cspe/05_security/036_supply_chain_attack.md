## Ⅰ. 개요
- **정의**: 소프트웨어·하드웨어 공급망의 신뢰 관계를 악용하여 다수 조직에 악성코드를 배포하는 공격
- **배경/필요성**: 하나의 공급자 침해로 수천 고객이 동시 피해를 입어 공급망 보안 검증이 필요함
- **비유**: 식수 정수장을 오염시켜 전체 도시에 피해를 주는 것과 유사함

| 출제 의도 | 반드시 짚을 핵심 | 감점 회피 포인트 |
|:---|:---|:---|
| 공격 벡터와 대응 프레임워크 | SBOM·코드 서명 | 오픈소스 의존성 관리 언급 필요 |

> 요약: 신뢰받는 공급 경로를 오염시켜 대규모 동시 침해를 유발하는 공격임

## Ⅱ. 구성요소
```text
[Supplier Build System] --> [Compromised Update] --> [Customer A]
                                                 --> [Customer B]
                                                 --> [Customer N]
```

| 구성요소 | 설명 | 비유 |
|:---|:---|:---|
| 빌드 시스템 침해 | CI/CD 파이프라인에 악성 코드를 삽입함 | 공장 생산라인에 불량 부품을 혼입하는 것 |
| 악성 업데이트 | 정상 서명된 업데이트에 백도어를 포함시켜 배포함 | 정품 포장에 위조품을 넣어 유통하는 것 |
| 오픈소스 의존성 | 인기 라이브러리에 악성 코드를 주입(타이포스쿼팅 등)함 | 공용 수도관에 독소를 투입하는 것 |
| 하드웨어 변조 | 펌웨어·칩셋 수준에서 백도어를 삽입함 | 전자기기 내부에 도청 장치를 심는 것 |

> 요약: 빌드 시스템·업데이트·오픈소스·하드웨어 등 다양한 공급 경로가 공격면임

## Ⅲ. 절차
```text
Supplier Compromise --> Code Injection --> Trusted Distribution --> Mass Exploitation
```
- 1단계: 공급자의 개발 환경·빌드 서버에 침투함
- 2단계: 정상 빌드 프로세스에 악성 코드를 삽입하고 서명을 유지함
- 3단계: 자동 업데이트 채널을 통해 고객 환경에 배포됨
- 4단계: 배포된 백도어로 다수 고객 환경에서 동시에 C2 통신·데이터 탈취를 수행함

> 요약: 공급자 침투→코드 삽입→신뢰 배포→대규모 악용의 4단계로 진행함

## Ⅳ. 문제점
- 신뢰 기반 우회: 정상 서명·업데이트 채널을 사용하여 보안 검증을 통과함
- 의존성 폭발: 간접 의존 라이브러리가 수백 개에 달하여 전수 검증이 곤란함
- 탐지 지연: 공급자 측 침해를 고객이 인지하기까지 수개월이 소요됨

> 요약: 신뢰 우회·의존성 복잡도·탐지 지연이 공급망 공격의 핵심 위험 요소임

## Ⅴ. 개선방안
1. 단기: SBOM 생성·검증과 코드 서명 무결성 확인으로 신뢰 기반 우회에 대응함
2. 중기: SCA 도구와 의존성 방화벽으로 오픈소스 취약 라이브러리를 자동 차단함
3. 장기: SLSA 프레임워크 기반 빌드 무결성 보증과 공급자 보안 감사를 제도화함

> 요약: SBOM→SCA→SLSA 순으로 공급망 전 구간의 무결성을 검증함

## Ⅵ. 전망
- 발전 방향: 소프트웨어 투명성 규제(EU CRA 등)로 SBOM 의무화가 확산될 전망임
- 기술사적 판단: 제로트러스트를 공급망까지 확장하는 것이 차세대 보안 패러다임임
- 기술사 제언: 공급자 보안 수준 인증 체계와 계약 조건 반영을 추진할 필요가 있음
