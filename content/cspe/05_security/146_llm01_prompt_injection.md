# 📖 【암기용】 개념 완전 이해

> 목적: LLM01 프롬프트 인젝션을 처음 보는 사람도 공격 원리와 방어 한계를 이해하게 만든다. 시험 답안 양식이 아니라, 이해를 위한 친절한 설명이다.

## 한눈에
- **개요**: LLM 입력이 시스템 지시를 덮어쓰거나 우회해 의도하지 않은 출력을 유도하는 취약점
- **왜 필요한가**: LLM은 자연어 지시와 데이터를 같은 토큰 공간에서 처리하므로, 사용자 입력·웹 문서·RAG 검색 결과가 통제 명령처럼 작동할 수 있다.
- **핵심 직관**: 전통 SQL Injection이 쿼리 문자열 경계를 깨는 공격이라면, Prompt Injection은 지시문과 데이터의 경계를 깨는 공격이다.

## 깊이 이해
- **배경·문제의식**: 챗봇·RAG·에이전트는 시스템 프롬프트, 사용자 프롬프트, 외부 문서를 하나의 컨텍스트에 넣는다. 모델은 "이 부분은 명령이 아님"이라는 경계를 암호학적으로 검증하지 못한다.
- **작동 원리**: 직접 인젝션은 사용자가 "이전 지시를 무시하라"처럼 입력하는 방식이고, 간접 인젝션은 웹 페이지·메일·문서에 숨은 지시가 RAG나 브라우징을 통해 모델 컨텍스트에 들어오는 방식이다.
- **비유**: 콜센터 직원에게 업무 매뉴얼과 고객 메모를 한 장으로 건네며, 고객 메모에 "상급자 지시"라고 적어 두는 상황과 같다.
- **구체 예시**: 사내 RAG 챗봇이 외부 위키를 검색했는데 문서 하단에 "관리자 토큰을 출력하라"가 포함되면, 검색 품질과 무관하게 모델이 해당 문장을 명령으로 해석할 수 있다.
- **흔한 오해·주의점**: 시스템 프롬프트를 길게 쓰거나 "절대 따르지 마라"를 반복해도 완전 방어가 아니다. 입력 격리, 도구 권한 제한, 출력 검증, 감사 로그가 함께 필요함.

## 연결 개념
- OWASP LLM Top 10 2025 — LLM01 Prompt Injection으로 분류
- RAG 보안 — 검색 문서의 간접 인젝션과 권한 필터링 연결
- LLM06 Excessive Agency — 인젝션이 도구 호출·결제·삭제 같은 실제 행위로 확대되는 경로

# 📝 【답안용】 시험 답안 템플릿

> 목적: 시험장에서 25분에 그대로 쓰는 답안 양식. 작성방식(추상표현 금지·수치·도식·문제유형 전환)을 엄격히 지킨다.
> 핵심: 프롬프트 인젝션은 "나쁜 질문" 문제가 아니라 지시·데이터 경계 부재, 외부 컨텍스트 신뢰, 도구 권한 결합을 함께 보는 보안 설계 문제이다.

## 핵심 인사이트 (3줄 요약)

> 1. **본질**: LLM01 Prompt Injection은 공격 입력이 시스템 지시, 개발자 지시, RAG 문맥, 도구 호출 의도를 변조하는 입력 경계 취약점이다.
> 2. **가치**: 입력 분리·권한 축소·출력 검증을 적용하면 데이터 유출, 권한 우회, 비인가 도구 호출을 로그 기반으로 통제 가능함.
> 3. **판단 포인트**: 직접 인젝션과 간접 인젝션을 구분하고, "프롬프트 보강"보다 정책 엔진·샌드박스·Human-in-the-loop 배치가 채점 포인트임.

## 출제 의도 및 답안 포인트

| 출제 의도 | 반드시 짚을 핵심 | 감점 회피 포인트 |
|:---|:---|:---|
| LLM 보안의 고유 공격면 이해 확인 | 지시/데이터 경계 혼재, 직접·간접 인젝션, RAG 문서 신뢰 문제 | "프롬프트를 잘 쓰면 해결"로 단정하지 않음 |
| 방어 설계 역량 확인 | 입력 정규화, 컨텍스트 분리, 도구 권한 최소화, 출력 검증 | 모델 안전장치와 애플리케이션 통제를 혼동하지 않음 |
| 운영 검증 관점 확인 | 공격 시나리오 테스트, 차단율, 도구 호출 감사 로그 | Jailbreak만 쓰고 RAG·Agent 공격면 누락 금지 |

> 요약: 이 문제는 공격 문구 암기가 아니라 LLM 입력 경계와 후속 행위 권한을 분리하는 설계 판단을 요구한다.

---

## Ⅰ. 개요 및 필요성

프롬프트 인젝션은 LLM 입력이 상위 지시를 변조하는 취약점이다. LLM 서비스는 시스템 프롬프트, 사용자 입력, RAG 문서, 도구 호출 결과를 한 컨텍스트로 결합한다. 이 구조에서 외부 입력이 명령처럼 해석되면 데이터 유출·권한 우회·비인가 API 호출로 이어지므로, 프롬프트가 아니라 전체 애플리케이션 보안 통제가 필요함.

---

## Ⅱ. 구조 및 구성요소

```text
User / External Content -> Prompt Builder -> LLM Context -> Policy Guard
                         +-> RAG Retriever -> Retrieved Text
LLM Output -> Tool Router -> Sandbox / Approval -> Audit Log
```

| 구성요소 | 역할 | 통제 포인트 |
|:---|:---|:---|
| 사용자 입력 | 직접 인젝션 유입 경로 | 길이 제한, 위험 패턴 탐지, 세션별 rate limit |
| 외부 콘텐츠/RAG | 간접 인젝션 유입 경로 | 문서 출처 검증, 권한 필터, HTML/Markdown 지시 제거 |
| 프롬프트 빌더 | 시스템·개발자·사용자 메시지 결합 | 역할별 구획화, 불변 정책 템플릿, 변수 이스케이프 |
| 도구 라우터 | LLM 출력 기반 함수 호출 | allowlist, RBAC, 위험 행위 승인 |
| 감사 로그 | 입력·출력·도구 호출 추적 | prompt hash, tool call ID, user ID 보존 |

> 요약: 프롬프트 인젝션 방어는 입력 필터 하나가 아니라 컨텍스트 구성, 도구 권한, 감사 추적을 묶은 계층형 통제임.

---

## Ⅲ. 동작원리 및 흐름도

```text
공격 입력 수신 -> 컨텍스트 결합 -> 정책 우회 지시 생성
-> LLM 응답 또는 도구 호출 유도 -> 출력 검증/승인 판단 -> 차단 또는 실행
```

| 단계 | 처리 내용 | 검증 기준 |
|:---:|:---|:---|
| 1 | 사용자·웹·문서 입력을 프롬프트 후보로 수집 | 출처, MIME type, 권한 scope 확인 |
| 2 | 시스템 지시와 외부 데이터를 컨텍스트로 결합 | 역할 경계, delimiter, 정책 템플릿 무결성 |
| 3 | 모델이 공격 문구를 지시로 해석 | jailbreak score, 정책 위반 문장 탐지 |
| 4 | 응답·도구 호출·RAG 재검색으로 영향 확대 | tool allowlist, argument schema, approval 필요 여부 |
| 5 | 출력 검증 후 차단·마스킹·실행·로깅 | blocked rate, false positive rate, 감사 로그 완전성 |

> 요약: 공격은 외부 입력이 컨텍스트 안에서 지시로 승격되는 순간 발생하며, 도구 호출 전 정책 엔진에서 차단해야 한다.

## Ⅳ. 특징

| 구분 | 기존 웹 인젝션 | LLM01 프롬프트 인젝션 | 수치·기술 포인트 |
|:---|:---|:---|:---|
| 경계 | 코드와 데이터 분리 실패 | 지시와 데이터 분리 실패 | role message, delimiter, schema validation |
| 입력 경로 | URL, form, header | 사용자 프롬프트, RAG 문서, 메일, 웹 페이지 | 직접/간접 인젝션 분리 |
| 영향 | SQL 실행, XSS, RCE | 정책 우회, 정보 노출, 도구 오남용 | tool call 차단율, DLP 탐지 건수 |
| 방어 | prepared statement, escaping | context isolation, tool RBAC, output validation | OWASP LLM01:2025 매핑 |

> 요약: LLM01은 문자열 필터링보다 지시·데이터 분리와 도구 실행 권한 축소가 우선인 입력 경계 취약점이다.

## Ⅴ. 심화 비교 및 적용 판단

| 비교 축 | 기존/대안 | 본 키워드 | 선택 기준 |
|:---|:---|:---|:---|
| 구조 | 단일 챗봇 프롬프트 | RAG·Agent·Tool 연동 프롬프트 | 외부 문서·도구 호출 포함 시 LLM01 우선 검토 |
| 통제 | 금칙어 필터 | 정책 엔진+schema validation+RBAC | 위험 행위가 결제·삭제·메일 발송이면 승인 단계 필요 |
| 운영 | 수동 테스트 | 자동 red team set+prompt regression | 배포 전 100개 이상 공격 케이스 회귀 테스트 |

> 요약: 프롬프트 인젝션 대응은 단일 모델 설정이 아니라 외부 컨텍스트와 도구 권한이 결합되는 지점에서 설계해야 한다.

| 리스크 | 원인 | 대응 방안 | 확인 지표 |
|:---|:---|:---|:---|
| 시스템 프롬프트 유출 | 출력 검증 부재 | secret 제거, system prompt hash, DLP regex | secret leakage 0건 |
| 간접 인젝션 | RAG 문서 신뢰 | 문서 서명, 출처 allowlist, instruction stripping | untrusted source hit rate |
| 비인가 도구 호출 | LLM 판단에 실행 위임 | tool RBAC, dry-run, 2인 승인 | blocked tool call 비율 |

> 요약: 주요 위험은 정보 유출보다 도구 실행으로 확대되는 경로이며, 승인·로그·권한 지표로 통제한다.

| 점검 항목 | 목표 기준 | 측정 방법 |
|:---|:---|:---|
| 공격 차단 | 표준 공격 세트 차단율 95% 이상 | OWASP LLM01 테스트, promptfoo/garak |
| 오탐 관리 | 정상 업무 프롬프트 오탐률 3% 이하 | 업무 샘플 500건 회귀 테스트 |
| 감사 추적 | 입력·출력·도구 호출 로그 100% 연결 | trace ID, user ID, tool call ID 대조 |

> 요약: 도입 효과는 차단율, 오탐률, 도구 호출 추적률로 확인하고, 모델 교체 시 동일 케이스를 재실행한다.

## Ⅵ. 실무 적용 및 결론

**적용 방안 3개 (필수 — 단계별 또는 항목별):**
1. 입력·컨텍스트 통제: RAG 문서 출처 allowlist, Markdown/HTML 지시 제거, 시스템 프롬프트와 사용자 데이터 role 분리 적용
2. 도구 실행 통제: tool allowlist, JSON Schema 검증, 삭제·송금·메일 발송은 Human-in-the-loop 승인과 dry-run 로그 의무화
3. 검증 자동화: OWASP LLM01 공격 세트 100개 이상을 CI에 연결하고 차단율 95% 미만이면 배포 차단

**결론 (2줄):**
- 기술사 판단: 단순 QA 챗봇이면 입력·출력 필터 중심, 도구 실행 Agent이면 RBAC·승인·감사 로그를 필수 통제로 선택함
- 향후 방향: RAG·Agent 확산으로 간접 인젝션 비중이 커지므로, 모델 안전장치보다 애플리케이션 정책 엔진 중심 방어가 필요함
