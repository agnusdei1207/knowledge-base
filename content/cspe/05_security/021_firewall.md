## Ⅰ. 개요
- **정의**: 사전 정의된 보안 규칙으로 네트워크 트래픽을 허용·차단하는 접근 제어 시스템임
- **배경/필요성**: 내부 네트워크와 외부 네트워크 경계에서 비인가 트래픽을 차단할 통제 지점이 필요함
- **비유**: 건물 출입구의 경비원이 출입증을 확인해 허가된 사람만 통과시키는 것과 유사함

| 출제 의도 | 반드시 짚을 핵심 | 감점 회피 포인트 |
|:---|:---|:---|
| 방화벽 유형별 동작 계층 차이 이해 | 패킷 필터링·상태 기반·프록시 방식 구분 | L3/L4 vs L7 검사 범위 혼동 주의 |

> 요약: 네트워크 경계에서 규칙 기반으로 트래픽을 통제하는 보안 장비임

## Ⅱ. 구성요소
```text
External Net ---> [ Packet Filter ] ---> [ Stateful Engine ] ---> Internal Net
                        |                       |
                        v                       v
                   Rule Base              Session Table
```

| 구성요소 | 설명 | 비유 |
|:---|:---|:---|
| Packet Filter | IP·포트 기반 L3/L4 헤더 검사로 허용·차단 판단함 | 우편물 겉봉투의 주소만 확인 |
| Stateful Engine | 세션 상태를 추적하여 연결 문맥 기반 필터링 수행함 | 대화 맥락을 기억하는 상담원 |
| Rule Base | 출발지·목적지·포트·프로토콜 조합의 허용·차단 정책 집합임 | 출입 허가 명단 |
| Session Table | 활성 연결 상태(SYN/ACK 등)를 저장·관리하는 테이블임 | 현재 통화 중인 전화 목록 |

> 요약: 규칙 기반 필터와 세션 추적 엔진이 트래픽 허용·차단을 결정함

## Ⅲ. 절차
```text
패킷 수신 --> 규칙 매칭 --> 세션 테이블 조회 --> 허용/차단 결정
```
- 1단계: 인터페이스로 유입된 패킷의 L3/L4 헤더 정보를 파싱함
- 2단계: Rule Base 상위부터 순차 매칭하여 해당 규칙을 탐색함
- 3단계: Stateful Engine이 기존 세션 여부를 Session Table에서 확인함
- 4단계: 매칭 결과에 따라 패킷을 허용(Forward) 또는 차단(Drop)하고 로그를 기록함

> 요약: 헤더 파싱 후 규칙·세션 매칭을 거쳐 트래픽 허용·차단을 결정함

## Ⅳ. 문제점
- 암호화 트래픽 미검사: L3/L4 헤더만 확인하므로 TLS 페이로드 내부 공격을 탐지하지 못함
- 규칙 복잡성 증가: 정책 누적으로 규칙 수천 건 이상 시 충돌·중복이 발생하여 관리가 어려움
- 애플리케이션 인지 부재: 포트 기반 판단만 수행하여 동일 포트의 서로 다른 앱을 구분하지 못함

> 요약: 페이로드 미검사·규칙 과잉·앱 비식별이 주요 한계임

## Ⅴ. 개선방안
1. 단기: SSL/TLS 복호화 장비 연동으로 암호화 트래픽 가시성을 확보함
2. 중기: 자동 규칙 최적화 도구를 도입하여 중복·미사용 규칙을 정리함
3. 장기: NGFW(022 참조)로 전환하여 애플리케이션 계층 식별·제어를 구현함

> 요약: 복호화 연동, 규칙 최적화, NGFW 전환으로 한계를 극복함

## Ⅵ. 전망
- 발전 방향: 마이크로세그멘테이션 기반 Zero Trust 아키텍처와 통합되는 추세임
- 기술사적 판단: 클라우드 환경에서 가상 방화벽·FWaaS 형태로 배포 모델이 다변화됨
- 기술사 제언: 경계 보안과 내부 세그멘테이션을 병행하는 다층 방어 전략 수립이 필요함
