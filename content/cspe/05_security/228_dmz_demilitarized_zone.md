## 1. 한눈에 이해하기 (Core Intuition)
- **정의**: 신뢰할 수 없는 외부 인터넷망과 보호해야 할 내부 업무망 사이에 위치하는 논리적/물리적 완충 지대(격리 네트워크)로, 외부에 서비스를 제공해야 하는 서버(Web, Mail 등)를 배치하는 공간입니다.
- **필요성**: 웹 서버를 내부망에 직접 배치하면, 웹 서버가 해킹당했을 때 해커가 내부망의 모든 자산(DB, 직원 PC)으로 손쉽게 횡적 이동(Lateral Movement)을 할 수 있습니다. 이를 막기 위해 "털려도 내부망으로는 못 들어오게" 차단막(방화벽) 밖의 샌드박스 공간에 서버를 내놓아야 합니다.
- **핵심 직관**: **"아파트 단지의 외부인 면회소"** - 택배 기사(인터넷 트래픽)가 아파트 세대 내부(내부망)로 직접 들어오지 못하게 하고, 외부 철문(외부 방화벽)과 내부 철문(내부 방화벽) 사이의 면회소(DMZ)에만 물건(데이터)을 두고 가게 만들어, 강도가 면회소를 장악하더라도 내부 단지로는 침투할 수 없게 만드는 아키텍처입니다.

## 2. 깊이 이해하기 (In-Depth Comprehension)
- **배경**: 초기 인터넷 환경의 단일 방화벽 구조에서 벗어나, 군사 용어인 비무장 지대(DMZ) 개념을 차용하여 다계층 방어(Defense in Depth)를 구현하고자 탄생했습니다.
- **작동 원리 (트래픽 통제 규칙)**:
  - **외부 $\rightarrow$ DMZ**: 웹(80/443), 메일(25) 등 서비스용 필수 포트만 제한적 허용 (그 외 Deny).
  - **외부 $\rightarrow$ 내부망**: 전면 차단 (Direct Access 불가).
  - **DMZ $\rightarrow$ 내부망**: 원칙적 차단. 단, 웹 서버가 데이터베이스와 통신해야 하는 특정 포트(예: MySQL 3306)만 엄격하게 제한적 허용. (웹 서버가 털려도 내부망 전체를 공격할 수 없도록 제한).
  - **내부망 $\rightarrow$ DMZ/외부**: 관리자 접속(SSH/RDP) 및 인터넷 아웃바운드 허용.
- **비유**: 은행 창구(DMZ). 고객은 은행 건물(외부)에 들어와 창구 직원(Web Server)과 대화할 수는 있지만, 창구 뒤의 금고(DB, 내부망)로는 절대 넘어갈 수 없는 유리벽(방화벽)이 존재합니다.
- **구체 예시**: 퍼블릭 클라우드(AWS)의 아키텍처에서 인터넷 게이트웨이(IGW)와 연결된 **Public Subnet**이 DMZ 역할을 하고, 인터넷이 차단된 **Private Subnet**이 내부망 역할을 합니다.
- **흔한 오해/주의점**: "DMZ에 두면 서버가 해킹당하지 않는다?" $\rightarrow$ 아닙니다. DMZ의 설계 철학은 "언젠가 뚫릴 수 있다(Assume Breach)"는 전제하에, 침투 사고 발생 시 그 피해가 내부망으로 전이되는 것을 막는 **피해 국소화(Containment)** 장치입니다.

## 3. 연결 개념 (Related Concepts)
- **Defense in Depth (심층 방어)**: DMZ 구축의 핵심 철학으로, 하나의 방어선이 무너져도 다음 방어선이 버티는 다중 방어 체계.
- **Lateral Movement (횡적 이동)**: 해커가 한 대의 시스템을 장악한 후 내부망의 다른 시스템으로 공격을 확장하는 행위 (DMZ는 이를 차단하는 목적).
- **VPC (Virtual Private Cloud)**: 클라우드 환경에서 Public/Private 서브넷으로 망을 나누어 DMZ 개념을 구현하는 네트워크 가상화 기술.

# ✍️ 답안용 골격 (Exam Preparation)

### Ⅰ. 핵심 인사이트
- **본질**: 인터넷(Untrusted)과 기업 내부망(Trusted) 사이에 방화벽을 통해 접근이 엄격히 통제된 중간 격리 영역(Semi-trusted)을 구축하여, 대외 공개 서비스와 내부 핵심 자산의 물리적/논리적 접점을 분리하는 엔터프라이즈 네트워크 아키텍처.
- **가치**: 대국민 서비스(웹, API)를 위해 개방한 80/443 포트를 통해 발생할 수 있는 초기 침투(Initial Access) 공격의 파급 범위를 DMZ 내로 국한시켜, 공격자의 내부망 피버팅(Pivoting) 및 횡적 이동을 구조적으로 차단(Containment)함.
- **판단 포인트**: 현대 클라우드 네이티브 설계에서는 단순한 DMZ(Public Subnet) 구축을 넘어, 프론트엔드(DMZ) - WAS(내부망1) - DB(내부망2)를 완전히 분리하는 3-Tier 마이크로 세그멘테이션 설계를 의무화하여 방어 종심을 극대화해야 함.

### Ⅱ. DMZ 아키텍처의 트래픽 통제(ACL) 원칙
```text
┌─────────────────┐       ┌──────────────┐       ┌────────────────┐
│ Untrusted (외부) │  ==>  │  DMZ (완충)  │  ==>  │ Trusted (내부) │
│ (Internet, User)│  <==  │ (Web, Proxy) │  <==  │ (DB, WAS, AD)  │
└─────────────────┘       └──────────────┘       └────────────────┘
      [Rule 1] 외부 ─(허용: 80/443)─> DMZ
      [Rule 2] 외부 ───(전면 차단)──> 내부
      [Rule 3] DMZ  ─(제한: DB포트)─> 내부 (★피버팅 차단 핵심)
      [Rule 4] 내부 ─(허용: SSH등) ─> DMZ / 외부
```

### Ⅲ. 물리적/논리적 구축 토폴로지 (물리 모델의 진화)
예산과 보안 수준에 따른 방화벽 배치 전략.
1. **스크린드 서브넷 (Screened Subnet / 1-Firewall Model)**
   - 방화벽 1대에 3개의 네트워크 인터페이스(외부/내부/DMZ)를 연결하여 논리적으로 분리.
   - 구축이 쉽고 비용이 저렴하나, 단일 방화벽의 취약점이 뚫리면 전사망이 붕괴되는 단일 장애점(SPOF) 리스크 존재.
2. **이중 방화벽 구조 (Dual-Firewall Model)**
   - 외부망 ↔ (방화벽 1) ↔ DMZ ↔ (방화벽 2) ↔ 내부망 직렬 배치.
   - **다중 벤더 정책(Heterogeneous Vendors)**: 해커가 한 방화벽의 제로데이 취약점(예: Palo Alto)을 악용하더라도, 다른 제조사(예: Fortinet)의 내부 방화벽은 뚫지 못하도록 기종(OS) 다양성을 확보하는 것이 금융망 최고 수준의 권고 사항.

### Ⅳ. 최신 트렌드: 클라우드 VPC와 ZTA로의 진화
- **Public/Private Subnet 분리**: 레거시의 DMZ 개념은 클라우드의 IGW(Internet Gateway)와 연결된 Public Subnet(ALB, Nginx 배치)과 라우팅이 차단된 Private Subnet(WAS, RDS 배치) 구조로 완벽히 1:1 매핑됨.
- **ZTA (제로 트러스트) 융합**: "내부망은 무조건 안전하다"는 성곽 경계(Perimeter) 패러다임이 붕괴됨에 따라, 물리적 DMZ 대신 클라우드 WAF나 SASE 프록시 뒤에 자산을 숨겨놓고 신원 검증(Identity)을 통과한 트래픽만 열어주는 소프트웨어 정의 경계(SDP)로 진화 중.

### Ⅴ. 결론 및 실무적 판단 포인트
- 인프라 보안 설계자는 편의성을 위해 DMZ에 있는 웹 서버에 DB를 함께 설치(로컬 DB)하거나, 내부망 DB로 향하는 방화벽 포트를 ANY(모두 허용)로 열어두는 최악의 설계(Design Flaw)를 감사 시 철저히 적발해야 합니다.
- 완벽한 방어는 존재하지 않으므로(Assume Breach), DMZ에 위치한 서버들이 내부망 공격의 점프 호스트(Jump Host)로 악용되지 않도록, 관리자용 프로토콜(SSH, RDP)의 아웃바운드를 엄격히 차단하고, EDR(엔드포인트 탐지 및 대응) 센서를 필수로 배포하는 종심 방어가 수반되어야 합니다.

### 💡 문제 유형별 목차 전환 포인트
- **[심층 방어(Defense in Depth) 기반 네트워크 보안 아키텍처 설계]**: Ⅰ과 Ⅱ(ACL 원칙)를 전면에 배치하여, 서비스 가용성을 보장하면서도 해커의 피버팅(Pivoting)을 물리/논리적으로 락다운하는 정통 네트워크 설계 논리 전개.
- **[클라우드 네이티브 환경의 망분리 토폴로지와 마이크로 세그멘테이션(Micro-segmentation)]**: Ⅲ(이중 방화벽)과 Ⅳ(VPC/ZTA)를 강조하여, 레거시 DMZ 모델의 한계를 넘어 클라우드의 Public/Private 서브넷과 SDP를 결합하여 동적인 하이브리드 클라우드 보안 경계를 그리는 심화 엔지니어링 방안 서술.
