# 📖 【암기용】 개념 완전 이해

> 목적: 보안 구성 관리를 처음 봐도 완벽히 이해하게 만든다. 시험 답안 양식이 아니라, 이해를 위한 친절한 설명이다.

## 한눈에
- **개요**: 서버, 네트워크, 클라우드, 애플리케이션 설정을 보안 기준선에 맞게 유지하는 관리 활동
- **왜 필요한가**: 기본 계정, 열린 포트, 약한 TLS, 공개 스토리지는 취약점이 없어도 침해 경로가 된다.
- **핵심 직관**: 건물의 출입문, 창문, CCTV 위치를 표준 설계도와 계속 대조해 임의 변경을 잡아내는 일이다.

## 깊이 이해
- **배경·문제의식**: 보안 사고는 CVE만으로 발생하지 않는다. 운영 중 임시 계정, 디버그 옵션, 보안 그룹 전체 공개, 미적용 보안 헤더 같은 구성 편류(drift)가 누적되어 신뢰 경계를 무너뜨린다.
- **작동 원리**: CIS Benchmark, NIST SP 800-128, 조직 hardening 기준을 만들고 CMDB와 IaC 상태를 기준선으로 삼는다. 배포 전 정책 검사, 배포 후 drift 탐지, 예외 승인, 재검증을 반복한다.
- **비유**: 호텔 객실 점검표처럼 문 잠금, 금고, 비상등, 창문 상태를 매일 확인하고 점검 결과를 기록하는 방식이다.
- **구체 예시**: Kubernetes에서 `runAsNonRoot=true`, `readOnlyRootFilesystem=true`, `allowPrivilegeEscalation=false`를 OPA Gatekeeper로 강제하고 위반 배포를 차단한다.
- **흔한 오해·주의점**: 보안 구성 관리는 체크리스트 1회 점검이 아니다. 운영 변경, 패치, IaC 수정, 긴급 조치 이후 기준선과 실제 상태를 다시 맞추는 폐루프가 핵심이다.

## 연결 개념
- CIS Benchmark - OS, DB, Kubernetes, Cloud hardening 기준
- IaC/Policy as Code - Terraform, Ansible, OPA로 구성 변경을 코드화
- CMDB/CSPM - 자산, 구성, 클라우드 drift 탐지 기반

# 📝 【답안용】 시험 답안 템플릿

> 목적: 시험장에서 25분에 그대로 쓰는 답안 양식. 작성방식(추상표현 금지·수치·도식·문제유형 전환)을 엄격히 지킨다.
> 핵심: 보안 구성 관리 답안은 기준선, 변경 통제, drift 탐지, 예외 승인, 재검증을 CMDB/IaC/CIS Benchmark와 연결해야 함.

## 핵심 인사이트 (3줄 요약)

> 1. **본질**: 보안 구성 관리는 정보시스템의 설정값을 보안 기준선과 지속 대조해 오설정과 구성 편류를 통제하는 활동임.
> 2. **가치**: 취약점 패치 전에도 기본 계정, 과다 권한, 공개 포트, 약한 암호 설정 같은 공격면을 줄임.
> 3. **판단 포인트**: 문서 기준선만으로는 부족하며 IaC, CMDB, policy as code, drift 탐지, 예외 만료일을 함께 관리해야 함.

## 출제 의도 및 답안 포인트

| 출제 의도 | 반드시 짚을 핵심 | 감점 회피 포인트 |
|:---|:---|:---|
| 보안 운영 통제 이해 확인 | CIS Benchmark, NIST SP 800-128, 기준선, 변경관리 | 단순 하드닝 항목 나열 |
| 클라우드/IaC 환경 판단 확인 | Terraform plan, OPA, CSPM, drift detection | 수동 점검만 제시 |
| 감사·재검증 역량 확인 | CMDB 자산, 예외 승인, remediation SLA, 증적 | 예외 만료일과 재점검 누락 |

> 요약: 이 문제는 설정값 목록이 아니라 기준선-변경-탐지-조치-감사로 닫히는 운영 통제 능력을 요구함.

## Ⅰ. 개요 및 필요성

- 개요: 설정 기준선 통제
- 배경: 시스템 설정은 배포, 패치, 장애 조치 과정에서 기준선과 달라지는 drift가 발생해 포트, 권한, 암호, 로그 설정의 감사 공백을 만들 수 있음.
- 필요성: CIS Benchmark, NIST SP 800-53 CM 계열 통제를 기준으로 기준선, 예외 만료일, drift 탐지 주기를 구성 항목별로 관리해야 함.

---

## Ⅱ. 구조 및 구성요소

```text
자산 식별 -> 보안 기준선 -> IaC/CMDB 등록 -> 변경 승인
          -> 배포 전 정책 검사 -> 운영 중 drift 탐지 -> 조치/예외 -> 감사 증적
```

| 구성요소 | 역할 | 특이사항 |
|:---|:---|:---|
| 보안 기준선 | OS, DB, WAS, Cloud, K8s 설정 기준 정의 | CIS Benchmark, 조직 hardening |
| CMDB/IaC | 자산과 의도한 설정 상태 관리 | Terraform state, Ansible inventory |
| 정책 검사 | 배포 전 위반 설정 차단 | OPA, Checkov, tfsec |
| Drift 탐지 | 운영 상태와 기준선 차이 확인 | CSPM, EDR posture, config scan |
| 예외 관리 | 업무 예외 승인과 만료일 관리 | owner, risk, expiry 필수 |

> 요약: 구성 관리는 기준선 문서, 자산 원장, 코드화된 정책, 운영 탐지, 예외 증적이 연결될 때 감사 가능한 통제가 됨.

---

## Ⅲ. 동작원리 및 흐름도

```text
요구 변경 접수 -> 기준선 영향 분석 -> 승인/거절
-> IaC 반영 -> 정책 검사 -> 배포 -> drift scan
-> 위반 조치 또는 예외 승인 -> 재검증/증적 보관
```

| 단계 | 처리 내용 | 검증 기준 |
|:---:|:---|:---|
| 1 | 자산과 신뢰 경계 식별 | CMDB 등록률 95% 이상 |
| 2 | CIS/NIST 기준선 매핑 | 고위험 항목 owner 지정 |
| 3 | IaC와 정책 검사로 변경 전 검증 | critical 위반 배포 차단률 100% |
| 4 | 운영 drift 탐지와 조치 | critical SLA 7일, high SLA 30일 |
| 5 | 예외 만료와 재검증 | 만료 예외 0건, 증적 보관 1년 |

> 요약: 보안 구성 관리는 변경 전 차단과 운영 후 drift 탐지를 결합해 기준선 이탈을 재검증하는 흐름임.

## Ⅳ. 특징

| 구분 | 수동 점검 중심 | 보안 구성 관리 | 수치/판단 포인트 |

| 통제 시점 | 분기·반기 점검 | 배포 전 검사 + 운영 중 탐지 | critical drift 24시간 내 알림 |

> 요약: 보안 구성 관리는 수동 점검을 코드화된 기준선과 drift 탐지로 전환해 변경과 운영을 함께 통제함.

> 요약: 자산 수와 변경 빈도가 증가하면 수동 점검보다 IaC와 정책 기반 구성 관리가 통제 범위를 넓힘.

|:---|:---|:---|:---|

| 예외 남용 | 업무 예외 만료일 부재 | risk owner, expiry, compensating control | 만료 예외 0건 |
| IaC 우회 | 콘솔 직접 변경 | cloud audit log, drift detection | console change alert 100% |
| 감사 증적 부족 | 조치 이력 분산 | ticket, scan result, approval link | 증적 누락 0건 |

> 요약: 주요 리스크는 미등록 자산, 예외 남용, IaC 우회, 증적 누락이며 자산 발견과 변경 로그로 통제함.

| 점검 항목 | 목표 기준 | 측정 방법 |
|:---|:---|:---|
| 기준선 준수 | CIS level 1 90%, critical 100% | CIS-CAT, OpenSCAP, CSPM |
| 변경 통제 | 정책 위반 배포 차단률 100% | CI/CD policy gate 로그 |
| 조치 관리 | critical 7일, high 30일 | ticket SLA, 재스캔 결과 |
| 로그·감사 | 관리자 변경 로그 1년 보관 | SIEM, cloud audit trail |

> 요약: 성공 여부는 기준선 준수율, 배포 차단률, 조치 SLA, 감사 로그 보존으로 판단함.

## Ⅵ. 실무 적용 및 결론

**적용 방안 3개 (필수 — 단계별 또는 항목별):**
1. 기준선 수립: CIS Benchmark와 NIST SP 800-128을 기준으로 OS, DB, Cloud, K8s별 금지 설정과 필수 로그 항목을 정의함.
2. 변경 통제: Terraform, Ansible, OPA, Checkov를 CI/CD에 연결해 공개 포트, root 실행, 미암호화 스토리지를 배포 전 차단함.
3. 운영 재검증: CSPM, EDR posture, SIEM audit log로 drift를 탐지하고 critical 7일, high 30일 SLA와 예외 만료일을 ticket에 기록함.

**결론 (2줄):**
- 기술사 판단: 변경 빈도가 낮은 온프레미스는 CIS 점검 중심, 클라우드·컨테이너는 IaC와 policy as code 기반 상시 통제를 선택해야 함.
- 향후 방향: 보안 구성 관리는 CNAPP, SBOM, CI/CD gate와 결합해 개발부터 운영까지 동일 기준선을 적용하는 방향으로 발전함.
