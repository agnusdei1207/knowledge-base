## 미리 알고가기

- 의존성 컴포넌트는 애플리케이션이 직접 쓰는 라이브러리뿐 아니라 하위 패키지와 컨테이너 베이스 이미지까지 포함함
- SBOM은 소프트웨어에 들어 있는 구성품 목록이고, SCA는 그 목록을 취약점 정보와 대조하는 도구임
- 취약한 컴포넌트 문제는 코드 품질보다 공급망 추적과 패치 우선순위 운영이 핵심임

## Ⅰ. 개요

- **정의/개념**: 취약한 의존성 컴포넌트는 라이브러리, 프레임워크, 패키지, 베이스 이미지가 알려진 취약 버전인 상태임
- **배경/필요성**: 현대 소프트웨어는 외부 패키지를 대량 사용함. 하위 구성품 하나가 원격 코드 실행과 정보 유출 경로가 될 수 있음

## Ⅱ. 특징

- 직접 선언하지 않은 하위 의존성도 운영 결과물에 포함될 수 있음
- 컨테이너 이미지와 OS 패키지도 점검 대상임
- 취약점 수보다 외부 노출 여부와 실제 악용 가능성이 우선순위를 좌우함
- 버전 업그레이드는 호환성 검증과 재빌드를 동반해야 함

## Ⅲ. 종류 및 비교

| 판단 기준 | 직접 의존성 | 하위 의존성 |
|:---|:---|:---|
| 관리 방식 | 개발자가 명시적으로 선언함 | 다른 패키지를 통해 간접 포함됨 |
| 가시성 | 비교적 확인이 쉬움 | 누락되기 쉬움 |
| 조치 방식 | 버전 수정과 테스트가 비교적 단순함 | 상위 패키지 교체나 구조 변경이 필요할 수 있음 |
| 위험 포인트 | 핵심 라이브러리 취약 버전 | 개발자가 인지하지 못한 채 배포될 가능성 |

## Ⅳ. 구성요소 및 구조

| 구성요소 | 설명 |
|:---|:---|
| SBOM | 빌드 결과물에 포함된 구성품과 버전을 목록화함 |
| 취약점 매핑 | CVE, OSV, NVD 등과 버전을 대조함 |
| 우선순위 기준 | 악용 가능성, 자산 중요도, 외부 노출, 패치 난도를 반영함 |
| 수정과 재배포 | 업그레이드, 재빌드, 재스캔으로 위험을 해소함 |

```text
구성품 목록화 -> 취약점 매핑 -> 영향 자산 식별 -> 우선순위 결정 -> 업그레이드/재배포
```

## Ⅴ. 원리 및 절차 흐름도

```text
SBOM 생성 -> SCA 점검 -> CVE 영향 확인 -> 패치 대상 선정 -> 빌드/배포 -> 재점검
```

1. **SBOM 생성**: 서비스에 포함된 구성품과 버전을 목록화함
2. **SCA 점검**: 취약 버전과 매칭되는 항목을 찾음
3. **영향 확인**: 인터넷 노출 여부와 실제 사용 기능과 자산 중요도를 봄
4. **패치와 재배포**: 버전을 올리고 이미지를 다시 만들어 배포함
5. **재점검**: 동일 구성품의 취약 노출이 사라졌는지 확인함

## Ⅵ. 실무 적용 및 유의점

1. 마이크로서비스·컨테이너 환경은 SBOM과 SCA를 CI에 넣고 고위험 취약 버전 잔존 여부·재배포 후 재스캔으로 확인함
2. 대규모 레거시는 버전 고정과 예외 근거를 관리하고 하위 의존성 누락 감소·패치 SLA 준수율·예외 만료 상태로 확인함

## Ⅶ. 결론

- 취약한 의존성 컴포넌트 문제는 단순 업데이트가 아니라 구성품 식별부터 재배포까지 완료하는 공급망 운영 문제임
