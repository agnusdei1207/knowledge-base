## 미리 알고가기

- 아티팩트는 컨테이너 이미지, 바이너리, 패키지처럼 배포되는 산출물을 말함
- Keyless 서명은 장기 개인키를 직접 들고 있지 않고 짧게 살아 있는 인증서로 서명하는 방식임
- Rekor는 누가 무엇에 서명했는지 남기는 투명성 로그임

## Ⅰ. 개요

- **정의/개념**: 아티팩트 서명은 배포 산출물에 암호학적 서명을 붙여 출처와 무결성을 검증하는 통제이며 Cosign·Sigstore는 이를 자동화함
- **배경/필요성**: 레지스트리와 패키지 저장소를 거치는 동안 이미지나 바이너리가 바뀔 수 있음. 배포 직전 서명 검증이 필요함

## Ⅱ. 특징

- 산출물이 누가 만든 것인지와 중간 변조가 없었는지를 함께 확인함
- 컨테이너 레지스트리와 CI 파이프라인에 붙여 자동 배포 흐름에서 검증함
- Sigstore는 인증서 발급과 투명성 로그를 묶어 키 관리 부담을 낮춤
- 서명만 있고 검증 정책이 없으면 운영 보호 효과가 약하므로 배포 거부 규칙이 함께 필요함

## Ⅲ. 종류 및 비교

| 판단 기준 | 전통적 장기 키 서명 | Sigstore 기반 Keyless 서명 |
|:---|:---|:---|
| 키 운영 | 개인키 보관과 교체 부담이 큼 | 짧은 인증서로 키 보관 부담을 줄임 |
| 추적성 | 서명자 확인과 기록 관리가 분리되기 쉬움 | 신원 확인과 로그 기록이 함께 남음 |
| 자동화 적합성 | 별도 키 배포가 필요함 | CI 환경에 비교적 쉽게 붙음 |
| 주의점 | 키 유출 시 영향이 큼 | 신뢰할 발급자와 검증 정책을 명확히 해야 함 |

## Ⅳ. 구성요소 및 구조

| 구성요소 | 설명 |
|:---|:---|
| Cosign | 이미지와 산출물의 서명과 검증을 수행하는 도구임 |
| 신원 확인 | OIDC 기반 로그인으로 서명자의 신원을 확인함 |
| 인증서 발급 | Fulcio가 짧은 수명의 인증서를 발급함 |
| 투명성 로그 | Rekor가 서명 기록을 남겨 추적 가능성을 높임 |
| 검증 정책 | 배포 전에 신뢰된 서명인지 확인하고 미검증 산출물을 막음 |

```text
개발자/CI 신원 확인 -> 짧은 인증서 발급 -> Cosign 서명 -> Rekor 기록 -> 배포 전 검증
```

## Ⅴ. 원리 및 절차 흐름도

```text
산출물 생성 -> 서명자 신원 확인 -> 서명 수행 -> 로그 기록 -> 배포 전 검증 -> 배포 허용
```

1. **산출물 생성**: 이미지나 바이너리를 빌드함
2. **신원 확인**: OIDC 기반으로 서명 주체를 확인함
3. **서명 수행**: Cosign으로 산출물에 서명을 부여함
4. **로그 기록**: 서명 기록을 투명성 로그에 남김
5. **배포 검증**: 신뢰된 서명만 통과시키고 나머지는 막음

## Ⅵ. 실무 적용 및 유의점

1. 컨테이너 배포 환경은 서명 없는 이미지를 차단하고 미서명 이미지 차단 건수와 신뢰된 발급자 일치율로 확인함
2. 검증이 외부 인증과 로그 조회에만 기대면 실패가 생기므로 장애 시 처리 절차를 정하고 검증 실패 배포 건수로 점검함

## Ⅶ. 결론

- 아티팩트 서명은 배포 전 마지막 확인 절차가 아니라 빌드부터 배포까지 신뢰 경로를 만드는 통제이므로 서명 자동화와 배포 차단 정책이 함께 있어야 함
