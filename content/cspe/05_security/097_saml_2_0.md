# 📖 【암기용】 개념 완전 이해

> 목적: SAML 2.0을 처음 봐도 Assertion, ACS, Metadata, Signature 검증의 의미를 이해하게 만든다. 시험 답안 양식이 아니라, 이해를 위한 설명이다.

## 한눈에
- **개요**: SAML 2.0은 IdP가 SP에 XML Assertion으로 인증 결과를 전달하는 Federation 표준
- **왜 필요한가**: 기업은 사내 계정 하나로 ERP, 그룹웨어, SaaS에 로그인해야 하며, 각 서비스가 비밀번호를 따로 저장하면 계정 회수와 감사가 분산된다.
- **핵심 직관**: SAML Assertion은 IdP가 서명한 "이 사용자는 이 시간에 이 SP 대상 인증을 통과했다"는 XML 증명서임.

## 깊이 이해
- **배경·문제의식**: 기업 SSO는 오래전부터 브라우저 기반 업무시스템과 연계되어 왔다. SAML 2.0은 서로 다른 조직의 IdP와 SP가 Metadata를 교환하고 신뢰 관계를 만들 수 있게 표준화함.
- **작동 원리**: 사용자가 SP에 접근하면 SP가 AuthnRequest를 IdP로 보낸다. IdP는 사용자를 인증하고 Assertion을 생성해 ACS(Assertion Consumer Service) URL로 전달한다. SP는 XML Signature, issuer, audience, recipient, NotOnOrAfter를 검증한 뒤 세션을 발급함.
- **비유**: 회사 출입증 발급소(IdP)가 방문증(Assertion)에 서명하고, 건물 입구(SP)가 서명과 방문 대상 건물을 확인한 뒤 출입을 허가하는 구조임.
- **구체 예시**: 사내 IdP와 SaaS SP가 metadata XML을 교환하고, SP EntityID와 ACS URL을 고정한다. Assertion 유효시간 5분, NameID는 email, 서명 알고리즘은 RSA-SHA256 이상 사용.
- **흔한 오해·주의점**: Base64로 인코딩된 SAMLResponse를 복호화했다고 신뢰하면 안 됨. 반드시 XML Signature와 Assertion Conditions를 검증해야 함.

## 연결 개념
- OAuth 2.0·OIDC - JSON/JWT 기반 현대 API·모바일 인증
- SSO - SAML이 구현하는 대표 기업 단일 로그인 방식
- XML Signature Wrapping - SAML 검증 취약점의 대표 공격

# 📝 【답안용】 시험 답안 템플릿

> 목적: 시험장에서 25분에 그대로 쓰는 답안 양식. SAML 흐름 나열보다 Assertion 검증 위치, Metadata 신뢰, XML Signature Wrapping 대응을 중심으로 작성한다.
> 핵심: IdP/SP/ACS/Metadata와 issuer/audience/time/signature 검증을 연결한다.

## 핵심 인사이트 (3줄 요약)

> 1. **본질**: SAML 2.0은 IdP가 XML Assertion으로 인증 결과와 속성을 SP에 전달하는 Federation 표준이다.
> 2. **가치**: SP는 비밀번호를 보관하지 않고 IdP 신뢰와 Assertion 검증으로 기업 SSO를 구현한다.
> 3. **판단 포인트**: 서명 검증, AudienceRestriction, ACS URL, 유효시간, XML Signature Wrapping 방어가 채점 핵심이다.

## 출제 의도 및 답안 포인트

| 출제 의도 | 반드시 짚을 핵심 | 감점 회피 포인트 |
|:---|:---|:---|
| 기업 Federation 이해 확인 | IdP, SP, Assertion, ACS, Metadata, Trust 관계 | SAML을 단순 세션 쿠키로 설명 |
| Assertion 검증 역량 확인 | signature, issuer, audience, recipient, NotOnOrAfter | Base64 디코딩과 서명 검증 혼동 |
| 취약점 대응 판단 확인 | XML Signature Wrapping, replay, metadata 변조 대응 | 서명 여부만 쓰고 XPath 고정 검증 누락 |

> 요약: SAML 답안은 "IdP가 발급한 Assertion을 SP가 어떤 조건으로 신뢰하는가"를 중심으로 써야 한다.

---

## Ⅰ. 개요 및 필요성

- 개요: XML 기반 인증 Assertion 교환
- 배경: 기업 IdP와 SaaS SP가 계정을 따로 관리하면 퇴사자 회수, MFA 적용, 접속 로그 감사가 분산된다.
- 필요성: SAML 2.0 Metadata와 서명된 Assertion으로 엔터프라이즈 SSO의 신뢰 관계, 계정 중앙 회수, 감사 추적을 구현해야 한다.

---

## Ⅱ. 구조 및 구성요소

```text
User -> SP -> AuthnRequest -> IdP
IdP -> SAML Assertion -> ACS -> SP Session
Metadata -> Certificate / EntityID / ACS Binding -> Trust
```

| 구성요소 | 역할 | 검증 포인트 |
|:---|:---|:---|
| IdP | 사용자 인증과 Assertion 발급 | signing certificate, issuer |
| SP | Assertion 검증 후 서비스 세션 발급 | EntityID, audience, session policy |
| ACS | SAMLResponse 수신 엔드포인트 | recipient, destination, HTTPS |
| Metadata | IdP/SP 신뢰 정보 교환 | certificate, binding, validUntil |
| Assertion | Subject, Attribute, Conditions 포함 | signature, NameID, time window |

> 요약: SAML 구조는 Metadata 신뢰를 전제로 IdP Assertion을 SP ACS에서 검증해 서비스 세션으로 변환한다.

---

## Ⅲ. 동작원리 및 흐름도

```text
SP Access -> AuthnRequest -> IdP Authentication
-> Signed Assertion -> ACS Receive -> Signature/Condition Verify
-> SP Session Issue -> Audit Log
```

| 단계 | 처리 내용 | 검증 기준 |
|:---:|:---|:---|
| 1 | SP가 AuthnRequest 생성 | ID, ACS URL, RelayState |
| 2 | IdP가 사용자 인증 수행 | MFA, session age, AuthnContext |
| 3 | IdP가 Assertion 서명 후 전송 | RSA-SHA256 이상, certificate chain |
| 4 | SP가 Assertion 조건 검증 | issuer, audience, recipient, NotBefore/NotOnOrAfter |
| 5 | SP 세션 발급과 감사 | NameID 매핑, replay cache, login log |

> 요약: SAML의 보안 판단은 IdP 인증보다 SP의 Assertion 검증과 replay 차단에서 완성된다.

## Ⅳ. 특징

| 구분 | 기존/대안 | SAML 2.0 | 수치·표준 포인트 |
|:---|:---|:---|:---|
| 인증 전달 | 앱별 ID/PW | XML Assertion 기반 Federation | OASIS SAML 2.0 |
| 신뢰 구성 | 수동 계정 연동 | Metadata 기반 인증서 교환 | metadata validUntil, EntityID |
| 검증 방식 | 세션 DB 확인 | XML Signature와 Conditions 검증 | NotOnOrAfter 5분 권고 |
| 적용 영역 | 모바일·API | 브라우저 기반 기업 SaaS | HTTP Redirect/POST Binding |

> 요약: SAML 2.0은 브라우저 기반 기업 SSO에 맞지만, XML 처리와 서명 검증 오류가 주요 취약점이 된다.

## Ⅴ. 심화 비교 및 적용 판단

| 구분 | 기존/대안 | SAML 2.0 | 선택 기준 |
|:---|:---|:---|:---|
| 구조 | OIDC JWT | XML Assertion, Metadata, ACS | 레거시 SaaS·ADFS 연계면 SAML |
| 비용/성능 | 앱별 계정 | 중앙 IdP 계정·MFA | 앱 10개 이상, 계정 회수 SLA 1일 이하 |
| 운영/위험 | 단순 로그인 | 인증서 만료·XML 취약점 관리 | 인증서 만료 알림 30일 전 |

> 요약: SAML은 기존 기업 업무시스템 연계에 적합하고, 신규 API·모바일 서비스는 OIDC와 병행 판단한다.

| 리스크 | 원인 | 대응 방안 | 확인 지표 |
|:---|:---|:---|:---|
| Signature Wrapping | 서명된 노드와 사용 노드 불일치 | ID 기반 단일 Assertion 선택, schema validation | wrapping 테스트 10건 통과 |
| Replay | Assertion 재전송 | InResponseTo, NotOnOrAfter, assertion ID cache | replay 차단률 100% |
| Metadata 변조 | 인증서·ACS URL 변경 | metadata 서명 검증, 변경 승인 2인 | metadata 변경 감사 로그 |

> 요약: SAML 운영 리스크는 XML 처리와 신뢰 정보 변경에서 발생하므로 검증 라이브러리와 변경 통제를 함께 적용한다.

| 점검 항목 | 목표 기준 | 측정 방법 |
|:---|:---|:---|
| Assertion 검증 | signature, issuer, audience, time 100% 확인 | SP 로그, 보안 테스트 |
| 계정 수명주기 | 퇴사 계정 차단 4시간 이하 | IdP provisioning 리포트 |
| 인증서 운영 | 만료 30일 전 교체 완료 | CMDB, 인증서 스캔 |

> 요약: SAML 성공 기준은 로그인 성공률보다 Assertion 검증률, 계정 회수 시간, 인증서 만료 통제이다.

## Ⅵ. 실무 적용 및 결론

**적용 방안 3개:**
1. SP는 SAML library를 고정하고 XML Signature, AudienceRestriction, Recipient, NotOnOrAfter를 필수 검증 항목으로 둠.
2. IdP/SP Metadata는 서명 검증, validUntil 확인, 인증서 만료 30일 전 알림, 변경 승인 2인 원칙으로 운영함.
3. Assertion ID replay cache 5분 이상, ACS HTTPS 고정, RelayState allowlist, SIEM 로그인 감사 로그를 적용함.

**결론 (2줄):**
- 기술사 판단: 레거시 기업 SaaS와 브라우저 SSO는 SAML, API·모바일·SPA는 OIDC를 우선 검토함.
- 향후 방향: SAML은 OIDC 전환과 병행하되, 기존 SP는 XML Signature Wrapping 테스트와 Metadata 자동 점검으로 통제함.
