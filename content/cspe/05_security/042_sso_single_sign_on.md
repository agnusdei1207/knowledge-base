## 1. 한눈에 이해하기 (Core Intuition)
- **정의**: 사용자가 수많은 회사 업무 시스템(메일, 메신저, 전자결재, ERP 등)에 접속할 때, **단 한 번의 로그인(인증)만으로** 모든 시스템을 재로그인 없이 프리패스로 이용할 수 있게 해주는 마법 같은 인증 기술입니다.
- **필요성**: 시스템마다 아이디/비밀번호가 다르면 직원은 기억하기 힘들어 포스트잇에 적어 모니터에 붙여둡니다(보안 붕괴). 비밀번호 까먹었다고 IT팀에 전화하는 것도 낭비입니다. 사용자 편의성과 중앙 통제를 동시에 잡기 위해 필요합니다.
- **핵심 직관**: **"놀이공원 자유이용권 손목띠"**. 
  롤러코스터, 회전목마 탈 때마다 지갑을 꺼내 표를 끊는 것(개별 로그인)은 너무 귀찮습니다. 놀이공원 입구(SSO 인증 서버)에서 한 번 신분증 확인과 결제를 마치면 **'자유이용권 손목띠(인증 토큰)'** 를 채워줍니다. 이제 어떤 놀이기구(사내 시스템)를 가든 손목띠만 쓱 보여주면(토큰 자동 제출) 추가 절차 없이 즉시 탑승(로그인)합니다.

## 2. 왜 중요한가? (Background & Value)
- **등장 배경**: 사내망 하나만 쓰던 시절과 달리, 이제 직원들은 사내 그룹웨어, Salesforce, Slack, 구글 드라이브 등 수십 개의 클라우드 서비스(SaaS)를 오가며 일합니다. 파편화된 인증 피로감(Authentication Fatigue)을 해결하는 것이 IT 부서의 1순위 과제가 되었습니다.
- **가치**: 
  1. 사용자: "출근해서 PC 켜고 딱 한 번 로그인하면 끝!" (극강의 편리함).
  2. 보안팀: 퇴사자 발생 시 SSO 중앙 서버에서 계정 스위치를 '딸깍' 한 번만 끄면 50개 시스템의 접속 권한이 동시 차단되어 완벽한 보안 통제가 가능함 (보안성/관리 효율).

## 3. 어떻게 작동하는가? (Mechanism)
SSO 시스템에는 크게 3명의 배우가 등장합니다.
- **사용자 (User / Browser)**
- **IDP (Identity Provider, 신원 제공자)**: 인증을 전담하는 중앙 서버 (예: Okta, Microsoft Entra ID). "여권 발급 기관".
- **SP (Service Provider, 서비스 제공자)**: 사용자가 실제로 쓰려는 앱 (Slack, Salesforce 등). "비행기 탑승구".

**작동 원리 (일반적 흐름)**:
1. 사용자가 Slack(SP)에 접속 시도.
2. Slack은 "너 누군지 모르니, 일단 우리 회사의 공식 인증소(IDP)에 가서 증명받고 와!" 하고 사용자를 **IDP 화면으로 튕겨냄 (Redirect)**.
3. 사용자가 IDP 로그인 창에서 ID/PW (또는 OTP)를 입력해 인증 성공.
4. IDP는 "이 사람 우리 회사 홍길동 맞음" 이라는 **전자 보증서(SAML 토큰 또는 JWT 등)** 를 암호화해서 브라우저에게 쥐여줌.
5. 브라우저가 그 보증서를 Slack(SP)에 제출. Slack은 보증서의 서명을 확인하고 "오케이, 통과!" 하며 로그인 시켜 줌.
6. 이후 Salesforce(다른 SP)에 가면, 브라우저에 이미 IDP가 준 세션(쿠키)이 살아있으므로 3번 과정(비밀번호 재입력)을 생략하고 1초 만에 보증서를 받아 로그인됨. (이것이 Single Sign-On의 핵심).

## 4. 실전 활용 및 예시 (Real-world Application)
- **구체적 사례**: 
  - **SAML 2.0 기반 기업용 SSO**: 대기업이나 대학에서 주로 쓰는 "회사 계정으로 로그인하기" 인프라. XML 형식의 무거운 보증서를 주고받습니다.
  - **OIDC (OpenID Connect) 기반 소셜 로그인**: "구글 계정으로 로그인", "카카오로 로그인". 모바일 앱과 최신 웹 서비스에서 쓰는 JSON 토큰(JWT) 기반의 가볍고 현대적인 SSO 방식입니다.
- **주의점 및 흔한 오해**: 
  - SSO는 **'단일 실패점(SPOF, Single Point of Failure)'** 이라는 치명적 약점이 있습니다. 만약 카카오 서버(IDP)가 불타서 다운되면, 카카오 로그인(SSO)에 의존하는 수만 개의 다른 앱들(업비트 등)까지 몽땅 로그인이 불가능해지는 도미노 대참사가 일어납니다. 철저한 이중화/DR(재해 복구) 아키텍처가 필수입니다.

## 5. 핵심 비교 및 연결 개념 (Relation)
- **SSO vs EAM (Enterprise Access Management) vs IAM**:
  - SSO: 단순히 로그인을 한 번에 통과시켜 주는 '입장권 발급' 기능.
  - EAM: SSO 입장권을 기반으로 이 시스템 메뉴는 열어주고 저 메뉴는 닫아주는 '권한 통제' 기능.
  - IAM: 입사부터 퇴사까지 사람의 뼈대(신분)를 관리하는 거대한 총괄 아키텍처. (보통 현대의 IAM 플랫폼 안에 SSO 기능이 패키지로 다 들어가 있음).

# ✍️ 단답형 / 서술형 시험장 출격 준비

### Ⅰ. 핵심 인사이트
- **본질**: 파편화된 다수의 서비스(Service Provider, SP) 환경에서, 중앙 집중화된 신원 제공자(Identity Provider, IDP)가 발급한 신뢰 토큰(Token/Ticket) 기반 인증 대행을 통해 사용자에게 단 1회의 인증 과정만 요구하는 통합 인증 프레임워크.
- **가치**: 사용자의 Password Fatigue(비밀번호 피로)를 해소하여 섀도우 IT 및 패스워드 재사용(Credential Reuse) 취약점을 원천 방어하고, 관리자에게는 퇴사/직무 변경 시 신속한 통합 계정 프로비저닝/디프로비저닝 통제력을 제공함.
- **판단 포인트**: SSO 서버 장애 시 전사 서비스 마비를 유발하는 단일 장애점(SPOF) 리스크를 내포하므로 고가용성(HA/Active-Active) 아키텍처 설계가 필수적이며, 토큰 재전송 공격(Replay Attack) 방지를 위한 보안 채널(TLS)과 타임스탬프 검증이 수반되어야 함.

### Ⅱ. SSO의 인증 대행 아키텍처 모델
인프라 환경(온프레미스 vs 클라우드) 및 통신 규약에 따라 여러 모델이 혼재됨.
1. **인증 대행 (Delegation) 모델 - Agent / Gateway 방식 (레거시 사내망)**
   - 개별 애플리케이션 서버 앞에 Agent(대행 프로그램)를 심어, 로그인 요청을 가로채어 중앙 SSO 서버(정책 서버)에 자격 검증을 묻는 방식. 주로 동일한 도메인 내의 웹 애플리케이션 묶음에서 사용.
2. **티켓 기반 분산 모델 (Kerberos)**
   - Windows Active Directory(AD)의 핵심 기술. KDC(Key Distribution Center)가 인증 완료 시 TGT(Ticket Granting Ticket)를 발급하고, 이 티켓으로 수많은 사내 인트라넷 서버/폴더 접근을 SSO로 승인. (대규모 엔터프라이즈 로컬 망 표준).
3. **토큰/어설션 (Federation) 모델 (최신 클라우드/SaaS 방식)**
   - 도메인이 전혀 다른 외부 클라우드 서비스(예: 회사 망 $\rightarrow$ Salesforce.com) 간의 SSO 구현체.
   - 쿠키나 세션을 직접 공유할 수 없으므로, 암호화된 **SAML Assertion(XML)** 이나 **OIDC ID Token(JWT)** 을 브라우저를 매개(Redirect)로 던져서 상호 신뢰(Trust)를 맺음. (현대 SSO의 주류).

### Ⅲ. 페더레이션 (Federated Identity, 연합 인증) 모델의 원리
SSO를 넘어 "서로 모르는 외부 조직 간에" 신원 정보를 믿고 거래하는 체계.
- **Trust Relationship (신뢰 관계 구축)**: IDP(인증 기관)와 SP(서비스) 간에 사전에 인증서(퍼블릭 키)를 교환하여, IDP가 서명한 티켓(토큰)을 SP가 위조되지 않았다고 수학적으로 확신할 수 있게 함.
- **SP-Initiated Flow**: 사용자가 서비스(SP)에 먼저 접속 $\rightarrow$ IDP로 리다이렉트되어 인증 $\rightarrow$ 서비스로 토큰 복귀.
- **IDP-Initiated Flow**: 사용자가 사내 통합 포털(IDP 화면)에 먼저 접속 $\rightarrow$ 메뉴에 나열된 Slack 아이콘 클릭 $\rightarrow$ 토큰을 쥐고 해당 서비스로 직접 리다이렉트.

### Ⅳ. 보안 취약점 및 핵심 통제 방안
1. **SSO 마스터 키(Token) 탈취 리스크**: 
   - 사용자의 SSO 인증 쿠키(Session Cookie)나 JWT 토큰을 XSS나 중간자 공격(MITM)으로 탈취하면, 해커는 사내 모든 시스템에 제약 없이 횡적 이동(Lateral Movement) 가능.
   - 방어책: 토큰/세션 쿠키에 `HttpOnly`, `Secure` 플래그 강제. IP 주소나 브라우저 핑거프린트가 급변하면 즉시 세션을 강제 종료(Revoke)하는 동적 리스크 엔진 탑재.
2. **Replay Attack (재전송 공격)**:
   - 해커가 암호화된 토큰(SAML/JWT)을 훔쳐서 다음날 다시 제출(로그인 시도).
   - 방어책: 토큰 내부에 만료 시간(`exp`)과 1회성 난수(`nonce`)를 삽입하여 짧은 유효기간(보통 1~5분 내에 소비해야 함)을 강제.

### Ⅴ. 결론 및 실무적 판단 포인트
- SSO 인프라의 성공적인 구축은 단순히 로그인을 하나로 합치는 것이 아니라, IDP 진입점(Front-door)에서의 보안 강도를 극대화하는 것에 달려있습니다. 
- 따라서 전사 SSO 포털(Azure AD, Okta 등) 진입 시 **다중 인증(MFA, FIDO2/생체인증)** 을 필수(Mandatory) 정책으로 강제하여, 단 한 번의 강력한 인증이 하위 수십 개 시스템의 인증 강도(Level of Assurance)를 동반 상향(Uplift)시키도록 아키텍처를 설계해야 합니다.

### 💡 문제 유형별 목차 전환 포인트
- **[SSO/EAM/IAM 등 접근 통제 시스템 간의 관계 및 발전 과정]**: Ⅰ의 정의와 Ⅱ의 Agent 모델에서 Federation 모델로 진화한 과정을 짚어주며, 폐쇄망에서 클라우드 SaaS 시대로 넘어온 IT 거버넌스의 필요성 부각.
- **[연합 인증(Federation) 및 차세대 클라우드 SSO 방식 (SAML/OIDC)]**: Ⅲ번 항목의 트러스트 관계(Trust Relationship)와 리다이렉션 흐름(SP-Initiated)을 시스템 다이어그램 관점으로 구조화하여 구체적 서술.
