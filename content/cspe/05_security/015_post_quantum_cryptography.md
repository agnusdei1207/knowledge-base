# 📖 【암기용】 개념 완전 이해

> 목적: PQC를 처음 봐도 양자컴퓨터가 왜 RSA·ECC를 위협하고 어떤 전환이 필요한지 이해하게 만든다. 시험 답안 양식이 아니라, 이해를 위한 친절한 설명이다.

## 한눈에
- **개요**: PQC는 양자컴퓨터의 Shor 알고리즘 공격에도 견디도록 설계된 공개키 암호 기술
- **왜 필요한가**: RSA·ECC는 대규모 양자컴퓨터가 등장하면 소인수분해·이산로그 계산으로 개인키 추정 위험이 생김
- **핵심 직관**: 지금 캡처한 암호문을 미래 양자컴퓨터로 복호화하는 Harvest Now, Decrypt Later 위험에 대비하는 암호 교체 작업임

## 깊이 이해
- **배경·문제의식**: 대칭키 AES와 해시는 키 길이를 늘려 대응 가능하지만, 공개키 RSA·ECDSA·ECDH는 수학적 기반이 양자 알고리즘에 취약함. 장기 기밀 데이터는 오늘 탈취되어 10년 뒤 복호화될 수 있음
- **작동 원리**: NIST는 FIPS 203 ML-KEM을 키 설정 표준으로, FIPS 204 ML-DSA와 FIPS 205 SLH-DSA를 전자서명 표준으로 선정함. 실무는 기존 ECDHE와 ML-KEM을 함께 쓰는 하이브리드 방식으로 전환 위험을 줄임
- **비유**: 금고 자물쇠를 당장 모두 교체하기 어려우므로, 기존 자물쇠와 새 양자내성 자물쇠를 한동안 이중으로 거는 방식임
- **구체 예시**: TLS 하이브리드 실험은 X25519와 ML-KEM-768 계열 KEM을 함께 사용해 하나가 깨져도 세션키 전체가 노출되지 않도록 설계함
- **흔한 오해·주의점**: PQC는 QKD와 다름. PQC는 일반 컴퓨터에서 동작하는 알고리즘이고, QKD는 양자 물리 기반 키 분배 장비가 필요함

## 연결 개념
- TLS 1.3 핸드셰이크 - PQC KEM을 key_share에 결합하는 전환 대상
- 전자 서명 - ML-DSA·SLH-DSA가 RSA/ECDSA 대체 후보
- 키 관리 HSM·KMS - PQC 키 생성, 보관, 알고리즘 교체 정책이 필요한 운영 영역

# 📝 【답안용】 시험 답안 템플릿

> 목적: 시험장에서 25분에 그대로 쓰는 답안 양식. 작성방식(추상표현 금지·수치·도식·문제유형 전환)을 엄격히 지킨다.
> 핵심: PQC 답안은 알고리즘 이름 암기가 아니라 양자 위협, NIST 표준, 하이브리드 전환, crypto inventory를 연결해야 함.

## 핵심 인사이트 (3줄 요약)

> 1. **본질**: PQC(Post-Quantum Cryptography)는 양자컴퓨터 공격에 대비해 공개키 키교환·전자서명을 ML-KEM, ML-DSA, SLH-DSA로 전환하는 암호 체계임.
> 2. **가치**: 장기 기밀 데이터의 Harvest Now, Decrypt Later 위험을 줄이고 TLS·VPN·PKI·코드서명 신뢰를 유지함.
> 3. **판단 포인트**: NIST FIPS 203/204/205, 하이브리드 키교환, 암호 자산 목록, 성능·패킷 크기·상호운용성 검증이 핵심임.

## 출제 의도 및 답안 포인트

| 출제 의도 | 반드시 짚을 핵심 | 감점 회피 포인트 |
|:---|:---|:---|
| 양자 위협 이해 | Shor 알고리즘, RSA/ECC 취약, Grover는 대칭키 영향 | "모든 암호가 즉시 무력화" 식 과장 금지 |
| 표준 알고리즘 확인 | FIPS 203 ML-KEM, FIPS 204 ML-DSA, FIPS 205 SLH-DSA | Kyber·Dilithium 명칭만 쓰고 FIPS 번호 누락 금지 |
| 전환 전략 판단 | Crypto Inventory, Hybrid TLS, HSM/KMS, 인증서 전환 | 단일 알고리즘 일괄 교체 답안 금지 |

> 요약: PQC는 양자 위협 대응 기술이면서 동시에 암호 자산 파악, 하이브리드 운영, 표준 기반 전환 프로젝트임.

---

## Ⅰ. 개요 및 필요성

- 개요: 양자내성 공개키 암호
- 배경: RSA·ECC는 대규모 양자컴퓨터의 Shor 알고리즘에 취약하고, 장기 보존 데이터는 HNDL 공격에 노출될 수 있음.
- 필요성: NIST FIPS 203/204/205 기반 KEM·서명 전환으로 TLS, VPN, PKI, 전자서명의 장기 기밀성과 무결성을 유지함.

---

## Ⅱ. 구조 및 구성요소

```text
Crypto Inventory -> 위험분류 -> PQC 알고리즘 선택 -> 하이브리드 적용 -> 성능/상호운용 검증
                                     +-> KMS/HSM 키관리
                                     +-> 인증서/프로토콜 전환
```

| 구성요소 | 역할 | 특이사항 |
|:---|:---|:---|
| ML-KEM | 키 캡슐화·키 설정 | NIST FIPS 203, TLS/VPN 키교환 후보 |
| ML-DSA | 일반 전자서명 | NIST FIPS 204, 인증서·코드서명 후보 |
| SLH-DSA | 해시 기반 전자서명 | NIST FIPS 205, 보수적 백업 서명 |
| Hybrid Mode | 기존 ECDHE/RSA와 PQC 병행 | 상호운용 위험 감소, 패킷 크기 증가 |
| Crypto Inventory | 암호 사용처 목록화 | 인증서, API, DB, 펌웨어, 백업 포함 |

> 요약: PQC 구조는 표준 알고리즘, 하이브리드 적용, 키관리, 자산 목록화가 결합된 전환 체계임.

---

## Ⅲ. 동작원리 및 흐름도

```text
자산 식별 -> 데이터 보존기간/위협 평가 -> ML-KEM/ML-DSA 선택
-> 하이브리드 PoC -> 인증서/KMS/프로토콜 반영 -> 모니터링/롤백
```

| 단계 | 처리 내용 | 검증 기준 |
|:---:|:---|:---|
| 1 | RSA/ECC 사용처 식별 | TLS, VPN, SSH, S/MIME, 코드서명 |
| 2 | 데이터 수명과 양자 위험 평가 | 5년 이상 기밀 데이터 우선순위 상향 |
| 3 | 표준 알고리즘 매핑 | ML-KEM 키교환, ML-DSA/SLH-DSA 서명 |
| 4 | 하이브리드 적용과 성능검증 | handshake size, CPU, p95 latency |
| 5 | 운영 전환과 롤백 | KMS 정책, 인증서 프로파일, 호환성 |

> 요약: PQC 전환은 알고리즘 선택보다 자산 식별, 우선순위, 하이브리드 검증, 운영 롤백이 핵심 흐름임.

## Ⅳ. 특징

| 구분 | RSA/ECC 기존 체계 | PQC 체계 | 수치·표준 판단 |
|:---|:---|:---|:---|
| 수학 기반 | 소인수분해, 이산로그 | 격자, 해시 기반 등 | FIPS 203/204/205 |
| 양자 공격 | Shor 알고리즘에 취약 | 알려진 Shor 직접 공격 대상 아님 | NIST 보안 카테고리 기준 |
| 성능/크기 | 인증서·서명 크기 작음 | 키·서명·패킷 크기 증가 | ML-KEM-768 공개키 약 1KB 수준 |
| 전환 방식 | 단일 알고리즘 운영 | 하이브리드·Crypto-Agility | TLS, PKI, HSM 호환성 검증 |

> 요약: PQC는 양자 위협 대응에 필요하지만, 키·서명 크기와 상호운용성 비용을 전환 계획에 반영해야 함.

## Ⅴ. 심화 비교 및 적용 판단

| 구분 | 기존/대안 | PQC 적용 | 선택 기준 |
|:---|:---|:---|:---|
| 키교환 | ECDHE, RSA key transport | ML-KEM 또는 ECDHE+ML-KEM | 장기 기밀 데이터와 인터넷 공개 서비스 우선 |
| 전자서명 | RSA-PSS, ECDSA | ML-DSA, SLH-DSA | 코드서명·펌웨어는 장기 검증 기간 기준 |
| 운영/위험 | 검증된 생태계 | 라이브러리·HSM·인증서 호환성 확인 필요 | canary, fallback, vendor 지원표 |

> 요약: PQC 선택은 양자 위협 수준보다 데이터 보존기간, 프로토콜 호환성, 운영 롤백 가능성으로 우선순위를 정함.

| 리스크 | 원인 | 대응 방안 | 확인 지표 |
|:---|:---|:---|:---|
| 상호운용 실패 | 클라이언트·중간장비 PQC 미지원 | 하이브리드 모드, canary 5%, fallback | handshake_failure 0.1% 이하 |
| 성능 저하 | 키·서명 크기 증가, CPU 비용 | p95 지연 측정, 압축 금지 검토, HW 가속 | p95 latency 증가 10% 이하 |
| 알고리즘 교체 | 표준 변경, 구현 취약점 | Crypto-Agility, 알고리즘 추상화 | 교체 소요 30일 이하 |

> 요약: PQC 리스크는 호환성·성능·표준 변경이며, 하이브리드와 암호 민첩성으로 통제함.

| 점검 항목 | 목표 기준 | 측정 방법 |
|:---|:---|:---|
| 자산 식별 | RSA/ECC 사용처 100% 목록화 | SBOM, 인증서 스캔, 코드 검색 |
| 전환 검증 | 우선순위 1 서비스 PoC 완료 | TLS/VPN/PKI 상호운용 테스트 |
| 운영 지표 | p95 지연 10% 초과 증가 없음, 오류율 0.1% 이하 | APM, LB 로그, KMS 감사로그 |

> 요약: PQC 도입은 자산 목록 완성도, PoC 범위, 지연·오류율로 단계별 성공 여부를 판단함.

## Ⅵ. 실무 적용 및 결론

**적용 방안 3개 (필수 - 단계별 또는 항목별):**
1. 1단계: TLS·VPN·SSH·PKI·코드서명 RSA/ECC 사용처를 Crypto Inventory로 목록화하고, 5년 이상 보존 데이터부터 우선순위 지정
2. 2단계: 인터넷 경계 TLS와 VPN에 ECDHE+ML-KEM 하이브리드 PoC 적용, p95 지연·handshake_failure·패킷 크기 측정
3. 3단계: KMS/HSM, 인증서 프로파일, CI/CD 서명 도구에 ML-KEM·ML-DSA 지원을 반영하고 30일 롤백 절차 수립

**결론 (2줄):**
- 기술사 판단: 장기 기밀 데이터와 공개 경계 채널은 PQC 하이브리드를 우선 적용하고, 내부 단기 데이터는 Crypto Inventory 후 단계 전환함
- 향후 방향: NIST FIPS 203/204/205 기반 표준 준수와 TLS·PKI·HSM 생태계 호환성 검증을 병행해야 함
