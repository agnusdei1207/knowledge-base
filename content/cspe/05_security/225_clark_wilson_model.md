## 1. 한눈에 이해하기 (Core Intuition)
- **정의**: 수학 공식(등급표)에만 의존하던 기존 모델(비바 등)을 버리고, **"사용자가 데이터(DB)를 직접 건드리지 못하게 막고 반드시 정해진 승인 프로그램(응용 프로그램)을 통해서만 고치도록 강제하며, 업무를 승인자와 실행자로 분리(직무 분리)하여 권한 있는 내부자의 횡령이나 실수를 원천 차단하는 상업용(금융권) 무결성 보안 모델"** 입니다.
- **필요성**: 은행원(최고 등급 권한자)이 고객 계좌의 잔고를 자기 마음대로 100원에서 1억 원으로 조작(횡령)한다고 칩시다. 기존 Biba 모델은 "최고 등급의 주체가 높은 등급의 파일에 글을 쓰는 것"이므로 이걸 막지 못했습니다. 즉, '합법적 권한을 가진 내부자의 악의적 조작이나 실수'에 무방비였습니다. 이를 막으려면 등급표(MAC)가 아니라, **'어떤 프로그램을 썼는가?'와 '결재 도장은 2개 다 받았는가?'** 라는 비즈니스 프로세스적인 통제가 필요했습니다.
- **핵심 직관**: **"식당 주방에 손님이 직접 들어가지 못하게 하는 시스템"**. 
  - 과거 (Biba 모델): VIP 손님(고권한)은 주방(DB)에 직접 들어가 자기가 원하는 대로 요리(조작)를 할 수 있음. 주방이 엉망이 됨.
  - **클라크-윌슨 모델**: 아무리 VIP 손님이라도 절대 주방에 못 들어감. 반드시 **'웨이터(검증된 프로그램)'** 에게 주문서(API)를 주고, 웨이터가 **'매니저의 승인(직무 분리)'** 을 받은 뒤에만 주방에 들어가 요리를 가져오게 만듦. $\rightarrow$ 데이터(주방)의 무결성이 완벽히 유지됨.

## 2. 왜 중요한가? (Background & Value)
- **등장 배경**: 1980년대 후반, 상업 환경(특히 금융/회계 분야)에서는 군대식 등급(Top Secret 등)이 의미가 없었습니다. 은행에서는 "정보 유출(기밀성)"보다도 "장부 금액이 1원이라도 틀어지는 것(무결성)"이 100배 더 중요했습니다. D. Clark과 D. Wilson은 1987년, 군사 목적의 Biba 모델이 현실 상거래에 맞지 않음을 비판하며, 기업 회계 감사 원칙인 '직무 분리(Separation of Duty)'와 '소프트웨어 통제'를 IT 보안 아키텍처로 구현해 냈습니다.
- **가치**: "엔터프라이즈(기업용) 보안 아키텍처의 완성". 오늘날 우리가 은행 앱에서 돈을 보낼 때 OTP를 입력(사용자 인증)하고, 이체 내역이 변경 불가능한 로그(Audit)로 남는 모든 전산 시스템의 뼈대가 바로 클라크-윌슨 모델의 설계 사상에서 출발했습니다.

## 3. 어떻게 작동하는가? (Mechanism)
이 모델은 '사람(주체)'과 '데이터(객체)' 사이에 **'가드(Guard, 프로그램)'** 를 세워 3자 구도를 만듭니다.

1. **데이터의 이원화 (보호받는 데이터 vs 일반 데이터)**
   - **CDI (제한적 데이터 항목)**: 무조건 보호해야 하는 핵심 데이터 (예: 은행 계좌 잔고, 장부).
   - **UDI (비제한적 데이터 항목)**: 외부에서 들어오는 일반 데이터 (예: 사용자가 웹에 입력한 키보드 값).
2. **TP (변환 절차 / 검증된 프로그램) - "웨이터 역할"**
   - 핵심 규칙: **"사용자는 절대 CDI(잔고 DB)를 직접 수정할 수 없다."**
   - 오직 사전에 검증받고 승인된 **응용 프로그램(TP, Transformation Procedure)** 만이 CDI를 만질 수 있습니다. (예: 은행 텔러의 송금 전용 UI 프로그램). 
   - TP는 UDI(사용자 입력)가 정상적인지 검사하고 CDI에 반영합니다.
3. **직무 분리 (Separation of Duty)**
   - 은행원이 송금(TP 실행)을 눌러도 바로 돈이 가지 않고, 부장님의 **'승인(Approval)'** 을 요구하게 만듭니다. 권한을 두 명에게 쪼개어(투맨 룰), 혼자서 횡령하는 것을 물리적으로 불가능하게 만듭니다.
4. **감사 추적 (Auditing)**
   - TP(검증된 프로그램)가 데이터를 수정할 때마다, "누가, 언제, 어떤 프로그램으로 잔고를 바꿨다"는 **수정 불가 로그(Append-only Log)** 를 남깁니다.

## 4. 실전 활용 및 예시 (Real-world Application)
- **구체적 사례 (웹 서버 아키텍처와 SQL 인젝션 방어)**: 
  - 클라크-윌슨 모델은 현대 웹서비스 아키텍처(3-Tier) 그 자체입니다.
  - 사용자는 데이터베이스(DB, CDI)에 직접 접속하지 못합니다(방화벽 차단). 오직 **WAS 서버의 응용 프로그램 API (TP)** 만이 DB를 만질 수 있습니다. 해커가 웹페이지 검색창에 이상한 해킹 문자(UDI)를 넣어도, 이 TP(프로그램)가 깐깐하게 필터링해서 DB가 망가지는 것(무결성 훼손)을 막아냅니다.
- **주의점 및 흔한 오해**: 
  - "이 모델은 완벽한 무결성을 지키나요?" $\rightarrow$ **'TP(프로그램)' 자체에 버그가 없어야 한다는 전제가 깔려있습니다.**
  - 만약 중간 웨이터 역할인 TP(응용 프로그램/웹 서버) 자체에 코딩 에러(버그)나 제로데이 취약점이 있다면 해커가 TP를 속이고 주방(DB)을 털어버릴 수 있습니다. 따라서 이 모델이 유지되려면 소프트웨어 소스코드에 대한 주기적인 보안 취약점 점검(시큐어 코딩)이 절대적으로 필요합니다.

## 5. 핵심 비교 및 연결 개념 (Relation)
기밀성과 무결성을 지키는 3대 천왕 비교의 최종 완성:
| 모델명 | 주요 목적 | 주된 통제 방법 | 단점 / 한계점 |
|---|---|---|---|
| **Bell-LaPadula** (벨-라파듈라) | **기밀성** (군사망) | 계급 기반 수학적 통제 (No Write Down) | 무결성이 망가질 수 있음 |
| **Biba** (비바) | **무결성** (초기 모델) | 계급 기반 수학적 통제 (No Write Up) | **내부자의 고의적 조작/횡령을 못 막음** |
| **Clark-Wilson** (클라크-윌슨) | **무결성** (금융권 상업망) | **중간 프로그램(TP) 경유, 직무 분리(결재)** | 프로그램 자체를 개발하고 검증하는 비용이 많이 듦 |

# ✍️ 단답형 / 서술형 시험장 출격 준비

### Ⅰ. 핵심 인사이트
- **본질**: 상업/금융 환경에서 요구되는 완벽한 데이터 무결성 보장을 위해, 사용자가 데이터에 직접 접근하는 것을 차단하고 반드시 **검증된 변환 절차(TP: Transformation Procedure) 소프트웨어를 통해서만 데이터 접근을 허용하며, 엄격한 직무 분리(Separation of Duty)를 시스템적으로 강제하는 응용 계층의 무결성(Integrity) 보안 모델 (Clark-Wilson Model).**
- **가치**: "합법적 내부자에 의한 고의/과실 오염(Fraud) 방어". Biba 모델 등 수학적 MAC 모델은 '접근 권한이 있는' 주체가 앙심을 품고 데이터를 변조하는 내부자 위협(Insider Threat)에는 무방비였습니다. 클라크-윌슨 모델은 보안의 초점을 OS 커널 레벨의 수식(Read/Write 규칙)에서 **'비즈니스 애플리케이션의 워크플로우(Workflow)'** 로 끌어올렸습니다. 모든 트랜잭션은 철저히 검증된 애플리케이션(TP)에 의해 통제되며, 투맨 룰(Two-man Rule)과 감사 추적(Audit Trail)을 아키텍처에 내재화함으로써, 회계 감사의 본질인 에러(Error)와 사기(Fraud) 방지를 IT 시스템으로 완벽히 구현해 냈습니다.
- **판단 포인트**: 엔터프라이즈 시스템 아키텍트는 3-Tier(Web-WAS-DB) 아키텍처를 그릴 때 이 모델을 차용해야 합니다. 개발자나 DBA(데이터베이스 관리자)가 운영(Production) DB에 직접 쿼리 툴(SSMS, DBeaver)을 붙여 데이터를 수정하는 행위는 이 모델의 철저한 위반(CDI 직접 수정)입니다. 아무리 급한 데이터 보정도 반드시 백오피스(Admin Web) 상의 검증된 UI(TP)를 통해 실행되어야 하고 다른 관리자의 승인(직무 분리)을 거치도록 설계하는 것이 컴플라이언스(ISMS/PCI-DSS) 인증의 필수 조건입니다.

### Ⅱ. Clark-Wilson 모델의 4대 핵심 구성 요소 (용어 매핑)
객관식/단답형 시험의 절대 출제 포인트.
1. **CDI (Constrained Data Item / 제한적 데이터 항목)**
   - 시스템 내에서 무결성이 반드시 유지되어야 하는 중요한 정보 자산 (예: 은행 계좌 원장, 급여 테이블).
   - 오직 사전에 승인된 검증 프로그램(TP)에 의해서만 조작될 수 있음.
2. **UDI (Unconstrained Data Item / 비제한적 데이터 항목)**
   - 무결성을 신뢰할 수 없는 외부 세계의 데이터나 일반 파일 (예: 사용자가 폼에 입력한 키보드 텍스트).
   - UDI는 TP를 거쳐 적절성 필터링(Input Validation)을 통과한 후에만 CDI로 변환/병합될 수 있음.
3. **TP (Transformation Procedure / 변환 절차)**
   - CDI를 하나의 유효한(Valid) 상태에서 다른 유효한 상태로만 변경하도록 사전에 엄격히 프로그래밍되고 테스트된 **검증된 애플리케이션/API.**
   - 사용자와 DB 사이의 프록시(Proxy) 역할을 수행.
4. **IVP (Integrity Verification Procedure / 무결성 검증 절차)**
   - 시스템(CDI)의 데이터가 현재 무결한 상태(에러나 조작이 없는 상태)인지를 주기적으로 점검(Audit)하고 보증하는 백그라운드 확인 절차 프로그램. (예: 매일 자정 계좌 총액의 대차대조표를 자동 검증하는 배치 프로그램).

### Ⅲ. 핵심 보안 통제 원칙 (인증과 결재)
1. **사용자-TP-데이터 간의 3자 관계 (접근 제어 삼원소)**
   - 전통적 모델이 `[사용자] $\rightarrow$ [데이터]` 권한만 검사했다면, 이 모델은 **`[사용자] $\rightarrow$ [이 TP(프로그램)를 실행할 권한이 있는가?] $\rightarrow$ [이 TP가 저 CDI(데이터)를 만질 권한이 있는가?]`** 라는 3단계 바인딩(Binding) 검사를 수행함.
2. **직무 분리 (Separation of Duty)**
   - 단일 사용자가 중요한 트랜잭션의 처음부터 끝까지 전체를 실행(Execute)할 수 없도록, 권한을 분할함. (예: 전표를 기안하는 TP 권한과 전표를 승인(결재)하여 DB에 반영하는 TP 권한을 2명의 다른 사용자에게 강제로 나누어 할당).

### Ⅳ. 최신 트렌드: 클라크-윌슨 사상의 클라우드/DevOps 적용
- **CI/CD 파이프라인의 무결성 통제**: 최신 데브옵스 환경에서 개발자(User)는 운영 환경(CDI)에 소스코드를 직접 밀어 넣지 못합니다. 코드는 반드시 Git(저장소)에 커밋(UDI)되며, 자동화된 빌드/테스트 파이프라인과 코드 리뷰 승인 절차(TP 및 직무 분리)를 거친 릴리스(Release) 패키지만 운영 서버에 배포됩니다.
- **블록체인 스마트 컨트랙트(Smart Contract)**: 이더리움 블록체인에서 원장(CDI)은 스마트 컨트랙트(TP)라는 검증된 불변의 코드에 의해서만 수정(State Transition)됩니다. 이 모델이 완벽하게 분산 환경으로 진화한 가장 현대적인 사례입니다.

### Ⅴ. 결론 및 실무적 판단 포인트
- 보안 컨설턴트 및 ISMS 심사원은 기업의 정보 시스템을 심사할 때, 단순한 패스워드 정책보다 **'애플리케이션 통제(Application Control) 및 트랜잭션 로그 추적성'** 을 중점 점검해야 합니다. 클라크-윌슨 모델의 철학에 따라, 시스템은 (1) 아무리 높은 권한자(DBA)라 하더라도 우회 경로(Bypass)로 데이터를 직접 변조하지 못하게 접근 경로를 일원화(Gateway)해야 하며, (2) 발생한 모든 상태 변경(State Change) 이력은 위변조 방지 스토리지(WORM)나 블록체인 기반의 불변(Immutable) 원장에 보관(IVP 검증용)되도록 아키텍처를 설계하여 내부자 횡령(Fraud) 위협을 시스템 구조적으로 차단해야 합니다.

### 💡 문제 유형별 목차 전환 포인트
- **[금융 비즈니스 환경의 데이터 위변조/내부자 횡령(Fraud) 방어 및 애플리케이션 무결성 보장 모델]**: Ⅰ과 Ⅱ번(CDI, TP 개념 중심)을 전면에 세워, 벨-라파듈라나 비바와 같은 수리적 MAC 모델이 실무 환경(은행)에서 왜 실패했으며 중간 매개체(TP)가 왜 필요한지 비즈니스 아키텍처 관점에서 증명.
- **[엔터프라이즈 시스템의 직무 분리(SoD) 구현 방안 및 현대 데브옵스(DevOps) 환경의 무결성 확보 아키텍처]**: Ⅲ번(3자 관계 및 직무 분리)을 핵심으로 짚고 Ⅳ번(스마트 컨트랙트, CI/CD 연계)을 엮어, "1980년대 상업 모델이 현대의 무중단 배포(CI/CD) 파이프라인과 블록체인 스마트 컨트랙트(TP) 아키텍처로 어떻게 진화하고 계승되었는가"에 대한 심화 기술 해법 전개.
