## 1. 한눈에 이해하기 (Core Intuition)
- **정의**: 클라우드 시대에는 마우스 클릭으로 서버를 만들지 않고 텍스트 코드(테라폼 등)로 수백 대의 서버를 한 방에 찍어냅니다. IaC 보안은 이 **"인프라를 찍어내는 텍스트 설계도(코드)"에 해킹 구멍(설정 오류)이 없는지 서버가 만들어지기 전에 미리 스캔해서 고치는 보안 기술**입니다.
- **필요성**: 개발자가 마우스 실수로 클라우드 DB의 접근 권한을 '전체 공개(Public)'로 만들면 대형 사고가 터집니다. 그런데 이걸 '코드(IaC)'로 돌리면 클릭 한 번에 100대의 DB가 순식간에 '전체 공개'가 되는 끔찍한 대량 복제 사고가 터집니다. 그래서 인프라가 켜지기 전, 텍스트 도면일 때 무조건 막아야 합니다.
- **핵심 직관**: **"아파트 단지 설계도면 사전 심사"**. 
  - 과거: 아파트를 다 지은(클라우드 인프라가 배포된) 다음에 소방 점검(CSPM 등)을 나가서 "스프링클러가 없네? 다 부수고 다시 지어!"라고 합니다. (돈과 시간 낭비).
  - IaC 보안: 아파트를 짓기도 전, 건축가가 그린 종이 '설계도(Terraform 코드)'를 보고 "어? 300세대 전부에 스프링클러 누락됐네. 설계도 수정해서 다시 가져와!" 라며 벽돌 하나 올리기 전에 사고를 100% 예방(Shift-Left)하는 심사입니다.

## 2. 왜 중요한가? (Background & Value)
- **등장 배경**: 클라우드 환경에서는 해킹 사고의 99%가 고도화된 해킹 기술이 아니라 관리자의 **'설정 오류(Misconfiguration)'** 때문에 일어납니다 (가트너 발표). Terraform, AWS CloudFormation 등 코드형 인프라(IaC)가 보편화되면서, 이 설정 오류가 코드를 타고 맹렬한 속도로 번지는 것을 런타임(운영) 단계에서 막기엔 너무 늦었다는 깨달음에서 대두되었습니다.
- **가치**: 보안을 인프라 생성 전(Pre-deployment)으로 완전히 끌어당깁니다(Shift-Left). 클라우드 운영 환경에서 발생할 99%의 설정 오류 취약점을 파이프라인 단계에서 원천 차단하여 막대한 보안 복구 비용을 0원으로 만듭니다.

## 3. 어떻게 작동하는가? (Mechanism)
IaC 보안은 CI/CD 파이프라인의 극초반에 개입합니다.

1. **설계도(IaC) 작성**
   - 개발자가 "AWS에 방화벽 포트 22번(SSH)을 전 세계(0.0.0.0/0)에 열어줘"라는 내용의 Terraform 코드를 짭니다.
2. **IaC 보안 스캐너 작동 (로컬/CI 단계)**
   - 개발자가 코드를 푸시(Push)하면, **Checkov(체코브)** 나 **TFLint**, **tfsec** 같은 전용 스캐너가 소스코드를 텍스트 분석합니다.
   - 룰 엔진: "포트 22번을 인터넷 전체에 개방하는 코드는 규정 위반(Violation)이다!"
3. **배포 차단 및 피드백 (Block & Remediation)**
   - 스캐너가 빌드 과정(CI 파이프라인)을 멈추고 실패(Fail) 처리합니다. (Break the build).
   - "22번 포트 전체 개방은 위험하니, 코드를 특정 회사 IP 대역으로 수정하세요"라고 개발자의 깃허브에 피드백(가이드)을 남겨줍니다.
4. **인프라 생성 (Deploy)**
   - 수정된 안전한 코드만이 클라우드 환경(AWS, GCP)에 쏴져서, 처음부터 튼튼한 방화벽과 서버가 생성됩니다.

## 4. 실전 활용 및 예시 (Real-world Application)
- **구체적 사례**: 
  - 개발자가 테라폼 코드에 AWS S3 버킷(저장소) 생성 코드를 넣으면서, 암호화 옵션(`encrypted = true`)을 빼먹었습니다. IaC 보안 툴이 이를 감지하고, 아예 코드를 `encrypted = true`가 포함된 상태로 자동 수정해서 커밋(Auto-Remediation)해 버려 개발자의 귀찮음을 없애주는 수준까지 발전했습니다.
- **주의점 및 흔한 오해**: 
  - IaC 보안 툴을 적용했다고 운영망 감시(CSPM)를 안 해도 될까요? 아닙니다. 누군가 급하다고 코드를 안 고치고 AWS 콘솔에 마우스로 직접 접속해서 S3 권한을 전체 공개로 풀어버리는 일(Configuration Drift, 설정 표류)이 반드시 발생합니다. 따라서 IaC 스캔(사전)과 CSPM(사후)은 양방향으로 필요합니다.

## 5. 핵심 비교 및 연결 개념 (Relation)
- **SAST vs IaC 보안**:
  - **SAST**: "어플리케이션(Java, Python) 소스코드"에 있는 논리적 버그(SQL 인젝션 등)를 찾음.
  - **IaC 보안**: "인프라(Terraform, YAML) 설정 코드"에 있는 클라우드 설정 구멍(포트 개방, 암호화 누락)을 찾음.
- **IaC 보안 vs CSPM**:
  - **IaC 보안**: 건물 짓기 전 "설계도" 상태에서 미리 검사(예방).
  - **CSPM**: 건물 지어진 후 "현장"에 돌아다니며 문이 잘 닫혀있는지 검사(탐지/모니터링).

# ✍️ 단답형 / 서술형 시험장 출격 준비

### Ⅰ. 핵심 인사이트
- **본질**: Terraform, AWS CloudFormation, Kubernetes YAML 등 인프라스트럭처를 프로비저닝하는 선언적/명령형 코드(IaC)를, 클라우드 환경에 배포되기 전(Pre-deployment) CI/CD 파이프라인 단계에서 정적 스캐닝하여 보안 설정 오류(Misconfiguration)와 컴플라이언스 위반을 원천 차단하는 기술.
- **가치**: 클라우드 보안 침해의 최대 원인인 '설정 오류'가 대규모 인프라로 프로비저닝되는 것을 방어(Shift-Left)하며, Policy as Code(코드형 정책)를 통해 보안 거버넌스를 개발자의 워크플로우 내에 일관되고 자동화된 형태로 강제함.
- **판단 포인트**: 현대 클라우드 보안 아키텍처는 IaC 보안(사전 통제)과 CSPM(사후 런타임 통제)의 결과를 매핑(Tracing)하여, 런타임에서 발생한 설정 변경(Drift)을 다시 IaC 코드로 역반영시키는 **양방향 피드백 루프(Drift Remediation)** 구현이 성숙도의 척도임.

### Ⅱ. IaC 보안의 주요 탐지 영역 및 통제 위협
클라우드 인프라 아키텍처 설계의 3대 치명적 리스크를 코딩 단계에서 제어함.
1. **Public Exposure (의도치 않은 노출)**
   - 위협: S3 버킷 ACL Public-Read 허용, Security Group의 0.0.0.0/0 All Open (SSH, RDP 등).
   - 통제: 외부 접근 허용 규칙 차단 및 사내 VPN/베스천(Bastion) 대역으로만 인바운드 제한 강제.
2. **Data at Rest & in Transit Encryption (암호화 누락)**
   - 위협: RDS(DB), S3 볼륨 생성 시 저장소 암호화(KMS) 옵션 미설정. 로드밸런서(ALB)에 HTTP(80) 리스너만 오픈.
   - 통제: 모든 스토리지 리소스 프로비저닝 시 `encryption_at_rest=true` 및 HTTPS/TLS 강제 옵션 스캐닝.
3. **Identity and Access Management (과도한 권한)**
   - 위협: AWS IAM Role 생성 시 특정 서비스에 `Action: "*"` (모든 권한 허용)이라는 와일드카드 부여.
   - 통제: 최소 권한의 원칙(PoLP) 위반 탐지. "필요한 S3 버킷 읽기 권한만 명시적으로 작성하라"는 경고 발생.

### Ⅲ. Policy as Code (코드형 정책) 아키텍처
보안팀의 규정(엑셀 문서)을 스캐너가 이해하는 언어(코드)로 변환하여 자동화하는 핵심 사상.
- **OPA (Open Policy Agent)와 Rego 언어**: 
  - 업계 표준 정책 엔진. 기업의 보안 요건(예: "모든 EC2 인스턴스에는 'Owner' 태그가 있어야 한다")을 **Rego**라는 언어로 작성(Policy as Code).
  - 테라폼으로 작성된 IaC 코드가 실행되기 전, OPA 엔진이 이 Rego 룰과 대조(Evaluate)하여 통과(Pass)해야만 빌드 파이프라인을 다음 단계로 넘김.

### Ⅳ. IaC와 CSPM의 상관관계: Configuration Drift (설정 표류)
- **문제 발생**: 파이프라인에서 IaC 코드를 검증하고 완벽히 안전한 상태로 프로비저닝을 마쳤음. 그러나 장애 처리 차 새벽에 인프라 관리자가 AWS 웹 콘솔에 직접 들어가 방화벽(Security Group) 포트를 마우스로 열어버림.
- **Configuration Drift (설정 표류)**: 저장소에 있는 IaC 소스코드(진실)와 현재 실제 돌아가는 클라우드 환경(현실)의 상태가 어긋나버린 위험한 상태.
- **아키텍처 대안 (GitOps 융합)**: CSPM이 런타임에서 설정 변경을 감지하면 즉시 알람을 울리고, 변경된 환경을 무시한 채 IaC 저장소의 '안전한 원본 코드'를 다시 덮어씌워 강제 롤백(Auto-remediation via GitOps)하는 파이프라인 설계가 필수.

### Ⅴ. 결론 및 실무적 판단 포인트
- 인프라 아키텍트는 데브옵스 조직의 반발을 줄이기 위해, CI/CD 서버에서 스캔하기 전에 **개발자의 로컬 노트북 IDE 환경에 Checkov, TFLint 플러그인을 설치**하여 타이핑하는 순간 즉시 피드백을 받도록 Shift-Left를 끝단까지 밀어붙여야 합니다. 이를 통해 보안팀과 개발팀 간의 리뷰 병목을 없애는 것이 핵심입니다.

### 💡 문제 유형별 목차 전환 포인트
- **[클라우드 설정 오류(Misconfiguration) 위협 대응 및 Shift-Left 통제]**: Ⅰ번과 Ⅱ번 위협/탐지 영역을 중심으로 전개. 클라우드 사고의 근본 원인이 잘못된 프로비저닝에 있음을 짚고, 이를 IaC 검증으로 선제 차단하는 아키텍처적 가치 서술.
- **[Policy as Code 기반의 클라우드 거버넌스 자동화]**: Ⅲ번 OPA/Rego 아키텍처를 강조하고, Ⅳ번의 설정 표류(Configuration Drift) 문제를 CSPM과 연계하여 어떻게 '선언적(Declarative) 인프라 통제'로 해결하는지 입체적 논의.
