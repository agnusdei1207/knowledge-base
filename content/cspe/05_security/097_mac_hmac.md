## 1. 한눈에 이해하기 (Core Intuition)
- **정의**: 내가 보낸 메시지가 중간에 조작되지 않았는지 확인하는 지문(해시) 기술에다가 **송신자와 수신자만 아는 '비밀 열쇠(대칭키)'를 섞어 넣어, "내용이 위조되지 않았음"은 물론 "진짜 내 친구가 보낸 게 맞음"까지 동시에 증명하는 보안 기술**입니다.
- **필요성**: 그냥 해시(Hash)만 쓰면, 해커가 택배 상자를 열고 안의 물건을 훔친 뒤, 가짜 물건을 넣고 자기가 새로 해시(지문)를 찍어서 보내면 속아 넘어갑니다. "이 지문을 찍을 수 있는 사람은 나와 내 친구뿐이다"라는 확신을 주기 위해, 해시 믹서기에 데이터를 갈 때 **비밀 열쇠**를 같이 넣고 갈아버리는 꼼수가 필요해졌습니다.
- **핵심 직관**: **"비밀 도장이 찍힌 봉인 씰(Seal)"**. 
  - 해시(Hash): 일반 테이프입니다. 누군가 뜯고 가짜 물건을 넣은 뒤 똑같은 일반 테이프로 다시 붙이면 티가 안 납니다.
  - **MAC (메시지 인증 코드)**: 송신자와 수신자만 나눠 가진 **'비밀 도장(Key)'** 을 꾹 찍어 만든 특수 테이프(봉인 씰)입니다. 해커가 뜯고 가짜 물건을 넣을 순 있지만, 겉면에 '비밀 도장'을 찍을 수가 없으니 봉인 씰이 가짜인 게 바로 들통납니다.

## 2. 왜 중요한가? (Background & Value)
- **등장 배경**: 네트워크 통신에서 무결성(데이터 변조 방지)은 확인했는데, "방금 나한테 접속한 사람이 해커가 위장한 거 아니야?"라는 '인증(Authentication)' 문제가 항상 뒤따랐습니다. 비대칭키(전자서명)로 인증하면 확실하지만 속도가 너무 느려서 폰이나 IoT 기기가 감당을 못했습니다. 그래서 빠르면서도 신원을 증명할 수 있는 MAC(특히 해시를 이용한 HMAC)이 통신 표준으로 자리 잡았습니다.
- **가치**: 초고속, 저비용. VPN 터널(IPsec), 클라우드 API 호출(AWS API 등), IoT 디바이스 통신 등에서 데이터를 암호화하지 않더라도 **"명령어의 진위 여부와 출처"** 를 1초에 수만 번씩 빛의 속도로 검증해 내는 백그라운드 엔진입니다.

## 3. 어떻게 작동하는가? (Mechanism)
가장 대표적이고 표준인 **HMAC (Hash-based MAC)** 의 작동 방식입니다.

1. **사전 준비 (키 공유)**
   - 통신을 시작하기 전, 서버와 스마트폰 앱이 몰래 만나 똑같은 비밀키(Secret Key = `K1`)를 나눠 가집니다.
2. **송신자 (지문 생성 후 발송)**
   - 폰 앱이 서버에 `[결재 10만 원]`이라는 원본 메시지($M$)를 보냅니다.
   - 이때 메시지 옆에, **메시지 $M$과 비밀키 `K1`을 해시 믹서기에 같이 넣고 돌려 나온 64자리 글자(이게 HMAC!)** 를 꼬리표처럼 붙여서 보냅니다.
3. **해커의 개입 시도 (변조 불가)**
   - 해커가 중간에서 가로채 `[결재 100만 원]`으로 조작합니다.
   - 하지만 해커는 비밀키 `K1`을 모르기 때문에 조작된 내용에 맞는 올바른 HMAC 꼬리표를 만들 수 없습니다. 대충 아무 글자나 붙여서 서버로 보냅니다.
4. **수신자의 검증 (서버의 판독)**
   - 서버가 조작된 `[결재 100만 원]` 메시지를 받았습니다. 
   - 서버도 자기가 가진 비밀키 `K1`과 방금 받은 메시지를 믹서기에 갈아봅니다. 자기가 만든 꼬리표와 해커가 대충 붙인 꼬리표 모양이 완전히 다릅니다! "위조/사칭이다!" 라며 거래를 파기합니다.

## 4. 실전 활용 및 예시 (Real-world Application)
- **구체적 사례 (AWS API 호출)**: 
  - 개발자가 AWS 클라우드에 "서버 1대 만들어줘!"라고 API 명령(HTTP)을 쏠 때, 중간에 해커가 명령을 변조하는 것을 막기 위해 AWS는 **AWS Signature Version 4**라는 방식을 씁니다. 이게 바로 전형적인 HMAC입니다. 내 계정의 Secret Access Key(비밀키)를 이용해 API 요청 내용 전체를 HMAC으로 갈아서 꼬리표를 붙여 던지면, AWS 서버가 확인 후 실행해 줍니다.
- **주의점 및 흔한 오해**: 
  - MAC/HMAC은 내용을 숨기는 '암호화'가 아닙니다! 편지 내용은 `[결재 10만 원]` 평문으로 그대로 날아갑니다(기밀성 X). 오직 **"이 편지를 보낸 사람이 내 친구(키 소유자)가 맞고, 편지 내용이 훼손되지 않았다"** 는 무결성과 인증 2가지만 보장합니다.

## 5. 핵심 비교 및 연결 개념 (Relation)
| 기능 / 기술 | Hash (해시) | MAC (HMAC) | 디지털 서명 (전자 서명) |
|---|---|---|---|
| **사용하는 키** | 없음 (Keyless) | **대칭키** (서로 같은 비밀키) | **비대칭키** (서명=개인키, 검증=공개키) |
| **보장성** | 무결성 | 무결성 + 인증 | 무결성 + 인증 + **부인 방지(핵심)** |
| **속도** | 초고속 | 초고속 | 느림 |
| **단점 (한계)** | 해커가 지문을 바꿔치기 가능 | 키를 둘이 공유하므로 "내가 안 보냈어"라고 오리발(부인) 내밀면 답이 없음 | 속도가 느림 |

# ✍️ 단답형 / 서술형 시험장 출격 준비

### Ⅰ. 핵심 인사이트
- **본질**: 데이터(Payload)와 송수신자 양방향 간에 사전에 공유된 비밀키(Shared Secret Key)를 입력값으로 받아, 암호학적 알고리즘(해시 또는 블록 암호)을 통해 고정된 길이의 인증 코드(Tag)를 생성하는 메시지 검증 아키텍처.
- **가치**: 단순 해시 함수의 한계점(해커에 의한 메시지와 해시값의 동시 변조 공격)을 방어. 공개키 기반의 전자 서명 대비 연산 처리 속도가 압도적으로 빨라, IPsec/SSL 통신, 라우팅 프로토콜(OSPF/BGP), API 인증 등에서 초당 수만 건의 **데이터 무결성(Integrity)** 과 **송신자 출처 인증(Authentication)** 을 동시 보장하는 통신 레이어의 핵심 무기임.
- **판단 포인트**: MAC은 대칭키를 활용하므로, 송신자와 수신자가 동일한 키를 가집니다. 따라서 송신자가 "내가 그 메시지(MAC)를 생성하지 않았다"라고 발뺌할 경우, 수신자도 동일한 키를 가지고 있어 수신자가 자작극을 벌였을 가능성을 수학적으로 배제할 수 없습니다. 즉, MAC은 **부인 방지(Non-repudiation) 기능은 절대 제공하지 못함**을 반드시 이해해야 합니다.

### Ⅱ. MAC의 생성 및 검증 메커니즘 아키텍처
기밀성(Encryption) 알고리즘과 독립적으로 동작하며, 통상적으로 메시지 꼬리에 덧붙여(Append) 전송됨.
1. **송신자 (Sender 측)**
   - 공유 비밀키($K$)와 평문 메시지($M$)를 MAC 생성 알고리즘에 통과시킴 $\rightarrow$ $MAC(K, M) = Tag(꼬리표)$ 생성.
   - 원본 메시지 $M$과 $Tag$를 수신자에게 전송함.
2. **수신자 (Receiver 측)**
   - 수신한 메시지 $M'$을 자신이 이미 가지고 있던 동일한 비밀키 $K$와 함께 MAC 알고리즘에 넣어 직접 계산 $\rightarrow$ $New Tag$ 생성.
   - 전송받은 $Tag$와 자신이 직접 돌려본 $New Tag$를 비교함. 일치하면 (1) 데이터 변조가 없었고 (무결성), (2) 나침반(키)을 가진 정당한 송신자가 보냈음(인증)을 확증함.

### Ⅲ. MAC의 대표적 구현 알고리즘 (HMAC vs CBC-MAC)
기반이 되는 수학적 엔진에 따라 분류.
- **HMAC (Hash-based MAC) ★업계 절대 표준**:
  - SHA-256 같은 단방향 해시 알고리즘을 내부 엔진으로 사용함.
  - 구조: `Hash( Key XOR opad, Hash( Key XOR ipad, Message ) )`. 단순히 `Hash(Key+Message)`로 만들면 취약점(길이 확장 공격)이 발생하므로, 키를 두 번의 패딩(ipad, opad)과 이중 해싱으로 뒤섞어 가장 완벽한 방어력을 갖춤. (IPsec, TLS, JWT 서명에 주로 쓰임).
- **CBC-MAC (Cipher Block Chaining MAC) / CMAC**:
  - 해시 함수 대신 AES 같은 대칭키 블록 암호화 알고리즘의 CBC 모드를 응용함. 메시지를 블록 단위로 암호화하며 체이닝(Chaining)해 나가다가, 제일 마지막 블록의 결과값만을 인증 태그(MAC)로 뽑아내어 전송함. (리소스를 극도로 아껴야 하는 IoT/임베디드 장비에서 선호).

### Ⅳ. 재전송 공격(Replay Attack) 위협과 통제 보완
- **MAC의 아키텍처적 한계**:
  - MAC 자체는 "과거에 해커가 도청해서 저장해 둔 정상적인 $M$과 $Tag$ 묶음"을 다음날 그대로 복사해서 다시 쏘는 **재전송 공격(Replay Attack)** 을 방어하지 못함. (예: 어제 한 번 쓴 "10만 원 송금 MAC 묶음"을 오늘 해커가 그대로 복사해서 서버에 쏘면 통과됨).
- **아키텍처 보완 설계**:
  - 이를 막기 위해 페이로드(Payload) 안에 반드시 1회성 순서 번호(Sequence Number), 전송 시간(Timestamp), 또는 난수(Nonce)를 포함시킨 후 그 전체를 HMAC으로 묶어야 함. (서버는 중복된 타임스탬프를 거부함).

### Ⅴ. 결론 및 실무적 판단 포인트
- 인프라 및 API 백엔드 설계 시, 두 서버 간의 트래픽을 안전하게 연동하기 위해 무거운 비대칭키(전자서명/RSA)를 API 호출마다 걸어버리면 서버 CPU가 병목(Bottleneck)으로 터져버립니다. 신뢰된 서버 구간(예: 마이크로서비스 환경 B2B 연동)에서는 사전 교환된 API Key를 기반으로 **HMAC-SHA256 해더 서명** 아키텍처를 도입하여 레이턴시(Latency)를 최소화하면서도 완벽한 무결성과 신원 인증을 달성하는 것이 정석입니다.

### 💡 문제 유형별 목차 전환 포인트
- **[암호학적 해시 함수의 취약점과 메시지 인증(MAC)의 발전 메커니즘]**: Ⅰ번과 Ⅱ번 동작 메커니즘을 중심으로 서술하여, 비밀키($K$)의 존재가 해커의 '중간자 해시값 변조 공격'을 어떻게 원천적으로 차단(송신자 인증)하는지 증명.
- **[데이터 무결성 및 인증 보장 기술 비교 (MAC vs 전자 서명)]**: Ⅴ번의 실무 활용 포인트를 참고하여, 두 기술의 공통점(무결성/인증 보장)을 짚되, 대칭키 구조(MAC)의 한계인 '부인 방지 불가'와 이를 해소하는 공개키(전자서명)의 트레이드오프(성능 vs 신뢰 구조)를 명확히 대비 서술.
