## Ⅰ. 개요
- **정의**: 공유 비밀키와 해시 함수를 결합하여 메시지의 무결성과 인증을 동시에 보장하는 코드
- **배경/필요성**: 해시 함수만으로는 메시지 변조 여부를 확인할 수 있으나 송신자 인증이 불가능하여 키 기반 인증이 필요함
- **비유**: 편지(메시지)에 인감(비밀키)을 찍어 보내면, 받는 사람이 같은 인감으로 진위를 확인하는 방식

| 출제 의도 | 반드시 짚을 핵심 | 감점 회피 포인트 |
|:---|:---|:---|
| MAC과 해시의 차이 이해 | 비밀키 포함 여부가 핵심 차이 | HMAC은 MAC의 구현 방식 중 하나임 |

> 요약: HMAC은 비밀키+해시 함수로 무결성과 송신자 인증을 동시에 제공하는 메커니즘임

## Ⅱ. 구성요소
```text
[메시지 + 비밀키] --> [HMAC 함수] --> [MAC 태그]
                         |
              H(K xor opad | H(K xor ipad | M))
```

| 구성요소 | 설명 | 비유 |
|:---|:---|:---|
| 비밀키(K) | 송수신자가 공유하는 대칭 비밀키 | 공용 인감 |
| 내부 패딩(ipad) | 키와 XOR 연산하여 내부 해시 입력을 생성하는 상수 | 안쪽 봉인 |
| 외부 패딩(opad) | 내부 해시 결과와 키를 XOR하여 최종 해시를 생성하는 상수 | 바깥 봉인 |
| MAC 태그 | 최종 출력값으로 메시지와 함께 전송하여 검증에 사용함 | 봉인 확인 마크 |

> 요약: 이중 해시 구조(ipad/opad)로 키와 메시지를 결합하여 인증 태그를 생성함

## Ⅲ. 절차
```text
키 준비 --> 내부 해시 --> 외부 해시 --> MAC 태그 비교
```
- 1단계: 송수신자가 비밀키 K를 사전에 안전한 채널로 공유함
- 2단계: 송신자가 `K xor ipad`와 메시지를 결합하여 내부 해시를 계산함
- 3단계: `K xor opad`와 내부 해시 결과를 결합하여 외부 해시(MAC 태그)를 계산함
- 4단계: 수신자가 동일 과정으로 MAC 태그를 계산하고 수신 태그와 상수 시간 비교로 검증함

> 요약: 이중 해시로 태그를 생성하고 수신측에서 동일 계산 후 비교하여 인증하는 흐름임

## Ⅳ. 문제점
- 키 공유 문제: 대칭키 기반이므로 키 분배 채널의 안전성이 전제 조건임
- 부인 방지 불가: 송수신자가 동일 키를 공유하므로 어느 쪽이 생성했는지 증명이 불가함
- 타이밍 공격: MAC 비교 시 바이트 단위 조기 종료 구현이면 시간 차이로 태그를 추론 가능함

> 요약: 키 분배·부인 방지 불가·타이밍 공격이 HMAC의 구조적 한계임

## Ⅴ. 개선방안
1. 단기: MAC 비교 시 상수 시간 비교 함수를 사용하여 타이밍 공격을 방지함
2. 중기: 키 교환에 비대칭키(DH, ECDH)를 사용하여 대칭키 분배 위험을 해소함
3. 장기: 부인 방지가 필요한 경우 디지털 서명(098 참조)으로 전환하거나 병용함

> 요약: 상수시간 비교 → 비대칭 키교환 → 디지털 서명 병용으로 한계를 보완함

## Ⅵ. 전망
- 발전 방향: TLS·JWT·API 인증 등에서 HMAC-SHA256이 표준 인증 메커니즘으로 사용됨
- 기술사적 판단: 경량·고속 메시지 인증 수단으로서 디지털 서명과 상호 보완 관계를 유지함
- 기술사 제언: 용도별로 HMAC(대칭 인증)과 디지털 서명(부인 방지)을 적절히 선택하는 설계가 필요함
