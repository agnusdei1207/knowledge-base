## 미리 알고가기

- SQL 인젝션은 사용자 입력이 데이터가 아니라 SQL 명령 일부로 해석될 때 발생하는 공격임
- 핵심 원인은 입력값과 SQL 구문을 문자열로 섞어 만드는 설계에 있음
- 방어의 중심은 입력 필터보다 Prepared Statement처럼 코드와 데이터를 분리하는 방식임

## Ⅰ. 개요

- **정의/개념**: SQL 인젝션은 웹 입력값이나 API 파라미터가 SQL 질의문 구조를 바꿔 데이터베이스가 공격자 의도대로 조회, 수정, 삭제, 인증 우회 등을 수행하게 만드는 공격임
- **배경/필요성**: 업무 데이터와 개인정보가 데이터베이스에 집중돼 있고, 입력 처리 실수 하나가 직접 데이터 유출과 변조로 이어질 수 있어 웹 보안의 대표 공격으로 관리됨

## Ⅱ. 특징

- 입력값이 쿼리 구조에 영향을 주면 인증 우회와 대량 조회와 데이터 변조가 가능함
- 검색창, 로그인 폼뿐 아니라 쿠키, 헤더, JSON 본문, 저장 프로시저 매개변수도 공격 지점이 될 수 있음
- 단순 이스케이프만으로는 DB별 문법 차이와 우회 기법을 모두 막기 어려움
- 애플리케이션 수정과 함께 DB 권한 최소화와 오류 메시지 통제가 병행돼야 피해를 줄일 수 있음

## Ⅲ. 종류 및 비교

| 판단 기준 | Union/Error 기반 | Blind 기반 |
|:---|:---|:---|
| 정보 획득 방식 | 응답 결과나 오류 메시지로 바로 확인 | 참/거짓, 시간 지연 등 간접 반응으로 추론 |
| 공격 난이도 | 비교적 낮을 수 있음 | 시간이 오래 걸리고 정교함이 필요함 |
| 탐지 포인트 | 비정상 SQL 구문과 오류 응답 | 반복 요청 패턴과 응답 시간 이상 |
| 대응 공통점 | 둘 다 파라미터 바인딩과 권한 통제가 핵심임 | 둘 다 파라미터 바인딩과 권한 통제가 핵심임 |

## Ⅳ. 구성요소 및 구조

| 구성요소 | 설명 |
|:---|:---|
| 입력 지점 | 폼, URL, API 파라미터, 쿠키 등 외부 입력이 들어오는 위치임 |
| 질의 생성 로직 | 문자열 결합, 동적 SQL, 저장 프로시저 호출이 이뤄지는 코드임 |
| DB 실행 계층 | 생성된 SQL을 실제로 실행하는 드라이버와 DB 계정임 |
| 방어 통제 | 파라미터 바인딩, 입력 검증, 최소 권한, 오류 통제, 로깅이 포함됨 |

```text
외부 입력 -> 질의 생성 -> DB 실행 -> 결과 반환
          \-> 코드/데이터 분리 실패 시 SQLi 발생
```

## Ⅴ. 원리 및 절차 흐름도

```text
입력 수신 -> 동적 쿼리 생성 -> SQL 구조 변조 -> DB 실행 -> 결과 노출/변조 -> 로그 분석/수정
```

1. **입력 수신**: 사용자가 파라미터나 본문으로 값을 보냄
2. **동적 쿼리 생성**: 애플리케이션이 문자열 결합으로 SQL을 만듦
3. **구조 변조**: 공격 문자열이 조건식이나 명령 흐름을 바꿈
4. **DB 실행**: DB가 조작된 질의를 실행함
5. **탐지와 수정**: 비정상 요청과 DB 로그를 분석해 원인을 제거함

## Ⅵ. 실무 적용 및 유의점

1. 신규 개발과 유지보수 모두 SQL 생성 구간에서 파라미터 바인딩을 강제하고 동적 정렬·검색 조건은 허용 목록으로 제한해야 하며 문자열 결합 쿼리 제거 여부와 침투 테스트 재현 실패로 확인함
2. 레거시 시스템은 즉시 전면 수정이 어렵다면 DB 계정 권한 축소와 오류 메시지 차단과 WAF 탐지를 함께 적용해야 하며 고위험 쿼리 로그 감소와 관리자 기능 우회 재현 실패와 재점검 해소율로 확인함

## Ⅶ. 결론

- SQL 인젝션은 입력 검증 실수의 문제가 아니라 SQL 코드와 데이터를 섞는 설계 문제이므로 질의 생성 방식 자체를 바꾸는 것이 핵심임
