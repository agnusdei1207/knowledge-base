# 📖 【암기용】 개념 완전 이해

> 목적: 클라우드 보안 공유 책임 모델을 처음 보는 사람도 CSP와 고객의 책임 경계를 이해하게 만든다. 시험 답안 양식이 아니라, 이해를 위한 친절한 설명이다.

## 한눈에
- **개요**: 클라우드 보안 책임을 CSP 책임과 고객 책임으로 나누는 운영 기준임
- **왜 필요한가**: IaaS, PaaS, SaaS마다 보호해야 할 계층이 다르다. 책임 경계를 모르면 "클라우드 제공자가 해준다"는 오해로 IAM, 데이터 암호화, 로그 수집이 빠진다.
- **핵심 직관**: 아파트 관리사무소가 엘리베이터와 전기를 관리해도, 세대 현관 비밀번호와 귀중품 관리는 입주자 책임인 구조임

## 깊이 이해
- **배경·문제의식**: 온프레미스에서는 조직이 물리, 네트워크, OS, 애플리케이션, 데이터를 모두 책임졌다. 클라우드에서는 물리 인프라 일부가 CSP로 이동하지만 계정, 데이터, 구성, 접근 정책은 고객이 계속 책임진다.
- **작동 원리**: CSP는 데이터센터, 하이퍼바이저, 관리형 서비스 기반을 보호한다. 고객은 IAM, 네트워크 보안그룹, 암호화 키, 로그, 규제 설정을 구성한다. 서비스 모델이 SaaS로 갈수록 CSP 책임이 늘고, IaaS로 갈수록 고객 책임이 늘어난다.
- **비유**: 렌터카 업체가 차량 정비와 보험을 제공해도 운전자의 속도, 탑승자, 적재물 관리는 운전자 책임인 것과 같음
- **구체 예시**: IaaS VM에서 CSP는 호스트 하드웨어와 가상화 계층을 담당하고, 고객은 OS 패치 30일 이내, 보안그룹 0.0.0.0/0 관리 포트 0개, KMS 암호화 키 회전 365일 이하를 관리함
- **흔한 오해·주의점**: 공유 책임은 책임 전가 문서가 아니다. 사고 조사 시 CSP 로그, 고객 CloudTrail, IAM 변경 이력, 키 사용 로그가 함께 있어야 원인과 책임 경계가 판정됨

## 연결 개념
- CSPM — 고객 책임 영역의 설정 오류를 지속 점검
- IAM/CIEM — 과도 권한과 특권 계정 통제
- CSAP, ISO 27017 — 클라우드 보안 통제와 인증 기준

# 📝 【답안용】 시험 답안 템플릿

> 목적: 시험장에서 25분에 그대로 쓰는 답안 양식. 작성방식(추상표현 금지·수치·도식·문제유형 전환)을 엄격히 지킨다.
> 핵심: 공유 책임 모델은 서비스 모델별 책임 경계와 고객 통제 항목을 연결해 사고 책임·감사 대응·운영 지표까지 제시해야 한다.

## 핵심 인사이트 (3줄 요약)

> 1. **본질**: 클라우드 보안 공유 책임 모델은 보안 책임을 CSP의 "of the cloud"와 고객의 "in the cloud"로 분리하는 기준이다.
> 2. **가치**: 책임 경계를 명확히 하여 IAM, 데이터 암호화, 네트워크 설정, 로그 보존 같은 고객 통제 누락을 줄인다.
> 3. **판단 포인트**: IaaS, PaaS, SaaS별 책임 이동과 규제·감사 증적 확보 방안을 함께 써야 한다.

## 출제 의도 및 답안 포인트

| 출제 의도 | 반드시 짚을 핵심 | 감점 회피 포인트 |
|:---|:---|:---|
| 클라우드 책임 경계 이해 확인 | CSP 책임, 고객 책임, 공동 책임, 서비스 모델별 차이 | CSP가 모든 보안을 담당한다고 서술 |
| 보안 통제 설계 역량 확인 | IAM, 암호화, 로그, 네트워크, 취약점 관리 | IaaS와 SaaS 책임 범위를 동일하게 작성 |
| 감사·사고 대응 판단 확인 | 증적 보존, SLA, 책임 매트릭스, RACI | 사고 시 책임 전가만 쓰고 통제 지표 누락 |

> 요약: 이 문제는 클라우드 전환 시 책임이 사라지는 것이 아니라 계층별로 재배치됨을 설명해야 한다.

## Ⅰ. 개요 및 필요성

공유 책임 모델은 클라우드 보안 책임 분담 기준이다.
클라우드는 물리 인프라를 CSP가 운영하지만 계정, 데이터, 구성, 애플리케이션 보안은 고객 통제가 남는다.
서비스 모델별 책임 경계를 문서화하지 않으면 관리 포트 노출, KMS 미적용, 로그 미보존 같은 고객 영역 사고가 발생함.

---

## Ⅱ. 구조 및 구성요소

```text
Cloud Service Model -> Responsibility Matrix -> Control Owner
  / CSP: Facility, Hardware, Hypervisor, Managed Service Base
  / Customer: Data, Identity, Configuration, Application, Logging
Control Owner -> Evidence -> Audit/Incident Response
```

| 구성요소 | 역할 | 특이사항 |
|:---|:---|:---|
| CSP 책임 | 물리센터, 하드웨어, 네트워크 기반, 가상화 계층 보호 | SOC 2, ISO 27001, CSA STAR 증적 활용 |
| 고객 책임 | 데이터 분류, IAM, 암호화, 보안그룹, 로그 설정 | 고객 계정 설정 오류가 주요 사고 원인 |
| 공동 책임 | 패치, 백업, 키 관리, 장애 대응 절차 | 관리형 서비스별 세부 범위 확인 필요 |
| 책임 매트릭스 | 서비스별 Owner, RACI, 감사 증적 정의 | IaaS/PaaS/SaaS별 책임 이동 표시 |
| 운영 증적 | 로그, 정책 변경, 키 사용, 접근 승인 이력 | 보존 1년 이상 또는 규제 기준 적용 |

> 요약: 공유 책임 모델은 CSP·고객·공동 책임을 매트릭스로 정의하고 통제 Owner와 증적을 연결한다.

---

## Ⅲ. 동작원리 및 흐름도

```text
서비스 식별 -> IaaS/PaaS/SaaS 분류 -> 책임 경계 매핑
-> 통제 Owner 지정 -> 로그/정책/키 증적 수집
-> 정기 점검 -> 감사/사고 대응
```

| 단계 | 처리 내용 | 검증 기준 |
|:---:|:---|:---|
| 1 | 클라우드 서비스와 데이터 등급 식별 | CMDB 등록률 100%, 데이터 등급 태깅 |
| 2 | IaaS, PaaS, SaaS 모델별 책임 범위 분류 | 책임 매트릭스 최신화 주기 분기 1회 |
| 3 | IAM, 암호화, 로그, 네트워크 통제 Owner 지정 | RACI 누락 항목 0건 |
| 4 | CSP 증적과 고객 로그를 통합 보관 | CloudTrail, Activity Log, KMS 로그 1년 이상 |
| 5 | 사고·감사 시 책임 경계와 통제 이력 확인 | 조사 착수 4시간 이내 증적 제출 |

> 요약: 공유 책임은 서비스 분류, 통제 Owner 지정, 증적 수집, 정기 점검 순서로 운영된다.

## Ⅳ. 특징

| 구분 | 온프레미스 | 클라우드 공유 책임 | 수치·판단 포인트 |
|:---|:---|:---|:---|
| 물리 보안 | 고객 직접 책임 | CSP 책임 | CSP 인증서와 감사보고서 확인 |
| OS·미들웨어 | 고객 직접 관리 | IaaS는 고객, PaaS는 CSP 비중 증가 | 패치 30일 이내, 예외 승인 |
| 데이터 보호 | 고객 직접 책임 | 고객 책임 유지 | KMS 암호화 100%, 키 회전 365일 |
| 접근 통제 | AD·방화벽 중심 | IAM·보안그룹·SaaS 권한 중심 | MFA 98% 이상, 관리 포트 공개 0건 |

> 요약: 클라우드는 물리 책임을 CSP가 맡지만 데이터와 권한 책임은 고객에게 남으므로 서비스 모델별 통제가 필요하다.

## Ⅴ. 심화 비교 및 적용 판단

| 비교 축 | 기존/대안 | 본 키워드 | 선택 기준 |
|:---|:---|:---|:---|
| 구조 | 내부 IT 전담 책임 | CSP·고객·공동 책임 분리 | 멀티클라우드 2개 이상, SaaS 확대 시 필수 |
| 비용/운영 | 장비 보안 투자 중심 | 통제 자동화, 로그 보존, 감사 증적 관리 | CSPM, SIEM, KMS 연계 가능성 |
| 위험 | 책임 경계 단순 | 설정 오류와 과도 권한이 고객 책임 | 공개 스토리지, 키 미적용, MFA 누락 점검 |

> 요약: 클라우드 책임 판단은 서비스 유형보다 실제 통제 Owner와 증적 확보 가능성을 기준으로 해야 한다.

| 리스크 | 원인 | 대응 방안 | 확인 지표 |
|:---|:---|:---|:---|
| 책임 공백 | 서비스별 Owner 미지정 | RACI 매트릭스, 계약 SLA, 보안 운영 절차 명시 | 미지정 통제 0건 |
| 설정 오류 | 고객 콘솔·IaC 변경 검토 부재 | CSPM 정책, IaC 스캔, 변경 승인 | Critical misconfig 24시간 이내 조치 |
| 증적 부족 | 로그 비활성화, 보존기간 누락 | 조직 단위 로그 강제, WORM 저장소 | 로그 수집률 100%, 보존 1년 이상 |

> 요약: 공유 책임의 주요 위험은 책임 공백, 설정 오류, 증적 부족이며 자동 점검과 RACI로 통제한다.

| 점검 항목 | 목표 기준 | 측정 방법 |
|:---|:---|:---|
| 책임 매핑 | 클라우드 서비스 100% RACI 지정 | CMDB, 계약서, 보안정책 대조 |
| 고객 통제 | MFA 98% 이상, 공개 관리 포트 0건 | IAM 리포트, CSPM |
| 감사 증적 | 로그 보존 1년 이상, 키 사용 이력 100% | SIEM, KMS, CSP 감사보고서 |

> 요약: 도입 성숙도는 책임 매핑률, 고객 통제 적용률, 감사 증적 확보율로 판단한다.

## Ⅵ. 실무 적용 및 결론

**적용 방안 3개:**
1. IaaS, PaaS, SaaS별 책임 매트릭스를 작성하고 서비스 Owner, 보안 Owner, CSP 지원 범위를 RACI로 분기 1회 갱신함
2. 고객 책임 영역에 MFA 98% 이상, KMS 암호화 100%, 공개 관리 포트 0건, 로그 보존 1년 이상 기준을 적용함
3. CSPM, SIEM, KMS, 티켓 시스템을 연결해 Critical 설정 오류는 24시간 이내 조치하고 예외는 CISO 승인으로 관리함

**결론 (2줄):**
- 기술사 판단: IaaS는 고객 통제 범위가 넓고 SaaS는 데이터·계정 통제가 남으므로 서비스 모델별 책임 매트릭스가 선행되어야 함
- 향후 방향: 공유 책임은 CSPM, CIEM, CNAPP와 결합해 계약 문서가 아니라 지속 점검 체계로 전환됨
