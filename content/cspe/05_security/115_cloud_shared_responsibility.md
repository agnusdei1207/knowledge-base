## 1. 한눈에 이해하기 (Core Intuition)
- **정의**: 클라우드 서비스(AWS, Azure, Google Cloud 등)를 이용할 때, **"어디서부터 어디까지는 클라우드 회사(CSP)가 보안을 책임지고, 어디서부터는 고객(나, 기업)이 스스로 책임져야 하는가"를 법적/기술적으로 명확하게 갈라놓은 가장 중요한 룰(Rule)이자 계약**입니다.
- **필요성**: 클라우드에 올린 회사 DB가 해킹당해 털렸습니다. 사장님이 화가 나서 AWS에 전화를 걸어 "너희 시스템이 털려서 우리 데이터 다 날아갔잖아! 배상해!"라고 따집니다. 하지만 AWS는 "저희 서버(기계)와 담벼락은 완벽히 멀쩡합니다. 고객님께서 데이터를 올리시곤 바보같이 누구나 접속할 수 있게 폴더 '전체 공개(Public)' 버튼을 눌러놓으셨잖아요. 그건 고객님 잘못입니다!"라며 반박합니다. 이런 피 터지는 책임 공방을 막기 위해 선을 그은 것입니다.
- **핵심 직관**: **"아파트 경비원과 내 집 현관문"**. 
  - **클라우드 제공자 (아파트 관리소)**: 아파트 건물 외벽이 무너지지 않게 튼튼하게 짓고, 1층 로비 출입문을 지키고, 엘리베이터 고장 안 나게 24시간 관리할(물리적/인프라 보안) '책임'이 있습니다.
  - **고객 (입주민, 나)**: 아파트가 아무리 튼튼해도, 내가 내 집(가상 서버) 현관문 비밀번호를 `1234`로 설정해놓거나 아예 문을 열어놓고 자서(설정 오류) 도둑이 들면? 그건 100% 입주민(나)의 '책임'입니다.

## 2. 왜 중요한가? (Background & Value)
- **등장 배경**: 클라우드로 시스템을 옮긴 기업들의 임원진 사이에서 "이제 보안도 AWS가 다 알아서 해주는 거니까 우리 보안팀 다 없애도 되지?"라는 엄청난 착각이 퍼졌습니다. 그 결과 클라우드 서버 설정 실수(Misconfiguration) 하나 때문에 수천만 명의 개인정보가 인터넷에 줄줄 새는 초대형 참사가 연일 발생했습니다. 이를 바로잡기 위해 가트너(Gartner)와 CSP들이 공동 책임 모델을 업계의 헌법으로 규정했습니다.
- **가치**: 보안 사고의 원인 규명 척도. 클라우드에서 발생하는 보안 침해 사고의 99%는 '클라우드 제공자(CSP)'의 인프라 취약점이 아니라, **'고객(Customer)'의 멍청한 설정 오류와 권한 남용**에서 발생한다는 뼈아픈 진실을 인지시키고 방어선을 재구축하게 합니다.

## 3. 어떻게 작동하는가? (Mechanism)
내가 어떤 종류의 클라우드(IaaS, PaaS, SaaS)를 빌려 쓰느냐에 따라 내 책임의 크기가 확확 바뀝니다.

1. **공통 원칙 (절대 불변)**
   - **클라우드 인프라 자체의 보안 (Security 'OF' the Cloud)**: 
     - AWS가 100% 책임. 
     - 하드웨어 칩, 데이터센터 물리적 출입 통제, 에어컨, 전력, 네트워크 케이블망.
   - **클라우드 안에서의 보안 (Security 'IN' the Cloud)**: 
     - 내가(고객) 100% 책임. 
     - 고객의 데이터베이스 내용물(고객 정보), 암호화 여부, 로그인 IAM(아이디/권한) 관리.
2. **IaaS (가상 서버, 컴퓨터 껍데기만 빌릴 때)**
   - 내(고객) 책임이 제일 **많음**. (아파트 뼈대만 빌리고 내가 다 인테리어).
   - OS(윈도우/리눅스) 설치, 보안 패치, 방화벽 설정(포트 열기) 모두 내가 해야 함.
3. **PaaS (데이터베이스, 플랫폼까지 다 세팅해서 빌려줄 때)**
   - 책임이 절반씩 나뉨. (풀옵션 오피스텔).
   - OS 패치나 DB 엔진 업그레이드 등 뼈대 관리는 AWS가 알아서 해줌. 나는 올라가는 내 소스코드(앱)와 데이터, 그리고 누가 접속할지 권한 설정만 잘하면 됨.
4. **SaaS (구글 드라이브, 마이크로소프트 365, 노션)**
   - 구글/MS가 거의 다 책임짐. (호텔 숙박).
   - 나는 딱 2가지만 책임지면 됨: "내 구글 아이디 안 털리게 관리하기(IAM)", "내 폴더 남들에게 공유 버튼 잘못 누르지 않기(Data 권한)".

## 4. 실전 활용 및 예시 (Real-world Application)
- **구체적 사례**: 
  - 2019년, 미국 금융사 '캐피탈 원(Capital One)'에서 1억 명의 고객 정보가 탈취되는 역사적 해킹이 터졌습니다. 해커는 AWS 클라우드 웹 방화벽의 빈틈을 파고들어 서버 안의 S3(데이터 저장소) 관리자 권한(IAM Role)을 훔쳐 모든 DB를 긁어갔습니다. 캐피탈 원은 AWS 탓을 하려 했지만, 재판부와 전문가들은 "AWS 인프라는 뚫린 적 없다. 캐피탈 원 개발자가 방화벽 설정을 잘못하고 권한을 과도하게 열어둔(Misconfiguration) **공동 책임 모델 위반(고객 책임)**"이라고 결론 내렸고, 캐피탈 원은 수천억 원의 벌금을 맞았습니다.
- **주의점 및 흔한 오해**: 
  - "클라우드 서비스가 백업도 다 알아서 해주죠?" $\rightarrow$ **아닙니다.** 랜섬웨어에 걸려 클라우드상의 데이터가 암호화되어 버리면, AWS는 복구해주지 않습니다(책임 밖). 주기적으로 다른 안전한 계정으로 **데이터 백업을 하는 것도 온전히 고객의 100% 책임(Data Accountability)** 입니다.

## 5. 핵심 비교 및 연결 개념 (Relation)
- **온프레미스 (전산실)**: 하드웨어(에어컨 고장)부터 앱까지 **100% 내가 똥 치우고 다 책임짐.**
- **클라우드 (공동 책임)**: 밑단의 하드웨어와 전기는 CSP(AWS/구글)가 100% 책임짐. 나는 그 위에 올리는 **'내 데이터'와 '내 암호'** 만 100% 집중해서 지키면 됨.

# ✍️ 단답형 / 서술형 시험장 출격 준비

### Ⅰ. 핵심 인사이트
- **본질**: 클라우드 서비스 사업자(CSP, Cloud Service Provider)와 클라우드 이용자(Customer/Tenant) 간의 보안 프레임워크이자 규제적 합의선(Demarcation Line). 인프라 스택 하단(물리적/가상화)의 보안은 CSP가 주도하고, 상위 스택(운영체제, 애플리케이션, 데이터)의 통제는 클라우드 서비스 모델(IaaS, PaaS, SaaS) 유형에 따라 고객에게 비례적으로 위임되는 **책임 분할(Responsibility Division) 아키텍처.**
- **가치**: "클라우드 도입 = 보안 위탁"이라는 C-Level의 치명적 인지 오류를 교정함. CSP는 물리적 컴플라이언스(SOC 2, ISO 27001 등) 통과를 보장하는 단단한 기초(Foundation)를 제공하지만, 그 위에서 일어나는 정보 유출, 랜섬웨어 감염, 권한 남용에 대한 **최종적인 거버넌스와 법적 책임(Accountability)은 무조건 데이터를 소유한 고객에게 귀속됨**을 명확히 함.
- **판단 포인트**: IT 감사인(Auditor)과 보안 아키텍트는 사고 발생 시 법적 배상 책임의 경계를 식별하기 위해 이 모델을 숙지해야 합니다. 가트너 예측에 따르면 2025년까지 발생하는 클라우드 보안 장애의 99%는 CSP의 시스템 결함이 아닌, 100% **고객의 설정 오류(Misconfiguration) 및 부적절한 IAM 정책(과다 권한)** 에 기인합니다.

### Ⅱ. 서비스 모델별(IaaS / PaaS / SaaS) 책임 경계선(Demarcation)의 이동
클라우드 스택이 위로 올라갈수록(SaaS 쪽으로 갈수록) CSP가 더 많은 보안 제어권을 가져가지만, '데이터'와 '접근 신원' 통제권은 끝까지 고객에게 남음.
1. **IaaS (Infrastructure as a Service, 예: AWS EC2, Azure VM)**
   - **CSP 책임**: 데이터센터 물리 보안, 전력/쿨링, 서버 하드웨어, 스토리지 디스크 포맷팅, 네트워크 스위치 장비, 하이퍼바이저(가상화 엔진) 펌웨어.
   - **고객 책임 (가장 무거움)**: 게스트 OS 보안 패치, 미들웨어/웹 서버 설정, 호스트 방화벽(Security Group) 및 라우팅 테이블(VPC) 설정, 애플리케이션 취약점(OWASP) 패치, IAM 계정 관리, 고객 데이터 암호화(KMS).
2. **PaaS (Platform as a Service, 예: AWS RDS, Heroku)**
   - **CSP 책임**: IaaS 책임 영역 + 게스트 OS 패치(DB 엔진 자동 업데이트 포함), 런타임 환경 구성.
   - **고객 책임 (중간)**: 자체 개발한 애플리케이션 코드(App Logic) 로직 취약점, 플랫폼에 연동되는 API 통신 암호화 설정, 데이터 및 IAM 계정 권한.
3. **SaaS (Software as a Service, 예: Google Workspace, Salesforce)**
   - **CSP 책임 (가장 무거움)**: 데이터센터부터 애플리케이션 소스코드, 방화벽, 백엔드 DB까지 전체 IT 인프라 스택 99% 통제.
   - **고객 책임 (핵심 고정)**: 1) **사용자 신원(IAM/SSO) 및 단말기(Endpoint) 보안 제어**, 2) **데이터 분류(Classification) 및 공유 권한(Public Link 통제)**, 3) 계정 하이재킹 방어(MFA 강제).

### Ⅲ. 절대 불변의 고객 책임 영역 (Security 'IN' the Cloud)
어떤 클라우드(IaaS/PaaS/SaaS)를 쓰든 CSP가 결코 터치하지(대신 해줄 수 없는) 않는 성역(Sanctuary).
- **데이터(Data) 자체에 대한 오너십과 책임**: 데이터의 민감도 분류, 데이터 백업 플랜 수립, 데이터 삭제 및 보존 주기 준수(개인정보보호법), 저장 데이터(At-rest) 및 전송 데이터(In-transit)의 **암호화 키(Key) 라이프사이클 관리**.
- **IAM (신원 및 접근 제어)**: 루트(Root) 계정 보호, MFA 활성화 적용, 최소 권한의 원칙(PoLP)에 기반한 접근 정책(Policy) 작성.

### Ⅳ. 책임 공유 모델 실패 시나리오와 대응 통제 (CSPM의 등장)
- **위협 시나리오 (클라우드 설정 오류, Misconfiguration)**:
  - AWS S3 버킷(Storage) 접근 권한을 실수로 `Public Read`(전 세계 누구나 다운로드 가능)로 설정하여 발생한 고객 정보 유출 (자주 발생하는 사고 패턴 1위).
  - 인터넷에서 누구나 접근할 수 있도록 22번 포트(SSH)를 '0.0.0.0/0'으로 활짝 열어둔 채 방치된 가상 서버.
- **아키텍처적 극복 (CSPM, Cloud Security Posture Management)**:
  - 수천 개의 클라우드 설정이 제대로 되어 있는지 사람이 눈으로 확인하는 것은 불가능함.
  - 보안팀은 CSPM(예: Prisma Cloud, AWS Security Hub) 솔루션을 도입하여 클라우드 API를 주기적으로 스캔, "공개 포트 열림", "S3 퍼블릭 공개됨", "MFA 미설정 계정" 등 설정 오류를 즉각 적발하여 자동 조치(Auto-remediation)하는 인프라 템플릿 감사(Audit) 파이프라인을 구축해야 함.

### Ⅴ. 결론 및 실무적 판단 포인트
- 인프라 보안 담당자는 조직이 멀티 클라우드(AWS + Azure) 전략을 취할 때 각 CSP마다 미세하게 다른 공동 책임 통제(Control) 매트릭스를 완벽히 매핑(Mapping)해야 합니다. 클라우드 보안 전략의 시작은 "AWS가 방어해 주는 항목 리스트"를 믿는 것이 아니라, 계약서(SLA)에 명시된 **"AWS가 뚫렸을 때 면책되는(우리가 덤터기를 쓰는) 고객 귀속 영역(Grey Area)"** 이 무엇인지 도출하여 자체적인 보안 솔루션(WAF, CSPM, CWPP) 3중 방어막을 설계하는 것입니다.

### 💡 문제 유형별 목차 전환 포인트
- **[클라우드 컴퓨팅 보안 위협 및 거버넌스(컴플라이언스) 확립 전략 묻는 유형]**: Ⅰ번 개념 정의 후, Ⅱ번(IaaS/PaaS/SaaS 책임 분할) 표를 활용하여 IT 아키텍처 스택 변화에 따른 보안 통제권(Control) 이양 범위를 명확히 서술.
- **[클라우드 설정 오류(Misconfiguration) 위협과 CSPM(클라우드 보안 형상 관리) 도입의 당위성]**: Ⅲ번(절대 불변의 고객 영역, 즉 IAM과 Data)을 방치했을 때 발생하는 Ⅳ번 침해 시나리오를 지적하고, 이를 통제하기 위한 자동화된 CSPM 검증 아키텍처로 답변 전개.
