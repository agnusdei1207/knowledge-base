## Ⅰ. 개요
| 항목 | 내용 |
|---|---|
| **정의** | OAuth 2.0은 리소스 소유자의 자격증명 노출 없이 제3자 앱에 제한된 접근 권한을 위임하는 인가 프레임워크이며, OIDC는 OAuth 위에 ID Token을 추가하여 인증 계층을 제공하는 표준임 |
| **배경/필요성** | 서비스 간 사용자 데이터 공유 시 패스워드를 직접 전달하는 위험을 제거하고, 표준화된 인증·인가 흐름이 필요함 |
| **출제 의도** | OAuth 2.0 Grant Type과 OIDC ID Token의 역할 차이를 이해하는지 평가함 |

## Ⅱ. 구성요소
```
+----------+     +----------+     +----------+
| 리소스   | --> | 인가서버  | --> | 클라이언트|
| 소유자   |     | (AuthZ)  |     | (3rd App)|
+----------+     +----------+     +----------+
```

| 구성요소 | 설명 | 비유 |
|---|---|---|
| 리소스 소유자 | 보호된 데이터의 주인으로, 접근 권한 위임에 동의함 | 집 주인 |
| 인가 서버 | 동의를 받아 Access Token·ID Token을 발급함 | 부동산 중개소 |
| 클라이언트 | Access Token으로 리소스 서버에 접근하는 제3자 애플리케이션임 | 집을 빌리는 세입자 |

> 요약: 리소스 소유자 동의 → 인가 서버 토큰 발급 → 클라이언트 리소스 접근으로 안전한 권한 위임을 수행함.

## Ⅲ. 절차
```
+------------+     +------------+
| 인가요청   | --> | 사용자동의  |
| (Redirect) |     | (Consent)  |
+------------+     +------------+
                        |
+------------+     +----+-------+
| 리소스접근  | <-- | 토큰발급  |
| (API호출)  |     | (Code교환)|
+------------+     +------------+
```

1. 인가 요청: 클라이언트가 사용자를 인가 서버의 동의 화면으로 리다이렉트함
2. 사용자 동의: 리소스 소유자가 요청된 스코프(권한 범위)에 동의함
3. Authorization Code 교환: 인가 서버가 Code를 발급하고, 클라이언트가 이를 Access Token으로 교환함
4. 리소스 접근: 클라이언트가 Access Token(+ OIDC 시 ID Token)으로 리소스 서버 API를 호출함

> 요약: 리다이렉트 → 동의 → Code 교환 → 토큰으로 API 접근하는 Authorization Code Grant 흐름임.

## Ⅳ. 문제점
- Redirect URI 미검증: 인가 서버가 Redirect URI를 정밀 검증하지 않으면 Code 탈취가 가능함
- Token 유출: Access Token이 URL·로그에 노출되면 세션 하이재킹이 발생함
- PKCE 미적용: SPA·모바일 앱에서 PKCE 없이 Authorization Code를 사용하면 가로채기 공격에 취약함

## Ⅴ. 개선방안
- (단기) 정확한 Redirect URI 매칭: 와일드카드 없이 정확한 URI만 허용하여 오픈 리다이렉트를 차단함
- (중기) PKCE 필수화: 모든 클라이언트에 PKCE(Proof Key for Code Exchange)를 강제 적용함
- (장기) DPoP 토큰 바인딩: Demonstration of Proof-of-Possession으로 토큰을 특정 키에 바인딩하여 도난 시 사용을 차단함

## Ⅵ. 전망
- OAuth 2.1 표준이 PKCE 필수·Implicit Grant 폐지를 확정하며, DPoP·RAR(Rich Authorization Requests)로 세밀한 권한 위임이 가능해질 전망임
