## 미리 알고가기

- OAuth 2.0은 사용자 비밀번호를 직접 넘기지 않고 제3자 애플리케이션에 제한된 권한을 위임하는 방식임
- OIDC는 OAuth 2.0 위에 로그인 확인용 `ID Token`을 더해 인증까지 처리하게 만든 계층임
- PKCE는 인가 코드 탈취를 막기 위해 코드 교환 시 추가 검증 값을 함께 쓰는 방식임
- 간단히 말해 OAuth는 권한 위임, OIDC는 로그인 확인까지 포함한 표준으로 보면 됨

## Ⅰ. 개요

- **정의/개념**: OAuth 2.0은 사용자 자원 접근 권한을 위임하고, OIDC는 그 위에 사용자 신원 확인을 표준화한 인증·인가 체계임
- **배경/필요성**: 서비스 간 연동이 늘면서 비밀번호 공유 방식은 보안과 사용자 통제 한계가 커짐. 권한 범위와 로그인 절차 표준화가 필요함

## Ⅱ. 특징

- 사용자 비밀번호를 제3자 애플리케이션에 직접 전달하지 않음
- 권한 범위와 만료 시간을 토큰으로 제한함
- OIDC는 로그인 정보와 사용자 기본 속성을 함께 표준화함
- 토큰 유출과 잘못된 리다이렉트 설정은 전체 흐름을 무력화함

## Ⅲ. 종류 및 비교

| 판단 기준 | OAuth 2.0 | OIDC |
|:---|:---|:---|
| 핵심 목적 | 권한 위임 | 인증 + 권한 위임 |
| 대표 토큰 | Access Token | Access Token + ID Token |
| 주 사용처 | API 접근 제어 | 로그인 연동과 사용자 프로필 확인 |
| 유의점 | 로그인 표준으로 단독 사용하면 의미가 불명확해질 수 있음 | ID Token 검증과 nonce 처리가 필요함 |

## Ⅳ. 구성요소 및 구조

| 구성요소 | 설명 |
|:---|:---|
| Resource Owner | 자신의 자원 접근을 승인하는 사용자임 |
| Client | 권한을 위임받아 API를 호출하는 애플리케이션임 |
| Authorization Server | 사용자 인증과 동의와 토큰 발급을 담당함 |
| Resource Server | 실제 보호 자원을 제공하고 토큰을 검증함 |
| Tokens | Access Token, Refresh Token, ID Token이 포함됨 |

```text
사용자 동의 -> 인가 서버 토큰 발급 -> 클라이언트 API 호출 -> 자원 서버 검증
```

## Ⅴ. 원리 및 절차 흐름도

```text
로그인 요청 -> 사용자 인증/동의 -> Authorization Code 발급 -> 토큰 교환 -> API 호출 -> 토큰 검증
```

1. **로그인 또는 권한 요청**: 클라이언트가 사용자를 인가 서버로 보냄
2. **사용자 인증과 동의**: 사용자가 로그인하고 요청 권한 범위를 승인함
3. **Authorization Code 발급**: 인가 서버가 클라이언트에 코드를 돌려줌
4. **토큰 교환**: 클라이언트가 코드를 Access Token과 필요 시 ID Token으로 바꿈
5. **API 호출과 검증**: 토큰으로 자원 서버를 호출하고 서버가 서명과 범위를 확인함

## Ⅵ. 실무 적용 및 유의점

1. 모바일 앱·SPA는 인가 코드와 PKCE를 기본 흐름으로 두고 리다이렉트 고정·짧은 토큰 수명·코드 가로채기 재현 여부로 확인함
2. 외부 파트너 API는 OIDC 사용 여부를 구분하고 ID Token 검증 정확도·권한 범위 최소화·Refresh Token 회전으로 확인함

## Ⅶ. 결론

- OAuth 2.0·OIDC는 비밀번호 공유 없이 권한과 로그인 정보를 표준화하므로 토큰 운영과 세부 검증 규칙까지 함께 설계해야 함
