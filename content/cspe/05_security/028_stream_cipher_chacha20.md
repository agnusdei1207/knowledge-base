# 📖 【암기용】 개념 완전 이해

> 목적: ChaCha20을 처음 봐도 완벽히 이해하게 만든다. 시험 답안 양식이 아니라, 이해를 위한 친절한 설명이다.

## 한눈에
- **개요**: 키·nonce·counter로 키스트림을 만들고 평문과 XOR하는 스트림 암호
- **왜 필요한가**: AES-GCM은 AES-NI가 있는 CPU에서 처리량이 크지만, 모바일·임베디드·소프트웨어 전용 환경에서는 ChaCha20-Poly1305가 일정한 연산 패턴과 256비트 키로 TLS 1.3에서 널리 사용됨.
- **핵심 직관**: 같은 비밀 키와 일회용 번호로 긴 난수 테이프를 만들고, 평문에 겹쳐 암호문을 만드는 방식임.

## 깊이 이해
- **배경·문제의식**: RC4는 편향 문제가 있어 TLS에서 폐기됨. ChaCha20은 Salsa20 계열의 ARX(Add-Rotate-Xor) 구조를 사용해 테이블 조회 없이 구현 가능함.
- **작동 원리**: 512비트 상태는 상수 128비트, 키 256비트, counter 32비트, nonce 96비트로 구성됨. 20라운드 quarter round 후 블록별 64바이트 키스트림을 생성함.
- **비유**: 금고 비밀번호(키), 주문번호(nonce), 페이지 번호(counter)로 매 페이지마다 다른 난수 필름을 만들어 문서에 덧씌우는 방식임.
- **구체 예시**: RFC 8439의 ChaCha20-Poly1305 AEAD는 96비트 nonce를 사용하며 같은 키에서 nonce 재사용 시 두 평문의 XOR 관계가 노출됨.
- **흔한 오해·주의점**: ChaCha20 단독은 기밀성만 제공함. 무결성·인증은 Poly1305 태그 128비트를 붙인 AEAD로 사용해야 함.

## 연결 개념
- Poly1305 - ChaCha20과 결합해 AEAD 인증 태그를 생성
- AEAD - 기밀성·무결성·추가 인증 데이터(AAD)를 함께 처리
- TLS 1.3 - ChaCha20-Poly1305를 표준 cipher suite로 지원

# 📝 【답안용】 시험 답안 템플릿

> 목적: 시험장에서 25분에 그대로 쓰는 답안 양식. 작성방식(추상표현 금지·수치·도식·문제유형 전환)을 엄격히 지킨다.
> 핵심: ChaCha20은 스트림 암호 원리보다 nonce 재사용 금지, counter 관리, Poly1305 AEAD 적용을 중심으로 답안을 구성한다.

## 핵심 인사이트 (3줄 요약)

> 1. **본질**: ChaCha20은 256비트 키와 96비트 nonce, 32비트 counter로 64바이트 키스트림 블록을 생성하는 ARX 기반 스트림 암호임.
> 2. **가치**: AES 가속기 없는 환경에서 테이블 조회 없는 constant-time 구현과 TLS 1.3 AEAD cipher suite 적용성이 있음.
> 3. **판단 포인트**: nonce 1회성, counter overflow 방지, Poly1305 128비트 tag 검증 실패 시 평문 폐기가 핵심임.

## 출제 의도 및 답안 포인트

| 출제 의도 | 반드시 짚을 핵심 | 감점 회피 포인트 |
|:---|:---|:---|
| 스트림 암호 구조 이해 확인 | 키스트림 생성, XOR, nonce/counter | 블록 암호 모드로 설명 |
| AEAD 적용 판단 확인 | ChaCha20 기밀성 + Poly1305 무결성 | ChaCha20 단독으로 인증 제공한다고 서술 |
| 운영 리스크 통제 확인 | nonce 재사용 금지, counter 한계, 태그 검증 | nonce를 IV처럼 재사용 가능하다고 처리 |

> 요약: ChaCha20 답안은 키스트림 원리와 AEAD 인증, nonce 운영 통제를 함께 제시해야 함.

## Ⅰ. 개요 및 필요성

- 개요: ARX 구조 스트림 암호
- 배경: AES 하드웨어 가속이 없는 모바일·임베디드 환경에서는 블록 암호 구현 방식과 부채널 통제 방식이 성능·보안 병목이 될 수 있음.
- 필요성: ChaCha20-Poly1305는 TLS 1.3, QUIC, WireGuard에서 AEAD로 사용되며 키스트림 XOR과 Poly1305 태그로 기밀성·무결성을 제공함.

---

## Ⅱ. 구조 및 구성요소

```text
256-bit Key + 96-bit Nonce + 32-bit Counter -> ChaCha20 Block Function -> Keystream
Plaintext + Keystream -> Ciphertext
AAD + Ciphertext -> Poly1305 -> 128-bit Tag
```

| 구성요소 | 역할 | 특이사항 |
|:---|:---|:---|
| 256비트 키 | 키스트림 생성의 비밀값 | 세션별 KDF로 파생 |
| 96비트 nonce | 메시지별 유일성 보장 | 같은 키에서 재사용 금지 |
| 32비트 counter | 64바이트 블록 순번 | 최대 약 256GiB 처리 한계 |
| Poly1305 tag | 무결성·인증 검증 | 128비트 tag, 실패 시 폐기 |

> 요약: ChaCha20-Poly1305는 키스트림 생성과 128비트 인증 태그를 결합한 AEAD 구조임.

---

## Ⅲ. 동작원리 및 흐름도

```text
세션 키 파생 -> nonce 생성 -> counter 초기화 -> 20라운드 block function
-> keystream XOR -> Poly1305 tag 생성 -> 수신 측 tag 검증 -> 평문 복호화
```

| 단계 | 처리 내용 | 검증 기준 |
|:---:|:---|:---|
| 1 | HKDF 등으로 256비트 세션 키 파생 | 키 재사용 범위 명시 |
| 2 | 메시지별 96비트 nonce 생성 | 동일 키 내 중복 0건 |
| 3 | counter별 64바이트 키스트림 생성 | counter overflow 차단 |
| 4 | 평문 XOR 및 Poly1305 tag 산출 | AAD 포함, tag 128비트 |
| 5 | 수신 측 tag 먼저 검증 후 복호화 | 실패 시 평문 반환 금지 |

> 요약: 복호화 전 인증 태그를 검증하고 nonce 중복을 0건으로 유지하는 것이 운영 핵심임.

## Ⅳ. 특징

| 구분 | AES-GCM | ChaCha20-Poly1305 | 수치·표준 포인트 |
|:---|:---|:---|:---|
| 구조 | 블록 암호 + GCM | 스트림 암호 + MAC | RFC 8439, TLS 1.3 |
| 연산 | AES-NI 활용 | ARX, 테이블 조회 없음 | 20라운드, 64바이트 블록 |
| 인증 | GHASH tag | Poly1305 tag | 128비트 tag |
| 운영 위험 | nonce 재사용 시 tag 위조 위험 | nonce 재사용 시 평문 관계 노출 | 96비트 nonce 중복 0건 |

> 요약: AES 가속기 유무와 nonce 운영 능력을 기준으로 AES-GCM과 ChaCha20-Poly1305를 선택함.

## Ⅴ. 심화 비교 및 적용 판단

| 구분 | 기존/대안 | 본 키워드 | 선택 기준 |
|:---|:---|:---|:---|
| 암호 방식 | RC4 스트림 암호 | ChaCha20 | RC4 금지, RFC 8439 준수 |
| 성능 환경 | AES-GCM + AES-NI | ChaCha20-Poly1305 | AES-NI 부재 모바일·IoT |
| 운영/위험 | nonce 관리 미흡 | nonce/counter 엄격 관리 | 중복 탐지 로그 100% |

> 요약: 소프트웨어 기반 단말과 TLS/QUIC 환경에서는 ChaCha20-Poly1305를 우선 후보로 검토함.

| 리스크 | 원인 | 대응 방안 | 확인 지표 |
|:---|:---|:---|:---|
| nonce 재사용 | 난수 품질 부족, 카운터 초기화 | 세션별 키, 단조 증가 nonce | 동일 키 nonce 중복 0건 |
| 무결성 누락 | ChaCha20 단독 사용 | Poly1305 AEAD 강제 | tag 검증 실패 평문 반환 0건 |
| counter 초과 | 대용량 메시지 단일 키 처리 | 메시지 분할, rekey | 키당 처리량 256GiB 미만 |

> 요약: ChaCha20 운영 위험은 알고리즘보다 nonce, tag, counter 관리 실패에서 발생함.

| 점검 항목 | 목표 기준 | 측정 방법 |
|:---|:---|:---|
| 기밀성 | 키 256비트, nonce 중복 0건 | 암호 로그, 중복 탐지 |
| 무결성 | Poly1305 tag 검증 100% | 실패 케이스 테스트 |
| 구현 검증 | RFC 8439 test vector 100% 통과 | CI Known Answer Test |

> 요약: 도입 후에는 nonce 중복, tag 검증, 표준 벡터 통과 여부를 필수 지표로 본다.

## Ⅵ. 실무 적용 및 결론

**적용 방안 3개 (필수 — 단계별 또는 항목별):**
1. AEAD 강제: ChaCha20 단독 사용을 금지하고 RFC 8439 ChaCha20-Poly1305를 TLS 1.3·QUIC 설정에 적용함.
2. nonce 정책: 세션 키별 96비트 nonce 중복 0건, 프로세스 재시작 시 카운터 복구 또는 rekey 절차를 둠.
3. 검증 자동화: RFC 8439 test vector, tag 실패 테스트, counter overflow 테스트를 CI에 포함함.

**결론 (2줄):**
- 기술사 판단: AES-NI 서버는 AES-GCM, 모바일·임베디드·소프트웨어 전용 환경은 ChaCha20-Poly1305를 선택함.
- 향후 방향: QUIC·VPN·메신저에서 AEAD 기본값으로 유지되며 nonce 관리 자동화와 키 수명 통제가 운영 핵심임.
