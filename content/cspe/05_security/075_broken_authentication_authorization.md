## 미리 알고가기

- 인증은 사용자가 누구인지 확인하는 단계이고, 권한 부여는 그 사용자가 무엇을 할 수 있는지 정하는 단계임
- 인증이 강해도 서버 측 권한 검증이 약하면 타 사용자 데이터 접근이나 관리자 기능 호출이 가능함
- 웹 서비스에서는 비밀번호 정책보다 세션 관리와 객체 단위 권한 검사가 실제 사고를 더 자주 좌우함

## Ⅰ. 개요

- **정의/개념**: 인증·권한 결함은 로그인, 세션, 토큰, 역할 검증, 객체 접근 통제 로직의 오류로 인해 비인가 사용자가 계정을 탈취하거나 허용되지 않은 기능과 데이터에 접근하게 되는 취약점 범주임
- **배경/필요성**: 웹과 API 서비스가 세분화되면서 인증 흐름과 권한 검사 지점이 늘어났고, 한 곳의 누락이 계정 탈취와 수평·수직 권한 상승으로 이어져 별도 핵심 주제로 관리됨

## Ⅱ. 특징

- 약한 비밀번호 정책, 세션 고정, 토큰 검증 누락은 인증 결함에 해당함
- IDOR, 서버 측 역할 검증 누락, 관리자 API 노출은 권한 결함에 해당함
- 프런트엔드 숨김 처리만으로는 권한 통제가 되지 않으며 서버 측 검사로 끝나야 함
- 인증과 권한은 분리된 단계지만 실제 사고에서는 함께 연쇄적으로 악용되는 경우가 많음

## Ⅲ. 종류 및 비교

| 판단 기준 | 인증 결함 | 권한 결함 |
|:---|:---|:---|
| 문제 지점 | 로그인, 세션, 토큰 발급·검증 | 리소스 접근과 기능 실행 허용 기준 |
| 대표 사례 | 크리덴셜 스터핑, 세션 탈취, MFA 미적용 | IDOR, 관리자 API 우회, 역할 상승 |
| 직접 피해 | 계정 장악 | 타 사용자 데이터 열람, 관리자 기능 실행 |
| 핵심 대응 | MFA, 세션 보호, 비밀번호·토큰 정책 | 서버 측 권한 검증, 기본 거부, 객체 단위 검사 |

## Ⅳ. 구성요소 및 구조

| 구성요소 | 설명 |
|:---|:---|
| 신원 확인 | 비밀번호, MFA, 토큰 검증 등 사용자 확인 단계임 |
| 세션/토큰 관리 | 로그인 이후 상태 유지와 만료와 회전 정책을 다룸 |
| 권한 정책 | 역할, 자원, 행위별 허용 기준을 정의함 |
| 서버 측 검증 | 모든 요청에서 실제 접근 가능 여부를 검사함 |

```text
신원 확인 -> 세션/토큰 발급 -> 요청 수신 -> 서버 측 권한 검증 -> 리소스 접근 허용/거부
```

## Ⅴ. 원리 및 절차 흐름도

```text
인증 우회 또는 세션 탈취 -> 요청 전송 -> 권한 검증 누락/오류 -> 비인가 리소스 접근 -> 탐지/차단
```

1. **인증 우회 또는 세션 탈취**: 공격자가 계정이나 세션을 확보함
2. **요청 전송**: 타 사용자 객체 ID나 관리자 기능 경로를 호출함
3. **검증 오류 발생**: 서버가 역할이나 소유권을 제대로 검사하지 않음
4. **비인가 접근 성립**: 데이터 조회, 수정, 삭제, 권한 상승이 발생함
5. **수정과 재검증**: 세션 정책과 권한 검사 로직을 보완하고 다시 점검함

## Ⅵ. 실무 적용 및 유의점

1. 고객 정보와 관리자 기능을 제공하는 웹·API 서비스는 인증 강화와 별개로 모든 객체 접근에 서버 측 소유권 검사를 넣어야 하며 ID 변경 재현 실패와 관리자 기능 직접 호출 차단과 세션 회전 정책 적용 여부로 확인함
2. 마이크로서비스와 모바일 API 환경은 토큰 검증과 권한 판단이 서비스마다 달라지기 쉬우므로 공통 미들웨어나 정책 엔진으로 일관화해야 하며 엔드포인트별 권한 매트릭스 완성도와 회귀 테스트 통과와 미인가 접근 로그 감소로 확인함

## Ⅶ. 결론

- 인증·권한 결함은 로그인 성공 여부보다 서버가 요청 주체와 대상 자원의 관계를 끝까지 검증하느냐의 문제이므로 세션 관리와 객체 단위 권한 검사를 함께 강화해야 함
