# 📖 【암기용】 개념 완전 이해

> 목적: 인증·권한 결함을 처음 봐도 완벽히 이해하게 만든다. 시험 답안 양식이 아니라, 이해를 위한 친절한 설명이다.

## 한눈에
- **개요**: 사용자가 누구인지 확인하거나 무엇을 할 수 있는지 통제하는 경계가 깨진 상태
- **왜 필요한가**: 로그인은 인증이고, 특정 주문·문서·관리 기능 접근 허용은 권한이다. 둘 중 하나라도 빠지면 계정 탈취, IDOR, 관리자 기능 오남용이 발생한다.
- **핵심 직관**: 신분증 확인과 출입권 확인은 다르며, 로그인 성공이 모든 문서 접근 허가를 의미하지 않는다.

## 깊이 이해
- **배경·문제의식**: 웹 서비스는 세션, JWT, OAuth, MFA, RBAC/ABAC를 조합한다. 세션 만료, 토큰 검증, 객체 단위 권한, 관리자 기능 분리가 빠지면 사용자는 자기 권한을 넘어 다른 객체나 기능에 접근한다.
- **작동 원리**: Broken Authentication은 약한 비밀번호, 세션 고정, 토큰 검증 누락, MFA 부재에서 발생한다. Broken Authorization은 URL이나 객체 ID 변경으로 타인 데이터에 접근하는 IDOR, 기능 수준 권한 검사 누락, 테넌트 경계 오류에서 발생한다.
- **비유**: 건물 입구에서 신분증만 확인하고 각 층·방의 출입권을 확인하지 않으면, 방문자가 회의실과 금고실을 모두 들어갈 수 있는 상황임.
- **구체 예시**: `/orders/1001`을 `/orders/1002`로 바꿨을 때 서버가 소유자 검사를 하지 않으면 다른 사용자의 주문 정보가 노출된다.
- **흔한 오해·주의점**: 화면의 버튼을 숨기는 것은 권한 통제가 아니다. 서버 API와 데이터 조회 쿼리에서 사용자, 역할, 객체, 테넌트 조건을 검증해야 한다.

## 연결 개념
- MFA(Multi-Factor Authentication) — 계정 탈취 위험을 줄이는 추가 인증
- RBAC/ABAC — 역할 또는 속성 기반 권한 모델
- IDOR(BOLA) — 객체 수준 권한 검증 누락

# 📝 【답안용】 시험 답안 템플릿

> 목적: 시험장에서 25분에 그대로 쓰는 답안 양식. 작성방식(추상표현 금지·수치·도식·문제유형 전환)을 엄격히 지킨다.
> 핵심: 인증·권한 결함 답안은 로그인 기능 설명이 아니라 세션, MFA, 객체 수준 권한, RBAC/ABAC, 감사로그를 경계별로 배치해야 한다.

## 핵심 인사이트 (3줄 요약)

> 1. **본질**: 인증은 사용자 식별, 권한은 자원·기능·객체 접근 허용 여부를 결정하는 별도 통제이다.
> 2. **가치**: 세션·토큰 검증, MFA, RBAC/ABAC, object-level authorization을 적용하면 계정 탈취와 IDOR를 분리해 통제할 수 있다.
> 3. **판단 포인트**: UI 숨김이 아니라 API, 서비스, 데이터 접근 계층에서 주체-행위-객체-조건을 검증해야 한다.

## 출제 의도 및 답안 포인트

| 출제 의도 | 반드시 짚을 핵심 | 감점 회피 포인트 |
|:---|:---|:---|
| 인증과 권한 구분 확인 | Authentication vs Authorization, 세션 vs 객체 권한 | 로그인 성공을 권한 통제로 오해 |
| 설계 통제 역량 확인 | MFA, session rotation, RBAC/ABAC, IDOR 방지 | 화면 버튼 숨김만 방안으로 제시 |
| 운영·감사 연결 확인 | 권한 실패 로그, 관리자 행위 감사, 재검증 | 권한 변경 승인과 로그 지표 누락 |

> 요약: 이 문제는 로그인 구현보다 API와 객체 단위 권한 경계를 설계하는 능력을 요구한다.

## Ⅰ. 개요 및 필요성

- 개요: 인증·인가 접근통제 실패
- 배경: 인증 실패는 계정 탈취로, 인가 실패는 IDOR와 관리자 기능 오남용으로 이어지며 마이크로서비스에서는 권한 검증 누락 지점이 늘어남.
- 필요성: OWASP ASVS, OAuth 2.0/OIDC, RBAC·ABAC 기준으로 세션, 토큰, 역할, 객체 소유권, 테넌트 경계를 요청마다 검증해야 함.

---

## Ⅱ. 구조 및 구성요소

```text
User -> Authentication -> Session/Token -> Authorization Policy -> Resource/API
        / MFA
        / Password Policy
        / Session Rotation
Policy -> RBAC/ABAC -> Object Ownership -> Tenant Boundary -> Audit Log
```

| 구성요소 | 역할 | 특이사항 |
|:---|:---|:---|
| 인증 | 사용자 신원 확인 | MFA, 비밀번호 정책, 토큰 검증 |
| 세션·토큰 | 인증 상태 전달 | 만료, 회전, 서명, audience 확인 |
| 권한 정책 | 기능·데이터 접근 결정 | RBAC, ABAC, policy engine |
| 객체 검증 | 소유자·테넌트·행위 확인 | IDOR와 BOLA 방지 핵심 |

> 요약: 인증·권한 구조는 신원 확인, 상태 전달, 정책 판단, 객체 검증을 요청마다 연결해야 한다.

---

## Ⅲ. 동작원리 및 흐름도

```text
로그인 요청 -> 자격 증명 검증 -> MFA/위험 기반 인증 -> 세션 발급
-> API 요청 -> 역할·속성·객체 소유권 확인 -> 허용/거부 -> 감사로그 저장
```

| 단계 | 처리 내용 | 검증 기준 |
|:---:|:---|:---|
| 1 | ID/PW, OAuth, 인증서 등 자격 증명 검증 | 비밀번호 해시 Argon2id/bcrypt, 실패 횟수 제한 |
| 2 | MFA 또는 위험 기반 추가 인증 수행 | 관리자·금융성 행위 step-up |
| 3 | 세션/JWT 서명·만료·audience 확인 | 만료 토큰 거부, session rotation |
| 4 | API별 RBAC/ABAC와 객체 소유권 검증 | 403 로그, IDOR 테스트 0건 |

> 요약: 정상 흐름은 인증 후에도 API마다 역할, 속성, 객체 소유권을 재검증하는 구조이다.

## Ⅳ. 특징

| 구분 | 기존/대안 | 인증·권한 통제 | 수치·기술 판단 |
|:---|:---|:---|:---|
| 인증 | ID/PW 단독 | MFA, 실패 제한, 세션 회전 | 관리자 MFA 적용률 100% |
| 세션 | 장기 토큰 | 만료, rotation, refresh token 보호 | access token 15분, refresh token 재사용 탐지 |
| 권한 | 화면 메뉴 숨김 | API 서버 RBAC/ABAC | deny by default 정책 |
| 객체 | ID 파라미터 신뢰 | object-level authorization | IDOR 회귀 테스트 0건 |

> 요약: 인증은 계정 탈취를, 권한은 객체·기능 오남용을 막는 별도 경계로 설계해야 한다.

## Ⅴ. 심화 비교 및 적용 판단

| 구분 | 기존/대안 | 본 키워드 | 선택 기준 |
|:---|:---|:---|:---|
| 구조 | 컨트롤러별 수동 if문 | 중앙 policy engine과 middleware | API 수 50개 이상 또는 다중 역할 서비스 |
| 비용/성능 | 매 요청 DB 권한 조회 | 캐시+짧은 TTL+정책 버전 | 권한 변경 반영 5분 이내 |
| 운영/위험 | 권한 변경 수동 반영 | 승인 workflow와 감사로그 | 관리자 권한 변경 2인 승인 |

> 요약: 권한 모델은 서비스 규모와 역할 복잡도에 따라 중앙 정책과 캐시 전략을 함께 선택한다.

| 리스크 | 원인 | 대응 방안 | 확인 지표 |
|:---|:---|:---|:---|
| 계정 탈취 | 약한 비밀번호, credential stuffing | MFA, rate limit, breached password 차단 | 로그인 실패율, MFA challenge 성공률 |
| IDOR/BOLA | 객체 소유권 검증 누락 | `{user_id, tenant_id, object_id}` 조건 강제 | IDOR 테스트 0건 |
| 권한 상승 | 관리자 API 기능 권한 누락 | RBAC/ABAC, deny by default, 2인 승인 | 403 비율, 권한 변경 감사로그 |

> 요약: 인증 리스크는 계정 탈취, 권한 리스크는 IDOR와 권한 상승으로 나누어 지표를 설정한다.

| 점검 항목 | 목표 기준 | 측정 방법 |
|:---|:---|:---|
| 인증 통제 | MFA 적용률 100%, 실패 제한 적용 | IAM 리포트, 로그인 로그 |
| 권한 검증 | 보호 API 100% middleware 경유 | 라우팅 목록과 정책 매핑 |
| 감사·재검증 | 관리자 행위 로그 100% 수집 | SIEM, 정기 권한 리뷰 |

> 요약: 성공 여부는 MFA 적용률, API 정책 경유율, 관리자 감사로그 수집률로 확인한다.

## Ⅵ. 실무 적용 및 결론

**적용 방안 3개 (필수 — 단계별 또는 항목별):**
1. 인증: Argon2id 또는 bcrypt 해시, 계정 잠금·rate limit, 관리자 MFA 100%, 로그인 성공 시 session id rotation 적용
2. 권한: API gateway와 서비스 계층에서 RBAC/ABAC 정책 적용, 객체 조회 쿼리에 `user_id`와 `tenant_id` 조건 강제
3. 운영: 관리자 권한 변경 2인 승인, 90일 주기 권한 리뷰, 401/403/권한 변경 로그를 SIEM에 수집

**결론 (2줄):**
- 기술사 판단: 인증은 MFA와 세션 보호, 권한은 object-level authorization과 deny by default를 분리 적용함
- 향후 방향: API 중심 서비스에서는 정책 엔진과 지속적 권한 리뷰로 계정·역할·객체 경계를 자동 검증함
