## 1. 한눈에 이해하기 (Core Intuition)
- **정의**: 개발자가 만든 애플리케이션(웹/앱)이 해킹에 뚫리는 구멍(취약점)이 없는지, 개발 단계부터 운영 단계까지 **각기 다른 시점과 방법(코드 분석, 실제 공격 시뮬레이션, 하이브리드, 실시간 방어)으로 진단하고 보호하는 4가지 핵심 보안 도구 세트**입니다.
- **필요성**: 코드를 눈으로만 검사하면(SAST) 실제 서버 설정 오류를 못 잡고, 외부에서 막 공격해 보면(DAST) 코드의 어디를 고쳐야 할지 정확한 줄 번호를 알려주지 않습니다. 완벽한 방패를 만들기 위해 4가지 도구가 각자의 단점을 보완하며 투입됩니다.
- **핵심 직관**: **"새로운 자동차(앱)를 개발하고 출고하는 품질 검사 과정"**. 
  - **SAST (설계도 검사)**: 차를 조립하기도 전에, 종이 '도면(소스코드)'만 보고 "어? 이 나사 위치가 잘못됐네" 찾아냄. 빠르지만 헛지적(오탐)이 많음.
  - **DAST (충돌 테스트)**: 차를 다 조립한 뒤 밖에서 망치로 직접 '때려보며(실제 해킹)' 부서지는지 확인. 진짜 부서지면 심각하지만, 도면의 어디가 문제인지는 모름.
  - **IAST (센서 부착 충돌 테스트)**: 차 내부에 '센서(에이전트)'를 달고 충돌 테스트를 함. 부서질 때 "도면의 34번 나사가 부러졌다!"고 정확히 알려주는 최신 기술.
  - **RASP (에어백과 자동 브레이크)**: 차가 고객에게 팔려서 실제 도로를 달릴 때(운영), 사고가 나려 하면 '스스로 해킹을 막아주는 보호막'.

## 2. 왜 중요한가? (Background & Value)
- **등장 배경**: DevSecOps 패러다임이 도래하면서 "보안을 왼쪽으로 앞당겨라(Shift-Left)"라는 지상 과제가 떨어졌습니다. 개발(SAST) $\rightarrow$ 테스트(DAST/IAST) $\rightarrow$ 운영(RASP)의 전체 생명주기(SDLC) 빈틈을 메우기 위해 4가지 툴이 유기적인 체인을 형성하게 되었습니다.
- **가치**: 가장 적절한 시점에, 가장 적은 비용으로 앱의 취약점을 제거합니다. 해커가 뚫을 구멍(SQL 인젝션, XSS 등)을 서비스 오픈 전에 원천 차단하는 가장 핵심적인 기술 벤치마크입니다.

## 3. 어떻게 작동하는가? (Mechanism)

**1. SAST (정적 애플리케이션 보안 테스트 - White Box)**
- **시점**: 코딩/빌드 단계. 앱을 실행하지 않습니다(정적).
- **작동**: IDE(VS Code 등)나 CI 서버에서, 개발자가 짠 소스코드 텍스트 자체를 문법 검사기처럼 쫙 스캔합니다. 
- **장점/단점**: "App.java 30번째 줄 고쳐!"라고 정확히 지적해 줘서 고치기 편함. 단, 실행할 때만 생기는 메모리 오류나 권한 오류는 못 잡고, 가짜 경보(오탐)가 너무 많아 개발자가 빡칩니다.

**2. DAST (동적 애플리케이션 보안 테스트 - Black Box)**
- **시점**: 테스트/QA 서버 오픈 단계. 앱이 실제 구동 중이어야 합니다(동적).
- **작동**: 해커처럼 외부 인터넷에서 게시판이나 로그인 창에 공격 코드(SQLi, XSS 무작위 문자열)를 수만 번 던져보고 에러가 나는지 봅니다(퍼징).
- **장점/단점**: 진짜 뚫리는 것만 잡기 때문에 오탐이 거의 없어 심각도가 매우 높음. 단, 코드 안쪽 구조를 모르기 때문에 "뚫리긴 했는데 서버 개발자야 알아서 고쳐라" 수준의 보고서만 줍니다. 소스코드 없는 상용 솔루션 점검에 유용합니다.

**3. IAST (상호작용 애플리케이션 보안 테스트 - Gray Box)**
- **시점**: 테스트/QA 단계 (SAST와 DAST의 장점 결합).
- **작동**: 앱 서버(WAS) 내부에 작은 감시 에이전트를 심어둡니다. QA 직원이 버튼을 누르거나 DAST가 밖에서 때릴 때, 내부 에이전트가 데이터의 흐름(Taint Tracking)을 쫓아가며 "방금 들어온 악성 데이터가 소스코드 45번째 줄 DB 쿼리에 도달했다!"고 짚어냅니다.
- **장점/단점**: DAST처럼 오탐이 없으면서도 SAST처럼 소스코드 줄 번호를 정확히 찍어주는 사기캐. 단, 에이전트를 깔면 서버가 약간 느려지고, 특정 언어(Java, .NET)만 지원하는 한계가 있습니다.

**4. RASP (런타임 애플리케이션 자가 방어 - Runtime Shield)**
- **시점**: 운영(Production) 환경. 테스팅 도구가 아니라 방어 장비입니다.
- **작동**: IAST처럼 서버(WAS) 내부에 딱 달라붙어 있습니다. 실제 고객 트래픽 중 해킹 코드가 날아와 앱의 핵심 메모리를 건드리려 하는 그 찰나의 순간(Runtime)에, 앱 스스로가 요청을 쳐내어(Drop) 버립니다.
- **장점/단점**: WAF(웹 방화벽)는 밖에서 필터링하지만, RASP는 앱 몸속에서 막기 때문에 제로데이 공격 차단율이 압도적입니다. 단, 버그로 앱 전체가 죽어버릴 장애 리스크가 있어 조심히 써야 합니다.

## 4. 핵심 비교 및 연결 개념 (Relation)

| 툴 이름 | 진단 시점 | 분석 대상 (접근 방식) | 타깃 대상 및 용도 | 오탐률 |
|---|---|---|---|---|
| **SAST** | 코딩/빌드 (Shift-Left) | 소스 코드 텍스트 (화이트박스) | 개발자에게 룰 위반 피드백 제공 | **매우 높음** |
| **DAST** | 테스트/QA 서버 | 실행 중인 겉모습 (블랙박스) | 실제 해킹 시뮬레이션 및 인증 결함 발견 | 매우 낮음 |
| **IAST** | 테스트/QA 서버 | 실행 중인 내부 메모리/흐름 (그레이박스) | DAST와 SAST 결합, 높은 정확도로 취약점 식별 | **거의 없음** |
| **RASP** | 운영 (Production) | 실행 중인 앱의 런타임 콜 (방어) | 운영망에서의 해킹 실시간 자가 방어 (탐지가 아님) | 낮음 |

# ✍️ 단답형 / 서술형 시험장 출격 준비

### Ⅰ. 핵심 인사이트
- **본질**: 애플리케이션 보안(AppSec) 및 DevSecOps 생태계를 구성하는 4대 코어 툴셋. 소스코드를 정적으로 분석하는 **SAST**, 런타임 환경에서 동적으로 찔러보는 **DAST**, 런타임 시 내부 에이전트를 통해 컨텍스트를 추적하는 **IAST**, 운영 환경에서 내부 콜을 차단하는 자가 방어 기제인 **RASP**로 나뉨.
- **가치**: 소프트웨어 취약점이 릴리스(Release) 이후 운영 환경에 도달하기 전, 개발 파이프라인(SDLC)의 각 마일스톤(Milestone)에서 다계층(Defense in Depth)으로 겹겹이 필터링하여 수정 비용을 최소화(Shift-Left)하는 보안 공학의 결정체.
- **판단 포인트**: 단일 도구로는 현대의 복합적인 웹 아키텍처(MSA, API 중심)를 완벽히 진단할 수 없습니다. SAST의 오탐 문제와 DAST의 코드 가시성 부재라는 맹점을, 인스트루멘테이션(Instrumentation) 기반의 **IAST 및 RASP** 아키텍처로 어떻게 보완하여 파이프라인의 자동화를 완성하느냐가 핵심입니다.

### Ⅱ. SAST와 DAST의 아키텍처 비교 및 한계
1. **SAST (Static Application Security Testing)**
   - 메커니즘: 앱 실행 전 소스코드(또는 바이트코드)의 추상 구문 트리(AST, Abstract Syntax Tree)를 파싱하여, 데이터 흐름과 컨트롤 플로우에서 알려진 보안 코딩 규칙(Secure Coding) 위반을 식별.
   - 장점: SDLC 가장 앞단에서 100% 코드 커버리지를 제공. 개발자에게 Line-of-code 단위로 Fix 가이드 제공.
   - 한계: 런타임 시 동적으로 할당되는 설정, 라이브러리 충돌, 논리적 인증 우회를 잡지 못하며 **과도한 오탐(False Positive)** 으로 인해 개발자의 '스캐너 무시' 현상(Alert Fatigue) 야기.
2. **DAST (Dynamic Application Security Testing)**
   - 메커니즘: 앱 구동 환경(Staging)에서, 크롤러가 URL 구조를 파악한 뒤 XSS/SQLi 페이로드를 HTTP Request 형태로 무차별 주입(Fuzzing/Injection)하여 응답(Response)의 이상 유무를 분석.
   - 장점: 소스코드 없는 3rd Party 솔루션 점검 가능. 실제 공격자의 관점(Attacker-facing)을 반영하여 오탐이 극히 낮음.
   - 한계: 전체 URL을 다 찾아내기 어려워 코드 커버리지가 낮음(Blind Spot 존재). 취약점을 발견해도 "어느 함수(Function)에서 뚫렸는지" 원인 추적 불능(Root Cause 부재).

### Ⅲ. 차세대 진단 및 방어: IAST와 RASP (Instrumentation)
SAST와 DAST의 태생적 한계를 극복하기 위해 바이트코드 삽입(Instrumentation) 기술을 활용한 3세대 기술.
1. **IAST (Interactive Application Security Testing)**
   - 메커니즘: 애플리케이션의 런타임 환경(WAS, JVM, Node.js) 내부에 에이전트를 심어 애플리케이션과 상호 작용(Interactive)함. 외부의 자동화 테스트(QA 툴, DAST) 트래픽이 들어올 때, 에이전트가 내부 메모리와 데이터의 오염 추적(Taint Tracking)을 수행하여 "입력값(Source)이 필터링 없이 취약한 함수(Sink)에 도달했다"는 것을 코드 레벨로 정확히 캐치.
   - 혁신: **"DAST 수준의 오탐 없는 정확도 + SAST 수준의 코드 줄 번호 제시"** 를 모두 달성하여 CI/CD 파이프라인의 자동화 병목을 제거.
2. **RASP (Runtime Application Self-Protection)**
   - 메커니즘: IAST와 동일한 에이전트 기술(Instrumentation)을 운영(Production) 환경에서 '방어' 목적으로 사용.
   - 혁신: WAF(웹 방화벽)는 네트워크 트래픽 패턴만 보고 차단하므로 암호화나 우회 기법에 뚫릴 수 있음. 반면 RASP는 "데이터베이스에 날아가는 SQL 쿼리가 실행되기 직전의 메모리 상태"를 검사하므로, 앱 자신이 스스로의 컨텍스트를 파악해 100% 확실한 공격만 정확히 차단(Drop)하거나 강제 세션 종료(Terminate)함. 제로데이 공격 방어의 끝판왕.

### Ⅳ. DevSecOps 파이프라인 적용 아키텍처 매핑
- **개발/코딩 (Code)** $\rightarrow$ IDE 플러그인 형태의 경량 **SAST** (문법 교정).
- **빌드/통합 (Build/CI)** $\rightarrow$ 중앙 서버 구동형 심층 **SAST** (결함 발견 시 빌드 브레이크).
- **스테이징/테스트 (Test/QA)** $\rightarrow$ **DAST** (동적 스캐닝) 및 QA 통합 자동화 **IAST** 동시 가동.
- **운영 및 모니터링 (Deploy/Ops)** $\rightarrow$ **RASP** 및 WAF를 통한 런타임 자가 방어.

### Ⅴ. 결론 및 실무적 판단 포인트
- 앱 보안을 완벽히 하려면 4가지 툴을 모두 사야 할까요? 아닙니다. CISO는 조직의 성숙도에 맞춰 도입해야 합니다. 코드가 엉망인 조직에 IAST를 먼저 들이면 부하만 가중됩니다. **SAST를 통해 기본적인 시큐어 코딩 문화를 정착(기초 체력)** 시킨 후, CI/CD 배포가 하루 10번씩 일어나는 초고도화된 애자일 환경에서는 오탐 병목이 없는 **IAST 중심의 파이프라인 자동화**로 갈아타는 것이 가장 훌륭한 로드맵입니다.

### 💡 문제 유형별 목차 전환 포인트
- **[소프트웨어 보안 취약점 진단 도구 비교 (SAST vs DAST)]**: Ⅰ과 Ⅱ번을 전면에 내세워, 화이트박스(정적)와 블랙박스(동적) 분석의 철학적 차이점과 커버리지 vs 정확도 트레이드오프를 상세히 비교.
- **[DevSecOps 고도화를 위한 차세대 진단 및 방어 (IAST / RASP)]**: 기존 진단 툴이 만든 개발 병목(오탐 수정) 현상을 비판하고, Ⅲ번의 에이전트 기반 인스트루멘테이션(Instrumentation) 기술이 개발과 테스트를 어떻게 혁신적으로 융합(하이브리드)했는지 논증.
