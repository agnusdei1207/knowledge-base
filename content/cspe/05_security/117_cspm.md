# 📖 【암기용】 개념 완전 이해

> 목적: CSPM을 처음 보는 사람도 클라우드 설정 오류를 어떻게 발견하고 조치하는지 이해하게 만든다. 시험 답안 양식이 아니라, 이해를 위한 친절한 설명이다.

## 한눈에
- **개요**: CSPM은 클라우드 계정의 보안 설정을 지속 점검하고 기준 위반을 조치하는 형상 관리 체계임
- **왜 필요한가**: 클라우드는 콘솔 클릭과 IaC 배포로 보안그룹, 스토리지 공개, 로그 설정이 빠르게 바뀐다. 작은 설정 오류 1개가 공개 버킷, 관리 포트 노출, 암호화 미적용 사고로 이어진다.
- **핵심 직관**: 건물 전체 문, 창문, CCTV, 출입기록 장치를 매일 점검해 열린 문과 꺼진 CCTV를 자동으로 찾는 점검반임

## 깊이 이해
- **배경·문제의식**: 온프레미스는 변경 창구가 제한적이지만 클라우드는 개발팀, 운영팀, 자동화 도구가 동시에 리소스를 만든다. 멀티계정·멀티리전 환경에서 수작업 점검은 누락 가능성이 높다.
- **작동 원리**: CSPM은 클라우드 API로 리소스와 설정을 수집하고, CIS Benchmark, NIST CSF, ISO 27001, 조직 정책과 비교한다. 위반 항목은 위험도별로 알림, 티켓, 자동 수정, 예외 승인 절차를 수행한다.
- **비유**: 자동차 정기검사처럼 라이트, 브레이크, 배출가스 기준을 항목별로 검사하고 불합격 항목은 정비 완료 전까지 운행 제한을 거는 구조임
- **구체 예시**: S3 버킷 공개 읽기, RDS 암호화 미적용, 보안그룹 22번 포트 0.0.0.0/0 허용을 Critical로 탐지하고 24시간 이내 조치 티켓을 생성함
- **흔한 오해·주의점**: CSPM은 취약점 스캐너가 아니다. VM 내부 CVE보다 클라우드 계정, IAM, 네트워크, 스토리지, 로그 같은 제어면 설정을 기준으로 판단함

## 연결 개념
- 공유 책임 모델 — 고객 책임 영역의 설정 오류 점검
- IaC Security — Terraform, CloudFormation 배포 전 정책 검사
- CNAPP — CSPM, CWPP, CIEM을 통합한 클라우드 네이티브 보호

# 📝 【답안용】 시험 답안 템플릿

> 목적: 시험장에서 25분에 그대로 쓰는 답안 양식. 작성방식(추상표현 금지·수치·도식·문제유형 전환)을 엄격히 지킨다.
> 핵심: CSPM은 클라우드 설정 오류를 찾는 도구명보다 정책 기준, 위험 점수, 조치 워크플로, 예외 관리까지 포함한 운영 체계로 써야 한다.

## 핵심 인사이트 (3줄 요약)

> 1. **본질**: CSPM(Cloud Security Posture Management)은 클라우드 리소스 설정을 보안 기준과 비교하여 위험 형상을 지속 관리하는 체계이다.
> 2. **가치**: 공개 스토리지, 과도 권한, 암호화 미적용, 로그 비활성화 같은 고객 책임 영역 사고를 조기 발견한다.
> 3. **판단 포인트**: 멀티클라우드 커버리지, 정책 기준, Critical 조치시간, 예외 승인 절차를 함께 제시해야 한다.

## 출제 의도 및 답안 포인트

| 출제 의도 | 반드시 짚을 핵심 | 감점 회피 포인트 |
|:---|:---|:---|
| 클라우드 설정 오류 관리 이해 확인 | 리소스 수집, 정책 비교, 위험 점수, 조치 워크플로 | CVE 스캐너와 혼동 |
| 공유 책임 기반 통제 설계 확인 | 고객 책임 영역, CIS Benchmark, 로그·암호화·IAM 점검 | CSP가 설정 오류까지 책임진다고 서술 |
| 운영 지표 판단 확인 | Critical 조치 SLA, 정책 준수율, 예외 만료 | 탐지 기능만 쓰고 조치·예외 관리 누락 |

> 요약: CSPM 문제는 클라우드 형상 위험을 자동 식별하고 조치까지 닫는 운영 역량을 평가한다.

---

## Ⅰ. 개요 및 필요성

- 개요: 클라우드 보안 형상 점검
- 배경: 클라우드 리소스는 API와 IaC로 수시 생성되며 보안그룹 공개, 스토리지 공개, KMS 미적용, 로그 비활성화가 고객 책임 사고로 이어진다.
- 필요성: CSPM은 CIS Benchmark, CSA CCM, 조직 표준 정책과 실제 설정을 자동 비교하고 위험도 기반으로 조치해야 한다.

---

## Ⅱ. 구조 및 구성요소

```text
Cloud Accounts -> API Collector -> Asset Inventory -> Policy Engine
  / CIS Benchmark
  / NIST/ISO/Company Policy
Policy Engine -> Risk Score -> Ticket/Auto Remediation -> Evidence
```

| 구성요소 | 역할 | 특이사항 |
|:---|:---|:---|
| API Collector | AWS, Azure, GCP 리소스와 설정 수집 | 읽기 전용 Role, 조직 계정 연동 |
| Asset Inventory | 계정, 리전, VPC, 스토리지, DB, IAM 목록화 | 태그 누락과 미소유 자산 탐지 |
| Policy Engine | 기준선과 설정 비교 | CIS Benchmark, NIST CSF, 조직 정책 |
| Risk Scoring | 심각도, 노출도, 데이터 민감도 산정 | 공개 인터넷+민감데이터는 Critical |
| Remediation | 티켓, 자동 수정, 예외 승인 | SLA와 변경관리 연계 |

> 요약: CSPM은 클라우드 API 수집, 자산 목록화, 정책 비교, 위험 점수화, 조치 워크플로로 구성된다.

---

## Ⅲ. 동작원리 및 흐름도

```text
계정 연결 -> 리소스 수집 -> 정책 기준 비교
-> 위험 점수 산정 -> 티켓/자동수정 -> 예외 만료 관리
-> 대시보드/감사 증적
```

| 단계 | 처리 내용 | 검증 기준 |
|:---:|:---|:---|
| 1 | 멀티계정·멀티리전 리소스 자동 수집 | 계정 커버리지 100%, 수집 주기 1시간 이하 |
| 2 | CIS, NIST, 내부 기준과 설정 비교 | 정책 버전 관리, 기준선 변경 승인 |
| 3 | 노출도와 데이터 등급으로 위험 점수 산정 | Critical, High, Medium 분류 |
| 4 | 티켓 생성 또는 자동 수정 실행 | Critical 24시간, High 7일 이내 조치 |
| 5 | 예외 승인, 만료, 감사 증적 관리 | 예외 만료일 90일 이하, 증적 1년 보존 |

> 요약: CSPM은 설정 수집에서 조치 완료와 예외 만료까지 닫힌 루프로 운영되어야 한다.

## Ⅳ. 특징

| 구분 | 수작업 점검 | CSPM | 수치·판단 포인트 |
|:---|:---|:---|:---|
| 점검 범위 | 표본 계정 중심 | 멀티계정·멀티리전 전체 | 계정 커버리지 100% |
| 기준 | 체크리스트 수동 적용 | CIS, NIST, 내부 정책 자동 비교 | 정책 준수율 95% 이상 |
| 대응 | 메일·수기 티켓 | 위험도 기반 티켓·자동 수정 | Critical 24시간 이내 |
| 증적 | 점검 시점 문서 | 설정 변경 이력과 조치 기록 | 로그 보존 1년 이상 |

> 요약: CSPM은 클라우드 설정 점검을 표본 검사에서 전체 계정 지속 점검으로 전환한다.

## Ⅴ. 심화 비교 및 적용 판단

| 구분 | 기존/대안 | 본 키워드 | 선택 기준 |
|:---|:---|:---|:---|
| 구조 | 수동 체크리스트, 정기 감사 | API 기반 지속 형상 점검 | 클라우드 계정 10개 이상, 리전 다수 |
| 비용/운영 | 감사 기간 집중 업무 | 상시 탐지, 티켓, 자동 수정 | DevOps 변경 빈도 일 10건 이상 |
| 위험 | 설정 오류 장기 방치 | 위험도 기반 조치 SLA | 인터넷 공개·암호화 미적용 위험 우선 |

> 요약: CSPM은 클라우드 변경 속도가 수작업 검토 속도를 초과할 때 필수 통제로 판단한다.

| 리스크 | 원인 | 대응 방안 | 확인 지표 |
|:---|:---|:---|:---|
| 알림 피로 | 정책 과다, 중요도 미분류 | 위험 점수, 자산 중요도, 억제 규칙 적용 | 월간 미처리 알림 10% 이하 |
| 자동 수정 사고 | 운영 영향 검토 없이 리소스 변경 | Dry-run, 승인 기반 수정, 롤백 절차 | 자동 수정 실패 1% 이하 |
| 사각지대 | 신규 계정 미연동, Shadow Cloud | 조직 계정 자동 등록, 계정 생성 차단 정책 | 미연동 계정 0건 |

> 요약: CSPM 운영은 알림 품질, 자동 수정 통제, 계정 커버리지 확보가 성패를 좌우한다.

| 점검 항목 | 목표 기준 | 측정 방법 |
|:---|:---|:---|
| 형상 준수 | 정책 준수율 95% 이상 | CSPM 대시보드 |
| 조치 SLA | Critical 24시간, High 7일 이내 | 티켓 시스템 |
| 커버리지 | 계정·리전·서비스 수집률 100% | CSP 조직 계정, CMDB 대조 |

> 요약: CSPM 효과는 정책 준수율, 조치 SLA, 커버리지로 정량 관리한다.

## Ⅵ. 실무 적용 및 결론

**적용 방안 3개:**
1. AWS Organizations, Azure Management Group, GCP Organization을 읽기 전용 Role로 연동하고 계정 커버리지 100%를 기준선으로 설정함
2. CIS Benchmark, KMS 암호화, CloudTrail/Activity Log, 공개 스토리지, 관리 포트 0.0.0.0/0 정책을 Critical 기준으로 등록함
3. Jira, ServiceNow, SIEM과 연계해 Critical 24시간 조치, 예외 만료 90일 이하, 증적 보존 1년 이상을 운영함

**결론 (2줄):**
- 기술사 판단: 멀티계정 클라우드에서는 수작업 점검으로 설정 편류를 통제할 수 없으므로 CSPM을 고객 책임 영역의 기본 통제로 둬야 함
- 향후 방향: CSPM은 IaC 검사, CIEM, CWPP와 통합되어 CNAPP 기반 사전·사후 통제로 확장됨
