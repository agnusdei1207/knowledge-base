# 📖 【암기용】 개념 완전 이해

> 목적: 프라이버시 중심 설계를 처음 보는 사람도 완벽히 이해하게 만든다. 시험 답안 양식이 아니라, 이해를 위한 친절한 설명이다.

## 한눈에
- **개요**: 개인정보 보호를 요구사항 분석부터 폐기까지 기본값으로 내장하는 설계 원칙
- **왜 필요한가**: 개인정보 침해는 배포 후 보안 기능을 덧붙여도 수집 최소화·동의·보관기간·제3자 제공 이력이 이미 꼬이면 복구 비용이 커진다. 설계 단계에서 데이터 흐름을 줄이고 통제 지점을 박아야 법 위반과 민원 리스크를 줄일 수 있다.
- **핵심 직관**: 집을 다 지은 뒤 비상구를 붙이는 방식이 아니라, 설계도에 비상구·소방센서·피난동선을 먼저 그리는 방식이다.

## 깊이 이해
- **배경·문제의식**: Privacy by Design은 7대 원칙(사전예방, 기본값 보호, 설계 내재화, 기능 균형, 전 생애주기 보호, 투명성, 이용자 중심)을 기반으로 한다. GDPR Article 25의 Data Protection by Design and by Default와도 연결된다.
- **작동 원리**: 개인정보 항목을 식별하고, 목적별 최소 수집을 정하며, 기본 설정을 비공개로 두고, 저장·전송·처리 단계에 암호화·접근통제·로그를 배치한다. 이후 PIA, DPIA, 보안성 검토, 삭제 검증으로 설계가 실제 운영까지 이어지는지 확인한다.
- **비유**: 쇼핑몰 회원가입 화면에서 선택 광고 수신을 기본 체크하지 않고, 필수 항목과 선택 항목을 분리하며, 보관기간이 끝나면 자동 파기되는 구조를 처음부터 만드는 것이다.
- **구체 예시**: 위치기반 앱은 GPS 원좌표를 30일 보관하지 않고, 1km 격자 단위로 가공한 위치만 7일 보관하며, 원좌표 접근은 RBAC와 감사로그 1년 보존으로 제한한다.
- **흔한 오해·주의점**: Privacy by Design은 개인정보 동의 문구를 길게 쓰는 작업이 아니다. 수집하지 않아도 되는 데이터 제거, 기본값 비공개, 목적 외 이용 차단이 핵심이다.

## 연결 개념
- 개인정보 영향평가(PIA) - 설계안의 침해 요인을 사전에 평가
- 개인정보보호 강화기술(PET) - 차등프라이버시·가명처리·암호기반 분석 적용
- ISO/IEC 29100 - 프라이버시 원칙과 역할 용어의 기준선

# 📝 【답안용】 시험 답안 템플릿

> 목적: 시험장에서 25분에 그대로 쓰는 답안 양식. 작성방식(추상표현 금지·수치·도식·문제유형 전환)을 엄격히 지킨다.
> 핵심: 동의·암호화 나열이 아니라, 데이터 생애주기별 기본값·최소수집·검증 지표를 설계 산출물로 제시한다.

## 핵심 인사이트 (3줄 요약)

> 1. **본질**: Privacy by Design은 개인정보 보호 요구사항을 사후 점검이 아니라 요구사항·설계·개발·운영·폐기 전 과정의 기본 제약으로 내장하는 접근이다.
> 2. **가치**: 최소수집, 기본값 비공개, 목적 제한, 보관기간 자동 파기, 감사로그로 개인정보보호법·GDPR Article 25 대응 근거를 남긴다.
> 3. **판단 포인트**: 보호조치 이름보다 개인정보 항목 수, 보관기간, 접근권한 수, 파기 성공률, 정보주체 요청 처리 SLA로 설계 품질을 판단한다.

## 출제 의도 및 답안 포인트

| 출제 의도 | 반드시 짚을 핵심 | 감점 회피 포인트 |
|:---|:---|:---|
| 개인정보 보호를 설계 요구사항으로 전환하는 역량 확인 | 7대 원칙, 기본값 보호, 수명주기 통제, PIA 연계 | 동의서·암호화만 쓰고 최소수집·기본값을 누락 |
| 법·표준·기술 통합 판단 확인 | GDPR Article 25, 개인정보보호법, ISO 29100, PET 연결 | 해외 법령을 국내 인증 대체 수단으로 단정 |
| 운영 검증 관점 확인 | DPIA/PIA, 접근로그, 보관기간, 파기증적, DSAR SLA | 원칙 설명 후 지표·감사 증거를 제시하지 않음 |

> 요약: 이 문제는 프라이버시 원칙을 데이터 흐름·기본 설정·감사 지표로 변환하는 설계 능력을 요구한다.

## Ⅰ. 개요 및 필요성

Privacy by Design은 개인정보 보호를 시스템 기본 설계에 내장하는 원칙이다. 개인정보 침해는 수집 단계의 과다 항목, 목적 외 이용, 보관기간 초과, 접근권한 과다에서 시작된다. 설계 단계에서 데이터 최소화와 기본값 보호를 확정해야 배포 후 법무·보안·운영 보정 비용을 줄일 수 있다.

---

## Ⅱ. 구조 및 구성요소

```text
서비스 요구 -> 개인정보 흐름 식별 -> 최소수집/기본값 설계
            -> 암호화/RBAC/로그 -> PIA/테스트 -> 운영 모니터링/파기
```

| 구성요소 | 역할 | 특이사항 |
|:---|:---|:---|
| 데이터 인벤토리 | 항목·목적·보관기간·제공처 식별 | RoPA, 데이터 맵, 처리 위탁 목록 |
| 기본값 보호 | 비공개 설정, 선택 동의 분리 | opt-in, 필수/선택 항목 UI 분리 |
| 생애주기 통제 | 수집·이용·제공·보관·파기 제어 | 보관기간 TTL, 파기 배치, 증적 보존 |
| 검증 체계 | PIA/DPIA, 위협모델링, 감사로그 | 위험등급, 조치계획, 재평가 주기 |

> 요약: Privacy by Design 구조는 데이터 흐름을 줄이고 기본값과 생애주기 통제를 설계 산출물로 고정하는 체계이다.

---

## Ⅲ. 동작원리 및 흐름도

```text
개인정보 처리 목적 정의 -> 항목별 필요성 검토 -> 기본값/동의 설계
-> 저장/전송/처리 보호조치 적용 -> PIA 검증 -> 운영로그/파기증적 확인
```

| 단계 | 처리 내용 | 검증 기준 |
|:---:|:---|:---|
| 1 | 처리 목적·법적 근거·정보주체 범위 식별 | 목적별 개인정보 항목 매핑 100% |
| 2 | 최소수집·가명처리·보관기간 설계 | 선택 항목 분리, 보관기간 만료 자동 파기 |
| 3 | 기본값·권한·암호화 통제 구현 | 비공개 기본값, AES-256, RBAC, MFA |
| 4 | PIA/DPIA와 운영 로그로 검증 | 고위험 조치 완료율, 접근로그 1년 이상 |

> 요약: 동작 원리는 개인정보 처리 목적을 먼저 고정하고 항목·기본값·보호조치·검증 증적을 순서대로 확정하는 방식이다.

## Ⅳ. 특징

| 구분 | 사후 보호 방식 | Privacy by Design | 수치·판단 포인트 |
|:---|:---|:---|:---|
| 설계 시점 | 배포 후 점검·보완 | 요구사항 단계부터 보호 요구 반영 | 요구사항 추적률 100% |
| 데이터 범위 | 서비스 편의 중심 수집 | 목적별 최소 항목 수집 | 필수 항목 비율, 보관기간 |
| 기본 설정 | 사용자가 직접 변경 | 비공개·최소노출 기본값 | opt-in 비율, 선택 동의 철회율 |
| 검증 방식 | 침해 발생 후 대응 | PIA/DPIA, 로그, 파기증적 | DSAR 30일 이내, 파기 성공률 99% |

> 요약: Privacy by Design은 보호 기능 추가가 아니라 수집 범위와 기본값을 설계 단계에서 제한하는 접근이다.

| 비용/성능 | 배포 후 법무·개발 재작업 | 요구사항 단계 비용 선투입 | 변경 비용 대비 PIA 조치 건수 |
| 운영/위험 | 과다수집·보관기간 초과 탐지 지연 | 보관기간 TTL, 권한 만료, 로그 감사 | 민감정보·아동정보·위치정보 처리 |

> 요약: 고위험 개인정보를 다루는 서비스는 동의 문구 보완보다 설계 단계의 최소수집과 보관기간 통제가 우선이다.

| 리스크 | 원인 | 대응 방안 | 확인 지표 |
|:---|:---|:---|:---|
| 과다수집 | 서비스 요구와 개인정보 항목 미분리 | 필수/선택 항목 표준, 데이터 최소화 리뷰 | 목적 없는 항목 0건 |
| 목적 외 이용 | 데이터 레이크 재사용 통제 미흡 | 목적 태그, ABAC, 쿼리 감사 | 미승인 쿼리 0건 |
| 파기 누락 | 보관기간·백업·로그 파기 정책 불일치 | TTL, 백업 파기 절차, 파기증적 보존 | 만료 데이터 잔존율 0.1% 이하 |

> 요약: 주요 리스크는 과다수집·목적 외 이용·파기 누락이며, 목적 태그와 파기 자동화로 감사 가능한 통제를 만든다.

| 점검 항목 | 목표 기준 | 측정 방법 |
|:---|:---|:---|
| 데이터 최소화 | 목적 없는 개인정보 항목 0건 | 데이터 인벤토리와 API 스키마 대조 |
| 정보주체 권리 | 열람·정정·삭제 요청 30일 이내 처리 | DSAR 티켓 SLA, 처리 로그 |
| 운영 감사 | 접근로그 1년 이상, 권한검토 분기 1회 | IAM 리포트, SIEM, 파기 결과표 |

> 요약: 성공 여부는 선언문이 아니라 항목 수, 처리 SLA, 로그·파기 증적으로 판단한다.

## Ⅵ. 실무 적용 및 결론

**적용 방안 3개 (필수 - 단계별 또는 항목별):**
1. 요구사항 단계: 개인정보 항목별 목적·법적 근거·보관기간·제공처를 데이터 인벤토리로 등록하고 PIA 체크리스트 100% 매핑
2. 개발 단계: 기본값 비공개, 선택 동의 opt-in, AES-256 저장 암호화, TLS 1.3 전송 암호화, RBAC·MFA 적용
3. 운영 단계: DSAR 30일 이내 처리, 접근로그 1년 이상 보존, 보관기간 만료 데이터 자동 파기와 파기증적 월 1회 점검

**결론 (2줄):**
- 기술사 판단: 신규 개인정보 서비스는 Privacy by Design을 요구사항 게이트로 두고, 고위험 처리이면 PIA/DPIA 완료 전 운영 반영을 보류함
- 향후 방향: PET, 데이터 계보, 정책 기반 접근통제를 결합해 AI·마이데이터 환경의 목적 제한과 최소수집을 자동 검증하는 방향으로 발전함
