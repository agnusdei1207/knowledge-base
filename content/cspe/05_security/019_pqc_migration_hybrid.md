## 미리 알고가기

- HNDL: 지금 암호문을 수집해 두었다가 나중에 양자 컴퓨터로 푸는 공격 가정임
- Crypto Agility: 코드를 크게 바꾸지 않고 알고리즘을 교체할 수 있게 만드는 설계 원칙임
- 하이브리드 방식: 기존 공개키 알고리즘과 PQC를 함께 써 전환기 위험을 줄이는 방식임
- CBOM: 조직 안에서 어떤 암호 알고리즘과 라이브러리가 쓰이는지 정리한 자산 목록임

## Ⅰ. 개요

- **정의/개념**: PQC 전환 로드맵은 RSA·ECDH·ECDSA 인프라를 PQC 표준으로 옮기는 계획임. 하이브리드는 기존 알고리즘과 PQC를 함께 적용함
- **배경/필요성**: 공개키 체계는 중간 장비, 인증서, 라이브러리 의존성이 얽혀 있음. 서비스 중단 없는 단계 전환 절차가 필요함

## Ⅱ. 특징

- 알고리즘 교체뿐 아니라 자산 식별·우선순위·상호 운용성 검증을 포함함
- 장기 기밀 데이터는 HNDL 위험 때문에 키 교환 전환 우선순위가 높음
- 하이브리드는 단일 실패 위험을 줄이지만 메시지 크기와 구현 복잡도를 키움
- 최종 목표는 벤더나 단일 알고리즘에 묶이지 않는 교체 가능 구조를 만드는 것임

## Ⅲ. 종류 및 비교

| 판단 기준 | 단독 전환 | 하이브리드 전환 |
|:---|:---|:---|
| 전환 속도 | 목표 알고리즘으로 바로 단순화함 | 기존 체계를 유지하며 단계적으로 옮김 |
| 위험 분산 | 새 알고리즘이나 중간 장비 호환성 실패가 바로 장애로 이어질 수 있음 | 기존 알고리즘과 PQC를 함께 써 전환기 단일 실패 위험을 줄일 수 있음 |
| 메시지와 운영 부담 | 구조가 단순해 오버헤드가 적음 | 공개키와 서명 데이터가 늘고 운영 정책도 복잡해짐 |
| 적합한 상황 | 폐쇄망이나 새 시스템처럼 통제 범위가 명확할 때 맞음 | 인터넷 서비스나 대규모 PKI처럼 상호 운용성 요구가 큰 환경에 맞음 |

> 요약: 단독 전환은 단순하지만 위험이 크고, 하이브리드 전환은 복잡하지만 현실 서비스에 적용하기 쉬움.

## Ⅳ. 구성요소 및 구조

| 구성요소 | 설명 |
|:---|:---|
| 암호 자산 인벤토리 | 프로토콜, 인증서, 라이브러리, HSM, 애플리케이션이 어떤 알고리즘을 쓰는지 정리하는 출발점이며 우선순위 판단의 근거가 됨 |
| 우선순위 모델 | 기밀성 보존 기간, 외부 노출 정도, 교체 난이도를 기준으로 전환 대상을 나누는 틀이며 일정과 예산에 직접 연결됨 |
| 하이브리드 구현 | 키 교환이나 서명에 기존 알고리즘과 PQC를 동시에 넣어 전환기 상호 운용성을 확인하는 설계임 |
| 검증 체계 | 성능, 호환성, 운영 절차를 점검하는 단계이며 전환 성공 여부를 수치로 확인하는 장치임 |

```text
+----------+     +------------+     +---------------+     +-----------+
| 자산 식별 | --> | 우선순위화 | --> | 하이브리드 적용 | --> | 검증 및 확대 |
+----------+     +------------+     +---------------+     +-----------+
```

> 요약: 무엇을 어디서 쓰는지 찾고, 우선순위를 세우고, 하이브리드로 넣고, 검증 뒤 확대하는 구조임.

## Ⅴ. 원리 및 절차 흐름도

```text
+----------+     +----------+     +----------+     +----------+     +----------+
| 현황 조사 | --> | 영향 분석 | --> | 시범 적용 | --> | 상호 운용 검증 | --> | 단계적 전환 |
+----------+     +----------+     +----------+     +----------+     +----------+
```

1. **현황 조사**: 조직 안의 암호 자산과 의존 경로를 정리함
2. **영향 분석**: 기밀성 보존 기간과 교체 난이도로 우선순위를 나눔
3. **시범 적용**: TLS, VPN, 메시징 같은 대표 경로에 하이브리드 구성을 적용함
4. **상호 운용 검증**: 중간 장비, 인증서 체인, 라이브러리 호환성을 점검함
5. **단계적 전환**: 성능과 장애 패턴을 확인하며 점진적으로 적용 범위를 넓힘

## Ⅵ. 실무 적용 및 유의점

1. 인터넷 서비스·VPN은 하이브리드 키 교환 파일럿을 먼저 수행하고 실패율·세션 지연·장비 로그로 확인함
2. 장기 기밀 데이터는 CBOM 기반 우선순위와 crypto agility를 세우고 식별률·교체율·전환 시간으로 확인함

## Ⅶ. 결론

- PQC 전환은 알고리즘 교체가 아니라 자산 의존성 파악, 하이브리드 위험 분산, 단계적 단독 전환 기반 확보 절차임

## 작성 근거(검토용)

- 전환 로드맵의 판단 축을 알고리즘 이름이 아니라 자산 식별, 우선순위, 검증 지표로 잡음
- `crypto agility 확보`를 교체 가능 구조로 풀어 써 문맥상 역할을 명확히 함
- 하이브리드 방식은 장점 표현보다 실패율, 세션 지연, 장비 로그로 검증하는 절차로 배치함
