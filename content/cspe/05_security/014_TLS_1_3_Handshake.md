## Ⅰ. 개요
| 항목 | 내용 |
|---|---|
| **정의** | 연결 지연을 단축하고 보안 강도를 높이기 위해 기존 TLS 1.2 구조를 전면 재설계한 최신 암호화 프로토콜임 |
| **배경/필요성** | 모바일/웹 환경에서 통신 지연(RTT)을 최소화하고, 과거 취약점이 드러난 레거시 암호 알고리즘을 과감히 제거할 필요성 대두 |
| **출제 의도** | TLS 1.2와의 차이점(1-RTT, 0-RTT, PFS 강제화) 및 강화된 Cipher Suite 구조 파악 |

## Ⅱ. 구성요소
```text
+-------------------+      +-------------------+      +-------------------+
|  1-RTT Handshake  |      |   0-RTT Resumption|      | AEAD Cipher Suites|
| (1회 왕복 접속)   +----->| (초기 데이터 전송)+----->| (무결성+기밀성)   |
+-------------------+      +-------------------+      +-------------------+
```
| 구성요소 | 설명 | 비유 |
|---|---|---|
| **1-RTT 핸드셰이크** | 클라이언트 인사와 키 교환용 공유값을 최초 연결 시 동시에 보내 왕복 시간을 절반으로 줄인 구조임 | 만날 때 신분증과 협상 카드를 한 번에 내밈 |
| **0-RTT 세션 재개** | 이전에 접속했던 서버의 경우, 연결 수립을 기다리지 않고 첫 패킷부터 응용 데이터를 암호화해 보내는 방식임 | 프리패스 카드로 대문 안 열고 바로 입장 |
| **AEAD 지원** | 암호화와 무결성 검증을 동시에 단일 연산으로 처리하는 현대적 블록 암호 모드(AES-GCM, ChaCha20)임 | 봉인과 서명을 한 번에 처리하는 특수 도장 |

> 요약: 통신 속도를 극대화(1-RTT)하면서 동시에 낡은 알고리즘을 제거하여 단순하고 강력한 보안을 달성함.

## Ⅲ. 절차
```text
+----------------+   +----------------+   +----------------+   +----------------+
| 1. Client Hello|-->| 2. Server Hello|-->| 3. 서명 및 종료|-->| 4. 데이터 교환 |
| (Key Share포함)|   | (Key Share응답)|   | (인증서 전송)  |   | (안전한 통신)  |
+----------------+   +----------------+   +----------------+   +----------------+
```
1. **Client Hello & Key Share**: 클라이언트가 접속 요청 시 자신이 지원하는 키 교환 매개변수(Diffie-Hellman 값)를 선제적으로 생성해 함께 전송함
2. **Server Hello & Key Share**: 서버가 매개변수를 확인 후 즉시 공통 세션키를 도출하고, 자신의 매개변수와 함께 응답함
3. **서명 및 Finished**: 서버가 인증서와 서명값을 대칭키로 암호화하여 보내며 핸드셰이크를 즉시 종료함
4. **보안 데이터 교환**: 이후 클라이언트와 서버는 합의된 대칭키와 AEAD 알고리즘으로 양방향 암호화 통신을 수행함

> 요약: 키 교환 정보를 첫 인사말에 포함하여 불필요한 왕복을 없애고 단 1회의 상호 작용만으로 보안 채널을 형성함.

## Ⅳ. 문제점
* **0-RTT 재전송 공격(Replay Attack)**: 0-RTT 모드 사용 시 공격자가 초기 데이터 패킷을 가로채어 동일 서버에 반복 재전송하는 취약점 발생
* **네트워크 장비의 호환성 결여**: 방화벽이나 미들박스(IDS/IPS)가 TLS 1.3의 암호화된 핸드셰이크나 압축된 구조를 비정상 트래픽으로 오인해 차단
* **레거시 시스템 마이그레이션 부담**: RSA 기반 정적 키 교환이나 낡은 Cipher Suite에 의존하던 오래된 서버/앱 환경에서 도입 불가

## Ⅴ. 개선방안
* **단기 방안 (재전송 보호 매커니즘)**: 0-RTT 허용 시 멱등성(Idempotent)이 보장되는 GET 요청에만 국한시키고, 타임스탬프 검증으로 재전송 차단
* **중기 방안 (호환성 모드 적용)**: 중간 장비 우회를 위해 겉모습을 TLS 1.2처럼 위장하는 호환성 매개변수(Middlebox Compatibility Mode) 활성화
* **장기 방안 (인프라 전면 교체)**: 클라우드 로드밸런서와 최신 WAS 엔진으로 점진적 교체를 단행하여 TLS 1.3 전용 아키텍처로 완전 마이그레이션

## Ⅵ. 전망
* 현재 신규 웹 서버 및 모바일 앱 통신의 90% 이상이 속도와 보안의 이점 때문에 TLS 1.3을 기본 채택하고 있음
* 차세대 HTTP/3 (QUIC) 프로토콜의 전송 계층 암호화 스택에 TLS 1.3 구조가 그대로 내장되어 인터넷 근간 표준으로 자리잡음
