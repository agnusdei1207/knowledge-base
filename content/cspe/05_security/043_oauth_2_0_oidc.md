## 1. 한눈에 이해하기 (Core Intuition)
- **정의**: 
  - **OAuth 2.0**: 내가 쓰려는 타사 앱(예: 배달 앱)에게, 내 진짜 구글/네이버 '비밀번호'를 주지 않고도 내 정보(친구 목록, 이메일)에 대신 접근할 수 있는 **'열쇠(Access Token, 접근 권한)'를 안전하게 발급해 주는 표준 프로토콜**입니다.
  - **OIDC (OpenID Connect)**: OAuth 2.0이라는 '권한 위임' 기술의 뼈대 위에, 사용자가 누구인지를 증명하는 **'신분증(ID Token, 인증)' 기능**을 추가로 얹어서 소셜 로그인을 완성하는 현대적 인증 표준입니다.
- **필요성**: 예전에는 앱이 내 페이스북 친구 목록을 가져오려면, 앱에게 내 페이스북 아이디와 비밀번호를 쌩으로 맡겨야 했습니다(끔찍한 보안 사고). 비밀번호 유출 없이 권한만 깔끔하게 빌려주기 위해 탄생했습니다.
- **핵심 직관**: **"호텔 발렛 파킹 키 (OAuth 2.0)"**. 
  내 자동차 키(비밀번호)에는 트렁크, 콘솔 박스, 엔진을 다 여는 권한이 있습니다. 이 진짜 키를 발렛 기사(서드파티 앱)에게 주면 내 차의 귀중품을 다 훔쳐 갈 수 있습니다. 그래서 주차만 딱 할 수 있고 트렁크는 못 여는 '발렛 전용 임시 키(Access Token)'를 발급해 주는 시스템이 OAuth입니다.

## 2. 왜 중요한가? (Background & Value)
- **등장 배경**: 모바일 앱과 API 경제가 폭발하면서(2010년대), 수많은 앱들이 구글, 페이스북, 카카오 등의 데이터(API)를 끌어다 써야 했습니다. 이 거대한 연결을 위해 OAuth 2.0이 사실상 전 세계 API 인가의 단일 언어로 통일되었습니다.
- **가치**: 개발자들은 귀찮은 회원가입/비밀번호 관리 DB를 만들 필요 없이 '카카오 로그인' 버튼 하나로 사용자를 끌어모으고, 사용자는 비밀번호를 입력하지 않고 안전하게 서비스를 이용하는 윈-윈(Win-Win) 생태계의 척추입니다.

## 3. 어떻게 작동하는가? (Mechanism)
OAuth 2.0의 가장 표준적인 흐름인 **"인가 코드(Authorization Code) 방식"** 의 흐름입니다. 총 4명의 배우가 등장합니다.
- 사용자 (Resource Owner), 배달 앱 (Client), 구글 로그인 창 (Authorization Server), 구글 주소록 서버 (Resource Server).

1. 사용자가 배달 앱에서 "구글 주소록 불러오기" 버튼을 누릅니다.
2. 배달 앱은 사용자를 구글의 공식 로그인 화면으로 튕겨냅니다(Redirect).
3. 사용자가 구글 화면에서 로그인(본인 확인)을 한 뒤, "배달 앱이 당신의 주소록을 읽으려 합니다. 허락할까요?" 창에 "예"를 누릅니다(권한 인가).
4. 구글은 배달 앱에게 **"임시 교환권(Authorization Code)"** 을 브라우저를 통해 은밀히 던져줍니다. (아직 토큰이 아님!).
5. 배달 앱 서버(백엔드)는 그 교환권을 들고 구글 서버로 직접 은밀히 뒷구멍으로 가서 찐 **"접근 열쇠(Access Token)"** 로 바꿔옵니다.
6. 이제 배달 앱은 이 열쇠를 구글 주소록 서버에 제시하고 내 주소록 데이터를 성공적으로 꺼내옵니다.

## 4. 실전 활용 및 예시 (Real-world Application)
- **구체적 사례**: 
  - **OIDC의 탄생**: 본래 OAuth 2.0은 "인가(권한 위임)" 프로토콜이라서 사용자가 누군지 관심이 없습니다. 하지만 앱들은 "그래서 방금 로그인한 얘가 누구(이메일, 이름)야?"가 알고 싶었죠. 그래서 OAuth 과정에서 발급되는 권한 열쇠(Access Token) 옆에, 덤으로 **JSON 포맷의 신분증명서(ID Token)** 를 하나 더 발급해 주는 표준인 OIDC가 만들어져 현재의 완벽한 '소셜 로그인'이 완성되었습니다.
- **주의점 및 흔한 오해**: 
  - OAuth와 OIDC를 헷갈리면 안 됩니다. 
  - **OAuth 2.0**: "내 데이터를 가져다 쓰게 **허락(인가, Authorization)** 할게." (결과물: Access Token)
  - **OIDC**: "나 로그인했어. 내 **신원(인증, Authentication)** 정보를 알려줘." (결과물: ID Token + Access Token)

## 5. 핵심 비교 및 연결 개념 (Relation)
- **SAML 2.0 vs OIDC (SSO 양대 산맥)**:
  - **SAML**: 무거운 XML 기반, 보안이 빡빡해서 대기업 인트라넷, B2B 엔터프라이즈 사내 로그인망에 주로 쓰임.
  - **OIDC**: 가벼운 JSON 기반, 모바일 앱과 REST API 통신에 특화되어 대국민 B2C 앱(소셜 로그인)의 99%를 장악함.

# ✍️ 단답형 / 서술형 시험장 출격 준비

### Ⅰ. 핵심 인사이트
- **본질**: **OAuth 2.0**은 서드파티 애플리케이션(Client)이 사용자의 비밀번호 노출 없이 한정된 자원에 대한 접근 권한(Access Token)을 위임받기 위한 인가(Authorization) 프레임워크. **OIDC**는 OAuth 2.0 확장을 통해 인증(Authentication) 기능과 신원 정보(ID Token)를 제공하는 상위 레이어 프로토콜.
- **가치**: 패스워드 공유(Anti-pattern) 리스크를 제거하고(API 경제 활성화), JWT(JSON Web Token) 및 RESTful API 아키텍처와 결합하여 모바일/클라우드 환경의 마이크로서비스 간 가장 가볍고 표준화된 B2C 기반 인증/인가 토대를 제공함.
- **판단 포인트**: OAuth 2.0은 4가지 이상의 'Grant Type(승인 방식)'을 제공하며, 클라이언트의 특성(백엔드 서버 유무, SPA 웹/모바일 앱)에 따라 토큰 탈취 취약점을 막기 위해 가장 안전한 **PKCE 기반의 인가 코드 흐름(Authorization Code Flow with PKCE)** 을 선택하는 것이 보안 설계의 핵심임.

### Ⅱ. OAuth 2.0의 4대 구성 요소(Roles)
1. **Resource Owner (자원 소유자)**: 웹 서비스를 이용하는 실제 일반 사용자(본인 계정의 데이터 소유권자).
2. **Client (클라이언트)**: 사용자의 자원을 대신 이용하고자 하는 서드파티 웹/모바일 애플리케이션 (예: 우버, 요기요 등).
3. **Authorization Server (인가 서버)**: 사용자 인증 후, 권한 위임 동의를 거쳐 클라이언트에게 토큰(Access Token)을 발행하는 인증/인가 통제 서버 (예: Google/Kakao 로그인 서버).
4. **Resource Server (자원 서버)**: 유효한 액세스 토큰을 제시하면 사용자의 자원(프로필, 사진, 연락처 API 등)을 응답해 주는 서버. (보통 인가 서버와 같은 기업에 속함).

### Ⅲ. 핵심 토큰의 종류 및 구조
**1. Access Token (접근 토큰)**
- 목적: Resource Server에서 데이터를 꺼내기 위한 짧은 수명(보통 1시간)의 열쇠. (주로 Bearer 방식의 JWT 사용).
- 한계: 누가, 언제 인증받았는지 명시적 확인이 보장되지 않는 순수 "인가(AuthZ)" 목적.

**2. Refresh Token (갱신 토큰)**
- 목적: Access Token이 만료되었을 때, 사용자를 다시 로그인 창으로 튕겨내지 않고 서버 간 통신만으로 조용히 새 Access Token을 재발급(Refresh)받기 위한 긴 수명(수 주~수 개월)의 토큰. 탈취 시 치명적이므로 클라이언트 백엔드에 안전하게 격리 저장해야 함.

**3. ID Token (OIDC의 핵심 발명품)**
- 목적: 사용자의 신원(이름, 이메일, 발급 시간 등)을 증명하는 **JWT(JSON Web Token)** 형식의 암호학적 신분증 (AuthN). 페이로드 내에 `sub(주체 식별자)`, `iss(발급자)`, `aud(수신자)` 등의 청구(Claim) 정보를 포함하여 무결성 검증.

### Ⅳ. 인증/인가 흐름 모델 (Grant Types)
1. **Authorization Code Grant (인가 코드 승인 방식 - 가장 안전, 표준)**:
   - 브라우저 프론트엔드로는 1회용 교환권인 '인가 코드(Auth Code)'만 보내고, 클라이언트의 백엔드 서버가 구글 서버와 통신할 때 '인가 코드 + 클라이언트 시크릿 패스워드(Client Secret)'를 제출하여 안전하게 진짜 Access Token을 교환받음. 토큰이 사용자 브라우저 노출을 최소화함.
2. **Implicit Grant (암묵적 승인 방식 - 퇴출 권고)**:
   - 과거 백엔드가 없는 SPA(React 등) 프론트엔드 앱을 위해 인가 코드 없이 브라우저 URL로 직접 Access Token을 꽂아준 방식. 해커의 토큰 가로채기(Fragment 탈취)에 극도로 취약해 현재 OAuth 2.1 초안에서 전면 폐기/사용 금지됨.
3. **Client Credentials Grant (클라이언트 자격증명 승인 방식)**:
   - 사용자 개입 없이, B2B 백엔드 서버 대 서버(Machine to Machine) 데몬 통신 시 사용하는 방식.

### Ⅴ. 보안 취약점: 토큰 가로채기(Interception)와 PKCE 방어
- **모바일 앱의 취약점**: 모바일에서 인가 코드(Auth Code)를 발급받아 다시 앱으로 돌아올 때(Custom URI Scheme 방식), 악성 앱이 중간에 해당 Scheme을 가로채어 교환권을 훔쳐 Access Token을 탈취하는 공격 발생.
- **해결책 (PKCE, Proof Key for Code Exchange)**:
  - 로그인을 시작할 때, 앱이 난수 비밀번호(`Code Verifier`)를 하나 만들고 이를 해시한 값(`Code Challenge`)을 구글에 먼저 줌.
  - 구글이 인가 코드를 내려주면, 악성 앱이 훔쳐서 토큰으로 바꾸러 가도, 구글이 "너 아까 만든 원본 난수 비번(`Code Verifier`) 대봐"라고 할 때 악성 앱은 원본을 모르므로 토큰 교환이 거부/차단됨. (현대 SPA 및 모바일 앱의 강제 보안 표준).

### 💡 문제 유형별 목차 전환 포인트
- **[모바일/B2C 서비스 최신 인증 아키텍처 묻는 유형]**: Ⅲ번의 ID Token(OIDC)과 Access Token(OAuth2.0)의 목적 분리를 명확히 비교하고, JSON(JWT) 기반 구조가 REST API 환경에서 갖는 무상태성(Stateless) 강점을 서술.
- **[SPA/모바일의 OAuth 보안 취약점 방어 대책]**: Ⅳ번에서 Implicit 방식이 사장된 배경을 설명하고, 이를 완전히 대체한 Ⅴ번의 인가 코드 + **PKCE (Proof Key)** 아키텍처를 토큰 가로채기 방어 관점에서 메인으로 도식화.
