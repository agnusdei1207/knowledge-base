## 1. 한눈에 이해하기 (Core Intuition)
- **정의**: 웹의 근간을 만드는 W3C(월드와이드웹 컨소시엄)가 제정한 글로벌 식별자 표준으로, 중앙 기관(국가, 구글 등)의 통제 없이 **개인이나 기계가 스스로 "내 이름(ID)은 이거야!"라고 무한대로 생성할 수 있고, 영원히 삭제당하지 않는 탈중앙화된 디지털 주민번호(식별 주소) 체계**입니다.
- **필요성**: 기존 인터넷에서는 "내 이름(도메인 주소나 아이디)"을 항상 누군가에게 빌려 써야 했습니다. 네이버 아이디는 네이버가 정지시키면 끝이고, `google.com` 도메인도 ICANN(중앙 기구)에 돈을 안 내면 압수당합니다. "남의 허락 없이 내가 스스로 통제하고, 서버가 망해도 영원히 사라지지 않는 나만의 식별자"가 필요해진 웹3.0(Web3)의 필연적 결과물입니다.
- **핵심 직관**: **"내가 직접 파서 쓰는 무인도 우체통 번호"**. 
  - 과거 (URI/URL): 정부(ICANN)가 구획을 나누고 번지를 지정해 준 집 주소입니다. 세금 안 내면 정부가 주소를 뺏어갑니다.
  - **DID**: 넓은 무인도(블록체인)에 내가 망치로 뚝딱뚝딱 우체통을 하나 세우고 겉에 `did:sov:1234abcd`라고 아무렇게나 고유한 페인트칠을 합니다. 이 주소는 누구의 허락도 받지 않았으므로 누구도 뺏을 수 없습니다(탈중앙화). 이 주소를 전 세계 표준 문법으로 정리한 것이 W3C DID 표준입니다.

## 2. 왜 중요한가? (Background & Value)
- **등장 배경**: 모바일 신분증(SSI)을 만들려고 보니, 내 신분증(VC) 안에 "이 신분증의 주인은 홍길동이다"라고 적어야 하는데, 동명이인이 너무 많았습니다. 그렇다고 국가 주민번호를 적으면 글로벌 호환이 안 되고 프라이버시가 침해됩니다. 전 세계 어디서든 유일무이하게 나를 특정할 수 있으면서도 특정 국가/기업에 종속되지 않는 고유한 텍스트 주소록(URI) 체계가 반드시 필요했습니다.
- **가치**: "영구적인 디지털 자아(Digital Persona)의 탄생". 이메일 주소나 휴대폰 번호는 바꾸면 옛날 지인들과 연락이 끊기지만, DID는 평생 뺏기지 않고 블록체인에 영원히 존재하므로 완전한 독립적 신원 생태계의 척추(Backbone) 역할을 합니다.

## 3. 어떻게 작동하는가? (Mechanism)
DID는 아주 단순한 텍스트 문자열(이름표)과 그 뒤에 숨겨진 설명서(Document)로 작동합니다.

1. **DID 포맷 (이름표 문자열)**
   - 항상 `did:` 로 시작하는 규칙을 가집니다.
   - 예: `did:sov:55GkHamJq1nv23g` 
   - 해석: `did(규격명)` : `sov(소브린 블록체인 네트워크를 쓴다는 뜻)` : `55Gk...(나의 고유한 난수 아이디)`
2. **DID 생성의 마법 (스스로 만들기)**
   - 사용자의 스마트폰 앱(지갑) 안에서 공개키/개인키 1쌍을 수학적으로 뚝딱 만듭니다.
   - 만들어진 공개키를 해시 믹서기에 넣고 돌려서 나온 난수(예: `55Gk...`)를 나의 DID로 선언합니다. 누구 허락도 필요 없고 0.1초면 수백 개도 만듭니다.
3. **DID Document (블록체인에 올리는 설명서)**
   - "내 DID는 `did:sov:55Gk...` 야. 그리고 나랑 안전하게 통신하려면 이 **[공개키]** 를 쓰고, 내 스마트폰 서버 **[엔드포인트 주소]** 로 연락해!" 라고 적힌 짧은 텍스트(JSON) 파일을 만듭니다.
   - 이 텍스트 파일을 전 세계 누구나 볼 수 있는 **블록체인 장부**에 업로드(등록)해 둡니다.
   - 이제 전 세계 어느 회사(검증자)든 내 DID 글자만 알면, 블록체인을 뒤져 내 공개키를 찾아내어 내 신분을 100% 검증할 수 있습니다.

## 4. 실전 활용 및 예시 (Real-world Application)
- **구체적 사례**: 
  - 내가 쇼핑몰(용도 A), 병원(용도 B), 회사(용도 C)에 내 신원 증명을 제출해야 합니다. 
  - 멍청한 방법: DID 하나를 파서 A, B, C에 다 씁니다. (A, B, C가 뒤에서 "어? 얘 똑같은 DID네?" 하고 정보를 합쳐버리면 내 동선이 추적당함).
  - 스마트한 방법 (DID의 존재 이유): 앱 버튼을 눌러 **쇼핑몰 제출용 DID 1개, 병원용 DID 1개, 회사용 DID 1개를 각각(총 3개) 따로 1초 만에 무료로 생성(Pairwise DID)** 해서 줍니다. 기업들은 서로 같은 사람인지 절대 추적할 수 없습니다. 이것이 DID가 주는 궁극의 프라이버시 보호입니다.
- **주의점 및 흔한 오해**: 
  - "DID는 블록체인 기술인가요?" $\rightarrow$ 엄밀히 말하면 **아닙니다.** W3C DID 표준은 "식별자 텍스트를 적는 문법 규칙"일 뿐입니다. DID를 블록체인에 저장하든, 깃허브(GitHub)에 저장하든, 일반 웹서버(`did:web`)에 저장하든 상관없이 자유롭게 쓰도록(Method-agnostic) 설계된 추상화된 표준 규격입니다.

## 5. 핵심 비교 및 연결 개념 (Relation)
- **도메인 네임 (DNS, `www.naver.com`)**: 특정 중앙 기관(ICANN)이 발급/삭제 통제권을 가짐. 서버 통신용.
- **분산 식별자 (DID, `did:sov:abc...`)**: 통제 기관 없음(탈중앙화). 암호학적 증명 기능 내장. 사람/사물/데이터의 영구적 식별용.

# ✍️ 단답형 / 서술형 시험장 출격 준비

### Ⅰ. 핵심 인사이트
- **본질**: W3C(월드와이드웹 컨소시엄)에서 제정한 인터넷 웹 표준 규격으로, 중앙 집중식 레지스트리(IdP나 ICANN 등)에 의존하지 않고 암호학적으로 생성/검증 가능한 **범용 식별자(URI) 문법(Syntax)과 해당 식별자를 리졸빙(Resolving)하기 위한 DID Document 데이터 모델 아키텍처.**
- **가치**: 검증가능 자격증명(VC/VP) 등 자기 주권 신원(SSI) 생태계에서 주체(Subject)를 영구적으로 식별할 수 있는 앵커(Anchor) 역할을 수행함. 특정 블록체인이나 프로토콜에 종속되지 않는 플랫폼 아그노스틱(Agnostic) 철학을 바탕으로, 디지털 세계 전반의 상호 운용성(Interoperability)을 담보하는 신원 식별의 척추(Backbone)임.
- **판단 포인트**: 아키텍처 설계 시 **DID 체계 자체는 본질적으로 '개인 식별(PII)'을 담지 않음**을 유의해야 합니다. DID는 암호학적 난수에 불과하며, 실질적인 개인정보(이름, 학위 등)는 VC 파일로 분리되어 사용자의 오프라인 단말기(Edge)에 저장되는 **데이터 궤적의 완전한 디커플링(Decoupling)** 이 이 사상의 심장입니다.

### Ⅱ. W3C DID 표준의 아키텍처 스키마 (Syntax 포맷)
모든 DID 식별자는 3단계의 직관적이고 표준화된 URI(Uniform Resource Identifier) 문자열 형태를 가짐.
- 포맷: `did:<method-name>:<method-specific-id>`
  1. **`did` (Scheme)**: 이 문자열이 일반 http나 ftp가 아닌 DID 규격임을 선언.
  2. **`method-name` (메서드 이름)**: 이 DID가 어느 네트워크/원장 인프라에서 작동하는지를 명시. (예: `sov`=Sovereign 블록체인, `ethr`=이더리움 블록체인, `web`=기존 웹서버).
  3. **`method-specific-id` (고유 식별 값)**: 해당 네트워크 내에서 주체를 특정하는 유일무이한 해시/난수 값. 보통 주체의 공개키(Public Key)를 해싱하여 자체 파생(Self-derivation) 생성함.

### Ⅲ. DID Document (DID 문서)의 구조와 역할
DID 문자열은 단순한 이름표일 뿐, 실질적인 암호학적 통신과 검증을 가능케 하는 것은 분산 원장(블록체인)에 기록되는 **DID Document (JSON-LD 파일)** 임.
- **핵심 구성 요소 3가지**:
  1. **`id`**: 이 문서가 설명하고 있는 DID 주소 원형 (Subject).
  2. **`verificationMethod` (암호학적 검증키)**: 가장 핵심. DID 소유자의 서명을 검증할 수 있는 **공개키(Public Key) 리스트**. (검증자 Verifier는 블록체인에서 이 문서를 읽어 공개키를 획득함).
  3. **`service` (서비스 엔드포인트)**: DID 소유자와 다음 단계의 통신(예: VC 제출 요청, 메시징)을 이어가기 위해 접속해야 할 오프라인 지갑 주소나 클라우드 에이전트의 네트워크 라우팅(URL) 정보.

### Ⅳ. DID 분산 구조의 핵심 아키텍처: 리졸버(Resolver)
- DNS 시스템에서 `www.google.com`을 입력하면 DNS 서버가 IP 주소를 반환(Resolving)하듯, DID 생태계에도 리졸빙 아키텍처가 필수적임.
- **DID Resolver / Universal Resolver**: 
  - 검증자(Verifier)가 특정 DID(`did:ethr:123...`)를 입력하면, 리졸버가 해당 네트워크(이더리움)의 블록체인 노드에 쿼리를 날려 매핑된 **'DID Document'를 긁어와 반환(Return)해 주는 중계 미들웨어.** 
  - 덕분에 검증자는 수십 개의 블록체인 메인넷 노드를 직접 다 구축할 필요 없이 단일 API로 통합 검증을 수행할 수 있음.

### Ⅴ. 결론 및 실무적 판단 포인트
- B2C 플랫폼 기획자는 프라이버시 보호 의무(Compliance) 방어를 위해 **'Pairwise DID(쌍방향 식별자)'** 아키텍처를 기본(Default)으로 적용해야 합니다. 사용자가 단 1개의 Public DID를 만들어 모든 서비스(A, B, C)에 돌려쓰면, 기업들이 뒷단에서 이 DID를 키(Key)값으로 조인하여 사용자의 동선을 추적하는 **연관성 분석(Correlation) 공격**이 발생합니다. 서비스에 가입할 때마다 매번 서로 다른 고유한 임시 DID를 1:1로 자동 생성하여 바인딩하는 아키텍처 구현이 W3C 표준 설계의 모범 사례입니다.

### 💡 문제 유형별 목차 전환 포인트
- **[웹3.0(Web3) 분산 신원(SSI) 인프라 구축을 위한 식별자 표준 설계]**: Ⅰ번 탈중앙화 개념과 Ⅱ번(Syntax)을 뼈대로 삼아, 기존 도메인(DNS) 기반 식별 체계가 갖는 단일 장애점(SPOF) 리스크를 어떻게 극복하는지 논증.
- **[암호학적 신뢰 구조 및 증명서(VC/VP) 검증을 위한 DID 리졸빙 메커니즘]**: Ⅲ번(DID Document의 공개키 배포 역할)을 집중 조명하고 Ⅳ번(Resolver) 파이프라인 흐름도를 서술하여, 블록체인이 어떻게 공개키 기반 인프라(PKI)의 분산 저장소 역할을 완벽히 수행하는지 기술적 증명.
