# 📖 【암기용】 개념 완전 이해

> 목적: ML-DSA CRYSTALS-Dilithium을 처음 봐도 완전하게 이해하게 만든다. 시험 답안 양식이 아니라, 이해를 위한 설명이다.

## 한눈에
- **개요**: 양자컴퓨터 공격에 대비한 NIST FIPS 204 전자서명 표준
- **왜 필요한가**: RSA·ECDSA 서명은 대규모 양자컴퓨터가 공개키에서 개인키를 유도할 수 있는 위험이 있다. ML-DSA는 인증서, 코드서명, 펌웨어 검증의 인증·무결성·부인방지를 PQC 기반으로 전환한다.
- **핵심 직관**: 서명자가 격자 난제 위에 위조하기 어려운 도장을 찍고, 검증자는 공개키로 도장의 수학적 일관성을 확인한다.

## 깊이 이해
- **배경·문제의식**: PQC 전환에서 키 교환은 ML-KEM, 서명은 ML-DSA가 담당한다. 인증서와 코드서명은 수년간 검증되므로 공격자가 지금 서명 검증 데이터를 저장해 두고 미래 양자컴퓨터로 위조를 시도할 수 있다.
- **작동 원리**: KeyGen으로 서명키와 검증키를 만들고, Sign은 메시지 해시와 서명키로 signature를 생성한다. Verify는 공개키, 메시지, signature의 관계를 검사한다. 기반 난제는 Module-LWE/Module-SIS 계열이다.
- **비유**: 봉인된 계약서에 회사 직인을 찍는 것과 같다. 누구나 직인 진위를 확인하지만, 직인을 새로 찍는 권한은 서명키 보유자에게만 있다.
- **구체 예시**: ML-DSA-65는 공개키 1952바이트, 개인키 4032바이트, 서명 3309바이트이며 인증서 체인과 코드서명 크기 증가를 설계에 반영해야 한다.
- **흔한 오해·주의점**: ML-DSA는 암호화 알고리즘이 아니다. 기밀성은 제공하지 않고 인증, 무결성, 부인방지 기능을 제공한다.

## 연결 개념
- ML-KEM — 세션키 합의용 PQC KEM
- X.509 인증서 — ML-DSA 공개키와 서명을 담는 인증 인프라
- 코드서명 — 펌웨어·소프트웨어 공급망 검증 적용처

## Ⅰ. 개요 및 필요성

- 개요: 격자 기반 전자서명
- 배경: RSA·ECDSA 서명은 양자컴퓨터 기반 이산로그·소인수분해 공격에 취약해 장기 검증이 필요한 코드·문서 서명에 위험을 남김.
- 필요성: ML-DSA는 NIST FIPS 204 표준으로 인증서, 문서, 코드, 펌웨어의 무결성과 서명자 인증을 PQC 기반으로 제공함.

---

## Ⅱ. 구조 및 구성요소

```text
Parameter Set -> KeyGen -> Signing Key / Verification Key
Message -> Hash -> Sign -> Signature
Message + Signature + Verification Key -> Verify -> Accept/Reject
/ HSM/KMS -> Key Access Control -> Audit Log
```

| 구성요소 | 역할 | 특이사항 |
|:---|:---|:---|
| KeyGen | 서명키·검증키 생성 | ML-DSA-44/65/87 선택 |
| Sign | 메시지에 서명 생성 | nonce·seed 관리, deterministic 처리 |
| Verify | 공개키로 서명 검증 | 메시지 변조·위조 서명 차단 |
| Key protection | 서명키 보관·접근 통제 | HSM, dual control, 감사로그 |

> 요약: ML-DSA는 KeyGen, Sign, Verify와 서명키 보호 체계가 결합될 때 인증·무결성·부인방지를 제공함.

---

## Ⅲ. 동작원리 및 흐름도

```text
서명키 생성 -> 메시지 해시 -> Sign
-> signature 배포 -> 공개키·메시지 수신
-> Verify -> 무결성·서명자 확인 -> 감사 기록
```

| 단계 | 처리 내용 | 검증 기준 |
|:---:|:---|:---|
| 1 | 파라미터와 키쌍 생성 | FIPS 204 KAT, ACVP 검증 |
| 2 | 메시지·컨텍스트 바인딩 | 해시 입력, domain separation |
| 3 | 서명 생성 | 서명키 HSM 접근 승인 |
| 4 | 서명 검증 | signature accept/reject, 변조 차단 |
| 5 | 증적 보관 | timestamp, signer ID, 감사로그 |

> 요약: ML-DSA는 메시지와 서명키를 결합해 signature를 만들고 공개키 검증으로 변조와 위조를 판정함.

## Ⅳ. 특징

| 구분 | RSA/ECDSA | ML-DSA | 판단 포인트 |
|:---|:---|:---|:---|
| 공격 모델 | 고전 컴퓨터 기반 | 양자컴퓨터 공격 포함 | 장기 검증 서명 우선 적용 |
| 표준 | FIPS 186-5 | NIST FIPS 204 | CNSA 2.0 서명 후보 |
| 크기 | ECDSA P-256 서명 64B | ML-DSA-65 서명 3309B | 인증서·패키지 크기 영향 |
| 적용처 | TLS, 코드서명 | PQC 인증서, 펌웨어 서명 | 검증 장비 메모리 제약 |

> 요약: ML-DSA는 서명 크기가 KB급으로 증가하므로 인증서 체인, OTA, 부트로더 메모리 조건을 함께 검토함.

## Ⅴ. 심화 비교 및 적용 판단

| 구분 | 기존/대안 | 본 키워드 | 선택 기준 |
|:---|:---|:---|:---|
| 구조 | ECDSA P-256 | ML-DSA-65 | 장기 검증·PQC 요구 |
| 비용/성능 | 64B 서명 | 3309B 서명 | 대역폭·저장소 허용치 |
| 운영/위험 | 기존 PKI 체인 | PQC 또는 hybrid 인증서 | CA·브라우저·검증기 호환성 |

> 요약: 공개 웹은 호환성 때문에 hybrid 인증서부터 검토하고, 코드서명·펌웨어는 장기 검증 요구에 따라 우선 전환함.

| 리스크 | 원인 | 대응 방안 | 확인 지표 |
|:---|:---|:---|:---|
| 서명키 유출 | HSM 미사용, 운영자 권한 과다 | HSM, M of N 승인, RBAC | 비인가 서명 0건 |
| 인증서 비대화 | ML-DSA 공개키·서명 크기 | chain 압축, OCSP stapling 테스트 | TLS handshake 실패 0.1% 이하 |
| 검증기 미지원 | 레거시 부트로더·JVM·TLS 스택 | dual-sign, canary 배포 | 검증 성공률 99.9% 이상 |

> 요약: ML-DSA 리스크는 키 보호, 크기 증가, 검증기 호환성으로 분류하고 HSM·dual-sign·단계 배포로 통제함.

| 점검 항목 | 목표 기준 | 측정 방법 |
|:---|:---|:---|
| 표준 적합성 | FIPS 204 KAT 100% 통과 | ACVP, 테스트 벡터 |
| 서명 운영 | HSM 서명키 저장, dual control | 감사로그, 권한 리뷰 |
| 검증 품질 | 위조·변조 서명 reject 100% | negative test, CI 검증 |

> 요약: ML-DSA 도입 효과는 FIPS 검증 통과, 서명키 접근 감사, 위조 서명 차단으로 판단함.

## Ⅵ. 실무 적용 및 결론

**적용 방안 3개 (필수 — 단계별 또는 항목별):**
1. 코드서명·펌웨어·인증서 발급 시스템의 RSA/ECDSA 사용처를 inventory화하고 장기 검증 대상부터 ML-DSA-65 파일럿 적용.
2. HSM 기반 서명키 생성·보관, M of N 승인, timestamp authority 연계, 서명 감사로그 1년 이상 보관.
3. legacy verifier를 고려해 ECDSA+ML-DSA dual-sign을 적용하고 검증 실패율 0.1% 이하까지 canary 배포.

**결론 (2줄):**
- 기술사 판단: ML-DSA는 기밀성 기술이 아니라 인증·무결성·부인방지 기술이므로 인증서·코드서명·펌웨어 검증에 우선 적용함.
- 향후 방향: FIPS 204와 CNSA 2.0 기준으로 CA, HSM, 빌드 파이프라인의 서명 알고리즘 민첩성을 확보해야 함.
