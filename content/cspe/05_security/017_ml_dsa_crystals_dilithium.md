# 📖 【암기용】 개념 완전 이해

## 한눈에
- **개요**: **ML-DSA는 격자 난제(Module-LWE·Module-SIS)에 기반한 NIST FIPS 204 전자서명 표준으로, 인증서·코드서명·펌웨어의 인증·무결성·부인방지를 양자내성으로 제공함**. 양자위협·PQC 전반은 (015 참조).
- **왜 필요한가**: 기존 서명 RSA·ECDSA(008)는 Shor 알고리즘이 공개키에서 개인키를 유도해 위조가 가능해지는데, ML-DSA는 격자 난제로 같은 서명 역할을 대체하기 때문임.
- **핵심 직관**: 서명자가 격자 위에 "위조하기 어려운 도장"을 찍고, 검증자는 공개키로 도장의 수학적 일관성을 확인함 — ECDSA의 "곡선 위 nonce 계산" 대신 "격자 위 잡음 낀 계산"을 씀.

## 핵심 용어 정리 (내부에 등장하는 것들)

답안(Ⅰ~Ⅵ·표)에 나오는 표기·연산을 비유와 함께 먼저 풀어 둠. 상위 핵심 키워드는 **DSA(Digital Signature Algorithm, 전자서명)** 로, 개인키로 서명하고 공개키로 위조·변조를 판정하는 방식임.

| 용어/표기 | 의미 | 비유·예 |
|:---|:---|:---|
| Module-LWE | 잡음 낀 선형식 복원의 어려움 | 오차 낀 방정식 되풀기 |
| Module-SIS | 격자에서 짧은 정수해 찾기의 어려움 | 촘촘한 격자에서 짧은 지름길 찾기 |
| KeyGen | 서명키·검증키 쌍 생성 | 도장과 진위확인표 제작 |
| Sign | 메시지 해시에 서명키로 signature 생성 | 계약서에 직인 찍기 |
| Verify | 공개키·메시지·서명 관계 검사 | 직인 진위 확인 |
| Fiat-Shamir | 대화형 증명을 해시로 비대화형 서명화 | 문답을 도장 하나로 압축 |
| rejection sampling | 개인키 누출 없게 부적합 서명을 재추첨 | 흠집난 도장 버리고 다시 찍기 |
| ML-DSA-44/65/87 | 보안강도별 파라미터(범주 2/3/5) | 직인 등급 하/중/상 |
| 부인방지 | 서명자가 서명 사실을 부인 못하게 함 | 찍은 직인은 발뺌 불가 |
| dual-sign | 기존+PQC 서명을 함께 붙임(하이브리드) | 직인 두 개 병용 |
| HSM | 서명키를 하드웨어에 보관·연산 | 금고 안 도장 |

## 깊이 이해
- **배경·문제의식**: PQC 전환에서 키교환은 ML-KEM(016), 서명은 ML-DSA가 담당함. 인증서·코드서명은 수년~수십년 검증되므로 공격자가 지금 데이터를 저장해 두고 미래 양자컴퓨터로 위조를 시도할 수 있어 서명도 양자내성이 필요함. 원래 공모명은 CRYSTALS-Dilithium, 2024년 8월 FIPS 204로 확정됨.
- **작동 원리(어떻게+왜)**: KeyGen으로 서명키·검증키를 만들고, Sign은 메시지 해시와 서명키로 signature를 생성하되 개인키 정보가 새지 않게 rejection sampling으로 부적합 후보를 버리고 재추첨함. 안전성은 Module-LWE/Module-SIS와 Fiat-Shamir 변환에 있음. Verify는 공개키·메시지·서명의 수학 관계를 검사해 accept/reject를 냄.
- **비유**: 봉인된 계약서에 회사 직인을 찍는 것과 같음 — 누구나 진위를 확인하지만, 직인을 새로 찍는 권한(서명키)은 보유자에게만 있음.
- **구체 예시**: ML-DSA-65는 공개키 1952B, 개인키 4032B, 서명 3309B로, ECDSA P-256 서명 64B 대비 약 50배임. 인증서 체인·펌웨어 패키지 크기 증가를 설계에 반영해야 함.
- **흔한 오해·주의점**: (1) ML-DSA는 암호화가 아님 — 기밀성은 없고 인증·무결성·부인방지만 제공함. (2) ML-KEM과 역할이 다름(키교환 아님). (3) "Dilithium"만 쓰고 FIPS 204를 빠뜨리면 표준 인지 부족으로 보임.

## 연결 개념
- ECDSA·전자서명 — ML-DSA가 대체하는 기존 서명 방식 (008 참조)
- ML-KEM — 서명이 아닌 키교환을 담당하는 격자 표준 (016 참조)
- SLH-DSA — 격자 대신 해시 기반으로 서명하는 보완 표준 (018 참조)

# 📝 【답안용】 시험 답안 템플릿

> 1. **본질**: ML-DSA는 CRYSTALS-Dilithium 기반 NIST FIPS 204 격자(Module-LWE/SIS) 전자서명 표준임.
> 2. **가치**: Shor에 취약한 RSA·ECDSA를 대체해 인증서·코드서명·펌웨어의 인증·무결성·부인방지를 양자내성으로 제공함.
> 3. **판단 포인트**: ML-DSA-44/65/87 파라미터·서명 크기 증가·서명키 HSM 보호·인증서 체인 전환을 함께 판단함이 관건임.

| 운영 적용 판단 | X.509·코드서명·HSM·서명 크기 | 알고리즘만 쓰고 키보호·검증 누락 |

## Ⅰ. 개요 및 필요성

- 개요: 격자 난제로 위조를 막는 양자내성 전자서명임.
- 배경: RSA·ECDSA 서명은 Shor 알고리즘에 무력화돼 장기 검증 코드·문서 서명에 위조 위험을 남김(015).
- 필요성: NIST FIPS 204 표준으로 인증서·문서·코드·펌웨어의 서명자 인증과 무결성을 PQC 기반으로 제공함.
- 전제: 양자위협·PQC 개괄은 (015 참조), 키교환은 (016 참조)로 위임하고 격자 서명에 집중함.

---

## Ⅱ. 구조 및 구성요소

```text
Parameter Set(44/65/87) -> KeyGen -> 서명키 / 검증키
Message -> Hash -> Sign(rejection sampling) -> Signature
Message + Signature + 검증키 -> Verify -> Accept/Reject
  / HSM/KMS -> 서명키 접근통제 -> 감사로그
```

| 구성요소 | 역할 | 특이사항 |
|:---|:---|:---|
| KeyGen | 서명키·검증키 생성 | ML-DSA-44/65/87 선택 |
| Sign | 메시지에 서명 생성 | rejection sampling, domain separation |
| Verify | 공개키로 서명 검증 | 변조·위조 서명 차단 |
| Key protection | 서명키 보관·접근 통제 | HSM·dual control·감사로그 |

> 요약: ML-DSA는 KeyGen·Sign·Verify 3연산과 서명키 보호 체계가 결합될 때 인증·무결성·부인방지를 제공함.

---

## Ⅲ. 동작원리 및 흐름도

```text
서명키 생성 -> 메시지 해시 -> Sign(재추첨)
  -> signature 배포 -> 검증자 공개키·메시지 수신
  -> Verify -> 무결성·서명자 확인 -> 감사 기록
```

1. 발급자가 KeyGen으로 서명키·검증키를 만들고 서명키를 HSM에 보관함.
2. 서명자가 메시지 해시에 서명키로 Sign을 수행하되 rejection sampling으로 개인키 누출을 차단함.
3. 검증자가 공개키·메시지·signature로 Verify를 수행해 변조·위조 시 reject를 냄.
4. 서명 시각·서명자 ID·검증 결과를 감사로그에 남겨 부인방지 증적을 확보함.

> 요약: 메시지 해시와 서명키를 결합해 signature를 만들고, 공개키 검증으로 변조·위조를 판정하며 증적을 남김.

---

## Ⅳ. 특징

- 난제 전환: 이산로그·소인수분해가 아닌 격자 Module-LWE/SIS에 안전성을 둬 Shor에 견딤.
- 서명 전용: 인증·무결성·부인방지만 제공하며 기밀성은 없음(암호화는 대칭·ML-KEM 담당).
- 개인키 보호 설계: rejection sampling으로 서명에서 서명키 정보가 새지 않게 함.
- 크기 증가: 서명이 KB급(ML-DSA-65 3309B)이라 인증서 체인·OTA 패키지 부담이 있음.
- dual-sign 병용: 레거시 검증기 호환을 위해 ECDSA+ML-DSA를 함께 붙일 수 있음.
- 표준 확립: 2024년 FIPS 204 확정으로 KAT·ACVP 적합성 검증 근거가 있음.

## Ⅴ. 심화 비교 및 적용 판단

기존 서명 ECDSA와 ML-DSA를 안전근거·양자내성·크기 축으로 비교함(다대상×다축이므로 표 사용).

| 구분 | ECDSA(P-256) | ML-DSA-65 |
|:---|:---|:---|
| 안전 근거 | 타원곡선 이산로그 | 격자 Module-LWE/SIS |
| 양자내성 | Shor로 파훼 | 현재까지 양자내성 |
| 서명 크기 | 64B | 3309B |
| 공개키 크기 | 33B(압축) | 1952B |
| 표준 | FIPS 186-5 | FIPS 204(CNSA 2.0 후보) |

> 요약: ML-DSA는 서명이 KB급으로 커지므로 장기 검증 코드·펌웨어에 우선 적용하고, 호환성 부담은 dual-sign으로 흡수함.

리스크는 불릿으로 정리함.
- 리스크: 서명키 유출 — 원인: HSM 미사용·운영자 권한 과다 — 대응: HSM·M-of-N 승인·RBAC, 비인가 서명 0건.
- 리스크: 인증서 비대화 — 원인: ML-DSA 공개키·서명 크기 — 대응: chain 압축·OCSP stapling 시험, handshake 실패 0.1% 이하.
- 리스크: 검증기 미지원 — 원인: 레거시 부트로더·JVM·TLS 스택 — 대응: dual-sign·canary 배포, 검증 성공률 99.9%↑.

지표는 불릿으로 정리함.
- 지표: 표준 적합성 — 목표: FIPS 204 KAT 100% 통과 — 측정: ACVP·테스트 벡터.
- 지표: 서명 운영 — 목표: 서명키 HSM 저장·dual control — 측정: 감사로그·권한 리뷰.
- 지표: 검증 품질 — 목표: 위조·변조 서명 reject 100% — 측정: negative test·CI 검증.

## Ⅵ. 실무 적용 및 결론

**적용 방안 3개 (필수 — 단계별 또는 항목별):**
1. 코드서명·펌웨어·인증서 발급의 RSA/ECDSA 사용처를 inventory화하고, 장기 검증 대상부터 ML-DSA-65 파일럿 적용.
2. HSM 기반 서명키 생성·보관, M-of-N 승인, timestamp authority 연계, 서명 감사로그 1년↑ 보관.
3. 레거시 검증기 대비 ECDSA+ML-DSA dual-sign을 적용하고 검증 실패율 0.1% 이하까지 canary 배포.

**결론 (2줄):**
- 기술사 판단: ML-DSA는 기밀성 기술이 아니라 인증·무결성·부인방지 기술이므로 인증서·코드서명·펌웨어 검증에 우선 적용함.
- 향후 방향: FIPS 204·CNSA 2.0 기준으로 CA·HSM·빌드 파이프라인의 서명 알고리즘 민첩성을 확보해야 함.
