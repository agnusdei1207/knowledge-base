# 📖 【암기용】 개념 완전 이해

## 한눈에
- **개요**: **인증서 폐지는 유효기간 전이라도 키 유출·오발급된 인증서를 무효화하는 절차로, 일괄 목록(CRL)·실시간 조회(OCSP)·서버 첨부(OCSP Stapling)로 확인**함. 인증서 필드·CDP/AIA는 (010 X.509 참조), CA·발급 절차는 (011 참조).
- **왜 필요한가**: 인증서는 유효기간이 있지만 그 전에 개인키가 유출되면 즉시 무효화가 필요함. 검증자는 서명·유효기간이 정상이어도 "이미 폐지되었는가"를 별도 확인해야 위조 인증서를 거부할 수 있음.
- **핵심 직관**: 분실 신고된 신분증과 같음. 발급일·만료일이 멀쩡해도 분실 대장(CRL)이나 즉시 조회 창구(OCSP)로 "이미 무효"임을 확인해야 함.

## 핵심 용어 정리 (내부에 등장하는 것들)

답안에 등장하는 폐지 채널·상태·실패 정책을 먼저 풀어 둠. 상위 핵심 키워드는 **폐지 확인(revocation checking)** 으로, 서명·유효기간 검증과 별개의 단계임.

| 용어/표기 | 의미 | 비유·예 |
|:---|:---|:---|
| 폐지(revocation) | 만료 전 인증서를 무효 처리 | 분실 신분증 사용정지 |
| CRL | CA가 서명·게시하는 폐지 인증서 목록 | 분실 신분증 대장 |
| Delta CRL | 직전 이후 변경분만 담은 증분 목록 | 대장의 변경분 부록 |
| OCSP | 인증서 상태를 실시간 조회하는 프로토콜 | 즉시 조회 창구 |
| OCSP Responder | 상태 응답을 서명해 주는 서버 | 창구 담당관 |
| good/revoked/unknown | 정상 / 폐지됨 / 미상 응답 | 유효 / 정지 / 확인불가 |
| OCSP Stapling | 서버가 OCSP 응답을 받아 핸드셰이크에 첨부 | 가게가 "정상" 확인증 대신 제시 |
| Must-Staple | 스테이플링 미첨부 시 거부하도록 강제 | "확인증 없으면 입장 불가" |
| Soft-fail/Hard-fail | 조회 실패 시 통과 / 차단 | 확인 불가 시 봐줌 / 막음 |
| reasonCode | 폐지 사유(keyCompromise 등) | 정지 사유란 |
| Nonce | 응답 재사용 방지용 일회성 값 | 매번 다른 확인 도장 |
| CRLite/CRLSet | 브라우저가 폐지 정보를 사전 배포하는 방식 | 미리 받아둔 분실 대장 요약 |

## 깊이 이해
- **배경·문제의식**: 폐지 확인은 PKI에서 가장 취약한 고리임. CRL은 목록이 커질수록 다운로드 부담이 크고 갱신 주기만큼 지연이 생김. OCSP는 실시간이지만 매 접속마다 CA에 조회해 지연·프라이버시(방문 사이트 노출)·응답기 가용성 문제가 있음.
- **작동 원리(어떻게+왜)**: CRL은 CA가 폐지된 serialNumber·폐지시각·사유를 모아 서명·게시하고 검증자가 CDP에서 내려받아 대조함. OCSP는 검증자가 AIA의 responder에 serialNumber를 물어 서명된 good/revoked/unknown을 받음. Stapling은 서버가 미리 OCSP 응답을 받아 TLS 핸드셰이크에 첨부해 클라이언트 조회·지연·프라이버시 문제를 동시에 완화함.
- **비유**: CRL은 매장에 비치된 두꺼운 분실카드 책자(주기적 교체), OCSP는 결제 때마다 카드사에 거는 승인 전화, Stapling은 가게가 미리 받아 둔 "이 카드 정상" 확인증을 손님에게 보여주는 방식임.
- **구체 예시**: 브라우저 대다수는 성능·가용성 문제로 OCSP를 soft-fail로 처리해 응답기 장애 시 그냥 통과함 — 공격자가 OCSP를 차단하면 폐지 확인이 무력화됨. 이 때문에 Chrome은 CRLSet, Firefox는 CRLite로 폐지 정보를 사전 배포하고, 업계는 짧은 수명 인증서로 폐지 의존을 줄이는 방향으로 이동 중임.
- **흔한 오해·주의점**: (1) 서명·유효기간이 정상이어도 폐지 확인을 빼면 유출된 인증서를 수용하게 됨. (2) soft-fail은 사실상 폐지 확인을 우회 가능하게 함 — Must-Staple로 hard-fail을 강제해야 실효가 있음. (3) OCSP Stapling은 프라이버시를 개선하지만 CA가 아니라 서버가 응답을 캐시·첨부하는 것임.

## 연결 개념
- X.509 CDP/AIA — CRL 배포지점·OCSP responder 위치를 담은 확장 (010 참조)
- CA — 폐지 목록·OCSP 응답을 서명·게시하는 주체 (011 참조)
- TLS 핸드셰이크 — Stapling이 첨부되는 지점 (013·014 참조)

> 2. **가치**: 키 유출·오발급 인증서를 차단해 서명·유효기간 검증만으로 놓치는 위조를 막음.
> 3. **판단 포인트**: soft-fail 우회와 성능·프라이버시 한계 때문에 Stapling·Must-Staple·짧은 수명이 실효 관건임.

## Ⅰ. 개요 및 필요성

- 개요: 만료 전 인증서를 무효화하고 그 상태를 확인하는 절차임.
- 배경: 인증서는 유효기간이 있으나 개인키 유출·오발급 시 즉시 무효화가 필요함.
- 필요성: 검증자는 서명·유효기간이 정상이어도 CRL·OCSP로 폐지 여부를 별도 확인해야 위조를 거부함.
- 전제: 인증서 필드·CDP/AIA·CA는 (010·011 참조)로 위임하고 폐지 확인 방식·실효성에 집중함.

---

## Ⅱ. 구조 및 구성요소

```text
CA -> 폐지 등록(serial·시각·reasonCode)
  / CRL: CDP에 서명 목록 게시 -> 검증자 다운로드·대조
  / OCSP: AIA responder -> 검증자 조회 -> good/revoked/unknown
  / Stapling: 서버가 OCSP 응답 미리 수신 -> TLS 핸드셰이크에 첨부
```

| 구성요소 | 역할 | 특이사항 |
|:---|:---|:---|
| CRL | 폐지 목록 게시 | 크기 증가·주기 지연, Delta CRL로 보완 |
| OCSP Responder | 실시간 상태 응답 | 서명 응답, 가용성·프라이버시 이슈 |
| OCSP Stapling | 서버가 응답 첨부 | 클라 조회·지연·프라이버시 완화 |
| Must-Staple | 미첨부 시 거부 강제 | soft-fail 우회 차단 |
| reasonCode | 폐지 사유 표기 | keyCompromise·cACompromise 등 |
| CRLite/CRLSet | 폐지정보 사전 배포 | 브라우저 성능·가용성 개선 |

> 요약: 폐지는 CA 등록을 기점으로 CRL(일괄)·OCSP(실시간)·Stapling(첨부)의 세 확인 채널로 전달됨.

---

## Ⅲ. 동작원리 및 흐름도

```text
CA 폐지 등록 -> (CRL 게시 | OCSP responder 갱신)
검증자: 서명·유효기간 확인 -> 폐지 확인
  CRL: CDP 다운로드 -> serial 포함 여부 대조
  OCSP: responder 조회 -> good이면 신뢰, revoked면 차단
  Stapling: 서버 첨부 응답 검증 -> Must-Staple면 미첨부 시 차단
```

1. CA가 사고 인증서의 serialNumber·폐지시각·reasonCode를 폐지 목록·OCSP 상태로 등록함.
2. 검증자가 인증서 서명·유효기간을 통과시킨 뒤 CDP·AIA를 보고 폐지 확인 채널을 선택함.
3. CRL 방식은 목록에서 serial 포함 여부를, OCSP 방식은 responder의 서명된 good/revoked 응답을 확인함.
4. 검증자가 revoked면 연결을 차단하고, OCSP 조회 실패 시 soft-fail은 통과·Must-Staple은 차단으로 처리함.

> 요약: 검증자는 서명·유효기간 통과 후 CRL/OCSP로 폐지를 확인하며, 실패 처리 정책(soft/hard-fail)이 실효를 좌우함.

---

## Ⅳ. 특징

- 독립 단계: 폐지 확인은 서명·유효기간 검증과 별개로, 이를 빼면 유출 인증서를 수용하게 됨.
- 트레이드오프: CRL은 캐시·가용성이 좋지만 지연·크기, OCSP는 실시간이지만 조회 부하·프라이버시가 약점임.
- 실패 정책 의존: soft-fail은 응답기 장애 시 사실상 폐지 확인을 우회해 Must-Staple로 hard-fail을 강제해야 함.
- 프라이버시: OCSP 조회는 방문 사이트를 CA에 노출하며 Stapling이 이를 완화함.
- 대안 이동: 짧은 수명 인증서·CRLite/CRLSet 사전 배포로 실시간 조회 의존을 줄이는 추세임.

## Ⅴ. 심화 비교 및 적용 판단

폐지 확인 방식(CRL·OCSP·OCSP Stapling)을 지연·프라이버시·가용성 축으로 비교함(다대상×다축이므로 표 사용).

| 구분 | CRL | OCSP | OCSP Stapling |
|:---|:---|:---|:---|
| 최신성·지연 | 갱신 주기만큼 지연 | 실시간 조회 | 서버 캐시 주기만큼 최신 |
| 프라이버시 | 노출 없음 | 방문 사이트 CA 노출 | 클라 조회 없어 노출 없음 |
| 성능·가용성 | 목록 클수록 부담 | 매 접속 조회 부하 | 서버가 대신 조회, 클라 부담 없음 |

> 요약: 대규모 웹 서비스는 OCSP Stapling+Must-Staple, 폐쇄망·오프라인 검증은 CRL, 실시간 개별 조회가 꼭 필요할 때만 OCSP 직접 조회를 택함.

리스크 관리는 불릿으로 정리함.
- 리스크: 폐지 확인 우회 — 원인: OCSP soft-fail·응답기 차단 — 대응: Must-Staple·hard-fail 적용, 폐지 인증서 수용 0건.
- 리스크: 폐지 지연 — 원인: CRL 주기 과대·OCSP 캐시 과길이 — 대응: 주기 단축·짧은 수명 인증서, 폐지 반영 1시간 이하.
- 리스크: 응답기 장애 — 원인: OCSP 단일화 — 대응: responder 이중화·CDN 캐시, OCSP 가용성 99.9%.

지표 관리도 불릿으로 정리함.
- 지표: 폐지 반영 시간 — 목표: 등록 후 1시간 내 확인 가능 — 측정: 폐지-반영 지연 모니터링.
- 지표: 확인 실효성 — 목표: Must-Staple·hard-fail 적용률 — 측정: TLS 스캔·핸드셰이크 로그.
- 지표: 채널 가용성 — 목표: OCSP/CRL 응답 99.9%↑ — 측정: responder·CDP 헬스체크.

## Ⅵ. 실무 적용 및 결론

**적용 방안 3개 (필수 — 단계별 또는 항목별):**
1. 확인 실효화: 공개 웹 서비스는 OCSP Stapling 활성화, 고신뢰 서비스는 Must-Staple로 hard-fail 강제.
2. 폐지 신속화: 짧은 수명 인증서(단기 유효)와 CRL 주기 단축으로 폐지-반영 지연을 1시간 이하로 관리.
3. 가용성 확보: OCSP responder·CRL 배포를 CDN·이중화하고 브라우저 CRLite/CRLSet 사전 배포를 활용.

**결론 (2줄):**
- 기술사 판단: 대규모 공개 서비스는 Stapling+짧은 수명으로 폐지 의존을 줄이고, 폐쇄·오프라인 검증은 CRL을 유지함.
- 향후 방향: 실시간 OCSP 의존을 낮추고 CRLite·단기 인증서·자동 갱신 중심으로 폐지 체계를 전환하는 것이 필요함.
