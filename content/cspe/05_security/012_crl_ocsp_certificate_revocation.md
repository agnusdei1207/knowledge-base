# 📖 【암기용】 개념 완전 이해

> 목적: 인증서 폐지를 처음 봐도 만료 전 인증서를 왜 무효화해야 하는지 이해하게 만든다. 시험 답안 양식이 아니라, 이해를 위한 친절한 설명이다.

## 한눈에
- **개요**: CRL·OCSP는 유효기간이 남은 인증서의 무효 상태를 클라이언트가 확인하는 방법
- **왜 필요한가**: 서버 개인키 유출, 도메인 소유권 변경, 오발급이 발생하면 인증서 만료일까지 기다릴 수 없음
- **핵심 직관**: 인증서 유효기간은 신분증 만료일이고, CRL·OCSP는 분실 신고 명단 조회임

## 깊이 이해
- **배경·문제의식**: 인증서는 발급 시점에는 정상이어도 운영 중 개인키가 유출될 수 있음. 공격자가 유출 키와 인증서를 사용하면 브라우저는 폐지 정보를 확인하지 않는 한 정상 서버로 오인함
- **작동 원리**: CRL은 CA가 폐지된 인증서 일련번호 목록을 주기적으로 서명해 배포함. OCSP는 클라이언트가 특정 인증서 상태를 Responder에 질의하고 good, revoked, unknown 응답을 받는 방식임
- **비유**: CRL은 분실 카드 전체 목록 PDF를 내려받는 방식이고, OCSP는 카드번호 1개를 콜센터에 조회하는 방식임
- **구체 예시**: TLS 서버는 OCSP Stapling으로 CA 응답을 핸드셰이크에 첨부해 클라이언트의 별도 외부 질의를 줄임
- **흔한 오해·주의점**: 인증서 폐지는 암호화 강도 문제가 아니라 신뢰 상태 문제임. AES-256 채널이어도 폐지된 인증서를 신뢰하면 중간자 공격을 막지 못함

## 연결 개념
- CA 인증 기관 - 폐지 목록을 서명하고 OCSP 응답자를 운영하는 주체
- X.509 인증서 - CRL Distribution Point와 Authority Information Access 확장에 폐지 조회 위치 포함
- TLS 1.3 - 인증서 검증 단계에서 폐지 상태와 호스트명을 확인함

# 📝 【답안용】 시험 답안 템플릿

> 목적: 시험장에서 25분에 그대로 쓰는 답안 양식. 작성방식(추상표현 금지·수치·도식·문제유형 전환)을 엄격히 지킨다.
> 핵심: 폐지 문제는 CRL과 OCSP 기능 나열보다 실시간성, 가용성, 개인정보 노출, fail-open 위험을 비교해야 득점함.

## 핵심 인사이트 (3줄 요약)

> 1. **본질**: CRL·OCSP는 X.509 인증서가 만료 전 폐지되었는지 확인해 신뢰사슬의 현재성을 보장하는 검증 체계임.
> 2. **가치**: 개인키 유출·오발급·권한 철회 시 인증서 악용 시간을 CRL 주기 또는 OCSP SLA 범위로 제한함.
> 3. **판단 포인트**: CRL은 배포 부하, OCSP는 응답자 가용성·프라이버시·Stapling 적용 여부가 핵심 비교축임.

## 출제 의도 및 답안 포인트

| 출제 의도 | 반드시 짚을 핵심 | 감점 회피 포인트 |
|:---|:---|:---|
| 폐지 필요성 확인 | 키 유출, 오발급, 권한 상실, CA 폐쇄 | 만료와 폐지 개념 혼동 금지 |
| CRL·OCSP 비교 | 목록 배포 vs 실시간 질의, thisUpdate/nextUpdate, nonce, Stapling | 둘 중 하나만 설명하는 답안 금지 |
| 운영 보안 판단 | fail-open, 캐시, 응답자 장애, 개인정보 노출 | OCSP가 항상 실시간이라는 단정 금지 |

> 요약: 인증서 폐지는 암호 알고리즘 문제가 아니라 신뢰 상태를 시간 기준으로 통제하는 운영 보안 문제임.

## Ⅰ. 개요 및 필요성

인증서 폐지는 만료 전 신뢰 철회 절차임.
개인키 유출·오발급·도메인 권한 상실이 발생하면 인증서를 즉시 무효화해야 함. CRL과 OCSP는 클라이언트가 인증서 상태를 확인해 중간자 공격과 위조 서버 접속을 차단하는 핵심 통제임.

---

## Ⅱ. 구조 및 구성요소

```text
CA 폐지 결정 -> CRL 생성/서명 -> Repository 배포 -> 클라이언트 다운로드 검증
CA 폐지 결정 -> OCSP DB 반영 -> Responder 질의/응답 -> 클라이언트 상태 판단
                                  +-> OCSP Stapling
```

| 구성요소 | 역할 | 특이사항 |
|:---|:---|:---|
| CRL | 폐지 인증서 일련번호 목록 | CA 서명, thisUpdate·nextUpdate, 목록 크기 증가 |
| OCSP Responder | 인증서 1건 상태 질의 응답 | good·revoked·unknown, 서명 응답 |
| CDP/AIA | 인증서 내 폐지 조회 위치 | CRL Distribution Point, Authority Information Access |
| OCSP Stapling | 서버가 OCSP 응답 첨부 | 클라이언트 외부 질의 감소, 응답 갱신 필요 |
| Client Validator | 체인·폐지·호스트명 검증 | fail-open/fail-closed 정책 결정 |

> 요약: 폐지 구조는 CA의 상태 결정, 배포 채널(CRL/OCSP), 클라이언트 검증 정책으로 구성됨.

---

## Ⅲ. 동작원리 및 흐름도

```text
인증서 수신 -> 체인/유효기간/SAN 검증 -> CDP/AIA 조회
-> CRL 다운로드 또는 OCSP 질의 -> 서명/시간 검증 -> good/revoked/unknown 판단
-> 연결 허용 또는 차단/경보
```

| 단계 | 처리 내용 | 검증 기준 |
|:---:|:---|:---|
| 1 | 인증서 기본 검증 | Issuer 서명, NotBefore/NotAfter, SAN 일치 |
| 2 | 폐지 위치 확인 | CDP URL, AIA OCSP URL 존재 |
| 3 | CRL 또는 OCSP 상태 조회 | CRL 서명, OCSP responder 서명 |
| 4 | 응답 시간성 확인 | thisUpdate, nextUpdate, producedAt |
| 5 | 정책 적용 | revoked 차단, unknown·timeout 처리 기준 |

> 요약: 폐지 검증은 인증서 체인 검증 후 상태 조회와 응답 시간성 검증을 거쳐 허용·차단 정책으로 연결됨.

## Ⅳ. 특징

| 구분 | CRL | OCSP | 수치·표준 판단 |
|:---|:---|:---|:---|
| 조회 방식 | 폐지 목록 다운로드 | 인증서 1건 상태 질의 | RFC 5280, RFC 6960 |
| 지연 특성 | nextUpdate 주기 의존 | Responder 응답 SLA 의존 | CRL 수 MB 가능, OCSP p95 500ms 목표 |
| 개인정보 | 조회 대상 노출 적음 | CA가 방문 사이트 추정 가능 | OCSP Stapling으로 질의 노출 감소 |
| 장애 처리 | 캐시로 지속 검증 | timeout 시 fail-open 빈번 | 고위험 시스템은 fail-closed 검토 |

> 요약: CRL은 대량 배포 비용, OCSP는 실시간 질의 장애와 개인정보 노출을 기준으로 선택해야 함.

## Ⅴ. 심화 비교 및 적용 판단

| 비교 축 | 기존/대안 | CRL·OCSP 폐지 | 선택 기준 |
|:---|:---|:---|:---|
| 상태 확인 | 만료일만 확인 | 만료 전 폐지 상태 확인 | 공개 TLS·코드서명·mTLS 필수 |
| 비용/성능 | 조회 없음 | CRL 다운로드 또는 OCSP 왕복 | 고트래픽 웹은 OCSP Stapling 선택 |
| 운영/위험 | 폐지 반영 지연 | 캐시·응답자 SLA·fail 정책 필요 | 금융·관리자 접속은 fail-closed 우선 |

> 요약: 인증서 폐지는 연결 지연과 신뢰 현재성의 교환관계이며, 서비스 위험도에 따라 fail 정책을 정해야 함.

| 리스크 | 원인 | 대응 방안 | 확인 지표 |
|:---|:---|:---|:---|
| 폐지 지연 | CRL nextUpdate 길이, OCSP DB 반영 지연 | 폐지 SLA 24시간 이내, 긴급 폐지 절차 | 폐지 요청부터 응답 반영 시간 |
| Responder 장애 | OCSP 단일 장애점 | 다중 리전, CDN, Stapling 캐시 | OCSP 가용성 99.9%, p95 500ms |
| fail-open 악용 | timeout 시 연결 허용 | 고위험 서비스 fail-closed, Must-Staple 검토 | timeout 허용률, 차단 로그 |

> 요약: 폐지 운영의 핵심 위험은 지연·장애·fail-open이며, SLA와 모니터링으로 통제함.

| 점검 항목 | 목표 기준 | 측정 방법 |
|:---|:---|:---|
| 폐지 반영 | revoked 상태 24시간 이내 배포 | CRL/OCSP 샘플링, thisUpdate 확인 |
| 응답 품질 | OCSP p95 500ms, 오류율 0.1% 이하 | Synthetic monitoring, access log |
| 정책 준수 | Stapling 적용률 95% 이상 | TLS 스캐너, 서버 설정 점검 |

> 요약: 폐지 체계 성공 여부는 반영 시간, OCSP 응답 품질, Stapling 적용률로 판단함.

## Ⅵ. 실무 적용 및 결론

**적용 방안 3개 (필수 - 단계별 또는 항목별):**
1. 공개 TLS: OCSP Stapling 적용, CRL URL 유지, 만료·폐지 모니터링을 CI/CD 배포 전 검사에 포함
2. 내부 PKI: 짧은 수명 인증서(24시간~30일)와 CRL/OCSP 병행, 관리자·결제 채널은 fail-closed 정책 적용
3. 사고 대응: 개인키 유출 확인 즉시 revoke, CT 로그·OCSP 상태 확인, 인증서 재발급과 서버키 교체를 4시간 이내 수행

**결론 (2줄):**
- 기술사 판단: 공개 웹은 OCSP Stapling과 짧은 인증서 수명을 병행하고, 내부 고위험 서비스는 fail-closed와 폐지 SLA를 우선 적용함
- 향후 방향: 단기 인증서, 자동 갱신, CT 모니터링, CRLite 계열 압축 폐지 정보로 신뢰 상태 검증 범위 확대 필요
