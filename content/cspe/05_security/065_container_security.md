## 1. 한눈에 이해하기 (Core Intuition)
- **정의**: 도커(Docker) 컨테이너와 쿠버네티스(Kubernetes) 같은 클라우드 네이티브 환경에서, **컨테이너를 찍어내는 '이미지 도면'부터 컨테이너가 돌아가는 '호스트 OS', 그리고 수만 개의 컨테이너를 지휘하는 '오케스트레이션 제어판'까지 전 구간을 해킹과 설정 오류로부터 방어하는 기술**입니다.
- **필요성**: 기존의 육중한 가상머신(VM)과 달리, 컨테이너는 수명(Lifecycle)이 짧게는 몇 분 만에 생겼다 사라집니다. 기존 백신(에이전트)이나 방화벽은 IP 주소가 1초마다 바뀌며 생겼다 사라지는 이 유령 같은 컨테이너들을 쫓아가며 감시할 수 없습니다. 완전히 새로운 '클라우드 맞춤형 보안 통제'가 필요해졌습니다.
- **핵심 직관**: **"항구의 물류 수출입 통제 시스템"**. 
  - 과거 (가상머신 시대): 커다란 화물선(서버) 1대를 경찰이 몇 달 동안 꼼꼼히 검문(백신, 방화벽)했습니다.
  - 현대 (컨테이너 시대): 도커 항구에선 하루에 10만 개의 작은 철제 컨테이너 박스(앱)들이 초단위로 뜨고 내립니다. 경찰이 하나하나 문을 열어볼 시간이 없습니다. 
  - $\rightarrow$ **컨테이너 보안**: 아예 화물을 박스에 '포장할 때(Build)' 엑스레이로 검사하고, 항구에 '쌓아둘 때(Registry)' 감시하며, 지게차가 '배에 실을 때(Runtime)' 불법 박스면 강제로 바다에 빠뜨려버리는(Drop) 초고속 파이프라인 검문소입니다.

## 2. 왜 중요한가? (Background & Value)
- **등장 배경**: 쿠버네티스와 마이크로서비스(MSA)가 IT의 표준이 되면서, 한 서버 안에 수백 개의 컨테이너가 서로 자원을 쪼개 쓰게 되었습니다. 만약 컨테이너 1개가 해킹당하면, 해커가 그 컨테이너 벽을 뚫고 나와(Container Breakout) 기저에 있는 OS(서버 심장부)와 다른 컨테이너 99개까지 싹 다 감염시키는 치명적인 참사가 발생합니다.
- **가치**: "보안 때문에 클라우드의 민첩성을 포기할 수 없다." 컨테이너의 생성과 소멸 사이클(CI/CD) 안에 자연스럽게 보안 룰을 녹여내어, 개발 속도 저하 없이 클라우드 인프라 전체를 보호하는 필수 방벽입니다.

## 3. 어떻게 작동하는가? (Mechanism)
컨테이너 보안은 생명주기 3단계(Build $\rightarrow$ Ship $\rightarrow$ Run)에 걸쳐 방어선을 구축합니다.

1. **빌드 (Build / 포장 단계)**
   - 개발자가 Dockerfile을 쓸 때 시작됩니다.
   - **이미지 취약점 스캐닝**: 컨테이너의 바탕이 되는 이미지(도면)에 구버전 라이브러리 결함이나 하드코딩된 패스워드(루트 권한 등)가 없는지 스캔합니다.
   - **조치**: "이 박스는 불량품이야!" 라며 파이프라인을 멈춥니다(Break the build).
2. **배포 (Ship & Registry / 저장 및 하역 단계)**
   - 만들어진 이미지가 올라가는 보관소(Registry, 예: Docker Hub, AWS ECR)를 보호합니다.
   - 며칠 전엔 안전했던 이미지도 오늘 새로운 제로데이 취약점이 뜰 수 있으므로 보관소에서 24시간 지속 스캔합니다.
   - **이미지 서명 체계 (Notary/Cosign)**: 해커가 몰래 바꿔치기 못하게 갓 구운 이미지에 '전자 서명 도장'을 찍습니다.
3. **실행 (Run / 런타임 단계) ★ 가장 중요**
   - **쿠버네티스 보안**: 관리자 제어판(Control Plane) API 포트를 외부에서 못 들어오게 잠그고, 수만 개의 컨테이너가 통신하는 규칙(Network Policy)을 엄격히 통제합니다.
   - **런타임 방어**: 컨테이너가 돌아가는 와중에 "어? 웹 서버 컨테이너가 갑자기 가상화폐 채굴(마이닝) 프로세스를 켜네?" 하면 OS 커널 레벨(eBPF 기술 등)에서 이를 감지하고 해당 컨테이너를 강제 삭제(Kill)해 버립니다.

## 4. 실전 활용 및 예시 (Real-world Application)
- **구체적 사례**: 
  - 최근 업계에서는 **Aqua Security, Sysdig, Palo Alto Prisma Cloud** 등의 전용 컨테이너/클라우드 보안 솔루션이 사용됩니다. 이들은 컨테이너 내부에 무거운 에이전트를 깔지 않고, 호스트 OS 커널(eBPF)에서 엿듣는 방식으로 퍼포먼스 저하 없이 모든 컨테이너의 활동을 감시합니다.
- **주의점 및 흔한 오해**: 
  - "컨테이너는 가상머신(VM)과 똑같이 안전하다?" $\rightarrow$ **위험한 착각입니다.** VM은 하드웨어 수준(하이퍼바이저)에서 완전히 분리되어 방음이 완벽하지만, 컨테이너는 하나의 커널(OS 엔진)을 공유하는 '얇은 판잣집'입니다. 권한 설정을 대충 하면(루트 권한 실행 등) 옆집(다른 컨테이너)으로 불이 순식간에 옮겨붙습니다.

## 5. 핵심 비교 및 연결 개념 (Relation)
- **호스트 보안 vs 컨테이너 보안**:
  - **호스트 보안**: 리눅스 OS(바닥재) 자체의 백신, 방화벽, 커널 패치 등 전통적 통제.
  - **컨테이너 보안**: OS 위에서 도는 수백 개의 컨테이너 이미지 위생 검사, 권한 통제(Rootless), K8s 네트워크 정책 등 클라우드 네이티브 계층 추가 통제.

# ✍️ 단답형 / 서술형 시험장 출격 준비

### Ⅰ. 핵심 인사이트
- **본질**: 마이크로서비스 기반 클라우드 환경에서 운영되는 컨테이너 워크로드의 전 생명주기(Build-Ship-Run)를 포괄하여, 호스트 OS, 컨테이너 런타임 환경, 오케스트레이션(Kubernetes) 제어 평면의 취약점과 권한 남용을 통제하는 클라우드 네이티브 보안 아키텍처.
- **가치**: 불변 인프라(Immutable Infrastructure)의 특성을 활용하여 런타임 환경에서의 패치를 금지하고 빌드 파이프라인에서 취약점을 원천 제거(Shift-Left)함으로써, 빠른 배포 사이클을 유지하면서도 공급망 오염과 횡적 확산(Lateral Movement)을 극적으로 억제함.
- **판단 포인트**: 컨테이너 환경의 가장 큰 치명적 위협은 단일 컨테이너가 침해당한 후 공용 커널(Host OS)로 권한이 상승하여 전체 시스템을 장악하는 **'컨테이너 이탈(Container Breakout)'** 이며, 이를 막기 위한 **최소 권한의 원칙(Rootless, Seccomp 등)** 이 아키텍처 설계의 0순위 과제임.

### Ⅱ. 컨테이너 아키텍처 4계층 위협 모델 (The 4C's of Cloud Native Security)
1. **Cloud (클라우드/인프라스트럭처)**
   - 위협: AWS, GCP 리소스의 네트워크(VPC) 설정 오류 및 IAM 권한 과다 부여.
   - 통제: CSPM(클라우드 보안 형상 관리) 도구를 통한 인프라 접근 통제.
2. **Cluster (클러스터 - Kubernetes)**
   - 위협: 외부에 노출된 K8s API Server, 인증 인가(RBAC) 우회, etcd(K8s 내부 DB) 탈취.
   - 통제: Control Plane의 API 서버 방화벽 격리, 노드 간 통신을 암호화하는 mTLS(Service Mesh), 엄격한 RBAC 기반 관리자 통제.
3. **Container (컨테이너 런타임)**
   - 위협: 컨테이너 이탈(Breakout), 잘못 구성된 리눅스 네임스페이스/Cgroups.
   - 통제: 커널 공격면(Attack Surface) 축소를 위한 **Seccomp(시스템 콜 제한)** 프로파일 적용, 컨테이너 실행 권한 제한(Privileged 모드 절대 금지), Read-only Root Filesystem 설정(런타임 위변조 방지).
4. **Code (애플리케이션 코드 및 이미지)**
   - 위협: Docker 이미지 내 오픈소스 취약점(CVE), 평문 시크릿(비밀번호) 유출.
   - 통제: 베이스 이미지 경량화(Distroless, 알파인 OS 활용), SAST/SCA를 활용한 CI 단계 이미지 스캐닝 및 서명(Image Signing).

### Ⅲ. CI/CD 파이프라인 연계 방어선 (Build-Ship-Run)
- **Build 단계 (Shift-Left 통제)**
  - Dockerfile 린팅(Linting) 도구를 돌려 `USER root` 명령어 등 배포 룰 위반 탐지.
  - 베이스 OS 취약점, 3rd-party 패키지 취약점 자동 스캐닝(Trivy, Clair).
- **Ship 단계 (Registry 통제)**
  - 컨테이너 레지스트리에 저장된 이미지의 무결성 검증 체계 도입. 개발자가 서명한(Cosign) '신뢰할 수 있는 이미지'만 클러스터로 넘김.
- **Run 단계 (Admission Control 및 Runtime 방어)**
  - **Admission Controller (승인 컨트롤러)**: K8s OPA Gatekeeper 등을 활용해 "서명이 없거나, High 등급 취약점이 있거나, Root 권한으로 실행하려는 파드(Pod)"는 K8s 클러스터 내 구동 자체를 거부(Block)함. (배포 시점의 수문장).
  - **Runtime 감시**: 불변(Immutable) 원칙에 위배되게 컨테이너 구동 중 내부 쉘(/bin/bash)을 띄우거나 알 수 없는 바이너리를 실행하려는 이상 행위를 **eBPF(커널 레벨 추적 기술)** 로 감지하여 즉시 Pod Kill 조치.

### Ⅳ. 쿠버네티스(Kubernetes) 환경의 네트워크 격리 전략
- **문제점**: K8s의 기본 사상은 '클러스터 내의 모든 파드(Pod)는 서로 제약 없이 통신할 수 있다(Flat Network)'는 것이므로, 1개 컨테이너만 감염돼도 전체로 웜(Worm)처럼 퍼짐(Blast Radius 확대).
- **아키텍처 대안 (Network Policies 적용)**:
  - 제로 트러스트(Zero Trust) 관점에서 L3/L4 계층의 **K8s Network Policy** (마이크로세그멘테이션)를 적용.
  - "Frontend 파드는 Backend 파드와만 통신할 수 있고, DB 파드와는 절대 통신 불가"라는 촘촘한 화이트리스트(Whitelist) 방화벽 룰을 파드 간에 선언적으로(Declarative) 구성해야 횡적 이동(Lateral Movement)을 막을 수 있음.

### Ⅴ. 결론 및 실무적 판단 포인트
- 컨테이너 보안의 대원칙은 **"운영(Runtime) 환경에서는 그 어떤 패치도 하지 말고, 문제가 생기면 컨테이너를 죽인(Kill) 뒤 소스코드를 고쳐 새로 배포하라(Immutable Infrastructure)"** 는 것입니다. 이 불변성 철학을 지키기 위해서는 CI 파이프라인 단의 강력한 자동 스캐닝과 배포 게이트(Admission Control)가 어우러진 DevSecOps 파이프라인 내재화가 필수 조건입니다.

### 💡 문제 유형별 목차 전환 포인트
- **[마이크로서비스 및 컨테이너(Docker/K8s) 보안 취약점/대응 대책]**: Ⅱ번 4C 위협 모델(Breakout, API 노출 등)을 전면에 세우고, 이를 막기 위한 커널 격리(Seccomp)와 권한 제한(Rootless) 등 컨테이너 고유의 통제 기법을 딥다이브.
- **[클라우드 네이티브 워크로드 보호 파이프라인 (Build-Ship-Run)]**: Ⅲ번 생명주기 통제와 Ⅳ번 네트워크 마이크로세그멘테이션을 결합하여, 유동적인 컨테이너 인프라를 코드(IaC) 레벨에서 어떻게 안전하게 릴리스(Release)하는지 인프라 아키텍처 관점 전개.
