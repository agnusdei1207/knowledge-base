## 미리 알고가기

- 모의 침투 테스트는 실제 공격 시나리오로 악용 가능성을 검증하는 활동이며 단순 취약점 목록화와 다름
- 블랙박스, 그레이박스, 화이트박스는 사전 제공 정보 범위에 따른 구분임
- 결과물의 핵심은 해킹 성공 여부보다 재현 가능한 공격 경로와 개선 우선순위임

## Ⅰ. 개요

- **정의/개념**: 모의 침투 테스트는 합의된 범위 안에서 공격자 관점의 기법을 사용해 시스템, 네트워크, 웹 애플리케이션의 취약점을 실제로 악용해 보고 침해 가능성과 영향도를 검증하는 보안 평가 활동임
- **배경/필요성**: 자동 스캔만으로는 취약점이 실제로 연결되는 공격 경로와 비즈니스 로직 결함을 확인하기 어려워 사람 중심의 시나리오 검증이 필요함

## Ⅱ. 특징

- 공격자 시점에서 정보 수집, 침투, 권한 상승, 영향 확인까지 연계해 수행함
- 기술 취약점뿐 아니라 인증 흐름, 권한 검증, 운영 절차의 허점도 확인할 수 있음
- 범위와 시간과 허용 행위를 명확히 합의하지 않으면 서비스 장애나 법적 문제가 생길 수 있음
- 결과 보고서는 취약점 나열보다 공격 성공 조건과 재현 절차와 대응 우선순위를 분명히 해야 함

## Ⅲ. 종류 및 비교

| 판단 기준 | 블랙박스 | 화이트박스 |
|:---|:---|:---|
| 사전 정보 | 최소 정보만 제공 | 계정, 구조, 소스 정보 제공 |
| 강점 | 외부 공격자 시점 검증에 적합 | 깊은 코드·설계 검증에 적합 |
| 한계 | 시간 대비 탐색 범위가 좁을 수 있음 | 실제 외부 공격자 시점과 차이가 날 수 있음 |
| 적합 환경 | 인터넷 노출 서비스 | 핵심 업무 시스템, 개발 단계 보안 점검 |

## Ⅳ. 구성요소 및 구조

| 구성요소 | 설명 |
|:---|:---|
| 사전 협의 | 범위, 일정, 허용 기법, 중단 조건을 정함 |
| 정보 수집 및 분석 | 자산, 계정, 흐름, 취약 가능 지점을 찾음 |
| 공격 수행 | 취약점 악용, 권한 상승, 우회 가능성을 검증함 |
| 결과 보고 | 재현 절차, 영향, 우선순위, 개선 권고를 정리함 |

```text
사전 협의 -> 정보 수집 -> 취약점 분석 -> 공격 검증 -> 영향 평가 -> 보고/개선
```

## Ⅴ. 원리 및 절차 흐름도

```text
범위 정의 -> 공격 표면 파악 -> 취약 경로 선정 -> 악용 시도 -> 권한/영향 확인 -> 개선안 정리
```

1. **범위 정의**: 대상 시스템과 허용 시간과 예외 조건을 합의함
2. **공격 표면 파악**: 외부 노출 서비스와 인증 흐름과 관리자 기능을 분석함
3. **취약 경로 선정**: 가능성이 높은 취약점 조합과 우회 시나리오를 정함
4. **악용 시도**: 실제 공격 코드나 절차로 침투 가능성을 검증함
5. **영향 확인과 보고**: 데이터 노출, 권한 탈취, 이동 가능 범위를 정리해 개선안을 제시함

## Ⅵ. 실무 적용 및 유의점

1. 인터넷 뱅킹이나 전자상거래처럼 인증과 권한 흐름이 복잡한 서비스는 정기 스캔 외에 모의 침투 테스트를 병행해야 하며 수행 전 중단 조건과 증적 수집 범위를 합의하고 재현 성공 여부와 조치 뒤 동일 시나리오 차단 여부로 확인함
2. 개발 단계의 핵심 시스템은 화이트박스 테스트로 설계 결함까지 확인하는 것이 효과적이지만 운영 환경 데이터 사용은 통제해야 하며 우회 가능한 권한 검증 제거 여부와 수정 코드 재검증 결과로 확인함

## Ⅶ. 결론

- 모의 침투 테스트는 취약점 존재 여부보다 실제 공격 경로와 업무 영향까지 검증하는 활동이므로 범위 합의와 재현 가능한 개선 결과가 함께 남아야 함
