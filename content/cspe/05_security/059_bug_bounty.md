## 미리 알고가기

- 버그 바운티는 외부 연구자가 취약점을 신고하면 보상하는 제도이며 무제한 해킹 허용과 같지 않음
- 프로그램 성공 여부는 포상금 규모보다 범위 정의, 접수 절차, 신속한 검증과 수정 역량에 크게 좌우됨
- 중복 신고와 품질 낮은 제보가 많을 수 있어 트리아지 체계가 필수임

## Ⅰ. 개요

- **정의/개념**: 버그 바운티는 조직이 정한 범위와 규칙에 따라 외부 보안 연구자가 취약점을 발견·신고하면 유효성과 영향도에 맞춰 보상하는 취약점 발굴 운영 제도임
- **배경/필요성**: 내부 인력과 정기 점검만으로는 다양한 공격 관점과 신규 취약점을 빠르게 찾기 어려워 외부 연구자 생태계를 활용해 발견 범위와 속도를 넓힐 필요가 커짐

## Ⅱ. 특징

- 다수 연구자의 다양한 기술과 시각을 활용해 내부 점검의 사각지대를 줄일 수 있음
- 성과 기반 보상 구조라 실제 유효한 취약점에 자원을 집중하기 쉬움
- 공개 범위와 법적 보호 조건이 불명확하면 무단 테스트나 분쟁이 생길 수 있음
- 접수 이후 검증과 수정과 커뮤니케이션이 느리면 프로그램 신뢰가 떨어짐

## Ⅲ. 종류 및 비교

| 판단 기준 | 공개 프로그램 | 비공개 프로그램 |
|:---|:---|:---|
| 참여 대상 | 누구나 또는 넓은 연구자 풀 | 초청된 연구자 중심 |
| 장점 | 발견 범위와 다양성이 큼 | 운영 부담과 위험 통제가 쉬움 |
| 한계 | 저품질 제보와 운영 부하가 큼 | 참여자 풀이 좁아 발견 다양성이 제한될 수 있음 |
| 적합 환경 | 성숙한 보안 대응 체계 보유 조직 | 금융, 핵심 인프라, 초기 도입 조직 |

## Ⅳ. 구성요소 및 구조

| 구성요소 | 설명 |
|:---|:---|
| Scope and Rules | 허용 대상, 금지 행위, 증적 형식, 공개 정책을 정함 |
| Submission and Triage | 취약점 접수, 중복 확인, 유효성 검증을 수행함 |
| Remediation | 개발·운영팀이 수정과 우회 대책을 적용함 |
| Reward and Disclosure | 영향도에 맞는 보상과 공개 시점을 관리함 |

```text
규칙 공지 -> 연구자 테스트 -> 신고 접수 -> 유효성 검증 -> 수정/보상 -> 공개 여부 결정
```

## Ⅴ. 원리 및 절차 흐름도

```text
범위 설정 -> 접수 채널 운영 -> 제보 검증 -> 심각도 산정 -> 수정 배포 -> 연구자 보상/회고
```

1. **범위 설정**: 대상 서비스와 금지 행위와 면책 조건을 명확히 공지함
2. **접수 채널 운영**: 재현 절차와 증적을 포함한 제보를 수집함
3. **제보 검증**: 중복 여부와 실제 영향과 재현 가능성을 판단함
4. **수정과 배포**: 코드 수정이나 설정 변경으로 위험을 제거함
5. **보상과 회고**: 보상 지급과 공개 여부를 결정하고 재발 방지 항목을 정리함

## Ⅵ. 실무 적용 및 유의점

1. 대외 서비스가 많은 기업은 비공개 프로그램부터 시작해 트리아지와 개발 수정 역량을 먼저 안정화해야 하며 운영 시에는 범위 외 테스트 차단과 SLA 기반 응답 시간을 관리하고 유효 제보 비율과 수정 완료 시간으로 확인함
2. 공개 프로그램을 운영하는 조직은 법무·개발·보안팀의 공조 없이 포상만 높이면 운영 부하만 커지므로 공개 정책과 책임 공개 시점을 사전에 정하고 중복 신고 비율과 고위험 취약점 해소율과 연구자 만족도로 확인함

## Ⅶ. 결론

- 버그 바운티는 외부 연구자의 집단 지성을 활용하는 제도이지만 효과는 포상금보다 범위 정의와 신속한 검증과 수정 운영 역량에 달려 있음
