## 미리 알고가기

- 블록 암호: AES처럼 고정 길이 블록을 입력으로 받는 암호 알고리즘임
- IV/nonce: 각 암호화 세션을 구분해 같은 평문이 반복돼도 같은 암호문이 나오지 않게 하는 값임
- AEAD: 기밀성과 무결성을 한 번에 제공하는 현대 암호 방식임
- 인증 태그: 복호화 전에 위변조 여부를 검사하는 검증값임

## Ⅰ. 개요

- **정의/개념**: 블록 암호 운영 모드는 AES 같은 블록 암호를 실제 데이터 흐름에 맞게 연결하는 규칙이며, 평문을 어떻게 섞고 nonce를 어떻게 쓰며 무결성을 어떻게 붙일지 결정하는 절차임
- **배경/필요성**: 같은 블록 암호라도 운영 모드를 잘못 고르면 패턴 노출, 위변조, 병렬 처리 한계 같은 문제가 바로 생기므로, 실제 보안성은 알고리즘 이름보다 모드 선택에 크게 좌우됨

## Ⅱ. 특징

- ECB처럼 단순 반복 모드는 같은 평문 패턴을 그대로 드러낼 수 있어 실무에 부적합함
- CBC는 한동안 널리 쓰였지만 패딩과 순차 처리 제약 때문에 현대 프로토콜에서 점차 밀려남
- CTR은 빠르고 병렬화가 쉽지만 기밀성만 제공하므로 별도 인증을 붙여야 함
- GCM은 CTR 기반 속도에 인증 태그를 결합해 현재 웹과 API 보안의 기본 선택지가 됨

## Ⅲ. 종류 및 비교

| 판단 기준 | CBC | CTR | GCM |
|:---|:---|:---|:---|
| 처리 방식 | 이전 암호문 블록과 현재 평문을 연결해 순차적으로 암호화함 | nonce와 counter로 키 스트림을 만들어 평문과 XOR함 | CTR로 암호화하면서 인증 태그도 함께 계산함 |
| 병렬 처리 | 암호화가 순차적이라 병렬 처리에 불리함 | 암호화와 복호화 모두 병렬 처리하기 쉬움 | 병렬 처리에 유리하며 고속 구현이 쉬움 |
| 무결성 제공 | 별도 MAC 없이는 위변조를 막지 못함 | 별도 MAC 없이는 위변조를 막지 못함 | 기밀성과 무결성을 함께 제공함 |
| 현재 선택 기준 | 레거시 호환이 필요한 구간에서만 제한적으로 검토함 | 별도 인증 설계를 붙일 수 있을 때 맞음 | 현대 TLS, API, 서비스 암호화 기본 선택지로 맞음 |

> 요약: CBC는 레거시, CTR은 경량 조합용, GCM은 현대 기본 선택지라는 구도가 분명함.

## Ⅳ. 구성요소 및 구조

| 구성요소 | 설명 |
|:---|:---|
| 블록 암호 코어 | AES 같은 기본 암호 연산이며 모드에 따라 같은 코어도 실제 보안 성질이 크게 달라짐 |
| IV 또는 nonce | 세션별 구분값이며 재사용되면 패턴 노출이나 키 스트림 중복 같은 중대 사고가 생길 수 있음 |
| 모드 로직 | 이전 블록 연결, counter 증가, 인증 태그 계산처럼 블록 암호를 실제 데이터 흐름으로 바꾸는 절차임 |
| 인증 태그 | AEAD 모드에서 위변조를 잡는 검증값이며 복호화 전에 반드시 확인해야 함 |

```text
+--------+     +-----------+     +-----------+     +-----------+
| 평문   | --> | IV/nonce  | --> | 모드 로직  | --> | 암호문/태그 |
+--------+     +-----------+     +-----------+     +-----------+
                   |
              +---------+
              | AES 코어 |
              +---------+
```

> 요약: 블록 암호 자체보다 IV/nonce와 모드 로직이 실제 보안 성질을 결정함.

## Ⅴ. 원리 및 절차 흐름도

```text
+----------+     +----------+     +----------+     +----------+     +----------+
| 모드 선택 | --> | nonce 준비 | --> | 블록 변환 | --> | 태그 계산 | --> | 복호화 검증 |
+----------+     +----------+     +----------+     +----------+     +----------+
```

1. **모드 선택**: 데이터 특성과 무결성 요구에 맞는 모드를 정함
2. **nonce 준비**: 세션마다 중복되지 않는 IV나 nonce를 생성함
3. **블록 변환**: 선택한 모드 규칙에 따라 평문 블록을 암호문으로 바꿈
4. **태그 계산**: GCM 같은 AEAD 모드에서는 인증 태그를 함께 계산함
5. **복호화 검증**: 수신 측이 태그와 nonce를 먼저 확인한 뒤 복호화함

## Ⅵ. 실무 적용 및 유의점

1. 웹 서비스와 내부 API 암호화에서는 CBC보다 GCM이 기본 선택이지만 nonce 재사용이 한 번만 생겨도 기밀성과 무결성이 동시에 무너질 수 있으므로 중앙 nonce 정책과 태그 검증 실패 처리 규칙을 함께 두고 태그 오류율, 세션 실패율, nonce 충돌 여부로 확인함
2. 디스크나 블록 스토리지처럼 무작위 접근이 많은 환경에서는 일반 통신용 GCM보다 XTS 같은 저장장치 전용 모드를 써야 하므로 대상 매체에 맞는 모드를 분리 적용하고 읽기·쓰기 지연, 복구 가능성, 데이터 이동 공격 테스트 결과로 확인함

## Ⅶ. 결론

블록 암호 운영 모드의 선택은 부가 옵션이 아니라 실제 보안 성질을 결정하는 핵심 판단이므로, 현대 서비스에서는 AEAD와 nonce 관리 체계를 함께 설계하는 것이 기본임.
