# 📖 【암기용】 개념 완전 이해

> 목적: 블록 암호 운영 모드를 처음 봐도 완벽히 이해하게 만든다. 시험 답안 양식이 아니라, 이해를 위한 친절한 설명이다.

## 한눈에
- **개요**: 고정 길이 블록 암호를 긴 메시지에 적용하는 연결 방식
- **왜 필요한가**: AES는 128비트 블록 하나를 암호화하는 함수임. 파일·패킷·DB 컬럼처럼 긴 데이터를 처리하려면 IV, nonce, counter, 인증 tag를 포함한 운영 모드가 필요함.
- **핵심 직관**: 같은 자물쇠(AES)를 쓰더라도 문서를 묶는 방식(CBC, CTR, GCM)에 따라 기밀성·병렬성·무결성이 달라짐.

## 깊이 이해
- **배경·문제의식**: ECB는 같은 평문 블록이 같은 암호문 블록으로 나타나 패턴이 노출됨. CBC는 이전 암호문을 섞고, CTR은 카운터를 암호화해 키스트림을 만들며, GCM은 CTR에 GHASH 인증을 결합함.
- **작동 원리**: CBC는 예측 불가능한 IV와 패딩 검증이 필요함. CTR은 nonce+counter 유일성이 핵심임. GCM은 96비트 nonce와 128비트 tag로 기밀성·무결성을 함께 제공함.
- **비유**: CBC는 앞 봉투의 봉인을 다음 봉투에 반영하고, CTR은 페이지 번호별 마스킹 테이프를 만들며, GCM은 봉투마다 위조 방지 봉인까지 붙이는 방식임.
- **구체 예시**: TLS 1.3은 CBC를 제거하고 AEAD인 AES-GCM, ChaCha20-Poly1305를 사용함. AES-GCM에서 같은 키·nonce 재사용은 인증키 노출과 평문 관계 노출로 이어짐.
- **흔한 오해·주의점**: 암호화는 무결성을 자동 제공하지 않음. CBC/CTR은 HMAC 등 별도 인증이 필요하며 GCM은 tag 검증 실패 시 평문 반환 금지임.

## 연결 개념
- AES - 블록 암호 운영 모드의 대표 기반 알고리즘
- AEAD - GCM처럼 암호화와 인증을 함께 제공하는 방식
- 패딩 오라클 - CBC 패딩 오류 처리 차이로 발생하는 공격

# 📝 【답안용】 시험 답안 템플릿

> 목적: 시험장에서 25분에 그대로 쓰는 답안 양식. 작성방식(추상표현 금지·수치·도식·문제유형 전환)을 엄격히 지킨다.
> 핵심: 모드 이름 나열이 아니라 IV/nonce/tag 요구사항과 무결성 제공 여부를 기준으로 비교한다.

## 핵심 인사이트 (3줄 요약)

> 1. **본질**: 블록 암호 운영 모드는 AES 같은 128비트 블록 암호를 긴 메시지에 적용하는 IV·nonce·counter·tag 처리 규칙임.
> 2. **가치**: CBC·CTR·GCM은 기밀성, 병렬 처리, 무결성 제공 여부가 달라 시스템 요구에 맞춰 선택해야 함.
> 3. **판단 포인트**: CBC는 padding oracle, CTR/GCM은 nonce 재사용, GCM은 128비트 tag 검증 실패 처리가 핵심임.

## 출제 의도 및 답안 포인트

| 출제 의도 | 반드시 짚을 핵심 | 감점 회피 포인트 |
|:---|:---|:---|
| 운영 모드 차이 이해 확인 | CBC, CTR, GCM의 IV/nonce/tag와 병렬성 | AES 자체와 운영 모드 혼동 |
| 무결성·기밀성 구분 확인 | CBC/CTR은 별도 MAC, GCM은 AEAD | 암호화만으로 위조 방지 가능하다고 서술 |
| 실무 설정 리스크 확인 | nonce 중복 0건, tag 128비트, padding oracle 차단 | IV를 비밀값으로 설명 |

> 요약: 블록 모드 답안은 IV/nonce 유일성, 인증 tag, 패딩 오류 처리까지 포함해야 함.

## Ⅰ. 개요 및 필요성

블록 암호 운영 모드는 고정 블록 암호를 연속 데이터에 적용하는 방식이다. AES는 128비트 블록 단위 함수이므로 긴 메시지에는 블록 연결, 카운터, 인증 태그 규칙이 필요함. 운영 모드 선택 오류는 평문 패턴 노출, 위조, padding oracle로 이어짐.

---

## Ⅱ. 구조 및 구성요소

```text
Plaintext Blocks -> AES Key Schedule -> Mode Logic(CBC/CTR/GCM) -> Ciphertext
IV/Nonce/Counter -> Mode Logic
AAD + Ciphertext -> GHASH(GCM) -> Authentication Tag
```

| 구성요소 | 역할 | 특이사항 |
|:---|:---|:---|
| 블록 암호 | 128비트 블록 암·복호화 | AES-128/192/256 |
| IV/nonce | 동일 평문 반복 노출 방지 | CBC는 예측 불가, CTR/GCM은 유일성 |
| counter | CTR/GCM 키스트림 블록 번호 | 재사용 시 평문 관계 노출 |
| tag/MAC | 무결성·인증 확인 | GCM tag 128비트 권장 |

> 요약: 운영 모드는 AES 위에 IV/nonce/counter/tag 규칙을 더해 긴 메시지의 기밀성·무결성을 제어함.

---

## Ⅲ. 동작원리 및 흐름도

```text
모드 선택 -> IV/nonce 생성 -> 블록별 AES 처리 -> ciphertext 생성
-> MAC/tag 생성 또는 검증 -> 실패 시 폐기 -> 성공 시 평문 반환
```

| 단계 | 처리 내용 | 검증 기준 |
|:---:|:---|:---|
| 1 | 요구사항에 따라 CBC/CTR/GCM 선택 | 무결성 필요 시 AEAD 우선 |
| 2 | IV 또는 nonce 생성 | 키별 중복 0건 |
| 3 | 블록별 암호화 수행 | CBC 순차, CTR/GCM 병렬 가능 |
| 4 | tag 또는 MAC 검증 | 128비트 tag, 실패 시 폐기 |
| 5 | 오류 처리·로그 기록 | padding 오류 메시지 단일화 |

> 요약: 안전한 동작은 모드 선택보다 IV/nonce 생성, tag 검증, 오류 처리 일관성에서 결정됨.

---

## Ⅳ. 특징

| 구분 | CBC | CTR | GCM |
|:---|:---|:---|:---|
| 기본 원리 | 이전 암호문과 XOR 후 AES | nonce+counter 암호화 후 XOR | CTR + GHASH 인증 |
| 무결성 | 별도 HMAC 필요 | 별도 MAC 필요 | AEAD, 128비트 tag |
| 병렬성 | 암호화 순차 | 암·복호화 병렬 | 병렬 처리 가능 |
| 주요 위험 | padding oracle | nonce 재사용 | nonce 재사용 시 tag 위조 위험 |

> 요약: 신규 설계는 AEAD인 GCM을 우선 검토하고 CBC/CTR은 별도 MAC과 오류 통제가 필요함.

---

## Ⅴ. 심화 비교 및 적용 판단

| 비교 축 | 기존/대안 | 본 키워드 | 선택 기준 |
|:---|:---|:---|:---|
| 기밀성 | ECB 금지 | CBC/CTR/GCM | 패턴 노출 제거 필요 |
| 인증 | CBC/CTR + HMAC | GCM AEAD | 신규 프로토콜은 AEAD 기본 |
| 운영/성능 | CBC 순차 처리 | CTR/GCM 병렬 처리 | AES-NI, p95 지연 목표 |

> 요약: 선택 기준은 무결성 요구, 병렬 처리, nonce 관리 가능성의 조합임.

| 리스크 | 원인 | 대응 방안 | 확인 지표 |
|:---|:---|:---|:---|
| padding oracle | CBC 오류 메시지 차이 | encrypt-then-MAC, 오류 응답 단일화 | 오류 코드 1종, 공격 테스트 통과 |
| nonce 재사용 | 난수 충돌, 카운터 초기화 | 단조 증가 nonce, rekey 정책 | 키별 nonce 중복 0건 |
| tag 미검증 | 복호화 후 인증 처리 | verify-then-decrypt 강제 | tag 실패 평문 반환 0건 |

> 요약: CBC는 오류 처리, CTR/GCM은 nonce 관리, GCM은 tag 검증 순서가 주요 통제점임.

| 점검 항목 | 목표 기준 | 측정 방법 |
|:---|:---|:---|
| 기밀성 | AES-128 이상, IV/nonce 중복 0건 | 암호정책·로그 점검 |
| 무결성 | AEAD tag 128비트 또는 HMAC-SHA-256 | 설정 리뷰, KAT |
| 운영/탐지 | 암호 오류율 0.1% 이하, 재시도 경보 | SIEM, 애플리케이션 로그 |

> 요약: 운영 모드의 성공 여부는 암호 알고리즘보다 IV/nonce 중복과 인증 실패 처리 지표로 판단함.

## Ⅵ. 실무 적용 및 결론

**적용 방안 3개 (필수 — 단계별 또는 항목별):**
1. 신규 설계: TLS 1.3, 저장 데이터 암호화, API 토큰에는 AES-GCM 또는 ChaCha20-Poly1305 AEAD를 우선 적용함.
2. 레거시 CBC: encrypt-then-MAC, PKCS#7 padding 검증 오류 단일화, HMAC-SHA-256을 함께 적용함.
3. 운영 통제: 키별 nonce 중복 0건, tag 실패 평문 반환 0건, KAT 100% 통과를 배포 게이트로 설정함.

**결론 (2줄):**
- 기술사 판단: 신규 시스템은 GCM 같은 AEAD를 선택하고, CBC는 호환성 요구가 있을 때만 MAC·오류 통제를 조건으로 제한 적용함.
- 향후 방향: 암호 운영은 알고리즘 선택에서 nonce 수명, 키 회전, 인증 실패 관측까지 포함하는 정책 기반 통제로 이동함.
