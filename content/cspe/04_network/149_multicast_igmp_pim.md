# 📖 【암기용】 개념 완전 이해

> 목적: 멀티캐스트를 단순 다중 전송이 아니라 수신자가 있는 구간에만 트래픽을 복제하는 네트워크 전달 방식으로 이해하게 만든다.

## 한눈에
- **개요**: 하나의 송신자가 여러 수신자에게 그룹 주소 기반으로 패킷을 전달하는 방식
- **왜 필요한가**: IPTV, 실시간 시세, 회의 중계처럼 같은 데이터를 여러 사용자에게 보낼 때 유니캐스트는 송신자와 링크 대역폭을 중복 소비한다.
- **핵심 직관**: 신문을 각 집마다 인쇄해 보내는 대신, 지역 배포 지점에서 필요한 가구 방향으로만 나누어 보내는 방식이다.

## 깊이 이해
- **배경·문제의식**: 동일 스트림을 유니캐스트로 N명에게 보내면 송신자에서 N개 흐름이 생성되어 서버와 링크 대역폭이 증가한다.
- **작동 원리**: 단말은 IGMP로 그룹 가입을 알리고, 라우터는 PIM으로 멀티캐스트 트리를 만들어 수신자가 있는 경로에만 패킷을 복제한다.
- **비유**: 방송국이 한 번 송출하고 중계소가 시청자가 있는 지역으로만 신호를 나누어 보내는 구조와 같다.
- **구체 예시**: IPTV 셋톱박스는 채널 변경 시 IGMP Join을 보내고, 라우터는 PIM-SM 트리를 통해 해당 그룹 트래픽을 전달한다.
- **흔한 오해·주의점**: 멀티캐스트는 브로드캐스트가 아니며, 가입한 그룹과 라우팅 트리가 없는 구간에는 트래픽을 보내지 않는다.

## 연결 개념
- IGMP - 호스트와 로컬 라우터 사이 그룹 가입 관리
- PIM-SM - 라우터 간 멀티캐스트 트리 구성
- IGMP Snooping - 스위치가 포트별 그룹 가입을 학습해 불필요한 flooding을 줄임

# 📝 【답안용】 시험 답안 템플릿

> 목적: 멀티캐스트 답안은 호스트 가입 관리(IGMP)와 라우터 트리 구성(PIM)을 분리해 작성한다.
> 핵심: 출제자는 그룹 가입, RP, 트리 생성, 스위치 snooping, 운영 지표를 정확히 연결하는지 확인한다.

## 핵심 인사이트 (3줄 요약)

> 1. **본질**: 멀티캐스트는 그룹 주소를 기준으로 수신자가 있는 경로에만 패킷을 복제하는 one-to-many 전달 방식이다.
> 2. **가치**: IGMP가 호스트 가입을 관리하고 PIM-SM이 라우터 간 공유 트리 또는 최단 경로 트리를 구성한다.
> 3. **판단 포인트**: IGMP Join/Leave, RP 위치, PIM neighbor, RPF check, IGMP Snooping을 함께 점검해야 한다.

## 출제 의도 및 답안 포인트

| 출제 의도 | 반드시 짚을 핵심 | 감점 회피 포인트 |
|:---|:---|:---|
| 멀티캐스트 전달 원리 확인 | 그룹 주소, IGMP, PIM-SM, RP, RPF | 브로드캐스트와 같은 개념으로 설명 |
| 프로토콜 역할 구분 확인 | IGMP는 호스트-라우터, PIM은 라우터-라우터 | IGMP가 라우팅 트리를 만든다고 설명 |
| 운영 장애 분석 확인 | Join 누락, RP 장애, RPF 실패, Snooping 문제 | 수신 장애 원인과 지표 분리 누락 |

> 요약: 멀티캐스트 문제는 IGMP 가입과 PIM 트리를 구분하고 장애 지점을 계층별로 나누어 쓰는 답안을 요구한다.

## Ⅰ. 개요 및 필요성

- 개요: 그룹 기반 one-to-many 전달
- 배경: 동일 스트림을 유니캐스트로 다수 수신자에게 보내면 송신 서버와 업링크 대역폭이 수신자 수에 비례해 증가함.
- 필요성: IPTV, 금융 시세, 사내 방송, 회의 중계에서 동일 데이터를 수신자 있는 경로에만 복제해야 함.
- 판단 기준: 그룹 가입 수, RP 위치, PIM neighbor, RPF 실패, IGMP Snooping 상태로 운영 품질을 판단함.

---

## Ⅱ. 구조 및 구성요소

```text
Source -> Multicast Router -> PIM-SM / RP -> Distribution Tree
                                   -> Access Switch IGMP Snooping
                                   -> Receiver IGMP Join
```

| 구성요소 | 역할 | 특이사항 |
|:---|:---|:---|
| Source | 멀티캐스트 그룹으로 패킷 송신 | 224.0.0.0/4 IPv4 그룹 주소 |
| Receiver | IGMP Join으로 그룹 수신 의사 표시 | IGMPv2/v3 사용 |
| IGMP Querier | 로컬 세그먼트 그룹 가입 상태 확인 | 주기 Query와 Leave 처리 |
| PIM Router | 라우터 간 멀티캐스트 트리 구성 | PIM-SM, RP, RPF check |
| IGMP Snooping Switch | 포트별 그룹 가입을 학습 | L2 flooding 범위 제한 |

> 요약: 멀티캐스트는 수신자 가입을 IGMP로 확인하고 라우터 간 전달 트리를 PIM으로 구성한다.

---

## Ⅲ. 동작원리 및 흐름도

```text
Receiver IGMP Join -> Access Switch Snooping -> First-hop Router
-> PIM Join toward RP / Source -> Multicast Tree 생성 -> Stream 전달
```

| 단계 | 처리 내용 | 검증 기준 |
|:---:|:---|:---|
| 1 | 수신자가 원하는 그룹에 IGMP Join을 전송 | IGMP membership table |
| 2 | 스위치가 IGMP Snooping으로 수신 포트를 기록 | snooping group table |
| 3 | 라우터가 PIM Join을 RP 또는 Source 방향으로 전송 | PIM neighbor, join state |
| 4 | RPF check로 역방향 경로 일치 여부를 확인 | RPF pass/fail |
| 5 | 트리 경로에 있는 라우터가 필요한 링크에만 패킷 복제 | multicast forwarding table |

> 요약: 멀티캐스트 전달은 IGMP 가입, PIM Join, RPF 검증, 트리 기반 복제 순서로 동작한다.

## Ⅳ. 특징

| 구분 | 유니캐스트 | 멀티캐스트 IGMP/PIM | 수치·기술 포인트 |
|:---|:---|:---|:---|
| 전송 방식 | 수신자 수만큼 세션 생성 | 그룹별 트리에서 링크별 1개 복제 | 224.0.0.0/4, 239/8 |
| 제어 프로토콜 | 라우팅 테이블 중심 | IGMP, PIM-SM, RP | IGMPv2/v3, PIM Register |
| 스위치 처리 | 목적지 MAC 학습 | IGMP Snooping 필요 | 그룹별 포트 테이블 |
| 장애 원인 | 경로 단절 중심 | Join, RP, RPF, Snooping 문제 | mroute, PIM neighbor |

> 요약: 멀티캐스트는 대역폭 중복을 줄이지만 IGMP와 PIM 상태가 맞지 않으면 일부 수신자만 장애를 겪을 수 있다.

## Ⅴ. 심화 비교 및 적용 판단

| 비교 축 | 기존/대안 | 본 키워드 | 선택 기준 |
|:---|:---|:---|:---|
| 구조 | 유니캐스트 복제 | 네트워크 트리 복제 | 동일 스트림 수신자가 많은 환경에 적용 |
| 비용/성능 | 서버와 링크 부하 증가 | 라우터·스위치 상태 관리 증가 | 그룹 수와 수신자 수로 판단 |
| 운영/위험 | TCP 세션 단위 추적 | IGMP/PIM/RPF 상태 추적 | 운영자가 mroute와 snooping 분석 가능해야 함 |

> 요약: 멀티캐스트는 동일 콘텐츠 다중 배포에 적합하지만 그룹 상태와 트리 장애 분석 역량이 필요하다.

| 리스크 | 원인 | 대응 방안 | 확인 지표 |
|:---|:---|:---|:---|
| 수신 불가 | IGMP Join 누락 또는 Snooping 오류 | Querier 설정, snooping table 점검 | IGMP group count |
| 트리 형성 실패 | RP 설정 오류 또는 PIM neighbor 불일치 | RP 이중화, PIM adjacency 점검 | PIM neighbor state |
| RPF 실패 | 유니캐스트 라우팅 경로와 수신 인터페이스 불일치 | 라우팅 경로 정합성 확인 | RPF fail count |

> 요약: 멀티캐스트 장애는 가입, 트리, RPF 세 영역으로 나누어 확인해야 원인 분리가 가능하다.

| 점검 항목 | 목표 기준 | 측정 방법 |
|:---|:---|:---|
| 그룹 가입 | 그룹별 수신 포트와 라우터 상태 일치 | IGMP table, snooping table |
| 라우팅 상태 | PIM neighbor와 RP 상태 정상 | mroute, PIM command |
| 전송 품질 | 손실, 지연, 지터 기준 충족 | packet capture, RTP metric |

> 요약: 운영 지표는 IGMP 가입 상태, PIM 트리 상태, 스트림 품질을 함께 확인해야 한다.

## Ⅵ. 실무 적용 및 결론

**적용 방안 3개 (필수 - 단계별 또는 항목별):**
1. IPTV나 사내 방송망은 IGMP Snooping과 IGMP Querier 위치를 명확히 하고 그룹별 수신 포트를 점검함.
2. 라우팅 구간은 PIM-SM, RP 이중화, RPF 경로 정합성을 기준으로 설계함.
3. 장애 분석은 IGMP table, snooping table, PIM neighbor, mroute, packet capture 순서로 표준 절차화함.

**결론 (2줄):**
- 기술사 판단: 동일 스트림을 다수 수신자가 소비하면 멀티캐스트를 선택하고, 수신자별 개인화 콘텐츠는 유니캐스트 또는 CDN을 선택함.
- 향후 방향: 멀티캐스트는 IPTV, 금융 시세, 사내 실시간 배포에서 SDN 관측성과 결합해 운영 자동화가 확대됨.
