# 📖 【암기용】 개념 완전 이해

> 목적: NMS를 단순 대시보드가 아니라 장애·성능·구성·계정·보안 관리를 묶는 네트워크 운영 플랫폼으로 이해하게 만든다.

## 한눈에
- **개요**: 네트워크 장비와 링크를 중앙에서 감시·제어·기록하는 운영 관리 시스템
- **왜 필요한가**: 라우터·스위치·방화벽 수백 대를 개별 접속으로 관리하면 장애 탐지, 구성 변경, 감사 추적이 누락된다.
- **핵심 직관**: NMS는 병원 중앙 모니터처럼 장비 생체신호를 모으고 이상 징후를 운영자에게 전달한다.

## 깊이 이해
- **배경·문제의식**: 네트워크 장애는 장비 down, 포트 error, 구성 변경, 회선 혼잡, 보안 이벤트가 얽혀 발생한다. NMS는 FCAPS 관점으로 장애(Fault), 구성(Configuration), 회계(Accounting), 성능(Performance), 보안(Security)을 통합한다.
- **작동 원리**: SNMP, Syslog, NetFlow/IPFIX, API, ICMP probe로 데이터를 수집하고, 토폴로지와 알림 규칙을 기반으로 장애를 상관 분석한다.
- **비유**: 여러 지점의 CCTV, 출입기록, 전력계량기를 한 관제실에 모아 운영하는 방식이다.
- **구체 예시**: 지사 라우터 down 발생 시 ICMP 실패, SNMP trap, BGP neighbor down, 회선 사용률 0%를 묶어 단일 장애 티켓으로 생성한다.
- **흔한 오해·주의점**: NMS는 장비가 많을수록 자동으로 정확해지지 않는다. 장비 인벤토리, 기준 구성, 알림 억제, 유지보수 창 관리가 필요하다.

## 연결 개념
- SNMP·NetFlow·sFlow — NMS의 주요 수집 채널
- ITSM — 장애 티켓·변경 승인 연계
- Network Automation — 구성 변경 자동화와 검증 연계

# 📝 【답안용】 시험 답안 템플릿

> 목적: NMS 출제 시 구성요소·FCAPS·장애 처리 흐름·운영 지표를 답안으로 전개한다.

## 핵심 인사이트 (3줄 요약)

> 1. **본질**: NMS는 네트워크 장비의 장애·성능·구성·보안 정보를 수집해 중앙에서 감시·분석·대응하는 운영 플랫폼이다.
> 2. **가치**: MTTA, MTTR, configuration drift, SLA 위반 시간을 수치화해 운영 품질을 관리한다.
> 3. **판단 포인트**: 단순 모니터링이 아니라 FCAPS, 토폴로지, 이벤트 상관분석, ITSM 연계를 포함해야 한다.

## 출제 의도 및 답안 포인트

| 출제 의도 | 반드시 짚을 핵심 | 감점 회피 포인트 |
|:---|:---|:---|
| 관리 기능 체계 이해 확인 | FCAPS, 장애·성능·구성·보안 관리 | 대시보드 기능만 서술 |
| 운영 프로세스 설계 확인 | 수집, 상관분석, 티켓, 조치, 검증 | 알림 발생 후 조치 흐름 누락 |
| 자동화·감사 관점 확인 | 변경 이력, 구성 백업, RBAC, 감사로그 | 관리자 계정 통제 누락 |

> 요약: 이 문제는 NMS를 관측 도구가 아니라 네트워크 운영 통제 체계로 설명해야 한다.

---

## Ⅰ. 개요 및 필요성

- 개요: 네트워크 운영 정보 중앙 관리
- 배경: 대규모 네트워크에서 장애 탐지, 구성 변경, 성능 추세, 보안 이벤트를 분리 처리하면 MTTR이 증가한다.
- 필요성: NMS는 FCAPS 기준으로 운영 데이터를 통합해 SLA 위반과 구성 편류를 탐지한다.

---

## Ⅱ. 구조 및 구성요소

```text
Network Devices -> Polling/Trap/Syslog/Flow/API
                -> NMS Collector -> Event Correlation -> Dashboard / Ticket / Report
```

| 구성요소 | 역할 | 특이사항 |
|:---|:---|:---|
| 수집 모듈 | SNMP, Syslog, NetFlow, ICMP, API 수집 | 1분 polling, trap 실시간 |
| 인벤토리·토폴로지 | 장비, 링크, 의존관계 관리 | LLDP/CDP, CMDB 연계 |
| 이벤트 엔진 | 중복 알림 제거와 상관분석 | root cause 후보 산출 |
| 운영 포털 | 대시보드, 티켓, 리포트 제공 | RBAC, 감사로그 필요 |

> 요약: NMS는 수집기, 토폴로지, 이벤트 엔진, 운영 포털이 결합된 중앙 관제 구조다.

---

## Ⅲ. 동작원리 및 흐름도

```text
장비 등록 -> 지표/로그 수집 -> 이벤트 정규화
-> 상관분석 -> 티켓 생성 -> 조치/검증 -> 리포트
```

| 단계 | 처리 내용 | 검증 기준 |
|:---:|:---|:---|
| 1 | 장비 인벤토리, SNMP v3, Syslog 대상 등록 | 등록 장비 100% 수집 |
| 2 | KPI, trap, log, flow 데이터 수집 | 누락률 1% 이하 |
| 3 | 이벤트 severity와 의존관계 정규화 | 중복 알림 50% 이상 감소 |
| 4 | 장애 티켓 생성과 담당자 라우팅 | MTTA 5분 이하 |
| 5 | 조치 후 복구 확인과 RCA 보고 | MTTR, 재발률 기록 |

> 요약: NMS 운영은 장비 등록부터 수집, 상관분석, 티켓, 복구 검증까지 폐루프로 진행된다.

## Ⅳ. 특징

| 구분 | 기존/대안 | NMS | 수치 컬럼 |
|:---|:---|:---|:---|
| 장애 처리 | 장비별 수동 접속 | 중앙 이벤트 상관분석 | MTTA 5분 이하 |
| 구성 관리 | 변경 후 문서 수기 갱신 | 구성 백업·drift 탐지 | drift 24시간 내 탐지 |
| 성능 관리 | 순간 사용률 확인 | 추세·예측 기반 용량 관리 | 사용률 70% 7일 지속 |
| 보안 운영 | 공용 계정 접속 | RBAC·감사로그 | 관리자 명령 100% 기록 |

> 요약: NMS는 장애 처리 시간을 줄이고 구성·성능·보안 통제를 운영 지표로 관리하게 한다.

## Ⅴ. 심화 비교 및 적용 판단

| 비교 축 | 기존/대안 | 본 키워드 | 선택 기준 |
|:---|:---|:---|:---|
| 감시 방식 | Ping, 개별 CLI | SNMP·Syslog·Flow 통합 | 장비 50대 이상 또는 SLA 운영 |
| 장애 분석 | 알림 단건 처리 | topology 기반 root cause | 회선·장비 의존관계 존재 |
| 운영 연계 | 메일 알림 | ITSM·CMDB·자동화 연계 | 변경 승인·감사 요구 |

> 요약: NMS는 장비 수와 운영 통제 요구가 커질수록 단순 모니터링보다 우선 적용한다.

| 리스크 | 원인 | 대응 방안 | 확인 지표 |
|:---|:---|:---|:---|
| 알림 폭주 | 임계치·의존관계 미설계 | event correlation, maintenance window | 중복 알림 50% 감소 |
| 구성 편류 | 수동 변경 누적 | nightly backup, diff, 승인 워크플로 | unauthorized change 0건 |
| 관리 권한 오남용 | 공용 계정·로그 미흡 | RBAC, MFA, command logging | 관리자 행위 100% 추적 |

> 요약: NMS 품질은 알림 정제, 구성 통제, 관리자 감사 체계로 좌우된다.

| 점검 항목 | 목표 기준 | 측정 방법 |
|:---|:---|:---|
| 장애 대응 | MTTA 5분 이하, MTTR 30분 이하 | NMS·ITSM 티켓 로그 |
| 수집 품질 | 장비 수집 성공률 99% 이상 | polling success rate |
| 구성 통제 | 백업 성공률 99%, drift 24시간 내 탐지 | config diff report |

> 요약: NMS 도입 효과는 장애 대응 시간, 수집 성공률, 구성 편류 탐지로 측정한다.

## Ⅵ. 실무 적용 및 결론

**적용 방안 3개 (필수 — 단계별 또는 항목별):**
1. FCAPS 범위 설정: Fault, Configuration, Accounting, Performance, Security별 수집 대상과 보존 기간 수립
2. 장비 연동 표준화: SNMP v3, Syslog TLS, NetFlow/IPFIX, RESTCONF API를 장비군별 적용
3. 운영 프로세스 연계: NMS 알림을 ITSM 티켓, CMDB, Ansible 변경 검증과 연결

**결론 (2줄):**
- 기술사 판단: 장비 수 50대 이상 또는 SLA 계약망은 NMS로 MTTA·MTTR·drift를 통제해야 함
- 향후 방향: streaming telemetry와 AIOps를 결합해 장애 예측, 경보 억제, 원인 후보 자동 제시로 확장
