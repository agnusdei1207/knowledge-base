# 📖 【암기용】 개념 완전 이해

> 목적: CAN 버스를 차량 제어 네트워크 관점에서 이해하게 만든다. 시험 답안 양식이 아니라, 이해를 위한 친절한 설명이다.

## 한눈에
- **개요**: 차량 ECU들이 두 가닥 버스에서 메시지 ID 우선순위로 통신하는 제어망
- **왜 필요한가**: 차량에는 엔진, 브레이크, 변속기, 차체 제어 ECU가 많고, 배선을 1:1로 연결하면 무게와 고장점이 급증한다.
- **핵심 직관**: CAN은 여러 ECU가 한 회의실에서 동시에 말하려 할 때, 낮은 숫자의 arbitration ID를 가진 메시지가 먼저 말하도록 정한 규칙이다.

## 깊이 이해
- **배경·문제의식**: 자동차 전장화로 ECU 수가 증가하면서 배선 하네스와 실시간 제어 메시지 충돌을 줄일 필요가 생겼다. CAN은 ISO 11898 기반 멀티마스터 버스로 1Mbps(Classical CAN)와 더 높은 데이터 구간을 쓰는 CAN FD를 지원한다.
- **작동 원리**: 모든 노드는 버스 상태를 보며 송신한다. dominant 비트와 recessive 비트의 유선 AND 특성 때문에 송신 중 더 높은 우선순위 ID가 감지되면 낮은 우선순위 노드는 즉시 양보한다.
- **비유**: 번호표가 낮은 응급 환자가 먼저 진료실에 들어가고, 나머지는 자기 차례를 다시 기다리는 방식과 같다.
- **구체 예시**: 브레이크 제어 메시지 ID 0x080과 창문 제어 메시지 ID 0x400이 동시에 송신되면 0x080 메시지가 arbitration에서 승리한다.
- **흔한 오해·주의점**: CAN ID는 송신 노드 주소가 아니라 메시지 의미와 우선순위를 나타낸다. 주소 기반 네트워크처럼 이해하면 arbitration과 필터링을 잘못 설명하게 된다.

## 연결 개념
- CAN FD — 데이터 필드와 데이터 구간 비트율 확장
- SOME/IP — 차량 이더넷 서비스 통신
- AUTOSAR — 차량 SW와 통신 스택 표준

# 📝 【답안용】 시험 답안 템플릿

> 목적: 시험장에서 25분에 그대로 쓰는 답안 양식. 작성방식(추상표현 금지·수치·도식·문제유형 전환)을 엄격히 지킨다.
> 핵심: CAN 답안은 버스 구조, arbitration ID, 오류 처리, 차량 이더넷과의 역할 분담을 함께 제시해야 한다.

## 핵심 인사이트 (3줄 요약)

> 1. **본질**: CAN Bus는 차량 ECU가 단일 공유 매체에서 메시지 ID 우선순위로 충돌을 해결하는 멀티마스터 직렬 통신이다.
> 2. **가치**: 1:1 배선을 줄이고 엔진·브레이크·차체 제어 메시지를 1Mbps 이하 제어망에서 결정적 우선순위로 전달한다.
> 3. **판단 포인트**: 제어 메시지는 CAN, 대용량·서비스 통신은 Ethernet/SOME/IP로 분리하는 차량 E/E 아키텍처 판단이 필요하다.

## 출제 의도 및 답안 포인트

| 출제 의도 | 반드시 짚을 핵심 | 감점 회피 포인트 |
|:---|:---|:---|
| 차량 제어망 원리 확인 | ISO 11898, arbitration ID, dominant/recessive | CAN ID를 송신 노드 주소로 오해 |
| 충돌·오류 처리 이해 확인 | 비파괴 arbitration, CRC, ACK, error frame | CSMA/CD와 동일하게 설명 |
| 차량 이더넷 전환 판단 확인 | CAN, CAN FD, LIN, FlexRay, Ethernet 역할 | 모든 차량 통신을 CAN으로 설명 |

> 요약: CAN 문제는 공유 버스에서 충돌을 없애는 방식보다 우선순위가 낮은 노드가 양보하는 원리를 정확히 써야 한다.

## Ⅰ. 개요 및 필요성

- 개요: 차량 ECU 공유 제어버스
- 배경: 차량 ECU 증가로 하네스 중량, 커넥터 고장점, 제어 메시지 충돌 관리가 문제로 부상함.
- 필요성: 엔진·브레이크·조향 메시지를 10ms 이하 주기로 교환하려면 우선순위 기반 매체 접근이 필요함.
- 범위: Classical CAN, CAN FD, 게이트웨이, 차량 이더넷 연동을 함께 판단함.

---

## Ⅱ. 구조 및 구성요소

```text
ECU A -> CAN Transceiver -> CAN High/Low Bus -> CAN Transceiver -> ECU B
ECU C -> CAN Controller  -> Arbitration ID / CRC / ACK / Error Frame
Gateway -> CAN Domain / Ethernet Domain
```

| 구성요소 | 역할 | 특이사항 |
|:---|:---|:---|
| ECU | 센서 처리와 제어 로직 실행 | 엔진, ABS, BCM 등 |
| CAN Controller | 프레임 생성·필터링·오류 카운터 관리 | arbitration ID 기반 |
| CAN Transceiver | 논리 신호와 차동 신호 변환 | CAN_H, CAN_L |
| Bus | 모든 노드가 공유하는 물리 매체 | 종단저항 120ohm |
| Gateway | CAN 도메인 간 라우팅 | Ethernet, diagnostics 연동 |

> 요약: CAN 구조는 ECU, 컨트롤러, 트랜시버, 공유 버스, 게이트웨이가 메시지 ID 중심으로 결합된 구조이다.

---

## Ⅲ. 동작원리 및 흐름도

```text
ECU 메시지 생성 -> Arbitration ID 송신 -> 버스 비트 비교
-> 우선순위 승리 노드 전송 -> CRC/ACK 확인 -> 수신 ECU 필터링
-> 오류 감지 시 Error Frame/재전송
```

| 단계 | 처리 내용 | 검증 기준 |
|:---:|:---|:---|
| 1 | ECU가 데이터와 arbitration ID를 프레임화 | ID 설계표, 주기 |
| 2 | 여러 노드가 SOF 이후 ID 비트를 동시 송신 | dominant/recessive 규칙 |
| 3 | 낮은 우선순위 노드가 버스 점유를 양보 | arbitration loss count |
| 4 | 수신 노드가 CRC, ACK, 필터를 확인 | CRC error, ACK error |
| 5 | 오류 노드가 error passive 또는 bus-off로 전환 | TEC/REC 카운터 |

> 요약: CAN은 메시지 ID 비트 비교로 충돌을 비파괴적으로 해결하고 CRC·ACK·오류 카운터로 전송 신뢰성을 점검한다.

---

## Ⅳ. 특징

| 구분 | CAN Bus | CAN FD | 차량 Ethernet |
|:---|:---|:---|:---|
| 대역폭 | Classical CAN 최대 1Mbps | 데이터 구간 2~8Mbps 사용 | 100Mbps~1Gbps |
| 접근 방식 | ID 우선순위 arbitration | 동일 arbitration 후 데이터 구간 확장 | 스위치 기반 전이중 |
| 적용 영역 | 제어·진단 | 제어 데이터 확장 | ADAS, 인포테인먼트, SOME/IP |
| 판단 포인트 | 실시간 우선순위 | 프레임 길이 증가 | 대용량 서비스 통신 |

> 요약: CAN은 우선순위 제어 메시지에 적합하고, 차량 Ethernet은 대역폭이 필요한 서비스·센서 데이터에 적용한다.

## Ⅴ. 심화 비교 및 적용 판단

| 구분 | 기존/대안 | CAN Bus | 선택 기준 |
|:---|:---|:---|:---|
| 배선 | ECU 1:1 연결 | 공유 2선 버스 | 하네스 중량과 ECU 수 |
| 통신 | LIN 저속 제어 | CAN 중속 제어 | 10ms~100ms 제어 주기 |
| 아키텍처 | 도메인별 CAN | CAN+Ethernet Gateway | ADAS·OTA 요구 |

> 요약: CAN은 저비용 제어망으로 유지하고 대용량·서비스 지향 통신은 게이트웨이를 통해 Ethernet으로 분담한다.

| 리스크 | 원인 | 대응 방안 | 확인 지표 |
|:---|:---|:---|:---|
| 우선순위 역전 | ID 설계 오류 | 안전 관련 메시지 낮은 ID 배정 | latency worst-case |
| Bus-off | 배선 노이즈·노드 오류 | 종단저항 점검, 오류 카운터 모니터링 | TEC/REC, bus-off count |
| 위조 메시지 | 인증 없는 브로드캐스트 | Gateway 필터, IDS, Secure Onboard Communication | 비정상 ID 빈도 |

> 요약: CAN 리스크는 ID 설계, 물리 배선, 메시지 위조이며 지연시간·오류 카운터·비정상 ID로 점검한다.

| 점검 항목 | 목표 기준 | 측정 방법 |
|:---|:---|:---|
| 지연시간 | 안전 메시지 주기 10ms 이내 | CAN analyzer |
| 버스 부하 | 평균 30~50%, 피크 70% 이하 | bus load measurement |
| 오류 상태 | bus-off 0건, CRC error 추적 | ECU DTC, 로그 |

> 요약: CAN 운영 품질은 버스 부하, 최악 지연시간, 오류 상태 카운터로 판단한다.

---

## Ⅵ. 실무 적용 및 결론

**적용 방안 3개 (필수 — 단계별 또는 항목별):**
1. 안전·제어 메시지에 낮은 arbitration ID를 배정하고, 차체·편의 메시지는 높은 ID로 분리함.
2. CAN analyzer로 bus load, worst-case latency, error frame을 측정하고 피크 부하 70% 초과 시 CAN FD 또는 도메인 분리를 검토함.
3. Gateway에서 허용 ID 목록, 진단 세션 제한, 차량 IDS를 적용해 비정상 프레임과 진단 남용을 탐지함.

**결론 (2줄):**
- 기술사 판단: 제어 주기와 우선순위가 핵심이면 CAN, 대용량 센서·서비스 통신이면 Ethernet/SOME-IP를 선택함.
- 향후 방향: 차량 E/E 아키텍처는 CAN 제어망과 Ethernet 백본을 결합하고, 보안 게이트웨이와 IDS를 기본 구성으로 포함함.
