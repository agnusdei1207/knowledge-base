## 미리 알고가기

- rwnd: 수신 측이 현재 받을 수 있다고 광고한 윈도우 크기임
- 슬라이딩 윈도우: 확인 응답이 올 때마다 송신 가능 구간이 앞으로 이동하는 방식임
- Zero Window: 수신 버퍼가 꽉 차 더 받지 못함을 알리는 상태임
- Window Scale: 기본 16비트 윈도우 한계를 넘어 더 큰 윈도우를 쓰게 하는 옵션임

## Ⅰ. 개요

- **정의/개념**: TCP 흐름 제어는 송신 속도가 수신 애플리케이션 처리 속도를 넘지 않도록 수신 측 버퍼 여유를 기준으로 송신량을 조절하는 메커니즘임. 핵심 도구는 수신 측이 광고하는 윈도우와 이를 연속 전송에 활용하는 슬라이딩 윈도우 구조임
- **배경/필요성**: 빠른 송신자가 느린 수신자에게 계속 데이터를 밀어 넣으면 수신 버퍼가 넘쳐 패킷이 버려지므로, 네트워크가 아닌 수신 측 처리 한계를 반영한 별도 제어가 필요함

## Ⅱ. 특징

- 수신 측이 현재 남은 버퍼 크기를 광고하므로 송신자는 실제 수신 가능량 안에서만 전송함
- 슬라이딩 윈도우를 사용하면 ACK를 기다리는 동안에도 여러 세그먼트를 연속으로 보내 정지-대기의 전송 공백을 줄임
- Zero Window가 발생하면 송신자는 전송을 멈추고 윈도우가 다시 열릴 때까지 기다려야 함
- 장거리 고속망에서는 기본 윈도우만으로 대역폭을 충분히 채우기 어려워 Window Scale이 중요해짐

## Ⅲ. 종류 및 비교

| 판단 기준 | 정지-대기 방식 | 슬라이딩 윈도우 방식 |
|:---|:---|:---|
| 전송 방식 | 세그먼트 하나를 보내고 ACK를 받을 때까지 기다림 | 허용된 윈도우 크기만큼 연속 전송한 뒤 ACK에 따라 구간을 이동함 |
| 링크 활용도 | RTT가 길수록 전송 공백이 커짐 | RTT가 길어도 파이프라인 형태로 링크를 더 채울 수 있음 |
| 구현 복잡도 | 미확인 세그먼트가 하나라 상태 관리가 단순함 | 여러 미확인 세그먼트의 순서와 버퍼를 관리해야 함 |
| 적합한 환경 | 매우 단순한 제어가 필요한 환경에 적합함 | 일반 TCP 데이터 전송에 기본으로 적합함 |

> 요약: 흐름 제어의 핵심 차이는 얼마나 연속으로 보내고, ACK에 맞춰 윈도우를 어떻게 이동시키느냐에 있음

## Ⅳ. 구성요소 및 구조

| 구성요소 | 설명 |
|:---|:---|
| 송신 버퍼 | 아직 확인받지 못한 데이터와 앞으로 보낼 데이터를 보관함 |
| 수신 버퍼 | 애플리케이션이 읽기 전까지 데이터를 임시로 저장하며 여유 공간이 rwnd에 반영됨 |
| ACK와 rwnd | 어디까지 받았는지와 얼마나 더 받을 수 있는지를 송신자에게 동시에 알려 줌 |
| Window Scale | 대역폭이 큰 회선에서 충분한 송신량을 유지하도록 윈도우 범위를 확장함 |

```text
+-------------- Sender Window --------------+
| Acked | Sent not Acked | Can Send | Closed |
+-------------------------------------------+
```

> 요약: 흐름 제어는 송신 버퍼, 수신 버퍼, ACK, rwnd가 맞물려야 안정적으로 동작함

## Ⅴ. 원리 및 절차 흐름도

```text
+----------+     +----------+     +----------+     +----------+
| 윈도우광고 | --> | 연속전송  | --> | ACK수신   | --> | 윈도우이동 |
+----------+     +----------+     +----------+     +----------+
```

1. **윈도우광고**: 수신 측이 현재 버퍼 여유를 rwnd 값으로 송신 측에 알림
2. **연속전송**: 송신 측이 rwnd 범위 안에서 여러 세그먼트를 연속 전송함
3. **ACK수신**: 수신 측이 받은 구간과 새 버퍼 여유를 ACK에 실어 돌려보냄
4. **윈도우이동**: 송신 측이 확인된 구간을 제거하고 새 전송 구간을 앞으로 이동시킴

## Ⅵ. 실무 적용 및 유의점

1. 장거리 고대역 회선에서는 기본 윈도우만으로 링크를 채우지 못하므로 Window Scale과 버퍼 크기를 함께 조정하고 처리량과 rwnd 광고 값으로 확인함
2. 애플리케이션이 데이터를 너무 늦게 읽는 구간에서는 Zero Window와 작은 윈도우 갱신이 반복될 수 있으므로 수신 애플리케이션 처리 배치를 조정하고 Zero Window 이벤트 수와 재전송 비율로 확인함

## Ⅶ. 결론

TCP 흐름 제어는 수신자가 광고한 버퍼 여유 안에서 연속 전송 범위를 이동하여 버퍼 초과와 전송 공백을 조절함.
