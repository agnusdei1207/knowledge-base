## Ⅰ. 개요
- **정의**: 공용 네트워크 위에 암호화된 터널을 구성하여 사설 네트워크처럼 사용하는 기술임
- **배경/필요성**: 전용선 비용 없이 원격지 간 기밀 통신을 확보해야 하는 수요가 증가함
- **비유**: 공용 고속도로에 전용 터널을 만들어 외부 차량이 진입하지 못하게 하는 것과 유사함

| 출제 의도 | 반드시 짚을 핵심 | 감점 회피 포인트 |
|:---|:---|:---|
| VPN 유형별 비교 | 터널링·암호화·인증 3요소 | IPsec(045)·SSL(046) VPN 구분 필요 |

> 요약: 터널링과 암호화로 공용망에서 사설망 수준 보안을 제공하는 기술임

## Ⅱ. 구성요소
```text
Remote User ---> VPN Client ---[Encrypted Tunnel]---> VPN Gateway ---> Internal Network
                                  |
                          Public Internet
```

| 구성요소 | 설명 | 비유 |
|:---|:---|:---|
| VPN Client | 터널 생성·암호화를 수행하는 사용자 측 소프트웨어 | 터널 입구의 검문소 |
| VPN Gateway | 터널을 종단하고 내부망에 트래픽을 전달하는 장비 | 터널 출구의 검문소 |
| 터널링 프로토콜 | 원본 패킷을 캡슐화하는 프로토콜(IPsec, SSL, L2TP 등) | 소포를 감싸는 포장지 |
| 인증/키 교환 | 상호 신원 확인 및 세션 키 협상 메커니즘 | 비밀번호를 교환하는 악수 |

> 요약: 클라이언트-터널-게이트웨이 구조로 암호화된 가상 사설망을 형성함

## Ⅲ. 절차
```text
Client -> 인증 요청 -> Gateway -> 인증 응답/키 협상 -> Client
Client -> 패킷 캡슐화 -> 암호화 전송 -> Gateway -> 복호화/역캡슐화 -> 내부망
```
- 1단계: VPN 클라이언트가 게이트웨이에 인증 요청(ID/PW, 인증서 등)을 전송함
- 2단계: 상호 인증 완료 후 키 교환 프로토콜(IKE 등)로 세션 키를 협상함
- 3단계: 원본 IP 패킷을 터널링 프로토콜로 캡슐화 후 세션 키로 암호화하여 전송함
- 4단계: 게이트웨이가 수신 패킷을 복호화·역캡슐화하여 내부 목적지로 라우팅함

> 요약: 인증-키협상-캡슐화/암호화-복호화/라우팅의 4단계로 동작함

## Ⅳ. 문제점
- 성능 저하: 암호화·캡슐화 오버헤드로 처리량(throughput) 감소 및 지연 증가
- Split Tunneling 위험: 터널 외부 트래픽이 보안 정책을 우회할 수 있음
- 단일 게이트웨이 병목: 전체 원격 트래픽이 한 지점에 집중되어 가용성 저하

> 요약: 오버헤드·정책 우회·병목이 VPN 운용의 주요 과제임

## Ⅴ. 개선방안
1. 단기: 하드웨어 가속(AES-NI) 적용으로 암호화 처리 성능을 개선함
2. 중기: ZTNA(Zero Trust) 모델 적용으로 Split Tunneling 없이 앱 단위 접근 제어
3. 장기: SD-WAN 통합으로 다중 경로 분산 및 게이트웨이 이중화 구현

> 요약: HW 가속·ZTNA·SD-WAN으로 VPN 한계를 보완함

## Ⅵ. 전망
- 발전 방향: SASE(Secure Access Service Edge) 아키텍처로 VPN 기능이 클라우드에 통합되는 추세임
- 기술사적 판단: 전통 VPN은 ZTNA로 점진적 전환되나 Site-to-Site 용도는 지속 유지 전망
- 기술사 제언: IPsec(045 참조)·SSL VPN(046 참조) 선택 시 보안 요건·사용자 환경을 고려해야 함
