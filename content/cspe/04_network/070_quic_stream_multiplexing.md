## Ⅰ. 개요
| 항목 | 내용 |
|---|---|
| **정의** | UDP 기반 전송 기술 QUIC에서 여러 독립된 데이터 스트림을 하나의 연결 내에서 병렬로 통신하는 방식 |
| **배경/필요성** | HTTP/2 over TCP 구조의 단점인 패킷 하나 유실 시 전체 통신이 중단되는 HOL Blocking 현상 타파 필요 |
| **출제 의도** | 0-RTT/1-RTT 연결 구조의 효율성과 스트림 독립에 따른 통신 지연시간 최소화 메커니즘 평가 |

## Ⅱ. 구성요소
```text
+----------+       +----------+
| Stream 1 | ----> | UDP Con. |
| Stream 2 | ----> | (QUIC)   |
+----------+       +----------+
```
| 구성요소 | 설명 | 비유 |
|---|---|---|
| 독립 스트림 | 논리적으로 분리되어 하나의 패킷 손실이 다른 스트림 대기를 유발하지 않음 | 독립적 고속 톨게이트 |
| UDP 통신 | 복잡한 TCP 제어를 버리고 OS 유저 레벨에서 혼잡/암호화를 자체 구현 | 빠른 오토바이 배달 |
| 0-RTT 핸드쉐이크 | 초기 연결과 TLS 1.3 암호화를 동시 처리하여 접속 대기 시간을 극도로 단축 | 원패스 프리패스 |

> 요약: 단일 연결 속에 다수의 독립된 통로를 생성하여 특정 패킷 손실에 따른 연쇄 지연을 완벽 차단함

## Ⅲ. 절차
```text
+----------+    +----------+    +----------+    +----------+
| 연결 수립| -> | 스트림할당| -> | 병렬 전송| -> | 개별 복구|
+----------+    +----------+    +----------+    +----------+
```
1. 연결 수립: 클라이언트와 서버가 UDP 기반에서 1-RTT로 암호화 터널 및 QUIC 연결 수립
2. 스트림할당: 웹페이지 내 다수 자원(HTML, CSS 등)마다 논리적 QUIC 스트림 ID 독립 할당
3. 병렬 전송: 다중화된 스트림 데이터를 단일 UDP 포트를 통해 동시 다발적으로 송수신
4. 개별 복구: 스트림 1의 패킷 유실 시에도, 정상 도착한 스트림 2의 데이터는 즉각 앱으로 전달

> 요약: UDP 연결 위에 논리적 채널을 분리하여 각 자원을 간섭 없이 병렬 통신함

## Ⅳ. 문제점
- OS 커널이 아닌 유저 공간(User Space)에서 암호화와 혼잡 제어 연산을 수행하여 서버 CPU 부하 상승 원인
- 기업 망 방화벽 정책 상 포트 443 기반 UDP 트래픽을 비정상으로 간주하고 전면 차단 (TCP Fallback 발생)
- QUIC 패킷 헤더의 대부분이 암호화되어 통신 사업자의 트래픽 품질 모니터링 및 방화벽 IPS 차단 불가

## Ⅴ. 개선방안
- [단기] 커널 우회 고속 패킷 처리(eBPF, XDP) 기술 도입으로 QUIC 웹서버의 프로세싱 부하 경감
- [중기] QUIC Spin Bit 옵션을 허용하여 중간 네트워크 모니터링 장비에서 제한적인 패킷 지연(RTT) 측정 지원
- [장기] 암호화 트래픽 검사(Decryption Proxy)를 지원하는 차세대 방화벽(NGFW) 도입 및 전용 정책 정비

## Ⅵ. 전망
- 모든 최신 웹 브라우저와 HTTP/3 표준의 근간으로 확정되어 향후 사실상 인터넷 통신의 지배적 구조가 될 전망임
