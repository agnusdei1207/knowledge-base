## Ⅰ. 개요
- **정의**: 하나의 물리 PCIe 장치를 여러 가상 함수로 분할하여 VM이 직접 접근하게 하는 I/O 가상화 표준임
- **배경/필요성**: 하이퍼바이저 소프트웨어 스위치 경유 시 패킷 처리 지연과 CPU 오버헤드가 VM 수에 비례하여 증가함
- **비유**: 하나의 고속도로에 전용 차선을 배정하여 각 차량이 톨게이트 없이 통과하는 것과 유사함

| 출제 의도 | 반드시 짚을 핵심 | 감점 회피 포인트 |
|:---|:---|:---|
| HW 기반 I/O 가상화 원리와 성능 이점 | PF/VF 구분, 하이퍼바이저 바이패스 | SR-IOV와 MR-IOV 차이, VF 수 제한 언급 필요 |

> 요약: SR-IOV는 물리 장치를 VF로 분할하여 VM이 하이퍼바이저 없이 I/O에 직접 접근하는 표준임

## Ⅱ. 구성요소
```text
Physical NIC (PF)
    |
    +--- VF 0 ---> VM 0
    +--- VF 1 ---> VM 1
    +--- VF n ---> VM n
    |
IOMMU (VT-d / AMD-Vi)
```

| 구성요소 | 설명 | 비유 |
|:---|:---|:---|
| PF (Physical Function) | NIC 전체를 제어하는 물리 함수로 VF 생성·관리를 담당함 | 건물 관리실 |
| VF (Virtual Function) | 경량화된 PCIe 함수로 VM에 할당되어 독립 I/O 경로를 제공함 | 전용 차선 |
| IOMMU | DMA 주소를 VM별로 격리하여 메모리 보호를 수행함 | 차선 간 방호벽 |
| Mailbox | PF-VF 간 제어 명령을 교환하는 통신 채널임 | 관리실 내선전화 |

> 요약: PF가 VF를 생성하고 IOMMU가 메모리를 격리하여 VM별 독립 I/O 경로를 제공함

## Ⅲ. 절차
```text
PF 드라이버 로드 --> VF 생성 --> IOMMU 매핑 --> VM에 VF 할당
```
- 1단계: 호스트에서 PF 드라이버를 로드하고 SR-IOV Capability를 활성화함
- 2단계: PF 드라이버가 요청된 수만큼 VF를 PCIe 설정 공간에 생성함
- 3단계: IOMMU가 각 VF의 DMA 영역을 VM 메모리에 매핑하여 격리함
- 4단계: 하이퍼바이저가 VF를 VM에 패스스루로 할당하여 직접 I/O를 수행함

> 요약: PF에서 VF를 생성하고 IOMMU 매핑 후 VM에 패스스루 할당하는 절차임

## Ⅳ. 문제점
- 라이브 마이그레이션 제약: VF가 물리 장치에 직접 바인딩되어 VM 이동 시 VF 해제·재할당이 필요함
- VF 수 제한: PCIe 설정 공간 크기에 따라 NIC당 VF 수가 고정되어 고밀도 환경에서 부족함
- 관리 복잡성: VF별 VLAN·QoS·보안 정책을 PF 드라이버에서 개별 설정해야 하여 운영 부담이 큼

> 요약: 마이그레이션 제약, VF 수 한계, 정책 관리 복잡성이 운영 과제임

## Ⅴ. 개선방안
1. 단기: VF 상태 저장·복원 기능을 드라이버에 구현하여 라이브 마이그레이션 지원함
2. 중기: Scalable IOV·SIOV 표준 도입으로 VF 수 제한을 소프트웨어적으로 확장함
3. 장기: SmartNIC 기반 통합 정책 엔진(083 참조)으로 VF별 정책을 일괄 관리함

> 요약: 상태 저장, SIOV 확장, SmartNIC 통합으로 단계적 개선이 필요함

## Ⅵ. 전망
- 발전 방향: SIOV·VFIO 프레임워크 발전으로 컨테이너 환경까지 하드웨어 I/O 가상화가 확대됨
- 기술사적 판단: 클라우드 네트워크 성능의 기반 기술로 NFV·5G UPF 가속에 활용 범위가 넓어짐
- 기술사 제언: SR-IOV 도입 시 IOMMU 그룹 설계와 VF 용량 산정을 사전에 계획해야 함
