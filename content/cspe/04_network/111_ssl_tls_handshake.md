## Ⅰ. 개요
- **정의**: 클라이언트-서버 간 암호 스위트 협상과 세션 키 교환을 수행하는 연결 수립 절차
- **배경/필요성**: 평문 통신은 도청·변조에 노출되므로 통신 전 상호 인증과 암호화 파라미터 합의가 필요함
- **비유**: 두 사람이 대화 전 공통 언어와 비밀 암호표를 먼저 정하는 것과 유사함

| 출제 의도 | 반드시 짚을 핵심 | 감점 회피 포인트 |
|:---|:---|:---|
| 핸드셰이크 단계별 메시지 흐름 이해 | ClientHello-ServerHello-키교환-Finished 4단계 | TLS 1.3의 1-RTT 축소 변경점 누락 주의 |

> 요약: 보안 통신 전 암호 파라미터를 협상하고 세션 키를 생성하는 절차임

## Ⅱ. 구성요소
```text
Client                        Server
  |--- ClientHello ------------>|
  |<-- ServerHello, Cert -------|
  |--- KeyExchange, Finished -->|
  |<-- Finished ----------------|
  |<== Encrypted Session ======>|
```

| 구성요소 | 설명 | 비유 |
|:---|:---|:---|
| ClientHello | 지원 암호 스위트·랜덤값 전송 | 자기소개와 사용 가능 언어 목록 제시 |
| ServerHello/Certificate | 암호 스위트 선택·서버 인증서 전달 | 상대가 언어 선택 후 신분증 제시 |
| Key Exchange | Pre-Master Secret 교환으로 세션 키 생성 | 공통 비밀 암호표 생성 |
| Finished | 핸드셰이크 무결성 검증 메시지 교환 | 합의 내용 최종 확인 서명 |

> 요약: 4개 메시지 교환으로 암호 스위트 합의·인증·키 생성을 완료함

## Ⅲ. 절차
```text
ClientHello -> ServerHello/Cert -> KeyExchange -> Finished
```
- 1단계: ClientHello — 클라이언트가 지원 암호 스위트·TLS 버전·랜덤 넌스를 서버에 전송함
- 2단계: ServerHello — 서버가 암호 스위트 선택 후 인증서와 랜덤 넌스를 응답함
- 3단계: Key Exchange — 클라이언트가 Pre-Master Secret을 서버 공개키로 암호화 전송하여 세션 키를 도출함
- 4단계: Finished — 양측이 핸드셰이크 해시를 교환하여 무결성을 검증하고 암호화 통신을 개시함

> 요약: 협상-인증-키생성-검증 4단계로 보안 채널을 수립함

## Ⅳ. 문제점
- RTT 지연: 풀 핸드셰이크 시 2-RTT 소요 — 모바일·저대역폭 환경에서 체감 지연 증가
- 인증서 검증 부하: 인증서 체인 검증에 공개키 연산 다수 발생 — 대량 연결 시 서버 CPU 부하 증가
- 하위 호환 취약점: 레거시 클라이언트 지원을 위한 다운그레이드 협상 — 약한 암호 스위트 선택 가능성 존재

> 요약: 지연·연산 부하·다운그레이드 공격이 핵심 문제임

## Ⅴ. 개선방안
1. 단기: TLS 1.3 적용으로 1-RTT 핸드셰이크 및 0-RTT 재연결을 통해 지연 감소
2. 중기: OCSP Stapling·세션 티켓 활용으로 인증서 검증 및 재연결 시 연산 부하 경감
3. 장기: 레거시 프로토콜 퇴출 정책 수립으로 다운그레이드 공격 원천 차단

> 요약: 프로토콜 최신화·검증 최적화·레거시 퇴출로 개선함

## Ⅵ. 전망
- 발전 방향: TLS 1.3 기반 0-RTT 확산과 양자내성 키 교환 알고리즘 통합이 진행됨
- 기술사적 판단: 핸드셰이크 효율화와 암호 강도 강화는 동시에 추구해야 하는 과제임
- 기술사 제언: 양자컴퓨팅 대비 PQC 하이브리드 핸드셰이크 도입 로드맵 수립이 필요함
