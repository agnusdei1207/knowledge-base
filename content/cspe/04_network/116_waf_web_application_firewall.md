# 📖 【암기용】 개념 완전 이해

> 목적: WAF를 웹 애플리케이션 공격을 HTTP 계층에서 탐지·차단하는 통제 장치로 이해하게 만든다.

## 한눈에
- **개요**: WAF는 HTTP 요청과 응답을 검사해 SQL Injection, XSS, 파일 업로드 공격 같은 웹 공격을 차단하는 보안 장비 또는 서비스이다.
- **왜 필요한가**: 네트워크 방화벽은 포트 443 허용 여부를 보지만, 로그인 파라미터와 쿠키에 담긴 공격 문자열은 애플리케이션 계층에서 봐야 한다.
- **핵심 직관**: 건물 입구에서 신분증만 확인하는 경비가 아니라, 제출 서류 내용까지 검사하는 접수 담당자에 가깝다.

## 깊이 이해
- **배경·문제의식**: 웹 서비스는 외부 공개가 필수이고, 취약한 입력값 검증은 계정 탈취, DB 유출, 웹셸 업로드로 이어진다.
- **작동 원리**: WAF는 Reverse Proxy 또는 Inline 방식으로 HTTP 메시지를 받아 OWASP CRS, 시그니처, 행위 규칙, 평판 정보를 적용한다.
- **비유**: 택배 상자를 열어 금지 품목, 송장 위조, 위험 물질을 확인한 뒤 통과·반송·격리로 처리하는 절차와 같다.
- **구체 예시**: `/login?id=' OR 1=1--` 요청은 SQL Injection 규칙에 매칭되어 차단되고, 차단 로그는 URI, 파라미터, 룰 ID, 소스 IP를 포함한다.
- **흔한 오해·주의점**: WAF는 취약한 코드를 고치는 도구가 아니다. Secure Coding, SAST/DAST, 패치와 함께 적용해야 한다.

## 연결 개념
- OWASP Top 10 - WAF 정책의 주요 공격 분류 기준
- API Gateway - API 인증·쿼터와 WAF 검사를 결합 가능
- SIEM/SOAR - WAF 이벤트를 상관분석과 대응 자동화에 활용

# 📝 【답안용】 시험 답안 템플릿

> 목적: WAF 답안은 공격 유형, 탐지 방식, 오탐 관리, 증적 지표를 분리해 작성한다.
> 핵심: OWASP CRS, SQL Injection, XSS, RCE, 파일 업로드, Bot 방어와 로그 연계를 구체화한다.

## 핵심 인사이트 (3줄 요약)

> 1. **본질**: WAF는 HTTP/HTTPS 트래픽을 L7에서 검사해 웹 애플리케이션 공격을 탐지·차단하는 보안 통제이다.
> 2. **가치**: 취약점 패치 전 가상 패치, OWASP Top 10 공격 차단, API 요청 검사를 수행한다.
> 3. **판단 포인트**: 탐지 정확도, 오탐 처리, TLS 복호화, 애플리케이션 변경 반영, 로그 증적이 운영 품질을 좌우한다.

## 출제 의도 및 답안 포인트

| 출제 의도 | 반드시 짚을 핵심 | 감점 회피 포인트 |
|:---|:---|:---|
| 웹 공격 통제 이해 확인 | SQLi, XSS, RCE, 파일 업로드, Bot | 방화벽과 WAF를 같은 계층으로 설명 |
| WAF 동작 방식 확인 | Reverse Proxy, Signature, Positive policy, OWASP CRS | 룰만 쓰고 오탐·튜닝 누락 |
| 운영 증적 제시 확인 | 룰 ID, 차단 로그, 오탐률, 탐지 시간 | "차단한다"로 끝내고 지표 누락 |

> 요약: WAF 문제는 HTTP 계층 공격을 어떤 규칙과 증적으로 통제하는지 묻는 문제이다.

### 🔑 핵심 용어 정리

| 용어 | 뜻 | 비유 |
|:---|:---|:---|
| **방화벽** | 네트워크 트래픽을 규칙 기반으로 허용/차단하는 보안 장비 | "건물 출입 경비원" |
| **IDS** | 침입 탐지 시스템. 비정상 트래픽을 탐지하여 알림 | "CCTV" |
| **IPS** | 침입 방지 시스템. 탐지 + 자동 차단 | "자동 잠금 시스템" |

## Ⅰ. 개요 및 필요성

- 개요: HTTP 계층 공격 차단 장치
- 배경: 웹 서비스는 80/443 포트를 공개하므로 네트워크 방화벽만으로 입력값 공격을 식별하기 어려움.
- 필요성: OWASP Top 10 공격을 룰 ID, URI, 파라미터 단위로 탐지·차단해야 함.
- 판단 기준: 공개 웹, 로그인, 결제, 파일 업로드, API 엔드포인트에 우선 적용함.

---

## Ⅱ. 구조 및 구성요소

```text
Client -> DNS/CDN -> WAF -> Web/API Server
                  -> Rule Engine -> Allow/Block/Challenge
                  +-> Log -> SIEM/SOAR -> Tuning
```

| 구성요소 | 역할 | 특이사항 |
|:---|:---|:---|
| Reverse Proxy | 클라이언트 요청을 수신하고 서버로 중계 | TLS 종료, 헤더 보존, 원본 IP 전달 |
| Rule Engine | 시그니처와 정책으로 요청을 평가 | OWASP CRS, Custom rule, Positive model |
| Bot/Rate Control | 자동화 공격과 대량 요청을 제한 | CAPTCHA, JS challenge, IP reputation |
| Log Pipeline | 차단·허용 이벤트를 저장 | URI, 파라미터, 룰 ID, 소스 IP 포함 |
| Tuning Process | 오탐 예외와 신규 룰을 관리 | 배포 전 탐지 모드 검증 필요 |

> 요약: WAF는 프록시, 룰 엔진, Bot 제어, 로그, 튜닝 절차가 함께 동작해야 운영 가능하다.

---

## Ⅲ. 동작원리 및 흐름도

```text
HTTP 요청 수신 -> TLS 복호화 -> 정규화/디코딩
-> 룰 매칭 -> 위험 점수 계산 -> 허용/차단/챌린지 -> 로그 저장
```

| 단계 | 처리 내용 | 검증 기준 |
|:---:|:---|:---|
| 1 | 요청 헤더, URI, 쿠키, Body를 수집 | 원본 IP, Host, Content-Type 보존 |
| 2 | URL 인코딩과 압축을 정규화 | 이중 인코딩 우회 탐지 |
| 3 | OWASP CRS와 사용자 정의 룰을 적용 | SQLi, XSS, RCE, LFI 룰 ID |
| 4 | 정책 결과에 따라 허용·차단·챌린지 수행 | 차단 코드, 응답 지연, 사용자 영향 |
| 5 | 이벤트를 SIEM/SOAR로 전송 | 룰 ID, 페이로드 샘플, 처리 결과 |

> 요약: WAF는 HTTP 메시지를 정규화한 뒤 룰을 적용하고, 처리 결과를 증적으로 남긴다.

---

## Ⅳ. 특징

| 구분 | 네트워크 방화벽 | WAF 적용 | 수치·기술 포인트 |
|:---|:---|:---|:---|
| 검사 계층 | L3/L4 IP·포트 | L7 HTTP 파라미터 | URI, Cookie, JSON Body |
| 공격 대응 | 포트 차단 중심 | SQLi, XSS, RCE 차단 | OWASP CRS, CVE virtual patch |
| 정책 방식 | ACL | Negative/Positive policy | Allowlist, schema validation |
| 운영 이슈 | 포트 룰 관리 | 오탐·우회·TLS 복호화 | 오탐률, 룰 튜닝 주기 |

> 요약: WAF는 웹 요청의 의미를 검사하므로 네트워크 방화벽이 보지 못하는 애플리케이션 공격을 통제한다.

## Ⅴ. 심화 비교 및 적용 판단

| 구분 | Signature WAF | Positive Security WAF | 선택 기준 |
|:---|:---|:---|:---|
| 탐지 방식 | 알려진 공격 패턴 매칭 | 허용된 요청 형태만 통과 | API 스키마 보유 여부 |
| 운영 난이도 | 룰 업데이트 중심 | 업무별 학습·예외 관리 | 서비스 변경 빈도 |
| 적용 대상 | 범용 웹 공격 | 결제, 관리자, API | 오탐 허용 수준 |
| 보완 통제 | SIEM 상관분석 | API schema validation | OpenAPI 문서 품질 |

> 요약: 범용 웹은 시그니처 기반, 핵심 API는 Positive policy와 스키마 검증을 병행한다.

| 리스크 | 원인 | 대응 방안 | 확인 지표 |
|:---|:---|:---|:---|
| 오탐 차단 | 정상 파라미터가 공격 룰에 매칭 | 탐지 모드 검증, 예외 룰 승인 | 오탐률, 고객 영향 건수 |
| 우회 공격 | 이중 인코딩, 분할 페이로드 | 정규화, 최신 CRS, 퍼징 테스트 | 우회 재현 건수 |
| TLS 사각 | 종단 암호화로 WAF가 본문 미확인 | WAF TLS 종료, 인증서 관리 | 미검사 트래픽 비율 |
| 로그 과다 | 대량 Bot 요청과 반복 탐지 | 샘플링, 룰별 우선순위 | EPS, 저장 비용, 경보 피로도 |

> 요약: WAF 리스크는 오탐, 우회, TLS 검사, 로그 과다로 나누어 운영 절차와 지표로 관리한다.

| 점검 항목 | 목표 기준 | 측정 방법 |
|:---|:---|:---|
| 탐지 커버리지 | OWASP Top 10 룰 적용 | 룰셋 감사, 모의 공격 |
| 오탐 관리 | 핵심 업무 오탐률 1% 이하 | 티켓 분석, 샘플 리뷰 |
| 대응 시간 | 신규 CVE virtual patch 24시간 이내 | 변경 이력, 승인 기록 |
| 증적 품질 | 룰 ID·URI·소스 IP 100% 기록 | SIEM 필드 매핑 점검 |

> 요약: WAF 운영 성과는 탐지 커버리지, 오탐률, 가상 패치 시간, 로그 필드 완전성으로 판단한다.

---

## Ⅵ. 실무 적용 및 결론

**적용 방안 3개 (필수):**
1. 공개 웹과 API 앞단에 WAF를 Reverse Proxy로 배치하고, TLS 종료와 원본 IP 전달 헤더 정책을 문서화함.
2. OWASP CRS를 탐지 모드로 2주 검증한 뒤 SQLi, XSS, RCE, 파일 업로드 룰을 차단 모드로 전환함.
3. WAF 이벤트를 SIEM/SOAR로 전송하고, 동일 소스 IP의 반복 차단, 관리자 URI 공격, 신규 CVE 룰 적중을 playbook으로 처리함.

**결론 (2줄):**
- 기술사 판단: 외부 공개 웹·API에는 WAF를 필수 통제로 적용하되, 코드 수정과 취약점 진단을 병행해야 함.
- 향후 방향: WAF는 API 보안, Bot 관리, WAAP(Web Application and API Protection) 형태로 확장됨.
