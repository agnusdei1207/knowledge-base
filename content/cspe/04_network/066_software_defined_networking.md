## 미리 알고가기

- 제어 평면은 경로와 정책을 결정하는 부분임
- 데이터 평면은 결정된 규칙대로 패킷을 전달하는 부분임
- 사우스바운드 API는 컨트롤러가 장비에 규칙을 내릴 때 쓰는 인터페이스임
- 화이트박스 스위치는 범용 하드웨어 위주로 구성된 네트워크 장비임

## Ⅰ. 개요

- **정의/개념**: SDN은 제어 평면과 데이터 평면을 논리적으로 분리하고 중앙 컨트롤러가 네트워크 정책과 경로를 소프트웨어로 제어하는 구조임
- **배경/필요성**: 클라우드와 가상화 환경에서는 장비마다 CLI를 수동으로 변경하는 방식이 느리고 오류가 많으므로, 대규모 네트워크를 코드와 API로 빠르게 바꿀 수 있는 중앙 제어 구조가 필요함

## Ⅱ. 특징

- 네트워크 제어를 중앙에 모아 전체 토폴로지와 정책을 한 시야에서 다루기 좋음
- API 기반 자동화와 연계돼 정책 변경과 트래픽 엔지니어링을 빠르게 수행할 수 있음
- 화이트박스와 소프트웨어 조합으로 벤더 종속을 낮출 수 있음
- 중앙화가 강한 만큼 컨트롤러 가용성과 분산 프로토콜과의 역할 분담이 중요함

## Ⅲ. 종류 및 비교

| 판단 기준 | 전통적 분산 네트워크 | SDN |
|:---|:---|:---|
| 제어 방식 | 각 장비가 라우팅 정보와 정책을 개별 판단함 | 중앙 컨트롤러가 전체 정책과 경로를 계산해 배포함 |
| 변경 속도 | 장비별 설정 반영과 검증이 느리고 운영 오차가 생기기 쉬움 | API와 자동화 도구로 다수 장비 설정을 빠르게 반영하기 좋음 |
| 가시성 | 장비 단위 상태는 잘 보이지만 전체 서비스 흐름 파악이 번거로움 | 중앙에서 경로와 정책 상태를 통합적으로 보기 쉬움 |
| 운영 리스크 | 장비 간 정책 불일치가 누적되기 쉬움 | 컨트롤러 장애나 정책 오배포 시 영향 범위가 넓을 수 있음 |

> 요약: SDN은 네트워크를 장비 중심에서 정책 중심으로 바꾸는 대신 중앙 제어 가용성을 함께 관리해야 함.

## Ⅳ. 구성요소 및 구조

| 구성요소 | 설명 |
|:---|:---|
| SDN 애플리케이션 | 보안, 로드밸런싱, QoS 같은 상위 정책을 정의하는 계층임 |
| SDN 컨트롤러 | 토폴로지와 정책을 해석해 장비 규칙으로 변환하는 중앙 제어 계층임 |
| 사우스바운드 인터페이스 | 컨트롤러가 스위치나 라우터에 플로우 규칙을 전달하는 통로임 |
| 데이터 평면 장비 | 전달 규칙을 실제 패킷 처리에 적용하는 스위치와 라우터 계층임 |
| 상태 수집과 분석 | 토폴로지 변화와 트래픽 상태를 수집해 정책 최적화에 반영하는 기능임 |

```text
+-------------+     +----------------+     +----------------+     +----------------+
| 정책·응용 계층  | --> | SDN 컨트롤러     | --> | 사우스바운드 API   | --> | 데이터 평면 장비   |
+-------------+     +----------------+     +----------------+     +----------------+
```

## Ⅴ. 원리 및 절차 흐름도

```text
+-------------+     +----------------+     +------------------+     +----------------+
| 정책 입력      | --> | 경로·규칙 계산     | --> | 장비 규칙 배포      | --> | 상태 수집·재조정   |
+-------------+     +----------------+     +------------------+     +----------------+
```

1. **정책 입력**: 운영자가 서비스 요구사항과 네트워크 정책을 컨트롤러에 입력함
2. **경로와 규칙 계산**: 컨트롤러가 토폴로지와 정책을 바탕으로 플로우 규칙을 계산함
3. **장비 규칙 배포**: 계산된 규칙을 사우스바운드 인터페이스로 스위치와 라우터에 배포함
4. **상태 수집과 재조정**: 장애나 혼잡 상태를 수집해 규칙을 다시 조정함

## Ⅵ. 실무 적용 및 유의점

1. 데이터센터와 SD-WAN처럼 경로를 자주 바꾸는 환경에서는 SDN이 유리하지만 컨트롤러 장애가 곧 전체 정책 장애로 번질 수 있으므로 클러스터 이중화와 롤백 절차를 함께 두고 정책 반영 시간과 컨트롤러 장애 복구 시간으로 확인함
2. 분산 라우팅을 완전히 없애기보다 특정 서비스 경로만 SDN으로 오버라이드하는 환경에서는 하이브리드 설계가 현실적이므로 OSPF, BGP와의 역할 경계를 먼저 정하고 정책 충돌 건수와 경로 수렴 시간을 기준으로 확인함

## Ⅶ. 결론

SDN의 핵심은 네트워크를 장비별 수동 설정에서 중앙 정책 제어로 바꾸는 데 있으므로 자동화 이점만큼 컨트롤러 가용성과 정책 검증 체계가 중요함.
