# 📖 【암기용】 개념 완전 이해

## 한눈에
- **개요**: ICMP와 IGMP는 IP가 스스로 못 하는 제어·관리 기능을 대신하는 보조 프로토콜임. ICMP는 오류·상태를 알리는 "전령", IGMP는 멀티캐스트 그룹 가입을 관리하는 "명부 담당"임(둘 다 IP 위에 얹혀 동작하나 전송이 아닌 제어용임).
- **왜 필요한가**: IP는 데이터를 목적지로 보내기만 할 뿐, 도달 실패를 알리거나(오류 보고) 한 번에 여러 수신자에게 보내는 그룹(멀티캐스트)을 관리할 수단이 없어 별도 제어 프로토콜이 필요했음.
- **핵심 직관**: ICMP는 배송 실패 시 "주소 없음" 반송 스티커를 붙여 돌려보내는 우체국 반송 시스템, IGMP는 "이 채널 구독합니다"를 아파트 관리사무소(라우터)에 신고하는 케이블TV 구독 신청서와 같음.

## 핵심 용어 정리 (내부에 등장하는 것들)

아래 표기는 답안 Ⅰ~Ⅵ에 그대로 등장하므로 먼저 이해해 둠. 상위 핵심 키워드는 **제어 메시지(데이터가 아닌 통제 신호)**임.

| 용어/표기 | 의미 | 비유·예 |
|:---|:---|:---|
| ICMP | IP 오류·상태를 보고하는 제어 프로토콜(IP 프로토콜 번호 1) | 배송 반송·상태 통지 우편 |
| Type / Code | ICMP 메시지 종류와 세부 사유 구분 필드 | 반송 사유 코드(주소불명/수취거부) |
| Echo Request/Reply | 상대 생존을 확인하는 왕복 메시지(Type 8/0) | "거기 있어?"—"응 있어" |
| ping | Echo로 도달성·지연을 측정하는 진단 도구 | 초인종 눌러보기 |
| traceroute | TTL을 1씩 늘려 경로 홉을 추적하는 도구 | 한 정거장씩 늘려 노선 확인 |
| TTL 초과(Type 11) | 홉 제한 소진 시 보내는 오류 메시지 | 유통기한 만료 통지 |
| Destination Unreachable(Type 3) | 목적지 도달 불가 통지(호스트·포트 등) | 주소지 없음 반송 |
| IGMP | 멀티캐스트 그룹 가입·유지를 관리하는 프로토콜(번호 2) | 채널 구독자 명부 관리 |
| 멀티캐스트 | 하나의 송신을 그룹 수신자에게만 전달하는 방식 | 케이블 방송 채널 |
| 그룹 주소(224.0.0.0/4) | 멀티캐스트 수신자 그룹을 지칭하는 D클래스 IP | 채널 번호 |
| Membership Query/Report | 라우터의 구독 확인 질의·호스트의 가입 응답 | "볼 사람?"—"저요" |
| Leave Group | 그룹 탈퇴 통보(IGMPv2+) | 구독 해지 |
| PIM | 멀티캐스트 패킷을 라우터 간 전달하는 라우팅 프로토콜(IGMP와 역할 구분) | 방송 신호를 지역 간 중계 |

## 깊이 이해
- **배경·문제의식**: IP(001·002 참조)는 비신뢰·비연결 전달만 담당해, 실패 통지나 그룹 수신 관리를 못 함. ICMP는 오류 보고, IGMP는 멀티캐스트 구독 관리를 각각 보완함.
- **작동 원리(어떻게+왜)**: ICMP는 오류 발생 시 원 패킷의 IP 헤더+앞 8바이트를 담아 송신자에게 되돌려보내 어떤 패킷이 실패했는지 알림. IGMP는 호스트가 그룹 가입을 Report 하고, 라우터가 주기적 Query로 아직 볼 사람이 있는지 확인해 없으면 전송을 끊음 — 불필요한 멀티캐스트 트래픽을 낭비하지 않기 위함임.
- **비유**: ICMP는 반송 우편(왜 못 갔는지 사유 첨부), IGMP는 케이블TV 구독/해지 신청(관리사무소가 시청자 유무 확인).
- **구체 예시**: `traceroute`는 TTL=1,2,3…으로 패킷을 연달아 보내 각 홉이 반환하는 ICMP TTL 초과(Type 11)로 경로를 그림. IPTV는 셋톱박스가 IGMP Report로 채널(그룹)에 가입하면 그 채널 스트림만 해당 회선으로 흘려보냄.
- **흔한 오해·주의점**: ICMP는 오류 "보고"만 할 뿐 재전송·복구는 하지 않음(그건 TCP 몫). IGMP는 그룹 "가입 관리"만 하며, 라우터 간 멀티캐스트 경로 구성은 PIM이 담당함 — 둘을 혼동하면 감점됨.

## 연결 개념
- ICMPv6·ND(IPv6에서 ARP·라우터 탐색까지 흡수, 004·005 참조)
- 멀티캐스트 라우팅(PIM-SM/DM, 149 참조)
- Path MTU Discovery(ICMP Type 3 Code 4 활용)

# 📝 【답안용】 시험 답안 템플릿

## 핵심 인사이트 (3줄 요약)

> 1. **본질**: ICMP는 IP 전달의 오류·상태를 보고하는 제어 프로토콜, IGMP는 멀티캐스트 그룹 멤버십을 관리하는 제어 프로토콜임(둘 다 IP 상위, 전송이 아닌 통제용).
> 2. **가치**: ICMP는 ping·traceroute 등 장애 진단의 기반, IGMP는 IPTV·스트리밍의 대역폭 절감형 그룹 전송을 가능케 함.
> 3. **판단 포인트**: ICMP는 오류 "보고"까지만(복구 없음), IGMP는 그룹 "가입 관리"까지만(경로는 PIM)이라는 역할 경계가 핵심임.

## 출제 의도 및 답안 포인트

| 출제 의도 | 반드시 짚을 핵심 | 감점 회피 포인트 |
|:---|:---|:---|
| IP 보조 제어 프로토콜의 역할·차이 이해 | ICMP Type/Code·ping·traceroute, IGMP Query/Report·그룹 관리 | ICMP를 재전송 수단으로 오인, IGMP와 PIM 역할 혼동 |

> 요약: ICMP의 오류 보고 메커니즘과 IGMP의 멤버십 관리 절차를 구분해 서술하고, 각 응용(진단·멀티캐스트)을 제시해야 함.

---

## Ⅰ. 개요 및 필요성
- 정의: ICMP는 IP 전달 오류·상태를 송신자에게 통지하는 제어 프로토콜, IGMP는 호스트의 멀티캐스트 그룹 가입·탈퇴를 라우터에 알리는 관리 프로토콜임.
- 배경: IP가 비신뢰·비연결 전달만 담당해 실패 통지 수단과 그룹 수신 관리 수단이 부재함.
- 필요성: 장애 진단(도달성·경로 확인)과 멀티캐스트 대역폭 절감(수신자에게만 전송)을 위해 별도 제어 계층 필요함.

---

## Ⅱ. 구조 및 구성요소

```text
ICMP 메시지: [IP 헤더] -> [ICMP: Type / Code / Checksum / 원 패킷 일부]
IGMP 메시지: [IP 헤더] -> [IGMP: Type / Max Resp Time / Checksum / Group Address]

동작 관계: 호스트 <-(ICMP 오류/Echo)-> 라우터
           호스트 -(IGMP Report/Leave)-> 라우터 -(PIM)-> 멀티캐스트 소스
```

| 구성요소 | 역할 | 특이사항 |
|:---|:---|:---|
| ICMP Type/Code | 메시지 종류·세부 사유 구분 | Type 8/0(Echo), 3(Unreachable), 11(TTL 초과) |
| ICMP 원 패킷 일부 | 실패한 원 IP 헤더+앞 8바이트 첨부 | 송신자가 어떤 패킷 실패인지 식별 |
| IGMP Query | 라우터가 그룹 구독 여부를 묻는 질의 | 주기적 전송으로 잔존 시청자 확인 |
| IGMP Report/Leave | 호스트의 가입 응답·탈퇴 통보 | v2 Leave, v3 소스 지정(SSM) |
| Group Address | 대상 멀티캐스트 그룹(224.0.0.0/4) | D클래스 IP |

> 요약: ICMP는 Type/Code로 오류를 분류해 원 패킷 정보와 함께 반송하고, IGMP는 Query/Report로 그룹 시청자 유무를 관리함.

---

## Ⅲ. 동작원리 및 흐름도

```text
[ICMP·traceroute] 송신자 -> TTL=1 패킷 -> 1홉 라우터: TTL 소진 -> ICMP Type11 반환
                          -> TTL=2 패킷 -> 2홉 라우터: ICMP Type11 -> ... 경로 완성
[IGMP·IPTV] 셋톱박스 -> IGMP Report(채널 가입) -> 접속 라우터: 스트림 전달 개시
            라우터 -> 주기적 Query -> 응답 없음 -> 전송 중단
```

1. ICMP 오류 보고: 라우터·호스트가 전달 실패(도달 불가·TTL 소진)를 감지하면 해당 사유의 Type/Code로 ICMP를 송신자에게 반환함.
2. ICMP 진단: ping은 Echo Request/Reply 왕복으로 도달성·RTT를 측정하고, traceroute는 TTL 증가로 홉별 ICMP를 수집해 경로를 추적함.
3. IGMP 가입: 호스트가 특정 그룹을 수신하려 Report를 보내면 접속 라우터가 해당 멀티캐스트 스트림을 그 회선으로 전달함.
4. IGMP 유지·정리: 라우터가 주기적 Query로 시청자 잔존을 확인하고, 응답이 없거나 Leave를 받으면 전송을 중단해 대역폭을 회수함.

> 요약: ICMP는 실패 감지 시 사유를 반환하고, IGMP는 Report로 가입·Query로 잔존 확인·Leave로 정리하는 구독 생명주기를 관리함.

---

## Ⅳ. 특징
- ICMP는 오류 "보고" 전용으로 재전송·복구는 하지 않음(신뢰성은 상위 TCP 담당).
- ICMP는 원 패킷의 IP 헤더+앞 8바이트를 첨부해 송신자가 실패 원인을 특정하게 함.
- ping·traceroute·Path MTU Discovery 등 핵심 진단 도구가 모두 ICMP에 기반함.
- IGMP는 수신자 있는 회선에만 스트림을 흘려 멀티캐스트 대역폭을 절감함.
- IGMP는 그룹 가입 관리만 담당하고, 라우터 간 배포 경로는 PIM이 별도로 구성함.
- ICMP 무제한 허용은 스머프·핑홍수 공격 표면이 되므로 방화벽 레이트 리밋 필요함.

## Ⅴ. 심화 비교 및 적용 판단

| 구분 | ICMP | IGMP |
|:---|:---|:---|
| 목적 | IP 오류·상태 보고 | 멀티캐스트 그룹 멤버십 관리 |
| 통신 방향 | 실패 지점 -> 송신자(주로 유니캐스트) | 호스트 <-> 접속 라우터(그룹 내) |
| 대표 동작 | Echo, Unreachable, TTL 초과 | Query, Report, Leave |
| 응용 | ping·traceroute·PMTUD 진단 | IPTV·스트리밍 그룹 수신 |
| 협력 프로토콜 | 상위 TCP가 복구 담당 | 라우터 간 PIM이 경로 담당 |

> 요약: 둘 다 IP 보조 제어이나 ICMP는 "장애 통지", IGMP는 "그룹 구독 관리"로 목적·응용이 명확히 갈림.

- 리스크: ICMP 플러딩(스머프·핑홍수) — 브로드캐스트 증폭·과다 Echo — 방화벽 레이트 리밋·Directed Broadcast 차단으로 대응함.
- 리스크: IGMP 스누핑 미적용 — L2 스위치가 멀티캐스트를 전 포트로 범람 — IGMP Snooping 활성화로 수신 포트에만 전달함.
- 지표: 진단 성공률 — ping 응답률·traceroute 완주율 — 주기 폴링으로 측정함.
- 지표: 멀티캐스트 효율 — 불필요 스트림 회선 수 최소화 — Query 응답·Snooping 테이블로 측정함.

---

## Ⅵ. 실무 적용 및 결론

**적용 방안 3개:**
1. [장애 진단] 운영망 모니터링에 ICMP ping(도달성·RTT)과 traceroute(경로·병목 홉)를 결합해 구간별 지연·손실을 상시 계측.
2. [멀티캐스트 서비스] IPTV·사내 방송에 IGMPv2/v3로 그룹 가입을 관리하고, L2 구간에는 IGMP Snooping을 적용해 수신 포트에만 스트림 전달.
3. [보안] 경계 방화벽에서 불필요한 ICMP Type을 선별 차단하고 레이트 리밋을 두되, PMTUD용 Type 3 Code 4는 허용해 블랙홀 방지.
4. [보안] Directed Broadcast를 차단해 스머프 증폭 공격 표면 제거.

**결론(2줄):**
- 기술사 판단: 진단·경로 가시성이 필요하면 ICMP 기반 계측을, 다수 동시 수신 서비스면 IGMP+Snooping 기반 멀티캐스트를 선택함.
- 향후 방향: IPv6에서는 ICMPv6가 ND·라우터 탐색까지 흡수하고 멤버십 관리는 MLD가 IGMP를 대체하므로, v6 전환 시 통합 제어 구조로 진화함.
