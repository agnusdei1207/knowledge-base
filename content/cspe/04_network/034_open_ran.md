## Ⅰ. 개요
- **정의**: RAN 장비 간 인터페이스를 개방·표준화하여 멀티벤더 구성을 가능하게 하는 아키텍처임
- **배경/필요성**: 단일 벤더 종속으로 비용 상승과 혁신 제약이 발생하여 개방형 인터페이스가 필요함
- **비유**: 특정 브랜드 전용 부품 대신 범용 규격 부품으로 조립하는 PC와 유사함

| 출제 의도 | 반드시 짚을 핵심 | 감점 회피 포인트 |
|:---|:---|:---|
| Open RAN 구조와 기존 RAN 차이 | O-CU/O-DU/O-RU 분리, RIC | O-RAN Alliance와 3GPP 역할 구분 |

> 요약: 개방형 인터페이스로 벤더 종속을 해소하고 RAN 혁신을 촉진하는 구조임

## Ⅱ. 구성요소
```text
        Non-RT RIC (SMO)
             |
         Near-RT RIC
          /       \
      O-CU       O-CU
       |           |
      O-DU       O-DU
       |           |
      O-RU       O-RU
```

| 구성요소 | 설명 | 비유 |
|:---|:---|:---|
| O-RU | 무선 신호 송수신을 담당하는 개방형 라디오 유닛 | 안테나 모듈 |
| O-DU | 실시간 L1/L2 처리를 수행하는 분산 유닛 | 현장 처리 서버 |
| O-CU | 비실시간 L3/PDCP를 처리하는 중앙 유닛 | 중앙 제어 서버 |
| Near-RT RIC | 10ms~1s 주기로 RAN 자원을 최적화하는 지능 제어기 | 실시간 교통 신호 제어기 |

> 요약: O-RU/DU/CU 분리와 RIC 지능 제어로 개방형 RAN을 구현함

## Ⅲ. 절차
```text
SMO -> Non-RT RIC -> 정책 생성
            |
       Near-RT RIC -> xApp 실행 -> O-CU/DU 제어
                                      |
                                    O-RU 송수신
```
- 1단계: SMO가 Non-RT RIC에 네트워크 정책·ML 모델을 배포함
- 2단계: Near-RT RIC가 xApp을 통해 실시간 자원 최적화를 수행함
- 3단계: 최적화된 제어 명령이 O-CU/O-DU에 전달됨
- 4단계: O-RU가 제어에 따라 무선 신호를 송수신함

> 요약: 정책 배포-xApp 최적화-제어 전달-신호 송수신의 4단계로 동작함

## Ⅳ. 문제점
- 멀티벤더 통합 검증 부담: 이기종 장비 간 상호운용성 테스트에 높은 비용이 소요됨
- Fronthaul 대역폭 요구: O-DU-O-RU 간 eCPRI 전송에 수십 Gbps 대역이 필요함
- 성능 격차: 범용 하드웨어 기반 처리 성능이 전용 장비 대비 낮을 수 있음

> 요약: 통합 검증, Fronthaul 대역폭, 범용 HW 성능이 주요 과제임

## Ⅴ. 개선방안
1. 단기: OTIC(Open Testing & Integration Centre) 활용으로 상호운용성 검증을 체계화함
2. 중기: 25G/50G 광전송 표준화 및 기능분할(Split) 최적화로 Fronthaul 부담을 경감함
3. 장기: GPU/DPU 가속기 탑재 범용 서버 도입으로 전용 장비 수준 성능을 확보함

> 요약: 검증 센터, 전송 최적화, HW 가속으로 개선 가능함

## Ⅵ. 전망
- 발전 방향: AI/ML 기반 RAN 자동 최적화(RIC rApp/xApp)가 핵심 차별화 요소로 부상함
- 기술사적 판단: 정부 지원과 통신사 도입 확대로 Open RAN 점유율이 지속 상승할 전망임
- 기술사 제언: 국산 O-RU/DU 생태계 육성과 보안 인증 체계 마련이 필요
