# 📖 【암기용】 개념 완전 이해

> 목적: 컴퓨팅 컨티뉴엄을 클라우드와 엣지의 단순 조합이 아니라 연속적인 배치·운영 모델로 이해하게 만든다.

## 한눈에
- **개요**: 컴퓨팅 컨티뉴엄은 IoT 디바이스부터 엣지, 포그, 클라우드까지 자원을 하나의 연속 공간으로 배치·운영하는 개념이다.
- **왜 필요한가**: 업무마다 지연, 데이터 위치, 비용, 연산 요구가 달라 한 위치에 모든 처리를 고정하면 SLA와 비용을 동시에 맞추기 어렵다.
- **핵심 직관**: 계산을 한 건물에 몰아넣지 않고, 현장·지역·중앙 중 가장 맞는 위치에 배치하는 스펙트럼이다.

## 깊이 이해
- **배경·문제의식**: 클라우드는 탄력 자원과 중앙 관리를 제공하지만 현장 지연과 데이터 이동 비용이 있다. 엣지는 현장 처리에 유리하지만 노드 수가 많아 운영 난도가 상승한다.
- **작동 원리**: 애플리케이션은 마이크로서비스, 데이터 파이프라인, AI 추론 단위로 쪼개지고, 오케스트레이터가 지연·비용·자원·정책을 기준으로 디바이스-엣지-클라우드에 배치한다.
- **비유**: 병원에서 응급 처치는 현장 구급차, 정밀 검사는 지역 병원, 장기 연구는 중앙 연구소가 맡는 구조와 같다.
- **구체 예시**: 스마트시티 영상은 카메라 NPU에서 객체 탐지, 엣지에서 교차로 제어, 클라우드에서 장기 교통 모델 학습을 수행한다.
- **흔한 오해·주의점**: 컨티뉴엄은 모든 곳에 같은 앱을 복제하는 것이 아니다. 데이터 중력, 지연, 보안 정책에 따라 기능을 분리 배치해야 한다.

## 연결 개념
- Edge/Fog Computing — 컨티뉴엄의 현장·중간 계층
- Kubernetes Federation — 다중 위치 워크로드 배포
- Data Fabric — 위치가 다른 데이터의 거버넌스와 접근 통제

## Ⅰ. 개요 및 필요성

컴퓨팅 컨티뉴엄은 디바이스부터 클라우드까지 자원을 연속적으로 활용하는 모델이다. 단일 클라우드 집중 구조는 실시간 제어, 데이터 주권, 전송 비용 제약을 동시에 해결하기 어렵다. 컨티뉴엄은 업무 특성에 따라 실행 위치를 배치해 서비스 SLA를 맞춘다.

---

## Ⅱ. 구조 및 구성요소

```text
IoT Device -> Edge Node -> Fog/Regional Node -> Cloud Region
     / 즉시 판단       / 현장 제어       / 지역 집계        / 장기 학습
Policy Engine -> Orchestrator -> Workload Placement -> Observability
```

| 구성요소 | 역할 | 특이사항 |
|:---|:---|:---|
| IoT Device | 데이터 생성·초기 필터링 | MCU, NPU, 배터리 제약 |
| Edge Node | 현장 추론·제어 | p95 10~50ms 업무 |
| Fog/Regional Node | 집계·캐시·지역 정책 | 마이크로 데이터센터 |
| Cloud Region | 장기 저장·학습·전사 분석 | Data Lake, MLOps |
| Orchestrator | 배치·확장·정책 관리 | Kubernetes, GitOps, policy engine |

> 요약: 컨티뉴엄은 여러 위치의 자원을 하나의 실행 후보군으로 보고 정책 기반으로 워크로드를 배치한다.

---

## Ⅲ. 동작원리 및 흐름도

```text
요구사항 수집 -> 지연/데이터/비용 점수화
-> 실행 위치 선택 -> 워크로드 배포
-> 데이터 동기화 -> SLA 관측
-> 정책 재조정과 재배치
```

| 단계 | 처리 내용 | 검증 기준 |
|:---:|:---|:---|
| 1 | 업무별 SLA와 데이터 민감도 정의 | p95 latency, RPO, 등급 분류 |
| 2 | 자원·네트워크 상태 수집 | CPU/GPU, bandwidth, RTT |
| 3 | 배치 정책으로 실행 위치 결정 | placement decision log |
| 4 | 컨테이너·모델·데이터 배포 | rollout success rate |
| 5 | 관측 결과로 재배치 | SLA violation count |

> 요약: 컨티뉴엄은 요구사항을 점수화하고 배치한 뒤 관측 결과로 위치를 계속 조정한다.

## Ⅳ. 특징

| 구분 | 단일 클라우드 | 컴퓨팅 컨티뉴엄 | 판단 포인트 |
|:---|:---|:---|:---|
| 실행 위치 | 리전 중심 | IoT~클라우드 연속 배치 | latency·data locality |
| 자원 관리 | 중앙 오토스케일 | 다중 위치 오케스트레이션 | Kubernetes, GitOps |
| 데이터 흐름 | 원본 중앙 수집 | 현장 처리+요약 전송 | bandwidth, privacy |
| 운영 지표 | 리전 SLO | 위치별 SLA와 정책 일관성 | drift, sync lag |

> 요약: 컨티뉴엄은 실행 위치 선택권을 넓히지만 정책 일관성과 관측 체계가 도입 조건이다.

## Ⅴ. 심화 비교 및 적용 판단

| 비교 축 | 기존/대안 | 컴퓨팅 컨티뉴엄 | 선택 기준 |
|:---|:---|:---|:---|
| 구조 | Cloud-only, Edge-only | IoT-Edge-Fog-Cloud 연속 | 업무별 지연·데이터 등급 차이 |
| 비용/성능 | 중앙 집중 자원 | 위치별 자원 분산 | 전송량, GPU 사용률, SLA 위반 |
| 운영/위험 | 운영 경계 단순 | 다중 사이트 정책 통제 | GitOps·관측 플랫폼 성숙도 |

> 요약: 업무별 요구가 이질적이고 위치별 데이터 가치가 클 때 컨티뉴엄 설계가 필요하다.

| 리스크 | 원인 | 대응 방안 | 확인 지표 |
|:---|:---|:---|:---|
| 배치 오류 | 정책·자원 상태 불일치 | policy-as-code, dry-run | SLA violation count |
| 데이터 불일치 | 비동기 동기화와 오프라인 노드 | CDC, store-and-forward | sync lag, conflict count |
| 운영 복잡도 | 다중 클러스터·버전 관리 | GitOps, fleet management | rollout failure rate |

> 요약: 컨티뉴엄 리스크는 배치·데이터·버전 상태가 분산되면서 발생하므로 정책 코드화와 관측이 필수다.

| 점검 항목 | 목표 기준 | 측정 방법 |
|:---|:---|:---|
| 배치 적합도 | SLA 위반 월 1건 이하 목표 | APM, policy log |
| 데이터 동기화 | sync lag 업무 기준 이내 | CDC metric, queue lag |
| 운영 일관성 | config drift 0건 목표 | GitOps diff, audit log |

> 요약: 컨티뉴엄은 SLA 위반, 동기화 지연, 설정 편류를 위치별로 측정해 운영한다.

## Ⅵ. 실무 적용 및 결론

**적용 방안 3개 (필수 — 단계별 또는 항목별):**
1. 업무를 즉시 제어, 지역 집계, 중앙 학습으로 분류하고 p95 지연·데이터 등급·GPU 요구량을 배치 기준으로 정의함
2. Kubernetes, GitOps, policy-as-code를 적용해 디바이스·엣지·클라우드 배포 정책과 rollback 절차를 표준화함
3. OpenTelemetry, CDC, mTLS를 적용해 다중 위치의 지표·데이터 동기화·접근통제를 한 관측 체계로 수집함

**결론 (2줄):**
- 기술사 판단: 요구사항이 단일하면 클라우드 또는 엣지로 충분하나, 지연·데이터·비용 요구가 혼재하면 컨티뉴엄을 적용함
- 향후 방향: 6G, MEC, AI Agent, 자율 운영이 결합되며 워크로드 배치는 정책 기반 자동 재배치로 발전함
