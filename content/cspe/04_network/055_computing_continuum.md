## 미리 알고가기

- Far Edge는 센서, 단말, 현장 게이트웨이처럼 데이터 발생 지점과 가장 가까운 구간임
- Near Edge는 기지국, 지역 거점, MEC처럼 현장과 중앙 사이에서 빠른 처리를 맡는 구간임
- 오케스트레이션은 워크로드를 어느 위치에 둘지 자동으로 배치하고 옮기는 제어 기능임
- 워크로드 이식성은 같은 애플리케이션을 위치가 다른 인프라에 옮겨도 동일하게 실행되는 성질임

## Ⅰ. 개요

- **정의/개념**: 컴퓨팅 연속체는 단말·엣지·지역 거점·중앙 클라우드를 연결하고 지연·데이터 위치·자원·비용 조건에 따라 워크로드를 배치하는 분산 컴퓨팅 구조임
- **배경/필요성**: 현장 제어는 왕복 경로가 짧은 엣지에, 통합 분석은 자원이 모인 클라우드에 배치해야 하므로 여러 계층을 같은 배포·관측 정책으로 관리할 구조가 필요함

## Ⅱ. 특징

- 단말부터 클라우드까지를 하나의 연속된 자원 계층으로 보고 작업을 배치함
- 서비스 요구가 바뀌면 워크로드를 엣지와 클라우드 사이에서 이동하거나 분산할 수 있음
- 컨테이너와 공통 운영 도구를 이용해 위치가 달라도 같은 방식으로 배포하고 관리하기 좋음
- 데이터 수집, 추론, 학습, 배포를 한 흐름으로 연결해 AI 운영과 궁합이 좋음

## Ⅲ. 종류 및 비교

| 판단 기준 | 고립형 클라우드·엣지 운영 | 컴퓨팅 연속체 |
|:---|:---|:---|
| 자원 관리 | 클라우드와 엣지를 별도 팀과 별도 도구로 운영하기 쉬움 | 여러 위치 자원을 공통 정책과 도구로 묶어 관리함 |
| 애플리케이션 배치 | 위치가 바뀌면 별도 버전과 별도 배포 절차가 필요하기 쉬움 | 같은 워크로드를 위치만 바꿔 재배치하기 쉬움 |
| 부하 대응 | 엣지 과부하나 클라우드 병목에 유연하게 대응하기 어려움 | 상태를 보고 인접 엣지나 클라우드로 작업을 옮길 수 있음 |
| 데이터 흐름 | 현장 데이터와 중앙 분석 흐름이 분절되기 쉬움 | 현장 추론, 중앙 학습, 모델 재배포를 하나의 순환 구조로 묶기 쉬움 |

> 요약: 컴퓨팅 연속체의 차별점은 새로운 위치를 만드는 것이 아니라 위치가 다른 자원을 하나의 운영 체계로 묶는 데 있음.

## Ⅳ. 구성요소 및 구조

| 구성요소 | 설명 |
|:---|:---|
| 단말과 Far Edge | 현장 제어와 1차 필터링을 담당하는 단말 인접 계층임 |
| Near Edge와 지역 거점 | 짧은 지연 처리가 필요하지만 단말만으로 부족한 연산을 맡는 중간 계층임 |
| 중앙 클라우드 | 장기 저장, 대규모 분석, 모델 학습, 전사 통합 관리를 담당함 |
| 공통 오케스트레이션 | 위치별 자원 상태를 보고 워크로드 배치와 이동을 결정하는 제어 계층임 |
| 데이터와 모델 동기화 | 현장 추론 결과, 로그, 모델 버전을 계층 간에 연결하는 운영 흐름임 |

```text
+-------------+     +-------------+     +-------------+     +-------------+
| 단말·Far Edge | --> | Near Edge    | --> | 지역·중앙 클라우드 | --> | 운영 오케스트레이션 |
+-------------+     +-------------+     +-------------+     +-------------+
       ^                                                             |
       +------------------ 데이터·모델 동기화 ------------------------+
```

## Ⅴ. 원리 및 절차 흐름도

```text
+-------------+     +----------------+     +------------------+     +----------------+
| 서비스 요구 해석 | --> | 배치 위치 결정     | --> | 실행·모니터링       | --> | 재배치·동기화      |
+-------------+     +----------------+     +------------------+     +----------------+
```

1. **서비스 요구 해석**: 지연 시간, 보안, 비용, 연산량을 기준으로 필요한 실행 위치를 판단함
2. **배치 위치 결정**: 단말, 엣지, 클라우드 중 적합한 위치에 워크로드를 배치함
3. **실행과 모니터링**: 운영 중 부하, 지연 시간, 장애 상태를 계속 수집함
4. **재배치와 동기화**: 상황 변화에 따라 워크로드를 이동하고 데이터와 모델을 동기화함

## Ⅵ. 실무 적용 및 유의점

1. 자율주행 보조, 리테일 영상 분석, 스마트 공장처럼 현장 추론과 중앙 학습이 함께 필요한 환경에서는 엣지와 클라우드를 별도 서비스로 운영하면 모델 배포가 끊기기 쉬우므로 공통 배포 체계와 버전 관리를 먼저 만들고 배포 성공률과 모델 동기화 지연 시간으로 확인함
2. 멀티 클라우드와 다수 엣지 거점을 함께 쓰는 조직에서는 연속체를 표방해도 실제로는 벤더별 운영 도구가 갈라질 수 있으므로 공통 오케스트레이션 계층과 정책 기준을 정하고 워크로드 이동 성공률과 운영 도구 수 감소율로 확인함

## Ⅶ. 결론

컴퓨팅 연속체의 본질은 엣지와 클라우드를 경쟁 관계가 아니라 하나의 연속된 실행 공간으로 다루는 데 있으므로 워크로드 이식성과 공통 운영 체계가 먼저 확보되어야 함.
