## Ⅰ. 개요
- **정의**: 전용 하드웨어의 네트워크 기능을 범용 서버에서 소프트웨어로 구현하는 기술
- **배경/필요성**: 전용 장비(방화벽, 로드밸런서 등) 도입·확장에 높은 비용과 긴 리드타임이 소요되어 가상화가 필요함
- **비유**: 전용 공장 설비를 범용 컴퓨터의 소프트웨어 프로그램으로 대체하는 것과 유사함

| 출제 의도 | 반드시 짚을 핵심 | 감점 회피 포인트 |
|:---|:---|:---|
| NFV 아키텍처 3요소와 SDN과의 관계 | VNF·NFVI·MANO 역할 구분 | NFV는 기능 가상화, SDN은 제어 분리로 대상이 다름을 구분할 것 |

> 요약: 네트워크 기능을 소프트웨어화하여 범용 인프라에서 유연하게 배포·운영하는 기술임

## Ⅱ. 구성요소
```text
        MANO (Management & Orchestration)
          |            |
    +-----+-----+     |
    |           |      |
   VNF-1     VNF-2    |
    |           |      |
   NFVI (Compute / Storage / Network)
```

| 구성요소 | 설명 | 비유 |
|:---|:---|:---|
| VNF | 가상화된 네트워크 기능(vFirewall, vRouter 등) | 소프트웨어로 실행되는 가상 공장 설비 |
| NFVI | VNF를 실행하는 범용 컴퓨팅·스토리지·네트워크 인프라 | 다목적 공장 건물과 전기·수도 설비 |
| MANO | VNF 생명주기(배포·확장·종료)를 관리하는 오케스트레이션 계층 | 공장 가동 계획을 수립·관리하는 본사 |

> 요약: VNF·NFVI·MANO 3요소가 네트워크 기능 가상화의 핵심 구조임

## Ⅲ. 절차
```text
서비스 요청 --> VNF 카탈로그 선택 --> NFVI 자원 할당 --> VNF 인스턴스 배포 --> 서비스 체이닝
```
- 1단계: 운영자가 필요한 네트워크 서비스(방화벽+LB 등)를 MANO에 요청함
- 2단계: MANO가 VNF 카탈로그에서 해당 기능을 선택하고 배치 계획을 수립함
- 3단계: NFVI에서 CPU·메모리·네트워크 자원을 할당하여 VNF 인스턴스를 생성함
- 4단계: Service Function Chaining으로 VNF 간 트래픽 흐름을 연결하여 서비스를 구성함

> 요약: 요청-선택-배포-체이닝의 4단계로 가상 네트워크 서비스를 구현함

## Ⅳ. 문제점
- 성능 저하: 가상화 오버헤드로 전용 장비 대비 패킷 처리 처리량이 감소함
- 장애 전파: NFVI 호스트 장애 시 다수 VNF가 동시에 영향을 받음
- 표준화 미흡: 벤더별 VNF 패키징·인터페이스가 달라 상호운용성이 제한됨

> 요약: 성능 저하·장애 전파·표준화 미흡이 NFV 운영의 주요 과제임

## Ⅴ. 개선방안
1. 단기: SR-IOV, DPDK 등 데이터 평면 가속 기술로 가상화 오버헤드를 감소시킴
2. 중기: VNF 분산 배치와 자동 복구(Auto-healing)로 장애 영향 범위를 축소함
3. 장기: ETSI NFV 표준 준수와 TOSCA 기반 VNF 패키징으로 멀티벤더 호환성을 확보함

> 요약: 데이터 가속·자동 복구·표준화로 단계적 개선이 가능함

## Ⅵ. 전망
- 발전 방향: CNF(Cloud-Native NF)로 전환되어 컨테이너 기반 경량 배포가 확대됨
- 기술사적 판단: 통신사 5G 코어에서 NFV/CNF가 표준 구현 방식으로 자리잡음
- 기술사 제언: SDN(026 참조)과의 상호보완 관계, CNF 전환 트렌드를 함께 파악할 필요
