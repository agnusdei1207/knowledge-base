## Ⅰ. 개요
- **정의**: 패킷 파싱·매칭·액션 파이프라인을 사용자가 재정의할 수 있는 데이터플레인 프로그래밍 가능 스위치임
- **배경/필요성**: 고정 ASIC 기반 스위치는 새 프로토콜·텔레메트리 요구에 펌웨어 교체 없이 대응할 수 없음
- **비유**: 메뉴가 고정된 식당 대신 셰프가 레시피를 자유로이 바꿀 수 있는 오픈 키친과 유사함

| 출제 의도 | 반드시 짚을 핵심 | 감점 회피 포인트 |
|:---|:---|:---|
| SDN 데이터플레인 프로그래밍 원리 | PISA 아키텍처, Match-Action 파이프라인 | OpenFlow 고정 매치필드와의 차이를 명확히 구분 |

> 요약: 프로그래머블 스위치는 Match-Action 파이프라인을 사용자가 정의하여 유연한 패킷 처리를 수행함

## Ⅱ. 구성요소
```text
Packet In --> Parser --> Match-Action Stage 1 --> ... --> Stage N --> Deparser --> Packet Out
                              |                           |
                          Match Table                 Match Table
                          + Action ALU                + Action ALU
```

| 구성요소 | 설명 | 비유 |
|:---|:---|:---|
| Parser | 패킷 헤더를 사용자 정의 규칙에 따라 추출·분해함 | 편지 개봉 담당 |
| Match-Action Stage | 테이블 조회와 연산을 파이프라인 단계로 수행함 | 조립 라인 공정 |
| Deparser | 처리된 헤더를 재조립하여 패킷을 출력함 | 편지 봉함 담당 |
| Control Plane Agent | 런타임에 테이블 엔트리를 삽입·갱신하는 소프트웨어임 | 작업지시서 관리자 |

> 요약: Parser-Match/Action-Deparser 파이프라인을 사용자 정의하여 라인레이트로 동작함

## Ⅲ. 절차
```text
P4 프로그램 작성 --> 컴파일/로드 --> 테이블 엔트리 삽입 --> 라인레이트 패킷 처리
```
- 1단계: P4 등 DSL(085 참조)로 파서·테이블·액션 로직을 작성함
- 2단계: 컴파일러가 프로그램을 스위치 ASIC 바이너리로 변환하여 로드함
- 3단계: 컨트롤러가 런타임 API로 Match 테이블에 플로우 엔트리를 삽입함
- 4단계: 스위치가 파이프라인을 따라 패킷을 라인레이트로 처리함

> 요약: DSL로 파이프라인을 정의하고 컴파일·로드 후 라인레이트 처리를 수행하는 흐름임

## Ⅳ. 문제점
- 스테이지 자원 제약: SRAM·TCAM 용량이 스테이지별로 고정되어 복잡한 로직 수용이 제한됨
- 상태 관리 한계: 파이프라인이 패킷 단위 처리에 최적화되어 플로우 단위 상태 유지가 어려움
- 생태계 미성숙: P4 지원 칩·도구·인력 풀이 제한적이어서 도입 장벽이 존재함

> 요약: 스테이지 자원, 상태 관리, 생태계 미성숙이 도입의 주요 제약임

## Ⅴ. 개선방안
1. 단기: 리소스 프로파일러를 활용하여 스테이지 간 SRAM·TCAM 배분을 최적화함
2. 중기: 레지스터·카운터·메터 등 Stateful ALU를 확장하여 플로우 상태를 파이프라인 내에서 유지함
3. 장기: P4 표준화·오픈소스 컴파일러 확산으로 다중 벤더 생태계를 성숙시킴

> 요약: 자원 최적화, Stateful ALU 확장, 생태계 성숙으로 활용 범위를 넓힘

## Ⅵ. 전망
- 발전 방향: In-Network Computing으로 확장되어 캐시·합의·집계를 스위치 내에서 수행하게 됨
- 기술사적 판단: SDN의 데이터플레인 혁신을 완성하는 기술로 텔코·클라우드에서 채택이 가속됨
- 기술사 제언: 프로그래머블 스위치 도입 시 P4 개발 역량과 파이프라인 자원 설계 역량을 동시에 확보해야 함
