## Ⅰ. 개요
- **정의**: 네트워크 장비로 입출력되는 트래픽의 전송률(Rate)을 모니터링하여, 허용된 대역폭 한계에 맞게 트래픽을 제어하는 QoS 메커니즘임.
- **배경/필요성**: 갑작스러운 트래픽 폭주(Burst)로 인한 네트워크 병목 방지 및 계약된 서비스 수준(SLA) 범위 내 대역폭 할당 보장.
- **출제 의도**: 트래픽 속도 제한(Rate Limiting)의 두 가지 방식인 Shaping(지연)과 Policing(폐기)의 동작 방식 및 차이점 비교.

## Ⅱ. 구성요소
```text
[ Traffic Policing ]        [ Traffic Shaping ]
+-------------------+       +-------------------+
|     Traffic In    |       |     Traffic In    |
|        |          |       |        |          |
|  [Token Bucket]   |       |  [Leaky Bucket]   |
| (초과분 즉시 Drop)|       | (초과분 버퍼 Queue) |
|        |          |       |        |          |
|    Traffic Out    |       |    Traffic Out    |
+-------------------+       +-------------------+
```
| 구성요소 | 설명 | 비유 |
|---|---|---|
| Policing | 허용된 대역폭을 초과하는 패킷을 즉시 폐기(Drop)하거나 등급을 강등시키는 정책 | 과적 차량 즉시 단속/벌금 |
| Shaping | 허용된 대역폭을 초과하는 패킷을 큐(버퍼)에 저장했다가 일정한 속도로 지연 전송하는 기법 | 톨게이트 병목 시 차량 서행/대기 |
| Token Bucket | 일정 주기로 토큰이 쌓이고 트래픽이 토큰을 소모하여 전송되는 대역폭 제어 알고리즘 | 놀이공원 입장권 배부 |
> 요약: 폴리싱은 단호하게 트래픽을 잘라내어 즉각 제어하고, 쉐이핑은 트래픽을 큐에 담아 부드럽게 다듬어 보냄.

## Ⅲ. 절차
```text
+-----------+   +-------------+   +-------------+   +-----------+
| 패킷 인입 |-> | 전송률 측정 |-> | 정책 비교   |-> | 지연/폐기 |
+-----------+   +-------------+   +-------------+   +-----------+
```
1. **패킷 인입**: 인터페이스를 통해 네트워크 트래픽이 장비로 들어오거나 나감.
2. **전송률 측정**: 알고리즘(Token Bucket 등)을 사용해 현재 트래픽의 전송 속도와 버스트(Burst) 크기를 계산함.
3. **정책 비교**: 측정된 트래픽 량이 계약된 대역폭(CIR, Committed Information Rate)을 초과하는지 평가함.
4. **지연/폐기**: 초과 시 Policing은 해당 패킷을 즉시 버리고, Shaping은 내부 버퍼(Queue)에 담아두었다가 여유가 생길 때 전송함.
> 요약: 트래픽 속도를 실시간 측정하여 초과분을 어떻게 처리할지(Drop vs Queue) 결정하는 흐름임.

## Ⅳ. 문제점
- **폴리싱의 비효율성**: 엄격한 Drop 처리 시 TCP의 혼잡 제어가 작동하여 전체 처리량(Throughput)이 급감하는 문제 발생.
- **쉐이핑의 지연 발생**: 버퍼를 사용하므로 지연(Latency)과 지터(Jitter)가 증가하여 VoIP 등 실시간 통신에 부적합함.
- **메모리 고갈**: 대량의 버스트 트래픽 발생 시 Shaping 큐의 크기 한계를 넘어 결국 꼬리 비우기(Tail Drop)가 발생.

## Ⅴ. 개선방안
- **적절한 버스트 허용**: 토큰 버킷의 버스트 크기(Bc, Be)를 튜닝하여 일시적인 트래픽 폭주는 허용하도록 유연성 확보 (단기).
- **WRED 혼잡 회피 병행**: 큐가 가득 차기 전에 우선순위가 낮은 트래픽을 선제적으로 폐기하여 중요 트래픽 보호 (중기).
- **하이브리드 적용**: 인바운드 트래픽에는 가벼운 Policing을, 아웃바운드 트래픽에는 매끄러운 Shaping을 적용하는 분리 설계 (장기).

## Ⅵ. 전망
- 클라우드 및 API 환경에서는 API Gateway 단에서의 소프트웨어 기반 Rate Limiting(Throttling)으로 폭넓게 응용되고 있음.
- SDN 기반 자동화 환경과 결합하여, 네트워크 혼잡 상태를 피드백 받아 실시간으로 쉐이핑 정책이 동적 변경되는 방향으로 발전 중임.
