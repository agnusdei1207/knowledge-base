## Ⅰ. 개요
- **정의**: 다수 서버에 트래픽을 분산하여 가용성과 응답속도를 확보하는 네트워크 장치임
- **배경/필요성**: 단일 서버는 처리 용량 한계가 있어 트래픽 급증 시 서비스 중단이 발생하므로 부하 분산 기법이 필요함
- **비유**: 은행 창구 안내원이 대기 고객을 빈 창구로 안내하는 것과 유사함

| 출제 의도 | 반드시 짚을 핵심 | 감점 회피 포인트 |
|:---|:---|:---|
| L4/L7 차이와 분산 알고리즘 이해 | 계층별 동작 차이, 헬스체크 메커니즘 | 세션 유지(Sticky Session) 언급 누락 주의 |

> 요약: 트래픽을 여러 서버로 분산하여 단일 장애점을 제거하고 서비스 연속성을 보장하는 장치임

## Ⅱ. 구성요소
```text
Client ---> VIP(Virtual IP)
              |
        +-----+-----+
        |  LB Engine |
        +--+--+--+--+
           |  |  |
         S1  S2  S3  (Backend Pool)
```

| 구성요소 | 설명 | 비유 |
|:---|:---|:---|
| VIP | 클라이언트가 접근하는 단일 가상 IP 주소 | 대표 전화번호 |
| LB Engine | 분산 알고리즘(RR, Least Conn, Hash)을 실행하는 핵심 모듈 | 창구 안내원의 판단 로직 |
| Backend Pool | 실제 요청을 처리하는 서버 그룹 | 각 창구 직원 |
| Health Check | 서버 생존 여부를 주기적으로 확인하는 프로브 | 창구 직원 출근 확인 |

> 요약: VIP로 수신한 트래픽을 LB Engine이 알고리즘에 따라 Backend Pool로 분배하는 구조임

## Ⅲ. 절차
```text
Request --> VIP 수신 --> 알고리즘 선택 --> 서버 전달 --> 응답 반환
```
- 1단계: 클라이언트가 VIP로 요청을 전송함
- 2단계: LB Engine이 분산 알고리즘(Round Robin, Least Connection 등)으로 대상 서버를 선택함
- 3단계: 선택된 서버로 패킷을 전달하고, L7의 경우 HTTP 헤더 기반 라우팅을 수행함
- 4단계: 서버 응답을 클라이언트로 반환하며, 비정상 서버는 풀에서 제외함

> 요약: VIP 수신 → 알고리즘 기반 서버 선택 → 전달 → 응답 반환의 4단계로 동작함

## Ⅳ. 문제점
- 세션 불일치: Stateless 분산 시 동일 사용자 요청이 다른 서버로 전달됨 — 로그인 세션 유실 발생
- 단일 장애점 전이: LB 자체가 SPOF가 될 수 있음 — LB 장애 시 전체 서비스 중단
- 헬스체크 지연: 프로브 주기가 길면 장애 서버로 트래픽이 계속 전달됨 — 사용자 오류 응답 증가

> 요약: 세션 관리, LB 자체 가용성, 헬스체크 정밀도가 주요 과제임

## Ⅴ. 개선방안
1. 단기: Sticky Session 또는 세션 클러스터링 적용으로 세션 일관성 확보
2. 중기: Active-Standby 또는 Active-Active 이중화로 LB 자체 가용성 보장
3. 장기: 능동 헬스체크 주기 최적화 및 서킷브레이커 패턴 연계로 장애 전파 차단

> 요약: 세션 클러스터링, LB 이중화, 능동 헬스체크로 단계별 개선이 가능함

## Ⅵ. 전망
- 발전 방향: 클라우드 네이티브 환경에서 서비스 메시 기반 L7 로드밸런싱으로 전환 중임
- 기술사적 판단: 마이크로서비스 아키텍처 확산에 따라 애플리케이션 계층 분산 중요성이 증가함
- 기술사 제언: 트래픽 패턴 분석 기반 자동 스케일링과 LB 정책 연동 설계가 필요함
