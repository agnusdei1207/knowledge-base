## Ⅰ. 개요
- **정의**: 단일 TCP 연결 위에서 클라이언트와 서버 간 풀 듀플렉스(Full-duplex, 양방향) 통신을 제공하는 웹 표준 프로토콜임.
- **배경/필요성**: 기존 HTTP의 비상태성(Stateless)과 단방향 특성 극복, 폴링(Polling) 방식의 헤더 오버헤드 및 지연 시간 감소 목적.
- **출제 의도**: 웹소켓의 동작 원리(Handshake, Frame), 기존 HTTP 통신과의 차이점 및 지속 연결 관리 이슈 이해.

## Ⅱ. 구성요소
```text
+-----------------------+                +-----------------------+
|      Web Client       |                |      Web Server       |
|  (Browser, App)       |                |  (WebSocket Support)  |
+-----------+-----------+                +-----------+-----------+
            | HTTP Upgrade Request (Handshake)       |
            |--------------------------------------->|
            | HTTP 101 Switching Protocols           |
            |<---------------------------------------|
            |       Bidirectional Data Frames        |
            |<======================================>|
```
| 구성요소 | 설명 | 비유 |
|---|---|---|
| Client | 연결을 초기화하고 서버와 실시간으로 데이터를 주고받는 브라우저 등 | 전화 거는 사람 |
| Server | 클라이언트의 연결 요청을 수락하고 비동기적으로 이벤트를 푸시하는 서버 | 전화를 받는 상담원 |
| Data Frame | 연결이 성립된 후 페이로드만 담아 작고 빠르게 송수신하는 데이터 단위 | 전화선 속 목소리 |
> 요약: HTTP로 시작하여 웹소켓 프로토콜로 전환(Upgrade)한 뒤, 지속적인 양방향 통신 채널을 확립함.

## Ⅲ. 절차
```text
+-----------+   +-------------+   +-------------+   +-----------+
| 연결 요청 |-> | 프로토콜전환|-> | 양방향 통신 |-> | 연결 종료 |
+-----------+   +-------------+   +-------------+   +-----------+
```
1. **연결 요청**: 클라이언트가 표준 HTTP 요청 헤더에 `Upgrade: websocket`을 포함하여 서버에 전송함.
2. **프로토콜 전환**: 서버가 이를 수락하면 `101 Switching Protocols` 상태 코드로 응답하여 핸드쉐이크를 완료함.
3. **양방향 통신**: HTTP 헤더 없이 경량화된 메시지 프레임(텍스트 또는 바이너리)을 양쪽에서 자유롭게 송수신함.
4. **연결 종료**: 어느 한쪽에서 Close 프레임을 전송하면 TCP 연결이 정상적으로 해제됨.
> 요약: 초기 협상만 HTTP를 거치며, 이후에는 전용 프레임 기반의 실시간 데이터 교환이 연속적으로 이루어짐.

## Ⅳ. 문제점
- **서버 리소스 고갈**: 대규모 클라이언트가 동시 접속을 유지(Keep-Alive)해야 하므로 서버의 소켓과 메모리 점유율 급증.
- **프록시 및 방화벽 차단**: 일부 구형 L7 로드밸런서나 방화벽이 장기 지속되는 HTTP 커넥션을 비정상으로 간주해 강제 단절함.
- **상태 관리 복잡성**: 서버가 재시작되거나 스케일 아웃될 때 세션 유지를 위한 세션 클러스터링 구성이 까다로움.

## Ⅴ. 개선방안
- **연결 안정성 확보**: 하트비트(Ping/Pong) 프레임을 주기적으로 전송하여 방화벽의 연결 해제 방지 및 상태 확인 (단기).
- **로드밸런싱 최적화**: L7 로드밸런서에서 웹소켓 프로토콜 지원 및 Sticky Session(세션 고정) 설정 활성화 (중기).
- **대체 기술 활용**: 단방향 푸시만 필요한 경우 SSE(Server-Sent Events)를 사용하거나 HTTP/3(QUIC) 기반 양방향 스트리밍 도입 (장기).

## Ⅵ. 전망
- 실시간 채팅, 주식 티커, 멀티플레이어 웹 게임 등 지연 시간이 중요한 애플리케이션의 필수 표준으로 유지됨.
- 향후 HTTP/3 프로토콜과 WebTransport API가 성숙해짐에 따라 웹소켓의 역할을 일부 대체하거나 보완할 것으로 예상됨.
