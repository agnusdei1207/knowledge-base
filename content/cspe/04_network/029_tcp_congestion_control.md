## 핵심 인사이트 (3줄 요약)
> 1. **본질**: TCP 혼잡 제어는 라우터 큐의 한계를 초과하여 발생하는 패킷 손실 및 전 네트워크의 마비(Congestion Collapse)를 막기 위해, 송신측이 자체적으로 전송량(`cwnd`)을 통제하는 기법이다.
> 2. **원리**: 1에서 시작해 지수적으로 전송량을 폭발시키는 **Slow Start**, 임계점 이후 선형적으로 조심스럽게 늘리는 **Congestion Avoidance**, 그리고 패킷 유실 시 전송량을 절반(또는 1)으로 대폭 줄이는 **AIMD** 방식을 통해 대역폭의 균형을 찾는다.
> 3. **판단 포인트**: 전통적인 패킷 손실(Loss) 기반의 Reno/CUBIC 알고리즘은 큐가 꽉 찰 때까지 속도를 올리므로 버퍼블로트(Bufferbloat)를 유발한다. 현대 클라우드와 미디어 환경에서는 지연(Delay)을 기반으로 혼잡을 미리 회피하는 구글 BBR의 도입이 필수적이다.

## Ⅰ. 개요 및 필요성

- **개요**: 네트워크 망의 혼잡 상태를 추정하여 송신 단말이 내보내는 데이터의 윈도우 크기(Congestion Window, `cwnd`)를 동적으로 조절하는 TCP의 핵심 보호 메커니즘.
- **필요성**:
  1. **네트워크 붕괴(Congestion Collapse) 방지**: 라우터 병목 구간에서 패킷이 버려지면 단말들이 일제히 재전송을 시도하여 전체 통신망이 마비되는 악순환을 막아야 함.
  2. **대역폭의 공평성(Fairness)**: 여러 TCP 연결이 제한된 대역폭을 공평하게 나누어 쓸 수 있도록 수학적(AIMD) 합의 메커니즘 제공.
  3. **효율 극대화**: 네트워크가 한산할 때는 최대한 빠르게 대역폭을 점유하고, 막힐 때는 즉각 양보하여 전체 스루풋(Throughput)을 높임.

## Ⅱ. 아키텍처 및 핵심 원리

- **TCP Reno 기준 혼잡 제어 상태 변화도**

```text
cwnd 크기
  |
  |             [ 혼잡 발생 (3 Dup ACK) ]
  |            /         | \ (절반으로 뚝 떨어짐)
  |           / (회피)   |  \
  |          / (선형)    |   \         / (다시 선형 증가)
  |         /            |    \       /
ssthresh --+             |     +-----+ (Fast Recovery 적용)
  |        |             |     (ssthresh)
  |        | (지수)      |
  |       /              |
  |      / (Slow Start)  |
  +--------------------------------------------------- Time
```

- **4단계 핵심 알고리즘**:
  1. **Slow Start (지수 증가)**: `cwnd`를 1로 시작해 매 ACK 수신 시마다 1씩 더함. 결과적으로 1 RTT마다 `cwnd`가 2배씩 폭발적으로 증가하여 남는 대역폭을 매우 빠르게 탐색.
  2. **Congestion Avoidance (혼잡 회피)**: `cwnd`가 특정 임계치(`ssthresh`)에 도달하면 1 RTT당 1씩만 증가(선형 증가, Additive Increase)시켜 병목 지점을 조심스럽게 탐색.
  3. **Fast Retransmit (빠른 재전송)**: 타임아웃을 기다리지 않고, 동일한 ACK 번호를 3번 중복 수신(3 Duplicate ACK)하면 해당 패킷이 유실된 것으로 간주하고 즉각 재전송.
  4. **Fast Recovery (빠른 회복)**: (Reno 방식) 패킷이 완전히 막힌 것(Timeout)이 아니라 일부만 유실(3 Dup ACK)된 경우, `cwnd`를 1로 초기화하지 않고 현재의 절반(1/2)으로만 줄여 통신 충격을 완화함.

## Ⅲ. 비교 및 연결

| 혼잡 감지 방식 | 발생 원인 및 해석 | 송신측 대응 (Reno 기준) |
|:---|:---|:---|
| **RTO (Timeout)** | 치명적 혼잡. 라우터 큐가 가득 차 패킷 흐름이 완전히 끊김. | `ssthresh` = 현재 cwnd/2<br>**`cwnd` = 1** (Slow Start로 강등) |
| **3 Duplicate ACK** | 경미한 혼잡. 일부 패킷은 유실됐으나 뒤이어 다른 패킷들은 도착함. | `ssthresh` = 현재 cwnd/2<br>**`cwnd` = ssthresh** (Fast Recovery) |

- **흐름 제어와의 관계**: TCP의 최종 송신량은 흐름 제어가 통보한 `rwnd(수신 버퍼)`와 자가 측정한 `cwnd(네트워크 한계)` 중 **더 작은 값**에 의해 결정된다.

## Ⅳ. 실무 적용 및 기술사 판단

- **버퍼블로트(Bufferbloat) 현상 트러블슈팅**
  - 문제: 라우터 메모리가 저렴해져 큐가 지나치게 커짐. 전통적인 CUBIC/Reno는 패킷이 "버려질 때까지" 속도를 올리므로 큐가 꽉 찬 상태가 유지되어 지연(Latency)이 기하급수적으로 길어지는 핑(Ping) 스파이크 발생.
  - 판단: 패킷 유실을 혼잡의 척도로 삼는 Loss-based 알고리즘의 구조적 한계임. RTT 변화량을 감지해 패킷 유실 전 미리 속도를 제어하는 **BBR(Delay-based)** 알고리즘 적용 및 라우터 단의 AQM(Active Queue Management) 도입을 병행해야 한다.
- **무선망(Wi-Fi/5G) 환경의 TCP 오판 문제**
  - 문제: 무선 환경에서는 전파 간섭으로 단순 패킷 에러가 자주 발생한다. 하지만 표준 TCP는 이를 "네트워크 혼잡"으로 오판하여 대역폭을 반 토막 낸다.
  - 판단: 무선망 구간이 포함된 인프라 설계 시, 무선 에러와 실제 혼잡을 구별해 내는 TCP Westwood 등의 통신 특화 알고리즘 튜닝을 적극 고려해야 한다.

## Ⅴ. 기대효과 및 결론

- **결론**: 혼잡 제어는 이기적인 단말들이 공용 인프라(인터넷)를 파괴하지 않도록 자율적으로 속도를 조절하는 수학적 예술(AIMD)이다.
- **기대효과**: 최신 BBR 알고리즘 등으로 커널 파라미터를 최적화하면, 버퍼블로트를 예방하고 패킷 손실률이 높은 글로벌 망에서도 수 배 이상 향상된 처리량과 낮은 지연 시간을 확보할 수 있다.

### 📌 관련 개념 맵
TCP 신뢰성 제어 $\rightarrow$ 슬라이딩 윈도우 $\rightarrow$ AIMD 메커니즘 $\rightarrow$ TCP Tahoe/Reno (Loss-based) $\rightarrow$ TCP BBR (Delay-based).

### 📈 관련 키워드 및 발전 흐름도
`인터넷 대란 (Congestion Collapse)` $\rightarrow$ `TCP Tahoe (Slow Start 도입)` $\rightarrow$ `TCP Reno (Fast Recovery 추가로 효율 증대)` $\rightarrow$ `TCP CUBIC (리눅스 표준, 3차 함수 고속화)` $\rightarrow$ `TCP BBR (현대 클라우드 표준, 지연 기반)`

### 👶 어린이를 위한 3줄 비유 설명
1. 명절 고속도로에 차(데이터)를 보낼 때, 처음엔 차가 없으니 1대, 2대, 4대씩 빠르게 확확 늘려서 톨게이트를 통과시킵니다 (Slow Start).
2. 그러다 조금 막힐 것 같으면 1대씩 살살 조심스럽게 늘립니다 (Avoidance).
3. 만약 고속도로 중간에서 빵빵거리고 난리가 났다는 소식이 들리면(패킷 유실), 즉시 톨게이트로 들어가는 차의 양을 반으로 팍 줄여서 고속도로를 보호합니다 (AIMD).
