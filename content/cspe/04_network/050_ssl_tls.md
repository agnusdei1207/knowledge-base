## Ⅰ. 개요
- **정의**: 클라이언트와 서버가 애플리케이션 데이터를 안전하게 교환하기 전, 서로의 신원을 확인하고 암호화에 쓸 대칭키를 생성하는 협상 과정임.
- **배경/필요성**: 인터넷(HTTP) 상의 데이터 도청(Sniffing), 변조 방지 및 통신 상대방(서버)이 신뢰할 수 있는지에 대한 인증 보장.
- **출제 의도**: 비대칭키와 대칭키를 혼합 사용하는 하이브리드 암호화 방식의 이유 파악, 인증서 체인 검증 메커니즘 이해.

## Ⅱ. 구성요소
```text
+-----------------------+              +-----------------------+
|        Client         |              |        Server         |
|  (Web Browser)        |              |  (Web/App Server)     |
+-----------+-----------+              +-----------+-----------+
            |  [1] Client Hello (지원 Cipher 목록) |
            |------------------------------------->|
            |  [2] Server Hello + Certificate      |
            |<-------------------------------------|
            |  [3] Key Exchange (Pre-Master Secret)|
            |------------------------------------->|
            |  [4] Finished (이후 양방향 대칭 암호화)|
            |<====================================>|
```
| 구성요소 | 설명 | 비유 |
|---|---|---|
| Cipher Suite | 서로 지원하는 암호화 알고리즘, 해시 방식, 키 교환 방식의 세트 목록 | 통신용 비밀규칙 세트 |
| Certificate (인증서)| 서버가 신뢰할 수 있는 기관(CA)으로부터 발급받은 전자 신분증 (서버의 공개키 포함) | 국가 발급 여권 |
| Session Key | 핸드쉐이크 결과로 양쪽이 나눠 가지며, 실제 대용량 데이터를 빠르게 암호화할 대칭키 | 일회용 자물쇠 열쇠 |
> 요약: 공개키 방식으로 안전하게 세션키(대칭키)를 교환하고, 이후 데이터는 세션키로 빠르게 암호화함.

## Ⅲ. 절차
```text
+-----------+   +-------------+   +-------------+   +-----------+
| Client인사|-> | Server응답  |-> | 세션키 생성 |-> | 보안통신  |
+-----------+   +-------------+   +-------------+   +-----------+
```
1. **Client 인사**: 클라이언트가 서버에 접속하며 자신이 지원하는 암호화 방식 목록(Cipher Suite)과 난수를 보냄(Client Hello).
2. **Server 응답**: 서버가 하나의 암호화 방식을 선택하고 자신의 인증서(공개키 포함)와 난수를 응답함(Server Hello).
3. **세션키 생성**: 클라이언트가 인증서를 검증한 후, 새로운 난수를 서버의 공개키로 암호화하여 전송함. 양측은 세 난수를 조합해 세션키를 생성함.
4. **보안 통신**: 핸드쉐이크 완료(Finished) 후, 생성된 세션키(대칭키)를 사용하여 빠르고 안전하게 애플리케이션 데이터를 교환함.
> 요약: 신분 확인과 암호 방식 합의를 거쳐, 대용량 전송에 적합한 대칭키를 생성하는 협상 과정임.

## Ⅳ. 문제점
- **초기 연결 지연**: TCP 3-Way Handshake 이후에 TLS 핸드쉐이크가 추가로 진행되므로 초기 응답 속도(RTT)가 크게 증가함.
- **CPU 연산 부하**: 연결을 맺을 때마다 복잡한 비대칭키(RSA 등) 수학적 연산을 수행해야 하므로 서버 리소스 고갈 유발.
- **구버전 취약점**: 하위 호환성을 위해 남겨둔 SSL 3.0, TLS 1.0/1.1 버전에서 POODLE, BEAST 등 치명적 보안 결함 지속 발생.

## Ⅴ. 개선방안
- **성능 최적화 활용**: 세션 재개(Session Resumption/Ticket) 기능을 활성화하여 재접속 시 핸드쉐이크 과정을 단축 (단기).
- **프로토콜 업그레이드**: 구버전 프로토콜 지원을 중단하고, 1-RTT(또는 0-RTT)만으로 핸드쉐이크를 완료하는 최신 TLS 1.3 강제 적용 (중기).
- **양자 내성 암호 대비**: 양자 컴퓨터의 연산력에 의해 기존 RSA/ECC 공개키가 해독될 위험에 대비하여 포스트 양자 암호(PQC) 알고리즘 연구 적용 (장기).

## Ⅵ. 전망
- 웹 생태계는 Let's Encrypt 등의 보급으로 사실상 100% HTTPS(TLS) 통신 환경으로 완전히 전환되었음.
- 향후 HTTP/3(QUIC) 기술의 보급과 함께 전송 계층 통신 시작 단계부터 TLS 1.3 기반 암호화가 기본 내장되는 방향으로 결합 발전 중임.
