## Ⅰ. 개요
- **정의**: 제어 평면과 데이터 평면을 분리하여 네트워크를 소프트웨어로 중앙 제어하는 아키텍처
- **배경/필요성**: 전통 네트워크는 장비별 개별 설정으로 변경 민첩성이 낮아 프로그래머블 제어가 필요함
- **비유**: 각 교차로 신호등을 개별 조작하던 것을 중앙 교통관제센터에서 일괄 제어하는 것과 유사함

| 출제 의도 | 반드시 짚을 핵심 | 감점 회피 포인트 |
|:---|:---|:---|
| 3계층 아키텍처와 제어/데이터 평면 분리 원리 | Northbound/Southbound API 역할 구분 | SDN은 특정 프로토콜이 아닌 아키텍처 개념임을 명확히 할 것 |

> 요약: 제어·데이터 평면 분리로 네트워크를 프로그래머블하게 관리하는 아키텍처임

## Ⅱ. 구성요소
```text
Application Layer (NB API)
        |
  Control Layer (SDN Controller)
        |
Infrastructure Layer (SB API)
   |       |       |
Switch  Switch  Switch
```

| 구성요소 | 설명 | 비유 |
|:---|:---|:---|
| SDN Controller | 네트워크 전체 토폴로지를 파악하고 포워딩 규칙을 결정하는 중앙 두뇌 | 교통관제센터 |
| Northbound API | 애플리케이션과 컨트롤러 간 통신 인터페이스(REST 등) | 관제센터에 요청을 보내는 민원 창구 |
| Southbound API | 컨트롤러와 스위치 간 통신 프로토콜(OpenFlow 등) | 관제센터가 신호등에 명령을 전달하는 통신선 |
| Data Plane | 컨트롤러 지시에 따라 패킷을 전달하는 스위치 계층 | 신호에 따라 차량을 통과시키는 교차로 |

> 요약: Controller·NB/SB API·Data Plane의 3계층 구조로 네트워크를 추상화함

## Ⅲ. 절차
```text
앱 요청 --> 컨트롤러 수신 --> 플로우 규칙 생성 --> 스위치 배포 --> 패킷 포워딩
```
- 1단계: 애플리케이션이 NB API를 통해 네트워크 정책(QoS, ACL 등)을 요청함
- 2단계: SDN Controller가 토폴로지 정보를 기반으로 포워딩 규칙을 생성함
- 3단계: SB API(OpenFlow 등)를 통해 스위치에 Flow Table 엔트리를 배포함
- 4단계: 스위치가 Flow Table에 따라 패킷을 매칭·포워딩함

> 요약: 앱 요청부터 스위치 포워딩까지 4단계로 중앙 제어 기반 패킷 전달을 수행함

## Ⅳ. 문제점
- 단일 장애점: 컨트롤러 장애 시 전체 네트워크 제어가 중단됨
- 확장성 제한: 대규모 망에서 컨트롤러-스위치 간 제어 트래픽이 병목이 됨
- 레거시 전환: 기존 장비의 OpenFlow 미지원으로 점진적 전환이 어려움

> 요약: 단일 장애점·확장성·레거시 호환이 SDN 도입의 주요 장벽임

## Ⅴ. 개선방안
1. 단기: 컨트롤러 이중화(Active-Standby/Cluster)로 가용성을 확보함
2. 중기: 계층형 컨트롤러 구조(Local + Global)로 제어 트래픽을 분산함
3. 장기: Hybrid SDN(기존 프로토콜 + SDN 병행)으로 점진적 마이그레이션을 수행함

> 요약: 이중화·계층화·하이브리드 전환으로 단계적 개선이 가능함

## Ⅵ. 전망
- 발전 방향: Intent-Based Networking과 결합하여 의도 기반 자동 네트워크 관리로 진화함
- 기술사적 판단: 데이터센터·캠퍼스·WAN 전 영역에서 SDN 원리가 표준 아키텍처로 정착 중임
- 기술사 제언: NFV(027 참조)·OpenFlow(029 참조)와의 관계, Intent-Based 연계를 함께 학습할 필요
