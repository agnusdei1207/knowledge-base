# 📖 【암기용】 개념 완전 이해

> 목적: 이 개념을 처음 보는 사람도 완벽히 이해하게 만든다. 시험 답안 양식이 아니라, 이해를 위한 친절한 설명이다.

## 한눈에
- **개요**: 전 세계 네트워크가 IPv4에서 IPv6로 넘어가기 위해 사용하는 3가지 징검다리 기술
- **왜 필요한가**: 인터넷 전체를 하루아침에 IPv6로 바꿀 수 없으므로, 구형(IPv4) 기기와 신형(IPv6) 기기가 서로 통신하며 공존할 방법이 필요하다.
- **핵심 직관**: **듀얼 스택**은 두 언어를 모두 하는 통역사, **터널링**은 섬(IPv6)과 섬(IPv6)을 잇는 배(IPv4 바다), **변환**은 번역기(번역 게이트웨이)다.

## 깊이 이해
- **배경·문제의식**: IPv4와 IPv6는 프로토콜 헤더 구조와 주소 체계가 전혀 달라 직접 통신할 수 없다. 기기 교체 주기가 제각각이므로 점진적이고 매끄러운 마이그레이션 전략이 필수적이다.
- **작동 원리**: 
  - **듀얼 스택(Dual Stack)**: 하나의 장비(라우터/PC)가 IPv4와 IPv6 프로토콜 스택을 모두 설치해 상황에 맞게 쓴다.
  - **터널링(Tunneling)**: IPv6 패킷을 IPv4 패킷으로 포장(캡슐화)하여 IPv4 망을 통과시킨 후, 반대편에서 포장을 뜯어 IPv6로 복원한다 (예: 6to4, ISATAP).
  - **변환(Translation)**: IPv6-Only 클라이언트가 IPv4-Only 서버에 접속할 때, 중간 라우터가 헤더와 주소를 바꿔치기한다 (예: NAT64, DNS64).
- **비유**: 듀얼 스택은 스마트폰에 유선과 무선 이어폰 단자를 둘 다 두는 것. 터널링은 한국(IPv6)에서 미국(IPv6)으로 편지를 보낼 때 중국(IPv4) 우체국을 지나야 해서 잠시 중국어 봉투에 넣어 보내는 것.
- **구체 예시**: 아이폰(IPv6 전용) 사용자가 네이버(IPv4)에 접속하면, 통신사 게이트웨이(NAT64)가 IPv6 주소를 공인 IPv4 주소로 변환하여 네이버로 보내고 응답을 받아 다시 변환해 준다.
- **흔한 오해·주의점**: 듀얼 스택이 가장 이상적이지만, 모든 장비가 IPv4 공인 주소를 소모한다는 한계가 있다. 장기적으로는 Native IPv6(IPv6-Only)로 가기 위해 변환 기술이 쓰인다.

## 연결 개념
- IPv4 / IPv6 — 두 세대의 IP 프로토콜
- 캡슐화(Encapsulation) — 터널링 기법의 핵심 원리
- NAT (Network Address Translation) — 주소 변환(NAT64/NAT-PT)의 근간 기술

# 📝 【답안용】 시험 답안 템플릿

> 핵심: 이 시험은 정보를 많이 나열하는 시험이 아니라, 문제 신호어에서 출제자 의도를 읽고 핵심 논점을 선별해 쓰는 시험이다.

## 핵심 인사이트 (3줄 요약)

> 1. **본질**: IPv6 전환 기술은 비호환적인 IPv4망과 IPv6망을 공존시키며 원활히 통신하게 하는 과도기적 마이그레이션 메커니즘이다.
> 2. **가치**: 대규모 인프라의 동시 교체(Forklift Upgrade) 위험을 피하고, 점진적인 투자를 통해 서비스 중단 없이 차세대 네트워크로 이행할 수 단서를 제공한다.
> 3. **판단 포인트**: 도입 환경과 투자 여력에 따라, 성능이 좋은 듀얼 스택, 망 연동을 위한 터널링, 주소 고갈 대처를 위한 변환(NAT64)을 전략적으로 선택해야 한다.

## Ⅰ. 개요 및 필요성

- 정의: IPv4망과 IPv6망 간 상호 호환성을 제공하여 점진적 네트워크 이전을 지원하는 마이그레이션 기술 셋
- 배경: IPv4 헤더와 IPv6 헤더는 근본적으로 호환되지 않아 직접 통신이 불가능하며, 인프라의 일괄 업그레이드는 불가능
- 필요성: 신규 모바일/IoT망(IPv6)이 기존 레거시 콘텐츠 서버(IPv4)와 단절 없이 통신하여 서비스 연속성을 보장하기 위함

---

## Ⅱ. 구조 및 구성요소

```text
IPv6 전환 전략 구조
  +-> 듀얼 스택 (Dual Stack): 호스트/라우터에 두 프로토콜 동시 탑재
  +-> 터널링 (Tunneling): IPv6 망 --- [ IPv4 망 캡슐화 ] --- IPv6 망
  +-> 변환 (Translation): IPv6 Only 단말 -> [ NAT64/DNS64 변환기 ] -> IPv4 서버
```

| 기술 분류 | 구성요소 | 핵심 메커니즘 |
|:---|:---|:---|
| 듀얼 스택 (Dual Stack) | IPv4/IPv6 스택, DNS (A, AAAA 레코드) | DNS 응답 결과(AAAA 선호)에 따라 목적지 스택 선택 연결 |
| 터널링 (Tunneling) | Dual-Stack 라우터 (터널 양단) | 송신측은 IPv6 패킷을 IPv4 헤더로 캡슐화, 수신측 역캡슐화 |
| 주소 변환 (Translation) | NAT64 라우터, DNS64 서버 | DNS64가 합성 주소 제공, NAT64가 L3/L4 헤더 정보를 동적 변환 |

> 요약: 듀얼 스택은 단말 관점의 완벽한 호환을, 터널링은 망 인프라 연동을, 변환은 이기종 프로토콜 간의 실제 대화를 중계한다.

---

## Ⅲ. 동작원리 및 흐름도

```text
[NAT64 / DNS64 동작 흐름]
IPv6 클라이언트 -> (A 쿼리) -> DNS64 -> (IPv4 쿼리) -> IPv4 서버 응답
-> DNS64가 가짜 IPv6 주소 합성 반환 -> 클라이언트가 해당 주소로 트래픽 전송
-> NAT64 게이트웨이가 IPv6 헤더를 IPv4 헤더로 치환 -> IPv4 서버 도달
```

| 단계 | 처리 내용 | 검증 기준 |
|:---:|:---|:---|
| 1 | **주소 요청 및 합성** | IPv6 클라이언트가 요청 시 DNS64가 IPv4 주소에 Prefix를 덧붙여 합성 |
| 2 | **세션 테이블 생성** | 클라이언트 트래픽이 NAT64 라우터 도달 시, IPv6-IPv4 매핑 세션 기록 |
| 3 | **헤더 변환** | NAT64가 패킷의 IP 헤더 형식을 변환(IPv6 → IPv4)하고 체크섬 재계산 |
| 4 | **응답 역변환** | 서버 응답 트래픽 수신 시, 세션 테이블 참조하여 IPv4 → IPv6로 복원 |

> 요약: 변환 기술은 DNS와 라우터가 유기적으로 협력하여, 단말이 상대방이 IPv4인지 모른 채 통신하게 하는 무결절(Seamless) 경험을 제공한다.

## Ⅳ. 특징

| 구분 | 듀얼 스택 (Dual Stack) | 터널링 (Tunneling) | 주소 변환 (Translation) |
|:---|:---|:---|:---|
| 장점 | 병목 없음, 최고 성능 및 완벽 호환 | 기존 망(IPv4) 구조 변경 없이 IPv6 연동 | IPv4 주소 절약, IPv6 단일 망 구축 가능 |
| 단점 | 여전히 IPv4 주소 소모 및 장비 부하 | 캡슐화 오버헤드 발생 (MTU 크기 주의) | 변환 지연 발생, NAT 내장 IPsec 사용 불가 |
| 적용 단계 | 초기(과도기) 망 장비 및 코어 라우터 | IPv6 지점 간 연결 (본사-지사) | 후기 단계, 5G/모바일 클라이언트 접속망 |

> 요약: 완벽한 통신은 듀얼 스택이나 IPv4 주소 고갈을 막지 못하므로, 궁극적으로는 터널링을 거쳐 Native IPv6망 + NAT64 변환 체계로 발전한다.

## Ⅴ. 심화 비교 및 적용 판단

| 비교 축 | NAT-PT (구형) | NAT64 + DNS64 (신형) | 선택 기준 |
|:---|:---|:---|:---|
| 변환 방식 | DNS ALG(Application Layer Gateway) 의존 | DNS와 라우터(NAT) 기능 명확 분리 | 아키텍처 결합도 하향 |
| 프로토콜 범위 | 모든 프로토콜 변환 시도 | TCP, UDP, ICMP 위주로 최적화 | 처리량 및 라우터 부하 |
| 현재 위상 | IETF RFC 4966에 의해 사장(Deprecated) | 모바일 통신사(SKT 등) 주력 도입 | 현재 표준 및 벤더 지원 여부 |

> 요약: 과거 NAT-PT는 DNS ALG의 잦은 버그와 병목으로 실패하였고, 현재는 책임을 명확히 분리한 NAT64/DNS64가 표준으로 자리 잡았다.

| 리스크 | 원인 | 대응 방안 | 확인 지표 |
|:---|:---|:---|:---|
| 캡슐화 단편화(Fragmentation) | 터널링 시 IPv4 헤더 추가(20B)로 MTU 1500 초과 | 터널 엔드포인트에서 TCP MSS Clamping 설정(1440 등) | 패킷 파편화 비율 및 폐기(Drop) 수 |
| 변환기 성능 병목 | NAT64 라우터의 세션 테이블 고갈 및 CPU 부하 | CGNAT 급 대용량 장비 도입 및 상태 비저장(MAP-T) 전환 검토 | 동시 세션 수, 포트 소갈(Port Exhaustion) |
| 애플리케이션 호환성 | 앱 코드 하드코딩된 IPv4 주소 (리터럴 IP) | 애플리케이션 레벨 도메인(FQDN) 사용 강제화 정책 | 404/Timeout 등 접속 실패율 |

> 요약: 전환 기술의 핵심 장애 포인트는 패킷 사이즈 초과와 세션 테이블 고갈이며, 네트워크 장비의 용량 산정과 앱 개발 표준(도메인 사용)으로 회피해야 한다.

## Ⅵ. 실무 적용 및 결론

**적용 방안 3개:**
1. **코어망 듀얼 스택 구성**: 엔터프라이즈 코어 스위치 및 방화벽을 듀얼 스택 모드로 프로비저닝하여, IPv4/IPv6 라우팅 프로토콜(OSPFv2/v3) 동시 구동
2. **5G/모바일 클라이언트 NAT64 적용**: 모바일 단말에는 IPv6만 할당하여 주소를 무한 확보하고, 외부 IPv4 웹사이트 접속은 통신사 코어 NAT64를 통해 중계
3. **ISATAP 기반 터널링 구축**: 사내 IPv4 전용 백본망을 교체할 수 없는 환경에서, 윈도우/리눅스 호스트 간 ISATAP 터널을 구성하여 사내 IPv6 통신 지원

**결론 (2줄):**
- 기술사 판단: 한 가지 기술로 완벽한 전환은 불가능하며, 인프라는 듀얼 스택으로 구성하고 레거시 앱 지원은 변환(NAT64)으로 푸는 혼합 아키텍처가 필수적이다.
- 향후 방향: IPv6-Only 망 구축이 대세가 되면서, 라우터가 변환 상태를 유지하지 않아 병목이 없는 MAP-T/MAP-E 등 무상태(Stateless) 전환 기술로 진화하고 있다.
