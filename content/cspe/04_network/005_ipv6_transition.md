# 📖 【암기용】 개념 완전 이해

> 목적: IPv6 전환 기술을 듀얼 스택, 터널링, 변환의 선택 문제로 이해하게 만든다. 시험 답안 양식이 아니라, 전환 시나리오를 설명한다.

## 한눈에
- **개요**: IPv4 운영망에서 IPv6로 단계 이전하기 위한 공존·연결 기술
- **왜 필요한가**: 인터넷 전체를 동시에 IPv6로 바꿀 수 없으므로 IPv4와 IPv6가 일정 기간 함께 동작해야 한다.
- **핵심 직관**: 낡은 도로와 새 도로가 공존할 때 두 길을 모두 쓰거나, 새 길을 낡은 길 안에 실어 보내거나, 중간에서 언어를 번역한다.

## 깊이 이해
- **배경·문제의식**: IPv4 주소 고갈과 NAT 복잡도 때문에 IPv6 도입이 필요하지만, 기존 장비·애플리케이션·운영 정책은 IPv4 중심이다. 전환 기술은 서비스 중단 없이 단계별 이전을 가능하게 한다.
- **작동 원리**: 듀얼 스택은 장비가 IPv4와 IPv6를 모두 처리한다. 터널링은 IPv6 패킷을 IPv4 패킷 안에 캡슐화한다. 변환은 IPv4와 IPv6 헤더와 주소를 중간 장비에서 변환한다.
- **비유**: 두 언어를 모두 아는 사람은 듀얼 스택, 편지를 다른 봉투에 넣는 방식은 터널링, 통역사가 중간에서 바꾸는 방식은 변환이다.
- **구체 예시**: IPv6-only 단말이 IPv4 서버에 접속할 때 DNS64가 AAAA 레코드를 합성하고 NAT64가 IPv6와 IPv4 주소·헤더를 변환한다.
- **흔한 오해·주의점**: 듀얼 스택은 전환 완료가 아니라 운영 범위가 두 배가 되는 과도기 방식이다. IPv6 방화벽과 로그 수집을 별도로 준비해야 한다.

## 연결 개념
- IPv4·IPv6 주소 체계: 전환 대상 주소 구조
- NAT64/DNS64: IPv6-only 환경에서 IPv4 서비스 접근
- PMTUD: 터널링 환경의 MTU 장애 진단

# 📝 【답안용】 시험 답안 템플릿

> 목적: 시험장에서 25분에 그대로 쓰는 답안 양식. 작성방식(추상표현 금지·수치·도식·문제유형 전환)을 준수한다.
> 핵심: IPv6 전환은 듀얼 스택, 터널링, 변환을 조건별로 선택하고 DNS·보안·MTU 리스크를 제시해야 한다.

## 핵심 인사이트 (3줄 요약)

> 1. **본질**: IPv6 전환 기술은 IPv4와 IPv6가 공존하는 기간에 서비스 연결성을 유지하기 위한 dual stack, tunneling, translation 기법이다.
> 2. **가치**: 서비스 중단 없이 IPv6 도입 범위를 확대하고 IPv4 주소 고갈, CGNAT 의존, 글로벌 연동 제약을 줄인다.
> 3. **판단 포인트**: 단순 연결보다 DNS, 보안 정책, MTU, 로그, 애플리케이션 IPv6 호환성을 함께 검토해야 한다.

## 출제 의도 및 답안 포인트

| 출제 의도 | 반드시 짚을 핵심 | 감점 회피 포인트 |
|:---|:---|:---|
| IPv6 전환 방식 분류 확인 | dual stack, tunneling, translation | 방식 이름만 나열하고 선택 조건 누락 |
| 전환 설계 판단 확인 | 단계별 도입, DNS A/AAAA, ACL, MTU | IPv6 도입을 주소 변경만으로 설명 |
| 운영 리스크 인식 확인 | ICMPv6, PMTUD, 로그, NAT64 한계 | IPv4 보안 정책만 적용 |

> 요약: IPv6 전환 답안은 공존 방식별 구조와 운영 리스크를 조건부로 제시해야 한다.

## Ⅰ. 개요 및 필요성

IPv6 전환 기술은 IPv4 기반 서비스를 IPv6 환경으로 단계 이전하는 공존 기술이다. 인터넷과 기업망은 IPv4 자산이 남아 있어 일괄 전환이 어렵다. 듀얼 스택, 터널링, 변환을 사용해 연결성, 보안, 운영 지표를 유지하며 이전한다.

---

## Ⅱ. 구조 및 구성요소

```text
IPv4 Network / IPv6 Network
-> Dual Stack: IPv4 + IPv6 동시 운용
-> Tunneling: IPv6 packet inside IPv4
-> Translation: IPv6 <-> IPv4 header/address 변환
-> DNS / Routing / Security Policy 연계
```

| 구성요소 | 역할 | 대표 기술 |
|:---|:---|:---|
| 듀얼 스택 | 단말·서버·라우터가 IPv4와 IPv6를 모두 사용 | A/AAAA, Happy Eyeballs |
| 터널링 | IPv6 패킷을 IPv4망 위로 전달 | 6in4, GRE, ISATAP |
| 변환 | IPv4와 IPv6 주소·헤더를 중간에서 변환 | NAT64, DNS64, SIIT |
| 운영 기반 | DNS, 방화벽, 로그, 모니터링 정합성 유지 | IPAM, ACL, flow log |

> 요약: IPv6 전환은 연결 방식뿐 아니라 DNS, 라우팅, 보안 정책, 관측성을 함께 구성해야 한다.

---

## Ⅲ. 동작원리 및 흐름도

```text
전환 대상 식별
-> 애플리케이션 IPv6 호환성 확인
-> dual stack 우선 적용
-> 미지원 구간 tunneling 또는 translation 적용
-> DNS A/AAAA 조정
-> 지표 측정 후 IPv6 비중 확대
```

| 단계 | 처리 내용 | 검증 기준 |
|:---:|:---|:---|
| 1 | 서비스와 장비의 IPv6 지원 여부 조사 | OS, LB, Firewall, DB driver |
| 2 | 주소와 DNS 설계 | /48, /64, A/AAAA TTL 60~300초 |
| 3 | dual stack 또는 NAT64/DNS64 구성 | IPv4/IPv6 reachability |
| 4 | 보안·로그 정책 동기화 | IPv6 ACL, WAF, flow log |
| 5 | 트래픽 비중과 오류율 측정 | IPv6 traffic ratio, p95 latency, 5xx |

> 요약: IPv6 전환은 호환성 점검, 주소·DNS 설계, 전환 방식 적용, 보안 동기화, 지표 검증 순서로 수행한다.

## Ⅳ. 특징

| 구분 | 듀얼 스택 | 터널링 | 변환 |
|:---|:---|:---|:---|
| 적용 조건 | 양쪽이 IPv4/IPv6 지원 | 중간망이 IPv4만 지원 | 한쪽만 IPv6 또는 IPv4 지원 |
| 장점 | 프로토콜 원형 유지 | 기존 IPv4망 활용 | IPv6-only와 IPv4-only 연결 |
| 제약 | 운영 정책 2벌 관리 | MTU 감소, 캡슐화 오버헤드 | 주소·포트 변환 로그 필요 |
| 수치 포인트 | A/AAAA 동시 운영 | IPv4 header 20byte 추가 | NAT64 session, DNS64 TTL |

> 요약: 듀얼 스택은 표준 전환 방식, 터널링은 임시 연결, 변환은 이종 주소 체계 간 접속 보완에 적합하다.

## Ⅴ. 심화 비교 및 적용 판단

| 비교 축 | 듀얼 스택 | NAT64/DNS64 | 선택 기준 |
|:---|:---|:---|:---|
| 호환성 | IPv4·IPv6 모두 지원 필요 | IPv6-only 단말이 IPv4 서버 접속 | 신규 모바일·IoT는 NAT64 검토 |
| 운영 복잡도 | 보안·라우팅 정책 2벌 | 변환 장비와 로그 관리 | 운영 인력과 관측 도구 지원 확인 |
| 성능 지표 | 경로별 RTT 비교 | 변환 지연·세션 수 | p95 latency 300ms 이하 유지 |

> 요약: 전환 방식은 호환성, 운영 복잡도, p95 지연, 로그 추적 가능성을 기준으로 선택한다.

| 리스크 | 원인 | 대응 방안 | 확인 지표 |
|:---|:---|:---|:---|
| PMTU 실패 | 터널 캡슐화와 ICMP 차단 | MSS clamping, ICMPv6 Packet Too Big 허용 | PMTUD 실패 0건 |
| 보안 정책 누락 | IPv6 ACL 미구성 | IPv4/IPv6 rule parity 점검 | IPv6 rule hit count |
| DNS 경로 오류 | A/AAAA TTL·우선순위 불일치 | Happy Eyeballs, TTL 60~300초 | IPv6 접속 실패율 |

> 요약: 전환 리스크는 MTU, 보안 정책, DNS 응답 경로에서 집중 발생하므로 사전 점검이 필요하다.

| 점검 항목 | 목표 기준 | 측정 방법 |
|:---|:---|:---|
| 연결성 | IPv4/IPv6 reachability 99.9% 이상 | ping6, curl -6, synthetic test |
| 품질 | IPv6 p95 latency가 IPv4 대비 20% 이내 | APM, RUM |
| 보안·추적 | IPv6 flow log 100% 수집 | SIEM, firewall log |

> 요약: IPv6 전환 성공은 연결성, 지연, 로그 추적성 지표가 IPv4 운영 기준을 충족할 때 판단한다.

## Ⅵ. 실무 적용 및 결론

**적용 방안 3개:**
1. 단계 전환: 내부 관리망 dual stack, 외부 서비스 A/AAAA 동시 제공, IPv6 비중 10%->50%->100% 순서로 확대
2. 보안 동기화: IPv4 ACL과 IPv6 ACL rule parity 점검, RA Guard, NDP inspection, ICMPv6 허용 정책 반영
3. 품질 검증: curl -4/-6, tracepath6, p95 latency, 5xx, NAT64 session count를 배포 전후 비교

**결론 (2줄):**
- 기술사 판단: 신규 서비스는 dual stack을 기본으로 하고, IPv6-only 단말과 IPv4-only 서버 연동은 NAT64/DNS64를 선택함
- 향후 방향: IPv6-only 데이터센터와 클라우드 네이티브 네트워크 확산으로 전환 기술은 공존보다 IPv4 제거 단계로 이동함
