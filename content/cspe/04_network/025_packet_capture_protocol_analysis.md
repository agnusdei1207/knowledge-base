# 📖 【암기용】 개념 완전 이해

## 한눈에
- **개요**: 패킷 캡처·프로토콜 분석은 네트워크 인터페이스를 통과하는 **패킷을 복사·수집(Capture)**하고, OSI 7계층 구조에 맞춰 **역어셈블·해석(Analysis)**하는 기술임.
- **왜 필요한가**: "서버가 느리다"는 현상만으로는 원인(네트워크 지연 vs 서버 처리 지연)을 특정할 수 없음. 양단 간 패킷의 타임스탬프와 TCP 상태를 직접 확인해야 물증 기반 장애 원인 분리가 가능함.
- **핵심 직관**: 도로에 지나가는 차량을 블랙박스로 녹화(캡처)하고, 녹화 영상을 돌려보며 "이 차는 속도위반(지연)이고 저 차는 불법물품(공격)이네"라고 해석하는 과정임.

## 핵심 용어 정리

| 용어 | 의미 | 비유 |
|:---|:---|:---|
| **SPAN (Mirroring)** | 스위치 포트의 트래픽을 복사하여 분석 포트로 전송 (SW 방식) | 통화 녹음을 나중에 듣는 것 |
| **TAP (Test Access Point)** | 케이블 중간에 삽입하는 하드웨어 분배기 (HW 방식) | 수도관 중간에 설치하는 유량계 |
| **Promiscuous Mode** | 자신의 MAC이 아닌 프레임도 모두 수신하는 NIC 모드 | 옆 사람 편지도 다 열어보기 |
| **BPF (Berkeley Packet Filter)** | 커널 레벨에서 조건(IP·Port)에 맞는 패킷만 선별하는 고속 필터 | 우체국 자동 분류기 |
| **PCAP** | 캡처된 패킷의 타임스탬프·바이너리를 저장하는 표준 파일 포맷 | 블랙박스 녹화 파일 |
| **Dissector** | PCAP의 바이트 배열을 OSI 계층별 헤더로 파싱하는 엔진 | 영상 프레임 분석기 |

## 깊이 이해
- **수집 단계 (SPAN vs TAP)**: 
    - **SPAN**은 스위치 설정만으로 가능해 간편하지만, 트래픽이 몰리면 스위치 CPU 부하가 늘고 패킷이 누락(Drop)될 수 있음. 
    - **TAP**은 별도 장비 비용이 들지만 트래픽 100%를 무결하게 수집하므로, 법적 포렌식 증거나 10Gbps 이상 대용량 환경에서 필수임.
- **분석 단계 (지연 시간의 과학)**: 패킷 캡처 도구(Wireshark 등)에서 두 패킷 사이의 'Delta Time'을 보면 지연의 진범을 알 수 있음.
    - `SYN` → `SYN/ACK` 사이가 길면: 네트워크(RTT) 지연.
    - `GET` → `HTTP 200 OK` 사이가 길면: 서버(DB/App) 처리 지연.
- **고대역폭 환경의 도전 (DPDK/eBPF)**: 초당 수백만 패킷이 들어오는 환경에서는 커널과 유저 영역 간의 복사(Copy) 과정이 병목이 됨. 이를 해결하기 위해 커널을 우회하여 메모리를 직접 참조하는 **DPDK(Zero-copy)** 기술이 활용됨.

## 연결 개념
- **IDS/IPS (024)**: 분석 기술을 활용한 실시간 침입 대응.
- **Network KPI (091)**: 패킷 분석을 통해 도출하는 지연, 지터 등 지표.
- **Network Forensics (122)**: 캡처된 PCAP 파일을 증거물로 활용.

# 📝 【답안용】 시험 답안 템플릿

## 핵심 인사이트 (3줄 요약)

> 1. **본질**: 네트워크 트래픽을 TAP/SPAN으로 수집하고 OSI 계층별로 디코딩하여 통신 상태를 가시화하는 물증 기반 분석 기술임.
> 2. **가치**: 장애 원인 분리(Fault Isolation) 및 침해사고 포렌식에서 "움직일 수 없는 물증"을 제공하여 대응 정확도를 극대화함.
> 3. **판단 포인트**: 10G 이상의 고속 환경에서는 패킷 유실(Drop) 방지를 위한 TAP 수집과 DPDK/eBPF 기반의 고속 처리 아키텍처 설계가 필수임.

## Ⅰ. 개요 및 필요성
- **정의**: NIC을 통과하는 패킷을 캡처하여 프로토콜 헤더 및 페이로드를 계층별로 분석하는 기술.
- **필요성**:
    1. **장애 원인 규명**: 클라이언트 vs 서버 vs 네트워크 구간 중 병목 지점을 데이터로 증명.
    2. **보안 가시성**: 이상 징후 탐지 및 침해사고 시 공격 패킷 재구성(Replay).

## Ⅱ. 패킷 수집 및 분석 프로세스

### 1. 패킷 수집 방식 비교 (SPAN vs TAP)
```text
[SPAN 방식: Software Copy]             [TAP 방식: Hardware Splitter]
Switch --(Mirroring)--> Analyzer        Switch --(Cable)--> [TAP] --(Split)--> Analyzer
                                                             |
                                                       Direct Path (무손실)
```

| 구분 | SPAN (Port Mirroring) | TAP (Test Access Point) |
|:---|:---|:---|
| **원리** | 스위치 백플레인에서 복사 | 물리적 계층에서 신호 분리 |
| **장점** | 비용 저렴, 원격 설정 가능 | 100% 무손실 수집, L1 에러 탐지 가능 |
| **단점** | 트래픽 폭주 시 패킷 유실 발생 | 별도 장비 필요, 케이블 단절 리스크 |

### 2. 패킷 분석 파이프라인
1. **Capture**: NIC Promiscuous 모드를 통한 원본 트래픽 수집.
2. **Filtering**: BPF(Berkeley Packet Filter)를 통한 관심 패킷 선별.
3. **Storage**: PCAP/PCAPNG 포맷으로 타임스탬프와 함께 저장.
4. **Analysis**: Dissector를 활용한 헤더 파싱 및 흐름(Flow) 분석.

## Ⅲ. 고속 패킷 처리를 위한 핵심 기술
- **DPDK (Data Plane Development Kit)**: 커널 우회(Kernel Bypass) 및 Zero-copy를 통한 고속 처리.
- **eBPF (Extended BPF)**: 커널 내부 샌드박스에서 패킷을 직접 처리하여 유저 영역 복사 오버헤드 최소화.
- **RSS (Receive Side Scaling)**: 멀티 코어 CPU에 패킷 수신 처리를 분산하여 병목 해소.

## Ⅳ. 패킷 분석을 통한 장애 진단 시나리오
- **네트워크 지연**: TCP Handshake 구간의 RTT(Round Trip Time) 증가 확인.
- **서버 지연**: Application Request 후 첫 Response 패킷까지의 Delta Time 분석.
- **패킷 유실**: TCP Sequence Number 역전 및 중복 ACK, Retransmission 패킷 추적.

## Ⅴ. 암호화 트래픽(HTTPS) 분석의 한계와 대응
- **한계**: TLS 1.3 및 PFS(Perfect Forward Secrecy) 적용 시 패킷을 캡처해도 페이로드 확인 불가.
- **대응 전략**:
    1. **SSL VA (Visibility Appliance)**: 전용 장비를 통한 복호화 후 분석 장비 전달.
    2. **ETA (Encrypted Traffic Analytics)**: 암호화된 상태의 메타데이터(JA3 핑거프린트 등) 기반 AI 탐지.

## Ⅵ. 실무 적용 전략 및 결론
- **전략**: 장애 분석용은 기동성이 좋은 **SPAN**을 활용하고, 상시 관제 및 포렌식용은 신뢰도가 높은 **TAP** 구성을 원칙으로 함.
- **결론**: 패킷 분석은 클라우드 및 암호화 환경으로 변화함에 따라 원본 데이터 자체보다 '메타데이터의 상관분석'과 '가시성 확보 기술'의 결합이 더욱 중요해질 전망임.

| 유형 | Ⅱ·Ⅲ 강조 (기술 중심) | Ⅴ·Ⅵ 강조 (전략/아키텍처) |
|:---|:---|:---|
| **기술형** | TAP vs SPAN 기술적 차이 및 수집 원리 | DPDK를 활용한 무손실 수집 아키텍처 설계 |
| **사례형** | 패킷 분석을 통한 네트워크/서버 지연 진단 | 암호화 환경(TLS 1.3)에서의 가시성 확보 방안 |
