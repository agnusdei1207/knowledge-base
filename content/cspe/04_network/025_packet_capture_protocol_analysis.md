# 📖 【암기용】 개념 완전 이해

> 목적: 네트워크 트래픽을 가로채고 분석하는 일련의 과정을 완벽히 이해하게 만든다.

## 한눈에
- **개요**: 네트워크를 오가는 패킷을 수집(Capture)하고, 프로토콜 구조에 맞게 해독하여 분석(Analysis)하는 기술
- **왜 필요한가**: 통신 장애 원인 규명, 해킹 위협 탐지, 네트워크 성능 측정 등을 위해서는 케이블을 지나는 실제 데이터를 뜯어봐야 함
- **핵심 직관**: 도로에 지나가는 차들의 번호판과 트렁크 내용물을 비디오로 녹화하는 것이 '패킷 캡처'고, 녹화된 영상을 돌려보며 "저 차는 속도위반(성능 저하)이고 이 차는 불법물품(해킹)이네"라고 해석하는 것이 '프로토콜 분석'이다.

## 깊이 이해
- **배경·문제의식**: 네트워크 장애는 "서버가 느려요"라는 현상만 있지 원인(네트워크 지연인지, 서버 응답 지연인지, 재전송 때문인지)은 보이지 않는다. 이를 증명하려면 양단 간 오가는 패킷의 타임스탬프와 TCP 상태를 직접 확인해야 한다.
- **작동 원리**:
  - **수집 (Capture)**: 스위치의 포트 미러링(SPAN)이나 물리적 TAP 장비를 이용해 타겟 트래픽의 복사본을 분석기로 전달. OS 단에서는 promiscuous(무차별) 모드로 랜카드를 설정해 자신에게 오지 않은 패킷도 모두 수신.
  - **필터링 (BPF)**: 초당 수백만 개의 패킷 중 분석할 특정 IP/Port만 골라냄 (Berkeley Packet Filter 문법 사용).
  - **분석 (Analysis)**: Wireshark 등의 도구가 0과 1의 바이너리를 OSI 7계층 구조(Ethernet -> IP -> TCP -> HTTP)에 맞춰 사람이 읽을 수 있는 형태로 디코딩함.
- **비유**: 법정에서 증거를 찾기 위해 전화 통화를 도청(캡처)하고, 암호화된 은어를 경찰이 풀어 해석(분석)하는 과정.
- **구체 예시**: 서버 응답이 3초 걸릴 때, 패킷을 캡처해 보면 클라이언트가 SYN을 보냈으나 서버가 SYN-ACK를 3초 뒤에 보냈는지, 아니면 DB 쿼리 후 HTTP 200 OK를 3초 뒤에 보냈는지 명확히 책임 소재를 가릴 수 있다.
- **흔한 오해·주의점**: "패킷만 뜨면 모든 해킹을 다 볼 수 있다"고 생각하지만, 현대 트래픽은 90% 이상이 TLS 암호화되어 있다. 패킷 캡처만으로는 페이로드를 볼 수 없으며, 복호화 키 연동이나 메타데이터(헤더) 분석 기법이 병행되어야 한다.

## 연결 개념
- SPAN / TAP — 패킷 복사본을 만들어내는 스위치 기능 / 물리 장비
- BPF (Berkeley Packet Filter) — 커널 레벨에서 고속으로 패킷을 필터링하는 규칙
- Wireshark / tcpdump — 가장 대표적인 프로토콜 분석 GUI / CLI 도구

# 📝 【답안용】 시험 답안 템플릿

> 목적: 시험장에서 25분에 그대로 쓰는 답안 양식.

## 핵심 인사이트 (3줄 요약)

> 1. **본질**: 패킷 캡처 및 프로토콜 분석은 네트워크 구간의 트래픽을 TAP/SPAN으로 수집하고 디코딩하여 상태와 페이로드를 가시화하는 기술이다.
> 2. **가치**: 장애 원인 분리(Fault Isolation), 애플리케이션 지연(Latency) 분석, 사이버 위협 침해사고 조사(Forensics)에 움직일 수 없는 물증(Evidence)을 제공한다.
> 3. **판단 포인트**: 10Gbps 이상 환경에서는 패킷 유실(Drop) 없는 하드웨어 TAP 수집과, 커널을 우회하는 고속 패킷 처리(DPDK, eBPF) 아키텍처가 분석 신뢰도를 좌우한다.

## 출제 의도 및 답안 포인트

| 출제 의도 | 반드시 짚을 핵심 | 감점 회피 포인트 |
|:---|:---|:---|
| 트래픽 수집 방식의 구조적 이해 | Port Mirroring(SPAN)과 Network TAP의 아키텍처 및 부하 비교 | 수집 방법 없이 분석 툴(Wireshark) 사용법만 나열 |
| 고대역폭 환경에서의 성능 보장 | BPF 기반 커널 필터링, DPDK를 통한 Zero-copy 패킷 수집 | 패킷 유실(Drop) 시 분석 결과 오류 발생 위험 간과 |
| 보안 및 성능 분석 활용 역량 | 장애 지연 원인 판별(TCP Handshake 시간 분석), 암호화(TLS) 한계 극복 | "패킷을 보면 다 안다" 식의 추상적 만능론 |

> 요약: 패킷 분석 문제는 "어떻게 유실 없이 모을 것인가(수집)"와 "어떻게 빠르고 정확하게 해석할 것인가(분석)"의 두 축으로 서술해야 한다.

## Ⅰ. 개요 및 필요성

- 정의: 네트워크 인터페이스를 통과하는 패킷 복사본을 수집(Capture)하고, 계층별 프로토콜 구조에 맞춰 역어셈블 및 분석하는 기술
- 배경: 분산 시스템(MSA, Cloud) 환경에서 애플리케이션 로그만으로는 통신 지연 및 단절 원인 식별 한계
- 필요성: 네트워크 지연(RTT) 측정, TCP 재전송 및 혼잡 추적, 침해사고 시 포렌식 증거 확보를 위해 필수적

---

## Ⅱ. 구조 및 구성요소

```text
Target Network -> [수집부: TAP / SPAN] -> [필터부: BPF] -> [저장부: PCAP] -> [분석부: Protocol Dissector]
```

| 구성요소 | 역할 | 특이사항 |
|:---|:---|:---|
| 수집 (Capture) | 망에 흐르는 트래픽 복사본 생성 | SPAN(스위치 복사), TAP(물리적 분배) |
| 필터링 (BPF) | 조건(IP, Port 등)에 맞는 패킷만 선별 | 커널 레벨 처리로 CPU 부하 및 저장공간 절감 |
| 캡처 파일 (PCAP) | 수집된 패킷의 타임스탬프와 바이너리 덤프 포맷 | libpcap(Linux), Npcap(Windows) 표준 라이브러리 |
| 디섹터 (Dissector) | 바이너리 스트림을 OSI 7계층 구조로 파싱 | Wireshark 등에서 계층별 헤더 가시화 |

> 요약: 패킷 분석 시스템은 물리적 수집(TAP)부터 커널 필터링(BPF), 바이너리 저장(PCAP), 논리적 파싱(Dissector)의 파이프라인 구조를 갖는다.

---

## Ⅲ. 동작원리 및 흐름도

```text
NIC Promiscuous Mode -> 커널 버퍼 적재 -> BPF 필터 대조 -> 유효 패킷 User Space 복사 -> PCAP 저장 -> 디코딩 및 가시화
```

| 단계 | 처리 내용 | 검증 기준 |
|:---:|:---|:---|
| 1 | Promiscuous 모드 수신 및 TAP/SPAN 연동 | 본인 MAC이 아닌 프레임도 모두 수용 |
| 2 | BPF(Berkeley Packet Filter) 매칭 | 패킷 캡처 유실률(Drop rate) 0.1% 미만 |
| 3 | PCAP 포맷 저장 (바이너리 + 타임스탬프) | 마이크로초(us) 단위 타임스탬프 정밀도 |
| 4 | 계층별(L2~L7) 헤더 분리 및 페이로드 분석 | 프로토콜 명세서(RFC) 기반 필드 맵핑 정확도 |

> 요약: 수신된 패킷은 고성능 필터를 거쳐 저장되며, 디섹터는 수집된 바이트 배열을 RFC 규격에 맞춰 계층별 구조체로 디코딩한다.

## Ⅳ. 특징 (수집 방식 비교)

| 구분 | Port Mirroring (SPAN) | Network TAP (Test Access Point) | 판단 포인트 |
|:---|:---|:---|:---|
| 구현 방식 | 스위치 S/W 설정 (특정 포트 트래픽 복사) | 케이블 중간에 하드웨어 광/UTP 스플리터 삽입 | 구성의 용이성 vs 무결성 |
| 네트워크 부하 | 스위치 CPU 리소스 소모, 백플레인 병목 시 Drop 발생 | 스위치 부하 없음, 트래픽 유실 Zero (100% 무결성) | 10Gbps 이상 대용량 환경 |
| Layer 1 에러 | CRC 에러 프레임 등은 스위치에서 자체 폐기하여 수집 불가 | 케이블 상의 모든 물리적 에러 프레임까지 수집 가능 | 정밀 장애(L1/L2) 디버깅 여부 |

> 요약: 간편한 장애 확인은 SPAN을 쓰지만, 법적 증거 능력이 필요한 포렌식이나 대용량 트래픽 환경에서는 하드웨어 TAP이 필수적이다.

## Ⅴ. 심화 비교 및 적용 판단

| 비교 축 | 헤더 분석 (Header Analysis) | 심층 페이로드 분석 (DPI) | 선택 기준 |
|:---|:---|:---|:---|
| 분석 범위 | L3/L4 (IP, Port, TCP Flag, Sequence) | L7 (HTTP URI, SQL Query, 파일 추출) | 문제의 원인 위치 (네트워크 vs 애플리케이션) |
| 활용 목적 | RTT 측정, 라우팅 오류, 포트스캔 탐지 | XSS/SQLi 공격 탐지, 악성코드 추출 | 성능 병목 진단 vs 보안 침해 분석 |
| 제약 사항 | 암호화 트래픽에서도 메타데이터 확보 가능 | TLS 암호화 적용 시 복호화 키 확보 전까지 무력화 | TLS 1.3 적용 환경 여부 |

> 요약: 암호화가 보편화된 현재는 페이로드(DPI) 분석보다 타임스탬프와 TCP 헤더 시퀀스를 통한 통신 패턴(메타데이터) 분석의 중요성이 커졌다.

| 리스크 | 원인 | 대응 방안 | 확인 지표 |
|:---|:---|:---|:---|
| 대용량 캡처 시 패킷 유실 | 커널-유저스페이스 간 컨텍스트 스위칭 오버헤드 | DPDK, eBPF를 통한 커널 바이패스(Zero-copy) 적용 | 패킷 캡처 Drop Rate (OS 레벨) |
| 민감 정보 유출 | 패킷 덤프 내에 평문 비밀번호 및 PII 포함 | 캡처 시 페이로드 제외(헤더만 저장, snaplen 제한) | PCAP 파일 내 민감정보 평문 노출 여부 |
| 암호화 트래픽 가시성 상실 | TLS 1.3 기본 적용 및 PFS(완전 순방향 비밀성) | SSL VA(가시성 장비) 연동, 세션 키 외부 로깅(Keylog) | 전체 수집 패킷 중 평문 분석 가능 비율 |

> 요약: 고대역폭 환경의 캡처 유실은 분석 결과 왜곡(가짜 재전송 추론 등)을 낳으므로 DPDK 같은 커널 우회 기술 적용이 필수이다.

## Ⅵ. 실무 적용 및 결론

**적용 방안 3개:**
1. 장애 책임 분리(Fault Isolation): 서버 응답 지연 시, 패킷 캡처의 타임스탬프 델타(Delta) 값을 분석하여 '네트워크 왕복 시간(RTT)' 문제인지 'WAS/DB 처리 시간' 문제인지 명확히 증명
2. 무손실 수집 아키텍처: 10G 이상 코어망에 광 TAP 장비를 설치하고, 수집 서버에 DPDK 기반 패킷 캡처 엔진을 적용하여 유실률 0% 달성
3. 능동적 포렌식: 침해사고 발생 시 과거 트래픽 흐름(PCAP)을 재생(Replay)하여 악성코드 유입 경로 및 데이터 유출량(Exfiltration)을 바이트 단위로 증명

**결론 (2줄):**
- 기술사 판단: 패킷 분석은 인프라 장애와 보안 침해의 "가장 확실한 물증"이며, SPAN의 한계를 보완할 TAP과 DPDK 가속 아키텍처 설계가 성패를 좌우한다.
- 향후 방향: TLS 1.3 확산으로 페이로드 복호화가 어려워짐에 따라, JA3 (TLS 핑거프린팅) 등 암호화된 메타데이터 패턴만을 AI로 분석하는 방향으로 진화 중이다.
