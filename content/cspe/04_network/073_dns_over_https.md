## Ⅰ. 개요
| 항목 | 내용 |
|---|---|
| **정의** | 기존 평문 UDP 방식의 DNS 질의를 암호화된 HTTPS(포트 443) 연결을 통해 수행하는 보안 프로토콜 |
| **배경/필요성** | ISP나 해커의 DNS 스니핑을 통한 프라이버시 침해, 웹사이트 검열 및 DNS 위변조(Spoofing) 공격 방지 필요 |
| **출제 의도** | 보안성이 강화된 DoH의 동작 원리와 기존 DNS 체계와의 구조적 차이, 장단점 평가 |

## Ⅱ. 구성요소
```text
+----------+       +----------+       +----------+
|  Browser |       | TLS 1.3  |       | DoH DNS  |
| (Client) | <---> | (HTTPS)  | <---> | Resolver |
+----------+       +----------+       +----------+
```
| 구성요소 | 설명 | 비유 |
|---|---|---|
| 전통 DNS | 포트 53(UDP)을 사용하는 평문 질의로 빠르지만 스니핑 및 변조에 무방비함 | 투명 봉투 우편 |
| HTTPS 프로토콜 | 포트 443(TCP)을 사용하여 데이터 기밀성과 서버 무결성을 보장하는 통로 | 장갑차 수송 |
| DoH Resolver | 클라이언트의 HTTPS 기반 암호화 DNS 요청을 수신하여 안전하게 처리하는 서버 | 보안 철저한 안내소 |

> 요약: 웹 브라우저 트래픽(HTTPS)과 DNS 질의가 섞여 구분이 불가능해져 완벽한 프라이버시를 보장함

## Ⅲ. 절차
```text
+----------+    +----------+    +----------+    +----------+
| TLS 연결 | -> | DNS 질의 | -> | 암호화전송| -> | IP 응답  |
+----------+    +----------+    +----------+    +----------+
```
1. TLS 연결: 클라이언트(브라우저)와 DoH 리졸버 간 안전한 TLS 1.3 보안 세션 수립
2. DNS 질의: 사용자가 접속할 도메인 주소에 대한 IP 변환 요청(HTTP GET/POST) 생성
3. 암호화전송: 요청 정보를 HTTPS 페이로드로 암호화하여 중간자 스니핑을 무력화하며 전송
4. IP 응답: DoH 서버가 결과(IP)를 암호화하여 응답하고, 브라우저는 이를 복호화해 대상 접속

> 요약: HTTPS 보안 터널 위에서 HTTP API 형태로 DNS 질의와 응답을 안전하게 교환함

## Ⅳ. 문제점
- UDP 대신 무거운 TCP/TLS 핸드쉐이크 과정을 거쳐야 하므로 초기 도메인 해석 지연(Latency) 증가
- 기업 내 통합 보안 장비(방화벽/IPS)가 악성 도메인 접속 차단 및 모니터링을 수행할 수 없는 가시성 상실
- 웹 브라우저(Chrome/Firefox) 자체 설정 우선으로 동작해 기업의 사내 내부망 도메인(인트라넷) 해석 실패 현상 유발

## Ⅴ. 개선방안
- [단기] 엔터프라이즈 환경에서는 그룹 정책(GPO)으로 브라우저의 DoH 기능 임의 활성화 강제 차단
- [중기] 사내 전용 DoH 프록시 서버를 구축하여 보안 가시성 유지 및 안전한 외부 릴레이 라우팅 지원
- [장기] QUIC 기반의 DoQ(DNS over QUIC) 도입으로 TLS 연결 지연 완화 및 암호화 DNS 표준 체계 최적화

## Ⅵ. 전망
- 글로벌 빅테크 주도로 기본 활성화 추세이며, 프라이버시 보호의 핵심 인프라로 자리매김할 전망임
