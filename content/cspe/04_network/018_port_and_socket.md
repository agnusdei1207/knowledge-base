## Ⅰ. 개요
- **정의**: 포트 번호는 시스템 내 여러 서비스를 식별하며, 소켓은 통신을 위해 제공되는 운영체제 API임.
- **배경 및 필요성**: IP를 통해 호스트를 찾은 뒤, 내부에서 동작 중인 특정 프로세스(웹, 메일 등)로의 데이터 역다중화 목적.
- **출제 의도**: L4 전송 계층의 논리적 식별자 구조와 애플리케이션 개발 시 네트워크 통신 인터페이스 구조 파악

## Ⅱ. 구성요소

```text
+-------------------------+
|  Component Architecture |
+-------------------------+
| [ Node A ] <-> [ Node B]|
+-------------------------+
```

| 구성요소 | 설명 | 비유 |
|---|---|---|
| **포트 (Port)** | 0~65535로 구성된 특정 프로세스 접근을 위한 논리적 채널 | 아파트 동/호수 뒤의 특정 방 번호 |
| **Well-known 포트** | HTTP(80), DNS(53) 등 IANA 예약 0~1023 사이 서비스 번호 | 관공서, 경찰서 등의 대표 전화번호 |
| **소켓 (Socket)** | 프로세스가 네트워크로 데이터를 입출력하는 커널 통신 접점 | 통신 케이블을 꽂는 소프트웨어 플러그 |

> 요약: 포트는 특정 서비스를 구분하는 주소이며, 소켓은 IP와 포트를 결합한 프로그래밍 통신 객체임.

## Ⅲ. 절차

```text
+-------+   +-------+   +-------+   +-------+
| Step1 |-->| Step2 |-->| Step3 |-->| Step4 |
+-------+   +-------+   +-------+   +-------+
```

1. **[서버 준비] 소켓 생성/바인드**: 서버 프로세스가 소켓을 만들고 특정 포트 번호에 결합함.
2. **[서버 대기] 리슨/억셉트**: 클라이언트의 연결 요청 수용을 대기하며 접속 시 별도 전담 소켓을 만듦.
3. **[클라이언트 연결] 동적 할당**: 클라이언트 OS가 임시 포트(49152~)를 할당받아 서버 포트로 접속함.
4. **[양방향 통신] 데이터 교환/종료**: 연결된 소켓 쌍 간에 스트림 통신 수행 후 자원을 해제함.

> 요약: 서버는 고정 포트에 소켓을 열고, 클라이언트는 임시 포트로 접속하여 상호 통신 파이프라인을 구축함.

## Ⅳ. 문제점
- 임시(Ephemeral) 포트 고갈 (원인: 대량 아웃바운드 연결 시 클라이언트가 쓸 수 있는 약 1.6만 개 포트 소진)
- 좀비 프로세스 포트 점유 (원인: 비정상 종료 시 소켓이 닫히지 않아 동일 포트 재할당 시 Bind Error 발생)
- 동기 소켓의 블로킹 병목 (원인: 통신 시 데이터를 기다리며 단일 스레드가 완전히 멈춰 서버 성능 저하)

## Ⅴ. 개선방안
- **단기 방안**: [단기] 커널 파라미터 튜닝 (임시 포트 범위를 최대화하고 TIME_WAIT 소켓 빠른 재사용 옵션 적용)
- **중기 방안**: [중기] 로드 밸런싱 아키텍처 도입 (단일 서버의 포트 제약을 극복하기 위해 트래픽을 다중 백엔드 팜으로 분산)
- **장기 방안**: [장기] 비동기(Asynchronous) 소켓 I/O 적용 (epoll 등 이벤트 루프 아키텍처(Node.js, Nginx)로 대규모 병렬 소켓 처리)

## Ⅵ. 전망
- 전통적 소켓 API는 컨테이너 및 서비스 메시 기반의 추상화된 프록시 통신 구조로 진화하고 있음.
