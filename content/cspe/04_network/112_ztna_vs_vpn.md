## 미리 알고가기

- ZTNA는 사용자의 신원과 기기 상태를 확인한 뒤 허가된 애플리케이션만 연결하는 제로트러스트 접속 방식임
- VPN은 사용자를 사설망 안으로 들여보내는 암호화 터널 방식임
- 애플리케이션 단위 접근은 필요한 서비스만 열어 주는 방식임
- 기기 상태 평가는 단말 보안 설정과 패치 수준을 확인하는 절차임

## Ⅰ. 개요

- **정의/개념**: ZTNA와 VPN 비교는 원격 접속을 네트워크 전체 터널로 열 것인지, 사용자와 기기 조건을 본 뒤 애플리케이션 단위로 제한할 것인지 판단하는 접근 통제 비교임
- **배경/필요성**: 원격 근무와 클라우드 사용이 늘면서 내부망 전체를 열어 주는 방식은 과도한 노출을 만들 수 있으므로, 접속 범위와 검증 수준을 다시 나눠 볼 필요가 커짐

## Ⅱ. 특징

- VPN은 연결 범위가 넓고 익숙하지만 사용자에게 내부망 일부를 직접 노출하기 쉬움
- ZTNA는 사용자와 기기 상태를 함께 보고 필요한 애플리케이션만 연결함
- VPN은 네트워크 중심 관리에, ZTNA는 서비스 중심 권한 통제에 더 잘 맞음
- 혼합 환경에서는 두 방식을 병행하되 대상 업무를 구분해야 운영이 깔끔함

## Ⅲ. 종류 및 비교

| 판단 기준 | VPN | ZTNA |
|:---|:---|:---|
| 접속 범위 | 터널 안에서 내부망 여러 자원에 닿기 쉬움 | 허가된 애플리케이션만 열어 줌 |
| 신뢰 방식 | 접속 후 내부 이동 통제가 느슨해질 수 있음 | 접속 전후로 신원과 기기 상태를 계속 확인함 |
| 배치 위치 | 게이트웨이 중심의 네트워크 접속 구조임 | 프록시나 커넥터 중심의 서비스 접속 구조임 |
| 적합 환경 | 지사 연결과 레거시 프로토콜에 적합함 | 하이브리드 근무와 SaaS·내부 웹앱 보호에 적합함 |

## Ⅳ. 구성요소 및 구조

| 구성요소 | 설명 |
|:---|:---|
| 사용자 단말 | 원격 접속을 시작하는 주체임 |
| VPN 게이트웨이 | 네트워크 터널을 열고 라우팅을 연결함 |
| ZTNA 브로커 | 사용자와 기기 상태를 확인한 뒤 필요한 앱만 중개함 |
| 인증 체계 | 계정과 인증서와 다중 인증을 처리함 |
| 내부 애플리케이션 | 최종 접근 대상 서비스임 |

```text
VPN  : [사용자] -> [VPN 게이트웨이] -> [내부망]
ZTNA : [사용자] -> [ZTNA 브로커] -> [허가된 애플리케이션]
```

## Ⅴ. 원리 및 절차 흐름도

```text
[사용자 요청] -> [신원·기기 확인] -> [접속 방식 결정] -> [자원 연결] -> [세션 감시]
```

1. **사용자 요청**: 원격 사용자가 업무 시스템 접속을 시도함
2. **신원·기기 확인**: 계정과 기기 상태와 위치 같은 조건을 점검함
3. **접속 방식 결정**: 광범위한 네트워크 연결인지, 앱 단위 연결인지 선택함
4. **자원 연결**: VPN은 터널을 열고 ZTNA는 허가된 서비스만 중개함
5. **세션 감시**: 접속 중 이상 행위를 기록하고 차단함

## Ⅵ. 실무 적용 및 유의점

1. 레거시 업무나 지사 간 연결은 VPN이 빠르게 적용되지만 내부망 노출 범위가 넓어지기 쉬우므로 네트워크 분할과 다중 인증과 접속 후 권한 통제를 함께 두고 세션별 접근 범위와 비인가 이동 시도를 같이 확인함
2. 하이브리드 근무와 내부 웹 서비스는 ZTNA가 더 잘 맞지만 애플리케이션 식별과 정책 매핑이 부정확하면 업무가 막히므로 서비스 목록 정리와 기기 상태 검사를 함께 운영하고 사용자 접속 성공률과 우회 시도와 정책 오탐 건수를 봐야 함

## Ⅶ. 결론

ZTNA와 VPN의 선택 기준은 암호화 자체가 아니라 사용자가 어디까지 들어가야 하는지와 그 범위를 얼마나 세밀하게 통제할지에 있음.
