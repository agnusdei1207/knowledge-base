# 📖 【암기용】 개념 완전 이해

> 목적: ZTNA와 VPN의 차이를 네트워크 접속과 애플리케이션 접속의 관점으로 이해하게 만든다.

## 한눈에
- **개요**: VPN은 사설망 터널을 열고, ZTNA는 사용자가 허가받은 애플리케이션만 프록시로 연결한다.
- **왜 필요한가**: VPN은 접속 후 내부망 대역이 보이는 구조가 많아 계정 탈취 시 내부 이동 위험이 생긴다.
- **핵심 직관**: VPN은 건물 출입증을 주는 방식이고, ZTNA는 회의실마다 예약자 명단을 확인하는 방식이다.

## 깊이 이해
- **배경·문제의식**: 클라우드, SaaS, 재택 환경에서는 내부망과 외부망 경계가 약해져 네트워크 위치만으로 신뢰를 판단하기 어렵다.
- **작동 원리**: ZTNA는 IdP, 단말 상태, 사용자 역할, 위치, 위험 점수를 평가한 뒤 애플리케이션별 커넥터와 프록시를 통해 세션을 중계한다.
- **비유**: VPN은 회사 정문을 통과하면 여러 층에 갈 수 있는 출입증이고, ZTNA는 특정 회의실 문마다 담당자가 다시 확인하는 출입 절차다.
- **구체 예시**: 개발자는 Git과 Jira만, 재무 담당자는 ERP만 접근하도록 정책을 만들면 계정 탈취 시 접근 가능한 자산 수를 줄일 수 있다.
- **흔한 오해·주의점**: ZTNA가 모든 VPN을 즉시 대체하지 않는다. 네트워크 레벨 라우팅, 레거시 프로토콜, 지사 간 연결은 VPN이 필요한 경우가 있다.

## 연결 개념
- SDP - ZTNA의 선행 개념으로 리소스를 숨기고 허가 세션만 개방
- SASE/SSE - ZTNA를 SWG, CASB, DLP와 통합 제공
- VPN - 망 단위 터널로 ZTNA 전환 대상과 공존 가능

# 📝 【답안용】 시험 답안 템플릿

> 목적: 비교 답안은 "어느 기술이 우위"가 아니라 접속 범위, 통제 단위, 운영 조건을 기준으로 선택한다.
> 핵심: VPN은 네트워크 터널, ZTNA는 애플리케이션 단위 정책 집행이라는 차이를 명확히 쓴다.

## 핵심 인사이트 (3줄 요약)

> 1. **본질**: VPN은 네트워크 접속을 제공하고, ZTNA는 신원·단말·상황 기반으로 애플리케이션 세션을 허가한다.
> 2. **가치**: ZTNA는 노출 표면을 애플리케이션 단위로 축소하고, VPN은 지사·관리망 등 L3 연결에 적합하다.
> 3. **판단 포인트**: 레거시 L3 통신, per-app 접근, 사용자 경험, 로그 증적을 함께 비교해야 한다.

## 출제 의도 및 답안 포인트

| 출제 의도 | 반드시 짚을 핵심 | 감점 회피 포인트 |
|:---|:---|:---|
| 원격접속 패러다임 비교 확인 | 망 단위 터널 vs 앱 단위 접근 | ZTNA를 단순 VPN 제품으로 설명 |
| 제로트러스트 적용 판단 확인 | IdP, MFA, 단말 상태, 정책 엔진 | "신뢰하지 않음" 구호만 쓰고 통제 절차 누락 |
| 전환 전략 수립 확인 | 공존, 단계적 앱 전환, 로그 통합 | VPN 전면 폐기처럼 단정 |

> 요약: 이 문제는 VPN 대체 여부보다 업무 자산별 접속 단위와 정책 집행 위치를 판단하는 문제이다.

### 🔑 핵심 용어 정리

| 용어 | 뜻 | 비유 |
|:---|:---|:---|
| **VPN** | 공용 네트워크 위에 암호화된 사설 터널을 구축하는 기술 | "비밀 터널" |
| **터널링** | 패킷을 다른 프로토콜로 캡슐화하여 전송 | "편지를 큰 봉투에 넣기" |
| **IPsec** | IP 계층 암호화·인증 프로토콜 스위트 | "IP 보안 외투" |

## Ⅰ. 개요 및 필요성

- 개요: VPN은 망 접속, ZTNA는 앱 접속
- 배경: 재택·SaaS·멀티클라우드 확산으로 사내망 위치만으로 신뢰를 부여하기 어려움.
- 필요성: 계정 탈취 후 내부망 스캔을 줄이기 위해 사용자·단말·앱 단위 인가가 필요함.
- 판단 기준: L3 라우팅 요구는 VPN, 업무 앱 접근은 ZTNA를 우선 검토함.

---

## Ⅱ. 구조 및 구성요소

```text
VPN: User -> VPN Tunnel -> Internal Network -> Multiple Resources
ZTNA: User -> IdP/MFA -> Policy Engine -> ZTNA Broker -> Approved App
                         +-> Device Posture -> Log/SIEM
```

| 구성요소 | VPN | ZTNA |
|:---|:---|:---|
| 접속 단위 | 서브넷, 라우팅 대역 | 애플리케이션, API, 사용자 세션 |
| 신뢰 판단 | 터널 인증 후 네트워크 접근 | 요청마다 신원·단말·위험 점수 확인 |
| 중계 위치 | VPN 게이트웨이 | Broker, Connector, Reverse Proxy |
| 로그 단위 | 접속 시작·종료, IP 대역 | 앱, 사용자, 단말, 정책 결과 |
| 통합 요소 | 방화벽, NAC, SIEM | IdP, EDR, CASB, SWG |

> 요약: VPN은 터널이 중심이고, ZTNA는 정책 엔진과 브로커가 애플리케이션 세션을 중계한다.

---

## Ⅲ. 동작원리 및 흐름도

```text
접속 요청 -> 신원 확인 -> 단말 상태 확인 -> 정책 평가
-> VPN이면 터널 라우팅 -> 내부망 접근
-> ZTNA이면 앱 커넥터 중계 -> 허가 앱 세션 생성 -> 로그 기록
```

| 단계 | 처리 내용 | 검증 기준 |
|:---:|:---|:---|
| 1 | 사용자가 업무 자원 접근을 요청 | IdP 계정, MFA, 조건부 접근 |
| 2 | 단말 보안 상태와 위치를 확인 | EDR 동작, OS 패치, 국가·ASN |
| 3 | 정책 엔진이 접근 대상을 결정 | 사용자 역할, 앱 중요도, 시간대 |
| 4 | VPN은 터널 라우팅을 생성 | 허용 대역, DNS, Split tunnel |
| 5 | ZTNA는 앱 프록시 세션을 생성 | 세션 단위 로그, 정책 결과 |

> 요약: VPN은 인증 후 네트워크 경로를 만들고, ZTNA는 매 요청의 조건을 평가해 특정 애플리케이션 세션만 허가한다.

---

## Ⅳ. 특징

| 구분 | VPN | ZTNA | 수치·기술 포인트 |
|:---|:---|:---|:---|
| 보호 범위 | 터널 구간 암호화 | 앱별 접근 제어 | per-app tunnel, ZTNA policy |
| 공격면 | 게이트웨이와 내부 대역 노출 | 비허가 앱 비노출 | Connector outbound-only 구성 |
| 사용자 경험 | 클라이언트 접속 후 라우팅 | 브라우저·에이전트 기반 앱 접속 | SSO, MFA, device posture |
| 운영 한계 | Full tunnel 병목 | 레거시 프로토콜 제약 | SMB, VoIP, 고정 L3 앱 검토 |

> 요약: ZTNA는 앱 단위 통제에 적합하고, VPN은 네트워크 레벨 연결이 필요한 업무에 남긴다.

## Ⅴ. 심화 비교 및 적용 판단

| 구분 | VPN 유지 | ZTNA 전환 | 선택 기준 |
|:---|:---|:---|:---|
| 업무 유형 | 지사, 운영망, L3 라우팅 | 웹·SaaS·업무 포털 | 프로토콜과 접속 범위 |
| 보안 통제 | 터널 인증, ACL | IdP, 단말 상태, 정책 엔진 | 사용자별 최소 권한 필요성 |
| 운영 비용 | 게이트웨이 증설, 라이선스 | PoP 구독, 앱 온보딩 | 동시 접속 수와 앱 수 |
| 로그 품질 | IP·세션 중심 | 사용자·앱·정책 결과 중심 | 감사 요구 수준 |

> 요약: 앱 수가 명확하고 사용자별 권한 차이가 클수록 ZTNA 전환 효과가 커진다.

| 리스크 | 원인 | 대응 방안 | 확인 지표 |
|:---|:---|:---|:---|
| 레거시 업무 중단 | ZTNA가 L3 프로토콜을 지원하지 않음 | VPN 공존, 앱별 전환 목록 작성 | 미전환 앱 수, 장애 티켓 |
| 정책 과다 허용 | 사용자 그룹과 앱 권한 매핑 오류 | RBAC, ABAC, 정기 권한 리뷰 | 과다 권한 계정 수 |
| 사용자 불편 | MFA 반복, 세션 재인증 | 위험 기반 인증, 세션 TTL 조정 | 인증 실패율, 헬프데스크 건수 |
| 로그 분산 | VPN·ZTNA 로그 포맷 차이 | SIEM 정규화, 공통 사용자 ID | 상관분석 성공률 |

> 요약: 전환 리스크는 기술 미지원, 권한 설계, 인증 경험, 로그 통합에서 발생한다.

| 점검 항목 | 목표 기준 | 측정 방법 |
|:---|:---|:---|
| 접근 범위 | 사용자별 허가 앱 목록 100% 문서화 | CMDB, ZTNA 정책 추출 |
| 탐지 지표 | 비정상 접근 MTTD 10분 이하 | SIEM correlation, UEBA |
| 운영 지표 | VPN 동시 세션 30% 이상 감소 | VPN 게이트웨이 로그 |
| 사용자 지표 | 인증 실패율 3% 이하 | IdP 로그, 서비스데스크 분석 |

> 요약: ZTNA 전환은 VPN 사용량 감소, 앱 권한 가시화, 탐지 지표 개선으로 판단한다.

## Ⅵ. 실무 적용 및 결론

**적용 방안 3개 (필수):**
1. VPN 접속 로그를 분석해 웹·SaaS·업무 포털은 ZTNA 앱으로 전환하고, 운영망·백업망은 VPN 예외 목록에 남김.
2. IdP, MFA, EDR 상태, 사용자 그룹을 ZTNA policy에 연결하고, 앱별 Connector를 아웃바운드 방식으로 배치함.
3. VPN과 ZTNA 로그를 SIEM 사용자 ID 기준으로 정규화하고, 계정 탈취 탐지 규칙을 공통으로 적용함.

**결론 (2줄):**
- 기술사 판단: 내부망 전체 접근이 필요하면 VPN, 업무 애플리케이션 접근이면 ZTNA를 적용하고 공존 기간을 둠.
- 향후 방향: 원격접속은 VPN 단독 구조에서 ZTNA, SASE, SSE와 결합된 신원 중심 접근 구조로 이동함.

| 유형 | 문제 신호어 | Ⅲ 강조 | Ⅳ 강조 |
|:---|:---|:---|:---|
| 포괄형 | "ZTNA와 VPN을 설명하시오" | 접속 요청부터 정책 평가까지 흐름 | 접속 단위와 통제 위치 차이 |
| 요구사항 명시형 | "비교하고 전환 방안을 제시하시오" | 공존 절차와 앱 온보딩 흐름 | 선택 기준, 리스크, 지표 |

> 요약: 비교형은 구조 차이를 먼저 보이고, 방안형은 어떤 업무를 언제 전환할지 판단 기준을 제시한다.
