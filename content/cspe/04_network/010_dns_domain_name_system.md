## 미리 알고가기

- DNS: 도메인 이름과 IP 주소, 메일 서버, 권한 서버 정보를 매핑하는 분산 이름 시스템임
- 재귀 질의: 클라이언트가 리졸버에게 최종 응답을 대신 찾아 달라고 요청하는 방식임
- 반복 질의: 리졸버가 Root, TLD, 권한 서버를 차례로 물어보며 답을 찾는 방식임
- TTL: DNS 응답을 캐시에 유지할 수 있는 시간 값임
- DNSSEC: DNS 응답의 출처와 무결성을 전자서명으로 검증하는 확장임

## Ⅰ. 개요

- **정의/개념**: DNS는 사람이 쓰는 도메인 이름을 IP 주소와 서비스 레코드로 해석하기 위해 계층형 위임과 캐싱을 사용하는 분산 데이터베이스임
- **배경/필요성**: 모든 호스트 이름과 주소를 중앙 파일로 관리하면 갱신 병목과 단일 장애점이 생기므로 권한을 계층별로 위임하는 이름 해석 구조가 필요함

## Ⅱ. 특징

- Root, TLD, Authoritative 서버가 계층적으로 권한을 위임함
- Local Resolver는 반복 질의로 답을 찾고 TTL 동안 캐시해 반복 질의를 줄임
- 레코드 유형에 따라 주소, 별칭, 메일 서버, 권한 서버 같은 정보를 구분함
- 캐시 오염과 평문 질의 노출을 줄이려면 DNSSEC, DoT, DoH 적용 범위를 정해야 함

## Ⅲ. 종류 및 비교

| 판단 기준 | 재귀 질의 | 반복 질의 |
|:---|:---|:---|
| 요청 주체 | 클라이언트가 리졸버에 최종 답을 요청함 | 리졸버가 상위 서버부터 차례로 질의함 |
| 응답 형태 | 리졸버가 최종 레코드나 오류를 돌려줌 | 각 서버가 다음에 물어볼 권한 서버 정보를 돌려줌 |
| 사용 구간 | 단말과 Local DNS 사이에서 주로 쓰임 | Local DNS와 Root, TLD, 권한 서버 사이에서 주로 쓰임 |
| 운영 쟁점 | 오픈 리졸버 남용과 캐시 정책을 통제해야 함 | 위임 정보와 권한 서버 가용성을 확인해야 함 |

> 요약: 재귀 질의는 최종 답을 맡기는 방식이고, 반복 질의는 권한 위임을 따라 답을 찾아가는 방식임

## Ⅳ. 구성요소 및 구조

| 구성요소 | 설명 |
|:---|:---|
| Root Server | 최상위 위임 정보를 제공해 TLD 서버를 찾게 함 |
| TLD Server | `.com`, `.kr` 같은 상위 도메인의 권한 서버 정보를 알려 줌 |
| Authoritative Server | 특정 도메인의 실제 레코드를 보유하고 권한 있는 응답을 제공함 |
| Resolver Cache | TTL 동안 응답을 저장해 지연과 상위 질의를 줄임 |
| Resource Record | A, AAAA, CNAME, MX, NS, TXT처럼 목적별 정보를 표현함 |

```text
+--------+    recursive    +----------+    iterative    +------+    +-----+    +------+
| Client | --------------> | Resolver | --------------> | Root | -> | TLD | -> | Auth |
+--------+                 +----------+                 +------+    +-----+    +------+
```

> 요약: DNS는 클라이언트가 리졸버에 맡기고 리졸버가 계층형 위임을 따라 권한 서버 답을 찾는 구조임

## Ⅴ. 원리 및 절차 흐름도

```text
+----------+     +----------+     +----------+     +----------+
| 질의수신  | --> | 위임추적  | --> | 레코드응답 | --> | 캐시저장 |
+----------+     +----------+     +----------+     +----------+
```

1. **질의수신**: 클라이언트가 도메인 이름과 레코드 유형을 리졸버에 요청함
2. **위임추적**: 리졸버가 캐시에 없으면 Root, TLD, 권한 서버 순서로 질의함
3. **레코드응답**: 권한 서버가 요청한 레코드나 오류 응답을 반환함
4. **캐시저장**: 리졸버가 TTL 범위에서 응답을 저장하고 클라이언트에 전달함

## Ⅵ. 실무 적용 및 유의점

1. 서비스 이전 시 TTL을 미리 낮추지 않으면 캐시된 예전 IP로 접속이 남을 수 있으므로 변경 전후 TTL, 권한 서버 응답, 실제 접속 IP 분포를 확인함
2. 공용 리졸버 운영에서는 캐시 포이즈닝과 증폭 공격을 줄여야 하므로 재귀 허용 범위를 제한하고 DNSSEC 검증 실패율과 비정상 질의량으로 확인함

## Ⅶ. 결론

DNS는 단순 주소 변환이 아니라 위임, 질의 절차, 캐시 시간을 조정해 서비스 도달성을 관리하는 분산 이름 시스템임.

## 작성 근거(검토용)

- DNS의 판단 축은 단순 주소 치환이 아니라 계층형 위임과 캐싱이므로 구조와 절차를 그 기준으로 재작성함
- 서비스 도달성은 TTL과 권한 서버 응답 확인이라는 운영 판단으로 바꿈
- 결론은 주소 변환을 넘어 도달성 관리라는 기술사 답안 축을 회수함
