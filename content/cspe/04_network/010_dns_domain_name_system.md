# 📖 【암기용】 개념 완전 이해

## 한눈에
- **개요**: DNS는 사람이 읽는 도메인 이름(www.naver.com)을 기계가 쓰는 IP 주소(004 참조)로 바꿔 주는 계층적 분산 이름 해석(Resolution) 시스템임.
- **왜 필요한가**: 사람은 32비트(IPv4)·128비트(IPv6) 숫자 주소를 외울 수 없고, 서버 IP는 수시로 바뀌므로, 기억하기 쉬운 이름과 실제 주소를 분리해 매핑하는 계층이 필요함.
- **핵심 직관**: 전화번호부와 같음. '홍길동'(도메인)만 알면 번호부(DNS)가 '010-1234-5678'(IP)를 찾아 주고, 번호가 바뀌어도 이름은 그대로 씀.

## 핵심 용어 정리 (내부에 등장하는 것들)
아래 용어는 답안(Ⅰ~Ⅵ·표)에 나오는 것들을 미리 풀어 둔 것임. 최상위 키워드는 **계층적 이름 해석(Recursive+Iterative)**임.

| 용어/표기 | 의미 | 비유·예 |
|:---|:---|:---|
| FQDN | 루트(.)까지 포함한 절대 도메인명 `www.naver.com.` | 국가·시·구까지 다 쓴 전체 주소 |
| Resolution | 도메인명을 IP로 해석하는 과정 | 이름으로 전화번호 찾기 |
| Root DNS | 트리 최상위 `.` 관리 서버(전 세계 13개 논리 서버) | 전국 번호부 총본부 |
| TLD DNS | `.com`·`.kr` 등 최상위 도메인 관리 | 지역(시) 번호부 |
| Authoritative DNS | 특정 도메인의 실제 레코드를 보유한 정답 서버 | 그 사람 번호를 확정 보유한 지점 |
| Local DNS(Resolver) | 단말 대신 질의를 수행·캐싱하는 서버(ISP·8.8.8.8) | 대신 찾아 주는 안내원 |
| Recursive Query | "최종 IP를 무조건 찾아 달라"는 위임형 질의 | 안내원에게 통째로 맡김 |
| Iterative Query | "다음은 저기로 가라"는 힌트만 받는 반복 질의 | 한 곳씩 물어 좁혀 감 |
| A / AAAA | 도메인→IPv4 / IPv6 매핑 레코드 | 집전화 / 휴대폰 번호 |
| CNAME | 도메인의 별칭(정식 이름으로 연결) | 별명→본명 연결 |
| MX | 메일 수신 서버를 지정하는 레코드 | 우편물 담당 창구 |
| TTL | 캐시 유지 시간(초), 만료 시 재질의 | 메모의 유효기간 |
| Delegation | 하위 도메인 관리 권한을 아래 서버로 위임 | 본부→지점에 권한 넘김 |
| DNSSEC | 레코드에 전자서명(RRSIG)해 위변조 검증 | 번호부에 위조 방지 봉인 |
| DoH/DoT | DNS 질의를 HTTPS(443)/TLS로 암호화 | 안내 통화를 도청 불가로 |
| GSLB | 위치·상태 기반으로 최적 IP를 응답하는 광역 부하분산 | 가장 가까운 지점 번호 안내 |

## 깊이 이해
- **배경·문제의식**: 초기 인터넷(ARPANET)은 `hosts.txt` 한 파일에 모든 이름-IP를 적어 공유했으나, 노드가 수백만으로 늘자 동기화·병목이 한계에 달해 분산 계층 구조인 DNS가 등장함.
- **작동 원리(어떻게+왜)**: 역트리(Inverted Tree) 구조로, 단말은 Local DNS에 재귀적으로 통째로 맡기고, Local DNS는 Root→TLD→Authoritative를 반복적으로 추적함. 각 상위 서버는 답 대신 "다음 서버 위치"만 위임(Delegation)해 Root 부하를 최소화함. 결과는 TTL 동안 캐싱해 재질의를 줄임.
- **비유**: 시골 우체국(Local DNS)이 모르는 주소를 본청(Root)에 물으면 "서울시(TLD)로 가봐", 서울시가 "강남구(Authoritative)로 가봐"라며 차례로 좁혀 주는 과정임.
- **구체 예시**: 브라우저에 `google.com`을 입력하면 PC는 로컬 캐시→OS 캐시→Local DNS(8.8.8.8) 순으로 조회하고, 없으면 Root·TLD·Auth를 거쳐 IP(142.250.x.x)를 받아 접속함.
- **흔한 오해·주의점**: DNS 서버 1대가 전 세계 주소를 다 아는 게 아님. 철저한 위임으로 분산 관리하며, IP를 바꿔도 TTL만큼 옛 IP가 캐시에 남아 전파 지연(Propagation Delay)이 생김.

## 연결 개념
- IP 주소 체계 (004 참조) — DNS가 최종적으로 반환하는 대상이 A(IPv4)·AAAA(IPv6) 주소임.
- CDN·GSLB (134 참조) — DNS 응답을 사용자 위치별로 다르게 주어 글로벌 트래픽을 분산하는 응용.
- DoH/DoT (138 참조) — 평문 UDP 53 질의의 감청·조작을 막는 DNS 암호화 프로토콜.

# 📝 【답안용】 시험 답안 템플릿

## 핵심 인사이트 (3줄 요약)

> 1. **본질**: DNS는 사람이 식별하는 도메인명(FQDN)과 기계가 식별하는 IP를 상호 변환하는 분산 계층형 이름 서비스 아키텍처임.
> 2. **가치**: 계층적 위임과 캐싱으로 SPOF 없이 수십억 기기의 질의를 수 ms 내 분산 처리하며, GSLB·CDN 라우팅의 근간이 됨.
> 3. **판단**: 평문 UDP 53 전송으로 Cache Poisoning·감청에 취약하므로, DNSSEC(무결성)과 DoH/DoT(기밀성)를 설계에 포함해야 함.

## 출제 의도 및 답안 포인트

| 출제 의도 | 반드시 짚을 핵심 | 감점 회피 포인트 |
|:---|:---|:---|
| 계층 구조·분산 원리 | Root→TLD→Authoritative의 위임(Delegation) 구조 | DNS 1대가 모두 처리하는 중앙집중식으로 서술 |
| 질의 해석 과정 | 재귀적(Recursive)·반복적(Iterative) 질의 결합 | 단말~Local DNS 구간과 외부망 구간 차이 누락 |
| 보안·가용성 실무 | DNSSEC·DoH/DoT 방어와 GSLB 연계 | 이름 변환 역할만 쓰고 보안·분산 통제 누락 |

> 요약: DNS는 '계층 분산'과 '캐싱'을 재귀·반복 질의 흐름으로 증명하고, GSLB와 DNSSEC로 결론지어야 함.

---

## Ⅰ. 개요 및 필요성

- 정의: 도메인명(FQDN)과 IP를 매핑해 전 세계에 분산 제공하는 계층형 이름 해석 시스템임.
- 배경: 단일 `hosts` 파일 관리는 노드 급증 시 동기화 실패·병목(SPOF)을 유발함.
- 필요성: 계층적 위임과 캐싱으로 어디서든 수 ms 내 IP를 해석하고 트래픽을 분산함.

---

## Ⅱ. 구조 및 구성요소

구조도(선형):

```text
Local DNS(Resolver) -> Root DNS(. 최상위, 13개 논리서버/Anycast)
  Root -> .com TLD 위치 반환 -> Local DNS -> TLD DNS(.com/.kr)
  TLD -> naver.com Auth 위치 반환 -> Local DNS -> Authoritative DNS
  Auth -> 최종 IP(A/AAAA) 반환 -> Local DNS(TTL 캐싱) -> PC
```

| 구성요소 | 역할 | 특징 |
|:---|:---|:---|
| Root DNS | 도메인 트리 최상위 `.` 관리 | 13개(A~M) 논리 서버, Anycast로 증설 |
| TLD DNS | `.com`·국가코드 등 관리 | 하위 Auth 서버 위치를 위임 |
| Authoritative DNS | 도메인의 실제 레코드 최종 보유 | 해당 도메인의 '권한 있는' 정답 제공 |
| Local DNS(Resolver) | 단말 대신 질의·캐싱 | ISP·8.8.8.8, 재귀 질의 수행 |

> 요약: 권한을 하위로 철저히 위임해 Root 부하를 최소화하는 극단적 분산 아키텍처임.

---

## Ⅲ. 동작원리 및 흐름도

흐름도(선형):

```text
PC -> (재귀 질의) -> Local DNS
  Local DNS -> (반복 질의) -> Root -> .com TLD 위치
  Local DNS -> (반복 질의) -> TLD -> naver Auth 위치
  Local DNS -> (반복 질의) -> Auth -> 최종 IP -> Local DNS(캐싱) -> PC
```

- 1단계: PC가 Local DNS에 "최종 IP를 찾아 달라"고 재귀적(Recursive)으로 위임함.
- 2단계: Local DNS가 Root에 질의하면 Root가 답 대신 `.com` TLD 서버 위치를 힌트로 반환함.
- 3단계: Local DNS가 TLD에 질의하면 TLD가 `naver.com` Authoritative 서버 위치를 반환함.
- 4단계: Local DNS가 Auth에 질의해 최종 IP를 받고 TTL 동안 캐싱한 뒤 PC에 전달함.

> 요약: 단말은 Local DNS에 재귀로 떠넘기고, Local DNS는 상위부터 반복적으로 추적해 IP를 캐싱함.

---

## Ⅳ. 특징

- 계층적 위임: Root→TLD→Auth로 권한을 분산해 단일 서버 부하와 SPOF를 제거하나, 위임 경로가 길어 초기 질의는 여러 홉을 거침.
- 캐싱 계층화: 단말→OS→Local DNS 순 캐시로 질의 속도를 단축하되, 변경 IP는 TTL만큼 전파 지연이 발생함.
- 레코드 확장성: A(IPv4)·AAAA(IPv6)·CNAME(별칭)·MX(메일)·TXT(SPF 등 인증)로 이름 해석 외 소유권·메일 보안까지 지원함.
- UDP 53 기반: 핸드셰이크 없이 빠르게 질의응답하나, 응답이 512바이트 초과·Zone Transfer 시에는 TCP 53을 사용함.

## Ⅴ. 심화 비교 및 적용 판단

| 구분 | 재귀적 질의(Recursive) | 반복적 질의(Iterative) |
|:---|:---|:---|
| 요청 주체 | 단말 → Local DNS | Local DNS → Root·TLD·Auth |
| 응답 방식 | 최종 IP를 대신 끝까지 찾아 반환 | 다음 서버 위치 힌트만 반환 |
| 부하 위치 | Local DNS에 처리 집중 | 상위 서버 부하 분산 |
| 캐싱 효과 | Local DNS가 결과를 캐싱해 재사용 | 위임 경로마다 참조용 힌트 캐싱 |

> 요약: 단말~Local DNS 구간은 재귀로 편의를 제공하고, 외부망 구간은 반복으로 상위 서버 부하를 분산하는 이원 구조임.

리스크·대응(불릿):
- Cache Poisoning — 정답 도착 전 해커가 가짜 IP 응답을 먼저 주입 — DNSSEC 서명(RRSIG)으로 무결성 검증.
- 감청·차단 — 평문 UDP 53 질의 노출 — DoH(443)·DoT로 질의 암호화.
- DNS Amplification DDoS — 출발지 위조 대량 질의로 증폭 공격 — Anycast 증설·Response Rate Limiting 적용.

---

## Ⅵ. 실무 적용 및 결론

**적용 방안 3개:**
1. **GSLB 트래픽 분산**: Route53 Latency-based Routing으로 미국 사용자는 US 리전 IP, 한국 사용자는 AP 리전 IP를 동적 응답해 체감 지연을 최소화.
2. **사내 Private DNS**: Route53 Resolver로 온프레미스·VPC 간 사설 도메인을 조건부 포워딩(Conditional Forwarding)해 내부 이름 해석을 격리.
3. **DNSSEC 무결성 검증**: 금융권 도메인에 RRSIG 서명을 적용해 Cache Poisoning과 파밍 유도를 원천 차단.

**결론(2줄):**
- 기술사 판단: 소규모 단일 도메인이면 ISP DNS 위임으로 충분하나, 글로벌 서비스면 GSLB 분산과 DNSSEC·DoH 방어를 함께 설계해야 함.
- 향후 방향: 브라우저의 DoH 기본 활성화로 방화벽의 DNS 기반 유해사이트 차단이 무력화되어, 기업 DNS 통제 아키텍처의 재설계가 필요함.
