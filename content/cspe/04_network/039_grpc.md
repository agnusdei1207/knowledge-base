## Ⅰ. 개요
- **정의**: 구글이 개발한 오픈소스 고성능 원격 프로시저 호출(RPC) 프레임워크로, HTTP/2를 전송 계층으로 하고 Protocol Buffers를 직렬화 포맷으로 사용함.
- **배경/필요성**: 기존 REST/JSON 방식의 파싱 오버헤드, 대용량 트래픽 및 양방향 스트리밍 처리에 대한 한계 극복.
- **출제 의도**: gRPC의 동작 원리, IDL(Protocol Buffers)의 구조적 장점, HTTP/2 기반 특성 및 마이크로서비스 간 통신 최적화 방안 이해.

## Ⅱ. 구성요소
```text
+-----------------------+       +-----------------------+
|     gRPC Client       |       |      gRPC Server      |
|  [ Client Stub ]      |------>|   [ Server Skeleton ] |
|  (Proto Generated)    |<------|   (Proto Generated)   |
+-----------------------+ HTTP/2+-----------------------+
     (Protocol Buffers)            (Protocol Buffers)
```
| 구성요소 | 설명 | 비유 |
|---|---|---|
| Protocol Buffers | 인터페이스 정의 언어(IDL)이자 이진(Binary) 데이터 직렬화 메커니즘 | 통역용 표준 기호 |
| Client Stub | 로컬 함수를 호출하듯 서버 기능을 호출할 수 있게 해주는 클라이언트 측 대리자 | 현지 대리인 |
| HTTP/2 Channel | 멀티플렉싱, 양방향 스트리밍, 헤더 압축을 지원하는 기저 전송 프로토콜 | 고속도로 전용차선 |
> 요약: 프로토콜 버퍼로 정의된 스펙을 양방향 HTTP/2 채널을 통해 빠르고 가볍게 주고받는 구조임.

## Ⅲ. 절차
```text
+-----------+   +-------------+   +-------------+   +-----------+
| IDL 작성  |-> | Stub/코드생성|->| 이진 직렬화 |-> | RPC 호출  |
+-----------+   +-------------+   +-------------+   +-----------+
```
1. **IDL 작성**: `.proto` 파일에 주고받을 메시지 구조와 서비스 인터페이스를 언어 독립적으로 정의함.
2. **코드 생성**: 프로토콜 버퍼 컴파일러(protoc)를 사용하여 클라이언트 및 서버용 뼈대 코드(Stub/Skeleton)를 자동 생성함.
3. **이진 직렬화**: 클라이언트가 생성된 Stub 메서드를 호출하면, 데이터가 빠르고 작은 크기의 이진 포맷으로 직렬화됨.
4. **RPC 호출**: HTTP/2 기반의 단일 TCP 연결을 통해 메시지가 서버로 전송되고, 역직렬화 후 비즈니스 로직이 실행됨.
> 요약: 설계도(IDL)를 기반으로 코드를 자동 생성하고 바이너리로 데이터를 주고받아 통신 효율을 극대화함.

## Ⅳ. 문제점
- **웹 브라우저 지원 한계**: 브라우저가 HTTP/2 프레임 제어를 완벽히 노출하지 않아 직접 호출이 불가능함(gRPC-Web 프록시 필요).
- **디버깅 어려움**: 데이터가 이진 포맷(Binary)으로 암호화/압축되므로 사람이 패킷을 직접 읽고 문제 원인을 파악하기 힘듦.
- **로드밸런싱 제약**: HTTP/2의 지속 연결(Persistent Connection) 특성 상 L4(TCP) 로드밸런서에서는 트래픽 분산이 제대로 안 됨(L7 필요).

## Ⅴ. 개선방안
- **접근성 향상**: 프론트엔드 연동을 위해 gRPC-Web 패키지 사용 또는 Envoy 프록시를 통한 트랜스코딩 적용 (단기).
- **디버깅 체계 구축**: gRPC UI, 분산 추적 시스템(Jaeger, Zipkin) 등 가시성 및 트러블슈팅 도구 적극 연동 (중기).
- **클라이언트 로드밸런싱**: xDS API를 활용한 서비스 디스커버리 및 클라이언트 측 지능형 로드밸런싱 아키텍처 도입 (장기).

## Ⅵ. 전망
- 마이크로서비스 내부(East-West) 통신의 사실상 표준으로 자리 잡으며 REST/JSON을 빠르게 대체 중임.
- MSA 아키텍처 고도화 시 인프라(Service Mesh)와의 원활한 결합을 통해 클라우드 네이티브 네트워크의 핵심으로 확고히 남을 것임.
