## Ⅰ. 개요
- **정의**: 호스트 주소가 아닌 콘텐츠 이름으로 데이터를 요청·전달하는 네트워크 아키텍처임
- **배경/필요성**: IP 기반 호스트 중심 구조에서는 동일 콘텐츠를 중복 전송하여 대역폭이 낭비됨
- **비유**: 도서관에서 책 이름만 말하면 가장 가까운 서가에서 꺼내주는 구조와 유사함

| 출제 의도 | 반드시 짚을 핵심 | 감점 회피 포인트 |
|:---|:---|:---|
| IP 중심 대비 ICN 패러다임 변화 | Interest/Data 패킷 교환 구조 | NDN·CCN 등 구체 구현체 구분 필요 |

> 요약: 콘텐츠 이름 기반 요청·전달로 IP 호스트 중심의 중복 전송 문제를 해소하는 아키텍처임

## Ⅱ. 구성요소
```text
Consumer --> Interest 패킷 --> [라우터: CS/PIT/FIB] --> Producer 또는 캐시
                                     |
                              Data 패킷 반환 (역경로)
```

| 구성요소 | 설명 | 비유 |
|:---|:---|:---|
| CS(Content Store) | 라우터 내 콘텐츠 캐시 저장소 | 도서관 서가 |
| PIT(Pending Interest Table) | 미응답 Interest의 유입 인터페이스를 기록 | 대출 예약 목록 |
| FIB(Forwarding Info Base) | 콘텐츠 이름 접두사별 전달 경로 테이블 | 서가 위치 안내 색인 |
| Interest/Data 패킷 | 콘텐츠 요청과 응답을 담는 두 가지 패킷 유형 | 대출 신청서와 반환 도서 |

> 요약: CS·PIT·FIB 구조와 Interest/Data 패킷이 이름 기반 전달의 핵심임

## Ⅲ. 절차
```text
Interest 발행 --> CS 캐시 조회 --> PIT/FIB 전달 --> Data 역경로 반환
```
- 1단계: Consumer가 콘텐츠 이름을 포함한 Interest 패킷을 발행함
- 2단계: 라우터가 CS에서 해당 콘텐츠를 조회하여 캐시 히트 시 즉시 반환함
- 3단계: 캐시 미스 시 PIT에 기록 후 FIB 경로에 따라 Interest를 상위로 전달함
- 4단계: Producer 또는 캐시 보유 노드가 Data 패킷을 Interest 역경로로 반환함

> 요약: Interest 발행·캐시 조회·전달·역경로 반환의 4단계로 콘텐츠를 전달함

## Ⅳ. 문제점
- 라우터 부하: 패킷별 이름 조회·캐시 관리 — 고속 라우터에서 처리 지연 발생
- 이름 공간 관리: 계층적 이름의 글로벌 고유성 보장 — 기존 DNS 대비 관리 복잡도 증가
- 보안 모델 변경: 채널이 아닌 콘텐츠 단위 보안 — 기존 TLS 체계와 호환 불가

> 요약: 라우터 부하·이름 공간 관리·보안 모델 변경이 ICN의 주요 과제임

## Ⅴ. 개선방안
1. 단기: 블룸필터 기반 이름 조회 가속으로 라우터 처리 지연 감소
2. 중기: 분산 이름 등록 체계(DNRS) 도입으로 글로벌 이름 공간 관리 표준화
3. 장기: 콘텐츠 서명·접근제어 통합 보안 프레임워크로 TLS 대체 체계 구축

> 요약: 조회 가속·이름 등록 표준화·콘텐츠 보안 프레임워크로 단계적 개선이 필요함

## Ⅵ. 전망
- 발전 방향: IoT·엣지 컴퓨팅 환경에서 콘텐츠 캐싱 효율 극대화 영역으로 확장
- 기술사적 판단: 전면 대체보다 CDN·IoT 등 특정 도메인에서 IP 보완재로 공존할 것으로 판단됨
- 기술사 제언: IETF 표준화 참여와 기존 IP 인프라와의 점진적 통합 전략 수립이 필요함
