## 미리 알고가기

- Intent는 운영자가 원하는 목표 상태를 정책 수준으로 표현한 의도임
- Assurance는 실제 네트워크 상태가 의도와 맞는지 지속적으로 검증하는 기능임
- Telemetry는 장비와 트래픽 상태를 실시간에 가깝게 수집하는 데이터임
- Remediation은 의도와 실제 상태 차이를 줄이기 위한 수정 조치임

## Ⅰ. 개요

- **정의/개념**: Intent-Based Networking은 운영자가 비즈니스 의도와 목표 상태를 입력하면 시스템이 이를 장비 설정으로 변환하고 실제 상태를 지속 검증해 수정까지 반복하는 폐루프 네트워크 운영 방식임
- **배경/필요성**: 자동화만으로는 원하는 결과가 보장되지 않고 설정 편차가 누적될 수 있으므로, 대규모 정책 환경에서는 의도와 실제 결과를 계속 비교하는 운영 구조가 필요함

## Ⅱ. 특징

- 장비 명령이 아니라 목표 상태를 입력 단위로 사용해 운영 추상화를 높임
- 정책 변환, 배포, 검증, 수정이 하나의 폐루프로 연결됨
- Telemetry와 Assurance를 바탕으로 구성 편류와 SLA 위반을 빠르게 찾기 좋음
- 의도 모델이 불명확하거나 자동 수정 범위가 과도하면 오히려 대형 장애를 키울 수 있음

## Ⅲ. 종류 및 비교

| 판단 기준 | 일반 네트워크 자동화 | Intent-Based Networking |
|:---|:---|:---|
| 입력 단위 | 플레이북, 템플릿, 장비 설정 명령이 중심임 | 비즈니스 의도와 목표 정책이 중심임 |
| 검증 방식 | 작업 후 별도 검증 절차에 의존하기 쉬움 | 원하는 상태와 실제 상태를 지속적으로 비교함 |
| 운영 흐름 | 배포 자동화에 초점이 강함 | 배포 뒤 Assurance와 Remediation까지 포함함 |
| 적용 난도 | 자동화 범위가 좁으면 비교적 단순함 | 의도 모델과 검증 체계를 함께 설계해야 하므로 난도가 높음 |

> 요약: IBN은 자동화의 상위 개념으로, 배포 이후의 의도 검증과 수정 루프까지 포함함.

## Ⅳ. 구성요소 및 구조

| 구성요소 | 설명 |
|:---|:---|
| Intent 모델 | 접근 정책, 세그먼트, 성능 목표를 사람이 이해할 수준으로 표현하는 계층임 |
| 정책 변환 엔진 | 의도를 VLAN, ACL, QoS, 라우팅 설정으로 바꾸는 해석 계층임 |
| 자동화 컨트롤러 | 변환된 정책을 장비와 컨트롤러에 실제로 배포하는 실행 계층임 |
| Telemetry 수집 | 플로우, 지연 시간, 경로, 오류 상태를 계속 수집하는 관측 계층임 |
| Assurance·Remediation | 의도와 실제 상태의 차이를 분석하고 수정 조치를 수행하는 폐루프 계층임 |

```text
+-------------+     +----------------+     +----------------+     +----------------+
| Intent 입력    | --> | 정책 변환 엔진     | --> | 자동화 컨트롤러    | --> | Telemetry·Assurance |
+-------------+     +----------------+     +----------------+     +----------------+
                                                               |
                                                               v
                                                         Remediation
```

## Ⅴ. 원리 및 절차 흐름도

```text
+-------------+     +----------------+     +------------------+     +----------------+
| 의도 정의      | --> | 정책 변환·배포     | --> | 상태 수집·비교      | --> | 수정·재검증       |
+-------------+     +----------------+     +------------------+     +----------------+
```

1. **의도 정의**: 서비스 접근 범위와 성능 목표를 사람이 이해할 수 있는 형태로 입력함
2. **정책 변환과 배포**: 시스템이 의도를 장비별 정책과 설정으로 변환해 배포함
3. **상태 수집과 비교**: 텔레메트리 데이터를 모아 실제 상태가 의도와 일치하는지 확인함
4. **수정과 재검증**: 위반이 있으면 권고 또는 자동 수정 후 다시 검증함

## Ⅵ. 실무 적용 및 유의점

1. 캠퍼스망과 데이터센터처럼 정책 수가 많고 변경이 잦은 환경에서는 IBN이 유리하지만 Telemetry 범위가 부족하면 의도 검증이 형식화되므로 수집 지표와 정책 모델을 먼저 표준화하고 정책 준수율과 위반 복구 시간을 기준으로 확인함
2. 자동 수정까지 허용하는 환경에서는 잘못된 의도 해석이 장애를 넓힐 수 있으므로 고위험 변경은 승인 절차를 남기고 시뮬레이션을 먼저 수행하며 자동 수정 실패율과 오탐 경보 건수로 확인함

## Ⅶ. 결론

IBN의 본질은 네트워크 운영을 설정 배포 중심에서 의도 검증 중심으로 바꾸는 데 있으므로 Telemetry와 Assurance 없이는 완성될 수 없음.
