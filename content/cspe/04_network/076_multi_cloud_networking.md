## Ⅰ. 개요
- **정의**: 복수 CSP의 VPC/VNet을 통합 연결·관리하는 네트워크 아키텍처임
- **배경/필요성**: 벤더 종속 회피·서비스 최적 배치를 위해 복수 CSP를 동시 사용하므로 통합 네트워크가 필요함
- **비유**: 여러 항공사 노선을 하나의 예약 시스템으로 통합 관리하는 것과 유사함

| 출제 의도 | 반드시 짚을 핵심 | 감점 회피 포인트 |
|:---|:---|:---|
| CSP 간 네트워크 통합 설계 | 추상화 계층과 통합 정책 관리 | 단순 VPN 연결과 MCN 아키텍처의 차이 명시 필요 |

> 요약: 복수 CSP의 가상 네트워크를 추상화하여 통합 연결·정책 관리하는 아키텍처임

## Ⅱ. 구성요소
```text
CSP-A VPC ---+                        +--- App-A
             +-- MCN Controller ---+
CSP-B VNet --+   (Abstraction)     +--- App-B
             +-- Transit GW Pool --+
CSP-C VPC ---+                        +--- App-C
```

| 구성요소 | 설명 | 비유 |
|:---|:---|:---|
| MCN Controller | CSP별 네트워크를 추상화하고 통합 정책을 배포하는 제어 평면임 | 통합 예약 시스템 |
| Transit Gateway Pool | CSP 간 트래픽을 중계하는 게이트웨이 허브 집합임 | 환승 터미널 |
| 통합 정책 엔진 | 보안·라우팅 정책을 CSP 독립적으로 정의·배포하는 엔진임 | 공통 운항 규정 |

> 요약: 컨트롤러-트랜짓 GW-통합 정책으로 CSP 간 네트워크를 통합함

## Ⅲ. 절차
```text
Step1 Abstract --> Step2 Connect --> Step3 Policy --> Step4 Observe
```
- 1단계: 각 CSP의 VPC/VNet을 MCN 컨트롤러에 등록하여 추상화함
- 2단계: Transit Gateway 또는 Interconnect(075 참조)로 CSP 간 데이터 플레인을 연결함
- 3단계: 통합 정책 엔진에서 라우팅·보안·QoS 정책을 CSP별로 변환·배포함
- 4단계: 통합 대시보드에서 CSP 간 트래픽·지연·장애를 모니터링함

> 요약: 추상화-연결-정책배포-관측 순서로 멀티 클라우드 네트워크를 구성함

## Ⅳ. 문제점
- IP 충돌: CSP별 독립 CIDR 설계로 VPC 간 IP 대역이 중복될 수 있음
- 정책 불일치: CSP별 보안 그룹·방화벽 모델 차이로 통합 정책 변환 시 의미 손실이 발생함
- 지연 증가: CSP 간 트래픽이 공용 인터넷 또는 원격 PoP를 경유하면 RTT가 증가함

> 요약: IP 충돌, 정책 불일치, CSP 간 지연이 핵심 과제임

## Ⅴ. 개선방안
1. 단기: IPAM(IP Address Management) 도구로 전체 CSP CIDR을 중앙 관리하여 충돌을 방지함
2. 중기: 정책 추상화 DSL을 정의하여 CSP별 변환 정확도를 향상함
3. 장기: CSP 간 직접 Interconnect·Edge PoP 확충으로 CSP 간 지연을 최소화함

> 요약: IPAM, 정책 DSL, 직접 연결로 멀티 클라우드 네트워크를 최적화함

## Ⅵ. 전망
- 발전 방향: CSP 네이티브 MCN 서비스 확대로 별도 어플라이언스 없이 통합이 가능해짐
- 기술사적 판단: 하이브리드·멀티 클라우드가 기본 전략이 되면서 MCN 설계 역량이 필수화됨
- 기술사 제언: CSP 간 데이터 주권·규제 차이를 반영한 네트워크 아키텍처 설계 기준 수립이 필요함
