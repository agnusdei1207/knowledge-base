# 📖 【암기용】 개념 완전 이해

> 목적: 분산 클라우드 네트워킹을 처음 보는 사람도 멀티클라우드와 엣지 연결 문제를 이해하게 만든다. 시험 답안 양식이 아니라, 이해를 위한 설명이다.

## 한눈에
- **개요**: 중앙 클라우드, 리전, 엣지, 온프레미스를 일관된 네트워크 정책과 연결성으로 묶는 구조이다.
- **왜 필요한가**: 워크로드가 여러 클라우드와 엣지에 흩어지면 라우팅, 보안정책, DNS, 관측성이 제각각 운영된다.
- **핵심 직관**: 여러 지점에 흩어진 사무실을 하나의 주소 체계, 출입정책, 관제 화면으로 운영하는 방식이다.

## 깊이 이해
- **배경·문제의식**: 기업은 AWS, Azure, GCP, 온프레미스, CDN 엣지, 통신사 MEC를 함께 쓴다. 각 환경의 VPC/VNet, 방화벽, 로드밸런서, DNS가 다르면 애플리케이션 이동과 장애 대응이 느려진다.
- **작동 원리**: 글로벌 컨트롤 플레인이 네트워크 의도와 정책을 관리하고, 각 클라우드·엣지에 데이터 플레인 게이트웨이를 배치한다. 서비스 간 트래픽은 overlay, service mesh, SD-WAN, API gateway를 통해 정책 기반으로 전달된다.
- **비유**: 여러 국가 지사를 운영하면서 본사 규정은 하나로 유지하고, 현지 사무실 출입 장치만 지역에 맞게 설치하는 구조와 같다.
- **구체 예시**: 제조사는 공장 MEC에서 영상 분석을 수행하고 중앙 클라우드에서 모델 학습을 수행하며, 분산 클라우드 네트워킹으로 공장별 정책과 로그를 중앙에서 관리한다.
- **흔한 오해·주의점**: 멀티클라우드 회선을 연결하면 끝나는 문제가 아니다. IP 충돌, egress 비용, 데이터 주권, 정책 일관성, 관측성까지 설계해야 한다.

## 연결 개념
- SD-WAN — 분산 사이트와 클라우드 경로를 정책 기반으로 제어
- Service Mesh — 서비스 간 통신 보안과 관측성 제공
- Edge Computing — 지연과 데이터 주권 요구로 워크로드를 사용자 가까이에 배치

# 📝 【답안용】 시험 답안 템플릿

> 목적: 시험장에서 25분에 그대로 쓰는 답안 양식. control plane, data plane, overlay, policy, observability, data residency를 중심으로 작성한다.
> 핵심: 출제자는 멀티클라우드 연결보다 정책 일관성, 경로 최적화, 보안·운영 통제를 확인한다.

## 핵심 인사이트 (3줄 요약)

> 1. **본질**: 분산 클라우드 네트워킹은 중앙 클라우드, 엣지, 온프레미스를 일관된 연결성·보안정책·관측성으로 묶는 네트워크 운영 구조이다.
> 2. **가치**: 워크로드 위치가 바뀌어도 서비스 접근, 암호화, 라우팅, 로그 수집 정책을 동일하게 적용한다.
> 3. **판단 포인트**: IP 충돌, egress 비용, 지연 p95, 데이터 주권, 정책 drift를 함께 관리해야 한다.

## 출제 의도 및 답안 포인트

| 출제 의도 | 반드시 짚을 핵심 | 감점 회피 포인트 |
|:---|:---|:---|
| 분산 클라우드 구조 이해 확인 | control plane, data plane, edge gateway, overlay | 단순 VPN 연결로 축소 설명 |
| 운영 판단 확인 | 정책 일관성, 경로 선택, 관측성, 비용 | 클라우드별 방화벽 규칙 나열에 그침 |
| 전망 기술 한계 확인 | 데이터 주권, 벤더 종속, 장애 전파 | 확정 표준처럼 단정하거나 규제 조건 누락 |

> 요약: 이 문제는 연결성보다 분산 환경 전체를 하나의 정책과 지표로 운영하는 설계 능력을 묻는다.

## Ⅰ. 개요 및 필요성

- 개요: 여러 클라우드·엣지를 단일 정책망으로 연결함.
- 배경: 앱과 데이터가 리전, 엣지, 온프레미스에 분산되면 경로·보안·DNS·로그 정책이 분리됨.
- 필요성: 지연 p95, egress 비용, 데이터 주권, 장애 격리를 기준으로 워크로드별 최적 경로가 필요함.
- 판단 기준: 정책 drift 0건, p95 지연 목표, egress 비용, 데이터 위치 규정을 확인함.

---

## Ⅱ. 구조 및 구성요소

```text
Global Control Plane -> Policy / Routing / Identity / Observability
Cloud Region Gateway -> Overlay Network -> Edge Gateway -> On-Prem Gateway
Application Service -> Service Mesh / API Gateway -> User / Device
```

| 구성요소 | 역할 | 특이사항 |
|:---|:---|:---|
| 글로벌 컨트롤 플레인 | 정책, 라우팅, 인증, 배포 상태 관리 | IaC, GitOps 연계 |
| 데이터 플레인 게이트웨이 | 클라우드·엣지·온프레미스 트래픽 전달 | overlay, VPN, SD-WAN |
| 정책 엔진 | 접근통제와 암호화 정책 적용 | mTLS, RBAC, segmentation |
| 관측성 계층 | 로그, 메트릭, 트레이스 통합 | SLO, p95 지연, packet loss |
| 비용·규제 관리 | egress와 데이터 위치 점검 | FinOps, data residency |

> 요약: 분산 클라우드 네트워킹은 컨트롤 플레인으로 정책을 통합하고 각 위치의 게이트웨이가 트래픽을 처리한다.

---

## Ⅲ. 동작원리 및 흐름도

```text
워크로드 배치 요구 -> 정책·규제 확인 -> 경로·보안정책 생성
-> 게이트웨이 배포 -> 트래픽 전달 -> 지연·비용·보안 로그 검증 -> 정책 보정
```

| 단계 | 처리 내용 | 검증 기준 |
|:---:|:---|:---|
| 1 | 서비스 요구와 데이터 위치 조건 식별 | latency, residency, SLA |
| 2 | 컨트롤 플레인이 라우팅·보안 정책 생성 | policy diff, approval |
| 3 | 클라우드·엣지 게이트웨이에 정책 배포 | 배포 성공률, config drift |
| 4 | overlay 또는 SD-WAN 경로로 트래픽 전달 | p95 지연, packet loss |
| 5 | 로그·비용·규제 지표로 보정 | egress cost, audit log |

> 요약: 분산 클라우드 네트워킹은 요구사항을 정책으로 변환하고, 위치별 게이트웨이에 배포한 뒤 지연·비용·규제를 검증한다.

## Ⅳ. 특징

| 구분 | 단일 클라우드 네트워크 | 분산 클라우드 네트워킹 | 수치·표준 포인트 |
|:---|:---|:---|:---|
| 범위 | VPC/VNet 내부 중심 | 멀티클라우드·엣지·온프레미스 | overlay, SD-WAN |
| 정책 | 클라우드별 개별 설정 | 중앙 정책과 지역 실행 | RBAC, mTLS, GitOps |
| 경로 | 리전 내부 최적화 | 위치·비용·지연 기반 선택 | p95 latency, egress cost |
| 한계 | 구조 단순 | 정책 drift와 벤더 종속 | drift count, audit |

> 요약: 분산 클라우드는 연결 범위를 넓히는 대신 정책 drift, 비용, 규제 통제를 핵심 운영 과제로 만든다.

## Ⅴ. 심화 비교 및 적용 판단

| 구분 | 기존/대안 | 분산 클라우드 네트워킹 | 선택 기준 |
|:---|:---|:---|:---|
| 구조 | 사이트 간 VPN 개별 연결 | 중앙 정책 + 위치별 게이트웨이 | 클라우드 2개 이상, 엣지 10개 이상 |
| 비용/성능 | 회선·egress 수동 관리 | 경로·비용 정책 기반 제어 | egress 월 비용과 지연 목표 동시 관리 |
| 운영/위험 | 환경별 운영팀 분리 | 단일 관측성과 정책 감사 | 규제 감사와 장애 대응 필요 시 |

> 요약: 분산 클라우드 네트워킹은 단순 연결보다 정책, 비용, 규제를 한 화면에서 통제해야 할 때 적합하다.

| 리스크 | 원인 | 대응 방안 | 확인 지표 |
|:---|:---|:---|:---|
| 정책 불일치 | 클라우드별 수동 설정 | GitOps, policy-as-code | drift count |
| 비용 급증 | 지역 간 egress 증가 | traffic locality, FinOps 태그 | egress cost per service |
| 규제 위반 | 데이터 위치 미준수 | residency rule, geo-fencing | 감사 위반 0건 |

> 요약: 분산 환경 리스크는 정책 코드화, 트래픽 지역성, 데이터 위치 규칙으로 통제한다.

| 점검 항목 | 목표 기준 | 측정 방법 |
|:---|:---|:---|
| 네트워크 품질 | 서비스별 p95 지연 목표 충족 | synthetic probe, APM |
| 정책 통제 | 정책 drift 0건 | IaC 상태 비교 |
| 비용 관리 | egress 예산 초과 0건 | FinOps 리포트 |

> 요약: 성공 여부는 지연, 정책 일관성, egress 비용을 서비스 단위로 측정해 판단한다.

## Ⅵ. 실무 적용 및 결론

**적용 방안 3개 (필수):**
1. 클라우드·엣지·온프레미스 게이트웨이를 표준화하고 라우팅, 접근통제, 암호화 정책을 policy-as-code로 관리함.
2. 워크로드별 p95 지연, egress 비용, 데이터 위치 조건을 태그로 관리하고 경로 선택 정책에 반영함.
3. 로그, 메트릭, 트레이스를 중앙 수집하고 지역별 장애 시 우회 경로와 데이터 반출 제한을 함께 검증함.

**결론 (2줄):**
- 기술사 판단: 멀티클라우드와 엣지가 동시에 존재하면 분산 클라우드 네트워킹을 정책 일관성 확보 수단으로 설계해야 함.
- 향후 방향: SASE, service mesh, AI 네트워크 운영, sovereign cloud 요구가 결합된 통합 제어 구조로 발전함.
