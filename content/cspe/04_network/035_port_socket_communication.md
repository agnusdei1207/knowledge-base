## 미리 알고가기

- 포트: 하나의 IP 주소 안에서 어떤 애플리케이션이 데이터를 받을지 구분하는 논리 번호임
- 소켓: 프로세스가 네트워크와 데이터를 주고받기 위해 OS가 제공하는 통신 종단점임
- Well-known Port: HTTP 80, HTTPS 443처럼 표준 서비스에 미리 할당된 포트 범위임
- Ephemeral Port: 클라이언트가 접속 시 임시로 쓰는 동적 포트 범위임

## Ⅰ. 개요

- **정의/개념**: 포트는 같은 장비 안에서 여러 애플리케이션을 구분하는 16비트 논리 식별자이고, 소켓은 IP 주소와 포트를 결합해 프로세스가 실제 통신을 수행하도록 만든 OS 수준 인터페이스임. 네트워크 세션은 보통 프로토콜과 양쪽 IP, 양쪽 포트 조합으로 식별함
- **배경/필요성**: 한 서버가 웹, 데이터베이스, 메시징을 동시에 제공하려면 하나의 IP 주소만으로는 어느 프로세스가 데이터를 받아야 하는지 구분할 수 없으므로 포트와 소켓 구조가 필요함

## Ⅱ. 특징

- 포트는 서비스 구분을, 소켓은 실제 읽기와 쓰기를 담당하므로 역할이 다름
- 서버는 정해진 포트에서 대기하고 클라이언트는 임시 포트를 열어 연결을 만듦
- TCP 소켓은 연결 상태와 바이트 스트림을 관리하고, UDP 소켓은 연결 상태 없이 메시지 경계를 유지함
- 대규모 서버에서는 소켓 수가 곧 자원 사용량이 되므로 동시 연결 설계가 중요함

## Ⅲ. 종류 및 비교

| 판단 기준 | TCP 스트림 소켓 | UDP 데이터그램 소켓 |
|:---|:---|:---|
| 통신 방식 | 연결을 먼저 맺고 연속된 바이트 흐름을 주고받음 | 연결 없이 메시지 단위 데이터그램을 주고받음 |
| 데이터 경계 | 애플리케이션이 직접 메시지 경계를 관리해야 함 | 한 번 보낸 메시지 경계가 그대로 유지됨 |
| 적합한 서비스 | 웹, 파일 전송, 데이터베이스 연결에 적합함 | DNS, 실시간 미디어, 짧은 질의 응답에 적합함 |
| 주의할 점 | 연결 수가 많으면 스레드와 파일 디스크립터 관리가 중요함 | 손실과 순서 뒤바뀜을 애플리케이션이 직접 처리해야 함 |

> 요약: 포트는 서비스 구분용 번호이고, 소켓은 실제 통신 수단이며, 소켓 종류에 따라 연결 방식과 책임 범위가 달라짐

## Ⅳ. 구성요소 및 구조

| 구성요소 | 설명 |
|:---|:---|
| 리슨 소켓 | 서버가 특정 포트에서 접속을 기다리는 소켓이며 새 연결 수락의 출발점이 됨 |
| 연결 소켓 | 실제 데이터 송수신을 담당하는 개별 세션 소켓이며 리슨 소켓과 구분됨 |
| 포트 번호 | 서비스 식별과 세션 분리를 위해 로컬과 원격 양쪽에 각각 존재함 |
| 소켓 버퍼와 큐 | 대기 연결과 송수신 데이터를 보관하며 크기 설정이 과부하 시 성능에 직접 영향을 줌 |

```text
+--------+     +---------+     +---------+     +--------+
|socket()| --> | bind()  | --> | listen()| --> |accept()|
+--------+     +---------+     +---------+     +--------+
```

> 요약: 서버 소켓 구조는 대기용 리슨 소켓과 통신용 연결 소켓을 분리해 다수 세션을 처리하는 데 맞춰져 있음

## Ⅴ. 원리 및 절차 흐름도

```text
+----------+     +----------+     +----------+     +----------+
| 포트할당 | --> | 연결수립  | --> | 데이터교환 | --> | 연결종료  |
+----------+     +----------+     +----------+     +----------+
```

1. **포트할당**: 서버는 고정 포트에 바인딩하고 클라이언트는 임시 포트를 확보함
2. **연결수립**: TCP라면 `connect()`와 `accept()`를 통해 세션 소켓이 생성됨
3. **데이터교환**: 읽기와 쓰기를 반복하며 애플리케이션 데이터를 주고받음
4. **연결종료**: 세션 종료 뒤 포트와 소켓 자원을 회수함

## Ⅵ. 실무 적용 및 유의점

1. 대규모 웹 서버에서는 연결마다 스레드를 붙이면 소켓 수가 늘 때 문맥 전환 비용이 커지므로 논블로킹 I/O와 `epoll` 기반 구조를 적용하고 활성 소켓 수와 이벤트 처리 지연으로 확인함
2. 프록시와 로드 밸런서처럼 아웃바운드 연결이 많은 장비에서는 임시 포트가 고갈될 수 있으므로 커넥션 재사용과 포트 범위 튜닝을 함께 적용하고 포트 사용률과 연결 실패 건수로 확인함

## Ⅶ. 결론

포트와 소켓은 한 장비의 프로세스를 번호로 구분하고, 리슨·연결 소켓과 버퍼·큐로 통신 자원을 관리하는 구조임.
