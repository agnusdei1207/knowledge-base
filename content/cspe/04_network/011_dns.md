## Ⅰ. 개요
- **정의**: 도메인 이름을 IP 주소로 변환하는 분산 계층형 네임 서비스
- **배경/필요성**: 숫자 기반 IP 주소를 사람이 기억하기 어려우므로 문자열 기반 식별 체계가 필요함
- **비유**: 전화번호부에서 이름으로 전화번호를 찾는 과정과 동일함

| 출제 의도 | 반드시 짚을 핵심 | 감점 회피 포인트 |
|:---|:---|:---|
| 계층 구조와 질의 방식 이해 | 재귀·반복 질의 차이, 캐시 TTL | UDP 53 기본이나 512B 초과 시 TCP 사용 |

> 요약: 도메인-IP 매핑을 분산 계층 구조로 제공하는 인터넷 핵심 인프라임

## Ⅱ. 구성요소
```text
Client --> Recursive Resolver --> Root NS
                                    |
                                    v
                                TLD NS (.com)
                                    |
                                    v
                              Authoritative NS
```

| 구성요소 | 설명 | 비유 |
|:---|:---|:---|
| Stub Resolver | 클라이언트 측 질의 발생 모듈 | 전화번호부를 펼치는 사용자 |
| Recursive Resolver | 클라이언트 대신 계층 순회하여 응답 반환 | 안내 데스크 직원 |
| Authoritative NS | 해당 도메인의 최종 레코드를 보유한 서버 | 원본 전화번호부 보관소 |
| Resource Record | A, AAAA, CNAME, MX 등 매핑 데이터 단위 | 전화번호부의 한 줄 항목 |

> 요약: 클라이언트-재귀서버-권한서버 3단 계층으로 이름 해석을 수행함

## Ⅲ. 절차
```text
Client --query--> Recursive Resolver ---> Root NS
                       |                     |
                       | <--- referral ------+
                       +---> TLD NS
                       | <--- referral ------+
                       +---> Auth NS
                       | <--- answer --------+
                       +---> Client (응답)
```
- 1단계: 클라이언트가 Recursive Resolver에 도메인 질의 전송
- 2단계: Resolver가 Root NS에 질의하여 TLD NS 위치를 수신
- 3단계: TLD NS에 재질의하여 Authoritative NS 위치를 수신
- 4단계: Authoritative NS에서 최종 IP를 받아 클라이언트에 응답 후 캐시 저장

> 요약: 루트-TLD-권한 서버를 순차 참조하여 최종 IP를 반환하는 반복 질의 절차임

## Ⅳ. 문제점
- DNS 스푸핑: 응답 위조가 용이함 — UDP 기반이라 출처 검증 없이 먼저 도착한 응답을 수용
- 캐시 포이즈닝: 오염된 레코드가 TTL 동안 전파됨 — Resolver 캐시에 위조 데이터가 저장되면 다수 클라이언트에 영향
- DDoS 증폭: DNS가 공격 도구로 악용됨 — 작은 질의에 큰 응답이 오는 비대칭 구조를 반사 공격에 이용

> 요약: 인증 부재와 UDP 특성으로 위·변조 및 증폭 공격에 취약함

## Ⅴ. 개선방안
1. 단기: DNSSEC 적용으로 응답 서명 검증 체계 구축
2. 중기: DNS over HTTPS(DoH)/DNS over TLS(DoT) 도입으로 전송 구간 암호화
3. 장기: Anycast 기반 분산 Resolver 인프라 확대로 DDoS 내성 강화

> 요약: 서명 검증, 전송 암호화, 인프라 분산의 단계적 보안 강화가 필요함

## Ⅵ. 전망
- 발전 방향: DoH/DoT 표준화 확산으로 DNS 프라이버시 보호가 기본값이 되는 추세임
- 기술사적 판단: 제로트러스트 환경에서 DNS 질의 자체가 보안 정책 집행점으로 활용 가능함
- 기술사 제언: DNS 보안과 가용성을 동시에 확보하는 아키텍처 설계 역량이 필요함
