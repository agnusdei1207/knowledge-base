## 미리 알고가기

- NaaS는 네트워크 자원을 구독형 서비스로 제공하는 모델임
- uCPE는 지사나 현장에 두는 범용 고객측 장비임
- SD-WAN은 여러 회선과 경로를 소프트웨어로 제어하는 광역망 기술임
- SASE는 네트워크 연결과 보안을 클라우드 서비스로 결합한 구조임

## Ⅰ. 개요

- **정의/개념**: NaaS는 회선, 라우팅, 방화벽, 광역망, 접속 정책 같은 네트워크 기능을 고객이 직접 구축하지 않고 서비스 형태로 구독해 사용하는 모델임
- **배경/필요성**: 지사·사용자·SaaS 연결을 장비와 회선 단위로 조달하면 개통·변경마다 현장 작업이 필요하므로 포털과 API로 주문·변경하는 서비스 모델이 필요함

## Ⅱ. 특징

- 초기 CAPEX를 줄이고 사용량과 지점 수에 맞춘 구독형 OPEX 운영이 가능함
- 셀프서비스 포털과 API로 회선·보안·정책 변경을 요청하고 적용 상태를 확인함
- SD-WAN, 보안, 클라우드 접속을 묶어 하나의 서비스로 제공하기 쉬움
- 서비스 민첩성은 높지만 SLA, 데이터 경로, 벤더 종속을 계약 단계에서 따져야 함

## Ⅲ. 종류 및 비교

| 판단 기준 | 전통적 자체 구축 네트워크 | NaaS |
|:---|:---|:---|
| 자산 소유 | 기업이 회선과 장비를 직접 도입하고 운영함 | 서비스 제공자가 기반망과 기능을 운영하고 기업은 구독해 사용함 |
| 변경 방식 | 장비 조달과 현장 작업으로 용량·정책을 변경함 | 포털과 API 요청으로 서비스 용량·정책을 변경함 |
| 비용 구조 | 초기 투자와 교체 비용이 큼 | 월 구독과 사용량 기반 과금으로 유연성이 높음 |
| 운영 책임 | 기업 내부 네트워크 인력이 장애와 패치를 직접 담당함 | 제공자와 고객이 운영 경계와 책임을 나눠 가짐 |

> 요약: NaaS는 장비 소유보다 서비스 이용을 선택하는 모델이므로 민첩성 대신 책임 경계와 종속 구조를 먼저 봐야 함.

## Ⅳ. 구성요소 및 구조

| 구성요소 | 설명 |
|:---|:---|
| 서비스 포털과 API | 고객이 회선, 정책, 보안 기능을 요청하고 변경하는 접점임 |
| 제공자 네트워크 패브릭 | 글로벌 백본, 지역 거점, 클라우드 연동을 제공하는 기반망임 |
| 가상 네트워크 기능 | 방화벽, 라우터, VPN, WAN 최적화 같은 기능을 소프트웨어로 제공함 |
| 고객 엣지 장비 | 본사와 지사, 원격 사용자 접속을 제공자 서비스와 연결하는 현장 단말임 |
| 과금과 모니터링 | 사용량, SLA, 장애 현황을 수집하고 서비스 품질을 보여주는 운영 계층임 |

```text
+-------------+     +----------------+     +----------------+     +----------------+
| 고객 포털·API  | --> | 제공자 패브릭      | --> | 가상 네트워크 기능   | --> | 고객 엣지·클라우드 |
+-------------+     +----------------+     +----------------+     +----------------+
```

## Ⅴ. 원리 및 절차 흐름도

```text
+-------------+     +----------------+     +------------------+     +----------------+
| 서비스 요청    | --> | 정책·용량 할당     | --> | 엣지 연결·기능 활성화 | --> | 모니터링·과금      |
+-------------+     +----------------+     +------------------+     +----------------+
```

1. **서비스 요청**: 고객이 필요한 회선, 보안, 대역폭, 지사 연결 요구를 등록함
2. **정책과 용량 할당**: 제공자가 가상 기능과 경로 정책을 고객 요구에 맞춰 할당함
3. **엣지 연결과 기능 활성화**: 현장 엣지 장비와 클라우드 접속 경로에 필요한 기능을 적용함
4. **모니터링과 과금**: 사용량과 SLA를 수집해 서비스 품질과 비용을 관리함

## Ⅵ. 실무 적용 및 유의점

1. 해외 지사와 클라우드 접속의 개통 기간을 줄여야 할 때는 NaaS를 검토하되 제공자 백본과 보안 경로가 업무 흐름과 맞지 않으면 지연과 우회가 생기므로 서비스 경로와 SLA를 계약 전에 확인하고 개통 시간과 종단 간 지연으로 점검함
2. SD-WAN과 SASE를 함께 구독하는 환경에서는 운영이 단순해 보이지만 벤더 종속이 깊어질 수 있으므로 정책 이식성과 로그 반출 기준을 먼저 정하고 서비스 이전 가능성과 보안 이벤트 대응 시간으로 확인함

## Ⅶ. 결론

NaaS의 본질은 네트워크를 장비 소유가 아닌 서비스 이용 모델로 바꾸는 데 있으므로 도입 판단에서는 기능 편의보다 SLA와 운영 경계가 먼저 검토되어야 함.
