# 📖 【암기용】 개념 완전 이해

> 목적: NaaS를 처음 봐도 완벽히 이해하게 만든다. 시험 답안 양식이 아니라, 이해를 위한 친절한 설명이다.

## 한눈에
- **개요**: 네트워크 기능과 연결 서비스를 장비 구매가 아니라 API·구독·정책 기반 서비스로 제공하는 모델
- **왜 필요한가**: 지점, 클라우드, 원격근무, 보안 연결이 자주 바뀌면서 회선·장비 중심 구축 방식은 변경 속도와 운영 인력 측면에서 부담이 큼
- **핵심 직관**: 회사가 발전기를 직접 사고 운영하지 않고 전기를 계약해 쓰듯, 네트워크도 대역폭·보안·연결을 서비스로 소비하는 방식임

## 깊이 이해
- **배경·문제의식**: 전통 네트워크는 회선 계약, 라우터·방화벽 구매, 현장 설치, 장비별 운영으로 구성됨. 클라우드 전환과 SaaS 사용 증가는 지점과 사용자의 연결·보안 정책을 동적으로 바꾸게 만들었음.
- **작동 원리**: NaaS Provider가 SD-WAN, SASE, Firewall, VPN, Zero Trust, 회선, 관측성을 패키지로 제공하고, 고객은 포털·API로 정책과 대역폭을 조정함.
- **비유**: 사내 식당을 직접 짓는 대신 식사 구독 서비스를 계약하고 인원 변화에 맞게 메뉴와 수량을 조절하는 구조와 같음.
- **구체 예시**: 50개 지점 기업이 라우터와 방화벽을 직접 구매하지 않고 NaaS 포털에서 지점별 100Mbps 회선, ZTNA, SWG, CASB 정책을 월 구독으로 설정함.
- **흔한 오해·주의점**: NaaS는 단순 회선 임대가 아님. 네트워크 연결, 보안 기능, 정책 자동화, 관측성, SLA가 결합된 운영 모델임.

## 연결 개념
- SD-WAN — 애플리케이션별 경로와 회선을 정책 제어하는 WAN 구조
- SASE — 네트워크와 보안을 클라우드 서비스로 통합하는 모델
- Zero Trust Network Access — 사용자·기기·앱 단위 접근 제어

# 📝 【답안용】 시험 답안 템플릿

> 목적: 시험장에서 25분에 그대로 쓰는 답안 양식. 작성방식(추상표현 금지·수치·도식·문제유형 전환)을 엄격히 지킨다.
> 핵심: NaaS를 회선 임대가 아니라 SD-WAN, SASE, API, SLA, 구독 과금, 운영 책임 분담 모델로 설명한다.

## 핵심 인사이트 (3줄 요약)

> 1. **본질**: NaaS는 네트워크 연결·보안·정책·관측성을 구독형 서비스와 API로 제공하는 운영 모델이다.
> 2. **가치**: 지점 개설, 클라우드 연결, 원격근무 보안을 장비 구매가 아니라 정책·SLA·과금 단위로 관리한다.
> 3. **판단 포인트**: SLA, 데이터 경로, 보안 책임, 벤더 종속, API 연동, 비용 예측성을 계약과 지표로 검증해야 한다.

## 출제 의도 및 답안 포인트

| 출제 의도 | 반드시 짚을 핵심 | 감점 회피 포인트 |
|:---|:---|:---|
| 서비스형 네트워크 모델 이해 확인 | 구독, API, SLA, 정책 기반 운영 | 회선 임대 또는 장비 렌탈로 축소 금지 |
| 클라우드·보안 연계 판단 확인 | SD-WAN, SASE, ZTNA, SWG, CASB | 보안 책임 분담 누락 금지 |
| 운영·계약 리스크 확인 | SLA, 데이터 위치, 벤더 종속, 비용 | 기능 나열만 하고 계약 지표 누락 금지 |

> 요약: 이 문제는 네트워크 기능을 서비스로 소비할 때의 기술 구조와 운영 책임을 함께 묻는다.

## Ⅰ. 개요 및 필요성

- 개요: 네트워크 기능의 구독형 제공
- 배경: 기업 네트워크는 지점, 클라우드, SaaS, 원격근무 확대로 고정 장비 중심 변경 절차가 길어진다.
- 필요성: NaaS는 SD-WAN·SASE·ZTNA·관측성을 포털/API로 제공해 연결과 보안 기능을 서비스 카탈로그로 소비하게 한다.

---

## Ⅱ. 구조 및 구성요소

```text
User/Branch/Cloud -> NaaS Edge/PoP -> Policy Engine
-> SD-WAN/SASE Services -> Internet/SaaS/IaaS/DC
Portal/API -> Provisioning -> SLA/Telemetry/Billing
```

| 구성요소 | 역할 | 특이사항 |
|:---|:---|:---|
| NaaS Portal/API | 서비스 신청·정책 변경 | IaC, REST API, 승인 절차 |
| Edge/PoP | 사용자·지점 접속 지점 | 지역별 지연·가용성 영향 |
| Policy Engine | 경로·보안 정책 결정 | 사용자, 기기, 앱, 위치 기준 |
| Network Service | SD-WAN, VPN, QoS | 대역폭, 경로, SLA |
| Security Service | ZTNA, SWG, CASB, FWaaS | 인증·인가·로깅·검사 |

> 요약: NaaS는 Portal/API, Edge/PoP, 정책 엔진, 네트워크·보안 서비스, SLA/과금 체계로 구성된다.

---

## Ⅲ. 동작원리 및 흐름도

```text
서비스 요청 -> 정책 템플릿 선택 -> API Provisioning
-> Edge/PoP 연결 -> 사용자/기기 인증
-> 경로·보안 정책 적용 -> Telemetry 수집
-> SLA 평가/과금 -> 정책 조정
```

| 단계 | 처리 내용 | 검증 기준 |
|:---:|:---|:---|
| 1 | 지점·사용자·클라우드 연결 요구 등록 | 서비스 카탈로그, 승인 이력 |
| 2 | API로 회선·보안·라우팅 정책 배포 | Provisioning Time |
| 3 | 사용자·기기 인증 후 정책 적용 | MFA, Device Posture |
| 4 | 애플리케이션별 경로와 보안 검사 수행 | SLA, SWG/CASB 로그 |
| 5 | 사용량·장애·품질 지표를 과금과 연계 | Billing, Telemetry |

> 요약: NaaS는 요구 등록부터 API 배포, 인증, 정책 적용, SLA·과금까지 서비스 운영 흐름으로 동작한다.

## Ⅳ. 특징

| 구분 | 전통 네트워크 | NaaS | 수치·표준 포인트 |
|:---|:---|:---|:---|
| 조달 | 장비 구매·회선 계약 | 구독·사용량 과금 | 월 단위, 대역폭 단위 |
| 변경 | 현장 설치·CLI 설정 | 포털/API Provisioning | 지점 개통 시간 측정 |
| 보안 | 장비별 방화벽/VPN | SASE, ZTNA, SWG, CASB | 사용자·기기 기반 정책 |
| 운영 | 자체 NOC 중심 | Provider SLA와 공동 운영 | 가용성 99.9%, MTTR |

> 요약: NaaS는 네트워크를 구독형 서비스로 전환하지만 SLA와 책임 분담을 계약으로 명확히 해야 한다.

## Ⅴ. 심화 비교 및 적용 판단

| 비교 축 | 기존/대안 | NaaS | 선택 기준 |
|:---|:---|:---|:---|
| 지점망 | MPLS, 장비 구매 | SD-WAN 구독 | 지점 수, 개통 리드타임, SaaS 사용률 |
| 보안 | VPN, 온프레미스 FW | SASE/Zero Trust | 원격근무, 사용자 단위 접근 제어 |
| 비용 | CAPEX 중심 | OPEX·사용량 과금 | 3년 TCO, 최소 약정, 초과 과금 |

> 요약: NaaS는 지점 변화와 원격근무 비중이 높고 OPEX 모델을 선호할 때 선택한다.

| 리스크 | 원인 | 대응 방안 | 확인 지표 |
|:---|:---|:---|:---|
| 벤더 종속 | 포털·정책·로그 형식 의존 | API 표준성, Exit Plan, 데이터 반출 | Migration Time |
| SLA 불일치 | 지역 PoP·회선 품질 차이 | 지역별 SLA, 장애 보상 조항 | Availability, MTTR |
| 비용 예측 실패 | 사용량·대역폭 초과 과금 | FinOps 태깅, 예산 알림 | Monthly Cost Variance |

> 요약: NaaS 리스크는 벤더 종속, 지역별 SLA, 비용 변동이며 계약과 FinOps 지표로 통제해야 한다.

| 점검 항목 | 목표 기준 | 측정 방법 |
|:---|:---|:---|
| 개통 시간 | 신규 지점 1일 이내 Provisioning | 티켓·API 로그 |
| 품질 | SaaS p95 지연 SLA 이하 | DEM, Synthetic Monitoring |
| 보안 | 정책 위반 탐지·감사로그 100% 수집 | SIEM, CASB/SWG 로그 |

> 요약: NaaS 효과는 개통 시간, 애플리케이션 지연, 보안 로그 수집률로 평가한다.

## Ⅵ. 실무 적용 및 결론

**적용 방안 3개 (필수 — 단계별 또는 항목별):**
1. 지점·클라우드·원격사용자 유형별 서비스 카탈로그를 정의하고 API Provisioning 시간을 기준선으로 측정함
2. SASE 정책은 사용자, 기기 상태, 애플리케이션, 위치 기준으로 분리하고 SIEM 연동 로그 필드를 계약에 포함함
3. SLA는 지역 PoP 가용성, p95 지연, MTTR, 장애 보상, 데이터 반출 조건을 계약서와 운영 대시보드에 매핑함

**결론 (2줄):**
- 기술사 판단: 지점 변화·원격근무·SaaS 이용률이 높으면 NaaS, 고정 폐쇄망과 특수 회선 요구가 크면 전통 WAN을 병행함
- 향후 방향: NaaS는 SASE, Zero Trust, 멀티클라우드 연결, AIOps 관측성과 결합해 정책 기반 네트워크 운영 모델로 확장됨
