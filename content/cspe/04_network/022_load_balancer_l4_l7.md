## 미리 알고가기

- VIP: 클라이언트가 접속하는 대표 가상 주소임
- 헬스 체크: 백엔드 서버가 실제로 요청을 처리할 수 있는지 확인하는 절차임
- 세션 고정: 한 사용자를 같은 서버에 계속 보내는 방식임
- 리버스 프록시: 클라이언트 앞에서 요청을 대신 받고 백엔드로 전달하는 구조임

## Ⅰ. 개요

- **정의/개념**: 로드 밸런서는 하나의 서비스 주소로 들어온 요청을 여러 서버에 분산해 가용성과 확장성을 높이는 장비 또는 소프트웨어임. L4는 IP와 포트 중심으로, L7은 애플리케이션 내용 중심으로 분산 결정을 내림
- **배경/필요성**: 서비스 트래픽이 한 서버에 몰리면 응답 지연과 단일 장애점이 동시에 생기므로, 서버 상태를 보면서 요청을 적절히 나누는 전면 제어 계층이 필요함

## Ⅱ. 특징

- 백엔드 여러 대를 하나의 VIP 뒤에 숨겨 서비스 주소를 단순하게 유지할 수 있음
- 헬스 체크를 통해 장애 서버를 자동으로 제외하므로 서비스 연속성이 높아짐
- L4는 빠른 세션 분산에 유리하고, L7은 URL과 쿠키 기준 정교한 분기에 유리함
- 세션 고정, SSL 종료, 경로별 분산처럼 편의 기능이 많지만, 잘못 쓰면 지연과 편향 분산이 커질 수 있음

## Ⅲ. 종류 및 비교

| 판단 기준 | L4 로드 밸런서 | L7 로드 밸런서 |
|:---|:---|:---|
| 분산 기준 | IP 주소와 포트, 프로토콜 정보를 기준으로 세션을 분산함 | URL, 호스트명, 쿠키, 헤더 값을 기준으로 요청을 분산함 |
| 처리 성격 | 패킷과 세션 수준에서 빠르게 처리해 지연이 작음 | 애플리케이션 내용을 해석하므로 더 세밀하지만 처리 비용이 큼 |
| 적합한 서비스 | 단순 TCP 서비스, 대량 연결, 내부 서비스 분산에 적합함 | 웹 서비스, API 게이트웨이, 콘텐츠 기반 분기에 적합함 |
| 주의할 점 | 애플리케이션 상태를 직접 알기 어려워 정교한 분기가 제한됨 | TLS 종료와 헤더 해석 때문에 CPU 사용량과 지연이 늘 수 있음 |

> 요약: 빠른 세션 분산이 우선이면 L4가 맞고, 요청 내용에 따라 다른 처리 경로가 필요하면 L7이 맞음

## Ⅳ. 구성요소 및 구조

| 구성요소 | 설명 |
|:---|:---|
| VIP | 클라이언트가 접속하는 대표 주소이며 실제 서버 변경을 사용자에게 숨겨 줌 |
| 서버 풀 | 같은 서비스를 제공하는 백엔드 서버 집합이며 분산 대상이 되는 자원임 |
| 스케줄링 엔진 | 라운드 로빈, 최소 연결, 해시 기반 방식으로 어떤 서버에 보낼지 결정함 |
| 헬스 체크 모듈 | TCP 포트 응답이나 HTTP 상태 코드로 서버 상태를 확인해 장애 서버를 제외함 |

```text
+--------+     +---------+     +------------------+
|Client  | --> |  VIP    | --> | Server Pool      |
+--------+     +---------+     +------------------+
                    |
                    v
              +-----------+
              |Health Check|
              +-----------+
```

> 요약: 로드 밸런서는 VIP로 요청을 모으고, 상태가 정상인 서버만 골라 분산하는 구조임

## Ⅴ. 원리 및 절차 흐름도

```text
+----------+     +----------+     +----------+     +----------+
| 상태점검 | --> | 요청수신  | --> | 서버선택  | --> | 응답전달  |
+----------+     +----------+     +----------+     +----------+
```

1. **상태점검**: 로드 밸런서가 주기적으로 백엔드 서버 상태를 확인함
2. **요청수신**: 클라이언트가 VIP로 요청을 보냄
3. **서버선택**: 분산 알고리즘과 정책에 따라 적절한 백엔드 서버를 선택함
4. **응답전달**: 선택된 서버의 응답을 받아 클라이언트에 전달함

## Ⅵ. 실무 적용 및 유의점

1. 웹 서비스에서는 L7 로드 밸런서로 URL과 쿠키 기준 분산을 하되 세션 고정이 과하면 특정 서버로 요청이 몰릴 수 있으므로 세션 정책과 무상태 설계를 함께 조정하고 백엔드별 응답 시간과 활성 세션 수로 확인함
2. 대량 TCP 연결을 처리하는 내부 서비스나 게임 게이트웨이에서는 L4 로드 밸런서가 유리하지만 단순 포트 응답만으로는 애플리케이션 장애를 놓칠 수 있으므로 L4 분산에 상위 헬스 체크를 보완하고 연결 실패율과 재시도율로 확인함

## Ⅶ. 결론

로드 밸런서는 서버 수를 늘리는 장비가 아니라, 어떤 계층 정보로 분산 결정을 내릴지와 장애 서버를 어떻게 제외할지를 함께 설계하는 제어 계층임.
