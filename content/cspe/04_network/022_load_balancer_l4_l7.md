# 📖 【암기용】 개념 완전 이해

> 목적: L4와 L7 로드 밸런서의 원리와 차이를 처음 봐도 완벽히 이해하게 만든다.

## 한눈에
- **개요**: 클라이언트의 요청을 여러 서버로 분산시켜 시스템의 부하를 줄이고 가용성을 높이는 트래픽 분배 기술
- **왜 필요한가**: 한 대의 서버로는 대규모 트래픽을 감당할 수 없고 단일 장애점(SPOF)이 되므로, 수평 확장(Scale-out)하여 처리해야 함
- **핵심 직관**: L4는 톨게이트 직원이 차 번호판(IP)과 차종(Port)만 보고 차로를 배정하는 것이고, L7은 세관원이 트렁크 속 물건(Payload, URL)까지 확인 후 보내는 것이다.

## 깊이 이해
- **배경·문제의식**: 초기 DNS 라운드 로빈은 대상 서버가 다운되어도 트래픽을 계속 보내는 문제가 있었다. 서버 상태를 체크(Health Check)하고 정상 서버로만 보내는 전용 장비가 필요해짐.
- **작동 원리**:
  - **L4 로드 밸런서**: TCP/UDP 계층에서 작동. 클라이언트 IP와 포트를 해싱하여 서버를 선택. 패킷 내용을 보지 않으므로 처리 속도가 매우 빠름.
  - **L7 로드 밸런서**: 애플리케이션 계층(HTTP 등)에서 작동. TCP 세션을 맺은 뒤 HTTP 헤더, 쿠키, URL을 분석해 서버를 선택하고 서버와 다시 세션을 맺음.
- **비유**: L4는 '우편물 겉봉투'만 보고 지역별 우체국으로 나누는 것, L7은 '우편물 내용'을 읽고 부서 담당자에게 직접 전달하는 것.
- **구체 예시**: `/api/video` 요청은 비디오 서버로, `/api/auth` 요청은 인증 서버로 보내는 것은 L7 로드밸런서만 할 수 있다. 반면 대량의 단순 UDP 패킷 분산은 L4가 유리하다.
- **흔한 오해·주의점**: "L7은 무조건 L4를 대체한다"고 생각하면 안 된다. L7은 패킷을 조립하고 복호화(TLS Termination)하므로 CPU 소모가 커, 앞단에 L4를 두고 뒷단에 L7(API Gateway 등)을 두는 2단 구성이 많다.

## 연결 개념
- DSR (Direct Server Return) — L4의 병목을 줄이기 위해 응답 패킷이 LB를 안 거치고 클라이언트로 직행하는 기술
- TLS Termination — SSL/TLS 암호화 해독을 로드밸런서가 대신 처리해 서버 부하를 줄임
- GSLB (Global Server Load Balancing) — DNS 기반으로 지리적으로 분산된 데이터센터 간 로드 밸런싱

# 📝 【답안용】 시험 답안 템플릿

> 목적: 시험장에서 25분에 그대로 쓰는 답안 양식.

## 핵심 인사이트 (3줄 요약)

> 1. **본질**: 서버 부하 분산 및 무중단 서비스를 위해 클라이언트 트래픽을 L4(IP/Port) 또는 L7(Payload) 정보를 기준으로 서버에 배분하는 아키텍처다.
> 2. **가치**: Health Check를 통한 단일 장애점(SPOF) 제거 및 가용성 확보, 트래픽 폭증 시 무중단 스케일아웃(Scale-out)을 가능하게 한다.
> 3. **판단 포인트**: 처리 성능이 중요한 단순 분산은 L4, 마이크로서비스(MSA) 라우팅이나 모바일 환경의 쿠키 세션 유지가 필요할 때는 L7을 선택한다.

## 출제 의도 및 답안 포인트

| 출제 의도 | 반드시 짚을 핵심 | 감점 회피 포인트 |
|:---|:---|:---|
| L4와 L7의 동작 계층 및 식별 정보 차이 확인 | L4: IP+Port, 빠른 처리 / L7: HTTP 헤더, 쿠키, Payload, 프록시 | 단순히 "L7이 더 똑똑하다"는 비기술적 서술 |
| 알고리즘 및 세션 유지 기법 이해 | Round Robin, Least Connection, Source IP vs 쿠키 Sticky 세션 | Sticky 세션의 단점(부하 불균형) 누락 |
| 아키텍처 구성 시 성능 트레이드오프 파악 | L7의 패킷 재조립 및 TLS 처리 오버헤드, NAT vs DSR 구성 방식 | L4/L7의 아키텍처적 배치 장단점 누락 |

> 요약: 트래픽 특성에 맞춘 계층(L4/L7) 선택, 알고리즘, 세션 유지 기법의 매핑을 묻는다.

---

## Ⅰ. 개요 및 필요성

- 정의: 클라이언트 트래픽을 다수의 백엔드 서버로 분산하여 가용성과 성능을 향상시키는 통신 중재 기술
- 배경: 단일 서버 자원 임계치 도달 및 DNS 라운드 로빈의 장애 서버 우회 불가 한계 극복 필요
- 필요성: 클라우드와 MSA 환경에서 마이크로서비스 간 라우팅, TLS 오프로딩, SLA 99.99% 달성 위해 필수적

---

## Ⅱ. 구조 및 구성요소

```text
Client Request -> [Load Balancer] -> [Health Check 통과 서버 풀]
                      | (스케줄링 알고리즘)     +-> Server A (Active)
                      +-> L4: IP/Port           +-> Server B (Active)
                      +-> L7: URI/Header        +-> Server C (Down - Bypass)
```

| 구성요소 | 역할 | 특이사항 |
|:---|:---|:---|
| VIP (Virtual IP) | 클라이언트가 접근하는 LB의 단일 진입점 IP | 서버 은닉 및 단일 엔드포인트 제공 |
| Server Pool | 실제 서비스를 제공하는 백엔드 서버 그룹 | Auto Scaling 연동 시 동적 증감 |
| Health Check | ICMP, TCP, HTTP 등으로 서버 생존 확인 | 실패 시 스케줄링 풀에서 자동 제외 |
| 스케줄링 알고리즘 | 트래픽을 분산할 대상 서버 결정 규칙 | RR, Least Connection, Hashing |

> 요약: 로드 밸런서는 VIP로 트래픽을 받아, 헬스 체크로 검증된 서버 풀 내에서 알고리즘에 따라 분산한다.

---

## Ⅲ. 동작원리 및 흐름도

```text
Client(CIP) -> VIP 요청 -> LB 서버 선택 -> DNAT(VIP를 RIP로 변환) -> Server 처리
Server 응답 -> LB 수신 -> SNAT(RIP를 VIP로 변환) -> Client 응답
```

| 단계 | 처리 내용 | 검증 기준 |
|:---:|:---|:---|
| 1 | 클라이언트 요청 수신 (VIP) | L4/L7 모두 클라이언트는 VIP만 인지 |
| 2 | 세션 확인 및 서버 스케줄링 | Sticky 세션 설정 시 기존 서버 유지율 |
| 3 | 패킷 변환 및 전송 (NAT, DSR, 프록시) | L7 프록시 방식 시 백엔드와 별도 TCP 세션 확립 |
| 4 | 서버 응답 및 클라이언트 반환 | DSR 시나리오에서는 응답 패킷 LB 우회 여부 |

> 요약: L4는 NAT를 통해 패킷 헤더만 조작하여 처리하고, L7은 프록시로 동작하여 클라이언트와 서버 간 세션을 분리 제어한다.

---

## Ⅳ. 특징

| 구분 | L4 스케줄링 / 세션 유지 | L7 스케줄링 / 세션 유지 | 판단 포인트 |
|:---|:---|:---|:---|
| 주요 알고리즘 | Round Robin, Least Connection | URL Path Hashing, Header 라우팅 | MSA의 API별 라우팅은 L7 필수 |
| 세션 유지 | Source IP Hashing | Cookie 삽입, Session ID 트래킹 | 모바일(IP 잦은 변경) 환경은 쿠키 필수 |
| TLS 오프로딩 | 패스스루 (Pass-through) | TLS 복호화 후 패킷 검사 가능 | 인증서 중앙화 및 서버 CPU 절감 |

> 요약: L4는 Source IP 기반의 빠른 분산에 유리하고, L7은 IP가 변하는 환경에서도 정밀한 세션 유지가 가능하다.

## Ⅴ. 심화 비교 및 적용 판단

| 비교 축 | L4 Load Balancing | L7 Load Balancing | 선택 기준 |
|:---|:---|:---|:---|
| 프로토콜 범위 | TCP, UDP 전반 (데이터베이스, 게임) | HTTP, HTTPS, HTTP/2, gRPC | 애플리케이션 프로토콜 의존성 |
| 네트워크 구성 | NAT, DSR(Direct Server Return) 구성 | 리버스 프록시 (Reverse Proxy) | DSR 통한 LB 아웃바운드 병목 제거 |
| 보안 기능 | 단순 SYN Flood 방어, 포트 필터링 | WAF 연동, SQLi/XSS 페이로드 차단 | 애플리케이션 계층 위협 노출 정도 |

> 요약: 대규모 스트리밍/게임은 응답 병목이 없는 L4 DSR 구성이 필수적이고, API 서비스망은 L7 프록시 구성이 표준이다.

| 리스크 | 원인 | 대응 방안 | 확인 지표 |
|:---|:---|:---|:---|
| Sticky 세션 쏠림 | 소수 IP가 대량 트래픽 발생 | 타임아웃 최소화, Stateless 재설계 | 서버별 CPU 자원 사용률 편차 |
| L7 LB 병목 현상 | TLS 복호화 및 정규식 매칭 오버헤드 | 하드웨어 NPU 가속, L4+L7 분산 구조 | L7 처리 Latency 및 CPU 사용률 |
| LB SPOF 발생 | 단일 LB 장비 하드웨어 장애 | LB 이중화(VRRP), DNS GSLB 연동 | VIP Failover 소요 시간 (초 단위) |

> 요약: 세션 유지는 부하 불균형 리스크를 낳으므로, 궁극적으로는 애플리케이션을 Stateless로 재설계해야 한다.

## Ⅵ. 실무 적용 및 결론

**적용 방안 3개:**
1. L4/L7 2-Tier 아키텍처: 외곽에 L4 밸런서를 두어 1차 대용량 트래픽을 N대의 L7 밸런서(API Gateway)로 분산시켜 병목 제거
2. DSR(Direct Server Return) 적용: 스트리밍 등 아웃바운드 트래픽이 큰 서비스에서 응답 패킷이 LB를 거치지 않게 구성
3. Stateless 전환: 세션 데이터(로그인 상태 등)를 외부 인메모리 DB로 분리하고, LB의 Sticky 구성을 제거하여 완벽한 Least Connection 달성

**결론 (2줄):**
- 기술사 판단: 클라우드 네이티브 환경에서는 L4 하드웨어 스위치보다 Ingress Controller, Envoy 같은 소프트웨어 L7 로드밸런서가 핵심이다.
- 향후 방향: 단순 트래픽 분산을 넘어, Service Mesh 사이드카 패턴을 통한 마이크로서비스 간 관측성·보안 제어로 발전하고 있다.

| 유형 | 문제 신호어 | Ⅲ 강조 | Ⅳ 강조 |
|:---|:---|:---|:---|
| 포괄형 | "로드 밸런싱 기술을 설명하시오" | 알고리즘별 동작 원리 | L4/L7 비교표, 헬스 체크 방식 |
| 비교형 | "L4와 L7 부하분산 방식을 비교하시오" | IP 기반 vs Payload 기반 파싱 단계 차이 | 세션 유지(Sticky) 방식 차이 및 장단점 |
| 방안형 | "로드 밸런서 병목 현상 해결방안" | NAT 모드와 DSR 모드 패킷 흐름도 대조 | 2-Tier 분산, DSR, TLS 오프로딩 적용 방안 |

> 요약: 어떤 문제든 "SPOF 제거"와 "알고리즘 분산", "상태 유지(Sticky) 한계 극복" 논점을 빠뜨리면 안 된다.
