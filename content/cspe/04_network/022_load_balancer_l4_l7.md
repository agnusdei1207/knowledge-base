# 📖 【암기용】 개념 완전 이해

## 한눈에
- **개요**: 서버 한 대에 몰리는 부하를 여러 대의 서버로 골고루 나눠주는 **부하 분산 장치**입니다.
- **필요성**: 사용자가 갑자기 늘어나면 서버 한 대는 버티지 못하고 죽어버립니다. 이때 여러 대의 서버(Scale-out)를 준비하고, 입구에서 교통정리를 해주는 로드 밸런서가 있어야 무중단 서비스가 가능합니다.
- **핵심 직관**: **"은행 창구 안내원"**. 손님(트래픽)이 오면 비어 있는 창구(서버)로 안내해주는 역할입니다.

## 깊이 이해
- **배경 (Single Point of Failure 방지)**: 서버가 한 대뿐이면 그 서버가 고장 날 때 서비스 전체가 멈춥니다. 로드 밸런서는 서버의 생존 여부(Health Check)를 수시로 확인하여, 죽은 서버에는 손님을 보내지 않습니다.
- **L4 vs L7 (분류 기준)**:
  - **L4 (Transport)**: IP와 포트 번호만 봅니다. "80번 포트 웹 요청이네? 그냥 순서대로 나눠주자." (속도가 빠름)
  - **L7 (Application)**: 실제 데이터 내용(URL, 쿠키, 이미지 등)을 봅니다. "이건 동영상 요청이니까 동영상 전용 서버로 보내고, 저건 이미지니까 이미지 서버로 보내!" (정교한 제어)
- **알고리즘 (나누는 방법)**:
  - **Round Robin**: 순서대로 하나씩 돌아가며 배분.
  - **Least Connection**: 현재 손님이 가장 적은 서버로 배분.
  - **Source Hashing**: 같은 사람(IP)은 계속 같은 서버로 배분. (로그인 유지 등에 필요)
- **비유 (뷔페 식당)**:
  - **L4**: 손님이 오면 그냥 빈 테이블로 순서대로 안내함.
  - **L7**: 손님이 "스테이크 먹고 싶어요" 하면 스테이크 코너로, "초밥 먹고 싶어요" 하면 일식 코너로 안내함.

## 연결 개념
- **Health Check**: 서버가 살아있는지 주기적으로 찔러보는 행위. (ICMP, TCP, HTTP 등 이용)
- **Persistence (Sticky Session)**: 한 번 연결된 서버와 계속 통신하도록 묶어주는 기능.

# 📝 【답안용】 시험 답안 템플릿

## 핵심 인사이트 (3줄 요약)
> 1. **본질**: 클라이언트의 요청을 다수의 서버로 분산하여 가용성(Availability)과 확장성(Scalability)을 확보하는 트래픽 제어 장치임.
> 2. **가치**: Health Check를 통한 장애 서버 자동 우회(Failover)로 무중단 서비스를 제공하며, 부하 분산을 통해 응답 속도를 최적화함.
> 3. **판단 포인트**: 단순 부하 분산은 L4(속도 중심)를, 애플리케이션 특성별 정밀 라우팅 및 보안 강화가 필요할 때는 L7(콘텐츠 중심)을 선택함.

## Ⅰ. 로드 밸런싱(Load Balancing)의 정의 및 목적
- **정의**: 네트워크 트래픽을 여러 대의 서버로 적절히 분산하여 서버 부하를 균형 있게 관리하는 기술.
- **주요 목적**:
  - **고가용성(High Availability)**: 특정 서버 장애 시에도 다른 서버를 통해 중단 없는 서비스 제공.
  - **확장성(Scalability)**: 트래픽 증가 시 서버 대수를 늘려 성능을 유연하게 확장 (Scale-out).
  - **효율성**: 자원의 낭비 없이 서버들의 활용도를 극대화.

## Ⅱ. L4 로드 밸런서 vs L7 로드 밸런서 심층 비교

| 비교 항목 | L4 로드 밸런서 (Layer 4) | L7 로드 밸런서 (Layer 7) |
|:---:|:---|:---|
| **참조 헤더** | IP, TCP/UDP 포트 번호 | HTTP Header, Cookie, URL, Payload |
| **분산 기준** | 4-tuple (Src/Dst IP, Port) | 콘텐츠 내용 (정규표현식 매칭) |
| **작동 방식** | 패킷 레벨 스위칭 (NAT/DSR) | 애플리케이션 프록시 (Reverse Proxy) |
| **장점** | 처리가 빠르고 저렴하며 효율적임 | 정교한 라우팅 및 보안 필터링 가능 |
| **단점** | 상위 계층 데이터 분석 불가 | 패킷 분석 부하(CPU) 및 지연 발생 |

## Ⅲ. 주요 부하 분산 알고리즘 (Scheduling)

### 1. 정적 알고리즘
- **Round Robin**: 서버 성능이 동일할 때 순차적으로 배분.
- **Weighted Round Robin**: 서버 스펙에 따라 가중치를 부여하여 차등 배분.

### 2. 동적 알고리즘
- **Least Connection**: 현재 활성화된 세션 수가 가장 적은 서버 우선 선택.
- **Response Time**: 서버의 응답 시간이 가장 빠른 서버 우선 선택.

### 3. 해싱 알고리즘
- **Source IP Hash**: 클라이언트 IP를 해싱하여 특정 사용자를 동일 서버로 고정 (세션 유지용).

## Ⅳ. 로드 밸런서의 핵심 기능: 가용성 보장 기술

### 1. Health Check (생존 확인)
- **L3(ICMP)**: Ping으로 장비 활성 상태 확인.
- **L4(TCP)**: 3-way Handshake를 통해 서비스 포트 활성 확인.
- **L7(HTTP)**: 실제 웹 페이지 요청(GET)에 대한 응답 코드(200 OK) 확인. (가장 정확)

### 2. DSR (Direct Server Return)
- 요청은 로드 밸런서를 거치지만, **응답은 서버가 직접 클라이언트에게 전송**하는 방식.
- 로드 밸런서의 부하(Outbound 트래픽 병목)를 획기적으로 줄여 대용량 서비스에 적합.

## Ⅴ. 실무적 로드 밸런서 구성 전략

### 1. In-Line 구조 vs One-Arm 구조
- **In-Line**: 트래픽의 모든 경로에 LB가 위치 (관리가 쉽지만 LB 장애 시 전체 영향).
- **One-Arm**: LB가 스위치 옆에 위치하여 필요한 트래픽만 처리 (유연한 확장 가능).

### 2. SSL Offloading (SSL Termination)
- 로드 밸런서가 SSL 암복호화를 대신 처리하여 백엔드 서버의 자원 소모 방지 및 인증서 통합 관리.

## Ⅵ. 기술사적 통찰: '하드웨어'에서 '클라우드'로
- **클라우드 서비스의 핵심**: AWS의 ELB(ALB, NLB)나 GCP의 Cloud Load Balancing은 클라우드 네이티브 아키텍처의 심장부임. 이제 로드 밸런서는 물리 장비가 아닌 '관리형 서비스'로 소비됨.
- **MSA와 Service Mesh**: 마이크로서비스 아키텍처(MSA)에서는 서비스 간 통신이 폭증함. 이를 제어하기 위해 사이드카 프록시(Envoy 등)를 이용한 서비스 내부의 로드 밸런싱이 더욱 중요해지고 있음.
- **결론**: 로드 밸런서는 단순히 부하를 나누는 도구를 넘어, 서비스의 가용성, 보안, 유연성을 결정짓는 **"현대 네트워크 아키텍처의 컨트롤 타워"**임.
