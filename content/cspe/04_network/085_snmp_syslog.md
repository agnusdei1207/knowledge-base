## Ⅰ. 개요
| 항목 | 내용 |
|---|---|
| **정의** | 다양한 벤더 장비의 성능 정보(CPU, Memory, Traffic)를 수집(SNMP)하고, 발생한 이벤트 로그를 중앙 서버로 전송(Syslog)하는 산업 표준 모니터링 체계 |
| **배경/필요성** | 대규모 망에서 장비 장애의 사전 예측(성능 저하 탐지) 및 사후 원인 분석(로그 감사)을 위한 단일 가시성 확보 필요 |
| **출제 의도** | SNMP (Manager-Agent, MIB/OID, Trap) 구조와 Syslog의 Facility/Severity 분류 체계 기반 관리 통제 원리 평가 |

## Ⅱ. 구성요소
```text
+----------+       +----------+       +----------+
|  Router  |       | Network  |       |  Syslog  |
| (Agent)  | ----> | (Manager)| <---- | (Server) |
+----------+       +----------+       +----------+
```
| 구성요소 | 설명 | 비유 |
|---|---|---|
| SNMP Agent/MIB | 장비 내장 모듈로 상태 정보(OID 기반 데이터베이스인 MIB)를 보유하고 응답 | 센서 탑재 정보 단말기 |
| SNMP Trap | 임계치 초과나 링크 다운 등 긴급 장애 시 에이전트가 매니저로 즉각 보고하는 비동기 메시지 | 긴급 119 출동 요청 |
| Syslog Severity | 이벤트의 심각도를 0(Emergency)부터 7(Debug)까지 8단계로 분류하여 필터링 전송 지원 | 병원 환자 중증도 분류 |

> 요약: SNMP로 실시간 성능 지표를 폴링(Polling)하고, Syslog로 정밀한 상태 변화 로그를 수집하여 NMS(네트워크 관리 시스템) 구축 핵심을 이룸

## Ⅲ. 절차
```text
+----------+    +----------+    +----------+    +----------+
| 정보 요청| -> | 성능 응답| -> | 장애 발생| -> | 경보 전송|
+----------+    +----------+    +----------+    +----------+
```
1. 정보 요청: NMS(Manager) 서버가 주기적으로 각 장비(Agent)의 특정 OID 값(CPU 점유율 등)을 요청 (Get-Request)
2. 성능 응답: 장비는 MIB DB를 조회하여 현재 값을 평문 혹은 암호화(v3)하여 응답 (Get-Response)
3. 장애 발생: 라우터의 핵심 링크 단절(Link-Down) 등 돌발적이고 심각한 시스템 이벤트 발생
4. 경보 전송: 즉시 SNMP Trap 및 최고 심각도(Level 0)의 Syslog 메시지를 중앙 통합 관제 서버로 자발적 발송

> 요약: 정기적 폴링 수집(Get)과 비정기적 긴급 보고(Trap/Syslog) 메커니즘을 결합한 입체적 관제 수행

## Ⅳ. 문제점
- 초기 SNMP v1/v2c는 인증 시 단순 평문(Community String)을 사용하여 스니핑 시 관리자 권한 즉시 탈취 위험
- 모든 장비를 단주기(Short Interval) 폴링 설정 시 NMS 서버 및 네트워크 자체 대역폭에 심각한 과부하(Overhead) 초래
- Syslog는 기본적으로 신뢰성 없는 UDP(포트 514)를 사용하여 통신 지연 시 중요 장애 로그 유실(Drop) 현상 발생

## Ⅴ. 개선방안
- [단기] 모든 네트워크 장비 설정을 사용자 인증과 페이로드 암호화(AES)를 100% 지원하는 SNMP v3 환경으로 강제 전환
- [중기] 중요 이벤트 로그 수집 장비에 한해 신뢰성 보장을 위한 TCP 기반 Syslog 서버 연결 설정 적용 반영
- [장기] 단순 폴링 방식(Pull)의 한계 극복을 위해 장비가 자체적으로 최신 데이터를 능동 밀어주는 원격 분석(Streaming Telemetry) 도입

## Ⅵ. 전망
- 기존 폴링 방식은 한계에 달해 빅데이터 플랫폼 연동 기반의 실시간 스트리밍 텔레메트리 아키텍처로 완전히 대체될 전망임
