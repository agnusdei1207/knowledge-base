## Ⅰ. 개요
- **정의**: 네트워크 장비·링크·트래픽 상태를 실시간으로 수집·분석하여 장애와 성능 저하를 감지하는 활동임
- **배경/필요성**: 네트워크 장애는 서비스 중단으로 직결되므로 사전 징후를 조기에 포착하여 대응 시간을 단축할 필요가 있음
- **비유**: 환자의 활력징후를 모니터링하여 이상 시 즉시 알람을 울리는 ICU 장비와 유사함

| 출제 의도 | 반드시 짚을 핵심 | 감점 회피 포인트 |
|:---|:---|:---|
| 모니터링 방식(폴링/푸시), 프로토콜 구분 | SNMP(059), NetFlow(060) 역할 분리 | 모니터링 vs 관측성(Observability) 범위 구분 |

> 요약: 네트워크 상태를 실시간 수집·분석하여 장애를 조기 감지하고 대응하는 활동임

## Ⅱ. 구성요소
```text
Agent(장비) --SNMP/Telemetry--> Collector --> 분석 엔진 --> 대시보드/알람
                                    |
                              NetFlow/sFlow 데이터
```

| 구성요소 | 설명 | 비유 |
|:---|:---|:---|
| Agent | 장비에 내장된 데이터 수집 모듈(SNMP Agent, Exporter) | ICU 센서 |
| Collector | 다수 Agent의 데이터를 중앙 수집하는 서버 | 중앙 모니터링 스테이션 |
| 분석 엔진 | 임계값·패턴 기반으로 이상을 판별하는 처리 모듈 | 의료진의 판독 시스템 |
| 대시보드/알람 | 시각화 및 이벤트 알림을 제공하는 인터페이스 | 경보 알람 표시판 |

> 요약: Agent가 데이터를 수집하고 Collector → 분석 엔진 → 대시보드 경로로 가시성을 제공함

## Ⅲ. 절차
```text
데이터 수집 --> 중앙 집계 --> 이상 탐지 --> 알람/대응
```
- 1단계: Agent가 SNMP 폴링 또는 스트리밍 텔레메트리로 장비 상태 데이터를 수집함
- 2단계: Collector가 다수 장비의 메트릭을 시계열 DB에 저장하고 정규화함
- 3단계: 분석 엔진이 임계값 초과·트렌드 이상을 탐지하여 이벤트를 생성함
- 4단계: 대시보드에 시각화하고 알람을 운영자에게 전달하여 조치를 유도함

> 요약: 수집 → 집계 → 이상 탐지 → 알람/대응의 4단계 루프로 운영함

## Ⅳ. 문제점
- 폴링 지연: SNMP 폴링 주기(통상 5분)가 길어 순간 장애를 놓칠 수 있음
- 데이터 과다: 대규모 네트워크에서 메트릭 볼륨이 폭증하여 저장·처리 비용이 증가함
- 알람 피로: 임계값 기반 알람이 과다 발생하면 운영자가 중요 이벤트를 간과함

> 요약: 폴링 지연, 데이터 과다, 알람 피로가 주요 과제임

## Ⅴ. 개선방안
1. 단기: 스트리밍 텔레메트리(gNMI/gRPC) 도입으로 폴링 지연을 초 단위로 단축함
2. 중기: 시계열 DB 압축·샘플링과 계층적 집계로 데이터 볼륨을 관리함
3. 장기: AIOps 기반 이상 탐지와 이벤트 상관 분석으로 알람 품질을 개선함

> 요약: 스트리밍 텔레메트리, 계층적 집계, AIOps 도입으로 단계별 개선이 가능함

## Ⅵ. 전망
- 발전 방향: 관측성(Observability) 개념으로 확장되어 메트릭·로그·트레이스 통합 분석이 표준화됨
- 기술사적 판단: 네트워크 자동화와 결합하여 감지 → 분석 → 자동 복구의 Closed-Loop 운영으로 진화함
- 기술사 제언: 모니터링 설계 시 SNMP(059)·NetFlow(060) 등 프로토콜별 역할을 명확히 분리할 필요가 있음
