## Ⅰ. 개요
- **정의**: IP 주소를 MAC 주소로 변환하는 L2-L3 간 주소 해석 프로토콜
- **배경/필요성**: 이더넷 프레임 전송 시 목적지 MAC 주소가 필수이나 상위 계층은 IP만 알고 있으므로 매핑이 필요함
- **비유**: 아파트 동·호수(IP)를 알지만 실제 현관문 열쇠번호(MAC)를 물어보는 과정과 유사함

| 출제 의도 | 반드시 짚을 핵심 | 감점 회피 포인트 |
|:---|:---|:---|
| L2-L3 주소 매핑 원리 | 브로드캐스트 요청-유니캐스트 응답 | ARP는 동일 서브넷에서만 동작, 라우터 경유 시 Proxy ARP 필요 |

> 요약: 동일 서브넷 내에서 IP-MAC 매핑을 브로드캐스트로 해석하는 프로토콜임

## Ⅱ. 구성요소
```text
Sender(IP_A, MAC_A) ---ARP Request(Broadcast)---> All Hosts
                                                      |
Target(IP_B, MAC_B) ---ARP Reply(Unicast)----------->+
                                                      |
Sender: ARP Cache [IP_B -> MAC_B] 저장               v
```

| 구성요소 | 설명 | 비유 |
|:---|:---|:---|
| ARP Request | 목적지 IP에 대한 MAC 질의를 브로드캐스트로 전송 | 교실에서 "이 번호 누구?" 소리침 |
| ARP Reply | 해당 IP 소유 호스트가 자신의 MAC을 유니캐스트로 응답 | "저요" 하고 손 드는 행위 |
| ARP Cache | IP-MAC 매핑을 일정 시간 저장하는 로컬 테이블 | 메모장에 적어두는 연락처 |
| ARP Header | 하드웨어 타입, 프로토콜 타입, Opcode 등 포함 | 질의서 양식 |

> 요약: 브로드캐스트 질의-유니캐스트 응답-캐시 저장의 3단 구조로 구성됨

## Ⅲ. 절차
```text
Host A           LAN(Broadcast)          Host B
  |---ARP Request(who has IP_B?)----------->|
  |                                         |
  |<--ARP Reply(IP_B is at MAC_B)-----------|
  |                                         |
  [ARP Cache 갱신]                          [ARP Cache 갱신]
```
- 1단계: 송신 호스트가 ARP 캐시에서 목적지 MAC 조회, 미존재 시 요청 생성
- 2단계: ARP Request를 브로드캐스트(`FF:FF:FF:FF:FF:FF`)로 전송
- 3단계: 해당 IP를 가진 호스트가 자신의 MAC 주소를 ARP Reply로 유니캐스트 응답
- 4단계: 송신 호스트가 ARP 캐시에 매핑 저장 후 프레임 전송 개시

> 요약: 캐시 조회-브로드캐스트 질의-유니캐스트 응답-캐시 갱신의 4단계로 동작함

## Ⅳ. 문제점
- ARP 스푸핑: 인증 없이 응답을 수용함 — 공격자가 위조 Reply를 전송하여 트래픽을 가로챌 수 있음
- 브로드캐스트 폭주: 대규모 서브넷에서 ARP 트래픽이 급증함 — 호스트 수 증가 시 브로드캐스트 도메인 부하가 비례 증가
- 캐시 만료 비효율: 타이머 기반 갱신이라 실시간 변경 반영이 지연됨 — IP 재할당 시 구 캐시로 인한 통신 장애 발생

> 요약: 인증 부재, 브로드캐스트 부하, 캐시 비동기가 주요 취약점임

## Ⅴ. 개선방안
1. 단기: Dynamic ARP Inspection(DAI) 적용으로 스위치에서 위조 ARP 차단
2. 중기: 서브넷 분할 및 VLAN 적용으로 브로드캐스트 도메인 축소 (019 참조)
3. 장기: IPv6 환경의 NDP(Neighbor Discovery Protocol) 전환으로 ARP 의존 제거

> 요약: 스위치 검증, 도메인 분할, NDP 전환의 단계적 개선이 필요함

## Ⅵ. 전망
- 발전 방향: IPv6 확산으로 ARP는 NDP로 대체되는 추세임
- 기술사적 판단: 레거시 IPv4 환경이 상당 기간 병존하므로 ARP 보안 대책은 지속 유효함
- 기술사 제언: 듀얼스택 환경에서 ARP와 NDP 양쪽 보안을 동시에 고려하는 설계가 필요함
