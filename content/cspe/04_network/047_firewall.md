## Ⅰ. 개요
- **정의**: 사전 정의된 보안 규칙에 따라 네트워크 트래픽을 허용·차단하는 접근 제어 장비임
- **배경/필요성**: 내부 네트워크와 외부 네트워크 경계에서 비인가 접근을 차단해야 함
- **비유**: 건물 출입구의 경비원이 출입 명부를 확인하고 통과 여부를 결정하는 것과 유사함

| 출제 의도 | 반드시 짚을 핵심 | 감점 회피 포인트 |
|:---|:---|:---|
| 방화벽 세대별 발전·NGFW 특징 | 패킷필터-상태검사-애플리케이션 계층 구분 | IDS/IPS(048)·WAF(049)와 역할 차이 명시 |

> 요약: 네트워크 경계에서 규칙 기반으로 트래픽을 필터링하는 보안 장비임

## Ⅱ. 구성요소
```text
External ---> [Packet Filter] ---> [Stateful Inspection] ---> [App Control] ---> Internal
                                          |
                                     Session Table
```

| 구성요소 | 설명 | 비유 |
|:---|:---|:---|
| Packet Filter | IP/Port 기반으로 개별 패킷의 허용·차단을 판단함 | 주소만 확인하는 검문소 |
| Stateful Inspection | TCP 세션 상태를 추적하여 정상 흐름만 허용함 | 대화 맥락을 기억하는 경비원 |
| Application Control | L7 프로토콜·앱을 식별하여 세분화된 정책을 적용함 | 소지품 내용까지 검사하는 보안관 |
| Policy Rule Base | 출발지·목적지·서비스·행위별 허용/차단 규칙 집합 | 출입 허가 명부 |

> 요약: 패킷필터-상태검사-앱제어의 계층적 구조로 트래픽을 통제함

## Ⅲ. 절차
```text
Packet In -> ACL Lookup -> Stateful Check -> DPI/App ID -> Allow/Deny -> Logging
```
- 1단계: 수신 패킷의 IP 5-tuple(출발지/목적지 IP·Port, 프로토콜)을 ACL과 대조함
- 2단계: 세션 테이블에서 기존 연결 상태를 조회하여 정상 흐름 여부를 판단함
- 3단계: NGFW의 경우 DPI로 애플리케이션을 식별하고 위협 시그니처를 검사함
- 4단계: 정책 매칭 결과에 따라 허용·차단·로깅을 수행함

> 요약: ACL매칭-상태검사-앱식별-정책적용의 4단계로 패킷을 처리함

## Ⅳ. 문제점
- 암호화 트래픽 검사 한계: TLS 암호화 패킷 내부를 검사하지 못하여 위협 은닉 가능
- 규칙 팽창: 운용 기간이 길어질수록 미사용·중복 규칙이 누적되어 관리 곤란
- 내부 위협 미탐지: 경계 기반 모델이므로 내부자 횡이동(Lateral Movement)을 탐지 곤란

> 요약: 암호화 트래픽·규칙 팽창·내부 위협이 방화벽의 구조적 한계임

## Ⅴ. 개선방안
1. 단기: TLS 복호화(SSL Inspection) 기능 활성화로 암호화 트래픽 가시성 확보
2. 중기: 정책 최적화 도구(Rule Analyzer)로 미사용·중복 규칙을 자동 정리함
3. 장기: 마이크로세그멘테이션·제로트러스트 모델로 내부 횡이동 통제 체계 구축

> 요약: SSL Inspection·규칙 최적화·제로트러스트로 한계를 보완함

## Ⅵ. 전망
- 발전 방향: NGFW에 SASE·XDR 기능이 통합되는 플랫폼화 추세임
- 기술사적 판단: 경계 보안의 핵심 역할은 유지하되 ZTNA 보완이 필수임
- 기술사 제언: IDS/IPS(048 참조)·WAF(049 참조)와의 역할 분담 및 통합 운영 전략 수립이 필요함
