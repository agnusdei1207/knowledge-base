# 📖 【암기용】 개념 완전 이해

> 목적: AI 네이티브 네트워킹을 처음 보는 사람도 자동화 네트워크와의 차이를 이해하게 만든다. 시험 답안 양식이 아니라, 이해를 위한 설명이다.

## 한눈에
- **개요**: 네트워크 설계·운영·장애 대응에 AI 모델을 내장해 폐루프 제어를 수행하는 접근이다.
- **왜 필요한가**: 클라우드, 5G, AI 데이터센터는 장비·경로·정책 조합이 많아 사람이 CLI로 변경하면 MTTR과 변경 실패율이 증가한다.
- **핵심 직관**: 관측 데이터를 계속 읽고 장애 원인을 추정한 뒤, 승인된 정책 범위에서 설정을 조정하는 네트워크 운전 보조 장치이다.

## 깊이 이해
- **배경·문제의식**: 기존 NMS는 임계값 경보와 수동 조치에 의존했다. AI 네이티브 네트워킹은 텔레메트리, 로그, 토폴로지, 변경 이력을 학습해 이상 탐지, 원인 분석, 설정 추천, 자동 복구를 연결한다.
- **작동 원리**: 장비가 streaming telemetry와 flow 로그를 보내면 데이터 파이프라인이 특징을 만들고, 모델이 이상 점수와 원인 후보를 산출한다. 정책 엔진은 변경 가능 범위와 승인 단계를 확인한 뒤 컨트롤러가 설정을 배포한다.
- **비유**: 자동차가 엔진 센서, 지도, 운전 패턴을 읽고 차선 유지와 제동 보조를 수행하지만 운전자가 승인 범위를 정하는 구조와 같다.
- **구체 예시**: AI 패브릭에서 RDMA CNP 증가와 ECN 마킹률을 모델이 감지하고, DCQCN 파라미터 조정 또는 경로 우회 후보를 제시한다.
- **흔한 오해·주의점**: AI가 네트워크를 완전 자율 운영한다고 단정하면 위험하다. 변경은 정책, 승인, 롤백, SLO 검증을 거쳐야 한다.

## 연결 개념
- Intent-Based Networking — 의도를 정책으로 선언하고 네트워크 상태를 맞추는 기반
- AIOps — 운영 이벤트를 AI로 분석하는 상위 운영 방법
- Streaming Telemetry — 모델 입력이 되는 실시간 상태 데이터

# 📝 【답안용】 시험 답안 템플릿

> 목적: 시험장에서 25분에 그대로 쓰는 답안 양식. telemetry, AI inference, closed-loop, intent, guardrail을 중심으로 작성한다.
> 핵심: 출제자는 AI 기능 소개가 아니라 운영 지표와 통제 범위를 갖춘 네트워크 자동 제어 설계를 묻는다.

## 핵심 인사이트 (3줄 요약)

> 1. **본질**: AI 네이티브 네트워킹은 텔레메트리와 AI 추론을 네트워크 제어 루프에 내장해 이상 탐지, 원인 분석, 설정 추천을 수행하는 구조이다.
> 2. **가치**: 장애 탐지, 변경 영향 예측, 용량 예측을 MTTR, 변경 실패율, SLO 위반률 지표와 연결한다.
> 3. **판단 포인트**: closed-loop 적용 범위, 승인 단계, rollback, 모델 drift 지표가 없으면 운영 위험이 커진다.

## 출제 의도 및 답안 포인트

| 출제 의도 | 반드시 짚을 핵심 | 감점 회피 포인트 |
|:---|:---|:---|
| AI 기반 네트워크 운영 구조 확인 | telemetry, feature store, inference, policy, controller | AI를 단순 모니터링 대시보드로만 설명 |
| 폐루프 자동화 판단 확인 | Observe, Analyze, Decide, Act, Verify | 사람 승인·롤백·변경 검증 누락 |
| 전망 기술 한계 인식 확인 | 데이터 품질, drift, 설명가능성, 표준화 한계 | 확정 상용 기능처럼 전면 자율 운영으로 단정 |

> 요약: 이 문제는 AI 모델보다 운영 폐루프와 통제 장치를 어떻게 설계하는지가 채점 포인트이다.

## Ⅰ. 개요 및 필요성

- 개요: AI 추론을 네트워크 제어 루프에 내장함.
- 배경: 멀티클라우드, 5G, AI 패브릭은 경로·정책·QoS 조합이 많아 수동 변경 실패가 증가함.
- 필요성: telemetry, flow, syslog, config diff를 결합해 MTTR, 변경 실패율, SLO 위반률을 낮추는 운영 체계가 필요함.
- 판단 기준: closed-loop 범위, 승인 정책, rollback 시간, 모델 drift 감시 여부를 확인함.

---

## Ⅱ. 구조 및 구성요소

```text
Device Telemetry -> Data Lake -> Feature Store -> AI Inference
AI Inference -> Policy Guardrail -> Controller -> Network Device
Controller -> Verification -> Feedback -> Model Monitoring
```

| 구성요소 | 역할 | 특이사항 |
|:---|:---|:---|
| Telemetry | 인터페이스, 경로, 지연, 손실 데이터 수집 | gNMI, NetFlow, syslog |
| AI Inference | 이상 탐지와 원인 후보 산출 | 지도학습, 시계열, 그래프 모델 |
| Policy Guardrail | 변경 가능 범위와 승인 조건 확인 | intent, RBAC, change window |
| Controller | 설정 배포와 롤백 수행 | SDN controller, IaC 연계 |
| Verification | 변경 후 SLO와 장애 여부 확인 | synthetic test, traceroute, p95 지연 |

> 요약: AI 네이티브 네트워킹은 데이터 수집, 추론, 정책 검증, 제어, 결과 검증이 닫힌 루프로 연결된다.

---

## Ⅲ. 동작원리 및 흐름도

```text
상태 관측 -> 이상 탐지 -> 원인 후보 산출 -> 조치 후보 생성
-> 정책·승인 확인 -> 설정 배포 -> SLO 검증 -> 피드백 학습
```

| 단계 | 처리 내용 | 검증 기준 |
|:---:|:---|:---|
| 1 | 장비 텔레메트리와 로그 수집 | 수집 지연, 누락률 |
| 2 | 모델이 이상 점수와 원인 후보 계산 | precision, recall, drift |
| 3 | 정책 엔진이 변경 허용 범위 확인 | RBAC, change window |
| 4 | 컨트롤러가 설정 변경 또는 우회 적용 | config diff, rollback plan |
| 5 | 변경 후 SLO와 사용자 영향 검증 | p95 지연, packet loss |

> 요약: 폐루프는 관측에서 조치까지 자동화하되, 정책 검증과 SLO 확인이 조치의 안전장치 역할을 한다.

## Ⅳ. 특징

| 구분 | 기존 자동화 | AI 네이티브 네트워킹 | 수치·표준 포인트 |
|:---|:---|:---|:---|
| 판단 방식 | 임계값·룰 기반 | 이상 탐지·원인 추론·예측 | precision, recall, F1 |
| 데이터 입력 | SNMP, syslog 중심 | streaming telemetry, flow, config diff | gNMI, NetFlow/IPFIX |
| 제어 구조 | 스크립트 실행 | closed-loop + guardrail | 승인 단계, rollback |
| 한계 | 복잡 패턴 탐지 제한 | 데이터 품질과 drift 영향 | drift score, false positive |

> 요약: AI 네이티브 네트워킹은 룰 기반 자동화를 추론 기반 폐루프로 확장하지만, 모델 검증과 변경 통제가 필수이다.

## Ⅴ. 심화 비교 및 적용 판단

| 구분 | 기존/대안 | AI 네이티브 네트워킹 | 선택 기준 |
|:---|:---|:---|:---|
| 구조 | NMS 경보와 수동 조치 | telemetry, inference, controller 폐루프 | 장비 수 1,000대 이상, 경보 상관분석 필요 시 |
| 비용/성능 | 운영자 분석 시간 증가 | 모델 학습·데이터 파이프라인 비용 발생 | MTTR 30% 이상 감소 목표 |
| 운영/위험 | 변경 책임 명확 | 자동 조치 오판 가능 | 승인 단계, canary, rollback 조건 |

> 요약: AI 적용은 자동 조치 범위를 제한하고 MTTR, 변경 실패율, SLO 위반률로 효과를 판단해야 한다.

| 리스크 | 원인 | 대응 방안 | 확인 지표 |
|:---|:---|:---|:---|
| 오탐 조치 | 모델 precision 부족 | shadow mode, human approval | 오탐 조치율 |
| 모델 drift | 트래픽 패턴 변화 | drift 감시, 재학습 주기 | drift score, F1 변화 |
| 장애 확산 | 잘못된 설정 일괄 배포 | canary, blast radius 제한 | 롤백 시간, 영향 장비 수 |

> 요약: 모델 오판은 운영 변경 사고로 이어지므로 shadow mode와 제한 배포로 통제한다.

| 점검 항목 | 목표 기준 | 측정 방법 |
|:---|:---|:---|
| 탐지 품질 | precision 90% 이상 | 라벨링 사건 대조 |
| 운영 효과 | MTTR 30% 이상 감소 | 장애 티켓 분석 |
| 변경 통제 | rollback 5분 이내 | config version 로그 |

> 요약: 성공 여부는 모델 정확도와 함께 장애 복구시간, 롤백 시간, SLO 지표로 판단한다.

## Ⅵ. 실무 적용 및 결론

**적용 방안 3개 (필수):**
1. 초기 3개월은 shadow mode로 AI 추천만 기록하고 운영자 조치 결과와 비교해 precision, recall을 산정함.
2. closed-loop 조치는 저위험 정책부터 적용하고, 경로 변경·ACL 변경은 승인 단계와 canary 배포를 요구함.
3. gNMI, NetFlow/IPFIX, syslog, config diff를 동일 시간축으로 저장하고 모델 drift와 SLO 변화를 매주 점검함.

**결론 (2줄):**
- 기술사 판단: AI 네이티브 네트워킹은 대규모·동적 네트워크에 적합하지만, 자동 조치는 guardrail과 rollback이 준비된 범위부터 적용해야 함.
- 향후 방향: intent, digital twin, AIOps가 결합되어 조치 전 시뮬레이션과 폐루프 검증 중심으로 발전함.
