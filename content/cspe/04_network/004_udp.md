## Ⅰ. 개요
- **정의**: 비연결형·비신뢰성 전송 계층 프로토콜로 최소 오버헤드 데이터그램 전송을 제공함
- **배경/필요성**: TCP(003 참조)의 연결 수립·흐름 제어 오버헤드가 실시간 서비스에 부적합하여 경량 전송이 필요함
- **비유**: 우체통에 편지를 넣으면 수신 확인 없이 배달되는 일반 우편과 동일함

| 출제 의도 | 반드시 짚을 핵심 | 감점 회피 포인트 |
|:---|:---|:---|
| UDP 특성과 적용 사례 이해 | 헤더 구조(8바이트), 비연결·비순서 보장 | "신뢰성 없음 = 쓸모없음"으로 서술하면 감점 |

> 요약: 연결 수립 없이 최소 헤더로 빠른 전송을 제공하는 경량 프로토콜임

## Ⅱ. 구성요소
```text
UDP Header (8 bytes)
+------------+------------+
| Src Port   | Dst Port   |  (각 2 bytes)
+------------+------------+
| Length     | Checksum    |  (각 2 bytes)
+------------+------------+
|        Payload           |
+--------------------------+
```

| 구성요소 | 설명 | 비유 |
|:---|:---|:---|
| Source Port | 송신 애플리케이션 식별 번호 | 발신자 전화번호 |
| Destination Port | 수신 애플리케이션 식별 번호 | 수신자 전화번호 |
| Length | UDP 헤더+페이로드 전체 길이(바이트) | 편지 봉투의 무게 표시 |
| Checksum | 데이터 무결성 검증용 값(선택적) | 봉투 봉인 스티커 |

> 요약: 8바이트 고정 헤더로 포트·길이·체크섬만 포함하는 최소 구조임

## Ⅲ. 절차
```text
Application --> UDP --> IP --> Network
    |            |       |        |
  Data     +Header(8B) +IP Hdr  Frame
           (no handshake, no ACK)
```
- 1단계: 애플리케이션이 데이터와 목적지 포트를 UDP에 전달
- 2단계: UDP가 8바이트 헤더를 부착하여 데이터그램 생성
- 3단계: IP 계층에서 목적지 주소 기반 라우팅 수행
- 4단계: 수신측 UDP가 포트 번호로 해당 애플리케이션에 데이터 전달

> 요약: 연결 수립 없이 헤더 부착→라우팅→포트 기반 전달의 단순 흐름임

## Ⅳ. 문제점
- 데이터 유실: 재전송 메커니즘 부재 — 패킷 손실 시 애플리케이션이 별도 복구해야 함
- 순서 미보장: 시퀀스 번호 부재 — 패킷 도착 순서가 송신 순서와 다를 수 있음
- 흐름 제어 부재: 수신측 버퍼 초과 시 데이터 폐기 — 송수신 속도 불일치 시 손실 증가

> 요약: 신뢰성·순서·흐름 제어가 프로토콜 수준에서 미지원됨

## Ⅴ. 개선방안
1. 단기: 애플리케이션 계층에서 ACK·재전송 로직 구현으로 유실 복구
2. 중기: RTP/RTCP 등 상위 프로토콜 적용으로 시퀀싱·지터 보정 수행
3. 장기: QUIC 프로토콜 채택으로 UDP 기반 신뢰성·흐름 제어·멀티플렉싱 확보

> 요약: 애플리케이션 보완, 상위 프로토콜, QUIC 전환으로 단계적 신뢰성 확보가 필요함

## Ⅵ. 전망
- 발전 방향: QUIC(HTTP/3)이 UDP 위에 신뢰성을 구현하여 UDP 활용 범위가 확대 중
- 기술사적 판단: IoT 센서·실시간 스트리밍 등 경량 전송 수요 증가로 UDP 중요성이 지속됨
- 기술사 제언: UDP 기반 서비스 설계 시 애플리케이션 수준 오류 복구 전략 수립이 필수임
