# 📖 【암기용】 개념 완전 이해

> 목적: STIX와 TAXII를 처음 보는 사람도 위협 인텔리전스 교환 구조를 이해하게 만든다. 시험 답안 양식이 아니라, 이해를 위한 설명이다.

## 한눈에
- **개요**: STIX는 위협 정보를 표현하는 JSON 언어이고, TAXII는 그 정보를 교환하는 HTTPS API이다.
- **왜 필요한가**: 침해지표, 공격기법, 캠페인 정보가 조직마다 다른 형식이면 SIEM·SOAR·EDR 자동 연계가 막힌다.
- **핵심 직관**: STIX는 표준 양식의 사건 카드이고, TAXII는 그 카드를 구독자에게 배달하는 우편함이다.

## 깊이 이해
- **배경·문제의식**: 기존 IOC 공유는 CSV, PDF, 메일 본문처럼 형식이 달라 기계 처리가 어려웠다. STIX 2.1은 indicator, malware, attack-pattern, relationship 같은 객체로 정보를 구조화한다.
- **작동 원리**: 생산자는 STIX Bundle에 객체와 관계를 담고, TAXII 2.1 서버는 Discovery, API Root, Collections, Objects 엔드포인트로 배포한다. 소비자는 컬렉션을 조회해 변경분을 가져와 탐지 룰과 대응 플레이북으로 변환한다.
- **비유**: 병원 간 감염병 정보를 보낼 때 질병명·감염경로·대응조치를 같은 서식으로 쓰고, 보건망 포털이 그 서식을 배포하는 구조와 같다.
- **구체 예시**: 랜섬웨어 캠페인에서 SHA-256 해시, C2 도메인, MITRE ATT&CK T1059 관계를 STIX 객체로 표현하고 TAXII Collection에서 15분 주기로 수집한다.
- **흔한 오해·주의점**: STIX·TAXII는 탐지 엔진 자체가 아니다. 신뢰도, 만료시간, 오탐 검증, 내부 자산 매핑이 없으면 많은 IOC가 경보 피로도를 만든다.

## 연결 개념
- CTI (Cyber Threat Intelligence) — 전략·전술·기술 인텔리전스의 상위 개념
- SIEM·SOAR — STIX 수집 결과를 탐지·대응 절차로 실행하는 운영 플랫폼
- MITRE ATT&CK — attack-pattern 객체와 전술·기법 매핑에 사용되는 지식베이스

# 📝 【답안용】 시험 답안 템플릿

> 목적: 시험장에서 25분에 그대로 쓰는 답안 양식. STIX 2.1, TAXII 2.1, IOC 품질 통제, 자동 대응 연계를 중심으로 작성한다.
> 핵심: 출제자는 표준명 암기가 아니라 위협 정보 표현, 전송, 검증, 대응 자동화의 전 과정을 묻는다.

## 핵심 인사이트 (3줄 요약)

> 1. **본질**: STIX 2.1은 위협 정보를 객체·관계로 표현하고 TAXII 2.1은 HTTPS 기반 API로 배포하는 CTI 교환 표준이다.
> 2. **가치**: IOC를 기계 판독 가능한 JSON으로 공유해 SIEM 룰, EDR 차단, SOAR 플레이북 입력으로 연결한다.
> 3. **판단 포인트**: 신뢰도, 만료시간, 출처 검증, 내부 자산 영향도를 함께 관리해야 오탐과 경보 피로도를 줄인다.

## 출제 의도 및 답안 포인트

| 출제 의도 | 반드시 짚을 핵심 | 감점 회피 포인트 |
|:---|:---|:---|
| CTI 표준 구조 이해 확인 | STIX 객체·관계, TAXII Collection·Objects API | STIX를 전송 프로토콜로 쓰거나 TAXII를 데이터 모델로 쓰는 혼동 |
| 보안운영 자동화 판단 확인 | SIEM·SOAR·EDR 연계, IOC 품질 관리 | IOC 수집만 쓰고 검증·만료·오탐 통제 누락 |
| 표준 기반 공유 한계 확인 | STIX 2.1, TAXII 2.1, TLP, 신뢰도 점수 | 공개 피드 적용을 내부 차단으로 즉시 연결하는 단정 |

> 요약: 이 문제는 CTI를 수집 자료가 아니라 표준 표현, 안전한 교환, 운영 검증까지 포함한 자동화 체계로 설명해야 한다.

## Ⅰ. 개요 및 필요성

- 개요: STIX는 표현, TAXII는 교환 표준임.
- 배경: 조직별 IOC 형식이 다르면 SIEM·EDR·SOAR 자동 연계가 지연됨.
- 필요성: STIX 2.1 JSON 객체와 TAXII 2.1 HTTPS API로 위협정보 수집 주기를 15분 단위로 운영 가능함.
- 판단 기준: 신뢰도 70점 이상, 만료일 포함, TLP 색상, 내부 자산 영향도 매핑 여부를 확인함.

---

## Ⅱ. 구조 및 구성요소

```text
Threat Source -> STIX Bundle -> TAXII Server -> Collection -> SIEM/SOAR/EDR
                       +-> Object Relationship
                       +-> Confidence / TLP / Valid Until
```

| 구성요소 | 역할 | 특이사항 |
|:---|:---|:---|
| STIX Object | indicator, malware, attack-pattern 등 위협 요소 표현 | JSON, STIX 2.1 사용 |
| Relationship | 공격자·기법·지표 간 관계 표현 | uses, indicates, targets 관계 사용 |
| TAXII Collection | 구독 단위로 객체 저장·조회 | Discovery, API Root, Objects 엔드포인트 |
| Consumer | SIEM·SOAR·EDR이 피드 수집 | 룰 변환, 차단, 티켓 생성 수행 |

> 요약: STIX는 위협 정보를 구조화하고 TAXII는 컬렉션 단위로 배포하며, 운영 도구는 이를 탐지·대응 입력으로 사용한다.

---

## Ⅲ. 동작원리 및 흐름도

```text
피드 생산 -> STIX 객체 생성 -> TAXII Collection 게시
-> 소비자 변경분 조회 -> 신뢰도·만료 검증 -> 탐지 룰 배포 -> 경보·대응 기록
```

| 단계 | 처리 내용 | 검증 기준 |
|:---:|:---|:---|
| 1 | 위협 출처에서 IOC·TTP 수집 | 출처, 수집시각, TLP 확인 |
| 2 | STIX Bundle에 객체와 관계 저장 | STIX 2.1 스키마 검증 |
| 3 | TAXII Collection으로 배포 | HTTPS, 인증 토큰, 객체 버전 확인 |
| 4 | SIEM·EDR에서 탐지 룰 변환 | 오탐률, 만료일, 내부 자산 매핑 |
| 5 | SOAR가 티켓·차단·보고 실행 | 평균 대응시간, 재발 경보 수 |

> 요약: CTI 운영은 수집에서 끝나지 않고 스키마 검증, 신뢰도 필터링, 탐지 배포, 대응 기록까지 이어진다.

## Ⅳ. 특징

| 구분 | 기존 IOC 공유 | STIX·TAXII | 수치·표준 포인트 |
|:---|:---|:---|:---|
| 표현 방식 | CSV·메일·PDF | STIX 2.1 JSON 객체·관계 | indicator, malware, relationship |
| 교환 방식 | 수동 다운로드 | TAXII 2.1 HTTPS API | Collection, Objects API |
| 운영 통제 | 출처·만료 누락 가능 | confidence, valid_until, TLP 관리 | 신뢰도 점수·만료일 필터 |
| 한계 | 자동화 낮음 | 피드 품질에 따라 오탐 발생 | 오탐률, 중복 IOC 비율 점검 |

> 요약: STIX·TAXII는 CTI 공유를 기계 처리 구조로 바꾸지만, 품질 점검 없는 자동 차단은 운영 리스크를 만든다.

## Ⅴ. 심화 비교 및 적용 판단

| 비교 축 | 기존/대안 | STIX·TAXII | 선택 기준 |
|:---|:---|:---|:---|
| 구조 | 파일 기반 IOC 전달 | 객체·관계·컬렉션 기반 교환 | 다기관 공유, 자동 룰 배포 필요 시 |
| 비용/성능 | 수동 분석 시간 증가 | API 수집, 중복 제거, 델타 조회 | 일 IOC 10만 건 이상이면 자동화 필요 |
| 운영/위험 | 담당자 판단 의존 | 신뢰도·만료·TLP 정책 기반 처리 | 오탐률 1% 이하, 만료 누락 0건 목표 |

> 요약: 다수 피드를 반복 수집하는 조직은 STIX·TAXII를 선택하되, 신뢰도와 만료 정책을 먼저 설계해야 한다.

| 리스크 | 원인 | 대응 방안 | 확인 지표 |
|:---|:---|:---|:---|
| 오탐 증가 | 낮은 신뢰도 IOC 자동 차단 | confidence 임계값, 샌드박스 재검증 | 오탐률, 해제 티켓 수 |
| 중복 경보 | 여러 피드가 같은 지표 제공 | indicator ID·값 기준 중복 제거 | 중복 IOC 비율 |
| 정보 유출 | TLP 제한 위반 공유 | TLP:AMBER 이상 외부 전송 차단 | TLP 위반 로그 0건 |

> 요약: CTI 품질 리스크는 신뢰도 필터, 중복 제거, TLP 접근통제로 통제한다.

| 점검 항목 | 목표 기준 | 측정 방법 |
|:---|:---|:---|
| 피드 품질 | valid_until 포함률 95% 이상 | STIX 스키마 검사 |
| 탐지 효과 | IOC 적중 경보 중 확인된 침해 비율 | SIEM 사건 태깅 |
| 운영 통제 | 피드 수집 지연 15분 이하 | TAXII API 수집 로그 |

> 요약: 도입 성과는 피드 양이 아니라 스키마 품질, 확인된 침해 비율, 수집 지연으로 판단한다.

## Ⅵ. 실무 적용 및 결론

**적용 방안 3개 (필수):**
1. TAXII 2.1 Collection을 피드별로 분리하고 API 토큰, mTLS, TLP 정책을 적용함.
2. STIX 2.1 indicator는 confidence 70점 이상, valid_until 존재, 내부 자산 매핑 완료 조건으로 SIEM 룰에 반영함.
3. SOAR 플레이북은 탐지, 샌드박스 재검증, EDR 격리, 티켓 기록을 단계별 승인 흐름으로 구성함.

**결론 (2줄):**
- 기술사 판단: 다기관 CTI 공유와 자동 탐지가 필요하면 STIX·TAXII를 선택하고, 자동 차단은 신뢰도·만료·자산 영향도 조건을 만족할 때만 적용함.
- 향후 방향: CTI는 ATT&CK, SBOM, 취약점 인텔리전스와 결합해 탐지 우선순위 산정 체계로 발전함.
