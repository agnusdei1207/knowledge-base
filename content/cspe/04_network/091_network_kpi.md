# 📖 【암기용】 개념 완전 이해

> 목적: 네트워크 성능 지표를 처음 봐도 지연·지터·대역폭·패킷 손실의 차이를 이해하게 만든다. 시험 답안 양식이 아니라, 장애 판단의 눈을 만드는 설명이다.

## 한눈에
- **개요**: 네트워크 품질을 지연·지터·대역폭·패킷 손실로 수치화한 운영 지표
- **왜 필요한가**: 사용자는 "느림"으로 표현하지만 원인은 RTT 증가, 지터 30ms 초과, 손실 1% 이상, 가용 대역폭 부족으로 나뉜다.
- **핵심 직관**: 도로 품질을 이동 시간·시간 흔들림·차선 수·사고율로 나누어 보는 것과 같다.

## 깊이 이해
- **배경·문제의식**: 네트워크 장애는 CPU나 메모리처럼 한 지표로 설명되지 않는다. 음성은 지터와 손실, 파일 전송은 처리량과 재전송, 게임은 RTT p95가 체감 품질을 좌우한다.
- **작동 원리**: 지연은 패킷이 출발해 응답까지 걸린 시간이고, 지터는 패킷 간 지연 편차다. 대역폭은 링크의 이론 용량, 처리량은 실제 전송량이며, 패킷 손실은 전송 중 사라진 비율이다.
- **비유**: 버스가 10분마다 와야 하는데 어떤 날은 1분, 어떤 날은 25분이면 평균 대기시간보다 시간 흔들림이 문제다. 이것이 지터다.
- **구체 예시**: VoIP는 one-way delay 150ms 이하, jitter 30ms 이하, packet loss 1% 이하를 목표로 잡는다. 영상회의는 p95 RTT 300ms 초과 시 음성 끊김과 화면 지연이 함께 보인다.
- **흔한 오해·주의점**: 대역폭 1Gbps 링크라고 실제 처리량이 1Gbps인 것은 아니다. TCP 윈도우, RTT, 손실률, QoS 정책이 실제 goodput을 제한한다.

## 연결 개념
- QoS — DSCP·큐잉·셰이핑으로 KPI 목표를 보장
- TCP 혼잡제어 — 손실과 RTT 변동이 처리량을 결정
- 네트워크 모니터링 — KPI 수집·시각화·경보 기준 제공

# 📝 【답안용】 시험 답안 템플릿

> 목적: 시험장에서 25분에 그대로 쓰는 답안 양식. 작성방식(추상표현 금지·수치·도식·문제유형 전환)을 엄격히 지킨다.
> 핵심: KPI 명칭 나열이 아니라 서비스 유형별 체감 품질과 측정 지표를 연결해야 한다.

## 핵심 인사이트 (3줄 요약)

> 1. **본질**: Network KPI는 지연(Latency), 지터(Jitter), 대역폭(Bandwidth), 패킷 손실(Packet Loss)로 네트워크 품질을 수치화하는 기준이다.
> 2. **가치**: SLA, QoS, 장애 분석에서 p95 latency, jitter ms, loss %, throughput Mbps를 공통 언어로 사용한다.
> 3. **판단 포인트**: 서비스별 민감 지표가 달라 VoIP는 지터·손실, 트랜잭션은 p95 지연, 백업은 처리량 중심으로 판단한다.

## 출제 의도 및 답안 포인트

| 출제 의도 | 반드시 짚을 핵심 | 감점 회피 포인트 |
|:---|:---|:---|
| 네트워크 품질 지표 구분 역량 확인 | latency, jitter, bandwidth, throughput, packet loss 차이 | 대역폭과 처리량을 같은 의미로 서술 |
| 서비스 유형별 SLA 판단 확인 | VoIP jitter 30ms, loss 1%, 웹 p95 latency 300ms | 평균값만 쓰고 p95·p99 누락 |
| 장애 원인 분석 능력 확인 | 재전송, 큐잉 지연, 혼잡, QoS drop 연결 | 단일 지표만 보고 원인 단정 |

> 요약: 이 문제는 네트워크 KPI를 서비스 체감 품질과 운영 임계치로 연결하는지를 확인한다.

---

## Ⅰ. 개요 및 필요성

Network KPI는 네트워크 품질을 수치로 측정하는 기준이다. 사용자의 "느림"은 p95 RTT, 지터, 손실률, 처리량 중 어떤 값이 임계치를 넘었는지로 분해해야 한다. SLA 위반 판단과 QoS 정책 검증에는 평균보다 p95·p99, 손실률, 재전송률이 필요하다.

---

## Ⅱ. 구조 및 구성요소

```text
서비스 요구 -> Latency / Jitter / Bandwidth / Packet Loss
          -> 측정 도구 -> SLA 기준 -> QoS 정책 -> 개선 검증
```

| 구성요소 | 역할 | 특이사항 |
|:---|:---|:---|
| 지연 | 패킷 왕복 또는 단방향 전송 시간 측정 | RTT, one-way delay, p95·p99 |
| 지터 | 연속 패킷 지연 편차 측정 | VoIP 목표 30ms 이하 |
| 대역폭·처리량 | 링크 용량과 실제 전송량 구분 | bandwidth, throughput, goodput |
| 패킷 손실 | 전송 실패 비율 측정 | TCP 재전송, UDP 음성 끊김 |

> 요약: KPI는 시간, 편차, 용량, 손실을 분리해 서비스 품질을 해석하게 해준다.

---

## Ⅲ. 동작원리 및 흐름도

```text
패킷 송신 -> 타임스탬프/카운터 수집 -> 지표 계산
-> SLA 임계치 비교 -> 경보/원인 분석 -> QoS 조정
```

| 단계 | 처리 내용 | 검증 기준 |
|:---:|:---|:---|
| 1 | ICMP, TWAMP, iPerf, NetFlow로 측정값 수집 | 1분·5분 단위 샘플 |
| 2 | RTT, jitter, throughput, loss % 계산 | p95·p99 분리 산출 |
| 3 | 서비스별 SLA와 비교 | VoIP jitter 30ms, loss 1% |
| 4 | 혼잡·큐잉·링크 장애 원인 분류 | interface drop, TCP retransmit |
| 5 | QoS, 증설, 라우팅 변경 후 재측정 | 임계치 이하 지속 24시간 |

> 요약: KPI 운영은 측정, 계산, 임계치 비교, 원인 분류, 재검증 순서로 진행된다.

---

## Ⅳ. 특징

| 구분 | 기존/대안 | Network KPI | 수치 컬럼 |
|:---|:---|:---|:---|
| 관찰 방식 | 사용자 민원 중심 | p95 latency, jitter, loss % 중심 | RTT 300ms, jitter 30ms |
| 용량 판단 | 회선 속도만 확인 | throughput·goodput 분리 | 1Gbps 링크, 700Mbps goodput |
| 장애 판단 | 평균 응답시간 중심 | p99와 재전송률 동시 확인 | TCP retransmit 3% |
| 운영 연계 | 사후 장애 대응 | SLA·QoS·증설 기준화 | loss 1% 초과 경보 |

> 요약: Network KPI는 체감 품질을 평균값이 아니라 분위수·손실률·처리량 조합으로 판단하게 한다.

---

## Ⅴ. 심화 비교 및 적용 판단

| 비교 축 | 기존/대안 | 본 키워드 | 선택 기준 |
|:---|:---|:---|:---|
| 품질 측정 | ping 평균값 | p95·p99 RTT, jitter, loss % | 실시간 서비스 포함 시 분위수 채택 |
| 용량 관리 | 링크 사용률 | throughput, goodput, retransmit | 사용률 70% 이상 지속 시 증설 검토 |
| 운영 기준 | 장애 후 수동 확인 | SLA 임계치 기반 경보 | 5분 연속 초과 시 티켓 생성 |

> 요약: KPI 선택은 서비스 민감도와 운영 자동화 수준에 맞춰 분위수·손실·처리량을 조합한다.

| 리스크 | 원인 | 대응 방안 | 확인 지표 |
|:---|:---|:---|:---|
| 평균값 착시 | 순간 지연 은폐 | p95·p99 대시보드 분리 | p99 RTT 500ms 초과 |
| 손실 원인 오판 | 무선 오류·혼잡·ACL drop 혼재 | interface counter, TCP retransmit 대조 | CRC error, drop packet |
| 과도한 경보 | 임계치·기간 미조정 | 5분 이동평균, 서비스별 SLA | alert noise 월 10건 이하 |

> 요약: KPI 운영 리스크는 측정 방식과 임계치 설계에서 발생하므로 분위수와 카운터를 함께 확인한다.

| 점검 항목 | 목표 기준 | 측정 방법 |
|:---|:---|:---|
| 지연·지터 | 웹 p95 RTT 300ms 이하, VoIP jitter 30ms 이하 | synthetic probe, TWAMP |
| 손실·재전송 | packet loss 1% 이하, TCP retransmit 3% 이하 | NetFlow, packet capture |
| 용량·처리량 | 링크 사용률 70% 이하, goodput 목표 대비 90% | SNMP ifHCInOctets, iPerf3 |

> 요약: 성공 여부는 지연·손실·처리량이 서비스 SLA 임계치 안에 머무는지로 판단한다.

## Ⅵ. 실무 적용 및 결론

**적용 방안 3개 (필수 — 단계별 또는 항목별):**
1. 서비스별 KPI 기준 수립: VoIP jitter 30ms·loss 1%, 웹 p95 RTT 300ms, 백업 throughput 800Mbps 등으로 분리
2. 측정 체계 구축: SNMP ifHCInOctets, NetFlow v9/IPFIX, synthetic probe를 1분 단위로 수집
3. 개선 루프 운영: QoS DSCP, 큐잉, 회선 증설 후 p95·loss %를 24시간 재측정

**결론 (2줄):**
- 기술사 판단: 실시간 서비스는 지터·손실, 데이터 전송은 throughput·retransmit 중심으로 KPI를 선택해야 함
- 향후 방향: AI 기반 이상탐지와 SLO 경보를 결합해 장애 전 5분 이상 선행 징후를 포착하는 방향
