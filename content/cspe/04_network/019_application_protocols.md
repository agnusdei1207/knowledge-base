## Ⅰ. 개요
- **정의**: 사용자가 직접 체감하는 네트워크 서비스 기능을 제공하기 위해 L7에서 동작하는 표준 규약임.
- **배경 및 필요성**: 웹 브라우징, 파일 전송, 주소 변환 등 서비스 성격에 특화된 메시지 교환 규칙 및 포맷 표준화.
- **출제 의도**: HTTP, FTP, DNS 등 핵심 서비스별 특징(비상태성, 제어/데이터 채널 분리) 및 프로토콜 설계 분석 역량 평가

## Ⅱ. 구성요소

```text
+-------------------------+
|  Component Architecture |
+-------------------------+
| [ Node A ] <-> [ Node B]|
+-------------------------+
```

| 구성요소 | 설명 | 비유 |
|---|---|---|
| **HTTP** | HTML/JSON 등 자원을 요청/응답하는 비상태(Stateless) 기반 웹 규약 | 식당에서 메뉴판을 보고 주문하기 |
| **FTP** | 제어(21)와 데이터(20) 포트를 분리하여 대용량 파일을 전송하는 규약 | 컨베이어 전용 화물 수송 라인 |
| **DNS** | 도메인 주소를 IP로 변환하여 기계 간 통신을 가능하게 하는 이름 규약 | 이름으로 번호를 찾는 전화번호부 |

> 요약: HTTP는 웹 서비스, FTP는 대용량 데이터 전송, DNS는 직관적인 주소 변환의 뼈대 역할을 수행함.

## Ⅲ. 절차

```text
+-------+   +-------+   +-------+   +-------+
| Step1 |-->| Step2 |-->| Step3 |-->| Step4 |
+-------+   +-------+   +-------+   +-------+
```

1. **[DNS 변환] URL 입력 시 접속할 도메인 주소를 DNS에 질의하여 실제 목적지 IP 획득.**: [DNS 변환] URL 입력 시 접속할 도메인 주소를 DNS에 질의하여 실제 목적지 IP 획득.
2. **[TCP 수립] 획득한 IP 주소와 서비스 포트(80, 21 등)를 향해 전송 계층 통신 세션 확립.**: [TCP 수립] 획득한 IP 주소와 서비스 포트(80, 21 등)를 향해 전송 계층 통신 세션 확립.
3. **[응용 메시지 교환] HTTP GET/POST 요청을 전송하거나 FTP 제어 명령으로 파일 전송 개시.**: [응용 메시지 교환] HTTP GET/POST 요청을 전송하거나 FTP 제어 명령으로 파일 전송 개시.
4. **[상태/연결 제어] 요청 완료 후 연결을 즉시 종료하거나, 효율성을 위해 Keep-Alive 세션 유지.**: [상태/연결 제어] 요청 완료 후 연결을 즉시 종료하거나, 효율성을 위해 Keep-Alive 세션 유지.

> 요약: DNS IP 변환, L4 세션 수립 단계를 거친 뒤 서비스 목적에 맞는 응용 메시지 구조로 통신함.

## Ⅳ. 문제점
- HTTP 프로토콜의 평문 전송 취약점 (원인: 데이터 암호화 없이 전송되어 중간자 스니핑 시 개인정보 탈취)
- FTP Active 모드 방화벽 제약 (원인: 서버가 클라이언트로 능동 연결을 시도해 사내 방화벽 및 NAT 인프라에서 막힘)
- HTTP 비상태성(Stateless) 제약 (원인: 매 요청이 독립적이어서 사용자 로그인 등 연속적 상태 유지가 불가능함)

## Ⅴ. 개선방안
- **단기 방안**: [단기] FTP Passive 모드 구동 설정 (클라이언트 주도 데이터 연결로 방화벽 이슈를 회피하며 서비스 정상화)
- **중기 방안**: [중기] 토큰 및 세션 기반 상태 유지 구현 (비상태성 한계 극복을 위해 Cookie 또는 JWT 토큰을 응용 헤더에 부여)
- **장기 방안**: [장기] 전면적 애플리케이션 암호화 적용 (HTTPS 및 SFTP 필수 적용으로 모든 응용 계층 트래픽 통신의 종단 간 기밀성 보장)

## Ⅵ. 전망
- 최근 클라우드와 RESTful 아키텍처의 확산으로, 별도의 FTP를 두지 않고 웹 기반 단일 프로토콜로 통합되는 추세임.
