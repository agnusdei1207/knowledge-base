## Ⅰ. 개요
- **정의**: 네트워크 장비 접속 시 인증·인가·과금(AAA)을 중앙 서버에서 처리하는 프로토콜
- **배경/필요성**: 다수 네트워크 장비의 접근 정책을 개별 관리하면 일관성 유지가 불가능하므로 중앙 AAA가 필요함
- **비유**: 건물마다 별도 출입증 대신 하나의 통합 출입관리 시스템으로 모든 건물을 관리하는 것과 유사함

| 출제 의도 | 반드시 짚을 핵심 | 감점 회피 포인트 |
|:---|:---|:---|
| RADIUS와 TACACS+ 비교 | 전송 프로토콜·암호화 범위·AAA 분리 여부 차이 | RADIUS는 UDP, TACACS+는 TCP 사용 구분 |

> 요약: AAA 기능을 중앙 서버에 위임하는 네트워크 인증 프로토콜임

## Ⅱ. 구성요소
```text
사용자 --> NAS(Network Access Server) --> AAA Server
              |                              |
         접근요청 전달              인증DB 조회/정책적용
```

| 구성요소 | 설명 | 비유 |
|:---|:---|:---|
| AAA Server | 인증·인가·과금 처리를 수행하는 중앙 서버 | 통합 출입관리 본부 |
| NAS | 사용자 접근을 AAA 서버에 중계하는 네트워크 장비 | 각 건물 출입문 |
| 인증 DB | 사용자 계정·권한·정책 정보를 저장하는 디렉터리 | 출입 허가자 명부 |
| Shared Secret | NAS-AAA Server 간 통신 무결성을 보장하는 공유 비밀키 | 출입문-본부 간 인증 암호 |

> 요약: AAA Server-NAS-인증DB-공유키 4요소로 중앙 인증 체계를 구성함

## Ⅲ. 절차
```text
접근요청 -> NAS중계 -> AAA인증/인가 -> 결과적용
```
- 1단계: 접근 요청 — 사용자가 NAS(스위치·VPN 등)에 접속을 시도함
- 2단계: NAS 중계 — NAS가 사용자 자격증명을 AAA 서버에 전달함
- 3단계: AAA 인증·인가 — 서버가 인증 DB를 조회하여 인증 후 권한 수준을 결정함
- 4단계: 결과 적용 — NAS가 AAA 서버의 응답에 따라 접근 허용·거부·제한을 적용함

> 요약: 요청-중계-인증인가-적용 4단계로 중앙 집중 접근 제어를 수행함

## Ⅳ. 문제점
- RADIUS 암호화 한계: 패스워드 필드만 암호화하여 나머지 페이로드 노출 — 도청 위험 존재
- 단일 장애점: AAA 서버 장애 시 전체 네트워크 접근 인증 불가 — 서비스 중단 발생
- 프로토콜 혼재: RADIUS·TACACS+ 혼용 시 정책 일관성 유지 곤란 — 관리 복잡성 증가

> 요약: 암호화 범위·단일장애점·프로토콜 혼재가 핵심 문제임

## Ⅴ. 개선방안
1. 단기: RadSec(RADIUS over TLS) 적용으로 전체 페이로드 암호화 달성
2. 중기: AAA 서버 이중화 및 장애 시 로컬 인증 Fallback 구성으로 가용성 확보
3. 장기: 통합 AAA 플랫폼 도입으로 프로토콜 추상화 및 정책 일원화 달성

> 요약: TLS암호화·이중화·통합플랫폼으로 개선함

## Ⅵ. 전망
- 발전 방향: 클라우드 기반 IDaaS와 AAA 통합으로 온프레미스·클라우드 일원화가 진행됨
- 기술사적 판단: ZTNA 환경에서 AAA는 지속적 인증의 핵심 인프라 역할을 수행함
- 기술사 제언: 멀티클라우드 환경에서 AAA 정책 일관성 유지를 위한 표준화 전략이 필요함
