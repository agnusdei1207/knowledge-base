## 핵심 인사이트 (3줄 요약)
> 1. **본질**: TLS 1.3은 인터넷 암호화 통신의 표준 규약으로, 구버전(TLS 1.2)의 취약한 암호화 알고리즘을 과감히 폐기하고 보안성을 극대화함과 동시에 연결 속도를 혁신적으로 끌어올린 차세대 보안 프로토콜이다.
> 2. **원리**: 기존 2번의 왕복(2-RTT)이 필요했던 키 교환 과정을, 접속 요청(Client Hello) 시점부터 미리 계산된 키 재료를 던져버리는 방식으로 **1-RTT** 만에 연결을 완료하며, 재접속 시에는 **0-RTT** 전송을 지원한다.
> 3. **판단 포인트**: 정적 RSA 키 교환 방식이 폐지되고 **PFS(완벽한 순방향 비밀성, Forward Secrecy)** 가 강제됨에 따라, 보안 장비(IDS/IPS)가 트래픽을 복호화하여 감시하는 전통적인 'Out-of-Band' 가시성 확보 아키텍처가 무력화되었으며, 이를 우회하는 Active Proxy 구성이 강제된다.

## Ⅰ. 개요 및 필요성

- **개요**: 웹의 데이터 통신(HTTP)을 암호화하는 전송 계층 보안 프로토콜(HTTPS의 기반)의 최신 규격(RFC 8446).
- **필요성**:
  1. **속도 한계 돌파**: TLS 1.2는 TCP(3-Way Handshake, 1-RTT)를 맺은 뒤 암호화 키 교환에만 2-RTT를 추가로 소모하여, 모바일 환경에서 체감 속도가 치명적으로 느렸다.
  2. **레거시 보안 취약점 제거**: 하위 호환성을 이유로 수십 년간 남아있던 낡은 암호화 방식(MD5, SHA-1, RC4)과 정적 RSA 방식을 해커들이 악용하는 사례(POODLE, FREAK 공격 등)가 속출했다.

---
## Ⅱ. 아키텍처 및 핵심 원리

- **TLS 1.2 vs TLS 1.3 핸드쉐이크 비교 흐름도**

```text
[ TLS 1.2 Handshake (2-RTT) ]           [ TLS 1.3 Handshake (1-RTT) ]
  Client                   Server         Client                   Server
    |                        |              |                        |
(1) |---- Client Hello ----->|          (1) |---- Client Hello ----->|
    |  (나 이런 알고리즘 써) |              |  (알고리즘 + 미리 만든 키 재료)
    |                        |              |                        |
(2) |<--- Server Hello ------|          (2) |<--- Server Hello ------|
    |  (알고리즘 선택/인증서)|              |  (인증서 + 서버 쪽 키 재료)|
    |                        |              |                        |
(3) |---- Client Key Ex ---->|          (3) |======= 암호화 Data ===>| (1-RTT 완료!)
    |  (클라이언트 키 재료)  |              |                        |
    |                        |
(4) |<--- Server Finished ---|
    |                        |
(5) |======= 암호화 Data ===>| (2-RTT)
```

- **핵심 원리**:
  1. **1-RTT 연결 (추측 기반 키 교환)**: 클라이언트는 서버가 무슨 암호화 방식을 고를지 기다리지 않는다. 자기가 지원하는 가장 안전한 키 교환 방식(예: ECDHE)의 수학적 '키 재료'를 `Client Hello` 패킷에 무작정 담아서 던져버린다. 서버가 이를 OK 하면 한 번의 왕복으로 즉시 암호화 통신이 시작된다.
  2. **0-RTT 재연결 (세션 부활)**: 이전에 통신했던 서버라면, 예전에 주고받았던 'Pre-Shared Key(PSK)' 티켓을 이용해 인사(Hello)와 동시에 암호화된 첫 데이터를 냅다 쏴버린다.
  3. **완벽한 순방향 비밀성(PFS) 강제**: 해커가 과거의 패킷을 모두 훔쳐 모아두었다가 훗날 서버의 마스터 비밀키를 해킹하더라도, 과거의 데이터를 해독할 수 없다. 매 세션마다 일회용 키(Ephemeral Key)를 생성해 쓰고 버리기 때문이다.

## Ⅲ. 비교 및 연결

| 비교 항목 | TLS 1.2 | TLS 1.3 |
|:---|:---|:---|
| **최초 연결 (Handshake RTT)**| 2-RTT | **1-RTT** |
| **재연결 (Resumption RTT)** | 1-RTT | **0-RTT** |
| **키 교환 방식** | 정적 RSA, (EC)DHE 등 혼용 | **(EC)DHE 전용** (RSA 키 교환 전면 폐지) |
| **순방향 비밀성 (PFS)** | 선택적 적용 가능 | **강제 적용** |
| **핸드쉐이크 암호화 시점** | 키 교환 완료 후(늦음) | **Server Hello 이후 즉시 암호화** |
| **지원 알고리즘 (Cipher Suites)**| 37개 이상 (복잡, 낡은 기술 포함)| **단 5개 (초강력 AEAD 기반만 남김)** |

## Ⅳ. 실무 적용 및 기술사 판단

- **보안 장비 가시성 상실 (Out-of-Band 복호화 불가)**
  - 문제: 기존 기업 보안팀은 서버의 'RSA 개인키'를 보안 장비(IDS/IPS, WAF)에 미리 복사해 두고, 미러링된 트래픽을 몰래 뜯어보았다. 하지만 TLS 1.3은 매번 키가 바뀌는 PFS(디피-헬만)가 강제되어, 개인키가 있어도 패킷 복호화가 불가능하다.
  - 판단/조치: TLS 1.3 환경에서 패킷 가시성을 확보하려면, 수동적인 미러링 방식(Out-of-Band)을 버리고, 보안 장비가 클라이언트와 서버 사이를 물리적으로 가로막고 대리인 행세를 하는 **Active Inline Proxy (SSL/TLS 복호화 장비)** 아키텍처로 전면 개편해야 한다.

- **0-RTT 의 취약점 (Replay Attack)**
  - 문제: 0-RTT는 너무 빨라서, 해커가 클라이언트의 암호화된 첫 요청(예: "내 계좌에서 10만 원 이체해") 패킷을 가로채서 서버에 여러 번 복사해 던지면 서버가 그대로 속아 처리해 버릴 수 있다.
  - 조치: 아키텍처 설계 시 0-RTT로 전송되는 첫 데이터는 반드시 **GET 요청처럼 멱등성(Idempotent, 여러 번 실행해도 결과가 같은)을 가진 안전한 데이터**만 허용하도록 웹 서버 설정을 강제해야 한다.

## Ⅴ. 기대효과 및 결론

- **결론**: TLS 1.3은 인터넷 암호화의 뼈대에서 불필요한 군살(낡은 알고리즘)을 과감히 도려내고, 현대 모바일 환경이 요구하는 '극강의 속도'와 '타협 없는 보안'을 동시에 달성한 마스터피스다.
- **기대효과**: 서버 아키텍처를 TLS 1.3으로 업그레이드하면 0-RTT/1-RTT를 통해 글로벌 체감 지연 시간을 수백 밀리초 단위로 단축시킬 수 있으며, 현존하는 대부분의 중간자 공격과 암호화 무력화 기법을 원천 차단할 수 있다.

### 📌 관련 개념 맵
TCP 3-Way Handshake $\rightarrow$ 비대칭키/대칭키 하이브리드 암호화 $\rightarrow$ 디피-헬만(DHE) 키 교환 $\rightarrow$ PFS(순방향 비밀성) $\rightarrow$ TLS 1.3 (1-RTT) $\rightarrow$ QUIC (HTTP/3 결합).

### 📈 관련 키워드 및 발전 흐름도
`SSL 3.0 / TLS 1.0 (초기 보안)` $\rightarrow$ `TLS 1.2 (표준 정착, 알고리즘 파편화/느림)` $\rightarrow$ `보안 사고 속출 (POODLE, Heartbleed)` $\rightarrow$ `TLS 1.3 표준화 (2018년, PFS 강제 & 1-RTT)` $\rightarrow$ `QUIC 융합 (0-RTT 극대화)`

### 👶 어린이를 위한 3줄 비유 설명
1. 비밀 편지를 주고받을 때 예전(TLS 1.2)에는 "안녕! 우리 무슨 암호 쓸까?" -> "이거 쓰자!" -> "그래, 이 열쇠로 풀자!" 하고 세 번이나 편지를 주고받아야 진짜 대화를 시작할 수 있었어요.
2. 새 버전(TLS 1.3)은 첫인사를 할 때부터 "안녕! 우리 이 암호 쓰고, 열쇠는 이거야!"라고 한 방에 묶어서 보내버리기 때문에 훨씬 빨리 비밀 대화가 시작됩니다.
3. 게다가 옛날에는 열쇠 하나만 평생 써서 열쇠를 잃어버리면 과거 편지까지 몽땅 들통났는데, 이제는 편지를 한 통 쓸 때마다 새 열쇠를 만들고 버리기 때문에(PFS) 해커가 절대 과거 편지를 풀 수 없답니다.
