## 미리 알고가기

- TLS는 전송 구간에서 기밀성, 무결성, 인증을 제공하는 보안 프로토콜임
- 핸드셰이크는 통신 전에 암호 알고리즘과 세션 키를 합의하는 절차임
- RTT는 요청과 응답이 한 번 왕복하는 데 걸리는 시간임
- PFS는 장기 키가 유출되어도 과거 세션 내용은 복호화되지 않게 하는 성질임
- PSK는 이전 통신에서 얻은 비밀값을 재사용해 빠르게 재연결할 때 쓰는 공유 비밀임

## Ⅰ. 개요

- **정의/개념**: TLS 1.3은 키 교환과 서버 인증을 기본 1-RTT에 수행하고 레거시 키 교환·암호 스위트를 제거한 전송 보안 규격임
- **배경/필요성**: 왕복 지연이 큰 경로에서는 핸드셰이크 횟수가 초기 응답 시간에 반영되고, 구버전 TLS의 레거시 알고리즘과 협상 분기는 설정 오류와 공격 표면을 늘리므로 절차와 선택지를 줄일 필요가 있었음

## Ⅱ. 특징

- 기본 핸드셰이크를 1-RTT로 줄여 초기 연결 지연을 낮춤
- 일시 키 교환을 기본으로 사용해 PFS를 사실상 강제함
- RC4, 정적 RSA 키 교환, 압축 같은 오래된 선택지를 제거해 협상 복잡도를 줄임
- 세션 재개 시 0-RTT를 지원하지만 재전송 공격 가능성이 있어 모든 요청에 무조건 쓰면 안 됨

## Ⅲ. 종류 및 비교

| 판단 기준 | TLS 1.2 | TLS 1.3 |
|:---|:---|:---|
| 기본 연결 왕복 수 | TCP 이후 추가 협상이 길어 2-RTT에 가까운 구성이 흔함 | 주요 키 교환과 인증을 1-RTT로 마침 |
| 키 교환 방식 | 정적 RSA와 여러 레거시 방식이 혼재할 수 있음 | 일시 키 기반 교환을 사용해 PFS를 기본으로 확보함 |
| 암호 스위트 구조 | 해시, 교환, 대칭키 조합이 복잡하게 섞여 있음 | 지원 조합을 단순화해 구현과 운영 판단이 쉬움 |
| 재연결 처리 | 세션 재개가 가능하지만 절차와 구현 편차가 큼 | PSK 기반 재개와 0-RTT를 표준적으로 제공함 |
| 운영상 영향 | 수동 예외 처리가 많고 취약한 옵션을 남기기 쉬움 | 보안 기본값은 좋아지지만 수동 복호화 관점의 가시성은 줄어듦 |

## Ⅳ. 구성요소 및 구조

| 구성요소 | 설명 |
|:---|:---|
| ClientHello | 지원 버전, 암호 스위트, 키 공유 정보, 확장 기능을 먼저 제시하는 시작 메시지임 |
| ServerHello | 사용할 알고리즘과 서버의 키 공유 정보를 선택해 응답하는 메시지임 |
| 인증서 체인 | 서버 신원을 검증하기 위해 CA 서명 정보를 전달하는 구조임 |
| Finished 메시지 | 지금까지 교환한 핸드셰이크 내용을 바탕으로 양측이 같은 비밀값을 계산했는지 확인하는 검증 단계임 |
| 세션 재개 정보 | 재접속 때 PSK나 세션 티켓으로 빠른 연결을 가능하게 하는 재사용 정보임 |

```text
+-------------+     +-------------+     +--------------+     +-------------+
| ClientHello | --> | ServerHello | --> | 인증서·Finished | --> | 암호화 데이터 |
+-------------+     +-------------+     +--------------+     +-------------+
```

## Ⅴ. 원리 및 절차 흐름도

```text
+-------------+     +-------------+     +----------------+     +----------------+     +-------------+
| 접속정보 제시 | --> | 알고리즘 선택 | --> | 서버 인증·키 확정 | --> | 클라이언트 완료 통보 | --> | 데이터 전송 |
+-------------+     +-------------+     +----------------+     +----------------+     +-------------+
```

1. **접속정보 제시**: 클라이언트가 지원 버전, 암호 스위트, 키 공유값을 담은 ClientHello를 보냄
2. **알고리즘 선택**: 서버가 사용할 버전과 키 공유값을 담아 ServerHello를 보냄
3. **서버 인증·키 확정**: 서버가 인증서와 Finished를 보내고 양측이 핸드셰이크 키를 계산함
4. **클라이언트 완료 통보**: 클라이언트가 Finished를 보내 동일한 비밀값 계산이 끝났음을 알림
5. **데이터 전송**: 이후 애플리케이션 데이터는 협상된 세션 키로 암호화되어 전달됨

## Ⅵ. 실무 적용 및 유의점

1. 웹 서비스나 모바일 API처럼 지연시간에 민감한 환경에서는 TLS 1.3과 세션 재개를 기본으로 적용하되 0-RTT는 재전송돼도 안전한 조회성 요청에만 허용하고 핸드셰이크 RTT, 재전송률, 재연결 성공률로 적용 상태를 확인함
2. 보안 장비가 수동 복호화에 의존하던 환경에서는 TLS 종료 지점 재설계나 프록시 기반 가시성 확보가 필요하므로 허용된 복호화 경로, 인증서 배포 방식, 복호화 후 로그 수집 범위로 운영 가능성을 확인함

## Ⅶ. 결론

TLS 1.3은 1-RTT 키 교환과 제한된 암호 스위트를 사용하며, 운영에서는 0-RTT 허용 범위와 재전송 위험을 함께 통제해야 함.
