## Ⅰ. 개요
- **정의**: 프로토콜 독립적으로 패킷 처리 파이프라인을 기술하는 도메인 특화 언어(DSL)임
- **배경/필요성**: OpenFlow는 매치 필드가 고정되어 새 프로토콜 헤더 추가 시 스펙 자체를 변경해야 함
- **비유**: 요리 레시피를 표준 양식으로 작성하면 어떤 주방(칩)에서든 동일하게 조리 가능한 것과 유사함

| 출제 의도 | 반드시 짚을 핵심 | 감점 회피 포인트 |
|:---|:---|:---|
| 데이터플레인 프로그래밍 언어 이해 | 프로토콜 독립, 타겟 독립, PISA 모델 | P4_14 vs P4_16 버전 차이, PSA·v1model 구분 |

> 요약: P4는 패킷 파서·테이블·액션을 프로토콜·타겟에 독립적으로 기술하는 DSL임

## Ⅱ. 구성요소
```text
P4 Source --> P4 Compiler --> Target Binary
                |
        +-------+-------+
        |       |       |
     Parser   Control  Deparser
     Block    Block    Block
```

| 구성요소 | 설명 | 비유 |
|:---|:---|:---|
| Header/Struct 선언 | 패킷 헤더 필드와 메타데이터 구조를 정의함 | 레시피 재료 목록 |
| Parser 블록 | 상태 머신으로 헤더 추출 순서를 기술함 | 재료 손질 순서 |
| Control 블록 | Match-Action 테이블과 액션 함수를 정의함 | 조리 단계 |
| Deparser 블록 | 출력 패킷의 헤더 재조립 순서를 기술함 | 플레이팅 |
| Architecture Model | PSA·v1model 등 타겟 추상화 인터페이스임 | 주방 규격 |

> 요약: Header-Parser-Control-Deparser 블록과 아키텍처 모델로 파이프라인을 기술함

## Ⅲ. 절차
```text
헤더 정의 --> 파서 작성 --> 테이블/액션 정의 --> 컴파일 및 배포
```
- 1단계: `header`, `struct` 타입으로 프로토콜 헤더 필드를 선언함
- 2단계: `parser` 블록에서 상태 전이로 헤더 추출 순서를 정의함
- 3단계: `control` 블록에서 `table`과 `action`을 정의하여 매칭·처리 로직을 기술함
- 4단계: P4 컴파일러가 타겟 바이너리를 생성하고 런타임 API로 스위치에 배포함

> 요약: 헤더·파서·제어 로직을 선언적으로 작성하고 컴파일러가 타겟에 맞게 변환하는 흐름임

## Ⅳ. 문제점
- 표현력 제한: 루프·부동소수점 연산 미지원으로 복잡한 알고리즘 구현이 어려움
- 타겟 간 이식성 격차: 아키텍처 모델별 지원 기능 차이로 동일 코드가 모든 칩에서 동작하지 않음
- 디버깅 도구 부족: 하드웨어 파이프라인 내부 상태를 관찰할 도구가 제한적임

> 요약: 표현력, 이식성, 디버깅 도구의 한계가 P4 활용 확대를 제약함

## Ⅴ. 개선방안
1. 단기: `extern` 블록·레지스터 활용으로 복잡 로직을 플랫폼 확장 함수로 보완함
2. 중기: Portable NIC Architecture(PNA) 등 표준 아키텍처 모델 통합으로 이식성을 높임
3. 장기: P4 시뮬레이터·하드웨어 디버거·형식 검증 도구 생태계를 확충함

> 요약: extern 확장, 아키텍처 통합, 도구 생태계 확충으로 실용성을 강화함

## Ⅵ. 전망
- 발전 방향: SmartNIC(083 참조)·프로그래머블 스위치(084 참조) 양쪽의 공통 프로그래밍 모델로 수렴함
- 기술사적 판단: 네트워크를 소프트웨어 정의에서 데이터플레인 정의로 전환하는 핵심 언어임
- 기술사 제언: P4 역량은 향후 네트워크 엔지니어의 차별화 요소로 교육·실습 환경 확보가 필요함
