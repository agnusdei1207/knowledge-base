## Ⅰ. 개요
- **정의**: 퍼블릭 클라우드 내에 논리적으로 격리된 가상 사설 네트워크를 제공하는 서비스임
- **배경/필요성**: 다수 테넌트가 공유 인프라를 사용하므로 네트워크 격리와 자체 IP 주소 체계가 필요함
- **비유**: 대형 오피스텔에서 각 세대가 독립된 도어록·내부 구조를 갖는 것과 유사함

| 출제 의도 | 반드시 짚을 핵심 | 감점 회피 포인트 |
|:---|:---|:---|
| 클라우드 네트워크 격리 원리 | 서브넷·라우팅·보안그룹의 계층적 정책 | VPN과 VPC의 차이, Overlay 기반(073 참조) 명시 필요 |

> 요약: 퍼블릭 클라우드에서 테넌트별 격리된 가상 네트워크를 제공하는 핵심 서비스임

## Ⅱ. 구성요소
```text
VPC
 +-- Subnet (Public) --+-- Internet GW ---> Internet
 |                      +-- NAT GW ----+
 +-- Subnet (Private) -----------------+---> On-Prem (VPN/DX)
 |
 +-- Route Table --- Security Group --- Network ACL
```

| 구성요소 | 설명 | 비유 |
|:---|:---|:---|
| Subnet | VPC 내 IP 대역을 AZ 단위로 분할한 논리 네트워크 세그먼트임 | 오피스텔 각 층 |
| Route Table | 서브넷별 트래픽 경로를 정의하는 라우팅 규칙 집합임 | 건물 내 안내 표지판 |
| Security Group | 인스턴스 단위 Stateful 방화벽으로 인바운드/아웃바운드를 제어함 | 각 세대 도어록 |

> 요약: 서브넷-라우팅-보안정책의 계층 구조로 네트워크 격리를 구현함

## Ⅲ. 절차
```text
Step1 Create VPC --> Step2 Define Subnet --> Step3 Set Route --> Step4 Apply Policy
```
- 1단계: CIDR 블록을 지정하여 VPC를 생성함
- 2단계: AZ별로 Public/Private 서브넷을 분할하여 배치함
- 3단계: 서브넷별 라우트 테이블에 IGW·NAT·VPN 게이트웨이 경로를 설정함
- 4단계: Security Group과 Network ACL로 트래픽 허용/차단 정책을 적용함

> 요약: VPC 생성-서브넷 분할-라우팅-정책 적용 순서로 격리 네트워크를 구성함

## Ⅳ. 문제점
- IP 고갈: CIDR을 작게 설계하면 워크로드 증가 시 IP가 부족하고 VPC 재생성이 필요함
- VPC 간 통신 복잡도: VPC 수 증가 시 Peering이 N*(N-1)/2로 증가하여 관리가 어려움
- 보안 정책 분산: Security Group과 Network ACL이 분리되어 정책 충돌이 발생할 수 있음

> 요약: IP 고갈, Peering 복잡도, 정책 분산이 핵심 과제임

## Ⅴ. 개선방안
1. 단기: CIDR을 충분히 크게 설계하고 Secondary CIDR 추가 기능을 활용함
2. 중기: Transit Gateway 도입으로 Hub-Spoke 구조를 적용하여 Peering 복잡도를 O(N)으로 감소함
3. 장기: 중앙 집중형 네트워크 정책 관리 도구로 Security Group·ACL 정책을 통합 관리함

> 요약: CIDR 설계, Transit Gateway, 정책 통합으로 VPC 운영을 최적화함

## Ⅵ. 전망
- 발전 방향: VPC 간 자동 연결·정책 동기화를 지원하는 클라우드 네이티브 네트워킹으로 진화함
- 기술사적 판단: 멀티 클라우드(076 참조) 환경에서 VPC는 네트워크 격리의 기본 단위로 유지됨
- 기술사 제언: VPC 설계 시 향후 확장성을 고려한 IP 체계·토폴로지 표준 수립이 필요함
