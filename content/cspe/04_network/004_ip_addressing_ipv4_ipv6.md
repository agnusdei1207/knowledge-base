# 📖 【암기용】 개념 완전 이해

> 목적: 이 개념을 처음 보는 사람도 완벽히 이해하게 만든다. 시험 답안 양식이 아니라, 이해를 위한 친절한 설명이다.

## 한눈에
- **개요**: 인터넷에서 컴퓨터를 식별하기 위한 논리적 주소 체계의 과거(IPv4)와 미래(IPv6)
- **왜 필요한가**: 인터넷에 접속하는 기기가 폭발적으로 늘어나면서 기존 32비트 주소(약 43억 개)로는 턱없이 부족해졌기 때문
- **핵심 직관**: IPv4가 '전화번호'라면, IPv6는 지구상의 모든 모래알에 주소를 부여할 수 있을 만큼 무한한 '우주 좌표'다.

## 깊이 이해
- **배경·문제의식**: 스마트폰, IoT 기기의 등장으로 IPv4 주소가 고갈되었다. NAT로 근근이 버티고 있으나, 종단 간 통신(End-to-End) 원칙이 깨지고 구조가 복잡해졌다.
- **작동 원리**: 
  - **IPv4**: 32비트(8비트 4개)로 구성, 점(.)으로 구분 (예: 192.168.0.1)
  - **IPv6**: 128비트(16비트 8개)로 구성, 콜론(:)으로 구분 (예: 2001:0db8::8a2e:0370:7334)
- **비유**: IPv4는 4자리 우편번호 체계로 동 단위까지만 구별하여 나머지는 아파트 경비실(NAT)이 처리했다면, IPv6는 16자리 체계로 집집마다 직접 우편을 넣을 수 있다.
- **구체 예시**: 32비트인 IPv4는 최대 $2^{32}$(약 43억)개, 128비트인 IPv6는 최대 $2^{128}$개 기기를 수용한다. IPv6는 주소 자동 설정(SLAAC) 기능을 지원하여 DHCP 없이도 네트워크에 붙자마자 스스로 주소를 만든다.
- **흔한 오해·주의점**: IPv6는 단순히 주소만 늘린 것이 아니다. 헤더 크기를 고정하고 검사합(Checksum)을 빼 라우터의 처리 속도를 높였으며, IPsec을 기본 탑재해 보안을 강화했다.

## 연결 개념
- 서브네팅 및 CIDR — IPv4 주소 낭비를 막기 위한 네트워크 분할 기법
- NAT (Network Address Translation) — 공인 주소를 사설 주소로 변환하여 IPv4 수명을 연장
- 듀얼 스택, 터널링, 변환 — IPv4와 IPv6가 공존하며 넘어가는 과도기 기술

# 📝 【답안용】 시험 답안 템플릿

> 목적: 시험장에서 25분에 그대로 쓰는 답안 양식. 작성방식(추상표현 금지·수치·도식·문제유형 전환)을 엄격히 지킨다.
> 핵심: 이 시험은 정보를 많이 나열하는 시험이 아니라, 문제 신호어에서 출제자 의도를 읽고 핵심 논점을 선별해 쓰는 시험이다.

## 핵심 인사이트 (3줄 요약)

> 1. **본질**: IP 주소 체계는 네트워크 계층(L3)에서 패킷의 출발지와 목적지를 식별하고 라우팅하기 위한 논리적 식별자이다.
> 2. **가치**: IPv6는 주소 공간을 128비트로 확장하여 주소 고갈을 해소하고, 헤더 단순화 및 내장 보안(IPsec)으로 라우팅 성능과 신뢰성을 높인다.
> 3. **판단 포인트**: IPv4에서 IPv6로의 전환은 단순히 주소 형식 변경이 아니라, End-to-End 통신 복원 및 IoT/5G 환경을 지원하는 인프라 혁신이다.

## 출제 의도 및 답안 포인트

| 출제 의도 | 반드시 짚을 핵심 | 감점 회피 포인트 |
|:---|:---|:---|
| IPv4와 IPv6의 구조적 차이 파악 | 주소 길이(32비트 vs 128비트), 헤더 구조(가변 vs 고정), 주소 할당 방식 | 크기 차이만 언급하고 헤더 최적화, SLAAC, 보안 특성 누락 |
| IPv6의 추가 기능 이해도 | IPsec 기본 지원, Checksum 제거로 인한 라우팅 성능 향상 | "속도가 빠르다" 등 구체적 이유 없는 성능 향상 서술 |
| 전환 필요성과 현 주소 | NAT/CIDR의 한계와 IoT 환경에서의 IPv6 필연성 | IPv4의 완전 단종 시점을 명시하는 무리수 (현실은 공존) |

> 요약: IPv6 도입의 핵심은 주소 부족 해결뿐만 아니라 모바일/IoT 시대에 맞는 라우팅 오버헤드 감소와 자동 설정(SLAAC)의 이점에 있다.

## Ⅰ. 개요 및 필요성

- 정의: 호스트의 네트워크 위치를 식별하기 위해 IETF가 정의한 L3 논리적 주소 체계(IPv4, IPv6)
- 배경: IPv4(32비트)는 주소 낭비 및 폭발적 기기 증가로 IANA 주소 풀이 고갈되었으며, NAT 의존으로 인한 통신 복잡도 증가
- 필요성: 모바일, 센서 등 100억 개 이상의 기기가 직접 통신(End-to-End)하기 위한 무한한 주소 공간과 효율적 패킷 처리가 요구됨

---

## Ⅱ. 구조 및 구성요소

```text
IPv4 주소 (32비트) : Network ID (Subnet) | Host ID
IPv6 주소 (128비트) : Routing Prefix (48) | Subnet ID (16) | Interface ID (64)
                   +-> 헤더 단순화 (가변 옵션 제거) 및 확장 헤더 도입
```

| 구분 | IPv4 (Internet Protocol v4) | IPv6 (Internet Protocol v6) |
|:---|:---|:---|
| 주소 길이/표현 | 32비트, 10진수(점 구분) | 128비트, 16진수(콜론 구분) |
| 헤더 크기 | 20~60바이트 (가변 길이) | 40바이트 (고정 길이) |
| 주소 할당 | 정적 할당 또는 DHCP(동적) | SLAAC(상태비저장 자동 설정), DHCPv6 |
| 보안 기능 | IPsec 선택적 적용 (별도 설정) | IPsec 확장 헤더로 기본(Mandatory) 지원 |

> 요약: IPv6는 128비트로 주소 공간을 확장하고, 가변 길이를 고정 크기로 단순화하여 라우터의 하드웨어 스위칭 성능을 최적화했다.

---

## Ⅲ. 동작원리 및 흐름도

```text
호스트 부팅 -> 라우터에 RS(Router Solicitation) 멀티캐스트 전송 -> 라우터가 RA(Router Advertisement) 응답
-> Prefix(64) + MAC 기반 Interface ID(64) 결합 -> 주소 자동 생성(SLAAC) -> 통신
```

| 단계 | 처리 내용 | 검증 기준 |
|:---:|:---|:---|
| 1 | **네트워크 탐색** | IPv6 호스트가 멀티캐스트(FF02::2)로 라우터 정보 요청(RS) |
| 2 | **네트워크 프리픽스 획득** | 라우터가 네트워크 대역(Prefix)과 기본 게이트웨이 정보 응답(RA) |
| 3 | **인터페이스 식별자 생성** | 호스트 MAC 주소를 EUI-64 방식으로 변환하여 하위 64비트 생성 |
| 4 | **주소 충돌 검증 (DAD)** | 생성된 128비트 주소의 중복 여부를 NS/NA 메시지로 확인 후 확정 |

> 요약: IPv6는 DHCP 서버 없이도 라우터의 Prefix와 단말의 MAC 주소를 결합하여 스스로 글로벌 유니캐스트 주소를 획득(SLAAC)한다.

## Ⅳ. 특징

| 구분 | 내용 | 판단 포인트 |
|:---|:---|:---|
| 라우팅 효율 향상 | IPv4의 Header Checksum 필드를 삭제하여 매 홉(Hop)마다 연산 부하 제거 | 라우터 패킷 처리 지연시간(Latency) 단축 |
| QoS 품질 제어 | Flow Label 필드(20비트)를 도입하여 실시간 트래픽 우선순위 지정 | 스트리밍, VoLTE의 패킷 지터(Jitter) 최소화 |
| 브로드캐스트 제거 | 네트워크를 마비시키는 Broadcast 대신 Multicast와 Anycast로 통신 최적화 | 불필요한 노드의 인터럽트 감소 |

> 요약: IPv6의 근본적 성능 향상은 헤더 구조를 고정하고 검사합을 제거해 라우터가 패킷 내부를 열어보지 않고 고속 포워딩하게 한 데 있다.

## Ⅴ. 심화 비교 및 적용 판단

| 구분 | NAT 적용 IPv4 | Native IPv6 | 선택 기준 |
|:---|:---|:---|:---|
| 통신 방향성 | 내부 -> 외부만 원활 (포트 포워딩 필요) | 양방향 End-to-End 직접 통신 | P2P, WebRTC, VoIP 등 실시간 세션 요구사항 |
| 네트워크 복잡도 | NAT 라우터 유지 및 세션 테이블 관리 | NAT 불필요, 단순한 라우팅 | 관문 라우터의 메모리 및 세션 한계(Port Exhaustion) |
| 도입 비용 | 기존 인프라 유지 (단기 저비용) | L3 스위치/라우터 펌웨어 교체 필요 | 장기적 확장성과 관리 비용 절감 |

> 요약: IPv4 NAT는 임시방편으로 세션 유지 오버헤드가 크며, 5G 및 IoT 초연결 사회에서는 NAT 병목이 없는 Native IPv6 전환이 필수적이다.

| 리스크 | 원인 | 대응 방안 | 확인 지표 |
|:---|:---|:---|:---|
| 변환 지연 및 호환성 | IPv4망과 IPv6망이 직접 통신 불가능 | 듀얼 스택, 터널링, 주소 변환(NAT-PT) 과도기 기술 적용 | IPv6 도달률 및 지연 시간(ms) |
| 방화벽 정책 복잡화 | IPv6 SLAAC로 주소가 동적 변경됨 (프라이버시 익스텐션) | 사용자 ID 또는 포트 기반의 차세대 방화벽(NGFW) 정책 수립 | 방화벽 차단/허용 룰 정합성 |
| 멀티캐스트 폭주 | ICMPv6 및 멀티캐스트 오작동 시 부하 | MLD Snooping 적용 및 라우터 멀티캐스트 Rate Limit 설정 | 멀티캐스트 패킷 드롭률 |

> 요약: IPv6 적용 리스크는 기존 보안 정책(IP 기반 차단)의 무력화이며, 동적 주소 환경에 맞는 논리적 식별 기반 통제로 대응해야 한다.

## Ⅵ. 실무 적용 및 결론

**적용 방안 3개:**
1. **점진적 듀얼 스택 도입**: 엣지 라우터와 코어 스위치부터 IPv4/IPv6를 동시 지원하는 듀얼 스택을 적용하고, 점진적으로 내부망까지 확대
2. **DNS64/NAT64 환경 구축**: IPv6 전용 모바일 클라이언트가 IPv4 레거시 웹 서버에 접근할 수 있도록 DNS 및 NAT 주소 변환 게이트웨이 구성
3. **스마트홈/IoT 무상태 주소 할당**: 수만 개의 센서가 동시 접속하는 환경에서 DHCP 병목을 없애기 위해 SLAAC 기반의 분산 주소 자동 할당 체계 적용

**결론 (2줄):**
- 기술사 판단: IPv6 전환은 선택이 아닌 필수 생존 전략으로, 주소 고갈 대응을 넘어 모바일 환경에서의 라우팅 오버헤드와 NAT 병목을 근본적으로 제거한다.
- 향후 방향: 5G Core, SRv6(Segment Routing over IPv6) 등 통신망 인프라는 이미 IPv6 단일 체계로 발전 중이므로, 엔터프라이즈 망 역시 애플리케이션 호환성 검증을 마치는 대로 Native IPv6로 전환해야 한다.
