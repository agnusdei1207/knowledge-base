## Ⅰ. 개요
- **정의**: 네트워크 상 호스트를 식별하기 위한 논리적 주소 체계임
- **배경/필요성**: 전 세계 장비에 고유 주소를 부여하여 라우팅과 목적지 식별이 가능해야 함
- **비유**: 우편 시스템의 우편번호+주소에 해당함

| 출제 의도 | 반드시 짚을 핵심 | 감점 회피 포인트 |
|:---|:---|:---|
| IPv4와 IPv6 구조 차이 이해 | 주소 길이·헤더 구조·NAT 필요성 차이 | 클래스 기반 vs CIDR 구분, IPv6 확장 헤더 언급 필요 |

> 요약: IP 주소는 네트워크 장비의 논리적 식별자로 IPv4(32비트)와 IPv6(128비트)로 구분됨

## Ⅱ. 구성요소
```text
IPv4: [네트워크부 | 호스트부] = 32bit (점 10진 표기)
IPv6: [프리픽스 | 인터페이스 ID] = 128bit (콜론 16진 표기)
```

| 구성요소 | 설명 | 비유 |
|:---|:---|:---|
| IPv4 헤더 | 20바이트 고정 + 옵션, TTL·체크섬 포함 | 짧은 편지 봉투 |
| IPv6 헤더 | 40바이트 고정, 확장 헤더 체인 방식 | 모듈형 봉투(필요한 것만 추가) |
| 서브넷 마스크 | 네트워크부와 호스트부 경계를 구분하는 비트 마스크 | 우편번호와 상세 주소의 경계선 |

> 요약: IPv4는 32비트 고정 헤더, IPv6는 128비트 확장 헤더 방식으로 주소를 관리함

## Ⅲ. 절차
```text
주소 할당 --> 서브넷 분할 --> 라우팅 테이블 등록 --> 패킷 전달
```
- 1단계: 주소 할당 — IANA → RIR → ISP → 기관 순으로 IP 블록을 분배함
- 2단계: 서브넷 분할 — CIDR 표기법으로 네트워크를 논리적으로 분할함
- 3단계: 라우팅 테이블 등록 — 목적지 네트워크·넥스트 홉을 라우터에 설정함
- 4단계: 패킷 전달 — 목적지 IP 기반 longest prefix match로 포워딩함

> 요약: 주소 할당 → 서브넷 → 라우팅 등록 → 포워딩 순으로 패킷이 전달됨

## Ⅳ. 문제점
- IPv4 고갈: 32비트 한계 — 약 43억 개 주소로 IoT 시대 수요를 감당 불가
- NAT 복잡성: 주소 부족 우회 — 엔드투엔드 연결성 훼손과 P2P 통신 장애 유발
- 이중 운영 부담: 전환기 공존 — IPv4/IPv6 듀얼스택 운영 시 관리 비용 증가

> 요약: IPv4 주소 고갈이 핵심 문제이며 NAT와 이중 운영이 복잡성을 가중함

## Ⅴ. 개선방안
1. 단기: CGNAT·IPv4 주소 거래 시장을 통한 잔여 주소 활용 극대화
2. 중기: 듀얼스택·터널링(6to4, DS-Lite)으로 IPv6 점진 전환
3. 장기: IPv6 단일 스택 전환 완료 및 NAT 제거로 엔드투엔드 연결성 회복

> 요약: 단기 NAT 활용 → 중기 듀얼스택 → 장기 IPv6 단일 전환으로 개선함

## Ⅵ. 전망
- 발전 방향: 5G·IoT 확산으로 IPv6 채택률이 가속화되는 추세임
- 기술사적 판단: IPv6 전환은 선택이 아닌 인프라 생존의 문제임
- 기술사 제언: 신규 인프라 구축 시 IPv6 기본 설계를 의무화할 것을 제안함
