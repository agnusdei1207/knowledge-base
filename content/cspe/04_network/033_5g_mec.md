## Ⅰ. 개요
- **정의**: 무선 접속망 인접 위치에서 컴퓨팅 자원을 제공하는 엣지 컴퓨팅 플랫폼임
- **배경/필요성**: 중앙 클라우드까지의 왕복 지연이 1ms급 초저지연 서비스 요구를 충족하지 못하여 에지 처리가 필요함
- **비유**: 본사까지 보고하지 않고 현장 지사에서 즉시 처리하는 구조와 유사함

| 출제 의도 | 반드시 짚을 핵심 | 감점 회피 포인트 |
|:---|:---|:---|
| MEC 배치 위치와 5GC 연동 | UPF 로컬 브레이크아웃, ETSI MEC 참조 아키텍처 | CDN과 MEC의 차이 혼동 주의 |

> 요약: 접속망 에지에 컴퓨팅을 배치하여 초저지연 서비스를 실현하는 플랫폼임

## Ⅱ. 구성요소
```text
UE -> gNB -> Local UPF -> MEC Host
                            |
                     +------+------+
                     |      |      |
                   MEP   MEC App  VIM
```

| 구성요소 | 설명 | 비유 |
|:---|:---|:---|
| MEC Host | 에지 애플리케이션을 실행하는 서버 인프라 | 현장 지사 사무실 |
| MEP(MEC Platform) | 서비스 등록·DNS·트래픽 규칙을 관리하는 플랫폼 | 지사 운영 시스템 |
| MEC App | 에지에서 실행되는 저지연 애플리케이션 | 현장 담당 직원 |
| Local UPF | 에지로 트래픽을 분기하는 사용자면 기능(032 참조) | 현장 직배송 경로 |

> 요약: Local UPF로 트래픽을 분기하고 MEC Host에서 저지연 처리를 수행함

## Ⅲ. 절차
```text
UE -> gNB -> UPF(anchor)
              |
         Local UPF -> MEC Host -> 응답
```
- 1단계: SMF가 UE 위치·서비스 유형에 따라 Local UPF를 선택함
- 2단계: Local UPF가 해당 트래픽을 MEC Host로 로컬 브레이크아웃함
- 3단계: MEC App이 요청을 처리하고 응답을 생성함
- 4단계: 응답이 Local UPF를 경유하여 UE에 저지연 전달됨

> 요약: Local UPF 분기-MEC 처리-저지연 응답의 흐름으로 동작함

## Ⅳ. 문제점
- 에지 자원 제약: 중앙 DC 대비 컴퓨팅·스토리지 용량이 한정적임
- 이동성 연속성: UE 이동 시 MEC 호스트 간 세션 마이그레이션이 복잡함
- 보안 경계 확장: 분산 에지 노드마다 독립적 보안 관리가 요구됨

> 요약: 자원 제약, 이동성 처리, 분산 보안이 주요 과제임

## Ⅴ. 개선방안
1. 단기: 컨테이너 기반 경량 배포로 에지 자원 활용률을 극대화함
2. 중기: MEC 오케스트레이터 도입으로 이동 시 앱 상태 마이그레이션을 자동화함
3. 장기: Zero Trust 기반 에지 보안 프레임워크를 표준화하여 보안 일관성을 확보함

> 요약: 경량화, 오케스트레이션, Zero Trust 보안으로 개선 가능함

## Ⅵ. 전망
- 발전 방향: 자율주행·XR·스마트팩토리 등 초저지연 수요 증가로 MEC 배치가 확산됨
- 기술사적 판단: MEC는 클라우드-에지 연속체(Continuum)의 핵심 계층으로 자리잡을 전망임
- 기술사 제언: 통신사-클라우드 사업자 간 에지 인프라 공유 모델 수립이 필요
