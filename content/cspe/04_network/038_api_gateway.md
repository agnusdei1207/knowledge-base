## Ⅰ. 개요
- **정의**: 클라이언트와 다양한 백엔드 서비스 사이에서 단일 진입점 역할을 하며, API 라우팅, 인증, 로깅 등 공통 기능을 처리하는 서버임.
- **배경/필요성**: MSA 환경에서 클라이언트가 다수 서비스를 직접 호출 시 발생하는 복잡도, 보안 취약성, 클라이언트-서버 간 결합도 증가 문제 해결.
- **출제 의도**: API 게이트웨이 패턴의 장단점, 핵심 기능(보안, 스로틀링, 라우팅) 및 서비스 메시와의 역할 차이 이해.

## Ⅱ. 구성요소
```text
+-----------------------+
|       Clients         | (Web, Mobile, IoT)
+-----------+-----------+
            | HTTP / REST
+-----------+-----------+
|      API Gateway      | (Auth, Rate Limit,
|                       |  Routing, Logging)
+-----------+-----------+
            |
+-----------+-----------+
|    Backend Services   | (Microservice A,
|                       |  Microservice B)
+-----------------------+
```
| 구성요소 | 설명 | 비유 |
|---|---|---|
| Clients | 백엔드 데이터나 기능을 요청하는 외부 애플리케이션 | 방문객 |
| API Gateway | 모든 요청을 가장 먼저 받아 검사하고 적절한 목적지로 안내하는 관문 | 건물 안내데스크 |
| Backend Services | 실제 비즈니스 로직을 수행하고 데이터를 반환하는 마이크로서비스 무리 | 개별 사무실 |
> 요약: 게이트웨이가 클라이언트 요청의 단일 창구가 되어 보안 및 라우팅 등 공통 관심사를 중앙에서 처리함.

## Ⅲ. 절차
```text
+-----------+   +-------------+   +-------------+   +-----------+
| API 요청  |-> | 인증/인가   |-> | 변환/라우팅 |-> | 응답 반환 |
+-----------+   +-------------+   +-------------+   +-----------+
```
1. **API 요청**: 클라이언트가 단일 도메인(엔드포인트)으로 특정 서비스의 API를 호출함.
2. **인증/인가**: API 게이트웨이가 토큰(JWT 등)을 검증하여 유효한 사용자인지 확인하고 속도 제한(Rate Limit)을 적용함.
3. **변환/라우팅**: 요청 패스(Path)를 분석하여 해당 API를 처리할 타겟 백엔드 서비스로 포워딩(또는 헤더 변환)함.
4. **응답 반환**: 백엔드로부터 받은 응답 데이터를 모니터링 로그로 기록하고, 클라이언트에 적합한 형태로 반환함.
> 요약: 방어막(인증)을 거쳐 길찾기(라우팅)를 수행하고 결과를 돌려주는 프록시 역할을 수행함.

## Ⅳ. 문제점
- **단일 장애점(SPOF) 및 병목**: 모든 트래픽이 집중되므로 게이트웨이 장애 시 전체 서비스가 마비될 위험.
- **결합도 증가**: 게이트웨이에 너무 많은 비즈니스 로직(데이터 취합 등)이 포함되면 모놀리식 구조의 단점이 재현됨.
- **지연 시간**: 클라이언트와 백엔드 사이에 홉(Hop)이 추가되어 미세한 네트워크 지연(Latency)이 발생함.

## Ⅴ. 개선방안
- **고가용성 확보**: 이중화(Active-Active) 클러스터링 및 오토스케일링 구성을 통해 트래픽 병목 방지 (단기).
- **BFF 패턴 적용**: 프론트엔드 유형(Web, Mobile)별로 맞춤형 게이트웨이를 분리하는 Backend For Frontend 패턴 도입 (중기).
- **기능 분리**: 내부 서비스 간(East-West) 통신 제어는 서비스 메시(Service Mesh)로 분리하고, 게이트웨이는 외부(North-South) 관문에 집중 (장기).

## Ⅵ. 전망
- SaaS 모델 및 오픈 API 생태계 확장에 따라 API 관리를 전문으로 하는 API 관리 플랫폼(APIM)으로 역할이 확장 중임.
- 서버리스(Serverless) 아키텍처와 결합하여 인프라 관리 없이 트래픽에 자동 대응하는 완전 관리형 서비스 사용이 보편화될 것임.
