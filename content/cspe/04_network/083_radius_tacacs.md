## Ⅰ. 개요
| 항목 | 내용 |
|---|---|
| **정의** | 분산된 네트워크 장비들의 사용자 접근 제어를 위해 인증(Auth), 인가(Authz), 과금(Acct)을 중앙에서 통합 처리하는 AAA 관리 프로토콜 |
| **배경/필요성** | 수백 대의 스위치/라우터마다 개별 계정을 생성하는 관리적 한계 극복 및 장비 접속자 권한의 정밀한 중앙 감사 필요 |
| **출제 의도** | RADIUS(UDP)와 TACACS+(TCP)의 암호화 수준, 프로토콜 구조 및 AAA 분리 처리(TACACS+) 등 아키텍처적 차이 평가 |

## Ⅱ. 구성요소
```text
+----------+       +----------+       +----------+
|  Admin   |       |  Router  |       | AAA Ser. |
| (Client) | <---> | (Client) | <---> | (TACACS) |
+----------+       +----------+       +----------+
```
| 구성요소 | 설명 | 비유 |
|---|---|---|
| AAA 구조 | Authentication(신원 확인), Authorization(권한 부여), Accounting(행위 기록)의 통합 보안 프레임워크 | 신분증/출입증/로그북 |
| RADIUS | 주로 단말 사용자의 무선/VPN 인증용이며 패스워드만 암호화하는 UDP 기반 개방형 표준 | 개방형 통합 톨게이트 |
| TACACS+ | 시스코 전용에서 출발해 장비 관리자 접속 제어용으로 쓰이며 페이로드 전체 암호화(TCP) | 엄격한 VIP 출입 심사 |

> 요약: 중앙 집중형 AAA 체계를 구성하여 전사적 계정 관리 일원화와 관리자 행위 추적성을 확보함

## Ⅲ. 절차
```text
+----------+    +----------+    +----------+    +----------+
| 접속 시도| -> | 인증 처리| -> | 권한 부여| -> | 과금 기록|
+----------+    +----------+    +----------+    +----------+
```
1. 접속 시도: 관리자가 라우터에 SSH 접속 시 라우터는 자체 DB 대신 AAA 서버(TACACS+)로 인증 위임(프록시)
2. 인증 처리: AAA 서버가 중앙 AD/DB를 통해 관리자 ID/PW가 유효한지 암호화된 통신으로 검증(Authentication)
3. 권한 부여: 인증 성공 시 해당 관리자가 실행 가능한 명령어(CLI) 목록 및 권한 레벨 전송(Authorization)
4. 과금 기록: 관리자가 장비에서 특정 명령어 실행 시, AAA 서버가 시간과 행위 내역을 빠짐없이 로깅(Accounting)

> 요약: 사용자 신원 확인부터 명령 실행 권한 승인, 사후 감사 기록까지 통일된 보안 라이프사이클을 제공함

## Ⅳ. 문제점
- RADIUS 프로토콜은 패스워드 필드만 암호화하고 나머지 트래픽은 평문 전송하여 중간자 스니핑 위험에 부분 노출
- RADIUS는 인증(Authentication)과 인가(Authorization)를 묶어서 처리하여 세밀한 명령어 기반 권한 제어 불가
- TACACS+는 TCP 기반 풀(Full) 암호화를 제공하나 복잡성(Overhead)이 높아 대규모 일반 단말 인증 처리에는 부적합

## Ⅴ. 개선방안
- [단기] 네트워크 장비 관리자 접속(Admin) 통제는 TACACS+로, 일반 단말망(VPN/Wi-Fi) 인증은 RADIUS로 분리 적용(베스트 프랙티스)
- [중기] 통신 구간 암호화 강화를 위해 평문 구간에 IPSec 터널링 또는 RadSec(TLS 기반 RADIUS) 기술 전면 도입
- [장기] 제로 트러스트 기조에 맞추어 단방향 인증을 탈피하고 관리자와 장비 간의 양방향 인증(Mutual Auth) 구조 강화 확립

## Ⅵ. 전망
- 단순 장비 접속 관리를 넘어 클라우드 및 멀티 벤더 환경을 지원하는 차세대 통합 ID 및 권한 관리 시스템(IAM) 플랫폼으로 진화할 것임
