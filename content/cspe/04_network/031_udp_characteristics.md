# 📖 【암기용】 개념 완전 이해

> 목적: UDP를 처음 봐도 TCP와 다른 이유를 이해하게 만든다. 시험 답안 양식이 아니라, 동작 직관과 적용 조건을 익히기 위한 설명이다.

## 한눈에
- **개요**: UDP는 연결 설정 없이 데이터그램을 전송하는 전송 계층 프로토콜
- **왜 필요한가**: DNS, VoIP, 스트리밍, 게임처럼 일부 손실보다 왕복 지연(RTT)과 헤더 오버헤드가 더 민감한 업무에서 사용함.
- **핵심 직관**: UDP는 등기우편이 아니라 엽서임. 주소와 내용만 적어 보내며, 도착 확인·순서 정리·재전송은 애플리케이션이 맡음.

## 깊이 이해
- **배경·문제의식**: TCP는 3-way handshake, 순서 보장, 재전송, 혼잡 제어를 제공하지만 지연과 상태 관리 비용이 생김. UDP는 8바이트 헤더와 무연결 구조로 전송 책임을 최소화함.
- **작동 원리**: 송신 애플리케이션이 목적지 IP와 포트를 지정하면 UDP 헤더(출발지 포트, 목적지 포트, 길이, 체크섬)를 붙여 IP에 전달함. 수신 측은 포트 기준으로 소켓에 전달하고, 손실·중복·순서 오류는 상위 프로토콜이 판단함.
- **비유**: 전화 통화 전 예약 절차 없이 무전기로 짧은 메시지를 보내는 방식임. 응답이 필요하면 사용자가 다시 물어봐야 함.
- **구체 예시**: DNS 질의는 보통 UDP 53을 사용하고, 응답이 512바이트를 넘거나 DNSSEC·EDNS0 조건에서 TCP 53으로 전환 가능함.
- **흔한 오해·주의점**: UDP는 신뢰성이 전혀 없는 기술이 아니라 전송 계층의 보장 기능을 제거한 구조임. QUIC처럼 애플리케이션 계층에서 TLS 1.3, 재전송, 스트림 제어를 얹을 수 있음.

## 연결 개념
- TCP vs UDP vs SCTP 비교: 연결성·순서·신뢰성 차이 비교
- QUIC·HTTP/3: UDP 443 위에서 신뢰성·암호화·멀티플렉싱 구현
- RTP/RTCP: 실시간 미디어 품질 피드백과 지터 보정

# 📝 【답안용】 시험 답안 템플릿

> 목적: 시험장에서 25분에 그대로 쓰는 답안 양식. 작성방식(추상표현 금지·수치·도식·문제유형 전환)을 엄격히 지킨다.
> 핵심: UDP는 "신뢰성 없음" 한 줄이 아니라 무연결 전송, 애플리케이션 책임, 지연 민감 업무의 선택 기준으로 답안을 구성함.

## 핵심 인사이트 (3줄 요약)

> 1. **본질**: UDP (User Datagram Protocol)는 8바이트 헤더와 무연결 전송으로 포트 기반 데이터그램 전달만 수행하는 전송 계층 프로토콜이다.
> 2. **가치**: DNS UDP 53, QUIC UDP 443, RTP, 게임 패킷처럼 TCP 3-way handshake를 생략해 초기 1 RTT를 절감하는 업무에 적합하다.
> 3. **판단 포인트**: 손실 허용도, 순서 보장 필요성, NAT/방화벽 통과, 애플리케이션 재전송 설계 여부를 함께 판단해야 한다.

## 출제 의도 및 답안 포인트

| 출제 의도 | 반드시 짚을 핵심 | 감점 회피 포인트 |
|:---|:---|:---|
| TCP와 UDP의 전송 책임 차이 확인 | 연결 설정 없음, 8바이트 헤더, 순서·재전송 미제공 | UDP를 "비신뢰"로만 쓰고 활용 사례·상위 보완 누락 |
| 지연 민감 서비스 적용 판단 확인 | DNS, VoIP, 스트리밍, QUIC, 게임 트래픽 | 모든 실시간 서비스에 UDP를 단정 적용 |
| 운영 리스크 인식 확인 | 패킷 손실, 증폭 공격, NAT timeout, MTU 단편화 | DDoS·방화벽 정책·관측 지표 누락 |

> 요약: UDP 문제는 기능 부재를 외우는 것이 아니라 지연·손실·상위 제어의 선택 기준을 제시하는 문제임.

---

## Ⅰ. 개요 및 필요성

- 개요: 연결 설정 없이 데이터그램을 전달하는 전송 계층 프로토콜
- 배경: TCP의 3-way handshake·순서 제어가 불필요한 서비스는 UDP로 RTT와 상태 저장 비용을 줄임
- 필요성: 손실·중복·순서 오류 복구를 애플리케이션 또는 별도 프로토콜에 위임해 지연 민감 서비스의 전송 효율을 높임

---

## Ⅱ. 구조 및 구성요소

```text
Application -> UDP Socket -> UDP Header -> IP Packet -> Network
                      / Port Demux
                      / Checksum
                      / App Reliability
```

| 구성요소 | 역할 | 특이사항 |
|:---|:---|:---|
| UDP 헤더 | 출발지/목적지 포트, 길이, 체크섬 포함 | 고정 8바이트 |
| 포트 다중화 | 목적지 포트로 수신 소켓 식별 | DNS 53, QUIC 443, NTP 123 |
| 체크섬 | 헤더·데이터 오류 검출 | IPv6에서는 UDP 체크섬 필수 |
| 애플리케이션 제어 | 재전송·순서·혼잡 제어 선택 구현 | QUIC, RTP, 게임 프로토콜 |

> 요약: UDP 구조는 포트 다중화와 오류 검출만 전송 계층에서 제공하고, 전송 품질 제어는 상위 계층에 위임함.

---

## Ⅲ. 동작원리 및 흐름도

```text
데이터 생성 -> 목적지 IP/Port 지정 -> UDP 헤더 부착
-> IP 전달 -> 수신 호스트 포트 분기 -> 애플리케이션 처리
```

| 단계 | 처리 내용 | 검증 기준 |
|:---:|:---|:---|
| 1 | 송신 소켓이 목적지 IP·포트 지정 | 5-tuple 로그 |
| 2 | UDP 헤더와 체크섬 생성 | 헤더 길이 8바이트 확인 |
| 3 | IP 계층이 라우팅·MTU 처리 | 단편화율, PMTU |
| 4 | 수신 커널이 포트 기준 소켓 전달 | socket receive queue drop |
| 5 | 애플리케이션이 손실·순서 처리 | app retry count, jitter |

> 요약: UDP는 연결 상태 없이 포트로 전달되며, 손실 복구와 순서 보장은 애플리케이션 설계 항목임.

---

## Ⅳ. 특징

| 구분 | TCP | UDP | 수치·표준 포인트 |
|:---|:---|:---|:---|
| 연결 설정 | 3-way handshake | handshake 없음 | TCP 1 RTT, UDP 0 RTT |
| 헤더 | 최소 20바이트 | 8바이트 | IPv4 기준 옵션 제외 |
| 신뢰성 | 순서·재전송 제공 | 상위 계층 구현 | QUIC은 UDP 443 위에서 재전송 |
| 적용 | 파일, 웹 HTTP/1.1·2 | DNS, RTP, QUIC, 게임 | DNS 53, NTP 123 |

> 요약: UDP는 전송 계층 기능을 줄여 RTT와 헤더 비용을 낮추고, 필요한 제어는 애플리케이션에서 선택 구현함.

---

## Ⅴ. 심화 비교 및 적용 판단

| 비교 축 | 기존/대안 | UDP 적용 | 선택 기준 |
|:---|:---|:---|:---|
| 지연 | TCP 연결 수립 1 RTT | 0 RTT 데이터 전송 | DNS·NTP·게임 상태 동기화 |
| 신뢰성 | TCP 자동 재전송 | 앱 레벨 ACK/Retry | 손실 1~3% 허용 여부 |
| 운영 | 세션 상태 유지 | NAT timeout 관리 필요 | UDP idle timeout 30~120초 점검 |

> 요약: UDP 선택은 RTT 절감 이득과 애플리케이션 복구 책임을 동시에 계산해야 함.

| 리스크 | 원인 | 대응 방안 | 확인 지표 |
|:---|:---|:---|:---|
| 패킷 손실 | 혼잡·무선 간섭 | 앱 재전송, FEC, jitter buffer | packet loss %, retry count |
| 증폭 공격 | spoofed source와 큰 응답 | BCP 38, rate limit, 응답 크기 제한 | amplification ratio |
| NAT 끊김 | UDP 상태 timeout | keepalive 15~30초, STUN/TURN | session timeout count |

> 요약: UDP 운영 리스크는 손실·증폭·NAT 상태이며, 재전송 정책과 레이트 제한으로 통제함.

| 점검 항목 | 목표 기준 | 측정 방법 |
|:---|:---|:---|
| 지연 | p95 one-way delay 50ms 이하 | APM, synthetic probe |
| 손실 | packet loss 1% 이하 또는 앱 허용치 | NetFlow, pcapture |
| 큐 드롭 | socket receive drop 0.1% 이하 | OS counter, eBPF |

> 요약: UDP 서비스는 RTT만 보지 말고 손실률, 큐 드롭, 앱 재전송률을 함께 측정해야 함.

## Ⅵ. 실무 적용 및 결론

**적용 방안 3개 (필수):**
1. DNS·NTP: UDP 53/123 기본, 응답 크기 초과·DNSSEC 조건에서는 TCP fallback과 EDNS0 크기 1232바이트 검토
2. 실시간 미디어: RTP/RTCP, jitter buffer 20~50ms, packet loss 1% 초과 시 FEC 또는 bitrate 조정 적용
3. 보안 운영: UDP reflection 방지를 위해 ingress filtering, per-source rate limit, NetFlow 기반 top talker 탐지 구성

**결론 (2줄):**
- 기술사 판단: 손실 허용·지연 민감이면 UDP, 순서·무결한 전달이 우선이면 TCP 또는 QUIC 적용 조건을 비교함
- 향후 방향: HTTP/3와 실시간 AI 스트리밍 확산으로 UDP 443 관측, QoS, 방화벽 정책 설계가 네트워크 운영 항목이 됨
