# 📖 【암기용】 개념 완전 이해

> 목적: 이 개념을 처음 보는 사람도 완벽히 이해하게 만든다. 시험 답안 양식이 아니라, 이해를 위한 친절한 설명이다.

## 한눈에
- **개요**: 연결 설정 과정 없이 데이터를 독립적인 데이터그램으로 빠르게 전송하는 4계층 프로토콜
- **왜 필요한가**: 동영상 스트리밍이나 음성 통화처럼 데이터 일부가 유실되더라도 끊김 없이 빠르게 전송해야 하는 서비스가 늘어났다.
- **핵심 직관**: 상대방이 받을 준비가 되었는지 묻지 않고 일단 우편물을 던져놓는 일방통행 배달부다.

## 깊이 이해
- **배경·문제의식**: TCP는 3-Way Handshake, 패킷 재전송, 혼잡 제어를 수행하므로 신뢰성은 높지만 지연(Delay)이 크다. 실시간성이 생명인 서비스에서는 "정확한 늦음"보다 "약간 틀리더라도 빠른 것"이 더 중요하다.
- **작동 원리**: UDP는 포트 번호와 오류 검출용 체크섬(Checksum)만 붙인 8바이트의 단순한 헤더를 사용하여 데이터를 던진다. 손실이 발생해도 재전송을 요구하지 않고 다음 데이터를 보낸다.
- **비유**: TCP가 등기 우편이라면, UDP는 일반 엽서다. 엽서는 중간에 분실될 수 있고 도착 순서도 뒤죽박죽일 수 있지만 빠르고 싸게 보낼 수 있다.
- **구체 예시**: 넷플릭스 영상이나 디스코드 음성 통화 시 프레임 하나가 깨지면 화면이 잠깐 튀지만, 다시 받아오기 위해 전체 영상을 멈추는(버퍼링) 것보다는 낫다.
- **흔한 오해·주의점**: "UDP는 신뢰성이 없어서 나쁘다"는 틀렸다. 신뢰성 제어를 애플리케이션 계층(L7)으로 넘긴 것뿐이며, 최근 QUIC처럼 UDP 위에서 자체적인 신뢰성을 구현하는 최적화가 대세다.

## 연결 개념
- TCP (Transmission Control Protocol) — UDP와 대비되는 신뢰성 기반 전송 프로토콜
- RTP (Real-time Transport Protocol) — UDP 위에서 실시간 미디어를 전송하는 표준
- QUIC — UDP 기반으로 TCP+TLS 기능을 통합한 차세대 프로토콜

# 📝 【답안용】 시험 답안 템플릿

> 목적: 시험장에서 25분에 그대로 쓰는 답안 양식. 작성방식(추상표현 금지·수치·도식·문제유형 전환)을 엄격히 지킨다.
> 핵심: 이 시험은 정보를 많이 나열하는 시험이 아니라, 문제 신호어에서 출제자 의도를 읽고 핵심 논점을 선별해 쓰는 시험이다.

## 핵심 인사이트 (3줄 요약)

> 1. **본질**: 비연결형(Connectionless), 비신뢰성(Unreliable) 특징을 가지며 최소한의 헤더(8바이트)로 데이터를 전송하는 트랜스포트 계층 프로토콜이다.
> 2. **가치**: 연결 설정 지연(Handshake)과 재전송 오버헤드를 제거하여 실시간 스트리밍, DNS 질의, IoT 디바이스 통신의 지연(Latency)을 최소화한다.
> 3. **판단 포인트**: 프로토콜 선택 시 재전송에 의한 지연 비용과 데이터 일부 유실의 수용 가능성을 저울질하여 TCP와 UDP를 분리 적용해야 한다.

## 출제 의도 및 답안 포인트

| 출제 의도 | 반드시 짚을 핵심 | 감점 회피 포인트 |
|:---|:---|:---|
| TCP와의 차이 및 UDP 활용처 이해 | 8바이트 헤더, 비연결성, 실시간 서비스 적용 | 단순히 "빠르다, 신뢰성 없다"로 끝나는 추상적 나열 |
| 신규 프로토콜 동향 인식 확인 | QUIC, HTTP/3 등 UDP 기반 L7 신뢰성 제어 트렌드 | 과거의 단순 스트리밍 용도로만 한정하는 서술 |

> 요약: UDP의 단순함을 기반으로 한 실시간성 확보와 최근 QUIC으로 이어지는 UDP의 재발견(L7 제어) 흐름을 짚어낸다.

## Ⅰ. 개요 및 필요성

- 정의: 송수신 간 논리적 연결 없이 데이터그램을 독립적으로 전송하는 RFC 768 표준 4계층 프로토콜
- 배경: TCP의 헤더 오버헤드(20바이트)와 혼잡 제어 메커니즘이 실시간 멀티미디어 전송에 병목으로 작용
- 필요성: 네트워크 지연(RTT) 50ms 이내 보장 등 신속한 데이터 전송이 데이터 무결성보다 우선시되는 서비스 증가

---

## Ⅱ. 구조 및 구성요소

```text
[UDP 데이터그램 구조: 총 8바이트 헤더 + 페이로드]
Source Port (16) -> Dest Port (16) -> Length (16) -> Checksum (16) -> Payload
      |                   |                 |                 |
      + 송신 프로세스     + 수신 프로세스   + 전체 길이       + 오류 검출
```

| 구성요소 | 역할 | 특이사항 |
|:---|:---|:---|
| Source Port (2B) | 응답을 받을 송신 측 포트 번호 | 응답이 불필요한 경우 0으로 설정 가능 |
| Destination Port (2B) | 수신 측 프로세스 식별자 | 멀티플렉싱/디멀티플렉싱 기준 |
| Length (2B) | 헤더와 데이터를 포함한 전체 바이트 길이 | 최소 8바이트 (헤더만 존재 시) |
| Checksum (2B) | 헤더와 데이터의 무결성 검증 (오류 검출) | IPv4에서는 선택사항, IPv6에서는 필수 |

> 요약: UDP는 20바이트 이상인 TCP 헤더와 달리 8바이트의 최소 필드만 구성하여 캡슐화 및 파싱 오버헤드를 극소화했다.

---

## Ⅲ. 동작원리 및 흐름도

```text
송신 애플리케이션 -> UDP 소켓 -> (연결 설정 없음) -> IP 계층 전송 -> 수신 UDP 소켓 -> 수신 프로세스
```

| 단계 | 처리 내용 | 검증 기준 |
|:---:|:---|:---|
| 1 | 데이터 분할 및 캡슐화 | 64KB(최대 크기) 이하 데이터그램 생성 |
| 2 | 연결 없이 즉시 전송 | Handshake 과정 0-RTT 처리 |
| 3 | 무결성 검증 (수신) | Checksum 불일치 시 패킷 자동 폐기 (재요청 안 함) |
| 4 | 애플리케이션 전달 | 포트 번호 기반으로 프로세스에 디멀티플렉싱 |

> 요약: 연결 설정이나 상태 정보 유지(Stateful) 과정 없이 패킷을 독립적으로 쏘고 폐기하는 단순 단방향 흐름을 가진다.

---

## Ⅳ. 특징

| 구분 | 내용 | 판단 포인트 |
|:---|:---|:---|
| 속도 (지연) | 3-Way Handshake 생략으로 초기 지연 제로 (0-RTT) | 실시간 스트리밍(VoIP) 채택 기준 |
| 오버헤드 | 헤더 8바이트 고정, 상태 정보 유지 불필요 | 수만 개 단말이 접속하는 IoT 서버 부하 감소 |
| 전송 보장 | 순서 역전 및 데이터 유실 발생 가능 (Best-Effort) | 데이터 정합성이 필수라면 애플리케이션 단 오류 제어 필요 |

> 요약: 신뢰성을 포기한 대신 초기 접속 지연 시간(RTT)을 없애고 헤더 파싱 자원 소모를 최소화한다.

## Ⅴ. 심화 비교 및 적용 판단

| 비교 축 | TCP | UDP | 선택 기준 |
|:---|:---|:---|:---|
| 연결 방식 | 연결 지향 (3-Way Handshake) | 비연결 지향 (Connectionless) | 초기 접속 지연 허용치 (허용 불가시 UDP) |
| 신뢰성 제어 | ARQ, 슬라이딩 윈도우 지원 | 제어 없음 (L7에서 직접 구현) | 데이터 무결성 100% 요구 여부 |
| 트래픽 제어 | 혼잡 제어, 흐름 제어 | 제어 없음 (보낼 수 있는 만큼 전송) | 대역폭 포화 시 트래픽 양보 필요 여부 |

> 요약: 파일 전송 및 웹 페이지 로딩은 정합성이 보장되는 TCP를, 실시간 미디어 및 짧은 질의응답은 지연이 없는 UDP를 선택한다.

| 리스크 | 원인 | 대응 방안 | 확인 지표 |
|:---|:---|:---|:---|
| 데이터 순서 역전 | 패킷별 라우팅 경로 상이 | L7에 순서 번호(Sequence Num) 부여 (예: RTP) | Out-of-Order 패킷 비율 |
| 패킷 유실 시 단절 | 라우터 큐 오버플로우로 폐기 | FEC(전진 에러 수정) 및 중복 패킷 전송 | 패킷 손실률 (Packet Loss Rate) < 1% |
| 대규모 트래픽 유발 | 혼잡 제어 부재로 망 포화 | 애플리케이션 레벨의 전송률 제한(Rate Limit) 구현 | 대역폭 점유율 및 지터(Jitter) 수치 |

> 요약: UDP 자체에는 제어 기능이 없으므로, 애플리케이션 계층에서 RTP나 FEC를 추가해 최소한의 서비스 품질(QoS)을 방어해야 한다.

## Ⅵ. 실무 적용 및 결론

**적용 방안 3개:**
1. 실시간 미디어 전송: WebRTC 미디어 채널(RTP/RTCP over UDP) 구축으로 200ms 이하의 실시간 양방향 화상 회의 구현
2. 마이크로서비스 DNS: Kubernetes 클러스터 내부 CoreDNS 질의응답을 UDP 53포트로 처리해 마이크로서비스 간 Discovery 지연 최소화
3. 차세대 웹 프로토콜 기반: TCP 홀블로킹을 해결하기 위해 UDP 위에서 자체 암호화와 신뢰성을 구현한 QUIC(HTTP/3) 프로토콜 전면 도입

**결론 (2줄):**
- 기술사 판단: 서비스 특성 상 "정확도 100%"보다 "지연 50ms 이하"가 중요하다면 애플리케이션 제어를 전제로 UDP를 채택한다.
- 향후 방향: 과거에는 단순 스트리밍용이었으나, 현재는 TCP 한계를 극복하기 위해 QUIC처럼 UDP 위에 신뢰성 계층을 얹는 커스텀 프로토콜 뼈대로 진화하고 있다.
