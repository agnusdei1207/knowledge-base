# 📖 【암기용】 개념 완전 이해

## 한눈에
- **개요**: 프로토콜 3요소는 통신 **프로토콜(규약)**이 성립하기 위해 반드시 합의해야 하는 세 축 — **구문(Syntax)·의미(Semantics)·타이밍(Timing)**이다.
- **왜 필요한가**: 001·002에서 본 각 계층의 프로토콜도 결국 이 세 가지 약속의 묶음이다. 셋 중 하나라도 어긋나면 통신은 실패한다.
- **핵심 직관**: **구문**="어떤 형식으로 쓸까", **의미**="그게 무슨 뜻이고 뭘 할까", **타이밍**="언제·얼마나 빠르게·어떤 순서로 보낼까".

## 핵심 용어 정리 (내부에 등장하는 것들)

계층·헤더·플래그·프레임 등 통신 구조 용어는 001·002에서 다뤘으므로, 여기서는 3요소와 직결된 용어를 정리한다.

| 용어/표기 | 의미 | 비유·예 |
|:---|:---|:---|
| 프로토콜 (Protocol) | 통신 당사자 간에 미리 합의한 규칙의 총칭. 3요소로 구성됨 | 두 나라가 정한 외교 의전 규칙 |
| 구문 (Syntax) | 데이터의 형식·구조·부호화·신호 레벨 (형태에 대한 약속) | 편지의 "우표는 우상단, 주소는 중앙" 배치 규칙 |
| 의미 (Semantics) | 각 비트·필드가 무엇을 뜻하고 어떤 동작을 지시하는지 (뜻·제어) | "긴급" 도장이 우선 처리를 뜻하는 것 |
| 타이밍 (Timing) | 통신 속도·전송 순서·시점 (언제·얼마나·순서) | 말하는 속도와 순서를 맞추는 대화 예절 |
| 부호화 (Encoding) | 데이터를 전송용 비트/신호 패턴으로 바꾸는 규칙 (구문 요소) | 문자를 모스 부호로 변환 |
| 플래그 (Flag) | 특정 제어 상태를 1비트로 표시하는 필드 (의미 요소) | SYN=연결 요청, ACK=응답 확인 |
| 흐름 제어 (Flow Control) | 수신자 처리 속도에 맞춰 송신 속도를 조절 (타이밍 요소) | 상대가 받아 적을 때까지 천천히 말하기 |
| 슬라이딩 윈도우 | 수신 여력만큼 미리 여러 패킷을 보내는 동적 흐름 제어 기법 | 상대 바구니 크기만큼만 공을 던지는 것 |
| TLV (Type-Length-Value) | 타입·길이·값 구조로 필드를 유연하게 확장하는 구문 설계 | 이름표+글자 수+내용으로 상자를 유연 포장 |
| FSM (유한상태기계) | 프로토콜의 상태 전이를 유한한 상태 집합으로 정의한 모델 | 신호등의 빨강→초록→노랑 상태 전이 |

## 깊이 이해
- **배경·문제의식**: 두 컴퓨터가 전선으로 이어졌다고 통신이 되는 게 아니다. 0·1의 연속을 어디서 끊고 어떻게 해석할지 사전 약속이 없으면 수신 측은 쓰레기 데이터로 인식한다. 001·002가 "통신을 계층으로 나눈다"였다면, 3요소는 "그 계층의 약속 하나하나가 무엇으로 이뤄지는가"를 푼다.
- **작동 원리(어떻게+왜)**:
  - **구문(Syntax)**: 헤더 필드의 순서·비트 길이·부호화를 정한다. 예) TCP 헤더는 앞 16비트=출발지 포트, 다음 16비트=목적지 포트. 구문이 있어야 수신 측이 비트 스트림을 필드로 잘라 파싱할 수 있다.
  - **의미(Semantics)**: 각 필드·플래그가 지시하는 동작을 정한다. 예) SYN 플래그=1이면 "연결 요청", 체크섬 불일치=오류이므로 재전송. 의미가 있어야 파싱한 값으로 무엇을 할지 정해진다.
  - **타이밍(Timing)**: 전송 속도·순서·시점을 정한다. 예) 순서번호로 1번 다음 2번을 보장하고, 혼잡 시 윈도우 크기를 줄여 속도를 낮춘다. 타이밍이 있어야 빠른 송신자가 느린 수신자의 버퍼를 넘치게 하지 않는다.
- **비유**: 편지에서 "우표·주소의 배치 규칙"은 **구문**, "긴급 도장의 뜻"은 **의미**, "도착 날짜와 순서"는 **타이밍**이다. 셋이 다 맞아야 편지가 제대로 전달된다.
- **구체 예시**: TCP 3-way handshake는 세 요소가 함께 작동한다. 헤더에 포트·순서번호를 규정 형식으로 배치(구문), SYN·ACK 플래그로 "연결 요청/수락"을 지시(의미), 순서번호와 윈도우로 전송 순서·속도를 조율(타이밍).
- **흔한 오해·주의점**: 세 요소는 독립이 아니라 상호 의존한다. 구문이 틀리면(포맷 오류) 의미를 해석조차 못 하고(파싱 에러), 타이밍이 안 맞으면(속도 초과) 데이터가 유실(버퍼 오버플로우)된다. "타이밍=단순히 시간"으로 뭉뚱그리면 동어반복 감점이다 — 순서 보장·속도 조절·시점 동기화를 구체적으로 짚어야 한다.

## 연결 개념
- 프로토콜 스택(001·002) — 3요소로 이뤄진 프로토콜을 계층으로 쌓은 것
- 캡슐화 — 구문에 따라 헤더를 붙이는 행위
- 흐름·혼잡 제어(028·029) — 타이밍 요소의 대표 메커니즘

> 2. **가치**: 세 축이 일치해야 파싱 정합성·오류 복구·버퍼 오버플로우 방지가 성립해 신뢰성 통신이 보장됨.

| 각 요소의 네트워크 매핑 | 구문=헤더 포맷, 의미=플래그/오류제어, 타이밍=흐름제어 | "타이밍은 시간이다" 식 동어반복 |

## Ⅰ. 개요 및 필요성

- 개요: 통신 규약 성립에 필요한 데이터 형식·제어 정보·전송 타이밍의 세 합의 축임
- 배경: (001·002 참조) 제조사별 상이한 통신 방식에서 비트 오해석·버퍼 고갈로 데이터 손실 발생
- 필요성: 일관된 파싱(구문)·명확한 해석(의미)·동적 속도 조절(타이밍)로 종단 간 신뢰성을 확보하기 위함

---

## Ⅱ. 구조 및 구성요소

```text
[송신]                                      [수신]
구문: 포맷 조립 (Header/Payload)      →   구문: 구조 해석 (Parsing)
의미: 제어·오류 표시 (Flag/CRC)       →   의미: 명령 수행 (Action)
타이밍: 전송 속도 제어 (Window)        →   타이밍: 수신 버퍼 속도 매칭
```

| 구성요소 | 개념 | 주요 역할 | 실제 프로토콜 예시 |
|:---|:---|:---|:---|
| 구문 (Syntax) | 데이터 형식·부호화·신호 레벨 | 구조 식별, 파싱 기준 제공 | TCP 16비트 포트, IPv4 20B 헤더 |
| 의미 (Semantics) | 제어·오류 관리를 위한 해석 규칙 | 명령 해석, 예외·오류 복구 | TCP SYN/ACK, HTTP 404 |
| 타이밍 (Timing) | 통신 속도·전송 순서·시점 | 흐름·혼잡 제어, 순서 보장 | 슬라이딩 윈도우, 순서번호 |

> 요약: 구문은 데이터의 '형태', 의미는 '뜻과 제어', 타이밍은 '속도와 순서'를 규정해 상호 운용의 뼈대를 이룸.

---

## Ⅲ. 동작원리 및 흐름도

```text
통신 개시 → 구문: 패킷 조립 → 의미: 제어 플래그 설정 → 타이밍: 혼잡도 맞춰 전송 → 수신 역해석
```

1. **구조화 (구문)**: 헤더 필드 순서·비트 길이에 맞춰 페이로드를 조립함
2. **명령 부여 (의미)**: 연결(SYN)·오류검출(CRC) 등 제어 비트를 할당함
3. **속도 동기화 (타이밍)**: 수신 윈도우 크기에 맞춰 전송 속도·순서를 조절함
4. **수신 역해석**: 수신 측이 구문 파싱 후 의미대로 처리하고 타이밍에 맞춰 응답함

> 요약: 형식 검증(구문)→명령 수행(의미)→속도 피드백(타이밍)의 순환 고리로 송수신이 이뤄짐.

---

## Ⅳ. 특징

- 상호 의존성: 구문 오류 시 의미 해석 불가, 타이밍 불일치 시 데이터 유실로 세 요소가 연쇄됨
- 확장성 지원: TLV 구문으로 하위 호환을 유지하며 필드를 확장함 (IPv4 옵션, HTTP 헤더)
- 구문 트레이드오프: 구문이 복잡할수록 파싱 오버헤드 증가 → IoT는 CoAP·MQTT로 경량화 필수
- 의미 트레이드오프: 제어 의미가 풍부할수록 제어 트래픽·상태 관리 부담 증가
- 타이밍 동적성: 고정 속도가 아니라 네트워크 상태를 반영해 윈도우를 동적 조절함

---

## Ⅴ. 심화 비교 및 적용 판단

| 구분 | HTTP/1.1 (전통) | HTTP/2·QUIC (차세대) |
|:---|:---|:---|
| 구문 | Text 기반, 사람이 읽기 쉬움 | Binary 프레이밍, 파싱 빠름 |
| 의미 | 메서드·헤더 중심 | 스트림·멀티플렉싱·헤더압축(HPACK) |
| 타이밍 | 순차 전송, HoL 블로킹 | 비동기 스트림, 0-RTT |
| 적용 | 단순·디버깅 용이 | 대규모 병렬·모바일 저지연 |

> 요약: 프로토콜 진화는 파싱을 줄이는 바이너리 구문과 지연을 줄이는 비동기 타이밍으로 발전함.

- 파싱 에러·보안 취약: 구문 예외 처리 미흡 → 스키마 검증·퍼징 테스트로 방어
- 데드락·연결 지연: 의미 해석 오류·상태 불일치 → FSM 검증과 타임아웃 강제
- 버퍼 오버플로우·혼잡: 타이밍 제어 실패 → 슬라이딩 윈도우·백프레셔(Backpressure) 적용

---

## Ⅵ. 실무 적용 및 결론

- IoT 경량 설계: 대역폭 제한 환경에서 헤더 구문을 축소하고 Publish-Subscribe 의미의 MQTT를 적용함
- 마이크로서비스 최적화: 텍스트 JSON 대신 바이너리 gRPC/Protobuf로 구문·타이밍을 개선함
- 3요소 관점 장애 모니터링: 구문 오류(Malformed)·의미 오류(Bad Flag)·타이밍 오류(Retransmission)를 분리 대시보드화함
- 결론(조건부 판단): 3요소는 이론에 그치지 않고 EAI/ESB·API(REST/gRPC) 설계 시 정합성·성능의 척도임
- 결론(향후 방향): V2X·자율주행에서는 밀리초 타이밍 제어와 동적 의미 확장이 가능한 적응형 프로토콜이 요구됨
