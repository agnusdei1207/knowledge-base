# 📖 【암기용】 개념 완전 이해

> 목적: 프로토콜 3요소를 단순 암기가 아니라 통신 약속의 구성 조건으로 이해하게 만든다. 시험 답안 양식이 아니라, 네트워크 메시지가 성립하는 이유를 설명한다.

## 한눈에
- **개요**: 프로토콜은 구문, 의미, 타이밍으로 구성되는 통신 규칙이다.
- **왜 필요한가**: 송신자와 수신자가 같은 형식, 같은 해석, 같은 순서와 속도로 메시지를 처리해야 통신 오류를 줄일 수 있다.
- **핵심 직관**: 약속된 문장 형식, 뜻, 말하는 순서가 맞아야 대화가 성립한다.

## 깊이 이해
- **배경·문제의식**: 네트워크에는 운영체제, 장비, 언어, CPU 구조가 다른 노드가 섞여 있다. 공통 규칙 없이는 같은 비트열도 서로 다르게 해석한다.
- **작동 원리**: 구문은 프레임·패킷·필드 길이 같은 형식을 정한다. 의미는 각 필드 값과 제어 코드의 뜻을 정한다. 타이밍은 언제 보내고 언제 기다리며 재전송할지를 정한다.
- **비유**: 회의에서 양식이 구문, 의제별 해석이 의미, 발언 순서와 제한 시간이 타이밍에 해당한다.
- **구체 예시**: TCP는 헤더 형식이 구문, SYN·ACK 플래그 의미가 의미, 3-way handshake와 재전송 타이머가 타이밍이다.
- **흔한 오해·주의점**: 구문만 맞아도 통신이 성립한다고 보면 안 된다. 의미 불일치와 타이밍 불일치는 패킷 형식이 맞아도 장애를 만든다.

## 연결 개념
- TCP/IP 모델: 프로토콜 3요소가 계층별로 구현되는 구조
- 상태 머신: 의미와 타이밍을 상태 전이로 표현
- 상호 운용성 시험: RFC 준수 여부 검증

# 📝 【답안용】 시험 답안 템플릿

> 목적: 시험장에서 25분에 그대로 쓰는 답안 양식. 작성방식(추상표현 금지·수치·도식·문제유형 전환)을 준수한다.
> 핵심: 프로토콜 3요소는 구문·의미·타이밍을 각각 필드 형식, 제어 의미, 송수신 순서·시간 제어로 연결해 써야 한다.

## 핵심 인사이트 (3줄 요약)

> 1. **본질**: 네트워크 프로토콜 3요소는 통신 메시지의 형식인 구문, 필드 해석인 의미, 송수신 순서·시간 제어인 타이밍이다.
> 2. **가치**: 이기종 장비가 RFC 기반 동일 규칙으로 메시지를 만들고 해석하며 재전송·흐름 제어를 수행하게 한다.
> 3. **판단 포인트**: 시험 답안은 TCP, HTTP, DNS 같은 구체 프로토콜의 필드·상태·타이머 예시로 3요소를 설명해야 한다.

## Ⅰ. 개요 및 필요성

- 정의: 구문·의미·타이밍으로 구성되는 통신 규칙
- 배경: 이기종 장비·소프트웨어가 같은 메시지를 교환하려면 형식·해석·순서가 일치해야 함
- 필요성: RFC 기반 상호 운용성 확보와 장애 원인(형식/해석/시간) 분리 판단의 기준

---

## Ⅱ. 구조 및 구성요소

```text
Protocol Specification
-> Syntax: field format / length / encoding
-> Semantics: control meaning / operation / state
-> Timing: sequence / timeout / retransmission / rate
-> Interoperable Communication
```

| 구성요소 | 역할 | 대표 예시 |
|:---|:---|:---|
| 구문 (Syntax) | 메시지 구조와 필드 배치 정의 | IP header, TCP header, DNS message format |
| 의미 (Semantics) | 필드 값과 제어 동작 해석 | TCP SYN, HTTP 404, DNS NXDOMAIN |
| 타이밍 (Timing) | 송수신 순서, 시간 제한, 재전송 제어 | TCP RTO, DHCP lease, DNS TTL |

> 요약: 구문은 모양, 의미는 뜻, 타이밍은 순서와 시간 제어를 담당하며 셋 중 하나가 깨지면 통신 장애가 발생한다.

---

## Ⅲ. 동작원리 및 흐름도

```text
송신 요구
-> Syntax에 맞는 메시지 생성
-> Semantics에 맞는 제어 필드 설정
-> Timing에 맞는 전송 순서·타이머 적용
-> 수신 검증 -> 상태 전이 -> 응답 또는 재전송
```

| 단계 | 처리 내용 | 검증 기준 |
|:---:|:---|:---|
| 1 | 헤더·본문 필드 길이와 인코딩 생성 | RFC field length, checksum |
| 2 | 제어 플래그와 상태 값 설정 | SYN/ACK, opcode, status code |
| 3 | 송신 순서와 타이머 적용 | RTO, TTL, lease time |
| 4 | 수신 측 구문·의미 검증 | malformed packet, invalid state |
| 5 | 응답, 폐기, 재전송 수행 | timeout count, retransmission rate |

> 요약: 프로토콜은 형식 생성, 의미 부여, 시간 제어, 수신 검증, 상태 전이 순서로 동작한다.

## Ⅳ. 특징

| 구분 | 구문 | 의미 | 타이밍 |
|:---|:---|:---|:---|
| 관리 대상 | 비트·바이트 배열 | 필드 값의 해석 | 순서·간격·시간 제한 |
| 오류 유형 | malformed packet | invalid opcode, state mismatch | timeout, duplicate, retransmission |
| 검증 도구 | Wireshark decode, schema | state machine test | packet trace, timer log |
| 수치·표준 | header length, MTU 1500 | RFC status code | TTL, RTO, DHCP lease |

> 요약: 구문·의미·타이밍은 오류 유형과 검증 도구가 다르므로 답안에서 분리해 제시해야 한다.

## Ⅴ. 심화 비교 및 적용 판단

| 비교 축 | 단순 메시지 규칙 | 프로토콜 3요소 | 선택 기준 |
|:---|:---|:---|:---|
| 설계 범위 | 필드 형식 중심 | 형식+해석+시간 제어 | 상호 운용 프로토콜은 3요소 모두 문서화 |
| 검증 | 파서 테스트 | 파서+상태 머신+타이머 테스트 | RFC compliance 필요 시 3종 시험 수행 |
| 장애 분석 | packet parse 오류 확인 | format/state/timeout 분리 | 재전송·세션 장애는 타이밍 우선 확인 |

> 요약: 네트워크 프로토콜 설계와 장애 분석은 필드 형식만으로 부족하며 상태와 타이머 검증이 필요하다.

| 리스크 | 원인 | 대응 방안 | 확인 지표 |
|:---|:---|:---|:---|
| 구문 불일치 | 버전·필드 길이 차이 | RFC 버전 고정, backward compatibility | malformed packet 비율 |
| 의미 불일치 | 상태 코드·플래그 해석 차이 | state machine 표준화, conformance test | invalid state count |
| 타이밍 불일치 | timeout·retransmission 정책 차이 | RTO, TTL, lease time 기준 문서화 | timeout rate, duplicate packet |

> 요약: 3요소별 리스크는 형식 불일치, 해석 불일치, 시간 제어 불일치로 나누어 통제한다.

| 점검 항목 | 목표 기준 | 측정 방법 |
|:---|:---|:---|
| 구문 준수 | RFC 필드 길이 위반 0건 | fuzz test, packet decoder |
| 의미 준수 | 상태 전이 coverage 100% | state machine test |
| 타이밍 준수 | timeout rate 1% 이하, TTL 정책 준수 | packet capture, timer log |

> 요약: 프로토콜 품질은 구문 파싱, 상태 전이, 타이머 동작을 각각 측정해야 한다.

## Ⅵ. 실무 적용 및 결론

**적용 방안 3개:**
1. 명세 작성: message format, field meaning, state transition, timeout 값을 RFC 형식 표로 분리 문서화
2. 시험 구축: Wireshark dissector, fuzz test, state transition test, retransmission scenario를 CI에 포함
3. 운영 관측: malformed packet, invalid state, timeout, retransmission 지표를 프로토콜별 로그로 수집

**결론 (2줄):**
- 기술사 판단: 프로토콜 설계·비교 문제는 구문·의미·타이밍 3축으로 구조화하고 TCP/DNS/DHCP 예시를 병기함
- 향후 방향: QUIC, HTTP/3처럼 암호화된 전송에서도 메시지 형식, 상태, 타이머 관측 체계를 별도로 설계해야 함
