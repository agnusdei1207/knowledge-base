# 📖 【암기용】 개념 완전 이해

> 목적: 이 개념을 처음 보는 사람도 완벽히 이해하게 만든다. 시험 답안 양식이 아니라, 이해를 위한 친절한 설명이다.

## 한눈에
- **개요**: 클라이언트가 서버의 신원만 확인하는 일반 TLS와 달리, 서버와 클라이언트가 서로의 인증서를 교환하여 양방향으로 신원을 증명하는 통신 보안 기술
- **왜 필요한가**: 클라우드/마이크로서비스(MSA) 시대가 되면서, 방화벽 내부(사내망)라고 해서 무조건 안전하다고 믿을 수 없게 되었다. 내부 서버끼리 통신할 때도 "정말 네가 A서버가 맞는지" 검증해야 한다.
- **핵심 직관**: 클럽에 들어갈 때 손님(클라이언트)은 클럽(서버) 간판이 진짜인지 확인하고, 클럽 기도(서버)는 손님의 신분증을 확인하는 양방향 신분 검사다.

## 깊이 이해
- **배경·문제의식**: 기존 웹 브라우징(일반 TLS)은 서버가 가짜 피싱 사이트가 아닌지만 증명하면 됐다. 클라이언트는 ID/PW로 인증하니까. 하지만 API 통신이나 백엔드 시스템(B2B, MSA)끼리는 비밀번호를 칠 사람이 없다. 기계끼리 서로 믿을 수단이 필요하다.
- **작동 원리**: 핸드셰이크 중간에 서버가 인증서를 보내면서 클라이언트에게 "너도 인증서 줘(CertificateRequest)"라고 요구한다. 클라이언트도 자신을 증명하는 인증서와 서명을 보내면, 양쪽 모두 서로의 신원을 CA(인증기관)를 통해 검증한 뒤 암호화 통신을 시작한다.
- **비유**: 스파이 접선. 스파이 A(클라)가 "너 B 맞냐? 암구호 대봐." -> B(서버) "나 B 맞다(서버 인증서). 근데 너도 A 맞냐? 네 암구호 대봐." -> A(클라) "나 A 맞다(클라이언트 인증서)." 서로 확인 후 비밀 장부 오픈.
- **구체 예시**: 은행 시스템에서 프론트 서버가 결제 서버를 호출할 때 쓴다. 만약 해커가 내부망에 침투해 결제 서버를 찌르려 해도, 프론트 서버의 클라이언트 인증서(Private Key)가 없으므로 연결 자체가 거부된다.
- **흔한 오해·주의점**: "mTLS는 일반 인터넷 사용자(B2C)에게 쓴다"는 틀렸다. 일반 사용자 PC마다 인증서를 발급하고 갱신하는 건 불가능하다. 주로 인트라넷, B2B API, MSA 컨테이너(사이드카 프록시) 간의 기계 대 기계(M2M) 통신에 한정해서 쓴다.

## 연결 개념
- 제로 트러스트 (Zero Trust) — "내부망이라도 아무도 믿지 마라"는 최신 보안 철학. mTLS가 이를 구현하는 핵심 기술이다.
- 서비스 메쉬 (Service Mesh) — 쿠버네티스 등에서 서비스 간 통신 보안(mTLS)과 트래픽을 중앙 통제하는 인프라 계층 (예: Istio)
- CA (Certificate Authority) — 신분증(인증서)이 진짜라고 도장 찍어주는 사내 또는 공인 인증 기관

# 📝 【답안용】 시험 답안 템플릿

> 목적: 시험장에서 25분에 그대로 쓰는 답안 양식. 작성방식(추상표현 금지·수치·도식·문제유형 전환)을 엄격히 지킨다.
> 핵심: 이 시험은 정보를 많이 나열하는 시험이 아니라, 문제 신호어에서 출제자 의도를 읽고 핵심 논점을 선별해 쓰는 시험이다.

## 핵심 인사이트 (3줄 요약)

> 1. **본질**: 암호화 통신 수립(Handshake) 과정에서 서버뿐만 아니라 클라이언트도 X.509 인증서를 제출하도록 강제하여 양방향 신원 증명을 수행하는 L4/L7 보안 프로토콜이다.
> 2. **가치**: 경계 기반 보안(Firewall)이 무너진 마이크로서비스(MSA) 및 클라우드 환경에서 "네트워크 위치와 무관하게 신원이 검증된 주체 간 통신만 허용"하는 제로 트러스트 아키텍처를 구현한다.
> 3. **판단 포인트**: mTLS는 강력한 보안을 제공하지만 인증서 발급/갱신/폐기(CRL) 등 PKI 인프라 생명주기 관리 비용이 기하급수적으로 증가하므로, Istio 같은 서비스 메쉬를 통한 완전 자동화가 수반되어야 한다.

## 출제 의도 및 답안 포인트

| 출제 의도 | 반드시 짚을 핵심 | 감점 회피 포인트 |
|:---|:---|:---|
| 상호 인증 메커니즘의 차별성 이해 | CertificateRequest 단계 추가 및 클라이언트 인증서 검증 | 일반 TLS 핸드셰이크를 그리고 mTLS라 우기는 서술 |
| 제로 트러스트 환경에서의 적용 가치 | 내부망(East-West 트래픽) 수평 이동(Lateral Movement) 차단 | 단순히 "보안이 강화된다" 식의 빈 추상 표현 나열 |
| 실제 아키텍처 도입 한계와 대응 역량 | PKI 인증서 라이프사이클 관리 부담, Service Mesh 사이드카 자동화 | 애플리케이션 코드에 직접 인증서를 하드코딩하는 방식 제안 |

> 요약: mTLS의 통신 흐름 차이를 정확히 도식화하고, 인증서 노가다라는 치명적 운영 오버헤드를 어떻게 인프라 자동화(Service Mesh)로 풀 것인지 논리를 전개한다.

## Ⅰ. 개요 및 필요성

- 정의: TLS(Transport Layer Security) 핸드셰이크 과정에서 서버와 클라이언트가 서로의 X.509 디지털 인증서를 교환하여 양방향으로 인증하는 보안 표준
- 배경: 애플리케이션이 수백 개의 컨테이너로 쪼개지는 MSA 확산으로 인해, 내부망(사설 IP)을 믿는 기존 방화벽 중심의 경계(Perimeter) 보안 무력화
- 필요성: 망 내부로 침투한 공격자가 인가되지 않은 트래픽을 생성하는 측면 이동(Lateral Movement)을 원천 차단하기 위한 통신 엔드포인트 간 상호 신뢰 기반 마련

## Ⅱ. 구조 및 구성요소

```text
[mTLS를 적용한 Service Mesh (Istio) 통신 구조]
[마이크로서비스 A]                            [마이크로서비스 B]
  앱 코드 (비즈니스 로직, 평문)                 앱 코드 (비즈니스 로직, 평문)
       |                                          ^
       v (localhost)                              | (localhost)
  Envoy 사이드카 프록시 (A 인증서) ===== mTLS ===== Envoy 사이드카 프록시 (B 인증서)
       ^                                          ^
       |------------- (인증서 자동 발급/갱신) -----------|
                      [사내 Root CA (Control Plane)]
```

| 구성요소 | 역할 | 특이사항 |
|:---|:---|:---|
| Server Certificate | 클라이언트에게 서버의 신원 증명 | 일반 TLS와 동일한 기능 |
| Client Certificate | 서버에게 클라이언트의 신원 증명 | 클라이언트의 Private Key 기반 서명 포함 (핵심 차별화) |
| Private CA | 조직 내부 통신을 위한 사설 인증 기관 | Public CA(Verisign 등) 대신 사내 인프라용 CA 사용 |
| Sidecar Proxy | 앱을 대신하여 mTLS 터미네이션 수행 | 애플리케이션 코드 수정 없이 네트워크 계층에서 인증 일괄 처리 |

> 요약: 양방향 인증서가 필수이므로, 통신을 수행하는 기계(VM, 컨테이너, IoT 장비)마다 고유한 인증서와 비밀키 쌍이 미리 주입되어 있어야 한다.

## Ⅲ. 동작원리 및 흐름도

```text
[mTLS 핸드셰이크 흐름 (TLS 1.2 기준)]
클라이언트                                      서버
  | --- 1. ClientHello ------------------------> |
  |                                              |
  | <-- 2. ServerHello, Server 인증서 ---------- |
  | <-- 3. CertificateRequest (★ 핵심 추가) ----- | (너도 인증서 줘)
  | <-- 4. ServerHelloDone --------------------- |
  |                                              |
  | --- 5. Client 인증서 (★ 핵심 추가) --------> | (나의 신분증)
  | --- 6. ClientKeyExchange, CertificateVerify->| (비밀키로 서명해 증명)
  | --- 7. Finished ---------------------------> |
  | <-- 8. Finished ---------------------------- |
(양방향 신원 검증 완료, 암호화 데이터 송수신 시작)
```

| 단계 | 처리 내용 | 일반 TLS와의 차이 |
|:---:|:---|:---|
| 1 | 서버 신원 증명 및 키 협상 | 서버 인증서를 검증하는 과정은 동일함 |
| 2 | 서버의 클라이언트 인증 요청 | 서버가 `CertificateRequest` 패킷을 추가로 발송 |
| 3 | 클라이언트 신원 증명 | 클라이언트가 고유 인증서와 개인키 서명(`CertificateVerify`) 제출 |
| 4 | 상호 검증 및 세션 키 생성 | 양측 모두 CA의 서명을 확인한 뒤 대칭키 합의 완료 |

> 요약: 서버가 신원 증명을 요구(`CertificateRequest`)하고 클라이언트가 이에 응답(`CertificateVerify`)하는 딱 두 단계가 추가됨으로써 중간자 공격이 완전히 차단된다.

## Ⅳ. 특징

| 구분 | 내용 | 판단 포인트 |
|:---|:---|:---|
| 제로 트러스트 실현 | IP/서브넷에 의존하지 않고 인증서 서명 유무로만 접근 제어 | 물리적/논리적 망 분리(Network ACL)를 암호학적 신원 기반으로 대체 |
| 중간자 공격(MITM) 차단 | 프록시가 패킷을 가로채도 클라이언트 비밀키가 없어 서명 위조 불가 | 사내망에 침투한 해커의 패킷 스니핑 및 조작 완벽 방어 |
| 오버헤드 급증 | 핸드셰이크 절차 증가 및 암복호화에 따른 CPU 자원 추가 소모 | 일반 TLS 대비 약 10~20%의 레이턴시(Latency) 지연 감수 필수 |

> 요약: 보안 강도는 최고 수준이나, 수만 개의 인스턴스 각각에 인증서를 꽂아주고 만료 전에 교체하는 인프라 관리의 복잡성이 폭발적으로 증가한다.

## Ⅴ. 심화 비교 및 적용 판단

| 비교 축 | One-way TLS (일반 웹) | mTLS (상호 인증) | 선택 기준 |
|:---|:---|:---|:---|
| 인증 방향 | 단방향 (서버만 증명) | 양방향 (서버 ↔ 클라이언트) | 통신 양측이 미리 신뢰 관계를 맺을 수 있는가? |
| 클라이언트 자격 | 익명 불특정 다수 허용 | 사전에 인증서가 발급된 기기/앱 | B2C 대고객 서비스(TLS) vs 사내 B2B/M2M(mTLS) |
| 인증서 발급 주체 | 공인 인증기관 (Public CA) | 사설 인증기관 (Private CA) | 외부 브라우저 신뢰 필요성 여부 |

> 요약: mTLS는 불특정 다수와의 통신에는 적용 불가능하며, 회사 내 마이크로서비스, B2B 결제망 등 단말(Endpoint) 통제가 가능한 폐쇄망에만 적용한다.

| 리스크 | 원인 | 대응 방안 | 확인 지표 |
|:---|:---|:---|:---|
| 인증서 만료 장애 | 수작업 관리로 인증서 갱신 누락 | SPIFFE/SPIRE 기반 단기 인증서 자동 발급(수 시간 단위) 및 갱신 아키텍처 | 인증서 만료 30일 전 알람, 발급/갱신 자동화율 100% |
| 폐기 인증서(CRL) 병목 | 침해된 인증서 차단을 위한 CRL 조회 시 통신 병목 | OSCP Stapling 적용 또는 분산 통제 평면에서 프록시로 정책 즉각 푸시 | CRL/OCSP 응답 시간 50ms 이내 |

> 요약: mTLS 실패의 90%는 "인증서 만료"로 인한 전체 서비스 다운이므로, 사람이 관리하는 1년짜리 인증서 대신 기계가 관리하는 1시간짜리 임시 인증서 시스템을 구축해야 한다.

## Ⅵ. 실무 적용 및 결론

**적용 방안 3개:**
1. Service Mesh(Istio) 기반 애플리케이션 투명성 확보: 개발자는 HTTP 평문 통신 로직만 작성하고, 인프라단의 Envoy 사이드카 프록시가 mTLS 암호화 및 복호화를 투명하게(Transparent) 대행하도록 설계
2. 오픈뱅킹 B2B 전용 API 보안: 은행과 핀테크 기업 간 API 연동 시, 양사 간 사전 교환된 Private CA 인증서를 통해서만 방화벽 인바운드를 허용하는 mTLS VPN 구축
3. SPIFFE 기반 기계 신원 부여: 클라우드 동적 할당 환경에서 IP 대신 SPIFFE ID(포맷: `spiffe://domain/ns/my-app`)를 인증서의 SAN(Subject Alternative Name) 필드에 주입하여 컨테이너 스케일링 무관 검증 수행

**결론 (2줄):**
- 기술사 판단: 클라우드 네이티브 환경에서 mTLS는 제로 트러스트 아키텍처를 구현하는 필수 기반 기술이나, "애플리케이션 코드 결합 배제(사이드카 패턴)"와 "인증서 갱신 자동화" 없이는 운영 재앙을 초래한다.
- 향후 방향: 보안 통제가 망(Network)에서 신원(Identity)으로 이동하는 추세에 따라, 서비스 간 통신(mTLS)뿐 아니라 인프라 자원 접근 전체를 묶는 동적 신원 관리 플랫폼으로 발전하고 있다.

| 운영/설계형 | "MSA 환경에서 내부 통신 보안(제로트러스트) 방안을 설계하시오" | 사이드카 프록시를 통한 mTLS 대행 흐름 (애플리케이션 투명성) | Ⅴ/Ⅵ 인증서 라이프사이클 관리 한계와 Istio 자동화 방안 |

> 요약: 통신 구조 문제면 `CertificateRequest` 패킷을 강조하고, 아키텍처 설계 문제면 "코드 수정 없는 사이드카 적용"과 "인증서 갱신 자동화"를 해법으로 제시한다.
