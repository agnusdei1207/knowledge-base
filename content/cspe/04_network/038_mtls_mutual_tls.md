## 미리 알고가기

- TLS는 서버 신원을 검증하고 통신 내용을 암호화하는 기본 보안 프로토콜임
- mTLS는 서버와 클라이언트가 서로 인증서를 검증하는 양방향 TLS 방식임
- CA는 인증서 서명과 신뢰 체인 관리를 맡는 기관 또는 내부 PKI임
- 개인키는 인증서 주체만 가져야 하는 비밀 키이며 서명으로 소유를 증명함
- 서비스 메시는 마이크로서비스 사이의 통신 보안과 제어를 공통 계층에서 처리하는 구조임

## Ⅰ. 개요

- **정의/개념**: mTLS는 TLS 핸드셰이크 과정에서 서버뿐 아니라 클라이언트도 자신의 인증서와 서명으로 신원을 증명하게 하는 상호 인증 방식임
- **배경/필요성**: 내부망이라고 해서 모두 신뢰할 수 없고 API 호출 주체가 사람보다 서비스나 장비인 경우가 많아졌으므로, 비밀번호나 IP 허용 목록보다 강한 기계 신원 확인 수단이 필요함

## Ⅱ. 특징

- 서버와 클라이언트가 모두 인증서를 검증하므로 비인가 주체를 애플리케이션 앞단에서 차단할 수 있음
- 인증과 암호화가 같은 세션 안에서 이뤄져 별도 토큰 교환 절차를 줄일 수 있음
- 인증서 발급, 배포, 폐기, 회전이 운영 핵심이므로 PKI 자동화 수준이 품질을 좌우함
- 사람 사용자 인증을 완전히 대체하는 개념이 아니라 서비스 간 신원 확인을 강화하는 수단임

## Ⅲ. 종류 및 비교

| 판단 기준 | 단방향 TLS | mTLS |
|:---|:---|:---|
| 인증 대상 | 서버만 자신의 신원을 증명함 | 서버와 클라이언트가 모두 신원을 증명함 |
| 주된 적용 환경 | 공개 웹 서비스, 일반 사용자 접속에 널리 쓰임 | 내부 API, 서비스 메시, B2B 연동, 장비 인증에 적합함 |
| 접근 통제 수준 | 암호화는 되지만 호출 주체 식별은 별도 수단이 필요함 | 통신 시작 단계에서 허용된 클라이언트만 연결시킬 수 있음 |
| 운영 부담 | 서버 인증서 중심이라 상대적으로 단순함 | 클라이언트 인증서 수명주기와 신뢰 저장소 관리가 필수임 |
| 장애 원인 | 서버 인증서 만료나 체인 오류가 주원인임 | 여기에 클라이언트 인증서 만료, 배포 누락, CA 불일치가 추가됨 |

## Ⅳ. 구성요소 및 구조

| 구성요소 | 설명 |
|:---|:---|
| 서버 인증서 | 접속 대상 서버의 신원을 증명하며 클라이언트가 먼저 검증함 |
| 클라이언트 인증서 | 호출 주체 서비스나 장비의 신원을 증명하며 서버가 검증함 |
| CA 및 신뢰 저장소 | 어떤 인증서를 믿을지 정의하는 신뢰 기준이며 양측 검증의 출발점임 |
| 개인키와 서명 | 인증서 소유자가 실제로 개인키를 갖고 있음을 서명으로 증명하는 요소임 |
| 회전·폐기 절차 | 만료, 유출, 교체에 대응하기 위해 자동 배포와 폐기 전파가 함께 준비돼야 함 |

```text
+-------------+     +--------------------+     +--------------------+     +-------------+
| ClientHello | --> | 서버 인증서·요청 전송 | --> | 클라이언트 인증서·서명 | --> | 암호화 통신 |
+-------------+     +--------------------+     +--------------------+     +-------------+
```

## Ⅴ. 원리 및 절차 흐름도

```text
+-------------+     +-------------+     +----------------+     +----------------+     +-------------+
| 접속 시작     | --> | 서버 신원 확인 | --> | 클라이언트 신원 확인 | --> | 상호 검증 완료 | --> | 데이터 전송 |
+-------------+     +-------------+     +----------------+     +----------------+     +-------------+
```

1. **접속 시작**: 클라이언트가 ClientHello를 보내 암호 알고리즘 협상을 시작함
2. **서버 신원 확인**: 서버가 자신의 인증서를 보내고 클라이언트는 신뢰 체인과 이름 정보를 검증함
3. **클라이언트 신원 확인**: 서버가 인증서를 요구하면 클라이언트가 인증서와 서명을 보내 자신의 개인키 소유를 증명함
4. **상호 검증 완료**: 서버가 클라이언트 인증서를 확인하고 양측이 세션 키 계산을 마치면 핸드셰이크가 끝남
5. **데이터 전송**: 인증된 주체끼리만 애플리케이션 데이터를 암호화해 주고받음

## Ⅵ. 실무 적용 및 유의점

1. 서비스 메시나 내부 API처럼 동서 트래픽이 많은 환경에서는 mTLS를 기본 보안 계층으로 적용하되 인증서 자동 발급과 회전이 없으면 운영이 바로 불안정해지므로 인증서 만료 여유일, 배포 성공률, 핸드셰이크 실패율로 상태를 확인함
2. B2B 연동이나 장비 인증처럼 외부 주체를 강하게 식별해야 하는 환경에서는 mTLS에 파트너별 CA 정책과 폐기 절차를 함께 두고 신뢰 체인 일치 여부, 폐기 반영 시간, 비인가 연결 차단 로그로 통제 수준을 확인함

## Ⅶ. 결론

mTLS는 통신 내용을 숨기는 수준을 넘어 통신 주체까지 확인하는 방식이므로, 효과의 핵심은 인증서 운영 자동화와 신뢰 체계 관리에 있음.
