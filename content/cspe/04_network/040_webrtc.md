## Ⅰ. 개요
- **정의**: 웹 브라우저 간에 별도의 플러그인 없이 실시간으로 음성, 영상 및 임의의 데이터를 주고받을 수 있게 하는 오픈소스 기술 표준임.
- **배경/필요성**: 플래시(Flash) 등 외부 플러그인의 보안 취약성 탈피, 화상회의/스트리밍의 웹 표준 네이티브 지원 필요.
- **출제 의도**: P2P 미디어 통신을 위한 시그널링 과정, NAT 트래버설(STUN/TURN) 원리, 미디어 스트리밍 아키텍처 이해.

## Ⅱ. 구성요소
```text
+-------------+      (Signaling)      +-------------+
|    Peer A   | <-------------------> |    Peer B   |
| (Browser A) |                       | (Browser B) |
+-------------+                       +-------------+
       |             STUN/TURN               |
       +-------------------------------------+
             (Media / Data P2P 통신)
```
| 구성요소 | 설명 | 비유 |
|---|---|---|
| Signaling Server| 서로의 주소(SDP, 통신 규격)를 교환하기 위해 초기 통신을 중개하는 서버 | 전화번호부/중매쟁이 |
| STUN Server | 단말이 자신의 공인 IP 주소와 포트를 알아낼 수 있게 도와주는 서버 | 거울 (내 모습 확인) |
| TURN Server | NAT 방화벽이 너무 엄격해 P2P가 불가능할 때 트래픽을 중계해 주는 릴레이 서버 | 우회 택배소 |
> 요약: 시그널링과 NAT 주소 확인(STUN)을 거쳐 브라우저끼리 다이렉트(P2P) 미디어 스트리밍을 연결함.

## Ⅲ. 절차
```text
+-----------+   +-------------+   +-------------+   +-----------+
| 시그널링  |-> | ICE 수집    |-> | P2P 연결    |-> | 미디어전송|
+-----------+   +-------------+   +-------------+   +-----------+
```
1. **시그널링**: 양 단말이 시그널링 서버(WebSocket 등)를 통해 서로의 미디어 규격(SDP)을 제안하고 수락함(Offer/Answer).
2. **ICE 수집**: 단말들이 STUN 서버를 통해 접속 가능한 자신의 공인 네트워크 후보(Candidate) 주소 목록을 수집함.
3. **P2P 연결**: ICE 프레임워크가 교환된 후보 주소들을 테스트하여 최적의 직접 연결(또는 TURN 중계 연결) 경로를 확립함.
4. **미디어 전송**: 확립된 P2P 연결(SRTP/UDP 기반) 위에서 오디오, 비디오, 데이터 채널을 통해 실시간 스트리밍을 수행함.
> 요약: 통신 규격을 맞추고 네트워크 경로를 뚫은 뒤 안전하게 실시간 데이터를 브라우저 간 직접 교환함.

## Ⅳ. 문제점
- **Symmetric NAT 제약**: 엄격한 사내 방화벽 환경에서는 STUN으로 P2P 연결이 불가능하여 중계(TURN) 서버에 전적으로 의존해야 함.
- **대역폭 제한 (N:N 통신)**: 다자간 화상회의 시 각 참여자가 모두에게 데이터를 보내야 하는 Mesh 구조 방식은 단말/네트워크 부하 급증 유발.
- **품질 보장(QoS) 한계**: 기본적으로 UDP 망을 사용하므로 네트워크 혼잡 시 패킷 손실로 인한 화질/음질 저하 발생.

## Ⅴ. 개선방안
- **서버 인프라 확보**: 안정적인 접속 보장을 위해 고가용성 TURN 서버 클러스터 인프라를 충분히 구축 (단기).
- **아키텍처 변경**: 다자간 통신의 클라이언트 부하를 줄이기 위해 단일 미디어를 받아 분배하는 SFU(Selective Forwarding Unit) 미디어 서버 도입 (중기).
- **프로토콜 융합**: QUIC/WebTransport 기반의 차세대 저지연 프로토콜을 도입하여 실시간 데이터 채널의 신뢰성 향상 (장기).
