## 미리 알고가기

- SDN 컨트롤러는 중앙에서 경로와 정책을 계산하는 제어 소프트웨어임
- OpenFlow는 컨트롤러와 스위치가 플로우 규칙을 주고받는 사우스바운드 프로토콜임
- 플로우 테이블은 조건과 동작을 묶은 Match-Action 규칙 집합임
- Packet-In과 Flow-Mod는 스위치 질의와 컨트롤러 응답을 나타내는 대표 메시지임

## Ⅰ. 개요

- **정의/개념**: SDN 컨트롤러는 분리된 데이터 평면 장비를 중앙에서 제어하는 핵심 요소이고, OpenFlow는 컨트롤러가 스위치에 플로우 규칙을 설치하고 상태를 수집할 때 쓰는 표준 제어 방식임
- **배경/필요성**: SDN 구조가 성립하려면 중앙 판단을 장비에 전달할 공통 언어가 필요하므로, 벤더별 CLI 대신 규칙 기반 제어와 상태 교환이 가능한 표준 프로토콜이 필요했음

## Ⅱ. 특징

- Match-Action 규칙으로 세밀한 트래픽 제어를 수행할 수 있음
- 반응형과 사전 배포형 방식 중 정책 특성에 맞춰 제어 전략을 고를 수 있음
- 컨트롤러는 토폴로지, 정책, 통계를 종합해 장비 동작을 바꿈
- 중앙 집중 제어이므로 규칙 폭증과 컨트롤러 병목을 함께 고려해야 함

## Ⅲ. 종류 및 비교

| 판단 기준 | 전통적 분산 라우팅 제어 | SDN 컨트롤러와 OpenFlow |
|:---|:---|:---|
| 경로 결정 주체 | 각 장비가 프로토콜 기반으로 개별 판단함 | 컨트롤러가 전체 정책과 상태를 보고 규칙을 계산함 |
| 제어 단위 | 라우팅 중심의 목적지 경로 제어가 기본임 | 포트, VLAN, IP, 프로토콜 같은 세밀한 플로우 단위 제어가 가능함 |
| 변경 반영 | 장비 간 프로토콜 수렴 과정이 필요함 | 규칙 계산 뒤 컨트롤러가 직접 장비에 설치함 |
| 운영 한계 | 정책 일관성이 약해질 수 있음 | 컨트롤러 부하와 Packet-In 폭주가 병목이 될 수 있음 |

> 요약: OpenFlow 기반 제어는 유연성이 높지만 분산 자율성 대신 중앙 병목을 관리해야 함.

## Ⅳ. 구성요소 및 구조

| 구성요소 | 설명 |
|:---|:---|
| SDN 애플리케이션 | 보안, QoS, 엔지니어링 정책을 정의하는 상위 계층임 |
| SDN 컨트롤러 | 정책을 플로우 규칙으로 바꾸고 장비 상태를 통합 관리하는 핵심 두뇌임 |
| OpenFlow 채널 | 컨트롤러와 스위치가 제어 메시지와 통계를 주고받는 통신 경로임 |
| OpenFlow 스위치 | 플로우 테이블에 저장된 규칙대로 실제 패킷을 전달하는 장비임 |
| 플로우 테이블 | 조건과 동작을 저장해 패킷 처리 기준을 제공하는 데이터 구조임 |

```text
+-------------+     +----------------+     +----------------+     +----------------+
| SDN 앱        | --> | SDN 컨트롤러     | --> | OpenFlow 채널    | --> | OpenFlow 스위치 |
+-------------+     +----------------+     +----------------+     +----------------+
```

## Ⅴ. 원리 및 절차 흐름도

```text
+-------------+     +----------------+     +------------------+     +----------------+
| 패킷·정책 인지  | --> | 규칙 계산         | --> | Flow-Mod 설치     | --> | 통계 수집·재배치  |
+-------------+     +----------------+     +------------------+     +----------------+
```

1. **패킷과 정책 인지**: 스위치가 미지의 플로우를 감지하거나 컨트롤러가 정책 변화를 인지함
2. **규칙 계산**: 컨트롤러가 토폴로지와 정책을 바탕으로 해당 플로우 처리 규칙을 계산함
3. **Flow-Mod 설치**: 계산 결과를 OpenFlow 메시지로 스위치 플로우 테이블에 반영함
4. **통계 수집과 재배치**: 플로우 통계를 수집해 혼잡이나 장애가 있으면 규칙을 다시 조정함

## Ⅵ. 실무 적용 및 유의점

1. 대규모 데이터센터처럼 신규 플로우가 많고 정책 변경이 잦은 환경에서는 OpenFlow가 유용하지만 반응형 규칙만 쓰면 Packet-In 폭주가 컨트롤러를 압박하므로 기본 규칙 사전 배포와 클러스터 이중화를 적용하고 컨트롤러 CPU 사용률과 플로우 설치 지연 시간으로 확인함
2. 순수 OpenFlow만으로 전 구간을 제어하기보다 BGP, OSPF 같은 분산 프로토콜과 혼합하는 환경에서는 역할 경계가 중요하므로 어떤 트래픽을 중앙 제어할지 먼저 정하고 정책 충돌 건수와 경로 우회 성공률로 확인함

## Ⅶ. 결론

SDN 컨트롤러와 OpenFlow의 핵심은 중앙 정책을 플로우 규칙으로 빠르게 반영하는 데 있으므로 제어 유연성만큼 병목과 가용성 설계가 중요함.
