# 📖 【암기용】 개념 완전 이해

> 목적: IoT 아키텍처를 디바이스, 게이트웨이, 네트워크, 클라우드가 데이터를 만들고 전달하고 분석하는 계층 구조로 이해하게 만든다.

## 한눈에
- **개요**: 센서·액추에이터 데이터를 게이트웨이와 클라우드로 연결해 제어·분석하는 구조
- **왜 필요한가**: 온도 센서, PLC, 카메라, 웨어러블처럼 자원이 제한된 장치를 안전하게 연결하고 원격 운영해야 한다.
- **핵심 직관**: 현장의 작은 직원들이 보고서를 게이트웨이에 모아 본사 클라우드로 보내고, 본사가 다시 지시를 내리는 체계다.

## 깊이 이해
- **배경·문제의식**: IoT 장치는 전력, CPU, 메모리, 네트워크 품질이 제한된다. 모든 데이터를 클라우드로 보내면 지연과 비용이 커지고, 현장 제어가 끊길 수 있다.
- **작동 원리**: 디바이스가 센싱하고, 게이트웨이가 프로토콜 변환과 edge filtering을 수행하며, 클라우드는 저장·분석·대시보드·디바이스 관리를 담당한다. 명령은 반대 방향으로 전달된다.
- **비유**: 각 가정의 계량기가 지역 사무소를 거쳐 중앙 서버에 전력 사용량을 보고하는 방식이다.
- **구체 예시**: 공장 진동 센서 1,000대가 MQTT QoS 1로 게이트웨이에 데이터를 보내고, 게이트웨이는 이상치만 클라우드로 전송해 월 전송량을 70% 줄인다.
- **흔한 오해·주의점**: IoT는 센서 연결만이 아니다. 장치 인증, OTA 업데이트, 키 관리, 데이터 보존, 장애 시 local control이 포함되어야 한다.

## 연결 개념
- MQTT — publish/subscribe 기반 경량 메시징
- CoAP — constrained device용 REST형 프로토콜
- OPC UA — 산업 장비 의미 모델과 통신 표준

# 📝 【답안용】 시험 답안 템플릿

> 목적: IoT 아키텍처 출제 시 계층, 데이터 흐름, 보안·운영·지표를 답안으로 제시한다.

## 핵심 인사이트 (3줄 요약)

> 1. **본질**: IoT Architecture는 디바이스, 게이트웨이, 네트워크, 플랫폼, 애플리케이션을 연결해 센싱·제어·분석을 수행하는 구조다.
> 2. **가치**: 원격 모니터링, 예지보전, 자동제어를 위해 데이터 수집부터 device lifecycle까지 통합 관리한다.
> 3. **판단 포인트**: 디바이스 제약, 프로토콜 선택, edge 처리, 보안 인증, OTA, 데이터 지표를 함께 설계해야 한다.

## 출제 의도 및 답안 포인트

| 출제 의도 | 반드시 짚을 핵심 | 감점 회피 포인트 |
|:---|:---|:---|
| IoT 계층 구조 이해 확인 | device, gateway, network, cloud, app | 센서와 클라우드만 연결 |
| 프로토콜·처리 판단 확인 | MQTT, CoAP, OPC UA, edge filtering | 모든 데이터를 클라우드 전송으로 가정 |
| 운영·보안 역량 확인 | device identity, TLS, OTA, fleet management | 장치 인증·패치 누락 |

> 요약: 이 문제는 IoT를 연결 구조가 아니라 운영 가능한 디바이스-데이터 플랫폼으로 설계하는지를 본다.

## Ⅰ. 개요 및 필요성

- 개요: 물리 장치와 디지털 서비스 연결
- 배경: IoT 장치는 CPU·메모리·전력 제약과 불안정한 네트워크 환경에서 센싱, 제어, 분석, 업데이트를 처리해야 한다.
- 필요성: IoT 아키텍처는 디바이스, Gateway, 플랫폼, 클라우드 전 구간의 보안과 운영 체계를 포함해야 한다.

---

## Ⅱ. 구조 및 구성요소

```text
Device/Sensor -> Gateway/Edge -> Network -> IoT Platform
              -> Storage/Analytics -> Application -> Command/OTA
```

| 구성요소 | 역할 | 특이사항 |
|:---|:---|:---|
| 디바이스 | 센싱·액추에이션 수행 | MCU, RTOS, battery 제약 |
| 게이트웨이 | 프로토콜 변환·필터링·local control | Modbus, BLE, MQTT bridge |
| IoT 플랫폼 | 수집·저장·분석·디바이스 관리 | registry, shadow, rule engine |
| 애플리케이션 | 모니터링·제어·예측 분석 | dashboard, API, alert |

> 요약: IoT는 디바이스 제약을 게이트웨이와 플랫폼이 보완하는 계층형 구조다.

---

## Ⅲ. 동작원리 및 흐름도

```text
센싱 -> 로컬 전처리 -> 메시지 발행 -> 플랫폼 수집
-> 저장/분석 -> 알림/제어 명령 -> OTA/상태 동기화
```

| 단계 | 처리 내용 | 검증 기준 |
|:---:|:---|:---|
| 1 | 센서 데이터 수집과 timestamp 부여 | clock drift 1초 이하 |
| 2 | edge filtering, 압축, 이상치 탐지 | 전송량 50% 이상 절감 |
| 3 | MQTT/CoAP/HTTPS로 플랫폼 전송 | TLS 1.2 이상 |
| 4 | time-series DB 저장과 rule engine 처리 | ingestion loss 0.1% 이하 |
| 5 | 제어 명령, OTA, device shadow 동기화 | OTA 실패율 1% 이하 |

> 요약: IoT 동작은 센싱, edge 처리, 메시징, 분석, 제어·업데이트의 폐루프다.

## Ⅳ. 특징

| 구분 | 기존/대안 | IoT Architecture | 수치 컬럼 |
|:---|:---|:---|:---|
| 연결 대상 | 서버·PC 중심 | 센서·액추에이터·PLC | 수천~수백만 device |
| 처리 위치 | 중앙 서버 | edge+cloud 분산 | 전송량 50% 절감 |
| 통신 방식 | HTTP 중심 | MQTT, CoAP, OPC UA | QoS 0/1/2, UDP 5683 |
| 운영 요소 | 앱 배포 | OTA, registry, certificate | 인증서 만료 0건 |

> 요약: IoT는 자원 제약 장치를 대규모로 관리하므로 edge 처리와 device lifecycle이 핵심이다.

## Ⅴ. 심화 비교 및 적용 판단

| 구분 | 기존/대안 | 본 키워드 | 선택 기준 |
|:---|:---|:---|:---|
| 처리 위치 | cloud-only | edge+cloud hybrid | 지연 100ms 이하 제어 |
| 프로토콜 | HTTP polling | MQTT/CoAP pub-sub | 저전력·저대역폭 장치 |
| 장치 관리 | 수동 펌웨어 | OTA·registry·shadow | device 1,000대 이상 |

> 요약: IoT 설계는 지연, 전력, 장치 수, 보안 패치 요구에 따라 edge와 cloud 역할을 나눈다.

| 리스크 | 원인 | 대응 방안 | 확인 지표 |
|:---|:---|:---|:---|
| 장치 탈취 | 기본 비밀번호·키 공유 | device certificate, secure boot | 미인증 접속 0건 |
| 데이터 유실 | 무선 품질 저하·broker 장애 | QoS 1, local buffer | ingestion loss 0.1% 이하 |
| OTA 실패 | 전원 차단·버전 충돌 | staged rollout, rollback | OTA 실패율 1% 이하 |

> 요약: IoT 리스크는 장치 인증, 메시지 유실, OTA 실패로 나뉘며 fleet 지표로 통제한다.

| 점검 항목 | 목표 기준 | 측정 방법 |
|:---|:---|:---|
| 연결 품질 | device online 99% 이상 | heartbeat, shadow 상태 |
| 데이터 품질 | ingestion loss 0.1% 이하, 지연 p95 5초 이하 | broker metric, time-series DB |
| 운영 보안 | 인증서 만료 0건, OTA 성공률 99% | PKI inventory, rollout log |

> 요약: IoT 성공 여부는 장치 온라인율, 데이터 유실률, OTA와 인증서 운영 지표로 판단한다.

## Ⅵ. 실무 적용 및 결론

**적용 방안 3개 (필수 — 단계별 또는 항목별):**
1. 장치군별 프로토콜 선택: 배터리 센서는 CoAP UDP 5683, telemetry는 MQTT QoS 1, 산업 장비는 OPC UA 적용
2. edge gateway에서 filtering, local buffer, protocol bridge를 수행해 전송량 50% 이상 절감
3. device certificate, secure boot, OTA staged rollout로 1,000대 이상 fleet 운영 체계 구축

**결론 (2줄):**
- 기술사 판단: 지연 민감 제어는 edge, 장기 분석은 cloud로 분리하고 장치 인증·OTA를 기본 설계에 포함해야 함
- 향후 방향: digital twin과 AI anomaly detection을 결합해 장치 상태 예측과 자동 제어로 확장
