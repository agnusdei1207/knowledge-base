## Ⅰ. 개요
- **정의**: LAN 포트 접속 시 EAP 기반 인증을 수행하여 비인가 단말의 네트워크 접근을 차단하는 표준
- **배경/필요성**: 물리 포트 연결만으로 네트워크에 접근 가능한 환경은 내부 위협에 취약하므로 포트 수준 인증이 필요함
- **비유**: 호텔 객실 키카드처럼 인증된 투숙객만 해당 층 엘리베이터를 이용할 수 있는 구조와 유사함

| 출제 의도 | 반드시 짚을 핵심 | 감점 회피 포인트 |
|:---|:---|:---|
| 802.1X 3자 구조와 EAP 흐름 이해 | Supplicant-Authenticator-Auth Server 역할 | 유무선 환경 차이 및 EAP 방식(PEAP/EAP-TLS) 구분 |

> 요약: 포트 수준에서 EAP 인증을 통해 네트워크 접근을 제어하는 표준임

## Ⅱ. 구성요소
```text
Supplicant --> Authenticator --> Authentication Server
 (단말)      (Switch/AP)        (RADIUS Server)
   |--- EAP Start --->|
   |                   |--- Access-Request --->|
   |                   |<-- Access-Accept/Reject|
   |<-- Port Open/Block|
```

| 구성요소 | 설명 | 비유 |
|:---|:---|:---|
| Supplicant | 인증을 요청하는 단말의 소프트웨어 | 키카드를 제시하는 투숙객 |
| Authenticator | 인증 결과에 따라 포트를 개방·차단하는 스위치/AP | 엘리베이터 카드 리더기 |
| Authentication Server | RADIUS 프로토콜(114 참조)로 인증을 처리하는 서버 | 호텔 프런트 인증 시스템 |
| EAP | 다양한 인증 방식을 캡슐화하는 확장 인증 프레임워크 | 다양한 키 타입을 지원하는 범용 리더기 규격 |

> 요약: Supplicant-Authenticator-Auth Server 3자 구조로 포트 인증을 수행함

## Ⅲ. 절차
```text
EAP Start -> EAP 인증교환 -> RADIUS 판정 -> 포트 개방/차단
```
- 1단계: EAP Start — Supplicant가 Authenticator에 인증 개시를 요청함
- 2단계: EAP 인증 교환 — Authenticator가 EAP 메시지를 중계하여 자격증명을 교환함
- 3단계: RADIUS 판정 — Authentication Server가 자격증명을 검증하고 Accept/Reject를 응답함
- 4단계: 포트 개방/차단 — Authenticator가 판정 결과에 따라 포트 상태를 Authorized/Unauthorized로 전환함

> 요약: EAP개시-인증교환-판정-포트전환 4단계로 접근을 제어함

## Ⅳ. 문제점
- MAC 우회 공격: 인증 완료된 포트의 MAC 주소를 탈취하여 비인가 접근 — 포트 인증 무력화
- 레거시 단말 미지원: 802.1X Supplicant가 없는 프린터·IoT 단말 — 인증 불가로 네트워크 격리
- 인증 지연: 부팅 시 PXE·DHCP 등 사전 통신이 인증 전 차단됨 — 단말 초기 구동 실패

> 요약: MAC우회·레거시미지원·사전통신차단이 핵심 문제임

## Ⅴ. 개선방안
1. 단기: Dynamic ARP Inspection·포트 보안 병행으로 MAC 스푸핑 탐지·차단
2. 중기: MAB(MAC Authentication Bypass) 적용으로 비인가 단말의 제한적 접근 허용
3. 장기: Pre-Auth VLAN 구성으로 인증 전 PXE·DHCP 등 필수 트래픽 허용

> 요약: MAC보안·MAB·Pre-Auth VLAN으로 개선함

## Ⅵ. 전망
- 발전 방향: NAC(113 참조)·ZTNA와 통합되어 지속적 단말 신뢰 평가 체계로 확장됨
- 기술사적 판단: 포트 기반 인증은 네트워크 보안의 기본 계층으로 지속 활용됨
- 기술사 제언: IoT 대량 접속 환경에서 확장 가능한 인증 프레임워크 설계가 필요함
