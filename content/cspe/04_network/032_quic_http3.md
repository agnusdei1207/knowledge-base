## 미리 알고가기

- QUIC: UDP 위에서 신뢰성, 혼잡 제어, 암호화를 함께 제공하는 전송 프로토콜임
- HTTP/3: QUIC 위에서 동작하도록 정의된 최신 HTTP 버전임
- 0-RTT: 이전 연결 정보를 활용해 첫 요청을 더 빠르게 보내는 방식임
- Connection ID: IP와 포트가 바뀌어도 같은 연결을 식별할 수 있게 하는 값임

## Ⅰ. 개요

- **정의/개념**: QUIC은 UDP를 바탕으로 신뢰성 전송, 혼잡 제어, TLS 1.3 암호화를 사용자 영역에서 함께 처리하는 전송 프로토콜이고, HTTP/3는 그 위에서 동작하는 HTTP 규격임. TCP와 TLS를 따로 쌓던 구조를 한 단계로 통합했다는 점이 핵심임
- **배경/필요성**: 모바일 환경과 대규모 웹 서비스에서는 연결 수립 RTT와 TCP 헤드오브라인 병목이 체감 품질에 직접 영향을 주므로, 더 짧은 초기 지연과 스트림 독립성을 가진 구조가 필요함

## Ⅱ. 특징

- 전송 계층 연결과 암호화 협상을 함께 처리해 초기 지연을 줄일 수 있음
- 하나의 연결 안에 여러 독립 스트림을 두므로 한 스트림 손실이 전체 요청 정체로 번지지 않음
- Connection ID를 사용해 IP가 바뀌어도 연결을 이어 갈 수 있어 모바일 환경에 유리함
- UDP 443 기반 암호화 트래픽이므로 기존 보안 장비에서 내부 가시성이 줄어들 수 있음

## Ⅲ. 종류 및 비교

| 판단 기준 | HTTP/2 over TCP | HTTP/3 over QUIC |
|:---|:---|:---|
| 연결 수립 | TCP와 TLS 절차를 따로 거쳐 초기 RTT가 더 큼 | QUIC과 TLS가 통합되어 초기 RTT를 줄이기 쉬움 |
| 스트림 처리 | 애플리케이션 다중화는 가능하지만 TCP 손실이 전체 흐름에 영향을 줄 수 있음 | 스트림이 독립적으로 처리돼 한 스트림 손실이 다른 스트림을 덜 막음 |
| 네트워크 이동성 | IP가 바뀌면 연결을 다시 잡는 경우가 많음 | Connection ID 기반으로 연결 유지가 쉬움 |
| 운영 고려 | 기존 장비와 호환성이 높음 | UDP 443 제어와 가시성 확보 전략이 함께 필요함 |

> 요약: QUIC과 HTTP/3의 강점은 지연 단축과 스트림 독립성이며, 운영상 과제는 UDP 기반 암호화 트래픽 가시성임

## Ⅳ. 구성요소 및 구조

| 구성요소 | 설명 |
|:---|:---|
| UDP 기반 전송 | 커널 TCP 수정 없이 사용자 영역에서 전송 제어를 구현할 수 있게 함 |
| TLS 1.3 통합 | 별도 TLS 계층을 두지 않고 연결 수립 과정에 암호화를 함께 묶음 |
| 스트림 관리 | 하나의 연결 안에서 여러 요청과 응답을 독립적으로 관리함 |
| Connection ID | 네트워크 경로와 무관하게 같은 연결을 식별해 이동성을 높임 |

```text
+---------+     +------------------+     +---------+
| HTTP/3  | --> | QUIC + TLS 1.3   | --> | UDP/IP  |
+---------+     +------------------+     +---------+
```

> 요약: QUIC 구조는 TCP와 TLS를 분리해 쌓던 방식을 줄이고, 전송과 암호화를 하나로 묶은 형태임

## Ⅴ. 원리 및 절차 흐름도

```text
+----------+     +----------+     +----------+     +----------+
| 초기교환 | --> | 암호협상  | --> | 스트림생성 | --> | 데이터전송 |
+----------+     +----------+     +----------+     +----------+
```

1. **초기교환**: 클라이언트가 QUIC 초기 패킷으로 연결을 시작함
2. **암호협상**: TLS 1.3 정보를 교환해 암호화 키를 확정함
3. **스트림생성**: 하나의 연결 안에 여러 요청 스트림을 독립적으로 만듦
4. **데이터전송**: 각 스트림이 손실 복구와 ACK 처리를 독립적으로 이어 감

## Ⅵ. 실무 적용 및 유의점

1. 글로벌 웹과 모바일 서비스에서는 QUIC과 HTTP/3로 초기 지연과 네트워크 전환 끊김을 줄일 수 있지만 구형 네트워크 경로에서 UDP 443 차단이 있을 수 있으므로 TCP 기반 대체 경로를 함께 두고 연결 성공률과 초기 응답 시간을 확인함
2. 기업 보안망에서는 QUIC 트래픽 내부 분석이 어려워 정책 통제가 약해질 수 있으므로 허용 대상 서비스를 먼저 정하고 필요 시 HTTP/2로 폴백시키며 UDP 443 사용 비율과 보안 장비 탐지 공백을 함께 확인함

## Ⅶ. 결론

QUIC과 HTTP/3의 핵심은 TCP를 단순히 대체하는 데 있지 않고, 지연과 이동성 문제를 웹 서비스 관점에서 다시 설계한 전송 구조를 제공하는 데 있음.
