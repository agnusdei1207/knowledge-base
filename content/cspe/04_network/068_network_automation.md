## Ⅰ. 개요
- **정의**: 네트워크 장비의 설정·운영·모니터링을 스크립트·도구로 자동화하는 기술 체계
- **배경/필요성**: 수동 CLI 설정은 장비 수 증가 시 인적 오류와 설정 불일치를 유발함
- **비유**: 수작업 농사를 자동 관개·수확 시스템으로 전환하는 것

| 출제 의도 | 반드시 짚을 핵심 | 감점 회피 포인트 |
|:---|:---|:---|
| 네트워크 운영 자동화 수단 이해 | Ansible·Python·NETCONF/YANG 도구 체인 | IBN(067)은 의도 추상화, 자동화는 실행 도구 레이어로 구분 |

> 요약: 스크립트·프레임워크로 네트워크 설정·운영을 자동화하여 일관성과 속도를 확보하는 체계임

## Ⅱ. 구성요소
```text
[Operator] ---> [Automation Tool]
                     |
            +--------+--------+
            |        |        |
            v        v        v
        [NETCONF] [REST API] [SSH/CLI]
            |        |        |
            +--------+--------+
                     |
                     v
              [Network Device]
```

| 구성요소 | 설명 | 비유 |
|:---|:---|:---|
| Automation Tool | Ansible·Nornir 등 자동화 프레임워크 | 자동 관개 컨트롤러 |
| NETCONF/YANG | 구조화된 설정 프로토콜·데이터 모델 | 표준 규격 배관 연결 |
| REST API | 장비·컨트롤러의 HTTP 기반 인터페이스 | 원격 제어 리모컨 |
| Source of Truth | 의도된 설정 상태를 저장하는 CMDB·Git 저장소 | 설계 도면 보관소 |

> 요약: 자동화 도구-프로토콜-API-SoT로 네트워크 설정 라이프사이클을 자동화함

## Ⅲ. 절차
```text
Step1 --> Step2 --> Step3 --> Step4
SoT정의    플레이북   배포실행   검증/롤백
           작성
```
- 1단계: Source of Truth에 의도된 네트워크 상태(설정·토폴로지)를 정의함
- 2단계: Ansible Playbook·Python 스크립트 등 자동화 코드를 작성함
- 3단계: NETCONF·API를 통해 대상 장비에 설정을 일괄 배포함
- 4단계: 배포 결과를 검증하고 실패 시 자동 롤백을 수행함

> 요약: SoT 정의-코드 작성-배포-검증/롤백의 4단계로 자동화를 수행함

## Ⅳ. 문제점
- 이기종 호환: 벤더별 API·데이터 모델 차이 — 자동화 코드 파편화
- 테스트 부재: 네트워크 변경의 사전 검증 환경 부족 — 장애 전파 위험
- 스킬 갭: 네트워크 엔지니어의 프로그래밍 역량 부족 — 자동화 도입 지연

> 요약: 이기종 호환·테스트 환경·인력 역량이 자동화 확산의 장벽임

## Ⅴ. 개선방안
1. 단기: OpenConfig YANG 모델 채택으로 벤더 중립 자동화 코드 작성
2. 중기: 네트워크 시뮬레이터(Containerlab 등)로 변경 사전 테스트 환경 구축
3. 장기: NetDevOps(069) 교육 체계 수립으로 네트워크+개발 융합 인력 양성

> 요약: 표준 모델·시뮬레이터·인력 양성으로 자동화 성숙도를 높일 필요

## Ⅵ. 전망
- 발전 방향: Event-Driven Automation으로 장애 탐지-대응까지 자동화 범위 확대
- 기술사적 판단: CLI 수동 운영에서 IaC 기반 선언적 운영으로 패러다임 전환 중임
- 기술사 제언: NetDevOps(069)·NaC(070) 파이프라인과 통합하여 E2E 자동화 체계를 구축할 필요
