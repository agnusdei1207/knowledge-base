## Ⅰ. 개요
- **정의**: 종단 간 프로세스의 데이터 전송을 담당하며, 신뢰성 보장의 TCP와 전송 속도 중심의 UDP로 구분됨.
- **배경 및 필요성**: 다양한 서비스 성격(웹서핑 무결성 vs 스트리밍 실시간성)에 맞춘 차별적 프로토콜 구조 분리.
- **출제 의도**: 서비스 요구사항에 맞춰 신뢰성 제어 로직과 저지연 무제어 로직 중 적합한 L4 전송 기술을 적용하는 능력 평가

## Ⅱ. 구성요소

```text
+-------------------------+
|  Component Architecture |
+-------------------------+
| [ Node A ] <-> [ Node B]|
+-------------------------+
```

| 구성요소 | 설명 | 비유 |
|---|---|---|
| **TCP** | 연결 지향형, 재전송/순서 보장, 흐름/혼잡 제어 기능을 지원하는 무결성 프로토콜 | 수령 확인을 꼭 받는 등기 우편 |
| **UDP** | 비연결형, 오류 복구 없이 최선을 다해 즉각 던지는(Best-Effort) 고속 프로토콜 | 확인 없이 던져넣는 빠른 일반 우편 |
| **포트(Port)** | 도착한 데이터가 최종적으로 진입할 목적 애플리케이션을 구별하는 논리적 채널 | 수신지 건물의 세부 호실 번호 |

> 요약: TCP는 신뢰할 수 있지만 절차가 복잡/무겁고, UDP는 절차가 없어 매우 가볍고 빠름.

## Ⅲ. 절차

```text
+-------+   +-------+   +-------+   +-------+
| Step1 |-->| Step2 |-->| Step3 |-->| Step4 |
+-------+   +-------+   +-------+   +-------+
```

1. **소켓 바인딩**: 양 단말의 애플리케이션이 포트를 열고 수신 대기함.
2. **[TCP] 세션 확립**: 3-Way Handshake로 서로 연결 의사와 시작 번호를 교환함.
3. **[TCP] 무결성 전송**: 전송 시 응답(ACK)을 확인하고 유실 패킷은 재전송함.
4. **[UDP] 단방향 전송**: 핸드셰이크나 에러 검사 없이 즉시 목적 포트로 데이터그램을 날림.

> 요약: TCP는 연결 확인과 재전송 절차를 철저히 지키며, UDP는 연결 확인 없이 전송에만 집중함.

## Ⅳ. 문제점
- TCP의 높은 초기 접속 지연 (원인: 데이터 전송 전 핸드셰이크 RTT 소모로 실시간 서비스 지연 발생)
- TCP 애플리케이션 스트림 병목 (원인: 패킷 하나 유실 시 복구될 때까지 이후 데이터 처리가 완전히 멈추는 HOL Blocking)
- UDP 자체적 복구 메커니즘 전무 (원인: 네트워크 혼잡이나 손실 시 애플리케이션 단에서 비디오 깨짐 등의 오류를 방치함)

## Ⅴ. 개선방안
- **단기 방안**: [단기] 트래픽 성격에 따른 프로토콜 분리 (파일/웹은 TCP, VoIP/스트리밍/DNS 질의는 UDP 적용)
- **중기 방안**: [중기] TCP Fast Open(TFO) 활성화 (초기 연결 과정에서 데이터 페이로드를 함께 보내 지연 시간 단축)
- **장기 방안**: [장기] QUIC 프로토콜 확산 적용 (UDP를 베이스로 하되 애플리케이션 계층에서 다중화 및 암호화를 자체 구현해 TCP 한계 극복)

## Ⅵ. 전망
- 전통적 TCP의 복잡성과 모바일 환경에서의 단점을 극복하기 위해 UDP 기반 신규 프로토콜(HTTP/3 등) 비중이 급증함.
