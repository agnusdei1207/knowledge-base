## Ⅰ. 개요
- **정의**: 수신 측 데이터 처리 버퍼 용량에 맞춰 송신 측의 패킷 송출량을 조율하는 TCP 신뢰성 보장 기술임.
- **배경 및 필요성**: 송/수신 단말의 성능 불균형으로 인한 버퍼 오버플로우와 데이터 드롭 현상 예방.
- **출제 의도**: End-to-End 연결에서 윈도우 크기(Window Size) 기반 데이터 송출량(Throughput) 최적화 제어 원리 평가

## Ⅱ. 구성요소

```text
+-------------------------+
|  Component Architecture |
+-------------------------+
| [ Node A ] <-> [ Node B]|
+-------------------------+
```

| 구성요소 | 설명 | 비유 |
|---|---|---|
| **흐름 제어** | 단말(End Point) 간 데이터 처리 속도의 불균형을 맞추어 오버플로우 방지 | 깔때기 넘치지 않게 물 붓기 |
| **슬라이딩 윈도우** | 수신자 여유 공간만큼 수신 확인(ACK) 없이 패킷을 연속 송신하는 기법 | 창문을 옆으로 밀듯 송신 범위 이동 |
| **윈도우 사이즈** | 수신 측이 TCP 헤더를 통해 송신 측에 알리는 가용 버퍼 용량 | 창고의 남은 적재 공간 크기 |

> 요약: 슬라이딩 윈도우 메커니즘을 통해 수신자의 가용 버퍼 한도 내에서 연속적으로 전송 효율을 높임.

## Ⅲ. 절차

```text
+-------+   +-------+   +-------+   +-------+
| Step1 |-->| Step2 |-->| Step3 |-->| Step4 |
+-------+   +-------+   +-------+   +-------+
```

1. **버퍼 여유 공간 알림**: 수신 측이 TCP 응답 시 자신의 수신 윈도우 사이즈(rwnd)를 헤더에 기록함.
2. **연속 전송**: 송신 측은 해당 윈도우 크기 내에서 ACK 대기 없이 여러 패킷을 한번에 전송함.
3. **수신 및 처리**: 수신 측 애플리케이션이 버퍼에서 데이터를 읽어가면 남은 공간이 확보됨.
4. **윈도우 갱신(슬라이딩)**: 다음 통신에서 갱신된 여유 공간을 알리며, 만약 0일 경우 송신을 멈춤.

> 요약: 수신자가 가용 버퍼를 알리면, 송신자는 그 한도 내에서 연속 전송과 멈춤을 반복하며 흐름을 조율함.

## Ⅳ. 문제점
- 기본 윈도우 필드 한계 (원인: 헤더 구조상 최대 64KB까지만 표현 가능해 초고속망(큰 BDP)에서 효율 저하)
- 바보 윈도우 증후군 (원인: 버퍼가 1바이트씩 미세하게 비워질 때마다 패킷을 보내어 헤더 낭비가 극심해짐)
- Zero Window 교착(데드락) 상태 (원인: 수신 버퍼 0 도달 후 업데이트 ACK 메시지가 유실되면 송신자는 영원히 대기함)

## Ⅴ. 개선방안
- **단기 방안**: [단기] Nagle 알고리즘 적용 (데이터가 모이거나 윈도우가 충분히 비워질 때까지 송/수신을 보류하여 작은 패킷 폭주 차단)
- **중기 방안**: [중기] TCP Window Scaling 활성화 (헤더의 Shift 옵션을 사용해 윈도우 크기를 기가바이트 단위로 확장 적용)
- **장기 방안**: [장기] 애플리케이션 비동기 I/O 고도화 (데이터를 가져가는 프로세스를 최적화해 상시 수신 버퍼를 여유 있게 확보)

## Ⅵ. 전망
- 100G 이상의 초고속 네트워크 환경에서는 OS 커널의 한계를 넘는 사용자 영역 스택(DPDK)이 적극 채택됨.
