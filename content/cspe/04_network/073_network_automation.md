## 미리 알고가기

- YANG은 장비 설정과 상태를 구조화해 표현하는 데이터 모델 언어임
- NETCONF는 SSH 기반으로 XML 데이터를 주고받는 장비 설정 프로토콜임
- RESTCONF는 HTTP 기반으로 YANG 모델 데이터를 다루는 API 방식임
- 멱등성은 같은 자동화 작업을 여러 번 실행해도 결과 상태가 같게 유지되는 성질임

## Ⅰ. 개요

- **정의/개념**: 네트워크 자동화는 Ansible 같은 오케스트레이션 도구와 NETCONF, RESTCONF 같은 구조화된 인터페이스를 이용해 장비 설정과 검증을 코드로 수행하는 운영 방식임
- **배경/필요성**: 장비 수와 정책 수가 늘어나면 CLI 명령과 화면 출력 형식의 차이로 설정 결과가 달라질 수 있으므로 버전 관리 가능한 선언과 구조화 API가 필요함

## Ⅱ. 특징

- YANG 모델을 기반으로 장비 설정을 구조화해 파싱 오류와 벤더 차이를 줄이기 좋음
- Ansible 같은 상위 도구로 다수 장비 작업을 일괄 배포하고 검증할 수 있음
- Git과 CI 파이프라인을 붙이면 변경 이력, 리뷰, 롤백을 운영 절차에 넣기 좋음
- 자동화 속도가 빠른 만큼 잘못된 변경이 넓게 퍼질 수 있어 사전 검증과 배포 범위 제한이 중요함

## Ⅲ. 종류 및 비교

| 판단 기준 | NETCONF | RESTCONF |
|:---|:---|:---|
| 전송 방식 | SSH 위에서 XML 기반 RPC를 사용함 | HTTP 기반 REST 방식으로 JSON이나 XML을 사용함 |
| 작업 성격 | 후보 설정·검증·커밋으로 트랜잭션 변경을 관리함 | HTTP 메서드와 REST 자원 모델로 외부 시스템과 연동함 |
| 데이터 처리 | XML 중심이라 표현은 엄격하지만 다루기가 무거울 수 있음 | 개발자 친화적인 구조로 외부 시스템과 붙이기 쉬움 |
| 적합 환경 | 코어 장비와 정교한 커밋 제어가 필요한 환경에 적합함 | 포털, 외부 오케스트레이터, 경량 자동화 연계에 적합함 |

> 요약: NETCONF는 후보 설정과 커밋 절차를 제공하고 RESTCONF는 HTTP 기반으로 YANG 자원을 조회·변경함.

## Ⅳ. 구성요소 및 구조

| 구성요소 | 설명 |
|:---|:---|
| YANG 데이터 모델 | 설정과 상태를 구조화해 자동화 도구와 장비가 같은 형식으로 이해하게 하는 기준임 |
| Ansible 플레이북 | 원하는 상태와 작업 순서를 정의해 다수 장비에 일괄 적용하는 상위 오케스트레이션 도구임 |
| NETCONF·RESTCONF | 구조화된 데이터를 장비에 전달하고 상태를 조회하는 실행 인터페이스임 |
| 인벤토리와 변수 | 장비 목록, 역할, 사이트별 차이를 분리해 재사용 가능성을 높이는 구성 요소임 |
| 검증과 저장소 | Git, 드라이런, 상태 비교를 통해 배포 전후 결과를 검증하는 운영 기반임 |

```text
+-------------+     +----------------+     +----------------+     +----------------+
| Git·플레이북   | --> | Ansible         | --> | NETCONF·RESTCONF | --> | 네트워크 장비     |
+-------------+     +----------------+     +----------------+     +----------------+
```

## Ⅴ. 원리 및 절차 흐름도

```text
+-------------+     +----------------+     +------------------+     +----------------+
| 목표 상태 정의  | --> | 드라이런·차이 확인   | --> | API 기반 설정 반영   | --> | 사후 검증·동기화   |
+-------------+     +----------------+     +------------------+     +----------------+
```

1. **목표 상태 정의**: 플레이북과 변수 파일에 원하는 네트워크 상태를 정의함
2. **드라이런과 차이 확인**: 배포 전 현재 상태와 차이를 비교해 위험 변경을 걸러냄
3. **API 기반 설정 반영**: 장비와 연결해 NETCONF 또는 RESTCONF로 변경을 적용함
4. **사후 검증과 동기화**: 반영 결과를 확인하고 코드와 실제 장비 상태를 다시 맞춤

## Ⅵ. 실무 적용 및 유의점

1. ACL, VLAN, 라우팅 정책을 수백 대 장비에 반복 반영하는 환경에서는 구조화 API 기반 자동화가 효과적이지만 검증 없이 일괄 배포하면 사고 범위가 커지므로 드라이런과 카나리 배포를 먼저 적용하고 배포 실패율과 롤백 시간을 기준으로 확인함
2. 레거시 장비가 구조화 API를 충분히 지원하지 않는 환경에서는 Ansible만 도입해도 화면 파싱 의존이 남으므로 YANG, NETCONF, RESTCONF 지원 범위를 먼저 조사하고 자동화 성공률과 설정 드리프트 건수로 확인함

## Ⅶ. 결론

네트워크 자동화의 핵심은 반복 작업을 줄이는 데 그치지 않고 장비 상태를 코드와 구조화된 API로 일관되게 관리하는 데 있음.
