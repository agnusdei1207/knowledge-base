## Ⅰ. 개요
- **정의**: 웹 데이터를 전송하는 HTTP 프로토콜이 복잡해지는 멀티미디어 웹 생태계 요구에 맞춰 속도와 병렬 구조로 진화한 과정임.
- **배경 및 필요성**: 웹 요소 급증 시 기존 TCP 기반 순차 구조(HTTP/1.1)의 심각한 렌더링 지연 및 병목 노출 극복.
- **출제 의도**: 버전별 아키텍처 특성 및 단점 해결 과정(다중화, QUIC 기반 UDP 전면 도입)의 핵심 차별화 이해 평가

## Ⅱ. 구성요소

```text
+-------------------------+
|  Component Architecture |
+-------------------------+
| [ Node A ] <-> [ Node B]|
+-------------------------+
```

| 구성요소 | 설명 | 비유 |
|---|---|---|
| **HTTP/1.1 (직렬)** | 파이프라이닝은 가능하나 근본적으로 앞선 요청 지연 시 뒤따르는 응답도 막히는 구조 | 마트의 단일 계산대 줄서기 병목 |
| **HTTP/2 (다중화)** | 데이터를 프레임으로 분리/압축해 단일 TCP 내에서 병렬 교차 전송함 | 하나의 컨베이어에 여러 물품 동시 교차 탑재 |
| **HTTP/3 (QUIC)** | UDP 기반 독립 스트림화 및 자체 암호화로 패킷 손실 시 전체 중단 해결 | 개별 오토바이 퀵서비스로 지연 없이 독립 전송 |

> 요약: HTTP 진화는 1.1의 직렬 대기를 2.0의 TCP 병렬로 완화하고, 3.0에서 UDP 기반 구조로 근본적 혁신을 이룸.

## Ⅲ. 절차

```text
+-------+   +-------+   +-------+   +-------+
| Step1 |-->| Step2 |-->| Step3 |-->| Step4 |
+-------+   +-------+   +-------+   +-------+
```

1. **[HTTP/1.1] 텍스트 순차 요청**: 텍스트 헤더와 함께 1요청-1응답 순차 방식으로 리소스를 수신함.
2. **[HTTP/2] 프레임 분할 병렬 처리**: 데이터를 바이너리 프레임으로 쪼개(Multiplexing) 단일 세션에서 동시 응답함.
3. **[HTTP/2 한계] TCP 계층 병목 발생**: 논리적 다중화에도 물리적 TCP 패킷 하나 유실 시 전체 연결이 대기함.
4. **[HTTP/3 도입] 독립 UDP 전송**: 각 스트림을 QUIC 프로토콜의 분리된 흐름으로 제어해 유실된 부분만 개별 복구함.

> 요약: 1.1의 지연을 2.0에서 논리적 병렬화로 개선했고, 2.0의 물리적 병목을 3.0의 QUIC(UDP)로 완전 해소함.

## Ⅳ. 문제점
- HTTP/1.1 애플리케이션 계층 HOL 블로킹 (원인: 앞서 들어간 응답 처리가 늦어지면 이후 리소스 로딩 전면 중단)
- HTTP/2 전송 계층 HOL 블로킹 한계 (원인: TCP 단에서 패킷 손실 시 무결성 보장을 위해 정상 다중화 프레임까지 멈춤)
- 모바일 IP 변경 시 무거운 재협상 오버헤드 (원인: 기지국/Wi-Fi 이동 시 기존 TCP 세션이 끊겨 암호화 핸드셰이크를 재수행함)

## Ⅴ. 개선방안
- **단기 방안**: [단기] 1.1 편법 제거 및 2.0 인프라 마이그레이션 (도메인 샤딩 등 과거 가속 편법을 버리고 HTTP/2 다중화 이점 적극 수용)
- **중기 방안**: [중기] 클라우드 엣지/CDN 인프라의 HTTP/3 지원 가동 (서버/프록시 구조를 QUIC 지원 버전으로 업데이트 및 방화벽 UDP 개방)
- **장기 방안**: [장기] Connection ID 활용 무중단 앱 통신 (모바일 이동 상황에서도 고유 연결 ID 기반 세션 유지로 끊김 없는 스트리밍 구현)

## Ⅵ. 전망
- 모바일 초저지연 중심의 통신 환경에서 HTTP/3 채택이 표준이 되며 TCP/IP 전송 체계를 본질적으로 뒤바꾸고 있음.
