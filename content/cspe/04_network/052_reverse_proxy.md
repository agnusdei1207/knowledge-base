## Ⅰ. 개요
- **정의**: 백엔드 서버를 대신하여 클라이언트 요청을 수신·중계하는 중간 서버임
- **배경/필요성**: 백엔드 서버를 외부에 직접 노출하면 보안 위협과 부하 집중이 발생하므로 중계 계층이 필요함
- **비유**: 호텔 프런트 데스크가 투숙객 요청을 받아 해당 부서로 전달하는 것과 유사함

| 출제 의도 | 반드시 짚을 핵심 | 감점 회피 포인트 |
|:---|:---|:---|
| 포워드 프록시와의 차이, 보안·캐싱 기능 | 클라이언트는 백엔드 존재를 모름 | LB와 역할 중첩 구분 필요(051 참조) |

> 요약: 백엔드 서버를 은닉하고 보안·캐싱·부하 분산을 제공하는 중계 서버임

## Ⅱ. 구성요소
```text
Client --> Reverse Proxy --> Backend Server A
                         --> Backend Server B
                         --> Cache Layer
```

| 구성요소 | 설명 | 비유 |
|:---|:---|:---|
| Listener | 클라이언트 요청을 수신하는 진입점(포트·도메인 바인딩) | 프런트 데스크 전화 |
| Routing Rule | URL 경로·헤더 기반으로 백엔드를 선택하는 규칙 | 내선번호 안내표 |
| Cache Module | 정적 콘텐츠를 저장하여 반복 요청 시 백엔드 호출을 생략함 | 자주 묻는 질문 답변지 |
| SSL Termination | TLS 암복호화를 프록시에서 처리하여 백엔드 부담을 경감함 | 경비실에서 신분 확인 후 입장 허용 |

> 요약: Listener로 수신 후 Routing Rule에 따라 백엔드로 중계하며 캐싱·SSL 처리를 담당함

## Ⅲ. 절차
```text
요청 수신 --> SSL 복호화 --> 라우팅 판단 --> 백엔드 중계/캐시 응답
```
- 1단계: 클라이언트 요청을 Listener가 수신함
- 2단계: SSL Termination에서 TLS 복호화를 수행함
- 3단계: Routing Rule에 따라 대상 백엔드를 결정하거나 캐시 히트 시 즉시 응답함
- 4단계: 백엔드 응답을 클라이언트로 반환하며 캐시 갱신 여부를 판단함

> 요약: 수신 → SSL 처리 → 라우팅 → 응답 반환의 4단계로 요청을 중계함

## Ⅳ. 문제점
- 단일 병목: 모든 트래픽이 프록시를 경유하므로 프록시 장애 시 전체 서비스 중단됨
- 캐시 정합성: 캐시된 콘텐츠와 원본 간 불일치 발생 시 오래된 데이터가 제공됨
- 디버깅 복잡도: 중계 계층 추가로 요청 추적이 어려워져 장애 원인 분석 시간이 증가함

> 요약: 프록시 병목, 캐시 정합성, 디버깅 복잡도가 주요 과제임

## Ⅴ. 개선방안
1. 단기: Active-Standby 이중화로 프록시 SPOF 제거
2. 중기: TTL 기반 캐시 무효화 정책과 Cache-Control 헤더 표준화로 정합성 확보
3. 장기: 분산 추적(Distributed Tracing) 도입으로 요청 경로 전구간 가시성 확보

> 요약: 이중화, 캐시 정책 표준화, 분산 추적 도입으로 단계별 개선이 가능함

## Ⅵ. 전망
- 발전 방향: API Gateway와 기능이 통합되어 인증·속도 제한·라우팅을 단일 계층에서 처리하는 추세임
- 기술사적 판단: 마이크로서비스 환경에서 서비스 메시의 사이드카 프록시로 역할이 세분화되고 있음
- 기술사 제언: 프록시 계층 설계 시 관측성(Observability) 기능을 초기부터 내장할 필요가 있음
