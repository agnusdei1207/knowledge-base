## Ⅰ. 개요
- **정의**: 분산 환경의 이기종 시스템 간 상호 통신 및 서비스 인터페이스(API)를 구축하는 대표적 아키텍처 및 규약임.
- **배경 및 필요성**: 플랫폼(OS, 언어)에 종속되지 않는 표준화된 외부 연동 및 경량화된 데이터 교환 패러다임 요구 증대.
- **출제 의도**: 무거운 행위 중심 프로토콜(SOAP)과 유연한 자원/상태 기반(REST) 아키텍처 특성에 따른 실무 적용 판단 역량 평가

## Ⅱ. 구성요소

```text
+-------------------------+
|  Component Architecture |
+-------------------------+
| [ Node A ] <-> [ Node B]|
+-------------------------+
```

| 구성요소 | 설명 | 비유 |
|---|---|---|
| **SOAP (Protocol)** | XML 기반의 엄격한 메시지 구조를 가지며 높은 보안성(WS-Security)과 신뢰성 지원 | 격식을 차린 공식 공문서 및 증빙 결재 |
| **REST (Architecture)** | 자원을 URI로 나타내고 HTTP 메서드(GET, POST 등)로 조작하는 경량화 패턴 | 간편하고 직관적인 일반 엽서/메모 소통 |
| **데이터 규격 비교** | SOAP는 파싱이 무거운 XML 봉투를 강제하며 REST는 유연한 JSON 포맷 주로 채택 | 포장 규격 제한 유무 및 짐의 무게 차이 |

> 요약: SOAP는 신뢰성과 트랜잭션이 생명인 복잡한 시스템에, REST는 모바일/웹 생태계의 유연한 고속 연동에 특화됨.

## Ⅲ. 절차

```text
+-------+   +-------+   +-------+   +-------+
| Step1 |-->| Step2 |-->| Step3 |-->| Step4 |
+-------+   +-------+   +-------+   +-------+
```

1. **[SOAP 준비] 인터페이스 정의**: 제공 서비스 구조를 담은 WSDL 문서를 발행 및 사전 공유함.
2. **[SOAP 통신] 엄격한 규격 교환**: 클라이언트가 규격화된 XML 봉투(Envelope)에 데이터를 감싸 요청/응답함.
3. **[REST 준비] 자원 매핑**: 시스템 모든 정보를 고유한 URI(/users)와 HTTP 메서드로 사상함.
4. **[REST 통신] 상태 데이터 직관적 교환**: 가벼운 JSON 기반 데이터 페이로드로 별도 껍데기 없이 요청/응답함.

> 요약: SOAP는 사전 정의된 명세 기반 무거운 XML 규격을 따르며, REST는 URI와 HTTP 메서드로 자원 데이터를 직관 조작함.

## Ⅳ. 문제점
- SOAP의 극심한 오버헤드 (원인: 데이터보다 메시지 구조(XML 껍데기)의 용량이 커서 네트워크 전송/파싱 비용 낭비)
- REST의 명확한 표준 부재 (원인: 단순 가이드라인이라 설계자마다 에러 규격과 URL 스타일이 파편화됨)
- REST의 다중 리소스 조작 비효율 (원인: 연관된 다중 데이터 조작 시 요청 횟수 과다(Under) 또는 불필요 데이터 노출(Over) 발생)

## Ⅴ. 개선방안
- **단기 방안**: [단기] 신규 프론트엔드 연동 구간 JSON-REST 전면 도입 (레거시를 감싼 API 게이트웨이 구축으로 모바일 연동 경량화 달성)
- **중기 방안**: [중기] OpenAPI(Swagger) 명세서 기반 개발/표준화 적용 (파편화된 REST 설계를 사내 표준화하고 자동화 문서 및 클라이언트 연동 규격화)
- **장기 방안**: [장기] GraphQL 및 gRPC 혼용 마이크로서비스 아키텍처 진화 (REST 한계 극복용 GraphQL 도입 및 백엔드 고속 바이너리 통신망(gRPC) 분리 구축)

## Ⅵ. 전망
- 퍼블릭 웹 오픈 API의 대다수가 REST 기반이나, 내부 코어 연동에서는 고속 바이너리 RPC 프로토콜이 대체제로 떠오름.
