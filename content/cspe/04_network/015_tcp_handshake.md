## Ⅰ. 개요
- **정의**: TCP 통신 시 신뢰성 있는 세션을 수립(3-Way)하고 안전하게 해제(4-Way)하는 제어 절차임.
- **배경 및 필요성**: 네트워크 패킷 유실 및 순서 뒤섞임 방지를 위한 초기 상태 동기화 및 잔여 데이터 처리 조율.
- **출제 의도**: TCP 연결 지향성 메커니즘과 세션 상태 전이도(State Machine)의 상세 구조 파악 역량 평가

## Ⅱ. 구성요소

```text
+-------------------------+
|  Component Architecture |
+-------------------------+
| [ Node A ] <-> [ Node B]|
+-------------------------+
```

| 구성요소 | 설명 | 비유 |
|---|---|---|
| **3-Way Handshake** | 데이터 전송 전 SYN/ACK 플래그를 교환하여 초기 시퀀스 번호를 동기화하는 연결 수립 | 통화 전 '여보세요? 네 말씀하세요' |
| **4-Way Handshake** | 전송 종료 시 FIN/ACK 플래그를 주고받아 양방향의 남은 데이터 처리 후 연결 해제 | 끊을게, 잠깐만, 응 끊어, 그래 |
| **Control Flags** | SYN, ACK, FIN 등 TCP 헤더 내 1비트 필드로 현재 제어 목적을 명시함 | 상황에 맞는 제어 신호 깃발 |

> 요약: 데이터 전송 전 3단계로 연결 세션을 확립하고, 종료 시 양측 동의 하에 4단계로 해제함.

## Ⅲ. 절차

```text
+-------+   +-------+   +-------+   +-------+
| Step1 |-->| Step2 |-->| Step3 |-->| Step4 |
+-------+   +-------+   +-------+   +-------+
```

1. **클라이언트 요청**: 연결 수립(SYN) 또는 연결 해제(FIN) 제어 플래그를 전송함.
2. **서버 인지 및 대응**: 수신한 플래그에 대한 확인 응답(ACK)을 보내고 자신의 제어 상태를 반환함.
3. **[3-Way 완료] 클라이언트 ACK**: 클라이언트가 최종 수락 응답(ACK)을 보내면 세션(ESTABLISHED) 활성화됨.
4. **[4-Way 완료] 잔여 데이터 정리**: 남은 데이터를 모두 보내고 최종 상호 해제 동의 후 소켓을 닫음.

> 요약: SYN/ACK를 통해 3단계 연결을, FIN/ACK를 통해 4단계 종료 과정을 안전하게 수행함.

## Ⅳ. 문제점
- SYN Flooding 공격 취약성 (원인: 악의적 다수 SYN 요청만 보내 서버의 Half-Open 대기 큐 자원을 고갈시킴)
- TIME_WAIT 상태 소켓 누적 (원인: 4-Way 후 마지막 ACK 유실 대비로 2MSL 간 소켓을 유지해야 해 포트가 고갈됨)
- 핸드셰이크로 인한 오버헤드 (원인: 아주 작은 데이터 전송에도 연결 수립/해제를 위한 왕복 지연 시간 낭비)

## Ⅴ. 개선방안
- **단기 방안**: [단기] SYN Cookie 기능 활성화 (서버가 연결 상태를 메모리에 저장하지 않고 쿠키 값으로 처리해 대기열 자원 방어)
- **중기 방안**: [중기] 타임아웃 최적화 (서버 커널에서 TIME_WAIT 소켓의 빠른 재사용/회수 옵션을 활성화해 자원 고갈 최소화)
- **장기 방안**: [장기] TCP Fast Open 및 UDP/QUIC 도입 (쿠키나 무연결 구조를 통해 0-RTT 연결을 실현하여 핸드셰이크 오버헤드 제거)

## Ⅵ. 전망
- 초저지연(Ultra-Low Latency) 환경 대응을 위해, 무거운 핸드셰이크는 보안(TLS)과 융합된 QUIC 구조로 대체 추세임.
