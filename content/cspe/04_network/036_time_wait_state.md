# 📖 【암기용】 개념 완전 이해

> 목적: 이 개념을 처음 보는 사람도 완벽히 이해하게 만든다. 시험 답안 양식이 아니라, 이해를 위한 친절한 설명이다.

## 한눈에
- **개요**: TCP 연결을 끊을 때 "먼저 연결을 끊자고 한 쪽(Active Close)"이 연결 종료 후 즉시 소켓을 없애지 않고 잠시 동안(보통 1~2분) 놔두는 대기 상태
- **왜 필요한가**: 지연되어 뒤늦게 도착한 패킷이 다음 번에 맺어진 새로운 연결(같은 IP/포트 조합)에 섞여 들어가는 대참사를 막기 위해서다.
- **핵심 직관**: 방을 빼고 이사 갈 때, 옛날 우편물이 다음 세입자에게 배달되는 걸 막기 위해 우체국에 잠시 "나사 감아둔 기간(유예 기간)"을 설정하는 것이다.

## 깊이 이해
- **배경·문제의식**: TCP 연결 종료(4-Way Handshake) 시 마지막으로 수신자에게 "알겠다(ACK)"라고 보낸 패킷이 공중에서 분실될 수 있다. 내가 바로 소켓을 닫아버리면, 상대방은 자기가 보낸 FIN이 유실된 줄 알고 계속 FIN을 재전송하게 되고 연결이 꼬인다.
- **작동 원리**: 먼저 종료(FIN)를 요청한 측은 최종 ACK를 보낸 후 **2MSL(Maximum Segment Lifetime, 약 1~2분)** 동안 소켓을 `TIME_WAIT` 상태로 유지한다. 이 기간 동안 오는 이전 세션의 잔여 패킷은 모두 폐기하고, 상대방이 재전송한 FIN이 오면 다시 ACK를 응답해준다.
- **비유**: 통화 끊기 전 "나 먼저 끊을게" -> "어 끊어라" -> "진짜 끊는다" -> 뚜뚜뚜... 여기서 수화기를 내려놓고 바로 코드를 뽑지 않고 1분 정도 귀에 대고 있는 거다. 상대가 못 들었을까 봐.
- **구체 예시**: 내 서버가 외부 API 서버에 초당 1000번씩 HTTP 단기 요청을 보낸다 치자. 내 서버(클라이언트 역할)가 먼저 끊기 때문에 내 서버에 TIME_WAIT 소켓이 초당 1000개씩 쌓인다. 1분이면 6만 개다. 임시 포트(65535개)가 바닥나서 새 통신이 불가능해진다.
- **흔한 오해·주의점**: "TIME_WAIT은 나쁜 거니까 무조건 없애야 한다"는 위험하다. TIME_WAIT은 TCP 신뢰성을 위한 정상적이고 필수적인 방어막이다. 무작정 끄면 데이터 오염이 발생할 수 있으니 `SO_REUSEADDR`나 커널 튜닝을 조심스레 쓴다.

## 연결 개념
- 4-Way Handshake — TCP 연결을 안전하게 종료하는 4단계 과정 (FIN -> ACK -> FIN -> ACK)
- MSL (Maximum Segment Lifetime) — 패킷이 네트워크 상에서 살아남을 수 있는 최대 시간 (보통 30초~1분)
- Port Exhaustion (포트 고갈) — 사용 가능한 임시 포트를 모두 소진하여 새 연결을 맺지 못하는 에러

# 📝 【답안용】 시험 답안 템플릿

> 목적: 시험장에서 25분에 그대로 쓰는 답안 양식. 작성방식(추상표현 금지·수치·도식·문제유형 전환)을 엄격히 지킨다.
> 핵심: 이 시험은 정보를 많이 나열하는 시험이 아니라, 문제 신호어에서 출제자 의도를 읽고 핵심 논점을 선별해 쓰는 시험이다.

## 핵심 인사이트 (3줄 요약)

> 1. **본질**: TCP 4-Way Handshake의 마지막 단계에서, 연결을 먼저 종료(Active Close)한 단말이 패킷 유실을 대비해 2MSL 시간 동안 소켓을 유지하는 대기 상태다.
> 2. **가치**: 지연 패킷에 의한 새 연결의 데이터 오염(Data Corruption)을 방지하고, 원격 단말의 정상적인 연결 종료를 보장하는 TCP 신뢰성의 최후 보루다.
> 3. **판단 포인트**: 마이크로서비스(MSA) 등 서버-서버 간 단기 통신이 급증하는 환경에서는 TIME_WAIT 누적으로 인한 아웃바운드 포트 고갈 리스크를 막기 위해 Connection Pool과 커널 파라미터 튜닝이 필수적이다.

## 출제 의도 및 답안 포인트

| 출제 의도 | 반드시 짚을 핵심 | 감점 회피 포인트 |
|:---|:---|:---|
| TCP 연결 종료 프로세스의 완벽한 이해 | Active Close 측에만 TIME_WAIT 발생, 2MSL 대기 원리 | 4-Way Handshake 그림만 그리고 TIME_WAIT 존재 이유 누락 |
| 분산 환경에서의 병목 원인 도출 | 로드밸런서, 프록시, API 서버의 로컬 포트 고갈 현상 | 대용량 트래픽 장애 원인을 단순히 CPU/Memory 부족으로 귀결 |
| 리스크 해결(튜닝) 역량 확인 | tcp_tw_reuse, SO_REUSEADDR, HTTP Keep-Alive 방안 | TIME_WAIT을 완전히 무력화(tcp_tw_recycle 등)하는 위험한 튜닝 권장 |

> 요약: 신뢰성을 위한 필수 스펙(TIME_WAIT)이 클라우드 대규모 분산 아키텍처에서 어떻게 치명적 병목(포트 고갈)으로 돌변하는지 원인과 제어 방안을 제시해야 한다.

## Ⅰ. 개요 및 필요성

- 정의: TCP 연결 종료 시, Active Close(먼저 FIN을 보낸 쪽) 호스트가 마지막 ACK 송신 후 일정 시간(2×MSL) 소켓 상태를 유지하는 기법
- 배경: 패킷 교환망 특성상 라우터 큐 지연으로 이전 연결의 잔류 패킷(Delayed Packet)이 뒤늦게 도착할 가능성 상존
- 필요성: 동일한 4-Tuple(IP/Port 조합)로 새 연결이 맺어질 경우 지연 패킷이 섞여 데이터가 오염되는 것을 방지하고, 마지막 ACK 유실 시 재전송 기회 제공

---

## Ⅱ. 구조 및 구성요소

```text
[TCP 4-Way Handshake 종료와 TIME_WAIT 상태]
[Active Close (먼저 끊는 쪽)]                 [Passive Close (기다리는 쪽)]
  상태                명령어 | 흐름 | 명령어              상태
ESTABLISHED          close() | FIN  |                    ESTABLISHED
FIN_WAIT_1    ---------------+----->+------------------- CLOSE_WAIT (앱 종료 대기)
                             | ACK  | close()
FIN_WAIT_2    <--------------+------+
                             | FIN  |
TIME_WAIT     <--------------+------+------------------- LAST_ACK
(2MSL 대기)                  | ACK  |
CLOSED        ---------------+----->+------------------- CLOSED
```

| 구성요소 | 역할 | 특이사항 |
|:---|:---|:---|
| Active Close | 종료를 주도하는 주체 (Client 혹은 프록시 서버) | 4단계 중 마지막 ACK를 전송하고 TIME_WAIT 돌입 |
| Passive Close | FIN을 받고 종료를 준비하는 주체 | 애플리케이션 자원을 정리하고 FIN을 송신 |
| 2 MSL 타이머 | Maximum Segment Lifetime의 2배 대기 시간 | 왕복(FIN 유실 + ACK 송신) 최대 지연시간 커버 (보통 60초) |
| 4-Tuple 잠금 | Source/Dest IP, Source/Dest Port 조합의 재사용 금지 | 대기 시간 동안 해당 포트 조합은 바인딩(bind) 불가 |

> 요약: 연결을 주도해서 끊는 쪽은 책임지고 상대방이 정상 종료될 때까지 소켓을 열어두고 기다려야 한다.

## Ⅲ. 동작원리 및 흐름도

```text
[TIME_WAIT의 2가지 존재 목적 검증 흐름]
1. (상대방 보호) 마지막 ACK 유실 시:
   내 ACK 유실 -> 상대방 타임아웃 -> 상대방 FIN 재전송 -> TIME_WAIT 소켓이 살아있어 즉시 ACK 재응답 -> 정상 종료 완료
   (소켓이 없었다면 상대방은 RST를 받고 비정상 종료 에러 발생)

2. (내 연결 보호) 지연 패킷 도착 시:
   이전 연결의 지연 패킷 도착 -> TIME_WAIT 소켓이 수신 후 폐기
   (소켓이 닫히고 우연히 같은 포트로 새 연결이 열렸다면 그 패킷이 섞여 들어감)
```

| 단계 | 예외 시나리오 | TIME_WAIT 동작 | 검증 효과 |
|:---:|:---|:---|:---|
| 1 | 최종 ACK 공중 분실 | 상대의 FIN 재전송을 수신하고 ACK 재발송 | 상대 측 LAST_ACK 상태 고립 방지 |
| 2 | FIN과 ACK 순서 역전 | 패킷 시퀀스 번호 대조 후 무시/폐기 | 연결 종료 루틴의 신뢰성 보장 |
| 3 | 이전 세션 데이터 도착 | 2MSL 기간 내 도착한 모든 잡음 패킷 폐기 | 4-Tuple 재사용 시 데이터 오염 원천 차단 |
| 4 | 2MSL 시간 만료 | 소켓 파일 디스크립터(FD) 완전 삭제, 포트 반환 | 시스템 자원 정상 환원 (CLOSED) |

> 요약: 타임아웃(2MSL) 동안 방패막이 역할을 하여, 과거의 유령 패킷이 미래의 새로운 통신을 덮어쓰는(Overwrite) 것을 물리적으로 막는다.

## Ⅳ. 특징

| 구분 | 내용 | 판단 포인트 |
|:---|:---|:---|
| 방향성 | 먼저 통신을 끊는 쪽(Active Close)에만 발생 | Nginx(Reverse Proxy)가 백엔드를 끊을 때 Nginx 서버 포트가 고갈됨 |
| 자원 점유 | 소켓 1개당 커널 메모리 할당 및 포트 번호 점유 | 보통 로컬 포트 범위(대략 3만 개) 소진 시 포트 고갈 에러(EADDRINUSE) |
| 불가피성 | TCP 스펙(RFC 793)상 정상적이고 필수적인 동작 | 오류로 취급하여 무리하게 소켓을 강제 삭제하면 2차 장애 유발 |

> 요약: 서버-클라이언트 통신에서 웹 브라우저(클라이언트)가 TIME_WAIT을 가지는 건 무해하지만, 프록시가 백엔드 서버망을 향해 가질 때는 대형 장애의 씨앗이 된다.

## Ⅴ. 심화 비교 및 적용 판단

| 비교 축 | TIME_WAIT 튜닝 안 함 | SO_REUSEADDR | tcp_tw_reuse (sysctl) |
|:---|:---|:---|:---|
| 적용 대상 | 디폴트 운영 환경 | 애플리케이션 소켓 레벨 | 커널 레벨 파라미터 제어 |
| 동작 원리 | 2MSL(60초) 정직하게 대기 | 서버 데몬 재시작 시 바인딩 허용 | 타임스탬프 기반 안전한 재사용 허용 |
| 적용 리스크 | 아웃바운드 포트 고갈 장애 | 개발 시 소켓 오류 방지용 (운영 무관) | NAT/로드밸런서 환경에서 타임스탬프 역전 시 패킷 드롭 가능성 존재 |

> 요약: 대용량 트래픽 서버에서는 커널 파라미터를 조작(sysctl)하는 방법보다 애플리케이션 단에서 커넥션 맺고 끊기를 최소화하는 구조적 접근이 안전하다.

| 리스크 | 원인 | 대응 방안 | 확인 지표 |
|:---|:---|:---|:---|
| Nginx 아웃바운드 포트 고갈 | 백엔드(Upstream)로 단기 연결 후 끊음 | 백엔드 통신 구간에 HTTP Keep-Alive 적용 (Connection Pool) | `netstat -ntp | grep TIME_WAIT | wc -l` |
| 로드밸런서(L4) 통신 단절 | TCP 튜닝(`tcp_tw_recycle`) 오남용 | `tcp_tw_recycle` 절대 사용 금지 (리눅스 4.12부터 폐기됨) | 클라이언트 연결 타임아웃 / RST 패킷 급증 |

> 요약: 위험한 커널 옵션(recycle)은 폐기되었으므로, TIME_WAIT 소켓 재사용(reuse)을 제한적으로 열거나 연결 재사용(Keep-Alive)으로 생성을 막아야 한다.

## Ⅵ. 실무 적용 및 결론

**적용 방안 3개 (포트 고갈 방지 대책):**
1. 애플리케이션 아키텍처: HTTP `Keep-Alive` 옵션 활성화 및 커넥션 풀(Connection Pool) 사용으로 한 번 맺은 연결을 끊지 않고 재활용해 TIME_WAIT 생성 자체를 원천 차단
2. 로컬 포트 범위 확장: 커널 변수 `net.ipv4.ip_local_port_range = 1024 65535` 적용을 통해 아웃바운드 임시 포트 가용량을 약 2.8만 개에서 6.4만 개로 2배 이상 확장
3. 타임스탬프 기반 안전한 소켓 재사용: `net.ipv4.tcp_tw_reuse = 1` 및 `net.ipv4.tcp_timestamps = 1`을 동시 활성화하여, 1초가 지난 TIME_WAIT 소켓은 아웃바운드용으로 즉시 재할당

**결론 (2줄):**
- 기술사 판단: TIME_WAIT은 에러가 아니라 TCP 신뢰성을 위한 필수 희생양이며, 대용량 MSA 환경에서는 이를 억지로 지우려 하기보다 커넥션 풀(Keep-Alive)로 우회하는 것이 정석이다.
- 향후 방향: 최근 클라우드 네이티브 환경에서는 서비스 메쉬(Envoy, Istio)가 프록시 역할을 전담하며, L7 멀티플렉싱(HTTP/2, HTTP/3)을 통해 물리적 소켓 연결 생성/종료 자체를 극소화하고 있다.
