## Ⅰ. 개요
- **정의**: 마이크로서비스 간 통신을 사이드카 프록시로 제어·관측하는 인프라 계층임
- **배경/필요성**: 서비스 수 증가 시 통신 로직(재시도·인증·로드밸런싱)을 각 서비스에 구현하면 중복·불일치가 발생함
- **비유**: 각 세대에 우편함을 두고 관리인이 우편 수발신을 대행하는 것과 유사함

| 출제 의도 | 반드시 짚을 핵심 | 감점 회피 포인트 |
|:---|:---|:---|
| 사이드카 패턴 기반 통신 제어 원리 | Data Plane(프록시)과 Control Plane 분리 | API Gateway와 Service Mesh의 역할 차이 명시 필요 |

> 요약: 사이드카 프록시를 통해 서비스 간 통신을 애플리케이션 코드와 분리하여 제어하는 계층임

## Ⅱ. 구성요소
```text
Service A --> Sidecar Proxy --+
                              +--> Control Plane (Istiod/Linkerd)
Service B --> Sidecar Proxy --+         |
                                   Config / Policy
                                   mTLS Cert Mgmt
```

| 구성요소 | 설명 | 비유 |
|:---|:---|:---|
| Sidecar Proxy | 각 서비스 Pod에 배치되어 인바운드/아웃바운드 트래픽을 가로채 처리함 | 세대별 관리인 |
| Control Plane | 라우팅 규칙·mTLS 인증서·정책을 프록시에 배포하는 중앙 관리자임 | 관리 사무소 |
| Data Plane | 사이드카 프록시들의 집합으로 실제 트래픽 전달을 수행함 | 우편 배달 네트워크 |

> 요약: Control Plane이 정책을 정의하고 Data Plane(사이드카)이 트래픽을 처리함

## Ⅲ. 절차
```text
Step1 Inject --> Step2 Discover --> Step3 Route --> Step4 Observe
```
- 1단계: Pod 배포 시 사이드카 프록시를 자동 주입(Injection)함
- 2단계: Control Plane이 서비스 레지스트리에서 엔드포인트를 탐색·동기화함
- 3단계: 트래픽 정책(가중치 라우팅, 재시도, 서킷 브레이커)에 따라 요청을 라우팅함
- 4단계: 프록시가 메트릭·트레이스·로그를 수집하여 관측성을 제공함

> 요약: 주입-탐색-라우팅-관측 순서로 서비스 간 통신을 제어함

## Ⅳ. 문제점
- 사이드카 오버헤드: 프록시 추가로 Pod당 CPU·메모리 사용량이 증가하고 요청 지연이 추가됨
- 운영 복잡도: Control Plane 장애 시 정책 갱신이 중단되어 전체 메시에 영향이 파급됨
- 학습 곡선: 트래픽 정책·mTLS·관측성 설정이 복잡하여 도입 초기 운영 부담이 큼

> 요약: 사이드카 오버헤드, Control Plane 가용성, 운영 복잡도가 핵심 과제임

## Ⅴ. 개선방안
1. 단기: eBPF(079 참조) 기반 Sidecar-less 메시로 프록시 오버헤드를 제거함
2. 중기: Control Plane 이중화·다중 리전 배치로 단일 장애점을 제거함
3. 장기: GitOps 기반 선언적 트래픽 정책 관리로 운영 복잡도를 감소함

> 요약: Sidecar-less, 이중화, GitOps로 서비스 메시 운영을 경량화함

## Ⅵ. 전망
- 발전 방향: Ambient Mesh(사이드카 없는 메시)가 차세대 모델로 부상함
- 기술사적 판단: 제로 트러스트 네트워크 구현에서 mTLS 자동화를 제공하는 핵심 수단임
- 기술사 제언: 서비스 메시 도입 범위를 단계적으로 확대하는 점진적 마이그레이션 전략이 필요함
