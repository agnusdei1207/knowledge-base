# 📖 【암기용】 개념 완전 이해

> 목적: MEC가 단순히 서버를 가까이 두는 개념이 아니라 5G 사용자면과 응용 처리를 결합하는 구조임을 이해하게 만든다.

## 한눈에
- **개요**: MEC는 사용자 가까운 기지국·집선국·사업자 엣지에 컴퓨팅 자원을 배치해 지연과 백홀 부하를 줄이는 구조다.
- **왜 필요한가**: AR/VR, 스마트팩토리, V2X는 중앙 클라우드 왕복 지연과 트래픽 집중이 서비스 품질을 제한한다.
- **핵심 직관**: 모든 요청을 본사 데이터센터로 보내지 않고, 현장 옆 사무실에서 바로 처리하는 방식이다.

## 깊이 이해
- **배경·문제의식**: 5G는 eMBB·URLLC·mMTC를 목표로 하지만 무선 구간만 줄여서는 전체 서비스 지연을 보장할 수 없다. 코어망 UPF와 애플리케이션을 엣지에 배치해야 왕복 경로가 짧아진다.
- **작동 원리**: 단말 트래픽은 gNB에서 5GC 제어를 거쳐 로컬 UPF로 분기되고, MEC 플랫폼은 애플리케이션 실행, DNS/traffic steering, API 노출을 담당한다.
- **비유**: 음식 배달에서 중앙 주방 하나가 아니라 동네 주방을 두면 이동 거리가 줄어드는 것과 같다. 대신 동네 주방마다 재고와 품질 관리가 필요하다.
- **구체 예시**: 공장 비전검사는 카메라 영상을 중앙 클라우드로 보내면 수십 ms 이상 지연이 발생한다. MEC는 현장 UPF와 GPU 서버에서 추론해 p95 10~20ms 목표를 설정할 수 있다.
- **흔한 오해·주의점**: MEC는 CDN과 다르다. CDN은 콘텐츠 캐싱 중심이고 MEC는 사용자면 분기, 실시간 처리, 5G QoS 연동까지 포함한다.

## 연결 개념
- 5G UPF Local Breakout — 사용자면을 엣지로 분기
- 네트워크 슬라이싱 — MEC 서비스별 QoS 격리
- 엣지 AI — 영상·센서 데이터를 현장 GPU/NPU에서 처리

# 📝 【답안용】 시험 답안 템플릿

> 목적: MEC 답안에서 지연 단축 구호가 아니라 5G UPF, 로컬 브레이크아웃, 배치 위치, 운영 지표를 구조화한다.
> 핵심: 출제자는 클라우드-네트워크-응용을 통합 설계하는지 확인한다.

## 핵심 인사이트 (3줄 요약)

> 1. **본질**: MEC는 5G 사용자면과 애플리케이션을 단말 가까운 엣지에 배치해 지연, 백홀, 데이터 주권 요구를 처리하는 구조다.
> 2. **가치**: UPF Local Breakout, DNS steering, MEC API로 AR/VR·스마트팩토리·V2X의 p95 지연과 트래픽 경로를 통제한다.
> 3. **판단 포인트**: 엣지 위치, UPF 배치, GPU/NPU 자원, 앱 배포 자동화, SLA 관측성을 함께 설계해야 한다.

## 출제 의도 및 답안 포인트

| 출제 의도 | 반드시 짚을 핵심 | 감점 회피 포인트 |
|:---|:---|:---|
| MEC 구조 이해 확인 | gNB, UPF, MEC Platform, App, Orchestrator | 단순 캐시 서버로 설명 |
| 5G 연동 판단 확인 | Local Breakout, QoS Flow, Network Slice | 무선 지연만 쓰고 코어 경로 누락 |
| 실무 운영 역량 확인 | p95 latency, GPU 사용률, 앱 배포·관측 | 지연 목표와 측정 방법 누락 |

> 요약: MEC 문제는 엣지 서버 위치보다 사용자면 분기와 응용 SLA를 어떻게 보장하는지가 핵심이다.

---

## Ⅰ. 개요 및 필요성

MEC는 모바일망 엣지에 컴퓨팅과 애플리케이션을 배치하는 구조다. 중앙 클라우드 왕복 경로는 AR/VR·V2X·공장 제어의 지연 요구를 충족하기 어렵다. 5G MEC는 UPF 로컬 분기와 엣지 앱 실행으로 서비스별 p95 지연 목표를 관리한다.

---

## Ⅱ. 구조 및 구성요소

```text
UE -> gNB -> 5GC Control Plane -> Local UPF -> MEC Platform -> MEC App
                         / QoS Flow
                         / Network Slice
Cloud Orchestrator -> Edge Orchestrator -> App Deploy -> Observability
```

| 구성요소 | 역할 | 특이사항 |
|:---|:---|:---|
| gNB | 무선 접속 및 QoS Flow 매핑 | 5QI, slice 식별 |
| Local UPF | 사용자 트래픽을 엣지로 분기 | Local Breakout, ULCL |
| MEC Platform | 앱 실행·서비스 발견·API 제공 | ETSI MEC API, DNS steering |
| MEC App | 영상분석·AR·V2X 등 업무 처리 | GPU/NPU, 컨테이너 배포 |
| Orchestrator | 앱 배치·확장·관측 | Kubernetes, SLA 정책 |

> 요약: MEC는 gNB-UPF-MEC App 경로를 짧게 만들고, 오케스트레이터가 엣지 자원과 SLA를 관리한다.

---

## Ⅲ. 동작원리 및 흐름도

```text
서비스 요청 -> QoS/Slice 식별 -> Local UPF 선택
-> MEC App 라우팅 -> 현장 데이터 처리
-> 결과 반환 -> latency, throughput, GPU 사용률 수집
```

| 단계 | 처리 내용 | 검증 기준 |
|:---:|:---|:---|
| 1 | 단말 세션 수립과 QoS Flow 생성 | PDU Session 성공률 |
| 2 | SMF 정책으로 Local UPF 선택 | UPF selection log |
| 3 | DNS/traffic steering으로 MEC App 연결 | service discovery 성공률 |
| 4 | 엣지 앱에서 추론·제어 처리 | p95 latency 10~20ms 목표 |
| 5 | 중앙 클라우드와 데이터 동기화 | sync lag, packet loss |

> 요약: MEC는 세션 정책으로 트래픽을 엣지에 붙이고, 앱 처리와 관측을 한 경로에서 관리한다.

## Ⅳ. 특징

| 구분 | 중앙 클라우드 | MEC | 판단 포인트 |
|:---|:---|:---|:---|
| 경로 | 단말-코어-인터넷-리전 | 단말-gNB-UPF-엣지 | 홉 수와 RTT |
| 지연 | 리전 위치에 따라 수십 ms 이상 | p95 10~20ms 목표 설정 가능 | 무선+코어+앱 합산 |
| 데이터 처리 | 원본 데이터 중앙 전송 | 현장 처리 후 요약 전송 | 영상·센서 트래픽 절감 |
| 운영 | 리전 집중 운영 | 다수 엣지 분산 운영 | 패치·관측·장애 격리 |

> 요약: MEC는 지연과 백홀 경로를 줄이는 대신 다수 엣지 노드 운영과 앱 배포 체계가 필요하다.

## Ⅴ. 심화 비교 및 적용 판단

| 비교 축 | 기존/대안 | MEC | 선택 기준 |
|:---|:---|:---|:---|
| 구조 | 중앙 클라우드 처리 | Local UPF+MEC App | p95 지연 20ms 이하 요구 |
| 비용/성능 | 리전 GPU 집중 | 엣지 GPU/NPU 분산 | 영상 원본 전송량과 GPU 사용률 |
| 운영/위험 | 중앙 장애 관리 | 사이트별 장애·패치 | Edge SRE와 원격관측 필요 |

> 요약: MEC는 지연·트래픽 절감 가치가 엣지 운영비와 자원 분산 비용을 초과할 때 적용한다.

| 리스크 | 원인 | 대응 방안 | 확인 지표 |
|:---|:---|:---|:---|
| 지연 목표 미달 | UPF 위치·앱 배치 불일치 | SMF 정책, DNS steering 조정 | p95/p99 latency |
| 자원 병목 | GPU/NPU 과점유 | HPA, GPU quota, 모델 경량화 | GPU utilization 70% 이하 목표 |
| 운영 편차 | 엣지 사이트별 버전 차이 | GitOps, canary, rollback | 배포 성공률, MTTR |

> 요약: MEC 리스크는 네트워크 경로와 앱 배치가 어긋날 때 발생하므로 지연·자원·배포 지표를 동시에 본다.

| 점검 항목 | 목표 기준 | 측정 방법 |
|:---|:---|:---|
| 지연 | p95 10~20ms, jitter 업무 기준 충족 | APM, UE probe, TWAMP |
| 처리량 | uplink video FPS, Mbps 기준 충족 | MEC App metric, UPF counter |
| 운영 | 배포 실패율 1% 이하 목표 | CI/CD log, Kubernetes event |

> 요약: MEC 성공 여부는 지연, 처리량, 배포 신뢰도를 서비스 단위로 측정해 판단한다.

## Ⅵ. 실무 적용 및 결론

**적용 방안 3개 (필수 — 단계별 또는 항목별):**
1. AR/VR·V2X·영상분석처럼 p95 20ms 이하 또는 원본 영상 로컬 처리 요구가 있는 업무를 MEC 후보로 선정함
2. Local UPF, ULCL, DNS steering을 설계하고 gNB-엣지-UPF 경로의 RTT와 packet loss 기준선을 측정함
3. Kubernetes 기반 엣지 배포, GPU quota, OpenTelemetry 관측을 적용해 앱 버전·자원·SLA를 사이트별로 추적함

**결론 (2줄):**
- 기술사 판단: 지연 민감·데이터 현장성 업무는 MEC, 일반 웹·배치 업무는 중앙 클라우드로 분리함
- 향후 방향: 5G SA, 네트워크 슬라이싱, 엣지 AI가 결합되어 MEC는 산업용 실시간 플랫폼으로 확장됨
