## 미리 알고가기

- SYN: 연결을 시작하고 시퀀스 번호를 맞추기 위한 TCP 제어 플래그임
- ACK: 상대가 보낸 번호를 확인했다는 의미의 제어 플래그임
- ISN: 각 방향 통신의 시작 시퀀스 번호임
- MSS: 한 번에 실을 수 있는 최대 TCP 데이터 크기임

## Ⅰ. 개요

- **정의/개념**: TCP 3-way handshake는 양 종단이 데이터 전송을 시작하기 전에 시퀀스 번호와 수신 가능 조건을 맞춰 신뢰성 있는 연결을 여는 3단계 절차임. 이 과정에서 SYN, SYN-ACK, ACK를 차례로 교환하며 연결 상태를 `ESTABLISHED`로 만든다
- **배경/필요성**: TCP는 순서 보장, 재전송, 흐름 제어를 수행해야 하므로 데이터를 보내기 전에 양측이 시작 번호와 옵션을 먼저 합의해야 하며, 그렇지 않으면 중복 세션과 손상된 상태가 생길 수 있음

## Ⅱ. 특징

- 송신과 수신 양방향에 대해 각각 시작 시퀀스 번호를 맞추므로 이후 데이터 순서를 추적할 수 있음
- MSS, Window Scale, SACK 허용 여부 같은 연결 옵션을 초기 단계에서 협상할 수 있음
- 연결 성립까지 최소 1 RTT가 필요하므로 짧은 연결이 많을수록 체감 지연이 커짐
- 서버는 SYN 수신 시 대기 자원을 잡아야 하므로 SYN Flood 같은 반쪽 연결 공격에 취약할 수 있음

## Ⅲ. 종류 및 비교

| 단계 | 송신 방향 | 핵심 내용 |
|:---|:---|:---|
| 1단계 | 클라이언트 -> 서버 | SYN을 보내며 자신의 ISN과 연결 옵션을 제안함 |
| 2단계 | 서버 -> 클라이언트 | SYN-ACK를 보내며 클라이언트 ISN을 확인하고 자신의 ISN을 함께 알림 |
| 3단계 | 클라이언트 -> 서버 | ACK를 보내 서버 ISN을 확인하고 실제 데이터 송수신 준비를 끝냄 |

> 요약: 3-way handshake는 단순 인사 절차가 아니라 양방향 번호와 옵션을 맞추는 동기화 과정임

## Ⅳ. 구성요소 및 구조

| 구성요소 | 설명 |
|:---|:---|
| 클라이언트 소켓 | 연결을 먼저 요청하며 SYN과 초기 옵션을 보냄 |
| 서버 리슨 큐 | 들어오는 SYN 요청을 임시로 유지하며 ACK 완료를 기다리는 구간임 |
| 시퀀스 번호 | 양측 데이터의 시작 지점을 정해 이후 재전송과 순서 보장의 기준이 됨 |
| TCP 옵션 | MSS, Window Scale, SACK 같은 성능 관련 정보를 연결 초기에 협상함 |

```text
+---------+                             +---------+
| Client  |                             | Server  |
+---------+                             +---------+
    | -------- SYN, Seq=x ----------->      |
    | <---- SYN+ACK, Seq=y Ack=x+1 ---      |
    | -------- ACK, Ack=y+1 ---------->      |
```

> 요약: 연결 수립은 양측 소켓, 대기 큐, 시퀀스 번호, 옵션 협상이 함께 맞아야 정상적으로 끝남

## Ⅴ. 원리 및 절차 흐름도

```text
+----------+     +----------+     +----------+     +----------+
| SYN전송  | --> | SYNACK수신 | --> | ACK전송  | --> | 연결성립  |
+----------+     +----------+     +----------+     +----------+
```

1. **SYN전송**: 클라이언트가 자신의 ISN과 옵션을 담아 SYN을 보냄
2. **SYNACK수신**: 서버가 요청을 받아 대기 큐에 올리고 자신의 ISN과 ACK를 함께 돌려보냄
3. **ACK전송**: 클라이언트가 서버 응답을 확인하는 ACK를 보냄
4. **연결성립**: 서버가 최종 ACK를 받으면 양측 모두 `ESTABLISHED` 상태로 들어감

## Ⅵ. 실무 적용 및 유의점

1. 인터넷 공개 서비스에서는 SYN Flood로 리슨 큐가 가득 차기 쉬우므로 SYN Cookie와 백로그 튜닝을 함께 적용하고 `SYN_RECV` 소켓 수와 연결 실패율로 확인함
2. 짧은 요청이 매우 많은 API 서비스에서는 1 RTT 연결 지연이 누적되므로 커넥션 재사용과 Keep-Alive를 우선 적용하고 새 연결 비율과 p95 응답 시간을 기준으로 확인함

## Ⅶ. 결론

TCP 3-way handshake의 핵심은 단순 연결 요청이 아니라, 이후 신뢰성 제어가 흔들리지 않도록 양측 상태와 번호를 먼저 정확히 맞추는 데 있음.
