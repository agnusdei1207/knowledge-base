# 📖 【암기용】 개념 완전 이해

> 목적: 이 개념을 처음 보는 사람도 완벽히 이해하게 만든다. 시험 답안 양식이 아니라, 이해를 위한 친절한 설명이다.

## 한눈에
- **개요**: UDP 기반으로 신뢰성과 보안(TLS 1.3)을 내재화하여 HTTP/2의 한계를 극복한 구글 주도의 차세대 전송 프로토콜
- **왜 필요한가**: TCP 기반의 HTTP/2는 패킷 하나만 유실되어도 뒤따르는 모든 데이터가 멈추는(HOL Blocking) 고질적 한계와 느린 연결 설정 지연을 안고 있었다.
- **핵심 직관**: 1차선 도로(TCP)에서 차 한 대가 고장 나면 꽉 막히던 것을, 차선 독립성을 보장하는 여러 차선(QUIC 스트림)으로 바꿔 한쪽이 막혀도 나머지는 달리게 만든 혁신이다.

## 깊이 이해
- **배경·문제의식**: 스마트폰 시대로 오면서 Wi-Fi에서 LTE로 망 전환이 빈번해졌다. TCP는 IP 주소가 바뀌면 연결이 끊어지고 재연결(3-Way Handshake + TLS Handshake)에 막대한 시간이 걸린다.
- **작동 원리**: QUIC는 커널에 박힌 TCP 대신 튜닝이 자유로운 UDP를 뼈대로 쓴다. 첫 연결 시 보안(TLS 1.3)과 연결을 동시에 맺어 1-RTT로 끝내고, 한 번 연결했던 서버는 0-RTT로 즉시 데이터를 보낸다.
- **비유**: TCP가 매번 신분증 검사하고 서류 쓰고 들어가는 은행이라면, QUIC은 한 번 등록된 지문으로 문 열면서 동시에 송금까지 요청하는 VIP 패스다.
- **구체 예시**: 유튜브 영상을 볼 때 HTTP/2는 앞부분 패킷이 유실되면 뒤 패킷이 멀쩡해도 버퍼링이 걸린다(HOL Blocking). HTTP/3는 영상 스트림, 자막 스트림을 독립 처리해 영상이 끊겨도 자막은 계속 나온다.
- **흔한 오해·주의점**: "QUIC은 UDP라서 신뢰성이 없다"는 완전한 오해다. 뼈대만 UDP를 쓸 뿐, 애플리케이션 계층(QUIC) 내부에서 TCP 수준 이상의 흐름 제어, 혼잡 제어, 재전송 로직을 독자적으로 구현한다.

## 연결 개념
- HOL Blocking (Head-of-Line Blocking) — 큐의 앞쪽 패킷이 지연되어 전체가 멈추는 현상
- TLS 1.3 — 1-RTT/0-RTT 핸드셰이크를 제공하는 최신 암호화 프로토콜
- Connection Migration — IP 변경 시에도 식별자(Connection ID)로 세션을 유지하는 기술

# 📝 【답안용】 시험 답안 템플릿

> 목적: 시험장에서 25분에 그대로 쓰는 답안 양식. 작성방식(추상표현 금지·수치·도식·문제유형 전환)을 엄격히 지킨다.
> 핵심: 이 시험은 정보를 많이 나열하는 시험이 아니라, 문제 신호어에서 출제자 의도를 읽고 핵심 논점을 선별해 쓰는 시험이다.

## 핵심 인사이트 (3줄 요약)

> 1. **본질**: TCP의 구조적 한계(HOLB, Handshake RTT)를 극복하기 위해 UDP 기반 위에 보안(TLS 1.3)과 다중화(Multiplexing)를 통합한 L4/L7 복합 프로토콜이다.
> 2. **가치**: 독립 스트림 구조로 HOL Blocking을 제거하고, Connection ID 기반 세션 유지로 망 전환(Wi-Fi ↔ LTE) 시 무중단 통신을 실현한다.
> 3. **판단 포인트**: 기존 커널/하드웨어 스택이 TCP에 최적화되어 있으므로, QUIC 도입 시 UDP 방화벽 개방 및 CPU 암복호화 오버헤드 증가를 고려해야 한다.

## 출제 의도 및 답안 포인트

| 출제 의도 | 반드시 짚을 핵심 | 감점 회피 포인트 |
|:---|:---|:---|
| TCP의 근본 한계 인식 확인 | TCP HOL Blocking 해결 원리, 0-RTT/1-RTT 연결 지연 감소 | "단순히 빠르다"로 서술, HOLB를 애플리케이션단으로 혼동 |
| 차세대 프로토콜 아키텍처 이해 | UDP 기반, 내재화된 TLS 1.3, Connection ID 식별 | QUIC을 단순 응용 계층 L7으로만 치부 (전송+보안 결합체임) |
| 모바일 환경 적용 가치 평가 | 망 전환 시 IP 무관하게 Connection Migration 지원 | 유선망 관점으로만 장점을 서술하는 한계 |

> 요약: HTTP/2의 TCP 한계를 UDP로 우회(Bypass)하여 지연과 패킷 손실 시 병목을 뚫어낸 아키텍처 혁신임을 강조한다.

## Ⅰ. 개요 및 필요성

- 정의: 구글이 제안하고 IETF(RFC 9000)에서 표준화한 UDP 기반 다중화 트랜스포트 프로토콜 및 이를 활용한 HTTP/3 규격
- 배경: HTTP/2에서 스트림 다중화를 도입했으나, 기저의 TCP 계층에서 발생하는 패킷 손실 시 전체 스트림이 지연되는 TCP HOL Blocking 한계 직면
- 필요성: 모바일 클라이언트 증가에 따른 잦은 IP 변경(네트워크 핸드오버) 무중단 지원 및 초기 연결(Handshake) 지연 RTT 획기적 단축 요구

## Ⅱ. 구조 및 구성요소

```text
[HTTP 계층 구조 비교]
HTTP/2 아키텍처             HTTP/3 아키텍처
+-----------------+       +-----------------+
|     HTTP/2      |       |     HTTP/3      |
+-----------------+       +-----------------+
|    TLS 1.2/1.3  |       |      QUIC       | (스트림 다중화, 혼잡제어, TLS 1.3 통합)
+-----------------+       +-----------------+
|       TCP       |       |       UDP       | (단순 전송)
+-----------------+       +-----------------+
```

| 구성요소 | 역할 | 특이사항 |
|:---|:---|:---|
| 통합 QUIC 계층 | 전송(혼잡제어/재전송) + 보안(TLS 1.3) + 다중화 일괄 처리 | 커널 TCP 스택 우회, 유저스페이스 구현 용이 |
| 독립 Stream | 스트림별 독립적 바이트 스트림 보장 (HOLB 해결) | 패킷 로스 발생 시 해당 스트림만 재전송 대기 |
| Connection ID | 64비트 고유 식별자로 연결 세션 관리 | 4튜플(IP, 포트) 변경 시에도 세션 유지 보장 |

> 요약: 전송, 보안, 스트림 관리 계층을 하나의 QUIC 계층으로 압축하고 기반 프로토콜을 UDP로 교체하여 의존성을 끊었다.

---

## Ⅲ. 동작원리 및 흐름도

```text
[0-RTT / 1-RTT 연결 흐름]
클라이언트 -> 최초 연결 (1-RTT) -> 서버 (전송+보안 동시 Handshake)
           |
           +-> 재방문 연결 (0-RTT) -> 서버 (이전 세션 티켓 재사용, 즉시 Data 송신)
```

| 단계 | 처리 내용 | 검증 기준 |
|:---:|:---|:---|
| 1 | Handshake 최소화 | 전송 계층 설정과 TLS 1.3 키 교환을 1-RTT에 통합 (기존 3-RTT) |
| 2 | 식별자 부여 및 전송 | Connection ID 발급, 다중 스트림 데이터 동시 송신 |
| 3 | 스트림 독립 오류 제어 | 스트림 1번 패킷 손실 시, 스트림 1만 대기, 스트림 2/3 정상 처리 |
| 4 | Connection Migration | IP/포트 변경 감지 시 Connection ID로 패킷 유효성 인증 후 재개 |

> 요약: TCP의 핸드셰이크와 TLS 핸드셰이크를 병합하여 지연을 줄이고, IP 주소가 아닌 Connection ID로 연결 무결성을 증명한다.

## Ⅳ. 특징

| 구분 | 내용 | 판단 포인트 |
|:---|:---|:---|
| HOL Blocking 해소 | 바이트 스트림 독립성 보장으로 타 스트림 영향 차단 | 손실률이 높은 무선 환경(Wi-Fi/LTE)에서 체감 속도 급증 |
| 무중단 로밍 | Connection ID로 망 전환 시 재연결 불필요 (Connection Migration) | 모바일 단말의 이동성(Mobility) 완벽 지원 |
| 커널 우회 | 유저스페이스(User Space) 레벨 업데이트 가능 | OS 커널 패치 없이 앱 업데이트만으로 프로토콜 진화 가능 |

> 요약: 높은 패킷 손실률과 잦은 네트워크 변경이라는 현대 모바일 환경의 악조건을 기술적으로 무력화하는 특성을 갖췄다.

## Ⅴ. 심화 비교 및 적용 판단

| 구분 | HTTP/2 (TCP) | HTTP/3 (QUIC) | 선택 기준 |
|:---|:---|:---|:---|
| 초기 지연 (First Visit) | 3-RTT (TCP 1 + TLS 2) | 1-RTT (전송+보안 통합) | 글로벌 글로벌 서비스의 첫 페이지 로딩 속도 |
| 다중화 병목 | TCP HOL Blocking 발생 | 스트림 독립으로 해소 | 고용량 미디어 및 잦은 패킷 로스 망 환경 |
| 보안 내재화 | TLS 별도 계층 적용 | TLS 1.3 필수 내장 | 평문 통신 허용 여부 (QUIC은 평문 통신 원천 불가) |

> 요약: 안정적인 인트라넷에서는 HTTP/2도 충분하나, 불확실성이 높은 글로벌 인터넷망과 모바일 앱에서는 HTTP/3 도입이 압도적으로 유리하다.

| 리스크 | 원인 | 대응 방안 | 확인 지표 |
|:---|:---|:---|:---|
| 방화벽 UDP 차단 | 엔터프라이즈 방화벽의 UDP 포트 443 차단 | HTTP Alt-Svc 헤더를 통한 TCP(HTTP/2) 폴백(Fallback) 구성 | UDP 443 헬스체크 성공률 |
| CPU 오버헤드 증가 | 하드웨어 오프로딩(TCP Offload) 부재 | 유저스페이스 암복호화 최적화 및 튜닝 (예: eBPF/XDP 활용) | 웹서버 CPU 사용률 < 70% |
| 보안 장비 가시성 상실 | TLS 1.3 SNI 암호화 및 헤더 비노출 | 엔드포인트 EDR 검사 혹은 프록시/WAF에서 QUIC 터미네이션 | 트래픽 복호화율 및 L7 WAF 룰 매칭율 |

> 요약: 기존 인프라 장비들이 TCP에 최적화되어 있으므로, QUIC 도입 시 UDP 방화벽 정책과 서버 CPU 부하 상승에 대한 대비가 필수적이다.

## Ⅵ. 실무 적용 및 결론

**적용 방안 3개:**
1. 대규모 CDN 및 OTT 스트리밍 적용: 모바일 환경에서 영상 스트리밍 패킷 손실 시 버퍼링을 제거하기 위해 Edge Server에 HTTP/3 적용
2. 모바일 앱 API 가속: 모바일 게임 및 앱의 API 통신 시 Wi-Fi ↔ 5G 망 전환 중에도 세션 끊김을 막기 위해 QUIC 클라이언트 라이브러리 탑재
3. HTTP Alternative Service (Alt-Svc) 폴백 구성: 기존 인프라(UDP 차단 방화벽) 호환성을 위해 브라우저에 `Alt-Svc: h3=":443"` 헤더를 전송하여 점진적 라우팅 유도

**결론 (2줄):**
- 기술사 판단: TCP의 태생적 한계를 UDP 기반 유저 레벨 제어로 돌파한 패러다임 전환이며, 글로벌 B2C 모바일 서비스라면 최우선 도입 대상이다.
- 향후 방향: 현재 웹 생태계를 넘어 IoT, 마이크로서비스 RPC 통신(gRPC over QUIC) 등 저지연과 무중단을 요구하는 전 산업 영역으로 QUIC의 적용이 확대될 것이다.
