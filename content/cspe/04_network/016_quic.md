## Ⅰ. 개요
- **정의**: UDP 위에 신뢰성·암호화·멀티플렉싱을 내장한 범용 전송 계층 프로토콜
- **배경/필요성**: TCP의 HOL Blocking과 핸드셰이크 지연이 모바일·고손실 환경에서 성능 저하를 초래하여 대안이 필요함
- **비유**: TCP가 정해진 철로 위의 기차라면, QUIC은 각 차량이 독립 경로로 이동하는 자율주행 화물차와 유사함

| 출제 의도 | 반드시 짚을 핵심 | 감점 회피 포인트 |
|:---|:---|:---|
| TCP 대비 구조적 차이와 성능 개선 원리 | 0-RTT, 독립 스트림, 내장 TLS 1.3 | QUIC은 UDP를 사용하나 자체 신뢰성 보장 — "비신뢰 프로토콜"이 아님 |

> 요약: UDP 기반으로 TCP+TLS 기능을 통합하여 저지연·무손실 멀티플렉싱을 제공하는 전송 프로토콜임

## Ⅱ. 구성요소
```text
+------------+
| HTTP/3     |  (Application)
+------------+
| QUIC       |  (Transport: 스트림 관리, 혼잡 제어, 암호화)
+------------+
| UDP        |  (Datagram)
+------------+
| IP         |  (Network)
+------------+
```

| 구성요소 | 설명 | 비유 |
|:---|:---|:---|
| Connection ID | IP 변경 시에도 연결을 유지하는 식별자 | 전화번호 대신 사용하는 개인 ID |
| Independent Stream | 스트림 간 패킷 손실이 상호 영향 없음 | 독립 차선의 화물차 |
| 내장 TLS 1.3 | 전송 계층에 암호화를 통합하여 별도 핸드셰이크 불필요 | 차량 자체에 잠금장치 내장 |
| 0-RTT Resumption | 이전 연결 정보로 왕복 없이 데이터 전송 개시 | 단골 가게에 들어서며 주문 |

> 요약: Connection ID, 독립 스트림, 내장 TLS, 0-RTT가 QUIC의 4대 핵심 요소임

## Ⅲ. 절차
```text
Client                        Server
  |--Initial(ClientHello+Data)->|   (1-RTT, 또는 0-RTT)
  |<-Initial(ServerHello)-------|
  |<-Handshake(Finished)--------|
  |--Short Header(App Data)---->|   (암호화 완료 후 데이터 전송)
  |<-Short Header(App Data)-----|
```
- 1단계: 클라이언트가 Initial 패킷으로 TLS ClientHello와 선택적 0-RTT 데이터 전송
- 2단계: 서버가 ServerHello + Handshake Finished를 반환하여 암호 파라미터 확정
- 3단계: 양측이 Short Header 패킷으로 암호화된 애플리케이션 데이터 교환
- 4단계: 연결 종료 시 CONNECTION_CLOSE 프레임으로 정상 종료 또는 타임아웃 처리

> 요약: Initial 교환-핸드셰이크 완료-암호화 데이터 전송-연결 종료의 4단계로 동작함

## Ⅳ. 문제점
- UDP 차단: 기업 방화벽이 UDP 443을 허용하지 않는 경우 연결 불가 — 기존 보안 정책이 TCP 중심으로 수립되어 있음
- 0-RTT 재전송 공격: 0-RTT 데이터는 리플레이 방어가 제한적임 — 서버 측 멱등성 미보장 시 중복 처리 위험
- CPU 오버헤드: 사용자 공간에서 구현되어 커널 TCP 대비 CPU 사용량이 높음 — 고트래픽 서버에서 자원 소모 증가

> 요약: UDP 차단, 리플레이 취약성, CPU 부하가 주요 과제임

## Ⅴ. 개선방안
1. 단기: TCP 폴백 메커니즘 구현으로 UDP 차단 환경에서도 서비스 연속성 확보
2. 중기: 0-RTT 사용 시 멱등 요청만 허용하고 서버 측 리플레이 토큰 검증 적용
3. 장기: 커널 수준 QUIC 구현(kQUIC 등) 및 하드웨어 오프로드로 CPU 부하 경감

> 요약: TCP 폴백, 리플레이 방어, 커널 구현의 단계적 성숙이 필요함

## Ⅵ. 전망
- 발전 방향: HTTP/3 외에도 DNS, MQTT 등 다양한 프로토콜이 QUIC 위로 이전되는 추세임
- 기술사적 판단: 전송 계층 혁신이 OS 커널이 아닌 사용자 공간에서 시작된 드문 사례로 프로토콜 진화 모델이 변화함
- 기술사 제언: QUIC 도입 시 기존 네트워크 모니터링·보안 장비와의 호환성을 사전 검증할 필요가 있음
