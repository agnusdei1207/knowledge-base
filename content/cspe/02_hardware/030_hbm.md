## 미리 알고가기

- TSV: 적층된 DRAM 다이를 수직으로 연결하는 관통 전극 기술임
- 인터포저: GPU, CPU, HBM 스택을 고밀도 배선으로 연결하는 패키지 기판임
- 대역폭: 단위 시간에 메모리와 프로세서 사이에서 전송할 수 있는 데이터량임
- 전력 효율: 전송한 비트당 소비 전력으로 메모리 시스템의 에너지 소비를 판단하는 기준임

## Ⅰ. 개요

- **정의**: HBM은 여러 DRAM 다이를 수직 적층하고 TSV와 인터포저로 프로세서 가까이에 넓은 I/O를 제공해 높은 메모리 대역폭과 낮은 비트당 전력으로 AI·HPC 연산의 데이터 공급 병목을 줄이는 메모리 기술임
- **배경/필요성**: GPU와 AI 가속기는 많은 연산 유닛을 병렬로 동작시키지만 외부 메모리 대역폭이 부족하면 연산기가 대기함. HBM은 클록을 무리하게 높이기보다 넓은 병렬 경로와 가까운 배치로 데이터 이동 비용을 줄임
- **비유**: 좁은 고속도로 하나를 더 빠르게 달리는 대신, 공장 바로 옆에 넓은 전용 차선을 여러 개 만든 것과 같음

| 출제 의도 | 반드시 짚을 핵심 | 감점 회피 포인트 |
|:---|:---|:---|
| AI/HPC 메모리 병목을 패키징과 대역폭 관점에서 설명하는 역량 확인 | TSV, 3D 적층, 인터포저, 넓은 I/O, 비트당 전력 | 단순 대용량 메모리로 설명, GDDR와 차이 누락, 패키징 비용 누락 |

> 요약: HBM은 넓은 병렬 I/O와 3D 적층 패키징으로 메모리 대역폭 병목을 완화하는 기술임.

## Ⅱ. 특징/비교

| 판단 기준 | GDDR 계열 | HBM |
|:---|:---|:---|
| 연결 방식 | 패키지 외부 메모리를 고속 신호로 연결 | 프로세서 인근에 적층 메모리를 넓은 I/O로 연결 |
| 대역폭 확보 | 높은 핀 속도와 보드 배선 최적화 | 낮은 핀 속도와 매우 넓은 버스 |
| 전력·면적 | 보드 면적과 신호 전력이 커질 수 있음 | 패키지 비용은 높지만 비트당 전력 유리 |
| 적용 영역 | 그래픽 카드, 범용 고성능 메모리 | AI 가속기, HPC, 고대역폭 서버 |

> 요약: HBM은 고속 신호보다 패키지 근접성과 넓은 버스로 대역폭을 확보하는 방식임.

- HBM은 메모리 채널을 많이 병렬화해 대규모 행렬 연산과 스트리밍 데이터 처리에 적합함
- 적층 구조는 용량과 대역폭을 높이지만 발열, 수율, 패키지 비용을 함께 증가시킴
- 시스템 성능은 HBM 용량 자체보다 연산기 사용률과 메모리 접근 패턴에 의해 결정됨

## Ⅲ. 구성요소

```text
+-----------+      +-----------+      +-----------+
| GPU/CPU   | <--> | Interposer| <--> | HBM Stack |
+-----------+      +-----------+      +-----------+
                                      | DRAM dies |
                                      | TSV/Base  |
                                      +-----------+
```

| 구성요소 | 설명 | 비유 |
|:---|:---|:---|
| DRAM 적층 다이 | 여러 메모리 다이를 수직으로 쌓아 용량과 병렬 채널을 확보함 | 층층이 쌓은 창고 |
| TSV | 적층 다이 사이를 수직으로 연결해 짧은 데이터 경로를 제공함 | 건물 내부 엘리베이터 |
| 베이스 다이 | HBM 스택의 인터페이스와 제어 로직을 담당하는 하단 계층임 | 물류 접수층 |
| 인터포저 | 프로세서와 HBM 스택 사이에 고밀도 배선을 제공함 | 전용 물류 허브 |

> 요약: HBM은 적층 DRAM, TSV, 베이스 다이, 인터포저가 하나의 고대역폭 패키지를 형성함.

## Ⅳ. 절차

```text
+-----------+      +-----------+      +-----------+      +-----------+
| 연산요청  | ---> | 주소분산  | ---> | 병렬전송  | ---> | 결과처리  |
+-----------+      +-----------+      +-----------+      +-----------+
```

1. **연산 요청 식별**: GPU나 가속기가 대량 행렬, 벡터, 텐서 데이터 접근을 요청함
2. **채널과 bank 분산**: 메모리 컨트롤러가 주소를 HBM 채널과 bank에 나누어 병렬성을 확보함
3. **넓은 I/O 전송**: TSV와 인터포저를 통해 다수 비트를 병렬로 주고받음
4. **연산기 공급 검증**: 연산 유닛의 stall과 HBM 대역폭 사용률을 측정해 데이터 공급을 조정함

> 요약: HBM은 대량 데이터를 여러 채널로 분산해 짧고 넓은 경로로 연산기에 공급하는 흐름으로 동작함.

## Ⅴ. 문제점

- **P1 패키징 비용과 수율**: 인터포저와 적층 공정이 복잡해 제품 비용과 제조 리스크가 커짐
- **P2 열 밀도 증가**: 프로세서와 메모리가 가까이 배치되어 발열 집중과 냉각 설계 부담이 커짐
- **P3 용량 제약**: 보드형 메모리보다 장착 가능한 스택 수와 총 용량이 제한될 수 있음

> 요약: HBM의 제약은 성능보다 패키징, 열, 용량 확장성에서 주로 발생함.

## Ⅵ. 개선방안

1. **단기**: HBM bandwidth, capacity 사용률, 온도, 연산기 stall을 동시에 측정함
2. **중기**: 메모리 접근 coalescing, tensor tiling, 냉각 설계, 패키지 검증을 워크로드에 맞게 최적화함
3. **장기**: HBM 용량형 서버와 CXL 확장 메모리의 역할 분담 기준을 수립함

- **P1 대응**: 제품 요구 대역폭과 비용을 기준으로 HBM 채택 범위를 제한함 (확인: 대역폭 대비 패키지 비용)
- **P2 대응**: 액체 냉각, 전력 제한, 열 인지 스케줄링을 적용함 (확인: hotspot 온도와 throttling)
- **P3 대응**: 데이터 압축, model partitioning, CXL 메모리 보완을 적용함 (확인: OOM 건수와 HBM hit ratio)

> 요약: HBM은 무조건 확대하기보다 대역폭 병목 워크로드에 집중 배치하고 열·용량을 함께 설계해야 함.

## Ⅶ. 전망

- **발전 방향**: AI 모델과 HPC 시뮬레이션이 커질수록 HBM은 GPU·NPU 패키지의 핵심 차별 요소로 유지될 가능성이 큼
- **기술사적 판단**: HBM은 CXL 메모리 풀링, NVLink, 고속 인터커넥트와 결합해 노드 단위 메모리 계층의 상위 대역폭 층을 담당함
- **기술사 제언**: 기술사는 HBM을 고가 부품으로만 보지 말고 데이터 이동 비용을 줄여 연산기 사용률을 높이는 아키텍처 선택으로 설명해야 함
