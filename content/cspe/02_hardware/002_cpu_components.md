# 📖 【암기용】 개념 완전 이해

> 목적: CPU 내부를 처음 봐도 ALU·CU·레지스터·버스가 각각 어떤 역할을 하고 명령어 1개가 어떻게 흘러가는지 이해하게 만든다. 시험 답안 양식이 아니라, 이해를 위한 친절한 설명이다.

## 한눈에
- **개요**: CPU는 연산을 수행하는 ALU, 흐름을 제어하는 CU, 값을 임시 저장하는 레지스터, 신호를 나르는 버스로 구성된 명령어 실행 엔진
- **왜 필요한가**: 이 네 요소의 역할을 구분해야 "명령어가 어떻게 인출되고 실행되는가"라는 CPU 내부 동작을 설명할 수 있다.
- **핵심 직관**: CU는 공장장이 작업 순서를 지시하고, ALU는 실제로 계산하는 작업자이며, 레지스터는 작업대 위 임시 부품함, 버스는 부품을 나르는 컨베이어 벨트다.

## 깊이 이해
- **배경·문제의식**: 폰 노이만 구조에서 CPU는 메모리에서 명령어를 가져와(fetch) 해석(decode)하고 실행(execute)하는 사이클을 반복하는데, 이 사이클을 수행하려면 제어 신호 생성, 연산, 임시 저장, 신호 전달이라는 4개 기능이 각각 필요하다.
- **작동 원리 — ALU(Arithmetic Logic Unit)**: 덧셈·뺄셈 같은 산술 연산과 AND·OR·시프트 같은 논리 연산을 수행하고, 연산 결과에 따라 zero flag·carry flag·overflow flag 같은 상태 플래그를 갱신한다.
- **작동 원리 — CU(Control Unit)**: 명령어 레지스터(IR)에 담긴 opcode를 해석해 ALU·레지스터·메모리로 보낼 제어 신호(read/write, ALU operation code, register select)를 생성한다.
- CU는 하드와이어드(Hardwired) 방식과 마이크로프로그램(Microprogrammed) 방식으로 나뉘는데, 하드와이어드는 고정 논리 회로로 속도가 빠르고 RISC에서 주로 쓰이며, 마이크로프로그램은 마이크로코드 ROM/SRAM에 제어 순서를 저장해 유연하고 CISC와 마이크로코드 패치(예: CPU 마이크로코드 업데이트를 통한 취약점 대응)에 활용된다.
- **작동 원리 — 레지스터**: PC(Program Counter)는 다음에 인출할 명령어 주소를 가리키고, IR(Instruction Register)은 인출된 명령어를 담으며, MAR(Memory Address Register)은 접근할 메모리 주소를, MBR/MDR(Memory Buffer/Data Register)은 메모리와 주고받을 데이터를 담는다.
- 범용 레지스터(General Purpose Register)는 연산 중간값을 저장해 메모리 접근 횟수를 줄이고, PSW/플래그 레지스터(Program Status Word)는 zero·carry·overflow·sign 같은 상태를 기록해 분기 조건 판단에 쓰인다.
- **작동 원리 — 버스**: 주소 버스(Address Bus)는 CPU가 접근할 메모리·I/O 주소를 단방향으로 전달하며 폭이 넓을수록 주소 지정 가능 공간이 늘어난다(예: 32비트 주소 버스는 4GB 주소 공간을 지정 가능).
- 데이터 버스(Data Bus)는 CPU와 메모리·I/O 사이에서 실제 값을 양방향으로 주고받으며 폭이 넓을수록 한 사이클에 옮기는 데이터양이 늘어난다(예: 64비트 데이터 버스는 한 번에 8바이트 전송).
- 제어 버스(Control Bus)는 read/write, clock, interrupt request, bus grant 같은 제어 신호를 전달해 버스 사용 시점과 방향을 조율한다.
- **비유**: CU는 작업 지시서를 읽고 순서를 외치는 반장이고, ALU는 실제로 계산기를 두드리는 작업자이며, 레지스터는 작업자 손 닿는 곳의 임시 부품함이고, 버스는 부품·완제품을 나르는 컨베이어 벨트다.
- **구체 예시**: `ADD R1, R2, R3` 명령이 들어오면 CU가 opcode를 해석해 ALU에 "덧셈"을 지시하고, R2·R3 레지스터 값이 ALU로 전달되어 연산 후 결과가 R1에 저장되며 이 과정에서 데이터는 내부 버스를 통해 이동한다.
- **흔한 오해·주의점**: "레지스터가 많으면 무조건 빠르다"는 성립하지 않는다. 레지스터 수가 늘어도 컴파일러의 레지스터 할당(register allocation) 효율과 명령어 인코딩 비트 폭이 뒷받침되지 않으면 이득이 제한된다.
- 버스 폭을 넓히면 한 번에 전송하는 데이터량은 늘지만 배선·핀 수·소비 전력이 함께 증가하므로 폭 확장이 항상 성능 개선으로 직결되지는 않는다.

## 연결 개념
- 폰 노이만 vs 하버드 아키텍처 — 버스·메모리 배치 구조의 상위 분류
- 명령어 집합 RISC vs CISC — CU 설계 방식(하드와이어드/마이크로프로그램)과 직결
- 파이프라이닝 — 레지스터(파이프라인 레지스터)로 단계 간 결과를 전달하는 응용
- 버스 중재 방식 — 다중 장치가 버스를 공유할 때의 조율 메커니즘

# 📝 【답안용】 시험 답안 템플릿

> 목적: 시험장에서 25분에 그대로 쓰는 답안 양식. 작성방식(추상표현 금지·수치·도식·문제유형 전환)을 엄격히 지킨다.
> 핵심: 네 구성요소를 나열하는 답안이 아니라, 명령어 사이클에서 각 요소가 담당하는 역할과 상호작용을 근거로 제시한다.

## 핵심 인사이트 (3줄 요약)

> 1. **본질**: CPU는 연산 담당 ALU, 흐름 제어 담당 CU, 임시 저장 담당 레지스터, 신호 전달 담당 버스(주소·데이터·제어)로 구성된 명령어 실행 장치다.
> 2. **가치**: 각 요소가 역할을 분담해 fetch-decode-execute 사이클을 클럭 단위로 반복 수행하며 명령어 처리량을 결정한다.
> 3. **판단 포인트**: CU 설계는 하드와이어드(속도)와 마이크로프로그램(유연성) 중 워크로드와 패치 요구에 따라 선택하고, 버스 폭은 성능과 배선·전력 비용을 함께 검토한다.

## 출제 의도 및 답안 포인트

| 출제 의도 | 반드시 짚을 핵심 | 감점 회피 포인트 |
|:---|:---|:---|
| CPU 내부 구조 이해 확인 | ALU·CU·레지스터·버스의 개별 역할과 연결 관계 | 구성요소 이름만 나열하고 상호작용 누락 |
| CU 설계 방식 판단 확인 | 하드와이어드 vs 마이크로프로그램 방식 차이 | RISC/CISC와의 연결 근거 없이 방식만 언급 |
| 버스 설계 트레이드오프 인식 확인 | 주소·데이터·제어 버스 폭과 성능·비용 관계 | "버스가 넓으면 무조건 빠르다"는 절대화된 서술 |

> 요약: 이 문제는 구성요소 나열이 아니라 명령어 사이클에서 각 요소가 맡는 역할과 설계 트레이드오프를 보여야 한다.

## Ⅰ. 개요 및 필요성

- 개요: CPU 내부에서 연산·제어·저장·전달을 각각 담당하는 ALU·CU·레지스터·버스 네 구성요소
- 배경: 폰 노이만 구조의 fetch-decode-execute 사이클을 수행하려면 제어 신호 생성, 연산, 임시 저장, 신호 전달 기능이 각각 필요
- 필요성: 네 요소의 역할과 상호작용을 이해해야 CPU 성능 병목(레지스터 부족, 버스 대역폭 제한, CU 지연)의 원인을 진단할 수 있음

---

## Ⅱ. 구조 및 구성요소

```text
Memory <-> Address Bus/Data Bus/Control Bus <-> CPU
CPU 내부:
  PC -> IR(명령어 보관) -> CU(제어신호 생성)
  CU -> ALU(연산 수행) <-> General Purpose Register
  CU -> MAR/MBR <-> 외부 버스
```

| 구성요소 | 역할 | 특이사항 |
|:---|:---|:---|
| ALU | 산술·논리 연산 수행, 플래그(zero/carry/overflow) 갱신 | 연산기 폭(예: 64비트)이 처리 단위 결정 |
| CU | opcode 해석 및 제어 신호 생성 | 하드와이어드(고속) vs 마이크로프로그램(유연) |
| 레지스터 | PC·IR·MAR·MBR·범용 레지스터·PSW로 값 임시 저장 | 레지스터 수·폭이 컴파일러 최적화 여지 결정 |
| 버스 | 주소(단방향)·데이터(양방향)·제어(신호) 전달 | 버스 폭 확장 시 배선·전력 비용 증가 |

> 요약: CU가 명령어를 해석해 ALU와 레지스터에 지시하고, 버스가 CPU와 메모리 사이 신호·데이터를 나른다.

---

## Ⅲ. 동작원리 및 흐름도

```text
PC -> Memory Fetch(주소버스로 주소 전달) -> IR 적재
  -> CU가 opcode 디코드 -> 제어신호 생성
  -> ALU 연산(레지스터 값 입력) -> 결과 레지스터 저장
  -> 필요 시 MAR/MBR 통해 메모리 접근 -> PC 갱신
```

| 단계 | 처리 내용 | 검증 기준 |
|:---:|:---|:---|
| 1 | PC가 가리키는 주소로 명령어 인출 | 주소버스 정합성 |
| 2 | CU가 IR의 opcode를 디코드 | 제어신호 정확성 |
| 3 | ALU가 레지스터 값으로 연산 수행 | 플래그 갱신 여부 |
| 4 | 결과를 레지스터 또는 메모리에 저장 | 데이터버스 전송 정합성 |

> 요약: 명령어는 인출-디코드-연산-저장 순서로 흐르며 각 단계에서 서로 다른 CPU 구성요소가 관여한다.

---

## Ⅳ. 특징

| 구분 | 하드와이어드 CU | 마이크로프로그램 CU | 수치·표준 포인트 |
|:---|:---|:---|:---|
| 속도 | 고정 논리 회로로 지연 적음 | 마이크로코드 인출 단계 추가로 지연 존재 | RISC 계열이 하드와이어드 선호 |
| 유연성 | 설계 변경 시 회로 재설계 필요 | 마이크로코드 갱신으로 패치 가능 | CISC·마이크로코드 업데이트 사례 |
| 복잡도 | 단순 명령어 집합에 적합 | 복잡한 명령어·다양한 주소지정 방식 지원 | 명령어당 마이크로 오퍼레이션 수 |

> 요약: 하드와이어드는 속도, 마이크로프로그램은 유연성과 패치 가능성이 강점이다.

## Ⅴ. 심화 비교 및 적용 판단

| 비교 축 | 하드와이어드/좁은 버스 | 마이크로프로그램/넓은 버스 | 선택 기준 |
|:---|:---|:---|:---|
| 구조 | 고정 회로, 좁은 데이터버스 | 마이크로코드 ROM, 넓은 데이터버스 | 명령어 집합 복잡도로 CU 방식 결정 |
| 비용/성능 | 회로 단순, 대역폭 제한 | 유연성 높으나 면적·전력 증가 | 처리량 목표(IPC)와 배선 비용 비교 |
| 운영/위험 | 설계 변경 어려움 | 마이크로코드 취약점 패치 가능 | 보안 패치 요구 시 마이크로프로그램 유리 |

> 요약: 고정 명령어·고속 처리는 하드와이어드, 복잡 명령어·패치 유연성은 마이크로프로그램을 선택한다.

| 리스크 | 원인 | 대응 방안 | 확인 지표 |
|:---|:---|:---|:---|
| 레지스터 부족 | 범용 레지스터 수 제한으로 메모리 재접근 증가 | 컴파일러 레지스터 할당 최적화 | 메모리 접근 대비 레지스터 재사용률 |
| 버스 대역폭 병목 | 데이터버스 폭 대비 전송 요구량 초과 | 버스 폭 확장 또는 캐시로 접근 빈도 감소 | 버스 이용률, 대기 사이클 수 |
| 마이크로코드 취약점 | 제어 로직 결함으로 사이드채널 노출(예: Meltdown류) | 마이크로코드 패치, 펌웨어 업데이트 | CVE 대응 완료율 |

> 요약: CPU 구성요소 리스크는 레지스터 재사용률, 버스 이용률, 마이크로코드 패치 이행률로 통제한다.

| 점검 항목 | 목표 기준 | 측정 방법 |
|:---|:---|:---|
| 연산 처리량 | ALU 이용률과 목표 IPC 근접 여부 | 성능 카운터, 시뮬레이터 |
| 버스 대역폭 | 데이터버스 이용률 70% 이하 유지 | 버스 트레이스 분석 |
| 제어 신뢰성 | 마이크로코드/하드와이어드 오류 0건 | RTL 시뮬레이션, 검증 테스트 |

> 요약: 도입 효과는 ALU 이용률, 버스 이용률, 제어 신뢰성 지표로 판단한다.

## Ⅵ. 실무 적용 및 결론

**적용 방안 3개 (필수 — 단계별 또는 항목별):**
1. 고정된 명령어 집합과 고속 처리가 필요한 RISC 코어는 하드와이어드 CU를 적용해 디코드 지연을 최소화함
2. 복잡한 명령어·다양한 주소지정 방식을 지원해야 하는 CISC 계열은 마이크로프로그램 CU로 유연성과 패치 가능성을 확보함
3. 버스 병목이 확인되면 데이터버스 폭 확장보다 캐시 계층 추가로 메모리 접근 빈도를 먼저 낮추고, 그래도 부족하면 버스 폭 확장을 검토함

**결론 (2줄):**
- 기술사 판단: CU 방식은 명령어 집합 복잡도로, 버스 설계는 대역폭 요구와 배선·전력 비용을 함께 검토해 결정함
- 향후 방향: 마이크로코드 기반 취약점 대응 사례가 늘면서 CU 유연성과 보안 패치 체계를 함께 설계하는 방향으로 발전하고 있음
