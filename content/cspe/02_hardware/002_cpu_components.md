# 📖 【암기용】 개념 완전 이해

> 목적: CPU를 구성하는 4대 요소의 역할과 상호작용, 그리고 실제 클럭 단위로 무슨 일이 일어나는지 처음 봐도 완벽히 이해하게 만든다.

## 한눈에
- **개요**: **중앙처리장치(CPU)**는 **제어장치(CU)·연산장치(ALU)·레지스터·버스**의 4대 요소가 **명령어 사이클(Instruction Cycle, Fetch-Decode-Execute)**을 클럭마다 반복하며 프로그램을 실행하는 핵심 하드웨어다.
- **왜 필요한가**: 컴퓨터가 소프트웨어를 실행하려면 '지시를 내리는 곳(CU)', '계산하는 곳(ALU)', '잠깐 기억하는 곳(Register)', '데이터를 나르는 길(Bus)'이 클럭 단위로 정확히 분업해야 한다.
- **핵심 직관**: CPU는 거대한 공장이다. CU는 작업 반장, 레지스터는 작업대, ALU는 조립 기계, 버스는 컨베이어 벨트다.

## 핵심 용어 정리

| 용어 | 의미 | 비유 |
|:---|:---|:---|
| 중앙처리장치(CPU) | 명령어를 해석하고 연산을 수행하는 컴퓨터의 두뇌 — 아래 4요소로 구성됨 | 공장 전체 |
| 명령어 사이클(Instruction Cycle) | Fetch(인출)-Decode(해독)-Execute(실행)-Store(저장)를 반복하는 CPU의 기본 동작 단위 | 공장의 반복 생산 공정 1회전 |
| 제어장치(CU, Control Unit) | 명령어를 해석하고 각 장치에 전기적 제어 신호를 보내는 지휘 회로 | 작업 반장 |
| 연산장치(ALU, Arithmetic Logic Unit) | 산술(+,-) 연산과 논리(AND,OR,Shift) 연산을 수행하는 회로 | 조립 기계 |
| 레지스터(Register) | CPU 내부에서 가장 빠른 임시 저장 공간 | 작업대 |
| 버스(Bus) | 장치 간 데이터·주소·제어 신호를 나르는 통로 | 컨베이어 벨트 |
| PC(Program Counter) | 다음에 실행할 명령어의 주소를 담는 레지스터 | 다음 작업 지시서 번호표 |
| IR(Instruction Register) | 방금 인출한 명령어를 담아 해독을 기다리는 레지스터 | 지금 읽고 있는 지시서 |
| MAR/MBR(Memory Address/Buffer Register) | 메모리에 보낼 주소 / 메모리에서 받거나 보낼 데이터를 담는 버퍼 | 창고 요청서 / 받은 물건 |
| AC(Accumulator, 누산기) | ALU의 입력값과 연산 결과를 담아두는 레지스터 | 계산 중인 메모장 |

## 깊이 이해

### 명령어 사이클을 클럭(마이크로 오퍼레이션) 단위로 뜯어보기
- CPU가 `ADD R1, R2, R3`(R2+R3를 R1에 저장) 같은 명령어 1개를 처리할 때, 실제로는 여러 클럭에 걸쳐 아래처럼 잘게 쪼갠 마이크로 오퍼레이션이 순서대로 실행된다.
- t0: `MAR ← PC` (다음 명령어 주소를 메모리 요청 레지스터로) → t1: `MBR ← M[MAR], PC ← PC+4` (메모리에서 명령어를 읽고 PC를 다음으로 이동) → t2: `IR ← MBR` (읽은 명령어를 명령어 레지스터에 적재, 여기까지가 Fetch) → t3: CU가 IR을 해독해 ALU에 "덧셈" 제어 신호 발생(Decode) → t4: `AC ← R2 + R3`(ALU 연산, Execute) → t5: `R1 ← AC`(결과 저장, Store).
- 이렇게 한 명령어가 여러 클럭(t0~t5, 총 6클럭)을 쓰는 방식을 다중 사이클(Multi-cycle) CPU라 한다. 파이프라이닝은 이 단계들을 겹쳐 실행해(예: 이번 명령어가 t3일 때 다음 명령어가 t0) 평균 처리 클럭을 1에 근접시킨다(정량 비교는 `001_von_neumann_vs_harvard.md` 참조).

### 레지스터 폭과 ALU 연산 단위 — 32비트 vs 64비트
- x86-64 CPU는 64비트 레지스터 RAX를 기본으로 하되, 하위 32비트를 EAX, 하위 16비트를 AX, 하위 8비트를 AL이라는 별도 이름(별칭)으로도 접근한다 — 레지스터 폭이 처리 가능한 최대 정수 크기(64비트=약 1.8×10¹⁹)와 한 번에 옮길 수 있는 데이터 양을 결정한다.
- ALU가 64비트 덧셈을 리플 캐리(Ripple Carry) 방식으로 하면, 최하위 비트의 캐리가 그 위 비트 계산을 순차적으로 기다려야 해 비트 수(64)에 비례해 지연이 누적된다. 그래서 실제 고속 ALU는 캐리를 미리 병렬로 계산하는 캐리 선견 가산기(Carry Look-ahead Adder)를 써서 이 지연을 크게 줄인다.

### AC(누산기)가 폰 노이만 병목을 줄이는 이유
- 레지스터가 없다면 `A = A + B`를 계산할 때마다 메모리에서 A를 읽고, B를 읽고, 결과를 다시 메모리에 쓰는 3번의 메모리 접근이 필요하다.
- AC 같은 레지스터에 중간값을 담아두면, 연속된 연산(예: `AC = AC + B1`, `AC = AC + B2`, ...)에서 매번 메모리를 왕복하지 않고 레지스터만 갱신하면 되므로 버스 접근 횟수가 크게 줄어든다 — 이는 001에서 다루는 폰 노이만 병목(단일 버스 공유로 인한 성능 상한)을 완화하는 실질적 수단이다.

### 비유로 정리
- 반장(CU)이 창고(메모리)에서 레시피(명령어)를 가져와 해석한다. 요리사(ALU)에게 도마(레지스터) 위의 재료를 썰라고 지시한다. 썰린 고기(연산 결과)는 벨트(버스)를 타고 다시 창고나 다음 작업대로 간다.

# 📝 【답안용】 시험 답안 템플릿

> 목적: 시험장에서 25분에 그대로 쓰는 답안 양식. 

## 핵심 인사이트 (3줄 요약)

> 1. **본질**: CPU는 제어장치(CU), 연산장치(ALU), 기억장치(Register), 통로(Bus)로 구성된 폰 노이만 아키텍처의 물리적 실행 엔진이다.
> 2. **가치**: 4대 요소가 클럭(Clock) 주기에 맞춰 동기화되며 명령어 사이클(Fetch-Decode-Execute)을 유기적으로 수행한다.
> 3. **판단 포인트**: 현대 CPU의 성능 병목은 ALU의 연산 속도보다 버스 대역폭과 레지스터 용량에서 발생하므로(메모리 벽), L1/L2 캐시 및 다중 버스 설계가 필수적이다.

## 출제 의도 및 답안 포인트
| 출제 의도 | 반드시 짚을 핵심 | 감점 회피 포인트 |
|:---|:---|:---|
| 폰 노이만 기반 컴퓨터 하드웨어의 동작 원리 확인 | CU/ALU 분리, PC/IR/AC 레지스터, 내부/외부 버스 | 4가지 구성요소를 단순 나열만 하고 이들의 상호작용 흐름(명령어 사이클)을 누락 |

> 요약: 각 장치의 정적 구조뿐만 아니라 명령어가 실행되는 동적 제어 흐름(Fetch-Execute)을 서술해야 한다.


## Ⅰ. 개요 및 필요성

- 정의: 메모리의 명령어를 해독하고 데이터를 연산하여 실행하는 4대 중앙처리 유닛
- 배경: 내장형 프로그램(Stored-Program)을 순차적으로 실행하기 위한 논리적·물리적 하드웨어 분업 필요
- 필요성: 클럭 단위의 정밀한 상태 제어(CU)와 고속 데이터 처리(ALU)를 분리하여 처리량(Throughput) 극대화


## Ⅱ. 구조 및 구성요소
```text
[CPU 내부 구조도]
제어장치(CU) <=====> 내부 버스 (데이터/주소/제어)
  |                    |
레지스터(Register) <======> 연산장치(ALU) <== 외부 버스 ==> 메인 메모리
```

| 구성요소 | 핵심 역할 | 세부 하위 요소 |
|:---|:---|:---|
| 제어장치 (CU) | 명령어 해독 및 각 장치 구동용 제어 신호 발생 | 명령어 해독기(Decoder), 제어 신호 발생기 |
| 연산장치 (ALU) | 산술(+, -) 연산 및 논리(AND, OR, Shift) 연산 수행 | 가산기(Adder), 상태 레지스터(Status Flag) |
| 레지스터 (Register) | 명령어·데이터·메모리 주소의 임시 초고속 저장 | PC, IR, MAR, MBR, AC (누산기) |
| 내부 버스 (Bus) | CPU 내부 장치 간 전기적 신호 및 데이터 전달 경로 | 데이터 버스, 주소 버스, 제어 버스 |

> 요약: CU의 제어 신호에 따라 레지스터의 데이터가 내부 버스를 타고 ALU로 이동하여 연산된다.


## Ⅲ. 동작원리 및 흐름도
```text
[명령어 사이클 처리 흐름: Fetch -> Decode -> Execute -> Store]
PC 주소 확인 -> MAR 전달 -> 메모리 명령어 Fetch -> MBR -> IR 저장
-> CU 디코드 -> 제어 신호 발생 -> ALU가 레지스터 데이터 연산 -> 결과 AC 저장
```

| 단계 | 사이클 | 주체 | 처리 내용 (마이크로 오퍼레이션) |
|:---:|:---|:---|:---|
| 1 | 인출 (Fetch) | CU, Register | PC가 가리키는 주소의 명령어를 IR(명령어 레지스터)로 적재 |
| 2 | 해독 (Decode) | CU | IR의 명령어를 해독하여 필요한 연산 및 데이터 이동 제어 신호 생성 |
| 3 | 실행 (Execute) | ALU | 제어 신호에 따라 레지스터 데이터를 가산기 등에서 연산 |
| 4 | 저장 (Store) | Register, Bus | ALU 연산 결과를 누산기(AC)나 메모리에 기록 및 상태 플래그 갱신 |

> 요약: 4대 요소는 독립적으로 동작하지 않고 Fetch-Decode-Execute 사이클이라는 하나의 흐름으로 동기화된다.


## Ⅳ. 주요 레지스터 구성 및 특징

| 구분 | 레지스터 | 역할 및 판단 포인트 |
|:---|:---|:---|
| 제어용 | PC (Program Counter) | 다음에 실행할 명령어의 번지(주소)를 보관하여 순차/분기 흐름 제어 |
| 제어용 | IR (Instruction Reg) | 현재 메모리에서 인출되어 해독(Decode) 대기 중인 명령어 보관 |
| 버퍼용 | MAR (Memory Address Reg) | 메모리 읽기/쓰기 시 참조할 물리 주소를 임시 저장 |
| 버퍼용 | MBR (Memory Buffer Reg) | 메모리에서 읽거나 메모리에 쓸 실제 데이터를 임시 저장 |
| 연산용 | AC (Accumulator, 누산기) | ALU의 연산 입력값 및 연산 결과값을 저장하여 메모리 접근 횟수 최소화 |

> 요약: 특수 목적 레지스터는 메모리와 ALU 사이의 지연(Latency)을 숨기고 파이프라인 병목을 줄이는 핵심 버퍼다.

## Ⅴ. 심화 비교 및 성능 병목 판단

| 병목 축 | 기존 구조의 한계 (병목) | 현대 CPU의 대응 아키텍처 | 적용 기준 |
|:---|:---|:---|:---|
| ALU 지연 | 단일 ALU로 인한 복잡한 부동소수점 연산 병목 | FPU(부동소수점), SIMD(벡터 연산기) 물리적 분리 및 다중화 | 고성능 멀티미디어, AI 워크로드 |
| 버스 대역폭 | 폰 노이만 단일 버스로 인한 IF/MEM 단계 충돌 | 하버드 구조(I-Cache/D-Cache) 분리 및 64bit 버스폭 확장 | 다중 데이터 동시 처리 필요 시 |
| 레지스터 용량 | 제한된 레지스터로 인한 Memory Wall(접근 지연) 현상 | 범용 레지스터 리네이밍(Renaming), L1/L2/L3 계층 캐시 | 데이터 의존성(RAW) 및 스톨 감소 |

> 요약: 고클럭 환경에서는 ALU 속도보다 버스 대역폭과 레지스터/캐시 아키텍처가 실제 명령어 처리량(IPC)을 결정한다.


## Ⅵ. 실무 적용 및 결론

**적용 방안 3개:**
1. SIMD 확장 적용: 벡터 레지스터와 전용 ALU 세트(AVX-512 등)를 확장하여 한 번의 인출로 대량의 데이터 배열을 병렬 처리
2. 하드웨어 멀티스레딩(SMT): 코어 내에 PC와 범용 레지스터 세트를 2개 이상 복제하여 특정 스레드 스톨 시 문맥 교환 없이 즉시 실행 전환
3. 분리형 버스 설계: L1 캐시 영역에 한해 명령어 버스와 데이터 버스를 분리하는 수정된 하버드 아키텍처를 도입하여 구조적 해저드 원천 차단

**결론 (2줄):**
- 기술사 판단: CPU 4대 요소의 발전 방향은 연산기 성능 향상에 그치지 않고, 다중 코어 간 버스 경합을 줄이기 위한 캐시 일관성과 레지스터 자원 확장에 집중된다.
- 향후 방향: 최근 대용량 AI 워크로드 처리 한계(폰 노이만 병목)를 넘기 위해 연산 장치(ALU)를 메모리 내부로 옮긴 PIM(Processing in Memory) 아키텍처로 진화하고 있다.
