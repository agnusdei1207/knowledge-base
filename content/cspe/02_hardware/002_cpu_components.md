## Ⅰ. 개요
- **정의**: 산술논리연산·제어·임시 저장·데이터 전송을 담당하는 CPU 내부 핵심 구성 단위
- **배경/필요성**: 프로그램 명령어를 인출·해석·실행하려면 연산기·제어기·레지스터·버스가 유기적으로 협력해야 함
- **비유**: ALU는 계산원, CU는 지시를 내리는 관리자, 레지스터는 계산원 앞 메모판, 버스는 부서 간 연결 복도

| 출제 의도 | 반드시 짚을 핵심 | 감점 회피 포인트 |
|:---|:---|:---|
| CPU 내부 구성요소의 역할과 상호작용 이해 | 명령어 사이클(Fetch-Decode-Execute) 흐름에서 각 구성요소의 역할 | 레지스터 종류(PC, IR, MAR, MBR, ACC)를 혼동하면 감점 |

> 요약: CPU는 ALU·CU·레지스터·버스의 협동으로 명령어 사이클을 수행하는 처리 장치임

## Ⅱ. 구성요소
```text
+-----------------------------------------------+
|                    CPU                         |
|   CU(제어장치) ----제어신호---->  ALU(연산장치) |
|       |                           |            |
|       v                           v            |
|   IR, PC, MAR          ACC, MBR, 범용 레지스터 |
+-----------------------------------------------+
        |           |           |
   주소 버스    데이터 버스   제어 버스
        |           |           |
      [      메모리 / I/O       ]
```

| 구성요소 | 설명 | 비유 |
|:---|:---|:---|
| ALU | 산술(+, -, *, /) 및 논리(AND, OR, NOT) 연산 수행 | 계산기를 두드리는 계산원 |
| CU | 명령어를 해석하여 ALU·레지스터·버스에 제어 신호를 발생 | 작업 순서를 지시하는 관리자 |
| PC(Program Counter) | 다음에 인출할 명령어의 메모리 주소를 보관 | 책갈피 — 읽을 페이지 번호 |
| IR(Instruction Register) | 현재 실행 중인 명령어를 저장 | 지금 읽고 있는 문장 |
| MAR/MBR | 메모리 주소/데이터를 임시 보관하는 버퍼 레지스터 | 택배 송장(MAR)과 택배 상자(MBR) |
| 범용 레지스터 | 연산 중간 결과나 피연산자를 임시 저장 | 계산 중 적어두는 메모지 |
| 버스(주소/데이터/제어) | CPU-메모리-I/O 간 신호 전달 경로 | 부서를 잇는 복도 — 폭이 대역폭 |

> 요약: CU가 제어 흐름을 관장하고, ALU가 연산을 수행하며, 레지스터와 버스가 데이터를 중계함

## Ⅲ. 절차
```text
[Fetch] --> [Decode] --> [Execute] --> [Writeback]
  PC->MAR    IR->CU      CU->ALU      ALU->레지스터
  메모리->MBR->IR        제어신호발생   결과->메모리
```
- 1단계: **Fetch** — PC 값을 MAR에 전달하고, 해당 주소의 명령어를 MBR을 거쳐 IR에 적재. PC는 다음 주소로 증가
- 2단계: **Decode** — CU가 IR의 명령어를 해석하여 연산 종류·오퍼랜드·주소 지정 방식을 결정
- 3단계: **Execute** — CU의 제어 신호에 따라 ALU가 연산을 수행하거나, 메모리/I/O 접근을 실행
- 4단계: **Writeback** — 연산 결과를 목적 레지스터 또는 메모리에 저장하고, 다음 Fetch 단계로 복귀

> 요약: Fetch→Decode→Execute→Writeback 사이클이 반복되며 프로그램이 순차 실행됨

## Ⅳ. 문제점
- **단일 사이클 처리 지연**: 한 명령어가 4단계를 모두 끝내야 다음 명령어 시작 — 파이프라인 미적용 시 CPI가 높아짐
- **레지스터 수 제한**: 범용 레지스터가 부족하면 메모리 접근 빈도 증가 — 버스 경합과 대기 시간이 늘어남
- **버스 대역폭 병목**: CPU 클록이 높아져도 외부 버스 속도가 따라가지 못함 — CPU-메모리 간 성능 격차 확대(001 참조)

> 요약: 사이클 직렬 처리, 레지스터 부족, 버스 대역폭 한계가 CPU 성능 향상의 주요 제약임

## Ⅴ. 개선방안
1. **단기**: 파이프라인 도입 — 명령어 단계를 중첩 실행하여 평균 CPI를 1에 근접시킴
2. **중기**: 레지스터 파일 확장 및 레지스터 리네이밍 — 데이터 의존성을 완화하고 메모리 접근을 줄임
3. **장기**: 캐시 계층 확대 및 NoC(Network-on-Chip) — 다코어 간 대역폭을 분산시켜 버스 병목을 해소

> 요약: 파이프라인·레지스터 확장·캐시/NoC로 사이클·레지스터·버스 각각의 병목을 순차 완화함

## Ⅵ. 전망
- **발전 방향**: 칩릿(Chiplet) 기반 이기종 통합으로 CPU·GPU·NPU가 하나의 패키지에서 협동하는 구조로 진화
- **기술사적 판단**: CPU 내부 구성요소 이해는 파이프라인·캐시·분기예측 등 상위 주제의 선행 지식에 해당함
- **기술사 제언**: 명령어 사이클의 각 단계에서 관여하는 레지스터와 제어 신호를 정확히 매핑할 수 있어야 함
