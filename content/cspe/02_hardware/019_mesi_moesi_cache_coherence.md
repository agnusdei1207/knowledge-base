# 📖 【암기용】 개념 완전 이해

> 목적: MESI·MOESI를 처음 봐도 여러 코어의 캐시가 같은 메모리 주소를 두고 서로 다른 값을 보지 않도록 어떻게 상태를 맞추는지 이해하게 만든다. 시험 답안 양식이 아니라, 이해를 위한 친절한 설명이다.

## 한눈에
- **개요**: 여러 코어의 사적 캐시가 같은 메모리 블록의 복사본을 가질 때, 그 복사본들이 서로 모순되지 않도록 상태를 관리하는 프로토콜
- **왜 필요한가**: 멀티코어에서 한 코어가 캐시에만 값을 갱신(Write-Back)하면 다른 코어가 그 메모리 주소를 읽을 때 옛날 값을 볼 수 있으므로, 이를 막을 상태 관리 규칙이 필요하다
- **핵심 직관**: 여러 사람이 같은 문서의 사본을 각자 들고 있을 때, 한 명이 자기 사본을 고치면 나머지 사본은 "무효" 표시를 하거나 새 내용을 받아야 서로 다른 버전을 보지 않는 것과 같다

## 깊이 이해
- **배경·문제의식**: Write-Back 캐시는 최신 값이 메인 메모리가 아니라 특정 코어의 캐시에만 있을 수 있으므로, 다른 코어가 같은 주소를 캐시에 갖고 있다면 그 상태를 알려주고 동기화해야 한다.
- **작동 원리 - MESI 4상태**: Modified(M, 수정됨·자신만 보유·메모리는 구버전), Exclusive(E, 자신만 보유·깨끗함·메모리와 일치), Shared(S, 여러 캐시가 보유 가능·깨끗함·메모리와 일치), Invalid(I, 유효하지 않음) 네 상태로 구성된다.
- **작동 원리 - 읽기 미스**: 다른 캐시에 사본이 없으면 새로 읽은 라인은 Exclusive로, 다른 캐시가 이미 갖고 있으면(E 또는 S) 그 라인은 Shared로 전이하고 기존 보유 캐시도 Shared로 전이한다.
- **작동 원리 - 쓰기**: Exclusive 상태에서 쓰기는 버스 트랜잭션 없이 바로 Modified로 전이하지만, Shared 상태에서 쓰기는 다른 캐시의 사본을 무효화하는 버스 트랜잭션(BusUpgr/BusRdX 계열)을 발생시킨 뒤 Modified로 전이한다.
- **작동 원리 - 다른 코어의 요청 스누핑**: 다른 코어가 자신이 Modified로 갖고 있는 라인을 읽으려 하면(BusRd 관측), 해당 캐시는 최신 값을 공급(메모리 라이트백 또는 캐시 간 전달)하고 자신은 Shared로 전이한다.
- **작동 원리 - MOESI의 Owned 상태**: MOESI는 MESI에 Owned(O) 상태를 추가해, 한 캐시가 수정된 데이터를 메모리에 즉시 반영하지 않고도 다른 캐시들과 공유할 수 있게 한다. Owned 캐시는 유일하게 최신(dirty) 값을 갖고 그 값을 캐시 간 직접 전달로 공급하며, 나머지 공유 캐시들은 Shared로 표시되고 메모리는 여전히 구버전을 유지한다.
- **작동 원리 - MOESI 도입 효과**: MOESI는 M 상태 라인을 다른 코어가 읽을 때 즉시 메모리에 라이트백하지 않고 Owned로 전이해 캐시 간 전달만으로 처리하므로, MESI 대비 불필요한 메모리 쓰기 트래픽을 줄일 수 있다.
- **비유**: MESI에서 수정본을 가진 사람이 남에게 보여주려면 일단 원본(메모리)부터 최신화해야 하지만, MOESI에서는 수정본을 가진 사람이 원본 갱신 없이 자기 사본을 직접 복사해 건네고 "내가 최신본 주인"이라는 표시(Owned)만 남긴다.
- **흔한 오해·주의점**: MESI와 MOESI를 같은 프로토콜의 다른 이름으로 혼동하면 안 된다. MOESI는 MESI에 Owned 상태를 추가로 도입해 dirty 공유(memory에 즉시 쓰지 않는 공유) 상태를 표현할 수 있다는 점이 핵심 차이다.
- **흔한 오해·주의점**: Exclusive 상태는 "값이 수정됨"을 뜻하지 않는다. Exclusive는 자신만 보유하지만 메모리와 값이 같은(clean) 상태이고, 수정이 일어나야 비로소 Modified로 바뀐다.

## 연결 개념
- 버스 스누핑·디렉터리 기반 일관성 — MESI·MOESI 상태 전이를 전달하는 두 가지 하드웨어 구현 방식
- 캐시 쓰기 정책(Write-Through·Write-Back) — Write-Back 캐시에서 Modified/Owned 상태가 발생하는 근본 원인
- 멀티코어 프로세서 — 사적 캐시 간 일관성 프로토콜이 반드시 필요한 이유

# 📝 【답안용】 시험 답안 템플릿

> 목적: 시험장에서 25분에 그대로 쓰는 답안 양식. 작성방식(추상표현 금지·수치·도식·문제유형 전환)을 엄격히 지킨다.
> 핵심: MESI 4상태 전이 규칙, MOESI의 Owned 상태 추가 이유와 메모리 쓰기 트래픽 절감 효과, 두 프로토콜을 혼동하지 않는 비교를 함께 제시한다.

## 핵심 인사이트 (3줄 요약)

> 1. **본질**: MESI는 Modified·Exclusive·Shared·Invalid 4상태로 캐시 라인의 소유·공유·유효 여부를 관리하는 캐시 일관성 프로토콜이다.
> 2. **가치**: 상태 전이 규칙에 따라 다른 코어의 읽기·쓰기 요청 시 자동으로 무효화·공급이 이뤄져 코어 간 데이터 정합성을 보장한다.
> 3. **판단 포인트**: MOESI는 MESI에 Owned 상태를 추가해 dirty 데이터를 메모리에 즉시 쓰지 않고도 캐시 간 공유할 수 있게 해 메모리 쓰기 트래픽을 줄인다.

## 출제 의도 및 답안 포인트

| 출제 의도 | 반드시 짚을 핵심 | 감점 회피 포인트 |
|:---|:---|:---|
| MESI 상태 전이 이해 확인 | M/E/S/I 각 상태 정의와 읽기·쓰기·스누핑에 따른 전이 규칙 | 상태 이름만 나열하고 전이 조건 누락 |
| MOESI 차별점 이해 확인 | Owned 상태가 메모리 즉시 갱신 없이 dirty 공유를 가능하게 함 | MESI와 MOESI를 동일 프로토콜로 서술 |
| 트래픽 절감 효과 이해 확인 | M 상태 라인을 다른 코어가 읽을 때 MESI는 메모리 반영, MOESI는 캐시 간 전달 | 두 프로토콜의 메모리 쓰기 트래픽 차이를 언급하지 않음 |

> 요약: 이 문제는 상태 이름 암기가 아니라 전이 조건과 MESI-MOESI의 메모리 갱신 시점 차이를 근거로 답안을 구성해야 한다.

## Ⅰ. 개요 및 필요성

- 정의: 여러 코어의 사적 캐시가 보유한 동일 메모리 블록 복사본의 정합성을 상태 전이로 관리하는 프로토콜
- 배경: Write-Back 캐시 구조에서 최신 값이 특정 코어의 캐시에만 존재할 수 있어, 다른 코어의 읽기·쓰기 시점에 정합성을 보장할 규칙이 필요함
- 필요성: MESI는 기본 4상태로 정합성을 보장하고, MOESI는 Owned 상태를 추가해 dirty 데이터 공유 시 불필요한 메모리 쓰기를 줄임

---

## Ⅱ. 구조 및 구성요소

```text
Cache Line State
  MESI: Modified(M) / Exclusive(E) / Shared(S) / Invalid(I)
  MOESI: Modified(M) / Owned(O) / Exclusive(E) / Shared(S) / Invalid(I)

전이 트리거
  -> Local Read/Write
  -> Bus Snoop: 다른 코어의 BusRd / BusRdX(BusUpgr) 관측
```

| 구성요소 | 역할 | 산출물 |
|:---|:---|:---|
| Modified(M) | 자신만 보유, 값이 수정되어 메모리보다 최신 | 다른 코어 읽기 요청 시 데이터 공급 필요 |
| Exclusive(E) | 자신만 보유, 값이 메모리와 동일(clean) | 로컬 쓰기 시 버스 트랜잭션 없이 Modified 전이 |
| Shared(S) | 여러 캐시가 보유 가능, 값이 메모리와 동일 | 쓰기 시 다른 사본 무효화 필요 |
| Invalid(I) | 유효하지 않은 라인 | 접근 시 반드시 재요청(미스) |
| Owned(O, MOESI만) | dirty 값을 보유한 유일한 소유자, 다른 캐시는 Shared로 값 공유 | 메모리 즉시 갱신 없이 캐시 간 데이터 공급 |

> 요약: MESI는 M/E/S/I 4상태로, MOESI는 여기에 Owned를 더해 dirty 공유 상태를 별도로 표현한다.

---

## Ⅲ. 동작원리 및 흐름도

```text
로컬 코어 접근
  -> Read Miss: 다른 캐시 사본 없음 -> Exclusive / 사본 존재 -> Shared(기존 보유 캐시도 Shared로 전이)
  -> Write (Exclusive 상태) -> 버스 트랜잭션 없이 Modified로 전이
  -> Write (Shared 상태) -> BusUpgr/BusRdX 발행, 다른 사본 Invalid화 -> Modified로 전이

다른 코어의 버스 트랜잭션 스누핑
  -> 자신이 Modified 상태인 라인에 대해 다른 코어의 BusRd 관측
       -> MESI: 데이터를 메모리에 반영(write-back) 후 Shared로 전이
       -> MOESI: 메모리 반영 없이 캐시 간 데이터 전달 후 Owned로 전이(요청 캐시는 Shared)
  -> 자신이 보유한 라인에 대해 다른 코어의 BusRdX/BusUpgr 관측 -> Invalid로 전이
```

| 단계 | 처리 내용 | 검증 기준 |
|:---:|:---|:---|
| 1 | 읽기 미스 시 다른 캐시 보유 여부 확인 | Exclusive/Shared 분기 정확성 |
| 2 | 쓰기 시 현재 상태에 따라 버스 트랜잭션 여부 결정 | Exclusive는 무트랜잭션, Shared는 무효화 트랜잭션 |
| 3 | 다른 코어의 BusRd 스누핑 시 Modified 라인 처리 | MESI 메모리 반영 vs MOESI 캐시 간 전달 구분 |
| 4 | 다른 코어의 BusRdX/BusUpgr 스누핑 시 자신의 사본 무효화 | Invalid 전이 정확성 |

> 요약: 상태 전이는 로컬 읽기·쓰기와 버스 스누핑 두 축으로 결정되며, MOESI는 Modified 라인 공유 시 메모리 반영을 생략하는 점이 MESI와 다르다.

## Ⅳ. 특징

| 구분 | MESI | MOESI | 수치·표준 포인트 |
|:---|:---|:---|:---|
| 상태 수 | 4상태(M/E/S/I) | 5상태(M/O/E/S/I) | Owned 상태 추가 |
| dirty 공유 처리 | Modified 라인 공유 시 메모리에 즉시 write-back | Owned로 전이해 메모리 미반영, 캐시 간 전달 | 메모리 쓰기 트래픽 차이 |
| 대표 적용 | 다수 프로세서 아키텍처의 기본 스누핑 프로토콜 | AMD 계열 프로세서에서 사용되는 것으로 알려짐 | 벤더별 채택 프로토콜 상이 |
| 복잡도 | 상대적으로 단순 | Owned 상태 관리로 전이 로직 복잡도 증가 | 검증 대상 상태 조합 증가 |

> 요약: MOESI는 MESI 대비 상태 하나를 더 두어 dirty 데이터의 메모리 즉시 반영을 생략하고 캐시 간 전달로 대체한다.

## Ⅴ. 심화 비교 및 적용 판단

| 비교 축 | MESI | MOESI | 선택 기준 |
|:---|:---|:---|:---|
| 구조 | 공유 시 메모리 갱신 후 Shared 전이 | 공유 시 Owned로 전이, 메모리 갱신 생략 | 쓰기 후 공유 빈도가 높으면 MOESI 유리 |
| 비용/성능 | 메모리 쓰기 트래픽 상대적으로 많음 | 캐시 간 전달로 메모리 트래픽 절감 | 인터커넥트 대역폭과 메모리 대역폭 비교 |
| 운영/위험 | 상태 전이 로직 단순, 검증 상대적으로 용이 | Owned 상태 추가로 전이 조합·검증 비용 증가 | 설계 복잡도 감내 여부 |

> 요약: 쓰기 후 여러 코어가 반복적으로 같은 데이터를 공유하는 워크로드는 MOESI가, 구현 단순성이 중요한 경우 MESI가 상대적으로 유리하다.

| 리스크 | 원인 | 대응 방안 | 확인 지표 |
|:---|:---|:---|:---|
| 메모리 쓰기 트래픽 과다(MESI) | Modified 라인 공유마다 메모리 write-back 발생 | MOESI 등 Owned 상태 도입 검토 | 메모리 쓰기 대역폭 사용률 |
| 상태 전이 로직 오류 | 다중 상태 조합에서 스누핑 처리 누락 | 정형 검증, 상태 전이 커버리지 테스트 | 상태 전이 커버리지 100% |
| 캐시 간 전달 지연 | Owned 상태 캐시로부터의 데이터 전달 경로 지연 | 인터커넥트 토폴로지 최적화 | 캐시 간 전달 지연(cycle) |

> 요약: MESI는 메모리 트래픽 리스크, MOESI는 전이 로직 복잡도와 캐시 간 전달 지연 리스크가 핵심이다.

| 점검 항목 | 목표 기준 | 측정 방법 |
|:---|:---|:---|
| 메모리 쓰기 트래픽 | 프로토콜 적용 전후 write-back 발생 횟수 비교 | 메모리 컨트롤러 카운터 |
| 상태 전이 정확성 | 모든 상태 조합에 대한 전이 커버리지 확보 | RTL 시뮬레이션, assertion |
| 캐시 간 전달 지연 | 목표 지연(cycle) 이내 데이터 공급 | 인터커넥트 트레이스 분석 |

> 요약: 도입 효과는 메모리 쓰기 트래픽, 상태 전이 커버리지, 캐시 간 전달 지연 세 지표로 판단한다.

## Ⅵ. 실무 적용 및 결론

**적용 방안 3개:**
1. 쓰기 후 여러 코어가 반복 공유하는 워크로드가 많은 시스템은 MOESI 등 Owned 상태 기반 프로토콜을 검토해 메모리 쓰기 트래픽을 줄임
2. 프로토콜 구현 시 상태 전이 조합에 대한 커버리지 테스트를 필수화해 스누핑 처리 누락을 방지함
3. Owned 상태 캐시로부터의 캐시 간 데이터 전달 경로는 인터커넥트 토폴로지 설계 시 지연을 최소화하도록 배치함

**결론 (2줄):**
- 기술사 판단: MESI는 구현이 단순하고 검증이 용이하며, MOESI는 dirty 공유가 잦은 워크로드에서 메모리 쓰기 트래픽을 줄이는 대신 전이 복잡도를 감수해야 함
