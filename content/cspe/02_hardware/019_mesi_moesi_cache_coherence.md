# 📖 【암기용】 개념 완전 이해
> 목적: MESI·MOESI를 처음 봐도, 여러 코어의 캐시가 같은 메모리 주소를 두고 서로 다른 값을 보지 않도록 어떤 규칙으로 상태를 맞추는지 완전히 이해하게 만든다. 시험 답안 양식이 아니라, 이해를 위한 친절한 설명이다.

## 한눈에
- **개요**: **캐시 일관성 프로토콜(Cache Coherence Protocol)** 중 상태 기계(state machine) 방식의 대표 구현이 MESI이며, MOESI는 여기에 상태 하나를 더한 확장판이다. 각 캐시 라인에 M/E/S/I(MOESI는 +O) 중 하나의 상태를 붙여두고, 읽기·쓰기·스누핑 이벤트가 일어날 때마다 정해진 규칙에 따라 상태를 전이시켜 여러 코어의 캐시가 같은 주소에 대해 서로 다른 값을 보유하지 않도록 만든다.
- **왜 필요한가**: 멀티코어는 코어마다 사적 L1/L2 캐시를 갖는다. Write-Back 캐시 정책에서는 코어가 값을 고쳐도 그 즉시 메모리에 쓰지 않고 자기 캐시에만 남겨두므로, 다른 코어가 같은 주소를 읽으면 옛날 값(메모리의 구버전)을 볼 위험이 있다. 이를 막으려면 "이 주소를 누가 갖고 있고 그게 최신인지 아닌지"를 캐시 라인마다 상태로 표시하고, 상태가 바뀔 때마다 다른 코어에 알려야 한다.
- **핵심 직관**: 여러 사람이 같은 계약서 사본을 각자 들고 있는 상황과 같다. 아무도 안 고쳤으면(Shared) 다 같이 봐도 안전하다. 한 명이 자기 사본에 도장을 찍어 고치면(Modified) 나머지 사본은 즉시 "무효" 표시를 해야 하고, 그 사람에게 최신본을 요청해야 한다.

## 핵심 용어 정리 (내부에 등장하는 것들)

| 표기/용어 | 의미 | 비유 |
|:---|:---|:---|
| 캐시 일관성(Cache Coherence) | 여러 캐시에 흩어진 같은 주소의 복사본이 항상 "누가 봐도 하나의 값"으로 보이도록 보장하는 성질 — MESI·MOESI가 소속된 상위 개념 | 여러 지점의 장부가 항상 같은 잔액을 보여줘야 하는 것 |
| Write-Back 캐시 | 값을 고칠 때 캐시에만 반영하고, 그 라인이 쫓겨나거나(eviction) 요청받을 때만 메모리에 반영하는 정책 | 메모 앱에 바로 저장, 클라우드 동기화는 나중에 |
| MESI | Modified·Exclusive·Shared·Invalid 4상태로 캐시 라인을 관리하는 프로토콜 | 계약서 사본에 4단계 도장(내가 고침/나만 있음/같이 봄/무효) |
| Modified(M) | 이 코어만 보유, 값을 수정해서 메모리보다 최신(dirty) | "내가 방금 고쳤고, 원본(메모리)은 아직 구버전" |
| Exclusive(E) | 이 코어만 보유하지만 메모리와 값이 같음(clean) | "나만 갖고 있지만 아직 안 고쳤음" |
| Shared(S) | 여러 코어가 동시에 보유 가능, 값이 메모리와 같음 | "다 같이 같은 사본을 보고 있음" |
| Invalid(I) | 이 캐시 라인은 유효하지 않음 — 접근하려면 반드시 다시 가져와야 함 | "이 사본은 폐기, 새로 받아와야 함" |
| BusRd | 다른 코어가 해당 주소를 읽으려 한다는 버스 신호 | "이 주소 좀 보여줘" 방송 |
| BusRdX / BusUpgr | 다른 코어가 해당 주소에 쓰려 하니 내 사본을 무효화하라는 버스 신호 | "이 주소 내가 고칠 거야, 네 사본 버려" 방송 |
| MOESI | MESI에 Owned(O) 상태를 추가해 dirty 데이터도 메모리 갱신 없이 캐시끼리 직접 공유하게 한 확장 프로토콜 | 원본을 아직 안 고쳤어도, 최신본 소지자가 직접 복사해주는 방식 |
| Owned(O, MOESI만) | dirty 값을 가진 유일한 코어의 상태 — 자신은 최신값을 캐시 간 전달로 공급하고, 메모리는 여전히 구버전 | "최신본은 나한테 있음, 원본은 아직 안 고쳤지만 사본은 나눠줄게" |

## 깊이 이해

### MESI 4상태 전이 규칙 — 왜 이렇게 나뉘는가
- 상태는 두 축으로 나뉜다. ① "나만 갖고 있나, 여럿이 갖고 있나"(단독 vs 공유) ② "메모리보다 최신인가, 같은가"(dirty vs clean). 이 2×2 조합이 M(단독·dirty)·E(단독·clean)·S(공유·clean)·I(무효)다. "공유·dirty" 조합만 MESI에는 없다 — 누군가 값을 고쳤는데 여럿이 그걸 동시에 보고 있으면 정합성이 깨지므로, MESI는 이 조합을 아예 허용하지 않는다(이 빈틈을 메우는 것이 MOESI의 Owned다).
- **읽기 미스 시**: 다른 캐시에 사본이 전혀 없으면 새로 읽은 라인은 Exclusive로 들어온다(나만 갖고 있고 아직 안 고쳤으니까). 다른 캐시가 이미 갖고 있었다면(E 또는 S 상태) 요청한 캐시도, 기존에 갖고 있던 캐시도 모두 Shared로 전이한다.
- **로컬 쓰기 시**: 이미 Exclusive 상태라면 나만 갖고 있다는 걸 이미 알고 있으므로 버스 트랜잭션 없이 조용히 Modified로 바뀐다(공짜 승격). 반면 Shared 상태에서 쓰려면 다른 코어가 같은 사본을 갖고 있을 수 있으므로, 먼저 BusUpgr/BusRdX를 방송해 다른 사본을 Invalid로 만든 뒤에야 Modified로 전이한다.
- **다른 코어의 스누핑**: 내가 Modified로 갖고 있는 라인을 다른 코어가 BusRd로 읽으려 하면, 나는 최신 값을 공급해야 한다. MESI에서는 이때 메모리에 먼저 write-back한 뒤 자신은 Shared로 내려간다(요청한 코어도 Shared).

### MOESI의 Owned — 구체적으로 무엇이 절약되는가 (수치 예제)
다음 시퀀스로 MESI와 MOESI의 차이를 직접 세어본다. 주소 X를 코어 A, B, C가 차례로 접근한다.
1. A가 X를 읽는다 → 다른 캐시에 사본 없음 → A: Exclusive.
2. A가 X에 쓴다 → 이미 Exclusive이므로 버스 트랜잭션 없이 → A: Modified. (메모리 쓰기 0회)
3. B가 X를 읽는다(BusRd 관측) →
   - **MESI**: A는 X를 메모리에 write-back(메모리 쓰기 1회 발생)한 뒤 Shared로, B도 Shared로 전이.
   - **MOESI**: A는 메모리를 건드리지 않고 캐시 간 전달로 B에게 값을 직접 공급, A는 Owned로, B는 Shared로 전이. (메모리 쓰기 0회)
4. C가 X를 읽는다(BusRd 관측) →
   - **MESI**: 메모리가 이미 최신이므로(3단계에서 write-back됨) 메모리에서 읽어 C도 Shared로.
   - **MOESI**: 여전히 Owned인 A가 캐시 간 전달로 C에게 공급, C는 Shared로. (메모리 쓰기 0회)
- 이 4단계 시퀀스 전체에서 MESI는 메모리 쓰기 1회(3단계)가 반드시 발생하지만, MOESI는 A가 캐시에서 쫓겨날 때까지 메모리 쓰기가 0회다. 같은 라인을 여러 코어가 번갈아 읽는 생산자-소비자 패턴일수록 이 차이는 누적되어, MOESI가 메모리 쓰기 트래픽을 크게 줄인다.
- 메모리 write-back은 온칩 캐시 간 전달보다 항상 더 비싸다 — DRAM 컨트롤러까지 나가는 오프칩 경로를 타야 하므로, 코어 간 캐시 전달(온칩 인터커넥트만 경유)보다 지연이 크다. MOESI는 3·4단계처럼 여러 코어가 "공유만" 하는 상황에서는 이 비싼 경로를 아예 타지 않도록 만든 것이다.

### 비유로 정리
- MESI: 원본(메모리)을 고친 사람(A)이 남에게 보여주려면, 먼저 원본 보관소(메모리)에 가서 원본부터 최신화(write-back)한 뒤에야 남(B, C)이 원본을 복사해 갈 수 있다.
- MOESI: 고친 사람(A)이 원본 보관소에 들르지 않고, "최신본은 나한테 있음"이라는 표찰(Owned)을 붙인 채 직접 사본을 복사해서 건네준다. 원본은 나중에 A가 그 사본을 버릴 때(eviction)가 되어서야 갱신된다.

### 흔한 오해·주의점
- MESI와 MOESI를 같은 프로토콜의 다른 이름으로 혼동하면 안 된다. MOESI는 MESI가 표현하지 못하는 "공유되면서 dirty인" 상태(Owned)를 추가로 표현할 수 있다는 점이 유일하고 핵심적인 차이다.
- Exclusive는 "값이 수정됨"을 뜻하지 않는다. Exclusive는 "나만 갖고 있지만 아직 메모리와 값이 같은(clean)" 상태이고, 실제로 값을 고쳐야 비로소 Modified로 바뀐다. 이 구분 덕분에 Exclusive→Modified 전이는 버스 트랜잭션 없이 공짜로 일어난다.

## 연결 개념
- 버스 스누핑·디렉터리 기반 일관성 — MESI·MOESI 상태 전이 정보를 코어 간에 실어 나르는 두 가지 하드웨어 통신 방식(다음 절에서 상세)
- 캐시 쓰기 정책(Write-Through·Write-Back) — Write-Back 캐시이기 때문에 Modified/Owned 같은 "메모리보다 최신인" 상태가 애초에 생겨난다
- 멀티코어 프로세서 — 코어마다 사적 캐시를 두는 구조이기 때문에 일관성 프로토콜이 필수가 된다

> 1. **본질**: MESI는 Modified·Exclusive·Shared·Invalid 4상태로 캐시 라인의 소유·공유·유효 여부를 관리하는 캐시 일관성 프로토콜이다.
> 2. **가치**: 상태 전이 규칙에 따라 다른 코어의 읽기·쓰기 요청 시 자동으로 무효화·공급이 이뤄져 코어 간 데이터 정합성을 보장한다.
> 3. **판단 포인트**: MOESI는 MESI에 Owned 상태를 추가해 dirty 데이터를 메모리에 즉시 쓰지 않고도 캐시 간 공유할 수 있게 해 메모리 쓰기 트래픽을 줄인다.

## Ⅰ. 개요 및 필요성
- 개요: 여러 코어의 사적 캐시가 보유한 동일 메모리 블록 복사본의 정합성을 상태 전이로 관리하는 프로토콜
- 배경: Write-Back 캐시 구조에서 최신 값이 특정 코어의 캐시에만 존재할 수 있어, 다른 코어의 읽기·쓰기 시점에 정합성을 보장할 규칙이 필요함
- 필요성: MESI는 기본 4상태로 정합성을 보장하고, MOESI는 Owned 상태를 추가해 dirty 데이터 공유 시 불필요한 메모리 쓰기를 줄임


## Ⅱ. 구조 및 구성요소
```text
Cache Line State
  MESI: Modified(M) / Exclusive(E) / Shared(S) / Invalid(I)
  MOESI: Modified(M) / Owned(O) / Exclusive(E) / Shared(S) / Invalid(I)

전이 트리거
  -> Local Read/Write
  -> Bus Snoop: 다른 코어의 BusRd / BusRdX(BusUpgr) 관측
```

| 구성요소 | 역할 | 산출물 |
|:---|:---|:---|
| Modified(M) | 자신만 보유, 값이 수정되어 메모리보다 최신 | 다른 코어 읽기 요청 시 데이터 공급 필요 |
| Exclusive(E) | 자신만 보유, 값이 메모리와 동일(clean) | 로컬 쓰기 시 버스 트랜잭션 없이 Modified 전이 |
| Shared(S) | 여러 캐시가 보유 가능, 값이 메모리와 동일 | 쓰기 시 다른 사본 무효화 필요 |
| Invalid(I) | 유효하지 않은 라인 | 접근 시 반드시 재요청(미스) |
| Owned(O, MOESI만) | dirty 값을 보유한 유일한 소유자, 다른 캐시는 Shared로 값 공유 | 메모리 즉시 갱신 없이 캐시 간 데이터 공급 |

> 요약: MESI는 M/E/S/I 4상태로, MOESI는 여기에 Owned를 더해 dirty 공유 상태를 별도로 표현한다.


## Ⅲ. 동작원리 및 흐름도
```text
로컬 코어 접근
  -> Read Miss: 다른 캐시 사본 없음 -> Exclusive / 사본 존재 -> Shared(기존 보유 캐시도 Shared로 전이)
  -> Write (Exclusive 상태) -> 버스 트랜잭션 없이 Modified로 전이
  -> Write (Shared 상태) -> BusUpgr/BusRdX 발행, 다른 사본 Invalid화 -> Modified로 전이

다른 코어의 버스 트랜잭션 스누핑
  -> 자신이 Modified 상태인 라인에 대해 다른 코어의 BusRd 관측
       -> MESI: 데이터를 메모리에 반영(write-back) 후 Shared로 전이
       -> MOESI: 메모리 반영 없이 캐시 간 데이터 전달 후 Owned로 전이(요청 캐시는 Shared)
  -> 자신이 보유한 라인에 대해 다른 코어의 BusRdX/BusUpgr 관측 -> Invalid로 전이
```

| 단계 | 처리 내용 | 검증 기준 |
|:---:|:---|:---|
| 1 | 읽기 미스 시 다른 캐시 보유 여부 확인 | Exclusive/Shared 분기 정확성 |
| 2 | 쓰기 시 현재 상태에 따라 버스 트랜잭션 여부 결정 | Exclusive는 무트랜잭션, Shared는 무효화 트랜잭션 |
| 3 | 다른 코어의 BusRd 스누핑 시 Modified 라인 처리 | MESI 메모리 반영 vs MOESI 캐시 간 전달 구분 |
| 4 | 다른 코어의 BusRdX/BusUpgr 스누핑 시 자신의 사본 무효화 | Invalid 전이 정확성 |

> 요약: 상태 전이는 로컬 읽기·쓰기와 버스 스누핑 두 축으로 결정되며, MOESI는 Modified 라인 공유 시 메모리 반영을 생략하는 점이 MESI와 다르다.


## Ⅳ. 특징
| 구분 | MESI | MOESI | 수치·표준 포인트 |
|:---|:---|:---|:---|
| 상태 수 | 4상태(M/E/S/I) | 5상태(M/O/E/S/I) | Owned 상태 추가 |
| dirty 공유 처리 | Modified 라인 공유 시 메모리에 즉시 write-back | Owned로 전이해 메모리 미반영, 캐시 간 전달 | 메모리 쓰기 트래픽 차이 |
| 대표 적용 | 다수 프로세서 아키텍처의 기본 스누핑 프로토콜 | AMD 계열 프로세서에서 사용되는 것으로 알려짐 | 벤더별 채택 프로토콜 상이 |
| 복잡도 | 상대적으로 단순 | Owned 상태 관리로 전이 로직 복잡도 증가 | 검증 대상 상태 조합 증가 |

> 요약: MOESI는 MESI 대비 상태 하나를 더 두어 dirty 데이터의 메모리 즉시 반영을 생략하고 캐시 간 전달로 대체한다.


## Ⅴ. 심화 비교 및 적용 판단
| 구분 | MESI | MOESI | 선택 기준 |
|:---|:---|:---|:---|
| 구조 | 공유 시 메모리 갱신 후 Shared 전이 | 공유 시 Owned로 전이, 메모리 갱신 생략 | 쓰기 후 공유 빈도가 높으면 MOESI 유리 |
| 비용/성능 | 메모리 쓰기 트래픽 상대적으로 많음 | 캐시 간 전달로 메모리 트래픽 절감 | 인터커넥트 대역폭과 메모리 대역폭 비교 |
| 운영/위험 | 상태 전이 로직 단순, 검증 상대적으로 용이 | Owned 상태 추가로 전이 조합·검증 비용 증가 | 설계 복잡도 감내 여부 |

> 요약: 쓰기 후 여러 코어가 반복적으로 같은 데이터를 공유하는 워크로드는 MOESI가, 구현 단순성이 중요한 경우 MESI가 상대적으로 유리하다.

| 리스크 | 원인 | 대응 방안 | 확인 지표 |
|:---|:---|:---|:---|
| 메모리 쓰기 트래픽 과다(MESI) | Modified 라인 공유마다 메모리 write-back 발생 | MOESI 등 Owned 상태 도입 검토 | 메모리 쓰기 대역폭 사용률 |
| 상태 전이 로직 오류 | 다중 상태 조합에서 스누핑 처리 누락 | 정형 검증, 상태 전이 커버리지 테스트 | 상태 전이 커버리지 100% |
| 캐시 간 전달 지연 | Owned 상태 캐시로부터의 데이터 전달 경로 지연 | 인터커넥트 토폴로지 최적화 | 캐시 간 전달 지연(cycle) |

> 요약: MESI는 메모리 트래픽 리스크, MOESI는 전이 로직 복잡도와 캐시 간 전달 지연 리스크가 핵심이다.

| 점검 항목 | 목표 기준 | 측정 방법 |
|:---|:---|:---|
| 메모리 쓰기 트래픽 | 프로토콜 적용 전후 write-back 발생 횟수 비교 | 메모리 컨트롤러 카운터 |
| 상태 전이 정확성 | 모든 상태 조합에 대한 전이 커버리지 확보 | RTL 시뮬레이션, assertion |
| 캐시 간 전달 지연 | 목표 지연(cycle) 이내 데이터 공급 | 인터커넥트 트레이스 분석 |

> 요약: 도입 효과는 메모리 쓰기 트래픽, 상태 전이 커버리지, 캐시 간 전달 지연 세 지표로 판단한다.


## Ⅵ. 실무 적용 및 결론
**적용 방안 3개:**
1. 쓰기 후 여러 코어가 반복 공유하는 워크로드가 많은 시스템은 MOESI 등 Owned 상태 기반 프로토콜을 검토해 메모리 쓰기 트래픽을 줄임
2. 프로토콜 구현 시 상태 전이 조합에 대한 커버리지 테스트를 필수화해 스누핑 처리 누락을 방지함
3. Owned 상태 캐시로부터의 캐시 간 데이터 전달 경로는 인터커넥트 토폴로지 설계 시 지연을 최소화하도록 배치함

**결론 (2줄):**
- 기술사 판단: MESI는 구현이 단순하고 검증이 용이하며, MOESI는 dirty 공유가 잦은 워크로드에서 메모리 쓰기 트래픽을 줄이는 대신 전이 복잡도를 감수해야 함
- 향후 방향: 코어 수 증가에 따라 MESIF(Forward 상태 추가) 등 벤더별 확장 프로토콜과 디렉터리 기반 구현이 함께 검토되고 있음
