## 미리 알고가기

- 퍼시스턴트 메모리는 바이트 주소 지정과 영속성을 함께 제공하는 메모리 계층임
- DAX는 페이지 캐시를 우회해 영속 메모리에 직접 접근하는 방식임
- 플러시(flush)와 펜스(fence)는 데이터를 영속 영역까지 반영하고 쓰기 순서를 보장하는 명령임
- 적재·저장(Load/Store)은 CPU가 메모리 주소의 데이터를 직접 읽고 쓰는 명령 방식임

## 작성 근거(검토용)

- 퍼시스턴트 메모리는 바이트 주소 지정, DAX, 플러시·펜스, 장애 정합성을 핵심 축으로 설명함
- 비교표는 DRAM·SSD·퍼시스턴트 메모리의 주소 지정, 접근 경로, 복구·정합성 책임을 대비함
- 실무 판단은 영속 반영 지연·장애 복구 정합성과 잔존 데이터·삭제 검증률로 검증함

## Ⅰ. 개요

- **정의/개념**: 퍼시스턴트 메모리는 CPU가 바이트 단위로 직접 접근하면서 전원 장애 후에도 데이터가 유지되는 메모리와 스토리지 사이의 영속 계층임
- **배경/필요성**: 인메모리 시스템의 재시작 복구 시간과 블록 I/O 경로를 줄이기 위해 바이트 주소 지정과 영속성을 결합한 계층이 필요함

## Ⅱ. 특징

- 블록 I/O 대신 적재·저장 방식으로 영속 데이터를 다룰 수 있음
- DAX로 페이지 캐시를 우회하고 영속 주소 공간을 재매핑해 재시작 적재 시간을 줄임
- 애플리케이션이 플러시와 쓰기 순서를 직접 관리해야 해 프로그래밍 부담이 큼
- 메모리처럼 보이지만 보안과 폐기 정책은 저장장치 수준으로 다뤄야 함

## Ⅲ. 종류 및 비교

| 판단 기준 | DRAM | SSD | 퍼시스턴트 메모리 |
|:---|:---|:---|:---|
| 주소 지정 | 바이트 단위로 접근하지만 영속성은 없음 | 블록 단위 I/O로 접근함 | 바이트 단위 접근과 영속성을 함께 제공함 |
| 접근 경로 | CPU 적재·저장 명령을 사용함 | 시스템 콜과 블록 I/O 경로를 거침 | 적재·저장 또는 DAX 경로로 접근함 |
| 복구·정합성 책임 | 재시작 시 저장장치에서 데이터를 다시 적재하며 프로세스 종료 뒤의 영속성은 없음 | 유지된 데이터를 블록 I/O 경로로 복구하며 파일시스템·블록 계층이 순서를 관리함 | 유지된 주소 공간을 다시 매핑해 복구하며 애플리케이션이 장애 정합성과 플러시 순서를 관리함 |

> 요약: 퍼시스턴트 메모리는 적재·저장과 영속성을 결합하지만 플러시·펜스와 장애 정합성을 애플리케이션이 관리함.

## Ⅳ. 구성요소 및 구조

| 구성요소 | 설명 |
|:---|:---|
| 애플리케이션 | 영속 자료구조를 직접 다루므로 성능 이득과 일관성 책임을 함께 가짐 |
| PM 라이브러리 | 트랜잭션 관리와 메모리 할당, 복구 지원 기능을 제공해 구현 부담을 줄임 |
| CPU 캐시 제어 | 플러시와 펜스가 실제 영속 시점과 쓰기 순서를 보장함 |
| PM 네임스페이스 | OS가 노출한 영속 메모리 영역으로 접근 정책과 생명주기를 관리함 |

> 요약: 애플리케이션은 PM 라이브러리와 CPU 캐시 제어를 거쳐 영속 메모리 영역의 데이터와 복구 상태를 관리함.

## Ⅴ. 원리 및 절차 흐름도

1. **영역 할당**: OS가 DAX 파일시스템 또는 네임스페이스를 애플리케이션에 제공함
2. **데이터 기록**: 애플리케이션이 적재·저장 명령으로 영속 자료구조를 갱신함
3. **영속 보장**: 플러시와 펜스로 기록 순서와 반영 시점을 보장함
4. **장애 복구**: 로그와 버전 정보와 체크섬을 바탕으로 일관된 상태를 복원함

> 요약: DAX 영역을 적재·저장으로 갱신하고 플러시·펜스로 영속 순서를 확정한 뒤 로그·버전으로 복구함.

## Ⅵ. 실무 사례

1. 인메모리 데이터베이스는 PM 라이브러리와 트랜잭션 패턴을 적용하고 장애 복구 정합성·영속 반영 지연을 확인함
2. 서버 재할당은 네임스페이스 암호화와 안전 삭제를 적용하고 잔존 데이터 검출 건수·삭제 검증률을 확인함

## Ⅶ. 결론

- 퍼시스턴트 메모리는 바이트 주소 지정과 영속성을 결합하므로 플러시·펜스 순서와 장애 복구·안전 삭제 절차를 설계해야 함
