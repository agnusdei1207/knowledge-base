## Ⅰ. 개요
- **정의**: 바이트 단위 접근이 가능하면서 전원 차단 후에도 데이터를 유지하는 메모리 계층임
- **배경/필요성**: DRAM과 SSD 사이 지연-용량 격차를 메워 I/O 병목을 해소할 필요가 있음
- **비유**: 책상 위 메모지가 지워지지 않고 영구히 남는 것과 유사함

| 출제 의도 | 반드시 짚을 핵심 | 감점 회피 포인트 |
|:---|:---|:---|
| DRAM-SSD 사이 새 계층 의의 | 바이트 주소 지정 + 비휘발성 | NVDIMM(097 참조)과의 관계 구분 |

> 요약: 바이트 접근성과 비휘발성을 동시에 제공하는 DRAM-SSD 중간 계층임

## Ⅱ. 구성요소
```text
CPU -- Memory Bus --+-- DRAM (volatile)
                    +-- PMem (non-volatile) -- App Direct / Memory Mode
```

| 구성요소 | 설명 | 비유 |
|:---|:---|:---|
| PMem 미디어 | 비휘발 셀로 바이트 단위 읽기/쓰기를 지원하는 물리 매체임 | 지워지지 않는 칠판 |
| App Direct 모드 | 애플리케이션이 DAX로 PMem을 직접 매핑하여 사용하는 모드임 | 파일 없이 메모리 직접 접근 |
| Memory 모드 | PMem을 대용량 메인 메모리로, DRAM을 캐시로 사용하는 모드임 | 큰 책장 + 작은 책상 |

> 요약: PMem 미디어를 App Direct 또는 Memory 모드로 활용하는 구조임

## Ⅲ. 절차
```text
PMem 장착 -> BIOS 모드 설정 -> 네임스페이스 생성 -> DAX 마운트/앱 매핑
```
- 1단계: PMem 모듈을 DIMM 슬롯에 장착함
- 2단계: BIOS에서 App Direct 또는 Memory 모드를 설정함
- 3단계: OS에서 네임스페이스(논리 영역)를 생성함
- 4단계: DAX 파일시스템으로 마운트하거나 `mmap`으로 앱에 직접 매핑함

> 요약: 장착-모드설정-네임스페이스-매핑 순으로 PMem을 활성화함

## Ⅳ. 문제점
- 쓰기 지연 비대칭: 읽기 대비 쓰기 지연이 3~4배 높아 쓰기 집약 워크로드에 불리함
- 내구성 한계: NAND 대비 높지만 쓰기 횟수 제한이 존재하여 웨어레벨링이 필요함
- 프로그래밍 복잡도: 캐시라인 플러시(`clflush`)와 순서 보장을 앱이 직접 관리해야 함

> 요약: 쓰기 비대칭·내구성·프로그래밍 복잡도가 채택 장벽임

## Ⅴ. 개선방안
1. 단기: 쓰기 버퍼링 및 배치 커밋으로 쓰기 지연 영향을 완화함
2. 중기: 컨트롤러 내 웨어레벨링 알고리즘 고도화로 셀 수명을 연장함
3. 장기: PMDK 등 라이브러리 표준화로 개발자 부담을 경감함

> 요약: 버퍼링·웨어레벨링·라이브러리 표준화로 PMem 채택 장벽을 낮춤

## Ⅵ. 전망
- 발전 방향: CXL 메모리 풀링과 결합하여 랙 수준 공유 영구 메모리 티어로 확장됨
- 기술사적 판단: 인메모리 DB·로그 영역에서 SSD 대체 수요가 지속적으로 증가함
- 기술사 제언: 메모리 계층 설계 시 PMem 티어의 읽기/쓰기 비대칭을 반영할 필요가 있음
