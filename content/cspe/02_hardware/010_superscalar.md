## Ⅰ. 개요
- **정의**: 한 클럭에 2개 이상의 명령어를 동시에 인출·실행할 수 있는 프로세서 구조
- **배경/필요성**: 단일 파이프라인(007 참조)은 CPI 하한이 1이므로, 이를 넘어서려면 다중 실행 경로가 필요함
- **비유**: 1차선 고속도로를 다차선으로 확장하여 동시에 여러 차량이 통행하는 것과 유사함

| 출제 의도 | 반드시 짚을 핵심 | 감점 회피 포인트 |
|:---|:---|:---|
| ILP 활용을 위한 하드웨어 접근 | 이슈 폭(issue width), 비순차 실행 | VLIW와의 차이(하드웨어 vs 컴파일러 스케줄링) 구분 |

> 요약: 다중 실행 유닛으로 CPI를 1 미만으로 낮추는 프로세서 구조임

## Ⅱ. 구성요소
```text
  +------------+     +---------------+     +-------------+
  | Multi-Fetch |---->| Dispatch/Issue|---->| Exec Units  |
  | (n-wide)   |     | (Rename+Queue)|     | (ALU/FPU/LS)|
  +------------+     +---------------+     +------+------+
                                                  |
                                           +------+------+
                                           |  Reorder    |
                                           |  Buffer(ROB)|
                                           +-------------+
```

| 구성요소 | 설명 | 비유 |
|:---|:---|:---|
| 다중 인출(Multi-Fetch) | 매 클럭 n개 명령어를 동시에 인출함 | 다차선 톨게이트에서 동시 진입 |
| 디스패치/이슈 큐 | 레지스터 리네이밍 후 준비된 명령어를 실행 유닛에 배정함 | 작업 배분 관리자 |
| 실행 유닛 그룹 | ALU·FPU·Load/Store 등 기능별 병렬 유닛 | 각 전문 분야 작업자 |
| ROB (Reorder Buffer) | 비순차 실행 결과를 원래 프로그램 순서로 커밋함 | 완료된 택배를 접수 순서대로 배송 |

> 요약: 다중 인출·디스패치·병렬 실행 유닛·ROB가 핵심 구성요소임

## Ⅲ. 절차
```text
  다중 인출        리네이밍/배정     병렬 실행        순서 커밋
  (Fetch n)       (Rename+Issue)   (Execute)        (Commit)
   |               |               |               |
   +--n개 동시--->+--의존성해소--->+--다중 유닛---->+
  명령어 캐시     레지스터 매핑    ALU/FPU/LS      ROB 순서대로
  에서 n개 인출   + 이슈 큐 투입   동시 수행        아키텍처 반영
```
- 1단계: 매 클럭 n개(이슈 폭)의 명령어를 명령어 캐시에서 동시에 인출함
- 2단계: 레지스터 리네이밍으로 WAR/WAW 해저드를 제거하고 이슈 큐에 투입함
- 3단계: 피연산자가 준비된 명령어부터 비순차적으로 해당 실행 유닛에서 수행함
- 4단계: ROB에서 프로그램 순서대로 결과를 커밋하여 정확한 예외 처리를 보장함

> 요약: 다중 인출-리네이밍-병렬 실행-순서 커밋의 4단계로 ILP를 극대화함

## Ⅳ. 문제점
- ILP 벽(ILP Wall): 일반 프로그램의 명령어 간 의존성으로 이슈 폭 대비 실제 IPC가 낮음 — 4-wide 설계에서 실측 IPC가 2 내외에 머무름
- 전력·면적 증가: 리네이밍 테이블·이슈 큐·ROB 등 제어 로직이 이슈 폭의 제곱에 비례하여 증가함 — 전력 효율이 저하됨
- 분기 오예측 비용 확대: 이슈 폭이 넓을수록 오예측 시 폐기되는 명령어 수가 증가함 — 플러시 페널티가 단일 파이프라인 대비 n배로 확대됨

> 요약: ILP 한계·전력 증가·오예측 비용 확대가 슈퍼스칼라의 주요 제약임

## Ⅴ. 개선방안
1. 단기: 컴파일러 최적화(루프 언롤링, 소프트웨어 파이프라이닝)로 ILP를 노출시켜 실효 IPC를 향상시킴
2. 중기: 클러스터드 마이크로아키텍처로 제어 로직을 분산하여 면적·전력 증가를 억제함
3. 장기: SMT(동시 멀티스레딩)를 결합하여 단일 스레드 ILP 부족분을 다중 스레드 TLP로 보완함

> 요약: 컴파일러 최적화·클러스터드 설계·SMT 결합으로 각 문제를 해결함

## Ⅵ. 전망
- 발전 방향: 이슈 폭 확대보다 SMT·이기종 코어(big.LITTLE) 조합으로 전력 대비 처리량 극대화 추세임
- 기술사적 판단: 슈퍼스칼라는 고성능 프로세서의 기본 구조이며, VLIW·SMT와의 비교 출제가 빈번함
- 기술사 제언: 워크로드 특성(ILP/TLP 비율)에 따른 이슈 폭·SMT 스레드 수 최적 설계를 제시할 필요
