## 미리 알고가기

- 슈퍼스칼라는 한 클록에 여러 명령어를 발행하는 구조임
- ILP를 하드웨어가 동적으로 찾아 병렬 실행함
- 비순서 실행과 ROB가 함께 동작하는 경우가 많음

## Ⅰ. 개요

- **정의/개념**: 슈퍼스칼라는 한 클록 주기에 여러 명령어를 동시에 인출하고 해독하고 발행해 복수 실행 유닛에서 병렬로 처리하는 CPU 아키텍처로, 단일 파이프라인의 처리량 한계를 넘기 위해 설계된 명령어 수준 병렬화 구조임
- **배경/필요성**: 파이프라이닝만으로는 이상적으로도 한 클록당 한 명령 처리에 머물기 때문에, 더 높은 IPC를 달성하려면 하드웨어가 독립 명령어를 실시간으로 찾아 병렬 발행해야 함

## Ⅱ. 특징

- 동적 의존성 분석으로 여러 명령어를 동시에 실행함
- 소프트웨어 수정 없이 기존 바이너리에서 ILP를 활용함
- 발행 폭이 넓어질수록 의존성 검사와 자원 배분 로직이 급격히 복잡해짐
- 분기 실패와 실행 유닛 유휴 슬롯이 성능 상한을 제한함

## Ⅲ. 종류 및 비교

| 판단 기준 | Scalar | Superscalar | VLIW |
|:---|:---|:---|:---|
| 동시 발행 | 1개 | N개 | N개 |
| 병렬성 탐지 | 없음 | 하드웨어 동적 탐지 | 컴파일러 정적 탐지 |
| 장점 | 단순성 | 기존 바이너리 활용 | 하드웨어 단순화 |
| 한계 | IPC 상한 낮음 | 회로 복잡도 높음 | 바이너리 유연성 낮음 |

> 요약: 슈퍼스칼라는 하드웨어가 동적으로 ILP를 찾아 기존 바이너리의 IPC를 높이는 구조임.

## Ⅳ. 구성요소 및 구조

| 구성요소 | 설명 |
|:---|:---|
| Wide Front-end | 여러 명령어를 동시에 fetch와 decode해 발행 폭의 기반을 만듦 |
| Dependency Check | 데이터와 자원 의존성을 판정해 병렬 발행 가능 여부를 결정함 |
| Multiple Execution Units | 정수·부동소수점·로드스토어 유닛이 병렬 실행을 담당함 |
| Reorder Buffer | 비순서로 끝난 결과를 프로그램 순서대로 retire해 정합성을 유지함 |

```text
+----------------+     +-----------------+     +----------------------+
| Wide Front-end | --> | Dependency Check | --> | Multiple Exec Units   |
+----------------+     +-----------------+     +----------------------+
                                                |
                                                v
                                         +---------------+
                                         | Reorder Buffer |
                                         +---------------+
```

> 요약: 슈퍼스칼라는 넓은 front-end, 의존성 검사, 복수 실행 유닛, ROB로 병렬 실행과 순차 확정을 함께 처리함.

## Ⅴ. 원리 및 절차 흐름도

```text
+-------------+     +-------------+     +-------------+     +-------------+
| 다중 인출       | --> | 의존성 분석      | --> | 병렬 발행       | --> | 순차 retire   |
+-------------+     +-------------+     +-------------+     +-------------+
```

1. **다중 인출**: 한 번에 여러 명령어를 가져옴
2. **의존성 분석**: 병렬 실행 가능한 조합을 찾음
3. **병렬 발행**: 실행 유닛에 동시에 배치함
4. **순차 retire**: 결과를 프로그램 순서대로 확정함

> 요약: 슈퍼스칼라는 발행 폭보다 실제 코드의 독립 명령어와 의존성 검사 비용이 성능을 좌우함.

## Ⅵ. 실무 적용 및 유의점

1. 독립 명령어가 부족하면 넓은 실행 유닛도 유휴 슬롯이 늘어나므로 register renaming과 out-of-order execution을 적용하고 issue slot utilization과 IPC로 검증함
2. 발행 폭 확대와 분기 실패는 전력·면적·폐기 비용을 키우므로 clustered design, selective width, front-end prediction을 조정하고 area efficiency, perf per watt, wasted uop ratio로 확인함

## Ⅶ. 결론

- 슈퍼스칼라의 판단 기준은 실행 유닛 수가 아니라 실제 코드에서 병렬 실행 가능한 명령어를 얼마나 찾아내는지에 있음

## 작성 근거(검토용)

- 슈퍼스칼라는 실행 유닛 개수보다 동적 의존성 분석과 발행 폭의 제약을 설명해야 하므로 해당 흐름으로 구성함
- 모호한 표현은 기존 바이너리 활용, issue slot utilization, IPC처럼 채점자가 확인 가능한 말로 구체화함
- 결론은 하드웨어가 실제 코드에서 병렬 발행 가능한 명령을 찾는 절차에 초점을 둠
