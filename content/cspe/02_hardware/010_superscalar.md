# 010. 슈퍼스칼라 아키텍처 (Superscalar) [출제:136회]

## 미리 알고가기

- **ILP (Instruction Level Parallelism)**: 프로그램 내의 명령어들 사이의 독립성을 활용하여 여러 명령어를 동시에 실행할 수 있는 잠재적 병렬성임
- **파이프라이닝**: 명령어 단계를 겹쳐 처리량을 높이는 기술인 반면, **슈퍼스칼라**는 이를 병렬로 여러 개 두어 처리량을 한 단계 더 높인 기술임
- **비순서 실행 (Out-of-Order)**: 실행 순서를 바꾸어 데이터 대기 시간을 최소화하는 기술로, 슈퍼스칼라의 효율을 극대화함

## Ⅰ. 개요

- **정의/개념**: 슈퍼스칼라(Superscalar)는 한 클록 주기에 여러 개의 명령어를 동시에 인출(Fetch)하고 발행(Issue)하여 실행할 수 있도록 다수의 실행 유닛(ALU 등)을 갖춘 CPU 아키텍처임
- **배경/필요성**: 단일 파이프라인 구조는 이론적으로 $CPI=1$이 한계임. 이를 극복하고 1보다 낮은 CPI(즉, $IPC > 1$)를 달성하기 위해 하드웨어가 동적으로 명령어 간의 의존성을 체크하며 병렬로 실행할 필요가 생김

## Ⅱ. 특징 및 비교

슈퍼스칼라는 하드웨어가 실시간으로 병렬성을 찾으므로 소프트웨어 호환성이 높으나 회로가 복잡함.

| 비교 항목 | 일반 파이프라인 (Scalar) | 슈퍼스칼라 (Superscalar) | VLIW (Very Long Instruction Word) |
|:---|:---|:---|:---|
| **동시 실행** | 한 클록에 1개 명령어 | **한 클록에 N개 명령어** | 한 클록에 N개 명령어 (묶음) |
| **병렬성 탐지** | 없음 | **하드웨어가 동적 탐지** | **컴파일러가 정적 탐지** |
| **H/W 복잡도** | 낮음 | **매우 높음** (의존성 체크 로직) | 낮음 (H/W 로직 제거) |
| **S/W 호환성** | 높음 | **높음** (기존 바이너리 실행 가능) | 낮음 (컴파일러 재구동 필수) |
| **주요 활용** | 저전력 MCU | **현대 고성능 CPU (x86/ARM)** | DSP, 초기 고성능 서버 |

> 요약: 슈퍼스칼라는 '똑똑한 하드웨어'가 실시간으로 최적의 실행 조합을 찾는 방식임.

## Ⅲ. 구성요소/구조

슈퍼스칼라는 넓은 명령어 입구(Fetch/Decode)와 여러 개의 실행 통로를 가짐.

- **구성요소**:
  - **Instruction Fetch Unit**: 여러 명령어를 한꺼번에 메모리에서 읽어옴
  - **Dependency Check Logic**: 명령어들 사이에 데이터/제어 의존성이 있는지 하드웨어적으로 분석
  - **Multiple Execution Units**: 복수의 정수 연산기(ALU), 부동소수점 연산기(FPU), 로드/스토어 유닛
  - **Commit Unit (ROB)**: 비순서로 끝난 결과를 다시 순서대로 취합하여 최종 반영

- **아키텍처 구조도 (ASCII)**:

```text
[Instruction Stream]
  Inst 1, Inst 2, Inst 3, Inst 4...
             |
      +------v-------+
      | Fetch/Decode |  (Wide Front-end)
      +------+-------+
             |
      +------v-------+
      |  Dispatch    |  (Dependency Check)
      +--+---+---+---+
         |   |   |
    +----v-+ v---v+ +----v-+
    | ALU 1| |ALU 2| | FPU  | (Multiple Units)
    +----+-+ +-+--+ +----+-+
         |     |         |
      +--v-----v---------v--+
      | Reorder Buffer (ROB)| (Sequential Commit)
      +---------------------+
```

1. **Fetch** 단계에서 명령어 묶음을 가져옴
2. **Dispatch** 유닛이 의존성이 없는 명령어들을 각 유닛으로 동시에 보냄
3. **ROB**는 실행이 끝난 명령어들을 원래 프로그램 순서에 맞게 하나씩 종료(Retire)시킴

## Ⅳ. 문제점 및 개선방안

1. **명령어 의존성 한계 (ILP Wall)**: 프로그램 자체에 독립적인 명령어가 적으면 하드웨어가 아무리 넓어도 병렬로 실행할 수 없음
   - **개선방안**: **레지스터 리네이밍(Register Renaming)**으로 가짜 의존성(WAR, WAW)을 제거하고, **비순서 실행**을 통해 멀리 떨어진 독립 명령어를 끌어와 실행함 (확인: 유휴 실행 슬롯 비율)

2. **기하급수적인 회로 복잡도**: 발행 폭(Issue Width)을 2배로 늘리면 의존성 체크 로직의 복잡도는 그 제곱으로 늘어나 전력 소모와 발열이 심해짐
   - **개선방안**: 코어 내 유닛을 그룹화(Clustering)하거나, 하드웨어 대신 컴파일러에게 짐을 넘기는 VLIW 방식을 일부 혼합함 (확인: 다이 면적 대비 성능 이득)

3. **분기 오예측 손실 가중**: 여러 명령어를 동시에 뽑아 쓰다가 분기 예측이 틀리면, 단일 파이프라인보다 훨씬 많은 양의 작업 결과가 한꺼번에 버려짐
   - **개선방안**: 더욱 정교한 동적 분기 예측 알고리즘과 투기적 실행(Speculative Execution) 제어 로직을 강화함 (확인: 분기 예측 성공률)

## Ⅴ. 실무 적용 사례

| 적용 영역 | 적용 방식 | 확인 지표 |
|:---|:---|:---|
| 데스크톱/서버 CPU | Intel Core나 AMD Ryzen 등은 4~8개 이상의 명령어를 동시 발행하는 슈퍼스칼라 구조 채택 | IPC (Instructions Per Cycle) |
| 고성능 스마트폰 AP | Apple A시리즈나 ARM Cortex-X 등에서 넓은 디코딩 폭(Wide Decoder)을 통해 단일 스레드 성능 극대화 | 싱글 코어 벤치마크 점수 |
| 실시간 임베디드 | 복잡한 의존성 체크로 인해 응답 시간이 불분명해지는 것을 막기 위해 제한적인 2-Way 슈퍼스칼라만 적용 | 인터럽트 응답 시간, 전력 효율 |

> 요약: 단일 코어의 성능을 극한으로 끌어올려야 하는 범용 컴퓨팅 시장의 주류 기술임.

## Ⅵ. 결론

슈퍼스칼라는 파이프라인 병렬성을 수평적으로 확장하여 '클록당 처리량'을 획기적으로 높인 현대 CPU의 정수임. 기술사는 슈퍼스칼라가 단순히 실행 유닛만 늘린 것이 아니라, 그 이면에 숨겨진 복잡한 의존성 체크와 리네이밍, 비순서 실행 기술이 조화를 이뤄야 성능이 발현됨을 이해해야 함.

향후 아키텍처는 전력 효율의 한계로 인해 무한정 발행 폭을 넓히기보다는, 특정 워크로드(AI 등)에 특화된 유닛을 슈퍼스칼라 파이프라인에 통합하는 방향으로 진화할 것임. 결국 최적의 설계는 소프트웨어의 병렬성을 하드웨어가 얼마나 영리하게 찾아내어 에너지 효율적으로 실행하느냐에 달려 있음.
