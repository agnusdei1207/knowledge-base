## Ⅰ. 개요
- **정의**: 한 클럭 사이클에 복수의 명령어를 동시에 발행·실행하는 프로세서 아키텍처
- **배경/필요성**: 단일 파이프라인(007 참조)은 CPI 하한이 1이므로 IPC > 1을 달성하려면 복수 발행 경로가 필요함
- **비유**: 1차선 도로를 4차선으로 확장하여 같은 시간에 더 많은 차량이 통과할 수 있게 하는 것과 유사함

| 출제 의도 | 반드시 짚을 핵심 | 감점 회피 포인트 |
|:---|:---|:---|
| IPC > 1 달성 구조와 ILP 한계 | 발행 폭, 동적 스케줄링, 의존성 검사 | VLIW(011)와의 스케줄링 주체 차이 명시 |

> 요약: 복수 명령어 동시 발행으로 IPC > 1을 달성하는 하드웨어 중심 아키텍처임

## Ⅱ. 구성요소
```text
I-Cache --> Fetch(N개) --> Decode(N개) --> Rename --> Issue Queue
                                                        |
                          +-----------------------------+
                          |        |        |        |
                         ALU0    ALU1    FPU     Load/Store
                          |        |        |        |
                          +-----------------------------+
                                        |
                                   Reorder Buffer --> Commit
```

| 구성요소 | 설명 | 비유 |
|:---|:---|:---|
| 다중 발행 프론트엔드 | 클럭당 N개 명령어를 동시에 인출·해독하는 Fetch/Decode 유닛 | 4차선 톨게이트에서 동시에 차량을 통과시킴 |
| 레지스터 리네이밍 | 논리 레지스터를 물리 레지스터에 재매핑하여 WAR/WAW 해저드를 제거함 | 사람마다 임시 이름표를 붙여 이름 충돌 방지 |
| 이슈 큐 (Issue Queue) | 피연산자가 준비된 명령어를 선별하여 기능 유닛에 비순차 발행함 | 재료가 갖춰진 주문부터 조리 시작하는 주방 |
| 기능 유닛 (FU) | ALU·FPU·Load/Store 등 복수 실행 유닛이 병렬로 연산 수행함 | 주방의 튀김·구이·디저트 전담 조리대 |
| 리오더 버퍼 (ROB) | 비순차 실행 결과를 프로그램 순서대로 커밋하여 정확한 예외 처리를 보장함 | 완성된 요리를 주문 번호순으로 서빙 |

> 요약: 다중 발행 프론트엔드, 리네이밍, 이슈 큐, 복수 FU, ROB가 핵심 구성임

## Ⅲ. 절차
```text
Fetch(N) --> Decode(N) --> Rename --> Issue(OoO) --> Execute --> Commit(In-Order)
```
- 1단계: **다중 인출·해독** — 클럭당 N개 명령어를 I-Cache에서 인출하고 동시에 해독함
- 2단계: **리네이밍·의존성 검사** — 물리 레지스터 매핑으로 가짜 의존을 제거하고 진정한 의존(RAW)만 추적함
- 3단계: **비순차 발행·실행** — 피연산자가 준비된 명령어를 이슈 큐에서 선별하여 가용 FU에 발행함
- 4단계: **순차 커밋** — ROB에서 프로그램 순서대로 결과를 아키텍처 레지스터에 반영하고 예외 처리를 보장함

> 요약: 다중 인출 → 리네이밍 → 비순차 실행 → 순차 커밋의 4단계로 IPC > 1을 달성함

## Ⅳ. 문제점
- **ILP 한계**: 프로그램 내 명령어 간 진정한 의존(RAW)이 병렬 발행 가능 명령 수를 제한함 — 발행 폭 증가 대비 IPC 향상이 수확 체감 (013 참조)
- **하드웨어 복잡도 증가**: 리네이밍 테이블·이슈 큐·ROB 크기가 발행 폭의 제곱에 비례하여 증가함 — 면적·전력·검증 비용 급증
- **분기 오예측 손실 확대**: 발행 폭이 넓을수록 오예측 시 폐기되는 투기 명령 수가 증가함 — 플러시 패널티가 단일 파이프라인 대비 증폭

> 요약: ILP 한계, 하드웨어 복잡도, 오예측 손실 확대가 슈퍼스칼라의 3대 제약임

## Ⅴ. 개선방안
1. 단기: 컴파일러 최적화(루프 언롤링, 소프트웨어 파이프라이닝)로 가용 ILP를 사전 확보
2. 중기: 클러스터형 실행 유닛 분할 및 분산 이슈 큐로 배선 지연·전력 증가 억제
3. 장기: SMT(Simultaneous Multithreading) 도입으로 단일 스레드 ILP 부족 시 타 스레드 명령으로 FU 유휴 슬롯 활용

> 요약: 컴파일러 ILP 확보 → 클러스터 분할 → SMT 도입 순서로 3대 제약을 각각 완화함

## Ⅵ. 전망
- **발전 방향**: 발행 폭 6~8을 유지하면서 SMT·이종 코어(big.LITTLE)와 결합하여 전력 대비 처리량 극대화 추세
- **기술사적 판단**: 슈퍼스칼라는 VLIW(011), ILP(013)와 비교 출제되며 동적 vs 정적 스케줄링 관점이 핵심임
- **기술사 제언**: 파이프라인(007) → 해저드(008) → 포워딩·예측(009) → 슈퍼스칼라(010) → VLIW(011)의 계층적 흐름을 답안에서 일관 서술할 필요
