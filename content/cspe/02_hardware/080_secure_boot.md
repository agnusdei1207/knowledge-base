# 📖 【암기용】 개념 완전 이해

> 목적: Secure Boot를 처음 봐도 왜 암호화가 아니라 서명 검증인지, 신뢰 체인이 어떻게 이어지는지 이해하게 만든다. 시험 답안 양식이 아니라, 이해를 위한 친절한 설명이다.

## 한눈에
- **개요**: 부팅 각 단계의 코드를 실행 전에 디지털 서명으로 검증해 신뢰 체인을 구성하는 부팅 보안 기법
- **왜 필요한가**: 공격자가 부트로더나 펌웨어를 변조하면 OS보다 먼저 실행돼 탐지가 어렵다. Secure Boot는 각 단계 실행 전 서명을 확인해 변조된 코드의 실행 자체를 차단한다.
- **핵심 직관**: 택배 봉인 스티커가 뜯겨 있으면 내용물을 확인하지 않고 반송하는 것처럼, 서명이 유효하지 않으면 다음 코드를 실행하지 않는다.

## 깊이 이해
- **배경·문제의식**: 부트킷·루트킷은 OS 로딩 이전 단계에 침투해 OS 수준 보안 통제를 우회한다.
- **배경·문제의식**: 이런 공격을 막으려면 OS가 아니라 칩 제조 시점부터 이어지는 불변 신뢰 뿌리가 필요하다.
- **작동 원리**: Secure Boot는 각 부팅 단계의 코드를 실행하기 전에 서명을 먼저 검증하고, 검증에 성공한 경우에만 해당 단계를 실행한다.
- **작동 원리**: 서명 검증은 코드의 해시값을 SHA-256 같은 해시 함수로 계산한 뒤, RSA나 ECDSA 같은 공개키 알고리즘으로 서명값과 대조하는 방식으로 이루어진다.
- **작동 원리**: 불변 RoT(Root of Trust)는 칩 제조 시점에 마스크 프로그래밍된 boot ROM이거나, 제조사 공개키 해시를 저장한 OTP(One-Time Programmable) 퓨즈다.
- **작동 원리**: RoT가 1차 부트로더(First-Stage Bootloader) 서명을 검증하고, 1차 부트로더가 2차 부트로더 서명을 검증하고, 2차 부트로더가 OS 커널·펌웨어 이미지 서명을 검증하는 순서로 신뢰가 단계별로 이어진다.
- **작동 원리**: 체인의 한 단계라도 서명 검증에 실패하면 부팅을 중단하거나 복구 이미지로 전환하며, 검증되지 않은 코드는 실행하지 않는다.
- **작동 원리**: 검증에 쓰이는 공개키(또는 공개키 해시)는 퓨즈나 ROM 같은 변경 불가 또는 쓰기 보호된 하드웨어에 저장해 공격자가 임의로 키를 교체하지 못하게 한다.
- **비유**: RoT는 위조가 불가능한 최초 발급 도장이고, 각 부팅 단계는 앞 단계가 찍은 도장을 확인한 뒤에만 다음 도장을 찍는 릴레이 검증이다.
- **구체 예시**: 스마트폰 부팅 시 boot ROM이 1차 부트로더 서명을 RSA 공개키로 검증하고, 통과하면 1차 부트로더가 2차 부트로더를, 2차 부트로더가 커널 이미지를 순차 검증한다.
- **구체 예시**: 서명 검증에 실패하면 정상 OS 대신 복구 모드(recovery image)로 전환해 사용자가 재설치하도록 유도한다.
- **흔한 오해·주의점**: Secure Boot는 부팅 데이터를 암호화하는 기능이 아니라 서명으로 무결성(integrity)과 인증(authenticity)을 검증하는 기능이다.
- **흔한 오해·주의점**: Measured Boot는 서명 검증 실패 시 부팅을 중단하지 않고 TPM PCR에 측정값을 누적해 추후 원격 증명(attestation)에 활용하는 개념으로, 실패 시 즉시 중단하는 Secure Boot와는 구분된다.
- **흔한 오해·주의점**: ARM TrustZone의 Secure World는 RoT 공개키 해시 같은 민감 정보를 저장·보호하는 데 활용될 수 있으나, TrustZone 자체가 Secure Boot 절차를 대체하는 것은 아니다.

## 연결 개념
- RoT(Root of Trust) — 신뢰 체인의 불변 출발점
- TPM·Measured Boot — 서명 검증 대신 측정값을 누적해 원격 증명에 활용하는 관련 개념
- ARM TrustZone — RoT 공개키 해시를 보호하는 하드웨어 격리 영역

# 📝 【답안용】 시험 답안 템플릿

> 목적: 시험장에서 25분에 그대로 쓰는 답안 양식. 작성방식(추상표현 금지·수치·도식·문제유형 전환)을 엄격히 지킨다.
> 핵심: Secure Boot 답안은 서명 검증 절차, RoT 구조, 신뢰 체인 단계, Measured Boot와의 차이를 함께 제시한다.

## 핵심 인사이트 (3줄 요약)

> 1. **본질**: Secure Boot는 부팅 각 단계 코드를 실행 전에 디지털 서명으로 검증해 변조된 코드 실행을 차단하는 기법이다.
> 2. **가치**: 불변 RoT에서 시작해 부트로더, OS 커널까지 이어지는 신뢰 체인으로 부트킷·루트킷 변조를 방지한다.
> 3. **판단 포인트**: 기밀성이 필요하면 암호화, 무결성·인증이 필요하면 Secure Boot, 실행 중단 없는 사후 증명이 필요하면 Measured Boot를 선택한다.

## 출제 의도 및 답안 포인트

| 출제 의도 | 반드시 짚을 핵심 | 감점 회피 포인트 |
|:---|:---|:---|
| 서명 검증 원리 이해 확인 | 해시 계산 + 공개키 서명 대조, 실행 전 검증 | Secure Boot를 암호화 기술로 오서술 |
| 신뢰 체인 구조 이해 확인 | RoT, 단계별 검증 순서, 실패 시 중단 | 체인 순서 누락, 단일 단계만 서술 |
| 유사 개념 구분 확인 | Secure Boot(중단) vs Measured Boot(측정·증명) | 두 개념을 동일시하여 서술 |

> 요약: 이 문제는 서명 검증 메커니즘과 RoT 기반 신뢰 체인 구조를 정확히 구분해 짚어야 한다.

## Ⅰ. 개요 및 필요성

- 개요: 부팅 각 단계를 서명 검증 후 실행하는 신뢰 체인 기법
- 배경: 부트킷·루트킷이 OS 이전 단계에 침투해 OS 보안 통제를 우회하는 위협에서 시작
- 필요성: 불변 RoT부터 커널까지 무결성·진위를 검증해 미검증 코드 실행을 차단하기 위해 필요

## Ⅱ. 구조 및 구성요소

```text
RoT(Boot ROM/OTP Fuse) -> 1st-Stage Bootloader
  -> 2nd-Stage Bootloader
  -> OS Kernel/Firmware Image
  -> 검증 실패 시 -> Recovery Image 또는 부팅 중단
```

| 구성요소 | 역할 | 특이사항 |
|:---|:---|:---|
| RoT(Root of Trust) | 최초 서명 검증 수행하는 불변 시작점 | boot ROM 마스크 프로그래밍 또는 OTP 퓨즈 |
| 1st-Stage Bootloader | RoT 검증 통과 후 2차 부트로더 서명 검증 | 변경 불가 영역에 저장 |
| 2nd-Stage Bootloader | 커널·펌웨어 이미지 서명 검증 | 하드웨어 초기화 수행 |
| 공개키 저장소 | 검증용 공개키 또는 해시 보관 | 퓨즈·ROM 등 쓰기 보호 영역 |
| Recovery Image | 서명 검증 실패 시 대체 실행 경로 | 정상 부팅 대신 복구 모드 진입 |

> 요약: RoT에서 시작한 서명 검증이 부트로더 단계를 거쳐 OS 이미지까지 순차적으로 이어진다.

---

## Ⅲ. 동작원리 및 흐름도

```text
전원 인가 -> RoT가 1st-Stage 서명 검증
  -> 통과 시 1st-Stage가 2nd-Stage 서명 검증
  -> 통과 시 2nd-Stage가 OS 커널 서명 검증
  -> 통과 시 정상 부팅, 실패 시 중단/Recovery 전환
```

| 단계 | 처리 내용 | 검증 기준 |
|:---:|:---|:---|
| 1 | RoT가 코드 해시를 SHA-256으로 계산 | 해시 알고리즘 표준 준수 |
| 2 | 공개키(RSA/ECDSA)로 서명값 대조 | 서명-해시 일치 여부 |
| 3 | 검증 통과 시에만 다음 단계 실행 | 실행 전 검증 순서 준수 |
| 4 | 실패 시 부팅 중단 또는 Recovery 전환 | 미검증 코드 실행 차단 |

> 요약: 각 단계는 다음 단계를 실행하기 전에 반드시 서명을 검증하며, 실패하면 실행 자체를 차단한다.

## Ⅳ. 특징

| 구분 | Secure Boot | Measured Boot(참고) | 수치·표준 포인트 |
|:---|:---|:---|:---|
| 목적 | 무결성·진위 검증 후 실행 통제 | 측정값 누적 후 원격 증명 지원 | integrity/authenticity vs attestation |
| 실패 시 동작 | 부팅 중단 또는 Recovery 전환 | 부팅 계속 진행, 측정값만 기록 | 중단 여부가 핵심 차이 |
| 검증 방식 | 해시 + 공개키 서명 대조 | TPM PCR에 해시 확장(extend) | SHA-256, RSA/ECDSA |
| 보호 대상 | 실행 전 코드의 진위·무결성 | 부팅 이력의 신뢰성 있는 기록 | 사전 차단 vs 사후 검증 |

> 요약: Secure Boot는 실행 전 차단, Measured Boot는 실행 후 기록과 원격 증명이라는 점에서 목적이 다르다.

## Ⅴ. 심화 비교 및 적용 판단

| 비교 축 | 암호화(기밀성) | Secure Boot(무결성·인증) | 선택 기준 |
|:---|:---|:---|:---|
| 구조 | 데이터를 키로 변환해 노출 방지 | 서명 검증으로 실행 통제 | 도청 방지 필요 시 암호화, 변조 방지 필요 시 Secure Boot |
| 비용/성능 | 암복호화 연산 오버헤드 | 해시·서명 검증 연산 오버헤드 | 부팅 시간 목표치로 결정 |
| 운영/위험 | 키 유출 시 기밀성 붕괴 | RoT 공개키 유출 시 체인 전체 붕괴 | 키 저장 위치의 물리적 보호 수준 |

> 요약: 기밀성은 암호화, 무결성·인증은 Secure Boot로 대응하며 둘은 대체 관계가 아니라 보완 관계다.

| 리스크 | 원인 | 대응 방안 | 확인 지표 |
|:---|:---|:---|:---|
| RoT 키 유출 | 퓨즈 관리 부실, 제조 공정 노출 | 하드웨어 격리, 접근 통제 강화 | 키 접근 로그, 감사 기록 |
| 신뢰 체인 우회 | 중간 단계 검증 누락 구현 결함 | 전 단계 서명 검증 코드 리뷰 | 취약점 스캔, 코드 감사 결과 |
| 복구 경로 악용 | Recovery Image 자체 미서명 | Recovery Image도 서명 검증 대상에 포함 | Recovery 서명 검증 로그 |

> 요약: Secure Boot 운영은 RoT 키 보호, 전 단계 검증 누락 방지, Recovery 경로 서명 검증으로 통제한다.

| 점검 항목 | 목표 기준 | 측정 방법 |
|:---|:---|:---|
| 검증 정합성 | 모든 부팅 단계 서명 검증 통과율 100% | 부팅 로그, 검증 이벤트 기록 |
| 실패 대응 | 검증 실패 시 부팅 중단/Recovery 전환 100% | 페일 인젝션 테스트 |
| 키 관리 | RoT 공개키 접근 이력 0건 이상 감사 | 접근 로그, 하드웨어 감사 |

> 요약: 도입 후 성공 여부는 서명 검증 통과율, 실패 시 차단 동작, 키 접근 감사 이력으로 판단한다.

## Ⅵ. 실무 적용 및 결론

**적용 방안 3개 (필수 — 단계별 또는 항목별):**
1. RoT 공개키 해시는 OTP 퓨즈나 boot ROM 같은 쓰기 보호 영역에 저장해 임의 키 교체를 원천 차단함
2. 부트로더부터 OS 커널까지 전 단계 서명 검증을 코드 리뷰와 페일 인젝션 테스트로 검증해 우회 가능성을 제거함
3. Recovery Image도 서명 검증 대상에 포함하고, 검증 실패 시 미검증 코드가 실행되지 않도록 강제함

**결론 (2줄):**
- 기술사 판단: 기밀성이 목적이면 암호화, 변조 방지·실행 통제가 목적이면 Secure Boot를 적용함
- 향후 방향: TPM 기반 Measured Boot 및 원격 증명과 결합해 부팅 무결성을 사후 검증까지 확장해야 함
