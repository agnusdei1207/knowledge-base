# Secure Boot 보안 부팅 (Secure Boot)

## 미리 알고가기

- Secure Boot: 부팅 단계마다 다음 단계 코드의 무결성과 출처를 검증한 뒤 실행하는 보안 절차임
- Root of Trust: 신뢰 루트(Root of Trust)는 변경되기 어려운 읽기 전용 메모리(Read-Only Memory, ROM), 키, 하드웨어 보안 영역처럼 신뢰의 시작점이 되는 요소임
- Chain of Trust: ROM, 부트로더, 펌웨어, 커널이 단계적으로 서로를 검증하는 신뢰 연결임
- 서명 검증: 코드 해시와 공개키 암호 서명을 확인해 승인된 이미지만 실행하는 방식임
- Rollback Protection: 오래된 취약 버전으로 되돌리는 공격을 막는 버전 검증 기능임

## Ⅰ. 개요

- **정의/개념**: Secure Boot는 전원이 켜진 직후부터 ROM, 부트로더, 펌웨어, 커널, 운영체제(Operating System, OS) 이미지가 코드 무결성·서명 키·버전·부팅 정책 검증을 순차적으로 통과해야 실행되도록 하는 부팅 신뢰 체계임
- **배경/필요성**: 부팅 초기 코드는 OS 보안 기능보다 먼저 실행되므로 이 단계가 변조되면 백신, 접근 통제, 로그가 우회될 수 있음. 따라서 가장 이른 시점에서 신뢰할 수 있는 코드만 실행되도록 해야 함
- **비유**: 건물 경비가 입구에서 방문증을 확인하고, 각 구역 문도 이전 구역에서 확인된 사람만 통과시키는 절차와 같음

| 출제 의도 | 반드시 짚을 핵심 | 감점 회피 포인트 |
|:---|:---|:---|
| 부팅 신뢰 체계 설명 | Root of Trust, Chain of Trust, 서명 검증, rollback 방지 | 단순 비밀번호 부팅으로 설명 |
| 펌웨어 보안 적용 판단 | 키 관리, 업데이트, 복구, attestation | 암호화와 무결성 검증 혼동 |

> 요약: Secure Boot는 부팅 단계별 코드 실행 전에 서명과 버전을 확인해 신뢰 체인을 유지하는 보안 메커니즘임.

## Ⅱ. 특징 및 비교

| 판단 기준 | 일반 부팅 | Secure Boot |
|:---|:---|:---|
| 실행 조건 | 저장 장치의 부트 코드를 순서대로 로드함 | 각 단계가 다음 단계 이미지의 서명과 정책을 검증함 |
| 보호 대상 | 부팅 성공과 장치 초기화 중심 | 펌웨어, 부트로더, 커널, OS 무결성 보호 |
| 공격 대응 | 부트킷과 변조 펌웨어 탐지가 어려움 | 미승인 코드 실행과 롤백 공격을 차단함 |
| 운영 요구 | 이미지 배포가 비교적 단순함 | 키 관리, 서명 절차, 복구 경로가 필수임 |

> 요약: Secure Boot는 부팅 흐름에 암호학적 검증을 추가해 초기 실행 코드의 신뢰성을 확보함.

- **검증 기준**: 해시만 확인하면 공격자가 해시도 바꿀 수 있으므로 신뢰 키 기반 서명 검증이 필요함
- **키 기준**: 루트 키는 하드웨어 보호 영역에 저장하고 키 교체·폐기 절차를 준비해야 함
- **운영 기준**: 업데이트 실패, 전원 차단, 키 분실 시 복구할 수 있는 안전한 fallback 구조가 필요함

## Ⅲ. 구성요소/구조

```text
+----------+      +----------+      +----------+      +----------+
| Boot ROM | ---> | Bootldr  | ---> | Firmware | ---> | OS Kernel|
+----+-----+      +----+-----+      +----+-----+      +----+-----+
     |                 |                 |                 |
     v                 v                 v                 v
+----------+      +----------+      +----------+      +----------+
| Root Key |      | Verify   |      | Version  |      | Policy   |
+----------+      +----------+      +----------+      +----------+
```

| 구성요소 | 설명 | 비유 |
|:---|:---|:---|
| Boot ROM | 변경이 어려운 초기 코드로 루트 키와 첫 검증 로직을 포함함 | 첫 검문소 |
| 루트 키 | 승인된 제조사 또는 운영자의 부팅 이미지를 검증하는 신뢰 기준임 | 공식 인장 |
| 부트로더 | 하드웨어 초기화와 다음 단계 펌웨어·커널 검증을 수행함 | 구역 안내자 |
| 서명된 이미지 | 해시와 서명, 버전, 정책 메타데이터가 포함된 실행 코드임 | 봉인된 문서 |
| 복구·정책 영역 | 롤백 방지 카운터, fallback 이미지, 부팅 허용 정책을 관리함 | 비상 매뉴얼 |

> 요약: Secure Boot는 변경 어려운 ROM과 루트 키에서 시작해 단계별 서명 검증과 복구 정책으로 신뢰 체인을 유지함.

### 원리/흐름도

```text
+----------+      +----------+      +----------+      +----------+
| Power On | ---> | Verify   | ---> | Load Next| ---> | Enforce  |
| ROM      |      | Image    |      | Stage    |      | Policy   |
+----------+      +----------+      +----------+      +----------+
```

1. **루트 초기화**: Boot ROM이 하드웨어 루트 키와 보안 설정을 읽고 첫 부트로더 이미지를 찾음
2. **이미지 검증**: 이미지 해시, 서명, 인증서 체인, 버전 카운터를 확인함
3. **다음 단계 실행**: 검증된 부트로더가 펌웨어, 커널, OS 이미지를 같은 방식으로 검증하고 로드함
4. **정책 적용·복구**: 검증 실패 시 부팅 중단, 복구 이미지 전환, 로그 기록, 원격 검증을 수행함

> 요약: Secure Boot는 전원 인가 후 ROM에서 시작해 각 단계 이미지 검증과 정책 적용을 반복하며 부팅을 진행함.

## Ⅳ. 문제점 및 개선방안

- **P1 키 관리 실패**: 서명 키가 유출되거나 루트 키 교체 절차가 없으면 공격자 코드도 신뢰된 코드처럼 실행될 수 있음
- **P1 대응**: 하드웨어 보안 모듈(Hardware Security Module, HSM) 기반 코드 서명, 키 권한 분리, 키 폐기·교체 절차를 운영함 (확인: 서명 감사 로그)
- **P2 롤백 공격**: 서명은 유효하지만 오래된 취약 버전으로 되돌리면 알려진 취약점이 다시 노출됨
- **P2 대응**: 보안 버전 카운터와 rollback protection을 적용함 (확인: 구버전 이미지 부팅 차단 시험)
- **P3 업데이트·복구 실패**: 검증 정책이 엄격해도 업데이트 중 전원 차단이나 이미지 손상 시 장치가 부팅 불능 상태가 될 수 있음
- **P3 대응**: A/B 파티션, 안전 복구 모드, 전원 차단 내성 업데이트를 설계함 (확인: 실패 주입 업데이트 시험)

> 요약: Secure Boot 개선은 암호 검증뿐 아니라 키 수명주기, rollback 방지, 안전한 업데이트 복구 구조를 포함해야 함.

## Ⅴ. 실무 적용 사례

| 적용 영역 | 적용 방식 | 확인 지표 |
|:---|:---|:---|
| 사물인터넷(Internet of Things, IoT) 게이트웨이 | ROM 루트 키가 부트로더와 커널 서명을 검증하고 실패 시 복구 파티션으로 전환함 | 변조 이미지 차단, 복구 부팅 성공률, 롤백 차단 시험 |
| 차량 전자 제어 장치(Electronic Control Unit, ECU) | 제조 단계에서 키를 주입하고 서명된 펌웨어만 업데이트되도록 Secure Boot와 A/B 업데이트를 결합함 | 서명 감사 로그, 전원 차단 업데이트 성공률, 구버전 부팅 차단 |
| 서버 펌웨어 | 펌웨어와 부트로더 검증 결과를 measured boot와 원격 검증에 연결해 공급망 변조를 탐지함 | 검증 로그 무결성, 원격 attestation 성공률, 키 폐기 시험 |

> 요약: Secure Boot는 부팅 차단만이 아니라 키 주입, 업데이트, 복구, 검증 로그까지 운영 지표로 확인해야 함.

## Ⅵ. 결론

- **발전 방향**: Secure Boot는 measured boot, 원격 검증, 소프트웨어 자재 명세서(Software Bill of Materials, SBOM), 장치 식별과 결합해 사물인터넷(Internet of Things, IoT)·차량·서버의 장치 신뢰 증명 기반으로 확대됨
- **기술사적 판단**: 신뢰 루트, 키 계층, 부팅 단계별 서명, 롤백 카운터, 복구 파티션, 제조 키 주입 절차를 함께 설계함; 변조 이미지 차단, 롤백 공격, 키 폐기, 복구 부팅, 전원 차단 업데이트, 디버그 잠금 해제 상태를 테스트함; Secure Boot는 부팅 무결성만 보장하므로 런타임 검증, 보안 업데이트, 키 유출 대응, 공급망 검증과 함께 적용해야 함
- **기술사 제언**: Secure Boot는 암호화 기능이 아니라 신뢰 루트에서 시작해 단계별 무결성을 확인하는 부팅 체인으로 설명함
