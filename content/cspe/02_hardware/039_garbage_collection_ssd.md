# 📖 【암기용】 개념 완전 이해

> 목적: SSD가 쓰다 보면 왜 점점 느려지는지, 그리고 컨트롤러가 어떤 기준으로 청소할 Block을 고르고 그 청소가 얼마나 손해를 유발하는지 수치로 완전히 이해하게 만든다.

## 한눈에
- **개요**: **가비지 컬렉션(GC)**은 낸드 플래시에서 무효화된(Invalid) 찌꺼기 데이터가 쌓인 Block을 찾아 유효 데이터만 대피시킨 뒤 Block 전체를 소거(Erase)하여 빈 Block(Free Block)을 되찾는 SSD 컨트롤러의 백그라운드 공간 회수 작업이다.
- **왜 필요한가**: FTL의 Out-of-place Update 때문에 데이터를 고칠 때마다 예전 자리는 지워지지 않고 '무효' 상태로 쌓이기만 한다. 빈 Block이 부족해질 때까지 이를 방치하면, 정작 새 데이터를 쓰려는 순간 빈 공간이 없어 SSD가 그 자리에서 급하게 청소를 시작해야 하고, 이때 호스트 입출력이 통째로 멈춘다. 이를 막기 위해 여유가 있을 때 미리 청소해 두는 것이 GC다.
- **핵심 직관**: Block(서랍장) 안에 쓰레기 서류(Invalid) 9장과 진짜 서류(Valid) 1장이 섞여 있다. 서랍 안에서 서류 한 장만 골라 태울 수는 없으므로(Block 단위 소거), 진짜 서류 1장을 다른 빈 서랍으로 옮겨 놓은 뒤, 원래 서랍을 통째로 태워 완전히 빈 서랍을 만든다.

## 핵심 용어 정리 (내부에 등장하는 것들)

| 용어 | 의미 | 비유 |
|:---|:---|:---|
| Valid Page | 최신 데이터가 담긴 유효한 Page. GC가 반드시 대피시켜야 함 | 서랍 속 진짜 서류 |
| Invalid Page | 덮어쓰기·삭제로 버려진 찌꺼기 Page | 서랍 속 쓰레기 서류 |
| Free Block | 완전히 소거되어 새 데이터를 바로 쓸 수 있는 빈 Block | 텅 빈 서랍 |
| Victim Block | GC가 청소 대상으로 선택한 Block | 오늘 태울 서랍 |
| Migration (이주) | Victim Block의 Valid Page를 다른 Free Block으로 복사하는 과정 | 진짜 서류만 옮겨 담기 |
| Utilization (u) | Block 안에서 Valid Page가 차지하는 비율 | 서랍 속 진짜 서류 비율 |
| WAF (Write Amplification Factor) | 호스트가 요청한 쓰기량 대비 낸드에 실제 기록된 양의 배율 | 서류 1장 정리하려다 몇 장을 더 옮기는 손해율 |
| Background GC / Foreground GC | 유휴 시간에 미리 도는 GC / 빈 공간이 없어 쓰기 요청 도중 강제로 도는 GC | 손님 없을 때 청소 / 손님 앞에서 급하게 청소 |
| TRIM | OS가 "이 데이터는 이제 안 쓴다"를 FTL에 미리 알려주는 명령 | 서류를 버렸다고 미리 알려주는 메모 |

## 깊이 이해

### 왜 GC가 필요한가 — Page/Block 단위 불일치의 결과 (배경)
- Out-of-place Update가 반복되면 예전 Page는 Invalid로 표시된 채 그대로 낸드 공간을 차지한다. 낸드는 Page 단위로는 지울 수 없고 Block 단위로만 지울 수 있으므로(Erase-before-write), Invalid Page 하나를 없애려 해도 그 Page가 속한 Block 전체를 손봐야 한다.
- 예: Block 하나가 Page 100개로 구성되어 있다고 하면, 그중 90개가 Invalid이고 10개만 Valid인 Block(Utilization 10%)을 그대로 두면 90개 분량의 공간이 영구히 낭비된다. GC는 이런 Block을 찾아 Valid 10개만 옮기고 Block 전체(100개 분량)를 회수한다.

### Victim Block 선정 — Greedy 알고리즘을 수치로 이해
- 가장 단순한 방법은 **Greedy**다: Invalid Page가 가장 많은(=Utilization이 가장 낮은) Block을 Victim으로 고른다. Utilization 10%(Valid 10/100)인 Block과 Utilization 90%(Valid 90/100)인 Block이 있다면, Greedy는 옮길 데이터가 적은 10% Block을 먼저 청소한다.
- 실무에서는 여기에 "그 Block이 얼마나 오래됐는가(age)"까지 반영하는 **Cost-Benefit** 공식을 쓴다: `이익 = age × (1-u) / (2u)` (u는 Utilization). u가 작을수록(청소 이득 큼), age가 클수록(콜드 데이터라 재사용 가능성 낮음) 이 값이 커져 우선 청소 대상이 된다.

### WAF를 수치로 계산해 보기
- WAF는 "이 Block을 청소해서 새로 확보한 빈 공간 1단위를 얻기 위해 낸드에 실제로 몇 단위를 더 썼는가"의 비율이며, Utilization u인 Block을 청소할 때 WAF ≈ 1 / (1 - u)로 근사된다.
- Block이 Page 100개로 구성되고 Utilization 50%(Valid 50개)인 상태에서 청소하면, Valid 50개를 옮겨야 그 Block이 회수된다. 이때 새로 확보되는 순수 여유 공간은 50개(=100-50)이므로 WAF = 1/(1-0.5) = 2다. 즉 SSD 내부에는 호스트가 요청한 것의 2배가 기록된다.
- Utilization 90%(Valid 90개)면 WAF = 1/(1-0.9) = 10, Utilization 99%면 WAF = 1/(1-0.99) = 100까지 치솟는다. SSD 저장공간이 꽉 찰수록 GC 대상 Block들의 평균 Utilization이 올라가므로, 빈 공간이 부족해질수록 WAF가 기하급수적으로 증가하는 이유가 여기에 있다.
- 반대로 Utilization이 0%(전부 Invalid)인 Block은 옮길 Valid가 없어 WAF = 1/(1-0) = 1(증폭 없음)로, GC 입장에서 가장 이상적인 Victim이다.

### Background GC vs Foreground GC — 언제 도는지 수치로 이해
- Background GC는 호스트 입출력이 없는 유휴 구간에 컨트롤러가 스스로 판단해 Free Block 비율을 일정 수준(예: 전체의 10~20%) 이상으로 미리 채워 놓는다. 사용자는 지연을 못 느낀다.
- Foreground GC는 Free Block이 바닥나(예: 1% 미만) 호스트의 쓰기 요청을 당장 처리할 수 없을 때, 그 요청 파이프라인 안에서 강제로 발동한다. 평소 수십 마이크로초(µs)이던 쓰기 응답 시간이 이때는 수 밀리초(ms) 이상으로 치솟는 지연 스파이크(Latency Spike)가 발생한다 — 이것이 SSD가 꽉 찼을 때 화면이 순간 멈추는 프리징의 정체다.

### 비유와 흔한 오해
- **비유**: 테트리스에서 줄 중간중간 구멍이 뚫려 있으면 그 줄만 쏙 지울 수 없어, 멀쩡한 블록은 위로 옮겨 놓고 맨 아래 줄을 통째로 지우는 노가다와 같다.
- **오해 1**: "파일을 삭제(Shift+Del)하면 그 즉시 GC가 실행돼 낸드에서 지워진다." → 틀렸다. 삭제는 OS가 L2P 매핑에서 해당 항목을 지우는 것뿐이고, 낸드의 실제 데이터는 Invalid로 표시된 채 남아 있다가 GC가 도래해야 실제로 소거된다.
- **오해 2**: "GC는 자바(Java) 같은 언어의 가비지 컬렉션과 같은 개념이다." → 이름만 같을 뿐 완전히 다르다. 언어의 GC는 메모리 상의 미사용 객체를 논리적으로 회수하는 소프트웨어 개념이고, SSD의 GC는 물리적으로 Block을 소거해 낸드 수명(P/E Cycle)을 소모하는 하드웨어 동작이다.

## 연결 개념
- FTL의 Out-of-place Update와 L2P 매핑 — 038_ssd_controller_ftl (GC가 회수하는 Invalid Page가 생기는 원인)
- TRIM 명령 — 호스트가 미리 Invalid를 알려줘 Migration 대상에서 제외시켜 WAF를 낮추는 힌트
- Over-Provisioning — Utilization을 구조적으로 낮게 유지시켜 Victim Block의 WAF를 줄이는 여유 공간 확보 전략

# 📝 【답안용】 시험 답안 템플릿

> 목적: 시험장에서 25분에 그대로 쓰는 답안 양식. 

## 핵심 인사이트 (3줄 요약)

> 1. **본질**: SSD 가비지 컬렉션(GC)은 NAND 플래시의 덮어쓰기 불가(Erase-before-write) 제약으로 인해 발생한 무효(Invalid) 페이지를 회수하여, 새로운 쓰기 공간(Free Block)을 확보하는 FTL의 핵심 알고리즘이다.
> 2. **가치**: 쓰레기가 가득 찬 블록을 삭제하기 위해 유효(Valid) 데이터만 추출해 새 블록으로 이주(Migration)시키고 기존 블록을 소거(Erase)함으로써, 임의 쓰기(Random Write) 시의 스토리지 성능 저하(Freezing)를 방지한다.
> 3. **판단 포인트**: GC는 필수불가결하지만 데이터를 불필요하게 이동시켜 쓰기 증폭(WAF)을 유발하고 수명을 갉아먹으므로, TRIM 명령어 지원과 오버프로비저닝(OP) 공간 확보를 통한 GC 최적화가 필수적이다.

## 출제 의도 및 답안 포인트

| 출제 의도 | 반드시 짚을 핵심 | 감점 회피 포인트 |
|:---|:---|:---|
| NAND 플래시의 물리적 속성과 공간 회수(GC) 원리 연계 | 읽기/쓰기(Page) 단위와 지우기(Block) 단위 불일치 | 자바(Java) 메모리의 가비지 컬렉션(S/W)과 혼동하여 서술하는 치명적 오류 |
| GC 수행 시 수반되는 비용과 성능 저하 문제 파악 | 유효 데이터 복사(Migration) 비용, 쓰기 증폭(WAF) 증가 | 단순히 "찌꺼기를 지운다"고만 적고, "유효 데이터 이동 복사" 과정을 누락 |

> 요약: SSD의 GC는 S/W 메모리 회수와 달리 "막대한 물리적 낸드 수명(P/E Cycle) 낭비와 성능 병목"을 동반하는 뼈아픈 양날의 검임을 반드시 서술해야 한다.

## Ⅰ. 개요 및 필요성

- 정의: SSD 내에서 무효화(Invalid)된 데이터(찌꺼기)가 점유한 블록을 식별하고, 잔여 유효 데이터를 대피시킨 후 블록 단위로 소거(Erase)하여 가용 공간(Free Block)을 회수하는 FTL 펌웨어 루틴
- 배경: NAND 플래시는 Page(4KB~16KB) 단위로 읽기/쓰기가 가능하나, 지우기(Erase)는 수백 개의 Page가 묶인 거대한 Block(수 MB) 단위로만 수행되는 하드웨어 구조적 비대칭성 존재
- 필요성: Out-of-place update(우회 덮어쓰기)로 인해 버려진 무효 페이지들이 플래시 공간을 잠식하는 것을 막고, 새로운 호스트 I/O 기록을 위한 깨끗한 빈 블록 풀(Free Block Pool)을 상시 유지해야 함

## Ⅱ. 공간 회수 메커니즘 및 블록의 생명 주기

```text
[NAND 플래시 블록 내부의 데이터 상태 (페이지 단위)]
* Valid (유효)  : 최신 데이터. 절대 지워지면 안 됨 (FTL이 L2P 맵핑 유지)
* Invalid(무효): 과거 데이터 찌꺼기. OS가 삭제했거나 덮어쓰기로 버려진 쓰레기
* Free (가용)   : 완전히 백지상태(소거됨). 새로운 데이터를 즉시 기록 가능
```

| GC 수행 단계 | FTL 컨트롤러의 핵심 제어 동작 | 병목 및 오버헤드 요인 |
|:---:|:---|:---|
| 1. Victim 선택 | 무효(Invalid) 페이지가 가장 많은 블록(Victim Block)을 Greedy 알고리즘 기반으로 선정 | 무효 페이지 개수 및 P/E Cycle을 동시 고려하는 스케줄링 연산 부하 |
| 2. Migration | 희생 블록 내 소수의 유효(Valid) 페이지를 읽어, 다른 깨끗한 Free Block으로 복사(Copy) 이동 | **유효 데이터 복사(I/O)** 로 인한 쓰기 증폭(WAF) 및 시스템 낸드 대역폭 낭비 |
| 3. Erase (소거) | 대피가 끝난 기존 희생 블록 전체에 강한 고전압을 가해 완전히 소거(Erase)하여 Free Block화 | 소거 단위(수 MB) 지연으로 인한 락(Lock) 발생 |
| 4. Mapping 갱신 | 이동된 유효 데이터의 새로운 물리 주소(PBA)를 FTL의 L2P 테이블(DRAM)에 업데이트 | - |

> 요약: GC의 진짜 공포는 찌꺼기를 지우는 데 있는 게 아니라, 같이 섞여 있는 '진짜 데이터(Valid)'를 다른 방으로 옮겨 적느라 수명과 시간을 이중으로 낭비한다는 데 있다.

## Ⅲ. 동작원리 및 GC 마이크로 흐름도

```text
[SSD 컨트롤러 주도의 가비지 컬렉션(GC) 공간 회수 흐름]
+-------------------------------------------------+
| 희생 블록 A: [Valid 1] [Invalid] [Valid 2]      |
| 희생 블록 B: [Invalid] [Invalid] [Valid 3]      |
+-------------------------------------------------+
          (GC 알고리즘 발동: Valid 데이터만 복사 이동)
                 =======> [ 빈 블록 C 에 순차 기록 ] -> [Valid 1][Valid 2][Valid 3] 완성
          (이주 완료 후, 희생 블록 소거 명령)
                 =======> [ 블록 A 소거! ], [ 블록 B 소거! ] -> 완벽한 Free Block 2개 획득!
```

| 비용 지표 | GC 발동 시나리오 | 동작 효과 | 시스템 성능 영향 (WAF) |
|:---:|:---|:---|:---|
| 최상의 경우 | 희생 블록 내 데이터가 100% 무효(Invalid) 상태일 때 | Valid 데이터 이동(Copy) 없이 즉각 Erase 소거 | WAF 상승 없음. 속도 저하 제로. (매우 드문 이상적 상황) |
| 최악의 경우 | 빈 공간 고갈 시 (디스크 99% Full 상태) | 무효 데이터 1개를 지우기 위해 유효 데이터 99개를 옮겨 적어야 함 | 호스트 I/O 멈춤(프리징). 쓰기 증폭률 10배 폭증 및 SSD 수명 급감 |

> 요약: "GC 효율 = 빈 공간(Free Space)의 여유율"이다. SSD를 꽉 채워 쓰면 컴퓨터가 미친 듯이 느려지고 칩이 빨리 죽는 이유가 바로 GC 복사 오버헤드 폭발 때문이다.

## Ⅳ. 심화 비교: 백그라운드(BGC) vs 포그라운드(FGC) GC 대조표

| 비교 축 | Background GC (백그라운드 GC) | Foreground GC (포그라운드 / On-demand GC) | 성능 튜닝 판단 기준 |
|:---|:---|:---|:---|
| 발동 조건 | 호스트 I/O가 없는 **유휴 상태(Idle)** 일 때 | SSD 공간이 고갈되어 **당장 쓰기(Write) 요청을 처리할 수 없을 때** | 펌웨어 스케줄링 |
| 동작 주체 | SSD 컨트롤러가 백그라운드로 남몰래 수행 | 호스트의 쓰기 요청 파이프라인 안에서 강제 수행 | 사용자 체감 |
| 시스템 성능 | 사용자 체감 성능 저하 없음 | **치명적 성능 저하 (사용자 화면 프리징)** | 최악의 Latency 스파이크 발생 |
| 배터리 소모 | 대기 상태(Idle)에서 배터리를 갉아먹음 | I/O 수행 시 동반 소모 | 모바일 기기(UFS) 전원 정책 |

> 요약: 우수한 컨트롤러 펌웨어는 윈도우(OS)가 가만히 쉴 때(BGC) 최대한 쓰레기 청소를 끝내놓아, 손님이 올 때 당황해서 청소(FGC)하는 참사를 원천 봉쇄한다.

## Ⅴ. 제약 사항 및 쓰기 증폭(WAF) 억제 방안

| 리스크 | 발생 원인 | 아키텍처 대응 방안 (OS 연계) | 극복 원리 및 효과 |
|:---|:---|:---|:---|
| 쓰기 증폭(WAF) | 호스트는 1MB를 썼는데 FTL이 GC 이동(Migration) 하느라 낸드에 실제 5MB를 기록해 수명 갉아먹음 | **TRIM (Discard) 명령어 지원** | OS가 파일을 삭제(Shift+Del)하면, 즉각 FTL에게 "저 LBA 주소 데이터는 쓰레기(Invalid)니 GC 때 대피(Copy)시키지 말고 걍 지워"라고 힌트를 줌 (WAF 극적 억제) |
| 희생 블록 고갈 | 빈 블록이 적어 억지로 Valid가 많은 블록을 희생양으로 삼아 이동(Copy) 오버헤드 폭증 | **Over-Provisioning (초과 할당)** | 컨트롤러가 제조 시 전체 용량의 7~28%를 사용자에게 안 보이고 숨겨둠. GC를 쾌적하게 수행할 절대적 빈방 확보 (엔터프라이즈 필수) |
| 데이터 핫/콜드 혼재| 한 블록 안에 자주 지워지는 핫(Hot) 데이터와 죽을 때까지 냅두는 콜드(Cold) 파일이 섞여 GC 꼬임 완벽 | **데이터 성질 분리 매핑 (Hot/Cold Separating)** | FTL이 쓰기 빈도를 분석해 OS 파일(Cold)과 캐시 임시 파일(Hot)을 애초에 다른 블록에 몰아서 써줌 |

> 요약: GC 최적화의 궁극적 해법은 하드웨어 단독이 아니라, 윈도우/리눅스 OS가 파일시스템 삭제 정보를 컨트롤러에게 즉각 통보하는 TRIM 프로토콜의 표준화(SATA/NVMe)로 완성되었다.

## Ⅵ. 실무 적용 및 결론

**적용 방안 3개:**
1. DBMS 전용 고성능 NVMe 설정 (Over-Provisioning 강제 할당): Oracle, MySQL 등 무작위 쓰기(Random Write)와 덮어쓰기가 폭발적으로 발생하는 DB 서버에서는 공장 초기화 상태의 SSD 파티션을 잡을 때, 의도적으로 전체 용량의 20%~30%를 미할당 상태(Unallocated)로 남겨두어 컨트롤러가 이를 GC 전용 워크스페이스(OP)로 전용하게 만들어 I/O 지연 스파이크(Latency Spike)를 완전 차단
2. RAID 및 ZFS 환경에서의 TRIM(UNMAP) 스케줄링 활성화: 소프트웨어 RAID 또는 ZFS 파일 시스템 구축 시 기본적으로 TRIM 패스스루(Pass-through)가 막히는 경우가 많아, `/etc/fstab`에 `discard` 옵션을 명시하거나 `fstrim.timer`를 주 1회 백그라운드 크론(Cron)으로 돌려 일괄적인 Invalid Mark 갱신 체계 확립
3. Zoned Namespace(ZNS) 아키텍처 도입: 페타바이트급 미디어 스트리밍 서버(CDN)나 클라우드 스토리지 구성 시, FTL의 멍청한 GC 오버헤드를 아예 회피하기 위해 호스트(OS)가 낸드 플래시 존(Zone) 단위로 직접 순차 쓰기(Sequential Write)를 통제하는 ZNS 인터페이스 기반의 펌웨어리스(Firmware-less) 아키텍처 연계

**결론 (2줄):**
- 기술사 판단: 가비지 컬렉션(GC)은 NAND 플래시의 물리적 한계(Erase-before-write)를 극복하기 위한 필수불가결한 펌웨어 로직이나, 필연적으로 시스템 대역폭 낭비와 수명 단축(WAF)을 동반하는 철저한 트레이드오프 메커니즘이다.
- 향후 방향: H/W 컨트롤러가 단독으로 낑낑대며 예측하던 블랙박스형 GC 시대는 종말하고, 애플리케이션(DBMS, OS)이 스토리지의 물리 구조를 인지하여 직접 배치(Placement)를 지시하는 방향(ZNS, FDP)으로 스토리지 패러다임이 전면 시프트하고 있다.
