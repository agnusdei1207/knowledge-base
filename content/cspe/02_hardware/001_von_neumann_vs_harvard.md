# 📖 【암기용】 개념 완전 이해

> 목적: 폰 노이만과 하버드 구조의 차이가 실제 파이프라인 성능에 얼마나(수치로) 영향을 주는지 처음 보는 사람도 완전히 이해하게 만든다. (구조·버스·역사적 정의는 `001_von_neumann_harvard_architecture.md`에서 다룬다.)

## 한눈에
- **개요**: **명령어 파이프라인(Instruction Pipeline)**에서 폰 노이만 구조와 하버드 구조가 만들어내는 **구조적 해저드(Structural Hazard)**의 유무를 **CPI(Cycles Per Instruction)**·**IPC(Instructions Per Cycle)** 수치로 비교하는 것이 이 키워드의 핵심이다.
- **왜 필요한가**: CPU 클럭 속도는 메모리 접근 속도보다 훨씬 빨리 발전해왔고, 그 격차를 메우려면 파이프라이닝으로 CPI를 1에 가깝게 만들어야 한다. 그런데 단일 버스(폰 노이만)는 그 자체가 파이프라인을 멈추게 하는 구조적 원인이 된다.
- **핵심 직관**: 편도 1차선에서는 앞차(데이터 접근)가 지나가는 동안 뒤차(다음 명령어 인출)가 못 지나가 정체(스톨)가 생기고, 왕복 2차선(하버드)에서는 이 정체가 생기지 않는다.

## 핵심 용어 정리

| 용어 | 의미 | 비유 |
|:---|:---|:---|
| 명령어 파이프라인 | 명령어 처리를 IF-ID-EX-MEM-WB 등 여러 단계로 쪼개 겹쳐 실행하는 기법 | 세탁-건조-접기를 겹쳐 돌리는 공장 라인 |
| IF/ID/EX/MEM/WB | 인출/해독/실행/메모리접근/저장, 5단계 파이프라인의 각 스테이지 | 라인의 각 작업대 |
| 구조적 해저드(Structural Hazard) | 서로 다른 명령어가 같은 하드웨어 자원(버스·메모리 포트)을 동시에 쓰려다 생기는 충돌 | 세탁기 1대를 두 사람이 동시에 쓰려는 것 |
| 스톨/버블(Stall/Bubble) | 해저드를 해소하려고 파이프라인을 강제로 1클럭 이상 멈추는 것 | 라인이 잠깐 서는 빈 슬롯 |
| CPI(Cycles Per Instruction) | 명령어 1개를 처리하는 데 드는 평균 클럭 수 — 낮을수록 좋음 | 제품 1개를 만드는 데 걸리는 평균 공정 수 |
| IPC(Instructions Per Cycle) | 클럭 1회당 처리하는 명령어 수(CPI의 역수 개념) — 높을수록 좋음 | 공정 1회당 나오는 제품 수 |
| 처리량(Throughput) | 단위 시간당 완료하는 명령어(작업) 수 | 시간당 생산량 |

## 깊이 이해

### 구조적 해저드가 실제로 발생하는 지점
- 5단계 파이프라인에서 명령어 1은 사이클 1에 IF, 사이클 4에 MEM(데이터 접근) 단계에 들어간다. 같은 타이밍표로 명령어 4는 사이클 4에 IF(명령어 인출) 단계에 들어간다.
- 명령어와 데이터를 같은 메모리·같은 버스로 접근하는 폰 노이만 구조라면, 사이클 4에 "명령어 1의 데이터 접근"과 "명령어 4의 명령어 인출"이 동시에 같은 메모리 포트를 요구한다 — 이것이 구조적 해저드다.
- 하드웨어는 둘 중 하나(보통 명령어 인출)를 1클럭 늦춰야 하고, 그 늦춘 자리가 파이프라인 버블(빈 슬롯)이 된다.

### 수치로 보는 성능 차이 — CPI 저하 계산 (워크드 예제)
- 가정(전형적인 명령어 구성비, 컴퓨터구조 교재 기준 참고치): 전체 명령어 중 load/store(메모리 접근 명령어) 비중 약 30%.
- **폰 노이만(단일 메모리 포트)**: MEM 단계를 쓰는 load/store 명령어가 실행될 때마다 뒤따르는 명령어의 IF 단계와 충돌해 1사이클 스톨이 발생한다고 하면 — 명령어 100만 개 실행 시 load/store 30만 개 × 1사이클 스톨 = 30만 사이클 추가. 총 사이클 = 100만 + 30만 = 130만 → **CPI = 1.3**.
- **하버드(명령어 버스·데이터 버스 분리)**: 이 충돌이 원천적으로 없어 다른 해저드가 없다고 가정하면 총 사이클 = 100만 → **CPI = 1.0**.
- 1GHz(1클럭 = 1ns) 기준으로 환산하면, 같은 100만 개 명령어를 처리하는 데 폰 노이만은 1.3ms, 하버드는 1.0ms가 걸려 **하버드가 약 23% 더 빠르다**. (실제 CPU는 스톨을 캐시·버퍼링으로 상당 부분 완화하므로 이 수치는 방향성을 보여주는 단순화한 예제다.)

### 왜 실제 CPU에서는 이 병목이 거의 안 보이는가
- 메인 메모리(DRAM)는 여전히 폰 노이만처럼 통합돼 있지만, CPU 코어가 매 클럭 실제로 접근하는 지점은 L1 캐시다. 대부분의 상용 파이프라인 CPU는 L1을 I-Cache/D-Cache로 분리해 이 구조적 해저드를 캐시 단계에서 원천 차단한다.
- 이것이 사실상 "파이프라인 CPU는 예외 없이 수정 하버드 구조를 쓴다"고 말하는 이유다 — 1985년 출시된 초기 상용 RISC 칩 중 하나인 MIPS R2000도 이미 명령어·데이터 캐시를 분리해 이 문제를 해결했다.

### 트레이드오프 — 하버드가 항상 이기는 것은 아니다
- 하버드는 명령어 메모리·데이터 메모리 용량을 설계 시점에 물리적으로 나눠야 한다. 프로그램은 크고 데이터는 작은 경우에도 데이터 메모리 여유분을 명령어 쪽으로 못 옮겨 쓴다(용량 경직성) — 폰 노이만은 하나의 공간을 유연하게 나눠 쓸 수 있다.
- self-modifying code·JIT 컴파일처럼 실행 중에 데이터로 코드를 만들어 바로 실행해야 하는 경우, 데이터 영역과 명령어 영역이 아예 분리된 순수 하버드에서는 이 흐름 자체가 성립하기 어렵다 — 통합 메모리(폰 노이만)가 필요하다.

### 비유로 정리
- 1차선 도로(폰 노이만)에서 택배차와 우편차가 번갈아 통행하면, 5분마다 1분씩 대기가 쌓이듯 CPI가 1.0에서 1.3으로 늘어난다.
- 왕복 2차선(하버드)에서는 두 차가 동시에 달릴 수 있어 대기가 없다 — 다만 도로(버스·핀 수)를 하나 더 까는 비용이 든다.

## Ⅰ. 개요 및 필요성

- 정의: CPU가 메모리의 명령어와 데이터에 접근하는 버스 분리 방식
- 배경: 폰 노이만 병목 현상과 파이프라인 동시 접근으로 인한 구조적 충돌 문제 대두
- 필요성: 클럭 주파수 증가에 맞춰 IPC(명령어 처리량)를 1.0에 근접시키기 위한 동시 접근 설계

## Ⅱ. 구조 및 구성요소

```text
[폰 노이만 아키텍처]
CPU (ALU, CU) <---> [통합 버스] <---> 통합 메모리 (명령어 + 데이터)

[하버드 아키텍처]
                    +-> [명령어 버스] <-> 명령어 메모리
CPU (ALU, CU) ------|
                    +-> [데이터 버스] <-> 데이터 메모리
```

| 구성요소 | 폰 노이만 구조 역할 | 하버드 구조 역할 |
|:---|:---|:---|
| 메모리 (Memory) | 프로그램과 데이터가 하나의 공간에 혼재 | 명령어 공간과 데이터 공간이 물리적 분리 |
| 버스 (Bus) | 명령어 인출과 데이터 접근이 같은 버스를 시분할 공유 | 주소·데이터 버스가 각각 독립적으로 존재 |
| CPU 제어 | 매 클럭 1회의 접근만 허용 | 매 클럭 2회(명령어1, 데이터1) 동시 접근 허용 |

> 요약: 폰 노이만은 자원 공유로 회로가 단순하나 충돌이 발생하고, 하버드는 자원 분리로 동시 접근이 가능하다.

## Ⅲ. 동작원리 및 흐름도

```text
[메모리 접근 흐름: 파이프라인 EX/MEM 단계 충돌 발생 시]
IF 단계 (명령어 인출 요구) -> 버스 경합 <- MEM 단계 (데이터 로드 요구)
-> 하버드 구조: 경합 없이 동시 처리
-> 폰 노이만 구조: 구조적 해저드 발생 -> 1사이클 Stall
```

| 단계 | 폰 노이만 처리 흐름 | 하버드 처리 흐름 |
|:---:|:---|:---|
| 1 | IF 단계 명령어 인출 (버스 점유) | IF 단계 명령어 인출 (명령어 버스) |
| 2 | MEM 단계 데이터 접근 시 대기(Stall) | MEM 단계 데이터 동시 접근 (데이터 버스) |
| 3 | 버스 해제 후 데이터 접근 완료 | 지연 없이 다음 파이프라인 진행 |
| 4 | 버틀넥 누적, IPC 감소 | 병목 해소, 파이프라인 효율 극대화 |

> 요약: 하버드 아키텍처는 IF와 MEM 단계의 버스 경합을 하드웨어적으로 분리하여 해저드(Stall)를 제거한다.

## Ⅳ. 심화 비교: 폰 노이만 vs 하버드

| 비교 축 | 폰 노이만 (Von Neumann) | 하버드 (Harvard) | 선택 기준 |
|:---|:---|:---|:---|
| 버스 구조 | 단일 버스 (공용) | 이중 버스 (독립) | 시스템 복잡도 수용 여부 |
| 파이프라이닝 | 구조적 해저드 발생 심함 | 해저드 원천 차단 | 목표 IPC 및 클럭 효율 |
| 메모리 활용 | 빈 공간 유연한 할당 가능 | 명령어/데이터 비율 고정으로 낭비 | 메모리 자원 제약 여부 |
| 적용 분야 | 범용 컴퓨터 메인 메모리 | DSP, 임베디드, 마이크로컨트롤러 | 목적의 범용성 vs 성능 |

> 요약: 폰 노이만은 유연한 메모리 활용에 유리하고, 하버드는 고속 파이프라인 처리에 유리하여 용도가 갈린다.

## Ⅴ. 현대적 적용 판단: 수정된 하버드 아키텍처

| 해결 과제 | 기존 한계 | 수정된 하버드 (Modified Harvard) 적용 |
|:---|:---|:---|
| 메모리 낭비 | 하버드는 사용 안 하는 공간 낭비 발생 | 메인 메모리는 통합(폰 노이만)하여 유연성 확보 |
| CPU 병목 | 폰 노이만은 파이프라인 Stall 유발 | CPU 내부 L1 캐시를 I-Cache / D-Cache로 분리 |
| 공간-속도 | 범용성과 고성능의 양립 불가 | 외부 버스는 하나로, 내부 캐시 버스는 두 개로 설계 |

> 요약: 현대 CPU는 외부 메인 메모리(유연성)와 내부 L1 캐시(고속 동시 접근)의 장점만 결합한 하이브리드 방식을 쓴다.

| 점검 항목 | 목표 기준 | 측정 방법 |
|:---|:---|:---|
| IPC (명령어 처리량) | 1.0 접근 유지 | 성능 카운터 분석 |
| 구조적 Stall 비율 | 전체 사이클의 1% 미만 통제 | RTL 시뮬레이션 |
| 캐시 적중률 | I-Cache 98%, D-Cache 95% 이상 | 워크로드 벤치마크 |

> 요약: 수정된 구조 도입 후 구조적 해저드로 인한 버블 감소와 목표 IPC 달성 여부를 검증한다.

## Ⅵ. 실무 적용 및 결론

**적용 방안 3개:**
1. L1 분리 설계: 코어 내부 L1 캐시를 Instruction과 Data로 분리 배포하여 5단 파이프라인 IF/MEM 병목 완전 제거
2. L2/L3 통합 설계: 코어 외부 L2/L3 캐시는 폰 노이만 방식의 통합 캐시(Unified Cache)로 구성하여 동적 메모리 할당 효율 극대화
3. DMA(Direct Memory Access) 적용: I/O 장치와 메인 메모리 간 데이터 이동을 CPU 개입 없이 처리하여 단일 버스의 부하를 분산

**결론 (2줄):**
- 기술사 판단: 폰 노이만 병목은 회로 수준에서 수정된 하버드 아키텍처로 1차 완화하고, 시스템 수준에서는 메모리 계층(Hierarchy)과 PIM(Processing in Memory)으로 극복해야 한다.
- 향후 방향: 폰 노이만 구조의 한계를 완전히 벗어나기 위해 뇌 구조를 모방한 뉴로모픽 컴퓨팅과 메모리 연산 통합형(PIM) 설계로 진화 중이다.
