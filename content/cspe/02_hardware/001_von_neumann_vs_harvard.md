## Ⅰ. 개요
- **정의**: 명령어와 데이터의 메모리 공유 여부로 구분되는 두 가지 컴퓨터 구조 모델임
- **배경/필요성**: 프로세서가 명령어와 데이터를 동시에 접근해야 처리량이 증가하므로, 버스 구조를 분리할지 통합할지 결정이 필요함
- **비유**: 도서관에서 책(명령어)과 노트(데이터)를 한 통로로 나르면 폰 노이만, 별도 통로로 나르면 하버드임

| 출제 의도 | 반드시 짚을 핵심 | 감점 회피 포인트 |
|:---|:---|:---|
| 두 구조의 차이와 트레이드오프 이해 | 버스 병목 vs 하드웨어 복잡도 | 현대 CPU는 변형 하버드(내부 분리, 외부 통합)를 채택한다는 점 언급 필요 |

> 요약: 메모리 버스 공유 여부가 두 아키텍처를 가르는 핵심 기준임

## Ⅱ. 구성요소
```text
[폰 노이만]                        [하버드]
                                   
+-------+    단일 버스    +-----+  +-------+  명령 버스  +----------+
|  CPU  |<-------------->| MEM |  |  CPU  |<---------->| 명령 MEM |
+-------+                +-----+  +-------+<---------->+----------+
                                       |    데이터 버스  +----------+
                                       +-------------->| 데이터 MEM|
                                                       +----------+
```

| 구성요소 | 설명 | 비유 |
|:---|:---|:---|
| 단일 버스(폰 노이만) | 명령어·데이터가 같은 경로를 시분할 사용함 | 편도 1차선 도로 |
| 분리 버스(하버드) | 명령어 버스와 데이터 버스가 물리적으로 독립임 | 상·하행 분리 고속도로 |
| 변형 하버드 | L1 캐시는 I-Cache/D-Cache 분리, 외부 메모리는 통합임 | 건물 내부는 분리, 외부 도로는 공용 |

> 요약: 버스·메모리 분리 수준이 구조적 차이의 본질임

## Ⅲ. 절차
```text
  명령 인출       명령 해독       데이터 접근       결과 저장
  (Fetch)        (Decode)       (Memory)         (Write-back)
    |               |               |               |
    +---버스 요청--->+---제어 신호--->+---버스 요청--->+
  폰노이만:동일버스  제어장치       폰노이만:버스경합  레지스터/메모리
  하버드:명령버스    공통           하버드:데이터버스   공통
```
- 1단계: CPU가 PC 주소로 명령어를 인출함 — 폰 노이만은 데이터와 버스 경합 발생 가능
- 2단계: 제어장치가 명령어를 해독하여 연산 종류·피연산자를 결정함
- 3단계: 필요 시 메모리에서 데이터를 읽거나 씀 — 하버드는 인출과 동시 수행 가능
- 4단계: 연산 결과를 레지스터 또는 메모리에 기록함

> 요약: 인출·데이터 접근 단계에서 버스 경합 여부가 처리량 차이를 결정함

## Ⅳ. 문제점
- [폰 노이만 병목]: 단일 버스 시분할 — 명령 인출과 데이터 접근이 같은 버스를 경합하여 처리량이 버스 대역폭에 제한됨
- [하버드 하드웨어 비용]: 버스·메모리 이중화 — 배선 면적과 핀 수가 증가하여 SoC 다이 크기가 커짐
- [코드-데이터 유연성 저하]: 하버드의 엄격 분리 — 자기 수정 코드나 JIT 컴파일처럼 코드를 데이터로 다루는 패턴 구현이 복잡함

> 요약: 통합은 대역폭 병목, 분리는 비용·유연성 문제를 유발함

## Ⅴ. 개선방안
1. 단기: L1 캐시를 I-Cache/D-Cache로 분리하여 폰 노이만 병목을 캐시 수준에서 해소함
2. 중기: 버스 계층화(AXI 등 다중 포트 인터커넥트) 적용으로 하드웨어 비용 대비 대역폭을 확보함
3. 장기: 캐시 일관성 프로토콜과 메모리 보호 유닛을 결합하여 코드-데이터 경계를 소프트웨어 제어 가능하게 함

> 요약: 캐시 분리 → 버스 계층화 → SW 제어 경계 순으로 두 구조의 단점을 절충함

## Ⅵ. 전망
- 발전 방향: 대부분의 범용 프로세서가 변형 하버드를 채택하며, 캐시 계층이 구조적 차이를 흡수하는 추세임
- 기술사적 판단: IoT·DSP 등 특수 목적 프로세서에서는 순수 하버드 구조가 여전히 유효함
- 기술사 제언: 시스템 설계 시 대역폭 요구량과 소프트웨어 유연성을 기준으로 구조를 선택해야 함
