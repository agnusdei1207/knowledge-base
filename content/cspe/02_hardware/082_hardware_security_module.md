## Ⅰ. 개요
- **정의**: 암호 키 생성·저장·연산을 전용 하드웨어 내부에서 수행하는 물리적 보안 장치
- **배경/필요성**: 소프트웨어 기반 키 관리는 메모리 덤프·사이드채널 공격에 노출되므로, 키가 장치 외부로 유출되지 않는 하드웨어 격리가 필요함
- **비유**: 금고 안에서만 열쇠를 만들고 사용하며, 금고 밖으로 열쇠를 꺼내지 않는 구조

| 출제 의도 | 반드시 짚을 핵심 | 감점 회피 포인트 |
|:---|:---|:---|
| 하드웨어 기반 키 보호 원리 | 키가 HSM 외부로 평문 노출되지 않는 구조 | TPM과의 차이점 미기술 시 감점 |

> 요약: HSM은 암호 키의 전 생명주기를 하드웨어 경계 내에서 처리하여 키 유출을 원천 차단함

## Ⅱ. 구성요소
```text
+--------- HSM Boundary ----------+
|                                 |
|  +----------+   +----------+   |
|  | Key Gen  |-->| Key Store|   |
|  +----------+   +----------+   |
|       |              |         |
|       v              v         |
|  +-------------------------+   |
|  | Crypto Engine           |   |
|  | (AES, RSA, ECC, HASH)  |   |
|  +-------------------------+   |
|       |                        |
|  +----------+  +-----------+  |
|  | Tamper   |  | Access    |  |
|  | Detect   |  | Control   |  |
|  +----------+  +-----------+  |
+---------------------------------+
        |
   PKCS#11 / KMIP API
```

| 구성요소 | 설명 | 비유 |
|:---|:---|:---|
| Key Generator | 난수 기반 암호 키 쌍 생성 모듈 | 금고 안 열쇠 제작기 |
| Key Store | 비휘발성 보안 메모리에 키를 암호화 저장 | 금고 내부 잠금 서랍 |
| Crypto Engine | AES·RSA·ECC 등 암호 연산 수행 전용 프로세서 | 금고 안에서만 작동하는 계산기 |
| Tamper Detection | 물리적 침입 감지 시 키 자동 삭제(Zeroization) | 금고 파손 감지 시 내용물 소각 |
| Access Control | 역할 기반 인증·권한 분리(M-of-N 쿼럼) | 두 명이 동시에 열쇠를 돌려야 여는 금고 |

> 요약: HSM은 키 생성·저장·연산·폐기를 물리적 경계 내에서 수행하고, 탬퍼 감지로 물리 공격에 대응함

## Ⅲ. 절차
```text
Application --> API 호출(PKCS#11)
  --> HSM 인증(PIN/Token)
    --> HSM 내부 키 연산 수행
      --> 결과값만 외부 반환 (키는 내부 유지)
```
- 1단계: 애플리케이션이 PKCS#11 또는 KMIP API를 통해 HSM에 암호 연산 요청을 전송함
- 2단계: HSM이 요청자의 인증 정보(PIN, 토큰, M-of-N 쿼럼)를 검증하여 권한 확인함
- 3단계: 인증 통과 시 HSM 내부의 Crypto Engine이 저장된 키로 서명·암호화·복호화 연산 수행함
- 4단계: 연산 결과(서명값, 암호문 등)만 API를 통해 반환하고, 키 자체는 HSM 경계 밖으로 노출하지 않음

> 요약: 외부에서 API로 연산을 요청하고, 키는 HSM 내부에서만 사용되어 결과값만 반환하는 흐름임

## Ⅳ. 문제점
- 단일 장애점: HSM 장비 고장 시 키 접근 불가 — 서비스 전체가 중단될 수 있음
- 높은 도입 비용: FIPS 140-3 Level 3 이상 인증 HSM은 수천만 원 단위 — 중소 조직 도입 장벽이 높음
- 성능 병목: 대량 TLS 핸드셰이크 시 HSM 암호 연산 처리량(TPS)이 한계에 도달함

> 요약: 가용성, 비용, 성능 측면에서 HSM 운영의 한계가 존재함

## Ⅴ. 개선방안
1. 단기: Active-Active 이중화 클러스터 구성으로 단일 장애점 제거
2. 중기: Cloud HSM(AWS CloudHSM, Azure Dedicated HSM) 활용으로 초기 투자 비용 절감
3. 장기: HSM 앞단에 세션 키 캐싱 계층을 두어 반복 연산 부하를 분산하고 TPS 병목 완화

> 요약: 이중화, 클라우드 HSM, 캐싱 계층으로 가용성·비용·성능 문제를 단계적으로 해소함

## Ⅵ. 전망
- 발전 방향: Post-Quantum Cryptography(PQC) 알고리즘 지원 HSM으로의 전환 가속화
- 기술사적 판단: FIDO2·WebAuthn 등 인증 표준 확산에 따라 HSM 수요가 클라우드 서비스 영역으로 확장 중임
- 기술사 제언: 양자 내성 암호 전환 시 HSM 펌웨어 업그레이드 경로를 사전에 확보하는 것이 필요
