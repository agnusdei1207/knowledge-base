# 📖 【암기용】 개념 완전 이해

## 한눈에
- **개요**: 암호화 키 생성, 저장, 처리 과정을 안전하게 수행하기 위해 물리적으로 격리된 전용 보안 하드웨어
- **왜 필요한가**: 서버 메모리나 하드디스크에 암호키를 두면 해킹 시 키가 유출된다. 키 유출은 암호화 체계 붕괴를 뜻하므로 "절대 털리지 않는 금고"가 필요하다.
- **핵심 직관**: 아무리 강한 자물쇠(암호 알고리즘)도 열쇠(키)를 문 앞에 두면 소용없다. HSM은 열쇠를 금고 안에 두고, 밖에서 요청(서명해줘)이 오면 금고 안에서 문서를 처리한 뒤 결과만 내보내는 장치다.

## 핵심 용어 정리

| 용어/표기 | 의미 | 비유·예 |
|:---|:---|:---|
| 키 생명주기 (Key Lifecycle) | 키의 생성, 저장, 사용, 갱신, 폐기에 이르는 전 과정 | "열쇠의 탄생과 파기" |
| 탬퍼 프루프 (Tamper-Proof) | 물리적 해체 시도를 원천 차단하거나 방해하는 기술 | "용접된 강철 금고" |
| 탬퍼 리액턴스 (Tamper-Reactive) | 물리적 침해 감지 시 내부 키를 즉시 영구 삭제(Zeroize) | "침입 시 폭발하는 잉크" |
| FIPS 140-2/3 | 미국 국립표준기술연구소(NIST)의 암호 모듈 보안 인증 기준 | "금고 등급 인증 마크" |

## 깊이 이해
- **배경·문제의식**: 소프트웨어 기반 암호화는 OS 취약점, 메모리 덤프, 부채널 공격에 의해 키가 탈취될 위험이 있다. 키가 유출되면 저장 데이터(Data at Rest) 전체가 유출된 것과 같다.
- **작동 원리**: HSM 내부에 전용 암호 프로세서와 난수 생성기(TRNG)가 있어 외부와 분리된 환경에서 키를 생성한다. 외부 애플리케이션이 암호화를 요청하면, HSM은 API(PKCS#11 등)를 통해 데이터만 전달받고 내부에서 연산 후 암호문만 반환한다. 즉, **키는 절대 HSM 밖으로 나가지 않는다**.
- **비유**: 은행 창구 직원이 돈(키)을 직접 만지지 않고, 방탄유리 너머의 자동 기계에 수표를 넣으면 현금이 나오는 것과 같다. 기계를 부수려 하면 돈은 즉시 불탄다(Zeroization).
- **구체 예시**: 결제 대행사(PG)는 카드번호를 암호화할 때 FIPS 140-2 Level 3 인증을 받은 PCI-HSM을 의무적으로 사용하여, 메모리 해킹 시에도 고객 카드 정보가 복호화되지 않도록 통제한다.
- **흔한 오해·주의점**: "클라우드 KMS(Key Management Service)면 충분하다"고 생각하기 쉬우나, 클라우드 KMS 뒷단도 결국 클라우드 사업자의 HSM 팜(Farm)으로 구동된다. 규제 요건에 따라 전용 단독 HSM(CloudHSM)이 필요할 수 있다.

## 연결 개념
- 암호키 생명주기 — HSM이 물리적으로 보호하는 대상
- PUF (물리적 복제 불가 함수) — HSM 칩의 고유 키 생성에 활용
- TPM (Trusted Platform Module) — PC나 모바일 기기 단말용 경량 보안 모듈(HSM의 소형화 개념)

# 📝 【답안용】 시험 답안 템플릿

## 핵심 인사이트 (3줄 요약)

> 1. **본질**: HSM(Hardware Security Module)은 암호키의 전 생명주기를 외부 시스템과 물리적·논리적으로 격리하여 처리하는 전용 보안 기기다.
> 2. **가치**: 소프트웨어적 메모리 탈취 및 물리적 훼손(Tampering)으로부터 키 유출을 원천 차단하여 시스템의 Root of Trust(RoT)를 제공한다.
> 3. **판단 포인트**: 논리적 격리(API 연동)와 물리적 통제(Zeroization), 고속 암호 가속 성능, FIPS 140-2 인증 등급이 핵심 설계 기준이다.

## 출제 의도 및 답안 포인트

| 출제 의도 | 반드시 짚을 핵심 | 감점 회피 포인트 |
|:---|:---|:---|
| 암호키 유출 방지 아키텍처 이해 | 키 은닉(내부 연산), Tamper-Resistance/Reactive, FIPS 인증 | 소프트웨어 암호화 가속기로만 오해 (핵심은 키 보호) |
| 기업 보안 요구사항에 따른 HSM 적용 판단 | 클라우드 HSM 연동, PKCS#11 API, 키 생명주기 관리 | 암호 알고리즘 세부 설명에 치중해 기기 특징 누락 |

> 요약: HSM 문제는 암호 알고리즘이 아닌 "암호키를 어떻게 물리적으로 보호하고 생명주기를 관리할 것인가"에 대한 아키텍처 판단을 묻는다.

---

## Ⅰ. 개요 및 필요성

- 개요: HSM은 암호키 생성·저장·파기 및 암호화 연산을 외부 OS·애플리케이션과 독립적으로 수행하는 하드웨어 기반 보안 모듈임
- 배경: 지능형 타겟 위협(APT) 및 메모리 덤프 공격으로 소프트웨어 기반 암호키 유출 사고 급증
- 필요성: 망분리 및 데이터 암호화 규제(전자금융감독규정, ISMS-P) 준수, 초당 수만 건의 암호 처리(TPS) 성능 병목 해소

---

## Ⅱ. 구조 및 구성요소

```text
Application -> [PKCS#11 / KMIP API] -> HSM Boundary
                                        | (논리적·물리적 격리)
                                        +-> TRNG (난수 생성)
                                        +-> Crypto Engine (암/복호화)
                                        +-> Key Storage (키 저장)
```

| 구성요소 | 역할 | 특이사항 |
|:---|:---|:---|
| TRNG (난수 생성기) | 엔트로피 소스를 활용한 고품질 난수 기반 암호키 생성 | 패턴 예측 불가 |
| Crypto Processor | RSA, AES, ECC 등 암호화 연산을 고속으로 전담 처리 | CPU 오버헤드 경감 |
| 보안 저장소 | 생성된 마스터 키 및 데이터 암호화 키를 안전하게 보관 | 외부에 키 평문 노출 없음 |
| 탬퍼 감지 센서 | 물리적 온도·전압·충격 변화 감지 시 Zeroization 수행 | FIPS 140-2 Level 3 이상 요구 |

> 요약: HSM은 난수 생성부터 키 저장·연산까지 모든 과정을 물리적 방어선(Boundary) 내부에서 완결 짓는 폐쇄형 구조다.

---

## Ⅲ. 동작원리 및 흐름도

```text
애플리케이션 요청 -> API 수신 및 인증 -> 암호키 로드 -> 내부 연산 -> 결과 반환
                     |                    |                |
                     +-> 권한 검증        +-> 평문 키 유지 +-> 암호문만 외부 전송
```

- 1단계 [요청 인가]: 앱이 PKCS#11 등 표준 API로 데이터를 전송하며 암호화·서명 요청
- 2단계 [키 인출]: HSM 내부 보안 메모리에서 접근 권한 확인 후 암호키 로드 (외부 반출 금지)
- 3단계 [내부 처리]: 내장된 전용 Crypto Engine이 평문 데이터를 암호키와 연산
- 4단계 [결과 반환]: 암호화된 결과물(Ciphertext) 또는 서명값만 외부 애플리케이션에 반환

> 요약: 암호화 대상 데이터만 HSM 내부로 들어왔다가 암호문으로 나가며, 가장 중요한 '키(Key)'는 절대 경계 밖으로 이동하지 않는다.

---

## Ⅳ. 특징
- [키 기밀성]: 소프트웨어 메모리나 스토리지에 평문 키가 존재하지 않아 해킹으로 인한 유출 원천 차단
- [물리적 방어]: Tamper-Resistance(분해 방지) 및 Tamper-Reactive(침해 시 데이터 자동 파기) 적용
- [고성능 가속]: 전용 하드웨어 칩셋(ASIC)을 사용해 서버 CPU 부하 없이 초당 수만 건의 비대칭키 연산(RSA) 처리

> 요약: HSM은 논리적/물리적 탈취를 모두 방어하는 최고 수준의 보안성을 제공하지만, 고가의 구축 비용과 구성의 복잡성이 따른다.

---

## Ⅴ. 심화 비교 및 적용 판단

| 비교 축 | 소프트웨어 암호화 | 일반 HSM (On-Premise) | Cloud HSM | 선택 기준 |
|:---|:---|:---|:---|:---|
| 키 제어권 | OS 및 애플리케이션 | 고객사 완전 통제 | 클라우드 인프라 기반 고객 제어 | 규제 준수 수준 |
| 확장성 | 스케일 아웃 용이 | 물리적 장비 추가 필요 | API 기반 탄력적 프로비저닝 | 트래픽 변동폭 |
| 구축 비용 | 낮음 | 매우 높음 (장비 도입) | 사용량 기반 과금 (OPEX) | 예산 아키텍처 |

> 요약: 극비 데이터나 금융망은 온프레미스 단독 HSM을, 탄력적 웹 서비스는 Cloud HSM을 선택해 보안과 유연성을 조율한다.

**리스크·대응:**
- [단일 장애점(SPOF)]: 단일 HSM 장애 시 암호화 시스템 전체 마비 → HA(Active-Active) 클러스터링 구성 및 동기화 (지표: 가용성 99.99%)
- [내부자 위협]: 관리자에 의한 불법 키 추출 시도 → M of N 통제(다수 관리자 동시 승인) 의무화 (지표: 분산 권한 인가율)

**도입 후 점검 지표:**
- 성능/효율: 피크 타임 암호화 지연 시간 p95 10ms 이하 — 처리량(TPS) 모니터링
- 품질/운영: 암호키 주기적 자동 로테이션 성공률 100% — 키 생명주기 감사 로그

---

## Ⅵ. 실무 적용 및 결론

**적용 방안 3개:**
1. 아키텍처 설계: 데이터베이스 암호화(TDE) 키 보관소로 HSM 연동, 애플리케이션 서버에는 API 연동 모듈만 배포
2. 클라우드 전환: 하이브리드 환경에서 온프레미스 HSM을 마스터로 두고 Cloud HSM으로 키를 안전하게 주입(BYOK: Bring Your Own Key)
3. 표준화 연동: KMIP(Key Management Interoperability Protocol) 적용을 통해 이기종 HSM 간 키 관리 체계 단일화

**결론 (2줄):**
- 기술사 판단: 제로 트러스트 보안의 핵심은 키 보호이므로, 규제 데이터가 있는 엔터프라이즈 환경에서 FIPS 140-2 Level 3 이상 HSM 도입은 선택이 아닌 필수다.
- 향후 방향: 양자 컴퓨터의 쇼어 알고리즘 위협에 대비해, 하드웨어 교체 없이 펌웨어 업데이트로 양자내성암호(PQC)를 지원하는 유연한 Crypto-Agile HSM으로 전환해야 한다.
