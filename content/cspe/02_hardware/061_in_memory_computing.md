# 📖 【암기용】 개념 완전 이해

> 목적: 인메모리 컴퓨팅을 처음 봐도 왜 디스크 기반 처리와 다른지 이해하게 만든다. 시험 답안 양식이 아니라, 이해를 위한 친절한 설명이다.

## 한눈에
- **개요**: 처리 대상 데이터 전체를 디스크가 아닌 DRAM 주기억장치에 상주시켜 연산하는 컴퓨팅 방식
- **왜 필요한가**: 디스크 I/O는 ms 단위 지연이 있고 DRAM 접근은 ns 단위이므로, 실시간 분석·대량 트랜잭션 처리는 디스크 탐색 지연을 제거해야 목표 응답시간을 만족한다.
- **핵심 직관**: 매번 창고(디스크)를 오가며 물건을 찾는 대신, 자주 쓰는 물건을 전부 책상(메모리) 위에 올려두고 바로 집어 쓰는 방식이다.

## 깊이 이해
- **배경·문제의식**: 전통 RDBMS는 데이터를 디스크에 두고 버퍼 캐시로 일부만 메모리에 올리므로 캐시 미스 시 디스크 I/O가 응답시간을 지배한다.
- **배경·문제의식**: DRAM 가격 하락과 서버 메모리 용량 증가(TB 단위)로 데이터셋 전체를 메모리에 상주시키는 것이 경제적으로 가능해졌다.
- **작동 원리**: 데이터를 처음부터 메모리 상주 구조(컬럼 스토어 또는 인메모리 테이블)로 적재하고, 질의 실행 엔진이 디스크 I/O 없이 메모리 주소로 직접 접근한다.
- **작동 원리**: 휘발성 문제는 WAL(Write-Ahead Log)을 디스크·NVMe에 기록하고 주기적 스냅샷과 복제본으로 보완해 전원 손실 시 복구한다.
- **비유**: 도서관 사서가 매번 서고(디스크)로 뛰어가는 대신, 자주 찾는 책을 카운터(메모리) 위에 미리 꺼내놓고 바로 건네주는 것과 같다.
- **구체 예시**: SAP HANA는 트랜잭션 처리(OLTP)와 분석(OLAP)을 같은 인메모리 컬럼 스토어에서 처리해 HTAP(Hybrid Transactional/Analytical Processing)를 구현한다.
- **구체 예시**: Redis는 키-값 데이터를 메모리에 두고 옵션으로 AOF(Append Only File)·RDB 스냅샷을 디스크에 남겨 재시작 후 복구한다.
- **흔한 오해·주의점**: 인메모리 컴퓨팅이 항상 무정전 안전한 것은 아니다. WAL·복제·NVDIMM 백업 설계가 없으면 전원 장애 시 미반영 데이터가 유실된다.
- **흔한 오해·주의점**: 캐싱(Redis 캐시 레이어)과 인메모리 DB는 다르다. 캐싱은 원본 데이터가 디스크 DB에 별도로 존재하는 보조 계층이고, 인메모리 DB는 그 자체가 정본(source of truth)이다.

## 연결 개념
- HBM·PIM — 메모리 자체의 대역폭·연산 결합으로 인메모리 처리를 가속
- NVDIMM·퍼시스턴트 메모리 — 휘발성 한계를 완화하는 비휘발성 메모리 계층
- CXL 메모리 풀링 — 여러 노드가 공유하는 대용량 메모리 풀 확장

# 📝 【답안용】 시험 답안 템플릿

> 목적: 시험장에서 25분에 그대로 쓰는 답안 양식. 작성방식(추상표현 금지·수치·도식·문제유형 전환)을 엄격히 지킨다.
> 핵심: 인메모리 컴퓨팅 답안은 디스크 I/O 병목 대비 지연시간 개선치, 휘발성 대응 기법, HTAP 적용 사례를 함께 제시한다.

## 핵심 인사이트 (3줄 요약)

> 1. **본질**: 인메모리 컴퓨팅은 데이터 전체를 DRAM에 상주시켜 디스크 탐색 지연 없이 연산하는 방식이다.
> 2. **가치**: 디스크 I/O ms 단위 지연을 DRAM ns 단위 접근으로 대체해 실시간 분석과 고빈도 트랜잭션 처리를 지원한다.
> 3. **판단 포인트**: 휘발성 대응(WAL·스냅샷·복제)과 DRAM 용량 대비 비용이 도입 여부를 가르는 기준이다.

## 출제 의도 및 답안 포인트

| 출제 의도 | 반드시 짚을 핵심 | 감점 회피 포인트 |
|:---|:---|:---|
| 디스크 기반 처리와의 차이 확인 | DRAM ns vs 디스크 ms 접근 지연 | 근거 수치 없는 저지연 주장으로만 서술 |
| 휘발성 리스크 대응 역량 확인 | WAL, 스냅샷, 복제, NVDIMM | 휘발성 문제 언급 없이 장점만 서술 |
| 적용 사례 이해 확인 | HTAP, 인메모리 DB, 캐시와의 차이 | 캐싱과 인메모리 DB를 동일 개념으로 혼동 |

> 요약: 이 문제는 속도 향상보다 휘발성 대응 설계와 캐싱과의 개념 구분을 보여야 한다.

## Ⅰ. 개요 및 필요성

- 개요: 데이터 전체를 주기억장치에 상주시켜 처리하는 컴퓨팅 방식
- 배경: 디스크 기반 RDBMS는 캐시 미스 시 디스크 I/O가 응답시간을 지배해 실시간 처리에 한계가 있음
- 필요성: DRAM 대용량화와 가격 하락으로 TB급 데이터셋 전체를 메모리 상주시켜 p95 응답시간을 ms 이하로 낮출 수 있음

---

## Ⅱ. 구조 및 구성요소

```text
Client Request -> In-Memory Query Engine
  -> Column/Row Store in DRAM
  -> WAL Writer -> Disk/NVMe Log
  -> Snapshot -> Replica Node
```

| 구성요소 | 역할 | 특이사항 |
|:---|:---|:---|
| In-Memory Store | 데이터 전체를 DRAM에 컬럼/로우 형태로 상주 | 컬럼 스토어는 분석 질의에 유리 |
| Query Engine | 메모리 주소 직접 접근으로 질의 실행 | 디스크 I/O 대기 없음 |
| WAL | 변경 이력을 디스크에 순차 기록 | 전원 손실 시 재적용 기준 |
| Snapshot/Checkpoint | 주기적 전체 상태 디스크 저장 | 복구 시간 단축 |
| Replica | 다른 노드에 동일 상태 복제 | 노드 장애 시 즉시 전환 |

> 요약: 인메모리 컴퓨팅은 DRAM 상주 저장소와 WAL·스냅샷·복제 조합으로 성능과 내구성을 동시에 확보한다.

---

## Ⅲ. 동작원리 및 흐름도

```text
Write Request -> Memory Update -> WAL Append(Disk)
  -> Ack Return -> Async Snapshot -> Replica Sync
```

| 단계 | 처리 내용 | 검증 기준 |
|:---:|:---|:---|
| 1 | 쓰기 요청을 메모리 구조에 즉시 반영 | 쓰기 지연 us 단위 |
| 2 | WAL을 디스크에 순차 기록 후 ack | fsync 지연, durability 보장 여부 |
| 3 | 주기적 스냅샷으로 전체 상태 디스크 저장 | 스냅샷 주기, 복구 시간(RTO) |
| 4 | 복제 노드에 변경분 동기화 | replication lag |

> 요약: 인메모리 처리는 메모리 갱신을 먼저 반영하고 WAL·스냅샷·복제로 내구성을 뒤따라 확보한다.

---

## Ⅳ. 특징

| 구분 | 내용 | 판단 포인트 |
|:---|:---|:---|
| 장점 | 디스크 탐색 지연 제거로 p95 응답시간을 ms 이하로 단축 | 실시간 분석·고빈도 트랜잭션 적합성 |
| 한계 | DRAM은 전원 차단 시 휘발되고 GB당 비용이 SSD보다 높음 | WAL·스냅샷·복제 설계 여부 |
| 비교 포인트 | 캐싱은 보조 계층, 인메모리 DB는 정본 저장소 | 데이터 정합성 책임 위치 |

> 요약: 인메모리 컴퓨팅의 성능 이득은 휘발성 대응 비용과 맞바꾸는 트레이드오프다.

## Ⅴ. 심화 비교 및 적용 판단

| 비교 축 | 디스크 기반 처리 | 인메모리 컴퓨팅 | 선택 기준 |
|:---|:---|:---|:---|
| 구조 | 버퍼 캐시 + 디스크 저장 | DRAM 전체 상주 + WAL 백업 | 데이터셋이 메모리 용량 내에 들어오는지 |
| 비용/성능 | GB당 비용 낮음, 지연 ms | GB당 비용 높음, 지연 us~ns | 실시간 SLA(p95) 요구 수준 |
| 운영/위험 | 디스크 장애 시 복구 절차 성숙 | 전원 차단 시 휘발 리스크 | UPS·WAL·복제 이중화 여부 |

> 요약: 실시간 SLA가 엄격하고 데이터셋이 메모리 용량 내에 들어오면 인메모리, 아니면 디스크 기반을 선택한다.

| 리스크 | 원인 | 대응 방안 | 확인 지표 |
|:---|:---|:---|:---|
| 데이터 유실 | 전원 차단 시 WAL 미반영분 손실 | UPS 연계, WAL fsync 주기 단축 | RPO 목표치 |
| 메모리 용량 초과 | 데이터셋 증가로 DRAM 부족 | 샤딩, CXL 메모리 풀링 확장 | 노드당 메모리 사용률 |
| 복구 지연 | 스냅샷 주기 김 | 스냅샷 주기 단축, 증분 백업 | RTO 목표치 |

> 요약: 인메모리 운영은 WAL·UPS 조합과 스냅샷 주기 관리로 유실·복구 리스크를 통제한다.

| 점검 항목 | 목표 기준 | 측정 방법 |
|:---|:---|:---|
| 성능 | p95 응답시간 ms 이하 | APM, 질의 로그 |
| 내구성 | RPO·RTO 목표 충족 | 장애 복구 훈련 |
| 자원 | DRAM 사용률 80% 이하 | 모니터링 지표 |

> 요약: 도입 후 성공 여부는 응답시간, RPO/RTO, DRAM 사용률로 판단한다.

## Ⅵ. 실무 적용 및 결론

**적용 방안 3개 (필수 — 단계별 또는 항목별):**
1. 실시간 분석·고빈도 트랜잭션 구간은 인메모리 컬럼 스토어를 도입하고 p95 응답시간을 SLA 기준으로 검증함
2. 휘발성 대응은 WAL fsync 주기, 스냅샷 주기, 복제본 수를 RPO·RTO 목표에 맞춰 설계함
3. 데이터셋이 DRAM 용량을 초과할 가능성에 대비해 샤딩 또는 CXL 메모리 풀링 확장 경로를 사전에 검토함

**결론 (2줄):**
- 기술사 판단: 실시간 SLA가 엄격하고 비용 대비 DRAM 용량이 충분하면 인메모리 컴퓨팅을, 그렇지 않으면 디스크 기반과 캐시 계층 조합을 선택함
- 향후 방향: CXL 메모리 풀링과 퍼시스턴트 메모리가 결합되며 휘발성 제약이 완화되는 방향으로 발전함
