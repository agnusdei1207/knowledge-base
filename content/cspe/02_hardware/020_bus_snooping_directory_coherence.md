# 📖 【암기용】 개념 완전 이해

> 목적: 버스 스누핑과 디렉터리 기반 일관성을 처음 봐도 캐시 일관성 프로토콜(MESI·MOESI)의 상태 전이 메시지가 실제로 어떤 하드웨어 경로로 전달되는지 이해하게 만든다. 시험 답안 양식이 아니라, 이해를 위한 친절한 설명이다.

## 한눈에
- **개요**: 캐시 일관성 프로토콜의 상태 전이 메시지를 모든 캐시에 방송(Broadcast)하는 버스 스누핑 방식과, 각 메모리 블록을 누가 갖고 있는지 별도 장부(디렉터리)로 추적해 필요한 캐시에만 보내는 디렉터리 기반 방식
- **왜 필요한가**: MESI·MOESI 같은 프로토콜이 상태를 "어떻게" 정의하는지는 정했어도, 그 상태 변경을 다른 코어들에게 "어떤 경로로" 전달할지는 별도의 하드웨어 구현 문제이며, 코어 수가 늘어날수록 이 전달 방식의 확장성이 성능을 좌우한다
- **핵심 직관**: 스누핑은 사무실 전체에 마이크로 공지하는 것이고, 디렉터리 기반은 안내 데스크가 누가 어떤 문서를 갖고 있는지 명부로 관리해 해당자에게만 개별 연락하는 것이다

## 깊이 이해
- **배경·문제의식**: 캐시 일관성 프로토콜은 다른 코어의 요청(BusRd, BusRdX 등)을 알아야 상태를 전이할 수 있는데, 이 요청을 코어들에게 어떻게 알릴지가 스누핑과 디렉터리 방식의 차이다.
- **작동 원리 - 버스 스누핑**: 모든 캐시 컨트롤러가 공유 버스(또는 방송 가능한 인터커넥트)를 항상 감시(snoop)하고 있다가, 다른 코어의 메모리 요청이 버스에 실리면 자신이 해당 라인을 갖고 있는지 확인해 상태를 전이하거나 데이터를 공급한다.
- **작동 원리 - 버스 스누핑의 확장성 한계**: 모든 요청이 모든 캐시에 방송되므로 코어 수가 늘어날수록 버스(또는 방송 인터커넥트)의 트래픽과 각 캐시 컨트롤러의 태그 비교 부하가 코어 수에 비례해 증가해, 소규모 코어 수에서는 효율적이지만 대규모로 갈수록 대역폭 병목이 된다.
- **작동 원리 - 디렉터리 기반 일관성**: 메모리 블록마다 디렉터리 엔트리를 두어 어느 캐시가 그 블록을 보유하고 있는지(sharer 목록)와 상태(공유/수정 등)를 기록하고, 요청이 오면 디렉터리가 실제로 관련 있는 캐시에만 점대점(point-to-point) 메시지를 보낸다.
- **작동 원리 - 디렉터리 구성**: 디렉터리는 중앙 집중형으로 둘 수도 있고, 대규모 시스템에서는 메모리 컨트롤러나 노드별로 분산된 형태로 두어 각 노드가 자신이 담당하는 메모리 주소 범위의 디렉터리만 관리하는 것이 일반적이다.
- **작동 원리 - 트레이드오프**: 스누핑은 방송 매체를 전제로 하며 추가 조회 단계 없이 바로 요청을 알리지만 코어 수가 늘면 트래픽이 급증하고, 디렉터리는 방송을 없애 트래픽을 줄이는 대신 디렉터리 조회라는 한 단계(hop)가 지연에 더해진다.
- **비유**: 스누핑은 교실 전체에 "이 책 누가 갖고 있어요?"라고 외치는 것이고, 디렉터리는 사서(디렉터리)에게 먼저 물어 대출자 명단을 확인한 뒤 그 사람에게만 직접 찾아가는 것이다.
- **구체 예시**: 코어 4~8개(예시 규모) 수준의 공유 버스 시스템에서는 스누핑 방식이 단순하고 지연도 낮지만, 코어 수십~수백 개 규모의 NUMA·대규모 멀티프로세서 시스템에서는 방송 트래픽이 감당되지 않아 디렉터리 기반 방식이 채택되는 경향이 있다.
- **흔한 오해·주의점**: 버스 스누핑과 디렉터리 기반 방식은 MESI·MOESI 같은 상태 모델 자체를 대체하는 것이 아니라, 그 상태 전이 메시지를 "어떤 경로로 전달하느냐"의 구현 방식 차이임을 구분해야 한다.
- **흔한 오해·주의점**: 디렉터리 기반이 스누핑보다 무조건 빠르다고 단정하면 안 된다. 소규모 코어 수에서는 디렉터리 조회 hop이 추가 지연으로 작용해 오히려 단순 스누핑보다 불리할 수 있다.

## 연결 개념
- 캐시 일관성 프로토콜(MESI·MOESI) — 스누핑·디렉터리가 전달하는 상태 전이 메시지의 상태 모델
- 멀티코어 프로세서 — 코어 수 확장에 따라 스누핑에서 디렉터리 기반으로 전환이 검토되는 배경
- 캐시 쓰기 정책(Write-Back) — Modified/Owned 라인의 소재를 스누핑·디렉터리가 추적해야 하는 근본 이유

# 📝 【답안용】 시험 답안 템플릿

> 목적: 시험장에서 25분에 그대로 쓰는 답안 양식. 작성방식(추상표현 금지·수치·도식·문제유형 전환)을 엄격히 지킨다.
> 핵심: 방송 기반 스누핑과 점대점 기반 디렉터리의 구조 차이, 확장성·지연 트레이드오프, 코어 수 규모별 적용 판단을 함께 제시한다.

## 핵심 인사이트 (3줄 요약)

> 1. **본질**: 버스 스누핑은 모든 캐시에 요청을 방송해 일관성을 유지하고, 디렉터리 기반은 블록별 보유 캐시 목록을 관리해 관련 캐시에만 점대점으로 통보한다.
> 2. **가치**: 스누핑은 구조가 단순하고 소규모에서 지연이 낮으며, 디렉터리는 방송 트래픽을 없애 대규모 코어 수까지 확장 가능하다.
> 3. **판단 포인트**: 코어 수가 적을 때는 스누핑이, 코어 수가 많아 방송 대역폭이 병목이 되는 대규모 시스템에서는 디렉터리 기반이 상대적으로 유리하다.

## 출제 의도 및 답안 포인트

| 출제 의도 | 반드시 짚을 핵심 | 감점 회피 포인트 |
|:---|:---|:---|
| 두 구현 방식의 구조 차이 이해 확인 | 방송(스누핑) vs 점대점 통보(디렉터리) | 두 방식을 캐시 일관성 상태 모델(MESI)과 동일 개념으로 혼동 |
| 확장성 한계 이해 확인 | 코어 수 증가에 따른 방송 트래픽 증가(스누핑) vs 디렉터리 조회 hop(디렉터리) | 디렉터리가 항상 스누핑보다 빠르다고 단정 |
| 적용 규모 판단 확인 | 소규모 공유 버스는 스누핑, 대규모 NUMA는 디렉터리 | 규모 조건 없이 한쪽이 절대적으로 우월하다고 서술 |

> 요약: 이 문제는 두 방식의 이름 나열이 아니라 방송 vs 점대점 전달 구조와 규모별 트레이드오프를 근거로 답안을 구성해야 한다.

## Ⅰ. 개요 및 필요성

- 개요: 버스 스누핑은 모든 캐시가 공유 버스를 감시해 상태를 전이하는 방식, 디렉터리 기반은 블록별 보유 캐시 목록을 관리해 점대점으로 통보하는 방식
- 배경: MESI·MOESI 같은 캐시 일관성 상태 모델은 다른 코어의 요청을 알아야 동작하는데, 이 요청 전달 경로가 코어 수 확장성에 직접 영향을 미침
- 필요성: 소규모 공유 버스 시스템과 대규모 NUMA·멀티프로세서 시스템은 요구되는 대역폭·지연 특성이 달라, 규모에 맞는 일관성 전달 방식을 선택해야 함

---

## Ⅱ. 구조 및 구성요소

```text
Cache 0 -- Cache 1 -- Cache 2 -- ... -- Cache N
        \___________Shared Bus(Broadcast)___________/
  -> 버스 스누핑: 모든 Cache가 모든 요청을 감시(Broadcast 수신)

Directory(중앙 또는 분산, 메모리 컨트롤러/노드별)
  -> 블록별 Sharer List + State 기록
  -> 요청 시 관련 Cache에만 Point-to-Point 메시지 전송
```

| 구성요소 | 역할 | 산출물 |
|:---|:---|:---|
| 공유 버스(스누핑) | 모든 캐시 요청을 방송하는 매체 | 전체 캐시 동시 감시 가능 |
| 캐시 컨트롤러(스누핑) | 버스 트랜잭션을 항상 감시하며 자신의 라인 상태 전이 | 방송 기반 상태 동기화 |
| 디렉터리 엔트리 | 블록별 sharer 목록과 상태 저장 | 요청 대상 캐시 특정 |
| 점대점 인터커넥트(디렉터리) | 디렉터리가 특정 캐시에만 메시지 전달 | 방송 트래픽 제거 |

> 요약: 스누핑은 방송 매체와 상시 감시로, 디렉터리는 sharer 목록 기반 점대점 통보로 일관성을 유지한다.

## Ⅲ. 동작원리 및 흐름도

```text
[버스 스누핑]
코어 요청 발생 -> 공유 버스에 트랜잭션 방송
  -> 모든 캐시 컨트롤러가 트랜잭션 감시
  -> 자신이 해당 라인 보유 시 상태 전이·데이터 공급
  -> 요청 코어가 응답 수신

[디렉터리 기반]
코어 요청 발생 -> 해당 블록 담당 디렉터리에 조회
  -> 디렉터리가 sharer 목록·상태 확인
  -> 관련 캐시에만 점대점 메시지 전송(무효화/데이터 공급 요청)
  -> 관련 캐시 응답 -> 디렉터리 경유 또는 직접 요청 코어에 전달
```

| 단계 | 처리 내용 | 검증 기준 |
|:---:|:---|:---|
| 1(스누핑) | 요청을 공유 버스에 방송 | 버스 대역폭 사용률 |
| 2(스누핑) | 모든 캐시가 트랜잭션 감시 후 상태 전이 | 캐시 컨트롤러 감시 부하 |
| 1(디렉터리) | 요청을 담당 디렉터리에 먼저 조회 | 디렉터리 조회 지연(hop) |
| 2(디렉터리) | sharer 목록 기반 점대점 메시지 전송 | 불필요한 방송 제거 여부 |

> 요약: 스누핑은 방송 후 전체 감시로, 디렉터리는 조회 후 점대점 전달로 상태 전이 메시지를 완성한다.

## Ⅳ. 특징

| 구분 | 버스 스누핑 | 디렉터리 기반 | 수치·표준 포인트 |
|:---|:---|:---|:---|
| 메시지 전달 방식 | 전체 방송(Broadcast) | 점대점(Point-to-Point) | sharer list, presence bit |
| 확장성 | 코어 수 증가 시 트래픽 급증 | 코어 수 증가에도 상대적으로 완만한 트래픽 증가 | 대규모 NUMA에서 디렉터리 우세 |
| 지연 특성 | 조회 단계 없이 즉시 방송 | 디렉터리 조회 hop 추가 | 소규모에서는 스누핑이 저지연 |
| 하드웨어 요구 | 방송 가능한 공유 버스/인터커넥트 | 디렉터리 저장 공간(메모리 오버헤드) | 디렉터리 엔트리 크기 설계 필요 |

> 요약: 스누핑은 즉시 방송으로 단순하지만 확장성이 제한되고, 디렉터리는 조회 hop이 추가되지만 대규모 확장에 유리하다.

## Ⅴ. 심화 비교 및 적용 판단

| 비교 축 | 버스 스누핑 | 디렉터리 기반 | 선택 기준 |
|:---|:---|:---|:---|
| 구조 | 방송 매체 기반 전체 감시 | sharer 목록 기반 점대점 통보 | 코어 수 규모로 결정 |
| 비용/성능 | 코어 수 적을 때 저지연·저비용 | 디렉터리 저장·조회 비용 발생하나 대규모에서 트래픽 절감 | 목표 코어 수와 인터커넥트 대역폭 예산 |
| 운영/위험 | 코어 수 증가 시 버스 포화 위험 | 디렉터리 크기·정확성 관리 필요 | 시스템 성장 로드맵 고려 |

> 요약: 소규모 공유 버스 시스템은 스누핑이, 코어 수가 많은 대규모 NUMA·멀티프로세서 시스템은 디렉터리 기반이 상대적으로 유리하다.

| 리스크 | 원인 | 대응 방안 | 확인 지표 |
|:---|:---|:---|:---|
| 버스 트래픽 포화 | 코어 수 증가에 따른 방송 트래픽 누적 | 디렉터리 기반 전환, 계층적 인터커넥트(mesh 등) 도입 | 버스 대역폭 사용률 |
| 디렉터리 조회 지연 | 모든 요청이 디렉터리를 경유 | 분산 디렉터리, 캐시된 디렉터리 정보 활용 | 디렉터리 조회 hop 수, 평균 지연 |
| 디렉터리 저장 오버헤드 | sharer 목록 저장 공간 증가 | 압축된 sharer 표현(비트벡터, 제한된 포인터 방식) 적용 | 디렉터리 메모리 오버헤드 비율 |

> 요약: 스누핑 리스크는 트래픽 포화, 디렉터리 리스크는 조회 지연과 저장 오버헤드이며 규모에 맞는 구조 선택으로 통제한다.

| 점검 항목 | 목표 기준 | 측정 방법 |
|:---|:---|:---|
| 인터커넥트 트래픽 | 코어 수 대비 목표 대역폭 사용률 이내 | 인터커넥트 성능 카운터 |
| 일관성 메시지 지연 | 목표 평균 지연(cycle) 이내 | 트레이스 분석, 시뮬레이션 |
| 디렉터리 정확성 | sharer 목록과 실제 캐시 보유 상태 100% 일치 | 정형 검증, coverage 테스트 |

> 요약: 도입 효과는 인터커넥트 트래픽, 일관성 메시지 지연, 디렉터리 정확성 세 지표로 판단한다.

## Ⅵ. 실무 적용 및 결론

**적용 방안 3개:**
1. 코어 수가 적은 공유 버스 시스템은 버스 스누핑을 채택해 구조를 단순화하고 저지연을 확보함
2. 코어 수가 많은 대규모 NUMA·멀티프로세서 시스템은 디렉터리 기반 일관성으로 전환해 방송 트래픽 병목을 제거함
3. 디렉터리 저장 오버헤드가 우려되는 경우 압축된 sharer 표현 방식을 적용해 메모리 오버헤드를 관리함

**결론 (2줄):**
- 기술사 판단: 일관성 전달 방식은 캐시 일관성 상태 모델(MESI·MOESI)과 별개의 구현 문제이며, 코어 수 규모에 따라 스누핑과 디렉터리 기반을 구분해 선택해야 함
- 향후 방향: 코어 수가 지속 증가함에 따라 계층적 인터커넥트와 분산 디렉터리를 결합한 확장형 일관성 설계가 주류로 자리잡고 있음
