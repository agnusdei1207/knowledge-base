# 📖 【암기용】 개념 완전 이해

> 목적: 4코어 PC가 쓰는 동기화 방식(스누핑)과 128코어 서버가 쓰는 동기화 방식(디렉터리)이 왜 다른지, 코어 수가 늘어날 때 무엇이 한계에 부딪히는지 수치로 이해하게 만든다.

## 한눈에
- **개요**: 버스 스누핑과 디렉터리 기반 프로토콜은 멀티코어의 **캐시 일관성(Cache Coherence)** 상태 변화(무효화·공유) 정보를 코어 간에 실어 나르는 두 가지 **인터커넥트(상호연결망) 통신 방식**이다. MESI 같은 프로토콜이 "무엇을 어떤 상태로 바꿀지"의 규칙이라면, 스누핑·디렉터리는 "그 변경 사실을 다른 코어에게 어떻게 전달할지"의 배달 방식이다.
- **왜 필요한가**: 한 코어가 데이터를 고치면 그 사실을 나머지 코어에게 알려 캐시를 무효화시켜야 한다. 코어가 4개면 전체에 방송해도 부담이 없지만, 코어가 64개·128개로 늘면 매번 전체 방송이 공유 배선(버스)의 물리적 대역폭을 순식간에 소진시킨다. "몇 명에게 알릴 것인가"를 규모에 맞게 설계해야 한다.
- **핵심 직관**: 버스 스누핑은 작은 사무실에서 "짜장면 시킬 사람?" 하고 육성으로 외치는 것과 같다(전원이 듣고 즉시 반응, 인원이 적을 때만 통함). 디렉터리 기반은 총무과가 신청자 명부를 들고 해당자에게만 사내 메신저로 개별 통지하는 것과 같다(인원이 많아도 관계자만 부담).

## 핵심 용어 정리 (내부에 등장하는 것들)

| 표기/용어 | 의미 | 비유 |
|:---|:---|:---|
| 캐시 일관성(Cache Coherence) | 여러 캐시의 같은 주소 복사본이 항상 같은 값으로 보이게 하는 성질 — 스누핑·디렉터리가 그 정보를 나르는 상위 목적 | 모든 지점 장부가 같은 잔액을 보여줘야 함 |
| 브로드캐스트(Broadcast) | 신호를 특정 대상 없이 연결된 모두에게 뿌리는 전송 방식 | 확성기로 전체 공지 |
| 버스 스누핑(Bus Snooping) | 모든 캐시 컨트롤러가 공유 버스를 항상 엿듣다가, 자기 주소가 불리면 반응하는 방식 | 다들 무전기를 켜놓고 도청 중 |
| 공유 버스(Shared Bus) | 모든 코어가 물리적으로 하나의 배선을 나눠 쓰는 통신로 — 스누핑의 전제 조건 | 한 채널짜리 무전 주파수 |
| 디렉터리(Directory) | 각 캐시 라인을 어떤 코어가 갖고 있는지 기록해두는 중앙(또는 분산) 장부 | 총무과의 신청자 명부 |
| 비트 벡터(Bit Vector) | 디렉터리가 "코어 0..N-1 중 누가 이 라인을 갖고 있나"를 코어당 1비트로 표시한 표 | 출석부의 체크 칸 |
| 유니캐스트(Unicast) / 점대점(Point-to-Point) | 특정 대상 하나(또는 명시된 소수)에게만 보내는 전송 방식 | 개인 메신저 1:1 대화 |
| 홈 노드(Home Node) | 특정 메모리 주소의 디렉터리 정보를 담당하는 노드 | 그 주소를 전담하는 총무과 지점 |
| SMP / NUMA | SMP는 모든 코어가 하나의 메모리·버스를 균일하게 공유하는 구조, NUMA는 노드마다 로컬 메모리를 두고 원격 접근은 더 느린 구조 | SMP=한 사무실, NUMA=여러 지사 연결망 |

## 깊이 이해

### 왜 버스 스누핑은 코어 수가 늘면 무너지는가 (수치로 보기)
- 공유 버스는 물리적으로 한 번에 하나의 트랜잭션만 실어 나를 수 있는 단일 통로다. 버스가 초당 처리할 수 있는 무효화 트랜잭션 수를 T(고정값)라 하자. 코어 하나가 평균 초당 k번의 쓰기(=무효화 방송)를 일으킨다면, 전체 요구량은 대략 N×k다.
- 예를 들어 버스가 초당 T=2,000건을 처리할 수 있고 코어 하나가 초당 k=50건의 쓰기를 낸다면, N=8일 때 요구량은 400건으로 여유(80% 미사용)가 있다. 하지만 N=40이면 요구량이 정확히 2,000건으로 버스 한계에 도달하고, N=64면 3,200건으로 60% 초과해 트랜잭션이 밀리며 파이프라인이 멈춘다(Stall). 코어 수가 늘수록 필요한 트래픽은 N에 비례(O(N))해 느는데, 버스 용량 T는 늘지 않으므로 어느 순간(대략 십수~수십 코어대) 반드시 병목이 온다.
- 반면 디렉터리 기반은 무효화를 "실제로 그 라인을 공유 중인 코어에게만" 보낸다. 공유자가 평균 m명(대개 m ≪ N)이라면 트랜잭션당 부하는 O(m)이라, 코어 수 N이 늘어도 트래픽이 N에 비례해 늘지 않는다. 이 O(N) vs O(m) 차이가 스누핑이 소규모에, 디렉터리가 대규모에 맞는 근본 이유다.

### 디렉터리의 대가 — 비트 벡터 오버헤드 (수치로 보기)
- 디렉터리는 공짜가 아니다. 각 캐시 라인마다 "누가 갖고 있나"를 기록할 공간이 필요하다. 캐시 라인 크기가 64바이트(512비트)이고 코어가 128개면, 순수 비트 벡터 방식은 라인 하나당 128비트(16바이트)의 디렉터리 정보가 추가로 필요하다. 이는 64바이트 데이터에 대해 16/64 = 25%의 메모리 오버헤드다 — 무시할 수 없는 크기다.
- 이를 줄이는 방법이 조대 디렉터리(Coarse Vector)다. 128개 코어를 8개씩 16개 그룹으로 묶으면 벡터가 16비트(2바이트)로 줄어 오버헤드가 2/64 = 3.1%로 떨어진다. 대신 무효화 신호를 보낼 때 그룹 전체(코어 8개)에 뿌려야 하므로 정밀도(누구에게만 보낼지)는 떨어진다 — 오버헤드와 정밀도의 트레이드오프다.

### 스누핑과 디렉터리의 지연시간 차이
- 스누핑은 브로드캐스트 즉시 모든 캐시가 동시에 신호를 받으므로 왕복 지연이 짧다(버스 전파 지연 정도).
- 디렉터리는 "요청 → 홈 노드(디렉터리) 조회 → 대상 코어에 전송 → 응답" 순서를 거치므로, 조회 한 단계가 추가되어 스누핑보다 기본 지연이 길다. 코어 수가 적을 땐 이 조회 단계가 순수 오버헤드로만 작용하므로 디렉터리가 스누핑보다 무조건 빠른 것은 아니다.

### 비유로 정리
- 스누핑 = 방송(Broadcast): 작은 동아리방에서 한 명이 "짜장면 먹을 사람?" 하고 외치면 3명이 도청(Snooping)하고 답한다. 인원이 4명이면 문제없지만 400명이면 아수라장이 된다.
- 디렉터리 = 연락처 기반 개별 통지(Unicast): 거대 회사의 총무과가 신청자 명부(Directory)를 보고, 해당자에게만 사내 메신저로 개별 연락한다. 관계없는 직원은 방해받지 않지만, 총무과에 물어보는 절차 자체가 시간이 든다.

### 흔한 오해·주의점
- "디렉터리 기반이 스누핑보다 항상 빠르다"는 틀렸다. 코어 수가 적을 때는 중앙 장부를 조회하는 절차 자체가 오버헤드라 스누핑이 더 빠르다. 코어 수가 수십 개를 넘어서야 디렉터리의 O(m) 트래픽 이점이 스누핑의 O(N) 한계를 압도한다.
- 스누핑·디렉터리는 MESI 같은 프로토콜을 대체하는 것이 아니라, 그 프로토콜의 상태 변경 신호를 "누구에게 어떻게 전달할지"를 정하는 하위 통신 계층이다. MESI 상태 자체는 두 방식 위에서 동일하게 유지된다.

## 연결 개념
- MESI/MOESI 프로토콜(앞 절) — 스누핑·디렉터리가 실어 나르는 상태 전이 규칙 자체 (배달 방식이 스누핑·디렉터리라면, 배달 내용물이 MESI다)
- 멀티코어 / NUMA — 스누핑은 SMP(단일 버스 공유) 규모에, 디렉터리는 NUMA(분산 노드) 규모에 적합하다
- CXL(Compute Express Link) — 최근 칩 외부의 가속기·메모리 풀까지 일관성을 확장하려는 표준화가 디렉터리 방식을 기반으로 진행되고 있다


# 📝 【답안용】 시험 답안 템플릿

> 목적: 시험장에서 25분에 그대로 쓰는 답안 양식. 

## 핵심 인사이트 (3줄 요약)

> 1. **본질**: 스누핑과 디렉터리 프로토콜은 멀티코어 환경에서 캐시 일관성(MESI) 제어 신호를 코어 간에 전파하기 위한 통신 아키텍처(라우팅) 모델이다.
> 2. **가치**: 스누핑은 공용 버스 도청을 통한 브로드캐스트로 0에 가까운 지연(Low Latency)을 제공하며, 디렉터리 방식은 중앙 명부를 통한 점대점(Point-to-Point) 통신으로 대규모 확장성(Scalability)을 보장한다.
> 3. **판단 포인트**: 프로세서 코어 수가 특정 임계점(약 16~32코어)을 넘어서면 스누핑 브로드캐스트가 시스템 대역폭을 마비시키므로, 매니코어(Many-core) 및 NUMA 서버에서는 디렉터리 기반 하드웨어 채택이 필수적이다.

## 출제 의도 및 답안 포인트
| 출제 의도 | 반드시 짚을 핵심 | 감점 회피 포인트 |
|:---|:---|:---|
| 멀티코어 시스템의 스케일아웃에 따른 동기화 병목 인식 | 스누핑의 버스 대역폭 한계(Broadcast) vs 디렉터리 장부의 오버헤드 | 두 방식을 설명하며 MESI 플래그 자체의 차이로 오해하는 것 (둘 다 MESI를 전송하는 인프라의 차이임) |
| 타겟 아키텍처에 따른 일관성 기법 선택 판단력 | 데스크톱(SMP/Ring 버스) = 스누핑, 대형 서버(NUMA/Mesh) = 디렉터리 | 어떤 아키텍처(코어 수)에 무엇이 적합한지 판단 기준을 누락 |

> 요약: 성능(Latency)이 우선인 소규모 버스망과, 버스 혼잡(Congestion) 방지가 우선인 대규모 노드망의 설계 트레이드오프를 철저히 대조해야 한다.


## Ⅰ. 개요 및 필요성

- 정의: 멀티 프로세서에서 캐시 라인의 상태(무효화, 공유 등) 변경을 모든 코어에 전파하기 위해, 버스 브로드캐스트를 쓰는 방식(스누핑)과 상태 명부를 쓰는 방식(디렉터리)
- 배경: 코어 집적도가 4~8코어(SMP)에서 수십~수백 코어(NUMA, 매니코어)로 급증하면서, 공유 버스의 물리적 대역폭 한계 도달
- 필요성: 시스템 규모(코어 수)에 맞춰 일관성 제어 트래픽이 일으키는 칩 내부 병목(Congestion)을 통제하고, 성능 확장성을 확보할 라우팅 전략 분리 요구


## Ⅱ. 버스 스누핑(Bus Snooping) 동작 원리

```text
[스누핑 기반 브로드캐스트 브로드캐스트 통신 흐름]
코어 A (쓰기 요청) -> [ 버스에 Invalidate 신호 무차별 송출 (Broadcast) ]
  |--> 코어 B (스누핑) -> 주소 불일치 (무시)
  |--> 코어 C (스누핑) -> 주소 일치 -> 로컬 상태를 I(무효화)로 변경
  |--> 코어 D (스누핑) -> 주소 불일치 (무시)
```

| 동작 요소 | 핵심 역할 및 특성 | 장점 및 한계점 |
|:---|:---|:---|
| 브로드캐스트 | 공유 버스(Shared Bus)에 무조건 신호를 뿌림 | **장점**: 제어 로직이 단순하고 전파 지연이 매우 짧음 |
| 스누퍼 회로 | 각 캐시 컨트롤러가 항상 버스의 주소를 도청(Snooping) | **단점**: 나랑 상관없는 신호도 들어야 해서 전력 소모 심화 |
| 버스 대역폭 | 코어 1개가 보낸 통신이 전체 버스 용량을 즉시 점유 | **한계**: 코어가 수십 개면 버스 경합 폭증으로 시스템 마비 |

> 요약: 스누핑은 모든 코어가 같은 버스를 물리적으로 공유하는 UMA(Uniform Memory Access) 아키텍처에 가장 찰떡궁합인 고속 해법이다.


## Ⅲ. 디렉터리 기반(Directory-based) 동작 원리

```text
[디렉터리 기반 중앙 집중 및 점대점 통신 흐름]
코어 A (쓰기 요청) -> [ 메인 메모리 단의 디렉터리(장부) 조회 ]
디렉터리 명부 비트맵: { 변수 X -> 코어 C만 공유 중 (상태=S) }
  |--> 디렉터리가 코어 C에게만 타겟팅된 Invalidate 전송 (Unicast)
코어 B, D는 버스 트래픽 방해 없이 본연의 연산 지속
```

| 동작 요소 | 핵심 역할 및 특성 | 장점 및 한계점 |
|:---|:---|:---|
| 디렉터리 메모리 | 어떤 코어가 어떤 캐시 라인을 들고 있는지(Bit Vector) 추적 | **장점**: 브로드캐스트 제거로 인터커넥트 트래픽 극적 감소 |
| P2P 통신망 | 메시(Mesh) 네트워크를 통해 타겟 코어에만 점대점 신호 전송 | **장점**: 128코어 이상의 NUMA 환경에서 스케일아웃 보장 |
| 메인 메모리 연계 | 각 메모리 블록마다 디렉터리 상태 비트를 별도 저장(오버헤드) | **단점**: 디렉터리를 조회하고 응답을 기다리는 기본 레이턴시 증가 |

> 요약: 디렉터리는 트래픽을 아끼기 위해 "명부를 찾고 조회하는 수고로움(시간 오버헤드)"과 "명부 보관소(메모리 오버헤드)"를 감수하는 전략이다.

## Ⅳ. 심화 비교: 스누핑 vs 디렉터리 확장성 대조

| 비교 축 | 버스 스누핑 (Bus Snooping) | 디렉터리 기반 (Directory Coherence) | 아키텍처 선택 기준 |
|:---|:---|:---|:---|
| 라우팅 방식 | 무차별 브로드캐스트 (Broadcast) | 타겟 지정 유니캐스트 (Point-to-Point) | 네트워크 스위칭 구조 의존 |
| 통신 트래픽 | O(N) (모두에게 전송) | O(1) ~ O(K) (공유 중인 대상에게만) | 버스 대역폭 포화 한계 |
| 기본 지연시간 | 짧음 (버스를 쏘면 즉시 모두 수신) | 상대적으로 긺 (디렉터리 조회 후 재발송) | 빠른 동기화 vs 확장의 안정성 |
| 상태 저장공간 | 로컬 캐시 내부 Tag에만 존재 | 캐시 내부 + 메인 메모리 디렉터리 표 | 램(RAM) 오버헤드 허용 수준 |
| 타겟 코어 수 | 최대 8~16코어 (SMP 아키텍처) | 64코어 ~ 무한대 (NUMA 아키텍처) | 데스크톱/모바일 vs 클라우드/HPC |

> 요약: 클라이언트 PC는 "빠른 스누핑"을 쓰고, 클라우드 데이터센터 서버 칩은 "교통정리가 확실한 디렉터리"를 쓴다.

## Ⅴ. 제약 사항 및 하이브리드 프로토콜 판단

| 확장 리스크 | 발생 원인 (디렉터리의 한계) | 아키텍처 대응 방안 | 성능 지표 |
|:---|:---|:---|:---|
| 메모리 오버헤드 | 코어 128개 시, 모든 메모리 블록에 128비트 벡터(누가 가졌는지)를 달아야 해 RAM 낭비 극심 | 조대 디렉터리(Coarse Vector): 코어를 그룹화하여 비트맵 축소 | 메모리 풋프린트 오버헤드 5% 이내 억제 |
| 홈 노드 병목 | 특정 메모리 블록(Home)에 쓰기 요청이 몰리면 해당 디렉터리 컨트롤러 마비 | 해시 기반 메모리 주소 분산 배치 (Interleaving) | 노드 간 레이턴시 편차 최소화 |
| 타협점(하이브리드)| 스누핑과 디렉터리 단점 동시 노출 | 칩 내부는 스누핑, 칩 간(Socket)은 디렉터리 기반 혼용 | 칩 내부 지연시간 및 소켓 간 대역폭 |

> 요약: 디렉터리 방식도 코어가 수백 개가 되면 명부(Bit Vector)가 기형적으로 커지므로, 트리 구조나 해시 구조로 압축하는 최적화가 필수적이다.


## Ⅵ. 실무 적용 및 결론
**적용 방안 3개:**
1. 매니코어(Many-core) 메시 네트워크 도입: 인텔 제온(Xeon) 스케일러블 시리즈 등 50코어 이상 프로세서 설계 시, 링 버스(스누핑)를 버리고 2D 메시 구조 인터커넥트를 적용하며 타일(Tile)마다 분산 디렉터리 컨트롤러를 배치해 일관성 트래픽 분산
2. 하이브리드 NUMA 일관성 구현: 대규모 AMD EPYC 서버 구성 시, 하나의 칩셋(CCX 단위, 4~8코어) 내부는 빠른 버스 스누핑으로 처리하고, 칩셋 외부나 다른 소켓(Socket)으로 신호가 넘어갈 때만 Infinity Fabric 기반 디렉터리 프로토콜을 통하도록 하여 지연과 확장성 동시 타협
3. 디렉터리 캐시 (Directory Cache) 적용: 디렉터리 정보를 읽기 위해 매번 느린 메인 메모리를 다녀오는 지연을 막기 위해, 프로세서 내부에 SRAM 기반의 소형 디렉터리 전용 캐시를 탑재하여 최근 공유된 변수의 명부 조회(Lookup) 지연 0사이클 은닉

**결론 (2줄):**
- 기술사 판단: 코어 간 캐시 동기화 아키텍처는 시스템 규모(N)가 작을 때는 스누핑의 낮고 빠른 레이턴시가 유리하나, N이 증가함에 따라 브로드캐스트의 물리적 한계를 유니캐스트로 해소하는 디렉터리 기반으로 반드시 임계 전환되어야 한다.
- 향후 방향: CXL(Compute Express Link) 기반 메모리 확장 시대가 열리면서, 단순히 칩 내부 코어뿐 아니라 외부 가속기(GPU, NPU) 및 메모리 풀까지 캐시 일관성을 유지하기 위해 디렉터리 프로토콜의 표준화(CXL.cache)가 넥스트 패러다임으로 정착하고 있다.
