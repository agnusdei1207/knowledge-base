## Ⅰ. 개요
- **정의**: 다수의 GPU를 클러스터로 구성하고 워크로드를 분산하여 처리 규모를 확장하는 기법
- **배경/필요성**: 단일 GPU의 메모리·연산 한계로 대규모 모델 학습 시 다중 GPU 병렬 처리가 필수적임
- **비유**: 한 사람이 못 드는 짐을 여러 사람이 나눠 드는 것과 유사하되, 사람 간 소통 비용이 핵심 변수임

| 출제 의도 | 반드시 짚을 핵심 | 감점 회피 포인트 |
|:---|:---|:---|
| 대규모 병렬 시스템 설계 역량 확인 | 스케일업/스케일아웃 구분과 통신 병목 | 선형 확장이 안 되는 이유(통신 오버헤드)를 논리적으로 서술 필요 |

> 요약: 다수 GPU를 묶어 연산 규모를 확장하되 통신 오버헤드 관리가 핵심인 기법임

## Ⅱ. 구성요소
```text
+-- Node 0 --+    +-- Node 1 --+
| GPU0  GPU1 |<-->| GPU2  GPU3 |
| NVLink     |    | NVLink     |
+-----+------+    +-----+------+
      |   InfiniBand/RoCE   |
      +---------+-----------+
                |
          +-----+------+
          |  Scheduler  |
          +-------------+
```

| 구성요소 | 설명 | 비유 |
|:---|:---|:---|
| 노드 내 인터커넥트 (NVLink) | 동일 노드 내 GPU 간 고대역폭 저지연 연결 | 같은 방 안에서 직접 물건을 건네는 것 |
| 노드 간 인터커넥트 (IB/RoCE) | 서로 다른 노드를 연결하는 네트워크 패브릭 | 건물 사이를 잇는 운송 도로 |
| 분산 스케줄러 | 워크로드를 GPU에 할당하고 동기화를 관리하는 제어 계층 | 작업 배분을 총괄하는 현장 감독 |
| 집합 통신 라이브러리 (NCCL 등) | AllReduce 등 GPU 간 그래디언트 교환을 최적화하는 SW 계층 | 일꾼들이 결과를 모아 공유하는 프로토콜 |

> 요약: 노드 내·간 인터커넥트, 스케줄러, 집합 통신 라이브러리가 확장성을 결정함

## Ⅲ. 절차
```text
모델 분할 --> GPU 배치 --> 집합 통신 --> 그래디언트 동기화
```
- 1단계: 모델/데이터를 병렬화 전략(데이터·텐서·파이프라인)에 따라 분할
- 2단계: 분할된 파티션을 토폴로지 인지 방식으로 각 GPU에 배치
- 3단계: 학습 반복마다 AllReduce 등 집합 통신으로 그래디언트 교환 수행
- 4단계: 동기화된 그래디언트로 파라미터를 갱신하고 다음 반복 진행

> 요약: 분할-배치-통신-동기화 순환으로 대규모 분산 학습을 수행함

## Ⅳ. 문제점
- 통신 병목: GPU 수 증가 시 AllReduce 통신량이 비례 증가하여 연산 대기 시간이 늘어남
- 메모리 단편화: 파이프라인 병렬 시 마이크로배치 간 활성화 메모리가 불균등하게 점유됨
- 장애 전파: 단일 GPU 고장 시 동기식 학습 전체가 중단되어 가용성이 저하됨

> 요약: 통신 병목·메모리 단편화·장애 전파가 선형 확장을 저해하는 주요 원인임

## Ⅴ. 개선방안
1. 단기: 통신-연산 오버랩(Overlap) 기법으로 통신 대기 시간 은닉
2. 중기: 활성화 재계산(Activation Checkpointing)과 메모리 풀링으로 단편화 해소
3. 장기: 비동기 학습 + 탄력적 스케줄링(Elastic Training)으로 장애 시 자동 복구

> 요약: 통신 은닉·메모리 최적화·탄력적 학습 순으로 확장 효율을 높여 나감

## Ⅵ. 전망
- 발전 방향: 수만 GPU 규모의 초대형 클러스터에서 네트워크 토폴로지 최적화가 핵심 과제로 부상
- 기술사적 판단: AI 학습 인프라의 규모가 곧 경쟁력이 되면서 스케일링 설계 역량이 필수화됨
- 기술사 제언: 통신 토폴로지와 병렬화 전략을 워크로드 특성에 맞게 공동 최적화할 필요
