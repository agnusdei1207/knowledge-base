# 📖 【암기용】 개념 완전 이해

> 목적: 클럭 속도 경쟁이 왜 끝났으며, 멀티코어로 넘어오면서 어떤 새로운 병목(캐시, 동기화)이 생겼는지 완벽히 이해하게 만든다.

## 한눈에
- **개요**: 하나의 반도체 칩(Die) 안에 두 개 이상의 독립적인 처리 엔진(Core)을 집적한 마이크로프로세서
- **왜 필요한가**: 클럭 주파수를 높여 성능을 올리는 방식(싱글코어)은 발열과 전력 누수 때문에 더 이상 불가능해졌다(Power Wall). 그래서 약간 느리더라도 여러 명의 일꾼(코어)을 투입해 일을 나눠서 끝내는 방식으로 전략을 바꿨다.
- **핵심 직관**: 1명의 요리사가 불을 미친 듯이 세게 켜고 요리하다가 주방이 타버릴 뻔하자(발열 한계), 불을 적당히 켜고 요리사 4명을 고용해 주방을 4칸으로 쪼갠 것이다.

## 깊이 이해
- **배경·문제의식**: 2000년대 중반 인텔의 펜티엄 4는 4GHz를 돌파하려다 막대한 열을 감당하지 못하고 포기했다(폴락의 법칙: 트랜지스터를 늘려도 성능 향상은 제곱근에 그친다). 또한 하나의 코어 안에서 명령어 병렬성(ILP)을 쥐어짜는 것도 구조적 한계(ILP Wall)에 다다랐다. 이에 업계는 스레드 수준의 병렬성(TLP)으로 방향을 선회했다.
- **작동 원리**: 
  - 각 코어는 자신만의 독립적인 제어장치(CU), 연산장치(ALU), 그리고 1차(L1)/2차(L2) 전용 캐시를 가진다.
  - 이 코어들은 칩 내부의 고속 링 버스(Ring Bus)나 메시(Mesh) 네트워크로 연결되어 있으며, 마지막 3차(L3) 캐시를 공유한다.
  - OS가 여러 개의 작업(프로세스/스레드)을 각 코어에 분배하여 진짜 동시에(True Parallelism) 실행한다.
- **비유**: 4코어 프로세서는 머리가 4개 달린 괴물이다. 각 머리는 자기 앞에 놓인 전용 접시(L1, L2 캐시)에서 밥을 먹고, 가끔 큰 공용 냄비(L3 캐시)에서 국을 퍼먹는다. 
- **구체 예시**: 웹 브라우저를 켜면서 넷플릭스를 보고 백그라운드로 바이러스 검사를 돌릴 때, 과거 싱글코어는 이 3개를 0.001초씩 번갈아 가며 했지만(시분할), 지금 4코어 CPU는 이 3개를 각자 다른 코어에서 "동시에" 처리한다.
- **흔한 오해·주의점**: "코어가 4개면 무조건 4배 빠르다"는 심각한 오해다. 프로그램 자체가 혼자서 순서대로만 해야 하는 작업(직렬 코드)이라면 코어 3개는 놀고 1개만 일하게 된다. 이를 수학적으로 증명한 것이 '암달의 법칙(Amdahl's Law)'이다.

## 연결 개념
- 스레드 수준 병렬성 (TLP) — 멀티코어가 실제로 처리하는 병렬성의 종류
- 캐시 일관성 (Cache Coherence) — 여러 코어가 동일한 데이터를 각자 L1 캐시로 가져가 수정할 때 값이 틀어지는 문제를 막는 기술
- 대칭형 다중 처리 (SMP) — 여러 코어가 동일한 권한으로 메모리를 공유하는 멀티코어의 기본 아키텍처

# 📝 【답안용】 시험 답안 템플릿

> 목적: 시험장에서 25분에 그대로 쓰는 답안 양식. 

## 핵심 인사이트 (3줄 요약)

> 1. **본질**: 멀티코어 프로세서는 단일 실리콘 다이(Die)에 복수의 코어를 집적하여, 스레드 수준 병렬성(TLP)을 하드웨어적으로 구현한 대칭형 다중 처리(SMP) 아키텍처다.
> 2. **가치**: 클럭 주파수 상승에 따른 전력 벽(Power Wall)과 ILP의 한계를 우회하여, 낮은 전력 소모로 전체 시스템의 스루풋(Throughput)을 기하급수적으로 확장한다.
> 3. **판단 포인트**: 코어 수가 늘어날수록 성능은 암달의 법칙에 의해 수렴하며, 병목의 핵심은 코어 자체가 아니라 코어 간 공유 자원(L3 캐시, 메모리 버스)의 일관성 동기화 오버헤드에 있다.

## 출제 의도 및 답안 포인트

| 출제 의도 | 반드시 짚을 핵심 | 감점 회피 포인트 |
|:---|:---|:---|
| 프로세서 진화 방향(싱글 -> 멀티)의 필연성 이해 | 전력 벽(Power Wall), ILP 한계 돌파, TLP 패러다임 전환 | 왜 싱글코어를 포기했는지 원인(전력/발열)을 빼놓고 구조만 서술 |
| 멀티코어 아키텍처의 구조적 병목 및 제약 이해 | 암달의 법칙(병렬화 한계), 캐시 일관성(MESI), 상호연결망 | 코어가 늘면 무조건 성능이 비례 증가한다고 서술하는 오류 |

> 요약: 멀티코어는 연산력의 증가가 아니라 "병목 지점의 이동(코어 내부 -> 코어 간 통신 및 공유 메모리)"임을 명확히 서술해야 한다.

## Ⅰ. 개요 및 필요성

- 정의: 단일 칩 패키지(SoC) 안에 두 개 이상의 독립적인 프로세싱 코어를 결합하여 다중 스레드를 동시 실행하는 아키텍처
- 배경: 트랜지스터 집적도 증가에도 불구하고, 클럭 주파수 상향에 따른 발열(Power Wall)과 명령어 병렬성(ILP) 한계 도달
- 필요성: 개별 코어의 클럭을 낮춰 전력 소모를 억제하면서도, OS의 다중 프로세스/스레드 배분(TLP)을 통해 전체 시스템 처리량 극대화

---

## Ⅱ. 구조 및 구성요소 (공유 및 독립 아키텍처)

```text
[멀티코어 프로세서 칩(Die) 내부 아키텍처]
+---------------------------------------------------+
|  [Core 0]  [Core 1]  [Core 2]  [Core 3]           |
|   L1/L2     L1/L2     L1/L2     L1/L2  (독립 캐시)|
|     |         |         |         |               |
| <======= 고속 상호연결망 (Ring Bus / Mesh) ======>|
|                         |                         |
|             [ L3 Shared Cache (공유 캐시) ]       |
+---------------------------------------------------+
              | 통합 메모리 컨트롤러 (IMC) |
```

| 구성요소 | 핵심 역할 | 상세 하위 요소 / 특징 |
|:---|:---|:---|
| 코어 (Core) | 스레드 단위의 독립적인 명령어 처리 엔진 | 제어장치(CU), 연산장치(ALU), 프라이빗 L1/L2 캐시 |
| LLC (Last Level Cache) | 코어 간 데이터 공유 및 메인 메모리 접근 지연 은닉 | 일반적으로 공유 L3 캐시 구조 채택 (용량 대형화) |
| 상호 연결망 (Interconnect) | 코어와 코어, 코어와 공유 캐시 간 고속 데이터 전송 | 링 버스(Ring Bus), 2D 메시 네트워크(Mesh) |
| 캐시 일관성 컨트롤러 | 각 코어의 L1/L2 캐시 간 데이터 정합성 유지 제어 | 스누핑(Snooping), 디렉터리(Directory) 기반 동기화 |

> 요약: 코어 자체의 연산력보다, 코어들이 어떻게 충돌 없이 데이터를 주고받느냐(캐시 계층과 연결망)가 전체 성능을 지배한다.

## Ⅲ. 동작원리 및 흐름도 (스레드 병렬 실행 처리)

```text
[OS의 멀티스레드 분배 및 동기화 흐름]
OS Task Scheduler -> 스레드 1 (Core 0 할당), 스레드 2 (Core 1 할당)
-> 각 코어 독립 실행 (TLP 달성)
-> 동일 데이터 수정 발생 시 -> 캐시 일관성 프로토콜(MESI) 개입 -> 데이터 동기화
```

| 단계 | 제어 주체 | 처리 내용 (TLP 워크플로우) |
|:---:|:---|:---|
| 1 | 작업 분배 | OS 스케줄러가 코어들의 부하 상태를 파악해 준비된 스레드를 각 코어에 분산 할당 (SMP) |
| 2 | 병렬 실행 | 각 코어가 독립된 L1/L2 캐시를 사용하여 명령어와 데이터를 인출하고 비순차 실행(OoO) 처리 |
| 3 | 일관성 유지 | Core 0이 공유 변수 'A'를 수정하면 하드웨어가 Core 1의 캐시에 있는 'A'를 무효화(Invalidate) |
| 4 | 컨텍스트 스위칭 | 특정 스레드가 I/O 대기에 빠지면 코어는 즉각 다른 스레드로 교환하여 연산 유휴(Idle) 최소화 |

> 요약: 스레드를 분배하는 소프트웨어(OS)와, 쪼개진 데이터의 무결성을 맞추는 하드웨어(캐시 일관성 컨트롤러)가 협력한다.

## Ⅳ. 핵심 제약: 암달의 법칙 (Amdahl's Law)

| 개념 축 | 암달의 법칙 (Amdahl's Law)의 시사점 |
|:---|:---|
| 수식 | 전체 성능 향상률 = 1 / [ (1 - 병렬화율) + (병렬화율 / 코어 수) ] |
| 병목 원인 | 프로그램 내에는 반드시 순차 실행만 가능한 "직렬 코드(초기화, 취합, 락)"가 존재 |
| 한계 지표 | 직렬 코드가 25%라면, 코어 수를 무한대로 늘려도 최대 성능 향상은 4배(1/0.25)로 수렴 |
| 기술사 판단 | 아무리 코어 수를 늘려도 소프트웨어 아키텍처(직렬성 해소)가 개선되지 않으면 칩 면적만 낭비됨 |

> 요약: 멀티코어의 성능 한계는 하드웨어가 아니라, 락(Lock)이나 임계 구역(Critical Section)이 유발하는 "직렬 코드의 비율"에 의해 결정된다.

## Ⅴ. 심화 비교 및 성능 병목 판단

| 비교 축 | 단일 코어 (Single Core) | 멀티 코어 (Multi-Core SMP) | NUMA (다중 물리 소켓) |
|:---|:---|:---|:---|
| 병렬성 중심 | ILP (명령어 수준 병렬) | TLP (스레드 수준 병렬) | 서버 스케일 TLP |
| 메모리 접근 | 1코어가 모두 독점 | 다중 코어가 단일 메모리 공유 | 소켓별 지역 메모리 분리 |
| 병목 지점 | 파이프라인 데이터 해저드 | 공유 L3 캐시 경합 및 일관성 오버헤드 | 원격(Remote) 노드 메모리 접근 지연 |
| 해결 기술 | 비순차 실행 (OoO) | MESI 프로토콜, Mesh 버스 | NUMA-Aware OS 스케줄링 |

> 요약: PC와 일반 서버는 단일 칩 내 메모리를 공유하는 SMP 멀티코어를 쓰며, 대형 DB 서버는 칩 여러 개를 묶는 NUMA 아키텍처로 확장된다.

| 점검 항목 | 목표 기준 | 측정 방법 |
|:---|:---|:---|
| 캐시 미스율 | 캐시 공유로 인한 스래싱 방지, L3 적중률 90% 방어 | 하드웨어 성능 카운터 분석 |
| 락(Lock) 경합 지연 | 동기화 오버헤드 및 스레드 대기 시간 10% 이하 | 소프트웨어 프로파일러 (Mutex 분석) |

## Ⅵ. 실무 적용 및 결론

**적용 방안 3개:**
1. 데이터 파티셔닝(Sharding): DBMS 및 대규모 웹 애플리케이션 개발 시, 암달의 법칙 한계를 깨기 위해 스레드 간 락(Lock)을 유발하는 공유 메모리 변수를 제거하고 데이터를 코어별로 분할(Partition) 처리
2. 하이퍼스레딩(SMT) 활성화: 코어 내부의 파이프라인 자원이 낭비되는 것을 막기 위해, 코어 1개당 논리 프로세서를 2개로 노출(예: 8코어 16스레드)시켜 물리 코어의 유휴 시간을 최소화
3. NUMA-Aware 스케줄링 적용: 다중 소켓 멀티코어 서버(예: 128코어 인스턴스) 운영 시, 프로세스가 자신이 할당된 코어와 가까운 로컬 메모리(Local Node)만 쓰도록 리눅스 `numactl`로 묶어 원격 메모리 지연 원천 차단

**결론 (2줄):**
- 기술사 판단: 클럭 주파수 경쟁이 가져온 전력 장벽(Power Wall)은 멀티코어로 우회하였으나, 이제는 다중 스레드를 먹여 살리기 위한 '메모리 대역폭의 벽(Memory Wall)'과 마주하고 있다.
- 향후 방향: 일반적인 코어 수 확장은 한계에 달했으며, 고성능 코어와 고효율 코어를 섞는 이기종 설계(big.LITTLE) 및 특정 워크로드를 하드웨어로 가속하는 NPU/칩렛(Chiplet) 구조로 패러다임이 전환 중이다.
