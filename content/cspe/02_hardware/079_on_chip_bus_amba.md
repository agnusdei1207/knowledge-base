## Ⅰ. 개요
- **정의**: SoC 내부 IP 간 데이터 전송을 위한 ARM 표준 온칩 버스 프로토콜 체계임
- **배경/필요성**: SoC 내 IP가 증가하면 각기 다른 인터페이스가 난립하므로, 표준 버스로 IP 연결 규격을 통일할 필요가 있음
- **비유**: 건물 내부 복도 규격을 통일하여 모든 방이 같은 방식으로 연결되는 것과 유사함

| 출제 의도 | 반드시 짚을 핵심 | 감점 회피 포인트 |
|:---|:---|:---|
| AMBA 프로토콜 계층과 특성 비교 | AHB vs AXI 차이, 버스 대역폭 산정 | NoC(080 참조)와의 확장성 차이를 언급할 것 |

> 요약: SoC IP 간 표준 통신을 제공하는 ARM의 온칩 버스 프로토콜 체계임

## Ⅱ. 구성요소
```text
        +--- AXI (High-Performance) ---+
        |                              |
Master --+--- AHB (System Bus) --------+-- Slave
        |                              |
        +--- APB (Peripheral Bus) -----+
```

| 구성요소 | 설명 | 비유 |
|:---|:---|:---|
| AXI | 고대역 다중 채널 버스, 읽기/쓰기 독립 채널 5개 지원함 | 왕복 8차선 고속도로 |
| AHB | 파이프라인 단일 버스, 중간 대역 시스템 연결에 사용함 | 왕복 4차선 국도 |
| APB | 저속 주변장치용 2단계(Setup-Access) 단순 버스임 | 이면도로 |

> 요약: AXI(고속)-AHB(중속)-APB(저속) 3계층으로 IP를 대역 요구에 맞게 연결함

## Ⅲ. 절차
```text
Master요청 --> Arbiter중재 --> Decoder주소해석 --> Slave응답
```
- 1단계: Master가 주소·제어 신호를 버스에 올림
- 2단계: Arbiter가 다중 Master 요청을 우선순위 기반으로 중재함
- 3단계: Decoder가 주소를 해석하여 대상 Slave를 선택함
- 4단계: Slave가 데이터를 반환하거나 `HREADY`/`RVALID` 신호로 완료를 통지함

> 요약: 요청-중재-주소해석-응답의 4단계로 버스 트랜잭션이 완료됨

## Ⅳ. 문제점
- 공유 버스 병목: AHB는 단일 트랜잭션만 허용하여 Master 수 증가 시 대기 시간이 선형 증가함
- 확장성 한계: 버스 토폴로지는 IP 수가 수십 개를 넘으면 배선 혼잡과 클럭 스큐가 심화됨
- 전력 오버헤드: 유휴 IP에도 클럭이 공급되어 동적 전력이 낭비됨

> 요약: 공유 버스 병목, 확장성 한계, 전력 낭비가 AMBA 버스의 주요 과제임

## Ⅴ. 개선방안
1. 단기: AXI 크로스바 인터커넥트 도입으로 다중 동시 트랜잭션을 허용함
2. 중기: NoC(080 참조) 전환으로 수백 개 IP 연결 시 확장성을 확보함
3. 장기: 클럭 게이팅·파워 도메인 분리로 유휴 IP의 전력 소비를 차단함

> 요약: 크로스바, NoC 전환, 클럭 게이팅으로 버스 한계를 극복함

## Ⅵ. 전망
- 발전 방향: AMBA 5 CHI 프로토콜이 캐시 코히런시를 내장하여 멀티코어 SoC에 대응함
- 기술사적 판단: IP 수 증가로 버스에서 네트워크(NoC)로의 전환이 가속되는 추세임
- 기술사 제언: SoC 규모에 따라 버스/NoC 하이브리드 인터커넥트 전략 수립이 필요함
