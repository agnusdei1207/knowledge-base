# 📖 【암기용】 개념 완전 이해

> 목적: RISC와 CISC를 처음 봐도 왜 같은 프로그램이 아키텍처에 따라 명령어 개수와 실행 방식이 달라지는지 이해하게 만든다. 시험 답안 양식이 아니라, 이해를 위한 친절한 설명이다.

## 한눈에
- **개요**: ISA(Instruction Set Architecture)를 명령어 개수·복잡도 설계 철학으로 나눈 분류로, RISC는 적고 단순한 명령어, CISC는 많고 복잡한 명령어를 지향한다.
- **왜 필요한가**: 이 구분을 알아야 왜 ARM·RISC-V는 명령어 길이가 고정이고 x86은 가변인지, 왜 파이프라이닝 효율이 아키텍처마다 다른지를 설명할 수 있다.
- **핵심 직관**: RISC는 "짧은 문장만 쓰되 여러 번 말하는" 화법이고, CISC는 "한 문장에 많은 뜻을 담되 문장 길이가 들쭉날쭉한" 화법이다.

## 깊이 이해
- **배경·문제의식**: 1970년대 CISC(예: DEC VAX, IBM System/360)는 컴파일러가 단순했던 시절 소프트웨어 부담을 하드웨어로 옮기려 복잡한 명령어(문자열 연산, 메모리-메모리 연산 등)를 늘렸다.
- 1980년대 IBM 801 프로젝트와 UC Berkeley RISC 프로젝트(패터슨), Stanford MIPS 프로젝트(헤네시)는 "자주 쓰는 단순 명령어를 빠르게" 실행하는 편이 전체 성능에 유리하다는 통계적 근거(명령어 사용 빈도 분석)를 바탕으로 RISC 개념을 제시했다.
- **작동 원리 — RISC**: 명령어 길이를 고정(예: 32비트)해 디코드 단계를 단순화하고, load/store 명령어만 메모리에 접근하는 load-store 아키텍처를 채택해 연산 명령어는 레지스터끼리만 동작한다.
- RISC는 범용 레지스터 수를 늘려(예: 32개) 메모리 접근 빈도를 줄이고, 주소지정 방식 종류를 단순화해 하드와이어드 CU로 1클럭당 1명령어 처리(IPC 1.0)에 가깝게 설계한다.
- **작동 원리 — CISC**: 명령어 길이를 가변(예: x86은 1~15바이트)으로 허용해 복잡한 연산(문자열 처리, BCD 연산 등)을 한 명령어로 표현하고, 메모리 피연산자를 직접 다루는 다양한 주소지정 방식을 지원한다.
- CISC는 마이크로프로그램 CU로 복잡한 명령어를 여러 마이크로 오퍼레이션으로 분해 실행하며, 동일 작업을 더 적은 명령어 수로 표현해 프로그램 코드 크기(static code size)를 줄이는 데 유리하다.
- **비유**: RISC는 "짧은 지시어만 쓰되 여러 번 반복해서 말하는" 화법이고, CISC는 "한 문장에 많은 의미를 압축하되 문장 길이가 들쭉날쭉한" 화법이다.
- **구체 예시**: CISC의 `MOVS` 계열 문자열 복사 명령어는 메모리 간 반복 복사를 한 명령어로 처리하지만, RISC는 같은 작업을 load-add-store 루프 명령어 여러 개로 표현한다.
- 현대 x86(CISC ISA)은 내부적으로 CISC 명령어를 디코더에서 RISC 스타일의 마이크로 오퍼레이션(micro-op, uop)으로 변환한 뒤 실행하는 하이브리드 방식을 사용한다.
- **흔한 오해·주의점**: "RISC는 명령어 수가 적다"는 명령어 집합의 종류 수가 적다는 뜻이지, 프로그램을 구성하는 명령어 개수(동적 명령어 수)가 적다는 뜻이 아니다. 같은 작업을 RISC는 더 많은 명령어로, CISC는 더 적은 명령어로 표현하는 경향이 있다.
- "CISC는 항상 느리다"도 성립하지 않는다. 현대 x86 계열은 내부 uop 변환과 슈퍼스칼라·비순차 실행으로 RISC 계열과 유사한 IPC를 달성하는 경우가 많다.

## 연결 개념
- RISC-V — RISC 설계 철학을 오픈소스 ISA로 구현한 사례
- ARM 아키텍처 — 상업적으로 성공한 대표 RISC ISA
- x86-64 아키텍처 — CISC ISA를 확장한 대표 사례이자 내부 RISC 변환 구조
- 파이프라이닝 — RISC의 고정 길이·단순 명령어가 파이프라인 설계를 쉽게 만드는 배경
- CPU 구성(CU 설계) — 하드와이어드(RISC 지향)·마이크로프로그램(CISC 지향)과 직결

# 📝 【답안용】 시험 답안 템플릿

> 목적: 시험장에서 25분에 그대로 쓰는 답안 양식. 작성방식(추상표현 금지·수치·도식·문제유형 전환)을 엄격히 지킨다.
> 핵심: RISC/CISC를 특징 나열로 답하지 않고, 명령어 길이·주소지정·CU 방식이 성능·코드 크기에 미치는 영향과 현대 하이브리드화 근거를 함께 제시한다. (124회 기출 대응)

## 핵심 인사이트 (3줄 요약)

> 1. **본질**: RISC(Reduced Instruction Set Computer)는 고정 길이·단순 명령어와 load-store 구조를, CISC(Complex Instruction Set Computer)는 가변 길이·복잡 명령어와 메모리 직접 연산을 지향하는 ISA 설계 철학이다.
> 2. **가치**: RISC는 파이프라인 효율과 IPC 극대화에, CISC는 프로그램 코드 크기 축소와 복잡 연산의 명령어 압축에 유리하다.
> 3. **판단 포인트**: 현대 CPU는 명칭상 RISC/CISC로 나뉘지만 x86도 내부적으로 uop 변환을 통해 RISC 실행 방식을 채택하는 하이브리드가 일반적이므로, 선택 기준은 ISA 자체보다 생태계(툴체인·라이선스)와 목표 워크로드에 있다.

## 출제 의도 및 답안 포인트

| 출제 의도 | 반드시 짚을 핵심 | 감점 회피 포인트 |
|:---|:---|:---|
| RISC/CISC 설계 철학 이해 확인 | 명령어 길이, load-store 여부, CU 방식(하드와이어드/마이크로프로그램) | 두 방식을 단순히 "빠르다/느리다"로만 서술 |
| 파이프라이닝과의 연결 이해 확인 | 고정 길이·단순 명령어가 디코드·파이프라인에 미치는 영향 | RISC/CISC 설명에서 파이프라인 연관성 누락 |
| 현대 CPU 하이브리드화 인식 확인 | x86의 CISC-to-uop 내부 변환 구조 | "CISC는 항상 느리다"는 절대화된 서술 |

> 요약: 이 문제는 RISC/CISC 명칭 구분이 아니라 명령어 설계가 파이프라인·코드 크기·성능에 미치는 영향과 현대 하이브리드화 근거를 요구한다.

## Ⅰ. 개요 및 필요성

- 정의: ISA를 명령어 개수·복잡도 설계 철학으로 나눈 분류로, RISC는 단순·고정 길이, CISC는 복잡·가변 길이 명령어를 지향
- 배경: 1980년대 IBM 801·Berkeley RISC·Stanford MIPS 프로젝트가 명령어 사용 빈도 분석을 근거로 단순 명령어 고속 처리 개념을 제시
- 필요성: 명령어 설계 방식이 파이프라인 효율, 코드 크기, 컴파일러 최적화 여지를 결정하므로 워크로드에 맞는 ISA 선택 기준이 필요

---

## Ⅱ. 구조 및 구성요소

```text
ISA 설계 철학
  / RISC: 고정 길이 명령어 -> Load-Store 구조 -> 다수 범용 레지스터 -> 하드와이어드 CU
  / CISC: 가변 길이 명령어 -> 메모리 직접 연산 -> 소수 레지스터(역사적) -> 마이크로프로그램 CU
현대 x86: CISC 명령어 디코드 -> RISC 스타일 micro-op 변환 -> 실행
```

| 구성요소 | RISC | CISC |
|:---|:---|:---|
| 명령어 길이 | 고정(예: 32비트) | 가변(예: x86 1~15바이트) |
| 메모리 접근 | load/store 명령어만 허용 | 대부분 명령어가 메모리 피연산자 직접 접근 |
| CU 방식 | 하드와이어드 위주 | 마이크로프로그램 위주 |
| 대표 사례 | ARM, RISC-V, MIPS, POWER | x86, 레거시 VAX·System/360 |

> 요약: RISC는 명령어를 단순·고정화해 하드웨어 제어를 쉽게 하고, CISC는 복잡한 명령어로 코드 표현을 압축한다.

---

## Ⅲ. 동작원리 및 흐름도

```text
RISC: Fetch(고정 길이) -> Decode(단순 opcode) -> Register-Register 연산 -> (필요시)Load/Store -> Writeback
CISC: Fetch(가변 길이, 길이 판별 필요) -> Decode(마이크로코드 매핑) -> Micro-op 순차 실행(메모리 직접 접근 포함) -> Writeback
```

| 단계 | RISC 처리 | CISC 처리 |
|:---:|:---|:---|
| 1 | 고정 길이로 다음 명령어 경계 즉시 판별 | 가변 길이로 명령어 경계를 순차 판별 |
| 2 | 단순 opcode를 하드와이어드 회로로 즉시 디코드 | 마이크로코드 ROM에서 실행 순서 조회 |
| 3 | 레지스터 간 연산, 메모리 접근은 load/store로 한정 | 메모리 피연산자를 명령어 내에서 직접 연산 |
| 4 | 파이프라인 단계별로 예측 가능한 지연 | 명령어별 실행 사이클 수 편차 발생 |

> 요약: RISC는 명령어 경계와 디코드가 단순해 파이프라인 지연이 예측 가능하고, CISC는 명령어 길이 판별과 마이크로코드 조회로 지연 편차가 발생한다.

## Ⅳ. 특징

| 구분 | RISC | CISC | 수치·표준 포인트 |
|:---|:---|:---|:---|
| 명령어 길이 | 고정(예: ARM A64 32비트) | 가변(예: x86-64 최대 15바이트) | 디코더 복잡도 차이 |
| 코드 크기 | 동일 작업에 더 많은 명령어 필요 경향 | 동일 작업을 더 적은 명령어로 압축 경향 | 정적 코드 크기(binary size) |
| 파이프라인 적합성 | 단순 디코드로 파이프라인 설계 용이 | 가변 길이로 디코드 단계 복잡 | IPC 목표 달성 난이도 |
| CU 방식 | 하드와이어드 위주 | 마이크로프로그램 위주, 현대는 uop 캐시 병행 | 마이크로코드 패치 가능성 |

> 요약: RISC는 파이프라인 효율, CISC는 코드 압축과 명령어 표현력이 강점이며 현대 x86은 내부적으로 RISC 실행 방식을 일부 차용한다.

## Ⅴ. 심화 비교 및 적용 판단

| 비교 축 | RISC | CISC | 선택 기준 |
|:---|:---|:---|:---|
| 구조 | load-store, 고정 길이, 다수 레지스터 | 메모리 직접 연산, 가변 길이 | 임베디드·모바일 저전력은 RISC 우선 |
| 비용/성능 | 하드와이어드로 저전력·고클럭 효율 | 마이크로코드 유연성, 레거시 호환 | 전력 예산·레거시 소프트웨어 호환성으로 판단 |
| 운영/위험 | 컴파일러 최적화 의존도 높음 | 마이크로코드 취약점 패치 필요 | 툴체인 성숙도와 보안 패치 체계 확인 |

> 요약: 전력 효율과 신규 설계는 RISC, 레거시 호환과 명령어 압축이 중요하면 CISC 계열을 선택한다.

| 리스크 | 원인 | 대응 방안 | 확인 지표 |
|:---|:---|:---|:---|
| 컴파일러 의존 | RISC는 레지스터 할당·명령어 스케줄링을 컴파일러가 담당 | 최적화 컴파일러(GCC/LLVM) 튜닝 | 생성 코드 명령어 수, 실행 사이클 |
| 마이크로코드 취약점 | CISC 마이크로코드 결함으로 사이드채널 노출 | 마이크로코드 패치, 완화 명령어 적용 | CVE 대응 완료율 |
| 생태계 종속 | 특정 ISA 툴체인·라이브러리 부재 | 오픈 ISA(RISC-V) 검토, 크로스 컴파일 환경 구축 | 지원 컴파일러·OS 포팅 완료 여부 |

> 요약: RISC는 컴파일러 성숙도, CISC는 마이크로코드 취약점 대응이 핵심 리스크다.

| 점검 항목 | 목표 기준 | 측정 방법 |
|:---|:---|:---|
| IPC | 목표 워크로드 기준 IPC 비교 | 성능 카운터, 벤치마크(SPEC 계열) |
| 코드 크기 | 동일 기능 바이너리 크기 비교 | objdump, 바이너리 크기 측정 |
| 전력 효율 | 명령어당 소비 전력(예: pJ/instruction) | 전력 측정 장비, 시뮬레이터 |

> 요약: ISA 선택 효과는 IPC, 코드 크기, 명령어당 전력으로 판단한다.

## Ⅵ. 실무 적용 및 결론

**적용 방안 3개 (필수 — 단계별 또는 항목별):**
1. 저전력·임베디드·모바일 SoC는 RISC 계열(ARM, RISC-V)을 채택해 하드와이어드 CU와 파이프라인 효율로 명령어당 전력을 낮춤
2. 레거시 소프트웨어 호환과 코드 밀도가 중요한 서버·PC 영역은 CISC 계열(x86-64)을 유지하되 내부 uop 변환과 슈퍼스칼라로 IPC를 보완함
3. 신규 설계나 커스텀 가속기는 오픈 RISC-V ISA로 명령어 확장 라이선스 비용을 낮추고 툴체인 성숙도를 함께 점검함

**결론 (2줄):**
- 기술사 판단: ISA 선택은 RISC/CISC 명칭보다 전력 예산, 레거시 호환성, 툴체인·생태계 성숙도를 기준으로 결정함
- 향후 방향: x86·ARM 모두 내부적으로 uop 기반 실행을 채택하는 추세이므로, ISA 표면(front-end)과 실행 엔진(back-end)을 분리해 이해하는 관점이 중요해짐
