# 📖 【암기용】 개념 완전 이해

> 목적: 멀티소켓 서버를 처음 봐도 CPU 여러 개를 꽂는다고 무조건 성능이 배로 늘지 않는 이유를 이해하게 만든다. 시험 답안 양식이 아니라, 이해를 위한 친절한 설명이다.

## 한눈에
- **개요**: 물리 CPU 소켓을 2개 이상 장착하고 코히런트 인터커넥트로 연결해 하나의 대칭형 다중처리(SMP) 시스템으로 동작시키는 서버 아키텍처
- **왜 필요한가**: 단일 소켓은 코어 수·메모리 채널·PCIe 레인 수에 물리적 한계가 있다. 멀티소켓은 소켓을 늘려 코어·메모리 대역폭을 확장하지만, 소켓 간 통신 비용이라는 새로운 병목을 만든다.
- **핵심 직관**: 사무실 하나(단일 소켓)를 넓히는 데 한계가 있으면 옆 건물(2번째 소켓)을 복도(코히런트 인터커넥트)로 연결해 같은 회사처럼 쓰게 하는 구조이며, 옆 건물 자료를 가져오는 데는 시간이 더 걸린다.

## 깊이 이해
- **배경·문제의식**: 단일 소켓 코어 수 증가는 다이 면적·수율·전력 한계에 부딪히므로, 대규모 서버는 여러 소켓을 코히런트 인터커넥트로 묶어 논리적으로 하나의 SMP 시스템처럼 보이게 한다.
- **작동 원리**: 각 소켓은 로컬 메모리 컨트롤러를 가지며 이는 NUMA(Non-Uniform Memory Access) 노드를 형성하고, 소켓 간 연결은 Intel UPI(Ultra Path Interconnect), AMD Infinity Fabric 같은 캐시 코히런트 링크가 담당한다.
- **작동 원리**: SMP는 모든 CPU가 동일한 물리 주소 공간과 OS 인스턴스를 공유하며 대칭적으로 스케줄링되지만, 소켓 간 메모리 접근은 로컬 메모리 접근보다 지연이 크다(NUMA 효과).
- **작동 원리**: 캐시 일관성(MESI/MOESI 계열 프로토콜의 확장)은 디렉터리 기반 방식으로 소켓 간까지 확장되어, 한 소켓의 코어가 다른 소켓 메모리를 캐싱해도 데이터 일관성이 유지된다.
- **비유**: 단일 소켓 내부 코어들은 같은 층 사무실 동료처럼 빠르게 협업하고, 다른 소켓 코어는 다른 층 동료처럼 협업은 가능하지만 이동(통신) 시간이 더 걸린다.
- **구체 예시**: 4소켓(4S) 서버에서 소켓 0의 코어가 소켓 3에 붙은 메모리에 접근하면, 로컬 메모리 접근 대비 지연이 늘어나므로 NUMA-aware 스케줄링으로 프로세스를 가능한 로컬 소켓 메모리에 바인딩한다.
- **흔한 오해·주의점**: 소켓 수를 2배로 늘리면 성능도 2배가 될 것이라 기대하면 안 된다.
- **흔한 오해·주의점**: NUMA 원격 접근 지연과 코히런트 인터커넥트 대역폭 한계 때문에, 애플리케이션이 NUMA를 고려하지 않으면 소켓 추가가 오히려 캐시 라인 바운싱과 원격 접근 증가로 성능을 저하시킬 수 있다.

## 연결 개념
- NUMA(Non-Uniform Memory Access) — 멀티소켓 구조가 만드는 대표 메모리 접근 특성
- 캐시 일관성 프로토콜(MESI·MOESI) — 소켓 간 확장되는 일관성 유지 메커니즘
- Interconnect Topology(Fat-Tree·Torus) — 소켓 간 연결을 넘어 서버 간 확장 시 적용되는 상위 토폴로지 개념

> 핵심: 멀티소켓 서버 답안은 SMP 구조, NUMA 효과, 코히런트 인터커넥트, NUMA-aware 운영 방안을 함께 제시한다.

## 핵심 인사이트 (3줄 요약)

> 1. **본질**: 멀티소켓 서버는 여러 CPU 소켓을 코히런트 인터커넥트로 묶어 하나의 대칭형 다중처리(SMP) 시스템처럼 동작시키는 아키텍처다.
> 2. **가치**: 단일 소켓의 코어·메모리 대역폭 한계를 넘어 대규모 워크로드에 필요한 연산·메모리 자원을 확장한다.
> 3. **판단 포인트**: 소켓 간 메모리 접근은 로컬 접근보다 느린 NUMA 효과가 있으므로, 소켓 수 증가가 곧 선형 성능 향상을 의미하지 않는다.

## 출제 의도 및 답안 포인트

| 출제 의도 | 반드시 짚을 핵심 | 감점 회피 포인트 |
|:---|:---|:---|
| SMP·멀티소켓 구조 이해 확인 | 코히런트 인터커넥트(UPI·Infinity Fabric), 공유 주소 공간 | SMP를 단순 코어 수 합산으로 서술 |
| NUMA 효과 이해 확인 | 로컬·원격 메모리 접근 지연 차이 | NUMA를 언급 없이 성능이 선형 증가한다고 서술 |
| 운영 최적화 이해 확인 | NUMA-aware 스케줄링, 메모리 바인딩 | 소켓 추가만 방안으로 제시하고 소프트웨어 대응 누락 |

> 요약: 이 문제는 소켓 확장이 만드는 NUMA 효과와 이를 완화하는 소프트웨어·하드웨어 대응을 함께 설명하는지를 본다.

## Ⅰ. 개요 및 필요성

- 개요: 여러 CPU 소켓을 코히런트 인터커넥트로 연결해 하나의 대칭형 다중처리(SMP) 시스템으로 동작시키는 서버 아키텍처
- 배경: 단일 소켓의 코어 수·메모리 채널·PCIe 레인 확장은 다이 면적과 수율 한계에 부딪힘
- 필요성: 대규모 OLTP·가상화 통합·분석 워크로드는 단일 소켓을 넘는 코어·메모리 용량이 필요해 멀티소켓 구성이 요구됨

---

## Ⅱ. 구조 및 구성요소

```text
Socket 0(Core+Local Memory) -- UPI/Infinity Fabric -- Socket 1(Core+Local Memory)
       |                                                    |
   PCIe/IO Local                                       PCIe/IO Local
  (2S 이상 확장 시 Socket 2, 3도 동일 인터커넥트로 all-to-all 또는 mesh 연결)
```

| 구성요소 | 역할 | 특이사항 |
|:---|:---|:---|
| 소켓별 로컬 메모리 컨트롤러 | 해당 소켓에 물리적으로 가까운 메모리 관리 | NUMA 노드 단위 |
| 코히런트 인터커넥트(UPI·Infinity Fabric) | 소켓 간 캐시 일관성 트래픽·데이터 전달 | 대역폭·홉 수가 원격 접근 지연 좌우 |
| 디렉터리 기반 캐시 일관성 | 소켓 간 캐시 라인 상태 추적 | MESI/MOESI 확장 |
| NUMA 토폴로지 정보(ACPI SRAT/SLIT) | OS에 소켓·메모리 거리 정보 제공 | NUMA-aware 스케줄링 근거 |

> 요약: 멀티소켓 서버는 소켓별 로컬 메모리와 코히런트 인터커넥트, 디렉터리 기반 일관성 프로토콜로 하나의 SMP처럼 동작한다.

---

## Ⅲ. 동작원리 및 흐름도

```text
프로세스 스케줄링 요청 -> NUMA 토폴로지 확인(로컬/원격 소켓)
  -> 가능하면 로컬 소켓 코어·메모리에 배치
  -> 메모리 접근 시 로컬/원격 경로 판단
  -> 원격 접근 시 코히런트 인터커넥트 경유 -> 디렉터리 일관성 확인 -> 데이터 반환
```

| 단계 | 처리 내용 | 검증 기준 |
|:---:|:---|:---|
| 1 | OS가 NUMA 토폴로지(SRAT/SLIT) 확인 | 소켓·노드 거리 정보 정확성 |
| 2 | 프로세스·메모리를 가능한 로컬 소켓에 배치 | NUMA 로컬 접근 비율 |
| 3 | 원격 접근 발생 시 인터커넥트 경유 | 원격 접근 지연(latency) |
| 4 | 디렉터리 기반 캐시 일관성 유지 | 캐시 라인 바운싱 빈도 |

> 요약: 멀티소켓 시스템은 NUMA 토폴로지를 기준으로 로컬 배치를 우선하고, 원격 접근은 인터커넥트와 디렉터리 프로토콜로 처리한다.

---

## Ⅳ. 특징

| 구분 | 단일 소켓(SMP 내 코어 간) | 멀티소켓(소켓 간) |
|:---|:---|:---|
| 메모리 접근 | 균일한 로컬 접근 | NUMA 효과로 로컬·원격 지연 차등 |
| 확장성 | 다이 면적·전력 한계 | 소켓 추가로 코어·메모리 확장 가능 |
| 통신 경로 | 온다이 인터커넥트(메시·링) | UPI·Infinity Fabric 등 소켓 간 링크 |
| 소프트웨어 고려사항 | 상대적으로 단순 | NUMA-aware 스케줄링·메모리 바인딩 필요 |

> 요약: 멀티소켓은 확장성을 얻는 대신 NUMA 효과라는 소프트웨어 고려사항을 추가로 요구한다.

## Ⅴ. 심화 비교 및 적용 판단

| 비교 축 | 단일 소켓 | 멀티소켓(2S·4S·8S) | 선택 기준 |
|:---|:---|:---|:---|
| 구조 | 균일 메모리 접근 | NUMA 노드 다중화 | 코어·메모리 용량 요구가 단일 소켓 한계 초과 시 멀티소켓 |
| 비용/성능 | 소켓·인터커넥트 비용 없음 | 소켓·인터커넥트 비용 증가, 확장 코어 확보 | 워크로드 병렬성과 예산으로 판단 |
| 운영/위험 | NUMA 튜닝 불필요 | NUMA 미최적화 시 성능 저하 위험 | numactl, NUMA-aware 스케줄러 적용 여부 |

> 요약: 대규모 병렬 워크로드는 멀티소켓으로 확장하되, NUMA 인식 소프트웨어 설계가 병행되어야 한다.

| 리스크 | 원인 | 대응 방안 | 확인 지표 |
|:---|:---|:---|:---|
| NUMA 원격 접근 과다 | 프로세스·메모리가 소켓 간 분산 배치 | numactl 바인딩, NUMA-aware 스케줄러 | 로컬/원격 메모리 접근 비율 |
| 캐시 라인 바운싱 | 여러 소켓 코어가 같은 캐시 라인 갱신 경합 | false sharing 제거, 데이터 구조 정렬 | 캐시 코히런시 트래픽량 |
| 인터커넥트 포화 | 소켓 간 대역폭 요구가 링크 한계 초과 | 토폴로지 재설계, 워크로드 소켓 분리 | 인터커넥트 링크 사용률 |

> 요약: 멀티소켓 운영 리스크는 NUMA 접근 비율, 캐시 바운싱, 인터커넥트 포화율로 통제한다.

| 점검 항목 | 목표 기준 | 측정 방법 |
|:---|:---|:---|
| NUMA 로컬 접근률 | 목표치(예: 90% 이상) 유지 | numastat, perf c2c |
| 인터커넥트 사용률 | 링크 대역폭 대비 임계치 이하 | 벤더 성능 카운터 |
| 애플리케이션 확장성 | 소켓 증가 대비 처리량 증가율 | 벤치마크(스케일 테스트) |

> 요약: 도입 성공 여부는 NUMA 로컬 접근률, 인터커넥트 사용률, 소켓 증가 대비 실제 처리량 증가율로 판단한다.

## Ⅵ. 실무 적용 및 결론

**적용 방안 3개:**
1. 대규모 OLTP·가상화 통합 워크로드는 멀티소켓 서버(2S·4S)를 도입하되 NUMA-aware 스케줄링을 함께 설정함
2. 고성능 애플리케이션은 numactl·CPU 어피니티로 프로세스와 메모리를 동일 소켓에 바인딩함
3. 소켓 간 인터커넥트 사용률이 높은 워크로드는 데이터 파티셔닝으로 소켓 간 트래픽을 줄임

**결론 (2줄):**
- 기술사 판단: 단일 소켓 한계를 넘는 코어·메모리 요구가 있으면 멀티소켓을 선택하되 NUMA 최적화를 필수 병행함
- 향후 방향: CXL 메모리 풀링과 결합해 소켓 경계를 넘는 메모리 자원 공유가 확대될 전망
