## 미리 알고가기

- **캐시 일관성 ($Cache\ Coherency$)**: 여러 개의 프로세서나 장치가 동일한 메모리 데이터를 참조할 때, 각자의 캐시에 저장된 데이터 값이 최신 상태로 일치하도록 유지하는 성질
- **$PCIe$ ($Peripheral\ Component\ Interconnect\ Express$)**: $CPU$와 주변 장치를 연결하는 범용 직렬 버스 규격. $CXL$은 이의 물리 계층을 활용함
- **가속기 ($Accelerator$)**: 특정 연산($AI$, 그래픽 등)을 전문적으로 수행하기 위해 메인 $CPU$를 보조하는 장치 ($GPU$, $NPU$ 등)
- **메모리 풀링 ($Memory\ Pooling$)**: 여러 대의 서버가 필요에 따라 메모리 자원을 공유하고 동적으로 할당받아 사용하는 기술

## Ⅰ. 개요

- **정의/개념**: 컴퓨트 익스프레스 링크(Compute Express Link, $CXL$)는 $PCIe$ 물리 계층 인터페이스를 기반으로 $CPU$와 가속기, 메모리 확장 장치 간의 고속 통신과 캐시 일관성을 보장하는 차세대 오픈 인터커넥트 표준임
- **배경/필요성**: 데이터센터의 $AI$ 및 빅데이터 워크로드가 급증하면서 개별 서버의 메모리 용량 한계와 장치 간 데이터 복사 오버헤드가 심각한 병목으로 작용함. 이를 해결하기 위해 서로 다른 장치들이 하나의 거대한 메모리 공간을 공유하고, 일관성 있는 데이터를 빠르게 주고받을 수 있는 통합 연결망이 절실히 요구됨

## Ⅱ. 특징 및 비교

### 가. $PCIe$와 $CXL$의 핵심 기술적 대비

| 구분 | $PCIe$ (기존 표준) | $CXL$ (차세대 표준) |
|:---|:---|:---|
| 물리 계층 | $PCIe\ Gen5/Gen6$ 활용 | $PCIe$ 물리 계층 그대로 활용 (호환) |
| 프로토콜 | $I/O$ 프로토콜 중심 | $io,\ cache,\ mem$ 3대 프로토콜 제공 |
| 캐시 일관성 | 하드웨어 수준 지원 미흡 | 장치 간 완벽한 캐시 일관성 보장 |
| 메모리 접근 | 명시적 $DMA$ 복사 필요 | 호스트와 장치가 단일 주소 공간 공유 |
| 지연 시간 | 상대적으로 높음 | 극도로 낮음 ($Low\ Latency$) |
| 주요 용도 | 일반 $I/O$, $GPU$, $SSD$ 연결 | 메모리 확장, 가속기 연결, 자원 풀링 |

> 요약: $CXL$은 $PCIe$의 범용성에 '메모리 일관성'과 '저지연'을 더한 상위 개념임

### 나. $CXL$의 3대 하위 프로토콜
- **$CXL.io$**: 장치 발견, 설정, 인터럽트 등 기본 $I/O$ 기능 수행 (기본 탑재)
- **$CXL.cache$**: 프로세서와 가속기 간의 캐시 일관성 있는 데이터 교환 지원
- **$CXL.mem$**: 호스트 프로세서가 장치에 탑재된 메모리를 로컬 메모리처럼 사용하게 함

## Ⅲ. 구성요소/구조

### 가. $CXL$ 장치 유형별 아키텍처 분류

| 장치 유형 | 구성 요소 | 주요 역할 | 대표 사례 |
|:---|:---|:---|:---|
| **Type 1** | $io,\ cache$ | 호스트 메모리를 캐시처럼 쓰는 장치 | 스마트 $NIC$, 가속기 |
| **Type 2** | $io,\ cache,\ mem$ | 호스트와 장치 메모리를 상호 공유 | $GPU$, $FPGA$ 가속기 |
| **Type 3** | $io,\ mem$ | 메모리 용량 확장용 장치 | $CXL$ 메모리 확장기 |

### 나. 시스템 내부 연결 구조 및 데이터 흐름

```text
[ Host CPU ] <--- (CXL Link) ---> [ CXL Fabric / Switch ]
       |                                |
       +-- (CXL.io) -> 관리/설정         +-- [ Device A (Type 3) ]
       +-- (CXL.mem) -> 메모리 확장      +-- [ Device B (Type 2) ]
       +-- (CXL.cache) -> 데이터 동기화   +-- [ Device C (Type 1) ]
```

> 요약: 장치의 성격에 따라 필요한 프로토콜 조합을 선택하여 연결하는 유연한 구조임

## Ⅳ. 문제점 및 개선방안

1. **상대적인 접근 지연 ($Latency$ Gap)**: $CXL$을 통해 연결된 확장 메모리는 $CPU$ 직결 $DRAM$($DDR$)보다 지연 시간이 약 $2 \sim 3$배 높음
   - **개선방안**: 운영체제 수준에서 **계층형 메모리($Tiered\ Memory$)** 정책을 적용하여, 자주 쓰이는 $Hot$ 데이터는 $DDR$에, $Cold$ 데이터는 $CXL$ 메모리에 배치함

2. **소프트웨어 생태계 미성숙**: 기존 운영체제나 애플리케이션이 $CXL$의 동적 메모리 할당 및 일관성 기능을 완벽히 지원하지 못함
   - **개선방안**: 리눅스 커널 등 주요 $OS$에 $CXL$ 드라이버를 통합하고, **$CXL\ Fabric\ Manager$**를 통해 자원 할당을 자동화함

3. **신호 무결성($Signal\ Integrity$) 및 물리적 거리**: 고속 통신($32GT/s$ 이상) 시 케이블 길이에 따른 신호 감쇄 발생
   - **개선방안**: 고성능 리타이머($Retimer$) 칩을 배치하여 신호 품질을 복원하고, $CXL$ 패브릭 스위치를 통해 물리적 거리 한계를 극복함

## Ⅴ. 실무 적용 사례

| 적용 영역 | 적용 방식 | 확인 지표 |
|:---|:---|:---|
| 메모리 확장 서버 | $DIMM$ 슬롯 부족 시 $PCIe$ 슬롯에 $CXL$ 메모리를 장착하여 전체 용량 증설 | $Total\ Capacity$, $TCO$ |
| 거대 모델 $AI$ 학습 | 여러 $GPU$가 $CXL.cache$를 통해 모델 파라미터를 복사 없이 공유하여 학습 속도 향상 | $Training\ Speed$, $Bus\ Traffic$ |
| 클라우드 자원 풀링 | 여러 서버가 하나의 거대한 $CXL$ 메모리 풀을 공유하여 자원 낭비 최소화 | $Resource\ Utilization$, $Cost\ per\ GB$ |

> 요약: 메모리 용량이 병목인 인메모리 $DB$, $AI$, 빅데이터 분석 환경이 최대 수혜처임

## Ⅵ. 결론

$CXL$은 개별 서버 중심의 컴퓨팅을 넘어 '컴포저블 인프라($Composable\ Infrastructure$)'로 가는 핵심 관문임. 단순히 전송 속도를 높이는 것을 넘어, 메모리라는 가장 중요한 자원을 시스템 전체가 효율적으로 나누어 쓸 수 있게 하는 기술적 토대를 제공함.

기술사는 $CXL$이 $PCIe\ 5.0/6.0$ 생태계와 어떻게 조화를 이루는지 이해해야 하며, 특히 $CXL\ 2.0/3.0$으로 발전하면서 추가되는 패브릭 스위칭 및 다중 호스트 풀링 기술의 파급력을 분석할 수 있어야 함. 또한, $HBM$이 연산 장치 '내부'의 대역폭을 책임진다면, $CXL$은 연산 장치 '외부'의 거대한 용량과 공유를 책임지는 상보적 관계임을 명확히 파악해야 함.
