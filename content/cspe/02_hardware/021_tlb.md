## 미리 알고가기

- TLB는 가상 페이지 번호를 물리 프레임 번호로 바꾸는 최근 변환 결과를 담는 캐시임
- TLB 미스가 나면 페이지 테이블을 따라가는 page walk가 발생함
- 큰 페이지를 쓰면 TLB 엔트리 하나가 덮는 메모리 범위가 넓어짐

## Ⅰ. 개요

- **정의/개념**: TLB는 MMU 내부에서 가상 주소의 페이지 번호와 접근 권한을 연관 검색으로 빠르게 찾아 주소 변환 지연을 줄이는 전용 캐시 구조임
- **배경/필요성**: 다단계 페이지 테이블을 매 접근마다 따라가면 메모리 접근 전에 추가 메모리 참조가 반복되므로, CPU 성능을 유지하려면 주소 변환 자체를 캐시해야 함

## Ⅱ. 특징

- 주소 변환 경로를 CPU 가까이에 두어 평균 메모리 접근 시간을 크게 줄임
- 연관 검색과 ASID, 권한 비트를 함께 사용해 속도와 보호 기능을 동시에 처리함
- 적중률은 지역성과 페이지 크기에 크게 좌우되며 작업 집합이 커지면 성능이 급격히 흔들릴 수 있음
- 가상화 환경에서는 guest와 host 변환이 겹쳐 TLB 미스 비용이 더 커짐

## Ⅲ. 종류 및 비교

| 판단 기준 | 페이지 테이블 | TLB |
|:---|:---|:---|
| 위치 | 주기억장치에 계층적으로 저장됨 | MMU 내부의 소용량 고속 캐시에 저장됨 |
| 조회 방식 | 인덱스 기반으로 단계별 탐색함 | 연관 검색으로 즉시 후보를 찾음 |
| 장점 | 전체 주소 공간을 완전하게 표현함 | 적중 시 page walk를 생략해 지연을 크게 줄임 |
| 한계 | 메모리 접근 전에 추가 참조가 필요함 | 용량이 작아 작업 집합이 크면 미스가 늘어남 |

## Ⅳ. 구성요소 및 구조

| 구성요소 | 설명 |
|:---|:---|
| VPN Tag | 가상 페이지 번호를 보관하며 입력 주소와 병렬 비교되어 적중 여부를 결정함 |
| PFN Entry | 대응되는 물리 프레임 번호를 제공해 최종 물리 주소 생성을 완료함 |
| ASID and Permission Bits | 프로세스 식별자와 읽기·쓰기·실행 권한을 함께 저장해 flush를 줄이고 보호 검사도 즉시 수행함 |
| Page Walker Interface | TLB 미스 시 페이지 테이블 탐색을 요청하고 새 변환 결과를 다시 채워 넣는 연결점임 |

```text
+------------------+     +----------------------+     +------------------+
| Virtual Address  | --> | TLB Lookup           | --> | Physical Address |
+------------------+     +----------------------+     +------------------+
         |                         |
         | miss                    | hit
         v                         v
+------------------+     +----------------------+
| Page Table Walk  | --> | TLB Refill           |
+------------------+     +----------------------+
```

## Ⅴ. 원리 및 절차 흐름도

```text
+-------------+     +-------------+     +-------------+     +-------------+
| 주소 분해        | --> | TLB 검색        | --> | page walk 여부 판단 | --> | 변환 결과 반영   |
+-------------+     +-------------+     +-------------+     +-------------+
```

1. **주소 분해**: 가상 주소를 VPN과 offset으로 나눔
2. **TLB 검색**: VPN과 ASID를 기준으로 엔트리를 병렬 비교함
3. **page walk 여부 판단**: 적중이면 PFN을 바로 쓰고 미스면 페이지 테이블을 탐색함
4. **변환 결과 반영**: 최종 물리 주소를 만들고 필요하면 새 엔트리를 TLB에 채움

## Ⅵ. 문제점 및 해결 방안

1. 문제: 문맥 전환이 잦으면 기존 변환 정보가 자주 무효화되어 warm-up 구간의 지연이 커짐
   - 해결방안: ASID 또는 PCID를 적용해 주소 공간을 구분 보존하고 context switch 직후 TLB hit rate와 tail latency로 검증함
2. 문제: 대용량 메모리 작업은 TLB가 덮는 범위를 쉽게 넘어 미스와 page walk 비용을 급증시킴
   - 해결방안: huge page와 multi-level TLB를 적용해 TLB coverage와 page walk rate로 검증함
3. 문제: 가상화 환경에서는 2단계 주소 변환이 겹쳐 단일 TLB 미스의 벌점이 과도하게 커질 수 있음
   - 해결방안: nested translation cache와 EPT 최적화를 적용하고 nested miss penalty와 VM memory access latency로 검증함

## Ⅶ. 적용 사례

- 인메모리 데이터베이스 서버는 huge page를 적용해 TLB coverage를 키우고 확인 지표는 page walk rate와 query latency임
- 클라우드 하이퍼바이저는 PCID와 nested translation cache를 활용해 warm-up 손실을 줄이고 확인 지표는 VM memory access latency와 TLB hit rate임
- 고빈도 트레이딩 시스템은 코어 고정과 메모리 지역성 최적화를 병행해 tail latency를 줄이고 확인 지표는 p99 latency와 context switch rate임

## Ⅷ. 결론

TLB는 단순 캐시가 아니라 주소 변환 비용을 제어해 CPU 파이프라인의 연속성을 지키는 핵심 장치이므로, 설계 판단은 용량보다도 miss penalty를 얼마나 낮출 수 있는지에 맞춰야 함.
