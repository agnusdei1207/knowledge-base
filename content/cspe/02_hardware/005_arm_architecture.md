## 미리 알고가기

- ARM은 RISC 계열 ISA와 SoC용 프로세서 IP 생태계를 제공함
- AArch32와 AArch64, EL0~EL3 권한 레벨을 구분함
- 모바일·임베디드에서는 와트당 처리량과 SoC IP 생태계가 선택 기준이 됨

## 작성 근거(검토용)

- ARM을 저전력이라는 평가어로만 설명하지 않고 실행 상태·예외 레벨·확장 명령·SoC 통합으로 분해함
- ARM과 x86-64를 ISA 형식·실행 상태·호환 조건·SoC 통합 기준으로 비교함
- ARM 도입 조건을 ABI·벡터 확장·예외 레벨 검증과 연결함

## Ⅰ. 개요

- **정의/개념**: ARM 아키텍처는 RISC 계열 ISA와 실행 상태, 예외 레벨, 확장 명령을 통해 모바일·임베디드·서버 환경을 지원하는 프로세서 구조임
- **배경/필요성**: 배터리 기반 기기와 SoC의 성능·전력·IP 통합 조건을 맞추기 위해 용도별 프로세서 구성이 필요함

## Ⅱ. 특징

- 규칙적 명령어와 load/store 구조로 해독 회로와 파이프라인 경로를 단순화함
- AArch32의 Thumb 명령과 AArch64 실행 상태를 지원해 코드 밀도와 주소·레지스터 폭 요구를 구분함
- 권한 모드와 예외 레벨 구조가 OS·하이퍼바이저 설계를 지원함
- 서버용 코어는 비순서 실행·분기 예측·다단 캐시를 사용하므로 ISA 분류만으로 처리량을 판단할 수 없음

## Ⅲ. 종류 및 비교

| 판단 기준 | ARM | x86-64 |
|:---|:---|:---|
| ISA 형식 | Load/Store와 고정 길이 명령 중심 | 가변 길이 명령과 메모리 피연산자 지원 |
| 실행 상태 | AArch32·AArch64 | 64비트 모드·호환 모드 |
| 바이너리 호환 조건 | ARM ISA·ABI에 맞춘 빌드 필요 | 기존 x86-64 소프트웨어 자산 활용 |
| SoC 통합 | 라이선스 IP와 주변 장치 조합 | 범용 PC·서버 플랫폼 중심 |
| 주요 선택 조건 | 전력 예산·SoC IP 조합 | 기존 x86 바이너리·운영체제 호환 |

> 요약: ARM은 전력 예산과 SoC IP 조합을, x86-64는 기존 바이너리·운영체제 호환을 기준으로 선택함.

## Ⅳ. 구성요소 및 구조

| 구성요소 | 설명 |
|:---|:---|
| 실행 상태 | AArch32와 AArch64가 명령어 폭과 레지스터 모델을 결정함 |
| 예외 레벨 | EL0~EL3 권한 구조가 사용자·커널·하이퍼바이저·보안 모드를 나눔 |
| 레지스터 집합 | 범용·특수 레지스터가 호출 규약과 문맥 교환 비용을 결정함 |
| 확장 명령 | NEON과 SVE가 멀티미디어·벡터 처리 명령을 제공함 |

```text
+----------------+     +----------------+     +--------------+
| 실행 상태        | --> | 레지스터 집합    | --> | 확장 명령      |
+----------------+     +----------------+     +--------------+
      |
      v
+----------------+
| 예외 레벨        |
+----------------+
```

> 요약: ARM 구조는 실행 상태, 권한 레벨, 레지스터, 확장 명령이 함께 동작해 OS와 SoC 요구를 맞춤.

## Ⅵ. 실무 사례

1. ARM 응용 프로그램 포팅은 대상 ABI를 고정하고, 바이너리 호환 시험 통과율과 포팅 소요시간으로 검증함
2. ARM 가상화 서버는 커널과 하이퍼바이저를 분리하기 위해 EL1·EL2 권한을 구성하고, 권한 위반 건수와 가상 머신 전환 지연으로 검증함

## Ⅶ. 결론

- ARM은 전력 예산, AArch32·AArch64 호환 조건, 예외 레벨, SoC IP 지원 범위를 기준으로 선택해야 함
