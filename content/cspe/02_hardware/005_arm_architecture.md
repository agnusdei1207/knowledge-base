# 📖 【암기용】 개념 완전 이해

> 목적: ARM을 처음 봐도 왜 스마트폰부터 서버까지 지배적인 저전력 아키텍처가 되었는지, 특권 레벨과 보안 월드가 어떻게 나뉘는지 이해하게 만든다. 시험 답안 양식이 아니라, 이해를 위한 친절한 설명이다.

## 한눈에
- **개요**: Arm Ltd가 설계도(IP)만 만들어 라이선스로 공급하는 RISC 계열 프로세서 아키텍처로, 저전력·고효율 설계가 특징이다.
- **왜 필요한가**: x86은 전력 소모가 커 배터리 기반 모바일 기기에 부적합했는데, ARM은 명령어를 단순화하고 특권 레벨·보안 월드를 계층화해 저전력과 보안을 동시에 확보한다.
- **핵심 직관**: ARM은 "설계도만 팔고 제조는 파트너가 하는" 반도체 설계 라이선스 사업 모델이며, 내부적으로는 권한을 4단계 계단(EL0~EL3)으로 나눈 건물 구조다.

## 깊이 이해
- **배경·문제의식**: ARM은 1980년대 영국 Acorn Computers의 "Acorn RISC Machine" 프로젝트에서 출발해 이후 "Advanced RISC Machine"으로 이름이 바뀌었고, Arm Ltd는 코어를 직접 제조하지 않고 설계 라이선스를 애플·퀄컴·삼성·MediaTek 등에 공급하는 팹리스(fabless) IP 라이선스 모델을 취한다.
- ARMv7까지는 32비트 AArch32 실행 상태만 지원했고, ARMv8-A(2011년 발표)부터 64비트 AArch64 실행 상태가 추가되어 32비트와 64비트를 모두 지원하게 되었으며, ARMv9(2021년 발표)는 v8 기반에 SVE2(벡터 확장)와 기밀 컴퓨팅 아키텍처를 더했다.
- **작동 원리 — 레지스터**: AArch64는 31개의 64비트 범용 레지스터(X0~X30)를 제공하고, X30은 관례적으로 링크 레지스터(LR, 함수 복귀 주소 저장)로 쓰이며, 별도의 스택 포인터(SP)와 프로그램 카운터(PC)를 둔다.
- 제로 레지스터(XZR, 32비트 접근 시 WZR)는 항상 값 0을 반환하거나 쓰기를 버려 상수 0 표현과 결과 폐기(discard)에 활용된다.
- **작동 원리 — 특권 레벨(Exception Level)**: ARMv8 이상은 EL0(응용 프로그램, 최소 권한)-EL1(OS 커널)-EL2(하이퍼바이저)-EL3(시큐어 모니터, 최고 권한) 4단계 예외 레벨(Exception Level)로 권한을 계층화한다.
- 상위 레벨일수록 권한이 높고, 예외·인터럽트·시스템 콜 발생 시 낮은 레벨에서 높은 레벨로 전환되며 처리 후 복귀한다.
- **작동 원리 — TrustZone**: ARM TrustZone은 하드웨어 수준에서 시스템을 Secure World와 Normal World 두 영역으로 분리하고, EL3의 시큐어 모니터가 두 월드 간 전환을 관리해 신뢰 실행 환경(TEE)을 구성한다.
- **작동 원리 — 이기종 코어 구성**: big.LITTLE(이후 DynamIQ로 발전)은 고성능 big 코어와 고효율 LITTLE 코어를 한 SoC에 함께 배치해 작업 부하에 따라 코어를 전환하거나 동시 사용하는 이기종 멀티프로세싱(HMP) 구조다.
- **비유**: ARM 라이선스 모델은 "설계도만 그리고 건축은 시공사가 하는" 건축 설계사무소와 같고, EL0~EL3 계층은 건물의 방문객(EL0)-관리인(EL1)-보안팀장(EL2)-최고 보안 책임자(EL3)로 권한이 올라가는 구조와 같다.
- **구체 예시**: 스마트폰 결제 앱은 Normal World(EL0/EL1)에서 UI를 실행하고, 지문 인증이나 결제 키 처리는 Secure World(TrustZone)로 전환해 처리한 뒤 결과만 Normal World에 반환하는 방식으로 민감 데이터를 격리한다.
- **흔한 오해·주의점**: "ARM은 회사가 프로세서를 직접 만든다"는 정확하지 않다. Arm Ltd는 코어 설계(IP)를 라이선스하고, 실제 칩 제조는 TSMC 등 파운드리와 각 반도체 업체가 수행한다.
- "ARM은 모바일 전용"도 성립하지 않는다. AWS Graviton, Ampere Altra 같은 Neoverse 기반 서버 코어가 클라우드 데이터센터에도 채택되고 있다.

## 연결 개념
- 명령어 집합 RISC vs CISC — ARM은 RISC 설계 철학의 대표 상용 사례
- RISC-V — 라이선스 없는 오픈 ISA로 ARM과 경쟁·비교 대상
- ARM TrustZone 보안 익스텐션 — EL3 시큐어 모니터 기반 TEE 구현
- 하이퍼바이저(Hypervisor Types) — EL2 계층이 담당하는 가상화 기능

# 📝 【답안용】 시험 답안 템플릿

> 목적: 시험장에서 25분에 그대로 쓰는 답안 양식. 작성방식(추상표현 금지·수치·도식·문제유형 전환)을 엄격히 지킨다.
> 핵심: ARM을 "저전력 RISC"라는 한 줄로 답하지 않고, 라이선스 모델·예외 레벨·TrustZone·이기종 코어 구성을 근거로 제시한다. (126회 기출 대응)

## 핵심 인사이트 (3줄 요약)

> 1. **본질**: ARM은 Arm Ltd가 설계 IP만 라이선스로 공급하는 RISC 계열 아키텍처로, AArch64에서 31개 64비트 범용 레지스터와 4단계 예외 레벨(EL0~EL3)을 사용한다.
> 2. **가치**: 예외 레벨 계층과 TrustZone Secure/Normal World 분리로 저전력 환경에서도 신뢰 실행 환경(TEE)을 구성할 수 있다.
> 3. **판단 포인트**: 라이선스 비용을 감수하고 성숙한 생태계·검증된 저전력 설계를 원하면 ARM, 라이선스 자유와 커스텀 확장이 우선이면 RISC-V를 선택 기준으로 삼는다.

## 출제 의도 및 답안 포인트

| 출제 의도 | 반드시 짚을 핵심 | 감점 회피 포인트 |
|:---|:---|:---|
| ARM 아키텍처·동작 모드 이해 확인 | AArch32/AArch64 구분, EL0~EL3 예외 레벨 계층 | "저전력 RISC"라는 표현만 쓰고 레벨 구조 누락 |
| 보안 구조 이해 확인 | TrustZone Secure/Normal World와 EL3 역할 | 보안 언급 시 TrustZone 근거 없이 "보안이 강화된다"만 서술 |
| 사업 모델·적용 범위 판단 확인 | 팹리스 IP 라이선스 모델, 모바일 외 서버(Neoverse) 적용 확대 | "ARM은 모바일 전용"이라는 절대화된 서술 |

> 요약: 이 문제는 ARM을 저전력이라는 한 단어로 답하지 않고 예외 레벨·TrustZone 구조와 적용 범위 확대를 근거로 제시할 것을 요구한다.

## Ⅰ. 개요 및 필요성

- 개요: Arm Ltd가 설계 IP를 라이선스로 공급하는 RISC 계열 프로세서 아키텍처
- 배경: Acorn RISC Machine에서 출발해 ARMv7(AArch32)에서 ARMv8-A(AArch64 추가), ARMv9(SVE2·기밀 컴퓨팅)로 확장
- 필요성: 배터리 기반 기기의 저전력 요구와 결제·인증 같은 민감 데이터 격리 요구에 대응하려면 계층화된 특권 레벨과 하드웨어 보안 월드가 필요

---

## Ⅱ. 구조 및 구성요소

```text
ARM 아키텍처 (AArch64)
  레지스터: X0~X30(범용) + XZR(제로) + SP + PC
  특권 레벨: EL0(응용) -> EL1(OS 커널) -> EL2(하이퍼바이저) -> EL3(시큐어 모니터)
  보안 월드: Normal World(EL0~EL2) <-> EL3 Monitor <-> Secure World(TrustZone)
```

| 구성요소 | 역할 | 특이사항 |
|:---|:---|:---|
| 범용 레지스터 | 연산·주소 임시 저장 | X0~X30(64비트), X30은 관례상 링크 레지스터 |
| 예외 레벨(EL) | 권한 계층 구분 | EL0 최소권한, EL3 최고권한 |
| TrustZone | Secure/Normal World 분리 | EL3 모니터가 월드 전환 관리 |
| big.LITTLE/DynamIQ | 이기종 코어 배치 | 성능 코어와 효율 코어 혼합 스케줄링 |

> 요약: ARM은 레지스터·예외 레벨·TrustZone·이기종 코어 구성을 조합해 저전력과 보안을 함께 확보한다.

---

## Ⅲ. 동작원리 및 흐름도

```text
응용 실행(EL0) -> 시스템 콜/예외 발생 -> EL1(OS 커널) 처리
  -> 가상화 필요 시 EL2(하이퍼바이저) 개입
  -> 보안 서비스 필요 시 EL3(시큐어 모니터) -> Secure World 진입
  -> 처리 결과 반환 -> Normal World(EL0) 복귀
```

| 단계 | 처리 내용 | 검증 기준 |
|:---:|:---|:---|
| 1 | EL0에서 응용 프로그램 실행 | 사용자 권한 범위 준수 |
| 2 | 예외/시스템 콜 발생 시 EL1으로 전환 | 예외 벡터 정합성 |
| 3 | 가상화 요청 시 EL2에서 게스트 OS 관리 | VM 격리 정합성 |
| 4 | 보안 연산 요청 시 EL3 경유 Secure World 진입 | Secure/Normal 월드 전환 무결성 |

> 요약: 권한은 EL0에서 EL3 방향으로 상승하며, 보안이 필요한 연산만 EL3를 거쳐 Secure World로 격리 처리된다.

## Ⅳ. 특징

| 구분 | ARM | x86-64(비교 참고) | 수치·표준 포인트 |
|:---|:---|:---|:---|
| 사업 모델 | 팹리스 IP 라이선스(아키텍처/코어 라이선스) | 자체 설계·제조 병행(Intel), 라이선스 제한적(AMD) | Arm Ltd, TSMC 등 파운드리 분업 |
| 특권 구조 | EL0~EL3 4단계 예외 레벨 | Ring 0~3(현재는 주로 Ring 0/3 사용) | TrustZone Secure/Normal World |
| 레지스터 | AArch64 X0~X30(64비트) | RAX~R15(64비트, 16개) | 레지스터 수·명명 규칙 차이 |
| 적용 범위 | 모바일, 임베디드, Neoverse 서버 코어 | 서버·PC·워크스테이션 중심 | AWS Graviton 등 서버 채택 확대 |

> 요약: ARM은 라이선스 모델과 예외 레벨 구조로 저전력·보안에 강점이 있고, 서버 영역까지 적용 범위를 넓히고 있다.

## Ⅴ. 심화 비교 및 적용 판단

| 비교 축 | ARM | RISC-V(비교 참고) | 선택 기준 |
|:---|:---|:---|:---|
| 구조 | 벤더 정의 확장, EL 기반 특권 계층 | 모듈형 확장, 커스텀 opcode 허용 | 검증된 특권·보안 구조 필요 시 ARM |
| 비용/성능 | 라이선스 비용 발생, 검증된 저전력 특성 | 로열티 없음, 자체 검증 부담 | 라이선스 총비용과 생태계 성숙도 비교 |
| 운영/위험 | 성숙한 툴체인·OS 지원 | 툴체인·OS 포팅 자체 확보 필요 | 소프트웨어 이식성·개발 인력 확보 여부 |

> 요약: 검증된 생태계와 보안 구조가 우선이면 ARM, 라이선스 자유와 커스텀 확장이 우선이면 RISC-V를 선택한다.

| 리스크 | 원인 | 대응 방안 | 확인 지표 |
|:---|:---|:---|:---|
| TrustZone 우회 | Secure World 앱 취약점으로 권한 상승 | Secure OS 패치, 최소 권한 원칙 적용 | Secure World CVE 대응 완료율 |
| 이기종 코어 스케줄링 오류 | big.LITTLE 작업 배치 미스로 성능·전력 저하 | OS 스케줄러 튜닝, 코어 친화도 설정 | 코어별 이용률 편차 |
| 라이선스 종속 | 특정 코어 IP에 설계가 종속 | 표준 코어(Cortex/Neoverse) 우선 채택, 대안 ISA 검토 | 라이선스 갱신 리스크 평가 |

> 요약: ARM 도입 리스크는 TrustZone 취약점, 이기종 코어 스케줄링, 라이선스 종속이 핵심이다.

| 점검 항목 | 목표 기준 | 측정 방법 |
|:---|:---|:---|
| 전력 효율 | 코어당 전력 대비 성능(performance per watt) | 전력 측정, 벤치마크 |
| 보안 격리 | Secure/Normal World 간 데이터 유출 0건 | 침투 테스트, TEE 검증 |
| 이기종 코어 활용률 | big/LITTLE 코어별 부하 배치 적정성 | 스케줄러 로그, 성능 카운터 |

> 요약: 도입 효과는 전력 효율, 보안 격리 검증 결과, 이기종 코어 활용률로 판단한다.

## Ⅵ. 실무 적용 및 결론

**적용 방안 3개 (필수 — 단계별 또는 항목별):**
1. 모바일·임베디드 SoC는 big.LITTLE/DynamIQ 구성으로 성능 코어와 효율 코어를 작업 부하별로 배치해 전력을 관리함
2. 결제·인증 등 민감 연산은 TrustZone Secure World로 격리하고 EL3 시큐어 모니터 전환 로그를 감사 대상으로 관리함
3. 서버 워크로드는 Neoverse 기반 ARM 서버 코어 도입 시 x86 대비 코어당 전력 효율과 소프트웨어 호환성을 함께 검증함

**결론 (2줄):**
- 기술사 판단: 검증된 저전력 설계와 보안 구조가 필요하면 ARM, 라이선스 자유와 커스텀 명령어가 필요하면 RISC-V를 선택함
- 향후 방향: ARM 서버 코어(Neoverse)와 온디바이스 AI 칩 적용이 늘며 EL 계층·TrustZone 기반 신뢰 실행 환경 설계 요구가 함께 커지고 있음
