# 📖 【암기용】 개념 완전 이해

> 목적: 세그멘테이션이 페이징과 무엇이 다르고, Base·Limit로 어떻게 주소를 변환·보호하는지, 왜 결국 페이징과 섞어 쓰게 됐는지를 실제 계산 예시로 이해하게 만든다.

## 한눈에
- **개요**: 세그멘테이션은 **가상 메모리**를 페이징처럼 고정 크기로 자르지 않고, 프로그램의 **논리적 의미 단위**(코드·데이터·스택·힙)로 서로 다른 크기의 조각(세그먼트)으로 나누는 **비연속 메모리 할당(non-contiguous allocation)** 기법이다.
- **왜 필요한가**: 4KB 고정 크기로 자르는 페이징은 의미상 다른 영역(읽기전용 코드와 쓰기가능 변수)이 같은 페이지 안에 섞일 수 있어, 영역별로 권한을 따로 주기 어렵다. 프로그래머가 실제로 인식하는 단위(함수, 배열, 스택)대로 잘라야 권한 제어와 공유가 명확해진다.
- **핵심 직관**: 페이징이 고기를 부위 상관없이 무조건 같은 무게(예: 500g)로 자르는 것이라면, 세그멘테이션은 삼겹살·안심처럼 부위(의미) 단위로 자르는 것이다. 크기는 제각각이지만 부위별로 용도(권한)를 정하기 쉽다.

## 핵심 용어 정리 (내부에 등장하는 것들)

| 용어 | 의미 | 비유 |
|:---|:---|:---|
| 가상 메모리 / 비연속 할당 | 논리 주소 공간을 물리 메모리에 연속되지 않게 나눠 배치하는 상위 기법 | 짐을 방 하나에 몰아넣지 않고 여러 방에 나눠 보관 |
| 세그먼트(Segment) | 논리적 의미로 묶인 가변 크기 메모리 블록(코드·데이터·스택 등) | 부위별로 자른 고기 덩어리 |
| s(Segment Number) | 세그먼트 테이블의 인덱스 — 어느 세그먼트인지 식별 | 부위 이름표 |
| d(Offset) | 세그먼트 시작점부터의 거리 | 그 부위 안에서 몇 g 지점인지 |
| Segment Table | 세그먼트 번호별 Base·Limit·권한을 기록한 표 | 부위별 위치·중량·용도가 적힌 장부 |
| Base | 세그먼트가 실제로 적재된 물리 메모리 시작 주소 | 그 부위가 진열된 매대 위치 |
| Limit | 세그먼트의 최대 허용 크기 | 그 부위의 총 중량 한도 |
| Segmentation Fault | offset이 Limit을 넘거나 권한을 위반해 하드웨어가 발생시키는 예외(트랩) | 한도를 넘어 집으려다 경보 울림 |
| External Fragmentation(외부 단편화) | 세그먼트 할당·해제를 반복하며 메모리 중간에 남는 자잘한 빈 공간 | 진열대 곳곳에 남은 자투리 빈칸 |
| Compaction(압축) | 빈 공간을 한쪽으로 몰아 큰 연속 공간을 만드는 재정렬 작업 | 진열대를 다시 정리해 빈 칸을 한곳에 모음 |
| Paged Segmentation(단편화 페이징) | 세그먼트 내부를 다시 고정 크기 페이지로 나눠 외부 단편화를 없앤 절충 기법 | 부위별로 자른 고기를 다시 균일한 팩으로 소분 |

## 깊이 이해

### 주소 변환을 숫자로 따라가기
- 세그먼트 테이블에 두 항목이 있다고 하자: Code 세그먼트(s=0, Base=4000, Limit=2000), Data 세그먼트(s=1, Base=8000, Limit=800).
- CPU가 논리 주소 (s=1, d=500)을 요청하면: 먼저 d(500) < Limit(800)인지 검사 → 통과 → 물리 주소 = Base + d = 8000 + 500 = **8500**.
- CPU가 (s=1, d=850)을 요청하면: d(850) ≥ Limit(800) → 하드웨어가 즉시 Segmentation Fault 트랩을 발생시켜 접근을 막는다. 이 한계 검사가 프로세스 밖 메모리를 건드리지 못하게 막는 핵심 보호장치다.
- 페이징은 모든 페이지 크기가 같아 Base만 알면 되지만, 세그멘테이션은 세그먼트마다 크기가 달라 Base와 Limit을 반드시 한 쌍으로 관리해야 한다.

### 보호와 공유가 쉬워지는 이유
- 세그먼트마다 별도로 권한(Read/Write/Execute)을 지정할 수 있다. 위 예시에서 Code 세그먼트를 Read+Execute만 허용하고 Write는 차단하면, 코드 영역을 변조하려는 시도를 하드웨어가 즉시 막는다.
- 공유 라이브러리(예: libc.so)를 여러 프로세스가 쓸 때, 페이징에서는 함수가 페이지 경계에 걸쳐 잘리면 공유 설정이 까다롭지만, 세그멘테이션은 라이브러리 전체를 세그먼트 하나로 두고 각 프로세스의 세그먼트 테이블 항목만 같은 Base를 가리키게 하면 된다.

### 외부 단편화를 숫자로 확인하기
- 메모리에 3개의 빈 공간(Hole)이 3KB, 2KB, 4KB로 흩어져 있다고 하자. 전체 여유는 3+2+4=9KB이지만, 8KB짜리 세그먼트 하나를 통째로 넣을 자리는 없다 — 어느 Hole도 8KB보다 작기 때문이다. 이것이 외부 단편화다.
- Compaction으로 세 조각을 합쳐 연속된 9KB로 만들면 8KB 세그먼트를 넣을 수 있지만, 이미 실행 중인 모든 세그먼트의 물리 주소를 옮기고 Base를 다시 계산해야 해서 시스템 정지(Stall) 비용이 크다.
- 그래서 현대 아키텍처는 세그먼트 내부를 다시 4KB 페이지로 잘라(Paged Segmentation) Base를 페이지 단위로만 관리해, 외부 단편화를 아예 없앤다.

### 비유와 흔한 오해
- **비유**: 호텔 객실 배정과 같다. 객실마다 크기(Limit)가 다르고, 손님(프로세스)이 자기 객실 범위를 벗어나면 보안요원(MMU)이 경보(Trap)를 울린다.
- **오해**: "세그멘테이션이 논리적으로 완벽하니 단독으로 쓴다"는 틀렸다. 가변 크기 할당은 필연적으로 외부 단편화를 낳으므로, 실무에서는 반드시 페이징과 결합해 쓴다.

## 연결 개념
- 페이징(Paging) — 고정 크기 분할로 세그멘테이션의 외부 단편화를 보완하는 짝 개념
- MMU — Base·Limit 레지스터 비교와 트랩 발생을 실제로 수행하는 하드웨어
- Segmentation Fault — 세그멘테이션 한계 위반 시 발생하는 예외, C 프로그램의 대표적 런타임 오류명의 어원
- Paged Segmentation — 세그멘테이션과 페이징을 절충한 현대 아키텍처(x86 GDT 등)의 실제 구현 방식

# 📝 【답안용】 시험 답안 템플릿

> 목적: 시험장에서 25분에 그대로 쓰는 답안 양식. 

## 핵심 인사이트 (3줄 요약)

> 1. **본질**: 세그멘테이션은 프로세스의 가상 메모리를 기계적인 고정 크기가 아닌 Code, Data, Stack 등 논리적 의미 단위의 가변 크기로 분할하는 비연속 메모리 할당 기법이다.
> 2. **가치**: 의미가 동일한 블록 단위로 Base(시작 주소)와 Limit(한계 길이)을 부여함으로써, 완벽한 메모리 보호(Protection) 및 다른 프로세스와의 안전한 공유(Sharing)를 가능하게 한다.
> 3. **판단 포인트**: 프로그래머 관점에선 완벽한 추상화이나 물리 메모리 상에는 심각한 외부 단편화(External Fragmentation)를 유발하므로, 순수 세그멘테이션 대신 단편화 페이징(Paged Segmentation) 구조로 타협해야 한다.

## 출제 의도 및 답안 포인트

| 출제 의도 | 반드시 짚을 핵심 | 감점 회피 포인트 |
|:---|:---|:---|
| 메모리의 논리적 분할 이유와 하드웨어 보호 체계 이해 | Base(기준 주소)와 Limit(한계 주소) 검사 로직, Trap 발생 | 페이지 테이블과 구별 없이 단순히 주소만 더한다고 적는 오류 (Limit 검사 누락) |
| 세그멘테이션의 장점(보호/공유)과 단점(단편화)의 명확한 트레이드오프 파악 | 의미론적 분할로 인한 완벽한 권한 제어 vs 외부 단편화 병목 | 내부 단편화와 외부 단편화를 헷갈려서 반대로 기재 |

> 요약: 세그멘테이션의 핵심은 "주소를 변환한다"가 아니라, "Limit를 넘어가는 불법 접근을 하드웨어가 차단한다(Segmentation Fault)"는 보호 메커니즘에 있다.

## Ⅰ. 개요 및 필요성

- 정의: 가상 메모리를 프로세스의 논리적 구조(함수, 객체, 변수 배열 등)에 맞춰 서로 다른 가변 크기의 세그먼트로 분할하고 관리하는 기법
- 배경: 페이징 기법의 기계적 4KB 분할로 인해 논리적으로 분리되어야 할 코드와 데이터가 하나의 페이지에 혼재(보안 취약점)
- 필요성: 프로그래머의 관점(의미 단위)과 동일하게 메모리를 구조화하여, 세그먼트별로 독립적인 권한(Read/Write/Exec)을 부여하고 타 프로세스와 유연하게 공유하기 위함

---

## Ⅱ. 구조 및 구성요소 (세그먼트 테이블 논리 구조)

```text
[논리 주소 공간과 세그먼트 테이블 매핑]
CPU 주소 (s, d) = (Segment Number, Offset)
       |
[ 세그먼트 테이블 (MMU 내부 또는 RAM) ]
+-------+--------------+---------------+--------------+
| s 번호| Limit (길이) | Base (물리주소) | Protection |
+-------+--------------+---------------+--------------+
| 0(Code) |   2000     |     4000      | R, Execute   |
| 1(Data) |   800      |     7000      | R, W         |
+-------+--------------+---------------+--------------+
```

| 구성요소 | 핵심 역할 | 상세 하위 요소 / 특징 |
|:---|:---|:---|
| Segment Number (s) | 논리 공간의 덩어리 식별 | 세그먼트 테이블의 인덱스로 사용됨 |
| Offset (d) | 세그먼트 시작점으로부터의 변위 | 반드시 해당 세그먼트의 Limit(길이)보다 작아야 함 |
| Base (기준 주소) | 물리 메모리에 적재된 실제 시작 번지 | 크기가 가변적이므로, 빈 공간을 찾는 할당 알고리즘(First-fit 등) 필요 |
| Limit (한계 레지스터)| 해당 세그먼트의 최대 허용 크기 | 악의적이거나 버그로 인한 메모리 침범을 H/W가 차단하는 기준선 |

> 요약: 페이징은 크기가 일정해 Base만 알면 되지만, 세그멘테이션은 덩어리 크기가 다 달라 반드시 Base와 Limit을 한 쌍으로 관리해야 한다.

## Ⅲ. 동작원리 및 주소 변환 흐름도 (보호 매커니즘 중심)

```text
[MMU 내부의 세그멘테이션 주소 변환 및 한계 검사 흐름]
CPU (s, d) 요청 -> 세그먼트 테이블의 s번 항목 접근
  |--> IF ( d >= Limit ) : [ 주소 지정 오류 Trap 발생 (SegFault) ] -> OS 강제 종료
  |--> IF ( 권한 위반 )  : (예: Code 세그먼트에 Write 시도) -> [ 권한 오류 Trap 발생 ]
  |--> ELSE (정상)       : 물리 주소 = ( Base + d ) 생성 -> 메인 메모리 접근
```

| 단계 | 제어 단위 | 처리 내용 (보호와 변환의 동시 수행) |
|:---:|:---|:---|
| 1 | H/W (MMU) | 논리 주소에서 추출한 s로 세그먼트 테이블 레지스터(STBR) 참조 |
| 2 | H/W (Comparator) | 오프셋 d가 해당 세그먼트의 Limit를 초과하는지 병렬 비교 검사 |
| 3 | H/W (Protection) | 해당 세그먼트의 권한(R/W/X)과 현재 CPU 명령어가 일치하는지 검증 |
| 4 | S/W (OS) | Trap 발생 시, 운영체제가 개입해 해당 프로세스(스레드)에 SIGSEGV 시그널 전송 및 코어 덤프 |

> 요약: 세그멘테이션은 단순한 주소 변환기가 아니라, 구역을 벗어나는 포인터 연산을 즉결 처형하는 완벽한 하드웨어 방화벽이다.

---

## Ⅳ. 심화 비교: 세그멘테이션에서의 공유와 보호

페이징은 페이지 테이블 엔트리를 공유하더라도 그 안에 무엇이 들었는지 명확하지 않다. 세그멘테이션은 의미론적 공유가 극강의 장점이다.

| 구분 | 공유(Sharing) 메커니즘 | 보호(Protection) 메커니즘 | 판단 포인트 |
|:---|:---|:---|:---|
| 세그멘테이션 (강점)| 'Shared Library(예: libc.so)'를 단 1개의 세그먼트로 올려 여러 프로세스가 테이블 엔트리만 공유 | Code는 Read-Only, Data는 Read-Write 등 의미 단위 완벽 통제 | 프로그래머 의도와 H/W 구조 100% 일치 |
| 페이징 (약점) | 함수가 2개의 4KB 페이지에 걸쳐 잘릴 경우, 두 프로세스의 페이지 테이블 공유 설정이 매우 까다로움 | 한 4KB 안에 Code 2KB, Data 2KB 섞이면 권한을 무엇으로 줄지 난감 | 기계적 분할의 태생적 의미 단절 |

> 요약: DLL(동적 링크 라이브러리)이나 공유 메모리(IPC) 기능은 본질적으로 세그멘테이션의 논리적 아키텍처에 빚을 지고 있다.

## Ⅴ. 제약 사항 및 단편화(Fragmentation) 병목 해결

| 리스크 | 발생 원인 | 아키텍처 대응 방안 | 극복 효과 및 한계 |
|:---|:---|:---|:---|
| 외부 단편화 (External) | 크기가 다른 세그먼트들이 할당/해제를 반복하며 메모리 중간에 쓸모없는 작은 빈 공간(Hole) 무수히 발생 | **압축(Compaction)** / 메모리 조각 모음 | 실행 중인 프로그램을 멈추고 주소를 다 옮겨야 하므로 막대한 H/W 스톨(Stall) 및 오버헤드 유발 (현실적 불가) |
| 할당 오버헤드 | 빈 공간(Hole) 리스트를 뒤져서 First-fit, Best-fit 등 최적의 자리를 찾는 시간 지연 | **단편화 페이징 (Paged Segmentation)** | 세그먼트의 Base를 물리 주소로 두지 않고, 내부를 4KB 고정 페이지로 잘라버림 |

> 요약: 세그멘테이션의 완벽한 논리성은 '외부 단편화'라는 물리적 치명상 때문에 단독으로는 쓰일 수 없게 되었다.

## Ⅵ. 실무 적용 및 결론

**적용 방안 3개:**
1. 하이브리드 아키텍처(단편화 페이징) 적용: 최신 인텔 x86-64 계열 칩셋 및 Linux 커널 설계 시, 프로그래머(논리 주소) -> 세그멘테이션 기법(보안/공유) -> 페이징 기법(외부 단편화 제거) -> 물리 주소로 2단계 변환하는 하이브리드 메모리 아키텍처 채택
2. 스택(Stack) 영역 동적 확장: 프로세스 스택 세그먼트는 하향(Downward)으로 자라나는 특성이 있으므로, 세그먼트 디스크립터(GDT/LDT)에 'Expand-Down' 속성을 부여해 오프셋 검사 로직을 반대로 뒤집어 Limit 한계를 논리적으로 동적 확장
3. 커널/유저 스페이스 하드웨어 격리: OS 커널 모드(Ring 0)와 사용자 모드(Ring 3)의 권한 레벨 분리를 위해, GDT(Global Descriptor Table) 상의 세그먼트 권한 필드(DPL)를 하드웨어적으로 강제하여 유저 프로세스의 커널 메모리 해킹(Privilege Escalation) 원천 차단

**결론 (2줄):**
- 기술사 판단: 세그멘테이션은 기계적 효율(페이징) 대신 소프트웨어의 의미적 본질(공유, 보호, 캡슐화)을 메모리 하드웨어 구조에 매핑시킨 가장 진보된 가상 메모리 철학이다.
- 향후 방향: 순수 세그멘테이션은 외부 단편화로 사장되었으나, 그 철학은 최신 x86/ARM 아키텍처의 GDT, 권한 레벨 링(Ring) 등 시스템 보안과 메모리 보호를 담당하는 중추적 방화벽으로 계승되어 영구히 작동하고 있다.
