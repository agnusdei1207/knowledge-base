## 미리 알고가기

- 세그먼트는 코드, 데이터, 스택처럼 의미가 다른 주소 영역을 말함
- 세그먼트 테이블은 각 영역의 시작 주소와 길이와 권한을 관리함
- 가변 크기 할당이라 외부 단편화가 생길 수 있음

## Ⅰ. 개요

- **정의/개념**: 세그멘테이션은 프로세스 주소 공간을 프로그램의 논리 단위별 가변 크기 세그먼트로 나누고, 각 세그먼트에 base와 limit와 보호 속성을 부여해 관리하는 메모리 구조임
- **배경/필요성**: 코드와 데이터와 스택은 크기 변화와 보호 요구가 다르므로, 물리 효율만이 아니라 논리 구조에 맞는 독립적인 보호와 공유 단위가 필요함

## Ⅱ. 특징

- 프로그램 논리 구조에 맞춰 영역을 나누므로 보호와 공유 정책을 직관적으로 적용하기 쉬움
- 세그먼트별 크기와 성장 방향을 다르게 둘 수 있어 stack과 heap 관리에 유연함
- 권한 검사를 세그먼트 단위로 수행해 코드 실행 영역과 데이터 수정 영역을 분리하기 좋음
- 가변 크기 할당 특성상 외부 단편화와 compaction 부담이 커질 수 있음

## Ⅲ. 종류 및 비교

| 판단 기준 | 세그멘테이션 | 페이징 |
|:---|:---|:---|
| 관리 관점 | 논리 단위 중심으로 메모리를 다룸 | 물리 효율 중심으로 고정 크기 블록을 다룸 |
| 장점 | 보호와 공유를 의미 단위로 설정하기 쉽음 | 외부 단편화 없이 배치와 교체가 단순함 |
| 한계 | 외부 단편화와 재배치 비용이 큼 | 내부 단편화와 메타데이터 오버헤드가 생김 |
| 활용 방향 | 보호 모델과 특수 하드웨어에서 보조적으로 쓰임 | 현대 범용 OS의 기본 메커니즘임 |

## Ⅳ. 구성요소 및 구조

| 구성요소 | 설명 |
|:---|:---|
| Segment Number and Offset | 논리 주소를 세그먼트 식별자와 내부 위치로 나눠 서로 다른 보호 경계를 갖게 함 |
| Segment Table | 각 세그먼트의 base, limit, privilege를 기록해 물리 위치와 접근 가능 범위를 결정함 |
| Bounds and Permission Checker | offset이 limit를 넘는지와 읽기·쓰기·실행 권한을 동시에 검사해 보호 예외를 발생시킴 |
| Physical Allocation Region | 세그먼트별 실제 저장 위치를 따로 배치해 크기 변화와 공유 요구를 반영함 |

```text
+-------------------+     +-------------------+     +------------------+
| Segment No/Offset | --> | Segment Table     | --> | Base + Offset    |
+-------------------+     +-------------------+     +------------------+
                                   |
                                   v
                           +-------------------+
                           | Limit / Permission|
                           +-------------------+
```

## Ⅴ. 원리 및 절차 흐름도

```text
+-------------+     +-------------+     +-------------+     +-------------+
| 논리 주소 입력   | --> | 세그먼트 엔트리 조회 | --> | 범위·권한 검사   | --> | 물리 주소 생성   |
+-------------+     +-------------+     +-------------+     +-------------+
```

1. **논리 주소 입력**: CPU가 세그먼트 번호와 offset을 가진 주소를 전달함
2. **세그먼트 엔트리 조회**: 해당 세그먼트의 base와 limit와 권한을 읽음
3. **범위와 권한 검사**: offset 초과나 금지된 접근이면 예외를 발생시킴
4. **물리 주소 생성**: 조건을 만족하면 base와 offset을 더해 최종 주소를 만듦

## Ⅵ. 문제점 및 해결 방안

1. 문제: 세그먼트 크기가 제각각이면 할당과 해제가 반복될수록 외부 단편화가 커져 큰 영역 배치가 어려워짐
   - 해결방안: paged segmentation이나 compaction 정책을 적용하고 fragmentation ratio와 allocation failure rate로 검증함
2. 문제: 큰 세그먼트 이동이 잦아지면 compaction 자체가 서비스 지연을 유발할 수 있음
   - 해결방안: free list 분리와 buddy allocation을 병행하고 relocation time과 allocation latency로 검증함
3. 문제: 현대 시스템은 페이징 중심 구조라 세그멘테이션을 광범위하게 쓰기보다 제한적으로 활용해야 일관성이 유지됨
   - 해결방안: 보호가 필요한 논리 경계에만 세그먼트 개념을 적용하고 protection fault accuracy와 management complexity로 검증함

## Ⅶ. 적용 사례

- x86 보호 모드에서는 코드와 데이터 세그먼트를 분리해 권한을 통제하고 확인 지표는 protection fault accuracy와 privilege violation rate임
- 임베디드 MPU 환경에서는 코드·데이터·스택 영역을 별도 세그먼트처럼 관리해 오동작을 격리하고 확인 지표는 fault isolation rate와 recovery time임
- 특수 목적 RTOS는 태스크별 메모리 경계를 논리 영역으로 나눠 안전성을 확보하고 확인 지표는 memory protection fault count와 task latency임

## Ⅷ. 결론

세그멘테이션의 가치는 물리 효율보다도 논리 경계에 맞는 보호와 공유를 제공하는 데 있으므로, 실무 판단은 단편화 비용보다 얻는 보호 이점이 큰지로 내려야 함.
