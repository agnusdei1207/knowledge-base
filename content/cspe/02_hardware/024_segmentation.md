# 📖 【암기용】 개념 완전 이해

## 한눈에
- **개요**: 세그멘테이션은 **메모리 관리 기법**으로, 가상 주소 공간을 고정 크기가 아닌 코드·데이터·스택 등 **논리적 의미 단위(세그먼트)**의 가변 길이 블록으로 분할하여 관리하는 방식임.
- **왜 필요한가**: 페이징(022 참조)은 4KB씩 기계적으로 분할하여 관리가 편하나, 하나의 함수나 데이터 구조가 여러 페이지에 걸쳐 찢어져 "이 함수만 읽기 전용으로 보호" 같은 논리 단위 접근 제어가 어려움. 세그멘테이션은 사용자/컴파일러 관점의 논리적 구조를 그대로 유지함.
- **핵심 직관**: 책을 보관할 때 무조건 100쪽 단위로 뜯어서(페이징) 꽂는 게 아니라, 1장(서론)·2장(본론)·3장(결론)처럼 의미 있는 장(Chapter) 단위로 나누어(세그멘테이션) 관리하는 방식임.

## 핵심 용어 정리 (내부에 등장하는 것들)

| 용어/표기 | 의미 | 비유·예 |
|:---|:---|:---|
| 메모리 관리 (상위 키워드) | OS가 물리 메모리를 프로세스에 할당·보호·회수하는 체계 | "창고 관리 시스템" |
| 세그먼트 (Segment) | 코드·데이터·스택 등 논리적으로 연관된 가변 크기 메모리 블록 | "책의 한 장(Chapter)" |
| Segment Table | 각 세그먼트의 시작 주소(Base)와 길이(Limit)를 기록한 표 | "목차(1장은 10p부터 15p 분량)" |
| Base | 세그먼트가 물리 메모리에서 시작하는 주소 | "장이 시작되는 실제 페이지 번호" |
| Limit | 세그먼트의 전체 길이(접근 범위 한계) | "그 장의 총 분량" |
| 외부 단편화 | 총 빈 공간은 충분하나 연속 공간이 부족하여 적재 불가 | "빈 칸은 100평인데 50평짜리 연속 공간이 없음" |

## 깊이 이해
- **배경·문제의식**: 사용자와 컴파일러는 메모리를 바이트의 연속 덩어리가 아니라 Code·Data·Heap·Stack 등 독립된 논리적 객체의 모음으로 바라봄. 이 논리적 관점을 하드웨어 관리에 그대로 반영하려는 시도에서 세그멘테이션이 탄생함. 페이징(022 참조)이 고정 크기 분할로 물리적 관리 효율에 초점을 맞춘 반면, 세그멘테이션은 논리적 보호·공유에 초점을 맞춤.
- **작동 원리**: CPU가 2차원 주소 `[세그먼트 번호(s), 오프셋(d)]`를 발행하면 MMU(025 참조)가 Segment Table에서 s번 항목을 찾음. 오프셋 d가 Limit을 초과하면 하드웨어 트랩(Protection Fault)을 발생시키고, 범위 내이면 Base + d를 산술 덧셈하여 물리 주소를 산출함.
- **비유**: 호텔 구조. "3번 세미나실, 입구에서 5m 앞"으로 가려 할 때, 3번 세미나실의 크기(Limit)가 4m뿐이면 "벽 밖으로 나간다"며 경호원(MMU)이 차단함.
- **구체 예시**: 공유 라이브러리(libc.so)를 여러 프로세스가 사용할 때, 페이징에서는 라이브러리가 여러 페이지에 걸쳐 분산되어 공유 설정이 복잡하나, 세그멘테이션에서는 '라이브러리 세그먼트 1개'를 여러 프로세스의 Segment Table이 동일 Base로 가리키면 완벽히 공유됨.
- **흔한 오해·주의점**: 세그멘테이션은 필요한 만큼만 자르므로 내부 단편화가 없으나, 가변 크기 블록의 적재·해제 반복으로 중간에 비연속적 빈 공간이 축적되는 외부 단편화가 발생함. 해소를 위한 메모리 압축(Compaction)은 전체 세그먼트를 이동해야 하므로 비용이 크며, 이 때문에 현대 OS는 세그먼트를 다시 페이지로 분할하는 Paged Segmentation을 채택함.

## 연결 개념
- **022 가상 메모리·페이징**: 세그멘테이션과 반대 특성(고정 분할, 내부 단편화)을 가진 대안 기법이며, Paged Segmentation으로 결합됨.
- **025 MMU**: Base+Offset 연산과 Limit 검증을 수행하는 하드웨어.
- **외부 단편화**: 총 빈 공간은 충분하나 연속 공간이 부족한 현상. 세그멘테이션의 근본적 한계임.

# 📝 【답안용】 시험 답안 템플릿

## 핵심 인사이트 (3줄 요약)

> 1. **본질**: 세그멘테이션은 가상 주소 공간을 논리적 의미 단위(Code, Data, Stack)의 가변 길이 블록으로 분할하여 매핑하는 메모리 관리 기법임.
> 2. **가치**: 논리 단위가 유지되어 세그먼트별 접근 제어(Read/Write/Execute)와 공유 라이브러리 매핑이 직관적이고 강력함.
> 3. **판단 포인트**: 가변 크기에 의한 외부 단편화가 치명적이므로, 현대 아키텍처(x86)는 세그먼트로 논리적 보호를 한 뒤 다시 페이징으로 분할하는 Paged Segmentation을 채택함.

## 출제 의도 및 답안 포인트

| 출제 의도 | 반드시 짚을 핵심 | 감점 회피 포인트 |
|:---|:---|:---|
| 사용자 관점 메모리 관리 원리 이해 | 가변 분할, Base/Limit 검증, 보호·공유 강점 | 페이징의 고정 분할 특성과 혼동 |
| 세그멘테이션의 한계 파악 | 외부 단편화 발생 메커니즘 | 내부 단편화가 발생한다고 오기 |
| 현대 시스템 적용 방식 확인 | 페이징과의 결합(Paged Segmentation) | 세그멘테이션 단독 사용으로 단정 |

> 요약: 왜 페이징을 두고 세그멘테이션이 필요한가(보호·공유)와, 왜 단독으로 쓸 수 없는가(외부 단편화)를 트레이드오프로 명확히 제시해야 함.

---

## Ⅰ. 개요 및 필요성

- 개요: 가상 주소 공간을 논리적 의미 단위(함수, 배열, 스택 등)의 가변 크기 블록으로 분할하여 물리 메모리에 적재하는 기법임.
- 배경: 페이징은 고정 크기로 물리적 관리 효율은 높이나, 논리적 객체가 여러 페이지에 분산되어 보호·공유 설정이 복잡해짐.
- 필요성: 모듈 단위 접근 권한 제어와 공유 라이브러리의 단일 세그먼트 매핑을 위해 논리 구조를 유지하는 분할 기법이 필요함.

---

## Ⅱ. 구조 및 구성요소

```text
CPU 가상 주소(Segment #, Offset) -> Segment Table 참조
  Limit 검사 통과 -> Base + Offset = 물리 주소
  Limit 초과 또는 권한 위반 -> Trap(보호 오류)
```

| 구성요소 | 역할 | 특이사항 |
|:---|:---|:---|
| Segment 번호(s) | 프로세스 내 논리 분할 단위의 식별자 | Segment Table의 인덱스 |
| Offset(d) | 세그먼트 시작점(Base)으로부터의 변위 | Limit보다 작아야 유효 |
| Segment Table | 각 세그먼트의 Base·Limit·권한 비트 보관 | MMU 내부 STBR 레지스터로 참조 |
| 권한 비트 | Read/Write/Execute 제어 플래그 | 논리 단위와 1:1 매핑으로 보호 |

> 요약: 세그멘테이션 하드웨어는 Base+Offset 연산 전에 반드시 Limit 검증과 권한 검사를 수행하여 메모리 침범을 하드웨어 레벨에서 차단함.

---

## Ⅲ. 동작원리 및 흐름도

```text
주소 발생(s, d) -> Segment Table 탐색 -> Limit 검증(d < Limit?) -> 권한 체크 -> 물리 주소 산출(Base + d)
                                           |
                                           +-> 위반 시 Trap(Protection Fault)
```

- 1단계 [주소 분리]: CPU가 2차원 논리 주소를 세그먼트 번호(s)와 변위(d)로 분리함.
- 2단계 [Limit 검증]: Segment Table에서 s번 항목을 찾아, d가 해당 세그먼트의 Limit을 초과하는지 하드웨어 검증함.
- 3단계 [권한 검사]: 접근 유형(Read/Write/Execute)이 권한 비트와 일치하는지 확인하고, 위반 시 Trap을 발생시킴.
- 4단계 [물리 주소 생성]: 검증 통과 시 Base + d를 산술 덧셈하여 최종 물리 주소를 산출함.

> 요약: Base+Offset 연산에 Limit 검증이라는 하드웨어 샌드박스가 강제되어 메모리 침범을 원천 차단함.

---

## Ⅳ. 특징
- 내부 단편화 없음: 필요한 크기만큼만 세그먼트를 할당하므로 페이징의 마지막 페이지 잔여 공간 문제가 발생하지 않음
- 외부 단편화 심화: 가변 크기 블록의 적재·해제 반복으로 비연속적 빈 공간이 축적되어, 총 여유 공간은 충분하나 연속 할당 불가 현상 발생
- 보호·공유의 직관성: Code 세그먼트=Read+Execute, Data 세그먼트=Read+Write 등 논리 단위별 권한 설정이 1:1 매핑되어, 공유 라이브러리도 단일 세그먼트 공유로 처리 가능

---

## Ⅴ. 심화 비교 및 적용 판단

| 구분 | 세그멘테이션 | 페이징 | Paged Segmentation |
|:---|:---|:---|:---|
| 분할 기준 | 논리 단위(가변 크기) | 물리 단위(고정 4KB) | 논리 분할 후 고정 분할 |
| 단편화 | 외부 단편화 | 내부 단편화 | 내부 단편화만(미미) |
| 보호·공유 | 세그먼트 단위 직관적 보호·공유 | 페이지 단위(세분화 곤란) | 세그먼트 보호 + 페이지 관리 |
| 테이블 크기 | 소규모(세그먼트 수 적음) | 대규모(수백만 엔트리) | 이중 테이블(TLB로 완화) |

> 요약: 현대 x86-64는 세그멘테이션의 물리 분할을 축소(Flat Segment: Base=0, Limit=Max)하고, 보호 권한 기능만 페이징과 결합하여 외부 단편화를 근본 차단함.

**리스크·대응:**
- 외부 단편화 심화: 세그먼트 생성/해제 반복 시 연속 공간 확보 불가 → 메모리 압축(Compaction) 수행, 단 시스템 일시 정지 비용이 큼 → Paged Segmentation으로 전환하여 근본 해소 (지표: 메모리 조각화율)
- Segment Table 변조 공격: 커널 영역의 GDT/LDT를 악의적으로 변경 → 하드웨어 보호 링(Ring 0~3)과 SMEP/SMAP으로 사용자 모드의 커널 메모리 접근 차단

---

## Ⅵ. 실무 적용 및 결론

**적용 방안 3개:**
1. x86 GDT/LDT 보호 링 설정: Intel x86 계열의 GDT(Global Descriptor Table)에서 Code/Data/Stack 세그먼트별 Ring 0~3 보호 수준을 설정하여 커널-사용자 메모리 격리를 하드웨어 레벨로 보장함.
2. 공유 라이브러리 매핑: libc.so 등 공유 라이브러리를 단일 세그먼트로 지정하여 여러 프로세스의 Segment Table이 동일 Base를 가리키게 설정, 물리 메모리 중복 사용을 방지함.
3. NX/XD 비트 연계 방어: 스택 세그먼트의 실행 권한 비트를 해제(NX bit)하고, 배열 접근 시 Limit 초과를 MMU 트랩으로 차단하여 Buffer Overflow·ROP 공격을 하드웨어 레벨에서 방어함.

**결론:**
- 기술사 판단: 순수 세그멘테이션은 외부 단편화로 단독 사용이 비실용적이나, 논리적 보호(Protection Ring)의 개념은 현대 OS 보안 모델의 근간으로 존속함.
- 향후 방향: x86-64에서는 세그멘테이션의 물리 분할 역할을 Flat 모델로 최소화하고, 보호 기능만 페이징·TLB와 결합하여 오버헤드를 줄이는 방향으로 최적화됨.
