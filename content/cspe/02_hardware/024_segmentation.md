# 📖 【암기용】 개념 완전 이해

> 목적: 세그멘테이션을 처음 봐도 왜 프로그램을 논리적 단위로 나눠 관리하는지 이해하게 만든다. 시험 답안 양식이 아니라, 이해를 위한 친절한 설명이다.

## 한눈에
- **개요**: 프로그램 주소 공간을 코드·데이터·스택 같은 논리적 단위(세그먼트)로 나눠 관리하는 메모리 관리 기법
- **왜 필요한가**: 페이징은 물리적으로 균일한 블록만 다뤄 프로그램의 논리 구조(코드·데이터·스택 경계)를 표현하지 못한다. 세그멘테이션은 이 논리 구조를 그대로 반영해 세그먼트별 보호·공유를 가능하게 한다.
- **핵심 직관**: 이사할 때 짐을 같은 크기 상자로 나누는 대신, 옷장·책장·냉장고처럼 원래 용도별 단위 그대로 옮기는 방식이다.

## 깊이 이해
- **배경·문제의식**: 프로그램은 코드(읽기·실행), 전역 데이터(읽기·쓰기), 스택(동적 증가)처럼 서로 다른 접근 패턴과 보호 요구를 가진 영역으로 구성된다.
- **작동 원리**: 세그멘테이션은 각 세그먼트에 번호를 부여하고, 세그먼트 테이블에 시작 주소(base)와 길이(limit)를 저장한다.
- **작동 원리**: 가상주소는 (세그먼트 번호, offset) 쌍으로 구성되며, MMU는 offset이 해당 세그먼트의 limit보다 작은지 검사한 뒤 base + offset으로 물리주소를 계산한다.
- **작동 원리**: offset이 limit을 초과하면 세그먼트 폴트(segmentation fault)를 발생시켜 잘못된 접근을 차단한다.
- **비유**: 세그먼트 테이블은 아파트 단지의 동별 안내판과 같아서, "몇 동(세그먼트 번호)의 몇 층부터 몇 층까지(base~base+limit)"를 알려주고 범위를 벗어난 요청은 막는다.
- **구체 예시**: 코드 세그먼트는 실행 권한만 부여하고 쓰기 권한을 제거해, 실행 중인 프로그램이 자기 코드 영역을 실수로 덮어쓰는 것을 방지한다.
- **구체 예시**: 여러 프로세스가 같은 라이브러리 코드 세그먼트를 공유하면, 물리 메모리에는 코드 사본 1개만 두고 각 프로세스의 세그먼트 테이블이 같은 base를 가리키게 할 수 있다.
- **흔한 오해·주의점**: 세그멘테이션은 "가변 크기"라는 이유로 페이징보다 무조건 비효율적이라고 단정할 수 없으며, 논리적 보호·공유가 중요한 경우 오히려 유리하다.
- **흔한 오해·주의점**: 세그멘테이션의 외부 단편화는 페이징의 내부 단편화와 다른 문제이며, 세그먼트 크기가 가변적이기 때문에 할당·해제가 반복되면 빈 공간이 조각난다.

## 연결 개념
- 페이징(Paging) — 고정 크기 블록 기반의 대비 기법
- 세그멘테이션+페이징 결합 — 논리적 보호와 고정 크기 배치를 함께 취하는 방식
- 외부 단편화(External Fragmentation)·압축(Compaction) — 세그멘테이션의 대표 문제와 대응
- 공유 라이브러리(Shared Library) — 세그먼트 공유의 실무 적용 사례

# 📝 【답안용】 시험 답안 템플릿

> 목적: 시험장에서 25분에 그대로 쓰는 답안 양식. 작성방식(추상표현 금지·수치·도식·문제유형 전환)을 엄격히 지킨다.
> 핵심: 세그멘테이션은 페이징과의 단순 비교를 넘어, base+limit 검사 메커니즘과 외부 단편화 대응까지 구체적으로 제시한다.

## 핵심 인사이트 (3줄 요약)

> 1. **본질**: 세그멘테이션(Segmentation)은 주소 공간을 코드·데이터·스택 같은 논리적 단위로 나눠 base+limit으로 관리하는 메모리 관리 기법이다.
> 2. **가치**: 세그먼트별 독립적인 보호(읽기·쓰기·실행 권한)와 공유(라이브러리 코드 세그먼트)를 가능하게 한다.
> 3. **판단 포인트**: 가변 크기 할당으로 인한 외부 단편화 발생 가능성과 압축 비용을 함께 판단해야 한다.

## 출제 의도 및 답안 포인트

| 출제 의도 | 반드시 짚을 핵심 | 감점 회피 포인트 |
|:---|:---|:---|
| 세그멘테이션 주소 변환 이해 확인 | 세그먼트 번호+offset, base+limit 검사 | limit 검사 절차를 생략하고 서술 |
| 보호·공유 이점 이해 확인 | 세그먼트별 권한 분리, 코드 세그먼트 공유 | 페이징과 차별화된 장점을 언급하지 않음 |
| 외부 단편화 문제 인식 확인 | 가변 크기 할당·해제로 인한 단편화, 압축 비용 | 단편화 문제를 페이징의 내부 단편화와 혼동 |

> 요약: 이 문제는 세그멘테이션 정의 암기가 아니라 base+limit 검사 절차와 외부 단편화 대응 방안을 함께 짚었는지를 확인한다.

## Ⅰ. 개요 및 필요성

- 정의: 주소 공간을 코드·데이터·스택 같은 논리적 단위(세그먼트)로 나눠 base+limit으로 관리하는 기법
- 배경: 페이징은 물리적 균일 블록만 다뤄 프로그램의 논리 구조별 보호·공유 요구를 반영하기 어려움
- 필요성: 세그먼트별 독립적 보호·공유가 필요한 환경에서는 논리 단위 관리가 페이징보다 요구사항에 부합함

---

## Ⅱ. 구조 및 구성요소

```text
Virtual Address (Segment Number, Offset)
  -> Segment Table 조회 (Base, Limit, 권한)
  -> Offset < Limit 검사
       -> 통과: Physical Address = Base + Offset
       -> 실패: Segmentation Fault
```

| 구성요소 | 역할 | 특이사항 |
|:---|:---|:---|
| Segment Table | 세그먼트 번호별 base·limit·권한 저장 | 세그먼트마다 크기가 다름 |
| Base Register | 세그먼트 시작 물리주소 | 세그먼트 이동 시 갱신 필요 |
| Limit Register | 세그먼트 길이 | offset 초과 시 폴트 발생 |
| 권한 비트 | 읽기/쓰기/실행 권한 구분 | 코드·데이터 세그먼트 보호 차별화 |

> 요약: 세그먼트 테이블은 세그먼트마다 base·limit·권한을 따로 관리해 논리적 보호 단위를 구성한다.

---

## Ⅲ. 동작원리 및 흐름도

```text
가상주소 발생 -> 세그먼트 번호 추출
  -> Segment Table 조회 -> Base, Limit 확인
  -> Offset < Limit 검사
       -> 통과 -> 물리주소 계산(Base+Offset) -> 메모리 접근
       -> 실패 -> Segmentation Fault -> 예외 처리
```

| 단계 | 처리 내용 | 검증 기준 |
|:---:|:---|:---|
| 1 | 가상주소에서 세그먼트 번호·offset 분리 | 세그먼트 번호 유효성 |
| 2 | 세그먼트 테이블에서 base·limit·권한 조회 | 유효 비트 확인 |
| 3 | offset이 limit 이내인지 검사 | 범위 초과 여부 |
| 4 | 물리주소 계산 및 접근 권한 검사 후 메모리 접근 | 읽기/쓰기/실행 권한 일치 여부 |

> 요약: 세그멘테이션은 limit 검사와 권한 검사 두 단계를 거친 뒤에만 실제 메모리 접근을 허용한다.

## Ⅳ. 특징

| 구분 | 내용 | 판단 포인트 |
|:---|:---|:---|
| 장점 | 논리적 단위(코드·데이터·스택)별 독립 보호와 공유가 가능함 | 라이브러리 코드 세그먼트 공유로 물리 메모리 절감 |
| 한계 | 가변 크기 할당·해제 반복 시 외부 단편화가 누적됨 | 압축(compaction) 수행 시 CPU 오버헤드 발생 |
| 비교 포인트 | 페이징 대비 논리 구조 반영은 우수하나 배치 효율은 낮음 | 배치 효율 우선이면 페이징, 보호·공유 우선이면 세그멘테이션 |

> 요약: 세그멘테이션은 보호·공유에 강점이 있지만 외부 단편화 관리 비용을 감수해야 한다.

## Ⅴ. 심화 비교 및 적용 판단

| 비교 축 | 페이징 | 세그멘테이션 | 선택 기준 |
|:---|:---|:---|:---|
| 구조 | 고정 크기 블록 | 가변 크기 논리 단위 | 논리 구조 보호가 중요하면 세그멘테이션 |
| 비용/성능 | 내부 단편화 존재 | 외부 단편화·압축 비용 존재 | 배치 효율 우선 시 페이징 |
| 운영/위험 | 페이지 테이블 크기 관리 | 세그먼트 재배치·압축 관리 | 공유 라이브러리 활용도가 높으면 세그멘테이션 결합 고려 |

> 요약: 배치 효율은 페이징, 논리적 보호·공유는 세그멘테이션이 유리하므로 요구사항에 따라 선택하거나 결합한다.

| 리스크 | 원인 | 대응 방안 | 확인 지표 |
|:---|:---|:---|:---|
| 외부 단편화 누적 | 세그먼트 할당·해제 반복 | 압축(compaction), 재배치 스케줄링 | 가용 공간 단편 개수 |
| 세그먼트 폴트 빈발 | limit 설정 오류 또는 동적 증가 미반영 | limit 동적 조정, 경계 검사 강화 | 세그먼트 폴트 발생 빈도 |
| 압축 오버헤드 | 대규모 세그먼트 재배치 | 압축 주기 최적화, 유휴 시간대 수행 | 압축 소요 시간, CPU 이용률 |

> 요약: 세그멘테이션 리스크는 외부 단편화와 압축 비용을 지표로 통제해야 한다.

| 점검 항목 | 목표 기준 | 측정 방법 |
|:---|:---|:---|
| 단편화 비율 | 가용 공간 대비 단편 비율 최소화 목표 설정 | 메모리 할당자 통계 |
| 세그먼트 폴트율 | 잘못된 접근 차단율 확인 | 커널 예외 로그 |
| 압축 소요 시간 | 압축 1회 수행 시간 확인 | 시스템 벤치마크 |

> 요약: 도입 효과는 단편화 비율, 세그먼트 폴트율, 압축 소요 시간으로 판단한다.

## Ⅵ. 실무 적용 및 결론

**적용 방안 3개:**
1. 코드·데이터·스택을 별도 세그먼트로 분리하고 권한 비트를 차별화해 코드 영역 무단 변경을 차단함
2. 공용 라이브러리는 코드 세그먼트를 공유 구조로 설계해 다중 프로세스에서 물리 메모리 중복 적재를 방지함
3. 외부 단편화가 심화되는 환경은 압축 주기를 설정하거나 세그먼트+페이징 결합 구조로 전환함

**결론 (2줄):**
- 기술사 판단: 배치 효율이 우선이면 페이징, 논리적 보호·공유가 우선이면 세그멘테이션 또는 결합 구조를 선택함
- 향후 방향: 현대 시스템은 순수 세그멘테이션보다 페이징 기반에 권한 링·영역 보호 개념을 결합한 형태로 진화하는 추세임
