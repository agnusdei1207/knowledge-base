# 📖 【암기용】 개념 완전 이해

## 한눈에
- **개요**: 포워딩·분기 예측은 파이프라인 해저드(008) 중 데이터 해저드를 "새치기"로 해소하는 포워딩과, 제어 해저드를 "미래 예측"으로 해소하는 분기 예측을 묶은 하드웨어 보상 회로다.
- **왜 필요한가**: 5단 파이프라인은 앞 명령 결과를 뒤가 바로 써야 하는 RAW 의존성과, 분기 다음에 뭘 인출할지 모르는 문제로 시도 때도 없이 멈춘다(Stall). 멈추면 CPI가 1.0에서 멀어져 성능이 수직 낙하하므로 전용 회로가 필요하다.
- **핵심 직관**: 포워딩은 요리가 접시에 담기길(WB) 기다리지 않고 프라이팬에서 갓 나온 고기(EX 결과)를 바로 덜어 쓰는 것이고, 분기 예측은 손님이 메뉴를 고민하는 동안 늘 먹던 메뉴를 미리 조리하기 시작하는 눈치 게임이다.

## 핵심 용어 정리 (내부에 등장하는 것들)

| 용어 | 의미 | 비유 |
|:---|:---|:---|
| 포워딩(Forwarding/Bypass) | WB를 기다리지 않고 EX 결과를 다음 명령 입력으로 바로 넘기는 회로 — 데이터 해저드(RAW) 전담 | 완성 전 반찬을 옆자리에 바로 건넴 |
| EX/MEM 포워딩 | 직전 명령의 ALU 결과를 현재 명령의 EX 입력으로 즉시 전달 | 방금 구운 고기를 바로 건넴 |
| MEM/WB 포워딩 | 두 명령 전의 결과(이미 MEM을 지난 값)를 현재 명령의 EX 입력으로 전달 | 조금 전 만든 반찬을 다시 꺼내 줌 |
| Load-Use 해저드 | Load 직후 그 값을 바로 쓰는 경우 — 데이터가 MEM에서야 나와 포워딩으로도 완전 제거 불가 | 냉장고 문 여는 동안은 재료를 못 씀 |
| 분기 예측(Branch Prediction) | 분기 결과 확정 전에 미리 추측해 다음 명령어를 인출하는 기법 — 제어 해저드 전담 | 주문 전에 늘 시키던 메뉴부터 조리 |
| 투기적 실행(Speculative Execution) | 예측을 믿고 확정 전에 미리 명령어를 실행하는 것 | 우산을 미리 챙겨 나감 |
| BTB (Branch Target Buffer) | IF 단계에서 "분기문 여부"와 "목적지 주소"를 캐싱하는 버퍼 | 자주 가는 목적지 주소록 |
| BHT (Branch History Table) | 분기의 과거 결과(Taken/Not Taken)를 저장해 다음을 예측하는 테이블 | 단골손님 주문 이력 노트 |
| 2비트 포화 카운터 | 00(강한 NT)~11(강한 T) 4단계로 최근 분기 성향을 누적 기록하는 예측기 | 한 번 틀려도 성향을 바로 안 바꾸는 신중함 |
| 정적/동적 예측 | 정적=컴파일러 규칙으로 미리 정함, 동적=런타임 이력으로 하드웨어가 실시간 판단 | 정적=고정 매뉴얼, 동적=경험 학습 |
| Flush (플러시) | 예측이 틀렸을 때 이미 인출·실행 중이던 명령어를 통째로 버리는 것 | 잘못 만든 요리를 폐기 |
| CPI / IPC | 명령어당 클럭 수 / 클럭당 완료 명령어 수 (이상값 1.0) | 라인이 꽉 찼을 때 1클럭당 1개 출고 |

## 깊이 이해

### 포워딩 — 데이터 해저드를 수치로 없애기
- `ADD R1,R2,R3` 직후 `SUB R4,R1,R5`는 R1을 즉시 필요로 한다. 원칙대로면 ADD가 WB(5단)를 마칠 때까지 SUB의 EX(3단)가 못 시작해 2클럭을 Stall한다(008 참조).
- **EX/MEM 포워딩**: ADD의 EX 연산이 끝나는 즉시(3단 직후) 그 결과를 레지스터 파일을 거치지 않고 다음 클럭 SUB의 EX 입력선으로 꽂는다. 이러면 Stall이 2클럭에서 0클럭으로 사라진다.
- **MEM/WB 포워딩**: 두 명령 떨어진 의존성(ADD 다음다음 명령이 R1 사용)은 ADD가 MEM을 지난 시점의 값을 포워딩해 처리한다.
- **한계 — Load-Use**: `LOAD R1,[addr]` 직후 `ADD R2,R1,R3`는 다르다. Load 결과는 MEM이 끝나야 나오는데 다음 명령의 EX는 그보다 먼저 시작돼야 하므로, 포워딩을 아무리 잘 설계해도 최소 1사이클 Stall이 남는다. 컴파일러가 Load와 사용 사이에 무관한 명령어를 끼우는 재배치로 이 1사이클을 흡수한다.

### 분기 예측 — BTB와 BHT의 역할 분담
- `if (a > b)` 조건 분기는 EX에서야 확정되므로, 예측이 없으면 IF는 그때까지 다음 명령어를 못 가져와 2~3클럭을 날린다.
- **BTB**는 "이 주소가 분기문인지, 분기면 목적지가 어디인지"를 캐시해 IF에서 바로 알려준다. **BHT**는 "이 분기가 최근 Taken이었는지"를 2비트 포화 카운터로 저장해 방향을 추측한다.
- CPU는 BTB로 목적지를, BHT로 방향을 동시에 예측해 그 주소로 투기적 실행을 시작한다. 맞으면 손실 0클럭, 틀리면 진행분을 전부 Flush하고 정상 주소부터 재시작하며, 이 페널티는 깊이에 비례해 보통 10~20클럭이다.

### 2비트 포화 카운터를 수치로 이해하기
- 상태는 00(강한 NT)→01(약한 NT)→10(약한 T)→11(강한 T) 4단계다. Taken이면 +1, Not-Taken이면 -1하되 0·3을 벗어나지 않는다.
- 1비트 예측기와 달리 2비트는 "가끔 한 번 튀는 예외"에 바로 흔들리지 않는다. `for(i=0;i<100;i++)`는 99번 Taken·마지막 1번 Not-Taken인데, 1비트는 마지막에 틀리고 다음 루프 진입에도 그 여파로 또 틀린다. 2비트는 11에서 10으로 한 칸만 내려가 다음 루프 첫 반복도 Taken으로 맞춘다. 이런 반복문에서 2비트 예측기는 98% 이상 적중한다.

### 흔한 오해
- "포워딩이 모든 데이터 해저드를 0사이클로 없앤다"는 틀렸다. Load-Use는 최소 1사이클이 남는다.
- "분기 예측은 언제나 이득"도 아니다. 틀리면 Flush로 수십 클럭을 손해 보므로, 파이프라인이 깊을수록 예측 정확도가 코어 전체 성능을 좌우한다.

## 연결 개념
- 파이프라인 해저드(008) — 포워딩·분기 예측이 각각 해소하는 데이터·제어 해저드의 근본 원인
- 투기적 실행 — 분기 예측을 믿고 미리 실행하는 기술, 보안 취약점(Meltdown/Spectre)의 원인
- 비순차 실행(OoO) — 포워딩·예측으로도 못 푸는 의존성을 명령어 순서를 섞어 해결하는 기법

# 📝 【답안용】 시험 답안 템플릿

## 핵심 인사이트 (3줄 요약)

> 1. **본질**: 데이터 포워딩과 분기 예측은 파이프라인의 데이터 의존성(RAW)과 제어 불확실성을 해소해 IPC 저하를 방어하는 하드웨어 최적화 회로임.
> 2. **가치**: 포워딩은 EX 결과를 즉시 재사용해 2사이클 스톨을 0사이클로 없애고, 분기 예측은 BHT/BTB로 제어 해저드 플러시 빈도를 5% 미만으로 통제함.
> 3. **판단 포인트**: 단 수가 깊은 슈퍼파이프라인일수록 분기 예측 실패 페널티(10~20사이클)가 치명적이라, 다단 동적 예측기의 정교함이 코어 성능을 좌우함.

|:---|:---|:---|

## Ⅰ. 개요 및 필요성

- 개요: 파이프라인 데이터 해저드를 해소하는 포워딩과, 제어 해저드를 완화하는 분기 예측 메커니즘임
- 배경: 명령어 간 의존성으로 인한 멈춤(Stall·Flush)이 깊은 파이프라인에서 심각한 CPI 손실을 유발함(008 참조)
- 필요성: 클럭 주파수를 낭비하지 않고 이상적 CPI 1.0에 근접하기 위한 필수 하드웨어 보상 회로가 요구됨

---

## Ⅱ. 구조 및 구성요소

```text
[포워딩 경로와 분기 예측 유닛의 배치]
IF -> ID -> EX(결과 생성) -> MEM -> WB
             |            |
   포워딩:   +--(EX/MEM)--+---> 다음 명령 EX 입력 MUX
             +--(MEM/WB)------> 다다음 명령 EX 입력 MUX
분기 예측: IF 단계에 BTB(목적지 캐시) + BHT(방향 예측기) 부착
```

| 구성요소 | 핵심 역할 | 하위 요소·특징 |
|:---|:---|:---|
| EX/MEM 포워딩 | 직전 명령 ALU 결과를 현재 EX 입력으로 우회 | ALU 출력 → 다음 클럭 EX 입력 MUX |
| MEM/WB 포워딩 | 전전 명령 결과를 현재 EX 입력으로 우회 | WB 기록 전 값을 EX로 패스 |
| BTB (Branch Target Buffer) | 분기 목적지 주소 캐싱 | IF에서 분기 여부·목표 주소 제공 |
| BHT (Branch History Table) | 분기 방향(T/NT) 예측 | 2비트 포화 카운터 배열 |

> 요약: 포워딩은 EX 결과를 우회하는 내부 데이터 버스이고, 분기 예측은 IF에 붙은 BTB·BHT 조회 유닛임.

---

## Ⅲ. 동작원리 및 흐름도

```text
[포워딩·분기 예측 통합 동작 흐름]
IF: PC 인출 -> BTB 검색(분기문·타겟) -> BHT 참조(2비트) -> Taken이면 타겟으로 즉시 IF
ID: 소스 레지스터 의존성 확인 -> 포워딩 가능/Load-Use 판별
EX: ALU 결과 즉시 포워딩 경로로 송출 / 분기 조건 실제 확정
WB 이후: 예측 오류면 Flush + BHT 상태 갱신
```

- 1단계: IF에서 BTB로 분기 여부·목적지를, BHT 2비트 카운터로 방향을 조회해 예측 주소로 투기적 인출을 시작함 (주체: 인출·예측 유닛)
- 2단계: ID에서 소스 레지스터 의존성을 확인해 EX/MEM·MEM/WB 포워딩 경로를 선택하거나, Load-Use면 1사이클 Stall을 발행함 (주체: 해저드 감지 로직)
- 3단계: EX에서 ALU 결과를 레지스터 기록 전에 포워딩 버스로 즉시 송출하고, 분기 조건을 실제로 확정함 (주체: 실행 유닛)
- 4단계: 예측이 맞으면 손실 0클럭으로 진행하고, 틀리면 투기 명령을 전부 Flush한 뒤 정상 주소로 재인출하며 BHT 카운터를 갱신함 (주체: 파이프라인 제어부)

> 요약: 포워딩은 EX에서 결과를 즉시 되먹여 스톨을 없애고, 분기 예측은 IF에서 미리 인출해 버블을 은닉하되 실패 시 Flush로 복구함.

---

## Ⅳ. 특징

- 포워딩은 RAW 데이터 해저드를 EX 시점에 우회해 2사이클 스톨을 0사이클로 없앰
- Load-Use 해저드는 데이터가 MEM에서야 나와 포워딩으로도 최소 1사이클 스톨이 잔존, 컴파일러 재배치로 흡수함
- 분기 예측은 실패 페널티가 파이프라인 깊이에 비례(10~20사이클)해, 예측 정확도가 코어 성능을 직접 좌우함
- 구현 난이도는 포워딩이 낮고(ALU 입력 MUX 추가) 분기 예측이 높음(다단 카운터·글로벌 이력 테이블)
- 투기적 실행은 성능 이득의 대가로 캐시 부채널(Spectre) 공격면을 만들어, 보안 격리 설계가 병행 필요함

> 요약: 포워딩은 저비용의 확실한 스톨 제거재이고, 분기 예측은 고비용이나 깊은 파이프라인 성능을 결정하는 핵심 회로임.

## Ⅴ. 심화 비교 및 적용 판단

| 구분 | 정적 분기 예측 | 동적 분기 예측 |
|:---|:---|:---|
| 판단 주체·시점 | 컴파일러가 컴파일 타임에 규칙으로 결정 | 하드웨어가 런타임 실행 이력으로 실시간 판단 |
| 대표 방식 | 후방 분기는 Taken 등 고정 규칙, 지연 분기 | 1비트·2비트 카운터, 글로벌 이력, TAGE·Perceptron |
| 적중률 | 60~80% (패턴 무관 고정) | 2비트 85~92%, 다단 TAGE 97~99% |
| 하드웨어 비용 | 없음 (H/W 추가 불필요) | BHT·BTB·이력 레지스터 등 면적 증가 |
| 적합 조건 | 저전력 임베디드, 얕은 파이프라인 | 고성능 서버·깊은 슈퍼파이프라인 |

> 요약: 얕은 파이프라인·저전력이면 정적 예측으로 충분하나, 실패 페널티가 큰 깊은 파이프라인은 동적 예측이 필수임.

리스크·대응(불릿):
- 리스크 — 분기 예측 실패 Flush(깊은 파이프라인에서 수십 사이클 손실) — 대응: TAGE·Perceptron 다단 예측기로 적중률 99% 확보 (지표: branch miss rate)
- 리스크 — Load-Use 잔여 스톨(포워딩으로도 1사이클 잔존) — 대응: 컴파일러 명령어 재배치로 무관 명령 삽입 (지표: 전체 사이클 대비 Load-Use 스톨 5% 이하)
- 리스크 — 투기 실행 부채널 유출(Spectre) — 대응: 예측 실패 시 캐시 상태 롤백, IBRS·Retpoline 격리 (지표: 부채널 취약 분기 커버리지)

지표·목표(불릿):
- 지표 — 분기 예측 적중률 — 목표: BHT+글로벌 이력으로 95% 이상 — 측정: SPECint 분기 트레이스
- 지표 — 브랜치 미스 페널티 — 목표: 파이프라인 깊이 이내 Flush 통제 — 측정: 성능 모니터링 카운터(PMU)
- 지표 — Load-Use 스톨 발생률 — 목표: 전체 사이클 5% 이하 — 측정: 재배치 코드 프로파일링

## Ⅵ. 실무 적용 및 결론

**적용 방안 3개:**
1. 컴파일러 명령어 스케줄링 연계: Load 직후 해당 레지스터를 쓰는 코드 사이에 무관한 명령어를 끼워(Instruction Scheduling) Load-Use 잔여 1사이클 방어
2. 다단 동적 분기 예측기 채택: 고성능 서버(ARM Neoverse, AMD EPYC) 설계 시 2비트 카운터를 넘어 TAGE·Perceptron 기반 예측기로 적중률 99% 달성
3. 투기적 실행 보안 격리: Spectre 방어를 위해 예측 실패 시 캐시 상태 롤백 및 IBRS 보안 격리를 적용해 성능과 격리를 동시 설계

**결론 (2줄):**
- 기술사 판단: 얕은 저전력 코어면 정적 예측+포워딩으로 충분하나, 깊은 고성능 코어면 다단 동적 예측기와 OoO를 함께 도입해 Flush 페널티를 억제해야 함
- 향후 방향: 분기 예측 페널티를 넘기 위해 AI 기반 예측기가 도입되고 있으며, 최후 보루로 명령어 순서를 뒤집는 비순차 실행(OoO)이 병행 확산되고 있음
