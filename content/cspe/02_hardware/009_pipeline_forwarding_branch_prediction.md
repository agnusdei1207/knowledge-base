# 📖 【암기용】 개념 완전 이해
> 목적: 포워딩과 분기 예측을 처음 봐도 어떤 신호를 어디서 가로채고, 무엇을 근거로 다음 명령어를 추측하는지 이해하게 만든다. 시험 답안 양식이 아니라, 이해를 위한 친절한 설명이다.

## 한눈에
- **개요**: 데이터 해저드는 결과값을 미리 전달(포워딩)하고, 제어 해저드는 분기 결과를 미리 추측(분기 예측)해 파이프라인 정지를 줄이는 두 가지 핵심 해소 기법
- **왜 필요한가**: 포워딩이 없으면 RAW 의존 명령마다 스톨이 생기고, 분기 예측이 없으면 분기마다 다음 인출을 멈춰야 해 CPI(Cycles Per Instruction)가 급격히 나빠진다
- **핵심 직관**: 포워딩은 완성된 요리를 등록대(레지스터 파일)까지 가져가지 않고 옆 테이블로 바로 건네주는 것이고, 분기 예측은 주문서를 다 읽기 전에 지난 손님 패턴을 보고 다음 메뉴를 미리 준비하는 것이다

## 깊이 이해
- **배경·문제의식**: 5단 파이프라인(IF·ID·EX·MEM·WB)에서 레지스터 쓰기는 WB 단계에서 일어나지만, 다음 명령어가 ID 단계에서 그 값을 바로 읽으려 하면 값이 아직 레지스터 파일에 없다.
- **작동 원리 - 포워딩**: EX/EX 포워딩은 바로 앞 명령어의 ALU 결과를 EX/MEM 래치에서 다음 명령어의 EX 입력으로 직접 연결한다.
- **작동 원리 - 포워딩 한계**: Load 명령어 결과는 MEM 단계에서야 나오므로, 바로 다음 명령어가 그 값을 EX에서 써야 하면 포워딩만으로 해결이 안 되고 load-use stall 1사이클이 남는다.
- **작동 원리 - 분기 예측**: 분기 방향(taken/not-taken)은 실행 결과가 나오기 전에 추측해야 하며, 정적 예측은 컴파일 시점 규칙(예: 후방 분기는 taken)을, 동적 예측은 실행 중 관측한 이력을 사용한다.
- **작동 원리 - 2비트 포화 카운터**: BHT(Branch History Table)의 각 엔트리는 2비트 상태 기계로 strongly-not-taken, weakly-not-taken, weakly-taken, strongly-taken을 오가며, 1비트 예측기 대비 반복 루프 종료 시 오예측을 1회로 줄인다.
- **작동 원리 - BTB와 RAS**: BTB(Branch Target Buffer)는 분기 목적지 주소를 캐싱해 taken 예측 시 다음 인출 주소를 즉시 제공하고, RAS(Return Address Stack)는 함수 호출 주소를 스택으로 쌓아 `ret` 명령의 목적지를 별도로 예측한다.
- **비유**: 포워딩은 요리사가 완성 접시를 창고에 넣지 않고 바로 옆 요리사에게 건네는 것이고, 분기 예측은 지난 열 번의 주문 패턴을 보고 다음 손님이 뭘 시킬지 미리 조리를 시작하는 것이다.
- **구체 예시**: `ADD R1,R2,R3` 다음 `SUB R4,R1,R5`는 EX/EX 포워딩으로 스톨 0사이클이지만, `LW R1,0(R2)` 다음 `SUB R4,R1,R5`는 MEM/EX 포워딩을 써도 1사이클 load-use stall이 남는다.
- **흔한 오해·주의점**: 포워딩은 스톨을 완전히 없애는 만능 기법이 아니며, load-use처럼 데이터가 물리적으로 아직 생성되지 않은 시점에는 스톨이 불가피하다.
- **흔한 오해·주의점**: 분기 예측 적중률이 높다고 해도 오예측 1회당 페널티는 파이프라인 깊이에 비례해 커지므로, 깊은 파이프라인일수록 예측기 정교화가 더 중요해진다.

> 1. **본질**: 포워딩은 데이터 해저드를, 분기 예측은 제어 해저드를 각각 겨냥한 파이프라인 정지 최소화 기법이다.
> 2. **가치**: EX/EX·MEM/EX 포워딩은 RAW 스톨을 0사이클로, 2비트 포화 카운터와 BTB는 분기 관련 버블을 대폭 줄인다.

## Ⅰ. 개요 및 필요성
- 개요: 포워딩은 계산 결과를 레지스터 파일을 거치지 않고 다음 명령어에 직접 전달하는 회로, 분기 예측은 분기 결과 확정 전에 다음 인출 주소를 추측하는 기법
- 배경: 5단 파이프라인은 WB 단계에서만 레지스터에 값을 쓰므로 후속 명령어가 그 전에 값을 필요로 하면 데이터 해저드가, 분기 명령은 EX 단계 이후에야 방향이 확정되므로 제어 해저드가 발생
- 필요성: 두 해저드를 방치하면 RAW 의존 명령마다 최대 3사이클, 분기마다 파이프라인 깊이만큼 스톨이 누적되어 실제 CPI가 1을 크게 초과


## Ⅱ. 구조 및 구성요소
```text
ID/EX Register -> Forwarding Unit -> EX Input Mux
  / EX/MEM Latch -> EX/EX Forwarding
  / MEM/WB Latch -> MEM/EX Forwarding
IF Stage -> Branch Predictor
  / BHT: 2-bit Saturating Counter -> Taken/Not-Taken 예측
  / BTB: Branch Target Buffer -> 목적지 주소 예측
  / RAS: Return Address Stack -> 함수 복귀 주소 예측
```

| 구성요소 | 역할 | 산출물 |
|:---|:---|:---|
| Forwarding Unit | EX/MEM, MEM/WB 값을 감지해 EX 입력으로 우회 | RAW 스톨 제거 |
| BHT | 분기별 이력을 2비트 카운터로 저장 | taken/not-taken 예측 |
| BTB | 분기 PC와 목적지 주소 매핑 저장 | 다음 인출 주소 |
| RAS | 함수 호출 시 복귀 주소를 스택으로 관리 | ret 목적지 예측 |

> 요약: 포워딩은 EX 입력단 우회 경로, 분기 예측은 BHT·BTB·RAS 조합으로 방향과 목적지를 함께 추측하는 구조다.


## Ⅲ. 동작원리 및 흐름도
```text
명령어 IF -> ID -> EX -> MEM -> WB
  -> ID 단계에서 레지스터 의존 확인
  -> Forwarding Unit이 EX/MEM, MEM/WB 값 존재 확인
  -> 존재하면 EX 입력에 직접 연결, load-use면 1사이클 Stall
  -> 분기 명령은 IF에서 BTB/BHT 조회 -> 예측 방향으로 인출 계속
  -> EX 단계에서 실제 분기 결과 확정 -> 예측 일치 시 계속, 불일치 시 Flush 후 PC 재설정
```

| 단계 | 처리 내용 | 검증 기준 |
|:---:|:---|:---|
| 1 | ID에서 소스 레지스터와 앞선 명령어 목적 레지스터 비교 | 레지스터 번호 일치 여부 |
| 2 | EX/MEM, MEM/WB 값을 EX 입력 멀티플렉서로 우회 | forwarding path hit |
| 3 | IF 단계에서 BHT·BTB로 분기 방향·목적지 예측 | 예측 지연 1사이클 이내 |
| 4 | EX에서 실제 분기 결과 확정 후 예측과 비교 | branch misprediction rate |
| 5 | 불일치 시 잘못 인출된 명령어 Flush, PC 복구 | flush penalty cycle 수 |

> 요약: 데이터 해저드는 EX 입력 우회로, 제어 해저드는 예측-확정-불일치 시 Flush 흐름으로 각각 통제한다.


## Ⅳ. 특징
| 구분 | 포워딩 | 분기 예측 | 수치·표준 포인트 |
|:---|:---|:---|:---|
| 대상 해저드 | 데이터(RAW) | 제어(분기·점프) | RAW, taken/not-taken |
| 한계 | load-use는 1사이클 스톨 잔존 | 오예측 시 penalty 발생 | load-use stall 1 cycle |
| 핵심 부품 | EX/EX, MEM/EX 우회 경로 | BHT, BTB, RAS | 2-bit saturating counter |
| 페널티 규모 | 사이클 단위로 제한적 | 파이프라인 깊이에 비례 확대 | 얕은 파이프라인 2~4cycle, 깊은 파이프라인 15cycle 이상(예시) |

> 요약: 포워딩은 스톨을 최소 1사이클로 줄이지만, 분기 예측은 실패 시 파이프라인 깊이만큼 페널티가 커진다.


## Ⅴ. 심화 비교 및 적용 판단
| 비교 축 | 정적 분기 예측 | 동적 분기 예측 | 선택 기준 |
|:---|:---|:---|:---|
| 구조 | 컴파일 시점 규칙(예: 후방분기 taken) | 실행 중 BHT/BTB 이력 갱신 | 반복 루프 비중이 높으면 동적 예측 우선 |
| 비용/성능 | 하드웨어 비용 거의 없음 | BHT·BTB 저장 공간 필요 | 예측 정확도 목표와 하드웨어 면적 트레이드오프 |
| 운영/위험 | 코드 패턴 변화에 취약 | 이력 오염 시 예측 저하 | 워크로드 분기 패턴 안정성으로 판단 |

> 요약: 분기 패턴이 반복적이면 동적 예측기가, 단순 정적 규칙으로 충분한 경량 코어는 정적 예측이 유리하다.

| 리스크 | 원인 | 대응 방안 | 확인 지표 |
|:---|:---|:---|:---|
| load-use stall 누적 | Load 결과가 MEM 단계 이후 확정 | 컴파일러 명령어 재배치로 Load와 사용 명령어 간격 확보 | load-use stall per kilo-instruction |
| 분기 오예측 페널티 | 이력 부족, 분기 패턴 변화 | 2비트 이상 포화 카운터, BTB 용량 확대 | branch misprediction rate |
| 함수 복귀 오예측 | 단순 BTB만으로 재귀·콜백 목적지 추적 실패 | RAS 도입으로 복귀 주소 별도 관리 | return misprediction rate |

> 요약: 데이터 해저드 리스크는 명령어 배치로, 제어 해저드 리스크는 예측기 정교화와 RAS 분리로 통제한다.

| 점검 항목 | 목표 기준 | 측정 방법 |
|:---|:---|:---|
| 포워딩 커버리지 | RAW 의존 조합 100% 우회 경로 검증 | RTL 시뮬레이션, assertion |
| 분기 예측 적중률 | 워크로드별 목표 적중률 설정 후 실측 비교 | 성능 카운터, 트레이스 분석 |
| CPI | 목표 CPI 대비 실측 CPI 편차 확인 | cycle simulator |

> 요약: 도입 효과는 포워딩 커버리지, 분기 예측 적중률, 최종 CPI 세 지표로 검증한다.


## Ⅵ. 실무 적용 및 결론
**적용 방안 3개:**
1. EX/EX·MEM/EX 포워딩 경로를 우선 구현하고, load-use 조합만 컴파일러 명령어 재배치 또는 1사이클 스톨로 처리함
2. 반복 루프 비중이 높은 워크로드는 2비트 이상 포화 카운터 기반 BHT와 BTB를 함께 적용해 분기 방향·목적지를 동시에 예측함
3. 재귀·콜백 호출이 많은 코드 경로는 RAS를 별도로 두어 `ret` 목적지 예측 실패를 줄임

**결론 (2줄):**
- 기술사 판단: 데이터 해저드는 포워딩으로 대부분 흡수하되 load-use는 스케줄링으로 보완하고, 제어 해저드는 파이프라인 깊이에 맞춰 예측기 정교도를 조정함
- 향후 방향: 파이프라인이 깊어질수록 예측 실패 비용이 커지므로 TAGE 계열 등 다단 이력 기반 예측기와 OoO 실행을 함께 검토해야 함
