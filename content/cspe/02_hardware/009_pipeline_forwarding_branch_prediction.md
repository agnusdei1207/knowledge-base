# 📖 【암기용】 개념 완전 이해

> 목적: 데이터 포워딩과 분기 예측이 파이프라인 해저드(008)로 인한 스톨(Stall)을 어떻게 제로에 가깝게 만드는지, 그 안의 모든 용어(EX/MEM 포워딩, BTB, BHT, 2비트 카운터)까지 완벽히 이해하게 만든다.

## 한눈에
- **개요**: **파이프라인 해저드(008)** 중 데이터 해저드를 해소하는 "새치기" 기법인 **포워딩**과, 제어 해저드를 해소하는 "미래 예측" 기법인 **분기 예측**을 묶은 하드웨어 보상 회로다.
- **왜 필요한가**: 5단 파이프라인은 앞 명령 결과를 뒤 명령이 바로 써야 하는 의존성 문제(RAW)와, 분기문 다음에 뭘 가져올지 모르는 문제 때문에 시도 때도 없이 멈춘다(Stall). 멈추면 CPI가 1.0에서 멀어지고 성능이 수직 낙하하므로, 이를 막는 전용 하드웨어가 필요하다.
- **핵심 직관**: 포워딩은 요리가 접시에 담기길(WB) 기다리지 않고 프라이팬에서 갓 나온 고기(EX 결과)를 바로 덜어 쓰는 것이고, 분기 예측은 손님이 메뉴를 고민하는 동안 늘 먹던 메뉴를 미리 요리하기 시작하는 눈치 게임이다.

## 핵심 용어 정리 (내부에 등장하는 것들)

| 용어 | 의미 | 비유 |
|:---|:---|:---|
| 포워딩(Forwarding/Bypass) | WB를 기다리지 않고 EX 결과를 바로 다음 명령의 입력으로 넘기는 회로 — 데이터 해저드(RAW) 전담 | 완성 전 반찬을 옆자리에 바로 건넴 |
| EX/MEM 포워딩 | 직전 명령의 ALU 결과를 현재 명령의 EX 입력으로 즉시 전달 | 방금 구운 고기를 바로 옆에 건넴 |
| MEM/WB 포워딩 | 두 명령 전의 결과(이미 MEM을 지난 값)를 현재 명령의 EX 입력으로 전달 | 조금 전에 만든 반찬을 다시 꺼내 줌 |
| Load-Use 해저드 | Load 직후 그 값을 바로 쓰는 경우 — 데이터가 MEM 단계에서야 나와 포워딩으로도 완전히 없앨 수 없음 | 냉장고 문을 여는 동안은 재료를 못 씀 |
| 분기 예측(Branch Prediction) | 분기 결과가 확정되기 전에 미리 추측해 다음 명령어를 인출하는 기법 — 제어 해저드 전담 | 주문 전에 늘 시키던 메뉴부터 조리 시작 |
| 투기적 실행(Speculative Execution) | 예측을 믿고 확정 전에 미리 명령어를 실행하는 것 | 우산을 미리 챙겨 나감 |
| BTB (Branch Target Buffer) | IF 단계에서 "이 명령어가 분기문인지"와 "목적지 주소가 어디인지"를 캐싱해두는 버퍼 | 자주 가는 목적지 주소록 |
| BHT (Branch History Table) | 분기의 과거 결과(Taken/Not Taken)를 저장해 다음 결과를 예측하는 테이블 | 단골손님의 주문 이력 노트 |
| 2비트 포화 카운터 | 00(강한 Not-Taken)~11(강한 Taken) 4단계로 최근 분기 성향을 누적 기록하는 예측기 | 한 번 틀려도 성향을 바로 안 바꾸는 신중한 판단 |
| 정적/동적 예측 | 정적=컴파일러가 규칙(예: 후방 분기는 Taken)으로 미리 정함, 동적=런타임 이력으로 하드웨어가 실시간 판단 | 정적=고정 매뉴얼, 동적=경험으로 학습 |
| Flush (플러시) | 예측이 틀렸을 때 이미 인출·실행 중이던 명령어를 통째로 버리는 것 | 잘못 만든 요리를 폐기 |

## 깊이 이해

### 포워딩 — 데이터 해저드를 수치로 없애기
- `ADD R1,R2,R3` 직후 `SUB R4,R1,R5`가 오면 SUB는 R1을 즉시 필요로 한다. 원칙대로면 ADD가 WB(5단계)를 마칠 때까지 SUB가 EX(3단계)를 시작하지 못해 **2클럭을 Stall**한다.
- **EX/MEM 포워딩**: ADD의 EX 연산이 끝나는 즉시(3단계 직후), 그 결과값을 레지스터 파일을 거치지 않고 바로 다음 클럭의 SUB EX 입력선으로 꽂아 넣는다. 이러면 Stall이 2클럭에서 **0클럭**으로 사라진다.
- **MEM/WB 포워딩**: 두 명령어 떨어진 의존성(예: ADD 다음다음 명령이 R1을 씀)은 ADD가 MEM 단계를 지난 시점의 값을 포워딩해 처리한다.
- **한계 — Load-Use**: `LOAD R1,[addr]` 직후 `ADD R2,R1,R3`처럼 Load 값을 바로 쓰는 경우는 다르다. Load 결과는 MEM 단계가 끝나야 나오는데, 다음 명령의 EX는 그보다 먼저 시작돼야 하므로 포워딩을 아무리 잘 설계해도 **최소 1사이클 Stall**은 피할 수 없다. 컴파일러가 Load와 사용 사이에 무관한 명령어를 끼워 넣는 명령어 재배치로 이 잔여 1사이클을 흡수한다.

### 분기 예측 — BTB와 BHT의 역할 분담
- `if (a > b)` 같은 조건 분기는 EX 단계에서야 조건이 확정되므로, 예측이 없다면 IF는 그때까지 다음 명령어를 가져올 수 없어 2~3클럭을 그냥 날린다.
- **BTB**는 "이 주소의 명령어가 분기문인지, 분기라면 목적지가 어디인지"를 캐시해 IF 단계에서 바로 알려준다. **BHT**는 "이 분기가 최근에 Taken이었는지 Not-Taken이었는지"의 이력을 2비트 포화 카운터로 저장해 다음 결과를 추측한다.
- CPU는 BTB로 목적지를, BHT로 방향을 동시에 예측해 그 주소로 즉시 투기적 실행을 시작한다. 예측이 맞으면 손실이 0클럭이고, 틀리면 그동안 진행된 명령어를 전부 Flush하고 정상 주소부터 다시 시작해야 한다 — 이 페널티는 파이프라인 깊이에 비례해 보통 10~20클럭에 이른다.

### 2비트 포화 카운터를 수치로 이해하기
- 상태는 00(강한 Not-Taken) → 01(약한 Not-Taken) → 10(약한 Taken) → 11(강한 Taken) 4단계다. 분기가 실제로 일어나면(Taken) 카운터를 1 증가, 안 일어나면 1 감소시키되 0과 3을 벗어나지 않는다.
- 1비트 예측기(단순 기억)와 달리 2비트는 "가끔 한 번 튀는 예외"에 바로 흔들리지 않는다. 예를 들어 `for(i=0;i<100;i++)` 반복문은 99번 Taken, 마지막 1번만 Not-Taken이다. 1비트라면 마지막에 딱 한 번 틀리고 다음 루프 진입 시에도 그 여파로 또 틀리지만, 2비트는 카운터가 11에서 10으로 한 칸만 내려가므로 다음 루프의 첫 반복도 여전히 Taken으로 예측해 적중한다. 이런 반복문 패턴에서 2비트 동적 예측기는 98% 이상의 적중률을 낸다.

### 비유
- 포워딩: 직원이 월급(WB)을 은행에 넣었다가 다시 찾는 대신, 현찰(ALU 출력)을 손에 쥔 순간 바로 물건을 사는 것과 같다.
- 분기 예측: 기상청이 강수 확률을 보고 우산을 미리 챙기는 것과 같다. 맞으면 안 젖지만(0클럭 손해), 틀리면 짐만 무겁다(Flush 페널티).

### 흔한 오해
- "포워딩이 모든 데이터 해저드를 0사이클로 없앤다"는 틀렸다. Load-Use 해저드는 최소 1사이클이 남는다.
- "분기 예측은 언제나 이득이다"도 정확하지 않다. 예측이 틀리면 Flush로 수십 클럭을 손해 보므로, 파이프라인이 깊을수록(슈퍼파이프라인) 예측 정확도가 코어 전체 성능을 좌우한다.

## 연결 개념
- 파이프라인 해저드(008) — 포워딩·분기 예측이 각각 해소하는 데이터·제어 해저드의 근본 원인
- 투기적 실행(Speculative Execution) — 분기 예측을 믿고 미리 명령어를 실행하는 기술, 보안 취약점(Meltdown/Spectre)의 원인
- 비순차 실행(Out of Order) — 포워딩·분기 예측으로도 못 푸는 의존성을 명령어 순서를 섞어 해결하는 기법


# 📝 【답안용】 시험 답안 템플릿

> 목적: 시험장에서 25분에 그대로 쓰는 답안 양식. 

## 핵심 인사이트 (3줄 요약)

> 1. **본질**: 데이터 포워딩과 분기 예측은 파이프라인의 데이터 의존성(RAW)과 제어 불확실성을 해소하여 IPC(명령어 처리량) 저하를 방어하는 하드웨어 최적화 회로다.
> 2. **가치**: 포워딩은 EX 단계의 결과를 즉각 재사용하여 2사이클 스톨을 0사이클로 없애며, 분기 예측은 BHT/BTB를 통해 제어 해저드 플러시(Flush) 빈도를 5% 미만으로 통제한다.
> 3. **판단 포인트**: 단(Stage) 수가 깊은 현대 슈퍼파이프라인 구조일수록 분기 예측 실패 페널티(10~20 사이클)가 치명적이므로, 다단 동적 분기 예측기의 정교함이 코어 성능을 좌우한다.

## 출제 의도 및 답안 포인트
| 출제 의도 | 반드시 짚을 핵심 | 감점 회피 포인트 |
|:---|:---|:---|
| 파이프라인 해저드의 원인과 하드웨어적 해결 메커니즘 이해 | 데이터 해저드(RAW) -> 포워딩 경로 회로 (EX/MEM, MEM/WB), 제어 해저드 -> BTB, BHT 기반 동적 예측 | 포워딩으로 Load-Use 해저드까지 0사이클로 없앨 수 있다고 적는 오류 (Load는 최소 1사이클 필요) |

> 요약: 스톨(Stall)을 줄이는 포워딩의 데이터 경로 추가와, 버블(Bubble)을 줄이는 분기 예측의 캐시(BTB) 메커니즘을 구체적으로 대조 서술해야 한다.


## Ⅰ. 개요 및 필요성

- 정의: 파이프라인 처리 중 발생하는 데이터 해저드를 해결하는 **포워딩**과, 제어 해저드를 완화하는 **분기 예측** 메커니즘
- 배경: 명령어 간 의존성으로 인해 발생하는 멈춤 현상(Stall, Flush)이 깊은 파이프라인 구조에서 심각한 CPI 손실을 유발
- 필요성: 클럭 주파수를 낭비하지 않고 이상적 CPI인 1.0에 근접하기 위한 필수 하드웨어 보상 회로 요구


## Ⅱ. 데이터 해저드 극복: 포워딩 (Forwarding/Bypass)

```text
[데이터 포워딩 회로 개념도 (RAW 의존성 해결)]
명령 1: [ IF ] -> [ ID ] -> [ EX (결과생성) ] -> [ MEM ] -> [ WB ]
                               |               |
                               +--->(EX/MEM)---+---> [ EX ] (명령 2 재사용)
                               |
                               +--->(MEM/WB)-------> [ EX ] (명령 3 재사용)
```

| 포워딩 회로 | 대상 해저드 조건 | 적용 방법 (마이크로 오퍼레이션) |
|:---|:---|:---|
| EX/MEM 포워딩 | 직전 명령의 ALU 결과를 현재 명령의 ALU 입력으로 필요 시 | ALU 연산 완료 즉시 다음 클럭의 ALU 입력 MUX로 결과값 패스 |
| MEM/WB 포워딩 | 전전 명령의 결과를 현재 명령의 ALU 입력으로 필요 시 | 메모리 접근/WB 단계의 레지스터 기록 전 데이터를 ALU로 패스 |
| Load-Use 한계 | Load 직후 해당 데이터를 ALU 연산에 쓸 경우 | 데이터 인출은 MEM에서 끝나므로 포워딩을 써도 최소 1사이클 스톨 발생 |

> 요약: 포워딩은 WB 단계를 기다리지 않고 내부 데이터 버스(Bypass)를 열어 스톨(Stall)을 0사이클로 차단한다.


## Ⅲ. 제어 해저드 극복: 분기 예측 (Branch Prediction)

```text
[동적 분기 예측 동작 흐름도 (IF 단계)]
PC 인출 -> BTB 검색 (분기문 여부 및 타겟 주소 확인)
  -> BHT 참조 (2-Bit 예측기) -> [ Taken(분기) ] 판단 시 Target 주소로 IF 
  -> [ EX 단계 실제 결과 ] -> 예측 실패 시 Flush 및 BHT 상태 업데이트
```

| 구성요소 | 핵심 역할 | 상세 하위 요소 / 특징 |
|:---|:---|:---|
| BTB (Branch Target Buffer) | 분기 목적지 주소 캐싱 | IF 단계에서 명령어가 분기문인지 판별하고 목표 주소 제공 |
| BHT (Branch History Table) | 분기 여부(Taken/Not Taken) 예측 | 과거 실행 결과를 저장하는 포화 카운터(Saturating Counter) |
| 정적 예측 (Static) | 컴파일러 기반의 하드코딩 규칙 | 후방 분기는 루프로 판단해 무조건 Taken 처리 |
| 동적 예측 (Dynamic) | 런타임 과거 이력 기반 H/W 예측 | 1-bit, 2-bit 예측기, 글로벌 예측기, TAGE 예측기 |

> 요약: BTB로 "어디로 갈지"를 캐싱하고, BHT로 "갈지 말지"를 예측하여 IF 단계의 지연(제어 해저드)을 완전히 은닉한다.


## Ⅳ. 심화 비교 및 성능 지표 판단

| 구분 | 데이터 포워딩 (Data Hazard) | 동적 분기 예측 (Control Hazard) | 판단 포인트 |
|:---|:---|:---|:---|
| 지연 원인 | RAW 데이터 의존성 (의존 레지스터 대기) | 분기 조건 및 목적지 계산 지연 (PC 불확실) | 어떤 해저드를 방어하는가 |
| 적용 단계 | EX 단계 (ALU 입력 시점) | IF 단계 (다음 명령어 반입 시점) | 마이크로 아키텍처 개입 위치 |
| 실패 패널티 | 포워딩 불가 시 1~2사이클 지연(Stall) | 예측 실패 시 파이프라인 전체 비우기(Flush) | 깊은 파이프라인일수록 분기 패널티 치명적 |
| 구현 복잡도 | ALU 입력 MUX 추가 등 비교적 단순 | 다단 카운터, 글로벌 히스토리 테이블 등 고비용 회로 | 면적 대비 성능 한계 효용 |

> 요약: 데이터 포워딩은 1~2사이클의 확실한 보완재이나, 분기 예측 실패는 수십 사이클의 붕괴(Flush)를 초래하므로 최신 CPU 트랜지스터의 상당수가 분기 예측에 투자된다.

| 점검 항목 | 목표 기준 | 측정 방법 |
|:---|:---|:---|
| 분기 예측 정확도 | BHT + 글로벌 이력 조합으로 95% 이상 적중 | SPECint 벤치마크 분기 추적 |
| 브랜치 미스 패널티 | Flush 사이클(파이프라인 깊이) 통제 | 성능 모니터링 카운터(PMU) 분석 |
| Load-Use 스톨 발생률 | 전체 사이클의 5% 이하 (컴파일러 협력) | 명령어 재배치 코드 프로파일링 |

> 요약: 하드웨어 포워딩과 예측기로 95%의 해저드를 막고, 남은 한계(Load-Use)는 컴파일러 스케줄링으로 방어해야 한다.


## Ⅵ. 실무 적용 및 결론
**적용 방안 3개:**
1. 컴파일러 명령어 스케줄링 연계: Load 명령어 직후 곧바로 해당 레지스터를 사용하는 코드를 지연시키기 위해, 서로 무관한 명령어를 끼워 넣어(Instruction Scheduling) Load-Use 스톨 잔여 1사이클 방어
2. 다단 동적 분기 예측기 채택: 고성능 서버(ARM Neoverse, AMD EPYC) 프로세서 설계 시 2-Bit 카운터를 넘어 패턴 히스토리(TAGE, Perceptron) 기반의 인공신경망 예측기를 도입해 적중률 99% 달성
3. 투기적 실행 보안 격리: 분기 예측을 믿고 미리 메모리를 읽어두는 투기적 실행(Speculative Execution)이 유발하는 캐시 부채널 공격(Spectre) 방어를 위해, 예측 실패 시 캐시 상태 롤백(Rollback) 및 IBRS 보안 격리 적용

**결론 (2줄):**
- 기술사 판단: 파이프라인의 성능(IPC)은 클럭 속도가 아니라 "포워딩 회로의 정교함"과 "분기 예측 실패 빈도(Flush Penalty)"를 억제하는 아키텍처 역량에 달려있다.
- 향후 방향: 분기 예측의 패널티 리스크를 넘기 위해 AI 기반 분기 예측기가 도입되고 있으며, 최후의 보루로 명령어 순서를 뒤집는 비순차 실행(Out-of-Order Execution) 기법이 병행 확산되고 있다.
