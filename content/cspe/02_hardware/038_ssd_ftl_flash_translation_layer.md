# 📖 【암기용】 개념 완전 이해

> 목적: FTL이 LBA를 PBA로 바꿀 때 어떤 단위(Page/Block/Hybrid)로 매핑 테이블을 구성하는지, 그 선택이 DRAM 용량과 쓰기 성능을 어떻게 정반대로 흔드는지 수치로 이해하게 만든다.

## 한눈에
- **개요**: **FTL의 매핑(Mapping) 알고리즘**은 논리 주소(LBA)와 물리 주소(PBA)를 어떤 크기 단위로 짝짓느냐를 정하는 규칙으로, **Page Mapping·Block Mapping·Hybrid Mapping** 세 가지로 나뉘며 이 선택이 SSD의 DRAM 원가와 무작위 쓰기 성능을 동시에 결정한다.
- **왜 필요한가**: L2P 테이블은 매핑 단위가 작을수록(Page 단위) 정밀하지만 항목 수가 폭증해 DRAM을 많이 먹는다. 반대로 매핑 단위가 크면(Block 단위) 테이블은 작아지지만, 한 Block 안의 일부 Page만 바뀌어도 Block 전체를 다시 써야 하는 손해가 생긴다. 이 트레이드오프를 어떻게 배분하느냐가 매핑 알고리즘의 핵심 문제다.
- **핵심 직관**: 도서관에서 책 한 권(Page) 위치를 낱권까지 정확히 적어둔 목록(Page Mapping)은 찾기는 빠르지만 목록 자체가 두껍다. 반면 "이 책장 칸(Block)에는 대충 이 시리즈가 있다"고만 적어두면(Block Mapping) 목록은 얇지만, 책 한 권을 찾으려면 그 칸을 통째로 뒤져야 한다.

## 핵심 용어 정리 (내부에 등장하는 것들)

| 용어 | 의미 | 비유 |
|:---|:---|:---|
| Page Mapping | Page(예: 4KB) 단위로 LBA-PBA를 1:1 매핑 | 책 한 권 단위 목록 |
| Block Mapping | Block(Page 수백 개 묶음) 단위로만 매핑하고, Block 내부 오프셋은 고정 순서로 간주 | 책장 칸 단위 목록 |
| Hybrid Mapping | 대부분은 Block 단위로 매핑하되, 최근 쓰기가 몰리는 일부 Block만 Page 단위로 세밀하게 매핑 | 자주 찾는 서가만 낱권 목록, 나머지는 칸 목록 |
| Log Block | Hybrid 방식에서 새 쓰기를 임시로 받아 Page 단위로 정밀 관리하는 예비 Block | 임시 대출 데스크 |
| Data Block | 매핑이 확정되어 Block 단위로만 관리되는 일반 저장 Block | 서가에 꽂힌 책장 |
| Merge (병합) | Log Block에 쌓인 변경을 원래 Data Block에 합쳐 넣고 Log Block을 비우는 연산 | 임시 데스크 책을 서가에 다시 꽂기 |
| Associativity (1:1 / N:1) | Log Block 1개가 Data Block 몇 개와 연결되는지 나타내는 매핑 방식 구분 | 임시 데스크 1개가 서가 몇 칸을 담당하는지 |

## 깊이 이해

### 왜 매핑 알고리즘 선택이 문제였나 (배경)
- 1TB SSD를 4KB Page 단위로 전부 매핑하면 L2P 테이블은 매핑 항목 약 2억 4,400만 개 × 4바이트 ≈ 976MB, 반올림해 약 1GB가 된다(1TB ÷ 4KB ≈ 2.44억 개). 이 DRAM 비용은 서버용 SSD에는 감당할 만하지만, USB 메모리나 저가형 SD카드처럼 컨트롤러 원가를 극한까지 낮춰야 하는 기기에는 부담이다. 그래서 매핑 단위를 키워 테이블을 줄이는 대안들이 등장했다.

### Page Mapping을 수치로 이해
- 4KB Page 단위로 1TB를 전부 매핑하면 매핑 항목은 약 2억 4,400만 개, 항목당 4바이트면 테이블은 약 1GB다.
- 장점은 어떤 LBA든 낸드의 아무 빈 Page에나 바로 꽂을 수 있어 무작위 쓰기 성능이 최상이라는 것이다. 대신 DRAM 원가가 가장 비싸며, 서버·NVMe급 고성능 SSD의 표준 방식이다.

### Block Mapping을 수치로 이해
- Block 크기를 4MB(16KB Page × 256개)라고 하면, 1TB SSD의 Block 수는 1TB ÷ 4MB ≈ 262,144개다. 항목당 4바이트면 테이블은 약 1MB로, Page Mapping(약 1GB) 대비 약 1,000분의 1이다.
- 그러나 Block 안의 Page 하나만 바뀌어도 매핑 규칙상 Block 전체(256개 Page)를 다른 곳에 다시 써야 한다. 즉 4KB를 고치려다 4MB를 다시 쓰는 셈이라, 이 경우 쓰기 증폭(WAF)이 최대 1,024배(4MB÷4KB)까지 치솟을 수 있다. USB 메모리·저가 SD카드처럼 무작위 쓰기가 드문 기기에만 적합하다.

### Hybrid Mapping(Log Block 방식)을 수치로 이해
- 절충안은 Data Block은 Block 단위(테이블 작음)로 두고, 최근 쓰기가 몰리는 소수의 Block만 Log Block으로 지정해 Page 단위(정밀함)로 관리하는 것이다.
- 예: Log Block 1개가 Data Block 4개를 담당하는 N:1(4:1) 구성이라면, 사용자가 그 4개 Block 범위 안에서 반복 수정하는 동안은 Log Block에 Page 단위로 빠르게 기록하다가, Log Block이 다 차면 유효 Page만 골라 원래 Data Block과 합치는 **병합(Merge)**을 수행한다.
- Merge는 두 종류로 갈린다: 순서가 그대로 유지된 경우 옆에 있는 Page들을 그대로 이어 붙이는 **Switch Merge**(비용 거의 없음)와, 순서가 뒤섞여 유효 Page를 하나씩 골라 복사해야 하는 **Full Merge**(Block 전체를 재작성하는 것과 같은 큰 비용)다. 무작위 쓰기가 많을수록 Full Merge 빈도가 늘어 성능이 Block Mapping에 가깝게 떨어진다.

### 비유와 흔한 오해
- **비유**: Page Mapping은 모든 책의 정확한 서가 위치를 손가락으로 짚어주는 사서이고, Block Mapping은 "이 계열 책은 대충 3번 서가"라고만 알려주는 사서다. Hybrid는 자주 찾는 신간 코너만 낱권으로 정리해 두고 나머지는 계열별로만 정리하는 절충형 사서다.
- **오해**: "Hybrid Mapping이 최신 기술이라 항상 더 낫다"는 오답이다. Hybrid는 DRAM이 부족했던 과거 저가·중저가 SSD의 절충안이었을 뿐, DRAM 원가가 내려간 현재 고성능 SSD는 오히려 Full Merge 지연을 아예 피하려고 100% Page Mapping을 표준으로 쓴다.

## 연결 개념
- L2P 테이블 DRAM 크기 산정과 FTL의 3대 임무(매핑·GC·웨어 레벨링) — 038_ssd_controller_ftl

# 📝 【답안용】 시험 답안 템플릿

> 목적: 시험장에서 25분에 그대로 쓰는 답안 양식. 

## 핵심 인사이트 (3줄 요약)

> 1. **본질**: FTL(Flash Translation Layer)은 덮어쓰기가 불가능한(Erase-before-write) NAND 플래시의 하드웨어적 제약을 추상화하여, 호스트(OS)가 블록 디바이스(HDD)처럼 사용할 수 있게 해주는 컨트롤러 펌웨어 계층이다.
> 2. **가치**: 논리-물리 주소 매핑(L2P), 가비지 컬렉션(GC), 웨어 레벨링(WL) 등의 알고리즘을 백그라운드로 수행하여 SSD의 임의 쓰기(Random Write) 속도 보장과 플래시 셀의 수명을 극대화한다.
> 3. **판단 포인트**: FTL의 성능(맵핑 단위)에 따라 매핑 테이블이 차지하는 DRAM 용량과 쓰기 증폭(WAF) 수치가 결정되므로, 시스템 I/O 워크로드에 맞춘 맵핑 기법(Page/Block/Hybrid) 선정이 SSD 아키텍처의 핵심이다.

## 출제 의도 및 답안 포인트

| 출제 의도 | 반드시 짚을 핵심 | 감점 회피 포인트 |
|:---|:---|:---|
| 플래시 메모리의 물리적 한계(덮어쓰기 불가)와 FTL의 매핑(Mapping) 원리 이해 | Erase-before-write 제약, Out-of-place Update (우회 쓰기) | FTL을 호스트 OS에 설치되는 디바이스 드라이버로 착각하는 서술 금지 (SSD 컨트롤러 내장 펌웨어임) |
| FTL의 3대 핵심 알고리즘 메커니즘 파악 | 매핑(주소 변환), GC(찌꺼기 청소), WL(수명 평준화) | GC와 WL을 헷갈리거나 하나만 서술하는 오류 (목적이 다름) |

> 요약: 낸드 플래시의 가장 치명적인 제약 2가지(덮어쓰기 불가, P/E Cycle 수명)를 소프트웨어 로직(FTL)이 어떻게 '숨겨주는지(Abstraction)'를 논리적으로 서술해야 한다.

## Ⅰ. 개요 및 필요성

- 정의: 호스트 파일시스템과 NAND 플래시 메모리 사이에서 논리적 주소(LBA)를 물리적 주소(PBA)로 변환하고 낸드의 특성을 관리하는 SSD 컨트롤러 내부 펌웨어 계층
- 배경: 기존 OS 파일시스템(NTFS, ext4)은 덮어쓰기가 가능한 HDD(자기 디스크) 구조에 맞춰져 있어, 지우고 다시 써야 하는 NAND 플래시에 직접 데이터를 기록할 수 없음
- 필요성: OS 수정 없이 기존 HDD 인터페이스 호환성을 100% 유지하면서, NAND의 약점인 배드 블록 관리, 데이터 찌꺼기 청소, 특정 셀 수명 고갈 방지를 통제할 중간 매개체 필수

## Ⅱ. 구조 및 구성요소 (SSD 내부 논리 스택)

```text
[호스트(OS)와 SSD 간의 FTL 계층 구조 및 처리 프로세스]
+-------------------------------------------------+
| 호스트 OS / 파일 시스템 (NTFS, EXT4)            | <- LBA(논리주소)로 HDD 다루듯 명령
+=================================================+
| SSD 컨트롤러 內 FTL (Flash Translation Layer)   |
|  1) Address Mapping (L2P 변환 테이블 - DRAM 상주) |
|  2) Garbage Collection / Wear Leveling 구동       |
+=================================================+
| NAND Flash Array (물리적 셀)                    | <- PBA(물리주소)로 실제 데이터 입출력
+-------------------------------------------------+
```

| FTL 핵심 구성요소 | 핵심 역할 | 상세 하위 동작 및 효과 |
|:---|:---|:---|
| Address Mapping | 주소 변환 (추상화) | 호스트의 LBA를 받아 NAND의 빈 공간(PBA)에 우회 쓰기(Out-of-place update)를 지시 |
| Garbage Collection (GC) | 찌꺼기 공간 회수 | 유효(Valid) 데이터만 다른 새 블록으로 복사 후, 구 블록을 전체 소거(Erase)하여 빈방 확보 |
| Wear Leveling (WL) | 특정 셀 단명 방지 | 수명(P/E Cycle)이 남은 블록을 추적하여 쓰기 횟수를 전체 블록에 균등 분배(평준화) |
| Bad Block Mgmt (BBM) | 불량 셀 격리 및 관리 | 수명이 다해 죽어버린 블록을 맵핑 테이블에서 영구 제외하여 데이터 유실 방지 |

> 요약: FTL은 속도를 위한 매핑, 용량 확보를 위한 GC, 생명 연장을 위한 WL이 삼위일체로 맞물려 돌아가는 극한의 임베디드 스케줄러다.

## Ⅲ. 동작원리 및 L2P(Logical-to-Physical) 맵핑 흐름도

낸드는 '덮어쓰기'가 불가능하므로, FTL은 기존 데이터를 무효화(Invalid)하고 새로운 곳에 쓰는 사기극(우회 쓰기)을 펼친다.

```text
[FTL의 우회 쓰기(Out-of-place Update) 마이크로 흐름]
1. OS 요청: "논리주소(LBA) 1번에 'A'를 'B'로 덮어써라"
2. FTL 인지: 물리주소(PBA) 100번에 있는 'A' 위에는 덮어쓸 수 없음 (물리적 한계)
3. FTL 기록: 빈 공간인 물리주소 [ PBA 200번 ]에 데이터 'B'를 새로 기록
4. 테이블 갱신: LBA 1번 -> PBA 200번으로 L2P(주소록) 맵핑 정보 변경
5. 구(Old) 처리: 기존 물리주소 100번의 데이터 'A'는 '무효(Invalid) 상태'로 라벨링 (추후 GC 대상)
```

| 쓰기 단계 | 동작 특성 | 폰 노이만 병목(HDD)과의 차이 |
|:---:|:---|:---|
| 탐색 (Search) | L2P 맵핑 테이블(DRAM 내장)에서 즉시 조회 | 디스크 헤드가 물리적으로 이동할 필요가 없어 탐색 지연 시간 0 |
| 쓰기 (Write) | 무조건 빈 페이지(Page)를 찾아서 순차 할당 | 덮어쓰기 대기 시간 제로. SSD가 HDD보다 임의 쓰기(Random Write)가 압도적으로 빠른 이유 |
| 회수 (Erase) | 무효화된 찌꺼기들을 백그라운드 단위(Block)로 삭제 | HDD는 찌꺼기 개념이 없음. SSD 컨트롤러의 성능을 깎아 먹는 최대 오버헤드 |

> 요약: 윈도우(OS)는 같은 곳에 덮어썼다고 믿지만, 실제 플래시 칩 내에서는 데이터가 빈 공간을 찾아 이리저리 메뚜기처럼 뛰어다닌다.

## Ⅳ. 심화 비교: 맵핑 방식별 트레이드오프

FTL이 맵핑 수첩(테이블)을 작성할 때, 어떤 크기 단위로 기록하느냐에 따라 SSD 성능과 제조 원가(DRAM 캐시 용량)가 갈린다.

| 비교 축 | Page Mapping (페이지 맵핑) | Block Mapping (블록 맵핑) | Hybrid Mapping (하이브리드) |
|:---|:---|:---|:---|
| 매핑 단위 | 가장 작은 Page 단위 매핑 | 거대한 Block 단위 매핑 | 데이터 특성에 따라 혼용 |
| 테이블 크기 (DRAM)| **가장 크고 비쌈** (수많은 주소 기록) | 가장 작고 저렴 (요약 기록) | 적절한 타협점 |
| 무작위 쓰기 성능 | **최상** (어디든 빈 페이지에 기록) | 최악 (블록 전체 복사 오버헤드 폭발)| 양호 (주로 임시 블록만 페이지 매핑) |
| 적용 기기 | 엔터프라이즈 서버 SSD, 고가 NVMe | USB 메모리, 저가 SD카드 | 과거 중저가 SSD |
| 시스템 선택 기준 | DRAM 캐시를 풍부하게 달 수 있는가? | 초저가 컨트롤러, DRAM-less 환경 | 펌웨어(FTL) 최적화 역량 |

> 요약: 현대 고성능 SSD는 무작위 쓰기(Random Write) 성능을 위해 압도적인 양의 L2P 테이블(DRAM 캐시)을 때려 넣는 '100% Page Mapping' 방식을 표준으로 삼는다.

| 리스크 | 발생 원인 | 아키텍처 및 컨트롤러 대응 방안 | 극복 원리 및 효과 |
|:---|:---|:---|:---|
| 쓰기 증폭 (WAF) | 호스트는 10MB를 썼는데, FTL이 GC(복사/지우기) 하느라 낸드에는 실제 30MB가 쓰이는 수명 단축 현상 | **TRIM 명령어 / Over-Provisioning** | OS가 "이 파일 지웠어"라고 TRIM으로 FTL에 힌트를 주어 무의미한 GC 복사 작업을 차단 / 숨겨둔 여유 공간(OP)으로 GC 효율 극대화 |
| 콜드 데이터 고착 | OS 영역처럼 1번 깔면 수정 안 되는 데이터(Cold)가 새 블록을 독차지하고 방을 안 빼줌 | **정적 웨어 레벨링 (Static Wear Leveling)** | 단순히 자주 쓰는 방만 돌려 막는 게 아니라, 가만히 있는 콜드 데이터 방의 짐을 강제로 빼서 새 방으로 이사시키고, 헌 방을 확보해 수명 평준화 |
| DRAM 캐시 휘발 | 정전 시 컨트롤러 DRAM에 있던 맵핑(L2P) 테이블이 증발하여 SSD 주소를 영구 상실 | PLP (Power Loss Protection) 커패시터 장착 | 칩에 대용량 콘덴서를 달아, 정전 시 남은 전력으로 DRAM 맵핑 테이블을 낸드 안전 구역에 강제 백업(Flush) 완료 후 셧다운 |

> 요약: 컨트롤러가 아무리 똑똑해도 SSD 내부에 빈 공간이 꽉 차면 GC 오버헤드로 인해 속도가 HDD급으로 추락하므로(WAF 폭발), TRIM과 오버프로비저닝이 SSD 생명의 방패막이다.

## Ⅵ. 실무 적용 및 결론

**적용 방안 3개:**
1. 데이터베이스(DBMS) 서버 Over-Provisioning 튜닝: OLTP처럼 작은 데이터를 미친 듯이 썼다 지우는 무작위 쓰기 서버 환경에서는 팩토리 디폴트 OP(7%)를 무시하고, 강제로 SSD 전체 파티션의 20~30%를 미할당 영역(OP)으로 떼어내어 FTL의 GC 부하를 획기적으로 낮춰 지연(Latency) 스파이크 차단
2. ZNS (Zoned Namespace) 아키텍처 도입: 메타(Meta), 구글 등 대규모 스토리지 노드에서는 멍청한 FTL을 바이패스(Bypass)하기 위해, 낸드를 큰 존(Zone)으로 나누고 호스트(OS) 파일시스템이 직접 낸드의 순차 쓰기 특성에 맞춰 구역별로 기록하는 ZNS NVMe 드라이브를 도입해 WAF를 1에 가깝게 수렴시킴
3. DRAM-less 환경 HMB (Host Memory Buffer) 활성화: 모바일이나 엣지 기기용 저가형 SSD 채택 시, 컨트롤러에 맵핑(L2P)용 DRAM이 없어 성능이 반토막 나는 현상을 막기 위해 호스트 PC의 메인 램(RAM) 64MB 정도를 PCIe 버스를 통해 FTL 테이블용으로 끌어다 쓰는 NVMe HMB 기술 적용

**결론 (2줄):**
- 기술사 판단: SSD 컨트롤러와 FTL은 하드웨어 결함(덮어쓰기 불가, 수명 제약)을 소프트웨어적 매핑과 스케줄링으로 덮어 완벽한 스토리지로 둔갑시킨 임베디드 컴퓨팅의 걸작이다.
- 향후 방향: 기존 FTL이 OS와 디바이스 간 블라인드(Black-box) 통신을 고수했다면, 차세대 스토리지(ZNS, CXL Memory)에서는 호스트(OS)와 컨트롤러가 정보를 실시간으로 교환하여 오버헤드를 원천 제거하는 방향으로 진화할 것이다.
