# 012. 비순서 실행·레지스터 리네이밍 (Out-of-Order Execution Register Renaming) [출제:136회]

## 미리 알고가기

- **비순서 실행 (Out-of-Order, OoO)**: 데이터 의존성이 없는 명령어를 프로그램에 적힌 순서와 상관없이 준비되는 대로 먼저 실행하는 기술임
- **레지스터 리네이밍 (Register Renaming)**: 한정된 논리 레지스터 이름을 다수의 물리 레지스터로 매핑하여 '가짜 의존성'을 제거하는 기술임
- **ILP (Instruction Level Parallelism)**: 명령어 수준에서 동시에 실행 가능한 독립적 연산의 정도를 의미함

## Ⅰ. 개요

- **정의/개념**: 비순서 실행은 실행 유닛의 유휴 시간을 최소화하기 위해 연산 순서를 동적으로 변경하는 기술이며, 레지스터 리네이밍은 이를 가능하게 하기 위해 데이터 충돌(WAR, WAW)을 하드웨어적으로 해결하는 핵심 메커니즘임
- **배경/필요성**: 순차 실행(In-order) 방식은 앞선 명령어가 메모리 지연(Cache Miss) 등으로 멈추면 뒤에 있는 독립적인 명령어들까지 모두 멈추게 됨. 이를 극복하여 CPU의 처리량(Throughput)을 극대화하기 위해 도입됨

## Ⅱ. 특징 및 비교

비순서 실행은 '가짜 의존성'을 제거하고 '진짜 의존성'만 지키며 실행 순서를 재배치함.

| 비교 항목 | 순차 실행 (In-order) | 비순서 실행 (Out-of-Order) |
|:---|:---|:---|
| **실행 순서** | 프로그램 코드 순서 고수 | **데이터 준비 순서** (순서 변경) |
| **의존성 처리** | 해저드 발생 시 파이프라인 정지 | **리네이밍**으로 가짜 의존성 해결 |
| **자원 활용도** | 낮음 (앞 명령 대기 시 유휴) | **높음** (가능한 연산 먼저 수행) |
| **회로 복잡도** | 단순함 | **매우 복잡함** (스케줄러, ROB 필요) |
| **주요 장점** | 저전력, 예측 가능한 성능 | **단일 스레드 성능 극대화** |

> 요약: 순차 실행은 '질서'를 중시하고, 비순서 실행은 '실질적 효율'을 중시함.

## Ⅲ. 구성요소/구조

비순서 실행은 인출-해독 단계 이후 '명령어 윈도우' 내에서 동적으로 스케줄링됨.

- **구성요소**:
  - **Register Alias Table (RAT)**: 논리 레지스터(EAX 등)를 물리 레지스터(P1, P2 등)로 매핑하는 표
  - **Reservation Station (RS)**: 연산에 필요한 데이터가 도착할 때까지 명령어를 대기시키는 장소
  - **Reorder Buffer (ROB)**: 비순서로 끝난 결과를 다시 프로그램 순서대로 정렬하여 반영(Commit)
  - **Physical Register File (PRF)**: 실제 연산 결과값이 저장되는 방대한 레지스터 집합

- **실행 구조도 (ASCII)**:

```text
[In-order Front-end]      [Out-of-Order Execution]     [In-order Commit]
+---------+    +----------+    +-------------+    +----------+
| Fetch   |--->| Rename   |--->| Issue Queue |--->| Execute  |
+---------+    |(RAT/PRF) |    | (RS)        |    |(ALU/FPU) |
               +----------+    +-------------+    +----+-----+
                                     ^                 |
                                     |       +---------v---------+
                                     +-------| Reorder Buffer    |
                                             | (ROB)             |
                                             +---------+---------+
                                                       |
                                                 [ Final Commit ]
```

1. **Rename** 단계에서 `WAR`, `WAW` 해저드를 물리 레지스터 할당으로 원천 봉쇄함
2. **Issue Queue**에서 데이터가 준비된 순서대로 연산기에 투입함 (비순서 실행)
3. **ROB**는 실행이 끝난 결과를 담아두었다가, 원래 순서대로 레지스터에 최종 기록함 (순서 확정)

## Ⅳ. 문제점 및 개선방안

1. **가짜 의존성(WAR, WAW)의 영향**: 레지스터 이름이 부족하여 생기는 의존성 때문에 병렬성이 제한됨
   - **개선방안**: **레지스터 리네이밍**을 통해 충분히 많은 물리 레지스터를 제공하여 논리적 이름 충돌을 제거함 (확인: 물리 레지스터 활용률)

2. **복잡한 정렬 로직 (ROB/RS)**: 수백 개의 명령어를 감시하고 재정렬하는 로직은 전력 소모가 매우 크고 칩 면적을 많이 차지함
   - **개선방안**: 명령어 윈도우 크기를 워크로드에 맞춰 최적화하고, 사용하지 않는 유닛을 차단하는 전력 관리 기술을 병행함 (확인: 단위 면적당 성능 향상분)

3. **정확한 예외 처리(Precise Exception) 곤란**: 비순서로 실행하다가 중간에 예외가 발생하면 시스템 상태를 복구하기 어려움
   - **개선방안**: **ROB(재정렬 버퍼)**를 통해 결과 반영(Commit)만은 반드시 순차적으로 수행하여 예외 발생 시 이전 상태로 안전하게 롤백함 (확인: 예외 처리 복구 시간)

## Ⅴ. 실무 적용 사례

| 적용 영역 | 적용 방식 | 확인 지표 |
|:---|:---|:---|
| 고성능 서버 (Xeon/EPYC) | 수백 단계의 명령어 윈도우를 지원하는 거대 OoO 엔진을 탑재하여 클라우드 워크로드 가속 | IPC, 싱글 스레드 처리량 |
| 스마트폰 AP (빅 코어) | 고성능 코어에 OoO와 리네이밍을 적용하여 복잡한 웹 브라우징이나 게임 실행 시 지연 최소화 | 앱 실행 속도, 반응성 |
| 보안 취약점 대응 | 비순서/투기적 실행 시 발생하는 캐시 흔적을 노린 스펙터(Spectre) 공격 방어를 위해 격리 로직 추가 | 패치 후 성능 저하율, 보안 강도 |

> 요약: 성능이 가장 중요한 현대의 모든 고성능 CPU에서 필수적으로 채택하는 기술임.

## Ⅵ. 결론

비순서 실행과 레지스터 리네이밍은 명령어 수준 병렬성(ILP)을 극한으로 끌어올리기 위한 마이크로아키텍처의 정수임. 기술사는 단순히 '순서를 바꾼다'는 개념을 넘어, 이를 가능케 하는 리네이밍의 논리-물리 매핑 원리와 결과의 순차적 확정(Commit)이 왜 중요한지를 명확히 이해해야 함.

향후 아키텍처는 전력 효율의 한계 내에서 명령어 윈도우를 더 넓히기 위해 인공지능 기반의 지능형 스케줄링을 도입할 것으로 보임. 또한 성능 향상을 위해 감수했던 투기적 실행의 보안 위험을 구조적으로 해결하는 것이 차세대 비순서 실행 엔진의 핵심 과제가 될 것임.
