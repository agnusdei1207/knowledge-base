## 미리 알고가기

- AUTOSAR는 차량 ECU 소프트웨어의 계층 구조와 인터페이스를 표준화한 플랫폼임
- SWC, RTE, BSW, MCAL이 핵심 계층임
- Classic과 Adaptive는 대상 ECU와 운영 방식이 다름

## 작성 근거(검토용)

- AUTOSAR는 SWC, RTE, BSW, MCAL, ARXML과 Classic·Adaptive 차이를 핵심 축으로 설명함
- 비교표는 독자 ECU 구조·Classic·Adaptive의 실행 구조, 적용 업무, 통합 방식을 대비함
- 실무 판단은 통합 결함 건수·타이밍 준수율과 부팅 시간·메모리 사용량으로 검증함

## Ⅰ. 개요

- **정의/개념**: AUTOSAR는 차량 ECU 소프트웨어를 응용 기능, 런타임, 기본 소프트웨어, 하드웨어 추상화 계층으로 나눠 재사용성과 공급사 독립성, 통합 검증성을 확보하는 자동차 SW 표준 플랫폼임
- **배경/필요성**: 공급사가 다른 ECU 소프트웨어를 재사용·통합 검증하기 위해 공통 계층과 인터페이스 표준이 필요함

## Ⅱ. 특징

- 응용 기능과 하드웨어 의존성을 분리해 이식성과 재사용성을 확보함
- ARXML 기반 설정과 코드 생성 품질이 개발 생산성을 좌우함
- Classic은 결정성과 제어 ECU에, Adaptive는 서비스 지향 고성능 ECU에 적합함
- 표준을 도입해도 툴 체인 관리와 통합 시험 부담은 남음

## Ⅲ. 종류 및 비교

| 판단 기준 | 전통 ECU 독자 구조 | AUTOSAR Classic | AUTOSAR Adaptive |
|:---|:---|:---|:---|
| 구조 방식 | 공급사별로 드라이버와 응용이 강하게 결합되는 경우가 많음 | 정적 계층 구조로 제어 중심 ECU를 표준화함 | 서비스 지향 구조로 고성능 ECU를 운영함 |
| 적합 업무 | 소규모 단일 기능 ECU에 맞음 | 제동과 조향과 바디 제어처럼 결정성이 중요한 업무에 맞음 | ADAS와 인포테인먼트와 중앙 컴퓨팅에 맞음 |
| 개발·확장 방식 | 공급사별 인터페이스를 직접 구현함 | 표준 인터페이스와 ARXML로 SWC를 통합함 | 서비스 검색·통신과 동적 배포 구조를 사용함 |
| 유의점 | 통합 규모가 늘수록 유지보수 비용이 증가함 | 설정 오류와 자원 오버헤드를 관리해야 함 | 자원 사용량과 서비스 복잡도를 통제해야 함 |

> 요약: Classic은 정적 계층으로 제어 ECU를 구성하고, Adaptive는 서비스 지향 구조로 고성능 ECU를 운영함.

## Ⅳ. 구성요소 및 구조

| 구성요소 | 설명 |
|:---|:---|
| SWC | 차량 기능 로직을 표준 포트 단위로 캡슐화함 |
| RTE | SWC와 BSW 사이 호출과 통신을 중개해 하드웨어 의존성을 줄임 |
| BSW | 통신과 진단과 운영체제와 메모리 서비스를 제공하는 공통 계층임 |
| MCAL | MCU 드라이버를 추상화해 상위 기본 소프트웨어와 하드웨어를 분리함 |
| ARXML | SWC·통신·ECU 설정을 교환하고 코드 생성 입력으로 사용함 |

> 요약: AUTOSAR는 SWC, RTE, BSW, MCAL·ARXML 계층으로 응용과 하드웨어 의존성을 분리함.

## Ⅴ. 원리 및 절차 흐름도

1. **기능 모델링**: 차량 기능을 SWC와 포트 단위로 정의함
2. **ECU 설정**: ARXML로 통신과 메모리와 BSW 구성을 정함
3. **코드 생성·통합**: RTE와 설정 코드를 생성해 응용 기능과 결합함
4. **HIL·SIL 검증**: 타이밍과 통신과 안전 요구를 시험함

> 요약: 기능을 SWC로 모델링하고 ARXML 설정, 코드 생성, HIL·SIL 검증으로 통합함.

## Ⅵ. 실무 사례

1. 바디 ECU는 ARXML 설정과 생성 코드를 CI에서 검증하고 통합 결함 건수·타이밍 준수율을 확인함
2. 도메인 컨트롤러는 서비스 계약을 관리하고 자원 사용량을 프로파일링해 부팅 시간·메모리 사용량을 확인함

## Ⅶ. 결론

- AUTOSAR는 ECU 요구에 따라 Classic·Adaptive를 선택하고 ARXML 설정·코드 생성·통합 타이밍을 검증해야 함
