# 📖 【암기용】 개념 완전 이해

> 목적: NUMA를 처음 봐도 "왜 같은 서버 안에서도 메모리에 따라 접근 속도가 다른가"를 구조적으로 이해하게 만든다. 시험 답안 양식이 아니라, 이해를 위한 친절한 설명이다.

## 한눈에
- **개요**: **메모리 접근 지연의 비대칭성**(Non-Uniform Memory Access)을 전제로 설계된 **멀티프로세서 메모리 아키텍처**로, 각 CPU(노드)가 자신에게 직접 연결된 로컬 메모리는 빠르게, 다른 노드의 원격 메모리는 인터커넥트를 거쳐 느리게 접근한다.
- **왜 필요한가**: 소켓(=CPU) 수가 늘어날수록 모든 코어가 메모리 컨트롤러 하나를 공유하는 UMA(Uniform Memory Access) 구조는 버스 경합으로 확장성 한계에 부딪힌다. NUMA는 메모리 컨트롤러 자체를 소켓마다 분산 배치해 이 병목을 근본적으로 없앤다.
- **핵심 직관**: 본사 건물 각 층(노드)에 자체 자료 보관함(로컬 메모리)을 두는 것과 같다. 내 층 보관함은 손을 뻗으면 닿지만, 다른 층 보관함 서류를 가져오려면 엘리베이터(인터커넥트)를 타고 이동해야 한다.

## 핵심 용어 정리 (내부에 등장하는 것들)

| 용어 | 의미 | 비유 |
|:---|:---|:---|
| 멀티프로세서 메모리 아키텍처 | CPU가 여러 개인 시스템에서 메모리를 어떻게 배치·공유할지 정하는 상위 설계 방식 — NUMA가 속한 **상위 개념** | 건물 전체의 자료 보관 정책 |
| UMA (Uniform Memory Access) | 모든 CPU가 단일 메모리 컨트롤러·버스를 공유해 어디서든 접근 지연이 동일한 구조 | 건물 1층 공용 보관함 하나를 전 직원이 씀 |
| NUMA 노드 (Node) | CPU 코어 + 그 코어에 직접 연결된 로컬 메모리 컨트롤러를 하나로 묶은 단위, 통상 소켓 1개 = 노드 1개 | 층별로 나뉜 부서 |
| 로컬 메모리 (Local Memory) | 현재 코어가 속한 노드에 직접 연결된 DRAM | 내 층 보관함 |
| 원격 메모리 (Remote Memory) | 다른 노드에 연결된 DRAM. 접근하려면 노드 간 인터커넥트를 거쳐야 함 | 다른 층 보관함 |
| 인터커넥트 (Interconnect) | 노드 간 메모리 요청을 중계하는 전용 통로. 인텔 UPI, AMD Infinity Fabric 등 | 층간 이동용 엘리베이터 |
| NUMA ratio (NUMA factor) | 원격 접근 지연 ÷ 로컬 접근 지연의 비율. 1에 가까울수록 UMA에 가까움 | 엘리베이터를 타는 데 드는 "배수 시간" |
| first-touch 정책 | 어떤 스레드가 특정 메모리 페이지를 처음 건드릴 때, 그 페이지를 그 스레드가 실행 중인 노드의 로컬 메모리에 할당하는 OS 정책 | 서류를 처음 꺼낸 사람 층 보관함에 자동 재배치 |
| ccNUMA (cache-coherent NUMA) | 노드가 물리적으로 나뉘어 있어도 캐시 일관성 프로토콜로 전체를 논리적으로 하나의 메모리 공간처럼 보이게 만든 NUMA | 층은 나뉘어도 회사 전체 서류 목록은 하나로 통합 관리 |

## 깊이 이해

### 왜 UMA에서 NUMA로 전환했나 (배경)
- UMA는 CPU가 몇 개 안 될 때는 단순하고 균일해서 좋다. 하지만 코어 수가 늘어나면 모든 코어가 메모리 컨트롤러 하나로 몰려들어 버스 경합이 기하급수적으로 늘어난다. 코어가 4개에서 64개로 늘면 메모리 요청이 동시에 몰릴 확률과 큐잉 지연이 함께 늘어, 실질 처리량은 코어 수만큼 늘지 않는다.
- NUMA는 이 병목을 코어 확장과 함께 메모리 컨트롤러도 분산시켜 해결한다 — 소켓마다 자기 메모리 컨트롤러를 두므로, 각 소켓은 자기 로컬 접근에서는 경합 없이 최대 대역폭을 낸다.

### 로컬 vs 원격 접근 — 수치로 이해
- 예시 수치(구조 이해용, 실제 값은 CPU 세대·토폴로지마다 다름): 2소켓 서버에서 로컬 DRAM 접근 지연이 약 90ns, 원격(1-hop 인터커넥트 경유) 접근 지연이 약 140ns라면 NUMA ratio는 140/90 ≈ 1.56이다.
- 이 차이가 작아 보여도 누적되면 크다. 어떤 스레드가 원격 노드 메모리에 1억 번 접근한다면, 로컬 접근 대비 추가 지연만 (140-90)ns × 1억 = 5초가 순수 대기 시간으로 누적된다. 초당 수십억 번 메모리를 참조하는 워크로드에서는 이 차이가 체감 성능 저하로 직결된다.
- 노드가 3개 이상이면 인터커넥트를 몇 번 거치느냐(hop 수)에 따라 지연이 더 늘 수 있다 — 예: Node 0 → Node 1 → Node 2로 2-hop을 거치면 1-hop보다 지연이 더 커진다.

### first-touch가 실제로 동작하는 방식
- 프로세스가 `malloc`으로 메모리를 할당해도, 그 순간에는 물리 페이지가 아직 어느 노드에도 배정되지 않는다(가상 주소만 예약됨).
- 어떤 스레드가 그 페이지를 실제로 처음 읽거나 쓰는 순간, OS가 "지금 이 스레드가 실행 중인 노드"의 로컬 메모리에서 물리 페이지를 배정한다 — 이것이 first-touch다.
- 문제는 스레드 A가 메모리를 초기화(첫 접근)하고 스레드 B가 나중에 그 데이터를 주로 쓰는 패턴이다. 이 경우 데이터가 A의 노드에 배정되어 B가 매번 원격 접근을 하게 된다. `numactl --membind=0 --cpunodebind=0`처럼 프로세스를 특정 노드에 고정(pinning)하거나, 데이터를 실제 소비 스레드의 노드에서 초기화하도록 코드를 바꿔 이 문제를 피한다.

### ccNUMA의 캐시 일관성 문제
- 물리적으로 메모리가 노드별로 나뉘어 있어도, 프로그램 입장에서는 하나의 주소 공간처럼 보여야 한다. 문제는 Node 0의 캐시에 있는 데이터를 Node 1의 코어가 수정하면, Node 0 캐시의 값이 오래된(stale) 값이 되는 것이다.
- ccNUMA는 디렉터리 기반 프로토콜로 "이 캐시 라인을 누가 갖고 있는지"를 노드마다 장부(디렉터리)로 관리해, 다른 노드가 값을 바꾸면 관련 노드의 캐시를 무효화(invalidate)하거나 갱신한다. 이 통신도 인터커넥트를 타므로, 여러 노드가 같은 데이터를 자주 공유·수정할수록 인터커넥트 트래픽이 늘어 성능이 떨어진다.

### 흔한 오해
- "NUMA는 메모리 용량이 노드마다 나뉘어 있어서 하나의 프로세스가 전체 메모리를 못 쓴다" — 틀렸다. ccNUMA 덕분에 논리적으로는 전체 메모리가 하나의 주소 공간으로 보이며, 접근 지연만 위치에 따라 다를 뿐 용량 제약은 없다.
- "코어를 늘리면 항상 빨라진다" — NUMA 인식 없이 스레드와 메모리가 서로 다른 노드에 흩어지면, 코어를 늘려도 원격 접근 비율이 늘어 오히려 성능이 떨어질 수 있다.

## 연결 개념
- UMA(Uniform Memory Access) — 단일 버스 공유 구조, NUMA가 극복하려는 이전 세대 구조
- QPI/UPI, Infinity Fabric — 소켓 간 인터커넥트의 실제 구현 예
- First-Touch 정책·numactl — NUMA 인식 메모리 배치 기법
- ccNUMA·디렉터리 기반 캐시 일관성 — 노드가 나뉘어도 하나의 메모리처럼 보이게 하는 하드웨어 프로토콜
- 026_non_uniform_memory_access — 같은 NUMA를 다른 관점(멀티스레드 앱 개발자 체감 사례 중심)으로 다룬 항목

# 📝 【답안용】 시험 답안 템플릿

> 목적: 시험장에서 25분에 그대로 쓰는 답안 양식. 작성방식(추상표현 금지·수치·도식·문제유형 전환)을 엄격히 지킨다.
> 핵심: NUMA는 "메모리가 여러 개"라는 설명에 그치지 않고, 로컬/원격 접근 지연 차이와 OS 배치 정책까지 답안에 포함한다.

## 핵심 인사이트 (3줄 요약)

> 1. **본질**: NUMA(Non-Uniform Memory Access)는 멀티소켓 시스템에서 각 노드가 자신의 로컬 메모리를 원격 메모리보다 빠르게 접근하는 아키텍처다.
> 2. **가치**: 메모리 컨트롤러를 노드별로 분산해 단일 공유 버스의 경합 병목을 완화하고 소켓 확장성을 높인다.
> 3. **판단 포인트**: 로컬/원격 접근 지연 비율(NUMA ratio)과 OS의 스레드·메모리 배치 정책을 함께 판단해야 성능 저하를 막을 수 있다.

## 출제 의도 및 답안 포인트

| 출제 의도 | 반드시 짚을 핵심 | 감점 회피 포인트 |
|:---|:---|:---|

| OS 배치 정책 이해 확인 | first-touch, numactl, NUMA 밸런싱 | 하드웨어 구조만 설명하고 OS 대응을 누락 |

## Ⅰ. 개요 및 필요성

- 개요: 멀티소켓 시스템에서 노드별 로컬 메모리 접근이 원격 메모리 접근보다 빠른 비균등 메모리 접근 아키텍처
- 배경: 소켓 수 증가 시 단일 공유 버스(UMA) 구조는 버스 경합으로 확장성 한계에 부딪힘
- 필요성: 노드별 메모리 컨트롤러 분산과 OS의 지역성 인식 배치가 함께 이뤄져야 멀티소켓 확장 이득을 실제로 얻을 수 있음

---

## Ⅱ. 구조 및 구성요소

```text
Node 0 (CPU + Local Memory) -- Interconnect -- Node 1 (CPU + Local Memory)
     |                                              |
     +-> 로컬 접근: 직접 메모리 컨트롤러 경유          +-> 로컬 접근: 직접 메모리 컨트롤러 경유
     +-> 원격 접근: Interconnect 경유(Node 1 메모리)   +-> 원격 접근: Interconnect 경유(Node 0 메모리)
```

| 구성요소 | 역할 | 특이사항 |
|:---|:---|:---|
| NUMA Node | CPU 코어 + 로컬 메모리 컨트롤러 묶음 | 소켓 단위로 구성되는 경우가 일반적 |
| Local Memory | 해당 노드에 직접 연결된 DRAM | 낮은 접근 지연 |
| Remote Memory | 다른 노드에 연결된 DRAM | 인터커넥트 경유로 지연 증가 |
| Interconnect | 노드 간 연결 통로(UPI, Infinity Fabric 등) | 대역폭·지연이 로컬 대비 불리 |

> 요약: NUMA 노드는 CPU와 로컬 메모리를 하나로 묶고, 원격 노드 메모리 접근은 인터커넥트를 거쳐야 한다.

---

## Ⅲ. 동작원리 및 흐름도

```text
스레드 실행(Node X) -> 메모리 접근 요청
  -> 요청 주소가 Node X 로컬 메모리인지 확인
       -> 로컬: 로컬 메모리 컨트롤러 직접 접근
       -> 원격: Interconnect 경유해 대상 노드 메모리 컨트롤러 접근
  -> OS/스케줄러가 배치 정책(first-touch 등)으로 향후 지역성 조정
```

| 단계 | 처리 내용 | 검증 기준 |
|:---:|:---|:---|
| 1 | 스레드가 실행 중인 노드 확인 | CPU affinity 설정 |
| 2 | 메모리 요청 주소의 소속 노드 판별 | 페이지의 물리 노드 위치 |
| 3 | 로컬/원격 여부에 따라 접근 경로 결정 | 인터커넥트 경유 여부 |
| 4 | OS가 배치 정책으로 이후 지역성 개선 시도 | first-touch, NUMA 밸런싱 적용 여부 |

> 요약: 메모리 접근은 요청 주소가 로컬인지 원격인지에 따라 경로가 갈리며, OS 배치 정책이 이 비율을 좌우한다.

## Ⅳ. 특징

| 구분 | UMA | NUMA | 수치·표준 포인트 |
|:---|:---|:---|:---|
| 접근 구조 | 단일 공유 버스로 전 메모리 균등 접근 | 노드별 로컬/원격 접근 지연 차등 | 소켓 간 인터커넥트 예: UPI, Infinity Fabric |
| 확장성 | 소켓 증가 시 버스 경합 심화 | 노드별 컨트롤러 분산으로 확장성 개선 | 대형 서버는 4~8소켓 NUMA 구성 사례 존재 |
| 지연 특성 | 위치와 무관하게 지연 균일 | 로컬 대비 원격 접근 지연 증가(NUMA ratio) | 실제 배수는 세대·토폴로지별 상이 |
| 소프트웨어 요구 | 배치 최적화 불필요 | NUMA 인식 스케줄링·배치 필요 | numactl, first-touch, NUMA 밸런싱 |

> 요약: UMA는 균일하지만 확장성에 한계가 있고, NUMA는 확장성은 좋지만 소프트웨어의 지역성 관리가 필요하다.

## Ⅴ. 심화 비교 및 적용 판단

| 구분 | UMA | NUMA | 선택 기준 |
|:---|:---|:---|:---|
| 구조 | 단일 버스, 균일 접근 | 노드 분산, 로컬/원격 차등 접근 | 소켓 수가 적으면 UMA로도 충분 |
| 비용/성능 | 소켓 증가 시 버스 경합으로 성능 저하 | 소켓 증가에도 로컬 접근 유지 가능 | 대규모 멀티소켓 서버는 NUMA 필수 |
| 운영/위험 | 배치 최적화 불필요 | 배치 오류 시 원격 접근 비율 증가로 성능 저하 | 워크로드가 NUMA 인식 스케줄링을 지원하는지 확인 |

> 요약: 소켓 수가 적으면 UMA로도 충분하지만, 대규모 멀티소켓 환경은 NUMA 인식 배치가 성능을 좌우한다.

| 리스크 | 원인 | 대응 방안 | 확인 지표 |
|:---|:---|:---|:---|
| 원격 접근 비율 증가 | 스레드와 메모리가 다른 노드에 배치 | first-touch 정책, numactl pinning | 원격/로컬 접근 비율 |
| NUMA 밸런싱 오버헤드 | 커널의 자동 페이지 마이그레이션 비용 | 워크로드별 밸런싱 활성화 여부 조정 | 페이지 마이그레이션 횟수 |
| 인터커넥트 병목 | 다수 스레드의 동시 원격 접근 집중 | 데이터 파티셔닝으로 노드별 작업 분리 | 인터커넥트 대역폭 사용률 |

> 요약: NUMA 리스크는 원격 접근 비율과 인터커넥트 병목 지표로 통제해야 한다.

| 점검 항목 | 목표 기준 | 측정 방법 |
|:---|:---|:---|
| 로컬 접근 비율 | 워크로드 기준 목표 비율 설정 | `numastat` 등 NUMA 통계 도구 |
| 메모리 지연 | 로컬/원격 접근 지연 격차 확인 | 마이크로벤치마크(예: STREAM 계열 도구) |
| 인터커넥트 사용률 | 노드 간 트래픽 임계치 이하 유지 | 하드웨어 성능 카운터 |

> 요약: 도입 효과는 로컬 접근 비율, 로컬/원격 지연 격차, 인터커넥트 사용률로 판단한다.

## Ⅵ. 실무 적용 및 결론

**적용 방안 3개:**
1. 대규모 멀티소켓 서버는 애플리케이션 스레드를 특정 노드에 고정(pinning)하고 first-touch 정책으로 로컬 메모리 할당 비율을 높임
2. 인메모리 DB·대형 데이터셋 워크로드는 데이터를 노드별로 파티셔닝해 원격 접근 비율을 낮춤
3. 자동 배치 최적화가 필요한 경우 NUMA 밸런싱을 활성화하되, 마이그레이션 오버헤드를 모니터링해 워크로드별로 조정함

**결론 (2줄):**
- 기술사 판단: 소켓 수가 적은 시스템은 UMA로도 충분하지만, 소켓 확장이 필요한 대규모 서버는 NUMA 인식 배치 설계가 필수임
- 향후 방향: CXL 메모리 풀링과 결합해 NUMA 노드 간 메모리 공유·확장 방식이 다양해지는 추세임
