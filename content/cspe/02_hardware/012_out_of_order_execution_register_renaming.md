## Ⅰ. 개요
- **정의**: 데이터 의존성이 없는 명령어를 프로그램 순서와 무관하게 먼저 실행하고, 결과를 원래 순서로 복원하는 기법
- **배경/필요성**: 파이프라인(007 참조) 스톨은 의존성 있는 명령어가 대기할 때 발생함. 의존성 없는 명령어를 앞당기면 파이프라인 유휴 사이클을 줄일 수 있음
- **비유**: 은행 창구에서 서류 미비 고객을 대기시키고, 준비된 다음 고객을 먼저 처리한 뒤 최종 번호표 순서로 결과를 정리하는 것과 같음

| 출제 의도 | 반드시 짚을 핵심 | 감점 회피 포인트 |
|:---|:---|:---|
| OoO 실행의 원리 | 발행-실행-완료 3단계 분리 | ROB로 순서 복원(in-order commit)을 명시 |
| 레지스터 리네이밍 목적 | WAR/WAW 해저드 제거 | RAW(진짜 의존)는 리네이밍으로 해결 불가임을 언급 |

> 요약: 의존성 없는 명령어를 먼저 실행하고 ROB로 순서를 복원하며, 리네이밍으로 거짓 의존을 제거함

## Ⅱ. 구성요소
```text
Fetch --> Decode --> Rename --> Issue Queue --> Execute --> ROB --> Commit
                      |                          |          ^
                      v                          v          |
               +-------------+            +----------+     |
               | Rename Table |            | Func Units|----+
               | (Phys Regs)  |            +----------+
               +-------------+
```

| 구성요소 | 설명 | 비유 |
|:---|:---|:---|
| 이슈 큐(RS) | 피연산자가 준비된 명령어를 FU에 디스패치하는 대기열 | 재료가 모인 주문서부터 조리대에 보내는 대기판 |
| 리네이밍 테이블 | 아키텍처 레지스터를 물리 레지스터에 매핑하여 WAR/WAW를 제거함 | 같은 이름의 우편함을 각자 다른 사서함으로 분리 |
| 재정렬 버퍼(ROB) | 실행 완료된 명령어를 프로그램 순서로 커밋하는 원형 큐 | 번호표 순서대로 결과를 돌려주는 접수 창구 |
| 물리 레지스터 파일 | 아키텍처 레지스터보다 큰 물리 레지스터 풀로 리네이밍을 지원함 | 실제 보관함 수가 이름표 수보다 많은 물류 창고 |

> 요약: 리네이밍 테이블로 거짓 의존을 제거하고, 이슈 큐에서 준비된 명령어를 실행한 뒤 ROB로 순서를 복원함

## Ⅲ. 절차
```text
Decode --> Register Rename --> Issue(Ready?) --> Execute --> ROB Commit
```
- 1단계: **레지스터 리네이밍** — 디코딩된 명령어의 목적 레지스터를 새 물리 레지스터에 매핑하여 WAR/WAW 해저드를 제거함
- 2단계: **이슈 큐 대기** — 피연산자가 모두 준비된 명령어를 선택하여 FU에 디스패치함(데이터 흐름 순서)
- 3단계: **비순서 실행** — 복수 FU가 프로그램 순서와 무관하게 준비된 명령어를 병렬 실행함
- 4단계: **순서 커밋** — ROB 헤드의 명령어부터 프로그램 순서로 아키텍처 상태에 반영(in-order commit)함

> 요약: 리네이밍 후 준비된 명령어를 먼저 실행하고, ROB에서 프로그램 순서로 커밋함

## Ⅳ. 문제점
- **하드웨어 복잡도**: 리네이밍 테이블·이슈 큐·ROB가 트랜지스터와 전력을 소모하여 칩 면적이 증가함
- **ROB 용량 한계**: ROB 엔트리 수가 부족하면 in-flight 명령어 수가 제한되어 ILP 활용률이 감소함
- **예외 처리 지연**: 비순서 실행 중 예외 발생 시 ROB를 롤백해야 하므로 복구 지연이 수십 사이클에 달함

> 요약: 하드웨어 복잡도 증가, ROB 용량 제한, 예외 복구 지연이 주요 문제임

## Ⅴ. 개선방안
1. 단기: **클러스터드 스케줄링** — 이슈 큐를 기능별로 분할하여 비교 회로 수를 줄이고 면적·전력을 절감함
2. 중기: **ROB 확장·체크포인트** — ROB 엔트리를 수백 개로 확대하고 주기적 체크포인트로 in-flight 윈도를 확장함
3. 장기: **하드웨어-컴파일러 협업** — 컴파일러가 명령어 순서를 사전 정렬하여 런타임 롤백 빈도를 줄이고 복구 경로를 단축함

> 요약: 클러스터드 스케줄링, ROB 확장, 컴파일러 협업으로 단계적으로 개선함

## Ⅵ. 전망
- **발전 방향**: ROB 엔트리 1,000개 이상의 광폭 비순서 코어가 고성능 서버 CPU의 기본 구조로 정착됨
- **기술사적 판단**: 단일 스레드 성능 향상의 핵심 기법이며, 멀티코어(014 참조)와 상호 보완 관계임
- **기술사 제언**: OoO 복잡도와 전력의 트레이드오프를 워크로드 특성에 맞게 설계하는 역량이 필요함
