# 📖 【암기용】 개념 완전 이해

> 목적: 비순서 실행과 레지스터 리네이밍을 처음 봐도 왜 명령어 순서를 바꿔 실행하고도 결과가 프로그램 순서와 같아지는지 이해하게 만든다. 시험 답안 양식이 아니라, 이해를 위한 친절한 설명이다.

## 한눈에
- **개요**: 프로그램 순서가 아니라 피연산자가 준비된 순서로 명령어를 먼저 실행하고, 결과는 다시 프로그램 순서로 커밋하는 실행 기법
- **왜 필요한가**: In-order 실행은 앞선 명령어가 스톨하면 뒤의 독립적인 명령어도 함께 멈춰야 하므로, 실행 유닛 활용률이 낮아진다
- **핵심 직관**: 은행 창구에서 앞사람 서류 처리가 지연되면, 뒷사람이 다른 창구에서 먼저 처리받고 나중에 순서대로 도장을 받는 구조다

## 깊이 이해
- **배경·문제의식**: In-order 슈퍼스칼라는 캐시 미스나 긴 연산으로 한 명령어가 막히면 프로그램 순서상 뒤에 있는 독립 명령어도 발행을 못 해 실행 유닛이 논다.
- **작동 원리 - Tomasulo 알고리즘**: 명령어는 디스패치 시 예약 스테이션(Reservation Station)에 들어가고, 필요한 피연산자가 모두 준비되면 프로그램 순서와 무관하게 실행 유닛으로 발행된다.
- **작동 원리 - 레지스터 리네이밍**: 아키텍처 레지스터(예: R1)를 여러 개의 물리 레지스터에 매핑해, 같은 이름의 레지스터를 재사용하는 명령어 간 WAR(Write-After-Read)·WAW(Write-After-Write) 해저드를 제거한다.
- **작동 원리 - RAT과 물리 레지스터 파일**: RAT(Register Alias Table)이 아키텍처 레지스터 번호를 현재 유효한 물리 레지스터 번호로 매핑하고, 물리 레지스터 파일(PRF)이 실제 값을 저장한다.
- **작동 원리 - ROB과 정밀 예외**: ROB(Reorder Buffer)은 비순서로 완료된 명령어 결과를 프로그램 순서대로 커밋(retire)해, 인터럽트·예외 발생 시에도 아키텍처 상태를 정확한 지점에서 복구할 수 있게 한다.
- **비유**: 리네이밍은 같은 사물함 번호(R1)를 여러 개 마련해 두고 매번 새 사물함을 배정하는 것이고, ROB은 사물함을 다 쓴 뒤에도 반드시 접수 순서대로 서류를 최종 도장 찍는 창구다.
- **구체 예시**: `R1 = R2 + R3` 다음 `R1 = R4 + R5`가 오면 두 번째 R1은 첫 번째 R1과 값이 무관한데, 리네이밍이 없으면 WAW 해저드로 순서를 지켜야 하지만 리네이밍이 두 번째 R1을 별도 물리 레지스터로 배정해 병렬 실행을 허용한다.
- **흔한 오해·주의점**: 비순서 실행은 실행 순서만 바꿀 뿐, 아키텍처적으로 보이는 결과(레지스터·메모리 상태, 예외 시점)는 반드시 프로그램 순서와 동일해야 하며 이는 ROB의 순서대로 커밋 규칙이 보장한다.
- **흔한 오해·주의점**: 레지스터 리네이밍은 RAW(진짜 데이터 의존) 해저드를 없애지 못한다. RAW는 실제 데이터 흐름이므로 값이 계산될 때까지는 기다려야 한다.

## 연결 개념
- 파이프라인 포워딩·분기 예측 — 비순서 실행과 함께 파이프라인 정지를 줄이는 기법
- 슈퍼스칼라(Superscalar) — 비순서 실행이 발행 폭 활용률을 끌어올리는 방식
- 명령어 수준 병렬성(ILP) — 비순서 실행이 추출 폭을 넓히는 대상

# 📝 【답안용】 시험 답안 템플릿

> 목적: 시험장에서 25분에 그대로 쓰는 답안 양식. 작성방식(추상표현 금지·수치·도식·문제유형 전환)을 엄격히 지킨다.
> 핵심: Tomasulo 예약 스테이션 구조, RAT·PRF 기반 레지스터 리네이밍, ROB의 순서 커밋을 통한 정밀 예외 보장을 함께 제시한다.

## 핵심 인사이트 (3줄 요약)

> 1. **본질**: 비순서 실행은 피연산자가 준비된 명령어부터 먼저 실행하고, 레지스터 리네이밍은 이름만 같은 레지스터 간 가짜 의존성(WAR·WAW)을 제거하는 기법이다.
> 2. **가치**: 두 기법을 결합하면 실행 유닛 idle 시간을 줄여 슈퍼스칼라 발행 폭 활용률을 높인다.
> 3. **판단 포인트**: ROB이 결과를 프로그램 순서대로 커밋해야만 비순서 실행에도 정밀 예외(precise exception)가 보장되므로, 실행 순서 변경과 커밋 순서 유지를 구분해서 답안에 반영해야 한다.

## 출제 의도 및 답안 포인트

| 출제 의도 | 반드시 짚을 핵심 | 감점 회피 포인트 |
|:---|:---|:---|
| 동적 스케줄링 메커니즘 이해 확인 | Tomasulo 예약 스테이션, 피연산자 준비 기반 발행 | 비순서 실행을 단순히 "명령어를 섞어 실행"으로만 서술 |
| WAR/WAW 제거 원리 이해 확인 | RAT·PRF 기반 물리 레지스터 매핑 | 레지스터 리네이밍이 RAW까지 없앤다고 서술 |
| 정밀 예외 보장 메커니즘 확인 | ROB 기반 순서 커밋 | 실행 순서와 커밋 순서를 동일한 것으로 혼동 |

> 요약: 이 문제는 실행은 비순서, 커밋은 순서라는 구분과 리네이밍이 제거하는 해저드 종류를 정확히 짚어야 한다.

## Ⅰ. 개요 및 필요성

- 정의: 비순서 실행은 피연산자 준비 순서로 명령어를 실행하는 기법, 레지스터 리네이밍은 아키텍처 레지스터를 물리 레지스터로 매핑해 가짜 의존성을 제거하는 기법
- 배경: In-order 실행은 선행 명령어 지연 시 후속 독립 명령어도 함께 멈춰 실행 유닛 활용률이 떨어짐
- 필요성: 예약 스테이션·리오더 버퍼·레지스터 리네이밍을 결합하면 WAR·WAW를 제거하고 실행 유닛 idle을 줄이면서도 프로그램 순서와 동일한 아키텍처 상태를 보장할 수 있음

---

## Ⅱ. 구조 및 구성요소

```text
Instruction Dispatch -> RAT: 아키텍처 레지스터 -> 물리 레지스터 매핑
  -> Reservation Station: 피연산자 대기
  -> 피연산자 준비 완료 -> Execution Unit 발행(비순서)
  -> ROB: 실행 결과를 프로그램 순서로 재정렬
  -> In-order Commit -> Architectural State 갱신
```

| 구성요소 | 역할 | 산출물 |
|:---|:---|:---|
| RAT(Register Alias Table) | 아키텍처 레지스터를 현재 물리 레지스터에 매핑 | 레지스터 이름 충돌 제거 |
| 물리 레지스터 파일(PRF) | 실제 값을 저장하는 확장된 레지스터 공간 | WAR·WAW 회피 공간 |
| 예약 스테이션(Reservation Station) | 피연산자 준비 여부 감시 후 실행 유닛에 발행 | 비순서 발행 스케줄 |
| ROB(Reorder Buffer) | 실행 완료 결과를 프로그램 순서로 커밋 | 정밀 예외·정합적 아키텍처 상태 |

> 요약: RAT·PRF가 가짜 의존성을 없애고, 예약 스테이션이 비순서 발행을, ROB이 순서 커밋을 담당한다.

---

## Ⅲ. 동작원리 및 흐름도

```text
명령어 Dispatch -> RAT 조회로 물리 레지스터 할당
  -> Reservation Station 대기(피연산자 미비 시)
  -> 피연산자 준비 완료 시점에 Execution Unit으로 비순서 발행
  -> 실행 결과를 ROB 슬롯에 기록
  -> ROB 헤드부터 순서대로 Commit -> Architectural State 갱신
  -> 예외 발생 시 ROB 커밋 지점 기준으로 상태 복구
```

| 단계 | 처리 내용 | 검증 기준 |
|:---:|:---|:---|
| 1 | Dispatch 시 RAT으로 물리 레지스터 배정 | 레지스터 이름 충돌 제거 여부 |
| 2 | 예약 스테이션에서 피연산자 준비 대기 | RAW 값 도착 여부 |
| 3 | 준비 완료 명령어부터 비순서 발행 | 실행 유닛 idle cycle 감소 |
| 4 | ROB 헤드 순서대로 커밋 | 프로그램 순서 아키텍처 상태 일치 |

> 요약: 실행은 피연산자 준비 순서로 비순서 진행되지만, 커밋은 반드시 ROB 헤드부터 프로그램 순서로 이뤄진다.

## Ⅳ. 특징

| 구분 | 내용 | 판단 포인트 |
|:---|:---|:---|
| 장점 | WAR·WAW 제거로 실행 유닛 활용률 상승 | idle cycle 감소 |
| 한계 | RAT·PRF·ROB 추가로 하드웨어 복잡도·검증 비용 증가 | 물리 레지스터 수, ROB 크기 설계 필요 |
| 비교 포인트 | RAW는 리네이밍으로 제거 불가, 포워딩·스톨로만 해소 | 해저드 종류별 대응 기법 구분 |

> 요약: 비순서 실행·리네이밍은 WAR·WAW를 없애 활용률을 높이지만 RAW는 여전히 데이터 도착을 기다려야 한다.

## Ⅴ. 심화 비교 및 적용 판단

| 비교 축 | In-order 실행 | Out-of-order 실행 | 선택 기준 |
|:---|:---|:---|:---|
| 구조 | 프로그램 순서대로만 발행 | 예약 스테이션·ROB 기반 비순서 발행 | ILP 활용 목표 수준에 따라 결정 |
| 비용/성능 | 하드웨어 단순, idle 발생 가능 | 실행 유닛 활용률 향상, 면적·전력 증가 | 성능 목표 대비 면적·전력 예산 |
| 운영/위험 | 검증 상대적으로 단순 | 리네이밍·ROB 조합 검증 비용 증가 | 검증 커버리지 확보 가능 여부 |

> 요약: 고성능 범용 코어는 out-of-order를, 저전력·단순 제어 목적 코어는 in-order를 선택한다.

| 리스크 | 원인 | 대응 방안 | 확인 지표 |
|:---|:---|:---|:---|
| 물리 레지스터 고갈 | 리네이밍 대상 명령어 과다 발행 | 물리 레지스터 수 확대, 조기 해제 정책 | 물리 레지스터 사용률 |
| ROB 정체 | 커밋 지연 명령어(긴 지연 연산) 존재 | ROB 크기 확대, 지연 연산 우선순위 조정 | ROB occupancy, commit stall 빈도 |
| 정밀 예외 오류 | 커밋 순서 위반 | ROB 기반 순서 커밋 검증, 정형 검증 | 예외 발생 지점 아키텍처 상태 일치 여부 |

> 요약: 리소스 고갈과 커밋 지연이 핵심 리스크이며, 물리 레지스터·ROB 크기 설계와 검증으로 통제한다.

| 점검 항목 | 목표 기준 | 측정 방법 |
|:---|:---|:---|
| IPC | 목표 IPC 대비 실측치 확보 | 성능 카운터 |
| 실행 유닛 활용률 | idle cycle 최소화 | 마이크로아키텍처 트레이스 |
| 정밀 예외 정합성 | 예외 발생 시 아키텍처 상태 100% 일치 | 검증 스위트, 정형 검증 |

> 요약: 도입 효과는 IPC, 실행 유닛 활용률, 정밀 예외 정합성 세 지표로 판단한다.

## Ⅵ. 실무 적용 및 결론

**적용 방안 3개:**
1. 고성능 범용 코어는 예약 스테이션·ROB 기반 비순서 실행을 적용해 실행 유닛 idle을 줄임
2. 리네이밍 대상 물리 레지스터 수를 워크로드 특성에 맞춰 산정해 물리 레지스터 고갈로 인한 발행 정체를 방지함
3. ROB 기반 순서 커밋 검증을 강화해 예외·인터럽트 발생 시 정밀 예외를 보장함

**결론 (2줄):**
- 기술사 판단: 비순서 실행은 실행 유닛 활용률을 높이지만 반드시 ROB 기반 순서 커밋으로 아키텍처 정합성을 유지해야 함
- 향후 방향: 코어당 물리 레지스터·ROB 확대에 따른 면적·전력 비용 증가로, 멀티코어·SMT와의 균형 설계가 함께 검토되어야 함
