# 📖 【암기용】 개념 완전 이해

> 목적: 명령어가 쓰인 순서를 뒤죽박죽 섞어버리는 비순차 실행(OoO)과, 가짜 의존성을 마법처럼 없애는 레지스터 리네이밍을 직관적으로 이해하게 만든다.

## 한눈에
- **개요**: **동적 스케줄링**(010 참조)을 실행 단계까지 완성하는 기법으로, 프로세서가 명령어를 프로그램에 쓰인 순서(program order)가 아니라 **데이터가 준비된 순서**대로 먼저 실행(OoO)하되, 최종 결과 반영(커밋)만은 원래 순서를 지키는 하드웨어 기법이다. 이를 가능하게 하는 핵심 보조 기술이 **레지스터 리네이밍**이다.
- **왜 필요한가**: 앞 명령어가 메모리 접근 등으로 오래 걸릴 때, 그 뒤에 있는(하지만 앞 명령어와 무관한) 명령어들까지 순서 때문에 덩달아 멈추는 것(스톨)을 막기 위해서다.
- **핵심 직관**: 식당에서 1번 손님이 30분 걸리는 스테이크를 시켰다고 2번 손님의 3분짜리 라면 주문까지 묶어두지 않는다. 주방(OoO)은 라면부터 빨리 내보내고, 계산서(Commit)만 원래 주문 순서대로 정리한다.

## 핵심 용어 정리 (내부에 등장하는 것들)

| 용어 | 의미 | 비유 |
|:---|:---|:---|
| 동적 스케줄링 | 실행 순서를 런타임에 하드웨어가 정하는 방식 (010 참조) | 즉석 배차 |
| RAW (진성 의존성) | 뒤 명령이 앞 명령의 **계산 결과**를 실제로 읽어야 함 — 없앨 수 없는 진짜 의존성 | 재료가 있어야 요리 가능 |
| WAR (반의존성) | 뒤 명령이 같은 레지스터에 쓰기 전에, 앞 명령이 그 레지스터를 먼저 읽어야 함 — 이름만 같을 뿐인 가짜 의존성 | 같은 좌석 번호를 다음 손님에게 주기 전 앞 손님이 일어나야 할 것 같지만, 다른 좌석을 주면 그만 |
| WAW (출력 의존성) | 두 명령이 같은 레지스터에 순서대로 써야 함 — 역시 이름만 겹치는 가짜 의존성 | 같은 문패를 두 번 거는 순서 문제일 뿐, 문패를 두 개 준비하면 해결 |
| 레지스터 리네이밍 | 논리 레지스터(R1 등) 이름을 매번 새로운 물리 레지스터로 바꿔 달아 WAR/WAW를 원천 제거하는 기법 | 동명이인 환자에게 각자 다른 내부 접수번호 부여 |
| RAT (Register Alias Table) | "논리 레지스터 R1은 지금 물리 레지스터 P10을 가리킨다"를 기록하는 매핑 표 | 접수번호 대장 |
| RS (Reservation Station) | 실행 유닛 앞에서 피연산자가 준비되길 기다리는 대기소 | 재료 다 모일 때까지 대기하는 조리대 |
| ROB (Re-Order Buffer) | 비순차로 끝난 결과를 임시 보관했다가 원래 순서대로 최종 반영(커밋)하는 버퍼 | 완성된 요리를 원래 주문 순서대로 내보내는 픽업대 |
| 물리 레지스터 파일 (PRF) | 논리 레지스터 개수보다 훨씬 많이 준비해둔 실제 저장 공간 | 넉넉히 준비한 여분 접수번호 |

## 깊이 이해

### 레지스터 리네이밍을 수치로 이해하기
- 다음 4개 명령어를 보자.
  - `I1: R1 = R2 + R3`   (R1에 쓰기)
  - `I2: R4 = R1 + 1`    (R1을 읽음 → I1과 RAW, 실제로 대기해야 함)
  - `I3: R1 = R5 + R6`   (R1에 다시 쓰기 → I1과 이름만 겹치는 WAW)
  - `I4: R7 = R1 + R8`   (R1을 읽음 → I3의 결과를 읽어야 함, I3과 RAW)
- 이름만 보면 I1과 I3이 둘 다 R1에 쓰므로 순서를 지켜야 할 것 같다. 하지만 리네이밍을 적용하면: RAT가 I1의 R1을 물리 레지스터 P10에, I3의 R1을 P11에 각각 새로 할당한다. 그러면 I2는 P10을 읽고(I1과의 진짜 RAW만 남음), I4는 P11을 읽는다(I3과의 진짜 RAW만 남음).
- 결과적으로 I1·I2 쌍과 I3·I4 쌍은 서로 완전히 남남이 되어 두 쌍을 **동시에** 실행할 수 있다. 리네이밍이 없었다면 I3은 I1·I2가 R1 사용을 끝낼 때까지 기다려야 했을 것이다.

### 판별 원리 — 진짜 대기 vs 가짜 대기
- 어떤 의존성이 실행 순서를 실제로 묶는지 판별하는 기준은 하나다: **읽는 값이 앞 명령의 계산 "결과"인가, 아니면 단지 "이름"이 같을 뿐인가**. 전자(RAW)는 리네이밍으로도 못 없앤다 — 데이터가 실제로 필요하기 때문이다. 후자(WAR·WAW)는 물리 레지스터를 새로 배정하는 순간 사라진다.

### 작동 흐름과 ROB의 역할
- 명령어는 인출·리네이밍(RAT 갱신)까지는 순서대로 처리된다. 이후 RS에서 피연산자가 준비되는 대로 비순차로 실행 유닛에 발행된다. 실행이 끝난 결과는 곧바로 레지스터에 쓰지 않고 ROB에 임시로 쌓아두며, ROB의 맨 앞(가장 오래된 명령)이 완료됐을 때만 순서대로 실제 레지스터·메모리에 반영(In-Order Commit)한다.
- 이렇게 커밋만 순서를 지키는 이유는 정합성 때문이다. 분기 예측이 틀렸거나 인터럽트가 발생하면, 아직 커밋되지 않은 ROB의 나머지 항목을 통째로 버리기만 하면 프로그램 상태가 항상 "마지막으로 순서대로 완료된 지점"으로 깔끔하게 복구된다.

### 구체 수치 — 명령어 윈도우 크기
- 실행을 기다리는 명령어를 얼마나 많이 동시에 들여다볼 수 있는지가 OoO의 성능을 좌우한다. 알려진 수치로 인텔 골든코브 세대의 ROB는 약 512개 항목, 애플 M1 계열은 약 600개 안팎의 항목을 동시에 관리한다고 알려져 있다 — 초기 OoO CPU(1990년대)의 수십 개 수준과 비교하면 자릿수가 다른 탐색 범위다. ROB가 클수록 "당장은 막혔지만 몇백 개 뒤에 있는 독립 명령어"까지 찾아내 실행할 수 있다.

### 역사와 비유
- 이 방식의 원조는 1967년 IBM System/360 Model 91에서 로버트 토마술로(Robert Tomasulo)가 부동소수점 연산 유닛의 병목을 풀기 위해 고안한 **토마술로 알고리즘**이다.
- **비유**: 리네이밍은 동명이인 환자 2명이 접수하면 병원 시스템이 내부 접수번호(P10, P11)를 따로 부여해 진료실이 엉키지 않게 하는 것이다.

## 연결 개념
- 010 슈퍼스칼라 — 다중 차선을 실제로 낭비 없이 채우기 위해 OoO와 반드시 결합되는 구조
- 013 ILP — OoO·리네이밍이 실행 단계에서 극대화하는 병렬성 목표치
- 008 파이프라인 해저드 — RAW·WAR·WAW 의존성 분류가 원래 정의된 선행 개념

# 📝 【답안용】 시험 답안 템플릿

> 목적: 시험장에서 25분에 그대로 쓰는 답안 양식. 

## 핵심 인사이트 (3줄 요약)

> 1. **본질**: 비순차 실행(OoO)은 컴파일러의 정적 순서에 얽매이지 않고, 런타임에 데이터 의존성이 풀린 명령어부터 동적으로 선행 실행하여 명령어 수준 병렬성(ILP)을 극대화하는 아키텍처다.
> 2. **가치**: 레지스터 리네이밍으로 가짜 의존성(WAR, WAW)을 제거하고, 긴 지연(Memory Load)을 가진 명령어 뒤의 독립적인 연산들을 스톨 없이 백그라운드 처리한다.
> 3. **판단 포인트**: 실행은 비순차(OoO)로 하되 최종 상태 반영(Commit)은 원래 순서(In-Order)로 강제하는 재정렬 버퍼(ROB)를 통해, 인터럽트와 분기 실패 시의 복구 정합성을 완벽히 보장한다.

## 출제 의도 및 답안 포인트

| 출제 의도 | 반드시 짚을 핵심 | 감점 회피 포인트 |
|:---|:---|:---|
| 파이프라인 한계 극복을 위한 동적 스케줄링 메커니즘 이해 | 예약 정거장(RS), 재정렬 버퍼(ROB), 레지스터 리네이밍(RAT) | OoO가 만능인 것처럼 적고 In-Order Commit의 필수 이유(정합성)를 누락 |
| 데이터 해저드의 근본 원인 해소 원리 파악 | 진성 의존성(RAW) 대기 vs 가성 의존성(WAR/WAW) 제거 | 세 가지 해저드를 구별 없이 리네이밍이 전부 해결한다고 적는 오류 |

> 요약: OoO의 성능 향상 원리(실행 순서 재배치)와 레지스터 리네이밍의 역할(가성 의존성 타파)을 유기적으로 연결해야 한다.

## Ⅰ. 개요 및 필요성

- 정의: 프로세서가 명령어의 원래 순서를 무시하고 연산 준비가 완료된 명령어부터 먼저 실행하는 동적 파이프라인 스케줄링 기법
- 배경: 슈퍼스칼라 구조에서 하나의 명령어 스톨(Stall)이 전체 다중 파이프라인의 유휴 상태를 유발하는 순차 실행(In-Order)의 한계
- 필요성: 레지스터 재사용으로 인한 가성 데이터 해저드(WAR, WAW)를 하드웨어적으로 제거하여 숨겨진 병렬성(ILP) 인출 필요

## Ⅱ. 구조 및 구성요소 (동적 스케줄링 아키텍처)

```text
[OoO 마이크로 아키텍처 실행 흐름]
(1. In-Order Fetch/Decode) -> [ RAT (리네이밍) ] -> [ ROB 할당 (커밋 대기표) ]
-> [ RS (예약 정거장) ] 대기 -> 데이터 준비 시 (2. Out-of-Order Execute) 
-> [ ROB (재정렬 버퍼) ] 에서 순서 조립 -> (3. In-Order Commit)
```

| 구성요소 | 핵심 역할 | 상세 하위 요소 / 특징 |
|:---|:---|:---|
| RAT (Register Alias Table) | 논리 레지스터(ISA)를 물리 레지스터 파일(PRF)로 동적 매핑 | 레지스터 리네이밍의 주체 (WAR/WAW 제거) |
| RS (Reservation Station) | ALU 등 유닛 앞에서 명령어가 피연산자 준비를 기다리는 대기소 | 데이터가 모두 모이면 H/W가 즉시 실행 유닛으로 발송(Issue) |
| ROB (Re-Order Buffer) | 비순차 완료된 결과를 임시 보관하여 원래 프로그램 순서대로 정렬 | 분기 실패 시 롤백(Rollback) 및 정확한 예외 처리 보장 |
| 물리 레지스터 파일 | 논리 레지스터 수(예: 16개)보다 훨씬 많은 실제 하드웨어 레지스터 | 수백 개의 명령어를 동시에 리네이밍하여 담을 수 있는 공간 |

> 요약: 인출(In)과 커밋(Out)은 순서를 지키고, 중간의 실행만 비순차(OoO)로 처리하여 성능과 정합성을 모두 잡은 구조다.

## Ⅲ. 동작원리 및 흐름도 (토마술로 알고리즘 기반)

```text
[OoO 파이프라인 단계별 상태 천이]
IF/ID (순차 인출) -> Rename (가짜 의존성 제거) -> Dispatch (RS, ROB 등록)
-> Issue (데이터 준비 시 비순차 실행) -> Write Result (결과 포워딩)
-> Commit (ROB 최상단 도달 시 순차 기록)
```

| 단계 | 제어 주체 | 처리 내용 (파이프라인 통과 조건) |
|:---:|:---|:---|
| 1 | 인출/디스패치 | 순서대로 명령어를 읽어 RAT를 통해 논리 레지스터 이름을 물리 레지스터로 변환하고 RS와 ROB에 할당 |
| 2 | 예약 대기 (Wait) | RS 내에서 피연산자가 모두 계산되어 도달할 때까지 대기 (데이터 버스 감시) |
| 3 | 비순차 실행 (OoO) | 원래 순서와 무관하게 데이터가 준비된 명령어부터 실행 유닛을 선점하여 연산 및 결과 Broadcast |
| 4 | 순차 커밋 (Commit)| ROB의 제일 오래된(Head) 명령어가 연산을 마쳤을 때만 최종 레지스터/메모리에 영구 기록 및 물리 레지스터 회수 |

> 요약: RS는 실행 대기를 관리하고, ROB는 결과의 순차 반영을 관리하는 두 축으로 OoO가 완성된다.

## Ⅳ. 핵심 메커니즘: 레지스터 리네이밍 (가성 의존성 극복)

| 의존성 유형 | 발생 원인 | OoO 처리 및 리네이밍 결과 | 성능 영향 (병목 극복) |
|:---|:---|:---|:---|
| RAW (Read After Write) | 진성 의존성: 앞 명령어 결과를 뒤에서 입력으로 사용 | 리네이밍 불가, RS에서 앞 결과가 연산될 때까지 실제 대기 | 데이터 포워딩(Bypass) 네트워크로 스톨 최소화 |
| WAR (Write After Read) | 반의존성: 앞 명령이 읽기 전에 뒤 명령이 덮어쓰려 함 | 뒤 명령에 새로운 물리 레지스터 할당 (이름 분리) | 의존성 소멸, 즉시 동시 실행 가능 |
| WAW (Write After Write) | 출력 의존성: 앞/뒤 명령이 같은 레지스터에 기록하려 함 | 각 명령어에 서로 다른 물리 레지스터 할당 (이름 분리) | 의존성 소멸, 즉시 동시 실행 가능 |

> 요약: 프로그래머(컴파일러)가 레지스터 부족으로 재사용한 변수 이름(가성 의존성)을, 하드웨어가 넉넉한 물리 레지스터를 활용해 투명하게 해체하는 것이 리네이밍이다.

## Ⅴ. 심화 비교 및 성능 지표 판단

| 비교 축 | 순차 실행 (In-Order Execution) | 비순차 실행 (Out-of-Order Execution) | 아키텍처 판단 기준 |
|:---|:---|:---|:---|
| 스톨 처리 | 1개의 스톨이 전체 파이프라인 멈춤 | 스톨 명령어를 우회하여 독립 명령어 선행 처리 | ILP(명령어 수준 병렬성) 한계 돌파 |
| 하드웨어 면적 | 제어 로직 단순, 전력 소모 적음 | RAT, RS, ROB 등 상태 추적 회로로 면적/전력 급증 | 폼팩터 전력(TDP) 내 수용 여부 |
| 분기/예외 복구 | 순차 실행이므로 문제 지점에서 단순 중단 | ROB를 버리고(Flush) 리네이밍 매핑 테이블(RAT) 복원 | 정교한 상태 저장(Checkpointing) 필수 |

> 요약: OoO는 하드웨어 복잡도(O(n²))라는 막대한 트랜지스터 자본을 대가로, 메모리 지연(Memory Wall)을 뒤에서 조용히 흡수해버리는 현대 CPU 성능의 핵심이다.

| 점검 항목 | 목표 기준 | 측정 방법 |
|:---|:---|:---|
| 명령어 윈도우 크기 | ROB 크기 200~400개 이상 유지 (병렬성 탐색 범위) | 마이크로 아키텍처 다이어그램 분석 |
| IPC (사이클 당 명령) | 이론치(슈퍼스칼라 Way 수)의 70% 이상 달성 방어 | SPECint/fp 벤치마크 워크로드 실행 |

## Ⅵ. 실무 적용 및 결론

**적용 방안 3개:**
1. 메모리 레이턴시 은닉: 캐시 미스(Cache Miss)로 인해 Load 명령어가 수백 사이클(RAM 접근) 지연될 때, OoO를 활용해 그 뒤에 있는 무관한 수백 개의 ALU 연산들을 멈춤 없이 100% 처리량으로 가동
2. 초광폭(Ultra-Wide) 코어 설계 연계: Apple M시리즈 등 최신 칩셋에서 프론트엔드 폭(8-Way 이상)과 수백 개의 ROB/RS를 결합하여, 클럭 주파수를 낮춰 배터리를 아끼면서도 데스크톱을 압도하는 스루풋 달성
3. 하드웨어 취약점(Spectre) 패치 융합: 투기적 비순차 실행 시 남는 마이크로 아키텍처 흔적(캐시 라인 상태)을 악용한 부채널 공격 방어를 위해, 예측 실패 시 캐시 상태까지 롤백하거나 분리하는 격리(Isolation) 메커니즘 칩 설계 반영

**결론 (2줄):**
- 기술사 판단: 비순차 실행(OoO)과 레지스터 리네이밍은 소프트웨어적 컴파일 최적화의 한계를 하드웨어가 동적으로 돌파한 토마술로(Tomasulo) 알고리즘의 위대한 승리다.
- 향후 방향: 트랜지스터 밀도가 한계에 다다르면서 OoO 윈도우(ROB 크기)를 무작정 늘리는 방식은 끝나가고 있으며, 향후 AI 워크로드를 위해 NPU와 같은 도메인 특화 아키텍처(DSA)로 병렬 처리를 분담하는 하이브리드 진화가 가속된다.
