## Ⅰ. 개요
- **정의**: 데이터 의존성이 해소된 명령어를 프로그램 순서와 무관하게 실행하고, 물리 레지스터 재매핑으로 거짓 의존성을 제거하는 기법
- **배경/필요성**: 순서 실행에서는 선행 명령어의 지연이 후속 독립 명령어까지 정지시키므로, 실행 유닛 활용률을 높이려면 동적 재배치가 필요함
- **비유**: 음식점에서 조리 시간이 긴 주문을 기다리지 않고, 준비 가능한 다른 주문을 먼저 내보내는 것과 유사함

| 출제 의도 | 반드시 짚을 핵심 | 감점 회피 포인트 |
|:---|:---|:---|
| 동적 스케줄링 원리와 의존성 유형 구분 | RAW(진짜)·WAR/WAW(거짓) 의존성 분류 | 레지스터 리네이밍이 WAR/WAW만 제거한다는 점 명시 |

> 요약: 하드웨어가 런타임에 명령어 순서를 재배치하여 파이프라인 유휴를 줄이는 기법임

## Ⅱ. 구성요소
```text
  Fetch --> Decode --> Rename --> Issue Queue
                        |              |
                        v              v
                  +----------+   +-----------+
                  | RAT      |   | Scheduler |
                  | (Rename  |   | (Ready    |
                  |  Table)  |   |  Check)   |
                  +----------+   +-----------+
                                       |
                                       v
                                 +----------+
                                 | Exec FU  |
                                 +----------+
                                       |
                                       v
                                 +----------+
                                 | ROB      |
                                 | (Reorder |
                                 |  Buffer) |
                                 +----------+
                                       |
                                       v
                                    Commit
```

| 구성요소 | 설명 | 비유 |
|:---|:---|:---|
| RAT (Register Alias Table) | 논리 레지스터를 물리 레지스터에 매핑하여 거짓 의존성을 제거함 | 손님 이름 대신 대기 번호를 부여하는 접수대 |
| Issue Queue | 오퍼랜드가 준비된 명령어를 선택하여 실행 유닛에 발행함 | 재료가 갖춰진 주문을 먼저 조리대에 올리는 주방장 |
| ROB (Reorder Buffer) | 비순서 실행 결과를 프로그램 순서대로 커밋하여 정확한 상태를 보장함 | 완성된 음식을 주문 순서대로 정렬하는 배식대 |
| 물리 레지스터 파일 | 논리 레지스터보다 많은 물리 레지스터를 제공하여 리네이밍 공간을 확보함 | 대기 번호표의 총 수량 |

> 요약: RAT로 거짓 의존성을 제거하고, ROB로 순서 커밋을 보장하는 구조임

## Ⅲ. 절차
```text
  Rename          Dispatch        Execute         Commit
  (매핑 변환)     (큐 대기)       (비순서 실행)   (순서 반영)
     |               |               |               |
     +---물리Reg----->+---Ready?------>+---결과기록---->+
  논리->물리       Issue Queue     기능 유닛       ROB Head
  RAT 갱신        오퍼랜드 감시    데이터 전달     아키텍처 상태
```
- 1단계: 디코드된 명령어의 논리 레지스터를 RAT를 통해 물리 레지스터로 재매핑함
- 2단계: 리네이밍된 명령어를 Issue Queue에 삽입하고, 오퍼랜드 준비 상태를 감시함
- 3단계: 오퍼랜드가 모두 준비된 명령어를 프로그램 순서와 무관하게 기능 유닛에서 실행함
- 4단계: ROB 헤드에서 가장 오래된 명령어부터 순서대로 아키텍처 상태에 커밋함

> 요약: 리네이밍 후 준비된 것부터 실행하되, 커밋은 프로그램 순서를 유지함

## Ⅳ. 문제점
- 하드웨어 복잡도 증가: RAT·ROB·Issue Queue 등 부가 구조로 트랜지스터 수가 순서 실행 대비 40~60% 증가함 — 칩 면적·전력 소모 상승
- 에너지 비효율: 투기 실행(speculative execution) 중 분기 예측 실패 시 실행 결과 폐기로 전력이 낭비됨 — 배터리 기반 기기에서 치명적
- ROB 크기 제약: ROB 엔트리 수가 명령어 윈도우 크기를 제한하여 추출 가능한 ILP(013 참조)에 상한이 존재함 — 메모리 지연이 긴 워크로드에서 성능 정체

> 요약: 동적 스케줄링의 대가로 면적·전력·ILP 상한 문제가 발생함

## Ⅴ. 개선방안
1. 단기: 클러스터드 실행 유닛 분할로 배선 길이와 단위 구조 복잡도를 줄여 면적·전력 절감
2. 중기: 선택적 투기 실행(confidence-based speculation) 도입으로 저신뢰 분기의 투기를 억제하여 에너지 낭비 감소
3. 장기: ROB 엔트리 확대와 계층적 스케줄링 윈도우 결합으로 ILP 추출 범위 확장

> 요약: 클러스터링·선택적 투기·윈도우 확장으로 OoOE의 비용 대비 효과를 개선함

## Ⅵ. 전망
- 발전 방향: AI 추론 워크로드의 불규칙 분기 패턴 증가로, OoOE의 동적 스케줄링 중요성이 지속 확대됨
- 기술사적 판단: VLIW(011 참조)의 정적 접근과 상호 보완적이며, 범용 CPU에서는 OoOE가 주류를 유지함
- 기술사 제언: 전력 제약 환경에서는 OoOE 깊이와 순서 실행 코어 수 간 트레이드오프를 폴락의 법칙(015 참조) 기반으로 판단할 필요가 있음
