## Ⅰ. 개요
- **정의**: PCIe 물리 계층 위에서 CPU·가속기·메모리 간 캐시 일관성을 지원하는 개방형 인터커넥트 표준
- **배경/필요성**: CPU 소켓 핀 수의 물리적 한계로 단일 서버에 장착 가능한 DRAM 슬롯 수가 제한됨. CPU와 GPU 간 메모리를 복사(Copy)하는 방식은 지연과 전력 낭비를 유발하므로, 하드웨어 수준에서 캐시 일관성을 보장하며 메모리를 공유하는 인터커넥트가 요구됨
- **비유**: 각자 별도 스케치북을 쓰던 학생들에게 공용 화이트보드를 제공하되, 동시에 같은 곳을 써도 내용이 엉키지 않도록 관리해 주는 시스템

| 출제 의도 | 반드시 짚을 핵심 | 감점 회피 포인트 |
|:---|:---|:---|
| 차세대 인터커넥트 표준 이해 | 3개 서브 프로토콜(CXL.io/.cache/.mem)의 역할 구분 | PCIe와 물리 계층은 공유하지만 논리 프로토콜은 별도이므로 PCIe 확장판이 아님 |

> 요약: CXL은 PCIe 물리 계층을 공유하면서 3개 프로토콜로 캐시 일관성 기반 메모리 공유를 실현하는 인터커넥트임

## Ⅱ. 구성요소
```text
+------------------+                          +----------------------+
|    Host CPU      |                          | CXL Device           |
|  +------------+  |   CXL.cache              | (가속기 / 메모리)     |
|  |   Cache    | <+-------------------------+> Device Cache         |
|  +------------+  |                          +----------------------+
|  +------------+  |   CXL.mem                | +------------------+ |
|  |   Memory   | <+-------------------------+> | Attached Memory | |
|  +------------+  |                          | +------------------+ |
+------------------+                          +----------------------+
        |                  CXL.io                       |
        +------------------+----------------------------+
                           |
                   PCIe PHY Layer
```

| 구성요소 | 설명 | 비유 |
|:---|:---|:---|
| CXL.io | 장치 발견·열거·에러 보고·인터럽트 등 기본 연결 관리, PCIe 프로토콜과 유사 | 건물 출입 관리 시스템 |
| CXL.cache | 디바이스가 호스트 CPU 캐시에 Load/Store로 접근, 하드웨어가 일관성 자동 유지 | 공용 칠판에 쓴 내용을 자동 동기화하는 규칙 |
| CXL.mem | 호스트 CPU가 디바이스 측 메모리를 로컬 NUMA 노드처럼 인식하여 직접 Load/Store 수행 | 옆 건물 서재를 내 책장처럼 쓸 수 있는 통로 |
| PCIe PHY Layer | CXL의 물리 전송 계층, PCIe 5.0(32GT/s) 또는 6.0(64GT/s) 규격을 그대로 활용 | 이미 깔린 고속도로 위에 새 교통 규칙을 적용 |

> 요약: CXL.io·CXL.cache·CXL.mem 3개 프로토콜이 PCIe 물리 계층 위에서 동작함

## Ⅲ. 절차
```text
장치 열거(CXL.io) -> 캐시 일관성 수립(CXL.cache) -> 메모리 맵핑(CXL.mem) -> 데이터 공유 연산
```
- 1단계: 호스트 부팅 시 CXL.io가 연결된 디바이스를 열거하고 타입(Type 1/2/3)을 식별함
- 2단계: Type 2 디바이스(가속기+메모리)의 경우 CXL.cache를 통해 호스트-디바이스 간 캐시 스누프 경로를 수립함
- 3단계: CXL.mem이 디바이스 측 메모리를 호스트 물리 주소 공간에 NUMA 노드로 맵핑하여 Load/Store 접근을 가능하게 함
- 4단계: 호스트와 디바이스가 동일 메모리 영역을 캐시 일관성 하에 공유하며 연산을 수행함

> 요약: 장치 열거 -> 캐시 경로 수립 -> 메모리 맵핑 -> 일관성 기반 공유 연산 순서로 동작함

## Ⅳ. 문제점
- NUMA 지연 격차: CXL 연결 메모리는 로컬 DDR 대비 접근 지연이 2~3배 높음 — 지연 민감 워크로드에서 성능 저하가 발생함
- 스위치/패브릭 비용: CXL 2.0 풀링 및 3.0 패브릭 구성 시 전용 스위치 장비가 요구됨 — 초기 도입 비용이 상승함
- 보안 격리 미비: 다수 호스트가 메모리 풀을 공유하므로 테넌트 간 메모리 격리(Isolation) 메커니즘이 미성숙 — 멀티테넌트 환경에서 데이터 유출 위험이 존재함

> 요약: NUMA 지연·스위치 비용·보안 격리 미비가 CXL 확산의 3대 과제임

## Ⅴ. 개선방안
1. 단기: OS 커널의 NUMA 티어링 정책을 개선하여 핫 데이터를 로컬 DDR에, 콜드 데이터를 CXL 메모리에 자동 배치하여 지연 영향을 최소화함
2. 중기: CXL 스위치를 SoC 수준으로 집적하고 PCIe 6.0 기반으로 전환하여 풀링 구성 비용과 레이턴시를 동시 절감함
3. 장기: CXL 3.0 규격의 하드웨어 기반 메모리 암호화·접근 제어(IDE) 기능을 확장하여 멀티테넌트 격리를 보장함

> 요약: NUMA 티어링 최적화 -> 스위치 SoC 집적 -> 하드웨어 기반 격리 확장 순으로 과제를 해소함

## Ⅵ. 전망
- 발전 방향: CXL 3.0 패브릭을 통해 랙 단위 메모리 풀링(036 참조)이 실현되며, 컴포저블 인프라(Composable Infrastructure)로 진화함
- 기술사적 판단: OpenCAPI·CCIX 등 경쟁 표준이 CXL로 통합되어 사실상 표준(de facto standard)이 확립됨
- 기술사 제언: 차세대 서버 아키텍처 설계 시 CXL 지원 여부를 필수 평가 항목으로 포함하고, PNM(034 참조) 가속기와의 결합 시나리오를 병행 검토할 필요
