# 📖 【암기용】 개념 완전 이해

> 목적: 펌웨어 보안 취약점을 처음 봐도 왜 OS 보안보다 아래 계층이 더 위험한지 이해하게 만든다. 시험 답안 양식이 아니라, 이해를 위한 친절한 설명이다.

## 한눈에
- **개요**: BIOS/UEFI, BMC(Baseboard Management Controller), 디스크 컨트롤러 등 하드웨어를 직접 제어하는 저수준 소프트웨어(펌웨어)에 존재하는 취약점과 그로 인한 영속적 침해 위험
- **왜 필요한가**: OS를 재설치하거나 디스크를 교체해도 펌웨어에 심어진 악성코드는 SPI flash에 남아 재감염을 반복시킨다. 백신·EDR은 OS 위 계층만 보므로 펌웨어 계층은 별도 방어 체계가 필요하다.
- **핵심 직관**: 건물의 CCTV(OS 보안)를 아무리 강화해도 건물 기초 콘크리트(펌웨어)에 도청장치가 박혀 있으면 리모델링을 해도 도청이 계속되는 것과 같다.

## 깊이 이해
- **배경·문제의식**: UEFI가 BIOS를 대체하며 펌웨어가 네트워크 드라이버, 그래픽 처리 등 복잡한 기능을 갖게 됐고, 코드량 증가가 공격 표면을 넓혔다.
- **작동 원리**: 부팅 시 CPU 마이크로코드가 첫 코드 블록을 실행하기 전에 Intel Boot Guard/AMD Platform Secure Boot가 퓨즈에 새긴 공개키 해시로 초기 부트블록 서명을 검증하고, 이후 UEFI Secure Boot가 Platform Key(PK) -> Key Exchange Key(KEK) -> db/dbx 순서로 부트로더 서명을 검증하는 체인을 형성한다.
- **비유**: 신분증 검사가 건물 로비(Secure Boot)에서만 이뤄지고 지하 배전실(SPI flash, BMC) 출입은 검사하지 않으면, 배전실을 통해 몰래 들어온 사람이 로비 검사를 매번 무력화할 수 있다.
- **구체 예시**: LoJax(2018)는 SPI flash 쓰기 보호가 풀린 시스템에서 UEFI 이미지를 조작해 OS 재설치·디스크 교체 후에도 재감염을 유지한 최초의 실제 UEFI 루트킷 사례다. BlackLotus(CVE-2023-24932)는 서명은 유효하지만 취약한 부트로더 바이너리를 실행시켜 Secure Boot가 켜진 상태에서도 우회에 성공한 사례다.
- **흔한 오해·주의점**: "Secure Boot를 켜면 펌웨어가 안전하다"는 오해다. Secure Boot는 부트로더 서명만 검증하므로, SPI flash 쓰기 보호 미흡, BMC 별도 펌웨어, 이미지 파싱 취약점(예: LogoFAIL) 등은 별도로 통제해야 한다.

## 연결 개념
- Secure Boot — 부트로더 서명 검증 체인의 최상위 통제
- ARM TrustZone — 실행 중 격리된 보안 실행환경(Secure World)
- HSM(Hardware Security Module) — 펌웨어 서명 키를 물리적으로 격리 보관하는 장치
- JTAG — 디버깅 인터페이스이자 펌웨어 물리 공격 경로

# 📝 【답안용】 시험 답안 템플릿

> 목적: 시험장에서 25분에 그대로 쓰는 답안 양식. 작성방식(추상표현 금지·수치·도식·문제유형 전환)을 엄격히 지킨다.
> 핵심: 펌웨어 취약점 답안은 공격 표면(부트체인·SPI flash·BMC), 실제 사례, NIST SP 800-193 3원칙(Protect·Detect·Recover)을 함께 제시한다.

## 핵심 인사이트 (3줄 요약)

> 1. **본질**: 펌웨어 보안 취약점은 OS 하위 계층(UEFI, BMC, 디스크 컨트롤러) 코드가 변조되어 OS 재설치로도 제거되지 않는 영속적 침해를 허용하는 문제이다.
> 2. **가치**: Boot Guard·Secure Boot·TPM 측정 부팅을 계층적으로 결합하면 부팅 각 단계의 무결성을 사전에 검증해 부트킷 실행을 차단할 수 있다.
> 3. **판단 포인트**: 서명 검증 유무가 아니라 SPI flash 쓰기 보호, 롤백 방지, BMC 분리 관리까지 포함했는지가 실질적 방어 수준을 가른다.

## 출제 의도 및 답안 포인트

| 출제 의도 | 반드시 짚을 핵심 | 감점 회피 포인트 |
|:---|:---|:---|
| 부팅 체인 취약점 구조 이해 확인 | Boot Guard, Secure Boot, PK/KEK/db/dbx 체인 | Secure Boot만 언급하고 하드웨어 root of trust 누락 |
| 실제 공격 사례 인식 확인 | LoJax, BlackLotus, LogoFAIL 등 구체 사례와 우회 원리 | "펌웨어가 취약하다"는 추상 서술만 나열 |
| 표준 기반 대응 체계 이해 확인 | NIST SP 800-193 Protect/Detect/Recover, RTU/RTD/RTRec | 대응 방안을 백신·안티멀웨어 수준으로만 서술 |

> 요약: 이 문제는 취약점 나열이 아니라 부팅 체인의 어느 지점이 뚫렸고 어떤 root of trust로 막는지 구조적으로 설명해야 한다.

## Ⅰ. 개요 및 필요성

- 개요: BIOS/UEFI·BMC 등 하드웨어 제어 저수준 코드의 변조·서명우회로 인한 영속적 보안 침해 위험
- 배경: UEFI 도입으로 펌웨어 코드량과 기능(네트워크, 그래픽 파싱)이 늘며 공격 표면이 확대됨
- 필요성: OS 계층 백신·EDR은 펌웨어를 보지 못하므로 부팅 이전 단계의 무결성 검증 체계가 별도로 필요함

---

## Ⅱ. 구조 및 구성요소

```text
Power On -> CPU Microcode/ACM
  -> Boot Guard(HW Root of Trust) 검증
  -> UEFI Firmware(PK/KEK/db/dbx) Secure Boot 검증
  -> Bootloader -> OS Kernel
BMC/EC 펌웨어 (독립 부팅 경로) -> SPI Flash 저장
```

| 구성요소 | 역할 | 특이사항 |
|:---|:---|:---|
| Boot Guard/PSB | 초기 부트블록 서명을 퓨즈 공개키로 검증 | CPU 내장, OS 개입 불가 |
| UEFI Secure Boot | 부트로더·드라이버 서명 검증 | PK/KEK/db/dbx 4단 체인 |
| SPI Flash | 펌웨어 이미지 저장소 | 쓰기 보호(BIOS_CNTL) 필요 |
| BMC/EC 펌웨어 | 서버 원격관리·임베디드 컨트롤러 별도 펌웨어 | 메인 UEFI와 별도 공격 경로 |
| TPM | 부팅 단계 해시를 PCR에 기록 | 원격 증명(Attestation) 근거 |

> 요약: 펌웨어 보안은 CPU 내장 root of trust, UEFI 서명 체인, SPI flash 보호, BMC 분리 관리가 계층적으로 결합되어야 완성된다.

---

## Ⅲ. 동작원리 및 흐름도

```text
전원 인가 -> Boot Guard ACM 검증(실패 시 정지)
  -> UEFI 초기화 -> db 서명으로 부트로더 검증
  -> TPM PCR 확장(측정값 기록)
  -> OS 부팅 -> 원격 서버가 PCR값으로 무결성 검증(Remote Attestation)
```

| 단계 | 처리 내용 | 검증 기준 |
|:---:|:---|:---|
| 1 | CPU 마이크로코드가 초기 부트블록 서명 확인 | 퓨즈 공개키 해시 일치 |
| 2 | UEFI가 db 인증서로 부트로더 서명 확인 | dbx 폐기목록 미포함 |
| 3 | 각 부팅 단계 해시를 TPM PCR에 확장 기록 | PCR 0~7 값 |
| 4 | 원격 서버가 PCR quote로 무결성 검증 | Remote Attestation 성공 여부 |

> 요약: 펌웨어 무결성은 부팅 각 단계마다 서명 검증과 TPM 측정을 반복해 최종적으로 원격 증명으로 확인한다.

---

## Ⅳ. 특징

| 구분 | 내용 | 판단 포인트 |
|:---|:---|:---|
| 장점 | 하드웨어 root of trust로 OS 계층 탐지 이전에 변조를 차단 | Boot Guard 미지원 구형 장비는 적용 불가 |
| 한계 | 서명 검증은 알려진 취약 바이너리(서명은 유효)의 논리적 결함까지 막지 못함 | BlackLotus류 우회 사례 존재 |
| 비교 포인트 | Secure Boot(부팅 시 1회 검증) vs Measured Boot(매 단계 기록 후 사후 증명) | 실시간 차단이 필요하면 Secure Boot, 사후 검증이 필요하면 Measured Boot |

> 요약: Secure Boot는 실행을 막는 예방 통제, TPM 기반 Measured Boot는 사후 확인 통제로 역할이 다르다.

## Ⅴ. 심화 비교 및 적용 판단

| 비교 축 | 기존/대안 | 본 키워드 | 선택 기준 |
|:---|:---|:---|:---|
| 구조 | OS 계층 백신·EDR 중심 | 부팅 이전 계층 root of trust 중심 | 영속적 침해 우려 시 펌웨어 계층 통제 추가 |
| 비용/성능 | 추가 통제 없음 | Boot Guard 퓨즈, TPM 모듈, 펌웨어 서명 인프라 비용 | 서버·금융 단말 등 고위험군 우선 적용 |
| 운영/위험 | 펌웨어 업데이트 서명 미검증 | 캡슐 업데이트(UEFI Capsule) 서명·롤백 방지 카운터 적용 | 다운그레이드 공격 방지 필요 시 필수 |

> 요약: 일반 사무용 PC보다 서버·금융단말·통신장비처럼 영속적 침해 피해가 큰 자산에 펌웨어 계층 통제를 우선 적용한다.

| 리스크 | 원인 | 대응 방안 | 확인 지표 |
|:---|:---|:---|:---|
| SPI flash 무단 쓰기 | BIOS_CNTL 쓰기 보호 미설정 | 쓰기 보호 레지스터 상시 활성화 | 펌웨어 해시 변경 이벤트 수 |
| 서명 우회 실행 | 유효 서명이지만 취약한 바이너리 로드 | dbx 갱신, 취약 바이너리 즉시 폐기 등록 | dbx 최신화 주기 |
| BMC 별도 침해 | BMC 펌웨어 패치 누락 | BMC 전용 패치 주기 관리, 관리망 분리(Out-of-Band 격리) | BMC 펌웨어 버전 점검 주기 |

> 요약: 펌웨어 리스크는 서명 검증만이 아니라 쓰기 보호, dbx 최신화, BMC 분리 관리로 함께 통제해야 한다.

| 점검 항목 | 목표 기준 | 측정 방법 |
|:---|:---|:---|
| 부팅 무결성 | PCR 기반 원격 증명 실패율 0건 | Remote Attestation 로그 |
| 펌웨어 최신성 | 알려진 CVE 대응 패치 적용 주기 30일 이내 | 자산관리·패치관리 시스템 |
| 쓰기 보호 | SPI flash 쓰기 보호 활성 비율 100% | 펌웨어 설정 점검 스크립트 |

> 요약: 도입 효과는 원격 증명 성공률, 패치 적용 주기, 쓰기 보호 활성 비율로 판단한다.

## Ⅵ. 실무 적용 및 결론

**적용 방안 3개 (필수 — 단계별 또는 항목별):**
1. 단기: Boot Guard/PSB, UEFI Secure Boot, SPI flash 쓰기 보호 설정 상태를 자산 전수 점검함
2. 중기: TPM 기반 Measured Boot와 원격 증명 체계를 도입해 부팅 무결성을 상시 모니터링함
3. 장기: NIST SP 800-193 기준 RTU(업데이트)·RTD(탐지)·RTRec(복구) 3대 root of trust를 서버·통신장비 조달 요건에 반영함

**결론 (2줄):**
- 기술사 판단: 일반 단말은 Secure Boot 기본 적용, 서버·금융·통신 인프라는 Measured Boot·원격 증명·BMC 분리 관리까지 확장 적용함
- 향후 방향: 공급망 단계 펌웨어 서명(SBOM 연계)과 자동 복구(RTRec) 체계로 침해 후 원복 시간을 단축하는 방향으로 발전함
