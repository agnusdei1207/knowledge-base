# 📖 【암기용】 개념 완전 이해

> 목적: HSM을 처음 봐도 소프트웨어 키 저장과 무엇이 다른지 이해하게 만든다. 시험 답안 양식이 아니라, 이해를 위한 친절한 설명이다.

## 한눈에
- **개요**: 암호 키 생성·저장·연산을 물리적으로 격리된 전용 하드웨어 안에서만 수행해 키 유출을 막는 변조 방지(tamper-resistant) 장치
- **왜 필요한가**: 서버 메모리나 파일에 키를 두면 루트 권한 탈취·메모리 덤프로 키가 유출된다. HSM은 키가 장치 밖으로 평문 상태로 나가지 않도록 물리적 경계를 만든다.
- **핵심 직관**: 은행 금고와 같다. 돈(키)은 금고 밖으로 나가지 않고, 금고 안에서 계산(서명·암호화)만 수행한 결과값만 밖으로 내보낸다.

## 깊이 이해
- **배경·문제의식**: PKI 루트 CA 키, 코드 서명 키, 결제 PIN 키처럼 유출 시 피해가 큰 키는 소프트웨어 저장으로는 감사 요구사항(FIPS 140-2/3, PCI HSM)을 충족하지 못한다.
- **작동 원리**: 애플리케이션은 PKCS#11, KMIP 같은 표준 API로 HSM에 연산을 요청하고, HSM 내부 보안 프로세서가 키를 꺼내지 않은 채 서명·암복호화만 수행해 결과만 반환한다.
- **비유**: 열쇠공에게 열쇠(키) 자체를 주지 않고, "이 문서에 도장을 찍어달라"고 요청만 하면 도장 찍힌 결과만 받는 것과 같다.
- **구체 예시**: 루트 CA는 개인키를 FIPS 140-2 Level 3 HSM에 저장하고, 인증서 서명 요청이 오면 HSM 내부에서만 개인키로 서명 연산을 수행한 뒤 서명값만 반환한다. 물리적 개봉 시도가 감지되면 HSM은 내부 키를 즉시 영지화(zeroization)한다.
- **흔한 오해·주의점**: "HSM이 있으면 애플리케이션 로직 취약점도 막아준다"는 오해다. HSM은 키 격리만 보장하며, API 호출 권한 관리·접근통제는 별도로 설계해야 한다.

## 연결 개념
- TPM(Trusted Platform Module) — 단말 내장형 저비용 보안 칩, HSM보다 처리량 낮음
- PUF — 물리적 특성으로 키를 유도하는 원리, 일부 HSM/보안칩에 결합
- Secure Boot·펌웨어 보안 — 부팅 체인 무결성과 HSM 키 보호는 상호 보완 관계
- ARM TrustZone — 프로세서 내 격리 실행환경으로 HSM과 유사한 목적을 소프트웨어/하드웨어 혼합으로 구현

# 📝 【답안용】 시험 답안 템플릿

> 목적: 시험장에서 25분에 그대로 쓰는 답안 양식. 작성방식(추상표현 금지·수치·도식·문제유형 전환)을 엄격히 지킨다.
> 핵심: HSM 답안은 키 격리 원리, FIPS 140-2/3 등급, PKCS#11 연동 구조, TPM과의 차이를 함께 제시한다.

## 핵심 인사이트 (3줄 요약)

> 1. **본질**: HSM은 키를 물리적으로 격리된 전용 하드웨어 안에서만 생성·저장·연산하도록 강제하는 변조 방지 장치이다.
> 2. **가치**: 루트 권한 탈취나 메모리 덤프가 발생해도 키 원본이 장치 밖으로 노출되지 않아 PKI·결제 시스템의 신뢰 기반이 유지된다.
> 3. **판단 포인트**: FIPS 140-2/3 등급(Level 1~4)과 처리량(TPS), 네트워크 연결형(Network HSM) vs 서버 내장형(PCIe HSM) 여부로 도입 형태를 선택한다.

## 출제 의도 및 답안 포인트

| 출제 의도 | 반드시 짚을 핵심 | 감점 회피 포인트 |
|:---|:---|:---|
| 키 격리 구조 이해 확인 | 키가 HSM 밖으로 평문 노출되지 않는 원리, PKCS#11/KMIP | HSM을 단순 암호화 소프트웨어로 서술 |
| 인증 등급·표준 이해 확인 | FIPS 140-2/3 Level, PCI HSM | 등급 구분 없이 "보안 인증을 받았다"로만 서술 |
| 유사 기술과 구분 역량 확인 | TPM·소프트웨어 키스토어와 격리 수준·처리량 차이 | HSM과 TPM을 동일 개념으로 혼용 |

> 요약: 이 문제는 암호화 여부가 아니라 키가 물리적으로 어디에 격리되고 어떤 등급으로 검증됐는지를 확인한다.

## Ⅰ. 개요 및 필요성

- 정의: 암호 키 생성·저장·연산을 전용 변조 방지 하드웨어 내부로 한정하는 보안 장치
- 배경: 소프트웨어 키스토어는 OS 권한 탈취·메모리 덤프로 키 유출 위험이 있어 감사 요구사항을 충족하지 못함
- 필요성: 루트 CA, 코드 서명, 결제 PIN 등 유출 피해가 큰 키는 FIPS 140-2/3 인증 HSM으로 물리적 격리가 필요함

---

## Ⅱ. 구조 및 구성요소

```text
Application -> PKCS#11/KMIP API 호출
  -> HSM 보안 경계(Tamper-Resistant Enclosure)
     -> 보안 프로세서(키 연산 전용)
     -> 키 저장 영역(암호화된 키 blob)
     -> 변조 감지 센서(개봉 시 영지화)
  -> 연산 결과만 반환
```

| 구성요소 | 역할 | 특이사항 |
|:---|:---|:---|
| 보안 경계(Enclosure) | 물리적 개봉·프로빙 차단 | 개봉 감지 시 키 영지화 |
| 보안 프로세서 | 키를 꺼내지 않고 서명·암복호화 수행 | 전용 크립토 가속 회로 |
| API 계층 | 애플리케이션 연동 표준 | PKCS#11, KMIP, JCE |
| 키 관리 정책 | 키 생성·백업·순환 규칙 | M of N 쿼럼 인증 |
| 감사 로그 | 모든 키 연산 기록 | 컴플라이언스 증적 |

> 요약: HSM은 물리적 경계, 전용 연산 프로세서, 표준 API, 키 관리 정책, 감사 로그가 결합돼 키를 격리한다.

---

## Ⅲ. 동작원리 및 흐름도

```text
클라이언트 서명 요청 -> API 인증(역할 기반 접근통제)
  -> HSM 내부 키 조회(키 자체는 이동하지 않음)
  -> 보안 프로세서에서 서명 연산 수행
  -> 서명 결과 반환 -> 연산 로그 기록
```

| 단계 | 처리 내용 | 검증 기준 |
|:---:|:---|:---|
| 1 | 클라이언트가 API로 서명 요청 전송 | 인증서·역할 기반 권한 확인 |
| 2 | HSM이 요청 대상 키를 내부에서 조회 | 키 ID, 사용 목적(usage flag) 일치 |
| 3 | 보안 프로세서가 키를 꺼내지 않고 연산 수행 | 연산 시간, 알고리즘(RSA/ECDSA/AES) |
| 4 | 결과 반환 및 감사 로그 기록 | 로그 무결성, 타임스탬프 |

> 요약: HSM 연산은 키 이동 없이 내부에서만 처리되고 모든 요청이 감사 로그로 남는 흐름이다.

## Ⅳ. 특징

| 구분 | 내용 | 판단 포인트 |
|:---|:---|:---|
| 장점 | 루트 권한 탈취·메모리 덤프로도 키 원본 노출 불가 | FIPS 140-2/3 Level 3 이상 물리 보안 |
| 한계 | 도입·운영 비용이 높고 처리량이 소프트웨어 대비 제한적 | 결제 피크 TPS 대비 클러스터링 필요 |
| 비교 포인트 | TPM(단말 내장, 저비용, 낮은 처리량) vs HSM(네트워크 연결, 고비용, 고처리량) | 서버 인프라는 HSM, 단말 무결성 검증은 TPM |

> 요약: HSM은 고신뢰·고처리량 키 연산에, TPM은 단말 부팅 무결성·저비용 키 저장에 적합하다.

## Ⅴ. 심화 비교 및 적용 판단

| 비교 축 | 기존/대안 | 본 키워드 | 선택 기준 |
|:---|:---|:---|:---|
| 구조 | 소프트웨어 키스토어(파일·KMS 소프트웨어) | 물리적 격리 전용 하드웨어 | 키 유출 시 피해가 크면 HSM 필수 |
| 비용/성능 | 저비용, 무제한 확장 | 고비용, TPS 제한(클러스터로 보완) | 결제·루트 CA는 비용보다 격리 우선 |
| 운영/위험 | 접근통제 정책에 전적으로 의존 | 물리적 영지화로 이중 방어 | 규제 준수(PCI HSM, FIPS) 요구 시 HSM 선택 |

> 요약: 규제 준수와 키 유출 피해 규모가 큰 영역은 비용이 높아도 HSM을 선택한다.

| 리스크 | 원인 | 대응 방안 | 확인 지표 |
|:---|:---|:---|:---|
| 단일 장애점 | HSM 1대 장애 시 서명 서비스 중단 | 클러스터링, 액티브-액티브 구성 | HSM 가용성 99.9% 이상 |
| 키 백업 유출 | 백업 키 blob 관리 소홀 | M of N 쿼럼 인증, 백업 HSM 이원화 | 백업 접근 승인 로그 100% |
| API 권한 오남용 | 역할 분리 미흡 | RBAC, 이중 승인(Dual Control) 적용 | 권한 변경 승인 이력 |

> 요약: HSM 리스크는 물리 보안보다 가용성 설계와 API 권한 통제에서 주로 발생한다.

| 점검 항목 | 목표 기준 | 측정 방법 |
|:---|:---|:---|
| 인증 등급 | FIPS 140-2/3 Level 3 이상 유지 | 인증서 갱신 이력 |
| 처리 성능 | 피크 서명 TPS 대비 여유율 30% 이상 | HSM 벤치마크, 부하테스트 |
| 감사 추적 | 키 연산 로그 보존 및 무결성 100% | SIEM 연동 로그 검증 |

> 요약: 도입 효과는 인증 등급 유지, 처리 성능 여유율, 감사 로그 무결성으로 판단한다.

## Ⅵ. 실무 적용 및 결론

**적용 방안 3개 (필수 — 단계별 또는 항목별):**
1. 단기: 루트 CA·코드 서명·결제 PIN 등 고위험 키를 식별해 FIPS 140-2/3 인증 HSM으로 이전함
2. 중기: PKCS#11/KMIP 표준 API로 애플리케이션을 연동하고 RBAC·이중 승인 정책을 적용함
3. 장기: 액티브-액티브 HSM 클러스터와 Cloud HSM 이중화로 가용성 99.9% 이상을 확보함

**결론 (2줄):**
- 기술사 판단: 고신뢰·규제 준수가 필요한 키는 HSM, 단말 부팅 무결성 검증은 TPM으로 역할을 분리해 적용함
- 향후 방향: Cloud HSM(AWS CloudHSM, Azure Dedicated HSM) 확산과 PQC(양자내성암호) 알고리즘 지원으로 HSM 기능이 확장되는 방향으로 발전함
