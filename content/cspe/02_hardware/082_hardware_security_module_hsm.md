# 📖 【암기용】 개념 완전 이해

> 목적: HSM을 표준·규정·API 계층에서 이해하게 만든다. 물리적 탬퍼 메커니즘의 공학적 상세는 082_hsm_hardware_security_module.md가 담당하므로 여기서는 FIPS 인증 레벨, PKCS#11/KMIP, 키 라이프사이클, 컴플라이언스 요구사항에 집중한다.

## 한눈에
- **개요**: **HSM(Hardware Security Module)**은 암호 키의 생성·저장·연산을 **FIPS 140-2/140-3** 같은 국제 표준 인증 요건 위에서 통제하고, **PKCS#11·KMIP** 표준 API로만 접근을 허용하는 **키 관리(Key Management)** 전용 하드웨어다.
- **왜 필요한가**: 감사·규제 기관은 "암호화했다"는 주장만으로 통과시키지 않는다. 어떤 표준으로 어느 레벨까지 검증됐는지, 키가 어떤 API·수명주기 정책으로 통제되는지 증적을 요구한다. HSM은 이 증적을 표준화된 형태로 제공하는 장치다.
- **핵심 직관**:
  - 인증 레벨은 "얼마나 엄격히 검증받았는가"의 등급표다. 같은 하드웨어라도 운영 설정에 따라 인증 레벨이 달라질 수 있다.
  - PKCS#11·KMIP는 "HSM 제품을 바꿔도 애플리케이션 코드는 그대로"를 보장하는 어댑터 표준이다.
  - 키 라이프사이클은 생성부터 폐기까지 한 방향으로 흐르는 파이프라인이며, 각 단계마다 통제점(control point)과 감사 로그가 있어야 규제를 통과한다.

## 핵심 용어 정리 (내부에 등장하는 것들)

| 표기/용어 | 의미 | 비유 |
|:---|:---|:---|
| 키 관리(Key Management) | 암호 키의 생성부터 폐기까지 전 수명주기를 통제하는 상위 분야 — HSM이 속하는 상위 개념 | 신분증의 발급·갱신·회수 전체 행정 체계 |
| 암호 모듈 검증(Cryptographic Module Validation) | 암호 하드웨어·소프트웨어가 정해진 보안 요구사항을 충족하는지 제3자가 검증하는 절차 | 자동차 충돌 안전 인증 프로그램 |
| HSM | 표준 인증을 받은 키 관리·암호 연산 전용 하드웨어 | 공인 감정사가 검수·봉인한 금고 |
| FIPS 140-2 / 140-3 | 미국 NIST가 정한 암호 모듈 보안 요구사항 표준. 140-3은 140-2의 후속(ISO/IEC 19790 기반)이며 신규 인증은 140-3으로 전환 중 | 자동차 안전 등급(NCAP)과 유사한 국가 공인 인증서 |
| 인증 레벨(Level 1~4) | 물리적·논리적 보안 요구사항이 단계적으로 강화되는 등급 | 금고 등급(가정용 금고 ~ 은행 본점 지하 금고) |
| PKCS#11(Cryptoki) | RSA Labs가 만든 암호 토큰용 함수 호출 API 표준 | 제조사가 달라도 꽂으면 되는 표준 USB 포트 |
| KMIP | OASIS가 만든 키 관리 서버-클라이언트 통신 프로토콜 표준 | 여러 은행이 같은 송금망(스위프트)을 공유하는 상호운용 규격 |
| 키 라이프사이클 | 생성 → 저장 → 사용 → 순환(rotation) → 폐기(destruction)로 이어지는 통제 단계 | 신분증의 발급 → 사용 → 갱신 → 회수·파기 절차 |
| 키 순환(Rotation) | 주기적으로 새 키로 교체해 노출 위험의 시간 창을 줄이는 정책 | 정기적으로 바꾸는 출입문 비밀번호 |
| 영지화(Zeroization) | 키를 복구 불가능하게 지우는 폐기 절차 | 문서 파쇄기 |
| PCI HSM | 결제카드산업표준위원회(PCI SSC)가 정한 결제 특화 HSM 요구사항, FIPS와 별개 인증 트랙 | 일반 위생 등급과 별도인 "조리시설 전용" 인증 |
| M of N 쿼럼 | N명의 관리자 중 M명이 동시 승인해야 민감 작업이 실행되는 접근통제 | 대여금고를 열려면 직원 2명의 열쇠가 동시에 필요한 절차 |
| 비반출성(Non-exportable) | 키 원본이 API로도 하드웨어 밖으로 나갈 수 없도록 설계된 속성 | 인출은 되지만 원본 서류는 은행 밖으로 못 나가는 규정 |
| TPM | 단말 내장형 저비용 보안 칩, 부팅 무결성·소량 키 저장에 특화 | 집 현관 도어락 |

## 깊이 이해

### FIPS 140-2/140-3 인증 레벨 — 무엇이 어떻게 강화되는가
- Level 1: 최소 요구사항. 승인된 암호 알고리즘만 쓰면 되고 물리 보안 요구는 없다. 소프트웨어 암호 모듈도 Level 1을 받을 수 있다.
- Level 2: 개봉하면 흔적이 남는 변조 증거(tamper-evident) 코팅·봉인이 필요하고, 역할 기반 인증(role-based authentication)이 요구된다.
- Level 3: 변조 저항(tamper-resistant) 구조에 더해, 변조가 감지되면 CSP(Critical Security Parameter, 즉 키)를 자동 영지화해야 한다. ID 기반 인증과 입출력 경로의 물리적 분리도 필요하다.
- Level 4: 온도·전압 같은 환경 공격까지 감지해 즉각 영지화하는 최고 등급이다.
- 실무 판단 포인트: "FIPS 140-2 인증을 받았다"는 문장만으로는 부족하다. 레벨을 명시하지 않으면 Level 1일 수도 있어 실질적인 물리 보안 보장이 없다. PCI DSS는 결제 키 저장에 최소 FIPS 140-2 Level 3 이상 또는 별도의 PCI HSM 인증을 요구한다.

### PKCS#11과 KMIP — 계층이 다른 두 표준
- PKCS#11은 애플리케이션이 HSM 하나에게 직접 명령을 내리는 함수 호출 API다. C_Sign, C_Encrypt 같은 함수로 세션을 열고 키 핸들(handle)로 연산을 요청하며, 키 값 자체는 핸들 뒤에 숨어 절대 반환되지 않는다.
- KMIP는 여러 벤더의 키 관리 서버와 클라이언트가 네트워크로 키 객체를 등록·조회·폐기하는 프로토콜이다. 서로 다른 제조사 HSM·KMS 간에 키의 생성일, 상태, 소유자 같은 메타데이터를 표준 포맷으로 교환한다.
- 즉 PKCS#11은 "연산 호출" 계층, KMIP는 "키 객체 관리" 계층으로 역할이 나뉜다. 실무에서는 애플리케이션이 PKCS#11로 서명 연산을 요청하고, 운영팀은 KMIP로 여러 HSM에 걸친 키 인벤토리를 중앙에서 관리하는 식으로 함께 쓰인다.
- 흔한 오해: "PKCS#11만 지원하면 어떤 HSM이든 코드 수정 없이 완전히 교체된다"는 과장이다. 표준 함수 집합은 같아도 벤더별 확장 속성(vendor-defined attribute)이 있어 완전한 이식성은 보장되지 않는다.

### 키 라이프사이클 — 단계별 통제점과 수치 예제
- 생성(Generation): HSM 내장 TRNG(True Random Number Generator)로 키를 생성하며, 생성 즉시 비반출(non-exportable) 속성이 부여된다.
- 저장(Storage): 암호화된 키 blob 또는 하드웨어 격리 슬롯에 보관된다. 예를 들어 RSA 2048비트 키 자체는 256바이트에 불과하지만, 접근은 오직 API 핸들을 통해서만 가능하다.
- 사용(Usage): usage flag(서명 전용, 암호화 전용 등)로 오용을 제한한다. 서명 전용으로 지정된 키에 암호화 연산을 요청하면 API가 거부한다.
- 순환(Rotation): 예를 들어 결제 PIN 암호화 키(PEK)는 규정상 연 1회 이상 순환하는 경우가 많다. 순환 주기가 짧을수록 유출 시 피해 시간 창은 줄지만 재발급 트랜잭션 오버헤드는 늘어난다 — 위험도와 운영 비용의 트레이드오프다.
- 폐기(Destruction): 영지화(zeroization)로 복구 불가능하게 삭제한다. FIPS 140-2 Level 3 이상은 변조 감지 시 자동 영지화가 필수 요구사항이다.
- 판별 원리: 각 단계마다 "누가, 어떤 승인으로" 실행했는지 감사 로그가 남아야 컴플라이언스(PCI DSS 요구사항 3, ISMS-P 등)를 통과한다. 감사 로그가 없으면 HSM을 쓰고 있어도 인증 심사에서 탈락한다.

### 처리량(TPS)과 클러스터링 — 수치 워크드 예제
- 단일 Network HSM의 RSA 2048 서명 처리량은 제품별 차이가 크지만 통상 초당 수천 TPS 수준이다. 결제 피크 시간대 요구 TPS가 이를 초과하면 클러스터링이 필요하다.
- 예: 피크 요구가 8,000 TPS이고 HSM 1대가 3,000 TPS를 처리한다면 산술적으로는 3대(8,000/3,000≈2.67 → 올림)가 필요하지만, 1대 장애를 감안한 N+1 이중화를 적용하면 4대 구성이 실무 기준이 된다.
- 가용성 계산: 개별 HSM 가용성이 99.9%(연간 다운타임 약 8.76시간)라도, 액티브-액티브 2대 병렬 구성에서 두 대가 동시에 죽을 확률은 0.1%×0.1%=0.0001%까지 낮아진다. 클러스터링이 성능뿐 아니라 가용성 설계이기도 한 이유다.

### TPM과의 격리수준·처리량 비교, 그리고 선택 기준
- TPM은 PC·스마트폰 메인보드에 내장된 저비용(개당 몇 달러) 칩으로, 부팅 무결성 측정(PCR)과 소량의 키 저장(엔도스먼트 키, 디스크 암호화 키 등)에 특화되어 있다. 연산 처리량은 초당 수십 건 수준으로 대량 트랜잭션 서명을 감당하지 못한다.
- HSM은 네트워크 연결형 또는 PCIe 장착형으로 초당 수천 건 이상의 RSA·ECDSA 연산을 처리하도록 설계되며, FIPS 140-2/3 Level 3~4, PCI HSM 등 다중 컴플라이언스 인증을 함께 요구받는 경우가 많다.
- 판별 원리: "이 키가 기기 한 대의 정체성을 증명하는가(TPM), 아니면 서버 인프라 전체의 대량 트랜잭션 서명을 책임지는가(HSM)"로 선택한다. 소프트웨어 키스토어(OS 키체인, 암호화된 설정 파일 등)는 규제 인증이 필요 없는 저위험 키에만 쓰고, 감사·규제 요구가 발생하는 순간 HSM으로 이전하는 것이 원칙이다.

### PCI HSM — 결제 산업 특화 요구사항
- PCI SSC가 관리하는 PCI HSM 요구사항은 FIPS 140-2/3과 별개의 인증 트랙이다. PIN 블록 암호화, 카드 검증 값(CVV) 생성 등 결제 특화 알고리즘·키 분리 요구사항을 포함한다.
- 실무에서 결제 게이트웨이는 FIPS 140-2 Level 3와 PCI HSM 인증을 동시에 요구받는 경우가 많다. 두 인증은 겹치지 않는 요구사항을 갖고 있어 하나만으로는 다른 하나를 대체하지 못한다.

### 비유와 흔한 오해
- 비유: HSM 하드웨어 자체는 "인증받은 금고 제조사의 모델명"이고, FIPS 140-2/3 레벨은 "그 금고가 어느 등급 인증시험을 통과했는지 보여주는 인증서"이며, PKCS#11·KMIP는 "어느 은행 창구에서든 같은 양식으로 입출금을 요청할 수 있게 만든 표준 서식"이다.
- 오해: "HSM을 쓰면 키 순환·폐기 정책은 자동으로 처리된다"는 오해가 흔하다. HSM은 정책을 실행하는 도구이지, 순환 주기·승인 절차 같은 정책 자체를 설계해주지 않는다. 이는 별도의 키 관리 거버넌스로 수립해야 한다.

## 연결 개념
- TPM(Trusted Platform Module) — 단말 내장형 저비용 보안 칩, HSM보다 처리량 낮고 용도가 부팅 무결성 검증으로 좁음
- 082_hsm_hardware_security_module.md — 같은 HSM을 물리적 탬퍼 메커니즘(메쉬 와이어, 온도/전압 센서) 관점에서 다루는 자매 문서
- PKI·루트 CA — HSM이 보호하는 대표적 키 자산의 발급 체계
- Secure Boot·펌웨어 보안 — 단말 신뢰 체인의 시작점으로, TPM과 함께 동작

# 📝 【답안용】 시험 답안 템플릿

> 목적: 시험장에서 25분에 그대로 쓰는 답안 양식. 작성방식(추상표현 금지·수치·도식·문제유형 전환)을 엄격히 지킨다.
> 핵심: HSM 답안은 키 격리 원리, FIPS 140-2/3 등급, PKCS#11 연동 구조, TPM과의 차이를 함께 제시한다.

## 핵심 인사이트 (3줄 요약)

> 1. **본질**: HSM은 키를 물리적으로 격리된 전용 하드웨어 안에서만 생성·저장·연산하도록 강제하는 변조 방지 장치이다.
> 2. **가치**: 루트 권한 탈취나 메모리 덤프가 발생해도 키 원본이 장치 밖으로 노출되지 않아 PKI·결제 시스템의 신뢰 기반이 유지된다.
> 3. **판단 포인트**: FIPS 140-2/3 등급(Level 1~4)과 처리량(TPS), 네트워크 연결형(Network HSM) vs 서버 내장형(PCIe HSM) 여부로 도입 형태를 선택한다.

## 출제 의도 및 답안 포인트

| 출제 의도 | 반드시 짚을 핵심 | 감점 회피 포인트 |
|:---|:---|:---|
| 키 격리 구조 이해 확인 | 키가 HSM 밖으로 평문 노출되지 않는 원리, PKCS#11/KMIP | HSM을 단순 암호화 소프트웨어로 서술 |
| 인증 등급·표준 이해 확인 | FIPS 140-2/3 Level, PCI HSM | 등급 구분 없이 "보안 인증을 받았다"로만 서술 |
| 유사 기술과 구분 역량 확인 | TPM·소프트웨어 키스토어와 격리 수준·처리량 차이 | HSM과 TPM을 동일 개념으로 혼용 |

> 요약: 이 문제는 암호화 여부가 아니라 키가 물리적으로 어디에 격리되고 어떤 등급으로 검증됐는지를 확인한다.

## Ⅰ. 개요 및 필요성

- 개요: 암호 키 생성·저장·연산을 전용 변조 방지 하드웨어 내부로 한정하는 보안 장치
- 배경: 소프트웨어 키스토어는 OS 권한 탈취·메모리 덤프로 키 유출 위험이 있어 감사 요구사항을 충족하지 못함
- 필요성: 루트 CA, 코드 서명, 결제 PIN 등 유출 피해가 큰 키는 FIPS 140-2/3 인증 HSM으로 물리적 격리가 필요함

---

## Ⅱ. 구조 및 구성요소

```text
Application -> PKCS#11/KMIP API 호출
  -> HSM 보안 경계(Tamper-Resistant Enclosure)
     -> 보안 프로세서(키 연산 전용)
     -> 키 저장 영역(암호화된 키 blob)
     -> 변조 감지 센서(개봉 시 영지화)
  -> 연산 결과만 반환
```

| 구성요소 | 역할 | 특이사항 |
|:---|:---|:---|
| 보안 경계(Enclosure) | 물리적 개봉·프로빙 차단 | 개봉 감지 시 키 영지화 |
| 보안 프로세서 | 키를 꺼내지 않고 서명·암복호화 수행 | 전용 크립토 가속 회로 |
| API 계층 | 애플리케이션 연동 표준 | PKCS#11, KMIP, JCE |
| 키 관리 정책 | 키 생성·백업·순환 규칙 | M of N 쿼럼 인증 |
| 감사 로그 | 모든 키 연산 기록 | 컴플라이언스 증적 |

> 요약: HSM은 물리적 경계, 전용 연산 프로세서, 표준 API, 키 관리 정책, 감사 로그가 결합돼 키를 격리한다.

---

## Ⅲ. 동작원리 및 흐름도

```text
클라이언트 서명 요청 -> API 인증(역할 기반 접근통제)
  -> HSM 내부 키 조회(키 자체는 이동하지 않음)
  -> 보안 프로세서에서 서명 연산 수행
  -> 서명 결과 반환 -> 연산 로그 기록
```

| 단계 | 처리 내용 | 검증 기준 |
|:---:|:---|:---|
| 1 | 클라이언트가 API로 서명 요청 전송 | 인증서·역할 기반 권한 확인 |
| 2 | HSM이 요청 대상 키를 내부에서 조회 | 키 ID, 사용 목적(usage flag) 일치 |
| 3 | 보안 프로세서가 키를 꺼내지 않고 연산 수행 | 연산 시간, 알고리즘(RSA/ECDSA/AES) |
| 4 | 결과 반환 및 감사 로그 기록 | 로그 무결성, 타임스탬프 |

> 요약: HSM 연산은 키 이동 없이 내부에서만 처리되고 모든 요청이 감사 로그로 남는 흐름이다.

---

## Ⅳ. 특징

| 구분 | 내용 | 판단 포인트 |
|:---|:---|:---|
| 장점 | 루트 권한 탈취·메모리 덤프로도 키 원본 노출 불가 | FIPS 140-2/3 Level 3 이상 물리 보안 |
| 한계 | 도입·운영 비용이 높고 처리량이 소프트웨어 대비 제한적 | 결제 피크 TPS 대비 클러스터링 필요 |
| 비교 포인트 | TPM(단말 내장, 저비용, 낮은 처리량) vs HSM(네트워크 연결, 고비용, 고처리량) | 서버 인프라는 HSM, 단말 무결성 검증은 TPM |

> 요약: HSM은 고신뢰·고처리량 키 연산에, TPM은 단말 부팅 무결성·저비용 키 저장에 적합하다.

## Ⅴ. 심화 비교 및 적용 판단

| 비교 축 | 기존/대안 | 본 키워드 | 선택 기준 |
|:---|:---|:---|:---|
| 구조 | 소프트웨어 키스토어(파일·KMS 소프트웨어) | 물리적 격리 전용 하드웨어 | 키 유출 시 피해가 크면 HSM 필수 |
| 비용/성능 | 저비용, 무제한 확장 | 고비용, TPS 제한(클러스터로 보완) | 결제·루트 CA는 비용보다 격리 우선 |
| 운영/위험 | 접근통제 정책에 전적으로 의존 | 물리적 영지화로 이중 방어 | 규제 준수(PCI HSM, FIPS) 요구 시 HSM 선택 |

> 요약: 규제 준수와 키 유출 피해 규모가 큰 영역은 비용이 높아도 HSM을 선택한다.

| 리스크 | 원인 | 대응 방안 | 확인 지표 |
|:---|:---|:---|:---|
| 단일 장애점 | HSM 1대 장애 시 서명 서비스 중단 | 클러스터링, 액티브-액티브 구성 | HSM 가용성 99.9% 이상 |
| 키 백업 유출 | 백업 키 blob 관리 소홀 | M of N 쿼럼 인증, 백업 HSM 이원화 | 백업 접근 승인 로그 100% |
| API 권한 오남용 | 역할 분리 미흡 | RBAC, 이중 승인(Dual Control) 적용 | 권한 변경 승인 이력 |

> 요약: HSM 리스크는 물리 보안보다 가용성 설계와 API 권한 통제에서 주로 발생한다.

| 점검 항목 | 목표 기준 | 측정 방법 |
|:---|:---|:---|
| 인증 등급 | FIPS 140-2/3 Level 3 이상 유지 | 인증서 갱신 이력 |
| 처리 성능 | 피크 서명 TPS 대비 여유율 30% 이상 | HSM 벤치마크, 부하테스트 |
| 감사 추적 | 키 연산 로그 보존 및 무결성 100% | SIEM 연동 로그 검증 |

> 요약: 도입 효과는 인증 등급 유지, 처리 성능 여유율, 감사 로그 무결성으로 판단한다.

## Ⅵ. 실무 적용 및 결론

**적용 방안 3개 (필수 — 단계별 또는 항목별):**
1. 단기: 루트 CA·코드 서명·결제 PIN 등 고위험 키를 식별해 FIPS 140-2/3 인증 HSM으로 이전함
2. 중기: PKCS#11/KMIP 표준 API로 애플리케이션을 연동하고 RBAC·이중 승인 정책을 적용함
3. 장기: 액티브-액티브 HSM 클러스터와 Cloud HSM 이중화로 가용성 99.9% 이상을 확보함

**결론 (2줄):**
- 기술사 판단: 고신뢰·규제 준수가 필요한 키는 HSM, 단말 부팅 무결성 검증은 TPM으로 역할을 분리해 적용함
- 향후 방향: Cloud HSM(AWS CloudHSM, Azure Dedicated HSM) 확산과 PQC(양자내성암호) 알고리즘 지원으로 HSM 기능이 확장되는 방향으로 발전함
