# 📖 【암기용】 개념 완전 이해

> 목적: 파이프라이닝을 처음 봐도 왜 CPU가 명령어를 5단계로 쪼개 겹쳐 실행하는지, 처리량과 지연시간이 왜 다르게 계산되는지 이해하게 만든다. 시험 답안 양식이 아니라, 이해를 위한 친절한 설명이다.

## 한눈에
- **개요**: 명령어 실행을 여러 단계로 나누고, 각 단계를 서로 다른 명령어가 동시에 사용하도록 겹쳐 실행하는 CPU 성능 향상 기법
- **왜 필요한가**: 명령어를 하나씩 처음부터 끝까지 순차 처리하면 각 하드웨어 유닛(인출기, 디코더, ALU 등)이 대부분 시간 놀고 있는데, 파이프라이닝은 이 유휴 시간을 다른 명령어로 채운다.
- **핵심 직관**: 세탁기-건조기-개기라는 3단계 빨래 작업을 한 사람이 매번 처음부터 끝까지 하는 대신, 세탁이 끝나자마자 다음 빨래를 세탁기에 넣는 방식으로 여러 빨래를 겹쳐 처리하는 것과 같다.

## 깊이 이해
- **배경·문제의식**: 명령어 처리는 인출(Fetch)-해석(Decode)-실행(Execute)-메모리 접근(Memory)-저장(Writeback) 같은 여러 하위 단계로 나뉘는데, 이를 순차 처리하면 한 명령어가 끝날 때까지 다음 명령어는 대기해야 해 하드웨어 유닛 활용률이 낮다.
- 고전적인 5단계 파이프라인(예: MIPS 참조 설계)은 IF(Instruction Fetch, 명령어 인출)-ID(Instruction Decode, 명령어 해석 및 레지스터 읽기)-EX(Execute, ALU 연산 또는 주소 계산)-MEM(Memory Access, 메모리 읽기/쓰기)-WB(Write Back, 결과를 레지스터에 저장) 순서로 구성된다.
- **작동 원리**: 각 단계는 전용 하드웨어 유닛을 가지며 단계 사이에는 파이프라인 레지스터(IF/ID, ID/EX, EX/MEM, MEM/WB)를 두어 이전 단계의 결과와 제어 신호를 다음 단계로 전달한다.
- 이상적인 상황(명령어 간 의존성·분기 없음)에서는 매 클럭 새 명령어가 IF 단계에 진입하고, 파이프라인이 가득 찬 이후(steady state)에는 매 클럭 하나의 명령어가 WB 단계를 완료해 처리량(throughput)이 1 명령어/클럭에 근접한다.
- **정량 관계**: k단계 파이프라인으로 n개의 독립적인 명령어를 처리할 때 이상적인 총 소요 클럭 수는 `k + (n-1)`이며, 이는 비파이프라인 방식의 `k × n` 클럭보다 짧다.
- 이때 이상적인 속도향상(Speedup)은 `(k×n) / (k+n-1)`로 계산되고, n이 매우 커지면 이 값은 단계 수 k에 수렴하지만 실제로는 해저드로 인한 스톨(stall)이 있어 이론값보다 낮게 나타난다.
- 파이프라인의 클럭 주기(clock period)는 가장 처리 시간이 긴 단계(가장 느린 stage)에 맞춰 결정되므로, 단계를 균등하게 나누지 못하면 전체 클럭 속도가 그 병목 단계에 종속된다.
- 첫 명령어가 WB까지 도달하는 지연시간(latency)은 여전히 k클럭이 걸리므로, 파이프라이닝은 개별 명령어의 지연시간을 줄이는 기법이 아니라 여러 명령어의 처리량을 늘리는 기법이다.
- **비유**: 세탁기-건조기-개기 3단계 빨래를 한 사람이 순서대로 끝까지 하면 빨래 3벌에 9단계 시간이 걸리지만, 세탁이 끝나자마자 다음 빨래를 세탁기에 넣으면 겹쳐 처리되어 총 시간이 크게 줄어드는 것과 같다.
- **구체 예시**: 5단계 파이프라인에서 독립적인 명령어 4개를 처리하면 이상적으로 `5 + (4-1) = 8`클럭이 걸리며, 이는 비파이프라인 방식의 `5 × 4 = 20`클럭보다 짧다.
- **흔한 오해·주의점**: "파이프라인 단계를 늘리면 무조건 빨라진다"는 성립하지 않는다. 단계가 깊어질수록 분기 예측 실패 시 버려야 할 명령어가 많아지고, 각 단계 간 전달 오버헤드(레지스터 지연)도 늘어난다.
- "파이프라이닝은 명령어 하나의 실행 속도를 높인다"도 틀렸다. 개별 명령어의 지연시간(latency)은 그대로이거나 오히려 늘어날 수 있으며, 파이프라이닝의 이득은 여러 명령어를 겹쳐 처리하는 처리량(throughput) 증가에 있다.

## 연결 개념
- 파이프라인 해저드(Pipeline Hazards) — 구조적·데이터·제어 해저드로 인한 이상적 처리량 미달 원인
- 파이프라인 포워딩·분기 예측 — 해저드로 인한 스톨을 줄이는 구체 기법
- 슈퍼스칼라 아키텍처 — 한 클럭에 여러 명령어를 동시에 파이프라인에 투입하는 확장
- 명령어 집합 RISC vs CISC — 고정 길이·단순 명령어가 파이프라인 설계를 쉽게 만드는 배경

# 📝 【답안용】 시험 답안 템플릿

> 목적: 시험장에서 25분에 그대로 쓰는 답안 양식. 작성방식(추상표현 금지·수치·도식·문제유형 전환)을 엄격히 지킨다.
> 핵심: 5단계 이름 나열이 아니라, 처리량·지연시간 정량 관계와 클럭 주기가 최장 단계에 종속되는 구조적 근거를 함께 제시한다. (122회 기출 대응)

## 핵심 인사이트 (3줄 요약)

> 1. **본질**: 파이프라이닝은 명령어 실행을 IF-ID-EX-MEM-WB 5단계로 분할해 서로 다른 명령어를 각 단계에서 동시에 처리하는 명령어 수준 병렬 처리 기법이다.
> 2. **가치**: 이상적인 경우 n개 명령어를 `k+(n-1)`클럭에 처리해 비파이프라인(`k×n`클럭) 대비 처리량을 높이지만 개별 명령어 지연시간은 그대로 k클럭이다.
> 3. **판단 포인트**: 클럭 주기는 가장 느린 단계에 종속되므로 단계 분할 균등성과 해저드로 인한 실제 스톨률을 함께 봐야 실질 성능 향상을 판단할 수 있다.

## 출제 의도 및 답안 포인트

| 출제 의도 | 반드시 짚을 핵심 | 감점 회피 포인트 |
|:---|:---|:---|
| 파이프라인 기본 구조 이해 확인 | IF-ID-EX-MEM-WB 5단계와 파이프라인 레지스터 역할 | 단계 이름만 나열하고 단계 간 전달 구조 누락 |
| 처리량·지연시간 정량 관계 이해 확인 | `k+(n-1)`클럭 공식과 속도향상(Speedup) 계산 | "빨라진다"는 표현만 쓰고 수식·수치 근거 누락 |
| 성능 상한 요인 판단 확인 | 클럭 주기가 최장 단계에 종속되는 구조 | "단계를 늘리면 무조건 빠르다"는 절대화된 서술 |

> 요약: 이 문제는 5단계 명칭 암기가 아니라 처리량·지연시간 공식과 클럭 주기 결정 구조를 정량적으로 제시할 것을 요구한다.

## Ⅰ. 개요 및 필요성

- 개요: 명령어 실행을 IF-ID-EX-MEM-WB 5단계로 나누고 서로 다른 명령어를 각 단계에서 동시에 처리하는 기법
- 배경: 순차 처리 방식은 하드웨어 유닛 활용률이 낮아, 단계별 유닛을 겹쳐 쓰는 방식이 필요해짐
- 필요성: 처리량을 높이되 클럭 주기는 최장 단계 지연에 종속되므로 단계 분할 균형과 해저드 제어 설계가 필요

---

## Ⅱ. 구조 및 구성요소

```text
명령어 스트림 -> IF -> ID -> EX -> MEM -> WB
                 |     |     |     |
              IF/ID  ID/EX EX/MEM MEM/WB  (파이프라인 레지스터)
```

| 구성요소 | 역할 | 특이사항 |
|:---|:---|:---|
| IF (Instruction Fetch) | PC 기준 명령어 인출 | I-Cache 접근 지연이 클럭 주기에 영향 |
| ID (Instruction Decode) | opcode 해석, 레지스터 읽기 | 제어 신호 생성 시작 |
| EX (Execute) | ALU 연산 또는 주소 계산 | 분기 조건 여기서 확정되는 설계도 존재 |
| MEM (Memory Access) | Load/Store 메모리 접근 | D-Cache 접근 지연 영향 |
| WB (Write Back) | 연산 결과 레지스터 저장 | 레지스터 파일 쓰기 포트 필요 |

> 요약: 5단계는 각각 전용 하드웨어 유닛을 가지며 파이프라인 레지스터가 단계 간 결과와 제어 신호를 전달한다.

## Ⅲ. 동작원리 및 흐름도

```text
클럭  1    2    3    4    5    6    7    8
명령1 IF   ID   EX   MEM  WB
명령2      IF   ID   EX   MEM  WB
명령3           IF   ID   EX   MEM  WB
명령4                IF   ID   EX   MEM  WB
```

| 단계 | 처리 내용 | 검증 기준 |
|:---:|:---|:---|
| 1 | 파이프라인 채움(fill), 첫 명령어만 진행 | 초기 k-1클럭은 스루풋 미달 상태 |
| 2 | 정상상태(steady state) 진입 | 매 클럭 새 명령어 IF 진입 |
| 3 | 매 클럭 WB 완료 | 처리량 1 명령어/클럭 근접 |
| 4 | 총 소요 클럭 `k+(n-1)` 확인 | 이상적 조건(해저드 없음) 전제 |

> 요약: 파이프라인은 채움 구간을 지나면 매 클럭 명령어 1개를 완료하는 정상상태에 도달하며, 총 소요 클럭은 `k+(n-1)`이다.

## Ⅳ. 특징

| 구분 | 비파이프라인 | 5단계 파이프라인 | 수치·표준 포인트 |
|:---|:---|:---|:---|
| n개 명령어 처리 클럭 | `k × n` | `k + (n-1)` (이상적) | 예: k=5, n=4 → 20클럭 vs 8클럭 |
| 개별 명령어 지연시간 | k클럭로 동일 | k클럭로 동일(단축되지 않음) | 지연시간이 아닌 처리량 개선 기법 |
| 클럭 주기 결정 | 전체 실행 시간 기준 | 가장 느린 단계(stage) 기준 | 단계 불균형 시 클럭 속도 손해 |
| 실제 성능 | 해저드 없음(참조 기준) | 해저드로 이상적 speedup 미달 | 실제 CPI는 이론값보다 높게 나타남 |

> 요약: 파이프라이닝은 처리량을 이상적으로 k배 가깝게 높이지만, 개별 지연시간은 그대로이고 실제로는 해저드로 이론값에 미달한다.

## Ⅴ. 심화 비교 및 적용 판단

| 비교 축 | 비파이프라인 | 5단계 파이프라인 | 선택 기준 |
|:---|:---|:---|:---|
| 구조 | 단일 명령어 순차 처리 | 단계 분할·동시 처리 | 처리량 목표(IPC 1.0 근접) 필요 시 파이프라인 채택 |
| 비용/성능 | 회로 단순, 처리량 낮음 | 파이프라인 레지스터·해저드 감지 회로 추가 | 추가 면적 대비 처리량 향상 비교 |
| 운영/위험 | 해저드 문제 없음 | 구조적·데이터·제어 해저드 관리 필요 | 해저드 해소 설계(포워딩·예측) 여부 확인 |

> 요약: 처리량이 중요한 범용 CPU는 파이프라인을 채택하되 해저드 관리 설계를 함께 검토해야 한다.

| 리스크 | 원인 | 대응 방안 | 확인 지표 |
|:---|:---|:---|:---|
| 단계 불균형 | 특정 단계(MEM 등)가 다른 단계보다 느림 | 단계 재설계, 캐시 접근 최적화 | 단계별 처리 시간 편차 |
| 파이프라인 채움 손실 | 초기 k-1클럭 동안 처리량 미달 | 짧은 실행 구간이 잦은 워크로드는 단계 수 재검토 | 채움 구간 대비 정상상태 비율 |
| 해저드 발생 | 명령어 간 의존성·분기로 스톨 발생 | 포워딩, 분기 예측 적용(별도 키워드 008 참조) | 실제 CPI vs 이론 CPI 차이 |

> 요약: 파이프라인 리스크는 단계 불균형, 채움 구간 손실, 해저드로 인한 실제 CPI 저하가 핵심이다.

| 점검 항목 | 목표 기준 | 측정 방법 |
|:---|:---|:---|
| 처리량 | 이론 speedup 대비 실제 speedup 비율 | 사이클 시뮬레이터, 벤치마크 |
| 클럭 주기 | 최장 단계 지연 기준 클럭 속도 확정 | 타이밍 분석(STA) |
| CPI | 이론 CPI(1.0 근접) 대비 실제 CPI 편차 | 성능 카운터, RTL 시뮬레이션 |

> 요약: 도입 효과는 이론 대비 실제 speedup, 클럭 주기 확정 근거, 실제 CPI 편차로 판단한다.

## Ⅵ. 실무 적용 및 결론

**적용 방안 3개 (필수 — 단계별 또는 항목별):**
1. 신규 코어 설계 시 IF-ID-EX-MEM-WB 5단계를 균등한 지연시간으로 분할해 클럭 주기가 특정 단계에 과도하게 종속되지 않도록 설계함
2. 처리량 목표(IPC)를 수립할 때 `k+(n-1)` 이론값과 실제 벤치마크 CPI 차이를 함께 보고해 해저드 영향을 정량화함
3. 짧은 실행 구간이 반복되는 워크로드(빈번한 함수 호출·인터럽트)는 파이프라인 채움 손실 비중을 점검해 단계 수 재설계 여부를 판단함

**결론 (2줄):**
- 기술사 판단: 파이프라이닝은 처리량 향상 기법이며 개별 명령어 지연시간은 그대로이므로, 지연시간 민감 워크로드와 처리량 민감 워크로드를 구분해 단계 수를 설계함
- 향후 방향: 해저드 제어(포워딩·분기 예측)와 슈퍼스칼라·비순차 실행 결합으로 이론 speedup에 근접하는 방향으로 발전하고 있음
