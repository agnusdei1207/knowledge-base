## 미리 알고가기

- 처리량: 단위 시간에 완료되는 명령어 수로 파이프라이닝의 주된 개선 대상임
- 지연시간: 명령어 하나가 시작부터 완료까지 걸리는 시간임
- Pipeline register: 단계 사이 결과를 클록 단위로 보관하는 임시 저장소임
- CPI: 명령어당 평균 클록 수로 stall과 flush가 증가하면 커짐

## Ⅰ. 개요

- **정의**: 파이프라이닝은 명령어 실행을 IF, ID, EX, MEM, WB 같은 단계로 나누고 서로 다른 명령어를 각 단계에서 겹쳐 처리하는 CPU 성능 향상 기법임. 단계 균형, 해저드, CPI를 기준으로 처리량 개선 효과를 판단하는 데 쓰임.
- **배경/필요성**: 단일 명령어를 끝까지 처리한 뒤 다음 명령어를 시작하면 실행 유닛과 메모리 경로가 대기하는 시간이 많음. 파이프라이닝은 조립 라인처럼 단계를 겹쳐 CPU 자원을 계속 사용하게 하여 전체 처리량을 높임.
- **비유**: 세차장에서 세척, 헹굼, 건조를 한 차가 모두 끝낸 뒤 다음 차를 받는 대신 각 단계에 차를 동시에 넣는 방식임.

| 출제 의도 | 반드시 짚을 핵심 | 감점 회피 포인트 |
|:---|:---|:---|
| 5단계 구조와 성능 영향 설명 | IF/ID/EX/MEM/WB, pipeline register, CPI, hazard | 개별 명령 지연시간 감소로 오해 |

> 요약: 파이프라이닝은 명령어 하나의 지연시간보다 연속 명령어 처리량을 높이는 구조임.

## Ⅱ. 특징/비교

| 판단 기준 | 비파이프라인 | 5단계 파이프라인 |
|:---|:---|:---|
| 실행 방식 | 한 명령어가 모든 단계를 끝낸 뒤 다음 명령어를 시작함 | 여러 명령어가 서로 다른 단계를 동시에 점유함 |
| 성능 기준 | 명령어 지연시간이 전체 성능을 좌우함 | ideal CPI 1에 가까운 처리량이 목표임 |
| 설계 조건 | 제어가 단순하고 해저드 처리가 적음 | 단계 균형, forwarding, stall, flush 제어가 필요함 |
| 적용 기준 | 단순 MCU, 낮은 클록, 예측 가능한 제어에 적합함 | 범용 CPU, 고성능 embedded, superscalar 기반에 적합함 |

> 요약: 파이프라인은 제어 복잡도를 감수하고 단계 중첩으로 처리량을 확보하는 선택임.

## Ⅲ. 구성요소

```text
+------+   +------+   +------+   +------+   +------+
| IF   |-->| ID   |-->| EX   |-->| MEM  |-->| WB   |
+------+   +------+   +------+   +------+   +------+
    |          |          |          |          |
    +---- pipeline registers between stages ----+
```

| 구성요소 | 설명 | 비유 |
|:---|:---|:---|
| IF | PC 기준으로 instruction cache에서 명령어를 가져옴 | 원재료 투입 |
| ID | 명령어를 해석하고 레지스터 operand를 읽음 | 작업 지시 해석 |
| EX | ALU 연산, 주소 계산, 분기 조건 평가를 수행함 | 핵심 가공 |
| MEM | load/store 명령의 데이터 메모리 접근을 수행함 | 창고 입출고 |
| WB | 실행 결과를 레지스터 파일에 기록함 | 결과 등록 |

> 요약: 5단계 파이프라인은 명령어 실행을 균등한 공정으로 나누어 단계별 중첩을 가능하게 함.

## Ⅳ. 절차

```text
Cycle:   1      2      3      4      5      6      7
Inst1:  IF --> ID --> EX --> MEM -> WB
Inst2:         IF --> ID --> EX --> MEM -> WB
Inst3:                IF --> ID --> EX --> MEM -> WB
```

1. **단계 분할** - 명령어 실행을 클록 기준으로 나눌 수 있는 IF, ID, EX, MEM, WB 단계로 분해함
2. **레지스터 삽입** - 단계 사이에 pipeline register를 두어 중간 결과와 제어 신호를 보관함
3. **중첩 실행** - 매 클록마다 새 명령어를 투입해 여러 단계가 동시에 동작하게 함
4. **완료와 제어** - WB 단계에서 결과를 확정하고 해저드 발생 시 stall 또는 flush를 수행함

> 요약: 파이프라인은 단계 분할, 중간 저장, 중첩 실행, 해저드 제어로 처리량을 만든다.

## Ⅴ. 문제점

- **P1 단계 불균형**: 가장 느린 단계가 전체 클록 주기를 결정해 빠른 단계의 여유 시간이 낭비됨
- **P2 해저드로 인한 stall**: 데이터 의존성, 분기, 자원 충돌이 발생하면 pipeline bubble이 삽입되어 CPI가 증가함
- **P3 과도한 깊이의 비용**: deep pipeline은 clock은 높일 수 있지만 branch miss penalty와 latch 전력이 증가함

> 요약: 파이프라인 성능은 이상적 단계 수가 아니라 불균형과 해저드 비용을 뺀 실제 CPI로 판단해야 함.

## Ⅵ. 개선방안

- **P1 대응**: 단계별 지연을 측정해 stage balancing, critical path 분해, pipeline register 위치를 조정함 (확인: cycle time, slack)
- **P2 대응**: forwarding, hazard detection, branch prediction, compiler scheduling을 함께 적용함 (확인: stall cycle, branch miss penalty)
- **P3 대응**: workload별 최적 pipeline depth를 정하고 clock gating과 predictor 품질을 같이 설계함 (확인: perf/W, flush 횟수)

> 요약: 파이프라인 개선은 단계 수 확대보다 실제 stall 원인과 전력 비용을 줄이는 방향이어야 함.

## Ⅶ. 전망

- **발전 방향**: 파이프라인은 단순 5단계 모델을 넘어 superscalar, out-of-order, speculative execution과 결합된 복합 실행 경로로 확장됨
- **기술사적 판단**: 단계 수는 목표 클록, branch penalty, forwarding 경로 길이, pipeline register 전력, 최악 지연시간 허용치를 기준으로 정해야 함; `IPC`, `CPI`, stall cycle, branch miss penalty, exception flush 경로를 측정해 깊은 파이프라인의 이득과 손실을 구분함
- **기술사 제언**: 5단계 명칭, 명령 중첩 원리, 해저드로 인한 `CPI` 증가를 한 흐름으로 설명해야 구조적 답안이 됨
