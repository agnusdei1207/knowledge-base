## Ⅰ. 개요
- **정의**: 메모리 다이 내부에 연산 유닛을 집적하여 데이터 이동 없이 제자리 연산하는 아키텍처
- **배경/필요성**: 프로세서 속도는 연간 수십% 향상되지만 메모리 대역폭 향상률은 그에 미치지 못하여 Memory Wall이 심화됨. 데이터를 외부로 이동시키는 전력이 연산 자체 전력의 수백 배에 달하므로, 이동을 원천 제거하는 구조가 요구됨
- **비유**: 창고(메모리) 안에 작업대(연산기)를 설치하여 물건을 꺼내지 않고 그 자리에서 가공하는 방식

| 출제 의도 | 반드시 짚을 핵심 | 감점 회피 포인트 |
|:---|:---|:---|
| 폰 노이만 병목 극복 방안 구분 | 연산기가 메모리 뱅크 내부에 위치하여 내부 대역폭을 활용함 | PNM(034 참조)은 메모리 외부 기판에 연산기를 배치하므로 위치가 다름 |

> 요약: PIM은 메모리 뱅크 내부에 연산 유닛을 배치하여 데이터 이동 병목과 전력 소모를 근본 제거하는 구조임

## Ⅱ. 구성요소
```text
+------------------------------------------+
|             HBM-PIM Stack                 |
|  +------+ +------+ +------+ +------+     |
|  | Bank | | Bank | | Bank | | Bank |     |
|  | +--+ | | +--+ | | +--+ | | +--+ |    |
|  | |MAC| | | |MAC| | | |MAC| | | |MAC| | |
|  | +--+ | | +--+ | | +--+ | | +--+ |    |
|  +------+ +------+ +------+ +------+     |
|  +--------------------------------------+ |
|  |        Base Logic Die / PCU          | |
|  +--------------------------------------+ |
+------------------------------------------+
        |  명령어 수신 / 결과 반환 (외부 I/O)
        v
  +------------+
  | Host CPU   |
  | / GPU      |
  +------------+
```

| 구성요소 | 설명 | 비유 |
|:---|:---|:---|
| MAC 연산기 | 각 뱅크 내부에 배치된 곱셈-누적(Multiply-Accumulate) 유닛, 행렬 연산을 뱅크 단위로 병렬 수행 | 각 선반마다 부착된 소형 계산기 |
| PCU | Programmable Computing Unit, 호스트 명령을 해석하고 각 뱅크 MAC에 연산을 분배하는 제어기 | 창고 관리자가 작업 지시서를 배분하는 역할 |
| 내부 광대역 버스 | 뱅크와 MAC 사이를 연결하는 칩 내부 배선, 외부 핀 대역폭의 수십 배에 달하는 내부 대역폭 제공 | 창고 내부의 컨베이어 벨트 |
| 호스트 인터페이스 | 호스트 프로세서가 PIM 명령어를 전송하고 최종 결과만 수신하는 외부 통신 경로 | 본사에서 창고로 작업 지시서를 보내는 전화선 |

> 요약: 뱅크 내 MAC·제어용 PCU·내부 광대역 버스·호스트 인터페이스로 구성됨

## Ⅲ. 절차
```text
호스트 명령 전송 -> PCU 명령 분배 -> 뱅크 내 MAC 병렬 연산 -> 결과 집약 및 반환
```
- 1단계: 호스트 프로세서가 연산 대상 주소와 연산 종류를 PIM 명령어로 인코딩하여 전송함
- 2단계: PCU가 명령어를 해석하고 해당 데이터가 저장된 뱅크의 MAC 유닛에 연산을 분배함
- 3단계: 각 뱅크의 MAC이 내부 대역폭을 활용하여 저장 데이터에 곱셈-누적 연산을 병렬 수행함
- 4단계: PCU가 각 뱅크 연산 결과를 집약(Reduce)하고, 최종 결과(수 MB)만 호스트로 반환함

> 요약: 명령 전송 -> 뱅크 분배 -> 내부 병렬 연산 -> 결과 집약 반환의 4단계로 동작함

## Ⅳ. 문제점
- 공정 복잡도: DRAM 공정과 로직 공정을 하나의 다이에 혼재시켜야 함 — 이종 공정 통합으로 수율이 저하됨
- 연산 범용성 부족: 뱅크 내 MAC은 행렬 곱·벡터 연산에 특화되어 범용 연산을 수행하기 어려움 — 워크로드 제약이 발생함
- SW 생태계 미비: 기존 CUDA/OpenCL 코드를 PIM 명령으로 변환하는 컴파일러·API가 미성숙 — 개발자 채택 장벽이 높음

> 요약: 이종 공정 수율·연산 범용성·SW 생태계 부재가 PIM 확산의 3대 장벽임

## Ⅴ. 개선방안
1. 단기: DRAM-로직 분리 적층(3D 패키징) 방식으로 이종 공정을 물리적으로 분리하여 수율을 개선함
2. 중기: MAC 외에 비교·정렬·활성화 함수 등 경량 범용 연산을 PCU에 추가하여 워크로드 커버리지를 확대함
3. 장기: JEDEC 표준 PIM ISA(명령어 집합)를 수립하고 주요 프레임워크(PyTorch 등) 런타임에 통합하여 SW 장벽을 해소함

> 요약: 적층 공정 분리 -> 연산 범용성 확대 -> 표준 ISA 수립 순으로 장벽을 해소함

## Ⅵ. 전망
- 발전 방향: HBM4(032 참조)의 Custom Logic Die와 결합하여 PIM 연산 능력이 대폭 강화될 전망임
- 기술사적 판단: AI 추론 워크로드(가중치 조회 위주)에서는 PIM이 GPU 대비 전력당 처리량 우위를 확보 가능함
- 기술사 제언: PIM 도입 검토 시 대상 워크로드가 행렬 연산 위주인지 확인하고, 범용 연산은 PNM(034 참조) 또는 호스트에 위임하는 하이브리드 설계를 고려할 필요
