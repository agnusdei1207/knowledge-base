# 📖 【암기용】 개념 완전 이해

> 목적: PIM을 처음 봐도 왜 메모리 안에 연산 회로를 넣는지, PNM과 무엇이 다른지 이해하게 만든다. 시험 답안 양식이 아니라, 이해를 위한 친절한 설명이다.

## 한눈에
- **개요**: 연산 로직을 DRAM 다이(뱅크) 내부에 직접 배치해 데이터를 CPU/GPU로 이동시키지 않고 메모리 안에서 연산을 수행하는 방식
- **왜 필요한가**: von Neumann 구조는 연산장치와 메모리가 분리되어 있어 데이터를 주고받는 버스 대역폭이 병목이 되는데, PIM은 이 데이터 이동 자체를 없애 병목을 근본적으로 줄인다
- **핵심 직관**: 재료를 창고에서 공장으로 옮겨 가공하는 대신, 창고 안에 소형 가공 설비를 넣어 그 자리에서 가공하는 것이다

## 깊이 이해
- **배경·문제의식**: AI 추론의 GEMV(행렬-벡터 곱)·MAC(곱셈누산) 연산은 연산량 대비 데이터 이동량이 많아 메모리-프로세서 간 버스 대역폭이 실질 처리 속도를 제한하는 메모리 병목(memory wall)을 유발한다.
- **작동 원리**: PIM은 DRAM 뱅크 옆 또는 뱅크 내부에 MAC 연산기 같은 경량 연산 유닛을 직접 삽입해, 데이터를 버스로 내보내지 않고 뱅크 접근과 동시에 연산을 수행한 뒤 결과만 호스트로 전달한다.
- **대표 구현 예시**: SK하이닉스의 GDDR6-AiM(Accelerator in Memory)과 삼성전자의 HBM-PIM(FIMDRAM, Aquabolt-XL 기반)은 각각 GDDR·HBM 뱅크 구조 내부에 연산 유닛(PU, Processing Unit)을 삽입해 GEMV 연산을 메모리 내부에서 처리하도록 설계되었다(제조사 공개 자료 기준).
- **비유**: PIM은 창고 선반 사이사이에 소형 조립 로봇을 심어, 물건을 꺼내는 동시에 조립까지 그 선반 위치에서 끝내는 방식이다.
- **구체 예시**: HBM-PIM은 HBM 뱅크 단위로 MAC 연산기를 배치해, 호스트 GPU가 벡터를 뱅크에 broadcast하면 각 뱅크의 PU가 병렬로 곱셈누산을 수행하고 결과만 반환하는 구조를 취한다.
- **흔한 오해·주의점**: PIM은 범용 CPU 연산을 메모리 안에서 전부 대체하는 기술이 아니며, DRAM 공정의 로직 성능 한계 때문에 GEMV·활성화 함수 같은 단순·반복 연산 위주로 적용 범위가 제한된다는 점을 구분해야 한다.

## 연결 개념
- PNM(Processing Near Memory) — 연산 로직을 메모리 다이 밖(근접 위치)에 두는 대비 개념
- HBM(High Bandwidth Memory) — PIM이 흔히 결합되는 메모리 스택 구조
- 인메모리 컴퓨팅(In-Memory Computing) — PIM을 포함하는 상위 개념
- Von Neumann Bottleneck — PIM이 해결하려는 근본 문제

# 📝 【답안용】 시험 답안 템플릿

> 목적: 시험장에서 25분에 그대로 쓰는 답안 양식. 작성방식(추상표현 금지·수치·도식·문제유형 전환)을 엄격히 지킨다.
> 핵심: PIM은 개념 나열이 아니라, PNM과의 위치·공정 차이, 적용 가능한 연산 범위의 한계를 함께 짚어야 한다.

## 핵심 인사이트 (3줄 요약)

> 1. **본질**: PIM은 연산 로직을 DRAM 다이·뱅크 내부에 직접 배치해 데이터 이동 없이 메모리 안에서 연산을 수행하는 구조다.
> 2. **가치**: 메모리-프로세서 간 데이터 이동을 없애 GEMV·MAC 같은 데이터 이동 집약적 AI 연산의 병목을 줄인다.
> 3. **판단 포인트**: DRAM 공정 기반 로직은 CMOS 로직 공정보다 연산 성능이 낮으므로, 적용 범위를 단순·반복 연산으로 한정하는 판단이 필요하다.

## 출제 의도 및 답안 포인트

| 출제 의도 | 반드시 짚을 핵심 | 감점 회피 포인트 |
|:---|:---|:---|
| PIM vs PNM 구분 역량 확인 | 연산 로직이 메모리 다이 내부(PIM)인지 별도 다이(PNM)인지 | PIM과 PNM을 위치 구분 없이 혼용 |
| 메모리 병목 해결 원리 이해 확인 | von Neumann 병목, 데이터 이동 제거 효과 | 병목 원인을 캐시 미스로만 서술 |
| 적용 한계 판단 확인 | DRAM 공정 로직 성능 제약, 적용 연산 범위 | PIM이 범용 연산을 전부 대체한다고 서술 |

> 요약: 이 문제는 PIM 명칭 암기가 아니라 PNM과의 위치·공정 차이와 적용 한계를 구분하는지를 확인한다.

## Ⅰ. 개요 및 필요성

- 정의: 연산 로직을 DRAM 다이·뱅크 내부에 직접 배치해 메모리 안에서 연산을 수행하는 구조
- 배경: AI 추론의 GEMV·MAC 연산이 데이터 이동량 대비 연산량이 적어 메모리-프로세서 버스가 병목이 됨
- 필요성: 데이터 이동 자체를 제거해 메모리 바운드 연산의 지연시간·전력 소모를 줄이는 것이 목적

---

## Ⅱ. 구조 및 구성요소

```text
Host GPU/CPU
  -> 벡터/명령 broadcast
  -> DRAM Die
       / Bank 0 + PU(Processing Unit)
       / Bank 1 + PU
       / Bank N + PU
  -> 뱅크별 MAC 연산 병렬 수행
  -> 결과만 Host로 반환
```

| 구성요소 | 역할 | 특이사항 |
|:---|:---|:---|
| PU(Processing Unit) | 뱅크 내부에서 MAC·누산 연산 수행 | DRAM 공정 기반, 단순 연산 위주 |
| DRAM Bank | 데이터 저장 및 PU 연산 대상 | 뱅크 병렬성을 연산 병렬성으로 활용 |
| I/O 경로 | Host와 결과값만 송수신 | 원본 데이터 대량 이동 없음 |
| 제어 로직 | Host 명령 해석, PU 활성화 | 기존 DRAM 명령 체계 확장 |

> 요약: PIM은 DRAM 뱅크마다 연산 유닛을 두어 데이터 이동 없이 뱅크 단위로 병렬 연산을 수행한다.

---

## Ⅲ. 동작원리 및 흐름도

```text
Host: 벡터 데이터 + 연산 명령 전달
  -> DRAM Bank 접근과 동시에 PU 활성화
  -> PU가 뱅크 내 데이터로 MAC 연산 수행
  -> 뱅크별 부분합 생성 -> 누산/합산
  -> 최종 결과만 Host로 반환
```

| 단계 | 처리 내용 | 검증 기준 |
|:---:|:---|:---|
| 1 | Host가 연산 대상 벡터·명령을 메모리로 전달 | 명령 디코딩 정확성 |
| 2 | 각 뱅크의 PU가 활성화되어 로컬 데이터 접근 | 뱅크 충돌 여부 |
| 3 | PU가 MAC 연산을 수행해 부분합 생성 | 연산 정확도, 처리 지연 |
| 4 | 부분합을 합산해 결과만 Host로 반환 | 데이터 이동량 감소율 |

> 요약: PIM은 뱅크 단위로 연산을 병렬 수행한 뒤 결과만 반환해 데이터 이동량을 근본적으로 줄인다.

---

## Ⅳ. 특징

| 구분 | 기존 GPU/CPU 연산 | PIM | 수치·포인트 |
|:---|:---|:---|:---|
| 데이터 이동 | 메모리→버스→프로세서 이동 필수 | 뱅크 내부에서 연산, 결과만 이동 | 버스 트래픽 대폭 감소 |
| 연산 로직 공정 | 고성능 CMOS 로직 공정 | DRAM 공정 기반 경량 로직 | 복잡 연산에는 성능 제약 |
| 적용 연산 | 범용 연산 전반 | GEMV, MAC 등 단순·반복 연산 위주 | 활성화 함수 등 일부만 지원 |
| 대표 구현 | - | GDDR6-AiM, HBM-PIM(FIMDRAM) | 제조사 공개 자료 기준 |

> 요약: PIM은 데이터 이동을 없애는 대신 DRAM 공정 제약으로 연산 범위가 단순·반복 연산 위주로 한정된다.

## Ⅴ. 심화 비교 및 적용 판단

| 비교 축 | 기존 GPU 중심 연산 | PIM | 선택 기준 |
|:---|:---|:---|:---|
| 구조 | 프로세서-메모리 분리, 버스 경유 | 메모리 뱅크 내부 연산 유닛 통합 | 데이터 이동량이 큰 연산 비중 |
| 비용/성능 | 고성능 로직, 높은 버스 트래픽 | 경량 로직, 낮은 버스 트래픽 | 대역폭 병목 완화 필요 정도 |
| 운영/위험 | 검증된 소프트웨어 생태계 | 뱅크 연산 프로그래밍 모델 제한 | 컴파일러·SDK 성숙도 |

> 요약: 데이터 이동이 병목인 GEMV류 연산 비중이 큰 워크로드는 PIM, 범용 연산 비중이 큰 워크로드는 기존 구조가 유리하다.

| 리스크 | 원인 | 대응 방안 | 확인 지표 |
|:---|:---|:---|:---|
| 연산 범위 제한 | DRAM 공정 기반 로직의 성능 한계 | GEMV·MAC 등 목표 연산으로 적용 범위 한정 | 지원 연산 커버리지 |
| 소프트웨어 생태계 미성숙 | 전용 컴파일러·SDK 부족 | 벤더 SDK와 프레임워크 연동 검증 | 빌드·배포 성공률 |
| 검증 복잡도 | 뱅크별 병렬 연산 정합성 검증 필요 | 뱅크 단위 unit test, 정합성 비교 | 결과 정확도 오차율 |

> 요약: PIM 도입 리스크는 연산 범위 제한과 소프트웨어 생태계 미성숙이며, 목표 연산을 한정해 검증해야 한다.

| 점검 항목 | 목표 기준 | 측정 방법 |
|:---|:---|:---|
| 대역폭 절감 | 버스 트래픽 감소율 | 메모리 트래픽 모니터링 |
| 연산 정확도 | 기존 GPU 연산 대비 오차 허용 범위 이내 | 결과 비교 테스트 |
| 전력 효율 | 연산당 소비 전력 감소율 | 전력 측정 벤치마크 |

> 요약: 도입 성공 여부는 버스 트래픽 감소율, 연산 정확도, 전력 효율로 판단한다.

## Ⅵ. 실무 적용 및 결론

**적용 방안 3개:**
1. 추천 시스템·LLM 추론의 GEMV 연산 구간을 PIM 지원 메모리로 오프로드해 버스 트래픽을 줄임
2. PIM 적용 전 지원 연산 커버리지를 확인하고 미지원 연산은 기존 GPU 경로로 유지하는 하이브리드 구조를 설계함
3. 벤더 SDK·컴파일러 성숙도를 사전 검증해 배포 리스크를 낮춤

**결론 (2줄):**
- 기술사 판단: 데이터 이동이 병목인 단순·반복 연산 비중이 큰 AI 추론 워크로드에는 PIM이 유효하나, 범용 연산에는 기존 구조를 유지해야 함
- 향후 방향: PIM은 PNM·CXL 메모리 풀링과 결합해 이종 메모리-연산 계층 구조로 확장될 전망임
