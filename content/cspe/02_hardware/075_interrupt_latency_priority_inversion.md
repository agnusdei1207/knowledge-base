# 📖 【암기용】 개념 완전 이해

> 목적: 인터럽트 레이턴시가 왜 생기고, 우선순위 역전이 왜 "낮은 우선순위 때문"이 아니라 "중간 우선순위 때문"에 생기는지 정확히 이해하게 만든다. 시험 답안 양식이 아니라, 이해를 위한 친절한 설명이다.

## 한눈에
- **개요**: 인터럽트 레이턴시는 인터럽트 신호 발생부터 ISR(Interrupt Service Routine) 첫 명령 실행까지 걸리는 시간이고, 우선순위 역전은 낮은 우선순위 태스크가 점유한 자원 때문에 높은 우선순위 태스크가 무기한 대기하는 현상이다
- **왜 필요한가**: RTOS(Real-Time Operating System)는 데드라인을 지켜야 하므로 이 두 지연 요인을 정량적으로 관리하지 못하면 시스템이 결정론적(deterministic)으로 동작한다고 말할 수 없다
- **핵심 직관**: 인터럽트 레이턴시는 "긴급 전화가 왔을 때 받기까지 걸리는 시간"이고, 우선순위 역전은 "VIP 손님이 예약한 회의실을 말단 직원이 쓰고 있는데, 그 말단 직원이 다른 평사원들에게 계속 밀려서 회의실을 못 비우는 상황"이다

## 깊이 이해
- **배경·문제의식**: 임베디드·제어 시스템은 외부 이벤트에 정해진 시간 안에 반응해야 하므로 인터럽트 응답이 늦어지면 센서 값 유실, 제어 주기 초과 같은 장애로 이어진다.
- **배경·문제의식**: 여러 태스크가 우선순위 기반 선점형 스케줄링을 쓰면서 뮤텍스 같은 공유 자원을 함께 쓰면, 우선순위와 무관한 순서로 실행이 뒤바뀌는 역전 현상이 발생할 수 있다.
- **작동 원리(레이턴시 구성요소)**: 하드웨어 인터럽트 신호가 CPU에 도달해 인지되는 hardware detection/response time이 첫 구간이다.
- **작동 원리(레이턴시 구성요소)**: 이미 실행 중인 인터럽트 비활성화 구간(critical section)이나 선점 불가능한 명령이 끝날 때까지 기다리는 시간이 두 번째 구간이다.
- **작동 원리(레이턴시 구성요소)**: 레지스터·PC·플래그를 스택에 저장하는 context save time이 세 번째 구간이다.
- **작동 원리(레이턴시 구성요소)**: 인터럽트 벡터 테이블을 조회해 해당 ISR 주소로 분기하는 ISR dispatch/vector lookup time이 마지막 구간이다.
- **작동 원리(RTOS 설계)**: RTOS는 인터럽트 비활성화 구간을 최소화하고 ISR을 짧게 유지해 무거운 처리는 태스크나 bottom-half로 넘기는 방식으로 레이턴시 상한을 결정론적으로 관리한다.
- **작동 원리(우선순위 역전, 인과 방향 고정)**: 낮은 우선순위 태스크 L이 공유 자원(뮤텍스)을 먼저 획득한다.
- **작동 원리(우선순위 역전)**: 높은 우선순위 태스크 H가 같은 자원을 요구하면 L이 반납할 때까지 블록(block)된다.
- **작동 원리(우선순위 역전)**: 이때 자원이 필요 없는 중간 우선순위 태스크 M이 L보다 우선순위가 높으므로 L을 선점한다.
- **작동 원리(우선순위 역전)**: M의 선점이 반복되면 L의 실행이 계속 지연되어 자원을 반납하지 못하고, 그 결과 H가 M들에게 간접적으로 밀려 무기한 대기한다.
- **작동 원리(해결책, priority inheritance)**: L이 H가 기다리는 자원을 보유한 동안 H의 우선순위를 임시로 상속받아 M이 더 이상 L을 선점하지 못하게 만든다.
- **작동 원리(해결책, priority inheritance)**: L은 자원을 반납한 직후 원래 우선순위로 복귀한다.
- **작동 원리(대안, priority ceiling protocol)**: 자원마다 그 자원을 잠글 수 있는 태스크 중 가장 높은 우선순위를 ceiling으로 미리 지정해, 자원 점유 중에는 ceiling 이하 우선순위 태스크의 선점을 원천 차단한다.
- **비유**: 인터럽트 레이턴시는 초인종이 울린 뒤 문을 열기까지 걸리는 시간이고, 그 사이 하던 설거지(critical section)를 마저 끝내야 하면 응답이 늦어진다.
- **비유**: 우선순위 역전은 사장(H)이 쓸 회의실을 신입사원(L)이 먼저 예약했는데, 신입사원이 다른 평사원들(M)의 잡무 요청에 계속 불려 다니느라 회의실을 못 비우는 상황이다.
- **구체 예시**: Mars Pathfinder 1997 화성 착륙선은 낮은 우선순위 기상 데이터 수집 태스크가 정보 버스 뮤텍스를 점유한 상태에서 중간 우선순위 통신 태스크에 계속 선점당해, 높은 우선순위 버스 관리 태스크가 무기한 대기하며 watchdog timeout으로 시스템 재부팅이 반복됐다.
- **구체 예시**: Mars Pathfinder 사례는 VxWorks 뮤텍스에 priority inheritance 옵션을 활성화해 원격으로 패치되면서 해결됐다.
- **흔한 오해·주의점**: 우선순위 역전은 "낮은 우선순위 태스크가 자원을 오래 쓰기 때문"이 아니라 "중간 우선순위 태스크들이 낮은 우선순위 태스크의 실행을 방해하기 때문"에 발생한다는 인과 방향을 혼동하면 안 된다.
- **흔한 오해·주의점**: priority inheritance는 역전을 완전히 없애는 것이 아니라 역전 시간을 자원을 들고 있는 임계구역 길이로 상한을 두는 것이며, 무한 대기를 유한 대기로 바꾸는 기법이다.
- **흔한 오해·주의점**: 인터럽트 레이턴시와 인터럽트 처리시간(ISR 실행시간 자체)은 다른 개념이며, 레이턴시는 ISR 진입 전까지의 지연만을 뜻한다.

## 연결 개념
- RTOS 스케줄링(Rate Monotonic, EDF) — 우선순위 배정과 데드라인 보장의 이론적 근거
- Mutex·Semaphore — 우선순위 역전이 발생하는 공유 자원 동기화 메커니즘
- Priority Ceiling Protocol — priority inheritance의 대안이자 데드락 방지까지 포함하는 확장 기법

## 핵심 인사이트 (3줄 요약)

> 1. **본질**: 인터럽트 레이턴시는 신호 발생부터 ISR 첫 명령까지의 지연이며, 우선순위 역전은 중간 우선순위 태스크가 낮은 우선순위 태스크를 계속 선점해 높은 우선순위 태스크를 간접적으로 막는 현상이다.

> 3. **판단 포인트**: 레이턴시는 하드웨어 응답·임계구역·context save·vector lookup 4구간으로 분해해 병목을 특정하고, 역전은 L-M-H 인과 순서와 inheritance 시점을 정확히 서술해야 한다.

## Ⅰ. 개요 및 필요성

- 개요: 인터럽트 레이턴시는 인터럽트 신호부터 ISR 첫 명령까지의 지연시간
- 개요: 우선순위 역전은 저우선순위 태스크의 자원 점유로 고우선순위 태스크가 무기한 대기하는 현상
- 배경: RTOS는 우선순위 기반 선점형 스케줄링을 쓰므로 임계구역과 공유 자원 잠금이 결정론성을 위협
- 필요성: 제어 주기 미준수, watchdog reset 같은 장애를 막으려면 레이턴시 상한 설계와 priority inheritance 적용이 필수

## Ⅱ. 구조 및 구성요소

```text
Interrupt Signal -> Hardware Detect/Response
  -> Critical Section 종료 대기 (interrupt disabled 구간)
  -> Context Save (register/PC/flag)
  -> Vector Lookup/ISR Dispatch
  -> ISR 첫 명령 실행
```

| 구성요소 | 역할 | 특이사항 |
|:---|:---|:---|
| Hardware Detect/Response | 인터럽트 신호를 CPU가 인지 | 클럭 주기, 인터럽트 컨트롤러 지연 |
| Critical Section 대기 | 인터럽트 비활성화 구간 종료까지 대기 | 임계구역 길이가 레이턴시 상한을 결정 |
| Context Save | 레지스터·PC·플래그를 스택에 저장 | CPU 아키텍처별 저장 레지스터 수 차이 |
| Vector Lookup/Dispatch | 인터럽트 벡터 테이블 조회 후 ISR 분기 | 벡터 테이블 크기, 우선순위 인코딩 |
| Priority Inheritance 모듈 | 자원 점유 태스크의 우선순위 임시 상승 | 뮤텍스 API의 옵션 플래그로 제공 |

> 요약: 인터럽트 레이턴시는 하드웨어 인지, 임계구역 대기, 컨텍스트 저장, 벡터 조회 4단계로 분해되고, 역전 방지는 뮤텍스 계층에서 별도로 동작한다.

---

## Ⅲ. 동작원리 및 흐름도

```text
L이 Mutex 획득 -> H가 동일 Mutex 요청 -> H Block
  -> M(우선순위 M > L, M은 Mutex 불필요)이 L을 선점
  -> L 실행 지연 -> Mutex 반납 지연 -> H 대기 지속
  [Priority Inheritance 적용 시]
  -> L이 H의 우선순위를 임시 상속 -> M이 L을 선점 불가
  -> L이 Mutex 신속 반납 -> H 재개 -> L 원래 우선순위로 복귀
```

| 단계 | 처리 내용 | 검증 기준 |
|:---:|:---|:---|
| 1 | L이 공유 자원(뮤텍스) 획득 | 점유 시각 기록 |
| 2 | H가 동일 자원 요청 후 블록 | 대기 큐 등록 여부 |
| 3 | M이 L을 선점(자원 불필요, 우선순위만 높음) | 선점 횟수, 누적 지연시간 |
| 4 | inheritance 적용 시 L이 H 우선순위로 격상되어 반납 후 H 재개 | 격상 시각, 반납까지 소요시간 |

> 요약: 우선순위 역전은 L-H 직접 관계가 아니라 M의 반복 선점이 L을 통해 H를 간접 지연시키는 구조이며, inheritance는 L의 우선순위를 임시로 높여 M의 선점을 차단한다.

## Ⅳ. 특징

| 구분 | 인터럽트 레이턴시 | 우선순위 역전 | 판단 포인트 |
|:---|:---|:---|:---|
| 발생 원인 | 하드웨어 응답·임계구역·context save·vector lookup 누적 | M이 L을 선점해 L의 자원 반납 지연 | 지연 발생 지점이 하드웨어인지 스케줄링인지 |
| 예측 가능성 | 임계구역 최소화 시 상한 예측 가능 | inheritance 미적용 시 상한 예측 불가(무기한) | 결정론적 설계 여부 |
| 대응 기법 | ISR 경량화, bottom-half 분리, 임계구역 축소 | priority inheritance, priority ceiling protocol | 자원 잠금 정책 적용 여부 |
| 실패 사례 | 워치독 타임아웃, 제어 주기 초과 | Mars Pathfinder 1997 watchdog reset | 실제 장애 재현 조건 |

> 요약: 레이턴시는 하드웨어·커널 경로의 누적 지연이고, 역전은 스케줄링 정책이 만드는 간접 지연이며 둘 다 상한을 설계로 확정해야 한다.

## Ⅴ. 심화 비교 및 적용 판단

| 비교 축 | Priority Inheritance | Priority Ceiling Protocol | 선택 기준 |
|:---|:---|:---|:---|
| 구조 | 자원 점유 시점에 동적으로 우선순위 상속 | 자원 생성 시점에 ceiling 우선순위 사전 지정 | 자원 잠금 조합이 적으면 ceiling, 동적이면 inheritance |
| 비용/성능 | 상속·반납 시 오버헤드 발생 | 데드락 방지까지 포함하나 설계 복잡도 증가 | 데드락 위험도와 구현 난이도 |
| 운영/위험 | 연쇄 상속(chained inheritance) 관리 필요 | ceiling 값 설계 오류 시 불필요한 선점 차단 | 자원별 최대 우선순위 사전 파악 가능 여부 |

> 요약: 자원 잠금 조합이 단순하면 priority ceiling, 동적이고 복잡하면 priority inheritance를 선택한다.

| 리스크 | 원인 | 대응 방안 | 확인 지표 |
|:---|:---|:---|:---|
| 무기한 우선순위 역전 | inheritance 미적용, M의 반복 선점 | 뮤텍스에 priority inheritance 옵션 활성화 | 최대 블록 시간, watchdog reset 횟수 |
| 레이턴시 상한 초과 | 임계구역 과다, ISR 내 무거운 연산 | ISR 경량화, bottom-half/deferred task 분리 | worst-case interrupt latency(WCIL) |
| 연쇄 상속 복잡도 증가 | 다중 자원 중첩 잠금 | 잠금 순서 표준화, 중첩 잠금 최소화 | 상속 체인 길이 |

> 요약: 우선순위 역전과 레이턴시 초과는 뮤텍스 옵션 활성화와 ISR 경량화, 잠금 순서 표준화로 통제한다.

| 점검 항목 | 목표 기준 | 측정 방법 |
|:---|:---|:---|
| 인터럽트 레이턴시 | worst-case latency가 제어 주기의 일정 비율 이하 | 오실로스코프, 트레이스 도구(예: Tracealyzer) |
| 우선순위 역전 시간 | H의 최대 대기시간이 임계구역 길이 합으로 상한 확정 | RTOS 트레이스, 뮤텍스 대기 로그 |
| 시스템 재부팅 이력 | watchdog reset 0건 | 이벤트 로그, 필드 리포트 분석 |

> 요약: 도입 후 성공 여부는 worst-case interrupt latency, 우선순위 역전 최대 대기시간, watchdog reset 발생 건수로 판단한다.

## Ⅵ. 실무 적용 및 결론

**적용 방안 3개 (필수 — 단계별 또는 항목별):**
1. ISR은 인터럽트 플래그 클리어와 최소 상태 저장만 수행하고 나머지 처리는 태스크나 bottom-half로 위임해 임계구역 길이를 축소함
2. 공유 자원을 잠그는 모든 뮤텍스에 priority inheritance 또는 priority ceiling protocol을 활성화하고 최대 대기시간을 사전 계산함
3. 개발 단계에서 트레이스 도구로 worst-case interrupt latency와 우선순위 역전 발생 이력을 계측해 회귀 테스트 기준에 포함함

**결론 (2줄):**
- 기술사 판단: 단순 자원 조합은 priority ceiling protocol, 동적이고 다양한 자원 조합은 priority inheritance를 선택함
- 향후 방향: 정적 분석과 런타임 트레이스를 결합해 레이턴시 상한과 역전 시간을 설계 단계부터 검증하는 체계를 구축해야 함
