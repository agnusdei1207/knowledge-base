# 📖 【암기용】 개념 완전 이해

## 한눈에
- **개요**: 스토리지 가상화는 여러 대의 이기종 물리적 스토리지 장치를 논리적인 하나의 거대한 저장 공간(Pool)으로 묶어 사용자에게 제공하는 기술이다.
- **왜 필요한가**: 스토리지 벤더가 다르면 관리 도구도 다르고 낭비되는 남은 용량을 합칠 수도 없다. 이를 하나의 풀로 묶으면 용량 관리가 편해지고 스토리지 낭비가 사라진다.
- **핵심 직관**: 여러 개의 작은 통장(물리 디스크)을 묶어서 하나의 큰 마이너스 통장(논리 볼륨)처럼 보이게 만드는 것. 통장이 어느 은행인지 사용자는 알 필요가 없다.

## 핵심 용어 정리

| 용어/표기 | 의미 | 비유·예 |
|:---|:---|:---|
| 물리 볼륨 (Physical Volume) | 실제 디스크나 스토리지 배열의 물리적 공간 | 1TB 하드디스크, 2TB SSD |
| 논리 볼륨 (Logical Volume) | 가상화를 통해 사용자(서버)에게 제공되는 가상 드라이브 | 내 컴퓨터의 C드라이브 (실제 디스크 여러 개 합일 수 있음) |
| In-Band 가상화 | 데이터와 제어 신호가 가상화 컨트롤러를 통과하는 방식 | 도로 한가운데 있는 검문소 (관리가 확실하나 병목 우려) |
| Out-of-Band 가상화 | 제어 신호만 컨트롤러가 처리하고 데이터는 직접 전송 | 하이패스와 네비게이션 (빠르지만 에이전트 설치 필요) |
| 씬 프로비저닝 (Thin Provisioning) | 실제 물리 용량보다 큰 가상 용량을 먼저 할당해두는 기술 | 항공사의 오버부킹 |

## 깊이 이해
- **배경·문제의식**: 데이터센터에 EMC, IBM, NetApp 등 다양한 스토리지가 혼재되면서(Silo 현상), A 스토리지는 꽉 차고 B 스토리지는 남는 비효율이 발생했다. 이를 통합할 소프트웨어 계층이 필요해졌다.
- **작동 원리**: 서버와 스토리지 사이에 가상화 엔진(소프트웨어 또는 어플라이언스)을 둔다. 서버가 "C드라이브의 10번 블록에 저장해"라고 명령하면, 가상화 엔진이 매핑 테이블을 보고 "아, 이건 실제 IBM 스토리지의 50번 블록이네"라고 변환하여 저장한다.
- **비유**: 대형 물류 센터. 고객(서버)은 '물품 번호'만 알고 창고에 요청한다. 물류 관리 시스템(가상화 엔진)이 A창고 구석에 있는지 B창고에 있는지 알아서 찾아준다.
- **구체 예시**: 서버 OS에 내장된 LVM(Logical Volume Manager)은 호스트 기반 가상화의 대표 예다. 네트워크 기반으로는 SAN 스위치 단에서 이기종 스토리지를 묶는 방식이 널리 쓰인다.
- **흔한 오해·주의점**: 가상화 엔진에 장애가 나면 전체 스토리지에 접근하지 못하는 단일 장애점(SPOF)이 될 수 있으므로, 반드시 이중화(HA) 구성을 해야 한다.

## 연결 개념
- 소프트웨어 정의 스토리지 (SDS) — 스토리지 가상화에서 한 걸음 더 나아가, 범용 x86 서버들을 묶어 스토리지처럼 쓰는 현대적 개념
- LVM (Logical Volume Manager) — 리눅스 환경의 호스트 기반 스토리지 가상화 도구
- 씬 프로비저닝 — 가상화를 기반으로 스토리지 할당 효율을 극대화하는 세부 기술

# 📝 【답안용】 시험 답안 템플릿

## 핵심 인사이트 (3줄 요약)

> 1. **본질**: 스토리지 가상화는 물리적 저장 장치의 위치, 기종, 한계를 추상화(Abstraction)하여 논리적 단일 스토리지 풀(Pool)로 매핑하는 기술이다.
> 2. **가치**: 스토리지 Silo 현상을 제거하여 버려지는 여유 용량을 회수하고, 씬 프로비저닝을 통해 용량 활용 효율성(Utilization)을 극대화한다.
> 3. **판단 포인트**: 가상화 엔진의 위치(Host, Network, Storage)와 통제 경로(In-band, Out-of-band)에 따라 성능 병목과 유연성이 좌우되므로 워크로드에 맞는 아키텍처 선정이 핵심이다.

## 출제 의도 및 답안 포인트

| 출제 의도 | 반드시 짚을 핵심 | 감점 회피 포인트 |
|:---|:---|:---|
| 스토리지 가상화의 구현 방식 파악 | 구현 계층(호스트, 네트워크, 스토리지) 분류 및 논리/물리 매핑 테이블 | 가상화를 단순히 디스크 파티션 나누기로 서술 |
| 네트워크 기반 통제 경로 구조 이해 | In-Band (데이터/제어 통합) vs Out-of-Band (데이터/제어 분리) | In/Out 방식의 병목과 에이전트 종속성 비교 누락 |

> 요약: 추상화 메커니즘을 명시하고, 대규모 인프라 적용 시 In-band/Out-of-band 아키텍처의 트레이드오프를 비교 판단한다.

## Ⅰ. 개요 및 필요성

- 개요: 스토리지 가상화(Storage Virtualization)는 이기종의 복수 물리적 스토리지를 통합하여 단일 논리적 가상 볼륨으로 서버에 제공하는 기술이다.
- 배경: 부서별, 업무별 스토리지 개별 도입으로 스토리지 파편화(Silo) 발생 및 이기종 스토리지 간 마이그레이션 어려움
- 필요성: 관리 포인트를 일원화하고, 유휴 용량을 논리 풀로 통합하여 전체 스토리지 투자 자원의 활용도(TCO 절감)를 높이기 위해 필요함

---

## Ⅱ. 구조 및 구성요소

```text
Server (가상 논리 볼륨 인식)
         |
[ Virtualization Engine (매핑 테이블) ]
   /             |             \
[Storage A]  [Storage B]  [Storage C] (이기종 물리 볼륨)
```

| 구성요소 | 역할 | 특이사항 |
|:---|:---|:---|
| 논리 볼륨 (Logical Volume) | 호스트가 인식하는 가상의 단일 드라이브 | 물리 제약 없이 크기 동적 확장 가능 |
| 매핑 테이블 (Mapping Table) | 논리적 주소(LUN)와 물리적 블록 주소 변환 | 메타데이터로 관리, 손실 시 데이터 접근 불가 |
| 가상화 엔진 (Appliance) | I/O 요청을 가로채어 주소 변환 및 라우팅 수행 | 단일 장애점(SPOF) 방지를 위한 HA 구성 필수 |

> 요약: 가상화 엔진이 논리/물리 주소 매핑 테이블을 관리하며 중간에서 모든 I/O를 중계하거나 길을 안내한다.

---

## Ⅲ. 동작원리 및 흐름도

```text
서버 I/O 요청(논리 주소) -> 엔진 개입 -> 주소 매핑(논리->물리) -> 대상 스토리지 전송 -> 결과 반환
```

- 1단계 [I/O 요청]: 서버가 가상화된 논리 볼륨(LUN)으로 읽기/쓰기 명령 발송
- 2단계 [주소 가로채기]: 가상화 컨트롤러 또는 에이전트가 요청을 인터셉트(Intercept)
- 3단계 [주소 매핑]: 내부 매핑 테이블을 조회하여 논리 블록 주소를 실제 이기종 스토리지의 물리 주소로 변환
- 4단계 [실제 I/O 실행]: 변환된 주소를 바탕으로 물리 스토리지에 데이터를 접근하고 서버에 완료 응답 반환

> 요약: 서버는 자신이 물리 디스크를 직접 다룬다고 생각하지만, 실제로는 가상화 엔진의 번역을 거친다.

---

## Ⅳ. 특징
- 유연한 자원 할당: 씬 프로비저닝(Thin Provisioning) 연계를 통해 물리 용량과 무관하게 거대 가상 볼륨을 선할당 가능
- 무중단 데이터 마이그레이션: 하단 물리 스토리지를 교체하거나 이동할 때, 매핑 테이블만 변경하면 호스트 서비스 중단 없음
- 벤더 종속성 탈피: 특정 제조사의 스토리지에 얽매이지 않고, 가성비 좋은 여러 스토리지 하드웨어를 혼합하여 풀(Pool) 구성 가능

> 요약: 용량 활용의 극대화와 무중단 마이그레이션이 스토리지 가상화의 가장 큰 실무적 이점이다.

## Ⅴ. 심화 비교 및 적용 판단

| 비교 축 | In-Band (대역 내) 방식 | Out-of-Band (대역 외) 방식 | 선택 기준 |
|:---|:---|:---|:---|
| 데이터 경로 | 제어 신호와 데이터가 가상화 어플라이언스를 통과 | 제어 신호만 어플라이언스 통과, 데이터는 스토리지로 직행 | I/O 성능 및 병목 허용치 |
| 성능 병목 | 어플라이언스 성능이 전체 I/O 대역폭의 병목 됨 | 데이터 우회로 대역폭 병목 없음 | 트래픽 규모 |
| 호스트 에이전트 | 서버에 별도 소프트웨어 설치 불필요 | 서버별 스토리지 라우팅 에이전트 설치 필수 | 호스트 관리 복잡도 |

> 요약: 구현 편의성과 범용성은 In-Band가 우수하나, 대규모 트래픽 환경에서는 병목이 없는 Out-of-Band 방식이 유리하다.

**스토리지 가상화 리스크·대응:**
- [단일 장애점(SPOF)]: 가상화 어플라이언스 장애 시 전체 데이터 접근 불가 → [대응 방안] 어플라이언스의 Active-Active 클러스터링 다중화 (지표: 가용성 99.999%)
- [메타데이터 오염]: 주소 매핑 테이블 손상 시 복구 불가능 → [대응 방안] 메타데이터 볼륨의 분산 실시간 복제본 구성

## Ⅵ. 실무 적용 및 결론

**적용 방안 3개:**
1. 데이터센터 통합: 노후화된 이기종 스토리지를 SAN 기반 네트워크 가상화 어플라이언스로 묶어 통합 관제 단일화
2. 씬 프로비저닝 적용: 가상화 풀 위에 씬 프로비저닝을 적용하여, 초기 디스크 구매 비용을 절감하고 실제 사용량 증가 시 디스크만 무중단 추가 증설
3. SDS로의 진화: 고가의 SAN 스위치 기반 가상화 대신, 하이퍼바이저 기반의 vSAN이나 Ceph 같은 소프트웨어 정의 스토리지(SDS) 구조로 전환

**결론 (2줄):**
- 기술사 판단: 스토리지 가상화는 단순히 디스크를 합치는 것을 넘어, 데이터 마이그레이션 비용과 다운타임을 없애주는 핵심 아키텍처 전략이다.
- 향후 방향: 전통적인 어플라이언스 기반 가상화는 점차 범용 서버의 내장 디스크를 묶는 하이퍼컨버지드 인프라(HCI)와 소프트웨어 정의 스토리지(SDS) 기술로 흡수되고 있다.
