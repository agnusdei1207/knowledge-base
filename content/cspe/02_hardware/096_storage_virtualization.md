# 📖 【암기용】 개념 완전 이해

> 목적: 이 개념을 처음 보는 사람도 완벽히 이해하게 만든다. 시험 답안 양식이 아니라, 이해를 위한 친절한 설명이다.

## 한눈에
- **개요**: 스토리지 가상화는 물리적으로 분산된 여러 저장장치를 **논리적 추상화 계층**으로 묶어, 서버에는 하나의 거대한 저장 공간 풀(Pool)처럼 보이게 하는 기술이다.
- **왜 필요한가**: 스토리지 제조사와 모델이 서로 다르면 관리 방식이 제각각이라 운영이 파편화되고, 특정 장비에만 남는 용량이 생겨 전체 활용률이 떨어진다. 스토리지 가상화는 이 이기종 장비들을 중앙에서 하나로 관리하고, 남는 용량을 어디서든 끌어다 쓸 수 있게 한다.
- **핵심 직관**: 은행 계좌와 같다. 스마트폰 앱에서 보는 잔고(가상 볼륨)는 하나지만, 실제 현금이 어느 지점 금고(물리 디스크)에 있는지는 신경 쓰지 않는다. 은행 내부의 장부(매핑 테이블)가 계좌 잔고와 실제 금고 위치를 연결해 준다.

## 핵심 용어 정리 (내부에 등장하는 것들)

| 용어 | 의미 | 비유 |
|:---|:---|:---|
| 스토리지 가상화 | 물리 저장장치를 논리적으로 추상화해 단일 자원처럼 제공하는 기술 — 이 개념 전체를 가리키는 상위 개념 | 여러 은행 지점 금고를 하나의 계좌 잔고로 묶어 보여주기 |
| LUN (Logical Unit Number) | 호스트에게 보이는 논리 볼륨의 식별 번호 | 계좌 번호 |
| LBA/PBA 매핑 | 논리 블록 주소(LBA)를 실제 물리 블록 주소(PBA)로 변환하는 테이블 | 계좌 잔고와 실제 금고 위치를 연결하는 장부 |
| 씬 프로비저닝(Thin Provisioning) | 서버에는 큰 논리 용량을 할당하되, 실제 쓰기가 발생한 만큼만 물리 용량을 소비 | 항공권 오버부킹(좌석보다 많이 팔되 실제 탑승 인원만 태움) |
| 오토 티어링(Auto Tiering) | 접근 빈도가 높은 데이터는 고속 매체(SSD)로, 낮은 데이터는 저비용 매체(HDD)로 자동 이동 | 자주 쓰는 물건은 책상 위에, 안 쓰는 물건은 창고에 |
| 인밴드(In-Band) 가상화 | 데이터 I/O와 제어(메타데이터) 신호가 같은 경로를 지나는 방식 | 화물차와 배차 지시가 같은 도로를 씀 |
| 아웃오브밴드(Out-of-Band) 가상화 | 데이터 I/O 경로와 제어 경로를 물리적으로 분리한 방식 | 화물차 도로와 배차 무전 채널을 분리 |
| SDS (Software-Defined Storage) | 특정 스토리지 하드웨어 없이, 범용 서버의 내장 디스크를 소프트웨어로 묶어 가상화 | 전용 창고 없이 여러 트럭의 짐칸을 앱으로 통합 관리 |

## 깊이 이해

### 배경 — DAS에서 가상화까지
- 서버마다 전용 디스크를 붙이던 DAS 시대에는 남는 용량은 놀고 부족한 서버는 디스크를 새로 꽂아야 했다. 이후 SAN/NAS로 네트워크 스토리지를 통합했지만, 제조사가 다른 스토리지 장비가 섞이면 관리 도구와 명령 체계가 파편화되는 사일로(Silo) 문제가 남았다. 스토리지 가상화는 이 이기종 장비들 위에 매핑 계층을 하나 더 얹어, 관리자와 서버가 벤더 차이를 신경 쓰지 않게 만든다.

### 작동 원리 — 가상화 엔진의 위치에 따른 3가지 구현
- **호스트 기반**: 서버의 OS 볼륨 매니저(LVM 등)가 직접 물리 디스크를 논리 볼륨으로 묶는다. 추가 장비가 필요 없어 비용이 낮지만, 서버 CPU 자원을 매핑 연산에 써야 하고 여러 서버가 매핑 정보를 공유하기 어렵다.
- **네트워크 기반**: SAN 스위치나 별도의 어플라이언스가 서버와 스토리지 사이에서 매핑을 처리한다. 서버 CPU 부담이 없고 벤더가 서로 다른 스토리지도 하나로 묶을 수 있지만, 이 어플라이언스 자체가 트래픽 병목이 될 수 있다.
- **스토리지 기반**: 스토리지 장비 내장 컨트롤러가 자체적으로 가상화를 수행한다. 해당 장비의 캐시·기능을 최대로 활용할 수 있지만, 다른 제조사의 스토리지를 매끄럽게 통합하기는 어렵다.

### 씬 프로비저닝 — 구체 수치로 이해
- 물리 용량이 10TB인 스토리지 풀이 있다고 하자. 씬 프로비저닝으로 서버 10대에 각각 "당신은 2TB를 할당받았다"고 알려주면, 논리적으로 할당된 총량은 20TB로 물리 용량의 200%(오버커밋)에 달한다. 실제로는 각 서버가 평균 1TB만 쓰고 있다면 물리적으로는 10TB만 소비되므로 문제가 없다. 단, 여러 서버가 동시에 실사용량을 늘리면 물리 용량을 초과(오버플로)할 위험이 있어, 물리 사용률이 특정 임계치(예: 80%)에 도달하면 자동 경고 후 풀을 증설해야 한다.

### 오토 티어링 — 구체 예시
- 어떤 데이터베이스의 데이터 중 5%는 매일 접근되는 "핫 데이터"이고 95%는 한 달에 한 번도 안 열리는 "콜드 데이터"라고 하자. 오토 티어링은 접근 빈도를 주기적으로 분석해 핫 데이터 5%만 비싼 SSD 계층으로 옮기고 나머지 95%는 저렴한 HDD 계층에 둔다. 이렇게 하면 전체 데이터를 SSD로 채울 때보다 훨씬 낮은 비용으로 체감 성능 대부분을 확보할 수 있다.

### 흔한 오해
- 스토리지 가상화를 단순히 디스크를 파티션으로 나누는 것(LVM 수준)으로 오해하기 쉽다. 하지만 실제로는 이기종 스토리지 통합, 서비스 중단 없는 볼륨 마이그레이션, 자동 계층화(오토 티어링)까지 아우르는 데이터 계층 전체의 추상화다.

## 연결 개념
- 씬 프로비저닝 — 물리 용량보다 큰 논리 용량을 미리 할당해 활용률을 높이는 응용 기술
- SDS (Software-Defined Storage) — 특정 하드웨어에 종속되지 않고 범용 서버 디스크를 소프트웨어로 가상화하는 확장 기술
- LVM (Logical Volume Manager) — OS 레벨에서 디스크 파티션을 가상화하는 가장 기초적인 호스트 기반 구현

# 📝 【답안용】 시험 답안 템플릿

> 목적: 시험장에서 25분에 그대로 쓰는 답안 양식. 작성방식(추상표현 금지·수치·도식·문제유형 전환)을 엄격히 지킨다.

## 핵심 인사이트 (3줄 요약)

> 1. **본질**: 이기종 물리 스토리지를 논리적 단일 풀(Pool)로 통합하는 논리/물리 블록 매핑 기술
> 2. **가치**: 자원 활용률 극대화(씬 프로비저닝)와 벤더 종속성 탈피, 무중단 데이터 마이그레이션 실현
> 3. **판단 포인트**: 가상화 엔진의 구현 위치(호스트, 네트워크, 스토리지)에 따라 성능 병목과 호환성 기준을 판단해야 한다.

## 출제 의도 및 답안 포인트

| 출제 의도 | 반드시 짚을 핵심 | 감점 회피 포인트 |
|:---|:---|:---|

| 가상화 엔진 위치별 아키텍처 비교 | 호스트 기반 / 네트워크 기반 / 스토리지 기반 구분 | 특정 단일 벤더 솔루션(솔루션명)에 국한된 편협한 설명 |

> 요약: 논리 주소(Virtual LUN)와 물리 주소의 분리 매핑 원리를 설명하고, 인프라 환경에 맞는 가상화 토폴로지 선택 기준을 제시해야 한다.

## Ⅰ. 개요 및 필요성

- 정의: 다수의 물리적 저장장치를 통합해 논리적 단일 볼륨(Virtual Volume)으로 추상화하여 제공하는 기술
- 배경: 이기종 스토리지가 혼재됨에 따라 관리 복잡도가 증가하고 볼륨 간 용량 불균형(Silo) 발생
- 필요성: 물리적 제약을 숨겨 디스크 사용률을 80% 이상 개선하고 서비스 중단 없는 데이터 재배치 구현

---

## Ⅱ. 구조 및 구성요소

```text
[호스트 요청] -> [논리 볼륨 매핑 (가상화 엔진)] -> [이기종 스토리지 풀]
서버 A/B        -> 가상화 테이블 (LUN -> PBA)  -> 스토리지 X (고속 SSD)
                -> 캐시 및 제어 모듈           -> 스토리지 Y (저비용 HDD)
```

| 구성요소 | 역할 | 특이사항 |
|:---|:---|:---|
| 호스트 (Host) | 가상 볼륨(Virtual LUN)을 인식하고 I/O 요청 수행 | 물리 디스크의 실제 위치 인지 불필요 |
| 가상화 엔진 | 논리 주소(LBA)를 물리 주소(PBA)로 변환 라우팅 | 매핑 테이블 유지 및 읽기/쓰기 캐싱 수행 |
| 스토리지 풀 | 이기종 물리 스토리지가 논리적으로 통합된 저장 공간 | 용량별·성능별(Tier) 그룹화하여 관리 |

> 요약: 가상화 엔진이 중간에서 매핑 테이블을 관리하여, 호스트는 단일 볼륨만 바라보고 백엔드 스토리지 풀은 독립적으로 확장된다.

---

## Ⅲ. 동작원리 및 흐름도

```text
[호스트 I/O 발생] -> [가상화 맵 조회] -> [물리 I/O 라우팅] -> [응답 및 동기화]
```

| 단계 | 처리 내용 | 검증 기준 |
|:---:|:---|:---|
| 1 | 호스트의 애플리케이션 Read/Write 요청 | Virtual LUN 타겟 식별 |
| 2 | 가상화 엔진의 메모리 내 논리/물리 매핑 조회 | 맵 캐시 히트율(Hit-rate) |
| 3 | 대상 물리 스토리지 컨트롤러로 트래픽 라우팅 | 경로 이중화(MPIO) 검증 |
| 4 | 실제 디스크 I/O 처리 후 호스트에 완료 응답 반환 | 총 레이턴시(ms 단위) |

> 요약: 호스트의 논리적 I/O를 가상화 엔진이 가로채 매핑 테이블을 참조하여 실제 물리 디바이스의 I/O로 투명하게 변환·전달한다.

## Ⅳ. 가상화 엔진 위치별 비교 (특징)

| 구분 | 호스트 기반 | 네트워크 기반 | 스토리지 기반 |
|:---|:---|:---|:---|
| 가상화 위치 | 서버 OS 볼륨 매니저 (LVM) | SAN 스위치 / 인밴드 어플라이언스 | 스토리지 컨트롤러 내부 엔진 |
| 장점 | 스위치 등 추가 하드웨어 도입 비용 없음 | 서버 부하 없음, 벤더 제약 없는 완벽한 이기종 통합 | 제조사 고유 기능 최적화, 고성능 대용량 캐시 |
| 한계 | 서버 CPU 리소스 점유, 멀티 서버 공유 난해 | 트래픽 병목 가능성, 전용 어플라이언스 도입 비용 | 타 벤더 스토리지 연동 제약 (종속성 잔존) |
| 판단 기준 | 소규모 혹은 단일 벤더 서버 환경 | 이기종 스토리지 통합이 시급한 대규모 SAN 환경 | 하이엔드 단일 스토리지 중심 통합 환경 |

> 요약: 인프라 규모와 이기종 스토리지 혼재 수준에 따라 가상화 위치를 결정하며, 대규모 통합 시 네트워크 기반 가상화를 우선 검토한다.

## Ⅴ. 심화 확장 기술 및 적용 지표

| 확장 기술 | 핵심 기능 | 측정 지표 / 판단 기준 |
|:---|:---|:---|
| 씬 프로비저닝 | 장래 수요를 예측하여 물리 용량보다 큰 논리 용량 사전 할당 | 오버커밋(Over-commit) 비율 및 물리 공간 임계치 경고 |
| 오토 티어링 | I/O 빈도에 따라 핫 데이터는 SSD로, 콜드 데이터는 HDD로 자동 이동 | 핫 데이터 판별 분석 주기 및 마이그레이션 부하량 |
| 무중단 마이그레이션 | 서버 중단 없이 구형 스토리지에서 신형 스토리지로 볼륨 백그라운드 복제 | 마이그레이션 중 호스트 I/O 지연(RTO 제로) 유지 여부 |

> 요약: 스토리지 가상화는 용량 속임수(Thin Provisioning)와 동적 계층화(Auto Tiering) 기술을 결합하여 ROI를 실질적으로 극대화한다.

## Ⅵ. 실무 적용 방안 및 결론

**적용 방안 3개:**
1. [구축 전략] 인밴드(In-Band) 및 아웃오브밴드(Out-of-Band) 방식 설계 시, I/O 지연에 민감한 DB 환경은 데이터와 메타데이터 경로가 분리된 아웃오브밴드 방식을 선별 도입
2. [용량 최적화 프로세스] 씬 프로비저닝 적용 시, 할당된 논리 용량이 아닌 실제 쓰인 물리 용량 임계치(예: 80%) 도달 시 자동 경고 및 긴급 스토리지 풀 증설 프로세스(Runbook) 수립
3. [현대화 아키텍처 연계] 특정 스토리지 하드웨어 종속성을 완전히 탈피하기 위해 x86 범용 서버 클러스터 기반의 SDS(Software-Defined Storage, 예: Ceph, vSAN)로 점진적 전환 설계

**결론:**
- 기술사 판단: 스토리지 환경이 2~3개 이상의 벤더로 파편화되어 용량 낭비가 심하다면, 스토리지 컨트롤러 기반보다 네트워크 기반 스토리지 가상화를 통해 풀링(Pooling)을 우선 구현해야 한다.
- 향후 방향: 레거시 하드웨어 종속적인 가상화 어플라이언스 방식에서 벗어나, 쿠버네티스 컨테이너 환경(CSI 연동)과 분산 SDS 기반 아키텍처로 진화하고 있다.
