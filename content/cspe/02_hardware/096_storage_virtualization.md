# 📖 【암기용】 개념 완전 이해

> 목적: 스토리지 가상화가 물리 디스크와 논리 볼륨을 어떻게 분리하는지 처음 봐도 이해하게 만든다. 시험 답안 양식이 아니라, 이해를 위한 친절한 설명이다.

## 한눈에
- **개요**: 여러 물리적 저장장치를 하나의 논리적 자원 풀로 추상화해 호스트에는 가상 볼륨(LUN)으로 제공하는 기술
- **왜 필요한가**: 이기종 벤더의 스토리지 장비를 개별 관리하면 용량 낭비와 마이그레이션 비용이 커지므로, 논리 계층으로 통합해 유연하게 배분해야 한다.
- **핵심 직관**: 여러 은행 계좌(물리 디스크)를 하나의 통합 잔고(논리 볼륨)로 보여주는 자산관리 앱과 같다.

## 깊이 이해
- **배경·문제의식**: 물리 디스크를 호스트가 직접 인식하면 특정 디스크 용량 부족·교체 시 애플리케이션 중단이 불가피하고, 벤더별 관리 도구가 달라 운영 복잡도가 커진다.
- **작동 원리**: 스토리지 가상화는 물리 계층과 논리 계층 사이에 매핑 테이블을 두어, 호스트는 논리 볼륨(LUN)만 보고 실제 물리 디스크 위치는 가상화 계층이 알아서 배치·이동한다.
- **작동 원리 보충**: 가상화 위치에 따라 호스트 기반(운영체제 볼륨 매니저), 네트워크 기반(SAN 상의 별도 어플라이언스), 어레이 기반(스토리지 컨트롤러 내장 기능) 세 층위로 나뉜다.
- **작동 원리 보충2**: 네트워크 기반 가상화는 다시 인밴드(in-band)와 아웃오브밴드(out-of-band)로 나뉘는데, 인밴드는 가상화 장치가 데이터 경로에 직접 위치해 모든 I/O를 중계하고, 아웃오브밴드는 메타데이터(매핑 정보) 관리만 별도 컨트롤러가 담당하고 실제 데이터는 호스트가 스토리지와 직접 주고받는다.
- **비유**: 인밴드는 모든 택배가 반드시 거치는 물류 허브(지연 발생 가능)이고, 아웃오브밴드는 배송 주소만 알려주는 안내소(실제 배송은 직접 경로)에 비유된다.
- **구체 예시**: 씬 프로비저닝(thin provisioning) — 호스트에는 10TB 볼륨을 할당했다고 보여주지만 실제 데이터가 쓰인 만큼만 물리 용량을 소비하는 방식. 스토리지 티어링(tiering) — 접근 빈도가 높은 데이터는 자동으로 SSD 티어로, 낮은 데이터는 HDD 티어로 이동시키는 방식.
- **흔한 오해·주의점**: 씬 프로비저닝은 논리 용량과 물리 사용량의 차이를 이용하는 기법이라, 물리 용량 모니터링을 소홀히 하면 논리적으로는 여유가 있어도 실제 물리 풀이 고갈되는 "오버커밋 고갈" 위험이 있다.
- **흔한 오해·주의점 보충**: 스토리지 가상화는 RAID와 다른 개념으로, RAID는 물리 디스크 묶음의 중복성·성능을 다루고, 스토리지 가상화는 그 위에서 논리 볼륨의 배치·이동·풀링을 다룬다.

## 연결 개념
- 스토리지 계층 — DAS·NAS·SAN — 가상화가 적용되는 물리 연결 기반
- RAID 레벨 0·1·5·6·10 비교 — 가상화 하위 계층의 물리적 중복성 구성 방식
- 서버 가상화 — Type 1·Type 2 하이퍼바이저 — 컴퓨트 자원 가상화와의 대응 개념

# 📝 【답안용】 시험 답안 템플릿

> 목적: 시험장에서 25분에 그대로 쓰는 답안 양식. 작성방식(추상표현 금지·수치·도식·문제유형 전환)을 엄격히 지킨다.
> 핵심: 스토리지 가상화를 단일 개념으로 뭉개지 않고 가상화 위치(호스트/네트워크/어레이)와 인밴드·아웃오브밴드 구조로 구분해 답안을 구성한다.

## 핵심 인사이트 (3줄 요약)

> 1. **본질**: 스토리지 가상화는 물리 디스크와 호스트가 인식하는 논리 볼륨(LUN) 사이에 매핑 계층을 두어 자원을 풀링·추상화하는 기술이다.
> 2. **가치**: 씬 프로비저닝·티어링·논디스럽티브 마이그레이션으로 용량 활용률을 높이고 벤더 종속을 줄인다.
> 3. **판단 포인트**: 인밴드는 관리가 단순하지만 데이터 경로 병목 위험이 있고, 아웃오브밴드는 지연이 적지만 호스트 에이전트 등 추가 구성이 필요하다는 점을 기준으로 선택한다.

## 출제 의도 및 답안 포인트

| 출제 의도 | 반드시 짚을 핵심 | 감점 회피 포인트 |
|:---|:---|:---|
| 가상화 계층 구조 이해 확인 | 호스트·네트워크·어레이 기반 가상화 위치 구분 | 세 위치를 구분하지 않고 하나로 서술 |
| 인밴드·아웃오브밴드 구조 확인 | 데이터 경로 위치와 지연·복잡도 트레이드오프 | 인밴드·아웃오브밴드 차이 누락 |
| 운영 기법 이해 확인 | 씬 프로비저닝, 티어링, 오버커밋 리스크 | 씬 프로비저닝을 무한 확장 가능한 것으로 서술 |

> 요약: 이 문제는 가상화 정의보다 적용 위치(호스트/네트워크/어레이)와 인밴드·아웃오브밴드 구조, 오버커밋 리스크 관리 방안을 함께 요구한다.

## Ⅰ. 개요 및 필요성

- 개요: 물리 저장장치를 논리적 자원 풀로 추상화해 호스트에 가상 볼륨으로 제공하는 기술
- 배경: 이기종 벤더 스토리지를 개별 관리하면 용량 낭비, 마이그레이션 중단, 관리 복잡도가 커짐
- 필요성: 물리 계층과 논리 계층을 분리해 씬 프로비저닝·티어링·무중단 마이그레이션 같은 유연한 운영이 필요함

---

## Ⅱ. 구조 및 구성요소

```text
물리 디스크(이기종 벤더) -> 매핑 테이블(가상화 계층)
  / 호스트 기반: OS 볼륨 매니저(LVM 등)
  / 네트워크 기반: SAN 상 가상화 어플라이언스(In-band/Out-of-band)
  / 어레이 기반: 스토리지 컨트롤러 내장 가상화
-> 논리 볼륨(LUN) -> 호스트/애플리케이션
```

| 구성요소 | 역할 | 특이사항 |
|:---|:---|:---|
| 호스트 기반 가상화 | 서버 OS 볼륨 매니저가 여러 디스크를 논리 볼륨으로 통합 | 서버별 개별 관리, 벤더 독립적 |
| 네트워크 기반(In-band) | 가상화 어플라이언스가 데이터 경로에 직접 위치 | 모든 I/O 경유로 지연·단일 장애점 위험 |
| 네트워크 기반(Out-of-band) | 메타데이터 컨트롤러가 매핑만 관리, 데이터는 직접 전송 | 호스트에 별도 에이전트 필요 |
| 어레이 기반 가상화 | 스토리지 컨트롤러가 자체적으로 풀링·티어링 수행 | 벤더 종속적이나 성능·안정성 높음 |

> 요약: 스토리지 가상화는 적용 위치에 따라 호스트·네트워크(인밴드/아웃오브밴드)·어레이 기반으로 나뉘며 각각 관리 주체와 성능 트레이드오프가 다르다.

---

## Ⅲ. 동작원리 및 흐름도

```text
호스트 I/O 요청 -> 가상화 계층이 논리 볼륨(LUN) 주소 수신
  -> 매핑 테이블 조회(물리 디스크 위치 확인)
  -> 물리 I/O 수행(필요 시 티어 이동·씬 프로비저닝 확장)
  -> 결과 반환 -> 사용량·용량 모니터링 갱신
```

| 단계 | 처리 내용 | 검증 기준 |
|:---:|:---|:---|
| 1 | 호스트가 논리 볼륨(LUN) 주소로 I/O 요청 | LUN 매핑 유효성 |
| 2 | 가상화 계층이 매핑 테이블로 물리 위치 확인 | 매핑 테이블 최신성 |
| 3 | 물리 디스크에서 실제 I/O 수행 | 물리 티어·용량 상태 |
| 4 | 씬 프로비저닝 시 실제 사용량만큼 물리 블록 할당 | 오버커밋 비율 |
| 5 | 사용량·성능 모니터링으로 티어링·용량 재배치 | 티어 이동 정확성, 임계치 초과 여부 |

> 요약: 가상화 계층은 논리 요청을 매핑 테이블로 물리 위치에 연결하고, 씬 프로비저닝·티어링으로 물리 자원을 동적으로 배분한다.

---

## Ⅳ. 특징

| 구분 | 호스트 기반 | 네트워크 기반(In-band/Out-of-band) | 어레이 기반 | 수치·표준 포인트 |
|:---|:---|:---|:---|:---|
| 관리 주체 | 서버 OS(볼륨 매니저) | 별도 가상화 어플라이언스/컨트롤러 | 스토리지 컨트롤러 자체 | 벤더 종속도: 어레이 기반이 가장 높음 |
| 성능 특성 | 서버별 개별 처리, 확장성 제한 | In-band는 경로 지연, Out-of-band는 에이전트 필요 | 컨트롤러 내장으로 최적화된 성능 | In-band 단일 장애점 위험 존재 |
| 이기종 지원 | 벤더 독립적 | 상대적으로 이기종 지원 용이 | 동일 벤더 내에서 강함 | 멀티벤더 통합은 네트워크 기반이 유리 |
| 대표 기법 | LVM, Storage Spaces | SAN 가상화 어플라이언스 | 어레이 기반 스냅샷·리플리케이션 | 씬 프로비저닝·티어링은 계층 무관하게 적용 가능 |

> 요약: 가상화 위치별로 관리 주체와 이기종 지원 범위가 다르며, In-band는 단일 장애점 위험, Out-of-band는 호스트 에이전트 부담이라는 트레이드오프가 있다.

## Ⅴ. 심화 비교 및 적용 판단

| 비교 축 | In-band 가상화 | Out-of-band 가상화 | 선택 기준 |
|:---|:---|:---|:---|
| 구조 | 가상화 장치가 데이터 경로에 직접 위치 | 메타데이터 컨트롤러와 데이터 경로 분리 | 단순 관리 우선이면 In-band, 저지연 우선이면 Out-of-band |
| 비용/성능 | 모든 I/O가 경유해 지연·병목 가능 | 데이터 직접 전송으로 지연 낮음, 에이전트 구축 비용 발생 | 호스트 에이전트 배포 여력에 따라 결정 |
| 운영/위험 | 단일 장애점 위험, 이중화 필요 | 메타데이터 컨트롤러 장애 시 매핑 갱신 중단 | 이중화·페일오버 설계 여부로 판단 |

> 요약: 관리 단순성이 중요하면 In-band, 저지연·확장성이 중요하면 Out-of-band를 선택하되 둘 다 이중화 설계가 필요하다.

| 리스크 | 원인 | 대응 방안 | 확인 지표 |
|:---|:---|:---|:---|
| 오버커밋 고갈 | 씬 프로비저닝 논리 용량과 물리 용량 괴리 방치 | 물리 용량 사용률 임계치 알림, 자동 확장 정책 | 물리 풀 잔여 용량 비율 |
| In-band 단일 장애점 | 가상화 어플라이언스 이중화 미비 | 액티브-액티브 이중화, 페일오버 테스트 | 페일오버 소요 시간(RTO) |
| 매핑 불일치 | 마이그레이션 중 매핑 테이블 갱신 오류 | 무중단 마이그레이션 절차 검증, 롤백 계획 수립 | 마이그레이션 후 데이터 정합성 검증 결과 |

> 요약: 스토리지 가상화의 핵심 리스크는 오버커밋 고갈과 단일 장애점이며, 용량 임계치 모니터링과 이중화로 통제한다.

| 점검 항목 | 목표 기준 | 측정 방법 |
|:---|:---|:---|
| 용량 효율 | 물리 용량 사용률과 씬 프로비저닝 오버커밋 비율 관리 | 스토리지 관리 콘솔, 용량 리포트 |
| 성능 | 가상화 계층 경유로 인한 지연 증가폭 목표치 이내 | I/O 벤치마크(IOPS, latency) |
| 가용성 | 가상화 어플라이언스·컨트롤러 이중화로 RTO 목표 충족 | 페일오버 테스트, 장애 시뮬레이션 |

> 요약: 스토리지 가상화 도입 효과는 용량 효율, 지연 증가폭, 이중화 기반 RTO 지표로 판단한다.

## Ⅵ. 실무 적용 및 결론

**적용 방안 3개:**
1. 이기종 벤더 스토리지 통합이 필요한 환경은 네트워크 기반 가상화(Out-of-band 우선 검토)를 적용하고 메타데이터 컨트롤러 이중화를 함께 설계함
2. 씬 프로비저닝 적용 시 물리 용량 사용률 임계치(예: 80%)에서 자동 경고·확장 정책을 설정해 오버커밋 고갈을 방지함
3. 접근 빈도가 다른 데이터는 자동 티어링 정책으로 SSD·HDD 티어 간 이동시켜 비용과 성능을 동시에 최적화함

**결론 (2줄):**
- 기술사 판단: 스토리지 가상화는 도입 위치(호스트/네트워크/어레이)와 인밴드·아웃오브밴드 구조를 워크로드 요구에 맞춰 선택해야 효과가 있음
- 향후 방향: 소프트웨어 정의 스토리지(SDS)와 클라우드 스토리지 게이트웨이로 가상화 범위가 온프레미스를 넘어 하이브리드 클라우드까지 확장되는 추세임
