# 📖 【암기용】 개념 완전 이해

> 목적: 물리 메모리보다 큰 프로그램이 어떻게 돌아가는지, 페이징과 세그멘테이션이 각각 어떤 대가를 치르는지 수치로 이해하게 만든다.

## 한눈에
- **개요**: **가상 메모리(Virtual Memory)**는 물리 메모리(RAM)의 크기 한계를 감추고, 각 프로세스에게 "내가 메모리 전체를 독점하고 있다"는 연속된 논리 주소 공간을 제공하는 OS·하드웨어 합작 기법이다. 이를 구현하는 두 가지 대표 방식이 고정 크기로 자르는 **페이징(Paging)**과 의미 단위로 자르는 **세그멘테이션(Segmentation)**이다.
- **왜 필요한가**: 8GB RAM에서 10GB짜리 프로그램을 실행하려면, 프로그램 전체를 한꺼번에 메모리에 올릴 필요 없이 지금 당장 쓰는 부분만 올리고 나머지는 디스크에 두면 된다. 이를 위해서는 프로그램이 쓰는 논리(가상) 주소와 실제 RAM 상의 물리 주소를 분리해서 관리하는 체계가 필요하다.
- **핵심 직관**: 페이징은 책을 무조건 4KB 크기로 기계적으로 잘라 빈 책장 아무 데나 꽂는 방식이고(빈틈은 없지만 마지막 조각이 남는다), 세그멘테이션은 챕터(의미) 단위로 잘라 꽂는 방식이다(관리는 편하지만 챕터 크기가 제각각이라 빈틈이 생긴다).

## 핵심 용어 정리 (내부에 등장하는 것들)

| 표기/용어 | 의미 | 비유 |
|:---|:---|:---|
| 가상 메모리(Virtual Memory) | 물리 메모리 크기와 무관하게 프로세스에 독립된 논리 주소 공간을 주는 상위 개념 | 실제 창고 크기와 무관한 "내 전용 창고" 환상 |
| 물리 메모리(Physical Memory) | 실제 RAM 칩의 저장 공간 | 진짜 창고 |
| 페이지(Page) | 가상 메모리를 고정 크기(보통 4KB)로 기계적으로 자른 단위 | 규격화된 4KB짜리 상자 |
| 프레임(Frame) | 물리 메모리를 페이지와 같은 크기로 자른 단위 — 페이지가 실제로 담기는 자리 | 상자가 들어가는 창고 칸 |
| 세그먼트(Segment) | 코드·데이터·스택처럼 의미 단위로 나눈, 크기가 제각각인 논리적 블록 | 크기가 다른 상자(옷장, 책장, 냉장고) |
| 페이지 테이블(Page Table) | 가상 페이지 번호 → 물리 프레임 번호 매핑을 담은 장부 | 상자 위치 안내 대장 |
| 세그먼트 테이블(Segment Table) | 세그먼트 번호 → Base(시작 주소)+Limit(크기) 매핑을 담은 장부 | 가구 배치도 |
| 내부 단편화(Internal Fragmentation) | 고정 크기 페이지에 데이터를 채우고 남는, 페이지 내부의 못 쓰는 공간 | 4KB 상자에 1KB만 채워 3KB가 빔 |
| 외부 단편화(External Fragmentation) | 가변 크기 세그먼트를 배치하다 생기는, 조각난 빈 공간(사이즈가 안 맞아 못 씀) | 가구 사이사이 애매하게 남는 빈 벽 공간 |
| Demand Paging(요구 페이징) | 지금 당장 필요한 페이지만 RAM에 올리고 나머지는 디스크에 두는 정책 | 지금 읽을 페이지만 책상에 꺼내둠 |
| Page Fault | CPU가 요청한 페이지가 RAM에 없어 발생하는 예외 — 디스크에서 가져와야 함 | 책상에 없는 페이지를 찾으러 서고까지 감 |
| Paged Segmentation(단편화 페이징) | 먼저 세그먼트(의미)로 나누고 그 세그먼트를 다시 페이지(고정 크기)로 잘라 배치하는 하이브리드 방식 | 가구(세그먼트)를 규격 컨테이너(페이지)에 나눠 담아 창고에 넣음 |

## 깊이 이해

### 내부 단편화 — 수치로 보기 (페이징의 대가)
- 페이지 크기가 4KB인 시스템에서 10KB짜리 데이터를 저장한다고 하자. 필요한 페이지 수는 ⌈10KB / 4KB⌉ = 3페이지, 즉 12KB가 할당된다. 실제 쓰는 건 10KB이므로 마지막 페이지에서 2KB가 낭비된다 — 할당량 대비 2/12 ≈ 16.7%가 내부 단편화다.
- 파일 크기가 무작위라면, 프로세스마다 마지막 페이지에서 평균적으로 페이지 크기의 절반 정도가 낭비된다고 근사할 수 있다(4KB 페이지면 프로세스당 평균 약 2KB). 페이지 크기를 줄이면 이 낭비는 줄지만 페이지 테이블 엔트리 수(관리 오버헤드)는 늘어난다 — 페이지 크기를 정할 때의 근본 트레이드오프다.

### 외부 단편화 — 수치로 보기 (세그멘테이션의 대가)
- 세그멘테이션에서는 크기가 다른 세그먼트를 순서대로 배치하다 보면, 프로세스가 종료되며 빈 공간이 여기저기 흩어진다. 예를 들어 전체 빈 공간의 합이 10MB라도, 그 공간이 2MB·3MB·5MB짜리 조각 3개로 흩어져 있다면 6MB짜리 새 세그먼트는 들어갈 자리가 없다 — 총량은 충분한데 "연속된" 공간이 부족해서 할당에 실패하는 것이 외부 단편화의 본질이다.
- 페이징은 어차피 프레임 단위(4KB)로 흩어 담기 때문에 "연속된 공간"이 필요 없어 외부 단편화가 원천적으로 생기지 않는다. 대신 각 프레임 내부의 자투리(내부 단편화)를 감수한다 — 두 기법은 단편화의 종류를 맞바꾼 관계다.

### Demand Paging이 여러 프로세스를 동시에 띄우는 원리 — 수치로 보기
- 프로세스 하나가 논리적으로 100MB를 요구해도 실제로 동시에 활성 참조하는 범위(작업 집합, working set)는 훨씬 작다. 예를 들어 물리 메모리가 총 1GB이고 각 프로세스가 실제로 동시에 쓰는 페이지가 평균 20MB라면, 전체를 미리 다 올리는 방식으로는 최대 10개 프로세스(1GB/100MB)만 동시 실행 가능하지만, Demand Paging으로 실제 사용분만 올리면 이론상 최대 50개(1GB/20MB)까지 동시에 실행할 수 있다. 다중 프로그래밍 정도(Degree of Multiprogramming)가 이렇게 늘어나는 것이 Demand Paging의 핵심 이득이다.
- 대가는 Page Fault다. 요청한 페이지가 RAM에 없으면 디스크 I/O(밀리초 단위)가 발생하는데, 이는 RAM 접근(수십~수백 ns)보다 수천~수만 배 느리다. Page Fault 자체를 없앨 수는 없어도 빈도를 낮추는 것이 페이지 교체 알고리즘(다음 절)의 목표다.

### 왜 현대 OS는 둘을 섞어 쓰는가 (Paged Segmentation)
- 세그멘테이션만 쓰면 의미 단위 보호(코드는 읽기 전용, 데이터는 쓰기 가능 등)는 쉽지만 외부 단편화가 심하다. 페이징만 쓰면 외부 단편화는 없지만, 서로 다른 성격의 데이터(코드·변수)가 같은 4KB 페이지 안에 섞여 세밀한 권한 제어가 어렵다.
- x86 계열은 먼저 의미 단위(코드 세그먼트, 데이터 세그먼트 등)로 크게 나눠 보호 속성을 부여하고, 그 세그먼트 내부를 다시 4KB 페이지로 잘라 물리 메모리에 배치한다. 세그먼트 수준에서 "무엇을 보호할지"를, 페이지 수준에서 "어떻게 흩어 담을지"를 각각 담당시켜 두 기법의 장점만 취한다.

### 비유로 정리
- 페이징: 화물 컨테이너(4KB) — 짐이 크든 작든 규격 컨테이너에 담아 배에 꽉 채운다. 배에 빈틈(외부 단편화)은 없지만 컨테이너 하나가 덜 찰 수 있다(내부 단편화).
- 세그멘테이션: 승용차·버스·트럭 — 크기가 제각각이라 주차장(RAM)에 세우다 보면 차 사이에 애매한 빈 공간(외부 단편화)이 생긴다.

### 흔한 오해·주의점
- "페이징을 쓰면 메모리가 전혀 낭비되지 않는다"는 반만 맞다. 조각난 빈 공간(외부 단편화)은 없지만, 각 페이지 내부의 자투리(내부 단편화)는 여전히 남는다.
- 가상 메모리는 단순히 "디스크를 RAM처럼 쓰는 것"에 그치지 않는다. 프로세스마다 독립된 주소 공간을 주므로, 한 프로세스가 다른 프로세스의 메모리를 침범하지 못하게 막는 보호·격리 기능도 함께 제공한다.

## 연결 개념
- TLB(앞 절) — 페이지 테이블 조회를 매번 반복하는 비용을 없애주는 주소 변환 캐시
- 페이지 교체 알고리즘(다음 절) — 물리 프레임이 꽉 찼을 때 Demand Paging이 어떤 페이지를 내보낼지 결정하는 규칙
- MMU — 페이지 테이블·세그먼트 테이블을 실제로 참조해 주소를 변환하는 하드웨어

# 📝 【답안용】 시험 답안 템플릿

> 목적: 시험장에서 25분에 그대로 쓰는 답안 양식. 

## 핵심 인사이트 (3줄 요약)

> 1. **본질**: 가상 메모리는 주 기억장치의 물리적 한계를 은닉하고 각 프로세스에 독립적인 연속 주소 공간을 제공하는 OS와 MMU 하드웨어의 메모리 추상화 기술이다.
> 2. **가치**: 프로그램의 일부분만(Demand Paging) RAM에 적재하여 다중 프로그래밍 정도(Degree of Multiprogramming)를 높이고, 메모리 보호 및 격리 보안성을 달성한다.
> 3. **판단 포인트**: 고정 크기 할당인 페이징은 내부 단편화가, 가변 크기 할당인 세그멘테이션은 외부 단편화가 발생하므로, 현대 운영체제는 논리적 분할과 물리적 배치를 결합한 단편화 페이징(Paged Segmentation) 기법을 표준으로 사용한다.

## 출제 의도 및 답안 포인트

| 출제 의도 | 반드시 짚을 핵심 | 감점 회피 포인트 |
|:---|:---|:---|
| 가상 메모리의 할당 방식과 단편화(Fragmentation) 한계 대조 | 페이징(고정 할당, 내부 단편화), 세그멘테이션(가변 할당, 외부 단편화) 비교표 | "가상 메모리는 디스크를 RAM처럼 쓰는 것"이라는 단순 정의에 머무는 것 (보호와 격리 목적 누락) |
| 주소 변환(MMU, 페이지 테이블)의 마이크로 아키텍처 이해 | 논리 주소 분할 구조, 페이지 테이블 참조 및 Page Fault 처리 흐름 | 페이징 기법만 쓰고 세그멘테이션의 논리적 의미(접근 제어) 가치를 누락 |

> 요약: 공간 낭비를 줄이려는 하드웨어적 접근(페이징)과 의미/보안을 지키려는 소프트웨어적 접근(세그멘테이션)의 명확한 트레이드오프를 서술해야 한다.

## Ⅰ. 개요 및 필요성

- 정의: 프로세스 전체가 메모리 내에 올라오지 않더라도 실행이 가능하도록 물리 주소와 논리 주소를 분리 매핑하는 메모리 관리 기법
- 배경: 물리 메모리(RAM) 크기를 초과하는 대규모 애플리케이션 등장 및 다중 스레드 환경에서의 메모리 공간 충돌(침범) 문제
- 필요성: 불연속 메모리 할당을 통해 물리 메모리의 단편화(Fragmentation)를 해소하고, 프로세스 간 완벽한 주소 공간 격리로 시스템 안정성 확보

## Ⅱ. 구조 및 구성요소 (가상 주소 변환 아키텍처)

```text
[MMU 기반 가상 주소 -> 물리 주소 변환 구조]
CPU (가상 주소 생성) -> [ MMU (Memory Management Unit) ] -> 실제 RAM / 디스크 접근
   |--> 논리 주소 (페이지 번호 p + 오프셋 d)
   |--> [ 페이지 테이블 조회 (RAM 또는 TLB) ]
   |--> 물리 주소 (프레임 번호 f + 오프셋 d) 
```

| 구성요소 | 핵심 역할 | 상세 하위 요소 / 특징 |
|:---|:---|:---|
| 페이지 (Page) | 가상 메모리의 고정 크기 분할 단위 | 보통 4KB 단위. OS가 관리하는 논리적 블록 |
| 프레임 (Frame) | 물리 메모리의 고정 크기 분할 단위 | 페이지와 크기가 1:1로 일치. 페이지가 실제로 탑재되는 빈 공간 |
| MMU | 런타임 하드웨어 주소 변환기 | CPU 다이(Die) 내장, TLB를 포함하여 초고속 주소 매핑 수행 |
| 페이지 테이블 | 각 페이지가 위치한 프레임 주소 매핑 장부 | RAM에 저장되며, Valid 비트를 통해 현재 RAM에 있는지 디스크(Swap)에 있는지 판별 |

> 요약: 가상 메모리는 연속된 논리 주소를 쪼개어 불연속적인 물리 프레임에 흩뿌리고, 페이지 테이블이라는 장부로 이를 이어 붙인다.

## Ⅲ. 동작원리 및 흐름도 (Page Fault 처리)

```text
[요구 페이징(Demand Paging) 및 Page Fault 런타임 흐름]
1. CPU 주소 요청 -> MMU가 페이지 테이블(또는 TLB) 검사
2. Valid Bit = 0 감지 (메모리에 없음) -> [ Page Fault 인터럽트 발생 ]
3. OS 커널 개입 -> 디스크(Swap)에서 해당 페이지 I/O 인출 
4. 빈 프레임에 적재 (없으면 LRU로 기존 프레임 방출) -> 페이지 테이블 Valid 갱신 -> 명령어 재시작
```

| 단계 | 제어 주체 | 처리 내용 (성능 오버헤드 관점) |
|:---:|:---|:---|
| 1 | H/W (MMU) | 논리 주소를 물리 주소로 1클럭 내에 변환 시도 |
| 2 | H/W Exception | 캐시/메모리에 데이터가 없음을 감지하고 OS에 트랩(Trap) 전송 |
| 3 | S/W (OS) | 디스크 I/O가 발생하므로, 해당 스레드를 Block 상태로 재우고 문맥 교환 수행 |
| 4 | S/W (OS) | I/O 완료 시 인터럽트 반환 후 페이지 테이블 갱신 및 스레드 재가동 |

> 요약: Page Fault는 메모리 접근 시간을 100ns에서 수 밀리초(디스크 속도)로 1만 배 이상 폭증시키는 치명적 지연이므로 최소화가 필수적이다.

## Ⅳ. 심화 비교: 페이징 vs 세그멘테이션

| 비교 축 | 페이징 (Paging) | 세그멘테이션 (Segmentation) | 판단 포인트 |
|:---|:---|:---|:---|
| 분할 기준 | 고정 크기 (기계적 분할, 예: 4KB) | 가변 크기 (논리적 의미 단위, Code/Data 등) | 사용자(프로그래머) 시각 반영 여부 |
| 메모리 낭비 | **내부 단편화** (끝부분 4KB 미만 시 공간 낭비) | **외부 단편화** (크기가 달라 애매한 빈틈 발생) | 연속 할당 여부에 따른 단편화 파생 |
| 보안 및 보호 | 4KB 단위라 Code와 Data가 섞일 위험 | 세그먼트 단위 권한(Read/Write/Exec) 부여 용이 | 의미 단위의 공유 및 보호 정책 |
| 구현 테이블 | 페이지 테이블 (페이지 번호 -> 프레임 번호) | 세그먼트 테이블 (세그먼트 번호 -> Base + Limit) | Base/Limit 레지스터 검사 필수 |

> 요약: 페이징은 "물리적 공간 최적화(단편화 억제)"에 뛰어나고, 세그멘테이션은 "논리적 보안 제어 및 공유"에 뛰어나다.

## Ⅴ. 제약 사항 및 하이브리드(Paged Segmentation) 구조 판단

| 리스크 | 발생 원인 | 아키텍처 대응 방안 (단편화 페이징) | 해결 원리 및 효과 |
|:---|:---|:---|:---|
| 외부 단편화 붕괴 | 순수 세그멘테이션 사용 시, 메모리 빈 공간이 조각나서 큰 세그먼트 적재 불가 | **단편화 페이징 (Paged Segmentation)** | 먼저 세그먼트(논리)로 나누고, 그 세그먼트를 다시 고정 크기 페이지(물리)로 잘게 쪼갬 |
| 보호 기능 약화 | 순수 페이징 사용 시, 하나의 페이지 내에 읽기 전용 코드와 쓰기 가능한 변수가 섞임 | 세그먼트 테이블에 권한 명시 후 페이징 | 의미 기반의 완벽한 보호 + 외부 단편화 제로 |
| 다단계 변환 지연 | 세그먼트 테이블 + 페이지 테이블 거치면 메모리 접근 지연 3배 폭증 | **TLB (Translation Lookaside Buffer)** 적용 | 2단계 변환 결과를 캐싱하여 1사이클로 단축 |

> 요약: 현대 x86 아키텍처는 세그멘테이션으로 보안(Ring 0/3)과 공유를 달성하고, 하위에서 페이징으로 물리 프레임을 할당하는 하이브리드 방식을 표준화했다.

## Ⅵ. 실무 적용 및 결론

**적용 방안 3개:**
1. 대형 페이지(Huge Pages) 최적화: RDBMS 등 초대용량 메모리를 사용하는 환경에서 4KB 페이징 사용 시 1억 개 이상의 페이지 테이블이 생성되어 램 낭비와 TLB Miss가 폭발하므로, 2MB 또는 1GB 단위의 Huge Pages를 적용해 테이블 크기 축소 및 히트율 극대화
2. mmap() 기반 제로 카피(Zero Copy): 애플리케이션 개발 시 파일 I/O를 위해 커널 버퍼를 거치는 대신, 메모리 맵 파일(mmap) 시스템 콜을 통해 디스크 파일을 가상 메모리 주소에 직접 매핑(Demand Paging 연동)시켜 복사 오버헤드를 원천 제거
3. 메모리 오버커밋(Overcommit) 통제: 리눅스 커널 운영 시, OS가 실제 물리 RAM보다 더 많은 가상 메모리를 프로세스들에게 남발(Overcommit)하다가 메모리 부족 시 OOM Killer가 강제 종료하는 참사를 막기 위해, `vm.overcommit_memory` 파라미터 튜닝 적용

**결론 (2줄):**
- 기술사 판단: 가상 메모리는 부족한 물리 RAM을 디스크로 보완하는 단순한 캐싱 기술을 넘어, 현대 다중 프로그래밍 운영체제의 프로세스 보호와 메모리 격리를 지탱하는 핵심 보안/추상화 인프라다.
- 향후 방향: 최근 클라우드 서버의 RAM이 수 TB 단위로 거대해짐에 따라 다단계 페이지 테이블(Page Walk) 조회의 오버헤드가 한계에 직면하여, 단일 단계의 직접 세그먼트 매핑이나 메모리 풀링(CXL) 아키텍처로의 회귀가 연구되고 있다.
