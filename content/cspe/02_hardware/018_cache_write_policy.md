# 018. 캐시 쓰기 정책 — Write-Through vs Write-Back (Cache Write Policy) [출제:129회]

## 미리 알고가기

- **쓰기 적중 (Write Hit)**: CPU가 데이터를 쓰려는 주소의 데이터가 이미 캐시에 존재하는 경우임
- **쓰기 미스 (Write Miss)**: 데이터를 쓰려는 주소가 캐시에 없어 메모리에서 가져오거나 다른 처리가 필요한 경우임
- **더티 비트 (Dirty Bit)**: 캐시의 데이터가 수정되었으나 아직 주기억장치에 반영되지 않았음을 나타내는 상태 비트임

## Ⅰ. 개요

- **정의/개념**: 캐시 쓰기 정책은 CPU가 연산 결과를 캐시에 저장할 때, 그 변경된 내용을 어느 시점에 주기억장치(RAM)에 반영할지 결정하는 규칙임
- **배경/필요성**: 캐시에만 데이터를 쓰면 속도는 빠르지만 메모리와의 데이터 불일치가 발생하고, 매번 메모리까지 쓰면 일관성은 완벽하지만 속도가 매우 느려짐. 따라서 시스템의 목적에 맞는 최적의 쓰기 전략이 필요함

## Ⅱ. 특징 및 비교

가장 큰 차이는 '메모리 업데이트 시점'과 '더티 비트 활용 여부'임.

| 비교 항목 | Write-Through (즉시 쓰기) | Write-Back (나중 쓰기) |
|:---|:---|:---|
| **업데이트 시점** | 캐시와 메모리에 **동시에 기록** | 캐시에만 쓰고, **교체 시 메모리에 기록** |
| **속도 (성능)** | 느림 (메모리 쓰기 속도에 제한됨) | **빠름** (캐시 속도로 연산 가능) |
| **메모리 트래픽** | 높음 (매 쓰기마다 메모리 접근) | **낮음** (필요할 때만 메모리 접근) |
| **더티 비트** | 필요 없음 | **필수** (수정 여부 표시용) |
| **일관성/복구** | 단순하고 안전함 | 복잡함 (전원 차단 시 데이터 손실 위험) |

> 요약: Write-Through는 '안전하지만 느림', Write-Back은 '위험할 수 있지만 매우 빠름'임.

## Ⅲ. 구성요소/구조

쓰기 정책은 캐시 제어기 내부의 상태 전이와 버퍼링 구조를 포함함.

- **구성요소**:
  - **Write Buffer**: Write-Through의 속도 저하를 막기 위해 메모리 쓰기를 비동기로 처리하는 임시 저장소
  - **Dirty Bit Logic**: Write-Back에서 해당 라인이 수정되었는지 체크하는 1비트 저장 공간
  - **Eviction Logic**: Write-Back에서 새 데이터를 위해 기존 데이터를 쫓아낼 때, Dirty bit가 $1$이면 메모리에 먼저 기록하는 로직

- **동작 흐름도 (ASCII)**:

```text
[ CPU Store Request ]
         |
    +----v----+       Hit?      +-----------+
    |  Cache  |---------------->|   Data    |
    +---------+       No        +-----------+
         |
 [ If Write-Back ]             [ If Write-Through ]
  Update Cache Line             Update Cache Line
  Set Dirty Bit = 1             AND Update Memory Immediately
         |                             |
 [ When Evicted ]              [ Process Finished ]
  If Dirty == 1:
    Write to Memory
```

1. **Write-Through**: 쓰기 명령이 떨어지자마자 버스를 타고 메모리까지 달려감
2. **Write-Back**: 캐시 안에서만 값을 바꾸고 "나중에 메모리에 쓸 것"이라고 포스트잇(Dirty Bit)을 붙여둠

## Ⅳ. 문제점 및 개선방안

1. **Write-Through의 버스 점유**: 잦은 쓰기 작업 시 메모리 버스가 계속 점유되어 전체 시스템 성능이 저하됨
   - **개선방안**: **Write Buffer**를 도입하여 CPU는 버퍼에만 쓰고 다음 작업을 수행하며, 버퍼가 배경(Background)에서 메모리에 기록하도록 함 (확인: 쓰기 버퍼 가득 참 빈도)

2. **Write-Back의 데이터 손실 및 일관성**: 전원이 갑자기 꺼지거나 다른 장치(DMA)가 메모리를 직접 읽을 때 캐시의 최신 데이터를 보지 못할 수 있음
   - **개선방안**: **MESI 프로토콜**을 통해 코어 간 일관성을 유지하고, 전원 상실 시 캐시 데이터를 백업하는 비휘발성 기술을 적용함 (확인: 일관성 유지 트래픽 부하)

3. **쓰기 미스(Write Miss) 시 처리**: 쓰려는데 캐시에 데이터가 없을 때의 정책이 성능에 큰 영향을 줌
   - **개선방안**: 메모리에서 캐시로 불러온 뒤 쓰는 **Write-Allocate**(주로 Write-Back과 조합)나 캐시를 거치지 않고 메모리에 바로 쓰는 **No-Write-Allocate**(주로 Write-Through와 조합)를 선택함 (확인: 쓰기 미스 발생 시 지연 시간)

## Ⅴ. 실무 적용 사례

| 적용 영역 | 적용 방식 | 확인 지표 |
|:---|:---|:---|
| 현대 고성능 CPU (L1/L2) | 성능이 최우선이므로 **Write-Back**을 기본으로 사용하며 복잡한 일관성 프로토콜로 보완 | $IPC$, 메모리 대역폭 절감률 |
| 특수 목적 제어기 / 임베디드 | 데이터의 신뢰성과 단순한 일관성 관리가 중요한 경우 **Write-Through** 채택 | 데이터 무결성, 프로그램 복잡도 |
| 그래픽 카드 (GPU) | 엄청난 양의 데이터를 쏟아붓는 쓰기 작업의 특성상 메모리 대역폭 확보를 위해 Write-Back 및 결합 쓰기 적용 | 픽셀 처리량 ($Fill\ Rate$), 전력 소모 |

> 요약: 연산량이 많으면 Write-Back, 데이터 안전이 최우선이면 Write-Through를 권장함.

## Ⅵ. 결론

캐시 쓰기 정책은 시스템의 성능과 데이터 무결성 사이의 가장 결정적인 설계 선택지임. 기술사는 단순히 두 방식의 장단점을 외우는 데 그치지 않고, 왜 현대의 고성능 시스템이 Write-Back의 복잡성을 감수하면서까지 이를 채택하는지, 그리고 그 부작용인 일관성 문제를 어떻게 해결하고 있는지를 종합적으로 설명할 수 있어야 함.

향후에는 비휘발성 메모리(PRAM 등)가 캐시 계층에 도입되면서, 전원 차단 시에도 Write-Back의 데이터를 보호할 수 있는 새로운 형태의 쓰기 정책과 지속성(Persistence) 보장 기술이 더욱 중요해질 전망임. 결국 최적의 정책은 응용 프로그램의 '읽기/쓰기 비율'과 '데이터의 중요도'에 따라 유연하게 결정되어야 함.
