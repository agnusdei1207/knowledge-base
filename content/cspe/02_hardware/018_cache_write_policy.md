# 📖 【암기용】 개념 완전 이해

## 한눈에
- **개요**: 캐시 쓰기 정책은 CPU가 데이터를 변경(Store)할 때 그 값을 캐시에만 적고 나중에 반영할지(Write-Back), 메인 메모리에 즉시 함께 적을지(Write-Through) 결정하는 제어 규칙임(017 매핑 이후 갱신 시점 문제).
- **왜 필요한가**: 캐시 값을 바꾸면 메모리 원본이 옛 값(Stale)이 되어 불일치가 생기므로, 언제 어떻게 동기화할지 정해 성능 저하와 데이터 오염을 함께 막아야 함.
- **핵심 직관**: 화이트보드(캐시)에 기획안을 고칠 때 — 고칠 때마다 원본 서류(메모리)도 즉시 함께 고치면 Write-Through(느리나 원본 항상 최신), 보드에서 자유롭게 고치다 지울 때 한 번만 서류에 옮기면 Write-Back(빠르나 중간 정전 시 원본은 옛 값)임.

## 핵심 용어 정리 (내부에 등장하는 것들)

먼저 답안에 나오는 용어를 비유와 함께 풀어 둔다. 최상위 키워드는 캐시 쓰기 정책이다.

| 용어/표기 | 의미 | 비유·예 |
|:---|:---|:---|
| Write-Through (연속 쓰기) | 캐시에 쓸 때 메인 메모리에도 동시 기록 | "실시간 동기화 저장" |
| Write-Back (후기록) | 캐시에만 쓰고 축출될 때 메모리에 반영 | "닫을 때 한 번에 저장" |
| Dirty Bit (변경 비트) | 캐시 라인이 메모리와 달라졌음을 표시하는 1비트 | "원본과 달라졌다는 경고 딱지" |
| Write Miss (쓰기 미스) | 수정할 데이터가 캐시에 없는 상황 | "보드에 원본이 안 올라와 있음" |
| Write-Allocate (쓰기 할당) | 쓰기 미스 시 메모리 블록을 캐시로 가져온 뒤 수정 | "원본을 보드로 가져와 수정" |
| No Write-Allocate | 쓰기 미스 시 캐시를 건너뛰고 메모리에 직접 기록 | "보드 안 쓰고 서류에 바로" |
| Store Buffer (쓰기 버퍼) | 메모리 쓰기를 비동기로 미루는 대기열 | "즉시 저장 대신 예약 큐" |

## 깊이 이해
- **배경·문제의식**: 프로그램은 읽기뿐 아니라 변수 수정(Store)도 많음. 수정마다 느린 메모리까지 다녀오면 캐시 도입 효과가 사라지므로, 동기화 시점을 늦추되 일관성은 지키는 균형이 필요함.
- **작동 원리(정책 결합)**: ① 쓰기 시점 — Write-Through는 동기화는 완벽하나 매 쓰기가 메모리 대역폭을 소모하므로 Store Buffer로 지연 은닉함. Write-Back은 Dirty Bit=1만 세팅하고 자유롭게 쓰다 축출(Eviction) 시에만 반영해 버스 트래픽을 크게 줄임. ② 쓰기 미스 시 — Write-Allocate는 원본을 캐시로 올려 적재 후 수정(Write-Back과 결합), No Write-Allocate는 캐시를 건너뛰고 메모리에 직접 기록(Write-Through와 결합)함.
- **비유**: 편의점(캐시) 장부와 본사(메모리) 장부 — Write-Through는 바코드 찍을 때마다 본사로 전송, Write-Back은 편의점 장부에만 쓰다 마감 때 한 번에 전송함.
- **구체 예시**: 루프에서 같은 변수 `i`를 100번 수정하면 Write-Through는 메모리에 100번 쓰지만, Write-Back은 마지막 축출 시 1번만 써 대역폭을 수십 배 절감함.
- **흔한 오해·주의점**: Write-Back이 항상 우월한 건 아님. 멀티코어에서 코어 A가 Write-Back으로 값을 자기 캐시에만 들면, 코어 B가 메모리에서 옛 값을 읽는 일관성 위반이 생겨 MESI 스누핑(019) 프로토콜이 추가로 필요해짐.

## 연결 개념
- **017 캐시 매핑**: 세트 축출이 곧 Write-Back의 반영 시점이므로 매핑·교체와 직결됨.
- **019 캐시 일관성(MESI)**: Write-Back의 멀티코어 부작용을 막는 필수 후속 프로토콜임.
- **044 DMA**: I/O 장치가 메모리를 직접 접근하므로 Dirty 데이터 플러시 동기화가 필요함.

# 📝 【답안용】 시험 답안 템플릿

## 핵심 인사이트 (3줄 요약)

> 1. **본질**: 캐시 쓰기 정책은 Store 연산 시 캐시 변경분을 메인 메모리에 동기화하는 시점·방식을 결정하는 제어 로직임.
> 2. **가치**: 데이터 일관성 유지 비용과 메모리 버스 트래픽 포화 사이의 트레이드오프를 조율함.
> 3. **판단**: 현대 범용 CPU는 트래픽 절감을 위해 Write-Back+Write-Allocate를 표준으로 쓰고, 일관성은 MESI로 보완함.

## 출제 의도 및 답안 포인트

| 출제 의도 | 반드시 짚을 핵심 | 감점 회피 포인트 |
|:---|:---|:---|
| 쓰기 정책 트레이드오프 이해 | Write-Through(트래픽↑·일관성)·Write-Back(Dirty Bit·트래픽↓) | Write-Back의 Dirty Bit·축출 시점 반영 누락 |
| 쓰기 미스 연계 정책 파악 | Write-Allocate vs No Write-Allocate 결합 규칙 | 쓰기 정책과 할당 정책의 결합 관계 누락 |

> 요약: 동기화 시점(Through/Back)과 쓰기 미스 시 행동(Allocate 여부)을 한 세트로 서술해야 완결됨.

---

## Ⅰ. 개요 및 필요성

- 개요: 캐시 쓰기 정책은 CPU 변경 시 캐시 값과 메모리 원본 간 불일치(Stale)를 해소하는 갱신 시점 규칙임.
- 배경: 매 쓰기마다 느린 메모리에 접근하면 파이프라인 스톨과 대역폭 고갈이 발생함.
- 필요성: 버스 트래픽을 줄이면서 타 코어·DMA의 메모리 참조 오류를 막는 최적 동기화 시점 결정이 필요함.

---

## Ⅱ. 구조 및 구성요소

```text
CPU Store 발생 -> 캐시 히트 여부 분기
  히트 / Write-Through: 캐시 갱신 + 메모리 동시 갱신(Store Buffer로 지연 은닉)
  히트 / Write-Back: 캐시 갱신 + Dirty Bit=1 -> 축출 시점에만 메모리 반영
```

| 쓰기 정책 | 메모리 갱신 시점 | 상태 플래그 |
|:---|:---|:---|
| Write-Through | 캐시에 쓸 때 메모리에 동시 기록 | 별도 비트 불필요 |
| Write-Back | 라인 축출(Eviction) 시 한 번에 기록 | Dirty Bit 1비트 |

> 요약: 트래픽·성능은 Write-Back이 유리하나, 구현 단순성·장애 시 안전성은 Write-Through가 유리함.

---

## Ⅲ. 동작원리 및 흐름도 (쓰기 미스 정책 결합)

```text
CPU Store -> 캐시 미스(Write Miss) 발생
  Write-Allocate: 메모리 블록을 캐시로 적재 -> 수정 -> Dirty Bit=1 (Write-Back과 결합)
  No Write-Allocate: 캐시 건너뛰고 메모리에 직접 기록 (Write-Through와 결합)
```

- 1단계 [Write-Allocate]: 수정 대상이 캐시에 없으면 메모리에서 블록을 통째로 캐시에 올림.
- 2단계 [Write-Back 결합]: 올린 블록을 수정하고 Dirty Bit=1로 세팅함(통상 Write-Back과 짝을 이룸).
- 3단계 [No Write-Allocate]: 캐시에 없으면 블록을 올리지 않고 메모리 주소에 직접 기록함.
- 4단계 [Write-Through 결합]: 어차피 메모리에 쓰므로 낭비를 막기 위해 통상 No Write-Allocate와 짝을 이룸.

> 요약: Write-Back은 캐시로 올려 재사용하는 전략, Write-Through는 메모리에 바로 쓰는 단순 전략임.

---

## Ⅳ. 특징
- 버스 트래픽 절감(Write-Back): 루프 내 동일 변수 100회 수정도 축출 시 메모리 1회 접근으로 대역폭을 수십 배 절감함.
- 데이터 오염 리스크: Write-Back 환경에서 정전 시 메모리 미반영 Dirty 블록이 영구 유실됨.
- 성능 완충 로직: Write-Through의 속도 저하를 덮기 위해 CPU-메모리 사이 Store Buffer 큐로 쓰기를 비동기화함.

> 요약: Write-Back의 트래픽 절감 효과가 커 현대 CPU는 이를 기본으로 쓰되 멀티코어 부작용을 별도 회로로 방어함.

---

## Ⅴ. 심화 비교 및 적용 판단

| 구분 | Write-Through (No-Allocate 결합) | Write-Back (Allocate 결합) | 선택 기준 |
|:---|:---|:---|:---|
| 메모리 대역폭 | 높음(병목 유발) | 낮음(축출 시점만 트래픽) | 시스템 버스 한계 |
| 데이터 일관성 | 메모리 항상 최신 | 캐시 최신·메모리 과거(Stale) | 신뢰성 요구 수준 |
| 하드웨어 구현 | 단순 | 복잡(Dirty Bit·일관성 프로토콜) | 회로 면적 예산 |
| 대표 적용 | 임베디드·DSP·I-Cache | x86·ARM 멀티코어 D-Cache | 코어 수·무결성 |

> 요약: 코어가 단순하고 무결성이 중요한 임베디드·DSP는 Write-Through, 고성능 멀티코어는 Write-Back을 채택함.

**리스크·대응 (기본은 불릿):**
- 멀티코어 불일치 리스크 — 원인: 코어 A Write-Back 값을 코어 B가 옛 값으로 읽음 — 대응: MESI 스누핑 일관성 프로토콜 탑재(지표: 코히런스 오류율 0%).
- DMA 동기화 실패 — 원인: NIC가 캐시에 갇힌 Dirty 데이터를 못 읽음 — 대응: DMA 접근 전 OS 명시적 캐시 플러시 실행(지표: 메모리 배리어 오버헤드).

---

## Ⅵ. 실무 적용 및 결론

**적용 방안 3개:**
1. 데이터 특성별 혼합 정책: 수정 잦은 D-Cache는 Write-Back, 수정 없는 읽기 전용 I-Cache는 단순 구조를 적용함.
2. 프레임 버퍼·스트리밍: 한 번 쓰고 버려지는 GPU 프레임 버퍼는 Write-Through·바이패스로 캐시 오염을 방지함.
3. 영속성 메모리(PMEM) 연계: NVDIMM 환경은 전원 차단 시 Dirty 데이터 유실을 막기 위해 ADR 배터리로 강제 Flush 후 차단함.

**결론 (2줄):**
- 기술사 판단: 성능·대역폭이 핵심인 멀티코어는 Write-Back+Allocate를, 무결성·단순성이 핵심인 임베디드는 Write-Through+No-Allocate를 선택해야 함.
- 향후 방향: 코어가 수십 개로 늘며 Write-Back 트래픽조차 병목이 되어, 디렉터리 기반 일관성으로 불필요한 스누핑 브로드캐스트를 억제하는 방향으로 진화 중임.
