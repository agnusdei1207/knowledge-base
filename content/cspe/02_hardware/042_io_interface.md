## Ⅰ. 개요
- **정의**: CPU와 I/O 장치 간 데이터 전송을 제어하는 방식을 분류한 체계임
- **배경/필요성**: CPU와 I/O 장치의 속도 차이가 수천 배이므로, 전송 중 CPU 유휴를 줄이는 기법이 필요함
- **비유**: 택배를 기다리는 방법 — 현관에서 계속 서 있기(폴링), 초인종 설치(인터럽트), 경비실에 위임(DMA), 전담 택배 관리인 고용(채널 I/O)

| 출제 의도 | 반드시 짚을 핵심 | 감점 회피 포인트 |
|:---|:---|:---|
| 4가지 I/O 방식의 CPU 부담 비교 | 폴링 → 인터럽트 → DMA → 채널 순으로 CPU 개입이 감소함 | DMA는 전송 시작·종료만 CPU가 관여함을 명시할 것 |

> 요약: I/O 방식은 CPU 개입 정도에 따라 폴링·인터럽트·DMA·채널 I/O로 발전함

## Ⅱ. 구성요소
```text
CPU <---> I/O Controller <---> Device
 |            |
 +-- Bus -----+
 |
 +-- Memory
```

| 구성요소 | 설명 | 비유 |
|:---|:---|:---|
| 폴링(Polling) | CPU가 주기적으로 상태 레지스터를 확인하여 I/O 완료를 감지함 | 현관에서 택배 올 때까지 대기 |
| 인터럽트(Interrupt) | I/O 완료 시 장치가 인터럽트 신호를 발생시켜 CPU에 통보함(043 참조) | 초인종이 울리면 나가는 방식 |
| DMA | DMA 컨트롤러가 CPU 없이 장치↔메모리 간 블록 전송을 수행함(044 참조) | 경비실이 택배를 대신 수령 |
| 채널 I/O | 전용 I/O 프로세서가 채널 프로그램을 실행하여 복수 장치를 독립 관리함 | 전담 관리인이 모든 택배를 처리 |

> 요약: CPU 부담이 높은 폴링에서 전담 프로세서인 채널 I/O까지 발전한 구조임

## Ⅲ. 절차
```text
I/O 요청 -> 전송 방식 선택 -> 데이터 전송 -> 완료 통보
   (1)           (2)             (3)           (4)
```
- 1단계: **I/O 요청** — 프로세스가 시스템 콜을 통해 I/O 동작을 요청함
- 2단계: **방식 선택** — OS 드라이버가 장치 특성에 맞는 전송 방식을 설정함
- 3단계: **데이터 전송** — 선택된 방식(폴링/인터럽트/DMA/채널)으로 데이터가 이동함
- 4단계: **완료 통보** — 전송 완료 후 CPU에 상태를 반환하고 프로세스를 재개함

> 요약: 요청 → 방식 설정 → 전송 → 완료 순으로 I/O 동작이 수행됨

## Ⅳ. 문제점
- **폴링의 CPU 낭비**: 상태 확인 루프가 CPU 사이클을 점유하여 다른 작업 처리량이 감소함
- **인터럽트 오버헤드**: 소량 데이터를 빈번히 전송하면 인터럽트 컨텍스트 스위칭 비용이 누적됨
- **DMA 버스 경합**: DMA 전송 중 CPU와 버스를 공유하므로 메모리 접근 지연이 발생함(045 참조)

> 요약: 각 방식은 CPU 낭비·인터럽트 빈도·버스 경합이라는 고유한 병목을 가짐

## Ⅴ. 개선방안
1. 단기: 인터럽트 코얼레싱(Coalescing)으로 다수 이벤트를 묶어 인터럽트 횟수를 감소시킴
2. 중기: 스캐터-개더 DMA로 비연속 메모리 영역을 한 번에 전송하여 버스 점유 시간을 단축함
3. 장기: RDMA·CXL 등 CPU 바이패스 인터커넥트를 도입하여 버스 경합 자체를 제거함

> 요약: 코얼레싱 → 스캐터-개더 DMA → CPU 바이패스 인터커넥트 순으로 I/O 병목을 해소함

## Ⅵ. 전망
- 발전 방향: NVMe, CXL 등 저지연 인터커넥트가 기존 버스 기반 I/O를 대체하는 추세임
- 기술사적 판단: I/O 방식 선택은 시스템 처리량 설계의 핵심 의사결정 항목임
- 기술사 제언: 워크로드 특성(대역폭 vs 지연시간)에 따라 I/O 방식을 정량적으로 선택할 필요
