# I/O 인터페이스 - 폴링·인터럽트·DMA·채널 I/O (I/O Interface)

## 미리 알고가기

- I/O: 입출력(Input/Output, I/O)은 프로세서와 주변장치가 데이터와 제어 신호를 주고받는 동작임
- 폴링: CPU가 장치 상태 레지스터를 반복 조회해 준비 여부를 확인하는 방식임
- 인터럽트: 장치가 이벤트 발생 시 CPU에 신호를 보내 처리를 요청하는 방식임
- DMA: 직접 메모리 접근(Direct Memory Access, DMA)은 장치와 메모리 사이의 데이터 전송을 CPU 개입 없이 컨트롤러가 수행하는 방식임
- 채널 I/O: 독립 I/O 프로세서가 여러 입출력 명령을 처리해 CPU 부담을 줄이는 방식임

## Ⅰ. 개요

- **정의/개념**: I/O 인터페이스는 CPU, 메모리, 주변장치가 상태 확인, 제어 명령, 데이터 전송, 완료 통지를 주고받는 하드웨어·소프트웨어 경계이며, 폴링·인터럽트·DMA·채널 I/O로 CPU 부담과 응답성을 조절함.
- **배경/필요성**: 주변장치는 CPU보다 느리고 동작 방식이 다양하므로 CPU가 직접 대기하면 연산 자원이 낭비됨. I/O 인터페이스는 장치 차이를 표준화하고 데이터 이동 주체를 분리해 처리량과 응답시간을 맞추기 위해 필요함.

| 출제 의도 | 반드시 짚을 핵심 | 감점 회피 포인트 |
|:---|:---|:---|
| 입출력 제어 방식을 CPU 부담과 데이터 전송 경로 관점에서 비교하는 역량 확인 | polling, interrupt, DMA, channel I/O, device controller | 장점 나열, DMA와 인터럽트 혼동, 데이터 경로 누락 |

> 요약: I/O 인터페이스의 핵심은 장치 상태 확인과 데이터 이동을 CPU가 직접 할지, 이벤트나 전용 컨트롤러에 맡길지 결정하는 것임.

## Ⅱ. 특징 및 비교

| 방식 | 동작 원리 | 장점 | 한계 | 적합 영역 |
|:---|:---|:---|:---|:---|
| 폴링 | CPU가 상태 레지스터를 반복 확인함 | 구조 단순, 예측 쉬움 | 대기 시간 동안 CPU 낭비 | 짧고 빈번한 장치 확인 |
| 인터럽트 | 장치가 이벤트 발생 시 CPU에 알림 | CPU 대기 감소, 비동기 처리 | 인터럽트 폭주 시 오버헤드 | 키보드, 네트워크 이벤트 |
| DMA | 전용 컨트롤러가 메모리와 장치 간 블록 전송 | 대용량 전송에서 CPU 부담 감소 | 캐시 일관성, 보호 문제 | 디스크, NIC, GPU 전송 |
| 채널 I/O | 독립 I/O 프로세서가 명령열 처리 | 대규모 I/O 병렬 제어 | 하드웨어 복잡도와 비용 | 메인프레임, 대형 스토리지 |

단순 제어는 폴링으로 충분하지만, 비동기 이벤트가 많으면 인터럽트가 적합함. 데이터 크기가 커질수록 CPU가 직접 복사하지 않도록 DMA나 채널 I/O가 필요하며, 이때 성능 판단 기준은 CPU 점유율, 전송량, 지연시간, 인터럽트 빈도임.

## Ⅲ. 구성요소/구조

```text
+----------+      +-------------+      +-------------+
| CPU      | <--> | I/O Ctrl    | <--> | Device      |
+----------+      +-------------+      +-------------+
      |                   |
      v                   v
+----------+      +-------------+
| Memory   | <--- | DMA Engine  |
+----------+      +-------------+
```

| 구성요소 | 설명 | 핵심 포인트 |
|:---|:---|:---|
| CPU | I/O 요청 설정, 완료 처리, 예외 처리를 담당함 | 제어 주체 |
| 장치 컨트롤러 | 상태 레지스터, 제어 레지스터, 데이터 버퍼를 제공함 | 장치 추상화 |
| 인터럽트 컨트롤러 | 장치 이벤트의 우선순위와 CPU 전달을 관리함 | 비동기 응답 |
| DMA 엔진 | 메모리와 장치 간 블록 데이터를 직접 이동함 | 전송 오프로딩 |
| 드라이버 | 운영체제와 장치 제어 레지스터 사이의 소프트웨어 인터페이스임 | 정책과 하드웨어 연결 |

### 원리/흐름도

```text
+---------+      +----------+      +----------+      +----------+
| Request | ---> | Control  | ---> | Transfer | ---> | Complete |
+---------+      +----------+      +----------+      +----------+
```

CPU는 장치와 전송 조건을 설정하고, 장치는 폴링 응답·인터럽트·DMA 중 선택된 방식으로 데이터를 이동함. 완료 후 상태 레지스터와 인터럽트로 결과를 알리므로, I/O 설계는 제어 경로와 데이터 경로를 분리해 봐야 함.

## Ⅳ. 문제점 및 개선방안

1. **CPU 낭비와 대기 지연**: 폴링을 과도하게 사용하면 CPU가 장치 준비를 기다리며 연산 자원을 소모함.
   - **개선방안**: 짧은 대기에는 폴링, 긴 대기와 비동기 이벤트에는 인터럽트를 적용함. (확인: CPU busy-wait 비율)
2. **인터럽트 폭주**: 고속 네트워크나 스토리지에서 이벤트마다 인터럽트를 발생시키면 문맥 전환 비용이 커짐.
   - **개선방안**: interrupt coalescing, 배치 처리, NAPI 같은 폴링-인터럽트 혼합 방식을 적용함. (확인: IRQ rate, p99 지연)
3. **DMA 보호와 일관성 문제**: 장치가 메모리에 직접 접근하면 잘못된 주소 접근과 캐시 불일치가 발생할 수 있음.
   - **개선방안**: IOMMU, DMA mapping, cache flush/invalidate 규칙을 적용함. (확인: DMA fault, 데이터 불일치)

## Ⅴ. 실무 적용 사례

| 적용 영역 | 적용 방식 | 확인 지표 |
|:---|:---|:---|
| 네트워크 카드 | 패킷 수신은 인터럽트와 폴링 혼합으로 처리하고 대량 데이터는 DMA로 메모리에 적재함 | IRQ rate, 패킷 드롭률, CPU 사용률 |
| NVMe 스토리지 | 큐 기반 명령 제출과 완료 큐 확인, DMA 전송으로 낮은 지연과 높은 처리량을 확보함 | IOPS, p99 지연, 큐 깊이 |
| 임베디드 센서 | 단순 센서는 폴링, 이벤트성 입력은 인터럽트, 연속 스트림은 DMA를 선택함 | 전력 소모, 샘플 유실률 |

## Ⅵ. 결론

I/O 인터페이스는 주변장치를 단순히 연결하는 포트가 아니라 CPU 개입 정도와 데이터 전송 경로를 결정하는 성능 구조임. 폴링, 인터럽트, DMA, 채널 I/O는 상호 대체가 아니라 장치 속도, 데이터 크기, 응답 요구에 따라 조합되는 방식임. 실무에서는 CPU 점유율, 지연시간, 전송량, 보호 실패 여부를 함께 측정해 적절한 I/O 제어 방식을 선택해야 함.
