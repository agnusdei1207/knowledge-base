# 📖 【암기용】 개념 완전 이해
> 목적: I/O 인터페이스 4가지 방식을 처음 봐도 CPU 개입 정도 차이로 구분할 수 있게 만든다. 시험 답안 양식이 아니라, 이해를 위한 친절한 설명이다.

## 한눈에
- **개요**: CPU와 주변장치 사이의 데이터 전송을 CPU가 어느 정도까지 직접 관여하는지에 따라 나눈 4가지 제어 방식
- **왜 필요한가**: 주변장치 속도는 CPU보다 훨씬 느려서, CPU가 매 순간 장치를 붙잡고 있으면 처리량이 낭비된다. 방식 선택에 따라 CPU 점유율과 시스템 처리량이 크게 달라진다.
- **핵심 직관**: 창구 직원이 손님을 계속 쳐다보는 폴링, 벨을 눌러야 반응하는 인터럽트, 택배 기사가 알아서 물건을 옮기는 DMA, 물류센터 전담 직원이 전체 프로세스를 대신 처리하는 채널 I/O로 CPU 개입도가 점점 줄어든다.

## 깊이 이해
- **배경·문제의식**: 초기 컴퓨터는 CPU가 모든 I/O를 직접 처리하는 Programmed I/O만 사용해 CPU 유휴 시간이 낭비되었다.
- **배경·문제의식**: 장치 간 속도 편차(키보드 수십 Hz vs 디스크 수백 MB/s)가 크기 때문에 상황별로 다른 전송 방식이 필요해졌다.
- **작동 원리 — Polling**: CPU가 상태 레지스터를 반복 확인하는 busy-wait 루프를 돌며 장치 준비 여부를 계속 검사한다.
- **작동 원리 — Polling**: 구현이 간단하지만 장치가 준비될 때까지 CPU가 다른 작업을 못 하고 사이클을 낭비한다.
- **작동 원리 — Interrupt-driven I/O**: 장치가 준비되면 IRQ 라인으로 CPU에 비동기 신호를 보내고, CPU는 다른 작업을 하다가 ISR(Interrupt Service Routine)로 문맥 전환한다.
- **작동 원리 — Interrupt-driven I/O**: ISR 안에서는 여전히 CPU가 word 또는 byte 단위로 device 레지스터와 메모리 간 데이터를 직접 옮긴다.
- **작동 원리 — DMA(Direct Memory Access)**: DMA 컨트롤러(DMAC)가 bus request/grant(또는 HOLD/HLDA) 신호로 버스 마스터 권한을 얻어 CPU 개입 없이 device와 memory 사이 블록 단위 전송을 수행한다.
- **작동 원리 — DMA**: CPU는 전송 시작 전 주소·길이·방향 레지스터만 설정하고, 전송 완료 시점에 인터럽트 1회만 받는다.
- **작동 원리 — 채널 I/O(Channel I/O)**: 메인프레임 계열에서 사용하는 전용 I/O 프로세서(채널)가 CCW(Channel Command Word)로 구성된 I/O 프로그램 전체를 자체 실행한다.
- **작동 원리 — 채널 I/O**: CPU는 SIO(Start I/O) 명령으로 채널 프로그램 실행만 지시하고, 이후 여러 장치의 복잡한 I/O 시퀀스는 채널이 전담한다.
- **CPU 관여도 스펙트럼**: Polling(연속 개입) > Interrupt-driven(word 단위 전송 + 비동기 알림) > DMA(block 단위, setup·completion만) > Channel I/O(I/O 프로그램 단위, 시작 지시만).
- **비유**: 우체국 창구에서 손님을 계속 쳐다보는 방식이 폴링, 벨을 눌러야 반응하는 방식이 인터럽트, 택배 기사가 알아서 물건을 옮기는 방식이 DMA, 물류센터 전담 직원이 전체 입고·분류·출고를 대신 처리하는 방식이 채널 I/O다.
- **구체 예시**: 키보드처럼 입력이 드물고 CPU가 매번 폴링하면 낭비인 장치는 interrupt-driven I/O가 적합하다.
- **구체 예시**: 디스크·네트워크의 대용량 순차 전송은 CPU 개입 없이 DMA가 block 단위로 처리한다.
- **구체 예시**: 메인프레임에서 다수 tape·disk를 동시에 운영할 때는 채널이 각 장치의 I/O 프로그램을 병행 실행한다.
- **흔한 오해·주의점**: "DMA는 CPU를 완전히 배제한다"는 부분적으로만 맞다. CPU는 전송 시작 전 레지스터 설정을 수행하고, cycle-stealing 방식 DMA는 버스 사이클 일부를 CPU와 나눠 쓴다.
- **흔한 오해·주의점**: "인터럽트가 폴링보다 항상 지연이 낮다"는 틀렸다. 매우 짧고 빈번한 이벤트(초고속 네트워크 패킷 도착)는 인터럽트마다 발생하는 문맥 전환 오버헤드가 폴링보다 커질 수 있어, 리눅스 NAPI처럼 폴링·인터럽트를 혼합한 방식이 쓰인다.

## 연결 개념
- DMA(Direct Memory Access) — CPU 개입 없는 block 전송의 상세 메커니즘
- 인터럽트 처리 방식(Vectored·Daisy-chain) — 인터럽트 우선순위·핸들러 결정 방식
- 버스 중재(Bus Arbitration) — DMA·채널이 버스 마스터 권한을 얻는 절차


# 📝 【답안용】 시험 답안 템플릿

> 핵심: I/O 인터페이스 답안은 4가지 방식의 이름 나열이 아니라 CPU 개입 단위(word/block/program)와 오버헤드 차이를 판단 기준으로 제시한다.

## 핵심 인사이트 (3줄 요약)
> 1. **본질**: I/O 인터페이스는 CPU가 데이터 전송에 관여하는 정도에 따라 폴링·인터럽트·DMA·채널 I/O로 구분되는 제어 방식이다.
> 2. **가치**: 전송 방식 선택은 CPU 점유율, 처리량, 응답 지연을 좌우해 시스템 성능을 결정한다.
> 3. **판단 포인트**: 장치 속도, 전송 데이터량, 실시간성 요구에 따라 CPU 개입 단위(word/block/program)가 다른 방식을 선택해야 한다.

## 출제 의도 및 답안 포인트
| 출제 의도 | 반드시 짚을 핵심 | 감점 회피 포인트 |
|:---|:---|:---|
| 4가지 방식 CPU 관여도 구분 역량 확인 | polling busy-wait, interrupt word 단위, DMA block 단위, channel I/O program 단위 | CPU 개입 단위를 구분하지 않고 이름만 나열 |
| 상황별 방식 선택 판단 확인 | 장치 속도·전송량·실시간성 기준 선택 | DMA가 CPU를 완전히 배제한다고 단정 |
| 대규모 I/O 처리 구조 이해 확인 | 채널 I/O의 CCW·SIO 개념 | 채널 I/O를 DMA와 동일한 개념으로 서술 |

> 요약: 이 문제는 방식 이름 암기가 아니라 CPU 개입 단위별 오버헤드 차이와 상황별 선택 근거를 보여야 한다.


## Ⅰ. 개요 및 필요성
- 개요: CPU의 데이터 전송 관여 정도에 따라 구분되는 폴링·인터럽트·DMA·채널 I/O 제어 방식
- 배경: Programmed I/O만 사용하면 CPU가 느린 장치를 기다리며 유휴 사이클을 낭비함
- 필요성: 장치 속도·전송량·실시간성이 다양해 상황별로 CPU 개입 단위가 다른 전송 방식 선택이 필요함


## Ⅱ. 구조 및 구성요소
```text
CPU Request
  -> Polling: Status Register Busy-Wait
  -> Interrupt: IRQ Line -> ISR -> Word Transfer
  -> DMA: Bus Req/Grant -> DMAC -> Block Transfer -> Completion IRQ
  -> Channel I/O: SIO -> CCW Program -> Channel End Interrupt
```

| 구성요소 | 역할 | 특이사항 |
|:---|:---|:---|
| Status Register | 장치 준비 상태 표시 | Polling이 반복 조회 |
| Interrupt Controller(PIC) | IRQ 신호 수신·우선순위 처리 | 벡터·데이지체인 방식과 연계 |
| DMA Controller(DMAC) | 버스 마스터 권한으로 block 전송 수행 | 주소·카운트·방향 레지스터 보유 |
| Channel Processor | CCW 기반 I/O 프로그램 자체 실행 | 메인프레임 SIO로 시작 지시 |

> 요약: I/O 인터페이스는 상태 레지스터, 인터럽트 컨트롤러, DMA 컨트롤러, 채널 프로세서를 조합해 CPU 개입 단위를 달리한다.


## Ⅲ. 동작원리 및 흐름도
```text
장치 준비 -> 방식 선택
  -> Polling: 상태 조회 반복 -> 준비 확인 시 CPU 직접 전송
  -> Interrupt: IRQ 발생 -> ISR 진입 -> word 단위 전송
  -> DMA: 버스 요청/승인 -> block 단위 전송 -> 완료 인터럽트
  -> Channel I/O: SIO -> CCW 순차 실행 -> channel end 인터럽트
```

| 단계 | 처리 내용 | 검증 기준 |
|:---:|:---|:---|
| 1 | 장치 상태·요구 특성 식별 | 실시간성, 전송량 |
| 2 | 방식별 CPU 개입 단위 결정 | word/block/program 단위 |
| 3 | 전송 수행 및 오류 검출 | 처리량, CPU 점유율 |
| 4 | 완료 통지 및 다음 요청 처리 | 인터럽트 지연, 처리 지연 |

> 요약: I/O 전송은 장치 특성에 맞는 방식을 고른 뒤 CPU 개입 단위가 다른 절차로 전송을 완료한다.


## Ⅳ. 특징
| 구분 | Polling | Interrupt-driven | DMA | Channel I/O |
|:---|:---|:---|:---|:---|
| CPU 개입 단위 | 지속적 busy-wait | word/byte 단위 | block 단위(setup+완료) | I/O program 단위(시작 지시만) |
| 오버헤드 | CPU 유휴 사이클 낭비 | 문맥 전환 오버헤드 | 초기 설정+완료 인터럽트만 | SIO 발행만, 이후 CPU 자유 |
| 적합 상황 | 매우 빠르거나 예측 가능한 장치 | 발생 빈도 낮은 장치(키보드) | 대용량 순차 전송(디스크·네트워크) | 다중 장치 대규모 I/O(메인프레임) |
| 감점 회피 포인트 | 실시간성 요구 시 사용 근거 명시 | interrupt storm 위험 언급 | cycle-stealing도 버스 일부 점유함을 명시 | DMA와 동일시하지 않음 |

> 요약: CPU 개입 단위가 word에서 block, program 단위로 줄어들수록 CPU 점유율이 낮아지고 처리량이 커진다.


## Ⅴ. 심화 비교 및 적용 판단
| 비교 축 | Programmed I/O(Polling/Interrupt) | DMA/Channel I/O | 선택 기준 |
|:---|:---|:---|:---|
| 구조 | CPU가 전송 자체를 수행 | 전용 컨트롤러·프로세서가 전송 수행 | 전송량이 크면 DMA/채널 |
| 비용/성능 | 소규모 전송에 오버헤드 적음 | 초기 설정 비용은 있으나 대량 전송에 유리 | 반복·대용량 전송이면 DMA/채널 |
| 운영/위험 | interrupt storm, busy-wait 낭비 | 버스 점유 경쟁, cycle-stealing 지연 | 실시간성과 버스 대역폭 요구 동시 고려 |

> 요약: 소규모·저빈도 전송은 Programmed I/O, 대용량·반복 전송은 DMA/채널 I/O를 선택한다.

| 리스크 | 원인 | 대응 방안 | 확인 지표 |
|:---|:---|:---|:---|
| Interrupt storm | 짧은 이벤트가 매우 빈번히 발생 | 폴링·인터럽트 혼합(NAPI 방식) | 초당 인터럽트 횟수 |
| 버스 경쟁 지연 | 다수 DMA/채널이 동시에 버스 요청 | 우선순위 기반 버스 중재 적용 | 버스 대기 시간 |
| 채널 병목 | 채널 수 대비 장치 수 과다 | 채널 다중화, 부하 분산 | 채널 사용률 |

> 요약: I/O 방식 운영 리스크는 인터럽트 폭주와 버스 경쟁이며 인터럽트 횟수와 버스 대기 시간으로 통제한다.

| 점검 항목 | 목표 기준 | 측정 방법 |
|:---|:---|:---|
| CPU 점유율 | I/O 처리로 인한 점유율 목표치 이내 | 성능 카운터, top/perf |
| 처리량 | 목표 전송률(MB/s) 충족 | I/O 벤치마크 |
| 지연 | 인터럽트·완료 통지 지연 목표치 이내 | 트레이스 로그 분석 |

> 요약: 도입 성공 여부는 CPU 점유율, 처리량, 지연 지표로 판단한다.


## Ⅵ. 실무 적용 및 결론
**적용 방안 3개:**
1. 저빈도·소규모 전송 장치는 interrupt-driven I/O를 적용해 CPU 유휴 시간을 활용함
2. 대용량 순차 전송이 필요한 디스크·네트워크는 DMA를 적용해 CPU 개입을 setup·완료 단계로 축소함
3. 다중 장치 대규모 I/O 환경은 채널 I/O 또는 다중 큐 기반 DMA로 확장해 처리량을 확보함

**결론 (2줄):**
- 기술사 판단: 전송량이 작고 드물면 인터럽트, 전송량이 크고 반복적이면 DMA·채널 I/O를 선택함
- 향후 방향: 고속 NVMe·스마트 NIC 환경에서는 폴링·인터럽트 혼합(NAPI, io_uring)과 DMA 기반 descriptor ring 구조로 CPU 개입을 더 줄여야 함
