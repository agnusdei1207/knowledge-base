# 📖 【암기용】 개념 완전 이해

> 목적: RAID 컨트롤러와 JBOD를 처음 봐도 두 방식이 정반대 철학이라는 점을 헷갈리지 않게 만든다. 시험 답안 양식이 아니라, 이해를 위한 친절한 설명이다.

## 한눈에
- **개요**: **스토리지 중복화(Redundancy)**와 **디스크 추상화(Abstraction)**를 "누가 담당하는가"로 갈리는 정반대 두 구성이다. RAID 컨트롤러는 전용 하드웨어가 패리티·스트라이핑을 계산해 여러 디스크를 하나의 논리 볼륨으로 추상화하고, JBOD(Just a Bunch Of Disks)는 RAID 없이 디스크를 있는 그대로 호스트에 노출한다.
- **왜 필요한가**: 디스크 장애·성능 요구에 대응하려면 중복·병렬화가 필요하지만, 소프트웨어 정의 스토리지처럼 호스트가 직접 디스크를 제어하고 싶은 경우도 있다. RAID 컨트롤러와 JBOD는 이 "누가 디스크를 통제하는가"의 양 극단이다.
- **핵심 직관**: RAID 컨트롤러는 여러 창고를 대신 관리해주는 물류대행업체이고, JBOD는 창고 열쇠 뭉치를 그대로 넘겨 직접 관리하게 하는 방식이다.

## 핵심 용어 정리 (내부에 등장하는 것들)

| 용어 | 의미 | 비유 |
|:---|:---|:---|
| 스토리지 중복화(Redundancy) | 디스크 장애에도 데이터를 잃지 않도록 복제·패리티로 여분을 두는 원칙 — 이 개념의 상위 목표 | 계란을 한 바구니에 담지 않는 것 |
| 스트라이핑(Striping) | 데이터를 여러 디스크에 조각내 나눠 쓰는 기법 — 병렬 I/O로 속도 향상 | 화물을 여러 트럭에 나눠 싣는 것 |
| XOR 패리티 | 스트라이프 조각들을 XOR 연산해 만든 여분 데이터로, 디스크 1개가 죽어도 나머지로 원본 복원 | 세 숫자 중 두 개만 알아도 합계로 나머지 계산 |
| RAID 컨트롤러 | 패리티 계산·캐시 관리를 전담하는 전용 하드웨어(ASIC) | 물류를 대신 관리해주는 대행업체 |
| Write-Back 캐시 | 쓰기 요청을 디스크가 아니라 컨트롤러 캐시에 먼저 완료 처리하는 방식 — 빠르지만 정전 시 유실 위험 | 접수만 하고 실제 배송은 나중에 |
| BBU/슈퍼커패시터 | 정전 시에도 write-back 캐시 내용을 디스크에 마저 기록할 때까지 지켜주는 비상 전원 | 정전 대비 UPS |
| JBOD | RAID 없이 디스크를 물리 디스크 그대로 노출하는 구성 | 창고 열쇠 뭉치를 그대로 넘기는 것 |
| HBA IT 모드 | RAID 기능을 끄고 디스크를 개별 장치로 그대로 전달하는 어댑터 설정 | 중간 관리자 없이 직통 연결 |
| 소프트웨어 정의 스토리지(Ceph·ZFS) | 하드웨어 대신 소프트웨어가 복제·이레이저코딩을 수행하는 상위 계층 | 본사가 창고를 직접 관리 |

## 깊이 이해

### RAID 5 패리티 계산 — 숫자로 이해
- 단순화한 예로, 디스크 3개(A, B, 패리티)에서 A=5, B=3을 저장하고 패리티에 A XOR B(=6)를 저장한다고 하자. A 디스크가 죽어도 B(3)와 패리티(6)를 XOR하면 A의 값(5)을 그대로 복원할 수 있다. 이것이 RAID 5가 디스크 1개 장애까지 버티는 원리이며, 이 XOR 연산을 전용 ASIC이 초당 수십만 회 수행한다.
- 디스크 개수가 N개인 RAID 5는 유효 용량이 (N-1)/N이다. 예를 들어 디스크 4개(각 2TB)면 총 8TB 중 1개(2TB)는 패리티로 쓰여 실사용 가능 용량은 6TB(75%)다.

### Write-Back 캐시가 빠른 이유와 위험 — 수치로 이해
- Write-through는 디스크에 실제로 기록이 완료된 뒤 호스트에 응답하므로 HDD 기준 회전 지연(수 ms)을 그대로 겪는다. Write-back은 컨트롤러의 DRAM 캐시(보통 수백 MB~수 GB)에 쓰는 즉시 "완료"로 응답하므로 응답 시간이 수십~수백 마이크로초 수준으로 줄어든다.
- 문제는 캐시에만 있고 디스크에 아직 안 쓰인 상태에서 정전이 나면 그 데이터가 통째로 사라진다는 점이다. BBU(배터리)나 슈퍼커패시터는 정전 후 캐시 내용을 디스크에 마저 flush할 수 있을 만큼(보통 수십 초~수 분)의 비상 전원을 공급한다. BBU가 방전되면 컨트롤러는 자동으로 write-through로 전환해 성능은 떨어지지만 안전을 우선한다.

### JBOD가 소프트웨어 정의 스토리지에 선호되는 이유
- Ceph 같은 분산 스토리지는 자체적으로 오브젝트를 3중 복제하거나 이레이저코딩(예: 데이터 6조각+패리티 3조각)으로 중복을 관리한다. 그 밑에 하드웨어 RAID까지 걸려 있으면 중복이 이중으로 걸려(RAID 중복 + Ceph 복제) 실사용 용량이 크게 줄고, RAID 컨트롤러의 재구성(rebuild) 로직이 Ceph의 장애 복구 로직과 충돌한다.
- 그래서 JBOD로 디스크를 있는 그대로 노출하고, 중복·장애 복구는 전적으로 상위 소프트웨어(Ceph CRUSH 알고리즘, ZFS RAID-Z)에 맡긴다 — 중복 책임의 계층을 하나로 통일하는 것이다.

### 판별 원리 — 언제 RAID 컨트롤러, 언제 JBOD
- 호스트 CPU 부담을 줄이고 싶고 전통적인 단일 서버·DB라면 RAID 컨트롤러가 유리하다(중복 계산을 하드웨어가 오프로드).
- 분산 소프트웨어가 이미 자체 복제 로직을 갖고 있다면(Ceph, HDFS, ZFS) JBOD로 노출해 중복 계층을 하나로 통일하는 것이 유리하다.

### 비유와 흔한 오해
- **비유**: RAID 컨트롤러는 여러 종업원의 업무를 감독하고 결과만 보고하는 매니저이고, JBOD는 매니저 없이 각 종업원(디스크)이 본사(호스트 소프트웨어)에 직접 보고하는 구조다.
- **오해**: RAID 컨트롤러가 JBOD보다 항상 우월한 것은 아니며, write-back 캐시는 배터리·슈퍼커패시터 보호가 없으면 오히려 정전 시 데이터 유실 위험을 키운다.

## 연결 개념
- RAID 레벨 0·1·5·6·10 — RAID 컨트롤러가 구현하는 대표 알고리즘
- 스토리지 계층(DAS·NAS·SAN) — RAID 컨트롤러·JBOD가 배치되는 상위 스토리지 구조
- 소프트웨어 정의 스토리지(Ceph·ZFS) — JBOD를 선호하는 대표 상위 소프트웨어

# 📝 【답안용】 시험 답안 템플릿

> 목적: 시험장에서 25분에 그대로 쓰는 답안 양식. 작성방식(추상표현 금지·수치·도식·문제유형 전환)을 엄격히 지킨다.
> 핵심: RAID 컨트롤러·JBOD 답안은 추상화 계층 위치, write-back 캐시 리스크, 소프트웨어 정의 스토리지와의 관계를 함께 제시한다.

## 핵심 인사이트 (3줄 요약)

> 1. **본질**: RAID 컨트롤러는 하드웨어가 패리티·스트라이핑을 계산해 디스크를 논리 볼륨으로 추상화하고, JBOD는 RAID 없이 디스크를 있는 그대로 호스트에 노출한다.
> 2. **가치**: RAID 컨트롤러는 호스트 CPU 부담 없이 중복·성능을 확보하고, JBOD는 소프트웨어 정의 스토리지가 자체 알고리즘으로 디스크를 직접 통제할 자유도를 준다.
> 3. **판단 포인트**: 두 개념은 스토리지 추상화 스펙트럼의 반대쪽 끝이며, RAID 컨트롤러=하드웨어 중복 관리, JBOD=중복 없는 원시 노출이라는 방향을 절대 반대로 쓰면 안 된다.

## 출제 의도 및 답안 포인트

| 출제 의도 | 반드시 짚을 핵심 | 감점 회피 포인트 |
|:---|:---|:---|
| 하드웨어 RAID 구조 이해 확인 | XOR 패리티 연산, write-back 캐시, BBU/슈퍼커패시터 | RAID 컨트롤러를 단순 디스크 묶음으로 서술 |
| JBOD 개념 이해 확인 | RAID 미적용, HBA IT 모드, 소프트웨어 정의 스토리지 연계 | JBOD를 RAID의 한 레벨로 서술 |
| 선택 기준 판단 확인 | 소프트웨어 정의 스토리지 vs 전통 하드웨어 RAID 선택 | 두 방식을 우열로만 서술하고 적용 맥락 누락 |

> 요약: 이 문제는 RAID 컨트롤러와 JBOD가 스토리지 추상화의 반대쪽 극단이라는 점과 선택 맥락을 함께 설명하는지를 본다.

## Ⅰ. 개요 및 필요성

- 개요: RAID 컨트롤러는 하드웨어가 패리티·스트라이핑을 계산해 디스크를 논리 볼륨으로 추상화하는 장치, JBOD는 RAID 없이 디스크를 있는 그대로 노출하는 구성
- 배경: 디스크 고장 대비와 성능 확보를 위해 RAID가 발전했으나, 소프트웨어 정의 스토리지는 자체 복제·이레이저코딩을 선호하며 JBOD를 요구
- 필요성: 워크로드가 호스트 CPU 부담 최소화를 원하면 RAID 컨트롤러, 소프트웨어가 직접 디스크를 통제하길 원하면 JBOD 선택이 필요

---

## Ⅱ. 구조 및 구성요소

```text
RAID 컨트롤러 구성
  Host -> RAID Controller(ASIC, XOR 엔진, Write-Back Cache+BBU)
    -> 논리 볼륨(LUN) -> OS는 논리 볼륨만 인식

JBOD 구성
  Host -> HBA(IT mode, RAID 기능 없음)
    -> 각 물리 디스크 개별 노출 -> 소프트웨어(mdadm/ZFS/Ceph)가 중복 처리
```

| 구성요소 | RAID 컨트롤러 | JBOD |
|:---|:---|:---|
| 중복 처리 주체 | 컨트롤러 하드웨어(XOR 엔진) | 상위 소프트웨어(mdadm, ZFS, Ceph) |
| OS 노출 단위 | 논리 볼륨(LUN) | 개별 물리 디스크 |
| 캐시 계층 | Write-Back Cache + BBU/슈퍼커패시터 | 캐시 계층 없음(소프트웨어 저널링에 위임) |
| 대표 어댑터 | RAID HBA(캐시 탑재) | HBA IT 모드(RAID 기능 비활성화) |

> 요약: RAID 컨트롤러는 중복 처리를 하드웨어가, JBOD는 상위 소프트웨어가 전담하는 정반대 구조다.

---

## Ⅲ. 동작원리 및 흐름도

```text
RAID 컨트롤러 쓰기 경로
  Host Write -> Write-Back Cache(BBU 보호) -> XOR 패리티 계산 -> 디스크 스트라이프 기록

JBOD 쓰기 경로
  Host Write -> HBA(패스스루) -> 개별 디스크 직접 기록 -> 소프트웨어가 복제/이레이저코딩 수행
```

| 단계 | RAID 컨트롤러 처리 | JBOD 처리 |
|:---:|:---|:---|
| 1 | 쓰기 요청이 컨트롤러 캐시로 진입 | 쓰기 요청이 HBA를 그대로 통과 |
| 2 | XOR 엔진이 패리티 계산 | 소프트웨어가 복제본·이레이저코딩 결정 |
| 3 | 스트라이프 단위로 디스크 기록 | 개별 디스크에 직접 기록 |
| 4 | 장애 시 컨트롤러가 자동 재구성 | 장애 시 소프트웨어가 재복제 트리거 |

> 요약: RAID 컨트롤러는 쓰기 경로 안에서 패리티·캐시를 자동 처리하고, JBOD는 이 책임을 모두 상위 소프트웨어로 넘긴다.

## Ⅳ. 특징

| 구분 | RAID 컨트롤러 | JBOD |
|:---|:---|:---|
| 추상화 수준 | 논리 볼륨으로 완전 추상화 | 물리 디스크 그대로 노출 |
| 호스트 CPU 부담 | 낮음(하드웨어 오프로드) | 상대적으로 높음(소프트웨어 처리) |
| 유연성 | 컨트롤러 지원 RAID 레벨에 한정 | 소프트웨어가 원하는 어떤 중복 정책도 적용 가능 |
| 대표 사용처 | 전통 엔터프라이즈 서버, DB 스토리지 | Ceph, ZFS, Hadoop 등 분산 스토리지 |

> 요약: RAID 컨트롤러는 CPU 부담을 줄이는 대신 유연성이 낮고, JBOD는 유연성이 높은 대신 소프트웨어 부담이 커진다.

## Ⅴ. 심화 비교 및 적용 판단

| 구분 | RAID 컨트롤러 | JBOD | 선택 기준 |
|:---|:---|:---|:---|
| 구조 | 하드웨어 중복 관리, 논리 볼륨 노출 | 중복 없음, 물리 디스크 원시 노출 | 소프트웨어 정의 스토리지 도입 시 JBOD |
| 비용/성능 | 컨트롤러·캐시 비용 발생, CPU 부담 낮음 | 컨트롤러 비용 절감, 호스트 CPU 부담 증가 | 분산 스토리지 CPU 여유와 비용으로 판단 |
| 운영/위험 | write-back 캐시 정전 리스크(BBU 필요) | 중복 정책 오류 시 데이터 손실 위험 소프트웨어에 전가 | 정전 대비책·소프트웨어 복제 정책 검증 |

> 요약: 전통 단일 서버·DB는 RAID 컨트롤러, 분산 소프트웨어 정의 스토리지는 JBOD를 선택하는 것이 일반적 기준이다.

| 리스크 | 원인 | 대응 방안 | 확인 지표 |
|:---|:---|:---|:---|
| Write-Back 캐시 데이터 유실 | BBU·슈퍼커패시터 미장착 또는 방전 상태에서 정전 | BBU 상태 모니터링, 캐시 정책을 write-through로 전환 | BBU 상태, 캐시 정책 설정값 |
| RAID 재구성 중 이중 장애 | 대용량 디스크 리빌드 시간 중 추가 디스크 장애 | RAID 6·핫스페어, 리빌드 시간 단축 설정 | 리빌드 소요 시간, URE(Unrecoverable Read Error) 발생률 |
| JBOD 소프트웨어 오설정 | 복제본 수·이레이저코딩 정책 오설정 | 정책 검증, 장애 시뮬레이션 테스트 | 복제본 수 준수율, 장애 복구 테스트 결과 |

> 요약: RAID 컨트롤러는 캐시 전원 보호를, JBOD는 소프트웨어 중복 정책 검증을 핵심 리스크 관리 대상으로 삼는다.

| 점검 항목 | 목표 기준 | 측정 방법 |
|:---|:---|:---|
| 데이터 내구성 | RAID 레벨·복제본 수 기준 목표 가용성 충족 | 장애 주입 테스트, 내구성 계산 |
| 쓰기 성능 | 목표 IOPS·처리량 달성 | 스토리지 벤치마크(fio 등) |
| 전원 보호 | BBU·슈퍼커패시터 상태 정상 100% | 컨트롤러 상태 모니터링 |

> 요약: 도입 성공 여부는 데이터 내구성, 쓰기 성능, 전원 보호 상태로 판단한다.

## Ⅵ. 실무 적용 및 결론

**적용 방안 3개:**
1. 전통 데이터베이스·단일 서버 스토리지는 RAID 컨트롤러(RAID 5·6·10)와 BBU 보호 캐시를 적용함
2. 분산 소프트웨어 정의 스토리지(Ceph·ZFS)는 JBOD 구성으로 하드웨어 중복 계층을 제거하고 소프트웨어가 복제·이레이저코딩을 전담하게 함
3. RAID 컨트롤러 운영 시 BBU 상태를 주기적으로 점검하고 방전 시 즉시 write-through로 전환함

**결론 (2줄):**
- 기술사 판단: 호스트 CPU 부담 최소화가 우선이면 RAID 컨트롤러, 소프트웨어 중복 정책 자유도가 우선이면 JBOD를 선택함
- 향후 방향: NVMe 기반 분산 스토리지 확산으로 하드웨어 RAID 대신 JBOD + 소프트웨어 정의 스토리지 채택이 늘어나는 추세
