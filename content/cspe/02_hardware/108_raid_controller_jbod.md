# 📖 【암기용】 개념 완전 이해

## 한눈에
- **개요**: 다수의 물리 디스크를 논리적 단일 볼륨으로 묶어 연산을 대행하는 장치(RAID 컨트롤러)와, 묶지 않고 개별 물리 디스크 그대로 OS에 노출하는 아키텍처(JBOD)
- **왜 필요한가**: 수십 개의 디스크를 묶어 안전성(패리티)과 속도를 높이려면 복잡한 연산이 필요한데, 이걸 서버 CPU가 하면 느려지므로 전용 컨트롤러가 필요함. 반대로 최신 소프트웨어(ZFS 등)가 알아서 다 관리하고 싶을 때는 컨트롤러의 개입을 끄고 원시 디스크(JBOD)만 던져달라고 요구함.
- **핵심 직관**: RAID 컨트롤러가 "내가 다 요리해서 뷔페로 내놓을게"라면, JBOD는 "요리는 내(OS)가 할 테니 날것(생선) 그대로 넘겨라"는 방식.

## 핵심 용어 정리

| 용어/표기 | 의미 | 비유·예 |
|:---|:---|:---|
| 하드웨어 RAID 컨트롤러 | 패리티 연산(XOR)과 캐시 관리를 전담하는 스토리지 전용 확장 카드 | 전문 주방장 |
| BBU (Battery Backed Unit) | 정전 시 컨트롤러 캐시에 남은 데이터를 보호하기 위한 배터리 모듈 | 정전 대비 예비 전력 |
| JBOD (Just a Bunch Of Disks) | 디스크들을 하드웨어적으로 묶지 않고 OS에 개별 드라이브로 1:1 노출 | 재료 그대로 직배송 |

## 깊이 이해
- **배경·문제의식**: RAID 5나 6을 쓰면 디스크에 쓸 때마다 패리티(복구 데이터)를 수학적으로 계산(XOR)해야 함. 옛날 서버 CPU는 이 계산을 하다 퍼졌음. 그래서 비싼 하드웨어 컨트롤러를 사다 끼웠음.
- **작동 원리 (RAID 컨트롤러)**: 자체 CPU(IOP)와 RAM(캐시)을 가짐. OS가 쓰기 명령을 내리면 컨트롤러 캐시에 일단 쏜 뒤 OS에는 "다 썼다"고 뻥침(Write-back). 그리고 뒷단에서 열심히 패리티를 계산해 디스크들에 분산 저장. 정전 시 날아가는 걸 막기 위해 배터리(BBU)를 닮.
- **작동 원리 (JBOD)**: 컨트롤러의 논리적 개입(RAID 구성)을 완전히 끄는 모드(Pass-through). OS가 `/dev/sda`, `/dev/sdb` 등 물리 디스크를 생눈으로 보고 직접 제어함.
- **구체 예시**: 12Bay 서버에 디스크 12개를 꽂았을 때, 하드웨어 RAID로 묶으면 OS는 거대한 `C드라이브` 1개만 봄. JBOD로 설정하면 OS는 `C, D, E...` 12개의 드라이브를 봄.
- **흔한 오해·주의점**: 요즘 클라우드나 분산 스토리지(Ceph, vSAN)는 하드웨어 RAID를 극도로 혐오함. 하드웨어 RAID가 중간에 캐싱하고 숨겨버리면 소프트웨어가 상태를 통제할 수 없기 때문에, 무조건 HBA나 컨트롤러를 JBOD(Passthrough) 모드로 설정하라고 강제함.

## 연결 개념
- RAID 레벨 (0, 1, 5, 6, 10)
- 분산 스토리지 (Software Defined Storage, Ceph)
- ZFS 파일 시스템

# 📝 【답안용】 시험 답안 템플릿

## 핵심 인사이트 (3줄 요약)

> 1. **본질**: 하드웨어 RAID 컨트롤러는 스토리지 패리티 연산과 캐싱을 전담하는 칩셋이며, JBOD는 그 개입을 배제하고 물리 디스크를 OS에 1:1로 노출하는 아키텍처다.
> 2. **가치**: RAID 컨트롤러는 단일 서버의 I/O 성능과 가용성을 보장하며, JBOD는 SDS(소프트웨어 정의 스토리지) 환경에서 OS 수준의 메타데이터 통제권을 보장한다.
> 3. **판단 포인트**: 레거시 단독 서버는 하드웨어 RAID가 유리하나, 현대의 스케일아웃(Scale-out) 클라우드 및 HCI 환경에서는 ZFS, Ceph, vSAN과 결합하는 JBOD가 표준으로 자리 잡았다.

## 출제 의도 및 답안 포인트

| 출제 의도 | 반드시 짚을 핵심 | 감점 회피 포인트 |
|:---|:---|:---|
| 하드웨어 RAID의 이점 및 병목 요인 파악 | XOR 연산 오프로딩, Write-Back 캐시, BBU | JBOD를 단순히 '단일 디스크 연결'로만 낮게 평가 |
| 최신 클라우드 스토리지 아키텍처 이해 | 소프트웨어 정의 스토리지(SDS)와 JBOD의 필수 결합성 | H/W RAID가 항상 S/W RAID보다 우수하다는 맹신 |

> 요약: 하드웨어 종속적인 RAID 컨트롤러의 한계와, 소프트웨어 주도 통제를 위해 물리 계층을 그대로 노출하는 JBOD 아키텍처의 트레이드오프를 묻는 문제다.

---

## Ⅰ. 개요 및 필요성

- 개요: 다수의 디스크를 논리 볼륨으로 추상화하는 하드웨어 장치(RAID 컨트롤러)와, 논리적 결합 없이 물리 디스크 자체를 개별 노출하는 방식(JBOD)임
- 배경: RAID 5/6의 복잡한 패리티 연산 오버헤드 방어를 위해 H/W 컨트롤러가 발전했으나, 클라우드 분산 환경에서는 컨트롤러 종속성이 오히려 장애물로 대두
- 필요성: 워크로드 특성(단일 노드 성능 vs 분산 노드 확장성)에 따라 하드웨어 추상화(RAID)와 소프트웨어 가시성(JBOD) 중 적절한 아키텍처 선택 필수

---

## Ⅱ. 구조 및 구성요소

```text
[ 하드웨어 RAID 아키텍처 ]            [ JBOD (Pass-through) 아키텍처 ]
OS -> /dev/sda (논리적 1개 볼륨)      OS (ZFS/Ceph) -> /dev/sda, /dev/sdb ...
          |                                      |
[ RAID Controller (CPU, Cache, BBU) ]       [ HBA (Host Bus Adapter) ]
          |                                      |
Physical Disks (Disk1, Disk2, Disk3)        Physical Disks (Disk1, Disk2, Disk3)
```

| 구성요소 | 역할 | 특이사항 |
|:---|:---|:---|
| XOR Processor | RAID 5/6의 패리티 계산을 하드웨어 칩이 대행 | 서버 메인 CPU의 오버헤드 0으로 제거 |
| Cache & BBU (NVRAM) | 디스크 쓰기 전 캐시에 적재하여 응답성 향상(Write-Back) | 정전 대비 배터리 모듈(BBU/Flash) 필수 |
| HBA (Host Bus Adapter) | 컨트롤러 개입 없이 디스크 명령 통로만 제공 | JBOD 구성 시 사용, OS에 물리 디스크 직결 |

> 요약: RAID 컨트롤러는 서버와 디스크 사이에서 복잡한 통제 계층을 형성하고, JBOD(HBA)는 이를 투명한 터널로 만들어 OS에 통제권을 넘긴다.

---

## Ⅲ. 동작원리 및 흐름도

```text
[RAID 컨트롤러 Write 흐름]
OS 쓰기 요청 -> 컨트롤러 캐시 적재 -> OS에 완료 통보 -> XOR 패리티 연산 -> 디스크 분산 저장
```

- 1단계 [요청 인가]: OS가 논리 볼륨으로 쓰기 요청을 보내면, RAID 컨트롤러 캐시에 데이터가 우선 적재됨
- 2단계 [즉시 응답]: 캐시 기록 후 물리 디스크 기록 전이라도 OS에 I/O 완료 신호를 보내 지연(Latency) 최소화
- 3단계 [연산 및 동기화]: 컨트롤러 내 IOP가 백그라운드에서 패리티 계산을 수행하고 스토라이핑 정책에 따라 쪼개어 저장

```text
[JBOD 기반 SDS (Software Defined Storage) 흐름]
OS 쓰기 요청 -> S/W 분산 시스템(Ceph) 연산 -> 개별 디스크(JBOD) 직접 I/O 제어 -> 무결성 검증
```

> 요약: 하드웨어 RAID는 속도를 위해 데이터를 컨트롤러에 쥐고(가리고) 처리하며, JBOD는 S/W 스토리지 스택이 끝단(물리 디스크)까지 투명하게 다루도록 허용한다.

---

## Ⅳ. 특징
- RAID 컨트롤러: 벤더 종속적인 메타데이터 구조를 가져, 컨트롤러 칩 고장 시 동일 벤더/모델 장비가 없으면 디스크 복구가 불가능한 단일 장애점(SPOF) 위험
- JBOD: H/W 병목(컨트롤러 캐시 한계)이 없고 디스크 SMART 정보 및 섹터 배드 상태를 OS가 직접 인지하여 예방 정비 극대화
- 구조 전환: 멀티코어 성능 발전으로 패리티 연산 오버헤드가 무의미해지면서, H/W 중심에서 OS(SW) 중심 스토리지 관리로 패러다임 전환

---

## Ⅴ. 심화 비교 및 적용 판단

| 비교 축 | 하드웨어 RAID 컨트롤러 | JBOD 기반 Software RAID / SDS | 선택 기준 |
|:---|:---|:---|:---|
| 연산 주체 | 전용 H/W 칩셋 및 캐시 메모리 | 서버 메인 CPU 및 시스템 RAM | 서버 CPU 리소스 여유도 |
| 볼륨 가시성 | OS는 블랙박스(단일 볼륨)로 인식 | OS가 개별 물리 디스크 100% 인식 | ZFS, Ceph 등 최신 FS 요구사항 |
| 장애 복구 | 동일 벤더 컨트롤러 부품 수급 필수 | 하드웨어 독립적, OS만 같으면 즉시 복구 | 벤더 종속성 회피(Lock-in) |

> 요약: 단일 레거시 서버 DB는 RAID 컨트롤러가 안전하나, 노드가 확장되는 클라우드 스토리지에서는 JBOD가 필수 인프라 요건이다.

- Write Hole 현상 리스크: H/W RAID 5 사용 시 정전 등으로 데이터는 써졌으나 패리티가 갱신되지 않아 볼륨이 통째로 깨지는 현상 → JBOD + ZFS(Copy-on-Write) 적용으로 구조적 원천 해결
- 컨트롤러 병목 리스크: 초고속 NVMe 디스크 여러 개를 구형 RAID 컨트롤러에 묶을 경우 PCIe 대역폭 한계로 병목 발생 → 소프트웨어 RAID 매핑으로 우회

- I/O 지연 시간: Write-Back 캐시 유무에 따른 응답 지연(ms) 비교 — Fio 스토리지 벤치마크
- 장애 복원력: 컨트롤러 고장 시 디스크 데이터 재접근 소요 시간(RTO) 측정

## Ⅵ. 실무 적용 및 결론

**적용 방안 3개:**
1. 레거시 단독 RDBMS 서버: H/W RAID 10으로 구성하고 BBU 배터리 상태 상시 모니터링 체계를 구축하여 컨트롤러 캐시 파괴(Write-Through 모드 전환) 예방
2. 클라우드 HCI(하이퍼컨버지드) 인프라: VMware vSAN 또는 Ceph 도입 시 스토리지 정책에 따라 서버 내부 디스크 어댑터를 반드시 JBOD(Pass-through) 모드로 전환하여 SW에 제어권 인계
3. 차세대 ZFS 파일시스템 연계: ZFS의 강력한 자가 치유(Self-Healing) 및 체크섬(Checksum) 기능을 100% 활용하기 위해 물리 계층을 그대로 노출하는 JBOD 토폴로지 구성

**결론 (2줄):**
- 기술사 판단: 과거 인프라는 H/W RAID의 신뢰성에 의존했으나, 현재는 강력해진 CPU 파워를 바탕으로 분산 S/W(JBOD 기반)가 데이터 정합성을 통제하는 것이 대세이다.
- 향후 방향: PCIe 대역폭을 극대화하는 NVMe 시대에는 H/W RAID 컨트롤러가 사실상 병목으로 전락하여, NVMe-oF와 결합된 소프트웨어 정의 스토리지로 완전 대체될 것이다.
