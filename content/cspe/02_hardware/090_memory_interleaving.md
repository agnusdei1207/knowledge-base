## 미리 알고가기

- 메모리 인터리빙은 연속 주소를 여러 메모리 뱅크에 나눠 배치하는 기법임
- bank conflict는 여러 요청이 같은 뱅크에 몰려 병렬성이 줄어드는 현상임
- stride 접근은 일정한 간격으로 주소를 건너뛰며 읽는 패턴임

## Ⅰ. 개요

- **정의/개념**: 메모리 인터리빙은 주소 공간을 여러 메모리 뱅크에 분산해 연속 또는 규칙적 접근 시 여러 뱅크를 겹쳐 사용하도록 만드는 메모리 대역폭 확장 기법임
- **배경/필요성**: 단일 뱅크 메모리는 한 번에 처리할 수 있는 요청 수가 제한적이므로 CPU, DMA, 벡터 처리기의 대역폭 요구를 맞추려면 뱅크 병렬성을 높여야 함

## Ⅱ. 특징

- 연속 접근과 규칙적 배열 접근에서 대역폭 향상 효과가 큼
- 주소 매핑이 적절하면 메모리 사이클을 겹쳐 처리할 수 있음
- stride와 뱅크 수 조합이 나쁘면 bank conflict가 늘어 효과가 줄어듦
- 캐시 미스 이후 하위 메모리 병목을 완화하는 데 자주 쓰임

## Ⅲ. 종류 및 비교

| 판단 기준 | 단일 뱅크 | 워드 인터리빙 | 블록 인터리빙 |
|:---|:---|:---|:---|
| 주소 분산 방식 | 모든 연속 주소가 같은 뱅크 흐름을 따름 | 인접 워드를 여러 뱅크에 순차 분산함 | 일정 크기 블록 단위로 뱅크를 나눔 |
| 연속 주소 배치 | 같은 뱅크에서 순차 처리 | 인접 주소를 서로 다른 뱅크에 배치 | 같은 블록은 한 뱅크에 배치 |
| conflict 조건 | 모든 요청이 단일 뱅크에서 대기 | stride와 뱅크 수가 겹치면 같은 뱅크에 집중 | 같은 블록 요청이 한 뱅크에 집중 |
| 적용 접근 패턴 | 요청 병렬성이 낮은 소규모 메모리 | 벡터·연속 스트림 접근 | 블록 지역성을 이용하는 캐시·NUMA 구조 |

> 요약: 워드 인터리빙은 인접 주소를 여러 뱅크에 분산하고, 블록 인터리빙은 같은 블록을 한 뱅크에 배치함.

## Ⅳ. 구성요소 및 구조

| 구성요소 | 설명 |
|:---|:---|
| 요청 발생원 | CPU, DMA, 가속기가 메모리 접근 패턴을 만들어 냄 |
| 주소 매퍼 | 주소 비트 규칙으로 요청을 특정 뱅크에 분산시킴 |
| 메모리 뱅크 집합 | 독립 접근 가능한 여러 뱅크가 실제 병렬 처리 기반이 됨 |
| 스케줄러·반환 경로 | 충돌 시 순서를 조정하고 결과를 원래 요청자에게 돌려줌 |

```text
+-------------+     +-------------+     +-------------+     +-------------+
| 주소 요청 생성   | --> | 뱅크 매핑      | --> | 병렬 또는 대기 처리 | --> | 데이터 반환      |
+-------------+     +-------------+     +-------------+     +-------------+
```

> 요약: 인터리빙 구조는 주소 매퍼가 요청을 여러 뱅크에 분산하고 충돌 시 스케줄러가 순서를 조정함.

## Ⅴ. 원리 및 절차 흐름도

1. **주소 요청 생성**: CPU나 DMA가 연속 또는 stride 요청을 발행함
2. **뱅크 매핑**: 주소 규칙에 따라 각 요청을 뱅크에 배정함
3. **병렬 또는 대기 처리**: 다른 뱅크 요청은 병렬 처리하고 같은 뱅크 요청은 대기시킴
4. **데이터 반환**: 처리 결과를 요청 순서에 맞춰 반환함

> 요약: 메모리 인터리빙은 주소를 뱅크에 나누고 충돌 없는 요청을 병렬 처리해 대역폭을 높임.

## Ⅵ. 실무 적용 및 유의점

1. 벡터 연산이나 대용량 스트림 처리는 연속 접근이 많아 인터리빙 효과가 크지만 접근 간격이 뱅크 수와 맞물리면 병렬성이 사라지므로 주소 해싱과 데이터 패딩을 적용하고 뱅크 충돌률, 지속 대역폭, 벡터 대기 시간으로 확인함
2. NUMA 서버나 DMA 경로는 인터리빙 규칙이 캐시 라인·페이지 배치와 어긋나면 지연 편차가 커지므로 메모리 정책과 소켓 배치를 조정하고 지연 편차, 소켓 대역폭, 쓰기 대기 시간으로 확인함

## Ⅶ. 결론

메모리 인터리빙의 성패는 뱅크 수보다 접근 패턴을 얼마나 고르게 분산시키느냐에 달려 있음.
