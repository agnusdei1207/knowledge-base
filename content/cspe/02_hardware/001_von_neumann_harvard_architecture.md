# 📖 【암기용】 개념 완전 이해

> 목적: 폰 노이만과 하버드 구조가 왜, 어떤 역사적 배경에서 갈라졌고, 각각의 버스·메모리가 물리적으로 어떻게 다른지 처음 보는 사람도 완전히 이해하게 만든다. (성능·파이프라인 관점의 정량 비교는 `001_von_neumann_vs_harvard.md`에서 다룬다.)

## 한눈에
- **개요**: **저장 프로그램 방식(Stored-Program Architecture)**에서 명령어와 데이터를 담는 메모리 공간을 하나로 통합하는가(폰 노이만), 물리적으로 분리하는가(하버드)로 나누는 **컴퓨터 구조(Computer Architecture) 분류**다.
- **왜 필요한가**: 최초의 전자식 계산기 ENIAC(1945)은 새 프로그램을 돌리려면 배선판을 며칠에 걸쳐 다시 꽂아야 했다. 프로그램을 명령어 코드로 만들어 메모리에 저장해두고 CPU가 순서대로 읽어 실행하게 한 것이 저장 프로그램 방식이고, 그 메모리를 데이터와 합칠지 나눌지에 따라 두 구조로 갈렸다.
- **핵심 직관**: 폰 노이만은 우편함과 택배함을 한 칸에 합쳐 놓고 문 하나로 번갈아 여닫는 것이고, 하버드는 처음부터 우편함과 택배함을 별도 칸·별도 문으로 만든 것이다.

## 핵심 용어 정리

| 용어 | 의미 | 비유 |
|:---|:---|:---|
| 저장 프로그램 방식(Stored-Program) | 명령어를 데이터처럼 메모리에 저장해두고 CPU가 순서대로 읽어 실행하는 방식 — 두 구조 모두의 공통 전제 | 매번 손으로 순서를 지시하지 않고, 레시피북에 적어두고 순서대로 읽음 |
| 폰 노이만 구조 | 명령어와 데이터가 같은 메모리 공간·같은 버스를 공유하는 구조 | 편도 1차선을 우편차·택배차가 번갈아 씀 |
| 하버드 구조 | 명령어 메모리·버스와 데이터 메모리·버스가 물리적으로 분리된 구조 | 우편 전용차선과 택배 전용차선을 따로 냄 |
| 주소 버스(Address Bus) | CPU가 읽거나 쓸 메모리 위치(번지)를 지정하는 신호선 다발 | 택배 상자에 적는 배송지 주소 |
| 데이터 버스(Data Bus) | 실제 값(명령어 또는 데이터)이 오가는 신호선 다발 | 상자 안에 든 물건 |
| 제어 버스(Control Bus) | 읽기/쓰기 구분, 타이밍 등을 지시하는 신호선 다발 | 수령인지 발송인지 알리는 표식 |
| 폰 노이만 병목(Bottleneck) | 단일 버스를 명령어 인출과 데이터 접근이 번갈아 써야 해 생기는 처리 속도 상한 | 1차선 도로의 정체 |
| 수정 하버드 구조(Modified Harvard) | 주기억장치는 통합하되 CPU 내부 L1 캐시만 명령어/데이터로 분리한 절충형 | 큰 창고는 하나, 작업대 옆 소형 서랍만 용도별로 나눔 |
| I-Cache / D-Cache | 수정 하버드 구조에서 분리된 명령어 전용/데이터 전용 1차(L1) 캐시 | 각각 다른 서랍 |

## 깊이 이해

### 왜 갈라졌나 — ENIAC의 배선판 문제와 두 갈래 해법
- ENIAC(1945)은 프로그램이 배선(플러그보드)으로 구현돼 있어, 새 계산을 시키려면 수백 개의 케이블과 스위치를 며칠씩 다시 꽂아야 했다.
- 존 폰 노이만은 1945년 "EDVAC 설계 초안 보고서"에서 명령어를 이진 코드로 만들어 데이터와 같은 메모리에 저장하고, CPU가 그 메모리를 순차적으로 읽어 실행하자고 제안했다 — 이것이 저장 프로그램 방식이며, 이후 이 방식으로 메모리를 하나로 합친 구조를 "폰 노이만 구조"라 부른다.
- 같은 시기 하버드 대학의 Harvard Mark I(1944, IBM과 공동 개발)은 명령어를 천공 종이테이프로 읽고, 데이터는 별도의 전자기계식 레지스터·카운터에 저장했다 — 명령어 경로와 데이터 경로가 물리적으로 처음부터 분리돼 있었기 때문에, 이후 "명령어·데이터를 분리한 구조"에 "하버드 구조"라는 이름이 붙었다.

### 폰 노이만 구조의 물리적 형태
- CPU와 메모리 사이에 주소 버스·데이터 버스·제어 버스가 하나씩만 있고, 명령어 영역과 데이터 영역이 같은 주소 공간(예: 0x00000000~0xFFFFFFFF) 안에 섞여 있다.
- 명령어 인출(Fetch)과 데이터 읽기/쓰기(Access)가 이 단일 버스를 시분할로 나눠 써야 한다 — 한 클럭에 "명령어를 읽으면서 동시에 데이터를 읽고 쓰는 것"이 하드웨어적으로 불가능하다.
- 대신 메모리 공간이 하나이므로 프로그램·데이터 사이의 경계를 소프트웨어(OS·컴파일러)가 자유롭게 조정할 수 있어, 동적 메모리 할당·자기수정코드(self-modifying code)·JIT(Just-In-Time) 컴파일처럼 실행 중에 코드를 데이터로 생성해 바로 실행하는 것이 가능하다.

### 하버드 구조의 물리적 형태 — 실제 사례로 확인
- 명령어 메모리와 데이터 메모리가 별도의 주소 공간·별도의 버스를 갖는다. 두 주소 공간은 물리적으로 분리돼 있어 둘 다 0번지부터 시작해도 서로 겹치지 않는다.
- **실제 예**: Arduino Uno에 쓰이는 ATmega328 마이크로컨트롤러(AVR 계열)는 프로그램을 담는 32KB Flash 메모리와, 변수를 담는 2KB SRAM 데이터 메모리가 완전히 분리된 주소 공간·버스를 쓴다. 컴파일러가 만드는 기계어 코드는 Flash 0번지부터, 전역변수는 SRAM 0번지부터 배치되며 두 공간은 서로 침범하지 않는다 — 순수 하버드 구조의 대표 사례다.
- 이 분리 덕분에 CPU는 다음 명령어를 Flash에서 인출하는 동시에, 현재 명령어가 필요로 하는 데이터를 SRAM에서 읽거나 쓸 수 있다 — 같은 클럭에 두 접근이 동시에 성립한다.

### 수정 하버드 구조 — 오늘날 범용 CPU가 쓰는 절충안
- x86·ARM 같은 범용 CPU는 주기억장치(DRAM)는 폰 노이만처럼 하나로 통합해 유연성을 유지하면서도, CPU 코어 안쪽의 L1 캐시만 명령어 전용(I-Cache)과 데이터 전용(D-Cache)으로 분리해 둔다 — 설계마다 다르지만 흔히 코어당 각각 32KB 안팎이다.
- 그 결과 CPU가 실제로 매 클럭 접근하는 지점(L1 캐시)에서는 하버드처럼 동시 접근이 가능하고, 메모리 전체 관점(DRAM)에서는 폰 노이만처럼 유연하다 — 두 구조의 장점을 층(계층)을 나눠 취한 것이다.

### self-modifying code와 보안 — 구조 차이가 만드는 취약점 차이
- 폰 노이만 구조는 데이터 영역에 쓴 값을 "명령어로 착각해" 실행할 수 있는 여지가 구조적으로 있다 — 버퍼 오버플로우 공격이 데이터 영역에 악성 코드를 심고 실행 흐름을 그쪽으로 돌리는 것이 이 여지를 이용한 것이다.
- 이를 막기 위해 CPU에 NX bit(No-eXecute, 실행 금지 비트)를 두어, 데이터로 표시된 페이지는 명령어로 실행하지 못하도록 하드웨어 수준에서 강제한다(OS의 DEP·데이터 실행 방지 기능이 이를 사용).
- 순수 하버드 구조는 애초에 데이터 메모리에서 명령어를 인출하는 경로 자체가 없어 이런 유형의 공격이 구조적으로 성립하지 않는다 — 대신 자기수정코드·동적 코드 생성을 지원하지 못한다.

### 흔한 오해
- "하버드가 최신이고 폰 노이만은 구식이라 안 쓴다" — 틀렸다. 범용 PC·서버의 주기억장치는 지금도 폰 노이만 방식이며, 하버드는 주로 DSP·마이크로컨트롤러(MCU)와 CPU 내부 L1 캐시 설계에 쓰인다.
- "하버드는 무조건 더 빠르다" — 구조상 동시 접근이 가능할 뿐이며, 실제 처리량 차이는 파이프라인·해저드 관점에서 정량적으로 봐야 한다(`001_von_neumann_vs_harvard.md` 참조).

## 핵심 인사이트 (3줄 요약)

> 1. **본질**: 폰 노이만 구조는 명령어·데이터를 단일 메모리·버스로 통합하고, 하버드 구조는 이를 물리적으로 분할한 아키텍처 분류다.
> 2. **가치**: 하버드는 명령어 인출과 데이터 접근을 병렬 수행해 처리량을 높이며, 폰 노이만은 메모리 유연성으로 동적 로딩에 유리하다.
> 3. **판단 포인트**: 범용 시스템은 폰 노이만 기반 수정 하버드, 실시간 신호처리는 순수 하버드를 선택 기준으로 삼는다.

| 보안·설계 트레이드오프 | self-modifying code와 코드 인젝션의 관계 | 선택 기준 없이 개념만 나열 |

## Ⅰ. 개요 및 필요성

- 정의: 명령어·데이터 메모리 및 버스의 통합(폰 노이만) 또는 분리(하버드) 여부로 구분하는 컴퓨터 구조
- 배경: 프로그램 내장 방식의 범용성을 확보했으나 단일 버스 공유로 인한 처리 병목(Bottleneck) 발생
- 필요성: CPU-메모리 간 대역폭이 성능 임계치를 결정하므로 워크로드 특성에 따른 버스 분리 설계가 필요

---

## Ⅱ. 구조 및 구성요소

```text
[폰 노이만] CPU -> 단일 Bus -> 통합 Memory (명령어 + 데이터)
[하버드]   CPU -> Instruction Bus -> I-Memory
               -> Data Bus        -> D-Memory
```

| 구성요소 | 폰 노이만 구조 | 하버드 구조 |
|:---|:---|:---|
| 메모리 | 단일 통합 메모리 공간 | 명령어/데이터 물리적 분리 |
| 버스 | 단일 버스 (주소·데이터 공유) | 명령어 버스·데이터 버스 분리 |
| 대표 사례 | x86·ARM 주기억장치 단 | DSP, AVR 마이크로컨트롤러 |

> 요약: 두 구조의 차이는 메모리 공간과 버스를 물리적으로 통합했는지 분리했는지에 있다.

---

## Ⅲ. 동작원리 및 흐름도

```text
Von Neumann: PC -> Fetch(버스 점유) -> Decode -> Execute -> Memory Access(버스 재점유)
Harvard: PC -> Instruction Bus Fetch (병렬)
               Data Bus Access      (병렬) -> Decode/Execute
```

| 단계 | 처리 내용 | 검증 기준 |
|:---:|:---|:---|
| 1 | 명령어 인출(Fetch) | 버스 점유/경합 여부 |
| 2 | 명령어 해석(Decode) | opcode 해석 정확성 |
| 3 | 실행 및 데이터 접근 | 데이터 버스 병렬 처리 여부 |
| 4 | 결과 저장(Writeback) | 레지스터·메모리 반영 |

> 요약: 하버드 구조는 데이터 접근과 다음 명령어 인출을 병렬로 수행해 버스 대기 시간을 제거한다.

## Ⅳ. 특징

| 구분 | 폰 노이만 구조 | 하버드 구조 | 수치·표준 포인트 |
|:---|:---|:---|:---|
| 성능 상한 | 버스 대역폭에 의한 병목 발생 | 병렬 처리로 대역폭 제약 완화 | 캐시 미스 시 병목 재발 |
| 유연성 | self-modifying code 지원 | 영역 고정으로 유연성 저하 | JIT 컴파일 최적화 유리 |
| 적용처 | 범용 PC·서버 주기억장치 | DSP, 제어용 MCU | 수정 하버드(L1 분리) |

> 요약: 폰 노이만은 유연성, 하버드는 대역폭이 강점이며 현대는 수정 하버드로 이를 절충한다.

## Ⅴ. 심화 비교 및 적용 판단

| 비교 축 | 폰 노이만 | 하버드 | 선택 기준 |
|:---|:---|:---|:---|
| 구조 효율 | 단일 메모리·버스 단순성 | 물리적 분리로 병렬성 확보 | 면적 대비 성능 목표 |
| 비용/성능 | 버스 공유로 비용 절감 | 버스·핀 증가로 비용 상승 | 결정론적 사이클 요구 여부 |
| 보안 위험 | 코드·데이터 혼용 위험 | 물리적 격리로 보안성 향상 | NX bit 적용 여부 |

> 요약: 범용성과 동적 로딩이 필요하면 폰 노이만 기반, 결정론적 대역폭이 필요하면 하버드를 선택한다.

| 리스크 | 원인 | 대응 방안 | 확인 지표 |
|:---|:---|:---|:---|
| 코드 인젝션 | 데이터 영역의 코드 실행 허용 | NX bit, DEP, ASLR 적용 | 실행 가능 페이지 비율 |
| 캐시 불일치 | I/D-Cache 분리 시 동적 코드 미반영 | Cache Invalidate 명령 삽입 | 일관성 오류 발생 건수 |
| 용량 경직성 | 명령어/데이터 메모리 비율 고정 | 통합 메모리 + 캐시 분리 전환 | 메모리 사용률 편차 |

> 요약: 폰 노이만은 보안(인젝션), 하버드는 정적 자원 배분 경직성이 핵심 리스크다.

| 점검 항목 | 목표 기준 | 측정 방법 |
|:---|:---|:---|
| 버스 이용률 | 명령어/데이터 접근 경합 5% 미만 | 성능 카운터(PMU) 분석 |
| 보안 통제 | 실행 가능 메모리 영역 최소화 | 스택/데이터 영역 NX 설정 점검 |
| 처리 지연 | 데이터 접근 시 명령어 인출 중단 0건 | 버스 트레이스 시뮬레이션 |

> 요약: 도입 효과는 버스 경합률, 보안 설정 준수, 처리 지연 제거 여부로 판단한다.

## Ⅵ. 실무 적용 및 결론

**적용 방안 3개:**
1. 범용 시스템은 주기억장치를 폰 노이만으로 설계하되 L1 캐시를 I/D로 분리해 수정 하버드 구조의 병렬성을 확보함
2. 하이엔드 DSP는 순수 하버드 구조를 채택해 단일 사이클 내 다중 오퍼랜드 인출이 필요한 신호처리 연산을 가속함
3. 폰 노이만 구조의 보안 취약점은 하드웨어 NX bit와 OS DEP를 결합해 데이터 영역의 실행 권한을 원천 차단함

**결론 (2줄):**
- 기술사 판단: 범용성과 유연성이 우선이면 폰 노이만 기반 수정 하버드, 확정적 성능이 우선이면 순수 하버드를 선택함
- 향후 방향: 온디바이스 AI 가속기는 데이터 재사용을 위해 하버드형 로컬 메모리 배치를 선호하는 추세임
