# 📖 【암기용】 개념 완전 이해

> 목적: 듀얼 CPU(소켓) 이상의 거대 서버에서 왜 특정 메모리에 접근할 때는 빠르고 어떤 메모리는 느린지, 그 구조적 이유와 최적화 방안을 완벽히 이해하게 만든다.

## 한눈에
- **개요**: 멀티 프로세서(CPU) 시스템에서, 각 CPU마다 자신 전용의 로컬 메모리를 두고 서로의 메모리에 접근할 때 속도(Latency)가 '비균등(Non-Uniform)'하게 차이가 나는 메모리 아키텍처
- **왜 필요한가**: 과거에는 4개의 CPU가 1개의 램(RAM)과 1개의 버스(Bus)를 같이 썼다(UMA 방식). 코어가 수십 개로 늘어나자 램으로 가는 1차선 도로가 꽉 막혔다. 그래서 CPU마다 램을 따로 달아주고(NUMA), 자기 램을 쓸 땐 초고속으로, 남의 램을 쓸 땐 조금 느리게 접근하도록 타협한 것이다.
- **핵심 직관**: 
  - **UMA (과거)**: 4가족이 거실 화장실 1개를 같이 쓴다. 거리가 같아(Uniform) 공평하지만, 아침에 줄 서느라 다 같이 지각한다(병목).
  - **NUMA (현대)**: 안방, 건넛방 등 방마다 화장실(로컬 메모리)을 둔다. 내 방 화장실을 쓰면 1초 컷(Local Access)이지만, 내 화장실이 막혀서 남의 방 화장실을 쓰려면 거실을 지나야 해서 3초(Remote Access)가 걸린다(비균등).

## 깊이 이해
- **배경·문제의식**: 코어 수가 기하급수적으로 늘어나면서 시스템 버스 대역폭 한계(Memory Wall)가 왔다. 코어가 64개인데 메인 메모리 컨트롤러가 1개라면 64명이 1개의 문을 통과하려다 폭동이 일어난다. 메모리 컨트롤러를 각 CPU(소켓) 내부로 분산시킬 필요가 생겼다.
- **작동 원리**: 
  - 서버에 CPU 소켓 2개(Node 0, Node 1)를 꽂는다. Node 0에 램 32GB, Node 1에 램 32GB를 단다.
  - Node 0의 코어는 자기 옆의 32GB 램을 쓸 때(로컬 접근)는 매우 빠르다.
  - Node 0의 코어가 Node 1의 32GB 램에 데이터를 쓸 일(원격 접근)이 생기면, 두 CPU를 잇는 특수 고속도로(인텔 UPI, AMD Infinity Fabric)를 건너가야 하므로 속도가 1.5배~2배 느려진다.
- **비유**: 
  - 로컬 메모리 접근 = 내 책상 서랍에서 펜 꺼내기 (빠름)
  - 리모트 메모리 접근 = 옆자리 동료 책상 서랍에서 펜 꺼내기 (느림, 허락 필요)
- **구체 예시**: 개발자가 멀티스레드 앱을 만들었는데, 스레드 A는 CPU 0에서 도는데 데이터는 CPU 1의 메모리에 있다면? 매번 통신망(UPI)을 건너가느라 CPU가 제 성능의 반도 못 낸다. 이를 막으려면 OS가 알아서 스레드와 메모리를 같은 노드(Node)에 묶어줘야 한다(NUMA 친화성).
- **흔한 오해·주의점**: "NUMA는 메모리가 쪼개져 있어서 프로그램이 32GB밖에 못 쓴다"는 틀렸다. 하드웨어적으로 속도 차이가 있을 뿐, 논리적으로는 64GB 통뼈로 하나로 묶여 있어 아무 문제 없이 접근 가능하다(ccNUMA).

## 연결 개념
- UMA (Uniform Memory Access) / SMP — NUMA 이전 세대의 공평하지만 꽉 막혔던 전통적 아키텍처
- 프로세스 친화성 (CPU/NUMA Affinity) — 스레드가 놀던 물(자기 노드의 CPU와 RAM)에서 계속 놀도록 OS가 못을 박아두는 최적화 튜닝 기법
- 디렉터리 기반 일관성 — NUMA 노드 간에 남의 메모리를 읽고 쓸 때 캐시 일관성을 유지하기 위해 연락을 주고받는 중앙 장부 시스템

# 📝 【답안용】 시험 답안 템플릿

> 목적: 시험장에서 25분에 그대로 쓰는 답안 양식. 

## 핵심 인사이트 (3줄 요약)

> 1. **본질**: NUMA는 대규모 멀티 프로세서(SMP) 환경에서 버스 병목을 해소하기 위해, 메모리와 I/O 컨트롤러를 각 프로세서 노드(Node)로 분산 배치한 분산 공유 메모리 아키텍처다.
> 2. **가치**: 프로세서가 자신의 로컬 메모리에 접근할 때는 극대화된 대역폭을 얻지만, 타 노드의 원격 메모리(Remote Memory) 접근 시에는 인터커넥트를 경유하여 지연(Latency)이 증가하는 비대칭성을 감수한다.
> 3. **판단 포인트**: NUMA 아키텍처의 성능을 100% 끌어내기 위해서는, 애플리케이션의 메모리 할당과 실행 스레드를 동일한 NUMA 노드에 묶어두는 NUMA 인식(NUMA-Aware) 튜닝과 Affinity 설정이 필수적이다.

## 출제 의도 및 답안 포인트

| 출제 의도 | 반드시 짚을 핵심 | 감점 회피 포인트 |
|:---|:---|:---|
| 대규모 멀티코어 서버의 메모리 병목 원인 및 구조적 진화 파악 | UMA(단일 버스 병목)와 NUMA(분산 노드 구조)의 아키텍처 대조 | "메모리가 비대칭이다"라고만 적고 "로컬 vs 원격 접근 지연 차이" 메커니즘을 누락 |
| NUMA 환경에서의 소프트웨어 최적화 한계 극복 역량 평가 | 메모리 할당 정책(Local Allocation) 및 CPU 친화성(Affinity) | 하드웨어 구조만 나열하고 S/W 차원(OS)의 NUMA 스케줄링 대응 방안 부재 |

> 요약: NUMA는 하드웨어의 한계(물리망 병목)를 극복하기 위해 소프트웨어(OS, 개발자)에게 "메모리와 코어의 위치를 신경 써달라"고 책임을 떠넘긴 타협의 산물임을 명시해야 한다.

## Ⅰ. 개요 및 필요성

- 정의: 멀티 프로세서 시스템에서 메모리를 각 프로세서 전용의 로컬 메모리로 분산 배치하여, 메모리 위치(로컬/원격)에 따라 접근 시간(Latency)이 달라지는 구조
- 배경: UMA(Uniform Memory Access) 환경에서 다수의 CPU 코어가 단일 메모리 버스를 공유함에 따라 메모리 병목(Memory Wall) 및 경합 현상 극심화
- 필요성: 시스템 대역폭을 선형적으로 확장(Scale-up)하기 위해, 프로세서 노드별로 독립된 메모리 컨트롤러를 내장하고 고속 인터커넥트로 노드 간 통신을 연결

## Ⅱ. 구조 및 구성요소 (NUMA Node 아키텍처)

```text
[2-Socket NUMA 시스템의 물리적 구성도]
[ NUMA Node 0 ]                     [ NUMA Node 1 ]
+-------+      Local Access         +-------+
| CPU 0 | <==================>      | CPU 1 |
+-------+                           +-------+
  |  ^                                |  ^
  |  |    QPI / UPI (인터커넥트)    |  |
  V  |       (Remote Access)          V  |
[ 로컬 RAM ] <--------------------> [ 원격 RAM ]
```

| 구성요소 | 핵심 역할 | 상세 하위 요소 / 특징 |
|:---|:---|:---|
| NUMA Node | 독립적 연산 단위 블록 | 1개의 CPU 소켓 + 내장 메모리 컨트롤러 + 로컬 메모리 뱅크로 구성 |
| Local Memory | 해당 Node에 직접 연결된 램 | 홉(Hop) 없이 다이렉트 통신하여 최고 속도(Low Latency) 달성 |
| Remote Memory | 타 Node에 소속된 램 | 인터커넥트(예: QPI, Infinity Fabric)를 경유하므로 접근 지연 상승 |
| Interconnect | 노드 간 데이터 버스 | 인텔 UPI, AMD Infinity Fabric 등 칩셋 간 고속 통신망 |

> 요약: NUMA 시스템에서 모든 메모리는 논리적으론 하나(통합 주소 공간)지만, 물리적으로는 거리가 달라 접근 비용이 이원화된다.

## Ⅲ. 동작원리 및 주소 요청 흐름도

```text
[MMU와 메모리 컨트롤러의 NUMA 라우팅 마이크로 흐름]
CPU 메모리 주소 요청 발생 -> [ 메모리 컨트롤러 라우팅 판별 ]
  |--> 해당 주소가 내 로컬 메모리 영역인 경우
  |      => [ 로컬 램 직접 읽기 ] -> 즉시 반환 (지연시간: 1x)
  |
  |--> 해당 주소가 타 노드(Remote) 영역인 경우
         => [ 인터커넥트(UPI) 통해 타 노드 메모리 컨트롤러에 요청 ]
         => 타 노드 메모리 컨트롤러가 램 읽음 -> UPI 통해 회신 (지연시간: 1.5x ~ 2.5x)
```

| 단계 | 제어 유닛 | 처리 내용 및 캐시 일관성(ccNUMA) |
|:---:|:---|:---|
| 1 | 로컬 컨트롤러 | 주소 맵을 확인하여 요청 데이터의 물리적 위치(Home Node) 파악 |
| 2 | 인터커넥트 전송 | 원격 노드일 경우 패킷화하여 QPI/UPI 망을 통해 요청 전달 |
| 3 | 스누핑/디렉터리 | 남의 메모리를 읽거나 수정할 때 캐시 불일치 방지를 위해 디렉터리 기반 일관성 프로토콜 작동 |
| 4 | 응답 및 캐싱 | 원격에서 가져온 데이터는 향후 지연 방지를 위해 내 L3 캐시에 캐싱 |

> 요약: 원격 메모리 접근 시 단순 물리적 거리 지연뿐만 아니라, 캐시 일관성을 묻고 답하는(Directory Coherence) 프로토콜 오버헤드가 더해져 성능이 급락한다.

## Ⅳ. 심화 비교: UMA (SMP) vs NUMA 대조표

| 비교 축 | UMA (Uniform Memory Access) | NUMA (Non-Uniform Memory Access) | 성능 판단 기준 |
|:---|:---|:---|:---|
| 시스템 구조 | 다수 CPU + 1개 공용 버스 + 1개 램 | 각 CPU마다 로컬 메모리 할당 후 결합 | 버스 병목 유발 여부 |
| 접근 지연시간| 어떤 CPU든, 어떤 주소든 **항상 동일** | 로컬은 **빠르고**, 원격은 **느림** | S/W 스케줄러의 복잡성 |
| 확장성(Scalability)| 4~8 소켓 이상 확장 불가 (버스 마비) | 64~128 소켓 이상 대규모 확장 가능 | 데이터센터 엔터프라이즈 적합성 |
| 캐시 일관성 | 공유 버스 스누핑(Snooping) 최적화 | 디렉터리(Directory) 기반 프로토콜 필수 | 브로드캐스트 트래픽 여부 |

> 요약: UMA는 소프트웨어가 편한 구조이고, NUMA는 하드웨어 확장을 위해 소프트웨어에게 희생(최적화 코딩)을 강요하는 구조다.

## Ⅴ. 제약 사항 및 NUMA 병목 (Remote Access) 튜닝 방안

| 리스크 | 발생 원인 | 아키텍처 및 OS 대응 방안 (NUMA 튜닝) | 확인 지표 및 도구 |
|:---|:---|:---|:---|
| CPU-메모리 미스매치 | OS 스케줄러가 코어 0(Node 0)에서 돌던 프로세스를 코어 8(Node 1)로 강제 이주(Migration)시킴 | **CPU Affinity(친화성) 고정**: `taskset`을 통해 특정 프로세스를 특정 NUMA 노드의 코어에 강제 결속 | `numastat` 원격 메모리 할당(Remote Node) 증가량 |
| 원격 할당 붕괴 | 프로세스가 Node 0에서 도는데, Node 0 램이 꽉 차서 어쩔 수 없이 Node 1 램을 할당받아 씀 | **NUMA Local Allocation 강제**: `numactl --localalloc`으로 내 로컬 램만 쓰도록 커널 정책 강제 설정 | 프로세스 응답 속도 편차 (지터) |
| 과도한 페이지 공유 | 여러 스레드가 하나의 전역 변수(원격 노드 존재)를 무한정 동시 참조 | **메모리 인터리빙 (Interleaving)**: 데이터를 여러 노드에 둥글게 쪼개 배치해 특정 노드 병목 분산 | `perf` 기반 원격 캐시 미스(Remote Cache Miss) |

> 요약: NUMA 환경에서 DBMS(오라클, MySQL 등) 구동 시, 노드 간 메모리 이주를 막는 NUMA-Aware 설정(numactl 튜닝)을 하지 않으면 UMA보다도 못한 재앙적 성능 저하가 발생한다.

## Ⅵ. 실무 적용 및 결론

**적용 방안 3개:**
1. RDBMS NUMA 아키텍처 튜닝: 대용량 MySQL/PostgreSQL 운영 시 `innodb_numa_interleave=ON` 옵션을 활성화하거나 `numactl --interleave=all`로 구동하여, 특정 NUMA 노드의 메모리만 고갈되어 OOM(Out of Memory)이 발생하는 Swap Insanity 버그 원천 회피
2. 하이퍼바이저 vNUMA 토폴로지 적용: VMware나 KVM 클라우드에서 대형 VM(예: 32코어, 128GB RAM) 생성 시, 호스트의 물리 NUMA 경계를 무시하고 통째로 할당하면 핑퐁 병목이 발생하므로, 게스트 OS에 vNUMA 토폴로지를 투영해 게스트 OS 스스로 NUMA 최적화를 하도록 유도
3. DPDK 기반 고성능 네트워크 튜닝: 100Gbps 트래픽을 처리하는 5G 코어망(NFV) 구축 시, 랜카드(NIC)가 장착된 PCIe 슬롯이 물리적으로 연결된 동일한 NUMA 노드의 CPU 코어에 패킷 처리 스레드(Worker)를 핀(Pinning) 매핑하여 원격 I/O 지연 제로화

**결론 (2줄):**
- 기술사 판단: NUMA는 무어의 법칙을 넘어선 코어 수 팽창(Scale-up) 시대에 시스템 대역폭 병목을 돌파한 유일한 하드웨어 해법이나, 이는 소프트웨어 스택의 철저한 NUMA 인지(NUMA-Awareness) 없이는 양날의 검으로 작용한다.
- 향후 방향: 최근 CXL(Compute Express Link) 3.0 패브릭의 도입으로 한 대의 랙(Rack) 전체가 거대한 NUMA 노드 풀로 묶이는 메모리 분리(Memory Disaggregation) 아키텍처로 진화하고 있다.
