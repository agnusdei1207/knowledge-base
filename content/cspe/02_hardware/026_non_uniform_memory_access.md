# 📖 【암기용】 개념 완전 이해

## 한눈에
- **개요**: 멀티 프로세서(CPU) 시스템에서, 자기 코어에 가까운 메모리는 빨리 접근하고 남의 코어에 붙은 메모리는 느리게 접근하는 불균형 메모리 아키텍처
- **왜 필요한가**: CPU 코어가 수십~수백 개로 늘어나면서, 모든 CPU가 하나의 좁은 길(시스템 버스)로 메모리에 접근하려다 보니 심각한 병목(트래픽 잼)이 발생했다. 길을 여러 개로 쪼개기 위해 CPU마다 개인 메모리를 나눠주는 방식을 택했다.
- **핵심 직관**: 대형 도서관 구조. 과거에는 중앙 서고(UMA) 하나에 모든 학생이 몰렸다면, NUMA는 각 열람실마다 전용 서재(로컬 메모리)를 둔다. 내 방 서재 책은 3초 만에 꺼내지만, 다른 방 서재 책(원격 메모리)은 복도를 걸어가서 10초 만에 꺼내야 하는 불균등(Non-Uniform)이 생긴다.

## 핵심 용어 정리

| 용어/표기 | 의미 | 비유·예 |
|:---|:---|:---|
| NUMA Node (노드) | CPU(소켓) 1개 + 그에 직결된 로컬 메모리의 한 세트 | 열람실 1개 (학생 + 전용 서재) |
| Local Access (로컬 접근) | CPU가 같은 노드에 꽂혀 있는 자기 메모리에 접근하는 것 | 내 방 서재에서 책 꺼내기 (빠름) |
| Remote Access (원격 접근) | CPU가 인터커넥트(QPI/UPI)를 타고 다른 노드 메모리에 접근 | 남의 방 서재에서 책 가져오기 (느림) |
| SMP / UMA | 모든 CPU가 하나의 메모리를 동등한 속도로 공유하는 과거 방식 | 중앙 통제식 단일 대형 서고 |

## 깊이 이해
- **배경·문제의식**: 고전적인 SMP(Symmetric Multiprocessing) / UMA 구조는 구조가 단순하지만, 코어 수가 8개, 16개를 넘어가면 버스 대역폭 한계로 병목 현상이 극심해져 확장성(Scalability)이 멈춰버렸다.
- **작동 원리**: 전체 물리 메모리 주소는 하나로 통합되어 논리적으로 공유되지만, 물리적 칩은 CPU 소켓별로 분산 배치된다. CPU가 메모리를 읽을 때 주소가 속한 노드를 판별하여, 로컬이면 램을 직접 읽고 원격이면 전용 고속 링크(인터커넥트)를 통해 상대 CPU를 거쳐 데이터를 받아온다.
- **비유**: 지사제 운영. 서울, 부산, 광주 지사(CPU)가 각자 지역 DB(로컬 메모리)를 둔다. 서울 지사가 서울 데이터를 보면 빠르지만, 광주 데이터를 보려면 망을 타야 하므로 지연시간(Latency)이 다르다.
- **구체 예시**: 듀얼 소켓 인텔 제온 서버에서 Node 0의 CPU가 Node 0 램을 읽으면 70ns가 걸리지만, Node 1 램을 읽으려면 UPI 버스를 타고 가야 하므로 110ns 이상 걸린다.
- **흔한 오해·주의점**: NUMA를 켠다고 무조건 빨라지는 게 아니다. OS가 스케줄링을 잘못해서 프로세스는 Node 0에 띄우고 데이터는 Node 1에 할당해버리면, 오히려 100% 원격 접근이 발생해 성능이 폭락한다. NUMA Aware 최적화가 필수다.

## 연결 개념
- 멀티코어 / 멀티소켓 — 여러 개의 CPU가 협력하는 하드웨어 환경
- 캐시 일관성 (Cache Coherence, ccNUMA) — 분산된 메모리 캐시 간의 최신 데이터 상태를 동기화하는 프로토콜
- CPU Pinning / `numactl` — 특정 프로세스를 특정 노드에 가두어 로컬 접근만 유도하는 실무 기술

# 📝 【답안용】 시험 답안 템플릿

## 핵심 인사이트 (3줄 요약)

> 1. **본질**: NUMA는 대규모 멀티 프로세서 환경의 시스템 버스 병목을 해소하기 위해, 메모리를 CPU 노드별로 분산 배치하고 접근 지연시간을 이원화(Local/Remote)한 메모리 아키텍처이다.
> 2. **가치**: 메모리 대역폭을 수평 확장(Scale-out)할 수 있어 수십~수백 코어 서버의 선형적 성능 증가를 가능하게 한다.
> 3. **판단 포인트**: 하드웨어 구조만 도입한다고 성능이 오르지 않으며, 프로세스의 실행과 메모리 할당을 동일 노드에 묶어주는 소프트웨어적 최적화(NUMA Affinity / Pinning)가 시스템 성패를 결정한다.

## 출제 의도 및 답안 포인트

| 출제 의도 | 반드시 짚을 핵심 | 감점 회피 포인트 |
|:---|:---|:---|
| 대규모 시스템의 메모리 병목 극복 원리 확인 | SMP/UMA 한계 극복, Node 구조, QPI/UPI 인터커넥트 | NUMA를 분산 시스템(네트워크 클러스터)으로 오해 |
| 로컬 접근과 원격 접근의 트레이드오프 이해 | 접근 지연 불균등(Non-Uniform), Remote Access 페널티 | 로컬과 원격의 물리적 속도 차이 누락 |
| 실무 아키텍처 튜닝 역량 확인 | NUMA Aware 프로그래밍, CPU Pinning, `numactl` | 하드웨어 구조만 쓰고 SW 통제 방안 누락 |

> 요약: 구조적 장점(확장성) 뒤에 숨은 치명적 단점(원격 접근 페널티)을 정확히 짚고, 이를 소프트웨어적으로 어떻게 회피하는지를 제시해야 한다.

## Ⅰ. 개요 및 필요성

- 개요: 멀티 소켓 프로세서 환경에서 물리 메모리를 CPU별로 분산 배치하여, 메모리 위치(로컬/원격)에 따라 접근 지연시간(Latency)이 달라지는 시스템 구조
- 배경: 코어 집적도 증가로 인해 기존 UMA(Uniform Memory Access) 아키텍처의 단일 시스템 버스 경합 및 메모리 대역폭 포화 한계 노출
- 필요성: 개별 노드의 대역폭을 독립적으로 확보하여 수십 코어 이상의 엔터프라이즈 서버 성능 확장을 지원하기 위해 채택 필수

---

## Ⅱ. 구조 및 구성요소

```text
[ NUMA Node 0 ]                     [ NUMA Node 1 ]
 CPU 0 <---> Local Memory (DRAM)     CPU 1 <---> Local Memory (DRAM)
   |                                   |
   +====== QPI/UPI 고속 인터커넥트 =======+
(로컬 접근: 고속 / 원격 접근: 타 노드 및 인터커넥트 경유로 저속)
```

| 구성요소 | 역할 | 특이사항 |
|:---|:---|:---|
| NUMA Node | 1개의 CPU 소켓과 그에 직결된 로컬 메모리의 논리적/물리적 그룹 | 노드별 독립적 메모리 컨트롤러 내장 |
| Local Memory | 해당 CPU 코어가 버스 경합 없이 가장 빠르게 직접 접근하는 메모리 | 지연시간 최저 (통상 60~80ns) |
| Remote Memory | 다른 Node에 연결되어 인터커넥트를 통해 간접 접근하는 메모리 | 지연시간 증가 (통상 110~140ns 이상) |
| Interconnect | 노드 간 데이터 전송 및 캐시 일관성(ccNUMA) 유지를 위한 통신망 | Intel UPI, AMD Infinity Fabric |

> 요약: 주소 공간은 하나로 통합되어 있지만(Shared Memory), 물리적 배치는 분산되어 지연시간 불균형이라는 특이성을 낳는다.

---

## Ⅲ. 동작원리 및 흐름도

```text
CPU 메모리 요청 -> 주소의 소속 Node 판별 -> [자신의 Node] -> 로컬 메모리 즉시 접근 (Fast)
                                          |
                                          +-> [타 Node] -> 인터커넥트 요청 전송 -> 상대 CPU 메모리 컨트롤러 
                                                        -> 원격 메모리 접근 후 데이터 반환 (Slow)
```

- 1단계 [주소 판독]: CPU 코어 내 메모리 컨트롤러가 요청된 물리 주소가 어느 NUMA Node에 속하는지 라우팅 테이블(Node Map) 확인
- 2단계 [로컬 라우팅]: 주소가 현재 노드 영역이면 칩 외부를 거치지 않고 직결된 램(DIMM)에 로컬 버스로 고속 읽기/쓰기 수행
- 3단계 [원격 라우팅]: 타 노드 영역이면 UPI 패킷으로 캡슐화하여 고속 인터커넥트를 통해 상대 CPU로 릴레이 전송
- 4단계 [ccNUMA 동기화]: 각 노드 간의 L3 캐시 일관성을 유지하기 위해 디렉터리(Directory) 또는 스누핑 프로토콜을 가동하여 데이터 정합성 보장

> 요약: 주소만 맞으면 동작 자체는 투명하게 이루어지지만, 하드웨어 백그라운드에서는 로컬/원격 처리가 완전히 다른 경로와 비용으로 수행된다.

## Ⅳ. 비교 (vs UMA / SMP 아키텍처)

| 비교 축 | UMA (Uniform Memory Access) | NUMA (Non-Uniform Memory Access) | 판단 기준 |
|:---|:---|:---|:---|
| 메모리 버스 구조 | 단일 시스템 버스 공유 | 노드별 다중 분산 버스 + 인터커넥트 | 병목 회피를 위한 버스 분산 여부 |
| 접근 지연시간 | 모든 주소 접근 속도 동일 | 로컬(빠름)과 원격(느림) 차이 발생 | 소프트웨어적 메모리 배치 튜닝 필요성 |
| 확장성 (Scalability) | 8~16 코어 이상 시 한계 | 수십~수백 코어로 선형적 확장 가능 | 데이터센터/엔터프라이즈 서버 적합도 |

> 요약: 단일 버스의 평등함(UMA)을 포기하는 대신, 확장성의 제약을 뚫어낸 것(NUMA)이 현대 서버 아키텍처의 핵심 진화다.

## Ⅴ. 심화 판단: NUMA 성능 병목 및 튜닝 전략

**리스크·대응 (원격 페널티 회피):**
- [원격 접근 핑퐁 현상]: OS 스케줄러가 프로세스를 잦은 빈도로 Node 0과 1 사이로 마이그레이션(Context Switch)시키면, 캐시 미스와 100% 원격 메모리 접근이 발생해 성능 폭락 → 프로세스와 메모리 할당을 동일 노드에 강제로 묶는 **CPU Pinning / NUMA Affinity** 설정 필수 (지표: Remote Node Memory Access Ratio)
- [대용량 공유 버퍼 편향]: RDBMS처럼 수백 GB의 공유 버퍼를 할당할 때 특정 노드에 쏠림 현상 발생 → 커널 파라미터(Interleave 정책)를 변경해 전체 노드에 둥글게 분산 할당하거나, DB 차원(NUMA-Aware) 파티셔닝 수행

## Ⅵ. 실무 적용 및 결론

**적용 방안 3개:**
1. RDBMS 버퍼풀 튜닝: Oracle, MySQL 등 엔터프라이즈 DB에서 `innodb_numa_interleave=1` 등을 적용해 특정 노드 메모리 고갈로 인한 Swap 폭주 리스크 방어
2. 컨테이너/가상머신(VM) 격리: KVM 하이퍼바이저 및 쿠버네티스(Topology Manager) 적용 시, vCPU와 가상 메모리(vRAM)를 동일 물리 NUMA 노드에 배치(Pinning)하여 가상화 오버헤드와 원격 지연 동시 제거
3. OS 레벨 제어 도구 활용: Linux `numactl --cpunodebind=0 --membind=0` 명령어로 핵심 실시간 처리 데몬이 절대로 원격 메모리에 접근하지 못하게 원천 강제

**결론 (2줄):**
- 기술사 판단: NUMA 아키텍처는 하드웨어의 확장성(Scale-out)을 보장하나, OS 및 애플리케이션의 'NUMA 인지(Aware) 튜닝'이 동반되지 않으면 UMA보다 못한 성능을 낸다.
- 향후 방향: 최근 CXL(Compute Express Link) 프로토콜의 등장으로, 물리적 보드에 묶인 로컬 NUMA를 넘어 랙(Rack) 단위의 원격 메모리 풀링을 지원하는 거대 분산 NUMA 아키텍처로 진화하고 있다.
