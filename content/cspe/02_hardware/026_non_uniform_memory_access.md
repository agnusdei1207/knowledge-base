# 📖 【암기용】 개념 완전 이해

## 한눈에
- **개요**: NUMA는 **멀티소켓 프로세서 아키텍처**에서 물리 메모리를 CPU 노드별로 분산 배치하여, 자기 노드 메모리(로컬)는 빠르게, 타 노드 메모리(원격)는 느리게 접근하는 비균등 메모리 구조임.
- **왜 필요한가**: 코어가 수십~수백 개로 늘어나면서 모든 CPU가 하나의 시스템 버스(UMA)로 메모리에 접근하면 대역폭이 포화되어 확장이 불가능해짐. CPU별로 전용 메모리를 두어 버스 병목을 해소하고 메모리 대역폭을 수평 확장함.
- **핵심 직관**: 중앙 서고 1개(UMA)에 모든 학생이 몰리는 대신, 각 열람실마다 전용 서재(로컬 메모리)를 두는 방식. 내 방 서재 책은 3초에 꺼내지만, 다른 방 서재 책(원격 메모리)은 복도를 걸어가서 10초에 꺼내야 하는 불균등(Non-Uniform)이 발생함.

## 핵심 용어 정리 (내부에 등장하는 것들)

| 용어/표기 | 의미 | 비유·예 |
|:---|:---|:---|
| 멀티소켓 아키텍처 (상위 키워드) | 복수 CPU 소켓이 하나의 시스템을 구성하는 서버 구조 | "여러 지사가 하나의 회사" |
| NUMA Node | CPU 소켓 1개 + 직결된 로컬 메모리의 논리적/물리적 그룹 | "열람실 1개(학생 + 전용 서재)" |
| Local Access | CPU가 자기 노드의 메모리에 직접 접근(저지연) | "내 방 서재에서 책 꺼냄(60~80ns)" |
| Remote Access | CPU가 인터커넥트를 경유하여 타 노드 메모리에 접근(고지연) | "남의 방 서재에서 책 빌림(110~140ns)" |
| UMA/SMP | 모든 CPU가 하나의 메모리를 동등한 속도로 공유하는 구조 | "중앙 통제식 단일 서고" |
| ccNUMA | 캐시 일관성(Cache Coherence)이 보장되는 NUMA | "서재마다 최신 판본 동기화" |
| 인터커넥트 | 노드 간 데이터 전송 및 캐시 일관성 유지를 위한 고속 통신망 | "복도(Intel UPI, AMD Infinity Fabric)" |
| NUMA Affinity | 프로세스와 메모리 할당을 동일 노드에 묶는 최적화 설정 | "학생을 자기 방 서재에 고정" |

## 깊이 이해
- **배경·문제의식**: 고전적 SMP/UMA 구조는 단일 시스템 버스를 모든 CPU가 공유하므로, 코어 수가 8~16개를 넘으면 버스 대역폭 포화로 확장성이 한계에 도달함. NUMA는 CPU별 독립 메모리 컨트롤러를 두어 대역폭을 수평 확장함.
- **작동 원리**: 전체 물리 주소 공간은 하나로 통합(Shared Memory)되지만, 물리 칩은 CPU 소켓별로 분산 배치됨. CPU가 메모리를 요청하면 메모리 컨트롤러가 라우팅 테이블(Node Map)로 주소가 속한 노드를 판별하여, 로컬이면 직접 접근하고 원격이면 인터커넥트(UPI/Infinity Fabric)를 경유하여 상대 CPU의 메모리 컨트롤러를 거쳐 데이터를 수신함.
- **비유**: 지사제 운영. 서울·부산·광주 지사(CPU)가 각자 지역 DB(로컬 메모리)를 보유함. 서울 지사가 서울 데이터를 조회하면 빠르지만, 광주 데이터를 조회하려면 WAN(인터커넥트)을 타야 하므로 지연이 발생함.
- **구체 예시**: 듀얼 소켓 Intel Xeon 서버에서 Node 0의 CPU가 Node 0 RAM을 읽으면 약 70ns, Node 1 RAM을 읽으면 UPI를 경유하여 약 110ns 이상. Remote Access Ratio가 30%를 넘으면 체감 성능이 급격히 저하됨.
- **흔한 오해·주의점**: NUMA를 활성화하면 자동으로 빨라지는 것이 아님. OS 스케줄러가 프로세스를 Node 0에 배치하고 메모리를 Node 1에 할당하면 100% 원격 접근이 발생하여 성능이 UMA보다 저하됨. 반드시 NUMA Aware 최적화(CPU Pinning, Memory Binding)가 동반되어야 함.

## 연결 개념
- **020 버스 스누핑/디렉터리**: NUMA의 노드 간 캐시 일관성(ccNUMA)은 디렉터리 기반 프로토콜로 유지됨.
- **109 멀티소켓 서버·SMP**: NUMA의 물리적 구현 환경.
- **035 CXL**: NUMA를 랙 단위의 원격 메모리 풀링으로 확장하는 차세대 인터커넥트.

# 📝 【답안용】 시험 답안 템플릿

## 핵심 인사이트 (3줄 요약)

> 1. **본질**: NUMA는 멀티소켓 환경의 시스템 버스 병목을 해소하기 위해, 메모리를 CPU 노드별로 분산 배치하고 접근 지연을 이원화(Local/Remote)한 메모리 아키텍처임.
> 2. **가치**: 노드별 독립 대역폭으로 수십~수백 코어 서버의 선형적 성능 확장이 가능함.
> 3. **판단 포인트**: 하드웨어 구조만으로는 성능이 보장되지 않으며, 프로세스와 메모리 할당을 동일 노드에 묶는 NUMA Affinity 튜닝이 시스템 성패를 결정함.

## 출제 의도 및 답안 포인트

| 출제 의도 | 반드시 짚을 핵심 | 감점 회피 포인트 |
|:---|:---|:---|
| 대규모 시스템의 메모리 병목 극복 원리 | UMA 한계 → Node 분산, QPI/UPI 인터커넥트 | NUMA를 분산 시스템(네트워크 클러스터)으로 오해 |
| Local/Remote 접근 트레이드오프 이해 | 지연 불균등(70ns vs 110ns), Remote Penalty | 로컬·원격 물리적 속도 차이 수치 누락 |
| 실무 튜닝 역량 확인 | NUMA Affinity, CPU Pinning, numactl | 하드웨어 구조만 서술하고 SW 통제 방안 누락 |

> 요약: 구조적 장점(확장성) 뒤의 단점(원격 접근 페널티)을 짚고, SW적 회피 방안(Affinity/Pinning)을 제시해야 함.

## Ⅰ. 개요 및 필요성

- 개요: 멀티소켓 환경에서 물리 메모리를 CPU 노드별로 분산 배치하여, 접근 위치(Local/Remote)에 따라 지연이 달라지는 메모리 아키텍처임.
- 배경: UMA 아키텍처의 단일 시스템 버스 경합으로 코어 수 8~16개 이상에서 메모리 대역폭 포화 한계가 노출됨.
- 필요성: 노드별 독립 대역폭 확보로 수십 코어 이상 엔터프라이즈 서버의 선형적 성능 확장을 지원해야 함.

---

## Ⅱ. 구조 및 구성요소

```text
[NUMA Node 0]                          [NUMA Node 1]
 CPU 0 <--> Local Memory (DRAM)         CPU 1 <--> Local Memory (DRAM)
   |                                      |
   +----- QPI/UPI 고속 인터커넥트 ----------+
(Local: 60~80ns / Remote: 110~140ns)
```

| 구성요소 | 역할 | 특이사항 |
|:---|:---|:---|
| NUMA Node | CPU 소켓 + 직결 로컬 메모리의 논리/물리 그룹 | 노드별 독립 메모리 컨트롤러 내장 |
| Local Memory | 해당 CPU가 버스 경합 없이 직접 접근하는 메모리 | 지연 60~80ns |
| Remote Memory | 인터커넥트를 경유하여 간접 접근하는 타 노드 메모리 | 지연 110~140ns 이상 |
| Interconnect | 노드 간 데이터 전송 및 ccNUMA 일관성 유지 | Intel UPI, AMD Infinity Fabric |

> 요약: 주소 공간은 하나로 통합(Shared Memory)되어 투명하게 접근 가능하나, 물리적 배치가 분산되어 지연 불균형이 발생함.

---

## Ⅲ. 동작원리 및 흐름도

```text
CPU 메모리 요청 -> 주소의 소속 Node 판별(Node Map)
  자기 Node -> 로컬 메모리 직접 접근(60~80ns)
  타 Node -> 인터커넥트 경유 -> 상대 CPU 메모리 컨트롤러 -> 원격 메모리 접근(110~140ns)
  -> ccNUMA: 노드 간 캐시 일관성을 디렉터리 프로토콜로 동기화
```

- 1단계 [주소 판독]: 메모리 컨트롤러가 요청된 물리 주소가 어느 NUMA Node에 속하는지 라우팅 테이블(Node Map)로 확인함.
- 2단계 [로컬 라우팅]: 자기 노드 영역이면 직결된 DIMM에 로컬 버스로 고속 접근(60~80ns)함.
- 3단계 [원격 라우팅]: 타 노드 영역이면 UPI/Infinity Fabric 패킷으로 캡슐화하여 상대 CPU에 릴레이 전송함.
- 4단계 [ccNUMA 동기화]: 노드 간 L3 캐시 일관성을 디렉터리 기반(020 참조) 프로토콜로 유지하여 데이터 정합성을 보장함.

> 요약: 주소 기반 라우팅으로 로컬/원격이 투명하게 처리되나, 하드웨어 내부적으로는 완전히 다른 경로와 비용으로 수행됨.

---

## Ⅳ. 특징
- 메모리 대역폭 수평 확장: 노드별 독립 메모리 컨트롤러로 전체 대역폭이 노드 수에 비례하여 증가하며, 수백 코어 서버에서도 선형적 확장이 가능함
- Remote Access 페널티: 원격 접근 시 인터커넥트 경유로 로컬 대비 1.5~2배 지연이 발생하며, Remote Access Ratio 30% 초과 시 체감 성능이 급격히 저하됨
- NUMA Aware 필수성: OS 스케줄러가 프로세스와 메모리를 다른 노드에 배치하면 100% 원격 접근이 발생하여 UMA보다 성능이 저하될 수 있으므로 Affinity 설정이 필수임

## Ⅴ. 심화 비교 및 적용 판단

| 구분 | UMA/SMP | NUMA | 선택 기준 |
|:---|:---|:---|:---|
| 메모리 버스 | 단일 시스템 버스 공유 | 노드별 분산 버스 + 인터커넥트 | 코어 수 확장 규모 |
| 접근 지연 | 모든 주소 동일 속도 | 로컬(70ns) vs 원격(110ns) 차이 | SW 튜닝 가용 여부 |
| 확장성 | 8~16코어 한계 | 수십~수백 코어 선형 확장 | 엔터프라이즈 서버 적합도 |
| 대표 적용 | 소규모 워크스테이션 | 듀얼/쿼드 소켓 서버, HPC | 시스템 규모 |

> 요약: 단일 버스의 평등함(UMA)을 포기하는 대신 확장성의 한계를 돌파한 것이 NUMA이며, SW 튜닝 없이는 성능 이점을 실현할 수 없음.

**리스크·대응:**
- 원격 접근 핑퐁: OS 스케줄러의 잦은 노드 간 마이그레이션으로 캐시 미스+100% 원격 접근 발생 → CPU Pinning(numactl --cpunodebind) + Memory Binding(--membind)으로 동일 노드 강제 (지표: Remote Node Memory Access Ratio)
- 대용량 공유 버퍼 편향: RDBMS 수백 GB 버퍼풀이 특정 노드에 쏠림 → Interleave 정책 적용(numactl --interleave=all) 또는 DB 레벨 NUMA-Aware 파티셔닝 (지표: 노드별 메모리 사용률 편차)

**점검 지표:**
- 성능: numastat으로 노드별 Local/Remote Hit 비율 측정, Remote Ratio 10% 이하 목표
- 운영: /proc/zoneinfo의 노드별 메모리 사용률 균형 확인

---

## Ⅵ. 실무 적용 및 결론

**적용 방안 3개:**
1. RDBMS 버퍼풀 튜닝: Oracle/MySQL 운영 시 innodb_numa_interleave=1 적용 또는 numactl --interleave=all로 버퍼풀을 전 노드에 균등 분산하여 특정 노드 메모리 고갈에 의한 Swap 방지
2. 가상화 환경 노드 격리: KVM/QEMU에서 vCPU와 vRAM을 동일 NUMA 노드에 배치(Pinning)하고, Kubernetes Topology Manager를 활용하여 Pod의 CPU·메모리를 노드 단위로 정렬
3. 실시간 데몬 로컬 바인딩: numactl --cpunodebind=0 --membind=0으로 핵심 실시간 처리 데몬을 특정 노드에 고정하여 원격 접근을 원천 차단

**결론:**
- 기술사 판단: NUMA는 하드웨어의 확장성을 보장하나, NUMA Aware 튜닝(Affinity/Pinning/Interleave)이 동반되지 않으면 UMA보다 저조한 성능을 보이므로 SW-HW 동시 설계가 필수임.
- 향후 방향: CXL 프로토콜의 등장으로 물리 보드에 묶인 로컬 NUMA를 넘어 랙 단위 원격 메모리 풀링(036 참조)을 지원하는 거대 분산 NUMA 아키텍처로 진화 중임.
