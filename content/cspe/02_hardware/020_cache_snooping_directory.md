# 📖 【암기용】 개념 완전 이해

## 한눈에
- **개요**: 멀티코어 캐시 간 데이터 불일치(MESI 상태 등)를 추적하고 업데이트할 때, 코어들이 서로 어떻게 통신하여 정보를 주고받을 것인지 정하는 두 가지 아키텍처 방법론이다. (버스 스누핑 vs 디렉터리 기반)
- **왜 필요한가**: 코어 수가 2~8개일 때는 모두가 모인 단톡방(버스)에 외쳐도 소화가 되지만, 코어가 64개, 128개로 늘어나면 단톡방이 터져버리므로(트래픽 병목) 이를 통제할 중앙 명부(디렉터리)가 필요해졌다.
- **핵심 직관**: 
  - **스누핑 (Snooping)**: 조별 과제 4명. "얘들아 나 이 파일 수정한다!"라고 허공에 외치면(Broadcast), 나머지 3명이 듣고(Snoop) 자기 노트북 파일을 폐기한다. 코어가 적을 때 빠르고 직관적이다.
  - **디렉터리 (Directory)**: 전교생 1,000명. 허공에 외치면 시끄러워서 학교가 마비된다. 대신 중앙 도서관 장부(디렉터리)에 "어느 반 아무개가 이 책을 대여 중"이라고 적어둔다. 책을 수정하고 싶으면 도서관에 물어보고, 도서관장이 대여 중인 애들에게만 쪽지를 보내 폐기시킨다.

## 핵심 용어 정리 (내부에 등장하는 것들)

| 용어/표기 | 의미 | 비유·예 |
|:---|:---|:---|
| 공유 버스 (Shared Bus) | 코어들이 묶여있는 하나의 통신선. 한 명이 말하면 모두가 듣는다. | "동네 마을 방송망" |
| 스누핑 (Snooping) | 공유 버스에 지나다니는 다른 코어의 읽기/쓰기 요청을 계속 엿듣는 감시 행위 | "다른 조원이 무슨 말 하는지 엿듣기" |
| 브로드캐스트 (Broadcast) | 버스에 물려있는 모든 캐시 컨트롤러에게 메시지를 무차별 살포하는 것 | "전체 공지 때리기" |
| 디렉터리 (Directory) | 메모리 블록마다 어느 코어 캐시에 적재되어 있는지(상태/위치) 기록해둔 중앙 장부 | "주민등록 원부 / 중앙 대출 장부" |

## 깊이 이해
- **배경·문제의식**: MESI 같은 캐시 일관성 규약이 동작하려면 다른 코어의 상태를 알아야 한다. 초기 멀티코어는 1개의 공유 버스로 묶여 있어서 스누핑 방식이 완벽했다. 하지만 서버용 매니코어(Many-core) 시대(수십~수백 개 코어)가 열리자, 코어 1개가 메모리에 접근할 때마다 64개 코어 전체에 브로드캐스트를 때리니 상호 연결(Interconnect)망이 마비되는 확장성(Scalability) 한계에 직면했다.
- **작동 원리**:
  1. **버스 스누핑**: 모든 코어의 캐시 컨트롤러가 버스를 감시한다. 내가 A주소를 쓴다고 버스에 흘리면, 그걸 들은 다른 캐시들이 자기 쪽에 A주소가 있는지 검색(Tag 비교)하고 있으면 버린다.
  2. **디렉터리 기반**: 메모리 컨트롤러 옆에 '디렉터리'라는 메모리를 하나 더 둔다. 코어 A가 쓴다고 하면 디렉터리에 요청한다. 디렉터리가 장부를 보니 "코어 B와 C가 가지고 있네"라고 파악한 뒤, 전체가 아닌 딱 B와 C에게만 "지워라"라고 유니캐스트(Unicast) 메시지를 쏜다.
- **비유**: 스누핑은 그룹채팅방 전체 알림(빠르지만 인원 많으면 알림 공해). 디렉터리는 게시판 관리자가 읽은 사람 명단을 확인하고 그 사람들에게만 개인 DM 보내기(DM 보내는 지연 시간은 있지만 전체방은 조용함).
- **흔한 오해·주의점**: 디렉터리 방식이 최신이니까 스누핑보다 속도가 '빠를' 거라 착각하면 안 된다. 디렉터리에 물어보고 응답받는 과정 때문에 '명령어 1개 처리 지연 시간(Latency)'은 디렉터리가 더 느리다. 하지만 코어가 수십 개일 때 버스가 안 터져서 '전체 코어의 스루풋(대역폭)'이 보장되므로 쓰는 것이다.

## 연결 개념
- **019 MESI 프로토콜**: 스누핑과 디렉터리가 '무엇을 통신할지' 규정한 내용물(알맹이)이라면, 이 2가지는 '어떻게 배달할지' 정하는 택배 시스템이다.
- **NUMA 아키텍처**: CPU 소켓이 여러 개인 거대 서버. 디렉터리 방식 없이는 NUMA 구성 자체가 불가능하다.

# 📝 【답안용】 시험 답안 템플릿

## 핵심 인사이트 (3줄 요약)

> 1. **본질**: 멀티코어 캐시 일관성(MESI 등)을 유지하기 위한 트래픽 통신 아키텍처로, 전파 방식(Broadcast 기반 Snooping)과 중앙 통제 방식(Directory)으로 양분된다.
> 2. **가치**: 스누핑은 저지연(Low Latency)으로 단일 CPU 내 소규모 코어 동기화에 유리하고, 디렉터리는 점대점(Point-to-point) 메시징으로 수십~수백 코어 환경의 확장성(Scalability)을 보장한다.
> 3. **판단 포인트**: 공유 버스의 대역폭 포화 한계로 인해 코어 수가 급증하는 현대 매니코어(Many-core) 및 NUMA 서버 환경에서는 디렉터리 기반 프로토콜이 필수 아키텍처로 채택되었다.

## 출제 의도 및 답안 포인트

| 출제 의도 | 반드시 짚을 핵심 | 감점 회피 포인트 |
|:---|:---|:---|
| 캐시 통신 아키텍처의 트레이드오프 파악 | Broadcast(스누핑) vs Directory 장부 조회의 통신 구조 차이 | MESI 상태(M,E,S,I) 설명만 길게 쓰고 스누핑 구조 설명 누락 |
| 확장성(Scalability) 한계 논리 도출 | 코어 수 증가에 따른 버스 병목(스누핑의 약점) | 디렉터리 방식이 무조건 지연 속도가 더 빠르다고 적는 오류 |

> 요약: 스누핑은 "빠르지만 확장이 불가능한 단톡방", 디렉터리는 "느리지만 트래픽이 통제되는 중앙 콜센터"라는 명확한 대조를 그려내야 한다.

## Ⅰ. 개요 및 필요성

- 개요: 캐시 일관성 유지방식은 멀티코어 환경에서 캐시 상태 변화(무효화 등)를 타 코어에 전달하는 토폴로지로, 스누핑(Snooping)과 디렉터리(Directory) 기반 방식으로 나뉜다.
- 배경: 버스 감시를 통한 스누핑 브로드캐스트 트래픽은 코어 수($N$)가 증가함에 따라 $O(N)$ 비율로 증가하여 상호 연결(Interconnect) 대역폭의 물리적 한계 도달
- 필요성: 시스템 크기(코어 수 및 물리적 소켓)에 따라 응답 시간(Latency) 최적화와 대역폭(Bandwidth) 확장성 중 적합한 통신 메커니즘을 선택 설계하기 위함

---

## Ⅱ. 구조 및 구성요소 (아키텍처 토폴로지 비교)

```text
[ 버스 스누핑 구조 ]               |   [ 디렉터리 기반 구조 ]
+----+ +----+ +----+             |   +----+     +----+     +----+
| C1 | | C2 | | C3 |             |   | C1 |     | C2 |     | C3 |
+--+-+ +--+-+ +--+-+             |   +--+-+     +--+-+     +--+-+
   |      |      |               |      +---------+----------+ (Point-to-point망)
======================= (공유 버스) |                |
       (모두가 엿들음)               |         [ Directory 장부 ] -- [ 메모리 ]
```

| 유지 방식 | 핵심 통신 매개체 | 브로드캐스트 유무 |
|:---|:---|:---|
| 버스 스누핑 | 공유 버스 (Shared Bus) 감시 | O (모든 코어에 무효화 신호 무차별 살포) |
| 디렉터리 기반 | 중앙 디렉터리 메모리 장부 | X (해당 캐시 라인을 가진 코어에만 점대점 전송) |

> 요약: 스누핑은 버스라는 선(Line)을 통해 모두가 동시에 외치는 방식이고, 디렉터리는 장부라는 점(Node)을 통해 대상만 타겟팅하는 방식이다.

---

## Ⅲ. 동작원리 및 흐름도 (쓰기 요청 발생 시)

**1. 스누핑 (Snooping) 동작 흐름**
- 1단계: 코어 1이 변수 $X$를 쓰기(Write) 위해 버스에 Invalidate(무효화) 신호를 브로드캐스트
- 2단계: 코어 2, 3은 자기 일 안 하고 버스를 엿듣다가(Snoop), 자기 캐시에 $X$가 있으면 즉시 무효화(I 상태로 강등)
- 3단계: 버스 응답을 확인한 코어 1이 즉시 데이터 수정

**2. 디렉터리 (Directory) 동작 흐름**
- 1단계: 코어 1이 변수 $X$를 쓰기 위해, 홈 노드의 디렉터리 컨트롤러에 쓰기 권한 요청 메시지 발송
- 2단계: 디렉터리가 장부를 뒤져 "코어 3이 공유(S) 중"임을 파악하고, 코어 3에게만 Invalidate 유니캐스트(Unicast) 발송
- 3단계: 코어 3이 디렉터리에 완료 Ack를 쏘면, 디렉터리가 코어 1에 승인 신호를 보내어 쓰기 수행

> 요약: 스누핑은 중앙 통제 없이 자율적으로 빠릿빠릿하게 움직이나, 디렉터리는 중앙 장부를 거쳐야 하므로 최소 3-hop의 지연 시간(Latency) 페널티를 감수해야 한다.

---

## Ⅳ. 특징
- 버스 스누핑의 병목: 단일 트랜잭션의 지연(Latency)은 극도로 짧으나, 코어 수가 8~16개를 초과하면 버스 트래픽이 100% 락(Lock)에 걸려 전체 시스템 확장 불가
- 디렉터리 메모리 오버헤드: 코어와 메모리가 늘어날수록 장부(Directory)를 저장할 추가적인 SRAM 공간이 비례하여 증가하므로 회로 면적 낭비 발생
- 확장성(Scalability) 역전: 코어 64개 환경에서는 스누핑 버스가 폭주하여 성능이 0으로 수렴하나, 디렉터리 방식은 장부 조회 오버헤드를 견디며 선형적 성능 확장을 유지

> 요약: 성능 평가 기준이 소규모 코어의 '응답 속도'라면 스누핑이 승자이고, 대규모 코어의 '트래픽 통제력'이라면 디렉터리가 승자이다.

## Ⅴ. 심화 비교 및 적용 판단

| 비교 축 | 버스 스누핑 방식 | 디렉터리 기반 방식 | 선택 기준 |
|:---|:---|:---|:---|
| 통신 방식 | 무차별 브로드캐스트 (Broadcast) | 타겟형 점대점 멀티캐스트/유니캐스트 | 코어의 확장 규모 |
| 레이턴시(지연) | 매우 짧음 (버스 직접 감시) | 김 (디렉터리 조회 및 분산 통신 Hop) | 응답 시간 민감도 |
| 적합한 아키텍처 | 4~8코어 UMA (단일 PC/스마트폰) | 64코어 이상 NUMA (클라우드/엔터프라이즈) | 물리적 소켓/노드 개수 |

> 요약: 스마트폰 AP나 데스크톱 CPU 수준에서는 스누핑이 완벽하지만, 서버 클러스터 등 거대 칩에서는 디렉터리 도입이 물리적 강제 사항이다.

**리스크·대응 (기본은 불릿):**
- 디렉터리 장부 오버헤드 폭증 리스크: 코어가 128개로 늘면 1개 메모리 블록당 128비트의 위치 장부가 필요해 SRAM 낭비 극심 → 듬성듬성 기록하는 성긴 디렉터리(Sparse Directory) 구조 최적화 적용 (지표: 디렉터리 SRAM 할당 비율 5% 이내)
- 분산 노드 홈-디렉터리 병목: 특정 메모리(Home Node)의 디렉터리에만 권한 요청이 몰릴 경우 응답 지연 → 메모리 주소를 해싱(Hashing)하여 여러 디렉터리에 분산 배치 적용 (지표: 노드 간 메시지 지연 편차 최소화)

## Ⅵ. 실무 적용 및 결론

**적용 방안 3개:**
1. 하이브리드(계층적) 아키텍처 설계: 인텔 제온(Xeon) 서버 설계 시, 1개의 CPU 칩 내부(코어 간)는 빠른 스누핑 버스로 묶고, 2소켓/4소켓 등 다른 CPU 칩과 통신할 때는 디렉터리 방식(UPI 링크)을 쓰는 투트랙(Two-track) 결합
2. NUMA(불균일 메모리 접근) 시스템 구성: 빅데이터 하둡/스파크 서버 운영 시, 다중 노드 메모리 일관성을 위해 디렉터리 기반인 ccNUMA(Cache Coherent NUMA)를 활성화하여 대역폭 고갈 차단
3. 칩렛(Chiplet) 인터커넥트 최적화: AMD EPYC 등 다수 다이(Die)를 인피니티 패브릭으로 묶을 때, 스누핑 필터(Snoop Filter)라는 일종의 간이 디렉터리를 칩렛 사이에 두어 불필요한 브로드캐스트 전파 차단

**결론 (2줄):**
- 기술사 판단: 코어 수 확대라는 무어의 법칙 파생 효과는 결국 공유 버스의 스누핑 한계를 조기에 노출시켰으며, 이를 극복하기 위해 통신 공학의 라우팅 기법을 빌려온 디렉터리 방식이 필연적으로 대두되었다.
- 향후 방향: 현대 아키텍처는 스누핑의 속도와 디렉터리의 확장성을 융합하기 위해, 모든 코어가 링(Ring)이나 메시(Mesh) 네트워크로 얽힌 상태에서 스누프 필터(Snoop Filter)를 통해 트래픽을 차단하는 하이브리드망으로 진화하고 있다.
