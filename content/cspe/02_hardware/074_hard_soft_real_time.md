## 미리 알고가기

- 실시간 시스템: 계산 결과의 정확성뿐 아니라 결과가 나온 시간이 시스템 성패를 좌우하는 시스템임
- 하드 실시간: 데드라인 위반이 안전사고나 시스템 실패로 이어지는 실시간 유형임
- 소프트 실시간: 데드라인 위반이 품질 저하를 만들지만 시스템 전체 실패는 아닌 유형임
- Firm 실시간: 늦은 결과는 가치가 없지만 하드 실시간처럼 치명적 사고로 이어지지는 않는 중간 유형임
- WCET: 최악 실행 시간(Worst-Case Execution Time, WCET)은 태스크가 최악 조건에서 실행되는 데 걸리는 최대 시간을 분석한 값임

## Ⅰ. 개요

- **정의**: 하드·소프트 실시간은 작업이 정해진 데드라인을 놓쳤을 때의 안전 영향·품질 저하·결과 가치·비용을 기준으로 실시간 요구와 검증 수준을 분류하는 기준임
- **배경/필요성**: 모든 지연이 같은 의미를 갖지는 않으며, 자동차 제동 제어와 동영상 스트리밍 버퍼 지연은 요구되는 보장 수준이 다름. 실시간 유형을 구분해야 과도한 안전 설계나 부족한 검증을 피할 수 있음
- **비유**: 비행기 착륙 신호는 늦으면 사고가 나지만, 영상 자막은 늦으면 불편해지는 정도인 것과 같음

| 출제 의도 | 반드시 짚을 핵심 | 감점 회피 포인트 |
|:---|:---|:---|
| 실시간 유형 구분 설명 | 하드, 소프트, firm, 데드라인, WCET | 단순히 빠른 시스템으로 설명 |
| 설계·검증 수준 판단 | 안전성, 품질 저하, 스케줄링 정책 | 하드 실시간과 고성능 혼동 |

> 요약: 하드·소프트 실시간은 속도 차이가 아니라 데드라인 위반 결과가 치명적인지 품질 저하인지로 구분함.

## Ⅱ. 특징/비교

| 판단 기준 | 하드 실시간 | Firm 실시간 | 소프트 실시간 |
|:---|:---|:---|:---|
| 데드라인 위반 영향 | 시스템 실패, 안전사고, 법규 위반 가능 | 늦은 결과는 폐기되나 치명적 실패는 아님 | 품질 저하, 사용자 불편, 성능 저하 |
| 대표 사례 | 잠김 방지 제동 장치(Anti-lock Braking System, ABS), 항공 제어, 의료 생명 유지 | 공정 검사, 금융 주문 일부, 센서 윈도우 처리 | 영상 재생, 음성 통화, 온라인 게임 |
| 설계 기준 | WCET, 형식 검증, 자원 격리, 이중화 | 기한 내 처리율과 폐기 정책 | 평균 지연, 지터, 서비스 품질(Quality of Service, QoS) |
| 선택 기준 | 안전과 시스템 무결성이 최우선 | 늦은 결과의 경제적 가치가 없음 | 사용자 경험과 처리 효율 균형 |

> 요약: 실시간 유형은 데드라인 위반 시 손실의 성격에 따라 검증 강도와 스케줄링 정책을 다르게 정하게 함.

- **하드 기준**: 최악 조건에서도 데드라인을 보장해야 하므로 보수적 용량 산정과 안전 인증이 필요함
- **소프트 기준**: 일부 지연을 허용하므로 버퍼링, 우선순위 조정, 품질 저하 정책으로 운영 효율을 높일 수 있음
- **혼합 기준**: 하나의 장치 안에서도 안전 제어는 하드, 사용자 표시 UI는 소프트로 분리될 수 있음

## Ⅲ. 구성요소

```text
+----------+      +----------+      +----------+
| Deadline | ---> | Critical | ---> | Schedule |
| Define   |      | Class    |      | Policy   |
+----------+      +----+-----+      +----+-----+
                         |                 |
                         v                 v
                   +----------+      +----------+
                   | WCET     |      | Monitor  |
                   +----------+      +----------+
```

| 구성요소 | 설명 | 비유 |
|:---|:---|:---|
| 데드라인 | 작업 결과가 의미를 가지는 시간 한계이며 실시간성의 기준점임 | 약속 시간 |
| 치명도 분류 | 데드라인 위반이 안전, 품질, 경제성에 미치는 영향을 구분함 | 위험 등급표 |
| WCET 분석 | 최악 조건에서 태스크가 완료되는 시간을 산정해 보장 가능성을 판단함 | 최장 이동 시간 |
| 스케줄링 정책 | 우선순위, 최단 마감 우선(Earliest Deadline First, EDF), 비율 단조 스케줄링(Rate Monotonic Scheduling, RMS) 등으로 태스크 실행 순서를 결정함 | 교통 통제 |
| 감시·대응 | 데드라인 미스 감지, 안전 정지, 품질 저하, 재시도 정책을 수행함 | 비상 절차 |

> 요약: 실시간 분류는 데드라인과 치명도, WCET, 스케줄링, 감시 대응을 연결해 보장 수준을 정하는 구조임.

## Ⅳ. 절차

```text
+----------+      +----------+      +----------+      +----------+
| Classify | ---> | Analyze  | ---> | Schedule | ---> | Verify   |
| Deadline |      | WCET     |      | Resource |      | Runtime  |
+----------+      +----------+      +----------+      +----------+
```

1. **기능 분류**: 기능별 데드라인 위반 결과를 분석해 하드, firm, 소프트 실시간으로 나눔
2. **시간 분석**: 태스크 주기, WCET, 블로킹 시간, 인터럽트 지연을 산정함
3. **스케줄링 설계**: 우선순위, 자원 잠금, 버퍼, 품질 저하 정책을 실시간 유형에 맞춰 정함
4. **검증·감시**: 최악 조건 시험과 런타임 모니터링으로 데드라인 미스와 대응 동작을 확인함

> 요약: 실시간 설계는 기능별 치명도를 분류한 뒤 최악 시간을 분석하고 유형별 보장 정책을 검증하는 과정임.

## Ⅴ. 문제점

- **P1 유형 분류 오류**: 소프트로 볼 기능을 실제로는 안전 관련 하드 기능으로 놓치면 검증 수준이 부족해짐
- **P2 WCET 과소평가**: 캐시 미스, 인터럽트, 공유 버스 지연을 반영하지 않으면 최악 조건에서 데드라인을 놓침
- **P3 혼합 중요도 간섭**: 하드 태스크와 소프트 태스크가 중앙처리장치(Central Processing Unit, CPU), 메모리, 버스를 공유하면 낮은 중요도 작업이 핵심 제어를 방해함

> 요약: 실시간 시스템은 잘못된 치명도 분류, 낙관적 시간 분석, 공유 자원 간섭 때문에 데드라인 보장이 깨짐.

## Ⅵ. 개선방안

1. **단기**: 기능별 데드라인과 위반 결과를 재분류하고 현재 미스 로그를 수집함
2. **중기**: WCET 분석, 우선순위 재설계, 자원 격리, 과부하 시 품질 저하 정책을 적용함
3. **장기**: 기능 안전 프로세스와 실시간 검증 자동화를 개발 수명주기에 통합함

- **P1 대응**: 위험 분석으로 기능 치명도를 재분류하고 안전 관련 기능을 별도 검증함 (확인: 위험 분석표, 안전 요구 추적)
- **P2 대응**: 하드웨어 최악 조건, 인터럽트 부하, 캐시 영향을 포함한 WCET 분석을 수행함 (확인: WCET 여유율)
- **P3 대응**: 파티셔닝, 우선순위 상속, 시간 예산, 버스 대역폭 예약을 적용함 (확인: 간섭 시험, 데드라인 미스율)

> 요약: 실시간 개선은 기능 치명도, 최악 시간, 공유 자원 간섭을 명확히 관리할 때 가능함.

## Ⅶ. 전망

- **발전 방향**: 하드·소프트 실시간은 차량·로봇·스마트팩토리에서 안전 제어와 인공지능(Artificial Intelligence, AI) 인지가 공존하는 혼합 중요도 구조로 확대됨
- **기술사적 판단**: 데드라인 미스 결과, WCET, 지터 허용치, 공유 자원 간섭, 안전 정지 상태를 기준으로 하드와 소프트 영역을 분리함; 데드라인 미스율, 응답시간 분포, 캐시·버스 경합, 과부하 동작, 결함 주입 결과를 중요도별로 확인함
- **기술사 제언**: 하드·소프트 실시간은 속도 차이가 아니라 데드라인 위반 영향과 검증 강도 차이로 구분해야 답안 논리가 선명함
