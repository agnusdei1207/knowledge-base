# 📖 【암기용】 개념 완전 이해

> 목적: 하드·소프트 실시간을 처음 봐도 "빠르고 느림"이 아니라 "마감시간을 놓쳤을 때 무슨 일이 생기는가"로 구분한다는 본질을 이해하게 만든다. 시험 답안 양식이 아니라, 이해를 위한 친절한 설명이다.

## 한눈에
- **개요**: 실시간 시스템을 마감시간(deadline) 초과 시 결과의 심각도 기준으로 분류하는 개념
- **왜 필요한가**: 모든 실시간 시스템에 동일한 수준의 검증 비용을 투입할 수 없다. 마감시간 초과가 재해로 이어지는 시스템과, 품질만 저하되는 시스템은 요구되는 설계·검증 강도가 다르다.
- **핵심 직관**: 하드 실시간은 늦으면 폭발하는 시한폭탄이고, 소프트 실시간은 늦으면 화질이 잠깐 떨어지는 스트리밍이다.

## 깊이 이해
- **배경·문제의식**: 실시간 시스템을 "빠른 시스템"으로만 이해하면 왜 어떤 시스템에는 수억 원대 정형 검증을 투입하고, 어떤 시스템은 통계적 테스트만으로 출시하는지 설명할 수 없다.
- 구분 기준은 처리 속도가 아니라 마감시간을 놓쳤을 때 발생하는 결과의 심각도다.
- 이 심각도 차이가 스케줄링 정책, 검증 방법, 인증 절차의 투입 수준을 결정한다.
- **작동 원리**: 하드 실시간은 마감시간 단 한 번의 초과도 시스템 실패(catastrophic failure)로 정의한다.
- 하드 실시간은 WCET(Worst-Case Execution Time) 정적 분석과 스케줄러빌리티(schedulability) 수학적 증명을 요구한다.
- 소프트 실시간은 마감시간을 놓쳐도 시스템은 계속 동작하되 결과물의 품질이나 효용이 저하된다.
- 소프트 실시간은 평균 응답시간, p95/p99 지연 같은 통계적·확률적 성능 지표로 검증한다.
- 일부 문헌은 펌 실시간(firm real-time)을 별도로 구분하는데, 마감시간을 넘긴 결과는 효용이 0으로 떨어져 폐기되지만 시스템 전체가 재해적으로 실패하지는 않는 중간 범주다.
- **비유**: 하드 실시간은 에어백처럼 늦게 터지면 사고 자체를 막지 못하는 시한폭탄형 계약이고, 소프트 실시간은 동영상 스트리밍처럼 프레임이 한 번 늦어도 버퍼링만 잠깐 발생하는 서비스다.
- **구체 예시**: 하드 실시간 — 자동차 에어백 전개 제어, 엔진 ECU 점화 타이밍, 항공기 비행 제어면(control surface) 구동, 산업 설비 비상정지 인터록.
- 소프트 실시간 — 동영상·오디오 스트리밍 버퍼 재생, 온라인 게임 프레임 갱신, 주식 시세 화면 갱신.
- 펌 실시간(선택적 언급) — 배송 물류 창고의 실시간 재고 조회 응답처럼, 늦은 응답은 그 시점 가치를 잃어 폐기되지만 시스템 전체를 재해로 만들지는 않는 경우.
- **흔한 오해·주의점**: "하드 실시간은 빨라야 하고 소프트 실시간은 느려도 된다"는 서술은 방향이 틀렸다.
- 구분축은 처리 속도가 아니라 마감시간 초과 시 결과의 심각도(시스템 실패 여부)다.
- 하드 실시간 시스템도 처리 속도 자체는 느릴 수 있으며, 대신 그 느린 속도로도 항상 마감시간을 지킨다는 보장이 핵심이다.
- 하드 실시간을 GPOS 통계적 성능 테스트만으로 검증하면 최악 케이스 누락 위험이 있어 부적합하다.

## 연결 개념
- RTOS 실시간 운영체제 — 하드·소프트 실시간 요구를 만족시키는 커널 구현체
- WCET 분석·스케줄러빌리티 증명 — 하드 실시간 마감시간 보장의 검증 방법
- Priority Inversion·Priority Inheritance — 하드 실시간 시스템에서 마감시간 위반을 유발하는 대표 리스크와 대응 기법

> 1. **본질**: 하드·소프트 실시간은 처리 속도가 아니라 마감시간 초과 시 결과가 시스템 실패인지 품질 저하인지로 구분한다.
> 2. **가치**: 이 구분에 따라 검증 강도(WCET 정적 증명 vs 통계적 성능 테스트)와 투입 비용을 다르게 결정할 수 있다.
> 3. **판단 포인트**: 마감시간 위반이 인명·안전 사고로 이어지면 하드 실시간, 효용 저하에 그치면 소프트 실시간으로 분류해 검증 방법을 선택한다.

## Ⅰ. 개요 및 필요성

- 개요: 마감시간 초과 시 결과의 심각도로 실시간 시스템을 구분하는 기준
- 배경: 모든 실시간 시스템에 동일한 검증 비용을 투입할 수 없어 심각도별 차등 검증 체계가 필요해짐
- 필요성: 안전 관련 제어는 WCET·정형 검증, 품질 관련 서비스는 통계적 성능 검증으로 자원을 배분해야 함

---

## Ⅱ. 구조 및 구성요소

```text
실시간 요구사항 -> 마감시간 초과 시 결과 분석
  -> 하드 실시간: 시스템 실패(catastrophic)
  -> 펌 실시간: 결과 효용 0(폐기), 시스템은 유지
  -> 소프트 실시간: 품질/효용 저하, 시스템 유지
  -> 각 분류별 검증 방법 선택
```

| 구성요소 | 역할 | 특이사항 |
|:---|:---|:---|
| 하드 실시간 | 단 1회 마감시간 초과도 실패로 간주 | 에어백, ECU 점화, 비행 제어면, 안전 인터록 |
| 펌 실시간(선택) | 늦은 결과는 효용 0으로 폐기, 시스템은 유지 | 재해적 실패는 아님 |
| 소프트 실시간 | 마감시간 초과 시 품질·효용만 저하 | 스트리밍 버퍼, 게임 프레임, 시세 화면 |
| 검증 체계 | 분류별로 다른 검증 방법 적용 | WCET 정적 증명 vs 통계적 테스트 |

> 요약: 세 범주는 마감시간 초과 결과가 시스템 실패인지, 효용 상실인지, 품질 저하인지로 나뉜다.

---

## Ⅲ. 동작원리 및 흐름도

```text
태스크 정의 -> 마감시간 초과 시나리오 식별
  -> 심각도 분류(하드/펌/소프트)
  -> 하드: WCET 분석 + 정적 스케줄러빌리티 증명
  -> 소프트: 평균·p95 지연 통계적 테스트
  -> 검증 결과에 따라 스케줄링 정책 확정
```

| 단계 | 처리 내용 | 검증 기준 |
|:---:|:---|:---|
| 1 | 태스크별 마감시간 초과 시 결과 영향 식별 | 안전·인명·재산 영향 여부 |
| 2 | 하드/펌/소프트 실시간으로 분류 | 시스템 실패 여부 기준 일관성 |
| 3 | 하드는 WCET·정적 증명, 소프트는 통계적 테스트 적용 | 검증 방법과 분류 일치 여부 |
| 4 | 분류에 맞는 스케줄링 정책(RMS/EDF 등) 확정 | deadline miss 허용 범위 문서화 |

> 요약: 마감시간 초과의 영향을 먼저 분류한 뒤, 그 분류에 맞는 검증 방법과 스케줄링 정책을 확정한다.

## Ⅳ. 특징

| 구분 | 하드 실시간 | 소프트 실시간 | 수치·표준 포인트 |
|:---|:---|:---|:---|
| 마감시간 초과 결과 | 시스템 실패(catastrophic) | 품질·효용 저하 | deadline miss 허용치 0 vs 통계적 허용 |
| 대표 사례 | 에어백, ECU 점화, 비행 제어면, 안전 인터록 | 스트리밍 버퍼, 온라인 게임, 시세 화면 | 응답시간 상한 vs 평균 지연 |
| 검증 방법 | WCET 정적 분석, 스케줄러빌리티 수학적 증명 | 평균·p95/p99 지연 통계적 테스트 | 정형 검증 vs 벤치마크 |
| 스케줄링 요구 | RMS/EDF 등 결정론적 정책 필수 | best-effort·우선순위 근사 허용 | 이용률 상한 준수 여부 |

> 요약: 하드 실시간은 정형 검증 필수, 소프트 실시간은 통계적 성능 검증으로 충분하다는 점이 핵심 차이다.

## Ⅴ. 심화 비교 및 적용 판단

| 비교 축 | 하드 실시간 | 소프트 실시간 | 선택 기준 |
|:---|:---|:---|:---|
| 검증 방법 | WCET 정적 분석 + 스케줄러빌리티 정형 증명 | 평균·p95 지연 통계적 성능 테스트 | 마감시간 위반이 인명·안전 사고로 이어지는지 여부 |
| 스케줄링 정책 | RMS/EDF 기반 결정론적 보장 필수 | 우선순위 근사, best-effort 허용 | 위반 시 결과 심각도 |
| 비용/인증 | 안전 인증(예: 기능안전 표준) 대응 비용 큼 | 통계적 SLA 관리 위주로 비용 상대적으로 낮음 | 규제·인증 요구 여부 |

> 요약: 마감시간 위반이 재해로 이어지면 하드 실시간 검증 체계, 품질 저하 수준이면 소프트 실시간 검증 체계를 선택한다.

| 리스크 | 원인 | 대응 방안 | 확인 지표 |
|:---|:---|:---|:---|
| 하드 실시간 오분류 | 안전 영향 태스크를 소프트 실시간으로 취급 | 태스크별 마감시간 초과 영향 재평가 | 안전 영향 태스크 식별 누락 건수 |
| WCET 과소 산정 | 최악 실행 경로 누락 | 정적 분석 도구로 전체 코드 경로 재검증 | WCET 대비 실측 최대 실행시간 초과 여부 |
| 소프트 실시간 품질 저하 누적 | 통계적 지연만 관리하고 사용자 체감 미측정 | p95/p99 지연과 사용자 이탈률 함께 관리 | 버퍼 언더런 발생률 |

> 요약: 하드 실시간은 오분류와 WCET 과소 산정을, 소프트 실시간은 체감 품질 저하를 리스크로 관리한다.

| 점검 항목 | 목표 기준 | 측정 방법 |
|:---|:---|:---|
| 하드 실시간 준수 | deadline miss 0건 | WCET 정적 분석, 스케줄러빌리티 증명 재검증 |
| 소프트 실시간 품질 | p95/p99 지연 목표치 이내 | APM, 버퍼 언더런 로그 |
| 분류 정합성 | 태스크별 하드/펌/소프트 분류 문서화 | 요구사항 추적표, 안전성 평가서 |

> 요약: 도입 후 성공 여부는 하드 실시간의 deadline miss 0건 유지와 소프트 실시간의 통계적 지연 목표 충족으로 판단한다.

## Ⅵ. 실무 적용 및 결론

**적용 방안 3개 (필수 — 단계별 또는 항목별):**
1. 마감시간 위반이 인명·안전 사고로 이어지는 제어 태스크는 하드 실시간으로 분류해 WCET 분석과 스케줄러빌리티 정형 증명을 의무화함
2. 스트리밍·게임·시세 서비스처럼 지연이 품질 저하로 그치는 태스크는 소프트 실시간으로 분류해 p95/p99 지연 기반 통계적 테스트로 검증함
3. 분류가 모호한 태스크는 늦은 결과의 효용 소멸 여부를 기준으로 펌 실시간 여부를 재검토하고 문서화함

**결론 (2줄):**
- 기술사 판단: 구분 기준은 처리 속도가 아니라 마감시간 초과 시 결과의 심각도이며, 이에 따라 검증 방법과 투입 비용을 차등화함
- 향후 방향: 자율주행·산업 IoT 확산으로 하드·소프트·펌 실시간이 혼재하는 mixed-criticality 아키텍처의 검증 체계 표준화가 필요함
