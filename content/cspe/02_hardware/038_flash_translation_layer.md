# 📖 【암기용】 개념 완전 이해

## 한눈에
- **개요**: 덮어쓰기가 안 되는 낸드 플래시의 치명적 단점을 감추고, 마치 하드디스크(HDD)처럼 자유롭게 쓰게 해주는 SSD 내부의 소프트웨어 계층
- **왜 필요한가**: 컴퓨터(OS)는 "A번지에 데이터를 덮어써라"고 명령하는데, 낸드 플래시는 덮어쓰기가 물리적으로 불가능하다. 먼저 크게 지워야만 쓸 수 있다.
- **핵심 직관**: "주소와 실제 창고 칸을 매핑하는 영리한 창고 관리자. OS가 '기존 칸에 덮어써라'고 하면, 빈 새 칸에 쓰고 주소표만 쓱 바꾼 뒤 예전 칸은 나중에 한 번에 청소한다."

## 핵심 용어 정리

| 용어/표기 | 의미 | 비유·예 |
|:---|:---|:---|
| 덮어쓰기 불가 (No Overwrite) | 플래시 메모리는 데이터가 있는 셀에 새 데이터를 바로 쓸 수 없음. 지우기(Erase) 후 쓰기(Program) 필수 | "이미 칠해진 도화지엔 그릴 수 없어 새 도화지를 쓴다" |
| 맵핑 테이블 (Mapping Table) | OS가 아는 논리 주소(LBA)와 실제 칩의 물리 주소(PBA)를 연결하는 장부 | "택배 송장 번호와 실제 창고 선반 번호 연결" |
| WAF (Write Amplification Factor) | 내가 쓰라고 명령한 데이터양 대비 실제 플래시에 기록된 데이터양의 비율 | "1MB 쓰려다 주변 데이터 옮기느라 3MB를 쓰는 현상" |

## 깊이 이해
- **배경·문제의식**: HDD는 같은 섹터에 자성을 바꿔 덮어쓰기가 자유롭다. 반면 낸드(NAND)는 쓸 때는 작은 페이지(Page, 보통 4~16KB) 단위지만, 지울 때는 거대한 블록(Block, 수 MB) 단위로만 지워진다. OS가 4KB를 덮어쓰려 할 때마다 블록 전체를 지웠다 쓰면 속도가 수만 배 느려지고 수명도 깎인다.
- **작동 원리**: FTL이 OS와 낸드 사이에 들어간다. 
  1. **주소 매핑**: OS가 주소 1번에 덮어쓰기를 요청하면, FTL은 기존 1번은 '무효(Invalid)' 처리하고, 비어있는 주소 10번에 데이터를 쓴 뒤 "OS의 1번 = 물리 10번"으로 장부를 고친다. (Out-of-place Update)
  2. **가비지 컬렉션(GC)**: 무효 처리된 쓰레기 데이터가 낸드에 가득 차면, 유효한 데이터만 새 블록으로 이사시키고 헌 블록을 통째로 지워 빈 공간을 확보한다.
  3. **웨어 레벨링(Wear Leveling)**: 낸드 셀은 썼다 지웠다 할 수 있는 수명(P/E Cycle)이 있다. FTL은 특정 블록만 혹사당해 죽지 않도록, 모든 블록이 골고루 지워지게 데이터를 순환시킨다.
- **비유**: 호텔 프런트(FTL). 손님(OS)이 "101호 청소하고 다시 들어갈게요" 하면, 101호 청소에 1시간이 걸리니 일단 빈 방인 102호를 주면서 간판만 101호로 바꾼다. 나중에 밤이 되면(Idle 타임) 더러운 방들을 한꺼번에 청소(GC)한다. 특정 방만 망가지지 않게 손님을 골고루 배정(Wear Leveling)한다.
- **구체 예시**: FTL이 없거나 꽉 찬 상태(Dirty State)에서 쓰기를 요청하면 쓰기 속도가 500MB/s에서 50MB/s로 급락한다(GC 부하 때문). 이를 막기 위해 SSD는 보통 7~10%의 숨겨진 예비 공간(Over Provisioning)을 두어 GC를 돕는다.
- **흔한 오해·주의점**: OS의 파일 시스템(NTFS, ext4)과 FTL은 다르다. OS는 디스크가 HDD인지 SSD인지 모른 채 논리 주소(LBA)만 보내고, FTL이 그 아래 펌웨어 단에서 몰래 주소를 변환하는 것이다.

## 연결 개념
- 가비지 컬렉션 (GC) — 흩어진 유효 데이터를 모으고 쓰레기 블록을 비우는 작업
- Wear Leveling — 플래시 셀의 수명을 평균화하여 드라이브 전체 수명을 늘리는 알고리즘
- TRIM 커맨드 — OS가 "이 파일 지웠어"라고 FTL에 알려주어 불필요한 GC 이동을 막는 최적화 명령

# 📝 【답안용】 시험 답안 템플릿

## 핵심 인사이트 (3줄 요약)

> 1. **본질**: SSD FTL은 덮어쓰기가 불가(No-Overwrite)하고 지우기 단위가 큰 낸드 플래시의 물리적 한계를 숨겨, 호스트(OS)가 HDD처럼 논리적 블록(LBA)으로 엑세스할 수 있게 하는 펌웨어 계층이다.
> 2. **가치**: 주소 매핑(Mapping), 가비지 컬렉션(GC), 웨어 레벨링(Wear Leveling)을 통해 성능 저하를 방지하고 낸드 미디어의 수명을 극대화한다.
> 3. **판단 포인트**: FTL의 3대 핵심 기능과 더불어, 백그라운드 작업이 유발하는 쓰기 증폭(Write Amplification) 부작용과 이를 완화하는 TRIM, Over Provisioning 기법을 함께 제시해야 한다.

## 출제 의도 및 답안 포인트

| 출제 의도 | 반드시 짚을 핵심 | 감점 회피 포인트 |
|:---|:---|:---|
| SSD 아키텍처 및 미디어 특성 파악 | No-Overwrite, Erase-before-Write 특성 | 낸드 물리 구조에 대한 설명 없이 FTL 기능만 나열 |
| FTL 3대 핵심 알고리즘 설명 | 맵핑, GC(가비지 컬렉션), Wear Leveling | 메모리(D램) 관점의 페이징이나 OS 캐시와 혼동 |
| 성능 저하 원인과 완화 기술 도출 | WAF (Write Amplification Factor), TRIM, OP | GC를 단순히 메모리 청소로 추상화 (이주 오버헤드 명시 필요) |

> 요약: 낸드의 물리적 약점(Erase-before-write, 수명 한계)이 FTL의 각 기능(맵핑, Wear Leveling)과 어떻게 인과적으로 연결되는지 구조화해야 한다.

## Ⅰ. 개요 및 필요성

- 개요: 낸드 플래시의 물리적 특성을 추상화하여, 파일 시스템(OS)이 디스크를 일반적인 논리 블록 스토리지처럼 사용할 수 있게 변환해주는 SSD 내장 컨트롤러 소프트웨어
- 배경: 낸드 플래시는 덮어쓰기(Overwrite)가 불가능하며, 읽기/쓰기는 페이지(Page) 단위로 이루어지나 지우기는 블록(Block) 단위로만 가능한 물리적 불일치 존재
- 필요성: 이러한 제약 하에서 성능(쓰기 속도)을 유지하고 특정 셀의 수명 조기 고갈(Wear-out)을 방지하는 지능적 주소 및 공간 관리 필수

---

## Ⅱ. 구조 및 구성요소

```text
[ File System (OS) ] -- (LBA: Logical Block Address) -->
      |
+==== [ SSD FTL (Flash Translation Layer) ] =================+
|  1. 주소 맵핑: LBA <-> PBA (SRAM에 테이블 캐싱)            |
|  2. 가비지 컬렉션(GC): Valid Page 이동 후 Block Erase      |
|  3. 웨어 레벨링: P/E Cycle 카운트 기반 Block 평준화        |
+============================================================+
      | (PBA: Physical Block Address)
[ NAND Flash Array (Pages / Blocks) ]
```

| 구성요소 | 역할 | 특이사항 |
|:---|:---|:---|
| Address Mapping | 논리 주소(LBA)를 비어있는 물리 주소(PBA)로 동적 맵핑 | Page 레벨, Block 레벨, Hybrid 레벨로 분류 |
| Garbage Collection | 무효(Invalid) 페이지가 많은 블록을 모아 빈 블록(Free Block) 생성 | Valid 데이터 이동 오버헤드 발생 (성능 저하 요인) |
| Wear Leveling | 낸드 블록의 P/E(Program/Erase) Cycle 편차를 줄여 수명 연장 | Static(정적) 및 Dynamic(동적) 방식으로 나뉨 |

> 요약: FTL은 맵핑 테이블을 통해 덮어쓰기를 "새 공간 쓰기"로 우회하고, 지워진 폐공간은 GC와 Wear Leveling으로 관리한다.

---

## Ⅲ. 동작원리 및 흐름도 (쓰기 동작 기준)

```text
OS 쓰기 요청(LBA 10) -> FTL 맵핑 검색 -> 빈 물리 페이지(PBA 50)에 쓰기 
-> 맵핑 테이블 업데이트(LBA 10=PBA 50) -> 기존 PBA 20을 무효(Invalid) 처리
```

- 1단계 [Out-of-place Update]: OS가 동일 주소(LBA)에 덮어쓰기를 요청하면, 기존 물리 위치를 지우지 않고 새로운 빈 물리 페이지(PBA)에 데이터를 기록
- 2단계 [주소 동기화]: 맵핑 테이블의 LBA 포인터를 새로운 PBA로 갱신하고, 기존 데이터가 있던 물리 페이지는 무효(Invalid/Stale) 상태로 마킹
- 3단계 [임계치 도달 및 GC 트리거]: 빈 블록(Free Block) 개수가 일정 수준 이하로 떨어지면 백그라운드에서 가비지 컬렉션(GC) 시작
- 4단계 [GC 수행]: 무효 페이지가 섞인 희생 블록(Victim Block)에서 유효 페이지만 새 블록으로 복사한 뒤, 희생 블록 전체를 Erase하여 새 빈 블록 확보

> 요약: 덮어쓰기를 빈 공간에 새로 쓰는 방식으로 우회하여 지연 없이 쓰기를 마치고, 쓰레기 공간은 한가할 때(GC) 몰아서 치운다.

---

## Ⅳ. 특징

- [쓰기 증폭 (WAF)]: GC 과정에서 유효 데이터를 새 블록으로 옮겨 쓰는 추가 작업이 발생하여, 호스트가 요청한 양보다 실제 플래시에 기록되는 양이 커지는(WAF > 1) 부작용 존재
- [오버 프로비저닝 (OP)]: OS에 노출되지 않는 약 7~28%의 예비 숨김 낸드 용량(Over Provisioning)을 확보하여 GC의 원활한 수행 공간 제공 및 WAF 통제
- [TRIM 최적화]: 파일 삭제 시 OS가 FTL에 LBA 무효화를 명시적으로 통보(TRIM 명령)하여, 불필요한 GC 데이터 이동 오버헤드 제거

> 요약: FTL의 백그라운드 관리 작업은 디스크 성능과 수명을 보장하지만, 구조적으로 쓰기 증폭(WAF)이라는 페널티를 동반한다.

## Ⅴ. 심화 비교 및 적용 판단

| 비교 축 | Page Mapping | Block Mapping | Hybrid Mapping | 선택 기준 |
|:---|:---|:---|:---|:---|
| 맵핑 단위 | 페이지 단위 (가장 작음) | 블록 단위 (가장 큼) | 논리 블록 단위 / 오프셋 페이지 | 워크로드 패턴의 무작위성 |
| 테이블 크기 (SRAM) | 매우 큼 (많은 메모리 소모) | 매우 작음 | 중간 수준 | SSD 컨트롤러 D램 크기 제약 |
| Random 쓰기 성능 | 가장 우수함 | 매우 취약함 (잦은 GC 발생) | 우수함 | 일반적인 현대 SSD 적용 여부 |

> 요약: 성능을 위해 Page 맵핑이 대세이나, 대용량 테이블을 메모리에 올리기 위한 컨트롤러 스펙(DRAM-less 여부 등) 제약이 판단 기준이 된다.

**리스크·대응:**
- 서든 파워 오프 (Sudden Power-Off): 전원 차단 시 휘발성 SRAM에 있는 맵핑 테이블 증발 및 데이터 유실 → PLP(Power Loss Protection) 커패시터 장착 및 저널링 플러시
- GC로 인한 Latency Spike: 대용량 연속 쓰기 중 GC와 Host I/O가 충돌하여 지연시간 폭증 → 선제적 백그라운드 GC 알고리즘 및 호스트-디바이스 협업 제어

**도입 후 점검 지표:**
- 수명 지표: SMART 정보의 TBW(TeraBytes Written) 한계 잔여량 및 실측 WAF(Write Amplification Factor) 모니터링
- 성능 지표: 디스크가 80% 이상 채워진 더티 상태(Dirty State)에서의 Random 쓰기 IOPS 하락 방어율

## Ⅵ. 실무 적용 및 결론

**적용 방안 3개:**
1. ZNS (Zoned Namespace) 적용: 하이퍼스케일 클라우드 인프라에서는 FTL의 GC 부하를 없애기 위해, OS가 직접 데이터를 순차 영역(Zone)별로 관리하는 ZNS SSD를 도입하여 WAF를 1에 가깝게 통제
2. 워크로드 맞춤 OP 튜닝: 쓰기 집약적(Write-Intensive)인 DB 서버는 OP(Over Provisioning) 비율을 28% 이상으로 늘려 수명과 더티 상태 성능 보장
3. FDP (Flexible Data Placement): 차세대 NVMe 표준인 FDP를 활용해 호스트가 비슷한 수명의 데이터끼리 물리 블록에 모아 쓰게 유도하여 GC 발생 원천 차단

**결론 (2줄):**
- 기술사 판단: FTL은 낸드의 태생적 결함을 소프트웨어로 완벽히 가린 걸작이나, 블랙박스화된 내부 동작으로 인해 호스트 스택(OS)과의 불필요한 이중 작업 오버헤드를 낳는다.
- 향후 방향: 오픈 채널 SSD, ZNS, FDP 등의 기술 발전으로 블랙박스(FTL)의 기능을 호스트 OS 또는 파일 시스템(예: F2FS)으로 점진적으로 개방(Offload)하는 방향으로 진화할 것이다.
