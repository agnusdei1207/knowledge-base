# 📖 【암기용】 개념 완전 이해

## 한눈에
- **개요**: CPU 내부의 명령어 실행, 캐시 적중, 분기 예측 등의 마이크로아키텍처 이벤트를 사이클 지연 없이 정량적으로 측정하는 특수 하드웨어 레지스터
- **왜 필요한가**: 프로그램이 느릴 때 코드를 뜯어고쳐서(SW 삽입 방식) 측정하면 측정 행위 자체가 성능을 떨어뜨림. CPU 하드웨어 단에서 직접 세어주면 오버헤드 0으로 진짜 병목을 찾을 수 있다.
- **핵심 직관**: 도로에 과속 방지턱과 초소를 세우고 차를 세워 세는 게 SW 측정이라면, PMU는 하늘에 떠 있는 위성이 차량 속도를 깎아먹지 않고 은밀히 실시간 계측하는 것.

## 핵심 용어 정리

| 용어/표기 | 의미 | 비유·예 |
|:---|:---|:---|
| PMU (Performance Monitoring Unit) | CPU 내부에 탑재된 성능 모니터링 하드웨어 장치 | 계기판 및 센서 모듈 |
| PMC (Performance Monitor Counter) | 특정 이벤트 발생 횟수를 누적 저장하는 하드웨어 레지스터 | 만보계 |
| Overflow Interrupt (NMI) | 카운터가 꽉 차면 멈추고 OS에 알리는 인터럽트 (샘플링 목적) | 알람 종 |

## 깊이 이해
- **배경·문제의식**: 소프트웨어 프로파일러(gprof 등)는 코드 중간에 시간을 재는 코드를 끼워 넣음. 이러면 실제 캐시 적중률이 왜곡되고 속도가 느려짐(Heisenberg Effect). CPU가 캐시 미스나 파이프라인 스톨을 스스로 세면 어떨까?
- **작동 원리**: CPU 코어 안에 PMU라는 하드웨어가 있음. 개발자가 `perf` 같은 도구로 "L3 캐시 미스를 세어라"라고 지정하면, 해당 이벤트가 발생할 때마다 PMC 레지스터 값이 1씩 올라감. CPU 동작을 전혀 멈추거나 방해하지 않음. 카운터가 특정 값에 도달(오버플로우)하면 인터럽트를 걸어 현재 실행 중인 코드가 어디인지 샘플링(Sampling)함.
- **비유**: 공장 컨베이어 벨트(CPU 파이프라인) 옆에 자동 계수기를 달아둔 것. 작업자가 불량품(캐시 미스)을 던질 때마다 계수기가 찰칵 올라가므로 공정 속도는 전혀 느려지지 않음.
- **구체 예시**: 리눅스에서 `perf stat ./my_program`을 치면 지시어 처리수(Instructions), 클럭(Cycles), 분기 예측 실패율(Branch Misses)이 수치로 딱 나옴.
- **흔한 오해·주의점**: PMU는 하드웨어 종속적임. 인텔 CPU의 이벤트 번호와 AMD CPU의 이벤트 번호가 다름. 따라서 커널(Linux perf_events 등)이 이를 추상화해 주어야 우리가 편하게 쓸 수 있음.

## 연결 개념
- 파이프라인 해저드 (Pipeline Hazards)
- 캐시 메모리 계층 구조
- 인터럽트 처리 (Interrupt Handling)

# 📝 【답안용】 시험 답안 템플릿

## 핵심 인사이트 (3줄 요약)

> 1. **본질**: 하드웨어 성능 카운터(PMU)는 마이크로아키텍처 수준의 하드웨어 이벤트를 오버헤드 없이 측정하는 전용 레지스터 유닛이다.
> 2. **가치**: 코드 주입이나 측정 간섭(Heisenberg Effect) 없이, 캐시 미스·파이프라인 스톨·분기 예측 실패 등 가장 밑바닥의 병목 원인을 정량적으로 도출한다.
> 3. **판단 포인트**: 클라우드와 HPC 성능 튜닝에서 맹목적인 코드 튜닝을 지양하고, PMU 지표(IPC, Cache Miss Rate)에 근거한 데이터 주도적 최적화를 수행하는 도구다.

## 출제 의도 및 답안 포인트

| 출제 의도 | 반드시 짚을 핵심 | 감점 회피 포인트 |
|:---|:---|:---|
| 시스템 레벨 성능 측정 메커니즘 이해 | PMU, PMC, 오버헤드 제로, 샘플링 인터럽트 | 단순한 OS 자원 모니터링(top, vmstat)과 혼동 |
| 병목 탐색 및 튜닝 역량 평가 | Cache Miss, Branch Prediction Miss 지표와 튜닝 방안 연계 | 벤더 종속성을 무시하고 범용 SW로 단정 |

> 요약: 소프트웨어를 수정하지 않고 CPU 하드웨어 단에서 어떻게 파이프라인 스톨과 캐시 병목을 찾아내는지 그 원리와 활용을 묻는 문제다.

---

## Ⅰ. 개요 및 필요성

- 개요: CPU 내부의 명령어 실행, 캐시 적중, 분기 예측 등의 마이크로아키텍처 이벤트를 사이클 지연 없이 정량적으로 측정하는 특수 레지스터 장치임
- 배경: 소프트웨어 코드 주입(Instrumentation) 방식은 측정 자체가 애플리케이션의 동작과 캐시 상태를 변경시키는 측정 간섭 오류 발생
- 필요성: 시스템 소프트웨어 및 고성능 애플리케이션 최적화를 위해 명령어 처리율(IPC)과 병목 구간을 나노초 단위로 정확히 진단해야 함

---

## Ⅱ. 구조 및 구성요소

```text
Microarchitecture Events ---> [ Event Selector ] ---> [ Performance Counter (PMC) ]
                                                            |
User Space Profiler (perf) <--- [ Interrupt (NMI) ] <-------+ (Overflow)
```

| 구성요소 | 역할 | 특이사항 |
|:---|:---|:---|
| Event Selector | 측정할 특정 하드웨어 이벤트(예: L1 Miss) 선택 제어 | MSR(Model Specific Register)로 설정 |
| PMC (Counter) | 선택된 이벤트 발생 횟수를 누적 저장하는 레지스터 | 48~64비트 크기, 개수 제한 존재 |
| Overflow Interrupt | 카운터 오버플로우 시 NMI를 발생시켜 커널에 알림 | 인터럽트 시점의 PC(Program Counter) 샘플링 |

> 요약: PMU는 CPU의 런타임 이벤트 신호를 가로채 카운팅하며, 일정 임계치 도달 시 인터럽트를 발생시켜 현재 병목 지점을 샘플링한다.

---

## Ⅲ. 동작원리 및 흐름도

```text
이벤트 설정(OS) -> 애플리케이션 실행 -> 하드웨어 이벤트 누적 -> 오버플로우 발생 -> 프로파일러 샘플링
```

- 1단계 [설정 및 인가]: 리눅스 `perf` 시스템 콜을 통해 측정할 이벤트 종류와 임계치(Threshold)를 PMU 레지스터에 기록
- 2단계 [투명한 계측]: 애플리케이션이 네이티브로 실행되는 동안, 파이프라인 및 캐시에서 발생하는 이벤트를 PMC가 1사이클 오버헤드 없이 누적
- 3단계 [임계치 도달]: 누적 값이 설정한 임계치(예: 캐시 미스 1만 번)를 넘어 오버플로우 발생 시 하드웨어가 NMI(Non-Maskable Interrupt) 트리거
- 4단계 [샘플링 및 분석]: OS가 인터럽트를 가로채어 당시의 Program Counter(명령어 주소)와 콜스택을 기록 후 통계로 병목 함수 도출

> 요약: PMU는 Counting(전체 횟수 요약)과 Sampling(이벤트 발생 시점의 코드 위치 기록) 두 가지 모드로 동작하여 정밀한 병목을 찾는다.

---

## Ⅳ. 특징
- 제로 오버헤드 측정: 소프트웨어 코드 삽입이 전혀 없으므로 측정 중인 시스템의 실제 성능(캐시 라인, 파이프라인)을 전혀 훼손하지 않음
- 마이크로아키텍처 가시성: OS 레벨 지표(CPU 사용률 등)가 아닌, 명령어 은퇴(Instruction Retired), 스톨 사이클(Stall Cycles) 등 최하단 설계 관점의 지표 제공
- 벤더 종속성(Vendor Lock-in): 인텔(PEBS), AMD(IBS), ARM 등 제조사와 CPU 세대별로 이벤트 식별 코드가 달라 공통 추상화 프레임워크(Linux perf) 필수

## Ⅴ. 심화 비교 및 적용 판단

| 비교 축 | SW Instrumentation (예: gprof) | HW PMU Sampling (예: perf) | 선택 기준 |
|:---|:---|:---|:---|
| 구현 방식 | 컴파일 시 타이밍 측정 코드 삽입 | 하드웨어 레지스터 인터럽트 | 측정 오버헤드 한계 |
| 성능 간섭 | 높음 (측정 자체가 런타임 방해) | 매우 낮음 (인터럽트 시만 개입) | 실환경(Production) 프로파일링 여부 |
| 가시성 | 함수 호출 빈도 및 실행 시간 | 캐시 미스, 파이프라인 스톨, IPC | 마이크로아키텍처 튜닝 여부 |

> 요약: 함수 레벨의 로직 분석은 SW 도구로 충분하나, 하드웨어 튜닝과 메모리 월(Wall) 돌파를 위해서는 HW PMU가 유일한 대안이다.

- 프로파일링 스키드(Skid) 리스크: 인터럽트 발생 시점과 실제 기록 시점 간 파이프라인 지연으로 엉뚱한 명령어 주소가 샘플링되는 현상 → Intel PEBS(Precise Event-Based Sampling) 등 정밀 하드웨어 보정 기능 활성화
- 카운터 자원 고갈 리스크: 하드웨어 PMC 레지스터 개수 한계(통상 4~8개)로 다수 이벤트 동시 측정 불가 → 다중 이벤트를 교대로 측정하는 시간 분할 멀티플렉싱(Multiplexing) 적용

- IPC (Instructions Per Cycle): 1클럭당 처리된 명령어 수 — 1.0 미만 시 스톨 분석
- Cache Miss Rate: L1/L2/L3 캐시 미스 비율 — 데이터 구조체 정렬(Padding) 튜닝 지표

## Ⅵ. 실무 적용 및 결론

**적용 방안 3개:**
1. Top-Down 분석 방법론 적용: PMU를 활용해 병목 원인을 Retiring(정상), Bad Speculation(분기실패), Frontend Bound(인출지연), Backend Bound(메모리/ALU지연) 4가지로 계층적 분류하여 근본 원인 도출
2. False Sharing 튜닝: 멀티스레드 환경에서 캐시 라인 무효화 이벤트(HITM)를 PMU로 추적하여, 성능 저하를 유발하는 캐시 False Sharing 코드 배열 패딩(Padding) 분리
3. 운영환경 연속 프로파일링: eBPF 프로파일러와 Linux perf_events를 결합하여 데이터센터 전체 서버의 마이크로아키텍처 효율을 1% 이하 오버헤드로 상시 모니터링

**결론 (2줄):**
- 기술사 판단: 코어가 아무리 늘어도 IPC가 낮으면 성능이 오르지 않으며, 이를 눈으로 보게 해주는 유일한 렌즈가 하드웨어 PMU이다.
- 향후 방향: 보안 취약점(Spectre/Meltdown)이 마이크로아키텍처의 부채널 공격으로 나타남에 따라, PMU 지표를 AI로 분석하여 런타임 침해를 탐지하는 보안 모니터링 영역으로 활용이 확대되고 있다.
