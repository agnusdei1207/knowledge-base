# 📖 【암기용】 개념 완전 이해

> 목적: PMU를 처음 봐도 CPU 내부에서 무엇을 세고 있는지, 왜 소프트웨어 프로파일러가 이를 필요로 하는지 이해하게 만든다. 시험 답안 양식이 아니라, 이해를 위한 친절한 설명이다.

## 한눈에
- **개요**: CPU 내부에서 캐시 미스, 분기 예측 실패, 명령어 실행 수 같은 마이크로아키텍처 이벤트를 실시간으로 세는 하드웨어 카운터 블록
- **왜 필요한가**: 소프트웨어 로그만으로는 CPU 파이프라인 내부에서 무엇이 병목인지 알기 어렵다. PMU는 실행에 거의 영향을 주지 않으면서 사이클 단위 이벤트를 정확히 측정해 성능 분석 근거를 제공한다.
- **핵심 직관**: 자동차 계기판의 회전수·연비 센서처럼, PMU는 CPU 내부에 미리 심어둔 계측기로 특정 사건이 몇 번 일어났는지를 센다.

## 깊이 이해
- **배경·문제의식**: CPI(Cycles Per Instruction)나 캐시 히트율 같은 지표는 소프트웨어 계측만으로는 오버헤드가 크고 정확도가 떨어져, CPU 설계 단계에서부터 하드웨어 카운터가 내장되었다.
- **작동 원리**: PMU는 MSR(Model-Specific Register) 형태의 카운터 레지스터 여러 개를 두고, 각 카운터에 어떤 이벤트(예: LLC miss, branch misprediction, instructions retired)를 셀지 설정할 수 있다.
- **작동 원리**: 운영체제는 Linux `perf_events`, Windows ETW, Intel VTune, AMD uProf 같은 도구로 PMU 레지스터를 읽어 프로파일링 정보를 사용자에게 제공한다.
- **작동 원리**: Intel PEBS(Precise Event-Based Sampling)는 카운터 오버플로 시점의 정확한 명령어 주소·레지스터 상태를 기록해, 일반 인터럽트 샘플링보다 훨씬 정밀한 프로파일링을 가능하게 한다.
- **비유**: 일반 샘플링은 신호가 울린 뒤 조금 늦게 사진을 찍는 것과 같고, PEBS는 신호가 울린 정확한 순간의 스냅샷을 하드웨어가 즉시 저장해 두는 것과 같다.
- **구체 예시**: `perf stat` 명령으로 특정 프로세스 실행 중 LLC(Last Level Cache) miss 수와 IPC(Instructions Per Cycle)를 측정해, 캐시 최적화가 필요한지 CPU 바운드인지 진단할 수 있다.
- **흔한 오해·주의점**: 카운터 개수는 무한하지 않다.
- **흔한 오해·주의점**: 물리 카운터가 코어당 4~8개 수준으로 제한되어 있어 동시에 측정 가능한 이벤트 종류가 유한하고, 너무 많은 이벤트를 동시에 요청하면 멀티플렉싱(시분할 측정)으로 정확도가 떨어질 수 있다.

## 연결 개념
- 파이프라인 해저드 — PMU가 측정하는 대표 이벤트(분기 예측 실패, 스톨) 발생 원인
- 캐시 메모리 구조 — PMU의 LLC miss, 캐시 히트율 지표와 직결
- VT-x·AMD-V — 가상화 환경에서 PMU 가상화(vPMU)가 게스트에 이벤트 카운팅을 제공

# 📝 【답안용】 시험 답안 템플릿

> 목적: 시험장에서 25분에 그대로 쓰는 답안 양식. 작성방식(추상표현 금지·수치·도식·문제유형 전환)을 엄격히 지킨다.
> 핵심: PMU 답안은 카운터 구조, 이벤트 종류, PEBS 정밀 샘플링, 프로파일링 도구 연계를 함께 제시한다.

## 핵심 인사이트 (3줄 요약)

> 1. **본질**: PMU(Performance Monitoring Unit)는 CPU 내부 마이크로아키텍처 이벤트를 실시간으로 세는 하드웨어 카운터 블록이다.
> 2. **가치**: 소프트웨어 계측 대비 오버헤드가 낮고 사이클 단위로 정확한 병목 지점(캐시 미스, 분기 예측 실패)을 진단할 수 있다.
> 3. **판단 포인트**: 물리 카운터 수가 제한적이므로 동시 측정 이벤트 수와 멀티플렉싱에 따른 정확도 저하를 함께 고려해야 한다.

## 출제 의도 및 답안 포인트

| 출제 의도 | 반드시 짚을 핵심 | 감점 회피 포인트 |
|:---|:---|:---|
| 하드웨어 프로파일링 원리 이해 확인 | MSR 기반 카운터, 이벤트 선택 방식 | PMU를 단순 소프트웨어 로그로 서술 |
| 정밀 샘플링 이해 확인 | PEBS와 일반 인터럽트 샘플링의 차이 | PEBS를 단순 샘플링과 동일시 |
| 활용·운영 이해 확인 | perf, VTune, uProf 등 도구 연계와 카운터 제약 | 카운터 개수 제약 언급 없이 무제한 측정 가능하다고 서술 |

> 요약: 이 문제는 하드웨어 카운터의 구조적 제약과 정밀 샘플링 기법을 근거로 병목 진단 절차를 설명하는지를 본다.

---

## Ⅰ. 개요 및 필요성

- 개요: CPU 내부 마이크로아키텍처 이벤트(캐시 미스, 분기 실패, 명령어 실행 수)를 세는 하드웨어 카운터 유닛
- 배경: 소프트웨어 계측은 오버헤드와 정확도 한계가 있어 CPU 설계 시점부터 전용 카운터 레지스터가 내장됨
- 필요성: CPI 저하 원인을 정확히 진단하려면 사이클 단위로 정밀한 이벤트 카운팅과 샘플링이 필요

---

## Ⅱ. 구조 및 구성요소

```text
CPU Core
  -> PMU: Event Select Register(MSR) + Counter Register
  -> Overflow Interrupt 발생 -> PEBS 레코드 저장(정밀 샘플링)
  -> OS/프로파일러(perf_events, VTune, uProf)가 카운터 값 수집
  -> 분석 리포트(IPC, cache miss rate, branch miss rate)
```

| 구성요소 | 역할 | 특이사항 |
|:---|:---|:---|
| Event Select MSR | 측정할 이벤트 종류 지정 | 코어별 이벤트 코드표 존재 |
| Counter Register | 이벤트 발생 횟수 누적 | 코어당 물리 카운터 4~8개 수준 |
| PEBS 버퍼 | 오버플로 시점 정밀 상태 저장 | 명령어 주소, 레지스터 스냅샷 |
| 프로파일링 도구 | 카운터 값 수집·시각화 | perf, VTune, uProf |

> 요약: PMU는 이벤트 선택 레지스터와 카운터로 이벤트를 세고, PEBS로 오버플로 시점의 정밀 상태를 별도 저장한다.

---

## Ⅲ. 동작원리 및 흐름도

```text
프로파일러가 측정 이벤트 설정(Event Select MSR)
  -> 실행 중 이벤트 발생 시 Counter 증가
  -> Counter Overflow 시 인터럽트 발생
  -> PEBS 지원 시 정밀 상태 레코드 저장
  -> OS/도구가 주기적으로 값 수집 -> 리포트 생성
```

| 단계 | 처리 내용 | 검증 기준 |
|:---:|:---|:---|
| 1 | 측정 대상 이벤트 코드 설정 | 이벤트 코드 유효성 |
| 2 | 실행 중 카운터 누적 | 카운터 오버헤드 최소화 |
| 3 | 오버플로 인터럽트·PEBS 기록 | 샘플링 정밀도 |
| 4 | 값 수집 및 리포트 생성 | IPC, miss rate 산출 정확도 |

> 요약: PMU는 카운터 오버플로를 트리거로 삼아 정밀 이벤트 기록을 남기고, 이를 도구가 수집해 병목을 진단한다.

---

## Ⅳ. 특징

| 구분 | 소프트웨어 계측(로그·타이머) | PMU 하드웨어 카운터 | 수치·표준 포인트 |
|:---|:---|:---|:---|
| 측정 오버헤드 | 상대적으로 높음 | 매우 낮음(하드웨어 내장) | 측정 대상 코드 실행 왜곡 정도 |
| 정확도 | 사이클 단위 정밀도 부족 | 사이클 단위 정밀 측정 | PEBS 정밀 이벤트 주소 |
| 측정 범위 | 애플리케이션 로직 중심 | 마이크로아키텍처 이벤트 중심 | 캐시 미스, 분기 실패, IPC |
| 동시 측정 한계 | 로그 항목 수 제약 적음 | 물리 카운터 수(4~8개) 제약 | 멀티플렉싱 필요 여부 |

> 요약: PMU는 오버헤드가 낮고 정밀하지만 물리 카운터 수 제약으로 동시 측정 이벤트 종류가 제한된다.

## Ⅴ. 심화 비교 및 적용 판단

| 비교 축 | 소프트웨어 계측 | PMU 기반 측정 | 선택 기준 |
|:---|:---|:---|:---|
| 구조 | 애플리케이션 레벨 타이머·로그 | CPU 내장 카운터·PEBS | 마이크로아키텍처 병목 분석 시 PMU 필수 |
| 비용/성능 | 계측 오버헤드로 결과 왜곡 가능 | 오버헤드 거의 없음 | 정밀도 요구 수준으로 판단 |
| 운영/위험 | 이식성 높음(플랫폼 독립) | 벤더·모델별 이벤트 코드 상이 | CPU 세대별 이벤트 코드 관리 필요 |

> 요약: 애플리케이션 흐름 분석은 소프트웨어 계측으로 충분하지만, 마이크로아키텍처 병목 진단은 PMU가 필요하다.

| 리스크 | 원인 | 대응 방안 | 확인 지표 |
|:---|:---|:---|:---|
| 카운터 멀티플렉싱 오차 | 동시 요청 이벤트가 물리 카운터 수 초과 | 측정 이벤트 그룹 분리, 반복 측정 | scaling factor(측정 시간 비율) |
| 가상화 환경 미지원 | 하이퍼바이저가 vPMU 미지원 | vPMU 활성화, 게스트 노출 확인 | vPMU exposed 여부 |
| 이벤트 코드 비호환 | CPU 세대·벤더 간 이벤트 코드 상이 | 벤더 이벤트 매뉴얼 기반 매핑 관리 | 이벤트 코드 버전 관리 이력 |

> 요약: PMU 활용 리스크는 멀티플렉싱 오차, 가상화 미지원, 이벤트 코드 비호환으로 통제한다.

| 점검 항목 | 목표 기준 | 측정 방법 |
|:---|:---|:---|
| 측정 정확도 | scaling factor 100%에 근접 | perf stat 반복 측정 |
| 진단 유효성 | IPC·miss rate 기반 병목 원인 특정 | 프로파일링 리포트 분석 |
| 가상화 호환성 | vPMU 노출 여부 확인 | 하이퍼바이저 설정 점검 |

> 요약: 도입 성공 여부는 측정 정확도, 병목 원인 특정 여부, 가상화 환경 호환성으로 판단한다.

## Ⅵ. 실무 적용 및 결론

**적용 방안 3개:**
1. CPU 바운드 성능 이슈는 PMU 기반 IPC·LLC miss rate 측정으로 병목 원인을 특정함
2. 정밀한 코드 라인 단위 분석이 필요하면 PEBS 지원 이벤트로 샘플링 정밀도를 높임
3. 가상화 환경에서 프로파일링이 필요한 워크로드는 vPMU를 활성화해 게스트에서도 카운터를 사용할 수 있게 함

**결론 (2줄):**
- 기술사 판단: 마이크로아키텍처 수준 병목 진단이 필요하면 PMU 기반 측정을 우선 적용함
- 향후 방향: 클라우드 멀티테넌시 환경에서 vPMU·컨테이너 단위 성능 카운터 격리 기술이 더 정교해질 전망
