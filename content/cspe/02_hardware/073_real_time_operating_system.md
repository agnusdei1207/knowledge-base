## 미리 알고가기

- RTOS는 태스크를 정해진 시간 안에 실행하도록 관리하는 운영체제임
- 평균 처리량보다 최악 응답시간과 지터가 더 중요함
- 우선순위 설계와 인터럽트 처리 방식이 실시간성을 좌우함

## Ⅰ. 개요

- **정의/개념**: RTOS는 태스크와 인터럽트와 타이머와 동기화 자원을 관리해 응답시간 상한과 지터와 데드라인 만족 여부를 예측 가능하게 만드는 실시간 운영체제임
- **배경/필요성**: 자동차와 로봇과 산업 설비는 결과가 빠른 것보다 늦지 않는 것이 더 중요하므로, 범용 운영체제보다 시간 보장에 초점을 둔 운영체제가 필요함

## Ⅱ. 특징

- 우선순위 기반 스케줄링으로 중요한 태스크를 먼저 실행함
- 짧고 예측 가능한 인터럽트 처리 구조가 필수임
- 세마포어와 뮤텍스 같은 동기화 방식이 blocking time에 직접 영향을 줌
- 처리량보다 결정성과 안전성을 우선하는 설계가 많음

## Ⅲ. 종류 및 비교

| 판단 기준 | Bare-metal 루프 | RTOS | 범용 OS |
|:---|:---|:---|:---|
| 실행 구조 | 단순 반복 제어에 맞지만 기능이 늘면 관리가 어려워짐 | 우선순위와 타이머 기반으로 여러 태스크를 예측 가능하게 운영함 | 기능은 풍부하지만 응답시간 상한을 보장하기 어려움 |
| 적합 업무 | 소형 단일 기능 장치에 적합함 | ECU와 로봇과 의료 제어처럼 시간 제약이 있는 장치에 적합함 | PC와 서버와 복합 UI 장치에 적합함 |
| 장점 | 구조가 작고 오버헤드가 적음 | 결정성과 확장성의 균형을 맞추기 쉬움 | 파일시스템과 네트워크와 사용자 기능을 폭넓게 활용할 수 있음 |
| 유의점 | 태스크 분리가 어려워 유지보수가 힘들어질 수 있음 | 우선순위 역전과 ISR 설계를 잘못하면 실시간성이 무너질 수 있음 | 평균 성능만으로는 최악 응답시간을 관리하기 어려움 |

> 요약: RTOS는 우선순위·타이머·동기화 기능으로 여러 태스크를 관리하고 최악 응답시간을 분석함.

## Ⅳ. 구성요소 및 구조

| 구성요소 | 설명 |
|:---|:---|
| 커널·스케줄러 | 태스크 상태와 우선순위와 문맥 전환을 관리함 |
| 인터럽트 계층 | 외부 이벤트를 즉시 받아 실시간 응답의 첫 경로를 형성함 |
| 타이머 서비스 | 주기 태스크와 timeout과 데드라인 감시의 시간 기준을 제공함 |
| IPC·동기화 | 큐와 세마포어와 뮤텍스로 태스크 간 데이터 전달과 자원 접근을 제어함 |

```text
+-------------+     +-------------+     +-------------+     +-------------+
| 태스크 모델 정의 | --> | 우선순위 설계  | --> | 인터럽트·동기화 구현 | --> | 타이밍 검증    |
+-------------+     +-------------+     +-------------+     +-------------+
```

> 요약: RTOS는 커널·스케줄러, 인터럽트 계층, 타이머, IPC·동기화로 시간 제약을 관리함.

## Ⅴ. 원리 및 절차 흐름도

1. **태스크 모델 정의**: 주기와 실행시간과 데드라인을 정리함
2. **우선순위 설계**: 중요한 제어 태스크가 먼저 실행되도록 우선순위를 배정함
3. **인터럽트·동기화 구현**: ISR 길이와 세마포어와 큐 사용 방식을 정함
4. **타이밍 검증**: 응답시간 상한과 지터와 데드라인 미스를 측정함

> 요약: 태스크 모델, 우선순위, ISR·동기화 방식을 정한 뒤 응답시간과 지터를 검증함.

## Ⅵ. 실무 적용 및 유의점

1. 자동차 ECU·산업 로봇은 ISR나 lock 경합이 길면 제어 주기가 흔들리므로 ISR 최소화와 priority inheritance를 적용하고 interrupt latency, deadline miss rate, control jitter로 확인함
2. 의료기기·경보 장치는 범용 기능이 늘수록 메모리와 지터가 불안정해질 수 있으므로 필요한 커널 기능만 남기고 memory usage, scheduling jitter, worst-case response time으로 확인함

## Ⅶ. 결론

RTOS는 평균 처리 속도보다 태스크의 최악 응답시간과 데드라인 준수 여부를 기준으로 설계해야 함.

## 작성 근거(검토용)

- RTOS는 태스크, 인터럽트, 타이머, 동기화, 최악 응답시간을 핵심 축으로 설명함
- 비교표는 bare-metal, RTOS, 범용 OS의 실행 구조와 시간 보장 차이를 대비함
- 실무 판단은 interrupt latency, deadline miss rate, control jitter, worst-case response time으로 검증 가능하게 작성함
