## 미리 알고가기

- RTOS는 태스크를 정해진 시간 안에 실행하도록 관리하는 운영체제임
- 핵심 판단 기준은 결정성과 interrupt latency와 deadline miss rate임
- 평균 성능보다 최악 응답시간 보장이 중요함

## Ⅰ. 개요

- **정의/개념**: RTOS는 태스크와 인터럽트와 타이머와 동기화 자원을 관리해 최악 응답시간과 지터와 데드라인 만족 여부를 예측 가능하게 만드는 운영체제임
- **배경/필요성**: 자동차와 로봇과 산업 설비는 결과가 빠른 것보다 늦지 않는 것이 중요하므로, 범용 OS 대신 시간 보장 중심 운영체제가 필요함

## Ⅱ. 특징

- 우선순위 기반 스케줄링으로 데드라인 중심 실행을 지원함
- 짧고 예측 가능한 인터럽트 처리와 낮은 지터가 중요함
- 동기화 primitive 선택이 blocking time과 우선순위 역전에 직접 영향을 줌
- 처리량보다 결정성과 안전성이 우선됨

## Ⅲ. 종류 및 비교

| 판단 기준 | 범용 OS | RTOS |
|:---|:---|:---|
| 최우선 목표 | 처리량, 공정성 | 결정성, 데드라인 |
| 스케줄링 성격 | 평균 성능 중심 | 최악 응답시간 중심 |
| 인터럽트 처리 | 효율 중심 | 상한 시간 예측 중요 |
| 대표 사용처 | PC, 서버 | 제어기, 로봇, 자동차 |

## Ⅳ. 구성요소 및 구조

| 구성요소 | 설명 |
|:---|:---|
| Kernel, Scheduler | 태스크 상태와 문맥 전환과 우선순위 스케줄링을 관리함 |
| ISR, Interrupt Layer | 외부 이벤트를 즉시 처리하며 실시간 응답성의 첫 관문이 됨 |
| Timer, Clock Service | 주기 태스크와 timeout과 데드라인 감시의 기준 시간을 제공함 |
| IPC, Synchronization | 큐와 세마포어와 뮤텍스로 데이터 전달과 자원 접근을 제어함 |

## Ⅴ. 원리 및 절차 흐름도

```text
+-------------+     +-------------+     +-------------+     +-------------+
| 태스크 모델 정의 | --> | 우선순위 배정  | --> | 인터럽트/태스크 실행 | --> | 타이밍 검증    |
+-------------+     +-------------+     +-------------+     +-------------+
```

1. **태스크 모델 정의**: 주기와 실행시간과 데드라인을 정의함
2. **우선순위 배정**: RMS나 EDF 같은 정책으로 우선순위를 정함
3. **인터럽트 및 태스크 실행**: 커널이 이벤트와 태스크를 제어함
4. **타이밍 검증**: 응답시간과 지터와 데드라인 미스를 측정함

## Ⅵ. 문제점 및 해결 방안

1. 문제: 우선순위 설계가 잘못되면 중요한 태스크가 지연돼 데드라인 미스가 반복될 수 있음
   - 해결방안: schedulability analysis를 수행하고 worst-case response time과 deadline miss rate로 검증함
2. 문제: ISR가 길거나 동기화 블로킹이 길면 지터와 응답 상한이 예측 불가능해질 수 있음
   - 해결방안: ISR 최소화와 우선순위 상속을 적용하고 interrupt latency와 blocking time으로 검증함
3. 문제: 일반 OS 기능을 과도하게 끌어오면 메모리와 결정성이 흔들려 RTOS 특성이 약화될 수 있음
   - 해결방안: 필요한 기능만 포함한 경량 구성을 선택하고 memory footprint와 scheduling jitter로 검증함

## Ⅶ. 적용 사례

- 자동차 제어 ECU에서는 주기 제어 태스크를 RTOS로 운영하고 확인 지표는 deadline miss rate와 control jitter임
- 산업 로봇 제어기에서는 인터럽트 기반 위치 제어를 수행하고 확인 지표는 interrupt latency와 cycle time stability임
- 의료기기 펌웨어에서는 안전 알람 태스크를 우선 실행하고 확인 지표는 response time upper bound와 fault handling latency임

## Ⅷ. 결론

RTOS의 핵심은 빠른 OS가 아니라 늦지 않는 OS이므로, 평균 성능보다 최악 응답시간과 blocking 구조를 먼저 관리해야 함.
