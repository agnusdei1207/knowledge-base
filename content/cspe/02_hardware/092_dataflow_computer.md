## Ⅰ. 개요
- **정의**: 데이터 가용성에 의해 명령어 실행 순서가 결정되는 비폰노이만 컴퓨팅 구조
- **배경/필요성**: 폰노이만 구조에서 프로그램 카운터 기반 순차 실행은 데이터 의존성이 없는 연산도 직렬화하여 병렬성 활용에 한계가 있음
- **비유**: 요리 레시피를 순서대로 따르는 것(폰노이만)이 아니라, 재료가 준비된 요리부터 동시에 조리하는 방식

| 출제 의도 | 반드시 짚을 핵심 | 감점 회피 포인트 |
|:---|:---|:---|
| 폰노이만 vs 데이터플로우 구조 차이 이해 | 토큰 매칭·발화 규칙(Firing Rule) | 정적 데이터플로우와 동적 데이터플로우 구분 |

> 요약: 데이터 준비 여부로 실행을 결정하여 최대 병렬성을 자동 추출하는 구조임

## Ⅱ. 구성요소
```text
Input Tokens
     |
     v
+-----------+     +-----------+
| Matching  |---->| Execution |
|   Unit    |     |   Unit    |
+-----------+     +-----------+
     ^                  |
     |    Result Tokens |
     +------------------+
```

| 구성요소 | 설명 | 비유 |
|:---|:---|:---|
| 토큰(Token) | 데이터 값과 목적지 태그를 포함한 메시지 단위 | 재료가 담긴 배달 상자 |
| 매칭 유닛(Matching Unit) | 노드에 필요한 입력 토큰이 모두 도착했는지 검사하는 장치 | 재료가 다 모였는지 확인하는 조리대 |
| 실행 유닛(Execution Unit) | 발화 조건 충족 시 연산을 수행하는 처리기 | 재료가 갖춰진 요리사 |
| 데이터플로우 그래프 | 연산 노드와 데이터 의존성을 방향 그래프로 표현한 프로그램 | 요리 흐름도 |

> 요약: 토큰이 매칭 유닛에서 모이면 실행 유닛이 발화하여 연산을 수행함

## Ⅲ. 절차
```text
토큰 생성 --> 매칭 검사 --> 발화 실행 --> 결과 토큰 전파
     |            |             |              |
     v            v             v              v
 입력 데이터   태그 비교    연산 수행     후속 노드 전달
```
- 1단계: 토큰 생성 — 입력 데이터를 목적지 태그와 함께 토큰으로 캡슐화함
- 2단계: 매칭 검사 — 매칭 유닛이 대상 노드의 입력 토큰 전부 도착 여부를 확인함
- 3단계: 발화 실행 — 모든 입력이 충족된 노드가 실행 유닛에서 연산을 수행함
- 4단계: 결과 전파 — 연산 결과를 새 토큰으로 생성하여 후속 노드에 전달함

> 요약: 토큰 매칭 → 발화 → 결과 전파 사이클이 자동으로 반복되며 병렬 실행됨

## Ⅳ. 문제점
- 토큰 저장 폭증: 대규모 그래프에서 대기 토큰 수가 급증하여 매칭 유닛 메모리가 부족해짐
- 세밀한 병렬성 오버헤드: 노드당 연산 단위가 지나치게 작으면 토큰 전달·매칭 비용이 연산 비용을 초과함
- 순차 제어 구현 난이도: 조건 분기·루프 등 제어 흐름을 토큰 기반으로 표현하는 프로그래밍 복잡도가 높음

> 요약: 토큰 관리 비용과 프로그래밍 복잡도가 상용화의 장벽임

## Ⅴ. 개선방안
1. 단기: 토큰 풀링(Token Pooling)과 만료 정책 도입으로 매칭 유닛 메모리 사용량을 제한함
2. 중기: 조립 블록(Coarse-Grain) 단위로 노드를 묶어 토큰 전달 횟수를 줄이고 유효 연산 비율을 높임
3. 장기: 컴파일러 수준에서 데이터플로우 그래프를 자동 생성하여 프로그래밍 복잡도를 해소함

> 요약: 토큰 관리 최적화·조립 블록화·컴파일러 자동화로 실용성을 확보함

## Ⅵ. 전망
- 발전 방향: AI 가속기·CGRA 등에서 데이터플로우 실행 모델이 부분 채택되어 확산 중임
- 기술사적 판단: 순수 데이터플로우 범용 프로세서보다 도메인 특화 가속기 내 혼합 모델로 활용 가치가 높음
- 기술사 제언: 폰노이만 구조 한계를 보완하는 대안 아키텍처로서 데이터플로우 개념 이해가 필요
