# 📖 【암기용】 개념 완전 이해

> 목적: 이 개념을 처음 보는 사람도 완벽히 이해하게 만든다. 시험 답안 양식이 아니라, 이해를 위한 친절한 설명이다.

## 한눈에
- **개요**: 데이터 흐름 컴퓨터(Dataflow Computer)는 명령어를 프로그램 카운터(PC) 순서대로 실행하는 폰 노이만의 **제어 흐름(Control-Flow)** 방식 대신, 연산에 필요한 피연산자(데이터)가 모두 준비되는 즉시 해당 연산을 실행(발화, Fire)하는 **데이터 구동형(Data-Driven)** 비(非) 폰 노이만 아키텍처다.
- **왜 필요한가**: 폰 노이만 컴퓨터는 명령어 사이에 실제로는 아무 의존관계가 없어도 PC가 가리키는 순서대로만 실행한다. 코어를 아무리 많이 늘려도 이 인위적 순서 종속성 때문에 병렬로 돌릴 수 있는 명령어가 제한된다. 데이터플로우는 "순서"가 아니라 "데이터가 준비됐는가"만을 실행 조건으로 삼아, 서로 의존하지 않는 연산들을 하드웨어가 자동으로 동시에 실행하게 한다.
- **핵심 직관**: 각 연산(노드)은 자신에게 필요한 입력값(토큰)이 모두 도착하는 순간 스스로 실행되고 결과를 다음 노드로 넘긴다. A+B와 C-D처럼 서로 무관한 두 연산은 각자의 입력이 준비되는 대로 동시에 실행되며, 어느 것이 "먼저 쓰인 명령"인지는 실행 순서와 무관하다.

## 핵심 용어 정리 (내부에 등장하는 것들)

| 용어 | 의미 | 비유 |
|:---|:---|:---|
| 제어 흐름(Control-Flow) | 프로그램 카운터가 정한 순서대로 명령어를 실행하는 폰 노이만 방식(데이터플로우가 대체하는 상위 개념) | 정해진 순서대로 진행하는 회의 안건 |
| 프로그램 카운터(PC) | 다음에 실행할 명령어의 주소를 가리키는 레지스터 — 데이터플로우에는 존재하지 않음 | 회의 진행 순서표 |
| 토큰(Token) | 값과 목적지 노드 정보를 담고 네트워크를 흘러 다니는 데이터 단위 | 배송 중인 소포(내용물+수신지 라벨) |
| 노드(Node) | 하나의 연산(덧셈, 뺄셈 등)을 나타내는 그래프상의 점 | 조립 라인의 개별 작업대 |
| 발화(Firing) | 노드에 필요한 입력 토큰이 모두 도착했을 때 연산이 실행되는 것 | 재료가 다 모이면 자동으로 시작되는 기계 |
| 매칭 유닛(Matching Unit) | 같은 노드로 향하는 토큰들이 모두 도착했는지 대조·결합하는 하드웨어 | 조각을 맞춰 그림을 완성하는 검사대 |
| 정적 데이터플로우(Static) | 노드(파이프)당 토큰을 1개만 허용하는 초기 방식. 구조는 단순하지만 반복문에서 병목 발생 | 한 번에 한 사람만 통과하는 좁은 문 |
| 동적 데이터플로우(Dynamic) | 토큰에 태그(꼬리표)를 붙여, 같은 노드에 여러 반복(iteration)의 데이터가 동시에 들어가도 섞이지 않게 하는 방식(현대 표준) | 같은 색 표를 가진 사람끼리만 짝짓는 방식 |
| DAG(방향성 비순환 그래프) | 데이터가 노드 사이를 어떤 순서로 흐르는지 나타내는 그래프 구조(순환 없음) | 물줄기가 갈라지고 합쳐지는 유역도 |
| 비순차적 실행(Out-of-Order Execution) | 현대 CPU 코어 내부에서 데이터플로우 사상을 국소적으로 구현한 기법 | 부분적으로만 순서를 무시하는 미니 버전 |

## 깊이 이해

### 토큰 매칭과 발화 — 간단한 그래프 worked example
- 수식 `(A+B) × (C-D)`를 데이터플로우 그래프로 그리면 덧셈 노드, 뺄셈 노드, 곱셈 노드 3개가 된다. A, B, C, D 네 개의 토큰이 동시에 준비돼 있다면, 덧셈 노드와 뺄셈 노드는 서로 입력을 공유하지 않으므로 **동시에 발화**한다. 두 결과 토큰이 모두 곱셈 노드에 도착한 뒤에야 곱셈 노드가 발화한다.
- 폰 노이만 방식이라면 프로그램 순서상 덧셈을 끝내야 뺄셈을 시작하는 식으로 강제되지만, 데이터플로우는 두 연산 사이에 데이터 의존이 없다는 것을 그래프 구조 자체가 보장하므로 순서를 지정할 필요조차 없다.

### 정적 vs 동적 데이터플로우 — 3회 반복 루프 worked example
- `for i = 1..3: x[i] = a[i] + b[i]` 라는 루프를 생각한다.
- **정적 데이터플로우**: 덧셈 노드로 이어지는 파이프에 토큰이 1개만 존재할 수 있다. i=1의 결과 토큰이 다음 노드로 완전히 빠져나가기 전에는 i=2의 입력 토큰이 덧셈 노드에 들어갈 수 없다 — 즉 세 번의 반복이 사실상 순차적으로 처리돼 병렬성이 거의 없다.
- **동적 데이터플로우**: i=1의 토큰에는 태그 "1"을, i=2에는 태그 "2"를, i=3에는 태그 "3"을 붙인다. 매칭 유닛은 같은 태그를 가진 토큰끼리만 짝을 짓기 때문에, 세 반복의 덧셈이 동일한 노드(하드웨어)를 시분할로 동시에 통과하면서도 서로 결과가 섞이지 않는다. 이 방식으로 루프 전체를 병렬화할 수 있다.

### 왜 범용 컴퓨터로 상용화되지 못했나 — 매칭 오버헤드
- 동적 데이터플로우의 태깅 방식은 병렬성을 얻는 대가로, 매 순간 "지금 도착한 토큰과 같은 태그·같은 목적지를 가진 짝이 이미 와 있는가"를 수백만 개의 대기 토큰 중에서 찾아야 한다. 이는 연관 메모리(CAM) 검색에 해당하며, 1980년대 MIT 태그드 토큰(Tagged-Token) 머신이나 맨체스터 데이터플로우 머신 실험에서 이 매칭 스토어 탐색 자체가 실제 연산보다 더 큰 하드웨어 비용과 지연을 유발한다는 것이 확인됐다. 결과적으로 처리 요소(PE) 수를 수백 개 이상으로 늘리기 어려웠다.

### 현대적 부활 — Out-of-Order 실행과 공간적 데이터플로우(CGRA/TPU)
- 데이터플로우 사상은 통째로 살아남지 못했지만, 두 가지 형태로 현대 하드웨어에 스며들었다.
- 첫째, 슈퍼스칼라 CPU의 비순차적 실행(Out-of-Order Execution)이다. 명령어 전체를 전역적으로 매칭하는 대신, 코어 내부의 작은 예약 스테이션(수십 개 엔트리 규모)에서만 "입력 레지스터 값이 준비된 명령어 먼저 실행"이라는 데이터플로우식 규칙을 국소적으로 적용한다. 전역 매칭 오버헤드 없이 명령어 수준 병렬성(ILP)을 끌어올린다.
- 둘째, 공간적 데이터플로우(Spatial Dataflow)다. 토큰이 태그를 달고 네트워크를 떠다니며 매칭되는 대신, 연산기(ALU/MAC)를 2차원 격자에 고정 배치하고 데이터가 배선을 따라 물리적으로 흘러가게 만든다. 구글 TPU v1의 시스톨릭 어레이(256×256 MAC 배열)가 대표 사례로, 데이터가 정해진 배선 경로를 따라 이웃 연산기로만 전달되므로 매칭 탐색 자체가 필요 없다.

## 연결 개념
- 비순차적 실행(Out-of-Order Execution) — 데이터플로우의 "데이터 준비되면 실행" 원칙을 CPU 코어 내부의 국소적 예약 스테이션 규모로 축소 적용한 현대적 계승
- DAG와 TensorFlow — 데이터플로우 프로그램의 실행 그래프 구조가 AI 프레임워크의 연산 그래프 컴파일(XLA 등)에 그대로 쓰이는 사례
- CGRA / TPU 시스톨릭 어레이 — 토큰 매칭 오버헤드를 제거하기 위해 데이터가 고정 배선을 따라 흐르게 만든 공간적 데이터플로우의 실현체

# 📝 【답안용】 시험 답안 템플릿

> 목적: 시험장에서 25분에 그대로 쓰는 답안 양식. 

## 핵심 인사이트 (3줄 요약)

> 1. **본질**: 데이터 흐름 컴퓨터(Dataflow Computer)는 명령어의 순차적 흐름을 지시하는 프로그램 카운터(PC) 개념을 폐기하고, 오직 연산에 필요한 피연산자(Operand 데이터/토큰)의 가용성(Availability)만 충족되면 즉각 명령어를 발화(Fire)시키는 데이터 구동형 비(非) 폰 노이만 아키텍처다.
> 2. **가치**: 명령어 간의 인위적 순서 종속성(Control Dependency)을 배제하여 프로그램 내재적 병렬성을 하드웨어 스케일 한계치까지 무한 추출해 내며, 현대 범용 CPU의 슈퍼스칼라 비순차적 실행(Out-of-Order Execution) 설계 사상과 AI 프레임워크(TensorFlow 방향성 그래프)의 근원적 아키텍처 뿌리가 되었다.
> 3. **판단 포인트**: 순차 병목(폰 노이만 갭) 타파라는 철학적 완벽성에도 불구하고, 수백만 개 토큰 간의 짝을 찾는 매칭(Matching Unit)의 하드웨어 스위칭 코스트 오버헤드와 연산 폭주 트래픽으로 범용화에 실패했으나, 최근 NPU/CGRA 공간적 배열 가속기 칩셋 설계로 부활하고 있다.

| 출제 의도 | 반드시 짚을 핵심 | 감점 회피 포인트 |
|:---|:---|:---|

> 요약: 데이터플로우 머신은 "지시서(PC)대로 1번부터 차례대로 요리해!"가 아니라 "재료(데이터 토큰) 2개가 도마(노드) 위에 모이는 즉시 무조건 불을 뿜어라(Fire)!"라는 조건 반사적 초병렬 폭주 기관차 설계다.

## Ⅰ. 개요 및 필요성

- 정의: 명령어의 명시적 순서(Sequence) 통제 없이, 방향성 그래프(DAG) 노드의 모든 입력 피연산자(Token)가 도착하여 유효해지는 순간 해당 연산을 병렬적으로 비동기 발화(Fire)시키는 데이터 구동형 극단적 병렬 컴퓨터 아키텍처
- 배경: 폰 노이만 머신은 CPU가 1클럭당 1개의 명령어를 프로그램 카운터(PC) 순서대로 가져와 실행하는 제어 흐름(Control Flow) 구조이므로, 메모리와 연산기(ALU) 간 1차선 톨게이트 병목(Memory Wall)과 명령어 간 데이터/제어 종속성 대기로 자원 낭비 극심화
- 필요성: 거대한 행렬 연산이나 날씨 시뮬레이션 시 코어 1만 개를 100% 쉬지 않고 가동하기 위해, 인위적인 프로그래밍 줄서기 순서를 파괴하고 조건만 맞으면 동시다발적으로 폭발하는 순수 병렬성 추출 메커니즘 필수

## Ⅱ. 구조 및 구성요소 (제어 흐름 순차 구조 vs 데이터 흐름 매칭-발화 링 구조 도해)

프로그램 카운터가 하나씩 읽는 기존 방식과, 토큰들이 둥둥 떠다니다 태그 짝꿍을 찾아 결합폭발하는 링 아키텍처를 대조한다.

```text
[ 1. 기존 제어 흐름 컴퓨터 (폰 노이만) ─ 순서(PC) 종속 병목 모델 ]
 (명령어 메모리) -> [Program Counter: "다음은 2번 명령어 읽어!"] -> [명령어 2 해독]
 -> [피연산자 메모리 주소 스캔] -> [ALU 계산] -> [결과 저장] (1사이클 1개 순차 노가다)

[ 2. 데이터 흐름 컴퓨터 아키텍처 ─ 비순차 토큰(Token) 발화 매칭 링 구조 ]
 ┌─── (네트워크 링 버스) ───────────────────────────────┐
 │                                                      │
 │  [토큰 매칭 유닛(Matching Unit)]                     │
 │   - 네트워크를 돌아다니는 토큰(Tag+Data) 중          │
 │   - 같은 목적지 노드/태그를 가진 짝꿍 토큰 A, B 탐색 │ [명령어 페치]
 │                                                      │ (매칭된 데이터에
 │               ↓ (짝꿍 결합 쓩!)                      │  해당하는 연산코드 결합)
 │                                                      │
 │  [처리 유닛(Processing Element / ALU 군단)]          │
 │   - 토큰 A, B 와 덧셈명령(+) 도착 즉시 연산 Fire!    │
 │   - 연산 결과(새로운 토큰) 생성 ─────────────────────┘
```

| 데이터플로우 3대 코어 메커니즘 | H/W 아키텍처 논리 제어 역할 | 병렬성 가속 스케일 및 병목 타파 효과 |
|:---|:---|:---|
| **토큰 (Token / Data Packet)** | 데이터 값, 목적지 주소(다음 명령어 노드), 고유 태그(Tag)로 포장된 자율 주행 캡슐 | 메모리 번지 락(Lock) 대기 없이 데이터 스스로 빈 코어(ALU)를 찾아 흘러 들어감 |
| **매칭 유닛 (Matching Unit)** | 파이프라인에서 입력된 두 개 이상의 토큰이 완벽한 연산 짝꿍이 될 때까지 대기하고 결합하는 거대 스위치(CAM) | 명령어 순서(제어 종속성)를 완벽히 찢어발겨 진정한 비동기 초병렬(Massively Parallel) 오버랩 튜닝 달성 |
| **발화 조건 (Firing Rule)** | '노드로 들어오는 모든 입력 토큰이 도착하면 연산을 수행하고 출력 토큰 발사(Fire)'라는 단일 원칙 | 100만 개의 노드가 조건만 맞으면 CPU 통제(PC) 없이 알아서 폭죽처럼 연쇄 폭발 가속 |

> 요약: 데이터플로우는 프로그램 카운터(지휘자)를 죽여버리고 악보를 찢은 거다. 대신 각 악기 연주자(ALU)에게 "네 귀에 바이올린 소리(데이터)랑 첼로 소리가 동시에 들리면 그냥 무조건 네 파트를 연주해 버려!"라고 지시한 미친 무정부 상태의 극강 병렬 오케스트라다.

---

## Ⅲ. 동작원리 및 정적(Static) vs 동적(Dynamic) 데이터플로우 토큰 태깅(Tagging) 한계 극복 대조표

단일 토큰만 허용하여 루프(Loop)를 꽉 막히게 만든 구형(정적)과, 토큰에 색깔 꼬리표를 달아 무한 루프 병렬화 병목을 박살 낸 현대(동적) 링 아키텍처를 대조 증명한다.

| 비교 축 | 🛑 정적(Static) 데이터플로우 구조 | 🟢 동적(Dynamic) 데이터플로우 구조 (태그 토큰) |
|:---|:---|:---|
| **토큰 발화(Fire) 전제 조건** | 1. 모든 입력 토큰이 도착해야 함 <br> **2. 출력 노드가 비어 있어야만 발사 허용 (병목 터짐)** | 1. 모든 입력 토큰 도착 <br> **2. 출력 노드 꽉 차도 꼬리표(Tag)가 다르므로 그냥 쏴버림** |
| **토큰 구조 식별자 (ID)** | 순수 [목적지 노드 번호 + 데이터 값] 단출함 | **[목적지 노드 번호 + 함수호출/루프 꼬리표 Tag + 데이터 값]** 패키징 |
| **반복문(Loop) 처리 및 병렬성 한계**| 1회차 루프(i=1) 연산이 늦어져 덜 빠지면, 2회차 루프(i=2) 토큰이 파이프에 **진입 불가 꽉 막힘 (순차 락)** | i=1 토큰은 빨강 태그, i=2 토큰은 파랑 태그로 구분(색칠). 노드 하나에 루프 데이터 10만 개가 우르르 섞여 돌아가도 병렬 오버랩 처리 폭발 |
| **하드웨어 칩 코스트 오버헤드** | 단순한 ACK 제어선 연결 배선으로 구현 저렴함 | 수백만 개 토큰 중 "태그+목적지"가 같은 짝꿍을 미친 듯이 스캔하는 **초거대 연관 메모리(CAM) 매칭 스위치 부하 폭주 셧다운** |

> 요약: 동적 데이터플로우의 태깅(Tagging) 마술은 병렬 처리에 날개를 달아주었지만, 날아다니는 수백만 개의 토큰 속에서 나랑 짝꿍인 놈을 초고속으로 스캔(연관 메모리 CAM)하는 하드웨어 비용(전기+면적)이 CPU 코어 연산 비용을 아득히 초과하는 기괴한 모순(매칭 병목)에 빠져버렸다.

---

## Ⅳ. 심화 비교: 폰 노이만 제어 흐름(Control) vs 데이터플로우 데이터 흐름 4단 대조표

메모리에 주소로 접근하는 철학과, 데이터가 값어치를 들고 둥둥 떠다니는 철학의 거대한 간극을 대조한다.

| 비교 축 | 💻 폰 노이만 (제어 흐름, Control-Flow) | ⚛️ 데이터플로우 (데이터 구동, Data-Flow) |
|:---|:---|:---|
| **실행의 주도권 (구동 주체)** | **프로그램 카운터 (PC)**가 지시한 명시적 순서(Sequence) | **데이터 가용성**. 재료(피연산자)만 있으면 무조건 즉결 처리 |
| **메모리(변수) 상태와 부작용** | 메모리 번지(Address)에 0,1 값을 덮어쓰고 갱신하는 상태 머신. 병렬 스레드 간 교착/락(Deadlock) 지옥 | 부작용(Side Effect) 없음. 변수 덮어쓰기 불가, 함수형 언어(Functional)처럼 새로운 토큰만 끝없이 생산 릴레이 방출 |
| **병렬성 추출 (어떻게 동시에 돌리는가)**| 프로그래머가 S/W(멀티스레드)로 억지 쪼개서 넣음 (수동) | 그래프 구조 맵핑 후 H/W 단에서 **극한의 병렬성 자동 추출 발현** |
| **치명적 한계(실패 원인)** | 메모리 속도가 CPU를 못 따라감 (**폰 노이만 병목**) | 토큰 짝꿍 찾는 스위치 트래픽이 연산기를 압살함 (**매칭 오버헤드 붕괴**) |

> 요약: 폰 노이만 아키텍처는 "순서 강박증" 때문에 효율이 떨어졌고, 데이터플로우는 "순서 무시 자유방임"을 주다 보니 파편화된 데이터(토큰) 조각들을 교통정리(매칭 라우팅) 하느라 정작 계산은 뒷전이 되어버려 범용 패권 싸움에서 자멸했다.

## Ⅴ. 제약 사항 및 실패한 철학의 위대한 부활 (Out-of-Order CPU 및 AI 텐서 공간 가속기 CGRA)

독립적인 컴퓨터 머신으로서는 망했지만, 이 무서운 병렬 사상은 현대 인텔 x86 코어 내부와 최신 AI 칩(NPU/TPU)의 공간적 배열 아키텍처 안으로 완벽히 스며들어 세계를 지배하고 있다.

| 리스크 (한계) | 발생 원인 (범용 H/W 스위치 스케일링 폭발) | 현대 아키텍처 이종(Heterogeneous) 사상 융합 계승 (부활) | 극복 원리 및 효과 |
|:---|:---|:---|:---|
| 끔찍한 연관 메모리(CAM) 매칭 오버헤드 데스록 | 100만 개의 변수(토큰)가 날아다닐 때, 1번 토큰의 짝꿍을 찾기 위해 매번 100만 번의 하드웨어 스캔 서치를 1클럭 내에 강행해야 함. 칩이 타버림 | **슈퍼스칼라 비순차적 명령어 실행 (Out-of-Order Execution, OoOE) 내재화** | 컴퓨터 전체를 데이터플로우로 만들지 않음! 폰 노이만 CPU(x86) 구조는 유지하되, **코어 내부 깊숙한 예약 스테이션(Reservation Station)** 단 한 곳에서만 들어온 명령어 100개를 몰래 쪼개서, '데이터 준비된 놈 먼저 처리(데이터플로우 사상)'하는 마이크로아키텍처 꼼수 튜닝으로 현대 CPU의 속도를 3배 뻥튀기시킴 |
| 프로그램 코드 맵핑 및 순차 직렬 루틴 처리 비효율 | 병렬화 할 게 널려있는 과학 계산(배열)엔 최강이지만, A 다음에 B를 해야만 하는 OS 커널 로직이나 조건(IF) 직렬 종속 분기에서는 토큰 낭비와 대기 큐 폭발 패닉 | **공간적 데이터플로우 (Spatial Dataflow / CGRA / AI NPU 가속기) 진화** | 날아다니는 토큰 방식(시간 매칭)을 버림. 대신 반도체 칩 위에 ALU(연산기) 1만 개를 바둑판(2D)으로 고정해 깔아두고, 데이터가 1번 ALU 거치면 구리 배선을 타고 자연스럽게 2번, 3번 ALU로 폭포수처럼 쏟아져 내리는 파이프라인 공간 라우팅(TPU 시스톨릭 어레이) 맵핑 구축. 매칭 오버헤드 없이 전성비 극강 폭발 AI 칩(딥러닝 행렬 곱 가속기) 점령 |

> 요약: 데이터 흐름 사상은 이단아 취급을 받았지만, 결국 범용 CPU 코어 안에 몰래 잠입해 '비순차 실행(OoO)'이라는 이름으로 살아남았고, 40년 뒤 수천억 개 파라미터를 행렬로 쏟아부어 곱하는 AI 딥러닝 NPU 가속기 구조(공간적 데이터플로우)의 진정한 지배자로 부활했다.

## Ⅵ. 실무 적용 및 결론

**적용 방안 3개:**
1. AI 프레임워크 방향성 비순환 그래프(DAG) 기반 TensorFlow 분산 병렬화 오프로딩 아키텍처 구축: 파이썬으로 작성된 AI 딥러닝 모델 코드를 폰 노이만식 순차 실행(Eager Execution)으로 처리하면 GPU 활용률 병목이 터지므로, 사전에 노드(연산)와 엣지(텐서 데이터 흐름)로 이어진 거대한 DAG 그래프 플랜으로 컴파일(XLA)한 뒤, 데이터 준비 상태에 따라 수천 개의 GPU 쿠다(CUDA) 코어에 비동기 비순차 발화(Fire)시켜 학습 전성비 효율 극대화
2. 멀티코어 환경의 함수형 프로그래밍(Functional Programming) 동시성 불변(Immutable) 상태 튜닝 실무: 스칼라(Scala), 하스켈(Haskell), 코틀린 코루틴(Coroutine) 등 소프트웨어 레벨에서 데이터플로우 아키텍처 철학을 차용. 변수 값을 덮어쓰는 상태 변이(Side Effect)를 금지하고 입력 인자가 불변(Immutable)의 토큰처럼 함수 노드로 흘러가게 강제함으로써, 100개 스레드가 병렬로 락(Mutex Lock) 없이 동시 구동되는 고가용 백엔드 파이프라인 구축
3. VLIW 및 슈퍼스칼라 CPU 코어 컴파일러 비순차적(OoOE) 파이프라인 레지스터 리네이밍 최적화: C/C++ 시스템 프로그래밍 시, 거짓 데이터 종속성(WAW, WAR 병목)으로 인해 내부 미니 데이터플로우 링(예약 스테이션)이 발화하지 못하고 정지(Stall)하는 것을 막기 위해, GCC/LLVM 컴파일러 플래그 튜닝 및 루프 언롤링(Loop Unrolling) 기법으로 피연산자 공급 딜레이를 은닉(Hide)하여 IPC(클럭당 명령어 처리수) 극한 도출

**결론 (2줄):**
- 기술사 판단: 데이터 흐름 컴퓨터(Dataflow)는 프로그램 카운터(PC)의 제어 지배를 부수고 피연산자 가용성 기반 매칭 발화(Fire)라는 혁명적 비동기 병렬성을 창조했으나, 동적 태깅 연관 메모리(CAM) 라우팅 트래픽 오버헤드 붕괴로 인해 독자적 범용 아키텍처로는 소멸한 비운의 천재다.
- 향후 방향: 그러나 그 극강의 병렬 데이터 파이프라이닝 DNA는 결코 죽지 않고, 범용 CPU의 슈퍼스칼라 비순차적 실행(OoOE) 내부 코어 튜닝과, 최신 거대 AI 행렬(LLM)을 분쇄하는 공간적 배열(CGRA/TPU 시스톨릭 어레이) 맞춤형 가속기 설계 철학으로 화려하게 부활하여 포스트 폰 노이만 시대를 주도하고 있다.
