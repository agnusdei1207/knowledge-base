## 미리 알고가기

- 제어 흐름: 프로그램 카운터가 명령 순서를 결정하는 실행 방식임
- 데이터 흐름: 필요한 입력 데이터가 준비된 연산부터 실행하는 방식임
- 토큰: 연산에 필요한 데이터 값과 준비 상태를 표현하는 단위임
- 의존성 그래프: 연산 노드와 데이터 의존 간선으로 프로그램을 표현한 구조임

## Ⅰ. 개요

- **정의**: 데이터 흐름 컴퓨터는 프로그램 순서가 아니라 연산 입력 데이터의 준비 여부를 기준으로 실행 가능한 노드를 병렬 수행하는 컴퓨터 구조임. 명령어 수준·태스크 수준 병렬성을 하드웨어나 런타임이 자동 노출하기 위해 사용함.
- **배경/필요성**: 순차 제어 흐름은 명령 순서가 병렬 실행 가능성을 가려 고성능 연산에서 자원 활용률을 낮출 수 있음. 데이터 의존성만 만족하면 독립 연산을 동시에 실행해 병렬성을 높일 수 있음.
- **비유**: 조립 순서표를 한 줄로 읽는 대신, 필요한 부품이 도착한 작업대부터 바로 조립을 시작하는 공장과 같음.

| 출제 의도 | 반드시 짚을 핵심 | 감점 회피 포인트 |
|:---|:---|:---|
| 비폰노이만 병렬 구조 이해 | 데이터 의존성, 토큰, 그래프 실행, 병렬성 | 단순 파이프라인과 혼동 |

> 요약: 데이터 흐름 컴퓨터는 명령 순서보다 데이터 준비 상태를 실행 기준으로 삼아 병렬성을 확보함.

## Ⅱ. 특징/비교

| 판단 기준 | 제어 흐름 컴퓨터 | 데이터 흐름 컴퓨터 |
|:---|:---|:---|
| 실행 기준 | 프로그램 카운터와 분기 명령 | 입력 토큰 도착과 의존성 만족 |
| 병렬성 추출 | 컴파일러와 OoO(Out-of-Order) 하드웨어가 제한적으로 추출 | 그래프상 독립 노드를 자연스럽게 병렬 실행 |
| 상태 관리 | 메모리와 레지스터의 순서 상태가 중요함 | 토큰과 노드 활성화 상태가 중요함 |
| 적용 영역 | 범용 순차 프로그램에 적합 | 스트림, 그래프, AI(Artificial Intelligence), 데이터 병렬 연산에 적합 |

> 요약: 데이터 흐름 방식은 제어 흐름의 순서 제약을 줄이고 데이터 의존성 기반 병렬 실행을 선택함.

- **적용 조건**: 연산 의존 그래프가 명확하고 독립 노드가 충분히 많아야 함
- **선택 지표**: ready node 수, token overhead, execution unit utilization을 함께 봐야 함
- **운영 관점**: 메모리 부작용과 통신 비용이 병렬성 이득을 넘지 않아야 함

## Ⅲ. 구성요소

```text
+-----------+      +-------------+      +-------------+
| Data token| ---> | Ready queue | ---> | Exec node   |
+-----------+      +-------------+      +-------------+
       |                   |                    |
       v                   v                    v
+-----------+      +-------------+      +-------------+
| Graph map |      | Scheduler   |      | Output token|
+-----------+      +-------------+      +-------------+
```

| 구성요소 | 설명 | 비유 |
|:---|:---|:---|
| 데이터 흐름 그래프 | 연산을 노드, 데이터 의존성을 간선으로 표현함 | 작업 공정도 |
| 토큰 저장소 | 값과 도착 여부를 저장해 연산 가능 상태를 판단함 | 부품 보관함 |
| 스케줄러 | 입력이 모두 준비된 노드를 실행 큐에 배치함 | 작업반장 |
| 실행 노드 | 산술, 메모리, 통신 연산을 수행하고 결과 토큰을 생성함 | 작업대 |

> 요약: 데이터 흐름 구조는 그래프, 토큰, 스케줄러, 실행 노드가 결합되어 준비된 연산을 병렬 실행함.

## Ⅳ. 절차

```text
+----------+      +----------+      +----------+      +----------+
| Graph    | ---> | Token    | ---> | Execute  | ---> | Propagate|
+----------+      +----------+      +----------+      +----------+
```

1. **그래프 생성** — 프로그램을 연산 노드와 데이터 의존성 간선으로 변환함
2. **토큰 수집** — 입력 데이터가 노드에 도착하면 준비 상태를 갱신함
3. **노드 실행** — 모든 입력이 준비된 노드를 실행 유닛에 배정해 계산함
4. **결과 전파** — 출력 토큰을 후속 노드로 보내 다음 병렬 실행을 유발함

> 요약: 데이터 흐름 실행은 그래프에서 토큰이 이동하며 가능한 연산을 계속 활성화하는 과정임.

## Ⅴ. 문제점

- **P1 토큰 관리 오버헤드**: 값 이동과 준비 상태 추적 비용이 커지면 병렬성 이득을 상쇄함
- **P2 메모리 부작용 처리**: 공유 메모리 읽기·쓰기 순서와 aliasing이 있으면 순수 데이터 의존성만으로 실행 순서를 정하기 어려움
- **P3 불균형 병렬성**: 그래프의 특정 노드나 통신 간선에 부하가 몰리면 실행 유닛 활용률이 낮아짐

> 요약: 데이터 흐름 구조는 병렬성은 높지만 토큰, 메모리 순서, 그래프 균형 관리가 어렵음.

## Ⅵ. 개선방안

- **P1 대응**: coarse-grained dataflow, 토큰 압축, 로컬 버퍼링으로 관리 단위를 키움 (확인: token overhead ratio)
- **P2 대응**: SSA(Static Single Assignment), memory dependence analysis, transactional memory 또는 명시적 동기화로 부작용 순서를 제한함 (확인: memory conflict rate)
- **P3 대응**: 그래프 파티셔닝, work stealing, 통신 locality 최적화로 부하를 분산함 (확인: execution unit utilization)

> 요약: 데이터 흐름의 실용성은 병렬성 추출보다 토큰·메모리·스케줄링 비용을 낮추는 데 달려 있음.

## Ⅶ. 전망

- **발전 방향**: AI 가속기, 스트림 처리, 데이터플로우 프로그래밍 모델, near-data processing과 결합해 특화 아키텍처로 확대됨
- **기술사적 판단**: 범용 CPU(Central Processing Unit) 대체보다 반복 데이터 의존 그래프가 명확한 워크로드에서 선택하는 것이 타당함
- **기술사 제언**: 도입 시 알고리즘의 의존성 그래프, 데이터 재사용성, 메모리 부작용을 먼저 분석해 적용 범위를 정해야 함
