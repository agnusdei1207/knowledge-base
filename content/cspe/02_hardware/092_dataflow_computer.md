# 📖 【암기용】 개념 완전 이해

> 목적: 데이터 흐름 컴퓨터가 왜 "프로그램 카운터 없이" 동작하는지 처음 봐도 이해하게 만든다. 시험 답안 양식이 아니라, 이해를 위한 친절한 설명이다.

## 한눈에
- **개요**: 명령어 순서(제어 흐름)가 아니라 데이터(토큰)가 준비되는 순간 연산이 실행되는 컴퓨팅 모델
- **왜 필요한가**: 폰 노이만 구조는 프로그램 카운터(PC)가 다음 명령을 순차 지정하므로 독립적인 연산도 순서를 강제받아 병렬성이 제한된다. 데이터 흐름 모델은 이 제약을 없애 자연스러운 병렬 실행을 가능하게 한다.
- **핵심 직관**: 요리 재료(데이터 토큰)가 도착한 순서대로 해당 조리 단계(연산 노드)가 자동으로 시작되는 주방과 같다.

## 깊이 이해
- **배경·문제의식**: 폰 노이만 컴퓨터는 PC가 다음 명령 주소를 순차 지정하는 제어 흐름(control-flow) 모델이라 명령어 간 실제 의존성이 없어도 순서대로 인출·실행해야 한다.
- **작동 원리**: 데이터 흐름 컴퓨터는 프로그램을 방향성 그래프(dataflow graph)로 표현하며, 노드는 연산, 에지는 데이터 토큰의 이동 경로다.
- **작동 원리 보충**: 발화 규칙(firing rule)에 따라 한 노드는 입력 에지에 필요한 토큰이 모두 도착했을 때만 실행되고, 실행 후 결과 토큰을 출력 에지로 내보낸다.
- **작동 원리 보충2**: 발화 조건만 충족하면 프로그램 순서와 무관하게 여러 노드가 동시에 발화할 수 있어 명령어 수준 병렬성이 하드웨어 차원에서 자연스럽게 드러난다.
- **비유**: 조립 라인이 아니라 여러 작업대가 동시에 놓인 주방으로, 재료가 도착한 작업대부터 순서 상관없이 조리가 시작된다.
- **구체 예시**: `C = A + B`와 `E = D * F`가 서로 독립이면 A,B 토큰과 D,F 토큰이 각각 준비되는 즉시 두 덧셈·곱셈 노드가 동시에 발화하며, PC 기반 구조처럼 한 줄씩 순서를 기다리지 않는다.
- **흔한 오해·주의점**: 데이터 흐름 컴퓨터는 완전히 새로운 프로그래밍 언어가 필요한 것은 아니며, 컴파일러가 소스 코드를 dataflow graph로 변환하는 방식이 일반적이다.
- **흔한 오해·주의점 보충**: 정적(static) 데이터 흐름 모델은 한 에지에 토큰이 하나만 존재하도록 제한해 반복문 재진입(reentrancy)이 어렵고, 이를 해결하려면 토큰에 태그(tag)를 붙이는 동적(dynamic tagged-token) 모델이 필요하다.

## 연결 개념
- 명령어 수준 병렬성 ILP — 데이터 흐름 모델이 하드웨어 차원에서 노리는 목표
- CGRA·공간 아키텍처(Coarse-Grained Reconfigurable Array) — 현대 AI 가속기에서의 데이터 흐름 개념 재등장
- 폰 노이만 vs 하버드 아키텍처 — 제어 흐름 모델과의 대조 대상

# 📝 【답안용】 시험 답안 템플릿

> 목적: 시험장에서 25분에 그대로 쓰는 답안 양식. 작성방식(추상표현 금지·수치·도식·문제유형 전환)을 엄격히 지킨다.
> 핵심: 데이터 흐름 컴퓨터를 역사적 개념으로만 나열하지 않고, 제어 흐름 대비 구조적 차이와 현대 AI 가속기 재등장 배경까지 연결한다.

## 핵심 인사이트 (3줄 요약)

> 1. **본질**: 데이터 흐름 컴퓨터(Dataflow Computer)는 프로그램 카운터 기반 순차 실행 대신 데이터 토큰의 도착(발화 규칙)으로 연산 실행 시점을 결정하는 컴퓨팅 모델이다.
> 2. **가치**: 명령어 간 실제 데이터 의존성만 실행 순서를 제약하므로, 독립적인 연산은 하드웨어가 자동으로 병렬 발화시킨다.
> 3. **판단 포인트**: 정적 모델은 구조가 단순하지만 반복문 재진입이 어렵고, 동적(tagged-token) 모델은 재진입을 지원하는 대신 토큰 매칭 하드웨어 복잡도가 증가한다.

## 출제 의도 및 답안 포인트

| 출제 의도 | 반드시 짚을 핵심 | 감점 회피 포인트 |
|:---|:---|:---|
| 제어 흐름과의 구조적 차이 이해 확인 | PC 기반 순차 실행 vs 토큰 발화 기반 실행 | 단순히 "병렬 처리가 빠르다"는 추상 서술 |
| 정적·동적 모델 차이 이해 확인 | 단일 토큰 제약과 태그드 토큰 방식의 재진입 지원 | 정적·동적 구분 없이 데이터 흐름을 하나로 뭉뚱그림 |
| 현대적 재조명 배경 이해 확인 | CGRA·AI 가속기에서의 공간적 데이터 흐름 재등장 | 데이터 흐름을 과거 실패한 기술로만 서술 |

> 요약: 이 문제는 역사적 정의 나열이 아니라 제어 흐름과의 구조적 차이, 정적·동적 모델의 트레이드오프, 현대 재조명 맥락을 함께 요구한다.

## Ⅰ. 개요 및 필요성

- 개요: 프로그램 카운터 대신 데이터 토큰 도착으로 연산 실행 시점을 결정하는 비폰노이만 컴퓨팅 모델
- 배경: 폰 노이만 구조는 PC가 명령어 순서를 강제해, 독립적인 연산도 순차적으로만 실행되는 한계가 있음
- 필요성: 명령어 수준 병렬성을 하드웨어 차원에서 자연스럽게 끌어내려면 실행 순서를 데이터 의존성에만 맡기는 모델이 필요함

---

## Ⅱ. 구조 및 구성요소

```text
Dataflow Graph
  Source Node(입력 토큰 생성)
  -> Operation Node(연산자, 입력 토큰 전부 도착 시 발화)
  -> Edge(토큰 이동 경로)
  -> Sink Node(결과 출력)
Token Matching Unit -> 발화 조건(firing rule) 판정 -> 병렬 발화
```

| 구성요소 | 역할 | 정적/동적 차이 |
|:---|:---|:---|
| Operation Node | 입력 토큰이 모두 도착하면 연산 실행 | 공통 |
| Edge(Arc) | 토큰이 이동하는 경로 | 정적: 에지당 토큰 1개, 동적: 다중 토큰 허용 |
| Token | 실행에 필요한 데이터 값 | 동적 모델은 토큰에 태그(호출 컨텍스트) 부착 |
| Token Matching Unit | 발화 조건 판정 및 매칭 | 동적 모델에서 태그 매칭 오버헤드 발생 |

> 요약: 데이터 흐름 그래프는 노드·에지·토큰으로 구성되며, 정적 모델은 단순하지만 재진입이 제한되고 동적 모델은 태그 매칭으로 재진입을 지원하는 대신 복잡도가 증가한다.

---

## Ⅲ. 동작원리 및 흐름도

```text
프로그램 -> 컴파일러가 Dataflow Graph로 변환
  -> 토큰 생성(입력 데이터 준비)
  -> Token Matching Unit이 발화 조건 확인
  -> 조건 충족 노드 병렬 발화(실행)
  -> 결과 토큰을 후속 에지로 전달 -> 반복
```

| 단계 | 처리 내용 | 검증 기준 |
|:---:|:---|:---|
| 1 | 소스 코드를 dataflow graph로 컴파일 | 노드·에지 의존성 정확성 |
| 2 | 초기 입력 토큰 생성 및 배치 | 토큰 개수와 에지 매핑 일치 |
| 3 | 발화 조건(모든 입력 토큰 도착) 확인 | firing rule 판정 정확성 |
| 4 | 조건 충족 노드 동시 발화 | 병렬 발화 노드 수, 처리량 |
| 5 | 결과 토큰 전달 및 재귀·반복 처리 | 동적 모델의 태그 매칭 정확성 |

> 요약: 데이터 흐름 실행은 그래프 변환 후 토큰 도착을 감지해 조건을 만족한 노드를 동시에 발화시키는 방식으로 진행된다.

## Ⅳ. 특징

| 구분 | 정적 데이터 흐름(Static Dataflow) | 동적 데이터 흐름(Dynamic/Tagged-Token) | 수치·표준 포인트 |
|:---|:---|:---|:---|
| 토큰 제약 | 에지당 토큰 1개만 허용 | 에지당 다중 토큰(태그로 구분) 허용 | 반복문 재진입은 동적 모델에서만 지원 |
| 하드웨어 복잡도 | 상대적으로 단순 | 태그 매칭 유닛 필요로 복잡도 증가 | 매칭 실패 시 토큰 저장 버퍼 필요 |
| 대표 연구 사례 | MIT Static Dataflow Machine | MIT Tagged-Token Dataflow, Manchester Dataflow Machine | 1970~1980년대 학계 연구 프로토타입 |
| 현대적 응용 | CGRA(Coarse-Grained Reconfigurable Array) | 공간적(spatial) AI 가속기의 코어 간 데이터 전달 방식 | 명령어 수준이 아닌 연산 그래프 수준 스케줄링 |

> 요약: 정적 모델은 구조가 단순하지만 반복 재진입이 어렵고, 동적 모델은 태그 매칭으로 이를 해결하는 대신 하드웨어 복잡도가 커진다.

## Ⅴ. 심화 비교 및 적용 판단

| 비교 축 | 폰 노이만(제어 흐름) | 데이터 흐름 컴퓨터 | 선택 기준 |
|:---|:---|:---|:---|
| 실행 순서 결정 | 프로그램 카운터(PC) 순차 지정 | 데이터 토큰 도착(firing rule) | 독립 연산 비중이 높은 워크로드는 데이터 흐름이 유리 |
| 병렬성 확보 방식 | 슈퍼스칼라·OoO 등 하드웨어가 순차 코드에서 병렬성 추출 | 그래프 구조 자체가 병렬성 표현 | 병렬성 추출 부담을 컴파일러(그래프 생성)로 이전 가능한지 확인 |
| 프로그래밍·디버깅 | 순차적 사고에 익숙, 디버깅 용이 | 그래프·토큰 흐름 추적 필요, 디버깅 난이도 증가 | 개발 생산성과 병렬성 이득의 트레이드오프로 판단 |

> 요약: 독립 연산이 많고 병렬성이 핵심인 워크로드는 데이터 흐름 모델이, 순차적 로직과 디버깅 용이성이 중요하면 폰 노이만 모델이 유리하다.

| 리스크 | 원인 | 대응 방안 | 확인 지표 |
|:---|:---|:---|:---|
| 토큰 매칭 오버헤드 | 동적 모델의 태그 매칭 하드웨어 비용 | 매칭 유닛 캐시화, 태그 재사용 최적화 | 토큰 매칭 지연 사이클 |
| 디버깅 난이도 | 순차 실행 흐름이 없어 추적이 어려움 | 그래프 시각화 도구, 토큰 트레이스 로깅 | 결함 재현 소요 시간 |
| 상용화 한계 | 범용 소프트웨어 생태계·컴파일러 부재 | CGRA·AI 가속기 등 특정 도메인에 한정 적용 | 도메인 특화 가속기 채택률 |

> 요약: 데이터 흐름 컴퓨터의 리스크는 매칭 오버헤드와 생태계 부재이며, 범용보다 도메인 특화 가속기로 적용 범위를 한정해 통제한다.

| 점검 항목 | 목표 기준 | 측정 방법 |
|:---|:---|:---|
| 병렬 발화율 | 동시 발화 가능 노드 비율 | 그래프 시뮬레이션, 스케줄 분석 |
| 토큰 매칭 지연 | 매칭 유닛 처리 지연 최소화 | 하드웨어 시뮬레이터 사이클 측정 |
| 도메인 적합성 | CGRA·AI 가속기 워크로드 처리량 향상 | 벤치마크 대비 처리량·전력 효율 |

> 요약: 데이터 흐름 모델의 도입 효과는 병렬 발화율, 토큰 매칭 지연, 도메인 특화 워크로드 처리량으로 판단한다.

## Ⅵ. 실무 적용 및 결론

**적용 방안 3개:**
1. 반복문 재진입이 필요한 워크로드는 태그드 토큰 기반 동적 데이터 흐름 모델을 적용하고 매칭 유닛 지연을 별도로 측정함
2. AI 가속기 설계 시 연산 그래프를 공간적으로 배치하는 CGRA·spatial architecture 개념을 도입해 데이터 흐름의 병렬 발화 이점을 활용함
3. 범용 소프트웨어 생태계 부재 한계를 인정하고, 도메인 특화 가속기 영역에 한정해 데이터 흐름 원리를 적용함

**결론 (2줄):**
- 기술사 판단: 데이터 흐름 컴퓨터는 범용 CPU 대체가 아니라, 독립 연산 병렬성이 큰 도메인 특화 가속기 설계 원리로 재조명해야 함
- 향후 방향: AI 가속기·CGRA에서 연산 그래프 기반 스케줄링이 확산되며 데이터 흐름 개념이 소프트웨어(TensorFlow 계산 그래프)와 하드웨어 양쪽에서 재사용되는 추세임
