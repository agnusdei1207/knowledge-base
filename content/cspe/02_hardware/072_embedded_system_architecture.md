# 📖 【암기용】 개념 완전 이해

> 목적: 임베디드 시스템을 처음 봐도 왜 일반 PC와 다르게 설계하는지, 어떤 요소로 구성되는지 이해하게 만든다. 시험 답안 양식이 아니라, 이해를 위한 친절한 설명이다.

## 한눈에
- **개요**: 특정 기능 수행을 위해 기계·전자 장치에 내장되는, 하드웨어·소프트웨어가 설계 시점에 고정된 전용 컴퓨터 시스템
- **왜 필요한가**: 세탁기, 자동차 ECU, IoT 센서는 범용 OS의 자원 소비와 불확실한 응답 시간을 감당할 수 없다. 임베디드 시스템은 메모리·전력·비용 제약 속에서 실시간성을 보장한다.
- **핵심 직관**: 만능 공구함(PC)과 달리, 특정 나사 하나만 정확히 빠르게 조이도록 만든 전용 드라이버가 임베디드 시스템이다.

## 깊이 이해
- **배경·문제의식**: 범용 컴퓨터는 다양한 응용을 실행하려고 여유 자원과 범용 OS 스케줄링을 사용한다.
- 제어 대상 장비는 정해진 입력에 정해진 시간 안에 반응해야 하고, 배터리·크기·원가 제약이 있어 범용 구조를 그대로 쓸 수 없다.
- 이 문제의식에서 CPU·메모리·I/O·소프트웨어를 하나의 목적에 맞춰 설계 시점에 고정하는 임베디드 구조가 등장했다.
- **작동 원리**: MCU(Microcontroller Unit)는 CPU 코어, RAM, Flash/ROM, GPIO, 타이머, 통신 인터페이스를 단일 칩에 통합해 외부 칩 없이 동작한다.
- Microprocessor(MPU)는 CPU 코어만 제공하고 메모리·I/O 칩을 외부에 별도로 연결해야 하므로 보드 설계 자유도는 높지만 부품 수와 비용이 늘어난다.
- Flash/ROM에는 부팅 시 실행되는 firmware를 저장하고, RAM은 실행 중 변수와 스택을 저장하며, EEPROM은 전원 차단 후에도 유지해야 하는 설정값을 저장한다.
- 인터럽트 컨트롤러는 센서 입력, 타이머 만료, 통신 수신 같은 이벤트 발생 시 CPU의 현재 흐름을 중단시키고 등록된 인터럽트 서비스 루틴(ISR)을 실행한다.
- 자원이 매우 제한된 시스템은 OS 없이 bare-metal firmware로 메인 루프에서 직접 폴링·인터럽트를 처리하고, 여러 태스크의 우선순위·타이밍 보장이 필요하면 RTOS(Real-Time OS)가 태스크 스케줄링을 담당한다.
- 개발은 자원이 풍부한 host PC에서 target 아키텍처용 바이너리를 만드는 cross-compilation으로 진행하고, 만든 바이너리를 JTAG 등 디버그 인터페이스로 target 보드에 올려 board bring-up과 디버깅을 수행한다.
- **비유**: 범용 OS가 여러 손님의 다양한 요청을 순서대로 받는 종합병원이라면, 임베디드 시스템은 정해진 응급 처치 하나만 정해진 시간 안에 수행하도록 훈련된 응급 구조대다.
- **구체 예시**: 자동차 ABS(Anti-lock Braking System) ECU는 바퀴 속도 센서 인터럽트를 수신하면 수 밀리초 안에 제동압을 재계산해 솔레노이드 밸브를 제어하는 hard real-time 임베디드 시스템이다.
- 가정용 IoT 온습도 센서는 저전력 MCU에서 수 초 주기로 센서값을 읽어 UART나 저전력 무선으로 전송하는 soft real-time에 가까운 임베디드 시스템이다.
- **흔한 오해·주의점**: 임베디드 시스템이라고 해서 항상 OS가 없는 것은 아니며, RTOS나 경량 Linux(Embedded Linux)를 탑재하는 경우도 많다.
- MCU와 MPU를 혼동하기 쉬운데, MCU는 메모리·I/O까지 한 칩에 통합한 것이고 MPU는 CPU 코어 자체만 가리킨다는 차이를 구분해야 한다.
- 실시간성은 "빠르다"가 아니라 "정해진 데드라인을 항상 지킨다"는 뜻이므로, 평균 응답 속도가 빨라도 데드라인을 한 번이라도 놓치면 hard real-time 요구를 위반한 것이다.

## 연결 개념
- RTOS(Real-Time OS) — 태스크 스케줄링과 데드라인 보장 메커니즘
- JTAG — 임베디드 보드 디버깅·펌웨어 다운로드 인터페이스(별도 077 참조)
- Cross-Compilation Toolchain — host에서 target 바이너리를 생성하는 개발 흐름

## Ⅰ. 개요 및 필요성

- 개요: 특정 기능 수행을 위해 하드웨어·소프트웨어가 설계 시점에 고정된 전용 컴퓨터 시스템
- 배경: 범용 OS와 여유 자원 기반 구조는 실시간 응답과 저전력·저비용 제약을 동시에 만족하지 못함
- 필요성: 자동차 ECU, 산업 제어기, IoT 센서는 제한된 메모리·전력 안에서 정해진 데드라인을 지키는 전용 구조가 필요함

---

## Ⅱ. 구조 및 구성요소

```text
CPU/MCU -> Memory(Flash/ROM, RAM, EEPROM)
  -> I/O Peripheral(GPIO, ADC/DAC, Timer, UART/SPI/I2C/CAN)
  -> Interrupt Controller -> ISR 처리
  -> RTOS/Bare-metal Firmware -> 제어 대상 장비
```

| 구성요소 | 역할 | 특이사항 |
|:---|:---|:---|
| CPU/MCU | 명령어 실행, 연산 처리 | MCU는 메모리·I/O를 단일 칩에 통합 |
| Memory | Flash/ROM은 firmware 저장, RAM은 실행 변수 저장 | EEPROM은 전원 차단 후 설정값 유지 |
| I/O Peripheral | 센서·액추에이터·통신 신호 입출력 | GPIO, ADC/DAC, UART/SPI/I2C/CAN |
| Interrupt Controller | 이벤트 발생 시 CPU 흐름 중단 후 ISR 실행 | 우선순위 기반 인터럽트 처리 |
| RTOS/Firmware | 태스크 스케줄링 또는 메인 루프 처리 | 데드라인 보장 여부로 선택 |

> 요약: 임베디드 시스템은 MCU 중심으로 메모리 계층, I/O, 인터럽트 처리, 펌웨어를 하나의 목적에 맞춰 구성한다.

---

## Ⅲ. 동작원리 및 흐름도

```text
전원 인가 -> Bootloader 실행 -> Firmware 로드(Flash->RAM)
  -> 초기화(클럭, I/O, 인터럽트 벡터)
  -> 메인 루프/RTOS 스케줄링 -> 인터럽트 발생 시 ISR 처리
  -> 제어 신호 출력
```

| 단계 | 처리 내용 | 검증 기준 |
|:---:|:---|:---|
| 1 | Bootloader가 Flash의 firmware를 RAM으로 로드 | 부팅 시간, 무결성 검증 |
| 2 | 클럭·I/O·인터럽트 벡터 초기화 | 초기화 실패 시 fallback 여부 |
| 3 | 메인 루프 또는 RTOS 태스크 스케줄링 실행 | 태스크 우선순위, 데드라인 준수 |
| 4 | 인터럽트 발생 시 ISR 실행 후 제어 신호 출력 | 인터럽트 응답 시간(latency) |

> 요약: 임베디드 시스템은 부팅과 초기화 후 메인 루프 또는 RTOS 스케줄링이 인터럽트에 반응해 제어 신호를 출력하는 흐름으로 동작한다.

---

## Ⅳ. 특징

| 구분 | 내용 | 판단 포인트 |
|:---|:---|:---|
| 장점 | 특정 기능에 최적화되어 메모리·전력·비용 효율이 높음 | 자원 제약 대비 목표 기능 충족 여부 |
| 한계 | 설계 시점에 하드웨어·소프트웨어가 고정되어 기능 확장이 제한됨 | 펌웨어 업데이트(OTA) 지원 여부 |
| 비교 포인트 | 범용 컴퓨터는 여유 자원과 범용 OS로 다목적 처리, 임베디드는 고정 자원으로 단일 목적 실시간 처리 | 실시간성 요구 수준(hard/soft) |

> 요약: 임베디드 시스템은 자원 효율과 실시간성에서 강점이 있으나 설계 후 변경 유연성은 범용 시스템보다 낮다.

## Ⅴ. 심화 비교 및 적용 판단

| 비교 축 | 범용 컴퓨터(OS 기반) | 임베디드 시스템 | 선택 기준 |
|:---|:---|:---|:---|
| 구조 | CPU+외부 메모리/I/O 칩, 범용 OS | MCU 단일 칩 통합 또는 MPU+전용 firmware | 기능 고정 여부와 확장성 요구 |
| 비용/성능 | 자원 여유, 다목적 성능 | 저전력·저비용, 목적 성능 최적화 | 배터리·원가·크기 제약 수준 |
| 운영/위험 | 범용 OS 패치, 다양한 장애 시나리오 | firmware 고정, OTA 미지원 시 현장 교체 필요 | 데드라인 미준수 시 안전 영향도 |

> 요약: 다목적 유연성이 필요하면 범용 OS 기반, 저전력·실시간·저비용이 필요하면 임베디드 구조를 선택한다.

| 리스크 | 원인 | 대응 방안 | 확인 지표 |
|:---|:---|:---|:---|
| 데드라인 미준수 | 인터럽트 우선순위 설계 오류, RTOS 미적용 | RTOS 도입, worst-case 응답시간 분석 | 인터럽트 latency, 데드라인 위반 횟수 |
| 메모리 오버플로우 | 제한된 RAM/Flash 초과 사용 | 정적 메모리 분석, 코드 최적화 | RAM/Flash 사용률 |
| 펌웨어 결함 고착 | 현장 배포 후 업데이트 경로 부재 | OTA 업데이트 체계, JTAG 재프로그래밍 절차 마련 | 업데이트 성공률, 롤백 가능 여부 |

> 요약: 임베디드 시스템 운영은 인터럽트 응답시간, 메모리 사용률, 펌웨어 업데이트 체계로 통제한다.

| 점검 항목 | 목표 기준 | 측정 방법 |
|:---|:---|:---|
| 실시간성 | 인터럽트 응답 latency 목표치 이내 | 오실로스코프, RTOS 트레이스 |
| 자원 사용 | RAM/Flash 사용률 80% 이하 | 링커 맵 파일, 정적 분석 |
| 신뢰성 | 장시간 구동 시 오동작률 목표치 이하 | HALT/HASS 테스트, 필드 로그 |

> 요약: 도입 후 성공 여부는 인터럽트 응답시간, 자원 사용률, 장시간 구동 신뢰성 지표로 판단한다.

## Ⅵ. 실무 적용 및 결론

**적용 방안 3개 (필수 — 단계별 또는 항목별):**
1. 요구 실시간성이 hard real-time이면 RTOS 기반 태스크 스케줄링을 적용하고 worst-case 인터럽트 latency를 사전 분석함
2. 저전력·저비용 목표 제품은 MCU 단일 칩 구조로 설계하고 Flash/RAM 사용률을 80% 이하로 관리함
3. 개발 단계에서 cross-compilation 툴체인과 JTAG board bring-up 절차를 표준화해 디버깅 시간을 단축함

**결론 (2줄):**
- 기술사 판단: 다목적 확장성이 필요하면 범용 OS 기반, 저전력·실시간·저비용이 핵심이면 MCU 기반 임베디드 구조를 선택함
- 향후 방향: Edge AI, OTA 업데이트, Embedded Linux 확대로 임베디드 시스템도 유연성과 실시간성을 동시에 확보하는 방향으로 발전해야 함
