# 📖 【암기용】 개념 완전 이해

> 목적: 벡터 인터럽트와 데이지체인 방식을 처음 봐도 어떻게 요청 장치를 식별하고 우선순위를 정하는지 이해하게 만든다. 시험 답안 양식이 아니라, 이해를 위한 친절한 설명이다.

## 한눈에
- **개요**: 여러 장치가 동시에 인터럽트를 걸 때 요청 장치를 식별하고 우선순위를 정해 해당 ISR(Interrupt Service Routine)로 분기하는 메커니즘
- **왜 필요한가**: 다수 장치가 동시에 인터럽트를 걸 수 있어, 식별·우선순위 결정이 없으면 CPU가 어느 ISR을 실행해야 할지 알 수 없다.
- **핵심 직관**: 여러 사람이 동시에 손을 들 때 미리 번호표(vector)를 나눠주는 방식과, 줄을 세워 앞사람부터 순서대로 확인하는 방식(daisy chain)의 차이다.

## 깊이 이해
- **배경·문제의식**: 초기 비벡터(polled) 인터럽트는 CPU가 인터럽트 발생 시 각 장치의 상태 레지스터를 우선순위 순서로 순차 검사해 요청 장치를 찾았다.
- **배경·문제의식**: 장치 수가 많아지면 순차 검사 시간이 늘어나 응답 지연이 커지는 문제가 있었다.
- **작동 원리 — Vectored Interrupt**: 인터럽트를 요청한 장치가 자신의 vector(ISR 주소 또는 vector number)를 직접 데이터 버스에 실어 CPU에 전달한다.
- **작동 원리 — Vectored Interrupt**: CPU는 이 vector로 인터럽트 벡터 테이블을 인덱싱해 해당 ISR로 곧바로 점프하며, 상태 레지스터를 순차 폴링할 필요가 없다.
- **작동 원리 — Daisy-chain**: 여러 장치가 인터럽트 확인 신호(INTA, Interrupt Acknowledge) 라인을 직렬로 연결한다.
- **작동 원리 — Daisy-chain**: CPU가 인터럽트 요청(INT)을 받으면 INTA를 체인의 첫 장치로 보내고, 요청하지 않은 장치는 신호를 다음 장치로 그대로 전달(pass-through)한다.
- **작동 원리 — Daisy-chain**: 실제 요청한 장치가 INTA를 가로채 자신의 vector를 버스에 싣고, 체인에서 CPU에 가까운 장치일수록 우선순위가 높다.
- **결합 구조**: PIC(Programmable Interrupt Controller, 예: 8259A)는 여러 IRQ 라인을 입력받아 우선순위 판별 로직(priority resolver)과 vector 생성 기능을 함께 제공한다.
- **결합 구조**: 8259A는 master에 8개, slave에 8개 IRQ를 배치하고 master의 IRQ2에 slave를 캐스케이드 연결해 최대 15개 인터럽트원을 관리한다.
- **비유**: 명함(vector)을 미리 주고 들어오는 손님이 벡터 인터럽트, 줄 서서 앞사람부터 순서대로 확인하는 방식이 데이지체인이다.
- **구체 예시**: x86 레거시 시스템은 8259A PIC가 IRQ0(타이머)~IRQ15까지 각 IRQ에 고정 vector number를 매핑하고 IRQ0을 최고 우선순위로 처리한다.
- **흔한 오해·주의점**: "벡터 인터럽트는 우선순위가 없다"는 틀렸다. PIC 레벨에서 IRQ 번호나 우선순위 레지스터로 우선순위를 부여할 수 있다.
- **흔한 오해·주의점**: "데이지체인은 소프트웨어 방식이다"는 틀렸다. 데이지체인은 배선 순서만으로 우선순위가 결정되는 순수 하드웨어 방식이다.

## 연결 개념
- I/O 인터페이스(폴링·인터럽트·DMA·채널 I/O) — 인터럽트가 속한 상위 I/O 제어 방식 분류
- PIC·APIC(Advanced PIC) — 벡터 생성·우선순위 판별을 수행하는 하드웨어
- 버스 중재(Bus Arbitration) — 다중 장치가 버스 접근 우선순위를 정하는 유사 메커니즘

# 📝 【답안용】 시험 답안 템플릿

> 목적: 시험장에서 25분에 그대로 쓰는 답안 양식. 작성방식(추상표현 금지·수치·도식·문제유형 전환)을 엄격히 지킨다.
> 핵심: 인터럽트 처리 답안은 벡터 방식의 즉시 분기 원리와 데이지체인의 배선 기반 우선순위 원리를 구분해 제시한다.

## 핵심 인사이트 (3줄 요약)

> 1. **본질**: 인터럽트 처리 방식은 다중 인터럽트 요청원 중 요청 장치를 식별하고 우선순위를 정해 ISR로 분기하는 메커니즘이며 벡터·데이지체인으로 구현된다.
> 2. **가치**: 벡터 방식은 폴링 없이 즉시 ISR로 분기해 응답 지연을 줄이고, 데이지체인은 배선 순서만으로 하드웨어 우선순위를 결정한다.
> 3. **판단 포인트**: 장치 수, 우선순위 요구, 응답 지연 목표에 따라 벡터+PIC 결합 방식 또는 데이지체인 방식을 선택한다.

## 출제 의도 및 답안 포인트

| 출제 의도 | 반드시 짚을 핵심 | 감점 회피 포인트 |
|:---|:---|:---|
| 인터럽트 식별 메커니즘 이해 확인 | vector 전달과 벡터 테이블 인덱싱 원리 | 벡터 방식을 단순 폴링 개선으로만 서술 |
| 하드웨어 우선순위 결정 원리 확인 | INTA 신호 daisy-chain 전달과 체인 위치별 우선순위 | 데이지체인을 소프트웨어 우선순위로 오인 |
| 실제 시스템 적용 이해 확인 | PIC의 우선순위 판별+vector 생성 결합, 8259A 캐스케이드 | 벡터와 데이지체인을 상호 배타적 방식으로만 서술 |

> 요약: 이 문제는 인터럽트 방식 명칭 암기가 아니라 요청 식별·우선순위 결정 메커니즘의 차이를 보여야 한다.

## Ⅰ. 개요 및 필요성

- 개요: 다중 인터럽트 요청원을 식별하고 우선순위를 정해 해당 ISR로 분기하는 처리 방식
- 배경: 비벡터 폴링 방식은 장치 수가 늘어날수록 순차 검사 시간이 길어져 응답 지연이 커짐
- 필요성: 응답 지연 최소화와 하드웨어 우선순위 결정을 위해 벡터·데이지체인 방식이 필요함

---

## Ⅱ. 구조 및 구성요소

```text
Device 1..N -> Interrupt Request(IRQ Lines)
  -> PIC(Priority Resolver + Vector Generator)
  -> Vectored: Vector Number -> Interrupt Vector Table -> ISR Jump
  -> Daisy-chain: INTA Pass-through -> Requesting Device -> Vector on Bus -> ISR Jump
```

| 구성요소 | 역할 | 특이사항 |
|:---|:---|:---|
| IRQ Line | 장치의 인터럽트 요청 신호 | 레벨 또는 엣지 트리거 |
| INTA Line | 인터럽트 확인 신호 | 데이지체인에서 직렬 전달 |
| Vector Table | vector number를 ISR 주소로 매핑 | CPU가 곧바로 점프하는 근거 |
| PIC(8259A 등) | 우선순위 판별과 vector 생성 결합 | master/slave 캐스케이드로 확장 |

> 요약: 인터럽트 처리는 IRQ·INTA 신호와 vector 테이블, PIC의 우선순위 판별을 조합해 ISR로 분기한다.

---

## Ⅲ. 동작원리 및 흐름도

```text
Device Interrupt Request -> CPU INT 수신
  -> Vectored: Device가 Vector 제공 -> Vector Table Index -> ISR Jump
  -> Daisy-chain: INTA를 체인 첫 장치부터 전달 -> 요청 장치가 가로챔 -> Vector 제공 -> ISR Jump
  -> ISR 실행 -> 인터럽트 종료(EOI)
```

| 단계 | 처리 내용 | 검증 기준 |
|:---:|:---|:---|
| 1 | 장치가 IRQ 라인으로 인터럽트 요청 | 신호 검출 |
| 2 | CPU가 INTA로 확인, vector 획득 방식 결정 | 벡터/데이지체인 방식 |
| 3 | vector로 ISR 주소 확정 후 분기 | 벡터 테이블 인덱싱 정확성 |
| 4 | ISR 실행 후 EOI(End Of Interrupt)로 종료 | 인터럽트 지연시간(latency) |

> 요약: 인터럽트는 요청 신호 발생 후 vector 획득 방식에 따라 ISR로 분기하고 EOI로 마무리된다.

---

## Ⅳ. 특징

| 구분 | Vectored Interrupt | Daisy-chain |
|:---|:---|:---|
| 식별 방식 | 장치가 vector를 직접 버스에 제공 | INTA 신호를 체인 순서로 전달해 요청 장치 확인 |
| 우선순위 결정 | PIC 레지스터·IRQ 번호로 소프트/하드 조합 | 체인 내 물리적 위치(배선 순서)로 고정 |
| 응답 지연 | 폴링 없이 즉시 분기 | 체인 앞쪽 장치일수록 지연 짧음 |
| 확장성 | PIC 캐스케이드로 다수 장치 확장 용이 | 체인 재배선 필요해 확장성 낮음 |

> 요약: 벡터 방식은 즉시 분기와 유연한 우선순위 설정에 유리하고, 데이지체인은 배선만으로 결정되는 단순한 하드웨어 우선순위를 제공한다.

## Ⅴ. 심화 비교 및 적용 판단

| 비교 축 | 비벡터(Polled) 인터럽트 | 벡터·데이지체인 인터럽트 | 선택 기준 |
|:---|:---|:---|:---|
| 구조 | 상태 레지스터 순차 검사 | vector 직접 제공 또는 INTA 체인 전달 | 장치 수 많으면 벡터 방식 |
| 비용/성능 | 장치 수 비례 지연 증가 | 응답 지연 일정 수준 유지 | 응답 지연 목표(latency SLA) 기준 |
| 운영/위험 | 검사 로직 단순 | PIC 설정·체인 배선 복잡도 존재 | 우선순위 변경 빈도로 판단 |

> 요약: 장치 수가 적고 우선순위가 고정적이면 데이지체인, 장치 수가 많고 우선순위 조정이 필요하면 PIC 기반 벡터 방식을 선택한다.

| 리스크 | 원인 | 대응 방안 | 확인 지표 |
|:---|:---|:---|:---|
| 인터럽트 손실 | 동시 다발 요청 시 낮은 우선순위 장치 무시 | 우선순위 레지스터·마스크 관리 | 미처리 인터럽트 카운트 |
| 체인 단선 | 데이지체인 배선 오류·장치 제거 | 체인 무결성 점검, 핫플러그 시 재구성 | 체인 연속성 테스트 결과 |
| 벡터 테이블 오류 | vector number와 ISR 주소 매핑 불일치 | 벡터 테이블 초기화 검증 | ISR 오분기 발생 횟수 |

> 요약: 인터럽트 처리 리스크는 우선순위 역전과 체인·테이블 오류이며 미처리 카운트와 오분기 횟수로 통제한다.

| 점검 항목 | 목표 기준 | 측정 방법 |
|:---|:---|:---|
| 응답 지연 | 인터럽트 latency 목표치 이내 | 트레이스, 오실로스코프 측정 |
| 우선순위 정확성 | 우선순위 순서대로 처리 확인 | PIC 레지스터 로그 |
| 확장성 | 신규 장치 추가 시 재구성 시간 목표치 이내 | 구성 변경 테스트 |

> 요약: 도입 성공 여부는 응답 지연, 우선순위 정확성, 확장 시 재구성 시간으로 판단한다.

## Ⅵ. 실무 적용 및 결론

**적용 방안 3개:**
1. 장치 수가 많고 우선순위 조정이 잦은 시스템은 PIC 기반 벡터 인터럽트를 적용해 확장성을 확보함
2. 장치 수가 적고 고정 우선순위면 데이지체인으로 배선 단순화와 비용 절감을 달성함
3. 대규모 장치 환경은 APIC·MSI(Message Signaled Interrupt)로 전환해 인터럽트 라인 제약을 해소함

**결론 (2줄):**
- 기술사 판단: 장치 수와 우선순위 변경 빈도가 낮으면 데이지체인, 높으면 PIC 기반 벡터 인터럽트를 선택함
- 향후 방향: 다중 코어·다중 장치 환경에서는 MSI-X 등으로 인터럽트를 특정 코어에 분산해 응답 지연과 부하를 함께 관리해야 함
