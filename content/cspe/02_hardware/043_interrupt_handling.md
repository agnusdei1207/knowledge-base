## 미리 알고가기

- **인터럽트 ($Interrupt$)**: 프로세서가 현재 실행 중인 프로그램의 흐름을 일시 중단하고, 특정 이벤트(장치 입출력, 예외 발생 등)를 우선 처리하도록 하는 제어 메커니즘
- **$ISR$ (Interrupt Service Routine)**: 특정 인터럽트가 발생했을 때 이를 처리하기 위해 실행되는 전용 함수 또는 루틴
- **문맥 보존 ($Context\ Saving$)**: 인터럽트 처리가 끝난 후 원래 프로그램으로 돌아가기 위해 현재의 레지스터 상태($PC$, $Status\ Reg$ 등)를 스택에 저장하는 과정
- **벡터 ($Vector$)**: 인터럽트의 종류별로 정해진 $ISR$의 시작 주소를 담고 있는 식별자 또는 주소 값
- **데이지체인 ($Daisy\ Chain$)**: 여러 장치를 직렬로 연결하여 인터럽트 승인 신호를 순차적으로 전달하는 우선순위 제어 방식

## Ⅰ. 개요

- **정의/개념**: 하드웨어나 소프트웨어의 긴급한 요청이 발생했을 때, $CPU$가 현재 작업을 중단하고 원인을 식별하여 적절한 $ISR$을 실행한 뒤 복구하는 메커니즘이며, 원인 식별 방식에 따라 벡터와 데이지체인으로 구분됨
  - **벡터 인터럽트 ($Vectored$)**: 장치가 고유의 식별 번호($Vector$)를 $CPU$에 직접 전달하여 즉각적으로 $ISR$ 주소를 찾는 방식임
  - **데이지체인 ($Daisy\ Chain$)**: 여러 장치를 직렬로 연결하여 인터럽트 승인 신호를 우선순위에 따라 순차적으로 전달하며 원인을 식별하는 방식임
- **배경/필요성**: 모든 장치를 일일이 확인하는 폴링($Polling$) 방식은 $CPU$ 자원의 낭비가 매우 큼. 인터럽트는 비동기적인 이벤트를 즉각적으로 감지하고 처리할 수 있게 하여 시스템의 응답성($Responsiveness$)과 자원 활용률을 극대화하기 위해 필수적임

## Ⅱ. 특징 및 비교

### 가. 벡터 인터럽트와 데이지체인 방식의 대비

| 구분 | 벡터 인터럽트 ($Vectored$) | 데이지체인 ($Daisy\ Chain$) |
|:---|:---|:---|
| **원인 식별** | 장치가 고유의 벡터 번호를 $CPU$에 직접 전달 | $CPU$가 승인 신호를 보내면 순차적으로 확인 |
| **우선순위 결정** | 소프트웨어 또는 인터럽트 컨트롤러가 관리 | 물리적인 연결 순서에 의해 자동 결정 |
| **응답 속도** | 매우 빠름 (즉시 $ISR$ 주소 획득) | 상대적으로 느림 (앞쪽 장치들을 거쳐야 함) |
| **하드웨어 구조** | 인터럽트 컨트롤러 등 복잡한 회로 필요 | 단순한 직렬 연결 구조 |
| **확장성** | 높음 (벡터 테이블 확장을 통해 다수 지원) | 낮음 (장치가 많아질수록 뒤쪽 장치 소외) |

> 요약: 벡터 방식은 '신속하고 유연한' 처리에, 데이지체인은 '단순하고 경제적인' 구성에 특화됨

### 나. 인터럽트 처리의 핵심 성능 지표
- **인터럽트 지연 ($Latency$)**: 요청 발생 시점부터 $ISR$의 첫 번째 명령어가 실행될 때까지의 시간
- **지터 ($Jitter$)**: 인터럽트 지연 시간의 불규칙한 변동성. 실시간 시스템($RTOS$)에서 매우 중요함

## Ⅲ. 구성요소/구조

### 가. 하드웨어 인터럽트 제어 및 $ISR$ 분기 구조

```text
[ I/O Device A ] --(IRQ)--> [ Interrupt Controller (PIC/APIC) ] --(INTR)--> [ CPU ]
                                      |                                       |
                             [ Priority Resolver ]                 [ Context Saving ]
                                      |                                       |
                             [ Vector Number (n) ] -------- (Lookup) ----> [ Vector Table ]
                                                                              |
[ Finish / Return ] <--------- [ Execute ISR_n ] <---------------------- [ ISR Address ]
```

### 나. 주요 구성 요소 및 역할

| 구성요소 | 역할 및 설명 | 핵심 포인트 |
|:---|:---|:---|
| 인터럽트 요청 선 ($IRQ$) | 장치가 $CPU$나 컨트롤러에 신호를 보내는 물리적 통로 | 에지($Edge$) 또는 레벨($Level$) 트리거 |
| 인터럽트 컨트롤러 | 여러 장치의 요청을 수집, 우선순위 판별, 마스킹 수행 | $Intel\ 8259A$, $APIC$ 등 |
| 벡터 테이블 | 인터럽트 번호와 $ISR$ 시작 주소의 매핑 정보를 담은 표 | 메모리의 특정 영역에 위치 |
| 스택 ($Stack$) | 복귀 주소와 레지스터 상태를 임시 저장하는 공간 | $LIFO$ 구조로 중첩 인터럽트 지원 |
| $IRET$ (명령어) | $ISR$ 종료 후 원래 프로그램으로 복귀시키는 특수 명령어 | 상태 레지스터 및 $PC$ 복원 |

> 요약: 요청($IRQ$) $\rightarrow$ 판별($Controller$) $\rightarrow$ 보존($Stack$) $\rightarrow$ 실행($ISR$) $\rightarrow$ 복구($IRET$)의 순환 구조임

## Ⅳ. 문제점 및 개선방안

1. **우선순위 역전 ($Priority\ Inversion$)**: 낮은 우선순위의 $ISR$이 실행 중일 때 높은 우선순위 작업이 대기하게 되는 현상
   - **개선방안**: **인터럽트 중첩($Nested\ Interrupt$)**을 허용하여 하위 루틴 실행 중 상위 인터럽트가 가로챌 수 있게 하거나, $ISR$의 실행 시간을 극도로 짧게 설계함

2. **지연 시간($Latency$)의 불확실성**: 인터럽트가 금지된 구간($Critical\ Section$)이 길어지면 긴급한 이벤트의 응답이 늦어짐
   - **개선방안**: **$Top-half$ / $Bottom-half$** 분리 처리를 적용함 ($ISR$에서는 필수 하드웨어 제어만 하고 복잡한 연산은 지연 처리로 넘김)

3. **컨텍스트 스위칭 오버헤드**: 잦은 인터럽트는 레지스터 저장 및 복원 과정에서 $CPU$ 자원을 과도하게 소모함
   - **개선방안**: 하드웨어적으로 여러 벌의 레지스터 세트를 두는 **레지스터 윈도우** 기술이나 **그림자 레지스터($Shadow\ Register$)**를 활용하여 저장 속도 높임

## Ⅴ. 실무 적용 사례

| 적용 영역 | 적용 방식 | 확인 지표 |
|:---|:---|:---|
| 리눅스 커널 ($Softirq$) | 하드웨어 인터럽트는 즉시 처리하고, 데이터 복사 등 무거운 작업은 $Softirq$나 $Tasklet$으로 후순위 처리 | $Interrupt\ Latency$, $Softirq\ Load$ |
| 자율주행 제어 ($ECU$) | 충돌 방지 센서 등에 최고 우선순위 벡터를 할당하여 $ms$ 단위의 즉각적인 브레이크 제어 보장 | $Worst-case\ Response\ Time$ |
| 네트워크 패킷 처리 | 패킷 도착 시 인터럽트를 통해 알림을 받되, 데이터 로드는 $DMA$와 연계하여 $CPU$ 부하 최소화 | $IRQ\ Rate$, $Packet\ Throughput$ |

> 요약: 실무에서는 '반응의 신속성'과 '시스템 전체의 안정성' 사이의 균형을 위해 계층적 인터럽트 설계를 수행함

## Ⅵ. 결론

인터럽트 처리는 현대 컴퓨팅의 동적인 특성을 가능케 하는 가장 핵심적인 제어 기법임. 단순히 흐름을 끊는 것을 넘어, 한정된 $CPU$ 자원을 시급성에 따라 지능적으로 분배하는 오케스트레이션 과정이라 할 수 있음.

기술사는 인터럽트의 물리적 신호 전달 방식(에지 vs 레벨)부터 운영체제 수준의 지연 처리 메커니즘까지 통합적인 시각을 갖추어야 함. 특히 멀티코어 환경에서 인터럽트를 특정 코어에 집중시키거나 분산시키는 **$Interrupt\ Affinity$** 기술과 가상화 환경에서의 인터럽트 전달 효율화 방안에 대해서도 깊은 통찰력이 요구됨.
