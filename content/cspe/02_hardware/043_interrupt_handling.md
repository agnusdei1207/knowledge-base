## Ⅰ. 개요
- **정의**: CPU가 현재 실행을 중단하고 긴급 이벤트를 처리한 뒤 복귀하는 하드웨어·소프트웨어 메커니즘임
- **배경/필요성**: I/O 완료·오류·타이머 등 비동기 이벤트에 즉시 대응하지 않으면 데이터 유실이나 시스템 교착이 발생함
- **비유**: 수업 중 긴급 전화가 오면 수업을 멈추고 통화 후 원래 자리로 돌아오는 것과 유사함

| 출제 의도 | 반드시 짚을 핵심 | 감점 회피 포인트 |
|:---|:---|:---|
| 벡터 vs 데이지체인 우선순위 결정 차이 | 벡터 = 주소 테이블 색인, 데이지체인 = 물리 체인 순서 | 소프트웨어 인터럽트(트랩)와 하드웨어 인터럽트를 구분할 것 |

> 요약: 인터럽트는 비동기 이벤트를 CPU가 즉시 처리할 수 있게 하는 제어 메커니즘임

## Ⅱ. 구성요소
```text
Device --IRQ--> Interrupt Controller --INTR--> CPU
                      |                         |
                      +-- Vector Table ---------+
                      |
                      +-- Priority Logic
```

| 구성요소 | 설명 | 비유 |
|:---|:---|:---|
| IRQ 라인 | 장치가 인터럽트를 요청하는 하드웨어 신호선 | 건물 각 방의 비상 벨 줄 |
| 인터럽트 컨트롤러(PIC/APIC) | 복수 IRQ의 우선순위를 판정하여 CPU에 하나의 INTR 신호를 전달함 | 비상 전화를 분류하는 교환원 |
| 벡터 테이블 | 인터럽트 번호별 ISR 시작 주소를 저장한 메모리 테이블 | 전화번호부에서 담당자 번호 검색 |
| ISR (Interrupt Service Routine) | 인터럽트 원인을 처리하고 CPU 상태를 복원하는 서비스 루틴 | 전화를 받고 문제를 처리하는 담당자 |

> 요약: IRQ → 컨트롤러 → 벡터 테이블 → ISR 순으로 인터럽트 처리 경로가 구성됨

## Ⅲ. 절차
```text
IRQ 발생 -> 우선순위 판정 -> 컨텍스트 저장 -> ISR 실행 -> 복원/복귀
   (1)          (2)             (3)            (4)
```
- 1단계: **IRQ 발생 및 우선순위 판정** — 장치가 IRQ를 발생시키고 인터럽트 컨트롤러가 우선순위를 결정함
- 2단계: **컨텍스트 저장** — CPU가 현재 PC·PSW·레지스터를 스택에 저장함
- 3단계: **ISR 실행** — 벡터 테이블에서 ISR 주소를 읽어 해당 루틴을 수행함
- 4단계: **복원 및 복귀** — 스택에서 컨텍스트를 복원하고 중단된 명령어로 복귀함

> 요약: 신호 수신 → 상태 보존 → 서비스 수행 → 상태 복원의 4단계로 인터럽트가 처리됨

## Ⅳ. 문제점
- **우선순위 역전**: 낮은 우선순위 ISR이 공유 자원을 점유하면 높은 우선순위 인터럽트 처리가 지연됨
- **인터럽트 폭주(Storm)**: 단시간에 대량 인터럽트가 몰리면 ISR 처리만으로 CPU가 포화됨
- **데이지체인 불공정**: 체인 앞쪽 장치가 지속 요청하면 뒤쪽 장치는 서비스 기회를 얻지 못함

> 요약: 우선순위 역전·인터럽트 폭주·데이지체인 불공정이 주요 문제임

## Ⅴ. 개선방안
1. 단기: 우선순위 상속(Priority Inheritance) 프로토콜로 우선순위 역전을 방지함
2. 중기: 인터럽트 스로틀링·코얼레싱 적용으로 단위 시간당 인터럽트 수를 제한함
3. 장기: APIC 기반 동적 우선순위 재배정으로 장치 간 서비스 공정성을 확보함

> 요약: 우선순위 상속 → 스로틀링 → 동적 재배정 순으로 인터럽트 처리 안정성을 높임

## Ⅵ. 전망
- 발전 방향: MSI/MSI-X 방식이 핀 기반 IRQ를 대체하여 인터럽트 라우팅 유연성이 증가함
- 기술사적 판단: 실시간 시스템 설계 시 인터럽트 지연시간(Latency) 분석이 핵심 검증 항목임
- 기술사 제언: 워스트케이스 인터럽트 지연시간을 정량 측정하여 실시간 요구사항 충족 여부를 검증할 필요
