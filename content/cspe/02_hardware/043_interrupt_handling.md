## 미리 알고가기

- 인터럽트는 비동기 이벤트가 발생했을 때 CPU 실행 흐름을 잠시 바꾸는 메커니즘임
- 벡터 방식은 ISR 주소를 빠르게 찾고 데이지체인은 하드웨어 우선순위를 단순하게 구현함
- 핵심 지표는 interrupt latency, prioritization, ISR overhead임

## Ⅰ. 개요

- **정의/개념**: 인터럽트 처리 방식은 장치나 예외가 CPU에 서비스 요청을 전달했을 때 원인을 식별하고 우선순위를 결정해 적절한 ISR로 분기한 뒤 원래 작업으로 복귀시키는 제어 구조임
- **배경/필요성**: 폴링만으로는 비동기 장치 이벤트를 적시에 처리하기 어렵기 때문에, 응답성과 CPU 활용률을 높이기 위한 비동기 제어 방식이 필요함

## Ⅱ. 특징

- 비동기 이벤트를 즉시 처리해 응답성이 높음
- 인터럽트 컨트롤러와 벡터 테이블 설계에 따라 식별 속도와 확장성이 달라짐
- 우선순위와 마스킹 정책이 실시간성에 직접 영향을 줌
- ISR가 길어지면 전체 시스템 지연과 중첩 처리 부담이 증가함

## Ⅲ. 종류 및 비교

| 판단 기준 | 벡터 인터럽트 | 데이지체인 |
|:---|:---|:---|
| 원인 식별 | 벡터 번호로 즉시 식별 | 승인 신호를 순차 전달하며 식별 |
| 응답 속도 | 빠름 | 상대적으로 느림 |
| 확장성 | 높음 | 낮음 |
| 우선순위 방식 | 컨트롤러 또는 테이블 기반 | 물리적 연결 순서 기반 |

## Ⅳ. 구성요소 및 구조

| 구성요소 | 설명 |
|:---|:---|
| IRQ 라인 | 장치가 인터럽트 요청을 발생시키는 신호 경로로 트리거 방식 선택이 중요함 |
| 인터럽트 컨트롤러 | 다수 요청을 수집하고 마스킹과 우선순위 결정을 수행해 CPU 부담을 줄임 |
| 벡터 테이블 | 인터럽트 번호와 ISR 주소를 매핑해 빠른 분기를 가능하게 함 |
| ISR, 복귀 메커니즘 | 문맥 저장과 서비스 수행과 복귀를 처리하며 ISR 길이가 시스템 응답성을 좌우함 |

```text
+-------------+     +----------------------+     +----------------+     +-------------+
| IRQ Sources | --> | Interrupt Controller | --> | Vector / ISR   | --> | CPU Return  |
+-------------+     +----------------------+     +----------------+     +-------------+
```

## Ⅴ. 원리 및 절차 흐름도

```text
+-------------+     +-------------+     +-------------+     +-------------+
| IRQ 발생       | --> | 원인/우선순위 판정 | --> | ISR 실행      | --> | 문맥 복귀      |
+-------------+     +-------------+     +-------------+     +-------------+
```

1. **IRQ 발생**: 장치가 CPU 또는 컨트롤러에 인터럽트 요청을 보냄
2. **원인 및 우선순위 판정**: 벡터 또는 체인 구조로 서비스 대상을 결정함
3. **ISR 실행**: 문맥 저장 후 서비스 루틴을 처리함
4. **문맥 복귀**: 상태를 복원하고 원래 프로그램 흐름으로 돌아감

## Ⅵ. 문제점 및 해결 방안

1. 문제: 우선순위가 부적절하면 중요한 장치 이벤트가 지연되어 실시간 응답성이 무너질 수 있음
   - 해결방안: priority map과 interrupt masking 정책을 조정하고 worst-case interrupt latency로 검증함
2. 문제: ISR가 과도하게 길면 다른 인터럽트와 사용자 작업이 함께 대기해 시스템 지터가 커질 수 있음
   - 해결방안: ISR는 최소 처리만 수행하고 하위 작업은 deferred handler로 넘기며 ISR execution time과 jitter로 검증함
3. 문제: 데이지체인 구조는 하위 장치일수록 승인 지연이 누적되어 다수 장치 환경에서 공정성이 떨어질 수 있음
   - 해결방안: 장치 수가 많으면 벡터 컨트롤러 구조로 전환하고 interrupt fairness와 service latency로 적합성을 검증함

## Ⅶ. 적용 사례

- 네트워크 카드 처리에서는 벡터 인터럽트로 장치 식별 시간을 줄이고, interrupt latency와 packet drop rate로 결과를 확인함
- 임베디드 제어 보드에서는 단순 장치 우선순위를 데이지체인으로 구성하고, hardware cost와 service delay로 결과를 확인함
- 실시간 운영체제에서는 짧은 ISR와 하위 작업 분리를 적용하고, jitter와 deadline miss rate로 결과를 확인함

## Ⅷ. 결론

인터럽트 처리 방식의 선택은 원인 식별 속도와 우선순위 제어 능력의 문제이므로, 다장치와 실시간 환경일수록 벡터 기반 구조와 짧은 ISR 설계가 유리함.
