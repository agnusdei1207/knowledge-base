## 미리 알고가기

- 인터럽트: 장치나 내부 이벤트가 CPU의 현재 흐름을 중단시키고 처리를 요청하는 신호임
- ISR: interrupt service routine의 약자로 인터럽트 원인별 처리 루틴임
- 벡터: 인터럽트 원인에 대응하는 ISR 주소 또는 식별 번호임
- 데이지체인: 여러 장치를 직렬 우선순위 순서로 연결해 인터럽트 승인 신호를 전달하는 방식임

## Ⅰ. 개요

- **정의**: 인터럽트 처리 방식은 CPU가 장치 이벤트, 예외, 타이머 신호를 받았을 때 원인을 식별하고 우선순위를 결정한 뒤 해당 ISR로 분기해 처리하는 제어 메커니즘이며 벡터 방식과 데이지체인 방식은 원인 식별과 우선순위 부여 방법을 달리함
- **배경/필요성**: CPU가 모든 장치를 폴링하면 대기 시간이 낭비되고 비동기 이벤트를 빠르게 처리하기 어려움. 인터럽트는 장치가 필요할 때만 CPU에 알리게 해 응답성과 CPU 활용률을 높임
- **비유**: 업무 중 전화가 오면 발신자와 긴급도를 확인해 담당 매뉴얼로 바로 이동하는 절차와 같음

| 출제 의도 | 반드시 짚을 핵심 | 감점 회피 포인트 |
|:---|:---|:---|
| 비동기 이벤트 처리 구조를 우선순위와 ISR 분기 관점에서 설명하는 역량 확인 | ISR, vector, priority, daisy chain, interrupt controller | 폴링과 혼동, context 저장 누락, 우선순위 처리 누락 |

> 요약: 인터럽트 처리는 CPU가 비동기 이벤트를 식별하고 우선순위에 따라 ISR을 실행하는 메커니즘임.

## Ⅱ. 특징/비교

| 판단 기준 | 벡터 인터럽트 | 데이지체인 인터럽트 |
|:---|:---|:---|
| 원인 식별 | 장치가 벡터 번호를 제공해 ISR 주소를 빠르게 결정 | 승인 신호가 직렬로 이동하며 요청 장치를 찾음 |
| 우선순위 | 컨트롤러와 벡터 테이블로 유연하게 설정 | 물리 연결 순서가 우선순위에 영향 |
| 성능 | 빠른 분기와 확장성 우수 | 단순하지만 뒤쪽 장치 지연 가능 |
| 적용 조건 | 다수 장치와 운영체제 환경 | 단순 버스·소규모 시스템 |

> 요약: 벡터 방식은 빠른 원인 식별과 유연성이 강점이고 데이지체인은 단순한 하드웨어 우선순위가 강점임.

- 인터럽트 컨트롤러는 여러 IRQ를 수집하고 mask, priority, acknowledge, EOI 처리를 담당함
- ISR은 짧게 처리하고 긴 작업은 bottom half, tasklet, workqueue 같은 지연 처리로 넘기는 구조가 일반적임
- 실시간 시스템에서는 interrupt latency와 jitter가 응답 시간 보장의 핵심 지표임

## Ⅲ. 구성요소

```text
+-----------+      +-----------+      +-----------+
| Device IRQ| ---> | Int Ctrl  | ---> | CPU       |
+-----------+      +-----------+      +-----------+
                        |
                        v
                  +-----------+
                  | Vector/ISR|
                  +-----------+
```

| 구성요소 | 설명 | 비유 |
|:---|:---|:---|
| IRQ 신호 | 장치가 CPU에 이벤트 발생을 알리는 요청 신호임 | 호출벨 |
| 인터럽트 컨트롤러 | 요청을 수집하고 우선순위, 마스킹, 벡터 전달을 수행함 | 접수·배정 데스크 |
| 벡터 테이블 | 인터럽트 번호와 ISR 시작 주소를 연결하는 테이블임 | 담당자 전화번호부 |
| ISR | 인터럽트 원인별 최소 처리를 수행하고 장치 상태를 정리하는 루틴임 | 긴급 처리 매뉴얼 |

> 요약: 인터럽트 처리는 IRQ, 컨트롤러, 벡터 테이블, ISR이 결합되어 이벤트를 코드 실행으로 연결함.

## Ⅳ. 절차

```text
+-----------+      +-----------+      +-----------+      +-----------+
| IRQ발생   | ---> | 우선순위결정 | ---> | ISR분기  | ---> | 복귀/EOI |
+-----------+      +-----------+      +-----------+      +-----------+
```

1. **IRQ 발생**: 장치나 내부 타이머가 인터럽트 요청을 발생시킴
2. **우선순위 결정**: 인터럽트 컨트롤러가 mask와 priority를 기준으로 처리 대상을 선택함
3. **상태 저장과 ISR 분기**: CPU가 현재 context를 저장하고 벡터 또는 탐색 결과로 ISR에 진입함
4. **처리 완료와 복귀**: ISR이 장치 상태를 정리하고 EOI 후 저장된 context로 복귀함

> 요약: 인터럽트는 요청 발생, 우선순위 선정, ISR 실행, 완료 통지와 복귀 순서로 처리됨.

## Ⅴ. 문제점

- **P1 interrupt latency 증가**: 높은 우선순위 작업, 긴 ISR, interrupt disable 구간이 응답 시간을 늘림
- **P2 interrupt storm**: 장치 오류나 과도한 이벤트가 계속 발생하면 CPU가 ISR 처리에 묶임
- **P3 우선순위 역전·기아**: 우선순위 설정이 부적절하면 낮은 우선순위 장치가 장시간 처리되지 못함

> 요약: 인터럽트의 핵심 문제는 응답 지연, 이벤트 폭주, 우선순위 관리 실패임.

## Ⅵ. 개선방안

1. **단기**: IRQ rate, ISR 실행 시간, interrupt disabled time, missed interrupt를 측정함
2. **중기**: ISR 최소화, interrupt coalescing, affinity, 우선순위 재조정을 적용함
3. **장기**: 실시간 요구에 맞는 interrupt controller 설정과 드라이버 작성 표준을 수립함

- **P1 대응**: ISR을 짧게 유지하고 긴 작업은 지연 처리로 넘김 (확인: max interrupt latency)
- **P2 대응**: coalescing, rate limit, 장치 오류 격리로 인터럽트 폭주를 완화함 (확인: IRQ/sec)
- **P3 대응**: priority와 affinity 정책을 워크로드에 맞게 조정함 (확인: starvation과 deadline miss)

> 요약: 인터럽트 개선은 ISR 시간 축소, 이벤트 빈도 제어, 우선순위 정책 정비로 이루어짐.

## Ⅶ. 전망

- **발전 방향**: 고속 I/O 장치가 늘수록 인터럽트 단독 처리보다 polling, batching, queue affinity를 결합한 하이브리드 방식이 중요해짐
- **기술사적 판단**: 실시간·임베디드 시스템에서는 평균 처리량보다 최악 interrupt latency와 jitter 관리가 핵심 평가 기준이 됨
- **기술사 제언**: 기술사는 인터럽트를 단순 신호가 아니라 CPU 스케줄링, I/O 큐, 실시간성에 영향을 주는 제어 경로로 설명해야 함
