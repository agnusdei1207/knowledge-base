# 인터럽트 처리 방식 - 벡터·데이지체인 (Interrupt Handling)

## 미리 알고가기

- 인터럽트: 장치나 내부 이벤트가 CPU의 현재 실행 흐름을 중단시키고 처리를 요청하는 신호임
- ISR: 인터럽트 서비스 루틴(Interrupt Service Routine, ISR)은 인터럽트 원인별 처리 루틴임
- IRQ: 인터럽트 요청(Interrupt Request, IRQ)은 장치가 CPU에 이벤트 처리를 요구하는 신호임
- 벡터: 인터럽트 원인에 대응하는 ISR 주소 또는 식별 번호임
- 데이지체인: 여러 장치를 직렬 우선순위 순서로 연결해 인터럽트 승인 신호를 전달하는 방식임

## 1. 개요

- **정의/개념**: 인터럽트 처리 방식은 CPU가 장치 이벤트, 예외, 타이머 신호를 받았을 때 현재 문맥을 보존하고 원인과 우선순위를 판단한 뒤 해당 ISR로 분기해 처리하는 제어 메커니즘임.
- **배경/필요성**: CPU가 모든 장치를 폴링하면 대기 시간이 낭비되고 비동기 이벤트를 빠르게 처리하기 어려움. 인터럽트는 장치가 필요할 때만 CPU에 알리게 해 응답성과 CPU 활용률을 높임.

| 출제 의도 | 반드시 짚을 핵심 | 감점 회피 포인트 |
|:---|:---|:---|
| 비동기 이벤트 처리 구조를 우선순위와 ISR 분기 관점에서 설명하는 역량 확인 | ISR, vector, priority, daisy chain, interrupt controller | 폴링과 혼동, context 저장 누락, 우선순위 처리 누락 |

> 요약: 인터럽트 처리는 비동기 이벤트를 빠르게 식별하고 우선순위에 따라 안전하게 ISR을 실행하는 구조임.

## 2. 특징 및 비교

| 판단 기준 | 벡터 인터럽트 | 데이지체인 인터럽트 |
|:---|:---|:---|
| 원인 식별 | 인터럽트 벡터 번호로 ISR 주소를 직접 찾음 | 승인 신호가 직렬로 전달되며 응답 장치가 원인을 제공함 |
| 우선순위 | 인터럽트 컨트롤러나 벡터 테이블에서 정책화함 | 연결 순서가 우선순위가 됨 |
| 처리 속도 | ISR 분기가 빠르고 확장성이 좋음 | 구조는 단순하지만 뒤쪽 장치 지연이 커질 수 있음 |
| 적용 조건 | 다수 장치, 복잡한 우선순위, 운영체제 기반 시스템 | 단순 버스, 제한된 장치 수, 하드웨어 단순화 요구 |

인터럽트의 핵심 판단 차원은 원인 식별 속도, 우선순위 공정성, 문맥 저장 비용, 인터럽트 중첩 제어임. 이벤트가 많고 우선순위가 복잡한 시스템일수록 인터럽트 컨트롤러와 벡터 방식의 역할이 커짐.

## 3. 구성요소/구조

```text
+----------+      +----------------+      +---------+
| Device   | ---> | IRQ Controller | ---> | CPU     |
+----------+      +----------------+      +---------+
                                             |
                                             v
                                      +-------------+
                                      | Vector/ISR  |
                                      +-------------+
```

| 구성요소 | 설명 | 핵심 포인트 |
|:---|:---|:---|
| 인터럽트 요청 장치 | 이벤트 발생 시 IRQ를 생성함 | 이벤트 발생원 |
| 인터럽트 컨트롤러 | IRQ 마스킹, 우선순위, 벡터 전달을 관리함 | 우선순위 통제 |
| CPU 문맥 저장부 | PC, 상태 레지스터, 일부 레지스터를 저장함 | 실행 흐름 보존 |
| 벡터 테이블 | 인터럽트 원인별 ISR 위치를 제공함 | 빠른 분기 |
| ISR | 장치 상태 확인, 데이터 처리, 인터럽트 종료 처리를 수행함 | 짧고 결정적인 처리 |

### 원리/흐름도

```text
+-------+      +----------+      +----------+      +---------+      +--------+
| IRQ   | ---> | Priority | ---> | Save Ctx | ---> | Run ISR | ---> | Return |
+-------+      +----------+      +----------+      +---------+      +--------+
```

CPU는 명령 실행 중 인터럽트 신호를 확인하고, 허용된 요청이면 현재 문맥을 저장한 뒤 벡터 테이블을 통해 ISR로 이동함. ISR은 원인을 처리하고 장치와 컨트롤러의 완료 상태를 정리한 후 복귀 명령으로 원래 흐름을 재개함.

## 4. 문제점 및 개선방안

1. **인터럽트 지연 증가**: 높은 우선순위 ISR이 길거나 인터럽트 비활성 구간이 길면 실시간 응답이 지연됨.
   - **개선방안**: ISR은 최소 처리만 수행하고 나머지는 bottom half, tasklet, workqueue 등 지연 처리로 넘김. (확인: interrupt latency)
2. **인터럽트 폭주**: 장치 이벤트가 과도하게 발생하면 CPU가 ISR 처리에 잠식되어 정상 작업 처리량이 낮아짐.
   - **개선방안**: interrupt coalescing, rate limiting, 폴링 전환 조건을 적용함. (확인: IRQ rate, CPU softirq 사용률)
3. **우선순위 역전과 기아**: 고정 우선순위나 데이지체인 구조에서는 낮은 우선순위 장치가 지속적으로 대기할 수 있음.
   - **개선방안**: 동적 우선순위, 라운드로빈, 마스킹 정책을 적용하고 실시간 장치의 최악 응답시간을 검증함. (확인: 장치별 대기 시간)

## 5. 실무 적용 사례

| 적용 영역 | 적용 방식 | 확인 지표 |
|:---|:---|:---|
| 운영체제 장치 드라이버 | ISR은 이벤트 확인과 큐 적재만 수행하고 실제 처리는 커널 작업 큐에서 실행함 | interrupt latency, ISR 실행 시간 |
| 실시간 임베디드 제어 | 타이머와 센서 인터럽트에 우선순위를 부여하고 마스킹 구간을 최소화함 | worst-case latency, deadline miss |
| 고속 네트워크 처리 | 패킷마다 인터럽트를 처리하지 않고 coalescing과 폴링 혼합으로 CPU 오버헤드를 줄임 | 패킷 드롭률, IRQ rate, p99 지연 |

## 6. 결론

인터럽트 처리는 CPU 활용률을 높이는 비동기 이벤트 처리 구조이지만, 우선순위와 ISR 길이를 통제하지 않으면 지연과 폭주가 발생함. 벡터 방식은 빠른 원인 식별에, 데이지체인은 단순한 우선순위 구성에 의미가 있음. 실무에서는 ISR 최소화, 우선순위 정책, 인터럽트율 제어를 함께 설계해야 안정적인 I/O 응답성을 확보할 수 있음.
