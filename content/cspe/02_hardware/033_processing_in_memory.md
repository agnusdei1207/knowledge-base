# 📖 【암기용】 개념 완전 이해

> 목적: PIM 중에서도 "메모리 뱅크가 병렬로 동시에 연산한다"는 것이 정확히 무엇을 뜻하는지, 그리고 그 병렬성이 왜 데이터 중심 컴퓨팅(Data-Centric Computing)이라는 새로운 패러다임으로 불리는지 완전히 이해하게 만든다.

## 한눈에
- **개요**: PIM(Processing-in-Memory)은 **폰 노이만 병목(Memory Wall)**을 해소하기 위해 D램 **뱅크(Bank)** 내부에 연산 유닛(PCU)을 붙여, 여러 뱅크가 **동시에(병렬로)** 계산해서 결과만 CPU로 돌려주는 **데이터 중심 컴퓨팅(Data-Centric Computing)** 기술이다.
- **왜 필요한가**: 폰 노이만 구조는 "메모리는 저장만, CPU는 계산만" 하도록 딱 분리돼 있다. 그런데 AI 연산은 계산량보다 옮겨야 할 데이터양이 압도적으로 많아서, 이 분리 구조 자체가 시간·전력을 잡아먹는 병목이 된다. PIM은 데이터를 옮기는 대신 계산을 데이터가 있는 자리(뱅크)로 보내서 이 병목을 없앤다.
- **핵심 직관**: 창고(메모리)에 물건을 쟁여두고 필요할 때마다 전부 사무실(CPU)로 실어 나르는 대신, 창고의 각 칸(뱅크)마다 소형 계산기(PCU)를 하나씩 놔두고 "이 칸 물건들끼리 더해서 합계만 갖고 와"라고 시키는 것. 칸이 10개면 10명이 동시에 계산하니 훨씬 빠르다.

## 핵심 용어 정리 (내부에 등장하는 것들)

| 용어 | 의미 | 비유 |
|:---|:---|:---|
| 폰 노이만 병목 (Memory Wall) | CPU-메모리 간 데이터 이동이 성능·전력의 병목이 되는 현상 — PIM이 풀려는 **상위 문제** | 창고와 사무실 사이 복도가 매번 꽉 막히는 것 |
| 데이터 중심 컴퓨팅 (Data-Centric Computing) | "계산이 데이터를 찾아간다"는 설계 철학 — PIM이 속한 **상위 패러다임** | 사람이 재료를 안 옮기고 재료가 있는 곳에 요리사가 감 |
| PCU (Programmable Computing Unit) | 각 뱅크에 심어진 소형 연산기 — 덧셈·곱셈(FMA) 같은 단순 연산 전담 | 창고 칸마다 배치된 계산기 1대 |
| Bank-level Parallelism (뱅크 수준 병렬성) | 여러 뱅크의 PCU가 동시에 독립적으로 연산하는 것 | 10개 창고 칸에서 10명이 동시에 계산 |
| PIM Instruction | 호스트(CPU)가 "이 연산 해"라고 내리는 전용 명령어 | 창고 관리자에게 보내는 업무 지시서 1장 |
| Local Data Path | 뱅크 내부에서만 도는, 칩 밖으로 안 나가는 초고속 데이터 통로 | 창고 칸 내부에서만 도는 컨베이어 벨트 |
| Reduction (결과 집계) | 여러 뱅크가 낸 부분 결과를 하나로 합치는 마지막 단계 | 각 칸의 소계를 모아 전체 합계를 내는 것 |

## 깊이 이해

### 뱅크 병렬성이 왜 속도를 올리는가 (수치로 이해)
- D램은 원래도 여러 개의 뱅크(예: 16개)로 나뉘어 있고, 뱅크마다 독립적으로 읽고 쓸 수 있다. 문제는 기존 구조에서는 이 뱅크들이 결국 **하나의 좁은 외부 버스**로 데이터를 내보내야 해서, 아무리 뱅크가 많아도 밖으로 나가는 통로에서 정체가 생겼다.
- PIM은 각 뱅크에 PCU를 붙여, 데이터를 밖으로 안 보내고 뱅크 안에서 바로 계산을 끝낸다. 단순화해서 예를 들면, 16개 뱅크가 각자 자기 몫(전체 데이터의 1/16)을 동시에 처리하면, 이론상 그 구간의 유효 처리량은 뱅크 1개가 순차로 처리할 때보다 최대 16배까지 늘어날 수 있다 — 실제로는 PCU 성능·전력 제약 때문에 이보다는 낮지만, 이 "동시에 여러 뱅크가 일한다"는 구조가 성능 향상의 근원이다.
- 이 원리가 실제 HBM-PIM 제품에서 AI 추론 성능 약 2.0~2.5배 향상, 에너지 소모 50~70% 절감이라는 결과로 나타난다(Ⅳ 참조) — 뱅크 병렬 연산으로 계산을 끝내고 압축된 결과만 내보내니 이동시켜야 할 데이터량 자체가 확 줄기 때문이다.

### PIM Instruction과 Local Data Path — 명령은 가고 데이터는 안 간다
- 호스트가 보통의 메모리 read/write 대신 **PIM Instruction**(예: "뱅크 0~15의 값을 다 더해라")을 보내면, 메모리 컨트롤러가 이를 일반 명령과 구분해 PIM 모드로 전환한다.
- 각 뱅크의 PCU는 뱅크 내부의 **Local Data Path**로 데이터를 끌어와 FMA(곱셈+덧셈) 연산을 수행한다. 이 경로는 칩 외부 핀을 전혀 거치지 않으므로, 외부 버스보다 훨씬 넓은 대역폭을 쓸 수 있고 전력도 적게 든다.
- 각 뱅크의 부분 결과는 **Reduction** 단계에서 하나로 합쳐진 뒤, 이 최종 결과값(원본 데이터보다 훨씬 작음)만 시스템 버스를 타고 CPU로 나간다.

### 어떤 연산에 PIM이 어울리는가 — 판별 원리
- 연산의 성격은 "계산이 많은가(Compute-Bound)" 또는 "옮길 데이터가 많은가(Data-Bound)"로 나뉜다. 이를 가르는 척도가 **연산 강도(Arithmetic Intensity = 연산 횟수 ÷ 이동 바이트 수)**다.
- 연산 강도가 낮다는 것은 "계산 한 번 할 때마다 옮겨야 할 데이터가 상대적으로 많다"는 뜻이며, 이런 워크로드(대규모 행렬-벡터 곱, 임베딩 조회 등)가 PIM에 최적이다. 반대로 복잡한 분기·제어 로직이 많은 연산은 여전히 CPU/GPU가 담당해야 한다.
- 그래서 답안 Ⅴ에서 "데이터 집약도(Intensity)가 높은 워크로드일수록 PIM 도입 효과가 크다"고 판정 기준을 잡는 것이다.

### 비유와 흔한 오해
- **비유**: 대형 물류창고에서 각 구역(뱅크)마다 소형 분류 로봇(PCU)을 배치해, 본사(CPU)로 전체 화물을 보내는 대신 각 구역이 알아서 분류·집계한 요약 보고서만 본사로 보내는 것과 같다.
- **오해**: "PIM은 메모리가 CPU를 완전히 대체한다"는 틀렸다. PCU는 단순 반복 연산(FMA 등)만 하고, 조건 분기나 복잡한 로직 제어는 여전히 호스트 CPU/GPU의 몫이다.

## 연결 개념
- 폰 노이만 병목 (Memory Wall) — PIM이 해소하려는 근본 문제
- PNM (Processing Near Memory) — 뱅크 '내부'가 아니라 메모리 칩 '외부' 인접 영역에서 연산하는 대안 (034에서 상세)
- 데이터 중심 컴퓨팅 (Data-Centric Computing) — PIM이 속한 상위 설계 패러다임
- 연산 강도(Arithmetic Intensity)·Roofline 모델 — 어떤 연산을 PIM에 오프로딩할지 판별하는 기준

# 📝 【답안용】 시험 답안 템플릿

> 목적: 시험장에서 25분에 그대로 쓰는 답안 양식. 

## 핵심 인사이트 (3줄 요약)

> 1. **본질**: PIM(Processing-In-Memory)은 메모리 반도체 내부에 병렬 연산 로직(MAC)을 집적하여 폰 노이만 아키텍처의 근원적 물리 분리를 파괴한 지능형 메모리 솔루션이다.
> 2. **가치**: 데이터를 호스트(CPU/GPU)로 이동시키지 않고 메모리 내부에서 자체 처리(In-situ Processing)함으로써, 데이터 이동에 소모되는 대역폭 병목과 전력 낭비를 70% 이상 극적으로 절감한다.
> 3. **판단 포인트**: PIM 하드웨어의 파괴력에도 불구하고, 이를 활용하기 위해서는 기존 컴파일러와 프로그래밍 모델(CUDA 등)을 PIM 친화적으로 뜯어고쳐야 하는 S/W 생태계 변환 오버헤드가 최대 제약 사항이다.

## 출제 의도 및 답안 포인트

| 출제 의도 | 반드시 짚을 핵심 | 감점 회피 포인트 |
|:---|:---|:---|
| 폰 노이만 병목 해소를 위한 차세대 메모리 융합 아키텍처 파악 | 연산과 저장의 융합, 데이터 이동 최소화(전력 절감) 원리 | 단순히 "메모리가 CPU 역할을 다 한다"고 과장되게 서술하는 오류 (단순 행렬 연산 위주임) |
| 내부 연산 회로 구조와 AI 워크로드(행렬) 매칭 이해 | MAC(곱셈누산기) 유닛 내장, HBM과의 결합(HBM-PIM) | PIM과 PNM(근접 처리)을 명확히 구분하지 않고 혼용 서술 |

> 요약: PIM의 핵심 가치는 "속도가 빨라진다"를 넘어서 "데이터를 옮기지 않아 전력 소모(TCO)를 획기적으로 줄인다"에 있음을 경제학적 비용 관점에서 강조해야 한다.

## Ⅰ. 개요 및 필요성

- 정의: 프로세서(CPU/GPU)가 수행하던 연산 기능의 일부(행렬 곱 등)를 메모리 반도체 칩 내부(Die)로 가져와, 데이터 저장과 연산을 동시에 수행하는 차세대 융합 지능 반도체
- 배경: AI 신경망 등 대규모 파라미터 처리 시, 프로세서 연산 속도는 높으나 데이터가 인터페이스 버스(PCIe, 메모리 버스)를 건너오며 발생하는 물리적 병목 및 에너지 낭비(Memory Wall) 극심화
- 필요성: 폰 노이만 구조의 근원적 한계인 '데이터 이동(Data Movement)' 오버헤드를 원천 제거하여 초저전력·초고속 대규모 병렬 데이터 처리를 실현하기 위함

## Ⅱ. 구조 및 구성요소 (메모리 뱅크 + 연산기 융합 다이)

```text
[HBM-PIM 기반 칩 내부(In-Memory) 물리적 논리 구조]
+-------------------------------------------------+
|   [ Memory Bank 0 ]   <->  [ PCU (PIM 연산 유닛) ] |
|   [ Memory Bank 1 ]   <->  [ PCU (PIM 연산 유닛) ] |
+-------------------------------------------------+
|   [ Global Control Logic / Command Decoder ]    |
+-------------------------------------------------+
|   [ 외부 인터페이스 버스 (GPU와 통신, 트래픽 극소화) ]|
+-------------------------------------------------+
```

| 구성요소 | 핵심 역할 | 상세 하위 요소 / 특징 |
|:---|:---|:---|
| PCU (Programmable Computing Unit) | PIM의 핵심 연산 엔진 | AI 연산의 90% 이상인 MAC(Multiplier-Accumulator, 곱셈-누산) 회로 중심의 소형 ALU 탑재 |
| Memory Bank | 실제 데이터 저장소 | PCU와 일대일 또는 다대일로 결합되어 내부 데이터 버스로 직접 통신 |
| Command Decoder | 호스트(GPU)의 PIM 명령 해석 | PIM 명령어(행렬 곱 등)를 수신하여 일반 메모리 읽기/쓰기 신호와 분리 후 PCU 구동 |
| Host 인터페이스 | PIM 미적용 데이터와 결과값 전송 | 연산된 콤팩트한 결과(스칼라/축소된 텐서)만 외부 핀으로 전송 |

> 요약: PIM은 거대한 메모리 다이(Die) 곳곳에 수백 개의 마이크로 연산기(PCU)를 촘촘히 심어 넣어, 내부에서 초병렬 연산이 쏟아져 나오게 만든 구조다.

## Ⅲ. 동작원리 및 연산 분산 마이크로 흐름도

```text
[GPU 호스트와 PIM 간의 데이터-명령 오프로딩 마이크로 흐름]
1. GPU(호스트) -> PIM으로 [행렬-벡터 곱셈(GEMM) 연산 명령어] 하달
2. PIM 내부 디코더 -> 해당 명령어를 가로채어 각 뱅크의 PCU 활성화
3. (데이터 이동 0) -> 각 PCU가 자기 옆의 뱅크에서 데이터를 바로 꺼내 MAC 연산 수행
4. 각 PCU의 계산 결과들을 취합(Accumulate)
5. PIM 메모리 -> GPU(호스트)로 [최종 산출된 작은 결과값]만 전송 
```

| 처리 주체 | 폰 노이만 (기존 메모리) | PIM 아키텍처 | 동작 효과 판단 |
|:---:|:---|:---|:---|
| 데이터 전송량 | 파라미터 수 TB 전체가 버스 횡단 | 연산 결과 수 MB만 버스 횡단 | I/O 병목 및 버스 트래픽 극적 소멸 |
| 연산 병렬성 | GPU 내부 코어 수에 의존 | 메모리 내부 뱅크 수백 개가 동시 가동 | 극한의 내부 대역폭 100% 활용 |
| 전력 소모(pJ/bit)| 버스 이동에 수백 pJ(피코줄) 낭비 | 칩 내부 이동으로 수십 pJ로 급감 | 에너지 효율성(Performance/Watt) 70%↑ |

> 요약: PIM은 "명령어가 데이터로 찾아가는(Compute moves to data)" 진정한 데이터 중심 컴퓨팅(Data-Centric Computing)의 실현이다.

## Ⅳ. 심화 비교: 폰 노이만 아키텍처 vs PIM 대조표

| 구분 | 폰 노이만 (Von Neumann) 아키텍처 | PIM (Processing-in-Memory) 아키텍처 | 시스템 평가 기준 |
|:---|:---|:---|:---|
| 설계 철학 | 연산(Processor)과 저장(Memory)의 엄격한 분리 | 연산과 저장의 공간적 융합 (In-situ) | 물리적 레이아웃 |
| 성능 병목점 | 메모리 대역폭 한계 (Memory Wall) | 연산 유닛(MAC) 집적도로 인한 발열 및 면적 | 아키텍처 페인 포인트 |
| 명령어 제어 | 호스트 CPU가 모든 명령어 A~Z까지 통제 | 호스트는 큰 명령만 하달, 디테일은 PIM이 처리 | 제어 복잡성 오프로딩 |
| S/W 프로그래밍 | 표준 C/C++, CUDA 등으로 완벽히 추상화됨 | PIM 전용 API 및 커스텀 컴파일러 튜닝 필수 | 생태계 진입 장벽 (단점) |

> 요약: 하드웨어 구조는 PIM이 압도적으로 우수하나, 지난 70년간 폰 노이만 구조 위에서 쌓아 올린 방대한 소프트웨어 제국을 수정해야 한다는 거대한 허들이 존재한다.

## Ⅴ. 제약 사항 및 프로그래밍 모델 호환성 병목

| 리스크 | 발생 원인 (생태계 한계) | 아키텍처 대응 방안 및 표준화 | 극복 원리 및 전망 |
|:---|:---|:---|:---|
| 소프트웨어 재작성 | 기존 텐서플로우/파이토치 코드가 PIM 연산 유닛을 인식하지 못함 (전용 명령어 부재) | **PIM-API 추상화 및 오픈 생태계** | SYCL 기반 개방형 컴파일러나 드라이버 단에서 기존 AI 코드를 PIM 명령어로 자동 트랜스파일링(Transpiling) |
| 다이(Die) 면적 포화 | 메모리 셀이 들어가야 할 자리에 연산 로직(PCU)이 들어가 전체 메모리 용량 밀도(Density) 15~20% 하락 | **3D 칩렛(Chiplet) 분리 적층** | HBM4 Base Die처럼 아예 로직(파운드리) 층과 메모리 층을 분리 적층하여 용량 침해 없이 융합 |
| 발열(Thermal) 붕괴 | 메모리 칩은 본래 발열을 고려 안 한 구조인데, 내부에 연산기(PCU)가 돌면서 칩이 녹아내림 | 첨단 방열 패키징(Advanced MR-MUF 등) 연계 | 열전도율이 높은 소재로 메모리 내부 연산열을 즉각 발산 |

> 요약: PIM 하드웨어를 아무리 잘 만들어도 NVIDIA CUDA처럼 프로그래머가 클릭 한 번에 PIM을 활성화할 수 있는 S/W 스택이 없으면 시장에서 외면받는다.

## Ⅵ. 실무 적용 및 결론

**적용 방안 3개:**
1. LLM 추론(Inference) 서버 폼팩터 전면 교체: 대형 언어 모델 추론은 훈련(Training)과 달리 지연 시간(Latency) 최소화가 관건이므로, 기존 범용 GPU 클러스터를 Samsung HBM-PIM 액셀러레이터로 교체하여 Memory-Bound로 인한 응답 지연을 해소하고 서버 전력 비용(TCO)을 50% 이상 감축
2. 추천 시스템(Recommendation System) 인메모리 처리: 페이스북 DLRM 등 방대한 임베딩 테이블(Embedding Table)을 무작위로 긁어오는 무거운 추천 알고리즘 운영 시, CXL 메모리 풀링 장비 칩 내부에 PIM 유닛(CXL-PNM/PIM)을 장착하여 호스트 CPU 개입 없이 거대 테이블 검색 연산을 자체 종결
3. 온디바이스(On-Device) AI 엣지 튜닝: 스마트폰이나 스마트워치 NPU 설계 시 배터리 제약을 극복하기 위해, 메인 LPDDR 내부에 소형 PIM 회로(LPDDR-PIM)를 설계 통합하여 카메라 비전 AI 파라미터 연산을 메모리단에서 저전력으로 실시간 처리

**결론 (2줄):**
- 기술사 판단: PIM은 폰 노이만 아키텍처의 70년 철칙을 깨부순 반도체 공학의 패러다임 시프트이며, 무어의 법칙 종료 이후 시스템 스케일업(Scale-up)을 견인할 유일한 하드웨어 대안이다.
- 향후 방향: 초기 HBM-PIM 단계를 넘어, HBM4의 3D Logic Base Die 구조, 그리고 궁극적으로는 데이터 자체에 연산 능력이 부여된 뉴로모픽(Neuromorphic) 인메모리 컴퓨팅으로 완전한 진화를 이룰 것이다.
