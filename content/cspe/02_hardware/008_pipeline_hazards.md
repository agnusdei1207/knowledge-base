# 📖 【암기용】 개념 완전 이해

> 목적: 파이프라인 해저드를 처음 봐도, 그리고 RAW·WAR·WAW·Stall·Bubble·Flush 같은 내부 용어까지 전부 완벽히 이해하게 만든다.

## 한눈에
- **개요**: **명령어 파이프라이닝(007)**에서 여러 명령어를 겹쳐 실행할 때, 자원 충돌·데이터 의존성·분기 불확실성 때문에 정상적인 흐름이 깨지는 충돌 현상이다.
- **왜 필요한가**: 파이프라인은 매 클럭 결과 1개(CPI=1.0)를 내야 이상적인데, 실제 명령어는 서로 자원을 나눠 쓰고 앞뒤로 값을 주고받고 분기로 갈라지므로 그 흐름이 자주 막힌다. 이 "막힘"의 정체를 알아야 CPU 실제 성능의 한계를 설명할 수 있다.
- **핵심 직관**: 공장 컨베이어처럼 명령어를 흘려보내는데, 같은 도구를 동시에 쓰려 하거나(구조적), 앞 작업 결과를 뒤 작업이 기다리거나(데이터), 다음에 뭘 만들지 몰라 멈추면(제어) 라인이 정지한다.

## 핵심 용어 정리 (내부에 등장하는 것들)

| 용어 | 의미 | 비유 |
|:---|:---|:---|
| 파이프라이닝 | 명령어를 여러 단계로 나눠 겹쳐 실행하는 기법 — 해저드가 발생하는 **상위 무대** | 컨베이어 벨트 공정 |
| 구조적 해저드(Structural) | 두 명령어가 같은 하드웨어 자원(메모리 포트·ALU)을 동시에 요구 | 칼 하나를 두 요리사가 동시에 쓰려 함 |
| 데이터 해저드(Data) | 명령어 사이의 값 의존성 때문에 순서를 지켜야 하는 충돌 | 앞사람이 만든 소스를 기다림 |
| RAW (Read After Write) | 뒤 명령이 앞 명령의 "쓰기 결과"를 읽어야 함 — 데이터 해저드의 대표 유형 | 소스가 완성되기 전엔 못 담음 |
| WAR (Write After Read) | 뒤 명령이 쓰기 전에 앞 명령이 그 값을 먼저 읽어야 함 | 손님이 다 먹기 전에 접시를 치우면 안 됨 |
| WAW (Write After Write) | 두 명령이 같은 곳에 쓰는데, 순서가 바뀌면 최종값이 틀어짐 | 같은 칠판에 두 사람이 답을 적는데 순서가 꼬임 |
| 제어 해저드(Control) | 분기·점프로 다음에 인출할 명령어 주소가 불확실해지는 충돌 | 다음 손님 주문이 뭔지 몰라 조리를 못 시작함 |
| Stall (스톨) | 의존성·자원 충돌 해소를 위해 파이프라인을 일시 정지시키는 것 | 재료가 없어 요리사가 잠깐 대기 |
| Bubble (버블) | Stall로 생긴, 아무 일도 하지 않는 빈 파이프라인 슬롯 | 컨베이어 벨트 위의 빈 칸 |
| Flush (플러시) | 분기 예측이 틀렸을 때 잘못 인출된 명령어들을 통째로 버리는 것 | 잘못 만든 요리를 폐기 |
| Forwarding(포워딩) | WB를 기다리지 않고 EX 결과를 바로 다음 명령의 입력으로 넘기는 회로 | 완성 전 반찬을 바로 옆자리에 건넴 |
| 레지스터 리네이밍 | 같은 이름의 레지스터를 물리적으로 다른 레지스터에 매핑해 WAR/WAW를 원천 제거 | 같은 이름 예약을 다른 테이블로 분산 배정 |

## 깊이 이해

### 배경 — 이상적 CPI 1.0이 무너지는 이유
- 5단 파이프라인(IF·ID·EX·MEM·WB)은 이론상 처리량이 5배이지만, 이는 명령어들이 서로 완전히 독립적일 때만 성립한다. 실제 프로그램은 앞 명령의 결과를 뒤 명령이 바로 쓰고, 조건 분기가 수시로 등장하므로 실제 CPI는 1.0을 넘어서게(느려지게) 된다.

### 구조적 해저드 — 자원 충돌
- 한 예로 명령어 캐시와 데이터 캐시가 분리되지 않은 CPU라면, IF 단계(명령어 인출)와 MEM 단계(데이터 접근)가 같은 클럭에 같은 메모리 포트를 동시에 요구해 충돌한다.
- 해소법은 자원을 아예 복제하는 것이다. L1 캐시를 I-Cache(명령어 전용)와 D-Cache(데이터 전용)로 분리하는 **하버드 구조**가 대표적이며, 이러면 구조적 해저드가 설계 단계에서 제거된다.

### 데이터 해저드 — RAW·WAR·WAW를 수치로 구분
- **RAW(대표 유형)**: `ADD R1,R2,R3` 직후 `SUB R4,R1,R5`가 오면, SUB는 ADD가 R1에 쓴 값을 곧바로 읽어야 한다. 포워딩이 없으면 ADD가 WB(5단계)를 마칠 때까지 SUB가 EX(3단계)를 시작하지 못해 **3사이클을 손해**본다. 포워딩 회로(EX/MEM, MEM/WB 경로)를 두면 ADD의 EX 결과를 즉시 SUB의 EX 입력으로 꽂아 넣어 **0사이클**로 줄일 수 있다.
- **WAR**: `MUL R5,R1,R2` 다음에 `ADD R1,R3,R4`가 오면, ADD가 R1에 새 값을 쓰기 전에 MUL이 기존 R1 값을 먼저 읽어야 한다. 순서가 뒤바뀌면 MUL이 잘못된 새 값을 읽는다. 표준 5단 순차 파이프라인에서는 ID 단계에서 읽기가 일찍 끝나 WAR이 잘 발생하지 않지만, 비순차 실행(OoO)에서는 실제로 문제가 되어 레지스터 리네이밍으로 해결한다.
- **WAW**: 두 명령이 같은 레지스터에 쓰기를 하는데 실행 순서가 뒤섞이면(OoO 환경), 나중에 실행됐어야 할 값이 먼저 쓰여 최종 결과가 틀어진다. 이 역시 레지스터 리네이밍으로 물리 레지스터를 분리해 제거한다.

### 제어 해저드 — 분기 불확실성
- `if (a > b)` 같은 조건 분기는 결과가 EX 단계에서야 확정되므로, 그 전까지 IF 단계는 다음에 어떤 명령어를 가져와야 할지 알 수 없다.
- 아무 대응이 없으면 분기 결과가 나올 때까지 IF를 멈춰야(Stall) 하고, 이는 파이프라인이 깊을수록 손해가 커진다. 그래서 대부분의 CPU는 결과를 추측해 먼저 실행(투기적 실행)하고, 틀리면 진행분을 통째로 버리는(Flush) 방식을 쓴다 — 이 예측 메커니즘이 분기 예측(009)이다.

### 비유로 한 번에 정리
- 요리사 5명이 차례로 한 접시를 만든다. 칼 하나를 둘이 쓰려 하면(구조적) 한 명이 기다린다. 2번 요리사가 1번의 소스(결과값)를 기다리면(데이터-RAW) 줄이 선다. 1번이 아직 안 쓴 재료를 2번이 먼저 치우면(데이터-WAR) 재료가 사라진다. 다음 손님 주문이 뭔지 모르면(제어) 일단 추측해서 만들다가, 틀리면 버린다(Flush).

### 흔한 오해
- "파이프라인 단(stage)을 늘리면 무조건 빨라진다"는 틀렸다. 단이 깊을수록 분기 예측이 틀렸을 때 버려야 할 명령어 수(Flush 페널티)가 커져, 제어 해저드로 인한 손실이 오히려 커질 수 있다.
- "포워딩이 모든 데이터 해저드를 0사이클로 없앤다"도 틀렸다. Load 명령 직후 그 값을 바로 쓰는 Load-Use 상황은 데이터가 MEM 단계에서야 나오므로, 포워딩을 써도 최소 1사이클 Stall이 남는다.

## 연결 개념
- 파이프라이닝(007) — 해저드가 발생하는 무대가 되는 상위 개념
- 데이터 포워딩·분기 예측(009) — 데이터·제어 해저드를 각각 해소하는 핵심 기법
- 레지스터 리네이밍 — WAR/WAW 해저드를 원천 제거하는 기법
- 비순차 실행(OoO) — 리네이밍을 기반으로 ILP를 극대화하는 실행 방식

# 📝 【답안용】 시험 답안 템플릿

> 목적: 시험장에서 25분에 그대로 쓰는 답안 양식. 작성방식(추상표현 금지·수치·도식·문제유형 전환)을 엄격히 지킨다.
> 핵심: 해저드 종류를 나열하는 답안이 아니라, 출제자가 묻는 병목 원인과 해소 기법을 구분해 CPI 손실 통제 관점으로 답안을 구성한다.

## 핵심 인사이트 (3줄 요약)

> 1. **본질**: 파이프라인 해저드 (Pipeline Hazards)는 여러 명령어를 겹쳐 흘려보낼 때 자원 충돌·데이터 의존성·분기 불확실성으로 이상적인 흐름이 깨지는 병목 현상이다.
> 2. **가치**: 실제 CPI (Cycles Per Instruction)는 단계 수보다 스톨(Stall)·버블(Bubble)·플러시(Flush)를 얼마나 줄이느냐에 의해 결정된다.
> 3. **판단 포인트**: 구조적·데이터·제어 해저드는 원인이 다르므로 자원 복제·포워딩·분기 예측·컴파일러 스케줄링을 각각 다른 처방으로 적용해야 한다.

## 출제 의도 및 답안 포인트

| 출제 의도 | 반드시 짚을 핵심 | 감점 회피 포인트 |
|:---|:---|:---|
| 파이프라인 성능 저하 원인 분류 역량 확인 | 구조적·데이터·제어 해저드 원인과 Stall·Forwarding·Flush 연결 | 해저드 3종을 이름만 쓰고 CPI 영향·해소 기법을 빠뜨림 |
| 하드웨어/컴파일러 공동 최적화 판단 확인 | 자원 복제, 포워딩 경로, 분기 예측, 명령어 스케줄링 선택 기준 | 단 수 증가를 성능 향상으로 단정 |
| 현대 CPU 설계 리스크 인식 확인 | 분기 miss penalty, load-use stall, 투기 실행 보안 취약점 | 보안 격리와 성능 최적화의 트레이드오프 누락 |

> 요약: 이 문제는 해저드 명칭 암기가 아니라 CPI 손실 원인별 처방과 검증 지표를 연결하는 판단력을 요구한다.

## Ⅰ. 개요 및 필요성

- 정의: 명령어 파이프라이닝(Instruction Pipelining)에서 여러 명령어가 동시에 흐를 때 정상 진행을 방해하는 충돌 조건
- 배경: 5단 파이프라인은 매 클럭 결과 1개를 내야 이상적이지만, 실제 프로그램은 자원 공유·데이터 의존·분기로 인해 이 흐름이 깨짐
- 필요성: 해저드가 많으면 고주파 CPU도 실제 성능이 기대를 밑돌므로, 파이프라인 설계는 단계 분리보다 충돌 방지 메커니즘 설계가 핵심

---

## Ⅱ. 구조 및 구성요소

```text
Instruction Pipeline
  / Structural Hazard: 자원 충돌
  / Data Hazard: RAW / WAR / WAW 의존성
  / Control Hazard: 분기·점프·예외로 인한 다음 PC 불확실
Hazard Detection -> Stall / Forwarding / Flush -> CPI 손실 통제
```

| 구성요소 | 개요 | 주요 원인 |
|:---|:---|:---|
| 구조적 해저드 (Structural) | 두 명령어가 같은 하드웨어 자원을 동시에 요구 | 단일 메모리 포트, 단일 ALU |
| 데이터 해저드 (Data) | 선행 명령어 결과를 후속 명령어가 즉시 필요 | RAW·WAR·WAW 의존성 |
| 제어 해저드 (Control) | 분기·점프로 인해 다음 인출 주소가 불확실 | 조건 분기·예외·인터럽트 |

> 요약: 해저드는 자원(구조적)·데이터 의존(데이터)·흐름 불확실(제어) 세 종류로 분류되며, 각 종류는 발생 원인과 해소 방법이 다르다.

---

## Ⅲ. 동작원리 및 흐름도

```text
명령어 IF -> ID -> EX -> MEM -> WB
  -> ID/EX 단계 해저드 감지
  -> 구조적: 자원 충돌 확인 -> Stall 또는 자원 복제
  -> 데이터: 의존 레지스터 확인 -> Forwarding 또는 Load-Use Stall
  -> 제어: 분기 결과 확인 -> 예측 유지 또는 Flush
  -> CPI, flush count, branch miss rate 측정
```

| 단계 | 처리 내용 | 해소 기법 |
|:---:|:---|:---|
| 1 | IF 단계에서 PC 기반 명령어 인출 | BTB, BHT, I-Cache |
| 2 | ID 단계에서 소스·목적 레지스터 의존성 확인 | Forwarding 경로 판단, Stall 발행 |
| 3 | EX 단계에서 ALU·분기 결과 확정 | 자원 복제, 빠른 분기 판정 |
| 4 | MEM 단계에서 Load-Use 충돌 확인 | 1사이클 Stall, 컴파일러 스케줄링 |
| 5 | 예측 오류 명령 제거 및 PC 복구 | Flush, pipeline redirect |

> 요약: 해저드는 IF/ID/EX/MEM 각 단계에서 감지되며, 데이터 해저드는 forwarding, 제어 해저드는 branch prediction과 flush로 통제한다.

## Ⅳ. 특징

| 구분 | 구조적 해저드 | 데이터 해저드 | 제어 해저드 |
|:---|:---|:---|:---|
| 발생 조건 | 자원 공유 | RAW·WAR·WAW 의존 | 분기·점프·예외 |
| 주요 해소법 | 자원 복제, Stall | 데이터 포워딩, Stall | 분기 예측, Flush |
| 정량 영향 | 단일 메모리 포트 시 IF/MEM 충돌 | Load-Use 1사이클 Stall | 예측 실패 5~20사이클 flush |
| 기술사 포인트 | 분리 I-Cache/D-Cache | RAW는 포워딩, WAR/WAW는 레지스터 리네이밍 | 동적 예측 vs 정적 예측 트레이드오프 |

> 요약: 제어 해저드가 성능 영향이 가장 크며, 현대 CPU는 TAGE 등 다단 동적 분기 예측기로 97~99% 적중률을 달성하여 플러시 빈도를 최소화한다(2비트 BHT 단독은 85~92%).

## Ⅴ. 심화 비교 및 적용 판단

| 비교 축 | 기존/대안 | 본 키워드 | 선택 기준 |
|:---|:---|:---|:---|
| 구조 | 단일 사이클 CPU | 5단 이상 파이프라인 | 명령어 처리량 목표 IPC 1.0 근접 시 적용 |
| 비용/성능 | 자원 복제 없음 | I/D Cache 분리, forwarding path 추가 | 면적 증가 대비 Stall cycle 감소 |
| 운영/위험 | 단순 제어 | 예측·flush·interlock 복합 제어 | 검증 비용과 분기 miss penalty 동시 판단 |

> 요약: 파이프라인은 클럭 주파수만이 아니라 Stall cycle, branch miss rate, forwarding coverage를 함께 봐야 선택 가능하다.

| 리스크 | 원인 | 대응 방안 | 확인 지표 |
|:---|:---|:---|:---|
| Load-Use Stall | Load 결과가 MEM 이후 확정 | MEM/WB forwarding, compiler scheduling | load-use stall per kilo-instruction |
| Branch Flush | 분기 결과 지연 확정 | BHT+BTB, early branch resolution | branch miss rate 5% 이하 |
| 검증 누락 | forwarding·stall 조건 조합 폭증 | SystemVerilog assertion, directed test | RAW/WAR/WAW coverage 100% |

> 요약: 해저드 설계의 핵심 리스크는 성능보다 검증 누락이며, 의존성 조합별 coverage로 통제해야 한다.

| 점검 항목 | 목표 기준 | 측정 방법 |
|:---|:---|:---|
| CPI | 기준 workload CPI 1.0~1.3 | cycle simulator, RTL simulation |
| 분기 예측 | branch prediction accuracy 95% 이상 | SPECint branch trace 분석 |
| Stall 비율 | stall cycle 전체 cycle의 10% 이하 | performance counter, waveform |

> 요약: 도입 효과는 CPI, 분기 예측률, stall cycle 비율로 측정하고, 세 지표가 동시에 개선될 때 유효하다.

## Ⅵ. 실무 적용 및 결론

**적용 방안 3개:**
1. 데이터 해저드: EX/MEM·MEM/WB 포워딩 경로 구현으로 RAW 스톨 지연을 3사이클 → 0사이클로 단축 (단, Load-Use는 1사이클 잔존)
2. 제어 해저드: 2비트 포화 카운터 BHT(Branch History Table) + BTB로 분기 적중률 95% 이상 확보, 플러시 빈도 최소화
3. 컴파일러 협력: 명령어 재배치(Instruction Scheduling)·지연 분기(Delayed Branch)로 잔여 버블을 정적으로 흡수

**결론 (2줄):**
- 기술사 판단: 파이프라인 성능 = IPC × 클럭 주파수이며, 단(stage) 수가 얕으면(5~8단) 정적 예측+간단한 BTB, 깊으면(12단 이상) 다단 동적 예측+OoO를 선택한다
- 향후 방향: Meltdown·Spectre 이후 투기적 실행의 보안 취약점이 부각되어, 해저드 해소와 보안 격리(예: IBRS, Retpoline)를 동시에 설계해야 한다
