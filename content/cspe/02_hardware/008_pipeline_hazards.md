# 008. 파이프라인 해저드 — 데이터·제어·구조 (Pipeline Hazards) [출제:122,135회]

## 미리 알고가기

- **스톨 (Stall)**: 해저드 해결을 위해 파이프라인 진행을 1클록 이상 멈추는 현상임
- **버블 (Bubble)**: 스톨로 인해 파이프라인 중간에 생기는 '아무것도 하지 않는 빈 슬롯'임
- **데이터 의존성 (Data Dependency)**: 어떤 명령어의 결과가 다음 명령어의 입력으로 쓰이는 관계임

## Ⅰ. 개요

- **정의/개념**: 파이프라인 해저드(Hazard)는 다음 명령어가 다음 클록에 실행될 수 없는 상황을 의미하며, 파이프라인의 이상적인 병렬 처리를 방해하여 성능을 저하시키는 핵심 요인임
- **배경/필요성**: 여러 명령어가 동시에 서로 다른 단계를 점유하므로, 자원 충돌이나 데이터 미확정, 분기 결과 미정 등의 문제가 필연적으로 발생함. 이를 해결하지 않으면 잘못된 연산 결과가 나오거나 시스템이 멈출 수 있음

## Ⅱ. 특징 및 비교

해저드는 원인에 따라 구조적, 데이터, 제어 세 가지로 분류되며 대응 방식이 각기 다름.

| 구분 | 구조적 해저드 (Structural) | 데이터 해저드 (Data) | 제어 해저드 (Control) |
|:---|:---|:---|:---|
| **발생 원인** | 두 명령어가 **동일한 하드웨어 자원**을 요구함 | 앞 명령어의 **연산 결과가 아직 준비 안 됨** | **분기(Branch)** 결과에 따라 실행 경로가 바뀜 |
| **대표 상황** | IF와 MEM이 같은 메모리 버스를 사용함 | ADD 연산 직후 그 결과를 읽는 명령 실행 | IF 단계에서 다음 주소를 결정 못 함 |
| **대응 기법** | 자원 추가 (하버드 구조), 스케줄링 | **포워딩 (Forwarding)**, 스톨, 리네이밍 | **분기 예측**, 지연 분기, 스톨 |

> 요약: 자원 싸움은 '구조', 값 싸움은 '데이터', 길 찾기 싸움은 '제어' 해저드임.

## Ⅲ. 구성요소/구조

해저드 탐지 및 해결 로직은 CPU의 제어부(CU) 내부에 복잡하게 얽혀 있음.

- **데이터 해저드 세부 유형**:
  - **RAW (Read After Write)**: 앞의 쓰기 결과를 뒤에서 읽어야 함 (가장 흔한 해저드)
  - **WAR (Write After Read)**: 앞의 읽기 전에 뒤에서 써버림 (비순서 실행 시 발생)
  - **WAW (Write After Write)**: 앞의 쓰기 전에 뒤에서 써버림 (비순서 실행 시 발생)

- **해저드 해결을 위한 포워딩 구조 (ASCII)**:

```text
[Pipeline with Forwarding Path]
       +-----+      +-----+      +-----+      +-----+
Inst 1 | IF  |----->| ID  |----->| EX  |--+-->| MEM |--+--> [WB]
       +-----+      +-----+      +--^--+  |   +-----+  |
                                    |     |            |
       +-----+      +-----+      +--|--+  | Forwarding |
Inst 2 |     | IF  |----->| ID  |----->| EX  | <---+--------+
       +-----+      +-----+      +-----+               |
                                                       |
        (결과가 나올 때까지 기다리지 않고, EX/MEM 단계에서 바로 전달)
```

1. **Forwarding Unit**: 연산 결과가 나오는 즉시 이를 다음 명령어의 입력(ALU input)으로 우회 전달함
2. **Hazard Detection Unit**: 명령어 간의 레지스터 번호를 비교하여 스톨을 삽입할지 결정함

## Ⅳ. 문제점 및 개선방안

1. **파이프라인 버블로 인한 CPI 증가**: 스톨이 자주 발생하면 이상적인 $CPI=1$을 달성하지 못하고 성능이 하락함
   - **개선방안**: 컴파일러 수준에서 명령어 순서를 재배치(Code Reordering)하여 의존성을 떨어뜨리거나, 하드웨어적으로 **비순서 실행(OoO)**을 지원함 (확인: CPI 지표)

2. **분기 예측 실패 시 패널티 (Flush)**: 잘못된 방향으로 명령어를 미리 채웠다가 버릴 때(Flush) 발생하는 손실이 큼
   - **개선방안**: 동적 분기 예측(2-bit Predictor, TAGE 등)의 정확도를 높이고, 예측 실패 시 즉시 복구할 수 있는 하드웨어 체크포인트를 마련함 (확인: 분기 오예측률)

3. **구조적 해저드로 인한 하드웨어 비용 증가**: 자원 충돌을 막기 위해 포트를 늘리거나 메모리를 분리하면 다이(Die) 면적과 전력이 늘어남
   - **개선방안**: 통합 메모리 구조를 유지하되 명령어/데이터 캐시를 분리하는 **수정 하버드 구조**를 활용하여 비용 효율성을 확보함 (확인: 단위 면적당 성능)

## Ⅴ. 실무 적용 사례

| 적용 영역 | 적용 방식 | 확인 지표 |
|:---|:---|:---|
| 컴파일러 최적화 | 파이프라인의 특성을 고려하여 `load` 명령어와 그 결과 사용 명령어 사이에 독립적인 연산을 끼워 넣어 스톨 방지 | 명령어 스케줄링 효율, 코드 크기 |
| 고성능 서버 설계 | 수백 개의 명령어를 윈도우에 띄워 놓고 해저드 없는 명령어부터 실행하는 비순서 실행 엔진 탑재 | ILP (Instruction Level Parallelism) |
| 저전력 임베디드 | 복잡한 우회 로직 대신 해저드 발생 시 파이프라인을 멈추는 단순 로직(Interlock)으로 전력 소모 최소화 | 와트당 처리 성능, 로직 게이트 수 |

> 요약: 성능을 원하면 복잡한 우회 로직을, 저전력을 원하면 스톨과 소프트웨어 최적화를 선택함.

## Ⅵ. 결론

파이프라인 해저드는 '병렬화의 역설'로, 성능을 높이기 위해 단계를 나눈 대가로 치러야 하는 기술적 부채임. 기술사는 해저드의 각 유형을 정확히 진단하고, 이를 해결하기 위한 하드웨어 기법(포워딩, 예측)과 소프트웨어 기법(스케줄링)의 상호작용을 깊이 이해해야 함.

특히 최신 아키텍처는 해저드 문제를 해결하기 위해 점점 더 투기적(Speculative)으로 변하고 있으나, 이는 보안 취약점(사이드 채널 공격)이라는 새로운 해저드를 낳고 있음. 따라서 미래의 해저드 해결은 단순히 '빠르게'를 넘어 '안전하고 빠르게'를 목표로 진화해야 함.
