# 📖 【암기용】 개념 완전 이해

## 한눈에
- **개요**: 파이프라인 해저드는 파이프라이닝(007)에서 여러 명령어를 겹쳐 실행할 때 자원 충돌·데이터 의존성·분기 불확실성 때문에 정상 흐름이 깨지는 충돌 현상이다.
- **왜 필요한가**: 파이프라인은 매 클럭 결과 1개(CPI=1.0)를 내야 이상적인데, 실제 명령어는 자원을 나눠 쓰고 앞뒤로 값을 주고받고 분기로 갈라져 흐름이 자주 막힌다. 이 "막힘"의 정체를 알아야 CPU 실제 성능 한계를 설명할 수 있다.
- **핵심 직관**: 컨베이어에 명령어를 흘리는데, 같은 도구를 동시에 쓰려 하거나(구조적), 앞 작업 결과를 뒤가 기다리거나(데이터), 다음에 뭘 만들지 몰라 멈추면(제어) 라인이 정지한다.

## 핵심 용어 정리 (내부에 등장하는 것들)

| 용어 | 의미 | 비유 |
|:---|:---|:---|
| 파이프라이닝 | 명령어를 여러 단계로 나눠 겹쳐 실행하는 기법 — 해저드가 발생하는 상위 무대 | 컨베이어 벨트 공정 |
| 구조적 해저드(Structural) | 두 명령어가 같은 하드웨어 자원(메모리 포트·ALU)을 동시에 요구 | 칼 하나를 두 요리사가 동시에 쓰려 함 |
| 데이터 해저드(Data) | 명령어 사이 값 의존성 때문에 순서를 지켜야 하는 충돌 | 앞사람이 만든 소스를 기다림 |
| RAW (Read After Write) | 뒤 명령이 앞 명령의 쓰기 결과를 읽어야 함 — 데이터 해저드 대표 유형 | 소스가 완성되기 전엔 못 담음 |
| WAR (Write After Read) | 뒤 명령이 쓰기 전에 앞 명령이 그 값을 먼저 읽어야 함 | 손님이 다 먹기 전 접시를 치우면 안 됨 |
| WAW (Write After Write) | 두 명령이 같은 곳에 쓰는데 순서가 바뀌면 최종값이 틀어짐 | 같은 칠판에 두 사람이 적는 순서가 꼬임 |
| 제어 해저드(Control) | 분기·점프로 다음에 인출할 명령어 주소가 불확실해지는 충돌 | 다음 손님 주문을 몰라 조리를 못 시작함 |
| Stall (스톨) | 충돌 해소를 위해 파이프라인을 일시 정지시키는 것 | 재료가 없어 요리사가 잠깐 대기 |
| Bubble (버블) | Stall로 생긴, 아무 일도 안 하는 빈 파이프라인 슬롯 | 컨베이어 위의 빈 칸 |
| Flush (플러시) | 분기 예측이 틀렸을 때 잘못 인출된 명령어를 통째로 버리는 것 | 잘못 만든 요리를 폐기 |
| Forwarding(포워딩) | WB를 기다리지 않고 EX 결과를 다음 명령 입력으로 바로 넘기는 회로 | 완성 전 반찬을 바로 옆자리에 건넴 |
| 레지스터 리네이밍 | 같은 이름 레지스터를 물리적으로 다른 곳에 매핑해 WAR/WAW를 원천 제거 | 같은 이름 예약을 다른 테이블로 분산 |
| 하버드 구조 | 명령어 캐시(I-Cache)와 데이터 캐시(D-Cache)를 분리한 메모리 구조 | 재료 창고와 도구 창고를 따로 둠 |

## 깊이 이해

### 배경 — 이상적 CPI 1.0이 무너지는 이유
- 5단 파이프라인은 이론상 처리량 5배이지만, 이는 명령어들이 완전히 독립적일 때만 성립한다(007 참조). 실제 프로그램은 앞 명령 결과를 뒤가 바로 쓰고 조건 분기가 수시로 나와, 실제 CPI가 1.0을 넘어서(느려져) 버린다.

### 구조적 해저드 — 자원 충돌
- 명령어 캐시와 데이터 캐시가 분리되지 않은 CPU라면, IF 단계(명령어 인출)와 MEM 단계(데이터 접근)가 같은 클럭에 같은 메모리 포트를 동시에 요구해 충돌한다.
- 해소는 자원 복제다. L1을 I-Cache와 D-Cache로 나누는 하버드 구조가 대표이며, 이러면 구조적 해저드가 설계 단계에서 제거된다.

### 데이터 해저드 — RAW·WAR·WAW를 수치로 구분
- **RAW(대표)**: `ADD R1,R2,R3` 직후 `SUB R4,R1,R5`는 ADD가 R1에 쓴 값을 즉시 읽어야 한다. 포워딩이 없으면 ADD가 WB(5단)를 마칠 때까지 SUB의 EX(3단)가 못 시작해 최대 2사이클을 손해 본다. 포워딩 경로를 두면 0사이클로 줄인다(해소 상세는 009).
- **WAR**: `MUL R5,R1,R2` 다음 `ADD R1,R3,R4`는 ADD가 R1에 새 값을 쓰기 전에 MUL이 기존 값을 먼저 읽어야 한다. 표준 순차 5단에서는 ID에서 읽기가 일찍 끝나 잘 안 생기나, 비순차 실행(OoO)에서는 실제 문제가 되어 레지스터 리네이밍으로 해결한다.
- **WAW**: 두 명령이 같은 레지스터에 쓰는데 실행 순서가 뒤섞이면(OoO), 나중 값이어야 할 것이 먼저 쓰여 최종 결과가 틀어진다. 역시 리네이밍으로 물리 레지스터를 분리해 제거한다.

### 제어 해저드 — 분기 불확실성
- `if (a > b)` 같은 조건 분기는 EX 단계에서야 결과가 확정되므로, 그전까지 IF는 다음에 어떤 명령어를 가져올지 알 수 없다.
- 대응이 없으면 결과가 나올 때까지 IF를 멈춰야 하고, 파이프라인이 깊을수록 손해가 커진다. 그래서 결과를 추측해 먼저 실행(투기적 실행)하고 틀리면 진행분을 통째로 버리는(Flush) 분기 예측(009)을 쓴다.

### 흔한 오해
- "단(stage)을 늘리면 무조건 빨라진다"는 틀렸다. 단이 깊을수록 분기 예측 실패 시 버릴 명령어 수(Flush 페널티)가 커져, 제어 해저드 손실이 오히려 커질 수 있다.
- "포워딩이 모든 데이터 해저드를 0사이클로 없앤다"도 틀렸다. Load 직후 그 값을 바로 쓰는 Load-Use는 데이터가 MEM에서야 나와, 포워딩을 써도 최소 1사이클 Stall이 남는다.

## 연결 개념
- 파이프라이닝(007) — 해저드가 발생하는 무대가 되는 상위 개념
- 데이터 포워딩·분기 예측(009) — 데이터·제어 해저드를 각각 해소하는 핵심 기법
- 비순차 실행(OoO)·레지스터 리네이밍 — WAR/WAW를 제거하고 ILP를 극대화하는 실행 방식

# 📝 【답안용】 시험 답안 템플릿

## 핵심 인사이트 (3줄 요약)

> 1. **본질**: 파이프라인 해저드는 여러 명령어를 겹쳐 흘릴 때 자원 충돌·데이터 의존성·분기 불확실성으로 이상 흐름이 깨지는 병목 현상임.
> 2. **가치**: 실제 CPI는 단계 수가 아니라 스톨(Stall)·버블(Bubble)·플러시(Flush)를 얼마나 줄이느냐로 결정됨.
> 3. **판단 포인트**: 구조적·데이터·제어 해저드는 원인이 달라 자원 복제·포워딩·분기 예측·컴파일러 스케줄링을 각각 다른 처방으로 적용해야 함.

## Ⅰ. 개요 및 필요성

- 개요: 명령어 파이프라이닝에서 여러 명령어가 동시에 흐를 때 정상 진행을 방해하는 충돌 조건임
- 배경: 5단 파이프라인은 매 클럭 결과 1개를 내야 이상적이나, 실제 프로그램은 자원 공유·데이터 의존·분기로 이 흐름이 깨짐
- 필요성: 해저드가 많으면 고주파 CPU도 실성능이 기대를 밑돌아, 파이프라인 설계의 핵심은 단계 분리보다 충돌 방지 메커니즘 설계임

---

## Ⅱ. 구조 및 구성요소

```text
[해저드 3종 분류 구조]
Instruction Pipeline (IF -> ID -> EX -> MEM -> WB)
  / 구조적 해저드 : 자원 충돌 (단일 메모리 포트·단일 ALU)
  / 데이터 해저드 : RAW / WAR / WAW 의존성
  / 제어 해저드   : 분기·점프·예외로 다음 PC 불확실
  -> 해저드 감지 -> Stall / Forwarding / Flush -> CPI 손실 통제
```

| 구성요소 | 개요 | 주요 원인 |
|:---|:---|:---|
| 구조적 해저드 (Structural) | 두 명령어가 같은 하드웨어 자원을 동시에 요구 | 단일 메모리 포트, 단일 ALU |
| 데이터 해저드 (Data) | 선행 명령어 결과를 후속 명령어가 즉시 필요 | RAW·WAR·WAW 의존성 |
| 제어 해저드 (Control) | 분기·점프로 다음 인출 주소가 불확실 | 조건 분기·예외·인터럽트 |

> 요약: 해저드는 자원(구조적)·데이터 의존(데이터)·흐름 불확실(제어) 3종으로 분류되며, 종류마다 발생 원인과 해소법이 다름.

---

## Ⅲ. 동작원리 및 흐름도

```text
[해저드 감지 및 통제 흐름]
명령어 IF -> ID(의존성/자원 감지) -> EX(분기 결과 확정) -> MEM -> WB
  -> 구조적 : 자원 충돌 확인  -> Stall 또는 자원 복제
  -> 데이터 : 의존 레지스터 확인 -> Forwarding 또는 Load-Use Stall
  -> 제어   : 분기 결과 확인   -> 예측 유지 또는 Flush
```

- 1단계: IF에서 PC 기반 명령어를 인출하며, BTB·BHT로 분기 여부를 조기 조회함 (주체: 인출 유닛)
- 2단계: ID에서 소스·목적 레지스터 의존성과 자원 요구를 검사해, 포워딩 가능 여부를 판단하거나 Stall을 발행함 (주체: 해저드 감지 로직)
- 3단계: EX에서 ALU·분기 결과를 확정하고, 구조적 충돌은 복제 자원으로 우회함 (주체: 실행 유닛)
- 4단계: MEM에서 Load-Use 충돌을 확인해 1사이클 Stall을 넣거나, 분기 예측 오류 시 진행 명령을 Flush하고 PC를 복구함 (주체: 파이프라인 제어부)

> 요약: 해저드는 ID·EX·MEM 각 단계에서 감지되며, 데이터 해저드는 포워딩·Stall, 제어 해저드는 예측·Flush로 통제함.

## Ⅳ. 특징

- 성능 지표는 IPC × 클럭 주파수이며, 해저드가 IPC를 갉아먹어 클럭만 올린 설계는 실성능이 정체됨
- 구조적 해저드는 하버드 구조(I/D 캐시 분리)로 설계 단계에서 원천 제거 가능함
- 데이터 해저드 중 RAW만 포워딩으로 해소되고, WAR·WAW는 레지스터 리네이밍(OoO 환경)으로 제거함
- 제어 해저드가 성능 영향이 가장 크며, 예측 실패 페널티는 파이프라인 깊이에 비례해 5~20사이클에 이름
- 현대 CPU는 TAGE 등 다단 동적 예측기로 97~99% 적중률을 달성해 플러시 빈도를 억제함(2비트 BHT 단독은 85~92%)

> 요약: 해저드 3종은 발생 계층이 달라 처방도 다르며, 제어 해저드 통제가 실성능을 좌우함.

## Ⅴ. 심화 비교 및 적용 판단

| 구분 | 구조적 해저드 | 데이터 해저드 | 제어 해저드 |
|:---|:---|:---|:---|
| 발생 원인 | 같은 하드웨어 자원 동시 요구 | RAW·WAR·WAW 값 의존 | 분기·점프로 다음 PC 불확실 |
| 감지 단계 | ID~MEM (자원 요구 시점) | ID (레지스터 의존 확인) | EX (분기 조건 확정) |
| 주요 해소법 | 자원 복제(I/D 캐시 분리), Stall | RAW→포워딩, WAR/WAW→리네이밍 | 분기 예측, 실패 시 Flush |
| 정량 영향 | 단일 포트 시 IF/MEM 매번 충돌 | Load-Use 1사이클 Stall 잔존 | 예측 실패 5~20사이클 Flush |

> 요약: 3종 해저드는 원인·감지 단계·처방이 모두 달라, 하나의 만능 대응이 아니라 종류별 전용 기법을 조합해야 함.

리스크·대응(불릿):
- 리스크 — Load-Use 스톨(Load 결과가 MEM 이후 확정) — 대응: MEM/WB 포워딩과 컴파일러 명령어 재배치로 잔여 1사이클 흡수 (지표: kilo-instruction당 Load-Use 스톨 수)
- 리스크 — 분기 플러시(분기 결과 지연 확정) — 대응: BHT+BTB 조기 분기 판정으로 branch miss rate 5% 이하 유지 (지표: 분기 예측 적중률)
- 리스크 — 검증 누락(포워딩·스톨 조건 조합 폭증) — 대응: SystemVerilog assertion·지향 테스트로 RAW/WAR/WAW 커버리지 확보 (지표: 의존성 조합 coverage 100%)

지표·목표(불릿):
- 지표 — CPI — 목표: 기준 워크로드 1.0~1.3 — 측정: 사이클 시뮬레이터·RTL 시뮬레이션
- 지표 — 분기 예측 적중률 — 목표: 95% 이상 — 측정: SPECint 분기 트레이스 분석
- 지표 — 스톨 비율 — 목표: 전체 사이클의 10% 이하 — 측정: 성능 카운터·파형 분석

## Ⅵ. 실무 적용 및 결론

**적용 방안 3개:**
1. 데이터 해저드: EX/MEM·MEM/WB 포워딩 경로 구현으로 RAW 스톨을 최대 2사이클 → 0사이클로 단축(단, Load-Use는 1사이클 잔존)
2. 제어 해저드: 2비트 포화 카운터 BHT + BTB로 분기 적중률 95% 이상 확보, 플러시 빈도 최소화
3. 컴파일러 협력: 명령어 재배치(Instruction Scheduling)·지연 분기(Delayed Branch)로 잔여 버블을 정적으로 흡수

**결론 (2줄):**
- 기술사 판단: 단 수가 얕으면(5~8단) 정적 예측+간단한 BTB로 충분하나, 깊으면(12단 이상) 다단 동적 예측+OoO를 선택해야 함
- 향후 방향: Meltdown·Spectre 이후 투기적 실행의 보안 취약점이 부각되어, 해저드 해소와 보안 격리(IBRS·Retpoline)를 동시에 설계해야 함
