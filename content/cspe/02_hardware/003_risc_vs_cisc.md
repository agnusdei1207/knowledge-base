# 003. 명령어 집합 — RISC vs CISC (ISA RISC CISC) [출제:124회]

## 미리 알고가기

- **명령어 집합 구조 (ISA)**: 하드웨어와 소프트웨어 사이의 인터페이스이며, CPU가 실행할 수 있는 명령어의 종류와 형식을 정의함
- **주소 지정 방식 (Addressing Mode)**: 명령어의 피연산자(Operand)가 있는 메모리 위치를 지정하는 방법임
- **마이크로 오퍼레이션 (u-op)**: 복잡한 CISC 명령어를 내부적으로 쪼갠 CPU의 최소 실행 단위임

## Ⅰ. 개요

- **정의/개념**: ISA(Instruction Set Architecture)는 CPU 설계의 철학을 결정하는 핵심 규격으로, 명령어의 복잡도에 따라 단순한 고정 길이의 RISC와 복잡한 가변 길이의 CISC로 분류됨
- **배경/필요성**: 초기에는 메모리 절약을 위해 복합 명령어(CISC)를 선호했으나, 반도체 기술의 발전으로 파이프라인 효율과 전력 대비 성능이 중요해지면서 단순 명령어(RISC) 기반 설계가 대두됨

## Ⅱ. 특징 및 비교

RISC는 '효율적인 실행'을, CISC는 '강력한 표현'과 '호환성'을 최우선 가치로 둠.

| 비교 항목 | RISC (Reduced) | CISC (Complex) |
|:---|:---|:---|
| **명령어 수/길이** | 적고 단순함 / **고정 길이** | 많고 복잡함 / **가변 길이** |
| **주소 지정 방식** | 단순함 (Load/Store 중심) | 매우 다양함 |
| **제어 유닛** | 하드와이어드(Hard-wired) 방식 | 마이크로코드(Microcode) 방식 |
| **파이프라이닝** | 매우 유리함 (단계별 시간 일정) | 불리함 (명령어마다 시간 다름) |
| **코드 밀도** | 낮음 (프로그램 크기 큼) | 높음 (프로그램 크기 작음) |
| **대표 아키텍처** | **ARM, RISC-V, MIPS** | **x86 (Intel/AMD)** |

> 요약: RISC는 '단순 반복을 빠르게', CISC는 '복잡한 일을 한 번에' 처리하는 철학임.

## Ⅲ. 구성요소/구조

명령어 집합은 단순히 연산 종류만 정의하는 것이 아니라 레지스터 모델과 실행 방식을 포함함.

- **구성요소**:
  - **Opcode**: 수행할 연산의 종류 (ADD, SUB, LOAD 등)
  - **Operand**: 연산의 대상이 되는 데이터나 주소
  - **Registers**: 연산을 위해 노출된 범용/특수 레지스터 집합
  - **Memory Model**: 메모리 정렬 및 바이트 오더링(Little/Big Endian) 방식

- **명령어 처리 흐름 (ASCII)**:

```text
[RISC: Simple & Fast]                [CISC: Complex & Flexible]
+---------+                          +---------+
| Inst 1  | ---+                     | Complex | ---+ (u-op split)
+---------+    |                     | Inst    |    |
+---------+    | Pipeline            +---------+    | +-------+
| Inst 2  | ---+ Exec                +---------+    | | u-op1 |
+---------+    |                     | Simple  | ---+ +-------+
+---------+    |                     | Inst    |      | u-op2 |
| Inst 3  | ---+                     +---------+      +-------+
+---------+
```

1. **RISC**: 모든 명령어가 표준화된 길이로 들어와 파이프라인을 쉼 없이 통과함
2. **CISC**: 가변 길이 명령어를 해독(Decode)하여 내부적으로 여러 개의 u-op로 쪼개어 실행함

## Ⅳ. 문제점 및 개선방안

1. **CISC의 해독 부하**: 가변 길이 명령어는 어디서부터 어디까지가 한 명령어인지 찾기 어려워 전력 소모와 지연이 발생함
   - **개선방안**: 마이크로오퍼레이션 캐시(u-op Cache)를 도입하여 이미 해독된 명령어를 재사용하고, 고성능 디코더를 병렬 배치함 (확인: 디코딩 대역폭 및 전력 효율)

2. **RISC의 코드 밀도 저하**: 명령어가 단순하다 보니 같은 기능을 구현할 때 프로그램 크기가 커져 캐시 메모리 부담이 증가함
   - **개선방안**: 16비트 압축 명령어 세트(예: ARM Thumb, RISC-V C extension)를 추가하여 코드 크기를 줄이고 메모리 효율을 높임 (확인: 바이너리 크기 및 I-Cache 적중률)

3. **아키텍처 수렴 현상**: 최근 CPU는 겉은 CISC(호환성)여도 속은 RISC(성능)로 동작하는 등 두 방식의 경계가 모호해짐
   - **개선방안**: ISA 고유의 철학보다는 실제 워크로드에 맞는 최적화 명령(벡터 연산, AI 가속 등)을 추가하여 하이브리드 형태로 발전시킴 (확인: 특정 워크로드 대비 성능 가속비)

## Ⅴ. 실무 적용 사례

| 적용 영역 | 적용 방식 | 확인 지표 |
|:---|:---|:---|
| 모바일/IoT 장치 | 저전력과 고효율 파이프라인이 필수적인 스마트폰(ARM) 및 IoT 기기에 RISC 적용 | 전력 대비 성능(Perf/Watt), 배터리 수명 |
| 데이터 센터/PC | 수십 년간 쌓인 소프트웨어 자산과의 호환성이 중요한 서버 및 데스크톱 시장에서 x86(CISC) 유지 | 레거시 앱 호환성, 단일 코어 성능 |
| 오픈 소스 하드웨어 | 로열티 없는 개방형 표준이 필요한 교육 및 연구 분야에서 RISC-V 채택 | 라이선스 비용 절감, 설계 자유도 |

> 요약: 성능과 전력이 중요하면 RISC, 호환성과 개발 생산성이 중요하면 CISC를 선택함.

## Ⅵ. 결론

RISC와 CISC는 단순한 기술적 우열이 아니라, '컴퓨터 자원의 가치'를 어디에 두느냐에 따른 선택의 문제임. 기술사는 현대의 프로세서가 CISC의 호환성을 유지하면서도 내부적으로는 RISC의 파이프라인 장점을 취하는 '수렴형 아키텍처'로 진화했음을 이해해야 함.

특히 클라우드와 AI 시대를 맞아 ARM 서버의 확산과 RISC-V의 부상은 ISA 시장의 판도를 바꾸고 있음. 결국 기술 선택의 핵심은 명령어의 개수나 길이가 아니라, 목표로 하는 워크로드에서 얼마나 최적의 전력 효율과 생태계 지원을 제공할 수 있는지에 달려 있음.
