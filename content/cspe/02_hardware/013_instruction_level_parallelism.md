## Ⅰ. 개요
- **정의**: 단일 프로그램 내에서 동시에 실행 가능한 명령어의 수를 나타내는 병렬성 척도
- **배경/필요성**: 클럭 주파수 향상이 전력 벽에 막히면서, 동일 주파수에서 처리량을 높이려면 사이클당 다수 명령어를 실행할 수 있는 ILP 추출이 필요함
- **비유**: 한 사람이 동시에 수행할 수 있는 독립적 작업(전화하면서 메모하기)의 개수와 유사함

| 출제 의도 | 반드시 짚을 핵심 | 감점 회피 포인트 |
|:---|:---|:---|
| ILP 개념과 추출 기법의 분류 | 정적(컴파일러) vs 동적(하드웨어) 추출 구분 | ILP는 프로그램 고유 속성이고, 추출 기법은 이를 활용하는 수단이라는 구분 |

> 요약: 프로그램이 내재한 명령어 간 병렬성을 정적·동적 기법으로 추출하여 CPI를 낮추는 개념임

## Ⅱ. 구성요소
```text
                    +--- ILP ---+
                    |           |
              정적 추출     동적 추출
              (컴파일러)    (하드웨어)
                |               |
         +------+------+   +---+---+
         |      |      |   |       |
      루프    소프트   VLIW  OoOE  투기
      언롤링  웨어         실행   실행
              파이프
              라이닝
```

| 구성요소 | 설명 | 비유 |
|:---|:---|:---|
| 데이터 의존성 | RAW·WAR·WAW 의존성이 병렬 실행 가능 명령어 수를 제한함 | 앞 작업 결과를 기다려야 시작 가능한 후속 작업 |
| 정적 추출 기법 | 컴파일러가 루프 언롤링·소프트웨어 파이프라이닝·VLIW(011 참조)로 ILP를 확보함 | 출발 전 최적 경로를 미리 계획하는 내비게이션 |
| 동적 추출 기법 | 하드웨어가 OoOE(012 참조)·투기 실행·동적 분기 예측으로 런타임 ILP를 확보함 | 실시간 교통 정보로 경로를 변경하는 내비게이션 |
| ILP 상한 | 프로그램의 의존성 구조가 결정하는 이론적 최대 병렬도 | 도로 폭이 결정하는 동시 통행 차량 수 상한 |

> 요약: ILP는 의존성이 허용하는 범위 내에서 정적·동적 기법으로 추출하는 병렬성임

## Ⅲ. 절차
```text
  의존성 분석      기법 선택        병렬 배치        동시 실행
  (그래프 구축)    (정적/동적)      (스케줄링)       (다중 FU)
     |               |               |               |
     +---의존그래프-->+---정책결정---->+---발행폭------>+
  RAW/WAR/WAW     컴파일러 or     슈퍼스칼라       CPI < 1.0
  제어 의존성     하드웨어 선택    VLIW 슬롯       목표 달성
```
- 1단계: 명령어 간 RAW·WAR·WAW 및 제어 의존성을 분석하여 의존성 그래프를 구축함
- 2단계: 워크로드 특성에 따라 정적 기법(컴파일러 최적화) 또는 동적 기법(하드웨어 스케줄링)을 선택함
- 3단계: 독립 명령어들을 동일 사이클에 배치하여 발행 폭(issue width)을 채움
- 4단계: 다수 기능 유닛이 배치된 명령어를 동시 실행하여 사이클당 완료 명령어 수(IPC)를 높임

> 요약: 의존성 분석 → 기법 선택 → 병렬 배치 → 동시 실행으로 IPC를 향상시키는 절차임

## Ⅳ. 문제점
- ILP 벽(ILP Wall): 범용 프로그램의 평균 ILP는 2~4 수준으로, 발행 폭을 넓혀도 활용률이 포화됨 — 하드웨어 투자 대비 성능 향상이 체감
- 제어 의존성 손실: 분기 예측 실패 시 투기 실행 결과를 폐기하므로 유효 ILP가 감소함 — 분기 빈도가 높은 코드에서 성능 저하 발생
- 메모리 지연 노출: 캐시 미스 시 수백 사이클 대기가 발생하여 명령어 윈도우 내 ILP를 소진함 — 메모리 집약 워크로드에서 파이프라인 정체

> 요약: 프로그램 고유 ILP 상한·분기·메모리 지연이 ILP 추출의 한계를 결정함

## Ⅴ. 개선방안
1. 단기: TLP(Thread-Level Parallelism)와 결합하여 SMT(Simultaneous Multithreading)로 유휴 슬롯을 다른 스레드가 활용
2. 중기: 신경망 기반 분기 예측기(TAGE-SC-L 등) 도입으로 예측 정확도를 99% 이상으로 끌어올려 투기 실패 감소
3. 장기: 프리페치·근접 메모리 처리(PIM) 기술로 메모리 지연을 줄여 명령어 윈도우 활용률 극대화

> 요약: SMT·고정밀 분기 예측·메모리 지연 감소를 통해 ILP 활용 한계를 확장함

## Ⅵ. 전망
- 발전 방향: 단일 스레드 ILP 한계로 멀티코어(014 참조) 및 TLP 중심으로 병렬성 추출 축이 이동 중임
- 기술사적 판단: ILP는 여전히 단일 스레드 성능의 핵심이며, 폴락의 법칙(015 참조)과 결합하여 코어 설계 전략의 기반이 됨
- 기술사 제언: ILP·TLP·DLP를 계층적으로 조합하는 이종 병렬 아키텍처 설계 역량 확보가 필요함
