# 📖 【암기용】 개념 완전 이해

> 목적: 싱글 코어 CPU 성능을 쥐어짜는 궁극의 목표치인 ILP가 무엇이고 어떻게 한계에 부딪혔는지 완벽히 이해하게 만든다.

## 한눈에
- **개요**: **IPC(사이클당 명령어 처리 수)**로 측정되는, 한 스레드 안에서 서로 의존성이 없어 동시에 겹쳐 실행할 수 있는 명령어의 양을 나타내는 지표가 **명령어 수준 병렬성(ILP, Instruction-Level Parallelism)**이다. 010 슈퍼스칼라, 011 VLIW, 012 비순차 실행은 모두 이 ILP를 최대한 뽑아내기 위한 서로 다른 구현 방법이다.
- **왜 필요한가**: 클럭 속도(Hz)를 올리면 발열(전력 벽) 때문에 한계에 부딪힌다. 클럭을 그대로 두고 성능을 올리려면 한 클럭에 끝내는 명령어 수(IPC)를 1보다 크게 만들어야 하고, 그 여지가 얼마나 있는지를 재는 척도가 ILP다.
- **핵심 직관**: 레시피에서 "면 삶기"와 "소스 끓이기"는 서로 의존성이 없어 두 화구(파이프라인)에서 동시에 진행할 수 있다. 이렇게 겹칠 수 있는 작업량이 ILP다.

## 핵심 용어 정리 (내부에 등장하는 것들)

| 용어 | 의미 | 비유 |
|:---|:---|:---|
| IPC / CPI | 클럭당 처리 명령어 수(IPC=처리 명령어 수/사이클 수)와 그 역수(CPI) — ILP를 실측하는 **단위** | 시간당 생산량 |
| ILP | 동시에 겹쳐 실행 가능한 독립 명령어의 이론적·실측 양 | 동시에 진행 가능한 요리 단계 수 |
| 정적 스케줄링 | 컴파일 타임에 ILP를 추출(011 VLIW) | 미리 짠 시간표 |
| 동적 스케줄링 | 런타임에 하드웨어가 ILP를 추출(010 슈퍼스칼라, 012 OoO) | 즉석 배차 |
| 제어 의존성 | 분기(if/else)의 결과를 알아야 다음 명령을 확정할 수 있는 제약 | 갈림길에서 어느 쪽으로 갈지 모르면 다음 걸음을 못 뗌 |
| 진성(RAW) 의존성 | 뒤 명령이 앞 명령의 계산 결과를 실제로 필요로 하는 제약(012 참조) | 재료가 나와야 다음 조리 가능 |
| 구조적(자원) 의존성 | 실행할 명령은 준비됐지만 그걸 처리할 유닛(ALU 등)이 부족해 대기하는 제약 | 화구는 2개인데 요리가 3개 |
| ILP Wall | 위 세 의존성 때문에 아무리 하드웨어를 늘려도 ILP가 특정 값 근처로 수렴하는 현상 | 아무리 화구를 늘려도 레시피 자체의 선후관계 때문에 못 줄이는 시간 |

## 깊이 이해

### IPC를 실제 수치로 계산하기
- 어떤 프로그램이 100만 개 명령어를 50만 클럭에 끝냈다면 IPC = 1,000,000 / 500,000 = 2.0, CPI = 1/2.0 = 0.5다. IPC가 2.0이라는 것은 "이 실행 구간에서 평균적으로 클럭당 명령어 2개를 끝냈다"는 뜻이며, 이 값이 클수록 그 구간의 ILP를 잘 뽑아냈다는 의미다.
- 이론적 ILP(코드 자체의 독립성 최대치)와 실측 IPC(실제 하드웨어가 뽑아낸 값)는 다르다. 예를 들어 코드상 이론적 ILP가 4여도, 하드웨어 실행 유닛이 2개뿐이면 실측 IPC는 2를 넘지 못한다(구조적 의존성).

### 코드에서 ILP를 직접 세어보기
- `A = B + C`, `D = E + F` — 서로 다른 변수만 쓰므로 이 둘의 ILP는 2(동시 실행 가능).
- `A = B + C`, `D = A + 1` — 두 번째 줄이 A(첫 줄의 결과)를 읽으므로 RAW, ILP는 1(직렬 필수).
- 실제 프로그램은 이런 명령어가 수백만 줄 섞여 있고, 그중 평균적으로 15~20% 정도가 분기문이라는 것이 흔히 보고되는 수치다. 분기마다 "다음에 뭐가 올지" 확정하지 못하면 그 뒤 명령어들을 미리 겹쳐 볼 수 없어, 병렬화 가능한 구간이 자주 끊긴다.

### ILP Wall — 왜 무한히 못 늘리나
- 1990년대 초 David Wall 등의 연구(이상적인 하드웨어를 가정한 시뮬레이션)는, 현실적인 분기 예측 정확도 하에서는 하드웨어 자원을 아무리 늘려도 평균 ILP가 한 자릿수(대략 5~7) 근처에서 수렴한다는 결과를 보였다. 이후 슈퍼스칼라의 이슈 폭을 6-way, 8-way로 넓혀도 실제 체감 성능 향상이 둔화된 것이 이 벽을 실측으로 보여준다.
- 이 벽의 정체는 하드웨어 부족이 아니라 **소스 코드 자체가 가진 순차적 논리 구조**다. 아무리 트랜지스터를 투입해도 `D = A + 1`처럼 진짜로 앞 결과가 있어야 하는 코드는 쪼갤 수 없다.

### 판별 원리 — 정적 vs 동적 스케줄링
- 같은 ILP를 뽑아내더라도 "언제 누가 결정하는가"로 구현이 갈린다. 컴파일러가 컴파일 타임에 확정하면 정적 스케줄링(011 VLIW), 하드웨어가 실행 중에 그때그때 판단하면 동적 스케줄링(010 슈퍼스칼라 + 012 OoO)이다. 정적은 하드웨어가 가볍지만 컴파일러 분석 한계에 갇히고, 동적은 실행 정보(실제 캐시 미스 등)까지 반영할 수 있지만 하드웨어가 무겁다.

## 연결 개념
- 010 슈퍼스칼라·011 VLIW·012 비순차 실행 — ILP를 뽑아내는 3대 구현 기법(동적 2가지 + 정적 1가지)
- 014 멀티코어(TLP) — ILP Wall에 부딪힌 뒤 병렬성의 방향을 스레드 단위로 돌린 다음 단계
- DLP(데이터 수준 병렬성)·SIMD — 명령어 1개로 여러 데이터를 처리하는 또 다른 병렬성 축

# 📝 【답안용】 시험 답안 템플릿

> 목적: 시험장에서 25분에 그대로 쓰는 답안 양식. 

## 핵심 인사이트 (3줄 요약)

> 1. **본질**: 명령어 수준 병렬성(ILP)은 단일 프로세서 환경에서 프로그램 명령어 간의 데이터/제어 의존성을 분석하여 다수의 명령어를 동시에 중첩 실행할 수 있는 척도다.
> 2. **가치**: 파이프라이닝, 슈퍼스칼라, 비순차 실행(OoO), 분기 예측 등의 마이크로 아키텍처 기술이 총동원되어 클럭 속도의 증가 없이 IPC(명령어 처리량)를 1.0 이상으로 수직 상승시켰다.
> 3. **판단 포인트**: ILP는 분기문의 불확실성과 진성 의존성(RAW)이라는 논리적 한계("ILP Wall")에 부딪혔으며, 현대 프로세서는 이를 우회하기 위해 멀티 스레딩(TLP) 및 데이터 병렬성(DLP)으로 설계 중심을 이동했다.

## 출제 의도 및 답안 포인트

| 출제 의도 | 반드시 짚을 핵심 | 감점 회피 포인트 |
|:---|:---|:---|
| 싱글코어 성능 향상의 핵심 원리와 한계치 이해 | 하드웨어적 기법(파이프라이닝, OoO), 의존성 제약(RAW, 분기) | ILP를 멀티코어(TLP)나 분산 처리와 혼동하여 서술하는 치명적 오류 |
| ILP 구현을 위한 세부 마이크로 아키텍처 연결 | 레지스터 리네이밍, 동적 스케줄링, VLIW 정적 스케줄링 | 단순 개념만 적고 성능 지표인 IPC와의 관계를 누락 |

> 요약: ILP는 싱글 코어 "내부"에서 명령어를 어떻게 겹치고(Overlap) 섞는가(OoO)에 대한 좁고 깊은 파이프라인 최적화 영역임을 명시해야 한다.

## Ⅰ. 개요 및 필요성

- 정의: 순차적으로 작성된 프로그램 명령어 스트림에서, 의존성이 없는 다수의 명령어를 식별하여 한 번에 병렬 처리하는 기법
- 배경: 클럭 주파수 상승에 따른 전력 벽(Power Wall) 직면으로 단일 스레드의 물리적 성능 한계 도달
- 필요성: 클럭 속도를 높이지 않은 상태에서 매 사이클 처리되는 명령어 수(IPC)를 2~6 이상으로 극대화하여 코어 단일 성능 향상

## Ⅱ. 구조 및 구성요소 (ILP 추출 2대 접근법)

```text
[ILP 추출 및 실행의 두 가지 철학]
1. 정적 스케줄링 (S/W 주도): 컴파일러(분석) -> 패킹(VLIW 포맷) -> 단순 하드웨어 실행
2. 동적 스케줄링 (H/W 주도): 바이너리 인출 -> 런타임 하드웨어(스케줄러) 분석 -> 비순차(OoO) 실행
```

| 접근 방식 | 구동 주체 | 핵심 기술 (ILP 구현 메커니즘) |
|:---|:---|:---|
| 소프트웨어적 방법 | 컴파일러 | 루프 언롤링(Loop Unrolling), 정적 명령어 스케줄링(Instruction Scheduling), VLIW 묶음 |
| 하드웨어적 방법 | CPU 마이크로 아키텍처 | 다중 파이프라인(슈퍼스칼라), 레지스터 리네이밍, 비순차 실행(OoO), 분기 예측(Branch Prediction) |

> 요약: 범용 CPU는 하드웨어(슈퍼스칼라/OoO)가 런타임에 ILP를 발굴하고, DSP 등 커스텀 칩은 소프트웨어(VLIW)가 컴파일 시점에 ILP를 고정한다.

## Ⅲ. 동작원리 및 흐름도 (ILP 적용 마이크로 오퍼레이션)

```text
[동적 스케줄링 기반 ILP 발굴 흐름]
다중 명령어 인출(IF 폭 4~8) -> [ 분기 예측 ] (제어 흐름 유지)
-> 디코딩 및 [ 리네이밍 ] (가짜 의존성 WAR/WAW 제거)
-> 예약 정거장 대기 -> [ 진성 의존성(RAW) 해결된 명령부터 동시 발행 ] -> IPC > 1.0 처리 완료
```

| 단계 | 제어 모듈 | 처리 내용 (명령어 겹침 병목 제거) |
|:---:|:---|:---|
| 1 | 분기 예측기 | 조건 분기로 인한 제어 해저드를 예측(TAGE 등)하여 끊김 없는 명령어 윈도우(Window) 확보 |
| 2 | RAT (리네이밍) | 레지스터 이름 부족으로 생긴 가성 의존성(WAR, WAW)을 물리 레지스터 매핑으로 원천 해체 |
| 3 | RS (스케줄러) | 남은 진성 의존성(RAW)이 데이터 포워딩을 통해 풀리는 즉시 다중 실행 유닛으로 비순차 발송 |
| 4 | 다중 ALU 유닛 | 독립적인 명령어 2~8개를 1클럭 내에 병렬로 최종 연산하여 ILP 실현 |

> 요약: ILP는 명령어를 많이 인출한다고 얻어지는 것이 아니라, 가짜 의존성과 분기 불안정을 "리네이밍"과 "예측"으로 걷어내야만 발현된다.

## Ⅳ. 병렬성을 제약하는 3대 한계 (ILP Wall)

| 제약 요소 (해저드) | 발생 원인 | 성능 영향 | 하드웨어/소프트웨어 대응 |
|:---|:---|:---|:---|
| 제어 의존성 (분기) | If/Else 반복으로 다음 명령어 불확실 | 파이프라인 플러시(Flush) 및 윈도우 단절 | 다단 동적 분기 예측, 루프 언롤링(S/W) |
| 진성 데이터 의존성 | 뒤 명령이 앞 명령의 결과(RAW)를 반드시 대기 | 포워딩으로 완화되나 본질적 대기 시간 잔존 | 비순차 실행(OoO)으로 후속 무관 명령 먼저 처리 |
| 자원 구조적 의존성 | 동시 실행할 다수 유닛(ALU, Memory Port) 부족 | 명령어가 준비되어도 실행 H/W 부족으로 대기 | 실행 유닛(Way) 다중화, 하버드 분리 구조 |

> 요약: "ILP의 벽(ILP Wall)"은 평균적인 소스코드 내 분기문 빈도(약 15%)와 순차적 데이터 의존성 때문에 4~6을 넘기 어렵다는 구조적 한계다.

## Ⅴ. 심화 비교 및 적용 판단 (ILP vs TLP vs DLP)

| 병렬성 종류 | 처리 관점 | 대응 아키텍처 및 기술 | 타겟 워크로드 및 적용 한계 |
|:---|:---|:---|:---|
| ILP (Instruction) | 단일 스레드 내 명령어 | 슈퍼스칼라, 비순차 실행(OoO) | 범용 S/W (싱글코어 성능 한계 도달) |
| TLP (Thread) | 다중 스레드/프로세스 | SMT(하이퍼스레딩), 멀티코어 | 웹 서버, DBMS (스레드 간 통신 오버헤드 존재) |
| DLP (Data) | 단일 명령어 다중 데이터 | SIMD, GPU, 벡터 가속 연산 | 그래픽 렌더링, 인공지능 행렬 곱 (조건 분기에 취약) |

> 요약: 싱글 코어 성능을 쥐어짜는 ILP가 벽에 부딪히자, 칩 제조사들은 코어를 늘리는 TLP(멀티코어)와 연산폭을 넓히는 DLP(GPU/NPU)로 방향을 틀었다.

## Ⅵ. 실무 적용 및 결론

**적용 방안 3개:**
1. 컴파일러 루프 언롤링(Loop Unrolling): 개발자가 짠 `for(i=0; i<100)` 코드를 컴파일러가 강제로 풀어서 연속된 연산으로 평탄화(Flatten)하여, 제어 의존성(분기문)을 없애고 하드웨어가 더 큰 ILP 윈도우를 찾도록 지원
2. SIMD (Data-Level) 확장 융합: ILP 확장이 한계에 봉착한 최신 CPU 코어 내에 AVX-512 등의 SIMD(DLP) 연산기를 통합하여, 명령어 1개로 512비트 데이터를 동시 처리해 전체 병렬 처리량을 폭증시킴
3. 하이퍼스레딩(SMT) 결합: 8-Way 슈퍼스칼라 코어에서 특정 스레드의 ILP가 3밖에 안 되어 5개 유닛이 놀 때, 다른 스레드의 명령어를 남는 유닛에 동시에 밀어 넣어 유닛 가동률 극대화

**결론 (2줄):**
- 기술사 판단: ILP 최적화는 레거시 단일 스레드 애플리케이션의 체감 속도를 결정하는 유일한 열쇠이지만, 구조적 한계(ILP Wall)로 인해 더 이상 N-Way 차선 폭을 넓히는 것은 전력 낭비에 불과하다.
- 향후 방향: 현대 아키텍처의 패러다임은 무리하게 단일 스레드 ILP를 올리는 데서 벗어나, 멀티코어(TLP) 및 이기종 가속기(DLP)를 활용해 거시적 병렬 처리로 진화하고 있다.
