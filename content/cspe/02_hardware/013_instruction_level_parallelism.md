# 📖 【암기용】 개념 완전 이해

> 목적: ILP를 처음 봐도 CPU가 한 프로그램 안에서 어디까지 동시에 실행할 수 있는지, 그 한계가 왜 생기는지 이해하게 만든다. 시험 답안 양식이 아니라, 이해를 위한 친절한 설명이다.

## 한눈에
- **개요**: 하나의 명령어 스트림 안에서 서로 의존성 없이 동시에 실행 가능한 명령어의 양을 나타내는 척도
- **왜 필요한가**: 파이프라이닝·슈퍼스칼라·VLIW·비순서 실행 같은 하드웨어·컴파일러 기법은 모두 코드에 내재된 ILP를 최대한 뽑아내려는 시도이므로, ILP 개념 없이는 이 기법들의 존재 이유를 설명할 수 없다
- **핵심 직관**: 요리 레시피에서 서로 재료가 겹치지 않는 단계(채소 썰기와 물 끓이기)는 동시에 할 수 있지만, 한 단계 결과가 다음 단계 재료인 경우(끓인 물에 재료 넣기)는 순서를 지켜야 하는 것과 같다

## 깊이 이해
- **배경·문제의식**: 클럭 주파수 상승이 발열·전력 한계에 부딪히면서, 동일 클럭 안에서 더 많은 명령어를 처리하는 방향(ILP 추출)이 성능 개선의 핵심 축이 되었다.
- **작동 원리**: ILP를 제한하는 요인은 데이터 의존성(RAW), 제어 의존성(분기), 자원 의존성(공유 실행 유닛) 세 가지이며, 이 중 하나라도 있으면 해당 명령어 쌍은 동시 실행할 수 없다.
- **작동 원리 - 추출 기법**: 하드웨어 측 기법으로 파이프라이닝, 슈퍼스칼라, 비순서 실행, 레지스터 리네이밍이 있고, 컴파일러 측 기법으로 명령어 스케줄링, 루프 언롤링(Loop Unrolling), 소프트웨어 파이프라이닝이 있다.
- **작동 원리 - ILP 벽(ILP Wall)**: 실제 범용 프로그램은 분기 빈도와 데이터 의존 체인 때문에 평균적으로 추출 가능한 ILP에 한계가 있다는 것이 실험적으로 알려져 있으며, 이 때문에 발행 폭을 계속 늘려도 IPC 향상이 체감된다.
- **비유**: 한 사람이 여러 냄비를 동시에 볼 수 있는 것은 각 요리가 서로 재료·순서에 얽매이지 않을 때뿐이고, 한 냄비 결과를 다른 냄비가 기다려야 하면 동시 진행 폭이 줄어드는 것과 같다.
- **구체 예시**: `for` 루프에서 매 반복이 이전 반복 결과를 쓰지 않는 독립 반복이면 루프 언롤링으로 여러 반복을 한 번에 스케줄링해 ILP를 끌어올릴 수 있지만, 누적 합처럼 이전 반복 결과에 의존하는 루프는 언롤링 효과가 제한적이다.
- **흔한 오해·주의점**: ILP는 하드웨어 발행 폭을 늘리면 무한정 커지는 값이 아니다. 코드 자체에 내재된 의존성 구조가 상한을 결정하므로, 발행 폭 확대만으로는 실제 IPC 향상이 비례하지 않는다.
- **흔한 오해·주의점**: ILP와 TLP(Thread-Level Parallelism), DLP(Data-Level Parallelism)는 서로 다른 병렬성 축이다. ILP는 한 명령어 스트림 내부의 병렬성이고, TLP는 여러 스레드 간, DLP는 벡터·SIMD처럼 같은 연산을 여러 데이터에 동시 적용하는 병렬성이다.

## 연결 개념
- 슈퍼스칼라·VLIW — ILP를 각각 하드웨어 동적 방식과 컴파일러 정적 방식으로 추출하는 구조
- 비순서 실행·레지스터 리네이밍 — 가짜 의존성을 제거해 추출 가능한 ILP 폭을 넓히는 기법
- 파이프라인 해저드 — ILP를 제한하는 세 가지 의존성(자원·데이터·제어)의 실제 발현 형태

# 📝 【답안용】 시험 답안 템플릿

> 핵심: ILP 제한 요인 세 가지, 하드웨어·컴파일러 추출 기법, ILP 벽과 TLP·DLP 구분을 함께 제시한다.

## 핵심 인사이트 (3줄 요약)

> 1. **본질**: ILP는 한 명령어 스트림 안에서 의존성 없이 동시 실행 가능한 명령어 양을 나타내는 병렬성 척도이다.
> 2. **가치**: 파이프라이닝·슈퍼스칼라·VLIW·비순서 실행 등 대부분의 마이크로아키텍처 기법은 ILP를 더 많이 뽑아내려는 목적을 공유한다.
> 3. **판단 포인트**: 코드에 내재된 의존성 구조가 ILP 상한을 결정하므로, 발행 폭 확대만으로는 IPC가 비례하지 않으며 TLP·DLP 같은 다른 병렬성 축과 함께 판단해야 한다.

| 추출 기법 분류 확인 | 하드웨어 기법(슈퍼스칼라, OoO)과 컴파일러 기법(스케줄링, 언롤링) 구분 | 하드웨어 기법만 나열하고 컴파일러 기법 누락 |

## Ⅰ. 개요 및 필요성

- 정의: 하나의 명령어 스트림 내에서 의존성 없이 동시 실행 가능한 명령어의 양을 나타내는 병렬성 척도
- 배경: 클럭 주파수 상승이 발열·전력 한계에 부딪히면서 동일 클럭 내 처리량을 늘리는 방향으로 마이크로아키텍처 설계 축이 이동함
- 필요성: 파이프라이닝·슈퍼스칼라·VLIW·비순서 실행 같은 기법의 효과를 판단하려면 대상 코드의 ILP 수준을 먼저 파악해야 함

---

## Ⅱ. 구조 및 구성요소

```text
명령어 스트림
  -> 의존성 분석
       / Data Dependency (RAW)
       / Control Dependency (분기)
       / Resource Dependency (실행 유닛 공유)
  -> 추출 기법 적용
       / Hardware: Pipeline, Superscalar, OoO, Register Renaming
       / Compiler: Instruction Scheduling, Loop Unrolling, Software Pipelining
  -> 실제 IPC 결정
```

| 구성요소 | 역할 | 산출물 |
|:---|:---|:---|
| 데이터 의존성 분석 | RAW 체인 길이 파악 | 동시 실행 불가 명령어 쌍 식별 |
| 제어 의존성 분석 | 분기 빈도·분기 예측 정확도 파악 | 투기 실행 범위 결정 |
| 하드웨어 추출 기법 | 슈퍼스칼라·비순서 실행·리네이밍 적용 | 런타임 ILP 활용 |
| 컴파일러 추출 기법 | 명령어 재배치·루프 언롤링 적용 | 정적 ILP 확보 |

> 요약: ILP는 의존성 분석으로 상한이 정해지고, 하드웨어·컴파일러 기법이 그 상한 안에서 실제 병렬 실행을 채운다.

---

## Ⅲ. 동작원리 및 흐름도

```text
소스 코드/명령어 스트림 -> 의존성 그래프 생성
  -> 독립 명령어 그룹 식별
  -> 하드웨어: 슈퍼스칼라 발행, OoO 스케줄, 레지스터 리네이밍 적용
  -> 컴파일러: 명령어 재배치, 루프 언롤링, 소프트웨어 파이프라이닝 적용
  -> 실행 유닛 병렬 실행 -> IPC 측정
```

| 단계 | 처리 내용 | 검증 기준 |
|:---:|:---|:---|
| 1 | 명령어 간 의존성 그래프 생성 | RAW/WAR/WAW/제어/자원 의존 식별 |
| 2 | 독립 명령어 그룹 추출 | 동시 실행 가능 명령어 수 |
| 3 | 하드웨어·컴파일러 기법으로 병렬 실행 스케줄링 | 발행 폭 대비 실제 발행 수 |
| 4 | 실행 후 IPC 측정 | 이론 ILP 대비 실측 IPC 격차 |

> 요약: ILP 추출은 의존성 그래프 분석 후 하드웨어와 컴파일러 기법을 결합해 병렬 실행을 채우는 흐름이다.

## Ⅳ. 특징

| 구분 | 내용 | 판단 포인트 |
|:---|:---|:---|
| 장점 | 클럭 주파수 증가 없이 처리량 향상 가능 | IPC 개선 |
| 한계 | 코드 내재 의존성이 상한을 결정(ILP 벽) | 발행 폭 확대 대비 IPC 향상 체감 |
| 비교 포인트 | ILP(명령어 수준) vs TLP(스레드 수준) vs DLP(데이터 수준) | 병렬성 축 구분 |

> 요약: ILP는 발행 폭이나 하드웨어 투자만으로 무한히 늘어나지 않고 코드 자체의 의존성 구조에 상한이 있다.

## Ⅴ. 심화 비교 및 적용 판단

| 비교 축 | ILP | TLP/DLP | 선택 기준 |
|:---|:---|:---|:---|
| 구조 | 단일 명령어 스트림 내부 병렬성 | 여러 스레드(TLP) 또는 벡터 데이터(DLP) 병렬성 | 단일 스레드 성능 한계 도달 시 TLP·DLP 병행 검토 |
| 비용/성능 | 발행 폭·리네이밍 확대로 면적·전력 증가 | 멀티코어·SIMD 확장으로 처리량 확대 | 워크로드 병렬성 형태(명령어/스레드/데이터)로 결정 |
| 운영/위험 | ILP 벽으로 단일 코어 성능 정체 가능 | 스레드 동기화, 벡터화 실패 리스크 | 코드 병렬화 가능성 사전 분석 |

> 요약: 단일 명령어 스트림의 ILP가 한계에 도달하면 멀티코어(TLP)·SIMD(DLP) 확장으로 병렬성 축을 전환한다.

| 리스크 | 원인 | 대응 방안 | 확인 지표 |
|:---|:---|:---|:---|
| ILP 벽 도달 | 분기 빈도·RAW 체인 길이 증가 | 분기 예측 고도화, 루프 언롤링 | branch frequency, dependency chain length |
| 발행 폭 대비 저조한 IPC | 코드 ILP 부족 | SMT·멀티코어로 TLP 확보 병행 | IPC 대비 이론 발행 폭 비율 |
| 컴파일러 최적화 한계 | 포인터 별칭·복잡한 제어 흐름 | 별칭 분석 강화, 프로파일 기반 최적화 | 컴파일러 정적 스케줄링 성공률 |

> 요약: ILP 벽에 부딪히면 예측·스케줄링 고도화와 함께 TLP·DLP로 병렬성 축을 옮기는 것이 대응 방안이다.

| 점검 항목 | 목표 기준 | 측정 방법 |
|:---|:---|:---|
| IPC | 워크로드별 목표 IPC 대비 실측치 | 성능 카운터 |
| 분기 예측 적중률 | 목표 적중률 확보 | 트레이스 분석 |
| 컴파일러 스케줄링 효과 | 루프 언롤링·재배치 적용 전후 IPC 비교 | 벤치마크 A/B 비교 |

> 요약: ILP 추출 효과는 IPC, 분기 예측 적중률, 컴파일러 최적화 전후 비교로 검증한다.

## Ⅵ. 실무 적용 및 결론

**적용 방안 3개:**
1. 데이터 의존 체인이 짧은 반복 구조는 루프 언롤링·소프트웨어 파이프라이닝으로 정적 ILP를 확보함
2. 분기 빈도가 높은 코드는 분기 예측 고도화와 비순서 실행을 병행해 제어 의존성으로 인한 ILP 손실을 줄임
3. 단일 스트림 ILP가 한계에 도달한 워크로드는 멀티코어(TLP)·SIMD(DLP) 확장으로 병렬성 축을 전환함

**결론 (2줄):**
- 기술사 판단: ILP는 코드 내재 의존성이 상한을 결정하므로 발행 폭 확대보다 의존성 완화 기법과 병렬성 축 전환을 함께 검토해야 함
- 향후 방향: 단일 코어 ILP 확장의 면적·전력 비용이 커짐에 따라 멀티코어·SMT·AI 가속기 결합 설계로 무게중심이 이동하고 있음
