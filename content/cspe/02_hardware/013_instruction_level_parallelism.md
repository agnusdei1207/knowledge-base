# 📖 【암기용】 개념 완전 이해

## 한눈에
- **개요**: 하나의 프로세서가 코딩된 순서에 얽매이지 않고 여러 개의 명령어를 동시에 중첩 실행하여 단위 시간당 처리량(명령어 수)을 높이는 잠재적 병렬성이다.
- **왜 필요한가**: 클럭 주파수를 올리는 물리적 한계(발열)에 직면한 상황에서, 소프트웨어가 가진 독립적인 연산들을 한 번에 많이 처리하여 프로세서의 실효 성능(IPC)을 끌어올리기 위함이다.
- **핵심 직관**: 한 사람이 요리(명령어)를 순서대로 하나씩 하면 오래 걸리지만, 요리 과정 중 서로 겹치지 않는 작업(물 끓이기, 야채 썰기)을 동시에 진행하면 전체 시간이 획기적으로 줄어드는 원리이다.

## 핵심 용어 정리 (내부에 등장하는 것들)

| 용어/표기 | 의미 | 비유·예 |
|:---|:---|:---|
| IPC (Instructions Per Clock) | 한 사이클(클럭) 당 실행 완료되는 명령어 수 | "1초에 처리하는 영수증 장수" |
| 파이프라이닝 (Pipelining) | 하나의 명령어를 여러 단계로 쪼개어 컨베이어 벨트처럼 중첩 실행 (시간적 병렬성) | "공장 조립 라인" |
| 다중 발행 (Multiple Issue) | 클럭 당 여러 개의 명령어를 동시에 인출하고 실행 (공간적 병렬성) | "다차선 도로, 슈퍼스칼라/VLIW" |
| 데이터 의존성 (Data Dependency) | 앞 명령어의 결과를 뒤 명령어가 기다려야 해서 동시에 병렬 실행할 수 없는 제약 | "앞사람 서류가 넘어가야 결재 가능" |

## 깊이 이해
- **배경·문제의식**: 클럭 속도를 높이는 것만으로는 트랜지스터 집적도 한계(Power Wall)로 인해 한계에 부딪혔다. 따라서 프로그래머가 작성한 단일 스레드 코드 내부에 숨어있는 "서로 무관한 독립적 연산"들을 찾아내 한꺼번에 묶어서 처리할 필요가 생겼다.
- **작동 원리**: ILP를 구현하는 하드웨어 및 소프트웨어 기술은 크게 3가지 축으로 발전했다.
  1. 깊은 파이프라인: 단계를 잘게 쪼개 동시에 더 많은 명령어가 파이프라인에 머물게 함.
  2. 동적 병렬화(슈퍼스칼라+비순서 실행): 하드웨어가 런타임에 의존성을 검사하고, 독립된 여러 명령어를 다수의 연산 유닛에 동시 배분함.
  3. 정적 병렬화(VLIW): 컴파일러가 미리 의존성 없는 명령어들을 묶어서 CPU에 전달함.
- **비유**: 순차 처리가 왕복 1차선 도로라면, ILP는 차로를 4차선으로 늘리고(다중 발행), 각 차로에 신호등 없이 차를 연속으로 진입시키는(파이프라이닝) 것과 같다.
- **구체 예시**: `X = A + B`, `Y = C + D` 두 명령어는 사용하는 변수가 다르므로 데이터 의존성이 없다. CPU는 이 둘을 파악하여 2개의 ALU에 동시에 밀어 넣어 1사이클 만에 모두 처리해버린다 (IPC = 2 달성).
- **흔한 오해·주의점**: ILP는 TLP(스레드 수준 병렬성)나 멀티코어와 다르다. 멀티코어는 아예 프로그램이나 스레드가 여러 개일 때 유리하지만, ILP는 "단일 스레드 프로그램 하나" 안에서 명령어 단위로 쪼개어 병렬화하는 기술이다. 그러나 코드에 분기문(If)이나 의존성(RAW)이 너무 많으면 아무리 하드웨어가 좋아도 ILP를 뽑아낼 수 없다.

## 연결 개념
- **007 파이프라이닝**: 시간적 ILP의 가장 기초.
- **010 슈퍼스칼라 / 012 비순서 실행**: 하드웨어 중심의 최고급 동적 ILP 구현 기법.
- **011 VLIW**: 소프트웨어(컴파일러) 중심의 정적 ILP 구현 기법.

# 📝 【답안용】 시험 답안 템플릿

## 핵심 인사이트 (3줄 요약)

> 1. **본질**: 명령어 수준 병렬성(ILP)은 단일 스레드 내 명령어들의 데이터 의존성을 회피하여 다수의 연산을 동시 중첩 실행하는 마이크로아키텍처의 목표 성능 지표이다.
> 2. **가치**: 클럭 스피드 극대화에 따른 발열 한계(Power Wall)를 우회하여, 사이클 당 명령어 처리량(IPC)을 1.0 이상으로 끌어올려 단일 코어 성능을 획기적으로 향상시킨다.
> 3. **판단 포인트**: ILP의 한계(명령어 간 진성 의존성, 분기 제어)에 봉착함에 따라 현대 프로세서의 성능 향상 패러다임은 멀티코어 중심의 스레드 수준 병렬성(TLP)으로 전환되었다.

## 출제 의도 및 답안 포인트

| 출제 의도 | 반드시 짚을 핵심 | 감점 회피 포인트 |
|:---|:---|:---|
| 단일 스레드 성능 향상의 근본 원리 이해 | 시간적 병렬성(파이프라인) + 공간적 병렬성(다중발행), IPC 향상 | TLP(멀티스레드)와의 개념 혼동, 하드웨어 기능 나열에 그침 |
| ILP 구현 기술 분류 역량 확인 | 정적 스케줄링(VLIW/컴파일러) vs 동적 스케줄링(Superscalar/비순서 실행) | VLIW와 슈퍼스칼라의 비교 누락, 제약 사항 미서술 |

> 요약: 단일 프로그램 내부의 병렬성을 하드웨어(동적)와 소프트웨어(정적)가 어떻게 추출하는지 기술하고, 데이터/제어 해저드로 인한 확장성 한계를 짚어야 한다.

## Ⅰ. 개요 및 필요성

- 개요: 명령어 수준 병렬성(Instruction-Level Parallelism, ILP)은 순차적으로 작성된 프로그램 코드 내에서 서로 의존성이 없는 명령어들을 찾아 동시에 실행하는 잠재적 병렬성이다.
- 배경: 트랜지스터 집적도 한계와 동적 전력 소모 폭증(Power Wall)으로 인해 클럭 주파수 상향을 통한 성능 향상 공식이 종말 맞이
- 필요성: 클럭 속도 유지 상태에서도 단일 코어의 연산 스루풋(Throughput)을 배가하기 위해, IPC(클럭 당 명령어)를 비약적으로 높이는 파이프라인 다중화 기술 필수

---

## Ⅱ. 구조 및 구성요소 (ILP 구현 아키텍처 매핑)

```text
[ ILP 한계 극복 흐름도 ]
순차 프로그램 (IPC <= 1) 
 -> 시간적 중첩: [ 슈퍼파이프라이닝 ] (클럭 속도 증가, 단수 증가)
 -> 공간적 다중화: [ 슈퍼스칼라 / VLIW ] (다중 이슈, IPC > 1)
 -> 실행 최적화: [ 비순서 실행 / 리네이밍 ] (데이터 의존성 타파)
```

| ILP 확장 요소 | 적용 기술 | 목표 효과 (성능 관점) |
|:---|:---|:---|
| 시간적 병렬성 (Temporal) | 깊은 파이프라이닝 (Deep Pipelining) | 명령어 단계를 잘게 쪼개 동시 처리량 증가 및 클럭 향상 |
| 공간적 병렬성 (Spatial) | 다중 발행 (Multiple Issue) 및 다중 실행 유닛 | 클럭 당 여러 명령어 동시 인출 및 연산 (IPC > 1 달성) |
| 동적 최적화 (Dynamic) | 비순서 실행(OoO), 레지스터 리네이밍 | 가성 의존성을 제거하여 파이프라인 스톨(Stall) 완전 은닉 |
| 정적 최적화 (Static) | VLIW, 루프 언롤링(Loop Unrolling) | 컴파일러 차원의 명시적 병렬 패키징 및 의존성 사전 해소 |

> 요약: ILP는 파이프라인 단수 늘리기(시간 축)와 다중 실행 유닛 배치(공간 축)의 물리적 결합에 동/정적 스케줄링 로직을 더해 완성된다.

---

## Ⅲ. 동작원리 및 흐름도 (의존성 판별 및 실행)

```text
명령어 스트림 인출 -> 데이터/제어 의존성 분석 -> 병렬화 가능 그룹 추출 -> 다중 유닛 동시 할당 및 실행
```

- 1단계 [의존성 스캔]: 런타임 하드웨어(또는 컴파일 타임 소프트웨어)가 명령어 간 RAW, WAR, WAW 및 조건 분기 충돌을 스캔
- 2단계 [가성 의존성 해체]: 레지스터 리네이밍 메커니즘을 가동하여 WAR, WAW로 묶여 있는 명령어들을 서로 분리시켜 독립 상태로 전환
- 3단계 [명령어 윈도우 스케줄링]: 실행 대기 큐(예: Reservation Station)에서 순서와 무관하게 모든 피연산자가 준비된 다수의 명령어 동시 선택
- 4단계 [병렬 처리 및 커밋]: 3~8개의 각기 다른 실행 유닛(ALU, FPU 등)에 동시 배분하여 1사이클 내 연산하고 순차 커밋하여 정합성 보장

> 요약: 명령어 윈도우 내의 해저드(충돌) 요인을 해체하고 독립적인 연산 그룹을 묶어 물리적 유닛의 가동률을 100%로 끌어올리는 과정이다.

## Ⅳ. 특징
- 실효 IPC 향상: 순차 실행 대비 2배~4배 이상의 명령어 처리 스루풋(Throughput) 달성으로 단일 애플리케이션 지연 시간 최소화
- 제약 조건 심화: 하드웨어가 아무리 ILP 윈도우를 넓혀도, 코드 자체의 진성 의존성(RAW) 비율이 높으면 병렬 추출에 한계 봉착
- 자원 투자 대비 수확 체감: ILP 확장을 위한 스케줄링 하드웨어 복잡도는 N² 단위로 증가하여, 일정 폭 이상에서는 전력 효율(Perf/Watt)이 급감

> 요약: ILP는 단일 스레드 최적화의 핵심이나, 프로그램 본연의 순차성 제약과 하드웨어 복잡도 폭증이라는 명확한 한계를 지닌다.

## Ⅴ. 심화 비교 및 적용 판단

| 비교 축 | ILP (Instruction-Level) | TLP (Thread-Level) | 기술사 선택 기준 |
|:---|:---|:---|:---|
| 병렬성 추출 단위 | 명령어 (Instruction) 단일 스트림 내 | 스레드 (Thread) 또는 프로세스 레벨 | 애플리케이션 특성 |
| 구현 주체 | H/W 동적 스케줄러, 컴파일러 (단일 코어) | 멀티코어(SMP), SMT (하이퍼스레딩) | 하드웨어 인프라 구성 |
| 의존성 제약 | 데이터 진성 의존성에 극도로 민감 | 스레드 간 독립성 높음 (Lock/동기화 예외) | 확장성(Scalability) 한계 |

> 요약: 단일 작업의 반응 속도는 ILP가 좌우하며, 웹 서버나 렌더링처럼 다중 작업 동시 처리가 필요한 환경은 TLP로 확장해야 한다.

**리스크·대응 (기본은 불릿):**
- 제어 의존성에 의한 ILP 파괴: 조건 분기(If/Else) 1회 실패가 수십 개의 병렬 실행 명령어를 플러시(Flush) 유발 → 타겟 예측기, TAGE 분기 예측 등으로 분기 실패율 5% 이하 통제 (지표: Branch Miss Penalty)
- 구조적 해저드 병목: ALU 등 특정 유닛으로 연산이 쏠려 ILP 저하 → 컴파일러의 명령어 혼합(Instruction Mix) 최적화 및 비대칭 실행 유닛 다중 배치 (지표: 유닛 가동 대기시간)

---

## Ⅵ. 실무 적용 및 결론

**적용 방안 3개:**
1. 컴파일러 최적화 옵션 연계: GCC/LLVM 컴파일 시 O3 옵션을 통해 루프 언롤링(Loop Unrolling)과 소프트웨어 파이프라이닝을 강제 적용하여 정적 ILP 블록 크기 확장
2. SMT(동시 멀티스레딩) 결합 아키텍처: 단일 스레드의 ILP 한계로 실행 유닛이 비는 시간(Bubble)을, 완전히 독립된 다른 스레드의 명령어(TLP)로 동시 채워 넣어 자원 활용률 극대화
3. 프로파일 기반 최적화(PGO): 프로그램 실행 런타임의 분기 패턴과 메모리 참조 주소 충돌 패턴을 수집하여 재컴파일 시 VLIW 패키징 힌트로 제공, 분기 실패 최소화

**결론 (2줄):**
- 기술사 판단: 단일 코어 성능을 책임지는 ILP는 슈퍼스칼라와 OoO를 통해 정점에 달했으나, 복잡도 대비 전력 효율 한계(Power Wall)로 인해 구조적 정체기를 맞았다.
- 향후 방향: 현대 아키텍처는 무리하게 단일 스레드의 ILP 윈도우를 넓히기보다 멀티코어 중심의 TLP 체제로 전환하였으며, 딥러닝과 같은 대규모 벡터 연산에서는 SIMD 및 데이터 수준 병렬성(DLP) 강화로 패러다임이 이동하고 있다.
