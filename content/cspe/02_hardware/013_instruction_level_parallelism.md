# 📖 【암기용】 개념 완전 이해

## 한눈에
- **개요**: 명령어 수준 병렬성(ILP)은 단일 스레드 프로그램 하나 안에서 서로 의존성 없는 명령어들을 찾아 동시에 겹쳐 실행하여 사이클당 처리량(IPC)을 높이는 잠재적 병렬성이다.
- **왜 필요한가**: 클럭 주파수를 더 올리면 전력이 급증하는 Power Wall에 막혀, 클럭을 안 올리고도 코드 속에 숨은 독립 연산을 한꺼번에 처리해 단일 코어 실효 성능을 끌어올려야 하기 때문이다.
- **핵심 직관**: 요리를 순서대로 하나씩 하면 오래 걸리지만, 물 끓이기와 야채 썰기처럼 서로 안 겹치는 작업을 동시에 진행하면 전체 시간이 줄어드는 것과 같다.

## 핵심 용어 정리 (내부에 등장하는 것들)

먼저 답안에 나오는 표기·수치를 비유와 함께 풀어 둔다. 최상위 키워드는 ILP다.

| 용어/표기 | 의미 | 비유·예 |
|:---|:---|:---|
| ILP | 단일 스레드 내 명령어를 동시 실행하는 병렬성 | "한 사람 작업 안에서 겹치는 부분 동시 진행" |
| IPC (Instructions Per Clock) | 한 클럭에 실행 완료되는 평균 명령어 수, ILP의 성능 척도 | IPC 2 = 1클럭에 명령어 2개 완료 |
| 파이프라이닝 (007 참조) | 명령어를 여러 단계로 쪼개 컨베이어처럼 겹쳐 실행하는 시간적 병렬성 | "공장 조립 라인" |
| 다중 발행 (Multiple Issue) | 한 클럭에 여러 명령어를 인출·실행하는 공간적 병렬성 | "다차선 도로" |
| 진성 의존성 (RAW) | 앞 결과를 뒤가 읽어야 해 동시 실행 불가한 참 의존 | "앞사람 서류가 넘어와야 결재" |
| 가성 의존성 (WAR/WAW) | 실제 데이터 흐름은 없고 레지스터 이름만 겹친 가짜 의존 | "이름만 같은 서류, 리네이밍으로 분리" |
| 제어 의존성 | 조건 분기 결과에 따라 실행 여부가 갈리는 의존 | "if 결과 나와야 다음 진행" |
| TLP (스레드 수준 병렬성) | 여러 스레드를 동시 실행하는 병렬성 (014 멀티코어) | ILP의 상위 대안 |

## 깊이 이해
- **배경·문제의식**: 클럭만 올리던 성능 향상 공식이 Power Wall(전력=클럭³ 비례)에 막히자, 프로그래머가 쓴 순차 코드 내부에 숨은 "서로 무관한 연산"을 찾아 한꺼번에 처리할 필요가 생겼다.
- **작동 원리(어떻게+왜)**: ILP는 두 축의 결합으로 나온다. 시간적 축은 파이프라인 단수를 늘려 더 많은 명령어를 동시에 흐르게 하고, 공간적 축은 실행 유닛을 여러 개 두어 한 클럭에 다중 발행한다. 구현은 하드웨어가 런타임에 의존성을 검사하는 동적 방식(010 슈퍼스칼라 + 012 비순서 실행)과, 컴파일러가 미리 독립 명령어를 묶는 정적 방식(011 VLIW)으로 나뉜다. 구체 구현은 해당 노트에 위임하고, 여기서는 ILP라는 목표와 그 한계에 집중한다.
- **비유**: 순차 실행이 왕복 1차선 도로라면, ILP는 차로를 4차선으로 넓히고(다중 발행) 신호등 없이 차를 연속 진입시키는(파이프라인) 것이다.
- **구체 예시**: `X = A + B`와 `Y = C + D`는 쓰는 변수가 모두 달라 의존성이 없다. CPU가 이를 판별해 2개 ALU에 동시에 밀어넣으면 1클럭에 둘 다 끝나 IPC 2를 달성한다. 반대로 `X = A + B; Z = X + C`는 X를 기다려야 해(RAW) 병렬화가 불가능하다.
- **흔한 오해**: ILP는 멀티코어(TLP)와 다르다. ILP는 스레드 하나 안에서 명령어를 쪼개는 것이고, TLP는 아예 스레드가 여럿일 때 코어를 나눠 쓰는 것이다. 또 하드웨어를 아무리 키워도 코드에 분기와 진성 의존성이 많으면 뽑을 수 있는 ILP 자체가 없다.

## 연결 개념
- **010 슈퍼스칼라 / 012 비순서 실행**: 동적 ILP의 하드웨어 구현.
- **011 VLIW**: 정적 ILP의 컴파일러 구현.
- **014 멀티코어**: ILP 한계를 TLP로 우회하는 상위 패러다임.

# 📝 【답안용】 시험 답안 템플릿

## 핵심 인사이트 (3줄 요약)

> 1. **본질**: ILP는 단일 스레드 내 명령어의 데이터·제어 의존성을 회피해 다수 연산을 동시 중첩 실행하는 마이크로아키텍처의 성능 목표이며, 척도는 IPC임.
> 2. **가치**: 클럭 상향의 발열 한계(Power Wall)를 우회해 IPC를 1.0 이상으로 끌어올려 단일 코어의 실효 성능을 향상시킴.
> 3. **판단**: 진성 의존성·분기라는 원천적 한계로 ILP 확장이 정체되자, 성능 향상 축이 멀티코어 기반 TLP로 전환됨.

## 출제 의도 및 답안 포인트

| 출제 의도 | 반드시 짚을 핵심 | 감점 회피 포인트 |
|:---|:---|:---|
| 단일 스레드 성능 향상 원리 이해 | 시간적(파이프라인)+공간적(다중 발행), IPC 향상 | TLP와 개념 혼동, 하드웨어 기능 단순 나열 |
| ILP 구현 기술 분류 역량 | 동적(슈퍼스칼라·OoO) vs 정적(VLIW·컴파일러) 스케줄링 | 구현 위임 대상 미분류, 한계(의존성) 누락 |

> 요약: 단일 프로그램 속 병렬성을 하드웨어(동적)·소프트웨어(정적)가 어떻게 추출하는지와, 데이터·제어 해저드에 의한 확장 한계를 함께 짚어야 함.

---

## Ⅰ. 개요 및 필요성

- 개요: ILP는 순차 코드 내 의존성 없는 명령어를 찾아 동시 실행하는 잠재적 병렬성임(단일 스레드 대상).
- 배경: 트랜지스터 집적도 한계와 동적 전력 급증(Power Wall)으로 클럭 상향 기반 성능 향상 공식 종료됨.
- 필요성: 클럭 유지 상태에서 단일 코어 처리량을 배가하기 위해 IPC를 1.0 이상으로 높이는 파이프라인·다중 발행 기술 필요함.

---

## Ⅱ. 구조 및 구성요소

```text
순차 프로그램 (IPC <= 1)
  -> 시간적 병렬성: 슈퍼파이프라이닝 (단계 세분화 / 클럭 상향)
  -> 공간적 병렬성: 슈퍼스칼라(010) / VLIW(011) (다중 발행, IPC > 1)
  -> 실행 최적화: 비순서 실행(012) / 레지스터 리네이밍 (가성 의존성 타파)
```

| 구성요소 | 역할 | 비고 |
|:---|:---|:---|
| 깊은 파이프라인 | 명령어 단계를 잘게 쪼개 동시 체류량·클럭 향상 (시간 축) | 단수 과다 시 분기 실패 페널티 증가 |
| 다중 실행 유닛 | ALU·FPU 등 여러 유닛에 한 클럭 다중 발행 (공간 축) | IPC > 1 달성의 물리적 근거 |
| 동적 스케줄러 | 런타임에 의존성 검사·리네이밍으로 스톨 은닉 (012 위임) | 하드웨어 복잡도 N² 증가 |
| 정적 스케줄러 | 컴파일러가 독립 명령어 사전 묶음 (011 위임) | 루프 언롤링·명령어 재배치 |

> 요약: ILP는 파이프라인 단수(시간 축)와 다중 실행 유닛(공간 축)의 물리적 결합에 동적·정적 스케줄링 로직을 더해 완성됨.

---

## Ⅲ. 동작원리 및 흐름도

```text
명령어 인출 -> 의존성 분석 -> 병렬 그룹 추출 -> 다중 유닛 동시 실행 -> 순차 커밋
```

- 1단계 [의존성 스캔]: 하드웨어(또는 컴파일러)가 명령어 간 RAW·WAR·WAW 및 분기 충돌을 스캔함.
- 2단계 [가성 의존성 해체]: 레지스터 리네이밍이 WAR·WAW로 묶인 명령어를 물리 레지스터 분리로 독립시킴.
- 3단계 [윈도우 스케줄링]: 예약 스테이션에서 피연산자가 준비된 명령어를 순서 무관하게 동시 선택함.
- 4단계 [병렬 실행·커밋]: 여러 실행 유닛에 동시 배분해 연산하고, ROB가 원래 순서로 커밋해 정합성을 보장함.

> 요약: 명령어 윈도우 내 해저드 요인을 해체하고 독립 연산 그룹을 묶어 실행 유닛 가동률을 끌어올리는 과정임.

---

## Ⅳ. 특징
- 실효 IPC 향상: 순차 대비 2~4배 처리량을 달성해 단일 애플리케이션 지연 시간을 최소화함.
- 원천적 한계: 코드의 진성 의존성(RAW) 비율이 높으면 윈도우를 아무리 넓혀도 뽑을 ILP 자체가 없음.
- 수확 체감: 스케줄링 하드웨어 복잡도가 발행 폭 N에 대해 N² 단위로 증가해 일정 폭 이상에서 전력 효율(Perf/Watt)이 급락함.

> 요약: ILP는 단일 스레드 최적화의 핵심이나, 프로그램 본연의 순차성과 하드웨어 복잡도 폭증이라는 명확한 한계를 지님.

## Ⅴ. 심화 비교 및 적용 판단

| 구분 | ILP (명령어 수준) | TLP (스레드 수준) |
|:---|:---|:---|
| 추출 단위 | 단일 스트림 내 명령어 | 스레드·프로세스 |
| 구현 주체 | 단일 코어 내 H/W 스케줄러·컴파일러 | 멀티코어(SMP)·SMT |
| 의존성 제약 | 진성 의존성에 극도로 민감 | 스레드 간 독립성 높음(동기화 예외) |
| 확장 한계 | 발행 폭 증가 시 N² 복잡도 | 코어 수 증가 시 암달 법칙 제약 |

> 요약: 단일 작업의 반응 속도는 ILP가 좌우하고, 웹 서버·렌더링처럼 다중 작업 동시 처리가 필요하면 TLP로 확장해야 함.

**리스크·대응 (기본은 불릿):**
- 제어 의존성에 의한 파이프라인 플러시 — 조건 분기 1회 오예측이 수십 개 병렬 명령어를 무효화 — TAGE 등 분기 예측기로 오예측률 5% 이하 통제(지표: Branch Miss Penalty)
- 구조적 해저드 병목 — 특정 유닛으로 연산 쏠림 — 컴파일러 명령어 혼합 최적화·비대칭 유닛 다중 배치(지표: 유닛 대기 시간)

## Ⅵ. 실무 적용 및 결론

**적용 방안 3개:**
1. 컴파일러 정적 ILP 확장: GCC/LLVM `-O3`으로 루프 언롤링·소프트웨어 파이프라이닝을 적용해 병렬 블록 크기를 확대함.
2. SMT 결합: 단일 스레드 ILP 부족으로 비는 실행 유닛(Bubble)을 독립 스레드 명령어로 채워 자원 활용률을 극대화함.
3. PGO(프로파일 기반 최적화): 런타임 분기·참조 패턴을 수집해 재컴파일 시 명령어 배치 힌트로 반영, 오예측을 최소화함.

**결론 (2줄):**
- 기술사 판단: 반응 속도가 핵심인 단일 스레드 워크로드면 ILP 확장(OoO·슈퍼스칼라)에 투자하고, 처리량이 핵심인 다중 워크로드면 TLP(멀티코어)로 축을 옮겨야 함.
- 향후 방향: 무리한 ILP 윈도우 확장 대신 멀티코어 TLP와, 대규모 벡터 연산의 SIMD·DLP 강화로 패러다임이 이동 중임.
