## Ⅰ. 개요
- **정의**: CXL 스위치를 통해 다수 호스트가 공유 메모리 풀을 동적 할당·회수하는 기술
- **배경/필요성**: 서버별 고정 메모리 구조에서 유휴 메모리(Stranded Memory)가 낭비되고, CPU 핀 수 제약으로 단일 서버 메모리 용량에 물리적 한계가 존재함
- **비유**: 각자 물통(메모리)을 들고 다니던 등산객이 공용 정수기(메모리 풀)를 설치해 목마른 사람부터 사용하는 구조

| 출제 의도 | 반드시 짚을 핵심 | 감점 회피 포인트 |
|:---|:---|:---|
| CXL 상위 활용 구조 이해 | 스위치 기반 동적 할당, Fabric Manager 역할 | CXL 프로토콜 자체(035 참조)와 풀링 개념 혼동 금지 |

> 요약: 서버 간 메모리 자원 격리 문제를 CXL 스위치 기반 공유 풀로 해소하는 기술임

## Ⅱ. 구성요소
```text
[Host A] [Host B] [Host C]
    |        |        |
    +---+----+----+---+
        |         |
        v         v
  +-- CXL Switch --+  <-- Fabric Manager 제어
        |         |
        v         v
  [CXL Mem Dev 1] [CXL Mem Dev 2]  <-- 공유 메모리 풀
```

| 구성요소 | 설명 | 비유 |
|:---|:---|:---|
| CXL 스위치 | 호스트와 메모리 디바이스 간 경로를 동적 연결하는 하드웨어 | 배전반: 전력을 필요한 곳에 분배 |
| Fabric Manager | 스위치에 연결된 장치를 탐색하고 메모리 할당·회수를 제어하는 소프트웨어 | 건물 관리실: 빈 방을 배정 |
| CXL Memory Device | Type-3 CXL 장치로 호스트에 종속되지 않는 독립 메모리 모듈 | 공용 창고의 선반 |
| MLD (Multi-Logical Device) | 하나의 물리 메모리를 논리 단위(LD)로 분할하여 복수 호스트에 제공 | 칸막이로 나눈 공용 서재 |

> 요약: CXL 스위치와 Fabric Manager가 독립 메모리 디바이스를 호스트에 동적 매핑하는 구조임

## Ⅲ. 절차
```text
장치 탐색 -> LD 분할 -> 동적 할당 -> 해제/회수
```
- 1단계: Fabric Manager가 CXL 스위치에 연결된 호스트·메모리 디바이스를 열거(Enumerate)
- 2단계: 물리 메모리 디바이스를 논리 단위(LD)로 분할하고 주소 공간을 구성
- 3단계: 호스트 A가 메모리를 요청하면 Fabric Manager가 LD를 호스트 A의 물리 주소 공간에 매핑
- 4단계: 워크로드 종료 시 LD를 회수하여 다른 호스트에 재할당

> 요약: 탐색-분할-할당-회수의 4단계로 메모리를 서버 간 동적 이동시키는 절차임

## Ⅳ. 문제점
- 접근 지연 증가: 원격 메모리가 CXL 스위치를 경유하므로 로컬 DDR 대비 100~300ns 지연 추가됨
- 캐시 일관성 오버헤드: 복수 호스트가 동일 LD를 공유(Shared Memory)할 때 CXL.cache 프로토콜의 스누핑 트래픽이 대역폭을 소모함
- 장애 전파 위험: CXL 스위치 단일 장애 시 연결된 모든 호스트의 메모리 접근이 중단됨

> 요약: 지연 증가, 일관성 오버헤드, 스위치 단일 장애점이 풀링의 주요 과제임

## Ⅴ. 개선방안
1. 단기: NUMA-aware OS 스케줄러를 적용하여 지연 민감 워크로드를 로컬 메모리에 우선 배치
2. 중기: CXL 3.0의 하드웨어 일관성 엔진(Back-Invalidate)을 활용하여 스누핑 트래픽 감소
3. 장기: 스위치를 다중 계층 패브릭(Multi-tier Fabric)으로 구성하고 이중화하여 단일 장애점 제거

> 요약: OS 스케줄링 최적화 → 프로토콜 개선 → 패브릭 이중화 순서로 문제를 해소함

## Ⅵ. 전망
- 발전 방향: CXL 3.0 패브릭을 통해 랙 스케일(Rack-Scale) 메모리 공유가 실현되고, 컴포저블 인프라로 확장됨
- 기술사적 판단: 메모리를 CPU 종속 자원에서 독립 네트워크 자원으로 전환하는 패러다임 전환의 핵심 기술임
- 기술사 제언: 도입 시 워크로드별 지연 허용 한계를 측정하고, 로컬/원격 메모리 비율을 설계 단계에서 결정할 필요
