## Ⅰ. 개요
- **정의**: 연산 강도 대비 달성 가능한 최대 성능을 시각화하는 하드웨어 성능 분석 모델
- **배경/필요성**: 프로세서의 연산 능력과 메모리 대역폭 중 어느 쪽이 병목인지 정량적으로 판단할 수단이 필요함
- **비유**: 수도관(메모리 대역폭)과 세탁기(연산 유닛)에서 느린 쪽이 전체 속도를 결정하는 것과 유사함

| 출제 의도 | 반드시 짚을 핵심 | 감점 회피 포인트 |
|:---|:---|:---|
| 성능 병목 분석 능력 확인 | 연산 강도(OI) 정의와 두 영역 구분 | 피크 FLOPS만 언급하고 대역폭 한계를 누락하지 않을 것 |

> 요약: 연산 강도 기반으로 컴퓨트 바운드와 메모리 바운드를 구분하는 성능 상한 모델임

## Ⅱ. 구성요소
```text
Performance (GFLOPS)
  |         ___________  <-- Peak FLOPS (천장)
  |        /
  |       / <-- Memory Bandwidth Slope
  |      /
  |     /
  |    /
  +--/-------------------> Operational Intensity (FLOP/Byte)
       ^
       Ridge Point
```

| 구성요소 | 설명 | 비유 |
|:---|:---|:---|
| Peak FLOPS | 프로세서가 이론적으로 달성 가능한 최대 연산 처리량 | 세탁기 최대 회전수 |
| Memory Bandwidth | 메모리에서 데이터를 읽고 쓰는 최대 전송률(GB/s) | 수도관 최대 유량 |
| Operational Intensity | 전송 바이트당 수행 연산 수(FLOP/Byte) | 물 1L당 세탁 가능 횟수 |
| Ridge Point | 메모리 바운드에서 컴퓨트 바운드로 전환되는 OI 지점 | 수도관과 세탁기가 동시에 포화되는 균형점 |

> 요약: 피크 연산력, 메모리 대역폭, 연산 강도 세 축으로 병목 영역을 결정함

## Ⅲ. 절차
```text
HW 스펙 수집 --> OI 계산 --> 그래프 매핑 --> 병목 판정
```
- 1단계: 대상 프로세서의 피크 FLOPS와 메모리 대역폭(GB/s)을 측정·수집함
- 2단계: 대상 커널의 총 연산량과 총 메모리 전송량으로 OI(FLOP/Byte) 계산함
- 3단계: 루프라인 그래프 위에 커널의 OI와 달성 성능을 점으로 매핑함
- 4단계: 천장선 대비 위치로 메모리 바운드 또는 컴퓨트 바운드 여부를 판정함

> 요약: 스펙 수집 후 OI를 계산하여 그래프 상 위치로 병목 유형을 판정하는 절차임

## Ⅳ. 문제점
- 캐시 계층 미반영: 단일 메모리 대역폭만 사용 — L1/L2/L3 캐시 효과를 무시하여 실측과 괴리 발생함
- 다중 병목 미분리: 연산과 메모리 두 축만 존재 — 네트워크 I/O, 분기 예측 실패 등 추가 병목을 표현 불가함
- 정적 분석 한계: 런타임 동적 변화 미반영 — 스케줄링, 주파수 스로틀링에 따른 성능 변동 포착이 어려움

> 요약: 캐시 계층, 다중 병목, 런타임 동적 변화를 반영하지 못하는 한계가 있음

## Ⅴ. 개선방안
1. 단기: 캐시 인지 루프라인(CARM) 적용 — L1/L2/L3 별도 대역폭 천장선 추가
2. 중기: 확장 루프라인에 네트워크·I/O 축을 추가하여 다중 병목 동시 시각화
3. 장기: 런타임 프로파일러와 연동하여 동적 OI 변화를 실시간 추적하는 자동화 도구 구축

> 요약: 캐시 계층 세분화, 다축 확장, 런타임 연동 순으로 모델 정밀도를 높여야 함

## Ⅵ. 전망
- 발전 방향: AI 가속기(GPU, NPU)의 Tensor 연산 특성에 맞춘 전용 루프라인 모델이 확산 중임
- 기술사적 판단: 이기종 컴퓨팅 환경에서 병목 분석 프레임워크의 중요도가 증가함
- 기술사 제언: 하드웨어 선정 시 벤치마크 수치만이 아닌 루프라인 기반 병목 분석을 병행할 것을 권고함
