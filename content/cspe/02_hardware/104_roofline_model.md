## Ⅰ. 개요
- **정의**: 연산 강도 대비 달성 가능 성능 상한을 시각화하는 하드웨어 성능 분석 모델
- **배경/필요성**: 프로세서의 연산 처리량과 메모리 대역폭 중 어느 쪽이 병목인지 정량 판별이 필요함
- **비유**: 공장(연산)과 도로(대역폭) 중 좁은 쪽이 전체 생산량을 결정하는 것과 같음

| 출제 의도 | 반드시 짚을 핵심 | 감점 회피 포인트 |
|:---|:---|:---|
| HW 병목 분석 역량 확인 | 연산 강도(OI) 축과 성능 천장 두 직선 교차 | 메모리-바운드/컴퓨트-바운드 구분 기준 명시 필요 |

> 요약: 연산 강도 기준으로 메모리-바운드와 컴퓨트-바운드 영역을 구분하는 성능 상한 모델임

## Ⅱ. 구성요소
```text
Performance (FLOPS)
  |         ______________ Peak Compute
  |        /
  |       / Ridge Point
  |      /
  |     / Memory BW Slope
  |    /
  +---/------------------------> Operational Intensity (FLOP/Byte)
```

| 구성요소 | 설명 | 비유 |
|:---|:---|:---|
| 연산 강도(OI) | 바이트당 부동소수점 연산 수(FLOP/Byte) | 원자재 1kg당 생산 제품 수 |
| 피크 연산 성능 | 프로세서가 달성 가능한 최대 FLOPS | 공장 최대 생산 라인 수 |
| 메모리 대역폭 경사 | BW x OI로 결정되는 대역폭 제한 직선 | 원자재 운송 도로 폭 |
| 능선점(Ridge Point) | 두 직선이 만나는 OI 임계값 | 도로와 공장이 균형 잡히는 지점 |

> 요약: OI 축 위에 대역폭 경사와 연산 천장 두 직선으로 병목 영역을 구분함

## Ⅲ. 절차
```text
HW 스펙 수집 --> OI 계산 --> 루프라인 도식화 --> 병목 판별
```
- 1단계: 대상 프로세서의 피크 FLOPS와 메모리 대역폭(GB/s) 측정
- 2단계: 워크로드별 연산 강도(FLOP/Byte) 산출
- 3단계: 로그-로그 축에 대역폭 경사선과 피크 연산 수평선 도식화
- 4단계: 워크로드 OI를 능선점과 비교하여 메모리-바운드/컴퓨트-바운드 판별

> 요약: HW 스펙과 워크로드 OI를 로그-로그 도식 위에 배치하여 병목을 판별함

## Ⅳ. 문제점
- 캐시 계층 미반영: 단일 대역폭만 가정 — L1/L2/L3 각 계층별 실효 대역폭 차이가 누락됨
- 멀티테넌트 간섭 무시: 단독 실행 전제 — 공유 자원 경합 시 실측 성능 괴리 발생함
- SIMD/파이프라인 활용률 미반영: 피크 연산을 100% 가정 — 분기·의존성으로 실제 IPC가 낮아짐

> 요약: 캐시 계층·자원 경합·실효 IPC 등 실측 괴리 요인을 반영하지 못함

## Ⅴ. 개선방안
1. 단기: 캐시 인지 루프라인(CARL) 적용으로 L1/L2/L3별 대역폭 천장 다중 표현
2. 중기: 동시 실행 워크로드의 공유 자원 경합 모델을 오버레이로 추가
3. 장기: 실측 프로파일링(PMU 카운터) 기반 동적 루프라인 자동 생성 도구 구축

> 요약: 캐시 계층별 천장 다중화와 실측 기반 동적 모델링으로 정밀도를 높임

## Ⅵ. 전망
- 발전 방향: GPU/NPU 등 이기종 가속기별 루프라인 통합 뷰 확대
- 기술사적 판단: AI 워크로드 최적화에서 병목 사전 판별 도구로 활용도 증가
- 기술사 제언: HW 선정·커널 튜닝 의사결정 시 루프라인 기반 정량 근거 제시 권장
