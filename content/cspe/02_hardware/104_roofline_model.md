## Ⅰ. 개요
- **정의**: 연산 강도 대비 달성 가능 성능 상한을 시각화하는 분석 모델
- **배경/필요성**: 프로세서 연산력과 메모리 대역폭 중 어느 쪽이 병목인지 정량 판별이 필요함
- **비유**: 도로(대역폭)와 공장(연산력) 중 좁은 쪽이 전체 처리량 상한을 결정하는 구조임

| 출제 의도 | 반드시 짚을 핵심 | 감점 회피 포인트 |
|:---|:---|:---|
| HW 병목 분석 역량 확인 | 연산 강도(OI) 기준 두 영역 구분 | 단위(FLOPS, Byte/s) 혼동 주의 |

> 요약: 연산 강도 축과 성능 축으로 병목 지점을 식별하는 시각적 성능 분석 모델임

## Ⅱ. 구성요소
```text
Performance (FLOP/s)
  |         ___________  <-- Peak Compute (천장)
  |        /
  |       / <-- Memory Bandwidth Slope
  |      /
  |     /
  +----------------------------> Operational Intensity (FLOP/Byte)
       ^
       Ridge Point
```

| 구성요소 | 설명 | 비유 |
|:---|:---|:---|
| Peak Compute | 프로세서 최대 연산 처리량(GFLOPS) | 공장 최대 생산 속도 |
| Memory Bandwidth | 메모리-프로세서 간 최대 데이터 전송률(GB/s) | 원자재 운반 도로 폭 |
| Operational Intensity | 전송 바이트당 수행 연산 수(FLOP/Byte) | 원자재 1톤당 생산 제품 수 |
| Ridge Point | 연산 병목과 메모리 병목의 교차점 | 도로와 공장 균형점 |

> 요약: 연산력, 대역폭, 연산 강도, 교차점 네 요소로 병목 영역을 판별함

## Ⅲ. 절차
```text
HW Spec 수집 --> OI 산출 --> Roofline 도식화 --> 병목 판별/최적화
```
- 1단계: 대상 HW의 Peak Compute와 Memory Bandwidth 사양 수집
- 2단계: 워크로드의 Operational Intensity(총 연산량 / 총 메모리 접근량) 산출
- 3단계: 로그-로그 그래프에 천장선과 경사선을 도식화
- 4단계: 워크로드 점이 경사 구간이면 메모리 최적화, 천장 구간이면 연산 최적화 수행

> 요약: HW 사양 수집부터 병목 식별 및 최적화 방향 도출까지 4단계로 수행함

## Ⅳ. 문제점
- 캐시 계층 미반영: 단일 대역폭 가정 — L1/L2/L3 캐시 효과를 무시하여 실측과 괴리 발생
- 다중 병목 미표현: 2차원 평면 한계 — 네트워크, 레이턴시 등 추가 병목 표현 불가
- 동적 워크로드 미반영: 정적 OI 가정 — 실행 중 연산 강도 변화를 포착하지 못함

> 요약: 캐시 계층, 다중 병목, 동적 워크로드에 대한 표현력이 제한적임

## Ⅴ. 개선방안
1. 단기: Cache-Aware Roofline — 캐시 레벨별 대역폭 천장선을 추가하여 계층적 분석 수행
2. 중기: 네트워크·레이턴시 축을 추가한 다차원 Roofline 확장 모델 적용
3. 장기: 런타임 프로파일러 연동으로 동적 OI 변화를 실시간 추적하는 자동화 도구 구축

> 요약: 캐시 계층화, 다차원 확장, 동적 프로파일링으로 분석 정밀도를 높임

## Ⅵ. 전망
- 발전 방향: AI 가속기(GPU, NPU) 전용 Roofline 변형 모델 확산 전망
- 기술사적 판단: HW-SW 공동 최적화(Co-design) 설계 시 정량적 판단 근거로 활용 가치 높음
- 기술사 제언: 성능 튜닝 프로젝트에서 Roofline 기반 병목 사전 분석을 표준 절차화할 필요
