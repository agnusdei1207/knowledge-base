# 📖 【암기용】 개념 완전 이해

> 목적: 하드웨어가 하던 복잡한 동시 실행 판단을 소프트웨어(컴파일러)에게 몽땅 떠넘긴 VLIW의 철학과 한계를 완벽히 이해하게 만든다.

## 한눈에
- **개요**: **정적 스케줄링(Static Scheduling)**으로 명령어 수준 병렬성(ILP, 013 참조)을 구현하는 아키텍처. VLIW(Very Long Instruction Word)는 서로 의존성이 없는 여러 명령어를 컴파일러가 **컴파일 타임**에 미리 찾아 하나의 긴 명령어 워드로 묶고, CPU는 그 워드를 그대로 쪼개 실행만 한다.
- **왜 필요한가**: 010에서 본 슈퍼스칼라의 발행 유닛(Issue Unit)은 런타임에 명령어 간 의존성을 검사하는 하드웨어인데, 이 검사 회로는 이슈 폭이 넓어질수록 비교해야 할 명령어 쌍이 급격히 늘어 복잡하고 전력을 많이 먹는다. VLIW는 이 검사를 통째로 컴파일 타임으로 옮겨 하드웨어를 가볍게 만든다.
- **핵심 직관**: 슈퍼스칼라가 매번 교차로에서 신호수(하드웨어)가 눈치껏 차 3대를 보내는 것이라면, VLIW는 출발 전에 내비게이션(컴파일러)이 3대를 미리 세트로 묶어 전용 도로로 함께 내보내는 것이다.

## 핵심 용어 정리 (내부에 등장하는 것들)

| 용어 | 의미 | 비유 |
|:---|:---|:---|
| 정적 스케줄링 | 컴파일 타임에 실행 순서·병렬 배치를 확정하는 방식 (010 동적 스케줄링과 대비) | 여행 전 미리 짜둔 시간표 |
| ILP | 정적 스케줄링으로 뽑아내려는 목표치인 명령어 수준 병렬성 (013 참조) | 동시에 처리 가능한 일감의 개수 |
| VLIW 워드/번들(Bundle) | 여러 실행 유닛에 1:1로 대응하는 서브 명령어들을 묶은 한 개의 긴 명령어 | 도시락 한 통에 반찬 여러 개를 미리 담아둔 것 |
| 슬롯(Slot) | 워드 안에서 특정 실행 유닛(정수/소수/메모리 등) 전용으로 정해진 자리 | 도시락 칸막이 |
| NOP 패딩 | 묶을 독립 명령어가 부족할 때 빈 슬롯을 채우는 무의미 연산 | 빈 도시락 칸을 빈 종이로 채우는 것 |
| 코드 팽창(Code Bloat) | NOP가 많아져 바이너리 용량이 커지는 현상 | 반찬은 적은데 도시락 통만 큰 것 |
| EPIC / IA-64 | VLIW의 고정 번들 문제를 완화한 인텔·HP의 개선형 아키텍처(아이태니엄) | 칸막이 크기를 유동적으로 조절한 도시락 |

## 깊이 이해

### 배경 — 왜 검사를 컴파일러로 옮겼나 (010 대비 delta)
- 010에서 슈퍼스칼라의 발행 유닛은 매 클럭 인출된 명령어들 사이의 의존성을 실시간으로 비교한다. 명령어 N개를 동시에 검사하려면 최악의 경우 서로 짝을 지어 비교해야 해 회로 복잡도가 N이 커질수록 빠르게 늘어난다.
- 컴파일러는 프로그램 전체를 미리 볼 수 있고 시간 제약도 없다. "어차피 컴파일러가 코드를 분석해 의존성 없는 명령어를 찾을 수 있다면, 그 결과를 아예 명령어 포맷에 고정해서 CPU에 넘기자"는 것이 VLIW의 발상이다. 1990년대 후반 인텔·HP가 이 철학으로 아이태니엄(Itanium, IA-64)을 만들었다.

### 워드 구조를 수치로 이해하기
- 아이태니엄의 VLIW 번들은 128비트다. 그 안에 41비트짜리 명령어 슬롯 3개(41×3=123비트)와, 이 3개를 어떻게 실행할지 알려주는 5비트 템플릿 필드(123+5=128비트)가 들어간다.
- 슬롯이 3개인데 컴파일러가 찾아낸 독립 명령어가 1개뿐이면, 나머지 2개 슬롯은 NOP로 채워야 한다 — 이 경우 슬롯 이용률은 1/3 ≈ 33%이고 67%는 낭비다. 반대로 3개를 다 채우면 이용률 100%로, 이상적으로는 1워드로 3명령어를 1클럭에 처리한다.

### 판별 원리 — VLIW인지 어떻게 알아보나
- 핵심 질문은 "명령어 집합 구조(ISA) 자체가 병렬 슬롯을 명시하는가"이다. 슈퍼스칼라는 ISA상으로는 평범한 순차 명령어 스트림이고 하드웨어가 몰래 여러 개를 묶어 실행한다. VLIW는 ISA 자체가 이미 "이 워드에는 정수 연산, 소수 연산, 메모리 연산이 각각 이 슬롯에 있다"고 고정해 컴파일러가 만든 병렬 구조를 그대로 노출한다. 그래서 VLIW 바이너리는 슬롯 배치가 하드웨어 세대(실행 유닛 개수)와 어긋나면 재컴파일이 필요하다.

### 성공한 곳과 실패한 곳
- 범용 CPU(아이태니엄)에서는 실패했다. 분기가 잦고 실행 흐름을 예측하기 힘든 일반 프로그램에서는 컴파일러가 미리 병렬 블록을 채우기 어려워 NOP가 많이 남았고, 기존 x86 소프트웨어와도 호환되지 않았다.
- 대신 정해진 루틴을 반복하는 도메인에서는 대성공을 거뒀다. 예: 퀄컴 헥사곤(Hexagon) DSP는 4개 슬롯 VLIW 구조로 통신 신호 처리를 담당하며, 분기가 거의 없는 신호처리 루프에서는 슬롯을 거의 100% 채울 수 있어 전력 대비 성능이 매우 높다.

### 비유와 흔한 오해
- **오해**: "하드웨어가 단순해지니 무조건 이득"이라는 생각이다. 실제로는 병렬화할 독립 명령어가 부족한 코드에서 NOP가 쌓여 코드 팽창이 심해지고, 캐시(I-Cache)에 담기는 실제 명령어 밀도가 낮아져 오히려 캐시 적중률이 떨어질 수 있다.

## 연결 개념
- 010 슈퍼스칼라 — 같은 ILP 목표를 하드웨어 동적 스케줄링으로 푸는 대척점
- 013 ILP — VLIW가 컴파일 타임에 추출하려는 병렬성의 정량 지표
- EPIC(IA-64) — VLIW의 고정 슬롯 문제를 템플릿 필드로 완화한 개선형

# 📝 【답안용】 시험 답안 템플릿

> 목적: 시험장에서 25분에 그대로 쓰는 답안 양식. 

## 핵심 인사이트 (3줄 요약)

> 1. **본질**: VLIW는 하드웨어의 동적 스케줄링 오버헤드를 제거하기 위해, 소프트웨어(컴파일러)가 컴파일 타임에 의존성이 없는 다수의 명령어를 하나의 긴 명령어 단어(Word)로 정적 묶음 처리하는 아키텍처다.
> 2. **가치**: 스케줄링 하드웨어(Instruction Issue Unit)를 제거하여 CPU 구조를 단순화하고 트랜지스터 밀도와 전력 효율(Performance/Watt)을 극대화한다.
> 3. **판단 포인트**: 범용 프로세서(CPU) 시장에서는 하위 호환성 결여와 컴파일러 의존성 한계로 실패했으나, 예측 가능한 벡터/배열 연산이 주를 이루는 DSP, NPU 등 도메인 특화 아키텍처(DSA)에서 주류로 자리 잡았다.

## 출제 의도 및 답안 포인트

| 출제 의도 | 반드시 짚을 핵심 | 감점 회피 포인트 |
|:---|:---|:---|
| 프로세서 병렬성(ILP)을 소프트웨어 레벨로 전이하는 철학 이해 | VLIW 포맷, 컴파일러 기반 정적 스케줄링, NOP 낭비 | 슈퍼스칼라와 구별 없이 단순히 명령어가 길다고만 서술 |
| VLIW의 시장 적용 한계와 도메인 특화 부활 구조 이해 | 호환성 문제, 코드 팽창(Code Bloat), DSP/GPU 적용 | 인텔 아이태니엄의 실패만 적고 임베디드 성공 사례를 누락 |

> 요약: 스케줄링의 책임을 "하드웨어에서 소프트웨어로" 옮긴 트레이드오프(구조 단순화 vs 코드 팽창/호환성 상실)를 명확히 대조해야 한다.

## Ⅰ. 개요 및 필요성

- 정의: 컴파일러가 데이터 의존성이 없는 다수의 서브 명령어들을 결합하여 하나의 매우 긴 명령어(VLIW)로 생성·실행하는 아키텍처
- 배경: 슈퍼스칼라 하드웨어의 명령어 검사(의존성 파악) 회로 복잡도가 N²으로 폭증하며 면적/전력 한계 도달
- 필요성: 클럭 사이클 당 다중 명령어(IPC > 1.0)를 실행하면서도, 디코딩과 의존성 검사 하드웨어를 제거하여 초저전력 칩 설계

## Ⅱ. 구조 및 구성요소 (정적 스케줄링 기반)

```text
[VLIW 컴파일러 및 실행 흐름도]
[고급 언어 소스코드] -> (컴파일러의 VLIW 패킹: NOP 포함 128비트 단위)
-> [ VLIW 명령어 (예: ALU1 | ALU2 | FPU | Load/Store) ]
-> [ 단순 디코더 (하드웨어 검사 없음) ]
-> 다중 실행 유닛 (병렬 처리 완료)
```

| 구성요소 | 핵심 역할 | 상세 하위 요소 / 특징 |
|:---|:---|:---|
| VLIW 컴파일러 | 프로그램의 병렬성 사전 추출 및 정적 스케줄링 | 루프 언롤링(Loop Unrolling), 소프트웨어 파이프라이닝 |
| VLIW 패킷 (Word) | 여러 실행 유닛에 1:1 대응되는 서브 명령어 묶음 | 보통 128~256비트 길이, 슬롯(Slot) 단위로 기능 매핑 |
| NOP 필드 | 의존성으로 인해 동시 실행할 명령이 없을 때 채우는 공백 | No Operation, VLIW의 가장 큰 단점(공간 낭비) 유발 |
| 단순 실행 하드웨어 | Issue Unit 없이 명령어를 직접 다중 유닛으로 분배 | 하드웨어 복잡도 감소로 발열 통제 가능 |

> 요약: VLIW 코어는 스스로 판단하지 않으며, 컴파일러가 잘라준 패킷 슬롯 위치대로 각 실행 유닛(EU)에 그대로 밀어 넣는다.

## Ⅲ. 동작원리 및 흐름도

```text
[VLIW의 클럭 당 패킷 처리 흐름]
메모리 -> 128비트 VLIW 인출 -> 병렬 디코드 (슬롯 1, 2, 3, 4 분리)
  |-- 슬롯 1 (정수)  -> ALU 수행
  |-- 슬롯 2 (소수)  -> FPU 수행 (동시에 진행, 충돌 발생 안 함)
  |-- 슬롯 3 (메모리) -> Load/Store 수행
  |-- 슬롯 4 (유휴)  -> NOP 수행 (아무 일도 안 함)
```

| 단계 | 제어 주체 | 처리 내용 (컴파일 타임 vs 런타임) |
|:---:|:---|:---|
| 1 | 컴파일 | 컴파일러가 의존성 그래프를 분석해 병렬 처리 가능한 명령어를 128비트 슬롯에 배치 |
| 2 | 인출 (Fetch) | CPU가 런타임에 아주 긴 VLIW 명령어 패킷을 한 번에 메모리에서 가져옴 |
| 3 | 해독/발행 | 별도의 의존성 검사(Hazard Check) 없이 슬롯 위치대로 즉시 유닛에 발행 |
| 4 | 실행 | 3~4개의 독립된 유닛이 데이터를 병렬 연산 및 저장 (1사이클 내 동시 처리) |

> 요약: 하드웨어의 검사 로직이 없기 때문에, 컴파일러가 실수로 충돌하는 명령을 넣으면 시스템 오류가 발생한다.

## Ⅳ. 심화 비교: VLIW vs 슈퍼스칼라

| 구분 | 슈퍼스칼라 (Superscalar) | VLIW (Very Long Instruction Word) | 판단 포인트 |
|:---|:---|:---|:---|
| 의존성 검사 | 런타임(H/W) 동적 검사 | 컴파일 타임(S/W) 정적 검사 | 트랜지스터 자원 투입 주체 |
| H/W 복잡도 | 극도로 높음 (Issue/ROB 버퍼) | 매우 단순 (디코딩 및 포워딩 최소화) | 전력 소비 및 발열 한계 돌파 |
| 하위 호환성 | x86, ARM 등 기존 바이너리 100% 동작 | 실행 유닛 수가 바뀌면 재컴파일 필수 | 시장 장악력의 핵심 차이 |
| 코드 밀도 | 가변/고정 길이 명령어 압축 | 독립 명령 부족 시 NOP 삽입으로 팽창 | 캐시 메모리 낭비 (Code Bloat) |

> 요약: 슈퍼스칼라는 레거시 호환성에 유리해 범용 CPU 시장을 장악했고, VLIW는 호환성이 필요 없는 커스텀 DSP 시장을 장악했다.

## Ⅴ. 제약 사항 및 현대적 변형 (EPIC)

| VLIW 리스크 | 원인 및 한계 | 대응 방안 (EPIC 적용) | 한계 극복 지표 |
|:---|:---|:---|:---|
| 바이너리 호환성 결여 | 차기 CPU에서 실행 유닛 수가 4개에서 6개로 늘면 기존 패킷과 구조가 불일치 | 템플릿(Template) 필드를 추가해 번들 길이를 동적 해석 (IA-64) | 재컴파일 없는 세대 간 실행 보장 |
| NOP로 인한 메모리 낭비 | 병렬 명령어가 1개뿐이면 나머지 3개 슬롯을 모두 NOP로 낭비 | Stop Bit를 도입해 NOP을 제거하고 병렬 블록 크기를 가변 처리 | 코드 팽창률 및 I-Cache 미스율 저하 |
| 분기 실패 패널티 | 정적 스케줄링은 런타임 캐시 미스나 분기에 매우 취약함 | 컴파일러 기반의 프레디케이션(Predication, 조건부 실행) 적극 활용 | 브랜치 플러시 빈도 최소화 |

> 요약: 인텔 아이태니엄(IA-64)은 VLIW의 단점을 보완한 EPIC(명시적 병렬 명령어 컴퓨팅) 아키텍처를 시도했으나, 기존 x86 앱 호환성 실패로 멸망했다.

## Ⅵ. 실무 적용 및 결론

**적용 방안 3개:**
1. 디지털 신호 처리기(DSP) 설계: 통신 기지국, 오디오/비디오 코덱 칩 설계 시, 제어 분기(If-Else)보다 고정된 수식 반복이 압도적으로 많은 특성을 살려 저전력 VLIW 코어를 채택
2. 딥러닝 텐서(Tensor) 가속기 통합: 신경망 연산은 완전한 데이터 병렬(Data-Parallel) 특성을 가지므로, 행렬 연산을 수행하는 커스텀 명령어를 VLIW 포맷으로 묶어 NPU(신경망 처리장치)의 전력/면적 효율 극대화
3. JIT(Just-In-Time) 컴파일러 연계: 안드로이드 ART(Android Runtime) 등에서 런타임 기기 프로파일을 수집해, 해당 기기의 VLIW 실행 유닛에 정확히 매핑되도록 루프 언롤링을 적용하는 정적/동적 하이브리드 최적화 수행

**결론 (2줄):**
- 기술사 판단: 범용 컴퓨팅에서는 하드웨어로 병렬성을 찾는 슈퍼스칼라(OoO)가 승리했지만, 특수 컴퓨팅(NPU, DSP) 환경에서는 S/W가 스케줄링을 통제하는 VLIW 아키텍처가 최적의 대안으로 부활했다.
- 향후 방향: 앞으로의 칩 설계는 범용 OS를 돌리는 코어는 '슈퍼스칼라'로, 특화된 벡터나 딥러닝 연산을 오프로딩하는 가속기는 'VLIW/SIMD'로 철저히 역할이 양분되는 이기종(Heterogeneous) SoC로 진화하고 있다.
