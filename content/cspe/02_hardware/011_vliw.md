# 📖 【암기용】 개념 완전 이해

## 한눈에
- **개요**: 하드웨어가 수행하던 복잡한 동적 명령어 의존성 검사를 컴파일러(소프트웨어)로 이관하여, 의존성 없는 명령어를 미리 하나의 긴 명령어로 묶어(Packing) 병렬 처리하는 정적 스케줄링 아키텍처이다.
- **왜 필요한가**: 슈퍼스칼라는 N개의 명령어를 동시 검사할 때 N²에 비례하는 하드웨어 복잡도와 전력 소모를 요구한다. 이를 극복하고 저전력 환경에서 명령어 수준 병렬성(ILP)을 확보하기 위해 필요하다.
- **핵심 직관**: 슈퍼스칼라가 현장에서 작업반장(하드웨어)이 인부들의 상황을 보고 즉석에서 일을 나눠주는 방식이라면, VLIW는 본사(컴파일러)가 미리 각 인부의 작업 지시서를 세트로 묶어서 현장에는 지시서대로 움직이기만 하라고 전달하는 방식이다.

## 핵심 용어 정리 (내부에 등장하는 것들)

| 용어/표기 | 의미 | 비유·예 |
|:---|:---|:---|
| 정적 스케줄링 (Static Scheduling) | 컴파일러가 실행 전에 병렬성을 묶어 실행 순서를 고정하는 방식 | "미리 짜둔 작업 스케줄" |
| 번들 (Bundle) / 슬롯 (Slot) | 여러 개의 기능 유닛에 대응하는 명령어들을 묶은 하나의 팩 | "한 세트로 묶인 도시락(번들)과 각각의 반찬 칸(슬롯)" |
| NOP (No Operation) | 병렬로 묶을 독립 명령어가 부족할 때 빈 슬롯을 채우는 무의미 연산 | "반찬 칸이 비어서 넣은 종이 뭉치" |

## 깊이 이해
- **배경·문제의식**: 고성능 연산을 위해 다중 기능 유닛을 두었으나, 슈퍼스칼라의 Scoreboard나 Tomasulo 알고리즘 같은 하드웨어 로직은 칩 면적을 크게 차지하고 발열을 유발한다. "이 복잡한 판단을 컴파일러가 미리 하면 어떨까?"라는 발상에서 출발했다.
- **작동 원리**: 컴파일러가 소스코드를 분석해 의존성이 없는 4~8개의 기본 명령어(예: 정수, 소수, 메모리 접근)를 찾는다. 이를 128비트나 256비트짜리 긴 명령어(VLIW) 안에 정해진 슬롯 위치에 채워 넣는다. CPU는 이 워드를 읽기만 하면 각 기능 유닛으로 곧바로 쏴준다(분배). 
- **비유**: 4개의 레일이 있는 공장에서, VLIW는 4개의 상자를 한 판에 미리 담아서 레일에 밀어 넣는 것과 같다. 레일 입구의 분배기는 상자들을 각 레일로 밀어주기만 하면 끝이다.
- **구체 예시**: 3개 슬롯(ALU, FPU, Memory)을 가진 구조에서 `A = B + C`, `D = E * F`, `G = Load(H)`가 서로 의존성이 없다면 컴파일러는 `[ADD B,C | MUL E,F | LOAD H]`라는 1개의 VLIW 번들로 생성한다.
- **흔한 오해·주의점**: 하드웨어가 단순해진다는 것은 장점이지만, 컴파일러가 독립 명령어를 찾지 못하면 빈칸을 NOP로 채워야 한다. 이로 인해 실제 코드 용량이 2~3배 커지는 코드 팽창(Code Bloat)이 발생하고 명령어 캐시 효율이 급감한다. 또한 하드웨어 유닛 개수가 3개에서 4개로 바뀌는 등 구조가 변하면 바이너리를 완전히 다시 컴파일해야 하는 호환성 문제가 있다.

## 연결 개념
- **슈퍼스칼라 (Superscalar)**: VLIW와 반대로 하드웨어가 런타임에 동적 스케줄링을 수행하는 병렬 아키텍처.
- **EPIC (Explicitly Parallel Instruction Computing)**: 인텔과 HP가 VLIW의 바이너리 호환성 단절과 NOP 낭비를 보완하기 위해 제안한 구조(예: 아이태니엄).
- **ILP (Instruction-Level Parallelism)**: VLIW가 컴파일 타임에 정적으로 추출하려는 근본적인 병렬성 지표.

# 📝 【답안용】 시험 답안 템플릿

## 핵심 인사이트 (3줄 요약)

> 1. **본질**: VLIW는 동적 스케줄링 하드웨어 복잡도를 소프트웨어(컴파일러)로 이관하여, 의존성 없는 명령어를 미리 단일 워드로 결합하는 정적 ILP 아키텍처이다.
> 2. **가치**: 명령어 발행(Issue) 유닛과 의존성 검사 회로를 제거하여 다이(Die) 면적과 전력 소모를 대폭 절감한다.
> 3. **판단 포인트**: 범용 CPU 시장에서는 바이너리 호환성 단절로 실패했으나, 분기 제어보다 루프 연산이 많은 DSP나 NPU 등 도메인 특화 아키텍처(DSA)에서는 최적의 선택지이다.

## 출제 의도 및 답안 포인트

| 출제 의도 | 반드시 짚을 핵심 | 감점 회피 포인트 |
|:---|:---|:---|
| 스케줄링 주체의 전환(H/W → S/W) 논리 파악 | 정적 스케줄링, 다중 유닛 직접 매핑, VLIW 포맷 | 슈퍼스칼라의 동적 스케줄링과 개념 혼동 |
| VLIW 구조가 직면한 기술적 트레이드오프 이해 | NOP로 인한 코드 팽창(Code Bloat), 바이너리 호환성 단절 | 구조 단순화 장점만 쓰고 캐시 효율 저하 리스크 누락 |

> 요약: 스케줄링 부담을 소프트웨어에 넘겨 전력을 아끼는 대가로, 코드 용량 증가와 호환성 상실이라는 대가를 치른 구조적 트레이드오프를 명시해야 한다.

## Ⅰ. 개요 및 필요성

- 개요: VLIW는 컴파일러가 데이터 의존성이 없는 다수의 명령어를 분석하여, 128~256비트 길이의 단일 명령어로 정적 결합해 병렬 실행하는 아키텍처이다.
- 배경: 슈퍼스칼라 코어 확장 시 동적 의존성 검사(Scoreboard 등) 회로 복잡도가 명령어 폭의 제곱(O(N²))에 비례하여 전력·면적 한계 도달
- 필요성: 모바일·임베디드 기기의 좁은 TDP 한계 내에서 IPC 1.0 초과 스루풋을 달성하려면, 하드웨어 복잡도를 컴파일러 단계로 이관하는 설계 필수

---

## Ⅱ. 구조 및 구성요소

```text
소스코드 -> VLIW 컴파일러 (정적 의존성 분석 / 스케줄링) -> 128bit VLIW 번들 생성
                                                 |
                                                 +-> 명령어 Fetch / Decode 
                                                 +-> H/W 검사 없이 다중 유닛 즉시 할당
```

| 구성요소 | 역할 | 특이사항 |
|:---|:---|:---|
| 최적화 컴파일러 | 소스 분석 및 의존성 없는 명령어 추출·패키징 | 루프 언롤링, SW 파이프라이닝 적용 |
| VLIW 명령어 형식 | 4~8개 서브 명령어를 고정 길이(예: 128bit)로 결합 | 각 슬롯이 특정 기능 유닛(ALU, FPU)에 1:1 매핑 |
| 다중 실행 유닛 | 런타임 의존성 검사 없이 할당된 슬롯의 연산 동시 실행 | Issue/Dispatch 제어 로직 최소화 |

> 요약: 똑똑한 컴파일러가 모든 의존성 계산을 끝낸 VLIW 번들을 생성하면, 바보 같지만 빠르고 전력 소모가 적은 하드웨어가 그대로 실행한다.

---

## Ⅲ. 동작원리 및 흐름도

```text
의존성 분석(S/W) -> 명령어 패키징(S/W) -> VLIW Fetch(H/W) -> 슬롯별 병렬 실행(H/W)
```

- 1단계 [정적 의존성 분석]: 컴파일 시점에 레지스터 및 메모리 주소 충돌(RAW, WAW 등)을 검사
- 2단계 [명령어 패키징]: 독립 명령어를 VLIW 슬롯에 배치하고, 남는 슬롯은 NOP(No Operation)로 패딩
- 3단계 [단일 워드 Fetch/Decode]: 실행 시 CPU가 긴 VLIW 워드를 한 번에 가져와 단순 해독
- 4단계 [병렬 실행]: 하드웨어적 인터락(Interlock) 없이 각 유닛이 할당된 연산을 1사이클 내 동시 수행

> 요약: 컴파일 시점(1~2단계)에 병렬성 배치가 확정되므로, 런타임(3~4단계)에는 의존성 검사 페널티 없이 즉시 실행된다.

---

## Ⅳ. 특징
- 하드웨어 단순화: 동적 스케줄링 큐 및 재정렬 버퍼(ROB)가 없어 트랜지스터 밀도 하락 및 누설 전류 절감
- 코드 팽창(Code Bloat): 독립 명령어가 부족한 제어 집약적 코드에서는 번들의 절반 이상이 NOP로 채워져 명령어 캐시 낭비 극심
- 세대 간 호환성 단절: 하드웨어 유닛 구성(예: ALU 2개 → 3개) 변경 시 이전 바이너리 포맷이 호환되지 않아 전체 애플리케이션 재컴파일 강제

> 요약: 발열 통제와 전력 효율은 극대화되나, 호환성 단절과 명령어 캐시 미스율 상승이라는 치명적 단점을 수반한다.

## Ⅴ. 심화 비교 및 적용 판단

| 비교 축 | 슈퍼스칼라 (Superscalar) | VLIW | 선택 기준 |
|:---|:---|:---|:---|
| 스케줄링 주체 | 하드웨어 (동적 런타임 결정) | 소프트웨어 컴파일러 (정적 컴파일 타임) | 전력/면적 예산 한계 |
| H/W 복잡도 | 극도로 높음 (OoO 로직) | 매우 단순 (검사 회로 부재) | 목표 클럭 및 TDP |
| 바이너리 호환 | 우수 (기존 코드 100% 실행) | 낮음 (H/W 구조 변경 시 재컴파일) | 레거시 생태계 중요도 |

> 요약: 기존 소프트웨어 생태계가 중요한 PC/서버 환경은 슈퍼스칼라를 채택하고, 특정 목적의 커스텀 칩 환경은 VLIW를 채택한다.

**리스크·대응 (기본은 불릿):**
- NOP 코드 팽창 리스크: 메모리 풋프린트 증가로 I-Cache 미스율 급증 → Stop Bit 기반 템플릿 인코딩(EPIC 구조) 도입으로 NOP 물리적 제거 (지표: 바이너리 압축률 30% 이상 확보)
- 예측 불가 메모리 지연: 캐시 미스 시 정적으로 짜인 스케줄이 무너짐 → 프리페칭(Prefetching) 강화 및 SMT 결합으로 지연 은닉 (지표: 캐시 미스 페널티 사이클 통제)

## Ⅵ. 실무 적용 및 결론

**적용 방안 3개:**
1. 임베디드 DSP(디지털 신호 처리기): TI C6000 계열 등 신호 처리 칩에 적용하여, 분기가 적고 반복되는 행렬 연산을 컴파일 타임에 밀집 스케줄링하여 저전력 통신 기지국 구현
2. AI 가속기(NPU) 최적화: Google TPU 및 각종 NPU 설계 시 복잡한 제어 로직을 걷어내고 VLIW 기반 명령어 묶음을 적용해 MAC(Multiply-Accumulate) 연산기 가동률 극대화
3. 컴파일러 고도화: VLIW 하드웨어 효율을 살리기 위해 LLVM 등 컴파일러 백엔드에서 루프 언롤링(Loop Unrolling) 및 소프트웨어 파이프라이닝 최적화 적용

**결론 (2줄):**
- 기술사 판단: VLIW는 호환성과 컴파일 한계로 인텔 아이태니엄 등 범용 CPU에서는 도태되었으나, 전력 효율과 면적당 연산량(TOPS/W)이 중요한 도메인 특화 아키텍처(DSA) 설계의 핵심 사상이다.
- 향후 방향: 엣지 AI 및 IoT 디바이스가 확산됨에 따라 칩의 로직 복잡도를 낮추고 AI 컴파일러(TVM 등)가 실행 효율을 극대화하는 하드웨어-소프트웨어 공동 설계(Co-design) 중심으로 VLIW가 재조명받고 있다.
