## 미리 알고가기

- VLIW는 여러 연산을 하나의 긴 명령어 번들로 묶는 구조임
- 병렬성 탐지는 하드웨어가 아니라 컴파일러가 맡음
- 실행 하드웨어는 동적 의존성 검사를 줄이지만 번들 폭이 달라지면 재컴파일이 필요함
- 슬롯: 번들 안에서 ALU·메모리·분기 등 특정 기능 유닛에 배정되는 명령어 자리임
- NOP(No Operation): 채울 병렬 명령이 없는 슬롯에 넣는 무동작 명령임
- 슈퍼스칼라(Superscalar): 하드웨어가 실행 시점에 독립 명령어를 동적으로 찾아 여러 개를 동시에 발행하는 구조임

## 작성 근거(검토용)

- VLIW는 하드웨어 동적 탐지가 아니라 컴파일러 정적 스케줄링이 선택 기준이므로 그 차이를 비교 축으로 둠
- 슈퍼스칼라와 VLIW를 병렬성 탐지·바이너리 호환성·빈 슬롯 비용으로 비교함
- NOP 비율과 재컴파일 범위를 VLIW 선택 조건으로 정리함

## Ⅰ. 개요

- **정의/개념**: VLIW는 컴파일러가 서로 독립적인 명령어를 미리 묶어 하나의 긴 명령어 워드에 배치하고, 프로세서는 이를 복잡한 동적 의존성 검사 없이 병렬 실행하는 아키텍처임
- **배경/필요성**: 동적 병렬성 탐지의 전력과 회로 복잡도를 줄이기 위해 명령어 스케줄링을 컴파일러가 담당하는 구조가 필요함

### 쉽게 이해하기 (학습용)
- 출발 전 짐꾼이 트럭 몇 칸에 무엇을 실을지 미리 다 정해두면, 운전기사는 현장에서 순서를 다시 따질 필요가 없음
- 즉석 판단 대신 사전 계획으로 현장 부담을 줄이는 방식임

## Ⅱ. 특징

- 병렬성 탐지를 컴파일러가 담당해 실행 시 의존성 검사 회로를 줄임
- 반복 구조가 고정된 연산은 컴파일러가 명령 슬롯을 사전에 배치할 수 있음
- 병렬로 채울 명령어가 부족하면 NOP가 늘어 실행 파일 크기가 증가함
- 구현이 바뀌면 재컴파일 부담이 커져 바이너리 호환성이 약함

### 쉽게 이해하기 (학습용)
- 짐 순서를 미리 정해둔 덕분에 트럭에서는 확인 절차 없이 바로 싣기만 하면 됨
- 실을 짐이 부족한 칸은 빈 채로 두고 가야 해서 트럭 공간이 낭비됨
- 트럭 칸 수(구현 폭)가 바뀌면 짐 계획을 처음부터 다시 짜야 함

## Ⅲ. 종류 및 비교

| 판단 기준 | 슈퍼스칼라 | VLIW |
|:---|:---|:---|
| 병렬성 탐지 | 하드웨어 동적 탐지 | 컴파일러 정적 탐지 |
| 바이너리 호환성 | 구현 폭 변화에 하드웨어가 대응 | 번들 폭·슬롯 구성이 바뀌면 재컴파일 필요 |
| 빈 슬롯 비용 | 발행 슬롯 이용률 저하 | NOP 삽입과 코드 크기 증가 |

> 요약: 슈퍼스칼라는 실행 중 병렬성을 찾고, VLIW는 컴파일 시 병렬성을 정해 실행 코어 부담을 줄임.

### 쉽게 이해하기 (학습용)
- 슈퍼스칼라는 기사가 현장에서 즉석으로 짐 순서를 판단해 싣는 방식이고, VLIW는 출발 전 계획표대로만 싣는 방식임
- 계획표 방식은 현장 판단 장비가 필요 없지만, 트럭 칸이 바뀌면 계획표를 새로 짜야 함

## Ⅳ. 구성요소 및 구조

| 구성요소 | 설명 |
|:---|:---|
| 컴파일러 스케줄러 | 의존성이 없는 명령어를 분석해 번들로 묶고 슬롯 배치를 결정함 |
| 명령어 번들 | ALU·메모리·분기 슬롯을 하나의 긴 워드에 담아 병렬 실행 단위를 형성함 |
| 기능 유닛 | 번들의 각 슬롯에 지정된 연산을 동시에 실행함 |
| 빈 슬롯·NOP | 병렬 명령이 없는 슬롯을 채우며 실행 파일 크기와 명령어 캐시 사용량을 늘림 |

```text
+-------------------+     +-------------------+     +------------------+
| 컴파일러 스케줄러   | --> | 명령어 번들        | --> | 기능 유닛          |
+-------------------+     +-------------------+     +------------------+
                                      |
                                      v
                                  +--------+
                                  | NOP    |
                                  +--------+
```

> 요약: 컴파일러가 슬롯을 채운 번들을 만들고, 프로세서는 각 슬롯을 병렬 실행함.

### 쉽게 이해하기 (학습용)
- 짐 계획을 짜는 사람(컴파일러 스케줄러), 계획대로 채운 트럭 칸(명령어 번들), 각 칸의 짐을 내리는 일꾼들(기능 유닛)이 순서대로 이어짐
- 채울 짐이 없는 칸은 빈 상자(NOP)로 남겨둠

## Ⅴ. 원리 및 절차 흐름도

```text
+-------------+     +-------------+     +-------------+     +-------------+
| 의존성 분석      | --> | 번들링 수행      | --> | 슬롯별 병렬 실행   | --> | 결과 확정      |
+-------------+     +-------------+     +-------------+     +-------------+
```

1. **의존성 분석**: 컴파일러가 병렬 가능한 명령어를 선택함
2. **번들링 수행**: 실행 슬롯에 맞게 하나의 긴 워드로 구성함
3. **슬롯별 병렬 실행**: 하드웨어가 번들 각 필드를 동시에 실행함
4. **결과 확정**: 연산 결과를 프로그램 의미에 맞게 반영함

> 요약: VLIW는 의존성이 없는 명령어를 번들로 묶어 슬롯별로 동시에 실행함.

### 쉽게 이해하기 (학습용)
- 짐꾼이 먼저 같이 실어도 되는 짐을 골라내고(의존성 분석), 트럭 칸에 나눠 담은 뒤(번들링), 모든 칸을 동시에 내리고(병렬 실행), 마지막에 짐 목록과 대조함(결과 확정)

## Ⅵ. 실무 사례

1. 미디어 DSP는 반복 연산을 VLIW 번들로 배치하고, 실행 슬롯 이용률과 처리량으로 검증함
2. VLIW 프로세서 세대 전환은 변경된 번들 폭에 맞춰 응용 프로그램을 재컴파일하고, 호환 시험 통과율과 재컴파일 소요시간으로 검증함

### 쉽게 이해하기 (학습용)
- 반복되는 영상 처리 작업은 미리 짜둔 적재 계획표를 그대로 재사용하는 것과 같음
- 트럭 모델이 바뀌면(세대 전환) 예전 계획표는 못 쓰므로 새 모델에 맞게 다시 짜야 함

## Ⅶ. 결론

- VLIW는 컴파일러가 독립 명령어를 정적으로 묶어 번들을 구성하고 하드웨어는 동적 의존성 검사 없이 병렬 실행하는 구조임
- 반복 구조가 고정되어 컴파일러가 슬롯을 채우기 쉬운 연산에 적용하고, NOP 비율·코드 크기·재컴파일 범위를 기준으로 선택해야 함

### 쉽게 이해하기 (학습용)
- 미리 계획을 세울 수 있는 짐일수록 이 방식이 유리하고, 빈 칸과 재계획 비용을 감수할 만한지 따져야 함
