## 미리 알고가기

- VLIW는 여러 연산을 하나의 긴 명령어 번들로 묶는 구조임
- 병렬성 탐지는 하드웨어가 아니라 컴파일러가 맡음
- 하드웨어는 단순하지만 바이너리 유연성은 낮아짐

## Ⅰ. 개요

- **정의/개념**: VLIW는 컴파일러가 서로 독립적인 명령어를 미리 묶어 하나의 긴 명령어 워드에 배치하고, 프로세서는 이를 복잡한 동적 의존성 검사 없이 병렬 실행하는 아키텍처임
- **배경/필요성**: 동적 병렬성 탐지의 전력과 회로 복잡도를 줄이기 위해 명령어 스케줄링을 컴파일러가 담당하는 구조가 필요함

## Ⅱ. 특징

- 병렬성 탐지를 컴파일러가 담당해 하드웨어가 단순함
- 정형화된 반복 연산에서 동적 스케줄링 회로 부담이 작음
- 병렬로 채울 명령어가 부족하면 NOP가 늘어 코드 밀도가 나빠짐
- 구현이 바뀌면 재컴파일 부담이 커져 바이너리 호환성이 약함

## Ⅲ. 종류 및 비교

| 판단 기준 | 슈퍼스칼라 | VLIW |
|:---|:---|:---|
| 병렬성 탐지 | 하드웨어 동적 탐지 | 컴파일러 정적 탐지 |
| 장점 | 기존 바이너리 호환성 | 단순 실행 코어와 낮은 스케줄링 전력 |
| 한계 | 회로 복잡도와 전력 부담 | 코드 팽창과 재컴파일 부담 |
| 적합 환경 | 범용 CPU | DSP·특화 가속기 |

> 요약: 슈퍼스칼라는 실행 중 병렬성을 찾고, VLIW는 컴파일 시 병렬성을 정해 실행 코어 부담을 줄임.

## Ⅳ. 구성요소 및 구조

| 구성요소 | 설명 |
|:---|:---|
| Compiler Scheduler | 의존성이 없는 명령어를 분석해 번들로 묶고 슬롯 배치를 결정함 |
| Instruction Bundle | ALU·메모리·분기 슬롯을 하나의 긴 워드에 담아 병렬 실행 단위를 형성함 |
| Functional Units | 번들 각 슬롯을 동시에 처리하며 하드웨어는 해석보다 실행에 집중함 |
| Padding or NOP | 병렬성을 채우지 못한 빈 슬롯을 메워 코드 크기와 i-cache 부담을 키움 |

```text
+-------------------+     +-------------------+     +------------------+
| Compiler Scheduler | --> | Instruction Bundle | --> | Functional Units |
+-------------------+     +-------------------+     +------------------+
                                      |
                                      v
                                  +--------+
                                  | NOP    |
                                  +--------+
```

> 요약: 컴파일러가 슬롯을 채운 번들을 만들고, 프로세서는 각 슬롯을 병렬 실행함.

## Ⅴ. 원리 및 절차 흐름도

```text
+-------------+     +-------------+     +-------------+     +-------------+
| 의존성 분석      | --> | 번들링 수행      | --> | 슬롯별 병렬 실행   | --> | 결과 확정      |
+-------------+     +-------------+     +-------------+     +-------------+
```

1. **의존성 분석**: 컴파일러가 병렬 가능한 명령어를 선택함
2. **번들링 수행**: 실행 슬롯에 맞게 하나의 긴 워드로 구성함
3. **슬롯별 병렬 실행**: 하드웨어가 번들 각 필드를 동시에 실행함
4. **결과 확정**: 연산 결과를 프로그램 의미에 맞게 반영함

> 요약: VLIW는 의존성이 없는 명령어를 번들로 묶어 슬롯별로 동시에 실행함.

## Ⅵ. 실무 적용 및 유의점

1. DSP·미디어 가속기는 반복 패턴이 뚜렷해 VLIW가 맞지만 번들 형식이 바뀌면 재컴파일 부담이 커지므로 compatibility rate와 recompilation effort로 확인함
2. 슬롯이 비거나 캐시 미스 영향이 큰 코드는 trace scheduling, compressed encoding, profile-guided optimization을 적용하고 NOP ratio, binary size, throughput stability로 확인함

## Ⅶ. 결론

VLIW는 긴 명령어 자체보다 컴파일러가 빈 슬롯과 재컴파일 부담을 얼마나 줄이는지가 핵심 판단 기준임.

## 작성 근거(검토용)

- VLIW는 하드웨어 동적 탐지가 아니라 컴파일러 정적 스케줄링이 선택 기준이므로 그 차이를 비교 기준으로 둠
- 모호한 표현은 동적 스케줄링 회로 부담, NOP 비율, 코드 크기로 구체화함
- 결론은 긴 명령어 자체보다 컴파일러가 빈 슬롯을 얼마나 줄이는지가 판단 대상임을 드러냄
