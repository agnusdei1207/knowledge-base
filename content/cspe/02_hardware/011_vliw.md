## Ⅰ. 개요
- 정의: 컴파일러가 병렬 실행 가능한 명령어들을 하나의 아주 긴 명령어로 묶는 기술
- 배경: 슈퍼스칼라의 복잡한 하드웨어 의존성 체크 로직을 소프트웨어로 전가
- 출제 의도: 정적 스케줄링(Compiler)과 동적 스케줄링(Hardware)의 성능 트레이드오프 이해

## Ⅱ. 구성요소
- ASCII 구조도
  +-----------------------------------------------------+
  | Very Long Instruction (VLI)                         |
  | [ ALU Op 1 ] [ ALU Op 2 ] [ Load/Store ] [ Branch ] |
  +------+-----------+-----------+------------+---------+
         |           |           |            |
  +------v---+ +-----v---+ +-----v---+ +------v---+
  | Unit 1   | | Unit 2   | | Unit 3   | | Unit 4   |
  +----------+ +----------+ +----------+ +----------+

- 구성요소 표
| 구성요소 | 설명 | 비유 |
| :--- | :--- | :--- |
| 번들(Bundle) | 동시에 실행될 명령어들의 집합 | 세트 메뉴 |
| 정적 스케줄러 | 컴파일 타임에 의존성 분석 및 최적화 | 여행 가이드 |
| 실행 유닛 | 지시된 대로 병렬 연산을 수행하는 단순 하드웨어 | 단순 노동자 |
> 요약: 하드웨어는 복잡한 판단 없이 컴파일러가 묶어준 대로 실행만 함

## Ⅲ. 절차
- ASCII 흐름도
  (Source Code) -> (Dependency Analysis) -> (Bundle Generation)
                            | (Compiler Side)
                            v
  (Fetch Bundle) -> (Direct Dispatch to Units) -> (Execute)

- 4단계 설명
1. 의존성 분석: 컴파일러가 소스 코드 내 병렬 실행 가능한 명령어 그룹 식별
2. 명령어 패킹: 하드웨어 실행 유닛 구조에 맞춰 명령어들을 긴 단어(Word)로 묶음
3. NOP 삽입: 병렬성 부족 시 빈 칸을 채워 동기화 유지
4. 단순 실행: 하드웨어는 분석 과정 없이 묶음 내 명령어를 각 유닛으로 즉시 분배
> 요약: 컴파일러가 똑똑해야 성능이 나오며, 하드웨어 구조는 단순화됨

## Ⅳ. 문제점
- 코드 팽창: 병렬성 부족 시 NOP(No Operation) 삽입으로 실행 파일 크기 증가
- 호환성 부재: 실행 유닛 수가 바뀌면 기존 바이너리를 다시 컴파일해야 함

## Ⅴ. 개선방안
- (단기) EPIC (Intel Itanium): 명시적 병렬 명령어 컴퓨팅으로 호환성 문제 일부 완화
- (중기) DSP/GPU 활용: 규칙적인 데이터 병렬성이 높은 특수 분야에 집중 적용
- (장기) 동적 재컴파일: 런타임에 바이너리를 타겟 구조에 맞게 최적화 (JIT 방식)

## Ⅵ. 전망
- 로드맵: 범용 CPU보다는 효율성이 중요한 DSP, Edge AI 가속기 시장에서 생존
- CSF: 고도로 최적화된 컴파일러 알고리즘 및 예측 가능한 코드 패턴 확보
