# 📖 【암기용】 개념 완전 이해

## 한눈에
- **개요**: VLIW(Very Long Instruction Word)는 컴파일러가 미리 병렬 가능한 여러 연산을 하나의 긴 명령어에 묶어 넣고, 하드웨어는 그대로 각 슬롯을 실행유닛에 뿌리기만 하는 정적 스케줄 구조다.
- **왜 필요한가**: 슈퍼스칼라(010)는 매 클럭 의존성을 검사하는 발행 로직 때문에 하드웨어가 복잡·전력 과다다. 이 검사를 컴파일 타임으로 옮기면 발행 하드웨어를 극단적으로 단순화할 수 있다.
- **핵심 직관**: 슈퍼스칼라가 손님을 계산대에 실시간 배정하는 매니저라면, VLIW는 개점 전에 "몇 번 손님은 몇 번 계산대"를 종이에 다 적어두고(컴파일러) 점원은 그 표대로만 움직이는 방식이다.

## 핵심 용어 정리 (내부에 등장하는 것들)

컴파일러가 병렬성을 미리 확정한다는 상위 키워드를 잡고, 슬롯·정적 스케줄 표기를 비유로 푼다.

| 용어/표기 | 의미 | 비유·예 |
|:---|:---|:---|
| VLIW | 병렬 연산 여러 개를 한 개의 긴 명령어로 묶은 구조 | 여러 주문을 한 장의 지시서에 묶음 |
| 명령어 슬롯(Slot) | 긴 명령어 안에서 각 실행유닛에 대응하는 자리 | 지시서의 칸 하나 = 계산대 하나 |
| 정적 스케줄(Static) | 컴파일 타임에 병렬성·순서를 확정하는 방식 | 개점 전 미리 짠 좌석 배치표 |
| 동적 스케줄(Dynamic) | 런타임에 하드웨어가 병렬성을 판단하는 방식(슈퍼스칼라) | 현장에서 실시간 배정 |
| NOP 슬롯 | 병렬 연산을 못 채워 빈 채로 둔 슬롯(no operation) | 손님 없어 노는 계산대 칸 |
| EPIC | Explicitly Parallel Instruction Computing, VLIW를 발전시킨 Intel/HP 방식(Itanium) | 개선판 지시서 규격 |
| 프레디케이션(Predication) | 분기 대신 각 명령에 실행 조건 플래그를 붙여 분기 제거 | "참일 때만 실행" 도장을 명령마다 찍음 |
| 소프트웨어 파이프라이닝 | 컴파일러가 루프 반복을 겹쳐 슬롯을 채우는 최적화 | 다음 손님 미리 줄 세워 칸 채움 |
| 코드 호환성 문제 | 실행유닛 개수가 바뀌면 명령어 폭도 바뀌어 재컴파일 필요 | 계산대 수 바뀌면 지시서 양식 다시 작성 |

## 깊이 이해

### 배경 — 슈퍼스칼라 발행 로직을 걷어내기
- 슈퍼스칼라(010)는 발행 폭이 커질수록 "어떤 명령이 서로 독립인가"를 매 클럭 검사하는 회로가 폭의 제곱으로 커진다. VLIW는 이 판단 전체를 컴파일러에 위임한다(011만의 차별점).
- 컴파일러가 이미 "이 슬롯들은 동시에 실행해도 안전"이라고 보장했으므로, 하드웨어는 의존성 검사 없이 각 슬롯을 대응 유닛에 곧장 보낸다. 발행 하드웨어가 거의 사라져 전력·면적이 크게 준다.

### 작동 원리 — 어떻게, 왜
- 컴파일러가 데이터 의존성 그래프를 분석해 동시에 실행 가능한 연산들을 한 워드(예: 128~256비트, 슬롯 4~8개)에 배치한다. 채울 병렬성이 없으면 그 슬롯에 NOP를 넣는다.
- 실행 시 하드웨어는 워드를 통째로 인출해 슬롯 순서 그대로 ALU·FPU·L/S에 나눠준다. 발행 로직이 없으니 파이프라인 제어가 단순하다.
- 대가는 컴파일러가 런타임 정보(캐시 미스로 인한 메모리 지연 등)를 모른다는 점이다. 슈퍼스칼라는 런타임에 지연을 보고 순서를 바꿀 수 있지만(012), VLIW는 컴파일 타임에 고정한 스케줄을 못 바꾼다.

### 비유
- VLIW는 항공사 사전 좌석 배정이다. 미리 다 짜두면 탑승이 빠르지만, 당일 결항·지연(캐시 미스) 같은 변수엔 대응이 굳어 있다. 슈퍼스칼라는 현장 대기표로 유연하나 카운터 직원(하드웨어)이 많이 필요하다.

### 구체 예시 — 수치로
- Intel Itanium(IA-64, 2001)이 EPIC 기반 대표작으로 128비트 번들에 3연산 슬롯을 담았으나, 컴파일러 최적화 난이도와 x86 호환성 부재로 시장에서 실패했다.
- 반면 DSP·GPU 셰이더·TI C6000 같은 규칙적 연산 도메인에서는 VLIW가 여전히 널리 쓰인다. 루프 위주라 컴파일러가 슬롯을 잘 채워 NOP 낭비가 적기 때문이다.

### 흔한 오해
- "VLIW가 슈퍼스칼라보다 항상 우월"은 틀렸다. 범용 코드는 분기·메모리 지연이 많아 컴파일러가 슬롯을 못 채우고 NOP가 폭증해, 오히려 명령어 캐시를 낭비한다.
- "VLIW는 병렬성을 더 많이 뽑는다"도 아니다. 병렬성 상한은 코드의 ILP가 정하며, VLIW는 그 추출 시점을 하드웨어에서 컴파일러로 옮긴 것뿐이다.

## 연결 개념
- 슈퍼스칼라(010) — VLIW의 대비쌍, 같은 ILP를 런타임 하드웨어로 추출하는 동적 스케줄
- 비순차 실행(012) — VLIW가 못 하는 런타임 순서 재조정으로 메모리 지연을 은닉
- 컴파일러 최적화 — VLIW 성능을 좌우하는 소프트웨어 파이프라이닝·프레디케이션의 주체

# 📝 【답안용】 시험 답안 템플릿

## 핵심 인사이트 (3줄 요약)

> 1. **본질**: VLIW는 병렬 연산 배치를 컴파일 타임에 확정해 하나의 긴 명령어로 묶고, 하드웨어는 발행 로직 없이 슬롯을 그대로 실행하는 정적 스케줄 구조임.
> 2. **가치**: 의존성 검사 하드웨어를 컴파일러로 이관해 발행 회로를 극단 단순화, 동일 병렬도에서 전력·면적 효율을 확보함.
> 3. **판단 포인트**: 런타임 지연을 못 반영해 범용 코드에선 NOP 낭비가 크므로, DSP·GPU 등 규칙적 도메인에 한정해 이점이 실현됨.

## 출제 의도 및 답안 포인트

| 출제 의도 | 반드시 짚을 핵심 | 감점 회피 포인트 |
|:---|:---|:---|
| 정적 스케줄과 발행 하드웨어 단순화 원리 이해 | 컴파일러가 슬롯 배치 확정, 하드웨어 의존성 검사 제거 | 슈퍼스칼라와 스케줄 주체 구분 누락 |
| VLIW의 한계와 적합 도메인 인식 | NOP 낭비·코드 호환성·런타임 지연 미대응 | VLIW가 범용에서도 우월하다는 단정 |

> 요약: 스케줄 주체를 컴파일러로 옮긴 이점과, 런타임 정보 부재로 인한 NOP·호환성 한계를 함께 서술함.

## Ⅰ. 개요 및 필요성

- 개요: 병렬 연산을 컴파일러가 한 긴 명령어로 묶어 정적 발행하는 CPU 구조임
- 배경: 슈퍼스칼라 발행 로직이 폭의 제곱으로 복잡·과전력화됨(010 참조)
- 필요성: 의존성 검사를 컴파일 타임으로 이관해 발행 하드웨어를 단순화하고 전력·면적 효율을 높일 구조가 요구됨

---

## Ⅱ. 구조 및 구성요소

```text
[VLIW 정적 발행 구조]
컴파일러(정적 스케줄) -> 긴 명령어 워드 생성
워드 = [슬롯1 | 슬롯2 | 슬롯3 | 슬롯4]  (빈 곳은 NOP)
하드웨어: 워드 통째 인출 -> 슬롯 순서대로 유닛 직결
   슬롯1->ALU / 슬롯2->ALU / 슬롯3->FPU / 슬롯4->Load-Store
```

| 구성요소 | 핵심 역할 | 하위 요소·특징 |
|:---|:---|:---|
| 컴파일러(정적 스케줄러) | 의존성 분석·슬롯 배치·NOP 삽입 | 소프트웨어 파이프라이닝·프레디케이션 |
| 긴 명령어 워드 | 여러 연산 슬롯을 한 번에 담는 명령 포맷 | 128~256비트, 슬롯 4~8개 |
| 명령어 슬롯 | 각 실행유닛에 1:1 대응하는 자리 | 못 채우면 NOP로 낭비 |
| 단순 발행부 | 검사 없이 슬롯을 유닛에 직결 | 발행 로직 제거로 면적·전력 절감 |

> 요약: 컴파일러가 슬롯을 확정한 긴 워드를 하드웨어가 검사 없이 유닛에 직결하는, 소프트웨어 주도 구조임.

---

## Ⅲ. 동작원리 및 흐름도

```text
[VLIW 컴파일~실행 흐름]
컴파일: 의존성 그래프 분석 -> 동시 실행 가능 연산 슬롯 배치 -> 빈 슬롯 NOP
인출: 하드웨어가 긴 워드 통째 인출
분배: 슬롯 순서 그대로 각 실행유닛에 직결(의존성 검사 없음)
실행: 유닛 동시 연산 -> 결과 기록
```

- 1단계: 컴파일러가 데이터 의존성 그래프를 분석해 동시 실행 가능한 연산을 한 워드의 슬롯에 배치하고 빈 슬롯에 NOP를 삽입함 (주체: 컴파일러)
- 2단계: 하드웨어가 긴 명령어 워드를 한 번에 인출함 (주체: 인출 유닛)
- 3단계: 발행부가 의존성 검사 없이 각 슬롯을 대응 실행유닛에 그대로 전달함 (주체: 단순 발행부)
- 4단계: 실행유닛들이 슬롯 연산을 동시 수행하고 결과를 레지스터에 기록함 (주체: 실행유닛)

> 요약: 병렬성 판단을 컴파일러가 끝내둔 워드를 하드웨어가 검사 없이 나눠 실행하므로, 발행 단계가 극도로 가벼움.

---

## Ⅳ. 특징

- 병렬성 추출을 컴파일 타임에 수행해 하드웨어 발행 로직을 제거, 전력·면적 효율이 높음
- 의존성 검사 부재로 파이프라인 제어가 단순해 클럭당 슬롯 수만큼 결정적 병렬 실행이 가능함
- 컴파일러가 런타임 지연(캐시 미스)을 모르므로, 예측 불가 지연이 잦은 범용 코드에서 NOP가 폭증함
- 실행유닛 개수가 곧 명령어 폭이라, 하드웨어 세대가 바뀌면 재컴파일이 필요해 바이너리 호환성이 약함
- DSP·GPU 셰이더 등 루프 위주 규칙적 도메인에서는 슬롯 충전율이 높아 실효 이득이 큼

> 요약: 하드웨어를 비우고 컴파일러에 부담을 몰아 효율을 얻으나, 런타임 미대응·호환성 취약이 범용 확산을 막는 근본 한계임.

## Ⅴ. 심화 비교 및 적용 판단

| 구분 | VLIW (정적) | 슈퍼스칼라 (동적) |
|:---|:---|:---|
| 스케줄 주체·시점 | 컴파일러가 컴파일 타임에 확정 | 하드웨어가 런타임에 판단 |
| 발행 하드웨어 | 의존성 검사 없음, 단순 | 폭 제곱의 검사·바이패스 회로 |
| 런타임 지연 대응 | 불가(고정 스케줄) | 가능(순서 재조정·OoO) |
| 바이너리 호환성 | 약함(유닛 수 바뀌면 재컴파일) | 강함(ISA 유지) |
| 적합 도메인 | DSP·GPU·임베디드 규칙 연산 | 범용 CPU·분기 많은 코드 |

> 요약: 규칙적·예측 가능 워크로드면 VLIW의 정적 효율이 우수하나, 분기·지연이 잦은 범용에선 슈퍼스칼라의 동적 유연성이 필수임.

**리스크·대응(불릿):**
- 리스크 — 슬롯 미충전 NOP로 명령어 캐시·대역 낭비 — 대응: 소프트웨어 파이프라이닝·루프 언롤로 충전율 상향 (지표: 슬롯 충전율)
- 리스크 — 하드웨어 세대 교체 시 재컴파일 필요 — 대응: EPIC식 템플릿·JIT 재컴파일 계층 도입 (지표: 재컴파일 없이 실행 가능 비율)
- 리스크 — 캐시 미스 등 런타임 지연 미대응 — 대응: 프레디케이션·프리페치 힌트로 지연 은닉 (지표: 지연 유발 스톨 사이클)

**지표·목표(불릿):**
- 지표 — 슬롯 충전율 — 목표: 도메인 코드 70% 이상 — 측정: 워드당 유효 슬롯/전체 슬롯
- 지표 — 코드 크기 팽창 — 목표: NOP 팽창 20% 이하 — 측정: 바이너리 크기 대비 유효 명령
- 지표 — 컴파일러 스케줄 효율 — 목표: 이론 ILP 대비 80% 추출 — 측정: 프로파일 기반 벤치

## Ⅵ. 실무 적용 및 결론

**적용 방안 3개:**
1. 도메인 특화 적용: TI C6000 DSP·GPU 셰이더처럼 루프 위주 규칙 연산에 VLIW를 적용해 슬롯 충전율을 70% 이상 확보
2. 컴파일러 최적화 강화: 소프트웨어 파이프라이닝·프레디케이션으로 분기·의존성으로 인한 NOP를 최소화
3. 호환성 계층 도입: EPIC 템플릿이나 JIT 재컴파일 계층을 두어 실행유닛 세대 교체 시 바이너리 재배포 부담 완화

**결론 (2줄):**
- 기술사 판단: 워크로드가 규칙적·컴파일 타임 예측 가능하면 VLIW의 정적 효율이 유리하나, 분기·메모리 지연이 잦으면 슈퍼스칼라·OoO가 실효 성능에 우위임
- 향후 방향: 순수 범용 VLIW는 Itanium 실패로 쇠퇴했고, GPU·AI 가속기·DSP 등 규칙적 병렬 도메인의 정적 스케줄 엔진으로 명맥이 이어지고 있음
