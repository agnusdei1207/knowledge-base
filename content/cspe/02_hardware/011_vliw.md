# 📖 【암기용】 개념 완전 이해

> 목적: VLIW를 처음 봐도 왜 컴파일러가 병렬 실행을 미리 다 짜놓는지 이해하게 만든다. 시험 답안 양식이 아니라, 이해를 위한 친절한 설명이다.

## 한눈에
- **개요**: 여러 개의 독립적인 연산을 컴파일러가 하나의 긴 명령어 워드로 미리 묶어, 하드웨어는 런타임 의존성 검사 없이 그대로 병렬 실행하는 구조
- **왜 필요한가**: 슈퍼스칼라의 런타임 의존성 검사 로직(스코어보드, 예약 스테이션)은 면적과 전력을 많이 쓰므로, 이를 컴파일 시점으로 옮기면 하드웨어를 단순하게 유지하면서 병렬성을 확보할 수 있다
- **핵심 직관**: 슈퍼스칼라가 현장 감독이 즉석에서 작업을 배분하는 방식이라면, VLIW는 설계도(컴파일러)가 이미 누가 무엇을 언제 할지 다 정해놓고 현장은 그대로 따르는 방식이다

## 깊이 이해
- **배경·문제의식**: 슈퍼스칼라는 런타임에 명령어 간 의존성을 검사하는 하드웨어 비용이 발행 폭 증가에 비례해 커지므로, 이 검사 부담을 컴파일 시점으로 이전하려는 시도에서 VLIW가 나왔다.
- **작동 원리**: VLIW 명령어 하나는 여러 개의 독립 슬롯(정수 연산, 부동소수점 연산, 메모리 접근 등)으로 구성되며, 컴파일러가 이 슬롯들을 서로 의존성 없는 연산으로 채운다.
- **작동 원리 - NOP 패딩**: 컴파일러가 특정 슬롯을 채울 만큼 독립적인 연산을 찾지 못하면 해당 슬롯은 NOP(No Operation)으로 채워지며, 이는 명령어 메모리 사용량 증가로 이어진다.
- **작동 원리 - EPIC 확장**: Itanium(IA-64)이 채택한 EPIC(Explicitly Parallel Instruction Computing)은 VLIW 개념에 예측 실행(predication)과 소프트웨어 파이프라이닝 힌트를 더해 컴파일러의 정적 스케줄링 범위를 확장한 설계다.
- **비유**: VLIW는 이미 좌석 배치도가 확정된 단체 버스와 같아서, 출발 전(컴파일 시점)에 자리를 다 정해야 하고 즉석에서 좌석을 바꾸는 유연성(런타임 의존성 검사)은 없다.
- **구체 예시**: 3-슬롯 VLIW(예시 구성)에서 정수 연산 슬롯 1개, 메모리 접근 슬롯 1개만 채울 독립 연산이 있고 부동소수점 슬롯을 채울 연산이 없으면, 해당 명령어의 부동소수점 슬롯은 NOP으로 채워진다.
- **흔한 오해·주의점**: VLIW는 하드웨어가 단순해서 무조건 저전력·고성능이라고 단정하면 안 된다. 컴파일러가 충분한 정적 ILP를 찾지 못하는 코드(분기·포인터 별칭이 많은 범용 코드)에서는 슬롯 활용률이 떨어져 이득이 줄어든다.
- **흔한 오해·주의점**: VLIW 바이너리는 슬롯 구성(파이프라인 세부 구조)에 강하게 결합되므로, 마이크로아키텍처가 바뀌면 재컴파일 없이는 이진 호환성이 유지되지 않는 경우가 일반적이다.

## 연결 개념
- 슈퍼스칼라(Superscalar) — 동일한 병렬 발행 목표를 하드웨어 동적 스케줄링으로 달성하는 대안 구조
- 명령어 수준 병렬성(ILP) — VLIW 효율은 컴파일러가 정적으로 찾아내는 ILP 양에 좌우
- 명령어 스케줄링(Instruction Scheduling)·소프트웨어 파이프라이닝 — VLIW 컴파일러 최적화의 핵심 기법

# 📝 【답안용】 시험 답안 템플릿

> 목적: 시험장에서 25분에 그대로 쓰는 답안 양식. 작성방식(추상표현 금지·수치·도식·문제유형 전환)을 엄격히 지킨다.
> 핵심: 컴파일러 정적 스케줄링 구조, 슬롯·NOP 패딩, EPIC 확장, 슈퍼스칼라 대비 이진 호환성·검증 비용 차이를 함께 제시한다.

## 핵심 인사이트 (3줄 요약)

> 1. **본질**: VLIW는 컴파일러가 정적으로 독립 연산을 여러 슬롯에 묶어 하나의 긴 명령어로 만들고, 하드웨어는 런타임 의존성 검사 없이 그대로 병렬 실행하는 구조이다.
> 2. **가치**: 런타임 스케줄링 하드웨어를 생략해 면적·전력을 줄이면서도 슬롯 수만큼의 병렬 실행을 얻을 수 있다.
> 3. **판단 포인트**: 정적 ILP가 부족한 범용 코드에서는 NOP 패딩이 늘어 슬롯 활용률이 떨어지므로, DSP·미디어 처리처럼 규칙적 연산이 많은 도메인에 적합하다.

## 출제 의도 및 답안 포인트

| 출제 의도 | 반드시 짚을 핵심 | 감점 회피 포인트 |
|:---|:---|:---|
| 정적 vs 동적 스케줄링 구분 확인 | 컴파일러가 슬롯을 채우는 구조, 하드웨어 의존성 검사 부재 | VLIW를 슈퍼스칼라와 동일 개념으로 서술 |
| 실무 한계 이해 확인 | NOP 패딩, 이진 비호환, 정적 ILP 의존 | 하드웨어 단순화만 장점으로 서술하고 한계 누락 |
| 적용 도메인 판단 확인 | DSP·미디어 처리 등 규칙적 연산 영역에 적합 | 범용 OS 워크로드에도 동일하게 유리하다고 단정 |

> 요약: 이 문제는 VLIW를 슈퍼스칼라의 하위 개념이 아니라 스케줄링 주체가 다른 대안 구조로 구분해 답안을 구성해야 한다.

## Ⅰ. 개요 및 필요성

- 개요: 컴파일러가 여러 독립 연산을 하나의 긴 명령어 워드에 정적으로 묶고, 하드웨어는 그대로 병렬 실행하는 명령어 집합 구조
- 배경: 슈퍼스칼라의 런타임 의존성 검사 하드웨어 비용을 줄이기 위해 스케줄링 책임을 컴파일러로 이전하려는 필요에서 등장
- 필요성: DSP·미디어 처리처럼 데이터 흐름이 규칙적인 도메인에서는 컴파일러가 충분한 정적 ILP를 찾을 수 있어 단순한 하드웨어로도 높은 병렬 실행이 가능함

---

## Ⅱ. 구조 및 구성요소

```text
Compiler Static Scheduling
  -> Slot 1: Integer Op
  -> Slot 2: Float Op
  -> Slot 3: Memory Access
  -> (미채움 슬롯 -> NOP)
  -> Single Long Instruction Word
  -> Hardware: 슬롯별 실행 유닛에 그대로 병렬 실행
```

| 구성요소 | 역할 | 산출물 |
|:---|:---|:---|
| 컴파일러 스케줄러 | 독립 연산을 식별해 슬롯에 배치 | 정적으로 확정된 명령어 워드 |
| 슬롯(Slot) | 정수·부동소수점·메모리 접근 등 연산 종류별 실행 채널 | 슬롯별 실행 결과 |
| NOP 패딩 | 채울 독립 연산이 없는 슬롯을 무연산으로 채움 | 명령어 크기 증가 |
| 실행 유닛 | 슬롯별로 고정 배정된 하드웨어 자원 | 의존성 검사 없이 즉시 실행 |

> 요약: VLIW는 컴파일러가 슬롯을 채우고 하드웨어는 검사 없이 그대로 실행하는 구조이며, 슬롯 미채움은 NOP으로 처리된다.

---

## Ⅲ. 동작원리 및 흐름도

```text
소스 코드 -> 컴파일러 의존성 분석
  -> 독립 연산 그룹화 -> 슬롯 배치(정수/부동소수점/메모리)
  -> 부족한 슬롯 NOP 채움 -> 긴 명령어 워드 생성
  -> 하드웨어가 슬롯별 실행 유닛으로 그대로 발행
  -> 병렬 실행 결과 반환
```

| 단계 | 처리 내용 | 검증 기준 |
|:---:|:---|:---|
| 1 | 컴파일러가 명령어 간 의존성 분석 | 정적 의존성 그래프 생성 |
| 2 | 독립 연산을 슬롯별로 배치 | 슬롯 활용률 |
| 3 | 부족한 슬롯을 NOP으로 채움 | NOP 비율 |
| 4 | 하드웨어가 슬롯을 그대로 병렬 실행 | 런타임 의존성 검사 없음 확인 |

> 요약: VLIW는 컴파일 시점에 모든 스케줄링을 끝내고, 하드웨어는 검사 없이 슬롯을 그대로 실행만 한다.

## Ⅳ. 특징

| 구분 | 내용 | 판단 포인트 |
|:---|:---|:---|
| 장점 | 런타임 의존성 검사 로직 생략으로 하드웨어 단순화 | 면적·전력 절감 |
| 한계 | 정적 ILP 부족 시 NOP 패딩 증가, 슬롯 활용률 저하 | 코드 크기 증가, 명령어 캐시 압박 |
| 비교 포인트 | 슈퍼스칼라는 런타임 검사, VLIW는 컴파일 시점 검사 | 스케줄링 주체 차이 |

> 요약: VLIW는 하드웨어를 단순화하는 대신 컴파일러 최적화 품질과 코드 크기에 성능이 좌우된다.

## Ⅴ. 심화 비교 및 적용 판단

| 비교 축 | 슈퍼스칼라 | VLIW | 선택 기준 |
|:---|:---|:---|:---|
| 구조 | 하드웨어 런타임 의존성 검사 | 컴파일러 정적 스케줄링 | 워크로드 ILP가 규칙적이면 VLIW 우선 |
| 비용/성능 | 검사 로직 면적·전력 부담 | 하드웨어 단순, 컴파일러 의존 | 컴파일러 최적화 역량 확보 여부 |
| 운영/위험 | 이진 호환성 유지 용이 | 마이크로아키텍처 변경 시 재컴파일 필요 | 장기 이진 호환성 요구 시 슈퍼스칼라 |

> 요약: 규칙적 데이터 흐름과 전용 컴파일러가 갖춰진 도메인은 VLIW, 범용·호환성 중심 시장은 슈퍼스칼라가 유리하다.

| 리스크 | 원인 | 대응 방안 | 확인 지표 |
|:---|:---|:---|:---|
| 슬롯 활용률 저하 | 정적 ILP 부족 코드 | 소프트웨어 파이프라이닝, 루프 언롤링 | 슬롯당 실제 연산 채움 비율 |
| 코드 크기 증가 | NOP 패딩 누적 | 슬롯 수 최적화, 명령어 압축 인코딩 | 명령어 캐시 미스율 |
| 이진 비호환 | 마이크로아키텍처 슬롯 구성 변경 | 재컴파일 프로세스 표준화 | 마이크로아키텍처 세대별 재컴파일 빈도 |

> 요약: VLIW 리스크는 정적 ILP 한계에서 비롯되며, 컴파일러 최적화와 재컴파일 절차로 관리한다.

| 점검 항목 | 목표 기준 | 측정 방법 |
|:---|:---|:---|
| 슬롯 활용률 | 슬롯당 실제 연산 채움 비율 목표치 확보 | 컴파일러 스케줄링 리포트 |
| 코드 밀도 | NOP 비율 최소화 | 정적 바이너리 분석 |
| 성능 대비 전력 | 목표 성능/전력 비율 충족 | 벤치마크, 전력 측정 |

> 요약: 도입 효과는 슬롯 활용률, 코드 밀도, 성능 대비 전력 지표로 판단한다.

## Ⅵ. 실무 적용 및 결론

**적용 방안 3개:**
1. DSP·미디어 처리처럼 데이터 흐름이 규칙적인 도메인에 VLIW를 적용해 전용 컴파일러로 슬롯 활용률을 높임
2. 정적 ILP가 부족한 구간은 소프트웨어 파이프라이닝·루프 언롤링을 적용해 NOP 비율을 낮춤
3. 마이크로아키텍처 세대 교체 시 재컴파일 절차를 표준화해 이진 비호환 리스크를 관리함

**결론 (2줄):**
- 기술사 판단: 범용·이진 호환성이 중요한 영역은 슈퍼스칼라, 컴파일러 최적화와 전용 도메인이 확보된 영역은 VLIW를 선택함
- 향후 방향: VLIW의 정적 스케줄링 개념은 GPU·AI 가속기의 컴파일러 기반 명령어 스케줄링 설계에도 참고되고 있어 지속적인 비교 검토가 필요함
