## Ⅰ. 개요
- 정의: 멀티코어 환경에서 여러 캐시가 동일 메모리 주소의 복사본을 가질 때 일관성을 유지하는 규약
- 배경: 한 코어가 공유 데이터를 수정하면 다른 코어가 가진 데이터는 유효하지 않게 됨(Stale)
- 출제 의도: 캐시 라인의 상태 전이(State Transition) 메커니즘과 프로토콜별 차이점 이해

## Ⅱ. 구성요소
- ASCII 구조도 (MESI States)
  Modified(M) <---+
      |           | (Write)
      v           |
  Exclusive(E) <--+--> Shared(S)
      ^           |
      |           | (Invalidate)
      +-----------+--> Invalid(I)

- 구성요소 표
| 상태 | 설명 | 비유 |
| :--- | :--- | :--- |
| Modified | 데이터 수정됨, 메모리와 다름, 유일 복사본 | 나만 고친 문서 |
| Exclusive | 메모리와 동일함, 유일 복사본 | 나만 빌린 책 |
| Shared | 메모리와 동일함, 여러 캐시가 공유 중 | 같이 보는 신문 |
> 요약: 데이터의 수정 여부와 공유 여부에 따라 4가지 상태로 관리함

## Ⅲ. 절차
- ASCII 흐름도
  (Core A Read) -> (Check Shared?) -> (State: S)
  (Core A Write) -> (Invalidate others) -> (State: M)
  (Core B Read M) -> (Core A Writeback) -> (State: S)

- 4단계 설명
1. 감시(Snooping): 코어는 버스 상의 메모리 요청 신호를 감시하여 자신의 상태 확인
2. 독점 확보: 데이터 쓰기 전 Invalidation 신호를 보내 다른 캐시의 데이터를 무효화
3. 상태 전이: 읽기/쓰기 동작 및 타 코어의 신호에 따라 즉시 상태(M, E, S, I) 변경
4. 일관성 복구: 다른 코어가 수정된 데이터(M) 요청 시 메모리 업데이트 후 데이터 공유
> 요약: 쓰기 시 다른 사본을 무효화하고, 읽기 시 최신 데이터를 공유하는 절차임

## Ⅳ. 문제점
- 버스 트래픽: 상태 전이 및 무효화 신호가 많아질수록 시스템 버스 대역폭 고갈
- 지연 시간: 수정된 데이터를 가져오기 위해 메모리 쓰기(Writeback) 대기 시간 발생

## Ⅴ. 개선방안
- (단기) MOESI 도입: Owned(O) 상태 추가로 메모리 쓰기 없이 캐시 간 데이터 직접 전송
- (중기) MESIF (Intel): Forward(F) 상태를 두어 공유 데이터 응답 우선순위 결정
- (장기) 디렉터리 기반: 버스 대신 디렉터리 노드를 두어 대규모 코어 확장성 확보

## Ⅵ. 전망
- 로드맵: 온칩 네트워크(NoC) 환경에 최적화된 하이브리드 일관성 모델로 진화
- CSF: 공유 데이터 접근 빈도에 따른 적응형(Adaptive) 프로토콜 전환 기술 확보
