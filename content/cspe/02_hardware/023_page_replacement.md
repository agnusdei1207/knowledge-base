# 📖 【암기용】 개념 완전 이해

> 목적: RAM이 꽉 찼을 때 어떤 페이지를 내쫓을지 정하는 규칙들의 원리와, "프레임을 늘렸는데 오히려 성능이 나빠지는" 벨라디의 모순을 실제 숫자로 확인시켜 이해하게 만든다.

## 한눈에
- **개요**: 페이지 교체 알고리즘은 **Demand Paging(요구 페이징)** 환경에서 물리 프레임이 가득 찼을 때, 새 페이지를 들이기 위해 기존 페이지 중 하나를 골라 디스크로 내보낼(Victim 선정) 규칙이다. Page Fault 발생 자체는 막을 수 없지만, 누구를 내보낼지 잘 고르면 그 빈도를 크게 줄일 수 있다.
- **왜 필요한가**: 물리 프레임은 유한하다. 아무나 무작위로 내쫓으면 방금 쫓아낸 페이지를 바로 다음 순간 다시 불러오는 일이 반복되어(Page Fault 폭주), 디스크 I/O 지연이 시스템 전체를 마비시킬 수 있다. "가장 오랫동안 안 쓸 것 같은" 페이지를 지능적으로 골라야 이 비용을 최소화한다.
- **핵심 직관**: 책상(RAM, 프레임 3개)에 책 3권만 올릴 수 있다. 4번째 책을 보려면 1권을 치워야 한다 — OPT는 미래를 알고 가장 늦게 다시 볼 책을 치우고(불가능한 이상), FIFO는 그냥 가장 먼저 올린 책을 치우고(무식함), LRU는 가장 오랫동안 안 펼친 책을 치운다(현실적 최선).

## 핵심 용어 정리 (내부에 등장하는 것들)

| 표기/용어 | 의미 | 비유 |
|:---|:---|:---|
| Demand Paging(요구 페이징) | 필요한 페이지만 그때그때 RAM에 올리는 정책 — 프레임이 부족해지는 근본 원인 | 필요한 책만 그때그때 책상에 꺼냄 |
| Victim(희생 페이지) | 교체 대상으로 선택되어 디스크로 쫓겨나는 페이지 | 책상에서 치워지는 책 |
| Page Fault | 요청한 페이지가 RAM에 없어 발생하는 예외 — 교체 알고리즘이 호출되는 계기 | 책상에 없어서 서고까지 가야 함 |
| OPT(Optimal) | 미래에 가장 늦게 다시 참조될 페이지를 교체 — 이론적 최선, 구현 불가능(미래를 모름) | 미래를 투시해서 안 볼 책부터 치움 |
| FIFO(First-In First-Out) | 가장 먼저 들어온(오래된) 페이지를 교체 | 책상에 제일 먼저 올린 책부터 치움 |
| LRU(Least Recently Used) | 가장 오랫동안 참조되지 않은 페이지를 교체 — 시간적 지역성에 근거 | 가장 오래 안 펼친 책을 치움 |
| LFU(Least Frequently Used) | 참조 횟수가 가장 적은 페이지를 교체 | 가장 적게 읽은 책을 치움 |
| NUR(Not Used Recently) / Clock | 참조 비트 1개와 시계바늘식 순회로 LRU를 근사하는 실무 알고리즘(Second Chance) | 최근에 안 편 책만 골라 치우되, 정확한 순서 대신 대충 훑어봄 |
| 참조 비트(Reference Bit) | 페이지가 최근에 접근됐으면 1, Clock 알고리즘이 순회하며 0으로 리셋 | 최근 열람 표시 스티커 |
| Dirty Bit(수정 비트) | 페이지가 수정됐는지 표시 — 1이면 내쫓을 때 디스크에 다시 써야 함 | "수정됨" 도장 |
| 벨라디의 모순(Belady's Anomaly) | 프레임(자리)을 늘렸는데 오히려 Page Fault가 늘어나는 역설 — FIFO 등 일부 알고리즘에서만 발생 | 책상을 넓혔는데 책을 더 자주 잃어버림 |
| 스택 알고리즘(Stack Algorithm) | N개 프레임일 때 캐시 내용이 항상 N+1개 프레임일 때의 부분집합이 되는 성질을 가진 알고리즘(LRU 등) — 이 성질을 가지면 벨라디의 모순이 생기지 않음 | 책상을 넓히면 기존에 있던 책은 그대로 있고 자리만 느는 것 |
| Working Set(작업 집합) | 특정 시간 구간 동안 프로세스가 실제로 활발히 참조하는 페이지들의 집합 | 지금 당장 펼쳐놓고 쓰는 책 묶음 |
| Thrashing(스래싱) | 프레임이 Working Set보다 부족해 CPU가 연산 대신 페이지 교체 I/O만 반복하는 마비 상태 | 책상이 좁아 책을 계속 바꿔 꽂기만 하다 정작 아무것도 못 읽음 |

## 깊이 이해

### 벨라디의 모순을 실제 숫자로 확인하기 (FIFO, 3프레임 vs 4프레임)
참조열 1,2,3,4,1,2,5,1,2,3,4,5 (총 12번 참조)를 FIFO로 처리하면:
- **3프레임**: 1→fault, 2→fault, 3→fault, 4→fault(1 축출), 1→fault(2 축출), 2→fault(3 축출), 5→fault(4 축출), 1→hit, 2→hit, 3→fault(1 축출), 4→fault(2 축출), 5→hit. **총 9회 fault**.
- **4프레임**: 1→fault, 2→fault, 3→fault, 4→fault, 1→hit, 2→hit, 5→fault(1 축출), 1→fault(2 축출), 2→fault(3 축출), 3→fault(4 축출), 4→fault(1 축출), 5→fault(2 축출). **총 10회 fault**.
- 프레임을 3개에서 4개로 **늘렸는데** fault가 9회에서 **10회로 오히려 증가**했다. 이것이 벨라디의 모순이다. 원인은 FIFO가 "얼마나 오래됐나"만 볼 뿐 "그 페이지가 지금 다시 필요한가"를 전혀 고려하지 않아, 프레임 배치가 바뀌면 축출 순서 자체가 완전히 달라지기 때문이다.
- LRU 계열은 이런 일이 생기지 않는다. LRU는 스택 알고리즘 성질을 가져, N프레임일 때 들어있는 페이지 집합이 항상 N+1프레임일 때 집합의 부분집합이 된다 — 프레임을 늘리면 기존에 캐싱되던 페이지는 그대로 유지된 채 자리만 늘어나므로, fault 수는 늘면 늘었지 줄어드는 방향으로 역전되지 않는다.

### NUR(Clock) 알고리즘이 LRU를 근사하는 방법 — 수치로 보기
- 순수 LRU는 페이지에 접근할 때마다 "가장 최근"이라는 순서 정보를 정확히 갱신해야 해서, 참조가 일어날 때마다 리스트 조작이 필요하다(참조 횟수만큼 오버헤드 발생).
- Clock 알고리즘은 이를 참조 비트 1개로 근사한다. 예를 들어 프레임 8개가 원형으로 배치되어 있고 시계바늘이 한 프레임씩 이동하며 검사한다고 하자. 바늘이 가리킨 페이지의 참조 비트가 1이면 0으로 바꾸고 다음 칸으로, 0이면 그 자리에서 즉시 축출한다. 최악의 경우에도 바늘이 프레임 수(8개)만큼만 돌면 반드시 축출 대상을 찾으므로, 정확한 시간 순서를 기록하지 않고도 "최근에 안 쓰인 페이지"를 프레임 수 이내의 순회로 찾아낸다 — LRU의 정밀도를 조금 포기하고 오버헤드를 크게 줄인 절충이다.

### Working Set과 스래싱 임계점 — 수치로 보기
- 프로세스가 특정 구간에서 실제로 활발히 쓰는 페이지 수(Working Set 크기)가 20개인데, 할당된 프레임이 10개뿐이라고 하자. 매 순간 최소 10개 페이지가 부족하므로, 방금 내쫓은 페이지를 다시 불러오는 일이 반복된다 — 이것이 스래싱이다.
- 여러 프로세스를 동시에 돌릴 때(다중 프로그래밍), 전체 프레임 수를 각 프로세스의 Working Set 합계보다 적게 나눠주면 시스템 전체가 스래싱에 빠져 CPU 이용률이 오히려 급락한다. Working Set 모델은 이 최소 요구치(20개)만큼은 프로세스마다 보장해 스래싱을 원천적으로 막자는 접근이다.

### 알고리즘 간 선정 원리 비교
- OPT: "미래에 가장 늦게 참조될 페이지" — Page Fault의 이론적 하한선을 계산하는 기준점으로만 쓰이고, 실제 구현은 불가능하다(미래를 모르므로).
- FIFO: "가장 오래 머문 페이지" — 지역성을 전혀 반영하지 않아 자주 쓰는 페이지도 오래됐다는 이유만으로 쫓겨날 수 있다.
- LRU: "가장 오랫동안 안 쓰인 페이지" — 시간적 지역성("최근에 안 쓴 건 앞으로도 안 쓸 것")에 근거해 OPT에 가장 근접하지만, 정확한 구현에는 매 접근마다 순서 갱신이 필요해 오버헤드가 크다.
- LFU: "누적 참조 횟수가 가장 적은 페이지" — 초반에 잠깐 몰아서 많이 참조된 페이지가 이후 전혀 안 쓰여도 참조 횟수 때문에 계속 살아남는 모순이 있다.
- NUR/Clock: LRU를 참조 비트 1개로 근사 — 현대 OS(리눅스 등)가 실제로 채택하는 실무 표준.

### 비유로 정리
- 옷장 정리에 비유하면: "가장 먼저 산 옷부터 버리기(FIFO)"는 옛날에 산 기본 반팔티를 실수로 버리게 되고, "가장 안 입은 옷부터 버리기(LRU)"는 2년간 한 번도 안 입은 패딩을 버리는 합리적 선택이 된다.

### 흔한 오해·주의점
- "LRU가 최고니까 무조건 LRU를 그대로 쓴다"는 실무와 다르다. 순수 LRU는 매 접근마다 순서를 갱신해야 하는 오버헤드 때문에, 실무에서는 참조 비트 기반의 근사 알고리즘(NUR/Clock)을 쓴다.
- 벨라디의 모순은 "프레임을 늘리면 무조건 나빠진다"는 뜻이 아니다. FIFO처럼 스택 알고리즘 성질이 없는 일부 알고리즘에서만, 특정 참조 패턴에 한해 나타나는 예외적 현상이다. LRU·OPT 등 스택 알고리즘에서는 발생하지 않는다.

## 연결 개념
- 가상 메모리·Demand Paging(앞 절) — 프레임이 부족해지는 원인이자, 교체 알고리즘이 작동하는 무대
- 지역성(Locality) — LRU·Working Set이 성립하는 근거("최근에 자주 쓴 건 앞으로도 자주 쓸 것")
- Thrashing — 교체 알고리즘이 아무리 좋아도 Working Set보다 프레임이 부족하면 무력화되는 근본적 한계

# 📝 【답안용】 시험 답안 템플릿

> 목적: 시험장에서 25분에 그대로 쓰는 답안 양식. 

## 핵심 인사이트 (3줄 요약)

> 1. **본질**: 페이지 교체 알고리즘은 요구 페이징(Demand Paging) 환경에서 물리 메모리(프레임)가 고갈되었을 때, 최적의 희생양(Victim)을 선정하여 Page Fault 레이트를 최소화하는 OS 스케줄링 기법이다.
> 2. **가치**: 시간적 지역성(Temporal Locality)에 기반한 LRU 및 근사 알고리즘(NUR/Clock)을 통해, 디스크 I/O로 인한 프로세서 스톨(Stall)을 극적으로 회피한다.
> 3. **판단 포인트**: 빈번한 페이지 교체는 시스템 붕괴인 스래싱(Thrashing)으로 이어지므로, 알고리즘 최적화뿐 아니라 워킹 셋(Working Set) 모델을 통한 적정 프레임 할당이 병행되어야 한다.

## 출제 의도 및 답안 포인트

| 출제 의도 | 반드시 짚을 핵심 | 감점 회피 포인트 |
|:---|:---|:---|
| 메모리 제약 하의 OS 자원 스케줄링 메커니즘 이해 | Page Fault 최소화 목표, LRU의 원리와 타당성 (지역성) | 각 알고리즘의 동작 방식만 나열하고 "왜 그런 방식을 쓰는지(지역성)"를 누락 |
| FIFO의 한계와 실무 알고리즘(NUR) 최적화 트레이드오프 파악 | 벨라디의 모순(Belady's Anomaly), 참조 비트를 활용한 하드웨어 오버헤드 완화 | "순수 LRU가 현대 OS의 표준"이라고 단정 짓는 오류 (실제론 근사 알고리즘 사용) |

> 요약: 이론적 이상(OPT), 비효율적 현실(FIFO), 합리적 대안(LRU), 실무적 타협(NUR)의 단계적 진화 과정을 명확한 표로 대조해야 한다.

## Ⅰ. 개요 및 필요성

- 정의: 가상 메모리에서 새로운 페이지를 적재하기 위해 빈 프레임이 없을 경우, 메모리에 상주 중인 페이지 중 가장 효용이 낮은 것을 선택해 교체(Swap-out)하는 알고리즘
- 배경: 제한된 물리 메모리(RAM) 용량과 무작위적인 프로그램의 요구 페이징(Demand Paging) 요청 간의 불균형
- 필요성: 부적절한 페이지 교체로 인한 Page Fault 폭증과 디스크 병목을 방지하고, 프로그램의 지역성(Locality)을 유지하기 위한 지능적 판단 기준 요구

## Ⅱ. 동작원리 및 페이지 교체 흐름도

```text
[Page Fault 발생 시 페이지 교체(Replacement) 마이크로 흐름]
CPU 주소 요청 -> MMU (Page Fault) -> OS 트랩 발생
  |--> 빈 프레임 확인 -> 여유 없음 (교체 알고리즘 발동)
  |--> [ 1. Victim(희생 페이지) 선정 ] (LRU, FIFO 등)
  |--> [ 2. Swap-out ] (희생 페이지의 Dirty 비트가 1이면 디스크에 쓰기)
  |--> [ 3. Swap-in ] (디스크에서 새 페이지를 빈 프레임에 적재)
  |--> 페이지 테이블 갱신 및 명령어 재개
```

| 단계 | 제어 주체 | 처리 내용 (오버헤드 억제 핵심) |
|:---:|:---|:---|
| 1 | OS 커널 | **Victim 선정 로직**: 알고리즘 성능이 Page Fault 횟수를 좌우함 |
| 2 | I/O 디바이스 | **Dirty Bit 확인**: 수정되지 않은 페이지를 내쫓으면 디스크 쓰기 오버헤드를 아낄 수 있음 |
| 3 | I/O 디바이스 | 디스크에서 메모리로 읽어오는 수 밀리초 지연 발생 (치명적) |
| 4 | OS 커널 | 문맥 교환 후 블록(Block)된 스레드를 다시 Ready 큐로 깨움 |

> 요약: 페이지 교체는 단순히 자리를 비우는 것이 아니라, 디스크 I/O라는 값비싼 대가를 동반하므로 Victim 선정에 사활을 걸어야 한다.

---

## Ⅲ. 주요 페이지 교체 알고리즘 비교

| 알고리즘 | 선정 원리 (Victim 선택 기준) | 특징 및 성능 판단 |
|:---|:---|:---|
| **OPT** (Optimal) | "가장 먼 미래에 사용될 페이지를 교체" | 불가능한 이론적 최상. 다른 알고리즘 성능 평가의 절대 기준점. |
| **FIFO** (First-In First-Out) | "메모리에 올라온 지 가장 오래된 페이지를 교체" | 단순하나 지역성을 무시함. 프레임을 늘려도 Fault가 느는 **벨라디의 모순** 발생. |
| **LRU** (Least Recently Used)| "과거에 가장 오랫동안 사용되지 않은 페이지 교체" | 시간적 지역성 대원칙에 부합하여 성능이 우수하나, 타임스탬프 기록 H/W 오버헤드 과다. |
| **LFU** (Least Frequently Used) | "과거에 가장 참조 횟수가 적은 페이지 교체" | 초기에만 반짝 많이 쓴 페이지가 끝까지 살아남는 모순 발생. |
| **NUR** (Not Used Recently) | "최근에 쓰이지 않은(참조 비트=0) 페이지를 교체" | LRU의 무거운 오버헤드를 줄인 **Clock(2차 기회)** 알고리즘. 현대 OS의 실무 표준. |

> 요약: 지역성 원리에 따라 LRU가 최상의 방어율을 보이나, 이를 유지하기 위한 H/W 부하를 줄이기 위해 참조 비트 1개만을 순회 감시하는 NUR(Clock)이 쓰인다.

## Ⅳ. 심화 비교: LRU 한계와 벨라디의 모순 (Belady's Anomaly)

벨라디의 모순은 시스템 자원(프레임)을 더 투입했는데도 성능(Page Fault)이 오히려 악화되는 역설적 현상이다.

| 구분 | FIFO 알고리즘 | LRU 계열 알고리즘 (스택 알고리즘) | 판단 포인트 |
|:---|:---|:---|:---|
| 미래 예측 근거 | 단순히 "오래 체류함" (순서 기반) | "최근에 안 썼으니 미래에도 안 씀" (시간 기반) | 지역성(Locality) 반영 여부 |
| 프레임 증가 시 | 페이지 적중률이 하락할 수 있음 (모순 발생) | $N$ 프레임의 캐시는 항상 $N+1$ 프레임 캐시의 부분집합 (모순 없음) | 스택 속성(Stack Property) 만족 여부 |
| 구현 오버헤드 | 큐(Queue) 포인터 이동만 필요 (매우 낮음) | 매 참조 시마다 리스트 위치 업데이트 필수 (높음) | TLB 및 캐시 라인 적용 가부 |

> 요약: LRU는 훌륭하지만 모든 페이지 접근마다 연결 리스트를 조작해야 하므로, MMU 내부의 하드웨어(TLB 교체 등)로는 쓰일 수 있어도 S/W 기반의 방대한 메인 메모리 교체에는 적합하지 않다.

---

## Ⅴ. 제약 사항 및 스래싱 (Thrashing) 방어

아무리 훌륭한 교체 알고리즘(LRU)도, 물리 메모리 자체가 프로그램이 요구하는 최소 프레임 수(Working Set)보다 절대적으로 작으면 무력화된다.

| 리스크 | 발생 원인 | S/W OS 대응 방안 | 극복 지표 |
|:---|:---|:---|:---|
| 스래싱 (Thrashing) | 다중 프로그래밍 정도가 너무 높아져, CPU 연산은 멈추고 하루 종일 페이지 교체 I/O만 수행하는 마비 상태 | **워킹 셋(Working Set) 모델**: 특정 시점에 집중적으로 참조되는 페이지들의 집합 크기만큼 프레임을 보장 할당 | CPU 이용률(Utilization) 반등 확인 |
| 페이지 지역 할당 붕괴 | A 프로세스 때문에 B 프로세스의 귀중한 페이지가 내쫓김 (전역 교체) | **PFF (Page Fault Frequency) 조절**: Fault 빈도가 높은 프로세스에 프레임을 집중 할당하고, 낮은 곳은 빼앗는 지역 교체(Local) | 프로세스별 일관된 응답 속도 |

> 요약: 교체 알고리즘은 '누구를 내쫓을 것인가'의 문제이며, 스래싱 방어(Working Set)는 '방을 애초에 몇 개나 줄 것인가'의 근본적 문제다.

## Ⅵ. 실무 적용 및 결론

**적용 방안 3개:**
1. RDBMS 버퍼 풀 옵티마이저 (Modified LRU): 오라클이나 MySQL 등 데이터베이스는 테이블 풀 스캔(Full Scan) 시 일회성 데이터가 캐시를 쓸어버려 LRU가 마비되는 것을 막기 위해, LRU 리스트를 핫(Hot)/콜드(Cold) 구역으로 나누고 중간에 삽입(Mid-point Insertion)하는 변형 LRU 적용
2. 엣지 디바이스 Clock 알고리즘 도입: 하드웨어 자원이 극히 제한적인 IoT 리눅스(임베디드 OS) 포팅 시, 1개의 참조 비트(Reference Bit)와 포인터 순회만으로 LRU와 거의 99% 유사한 적중률을 내는 2차 기회(Second Chance, Clock) 교체 알고리즘 커널 적용
3. 스래싱 회피를 위한 OOM 제어: 클라우드 컨테이너 환경(K8s)에서 메모리가 부족해져 교체 알고리즘이 한계(Thrashing)에 달하면, 전체 시스템 마비를 막기 위해 cgroup 기반의 OOM(Out of Memory) Killer가 우선순위가 낮은 프로세스(파드)를 선제적으로 강제 종료하여 워킹 셋 확보

**결론 (2줄):**
- 기술사 판단: 페이지 교체 알고리즘은 컴퓨터 과학의 난제인 "미래 참조 예측"을 지역성(Locality)이라는 통계적 타당성으로 타협한 스케줄링 예술이다.
- 향후 방향: 최근 SSD의 발전과 NVMe 도입으로 Swap I/O 속도가 극적으로 빨라지면서, 복잡한 LRU 추적 오버헤드 대신 압축 메모리(ZRAM)와 기계학습 기반의 지능형 페이지 프리패칭(Prefetching)이 주류 최적화 기법으로 부상하고 있다.
