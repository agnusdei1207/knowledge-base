# 📖 【암기용】 개념 완전 이해

> 목적: PCIe 스위치가 왜 필요하고 루트 컴플렉스와 무엇이 다른지 처음 봐도 이해하게 만든다. 시험 답안 양식이 아니라, 이해를 위한 친절한 설명이다.

## 한눈에
- **개요**: 하나의 PCIe 루트 포트를 여러 다운스트림 장치로 팬아웃(fan-out)해 연결하는 점대점 스위칭 구조
- **왜 필요한가**: CPU가 제공하는 PCIe 레인 수는 제한적인데, SSD·GPU·NIC 등 연결할 장치는 계속 늘어나므로 스위치로 레인을 분배해야 한다.
- **핵심 직관**: 건물 전기 배전반이 한 개의 메인 차단기 전력을 여러 층 콘센트로 분배하듯, PCIe 스위치는 하나의 업스트림 링크를 여러 다운스트림 장치에 분배한다.

## 깊이 이해
- **배경·문제의식**: PCIe는 병렬 버스가 아니라 레인(lane)이라는 직렬 차동 신호 쌍을 여러 개 묶어 쓰는 점대점 구조라, 루트 컴플렉스가 제공하는 레인 수를 넘는 장치를 직접 연결할 수 없다.
- **작동 원리**: PCIe 스위치는 1개의 업스트림 포트(Root Complex 방향)와 여러 개의 다운스트림 포트로 구성되며, 각 다운스트림 포트는 내부적으로 가상 PCI-to-PCI 브리지(virtual PCI-to-PCI bridge)로 동작한다.
- **작동 원리 보충**: 스위치는 트랜잭션 계층 패킷(TLP)의 주소·라우팅 정보를 보고 업스트림·다운스트림 포트 간에 패킷을 전달하며, 이 과정에서 홉당 지연이 추가된다.
- **작동 원리 보충2**: Non-Transparent Bridging(NTB)은 스위치 양쪽에 있는 두 개의 독립된 호스트가 서로의 주소 공간을 직접 보지 않고도 통신할 수 있게 하는 기능으로, 이중화 스토리지·클러스터 간 연결에 쓰인다.
- **비유**: 루트 컴플렉스는 건물의 메인 전력 인입구이고, PCIe 스위치는 각 층 배전반으로 한정된 전력(레인)을 여러 콘센트(SSD·GPU 슬롯)에 나눠준다.
- **구체 예시**: CPU가 PCIe Gen4 x16 레인만 제공해도, PCIe 스위치를 거치면 x4 레인짜리 NVMe SSD 4개를 동시에 연결할 수 있다(단, 스위치 업스트림 대역폭을 공유하므로 4개 SSD가 동시에 최대 성능을 낼 때는 업스트림 링크가 병목이 될 수 있음).
- **흔한 오해·주의점**: PCIe 스위치를 거치면 대역폭이 늘어나는 것이 아니라, 제한된 업스트림 대역폭을 다운스트림 여러 장치가 공유(oversubscription)하는 구조이므로 총 대역폭 설계 시 동시 사용률을 고려해야 한다.
- **흔한 오해·주의점 보충**: 스위치는 물리적 레인 폭을 늘려주지 않으며, 협상된(negotiated) 링크 폭과 속도는 항상 호스트-스위치-장치 구간 중 가장 작은 값으로 제한된다.

## 연결 개념
- NVMe·PCIe 인터페이스 — 스위치가 팬아웃하는 대표 저장장치 프로토콜
- CXL 컴퓨트 익스프레스 링크 — PCIe 물리 계층 위에 코히런시를 추가한 확장 개념
- 버스 대역폭·전송률 계산 — 레인당 GT/s x 레인 수로 대역폭을 산정하는 계산법

# 📝 【답안용】 시험 답안 템플릿

> 목적: 시험장에서 25분에 그대로 쓰는 답안 양식. 작성방식(추상표현 금지·수치·도식·문제유형 전환)을 엄격히 지킨다.
> 핵심: PCIe 스위칭을 단순 확장 장치로 서술하지 않고, 업스트림 대역폭 공유(oversubscription) 구조와 NTB를 통한 멀티호스트 연결까지 함께 제시한다.

## 핵심 인사이트 (3줄 요약)

> 1. **본질**: PCIe 스위치는 1개의 업스트림 포트와 여러 다운스트림 포트로 구성돼 루트 컴플렉스의 제한된 레인을 여러 장치로 팬아웃하는 점대점 중계 장치다.
> 2. **가치**: CPU가 직접 제공하지 못하는 수의 NVMe SSD·GPU를 연결할 수 있게 하되, 다운스트림 장치들은 업스트림 링크 대역폭을 공유한다.
> 3. **판단 포인트**: 동시 사용률이 낮은 워크로드는 스위치로 팬아웃해 비용을 절감하고, 동시 풀 대역폭이 필요한 워크로드는 루트 포트 직결 또는 업스트림 대역폭 확장을 선택해야 한다.

## 출제 의도 및 답안 포인트

| 출제 의도 | 반드시 짚을 핵심 | 감점 회피 포인트 |
|:---|:---|:---|
| 스위치 구조 이해 확인 | 업스트림·다운스트림 포트, 가상 P2P 브리지 구조 | 스위치를 단순 커넥터 확장 장치로 서술 |
| 대역폭 공유 개념 확인 | 업스트림 링크 대역폭 oversubscription | 스위치가 대역폭을 늘려준다는 오개념 |
| 멀티호스트 연결 이해 확인 | NTB(Non-Transparent Bridging)의 역할 | NTB와 일반 투명 스위칭을 혼동 |

> 요약: 이 문제는 스위치의 팬아웃 구조뿐 아니라 업스트림 대역폭 공유와 NTB 기반 멀티호스트 연결 개념까지 요구한다.

## Ⅰ. 개요 및 필요성

- 개요: 1개의 업스트림 포트를 여러 다운스트림 포트로 팬아웃하는 PCIe 점대점 스위칭 장치
- 배경: 루트 컴플렉스가 제공하는 PCIe 레인 수는 CPU 스펙에 제한되는데 연결할 SSD·GPU·NIC 수는 계속 증가함
- 필요성: 제한된 레인으로 다수 장치를 연결하려면 업스트림 대역폭을 공유하는 스위칭 구조와 동시 사용률 설계가 필요함

---

## Ⅱ. 구조 및 구성요소

```text
Root Complex(CPU) -> Upstream Port(스위치)
  -> Virtual PCI-to-PCI Bridge(내부 라우팅)
  -> Downstream Port 1 -> NVMe SSD
  -> Downstream Port 2 -> GPU
  -> Downstream Port 3 -> NTB -> 별도 호스트
```

| 구성요소 | 역할 | 특이사항 |
|:---|:---|:---|
| Upstream Port | 루트 컴플렉스 방향 연결 포트 | 다운스트림 전체가 공유하는 대역폭 상한 |
| Downstream Port | 종단 장치 방향 연결 포트 | 각 포트가 가상 PCI-to-PCI 브리지로 동작 |
| TLP Routing | 트랜잭션 계층 패킷 주소 기반 전달 | 홉(hop)당 약 100~150ns 수준의 지연 추가(참고용 수치) |
| NTB(Non-Transparent Bridging) | 독립된 두 호스트 간 주소 공간 격리 통신 | 이중화 스토리지, 클러스터 간 연결에 활용 |

> 요약: PCIe 스위치는 업스트림 1포트와 다운스트림 다수 포트를 가상 P2P 브리지로 연결하며, NTB로 독립 호스트 간 통신도 지원한다.

---

## Ⅲ. 동작원리 및 흐름도

```text
장치 요청 -> Downstream Port 수신 -> TLP 헤더 주소 확인
  -> 내부 가상 P2P 브리지 라우팅 -> Upstream Port로 전달
  -> Root Complex 응답 수신 -> 역경로로 Downstream Port에 전달
  -> 링크 협상(Speed/Width) 상태 지속 모니터링
```

| 단계 | 처리 내용 | 검증 기준 |
|:---:|:---|:---|
| 1 | 장치가 TLP 패킷을 Downstream Port로 송신 | 패킷 헤더 주소·타입 유효성 |
| 2 | 스위치 내부 라우팅 테이블로 목적지 확인 | 라우팅 테이블 일치 여부 |
| 3 | Upstream Port를 통해 Root Complex로 전달 | 업스트림 대역폭 사용률 |
| 4 | 응답을 역경로로 Downstream Port에 반환 | 왕복 지연(latency) 목표치 이내 |
| 5 | 링크 협상 상태(negotiated width/speed) 확인 | lspci 등으로 실제 협상값 검증 |

> 요약: PCIe 스위치는 TLP 주소 기반 라우팅으로 다운스트림-업스트림 간 패킷을 중계하며, 홉마다 지연이 추가되므로 링크 협상 상태를 지속 점검해야 한다.

---

## Ⅳ. 특징

| 구분 | 루트 컴플렉스 직결 | PCIe 스위치 경유 | 수치·표준 포인트 |
|:---|:---|:---|:---|
| 레인 확장성 | CPU 제공 레인 수로 제한 | 다운스트림 포트 수만큼 장치 확장 | Gen4 레인당 이론치 약 1.97GB/s(참고용 계산) |
| 대역폭 특성 | 장치별 독점 대역폭 확보 | 업스트림 대역폭을 다운스트림이 공유(oversubscription) | 동시 사용률에 따라 실효 대역폭 감소 |
| 지연 | 홉 없음, 최소 지연 | 스위치 홉당 추가 지연 발생 | 홉당 약 100~150ns 수준(참고용) |
| 멀티호스트 지원 | 단일 호스트 전용 | NTB로 독립 호스트 간 연결 가능 | 이중화 스토리지 컨트롤러 등에 활용 |

> 요약: 스위치 경유는 확장성과 멀티호스트 연결을 얻는 대신 업스트림 대역폭 공유와 홉 지연이라는 비용을 지불한다.

## Ⅴ. 심화 비교 및 적용 판단

| 비교 축 | 루트 컴플렉스 직결 | PCIe 스위치 팬아웃 | 선택 기준 |
|:---|:---|:---|:---|
| 구조 | CPU 레인에 장치 직접 연결 | 스위치로 다수 장치 팬아웃 | 연결 장치 수가 CPU 레인 수를 초과하면 스위치 필요 |
| 비용/성능 | 장치당 독점 대역폭, 레인 부족 시 확장 불가 | 저비용으로 장치 수 확장, 동시 풀 성능 시 병목 가능 | 동시 사용률이 낮은 다수 SSD는 스위치가 유리 |
| 운영/위험 | 단순 구조, 장애 지점 적음 | 스위치 장애 시 다운스트림 전체 영향 | 스위치 이중화·NTB 페일오버 설계 필요 여부 |

> 요약: 장치 수가 레인 한계를 넘고 동시 사용률이 낮으면 스위치 팬아웃을, 개별 장치의 독점 풀 대역폭이 필요하면 직결을 선택한다.

| 리스크 | 원인 | 대응 방안 | 확인 지표 |
|:---|:---|:---|:---|
| 업스트림 병목 | 다운스트림 장치들이 동시에 풀 대역폭 요구 | 워크로드 분산 스케줄링, 업스트림 대역폭 여유 설계 | 업스트림 링크 사용률 |
| 링크 다운그레이드 | 슬롯 배선·펌웨어 오류로 협상 레인 폭 축소 | lspci로 negotiated width/speed 확인 및 재협상 | 실제 협상 lane width 대 설계값 |
| 스위치 단일 장애점 | 스위치 고장 시 다운스트림 장치 전체 접근 불가 | 이중화 스위치 구성, NTB 기반 페일오버 | 스위치 장애 시 페일오버 소요 시간 |

> 요약: PCIe 스위칭의 핵심 리스크는 업스트림 병목과 단일 장애점이며, 대역폭 여유 설계와 이중화로 통제한다.

| 점검 항목 | 목표 기준 | 측정 방법 |
|:---|:---|:---|
| 링크 협상 상태 | 설계된 lane width·speed와 일치 | lspci -vv, PCIe AER 로그 |
| 업스트림 사용률 | 피크 시 업스트림 대역폭 사용률 목표치 이내 | 스위치 관리 인터페이스, 성능 카운터 |
| 홉 지연 | 목표 왕복 지연 이내 유지 | 트레이스 분석, 벤치마크 |

> 요약: PCIe 스위칭 설계의 성공 여부는 협상된 링크 상태, 업스트림 사용률, 홉 지연 지표로 판단한다.

## Ⅵ. 실무 적용 및 결론

**적용 방안 3개:**
1. 다수 NVMe SSD를 연결할 때 PCIe 스위치로 팬아웃하되 동시 접근 워크로드 패턴을 분석해 업스트림 대역폭 병목 여부를 사전 검증함
2. 이중화 스토리지·클러스터 간 연결에는 NTB 기능을 활용해 독립 호스트 간 주소 공간을 격리한 채 통신하도록 설계함
3. 슬롯 배치 후 lspci로 협상된 lane width·speed를 확인해 설계 스펙과 실제 링크 상태가 일치하는지 검증함

**결론 (2줄):**
- 기술사 판단: PCIe 스위치는 레인을 늘리는 장치가 아니라 제한된 대역폭을 여러 장치에 공유시키는 구조이므로 동시 사용률 설계가 핵심임
- 향후 방향: CXL·PCIe Gen5/6 기반 GPU·메모리 풀링 확산으로 스위칭 패브릭 규모가 커지며 NTB·코히런시 확장이 함께 요구되는 추세임
