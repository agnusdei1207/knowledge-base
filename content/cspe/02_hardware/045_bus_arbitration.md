## 미리 알고가기

- **버스 마스터 ($Bus\ Master$)**: 시스템 버스의 사용권을 요청하고 제어할 수 있는 주체 ($CPU$, $DMA$, $I/O$ 컨트롤러 등)
- **버스 슬레이브 ($Bus\ Slave$)**: 마스터의 요청에 따라 데이터를 제공하거나 수용하는 수동적 장치 (메모리 등)
- **버스 중재 ($Arbitration$)**: 여러 마스터가 동시에 버스를 사용하려 할 때, 충돌을 방지하기 위해 한 번에 하나의 마스터에게만 사용권을 부여하는 제어 과정
- **기아 현상 ($Starvation$)**: 우선순위가 낮은 장치가 높은 순위 장치들에 밀려 장기간 버스 사용권을 얻지 못하는 상태
- **버스 요청/승인 ($BR/BG$)**: 버스 사용을 요청($Bus\ Request$)하고 승인($Bus\ Grant$)하는 신호 체계

## Ⅰ. 개요

- **정의/개념**: 버스 중재는 공용 전송로인 시스템 버스를 점유하기 위해 복수의 장치가 경합할 때, 미리 정의된 우선순위나 공정성 정책에 따라 사용권을 배분하여 데이터 충돌을 막고 시스템 전체의 전송 효율을 최적화하는 하드웨어 제어 방식임
- **배경/필요성**: 현대 컴퓨터는 멀티코어 $CPU$, $DMA$, 고속 네트워크 카드 등 수많은 버스 마스터가 공존함. 중재 기작이 없다면 전기적 충돌로 인한 데이터 파손은 물론, 특정 장치가 버스를 독점하여 실시간 시스템의 응답성이 파괴될 수 있음

## Ⅱ. 특징 및 비교

### 가. 중앙 집중식 vs 분산식 중재 방식 비교

| 구분 | 중앙 집중식 중재 ($Centralized$) | 분산식 중재 ($Distributed$) |
|:---|:---|:---|
| **제어 주체** | 별도의 중재기($Arbiter$) 존재 | 모든 마스터가 중재 로직 내장 |
| **장점** | 제어 로직 단순, 우선순위 변경 용이 | 단일 장애점($SPOF$) 없음, 확장성 우수 |
| **단점** | 중재기 고장 시 전체 시스템 마비 | 하드웨어 비용 상승, 구현 복잡 |
| **적합 영역** | 일반적인 $PC$, 소규모 시스템 | 고성능 서버, 멀티프로세서 시스템 |

### 나. 세부 중재 기법별 특성

| 기법 | 동작 원리 | 핵심 장점 | 한계점 |
|:---|:---|:---|:---|
| **데이지 체인** | $BG$ 신호를 직렬로 순차 전달 | 선로 구성이 매우 단순함 | 뒤쪽 장치의 기아 발생 위험 |
| **폴링 방식** | 중재기가 장치를 순서대로 조회 | 공정성 확보 가능 | 조회 시 오버헤드 발생 |
| **독립 요청** | 장치마다 전용 $BR/BG$ 선 배정 | 응답 속도가 가장 빠름 | $I/O$ 핀 소모가 많음 |

> 요약: 신속함이 중요하면 '독립 요청', 단순함이 중요하면 '데이지 체인'을 선택함

## Ⅲ. 구성요소/구조

### 가. 중앙 중재기 기반의 버스 점유 프로세스 구조

```text
[ Master A ] --(BR_A)--> [ Bus Arbiter ] --(BG_A)--> [ System Bus ]
      |                      |                          |
[ Master B ] --(BR_B)--------+                          |
      |                      |                          |
[ Master C ] --(BR_C)--------+      [ Busy Signal ] <---+
```

### 나. 주요 구성 요소 및 역할

| 구성요소 | 역할 및 설명 | 핵심 포인트 |
|:---|:---|:---|
| 버스 중재기 ($Arbiter$) | 요청 신호를 수집하고 승인 여부를 결정 | 우선순위 결정 알고리즘 탑재 |
| 우선순위 분석기 | 경합 발생 시 어떤 장치를 먼저 처리할지 판단 | 고정 vs 가변 우선순위 정책 |
| 버스 비지 신호 ($BBUSY$) | 현재 버스가 사용 중임을 나타내는 상태선 | 중복 승인 방지를 위한 락($Lock$) |
| 타임아웃 타이머 | 특정 장치가 버스를 너무 오래 독점하는 것을 방지 | 강제 회수 및 시스템 데드락 방지 |

> 요약: 요청자가 손을 들면($BR$), 중재기가 판단하여 허가증($BG$)을 주고, 사용 중임을 표시($BBUSY$)하는 흐름임

## Ⅳ. 문제점 및 개선방안

1. **저우선순위 장치의 기아 ($Starvation$)**: 고정 우선순위 방식에서 특정 장치가 버스를 전혀 사용하지 못하는 문제
   - **개선방안**: **가변 우선순위(Rotating Priority)** 또는 **라운드 로빈(Round-Robin)** 방식을 적용하여 모든 장치에 공평한 기회를 제공함

2. **중재 지연 시간 ($Arbitration\ Latency$)**: 장치가 많아질수록 누가 버스를 쓸지 결정하는 시간 자체가 성능 병목이 됨
   - **개선방안**: 실제 전송이 일어나는 동안 다음 중재를 미리 수행하는 **버스 파이프라이닝($Pipelining$)** 기법을 적용함

3. **버스 독점 현상**: 한 장치가 대량의 데이터를 보내느라 버스를 장시간 점유하여 다른 장치의 응답성을 해치는 경우
   - **개선방안**: 최대 점유 시간($Time\ Slice$)을 설정하거나, **사이클 스틸링($Cycle\ Stealing$)**을 통해 $CPU$와 $DMA$가 번갈아 사용하도록 강제함

## Ⅴ. 실무 적용 사례

| 적용 영역 | 적용 방식 | 확인 지표 |
|:---|:---|:---|
| 시스템 온 칩 ($SoC$) | $AXI$ 버스 프로토콜 내에서 여러 마스터의 접근을 $QoS$ 기반으로 중재 | $Bus\ Latency$, $Throughput$ |
| 산업용 제어 장치 | 실시간성이 중요한 센서에는 최상위 우선순위를, 로그 저장 장치에는 낮은 순위 부여 | $Response\ Time\ Determinism$ |
| 서버 스토리지 | 수십 개의 $SAS/SATA$ 드라이브 접근 요청을 지능형 컨트롤러가 중재하여 병목 최소화 | $Aggregate\ IOPS$, $Stall\ Time$ |

> 요약: '절대적 우선순위'가 필요한 분야와 '균등한 배분'이 필요한 분야를 구분하여 정책을 수립함

## Ⅵ. 결론

버스 중재 방식은 시스템 내부의 자원 배분 정책을 하드웨어 수준에서 구현한 것임. 단순히 충돌을 막는 것을 넘어, 시스템의 성격(실시간성 vs 처리량)을 결정짓는 아키텍처의 설계 철학이 담겨 있음.

기술사는 단순한 중재 알고리즘 암기를 넘어, **$PCIe$**와 같이 점대점($Point-to-Point$) 연결로 변화한 현대의 인터커넥트 환경에서도 스위치 내부의 중재 로직이 어떻게 활용되는지 이해해야 함. 또한, 멀티프로세서 환경에서 캐시 일관성 유지와 버스 중재가 결합되어 시스템의 확장성($Scalability$)에 미치는 영향을 분석할 수 있는 통찰력이 요구됨.
