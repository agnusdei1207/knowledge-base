## Ⅰ. 개요
- **정의**: 출력이 0, 1, 고임피던스(High-Z) 세 상태를 갖는 논리 소자
- **배경/필요성**: 공유 버스에 복수 장치가 동시 출력하면 전기적 충돌(Bus Contention)이 발생하므로, 비활성 장치의 출력을 전기적으로 분리할 수단이 필요함
- **비유**: 여러 사람이 하나의 마이크를 공유할 때, 발언권이 없는 사람은 마이크 스위치를 꺼 두는 것과 같음

| 출제 의도 | 반드시 짚을 핵심 | 감점 회피 포인트 |
|:---|:---|:---|
| 버스 구조에서 다중 드라이버 충돌 해결 원리 | High-Z 상태의 전기적 의미(오픈 회로) | High-Z를 논리 0과 혼동하지 않을 것 |

> 요약: Enable 신호로 출력을 0/1/High-Z 중 하나로 전환하여 공유 버스의 충돌을 방지하는 소자임

## Ⅱ. 구성요소
```text
Enable ---+
          |
          v
Input -->[Buffer]---> Output (0 / 1 / High-Z)
```

| 구성요소 | 설명 | 비유 |
|:---|:---|:---|
| Enable(OE) | 출력 활성/비활성 제어 신호, Active-Low 또는 Active-High로 동작함 | 마이크 스위치 |
| Input | 전달할 논리값(0 또는 1) | 발언 내용 |
| Output | Enable=1이면 Input 값 출력, Enable=0이면 High-Z 상태로 전환됨 | 마이크 출력 |
| High-Z 상태 | 출력 단자가 회로에서 전기적으로 분리된 상태 | 전화기 수화기를 내려놓은 상태 |

> 요약: Enable 신호가 버퍼의 출력 연결/분리를 결정하며, High-Z는 전기적 오픈 회로와 동등함

## Ⅲ. 절차
```text
버스 마스터 선정 --> Enable 신호 인가 --> 데이터 출력 --> 전송 완료 후 High-Z 복귀
```
- 1단계: 버스 중재기(Arbiter)가 버스 사용 권한을 특정 장치에 부여함
- 2단계: 선정된 장치의 Enable(OE) 핀에 활성 신호를 인가하여 출력을 개방함
- 3단계: 장치가 데이터 버스에 0 또는 1 논리값을 구동(Drive)함
- 4단계: 전송 완료 후 Enable을 비활성화하여 출력을 High-Z로 복귀시킴

> 요약: 중재 → 활성화 → 데이터 구동 → High-Z 복귀의 4단계로 버스 충돌 없이 데이터를 전송함

## Ⅳ. 문제점
- Bus Contention: 두 장치의 Enable이 동시에 활성화되면 0과 1이 충돌하여 과전류 발생 — 버퍼 또는 버스 드라이버 손상 위험이 있음
- Floating Bus: 모든 장치가 High-Z 상태이면 버스 전압이 불확정(Floating) — 수신 측에서 잘못된 값을 래치할 수 있음
- 전파 지연 누적: Enable 전환 시 출력 안정까지 수 ns의 지연 발생 — 고속 버스에서 타이밍 마진을 축소시킴

> 요약: 동시 활성화에 의한 충돌, 전체 비활성화에 의한 부유 전압, 전환 지연이 주요 문제임

## Ⅴ. 개선방안
1. 단기: 버스 중재 로직에 상호 배타(Mutual Exclusion) 인터록을 삽입하여 동시 Enable 방지
2. 중기: 풀업/풀다운 저항 또는 버스 홀더(Bus Holder) IC를 적용하여 Floating 상태 제거
3. 장기: 포인트-투-포인트 직렬 링크(PCIe, CXL 등)로 전환하여 공유 버스 자체를 제거함

> 요약: 중재 인터록, 버스 홀더, 직렬 링크 전환 순으로 공유 버스 한계를 극복함

## Ⅵ. 전망
- 발전 방향: 레거시 병렬 버스(ISA, PCI)는 직렬 링크로 대체 중이나, DRAM 데이터 버스·FPGA I/O 등에서 3-상태 버퍼는 여전히 사용됨
- 기술사적 판단: SoC(047 참조) 내부 AMBA 버스는 MUX 기반으로 전환되었으나, 보드 레벨 병렬 인터페이스에는 3-상태 제어 지식이 필수임
- 기술사 제언: 공유 버스 설계 시 타이밍 분석과 중재 프로토콜을 함께 검토하여 Contention·Floating 문제를 예방할 것을 권고함
