# 📖 【암기용】 개념 완전 이해

> 목적: Type 1과 Type 2 하이퍼바이저를 처음 봐도 무엇이 하드웨어 위에서 직접 도는지 헷갈리지 않게 만든다. 시험 답안 양식이 아니라, 이해를 위한 친절한 설명이다.

## 한눈에
- **개요**: 하이퍼바이저는 물리 하드웨어를 여러 가상 머신(VM)에 나눠주는 소프트웨어이며, 실행 위치에 따라 Type 1(베어메탈)과 Type 2(호스티드)로 나뉜다.
- **왜 필요한가**: 서버 한 대를 여러 워크로드가 안전하게 나눠 쓰려면 CPU·메모리·디바이스를 격리해 할당하는 계층이 필요하다. Type 1과 Type 2는 이 계층을 어디에 두느냐로 성능과 활용 목적이 갈린다.
- **핵심 직관**: Type 1은 건물 자체가 관리사무소(하이퍼바이저)이고 그 위에 세대(VM)가 있는 구조이며, Type 2는 이미 완공된 집(호스트 OS) 안에 컨테이너 박스(VM)를 들여놓는 구조다.

## 깊이 이해
- **배경·문제의식**: 서버 가상화 초기에는 VM 하나에 애플리케이션 하나만 돌려도 하드웨어 자원을 낭비했고, 반대로 물리 서버 여러 대를 유지하면 운영 비용이 컸다.
- **배경·문제의식**: Type 1은 하이퍼바이저가 하드웨어를 직접 제어하므로 오버헤드가 작아 프로덕션 데이터센터에 쓰이고, Type 2는 기존 OS 위에서 바로 실행할 수 있어 개발·테스트 환경에 적합하다.
- **작동 원리**: Type 1(베어메탈)은 물리 하드웨어에 하이퍼바이저가 직접 설치되어 VM을 관리하며, 대표 예시는 VMware ESXi, Xen, Microsoft Hyper-V, KVM(리눅스 커널에 통합된 하이퍼바이저)이다.
- **작동 원리**: Type 2(호스티드)는 호스트 OS 위에 애플리케이션 형태로 하이퍼바이저가 설치되고 그 안에서 VM이 실행되며, 대표 예시는 VMware Workstation, Oracle VirtualBox, Parallels Desktop이다.
- **비유**: Type 1은 공항 관제탑이 활주로(하드웨어)를 직접 통제하는 구조이고, Type 2는 관제탑 없이 여행사 앱(호스트 OS 위 애플리케이션)이 항공편을 예약해주는 구조다.
- **구체 예시**: 데이터센터에서 ESXi(Type 1)를 서버에 직접 설치해 수십 개 VM을 운영하는 반면, 개발자 노트북에서는 Windows(호스트 OS) 위에 VirtualBox(Type 2)를 설치해 테스트 VM 한두 개를 띄운다.
- **흔한 오해·주의점**: "Type 1은 하드웨어 위에서 직접 실행되고 Type 2는 OS 위에서 실행된다"는 방향을 절대 반대로 쓰면 안 된다.
- **흔한 오해·주의점**: KVM은 리눅스 커널 자체가 하이퍼바이저 기능(커널 모듈)을 갖는 구조라서 통상 Type 1로 분류하지만, 호스트 리눅스가 범용 OS로도 동시에 동작한다는 점에서 순수 베어메탈과 다르다는 논쟁이 있다.

## 연결 개념
- VT-x·AMD-V — 두 타입 모두가 의존하는 CPU 하드웨어 가상화 기반
- IOMMU — Type 1 환경에서 디바이스 패스스루를 지원하는 하드웨어
- 컨테이너(Docker·Kubernetes) — 커널 공유 방식으로 하이퍼바이저 계층 자체를 생략하는 대안 가상화

# 📝 【답안용】 시험 답안 템플릿

> 목적: 시험장에서 25분에 그대로 쓰는 답안 양식. 작성방식(추상표현 금지·수치·도식·문제유형 전환)을 엄격히 지킨다.
> 핵심: 하이퍼바이저 답안은 Type 1·Type 2 실행 위치 차이, 성능·오버헤드 차이, 적용 시나리오, 대표 제품을 함께 제시한다.

## 핵심 인사이트 (3줄 요약)

> 1. **본질**: 하이퍼바이저는 CPU·메모리·디바이스를 VM 단위로 격리·할당하는 가상화 계층이며, 실행 위치에 따라 Type 1(베어메탈)과 Type 2(호스티드)로 구분한다.
> 2. **가치**: Type 1은 하드웨어 직접 제어로 오버헤드를 줄여 프로덕션 데이터센터에 적합하고, Type 2는 기존 OS 위에서 손쉽게 설치·실행할 수 있어 개발·테스트에 적합하다.
> 3. **판단 포인트**: "하드웨어 위 직접 실행=Type 1, 호스트 OS 위 실행=Type 2"라는 방향을 반드시 정확히 서술해야 하며 반대로 쓰면 개념 오류로 감점된다.

## 출제 의도 및 답안 포인트

| 출제 의도 | 반드시 짚을 핵심 | 감점 회피 포인트 |
|:---|:---|:---|
| 가상화 아키텍처 이해 확인 | Type 1·Type 2 실행 위치, 대표 제품(ESXi/Xen/Hyper-V vs Workstation/VirtualBox) | Type 1·Type 2 정의를 반대로 서술 |
| 성능·오버헤드 판단 확인 | 하드웨어 직접 제어 vs 호스트 OS 경유 오버헤드 | 오버헤드 차이 근거 없이 "Type 1이 빠르다"고만 서술 |
| 적용 시나리오 판단 확인 | 프로덕션 vs 개발·테스트 환경 선택 기준 | 두 타입을 용도 구분 없이 나열만 함 |

> 요약: 이 문제는 Type 1·Type 2의 실행 위치 방향을 정확히 짚고, 그에 따른 성능·용도 차이를 근거로 제시하는지를 본다.

## Ⅰ. 개요 및 필요성

- 정의: 물리 하드웨어를 여러 VM에 격리·할당하는 소프트웨어 계층으로, 실행 위치에 따라 베어메탈(Type 1)과 호스티드(Type 2)로 구분
- 배경: 물리 서버 단위 운영은 자원 낭비와 비용 증가를 초래해 하드웨어 공유 계층인 하이퍼바이저가 등장
- 필요성: 프로덕션과 개발·테스트는 요구되는 오버헤드·격리 수준이 달라 적합한 하이퍼바이저 타입 선택이 필요

---

## Ⅱ. 구조 및 구성요소

```text
Type 1(베어메탈)
  Hardware -> Hypervisor(ESXi/Xen/Hyper-V/KVM) -> VM1/VM2/VM3

Type 2(호스티드)
  Hardware -> Host OS -> Hypervisor App(Workstation/VirtualBox) -> VM1/VM2
```

| 구성요소 | Type 1 | Type 2 |
|:---|:---|:---|
| 실행 위치 | 하드웨어 위에 직접 설치 | 호스트 OS 위에 애플리케이션으로 설치 |
| 대표 제품 | VMware ESXi, Citrix Xen, Microsoft Hyper-V, KVM | VMware Workstation, Oracle VirtualBox, Parallels Desktop |
| 주 활용처 | 데이터센터, 클라우드 프로덕션 | 개발자 PC, 테스트·데모 환경 |
| 오버헤드 | 하드웨어 직접 제어로 낮음 | 호스트 OS 커널 경유로 상대적으로 높음 |

> 요약: Type 1은 하드웨어와 하이퍼바이저 사이에 다른 OS가 없고, Type 2는 호스트 OS가 하이퍼바이저와 하드웨어 사이에 존재한다.

---

## Ⅲ. 동작원리 및 흐름도

```text
Type 1: VM 요청 -> Hypervisor(root mode, VT-x/AMD-V) -> 하드웨어 직접 스케줄링 -> VM 실행
Type 2: VM 요청 -> Hypervisor App -> Host OS 커널 드라이버 경유 -> 하드웨어 접근 -> VM 실행
```

| 단계 | Type 1 처리 | Type 2 처리 |
|:---:|:---|:---|
| 1 | 하이퍼바이저가 부팅 시 하드웨어를 직접 초기화 | 호스트 OS 부팅 후 하이퍼바이저 애플리케이션 실행 |
| 2 | VM 스케줄링을 하이퍼바이저 커널이 직접 수행 | 호스트 OS 스케줄러가 하이퍼바이저 프로세스를 스케줄링 |
| 3 | 디바이스 접근은 하이퍼바이저 드라이버가 처리 | 디바이스 접근은 호스트 OS 드라이버를 경유 |
| 4 | VT-x·AMD-V로 게스트 특권 명령어 트랩 | 동일 CPU 확장을 호스트 OS 위에서 활용 |

> 요약: Type 1은 하이퍼바이저가 스케줄링·디바이스 접근을 직접 담당하고, Type 2는 호스트 OS를 한 단계 더 거친다.

---

## Ⅳ. 특징

| 구분 | Type 1(베어메탈) | Type 2(호스티드) | 수치·표준 포인트 |
|:---|:---|:---|:---|
| 실행 위치 | 하드웨어 직접 | 호스트 OS 위 애플리케이션 | 커널 계층 개수 차이 |
| 성능 오버헤드 | 낮음(하드웨어 직접 제어) | 상대적으로 높음(호스트 OS 경유) | I/O 경로 hop 수 |
| 설치·운영 난이도 | 전용 서버·부팅 매체 필요 | 기존 OS에 설치 파일로 배포 | 운영 인력·자동화 수준 |
| 대표 활용 | 데이터센터, 프라이빗·퍼블릭 클라우드 | 개발·테스트, 데스크톱 가상화 | 워크로드 SLA 요구 수준 |

> 요약: Type 1은 성능·격리 중심 프로덕션에, Type 2는 편의성 중심 개발·테스트에 적합하다.

## Ⅴ. 심화 비교 및 적용 판단

| 비교 축 | Type 1 | Type 2 | 선택 기준 |
|:---|:---|:---|:---|
| 구조 | 하드웨어 직접, 전용 부팅 | 호스트 OS 종속 | 프로덕션 SLA 요구 시 Type 1 |
| 비용/성능 | 전용 서버·라이선스 비용 | 기존 PC 재활용 가능 | VM 밀도·성능 목표로 결정 |
| 운영/위험 | 전용 관리 도구·패치 필요 | 호스트 OS 장애가 VM에 전파 | 격리 수준과 장애 영향 범위로 판단 |

> 요약: 프로덕션·고밀도 VM은 Type 1, 개발·개인 테스트는 Type 2를 선택하는 것이 일반적 기준이다.

| 리스크 | 원인 | 대응 방안 | 확인 지표 |
|:---|:---|:---|:---|
| 호스트 OS 장애 전파(Type 2) | 호스트 OS 크래시·업데이트 재부팅 | 프로덕션 워크로드는 Type 1로 이전 | 호스트 OS 가용성 |
| VM 밀도 저하 | 오버헤드 누적으로 코어당 VM 수 제한 | 하드웨어 가속(VT-x/AMD-V, EPT/NPT) 활성화 | VM 대비 CPU 사용률 |
| 관리 복잡도 | Type 1 다수 클러스터 운영 복잡 | vCenter·SCVMM 등 중앙 관리 도구 도입 | 클러스터 장애 대응 시간(MTTR) |

> 요약: 하이퍼바이저 리스크는 호스트 의존성, VM 밀도, 관리 복잡도로 구분해 통제한다.

| 점검 항목 | 목표 기준 | 측정 방법 |
|:---|:---|:---|
| VM 성능 | 네이티브 대비 오버헤드 목표치 이내 | 벤치마크, hypervisor 성능 카운터 |
| 가용성 | 호스트 장애 시 VM 재기동 RTO 목표 이내 | HA/failover 테스트 로그 |
| 자원 활용 | CPU·메모리 사용률 목표 범위 유지 | vCenter/Hyper-V Manager 모니터링 |

> 요약: 도입 성공 여부는 VM 성능 오버헤드, 장애 복구 시간, 자원 활용률로 판단한다.

---

## Ⅵ. 실무 적용 및 결론

**적용 방안 3개:**
1. 프로덕션·클라우드 인프라는 Type 1(ESXi·Hyper-V·KVM)을 기본으로 하고 VT-x/AMD-V·EPT/NPT를 활성화함
2. 개발·테스트·데모 환경은 Type 2(VirtualBox·Workstation)로 신속히 구성해 배포 주기를 단축함
3. Type 1 클러스터는 HA·vMotion 등 라이브 마이그레이션 기능으로 RTO 목표를 관리함

**결론 (2줄):**
- 기술사 판단: 프로덕션·고밀도 요구는 Type 1, 개인·개발 환경은 Type 2를 선택 기준으로 삼음
- 향후 방향: 컨테이너·경량 VM(Kata Containers, Firecracker) 확산으로 하이퍼바이저와 커널 공유 가상화의 경계가 재편됨
