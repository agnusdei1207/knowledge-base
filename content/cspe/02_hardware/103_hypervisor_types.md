## 미리 알고가기

- Type 1은 물리 하드웨어 위에서 직접 동작하는 하이퍼바이저임
- Type 2는 호스트 OS 위에서 애플리케이션처럼 동작하는 하이퍼바이저임
- overcommit은 물리 자원보다 많은 가상 자원을 할당해 쓰는 운영 방식임
- 스냅샷은 VM 디스크와 상태를 특정 시점 기준으로 보존하는 기능임

## Ⅰ. 개요

- **정의/개념**: Type 1과 Type 2 하이퍼바이저는 가상머신을 관리하는 계층이 물리 하드웨어에 직접 위치하는지, 호스트 OS 위에 위치하는지를 기준으로 구분하는 서버 가상화 구조임
- **배경/필요성**: 운영 서버는 낮은 오버헤드와 강한 격리와 자동화가 중요하지만 개발과 테스트 환경은 설치 편의와 호스트 연동이 더 중요하므로, 하이퍼바이저 위치를 구분해 선택해야 함

## Ⅱ. 특징

- Type 1은 하드웨어 위에서 VM과 장치 자원을 직접 관리함
- Type 2는 호스트 OS의 드라이버와 프로세스 위에서 VM을 실행함
- Type 1은 운영 서버·클라우드, Type 2는 개발·시험용 호스트에 배치함
- 장애 범위와 보안 경계가 하이퍼바이저 위치에 따라 달라짐

## Ⅲ. 종류 및 비교

| 판단 기준 | Type 1 하이퍼바이저 | Type 2 하이퍼바이저 |
|:---|:---|:---|
| 위치 | 하드웨어 위에서 직접 실행됨 | 호스트 OS 위에서 실행됨 |
| 성능과 격리 | 오버헤드가 낮고 격리 경계가 더 단순함 | 호스트 OS 경유 비용과 의존성이 추가됨 |
| 대표 환경 | 데이터센터·클라우드 운영 서버 | 개발 노트북·시험·교육 환경 |
| 장애 영향 | 관리 도메인 문제로 범위가 제한되기 쉬움 | 호스트 OS 장애가 VM 전체에 전파될 수 있음 |

## Ⅳ. 구성요소 및 구조

| 구성요소 | 설명 |
|:---|:---|
| 가상머신 | 게스트 OS와 애플리케이션이 실행되는 논리 서버로 자원 격리 대상이 됨 |
| 하이퍼바이저 코어 | vCPU와 메모리와 I/O를 가상화하며 성능과 격리 수준을 직접 결정함 |
| 호스트 OS | Type 2에서 장치 드라이버와 파일시스템 기반을 제공하지만 추가 장애 경로가 됨 |
| 관리 계층 | 이미지 배포와 snapshot과 migration과 정책 제어를 담당해 운영 자동화 수준을 좌우함 |

```text
+-------------+     +-------------+     +-------------+     +-------------+
| 자원 등록      | --> | VM 생성        | --> | 자원 스케줄링  | --> | 운영 관리      |
+-------------+     +-------------+     +-------------+     +-------------+
```

## Ⅴ. 원리 및 절차 흐름도

1. **자원 등록**: CPU와 메모리와 스토리지와 네트워크를 가상화 플랫폼에 연결함
2. **VM 생성**: vCPU와 vRAM과 가상 디스크와 이미지 구성을 설정함
3. **자원 스케줄링**: 하이퍼바이저가 VM별 자원 배분과 격리를 수행함
4. **운영 관리**: HA와 snapshot과 patch와 monitoring으로 수명주기를 관리함

## Ⅵ. 실무 적용 및 유의점

1. 운영 서버 통합과 클라우드 호스트는 Type 1이 맞지만 과도한 자원 과할당과 I/O 에뮬레이션은 지연을 키우므로 준가상화 드라이버와 적정 자원 비율을 함께 적용하고 CPU 대기 시간과 p99 지연시간과 HA 절체 성공률로 확인함
2. 개발 노트북과 교육 환경은 Type 2가 편하지만 호스트 OS 장애와 패치가 VM 안정성에 바로 영향을 주므로 스냅샷 관리와 호스트 자원 한도를 함께 운영하고 호스트 영향 비율과 VM 준비 시간과 스냅샷 보관 기한 위반 건수로 확인함

## Ⅶ. 결론

하이퍼바이저 유형 선택은 제품 선호가 아니라 성능 오버헤드와 보안 경계와 운영 자동화 요구를 어느 계층에서 감당할지 정하는 문제임.
