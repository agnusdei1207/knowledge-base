## 미리 알고가기

- Type 1은 물리 하드웨어 위에서 직접 동작하는 bare-metal 하이퍼바이저임
- Type 2는 호스트 OS 위에서 애플리케이션처럼 동작하는 하이퍼바이저임
- 하이퍼바이저 위치가 성능과 격리와 운영 자동화 수준을 좌우함

## Ⅰ. 개요

- **정의/개념**: Type 1과 Type 2 하이퍼바이저는 가상머신을 관리하는 계층이 물리 하드웨어에 직접 위치하는지, 호스트 OS 위에 위치하는지를 기준으로 구분하는 서버 가상화 구조임
- **배경/필요성**: 운영 서버는 낮은 오버헤드와 강한 격리와 자동화가 중요하지만 개발과 테스트 환경은 설치 편의와 호스트 연동이 더 중요하므로, 가상화 계층 위치를 구분해 선택해야 함

## Ⅱ. 특징

- Type 1은 자원 오버헤드가 적고 운영 자동화와 고가용성에 유리함
- Type 2는 설치와 사용이 간단하지만 호스트 OS 의존성과 추가 오버헤드가 큼
- Type 1은 데이터센터와 클라우드에 적합하고 Type 2는 개발과 교육 환경에 적합함
- 장애 범위와 보안 경계가 하이퍼바이저 위치에 따라 달라짐

## Ⅲ. 종류 및 비교

| 판단 기준 | Type 1 하이퍼바이저 | Type 2 하이퍼바이저 |
|:---|:---|:---|
| 위치 | 하드웨어 위에서 직접 실행 | 호스트 OS 위에서 실행 |
| 성능과 격리 | 오버헤드가 낮고 격리가 강함 | 호스트 경유로 오버헤드 증가 |
| 운영 목적 | 데이터센터, 클라우드, 운영 서버 | 개발, 테스트, 교육, 개인 사용 |
| 장애 영향 | 관리 도메인 중심 | 호스트 OS 장애가 VM에 전파됨 |

## Ⅳ. 구성요소 및 구조

| 구성요소 | 설명 |
|:---|:---|
| Virtual Machine | 게스트 OS와 애플리케이션이 실행되는 논리 서버로 자원 격리와 배치 대상이 됨 |
| Hypervisor Core | vCPU와 메모리와 I/O를 가상화하며 성능과 격리 수준을 직접 결정함 |
| Host OS | Type 2에서 장치 드라이버와 파일 시스템 기반을 제공하지만 추가 장애 경로와 오버헤드를 만듦 |
| Management Plane | 이미지 배포와 스냅샷과 migration과 정책 제어를 담당해 운영 자동화 수준을 좌우함 |

## Ⅴ. 원리 및 절차 흐름도

```text
+-------------+     +-------------+     +-------------+     +-------------+
| 자원 등록      | --> | VM 생성        | --> | 자원 스케줄링  | --> | 운영 관리      |
+-------------+     +-------------+     +-------------+     +-------------+
```

1. **자원 등록**: CPU와 메모리와 스토리지와 네트워크를 가상화 플랫폼에 연결함
2. **VM 생성**: vCPU와 vRAM과 가상 디스크와 이미지 구성을 설정함
3. **자원 스케줄링**: 하이퍼바이저가 VM별 자원 배분과 격리를 수행함
4. **운영 관리**: HA와 snapshot과 patch와 monitoring으로 수명주기를 관리함

## Ⅵ. 문제점 및 해결 방안

1. 문제: 과도한 overcommit과 I/O 에뮬레이션은 VM 지연과 성능 흔들림을 크게 만들 수 있음
   - 해결방안: 적정 overcommit과 paravirtual driver를 적용하고 CPU ready time과 p99 latency로 검증함
2. 문제: 하이퍼바이저와 관리 콘솔 보안이 약하면 다중 테넌트 환경 전체가 한 번에 노출될 수 있음
   - 해결방안: 관리망 분리와 RBAC와 패치 기준선을 운영하고 hardening compliance와 audit finding count로 검증함
3. 문제: VM sprawl과 snapshot 남용이 누적되면 자원 낭비와 운영 복잡도가 급증할 수 있음
   - 해결방안: lifecycle policy와 snapshot retention 기준을 적용하고 orphan VM count와 snapshot age violation으로 검증함

## Ⅶ. 적용 사례

- 운영 서버 통합 환경에서는 Type 1 하이퍼바이저를 사용하고 확인 지표는 CPU ready time과 HA failover success rate임
- 개발 노트북 환경에서는 Type 2 하이퍼바이저를 제한적으로 사용하고 확인 지표는 VM provision time과 host impact rate임
- 다중 테넌트 클라우드에서는 관리망 분리와 보안 기준선을 적용하고 확인 지표는 hardening compliance와 audit finding count임

## Ⅷ. 결론

하이퍼바이저 유형 선택은 제품 선호가 아니라 성능 오버헤드와 보안 경계와 운영 자동화 요구를 어떤 계층에서 감당할지에 대한 구조 결정임.
