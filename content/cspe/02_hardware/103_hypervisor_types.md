# 📖 【암기용】 개념 완전 이해

> 목적: 이 개념을 처음 보는 단어도 완벽히 이해하게 만든다. 시험 답안 양식이 아니라, 이해를 위한 친절한 설명이다.

## 한눈에
- **개요**: 물리적인 서버 한 대를 여러 대의 논리적 컴퓨터(가상 머신)로 쪼개어 주는 관리 소프트웨어가 하이퍼바이저다. 하드웨어 위에 바로 설치되느냐(Type 1), 기존 OS 위에 프로그램처럼 설치되느냐(Type 2)로 나뉜다.
- **왜 필요한가**: 과거에는 서버 한 대에 OS 하나, 앱 하나만 띄워서 썼기 때문에 자원(CPU, 메모리) 낭비가 심했다. 한 대의 고성능 물리 서버를 10~20대의 독립된 환경으로 나누어 쓰기 위해 가상화가 등장했다.
- **핵심 직관**: **Type 1**은 땅(하드웨어) 위에 직접 건물을 올리는 것(네이티브). **Type 2**는 이미 지어진 남의 건물(호스트 OS) 안에 세를 들어 가벽을 치는 것(호스티드)이다.

## 깊이 이해
- **배경·문제의식**: 개발자들은 윈도우 환경과 리눅스 환경이 동시에 필요했다. 이를 위해 기존 윈도우 위에 VMware Workstation 같은 프로그램을 깔고 가상 머신(VM)을 띄웠다(Type 2). 하지만 이 방식은 밑에 깔린 호스트 OS가 메모리를 잡아먹고 자원 분배를 방해해, 서버급의 대규모 트래픽을 견딜 수 없었다.
- **작동 원리**: **Type 1 (Bare-metal)**은 무거운 범용 OS 대신, 오직 '가상 머신 쪼개기'에만 특화된 초경량 커널(하이퍼바이저)을 하드웨어(베어메탈) 위에 직접 설치한다. 호스트 OS가 없어 불필요한 레이어가 사라지고 I/O 직결(Passthrough)이 가능해져 성능이 극대화된다.
- **비유**: (Type 1) 전문 임대사업자가 처음부터 10층짜리 고시원 전용 건물을 지어 방마다 독립된 통신선과 계량기를 달아줌. (Type 2) 일반 아파트 주인이 남는 방을 에어비앤비로 내주면서 인터넷과 화장실을 자기와 공유하게 함.
- **구체 예시**: 
  - Type 1 (서버용): VMware ESXi, MS Hyper-V, Xen, KVM (KVM은 리눅스 커널 자체가 하이퍼바이저 모듈을 품어 Type 1으로 분류됨)
  - Type 2 (PC/테스트용): VMware Workstation, Oracle VirtualBox, Parallels Desktop
- **흔한 오해·주의점**: 요즘 Type 1 하이퍼바이저는 가상 머신 내에서 무거운 특권 명령을 번역(소프트웨어 가상화)하지 않는다. VT-x 같은 하드웨어 가상화 지원 덕분에 논리적인 구획만 지어주고 연산은 100% 네이티브 하드웨어가 직접 처리한다.

## 연결 개념
- **가상 머신 모니터 (VMM)**: 하이퍼바이저와 동일한 의미로 혼용되며, VM들의 하드웨어 접근을 중재하고 격리하는 관리자 프로그램
- **반가상화 (Paravirtualization)**: 게스트 OS의 커널 소스를 수정하여 하이퍼바이저와 직접 통신(Hypercall)하게 만들어 성능을 올린 Xen의 초기 모델 기술
- **전가상화 (Full Virtualization)**: 게스트 OS 수정 없이 그대로 설치(윈도우 등)하며, 하드웨어(VT-x)의 도움을 받아 네이티브 급 성능을 내는 현대 가상화 기술

# 📝 【답안용】 시험 답안 템플릿

> 목적: 시험장에서 25분에 그대로 쓰는 답안 양식. 작성방식(추상표현 금지·수치·도식·문제유형 전환)을 엄격히 지킨다.
> 핵심: 이 시험은 정보를 많이 나열하는 시험이 아니라, 문제 신호어에서 출제자 의도를 읽고 핵심 논점을 선별해 쓰는 시험이다.

## 핵심 인사이트 (3줄 요약)

> 1. **본질**: 단일 물리 하드웨어를 다수의 논리적 가상 머신(VM)으로 분할·격리 통제하는 시스템 소프트웨어 레이어(Layer)
> 2. **가치**: 호스트 OS 개입 유무에 따라 성능(Type 1)과 호환성(Type 2)으로 나뉘며, 서버 자원 활용률을 극대화
> 3. **판단 포인트**: 기업용 클라우드 아키텍처에서는 오버헤드가 제로에 수렴하는 베어메탈(Type 1)과 반가상화/하드웨어 가상화 조합을 제시해야 한다.

## 출제 의도 및 답안 포인트

| 출제 의도 | 반드시 짚을 핵심 | 감점 회피 포인트 |
|:---|:---|:---|
| 가상화 아키텍처 계층 구조 파악 | 하이퍼바이저 설치 위치(하드웨어 위 vs OS 위) | 클라우드 서비스(IaaS) 설명으로 논점이 어긋나는 오류 |
| Type 1과 Type 2의 한계 및 장단점 | 호스트 OS 오버헤드 유무, 디바이스 드라이버 호환성 | KVM을 Type 2로 잘못 분류 (KVM은 커널 자체 편입으로 Type 1 간주) |

> 요약: 스택 구조도(하드웨어 -> 하이퍼바이저/OS -> VM)를 명확히 그리고, 엔터프라이즈 환경에서 Type 1이 강제되는 기술적 근거(I/O 지연)를 제시해야 한다.

## Ⅰ. 개요 및 필요성

- 정의: 물리적 하드웨어와 가상 머신(VM) 사이에 위치하여 자원(CPU, 메모리, I/O)을 가상화하고 분배·격리하는 VMM(Virtual Machine Monitor)
- 배경: 기존 1 Server - 1 OS 구조의 극심한 자원 유휴 상태(10~20% 활용) 및 어플리케이션 간 충돌 문제
- 필요성: 시스템 자원 프로비저닝 시간을 단축하고, 물리 서버 장애 시 VM 실시간 마이그레이션을 통한 무중단 고가용성 확보

---

## Ⅱ. Type 1 vs Type 2 아키텍처 계층 비교도

```text
[Type 1 (Bare-Metal) 구조]            |  [Type 2 (Hosted) 구조]
+------------------------------+     |  +------------------------------+
| [VM 1 (OS)]  [VM 2 (OS)]     |     |  | [VM 1 (OS)]  [VM 2 (OS)]     |
| [ 애플리케이션 ] [ 애플리케이션 ] |     |  | [ 애플리케이션 ] [ 애플리케이션 ] |
+------------------------------+     |  +------------------------------+
| Type 1 하이퍼바이저 (ESXi, Xen)|     |  | Type 2 하이퍼바이저 (VirtualBox)|
+------------------------------+     |  +------------------------------+
| 물리 하드웨어 (베어메탈)        |     |  | 호스트 운영체제 (Windows/Linux) |
+------------------------------+     |  +------------------------------+
                                     |  | 물리 하드웨어                   |
                                     |  +------------------------------+
```

| 구분 | 설치 위치 | 특이사항 |
|:---|:---|:---|
| Type 1 (네이티브) | 하드웨어 바로 위 (Bare-Metal) | 얇은 VMM 커널이 디바이스 제어권 완전 장악 |
| Type 2 (호스티드) | 일반 호스트 OS 위 (Application) | 호스트 OS가 하드웨어 통제, VMM은 스케줄링 요청만 수행 |

> 요약: 호스트 운영체제의 존재 여부가 레이턴시와 보안 공격 표면(Attack Surface)을 결정짓는 가장 핵심적인 차이다.

---

## Ⅲ. Type별 주요 특징 및 성능 갭 비교

| 비교 축 | Type 1 (Bare-Metal) | Type 2 (Hosted) | 선택 기준 |
|:---|:---|:---|:---|
| I/O 오버헤드 지연 | 낮음 (네이티브 급 성능) | 높음 (호스트 OS 인터럽트 경유 필수) | 데이터베이스/서버 구동 여부 |
| 자원 할당 통제력 | 하이퍼바이저가 하드웨어 100% 스케줄링 | 호스트 OS 프로세스와 우선순위 경쟁 발생 | 엔터프라이즈 SLA 보장 여부 |
| 하드웨어 호환성 | 전용 HCL(호환 리스트) 벤더 드라이버 필요 | 호스트 OS가 지원하는 모든 하드웨어 사용 | 다양한 PC 환경 적용성 |
| 대표 상용 솔루션 | VMware ESXi, KVM, Xen, Hyper-V | VMware Workstation, Oracle VirtualBox | 클라우드 센터 vs 개발자 PC |

> 요약: Type 1은 성능 극대화를 위해 범용 하드웨어 호환성을 일부 포기하며, Type 2는 성능을 희생하는 대신 어떤 PC에서도 쉽게 설치되는 편의성을 택했다.

---

## Ⅳ. 심화 기술: 가상화 구현 방식의 진화 (전가상화 vs 반가상화)

Type 1 환경에서도 게스트 OS의 커널 명령을 어떻게 하드웨어로 전달하느냐에 따라 3세대로 나뉜다.

| 진화 단계 | 처리 방식 | 한계 및 돌파구 |
|:---|:---|:---|
| 전가상화 (소프트웨어) | 하이퍼바이저가 게스트의 특권 명령을 인터셉트 후 실시간 바이너리 번역(BT) 수행 | 번역 부하(오버헤드) 극심 / 윈도우 무수정 구동 가능 |
| 반가상화 (Paravirtualization) | 게스트 OS 커널 소스를 수정(Hypercall)하여 하이퍼바이저와 직접 통신 (예: Xen) | 성능 우수 / 윈도우 등 오픈소스가 아닌 OS 설치 불가 |
| 전가상화 (하드웨어 지원) | CPU 명령어 셋(Intel VT-x, AMD-V)을 통해 하드웨어가 특권 명령(Root 모드) 자동 우회 | OS 무수정 구동과 네이티브 성능 동시 달성 (현재 표준) |

> 요약: 현재는 복잡한 커널 수정을 요구하는 반가상화를 버리고, 인텔 VT-x 기술을 바탕으로 한 하드웨어 지원 전가상화(KVM 등)로 천하가 통일되었다.

## Ⅴ. 극복해야 할 리스크 및 컨테이너와의 아키텍처 충돌

| 리스크 | 발생 원인 | 아키텍처 대응 방안 |
|:---|:---|:---|
| 자원 오버헤드 지속 | Type 1이라 할지라도 게스트 OS 자체를 수십 개 띄우는 중복 부하(메모리 낭비) 발생 | **컨테이너 가상화(Docker/K8s)** 전면 도입: 게스트 OS 없이 호스트 커널(Linux Namespace/Cgroups)을 공유하여 부하 제로화 |
| 보안 격리 취약 | 컨테이너는 가볍지만 하드웨어 레벨의 강력한 격리(Isolation) 부족으로 커널 패닉 시 동반 다운 | **마이크로 VM (Firecracker/Kata)**: 하드웨어 가상화(KVM)의 철벽 보안 위에 컨테이너의 빠른 기동 속도(수백 ms) 결합 |

> 요약: 하이퍼바이저의 무거운 Guest OS 구조는 결국 도커(컨테이너) 생태계로 주도권을 내주었으나, 현재는 보안을 위해 둘을 융합한 경량 하이퍼바이저로 회귀 중이다.

## Ⅵ. 실무 적용 방안 및 결론

**적용 방안 3개:**
1. [클라우드 인프라 구축] 프라이빗 클라우드(IaaS) 서버 팜 설계 시, 리눅스 커널 모듈 자체가 하이퍼바이저로 편입되어 성능 튜닝이 유리한 KVM(Kernel-based Virtual Machine) 오픈소스 스택 우선 도입
2. [개발/검증 환경] 로컬 PC에서 이기종 환경(리눅스, 안드로이드 에뮬레이터 등)을 테스팅할 때는, 호스트 OS 환경을 해치지 않고 쉽게 구축 및 삭제가 가능한 Type 2 하이퍼바이저 적용
3. [I/O 병목 제거] Type 1 환경에서도 네트워크 지연에 민감한 5G 코어망(NFV) 구축 시, 하이퍼바이저 가상 스위치를 우회(Bypass)하여 물리 NIC를 VM에 직접 맵핑하는 SR-IOV 및 PCIe 패스스루 결합 설계

**결론:**
- 기술사 판단: 클라우드 센터에서 하이퍼바이저는 무조건 하드웨어 기반 전가상화(VT-x)를 지원하는 Type 1 솔루션을 배포하여 I/O 병목과 CPU 번역 오버헤드를 원천 제거해야 한다.
- 향후 방향: 전통적인 거대 Type 1 하이퍼바이저 시장은 축소되고, AWS Firecracker처럼 컨테이너 호스팅에 최적화된 초경량(Micro) 하이퍼바이저 시대로 재편되고 있다.
