# 📖 【암기용】 개념 완전 이해

## 한눈에
- **개요**: 물리 서버 자원을 논리적으로 분할해 다수의 독립된 가상 머신(VM)을 실행하는 계층 소프트웨어(하이퍼바이저) 기술
- **왜 필요한가**: 서버 1대에 OS 1개만 돌리면 CPU 점유율이 10~20% 수준으로 낭비됨. 물리 서버 한 대에 여러 서버를 구동해 자원 활용률을 80% 이상으로 끌어올리기 위함.
- **핵심 직관**: 거대한 단독 주택(물리 서버)을 개조해서 방마다 독립된 화장실과 현관을 갖춘 아파트(가상머신)로 분할 임대하는 기술.

## 핵심 용어 정리

| 용어/표기 | 의미 | 비유·예 |
|:---|:---|:---|
| 하이퍼바이저 (VMM) | 다수의 가상머신을 생성하고 물리 자원을 조율하는 소프트웨어 계층 | 건물 관리사무소 |
| Type 1 (Bare-metal) | 하드웨어 위에 하이퍼바이저가 직접 설치되는 구조 | 건물 뼈대부터 아파트로 지음 (ESXi, KVM) |
| Type 2 (Hosted) | 호스트 OS(윈도우 등) 위에 응용프로그램처럼 설치되는 구조 | 남의 집 방 하나를 렌트함 (VMware Workstation) |

## 깊이 이해
- **배경·문제의식**: 레거시 환경에서는 서비스 격리를 위해 "1 서비스 = 1 물리 서버" 원칙을 고수함. 결과적으로 상면(공간), 전력, 냉각 비용이 폭발적으로 증가. 이를 해결하기 위해 논리적으로 시스템을 분할하는 가상화가 대두됨.
- **작동 원리**: 하이퍼바이저가 CPU, 메모리, I/O 자원을 가상화하여 각 VM에게 자신이 독립된 하드웨어를 독점하고 있는 것처럼 속임. Type 1은 얇은 하이퍼바이저 커널이 하드웨어를 직접 제어하므로 오버헤드가 적음. Type 2는 호스트 OS의 커널을 한 번 더 거치므로 무겁지만 설치가 간편함.
- **비유**: Type 1은 전문 임대업자가 처음부터 원룸 건물을 올린 것(효율 극대화). Type 2는 본인(호스트 OS)이 살고 있는 집의 남는 방을 에어비앤비로 내놓은 것(접근성 좋으나 집주인 눈치 봄).
- **구체 예시**: 개발자 PC에서 테스트할 때는 Type 2(VirtualBox)를 쓰고, 데이터센터 실전 서버에는 Type 1(VMware ESXi, Proxmox)을 설치함.
- **흔한 오해·주의점**: KVM은 커널 모듈을 통해 리눅스 자체가 하이퍼바이저가 되므로 구조적으로 Type 1(또는 Type 1.5)로 분류되며 현대 클라우드의 표준임. 컨테이너(Docker)는 OS 커널을 공유하므로 하이퍼바이저 기반 가상화와는 범주가 다름.

## 연결 개념
- 하드웨어 가상화 (VT-x, AMD-V)
- 컨테이너 가상화 (Docker, Kubernetes)
- 클라우드 컴퓨팅 (IaaS)

# 📝 【답안용】 시험 답안 템플릿

## 핵심 인사이트 (3줄 요약)

> 1. **본질**: 서버 가상화는 하이퍼바이저(VMM)를 통해 물리 자원을 추상화하고 논리적으로 분할하여 다수의 가상 머신(VM)을 실행하는 아키텍처이다.
> 2. **가치**: 자원 활용률 극대화(Consolidation), 프로비저닝 시간 단축, 라이브 마이그레이션을 통한 무중단 운영 가치를 제공한다.
> 3. **판단 포인트**: 엔터프라이즈 환경에서는 오버헤드가 적은 Type 1 하이퍼바이저가 필수적이며, 최근에는 OS 커널을 공유하는 컨테이너 방식과 결합하여 진화 중이다.

## 출제 의도 및 답안 포인트

| 출제 의도 | 반드시 짚을 핵심 | 감점 회피 포인트 |
|:---|:---|:---|
| 하이퍼바이저 아키텍처 이해 확인 | Type 1 (Bare-metal)과 Type 2 (Hosted)의 계층 구조 차이 | 컨테이너 가상화와 혼동하여 설명 |
| 엔터프라이즈 가상화 채택 기준 평가 | 성능 오버헤드, 보안 격리성 측면의 장단점 비교 | Type 2를 서버용으로 추천하는 논리 오류 |

> 요약: 서버 가상화의 핵심 계층인 하이퍼바이저의 두 가지 배치 구조를 비교하고 실무 환경에 맞는 선택 기준을 제시해야 한다.

---

## Ⅰ. 개요 및 필요성

- 개요: 물리 서버의 자원(CPU, 메모리, I/O)을 논리적으로 추상화하여 다수의 독립된 가상 머신(VM)을 실행하는 하이퍼바이저 기반 가상화 기술임
- 배경: 1서버-1어플리케이션(Silo) 구조로 인한 평균 CPU 사용률 10~20% 미만의 자원 낭비 및 전력·상면 비용 증가
- 필요성: 물리 인프라 통합(Consolidation)을 통한 TCO 절감 및 클라우드 IaaS 기반의 신속한 자원 프로비저닝 요구

---

## Ⅱ. 구조 및 구성요소

```text
[Type 1 : Bare-metal 구조]           [Type 2 : Hosted 구조]
 VM 1     VM 2     VM 3             VM 1     VM 2     VM 3
Guest OS Guest OS Guest OS         Guest OS Guest OS Guest OS
--------------------------         --------------------------
    Hypervisor (VMM)                   Hypervisor (VMM)
--------------------------         --------------------------
       Hardware                          Host OS
                                   --------------------------
                                         Hardware
```

| 구성요소 | 역할 | 특이사항 |
|:---|:---|:---|
| Hypervisor (VMM) | CPU/메모리 스케줄링 및 특권 명령 통제 | 하드웨어와 Guest OS 사이의 중재자 |
| Host OS (Type 2 한정) | 기저에서 물리 하드웨어 드라이버 관리 | 하이퍼바이저가 애플리케이션 레벨로 구동됨 |
| Guest OS | 논리적 분할 구역(VM) 내부의 운영체제 | 물리 장치를 모름(추상화된 가상 장치 인식) |

> 요약: Type 1은 하드웨어 위에 하이퍼바이저가 직결되고, Type 2는 무거운 호스트 OS를 한 번 더 거치는 구조적 차이가 있다.

---

## Ⅲ. 동작원리 및 흐름도

```text
VM 실행 요청 -> VMM 자원 매핑 -> Guest OS 명령 실행 -> 특권 명령 가로채기(Trap) -> 물리 자원 통제
```

- 1단계 [자원 프로비저닝]: 하이퍼바이저가 물리 CPU 코어와 메모리를 논리적 vCPU와 가상 메모리로 분할 할당
- 2단계 [명령어 처리]: Guest OS가 연산을 수행하며, 일반 명령은 하드웨어에서 네이티브 속도로 직접 실행
- 3단계 [트랩 앤 에뮬레이트]: Guest OS가 하드웨어 제어(특권 명령)를 시도할 때 하이퍼바이저가 가로챔(Trap)
- 4단계 [결과 반환]: 하이퍼바이저가 물리 자원을 제어한 후 결과를 Guest OS에 가상화하여 반환

> 요약: 하이퍼바이저는 각 VM이 시스템 자원을 독점하고 있다고 착각하게 만들며, 트랩(Trap) 기법을 통해 충돌을 방지한다.

---

## Ⅳ. 특징
- 물리 자원 통합: 유휴 자원을 한 곳에 모아 여러 서비스에 동적 할당함으로써 시스템 활용률을 80% 이상으로 극대화
- 이식성 및 캡슐화: VM 전체가 몇 개의 파일(예: vmdk, qcow2)로 저장되어 백업, 복제, 스냅샷 생성이 용이함
- 장애 격리(Isolation): 한 VM의 커널 패닉이나 보안 침해가 물리 서버의 다른 VM에 영향을 미치지 않음

---

## Ⅴ. 심화 비교 및 적용 판단

| 비교 축 | Type 1 (Bare-metal) | Type 2 (Hosted) | 선택 기준 |
|:---|:---|:---|:---|
| 자원 오버헤드 | 낮음 (네이티브 근접) | 높음 (Host OS 개입) | 성능 민감도 및 밀도 |
| 설치/호환성 | 전용 드라이버 필요 | Host OS 드라이버 활용 | 하드웨어 제약 유무 |
| 대표 솔루션 | VMware ESXi, KVM | VMware Workstation | 운영계(Type1) vs 개발계(Type2) |

> 요약: 엔터프라이즈 환경의 성능과 보안을 위해서는 오버헤드가 적은 Type 1 도입이 필수적이다.

- I/O 지연 리스크: 하이퍼바이저의 소프트웨어 스위칭으로 인한 네트워크 병목 → SR-IOV 및 PCI Passthrough로 하드웨어 직접 연결
- 단일 장애점(SPOF) 리스크: 하이퍼바이저 패닉 시 모든 게스트 다운 → 다중 노드 클러스터링 및 HA(High Availability) 기능 연동

- 자원 오버커밋: 물리 CPU 대비 vCPU 할당 비율(예: 4:1) — 모니터링 시스템(vCenter 등)
- 이그레스(Egress) 대역폭: 가상 스위치 밖으로 나가는 트래픽 통과량(Gbps) — 네트워크 대시보드

---

## Ⅵ. 실무 적용 및 결론

**적용 방안 3개:**
1. KVM 기반 프라이빗 클라우드 구축: 리눅스 커널을 Type 1 하이퍼바이저로 활용하는 KVM을 OpenStack과 연동하여 온프레미스 IaaS 구현
2. 라이브 마이그레이션(vMotion) 적용: 공유 스토리지(SAN)를 기반으로 무중단으로 VM을 다른 물리 서버로 이동시켜 하드웨어 유지보수 시간 확보
3. 하드웨어 가상화 기능(VT-x) 필수 활성화: 서버 BIOS 설정에서 CPU 가상화 및 IOMMU를 켜서 바이너리 변환(BT) 오버헤드 원천 제거

**결론 (2줄):**
- 기술사 판단: 서버 가상화는 Type 1 아키텍처 적용과 함께 공유 스토리지 아키텍처가 동반되어야 진정한 고가용성(HA)을 달성할 수 있다.
- 향후 방향: 무거운 Guest OS를 띄우는 하이퍼바이저의 단점을 보완하기 위해, 애플리케이션 레벨 격리인 컨테이너(Docker/K8s) 가상화로 인프라 표준이 진화하고 있다.
