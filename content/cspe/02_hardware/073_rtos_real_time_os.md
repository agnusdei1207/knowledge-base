# 📖 【암기용】 개념 완전 이해

> 목적: RTOS가 마감 시간을 "느낌"이 아니라 스케줄링 알고리즘의 수학적 계산(유틸라이제이션, WCET)으로 보장한다는 것을, 실제 숫자를 대입해 검증하는 수준까지 이해하게 만든다.

## 한눈에
- **개요**: RTOS는 실시간 시스템(Real-Time System)에 탑재되는 운영체제로, 각 태스크에 부여된 마감 시간(Deadline)을 스케줄링 알고리즘(RMS·EDF)과 최악 실행 시간(WCET) 분석을 통해 수학적으로 보장하는 결정론적 커널이다.
- **왜 필요한가**: "설계자가 감으로 우선순위를 정했더니 어쩌다 마감을 못 지켰다"는 실시간 시스템에서 용납되지 않는다. 태스크 여러 개가 CPU 하나를 나눠 쓸 때 "이 조합으로 모든 태스크의 데드라인을 항상 지킬 수 있는가"를 수식으로 미리 증명해야 한다. 이 증명 도구가 스케줄링 가능성 분석(Schedulability Analysis)이다.
- **핵심 직관**: 여러 태스크를 CPU라는 하나의 도로에 배차하는 문제라고 보면, RMS는 "자주 오는 버스(짧은 주기)에 먼저 신호를 준다"는 고정 배차표이고, EDF는 "지금 가장 급한 버스부터 보낸다"는 실시간 관제탑이다.

## 핵심 용어 정리 (내부에 등장하는 것들)

| 용어 | 의미 | 비유 |
|:---|:---|:---|
| 실시간 시스템 (상위 개념) | 결과의 정확성뿐 아니라 산출 시각의 정확성도 요구되는 시스템 | 정시 도착이 생명인 기차 |
| 주기적 태스크 (Periodic Task) | 일정한 주기(Period, T)마다 반복 실행되는 작업 | 매 10분마다 순찰을 도는 경비원 |
| 실행 시간 (Execution Time, C) | 태스크가 CPU를 실제로 점유하는 시간 | 순찰 한 바퀴에 걸리는 시간 |
| WCET (Worst-Case Execution Time) | 태스크가 실행될 수 있는 가장 긴 시간의 이론적 상한 | 가장 막힐 때 걸리는 최악의 출근 시간 |
| CPU 이용률 (Utilization, U) | ΣCᵢ/Tᵢ — 태스크들이 요구하는 CPU 시간의 합이 전체 시간에서 차지하는 비율 | 하루 24시간 중 이미 예약된 시간의 비율 |
| RMS (Rate Monotonic Scheduling) | 주기(T)가 짧은 태스크일수록 더 높은 고정 우선순위를 부여하는 정적 스케줄링 | 자주 도는 순찰조에게 항상 우선권을 줌 |
| EDF (Earliest Deadline First) | 그 순간 마감 시간이 가장 임박한 태스크에게 우선순위를 동적으로 부여하는 스케줄링 | 그때그때 가장 급한 업무부터 처리 |
| 유틸라이제이션 상한 (Liu & Layland Bound) | RMS로 모든 태스크의 스케줄링이 가능함을 보장하는 CPU 이용률의 한계치 | 안전하게 실을 수 있는 트럭의 최대 적재량 |

## 깊이 이해

### Liu & Layland 유틸라이제이션 상한을 숫자로 검증하기
- RMS의 스케줄링 가능 충분조건은 U ≤ n(2^(1/n) − 1)이다. 태스크 개수 n이 늘어날수록 이 상한은 점점 작아져, n→∞일 때 ln2 ≈ 0.693, 즉 **약 69.3%**로 수렴한다.
- n=2일 때: 2(2^(1/2) − 1) = 2 × 0.414 = 0.828 → 82.8%
- n=3일 때: 3(2^(1/3) − 1) = 3 × 0.26 = 0.78 → 78%
- **워크드 예제**: 태스크 3개 — T1(주기 10ms, 실행 2ms), T2(주기 20ms, 실행 4ms), T3(주기 50ms, 실행 5ms)이 있다고 하자. U = 2/10 + 4/20 + 5/50 = 0.2 + 0.2 + 0.1 = 0.5, 즉 50%. n=3일 때 상한이 78%이므로 0.5 ≤ 0.78을 만족해 RMS로 스케줄링 가능함이 수학적으로 보장된다.
- EDF는 더 관대해서 필요충분조건이 단순히 U ≤ 1(100%)이다. 같은 예제에서 U=50%는 당연히 EDF로도 스케줄링 가능하다. 다만 EDF는 태스크가 도착할 때마다 마감 시간을 비교해 우선순위를 다시 계산해야 하므로(동적 우선순위), RMS의 정적 우선순위 룩업보다 런타임 오버헤드가 크다.

### WCET은 왜 평균이 아니라 "최악"이어야 하는가
- 어떤 태스크가 평소 2ms 만에 끝나더라도, 캐시 미스와 인터럽트 중첩이 겹치는 드문 경우에는 2.4ms까지 늘어날 수 있다고 하자(20% 변동). 만약 데드라인을 평균값(2ms)에 맞춰 2.2ms로 설계했다면, 캐시 미스가 겹치는 드문 순간(예: 1만 번 중 3번)에 데드라인을 넘긴다.
- 하드 실시간 시스템은 이 드문 3번도 "허용 불가"로 본다. 그래서 정적 분석(코드 경로별 최악 사이클 수 계산)이나 극단적 스트레스 테스트를 통해 WCET을 구하고, 스케줄링 설계는 항상 평균이 아닌 이 WCET 값을 기준으로 한다.

### RMS와 EDF의 트레이드오프
- RMS: 우선순위가 한 번 정해지면 고정(정적)되므로 스케줄러 구현이 단순하고 오버헤드가 작다. 대신 이론적 최대 이용률이 69.3%~82.8% 수준으로 제한되어, CPU 자원의 일부는 항상 여유로 남겨둬야 한다.
- EDF: 이론적으로 이용률 100%까지 스케줄링이 가능해 CPU를 더 알뜰하게 쓸 수 있다. 대신 태스크 도착·완료마다 마감 시간 비교 연산(우선순위 큐 재정렬)이 필요해 구현이 복잡하고 런타임 오버헤드가 RMS보다 크다. 그래서 자원이 극도로 제한된 소형 MCU에는 RMS, 계산 여력이 있는 시스템에는 EDF가 흔히 선택된다.

## 연결 개념
- Hard vs Soft Real-Time — 마감 시간 위반 시 시스템에 미치는 치명성으로 실시간 시스템을 분류하는 기준. 074에서 상세히 다룬다.
- Context Switch — RMS·EDF가 아무리 정확히 우선순위를 계산해도, 태스크 전환 자체에 걸리는 오버헤드가 크면 WCET이 늘어난다.
- 우선순위 역전 (Priority Inversion) — RMS·EDF로 계산한 스케줄링 가능성 분석이 공유 자원(뮤텍스) 경합으로 무너지는 현상. 075에서 상세히 다룬다.

# 📝 【답안용】 시험 답안 템플릿

> 목적: 시험장에서 25분에 그대로 쓰는 답안 양식. 작성방식(추상표현 금지·수치·도식·문제유형 전환)을 엄격히 지킨다.
> 핵심: 결정론적(Deterministic) 동작, 선점형 커널, 우선순위 기반 스케줄링을 키워드로 답안을 구성한다.

## 핵심 인사이트 (3줄 요약)

> 1. **본질**: RTOS는 태스크의 마감 시간(Deadline) 내 처리를 보장하기 위해 결정론적(Deterministic) 스케줄링과 선점형 커널 구조를 갖춘 전용 OS이다.
> 2. **가치**: 인터럽트 지연(Latency) 및 태스크 전환 시간을 예측 가능하게 하여 시스템의 신뢰성과 실시간성을 확보한다.
> 3. **판단 포인트**: 설계 시 Hard Real-time 요구사항에 맞춘 최악 실행 시간(WCET) 분석과 우선순위 역전 방지 메커니즘 적용이 필수적이다.

## 출제 의도 및 답안 포인트

| 출제 의도 | 반드시 짚을 핵심 | 감점 회피 포인트 |
|:---|:---|:---|
| RTOS 핵심 메커니즘 이해도 확인 | 선점형 스케줄링, 결정론(Determinism), Context Switch | 단순히 "빠른 OS"라고 서술 |
| GPOS와의 차이점 분석 능력 | 처리량(Throughput) vs 응답성(Responsiveness) 비교 | 성능 지표 혼용 |
| 실무적 결함 대응 역량 | 우선순위 역전, 지연 시간(Latency) 관리 | 이론적 정의에만 치중 |

> 요약: 평균 응답 속도가 아닌 '최악의 경우에 대한 보장(Guarantee)' 관점에서 서술한다.

## Ⅰ. 개요 및 필요성

- 정의: 실시간(Real-time) 환경에서 각 태스크에 부여된 마감 시간(Deadline) 내 처리를 하드웨어적으로 보장하는 운영체제
- 배경: 제어 대상이 물리적 시간과 연동되는 산업 기기, 국방, 항공 분야의 시스템 안정성 확보 필요
- 필요성: 작업의 수행 결과만큼 '수행 시간'이 품질의 핵심 요소인 결정론적(Deterministic) 시스템 구축

---

## Ⅱ. 구조 및 구성요소

```text
Application Tasks (T1, T2, T3...) -> RTOS Kernel -> Hardware
                                        |
+---------------------------------------+---------------------------------------+
|  Scheduler (Priority-based)  /  Timer Management  /  IPC (Semaphore, Queue)   |
|  Interrupt Handler (ISR)     /  Memory Management (Static/Dynamic)            |
+-------------------------------------------------------------------------------+
```

| 구성요소 | 역할 | 특이사항 |
|:---|:---|:---|
| 마이크로 커널 | 핵심 기능(스케줄링, 통신)만 최소화 | 작은 코드 사이즈(Footprint) |
| 스케줄러 | 우선순위 기반 태스크 실행 순서 결정 | 선점(Preemption) 기능 필수 |
| 동기화 도구 | 태스크 간 자원 공유 및 통신 관리 | Semaphore, Mutex, Message Queue |
| 타이머 서비스 | 정밀한 시간 기반 이벤트 제어 | High-resolution Timer 지원 |

> 요약: 커널의 오버헤드를 최소화하고 모든 하드웨어 자원 접근을 시간 예측 가능한 범위 내에서 관리한다.

## Ⅲ. 동작원리 및 흐름도

```text
High-Priority Task -> [ Run ] -> [ Wait for Event ] -> [ Sleep ]
                                         ^
Low-Priority Task  -> [ Run ] -> [ Preempted ] --------+
                                         |
Event Trigger ---------------------------+ -> [ ISR Execution ] -> [ High-Priority Wakeup ]
```

| 단계 | 처리 내용 | 검증 기준 |
|:---:|:---|:---|
| 1 | 낮은 순위 태스크 실행 중 외부 인터럽트 발생 | 인터럽트 금지 구간 최소화 |
| 2 | ISR 실행 후 높은 순위 태스크로의 선점 결정 | 스케줄러 판단 속도 |
| 3 | 현재 태스크 상태 저장 및 새 태스크 상태 복구 | 문맥 전환(Context Switch) 시간 |
| 4 | 높은 순위 태스크 실행 및 마감 시간 준수 | 결정론적 응답 시간 보장 |

> 요약: 사건 발생 시 현재 작업을 즉시 중단하고 가장 중요한 작업을 수행하는 선점형 스케줄링이 핵심 원리다.

## Ⅳ. 특징

| 구분 | 내용 | 판단 포인트 |
|:---|:---|:---|
| 결정론 (Determinism) | 동일 입력에 대해 항상 일정한 시간 내 결과 도출 | 응답 시간의 지터(Jitter) 최소화 |
| 선점형 (Preemption) | 고순위 태스크 출현 시 실행 중인 저순위 태스크 중단 | 선점 지연 시간 보장 |
| 소형화 (Compactness) | 임베디드 자원 제약을 고려한 가벼운 커널 구조 | 수십 KB ~ 수 MB 수준 |

> 요약: 일반 OS가 "최선을 다하는(Best-effort)" 방식이라면, RTOS는 "약속을 지키는(Guaranteed)" 방식이다.

## Ⅴ. 심화 비교 및 적용 판단

| 구분 | GPOS (범용 OS) | RTOS (실시간 OS) | 선택 기준 |
|:---|:---|:---|:---|
| 스케줄링 | 시분할 (Time-sharing) | 우선순위 기반 선점 | 응답의 긴급성 |
| 최적화 목표 | 처리량 (Throughput) 극대화 | 응답 시간 (Latency) 보장 | 시간 제약 존재 여부 |
| 실패 시 결과 | 사용자 불편 (렉 발생) | 시스템 파괴 (사고 발생) | 안전성(Safety) 수준 |

> 요약: 서비스 지연이 허용되지 않는 미션 크리티컬(Mission Critical) 환경에는 반드시 RTOS를 적용한다.

| 리스크 | 원인 | 대응 방안 | 확인 지표 |
|:---|:---|:---|:---|
| 우선순위 역전 | 중순위 태스크가 저순위의 자원 점유 방해 | PIP (Inheritance), PCP (Ceiling) | 최대 차단 시간 (T_block) |
| 인터럽트 과부하 | 과도한 이벤트 발생으로 CPU 점유율 100% | 인터럽트 병합, 스케줄링 포인트 관리 | CPU 부하율 (Utilization) |
| 시간 지터 | 캐시 미스 또는 공유 자원 경합으로 응답 가변 | 캐시 고정(Locking), 버스 중재 최적화 | 지터 편차 (us 단위) |

> 요약: 시간 지연을 유발하는 모든 하드웨어/소프트웨어적 변수를 통제하여 예측 가능성을 높인다.

| 점검 항목 | 목표 기준 | 측정 방법 |
|:---|:---|:---|
| 인터럽트 레이턴시 | 최악의 경우 < 10us | 로직 분석기 측정 |
| 문맥 전환 시간 | 최악의 경우 < 5us | 커널 프로파일링 |
| 태스크 데드라인 | 적중률 100% (Hard RT) | 스케줄링 시뮬레이션 (RMS/EDF) |

> 요약: 도입 효과는 평균값이 아닌 최악 실행 시간(WCET) 기준으로 검증해야 한다.

## Ⅵ. 실무 적용 및 결론

**적용 방안 3개:**
1. 설계 최적화: Rate Monotonic Scheduling(RMS) 알고리즘을 적용하여 주기가 짧은 태스크에 높은 우선순위를 부여, 시스템 가용률 69.3% 이내 설계
2. 결함 대응: 우선순위 상속(Priority Inheritance) 프로토콜을 활성화하여 뮤텍스 사용 시 발생하는 무한 대기 리스크 차단
3. 성능 튜닝: 커널 틱(Tick) 주기를 정밀하게 설정하고, 자주 사용되는 ISR을 빠른 메모리(TCM)에 배치하여 응답 속도 향상

**결론 (2줄):**
- 기술사 판단: RTOS는 스마트 모빌리티와 같은 기능 안전(Functional Safety)이 중요한 분야의 핵심 플랫폼이며, 향후 가상화 기술을 결합하여 멀티코어 환경에서 GPOS와 RTOS를 공존시키는 구조가 대세가 될 것이다.
- 향후 방향: 오픈 아키텍처 기반의 AUTOSAR(전장)나 ROS 2(로봇)와 같은 표준 프레임워크와의 연동을 통해 이식성과 확장성을 강화하는 방향으로 발전 중이다.
