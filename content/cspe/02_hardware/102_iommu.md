# 📖 【암기용】 개념 완전 이해

> 목적: IOMMU를 처음 봐도 CPU의 MMU와 무엇이 다른지, 왜 가상화에 필수인지 이해하게 만든다. 시험 답안 양식이 아니라, 이해를 위한 친절한 설명이다.

## 한눈에
- **개요**: 디바이스가 DMA(Direct Memory Access)로 접근하는 I/O 가상 주소(IOVA)를 실제 물리 주소로 변환·통제하는 하드웨어 유닛
- **왜 필요한가**: 디바이스가 물리 메모리 주소를 직접 지정해 DMA하면 다른 VM이나 프로세스의 메모리를 침범할 수 있다. IOMMU는 디바이스별 주소 공간을 격리해 이 위험을 차단하고 디바이스 패스스루를 가능하게 한다.
- **핵심 직관**: 택배기사(디바이스)가 아파트 동·호수(물리 주소)를 직접 아는 대신, 경비실(IOMMU)이 배정한 사서함 번호(IOVA)만 보고 배달하게 하는 구조다.

## 깊이 이해
- **배경·문제의식**: CPU의 MMU는 CPU가 발행하는 가상 주소를 물리 주소로 변환하지만, 디바이스가 발행하는 DMA 요청은 MMU를 거치지 않고 버스를 통해 물리 메모리에 직접 접근했다.
- **배경·문제의식**: 가상화 환경에서 디바이스를 VM에 패스스루하면, 그 디바이스가 임의 물리 주소로 DMA를 요청할 경우 호스트나 다른 VM의 메모리를 침해할 수 있어 격리 메커니즘이 필요해졌다.
- **작동 원리**: IOMMU는 디바이스가 사용하는 I/O 가상 주소(IOVA)를 페이지 테이블 기반으로 물리 주소(HPA)로 변환하며, 변환 결과는 IOTLB(I/O TLB)에 캐시된다.
- **작동 원리**: Intel은 이를 VT-d(Virtualization Technology for Directed I/O), AMD는 AMD-Vi(구 IOMMU)라는 이름으로 제공하며, 인터럽트 리매핑(interrupt remapping) 기능도 함께 포함한다.
- **비유**: MMU는 "내가(CPU) 보는 주소"를 바꾸는 창구이고, IOMMU는 "저 기계(디바이스)가 보는 주소"를 바꾸는 별도 창구다.
- **구체 예시**: SR-IOV로 분할된 NIC의 VF(Virtual Function)를 VM에 직접 할당(VFIO passthrough)할 때, IOMMU가 해당 VF의 DMA 요청을 그 VM에 할당된 물리 메모리 영역으로만 변환되도록 격리한다.
- **흔한 오해·주의점**: IOMMU와 MMU를 같은 것으로 혼동하면 안 된다.
- **흔한 오해·주의점**: MMU는 CPU 코어의 load/store 명령어 주소를 변환하고, IOMMU는 디바이스가 버스를 통해 발행하는 DMA 주소를 변환하는 별개의 하드웨어다.

## 연결 개념
- VT-x·AMD-V — CPU 명령어 가상화, IOMMU는 이를 디바이스 영역까지 확장
- SR-IOV·VFIO — IOMMU 기반 디바이스 패스스루 구현 기술
- DMA(Direct Memory Access) — IOMMU가 통제하는 대상 접근 방식

# 📝 【답안용】 시험 답안 템플릿

> 목적: 시험장에서 25분에 그대로 쓰는 답안 양식. 작성방식(추상표현 금지·수치·도식·문제유형 전환)을 엄격히 지킨다.
> 핵심: IOMMU 답안은 MMU와의 차이, IOVA 변환 구조, 디바이스 격리·패스스루 효과, 인터럽트 리매핑을 함께 제시한다.

## 핵심 인사이트 (3줄 요약)

> 1. **본질**: IOMMU는 디바이스가 발행하는 DMA 요청의 I/O 가상 주소(IOVA)를 물리 주소로 변환·통제하는 하드웨어 유닛이다.
> 2. **가치**: 디바이스별 주소 공간을 격리해 rogue DMA로 인한 메모리 침해를 차단하고, VM에 디바이스를 직접 할당(패스스루)할 수 있게 한다.
> 3. **판단 포인트**: CPU 코어용 MMU와 디바이스용 IOMMU는 별개 하드웨어이므로 시험 답안에서 절대 동일시하면 안 된다.

## 출제 의도 및 답안 포인트

| 출제 의도 | 반드시 짚을 핵심 | 감점 회피 포인트 |
|:---|:---|:---|
| MMU와 IOMMU 구분 역량 확인 | 변환 대상 주체(CPU vs 디바이스), IOVA 개념 | IOMMU를 MMU의 하위 개념으로 서술 |
| 가상화 보안·격리 이해 확인 | rogue DMA 차단, VM별 주소 공간 격리 | 격리 메커니즘 없이 "성능 향상"만 서술 |
| 디바이스 패스스루 구조 이해 확인 | SR-IOV·VFIO, 인터럽트 리매핑 | 패스스루와 에뮬레이션 디바이스를 혼동 |

> 요약: 이 문제는 IOMMU를 MMU와 구분하고, DMA 격리·패스스루 구조를 정확히 설명하는지를 본다.

## Ⅰ. 개요 및 필요성

- 개요: 디바이스의 DMA 요청 주소(IOVA)를 물리 주소로 변환·격리하는 하드웨어 유닛(Intel VT-d, AMD-Vi)
- 배경: 디바이스 DMA는 전통적으로 MMU를 거치지 않고 물리 주소에 직접 접근해 격리가 불가능했음
- 필요성: 가상화 환경에서 디바이스 패스스루와 rogue DMA 차단을 동시에 만족하려면 디바이스 전용 주소 변환·통제 계층이 필요

---

## Ⅱ. 구조 및 구성요소

```text
Device (NIC/GPU/SSD) -> DMA 요청(IOVA)
  -> IOMMU: IOVA -> HPA 변환(IOTLB 캐시)
  -> Domain 격리 확인(VM별 주소 공간)
  -> Interrupt Remapping -> 목적 vCPU로 인터럽트 전달
  -> Host/Guest Physical Memory 접근
```

| 구성요소 | 역할 | 특이사항 |
|:---|:---|:---|
| I/O Page Table | IOVA -> HPA 변환 테이블 | VM(도메인)별 독립 테이블 |
| IOTLB | 변환 결과 캐시 | 변환 지연 감소 |
| Interrupt Remapping Table | 디바이스 인터럽트를 목적 vCPU로 매핑 | MSI/MSI-X 가상화 지원 |
| Domain | 디바이스 그룹별 격리 단위 | 도메인 간 메모리 접근 차단 |

> 요약: IOMMU는 도메인 단위로 IOVA-HPA 변환 테이블과 인터럽트 리매핑을 관리해 디바이스별 접근을 격리한다.

---

## Ⅲ. 동작원리 및 흐름도

```text
디바이스 DMA 요청 발행(IOVA) -> IOTLB 조회
  -> Miss 시 I/O Page Table Walk -> HPA 확정
  -> Domain 경계 확인(허용 여부 판정)
  -> 물리 메모리 접근 허용/차단
  -> 인터럽트 발생 시 Remapping Table 참조 -> 목적 vCPU 전달
```

| 단계 | 처리 내용 | 검증 기준 |
|:---:|:---|:---|
| 1 | 디바이스가 IOVA로 DMA 요청 발행 | 요청 발생 디바이스 식별(BDF) |
| 2 | IOTLB 조회, miss 시 페이지 테이블 워크 | IOTLB hit rate |
| 3 | 도메인 경계 내 접근인지 판정 | 도메인 위반 이벤트 로그 |
| 4 | 허용 시 물리 메모리 접근, 인터럽트 리매핑 | interrupt remap 정확성 |

> 요약: IOMMU는 IOTLB로 변환을 가속하고 도메인 경계 판정으로 디바이스 간 메모리 침해를 차단한다.

---

## Ⅳ. 특징

| 구분 | MMU | IOMMU |
|:---|:---|:---|
| 변환 주체 | CPU 코어의 load/store 주소 | 디바이스의 DMA 주소(IOVA) |
| 목적 | 프로세스 가상 메모리 관리 | 디바이스 접근 격리·패스스루 |
| 대표 표준 | x86 페이징, ARM MMU | Intel VT-d, AMD-Vi(AMD IOMMU) |
| 관련 기능 | TLB | IOTLB, Interrupt Remapping |

> 요약: MMU와 IOMMU는 변환 주체가 다른 별개 하드웨어이며, 시험에서 동일시하면 감점 대상이다.

## Ⅴ. 심화 비교 및 적용 판단

| 비교 축 | IOMMU 미사용(디바이스 직접 DMA) | IOMMU 사용 | 선택 기준 |
|:---|:---|:---|:---|
| 구조 | 물리 주소 직접 접근 | IOVA-HPA 변환·도메인 격리 | 멀티테넌트·VM 패스스루 시 IOMMU 필수 |
| 비용/성능 | 변환 오버헤드 없음 | IOTLB miss 시 지연 발생 | IOTLB hit rate로 오버헤드 판단 |
| 운영/위험 | rogue DMA 차단 불가 | 도메인 격리로 침해 차단 | 보안 요구 수준에 따라 결정 |

> 요약: 디바이스 패스스루와 멀티테넌트 격리가 필요하면 IOMMU 활성화가 필수이며, IOTLB 적중률로 오버헤드를 관리한다.

| 리스크 | 원인 | 대응 방안 | 확인 지표 |
|:---|:---|:---|:---|
| IOTLB miss 급증 | 대용량 DMA 버퍼 빈번 변경 | huge page 매핑, IOVA 재사용 최소화 | IOTLB miss rate |
| 인터럽트 오배송 | Remapping Table 설정 오류 | MSI-X 벡터·vCPU 매핑 검증 | 인터럽트 지연·오배송 로그 |
| 격리 우회 취약점 | ACS(Access Control Services) 미지원 브리지 | ACS 지원 디바이스·슬롯 구성 확인 | PCIe topology 점검 결과 |

> 요약: IOMMU 운영 리스크는 변환 성능, 인터럽트 정확성, ACS 기반 격리 우회 여부로 통제한다.

| 점검 항목 | 목표 기준 | 측정 방법 |
|:---|:---|:---|
| 변환 성능 | IOTLB hit rate 목표치 이상 유지 | perf, vendor 진단 툴 |
| 격리 정확성 | 도메인 간 접근 위반 이벤트 0건 | IOMMU fault 로그 |
| 패스스루 안정성 | VFIO 디바이스 hot-plug 정상 동작 | 가상화 플랫폼 테스트 로그 |

> 요약: 도입 성공 여부는 IOTLB 적중률, 도메인 위반 이벤트, 패스스루 안정성으로 판단한다.

---

## Ⅵ. 실무 적용 및 결론

**적용 방안 3개:**
1. 멀티테넌트 VM 환경은 IOMMU를 활성화하고 도메인별 위반 이벤트 0건을 배포 기준으로 설정함
2. GPU·NIC 패스스루가 필요한 워크로드는 SR-IOV VF + VFIO + IOMMU 조합을 적용함
3. 대용량 DMA 워크로드는 huge page 매핑으로 IOTLB miss rate를 낮춤

**결론 (2줄):**
- 기술사 판단: 디바이스 격리·패스스루가 필요하면 IOMMU(VT-d·AMD-Vi) 활성화를 기본값으로 함
- 향후 방향: PCIe ACS·인터럽트 리매핑 표준화가 확대되며 클라우드 멀티테넌시 보안 요구와 함께 IOMMU 활용이 늘어남
