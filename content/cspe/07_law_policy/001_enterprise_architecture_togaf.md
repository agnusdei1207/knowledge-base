# 📖 【암기용】 개념 완전 이해

> 목적: EA(Enterprise Architecture)를 처음 봐도 왜 조직 전체의 청사진이 필요한지, ISP·ISMP와 무엇이 다른지 감을 잡게 만든다. 시험 답안 양식이 아니라, 이해를 위한 친절한 설명이다.

## 한눈에
- **개요**: 조직의 비즈니스·데이터·애플리케이션·기술 구조를 하나의 참조 모델로 정렬하는 장기 구조적 청사진
- **왜 필요한가**: 부서별로 시스템을 따로 구축하면 중복 투자, 데이터 불일치, 상호운용성 저하가 누적된다. EA는 전사 관점에서 표준 구조를 정의해 개별 사업이 그 틀 안에서 설계되도록 통제한다.
- **핵심 직관**: 도시 전체의 도로·상하수도·전력망을 미리 설계하는 도시계획과 같다. 개별 건물(개별 정보화 사업)은 이 도시계획 안에서 지어진다.

## 깊이 이해
- **배경·문제의식**: 대규모 조직은 수십~수백 개의 정보시스템을 부서별로 발주해왔다.
- 표준 없이 개별 발주가 반복되면 동일 기능 중복 개발과 데이터 정의 불일치가 발생한다.
- EA는 이 문제를 조직 전체 수준의 참조 아키텍처로 통제하기 위해 도입됐다.
- **작동 원리**: TOGAF ADM(Architecture Development Method)은 비전 수립부터 비즈니스·데이터·애플리케이션·기술 아키텍처 정의, 기회·솔루션 도출, 이행 계획, 거버넌스까지 반복 주기로 진행한다.
- 각 단계 산출물은 현행(As-Is) 구조와 목표(To-Be) 구조의 gap을 명시한다.
- 한국 공공부문은 범정부 EA(행정기관 정보화 참조모델)로 이 개념을 제도화해 기관별 EA를 표준 메타모델에 맞춰 등록·관리한다.
- **비유**: 아파트 단지 전체의 배관·전기 설계도가 EA라면, 개별 세대 인테리어는 개별 정보화 사업이다.
- 세대 인테리어가 아무리 달라도 공용 배관 규격은 지켜야 한다.
- **구체 예시**: A기관이 EA에서 "고객정보는 단일 마스터 DB만 정본으로 인정한다"는 데이터 아키텍처 원칙을 정했다면, 이후 신규 사업은 별도의 고객 DB를 새로 만들 수 없고 마스터 DB를 참조해야 한다.
- **흔한 오해·주의점**: EA는 단일 시스템의 설계 문서가 아니다.
- EA는 여러 사업에 걸쳐 장기간(보통 수년 단위) 유지되는 구조적 원칙과 참조모델이며, 특정 사업의 상세 설계는 EA의 하위 산출물이다.

## 연결 개념
- ISP·ISMP — EA라는 전사 틀 안에서 개별 사업 단위로 구체화되는 계획 문서
- TOGAF ADM — EA를 수립·갱신하는 반복적 방법론
- IT 거버넌스 — EA 원칙 준수 여부를 통제하는 상위 체계

# 📝 【답안용】 시험 답안 템플릿

> 목적: 시험장에서 25분에 그대로 쓰는 답안 양식. 작성방식(추상표현 금지·수치·도식·문제유형 전환)을 엄격히 지킨다.
> 핵심: EA 답안은 계층 구조, TOGAF ADM 단계, 범정부 EA 참조모델, ISP·ISMP와의 위계 관계를 함께 제시한다.

## 핵심 인사이트 (3줄 요약)

> 1. **본질**: EA는 비즈니스·데이터·애플리케이션·기술 아키텍처를 하나의 참조모델로 정렬하는 조직 전체의 장기 구조적 청사진이다.
> 2. **가치**: 개별 정보화 사업의 중복 투자와 데이터 불일치를 사전에 통제해 상호운용성을 확보한다.
> 3. **판단 포인트**: EA는 조직 전체·장기 원칙, ISP·ISMP는 그 원칙 안에서 개별 사업을 구체화하는 단기 계획이라는 위계로 구분한다.

## 출제 의도 및 답안 포인트

| 출제 의도 | 반드시 짚을 핵심 | 감점 회피 포인트 |
|:---|:---|:---|
| EA 계층 구조 이해 확인 | 비즈니스·데이터·애플리케이션·기술 아키텍처 4계층 | 4계층을 나열 없이 "구조"로만 뭉뚱그림 |
| TOGAF ADM 절차 이해 확인 | Preliminary·비전·B/D/A/T 단계·이행계획·거버넌스 | ADM을 단일 단계처럼 서술 |
| ISP·ISMP와의 위계 구분 확인 | EA는 전사 장기 원칙, ISP·ISMP는 개별 사업 단기 계획 | EA와 ISP·ISMP를 동일 개념으로 혼동 |

> 요약: 이 문제는 EA의 계층 구조 나열보다 전사 장기 원칙으로서 개별 사업 계획을 어떻게 통제하는지를 보여야 한다.

## Ⅰ. 개요 및 필요성

- 개요: 조직의 구조를 계층별 참조모델로 정렬하는 장기 아키텍처 체계
- 배경: 부서별 개별 발주가 반복되며 중복 투자와 데이터 불일치가 누적되어 전사 통제 체계 필요성이 대두됨
- 필요성: 상호운용성과 재사용성을 확보하려면 비즈니스·데이터·애플리케이션·기술 계층의 표준 원칙 수립이 필요함

---

## Ⅱ. 구조 및 구성요소

```text
전사 전략/비전 -> Business Architecture -> Data Architecture
  -> Application Architecture -> Technology Architecture
  -> 이행계획(Migration Plan) -> 거버넌스(Governance)
```

| 구성요소 | 역할 | 특이사항 |
|:---|:---|:---|
| Business Architecture | 업무 프로세스·조직 구조 정의 | 전략-업무 정렬 |
| Data Architecture | 데이터 표준·마스터 데이터 정의 | 단일 정본(Single Source of Truth) 원칙 |
| Application Architecture | 애플리케이션 포트폴리오·연계 구조 정의 | 중복 시스템 통폐합 대상 식별 |
| Technology Architecture | 인프라·플랫폼 표준 정의 | 클라우드·네트워크 표준 |
| 이행계획 | As-Is와 To-Be 간 gap 해소 로드맵 | 우선순위·단계별 일정 |

> 요약: EA는 전략에서 인프라까지 4계층 아키텍처를 이행계획과 거버넌스로 연결한 구조다.

---

## Ⅲ. 동작원리 및 흐름도

```text
Preliminary(원칙 수립) -> Architecture Vision
  -> Business/Data/Application/Technology Architecture
  -> Opportunities & Solutions -> Migration Planning
  -> Implementation Governance -> Architecture Change Management
```

| 단계 | 처리 내용 | 검증 기준 |
|:---:|:---|:---|
| 1 | 원칙·범위·이해관계자 정의 | 거버넌스 승인 여부 |
| 2 | 4계층 아키텍처 As-Is/To-Be 분석 | gap 목록 완성도 |
| 3 | 이행 우선순위와 로드맵 수립 | 단계별 일정, 자원 배분 |
| 4 | 구현 통제와 변경관리 반복 | 원칙 준수율, 예외 승인 건수 |

> 요약: TOGAF ADM은 원칙 수립부터 4계층 분석, 이행계획, 거버넌스까지 반복 주기로 EA를 갱신한다.

---

## Ⅳ. 특징

| 구분 | 내용 | 판단 포인트 |
|:---|:---|:---|
| 장점 | 전사 표준화로 중복 투자와 데이터 불일치 감소 | 시스템 통폐합 건수, 표준 준수율 |
| 한계 | 수립·갱신에 장기간과 조직적 합의가 필요 | 조직 저항, 이해관계자 조율 비용 |
| 비교 포인트 | ISP·ISMP는 EA 원칙 하위의 개별 사업 계획 | 계획 범위와 수립 주기 차이 |

> 요약: EA는 전사 표준화 효과가 크지만 수립·합의 비용이 높아 개별 사업 계획과 역할을 분담한다.

## Ⅴ. 심화 비교 및 적용 판단

| 구분 | 기존(개별 발주) | EA 적용 | 선택 기준 |
|:---|:---|:---|:---|
| 구조 | 부서별 독립 설계 | 전사 참조모델 기반 설계 | 기관 수 3개 이상, 시스템 10개 이상 시 EA 우선 |
| 비용/성능 | 중복 투자 반복 | 초기 수립 비용 크나 장기 중복 제거 | 3~5년 이상 운영 기준 총소유비용(TCO) 비교 |
| 운영/위험 | 데이터 불일치 누적 | 원칙 위반 시 예외 승인 절차 필요 | 예외 승인 건수와 사유 추적 |

> 요약: 다부서·다시스템 환경에서 장기 TCO 절감이 목표라면 EA를 우선 적용한다.

| 리스크 | 원인 | 대응 방안 | 확인 지표 |
|:---|:---|:---|:---|
| 원칙 형해화 | 개별 사업이 EA 원칙을 예외 처리로 우회 | 예외 승인 절차와 상위 거버넌스 심의 의무화 | 예외 승인 건수, 심의 통과율 |
| 수립 지연 | 이해관계자 합의 실패 | 단계적 범위 축소, 우선순위 도메인부터 착수 | 단계별 완료 일정 준수율 |
| As-Is 문서 노후화 | 조직 변경에도 EA 미갱신 | 정기 갱신 주기(연 1회 이상) 지정 | 갱신 이력, 최종 수정일 |

> 요약: EA 운영은 예외 승인 통제, 단계적 수립, 정기 갱신 지표로 관리한다.

| 점검 항목 | 목표 기준 | 측정 방법 |
|:---|:---|:---|
| 표준 준수율 | 신규 사업의 EA 원칙 준수율 90% 이상 | 사업 심의 체크리스트 |
| 중복 제거 | 유사 기능 시스템 통폐합 건수 | 시스템 인벤토리 비교 |
| 갱신 주기 | 연 1회 이상 As-Is/To-Be 갱신 | EA 저장소 변경 이력 |

> 요약: 도입 후 성공 여부는 표준 준수율, 시스템 통폐합 건수, 갱신 주기 준수로 판단한다.

## Ⅵ. 실무 적용 및 결론

**적용 방안 3개 (필수 — 단계별 또는 항목별):**
1. 단기: 데이터 아키텍처부터 단일 정본 원칙을 수립하고 마스터 데이터 항목을 식별함
2. 중기: 애플리케이션 포트폴리오를 분석해 중복 시스템 통폐합 로드맵을 이행계획에 반영함
3. 장기: 거버넌스 절차로 신규 사업의 EA 원칙 준수를 심의하고 예외 승인 건수를 연 단위로 관리함

**결론 (2줄):**
- 기술사 판단: 다부서·다시스템 조직은 EA로 전사 원칙을 먼저 세우고 개별 사업은 ISP·ISMP로 구체화함
- 향후 방향: 범정부 EA는 클라우드 네이티브 표준, API 기반 상호연계, AI 서비스 아키텍처를 참조모델에 반영하는 방향으로 확장돼야 함

### 🔀 문제 유형별 목차 전환 (이 키워드 출제 시)

| 유형 | 문제 신호어 | Ⅲ 강조 | Ⅳ 강조 |
|:---|:---|:---|:---|
| 포괄형 | "EA를 설명하시오" | 4계층 구조와 ADM 절차 | 계층별 역할과 이행계획 |
| 요구사항 명시형 | "EA 구축 방안을 제시하시오" | As-Is/To-Be gap 분석, 거버넌스 | 통폐합 우선순위, 예외 통제 |

> 요약: 설명형은 계층 구조와 ADM 절차, 방안형은 gap 분석과 거버넌스 통제 중심으로 답안 축을 바꾼다.
