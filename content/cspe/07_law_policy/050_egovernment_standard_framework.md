# 📖 【암기용】 개념 완전 이해

> 목적: 전자정부 표준프레임워크를 처음 봐도 왜 정부가 개발 프레임워크를 표준화했는지 이해하게 만든다. 시험 답안 양식이 아니라, 이해를 위한 친절한 설명이다.

## 한눈에
- **개요**: 행정안전부가 공공 정보시스템 개발에 공통 적용하도록 표준화한 오픈소스 기반 Java 웹 애플리케이션 프레임워크
- **왜 필요한가**: 공공 SW 사업마다 특정 업체의 상용 프레임워크를 써서 유지보수·이관 시 특정 업체 종속(vendor lock-in)이 발생하고 재사용성이 낮았음
- **핵심 직관**: 전국 관공서가 서로 다른 규격의 문서 양식을 쓰면 행정 처리가 비효율적이듯, 공공 SW도 공통 표준 설계도(프레임워크)를 쓰면 유지보수와 재사용이 쉬워진다

## 깊이 이해
- **배경·문제의식**: 2007년경 공공기관마다 상이한 프레임워크로 개발해 담당 업체 교체 시 재개발 비용이 크고, 개발자 학습 곡선도 반복적으로 발생함
- **작동 원리**: Spring Framework를 기반으로 공통 컴포넌트(게시판, 결재, 파일업로드 등)를 표준화하고, 실행환경·개발환경·관리환경 3개 축으로 구성됨
- **작동 원리**: 실행환경은 웹·모바일·배치 등 런타임 환경을, 개발환경은 이클립스 기반 통합개발도구(IDE)를, 관리환경은 형상관리·배포·모니터링 도구를 제공함
- **작동 원리**: 오픈소스 기반으로 무상 배포되어 특정 상용 벤더 종속 없이 여러 SI 업체가 동일 표준으로 개발·유지보수 가능함
- **비유**: 전국 관공서가 같은 양식의 공문서 서식을 쓰면 담당자가 바뀌어도 업무가 끊기지 않듯, 표준프레임워크를 쓰면 개발업체가 바뀌어도 유지보수가 이어진다
- **구체 예시**: 4.x 버전 이후 Spring Boot 기반 경량화, 컨테이너(Docker)·쿠버네티스 배포를 지원해 클라우드 네이티브 공공시스템 전환을 지원함
- **흔한 오해·주의점**: 전자정부 표준프레임워크는 특정 상용 제품이 아니라 오픈소스 기반 공통 표준이므로, 특정 업체의 독자 프레임워크와 혼동하면 안 됨

## 연결 개념
- 오픈소스 라이선스 — 표준프레임워크가 오픈소스로 무상 배포되는 근거
- ISP·ISMP·EA — 공공 정보화 전략·아키텍처 수립과 연계되는 상위 개념
- 디지털 플랫폼 정부 — 표준프레임워크가 적용되는 공공 서비스 전달 체계

# 📝 【답안용】 시험 답안 템플릿

> 목적: 시험장에서 25분에 그대로 쓰는 답안 양식. 작성방식(추상표현 금지·수치·도식·문제유형 전환)을 엄격히 지킨다.
> 핵심: 전자정부 표준프레임워크 답안은 도입 배경(벤더 종속 해소), 3대 환경 구조, 오픈소스 기반 특성, 클라우드 네이티브 전환을 함께 제시한다.

## 핵심 인사이트 (3줄 요약)

> 1. **본질**: 전자정부 표준프레임워크는 행정안전부가 표준화한 오픈소스 기반 공공 SW 개발 공통 프레임워크이다.
> 2. **가치**: 특정 업체 종속을 해소하고 실행·개발·관리 3대 환경으로 재사용성과 유지보수성을 확보한다.
> 3. **판단 포인트**: 오픈소스 기반 무상 배포와 Spring 기반 표준화가 벤더 종속 해소의 핵심 근거라는 점이 답안의 축이다.

## 출제 의도 및 답안 포인트

| 출제 의도 | 반드시 짚을 핵심 | 감점 회피 포인트 |
|:---|:---|:---|
| 도입 배경 이해 확인 | 벤더 종속(lock-in) 해소, 재사용성 확보 | 단순히 "표준 프레임워크가 있다"고만 서술 |
| 구조 이해 확인 | 실행환경/개발환경/관리환경 3대 축 | 세 환경을 구분 없이 나열 |
| 최신 동향 이해 확인 | Spring Boot 기반 경량화, 클라우드 네이티브 전환 | 구버전 구조만 서술하고 최신 동향 누락 |

> 요약: 이 문제는 프레임워크 기능 나열이 아니라 벤더 종속 해소라는 도입 배경과 최신 클라우드 네이티브 전환 흐름을 함께 짚어야 한다.

## Ⅰ. 개요 및 필요성

- 개요: 행정안전부가 표준화한 오픈소스 기반 공공 SW 개발 공통 프레임워크
- 배경: 공공기관별 상이한 프레임워크 사용으로 벤더 종속과 재개발 비용 문제가 발생함
- 필요성: 개발업체가 바뀌어도 유지보수가 이어지도록 공통 표준 설계와 오픈소스 배포가 필요함

---

## Ⅱ. 구조 및 구성요소

```text
공공 SW 개발 요구 -> 표준프레임워크 적용
  -> 실행환경(웹/모바일/배치)
  -> 개발환경(이클립스 기반 IDE)
  -> 관리환경(형상관리/배포/모니터링)
  -> 공통 컴포넌트(게시판/결재/파일업로드)
```

| 구성요소 | 역할 | 특이사항 |
|:---|:---|:---|
| 실행환경 | 웹·모바일·배치 등 런타임 표준 제공 | Spring 기반 계층 구조 |
| 개발환경 | 통합개발도구·코드 생성기 제공 | 이클립스 기반, 표준 템플릿 |
| 관리환경 | 형상관리·배포·모니터링 도구 제공 | 운영 표준화, 배포 자동화 |
| 공통 컴포넌트 | 게시판·결재·파일업로드 등 재사용 모듈 | 중복 개발 방지 |

> 요약: 실행·개발·관리 3대 환경과 공통 컴포넌트가 결합해 공공 SW 개발의 표준 기반을 제공한다.

---

## Ⅲ. 동작원리 및 흐름도

```text
공공 SW 사업 착수 -> 표준프레임워크 다운로드(오픈소스)
  -> 개발환경에서 표준 템플릿 개발
  -> 실행환경에 배포·운영
  -> 관리환경으로 형상·배포 관리 -> 유지보수 이관
```

| 단계 | 처리 내용 | 검증 기준 |
|:---:|:---|:---|
| 1 | 오픈소스 표준프레임워크 도입 결정 | 사업 지침·고시 준수 |
| 2 | 개발환경에서 공통 컴포넌트 기반 개발 | 표준 준수율, 재사용 컴포넌트 비율 |
| 3 | 실행환경에 배포 후 서비스 운영 | 배포 자동화 여부, 가용성 |
| 4 | 유지보수 업체 이관 시 표준 준수로 인수인계 | 이관 소요 기간, 문서화 수준 |

> 요약: 오픈소스 표준을 도입해 표준 템플릿으로 개발·배포한 뒤 업체가 바뀌어도 표준 준수로 원활히 이관한다.

## Ⅳ. 특징

| 구분 | 내용 | 판단 포인트 |
|:---|:---|:---|
| 장점 | 오픈소스 기반으로 라이선스 비용 없이 벤더 종속을 해소함 | 여러 SI 업체가 동일 표준으로 유지보수 가능 |
| 한계 | 공공 특화 요구로 최신 상용 프레임워크 대비 생태계 대응이 늦을 수 있음 | 최신 버전 도입 속도 관리 필요 |
| 비교 포인트 | 4.x 버전부터 Spring Boot 기반 경량화, 클라우드 네이티브 전환 | 레거시 3.x 시스템은 전환 로드맵 필요 |

> 요약: 표준프레임워크는 벤더 종속 해소라는 강점이 있지만 최신 기술 반영 속도를 관리해야 한다.

## Ⅴ. 심화 비교 및 적용 판단

| 구분 | 상용 프레임워크 개별 도입 | 전자정부 표준프레임워크(레거시 3.x) | 전자정부 표준프레임워크(4.x, Spring Boot) | 선택 기준 |
|:---|:---|:---|:---|:---|
| 구조 | 업체별 상이한 설계, 낮은 재사용성 | 표준 실행/개발/관리 환경 | 경량 컨테이너 기반 마이크로서비스 지원 | 신규 구축은 4.x 이상 우선 채택 |
| 비용/성능 | 라이선스 비용, 업체 종속 비용 | 오픈소스 무상, 유지보수 표준화 | 클라우드 자원 최적화, 오토스케일링 | 클라우드 전환 사업은 4.x 필수 검토 |
| 운영/위험 | 업체 교체 시 재개발 위험 큼 | 표준 준수로 이관 위험 낮음 | 컨테이너 오케스트레이션 운영 역량 필요 | 운영 인력의 쿠버네티스 역량 확보 필요 |

> 요약: 신규 공공 SW 사업은 Spring Boot 기반 4.x 표준프레임워크로 클라우드 네이티브 전환을 우선 고려한다.

| 리스크 | 원인 | 대응 방안 | 확인 지표 |
|:---|:---|:---|:---|
| 레거시 종속 | 3.x 구버전 유지로 신기술 도입 지연 | 단계적 4.x 전환 로드맵 수립 | 버전별 시스템 비율 |
| 표준 미준수 | 사업자가 표준 가이드 미준수 개발 | 표준 준수 점검, 감리 체계 적용 | 감리 지적 건수 |
| 운영 역량 부족 | 컨테이너·클라우드 운영 인력 미비 | 교육·인증 프로그램 운영 | 운영 인력 인증 이수율 |

> 요약: 표준프레임워크 리스크는 버전 전환 로드맵, 표준 준수 감리, 운영 인력 역량 강화로 통제한다.

| 점검 항목 | 목표 기준 | 측정 방법 |
|:---|:---|:---|
| 표준 준수 | 공통 컴포넌트 재사용률 목표치 | 소스코드 감리 결과 |
| 버전 전환 | 4.x 이상 전환 시스템 비율 목표치 | 시스템 인벤토리 점검 |
| 운영 안정성 | 배포 자동화율, 장애 대응 시간 목표 | 배포 로그, 장애 이력 |

> 요약: 도입 후 성공 여부는 표준 준수율, 4.x 전환 비율, 배포·장애 대응 지표로 판단한다.

## Ⅵ. 실무 적용 및 결론

**적용 방안 3개 (필수 — 단계별 또는 항목별):**
1. 단기: 신규 공공 SW 사업에 전자정부 표준프레임워크 4.x(Spring Boot 기반) 도입을 의무화함
2. 중기: 레거시 3.x 시스템을 단계적으로 4.x로 전환하며 표준 준수 감리 체계를 강화함
3. 장기: 컨테이너·쿠버네티스 기반 클라우드 네이티브 운영 체계로 확장하고 MSA 전환을 지원함
