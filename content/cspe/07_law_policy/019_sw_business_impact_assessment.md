## 미리 알고가기

- SW사업 영향 평가는 공공기관이 정보화 사업을 추진할 때 민간 SW시장 침해 가능성을 사전에 검토하는 절차임
- 민간시장 침해는 공공기관이 세금으로 민간 서비스와 직접 경쟁하는 구조를 만드는 상황을 뜻함
- 디지털 플랫폼 정부는 공공이 데이터와 기반을 제공하고 민간이 서비스를 확장하는 방향을 강조함
- 자체평가와 협의 절차는 입찰 이전 단계에서 수행해야 실효성이 생김

## Ⅰ. 개요

- **정의/개념**: 소프트웨어 사업 영향 평가는 국가기관 등이 소프트웨어나 정보서비스를 직접 구축하거나 제공하려 할 때 그 사업이 민간 상용 SW시장과 서비스를 침해하는지 사전에 판단하는 제도임
- **배경/필요성**: 공공기관이 민간에 이미 존재하는 서비스를 세금으로 다시 만들면 시장 위축과 중복 투자가 발생하므로, 공공 직접 구축 필요성과 민간 대체 가능성을 먼저 검토해야 함

## Ⅱ. 특징

- 사업 착수 전에 민간 대체 가능성과 공공성 여부를 검토하므로 불필요한 공공 직접 구축을 줄이는 기능을 가짐
- 공공이 데이터를 열고 민간이 서비스를 만드는 구조를 유도해 디지털 플랫폼 정부 방향과 맞물림
- 평가 시점이 늦으면 예산과 사업 방향이 이미 굳어져 기능 축소나 민간 활용 전환이 어려워질 수 있음
- 자체평가, 의견수렴, 협의 결과 반영까지 문서로 남겨야 제도 운영의 객관성이 확보됨

## Ⅲ. 종류 및 비교

| 판단 기준 | 공공 직접 구축 | 민간 활용·협업 중심 |
|:---|:---|:---|
| 서비스 제공 방식 | 공공기관이 직접 애플리케이션과 서비스를 구축해 제공함 | 공공은 데이터, API, 기준 정보 제공에 집중하고 민간이 서비스를 구현함 |
| 민간시장 영향 | 기존 민간 서비스와 기능이 겹치면 시장 침해 우려가 큼 | 민간 서비스 확장을 촉진해 시장 침해 가능성이 상대적으로 낮음 |
| 공공성 확보 방식 | 공공기관이 기능을 직접 통제함 | 공공은 필수 데이터와 표준을 관리하고 민간 참여로 서비스 다양성을 확보함 |
| 적합한 상황 | 국가 고유 업무나 민간 대체가 사실상 어려운 경우에 적합함 | 생활 편의 서비스나 부가서비스처럼 민간 사업자가 구현하는 영역에 적합함 |

> 요약: 영향 평가는 공공이 직접 만들 필요가 있는지와 민간이 더 잘할 수 있는지를 구분하는 제도임

## Ⅳ. 구성요소 및 구조

| 구성요소 | 설명 |
|:---|:---|
| 발주기관 | 사업 목적과 범위를 정하고 민간시장 침해 가능성을 자체평가하는 주체임 |
| 평가 기준 | 상용 SW 대체 가능성, 민간 서비스 유사성, 공공성, 불가피성을 판단하는 기준임 |
| 협의 기관 | 제출된 평가 결과를 검토하고 조정 의견을 제시해 공공과 민간의 균형을 맞추는 역할을 함 |
| 민간 의견수렴 | 이해관계 기업이나 단체의 이의 제기와 의견을 받아 실제 시장 영향을 보완 검토하는 절차임 |
| 결과 반영 체계 | 사업 축소, 기능 조정, 데이터 개방 전환 같은 후속 조치를 사업계획과 발주문서에 반영하는 구조임 |

> 요약: 이 제도는 평가 문서 작성보다 평가 결과를 사업 범위와 발주 구조에 반영하는 절차가 판단 기준임

```text
+-----------+     +-------------+     +----------------+     +----------------+
| 사업 기획 | --> | 자체 영향평가 | --> | 협의와 의견수렴   | --> | 결과 반영 및 발주  |
+-----------+     +-------------+     +----------------+     +----------------+
```

## Ⅴ. 원리 및 절차 흐름도

```text
+-------------+     +-------------+     +-------------+     +----------------+
| 사업 구상      | --> | 민간시장 검토  | --> | 협의 및 조정    | --> | 수정 후 사업 추진  |
+-------------+     +-------------+     +-------------+     +----------------+
```

1. **사업 구상**: 발주기관이 서비스 목적과 제공 범위를 정리함
2. **민간시장 검토**: 상용 SW 대체 가능성과 민간 서비스 중복 여부를 자체평가함
3. **협의 및 조정**: 평가 결과를 제출하고 민간 의견과 전문 검토를 반영해 조정안을 도출함
4. **수정 후 사업 추진**: 기능 축소, API 개방, 민간 위탁 같은 조정 결과를 반영해 사업을 발주함

## Ⅵ. 실무 적용 및 유의점

1. 생활 편의 앱이나 플랫폼형 공공 서비스 기획에서는 민간과 기능이 겹치기 쉬우므로 예산 편성 전에 시장 조사와 API 우선 설계를 수행하고 민간 대체 가능성 검토율과 기능 조정 반영률로 확인함
2. 민간기업 이의 제기가 예상되는 사업에서는 공공성 근거와 불가피성 자료를 미리 문서화하고 필요하면 직접 구축 범위를 데이터 제공 중심으로 줄이며 이의 제기 건수와 협의 결과 반영률로 확인함

## Ⅶ. 결론

소프트웨어 사업 영향 평가는 공공의 직접 구축 필요성을 민간시장 보호 관점에서 다시 점검하는 제도이므로 평가 시점을 앞당기고 결과를 발주 범위에 실제 반영해야 실효성이 생김.

## 작성 근거(검토용)

- 영향 평가는 공공성 선언이 아니라 직접 구축 필요성과 민간 대체 가능성을 판단하는 절차이므로 두 기준을 정의와 비교표에 반복 반영함
- `민간 혁신`, `조정 효과` 같은 넓은 표현은 기능 축소, 민간 활용 전환, API 개방 같은 조치로 구체화함
- 평가 결과가 발주 범위에 반영되지 않으면 제도 목적이 약해지므로 절차의 마지막을 결과 반영으로 두었음
