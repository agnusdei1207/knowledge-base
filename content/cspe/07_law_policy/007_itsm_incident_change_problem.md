# 📖 【암기용】 개념 완전 이해

## 한눈에
- **개요**: ITSM의 3대 운영 프랙티스인 **인시던트·문제·변경 관리**는 각각 **서비스 복구(빠른 정상화) / 근본원인 제거(재발 방지) / 위험 통제(안전한 변경)** 라는 서로 다른 목적을 가진 별개의 프랙티스다. ITIL v4 프레임(4차원·SVS·SVC)은 006에서 다뤘고, 여기서는 이 세 프랙티스의 실무 흐름에 집중한다.
- **왜 필요한가**: 장애가 나면 "지금 당장 살리는 일"과 "다시는 안 나게 하는 일"이 뒤섞이기 쉽다. 이 둘을 분리하지 않으면, 급한 복구에 매달려 근본원인을 영원히 못 잡거나, 반대로 원인 분석하느라 복구가 늦어져 서비스가 계속 죽어 있게 된다. 변경 관리는 이 복구·개선을 실제 시스템에 반영할 때 새 장애를 유발하지 않도록 위험을 통제한다.
- **핵심 직관**: 인시던트는 "불 끄기(일단 진화)", 문제는 "발화 원인 조사(전선 교체)", 변경은 "전선 교체 공사를 안전하게 승인·시행". 불을 끄는 사람과 원인을 조사하는 사람의 목표는 다르다 — 이 구분이 이 주제의 전부다.

## 핵심 용어 정리
답안에 등장하는 상위 키워드와 내부 용어를 먼저 이해한다.

| 용어/표기 | 의미 | 비유·예 |
|:---|:---|:---|
| ITSM | IT 서비스 관리 — IT를 서비스로 기획·제공·개선 | IT를 상품처럼 운영 |
| 인시던트(Incident) | 서비스 품질 저하·중단을 일으키는 계획되지 않은 사건 | 불이 남 |
| 문제(Problem) | 하나 이상의 인시던트를 유발하는 **미지의 근본원인** | 불의 발화 원인(누전) |
| 알려진 오류(Known Error) | 근본원인이 규명됐으나 아직 미해결인 문제 | 원인은 밝혔으나 미수리 |
| 변경(Change) | 서비스·구성에 대한 추가·수정·제거 행위 | 전선 교체 공사 |
| 서비스 복구 | 인시던트를 정상 상태로 되돌리는 것(원인 규명과 무관) | 우회로로 일단 살림 |
| 워크어라운드(Workaround) | 근본 해결 없이 영향을 줄이는 임시 우회책 | 두꺼비집 임시 조치 |
| CAB | 변경자문위원회(Change Advisory Board) — 변경 위험 심의 | 공사 승인 심의회 |
| RFC | 변경요청(Request for Change) | 공사 신청서 |
| MTTR | 평균 복구 시간(Mean Time To Restore/Repair) | 불 끄는 데 걸린 평균 시간 |
| SLA | 서비스 수준 협약(Service Level Agreement) | 복구 시간 약속 문서 |
| 우선순위 | 영향도(Impact) × 긴급도(Urgency) 로 산정 | 큰불·번지는 불부터 |
| 표준변경 | 사전 승인된 저위험 반복 변경(개별 CAB 불요) | 정기 소모품 교체 |

## 깊이 이해
- **배경·문제의식**: 세 프랙티스는 모두 ITIL v4의 34개 프랙티스에 속한다(프레임은 006 참조). 실무에서 가장 흔한 실패는 인시던트와 문제를 한 덩어리로 처리하는 것이다. 인시던트 관리의 KPI는 "얼마나 빨리 복구했나(MTTR)"이고, 문제 관리의 KPI는 "재발을 얼마나 줄였나(반복 인시던트 감소율)"로 서로 다르다. 목적이 다르니 팀·프로세스·지표를 분리해야 한다.
- **작동 원리(어떻게+왜)**: ① 인시던트 관리는 원인을 몰라도 된다 — 목적은 오직 **복구**다. 서버가 죽으면 원인 분석 없이 재기동·페일오버·우회로로 일단 서비스를 살린다. 왜냐면 고객은 원인이 아니라 서비스 가용성을 원하기 때문이다. ② 문제 관리는 복구된 뒤(또는 병행해) **근본원인(RCA)** 을 파고들어 재발을 막는다. 원인이 규명되면 '알려진 오류'로 등록하고, 영구 해결책을 도출한다. ③ 그 영구 해결책을 실제 운영에 반영하려면 **변경 관리**를 거친다 — RFC 제출 → 위험·영향 평가 → CAB 심의(또는 표준변경 자동승인) → 시행 → 검토. 왜 변경을 통제하냐면, 통계적으로 서비스 장애의 상당수가 '통제되지 않은 변경'에서 비롯되기 때문이다.
- **비유**: 건물 화재. 인시던트 관리 = 소방관(일단 진화, 원인 불문). 문제 관리 = 화재조사관(누전 원인 규명, 재발 방지 권고). 변경 관리 = 전기공사 승인·시공(권고를 안전하게 반영, 새 화재 유발 금지). 세 역할은 목표도 담당도 다르다.
- **구체 예시**: 결제 서비스가 오후 2시 다운. (인시던트) 온콜 엔지니어가 DB 커넥션풀 고갈을 감지, 인스턴스 재기동으로 14분 만에 복구(MTTR 14분). (문제) 이후 문제 관리팀이 RCA 수행 → 특정 배치가 커넥션을 반환 안 하는 코드 결함 발견 → '알려진 오류' 등록, 워크어라운드로 배치 실행시간 조정. (변경) 코드 수정본을 RFC로 제출 → 회귀 위험 평가 → CAB 승인 → 다음 릴리스 창에 배포 → 재발 0건 확인.
- **흔한 오해·주의점**: ① **인시던트와 문제를 혼동 금지** — 인시던트는 '증상(불)', 문제는 '원인(누전)'이다. 하나의 문제가 여러 인시던트를 낳고, 인시던트를 복구해도 문제(원인)는 남아 재발한다. ② 인시던트 관리에 근본원인 분석을 강요하면 복구가 늦어진다 — RCA는 문제 관리의 몫이다. ③ 모든 변경에 CAB 심의를 요구하면 병목이 된다 — 저위험 반복 변경은 '표준변경'으로 사전 승인해 자동화한다. ④ 서비스 요청(Service Request, 비밀번호 초기화 등 정상 요청)은 인시던트가 아니다 — 별도 요청 이행(Request Fulfilment)으로 처리한다.

## 연결 개념
- ITIL v4 서비스 관리 (006 참조): 본 세 프랙티스를 포함하는 상위 프레임(4차원·SVS·SVC)
- IT 거버넌스 — COBIT (005 참조): 변경·문제의 통제·책임 체계를 상위에서 규율
- 디지털 전환 전략 (009 참조): 데브옵스·SRE로 인시던트·변경 관리를 자동화·고속화

# 📝 【답안용】 시험 답안 템플릿

## 핵심 인사이트 (3줄 요약)

> 1. **본질**: 인시던트=서비스 복구, 문제=근본원인 제거, 변경=위험 통제로 목적이 서로 다른 3대 ITSM 운영 프랙티스임.
> 2. **가치**: 복구와 원인 규명을 분리해 가용성과 재발 방지를 동시에 확보하고, 변경 통제로 새 장애 유발을 차단함.
> 3. **판단 포인트**: 인시던트(증상)와 문제(원인)를 혼동하면 안 되며, 변경은 위험도에 따라 표준변경·정규변경으로 차등 통제함.

## 출제 의도 및 답안 포인트

| 출제 의도 | 반드시 짚을 핵심 | 감점 회피 포인트 |
|:---|:---|:---|
| 3대 프랙티스 목적 구분 | 복구·근본원인·위험통제의 상이한 목적 | 인시던트와 문제 목적 혼동 |
| 인시던트·문제 관계 이해 | 문제가 다수 인시던트 유발, RCA·알려진오류 | 복구=문제해결로 단정 |
| 변경 관리 통제 흐름 | RFC·CAB·표준변경 차등 통제 | 전 변경에 CAB 일괄 적용 단정 |

> 요약: 세 프랙티스의 목적 차이, 인시던트(증상)와 문제(원인)의 구분, 변경의 위험 차등 통제를 명확히 짚어야 함.

## Ⅰ. 개요 및 필요성

- 개요: 인시던트·문제·변경 관리는 목적이 다른 ITSM 3대 운영 프랙티스임
- 배경: 급한 복구와 재발 방지가 뒤섞여 근본원인 미해결·복구 지연이 반복됨
- 필요성: 복구(가용성)와 원인 제거(재발 방지)를 분리하고, 변경 위험을 통제해 서비스 안정성 확보 필요
- 위치: ITIL v4 프레임(4차원·SVS·SVC)은 006이 담당, 본 키워드는 개별 프랙티스 실무 흐름에 집중

---

## Ⅱ. 구조 및 구성요소

```text
[사용자·모니터링] -> 인시던트 관리 (복구 목적)
                        /  반복·중대 인시던트 발생
                        v
                     문제 관리 (근본원인 RCA -> 알려진 오류 -> 영구 해결책)
                        /  영구 해결책을 운영에 반영
                        v
                     변경 관리 (RFC -> 위험평가 -> CAB/표준변경 -> 시행 -> 검토)
                        /
                     [CMDB·형상정보 / SLA·우선순위(영향도×긴급도) 공통 참조]
```

| 구성요소 | 목적 | 핵심 산출물·특이사항 |
|:---|:---|:---|
| 인시던트 관리 | 서비스 신속 복구 | MTTR·SLA 준수, 워크어라운드, 원인 불문 |
| 문제 관리 | 근본원인 제거·재발 방지 | RCA, 알려진 오류 등록부, 영구 해결책 |
| 변경 관리 | 변경 위험 통제 | RFC, CAB 심의, 표준·정규·긴급 변경 구분 |
| 우선순위 체계 | 처리 순서 결정 | 영향도(Impact)×긴급도(Urgency) |
| CMDB(형상DB) | 세 프랙티스 공통 참조 정보 | 구성항목(CI) 간 영향 관계 파악 |

> 요약: 인시던트→문제→변경으로 복구·원인제거·반영이 이어지며, 우선순위·CMDB를 공통 기반으로 함.

## Ⅲ. 동작원리 및 흐름도

```text
인시던트 발생 -> [탐지·기록] -> [분류·우선순위(영향도×긴급도)] -> [복구·워크어라운드] -> [종료]
   반복/중대 -> 문제 관리: [문제 등록] -> [근본원인 분석(RCA)] -> [알려진 오류] -> [영구 해결책 도출]
   영구 해결책 -> 변경 관리: [RFC 제출] -> [위험·영향 평가] -> [CAB 승인/표준변경] -> [시행·검토]
```

- 1단계 [인시던트 복구]: 서비스데스크·모니터링이 인시던트를 탐지·기록하고, 담당 엔지니어가 원인과 무관하게 복구를 우선함
- 2단계 [문제 등록·분석]: 문제 관리팀이 반복·중대 인시던트의 근본원인을 RCA로 규명하고 알려진 오류로 등록함
- 3단계 [영구 해결·변경 요청]: 문제 관리팀이 영구 해결책을 도출하고 이를 반영하기 위해 변경 관리팀에 RFC를 제출함
- 4단계 [변경 시행·검토]: 변경 관리팀이 위험을 평가해 CAB 승인 또는 표준변경으로 시행하고, 사후 검토로 재발 여부를 확인함

> 요약: 인시던트팀이 복구하고, 문제팀이 원인을 규명하며, 변경팀이 해결책을 안전하게 반영하는 3단 흐름임.

---

## Ⅳ. 특징
- 목적 분리: 인시던트(복구)·문제(원인 제거)·변경(위험 통제)이 각기 다른 목적과 지표를 가짐
- 증상·원인 구분: 인시던트는 증상, 문제는 원인 — 한 문제가 다수 인시던트를 유발함
- 위험 차등 통제: 변경을 표준(사전승인)·정규(CAB)·긴급으로 나눠 병목 없이 통제함
- 공통 기반 연계: 우선순위(영향도×긴급도)·CMDB를 세 프랙티스가 공유해 영향 분석을 일관화함

> 요약: 목적 분리, 증상·원인 구분, 변경 위험 차등 통제, 공통 기반 연계가 3대 프랙티스의 특징임.

## Ⅴ. 심화 비교 및 적용 판단

| 구분 | 인시던트 관리 | 문제 관리 | 변경 관리 |
|:---|:---|:---|:---|
| 목적 | 서비스 신속 복구 | 근본원인 제거·재발 방지 | 변경 위험 통제 |
| 원인 규명 | 불필요(복구 우선) | 필수(RCA 핵심) | 변경 자체의 위험 평가 |
| 대표 지표 | MTTR·SLA 준수율 | 반복 인시던트 감소율 | 변경 성공률·변경유발 장애율 |
| 시간 축 | 실시간·즉각 | 사후·중기 분석 | 계획·승인 후 시행 |
| 핵심 산출물 | 복구·워크어라운드 | 알려진 오류·영구 해결책 | RFC·CAB 승인 이력 |

> 요약: 인시던트는 즉각 복구, 문제는 사후 원인 제거, 변경은 계획적 위험 통제로 시간축·지표·산출물이 모두 다름.

**리스크·대응(리스크 — 원인 — 대응):**
- 근본원인 미해결 — 복구만 반복하고 문제 관리 미가동 — 반복 인시던트 임계치 초과 시 문제 자동 등록
- 변경 유발 장애 — 통제 없는 변경 배포 — 표준/정규 변경 분류와 CAB·롤백 계획 의무화
- CAB 병목 — 저위험 변경까지 일괄 심의 — 반복·저위험 변경을 표준변경으로 사전 승인·자동화

**적용 판단 지표(지표 — 목표 — 측정):**
- MTTR — 서비스별 SLA 이내 — 인시던트 복구 소요시간 집계
- 재발률 — 알려진 오류 대비 재발 감소 — 동일 원인 반복 인시던트 건수 추이
- 변경 유발 장애율 — 임계치 이하 — 변경 후 일정기간 내 인시던트 연관 분석

---

## Ⅵ. 실무 적용 및 결론

**적용 방안 3개:**
1. 인시던트·문제 분리 운영: 서비스데스크의 인시던트 티켓과 문제 관리 티켓을 별도 워크플로로 분리하고, 반복 임계치(예: 동일 증상 3회) 초과 시 문제로 자동 승격
2. 변경 위험 차등화: 변경을 표준(사전승인·자동)·정규(CAB 심의)·긴급(사후 검토)으로 분류하고, 표준변경 카탈로그로 CAB 부하를 경감
3. 데브옵스·SRE 연계: CI/CD 파이프라인에 변경 승인·자동 롤백을 내재화하고, 인시던트 대응에 온콜·포스트모템(비난 없는 회고)을 정착

**결론 (2줄):**
- 기술사 판단: 조직이 복구 속도를 다투는 운영 성숙도라면 인시던트 관리와 MTTR 개선에 우선 투자하고, 반복 장애로 신뢰가 흔들리는 단계라면 문제 관리·근본원인 제거에 무게를 두어야 함.
- 향후 방향: AIOps로 인시던트 자동 탐지·상관분석을 고도화하고, 변경 관리를 GitOps·정책 기반 자동 승인으로 진화시켜야 함.
