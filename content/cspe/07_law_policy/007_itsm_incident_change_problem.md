# 📖 【암기용】 개념 완전 이해

> 목적: 인시던트·문제·변경 관리 세 프로세스를 처음 봐도 목적이 어떻게 다른지 명확히 구분하게 만든다. 시험 답안 양식이 아니라, 이해를 위한 친절한 설명이다.

## 한눈에
- **개요**: 인시던트 관리는 서비스를 최대한 빨리 복구하고, 문제 관리는 반복되는 인시던트의 근본 원인을 찾으며, 변경 관리는 시스템 수정 작업을 통제된 절차로 관리하는 ITSM 핵심 프로세스 3종
- **왜 필요한가**: 장애가 나면 "빨리 고치는 일"과 "왜 생겼는지 밝히는 일"과 "고치는 작업 자체를 안전하게 통제하는 일"은 서로 다른 목적이라 별도 프로세스로 분리해야 한다.
- **핵심 직관**: 응급실(인시던트, 증상 완화 우선)과 정밀검진(문제, 원인 규명)과 수술 승인 절차(변경, 통제된 시행)의 관계와 같다.

## 깊이 이해
- **배경·문제의식**: 장애 발생 시 근본 원인 규명에 매달리면 서비스 중단 시간이 길어지고, 반대로 임시 복구만 반복하면 같은 장애가 계속 재발한다.
- ITIL은 이 두 목적을 인시던트 관리(증상 완화, 신속 복구)와 문제 관리(원인 규명, 재발 방지)로 분리하고, 수정 작업 자체는 변경 관리로 통제한다.
- **작동 원리**: 인시던트 관리는 접수-분류-우회 조치 또는 임시 복구-종결의 흐름으로 서비스 정상화를 최우선한다.
- 문제 관리는 반복 인시던트 패턴을 분석해 근본 원인(Root Cause)을 찾고 영구적 해결책(Known Error, 해결 방안)을 도출한다.
- 변경 관리는 문제 관리에서 도출된 해결책이든 신규 기능 추가든, 실제 시스템 수정을 요청-평가-승인-구현-검토 절차로 통제해 부작용을 예방한다.
- **비유**: 인시던트 관리는 화재 진압, 문제 관리는 화재 원인 감식, 변경 관리는 재발 방지를 위한 소방시설 공사 인허가 절차에 해당한다.
- **구체 예시**: 웹 서버 응답 지연이 발생하면 인시던트 관리로 서버 재기동으로 즉시 복구하고(증상 완화), 문제 관리로 분석한 결과 메모리 누수가 원인임을 밝히며(근본 원인), 변경 관리를 통해 승인받은 패치를 정식 배포한다(통제된 수정).
- **흔한 오해·주의점**: 인시던트를 종결했다고 문제가 해결된 것은 아니다.
- 인시던트 종결은 서비스가 복구됐다는 뜻이지 재발 원인이 제거됐다는 뜻이 아니며, 재발 방지책은 문제 관리와 변경 관리를 거쳐야 확정된다.

## 연결 개념
- ITIL v4 — 세 프로세스가 속한 서비스 가치 사슬의 관리 관행
- Known Error DB — 문제 관리에서 축적하는 원인-해결책 데이터베이스
- 변경 자문위원회(CAB) — 변경 관리에서 고위험 변경을 심의하는 기구

# 📝 【답안용】 시험 답안 템플릿

> 목적: 시험장에서 25분에 그대로 쓰는 답안 양식. 작성방식(추상표현 금지·수치·도식·문제유형 전환)을 엄격히 지킨다.
> 핵심: ITSM 답안은 세 프로세스의 목적 차이, 처리 흐름, 상호 연계 관계를 함께 제시한다.

## 핵심 인사이트 (3줄 요약)

> 1. **본질**: 인시던트 관리는 신속 복구, 문제 관리는 근본 원인 규명, 변경 관리는 수정 작업의 통제된 시행을 각각 목적으로 하는 ITSM 핵심 프로세스다.
> 2. **가치**: 세 프로세스를 분리하면 복구 속도와 재발 방지, 안전한 수정이라는 서로 다른 목표를 동시에 달성할 수 있다.
> 3. **판단 포인트**: 증상 대응은 인시던트, 원인 분석은 문제, 실제 수정 시행은 변경 관리로 구분해 담당 범위를 정한다.

## 출제 의도 및 답안 포인트

| 출제 의도 | 반드시 짚을 핵심 | 감점 회피 포인트 |
|:---|:---|:---|
| 세 프로세스 목적 구분 확인 | 복구 vs 원인 규명 vs 통제된 수정 | 세 프로세스를 유사한 장애 대응으로 뭉뚱그림 |
| 처리 흐름 이해 확인 | 접수-분류-복구/원인분석-변경요청-검토 | 프로세스 간 순서를 생략하고 정의만 나열 |
| 상호 연계 이해 확인 | 인시던트 반복 -> 문제 등록 -> 변경 요청 흐름 | 세 프로세스가 독립적이라고 서술 |

> 요약: 이 문제는 정의 나열보다 인시던트-문제-변경이 이어지는 연계 흐름과 목적 차이를 보여야 한다.

---

## Ⅰ. 개요 및 필요성

- 개요: 서비스 복구·원인 규명·통제된 수정을 각각 담당하는 ITSM 3대 프로세스
- 배경: 복구와 원인 규명을 하나의 절차로 처리하면 서비스 중단이 길어지거나 재발이 반복되어 프로세스 분리 필요성이 대두됨
- 필요성: 신속 복구와 재발 방지, 안전한 변경 시행을 동시에 확보하려면 세 프로세스의 명확한 역할 분담이 필요함

---

## Ⅱ. 구조 및 구성요소

```text
장애 발생 -> 인시던트 관리(접수/분류/복구)
  -> 반복 패턴 감지 -> 문제 관리(원인분석/Known Error)
  -> 해결책 확정 -> 변경 관리(요청/평가/승인/구현/검토)
```

| 구성요소 | 역할 | 특이사항 |
|:---|:---|:---|
| 인시던트 관리 | 서비스 중단·저하를 신속히 복구 | 우회 조치, 임시 복구 허용 |
| 문제 관리 | 반복 인시던트의 근본 원인 규명 | Known Error DB 축적 |
| 변경 관리 | 시스템 수정을 통제된 절차로 시행 | CAB(변경 자문위원회) 심의 |
| 서비스 데스크 | 인시던트 접수 창구 | 사용자 단일 접점 |

> 요약: 인시던트 관리가 서비스를 즉시 복구하고 문제 관리가 원인을 규명하며 변경 관리가 해결책을 통제된 방식으로 시행한다.

---

## Ⅲ. 동작원리 및 흐름도

```text
장애 접수 -> 인시던트 분류/우선순위 -> 임시 복구/우회
  -> 종결 -> (반복 시) 문제 등록 -> 근본 원인 분석
  -> 해결책 도출 -> 변경 요청 -> 평가/승인 -> 구현 -> 사후 검토
```

| 단계 | 처리 내용 | 검증 기준 |
|:---:|:---|:---|
| 1 | 인시던트 접수 후 우선순위 분류 | 응답 시간(SLA) |
| 2 | 임시 복구 또는 우회 조치로 서비스 정상화 | 복구 시간(MTTR) |
| 3 | 반복 발생 시 문제로 등록해 원인 분석 | 근본 원인 도출 여부 |
| 4 | 해결책을 변경 요청으로 전환해 평가·승인·구현 | 변경 성공률, 롤백 여부 |

> 요약: 장애는 인시던트로 신속히 복구되고, 반복되면 문제로 전환되어 원인 분석 후 변경 관리로 해결책이 시행된다.

---

## Ⅳ. 특징

| 구분 | 인시던트 관리 | 문제 관리 | 변경 관리 |
|:---|:---|:---|:---|
| 목적 | 서비스 신속 복구 | 근본 원인 규명, 재발 방지 | 수정 작업의 통제된 시행 |
| 시간 압박 | 매우 높음(즉시 대응) | 낮음(분석 시간 확보) | 계획된 일정 내 진행 |
| 산출물 | 복구 완료, 인시던트 로그 | Known Error, 해결책 | 변경 승인 이력, 구현 결과 |

> 요약: 세 프로세스는 시간 압박과 산출물이 달라 동일한 절차로 처리하면 목적을 달성하기 어렵다.

---

## Ⅴ. 심화 비교 및 적용 판단

| 구분 | 인시던트 관리 | 문제 관리 | 변경 관리 |
|:---|:---|:---|:---|
| 구조 | 접수-분류-복구-종결 | 감지-분석-Known Error 등록 | 요청-평가-승인-구현-검토 |
| 비용/성능 | 임시 조치로 재발 가능 | 분석 시간 소요, 재발 방지 효과 | 승인 지연 시 해결책 적용 지연 |
| 운영/위험 | 근본 원인 미해결 위험 | 분석 지연 시 인시던트 누적 | 무통제 변경 시 신규 장애 유발 |

> 요약: 신속 복구가 급하면 인시던트, 재발 방지가 목적이면 문제, 실제 수정 시행이 필요하면 변경 관리를 적용한다.

| 리스크 | 원인 | 대응 방안 | 확인 지표 |
|:---|:---|:---|:---|
| 인시던트 반복 | 임시 복구만 하고 문제 미등록 | 반복 인시던트 임계값 초과 시 자동 문제 등록 | 문제 등록률 |
| 원인 분석 지연 | 문제 관리 인력·시간 부족 | 우선순위 기반 분석 자원 배분 | 평균 원인 규명 소요일 |
| 무통제 변경 | CAB 심의 생략 | 고위험 변경은 CAB 필수 심의 | 미승인 변경 발생 건수 |

> 요약: ITSM 운영은 문제 등록률, 원인 규명 소요일, 미승인 변경 건수로 통제한다.

| 점검 항목 | 목표 기준 | 측정 방법 |
|:---|:---|:---|
| 복구 속도 | MTTR 목표 시간 이내 | 인시던트 로그 |
| 재발 방지 | 동일 원인 재발률 감소 | 문제 관리 이력 |
| 변경 안정성 | 변경 실패율(롤백률) 최소화 | 변경 관리 이력 |

> 요약: 도입 후 성공 여부는 MTTR, 재발률, 변경 실패율로 판단한다.

---

## Ⅵ. 실무 적용 및 결론

**적용 방안 3개 (필수 — 단계별 또는 항목별):**
1. 단기: 인시던트 분류와 우선순위 기준을 정립해 MTTR을 단축함
2. 중기: 반복 인시던트 임계값을 정해 자동으로 문제 관리로 전환하고 Known Error DB를 구축함
3. 장기: 고위험 변경은 CAB 심의를 의무화하고 변경 실패율을 지표로 관리함

**결론 (2줄):**
- 기술사 판단: 서비스 복구·원인 규명·안전한 수정이라는 서로 다른 목적을 가진 세 프로세스는 분리 운영하되 반드시 연계 흐름으로 통합해야 함
- 향후 방향: AIOps 기반 이상 탐지로 인시던트 예측과 문제 관리 자동화를 결합해 재발률을 낮추는 방향으로 발전해야 함
