# 📖 【암기용】 개념 완전 이해

## 한눈에
- **개요**: 디지털 플랫폼 정부(DPG, Digital Platform Government)는 **모든 공공 데이터와 서비스가 하나의 디지털 플랫폼 위에서 연결되고, 국민·기업·정부가 그 위에서 함께 문제를 해결·창업하는 정부 운영 모델**이다. 핵심은 '정부가 서비스를 다 만드는 것'이 아니라 '정부가 데이터·기능을 플랫폼으로 열고, 민간이 그 위에서 서비스를 만들게 하는 것'이다.
- **왜 필요한가**: 기존 전자정부는 부처·기관마다 시스템을 따로 구축해(칸막이), 국민이 서비스마다 같은 서류를 반복 제출하고 여러 사이트를 오가야 했다. 데이터가 기관 안에 갇혀 민간이 활용하기도 어려웠다. DPG는 이 칸막이를 허물어 데이터를 한 플랫폼으로 통합·개방하고, 국민이 신청하지 않아도 먼저 챙겨주는 '선제적 서비스'로 전환하려는 국가 전략이다.
- **핵심 직관**: 스마트폰 앱스토어를 떠올리면 된다. 애플이 앱을 다 만들지 않고 iOS라는 플랫폼과 API만 열어주면 수많은 개발사가 앱을 만든다. DPG도 정부가 데이터·인증·결제 같은 공통 기능을 플랫폼으로 열면, 민간이 그 위에서 창의적 공공서비스를 만든다 — 정부는 '서비스 공급자'에서 '플랫폼 운영자'로 역할이 바뀐다.

## 핵심 용어 정리
답안에 등장하는 상위 키워드와 내부 용어를 먼저 이해한다.

| 용어/표기 | 의미 | 비유·예 |
|:---|:---|:---|
| DPG(디지털 플랫폼 정부) | 데이터·서비스를 한 플랫폼으로 통합·개방한 정부 모델 | 정부판 앱스토어 |
| 전자정부(e-Gov) | 행정 업무를 온라인화한 기존 정부 | 민원24·홈택스 |
| 원플랫폼(One Platform) | 부처별 시스템을 논리적으로 하나로 연결한 기반 | 흩어진 창구를 하나로 |
| 부처 칸막이 | 기관마다 데이터·시스템이 단절된 상태 | 서류 반복 제출 |
| 공공데이터 개방 | 정부 보유 데이터를 API·오픈포맷으로 공개 | data.go.kr |
| 오픈 API | 외부가 데이터·기능을 호출하는 표준 창구 | 앱이 지도 불러오듯 |
| 마이데이터 | 본인 정보를 스스로 내려받아 활용·이동 | 내 건강기록 앱 연동 |
| 선제적·맞춤형 서비스 | 신청 전에 자격을 찾아 먼저 안내·지급 | 숨은 복지 알림 |
| 민관협력(PPP) | 정부가 플랫폼 제공, 민간이 서비스 개발 | 창업 생태계 |
| 클라우드 네이티브 | 클라우드 기반으로 유연·확장 가능한 시스템 | MSA·컨테이너 |
| 애자일 정부 | 작은 단위로 빠르게 만들고 개선하는 행정 방식 | 파일럿 후 확산 |
| DPG위원회 | 디지털플랫폼정부위원회, 추진 총괄 거버넌스 | 컨트롤타워 |

## 깊이 이해
- **배경·문제의식**: DX(디지털 전환)가 사업·조직을 재설계하는 흐름(009 참조)이라면, DPG는 그 공공 부문 구현체다. 한국의 전자정부는 세계 최고 수준으로 온라인화됐지만, 부처별로 1,000개가 넘는 시스템이 개별 구축돼 데이터가 단절됐다. 그 결과 국민은 서비스마다 주민등록등본·소득증명을 반복 발급받아 제출했고, 민간은 정부 데이터를 활용해 신사업을 하기 어려웠다. DPG는 이 '칸막이·수동 신청' 구조를 '연결·선제 제공'으로 바꾸려는 국정 전략이다.
- **작동 원리(어떻게+왜)**: DPG는 ① 데이터를 표준·API로 통합·개방하는 '데이터 기반', ② 인증·결제·알림 같은 공통 기능을 재사용하는 '공통 인프라(원플랫폼)', ③ 민간이 그 위에서 서비스를 만드는 '민관 개방 생태계', ④ 클라우드 네이티브·AI 기반의 '지능형 서비스'로 구성된다. 왜 개방하느냐면, 정부가 모든 서비스를 직접 만들면 속도·창의성에 한계가 있고, 데이터·기능을 플랫폼으로 열어 민간의 역량을 끌어들여야 국민 체감 서비스가 빠르게 늘기 때문이다.
- **비유**: 옛 전자정부가 부처마다 '독립된 매점'을 여러 개 차린 것이라면, DPG는 이들을 '하나의 대형 쇼핑몰(플랫폼)'로 묶고, 입점 규칙(API·표준)만 정한 뒤 민간 상점이 자유롭게 입점하게 하는 것이다. 손님(국민)은 한 번의 로그인·결제로 모든 층을 이용한다.
- **구체 예시**: 출산하면 국민이 따로 신청하지 않아도 정부가 자격을 찾아 출산지원금·양육수당·전기료 감면을 한 번에 안내·신청 처리(선제적 서비스). 이를 위해 복지부·행안부·한전 데이터가 API로 연결되고, 마이데이터로 본인 동의 하에 정보가 오간다. 민간 앱은 공공데이터 API를 불러와 '숨은 복지 찾기' 서비스를 만든다.
- **흔한 오해·주의점**: ① **DPG ≠ 전자정부의 이름만 바꾼 것** — 전자정부는 '업무 온라인화', DPG는 '데이터 통합·민간 개방·선제 서비스'로 지향점이 다르다. ② **DPG ≠ 정부 포털 하나로 통합** — 물리적으로 시스템을 하나로 합치는 게 아니라, API·표준으로 '논리적 연결(원플랫폼)'을 이루는 것이다. ③ 데이터를 열수록 개인정보·보안 위험이 커지므로, 마이데이터 동의·가명처리·제로트러스트 보안이 반드시 함께 가야 한다 — 개방과 보호는 대립이 아니라 병행 과제다.

## 연결 개념
- 디지털 전환 DX 전략 (009 참조): DPG는 DX의 공공 부문 구현체로 데이터·플랫폼 기반 행정 전환
- 전자정부 성숙도 모형 (011 참조): DPG는 UN 성숙도의 최상위(연결형·플랫폼형) 지향
- 클라우드 컴퓨팅법·공공 클라우드 (029 참조): DPG의 클라우드 네이티브 기반을 뒷받침하는 제도

# 📝 【답안용】 시험 답안 템플릿

## 핵심 인사이트 (3줄 요약)

> 1. **본질**: DPG는 공공 데이터·서비스를 한 플랫폼으로 통합·개방해 국민·기업·정부가 함께 문제를 해결하는 정부 운영 모델임.
> 2. **가치**: 부처 칸막이를 허물어 데이터를 연결·개방하고, 신청 없이 먼저 챙기는 선제적·맞춤형 서비스로 전환함.
> 3. **판단 포인트**: DPG는 전자정부의 온라인화를 넘어 민관 개방 생태계를 지향하며, 개방과 개인정보·보안 보호를 반드시 병행해야 함.

## 출제 의도 및 답안 포인트

| 출제 의도 | 반드시 짚을 핵심 | 감점 회피 포인트 |
|:---|:---|:---|
| DPG 개념·전자정부와 차이 | 데이터 통합·개방, 선제 서비스, 민관 개방 | DPG를 전자정부 명칭 변경으로 단정 |
| 구조·구성요소 이해 | 원플랫폼·데이터 개방·민관 생태계·지능형 | 포털 물리 통합으로 오해 |
| 개방과 보안 균형 | 마이데이터 동의·가명처리·제로트러스트 병행 | 개인정보 보호 대책 누락 |

> 요약: DPG의 데이터 통합·개방과 선제 서비스, 민관 개방 생태계 구조, 개방과 개인정보 보호의 병행을 명확히 짚어야 함.

## Ⅰ. 개요 및 필요성

- 개요: DPG는 공공 데이터·서비스를 하나의 플랫폼으로 연결·개방한 정부 운영 모델임
- 배경: 부처별 개별 구축으로 데이터가 단절돼 서류 반복 제출·수동 신청의 불편이 반복됨
- 필요성: 칸막이를 허물어 데이터를 통합·개방하고 신청 전 먼저 제공하는 선제적 서비스 전환 필요
- 지향: 정부가 플랫폼·API를 열고 민간이 서비스를 창출하는 민관 개방 생태계 구현 필요

---

## Ⅱ. 구조 및 구성요소

```text
[국민/기업/민간개발사]
      |  오픈 API 호출 / 마이데이터 동의
   [원플랫폼: 인증·결제·알림 공통 기능]
      |
   +--+ 데이터 기반 (부처 데이터 표준·API 통합·개방)
   +--+ 민관 개방 생태계 (민간이 공공데이터로 서비스 개발)
   +--+ 지능형 서비스 (AI·클라우드 네이티브 기반 선제·맞춤)
      |
   [DPG위원회] 거버넌스 / [개인정보·보안] 가명처리·제로트러스트
```

| 구성요소 | 역할 | 특이사항 |
|:---|:---|:---|
| 원플랫폼 | 인증·결제·알림 공통기능을 논리적 통합 | 물리 통합 아닌 API 연결 |
| 데이터 기반 | 부처 데이터를 표준·API로 통합·개방 | 공공데이터 오픈 |
| 민관 개방 생태계 | 민간이 공공 API로 서비스 개발 | 정부는 플랫폼 운영자 |
| 지능형 서비스 | AI·클라우드로 선제적·맞춤형 제공 | 신청 전 자격 안내 |
| DPG위원회 | 추진 총괄·부처 조정 거버넌스 | 컨트롤타워 |

> 요약: DPG는 원플랫폼 공통기능 위에 데이터 개방·민관 생태계·지능형 서비스를 얹고, 거버넌스와 보안이 이를 관통함.

---

## Ⅲ. 동작원리 및 흐름도

```text
[부처 데이터 표준화·API화] -> [원플랫폼에 데이터·기능 등록·개방]
   -> [민간/정부가 API로 서비스 구성] -> [국민이 한 번의 인증으로 이용]
   -> [AI가 자격 탐지 -> 선제적 안내·처리] (마이데이터 동의·보안 관통)
```

- 1단계 [개방]: 정부가 부처별 데이터를 표준·API로 정비해 원플랫폼에 등록·개방함
- 2단계 [조합]: 민간 개발사·정부가 개방된 API를 조합해 국민 대상 서비스를 구성함
- 3단계 [연결 이용]: 국민이 한 번의 인증·동의로 여러 기관 서비스를 끊김 없이 이용함
- 4단계 [선제 제공]: AI가 데이터로 수급 자격을 탐지해 국민이 신청하기 전에 먼저 안내·처리함

> 요약: 정부가 데이터를 API로 개방하면 민관이 서비스를 조합하고, 국민은 단일 인증으로 이용하며 AI가 선제적으로 제공함.

## Ⅳ. 특징
- 데이터 연결성: 부처 칸막이를 허물어 데이터를 표준·API로 통합·개방함
- 민관 개방성: 정부가 플랫폼·API를 열고 민간이 서비스를 창출하는 생태계 구조임
- 선제성: 국민 신청을 기다리지 않고 자격을 먼저 찾아 안내·지급하는 선제적 서비스 지향
- 지능·확장성: 클라우드 네이티브·AI 기반으로 서비스를 유연하게 확장·고도화함
- 보안 병행성: 개방과 동시에 마이데이터 동의·가명처리·제로트러스트로 개인정보를 보호함

> 요약: 데이터 연결성·민관 개방성·선제성·지능 확장성을 지니되, 개인정보 보호를 반드시 병행하는 정부 모델임.

## Ⅴ. 심화 비교 및 적용 판단

| 구분 | 전자정부(기존) | 디지털 플랫폼 정부(DPG) |
|:---|:---|:---|
| 지향 | 행정 업무 온라인화 | 데이터 통합·민관 개방 |
| 시스템 구조 | 부처별 개별 구축(칸막이) | 원플랫폼 API 논리 연결 |
| 서비스 방식 | 국민이 신청·방문 | 선제적·맞춤형 자동 제공 |
| 데이터 | 기관 내 폐쇄 보관 | 표준·API로 개방·연계 |
| 민간 역할 | 이용자 | 서비스 개발 주체(생태계) |

> 요약: 전자정부는 업무 온라인화·부처 칸막이·수동 신청인 반면, DPG는 데이터 개방·원플랫폼 연결·선제 서비스·민관 생태계로 근본적으로 다름.

**리스크·대응(리스크 — 원인 — 대응):**
- 개인정보 유출 — 데이터 개방·연계 확대 — 마이데이터 동의·가명처리·제로트러스트 접근통제
- 데이터 품질 저하 — 부처별 표준·정합성 미비 — 공통 데이터 표준·품질관리 체계 선행
- 민관 참여 저조 — API 불안정·수익모델 부재 — 안정적 API·SLA·창업 인센티브 제공

**적용 판단 지표(지표 — 목표 — 측정):**

## Ⅵ. 실무 적용 및 결론

**적용 방안 3개:**
1. 원플랫폼·API 우선 구축: 인증·결제·알림 등 재사용 공통기능을 원플랫폼으로 표준화하고, 부처 데이터를 오픈 API로 등록해 논리적 연결(물리 통합이 아닌)을 우선 확보
2. 선제적 서비스 파일럿: 출산·복지 등 국민 체감 영역에서 마이데이터 동의 기반으로 자격을 자동 탐지·안내하는 선제 서비스를 파일럿한 뒤 애자일하게 확산
3. 개방·보안 동시 설계: 공공데이터 개방과 함께 가명처리·제로트러스트·접근통제를 설계 단계에 내재화하고, DPG위원회 거버넌스로 부처 표준·품질을 조정

**결론 (2줄):**
- 기술사 판단: 데이터 표준·품질이 미성숙한 기관이면 데이터 정비·API 표준화를 선행하고, 기반이 갖춰진 영역이면 선제적·맞춤형 서비스와 민관 개방 생태계로 자원을 집중하는 것이 합리적임.
- 향후 방향: 생성형 AI·마이데이터를 축으로 초개인화 선제 행정을 확대하되, 개인정보 보호·알고리즘 신뢰성을 함께 갖춰 개방과 보호가 균형된 정부를 실현해야 함.
