# 📖 【암기용】 개념 완전 이해

> 목적: GPL·MIT·Apache 라이선스를 처음 봐도 무엇을 강제하고 무엇을 자유롭게 두는지 이해하게 만든다. 시험 답안 양식이 아니라, 이해를 위한 친절한 설명이다.

## 한눈에
- **개요**: 저작권을 기반으로 오픈소스 코드의 이용·수정·재배포 조건을 정한 표준 계약 문서
- **왜 필요한가**: 저작권만으로는 재이용 조건이 불명확해 라이선스로 복제·수정·배포·특허 관련 권리와 의무를 명시해야 함
- **핵심 직관**: GPL은 "이 재료로 요리하면 레시피도 공개해야 한다"는 계약이고, MIT·Apache는 "재료 출처만 밝히면 레시피는 비공개해도 된다"는 계약이다

## 깊이 이해
- **배경·문제의식**: 오픈소스 코드를 상용 제품에 포함할 때 소스코드 공개 의무, 특허 분쟁 위험, 라이선스 충돌 여부가 사업에 직접 영향을 줌
- **작동 원리**: GPL은 카피레프트 라이선스로, GPL 코드를 사용한 결합물을 배포하면 그 결합물도 GPL로 소스코드를 공개해야 함
- **작동 원리**: LGPL은 GPL의 완화 버전으로, 라이브러리를 링크만 하는 응용 프로그램에는 카피레프트 전파 의무를 면제함
- **작동 원리**: MIT는 퍼미시브 라이선스로, 저작권 고지와 라이선스 문구만 유지하면 소스 비공개 상용 제품에도 자유롭게 포함 가능함
- **작동 원리**: Apache 2.0도 퍼미시브 라이선스이지만 MIT와 달리 기여자의 특허를 명시적으로 사용자에게 라이선스하는 특허 부여 조항과 특허소송 시 라이선스가 종료되는 조항을 포함함
- **비유**: GPL은 전염성 있는 계약(결합물 전체에 공개 의무 전파)이고, MIT·Apache는 전염되지 않는 계약(가져다 써도 원본 조건만 유지)이다
- **구체 예시**: 리눅스 커널(GPLv2)을 수정해 배포하면 수정 소스를 공개해야 하지만, React(MIT) 코드를 가져와 상용 SaaS에 포함해도 소스 공개 의무가 없음
- **흔한 오해·주의점**: MIT 라이선스는 특허에 대해 명시적으로 언급하지 않아 특허 분쟁 시 보호가 불명확하지만, Apache 2.0은 특허 부여 조항으로 이 공백을 명시적으로 메운다는 차이를 혼동하면 안 됨

## 연결 개념
- 소프트웨어 저작권 보호 — 라이선스가 근거하는 저작권 체계
- 오픈소스 컴플라이언스·SBOM — 라이선스 의무 이행을 실무에서 관리하는 절차
- 특허 — Apache 2.0의 특허 부여·소송 종료 조항과 연결되는 권리

> 2. **가치**: GPL은 카피레프트로 공개 생태계 확산을 유도하고, MIT·Apache는 퍼미시브로 상용 채택을 촉진한다.

## Ⅰ. 개요 및 필요성

- 개요: 저작권 기반으로 오픈소스 코드의 이용·수정·재배포 조건을 규정한 라이선스
- 배경: 카피레프트(GPL, 결합물 공개 의무)와 퍼미시브(MIT·Apache, 공개 의무 없음)
- 필요성: 상용 제품에 오픈소스를 포함할 때 소스 공개 의무와 특허 리스크를 사전에 판단해야 함

---

## Ⅱ. 구조 및 구성요소

```text
오픈소스 코드 도입 -> 라이선스 유형 판단
  -> GPL(카피레프트): 결합물 소스 공개 의무
  -> LGPL: 링크만 하면 공개 의무 면제
  -> MIT(퍼미시브): 고지 유지, 특허 조항 없음
  -> Apache 2.0(퍼미시브): 고지 유지 + 특허 부여·소송종료 조항
```

| 구성요소 | 역할 | 특이사항 |
|:---|:---|:---|
| GPL | 결합물 전체에 소스 공개 의무 전파(카피레프트) | GPLv3은 특허 보복·티보이제이션 금지 추가 |
| LGPL | 라이브러리 링크 시 전파 의무 면제 | 라이브러리 자체 수정분은 공개 의무 유지 |
| MIT | 저작권 고지·라이선스 문구 유지만 요구 | 특허에 대한 명시적 조항 없음 |
| Apache 2.0 | 고지·NOTICE 파일 유지 요구 | 특허 부여 조항, 특허소송 시 라이선스 자동 종료 |

> 요약: GPL 계열은 공개 의무를 전파하고, MIT·Apache는 공개 의무가 없되 특허 조항 유무로 구분된다.

## Ⅲ. 동작원리 및 흐름도

```text
오픈소스 코드 포함 -> 배포 형태 판단(링크/결합/수정)
  -> 카피레프트 여부 확인
  -> 소스 공개 의무 이행 또는 퍼미시브 고지 유지
  -> 특허 조항 확인(Apache 2.0 특허 부여) -> 상용 배포
```

| 단계 | 처리 내용 | 검증 기준 |
|:---:|:---|:---|
| 1 | 사용 코드의 라이선스 식별 | SBOM·라이선스 스캔 결과 |
| 2 | 카피레프트 전파 범위 판단(정적/동적 링크) | 결합 방식, 배포 여부 |
| 3 | 공개 의무 또는 고지 의무 이행 | 소스 공개, NOTICE 파일 포함 |
| 4 | 특허 조항 확인 후 상용 배포 결정 | 특허 부여 범위, 소송 종료 조건 |

> 요약: 결합 방식과 배포 여부를 먼저 판단한 뒤 공개 의무 또는 고지 의무를 이행하고 특허 조항을 최종 확인한다.

## Ⅳ. 특징

| 구분 | GPL | MIT | Apache 2.0 | 판단 포인트 |
|:---|:---|:---|:---|:---|
| 라이선스 성격 | 카피레프트 | 퍼미시브 | 퍼미시브 | 카피레프트만 재배포 시 소스 공개 의무 발생 |
| 폐쇄 소스 결합 | 불가(공개 의무 전파) | 가능 | 가능 | 상용 폐쇄형 제품은 MIT·Apache 선호 |
| 특허 조항 | GPLv3에 특허 보복 조항 존재 | 명시적 특허 조항 없음 | 특허 부여 + 소송 시 라이선스 종료 조항 | 특허 분쟁 대비는 Apache 2.0이 유리 |
| 고지 의무 | 소스 코드·라이선스 사본 제공 | 저작권 고지·라이선스 문구 유지 | 저작권 고지 + NOTICE 파일 유지 | Apache는 고지 의무가 상대적으로 더 구체적 |

> 요약: 폐쇄형 상용화에는 MIT·Apache가 적합하며, 특허 리스크를 명시적으로 관리하려면 Apache 2.0이 유리하다.

## Ⅴ. 심화 비교 및 적용 판단

| 구분 | GPL | MIT | Apache 2.0 | 선택 기준 |
|:---|:---|:---|:---|:---|
| 구조 | 강한 카피레프트 전파 | 최소 제약 퍼미시브 | 특허 조항 포함 퍼미시브 | 공개 생태계 확산 목적이면 GPL |
| 비용/사업 위험 | 상용 폐쇄 제품 결합 시 공개 의무 위반 위험 | 특허 분쟁 시 보호 조항 부재 | 특허 소송 억지력 확보 | 특허 리스크 관리가 중요하면 Apache 2.0 |
| 운영/거버넌스 | 라이선스 준수 감사 필요 | 고지 누락 관리 필요 | NOTICE 파일 관리 필요 | 사내 OSS 정책에 라이선스별 승인 절차 필요 |

> 요약: 공개 생태계 기여는 GPL, 상용 결합은 MIT, 특허 리스크 관리가 중요한 상용 결합은 Apache 2.0을 선택한다.

| 리스크 | 원인 | 대응 방안 | 확인 지표 |
|:---|:---|:---|:---|
| GPL 오염 | GPL 코드를 상용 폐쇄 제품에 정적 링크 | 라이선스 스캔, LGPL/퍼미시브 대체 검토 | GPL 코드 포함 건수 |
| 특허 분쟁 | MIT 코드 사용 시 특허 보호 부재 | Apache 2.0 대체 라이브러리 검토, 특허 조사 | 특허 소송 리스크 평가 결과 |
| 라이선스 충돌 | 서로 다른 라이선스 코드 혼용 | 라이선스 호환성 매트릭스 적용 | 호환성 검토 완료율 |

> 요약: 오픈소스 라이선스 리스크는 정적 링크 여부, 특허 조항 유무, 라이선스 호환성 검토로 통제한다.

| 점검 항목 | 목표 기준 | 측정 방법 |
|:---|:---|:---|
| 라이선스 식별 | 전체 의존성의 라이선스 식별률 100% | SBOM·SCA 스캔 결과 |
| 정책 준수 | GPL 계열 코드 승인 절차 준수율 | 사내 OSS 승인 대장 |
| 고지 이행 | NOTICE·저작권 고지 포함률 | 배포본 점검 |

> 요약: 도입 후 성공 여부는 라이선스 식별률, 승인 절차 준수율, 고지 이행률로 판단한다.

## Ⅵ. 실무 적용 및 결론

**적용 방안 3개 (필수 — 단계별 또는 항목별):**
1. 단기: SCA(Software Composition Analysis) 도구로 전체 의존성 라이선스를 식별하고 GPL 계열 코드 사용 여부를 점검함
2. 중기: 상용 폐쇄 제품에는 MIT·Apache 2.0 계열 라이브러리를 우선 채택하고 특허 리스크는 Apache 2.0으로 관리함
3. 장기: 사내 OSS 거버넌스 정책을 수립해 라이선스별 승인 절차와 호환성 매트릭스를 표준화함

**결론 (2줄):**
- 기술사 판단: 공개 확산이 목적이면 GPL, 상용 결합·특허 리스크 관리가 목적이면 Apache 2.0을 우선 선택함
- 향후 방향: AI 모델·데이터셋 라이선스(RAIL 등) 확산에 맞춰 코드 라이선스 정책을 모델·데이터까지 확장해야 함
