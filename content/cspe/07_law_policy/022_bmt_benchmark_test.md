# 📖 【암기용】 개념 완전 이해

## 한눈에
- **개요**: BMT(Benchmark Test)는 정보화 사업에서 제품·시스템을 도입하기 전, **실제 부하 조건**에서 성능·기능·안정성을 **정량 측정**해 요구사항 충족 여부를 검증하는 **사전 성능 검증 절차**다.
- **왜 필요한가**: 카탈로그 스펙(제안서 수치)과 실제 운영 환경 성능은 다를 수 있다. 도입 후 SLA 미달·재구축이 발생하면 비용이 수배 이상 증가하므로, 사전에 실측으로 걸러내야 한다.
- **핵심 직관**: 자동차를 사기 전 시승(test drive)을 통해 카탈로그 연비와 실제 주행 성능 차이를 확인하는 절차다.

## 핵심 용어 정리 (내부에 등장하는 것들)

| 용어/표기 | 의미 | 비유·예 |
|:---|:---|:---|
| BMT (Benchmark Test) | 도입 전 실측 성능 검증 절차 | 시승·시식 평가 |
| TPS (Transactions Per Second) | 초당 처리 트랜잭션 수 | 초당 주문 처리 건수 |
| 응답시간 (Response Time) | 요청 후 결과 수신까지 소요 시간 | 주문 후 음식 나오는 시간 |
| 가용성 (Availability) | 장시간 부하에서 서비스 정상 비율(예: 99.9%) | 24시간 영업 가능 비율 |
| 부하 시나리오 | 실사용 패턴을 재현한 테스트 조건 | 점심 피크 시간대 시뮬레이션 |
| 테스트베드 | BMT용 하드웨어·네트워크 환경 | 모형 도로 |
| 부하테스트 도구 | 동시 사용자·트랜잭션 부하를 생성하는 SW | JMeter·nGrinder 등 |
| 평가위원회 | 발주기관·외부 전문가가 결과를 심사하는 위원회 | 시승 심사 패널 |
| SLA (Service Level Agreement) | 서비스 수준 합의 기준 | 최소 연비 보증 |

## 깊이 이해
- **배경·문제의식**: 제안서 스펙만으로 제품을 선정하면 실사용 환경에서 TPS 미달·장애 빈발 문제가 뒤늦게 드러난다. 특히 공공 정보화 사업에서 도입 후 재구축은 수억~수십억 원의 예산 낭비로 이어진다. 이를 방지하기 위해 도입 전 실측 검증 절차가 제도화됐다.
- **작동 원리**: ① BMT 계획서를 작성해 목표 지표(TPS·응답시간·가용성·오류율)와 부하 시나리오를 사전 정의한다. ② 운영 환경과 유사한 테스트베드를 구성하고 부하테스트 도구(JMeter·nGrinder 등)로 동시 사용자 부하를 인가한다. ③ 측정 결과를 목표 기준과 대조해 충족 여부를 판정한다. ④ 평가위원회(발주기관·제3자 전문가)가 반복 측정 일관성·이상치를 검토하고 최종 도입 여부를 결정한다.
- **비유**: 신입사원 채용 시 이력서(카탈로그 스펙)만 보지 않고 실무 과제(BMT)를 시켜 실제 역량을 확인하는 방식이다. 이력서가 아무리 화려해도 과제를 못 풀면 탈락한다.
- **구체 예시**: 공공 민원 시스템 도입 BMT에서 목표 TPS 1,000, 응답시간 200ms 이내, 가용성 99.9%를 설정한다. 동시 사용자 500명 시나리오로 1시간 부하를 인가해 평균 응답시간 180ms·TPS 1,050·오류율 0.05%를 측정했다면 기준을 충족한 것이다.
- **흔한 오해·주의점**: ① BMT 통과가 운영 환경 전체 안정성을 보장하지는 않는다 — 테스트베드와 운영 환경의 하드웨어·네트워크 차이로 결과가 달라질 수 있다. ② BMT는 '제품 성능 실측'이고, 기술성 평가(021)는 '수행사 역량 심사' — 별개 절차이며 대규모 사업에서 병행된다. ③ 1회 측정만으로는 신뢰도가 낮다 — 반복 측정과 통계적 신뢰구간(95% CI) 적용이 필요하다.

## 연결 개념
- **SW 기술성 평가 (021)**: 역량 심사(서면·발표)와 BMT(성능 실측)는 별개 절차로 병행됨
- **SLA·성능테스트**: BMT 목표 지표가 계약 SLA로 이어지며, 성능·부하·스트레스 테스트는 BMT의 세부 기법
- **SW 대가 산정 (020)**: 대가 산정 → 기술성 평가 → BMT → 계약 체결로 이어지는 발주 흐름

# 📝 【답안용】 시험 답안 템플릿

## 핵심 인사이트 (3줄 요약)

> 1. **본질**: BMT는 도입 전 제품·시스템 성능을 실제 부하 조건에서 정량 측정해 요구사항 충족 여부를 검증하는 절차임.
> 2. **가치**: 카탈로그 스펙과 실사용 성능 간 괴리를 사전에 걸러내 재구축·SLA 미달 위험을 줄임.
> 3. **판단 포인트**: 테스트베드의 운영 환경 재현도와 반복 측정 일관성이 BMT 결과의 신뢰도를 좌우함.

## 출제 의도 및 답안 포인트

| 출제 의도 | 반드시 짚을 핵심 | 감점 회피 포인트 |
|:---|:---|:---|
| BMT 절차·지표 이해 | 계획서·시나리오·측정·평가위원회 | "성능 테스트한다" 수준 서술 |
| 정량 지표 이해 | TPS·응답시간·가용성·오류율 | 지표 없이 추상적 서술 |
| 신뢰성 확보 방안 | 환경 재현·반복 측정·제3자 검증 | 1회성 측정만 언급 |

> 요약: 시나리오 설계와 정량 지표를 구체적으로 보이고, 결과 신뢰성 확보 절차를 짚어야 함.

## Ⅰ. 개요 및 필요성

- 개요: 도입 전 제품·시스템 성능을 실제 부하 조건에서 정량 측정해 요구사항 충족을 검증하는 절차임
- 배경: 제안서 스펙과 실사용 성능 간 괴리로 도입 후 SLA 미달·재구축 사례가 반복됨
- 필요성: 목표 TPS·응답시간·가용성을 사전 실측해 재구축·장애 위험을 예방할 필요

---

## Ⅱ. 구조 및 구성요소

```text
요구사항 정의 -> BMT 계획서 작성(지표·시나리오)
  -> 테스트베드 구성 -> 부하 인가·측정
  -> 기준 대비 판정 -> 평가위원회 검토 -> 도입 결정
```

| 구성요소 | 역할 | 특이사항 |
|:---|:---|:---|
| BMT 계획서 | 목표 지표(TPS·응답시간·가용성)·시나리오·일정 정의 | 발주기관 사전 승인 |
| 부하 시나리오 | 실사용 패턴 재현(동시 사용자·트랜잭션 비율) | 피크 타임 시뮬레이션 포함 |
| 테스트베드·측정 도구 | 운영 유사 환경 구성, JMeter·nGrinder 등 활용 | 환경 재현도가 결과 신뢰도 결정 |
| 평가위원회 | 발주기관·제3자 전문가가 결과 적합성 최종 심사 | 반복 측정 일관성·이상치 검토 |

> 요약: 계획서·시나리오·테스트베드·평가위원회를 통해 도입 전 성능을 정량 검증하는 구조임.

---

## Ⅲ. 동작원리 및 흐름도

```text
목표 지표 확정 -> 테스트베드 구성(운영 유사 환경)
  -> 부하 인가(동시 사용자·피크 시나리오) -> 지표 측정(TPS/응답시간/오류율)
  -> 기준 대비 판정 -> 반복 측정·신뢰구간 확인 -> 평가위원회 승인 -> 도입 결정
```

1. 목표·시나리오 확정: 목표 TPS·응답시간·가용성을 수치로 확정하고 부하 시나리오를 설계함
2. 테스트베드·부하 인가: 운영 환경과 유사한 테스트베드를 구성하고 부하테스트 도구로 동시 사용자 부하를 인가함
3. 지표 측정·판정: 처리량·응답시간·오류율을 측정하고 목표 기준 대비 충족 여부를 판정함
4. 검증·승인: 반복 측정으로 일관성을 확인하고, 평가위원회가 이상치를 검토해 최종 도입 여부를 결정함

> 요약: 목표 확정 → 부하 인가 → 지표 측정 → 반복 검증 → 위원회 승인의 순서로 도입 여부를 결정함.

---

## Ⅳ. 특징
- 실측 기반 검증: 카탈로그 스펙이 아닌 실제 부하에서 성능을 측정해 서류 심사 대비 신뢰도가 높음
- 사전 위험 제거: 도입 후 SLA 미달·재구축 위험을 사전에 걸러내 예산 낭비를 예방함
- 환경 재현 한계: 테스트베드와 운영 환경의 하드웨어·네트워크 차이로 측정치가 왜곡될 수 있음
- 반복 측정 필수: 1회 측정만으로는 재현성이 보장되지 않아 반복 측정과 통계적 신뢰구간 적용이 필요함

> 요약: 실측 기반 사전 검증 효과가 크지만, 환경 재현성과 반복 측정으로 결과 신뢰도를 확보해야 함.

## Ⅴ. 심화 비교 및 적용 판단

| 구분 | 서류 심사(스펙 검토) | BMT(실측 검증) | 선택 기준 |
|:---|:---|:---|:---|
| 검증 방식 | 제안서 기재 수치 확인 | 실제 부하에서 정량 측정 | 장애 영향도 |
| 신뢰도 | 카탈로그 스펙 의존, 검증 한계 | 실측 데이터 기반, 재현 오차 존재 | 핵심 업무 시스템 여부 |
| 비용 | 검증 비용 낮음 | 테스트베드·도구·인력 비용 발생 | 재구축 비용 대비 BMT 비용 |

> 요약: 장애 영향이 큰 핵심 시스템일수록 서류 심사보다 BMT 실측 검증을 우선 적용함.

**리스크·대응:**
- 환경 재현 오차: 테스트베드와 운영 환경 차이로 결과 왜곡 → 운영 환경 동일 사양 테스트베드 구성 (지표: HW·네트워크 사양 일치율)
- 시나리오 편향: 유리한 조건만 측정해 결과 과대 평가 → 발주기관이 시나리오를 사전 승인·피크 시나리오 의무 포함 (지표: 시나리오 요구사항 반영률)
- 1회성 측정: 단발 테스트로 재현성 미확인 → 최소 3회 반복 측정, 95% 신뢰구간 적용 (지표: 측정 간 편차율)

**점검 지표:**
- 처리량: 목표 TPS 달성 여부 — 부하테스트 도구 로그
- 응답성: 목표 응답시간(p95) 이내 — APM·트랜잭션 로그

---

## Ⅵ. 실무 적용 및 결론

**적용 방안 3개:**
1. BMT 계획서 표준화: 목표 TPS·응답시간·가용성 기준을 수치로 명시하고 피크 시나리오를 의무 포함해 발주기관이 사전 승인함
2. 테스트베드 재현성 확보: 운영 환경과 동일 사양의 테스트베드를 구성하고, HW·네트워크 일치율을 사전 점검함
3. 반복 측정·통계 검증: 최소 3회 반복 측정으로 95% 신뢰구간을 확인하고, 평가위원회가 이상치를 검토해 최종 판정함

**결론:**
- 기술사 판단: 장애 영향도가 큰 핵심 정보화 사업은 서류 심사에 그치지 않고 BMT 실측 검증을 의무화해야 함
- 향후 방향: 클라우드 기반 자동화 부하테스트 도구를 활용해 BMT 반복 검증 주기를 단축하고 재현성을 높여야 함
