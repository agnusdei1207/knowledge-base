## Ⅰ. 개요
- **정의**: SW 개발-빌드-배포-운영 전 과정에서 구성요소 무결성을 보장하는 보안 체계임
- **배경/필요성**: 오픈소스·서드파티 의존이 증가하며 한 구성요소 침해가 전체 공급망에 전파됨
- **비유**: 식품 유통 과정 전체를 감시하는 HACCP처럼 SW 공급 경로를 통제하는 것임

| 출제 의도 | 반드시 짚을 핵심 | 감점 회피 포인트 |
|:---|:---|:---|
| 공급망 공격 방어 전략 | SBOM(111 참조), 서명, 무결성 검증 연계 | 개발 단계뿐 아니라 빌드·배포 단계 포함 |

> 요약: SW 생산-유통 전 구간의 무결성·신뢰성을 확보하는 보안 프레임워크임

## Ⅱ. 구성요소
```text
Supply Chain Security
 +-- Source Integrity ----- 소스코드 변조 방지
 +-- Build Integrity ------ 빌드 환경 격리·재현
 +-- Dependency Mgmt ------ 의존성 검증(SBOM 연계)
 +-- Distribution Security - 서명·해시 검증 배포
 +-- Runtime Monitoring ---- 배포 후 이상 탐지
```

| 구성요소 | 설명 | 비유 |
|:---|:---|:---|
| Source Integrity | 코드 서명·커밋 검증으로 변조 차단 | 봉인된 원재료 |
| Build Integrity | 격리 환경에서 재현 가능한 빌드 수행 | 무균실 제조 |
| Runtime Monitoring | 배포 후 행위 이상을 탐지·대응 | 출하 후 리콜 감시 |

> 요약: 소스-빌드-의존성-배포-런타임 5계층 방어 체계임

## Ⅲ. 절차
```text
코드 커밋 서명 --> 격리 빌드 --> 아티팩트 서명 --> 배포 검증
```
- 1단계: 개발자가 GPG/Sigstore로 커밋·태그 서명
- 2단계: 격리된 CI 환경에서 재현 가능 빌드(Reproducible Build) 수행
- 3단계: 빌드 산출물에 디지털 서명·해시 부여(SLSA 프레임워크 적용)
- 4단계: 배포 시점에 서명·해시 검증 후 무결성 확인된 아티팩트만 릴리스

> 요약: 서명-격리빌드-아티팩트서명-배포검증의 4단계 신뢰 체인임

## Ⅳ. 문제점
- 의존성 공격: 악성 패키지가 공개 저장소에 등록되면 자동으로 빌드에 포함됨
- 빌드 변조: CI/CD 파이프라인이 침해되면 서명 전 단계에서 코드 삽입 가능
- 검증 비용: 모든 구성요소의 출처·무결성을 실시간 검증하면 배포 지연 발생

> 요약: 의존성 오염, 빌드 침해, 검증 부하가 핵심 위협임

## Ⅴ. 개선방안
1. 단기: 프라이빗 미러 저장소 운영으로 외부 패키지 사전 검증
2. 중기: SLSA Level 3 이상 빌드 보안 체계 적용으로 빌드 변조 차단
3. 장기: 정책 기반 자동 검증 게이트를 파이프라인에 내재화하여 지연 최소화

> 요약: 저장소 격리, 빌드 보안 강화, 자동 검증으로 공급망을 방어함

## Ⅵ. 전망
- 발전 방향: SLSA·SBOM 의무화와 함께 공급망 보안이 규제 영역으로 확대됨
- 기술사적 판단: Zero Trust 원칙이 네트워크에서 SW 공급망으로 확장 중임
- 기술사 제언: 개발 조직 내 공급망 보안 거버넌스를 DevSecOps에 통합할 필요
