## 미리 알고가기

- Iceberg는 데이터 파일을 디렉터리가 아니라 스냅샷 메타데이터로 추적하는 오픈 테이블 포맷임
- Manifest는 데이터·삭제 파일의 경로, 파티션, 통계와 스냅샷 상태를 기록함
- Manifest List는 한 스냅샷이 참조하는 Manifest와 파티션 통계를 나열함
- 필드 ID는 열 이름과 분리된 고유 식별자로 열 추가·삭제·이름 변경의 정확성을 유지함
- 숨은 파티셔닝은 논리 열 조건을 물리 파티션 변환에 매핑해 사용자가 파티션 열을 직접 관리하지 않게 함
- Delete File은 기존 데이터 파일을 즉시 재작성하지 않고 삭제 위치나 키를 별도 기록함

## 작성 근거(검토용)

- Iceberg는 스냅샷·Manifest 계층·필드 ID·숨은 파티셔닝·스키마·파티션 진화를 핵심으로 선정함
- 비교표는 Hive식 파일 테이블과 파일 추적·파티션·스키마·커밋·질의 계획·적합 업무를 대비함
- 절차는 데이터 파일과 Manifest 작성부터 카탈로그 포인터 교체까지 원자적 커밋 흐름을 설명함
- 제목부터 결론까지 모든 문장·표 셀·요약을 5회 전수 검수해 메타데이터 계층의 역할을 구분함

## Ⅰ. 개요

- **정의/개념**: Iceberg는 스냅샷·Manifest·필드 ID·파티션 명세로 객체 스토리지 파일 변경과 테이블 진화를 관리하는 오픈 테이블 포맷임
- **배경/필요성**: 대규모 파일 테이블의 목록 조회와 파티션 의존을 줄이고 여러 엔진이 동일한 스키마·스냅샷을 읽기 위해 계층형 메타데이터가 필요함

## Ⅱ. 특징

- 테이블 메타데이터가 스키마·파티션 명세·정렬 순서와 스냅샷 이력을 관리함
- Snapshot이 Manifest List를, Manifest가 데이터·삭제 파일과 열 통계를 참조함
- 필드 ID로 열을 추적해 이름 변경과 중첩 스키마 진화에서 열 오인식을 방지함
- 숨은 파티셔닝이 논리 조건을 파티션 변환에 연결하고 파티션 명세를 버전별로 진화시킴
- 카탈로그의 현재 메타데이터 포인터를 원자적으로 교체하고 충돌 시 새 기준에서 커밋을 재시도함

## Ⅲ. 종류 및 비교

| 판단 기준 | Hive식 파일 테이블 | Apache Iceberg |
|:---|:---|:---|
| 파일 추적 | 디렉터리·파티션 경로를 목록 조회 | Snapshot·Manifest가 파일을 명시적으로 추적 |
| 파티션 사용 | Writer와 질의가 파티션 열을 직접 관리 | 숨은 파티션 변환과 파티션 명세 진화 |
| 스키마 식별 | 열 이름·위치 의존 가능 | 영구 필드 ID로 열 추적 |
| 쓰기 확정 | 파일·메타스토어 갱신을 작업이 조정 | 새 메타데이터 포인터의 원자적 교체 |
| 질의 계획 | 디렉터리·파티션 목록과 파일 통계 사용 | Manifest 파티션·열 통계로 파일 제외 |
| 적합 업무 | 정적 파티션의 단순 배치 테이블 | 다중 엔진·스키마 진화·대규모 파일 테이블 |

> 요약: Iceberg는 스냅샷과 Manifest로 파일을 추적하고 필드 ID·숨은 파티셔닝으로 테이블 진화를 관리함.

## Ⅳ. 구성요소 및 구조

| 구성요소 | 설명 |
|:---|:---|
| Catalog | 테이블 이름과 현재 Metadata File 위치를 원자적으로 관리함 |
| Metadata File | 스키마·파티션 명세·정렬 순서·속성·스냅샷 이력을 저장함 |
| Snapshot·Manifest List | 특정 커밋의 파일 집합과 참조할 Manifest 목록을 정의함 |
| Manifest File | 데이터·삭제 파일의 파티션·통계·추가·삭제 상태를 기록함 |
| Data·Delete File | 실제 행과 위치·키 기반 삭제 정보를 각각 저장함 |
| Maintenance | Manifest 병합·데이터 파일 재작성·스냅샷 만료·고아 파일 제거를 수행함 |

```text
Catalog -> Metadata -> Snapshot -> Manifest List -> Manifest -> Data·Delete Files
```

> 요약: Catalog의 현재 Metadata가 Snapshot·Manifest 계층을 통해 유효한 데이터·삭제 파일 집합을 결정함.

## Ⅴ. 원리 및 절차 흐름도

```text
기준 스냅샷 읽기 -> 파일·Manifest 작성 -> 새 Metadata 생성 -> 충돌 검사 -> 포인터 교체
```

1. **기준 읽기**: Writer가 Catalog에서 현재 Metadata와 Snapshot을 가져옴
2. **파일 작성**: 변경 데이터·삭제 파일과 이를 설명하는 Manifest를 생성함
3. **메타데이터 생성**: 새 Snapshot·Manifest List와 테이블 이력을 포함한 Metadata를 작성함
4. **충돌 검사**: 현재 Catalog 포인터와 Writer의 기준 Metadata가 같은지 확인함
5. **포인터 교체**: 충돌이 없으면 Catalog가 새 Metadata를 현재 테이블 상태로 확정함

> 요약: Iceberg는 새 파일과 메타데이터를 만든 뒤 Catalog 포인터를 원자적으로 바꿔 스냅샷을 커밋함.

## Ⅵ. 실무 사례

1. 이벤트 분석 테이블은 시간 열의 숨은 파티셔닝을 적용하고 스캔 파일 수·질의 계획 시간을 확인함
2. 다중 엔진 공유 테이블은 필드 ID 기반 스키마 진화를 적용하고 읽기 오류·커밋 충돌을 확인함

## Ⅶ. 결론

- Iceberg는 다중 엔진 호환·메타데이터 규모·파티션 진화·행 삭제 방식과 유지관리 비용으로 선택해야 함
