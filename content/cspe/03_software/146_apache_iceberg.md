## 핵심 인사이트 (3줄 요약)
- 넷플릭스(Netflix)가 수십 페타바이트(PB)의 데이터 레이크를 다루다가 기존 Hive 파티션 구조가 너무 느려서 뻗어버리자, **"폴더(디렉터리) 중심의 탐색"을 버리고 "파일 메타데이터 추적" 방식으로 완전히 뒤엎어 만든 오픈 테이블 포맷**.
- 거대한 S3 레이크에 ACID 트랜잭션과 시간 여행(Time Travel) 기능을 부여하는 점은 Delta Lake와 같으나, Iceberg는 **특정 기업(Databricks)이나 엔진(Spark)에 종속되지 않는 100% 순수 오픈소스**의 독립성을 강력히 표방함.
- "엔진(Spark, Trino, Snowflake)은 네 맘대로 바꿔 써, 데이터 포맷은 Iceberg로 통일해!"라는 철학 덕분에, 현재 글로벌 클라우드 생태계(AWS, Snowflake 등)에서 가장 폭넓게 지지받는 테이블 포맷의 대세 1위임.

## Ⅰ. 개요 및 필요성
- **개요**: 거대한 데이터 레이크(S3 등)를 마치 SQL 데이터베이스의 테이블처럼 안정적이고 초고속으로 다룰 수 있게 해주는 고성능 오픈 테이블 포맷(Open Table Format).
- **필요성**: 기존 하둡 생태계의 표준이었던 Apache Hive는 데이터를 찾을 때 "2024년 폴더 ➡️ 7월 폴더 ➡️ 5일 폴더" 식으로 디렉터리 경로를 스캔했음. 넷플릭스는 폴더 안에 파일이 수만 개가 넘어가니 `ls` (폴더 읽기) 명령만 내리는 데 수십 분이 걸려 쿼리가 멈춤. "폴더 구조에 의존하지 말고, 파일 주소 10만 개를 텍스트 파일(메타데이터)에 적어두고 0.1초 만에 바로 찾아가자!"는 발상에서 탄생함.
---
## Ⅱ. 아키텍처 및 핵심 원리
- **1. 트리(Tree) 구조의 메타데이터 설계**:
  - Iceberg의 핵심은 데이터를 저장하는 방식이 아니라, **"데이터가 어디 있는지 완벽하게 추적하는 장부 구조"**임.
  - `Metadata 파일 (전체 버전 관리)` ➡️ `Manifest List (스냅샷 상태)` ➡️ `Manifest 파일 (실제 데이터 파일 주소)` 형태의 3단 트리 구조로 완벽히 격리하여 S3의 느린 디렉터리 스캔을 100% 우회함.
- **2. Hidden Partitioning (숨겨진 파티셔닝)**:
  - 구식 Hive는 파티션을 바꿀 때(`시간` ➡️ `일` 단위) 전체 데이터를 뜯어고쳐야 했고(개발자 노가다), SQL을 날릴 때 개발자가 `WHERE date='2024-07'` 처럼 파티션 컬럼을 무조건 적어야 했음.
  - Iceberg는 테이블 밑단에서 파티션 구조를 마음대로 진화(Partition Evolution)시켜도, 사용자는 `WHERE timestamp > '어제'` 라고만 치면 엔진이 알아서 파티션 포맷을 변환해 찾아주는 천재적인 추상화를 제공함.
- **3. 독립성과 개방성 (Engine Agnostic)**:
  - Delta Lake가 태생적으로 Spark에 강하게 묶여 있다면, Iceberg는 저장 규격일 뿐임. Spark, Trino, Flink, Snowflake, AWS Athena 등 어떤 쿼리 엔진이든 완벽하게 붙어서 동일한 ACID 성능을 냄.

```text
[ Hive(디렉터리 방식) vs Iceberg(메타데이터 방식) 파일 찾기 차이 ]

 🐌 [ 기존 Hive 방식 ] 
 쿼리: "한국 유저 데이터 줘!"
 동작: S3에서 `country=KR` 폴더를 찾음 ➡️ 그 안의 1만 개 파일 리스트를 `ls` 명령으로 전부 다 긁어옴 ➡️ (S3는 API 호출이 느려서 30초 걸림) ➡️ 쿼리 시작.

 🚀 [ Apache Iceberg 방식 ]
 쿼리: "한국 유저 데이터 줘!"
 동작: Iceberg 메타데이터 파일(장부)을 1개 딱 염 ➡️ "한국 유저 파일은 A, B, C에 있습니다"라고 적혀 있음 ➡️ (디렉터리 스캔 전혀 안 함, 0.1초 소요) ➡️ 쿼리 시작!
```

## Ⅲ. 비교 및 연결
| 구분 | Delta Lake | Apache Iceberg | Apache Hudi |
|---|---|---|---|
| **탄생 배경** | Databricks 주도 (상업 생태계 강력) | **Netflix 주도 (오픈 생태계 강력)** | Uber 주도 (실시간/스트리밍) |
| **특장점** | Spark 최적화 극강, 튜닝 쉬움 | **어떤 엔진을 붙여도 호환성 최고** | UPDATE/UPSERT (CDC) 성능 최고 |
| **메타데이터 구조**| 단일 트랜잭션 로그 (JSON) | **Tree 구조의 Manifest 파일** | 타임라인 기반 (커밋 로그) |
| **산업계 지지** | MS Azure, Databricks | **AWS, Snowflake, Cloudera 대동단결**| 구글 GCP 진영 선호 |

## Ⅳ. 실무 적용 및 기술사 판단
- **클라우드 벤더 종속성(Lock-in) 탈피 아키텍처**: 실무 데이터 아키텍트가 Iceberg를 선택하는 가장 큰 이유는 '벤더 락인 방지'임. 데이터를 S3에 Iceberg 포맷으로 저장해 두면, 오늘은 AWS Athena로 쿼리를 치고, 내일 쿼리 요금이 비싸지면 3rd Party인 Snowflake로 엔진만 갈아 끼워도 아무런 마이그레이션(데이터 이동) 비용 없이 똑같이 쿼리가 동작함. 즉, "스토리지와 컴퓨팅의 완벽한 이혼(Separation)"을 실현하는 핵심 키(Key)임.
- **Row-Level Update와 Merge-on-Read**: GDPR(개인정보 보호법) 때문에 특정 사용자의 데이터를 지워달라는 요청이 오면, 거대한 레이크 파일(Parquet)을 통째로 뜯어고치는 건 너무 비쌈. Iceberg는 "이 파일에서 3번째 줄 데이터는 무효(Delete)야"라고 적힌 아주 작은 가벼운 파일(Delete File)만 슬쩍 추가해 두면, 엔진이 읽을 때 알아서 합쳐서(Merge-on-Read) 안 보여주는 최적화 기능을 제공하여 빅데이터 수정의 비용을 극적으로 낮춤.

## Ⅴ. 기대효과 및 결론
- 넷플릭스의 스토리지 지옥을 구원하기 위해 만들어진 '메타데이터 튜닝'의 걸작으로, 대용량 데이터 레이크를 다루는 컴퓨터 공학적 접근법을 디렉터리(Folder)에서 장부(Manifest) 체계로 완전히 바꿔놓았음.
- 글로벌 IT 기업들이 특정 벤더(Databricks)의 독주를 막기 위해 대동단결하여 밀어주는 '중립 지대 오픈 테이블 포맷'으로, 미래의 레이크하우스 아키텍처 표준 전쟁에서 가장 승리에 가까운 포맷임.

### 👶 어린이를 위한 3줄 비유 설명
1. 기존 하둡(Hive) 방식은 도서관에서 '역사책'을 찾으려면, 3층 역사 코너로 가서 책꽂이에 꽂힌 수천 권의 책 제목을 일일이 다 눈으로 확인해야 했어요 (엄청 느림).
2. **아파치 아이스버그(Iceberg)**는 1층 안내데스크에 있는 완벽한 '컴퓨터 장부(메타데이터)'예요!
3. 책꽂이까지 갈 필요도 없이 컴퓨터 장부 딱 한 번만 검색하면, "세종대왕 책은 3층 5번 줄 7번째 책상에 있습니다!"라고 바로 0.1초 만에 알려주는 마법의 장부랍니다!
