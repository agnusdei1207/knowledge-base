# 📖 【암기용】 개념 완전 이해

> 목적: 이 개념을 처음 보는 사람도 완벽히 이해하게 만든다. 시험 답안 양식이 아니라, 이해를 위한 친절한 설명이다.

## 한눈에
- **개요**: **DDD(도메인 주도 설계)**는 데이터베이스 스키마나 프레임워크가 아니라 **도메인(비즈니스 업무 규칙)**을 소프트웨어 설계와 코드 구조의 중심에 두는 방법론으로, 큰 시스템을 나누는 **전략적 설계**와 코드 내부를 모델링하는 **전술적 설계**로 구성된다.
- **왜 필요한가**: 비즈니스 규칙(예: "VIP 회원은 주문 취소 시 포인트 반환 안 함")이 Controller, SQL 저장 프로시저, Service 여기저기에 흩어져 있으면 그 규칙 하나를 바꾸려 해도 코드 전체를 다 뒤져야 한다. DDD는 이 규칙을 도메인 객체 안에 모아 캡슐화한다.
- **핵심 직관**: 전술적 설계의 핵심 구분은 "식별자(ID)로 구별하는가, 값(Value) 자체로 구별하는가"다. 이 구분이 Entity와 Value Object를 가른다.

## 핵심 용어 정리 (내부에 등장하는 것들)

| 용어 | 의미 | 비유 |
|:---|:---|:---|
| 유비쿼터스 언어 | 기획자와 개발자가 합의해 코드 변수명까지 그대로 쓰는 공통 용어 | 같은 설계도를 보는 건축주와 시공사 |
| 전략적 설계 | 시스템을 여러 도메인(바운디드 컨텍스트)으로 나누는 상위 설계 | 회사 조직도를 부서로 나누는 일 |
| 전술적 설계 | 한 도메인 내부를 Entity·VO·Aggregate로 모델링하는 하위 설계 | 한 부서 안의 업무 분장 |
| Entity | 식별자(ID)로 구별되며 속성이 변해도 같은 대상으로 취급되는 객체 | 주민등록번호 — 개명해도 동일인 |
| Value Object (VO) | 식별자가 없고 속성 값 전체가 같아야 동일하게 취급되는 불변 객체 | 만 원짜리 지폐 — 어느 지폐든 만 원이면 동일 |
| Aggregate | 데이터 일관성을 지키기 위해 하나의 트랜잭션 단위로 묶은 Entity·VO 묶음 | 자동차 1대 (엔진·타이어·핸들의 묶음) |
| Aggregate Root | Aggregate의 유일한 외부 진입점 Entity | 자동차 키 — 반드시 이걸 통해서만 조작 |
| Repository | Aggregate를 저장·조회하는 인터페이스(영속성 기술을 감춤) | 도서관 대출 창구 |
| Domain Event | 도메인 상태 변화를 알리는 과거분사형 이벤트 (예: OrderCreated) | 부서 간 업무 완료 통지 메일 |

## 깊이 이해

### 배경 — 데이터 중심 설계에서 도메인 중심 설계로
- 전통적 방식은 "DB 테이블 설계 → 화면 설계 → 로직 채워넣기" 순서로 진행됐다(데이터 중심 설계). 이 방식에서는 도메인 객체가 getter/setter만 가진 껍데기(빈약한 도메인 모델, Anemic Domain Model)로 전락하고, 실제 계산 로직은 Service 클래스에 절차적으로 쌓인다. 에릭 에반스는 2003년 저서에서 이를 지적하며 도메인 모델이 곧 코드가 되어야 한다고 제안했다.

### Entity와 VO 판별 — 코드 레벨 기준
- 판별 원리: 동등성 비교를 ID로 하면 Entity, 값 전체로 하면 VO다. `Member` 클래스는 `equals()`를 `memberId`만 비교하도록 구현한다(이름이 "홍길동"에서 "홍개똥"으로 바뀌어도 `memberId`가 같으면 동일 회원). 반면 `Money(amount, currency)` 클래스는 `equals()`를 `amount`와 `currency` 필드 전부 비교하도록 구현한다 — 1만원짜리 인스턴스 2개는 메모리 주소가 달라도 논리적으로 같다.
- VO는 불변(Immutable)이어야 한다. 주소가 바뀌면 기존 `Address` 객체의 필드를 수정하는 게 아니라 새 `Address` 인스턴스를 만들어 통째로 교체한다. 필드를 하나씩 수정하게 허용하면 다른 곳에서 참조 중인 객체까지 같이 바뀌는 부작용이 생기기 때문이다.

### Aggregate와 트랜잭션 경계 — 워크드 예제
- `Order` Aggregate 안에 `Order`(Root Entity), `OrderLine`(하위 Entity, 상품별 수량), `ShippingAddress`(VO)가 묶여 있다고 하자. 배송지를 변경할 때 외부 코드는 `shippingAddress.setStreet(...)`처럼 하위 객체를 직접 고치지 않고 반드시 `order.changeShippingAddress(newAddress)`를 호출한다. Aggregate Root(`Order`)가 이 요청을 받아 "이미 배송이 시작된 주문은 배송지 변경 불가" 같은 불변식(Invariant)을 검사한 뒤에만 하위 객체를 수정한다.
- 판별 원리(트랜잭션 경계): 1번의 DB 트랜잭션(commit)은 원칙적으로 Aggregate 1개만 수정해야 한다. 하나의 트랜잭션에서 `Order`와 `Member`(별개 Aggregate) 둘 다 수정하면 두 Aggregate가 같은 락을 공유하게 되어 동시 요청이 몰릴 때 잠금 경합이 커진다. 다른 Aggregate에 후속 처리가 필요하면 트랜잭션을 커밋한 뒤 Domain Event(`OrderCreatedEvent`)를 발행해 비동기로 처리한다(결과적 일관성).

### Rich Domain Model — Anemic과의 구체적 차이
- Anemic(빈약한) 모델: `Order` 클래스에 `getStatus()`, `setStatus()`만 있고 "주문 취소 가능 여부 판단"은 `OrderService.cancelOrder()` 안에 `if (order.getStatus() == PAID && ...) {...}`처럼 절차적으로 흩어진다.
- Rich(풍부한) 모델: 판단 로직을 `order.cancel()` 메서드 안으로 옮긴다. `cancel()` 내부에서 "결제 완료 후 24시간 이내인가", "이미 배송이 시작되지 않았는가"를 스스로 검사하고 위반 시 예외를 던진다. 판별 원리: 클래스가 상태(필드)만 갖고 판단 로직은 다른 클래스에 있다면 Anemic, 상태와 그 상태에 대한 판단 로직이 같은 클래스에 있으면 Rich다.

### 흔한 오해
- "JPA `@Entity`를 쓰면 DDD"라는 것은 오해다. JPA Entity는 영속성 기술(테이블 매핑)일 뿐이며 DDD의 Entity 개념(식별자 기반 동등성 + 도메인 로직 캡슐화)과는 별개다. 오히려 DB 테이블 구조를 그대로 `@Entity` 클래스로 옮기기만 하면 데이터 중심 설계로 회귀한 것이다.

## 연결 개념
- 헥사고날 아키텍처 — 도메인 코어(Aggregate)를 DB·프레임워크로부터 격리하는 구조적 짝
- 바운디드 컨텍스트 — 전략적 설계에서 도메인을 나누는 경계 (054에서 상세)
- CQRS — Aggregate 단위 쓰기(Command)와 조회 성능(Query) 최적화를 분리하는 보완 패턴

# 📝 【답안용】 시험 답안 템플릿

> 목적: 시험장에서 25분에 그대로 쓰는 답안 양식. 작성방식(추상표현 금지·수치·도식·문제유형 전환)을 엄격히 지킨다.
> 핵심: 이 시험은 정보를 많이 나열하는 시험이 아니라, 문제 신호어에서 출제자 의도를 읽고 핵심 논점을 선별해 쓰는 시험이다.

## 핵심 인사이트 (3줄 요약)

> 1. **본질**: 소프트웨어의 복잡성을 통제하기 위해, 기술적 관점(데이터베이스, 프레임워크)이 아닌 순수 '비즈니스 도메인(현실의 업무)'을 시스템 설계와 소스코드의 최중심(Core)에 배치하는 개발 방법론이다.
> 2. **가치**: 유비쿼터스 언어를 통해 기획(도메인 전문가)과 개발(엔지니어) 간의 커뮤니케이션 단절을 타파하고, 복잡한 비즈니스 룰을 객체 지향 모델로 완벽히 투영(Traceability)하여 변경 시 파급 효과를 최소화한다.
> 3. **판단 포인트**: 쪼개기 중심의 전략적 설계(Bounded Context)와 뭉치기 중심의 전술적 설계(Aggregate, Entity, VO) 메커니즘을 명확히 대조하고, 어그리거트 루트(Root)를 통한 트랜잭션 무결성 방어 원리를 도출해야 한다.

## 출제 의도 및 답안 포인트

| 출제 의도 | 반드시 짚을 핵심 | 감점 회피 포인트 |
|:---|:---|:---|
| 데이터 중심(Data-driven) 레거시 설계의 한계 비판 | 비즈니스 로직이 UI나 SQL에 흩어지는 파편화(Spaghetti) 리스크 | DDD를 단순히 객체 지향(OOP) 기법 중 하나로 얕게 치부 |
| 전술적 설계(Tactical Design)의 핵심 컴포넌트 도식화 | **Aggregate(군집)**와 **Aggregate Root(진입점)** 매핑 | Entity와 Value Object의 물리적 차이(식별자 유무, 가변성) 누락 |
| 실무 MSA 환경에서의 데이터 트랜잭션 정합성 제어 | 1 트랜잭션 당 1 Aggregate 수정 (비동기 이벤트 전파) | 하나의 트랜잭션 안에서 2개 이상의 어그리거트를 묶어 저장한다고 적는 치명적 에러 |

> 요약: 타이어(객체)의 공기압을 밖에서 맘대로 고치지 마라. 반드시 자동차(Aggregate Root)라는 대표를 통해서만 타이어에 접근하게 통제하라. 그래야 타이어를 고치면서 속도(비즈니스 룰)도 같이 조절하는 완벽한 무결성이 유지된다.

## Ⅰ. 개요 및 필요성

- 정의: 에릭 에반스(Eric Evans)가 제안한 패러다임으로, 비즈니스 도메인(요구사항)을 탐구하여 도출된 도메인 모델을 소프트웨어 아키텍처와 소스코드 구조에 그대로 매핑하는 설계 접근법
- 배경: 비즈니스 룰(할인율 계산 등)이 프레젠테이션(UI) 계층이나 DB Stored Procedure에 무분별하게 흩어져(Anemic Domain Model), 기획 변경 시 디버깅이 불가능해지는 기술 부채 임계점 도달
- 필요성: 전략적 설계를 통해 MSA의 분리 기준(Bounded Context)을 획정하고, 전술적 설계를 통해 순수 비즈니스 로직(Domain Model)을 영속성 인프라(DB)로부터 100% 격리(Isolation)하기 위함

## Ⅱ. DDD 전술적(Tactical) 설계 빌딩 블록 도식

DDD는 작은 데이터(VO)를 모아 객체(Entity)를 만들고, 객체들을 모아 군집(Aggregate)이라는 거대한 성을 쌓는다.

```text
[ Aggregate (군집) 기반 트랜잭션 제어 아키텍처 ]

(외부 Controller/Service)
        | (명령: "배송지 주소 변경해!")
        |
        V (절대 내부 객체 직접 찌르기 금지)
=================== < 👑 Aggregate Root (대장) > =====================
       [ 주문(Order) Entity (식별자: ID=1001) ] 
          |  (통제)                       |  (통제)
          V                               V 
  [ 주문 상품(OrderLine) Entity ]    [ 배송지(Address) Value Object ]
  (식별자: 상품ID, 변경 가능)          (식별자 없음, 시/구/동 전체 값, ❄️불변)
====================================================================
```

| 핵심 빌딩 블록 | 아키텍처적(엔지니어링) 제어 메커니즘 | 실무 튜닝 효과 |
|:---|:---|:---|
| **Entity (엔티티)** | 고유한 식별자(ID)를 가지며, 시간이 지나 내부 상태가 변해도 동일 객체로 추적됨 (예: `User`, `Order`) | 생명주기(Lifecycle) 내내 연속성(Continuity)을 가지며 데이터베이스에 영속화(Persist)됨 |
| **Value Object (값 객체)**| 식별자가 없고 오직 속성 값들의 조합으로만 의미를 가짐 (예: `Money(금액+통화)`, `Address`). **절대 변경 불가(Immutable) 원칙** 강제 | 값이 하나라도 바뀌면 객체를 아예 새로 생성(new)하여 할당. 사이드 이펙트(Side-effect) 원천 차단 |
| **Aggregate (어그리거트)**| 연관된 엔티티와 값 객체들을 데이터 일관성(Consistency) 유지를 위해 하나의 단위로 묶어놓은 논리적 트랜잭션 경계 | **동시성 락(Lock)의 범위**. 여러 테이블에 데이터가 저장되더라도 비즈니스 룰 상 1세트로 묶어 붕괴 방어 |
| **Aggregate Root (루트)** | 외부 접근을 허용하는 단 하나의 창구(진입점 엔티티). 하위 객체들의 변경 무결성을 검사하는 파사드(Facade) 역할 | 밖에서 하위 객체(배송지)를 직접 수정 불가. 오직 루트(주문)를 통해서만 변경하여 캡슐화 100% 달성 |

> 요약: DB 테이블이 5개라고 객체(Entity)를 5개 따로 노출하는 것은 최악이다. 5개를 하나의 큰 비닐봉지(Aggregate)에 담고, 비닐봉지 손잡이(Root)만 바깥으로 빼서 제공해야 데이터 무결성이 지켜진다.

## Ⅲ. 극복해야 할 시스템적 리스크 (안티패턴 및 데이터 붕괴)

도메인 모델링을 잘못하면, 껍데기만 객체 지향인 거대한 C언어 구조체(Struct) 공장으로 전락한다.

| 리스크 요인 | 발생 시나리오 및 시스템 붕괴 원인 (안티패턴) | 아키텍처 대응 방안 (실무 튜닝) |
|:---|:---|:---|
| **빈약한 도메인 모델** <br> (Anemic Domain Model) | 도메인 객체(`User`)에 `get`, `set`만 뚫어놓고 껍데기로 방치함. 실제 중요한 '할인율 로직'은 바깥의 `OrderService`에 1,000줄짜리 스파게티로 짬처리됨 | **로직의 도메인 내재화 (Rich Domain Model)**: 상태를 가진 객체가 행위(기능)도 스스로 책임지게 함. `User.calculateDiscount()`처럼 로직을 도메인 캡슐 안으로 강력히 끌어들여 Service 클래스 비대화 방어 |
| **어그리거트 간 동시성 경합 폭주** | 하나의 DB 트랜잭션 안에서 `주문(Aggregate)` 상태를 바꾸고, 동시에 억지로 `회원(Aggregate)`의 포인트까지 수정하다가 데드락(Deadlock) 파국 발생 | **1 트랜잭션 = 1 어그리거트 룰 강제**: 자신의 어그리거트만 트랜잭션(ACID)으로 저장하고, 남의 어그리거트 수정은 **도메인 이벤트(Domain Event)를 Kafka에 발행하여 비동기(Eventual)로 위임(Saga 패턴 융합)** |

> 요약: 개발자들은 습관적으로 `@Service` 클래스 안에 로직을 다 짜넣는다. DDD는 그 비즈니스 로직(계산식, 룰)을 Service에서 뜯어내서, 데이터(상태)를 쥐고 있는 Domain 객체 안으로 밀어 넣으라고 강제하는 "행위와 상태의 통합" 철학이다.

## Ⅳ. 현대 아키텍처와의 전술적 설계 융합 (Repository & Event)

도메인을 아무리 예쁘게 짜도, 결국 DB에 넣고 다른 MSA와 핑퐁을 쳐야 한다.

| 전술적 구현 요소 | 물리적 매핑 및 엔지니어링 구현체 |
|:---|:---|
| **Repository (저장소)** | 인프라(DB) 코드를 숨기는 인터페이스. 도메인 입장에선 DB가 Oracle인지 Mongo인지 알 필요 없음. 오직 Aggregate Root 1개당 Repository 1개만 매핑 허용 |
| **Domain Service** | 여러 어그리거트나 객체들에 걸쳐서 "어느 한쪽에 책임을 할당하기 애매한 복잡한 로직" (예: 암호화 변환, 계좌 간 이체 연산)을 처리하는 상태 없는(Stateless) 도우미 객체 |
| **Domain Event** | 상태가 바뀌었을 때(`OrderCreated`), 이를 과거분사형 이벤트 캡슐로 만들어 밖(Spring ApplicationEventPublisher, Kafka)으로 던져 결합도(Coupling)를 끊어냄 |

> 요약: DDD에서 Repository는 Entity를 테이블에 `Insert`하는 단순 SQL 기계가 아니다. 도메인 입장에서 볼 때, "어디선가 컬렉션(List)처럼 데이터를 가져오고 저장해 주는 신비한 마법 주머니"일 뿐이다. (영속성 캡슐화).

## Ⅴ. 실무 적용 방안 및 결론

**적용 방안 3개:**
1. [헥사고날(Hexagonal) 아키텍처 기반 코어 격리 튜닝] MSA의 '정산 도메인' 코드를 짤 때, 안쪽 육각형(도메인 모델)에는 JPA `@Entity` 어노테이션이나 DB 관련 코드를 100% 제거하고 순수 POJO Java로만 비즈니스 룰을 짜서, 향후 DB가 교체되더라도 비즈니스 코어(Core)는 무상해 재사용
2. [CQRS 패턴 결합을 통한 조회 성능(Read Model) 극대화] DDD의 거대한 Aggregate 덩어리를 화면에 뿌리기 위해 조인(Join)을 걸면 성능이 죽음. 뷰(View) 렌더링 시에는 복잡한 DDD Repository(명령)를 통하지 않고, 프레젠테이션 계층에서 MyBatis나 QueryDSL을 통해 DB 뷰 모델을 직선으로 찌르는(Bypass) CQRS 타협안 적용
3. [엔티티 간 참조(Reference) ID 강제화] 어그리거트 간 결합도를 끊기 위해, `Order` 객체 안에 `User user` 객체를 직접 물고 있는(JPA 객체 그래프 탐색) 것을 금지하고, 무조건 `Long userId` (식별자 ID)만을 들고 있게 코딩 룰을 강제하여 트랜잭션 바운더리 철저히 단절

**결론:**
- 기술사 판단: 도메인 주도 설계(DDD)는 단순한 클래스 설계 패턴이 아니라 기획, 비즈니스, 코드가 하나로 호흡하는 '사상(Philosophy)'의 혁명이다. 특히 클라우드 네이티브 환경에서 MSA 경계를 식별하는 전략적 도구(Bounded Context)와, 마이크로서비스 내부의 복잡성을 통제하는 전술적 도구(Aggregate)를 동시에 제공하는 현대 아키텍처의 디팩토(De-facto) 마스터키다.
- 향후 방향: 최근 현업에서는 무거운 패러다임(Repository, Factory 패턴) 전체를 강제 적용하여 보일러플레이트가 폭발하는 피로도를 줄이기 위해, 비즈니스 복잡도가 낮은 조회(Query) 서비스에는 단순 트랜잭션 스크립트를 허용하고, 복잡한 트랜잭션(Command) 도메인에만 DDD를 외과 수술처럼 적용하는 '실용적 DDD(Pragmatic DDD) + CQRS' 하이브리드 아키텍처가 실리콘밸리 표준으로 안착했다.
