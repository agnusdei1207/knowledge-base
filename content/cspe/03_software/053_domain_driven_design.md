## 미리 알고가기

- DDD는 복잡한 비즈니스 도메인을 중심으로 모델과 코드를 설계하는 접근임
- Ubiquitous language는 도메인 전문가와 개발자가 함께 쓰는 공통 언어임
- Core domain은 경쟁력과 차별성이 집중된 핵심 업무 영역임

## Ⅰ. 개요

- **정의/개념**: DDD는 복잡한 비즈니스 문제를 해결하기 위해 도메인 전문가와 개발자가 공통 언어를 만들고, 그 언어를 코드와 모델과 서비스 경계에 일치시키는 소프트웨어 설계 접근법임.
- **배경/필요성**: 비즈니스 규칙이 복잡한 시스템은 기술 계층만 잘 나눠도 요구의 실제 의미를 놓치기 쉬우므로, 도메인 자체를 설계 중심에 두는 방식이 필요함.

## Ⅱ. 특징

- 도메인 모델과 코드 구조와 팀 언어를 같은 방향으로 맞추려 함
- 복잡한 핵심 도메인에서 변경 의미를 정확히 반영하는 데 강함
- 모델링과 협업 비용이 커서 단순 서비스에는 과할 수 있음
- bounded context, aggregate, domain event 같은 개념으로 경계를 체계화함

## Ⅲ. 종류 및 비교

| 구분 | 기술 중심 설계 | DDD |
|:---|:---|:---|
| 설계 초점 | 계층 분리와 프레임워크 구조를 먼저 봄 | 도메인 개념과 업무 규칙을 먼저 봄 |
| 얻는 장점 | 시작이 빠르고 구현 경로가 단순함 | 복잡한 규칙을 코드와 모델에 일관되게 반영하기 좋음 |
| 주된 한계 | 비즈니스 의미가 코드에서 왜곡될 수 있음 | 도메인 탐색과 모델 정리에 시간과 비용이 듦 |
| 적합한 환경 | 단순 CRUD나 짧은 수명 서비스에 맞음 | 복합 도메인과 장기 진화 시스템에 맞음 |

> 요약: DDD는 기술을 예쁘게 나누는 방식이 아니라 비즈니스 의미를 코드 구조에 남기는 방식임.

## Ⅳ. 구성요소 및 구조

| 구성요소 | 설명 |
|:---|:---|
| Ubiquitous Language | 도메인 전문가와 개발자가 같은 용어로 대화하게 해 요구 해석 오류를 줄임 |
| Bounded Context | 용어와 규칙이 유효한 경계를 나눠 모델 충돌과 서비스 결합을 줄임 |
| Entity and Value Object | 식별과 상태와 불변성 차이를 구분해 도메인 개체를 정확히 모델링함 |
| Domain Event | 중요한 상태 변화를 모델에 반영해 경계 간 협력과 이력 표현을 돕음 |

## Ⅴ. 원리 및 절차 흐름도

```text
+-------------+     +-------------+     +-------------+     +-------------+
| 도메인 탐색      | --> | 공통 언어 정립 | --> | 모델/경계 설계 | --> | 코드와 정합 유지 |
+-------------+     +-------------+     +-------------+     +-------------+
```

1. **도메인 탐색**: 핵심 업무 규칙과 용어를 식별함
2. **공통 언어 정립**: 이해관계자와 개발자가 같은 말을 쓰도록 맞춤
3. **모델 및 경계 설계**: 엔티티와 애그리게이트와 컨텍스트를 정의함
4. **코드와 정합 유지**: 모델과 구현이 멀어지지 않게 지속 검토함

## Ⅵ. 실무 적용 및 유의점

1. 보험·금융처럼 업무 규칙이 복잡한 핵심 도메인에서는 DDD가 효과적이지만 모든 영역에 같은 수준으로 적용하면 비용이 커지므로 핵심 도메인부터 우선 적용하고 모델링 투입 비율과 업무 영향도로 확인함
2. 장기 운영 플랫폼에서는 시간이 지나며 코드가 모델을 배반하기 쉬우므로 용어 사전과 모델 리뷰를 함께 운영하고 용어 충돌 건수와 모델-코드 불일치 비율로 확인함

## Ⅶ. 결론

DDD의 가치는 도메인 의미와 코드 구조와 팀 언어를 같은 방향으로 맞춰 복잡한 규칙 변경을 견디게 하는 데 있음.
