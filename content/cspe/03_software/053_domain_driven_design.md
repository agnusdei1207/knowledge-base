## 미리 알고가기

- DDD: 복잡한 비즈니스 도메인을 중심으로 모델과 코드를 설계하는 소프트웨어 개발 접근법임
- 보편적 언어(Ubiquitous Language): 도메인 전문가와 개발자가 설계 및 소통의 오해를 없애기 위해 공동으로 사용하는 용어 체계임
- 핵심 도메인(Core Domain): 기업의 비즈니스 경쟁력과 차별성이 집중되어 가장 리소스를 많이 투입해야 하는 핵심 영역임
- 전략적 설계(Strategic Design): 비즈니스 도메인을 분석하여 바운디드 컨텍스트를 도출하고 그들의 관계를 정의하는 거시적 설계 과정임
- 전술적 설계(Tactical Design): 정의된 바운디드 컨텍스트 내부의 도메인 모델을 정교화하기 위해 엔티티, 값 객체, 서비스 등을 구현하는 미시적 설계 과정임

## 작성 근거(검토용)

- DDD는 설계 초점, 업무 규칙 표현, 적용 비용을 핵심 비교축으로 선정함
- 구성은 공통 언어, 모델 경계, 도메인 객체, 상태 변화 표현을 중심으로 제시함
- 실무 판단은 용어 충돌 건수, 모델·코드 불일치율, 변경 영향 범위로 구체화함
- 제목, frontmatter, 미리 알고가기, 작성 근거, 본문, 표 헤더·셀, 요약, 결론을 한 줄도 빠뜨리지 않고 확인했으며 어색한 단어·조사·동사 결합·장황한 명사구를 교정함

## Ⅰ. 개요

- **정의/개념**: DDD는 도메인 전문가와 개발자가 공통 언어를 만들고 이를 모델·코드·경계에 반영하는 소프트웨어 설계 접근법임
- **배경/필요성**: 복잡한 업무 규칙은 기술 계층만으로 의미를 표현하기 어려우므로 도메인 개념을 설계 중심에 둘 필요가 있음

### 쉽게 이해하기 (학습용)
- 집을 지을 때 건축주(현업)와 설계사(개발자)가 똑같은 단어로 소통하며, 그 소통 내용을 그대로 설계도와 건물의 방(코드)에 반영하는 방식임

## Ⅱ. 특징

- 공통 언어를 모델·코드 이름·팀 대화에 동일하게 사용함
- 업무 규칙의 변경 의미를 엔티티·값 객체·애그리게이트의 책임과 연결함
- 업무 규칙 변화가 적고 용어 의미가 단일한 서비스는 모델링·협업 비용이 편익을 초과할 수 있음
- 바운디드 컨텍스트, 애그리게이트, 도메인 이벤트 같은 개념으로 경계를 체계화함

### 쉽게 이해하기 (학습용)
- 비즈니스 현장에서 쓰는 용어를 그대로 변수나 클래스 이름으로 쓰고, 도메인의 본질적인 규칙을 코드에 그대로 구현해 관리함

## Ⅲ. 종류 및 비교

| 판단 기준 | 기술 중심 설계 | DDD |
|:---|:---|:---|
| 설계 및 모델링 초점 | 계층 분리와 프레임워크 구조를 우선함 | 도메인 개념과 업무 규칙을 우선함 |
| 업무 규칙 구현 방식 | 화면·데이터 중심으로 CRUD 구현 | 공통 언어·Entity·Value Object로 업무 규칙 표현 |
| 주요 고려사항 및 한계 | 비즈니스 의미가 코드에서 왜곡될 수 있음 | 도메인 탐색과 모델 정리에 시간과 비용이 듦 |

> 요약: 규칙이 적은 CRUD는 기술 중심 설계, 업무 규칙과 용어가 지속 변경되면 DDD가 적합함.

### 쉽게 이해하기 (학습용)
- DB 테이블에만 맞춰 데이터를 넣고 빼던 기존 방식과 달리, 실제 비즈니스의 동작과 의미가 살아서 코드로 변환되는 방식임

## Ⅳ. 설계 요소 및 구조

```text
[전략적 설계] ──> 비즈니스 도메인 분석 ──> 바운디드 컨텍스트 도출 ──> 컨텍스트 맵 작성
                                                                           │
[전술적 설계] <── 엔티티/밸류 객체 정의 <── 애그리게이트 경계 설정 <───┘
```

| 설계 요소 | 설명 |
|:---|:---|
| 공통 언어 | 도메인 전문가와 개발자가 같은 업무 용어로 모델을 설명함 |
| 바운디드 컨텍스트 | 용어와 규칙이 유효한 모델 경계를 나눔 |
| 엔티티·값 객체 | 식별자 유무와 불변성에 따라 도메인 객체를 구분함 |
| 도메인 이벤트 | 다른 컨텍스트가 후속 처리해야 하는 상태 변화를 표현함 |

> 요약: 공통 언어로 업무 의미를 맞추고 컨텍스트 경계 안에서 객체와 상태 변화를 모델링함.

### 쉽게 이해하기 (학습용)
- 큰 틀에서 구역을 나누고(전략적), 그 구역 안에서 구체적으로 어떤 물건과 책임이 필요한지 상세히 지정하는(전술적) 2단계 구조임

## Ⅴ. 원리 및 절차 흐름도

```text
[1. 비즈니스 도메인 분석] ──> [2. 컨텍스트 및 언어 정의] ──> [3. 컨텍스트 맵핑] ──> [4. 전술적 모델 구현]
```

- **1. 비즈니스 도메인 분석**: 해결하려는 문제 공간(Problem Space)을 탐색하고 하위 도메인(핵심, 지원, 일반)으로 분류함
- **2. 컨텍스트 및 언어 정의**: 도메인 개념의 범위가 유지되는 바운디드 컨텍스트(Bounded Context) 경계를 도출하고, 공통 언어를 정의함
- **3. 컨텍스트 맵핑**: 여러 컨텍스트 간의 데이터 교환 방식 및 상호 의존 관계를 정의하여 컨텍스트 맵(Context Map)을 도출함
- **4. 전술적 모델 구현**: 각 컨텍스트 내에서 엔티티(Entity), 값 객체(Value Object), 애그리게이트(Aggregate)를 설계 및 구현함

### 쉽게 이해하기 (학습용)
- 비즈니스를 이해하고, 구역을 나누고, 공통 용어를 정한 뒤, 그 안의 핵심 개념들을 코드 부품으로 만들어 나가는 흐름임

## Ⅵ. 실무 사례

- 금융 코어 뱅킹 시스템 구축 시, 예금 및 대출 업무 영역을 전략적으로 격리하고, 각 도메인 내의 거래 처리 규칙은 전술적 설계를 적용해 엔티티와 값 객체(Value Object)로 조치함.

### 쉽게 이해하기 (학습용)
- 복잡한 대출 심사 시스템에서 예금 부서와 대출 부서의 용어를 분리하고, 대출 심사 규칙을 코드로 직접 표현해 유지보수성을 높인 사례임

## Ⅶ. 결론

- DDD는 도메인 전문가와 개발자 간의 언어적 불일치를 해소하고, 비즈니스 중심의 안정적인 모델을 소프트웨어 구조로 정착시킴.
- 그러나 높은 도메인 분석 비용과 숙련도 요구라는 제약이 있으므로, 핵심 차별화 영역(Core Domain)에 한하여 전술적 설계를 집중 적용하는 선택과 집중이 필요함.

### 쉽게 이해하기 (학습용)
- 비즈니스가 바뀌어도 코드가 쉽게 따라가게 돕지만, 만드는 비용이 크므로 돈이 되고 중요한 핵심 기능에만 집중해서 써야 함
