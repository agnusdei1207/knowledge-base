# 📖 【암기용】 개념 완전 이해

> 목적: DDD 도메인 주도 설계를 처음 보는 사람도 완벽히 이해하게 만든다. 시험 답안 양식이 아니라, 이해를 위한 친절한 설명이다.

## 한눈에
- **개요**: 복잡한 업무 도메인을 모델과 언어 중심으로 소프트웨어에 반영하는 설계 접근
- **왜 필요한가**: 업무 용어와 코드 용어가 다르면 요구사항 해석 오류, 중복 모델, 서비스 간 책임 충돌이 생긴다. DDD는 업무 전문가와 개발자가 같은 언어로 모델을 다듬게 한다.
- **핵심 직관**: 데이터베이스 테이블을 먼저 그리는 설계가 아니라, 업무에서 변하지 말아야 할 규칙과 경계를 먼저 찾는 설계이다.

## 깊이 이해
- **배경·문제의식**: 복잡한 업무 시스템에서 단순 CRUD 모델은 할인, 정산, 재고 예약, 승인 상태 전이를 코드 곳곳에 흩뜨린다.
- **작동 원리**: 전략적 설계는 바운디드 컨텍스트와 컨텍스트 맵으로 모델 경계를 나누고, 전술적 설계는 Entity, Value Object, Aggregate, Repository, Domain Service로 내부 모델을 구성한다.
- **비유**: 병원에서 접수, 진료, 수납이 같은 "환자"라는 말을 쓰지만 각 부서가 보는 속성과 규칙이 다르므로 문맥별 모델을 나누는 것과 같다.
- **구체 예시**: 주문 도메인에서 `Order` Aggregate는 주문항목, 배송지, 결제상태를 묶고, 주문 총액 불변식과 취소 가능 상태를 한 트랜잭션 안에서 보장한다.
- **흔한 오해·주의점**: DDD는 MSA 전용 기법이 아니다. 모놀리식에서도 모듈 경계와 도메인 모델을 잡는 데 사용한다.

## 연결 개념
- 바운디드 컨텍스트: 모델 의미가 일관되는 경계
- 애그리게이트: 트랜잭션 일관성 경계
- 이벤트 스토밍: 도메인 이벤트로 업무 흐름을 발견하는 워크숍

# 📝 【답안용】 시험 답안 템플릿

> 목적: 시험장에서 25분에 그대로 쓰는 답안 양식. 작성방식(추상표현 금지·수치·도식·문제유형 전환)을 엄격히 지킨다.
> 핵심: DDD는 객체 패턴 모음이 아니라, 복잡한 도메인의 언어·경계·모델·트랜잭션을 정렬하는 방법이다.

## 핵심 인사이트 (3줄 요약)

> 1. **본질**: DDD는 유비쿼터스 언어와 도메인 모델을 기반으로 복잡한 업무 규칙을 코드 구조에 반영하는 설계 접근이다.
> 2. **가치**: 업무 용어와 코드 용어를 일치시켜 요구사항 재작업률을 낮추고, 컨텍스트 경계로 서비스 분해 기준을 제공한다.
> 3. **판단 포인트**: 전략적 설계는 경계와 관계, 전술적 설계는 모델 구성요소와 불변식 보호에 초점을 둔다.

## 출제 의도 및 답안 포인트

| 출제 의도 | 반드시 짚을 핵심 | 감점 회피 포인트 |
|:---|:---|:---|
| 복잡한 도메인 모델링 역량 확인 | Ubiquitous Language, Bounded Context, Context Map | DDD를 단순 클래스 설계로 축소 |
| 전술 패턴 이해 확인 | Entity, Value Object, Aggregate, Repository, Domain Service | Repository를 DAO와 동일시 |
| MSA 분해 기준 판단 확인 | 도메인 경계, 팀 경계, 데이터 소유권 | 테이블 기준 서비스 분리 답안 |
> 요약: 출제자는 업무 언어에서 모델 경계를 찾고 전술 패턴으로 일관성을 보장하는지를 확인한다.

## Ⅰ. 개요 및 필요성

DDD는 복잡한 업무 도메인을 모델 중심으로 설계하는 접근이다.
업무 규칙이 서비스 코드와 SQL에 흩어지면 변경 영향 분석과 장애 원인 추적이 어려워진다.
DDD는 업무 언어, 모델 경계, 애그리게이트 단위 일관성으로 복잡도를 통제한다.

---

## Ⅱ. 구조 및 구성요소

```text
업무 전문가 + 개발자 -> Ubiquitous Language
Ubiquitous Language -> Bounded Context -> Context Map
Bounded Context -> Entity / Value Object / Aggregate
Aggregate -> Repository / Domain Service
Domain Event -> 다른 Context 통합
```

| 구성요소 | 역할 | 특이사항 |
|:---|:---|:---|
| Ubiquitous Language | 업무와 코드의 공통 용어 | 회의록, 코드, 테스트명 일치 |
| Bounded Context | 모델 의미가 일관되는 경계 | 팀·배포·데이터 경계 후보 |
| Aggregate | 불변식을 지키는 객체 묶음 | 트랜잭션 1개 단위 |
| Repository | Aggregate 저장·조회 추상화 | 컬렉션처럼 보이는 인터페이스 |
| Domain Service | 특정 Entity에 넣기 어려운 도메인 행위 | 업무 규칙만 포함 |
> 요약: DDD는 언어와 경계를 먼저 정하고, 애그리게이트와 Repository로 내부 일관성을 구현한다.

---

## Ⅲ. 동작원리 및 흐름도

```text
도메인 탐색 -> 용어 수집
용어 수집 -> 유비쿼터스 언어 정리
언어 충돌 -> Bounded Context 분리
Context 내부 -> Entity / Value Object / Aggregate 설계
Aggregate 변경 -> Repository 저장 -> Domain Event 발행
```

| 단계 | 처리 내용 | 검증 기준 |
|:---:|:---|:---|
| 1 | 업무 이벤트, 명령, 정책 수집 | Event Storming 산출물 |
| 2 | 용어 충돌과 의미 차이 식별 | 동일 용어 다른 속성 2개 이상 |
| 3 | Bounded Context와 Context Map 작성 | Upstream, Downstream 관계 명시 |
| 4 | Aggregate와 불변식 설계 | 트랜잭션 경계 1개로 보호 |
| 5 | Repository, Domain Event로 통합 | 최종 일관성 지연 시간 측정 |
> 요약: DDD는 도메인 탐색에서 시작해 경계를 나누고 애그리게이트로 일관성을 보장한다.

## Ⅳ. 특징

| 구분 | 데이터 중심 설계 | DDD | 수치·판단 포인트 |
|:---|:---|:---|:---|
| 출발점 | ERD, 테이블 | 도메인 언어, 업무 규칙 | 용어 사전 1개 운영 |
| 경계 | 스키마·업무 화면 | Bounded Context | 컨텍스트별 모델 충돌 0건 |
| 일관성 | DB 트랜잭션 중심 | Aggregate 불변식 중심 | Aggregate당 트랜잭션 1개 |
| 통합 | FK·JOIN | Domain Event, ACL | 이벤트 지연 p95 1초 이하 |
| 리스크 | 빠른 CRUD | 모델링 시간 증가 | 2주 이상 탐색 워크숍 관리 |
> 요약: DDD는 복잡한 업무 규칙과 모델 충돌이 있는 시스템에서 데이터 중심 설계보다 경계 판단에 유리하다.

## Ⅴ. 심화 비교 및 적용 판단

| 비교 축 | Transaction Script | DDD | 선택 기준 |
|:---|:---|:---|:---|
| 업무 복잡도 | CRUD, 단순 승인 | 규칙·예외·상태 전이 다수 | 규칙 20개 이상 |
| 변경 빈도 | 월 1회 이하 | 주 1회 이상 | 도메인 전문가 상시 협업 |
| 팀 구조 | 단일 팀 | 컨텍스트별 팀 | 팀 3개 이상 |
| 데이터 | 단일 스키마 | Context별 소유 데이터 | 공유 테이블 5개 이상이면 분리 검토 |
> 요약: DDD는 업무 규칙과 팀 경계가 동시에 복잡한 시스템에서 적용 가치가 높다.

| 리스크 | 원인 | 대응 방안 | 확인 지표 |
|:---|:---|:---|:---|
| 모델 빈혈 | 로직이 Application Service에 집중 | Entity, Value Object에 규칙 이동 | 도메인 메서드 수 |
| 컨텍스트 과분할 | 용어 차이 없이 서비스 분리 | Context Map 리뷰 | 서비스 간 호출 수 |
| Repository 오용 | SQL 조건 메서드 남발 | Aggregate 단위 저장·조회 | Repository 메서드 수 |
| 이벤트 정합성 지연 | 최종 일관성 적용 | Outbox, 재처리, 보상 트랜잭션 | 이벤트 실패율 0.1% 이하 |
> 요약: DDD의 위험은 과분할과 빈약한 모델이며, Context Map과 도메인 테스트로 통제한다.

| 점검 항목 | 목표 기준 | 측정 방법 |
|:---|:---|:---|
| 언어 일치 | 코드·문서·테스트 용어 불일치 0건 | 용어 사전 리뷰 |
| 경계 품질 | Context 간 공유 테이블 0개 | DB 스키마 분석 |
| 일관성 | Aggregate 불변식 테스트 80% 이상 | 단위 테스트 |
| 통합 | Domain Event 재처리 성공률 99.9% | 메시지 로그 |
> 요약: DDD 도입 효과는 언어 일치, 경계 품질, 불변식 테스트, 이벤트 통합 지표로 판단한다.

## Ⅵ. 실무 적용 및 결론

**적용 방안 3개:**
1. Event Storming으로 Command, Domain Event, Policy, Hot Spot을 도출하고 용어 사전을 코드·API·테스트명에 반영한다.
2. 주문, 결제, 정산처럼 의미가 다른 영역은 Bounded Context로 나누고 Context Map에 Shared Kernel, ACL 관계를 표시한다.
3. Aggregate별 불변식 테스트를 작성하고 Repository는 Aggregate Root 기준 저장·조회만 허용한다.

**결론 (2줄):**
- 기술사 판단: 단순 CRUD는 Transaction Script, 복잡한 상태 전이와 팀 경계가 있으면 DDD를 선택함
- 향후 방향: DDD는 MSA, Event Sourcing, Hexagonal Architecture와 결합해 도메인 중심 플랫폼 구조로 확장됨
