# 📖 【암기용】 개념 완전 이해

## 한눈에
- **개요**: 도메인 주도 설계(DDD)는 소프트웨어의 복잡성을 해결하기 위해, 비즈니스 도메인(업무 영역)을 중심으로 모델링하고 개발하는 설계 방법론이다.
- **왜 필요한가**: 데이터베이스 테이블(ERD)부터 짜고 코딩을 시작하면, 비즈니스 로직이 파편화되어 업무가 조금만 복잡해져도 코드를 수정하기 어렵다. 비즈니스 그 자체를 코드에 담아야 한다.
- **핵심 직관**: 통역사 없는 회의실. 기획자, 실무자, 개발자가 모두 '동일한 단어(유비쿼터스 언어)'로 소통하고, 그 단어가 코드와 DB에 똑같이 반영되는 구조다.

## 핵심 용어 정리

| 용어/표기 | 의미 | 비유·예 |
|:---|:---|:---|
| 유비쿼터스 언어 (Ubiquitous Language) | 도메인 전문가와 개발자가 공통으로 사용하는 보편적 언어 | "사용자 취소"라는 말을 기획/코드/DB 모두 동일하게 사용 |
| 도메인 모델 (Domain Model) | 특정 도메인의 핵심 규칙과 로직을 추상화한 객체망 | 실제 은행의 '계좌 이체' 업무 룰을 코드로 구현한 덩어리 |
| 전략적 설계 (Strategic Design) | 큰 비즈니스를 여러 도메인으로 쪼개고 경계를 긋는 상위 설계 | 회사를 인사팀, 재무팀, 영업팀으로 구획 분리 |
| 전술적 설계 (Tactical Design) | 쪼개진 구역 안에서 클래스와 객체를 어떻게 짤지 구체적 구현 | 팀 내부의 업무 프로세스 및 결재 서류 양식 설계 |

## 깊이 이해
- **배경·문제의식**: 소프트웨어의 본질은 사용자의 비즈니스 문제를 해결하는 것이다. 하지만 기술(프레임워크, DB)에 종속된 '데이터 주도 설계'를 하면, 현실 업무 룰(도메인 지식)이 코드 여기저기에 분산되어 파악이 불가능해진다.
- **작동 원리**: 크게 전략적 설계와 전술적 설계로 나뉜다.
  - **전략적 설계**: 도메인을 핵심/지원/일반 서브도메인으로 나누고, 문맥이 유지되는 경계인 '바운디드 컨텍스트(Bounded Context)'를 식별한다.
  - **전술적 설계**: 엔티티(Entity), 값 객체(Value Object), 애그리게이트(Aggregate) 패턴을 활용해 도메인 모델을 객체 지향적으로 코딩한다.
- **비유**: 대형 백화점 짓기. 전략적 설계는 층별로 명품관, 식품관, 의류관(바운디드 컨텍스트)을 나누는 것이고, 전술적 설계는 식품관 안의 진열대와 계산대(엔티티, VO)를 배치하는 것이다.
- **흔한 오해·주의점**: DDD는 새로운 기술 스택이 아니라 방법론이다. 또한 모든 시스템에 DDD를 쓰면 안 된다. 단순 CRUD 게시판에 DDD를 쓰면 쓸데없는 클래스만 수십 개 늘어나 설계가 비대해진다.

## 연결 개념
- 바운디드 컨텍스트 (Bounded Context) — 전략적 설계의 핵심 논리적 경계
- 애그리게이트 (Aggregate) — 전술적 설계의 데이터 변경 트랜잭션 단위
- 마이크로서비스 아키텍처 (MSA) — DDD의 바운디드 컨텍스트 단위로 서비스를 나누는 것이 가장 이상적

# 📝 【답안용】 시험 답안 템플릿

## 핵심 인사이트 (3줄 요약)

> 1. **본질**: 복잡한 비즈니스 도메인을 유비쿼터스 언어와 도메인 모델을 기반으로 전략적/전술적으로 분할하여 해결하는 소프트웨어 설계 방법론이다.
> 2. **가치**: 비즈니스 로직과 기술적 복잡성을 격리하여 요구사항 변경에 유연하게 대응하며, MSA 체제의 서비스 도출 기준으로 활용된다.
> 3. **판단 포인트**: 도메인 전문가와 개발자 간의 소통 갭을 줄이는 것이 핵심이나, 초기 모델링 오버헤드가 크므로 핵심 서브도메인에 제한적으로 적용해야 한다.

## 출제 의도 및 답안 포인트

| 출제 의도 | 반드시 짚을 핵심 | 감점 회피 포인트 |
|:---|:---|:---|
| 소프트웨어 복잡성 해결 전략 이해 | 유비쿼터스 언어, 전략적 설계(경계), 전술적 설계(객체) | 단순 객체지향 설계(OOP)와의 차별점 누락 |
| MSA 서비스 분할 기준 제시 역량 | 바운디드 컨텍스트 중심의 독립 서비스 도출 | 테이블 구조 중심의 분산 DB 설계로 오답 기재 |
| 전술적 모델링 패턴 활용 역량 | Entity, Value Object, Aggregate의 역할 구분 명시 | 모든 도메인에 동일 수준의 복잡도 템플릿 강제 단정 |

> 요약: 데이터 중심의 ERD 설계에서 벗어나, 비즈니스 행위 중심의 도메인 모델 구축과 시스템 경계 분할 역량을 보여주어야 한다.

---

## Ⅰ. 개요 및 필요성

- 개요: 소프트웨어의 복잡성을 관리하기 위해 비즈니스 도메인 중심으로 유비쿼터스 언어를 정의하고 모델링을 수행하는 설계 패러다임임
- 배경: 데이터 중심 설계(Data-Driven Design) 시 비즈니스 로직이 쿼리나 서비스 계층에 파편화되어 유지보수 한계 도달
- 필요성: 비즈니스 언어와 코드의 일치를 통해 커뮤니케이션 오해를 제거하고, MSA 전환 시 결합도를 낮추는 논리적 경계 식별 기준 수립 필수

---

## Ⅱ. 구조 및 구성요소

```text
비즈니스 요구 -> [전략적 설계: 도메인 분할 및 컨텍스트 경계 확립] -> [전술적 설계: 객체 모델링 구현] -> 도메인 코드
                (바운디드 컨텍스트, 컨텍스트 맵)                 (엔티티, VO, 애그리게이트)
```

| 구성요소 | 역할 | 특이사항 |
|:---|:---|:---|
| 유비쿼터스 언어 | 도메인 전문가와 개발자가 공유하는 단일 언어 모델 | 클래스명, 메서드명과 1:1 매핑 원칙 |
| 전략적 설계 (Strategic) | 비즈니스 목적에 따라 서브도메인 도출 및 경계 정의 | MSA의 마이크로서비스 식별의 논리적 기준 |
| 전술적 설계 (Tactical) | 바운디드 컨텍스트 내부의 도메인 로직을 패턴으로 구현 | 헥사고날 아키텍처 내부 영역 구성에 적극 활용 |

> 요약: 크게 시스템을 쪼개는 전략적 설계와 쪼개진 내부를 객체로 채우는 전술적 설계로 구성되어 비즈니스를 코드화한다.

---

## Ⅲ. 동작원리 및 흐름도

```text
도메인 지식 탐구 -> 언어 정의 -> 전략적 바운디드 컨텍스트 매핑 -> 전술적 애그리게이트 설계 -> 코드 반영
```

- 1단계 [도메인 지식 탐구]: 이벤트 스토밍 워크숍 등을 통해 비즈니스 흐름을 파악하고 유비쿼터스 언어 도출
- 2단계 [서브도메인 식별]: 전체 도메인을 비즈니스 중요도에 따라 핵심(Core), 지원(Supporting), 일반(Generic) 도메인으로 분할
- 3단계 [전략적 모델링]: 의미적 일관성이 유지되는 경계인 바운디드 컨텍스트를 설정하고 컨텍스트 맵으로 관계(ACL 등) 정의
- 4단계 [전술적 모델링]: 단일 트랜잭션 경계인 애그리게이트 단위로 엔티티와 Value Object(불변 객체)를 묶어 코드로 구현

> 요약: 비즈니스 탐구에서 시작해 논리적 경계를 긋고, 최종적으로 데이터와 행위가 결합된 객체 모델로 구체화된다.

---

## Ⅳ. 특징

- 커뮤니케이션 비용 절감: 기획서의 용어가 코드의 클래스명과 동일하게 유지되어 번역 비용 감소 및 요구사항 누락 방지
- 독립적 생명주기 관리: 바운디드 컨텍스트 단위로 모델이 격리되어, 한 컨텍스트의 로직 변경이 타 컨텍스트로 전파(Ripple Effect) 차단
- 러닝 커브 및 초기 오버헤드: 도메인 전문가의 적극적 참여가 필수적이며, 전술적 패턴 적용 시 인터페이스 및 객체 매핑 코드 초기 팽창

> 요약: 복잡한 비즈니스 로직을 통제하는 강력한 수단이나, 도입 초기 모델링 합의에 상당한 시간과 학습 비용이 소요된다.

---

## Ⅴ. 심화 비교 및 적용 판단

| 비교 축 | 데이터 주도 설계 (Data-Driven) | 도메인 주도 설계 (DDD) | 선택 기준 |
|:---|:---|:---|:---|
| 시작점 | ERD (데이터베이스 테이블) 구축 중심 | 비즈니스 행위 및 이벤트 모델링 도출 | 프로젝트의 본질(저장 vs 로직 연산) |
| 객체 상태 | getter/setter 기반의 빈약한 도메인(Anemic) | 행위를 포함한 풍부한 도메인 모델(Rich) | 로직의 복잡도 및 상태 캡슐화 필요성 |
| 적용 환경 | 단순 CRUD 중심의 레거시 모놀리스 | 복잡한 비즈니스 룰 및 MSA 전환 환경 | 도메인 전문가의 헌신적 참여 가능 여부 |

> 요약: 데이터 저장이 목적인 단순 시스템은 데이터 주도 설계가 경제적이나, 비즈니스 룰이 핵심 가치라면 DDD를 선택한다.

**리스크·대응:**
- 애그리게이트 비대화: 한 애그리게이트에 너무 많은 엔티티를 묶어 트랜잭션 충돌 및 DB 병목 발생 → 결과적 일관성(Eventual Consistency) 기반으로 애그리게이트를 잘게 분할 (지표: 낙관적 락 충돌 발생 빈도)
- 모든 도메인에 동등 적용: 덜 중요한 지원 도메인까지 전술적 패턴을 남용하여 리소스 낭비 심화 → 핵심 도메인에만 전술적 DDD 집중하고, 지원 도메인은 단순 CRUD 적용 (지표: 복잡도 대비 투입 공수)

## Ⅵ. 실무 적용 및 결론

**적용 방안 3개:**
1. MSA 서비스 식별 도구로 활용: 레거시 모놀리스 분할 시 1개의 바운디드 컨텍스트를 1개의 마이크로서비스로 매핑하여 서비스 간 배포 독립성 보장
2. 이벤트 스토밍(Event Storming) 워크숍 도입: 프로젝트 초기 도메인 이벤트(주황색)와 커맨드(파란색) 포스트잇을 활용해 유비쿼터스 언어 및 도메인 경계 가시화
3. 헥사고날 아키텍처와 결합 설계: 전술적 도메인 모델을 헥사고날 구조의 내부 육각형에 두고 외부 포트 어댑터로 감싸 인프라(DB 등) 종속성 차단

**결론 (2줄):**
- 기술사 판단: DDD는 단순한 코딩 템플릿이 아니라 조직 간 소통 갭을 줄이는 방법론이므로, 기술 도입 이전에 조직 문화와 도메인 전문가의 협력이 전제되어야 함
- 향후 방향: 마이크로서비스와 클라우드 네이티브의 확산으로 DDD의 전략적 설계(바운디드 컨텍스트) 가치가 재조명되며 엔터프라이즈 아키텍처의 표준으로 자리잡음
