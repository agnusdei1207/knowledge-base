## Ⅰ. 개요
- **정의**: 복잡한 비즈니스 도메인을 소프트웨어 모델의 중심에 놓고 설계·구현하는 방법론
- **배경/필요성**: 기술 중심 설계는 비즈니스 변화에 취약하므로, 도메인 전문가와 개발자가 공통 모델로 소통할 필요
- **비유**: 의사와 환자가 같은 차트(유비쿼터스 언어)를 보며 치료 계획을 세우는 것과 유사함

| 출제 의도 | 반드시 짚을 핵심 | 감점 회피 포인트 |
|:---|:---|:---|
| 전략·전술 패턴 구분 이해 | 유비쿼터스 언어, 바운디드 컨텍스트 | 단순 계층 구조 설명에 그치지 말고 전략 패턴 포함 필요 |

> 요약: 도메인 모델 중심으로 비즈니스와 코드를 일치시키는 설계 방법론임

## Ⅱ. 구성요소
```text
+--- Strategic Design ---+    +--- Tactical Design ---+
| Ubiquitous Language    |    | Entity / Value Object |
| Bounded Context (054)  |    | Aggregate (055)       |
| Context Map            |    | Repository / Service  |
+------------------------+    +-----------------------+
```

| 구성요소 | 설명 | 비유 |
|:---|:---|:---|
| 유비쿼터스 언어 | 도메인 전문가·개발자가 공유하는 단일 용어 체계 | 팀 전체가 쓰는 공용 사전 |
| 전략 설계 | 바운디드 컨텍스트·컨텍스트 맵 등 시스템 경계를 정의하는 상위 설계 | 도시 구역 계획 |
| 전술 설계 | Entity·Value Object·Aggregate 등 도메인 모델 구현 패턴 | 건물 내부 설계도 |

> 요약: 전략 설계로 경계를 나누고, 전술 설계로 모델을 구현하며, 유비쿼터스 언어로 소통함

## Ⅲ. 절차
```text
도메인분석 --> 유비쿼터스언어정의 --> 바운디드컨텍스트식별 --> 전술패턴적용
```
- 1단계: 도메인 전문가와 워크숍을 통해 핵심 도메인과 서브도메인을 분석함
- 2단계: 팀 공통 용어(유비쿼터스 언어)를 정의하고 문서·코드에 일관 적용함
- 3단계: 모델 경계를 바운디드 컨텍스트로 식별하고 컨텍스트 맵을 작성함(054 참조)
- 4단계: Entity·Aggregate·Repository 등 전술 패턴을 적용해 도메인 모델을 구현함

> 요약: 도메인 분석에서 전술 패턴 적용까지 4단계로 진행함

## Ⅳ. 문제점
- 초기 비용: 도메인 분석·워크숍에 상당한 시간 투자 필요 — 단순 CRUD 시스템에서는 과잉 설계
- 언어 괴리: 유비쿼터스 언어가 코드에 미반영 — 모델과 구현 간 불일치 누적
- 경계 설정 난이도: 바운디드 컨텍스트 경계 오류 — 컨텍스트 간 강결합 발생

> 요약: 초기 비용, 언어 괴리, 경계 설정 오류가 주요 문제임

## Ⅴ. 개선방안
1. 단기: 핵심 도메인에만 DDD를 선별 적용하여 초기 비용 최소화
2. 중기: 코드 리뷰·정적 분석으로 유비쿼터스 언어와 코드 용어 일치 여부 자동 검증
3. 장기: 이벤트 스토밍(055 참조) 기반으로 컨텍스트 경계를 반복 검증·조정

> 요약: 선별 적용, 용어 자동 검증, 이벤트 스토밍 기반 경계 조정으로 개선함

## Ⅵ. 전망
- 발전 방향: MSA 전환과 함께 서비스 경계 설계의 표준 방법론으로 채택 확대 중임
- 기술사적 판단: 기술 복잡도가 아닌 비즈니스 복잡도가 높은 시스템에 적용 가치가 큼
- 기술사 제언: 헥사고날 아키텍처(052 참조)와 결합하여 도메인 순수성 확보 필요
