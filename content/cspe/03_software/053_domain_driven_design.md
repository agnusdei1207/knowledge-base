## 미리 알고가기

- DDD는 복잡한 비즈니스 도메인을 중심으로 소프트웨어 모델을 만드는 접근임
- ubiquitous language와 bounded context가 핵심 기반임
- 기술 설계보다 도메인 의미와 협업 언어 정렬이 더 중요함

## Ⅰ. 개요

- **정의/개념**: DDD는 복잡한 비즈니스 문제를 해결하기 위해 도메인 전문가와 개발자가 공통 언어를 만들고, 그 언어를 코드와 모델과 서비스 경계에 일치시키는 소프트웨어 설계 접근법임
- **배경/필요성**: 비즈니스 규칙이 복잡한 시스템에서는 기술 중심 설계만으로는 요구의 진짜 의미를 놓치기 쉬우므로, 도메인 자체를 설계 중심에 두는 방식이 필요함

## Ⅱ. 특징

- 도메인 모델과 코드 구조와 팀 언어를 정렬하려 함
- 복잡한 핵심 도메인에 특히 효과가 큼
- 모델링과 협업 비용이 크므로 단순 시스템에는 과할 수 있음
- bounded context와 aggregate와 domain event 같은 개념으로 경계를 체계화함

## Ⅲ. 종류 및 비교

| 판단 기준 | 기술 중심 설계 | DDD |
|:---|:---|:---|
| 초점 | 계층과 프레임워크 | 도메인 개념과 규칙 |
| 장점 | 시작이 빠름 | 복잡한 규칙 표현과 변경 대응 유리 |
| 한계 | 비즈니스 의미 왜곡 가능 | 모델링 비용과 학습 비용 큼 |
| 적합 환경 | 단순 서비스 | 복합 도메인과 장기 진화 시스템 |

## Ⅳ. 구성요소 및 구조

| 구성요소 | 설명 |
|:---|:---|
| Ubiquitous Language | 도메인 전문가와 개발자가 같은 용어로 대화하게 해 요구 해석 오류를 줄임 |
| Bounded Context | 용어와 규칙이 유효한 경계를 나눠 모델 충돌과 서비스 결합을 줄임 |
| Entity and Value Object | 상태와 식별과 불변성을 구분해 도메인 개체를 정확히 모델링함 |
| Domain Event | 중요한 상태 변화를 모델에 반영해 경계 간 협력과 이력 표현을 돕음 |

## Ⅴ. 원리 및 절차 흐름도

```text
+-------------+     +-------------+     +-------------+     +-------------+
| 도메인 탐색      | --> | 공통 언어 정립 | --> | 모델/경계 설계 | --> | 코드와 정합 유지 |
+-------------+     +-------------+     +-------------+     +-------------+
```

1. **도메인 탐색**: 핵심 비즈니스 규칙과 용어를 식별함
2. **공통 언어 정립**: 이해관계자와 개발자가 같은 말을 쓰도록 맞춤
3. **모델과 경계 설계**: 엔티티와 애그리게이트와 컨텍스트를 정의함
4. **코드와 정합 유지**: 모델과 구현이 멀어지지 않게 지속 검토함

## Ⅵ. 문제점 및 해결 방안

1. 문제: 도메인 용어가 팀마다 다르면 같은 기능도 다른 의미로 구현돼 통합 결함이 커질 수 있음
   - 해결방안: 용어 사전과 이벤트 스토밍을 운영하고 terminology conflict count와 model drift rate로 검증함
2. 문제: 핵심 도메인과 일반 지원 영역을 구분하지 않으면 모든 영역에 과도한 모델링 비용이 들어갈 수 있음
   - 해결방안: core domain 우선순위를 정하고 modeling effort ratio와 business impact score로 검증함
3. 문제: 시간이 지나며 코드 구조가 모델을 배반하면 DDD는 이름만 남고 유지보수 난도는 더 커질 수 있음
   - 해결방안: 모델 리뷰와 아키텍처 테스트를 병행하고 model drift rate와 dependency violation count로 검증함

## Ⅶ. 적용 사례

- 복잡한 보험 청약 시스템에서는 DDD를 적용하고 확인 지표는 terminology conflict count와 business impact score임
- 도메인 탐색 워크숍에서는 이벤트 스토밍을 사용하고 확인 지표는 modeling effort ratio와 model drift rate임
- 장기 운영 플랫폼에서는 모델 정합 리뷰를 운영하고 확인 지표는 dependency violation count와 integration defect count임

## Ⅷ. 결론

DDD의 본질은 객체를 예쁘게 나누는 것이 아니라 비즈니스 의미와 코드 구조와 팀 언어를 같은 방향으로 정렬하는 데 있음.
