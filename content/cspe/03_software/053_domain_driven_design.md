## 미리 알고가기

- DDD는 복잡한 비즈니스 도메인을 중심으로 모델과 코드를 설계하는 접근임
- Ubiquitous language는 도메인 전문가와 개발자가 함께 쓰는 공통 언어임
- Core domain은 경쟁력과 차별성이 집중된 핵심 업무 영역임

## 작성 근거(검토용)

- DDD는 설계 초점, 업무 규칙 표현, 적용 비용을 핵심 비교축으로 선정함
- 구성은 공통 언어, 모델 경계, 도메인 객체, 상태 변화 표현을 중심으로 제시함
- 실무 판단은 용어 충돌 건수, 모델·코드 불일치율, 변경 영향 범위로 구체화함

## Ⅰ. 개요

- **정의/개념**: DDD는 도메인 전문가와 개발자가 공통 언어를 만들고 이를 모델·코드·경계에 반영하는 소프트웨어 설계 접근법임
- **배경/필요성**: 복잡한 업무 규칙은 기술 계층만으로 의미를 표현하기 어려우므로 도메인 개념을 설계 중심에 둘 필요가 있음

## Ⅱ. 특징

- 공통 언어를 모델·코드 이름·팀 대화에 동일하게 사용함
- 업무 규칙의 변경 의미를 엔티티·값 객체·애그리게이트의 책임과 연결함
- 업무 규칙 변화가 적고 용어 의미가 단일한 서비스는 모델링·협업 비용이 편익을 초과할 수 있음
- bounded context, aggregate, domain event 같은 개념으로 경계를 체계화함

## Ⅲ. 종류 및 비교

| 판단 기준 | 기술 중심 설계 | DDD |
|:---|:---|:---|
| 설계 초점 | 계층 분리와 프레임워크 구조를 우선함 | 도메인 개념과 업무 규칙을 우선함 |
| 규칙 표현 | 화면·데이터 중심으로 CRUD 구현 | 공통 언어·entity·value object·aggregate로 업무 규칙 표현 |
| 주된 한계 | 비즈니스 의미가 코드에서 왜곡될 수 있음 | 도메인 탐색과 모델 정리에 시간과 비용이 듦 |
| 대표 환경 | 규칙이 적은 CRUD·단기 서비스 | 업무 규칙과 용어가 지속 변경되는 복합 도메인 |

> 요약: 규칙이 적은 CRUD는 기술 중심 설계, 업무 규칙과 용어가 지속 변경되면 DDD가 적합함.

## Ⅳ. 구성요소 및 구조

| 구성요소 | 설명 |
|:---|:---|
| 공통 언어 | 도메인 전문가와 개발자가 같은 업무 용어로 모델을 설명함 |
| 바운디드 컨텍스트 | 용어와 규칙이 유효한 모델 경계를 나눔 |
| 엔티티·값 객체 | 식별자 유무와 불변성에 따라 도메인 객체를 구분함 |
| 도메인 이벤트 | 다른 컨텍스트가 후속 처리해야 하는 상태 변화를 표현함 |

> 요약: 공통 언어로 업무 의미를 맞추고 컨텍스트 경계 안에서 객체와 상태 변화를 모델링함.

## Ⅵ. 실무 사례

1. 보험 계약 모듈은 공통 언어와 애그리게이트로 규칙을 표현하고 변경 영향 범위를 확인함
2. 장기 운영 플랫폼은 용어 사전과 모델 리뷰를 운영하고 용어 충돌·모델과 코드 불일치율을 확인함

## Ⅶ. 결론

DDD는 도메인 의미를 공통 언어·모델·코드에 일관되게 반영해 복잡한 업무 규칙의 변경 범위를 줄임
