## 핵심 인사이트 (3줄 요약)
- 에릭 에반스(Eric Evans)가 창시한 소프트웨어 설계 방법론으로, 시스템을 설계할 때 'DB 테이블'이나 '기능'이 아닌, 비즈니스 문제 영역인 **'도메인(Domain)'**을 중심에 두는 철학.
- 개발자와 도메인 전문가(기획자, 현업)가 **유비쿼터스 언어(Ubiquitous Language)**를 사용하여 완벽히 동일한 언어와 모델로 소통하고 코딩함.
- 마이크로서비스(MSA) 시대를 맞아, 거대한 시스템을 어떻게 쪼개야 하는지(Bounded Context)에 대한 가장 명확한 해답을 제시하며 업계 표준으로 자리 잡음.

## Ⅰ. 개요 및 필요성
- **개요**: 비즈니스 도메인의 복잡성을 해결하기 위해, 도메인 모델을 구축하고 이를 코드로 직결시키는 소프트웨어 공학 접근법.
- **필요성**: 개발자는 코드로 말하고 기획자는 비즈니스 용어로 말하다 보니, 요구사항이 코드로 변환되는 과정에서 치명적인 왜곡과 버그가 발생함. 소프트웨어가 복잡해질수록 '기술'보다 '비즈니스 자체의 규칙(도메인 지식)'을 코드에 정확히 담아내는 것이 더 중요해짐.
---
## Ⅱ. 아키텍처 및 핵심 원리
- **전략적 설계 (Strategic Design) - 시스템을 어떻게 나눌 것인가?**:
  1. **유비쿼터스 언어**: "결제한다", "승인한다" 등 팀 전체가 사전에 정의한 공통 언어. (코드의 클래스명/메서드명과 100% 일치해야 함).
  2. **바운디드 컨텍스트 (Bounded Context)**: 거대한 도메인을 논리적인 경계로 쪼갠 것. (예: '상품'이라는 단어가 '주문 컨텍스트'에서는 결제 대상이고, '배송 컨텍스트'에서는 박스 크기임. 이 경계를 명확히 나눔).
- **전술적 설계 (Tactical Design) - 내부를 어떻게 코딩할 것인가?**:
  1. **Entity (엔티티)**: 고유한 식별자(ID)를 가지며 상태가 변하는 객체 (예: 회원, 주문).
  2. **Value Object (값 객체)**: 식별자 없이 속성들로만 묶인 불변 객체 (예: 주소, 금액).
  3. **Aggregate (애그리거트)**: 엔티티와 값 객체들의 묶음이자, 트랜잭션과 데이터 일관성을 유지하는 최소 단위.

```text
[ DDD의 유비쿼터스 언어와 바운디드 컨텍스트 ]

 (비즈니스 요구사항) ➡️ [ 유비쿼터스 언어 (사전) ] ➡️ (실제 소스 코드 `Order.java`)
 
 [ 이커머스 시스템 (Domain) ]
 
      (바운디드 컨텍스트 A)                (바운디드 컨텍스트 B)
 +--------------------------+        +--------------------------+
 |       [ 주문 팀 ]          |        |       [ 배송 팀 ]          |
 |  '상품' = 주문할 품목(가격)  |  <====>  |  '상품' = 배송할 박스(부피)  |
 |                          |  (매핑)  |                          |
 +--------------------------+        +--------------------------+
 * 같은 단어라도 컨텍스트 경계가 다르면 의미와 모델이 완벽히 분리됨 (MSA 분리의 핵심)
```

## Ⅲ. 비교 및 연결
| 구분 | 데이터 주도 설계 (Data-Driven Design) | 도메인 주도 설계 (Domain-Driven Design) |
|---|---|---|
| **시작점** | ERD (DB 테이블) 설계부터 시작 | 비즈니스 용어와 행위 정의부터 시작 |
| **객체의 상태**| Getter/Setter로 무분별한 상태 변경 | 비즈니스 의미가 담긴 메서드(`cancelOrder()`)로 변경 |
| **협업 주체** | DBA, 아키텍트 중심 | 도메인 전문가(기획/운영) + 개발자 |
| **적합한 아키텍처**| Monolithic (전통적 시스템) | Microservices Architecture (MSA) |
---
## Ⅳ. 실무 적용 및 기술사 판단
- **DDD의 맹점(학습 곡선과 오버엔지니어링)**: DDD의 전술적 패턴(애그리거트, 리포지토리 패턴 등)은 매우 복잡함. 모든 프로젝트에 DDD를 도입하는 것은 재앙이며, CRUD 위주의 '서브 도메인'은 기존 방식(Active Record 등)으로 빠르게 짜고, 비즈니스 성공을 좌우하는 '핵심 도메인(Core Domain)'에만 DDD 역량을 집중해야 함.
- **MSA와의 찰떡궁합**: MSA에서 가장 어려운 "서비스를 어느 크기로 잘라야 하는가?"라는 질문에, DDD는 "바운디드 컨텍스트 단위로 자르면 된다"는 명확한 수학적/논리적 기준을 제공함.
---
## Ⅴ. 기대효과 및 결론
- "코드가 곧 비즈니스 문서가 되는 마법"을 통해, 수년 뒤에 새로 입사한 개발자도 코드(유비쿼터스 언어)만 읽고 비즈니스 룰을 100% 이해할 수 있게 됨.
- 기술 중심의 개발 문화를 비즈니스 가치 중심으로 혁신하며, 현대 복잡계 시스템을 지탱하는 가장 거대하고 강력한 소프트웨어 철학임.

### 👶 어린이를 위한 3줄 비유 설명
1. 예전에는 집을 지을 때, 벽돌(데이터베이스)을 어떻게 쌓을지만 고민하고 '이 방을 누가 쓸 건지'는 나중에 생각했어요.
2. 도메인 주도 설계(DDD)는 집에 살 '가족(기획자)'과 집을 짓는 '목수(개발자)'가 모여서, 먼저 "여기서 밥을 먹자!(비즈니스)"라고 공통의 언어로 꼼꼼히 대화부터 하는 거예요.
3. 그렇게 설계된 집은 가족들이 살기에 완벽하게 편리하고, 나중에 방을 고칠 때도 절대 헷갈리지 않는답니다!
