# 📖 【암기용】 개념 완전 이해

> 목적: 프로그레시브 딜리버리를 처음 봐도 배포 후 점진 공개와 자동 검증의 차이를 이해하게 만든다. 시험 답안 양식이 아니라, 이해를 위한 설명이다.
> 이 파일은 카나리·블루-그린의 배포 메커니즘 자체(070 참조)와 피처 플래그의 공개 제어 메커니즘 자체(307 참조)는 다시 설명하지 않는다. 이 파일이 새로 다루는 것은 그 위에 얹히는 **자동 지표 분석 → 승격/롤백 루프**다.

## 한눈에
- **개요**: **프로그레시브 딜리버리**는 **배포(Deploy)**와 **릴리스(Release)**를 분리하고, 신버전을 소수 트래픽·사용자에게 노출한 뒤 관측 지표를 **자동 분석**해 단계적으로 **승격(Promotion)**하거나 **롤백(Rollback)**하는 릴리스 전략이다.
- **왜 필요한가**: 카나리 배포만 도입하면 "1%에 내보낸다"까지는 되지만, 그 1%가 정상인지 판단하는 일은 여전히 사람이 대시보드를 보고 결정한다. 새벽 시간대 장애나 판단 지연이 그대로 사고로 이어진다. 프로그레시브 딜리버리는 이 판단 자체를 지표 기준으로 자동화한다.
- **핵심 직관**: 신약 임상시험처럼 소수 대상에서 이상 반응을 확인하고 단계적으로 대상을 늘리되, 이상 반응 여부를 사람이 매번 회의를 열어 판단하는 게 아니라 "이 수치를 넘으면 즉시 중단"이라는 **자동 판정 규정(SLO)**을 미리 정해두는 방식이다.

## 핵심 용어 정리 (내부에 등장하는 것들)

| 용어 | 의미 | 비유 |
|:---|:---|:---|
| 배포(Deploy) | 새 코드를 운영 서버에 올리는 것 — 아직 사용자에게 보이지 않을 수 있음 | 창고에 신제품을 입고하는 것 |
| 릴리스(Release) | 사용자가 실제로 그 기능을 쓸 수 있게 공개하는 것 — 배포와 시점이 분리될 수 있음 | 창고 물건을 매장 진열대에 꺼내는 것 |
| 카나리(Canary) | 신버전에 트래픽을 소량부터 늘려가며 검증하는 방식 (070 참조) | 새 메뉴를 일부 손님에게 먼저 내보는 시식 |
| 블루-그린(Blue/Green) | 구·신버전을 동일 규모로 병렬 운영하다 라우팅을 일괄 전환하는 방식 (070 참조) | 새 매장을 통째로 준비해두고 간판만 바꿔 다는 것 |
| 피처 플래그(Feature Flag) | 배포된 코드의 기능 노출 여부를 런타임 설정으로 켜고 끄는 장치 (307 참조) | 이미 설치된 전등의 스위치 |
| 트래픽 스플릿(Traffic Split) | 로드밸런서·서비스 메시가 신버전으로 보내는 요청 비율을 나누는 것 | 수도꼭지를 몇 %만 여는 것 |
| SLO / Guardrail Metric | "이 수치를 넘으면 실패로 간주한다"는 사전 합의된 임계값(5xx율, p95, 전환율 등) | 임상시험의 중단 기준(부작용 발생률 몇 % 이상이면 즉시 중단) |
| 자동 분석(Automated Analysis) | 카나리군과 기준(baseline)군의 지표를 통계적으로 비교해 통과·실패를 자동 판정하는 절차 | 임상시험의 자동 통계 검정 |
| 승격(Promotion) / 롤백(Rollback) | 분석 통과 시 다음 비율로 확대 / 실패 시 이전 상태로 자동 복귀 | 다음 병동으로 확대 / 시험 중단하고 원상복구 |
| Delivery Controller | 위 전체 루프(배포-노출-분석-승격/롤백)를 조율하는 도구 | 임상시험 전체를 관장하는 운영위원회 |

## 깊이 이해

### 왜 카나리·플래그만으로는 부족한가 (배경)
- 070에서 다룬 카나리·블루-그린은 "트래픽을 어떻게 나눌지"를, 307에서 다룬 피처 플래그는 "기능을 누구에게 보일지"를 다룬다. 두 기법 모두 **메커니즘**일 뿐, "지금 이 상태가 정상인가"를 판단하는 주체는 별도로 필요하다.
- CI/CD 도입 이후 배포 빈도가 하루 수십 회로 늘면서, 사람이 매 배포마다 대시보드를 보고 승격을 결정하는 방식은 확장되지 않는다. 프로그레시브 딜리버리는 이 판단을 SLO 기준의 자동 통계 비교로 대체해 배포 빈도를 유지하면서도 판단 속도와 일관성을 확보한다.

### 승격 루프를 수치로 이해하기
- 결제 서비스 v2를 배포한다고 하자. 1단계로 트래픽 1%만 카나리로 보내고 10분간 지표를 쌓는다.
- 자동 분석: 기준(baseline, 구버전 v1) 5xx율 0.05%, 카나리(v2) 5xx율 0.08% → 사전에 정한 guardrail(0.1%) 이내이므로 통과. p95도 baseline 280ms, canary 295ms로 기준(300ms) 이내 → 통과. 핵심 전환율(결제 성공률)도 baseline 대비 -0.2%p로 guardrail(-0.5%p) 이내 → 통과.
- 통과하면 5% → 25% → 50% → 100%로 단계마다 같은 분석을 반복한다. 만약 25% 단계에서 카나리 5xx율이 0.4%로 튀면(baseline은 여전히 0.05%) guardrail(0.1%)을 넘으므로 즉시 실패 판정되고, Delivery Controller가 트래픽을 5분 이내 자동으로 0%로 되돌린다(rollback).
- 이 반복에서 핵심은 baseline과 canary를 **동시에·같은 시간대에** 비교한다는 점이다. 시간대가 다르면 트래픽 패턴 차이(예: 점심시간 vs 새벽)가 지표 차이로 오인될 수 있기 때문이다.

### 배포와 릴리스를 분리하는 원리
- 피처 플래그를 결합하면 "코드는 100% 배포했지만 기능은 0% 공개"인 상태를 만들 수 있다. 이렇게 배포(위험이 낮은 인프라 작업)와 릴리스(위험이 있는 사용자 노출)를 분리하면, 장애 원인이 "새 코드 자체의 버그"인지 "기능이 켜지면서 생긴 문제"인지 구분하기 쉬워진다 — 코드 롤백 없이 플래그만 꺼서 즉시 복구할 수 있다.

### 비유와 흔한 오해
- **비유**: 신약 임상시험 4단계(소규모 안전성 → 확대 → 대규모 효능 → 시판 후 감시)와 동일한 구조다. 각 단계마다 "부작용 발생률이 몇 %를 넘으면 중단"이라는 규정이 미리 있고, 이 규정을 사람이 매번 재해석하지 않고 기계적으로 적용한다.
- **오해**: 카나리 배포를 도입했다고 프로그레시브 딜리버리를 한다고 착각하기 쉽다. 지표 기준(guardrail), 자동 분석, 자동 롤백, 관측성(Observability) 네 가지가 모두 갖춰져야 "자동화된 릴리스 전략"이라 부를 수 있다. 사람이 수동으로 대시보드를 보고 승격 버튼을 누르는 방식은 여전히 카나리 배포 단계에 머문 것이다.

## 연결 개념
- 070 카나리·블루-그린 배포 (트래픽 전환 메커니즘, 선행 개념)
- 307 피처 토글·실험 플랫폼 (기능 공개 제어 메커니즘, 선행 개념)
- 192 SLO/SLA/SLI (승격·중단을 결정하는 품질 기준의 정의)

# 📝 【답안용】 시험 답안 템플릿

> 목적: 시험장에서 25분에 그대로 쓰는 답안 양식. Progressive Delivery는 배포 전략 나열이 아니라 지표 기반 자동 확대·중단 판단으로 답한다.

## 핵심 인사이트 (3줄 요약)

> 1. **본질**: Progressive Delivery는 새 버전을 트래픽·사용자 비율별로 점진 노출하고 관측 지표로 확대·중단을 자동 결정하는 릴리스 방식이다.
> 2. **가치**: 배포와 공개를 분리해 장애 반경을 제한하고, SLO 기반으로 롤백 판단을 표준화한다.
> 3. **판단 포인트**: 트래픽 분할, 지표 수집, 자동 분석, 롤백 시간이 모두 설계되어야 단순 Canary와 구분된다.

## 출제 의도 및 답안 포인트

| 출제 의도 | 반드시 짚을 핵심 | 감점 회피 포인트 |
|:---|:---|:---|
| 릴리스 전략 이해 확인 | Canary, Blue/Green, Feature Flag, Traffic Split | Canary만 설명하고 자동 분석 누락 |
| 운영 품질 판단 확인 | 오류율, p95, 비즈니스 지표, SLO | 배포 성공률만 지표로 제시 |
| 자동화·롤백 역량 확인 | Analysis, Promotion, Rollback | 수동 승인만으로 마무리 |

> 요약: 이 문제는 새 버전을 어떻게 조금씩 노출하고 어떤 기준으로 중단할지 묻는다.

---

## Ⅰ. 개요 및 필요성

- 개요: 신규 버전의 단계적 공개 방식
- 배경: 전체 배포는 결함 발생 시 사용자 영향 범위가 넓고 원인 추적 시간이 길어짐
- 필요성: Canary, Blue-Green, SLO Gate로 트래픽 비율과 중단 기준을 통제해 장애 반경과 롤백 시간을 제한해야 함

---

## Ⅱ. 구조 및 구성요소

```text
Developer -> CI/CD -> Delivery Controller -> Traffic Router -> Stable/Canary -> Observability
  / Feature Flag
  / SLO Analysis
  / Rollback
```

| 구성요소 | 역할 | 특이사항 |
|:---|:---|:---|
| Delivery Controller | 배포 단계와 승격 정책 제어 | Argo Rollouts, Flagger |
| Traffic Router | 트래픽 비율 분할 | Ingress, Service Mesh |
| Observability | 오류·지연·비즈니스 지표 수집 | Prometheus, APM, 로그 |
| Feature Flag | 사용자·기능 단위 공개 | 코드 배포와 공개 분리 |

> 요약: Controller가 트래픽을 나누고 Observability 지표를 판단해 승격 또는 롤백을 수행한다.

---

## Ⅲ. 동작원리 및 흐름도

```text
신규 버전 배포 -> 1% 노출 -> 지표 분석 -> 5% 확대 -> 지표 분석 -> 100% 승격 또는 롤백
```

| 단계 | 처리 내용 | 검증 기준 |
|:---:|:---|:---|
| 1 | Canary 버전 배포 | readiness, smoke test |
| 2 | 소량 트래픽 분배 | 1% 또는 내부 사용자 |
| 3 | 자동 분석 | 5xx, p95, error budget |
| 4 | 단계 확대 | 5%, 25%, 50%, 100% |
| 5 | 승격·롤백 | SLO 위반 시 5분 이내 rollback |

> 요약: Progressive Delivery는 소량 노출과 지표 분석을 반복하며 조건 충족 시 승격하고 위반 시 롤백한다.

---

## Ⅳ. 특징

| 구분 | 전통 배포 | Progressive Delivery | 수치·판단 포인트 |
|:---|:---|:---|:---|
| 공개 범위 | 전체 즉시 공개 | 1%부터 단계 공개 | 장애 반경 제한 |
| 판단 기준 | 배포 성공 | SLO·비즈니스 지표 | 5xx 0.1%, p95 300ms |
| 롤백 | 수동 재배포 | 자동 rollback | MTTR 10분 이하 |
| 실험 | 별도 분석 | Flag·Canary 연계 | 전환율 변화 0.5%p |

> 요약: Progressive Delivery는 배포 완료보다 사용자 지표를 기준으로 릴리스 승격 여부를 판단한다.

## Ⅴ. 심화 비교 및 적용 판단

| 비교 축 | 기존/대안 | 본 키워드 | 선택 기준 |
|:---|:---|:---|:---|
| Blue/Green | 즉시 전체 전환 | 단계별 트래픽 전환 | 사용자 영향 최소화 필요 |
| Canary | 소량 검증 | 자동 분석·승격 포함 | SLO 기반 자동화 필요 |
| Feature Flag | 기능 공개 제어 | 배포·트래픽·기능 통합 | 사용자군별 점진 공개 |

> 요약: Progressive Delivery는 Canary, Blue/Green, Feature Flag를 지표 기반 승격 절차로 묶는 상위 운영 방식이다.

| 리스크 | 원인 | 대응 방안 | 확인 지표 |
|:---|:---|:---|:---|
| 잘못된 승격 | 지표 부족 | guardrail metric, 최소 관측 시간 | false promotion 건수 |
| 트래픽 불균형 | 세션 고정·캐시 영향 | consistent hashing, header routing | canary traffic 오차 1%p 이하 |
| 롤백 실패 | DB 변경 비호환 | backward compatible schema | rollback success rate |

> 요약: 지표 설계, 트래픽 분배, 스키마 호환성이 Progressive Delivery의 핵심 리스크이다.

| 점검 항목 | 목표 기준 | 측정 방법 |
|:---|:---|:---|
| 품질 | 5xx 0.1% 이하, p95 300ms 이하 | Prometheus, APM |
| 롤백 | 5분 이내 자동 rollback | CD 로그 |
| 트래픽 | 설정 비율 대비 오차 1%p 이하 | Ingress, mesh metric |

> 요약: 품질, 롤백 시간, 트래픽 분배 정확도가 릴리스 성공 기준이다.

## Ⅵ. 실무 적용 및 결론

**적용 방안 3개 (필수):**
1. Argo Rollouts 또는 Flagger로 1%, 5%, 25%, 50%, 100% 승격 단계를 정의하고 각 단계 최소 관측 시간을 30분으로 설정함.
2. 승격 조건은 5xx 0.1% 이하, p95 300ms 이하, 핵심 전환율 하락 0.5%p 이내로 정의함.
3. DB 변경은 expand-contract, backward compatible API, feature flag off 경로를 준비해 rollback success rate 100%를 목표로 함.

**결론 (2줄):**
- 기술사 판단: 사용자 영향이 큰 서비스와 배포 빈도가 높은 조직은 Progressive Delivery, 내부 배치성 서비스는 Blue/Green 또는 Rolling Update로 충분함.
- 향후 방향: 릴리스 판단은 SLO와 비즈니스 guardrail을 결합한 자동 분석, AIOps 기반 이상 탐지와 연결됨.
