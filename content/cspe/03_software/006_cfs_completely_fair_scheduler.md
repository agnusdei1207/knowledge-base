# 📖 【암기용】 개념 완전 이해

> 목적: 이 개념을 처음 보는 사람도 완벽히 이해하게 만든다. 시험 답안 양식이 아니라, 이해를 위한 친절한 설명이다.

## 한눈에
- **개요**: 현재 전 세계 리눅스(Android, K8s, 서버)의 기본 스케줄러다. "착한 애는 많이 주고 나쁜 애는 쫓아내자"는 복잡한 계급장(MLFQ)을 버리고, 오직 **"태어나서 지금까지 CPU를 제일 적게 만진 녀석(가장 불쌍한 녀석)을 무조건 1등으로 시켜주자"**라는 단일 원칙으로 돌아가는 알고리즘이다.
- **왜 필요한가**: 과거의 스케줄러(O(1) 등)는 휴리스틱(꼼수) 코드가 너무 많았다. "I/O를 많이 하니까 얘는 상위 큐에 넣자, 얘는 하위 큐에 넣자" 하다 보니 코드가 지저분해지고 예측할 수 없는 렉(버그)이 생겼다. 이를 싹 밀어버리고 완벽한 수식 하나로 공평함을 증명하기 위해 탄생했다.
- **핵심 직관**: CFS에는 줄을 서는 큐(Queue)가 없다. 대신 모든 프로세스의 이름 옆에 "CPU 쓴 시간(vruntime)"이라는 장부 점수가 적혀 있다. 10명이 게임기(CPU)를 돌려 쓸 때, OS는 무조건 점수가 제일 낮은 녀석을 불러 게임기를 쥐여준다.

## 깊이 이해
- **배경·문제의식**: 유닉스의 MLFQ나 이전 리눅스 스케줄러들은 프로세스를 강등/승격시키는 타임 파라미터를 관리자가 일일이 튜닝해야 했다. 워크로드가 달라지면 세팅도 달라져야 하는 한계가 명확했다.
- **작동 원리**: 
  - CFS는 '타임 퀀텀(고정 시간)' 개념 대신 **'목표 지연 시간(Target Latency)'**을 쓴다. (예: 20ms)
  - 만약 프로세스가 4개면 20ms를 공평하게 나눠 각자 5ms씩 쪼개준다. (프로세스가 늘어나면 쪼개지는 파이도 작아진다)
  - 프로세스들은 자신이 CPU를 쓴 실제 시간에 가중치(nice 값)를 곱한 **vruntime(가상 실행 시간)**을 누적한다.
  - 이 장부 점수들을 **레드-블랙 트리(Red-Black Tree)**라는 자료구조에 담아둔다. vruntime이 가장 작은 놈은 항상 트리의 가장 왼쪽 맨 밑(O(1) 추출 가능 위치)에 온다.
- **비유**: 피자 1판(Target Latency)을 놓고, 모인 사람 수만큼 알아서 칼집(타임 퀀텀)을 낸다. 그리고 "지금까지 피자를 제일 덜 먹은 사람(vruntime 최저점)"을 무조건 먼저 먹게 한다.
- **구체 예시**: 잠만 자느라 CPU를 한 번도 못 쓴 키보드 입력 프로세스가 깨어났다. 얘의 vruntime은 바닥이므로, 깨어나자마자 기존에 돌고 있던 무거운 동영상 인코딩 프로세스들을 다 밀어내고 즉시 CPU를 차지한다. 덕분에 화면 스크롤이나 타이핑 렉이 전혀 없다.
- **흔한 오해·주의점**: CFS는 "모두에게 똑같은 시간을 준다"가 아니다. 우선순위(nice)가 높은 프로세스는 10초를 썼어도 장부(vruntime)에는 1초만 쓴 것으로 깎아서 적어준다. 반대로 우선순위가 낮으면 1초만 써도 10초 쓴 것으로 뻥튀기해 적는다. 공평함의 기준이 '시간'이 아니라 '가중치가 반영된 장부(vruntime)'라는 점이 핵심이다.

## 연결 개념
- **Nice 값 (우선순위 가중치)**: -20부터 19까지 있으며, 낮을수록 CPU를 더 자주 받는다. CFS에서는 이 값이 vruntime이 오르는 '속도'를 결정한다.
- **스케줄링 대역폭 제어 (CFS Bandwidth Control)**: 도커나 쿠버네티스에서 `CPU Limit: 0.5`를 걸면, 딱 50%만 쓰고 강제로 잠들게(Throttle) 만드는 CFS의 계층적 자원 통제 기술이다.

# 📝 【답안용】 시험 답안 템플릿

> 목적: 시험장에서 25분에 그대로 쓰는 답안 양식. 작성방식(추상표현 금지·수치·도식·문제유형 전환)을 엄격히 지킨다.
> 핵심: 이 시험은 정보를 많이 나열하는 시험이 아니라, 문제 신호어에서 출제자 의도를 읽고 핵심 논점을 선별해 쓰는 시험이다.

## 핵심 인사이트 (3줄 요약)

> 1. **본질**: 복잡한 휴리스틱 다단계 큐(MLFQ)를 폐기하고, 누적 CPU 사용량(vruntime) 기반의 Red-Black 트리 구조로 공정성을 수식화한 리눅스 표준 스케줄러
> 2. **가치**: 목표 지연 시간(Target Latency) 안에서 프로세스 수에 비례해 타임 슬라이스를 동적 분할하므로, 튜닝 파라미터 없이도 대화형(I/O) 응답성과 연산(CPU) 처리량을 통합
> 3. **판단 포인트**: CFS가 공정함을 구현하는 매커니즘은 단순한 시간 쪼개기가 아니라, 우선순위(nice) 가중치를 역산하여 vruntime 증가 속도를 조절하는 수학적 장부 설계에 있음을 짚어야 한다.

## 출제 의도 및 답안 포인트

| 출제 의도 | 반드시 짚을 핵심 | 감점 회피 포인트 |
|:---|:---|:---|
| 기존 다단계 큐(MLFQ) 스케줄러의 한계 극복 원리 | 휴리스틱 배제, vruntime(가상 실행 시간), 동적 타임 퀀텀 | 고정 타임 퀀텀을 쓴다고 서술하는 치명적 오류 (CFS는 동적 파이 분배) |
| 고속 스케줄링을 위한 커널 자료구조 이해 | Red-Black 트리의 좌측 최하단 탐색 O(1), 삽입 O(logN) | FIFO 큐 구조로 도식화하는 실수 |

> 요약: 스케줄링 규칙을 "누가 큐의 몇 층에 있는가"에서 "누구 장부 값이 제일 작은가"로 패러다임을 바꾼 컴퓨터 과학의 미니멀리즘(뺄셈 철학) 정수다.

## Ⅰ. 개요 및 필요성

- 정의: 프로세스들의 CPU 누적 사용 시간을 가상 실행 시간(vruntime)으로 환산하여, 이 값이 가장 작은 프로세스에게 우선적으로 CPU를 할당하는 리눅스 커널 완전 공정 스케줄러
- 배경: 과거 O(1) 스케줄러 등은 대화형 프로세스를 우대하기 위해 복잡한 조건문(휴리스틱 꼼수)을 남발하여, 커널 유지보수가 불가능해지고 엣지 케이스에서 렉(Latency) 발생
- 필요성: 모바일(Android)의 즉각적인 터치 반응부터 10만 개의 스레드가 도는 K8s 클라우드 서버까지, 단 하나의 스케줄링 아키텍처로 모든 워크로드를 방어하는 범용 통일성 확보

## Ⅱ. CFS 코어 아키텍처 (Red-Black 트리 구조도)

```text
[ 물리 CPU 코어 ]
        |
[ CFS Runqueue (Red-Black Tree) ]  -> vruntime 값 기준 정렬
        |
        +-- (Root) [ vruntime: 12ms ]
            /                        \
    [ 8ms ]                        [ 20ms ]
    /      \                       /      \
[ 3ms ]  [ 10ms ]             [ 18ms ]  [ 30ms ]
  ^
  | 
(스케줄러 픽업 O(1) 포인트: 트리의 가장 왼쪽 단말 노드 = vruntime 최소값)
```

| 구성요소 | 커널(OS) 처리 역할 | 성능 지표 (Big-O) |
|:---|:---|:---|
| 레드-블랙 트리 | 스스로 밸런스를 맞추는 이진 탐색 트리로, 삽입/삭제 시 트리의 높이가 한쪽으로 치우치지 않음 보장 | 트리에 다시 꽂아 넣는(삽입) 시간 O(log N) |
| Leftmost Node 포인터 | 트리의 맨 왼쪽 끝(vruntime이 가장 작은 녀석)을 커널 변수에 캐싱해 둠 | 다음 실행 프로세스를 뽑아내는 시간 O(1) |
| 가상 실행 시간 (vruntime) | 실제 CPU 사용 시간에 프로세스 우선순위(nice)에 따른 가중치를 곱하여 누적 계산 | N/A (판단 기준점) |

> 요약: CFS에는 전통적인 큐(Queue)가 없다. 항상 정렬되어 있는 족보(Tree)에서 맨 막내(왼쪽)를 꺼내 밥을 먹이고 다시 족보에 꽂아 넣는 과정의 반복이다.

## Ⅲ. CFS의 2대 혁신: 동적 분할(파이 쪼개기)과 가상 장부

```text
[ 1. 목표 지연 시간(Target Latency) 기반 동적 타임 슬라이스 분할 ]
Target = 20ms (고정)
- 프로세스 2개: 20ms / 2 = 각 10ms 부여
- 프로세스 4개: 20ms / 4 = 각 5ms 부여 
(단, 스위칭 폭주 방지를 위해 sched_min_granularity_ns = 3ms 하한선 방어벽 존재)

[ 2. vruntime(가상 시간) 계산 방정식 ]
vruntime += (실제 사용 시간) * (기본 가중치 / 현재 프로세스의 가중치)
```

| 원리 | 전통적 스케줄러(RR/MLFQ) | 리눅스 CFS |
|:---|:---|:---|
| 타임 퀀텀 배분 | 정해진 고정 시간(예: 10ms)을 무조건 줌 | 커널 지연 목표치 안에서 N등분하여 유동적으로 쪼개 줌 |
| 우선순위(Nice) 적용 | 우선순위가 낮으면 타임 퀀텀을 적게 줌 | 높은 녀석은 10초를 써도 vruntime에 1초만 적어줌 (느리게 증가), 낮은 녀석은 1초만 써도 10초로 적음 (빠르게 증가) |
| I/O 바운드 우대 | I/O 요청 시 상위 큐로 인위적 승격 | 잠자느라 vruntime이 안 올랐으므로, 깨어나는 순간 트리의 최좌측에 놓여 '자동' 최우선 실행 |

> 요약: CFS는 I/O 바운드를 우대하는 코드를 단 한 줄도 짜지 않았다. 단지 자느라 밥(CPU)을 못 먹었으니 점수가 바닥일 뿐이고, 그래서 자동으로 우대받는 우아한 수식이다.

## Ⅳ. 극복해야 할 리스크 및 커널 실무 방어 기법

| 리스크 (취약점) | 해커의 공격 / 오동작 시나리오 | 커널 방어 매커니즘 (튜닝) |
|:---|:---|:---|
| Fork() 폭탄 호위 효과 | 프로세스가 `fork()`로 자식을 10만 개 생성. 신규 자식의 vruntime이 0이면 모든 CPU를 탈취함 | **vruntime 상속 및 패널티**: 신규 생성 프로세스는 0이 아니라 현재 트리의 `min_vruntime` 값 이상을 부여받아 태어나게 하여 새치기 원천 차단 |
| 극단적 컨텍스트 스위칭 | 트래픽 폭주로 스레드가 1,000개 뜰 경우 파이 분할 수식에 의해 퀀텀이 0.02ms로 극단적 쪼개짐 발생 | **최소 보장 퀀텀 (Min Granularity)**: 커널 파라미터 `sched_min_granularity_ns` (예: 3ms) 설정으로, 프로세스가 아무리 많아도 이 시간 이하는 쪼개지 않게 방어 |

> 요약: CFS의 완벽한 수학 방정식도 10만 개의 스레드가 쏟아지는 클라우드 폭격 앞에서는 무너지므로, 최소 보장 파이 조각(3ms)이라는 커널의 안전장치가 필수다.

## Ⅴ. 쿠버네티스(Cgroups) 자원 격리 연계 (CFS Bandwidth Control)

| 자원 통제 계층 | CFS의 계층적 제어 매커니즘 | 실무 클라우드 매핑 (Docker/K8s) |
|:---|:---|:---|
| 그룹 스케줄링 | 트리의 노드에 단일 스레드가 아니라 그룹(Cgroups) 자체를 통째로 매핑 | K8s Pod나 Docker 컨테이너 단위의 자원 경쟁 구조 형성 |
| 대역폭 할당 한도 | 일정 기간(Period, 100ms) 내에 할당된 쿼터(Quota, 50ms) 소진 검사 | K8s 매니페스트의 `CPU Limit: 0.5` 옵션 처리 |
| 강제 스로틀링 | 그룹 내 스레드들이 쿼터를 다 쓴 즉시 그룹 전체를 CFS 트리에서 뽑아내어 유배(Sleep) 보냄 | Limit에 걸린 컨테이너가 CPU를 더 쓰지 못하고 멈춤 (Throttling 지연 폭발) |

> 요약: 도커나 K8s에서 컨테이너 CPU 제한이 마법처럼 오차 없이 동작하는 진짜 이유는, 커널 밑단의 CFS가 Cgroups 트리를 뽑아버렸다 꽂았다를 반복(스로틀링)하기 때문이다.

## Ⅵ. 실무 적용 방안 및 결론

**적용 방안 3개:**
1. [쿠버네티스 스로틀링(Throttling) 해결 튜닝] K8s 컨테이너에 CPU Limit을 걸었을 때 멀티스레드 앱(Java)에서 쿼터(Quota)가 순식간에 소진되어 지연(Latency)이 치솟는 CFS 버그 완화를 위해, 커널 버전을 5.14 이상으로 올리고 `CPU Request`만 걸어 완전 공정 분배 유도
2. [DB 서버 (PostgreSQL) 전용 최적화] I/O와 무거운 쿼리가 동반되는 배치 서버의 캐시 히트율을 극대화하기 위해, 커널의 `sched_latency_ns`(파이 크기)를 24ms 등 크게 늘려 잦은 트리 좌우 스위칭을 억제하고 스루풋 중심 환경으로 변조
3. [안드로이드 터치 응답성 향상] 모바일 화면 터치 시 발생하는 UI 스레드 렌더링에 대해, 리눅스 CFS의 nice 값을 극도로 낮게 주어 vruntime 팽창을 지연시킴으로써 프레임 드랍(Jank) 없이 화면을 강제 장악하도록 아키텍처 설계

**결론:**
- 기술사 판단: 스케줄링이란 결국 튜닝 파라미터(휴리스틱)와의 싸움이다. CFS는 이를 vruntime이라는 단일 수식 하나로 추상화함으로써, 성능뿐만 아니라 소프트웨어 공학적으로 가장 우아한 커널 코드를 완성해 냈다.
- 향후 방향: 모바일 기기의 big.LITTLE 코어(크고 작은 전력 코어 섞임) 등장에 맞춰, 단순히 공정하게 CPU를 주던 CFS는 이제 소비 전력(Energy) 대비 효율까지 계산하여 코어를 할당하는 EAS(Energy Aware Scheduling) 모델로 완전히 진화하였다.

### 🔀 문제 유형별 목차 전환 (이 키워드 출제 시)
