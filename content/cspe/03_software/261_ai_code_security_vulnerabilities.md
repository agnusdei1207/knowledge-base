# 📖 【암기용】 개념 완전 이해

> 목적: AI 코드 생성 보안 취약점을 처음 봐도 이해하게 만든다. 시험 답안 양식이 아니라, 이해를 위한 설명이다.

## 한눈에
- **개요**: AI 코드 생성 보안 취약점은 **소프트웨어 공급망 보안(Software Supply Chain Security)**의 한 영역으로, LLM 기반 코드 어시스턴트(Copilot 등)가 제안한 코드에 CWE 취약점, 비밀정보 노출, 취약 의존성, 라이선스 위반이 섞여 들어가는 위험을 말한다.
- **왜 필요한가**: Copilot류 도구는 개발 속도를 크게 높이지만, 제안된 코드를 검증 없이 그대로 병합하면 SQL Injection, 하드코딩된 비밀키, 오래된 취약 패키지가 배포 파이프라인에 그대로 들어간다.
- **핵심 직관**: AI가 만든 코드는 동료 개발자가 급하게 쓴 초안처럼 다뤄야 한다. 초안은 초안일 뿐, SAST·SCA·Secret Scan·사람 리뷰라는 관문을 통과해야 비로소 제품 코드가 된다.

## 핵심 용어 정리 (내부에 등장하는 것들)

| 용어 | 의미 | 비유 |
|:---|:---|:---|
| 소프트웨어 공급망 보안 | 코드 작성부터 의존성·빌드·배포까지 이어지는 전 과정에서 유입되는 보안 위험을 관리하는 영역 — AI 코드 생성은 그 유입 경로 중 하나 | 식품 안전에서 재료 산지부터 조리까지 전 과정을 관리하는 것 |
| DevSecOps | 개발(Dev)·보안(Sec)·운영(Ops)을 분리하지 않고 파이프라인 전 단계에 보안 검증을 내장하는 방식론 | 완성 후 검사가 아니라 공정 각 단계마다 품질 검사대를 두는 것 |
| CWE (Common Weakness Enumeration) | 소프트웨어에서 반복적으로 나타나는 결함 유형을 번호로 분류한 표준 목록 — 예: CWE-89(SQL Injection), CWE-798(하드코딩된 자격증명) | 질병을 코드로 분류하는 국제질병분류(ICD)와 유사 |
| SAST (정적 애플리케이션 보안 테스트) | 코드를 실행하지 않고 소스 자체를 분석해 취약 패턴을 찾는 도구 | 시험 답안을 채점하기 전에 문법·논리 오류부터 훑어보는 것 |
| SCA (소프트웨어 구성요소 분석) | 프로젝트가 사용하는 오픈소스 라이브러리의 알려진 취약점(CVE)과 버전을 점검하는 도구 | 조립 부품마다 리콜 대상인지 확인하는 것 |
| Secret Scan | 소스코드·커밋·프롬프트에 API 키, 비밀번호 같은 비밀정보가 노출됐는지 찾는 검사 | 우편물을 보내기 전 봉투 속에 신분증이 들어있는지 확인하는 것 |
| License Scan | 코드나 추천된 패키지에 사용 제한이 있는 라이선스(GPL 등)가 섞였는지 검사하는 것 | 표절 검사기가 출처와 이용 조건까지 확인하는 것 |
| SBOM (Software Bill of Materials) | 소프트웨어에 포함된 모든 구성요소(패키지·버전·출처)를 기록한 명세서 | 가공식품의 원재료 성분표 |
| CVSS (Common Vulnerability Scoring System) | 취약점의 심각도를 0~10점으로 계량화한 점수 체계 — 보통 7.0 이상을 High/Critical로 분류 | 태풍의 강도를 등급으로 매기는 것 |
| Hard-coded Credential | 비밀번호·API 키 등을 변수나 설정이 아니라 소스코드에 문자열로 직접 박아 넣는 것(CWE-798) | 현관 비밀번호를 문에 포스트잇으로 붙여두는 것 |
| Prompt Leakage | 사내 코드나 비밀정보가 LLM 프롬프트에 실려 외부로 전송되는 위험 | 상담 중 무심코 고객 주민번호를 남에게 불러주는 것 |

## 깊이 이해

### 배경 — 왜 AI가 취약한 코드를 제안하는가
LLM은 공개된 코드 저장소와 질의응답 사이트의 방대한 예제를 학습해, 문맥상 "그럴듯한" 코드를 생성한다. 문제는 학습 데이터 자체에 오래된 취약 패턴(레거시 API, 문자열 결합 SQL, 검증 안 된 입력 처리)이 다수 섞여 있다는 점이다. LLM은 "이게 안전한가"를 판단하는 게 아니라 "문맥상 흔히 쓰이는 형태"를 재현하므로, 낡고 위험한 관용구도 자연스러운 문장처럼 함께 따라온다.

### 구체 예시로 보는 CWE-89 SQL Injection
AI가 다음과 같은 Java 코드를 제안했다고 하자.

```
String sql = "SELECT * FROM user WHERE id = " + userInput;
```

이 코드는 사용자 입력을 SQL 문자열에 그대로 이어붙인다. 만약 userInput에 `1; DROP TABLE user;--` 같은 문자열이 들어오면 원래 쿼리 뒤에 임의 SQL이 추가 실행될 수 있다 — 이것이 CWE-89 SQL Injection이다. 겉보기엔 자연스러운 코드지만, `PreparedStatement`로 바인딩 변수를 쓰거나 ORM의 파라미터 바인딩을 쓰면 입력값이 SQL 구문으로 해석되지 않아 이 위험이 사라진다. SAST 룰셋은 바로 이런 문자열 결합 패턴을 자동으로 잡아내 병합 전에 차단한다.

### CVSS 점수로 심각도를 수치화하는 법
발견된 취약점은 그냥 "위험하다"가 아니라 CVSS 점수로 등급화된다. 예를 들어 인증 없이 원격에서 실행 가능한 취약점은 9점대(Critical), 특정 조건에서만 정보가 노출되는 취약점은 4~5점대(Medium)로 매겨진다. 조직은 보통 "CVSS 7.0 이상은 병합 차단"처럼 수치 기준을 배포 게이트로 못 박는다 — 이렇게 하면 "심각해 보인다"는 주관 판단 없이 자동화된 차단이 가능하다.

### SDLC 각 지점의 통제 흐름
1. **IDE 단계**: 사내 코드·비밀정보가 프롬프트로 외부에 전송되지 않도록 컨텍스트 범위를 제한하고, AI가 생성한 코드에는 PR 라벨을 자동으로 붙여 추적 가능하게 한다.
2. **PR 리뷰 단계**: 개발자가 요구사항·경계값·예외 처리를 사람 눈으로 검토한다 — AI 코드라도 이 단계를 생략하지 않는다.
3. **CI 게이트 단계**: SAST·SCA·Secret Scan·License Scan을 병렬로 돌려, CVSS 7.0 이상·하드코딩된 키·금지 라이선스가 발견되면 자동으로 병합을 막는다.
4. **감사 단계**: 예외로 병합을 허용해야 할 때는 승인자·사유·만료일을 남기고, 통상 30일 단위로 재검토한다. 왜 30일인가 — 예외를 무기한 허용하면 "임시"가 영구화되므로, 주기적 재평가로 부채가 방치되지 않게 강제하는 것이다.

### 판별 원리 — 언제 차단, 언제 경고만 하는가
같은 취약점이라도 서비스 성격에 따라 대응 강도가 다르다. 사내 업무 도구처럼 노출 범위가 제한적인 경우는 경고 후 개발자 재량에 맡기는 정도로도 충분할 수 있다. 반면 대외 서비스, 금융, 개인정보를 다루는 코드는 CVSS 기준을 넘으면 예외 없이 자동 차단하는 게이트를 둔다. 즉 "위험이 실제 사용자·법적 책임으로 이어질 수 있는가"가 차단 여부의 기준이다.

### 비유와 흔한 오해
- **비유**: 자동완성으로 계약서를 쓰되 법무 검토 없이 날인하지 않는 것과 같다. 문장이 자연스러워도 조항의 법적 책임은 작성자(서명자)에게 남는다.
- **오해**: "AI가 만든 코드라 책임이 줄어든다" — 틀렸다. 운영 장애, 개인정보 유출, 오픈소스 라이선스 위반의 법적·업무적 책임은 그 코드를 채택하고 배포한 조직과 개발자에게 그대로 남는다. AI는 도구일 뿐 책임의 주체가 아니다.

## 연결 개념
- DevSecOps: IDE·PR·CI 각 단계에 보안 게이트를 배치하는 실행 방법론
- SAST/SCA/Secret Scan: AI 코드를 병합 전에 걸러내는 세 가지 기본 자동 검증 도구
- SBOM: AI가 제안한 의존성의 출처와 버전을 릴리스 이후까지 추적하는 명세서

# 📝 【답안용】 시험 답안 템플릿

> 목적: 시험장에서 25분에 그대로 쓰는 답안 양식. 작성방식(추상표현 금지·수치·도식·문제유형 전환)을 엄격히 지킨다.
> 핵심: AI 코드 생성 도입 효과 나열이 아니라, 취약 코드 유입 경로와 통제 지점을 SDLC에 연결한다.

## 핵심 인사이트 (3줄 요약)

> 1. **본질**: AI 코드 생성 보안 취약점은 LLM 제안 코드에 CWE, 비밀정보, 취약 의존성, 라이선스 위험이 포함되는 공급망 위험이다.
> 2. **가치**: IDE 단계부터 PR, CI, 배포 전까지 SAST/SCA/Secret Scan을 배치해 결함 발견 시점을 릴리스 전으로 앞당긴다.
> 3. **판단 포인트**: 생산성 지표보다 CWE 차단율, 비밀정보 탐지 건수, 취약 패키지 SLA, 리뷰 승인율을 함께 봐야 한다.

## 출제 의도 및 답안 포인트

| 출제 의도 | 반드시 짚을 핵심 | 감점 회피 포인트 |
|:---|:---|:---|
| 생성형 AI 개발 도구의 위험 인식 확인 | CWE, Secret, SCA, License, Prompt Leakage | "AI가 코드를 잘 만든다" 식 기능 설명으로 끝냄 |
| SDLC 통제 설계 역량 확인 | IDE 정책, PR 리뷰, CI 보안 게이트, SBOM | 도구명만 쓰고 차단 위치를 누락 |
| 책임·감사 관점 확인 | 개발자 책임, 로그, 승인 이력, 예외 승인 | AI 책임 전가 또는 무검증 병합 허용 |

> 요약: 이 문제는 AI 코드 작성 자체보다 취약 코드가 제품에 들어가지 못하게 하는 통제 구조를 묻는다.

## Ⅰ. 개요 및 필요성

- 개요: AI 코드 생성 보안 취약점은 AI 제안 코드의 보안 결함 위험이다.
- 배경: 개발자는 AI 제안을 즉시 수락할 수 있지만 제안 코드는 학습 데이터의 취약 패턴과 낡은 API를 포함할 수 있다.
- 필요성: AI 코드를 신뢰 코드가 아닌 검증 대상 산출물로 관리하고 SAST·SCA·리뷰 게이트를 적용해야 한다.

## Ⅱ. 구조 및 구성요소

```text
Prompt/Context -> AI Code Suggestion -> IDE Policy -> PR Review
                                   -> CI Security Gate -> Artifact/SBOM -> Release
```

| 구성요소 | 역할 | 특이사항 |
|:---|:---|:---|
| 프롬프트·컨텍스트 | 요구사항, 기존 코드, API 사용 맥락 제공 | 사내 코드·키 노출 통제 필요 |
| AI 코드 제안 | 함수, 테스트, 설정, IaC 후보 생성 | 취약 패턴과 라이선스 위험 포함 가능 |
| 보안 검증 게이트 | SAST, SCA, Secret Scan, License Scan 실행 | High/Critical 차단 기준 명시 |
| 감사·예외 관리 | 승인자, 사유, 만료일 기록 | 예외 30일 단위 재검토 권장 |

> 요약: AI 코드 위험 통제는 생성 지점, 리뷰 지점, CI 지점, 감사 지점을 하나의 흐름으로 묶어야 한다.

## Ⅲ. 동작원리 및 흐름도

```text
요구 입력 -> AI 코드 후보 생성 -> 개발자 검토 -> 보안 스캔
-> CWE/Secret/License 판정 -> 수정 또는 예외 승인 -> 병합/배포
```

| 단계 | 처리 내용 | 검증 기준 |
|:---:|:---|:---|
| 1 | AI 코드 후보 생성 | 사내 비밀정보 프롬프트 차단 |
| 2 | 개발자 의미 검토 | 요구사항, 경계값, 예외 처리 확인 |
| 3 | 자동 보안 분석 | CWE Top 25, OWASP Top 10, CVSS 7.0 이상 차단 |
| 4 | 병합 판단 | 리뷰 2인 승인, 예외 만료일 등록 |

> 요약: AI 코드 병합은 사람 검토와 자동 분석을 모두 통과한 경우에만 허용한다.

## Ⅳ. 특징

| 구분 | 기존 수작업 코드 | AI 생성 코드 | 판단 포인트 |
|:---|:---|:---|:---|
| 결함 형태 | 개발자 습관 중심 | 학습 데이터의 취약 패턴 재현 | CWE 매핑률 |
| 유입 속도 | PR 단위 증가 | 대량 코드 후보 수락 | PR당 신규 LOC와 결함 밀도 |
| 통제 지점 | 리뷰·CI 중심 | IDE 정책 추가 필요 | IDE 플러그인 정책 적용률 |
| 책임 범위 | 작성자 명확 | 도구·사용자·조직 책임 혼재 | 승인 로그와 감사 증적 |

> 요약: AI 생성 코드는 유입 속도가 커서 IDE 단계 통제와 CI 차단 기준을 함께 설계해야 한다.

## Ⅴ. 심화 비교 및 적용 판단

| 비교 축 | 기존/대안 | 본 키워드 | 선택 기준 |
|:---|:---|:---|:---|
| 검증 방식 | 사후 SAST | IDE+PR+CI 다단 검증 | 릴리스 전 결함 제거율 95% 목표 |
| 의존성 | 수동 버전 선택 | AI가 패키지 제안 | CVSS 7.0 이상, EOL 패키지 차단 |
| 운영/위험 | 개발자 재량 | 정책 기반 수락·차단 | 예외 승인 30일 만료 |

> 요약: AI 코드 생성은 허용하되, 취약점 등급과 예외 만료 기준으로 병합 여부를 판단한다.

| 리스크 | 원인 | 대응 방안 | 확인 지표 |
|:---|:---|:---|:---|
| 취약 코드 병합 | 검증 없는 자동 수락 | SAST, CWE Top 25 룰셋 | High 결함 병합 0건 |
| 비밀정보 노출 | 프롬프트에 키·토큰 포함 | Secret Scan, DLP, 마스킹 | API Key 탐지 건수 |
