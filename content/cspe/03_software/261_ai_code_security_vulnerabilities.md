# 📖 【암기용】 개념 완전 이해

> 목적: AI 코드 생성 보안 취약점을 처음 봐도 이해하게 만든다. 시험 답안 양식이 아니라, 이해를 위한 설명이다.

## 한눈에
- **개요**: 생성형 AI가 만든 코드에 CWE, 비밀정보 노출, 라이선스 위반이 섞이는 위험
- **왜 필요한가**: Copilot류 도구는 개발 속도를 줄여도, 검증 없이 병합하면 SQL Injection, Hard-coded Key, 취약 의존성이 배포 파이프라인에 들어간다.
- **핵심 직관**: AI 코드는 동료 개발자의 초안처럼 다루며, SAST, SCA, Secret Scan, 리뷰 게이트를 통과해야 제품 코드가 된다.

## 깊이 이해
- **배경·문제의식**: LLM은 공개 코드와 문맥을 기반으로 그럴듯한 코드를 생성한다. 학습 데이터의 취약 패턴, 낡은 API, 권한 없는 예외 처리 방식까지 함께 제안될 수 있다.
- **작동 원리**: 프롬프트가 요구사항을 주면 LLM이 코드 후보를 만들고, 개발자는 IDE에서 수락한다. 이때 CWE-89 SQL Injection, CWE-798 Hard-coded Credential, 취약 패키지 버전이 CI 검증 전까지 눈에 띄지 않을 수 있다.
- **비유**: 자동완성으로 계약서를 쓰되 법무 검토 없이 날인하지 않는 것과 같다. 문장이 자연스러워도 조항 책임은 작성자에게 남는다.
- **구체 예시**: AI가 `SELECT * FROM user WHERE id = ` + userInput 형태 Java 코드를 제안하면 CWE-89 위험이다. PreparedStatement, ORM 바인딩, SAST 룰셋으로 병합 전 차단해야 한다.
- **흔한 오해·주의점**: "AI가 만든 코드라 책임이 줄어든다"는 오해다. 운영 장애, 개인정보 유출, 오픈소스 라이선스 책임은 서비스 제공 조직에 남는다.

## 연결 개념
- DevSecOps - IDE, PR, CI 단계에서 보안 게이트를 배치
- SAST/SCA/Secret Scan - AI 코드 검증의 기본 도구
- SBOM - AI가 제안한 의존성의 출처와 버전 추적

# 📝 【답안용】 시험 답안 템플릿

> 목적: 시험장에서 25분에 그대로 쓰는 답안 양식. 작성방식(추상표현 금지·수치·도식·문제유형 전환)을 엄격히 지킨다.
> 핵심: AI 코드 생성 도입 효과 나열이 아니라, 취약 코드 유입 경로와 통제 지점을 SDLC에 연결한다.

## 핵심 인사이트 (3줄 요약)

> 1. **본질**: AI 코드 생성 보안 취약점은 LLM 제안 코드에 CWE, 비밀정보, 취약 의존성, 라이선스 위험이 포함되는 공급망 위험이다.
> 2. **가치**: IDE 단계부터 PR, CI, 배포 전까지 SAST/SCA/Secret Scan을 배치해 결함 발견 시점을 릴리스 전으로 앞당긴다.
> 3. **판단 포인트**: 생산성 지표보다 CWE 차단율, 비밀정보 탐지 건수, 취약 패키지 SLA, 리뷰 승인율을 함께 봐야 한다.

## 출제 의도 및 답안 포인트

| 출제 의도 | 반드시 짚을 핵심 | 감점 회피 포인트 |
|:---|:---|:---|
| 생성형 AI 개발 도구의 위험 인식 확인 | CWE, Secret, SCA, License, Prompt Leakage | "AI가 코드를 잘 만든다" 식 기능 설명으로 끝냄 |
| SDLC 통제 설계 역량 확인 | IDE 정책, PR 리뷰, CI 보안 게이트, SBOM | 도구명만 쓰고 차단 위치를 누락 |
| 책임·감사 관점 확인 | 개발자 책임, 로그, 승인 이력, 예외 승인 | AI 책임 전가 또는 무검증 병합 허용 |

> 요약: 이 문제는 AI 코드 작성 자체보다 취약 코드가 제품에 들어가지 못하게 하는 통제 구조를 묻는다.

## Ⅰ. 개요 및 필요성

AI 코드 생성 보안 취약점은 생성형 AI가 제안한 코드가 보안 결함을 포함하는 위험이다. 개발자는 AI 제안을 빠르게 수락하지만, 제안 코드는 학습 데이터의 취약 패턴과 낡은 API를 포함할 수 있다. 따라서 AI 코드는 신뢰 코드가 아니라 검증 대상 산출물로 관리해야 한다.

---

## Ⅱ. 구조 및 구성요소

```text
Prompt/Context -> AI Code Suggestion -> IDE Policy -> PR Review
                                   -> CI Security Gate -> Artifact/SBOM -> Release
```

| 구성요소 | 역할 | 특이사항 |
|:---|:---|:---|
| 프롬프트·컨텍스트 | 요구사항, 기존 코드, API 사용 맥락 제공 | 사내 코드·키 노출 통제 필요 |
| AI 코드 제안 | 함수, 테스트, 설정, IaC 후보 생성 | 취약 패턴과 라이선스 위험 포함 가능 |
| 보안 검증 게이트 | SAST, SCA, Secret Scan, License Scan 실행 | High/Critical 차단 기준 명시 |
| 감사·예외 관리 | 승인자, 사유, 만료일 기록 | 예외 30일 단위 재검토 권장 |

> 요약: AI 코드 위험 통제는 생성 지점, 리뷰 지점, CI 지점, 감사 지점을 하나의 흐름으로 묶어야 한다.

---

## Ⅲ. 동작원리 및 흐름도

```text
요구 입력 -> AI 코드 후보 생성 -> 개발자 검토 -> 보안 스캔
-> CWE/Secret/License 판정 -> 수정 또는 예외 승인 -> 병합/배포
```

| 단계 | 처리 내용 | 검증 기준 |
|:---:|:---|:---|
| 1 | AI 코드 후보 생성 | 사내 비밀정보 프롬프트 차단 |
| 2 | 개발자 의미 검토 | 요구사항, 경계값, 예외 처리 확인 |
| 3 | 자동 보안 분석 | CWE Top 25, OWASP Top 10, CVSS 7.0 이상 차단 |
| 4 | 병합 판단 | 리뷰 2인 승인, 예외 만료일 등록 |

> 요약: AI 코드 병합은 사람 검토와 자동 분석을 모두 통과한 경우에만 허용한다.

## Ⅳ. 특징

| 구분 | 기존 수작업 코드 | AI 생성 코드 | 판단 포인트 |
|:---|:---|:---|:---|
| 결함 형태 | 개발자 습관 중심 | 학습 데이터의 취약 패턴 재현 | CWE 매핑률 |
| 유입 속도 | PR 단위 증가 | 대량 코드 후보 수락 | PR당 신규 LOC와 결함 밀도 |
| 통제 지점 | 리뷰·CI 중심 | IDE 정책 추가 필요 | IDE 플러그인 정책 적용률 |
| 책임 범위 | 작성자 명확 | 도구·사용자·조직 책임 혼재 | 승인 로그와 감사 증적 |

> 요약: AI 생성 코드는 유입 속도가 커서 IDE 단계 통제와 CI 차단 기준을 함께 설계해야 한다.

## Ⅴ. 심화 비교 및 적용 판단

| 비교 축 | 기존/대안 | 본 키워드 | 선택 기준 |
|:---|:---|:---|:---|
| 검증 방식 | 사후 SAST | IDE+PR+CI 다단 검증 | 릴리스 전 결함 제거율 95% 목표 |
| 의존성 | 수동 버전 선택 | AI가 패키지 제안 | CVSS 7.0 이상, EOL 패키지 차단 |
| 운영/위험 | 개발자 재량 | 정책 기반 수락·차단 | 예외 승인 30일 만료 |

> 요약: AI 코드 생성은 허용하되, 취약점 등급과 예외 만료 기준으로 병합 여부를 판단한다.

| 리스크 | 원인 | 대응 방안 | 확인 지표 |
|:---|:---|:---|:---|
| 취약 코드 병합 | 검증 없는 자동 수락 | SAST, CWE Top 25 룰셋 | High 결함 병합 0건 |
| 비밀정보 노출 | 프롬프트에 키·토큰 포함 | Secret Scan, DLP, 마스킹 | API Key 탐지 건수 |
| 라이선스 위반 | 유사 코드·패키지 추천 | License Scan, SBOM | 금지 라이선스 0건 |

> 요약: 주요 위험은 코드 결함, 비밀정보, 라이선스이며 자동 스캔과 감사 증적으로 통제한다.

| 점검 항목 | 목표 기준 | 측정 방법 |
|:---|:---|:---|
| 보안 결함 | Critical/High 0건 배포 | SAST 리포트, 릴리스 게이트 |
| 공급망 | SBOM 100%, CVSS 7.0 이상 SLA 7일 | SCA, Dependency Track |
| 감사 | AI 생성 코드 PR 라벨 100% | Git 로그, PR 템플릿 |

> 요약: 성공 여부는 생산성보다 릴리스에 남은 취약점 등급과 추적 가능성으로 판단한다.

## Ⅵ. 실무 적용 및 결론

**적용 방안 3개 (필수 - 단계별 또는 항목별):**
1. IDE 정책: 사내 저장소 컨텍스트 사용 범위 제한, 비밀정보 마스킹, AI 생성 코드 PR 라벨 자동 부여
2. CI 게이트: SAST/SCA/Secret/License Scan을 병렬 실행하고 CVSS 7.0 이상, Hard-coded Key, 금지 라이선스 병합 차단
3. 감사 체계: 예외 승인자·사유·만료일을 이슈로 등록하고 30일마다 재평가, SBOM을 릴리스 산출물로 보관

**결론 (2줄):**
- 기술사 판단: 내부 업무 도구는 경고 기반 허용, 대외 서비스·금융·개인정보 코드는 차단 게이트 기반으로 운영함
- 향후 방향: AI 코드 생성은 DevSecOps, SBOM, 정책형 IDE 통제와 결합해 검증 가능한 개발 체계로 수렴함
