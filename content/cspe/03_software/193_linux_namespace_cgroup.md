## Ⅰ. 개요
- **정의**: Namespace는 프로세스별 커널 자원 격리, Cgroup은 프로세스 그룹별 자원 사용량 제한을 담당하는 리눅스 커널 메커니즘
- **배경/필요성**: 컨테이너 기술은 VM 없이 프로세스 수준 격리가 필요하며, 이를 커널 레벨에서 구현하는 기반이 필요함
- **비유**: Namespace는 각 세입자에게 독립 주소·우편함을 부여하는 것, Cgroup은 전기·수도 사용량 상한을 설정하는 것

| 출제 의도 | 반드시 짚을 핵심 | 감점 회피 포인트 |
|:---|:---|:---|
| 컨테이너 격리의 커널 원리 | Namespace 종류(PID·Net·Mount 등)와 Cgroup v2 | 격리≠보안, seccomp 등 보완 필요 언급(194 참조) |

> 요약: Namespace로 자원을 격리하고 Cgroup으로 사용량을 제한하여 컨테이너 런타임의 기반을 구성함

## Ⅱ. 구성요소
```text
+----- Namespace (격리) -----+    +----- Cgroup (제한) -----+
| PID : 프로세스 ID 분리     |    | cpu : CPU 시간 할당     |
| Net : 네트워크 스택 분리   |    | memory : 메모리 상한    |
| Mount : 파일시스템 분리    |    | io : 블록 I/O 대역폭    |
| UTS : 호스트명 분리        |    | pids : 프로세스 수 상한 |
| IPC : IPC 자원 분리        |    +-------------------------+
| User : UID/GID 매핑 분리   |
+----------------------------+
```

| 구성요소 | 설명 | 비유 |
|:---|:---|:---|
| PID Namespace | 프로세스 ID 공간을 분리하여 컨테이너 내부에 독립 PID 트리 제공 | 독립 호실 번호 체계 |
| Net Namespace | 네트워크 인터페이스·라우팅 테이블·iptables를 프로세스별 분리 | 전용 전화번호 |
| Cgroup v2 | 통합 계층 구조로 CPU·메모리·IO 자원을 그룹 단위 제어 | 전기 차단기 |

> 요약: 6종 Namespace가 자원 뷰를 격리하고 Cgroup이 자원 소비량에 상한을 부여함

## Ⅲ. 절차
```text
생성 --> 격리 --> 제한 --> 실행
```
- 1단계: `clone()` 또는 `unshare()` 시스콜로 새 Namespace 생성
- 2단계: PID·Net·Mount 등 필요한 Namespace에 프로세스를 진입시켜 자원 뷰 격리
- 3단계: Cgroup 컨트롤러에 프로세스 등록 후 CPU·메모리·IO 상한값 설정
- 4단계: 격리·제한이 적용된 환경에서 컨테이너 프로세스 실행

> 요약: Namespace 생성-격리 적용-Cgroup 제한-프로세스 실행의 순서로 컨테이너 환경을 구성함

## Ⅳ. 문제점
- 커널 공유 위험: 호스트 커널을 공유하므로 커널 취약점이 전체 컨테이너에 전파됨
- 자원 누수: Cgroup 설정 오류 시 OOM Killer 미작동 등 자원 누수 발생 가능
- 설정 복잡성: 6종 Namespace × 다수 Cgroup 컨트롤러 조합으로 관리 난이도 증가

> 요약: 커널 공유·자원 누수·설정 복잡성이 컨테이너 격리의 주요 위험 요소임

## Ⅴ. 개선방안
1. 단기: gVisor·Kata 등 추가 격리 계층으로 커널 공유 위험 완화
2. 중기: Cgroup v2 통합 계층 전환 및 자동 OOM 정책으로 자원 누수 방지
3. 장기: 컨테이너 런타임 표준(OCI)에 보안 프로파일 기본 탑재로 설정 단순화

> 요약: 추가 격리-Cgroup v2 전환-표준화 순으로 컨테이너 보안·운영성을 강화하는 방향임

## Ⅵ. 전망
- 발전 방향: Cgroup v2 단일 계층 모델이 표준으로 정착하며 User Namespace 활용 확대
- 기술사적 판단: 컨테이너 보안의 근본은 커널 격리 메커니즘 이해에서 출발함
- 기술사 제언: Namespace·Cgroup 기반 격리 수준 평가와 보완 기술(194 참조) 조합 설계 필요
