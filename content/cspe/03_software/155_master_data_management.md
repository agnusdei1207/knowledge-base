# 📖 【암기용】 개념 완전 이해

> 목적: MDM을 처음 보는 사람도 완벽히 이해하게 만든다. 시험 답안 양식이 아니라, 이해를 위한 친절한 설명이다.

## 한눈에
- **개요**: MDM(마스터 데이터 관리)은 고객·상품·조직처럼 여러 시스템이 공유하는 **기준 데이터(Master Data)**를 하나의 **단일 진실 원천(Single Source of Truth)**으로 통합·관리하는 체계다.
- **왜 필요한가**: 같은 고객이 CRM·ERP·쇼핑몰에 서로 다른 이름과 주소로 존재하면 매출 집계, 배송, 마케팅, 규제 대응이 시스템마다 다른 답을 내놓는다.
- **핵심 직관**: 주민등록 원장처럼 핵심 식별자와 속성의 기준본(golden record)을 하나 정해, 각 업무 시스템이 같은 대상을 같은 의미로 쓰게 한다.

## 핵심 용어 정리 (내부에 등장하는 것들)

| 용어 | 의미 | 비유 |
|:---|:---|:---|
| 기준 데이터(Master Data) | 여러 시스템이 공통으로 참조하는 핵심 개체(고객·상품·조직 등) 데이터 — 거래(transaction) 데이터와 구분 | 사전에 실리는 표준 단어 |
| Single Source of Truth | "이 값이 맞다"고 조직 전체가 합의하는 단 하나의 원천 | 국가 표준시계 |
| 매칭(Match) / 매칭 점수 | 서로 다른 시스템의 레코드가 "같은 대상"인지 속성 일치도로 점수화하는 것 | 지문 대조 유사도 |
| survivorship rule | 후보 레코드들 중 어떤 속성 값을 최종 대표값으로 채택할지 정하는 규칙 | 여러 증언 중 가장 신뢰되는 증언을 채택 |
| golden record | survivorship rule을 적용해 만든, 그 대상에 대한 최종 대표 레코드 | 여러 초안을 합친 확정본 |
| Registry 패턴 | 원천 시스템 데이터는 그대로 두고, ID 간 연결 정보(링크)만 별도로 관리 | 여러 부서 문서를 안 옮기고 색인 카드만 만듦 |
| Consolidation 패턴 | 배치로 원천 데이터를 모아 별도 저장소에 golden record를 만들지만, 원천 시스템 변경 권한은 그대로 원천에 있음 | 각 지점 장부를 본사가 취합해 통합 장부만 작성 |
| Coexistence 패턴 | golden record를 만들고 원천 시스템과 양방향 동기화까지 수행 | 본사 장부와 지점 장부를 서로 실시간 대조·갱신 |
| Centralized 패턴 | 모든 업무 시스템이 마스터 허브를 직접 조회·수정 | 모든 지점이 본사 장부 하나만 사용 |
| source priority | 속성별로 어느 원천 시스템 값을 더 신뢰할지 정한 우선순위 | 증인 중 전문가 증언을 더 신뢰 |

## 깊이 이해

### 왜 MDM이 필요해졌나 (배경)
업무 시스템은 도입 시점과 목적이 달라, 같은 고객·상품·공급사가 시스템마다 다른 코드와 다른 값으로 저장된다. 이를 방치하면 "이번 달 고객 수"가 CRM에서는 10만 명, ERP에서는 9만 8천 명으로 나오는 식의 불일치가 반복된다. MDM은 식별 → 매칭 → 병합 → golden record 생성 → 배포라는 절차로 이 기준 데이터를 하나로 정리한다.

### 매칭 점수는 어떻게 계산하나 — 수치로 이해
동일 인물인지 판단할 때 속성마다 가중치를 두고 합산한다. 예를 들어 이름 일치에 0.4, 휴대폰 일치에 0.4, 생년월일 일치에 0.2를 배정했다고 하자.
- 이름 일치 + 휴대폰 일치 + 생년월일 일치 = 0.4+0.4+0.2 = **1.0** → 확실한 동일 인물, 자동 병합.
- 이름 일치 + 휴대폰 일치, 생년월일 불일치(오타·미기재) = 0.4+0.4+0 = **0.8** → 애매한 구간, steward가 수동으로 확인.
- 이름만 일치 = 0.4 → 동일 인물로 보기엔 근거 부족, 별개 레코드로 유지.
- 실무에서는 이 점수에 임계값을 그어 자동화한다: **0.92 이상**은 자동 병합, **0.80~0.92**는 steward 검토, **0.80 미만**은 별개 유지. 임계값을 너무 낮추면 서로 다른 사람을 하나로 합치는 오병합(false merge)이 늘고, 너무 높이면 같은 사람을 못 알아보는 누락이 늘어난다.

### golden record는 어떻게 만드나 (survivorship rule)
동일 인물로 묶인 후보들 중 어떤 속성값을 채택할지는 속성별로 다르게 정할 수 있다. 예: 휴대폰 번호는 본인인증을 거친 시스템의 값을 채택(가장 신뢰도 높음), 주소는 가장 최근에 갱신된 시스템 값을 채택(최신성이 중요), 마케팅 동의 여부는 동의를 직접 받은 채널(콜센터)의 값을 채택. 이렇게 "출처별 신뢰 기준"을 미리 정해두는 것이 survivorship rule이다.

### 4가지 아키텍처 패턴 — 무엇이 다르고 언제 고르나
| 패턴 | 원천 데이터 위치 | 변경 권한 | 실시간성 | 적합한 경우 |
|:---|:---|:---|:---|:---|
| Registry | 원천에 그대로 유지 | 원천 시스템 | 조회 시점 연결 | 도입 부담을 낮추고 우선 "누가 누구인지"만 파악하고 싶을 때 |
| Consolidation | 별도 저장소로 취합(배치) | 원천 시스템 | 배치 주기(예: 1일) | 분석·리포트용으로 통합 뷰만 필요할 때 |
| Coexistence | 마스터 허브 + 원천 양방향 동기화 | 양쪽 모두 | 준실시간 | 원천 시스템 업무를 유지하면서 품질도 개선하고 싶을 때 |
| Centralized | 마스터 허브 단일 저장 | 마스터 허브만 | 실시간 | 변경 이력·정합성을 가장 엄격히 통제해야 할 때(규제 대응 등) |

판별 원리는 두 가지다: ① 원천 시스템의 업무 변경 권한을 얼마나 유지해야 하는가(Registry일수록 원천 자율성 유지, Centralized일수록 통제 강함), ② 데이터가 얼마나 실시간으로 정확해야 하는가(Registry·Consolidation은 배치 지연 허용, Coexistence·Centralized는 실시간 요구).

### 비유
여러 주소록을 합쳐 하나의 공식 연락처를 만드는 일과 같다. 전화번호는 A 주소록(본인이 최근 입력), 주소는 B 주소록(택배사 연동으로 최신), 수신 동의 여부는 C 시스템(직접 동의 받은 채널) 값을 기준으로 삼아 하나의 확정 연락처를 만드는 것이 golden record 생성과 같다.

### 흔한 오해
MDM은 단순 중복 제거(dedup)가 아니다. 매칭 알고리즘뿐 아니라 누가 원천 데이터를 승인하는지(steward), 변경이 언제 배포되는지, 과거 이력을 어떻게 보존하는지까지 포함하는 조직·시스템 운영 체계다.

## 연결 개념
- 데이터 품질 관리 — 표준화, 중복률, 매칭 정확도 측정
- 데이터 거버넌스 — master owner 지정과 승인 정책 제공
- 데이터 카탈로그 — 마스터 데이터 정의와 사용처 노출

## Ⅰ. 개요 및 필요성

- 개요: MDM은 기준 데이터의 신뢰 원천 관리 체계임.
- 배경: 고객, 상품, 공급사, 조직 데이터가 시스템별로 불일치하면 집계 오류와 업무 처리 지연이 발생한다.
- 필요성: golden record와 배포 절차로 고객, 상품, 조직 등 기업 공통 기준 데이터를 제공한다.

---

## Ⅱ. 구조 및 구성요소

```text
Source Systems -> Standardization -> Match/Merge -> Golden Record -> Publish/API
                               +-> Steward Review
                               +-> Audit History
```

| 구성요소 | 역할 | 특이사항 |
|:---|:---|:---|
| 원천 시스템 | CRM, ERP, 쇼핑몰, 콜센터 데이터 제공 | source priority 필요 |
| 표준화 | 이름, 주소, 코드, 형식 정리 | 주소 표준, 코드 표준 |
| 매칭/병합 | 동일 대상 후보 식별과 중복 제거 | rule/probabilistic match |
| Golden Record | 대표 속성 기준본 생성 | survivorship rule 적용 |
| 배포/API | 업무 시스템에 기준 데이터 제공 | CDC, REST, message |

> 요약: MDM은 원천 수집, 표준화, 매칭, 기준본 생성, 배포로 구성됨.

---

## Ⅲ. 동작원리 및 흐름도

```text
수집 -> 표준화 -> 중복 후보 산정 -> steward 승인 -> golden record 생성 -> 하위 시스템 배포
```

| 단계 | 처리 내용 | 검증 기준 |
|:---:|:---|:---|
| 1 | 원천 데이터 수집과 식별자 추출 | source coverage 95% 이상 |
| 2 | 주소, 코드, 전화번호 표준화 | 형식 오류율 1% 이하 |
| 3 | 매칭 점수 산정과 병합 후보 생성 | match precision 95% 이상 |
| 4 | steward 승인과 예외 처리 | 승인 SLA 2일 이하 |
| 5 | golden record 배포와 이력 관리 | 배포 지연 5분 이하 |

> 요약: MDM은 자동 매칭과 steward 승인을 결합해 기준 데이터를 만들고 배포함.

> 요약: MDM은 중복률과 기준 오류가 업무 비용으로 이어지는 도메인부터 적용함.

| 리스크 | 원인 | 대응 방안 | 확인 지표 |

> 요약: MDM 리스크는 오병합과 책임 불명확에서 발생하므로 승인과 우선순위 규칙이 필요함.

|:---|:---|:---|

| 정확도 | match precision 95% 이상 | 표본 검수 |
| 배포 | 변경 배포 지연 5분 이하 | CDC/API 로그 |

> 요약: MDM 성과는 중복률, 매칭 정확도, 배포 지연으로 판단함.

## Ⅵ. 실무 적용 및 결론

**적용 방안 3개 (필수 - 단계별 또는 항목별):**
1. 도메인 선정: 고객, 상품, 조직 중 중복률 3% 이상 또는 규제 보고 대상 도메인을 1차 범위로 선정
2. 매칭 설계: 이름, 휴대폰, 생년월일, 주소 정규화 후 match score 0.92 이상 자동 병합, 0.80~0.92 steward 검토
3. 배포 통제: golden record 변경은 CDC/API로 5분 이내 배포하고 변경 전후 값을 1년 이상 감사로그로 보관
