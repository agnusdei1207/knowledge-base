# 📖 【암기용】 개념 완전 이해

> 목적: 이 개념을 처음 보는 사람도 완벽히 이해하게 만든다. 시험 답안 양식이 아니라, 이해를 위한 친절한 설명이다.

## 한눈에
- **개요**: 거대한 모놀리식(Monolithic) 통짜 서버를 MSA로 쪼갤 때, **"도대체 무슨 기준으로 쪼개야 하는가?"**에 대한 완벽한 정답이 바로 **도메인 주도 설계(DDD, Domain-Driven Design)**다. 
- **왜 필요한가**: 그냥 "DB 테이블 개수대로 쪼개자" 하거나 "비슷한 기능끼리 묶자"라고 대충 찢으면, 나중에 API 통신(네트워크) 횟수만 1,000번 폭발하는 끔찍한 '분산 모놀리식' 지옥에 빠진다. 결합도는 낮추고 응집도는 뭉쳐두는 완벽한 경계선을 그어야 했다.
- **핵심 직관**: 
  - **도메인 (Domain)**: 쇼핑몰의 '결제', '배송', '주문' 같은 진짜 현실 세계의 업무 단위.
  - **바운디드 컨텍스트 (Bounded Context)**: "이 선 넘지 마!"라고 치는 울타리. 이 울타리 하나가 MSA의 '서비스(서버) 1개'와 정확히 1:1 매칭된다.

## 깊이 이해
- **배경·문제의식**: 에릭 에반스(Eric Evans)가 2003년에 쓴 책에서 유래했다. 옛날 개발자들은 '테이블(DB) 구조'를 먼저 짜고 거기에 코드를 맞췄다(데이터 주도). 하지만 비즈니스는 '로직'이 핵심이지 DB가 전부가 아니다. 비즈니스 기획자와 개발자가 같은 언어(유비쿼터스 언어)를 쓰며 현실의 업무 덩어리(도메인)를 코드로 구현하자는 철학이 DDD다.
- **작동 원리 (MSA 쪼개기의 마법)**:
  1. **유비쿼터스 언어 (Ubiquitous Language)**: 기획자의 말과 개발자의 변수명을 강제로 통일한다. (예: 기획자가 '고객'이라고 하면, 개발자도 변수명을 `Client`가 아닌 무조건 `Customer`로 통일).
  2. **바운디드 컨텍스트 (Bounded Context)**: 같은 '상품'이라는 단어라도 '주문 팀'이 볼 때는 '가격과 재고'가 중요하고, '배송 팀'이 볼 때는 '크기와 무게'가 중요하다. 즉, 같은 단어라도 **문맥(Context)**이 달라지면 아예 서버(마이크로서비스)와 DB를 분리해서 찢어버려야 한다.
  3. **이벤트 스토밍 (Event Storming)**: 어떻게 쪼갤지 모르겠을 때, 기획자/개발자/디자이너가 다 같이 모여서 오렌지색 포스트잇(도메인 이벤트)을 화이트보드에 미친 듯이 이어 붙이며 시간순으로 업무 흐름을 그려보고, 그 흐름이 뭉치는 곳을 칼로 잘라 MSA 경계로 삼는다.
- **비유**: 
  - 쇼핑몰에서 '상품(Item)'이라는 개념 하나를 통짜로 쓰면(모놀리식) 주문팀, 배송팀이 매번 멱살 잡고 싸운다.
  - DDD로 쪼개기: "주문 울타리(컨텍스트) 안에 주문용 상품 객체를 따로 만들고, 배송 울타리 안에 배송용 상품 객체를 따로 만들어라!"
- **구체 예시**: 배달의민족 서버는 처음엔 거대한 모놀리식 1개였다. 주문 폭주로 서버가 터지자, DDD 워크숍(이벤트 스토밍)을 열어 '가게 노출', '주문', '결제', '배달'이라는 바운디드 컨텍스트 울타리를 쳤고, 지금은 이 울타리들이 각자의 독립된 MSA 서버로 돌아가고 있다.
- **흔한 오해·주의점**: "MSA 서버는 작을수록 좋지 않나요?" (X) 마이크로(Micro)라는 단어 때문에 무조건 작게(함수 1개 크기) 쪼개는 짓이 최악의 안티패턴이다. 작게 쪼갤수록 네트워크 호출로 다 뻗어버린다. 비즈니스 트랜잭션이 한 번에 묶여야 하는 애들(응집도 높은 애들)은 무조건 하나의 덩어리(컨텍스트)로 남겨둬야 한다.

## 연결 개념
- **전략적 설계 vs 전술적 설계**: DDD는 2파트로 나뉜다. 전략적 설계는 위에서 말한 "MSA 경계를 어디서 찢을 것인가(Bounded Context)"이고, 전술적 설계는 "그 찢어진 서버 안에서 Entity와 Repository 코드를 어떻게 예쁘게 짤 것인가"를 다룬다.
- **이벤트 기반 아키텍처 (EDA)**: DDD로 찢어진 서버(결제, 배송)끼리 통신하려면 무조건 Kafka(카프카) 같은 이벤트 버스를 통해 "결제됐어!"라는 도메인 이벤트(Domain Event)를 날려야 완벽한 분리가 완성된다.

# 📝 【답안용】 시험 답안 템플릿

> 목적: 시험장에서 25분에 그대로 쓰는 답안 양식. 작성방식(추상표현 금지·수치·도식·문제유형 전환)을 엄격히 지킨다.
> 핵심: 이 시험은 정보를 많이 나열하는 시험이 아니라, 문제 신호어에서 출제자 의도를 읽고 핵심 논점을 선별해 쓰는 시험이다.

## 핵심 인사이트 (3줄 요약)

> 1. **본질**: 복잡한 소프트웨어 시스템을 기술(데이터베이스, 계층)이 아닌 '비즈니스 도메인' 중심으로 분석하여, 기획자와 개발자가 공통 언어로 아키텍처를 설계하는 론(Theory)이자 마이크로서비스(MSA) 경계 식별의 절대 표준이다.
> 2. **가치**: 모놀리식 시스템을 분해할 때 흔히 저지르는 기능적/데이터적 파편화(분산 모놀리식 안티패턴)를 방어하고, 비즈니스 문맥(Context)이 강하게 응집된 울타리를 쳐서 팀 독립성과 서비스 자율성(Autonomy)을 극대화한다.
> 3. **판단 포인트**: 도메인/서브도메인의 개념, 기획/개발을 일치시키는 유비쿼터스 언어(Ubiquitous Language), 그리고 MSA의 마이크로서비스 1개와 정확히 매핑되는 바운디드 컨텍스트(Bounded Context)의 아키텍처 도식을 그려내야 한다.

## 출제 의도 및 답안 포인트

| 출제 의도 | 반드시 짚을 핵심 | 감점 회피 포인트 |
|:---|:---|:---|
| 거대 시스템을 MSA로 쪼개는 절대적 기준(철학) 맵핑 | Bounded Context = 1개의 마이크로서비스 (응집도) | DDD를 단순히 객체 지향(OOP) 코딩 방법론이나 패턴 중 하나로 축소 서술 |
| 비즈니스 분석(기획)과 코드(개발)의 괴리를 극복하는 메커니즘 | 유비쿼터스 언어를 통한 소스코드 네이밍(변수) 강제 통일 | 이벤트 스토밍(워크숍 기법)을 도메인 추출 과정에서 누락 |
| 단일 개념(엔티티)이 컨텍스트에 따라 다르게 모델링되는 원리 | '상품'이라는 객체가 결제/배송 컨텍스트별로 분리(독립)됨 | 모놀리식처럼 전역 데이터 모델(Global Model) 1개를 유지한다고 적는 치명적 에러 |

> 요약: 서버를 쪼갤 때 "코드 길이가 1000줄 넘으면 쪼개자"는 건 미친 짓이다. "결제팀 업무와 배송팀 업무의 문맥(Context)이 달라지는 그 선(경계)"을 칼로 자르는 것, 그것이 도메인 주도 설계다.

## Ⅰ. 개요 및 필요성

- 정의: 소프트웨어의 복잡성을 통제하기 위해 비즈니스 도메인(현실 업무)을 중심에 두고, 이해관계자 전원이 공용 언어(Ubiquitous Language)를 사용하여 도메인 모델을 구축 및 경계를 식별하는 설계 방법론
- 배경: 기존 데이터(테이블) 중심 설계나 기술 중심(계층형) 설계는 비즈니스 로직을 코드 여기저기에 파편화시켰고, 이 상태로 MSA로 전환할 시 극악의 네트워크 호출 지옥(Distributed Monolith) 발생
- 필요성: 시스템 분해 시 고응집(High Cohesion) 저결합(Loose Coupling)을 달성할 수 있는 명확한 비즈니스 경계(Bounded Context)를 도출하여, 각 마이크로서비스의 데이터 베이스와 배포 독립성을 방어하기 위함

## Ⅱ. 전략적 설계 도식: 바운디드 컨텍스트(Bounded Context)의 분리

DDD의 핵심은 전역(Global) 모델을 부정하고, 문맥(Context)의 울타리를 치는 것이다.

```text
[ 모놀리식의 비극 (전역 모델) ] 
결제 팀 --+                                 +-- 배송 팀
          |  [통합 DB] 상품(Item) 테이블    | 
주문 팀 --+ (컬럼 100개짜리 거대 쓰레기) --+ (누구 하나 수정하면 다 같이 폭발 🚨)


[ DDD 전략적 설계: MSA 쪼개기 (Bounded Context) ] 
======================================================================
[ 컨텍스트 A: 주문 도메인 (Order MSA) ]    [ 컨텍스트 B: 배송 도메인 (Delivery MSA) ]
- 🗣️ 유비쿼터스 언어 적용                 - 🗣️ 유비쿼터스 언어 적용
- 📦 주문 관점의 '상품' 객체 (가격, 옵션)   - 📦 배송 관점의 '상품' 객체 (무게, 부피)
- 💾 전용 분리 DB (주문 DB)                - 💾 전용 분리 DB (배송 DB)
                |                                  |
                +----------(Kafka 이벤트 통신)-------+
======================================================================
```

| 핵심 전략 메커니즘 | 철학적 의미와 아키텍처적 가치 | MSA와의 맵핑 (엔지니어링) |
|:---|:---|:---|
| **유비쿼터스 언어** <br> (Ubiquitous Language) | 기획서의 단어 = 개발자의 대화 = 클래스(변수)명. 3자를 100% 동기화시키는 절대 규칙 | 기획이 바뀌면 코드가 어디서 바뀌어야 할지 1초 만에 식별하는 추적성(Traceability) 락인 |
| **바운디드 컨텍스트** <br> (Bounded Context) | 모델(객체)의 의미가 완벽히 보장되는 논리적/물리적 울타리(경계). 밖으로 나가면 의미가 바뀜 | **Bounded Context 1개 = 1개의 마이크로서비스 서버 = 1개의 독립 DB** (완벽한 MSA 쪼개기 기준) |
| **컨텍스트 매핑** <br> (Context Map) | 울타리와 울타리 사이를 어떻게 연결할 것인가? (API 호출할지, 비동기 큐 던질지)에 대한 관계도 | MSA 간 통신 프로토콜 결정. (Anti-corruption Layer, Open Host Service 등 통신 보호막 구축) |

> 요약: 같은 '사용자'라도 마케팅팀(이메일, 쿠폰)과 정산팀(계좌번호)이 보는 관점은 다르다. 이걸 User라는 테이블 하나에 몰아넣는 게 레거시의 죄악이다. DDD는 정산 컨텍스트와 마케팅 컨텍스트를 찢고 각자 User 객체를 따로 만들라고 강제한다.

## Ⅲ. MSA 도출 워크숍: 이벤트 스토밍 (Event Storming)

빈 화이트보드에서 Bounded Context(MSA 경계)를 가장 빠르고 직관적으로 뽑아내는 시각화 회의 기법.

| 이벤트 스토밍 단계 | 색상 룰 및 도출 행동 메커니즘 | 아키텍처 산출물 (MSA화) |
|:---|:---|:---|
| **1. 도메인 이벤트 도출** | 주황색(Orange) 포스트잇. 시스템에서 발생하는 모든 사건을 **과거 분사형(결제 완료됨, 배송 시작됨)**으로 닥치는 대로 벽에 붙이고 시간순 배열 | 비동기 통신(Kafka)으로 쏠 **이벤트(Event)** 명세 정의 |
| **2. 커맨드/액터/외부 시스템** | 파란색(명령), 노란색(사용자). "결제 완료됨" 이벤트를 발생시키는 명령(결제 승인)과 찌르는 외부 시스템(PG사 API) 매핑 | MSA의 Inbound **API (엔드포인트)** 및 Outbound 타겟 도출 |
| **3. 어그리거트 (Aggregate)** | 노란색(또는 보라색). 명령을 받아 이벤트를 뱉어내는 진짜 주체(데이터 덩어리, 예: `주문 결제서`). 커맨드와 이벤트 사이에 부착 | 트랜잭션(ACID)이 보장되어야 하는 **비즈니스 객체 단위 식별** |
| **4. 경계(Context) 그룹핑** | 워크숍 참석자들이 응집도(친밀도)가 높은 포스트잇 무리를 매직펜(원)으로 묶어 울타리를 침 | **마이크로서비스(MSA) 경계 획정 및 분리 확정** |

> 요약: 개발자 혼자 키보드 치며 아키텍처를 설계하는 시대는 끝났다. 기획자와 함께 "포스트잇"을 이어 붙이며 업무 흐름(이벤트)을 따라가다 보면, 자연스럽게 뭉치는 곳(응집도)이 생기는데 거기가 바로 MSA 서버를 쪼갤 선이다.

## Ⅳ. 극복해야 할 시스템적 리스크 및 전술적(Tactical) 설계 튜닝

서버를 쪼갰다(전략적 설계)고 끝이 아니다. 쪼개진 서버 안에서 코드를 어떻게 짤지(전술적 설계) 못 정하면 다시 스파게티가 된다.

| 리스크 요인 | 발생 시나리오 및 시스템 붕괴 원인 | 아키텍처 대응 방안 (전술적 실무 튜닝) |
|:---|:---|:---|
| **트랜잭션 바운더리 붕괴** | 결제 서버 안에서 '주문서'와 '쿠폰'을 같이 업데이트하다가 DB 락(Lock) 경합 폭증으로 성능 마비 및 일관성 파괴 | **Aggregate (어그리거트) 패턴 적용**: 관련된 객체들을 묶고, 그중 대장(Root)을 통해서만 자식 객체에 접근(변경)하도록 생명주기를 강제. **"1 트랜잭션 = 1 어그리거트 수정"** 절대 원칙 사수 |
| **오염된 모델 강제 이식** | '주문' 도메인이 외부 PG(결제) 사의 구린 모델(변수명, JSON 구조)을 그대로 받아쓰다가 주문 도메인 전체의 코드가 더러워지고 종속됨 | **ACL (Anti-Corruption Layer, 부패 방지 계층)** 삽입: 외부 API와 통신하기 직전에 파사드(Facade)/어댑터 클래스를 하나 세워, 외부의 더러운 모델을 우리 도메인의 '유비쿼터스 언어'로 매끄럽게 번역 후 수용 |

> 요약: 서버를 쪼개는 것(전략)만큼, 남의 똥(구린 외부 API 모델)이 우리 서버 안으로 안 들어오게 막는 방어막(ACL)을 치는 것(전술)도 중요하다.

## Ⅴ. 실무 적용 방안 및 결론

**적용 방안 3개:**
1. [모놀리식 분리(Strangler Fig) 시 이벤트 스토밍 적용] 기존 대형 커머스 시스템을 MSA로 쪼개기 전, 모든 비즈니스 인원이 참여하는 2일짜리 이벤트 스토밍을 수행하여 Bounded Context 경계를 먼저 긋고, 경계 간 결합도(API 호출 횟수)가 가장 낮은 '알림 모듈'이나 '통계 모듈'부터 1차 MSA 분리(디커플링)
2. [헥사고날(Hexagonal) 아키텍처 기반의 DDD 전술적 구현] 쪼개진 개별 마이크로서비스(주문 MSA) 내부 코딩 시, 비즈니스 로직(도메인 모델)을 가장 안쪽(Core)에 격리하고 DB나 외부 API 호출은 포트와 어댑터(Port & Adapter)를 통해 주입받는 헥사고날 뼈대를 강제하여, 도메인 로직이 Spring 프레임워크나 JPA에 종속되는 현상 원천 차단
3. [CQRS 패턴 결합을 통한 조회 성능(Read Model) 최적화] DDD 적용 시 단일 모델로 쓰기(Command)와 조회(Query)를 동시에 처리하면 화면 렌더링 성능이 저하되므로, 쓰기는 Aggregate를 준수해 비즈니스 정합성을 방어하고, 조회 전용 모델은 Bounded Context를 넘나드는 조인(Join) 대신 Kafka를 통해 뷰(View) 전용 데이터베이스(Elasticsearch)를 구독/생성하여 해결

**결론:**
- 기술사 판단: 도메인 주도 설계(DDD)는 단순한 코딩 패턴이 아니다. "비즈니스 기획이 곧 아키텍처 도면이 되게 하라"는 설계 사상의 정점이다. 특히 클라우드 네이티브 시대에 MSA 분리의 절대적 기준선(Bounded Context)을 제공함으로써, 분산 시스템 설계의 패러다임을 데이터(DB)에서 도메인(비즈니스)으로 영구히 이동시켰다.
- 향후 방향: 최근 마이크로서비스 간의 복잡한 호출(Choreography vs Orchestration) 문제를 해결하기 위해, DDD의 도메인 이벤트 사상은 이벤트 기반 아키텍처(EDA, Event-Driven Architecture) 및 Serverless(이벤트 훅 기반 동작)와 완벽히 결합하며 엔터프라이즈 설계의 디팩토(De-facto) 표준으로 자리 잡았다.
