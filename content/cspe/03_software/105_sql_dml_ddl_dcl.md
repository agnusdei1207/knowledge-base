## 핵심 인사이트 (3줄 요약)
- SQL(Structured Query Language)은 관계형 데이터베이스와 소통하는 세계 공통 언어로, 목적에 따라 크게 **DDL(구조 정의), DML(데이터 조작), DCL(권한 제어), TCL(트랜잭션 제어)** 4가지로 나뉨.
- **DDL**이 집의 뼈대(테이블 구조)를 세우고 부수는 명령어라면, **DML**은 그 집 안에 가구를 넣고(INSERT), 옮기고(UPDATE), 버리는(DELETE) 실질적인 비즈니스 쿼리임.
- DML은 실수를 해도 롤백(Rollback)으로 시간을 되돌릴 수 있지만, DDL은 실행 즉시 자동 커밋(Auto-commit)되어 되돌릴 수 없으므로 실무에서 가장 위험하고 신중해야 할 명령어임.

## Ⅰ. 개요 및 필요성
- **개요**: RDBMS의 데이터를 관리하기 위해 설계된 특수 목적의 프로그래밍 언어 분류 체계.
- **필요성**: 데이터베이스 시스템은 단순한 데이터 저장소가 아니라 구조를 설계하는 DBA, 데이터를 다루는 개발자, 권한을 제어하는 보안 담당자가 함께 쓰는 거대한 플랫폼임. 역할과 목적에 맞게 명령어를 분리(추상화)하여 안전한 통제가 필요했음.
---
## Ⅱ. 아키텍처 및 핵심 원리
- **1. DDL (Data Definition Language, 데이터 정의어)**:
  - **목적**: 테이블, 인덱스, 뷰 등의 '데이터베이스 객체(구조)'를 생성/수정/삭제함.
  - **명령어**: `CREATE` (생성), `ALTER` (수정), `DROP` (완전 삭제), `TRUNCATE` (데이터만 싹 비우기).
  - **특징**: **Auto-Commit 됨**. (실행 즉시 디스크에 반영되며 ROLLBACK 불가).
- **2. DML (Data Manipulation Language, 데이터 조작어)**:
  - **목적**: 테이블 안의 실제 '데이터(Row)'를 입력, 수정, 삭제, 조회함.
  - **명령어**: `INSERT`, `UPDATE`, `DELETE`, `SELECT` (SELECT는 별도로 DQL로 빼기도 함).
  - **특징**: 메모리(버퍼) 상에서 먼저 작업하므로, 언제든 **COMMIT이나 ROLLBACK으로 제어 가능**.
- **3. DCL (Data Control Language, 데이터 제어어)**:
  - **목적**: 특정 사용자에게 DB 접근 권한을 부여하거나 뺏음 (보안).
  - **명령어**: `GRANT` (권한 부여), `REVOKE` (권한 회수).
- **4. TCL (Transaction Control Language, 트랜잭션 제어어)**:
  - **목적**: DML로 조작한 데이터의 결과를 논리적으로 확정하거나 취소함.
  - **명령어**: `COMMIT` (완벽히 저장), `ROLLBACK` (되돌리기), `SAVEPOINT` (중간 저장점 설정).

```text
[ DROP, TRUNCATE, DELETE의 결정적 차이 (실무 핵심 면접 질문) ]

 1. DELETE (DML) ➡️ "가구를 하나씩 창밖으로 던짐"
    - 행 단위로 지움. 롤백(취소) 가능. 속도가 가장 느림. 디스크 용량은 그대로.
 2. TRUNCATE (DDL) ➡️ "집안의 가구를 한 번에 다 태워버림"
    - 데이터만 순식간에 다 지움. 롤백 불가능. 속도 엄청 빠름. 디스크 용량 초기화됨.
 3. DROP (DDL) ➡️ "집 자체를 포크레인으로 부숴버림"
    - 테이블 뼈대(구조)까지 통째로 날림. 롤백 불가능. 복구 불가(백업 없으면 끝).
```

## Ⅲ. 비교 및 연결
| 언어 종류 | 주 사용 대상 | 롤백(Rollback) 가능 여부 | 대표 명령어 |
|---|---|---|---|
| **DDL (정의)** | 아키텍트, DBA | **불가능 (Auto Commit)** | `CREATE`, `ALTER`, `DROP` |
| **DML (조작)** | 개발자, 백엔드 로직 | **가능 (TCL로 제어)** | `INSERT`, `UPDATE`, `DELETE`, `SELECT` |
| **DCL (제어)** | DBA, 보안 관리자 | 불가능 | `GRANT`, `REVOKE` |
| **TCL (트랜잭션)**| 개발자 | - | `COMMIT`, `ROLLBACK` |

## Ⅳ. 실무 적용 및 기술사 판단
- **무중단 배포 시 DDL의 위험성**: 라이브(운영) 중인 DB에 컬럼을 추가하려고 `ALTER TABLE` (DDL)을 날리면, DB 엔진은 테이블 전체에 구조 락(Metadata Lock)을 걸어버림. 순간적으로 수만 건의 `INSERT`/`UPDATE` (DML)가 대기 상태(Lock Wait)에 빠져 서비스가 다운되는 대참사가 발생함. 실무 아키텍트는 반드시 트래픽이 적은 새벽에 DDL을 수행하거나, pt-online-schema-change 같은 무중단 DDL 도구를 사용해야 함.
- **ORM과 SQL 추상화**: 최근 JPA/Hibernate 등 ORM의 발전으로 백엔드 개발자가 SQL을 직접 칠 일이 줄어들고 있음. 객체(Entity)만 정의하면 ORM이 DDL과 DML을 자동으로 쏴줌. 하지만 자동 생성된 DDL에 의해 운영 DB 테이블이 날아가는 사고를 막기 위해, 운영 환경에서는 `hibernate.hbm2ddl.auto` 속성을 절대 `create`나 `update`로 두지 않고 `validate`로 방어하는 것이 필수 거버넌스임.

## Ⅴ. 기대효과 및 결론
- 데이터베이스를 건드리는 모든 행위가 4가지 언어 구조로 완벽하게 캡슐화되어, 역할 기반의 접근 제어(RBAC)와 안전한 트랜잭션 처리가 가능해짐.
- SQL은 1970년대에 탄생했음에도 불구하고, 인간의 자연어 구조(S-V-O)와 가장 닮아있는 선언적(Declarative) 언어의 정수로, 빅데이터(HiveQL)와 NoSQL(N1QL) 시대에도 영원히 살아남는 IT 제1 언어임.

### 👶 어린이를 위한 3줄 비유 설명
1. 레고 마을을 만들 때, **DDL**은 "여기 3층짜리 경찰서를 짓자(CREATE), 아예 부수자(DROP)!"라고 건물 자체를 만드는 명령어예요.
2. **DML**은 "경찰서 안에 경찰관 인형을 넣자(INSERT), 옷을 갈아입히자(UPDATE)!"처럼 건물 안에서 노는 명령어예요. 실수하면 "시간을 되돌려(ROLLBACK)!" 할 수 있죠.
3. **DCL**은 "동생은 경찰서 만지지 마(REVOKE)!" 하고 장난감을 만질 수 있는 규칙(권한)을 정하는 거랍니다.
