# 📖 【암기용】 개념 완전 이해

## 한눈에
- **개요**: 관계형 데이터베이스와 소통하기 위해 사용하는 표준화된 구조화 질의어(SQL)의 3가지 핵심 명령어 그룹이다.
- **왜 필요한가**: 데이터베이스 구조를 정의하고, 데이터를 조작하고, 접근을 통제하는 작업을 표준 언어로 수행하기 위해 필요하다.
- **핵심 직관**: DDL은 건물의 **설계도와 방 만들기**, DML은 방에 **가구 넣고 빼기**, DCL은 방 **출입 키 통제하기**다.

## 핵심 용어 정리

| 용어/표기 | 의미 | 비유·예 |
|:---|:---|:---|
| DDL (데이터 정의어) | 테이블, 인덱스 등 구조를 생성/변경/삭제 | 건물을 짓고(`CREATE`), 부숨(`DROP`) |
| DML (데이터 조작어) | 실제 데이터를 검색, 삽입, 수정, 삭제 | 책상에 앉고(`SELECT`), 짐 넣기(`INSERT`) |
| DCL (데이터 제어어) | 데이터 접근 권한을 부여하거나 회수 | VIP 출입증 발급(`GRANT`), 회수(`REVOKE`) |
| TCL (트랜잭션 제어어) | 논리적 단위를 확정하거나 취소 | 작업 저장(`COMMIT`), 취소(`ROLLBACK`) |

## 깊이 이해
- **배경·문제의식**: 과거에는 DB 벤더마다 독자적 프로그래밍으로 호환성이 없었다. 목적에 맞게 분리된 표준 언어(ANSI SQL)가 제정되었다.
- **작동 원리**: SQL 쿼리를 전송하면 DBMS 파서가 식별하여 DDL은 데이터 딕셔너리를 수정하고, DML은 디스크 블록 데이터를 조작하며, DCL은 보안 카탈로그를 갱신한다.
- **비유**: 회사의 조직도 신설(DDL), 직원들의 실제 업무 결재(DML), 보안팀의 출입 통제(DCL).
- **구체 예시**: `CREATE TABLE` (DDL), `INSERT INTO` (DML), `GRANT SELECT` (DCL).
- **흔한 오해·주의점**: DML은 `ROLLBACK`이 가능하지만 DDL은 실행 즉시 커밋(Auto-Commit)되어 되돌릴 수 없는 경우가 많아 주의해야 한다.

## 연결 개념
- **관계 대수 (Relational Algebra)**: DML SELECT 연산의 수학적 근간.
- **트랜잭션 (Transaction)**: DML의 묶음 단위로 TCL 통제 대상.

# 📝 【답안용】 시험 답안 템플릿

## 핵심 인사이트 (3줄 요약)

> 1. **본질**: 목적(구조 정의, 데이터 조작, 권한 제어)에 따라 역할을 분리한 관계형 데이터베이스 표준 질의어
> 2. **가치**: 선언적(Declarative) 특성을 유지하며 데이터 접근 글로벌 표준 인터페이스 제공
> 3. **판단 포인트**: DDL, DML, DCL 세부 명령어와 트랜잭션 롤백 여부 등 작동 상 결정적 차이 제시

## 출제 의도 및 답안 포인트

| 출제 의도 | 반드시 짚을 핵심 | 감점 회피 포인트 |
|:---|:---|:---|
| SQL 언어 구조적 분류와 명령어별 역할 이해 | 3대 언어별 목적, 주요 명령어 매핑 | `TRUNCATE`(DDL)와 `DELETE`(DML) 차이 혼동 서술 |

> 요약: 스키마 조작, 인스턴스 조작, 보안 통제의 역할 분담을 명확히 설명해야 한다.

---

## Ⅰ. 개요 및 필요성

- 개요: RDBMS에서 데이터를 정의, 조작, 제어하기 위해 사용되는 국제 표준 비절차적 질의어
- 배경: 데이터 모델의 독립성 확보 및 사용자와 DBMS 간의 범용적 인터페이스 요구
- 필요성: 시스템 카탈로그, 트랜잭션 처리, 보안 제어를 분리하여 일관된 DB 운영 지원

---

## Ⅱ. 구조 및 구성요소

```text
사용자 쿼리 입력 -> SQL 파서(Parser) -> 명령어 그룹 분류 -> 타겟 영역
                                          +-> [DDL] -> 메타데이터 변경
                                          +-> [DML] -> 데이터 블록 조작
                                          +-> [DCL] -> 보안 카탈로그 갱신
```

| 구분 | 목적 | 대상 | 주요 명령어 |
|:---|:---|:---|:---|
| **DDL** (정의어) | DB 스키마, 구조 생성/변경 | 테이블, 인덱스 등 객체 | `CREATE`, `ALTER`, `DROP`, `TRUNCATE` |
| **DML** (조작어) | 실제 데이터 검색/갱신 | 테이블 내부 튜플 | `SELECT`, `INSERT`, `UPDATE`, `DELETE` |
| **DCL** (제어어) | 무결성 유지, 권한 제어 | 사용자 권한, 트랜잭션 | `GRANT`, `REVOKE` |
| (TCL) | 트랜잭션 단위 확정/취소 제어 | DML 작업 세션 | `COMMIT`, `ROLLBACK` |

> 요약: 객체 구조(DDL), 데이터 내용(DML), 보안 통제(DCL)로 시스템을 제어한다.

---

## Ⅲ. 동작원리 및 흐름도

```text
DDL 요청(개발자) -> 구조 생성 -> DCL 요청(DBA) -> 접근제어 확립 -> DML 요청(앱) -> 데이터 조작
```

- 1단계 스키마 정의 (DDL): `CREATE TABLE`을 통해 논리적 구조를 데이터 딕셔너리에 등록
- 2단계 권한 부여 (DCL): `GRANT` 실행하여 애플리케이션 계정에 최소 권한 부여
- 3단계 데이터 조작 (DML): 로직에 따라 `INSERT`, `SELECT` 등을 통한 비즈니스 요건 처리
- 4단계 트랜잭션 확정 (TCL): `COMMIT`하여 변경 사항을 영구적으로 디스크에 반영

> 요약: DDL로 그릇을 빚고 DCL로 접근 통제 후 실 서비스에서 DML로 데이터 조작한다.

---

## Ⅳ. 특징
- 선언적 언어: "어떻게" 찾을지는 옵티마이저에 맡기고 "무엇"을 원하는지 기술
- Auto-Commit 여부: DDL은 실행 즉시 트랜잭션 확정(롤백 불가), DML은 `COMMIT` 전까지 롤백 가능
- 딕셔너리 기반 연동: 파서는 DML 쿼리 인입 시 카탈로그(DDL 결과)를 참조하여 유효성 검사
- 보안 세분화: DCL을 통해 뷰(View)를 활용한 컬럼/로우 단위 미세 권한 통제 가능

> 요약: 높은 추상화를 제공하며 명령어 그룹 간 트랜잭션 처리 방식이 다르다.

---

## Ⅴ. 심화 비교 및 적용 판단

| 비교 축 | DELETE (DML) | TRUNCATE (DDL) | 선택 기준 |
|:---|:---|:---|:---|
| 데이터 삭제 방식 | 튜플을 한 줄씩 삭제 (로그 생성) | 스토리지 할당량 통째 해제 | 조건부 삭제 vs 전체 초기화 |
| 트랜잭션 복구 | 취소(`ROLLBACK`) 가능 | 취소 불가 | 데이터 복구 중요도 |
| 성능 오버헤드 | 매우 높음 (대량 Undo 발생) | 매우 낮음 (고속 삭제) | 테이블 리셋 시간 |

> 요약: 조건 삭제는 DML(`DELETE`)을, 통째 고속 비우기는 DDL(`TRUNCATE`)을 쓴다.

**리스크·대응:**
- DDL 락 장애: 대용량 테이블 `ALTER` 시 장시간 락 발생 → Online DDL 도구 활용 (지표: DDL 대기 시간)
- SQL 인젝션 공격: 악의적 쿼리 주입 → ORM 프레임워크 또는 바인딩 변수 필수 사용 (지표: 공격 탐지 건수)

**도입 후 점검 지표:**
- 품질/운영: DCL 최소 권한 원칙 준수율 — `GRANT ALL` 계정 정기 감사
- 성능 효율: DML 슬로우 쿼리 빈도 — 옵티마이저 실행 계획 점검 및 튜닝

---

## Ⅵ. 실무 적용 및 결론

**적용 방안 3개:**
1. DDL 형상 관리: Liquibase 등 마이그레이션 툴을 도입하여 DDL 스크립트를 코드(Git) 기반으로 버전 관리
2. DCL 기반 역할 분리(RBAC): 앱 연결 계정에는 DML 권한만 부여하고 DDL 권한은 전용 DBA 계정에 격리
3. 대용량 일괄 DML 처리: 수백만 건 조작 시 언두 버퍼 초과 장애 방지를 위해 청크(Chunk) 단위 분할 커밋 적용

**결론:**
- 기술사 판단: SQL 3대 분류는 운영 역할을 분리하므로 실무에서는 DDL/DML/DCL 권한을 엄격히 격리해 사고를 예방해야 한다.
- 향후 방향: 클라우드 네이티브 환경에서 DDL이 코드화(IaC)되며 CI/CD 파이프라인 안에서 SQL 배포가 자동화되고 있다.
