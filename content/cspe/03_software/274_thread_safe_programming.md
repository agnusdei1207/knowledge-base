## Ⅰ. 개요
- **정의**: 다수 스레드가 공유 자원에 동시 접근해도 데이터 정합성이 보장되는 프로그래밍 기법
- **배경/필요성**: 멀티코어 환경에서 동시 실행이 기본이므로 경쟁 조건을 구조적으로 제거할 필요
- **비유**: 여러 사람이 동시에 한 칠판에 쓸 때 구역을 나누거나 순서를 정하는 것과 유사함

| 출제 의도 | 반드시 짚을 핵심 | 감점 회피 포인트 |
|:---|:---|:---|
| 동시성 제어 기법 분류·적용 | 상호 배제, 불변 객체, Lock-Free 구분 | 동기화 = 성능 저하라는 단순 공식 지양, 기법별 트레이드오프 명시 |

> 요약: 공유 자원 동시 접근 시 정합성을 보장하는 설계·구현 기법의 총칭임

## Ⅱ. 구성요소
```text
Thread A --\
            +--> Shared Resource <-- Guard Mechanism
Thread B --/
Guard: Mutex | RWLock | CAS | Immutable
```

| 구성요소 | 설명 | 비유 |
|:---|:---|:---|
| Mutex/Lock | 임계 영역에 하나의 스레드만 진입을 허용하는 상호 배제 장치 | 화장실 잠금장치 — 한 명만 사용 |
| Read-Write Lock | 읽기는 동시 허용, 쓰기는 배타 잠금으로 처리 | 열람실 — 동시 열람 가능, 수정 시 대출 |
| CAS(Compare-And-Swap) | 기대값과 현재값이 일치할 때만 원자적으로 갱신하는 Lock-Free 연산 | 택배 수취 — 이름 확인 후 전달 |
| Immutable Object | 생성 후 상태 변경이 불가하여 동기화가 불필요한 객체(275 참조) | 인쇄된 책 — 수정 불가 |

> 요약: 잠금, 원자 연산, 불변 객체를 조합하여 공유 자원 접근을 제어함

## Ⅲ. 절차
```text
공유 자원 식별 -> 접근 패턴 분류 -> 보호 기법 적용 -> 검증
```
- 1단계: 코드 내 다수 스레드가 읽기/쓰기하는 공유 변수·컬렉션을 식별
- 2단계: 읽기 전용, 읽기 다수/쓰기 소수, 쓰기 빈번 등 접근 패턴을 분류
- 3단계: 패턴별로 불변 객체, RWLock, CAS 등 적합한 보호 기법을 적용
- 4단계: 스레드 새니타이저·스트레스 테스트로 경쟁 조건 부재를 검증

> 요약: 공유 자원 식별 → 패턴 분류 → 기법 적용 → 검증 순서로 진행함

## Ⅳ. 문제점
- 데드락: 다수 Lock의 획득 순서가 교차하면 상호 대기로 시스템이 교착됨
- 성능 저하: 과도한 동기화가 직렬 실행을 유발하여 멀티코어 활용률이 감소함
- 테스트 난이도: 경쟁 조건이 비결정적으로 발생하여 재현·디버깅이 어려움

> 요약: 데드락, 동기화 성능 저하, 비결정적 버그 재현이 주요 문제임

## Ⅴ. 개선방안
1. 단기: Lock 획득 순서를 전역 규칙으로 통일하여 데드락 방지
2. 중기: Lock-Free 자료구조(`ConcurrentHashMap`, Atomic 변수) 적용으로 직렬화 구간 축소
3. 장기: 액터 모델·코루틴 기반 메시지 패싱 아키텍처로 공유 상태 자체를 제거

> 요약: Lock 순서 통일, Lock-Free 구조, 메시지 패싱으로 각 문제에 대응함

## Ⅵ. 전망
- 발전 방향: 구조적 동시성(Structured Concurrency) 표준화로 스레드 수명주기 관리 간소화
- 기술사적 판단: 가상 스레드(Java Loom) 등 경량 스레드 모델이 동기화 설계를 변화시킴
- 기술사 제언: 공유 가변 상태 최소화를 설계 원칙으로 수립하고 코드 리뷰에 반영할 필요
