# 📖 【암기용】 개념 완전 이해

> 목적: AIOps를 처음 보는 사람도 관측성 데이터가 이상 탐지·원인 분석으로 이어지는 과정과 한계를 완전히 이해하게 만든다. 시험 답안 양식이 아니라, 이해를 위한 설명이다.

## 한눈에
- **개요**: AIOps는 **관측성(Observability)** 데이터인 로그·메트릭·트레이스·이벤트에 머신러닝 기반 **이상 탐지**와 **상관분석**을 적용해 원인 후보를 좁히는 IT 운영 방식이다.
- **왜 필요한가**: MSA·컨테이너·오토스케일링 환경은 이벤트 수가 폭증해 사람이 모든 알림을 읽고 상관관계를 찾기 어렵다.
- **핵심 직관**: 관제실의 수많은 경보를 묶고, 평소 패턴과 다른 지점을 먼저 보여주는 분석 보조자다.

## 핵심 용어 정리 (내부에 등장하는 것들)

| 용어 | 의미 | 비유 |
|:---|:---|:---|
| 관측성 (Observability) | 로그·메트릭·트레이스 3요소로 시스템 내부 상태를 외부에서 추론하는 능력 — AIOps가 분석하는 **원재료** | 몸에 꽂은 각종 센서 |
| 로그 (Log) | 특정 시점에 발생한 이산적 이벤트 기록 | 사건 일지 |
| 메트릭 (Metric) | 시간에 따라 집계되는 수치(오류율, 지연시간) | 체온계 그래프 |
| 트레이스 (Trace) | 요청 하나가 여러 서비스를 거치는 경로 기록 | 택배 배송 조회 |
| 이상 탐지 (Anomaly Detection) | 정상 기준선(baseline)과 다른 패턴을 찾는 모델 | 평소와 다른 심박수 알람 |
| 상관분석 (Correlation) | 서로 다른 이벤트를 시간·서비스·토폴로지로 묶는 분석 | 여러 목격자 진술 대조 |
| RCA (근본원인분석, Root Cause Analysis) | 원인 후보를 순위화해 제시하는 결과물 | 사고 원인 보고서 초안 |
| Runbook | 조치 절차를 정의한 자동화 스크립트·문서 | 응급처치 매뉴얼 |
| Human-in-the-loop | 자동 조치 전에 사람 승인을 거치는 통제 | 자동운전의 운전자 개입 |

## 깊이 이해

### 왜 AIOps가 필요했나 (배경)
- 전통 관제는 임계치(threshold) 알림에 의존한다. 그런데 컨테이너·오토스케일링 환경에서는 정상 범위 자체가 시간대·트래픽에 따라 계속 바뀌어, 고정 임계치로는 오탐과 미탐이 동시에 늘어난다. AIOps는 이 정상 범위(기준선)를 데이터로 학습해 동적으로 잡는다.

### 파이프라인 동작 원리 — 단계별
- ① 데이터 수집: 로그·메트릭·트레이스·이벤트를 OpenTelemetry 등으로 정규화한다. ② 기준선 학습: 서비스별 정상 범위(예: 평시 5xx 오류율 0.1%)를 학습한다. ③ 이상 탐지: 기준선을 벗어나면 이상 이벤트로 표시한다. ④ 상관분석: 같은 시간대·같은 서비스의 배포·인프라 이벤트와 묶는다. ⑤ RCA 후보 산출과 조치 제안.

### 이상 탐지 — 수치로 이해
- 배포 후 10분 내 5xx 오류율이 평시 0.1%에서 3%로(30배), p95 지연이 300ms에서 1.2초로(4배) 뛰면, 이 변화 폭은 정상 변동 범위를 크게 벗어나 이상으로 표시된다.
- 동시에 "배포 이벤트가 10분 전에 있었다"는 사실이 상관분석에 걸려, RCA 후보 1순위로 해당 배포가 제시된다. 배포 이벤트가 없었다면 인프라(노드 장애)나 의존 서비스 쪽으로 후보가 이동한다.

### 탐지 품질 — Precision과 Recall로 이해
- Precision(정밀도) 80%는 "AIOps가 이상이라고 울린 알림 100건 중 80건이 실제 장애"라는 뜻이다. 나머지 20건은 오탐(false positive)이다.
- Recall(재현율) 70%는 "실제 발생한 장애 100건 중 70건을 탐지했다"는 뜻이다. 나머지 30건은 놓친 것(false negative)이다.
- 둘은 트레이드오프다. 민감하게(임계값을 낮게) 잡으면 recall은 오르지만 precision(오탐)이 나빠진다. 그래서 알림 소음률과 미탐 위험을 함께 보고 임계값을 조정한다.

### 자동 조치의 한계 — 왜 Human-in-the-loop인가
- AIOps가 원인 후보를 제시해도, 데이터 품질이 나쁘거나 Runbook·승인 정책이 없으면 잘못된 자동 조치(예: 정상 노드를 장애로 오판해 강제 재시작)가 오히려 장애를 확대할 수 있다. 그래서 영향 범위가 큰 조치는 사람 승인을 거치게 한다.

### 비유
- 병원 응급실에서 여러 검사 결과를 종합해 위험 환자를 먼저 표시하는 트리아지(triage) 시스템과 같다. 진단과 치료는 결국 의사가 하지만, 우선순위는 시스템이 좁혀준다.

## 연결 개념
- Observability: AIOps 분석의 입력 데이터(로그·메트릭·트레이스)
- SRE: 알림 소음 감소와 MTTR 단축에 AIOps 활용
- MLOps: 이상 탐지 모델의 학습·드리프트 감시·재학습 운영

# 📝 【답안용】 시험 답안 템플릿

> 목적: AIOps를 도구명 나열이 아니라 데이터 수집, 분석, 자동 조치, 검증 지표로 답안화한다.
> 핵심: 출제자는 AI 적용 자체보다 운영 데이터 품질과 자동 조치 통제 기준을 본다.

## 핵심 인사이트 (3줄 요약)

> 1. **본질**: AIOps는 IT 운영 데이터에 머신러닝·상관분석을 적용해 이상 탐지, 원인 후보, 자동 조치를 지원하는 운영 플랫폼이다.
> 2. **가치**: 알림 소음률, MTTA, MTTR, 재발 장애 건수를 줄이기 위해 이벤트를 묶고 원인 후보를 우선순위화한다.
> 3. **판단 포인트**: 자동 복구는 승인 정책과 Runbook이 있는 범위에서만 적용하고, 모델 오탐률과 데이터 누락률을 함께 관리해야 한다.

## Ⅰ. 개요 및 필요성

- 개요: AI 기반 IT 운영 분석 체계
- 배경: 클라우드 네이티브 환경에서는 로그·메트릭·트레이스·이벤트가 폭증해 수동 관제로 원인 분석 시간이 길어진다.
- 필요성: 이상 탐지, 이벤트 상관분석, RCA 후보 산출로 장애 판단과 Runbook 실행 기준을 제공한다.

---

## Ⅱ. 구조 및 구성요소

```text
Logs/Metrics/Traces/Events -> Data Lake -> Correlation/Anomaly Model
                                      +-> RCA 후보 -> Runbook/Automation
```

| 구성요소 | 역할 | 특이사항 |
|:---|:---|:---|
| 데이터 수집 | 로그·메트릭·트레이스 통합 | OpenTelemetry, Syslog |
| 정규화/상관분석 | 시간·서비스·토폴로지 기준 매핑 | CMDB, Service Map |
| AI 분석 | 이상 탐지, 예측, 군집화 | 오탐률 관리 필요 |
| 자동 조치 | Runbook 실행, 티켓 생성 | 승인 단계와 권한 통제 |

> 요약: AIOps는 관측 데이터를 정규화한 뒤 상관분석과 모델 분석으로 원인 후보와 조치안을 만든다.

---

## Ⅲ. 동작원리 및 흐름도

```text
데이터 수집 -> 기준선 학습 -> 이상 탐지 -> 이벤트 상관분석
-> 원인 후보 산출 -> 영향 범위 표시 -> Runbook 실행/승인
```

| 단계 | 처리 내용 | 검증 기준 |
|:---:|:---|:---|
| 1 | 로그·메트릭·트레이스 수집 | 데이터 누락률 1% 이하 |
| 2 | 기준선과 계절성 학습 | 서비스별 정상 범위 |
| 3 | 이상 이벤트 탐지 | precision, recall |
| 4 | 배포·인프라 이벤트 연결 | RCA 후보 Top 3 |
| 5 | 조치 실행 또는 티켓 생성 | MTTR, rollback 시간 |

> 요약: AIOps는 정상 패턴과 다른 이벤트를 찾고, 배포·토폴로지 정보를 결합해 원인 후보를 좁힌다.

## Ⅴ. 심화 비교 및 적용 판단

| 비교 축 | 기존/대안 | 본 키워드 | 선택 기준 |
|:---|:---|:---|:---|
| 구조 | NMS/APM 개별 운영 | 통합 데이터와 분석 모델 | 도구 3개 이상 분산 시 |
| 비용/성능 | 임계치 튜닝 반복 | 동적 기준선과 군집화 | 알림 소음률 30% 이상 |
| 운영/위험 | 수동 조치 | 승인 기반 자동 조치 | Runbook 표준화 완료 시 |

> 요약: AIOps는 관측 데이터가 충분하고 반복 장애 패턴이 누적된 조직에서 도입 우선순위가 높다.

| 리스크 | 원인 | 대응 방안 | 확인 지표 |
|:---|:---|:---|:---|
| 오탐 증가 | 학습 데이터 품질 저하 | 서비스별 기준선 재학습 | false positive rate |
| 자동 조치 사고 | 권한·승인 누락 | Human-in-the-loop 적용 | 자동 조치 실패율 |
| 데이터 사일로 | 로그·APM·CMDB 분리 | OpenTelemetry와 공통 태그 | trace-log 매핑률 |

> 요약: AIOps 리스크는 데이터 품질과 자동화 권한에서 발생하므로 공통 태그와 승인 체계가 필요하다.

| 점검 항목 | 목표 기준 | 측정 방법 |
|:---|:---|:---|
| 탐지 품질 | precision 80% 이상, recall 70% 이상 | 장애 라벨 데이터 검증 |
| 대응 시간 | MTTA 5분, MTTR 30분 | Incident 로그 |
| 알림 품질 | 중복 알림 50% 감소 | Alertmanager, 티켓 분석 |

> 요약: AIOps 성과는 탐지 품질, 대응 시간, 알림 중복 감소로 검증한다.

## Ⅵ. 실무 적용 및 결론

**적용 방안 3개:**
1. OpenTelemetry 기반으로 서비스명, 버전, 배포 ID, 리전 태그를 통일하고 로그·메트릭·트레이스를 같은 Trace ID로 연결함
2. 6개월 Incident 데이터를 라벨링해 이상 탐지 모델의 precision 80%, recall 70% 목표를 설정하고 오탐 사례를 재학습 데이터로 반영함
3. 자동 조치는 캐시 재시작, 스케일 아웃, rollback 후보 생성처럼 영향 범위를 제한하고 승인자·감사 로그를 남김

**결론 (2줄):**
- 기술사 판단: AIOps는 관측성 데이터와 Runbook이 준비된 조직에 적용하고, 데이터 사일로가 큰 조직은 수집 표준화부터 수행함
- 향후 방향: 생성형 AI 기반 운영 코파일럿과 결합하되 조치 권한, 감사, 변경 승인 체계를 먼저 고정함
