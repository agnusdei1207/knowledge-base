# 📖 【암기용】 개념 완전 이해

## 한눈에
- **개요**: Git을 단일 진실 공급원(SSOT)으로 삼아 인프라와 애플리케이션의 배포를 자동화하는 운영 방법론
- **왜 필요한가**: 수동 배포나 단순 파이프라인(Push 방식)은 현재 운영 환경의 실제 상태와 코드 저장소의 상태가 불일치할 위험이 크고, 장애 발생 시 롤백이 어렵다.
- **핵심 직관**: "Git에 코드를 푸시하면, 클러스터에 상주하는 로봇(Agent)이 알아서 Git의 상태와 현재 상태를 비교해 똑같이 맞춰준다."

## 핵심 용어 정리

| 용어/표기 | 의미 | 비유·예 |
|:---|:---|:---|
| 선언적 인프라 (Declarative) | 시스템이 도달해야 할 최종 상태(What)를 명시 | "온도를 24도로 맞춰줘" (에어컨) |
| SSOT (단일 진실 공급원) | 모든 설정과 코드의 유일한 기준점 | 헌법 (모든 법은 헌법에 맞춘다) |
| Reconciliation (상태 동기화) | 목표 상태와 현재 상태를 지속적으로 비교하고 일치시킴 | 온도 조절기의 피드백 루프 |
| Pull-based CD | 대상 환경 내부의 에이전트가 저장소의 변경을 가져와 배포 | 직원이 지시서를 직접 확인하고 실행 |

## 깊이 이해
- **배경·문제의식**: 기존 CI/CD 파이프라인(Push 방식)은 CI 서버가 운영 환경에 직접 접근하기 위해 막강한 권한(보안 취약점)을 가져야 했다. 또, 누군가 kubectl로 직접 클러스터를 수정하면 Git의 설정과 실제 환경이 달라지는 구성 표류(Configuration Drift)가 발생한다.
- **작동 원리**: 모든 인프라와 앱 설정(YAML)을 Git에 선언적으로 저장한다. Kubernetes 클러스터 내부에는 ArgoCD나 Flux 같은 GitOps 에이전트가 돌고 있다. 에이전트는 주기적으로 Git을 폴링(Pull)하여 변경 사항을 감지하고, 클러스터의 현재 상태를 Git 상태로 동기화(Reconcile)한다.
- **비유**: 레스토랑의 레시피 북(Git). 주방장(ArgoCD)은 항상 레시피 북을 보고 요리(운영 환경)를 만든다. 누군가 레시피 북을 수정하면 주방장은 즉시 요리를 그에 맞게 다시 만든다.
- **구체 예시**: 개발자가 `deployment.yaml`의 이미지 태그를 `v1`에서 `v2`로 바꾸고 Git에 PR을 머지하면, ArgoCD가 이를 감지해 자동으로 클러스터의 Pod를 `v2`로 롤링 업데이트한다.
- **흔한 오해·주의점**: "GitOps는 단순히 CI/CD의 CD 부분일 뿐이다?" 아니다. 모든 변경을 Git PR 리뷰를 거치게 함으로써 감사를 투명하게 하고 보안을 강화하는 전체적인 운영 철학이다.

## 연결 개념
- Kubernetes: 선언적 상태 관리를 기본으로 하여 GitOps와 최상의 궁합을 이룸
- ArgoCD / Flux: 대표적인 Pull 기반 GitOps 도구
- IaC (Infrastructure as Code): GitOps의 토대가 되는 인프라 코드화

# 📝 【답안용】 시험 답안 템플릿

## 핵심 인사이트 (3줄 요약)

> 1. **본질**: GitOps는 Git을 단일 진실 공급원(SSOT)으로 하여, 선언적 인프라와 앱 설정을 Pull 방식으로 자동 동기화하는 운영 방법론이다.
> 2. **가치**: 구성 표류 방지, 빠른 롤백, CI 서버 권한 분리를 통해 배포 안정성과 보안(Audit)을 획기적으로 향상시킨다.
> 3. **판단 포인트**: 기존 Push 방식 CD와 Pull 방식 GitOps의 차이를 명확히 하고, 상태 동기화(Reconciliation) 루프를 핵심으로 제시해야 한다.

## 출제 의도 및 답안 포인트

| 출제 의도 | 반드시 짚을 핵심 | 감점 회피 포인트 |
|:---|:---|:---|
| 클라우드 네이티브 배포 패러다임 이해 | 단일 진실 공급원(SSOT), 선언적 인프라, Pull 모델, Reconciliation | 단순 CI/CD와 동일시 단정 |
| 기존 Push 기반 배포와의 차별성 | 구성 표류(Drift) 방지, 보안(CI 권한 분리), 빠른 롤백 | ArgoCD 같은 특정 툴 설명에만 매몰 |
| 도입 시 기대효과와 아키텍처 | 상태 감시 루프(Control Loop), 감사 추적(Audit Trail) | 원리 누락 |

> 요약: Git을 통한 명시적 선언과 Pull 기반 상태 동기화 루프가 결합된 아키텍처적 우수성을 보여주어야 한다.

---

## Ⅰ. 개요 및 필요성

- 개요: 시스템의 선언적 설정(Declarative Configuration)을 Git에 저장하고, 에이전트가 이를 운영 환경에 자동 동기화하는 배포/운영 방법론
- 배경: Push 기반 CD는 CI 서버의 과도한 권한 요구 및 수동 변경 시 발생하는 구성 표류(Configuration Drift) 문제 노출
- 필요성: 일관된 상태 유지(SSOT 보장), 배포 권한 통제 강화, 재해 복구(DR) 및 롤백 시간 50% 이상 단축 필요

---

## Ⅱ. 구조 및 구성요소

```text
[개발 환경]          [Git Repository]         [운영 환경 (Kubernetes)]
Dev -> PR/Merge -> App Repo / Config Repo <- (Pull) GitOps Agent
                         |                             |
                         +-- 단일 진실 공급원          +-- 상태 동기화(Reconcile)
```

| 구성요소 | 역할 | 특이사항 |
|:---|:---|:---|
| Git Repository | 인프라/앱의 선언적 설정 저장 (SSOT) | 모든 변경 이력 감사(Audit) 역할 |
| GitOps Agent | 대상 환경 내에서 실행되며 Git 상태 감시 | ArgoCD, Flux 등 (Pull 방식 동작) |
| Declarative Config | 도달해야 할 최종 상태 정의 명세서 | Kubernetes YAML, Helm, Kustomize |

> 요약: Git 저장소가 유일한 기준(SSOT)이 되며, 클러스터 내부의 에이전트가 이를 Pull하여 상태를 일치시키는 구조다.

---

## Ⅲ. 동작원리 및 흐름도

```text
코드 변경 -> PR 생성 및 리뷰 -> Git 머지 -> Agent 변경 감지 -> 상태 동기화(Reconcile)
```

- 1단계 [코드 및 설정 변경]: 개발자가 앱 코드나 인프라 설정(YAML)을 수정하고 Git에 Push 및 PR 요청
- 2단계 [검토 및 머지]: 코드 리뷰 및 CI 테스트 통과 후 메인 브랜치에 Merge (SSOT 업데이트)
- 3단계 [상태 감지 및 Pull]: 클러스터 내의 GitOps 에이전트가 Git의 새로운 상태를 Polling 또는 Webhook으로 감지
- 4단계 [Reconciliation]: 에이전트가 클러스터 현재 상태와 Git 상태의 차이를 계산(Diff)하여 일치하도록 배포 적용

> 요약: 변경 사항은 오직 Git PR을 통해서만 반영되며, 에이전트가 차이를 감지해 자동으로 목표 상태에 도달시킨다.

---

## Ⅳ. 특징
- [보안 강화]: CI 서버가 클러스터 접근 권한(크리덴셜)을 가지지 않아 공격 표면 감소
- [빠른 복구(MTTR)]: 장애 발생 시 Git 커밋 리버트(Revert)만으로 즉시 이전 정상 상태로 자동 롤백
- [구성 표류 방지]: 누군가 클러스터를 수동으로 조작해도, 에이전트가 즉시 Git 상태로 덮어써 일관성 유지
- [감사 추적 용이]: 누가, 언제, 무엇을 변경했는지 Git 커밋 히스토리에 완벽히 기록됨

> 요약: Pull 방식을 통한 보안성 향상과 구성 표류 방지가 가장 큰 특징이다.

## Ⅴ. 심화 비교 및 적용 판단

| 비교 축 | Push 기반 CD (Jenkins 배포) | Pull 기반 GitOps (ArgoCD) | 선택 기준 |
|:---|:---|:---|:---|
| 배포 주체 | 외부 CI/CD 서버 | 클러스터 내부 에이전트 | 클러스터 보안 격리 요구 수준 |
| 권한 관리 | CI 서버가 클러스터 인증서 보유 | 클러스터가 Git 읽기 권한만 보유 | 제로 트러스트(Zero Trust) 보안 정책 |
| 수동 변경 대응 | 구성 표류 발생 가능 | 즉각적 동기화로 덮어씀 (방지) | 선언적 인프라 성숙도 |

> 요약: 보안이 중요하고 쿠버네티스 중심의 선언적 인프라가 갖춰진 환경에서는 Pull 기반 GitOps가 필수적이다.

**리스크·대응:**
- [Git 저장소 장애]: 단일 장애점(SPOF)화 → Git 서비스 고가용성 구성 및 로컬 캐싱 적용 (지표: Git Uptime 99.9%)
- [시크릿 관리 취약]: Git에 비밀번호 평문 노출 → Sealed Secrets, SOPS 연동으로 암호화 저장 (지표: 시크릿 노출 건수 0)

**도입 후 점검 지표:**
- 배포 속도/안정성: 리드 타임 및 MTTR 감소율 — 배포 도구 대시보드
- 구성 표류 비율: Git 설정과 클러스터 상태 불일치 발생 횟수 — GitOps 에이전트 상태 모니터링

---

## Ⅵ. 실무 적용 및 결론

**적용 방안 3개:**
1. 아키텍처 분리: 앱 소스코드 저장소(App Repo)와 배포 설정 저장소(Config Repo)를 분리하여 CI 루프와 CD 루프의 결합도를 낮춤
2. 시크릿 보안 적용: HashiCorp Vault 또는 Sealed Secrets를 도입하여 GitOps 파이프라인 내 자격 증명 평문 노출 원천 차단
3. 자동 구성 표류 복구: ArgoCD의 `Self-Heal` 옵션을 활성화하여 운영자 수동 개입 시 즉시 Git 상태로 원복되도록 강제 설정

**결론 (2줄):**
- 기술사 판단: 쿠버네티스 기반 클라우드 네이티브 환경에서는 보안과 일관성 유지를 위해 Push 기반보다 Pull 기반 GitOps가 유리하다.
- 향후 방향: 다중 클러스터(Multi-Cluster) 및 멀티 클라우드 환경의 통합 관리를 위해 Crossplane 등과 결합된 GitOps 2.0 모델로 발전해야 한다.
