## Ⅰ. 개요
- **정의**: Git 저장소를 단일 진실 원천으로 삼아 인프라·배포를 선언적으로 관리하는 운영 모델
- **배경/필요성**: 수동 배포는 환경 간 구성 편차와 감사 추적 불가 문제를 유발하므로, 변경 이력이 자동 기록되는 선언적 파이프라인이 필요함
- **비유**: 레시피(Git)대로 자동 조리하는 주방 — 셰프가 직접 볶지 않아도 레시피 변경만으로 요리가 달라짐

| 출제 의도 | 반드시 짚을 핵심 | 감점 회피 포인트 |
|:---|:---|:---|
| 선언적 운영과 CI/CD 차이 이해 | Pull 기반 동기화, 단일 진실 원천 | Push 기반 CD와 혼동 금지 |

> 요약: Git 저장소 상태와 클러스터 상태를 자동 동기화하는 선언적 운영 모델임

## Ⅱ. 구성요소
```text
Developer --> Git Repo --> GitOps Operator --> Target Cluster
                |                 |
                v                 v
          Desired State      Reconcile Loop
```

| 구성요소 | 설명 | 비유 |
|:---|:---|:---|
| Git Repository | 인프라·앱 매니페스트의 단일 진실 원천 | 레시피북 |
| GitOps Operator | Git 상태와 클러스터 상태를 비교·동기화하는 에이전트 | 자동 조리 로봇 |
| Reconcile Loop | 현재 상태와 선언 상태 차이를 주기적으로 감지·수정하는 루프 | 품질 검수 라인 |
| Target Cluster | 실제 워크로드가 배포되는 실행 환경 | 식당 주방 |

> 요약: Git 저장소의 선언 상태를 Operator가 주기적으로 클러스터에 반영하는 구조임

## Ⅲ. 절차
```text
Commit --> Merge to Main --> Operator Detect --> Sync to Cluster
```
- 1단계: 개발자가 매니페스트 변경을 Git에 커밋·PR 생성함
- 2단계: 코드 리뷰 후 Main 브랜치에 병합함
- 3단계: GitOps Operator가 변경을 감지하고 Diff를 계산함
- 4단계: 클러스터에 선언 상태를 적용하고 결과를 검증함

> 요약: 커밋-병합-감지-적용의 4단계로 배포가 자동 수행됨

## Ⅳ. 문제점
- 비밀정보 노출: Git에 Secret을 평문 저장 시 자격증명 유출 위험이 있음
- Drift 감지 지연: Reconcile 주기 사이에 수동 변경이 발생하면 불일치 상태가 지속됨
- 멀티클러스터 복잡성: 클러스터별 분기 전략이 없으면 환경 간 구성 충돌이 발생함

> 요약: 비밀정보 관리, 동기화 지연, 멀티클러스터 분기가 주요 과제임

## Ⅴ. 개선방안
1. 단기: Sealed Secrets·SOPS 등 암호화 도구로 비밀정보를 Git에 안전 저장함
2. 중기: Reconcile 주기를 단축하고 Webhook 기반 즉시 동기화를 병행함
3. 장기: ApplicationSet 등 멀티클러스터 전용 추상화 계층을 도입함

> 요약: 암호화 저장, 즉시 동기화, 멀티클러스터 추상화로 개선 가능함

## Ⅵ. 전망
- 발전 방향: Policy-as-Code와 결합하여 거버넌스까지 Git 기반 관리로 확대됨
- 기술사적 판단: 클라우드 네이티브 운영 표준으로 정착 중이며 IaC(062 참조)와 상호 보완 관계임
- 기술사 제언: Pull 기반 모델의 보안 이점과 감사 추적 가치를 설계에 반영할 필요
