## 미리 알고가기

- GitOps는 Git 저장소를 운영 상태의 기준점으로 삼는 배포·운영 방식임
- 선언적 설정은 현재 환경을 어떻게 바꿀지 절차를 적는 대신 원하는 최종 상태를 파일로 적는 방식임
- 드리프트는 Git에 적힌 상태와 실제 운영 환경 상태가 서로 어긋난 상태임

## Ⅰ. 개요

- **정의/개념**: GitOps는 인프라와 애플리케이션 배포 상태를 선언적 파일로 Git에 저장하고 운영 환경이 그 저장소와 자동으로 동기화되도록 운용하는 배포·운영 방식임.
- **배경/필요성**: 운영자가 직접 환경을 바꾸는 방식은 추적성과 재현성이 약해 장애와 보안 위험을 키우므로, Git 승인 흐름을 기준으로 운영 상태를 관리할 필요가 커짐.

## Ⅱ. 특징

- Git commit·review 기록이 운영 변경의 승인 이력과 이전 선언 상태를 보존함
- 원하는 상태와 실제 상태 차이를 자동으로 감시할 수 있음
- 배포 권한을 Git 리뷰 흐름으로 통제하기 좋음
- 직접 수정이 허용되면 드리프트 관리가 어렵고 신뢰가 무너짐

## Ⅲ. 종류 및 비교

| 구분 | 전통 수동 운영 | GitOps |
|:---|:---|:---|
| 변경 출발점 | 운영자가 환경에 직접 접속해 설정을 바꿈 | Git 변경과 승인 흐름이 운영 변경의 출발점이 됨 |
| 추적 방식 | 접속 기록·명령 이력·작업 문서를 함께 조회 | commit과 review에서 변경자·내용·승인자를 조회 |
| 상태 복원 | 운영 환경에서 복구 명령 직접 실행 | 이전 선언 상태를 Git에 반영하고 controller가 동기화 |
| 구조상 한계 | 실수와 드리프트와 권한 남용 위험이 큼 | 선언형 파일 관리와 동기화 체계가 갖춰져야 함 |

> 요약: GitOps의 핵심은 Git을 쓰는 데 있지 않고 운영 상태를 코드처럼 승인하고 복원하는 데 있음.

## Ⅳ. 구성요소 및 구조

| 구성요소 | 설명 |
|:---|:---|
| 목표 상태 저장소 | 운영에 필요한 선언적 설정을 보관하는 단일 기준점이 됨 |
| 동기화 제어기 | 실제 환경과 Git 상태를 비교해 차이를 자동으로 맞춤 |
| 리뷰와 승인 흐름 | 운영 변경을 코드 리뷰와 승인 절차로 관리해 권한을 통제함 |
| 드리프트 탐지 | 수동 변경이나 동기화 실패로 생긴 불일치를 찾아 복원이나 경보를 수행함 |

## Ⅴ. 원리 및 절차 흐름도

```text
+-------------+     +-------------+     +-------------+     +-------------+
| 설정 변경 커밋  | --> | 리뷰/승인      | --> | 자동 동기화    | --> | 드리프트 감시  |
+-------------+     +-------------+     +-------------+     +-------------+
```

1. **설정 변경 커밋**: 원하는 상태를 Git에 반영함
2. **리뷰 및 승인**: 정책에 따라 변경 내용을 검토함
3. **자동 동기화**: 컨트롤러가 실제 환경을 원하는 상태로 맞춤
4. **드리프트 감시**: 불일치가 생기면 복원하거나 경보를 보냄

## Ⅵ. 실무 적용 및 유의점

1. 쿠버네티스 운영 조직에서는 GitOps가 배포 추적성을 크게 높이지만 운영자가 직접 환경을 수정하면 재현성이 깨지므로 직접 수정 경로를 제한하고 환경 불일치 건수와 수동 수정 비율로 확인함
2. 보안 민감 환경에서는 Git 승인 흐름이 유리하지만 긴급 복구가 느려질 수 있으므로 예외 복구 절차를 함께 두고 긴급 복구 시간과 승인 기록 완전성으로 확인함

## Ⅶ. 결론

GitOps는 운영 변경을 코드처럼 승인하고 복원할 필요가 큰 환경에서 특히 효과적인 운영 방식임.
