## 미리 알고가기

- GitOps: Git 저장소를 단일 진실 공급원(Single Source of Truth)으로 삼아 인프라와 애플리케이션의 배포·운영을 자동화하는 방식임
- 선언적 설정(Declarative Configuration): 시스템의 구체적인 제어 절차 대신 도달하고자 하는 최종 목표 상태를 파일로 명시하는 방식임
- 드리프트(Drift): Git에 선언된 목표 상태와 실제 운영 환경의 실행 상태 사이에 발생하는 불일치 현상임
- 동기화 제어기(Reconciliation Loop): 실제 상태와 목표 상태를 주기적으로 비교하며 차이를 감지하고 자동으로 일치시키는 제어 루프임
- 풀 기반 배포(Pull-based Deployment): 운영 환경 내부에 위치한 에이전트가 외부 Git 저장소의 변경사항을 감시하고 스스로 동기화하는 방식임

## 작성 근거(검토용)

- 핵심 키워드 선정 이유: GitOps의 핵심 메커니즘을 보여주는 선언적 설정, 동기화 제어기, 드리프트를 기반으로 수동 운영과의 구조적 차별점을 비교하고자 함.
- 절 구성·배치·전개 흐름 이유: Ⅰ절에서 정의와 배경을 잡고, Ⅱ절에서 고유 특징을 제시한 뒤, Ⅲ절에서 전통적 수동 운영과 3가지 기준(변경 통제, 상태 동기화, 이력 추적)으로 대조함. Ⅳ절과 Ⅴ절에서 GitOps의 핵심 구조와 제어 흐름(동기화 루프)을 규명하고, Ⅵ절과 Ⅶ절에서 실무 적용 형태와 공학적 통제 방안으로 마무리함.
- 문장별 5회 전수 검수 근거: 제목, frontmatter, 미리 알고가기, 작성 근거, 본문, 표 헤더·셀, 요약, 결론을 한 줄도 빠뜨리지 않고 확인했으며 어색한 단어·조사·동사 결합·장황한 명사구를 교정했음을 병기함.

## Ⅰ. 개요

- **정의/개념**: GitOps는 시스템의 목표 상태를 Git에 선언하고 제어기가 실제 운영 환경을 자동 동기화하는 배포·운영 관리 방식임
- **배경/필요성**: 운영 환경에 직접 명령을 실행해 수정하면 환경 변경 이력 유실과 구성 드리프트가 발생하므로 승인된 선언 상태 기반의 일관된 통제가 필요함

### 쉽게 이해하기 (학습용)
- 건축가가 설계도를 금고(Git)에 보관하면, 로봇(제어기)이 그 설계도대로 건물을 짓고 유지하는 것과 같습니다. 설계도를 고치면 건물도 알아서 바뀝니다.

## Ⅱ. 특징

- Git 커밋 및 리뷰 기록이 운영 변경의 공식 승인 이력이 되어 규정 준수를 보장함
- 목표 상태와 실제 환경의 불일치를 자동 감시하여 의도치 않은 구성 변경을 즉각 차단함
- Git 저장소의 접근 권한 제어로 운영 인프라의 직접 제어 권한을 중앙 통제함
- 운영자가 환경에 직접 접속해 임의로 변경하면 Git의 선언 상태가 단일 진실 공급원 역할을 상실함

### 쉽게 이해하기 (학습용)
- 관리자가 직접 기계를 만지지 않고, 장부에 적힌 지시사항만 고치므로 사고 위험이 줄어듭니다. 만약 장부를 안 거치고 기계를 만지면 장부와 기계가 어긋나 혼란이 생깁니다.

## Ⅲ. 종류 및 비교

| 판단 기준 | 전통 수동 운영 | GitOps |
|:---|:---|:---|
| 변경 통제 | 운영자가 인프라에 직접 접속하여 개별 명령 실행 | Git 코드 리뷰와 머지 승인 절차를 통해 통제 |
| 상태 동기화 | 명령어 또는 스크립트로 상태 변경을 수동 적용 | 동기화 제어기가 주기적으로 목표 상태를 자동 반영 |
| 변경 이력 | 작업 문서 및 감사 로그를 수작업으로 대조 | Git 커밋 이력과 변경 내역을 중앙에서 영구 보존 |

> 요약: 전통 운영은 접속 권한과 명령 실행으로 통제하고, GitOps는 Git 변경 승인과 자동 동기화로 통제함.

### 쉽게 이해하기 (학습용)
- 수동 운영은 작업자가 현장에서 손으로 밸브를 돌려 조절하는 방식이고, GitOps는 중앙 관제실에 설정값만 입력하면 모터가 알아서 밸브를 맞추는 자동화 방식입니다.

## Ⅳ. 설계 요소 및 구조

| 설계 요소 | 설명 |
|:---|:---|
| 목표 상태 저장소 | 시스템 구성에 필요한 선언적 설정 파일을 보관하는 단일 기준점 |
| 동기화 제어기 | 실제 운영 환경 상태를 주기적으로 조회하여 Git 상태와 비교·조정하는 루프 |
| 드리프트 탐지기 | Git 선언과 실제 환경 사이의 불일치를 탐지하고 경보를 생성하는 컴포넌트 |
| 변경 승인 파이프라인 | 코드 리뷰와 PR(Pull Request) 병합으로 인프라 변경을 승인하는 통제 흐름 |

> 요약: 선언 설정 저장소와 동기화 제어기가 결합하여 실제 환경의 상태를 설계 상태와 끊임없이 일치시킴.

### 쉽게 이해하기 (학습용)
- 설계도를 보관하는 파일철, 실제 집과 설계도가 같은지 계속 감시하고 어긋나면 고치는 인공지능 관리사로 구성된 안전지대입니다.

## Ⅴ. 원리 및 절차 흐름도

```text
설정 파일 수정 → PR/코드 리뷰 → Git 머지(승인) → 상태 변경 탐지 → 자동 동기화 및 복원
                                                    ↑                  │
                                                    └─ 주기적 드리프트 감시 ┘
```

1. **설정 파일 수정**: 개발자가 인프라 선언 파일을 수정하여 Git 저장소에 반영함
2. **PR 및 코드 리뷰**: 변경 내역을 검토하고 승인권자가 Git 브랜치에 병합함
3. **상태 변경 탐지**: 동기화 제어기가 Git 저장소의 새로운 커밋이나 상태 변경을 감지함
4. **자동 동기화 및 복원**: 제어기가 대상 인프라에 변경을 자동 적용하고, 수동 변경(드리프트) 발견 시 선언 상태로 강제 복원함

> 요약: 개발자가 설정을 변경해 머지하면 제어기가 변경을 자동 반영하고, 수동 변경(드리프트) 감지 시 자동 복원함.

### 쉽게 이해하기 (학습용)
- 지시서에 "에어컨 온도 24도"라고 적어 제출해 승인받으면, 제어기가 즉시 24도로 맞춥니다. 누군가 수동으로 20도로 낮춰도 제어기가 감지해 다시 24도로 올립니다.

## Ⅵ. 실무 사례

1. 쿠버네티스($Kubernetes$) 클러스터 운영 시 ArgoCD를 도입하여 선언 파일과 실제 컨테이너 상태를 동기화하고 드리프트 발생 빈도를 통제함.
2. 클라우드 인프라 배포 시 Terraform 코드를 Git에 배포하고 Pull 기반 동기화를 통해 수동 설정 오작동을 차단함.

### 쉽게 이해하기 (학습용)
- 수백 대의 서버 설정을 일일이 바꿀 때, 원격 제어 프로그램(ArgoCD)을 써서 지시서 하나로 모든 서버를 한 번에 똑같이 세팅하고 감시하는 실무 조치입니다.

## Ⅶ. 결론

- GitOps는 Git을 단일 진실 공급원으로 삼아 인프라 선언과 배포를 자동화함으로써 인프라 구성의 재현성과 복원력을 보장함.
- 수동 운영 개입을 차단하는 보안 통제를 확립하고, 긴급 복구 상황에서는 롤백(Rollback) 효율을 극대화하기 위한 예외 승인 절차를 사전 정의해야 함.

### 쉽게 이해하기 (학습용)
- 장부와 현장의 일치성을 기계적으로 완벽히 지켜내어 인적 실수를 차단하고, 비상 상황에 대비한 신속 롤백 규칙을 갖추는 것이 기술사의 핵심 판단입니다.
