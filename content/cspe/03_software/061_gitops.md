## 미리 알고가기

- GitOps는 Git 저장소를 운영 상태의 기준점으로 삼는 배포·운영 방식임
- 선언적 설정은 현재 환경을 어떻게 바꿀지 절차를 적는 대신 원하는 최종 상태를 파일로 적는 방식임
- 드리프트는 Git에 적힌 상태와 실제 운영 환경 상태가 서로 어긋난 상태임

## 작성 근거(검토용)

- GitOps는 변경 출발점, 추적 방식, 복원 방식, 운영 제약을 핵심 비교축으로 선정함
- 구성과 절차는 목표 상태와 실제 상태를 비교·동기화하는 제어 흐름을 중심으로 제시함
- 실무 판단은 드리프트 건수, 수동 수정률, 복구 시간, 승인 기록 누락률로 구체화함

## Ⅰ. 개요

- **정의/개념**: GitOps는 인프라와 애플리케이션의 목표 상태를 Git에 선언하고 제어기가 운영 환경을 자동 동기화하는 방식임
- **배경/필요성**: 운영 환경을 직접 수정하면 변경 이력과 재현성이 약해지므로 승인된 선언 상태를 기준으로 운영할 필요가 있음

## Ⅱ. 특징

- Git 커밋·리뷰 기록이 운영 변경의 승인 이력과 이전 선언 상태를 보존함
- 원하는 상태와 실제 상태 차이를 자동으로 감시할 수 있음
- Git 리뷰 승인 권한으로 운영 변경 권한을 통제함
- 운영 환경 직접 수정이 반복되면 Git 선언 상태가 기준점 역할을 잃음

## Ⅲ. 종류 및 비교

| 판단 기준 | 전통 수동 운영 | GitOps |
|:---|:---|:---|
| 변경 출발점 | 운영자가 환경에 직접 접속해 설정을 바꿈 | Git 변경과 승인 흐름이 운영 변경의 출발점이 됨 |
| 추적 방식 | 접속 기록·명령 이력·작업 문서를 함께 조회 | 커밋과 리뷰에서 변경자·내용·승인자를 조회 |
| 상태 복원 | 운영 환경에서 복구 명령 직접 실행 | 이전 선언 상태를 Git에 반영하고 제어기가 동기화 |
| 구조상 한계 | 실수와 드리프트와 권한 남용 위험이 큼 | 선언형 파일 관리와 동기화 체계가 갖춰져야 함 |

> 요약: 운영자가 환경을 직접 변경하면 수동 운영, Git의 선언 상태를 자동 반영하면 GitOps 방식임.

## Ⅳ. 구성요소 및 구조

| 구성요소 | 설명 |
|:---|:---|
| 목표 상태 저장소 | 운영에 필요한 선언적 설정을 보관하는 단일 기준점이 됨 |
| 동기화 제어기 | 실제 환경과 Git 상태를 비교해 차이를 자동으로 맞춤 |
| 리뷰와 승인 흐름 | 운영 변경을 코드 리뷰와 승인 절차로 관리해 권한을 통제함 |
| 드리프트 탐지 | 수동 변경이나 동기화 실패로 생긴 불일치를 찾아 복원이나 경보를 수행함 |

> 요약: Git 저장소가 목표 상태를 보관하고 동기화 제어기가 실제 상태와의 차이를 탐지·복원함.

## Ⅴ. 원리 및 절차 흐름도

```text
+-------------+     +-------------+     +-------------+     +-------------+
| 설정 변경 커밋  | --> | 리뷰/승인      | --> | 자동 동기화    | --> | 드리프트 감시  |
+-------------+     +-------------+     +-------------+     +-------------+
```

1. **설정 변경 커밋**: 원하는 상태를 Git에 반영함
2. **리뷰 및 승인**: 정책에 따라 변경 내용을 검토함
3. **자동 동기화**: 컨트롤러가 실제 환경을 원하는 상태로 맞춤
4. **드리프트 감시**: 불일치가 생기면 복원하거나 경보를 보냄

> 요약: 승인된 목표 상태를 제어기가 운영 환경에 반영하고 이후 드리프트를 지속적으로 복원함.

## Ⅵ. 실무 사례

1. 쿠버네티스 운영은 선언 파일을 자동 동기화하고 드리프트 건수·수동 수정률을 확인함
2. 보안 환경은 Git 승인과 긴급 복구 절차를 운영하고 복구 시간·승인 기록 누락률을 확인함

## Ⅶ. 결론

GitOps는 승인된 선언 상태와 운영 환경을 자동 동기화해 변경 추적성과 복원성을 확보하는 운영 방식임
