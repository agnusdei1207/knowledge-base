# 📖 【암기용】 개념 완전 이해

## 한눈에
- **개요**: 커널 소스코드 수정이나 커널 모듈 적재 없이, 운영체제 커널 공간 안에서 샌드박스된 안전한 프로그램을 동적으로 실행할 수 있게 해주는 리눅스 기술이다.
- **왜 필요한가**: 기존에 시스템 성능 모니터링이나 네트워크 패킷 제어를 하려면 커널 코드를 뜯어고치거나 시스템 크래시 위험이 있는 커널 모듈을 만들어야 했다. eBPF는 안전하고 미친 듯이 빠른 커널 레벨 제어 길을 열어준다.
- **핵심 직관**: 운영체제 커널(요리사)이 일하는 주방에 외부인(사용자 프로그램)이 직접 들어갈 순 없지만, eBPF(레시피 검증기)를 통해 "안전성 인증을 받은 레시피"만 주방 요리사에게 넘겨서 그대로 요리하게 만드는 것이다.

## 핵심 용어 정리

| 용어/표기 | 의미 | 비유·예 |
|:---|:---|:---|
| 커널 공간 (Kernel Space) | 운영체제 핵심부로 하드웨어 자원을 직접 제어하는 고특권 영역 | 주방장 전용 출입구역 |
| Verifier (검증기) | eBPF 프로그램이 커널을 멈추거나 무한 루프에 빠지지 않는지 실행 전 검사하는 모듈 | 독성 감별사 |
| JIT Compiler | eBPF 바이트코드를 머신 코드로 실시간 변환하여 네이티브 속도로 실행하게 함 | 동시통역사 |
| 훅(Hook) 포인트 | 시스템 콜, 네트워크 패킷 도달 등 커널 내 특정 이벤트 발생 지점 | cctv 설치 지점 |

## 깊이 이해
- **배경·문제의식**: 과거 BPF는 네트워크 패킷 필터링(tcpdump) 용도로만 쓰였다. 커널 레벨에서 다양한 관측과 통제를 하고 싶었지만, LKM(Linux Kernel Module)을 작성하는 것은 커널 패닉 위험과 보안 취약성을 감수해야 했다.
- **작동 원리**: 사용자 공간에서 작성된 C 코드가 LLVM에 의해 eBPF 바이트코드로 컴파일된다. 커널 내 Verifier가 코드를 엄격히 검사(무한 루프 방지, 잘못된 메모리 접근 차단)한 후 통과하면 JIT 컴파일러가 기계어로 바꿔 커널의 훅(kprobes, tracepoints, XDP 등)에 부착(Attach)한다.
- **비유**: 웹 브라우저(커널)가 JavaScript(eBPF 프로그램)를 샌드박스 안에서 안전하게 실행하여, 브라우저 소스를 수정하지 않고도 동적 페이지(네트워크/관측 제어)를 만드는 것과 완전히 같은 원리다.
- **구체 예시**: 클라우드 네이티브 환경에서 컨테이너 간 패킷이 오갈 때 커널 네트워킹 스택(iptables)을 다 거치면 너무 느리다. eBPF의 XDP(eXpress Data Path) 훅을 사용하면 랜카드 드라이버 수준에서 패킷을 낚아채어 10배 이상 빠르게 드롭하거나 라우팅할 수 있다.
- **흔한 오해·주의점**: eBPF 코드는 튜링 완전(Turing Complete)하지 않다. 무한 루프를 짤 수 없고, 프로그램 크기 제약이 존재한다. 이는 커널의 절대적 안전을 보장하기 위한 의도적 제약이다.

## 연결 개념
- **Cilium**: eBPF 기반으로 설계된 차세대 쿠버네티스 CNI(네트워크 플러그인)
- **XDP (eXpress Data Path)**: 네트워크 스택 최하단에서 패킷을 처리해 성능을 극대화하는 eBPF 훅
- **Kprobes / Tracepoints**: 커널 함수 호출을 동적으로 가로채는 디버깅 훅

# 📝 【답안용】 시험 답안 템플릿

## 핵심 인사이트 (3줄 요약)

> 1. **본질**: eBPF는 리눅스 커널 소스 수정 없이 커널 공간 내부에서 사용자 정의 프로그램을 안전하게 실행하는 동적 샌드박스 런타임이다.
> 2. **가치**: 컨텍스트 스위칭 오버헤드를 극적으로 줄이면서 커널 레벨의 초고속 네트워크 처리(XDP), 심층 보안 통제, 세밀한 관측성을 제공한다.
> 3. **판단 포인트**: 커널 패닉 리스크를 없앤 것이 핵심이나, Verifier의 엄격한 제약(무한 루프 불가 등)으로 인해 복잡한 비즈니스 로직 적용에는 한계가 있음을 고려해야 한다.

## 출제 의도 및 답안 포인트

| 출제 의도 | 반드시 짚을 핵심 | 감점 회피 포인트 |
|:---|:---|:---|
| 기존 커널 제어(LKM) 대비 eBPF의 구조적 우위 확인 | Verifier(검증기), JIT 컴파일, Sandbox | 단순히 "가볍다/빠르다"는 빈 추상 표현 |
| eBPF의 3대 적용 영역 분별 | 고성능 네트워킹, 시스템 관측성, 런타임 보안 | 쿠버네티스 컨테이너 기술로만 국한하는 좁은 해석 |
| 동작 메커니즘과 통제 모델 이해 | LLVM 컴파일 → 커널 훅 부착 → 이벤트 트리거 | 커널 소스코드를 수정한다는 사실 오류 |

> 요약: 커널 모듈의 위험성을 제거한 검증 메커니즘을 설명하고, 클라우드 네이티브 환경의 네트워크/보안 가속기로서의 실무 적용 방안을 제시해야 한다.

---

## Ⅰ. 개요 및 필요성

- 개요: eBPF(Extended BPF)는 리눅스 커널 이벤트(Syscall, Network 등) 발생 시 커널 내부의 샌드박스에서 사용자 정의 바이트코드를 실행하는 기술임
- 배경: 기존 iptables나 LKM(Linux Kernel Module) 방식은 룰이 많아지면 성능이 급감하거나 시스템 크래시(Kernel Panic) 위험이 큼
- 필요성: 클라우드 네이티브 환경의 방대한 마이크로서비스 간 트래픽과 컨테이너 행위를 저지연·무중단으로 관측하고 제어할 혁신 수단 요구

---

## Ⅱ. 구조 및 구성요소

```text
[User Space]         [Kernel Space]
C Code -> LLVM -> eBPF Bytecode -> Verifier (검증) -> JIT Compiler
                                                         |
                                                  Event Hook 부착 (XDP, Kprobe) -> BPF Map (데이터 공유)
```

| 구성요소 | 역할 | 특이사항 |
|:---|:---|:---|
| Verifier (검증기) | 커널 크래시 방지를 위해 메모리 접근, 무한 루프 등 안전성 정적 분석 | 통과하지 못하면 실행 거부 |
| JIT Compiler | 바이트코드를 타겟 아키텍처의 네이티브 머신 코드로 실시간 변환 | 실행 성능 극대화 (네이티브 속도) |
| Event Hooks | kprobes, urobes, tracepoints, XDP 등 이벤트 트리거 진입점 | 커널의 특정 동작 순간 캡처 |
| BPF Maps | 커널 공간과 유저 공간 간의 양방향 상태 및 데이터 공유 자료구조 | Key-Value 저장소 형태 |

> 요약: 유저 공간에서 컴파일된 코드가 커널 내부의 엄격한 검증(Verifier)을 거쳐 특정 훅에 부착되며, BPF Map을 통해 결과를 공유한다.

---

## Ⅲ. 동작원리 및 흐름도

```text
코드 작성/컴파일 -> 시스템 콜 적재 -> 안정성 검증/JIT 변환 -> 이벤트 후킹 -> 데이터 공유
```

- 1단계 [작성 및 컴파일]: 개발자가 C언어로 작성한 제한적 코드를 LLVM 파이프라인을 통해 eBPF 바이트코드로 생성
- 2단계 [적재 및 검증]: bpf() 시스템 콜을 통해 커널로 전달되며, Verifier가 유효성(크기, 권한, 무한루프 제어플로우) 검사
- 3단계 [변환 및 부착]: 안전성이 확인되면 JIT 컴파일러가 기계어로 변환하여 XDP나 시스템 콜 등의 타겟 훅에 Attach
- 4단계 [실행 및 수집]: 해당 커널 이벤트 발생 시 eBPF 프로그램이 즉각 실행되며, 패킷 필터링 결과나 메트릭을 BPF Map에 기록

> 요약: "작성 → 엄격한 검증 → 네이티브 변환 → 훅 부착"의 흐름을 통해 커널 패닉 리스크를 제로화하면서 런타임 로직을 주입한다.

---

## Ⅳ. 특징
- [성능 압도]: 커널-유저 공간 컨텍스트 스위칭 최소화 및 XDP를 통한 네트워크 스택 우회로 수백만 PPS(Packet Per Second) 처리 달성
- [무중단 동적 삽입]: 커널 재기동이나 모듈 로드 없이 런타임 중 실시간으로 추적·제어 로직 주입 및 해제 가능
- [절대적 안전성 보장]: Verifier에 의해 루프 제한, 후방 점프 금지, 제한적 메모리 접근만 허용되어 시스템 안정성 담보
- [로직 구현 한계]: 엄격한 안전성 제약으로 인해 튜링 완전(Turing Complete)하지 않아 복잡한 비즈니스 애플리케이션 로직 작성 불가

> 요약: 유저 스페이스 솔루션 대비 극단적 고성능을 제공하면서 LKM의 불안정성을 완벽히 극복하나, 복잡성 제약을 가진다.

## Ⅴ. 심화 비교 및 적용 판단

| 비교 축 | Linux Kernel Module (LKM) | iptables/Netfilter | eBPF | 선택 기준 |
|:---|:---|:---|:---|:---|
| 안전성 | 낮음 (커널 패닉 위험) | 높음 | 매우 높음 (Verifier) | 장애 격리 중요도 |
| 성능 | 높음 | O(N) 탐색으로 룰 증가시 저하 | O(1) 처리로 극강의 성능 | 대규모 트래픽 발생 여부 |
| 변경 유연성 | 커널 재빌드/재시작 필요 | 동적 룰 변경 | 런타임 동적 후킹 | 무중단 관측/제어 요구 |

> 요약: 단순 방화벽 룰은 iptables가 익숙하나, 클라우드 네이티브의 대규모 동적 트래픽과 심층 관측에는 eBPF가 압도적으로 유리하다.

**리스크·대응 (기본은 불릿):**
- [이식성 문제]: 커널 버전에 따라 커널 구조체 오프셋이 달라 동작 실패 → CO-RE(Compile Once, Run Everywhere) 기술 및 BTF 적용 (지표: 이종 커널 간 호환율)
- [보안 오남용]: 공격자가 eBPF 권한 획득 시 런타임 악성코드(Rootkit)로 악용 가능 → CAP_BPF 권한 엄격 통제 및 서명 기반 로드 강제 (지표: 권한 남용 이벤트 탐지 건수)

**도입 후 점검 지표 (기본은 불릿):**
- 시스템 성능: 패킷 처리 지연 시간(Latency) 기존 대비 40% 이상 감소 — 벤치마크 툴 측정
- 관측 커버리지: 컨테이너 간 L3~L7 네트워크 가시성 커버리지 100% 확보 — 텔레메트리 대시보드

## Ⅵ. 실무 적용 및 결론

**적용 방안 3개 (필수 — 단계별 또는 항목별):**
1. [고성능 CNI 전환]: 쿠버네티스 클러스터 네트워크 플러그인을 eBPF 기반의 Cilium으로 교체하여 kube-proxy(iptables) 병목 제거
2. [심층 관측성 확보]: Pixie 또는 Hubble을 도입하여 애플리케이션 코드 수정 없이 커널 단에서 HTTP, gRPC 등 L7 트레이스 자동 수집
3. [런타임 보안 통제]: Falco, Tetragon 같은 eBPF 기반 보안 도구를 적용하여 비정상 프로세스 실행 및 인가되지 않은 파일 접근 실시간 차단

**결론 (2줄):**
- 기술사 판단: eBPF는 단순한 네트워크 가속 기능을 넘어, 커널 수준 관측성과 제로 트러스트 보안을 코드 수정 없이 적용하는 클라우드 네이티브의 핵심 인프라임
- 향후 방향: 서비스 메시의 사이드카 프록시 오버헤드를 극복하기 위해, 사이드카리스(Ambient Mesh) 기반 eBPF 라우팅으로 시장이 빠르게 재편될 것임
