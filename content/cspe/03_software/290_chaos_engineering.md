# 📖 【암기용】 개념 완전 이해

> 목적: 카오스 엔지니어링을 처음 봐도 완벽히 이해하게 만든다. 시험 답안 양식이 아니라, 이해를 위한 친절한 설명이다.

## 한눈에
- **개요**: 장애를 통제된 방식으로 주입해 시스템 복원력을 검증하는 실험 기법
- **왜 필요한가**: 분산 시스템은 장애가 발생하지 않는 것이 아니라 일부 구성요소가 실패해도 서비스 목표를 지켜야 한다. 실제 장애 전 복구 능력을 검증해야 한다.
- **핵심 직관**: 카오스 엔지니어링은 재난 훈련이다. 불을 내는 것이 목적이 아니라 대피 경로와 대응 절차가 작동하는지 확인한다.

## 깊이 이해
- **배경·문제의식**: MSA, Kubernetes, 클라우드 환경은 네트워크 지연, pod 종료, zone 장애, dependency timeout이 상시 발생할 수 있다. 테스트 환경의 정상 케이스만으로 운영 복원력을 검증하기 어렵다.
- **작동 원리**: 정상 상태 가설(Steady State Hypothesis)을 세우고, 작은 blast radius에서 장애를 주입한 뒤, SLO 지표가 허용 범위에 있는지 관찰한다. 실패하면 자동 복구, 타임아웃, fallback, runbook을 개선한다.
- **비유**: 건물 비상훈련에서 일부 출입구를 막고 대피 시간이 기준 이내인지 측정하는 것과 같다.
- **구체 예시**: Kubernetes에서 5% pod를 강제 종료하고 p95 지연 300ms 이하, 오류율 1% 이하, 자동 재시작 2분 이내를 만족하는지 확인한다.
- **흔한 오해·주의점**: 카오스 엔지니어링은 무작위 장애 투입이 아니다. 가설, 범위 제한, 중단 조건, 관측성, 승인 절차가 있어야 한다.

## 연결 개념
- SRE - SLO와 error budget 기반 운영
- Resilience Pattern - timeout, retry, circuit breaker, bulkhead
- Observability - 실험 영향 측정

# 📝 【답안용】 시험 답안 템플릿

> 목적: 시험장에서 25분에 그대로 쓰는 답안 양식. 작성방식(추상표현 금지·수치·도식·문제유형 전환)을 엄격히 지킨다.
> 핵심: 장애 주입 도구 나열이 아니라 가설, blast radius, SLO, 중단 조건, 개선 루프를 포함한 실험 설계로 답안을 구성한다.

## 핵심 인사이트 (3줄 요약)

> 1. **본질**: 카오스 엔지니어링은 통제된 장애 주입으로 분산 시스템의 복원력 가설을 검증하는 실험 방법이다.
> 2. **가치**: 운영 장애 전에 SPOF, timeout 누락, 자동 복구 실패, 모니터링 공백을 발견한다.
> 3. **판단 포인트**: 실험은 SLO, blast radius, abort condition, observability가 준비된 범위에서만 수행해야 한다.

## 출제 의도 및 답안 포인트

| 출제 의도 | 반드시 짚을 핵심 | 감점 회피 포인트 |
|:---|:---|:---|
| 복원력 검증 개념 이해 확인 | 정상 상태 가설, 장애 주입, 관찰, 학습 | 무작위 장애 발생으로 오해 |
| SRE·운영 설계 판단 확인 | SLO, error budget, blast radius | 장애 주입 도구명만 나열 |
| 실무 적용 리스크 인식 확인 | 중단 조건, 승인, rollback, 고객 영향 통제 | 운영 실험의 위험 통제 누락 |

> 요약: 카오스 엔지니어링은 장애를 만드는 활동이 아니라 복원력 가설을 수치로 검증하는 실험이다.

---

## Ⅰ. 개요 및 필요성

- 개요: 카오스 엔지니어링은 장애 주입 실험이다.
- 배경: 클라우드와 MSA는 부분 장애가 전파되기 쉬우므로 운영 전 복원력 검증이 필요하다.
- 필요성: SLO와 중단 조건을 기준으로 통제된 실험을 수행해 장애 대응 절차를 검증해야 한다.

---

## Ⅱ. 구조 및 구성요소

```text
Steady State Hypothesis -> Fault Injection -> Observability -> Abort/Continue -> Learning/Remediation
                                +-> Blast Radius Control
                                +-> SLO/Error Budget
```

| 구성요소 | 역할 | 특이사항 |
|:---|:---|:---|
| 정상 상태 가설 | 서비스가 유지해야 할 수치 기준 정의 | 오류율, p95 지연, 처리량 |
| 장애 주입기 | pod kill, latency, CPU stress 주입 | Chaos Mesh, LitmusChaos, Gremlin |
| 관측성 | 영향 측정과 원인 분석 | metric, log, trace |
| 중단 조건 | 고객 영향 초과 시 즉시 중단 | error rate 1% 초과 등 |
| 개선 루프 | 발견 결함을 설계·운영에 반영 | runbook, circuit breaker |

> 요약: 카오스 실험은 가설, 주입, 관측, 중단, 개선 루프가 갖춰져야 운영 통제 안에서 수행된다.

---

## Ⅲ. 동작원리 및 흐름도

```text
가설 수립 -> 실험 범위 제한 -> 장애 주입 -> SLO 관찰 -> 결과 판정 -> 개선 조치
```

| 단계 | 처리 내용 | 검증 기준 |
|:---:|:---|:---|
| 1 | 정상 상태와 SLO 기준 정의 | p95 300ms 이하, 오류율 1% 이하 |
| 2 | blast radius와 승인 범위 설정 | 대상 트래픽 5% 이하 |
| 3 | 장애 주입 실행 | pod kill, network latency 200ms |
| 4 | metric, log, trace 관찰 | alert 발생과 자동 복구 확인 |
| 5 | 결과 회고와 결함 수정 | action item 완료율 95% 이상 |

> 요약: 카오스 엔지니어링은 작은 범위에서 장애를 주입하고 SLO 기준으로 복원력을 판정한다.

## Ⅳ. 특징

| 구분 | 전통 장애 테스트 | 카오스 엔지니어링 | 수치·기술 포인트 |
|:---|:---|:---|:---|
| 접근 방식 | 사전 정의 시나리오 | 가설 기반 실험 | steady state hypothesis |
| 범위 | 테스트 환경 중심 | stage에서 운영 일부까지 | blast radius 5% 이하 |
| 판단 기준 | 기능 정상 여부 | SLO 유지 여부 | p95, error rate, recovery time |
| 운영 통제 | 수동 점검 | abort condition과 관측성 | error budget |

> 요약: 카오스 엔지니어링은 기능 테스트가 아니라 SLO 기준 복원력 검증이다.

## Ⅴ. 심화 비교 및 적용 판단

| 비교 축 | 기존/대안 | 본 키워드 | 선택 기준 |
|:---|:---|:---|:---|
| 구조 | 장애 후 재발 방지 | 장애 전 가설 검증 | SLA 99.9% 이상 서비스 |
| 비용/성능 | 테스트 환경 한정 | 운영 일부 실험 | 관측성·롤백 준비 여부 |
| 운영/위험 | 미검증 복구 절차 | blast radius와 abort 조건 | 고객 영향 5% 이하 제한 |

> 요약: 카오스 실험은 관측성과 중단 조건이 없는 조직보다 SRE·자동복구 기반이 갖춰진 조직에 먼저 적용한다.

| 리스크 | 원인 | 대응 방안 | 확인 지표 |
|:---|:---|:---|:---|
| 고객 영향 확대 | blast radius 과다 | 트래픽 5% 이하, canary 범위 | 영향 사용자 수 |
| 실험 중단 실패 | abort 조건 미정의 | 자동 rollback, kill switch | 중단 시간 1분 이하 |
| 원인 분석 불가 | 관측성 부족 | metric, log, trace 사전 검증 | trace 수집률 95% 이상 |

> 요약: 카오스 엔지니어링의 위험은 범위, 중단, 관측성을 수치로 통제해야 낮출 수 있다.

| 점검 항목 | 목표 기준 | 측정 방법 |
|:---|:---|:---|
| 복원력 | p95 300ms 이하, 오류율 1% 이하 유지 | APM, SLO dashboard |
| 실험 안전 | blast radius 5% 이하, abort 1분 이하 | experiment log |
| 개선 완료 | action item 완료율 95% 이상 | postmortem tracker |

> 요약: 카오스 실험 성공은 장애를 견딘 사실보다 SLO 유지와 개선 항목 완료로 판단한다.

## Ⅵ. 실무 적용 및 결론

**적용 방안 3개:**
1. stage 환경에서 pod kill, network latency, CPU stress 실험을 먼저 수행하고 SLO dashboard와 alert 동작을 검증함
2. 운영 실험은 canary 트래픽 5% 이하, abort 조건 오류율 1% 초과, 자동 rollback 1분 이하로 제한함
3. Chaos Mesh 또는 LitmusChaos를 CI/CD와 연계해 월 1회 game day를 수행하고 개선 항목 완료율 95% 이상을 추적함

**결론 (2줄):**
- 기술사 판단: 관측성, 자동 복구, 중단 조건이 준비된 서비스부터 제한된 blast radius로 도입해야 함
- 향후 방향: 카오스 엔지니어링은 SRE game day, 자동 복원 테스트, 클라우드 장애 모의훈련으로 발전함
