# 📖 【암기용】 개념 완전 이해

> 목적: 카오스 엔지니어링을 처음 봐도 완벽히 이해하게 만든다. 시험 답안 양식이 아니라, 이해를 위한 친절한 설명이다.

## 한눈에
- **개요**: 카오스 엔지니어링은 **정상 상태 가설(Steady State Hypothesis)**을 세우고 통제된 **장애 주입(Fault Injection)**으로 시스템의 **복원력(Resilience)**을 검증하는 실험 방법론이다.
- **왜 필요한가**: 분산 시스템은 네트워크 지연, 서버 다운, 의존 서비스 장애가 언젠가 반드시 일어난다. 그 상황이 실제 운영 중 처음 벌어지면 대응 절차가 검증되지 않은 채로 장애를 맞는다. 카오스 엔지니어링은 그 첫 실전을 통제된 실험 조건으로 앞당긴다.
- **핵심 직관**: 예방접종이 몸에 약화된 병원체를 소량 주입해 면역 체계가 실제 감염 전에 대응 능력을 갖추게 하는 것처럼, 카오스 엔지니어링은 시스템에 작은 장애를 의도적으로 주입해 복구 메커니즘이 실전에서 작동하는지 미리 확인한다.

## 핵심 용어 정리 (내부에 등장하는 것들)

| 용어 | 의미 | 비유 |
|:---|:---|:---|
| 복원력(Resilience) | 장애가 발생해도 서비스 목표를 유지하는 능력 — 카오스 엔지니어링이 검증하려는 대상 | 충격을 흡수하고 원래 형태로 돌아오는 스프링 |
| 정상 상태 가설(Steady State Hypothesis) | "이 장애가 나도 시스템은 이 수치 범위를 유지할 것이다"라는 검증 대상 명제 | 백신 접종 전 세운 "면역이 형성될 것이다"라는 가설 |
| Blast Radius(영향 반경) | 실험이 영향을 미치는 범위 — 트래픽 비율, 인스턴스 수 등으로 제한 | 백신 임상시험의 접종 대상자 수 |
| Fault Injection(장애 주입) | 실제로 시스템에 넣는 결함의 종류 — pod kill, latency injection, CPU/메모리 stress, 의존 서비스 timeout 등 | 병원체를 몸에 넣는 방식(주사, 경구 등) |
| Abort Condition(중단 조건) | 사전에 정한 위험 수준을 넘으면 실험을 즉시 멈추는 규칙 | 임상시험 중 부작용 기준 초과 시 즉시 중단 |
| Game Day(게임데이) | 정기적으로 조직이 모여 수행하는 대규모 카오스 실험 훈련 | 정기 예방접종 캠페인 |
| SLO/Error Budget | 실험이 유지해야 할 목표 수치와 허용 여유분 — 판정 기준이 됨 | 면역 반응이 정상 범위 안에 있는지 판단하는 기준치 |
| Resilience Pattern(복원 패턴) | 카오스로 발견된 약점을 보완하는 설계 기법(circuit breaker, bulkhead, retry, timeout) | 백신 접종 후 강화된 면역 체계 자체 |

## 깊이 이해

### 왜 "가설"이라는 단어를 쓰는가 — 과학적 방법론
- 카오스 엔지니어링은 무작위로 시스템을 망가뜨리는 것이 아니라, 먼저 "이 장애가 발생해도 오류율은 1% 이하를 유지할 것이다"처럼 반증 가능한 가설을 세우고, 실험으로 그 가설을 검증하거나 반증한다.
- 가설이 반증되면(즉 오류율이 기준을 넘으면) 그 자체가 성과다 — 운영 중 실제 장애가 나기 전에 약점을 발견했기 때문이다. 가설이 유지되면 그 복원력 설계가 실제로 작동함을 증명한 것이다.

### Blast Radius를 단계적으로 넓히는 원리 — 수치로 이해
- 실험은 처음부터 전체 트래픽에 적용하지 않는다. 1% → 5% → 25% → 100% 순서로 영향 범위를 넓히며, 각 단계에서 문제가 없어야 다음 단계로 진행한다.
- 예: 신규 결제 서비스에 대해 처음엔 내부 테스트 계정(0.1%)에만 pod kill을 적용해 자동 복구를 확인하고, 문제가 없으면 실제 트래픽의 1%, 이후 5%로 넓힌다. 만약 5% 단계에서 오류율이 3%로 튀면(기준 1% 초과) 즉시 실험을 중단하고 25% 확대는 보류한다.
- 이렇게 단계를 나누는 이유는, 설계 결함이 있어도 피해를 최소 범위로 가두기 위해서다.

### 대표적 장애 주입 기법과 구체 예시
- **Pod/Instance Kill**: Kubernetes에서 무작위로 pod를 강제 종료해 오토스케일러·재시작 로직이 정상 작동하는지 확인한다. 예: 5%의 pod를 종료하고 2분 이내 자동 재기동되는지 측정.
- **Network Latency Injection**: 특정 서비스 간 통신에 인위적으로 지연을 추가한다. 예: 결제 서비스 → 재고 서비스 호출에 200ms 지연을 주입해, timeout 설정(예: 150ms)이 실제로 동작해 fallback으로 전환되는지 확인한다.
- **CPU/Memory Stress**: 인스턴스의 리소스를 인위적으로 소모시켜 오토스케일링·리소스 격리(bulkhead)가 작동하는지 본다.
- **Dependency Timeout/실패 주입**: 외부 API 호출을 강제로 실패시켜 재시도(retry)·circuit breaker가 연쇄 장애를 막는지 확인한다.

### 실험 성공/실패를 판정하는 수치 기준
- 정상 상태 가설은 구체적인 SLO 수치로 표현해야 판정이 가능하다. 예: "pod 5% 강제 종료 시 p95 응답 지연 300ms 이하, 오류율 1% 이하, 2분 이내 자동 재기동"이 가설이라면, 실험 중 관측치가 이 세 조건을 모두 만족하면 가설 유지(복원력 확인), 하나라도 벗어나면 가설 기각(약점 발견)이다.

### Abort Condition — 실험이 사고로 번지지 않게 막는 장치
- 사전에 "오류율이 5%를 넘으면 즉시 자동 롤백"처럼 자동 중단 규칙을 정해 두고, 이 조건은 사람이 대시보드를 지켜보지 않아도 시스템이 스스로 트리거하도록 구현한다.
- 예: 카오스 도구가 1분마다 오류율을 확인하다가 5% 초과를 감지하면 주입된 장애를 즉시 원복하고, 감지부터 중단까지 걸린 시간(1분 이내)이 실험 안전성의 지표가 된다.

### 배경 — Netflix Chaos Monkey
- 이 개념은 2010년대 초 Netflix가 AWS 클라우드로 이전하면서, 인스턴스가 예고 없이 사라지는 클라우드 환경에 견디는 시스템을 만들기 위해 "Chaos Monkey"라는 도구로 운영 시간 중 무작위로 인스턴스를 종료시킨 것에서 시작했다. 이후 이 사고방식이 Blast Radius 제한, 가설 검증, 자동 중단 같은 체계로 정교화되며 카오스 엔지니어링이라는 실천 분야로 발전했다.

### 흔한 오해
- "무작위로 아무거나 부수는 것"이 아니다. 가설, 영향 범위 제한, 중단 조건, 관측 체계가 사전에 준비된 상태에서만 수행하는 통제된 실험이다. 이 준비 없이 운영 환경에서 장애를 주입하면 그 자체가 사고가 된다.

## 연결 개념
- SRE·온콜 인시던트 대응(289) — 카오스 실험으로 발견한 약점이 runbook과 escalation 정책 개선으로 이어짐
- Resilience Pattern(circuit breaker, bulkhead, retry, timeout) — 카오스가 검증하는 대상이자, 실험 후 보강되는 설계
- SLO/Error Budget — 실험의 판정 기준이자 중단 조건의 근거
- Observability — 실험 중 영향을 실시간으로 측정하는 인프라

# 📝 【답안용】 시험 답안 템플릿

> 목적: 시험장에서 25분에 그대로 쓰는 답안 양식. 작성방식(추상표현 금지·수치·도식·문제유형 전환)을 엄격히 지킨다.
> 핵심: 장애 주입 도구 나열이 아니라 가설, blast radius, SLO, 중단 조건, 개선 루프를 포함한 실험 설계로 답안을 구성한다.

## 핵심 인사이트 (3줄 요약)

> 1. **본질**: 카오스 엔지니어링은 통제된 장애 주입으로 분산 시스템의 복원력 가설을 검증하는 실험 방법이다.
> 2. **가치**: 운영 장애 전에 SPOF, timeout 누락, 자동 복구 실패, 모니터링 공백을 발견한다.
> 3. **판단 포인트**: 실험은 SLO, blast radius, abort condition, observability가 준비된 범위에서만 수행해야 한다.

## 출제 의도 및 답안 포인트

| 출제 의도 | 반드시 짚을 핵심 | 감점 회피 포인트 |
|:---|:---|:---|
| 복원력 검증 개념 이해 확인 | 정상 상태 가설, 장애 주입, 관찰, 학습 | 무작위 장애 발생으로 오해 |
| SRE·운영 설계 판단 확인 | SLO, error budget, blast radius | 장애 주입 도구명만 나열 |
| 실무 적용 리스크 인식 확인 | 중단 조건, 승인, rollback, 고객 영향 통제 | 운영 실험의 위험 통제 누락 |

> 요약: 카오스 엔지니어링은 장애를 만드는 활동이 아니라 복원력 가설을 수치로 검증하는 실험이다.

## Ⅰ. 개요 및 필요성

- 개요: 카오스 엔지니어링은 장애 주입 실험이다.
- 배경: 클라우드와 MSA는 부분 장애가 전파되기 쉬우므로 운영 전 복원력 검증이 필요하다.
- 필요성: SLO와 중단 조건을 기준으로 통제된 실험을 수행해 장애 대응 절차를 검증해야 한다.

---

## Ⅱ. 구조 및 구성요소

```text
Steady State Hypothesis -> Fault Injection -> Observability -> Abort/Continue -> Learning/Remediation
                                +-> Blast Radius Control
                                +-> SLO/Error Budget
```

| 구성요소 | 역할 | 특이사항 |
|:---|:---|:---|
| 정상 상태 가설 | 서비스가 유지해야 할 수치 기준 정의 | 오류율, p95 지연, 처리량 |
| 장애 주입기 | pod kill, latency, CPU stress 주입 | Chaos Mesh, LitmusChaos, Gremlin |
| 관측성 | 영향 측정과 원인 분석 | metric, log, trace |
| 중단 조건 | 고객 영향 초과 시 즉시 중단 | error rate 1% 초과 등 |
| 개선 루프 | 발견 결함을 설계·운영에 반영 | runbook, circuit breaker |

> 요약: 카오스 실험은 가설, 주입, 관측, 중단, 개선 루프가 갖춰져야 운영 통제 안에서 수행된다.

## Ⅲ. 동작원리 및 흐름도

```text
가설 수립 -> 실험 범위 제한 -> 장애 주입 -> SLO 관찰 -> 결과 판정 -> 개선 조치
```

| 단계 | 처리 내용 | 검증 기준 |
|:---:|:---|:---|
| 1 | 정상 상태와 SLO 기준 정의 | p95 300ms 이하, 오류율 1% 이하 |
| 2 | blast radius와 승인 범위 설정 | 대상 트래픽 5% 이하 |
| 3 | 장애 주입 실행 | pod kill, network latency 200ms |
| 4 | metric, log, trace 관찰 | alert 발생과 자동 복구 확인 |
| 5 | 결과 회고와 결함 수정 | action item 완료율 95% 이상 |

> 요약: 카오스 엔지니어링은 작은 범위에서 장애를 주입하고 SLO 기준으로 복원력을 판정한다.

## Ⅵ. 실무 적용 및 결론

**적용 방안 3개:**
1. stage 환경에서 pod kill, network latency, CPU stress 실험을 먼저 수행하고 SLO dashboard와 alert 동작을 검증함
2. 운영 실험은 canary 트래픽 5% 이하, abort 조건 오류율 1% 초과, 자동 rollback 1분 이하로 제한함
