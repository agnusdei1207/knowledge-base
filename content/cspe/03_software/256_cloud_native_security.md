## Ⅰ. 개요
- 정의: 클라우드 환경 전반에 보안을 내재화하고 개발-보안-운영을 통합하는 체계임
- 배경: 코드·이미지·IaC·클러스터 설정이 반복 배포되므로 단계별 보안 검증과 추적 필요
- 출제 의도
| 대상 | 주요 포인트 | 비중 |
|------|------------|------|
| 4C 보안 | Cloud, Cluster, Container, Code | 매우높음 |
| Shift Left | 개발 초기 단계 보안 적용 | 높음 |

## Ⅱ. 구성요소
- ASCII 구조도
  [ Plan ] -> [ Code ] -> [ Build ] -> [ Test ] -> [ Deploy ]
     |          |          |          |            |
     +----------+---- [ Security Scan ] ----+----------+

- 구성요소 표
| 구성요소 | 설명 | 비유 |
|----------|------|------|
| SAST | 소스 코드 단계의 정적 취약점 분석 | 맞춤법 검사 |
| DAST | 실행 중인 앱에 대한 동적 취약점 분석 | 실제 시운전 |
| IaC 스캔 | 인프라 설정 파일(Terraform 등)의 보안 점검 | 설계도 검토 |

> 요약: SAST·DAST·IaC·이미지 스캔과 배포 정책을 개발·빌드·시험·운영 단계에 연결함

## Ⅲ. 절차
- ASCII 흐름도
  [보안 요건 수립] -> [CI/CD 보안 자동화] -> [런타임 모니터링] -> [피드백]
     (Policy)           (Scanning)           (Observability)     (Improve)

- 4단계 설명
1. 설계: 제로 트러스트 기반의 접근 제어 및 보안 가이드라인을 수립함
2. 빌드: 코드 커밋 시 스캔 도구를 실행하고 취약점 등급과 차단 기준을 판정함
3. 배포: 검증된 이미지만 배포되도록 정책 엔진(Admission Control)을 가동함
4. 운영: 실시간 위협 탐지 및 로그 분석을 통해 침해 사고를 방어하고 개선함

> 요약: 개발 단계의 검사 결과를 배포 승인과 런타임 탐지 규칙에 연결하고 결과를 환류함

## Ⅳ. 문제점
- 보안 점검 단계가 늘어남에 따라 개발 생산성 및 배포 속도가 저하될 우려 있음
- 오탐(False Positive) 결과가 많을 경우 개발자의 보안 피로도가 급증함

## Ⅴ. 개선방안
- (단기) 오탐을 줄이기 위해 보안 규칙을 정교화하고 점진적으로 자동 차단 적용함
- (중기) 개발자에게 보안 교육을 실시하여 '보안 내재화(Security Mindset)' 강화함
- (장기) AI 기반의 지능형 위협 탐지 도구를 도입하여 대응 자동화 수준을 높임

## Ⅵ. 전망
- 소프트웨어 공급망 보안(SBOM)이 DevSecOps의 필수 구성 요소로 자리 잡음
- 보안 정책 자체가 코드로 관리되는 PaC(Policy as Code) 환경이 보편화될 것임
