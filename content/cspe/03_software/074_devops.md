## Ⅰ. 개요
- **정의**: 개발(Dev)과 운영(Ops)을 통합하여 소프트웨어 배포 주기를 단축하는 문화·자동화 체계임
- **배경/필요성**: 개발과 운영 조직이 분리되면 릴리스 지연·장애 책임 전가가 반복되므로 협업 체계가 필요함
- **비유**: 설계팀과 시공팀이 같은 현장 사무실에서 일하며 즉시 피드백을 교환하는 방식과 유사함

| 출제 의도 | 반드시 짚을 핵심 | 감점 회피 포인트 |
|:---|:---|:---|
| CI/CD 파이프라인과 문화적 요소 이해 | CI/CD/CD 3단계, IaC, 피드백 루프 | DevOps를 도구 도입으로만 설명하지 말 것(문화 포함) |

> 요약: DevOps는 Dev-Ops 협업 문화와 CI/CD 자동화를 결합한 소프트웨어 배포 체계임

## Ⅱ. 구성요소
```text
Plan --> Code --> Build --> Test --> Release --> Deploy --> Operate --> Monitor
  ^                                                                      |
  +----------------------------------------------------------------------+
                           (Feedback Loop)
```

| 구성요소 | 설명 | 비유 |
|:---|:---|:---|
| CI (Continuous Integration) | 코드 커밋 시 자동 빌드·테스트 수행 | 원고 교정 자동화 |
| CD (Continuous Delivery) | 검증된 아티팩트를 릴리스 가능 상태로 유지 | 인쇄 대기 상태 |
| CD (Continuous Deployment) | 릴리스 승인 없이 프로덕션 자동 배포 | 자동 출판 |
| IaC | 인프라를 코드로 선언하여 버전 관리·재현성 확보 | 건축 설계도의 CAD 파일화 |

> 요약: CI/CD 파이프라인과 IaC를 기반으로 무한 피드백 루프를 구성함

## Ⅲ. 절차
```text
Commit --> Build --> Test --> Stage --> Deploy --> Monitor
   |                                                 |
   +<------------- Feedback / Rollback <-------------+
```
- 1단계: 개발자가 코드 커밋 시 CI 서버가 자동 빌드·단위 테스트 수행함
- 2단계: 통합 테스트·보안 스캔 통과 시 아티팩트를 레지스트리에 저장함
- 3단계: 스테이징 환경 배포 후 인수 테스트·성능 테스트 수행함
- 4단계: 프로덕션 배포 후 모니터링 지표 기반으로 이상 시 자동 롤백함

> 요약: 커밋-빌드-테스트-배포의 자동화 파이프라인과 모니터링 피드백으로 순환함

## Ⅳ. 문제점
- 조직 사일로 잔존: 도구만 도입하고 문화 변화 없으면 Dev-Ops 벽이 유지됨
- 파이프라인 복잡도 증가: 마이크로서비스 증가 시 파이프라인 수가 비례 증가하여 관리 부담 가중됨
- 보안 후순위화: 속도 중심 파이프라인에서 보안 검증 단계가 생략되는 경향 존재함

> 요약: 조직 문화, 파이프라인 복잡도, 보안 누락이 주요 문제임

## Ⅴ. 개선방안
1. 단기: 공동 온콜·Blameless 포스트모텀으로 Dev-Ops 협업 문화 정착함
2. 중기: 템플릿 기반 파이프라인 표준화로 서비스별 중복 설정 제거함
3. 장기: DevSecOps(075 참조) 전환으로 보안 게이트를 파이프라인에 내재화함

> 요약: 문화 정착, 파이프라인 표준화, 보안 내재화로 개선 가능함

## Ⅵ. 전망
- 발전 방향: Platform Engineering으로 진화하여 내부 개발자 플랫폼(IDP) 제공 추세임
- 기술사적 판단: 기술 도구와 조직 문화 양면을 균형 있게 서술해야 고득점 가능함
- 기술사 제언: DORA 4대 지표(배포 빈도·리드타임·MTTR·변경 실패율) 기반 성숙도 측정 체계 도입을 권고함
