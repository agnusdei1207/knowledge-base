## 핵심 인사이트 (3줄 요약)
- 깡통 스토리지(S3)로 구축된 '데이터 레이크'에 RDBMS의 고유 권한이던 **ACID 트랜잭션, Time Travel(시간 여행), 스키마 진화(Schema Evolution)** 기능을 부여하는 오픈소스 저장소 계층 (Table Format).
- Databricks가 개발하여 오픈소스로 푼 기술로, S3의 무식한 Parquet 파일들 옆에 `_delta_log`라는 트랜잭션 장부를 몰래 달아두어, 수천 명이 동시에 데이터를 읽고 써도 절대 꼬이지 않게 통제하는 마법을 부림.
- Hudi, Iceberg와 함께 '오픈 테이블 포맷' 3대장 중 하나이며, Apache Spark와 가장 완벽하게 한 몸처럼 돌아가는 최적화 덕분에 빅데이터 엔지니어들에게 가장 사랑받는 포맷임.

## Ⅰ. 개요 및 필요성
- **개요**: 데이터 레이크하우스(Lakehouse) 아키텍처를 구현하기 위해 스토리지 위에 구축되는 오픈소스 트랜잭션 스토리지 계층.
- **필요성**: 기존 데이터 레이크(S3)는 파일을 덮어쓰거나 중간에 실패하면 파일이 쪼개져 쓰레기 데이터가 남음. 만약 스파크(Spark)가 10시간 동안 100만 건을 S3에 쓰다가 99만 건에서 에러가 나서 뻗어버리면, 데이터 사이언티스트는 반쪽짜리 쓰레기 데이터를 읽고 잘못된 통계를 내버림. "S3에도 100% 성공 아니면 100% 롤백(Atomicity)을 보장하는 장부가 필요해!"라는 절규에서 탄생함.
---
## Ⅱ. 아키텍처 및 핵심 원리
- **1. 트랜잭션 로그 (Transaction Log / _delta_log)**:
  - Delta Lake의 핵심 심장부. 데이터 디렉터리 안에 JSON 형태로 모든 변경(INSERT, UPDATE)의 이력을 차곡차곡 장부에 기록함.
  - 읽는 사람은 장부를 먼저 보고 "아, 3번 파일은 방금 삭제됐으니 무시하고 4번 파일을 읽으면 되는구나"라고 완벽한 최신 상태(Consistency)를 파악함.
- **2. 타임 트래블 (Time Travel)**:
  - 장부(`_delta_log`)가 모든 파일의 과거 기록을 들고 있으므로, 물리적 파일이 지워지기 전까지는 언제든 과거로 돌아갈 수 있음.
  - `SELECT * FROM 테이블 TIMESTAMP AS OF '2026-07-04';` 쿼리 한 줄로, 백업본 없이도 어제 데이터 상태를 똑같이 100% 복원해 냄.
- **3. 스키마 강제와 진화 (Schema Enforcement & Evolution)**:
  - 레이크에 쓰레기 데이터가 들어오지 않게 타입(Type)을 깐깐하게 막음(Enforcement).
  - 반대로, 기존에 없던 '주소' 컬럼이 새로 추가된 데이터가 들어오면 기존 테이블 구조를 자동으로 안전하게 업데이트해 주는 마법(Evolution)을 제공함.

```text
[ Delta Lake의 트랜잭션(ACID) 동작 원리 ]

 🗂️ [ S3 스토리지 (원본) ]
 - file_A.parquet (회원 100명)
 - file_B.parquet (회원 50명)
 
 ⚡ [ 스파크 엔진의 UPDATE 요청: "회원 1명 삭제해!" ]
 
 1. 기존 데이터 레이크 (S3): 
    - file_A를 통째로 메모리에 올려서 1명 지우고 file_C로 다시 씀. 
    - 이 과정에서 다른 사람이 읽으면 쓰레기 값(Dirty Read) 보게 됨! 🚨
 
 2. Delta Lake 동작 방식:
    - file_A를 놔두고, 1명 지운 file_C를 새로 생성함.
    - 장부(`_delta_log`)에 적음: "이제부터 file_A는 폐기! file_C가 최신임!" 📝
    - 읽는 사람은 장부만 보고 즉각 file_C를 읽음 (충돌 제로, ACID 완벽 보장!) 🚀
```

## Ⅲ. 비교 및 연결
| 구분 | 기존 Data Lake (순수 Parquet) | Delta Lake |
|---|---|---|
| **트랜잭션(ACID)**| 미지원 (쓰다가 죽으면 쓰레기 남음) | **완벽 지원 (All or Nothing)** |
| **데이터 업데이트** | 파일 전체를 수동으로 갈아치워야 함 | **RDB처럼 UPDATE / MERGE INTO 지원** |
| **과거 복구** | 백업 스냅샷 없으면 불가능 | **Time Travel 기능으로 상시 복구 가능** |
| **동시성 제어** | 수십 명이 동시에 쓰면 100% 파일 꼬임 | **Optimistic Concurrency Control로 충돌 방지** |

## Ⅳ. 실무 적용 및 기술사 판단
- **Medallion(메달리온) 아키텍처의 구현**: Databricks가 밀고 있는 데이터 정제 파이프라인. Bronze(가공 안 된 원시 쓰레기) ➡️ Silver(필터링되고 조인된 깨끗한 데이터) ➡️ Gold(비즈니스 통계용 완벽한 테이블)의 3단계를 거침. 기술사는 이 단계마다 Delta Lake의 트랜잭션과 MERGE 기능을 활용하여 파이프라인 중간에 에러가 나도 데이터 정합성이 절대 깨지지 않는 완벽한 레이크하우스 파이프라인을 설계해야 함.
- **VACUUM을 통한 스토리지 최적화**: Time Travel은 기적 같지만, 물리적 파일을 안 지우고 놔두므로 S3 스토리지 요금이 기하급수적으로 폭발함. 실무에서는 주기적으로 `VACUUM` 명령어를 스케줄링하여 (보통 7일 이상 지난) 오래된 과거 히스토리 파일을 물리적으로 삭제해 비용을 최적화하는 핀옵스(FinOps) 엔지니어링이 필수적임.
---
## Ⅴ. 기대효과 및 결론
- "S3는 그냥 멍청한 파일 저장소"라는 고정관념을 깨고, 그 위에 얇은 논리적 장부(Transaction Log) 하나를 얹어 엔터프라이즈급 데이터베이스로 격상시킨 혁신 기술.
- 데이터 레이크가 가진 치명적 약점(데이터의 늪, 신뢰성 부족)을 완벽하게 치유함으로써, 현대 기업들이 데이터 웨어하우스를 버리고 레이크하우스(Lakehouse)로 넘어갈 수 있게 만든 가장 큰 1등 공신임.

### 👶 어린이를 위한 3줄 비유 설명
1. 기존 데이터 레이크는 도서관에서 책을 수정할 때, 원래 있던 책 페이지를 북북 찢어내고 새 페이지를 붙였어요. 누군가 옆에서 읽고 있으면 글씨가 다 엉망이 되죠.
2. **델타 레이크(Delta Lake)**는 마법의 '사서 선생님(장부)'이에요!
3. 책을 수정할 때 기존 책은 놔두고, 새 책을 몰래 만든 다음에 사서 선생님이 "오늘부터 1번 책 대신 저기 2번 책을 보세요!"라고 안내판(장부)만 딱 바꿔치기해서 아무도 헷갈리지 않게 해 준답니다!
