## 미리 알고가기

- Delta Lake는 객체 스토리지의 데이터 파일과 `_delta_log` 트랜잭션 로그로 테이블 상태를 관리함
- ACID는 트랜잭션의 원자성·일관성·격리성·지속성을 뜻함
- Add·Remove Action은 현재 스냅샷에 포함하거나 제외할 데이터 파일을 로그에 기록함
- Checkpoint는 누적된 로그 동작을 Parquet 형식으로 집약해 스냅샷 재구성 범위를 줄임
- 낙관적 동시성 제어는 데이터를 먼저 쓰고 커밋 시 현재 버전과 충돌을 검사함
- MERGE는 키 조건에 따라 기존 행의 수정과 새 행의 삽입을 한 문장으로 처리함
- VACUUM은 보존 기준이 지난 미참조 데이터 파일을 제거하므로 Time Travel 범위와 함께 설정해야 함

## 작성 근거(검토용)

- Delta Lake는 트랜잭션 로그·스냅샷·낙관적 커밋·MERGE·배치·스트림 통합을 핵심으로 선정함
- 비교표는 일반 Parquet 파일과 테이블 상태·쓰기·스키마·갱신·버전·적합 업무를 대비함
- 절차는 파일 선기록부터 로그 커밋과 Reader의 스냅샷 재구성까지 실제 버전 전이를 설명함
- 제목부터 결론까지 모든 문장·표 셀·요약을 5회 전수 검수해 로그와 데이터 파일 역할을 구분함

## Ⅰ. 개요

- **정의/개념**: Delta Lake는 객체 스토리지 파일과 순차 트랜잭션 로그로 ACID 커밋·스키마·버전·배치·스트림을 관리하는 오픈 테이블 포맷임
- **배경/필요성**: 파일 기반 레이크에서 동시 쓰기와 부분 적재를 통제하고 수정·삭제·이력 조회를 수행하기 위해 원자적 테이블 버전 관리가 필요함

## Ⅱ. 특징

- `_delta_log`가 파일 추가·제거·스키마·프로토콜·트랜잭션 정보를 버전별로 기록함
- Reader는 Checkpoint와 이후 로그를 재생해 선택한 버전의 유효 데이터 파일을 결정함
- Writer는 새 데이터 파일을 작성한 뒤 현재 버전과 충돌을 검사하고 다음 로그 버전을 원자적으로 생성함
- 스키마 검사·진화가 입력 열과 테이블 정의의 호환 범위를 통제함
- MERGE·UPDATE·DELETE와 Time Travel이 CDC 병합과 과거 버전 재현을 지원함

## Ⅲ. 종류 및 비교

| 판단 기준 | 일반 Parquet 파일 집합 | Delta Lake 테이블 |
|:---|:---|:---|
| 테이블 상태 | 디렉터리의 파일 목록을 직접 해석 | 트랜잭션 로그가 유효 파일 집합을 정의 |
| 쓰기 확정 | 파일 생성 완료 여부를 작업이 관리 | 새 로그 버전 생성으로 커밋 확정 |
| 스키마 통제 | Writer·Reader가 파일별 스키마 해석 | 테이블 스키마 검사와 진화 규칙 적용 |
| 행 변경 | 대상 파일을 응용이 찾아 재작성 | MERGE·UPDATE·DELETE로 변경 계획 실행 |
| 버전 조회 | 별도 백업·경로 관리 필요 | 로그 버전·시각으로 과거 스냅샷 조회 |
| 적합 업무 | 불변 배치 파일 교환·보관 | CDC 병합·동시 쓰기·배치·스트림 공유 |

> 요약: Delta Lake는 Parquet 파일 집합을 트랜잭션 로그 버전으로 관리해 원자적 변경과 과거 스냅샷 조회를 제공함.

## Ⅳ. 구성요소 및 구조

| 구성요소 | 설명 |
|:---|:---|
| Data File | Parquet 파일에 실제 테이블 행을 저장하며 커밋 전후에도 불변으로 유지함 |
| `_delta_log` | JSON 커밋 파일에 Add·Remove·Metadata·Protocol Action을 순서대로 기록함 |
| Checkpoint | 특정 버전까지 누적된 테이블 동작을 집약해 로그 재생량을 줄임 |
| Snapshot | 선택한 버전에서 유효한 파일·스키마·속성을 Reader에 제공함 |
| Optimistic Transaction | Writer의 기준 버전과 최신 변경을 비교해 충돌과 커밋을 판정함 |
| Maintenance | 파일 압축·통계 갱신·VACUUM으로 파일 수와 보존 범위를 관리함 |

```text
Writer -> Data Files -> _delta_log Commit -> Table Snapshot -> Reader
                         |
                     Checkpoint
```

> 요약: 새 데이터 파일은 `_delta_log` 커밋에 포함된 뒤 스냅샷의 유효 파일로 Reader에 공개됨.

## Ⅴ. 원리 및 절차 흐름도

```text
기준 버전 읽기 -> 새 파일 작성 -> 충돌 검사 -> 로그 버전 커밋 -> 스냅샷 재구성
```

1. **기준 버전 읽기**: Writer가 현재 스냅샷과 대상 파일·스키마를 확인함
2. **파일 작성**: 삽입·병합 결과를 새 데이터 파일로 객체 스토리지에 기록함
3. **충돌 검사**: 기준 버전 이후 커밋이 현재 작업의 읽기·쓰기 범위와 충돌하는지 판단함
4. **버전 커밋**: Add·Remove Action을 포함한 다음 로그 버전을 원자적으로 생성함
5. **스냅샷 재구성**: Reader가 Checkpoint와 로그로 새 버전의 유효 파일을 결정함

> 요약: Delta Writer는 새 파일을 먼저 작성하고 충돌 없는 로그 버전을 커밋해 테이블 스냅샷을 전환함.

## Ⅵ. 실무 사례

1. 주문 CDC 적재는 MERGE와 키 중복 검사를 적용하고 커밋 충돌·중복 주문 수를 확인함
2. 스트림 적재 테이블은 로그 커밋과 파일 압축 주기를 관리하고 적재 지연·평균 파일 크기를 확인함

## Ⅶ. 결론

- Delta Lake는 동시 쓰기 충돌·스키마 진화·행 변경 빈도·버전 보존과 파일 유지관리 조건으로 선택해야 함
