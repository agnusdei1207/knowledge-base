## Ⅰ. 개요
- **정의**: 인프라를 코드로 선언하여 프로비저닝을 자동화하는 IaC 도구임
- **배경/필요성**: 클라우드 자원이 수백 개로 늘어나면서 수작업 콘솔 관리는 재현성과 감사 추적이 불가능해짐
- **비유**: 요리 레시피(코드)를 한 번 작성하면 누가 만들어도 같은 요리(인프라)가 나오는 것과 유사함

| 출제 의도 | 반드시 짚을 핵심 | 감점 회피 포인트 |
|:---|:---|:---|
| IaC 도구 간 차이점 이해 | 선언형(HCL) vs 범용언어(TypeScript 등) | 둘 다 상태 파일 관리 필요성 언급 필요 |

> 요약: 인프라를 코드로 정의하여 일관된 환경 재현과 변경 이력 관리를 달성하는 도구임

## Ⅱ. 구성요소
```text
  Provider API
      ^
      |
+-----+------+
| State File  |
+-----+------+
      ^
      |
+-----+------+
| Engine/CLI  |
+-----+------+
      ^
      |
+-----+------+
| Code (HCL/  |
|  TypeScript) |
+-------------+
```

| 구성요소 | 설명 | 비유 |
|:---|:---|:---|
| 코드(정의 파일) | HCL 또는 범용 언어로 자원 상태를 선언함 | 설계 도면 |
| 상태 파일 | 현재 인프라 상태를 JSON으로 기록함 | 현장 대장 |
| 엔진/CLI | 코드와 상태 차이를 비교해 변경 계획을 생성함 | 시공 감독 |
| Provider | 클라우드 API를 호출해 실제 자원을 생성·변경함 | 전문 시공팀 |

> 요약: 코드-상태-엔진-Provider 4계층으로 선언과 실행을 분리함

## Ⅲ. 절차
```text
Init --> Plan --> Apply --> Destroy
```
- 1단계: Init — Provider 플러그인 다운로드 및 상태 백엔드 초기화
- 2단계: Plan — 코드와 상태 파일 차이를 비교해 변경 계획 산출
- 3단계: Apply — 변경 계획을 실제 클라우드 API에 적용
- 4단계: Destroy — 관리 대상 자원을 역순으로 삭제

> 요약: Init-Plan-Apply-Destroy 4단계로 인프라 생명주기를 관리함

## Ⅳ. 문제점
- 상태 파일 충돌: 다수 사용자가 동시에 Apply 시 상태 파일 불일치 발생 — 인프라 드리프트 유발
- Provider 종속: 멀티 클라우드 시 Provider별 리소스 정의가 달라 이식성 저하 — 코드 재작성 부담
- 학습 곡선 차이: Terraform은 HCL 별도 학습, Pulumi는 범용 언어 사용 — 팀 역량에 따라 도구 선택 제약

> 요약: 상태 관리, Provider 종속, 언어 학습 부담이 주요 과제임

## Ⅴ. 개선방안
1. 단기: 원격 상태 백엔드(S3+DynamoDB 잠금)로 동시 접근 충돌 방지
2. 중기: 추상화 모듈·Crossplane 등 멀티 클라우드 계층 도입으로 이식성 확보
3. 장기: Policy-as-Code(OPA, Sentinel) 적용으로 거버넌스 자동화 및 팀 표준화

> 요약: 원격 상태 관리 → 멀티 클라우드 추상화 → 정책 자동화 순으로 성숙도 향상

## Ⅵ. 전망
- 발전 방향: GitOps 파이프라인과 통합되어 PR 기반 인프라 변경 승인 체계로 수렴
- 기술사적 판단: IaC는 DevOps 성숙도 평가의 기본 척도로 자리잡음
- 기술사 제언: 조직 언어 역량과 클라우드 전략에 맞춰 도구를 선정하고, 상태 관리 정책을 우선 수립할 것을 권고함
