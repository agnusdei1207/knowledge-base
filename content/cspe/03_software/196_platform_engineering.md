## Ⅰ. 개요
- **정의**: 개발자가 셀프서비스로 인프라·도구를 활용할 수 있도록 내부 플랫폼을 설계·구축·운영하는 엔지니어링 분야
- **배경/필요성**: DevOps 확산으로 개발팀의 인프라 자율성이 높아졌으나, 도구 파편화와 인지 부하가 증가하여 표준화된 추상 계층이 필요함
- **비유**: 각 세입자가 직접 배관·전기를 시공하는 대신, 건물 관리소가 표준 인프라를 제공하는 구조

| 출제 의도 | 반드시 짚을 핵심 | 감점 회피 포인트 |
|:---|:---|:---|
| DevOps 진화 방향 이해 | 셀프서비스·Golden Path·IDP(197 참조) | DevOps 대체가 아닌 보완 관계 명시 필요 |

> 요약: 개발자 경험(DX) 최적화를 위해 표준화된 셀프서비스 플랫폼을 구축·운영하는 분야임

## Ⅱ. 구성요소
```text
Developer
    |
    v
+------------------+
| Self-Service     |
| Portal / CLI     |
+--------+---------+
         |
+--------v---------+
| Internal Dev     |
| Platform (IDP)   |
+--------+---------+
         |
    +----+----+
    |         |
    v         v
Infra API   CI/CD
(K8s/Cloud) Pipeline
```

| 구성요소 | 설명 | 비유 |
|:---|:---|:---|
| Self-Service Portal | 개발자가 환경·파이프라인을 직접 요청·생성하는 UI/CLI 인터페이스 | 건물 관리소 접수 창구 |
| Golden Path | 조직이 검증한 표준 기술 스택·워크플로 템플릿 | 권장 등산 코스 |
| Platform Team | IDP를 제품으로 취급하여 설계·운영·개선하는 전담 조직 | 건물 관리소 팀 |

> 요약: 플랫폼 팀이 Golden Path와 셀프서비스 포털을 통해 개발자에게 표준 인프라를 제공함

## Ⅲ. 절차
```text
니즈 파악 --> 플랫폼 설계 --> MVP 제공 --> 피드백 반복
```
- 1단계: 개발팀 인터뷰·관찰을 통해 반복 업무·병목 지점 파악
- 2단계: Golden Path·API 추상 계층·CI/CD 템플릿 등 플랫폼 핵심 기능 설계
- 3단계: MVP(Minimum Viable Platform)를 파일럿 팀에 제공하여 실사용 검증
- 4단계: 사용자 피드백 수집 후 기능 개선·확장을 반복하며 내부 제품으로 성숙

> 요약: 니즈 파악-설계-MVP-피드백 루프의 제품 관리 방식으로 플랫폼을 점진 발전시킴

## Ⅳ. 문제점
- 과잉 추상화: 지나친 표준화가 개발팀의 특수 요구를 수용하지 못해 우회 경로 발생
- 채택률 저조: 강제 없이 제공 시 기존 도구 관성으로 신규 플랫폼 이용률 미달
- 플랫폼 팀 병목: 소수 플랫폼 팀에 요구가 집중되어 응답 지연 발생

> 요약: 과잉 추상화·채택률·팀 병목이 플랫폼 엔지니어링의 주요 리스크임

## Ⅴ. 개선방안
1. 단기: 확장 가능한 플러그인·오버라이드 메커니즘으로 특수 요구 수용
2. 중기: 개발자 만족도(DX) 지표 기반 가치 입증으로 자발적 채택 유도
3. 장기: API 기반 자동화·IaC 템플릿 확충으로 플랫폼 팀 개입 최소화

> 요약: 유연성 확보-가치 입증-자동화 순으로 플랫폼의 실효성과 확장성을 높이는 방향임

## Ⅵ. 전망
- 발전 방향: IDP(197 참조) 제품군과 결합하여 조직 표준 개발 환경으로 정착 가속
- 기술사적 판단: DevOps 성숙도가 높은 조직에서 다음 단계 생산성 향상의 핵심 전략
- 기술사 제언: 플랫폼을 내부 제품으로 관리하는 조직 문화·거버넌스 설계가 선행 과제임
