# 📖 【암기용】 개념 완전 이해

> 목적: 모놀리식과 마이크로서비스 비교를 처음 보는 사람도 완벽히 이해하게 만든다. 시험 답안 양식이 아니라, 이해를 위한 친절한 설명이다.

## 한눈에
- **개요**: 하나의 배포 단위로 묶는 모놀리식과 독립 서비스로 나누는 마이크로서비스의 구조 비교
- **왜 필요한가**: 서비스가 커지면 배포 충돌, 장애 전파, 데이터 소유권 문제가 생긴다. 반대로 너무 일찍 나누면 네트워크, 관측성, 데이터 정합성 운영 비용이 급증한다.
- **핵심 직관**: 모놀리식은 한 건물에 모든 부서가 있는 구조이고, 마이크로서비스는 부서별 건물이 API와 이벤트로 협업하는 구조이다.

## 깊이 이해
- **배경·문제의식**: 초기 제품은 빠른 기능 검증이 필요해 모놀리식이 유리하지만, 팀과 도메인이 늘면 단일 배포와 공유 DB가 병목이 된다.
- **작동 원리**: 모놀리식은 단일 코드베이스와 DB에서 트랜잭션 일관성을 얻고, MSA는 서비스별 코드·DB·배포 단위를 나눠 독립 변경을 얻는다.
- **비유**: 작은 식당은 한 주방에서 모든 메뉴를 처리하지만, 대형 푸드코트는 메뉴별 매장이 독립 운영되고 주문 시스템으로 연결된다.
- **구체 예시**: 팀 2개, 월 배포 2회, 공유 DB 1개면 모놀리식 유지가 타당하다. 팀 8개, 일 배포 20회, 도메인별 데이터 소유권이 분리되면 MSA 전환 후보이다.
- **흔한 오해·주의점**: MSA가 항상 더 나은 구조가 아니다. 분산 시스템 운영 역량 없이 전환하면 장애 추적과 배포 복잡도가 증가한다.

## 연결 개념
- DDD 바운디드 컨텍스트: 서비스 분해 기준
- API Gateway·Service Mesh: MSA 통신과 정책 통제
- Saga·Outbox: 서비스 간 데이터 정합성 처리

# 📝 【답안용】 시험 답안 템플릿

> 목적: 시험장에서 25분에 그대로 쓰는 답안 양식. 작성방식(추상표현 금지·수치·도식·문제유형 전환)을 엄격히 지킨다.
> 핵심: 구조 비교를 넘어 팀 규모, 배포 빈도, DB 소유권, 운영 역량 기준으로 선택한다.

## 핵심 인사이트 (3줄 요약)

> 1. **본질**: 모놀리식은 단일 배포 단위, 마이크로서비스는 도메인별 독립 배포·데이터 소유권을 갖는 분산 구조이다.
> 2. **가치**: MSA는 팀별 배포 독립성과 장애 격리를 제공하지만, 네트워크 지연, 관측성, 데이터 정합성 비용이 증가한다.
> 3. **판단 포인트**: 팀 5개 이상, 배포 충돌 빈번, 도메인별 데이터 소유권 필요 시 MSA를 검토하고 초기 제품은 모듈형 모놀리식이 우선이다.

## 출제 의도 및 답안 포인트

| 출제 의도 | 반드시 짚을 핵심 | 감점 회피 포인트 |
|:---|:---|:---|
| 아키텍처 선택 기준 확인 | 배포 단위, DB, 결합도, 운영 복잡도 | MSA를 무조건 우위로 서술 |
| 전환 전략 판단 확인 | Strangler Fig, 모듈형 모놀리식, DDD 경계 | Big Bang 전환만 제시 |
| 운영 리스크 인식 확인 | 관측성, 장애 전파, Saga, API 계약 | 분산 트랜잭션 문제 누락 |
> 요약: 출제자는 구조 장단점보다 조건별 선택과 단계적 전환 전략을 본다.

## Ⅰ. 개요 및 필요성

- 개요: 배포 단위별 아키텍처 비교
- 배경: 서비스 성장에 따라 단일 배포 충돌, 공유 DB 병목, 장애 영향 범위 문제가 나타나지만, 과도한 서비스 분해는 네트워크 지연과 운영 복잡도를 키움.
- 필요성: 제품 단계, 팀 규모, 변경 빈도, 배포 주기, SRE·관측성 성숙도 기준으로 Monolith와 Microservice 전환 시점을 판단해야 함.

---

## Ⅱ. 구조 및 구성요소

```text
Monolith -> UI / Business / Data Access -> Single DB -> Single Deploy
Microservice -> API Gateway -> Service A / Service B / Service C
Service A -> DB A
Service B -> DB B
Service C -> DB C -> Event Bus -> Observability
```

| 구성요소 | 모놀리식 | 마이크로서비스 |
|:---|:---|:---|
| 배포 단위 | 애플리케이션 1개 | 서비스별 독립 배포 |
| 데이터 | 공유 DB, 단일 트랜잭션 | DB per Service, 최종 일관성 |
| 통신 | 프로세스 내부 호출 | REST, gRPC, Message |
| 운영 | 단순 배포·관측 | 분산 추적·서비스 메시 필요 |
| 팀 | 소규모 단일 팀 | 도메인별 자율 팀 |
> 요약: 핵심 차이는 코드 구조가 아니라 배포 단위, 데이터 소유권, 통신 방식이다.

---

## Ⅲ. 동작원리 및 흐름도

```text
요구 변경 -> 도메인 영향 분석
모놀리식 -> 단일 코드 수정 -> 통합 테스트 -> 전체 배포
MSA -> 서비스 경계 확인 -> 계약 테스트 -> 서비스별 배포
서비스 간 변경 -> API / Event 계약 조정
운영 -> Trace / Metric / Log로 영향 추적
```

| 단계 | 처리 내용 | 검증 기준 |
|:---:|:---|:---|
| 1 | 요구 변경의 도메인 경계 식별 | Bounded Context 매핑 |
| 2 | 배포 단위와 데이터 소유권 확인 | 공유 DB 접근 수 |
| 3 | 통신 방식과 계약 설계 | API Schema, Event Schema |
| 4 | 테스트와 배포 파이프라인 구성 | 서비스별 CI 10분 이하 |
| 5 | 관측성과 장애 대응 구성 | Trace coverage 90% 이상 |
> 요약: MSA는 서비스 분리보다 계약 테스트와 관측성 운영 흐름이 핵심이다.

---

## Ⅳ. 특징

| 구분 | 모놀리식 | 마이크로서비스 | 수치·판단 포인트 |
|:---|:---|:---|:---|
| 개발 초기 | 단일 코드로 기능 검증 | 서비스 분리 비용 발생 | 팀 1~3개면 모놀리식 |
| 배포 | 전체 배포 | 서비스별 배포 | 일 배포 10회 이상이면 MSA 검토 |
| 트랜잭션 | ACID 처리 수월 | Saga·Outbox 필요 | 정합성 지연 p95 1초 이하 |
| 장애 | 프로세스 전체 영향 | 서비스 격리 가능 | Circuit Breaker 필요 |
| 운영 | 로그 1곳 | 분산 로그·트레이스 | Trace ID 전파율 90% 이상 |
> 요약: 모놀리식은 단순성과 트랜잭션에, MSA는 독립 배포와 장애 격리에 강점이 있다.

## Ⅴ. 심화 비교 및 적용 판단

| 비교 축 | 모놀리식 | 마이크로서비스 | 선택 기준 |
|:---|:---|:---|:---|
| 제품 단계 | MVP, 초기 성장 | 대규모 운영 | 사용자 검증 전 분리 보류 |
| 팀 규모 | 1~3개 팀 | 5개 이상 도메인 팀 | 팀 간 배포 충돌 빈도 |
| 데이터 | 단일 트랜잭션 요구 | 도메인별 DB 소유 | 공유 테이블 변경 충돌 |
| 운영 역량 | 기본 CI/CD | SRE, 관측성, 자동 복구 | 온콜·대시보드 운영 여부 |
> 요약: MSA는 팀과 운영 체계가 준비된 뒤 도메인 경계 기준으로 단계 전환해야 한다.

| 리스크 | 원인 | 대응 방안 | 확인 지표 |
|:---|:---|:---|:---|
| 분산 장애 추적 | 서비스 간 호출 다단계 | OpenTelemetry Trace ID 전파 | Trace coverage |
| 데이터 불일치 | DB per Service와 이벤트 지연 | Saga, Outbox, 재처리 | 미처리 이벤트 수 |
| 서비스 과분할 | 경계 검증 전 분리 | 모듈형 모놀리식 선행 | 서비스당 코드량, 호출 수 |
| 배포 실패 | 계약 불일치 | Consumer Driven Contract Test | 계약 테스트 통과율 |
> 요약: MSA 리스크는 관측성, 정합성, 과분할, 계약 불일치이며 자동 검증으로 통제한다.

| 점검 항목 | 목표 기준 | 측정 방법 |
|:---|:---|:---|
| 배포 독립성 | 서비스별 독립 배포 90% 이상 | 배포 이력 분석 |
| 장애 격리 | 단일 서비스 장애 영향 1개 도메인 이내 | 장애 리포트 |
| 정합성 | 이벤트 처리 성공률 99.9% | 브로커 메트릭 |
| 운영 품질 | MTTR 30분 이하, Trace coverage 90% 이상 | APM, 온콜 기록 |
> 요약: 전환 효과는 배포 독립성, 장애 격리, 정합성, MTTR로 측정한다.

## Ⅵ. 실무 적용 및 결론

**적용 방안 3개:**
1. 초기 시스템은 모듈형 모놀리식으로 시작하고 패키지 순환 의존 0건, 모듈별 테스트를 먼저 확보한다.
2. 배포 충돌과 공유 DB 변경 충돌이 반복되는 도메인은 Strangler Fig 방식으로 API Gateway 뒤에서 단계 분리한다.
3. MSA 전환 전 OpenTelemetry, API 계약 테스트, Saga·Outbox, 서비스별 CI/CD를 구축한다.

**결론 (2줄):**
- 기술사 판단: 팀 3개 이하와 단일 트랜잭션 중심이면 모놀리식, 팀 5개 이상과 독립 배포 요구가 있으면 MSA가 타당함
- 향후 방향: 모듈형 모놀리식에서 검증된 도메인 경계를 점진적으로 MSA로 분리하는 전환 방식이 확산됨
