## 미리 알고가기

- 모놀리식(Monolithic Architecture): 단일 코드베이스에서 모든 비즈니스 기능을 빌드하고 하나의 아티팩트로 통합 배포하는 아키텍처 구조임
- 마이크로서비스(Microservices Architecture, MSA): 시스템을 독립적으로 배포 및 확장이 가능한 작고 느슨하게 결합된 서비스들의 집합으로 설계하는 방식임
- 바운디드 컨텍스트(Bounded Context): 도메인 주도 설계(DDD)에서 특정 비즈니스 모델이 정의되고 적용되는 논리적인 경계 영역임
- Saga 패턴(Saga Pattern): 분산 데이터베이스 환경에서 데이터의 일관성을 유지하기 위해 여러 마이크로서비스 간에 로컬 트랜잭션을 연속적으로 실행하고 실패 시 보상 트랜잭션을 수행하는 패턴임
- Strangler Fig 패턴(Strangler Fig Pattern): 기존 모놀리식 시스템의 기능을 점진적으로 교체하여 마이크로서비스로 전환하는 마이그레이션 전략임

## 작성 근거(검토용)

- 모놀리식과 마이크로서비스의 실질적인 트레이드오프를 도출하기 위해 배포 및 빌드 경계, 데이터 관리 방식, 장애 격리 및 확장을 3대 비교축으로 정의함
- Ⅴ절(원리 및 절차 흐름도)이 기존 문서에서 누락되었으므로, 실무에서 널리 쓰이는 모놀리식의 마이크로서비스 전환 절차를 단계별 흐름과 함께 보강함
- 제목부터 결론까지 5회 이상 검수를 수행하여 복잡한 조사와 장황하게 기술된 부분을 답안용 문체로 정밀화하고 Zola 사이트 빌드를 완료함

## Ⅰ. 개요

- **정의/개념**: 모놀리식은 단일 실행 단위 내에 모든 애플리케이션 기능을 포함하는 구조이며, 마이크로서비스는 도메인 영역별로 서비스를 느슨하게 분격하여 독립 배포 가능한 구조임
- **배경/필요성**: 비즈니스 규모 확대에 따른 개발 병목을 해소하고 대형 시스템의 릴리스 유연성을 극대화하기 위해 각 비즈니스 특성에 적합한 아키텍처 선택 기준이 필요함

### 쉽게 이해하기 (학습용)
- 하나의 큰 건물 안에 주방, 침실, 화장실이 모두 들어있는 단독주택(모놀리식)과 필요에 따라 여러 채의 독립된 건물을 지어 길로 연결한 마을(마이크로서비스)의 차이임

## Ⅱ. 특징

- 모놀리식은 초기 개발 속도가 빠르고 단일 런타임 내 호출이 일어나 네트워크 지연이 없으며 트랜잭션 관리가 단순함
- 마이크로서비스는 서비스별로 최적의 기술 스택(Polyglot)을 채택할 수 있고 개별 배포가 가능하여 개발 생산성을 향상시킴
- 모놀리식은 시스템 규모가 확장될수록 빌드 및 배포 시간이 급증하고 특정 기능의 오류가 전체 시스템 장애로 전파됨
- 마이크로서비스는 분산 데이터 일관성을 유지하기 어렵고 네트워크 간 호출 지연이 발생하며 모니터링 복잡도가 매우 증가함

### 쉽게 이해하기 (학습용)
- 집 안의 전기가 합선되면 집 전체가 정전되지만 이동이 쉬운 것과, 건물이 분리되어 한 건물의 화재가 번지진 않으나 건물 간 이동 시 시간이 걸리는 특징과 같음

## Ⅲ. 종류 및 비교

| 판단 기준 | 모놀리식 | 마이크로서비스 |
|:---|:---|:---|
| 배포 및 빌드 경계 | 전체 기능이 하나의 아티팩트로 통합되어 단일 빌드로 배포됨 | 각 서비스가 독립적인 코드 저장소와 빌드 배포 파이프라인을 보유함 |
| 데이터 관리 방식 | 단일 RDBMS 저장소를 공유하며 데이터 무결성과 강한 트랜잭션 결합을 지원함 | 서비스별 독립 저장소(Database per Service)를 사용하며 분산 일관성이 필요함 |
| 장애 전파 및 확장 | 한 기능의 메모리 누수 등이 전체 프로세스 다운을 유발하며 수평 확장은 전체만 가능함 | 서비스 간 결합도가 낮아 장애가 격리되며 트래픽이 몰리는 특정 서비스만 표적 확장함 |

> 요약: 개발 복잡도가 낮고 강력한 데이터 정합성이 필요하면 모놀리식, 대형 조직의 빠른 배포와 개별 확장이 중시되면 마이크로서비스가 유리함.

### 쉽게 이해하기 (학습용)
- 단일 기계로 모든 공정을 수행하여 관리가 쉬우나 고장 시 전면 중단되는 방식과, 조립 라인을 여러 기계로 나누어 유지보수가 용이하나 기계 간 협업 조율이 필요한 방식의 비교임

## Ⅳ. 설계 요소 및 구조

```text
[ 모놀리식 구조 ]                      [ 마이크로서비스 구조 ]
+----------------------+              +----------------------------+
|      API Gateway     |              |         API Gateway        |
+----------------------+              +----------------------------+
| UI | Biz A | Biz B   |                 ↓                      ↓
+----------------------+              +-----------+          +-----------+
|      Shared DB       |              | Service A |          | Service B |
+----------------------+              +-----------+          +-----------+
                                         ↓                      ↓
                                      +-----------+          +-----------+
                                      |   DB A    |          |   DB B    |
                                      +-----------+          +-----------+
```

| 설계 요소 | 설명 |
|:---|:---|
| API 게이트웨이 | 클라이언트의 요청 관문으로서 라우팅, 인증, 보안 필터링을 통합 처리하는 중계 계층임 |
| 비즈니스 경계(Context) | 모놀리식은 프로세스 내 논리 모듈로 구분하며 마이크로서비스는 네트워크 인터페이스를 둔 가상화 프로세스로 격리함 |
| 서비스 데이터베이스 | 마이크로서비스의 느슨한 결합을 구현하기 위해 각 서비스가 전용 DB를 소유하여 데이터 결합도를 차단함 |
| 분산 관측 계층 | 서비스 간 복잡한 API 호출 경로를 추적하기 위해 분산 트레이싱 및 통합 로그 수집기 등으로 구성된 모니터링 환경임 |

> 요약: 모놀리식은 단일 서버 및 DB 구조로 성능을 최적화하고, 마이크로서비스는 API 게이트웨이와 개별 DB를 배치해 배포와 장애 경계를 완전히 격리함.

### 쉽게 이해하기 (학습용)
- 한 서류 캐비닛(단일 DB)에 모든 부서 문서를 꽂아두고 함께 쓰는 것과, 각 부서 금고(개별 DB)를 따로 두고 정보 공유 시 전자메일(API Gateway)을 이용하는 구조의 대비임

## Ⅴ. 원리 및 절차 흐름도

```text
[1. 도메인 경계 정의] -> [2. API 라우팅 통합] -> [3. 점진적 모듈 분격] -> [4. 데이터 이관/조정] -> [5. 모놀리식 제거]
```

1. **도메인 분석 및 Bounded Context 정의**: 이벤트 스토밍 등의 기법을 통해 비즈니스 경계를 식별하고 서비스 후보군을 결정함
2. **API 게이트웨이 배치**: 서비스 전면에 라우팅 규칙을 수행할 관문을 도입하여 신규 및 기존 기능으로의 요청 경로를 단일화함
3. **점진적 서비스 추출 (Strangler 패턴)**: 모놀리식 내부의 핵심도가 낮고 의존성이 적은 모듈부터 독립된 마이크로서비스 코드로 재구현해 배포함
4. **데이터 분리 및 일관성 연동**: 공유 DB에서 추출된 서비스의 전용 테이블을 분리 이관하고, Saga 패턴을 설계해 트랜잭션을 연동함
5. **구 모듈 제거 및 라우팅 전환**: 기존 모놀리식 모듈로 가는 요청을 마이크로서비스로 전량 전환하고 모놀리식 내 구 코드를 안전하게 삭제함

> 요약: 비즈니스 경계를 식별한 후 API 게이트웨이를 통해 요청을 통제하고, Strangler 패턴을 적용해 핵심 모듈부터 점진적으로 분리하여 무장애 마이그레이션을 완수함.

### 쉽게 이해하기 (학습용)
- 오래된 건물을 허물고 새 아파트를 지을 때 주민들을 한 번에 이주시키지 않고, 동 단위로 하나씩 완공해가며 점진적으로 사람들을 이사시키는 절차와 같음

## Ⅵ. 실무 사례

- 실무에서는 대규모 전자상거래 플랫폼 구축 시 트래픽 변동이 극심한 '상품 조회'와 '결제 서비스'의 DB와 런타임을 완전히 분리하여 마이크로서비스 아키텍처로 독립 설계함
- 트래픽 분산과 빠른 기능 릴리스를 위해 기존 모놀리식 금융 원장을 마이크로서비스로 전환하는 과정에서 Strangler Fig 패턴과 Saga 분산 트랜잭션 관리 도구를 사용해 신구 시스템을 무장애 이관함

### 쉽게 이해하기 (학습용)
- 쇼핑몰에서 결제 시스템 장애가 나도 상품을 구경하는 첫 페이지는 계속 열리도록 만들거나, 기존 금융 전산망을 멈추지 않고 단계적으로 새 전산망으로 바꾸는 사례임

## Ⅶ. 결론

- 마이크로서비스는 독립 배포 및 확장의 가치를 제공하지만 분산 복잡성과 운영 오버헤드가 크므로, 시스템 복잡도가 기준 임계치를 초과할 때 전환을 결정함
- 시스템 생애 초기에는 모듈 경계가 명확한 '모듈러 모놀리식'으로 구현하여 도메인 이해도를 높인 뒤 트래픽 규모에 따라 단계적으로 MSA로 분리해 나가는 진화적 설계 전략이 바람직함

### 쉽게 이해하기 (학습용)
- 처음 사업을 시작할 때는 한 사무실에 모여 일(모놀리식)하다가, 회사가 성장하고 분야가 세분화되면 지사를 세워 독립적으로 일하게 하는 것이 성장에 유리함
