## Ⅰ. 개요
- **정의**: 모놀리식은 단일 배포 단위로 구성된 아키텍처이고, MSA는 독립 배포 가능한 소규모 서비스들의 조합 아키텍처
- **배경/필요성**: 시스템 규모 확대 시 모놀리식의 빌드·배포·장애 전파 문제가 심화되므로, 서비스 분리를 통한 독립 배포·확장이 필요
- **비유**: 하나의 대형 공장(모놀리식) vs 전문 공방들의 협업 네트워크(MSA)와 유사함

| 출제 의도 | 반드시 짚을 핵심 | 감점 회피 포인트 |
|:---|:---|:---|
| 두 아키텍처의 트레이드오프 비교 | 독립 배포, 데이터 분리, 운영 복잡도 | MSA가 무조건 우월하다는 식의 편향 서술 금지 |

> 요약: 단일 배포(모놀리식)와 서비스별 독립 배포(MSA)의 트레이드오프를 비교하는 주제임

## Ⅱ. 구성요소
```text
Monolith                    MSA
+--------------+        +-----+ +-----+ +-----+
| UI + Logic   |        |Svc A| |Svc B| |Svc C|
| + Data       |        +--+--+ +--+--+ +--+--+
| (Single DB)  |           |       |       |
+--------------+        +--v--+ +--v--+ +--v--+
                        |DB A | |DB B | |DB C |
                        +-----+ +-----+ +-----+
```

| 구성요소 | 설명 | 비유 |
|:---|:---|:---|
| 모놀리식 | UI·로직·데이터가 단일 프로세스에 통합, 단일 DB 사용 | 원룸(모든 기능이 한 공간) |
| MSA 서비스 | 바운디드 컨텍스트(054 참조) 단위로 분리된 독립 배포 단위 | 전문 공방 |
| API Gateway | MSA 진입점으로 라우팅·인증·로드밸런싱 수행 | 종합 안내 데스크 |
| Service Mesh | 서비스 간 통신·보안·관측을 사이드카 프록시로 처리하는 인프라 계층 | 공방 간 물류 네트워크 |

> 요약: 모놀리식은 단일 통합 구조, MSA는 독립 서비스+API Gateway+Service Mesh로 구성됨

## Ⅲ. 절차
```text
현황분석 --> 서비스경계식별 --> 점진적분리(Strangler) --> 독립배포/운영
```
- 1단계: 기존 모놀리식 시스템의 모듈 간 결합도와 변경 빈도를 분석함
- 2단계: 이벤트 스토밍(055 참조) 등으로 서비스 경계를 바운디드 컨텍스트 기준 식별함
- 3단계: Strangler Fig 패턴으로 기존 모듈을 점진적으로 MSA 서비스로 분리함
- 4단계: CI/CD 파이프라인(059 참조) 구축 후 서비스별 독립 배포·모니터링 체계를 운영함

> 요약: 현황 분석에서 점진 분리를 거쳐 독립 배포 체계로 전환함

## Ⅳ. 문제점
- 분산 복잡도: 서비스 간 네트워크 호출 증가 — 장애 전파·지연 누적 위험
- 데이터 일관성: DB 분리로 분산 트랜잭션 필요 — Saga 패턴 등 보상 로직 복잡도 증가
- 운영 부담: 서비스 수 증가에 비례한 모니터링·로깅·배포 파이프라인 관리 필요

> 요약: 분산 복잡도, 데이터 일관성, 운영 부담이 MSA 전환의 주요 문제임

## Ⅴ. 개선방안
1. 단기: Circuit Breaker·Retry 패턴 적용으로 분산 장애 전파 차단
2. 중기: 이벤트 기반 Saga 패턴 도입으로 분산 트랜잭션 보상 로직 표준화
3. 장기: Service Mesh·통합 관측 플랫폼 도입으로 운영 가시성 확보

> 요약: Circuit Breaker, Saga 패턴, Service Mesh로 단계적 개선함

## Ⅵ. 전망
- 발전 방향: 모듈러 모놀리식(Modular Monolith)이 MSA 전 단계 전략으로 부상 중임
- 기술사적 판단: 조직 규모·도메인 복잡도에 따라 아키텍처를 선택하는 의사결정 역량이 핵심임
- 기술사 제언: MSA 전환 전 모듈러 모놀리식으로 경계를 검증한 후 점진 전환 필요
