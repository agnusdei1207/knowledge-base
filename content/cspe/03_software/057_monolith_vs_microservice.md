# 📖 【암기용】 개념 완전 이해

> 목적: 이 개념을 처음 보는 사람도 완벽히 이해하게 만든다. 시험 답안 양식이 아니라, 이해를 위한 친절한 설명이다.

## 한눈에
- **개요**: 모놀리식과 마이크로서비스(MSA)는 애플리케이션을 몇 개의 **배포 단위**로 쪼개고, 어디까지를 하나의 **DB 트랜잭션 경계**로 묶을지에 대한 두 가지 대조적인 **서버 아키텍처 스타일**이다. 모놀리식은 모든 기능을 하나의 프로세스·DB로 묶고, MSA는 기능마다 독립된 프로세스·DB로 쪼개 네트워크(API)로 통신한다.
- **왜 비교하는가**: 클라우드 시대에 "무조건 MSA가 우월하다"는 오해가 퍼졌지만, MSA는 네트워크 통신 지연과 데이터 분산이라는 새로운 비용을 발생시킨다. 조직 규모와 트래픽 특성에 맞춰 어느 쪽을 택할지 판단하는 것이 핵심이다.
- **핵심 직관**: 원룸(모놀리식) vs 여러 채의 단독주택(MSA). 원룸은 방 이동이 즉시(0초)지만 한 방에서 불이 나면 전체가 탄다. 단독주택은 한 집에 불이 나도 옆집은 안전하지만, 이웃집에 가려면 문을 나서서 걸어가야(네트워크 이동) 한다.

## 핵심 용어 정리 (내부에 등장하는 것들)

| 용어 | 의미 | 비유 |
|:---|:---|:---|
| 모놀리식(Monolithic) | 모든 기능이 하나의 프로세스·아카이브(WAR/JAR)로 배포되는 구조 | 모든 방이 하나로 붙은 원룸 |
| 마이크로서비스(MSA) | 기능별로 독립된 프로세스·DB를 가지고 API로 통신하는 분산 구조 | 담장으로 나뉜 여러 채의 단독주택 |
| 단일장애점(SPOF) | 한 부분의 장애가 시스템 전체를 멈추게 하는 지점 — 모놀리식의 대표 약점 | 두꺼비집 하나가 나가면 집 전체가 정전 |
| 장애 격리(Fault Tolerance/Isolation) | 한 서비스의 장애가 다른 서비스로 번지지 않는 성질 — MSA의 대표 장점 | 옆집 정전이 우리 집엔 영향 없음 |
| Scale-out / Scale-up | 서버를 여러 대로 늘리는 것(out) vs 한 대의 성능을 높이는 것(up) | 가게를 여러 곳에 내기(out) vs 가게를 크게 넓히기(up) |
| DB-per-service | 서비스마다 자기 전용 DB를 따로 갖는 MSA의 원칙 | 집마다 자기 냉장고를 따로 두기 |
| 분산 트랜잭션 / Saga 패턴 | 여러 서비스에 걸친 작업을 하나의 트랜잭션처럼 묶을 수 없어, 실패 시 보상 동작으로 되돌리는 방식 | 여러 가게에서 나눠 산 물건 중 하나가 품절이면 나머지도 환불 처리 |
| 결과적 일관성(Eventual Consistency) | 지금 당장은 데이터가 서로 달라도, 이벤트 전파 후 시간이 지나면 맞춰지는 일관성 모델 | 문자로 소식 전하기 — 상대가 읽기 전까지는 서로 다른 정보 상태 |
| 분산 모놀리식(Distributed Monolith) | 서버는 여러 개로 쪼갰지만 DB는 여전히 하나를 공유해, MSA와 모놀리식의 단점을 동시에 갖는 최악의 혼종 | 집은 나눴는데 화장실은 공용으로 남겨둔 상태 |
| 모듈러 모놀리식(Modular Monolithic) | 배포는 하나(모놀리식)로 하되, 내부 코드는 모듈 경계를 엄격히 지켜 나중에 쉽게 MSA로 분리할 수 있게 설계하는 절충안 | 한 건물 안에서 부서별로 출입증이 다른 사무실 구획 |

## 깊이 이해

### 배경 — 서버가 비싸던 시절과 트래픽 폭증 시대
- 서버가 비쌌던 시절에는 코드 전체를 압축해 물리 서버 한 대에 올리는 모놀리식이 합리적이었다. 그러나 트래픽이 폭증하는 서비스에서는 장바구니 기능 하나의 결함(메모리 누수 등)이 결제·배송 로직까지 함께 물고 들어가 앱 전체가 멈추는 문제가 반복됐다. 이 문제를 해결하려고 기능 단위로 프로세스를 쪼개는 MSA가 등장했다.

### 4대 비교축을 수치로 이해하기
- **배포**: 모놀리식은 코드 1줄만 고쳐도 전체(예: 100만 줄)를 다시 빌드·재기동해야 해 배포에 수십 분이 걸릴 수 있다. MSA는 장바구니 서비스(예: 5천 줄)만 재배포하면 되어 배포 시간이 수 분 이내로 줄어든다.
- **확장(Scaling)**: 결제 트래픽만 10배 증가했다고 하자. 모놀리식은 결제와 무관한 배송·알림 로직까지 포함된 무거운 프로세스 전체를 10대로 복제해야 한다. MSA는 결제 서비스만 골라 10대로 늘리면 되므로, 같은 트래픽을 처리하는 데 필요한 서버 자원이 훨씬 적다.
- **통신 지연(Latency)**: 모놀리식 내부의 함수 호출은 같은 메모리 안에서 이뤄져 마이크로초(약 0.000001~0.0001초) 단위로 끝난다. MSA는 다른 프로세스를 네트워크(HTTP)로 호출해야 하므로 같은 데이터센터 안에서도 최소 수 ms, 왕복 처리까지 포함하면 0.01~0.05초 수준이 걸린다 — 대략 수백 배 느리다. 서비스 호출이 5단계로 이어지면(A→B→C→D→E) 지연이 누적돼 전체 응답 시간이 눈에 띄게 늘어난다.
- **데이터**: 모놀리식은 DB가 하나라 SQL `JOIN` 한 번으로 여러 테이블 데이터를 즉시 묶어 볼 수 있다(강한 일관성). MSA는 서비스마다 DB가 나뉘어 있어(DB-per-service), 다른 서비스의 데이터가 필요하면 API를 호출해 각자 받아온 뒤 애플리케이션 레벨에서 조립해야 하고, 여러 서비스에 걸친 갱신은 Saga 패턴 같은 별도 장치로 결과적 일관성을 맞춰야 한다.

### 판별 원리 — 언제 모놀리식, 언제 MSA인가
- 판단 기준은 "조직 규모"와 "기능별 트래픽 편차"다. 개발 인원이 적고(예: 10명 내외) 아직 어떤 기능이 핵심인지 검증 중인 초기 단계라면, 배포·운영이 단순한 모놀리식이 유리하다. 반대로 개발자가 수백 명 규모이고 특정 기능(예: 결제)의 트래픽만 유독 튀는 상황이라면, 그 부분만 독립적으로 확장할 수 있는 MSA가 유리하다.
- 안티패턴은 "서버만 쪼개고 DB는 그대로 공유"하는 분산 모놀리식이다. 이 경우 한 서비스가 공유 테이블 스키마를 바꾸면 나머지 서비스가 줄줄이 깨지는데, 네트워크 통신 비용은 그대로 떠안는 최악의 조합이 된다. 그래서 MSA로 갈 거라면 반드시 DB도 함께 분리해야 한다.

### 절충안 — 모듈러 모놀리식으로의 회귀
- 최근 일부 빅테크(예: 아마존 프라임 비디오 팀)는 과도하게 쪼갰던 MSA를 모놀리식으로 재통합해 인프라 비용을 크게 절감한 사례를 발표했다. 트래픽 분산이 굳이 필요 없는 내부 처리(영상 인코딩 등)까지 네트워크 호출로 쪼갠 과잉 설계였기 때문이다.
- 그래서 나온 절충안이 모듈러 모놀리식이다. 배포는 하나의 프로세스로 묶어 네트워크 지연 없이 빠르게 동작시키되, 소스코드 내부는 모듈(패키지) 간 의존성을 인터페이스로 엄격히 격리해, 트래픽이 실제로 커졌을 때 해당 모듈만 떼어내 MSA로 쉽게 전환할 수 있게 설계해 둔다.

### 비유와 흔한 오해
- **비유**: 군대의 정규군(모놀리식)과 유격대(MSA). 정규군은 하나의 사령부(DB) 지휘를 받아 움직임은 느리지만 통제가 쉽다. 유격대는 각 소대가 독자적으로 빠르게 움직이지만, 전체 작전 조율이 실패하면 수습이 어렵다.
- **오해**: "MSA가 무조건 더 좋다"는 잘못된 생각이다. 인프라 자동화(CI/CD, 컨테이너 오케스트레이션)를 갖추지 못한 조직이 MSA로 전환하면, 네트워크 오류 디버깅과 배포 관리 부담만 커져 오히려 생산성이 떨어진다.

## 연결 개념
- 이벤트 스토밍·애그리게이트: MSA의 서비스 경계(바운디드 컨텍스트)를 정하는 실무 기법.
- Saga 패턴: MSA에서 분산 트랜잭션을 보상 동작으로 처리하는 기법.
- 서버리스(FaaS): MSA보다 더 잘게(함수 단위로) 쪼갠 극단적 확장.

# 📝 【답안용】 시험 답안 템플릿

> 목적: 시험장에서 25분에 그대로 쓰는 답안 양식. 작성방식(추상표현 금지·수치·도식·문제유형 전환)을 엄격히 지킨다.
> 핵심: 이 시험은 정보를 많이 나열하는 시험이 아니라, 문제 신호어에서 출제자 의도를 읽고 핵심 논점을 선별해 쓰는 시험이다.

## 핵심 인사이트 (3줄 요약)

> 1. **본질**: 애플리케이션의 모든 비즈니스 로직을 단일 프로세스와 단일 DB로 묶어 배포하는 **모놀리식**과, 도메인 경계(Bounded Context) 단위로 분리하여 다수의 프로세스와 분산 DB로 나눈 **마이크로서비스(MSA)** 간의 토폴로지 대조 아키텍처다.
> 2. **가치**: 모놀리식은 강력한 데이터 일관성(ACID)과 개발 초기의 직관적 단순성을 제공하며, MSA는 독립적 배포(Time-to-Market)와 국소적 오토스케일링(Scale-out)을 통한 클라우드 네이티브 생존력을 제공한다.
> 3. **판단 포인트**: MSA의 무조건적 찬양을 경계하고, MSA로 전환 시 필연적으로 발생하는 네트워크 지연(Latency)과 분산 트랜잭션 붕괴 리스크를 모놀리식의 장점(메모리 펑션 콜)과 완벽히 대조(Trade-off)해야 한다.

## 출제 의도 및 답안 포인트

| 출제 의도 | 반드시 짚을 핵심 | 감점 회피 포인트 |
|:---|:---|:---|
| 아키텍처의 트레이드오프(Trade-off) 분석 역량 검증 | 스케일링(확장) 단위 차이 vs 데이터 정합성(Join) 제약 | 모놀리식은 단점만 있고 MSA는 장점만 있다고 편파적으로 서술 |
| 통신 프로토콜 물리적 차이 맵핑 | Local Method Call(빠름) vs Remote HTTP/API Call(느림) | MSA가 응답 속도 측면에서도 모놀리식보다 무조건 빠르다고 적는 기초 성능 지식 결여 |
| 장애 전파(Cascading Failure) 및 복원력 차이 | 모놀리식의 단일 장애점(SPOF) vs MSA의 장애 격리(Fault Tolerance) | 서킷 브레이커(차단기) 없는 MSA가 모놀리식보다 장애에 훨씬 취약하다는 함정 누락 |

> 요약: 신생 스타트업이 처음부터 MSA로 시작하면 인프라 헬(Hell)에 빠져 굶어 죽는다. 모놀리식으로 시작해서 트래픽이 폭발하여 더 이상 코드를 땜질할 수 없는 한계에 다다랐을 때 비로소 MSA로 쪼개는 것이 정석이다.

## Ⅰ. 개요 및 필요성

- 정의: **모놀리식**은 모든 비즈니스 컴포넌트가 하나의 아카이브(WAR/JAR)로 패키징되어 단일 프로세스로 동작하는 구조이며, **마이크로서비스**는 기능별로 독립된 런타임과 DB를 갖는 분산 아키텍처 모델
- 배경: 서비스 규모 확장 시 모놀리식 코드 베이스는 빌드/테스트 시간이 기하급수적으로 늘어나 민첩성(Agility)이 소멸하고 잦은 배포가 불가능한 빅뱅 릴리즈(Big-bang Release)의 덫에 갇힘
- 필요성: 모놀리식의 강결합(Tightly Coupled)을 끊어 특정 기능 단위의 독립적 Scale-out과 Polyglot(다언어) 적용을 가능케 하여 대규모 트래픽과 조직 확장에 대응하기 위함

## Ⅱ. 모놀리식 vs 마이크로서비스 구조 대조 도식

서버를 쪼갰다는 것은, 100배 빠른 메모리 펑션 콜(Call)을 포기하고 100배 느린 네트워크 API를 탔다는 뜻이다.

```text
[ 1. 모놀리식 (Monolithic: 수직적 통합) ]             [ 2. 마이크로서비스 (MSA: 수평적 분산) ]
                                          
[ 프론트엔드 (UI) ] <--------- (응답: 0.05초) ---------- [ 프론트엔드 (UI) ]
      |                                                      |
+-----V----------------------+                           +---V---+ (API Gateway)
| 📦 통짜 프로세스 (App)         |                           |       |
|                            |                     +-----V-----+-----V-----+
| {주문}->(Method Call)->{결제} |                     | 주문 서버 |<--API-->| 결제 서버 |
+----------------------------+                     +-----------+         +-----------+
      | (단일 트랜잭션/Join)                                 |  (네트워크 호출 지연 0.5초) |
  [ 거대 단일 DB (Oracle) ]                             [주문 DB]             [결제 DB]
 (데이터 일관성 100% 보장 ✅)                        (절대 남의 DB 훔쳐보기 금지. 데이터 일관성 붕괴 🚨)
```

| 비교 축 (Trade-off) | 모놀리식 (Monolithic) | MSA (Microservice Architecture) |
|:---|:---|:---|
| **트래픽 확장 (Scale-out)** | **비효율적**: 특정 기능(주문)만 부하가 와도 무거운 서버 전체(100GB)를 복제해야 함 | **최적화**: 부하가 집중된 컨테이너(주문 서버 10MB)만 타겟팅하여 수천 개로 Auto-scaling |
| **장애 격리 (Fault Tolerance)**| **SPOF (단일장애점)**: 댓글 기능의 메모리 누수(OOM)가 서버 전체를 셧다운시켜 결제까지 마비 | **격리 (Isolation)**: 댓글 서버가 죽어도 결제/추천 서버는 영향을 받지 않고 독자 생존 |
| **통신 레이턴시 (Latency)** | **극강 (Local Call)**: 모든 로직이 동일한 메모리(JVM) 내부에 있어 통신 비용 제로 | **네트워크 홉(Hop) 병목**: 서비스 하나를 처리하기 위해 5개의 프록시를 HTTP로 핑퐁 치며 지연 폭발 |
| **데이터 정합성 / 복잡도** | 단일 DB의 트랜잭션 롤백(ACID) 지원으로 개발자 체감 복잡도 최저 수준 | 분산 트랜잭션(Saga), 결과적 일관성, DB 분할로 인한 Join 조립 등 인지 부하(Cognitive Load) 극한 |

> 요약: MSA는 '네트워크'라는 바다 위에 조각배들을 띄운 것이다. 바다가 평온하면 각자 잘 가지만, 폭풍우(타임아웃)가 오면 조각배들은 뿔뿔이 흩어져 미아(데이터 오염)가 된다. 모놀리식은 무겁지만 절대 가라앉지 않는 거북선 1척이다.

## Ⅲ. 극복해야 할 시스템적 리스크 (MSA 은총알 맹신)

"넷플릭스가 하니까 우리도 하자!"며 인프라 체력 없이 MSA로 넘어가면 회사가 문자 그대로 파산한다.

| 리스크 요인 | 발생 시나리오 및 시스템 붕괴 원인 (안티패턴) | 아키텍처 대응 방안 (실무 튜닝) |
|:---|:---|:---|
| **분산 모놀리식 (Distributed Monolith)** | 서버만 10개로 찢어놓고 DB는 옛날처럼 1개(통합 DB)를 그대로 공유함. 결국 하나의 서비스가 DB 테이블을 수정하면 나머지 9개 서비스가 줄줄이 다 터지는 최악의 혼종 붕괴 발생 | **Database-per-Service 사수**: 물리적으로 서버를 쪼갰으면 무조건 DB 인스턴스도 물리적으로 찢어라. 남의 데이터를 보려면 SQL이 아니라 무조건 API로 통신하는 Bounded Context 락인 |
| **분산 추적 상실 (디버깅 지옥)** | 사용자가 버튼 하나를 눌렀을 뿐인데 뒤에서는 10개의 마이크로서비스가 핑퐁을 침. 어디서 에러가 났는지 로그 파일 10개를 열어봐야 해서 장애 복구에 3일 소요 | **분산 추적(Distributed Tracing) 인프라 도입**: API Gateway 진입 시점에 고유한 `Trace-ID`를 발급하고, HTTP 헤더를 통해 모든 마이크로서비스로 전파(Propagate)하여 Zipkin/Jaeger 대시보드에 폭포수 추적 렌더링 |

> 요약: MSA는 개발자의 코딩 비용을 깎는 대신, 데브옵스(DevOps) 인프라 엔지니어의 피를 말려버린다. CI/CD 자동화 배포 파이프라인과 쿠버네티스 통제력이 없는 조직에게 MSA는 재앙의 동의어다.

## Ⅳ. 현대 아키텍처의 펜듈럼 현상 (모듈러 모놀리식 회귀)

무지성 MSA 분할에 지친 빅테크들이 "통신 낭비가 심하다"며 다시 뭉치는 타협안을 꺼내 들었다.

| 진화 아키텍처 | 물리적 구성 메커니즘 | 해결되는 비즈니스/운영 한계 (모놀리식과 MSA의 장점 결합) |
|:---|:---|:---|
| **Modular Monolithic** <br> (모듈러 모놀리식) | 배포(Deploy)는 옛날처럼 **WAR 파일 1개(통짜 서버 1대)로 배포**하되, 자바 소스코드 내부는 **MSA처럼 패키지(모듈) 간의 의존성을 인터페이스로 완벽히 격리(디커플링)**하여 짬뽕 코딩 차단 | 네트워크 통신(API HTTP)을 안 타니까 **모놀리식처럼 속도는 미친 듯이 빠름**. 코드는 철저히 분리(모듈화)돼 있어서, **나중에 트래픽이 커지면 언제든 손쉽게 뚝 떼어내어 진짜 MSA로 찢을 수 있음(미래 대비형)** |

> 요약: 최근 Amazon Prime 비디오 팀이 MSA로 찢어져 있던 아키텍처를 다시 모놀리식으로 합쳤더니 서버 비용이 90%나 줄었다고 발표했다. 트래픽 분산이 굳이 필요 없는 내부 영상 인코딩 작업 같은 것을 억지로 네트워크(MSA)로 찢어놨던 오버엔지니어링의 패착을 꼬집은 것이다.

## Ⅴ. 실무 적용 방안 및 결론

**적용 방안 3개:**
1. [Strangler Fig(스트랭글러) 패턴 기반 점진적 마이그레이션] 거대 레거시 통짜(Monolithic) 시스템을 일시에 MSA로 뒤엎는 빅뱅(Big-bang) 프로젝트를 배제하고, 앞단에 API Gateway를 둔 뒤 신규 기능(예: 추천 엔진)만 작고 가벼운 Node.js 마이크로서비스로 빼내어 트래픽을 서서히 돌리는 안전한 점진적 분할 수행
2. [Saga 패턴 기반 분산 데이터 정합성(ACID) 복원] MSA 쪼개기로 인해 상실한 모놀리식의 단일 DB 롤백(`ROLLBACK`) 기능을 복구하기 위해, 각 마이크로서비스가 즉시 Commit 후 Kafka를 통해 도메인 이벤트를 발행하고, 실패 시 역순으로 보상 트랜잭션(Compensating)을 던져 결과적 일관성(Eventual Consistency) 방어
3. [도메인 주도 설계(DDD) 기반 찢기 기준선(Bounded Context) 확립] 단순히 "코드 1,000줄 넘었으니 서버 하나 더 쪼개자"라는 무식한 접근을 막기 위해, 기획팀과 이벤트 스토밍 워크숍을 수행하여 '결제'와 '배송'이라는 명확한 비즈니스 경계(Context)가 나뉘는 지점에만 메스(MSA 분할)를 대는 응집도 설계 튜닝

**결론:**
- 기술사 판단: 모놀리식과 마이크로서비스는 선악의 개념이 아니다. 초기 비즈니스의 생사결(PMF 탐색기)에서는 압도적인 생산성과 단순성을 가진 모놀리식이 무조건 정답이다. 그러나 트래픽 폭증으로 인해 빌드에 1시간이 걸리고 서버 1대 확장에 막대한 비용(Scale-up 한계)이 드는 임계점에 도달했을 때, 그 고통(Pain)을 네트워크 복잡도(MSA)라는 새로운 고통으로 맞바꾸는 엔지니어링의 극단적 트레이드오프 결단이다.
- 향후 방향: 최근 아마존(AWS)의 모놀리식 회귀 발표에서 보듯, 무분별한 MSA 쪼개기는 네트워크 비용 폭발과 디버깅 불능을 낳는다. 결국 코드는 MSA 수준으로 철저히 격리(Decoupled)하되 런타임 배포는 단일로 가져가는 **모듈러 모놀리식(Modular Monolithic)**이 현대 실용주의 아키텍처의 강력한 대안으로 안착하고 있다.
