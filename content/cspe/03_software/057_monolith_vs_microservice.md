# 📖 【암기용】 개념 완전 이해

## 한눈에
- **개요**: 모놀리식 아키텍처는 시스템의 모든 기능이 하나의 거대한 프로세스로 결합되어 배포되는 구조이며, 마이크로서비스 아키텍처(MSA)는 독립적인 소규모 서비스들로 분할되어 API를 통해 통신하는 구조이다.
- **왜 필요한가**: 시스템이 작을 때는 하나의 덩어리로 개발하는 게 빠르지만, 커지면 "스파게티 코드"가 되어 한 곳의 수정이 전체 장애로 이어진다. 배포와 확장의 한계를 극복하기 위해 잘게 쪼개는 패러다임이 등장했다.
- **핵심 직관**: 다용도 스위스 아미 나이프(모놀리식)와 공구함(MSA)의 차이다. 스위스 나이프는 하나만 들고 다니면(배포) 편하지만 칼날 하나가 고장나면 통째로 수리해야 한다. 공구함은 무겁고 복잡하지만 톱이 고장나면 톱만 버리고 새 톱으로 바꿀 수 있다.

## 핵심 용어 정리

| 용어/표기 | 의미 | 비유·예 |
|:---|:---|:---|
| 모놀리식 (Monolithic) | UI, 비즈니스 로직, 데이터 접근 계층이 단일 애플리케이션으로 패키징된 구조 | 하나의 큰 성(Castle) |
| 마이크로서비스 (Microservice) | 독립적으로 배포 가능하고 각자 DB를 가지며 경량 프로토콜(HTTP)로 통신하는 구조 | 여러 채의 독립된 주택 단지 |
| 스트랭글러 패턴 (Strangler) | 모놀리식에서 MSA로 점진적 전환 시 사용하는 덩굴 식물 형태의 교체 기법 | 새 건물을 짓고 낡은 건물을 조금씩 철거 |
| 분산 트랜잭션 (Distributed Tx) | 쪼개진 MSA 환경에서 여러 서비스에 걸친 데이터 무결성을 보장하기 위한 기법 | 여러 은행을 거쳐 계좌이체를 처리하는 과정 |

## 깊이 이해
- **배경·문제의식**: 비즈니스가 고도화되며 모놀리식은 '거대한 진흙 덩어리(Big Ball of Mud)'가 된다. 컴파일에 30분이 걸리고, 결제 모듈의 사소한 오타 하나 때문에 전체 시스템을 재시작해야 하며, 회원 가입 트래픽이 몰리는데 연관 없는 게시판 서버 리소스까지 낭비되는 확장성(Scale-out) 한계에 봉착했다.
- **작동 원리 (비교)**: 
  - **모놀리식**: 웹브라우저 -> 톰캣 1대(UI+결제+주문+배송) -> 통합 DB. (호출 시 인메모리 함수 호출)
  - **MSA**: 웹브라우저 -> API Gateway -> 각각 독립된 톰캣(결제, 주문, 배송) -> 각자의 DB. (호출 시 네트워크 REST API 통신)
- **구체 예시**: 넷플릭스가 MSA 전환의 대표 사례다. 비디오 스트리밍, 추천 엔진, 결제 등 수천 개의 마이크로서비스가 독립적으로 업데이트된다.
- **흔한 오해·주의점**: "MSA가 무조건 더 좋은 최신 기술이다"라는 환상. MSA는 네트워크 지연, 분산 트랜잭션, 복잡한 인프라 관리라는 거대한 오버헤드를 대가로 치른다. 넷플릭스급 트래픽이 아닌 초기 스타트업이 MSA로 시작하면 개발 복잡도에 짓눌려 실패한다. (Monolith First 원칙)

## 연결 개념
- API 게이트웨이 (API Gateway) — 쪼개진 MSA 서비스들 앞단에서 요청을 라우팅해주는 문지기
- 바운디드 컨텍스트 (Bounded Context) — (054 참조) 마이크로서비스를 나누는 크기의 기준점
- 폴리글랏 프로그래밍 (Polyglot) — MSA 환경에서는 각 서비스마다 가장 적합한 언어와 DB(Java+MySQL, Node+MongoDB 등)를 선택할 수 있는 장점

# 📝 【답안용】 시험 답안 템플릿

## 핵심 인사이트 (3줄 요약)

> 1. **본질**: 애플리케이션을 단일 배포 단위로 통합하는 모놀리식 아키텍처와 비즈니스 역량 단위로 잘게 쪼개어 독립 배포하는 마이크로서비스(MSA)의 구조적 트레이드오프 비교이다.
> 2. **가치**: 모놀리식은 초기 개발 속도와 단순성을 제공하며, MSA는 복잡한 대규모 시스템에서 배포 유연성, 국소 장애 격리, 탄력적 스케일링을 보장한다.
> 3. **판단 포인트**: MSA 전환은 은탄환이 아니며 데이터 일관성 분리(분산 트랜잭션)와 인프라 복잡도 폭증을 대가로 하므로, 조직 규모와 시스템 복잡도가 임계점을 넘었을 때 도입해야 한다.

## 출제 의도 및 답안 포인트

| 출제 의도 | 반드시 짚을 핵심 | 감점 회피 포인트 |
|:---|:---|:---|
| 아키텍처 구조 트레이드오프 파악 역량 | 단일 DB vs 서비스별 DB(Database per service), 결합도 차이 | 무조건 MSA가 모놀리식보다 우월하다는 단정적 기재 |
| MSA 도입 시 아키텍처 복잡성 극복 방안 | API Gateway, 서비스 디스커버리, Saga 패턴 | 마이그레이션 시나리오(스트랭글러 패턴) 누락 |
| 실무 환경에 맞는 아키텍처 선택 기준 제시 | 시스템 규모, 조직 분할(콘웨이 법칙), 트래픽 스파이크 유무 | 기술적 요인만 적고 조직적 요인(Conway's Law) 배제 |

> 요약: 양쪽 아키텍처는 대립 관계가 아닌 진화의 단계이며, 시스템의 성장 라이프사이클에 맞춰 선택하는 판단 기준 제시가 핵심이다.

## Ⅰ. 개요 및 필요성

- 개요: 모놀리식은 단일 코드베이스와 통합 DB 기반의 아키텍처이며, MSA는 느슨하게 결합된 독립 서비스들이 경량 API로 통신하는 클라우드 네이티브 아키텍처임
- 배경: 서비스 비대화 시 모놀리식은 코드 결합도 증가, 배포 지연, 특정 모듈 트래픽 병목 시 전체 스케일아웃이 강제되는 한계 노출
- 필요성: 시장 변화에 따른 신속한 배포(TTM 단축)와 대용량 트래픽의 부분적 확장을 처리하기 위해 아키텍처의 패러다임 전환 필수

## Ⅱ. 구조 및 구성요소

```text
[ 모놀리식 아키텍처 ]                      [ 마이크로서비스 아키텍처 (MSA) ]
UI/Client                                UI/Client
   |                                        | -> [ API Gateway ]
[ 통합 애플리케이션 ]                       +-> [ Service A ] -> DB A
  - Service A, B, C (함수 호출)             +-> [ Service B ] -> DB B (API 통신)
   |                                        +-> [ Service C ] -> DB C
[ 통합 데이터베이스 ]
```

| 구성요소 관점 | 모놀리식 (Monolithic) | 마이크로서비스 (MSA) |
|:---|:---|:---|
| 데이터베이스 | 단일 통합 DB 스키마 공유 | Database per service (서비스별 독립 DB) |
| 통신 방식 | 인메모리 메서드 호출 (Call by Reference) | 네트워크 간 REST/gRPC 호출 (IPC) |
| 배포 단위 | 단일 WAR/JAR 통합 배포 | 컨테이너 단위 개별 마이크로서비스 배포 |

> 요약: 모놀리식이 강력한 결합을 통한 트랜잭션의 단일성을 보장한다면, MSA는 분할과 격리를 통해 자율성을 확보한다.

## Ⅲ. 동작원리 및 흐름도 (스트랭글러 패턴 기반 MSA 전환 흐름)

```text
레거시 식별 -> 바운디드 컨텍스트 추출 -> API 라우팅 변경 -> 분산 트랜잭션 수립 -> 레거시 기능 폐기
```

- 1단계 [도메인 식별]: 이벤트 스토밍을 통해 기존 모놀리식 시스템 내부의 결합도가 낮은 서브도메인을 식별
- 2단계 [서비스 추출 및 DB 분리]: 식별된 도메인을 신규 마이크로서비스로 추출하고 해당 데이터베이스 스키마도 논리적/물리적 분리
- 3단계 [API 라우팅 (Strangler)]: API Gateway를 도입하여 신규 기능은 새 서비스로, 기존 기능은 모놀리식으로 라우팅하여 점진적 교체
- 4단계 [통합 및 고도화]: 분산된 서비스 간의 데이터 일관성을 위해 이벤트 드리븐 비동기 통신 및 Saga 패턴을 적용하고 레거시 모듈 폐기

> 요약: 한 번에 빅뱅 방식으로 전환하지 않고, 문지기(API Gateway)를 세워 야금야금 갉아먹듯(Strangler) 점진적으로 분할한다.

## Ⅳ. 특징 (트레이드오프 비교)

- 확장성(Scalability): 모놀리식은 시스템 전체를 복제해야 하므로 리소스 낭비가 크나, MSA는 부하가 집중되는 특정 서비스(예: 결제)만 스케일아웃 가능
- 장애 격리(Fault Isolation): 모놀리식은 단일 모듈의 메모리 릭(Leak)이 전체 시스템 다운을 유발하나, MSA는 특정 서비스 장애가 타 서비스로 전파되지 않음 (서킷 브레이커 적용 시)
- 기술 다양성(Polyglot): 모놀리식은 단일 언어와 단일 DB에 종속되나, MSA는 각 서비스 특성에 맞춰 최적의 언어와 저장소(RDBMS, NoSQL) 융합 가능

> 요약: MSA는 유연성, 확장성, 장애 격리성에서 압도적 우위를 가지지만, 네트워크 지연과 아키텍처 복잡도라는 비용을 지불한다.

## Ⅴ. 심화 비교 및 적용 판단

| 비교 축 | 모놀리식 아키텍처 | 마이크로서비스 아키텍처 (MSA) | 선택 기준 |
|:---|:---|:---|:---|
| 시스템 복잡도 | 아키텍처는 단순하나, 내부 코드 결합도 복잡 | 내부 코드는 단순하나, 아키텍처와 인프라 복잡 | 프로젝트 라이프사이클 및 규모 |
| 트랜잭션 처리 | 단일 DB의 강력한 ACID 보장 | 분산 시스템의 최종 일관성 (Eventual Consistency) | 데이터 정합성의 실시간 요구 수준 |
| 조직 구조 (콘웨이) | 단일 거대 개발 조직 중심 | 목적 조직 중심의 소규모 다기능 팀 (2-Pizza Team) | 개발 조직의 성숙도와 분할 정도 |

> 요약: 도입의 잣대는 기술적 우수성이 아니라 "조직의 크기와 트래픽 규모가 분산 복잡도를 감당할 만큼 큰가"이다.

**리스크·대응:**
- 분산 트랜잭션 실패: 분할된 DB 환경에서 여러 서비스에 걸친 쓰기 실패 시 롤백 불가 → 보상 트랜잭션 기반의 Saga 패턴 또는 2PC(Two-Phase Commit) 선별 도입 (지표: 트랜잭션 롤백 실패 건수)
- 네트워크 지연 및 연쇄 장애: 인메모리 호출이 네트워크 API 호출로 변환되며 지연 발생 및 한 서비스 장애가 타 서비스로 타임아웃 전파 → 로컬 캐시 도입 및 서킷 브레이커(Circuit Breaker) 패턴으로 연쇄 장애 차단 (지표: 서비스 간 API 호출 응답 속도 p95)

## Ⅵ. 실무 적용 및 결론

**적용 방안 3개:**
1. Monolith First 전략 적용: 서비스 초기(스타트업 단계)에는 도메인 경계가 불명확하므로 모놀리식으로 빠르게 시장을 검증하고, 복잡도 임계점 도달 시 MSA로 분할 전환
2. 클라우드 네이티브 인프라 결합: MSA의 수많은 서비스 배포 및 헬스 체크 관리를 위해 Docker/Kubernetes 컨테이너 인프라와 CI/CD 파이프라인 자동화 구축 필수
3. 분산 추적(Distributed Tracing) 도입: 서비스 간 호출 관계 파악이 어려우므로 Zipkin, Jaeger, OpenTelemetry를 적용하여 Request ID 기반 병목 구간 가시성 확보

**결론 (2줄):**
- 기술사 판단: MSA는 조직과 시스템이 대규모일 때 유효한 최적화 전략이므로, 무리한 MSA 도입보다는 '모듈러 모놀리식(Modular Monolithic)'을 중간 기착지로 활용하는 것이 안전함
- 향후 방향: 최근 MSA의 인프라 복잡도를 해결하기 위해 통신 및 보안 계층을 사이드카(Sidecar)로 빼내는 서비스 메시(Service Mesh) 아키텍처로 진화하고 있음
