# 📖 【암기용】 개념 완전 이해

## 한눈에
- **개요**: 가상화(Virtualization)는 물리적 컴퓨팅 자원(CPU·메모리·I/O)을 **소프트웨어로 추상화**하여 단일 서버 위에 복수의 독립된 가상 머신(VM)을 구동하는 기술이며, **하이퍼바이저(Hypervisor, VMM)**가 이 분할·격리를 통제함.
- **왜 필요한가**: 물리 서버 1대에 OS 1개만 운용하면 CPU 이용률이 10~20%에 머물러 상면·전력·관리 비용이 낭비됨. 가상화로 서버 1대에 VM 10~20대를 통합(Consolidation)해 이용률을 60~80%로 끌어올리고, 클라우드 IaaS의 기반 인프라를 구성함.
- **핵심 직관**: 100평 창고(물리 서버)에 가벽을 세워 10평 방 10개(VM)로 쪼개고, 각 방에 다른 세입자(게스트 OS)를 입주시키는 것. 하이퍼바이저는 가벽을 치고 전기·수도(CPU·메모리)를 배분하는 건물 관리인임.

## 핵심 용어 정리 (내부에 등장하는 것들)

| 용어/표기 | 의미 | 비유·예 |
|:---|:---|:---|
| 가상화 (상위 키워드) | 물리 자원을 논리적으로 추상화해 다수 인스턴스가 공유하는 기술 | 1대 서버를 10대처럼 쓰기 |
| 가상 머신 (VM) | 물리 H/W를 추상화한 논리적 컴퓨터 1대 — 독립된 OS·커널 보유 | 가벽으로 나뉜 독립 원룸 |
| 하이퍼바이저 (VMM) | VM에 물리 자원을 분배하고 격리·통제하는 소프트웨어 계층 | 건물 관리인 |
| Type 1 (Bare-Metal) | H/W 바로 위에 설치되는 하이퍼바이저 — ESXi, KVM, Xen | 빈 땅에 직접 세운 관리 사무소 |
| Type 2 (Hosted) | 호스트 OS 위에 애플리케이션으로 설치 — VMware Workstation, VirtualBox | 기존 건물 안 임시 사무소 |
| Trap & Emulate | 게스트 OS의 특권 명령을 H/W가 가로채(Trap) 하이퍼바이저가 대신 실행(Emulate) | 자물쇠 잠긴 문을 관리인이 대신 열어줌 |
| H/W 보조 가상화 | Intel VT-x·AMD-V가 Ring -1을 제공해 Trap 오버헤드를 감소 | 전용 마스터키 제공 |

## 깊이 이해
- **배경·문제의식**: 2000년대 초 데이터센터의 서버 대수가 급증하면서 상면·전력·냉각 비용이 IT 예산의 상당 부분을 차지함. 서버 통합(Consolidation)을 통해 물리 서버 수를 1/10로 줄이면서 동일 워크로드를 운용하려는 요구가 가상화 기술의 핵심 동인임.
- **작동 원리(CPU 가상화)**:
  - 게스트 OS는 자신이 H/W를 독점한다고 인식하고 특권 명령(Ring 0)을 실행함.
  - 하이퍼바이저가 Ring 0(또는 Ring -1)을 점유하고 게스트 OS는 Ring 1로 강등됨.
  - 게스트 OS가 특권 명령을 호출하면 H/W가 Trap을 발생시켜 하이퍼바이저로 제어권을 전달하고, 하이퍼바이저가 에뮬레이션 후 결과를 반환함(Trap & Emulate).
  - Intel VT-x(2005)·AMD-V는 VMX root/non-root 모드를 도입해 Trap 비용을 VMEXIT/VMENTRY 하드웨어 전환으로 대체, 오버헤드를 수십 %에서 2~5%로 감소시킴.
- **비유**: 호텔의 프론트 데스크(하이퍼바이저)가 객실 열쇠(물리 자원)를 관리하고, 투숙객(게스트 OS)이 열쇠를 요청하면 확인 후 전달하는 구조. VT-x는 객실에 전자 잠금장치를 달아 프론트 경유 없이 카드키로 직접 입실하게 하는 것.
- **구체 예시**: AWS EC2 인스턴스는 Nitro 시스템(KVM 기반 + 전용 DPU 오프로딩) 위의 VM 1대이며, 네트워크·스토리지 I/O를 전용 Nitro Card가 처리해 호스트 CPU의 100%를 게스트에 할당함.
- **흔한 오해·주의점**: (1) VM과 컨테이너를 혼동하면 안 됨 — VM은 OS 자체를 통째로 가상화(H/W 레벨), 컨테이너는 OS 커널을 공유하고 프로세스만 격리(OS 레벨). (2) Type 2가 Type 1보다 열등한 것은 아님 — 개발·테스트 용도에서는 호스트 OS 위의 편의성이 더 적합함.

## 연결 개념
- (021 전가상화·반가상화·컨테이너 비교) 가상화 최적화의 세부 기법 분류
- (170 Docker 컨테이너) 하이퍼바이저 VM의 무거움을 극복한 OS 레벨 경량 대안
- (161 클라우드 서비스 모델) 가상화 기술 위에 성립하는 IaaS·PaaS·SaaS

# 📝 【답안용】 시험 답안 템플릿

## 핵심 인사이트 (3줄 요약)

> 1. **본질**: 하이퍼바이저는 물리 H/W를 논리적으로 추상화해 다수 게스트 OS(VM)의 동시 구동을 통제하는 자원 분할·격리 기술임.
> 2. **가치**: 서버 통합(Consolidation Ratio 10:1 이상)으로 H/W 이용률을 60~80%로 끌어올리고, IaaS 클라우드의 근간 인프라를 제공함.
> 3. **판단 포인트**: Type 1(Bare-Metal) vs Type 2(Hosted)의 계층 구조 차이와, Trap & Emulate 오버헤드를 H/W 보조(VT-x)·DPU 오프로딩으로 극복하는 아키텍처 선택이 핵심임.

## 출제 의도 및 답안 포인트

| 출제 의도 | 반드시 짚을 핵심 | 감점 회피 포인트 |
|:---|:---|:---|
| 가상화 아키텍처와 Type 1·2 차이 이해 | H/W 추상화, Trap & Emulate 원리, Type 1·2 계층 구조 | Type 1과 Type 2의 계층 위치 혼동 |
| 가상화 오버헤드와 통제 메커니즘 | VT-x Ring -1, SR-IOV 네트워크 직결, DPU 오프로딩 | 개념 나열에 그치고 성능 오버헤드 리스크 누락 |

> 요약: 하이퍼바이저의 두 구조(Type 1·2)를 비교하고, 에뮬레이션 오버헤드를 H/W 보조로 극복하는 최적화 기준을 제시해야 함.

## Ⅰ. 개요 및 필요성

- 개요: 물리 자원을 논리적으로 추상화해 다수 독립 VM을 구동·격리하는 자원 분할 기술임
- 배경: 1-Server 1-OS 구조의 낮은 이용률(10~20%), 상면·전력 비용 증가, 프로비저닝 지연
- 필요성: 서버 통합 비율 10:1 이상 달성, 동적 프로비저닝(수 분 내 VM 생성), IaaS 클라우드 기반 인프라 구축을 위해 필수임

---

## Ⅱ. 구조 및 구성요소

```text
[Type 1 Bare-Metal]                    [Type 2 Hosted]
VM1(Guest OS) VM2(Guest OS)            VM1(Guest OS) VM2(Guest OS)
      |             |                        |             |
  Hypervisor(VMM)                        Hypervisor(VMM)
      |                                      |
  Physical H/W                           Host OS(Linux/Windows)
                                             |
                                         Physical H/W
```

| 구성요소 | 역할 | 비고 |
|:---|:---|:---|
| Type 1 Hypervisor | H/W 위에 직접 설치, 자원 직결 제어 | ESXi, KVM, Xen — 엔터프라이즈 표준 |
| Type 2 Hypervisor | 호스트 OS 위에 앱으로 설치 | VirtualBox, Workstation — 개발·테스트 |
| vCPU/vMemory | VM에 할당된 가상 CPU·메모리 | 물리 자원의 논리적 분할 단위 |
| 가상 NIC/가상 디스크 | VM의 네트워크·스토리지 가상 디바이스 | SR-IOV·virtio로 오버헤드 감소 |

> 요약: Type 1은 호스트 OS 레이어를 제거해 오버헤드를 극소화하므로 대규모 서버 인프라의 표준이며, Type 2는 편의성을 위한 개발·테스트 용도임.

---

## Ⅲ. 동작원리 및 흐름도

```text
게스트 OS: 특권 명령(I/O 등) 실행 시도
  -> H/W: Ring 권한 검사 -> 게스트는 Ring 1(비특권) -> Trap 발생
    -> Hypervisor(Ring 0/-1): 명령 분석 -> 물리 자원에 맞게 에뮬레이션
      -> 결과를 게스트 OS에 반환 -> 게스트 실행 재개
```

1. 권한 강등: 하이퍼바이저가 Ring 0(또는 VT-x의 Root Mode)을 점유하고, 게스트 OS는 비특권 링으로 적재됨
2. Trap 발생: 게스트 OS가 특권 명령 실행 시 H/W가 인터럽트(Trap)를 발생시켜 하이퍼바이저로 제어권 전환함
3. Emulate 처리: 하이퍼바이저가 해당 요청을 물리 자원에 매핑해 대신 실행 후 결과 반환함
4. 격리 유지: VM 간 메모리·네트워크 영역을 분리해 한 VM의 오류가 다른 VM에 전파되지 않도록 차단함

> 요약: 게스트 OS는 H/W를 독점한다고 인식하지만, 하이퍼바이저가 모든 특권 명령을 에뮬레이션해 자원을 안전하게 통제함.

---

## Ⅳ. 특징

- H/W 수준 격리: VM별 독립 커널·메모리 공간을 보유해 멀티테넌트 환경에서 보안 격리가 컨테이너보다 강력함
- 에뮬레이션 오버헤드: Trap & Emulate는 VM당 CPU 사이클을 소모하며, H/W 보조 없이는 15~30% 성능 저하 발생
- 이종 OS 지원: 동일 H/W에서 Linux·Windows·FreeBSD 등 이종 게스트 OS를 동시 구동 가능함
- 라이브 마이그레이션: VM 메모리를 네트워크로 복제해 서비스 중단 없이 호스트 간 이전 가능(vMotion 기준 수 초)

## Ⅴ. 심화 비교 및 적용 판단

| 구분 | Type 1 (Bare-Metal) | Type 2 (Hosted) | 선택 기준 |
|:---|:---|:---|:---|
| 설치 위치 | H/W 직접 | 호스트 OS 위 | 운영 환경(DC vs 개발PC) |
| 성능 오버헤드 | 2~5%(VT-x 적용 시) | 10~20%(호스트 OS 경유) | 워크로드 성능 요구 |
| 격리 수준 | 강함(독립 커널) | 중간(호스트 OS 의존) | 멀티테넌트 보안 요구 |
| 관리 편의성 | 전용 관리 콘솔 필요 | 호스트 OS에서 직접 관리 | 운영 인력·규모 |

> 요약: 프로덕션 DC는 Type 1(ESXi·KVM)으로 성능·격리 확보, 개발·테스트는 Type 2(VirtualBox)로 편의성을 확보함.

**리스크·대응:**
- Trap & Emulate 병목: I/O 명령 번역에 CPU 사이클 과소비 -> H/W 보조(VT-x), SR-IOV 네트워크 직결, DPU 오프로딩 적용 (지표: VM I/O 지연 ms)
- Noisy Neighbor: 특정 VM의 자원 독식으로 동일 호스트 타 VM 성능 급락 -> 하이퍼바이저 QoS(CPU Capping·메모리 Limit) 강제 설정 (지표: VM별 CPU Steal Time)

**도입 후 점검 지표:**
- 성능: 서버 통합 비율(Consolidation Ratio) 10:1 이상, CPU 이용률 60~80% 유지
- 가용성: 라이브 마이그레이션 전환 시간 — RTO 기준 수 초 이내 통제

---

## Ⅵ. 실무 적용 및 결론

**적용 방안 3개:**
1. DPU 오프로딩: AWS Nitro처럼 네트워크·스토리지 I/O를 전용 SmartNIC(DPU)로 이관해 호스트 CPU 100%를 게스트 VM에 할당함
2. 무중단 라이브 마이그레이션: VMware vMotion + SAN 연동으로 물리 서버 유지보수 시 다운타임 0으로 VM을 타 호스트로 실시간 이전함
3. 마이크로 VM 채택: Firecracker(AWS Lambda 기반)로 불필요한 디바이스 드라이버를 제거해 부팅 125ms + VM 수준 보안 격리를 동시 달성함

**결론:**
- 기술사 판단: 엔터프라이즈 가상화의 핵심은 에뮬레이션 오버헤드 최소화이며, Type 1 + H/W 보조(VT-x·SR-IOV) + DPU 오프로딩 조합이 최적 아키텍처임
- 향후 방향: 하이퍼바이저와 컨테이너의 경계가 융합되어 Kata Containers·Firecracker 등 마이크로 VM 기반 클라우드 네이티브 격리 모델로 진화 중임
