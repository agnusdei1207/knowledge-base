# 📖 【암기용】 개념 완전 이해

> 목적: 비밀 관리를 처음 봐도 완전히 이해하게 만든다. 시험 답안 양식이 아니라, 이해를 위한 설명이다.

## 한눈에
- **개요**: 비밀 관리는 API 키·DB 비밀번호·인증서 같은 **자격증명(Credential)**을 코드 밖 중앙 저장소에서 안전하게 저장·조회·교체·폐기하는 **자격증명 생명주기 관리(Credential Lifecycle Management)** 체계다.
- **왜 필요한가**: 자격증명이 Git 커밋, 컨테이너 이미지, 환경변수, 로그에 평문으로 남으면 저장소 하나만 유출돼도 그 값을 손에 넣은 공격자가 다른 시스템까지 침투(lateral movement)하는 출발점이 된다.
- **핵심 직관**: 호텔에서 방 열쇠를 손님마다 복제해 영구히 나눠주지 않고, 체크인 시 임시 스마트키를 발급하고 체크아웃하면 즉시 무효화하는 것과 같다 — 자격증명도 필요한 순간에만 짧게 살아있어야 유출돼도 피해가 제한된다.

## 핵심 용어 정리 (내부에 등장하는 것들)

| 용어 | 의미 | 비유 |
|:---|:---|:---|
| 자격증명(Credential) | 비밀 관리가 다루는 상위 대상 — API 키, 비밀번호, 인증서, 토큰 전체 | 열쇠·출입증 전체 |
| Secret Manager(Vault·AWS Secrets Manager) | 자격증명을 중앙에서 저장·버전 관리·접근 통제하는 시스템 | 호텔 프런트의 키 관리 시스템 |
| KMS(Key Management Service) | 암호화 키 자체를 생성·보관·회전하는 서비스 | 마스터키를 보관하는 금고 |
| Envelope Encryption(봉투 암호화) | 실제 데이터는 데이터 키(DEK)로, 그 데이터 키는 다시 KMS의 마스터 키(KEK)로 감싸 암호화하는 이중 구조 | 편지(비밀값)를 봉투(DEK)에 넣고, 그 봉투를 다시 금고 열쇠(KEK)로 잠그는 것 |
| Static Secret(정적 시크릿) | 값이 고정돼 있고 사람이 직접 교체해야 하는 비밀값 | 오래 안 바꾼 집 열쇠 |
| Dynamic Secret(동적 시크릿) | 요청할 때마다 새로 발급되고 TTL이 지나면 자동 폐기되는 비밀값 | 체크인마다 새로 발급되는 호텔 스마트키 |
| TTL(Time To Live) | 발급된 비밀값이 유효한 시간 — 지나면 자동 만료 | 스마트키의 체크아웃 시각 |
| Rotation(회전) | 비밀값을 주기적으로 새 값으로 교체하는 절차 | 정기적으로 열쇠를 바꾸는 것 |
| Workload Identity(워크로드 신원) | 애플리케이션이 자기 자신임을 증명하는 방법(IAM Role, OIDC, Kubernetes SA) | 투숙객 본인 확인(신분증) |
| Audit Log(감사 로그) | 누가 언제 어떤 비밀값을 조회·변경했는지 남기는 기록 | 출입 기록부 |
| Least Privilege(최소 권한) | 각 서비스가 자신에게 필요한 비밀값에만 접근하도록 제한하는 원칙 | 객실 카드키가 그 방문만 여는 것 |

## 깊이 이해

### 정적 시크릿과 동적 시크릿의 차이 — 수치로 이해
- 정적 시크릿은 사람이 값을 만들어 저장소에 넣고, 유출되면 사람이 수동으로 찾아 교체해야 한다. 이 교체가 끝날 때까지(보통 며칠~몇 주) 유출된 값은 계속 유효하다.
- 동적 시크릿은 다르다. 예: Vault의 Database Secrets Engine에 애플리케이션이 DB 자격증명을 요청하면, Vault가 그 순간 PostgreSQL에 새 계정을 만들어 TTL 1시간으로 발급한다. 1시간이 지나면 Vault가 그 계정을 자동으로 폐기(DROP)한다.
- 만약 이 동적 자격증명이 유출돼도 공격자가 쓸 수 있는 시간은 최대 1시간(TTL 이내)으로 제한된다. 정적 시크릿이 유출 후 며칠씩 유효한 것과 비교하면 피해 시간이 수십~수백 배 줄어든다.

### Envelope Encryption이 필요한 이유
- KMS로 모든 비밀값을 직접 암호화하면 값이 커질수록, 개수가 많아질수록 KMS 호출량이 폭증하고 비용·지연이 커진다.
- 그래서 실제 비밀값은 로컬에서 생성한 데이터 키(DEK)로 암호화하고, 그 DEK 자체만 KMS의 마스터 키(KEK)로 암호화해 저장한다. 비밀값을 읽을 때는 암호화된 DEK를 KMS에 보내 복호화받고, 그 DEK로 실제 값을 복호화한다.
- 이렇게 하면 KMS는 짧은 DEK만 처리하면 되고, 수천 개의 비밀값이 있어도 KMS 호출은 DEK 단위로만 발생해 성능 부담이 줄어든다.

### Workload Identity로 신원을 증명하는 흐름 — 워크드 예제
- 전통적 방식은 애플리케이션 설정 파일에 Secret Manager 접근용 API 키를 하드코딩하는데, 이 키 자체가 또 다른 유출 대상이 된다.
- OIDC 기반 방식은 다르다. 예: Kubernetes Pod가 자신의 ServiceAccount로 서명된 JWT(OIDC 토큰)를 발급받는다 → 이 토큰을 AWS STS의 `AssumeRoleWithWebIdentity`에 제시한다 → AWS가 토큰 서명을 검증하고 TTL 15분~1시간짜리 임시 AWS 자격증명을 발급한다 → 이 임시 자격증명으로 Secrets Manager를 조회한다.
- 이 흐름에는 어디에도 영구히 저장된 비밀 키가 없다. 신원 증명 자체가 단기 토큰 교환으로 이뤄지므로, Pod 설정 파일이 유출돼도 그 안에는 재사용 가능한 비밀값이 없다.

### Rotation을 무중단으로 하는 원리 — Dual Credential
- 자격증명 하나만 쓰다가 즉시 교체하면, 교체 순간 아직 옛 값을 캐시한 인스턴스들의 연결이 끊길 수 있다.
- Dual credential rotation은 항상 A/B 두 자격증명을 동시에 유효 상태로 유지한다. 예: 현재 A가 활성이고 B가 대기 상태일 때, 새 값을 B에 발급하고 애플리케이션들이 순차적으로 B로 전환을 완료할 때까지(예: 10분) A도 계속 유효하게 둔 뒤, 전환이 끝나면 A를 폐기한다.
- 이렇게 하면 배포 타이밍이 어긋난 인스턴스가 있어도 순간적으로 인증이 실패하는 일 없이 회전이 끝난다.

### 판별 원리 — 언제 정적, 언제 동적을 쓰는가
- DB 계정, 클라우드 임시 자격증명처럼 발급 주체가 즉석에서 새 값을 만들 수 있는 대상은 동적 시크릿이 우선이다.
- 반면 제3자 SaaS API 키처럼 발급 주체가 외부이고 우리가 즉석 발급을 요청할 수 없는 경우는 정적 시크릿으로 저장하되, 최소 권한·짧은 rotation 주기(예: 90일)·감사 로그로 보완한다.

### 흔한 오해
- "비밀값을 암호화해서 Git에 커밋하면 안전하다"는 생각은 위험하다. 그 복호화 키가 어딘가에 있어야 하고, 그 키 관리·접근 로그·회전이 없으면 암호화된 파일도 결국 키 유출과 함께 뚫린다. 저장 방식보다 접근 제어·TTL·감사·회전을 모두 갖춰야 비밀 관리가 성립한다.

## 연결 개념
- KMS — Envelope Encryption의 마스터 키를 보관하는 하위 인프라
- IAM/OIDC — Workload Identity로 신원을 증명하는 구체 메커니즘
- 의존성 취약점 스캔(291) — 공급망 보안의 다른 축(패키지 취약점 vs 자격증명 유출)
- Zero Trust — "네트워크 안에 있다고 신뢰하지 않는다"는 원칙이 동적 시크릿·짧은 TTL의 근거가 됨

## Ⅰ. 개요 및 필요성

- 개요: 비밀 관리는 자격증명의 저장·조회·교체·폐기 통제이다.
- 배경: API 키와 DB 비밀번호가 코드·이미지·로그에 남으면 권한 탈취와 내부 확산이 발생한다.
- 필요성: Vault·AWS Secrets Manager와 KMS를 결합해 최소 권한, TTL, rotation, 감사 로그를 적용해야 한다.

---

## Ⅱ. 구조 및 구성요소

```text
Application -> Workload Identity -> Secret Manager -> KMS Encryption -> Secret Value
                                      / Rotation Job
                                      / Audit Log
```

| 구성요소 | 역할 | 특이사항 |
|:---|:---|:---|
| Secret Manager | 비밀값 저장·버전 관리 | Vault, AWS Secrets Manager |
| KMS/HSM | envelope encryption 키 보호 | 키 회전 90~365일 정책 |
| Workload Identity | 애플리케이션 신원 증명 | IAM Role, OIDC, Kubernetes SA |
| Audit Log | 조회·변경·폐기 기록 | SIEM 연동, 1년 이상 보관 |

> 요약: 비밀 관리는 저장소, 키 관리, 워크로드 신원, 감사 로그가 결합되어 자격증명 생명주기를 통제한다.

---

## Ⅲ. 동작원리 및 흐름도

```text
서비스 시작 -> 신원 토큰 발급 -> Secret 조회 요청 -> 정책 평가 -> 복호화 반환 -> TTL 만료/회전
```

| 단계 | 처리 내용 | 검증 기준 |
|:---:|:---|:---|
| 1 | 애플리케이션이 IAM·OIDC로 신원 증명 | 서비스별 Role 분리 |
| 2 | Secret Manager가 정책·경로 권한 확인 | 최소 권한 policy |
| 3 | KMS로 암호문 복호화 후 secret 반환 | TLS 1.2 이상, mTLS 선택 |
| 4 | rotation·TTL 만료 시 재발급 또는 폐기 | rotation 성공률 99% 이상 |

> 요약: 동작은 신원 증명, 권한 평가, 복호화, 회전 순서이며 TTL과 감사 로그가 피해 범위를 제한한다.

## Ⅳ. 특징

| 구분 | 파일·환경변수 방식 | Vault·Secrets Manager | 수치·판단 기준 |

## Ⅴ. 심화 비교 및 적용 판단

| 비교 축 | 기존/대안 | 본 키워드 | 선택 기준 |
|:---|:---|:---|:---|
| 구조 | .env, config file | Secret Manager + KMS | 서비스 5개 이상, 배포 환경 2개 이상 |
| 비용/성능 | 조회 지연 없음 | 캐시·TTL로 조회 제어 | p95 조회 100ms 이하 |

> 요약: 운영 규모가 커질수록 파일 방식보다 중앙 저장소와 자동 교체가 자격증명 통제에 적합하다.

| 리스크 | 원인 | 대응 방안 | 확인 지표 |
|:---|:---|:---|:---|
| 단일 장애점 | Secret Manager 장애 | local cache, multi-AZ, break-glass | 조회 실패율 0.1% 이하 |
| 권한 과다 | wildcard policy | 경로 기반 RBAC, policy review | 과권한 policy 0건 |
| 회전 실패 | 애플리케이션 재연결 미흡 | dual credential, canary rotation | rotation 실패 건수 |

> 요약: 주요 위험은 장애, 과권한, 회전 실패이며 캐시·RBAC·이중 자격증명으로 통제한다.

| 점검 항목 | 목표 기준 | 측정 방법 |
|:---|:---|:---|
| 유출 방지 | Git secret 탐지 0건 | pre-commit, repository scan |
| 교체 준수 | 중요 secret 90일 이하 회전 | rotation report |
| 접근 감사 | secret 조회 로그 100% 수집 | CloudTrail, Vault audit device |

> 요약: 성공 여부는 저장소 유출 건수, 회전 주기, 조회 로그 수집률로 판단한다.

## Ⅵ. 실무 적용 및 결론

**적용 방안 3개 (필수 - 단계별 또는 항목별):**
1. Git secret scanning과 pre-commit hook으로 AWS Access Key, JWT private key, DB password 커밋을 차단
2. Vault 또는 AWS Secrets Manager에 secret을 저장하고 KMS CMK, IAM Role, path policy로 서비스별 접근 범위 제한
3. DB 계정은 dynamic secret 또는 dual credential rotation으로 30~90일 회전 및 감사 로그 SIEM 전송

**결론 (2줄):**
- 기술사 판단: 규제·감사 대상 시스템은 중앙 Secret Manager와 KMS를 기본 선택, 소규모 내부 도구는 관리형 클라우드 Secret으로 운영 부담 축소
