# 📖 【암기용】 개념 완전 이해

> 목적: Low-Code·No-Code 플랫폼을 처음 봐도 이해하게 만든다. 시험 답안 양식이 아니라, 이해를 위한 설명이다.

## 한눈에
- **개요**: Low-Code·No-Code는 **시각적 개발(Visual Development)** 방식으로 화면·데이터·워크플로를 조립해 애플리케이션을 만드는 플랫폼이며, 코드를 적게 쓰거나(Low-Code) 아예 쓰지 않고(No-Code) 만드는 두 방식을 함께 가리킨다.
- **왜 필요한가**: 현업의 업무 앱 요구는 계속 쌓이는데 전문 개발 인력은 한정돼 있다. 단순 승인·조회·입력 업무까지 매번 전문 개발자가 코드로 짜면 대기열이 길어지고, 현업은 결국 엑셀·메일로 우회 시스템을 만든다.
- **핵심 직관**: 레고 블록처럼 화면·데이터·업무 흐름을 조립하되, 전기·소방 안전 기준(보안·권한 통제)은 별도로 반드시 지켜야 하는 방식이다.

## 핵심 용어 정리 (내부에 등장하는 것들)

| 용어 | 의미 | 비유 |
|:---|:---|:---|
| 시각적 개발(Visual Development) | 코드를 타이핑하는 대신 드래그 앤드 드롭·선언형 설정으로 화면·로직을 구성하는 방식 — Low-Code·No-Code의 **본질** | 도면을 그려 건물을 짓는 것처럼 조립으로 앱을 만듦 |
| Low-Code | 대부분을 시각적으로 만들되, 필요하면 코드를 추가로 작성해 확장하는 방식 | 조립 가구에 필요하면 직접 나사를 더 박는 것 |
| No-Code | 코드 작성 없이 오직 설정·조립만으로 앱을 완성하는 방식 | 완전 조립식 가구, 나사 없이 끼우기만 |
| 시각 모델러(Visual Modeler) | 화면·폼·데이터 구조를 마우스 조작으로 정의하는 플랫폼 도구 | 화면 설계용 그림판 |
| 워크플로 엔진(Workflow Engine) | 승인·알림·상태 전이 같은 업무 절차를 규칙으로 실행하는 엔진 | 결재 서류가 정해진 순서로 도장을 받으며 이동 |
| 커넥터(Connector) | ERP·CRM·DB·SaaS 등 외부 시스템과 미리 만들어진 방식으로 연결하는 부품 | 전기 콘센트 규격 어댑터 |
| Citizen Developer(시민 개발자) | 전문 개발자가 아닌 현업 직원이 플랫폼으로 직접 앱을 만드는 사람 | 전문 목수 없이도 조립 가구를 만드는 사람 |
| Shadow IT | IT 부서 승인·등록 없이 현업이 임의로 만들어 운영하는 앱·시스템 | 회사 몰래 만든 비상구(통제 밖 통로) |
| RBAC | 역할(직무)에 따라 접근 권한을 부여하는 방식 | 직급별 출입카드 등급 |

## 깊이 이해

### 왜 필요했나 — 개발 대기열과 Shadow IT의 악순환
- 전통적 개발은 요구사항 정의, 설계, 코딩, 테스트를 모두 거쳐 단순한 승인 앱 하나에도 수 주~수개월이 걸린다. 개발팀 대기열이 길어지면 현업은 기다리지 못하고 엑셀·메일·개인 스프레드시트로 임시 시스템을 만든다 — 이것이 통제 밖에서 운영되는 Shadow IT다.
- Low-Code·No-Code는 이 대기열 문제를 "현업이 직접, 그러나 IT가 정한 표준 부품 안에서" 만들게 해 해결하려는 접근이다. 즉 속도 문제 해결과 동시에 Shadow IT를 양성화하려는 목적도 있다.

### 작동 원리 — 조립부터 배포까지
- 시각 모델러로 화면(폼)과 데이터 구조를 정의한다.
- 워크플로 엔진으로 승인·알림·상태 전이 같은 처리 절차를 규칙으로 연결한다.
- 커넥터로 ERP·CRM·DB 등 외부 시스템과 데이터를 주고받는다.
- 복잡한 계산이나 특수 로직이 필요하면 개발자가 스크립트를 부분적으로 추가한다(Low-Code의 확장 지점).
- 배포 전 데이터 등급 분류, 접근권한(RBAC) 설정, 배포 승인을 거쳐 앱 카탈로그에 등록한 뒤 릴리스한다.

### 구체 수치로 보는 생산성과 통제 기준
- 예: 휴가 신청 앱은 직원 테이블, 신청 폼, 팀장 승인, 인사팀 알림, 권한 정책을 조합해 2주 내 파일럿을 만들 수 있다. 전통 개발로 동일한 앱을 만들면 요구정의부터 배포까지 8주 안팎이 걸리는 경우가 흔하다 — 리드타임이 약 4분의 1로 줄어드는 셈이다.
- 그러나 이 속도를 통제 없이 방치하면 위험하다. 그래서 실무에서는 앱 소유자 등록률 100%, 커스텀 코드 비율 20% 이하(이 이상이면 전통 개발 전환 검토), 데이터 접근 권한 위반 0건을 운영 기준으로 둔다.

### 판별 원리 — 언제 Low-Code·No-Code, 언제 전통 개발인가
- 업무가 CRUD(등록·조회·수정·삭제), 승인, 대시보드처럼 정형화된 패턴이면 Low-Code·No-Code로 충분하다.
- 복잡한 알고리즘, 대량 트랜잭션, 초저지연·고성능이 필요한 핵심 업무는 플랫폼의 표준 부품으로 감당이 안 되고 벤더 종속 위험도 커지므로 전통 개발이 적합하다.
- 판별 기준 수치 예: 동시 사용자 50명 이하 부서 앱은 파일럿 후보, 그 이상이거나 핵심 거래를 다루면 전통 개발·하이브리드를 검토한다.

### 비유와 흔한 오해
- **비유**: 주방을 새로 짓는 대신, 검증된 모듈형 조리대와 조리 도구를 배치해 메뉴를 완성하는 것과 같다. 다만 화재·위생 기준(보안·개인정보 규정)은 조리대를 조립했다고 자동으로 지켜지지 않는다.
- **오해**: No-Code가 "IT 통제가 필요 없다"는 뜻이 아니다. 데이터 접근권한, 배포 승인, API 사용량, 앱 소유자 관리가 빠지면 오히려 통제된 Shadow IT가 아니라 통제되지 않는 Shadow IT를 양산하게 된다.

## 연결 개념
- Citizen Developer - 현업 사용자가 앱 제작에 참여 (Low-Code·No-Code가 가능하게 만드는 새로운 개발자 계층)
- BPM/Workflow - 승인·처리 절차 자동화 (플랫폼 내 워크플로 엔진이 구현하는 대상)
- API Management - 커넥터와 외부 연계 통제 (플랫폼 확장성과 벤더 종속 리스크를 관리하는 상위 체계)

# 📝 【답안용】 시험 답안 템플릿

> 목적: 시험장에서 25분에 그대로 쓰는 답안 양식. 작성방식(추상표현 금지·수치·도식·문제유형 전환)을 엄격히 지킨다.
> 핵심: Low-Code·No-Code는 개발 생산성 논의가 아니라 거버넌스, 확장성, 보안 통제를 포함한 애플리케이션 공급 모델이다.

## 핵심 인사이트 (3줄 요약)

> 1. **본질**: Low-Code·No-Code 플랫폼은 시각적 모델링과 재사용 컴포넌트로 업무 앱과 워크플로를 구성하는 개발 플랫폼이다.
> 2. **가치**: 단순 업무 앱의 개발 리드타임을 8주에서 2주 수준으로 줄이고, IT는 표준 커넥터와 권한 정책을 통제한다.
> 3. **판단 포인트**: 업무 복잡도, 사용자 수, 데이터 민감도, 커스텀 코드 비율, 벤더 종속성을 기준으로 적용 범위를 정한다.

## 출제 의도 및 답안 포인트

| 출제 의도 | 반드시 짚을 핵심 | 감점 회피 포인트 |
|:---|:---|:---|
| 플랫폼 개발 방식 이해 확인 | 모델러, 워크플로, 커넥터, 권한, 배포 | 화면 제작 도구 설명으로 축소 |
| 현업 개발 거버넌스 확인 | Citizen Developer, 승인, 표준 템플릿 | 무통제 Shadow IT 누락 |
| 적용 판단 확인 | 단순 앱 vs 복잡 트랜잭션, 벤더 종속 | 모든 시스템 대체 가능으로 서술 |

> 요약: 이 문제는 빠른 개발보다 통제된 현업 참여와 적용 경계 설정을 요구한다.

## Ⅰ. 개요 및 필요성

- 개요: Low-Code·No-Code는 시각적 조립 방식 앱 개발 플랫폼이다.
- 배경: 현업 요구 증가와 개발 인력 부족으로 단순 업무 앱의 개발 대기 시간이 커지고 있다.
- 필요성: 표준 컴포넌트, 권한, 배포 승인, 데이터 접근 정책으로 현업 개발과 IT 통제를 함께 적용해야 한다.

---

## Ⅱ. 구조 및 구성요소

```text
Business Requirement -> Visual Modeler -> Data Model/Workflow
                     -> Connector/API -> Security/Policy -> App Release
```

| 구성요소 | 역할 | 특이사항 |
|:---|:---|:---|
| 시각 모델러 | 화면, 폼, 로직을 선언형으로 구성 | 복잡 알고리즘은 한계 |
| 워크플로 엔진 | 승인, 알림, 상태 전이를 처리 | SLA와 예외 경로 정의 |
| 커넥터/API | ERP, CRM, DB, SaaS 연계 | API 사용량과 권한 통제 |
| 거버넌스 계층 | 템플릿, 배포 승인, 접근권한 관리 | 앱 소유자 등록 필요 |

> 요약: 플랫폼은 화면 조립뿐 아니라 데이터, 워크플로, 연계, 정책 계층으로 구성된다.

## Ⅲ. 동작원리 및 흐름도

```text
요구사항 접수 -> 앱 모델링 -> 데이터/권한 설정 -> 커넥터 연결
-> 테스트/승인 -> 배포 -> 사용량·오류 모니터링
```

| 단계 | 처리 내용 | 검증 기준 |
|:---:|:---|:---|
| 1 | 업무 요구와 데이터 등급 식별 | 개인정보·중요정보 분류 |
| 2 | 화면·흐름·권한 모델링 | 역할 기반 접근통제 적용 |
| 3 | 테스트와 배포 승인 | 핵심 시나리오 20건 이상 검증 |
| 4 | 운영 모니터링 | 오류율, API 호출량, 앱 소유자 점검 |

> 요약: Low-Code·No-Code는 모델링 후 배포 승인과 운영 모니터링까지 포함해야 한다.

## Ⅵ. 실무 적용 및 결론

**적용 방안 3개 (필수 - 단계별 또는 항목별):**
1. 대상 선정: CRUD, 승인, 조회, 대시보드 업무를 1차 범위로 두고 핵심 거래·대량 배치 업무는 제외
2. 거버넌스 수립: 앱 소유자, 데이터 등급, 배포 승인, RBAC, 감사 로그를 플랫폼 표준으로 강제
3. 운영 전환: 사용량, 오류율, 커스텀 코드 비율 20% 초과 앱은 전문 개발 또는 API 기반 재구축 후보로 전환

**결론 (2줄):**
- 기술사 판단: 현업 단순 앱은 Low-Code·No-Code, 핵심 업무와 복잡 트랜잭션은 전통 개발 또는 하이브리드 개발을 선택함
- 향후 방향: 플랫폼은 AI 코드 생성, 업무 프로세스 마이닝, API 관리와 결합해 기업 앱 공급 체계로 발전함
