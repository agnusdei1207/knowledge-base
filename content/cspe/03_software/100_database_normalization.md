## 미리 알고가기

- 정규화는 데이터 중복과 이상 현상을 줄이기 위해 테이블 구조를 분해하는 설계 원칙임
- 1NF에서 BCNF로 갈수록 함수 종속성과 결정자 조건을 더 엄격히 다룸
- 지나친 정규화는 조회 조인 비용을 높일 수 있음

## Ⅰ. 개요

- **정의/개념**: 데이터베이스 정규화는 함수 종속성과 키 구조를 기준으로 테이블을 단계적으로 분해해 중복 저장과 삽입·삭제·갱신 이상을 줄이고 데이터 의미를 안정적으로 유지하는 논리 설계 기법임
- **배경/필요성**: 초기 설계에서 편의상 한 테이블에 많은 속성을 몰아넣으면 데이터 불일치와 수정 비용이 커지므로, 구조적 중복을 제거하는 기준이 필요함

## Ⅱ. 특징

- 중복 최소화와 무결성 향상에 유리함
- 함수 종속성을 기준으로 설계 오류를 체계적으로 교정함
- 업무 규칙이 명확할수록 정규화 품질이 높아짐
- 과도한 분해는 조인 증가와 조회 복잡도 상승을 초래할 수 있음

## Ⅲ. 종류 및 비교

| 판단 기준 | 1NF | 2NF | 3NF | BCNF |
|:---|:---|:---|:---|:---|
| 핵심 조건 | 원자값 보장 | 부분 함수 종속 제거 | 이행 함수 종속 제거 | 모든 결정자가 후보키 |
| 개선 효과 | 반복 속성 제거 | 복합키 중복 감소 | 비키 속성 종속 정리 | 더 강한 결정자 통제 |
| 설계 난이도 | 낮음 | 중간 | 중간 | 상대적으로 높음 |
| 적용 포인트 | 기본 구조 정리 | 복합키 테이블 | 일반 업무 DB | 고급 무결성 요구 |

## Ⅳ. 구성요소 및 구조

| 구성요소 | 설명 |
|:---|:---|
| Functional Dependency | 어떤 속성이 다른 속성을 결정하는지 밝혀 분해 기준을 만든다 |
| Candidate Key | 튜플을 식별하는 최소 속성 집합으로 정규화 판단의 기준이 된다 |
| Decomposition Rule | 종속 위반을 제거하도록 테이블을 나누어 중복을 줄인다 |
| Validation Step | 무손실 분해와 종속 보존 여부를 확인해 설계 품질을 보장한다 |

## Ⅴ. 원리 및 절차 흐름도

```text
+-------------+     +-------------+     +-------------+     +-------------+
| 종속성 파악    | --> | 위반 형태 식별  | --> | 테이블 분해    | --> | 무손실 검증     |
+-------------+     +-------------+     +-------------+     +-------------+
```

1. **종속성 파악**: 속성 간 결정 관계를 정리함
2. **위반 형태 식별**: 부분 종속과 이행 종속 여부를 판정함
3. **테이블 분해**: 단계별 정규형 기준에 맞게 나눔
4. **무손실 검증**: 정보 손실과 종속 보존 문제를 점검함

## Ⅵ. 문제점 및 해결 방안

1. 문제: 업무 규칙 분석 없이 형식적으로만 정규화하면 실제 종속성이 반영되지 않아 중복과 무결성 문제가 남을 수 있음
   - 해결방안: domain rule workshop을 병행하고 dependency completeness와 anomaly recurrence rate로 검증함
2. 문제: 높은 정규형만 추구하면 조회 조인이 과도해져 운영 성능이 크게 떨어질 수 있음
   - 해결방안: workload 기반 정규화 수준을 선택하고 join depth와 critical query latency로 검증함
3. 문제: 분해 후 키와 관계를 명확히 관리하지 않으면 애플리케이션 매핑 복잡도가 급증할 수 있음
   - 해결방안: schema documentation과 ORM mapping review를 수행하고 mapping defect count와 schema comprehension score로 검증함

## Ⅶ. 적용 사례

- 공공 업무 DB 설계에서는 종속성 워크숍을 수행하고 확인 지표는 dependency completeness와 anomaly recurrence rate임
- 전자상거래 조회 중심 DB에서는 정규화 수준을 조정하고 확인 지표는 join depth와 critical query latency임
- SaaS 개발팀에서는 스키마 문서를 관리하고 확인 지표는 mapping defect count와 schema comprehension score임

## Ⅷ. 결론

정규화의 목적은 표준 단계를 외우는 데 있지 않고 데이터 중복과 이상 현상을 줄이면서도 실제 조회 특성에 맞는 구조 균형을 잡는 데 있음.
