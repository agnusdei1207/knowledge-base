# 📖 【암기용】 개념 완전 이해

## 한눈에
- **개요**: 관계형 데이터베이스에서 데이터 중복을 최소화하고 이상 현상(Anomaly)을 방지하기 위해 릴레이션(테이블)을 분해하는 수학적 과정
- **왜 필요한가**: 하나의 큰 테이블에 모든 정보를 때려 넣으면(예: 학생+수강과목+학과정보), 1명이 과목을 3개 들으면 이름과 학과정보가 3번 중복 저장된다. 나중에 학과이름이 바뀌면 3개를 다 찾아서 고쳐야 하는 끔찍한 이상(Anomaly)이 생긴다.
- **핵심 직관**: "한 테이블에는 하나의 주제(Entity)만 담는다." 비대한 덩어리를 쪼개어 날씬하고 중복 없는 테이블 여러 개로 만드는 과정.

## 핵심 용어 정리

| 용어/표기 | 의미 | 비유·예 |
|:---|:---|:---|
| 정규화 (Normalization) | 테이블 구조를 단계별 규칙(NF)에 따라 분해하는 과정 | 뒤섞인 서랍을 칸막이 쳐서 정리하기 |
| 함수적 종속 (FD, Functional Dependency) | X값을 알면 Y값이 무조건 하나로 결정되는 관계 (X -> Y) | '학번'을 알면 '이름'이 정해짐 |
| 이상 현상 (Anomaly) | 중복 때문에 발생하는 삽입/수정/삭제 오류 | 정보가 꼬여서 삭제 시 원치 않는 정보도 날아감 |

## 깊이 이해
- **배경·문제의식**: RDBMS 설계 초기에 개발자가 편의상 거대한 테이블 1개를 만들면, 데이터가 쌓일수록 갱신 이상(Update Anomaly)이 터져 데이터 정합성이 붕괴된다. 이를 설계 시점부터 예방할 과학적 규칙이 필요했다.
- **작동 원리 (정규화 단계 - 도부이결다조)**: 
  - **1NF (제1정규형)**: 모든 속성은 원자값(쪼갤 수 없는 단일 값)이어야 한다. [도메인 원자값]
  - **2NF (제2정규형)**: 부분 함수적 종속 제거. 기본키의 일부에만 종속된 일반 속성을 떼어낸다. (복합키일 때만 발생)
  - **3NF (제3정규형)**: 이행적 함수 종속 제거. (X->Y, Y->Z일 때 X->Z가 되는 관계 끊기). 즉, 일반 속성끼리 종속된 걸 떼어낸다.
  - **BCNF (보이스-코드 정규형)**: 모든 결정자는 후보키여야 한다. 후보키가 아닌 녀석이 기본키의 일부를 결정하는 기형적 관계를 끊는다.
- **비유**: '주소' 필드에 "서울시 강남구 역삼동"을 다 쓰면(원자값 위배, 1NF). 주문 테이블에 고객 등급까지 넣으면 고객 테이블로 분리(3NF).
- **흔한 오해·주의점**: "무조건 BCNF, 5NF까지 쪼개는 게 최고다?" 아니다. 너무 쪼개면 조회할 때마다 JOIN(결합)을 엄청나게 해야 해서 성능이 폭락한다. 실무에서는 보통 3NF까지만 하고, 필요하면 오히려 거꾸로 합치는 '반정규화'를 한다.

## 연결 개념
- **이상 현상 (Anomaly)**: 정규화를 하지 않았을 때 터지는 에러들 (102 키워드)
- **반정규화 (Denormalization)**: 정규화로 인해 쪼개진 테이블을 성능 때문에 다시 합치는 타협 (101 키워드)

# 📝 【답안용】 시험 답안 템플릿

## 핵심 인사이트 (3줄 요약)

> 1. **본질**: 데이터베이스 정규화는 함수적 종속성(Functional Dependency) 원리를 기반으로 릴레이션의 중복을 제거하여 이상 현상(Anomaly)을 방지하는 논리적 분해 과정이다.
> 2. **가치**: 데이터 쓰기(Insert/Update/Delete) 시 정합성 위배와 무결성 붕괴를 원천적으로 차단하여 시스템의 데이터 신뢰도를 보장한다.
> 3. **판단 포인트**: 정규화는 쓰기 성능과 무결성을 높이나 과도한 분해는 읽기(Join) 연산 부하를 유발하므로, 성능 요건(SLA)에 따라 반정규화(Denormalization)와의 균형(Trade-off) 설계가 핵심이다.

## 출제 의도 및 답안 포인트

| 출제 의도 | 반드시 짚을 핵심 | 감점 회피 포인트 |
|:---|:---|:---|
| 정규화의 목적과 단계별 수학적 원리 이해 | 1NF~BCNF 각 단계별 제거하는 대상(함수적 종속성 조건) 명시 | 각 NF의 제거 조건을 혼동(예: 2NF와 3NF 원리 뒤바뀜) |
| 설계 시 트레이드오프 판단 역량 | 무결성(정규화) vs 성능(JOIN 부하) 간의 트레이드오프 언급 | 정규화를 완벽한 해답으로만 기술하고 부작용을 누락 |

> 요약: 정규화 단계(1NF~BCNF)의 조건을 함수 종속 관점에서 정확히 기술하고, 이로 인한 '조인 성능 저하' 리스크를 짚어주어야 한다.

---

## Ⅰ. 개요 및 필요성

- 개요: 데이터베이스 정규화(Normalization)는 릴레이션 내 데이터 중복을 최소화하고 갱신 이상(Anomaly)을 방지하기 위해 속성 간의 함수적 종속성(FD)을 분석하여 릴레이션을 무손실 분해하는 과정임
- 배경: 비정규화된 단일 거대 테이블 운영 시, 데이터 갱신 과정에서 삽입/삭제/수정 이상 현상이 빈번하게 발생하여 데이터 무결성이 심각하게 훼손됨
- 필요성: 스키마 설계 단계에서 각 엔티티(Entity)가 하나의 독립적 주제만 포함하도록 강제하여 데이터 정합성 유지 비용을 최소화하기 위해 필수적임

---

## Ⅱ. 구조 및 구성요소 (정규화 단계의 함수 종속)

```text
비정규 릴레이션 -> [도메인 원자성] -> 1NF -> [부분 함수 종속 제거] -> 2NF
               -> [이행 함수 종속 제거] -> 3NF -> [결정자 중 후보키 아닌 것 제거] -> BCNF
```

| 정규형 | 분해/제거 조건 (함수적 종속) | 비즈니스 예시 (해결 내용) |
|:---|:---|:---|
| 1NF | 모든 속성의 도메인이 쪼갤 수 없는 원자값(Atomic) | '전화번호' 컬럼에 번호 2개 입력 금지 |
| 2NF | 기본키가 복합키일 때, 일부 기본키에만 종속된 속성 분리 | (학번, 과목) PK 중 과목명은 과목코드에만 종속되므로 분리 |
| 3NF | 기본키가 아닌 일반 속성 간의 이행적 종속 (X->Y, Y->Z) 제거 | 주문 테이블에서 '고객번호'로 '고객등급'을 유추하는 관계 분리 |
| BCNF | 모든 결정자(Determinant)는 반드시 후보키여야 함 | 일반 속성(교수)이 기본키 일부(수강과목)를 결정하는 기형 분리 |

> 요약: 각 정규형은 부분 종속(2NF), 이행 종속(3NF), 비후보키 결정자(BCNF)라는 구체적인 불완전 종속 구조를 제거하며 단계를 높여간다.

---

## Ⅲ. 동작원리 및 흐름도 (무손실 분해 절차)

```text
스키마 분석 -> 이상 현상 유발 속성 식별 -> 기준 테이블(PK 유지)과 신규 테이블(PK-FK 매핑)로 분해
-> 분해 후 조인 테스트 -> 무손실 조인(Lossless Join) 확인 -> 릴레이션 확정
```

- 1단계 [종속성 식별]: 릴레이션 내 모든 속성 간의 함수적 종속 다이어그램(FD Diagram)을 그려 종속 관계 파악
- 2단계 [분해(Decomposition)]: 정규화 규칙 위반 속성 발견 시, 해당 속성과 결정자를 묶어 새로운 릴레이션으로 쪼개고 외래키(FK)로 연결
- 3단계 [무손실 검증]: 쪼개진 두 릴레이션을 Natural Join 했을 때 원래의 릴레이션과 동일한 튜플을 복원할 수 있는지(Lossless Join) 검증
- 4단계 [종속성 보존]: 분해 후에도 본래의 릴레이션이 가지고 있던 함수적 종속성이 새로운 릴레이션들에 그대로 유지되는지 확인

> 요약: 단순 분해가 목적이 아니라, 원래 데이터를 조인으로 100% 복원 가능(무손실)하게 분해하는 것이 정규화 알고리즘의 핵심이다.

---

## Ⅳ. 특징

- 무결성(Integrity) 극대화: 1 Fact 1 Place (한 사실은 한 곳에만 저장) 원칙에 따라, 데이터 수정 시 1곳만 갱신하므로 이상 현상 원천 차단
- 스토리지 최적화: 불필요한 중복 저장이 제거되므로 디스크 공간 낭비 방지 및 캐시 메모리 효율화
- 조인 페널티: 분해된 릴레이션을 조회할 때마다 다중 조인(Multi-Join) 연산이 강제되어 CPU와 메모리 오버헤드(I/O 부하) 유발

---

## Ⅴ. 심화 비교 및 적용 판단

| 비교 축 | 비정규화 스키마 | 정규화 스키마 (3NF 기준) | 선택 기준 |
|:---|:---|:---|:---|
| 데이터 정합성 | 낮음 (이상 현상 빈발) | 높음 (무결성 보장) | 데이터 신뢰도 요구 수준 |
| 쿼리 성능 | 단순 조회(SELECT) 우수 | 쓰기(INSERT/UPDATE) 우수, 조회 저하 | Read/Write 연산 비율 |
| 스키마 유연성 | 경직됨 (변경 시 대규모 마이그레이션) | 유연함 (독립 개체별 분리) | 시스템 수명주기 |

> 요약: 정규화는 OLTP(온라인 트랜잭션) 환경의 쓰기 성능과 무결성에 최적화되어 있으나, OLAP(분석/집계) 환경에서는 독이 될 수 있다.

**리스크·대응 (기본은 불릿):**
- 과도한 정규화(Over-normalization): BCNF, 4NF, 5NF까지 진행 시 5~6개 테이블 조인으로 응답시간 SLA 초과 → 3NF 수준으로 타협하고 성능 병목 구간만 반정규화(Denormalization) 수행
- 분해 시 정보 손실(Lossy Join): 잘못된 식별자로 릴레이션을 쪼개어 복원 시 가짜 튜플 생성 → 무손실 분해 원칙에 따라 조인 속성이 분해된 어느 한쪽의 기본키(또는 후보키)인지 반드시 검증

## Ⅵ. 실무 적용 및 결론

**적용 방안 3개:**
1. 논리 모델링 3NF 원칙: 개념/논리 모델링 단계에서는 성능을 고려하지 않고 순수 업무 규칙에 따라 무조건 3NF(또는 BCNF)까지 정규화를 완료하여 스키마 기초를 확립
2. 선택적 반정규화: 물리 모델링 단계에서 APM(애플리케이션 성능 모니터링) 부하 테스트 결과, 특정 테이블 조인이 CPU 부하의 60%를 차지할 경우 파생 컬럼 추가 형태의 반정규화 부분 적용
3. 조인 성능 튜닝 인프라: 정규화된 스키마의 조인 부하를 극복하기 위해 복합 인덱스(Composite Index) 설계 및 쿼리 캐시(Redis), 뷰(Materialized View) 적극 활용

**결론 (2줄):**
- 기술사 판단: 정규화는 데이터 무결성을 지키는 가장 강력한 방어선이므로, 성능을 핑계로 초기부터 정규화를 포기하는 것은 기술 부채를 급증시키는 행위이다
- 향후 방향: 최근 NoSQL이나 데이터 웨어하우스(DW) 환경에서는 오히려 조인을 없애기 위해 비정규화(Denormalization) 상태를 기본 스키마(예: Star Schema)로 설계하는 추세이다
