# 📖 【암기용】 개념 완전 이해

> 목적: 데이터베이스 정규화를 처음 보는 사람도 함수 종속, 1NF·2NF·3NF·BCNF, 반정규화의 관계를 이해하게 만든다. 시험 답안 양식이 아니라, 이해를 위한 설명이다.

## 한눈에
- **개요**: 데이터베이스 정규화(Normalization)는 **함수 종속**(Functional Dependency)을 분석해 릴레이션을 여러 개로 분해함으로써 데이터 중복과 **이상현상**(Anomaly)을 줄이는 관계형 데이터베이스 설계 절차이다.
- **왜 필요한가**: 한 테이블에 성격이 다른 사실(학생 정보, 부서 정보 등)을 섞어 저장하면, 같은 값이 여러 행에 반복되어 변경할 때마다 모든 행을 함께 고쳐야 하고, 일부만 고치면 데이터가 모순된다(102 이상현상 참고). 정규화는 "한 사실은 한 곳에만 저장한다"는 원칙으로 이를 막는다.
- **핵심 직관**: 회사 인사 시스템에서 부서명을 사원 표마다 적지 않고, 부서 표에 한 번만 적은 뒤 사원 표에는 부서코드만 적어 연결하는 방식이다.

## 핵심 용어 정리

| 용어 | 의미 | 비유 |
|:---|:---|:---|
| 함수 종속(Functional Dependency, FD) | 속성 X 값이 정해지면 속성 Y 값이 하나로 결정되는 관계. `X → Y`로 표기하고 X를 결정자, Y를 종속자라 함 | "학번을 알면 학생명이 하나로 정해진다" |
| 후보키(Candidate Key) | 릴레이션의 모든 속성을 함수적으로 결정하는 최소 속성 집합. 한 릴레이션에 여러 개 있을 수 있음 | 문을 열 수 있는 여러 벌의 예비 열쇠 |
| 기본키(Primary Key) | 여러 후보키 중 대표로 선택해 실제로 사용하는 키 | 예비 열쇠 중 평소 쓰는 열쇠 1개 |
| 완전 함수 종속 | 복합키 전체에 종속되어, 키의 일부만으로는 결정되지 않는 관계 | 자물쇠 2개를 다 맞춰야 열림 |
| 부분 함수 종속 | 복합키의 일부에만 종속되는 관계(2NF가 제거 대상) | 자물쇠 2개 중 1개만 맞아도 열림 |
| 이행 함수 종속 | `A→B`이고 `B→C`이면 성립하는 `A→C`처럼, 비키 속성을 거쳐 간접적으로 성립하는 종속(3NF가 제거 대상) | "반 배정을 알면 담임을 알고, 담임을 알면 교무실 위치를 안다" |
| 1NF(제1정규형) | 모든 속성값이 더는 나눌 수 없는 원자값인 상태 | 한 칸에 값 1개만 |
| 2NF(제2정규형) | 1NF를 만족하고, 부분 함수 종속을 제거한 상태 | 열쇠 일부만으로 열리는 자물쇠 제거 |
| 3NF(제3정규형) | 2NF를 만족하고, 이행 함수 종속을 제거한 상태 | 간접 연결 고리 끊기 |
| BCNF(보이스-코드 정규형) | 모든 결정자가 후보키인 상태(3NF보다 엄격) | 결정권자는 반드시 대표 열쇠를 가진 사람이어야 함 |
| 무손실 분해(Lossless-Join Decomposition) | 분해한 릴레이션들을 다시 조인하면 원본과 정확히 같아지는 분해 | 퍼즐을 나눴다 맞춰도 원본 그림과 똑같음 |
| 종속성 보존(Dependency Preservation) | 분해 후에도 원래의 함수 종속을 조인 없이 각 테이블 안에서 검증할 수 있는 성질 | 원본 규칙이 조각난 뒤에도 각 조각에서 확인 가능 |

## 깊이 이해

### 정규화 절차를 숫자로 따라가기 — 1NF → 2NF → 3NF
5,000개 수강 기록을 담은 `수강(학번, 과목코드, 성적, 학생명, 학과, 학과사무실)` 테이블을 생각하자. 기본키는 (학번, 과목코드)인 복합키다. FD를 분석하면 다음과 같다.
- `(학번, 과목코드) → 성적` : 완전 함수 종속(두 값을 다 알아야 성적이 정해짐)
- `학번 → 학생명, 학과` : 부분 함수 종속(복합키 중 학번만으로 정해짐 — 2NF 위반)
- `학과 → 학과사무실` : 이행 함수 종속(학번 → 학과 → 학과사무실, 비키 속성을 거쳐 결정됨 — 3NF 위반)

이 테이블은 이미 원자값만 가지므로 1NF는 만족한다. 2NF를 적용하면 부분 종속인 학생명·학과를 `학생(학번, 학생명, 학과)`으로 분리하고, 수강 테이블은 `수강(학번, 과목코드, 성적)`만 남는다. 3NF를 적용하면 이행 종속인 학과사무실을 다시 `학과(학과, 학과사무실)`로 분리한다.

수치로 보면 효과가 뚜렷하다. 5,000행짜리 원본에서 800명 학생이 평균 6.25과목을 들었다면, 정규화 전에는 학과사무실 값이 학생 수만큼(최대 5,000번) 반복 저장될 수 있다. 정규화 후에는 학과 수만큼만(예: 30개 학과면 30번) 저장된다. 학과사무실이 이전되면 정규화 후에는 UPDATE 1건이면 되지만, 정규화 전에는 그 학과 소속 모든 수강 행(수백~수천 건)을 찾아 고쳐야 한다.

### BCNF가 3NF보다 엄격한 이유 — 반례로 이해
3NF는 통과하지만 BCNF는 위반하는 경우가 실제로 있다. `수강지도(학생, 과목, 교수)`에서 "한 학생이 한 과목을 들으면 특정 교수가 지도한다"(`(학생,과목) → 교수`)이고, 동시에 "한 교수는 오직 한 과목만 담당한다"(`교수 → 과목`)는 업무 규칙이 있다고 하자. 후보키는 (학생, 과목)과 (학생, 교수) 둘 다 될 수 있다. 여기서 `교수 → 과목`은 결정자(교수)가 후보키가 아니므로 BCNF를 위반한다. 하지만 3NF는 "종속자(과목)가 어떤 후보키에도 속하는 속성(prime attribute)이면 이행 종속이어도 봐준다"는 예외 조항이 있어 통과한다. 이런 드문 케이스가 실무에서 나타나면 `교수담당(교수, 과목)`과 `수강지도(학생, 교수)`로 한 번 더 쪼개 BCNF까지 맞춘다.

### 무손실 분해와 종속성 보존을 함께 확인해야 하는 이유
테이블을 잘못 분해하면 조인했을 때 원본에 없던 행이 생기거나(무손실 분해 실패), 원래 있던 제약을 어느 테이블에서도 검증할 수 없게 된다(종속성 보존 실패). 예를 들어 `수강(학번, 과목코드, 성적)`과 `학생(학번, 학생명, 학과)`으로 나누면 공통 속성 학번이 어느 한쪽의 키이므로 무손실 분해가 보장된다. 반면 공통 속성이 후보키가 아닌 방식으로 잘못 나누면, 조인 시 원본에 없던 조합 행(허위 행, spurious tuple)이 생길 수 있다. 실무에서는 chase test 또는 마이그레이션 전후 row count·checksum 비교로 이를 검증한다.

## 연결 개념
- 함수 종속(FD) — 정규형 판단의 기준이 되는 핵심 개념
- 이상현상(102) — 정규화하지 않았을 때 실제로 겪는 문제
- 반정규화(101) — 정규화를 마친 뒤 읽기 성능을 위해 되돌리는 의도적 중복 설계

# 📝 【답안용】 시험 답안 템플릿

> 핵심: 정규화 답안은 1NF~BCNF 순서 암기가 아니라 중복 원인과 분해 기준을 제시해야 한다.

## 핵심 인사이트 (3줄 요약)

> 2. **가치**: 한 사실을 한 장소에 저장해 중복 갱신과 참조 불일치를 감소시키며, PK/FK 기반 무결성을 만든다.
> 3. **판단 포인트**: 정규형 단계, 무손실 분해, 종속성 보존, Join 비용, 반정규화 조건을 함께 판단한다.

## Ⅰ. 개요 및 필요성

- 정의: 함수 종속을 분석해 릴레이션을 분해함으로써 중복을 줄이는 설계 절차
- 배경: 업무 사실이 여러 행에 반복되면 삽입·수정·삭제 이상이 발생함
- 필요성: 테이블을 분해하고 키 기반 참조로 연결하면 데이터 정합성을 DB 스키마에 반영 가능

---

## Ⅱ. 구조 및 구성요소

```text
업무 속성 수집 -> 함수 종속 분석
-> 1NF 원자값 -> 2NF 부분 종속 제거
-> 3NF 이행 종속 제거 -> BCNF 결정자 후보키화
-> PK/FK 연결 -> 무손실 분해 검증
```

| 구성요소 | 역할 | 판단 포인트 |
|:---|:---|:---|
| 함수 종속 | 속성 간 결정 관계 표현 | `X -> Y`, 후보키 도출 |
| 1NF | 반복 그룹 제거와 원자값 보장 | 다중값 컬럼 분리 |
| 2NF | 복합키 일부에만 종속된 속성을 별도 테이블로 분리 | 부분 종속 제거 |
| 3NF | 비키 속성 간 이행 종속 관계를 분해하여 제거 | `A -> B -> C` 분리 |
| BCNF | 모든 결정자를 후보키로 제한 | 3NF보다 엄격한 분해 |
> 요약: 정규화는 함수 종속을 기준으로 반복·부분·이행 종속을 차례로 제거하는 구조화 절차이다.

---

## Ⅲ. 동작원리 및 흐름도

```text
Relation R 분석 -> Candidate Key 식별
-> Functional Dependency 목록화
-> Normal Form 위반 탐지
-> Decompose Relation -> Lossless Join / Dependency Preservation 검증
```

| 단계 | 처리 내용 | 검증 기준 |
|:---:|:---|:---|
| 1 | 속성·후보키·기본키 식별 | 후보키 1개 이상 |
| 2 | 함수 종속과 다치 종속 분석 | FD 목록 완성 |
| 3 | 정규형 위반 판단 | 1NF~BCNF 조건 충족 여부 |
| 4 | 테이블 분해와 PK/FK 설계 | 무손실 조인 가능 |
| 5 | 성능 요구에 따라 반정규화 검토 | p95 지연, Join 수, 중복률 |
> 요약: 정규화는 키와 함수 종속을 먼저 찾고, 분해 후 무손실성과 종속성 보존을 검증한다.

## Ⅳ. 특징

| 구분 | 비정규 설계 | 정규화 설계 | 정량·판단 기준 |
|:---|:---|:---|:---|
| 중복 | 같은 사실 반복 저장 | 한 사실 한 위치 저장 | 중복 컬럼 수, 중복률 |
| 갱신 이상 | 일부 행만 변경 가능 | PK/FK로 변경 대상 명확 | 불일치 건수 0건 |
| 조회 비용 | 단일 테이블 조회 | Join 필요 | Join 수, p95 지연 |

> 요약: 정규화는 중복과 이상현상을 줄이지만 조회 Join 비용이 증가할 수 있어 성능 요구와 함께 판단한다.

## Ⅴ. 심화 비교 및 적용 판단

| 구분 | 기존/대안 | 본 키워드 | 선택 기준 |
|:---|:---|:---|:---|
| 구조 | 비정규 단일 테이블 | 3NF/BCNF 분해 | 갱신 빈도와 정합성 요구 |
| 비용/성능 | Join 감소, 중복 증가 | 중복 감소, Join 증가 | p95 200ms, 저장 중복률 10% 이하 |
| 운영/위험 | 갱신 이상 | 반정규화 관리 필요 | 정합성 오류 비용 vs 조회 비용 |
> 요약: 갱신 정합성이 우선이면 3NF 이상, 읽기 지연이 우선이면 통제된 반정규화를 선택한다.

| 리스크 | 원인 | 대응 방안 | 확인 지표 |
|:---|:---|:---|:---|
| 과도한 Join | 세분화된 분해 | 조회 패턴 기반 반정규화 | p95 query latency |
| 종속성 손실 | 분해 후 FD 검증 부족 | Dependency Preservation 검사 | FD 위반 테스트 0건 |
| 중복 재발 | 반정규화 컬럼 관리 부재 | Trigger, Materialized View, CDC | 불일치 건수 |
> 요약: 정규화 리스크는 Join 비용, 종속성 손실, 반정규화 불일치이며 검증과 동기화 장치로 통제한다.

| 점검 항목 | 목표 기준 | 측정 방법 |
|:---|:---|:---|
| 정규형 | 주요 OLTP 테이블 3NF 이상 | 스키마 리뷰, FD 분석 |
| 무결성 | PK/FK 위반 0건 | 제약조건 검사 |
| 조회 성능 | 주요 SQL p95 200ms 이하 | EXPLAIN ANALYZE, APM |
> 요약: 정규화 성공 여부는 정규형 충족, 제약조건 위반, 주요 SQL 지연으로 판단한다.

## Ⅵ. 실무 적용 및 결론

**적용 방안 3개:**
1. 설계 단계: ERD 작성 후 함수 종속 표를 만들고 주요 OLTP 테이블은 3NF 이상, 후보키·PK·FK를 DDL에 반영함
2. 검증 단계: 분해 테이블에 대해 무손실 조인과 종속성 보존을 확인하고 FK 위반 0건을 CI 데이터 테스트에 포함함
3. 반정규화 단계: p95 200ms 초과 Join 쿼리에 한해 Materialized View, 요약 테이블, 캐시를 적용하고 불일치 건수 0건을 모니터링함

**결론 (2줄):**
- 기술사 판단: 갱신 중심 OLTP는 3NF/BCNF를 기본으로 하고, 조회 병목은 통제된 반정규화로 해결함
- 향후 방향: 데이터 모델링은 정규화 원칙에 CDC·Materialized View·캐시 무효화를 결합해 정합성과 조회 성능을 함께 관리하는 방향임
