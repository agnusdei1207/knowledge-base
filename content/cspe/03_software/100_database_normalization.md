## 미리 알고가기

- 정규화는 한 테이블에 섞인 사실을 나누어 중복과 이상 현상을 줄이는 설계 원칙임
- 함수 종속성은 어떤 속성 값이 다른 속성 값을 결정하는 관계를 뜻함
- BCNF는 모든 결정자가 후보키가 되도록 요구하는 더 엄격한 정규형임

## Ⅰ. 개요

- **정의/개념**: 데이터베이스 정규화는 함수 종속성과 키 구조를 기준으로 테이블을 단계적으로 분해해 데이터 중복과 삽입·삭제·갱신 이상을 줄이고 각 테이블이 한 가지 의미를 분명하게 갖게 하는 논리 설계 기법임.
- **배경/필요성**: 업무 항목을 한 테이블에 몰아넣으면 같은 사실을 여러 행에 반복 저장하게 되어 수정 누락과 정보 손실이 생기므로, 구조적으로 중복을 줄이는 기준이 필요함.

## Ⅱ. 특징

- 데이터 중복을 줄여 갱신 누락과 삭제에 따른 정보 손실을 예방함
- 함수 종속성을 기준으로 설계 오류를 설명하고 수정할 수 있음
- 업무 규칙과 후보키가 명확할수록 정규화 품질이 높아짐
- 분해가 지나치면 조회 조인 수가 늘어 물리 설계 보완이 필요할 수 있음

## Ⅲ. 종류 및 비교

| 판단 기준 | 1NF | 2NF | 3NF | BCNF |
|:---|:---|:---|:---|:---|
| 핵심 조건 | 컬럼 값이 더 쪼갤 수 없는 원자값이어야 함 | 복합키의 일부에만 의존하는 속성을 분리함 | 비키 속성이 다른 비키 속성에 의존하지 않게 함 | 후보키가 아닌 결정자를 허용하지 않음 |
| 줄이는 문제 | 반복 속성과 다중 값 저장 | 복합키 기반 중복 | 이행 종속에 따른 중복 | 숨은 결정자 때문에 남는 이상 현상 |
| 보통 적용 범위 | 기본 테이블 정리의 출발점 | 복합 기본키 테이블 | 일반 업무 데이터 모델의 기본 목표 | 규칙이 복잡한 고급 설계 |
| 유의점 | 값 분리만으로 충분하지 않음 | 후보키를 정확히 알아야 함 | 업무 규칙을 잘못 이해하면 의미가 깨질 수 있음 | 분해 후 조인 부담을 함께 검토해야 함 |

## Ⅳ. 구성요소 및 구조

| 구성요소 | 설명 |
|:---|:---|
| 함수 종속성 | 어떤 속성이 다른 속성을 결정하는지 밝혀 분해 기준을 만듦 |
| 후보키 | 각 행을 유일하게 식별하는 최소 속성 집합으로 정규화 판단의 기준이 됨 |
| 분해 규칙 | 부분 종속과 이행 종속과 결정자 문제를 제거하도록 테이블을 나눔 |
| 검증 절차 | 무손실 분해와 종속 보존 여부를 확인해 설계가 의미를 유지하는지 점검함 |

## Ⅴ. 원리 및 절차 흐름도

```text
+-------------+     +-------------+     +-------------+     +-------------+
| 종속성 파악    | --> | 위반 형태 식별  | --> | 테이블 분해    | --> | 무손실 검증     |
+-------------+     +-------------+     +-------------+     +-------------+
```

1. **종속성 파악**: 어떤 속성이 어떤 속성에 의존하는지 정리함
2. **위반 형태 식별**: 부분 종속과 이행 종속과 결정자 문제를 구분함
3. **테이블 분해**: 단계별 정규형 기준에 맞춰 속성을 분리함
4. **무손실 검증**: 분해 뒤에도 원래 의미와 관계를 복원할 수 있는지 확인함

## Ⅵ. 실무 적용 및 유의점

1. 신규 업무 DB를 설계할 때는 먼저 정규화로 중복과 이상 현상을 줄이되 업무 규칙을 잘못 읽으면 분해가 틀어지므로 함수 종속성 목록을 검토하고 이상 현상 재발 건수와 후보키 정의 완전성으로 확인함.
2. 조회 비중이 큰 서비스에서는 정규화 후에도 조인 비용이 과하면 반정규화를 별도로 검토하되 기본 모델은 유지하고 핵심 조회 지연 시간과 조인 깊이로 확인함.

## Ⅶ. 결론

정규화는 단계 이름을 외우는 절차가 아니라 데이터 의미를 분리해 이상 현상을 줄이고 이후 성능 최적화의 기준점을 만드는 논리 설계 작업임.
