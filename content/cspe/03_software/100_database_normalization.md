## 미리 알고가기

- 정규화는 한 테이블에 섞인 사실을 나누어 중복과 이상 현상을 줄이는 설계 원칙임
- 함수 종속성은 어떤 속성 값이 다른 속성 값을 결정하는 관계를 뜻함
- BCNF는 모든 결정자가 후보키가 되도록 요구하는 더 엄격한 정규형임

## 작성 근거(검토용)

- 제목·frontmatter·미리 알고가기·본문·표·요약·결론을 5회 전수 검수해 어색한 단어·조사·동사 결합·장황한 명사구를 교정함
- 정규화는 함수 종속성, 후보키, 단계별 분해, 무손실·종속 보존을 핵심 축으로 설명함
- 비교표는 1NF·2NF·3NF·BCNF의 제거 대상·분해 기준·적용 조건을 대비함
- 업무 DB 설계와 조회 모델은 이상 현상 건수·조인 깊이로 검증함

## Ⅰ. 개요

- **정의/개념**: 정규화는 함수 종속성과 후보키를 기준으로 릴레이션을 무손실 분해해 중복과 삽입·삭제·갱신 이상을 줄이는 논리 설계 기법임
- **배경/필요성**: 같은 사실의 반복 저장과 갱신 누락·정보 손실을 방지하기 위해 함수 종속성 기반의 분해 기준이 필요함

## Ⅱ. 특징

- 데이터 중복을 줄여 갱신 누락과 삭제에 따른 정보 손실을 예방함
- 함수 종속성을 기준으로 설계 오류를 설명하고 수정할 수 있음
- 업무 규칙과 후보키가 명확할수록 정규화 품질이 높아짐
- 분해가 지나치면 조회 조인 수가 늘어 물리 설계 보완이 필요할 수 있음

## Ⅲ. 종류 및 비교

| 판단 기준 | 1NF | 2NF | 3NF | BCNF |
|:---|:---|:---|:---|:---|
| 정규화 조건 | 속성 값을 관계 모델의 원자값으로 구성 | 복합 후보키 일부에 대한 부분 함수 종속 제거 | 비키 속성 사이 이행 함수 종속 제거 | 모든 비자명 함수 종속의 결정자를 후보키로 제한 |
| 줄이는 문제 | 반복 속성과 다중 값 저장 | 복합키 기반 중복 | 이행 종속에 따른 중복 | 숨은 결정자 때문에 남는 이상 현상 |
| 유의점 | 값 분리만으로 충분하지 않음 | 복합 후보키를 모두 식별해야 함 | 업무 규칙을 잘못 이해하면 의미가 깨질 수 있음 | 분해 후 조인 부담을 함께 검토해야 함 |

> 요약: 1NF는 원자값, 2NF는 부분 종속, 3NF는 이행 종속, BCNF는 후보키가 아닌 결정자 문제를 다룸.

## Ⅳ. 구성요소 및 구조

| 구성요소 | 설명 |
|:---|:---|
| 함수 종속성 | 어떤 속성이 다른 속성을 결정하는지 밝혀 분해 기준을 만듦 |
| 후보키 | 각 행을 유일하게 식별하는 최소 속성 집합으로 정규화 판단의 기준이 됨 |
| 분해 규칙 | 부분 종속과 이행 종속과 결정자 문제를 제거하도록 테이블을 나눔 |
| 검증 절차 | 무손실 분해와 종속 보존 여부를 확인해 설계가 의미를 유지하는지 점검함 |

> 요약: 함수 종속성과 후보키로 분해 대상을 찾고 무손실 분해·종속 보존으로 결과를 검증함.

## Ⅴ. 원리 및 절차 흐름도

1. **종속성 파악**: 어떤 속성이 어떤 속성에 의존하는지 정리함
2. **위반 형태 식별**: 부분 종속과 이행 종속과 결정자 문제를 구분함
3. **테이블 분해**: 단계별 정규형 기준에 맞춰 속성을 분리함
4. **무손실 검증**: 분해 뒤에도 원래 의미와 관계를 복원할 수 있는지 확인함

> 요약: 함수 종속성 위반을 식별해 릴레이션을 분해하고 원래 관계의 무손실 복원 여부를 검증함.

## Ⅵ. 실무 사례

1. 신규 업무 DB는 함수 종속성과 후보키로 정규화하고 무손실 분해 위반 건수·중복 속성 수를 확인함
2. 조회 API DB는 정규 모델을 유지한 채 반정규화 후보를 검증하고 p95 조회 지연·조인 깊이를 확인함

## Ⅶ. 결론

- 정규화는 함수 종속성·후보키로 릴레이션을 분해하고 무손실·종속 보존을 검증함
