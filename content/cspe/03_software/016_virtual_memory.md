## Ⅰ. 개요
- **정의**: 물리 메모리보다 큰 주소 공간을 프로세스에 제공하기 위해 디스크를 확장 메모리로 활용하는 기법
- **배경/필요성**: 프로세스마다 독립된 메모리 공간이 필요하지만 물리 메모리는 유한하므로 추상화 계층이 필요함
- **비유**: 작은 책상(물리 메모리)에 큰 서재(디스크)를 연결하여 필요한 책만 꺼내 쓰는 방식과 같음

| 출제 의도 | 반드시 짚을 핵심 | 감점 회피 포인트 |
|:---|:---|:---|
| 가상 주소-물리 주소 매핑 원리 | 페이지 테이블, TLB, 요구 페이징 | 가상 메모리와 스왑을 동일시하지 않을 것 |

> 요약: 주소 변환과 요구 페이징으로 물리 메모리 한계를 넘는 메모리 공간을 제공하는 기법임

## Ⅱ. 구성요소
```text
CPU -> Virtual Addr -> TLB --hit--> Physical Addr -> RAM
                        |
                       miss
                        |
                        v
                   Page Table -> Frame Number -> RAM
                        |
                      invalid
                        |
                        v
                   Page Fault -> Disk (Swap)
```

| 구성요소 | 설명 | 비유 |
|:---|:---|:---|
| Page Table | 가상 페이지 번호를 물리 프레임 번호로 매핑하는 자료구조 | 책 목차(페이지-서가 위치 대응표) |
| TLB | 최근 사용된 매핑을 캐싱하여 주소 변환 속도를 높이는 하드웨어 캐시 | 자주 보는 책을 책상 위에 올려둠 |
| Swap Area | 물리 메모리에서 내보낸 페이지를 저장하는 디스크 영역 | 서재의 보관 선반 |

> 요약: 페이지 테이블, TLB, 스왑 영역이 주소 변환과 페이지 이동을 담당함

## Ⅲ. 절차
```text
가상 주소 발행 -> TLB 조회 -> 페이지 테이블 조회 -> 디스크에서 적재(폴트 시)
```
- 1단계: CPU가 가상 주소를 발행하고 TLB에서 매핑을 조회함
- 2단계: TLB 미스 시 페이지 테이블을 참조하여 물리 프레임 번호를 획득함
- 3단계: 페이지 테이블 엔트리가 invalid이면 페이지 폴트가 발생하고 디스크에서 해당 페이지를 적재함
- 4단계: 적재 완료 후 페이지 테이블과 TLB를 갱신하고 중단된 명령어를 재실행함

> 요약: TLB-페이지 테이블-디스크 3단계 계층을 통해 가상 주소를 물리 주소로 변환하는 절차임

## Ⅳ. 문제점
- 주소 변환 오버헤드: 페이지 테이블 조회가 메모리 접근을 추가로 발생시켜 지연이 증가함
- 페이지 테이블 크기: 64비트 주소 체계에서 단일 레벨 페이지 테이블은 수 TB 크기가 되어 비현실적임
- 스레싱 위험: 물리 메모리 대비 과도한 프로세스 적재 시 페이지 폴트가 급증함 (015 참조)

> 요약: 변환 오버헤드, 테이블 크기, 스레싱이 가상 메모리의 주요 한계임

## Ⅴ. 개선방안
1. 단기: TLB 적중률을 높여 주소 변환 오버헤드를 최소화함 (대형 페이지, Huge Page 활용)
2. 중기: 다단계(Multi-level) 페이지 테이블로 실제 사용 영역만 매핑하여 테이블 크기를 절감함
3. 장기: 워킹 셋 기반 프레임 할당과 부하 제어를 결합하여 스레싱을 예방함

> 요약: TLB 최적화, 다단계 테이블, 워킹 셋 기반 할당으로 각 한계를 해소할 수 있음

## Ⅵ. 전망
- 발전 방향: CXL 메모리 확장과 결합하여 가상 메모리 계층이 DRAM-CXL-SSD로 확대되는 추세임
- 기술사적 판단: IOMMU 기반 디바이스 가상 메모리가 GPU·가속기 환경에서 필수 요소로 부상 중임
- 기술사 제언: Huge Page, NUMA 인지 배치 등 가상 메모리 튜닝을 애플리케이션 특성에 맞춰 적용할 필요
