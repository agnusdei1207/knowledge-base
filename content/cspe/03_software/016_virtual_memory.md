## Ⅰ. 개요
- **정의**: 물리 메모리보다 큰 주소 공간을 프로세스에 제공하기 위해 디스크를 확장 메모리로 활용하는 메모리 관리 기법
- **배경/필요성**: 다수 프로세스가 제한된 물리 메모리를 공유할 때 메모리 부족과 주소 충돌을 해결할 수단이 필요함
- **비유**: 작은 책상(물리 메모리)에서 필요한 책만 올려놓고 나머지는 서재(디스크)에 두는 것과 유사함

| 출제 의도 | 반드시 짚을 핵심 | 감점 회피 포인트 |
|:---|:---|:---|
| 메모리 관리 체계 이해 | 가상 주소 -> 물리 주소 변환(MMU) | 가상 메모리 = 스왑이 아님, 주소 변환 메커니즘 전체를 포괄함 |

> 요약: MMU를 통해 가상 주소를 물리 주소로 변환하여 프로세스별 독립 주소 공간을 제공하는 기법임

## Ⅱ. 구성요소
```text
CPU --> MMU --> Page Table --> Physical Memory
                  |                  |
                  v                  v
                TLB(캐시)       Swap Area(디스크)
```

| 구성요소 | 설명 | 비유 |
|:---|:---|:---|
| 가상 주소 공간 | 프로세스마다 독립적으로 부여되는 논리적 메모리 영역 | 각자의 사서함 번호 |
| MMU | 가상 주소를 물리 주소로 변환하는 하드웨어 유닛 | 우편 분류기 |
| 페이지 테이블 | 가상 페이지와 물리 프레임 간 매핑 정보를 저장하는 자료구조 | 주소록 |
| 스왑 영역 | 물리 메모리 부족 시 페이지를 임시 저장하는 디스크 공간 | 서재의 예비 선반 |

> 요약: MMU, 페이지 테이블, 스왑 영역이 협력하여 주소 변환과 메모리 확장을 수행함

## Ⅲ. 절차
```text
가상 주소 발생 --> 페이지 테이블 조회 --> 적중/미스 판정 --> 물리 주소 접근
```
- 1단계: CPU가 명령 실행 시 가상 주소를 생성하여 MMU에 전달함
- 2단계: MMU가 TLB를 먼저 확인하고, 미스 시 페이지 테이블을 조회함
- 3단계: 유효 비트 확인 후 페이지 폴트 발생 시 디스크에서 페이지를 적재함
- 4단계: 물리 프레임 번호 + 오프셋으로 물리 주소를 구성하여 메모리에 접근함

> 요약: 가상 주소 발생부터 TLB/페이지 테이블 조회를 거쳐 물리 메모리에 접근하는 흐름임

## Ⅳ. 문제점
- 페이지 폴트 오버헤드: 디스크 I/O 발생 — 메모리 접근 대비 수만 배 느린 지연이 발생함
- 페이지 테이블 크기: 64비트 주소 공간 — 테이블 자체가 메모리를 대량 소비함
- 스래싱: 과도한 다중 프로그래밍 — 페이지 교체가 반복되어 유효 CPU 이용률이 급감함

> 요약: 페이지 폴트 지연, 테이블 크기, 스래싱이 주요 성능 저하 요인임

## Ⅴ. 개선방안
1. 단기: TLB 적중률 향상을 위해 Huge Page(2MB/1GB) 적용으로 페이지 폴트 빈도 감소
2. 중기: 다단계·역 페이지 테이블로 테이블 메모리 사용량을 절감
3. 장기: 워킹셋 기반 적응형 페이지 교체와 메모리 오버커밋 제어로 스래싱 방지

> 요약: Huge Page, 테이블 구조 개선, 워킹셋 기반 제어 순으로 개선해야 함

## Ⅵ. 전망
- 발전 방향: CXL 기반 메모리 풀링으로 물리 메모리 확장 시 가상 메모리 부담이 경감될 전망임
- 기술사적 판단: 컨테이너·서버리스 환경에서 메모리 격리와 효율의 균형이 더욱 중요해짐
- 기술사 제언: 대용량 메모리 시스템에서는 Huge Page 정책과 NUMA 배치를 함께 설계할 것을 권고함
