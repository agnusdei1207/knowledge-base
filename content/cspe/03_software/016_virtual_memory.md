# 📖 【암기용】 개념 완전 이해

## 한눈에
- **개요**: 가상 메모리는 **프로세스에 물리 메모리 용량과 무관한 연속된 논리 주소 공간을 제공하고, 실제로 참조되는 부분만 물리 프레임에 올려 두는 메모리 관리 기법**으로, 페이징·세그멘테이션과 주소 변환(MMU·페이지 테이블·TLB)으로 구현된다.
- **왜 필요한가**: 프로그램이 물리 메모리보다 커도 실행하려면, 그리고 여러 프로세스가 서로의 메모리를 침범하지 않고 안전하게 공존하려면, 논리 주소와 물리 주소를 분리해 필요한 조각만 적재하는 구조가 있어야 한다.
- **핵심 직관**: 도서관 전체(디스크의 전체 프로그램)를 다 책상에 올릴 수 없으니, 지금 읽는 몇 쪽(페이지)만 책상(물리 메모리)에 두고, 쪽 번호 색인표(페이지 테이블)로 "이 쪽이 책상 어디에 있나"를 즉시 찾는 것과 같다.

## 핵심 용어 정리 (내부에 등장하는 것들)
아래 답안용에 나오는 가상 메모리 관련 표기를 비유와 함께 먼저 세운다. 맨 위가 이 주제의 상위 핵심 키워드다.

| 용어/표기 | 의미 | 비유·예 |
| --- | --- | --- |
| 가상 메모리 (상위 키워드) | 논리 주소 공간을 물리 메모리에서 분리해 필요한 부분만 적재 | 책 전체를 두지 않고 지금 읽는 쪽만 책상에 |
| 논리(가상) 주소 | 프로세스가 보는 주소, CPU가 생성 | 책의 "쪽 번호" |
| 물리 주소 | 실제 RAM의 주소 | 책상 위 실제 위치 |
| MMU (Memory Management Unit) | 논리→물리 주소를 하드웨어로 변환하는 CPU 내 장치 | 쪽 번호를 책상 위치로 바꿔주는 자동 색인기 |
| 페이지 (Page) | 논리 주소 공간을 나눈 고정 크기 블록(보통 4KB) | 책을 자른 한 쪽 |
| 프레임 (Frame) | 물리 메모리를 페이지와 같은 크기로 나눈 칸 | 책상 위 한 칸 |
| 페이지 테이블 | 페이지 번호→프레임 번호 매핑표 | 쪽 번호↔책상 칸 색인표 |
| 페이지 폴트 (Page Fault) | 참조한 페이지가 물리 메모리에 없어 디스크에서 가져오는 예외 | 필요한 쪽이 책상에 없어 서가에서 꺼냄 |
| TLB (Translation Lookaside Buffer) | 최근 주소 변환 결과를 캐시하는 고속 버퍼 | 자주 보는 쪽의 위치를 외워 둔 쪽지 |
| 세그먼트 (Segment) | 코드·데이터·스택 등 논리 단위로 나눈 가변 크기 영역 | 책을 장(章) 단위로 나눔 |
| 내부 단편화 | 고정 크기 페이지에서 마지막 조각이 남아 낭비되는 공간 | 한 쪽에 몇 줄만 써 빈 공간 남음 |
| 외부 단편화 | 가변 크기 할당에서 사이사이 못 쓰는 자투리 공간 | 책장 칸 사이 애매한 틈 |

## 깊이 이해
- **배경·문제의식**: 초기에는 프로그램 전체를 연속된 물리 메모리에 통째로 올렸다. 이러면 (1) 물리 메모리보다 큰 프로그램을 못 돌리고, (2) 프로세스마다 연속 공간이 필요해 외부 단편화가 심하며, (3) 한 프로세스가 다른 프로세스 메모리를 침범할 위험이 있었다. 가상 메모리는 논리 주소와 물리 주소를 분리해 이 세 문제를 한 번에 푼다.
- **작동 원리(어떻게+왜)**: CPU가 논리 주소를 내면 MMU가 페이지 테이블을 조회해 프레임 번호로 바꾼다. 해당 페이지가 메모리에 없으면(유효비트=0) 페이지 폴트가 발생하고, OS가 디스크에서 프레임으로 적재한 뒤 테이블을 갱신하고 명령을 재실행한다. 매번 테이블(메모리)을 읽으면 접근이 2배 느려지므로, 최근 변환을 TLB(수십~수백 엔트리)에 캐시해 대부분을 1클록에 처리한다. 필요한 부분만 올리므로(요구 페이징) 물리 메모리보다 큰 프로그램도 실행된다.
- **비유**: 논리 주소는 "책의 쪽 번호", 물리 주소는 "책상 위 실제 위치"다. 색인표(페이지 테이블)가 쪽 번호를 책상 칸으로 바꿔 주고, 자주 보는 쪽은 위치를 외운 쪽지(TLB)로 즉시 찾는다. 없는 쪽은 서가(디스크)에서 꺼내 오는데(페이지 폴트) 이때가 가장 느리다.
- **구체 예시**: 4KB 페이지·32비트 주소 체계에서 논리 주소 상위 20비트가 페이지 번호, 하위 12비트가 페이지 내 오프셋이다. TLB 히트율 98%, TLB 접근 1ns, 메모리 접근 100ns면 유효 접근 시간은 대략 0.98×101ns + 0.02×201ns ≈ 103ns로, 매번 테이블을 읽는 200ns보다 훨씬 빠르다.
- **흔한 오해·주의점**: (1) **가상 메모리 = 스왑(디스크)만이 아니다** — 핵심은 주소 분리와 요구 적재이고, 스왑은 그 결과 중 하나다. (2) **페이지 폴트는 오류가 아니다** — 요구 페이징에서 정상적으로 발생하며, 문제는 폴트율이 과도할 때(스레싱, 015 참조)다. (3) 페이징은 내부 단편화, 세그멘테이션은 외부 단편화가 생겨 실무는 둘을 결합(세그먼트를 페이지로 관리)한다.

## 연결 개념
- 페이지 교체 알고리즘(017 참조) — 프레임이 꽉 찼을 때 어떤 페이지를 내보낼지 결정
- 워킹셋·페이지 폴트 빈도(018 참조) — 프로세스별 적정 프레임을 정해 스레싱을 예방
- 프로세스 스레싱(015 참조) — 프레임이 워킹셋에 못 미쳐 폴트가 폭증하는 붕괴 현상

# 📝 【답안용】 시험 답안 템플릿

## 핵심 인사이트 (3줄 요약)
> 1. **본질**: 가상 메모리는 논리 주소와 물리 주소를 분리하고 참조되는 부분만 적재해, 물리 용량을 넘는 프로그램 실행과 프로세스 간 격리를 동시에 달성함.
> 2. **가치**: 페이징·세그멘테이션과 MMU·페이지 테이블·TLB로 주소 변환을 하드웨어 가속해, 다중 프로그래밍과 메모리 보호의 기반이 됨.
> 3. **판단 포인트**: 단순·균등 관리는 페이징, 논리 단위 보호·공유는 세그멘테이션이며, 실무는 둘을 결합함.

| 주소 변환 메커니즘 | MMU·페이지 테이블·TLB·페이지 폴트 흐름 | TLB·페이지 폴트 처리 누락 |

> 요약: 가상 메모리를 주소 분리·요구 적재로 정의하고, MMU 기반 변환 흐름과 페이징·세그멘테이션의 단편화 트레이드오프를 제시함.

## Ⅰ. 개요 및 필요성
- 개요: 논리 주소 공간을 물리 메모리에서 분리해 필요한 부분만 적재하는 메모리 관리 기법임
- 배경: 프로그램 전체 적재 방식은 물리 용량 한계·외부 단편화·프로세스 침범 문제를 안음
- 필요성: 물리 용량 초과 프로그램 실행, 다중 프로그래밍, 메모리 보호·공유를 위해 주소 분리가 필요함
- 목표: 요구 적재로 메모리 활용을 높이되 페이지 폴트 비용을 관리 가능한 수준으로 유지함

## Ⅱ. 구조 및 구성요소
선형 텍스트 구조도:
```
CPU (논리 주소 생성)
  -> MMU: 페이지 번호로 TLB 조회
       -> TLB 히트: 프레임 번호 즉시 반환
       -> TLB 미스: 페이지 테이블 조회
              -> 유효비트=1: 프레임 번호 반환 / TLB 갱신
              -> 유효비트=0: 페이지 폴트 -> OS가 디스크에서 프레임 적재
  -> 물리 주소 = 프레임 번호 + 오프셋 -> 물리 메모리 접근
```

| 구성요소 | 역할 | 비고 |
| --- | --- | --- |
| MMU | 논리→물리 변환을 하드웨어로 수행 | CPU 내장 |
| 페이지 테이블 | 페이지→프레임 매핑, 유효·보호 비트 보유 | 프로세스마다 하나 |
| TLB | 최근 변환 결과 캐시 | 히트 시 테이블 조회 생략 |
| 페이지/프레임 | 논리/물리를 나눈 고정 크기 단위 | 보통 4KB |
| 스왑 영역 | 메모리에 없는 페이지를 보관하는 디스크 공간 | 페이지 폴트 시 소스 |

> 요약: MMU가 TLB·페이지 테이블로 논리 주소를 변환하고, 미적재 페이지는 페이지 폴트로 디스크에서 채움.

## Ⅲ. 동작원리 및 흐름도
선형 텍스트 흐름도:
```
논리 주소 -> [MMU] TLB 조회 -> 히트? -> 예: 프레임 반환
                                      -> 아니오: 페이지 테이블 조회
페이지 테이블 -> 유효? -> 예: 프레임 반환·TLB 채움
                       -> 아니오: 페이지 폴트 -> 디스크 적재 -> 재실행
```
1. CPU가 논리 주소(페이지 번호 + 오프셋)를 생성하면 MMU가 페이지 번호로 TLB를 먼저 조회함.
2. TLB 미스면 MMU가 페이지 테이블에서 해당 엔트리를 읽어 유효비트를 확인함.
3. 유효비트가 0이면 OS가 페이지 폴트를 처리해 디스크에서 빈 프레임으로 페이지를 적재하고 테이블·TLB를 갱신함.
4. 프레임 번호에 오프셋을 결합한 물리 주소로 실제 메모리에 접근하고, 폴트였던 명령은 재실행함.

## Ⅳ. 특징
- 물리 용량과 무관한 논리 주소 공간 제공으로 대용량 프로그램 실행이 가능함
- 프로세스별 독립 페이지 테이블·보호 비트로 메모리 격리·보호가 강제됨
- 페이지 공유(읽기전용 코드·COW)로 프로세스 다수 기동 시 메모리 사용을 절감함
- 트레이드오프 — 주소 변환·페이지 폴트 오버헤드가 있어 TLB 히트율과 참조 지역성에 성능이 좌우됨

## Ⅴ. 심화 비교 및 적용 판단
페이징과 세그멘테이션은 논리 주소 공간을 나누는 단위가 달라 단편화·보호 특성이 대비된다.

| 구분 | 페이징 | 세그멘테이션 |
| --- | --- | --- |
| 분할 단위 | 고정 크기 페이지 | 논리 단위 가변 세그먼트 |
| 단편화 | 내부 단편화 발생 | 외부 단편화 발생 |
| 주소 구성 | 페이지 번호 + 오프셋 | 세그먼트 번호 + 오프셋(한계 검사) |
| 보호·공유 | 페이지 단위(균일) | 논리 단위(코드/데이터별 정교) |
| 관점 | 물리 관리에 최적 | 프로그래머 관점에 부합 |

> 요약: 균등·단순 관리는 페이징, 논리 단위 보호·공유는 세그멘테이션이며, 실무는 세그먼트를 페이지로 관리해 결합함.

- 리스크 — TLB 미스 폭증 — 원인: 지역성 낮은 접근 — 대응: 대형 페이지(Huge Page)로 엔트리당 커버리지 확대
- 리스크 — 페이지 테이블 메모리 과다 — 원인: 큰 주소 공간 — 대응: 다단계·역페이지 테이블 적용
- 지표 — TLB 히트율 — 목표: 99% 이상 — 측정: 성능 카운터(perf)로 dtlb_miss 집계

## Ⅵ. 실무 적용 및 결론
- 적용 방안: 리눅스에서 THP(Transparent Huge Page, 2MB)로 대용량 힙 워크로드의 TLB 미스를 줄임
- 적용 방안: 64비트 x86의 4단계 페이지 테이블 + `mmap`으로 파일을 페이지 단위 매핑해 요구 적재를 활용함
- 적용 방안: 읽기전용 라이브러리 코드 페이지 공유·COW로 컨테이너 다수 기동 시 물리 메모리를 절감함
- 결론: 접근 지역성이 높고 균등 관리가 중요하면 페이징 중심, 논리 단위 보호·공유가 중요하면 세그먼트 결합이 유리함
- 향후 방향: 대형 페이지·다단계 테이블·하드웨어 TLB 개선으로 변환 오버헤드를 지속 축소함
