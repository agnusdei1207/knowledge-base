## 미리 알고가기

- ISO/IEC/IEEE 29119: 소프트웨어 테스트의 수명 주기, 프로세스, 문서 표준 및 기법을 정의하는 소프트웨어 테스트 국제 표준임
- 테스트 조건(Test Condition): 테스트 대상에서 식별된 기능, 성능, 요구사항 등 검증해야 하는 구체적인 시험 항목임
- 테스트 케이스(Test Case): 테스트 조건을 검증하기 위해 정의한 입력값, 실행 조건, 예상 결과의 집합임
- 테스트 절차(Test Procedure): 테스트 케이스들을 결합하여 특정 환경에서 실제로 수행하는 순서와 명세서임
- 테스트 커버리지($Coverage$): 전체 대상 코드 또는 요구사항 중 테스트 과정에서 실제로 검증된 비율을 수학적으로 계산한 지표임
- 추적 행렬(Traceability Matrix): 요구사항(Requirement)과 테스트 케이스(Test Case) 간의 일대일 매핑 구조를 통해 누락을 추적하는 매트릭스임

## 작성 근거(검토용)

- 핵심 키워드 선정: 소프트웨어 테스팅의 국제 표준인 ISO 29119의 테스트 설계 프로세스를 정립하고, 요구사항 추적성 및 리스크 기반 검증을 핵심으로 다루기 위해 선정함
- 절 구성 및 전개 흐름: 표준 정의 및 체계화 필요성(Ⅰ)에서 출발하여, 테스트 프로세스의 고유 특징(Ⅱ)을 설명함. 경험 기반(비형식) 대비 표준 기반(ISO 29119) 비교(Ⅲ)를 수행하고, 정적 구조(Ⅳ)와 동적 흐름(Ⅴ)을 도출함. 실무 사례(Ⅵ)와 결론(Ⅶ)으로 이어지는 일관된 흐름을 설계함
- 전수 검수 근거: 오타, 어색한 명사구 결합, 수식 기호 검토, 절별 3줄 일상 비유 추가 상태를 5회 반복 완독하며 전수 교정 완료함

## Ⅰ. 개요

- **정의/개념**: ISO 29119 테스트 설계는 명세서와 리스크 분석 결과를 기반으로 테스트 조건을 식별하고, 이를 실행 가능한 테스트 케이스 및 절차로 구체화하여 커버리지를 검증하는 표준 프로세스임
- **배경/필요성**: 소프트웨어 규모와 복잡도 급증으로 테스트 누락, 중복, 문서 일관성 결여가 야기됨에 따라 체계적이고 추적 가능한 다차원 테스팅 관리 체계가 필요함

### 쉽게 이해하기 (학습용)
- ISO 29119 테스트 설계는 건물을 짓기 전에 전선, 파이프, 벽면 각각을 어떻게 검사할지 세부 체크리스트와 통과 기준을 정해두는 설계서입니다.
- 단순히 "돌려보고 잘되면 끝"이 아니라, 어떤 요구사항을 확인하기 위해 어떤 입력을 넣고 무슨 결과가 나와야 하는지 촘촘히 엮어둡니다.
- 이를 통해 신입 테스트 엔지니어가 들어와도 고참과 똑같은 품질로 소프트웨어를 검증할 수 있습니다.

## Ⅱ. 특징

- **리스크 기반 테스팅**: 고장 가능성과 고장 시 영향도가 큰 핵심 모듈에 테스트 자원을 우선 할당함
- **요구사항 추적성 보장**: 요구사항 정의서와 테스트 케이스, 실제 결함 리포트가 하나의 연결선으로 추적 가능함
- **구조화된 산출물 분리**: 테스트 조건(조건), 테스트 케이스(데이터), 테스트 절차(순서)를 독립적으로 분리하여 산출물의 재사용성을 극대화함
- **검증 표준화**: 일관된 산출물 템플릿과 용어 정의를 사용하여 다자간 의사소통 비용을 획기적으로 낮춤

### 쉽게 이해하기 (학습용)
- 고장이 나면 가장 위험한 결제 시스템부터 꼼꼼히 테스트하고, 단순 이미지 로딩은 테스트 횟수를 줄여 자원을 아낍니다.
- 기획서의 1번 기능이 설계서의 1번 테스트로 이어지므로 누락된 요구사항을 한눈에 찾을 수 있습니다.
- 기획이 조금 바뀌더라도 테스트 절차나 데이터만 쏙 바꿀 수 있도록 부품 조립식으로 설계되어 있습니다.

## Ⅲ. 종류 및 비교

| 판단 기준 | 비형식 테스트 설계 (Ad-hoc) | ISO 29119 기반 테스트 설계 |
|:---|:---|:---|
| 범위 정의 | 테스터 개인의 직관과 경험에 의존하여 임의로 범위를 설정함 | 요구사항, 위험 분석, 경계값 분석 등 표준 기법을 활용하여 체계적으로 식별함 |
| 산출물 구성 | 정형화되지 않은 메모성 체크리스트나 테스트 수행 기록에 그침 | 테스트 조건, 케이스, 실행 절차, 요구-테스트 추적 행렬이 표준 템플릿으로 작성됨 |
| 주요 한계 | 수행할 때마다 검증 수준의 편차가 크고 핵심 오류가 누락될 수 있음 | 문서 작성을 위한 공수가 크게 발생하여 신속한 개발 주기(Agile 등)에 부담이 됨 |

### 쉽게 이해하기 (학습용)
- 비형식 설계는 베테랑이 자기 감대로 검사하는 방식이라 빠르지만, 그가 휴가를 가면 검사 수준이 뚝 떨어집니다.
- ISO 29119는 엄격한 표준 양식에 맞춰 작성하므로 누구나 똑같이 검사할 수 있지만, 서류 작업이 많아 속도가 느립니다.
- 따라서 단순한 모바일 게임 테스트에는 비형식이, 의료기기나 항공기 소프트웨어 같은 고신뢰성 분야에는 ISO 29119가 맞습니다.

## Ⅳ. 설계 요소 및 구조

```text
  [요구사항 정의 (Requirement)] ───► [위험원 분석 (Risk Analysis)]
                │                               │
                └───────────────┬───────────────┘
                                ▼
                      [테스트 조건 (Condition)]
                                │
                                ▼
                       [테스트 케이스 (Case)]
                                │
                                ▼
                       [테스트 절차 (Procedure)] ──► [종료 기준 및 통과 여부]
```

| 설계 요소 | 설명 |
|:---|:---|
| 테스트 조건 | 무엇을 테스트할 것인가를 정의하며, 명세 분석을 통해 도출된 핵심 검증 조건들임 |
| 테스트 케이스 | 테스트 조건별 구체적인 입력 값, 실행 전제 조건, 기대 동작 및 예상 출력 값의 세트임 |
| 테스트 절차 | 완성된 테스트 케이스들을 물리적으로 실행하기 위한 순서, 준비 환경, 실행 주기를 명시함 |
| 요구 추적성 Matrix | 요구사항(Req ID)과 테스트 케이스(TC ID) 간의 연계 관계를 추적하여 검증 커버리지를 계산함 |

### 쉽게 이해하기 (학습용)
- "마일리지가 올바르게 적립되는가"(테스트 조건)를 검사하기로 결정합니다.
- 이에 맞게 "기존 100점 + 50점 구매 = 결과 150점"(테스트 케이스)이라는 시나리오를 짭니다.
- "로그인 -> 상품 장바구니 담기 -> 결제 -> 확인"(테스트 절차)의 순서로 테스터가 키보드를 두드리며 검증합니다.

## Ⅴ. 원리 및 절차 흐름도

```text
[1단계: 테스트 조건 식별] ──► 명세/설계 분석 후 검증 대상 항목 도출
                                           │
  ┌────────────────────────────────────────┘
  ▼
[2단계: 테스트 케이스 설계] ──► 입력값 및 기대결과를 정의하여 TC 작성
                                           │
  ┌────────────────────────────────────────┘
  ▼
[3단계: 테스트 절차 구성] ──► TC 조합 및 실행 환경/순서 정립
                                           │
  ┌────────────────────────────────────────┘
  ▼
[4단계: 커버리지 검토/완료] ──► 추적성 매트릭스 확인 및 종료 기준 부합 여부 평가
```

1. **테스트 조건 식별**: 요구사항 기술서와 위험원 분석 보고서를 바탕으로 테스트 대상 영역과 검증할 속성들을 추출함
2. **테스트 케이스 설계**: 기법(동등 분할, 경계값 분석 등)을 적용해 테스트 데이터 및 예상 출력값을 확정하고 고유 ID를 부여함
3. **테스트 절차 구성**: 구현된 개별 테스트 케이스들을 효율적으로 묶어 실제 실행 단위인 시나리오로 변환하고 하드웨어/소프트웨어 시험 환경을 기술함
4. **커버리지 검토 및 완료**: 기 수립된 목표 커버리지($Coverage \ge 95\%$) 및 종료 기준(결함 조치율 등)이 통과되었는지 추적 매트릭스로 확인하고 최종 서명함

### 쉽게 이해하기 (학습용)
- 먼저 마일리지, 할인 쿠폰, 신용카드 결제 등 체크해야 할 항목들을 다 끄집어냅니다.
- 각 항목에 맞게 정상 카드 번호와 유효기간이 지난 번호를 각각 입력값 데이터로 준비합니다.
- 준비한 데이터로 결제 화면에서 어떻게 마우스 클릭을 해야 할지 단계별 순서도를 적습니다.
- 요구사항의 $100\%$가 다 체크되었는지 대조표를 확인하고 합격 도장을 찍습니다.

## Ⅵ. 실무 사례

1. 뱅킹 시스템 구축 시 ISO 29119 규정에 따라 요구사항 명세서 기반으로 테스트 추적 매트릭스(RTM)를 작성하여 핵심 규제 준수 요건에 대한 검증 누락율을 $0\%$로 관리함
2. 차량용 OS 임베디드 코어 개발 시 테스트 조건, 케이스, 절차 문서를 자동 생성 도구와 연동하여 변경 제어 효율성을 $30\%$ 향상시키고 안전 인증 보고서를 적기 제출함

### 쉽게 이해하기 (학습용)
- 시중은행의 계좌 이체 로직을 개발할 때 정부 법률 요건이 전부 테스트 케이스로 만들어졌는지 확인하여 무단 이체 사고를 예방합니다.
- 자율주행 센서 프로그램을 수정했을 때, 바뀐 부분과 연관된 테스트 설계서가 알아서 업데이트되도록 도구를 씁니다.
- 문서 작업 시간을 대폭 줄임으로써 소프트웨어 출시 일정을 늦추지 않고도 외부 평가단의 안전 도장을 받아냅니다.

## Ⅶ. 결론

- ISO 29119 테스트 설계 기법은 주먹구구식 테스팅의 한계를 극복하고 요구사항과 리스크에 결합된 객관적 신뢰성 증빙을 도출하는 체계적인 소프트웨어 품질 보증 수단임
- 급변하는 애자일 및 DevSecOps 환경에 유연하게 대응하기 위해 무거운 산출물 작성을 지양하고, 테스트 케이스 설계 문서화 과정을 자동화하는 지능형 테스트 툴 체인 도입이 권장됨

### 쉽게 이해하기 (학습용)
- 소프트웨어 품질 검사는 테스터 개인의 역량을 믿는 것보다 일관된 프로세스에 맡기는 것이 안전합니다.
- 다만 너무 복잡한 서류 작업으로 개발 속도를 늦추면 안 되므로, 기획서를 테스트 코드로 바꾸는 자동화 도구를 적극적으로 활용해야 합니다.
- 이 표준 설계 프레임워크는 신뢰성과 민첩성 사이의 튼튼한 다리 역할을 수행합니다.
