# 📖 【암기용】 개념 완전 이해

## 한눈에
- **개요**: 수많은 저렴한 서버(Commodity Hardware)를 하나의 클러스터로 묶어 거대한 데이터를 저장(HDFS)하고 병렬 처리(MapReduce)하는 아키텍처다.
- **왜 필요한가**: 수십 테라바이트 이상의 데이터를 단일 슈퍼컴퓨터로 처리하려면 비용이 기하급수적으로 들고 확장도 어렵다.
- **핵심 직관**: 데이터를 잘게 쪼개 여러 컴퓨터에 나눠 저장하고, 연산할 때도 데이터를 중앙으로 모으지 않고 각 컴퓨터가 자기가 가진 데이터를 알아서 처리하게 만든다.

## 핵심 용어 정리 (내부에 등장하는 것들)

| 용어/표기 | 의미 | 비유·예 |
|:---|:---|:---|
| Hadoop | 분산 저장과 분산 처리를 위한 오픈소스 프레임워크 생태계 | "거대한 가상 슈퍼컴퓨터" |
| HDFS | 하둡 분산 파일 시스템 (Hadoop Distributed File System) | "여러 창고를 하나의 큰 창고처럼 쓰기" |
| MapReduce | 맵(나누어 작업)과 리듀스(결과 취합)로 구성된 병렬 처리 모델 | "각자 단어 수 세고(Map), 나중에 합치기(Reduce)" |
| Data Locality | 연산을 데이터가 저장된 노드에서 직접 수행하는 특성 | "작업자를 창고로 보내지 않고 창고 직원이 직접 작업" |
| NameNode / DataNode | 마스터 역할(메타데이터 관리)과 워커 역할(실제 데이터 저장) | "도서관 사서와 서가의 책장" |

## 깊이 이해
- **배경·문제의식**: 2000년대 중반 폭증하는 웹 로그 데이터를 RDBMS 장비 하나로 처리하는 것은 물리적으로 불가능해졌다. 구글은 논문(GFS, MapReduce)을 통해 고가 장비 대신 저렴한 PC 수천 대를 묶어 신뢰성 있게 처리하는 방법을 제시했고, 이를 더그 커팅이 오픈소스로 구현한 것이 하둡이다.
- **작동 원리**: 파일을 통째로 저장하지 않고 128MB 단위 블록으로 쪼개 여러 DataNode에 분산 저장하며 3벌씩 복제(Replication)해 장애에 대비한다. MapReduce 연산 시 NameNode가 데이터 위치 파악해 데이터가 있는 노드에서 바로 Map 함수를 실행시킨다. 이후 중간 결과(Key-Value)를 정렬 및 셔플(Shuffle)하여 Reduce 노드로 보내 최종 집계한다.
- **비유**: 1만 권의 책에서 '사과'라는 단어가 몇 번 나오는지 세고 싶다. 혼자 1만 권을 읽으면 몇 달이 걸린다. 100명에게 100권씩 나눠주고(HDFS), 각자 자기 책에서 사과 단어 수를 세게 한 뒤(Map), 그 결과 메모지만 취합해 모두 더한다(Reduce).
- **구체 예시**: 1TB 크기의 웹 서버 로그에서 일별 방문자 수를 집계할 때, HDFS는 로그를 8000개의 블록으로 분산한다. MapReduce는 8000개의 Map 작업을 노드들에 병렬로 띄워 '날짜-1' 쌍을 만들고, Reduce가 날짜별로 값을 합산해 출력한다. 수 시간 걸릴 작업이 수 분 내에 끝난다.
- **흔한 오해·주의점**: 하둡은 훌륭한 시스템이지만 모든 연산에 적합한 것은 아니다. 중간 결과를 항상 디스크에 쓰고 읽기 때문에 머신러닝처럼 반복(Iterative) 연산이 잦은 작업에서는 너무 느리다. 실시간 쿼리용이 아니라 대규모 배치를 위한 시스템이다.

# 📝 【답안용】 시험 답안 템플릿

## 핵심 인사이트 (3줄 요약)

> 1. **본질**: 하둡 생태계는 저비용 분산 파일 저장소(HDFS)와 분산 병렬 연산 프레임워크(MapReduce)를 결합한 대용량 배치 처리의 표준이다.
> 2. **가치**: 데이터를 연산 노드로 가져오는 대신, 연산 코드를 데이터가 있는 노드로 보내는 데이터 지역성(Data Locality)으로 네트워크 병목을 획기적으로 제거했다.
> 3. **판단 포인트**: HDFS 기반 맵리듀스는 I/O 오버헤드로 인해 실시간 스트리밍이나 반복적 머신러닝 연산에는 한계가 있어, 최신 아키텍처는 Spark로 전환하는 추세다.

## 출제 의도 및 답안 포인트

| 출제 의도 | 반드시 짚을 핵심 | 감점 회피 포인트 |
|:---|:---|:---|
| 빅데이터 분산 처리의 기본 사상 확인 | HDFS(블록 분산·복제), MapReduce(Map/Shuffle/Reduce), Data Locality | "데이터를 모아서 처리한다"는 오개념 기술 |
| 하둡 아키텍처 구성요소의 역할 분리 이해 | NameNode(메타데이터) / DataNode(실제 데이터), 단일 장애점(SPOF) 리스크 | 단순 기능 나열, 마스터-워커 분리 누락 |
| 레거시 하둡 플랫폼의 한계 인지 및 개선 방향 | 디스크 I/O 오버헤드, 배치 중심의 지연(Latency), In-Memory(Spark) 대안 | 하둡을 실시간 처리나 AI에 적합하다고 단정 |

> 요약: 하둡은 분산 저장과 데이터 지역성 기반 병렬 처리로 빅데이터 시대를 열었으나 디스크 I/O 기반의 한계가 명확함을 서술해야 한다.

## Ⅰ. 개요 및 필요성

- 개요: 대용량 데이터를 클러스터 환경에서 분산 저장(HDFS)하고 병렬 처리(MapReduce)하는 오픈소스 소프트웨어 프레임워크
- 배경: 페타바이트급 비정형 데이터의 폭증으로 고가의 단일 스케일업(Scale-up) 장비로는 처리 비용 및 확장성 한계에 도달
- 필요성: 저렴한 범용 하드웨어(Commodity Hardware) 클러스터를 이용해 높은 결함 허용성(Fault Tolerance)과 확장성 확보 필요

---

## Ⅱ. 구조 및 구성요소

```text
Client -> NameNode (메타데이터/블록 위치 관리)
            |
            +-> DataNode 1 (블록 A, B)
            +-> DataNode 2 (블록 B, C) -> [Map] -> [Shuffle] -> [Reduce] -> HDFS 저장
            +-> DataNode 3 (블록 C, A)
```

| 구성요소 | 역할 | 특이사항 |
|:---|:---|:---|
| NameNode (마스터) | 파일 시스템의 네임스페이스와 블록 매핑 메타데이터 메모리 유지 | HA(High Availability) 구성 안 하면 SPOF 위험 |
| DataNode (워커) | 128MB 단위 파일 블록을 저장하고 3중 복제(Replication) 수행 | 디스크 손상 시 NameNode에 보고해 자동 복구 |
| YARN / MapReduce | 자원 관리 및 데이터 지역성(Locality) 기반 병렬 작업 할당 | 중간 결과를 로컬 디스크에 저장(I/O 병목 원인) |

> 요약: HDFS는 메타데이터와 실제 데이터를 물리적으로 분리해 무한 스케일아웃을 지원하는 구조다.

---

## Ⅲ. 동작원리 및 흐름도

```text
Input Split -> Map (KV 추출) -> Shuffle & Sort -> Reduce (병합) -> HDFS Output
```

- 1단계 [입력 분할 및 Map]: HDFS 블록 단위로 데이터를 쪼개어 해당 노드에서 Map 함수 실행(Data Locality), <Key, Value> 추출
- 2단계 [Spill 및 로컬 Sort]: Map 결과를 메모리에 버퍼링 후 로컬 디스크에 기록하며, Key 기준으로 정렬 수행
- 3단계 [Shuffle 및 병합]: Reduce 노드가 네트워크를 통해 각 Map 노드에서 필요한 파티션 데이터를 당겨와(Fetch) 병합 정렬
- 4단계 [Reduce 및 출력]: 동일 Key 그룹별 집계 등 사용자 정의 Reduce 연산을 수행 후 최종 결과를 HDFS에 저장

> 요약: 데이터가 있는 곳에서 Map을 수행해 네트워크 부하를 줄이고 셔플로 데이터를 재분배해 집계한다.

---

## Ⅳ. 특징
- [결함 허용성]: DataNode 장애 시 다른 노드의 복제본을 활용해 작업을 자동 복구하고 데이터 유실 방지
- [데이터 지역성]: 코드가 데이터로 이동해 실행되므로 랙 간 대역폭(Network Bandwidth) 병목 우회
- [디스크 오버헤드]: Map과 Reduce 단계 사이에 매번 디스크 쓰기/읽기가 발생해 지연율이 큼

> 요약: 비용 효율과 무중단성은 뛰어나지만 디스크 기반 아키텍처 특성상 I/O 레이턴시의 한계가 뚜렷하다.

---

## Ⅴ. 심화 비교 및 적용 판단

| 비교 축 | 기존/대안 (MapReduce) | 본 키워드 (Apache Spark) | 선택 기준 |
|:---|:---|:---|:---|
| 데이터 처리 기반 | Disk I/O 기반 중간 저장 | In-Memory 처리 (RDD/DataFrame) | 반복적 연산 및 실시간 요구 사항 |
| 처리 지연(Latency) | 분 단위 배치 최적화 | 초 단위 마이크로 배치/스트리밍 | 서비스 응답 속도 (SLA) |
| 프로그래밍 복잡도 | Java, 복잡한 맵/리듀스 코드 | SQL, Python, 풍부한 추상화 API | 개발 생산성 및 데이터 분석가 활용도 |

> 요약: 단순 대용량 야간 배치는 여전히 하둡이 쓰이나, 기계학습이나 대화형 질의에는 스파크가 압도적 우위다.

**리스크·대응 (기본은 불릿):**
- [NameNode SPOF]: 마스터 노드 장애 시 전체 클러스터 정지 → Active-Standby 구조의 HA(High Availability) 및 Zookeeper 쿼럼 적용 (지표: 메타데이터 가용성 99.99%)
- [Small File Problem]: 수KB 단위 작은 파일이 많으면 NameNode 메모리 고갈 → SequenceFile 결합 보관 또는 HBase/Iceberg 전환 (지표: 평균 블록 대비 실 파일 크기)

**도입 후 점검 지표 (기본은 불릿):**
- 성능/효율: 일일 집계 배치 작업 처리 시간(Turnaround Time) 4시간 이내 유지 — YARN Resource Manager 지표
- 품질/운영: 블록 결손(Missing Block) 0건 — HDFS FSCK(File System Check) 리포트

## Ⅵ. 실무 적용 및 결론

**적용 방안 3개:**
1. 아키텍처 개편: HDFS를 저비용 콜드/웜 데이터 레이크 저장소로 유지하되, 연산 엔진은 YARN 위에서 구동되는 Spark로 마이그레이션
2. 클라우드 전환 검토: 온프레미스 노드 유지보수 부담 절감을 위해 AWS EMR 또는 구글 Dataproc 같은 매니지드 하둡 환경으로 전환
3. 데이터 수명 주기 정책: 생성된 지 1년 지난 로그는 압축 포맷(Parquet)화 및 복제 계수(Replication Factor) 3에서 2로 조정해 HDFS 스토리지 비용 절감

**결론 (2줄):**
- 기술사 판단: 하둡 생태계는 빅데이터의 기반 사상을 확립했으나, 현대에는 객체 스토리지(S3)와 인메모리 엔진(Spark)으로 분리 발전하고 있어 HDFS+MapReduce 단일 의존은 지양해야 한다.
- 향후 방향: 하둡의 개념은 향후 클라우드 네이티브 기반의 서버리스 데이터 레이크하우스(Lakehouse)로 완벽히 진화·대체될 것이다.
