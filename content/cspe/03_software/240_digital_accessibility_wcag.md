# 📖 【암기용】 개념 완전 이해

> 목적: 디지털 접근성 WCAG 2.1을 처음 보는 사람도 완벽히 이해하게 만든다. 시험 답안 양식이 아니라, 이해를 위한 친절한 설명이다.

## 한눈에
- **개요**: WCAG(Web Content Accessibility Guidelines) 2.1은 **디지털 접근성**을 판정하는 국제 표준 지침으로, 장애 유형과 사용 환경 차이에 관계없이 웹 콘텐츠를 동등하게 이용할 수 있는지를 검증 가능한 기준으로 정의한다.
- **왜 필요한가**: 시각·청각·운동·인지 특성이 다른 사용자는 같은 화면도 접근 방식이 다르다(스크린리더로 듣기, 키보드만으로 조작하기 등). WCAG는 "배려하자"는 선언이 아니라, 개발자가 통과/실패를 판정할 수 있는 구체적 성공 기준을 제공한다.
- **핵심 직관**: 건물에 계단만 두지 않고 경사로·엘리베이터·점자 안내판을 함께 두어, 어떤 신체 조건의 사람도 같은 목적지(같은 업무 완료)에 도달하게 만드는 설계 원칙이다.

## 핵심 용어 정리 (내부에 등장하는 것들)

| 용어 | 의미 | 비유 |
|:---|:---|:---|
| 웹 접근성(Accessibility) | 신체·환경 차이와 무관하게 웹 콘텐츠를 이용할 수 있는 성질 (WCAG가 판정하려는 대상, 상위 개념) | "누구나 들어갈 수 있는 문" |
| POUR 4원칙 | 인식 가능(Perceivable)·운용 가능(Operable)·이해 가능(Understandable)·견고함(Robust) | 접근성을 보는 네 가지 창 |
| 성공 기준(Success Criterion) | 각 원칙 아래 통과/실패를 판정할 수 있게 만든 구체 규칙(총 78개) | 시험의 채점 기준표 |
| 적합성 수준 A/AA/AAA | 성공 기준을 얼마나 엄격히 만족하는지의 3단계 등급(A<AA<AAA) | 자격증의 초급·중급·고급 |
| 명도 대비(Contrast Ratio) | 텍스트와 배경색의 밝기 차이를 1:1~21:1로 수치화한 값 | 흑백 인쇄물의 "선명도" |
| ARIA | 스크린리더에게 버튼·상태·역할을 알려주는 HTML 보강 속성 | 화면에 붙이는 "음성 설명 스티커" |
| KWCAG | 한국형 웹 콘텐츠 접근성 지침(국가표준, WCAG를 국내 실정에 맞게 구체화) | WCAG의 한국어 로컬 버전 |

## 깊이 이해

### 왜 이런 지침이 필요했나 (배경)
- 스크린리더 사용자는 화면을 못 보고 음성으로 듣는다. 이때 이미지에 설명 글(대체 텍스트)이 없으면 스크린리더는 "이미지"라고만 읽어 정보가 사라진다. 반대로 저시력 사용자는 화면을 보긴 하지만 연한 회색 글씨를 구분하지 못한다. 서로 다른 장벽에 대해 "이 정도면 통과"라는 공통 기준이 없으면 개발자마다 판단이 달라진다. W3C는 이 문제를 POUR 4원칙과 구체적 성공 기준으로 표준화했다.

### 명도 대비를 숫자로 판정하는 법
- 명도 대비는 두 색의 상대 휘도(Relative Luminance)를 (L1+0.05)/(L2+0.05) 공식으로 계산해 1:1(대비 없음)부터 21:1(흑백 최대 대비) 사이 값으로 나타낸다.
- WCAG 2.1 AA 기준: 일반 텍스트는 4.5:1 이상, 18pt 이상 큰 텍스트는 3:1 이상이어야 통과한다. 예: 흰 배경(#FFFFFF)에 회색 글씨(#999999)를 놓으면 대비가 약 2.8:1로 AA 기준(4.5:1)에 미달해 실패이고, 더 짙은 회색(#767676)으로 바꾸면 대비가 약 4.5:1이 되어 통과선에 걸린다.
- 이런 식으로 "느낌상 괜찮다"가 아니라 도구(대비 계산기)로 숫자를 재서 통과/실패를 판정하는 것이 성공 기준의 핵심이다.

### 4원칙이 실제로 요구하는 것
- **인식 가능(P)**: 이미지에 대체 텍스트, 동영상에 자막, 색만으로 정보를 구분하지 않기(예: 빨간 글씨만으로 "필수"를 표시하면 색맹 사용자는 구분 못함 → 별표(*)나 텍스트를 병기).
- **운용 가능(O)**: 마우스 없이 Tab·Enter 키만으로 모든 기능을 순서대로 이용할 수 있어야 하고, 지금 포커스가 어디 있는지 테두리 등으로 표시돼야 한다.
- **이해 가능(U)**: 입력 오류가 나면 "오류입니다"가 아니라 "전화번호는 숫자 10~11자리로 입력하세요"처럼 원인과 해결법을 알려줘야 한다.
- **견고함(R)**: 시맨틱 HTML(`<button>`을 `<div onclick>`으로 대체하지 않기)과 ARIA 속성을 써서 다양한 스크린리더·브라우저 조합에서도 깨지지 않게 만든다.

### A/AA/AAA는 어떻게 다른가, 그리고 판별 원리
- A는 최소한(예: 대체 텍스트 존재), AA는 실무 표준(예: 대비 4.5:1, 자막 제공), AAA는 최고 수준(예: 대비 7:1, 수어 통역)이다. 공공기관은 보통 AA를 목표로 삼는다 — AAA는 모든 콘텐츠에 적용하기 현실적으로 어렵기 때문이다.
- **판별 원리**: 자동 도구(axe, Lighthouse)는 대비·대체 텍스트 누락처럼 "규칙으로 기계 판정 가능한" 항목만 잡아낸다. "Tab 순서가 논리적인가", "스크린리더로 실제 업무를 완료할 수 있는가"는 기계가 판단 못 하므로 반드시 사람이 키보드·스크린리더로 수동 검수해야 한다.

### 비유와 흔한 오해
- **비유**: 접근성은 건물의 경사로와 같다 — 휠체어 사용자만을 위한 것 같지만, 유모차나 캐리어를 끄는 사람에게도 유용하다. 자막도 청각장애인뿐 아니라 소음이 있는 환경의 모든 사용자에게 도움이 된다.
- **흔한 오해**: "대체 텍스트만 넣으면 접근성 완료"라는 생각이 가장 흔한 오해다. 실제로는 키보드 조작, 동적 UI(모달·알림)의 포커스 이동, 오류 메시지의 구체성까지 모두 확인해야 하며, 자동 검사 점수가 100점이어도 실제 업무 흐름은 막혀 있을 수 있다.

## 연결 개념
- KWCAG — WCAG를 국내 표준으로 구체화한 지침, 공공 서비스 검수의 법적 근거
- ARIA — Robust 원칙을 실제 코드로 구현하는 기술 명세
- 사용성(Usability) — 접근성이 확보된 위에서 효율성·만족도를 높이는 상위 품질 속성

# 📝 【답안용】 시험 답안 템플릿

> 목적: 시험장에서 25분에 그대로 쓰는 답안 양식. 작성방식(추상표현 금지·수치·도식·문제유형 전환)을 엄격히 지킨다.
> 핵심: 접근성 답안은 WCAG 2.1 4원칙, A/AA/AAA 기준, 설계·개발·검수 절차, 자동·수동 테스트를 함께 제시해야 한다.

## 핵심 인사이트 (3줄 요약)

> 1. **본질**: 디지털 접근성은 장애와 사용 환경 차이에도 웹·앱 기능을 동등하게 이용하도록 설계·검증하는 품질 속성이다.
> 2. **가치**: WCAG 2.1은 4원칙, 13개 지침, 78개 성공 기준과 A/AA/AAA 수준으로 접근성 검수를 구조화한다.
> 3. **판단 포인트**: 자동 검사만으로는 부족하므로 키보드 조작, 스크린리더, 오류 안내, 명도 대비를 수동 검수와 결합해야 한다.

## 출제 의도 및 답안 포인트

| 출제 의도 | 반드시 짚을 핵심 | 감점 회피 포인트 |
|:---|:---|:---|
| WCAG 구조 이해 확인 | POUR 4원칙, 성공 기준, A/AA/AAA | 대체 텍스트만 접근성으로 축소 |
| 공공 서비스 품질 판단 확인 | 설계 단계 반영, 개발 표준, 검수 증적 | 배포 직전 검사로만 설명 |
| 테스트 전략 확인 | 자동 도구 + 키보드 + 스크린리더 수동 테스트 | 자동 점수 100점이면 완료로 단정 |

> 요약: 접근성 문제는 표준 구조와 실제 검수 절차를 함께 써야 채점 포인트가 확보된다.

## Ⅰ. 개요 및 필요성

- 개요: 모든 사용자의 웹·앱 이용 보장
- 배경: WCAG 2.1은 웹 콘텐츠 접근성을 평가하는 국제 지침이며 4원칙과 성공 기준을 제공한다.
- 필요성: 공공 서비스는 설계, 개발, 검수 전 단계에서 접근성 기준을 반영해야 한다.

---

## Ⅱ. 구조 및 구성요소

```text
사용자 요구 -> WCAG 2.1 4원칙 -> 성공 기준 A/AA/AAA -> 설계/개발 표준 -> 자동+수동 검수 -> 개선 이력
```

| 구성요소 | 역할 | 점검 예시 |
|:---|:---|:---|
| Perceivable | 정보와 UI를 인식 가능하게 제공 | 대체 텍스트, 자막, 명도 대비 |
| Operable | 키보드와 보조기기로 조작 가능하게 설계 | Tab 순서, 포커스 표시, 시간 제한 |
| Understandable | 화면과 오류를 이해 가능하게 제공 | 라벨, 입력 오류 안내, 일관된 내비게이션 |
| Robust | 다양한 브라우저·보조기기와 호환 | 시맨틱 HTML, ARIA, DOM 구조 |

> 요약: WCAG 2.1은 인식, 운용, 이해, 견고함의 4원칙으로 접근성 요구를 검수 가능한 기준으로 분해한다.

## Ⅲ. 동작원리 및 흐름도

```text
요구사항 반영 -> 디자인 검토 -> 시맨틱 개발 -> 자동 검사 -> 키보드/스크린리더 테스트 -> 결함 수정 -> 재검수
```

| 단계 | 처리 내용 | 검증 기준 |
|:---:|:---|:---|
| 1 | RFP와 요구사항에 WCAG 2.1 AA 기준 반영 | 접근성 요구사항 명시 |
| 2 | 디자인 단계에서 명도 대비, 포커스, 오류 안내 검토 | 대비율, 컴포넌트 체크리스트 |
| 3 | 개발 단계에서 시맨틱 HTML과 ARIA 적용 | axe, Lighthouse, 코드 리뷰 |
| 4 | 수동 검수로 실제 업무 완료 확인 | 키보드 전용, 스크린리더, 모바일 조작 |

> 요약: 접근성은 요구사항부터 검수까지 이어지는 품질 활동이며 자동 검사와 수동 테스트를 결합해야 한다.

| 구분 | 일반 UI 검수 | WCAG 2.1 접근성 검수 | 판단 포인트 |

> 요약: WCAG 2.1 검수는 화면 표시가 아니라 다양한 사용자가 동일 업무를 완료하는지 확인하는 활동이다.

## Ⅴ. 심화 비교 및 적용 판단

| 비교 축 | 기존/대안 | WCAG 2.1 접근성 | 선택 기준 |
|:---|:---|:---|:---|
| 구조 | 개발 완료 후 화면 검사 | 요구-디자인-개발-검수 전 단계 반영 | 공공·대민 서비스 전환 시 |
| 비용/성과 | 사후 수정 비용 증가 | 컴포넌트 표준과 자동 검사 내재화 | 재작업률, 결함 밀도 |
| 운영/위험 | 담당자 경험 의존 | 체크리스트와 증적 기반 검수 | 감사·인증·민원 대응 |

> 요약: 접근성은 사후 점검보다 디자인 시스템과 CI 검사에 내재화할 때 결함 수정 비용을 줄인다.

| 리스크 | 원인 | 대응 방안 | 확인 지표 |
|:---|:---|:---|:---|
| 자동 검사 과신 | 도구가 의미·업무 흐름을 판단하지 못함 | 키보드와 스크린리더 수동 테스트 병행 | 수동 결함 비율 |
| 동적 UI 오류 | SPA, 모달, 알림의 포커스 관리 누락 | ARIA Live, Focus Trap, 라우팅 알림 적용 | 포커스 오류 건수 |
| 디자인 불일치 | 색상·컴포넌트 기준 부재 | 접근성 디자인 토큰, 컴포넌트 가이드 | 대비 미달 건수 |

> 요약: 접근성 리스크는 자동 검사 한계, 동적 UI, 디자인 기준 부재이며 수동 검수와 컴포넌트 표준으로 통제한다.

| 점검 항목 | 목표 기준 | 측정 방법 |
|:---|:---|:---|
| 기준 준수 | WCAG 2.1 AA 성공 기준 충족 | 체크리스트, 외부 검수 |
| 자동 검사 | 심각 결함 0건 | axe, Lighthouse CI |
| 수동 테스트 | 주요 업무 10개 키보드·스크린리더 완료 | NVDA, VoiceOver, TalkBack |

> 요약: 접근성 성과는 AA 기준 충족, 자동 검사 심각 결함 0건, 주요 업무 수동 완료 여부로 판단한다.

## Ⅵ. 실무 적용 및 결론

**적용 방안 3개:**
1. RFP와 Definition of Done에 WCAG 2.1 AA, KWCAG, 키보드 조작, 스크린리더 검수 항목을 명시함
2. 디자인 시스템에 대비율, 포커스 표시, 오류 메시지, ARIA 패턴을 컴포넌트 단위로 등록함
3. CI에 axe 또는 Lighthouse 검사를 연결하고 배포 전 NVDA·VoiceOver 수동 테스트 증적을 남김

**결론 (2줄):**
- 기술사 판단: 대민·공공 서비스는 WCAG 2.1 AA를 기준으로 요구사항부터 검수까지 내재화하고, 내부 제한 시스템도 핵심 업무 흐름은 수동 검수함
- 향후 방향: 접근성은 WCAG 2.2, 모바일 앱 접근성, AI 인터페이스 설명 가능성까지 포함해 지속 점검되어야 함
