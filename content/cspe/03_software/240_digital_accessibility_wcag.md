# 📖 【암기용】 개념 완전 이해

> 목적: 디지털 접근성 WCAG 2.1을 처음 보는 사람도 완벽히 이해하게 만든다. 시험 답안 양식이 아니라, 이해를 위한 친절한 설명이다.

## 한눈에
- **개요**: WCAG 2.1은 장애와 사용 환경 차이를 고려해 웹 콘텐츠 접근성을 평가하는 국제 지침이다.
- **왜 필요한가**: 시각, 청각, 운동, 인지 특성이 다른 사용자는 동일한 화면도 접근 방식이 다르다. 접근성은 키보드, 스크린리더, 명도 대비, 대체 텍스트 같은 설계로 서비스 이용 장벽을 줄인다.
- **핵심 직관**: 접근성은 별도 기능이 아니라 모든 사용자가 같은 업무를 완료하도록 입구와 조작 방법을 여러 개 두는 설계다.

## 깊이 이해
- **배경·문제의식**: 웹 서비스가 행정, 금융, 교육, 의료의 기본 창구가 되면서 접근 불가능한 화면은 서비스 배제 문제로 이어진다. WCAG는 개발자가 검수 가능한 성공 기준을 제공한다.
- **작동 원리**: WCAG 2.1은 인식 가능, 운용 가능, 이해 가능, 견고함의 4원칙을 둔다. 각 원칙은 지침과 성공 기준으로 나뉘며 A, AA, AAA 적합성 수준으로 평가한다.
- **비유**: 건물에 계단만 두지 않고 경사로, 엘리베이터, 안내 표시를 함께 제공하는 것과 같다.
- **구체 예시**: 이미지 버튼에 대체 텍스트를 넣고, 키보드 Tab 순서를 논리적으로 만들며, 텍스트와 배경 명도 대비를 WCAG AA 기준에 맞추면 스크린리더와 저시력 사용자의 업무 완료율이 올라간다.
- **흔한 오해·주의점**: 접근성은 색상 보정이나 대체 텍스트만의 문제가 아니다. 키보드 조작, 오류 안내, 동적 콘텐츠 ARIA, 반응형 화면, 모바일 입력까지 함께 검토해야 한다.

## 연결 개념
- KWCAG: 국내 웹 접근성 지침과 공공 서비스 검수 기준
- UI/UX 품질: 사용성, 오류 예방, 반응형 설계와 연결
- 테스트 자동화: axe, Lighthouse, 스크린리더 수동 테스트와 연결

# 📝 【답안용】 시험 답안 템플릿

> 목적: 시험장에서 25분에 그대로 쓰는 답안 양식. 작성방식(추상표현 금지·수치·도식·문제유형 전환)을 엄격히 지킨다.
> 핵심: 접근성 답안은 WCAG 2.1 4원칙, A/AA/AAA 기준, 설계·개발·검수 절차, 자동·수동 테스트를 함께 제시해야 한다.

## 핵심 인사이트 (3줄 요약)

> 1. **본질**: 디지털 접근성은 장애와 사용 환경 차이에도 웹·앱 기능을 동등하게 이용하도록 설계·검증하는 품질 속성이다.
> 2. **가치**: WCAG 2.1은 4원칙, 13개 지침, 78개 성공 기준과 A/AA/AAA 수준으로 접근성 검수를 구조화한다.
> 3. **판단 포인트**: 자동 검사만으로는 부족하므로 키보드 조작, 스크린리더, 오류 안내, 명도 대비를 수동 검수와 결합해야 한다.

## 출제 의도 및 답안 포인트

| 출제 의도 | 반드시 짚을 핵심 | 감점 회피 포인트 |
|:---|:---|:---|
| WCAG 구조 이해 확인 | POUR 4원칙, 성공 기준, A/AA/AAA | 대체 텍스트만 접근성으로 축소 |
| 공공 서비스 품질 판단 확인 | 설계 단계 반영, 개발 표준, 검수 증적 | 배포 직전 검사로만 설명 |
| 테스트 전략 확인 | 자동 도구 + 키보드 + 스크린리더 수동 테스트 | 자동 점수 100점이면 완료로 단정 |

> 요약: 접근성 문제는 표준 구조와 실제 검수 절차를 함께 써야 채점 포인트가 확보된다.

---

## Ⅰ. 개요 및 필요성

- 개요: 모든 사용자의 웹·앱 이용 보장
- 배경: WCAG 2.1은 웹 콘텐츠 접근성을 평가하는 국제 지침이며 4원칙과 성공 기준을 제공한다.
- 필요성: 공공 서비스는 설계, 개발, 검수 전 단계에서 접근성 기준을 반영해야 한다.

---

## Ⅱ. 구조 및 구성요소

```text
사용자 요구 -> WCAG 2.1 4원칙 -> 성공 기준 A/AA/AAA -> 설계/개발 표준 -> 자동+수동 검수 -> 개선 이력
```

| 구성요소 | 역할 | 점검 예시 |
|:---|:---|:---|
| Perceivable | 정보와 UI를 인식 가능하게 제공 | 대체 텍스트, 자막, 명도 대비 |
| Operable | 키보드와 보조기기로 조작 가능하게 설계 | Tab 순서, 포커스 표시, 시간 제한 |
| Understandable | 화면과 오류를 이해 가능하게 제공 | 라벨, 입력 오류 안내, 일관된 내비게이션 |
| Robust | 다양한 브라우저·보조기기와 호환 | 시맨틱 HTML, ARIA, DOM 구조 |

> 요약: WCAG 2.1은 인식, 운용, 이해, 견고함의 4원칙으로 접근성 요구를 검수 가능한 기준으로 분해한다.

---

## Ⅲ. 동작원리 및 흐름도

```text
요구사항 반영 -> 디자인 검토 -> 시맨틱 개발 -> 자동 검사 -> 키보드/스크린리더 테스트 -> 결함 수정 -> 재검수
```

| 단계 | 처리 내용 | 검증 기준 |
|:---:|:---|:---|
| 1 | RFP와 요구사항에 WCAG 2.1 AA 기준 반영 | 접근성 요구사항 명시 |
| 2 | 디자인 단계에서 명도 대비, 포커스, 오류 안내 검토 | 대비율, 컴포넌트 체크리스트 |
| 3 | 개발 단계에서 시맨틱 HTML과 ARIA 적용 | axe, Lighthouse, 코드 리뷰 |
| 4 | 수동 검수로 실제 업무 완료 확인 | 키보드 전용, 스크린리더, 모바일 조작 |

> 요약: 접근성은 요구사항부터 검수까지 이어지는 품질 활동이며 자동 검사와 수동 테스트를 결합해야 한다.

## Ⅳ. 특징

| 구분 | 일반 UI 검수 | WCAG 2.1 접근성 검수 | 판단 포인트 |
|:---|:---|:---|:---|
| 기준 | 화면 표시와 기능 동작 | 성공 기준 A/AA/AAA | 공공 서비스는 AA 목표 설정 가능 |
| 방법 | 브라우저 기능 테스트 | 자동 도구 + 보조기기 수동 검수 | 자동 검사 한계 인식 |
| 범위 | 시각 중심 사용성 | 시각·청각·운동·인지 특성 고려 | 업무 완료 가능성 |

> 요약: WCAG 2.1 검수는 화면 표시가 아니라 다양한 사용자가 동일 업무를 완료하는지 확인하는 활동이다.

## Ⅴ. 심화 비교 및 적용 판단

| 비교 축 | 기존/대안 | WCAG 2.1 접근성 | 선택 기준 |
|:---|:---|:---|:---|
| 구조 | 개발 완료 후 화면 검사 | 요구-디자인-개발-검수 전 단계 반영 | 공공·대민 서비스 전환 시 |
| 비용/성과 | 사후 수정 비용 증가 | 컴포넌트 표준과 자동 검사 내재화 | 재작업률, 결함 밀도 |
| 운영/위험 | 담당자 경험 의존 | 체크리스트와 증적 기반 검수 | 감사·인증·민원 대응 |

> 요약: 접근성은 사후 점검보다 디자인 시스템과 CI 검사에 내재화할 때 결함 수정 비용을 줄인다.

| 리스크 | 원인 | 대응 방안 | 확인 지표 |
|:---|:---|:---|:---|
| 자동 검사 과신 | 도구가 의미·업무 흐름을 판단하지 못함 | 키보드와 스크린리더 수동 테스트 병행 | 수동 결함 비율 |
| 동적 UI 오류 | SPA, 모달, 알림의 포커스 관리 누락 | ARIA Live, Focus Trap, 라우팅 알림 적용 | 포커스 오류 건수 |
| 디자인 불일치 | 색상·컴포넌트 기준 부재 | 접근성 디자인 토큰, 컴포넌트 가이드 | 대비 미달 건수 |

> 요약: 접근성 리스크는 자동 검사 한계, 동적 UI, 디자인 기준 부재이며 수동 검수와 컴포넌트 표준으로 통제한다.

| 점검 항목 | 목표 기준 | 측정 방법 |
|:---|:---|:---|
| 기준 준수 | WCAG 2.1 AA 성공 기준 충족 | 체크리스트, 외부 검수 |
| 자동 검사 | 심각 결함 0건 | axe, Lighthouse CI |
| 수동 테스트 | 주요 업무 10개 키보드·스크린리더 완료 | NVDA, VoiceOver, TalkBack |

> 요약: 접근성 성과는 AA 기준 충족, 자동 검사 심각 결함 0건, 주요 업무 수동 완료 여부로 판단한다.

## Ⅵ. 실무 적용 및 결론

**적용 방안 3개:**
1. RFP와 Definition of Done에 WCAG 2.1 AA, KWCAG, 키보드 조작, 스크린리더 검수 항목을 명시함
2. 디자인 시스템에 대비율, 포커스 표시, 오류 메시지, ARIA 패턴을 컴포넌트 단위로 등록함
3. CI에 axe 또는 Lighthouse 검사를 연결하고 배포 전 NVDA·VoiceOver 수동 테스트 증적을 남김

**결론 (2줄):**
- 기술사 판단: 대민·공공 서비스는 WCAG 2.1 AA를 기준으로 요구사항부터 검수까지 내재화하고, 내부 제한 시스템도 핵심 업무 흐름은 수동 검수함
- 향후 방향: 접근성은 WCAG 2.2, 모바일 앱 접근성, AI 인터페이스 설명 가능성까지 포함해 지속 점검되어야 함
