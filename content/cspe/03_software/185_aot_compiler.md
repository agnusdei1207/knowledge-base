## Ⅰ. 개요
- **정의**: 프로그램 실행 전(빌드 타임)에 바이트코드 또는 소스를 네이티브 기계어로 변환하는 컴파일러
- **배경/필요성**: JIT(184 참조)의 워밍업 지연과 메모리 오버헤드를 제거하여 즉시 기동이 요구되는 환경에 적합한 실행 방식이 필요함
- **비유**: 출판 전에 완역된 책을 인쇄해두면 독자가 펼치자마자 읽을 수 있는 것과 유사함

| 출제 의도 | 반드시 짚을 핵심 | 감점 회피 포인트 |
|:---|:---|:---|
| AOT의 장단점과 JIT 대비 차이 | 즉시 기동·낮은 메모리·런타임 최적화 불가 트레이드오프 | Closed-World Assumption(모든 코드가 빌드 시 결정)의 제약 명시 |

> 요약: 빌드 타임에 네이티브 변환을 완료하여 즉시 기동과 낮은 메모리 사용을 달성하는 기법임

## Ⅱ. 구성요소
```text
Source / Bytecode
       |
       v
+------------------+
| Static Analysis  |
+------------------+
       |
       v
+------------------+
| AOT Compiler     |
+------------------+
       |
       v
+------------------+
| Native Binary    |
+------------------+
       |
       v
Direct Execution
```

| 구성요소 | 설명 | 비유 |
|:---|:---|:---|
| 정적 분석 | 도달 가능 코드·타입 정보를 빌드 시 전수 분석 | 여행 전 전체 일정 확정 |
| AOT 컴파일러 | 분석 결과를 바탕으로 타깃 ISA 네이티브 코드 생성 | 확정 일정에 맞춰 항공권 사전 발권 |
| 네이티브 바이너리 | VM 없이 OS 위에서 독립 실행 가능한 산출물 | 발권 완료된 e-티켓 |

> 요약: 정적 분석-네이티브 변환-독립 바이너리 생성으로 VM 의존성을 제거함

## Ⅲ. 절차
```text
소스/바이트코드 --> 정적 도달성 분석 --> 네이티브 코드 생성 --> 링킹 --> 독립 실행파일 출력
```
- 1단계: 소스 또는 바이트코드를 입력받아 전체 호출 그래프 구성
- 2단계: 도달 가능 클래스·메서드만 추출하고 리플렉션·동적 로딩 대상을 설정 파일로 명시
- 3단계: 타깃 아키텍처에 맞는 네이티브 코드를 생성하고 GC·런타임 서브스트레이트 포함
- 4단계: 정적 링킹을 수행하여 단일 실행 파일(또는 공유 라이브러리) 산출

> 요약: 호출 그래프 분석-도달성 추출-네이티브 생성-링킹의 4단계로 독립 바이너리를 생성함

## Ⅳ. 문제점
- 동적 기능 제약: 리플렉션·동적 프록시·클래스 로딩이 빌드 시 결정되지 않으면 사용 불가 — 프레임워크 호환성 저하
- 피크 성능 한계: 런타임 프로파일 정보 없이 정적 최적화만 수행 — JIT 대비 장기 실행 시 성능 열위
- 빌드 시간 증가: 전체 프로그램 분석과 네이티브 컴파일로 빌드 시간이 수 분~수십 분 소요 — 개발 반복 사이클 저하

> 요약: 동적 기능·피크 성능·빌드 시간에서 JIT 대비 트레이드오프가 존재함

## Ⅴ. 개선방안
1. 단기: 리플렉션 메타데이터 자동 수집 도구(GraalVM Tracing Agent 등) 활용으로 동적 기능 호환성 향상
2. 중기: PGO(Profile-Guided Optimization) 데이터를 AOT 빌드에 반영하여 정적 최적화 품질 개선
3. 장기: 증분 AOT 컴파일 기법 개발로 변경 모듈만 재컴파일하여 빌드 시간 단축

> 요약: 메타데이터 자동화·PGO·증분 컴파일로 AOT의 제약을 완화함

## Ⅵ. 전망
- 발전 방향: 컨테이너·서버리스 환경에서 즉시 기동 요구 증가로 AOT 네이티브 이미지 채택 확대
- 기술사적 판단: Spring Native, Quarkus 등 프레임워크가 AOT를 기본 지원하며 생태계가 성숙하고 있음
- 기술사 제언: JIT 워밍업 데이터와 AOT 정적 분석을 결합한 하이브리드 컴파일 파이프라인 설계가 필요함
