## Ⅰ. 개요
- **정의**: 단위 시간당 허용 요청 수를 제한하여 시스템을 과부하로부터 보호하는 기법
- **배경/필요성**: 제한 없는 요청 수용은 서버 자원 고갈, 서비스 장애, 악의적 남용으로 이어짐
- **비유**: 놀이공원 입장 인원을 시간당 제한하여 안전과 체험 품질을 유지하는 것

| 출제 의도 | 반드시 짚을 핵심 | 감점 회피 포인트 |
|:---|:---|:---|
| 알고리즘별 특성과 분산 환경 적용 | Token Bucket, Sliding Window 차이 | 분산 환경에서 카운터 동기화 문제를 언급할 것 |

> 요약: 요청 빈도를 제어하여 시스템 안정성과 공정성을 확보하는 보호 기법임

## Ⅱ. 구성요소
```text
Client --> Rate Limiter --허용--> Backend Server
                |
              초과
                |
                v
           429 Too Many Requests
```

| 구성요소 | 설명 | 비유 |
|:---|:---|:---|
| Rate Limiter | 요청 빈도를 측정하고 임계치 초과 시 차단하는 게이트 | 입장 카운터 |
| 알고리즘 | Token Bucket, Leaky Bucket, Fixed/Sliding Window 등 제한 방식 | 입장 규칙 |
| 카운터 저장소 | 요청 횟수를 기록하는 인메모리/분산 저장소(Redis 등) | 출입 기록부 |

> 요약: 게이트-알고리즘-카운터로 구성된 요청 제어 체계임

## Ⅲ. 절차
```text
요청 도착 --> 카운터 조회 --> 임계치 비교 --> 허용/거부
```
- 1단계: 요청 도착 — 클라이언트 요청이 Rate Limiter에 진입
- 2단계: 카운터 조회 — 요청자 식별키(IP, API Key 등) 기준으로 현재 카운트 조회
- 3단계: 임계치 비교 — 카운트가 설정 한도 이내인지 판정
- 4단계: 허용/거부 — 이내이면 백엔드 전달 및 카운트 증가, 초과 시 429 응답 반환

> 요약: 도착-조회-비교-판정의 4단계로 요청 빈도를 제어함

## Ⅳ. 문제점
- 분산 카운터 동기화: 다수 LB/게이트웨이에서 카운터 불일치로 한도를 초과 허용함
- 정당 사용자 차단: 공유 IP 환경에서 무관한 사용자까지 제한됨
- 버스트 허용 부재: Fixed Window는 윈도우 경계에서 2배 버스트가 발생함

> 요약: 분산 동기화, 오탐, 윈도우 경계 버스트가 주요 과제임

## Ⅴ. 개선방안
1. 단기: Redis 기반 중앙 카운터로 분산 환경 카운터 동기화
2. 중기: API Key·JWT 등 사용자별 식별 체계 도입으로 오탐 감소
3. 장기: Sliding Window Log 알고리즘 적용으로 경계 버스트 제거

> 요약: 중앙 카운터, 사용자 식별, 고급 알고리즘 순으로 정밀도를 향상함

## Ⅵ. 전망
- 발전 방향: API Gateway에 내장된 적응형 Rate Limiting이 표준화되는 추세
- 기술사적 판단: DDoS 방어, API 과금, 공정 사용 정책의 기술적 기반으로 중요성 증대
- 기술사 제언: 서비스 등급별 차등 제한 정책을 API 거버넌스에 포함할 필요
