## 핵심 인사이트 (3줄 요약)
- 특정 사용자나 IP가 1초에 API를 100번씩 미친 듯이 호출해서 서버를 죽이거나 해킹(Brute Force)하는 것을 막기 위해, **"1분에 10번까지만 호출 가능!"이라고 방어막을 치는 API 보호 기술**.
- 허용량을 넘었을 때 완전히 차단해버리면 **Rate Limiting(429 Too Many Requests 에러 반환)**, 차단하지 않고 대기줄(Queue)에 세워뒀다가 천천히 처리해 주면 **Throttling(조절)**이라고 부름.
- 토큰 버킷(Token Bucket), 누수 버킷(Leaky Bucket) 같은 알고리즘을 사용하며, MSA 환경에서는 API Gateway 단에서 Redis와 연동하여 글로벌하게 통제하는 것이 필수 아키텍처임.
---
## Ⅰ. 개요 및 필요성
- **개요**: 시스템 자원(CPU, 메모리, DB)의 과부하를 방지하고, 특정 클라이언트의 독점적 리소스 사용이나 악의적 공격을 차단하기 위해 들어오는 요청의 속도와 횟수를 제어하는 메커니즘.
- **필요성**: 오픈 API를 만들었음. A 회사가 우리 API를 초당 1,000번씩 긁어가서 우리 DB가 터짐. 다른 선량한 B 회사도 접속을 못 함. **"아니, 무식하게 들어온다고 다 받아주지 마! 한 놈이 1초에 10번 이상 호출하면 얄짤없이 에러(429)를 뱉어서 입구를 닫아버려라!"**
---
## Ⅱ. 아키텍처 및 핵심 원리
- **1. 토큰 버킷 알고리즘 (Token Bucket - 가장 많이 씀)**:
  - 유저마다 가상의 '바구니(버킷)'를 줌. 바구니 안에는 1분에 10개씩 '티켓(토큰)'이 자동으로 채워짐.
  - 유저가 API를 1번 쏠 때마다 티켓을 1개씩 제출해야 함.
  - 티켓을 다 썼는데 또 API를 쏘면? ➡️ 문지기가 "티켓 없잖아! 돌아가! (HTTP 429 Error)"라며 내쫓음.
  - 트래픽이 한꺼번에 팍! 터지는 것(Burst)을 어느 정도 허용해 줌 (바구니에 10개가 꽉 차 있으면 1초 만에 10번 다 쏴도 통과됨).
- **2. 누수 버킷 알고리즘 (Leaky Bucket)**:
  - 밑 빠진 독(구멍 뚫린 양동이)에 물(요청)을 쏟아부음.
  - 물은 항상 **'일정한 속도(예: 1초에 1방울)'**로만 아래로 떨어져서 서버로 감.
  - 양동이 용량을 넘치게 물을 부으면? 넘친 물(요청)은 다 버려짐(차단).
  - 트래픽을 아주 매끄럽고 일정한 속도(Load Leveling)로 다듬어주는 효과가 있음.
- **3. 고정 창 카운터 (Fixed Window Counter)**:
  - 1시 00분~1시 01분 사이에 딱 10번만 허용. 1시 01분이 땡! 치면 카운트 리셋. (구현은 쉽지만 경계선 시간대에 트래픽이 몰리는 단점이 있음).

```text
[ Rate Limiting 작동 흐름도 (Redis 활용) ]

 👤 해커 "초당 100번 호출 공격!!"
   ⬇️
 🛡️ [ API Gateway ] 
   |-- 1. 해커의 IP 획득 (192.168.1.5)
   |-- 2. 🧠 [ Redis ] 에 물어봄: "이 IP 이번 분에 몇 번 호출했어?"
   |-- 3. Redis: "어우, 벌써 99번 호출했어! 제한이 100번이야!"
   |-- 4. 한 번 더 호출 들어옴 ➡️ 100번 초과!
   |
   ⬇️ ❌ 거절 (HTTP 429 Too Many Requests)
 👤 해커 "앗 차단당했다.." 
 * 💡 뒷단의 진짜 백엔드 서버(Spring Boot)는 이 공격을 구경도 못 함. 평화로움.
```

## Ⅲ. 비교 및 연결
| 구분 | Rate Limiting (제한) | Throttling (스로틀링/조절) |
|---|---|---|
| **동작 방식** | 제한치 초과 시 **즉시 연결 끊고 에러 반환** | 제한치 초과 시 **에러 안 내고 큐에 넣어 천천히 처리** |
| **HTTP 응답** | `429 Too Many Requests` | 늦게라도 `200 OK` (대신 무한 로딩 걸림) |
| **비유** | 놀이공원 매진 시 **"오늘 문 닫았습니다. 가세요!"** | 놀이공원 꽉 찼을 때 **"대기줄에 서서 1시간만 기다리세요"** |
| **주 사용처** | 외부 공개 API, 해킹 방어 | 백그라운드 데이터 동기화, 내부 배치 처리 |
---
## Ⅳ. 실무 적용 및 기술사 판단
- **API Gateway 계층에서의 중앙 통제**: Rate Limiting 로직을 백엔드 비즈니스 로직(Java/Node.js) 안에 짜넣는 것은 자원 낭비임. 해커의 트래픽이 일단 백엔드 앱까지 살아서 들어왔다는 것 자체가 이미 CPU와 스레드를 소모시켰다는 뜻임. 기술사는 반드시 **가장 최전방인 API Gateway(Kong, Nginx) 레벨에서 쳐내도록 아키텍처를 설계**하여 비즈니스 서버를 완벽히 격리(Isolation)해야 함.
- **분산 환경의 동기화 문제**: 서버가 5대일 때, 로컬 메모리로 횟수를 카운트하면 해커가 1번 서버 10번, 2번 서버 10번을 치면서 제한(10번)을 뚫어버림. 실무에서는 여러 대의 API Gateway가 횟수 데이터를 공유할 수 있도록 반드시 **Redis 같은 초고속 글로벌 메모리 DB**를 둬서 중앙에서 카운트를 합산 관리하게 만들어야 함.

## Ⅴ. 기대효과 및 결론
- 한 명의 악성 유저나 버그 난 클라이언트가 전체 서버 자원을 독식하는 현상(Noisy Neighbor)을 막아내어, 시스템의 안정성과 공정성을 보장함.
- API를 상품화하여 파는 클라우드 시대(Stripe, Twilio 등)에, 돈을 낸 만큼만 API를 부를 수 있게 만드는 **'API 과금 모델(Monetization)'의 핵심 기반 기술**임.

### 👶 어린이를 위한 3줄 비유 설명
1. 뷔페에 갔는데, 한 욕심쟁이 아저씨가 맛있는 고기를 한 번에 100접시씩 다 퍼가면 다른 사람들은 못 먹잖아요?
2. 그래서 식당 주인이 **"1인당 5분에 고기 1접시만 가능!"**이라는 규칙(Rate Limiting)을 만들었어요.
3. 아저씨가 또 고기를 가지러 오면 요리사가 "삐-! 5분 아직 안 지났어요! 돌아가세요!(429 에러)"라고 막아서 모두가 사이좋게 먹을 수 있게 해 준답니다!
