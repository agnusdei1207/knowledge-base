# 📖 【암기용】 개념 완전 이해

## 한눈에
- **개요**: 시스템 보호를 위해 클라이언트나 API가 특정 시간 동안 보낼 수 있는 요청 횟수를 통제하고 제한하는 메커니즘
- **왜 필요한가**: 악의적인 공격(DDoS), 잘못 짠 매크로, 또는 순간적인 트래픽 폭주로부터 백엔드 서버 자원 고갈과 전체 시스템 마비를 막기 위해 필수적이다.
- **핵심 직관**: 놀이공원 입장 게이트. 한꺼번에 만 명이 몰리면 놀이공원 안이 엉망이 되므로, 1분에 100명씩만 들여보내고 나머지는 줄 세우거나(Throttling) 돌려보낸다(Rate Limiting).

## 핵심 용어 정리

| 용어/표기 | 의미 | 비유·예 |
|:---|:---|:---|
| Rate Limiting | 허용된 한도를 초과한 요청을 즉시 거부(HTTP 429) 처리 | "표 다 팔렸어, 돌아가!" |
| Throttling | 한도를 초과한 요청을 큐(Queue)에 담아 지연(Delay) 처리하여 트래픽 평탄화 | "잠깐 줄 서서 기다려, 차례대로 들여보내줄게" |
| Token Bucket | 토큰이 버킷에 일정한 속도로 쌓이고, 요청 시 토큰을 소모하는 알고리즘 | 오락실 코인 바구니, 코인 없으면 게임 불가 |
| Leaky Bucket | 물(요청)이 쏟아져도 양동이 바닥 구멍으로 일정한 속도로 물이 새어나감 | 깔때기, 들어오는 양 무관하게 나가는 속도 고정 |

## 깊이 이해
- **배경·문제의식**: MSA 환경은 API 호출이 꼬리를 물고 일어나므로(Cascading), 특정 사용자의 API 과다 호출이 한 서비스를 죽이면 전체 시스템 장애(Ripple Effect)로 번진다.
- **작동 원리**:
  - 클라이언트 요청 시 게이트웨이나 미들웨어가 "이 클라이언트 IP/API Key가 최근 1분간 몇 번 요청했나?"를 레디스(Redis) 같은 캐시에서 조회한다.
  - 한도 이내면 Pass, 한도 초과 시 **429 Too Many Requests** 오류 반환(Rate Limit) 또는 대기열 진입(Throttle).
- **비유**: 
  - Token Bucket: 통신사 데이터 요금제. 매달 1일 데이터(토큰) 리필, 안 쓰면 모이고, 다 쓰면 차단. 순간적인 폭발적 사용(Burst) 허용.
  - Leaky Bucket: 정수기 필터. 물을 들이부어도 쫄쫄쫄 일정하게만 나옴. Burst 허용 불가, 완전히 평탄한 트래픽.
- **구체 예시**: 오픈 API (예: Google Maps API)에서 "초당 50건, 월 10만 건 한도". 초과 시 결제 유도.
- **흔한 오해·주의점**: Rate Limiting은 100% 차단만 의미하지 않는다. 비즈니스 중요도에 따라, 초과 시 캐싱된 옛날 데이터를 주거나(Fallback), 과금 단가를 높이는 유연한 설계가 가능하다.

## 연결 개념
- API 게이트웨이
- 서킷 브레이커 패턴 (Circuit Breaker)
- 마이크로서비스 아키텍처 MSA

# 📝 【답안용】 시험 답안 템플릿

## 핵심 인사이트 (3줄 요약)

> 1. **본질**: 시스템 처리 용량을 넘어서는 인바운드 트래픽에 대해, 초과분을 거부(Rate Limiting)하거나 지연(Throttling)시켜 인프라를 보호하는 방어 메커니즘이다.
> 2. **가치**: 특정 사용자나 악성 매크로의 자원 독점을 방지하고, 백엔드 서비스의 가용성(Availability)과 안정적 응답 시간(SLA)을 보장한다.
> 3. **판단 포인트**: 트래픽 억제 목적에 따라 토큰 버킷(Burst 허용), 누수 버킷(평탄화), 고정 윈도우 등 통제 알고리즘의 성질을 맞춤 적용해야 한다.

## 출제 의도 및 답안 포인트

| 출제 의도 | 반드시 짚을 핵심 | 감점 회피 포인트 |
|:---|:---|:---|
| 대규모 트래픽 환경의 시스템 방어 설계 이해 | 거부(Limiting) vs 지연(Throttling), HTTP 429 상태 코드 | Rate Limit과 Circuit Breaker(장애 전파 방지)의 혼동 |
| 통제 알고리즘 원리 파악 및 트레이드오프 판별 | Token Bucket, Leaky Bucket, Sliding Window 원리 비교 | 알고리즘을 단순 나열하고 "토큰이 좋다"식 단정 |

> 요약: 시스템 과부하를 막는 방어 수단임을 명시하고, 비즈니스 성격에 따라 트래픽을 즉시 끊어낼지 늦출지, 알고리즘은 무엇을 쓸지 선택 기준을 제시해야 한다.

---

## Ⅰ. 개요 및 필요성

- 개요: API나 네트워크 엔드포인트에 대한 클라이언트의 단위 시간당 요청 횟수를 통제하고 제어하는 트래픽 관리 기법
- 배경: 대용량 트래픽 스파이크, 분산 서비스 거부(DDoS) 공격, 버그성 스크립트로 인한 백엔드 자원(CPU, DB 연결) 급속 고갈
- 필요성: 시스템 가용성 유지, 다수 사용자에 대한 공평한 자원 분배, API 과금 모델(Monetization) 기반 제공

---

## Ⅱ. 구조 및 구성요소

```text
클라이언트 -> API Gateway / Load Balancer (Rate Limiter 연동) -> 내부 WAS
                     |
            (규칙 및 카운터 저장)
            Redis (In-Memory DB)
```

| 구성요소 | 역할 | 특이사항 |
|:---|:---|:---|
| Interceptor / Gateway | 요청 인입점 통제 및 제한 임계치 초과 여부 검사 | API Gateway에서 중앙 통제 권장 |
| 분산 저장소 (Redis) | 분산 환경에서 클라이언트(IP, API Key)별 호출 카운트 공유 | 빠르고 원자적인 증감 연산(INCR) 처리 |
| 통제 알고리즘 | 한도 초과 판별 로직 (Token Bucket 등) | 트래픽 버스트 수용 여부 결정 |
| Fallback / Reject | 초과 트래픽에 대한 대응 (HTTP 429 반환 또는 대기열 추가) | 사용자 경험 위한 Retry-After 헤더 제공 |

> 요약: 분산 환경에서는 개별 서버 메모리가 아닌, 레디스 같은 중앙 공유 저장소를 통해 호출 카운트를 통제해야 일관성이 맞는다.

---

## Ⅲ. 동작원리 및 흐름도

```text
요청 도달 -> 클라이언트 식별(Key) -> 알고리즘 기반 한도 갱신/검사 -> (초과) 차단/지연 
                                                                -> (통과) 트래픽 전달
```

- 1단계 [식별자 추출]: 들어온 요청의 IP 주소, API 키, 사용자 토큰 등 제한 기준(Key) 추출
- 2단계 [카운트 갱신]: Redis 등 중앙 캐시에서 해당 Key의 단위 시간당 현재 카운트 또는 토큰 잔량 조회
- 3단계 [임계치 검증]: 선택된 알고리즘을 통해 잔여 용량이 허용 범위 이내인지 원자적(Atomic) 판별
- 4단계 [통제 반영]: 허용 시 카운트 증가 후 백엔드 전송, 초과 시 429 Too Many Requests 응답 또는 메시지 큐 적재

> 요약: 찰나의 순간에 들어오는 다건의 요청을 원자적(Atomic)으로 계수하여 정해진 규칙 안에 묶어두는 과정이다.

---

## Ⅳ. 특징
- 서비스 방어벽: 예측 불가능한 트래픽 폭주로부터 백엔드와 DB의 치명적 장애(Cascading Failure)를 1차 방어
- API 비즈니스 모델링: Tier별(무료/프리미엄) 허용량(Quota)을 다르게 설정하여 SaaS형 과금 비즈니스(SLA)의 핵심 기반으로 작용
- 지연 시간 트레이드오프: 모든 요청 시마다 중앙 Redis를 조회하므로, 통제 로직 자체가 마이크로초 단위의 네트워크 지연(Overhead) 야기

> 요약: 시스템 보호와 수익화의 필수 장치이나, 통제 로직 자체의 부하와 정합성 관리가 병행되어야 한다.

---

## Ⅴ. 심화 비교 및 적용 판단

| 알고리즘 비교 축 | 토큰 버킷 (Token Bucket) | 누수 버킷 (Leaky Bucket) | 슬라이딩 윈도우 로그 (Sliding Window Log) | 선택 기준 |
|:---|:---|:---|:---|:---|
| 동작 원리 | 정기적 토큰 리필, 토큰 소모 | 요청을 큐에 담고 일정 속도 유출 | 요청의 타임스탬프를 로그로 기록하여 계산 | 트래픽 패턴 수용 |
| 버스트(Burst) | 토큰 한도 내에서 한순간 폭주 허용 | 허용 안 함 (항상 평탄화 처리) | 정밀하게 계산하여 허용 한도 통제 | 엄격성 요구도 |
| 메모리 효율 | 메모리 적음, 대규모 통제 적합 | 메모리 적음, 메시지 큐 활용 | 타임스탬프 개별 저장으로 낭비 극심 | 리소스 제약 |
| 적용 사례 | 일반적인 웹 API 통제 (AWS 등) | 비동기 백그라운드 작업, 라우터 | 엄격한 금융/결제 API 호출 통제 | 비즈니스 도메인 |

> 요약: 짧은 순간의 트래픽 폭주를 정상으로 볼 것인가(Token Bucket) 막을 것인가(Leaky Bucket)에 따라 선택이 나뉜다.

**리스크·대응 (기본은 불릿):**
- Race Condition 카운트 오류: 다수 서버 동시 갱신 시 카운터 정합성 깨짐 초과 허용 → Redis INCR 명령어 활용 또는 Lua Script로 원자성(Atomicity) 보장 (지표: 한도 초과된 비정상 통과 건수)
- 통제 서버 장애 전파: Redis 장애 시 전체 API 요청 대기 및 타임아웃 → Fall-open(에러 시 무조건 통과) 또는 로컬 인메모리 캐시 폴백 설계 (지표: Rate Limiter 지연 시간)

## Ⅵ. 실무 적용 및 결론

**적용 방안 3개:**
1. 다층 통제(Multi-Layer) 아키텍처: L4/L7 방화벽 레벨에서 IP 기반 악성 볼륨 통제(DDoS 차단)를 1차로 하고, API Gateway에서 비즈니스(User ID/API Key) 통제를 2차로 분리 적용
2. Retry-After 헤더 및 클라이언트 백오프: 429 오류 반환 시 '몇 초 뒤에 재시도하라'는 헤더를 포함하고, 클라이언트는 지수 백오프(Exponential Backoff)로 재요청하게 하여 네트워크 낭비 억제
3. 동적 임계치 조절 기능: 프로메테우스(Prometheus) 모니터링 메트릭과 연동하여, 백엔드 CPU가 80%를 넘으면 Rate Limit 임계치를 동적으로 낮추는 자가 치유(Self-Healing) 로직 도입

**결론:**
- 기술사 판단: 한도 통제는 단순히 막는 것이 목적이 아니라, "처리할 수 있는 만큼만 받아내어 시스템이 죽지 않게 하는" 핵심 회복 탄력성(Resilience) 설계다.
- 향후 방향: 정적인 수치 기반 제한에서 벗어나, 머신러닝 모델이 정상/비정상 트래픽 패턴을 분석하여 사용자별 한도를 실시간으로 자동 튜닝하는 AI 기반 통제로 진화하고 있다.
