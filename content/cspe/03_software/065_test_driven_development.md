# 📖 【암기용】 개념 완전 이해

## 한눈에
- **개요**: 실제 코드를 짜기 전에 "실패하는 테스트 코드"를 먼저 작성하고, 그 테스트를 통과할 만큼만 실제 코드를 구현하는 짧은 주기의 개발 방법론
- **왜 필요한가**: 기능부터 짜고 나중에 테스트를 붙이려 하면, 코드가 이미 복잡해져서 테스트하기 어렵고 예외 상황을 놓치기 십상이다.
- **핵심 직관**: "목표(테스트)를 먼저 세워놓고, 그 목표를 달성하는 최소한의 짓만 한다. 그리고 나서 코드를 예쁘게 다듬는다."

## 핵심 용어 정리

| 용어/표기 | 의미 | 비유·예 |
|:---|:---|:---|
| Red | 실패하는 테스트 코드 작성 (아직 구현이 없으므로 실패) | 빨간불: "이 기능이 필요해!" |
| Green | 테스트를 통과하기 위한 최소한의 실제 코드 작성 | 초록불: "일단 굴러가게 만들었어!" |
| Refactor | 동작은 유지한 채 코드 구조와 중복을 개선 | 다듬기: "이제 깔끔하게 정리하자" |
| 테스트 더블 (Mock, Stub) | 외부 의존성(DB, API 등)을 대체하는 가짜 객체 | 연극의 대역 배우 |

## 깊이 이해
- **배경·문제의식**: 기존 개발(코드 먼저 -> 테스트 나중)은 마감에 쫓기면 테스트를 생략하게 만들고, 코드가 뚱뚱해져(강한 결합) 테스트 뼈대를 끼워넣기 힘들다. XP(Extreme Programming) 창시자 켄트 벡이 이를 극복하고자 제안했다.
- **작동 원리**: TDD 사이클은 `Red -> Green -> Refactor`의 무한 반복이다. 로그인 함수를 만든다면, ① "빈 패스워드면 False를 반환한다"는 테스트 코드를 짠다(Red). ② 함수에 `return False`라고 무식하게 하드코딩해서 통과시킨다(Green). ③ 하드코딩을 실제 로직으로 바꾸고 중복을 제거한다(Refactor).
- **비유**: 건물을 지을 때, 철근 뼈대(테스트)를 먼저 촘촘히 세워두고 그 사이에 시멘트(실제 코드)를 붓는 것. 뼈대가 이미 잡아주므로 시멘트가 잘못 퍼질 일이 없다.
- **구체 예시**: 자바 `JUnit`을 열고 `assertEquals(2, add(1,1))`을 먼저 작성. `add` 함수가 없으므로 컴파일 에러(Red). `add` 함수를 만들고 `return 2` 작성하여 성공(Green). 입력 파라미터 `a+b`를 반환하도록 수정(Refactor).
- **흔한 오해·주의점**: "TDD를 하면 개발 속도가 엄청 느려진다?" 초기 코딩 속도는 확실히 느리다(테스트를 짜야 하니까). 그러나 디버깅 시간과 유지보수 시간이 획기적으로 줄어들어, 프로젝트 전체 수명주기로 보면 오히려 훨씬 빠르다.

## 연결 개념
- BDD (Behavior-Driven Development): TDD를 확장하여 비즈니스 요구사항(Given/When/Then) 중심으로 테스트를 짜는 기법
- CI/CD 파이프라인: TDD로 만들어진 촘촘한 단위 테스트들이 CI에서 빛을 발함
- 애자일 (Agile) / XP: TDD를 필수 프랙티스로 채택하는 개발 방법론

# 📝 【답안용】 시험 답안 템플릿

## 핵심 인사이트 (3줄 요약)

> 1. **본질**: TDD는 실패하는 단위 테스트(Red)를 먼저 작성하고, 이를 통과하는 최소 코드(Green)를 구현한 뒤, 지속적으로 리팩터링(Refactor)하는 짧은 사이클의 개발 방법론이다.
> 2. **가치**: 테스트 커버리지를 자연스럽게 100%에 가깝게 유지하여 결함을 조기 발견하고, 개발자에게 코드 설계(응집도 향상, 결합도 저하)를 강제하는 효과가 있다.
> 3. **판단 포인트**: TDD의 3단계 사이클 구조와 기존 개발 프로세스(Test-Last)와의 차이점, 그리고 도입 시의 트레이드오프(초기 비용 vs 유지보수 이점)를 비교해야 한다.

## 출제 의도 및 답안 포인트

| 출제 의도 | 반드시 짚을 핵심 | 감점 회피 포인트 |
|:---|:---|:---|
| TDD 사이클의 정확한 이해 | Red - Green - Refactor 3단계 흐름, 짧은 피드백 루프 | TDD를 단순 단위 테스트 작성 행위로만 서술 |
| 전통적 개발론과의 차별성 | Test-First vs Test-Last, 설계 강제성, 오버엔지니어링 방지 | 코드 작성 속도 저하를 단점으로만 치부 |
| 실무 한계 및 극복 방안 | 레거시 코드 적용 어려움, Mock/Stub 활용, BDD 확장 | 테스트 도구(JUnit 등) 사용법에 치중 |

> 요약: TDD는 단순한 테스트 기법이 아니라, 테스트를 통해 시스템 설계를 주도(Driven)하는 객체지향 설계 방법론임을 강조해야 한다.

## Ⅰ. 개요 및 필요성

- 개요: 실제 코드를 작성하기 전에 결함을 잡아낼 테스트 코드를 먼저 작성하고, 이를 통과하는 코드를 구현하여 점진적으로 리팩터링하는 애자일 개발 기법
- 배경: 개발 후반부에 테스트를 몰아서 수행하면 테스트 작성이 어렵고(결합도 증가), 마감 압박으로 인해 테스트가 누락되는 문제 만연
- 필요성: 명확한 요구사항 이해 기반의 코딩(오버엔지니어링 방지), 수정 시 기존 기능이 깨지지 않는다는 심리적 안정감(안전망) 확보, 모듈화된 설계 유도

---

## Ⅱ. 구조 및 구성요소

```text
[요구사항/설계]
      |
      v
+--> [Red: 실패하는 테스트 작성] (인터페이스/명세 결정)
|     |
|     v
|    [Green: 최소 코드 구현] (테스트 통과 목적)
|     |
|     v
+--- [Refactor: 리팩터링] (중복 제거, 구조 개선)
```

| 구성요소 | 주요 활동 | 목적 (왜 하는가?) |
|:---|:---|:---|
| Red 단계 | 아직 구현되지 않은 기능에 대한 실패하는 테스트 케이스 작성 | 기능의 스펙과 인터페이스(API)를 사용자 관점에서 먼저 설계 |
| Green 단계 | 죄악을 저질러서라도(하드코딩 등) 테스트를 가장 빠르게 통과 | 테스트의 정확성 확인 및 빠른 성취감(피드백) 획득 |
| Refactor 단계 | 기능 유지 상태에서 코드 스멜 제거 및 패턴 적용 | 시스템 품질 향상 및 유지보수성 확보 |

> 요약: TDD는 기능 명세(Red) -> 구현(Green) -> 설계 개선(Refactor)의 무한 반복 피드백 루프다.

---

## Ⅲ. 동작원리 및 흐름도

```text
기능 요구사항 도출 -> 단위 테스트(TC) 작성 -> 컴파일/실행 (Fail) -> 로직 구현 -> 실행 (Pass) -> 코드 리팩터링
```

- 1단계 [TC 작성 (Test-First)]: 요구사항을 충족하는 가장 작은 단위의 기능에 대해 `Assert` 문을 활용하여 테스트 코드 작성
- 2단계 [실패 확인 (Red)]: 코드를 실행하여 붉은색 막대(테스트 실패)를 확인 (테스트 코드가 정상 동작함을 입증)
- 3단계 [코드 작성 및 통과 (Green)]: 비즈니스 로직을 구현하여 녹색 막대(테스트 성공)를 만듦. 이때 불필요한 기능(오버엔지니어링)은 배제
- 4단계 [설계 개선 (Refactoring)]: 중복 코드 추출, 변수명 변경, 디자인 패턴 적용 등을 수행하고 다시 테스트를 돌려 기능 불변 확인

> 요약: 아주 작은 목표를 세우고(Red), 달성하고(Green), 정리하는(Refactor) 마이크로 스텝을 밟으며 소프트웨어를 성장시킨다.

---

## Ⅳ. 특징
- [설계 주도(Design-Driven)]: 테스트하기 쉬운 코드를 짜야 하므로, 자연스럽게 모듈 간 결합도가 낮고 응집도가 높은 객체지향적 설계가 강제됨
- [살아있는 문서(Living Document)]: 테스트 코드가 곧 그 기능이 어떻게 동작해야 하는지 보여주는 최신화된 명세서(API Docs) 역할을 함
- [디버깅 시간 단축]: 오류 발생 시 가장 최근에 추가한 테스트/코드(수 분 내 분량)만 확인하면 되므로 원인 파악이 즉각적임
- [안전망(Safety Net)]: 촘촘한 테스트 베드가 존재하여, 향후 과감한 리팩터링이나 레거시 개선 시 회귀(Regression) 오류의 두려움을 없앰

> 요약: 테스트 자체가 설계 피드백이자 안전망 역할을 하여 장기적인 소프트웨어 품질을 보장한다.

## Ⅴ. 심화 비교 및 적용 판단

| 비교 축 | 전통적 개발 (Test-Last) | 테스트 주도 개발 (Test-First) | 선택 기준 |
|:---|:---|:---|:---|
| 코드 설계 | 코딩 후 구조 확정 (강한 결합 우려) | 테스트 작성 중 인터페이스 도출 (느슨한 결합) | 객체지향 설계 중요도 |
| 테스트 커버리지 | 일정 압박 시 생략됨 (낮은 커버리지) | 코드 작성 전 필수 수행 (높은 커버리지) | 도메인 핵심 비즈니스 로직 여부 |
| 비용 구조 | 초기 비용 낮음, 유지보수 비용 기하급수 증가 | 초기 개발 시간 증가(테스트 작성), 유지보수 비용 고정 | 프로젝트 수명 (단기 SI vs 장기 프로덕트) |

> 요약: 단기 프로토타이핑에는 전통적 개발이 빠르지만, 수년간 유지보수할 핵심 프로덕트에는 초기 비용을 감수하더라도 TDD가 압도적으로 유리하다.

**리스크·대응:**
- [데이터베이스/외부 API 의존성]: 외부 상태에 따라 테스트가 실패하거나 느려짐 → Mock 객체 및 Stub 패턴을 활용하여 의존성을 격리 (지표: 단위 테스트 소요 시간 10초 이내)
- [레거시 코드 적용 불가]: 기존의 강결합 코드에 TDD 적용 시 테스트 불가 → BDD(행위 주도 개발) 형태의 통합 테스트를 껍데기로 먼저 씌우고 내부를 분해 (지표: 레거시 코드 커버리지 점진적 향상)

**도입 후 점검 지표:**
- 코드 커버리지: 분기/구문 커버리지 자동 측정 (80% 이상 권장) — SonarQube 등 정적 분석
- 결함 밀도(Defect Density): 운영 배포 후 발생하는 버그 건수 — TDD 도입 전후 대비 감소율 측정

## Ⅵ. 실무 적용 및 결론

**적용 방안 3개:**
1. 핵심 도메인 우선 적용: 전체 시스템이 아닌 복잡도가 높고 결함 발생 시 타격이 큰 결제/정산 등의 코어 도메인 로직에만 TDD를 의무 적용
2. 테스트 대역(Test Double) 표준화: Mockito, JUnit 등의 프레임워크를 표준화하여 외부 의존성(DB, 파일 등)을 분리하는 가짜 객체(Mock/Stub) 작성 가이드라인 수립
3. CI 파이프라인 연동 게이트웨이: 커밋 시 단위 테스트가 1개라도 실패하면(Red) 빌드를 중단시키는 Quality Gate를 Jenkins/GitLab CI에 강제

**결론 (2줄):**
- 기술사 판단: TDD는 단위 테스트 작성이 목적이 아니라, "테스트 가능한 구조"를 강제하여 느슨한 결합의 아키텍처를 얻어내는 설계 기법으로 접근해야 한다.
- 향후 방향: 개발자와 기획자의 언어 장벽을 허물기 위해 TDD를 확장한 BDD(행위 주도 개발, Given/When/Then) 및 ATDD(인수 테스트 주도 개발)로 발전시켜야 한다.
