## 핵심 인사이트 (3줄 요약)
- 프로덕션 코드(기능)를 작성하기 전에, 그 기능을 검증하는 실패하는 테스트 코드(Test)를 먼저 작성하는 극단적인 개발 방법론(켄트 벡 제안).
- Red(실패) ➡️ Green(성공) ➡️ Refactor(코드 개선)의 짧은 사이클을 끊임없이 반복하여, 버그 없는 깔끔한 코드를 산출함.
- TDD는 단순한 '테스트 기법'이 아니라, 사용자의 입장에서 인터페이스를 먼저 고민하게 만드는 훌륭한 **'설계 기법(Design Method)'**임.
---
## Ⅰ. 개요 및 필요성
- **개요**: 익스트림 프로그래밍(XP)의 핵심 실천법으로, 테스트 코드가 설계서와 명세서의 역할을 동시에 수행하는 개발 철학.
- **필요성**: 기존에는 코드를 다 짠 후 테스트를 했기 때문에, 설계가 잘못된 것을 뒤늦게 깨닫거나 시간에 쫓겨 테스트를 생략하는 일이 빈번했음. 코드 수정 시 발생하는 회귀 버그(Regression Bug)의 공포를 없애고 과감한 리팩토링을 가능하게 할 안전망이 필요했음.
---
## Ⅱ. 아키텍처 및 핵심 원리
- **TDD 3단계 라이프사이클**:
  1. **RED (실패하는 테스트 작성)**: 아직 구현되지 않은 기능을 호출하는 테스트 코드를 짬 (당연히 에러/실패 발생).
  2. **GREEN (최단 시간 내 테스트 통과)**: 꼼수(하드코딩)를 써서라도 테스트를 통과하는 가장 무식하고 빠른 프로덕션 코드를 작성함.
  3. **REFACTOR (리팩토링)**: 테스트가 통과하는 상태(안전망)를 유지하면서, 중복 코드를 제거하고 디자인 패턴을 적용해 코드를 예쁘게 가다듬음.

```text
[ TDD의 짧은 호흡 (Micro-cycle) ]

     (시작) ➡️ 🔴 RED: Write a failing test
                     ⬇️
               🟢 GREEN: Make the test pass (최소한의 코드)
                     ⬇️
               🔵 REFACTOR: Clean up the code (설계 개선)
                     ⬇️ (반복)
```
---
## Ⅲ. 비교 및 연결
| 구분 | 전통적 개발 (Test-Last) | 테스트 주도 개발 (Test-First, TDD) |
|---|---|---|
| **개발 순서** | 설계 ➡️ 코드 구현 ➡️ 테스트 작성 | 테스트 작성 ➡️ 코드 구현 ➡️ 리팩토링 |
| **코드의 목적** | 기능이 돌아가게 만드는 것 | 테스트를 통과하게 만드는 것 |
| **테스트 커버리지**| 30~50% 수준 (귀찮아서 안 짬) | 90% 이상 (테스트 없이 코드가 존재할 수 없음) |
| **리팩토링 심리** | "건드리면 고장 날까 무서움" | "버튼 하나 누르면 1초 만에 검증되니 안심" |
---
## Ⅳ. 실무 적용 및 기술사 판단
- **TDD 도입의 가장 큰 장벽**: 개발 초기 속도가 20~30% 느려짐. 경영진은 "왜 코드 짤 시간에 테스트나 짜고 있냐"고 압박함. 하지만 프로젝트 후반부로 갈수록 디버깅과 통합 오류 픽스 시간이 0에 수렴하여, 전체 프로젝트 리드 타임(Lead Time)은 오히려 단축(J-Curve)된다는 것을 지표로 설득해야 함.
- **Mocking의 양면성**: 단위 테스트 시 외부 DB나 API를 가짜(Mock/Stub)로 대체하는데, 무분별한 Mocking은 테스트 코드를 실제 코드의 내부 로직에 지나치게 결합시킴(Fragile Test). 이를 막기 위해 상태 기반 검증(State Verification)을 우선시해야 함.
---
## Ⅴ. 기대효과 및 결론
- 100% 자동화된 회귀 테스트 스위트를 구축하게 되어, 낡고 거대한 레거시 시스템을 두려움 없이 리팩토링하고 클라우드로 마이그레이션할 수 있는 기술적 용기를 제공함.
- TDD는 코드를 얼마나 빨리 짜느냐가 아니라, 얼마나 확신을 가지고 '올바른' 코드를 짜느냐에 대한 대답이며, 장인정신(Software Craftsmanship)을 갖춘 개발 조직의 필수 DNA임.

### 👶 어린이를 위한 3줄 비유 설명
1. 수학 문제를 풀 때, 답안지부터 먼저 보고 "아, 정답이 5가 나와야 하는구나!"를 확인한 뒤에(RED),
2. 어떻게든 식을 세워서 5가 나오게 대충 맞추고(GREEN),
3. 나중에 식을 깔끔하게 다시 정리하는(REFACTOR) 방식이에요. 정답(테스트)을 미리 알고 시작하니까 절대 엉뚱한 길로 빠지지 않죠!
