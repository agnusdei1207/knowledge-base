## 미리 알고가기

- TDD는 실패하는 테스트를 먼저 작성한 뒤 최소 구현과 리팩터링을 반복하는 개발 방식임
- Red-Green-Refactor는 실패하는 테스트 작성, 최소 구현, 구조 정리의 짧은 반복 주기임
- 테스트를 많이 쓰는 것과 TDD를 실제로 수행하는 것은 같지 않음

## 작성 근거(검토용)

- TDD는 테스트 작성 시점, 요구·회귀 검증, 설계 영향, 적용 부담을 핵심 비교축으로 선정함
- 구성과 절차는 실패 테스트·최소 구현·리팩터링의 반복 상태를 중심으로 제시함
- 실무 판단은 테스트 실행시간, 회귀 결함률, 보호 테스트 통과율, 리팩터링 후 결함 수로 구체화함

## Ⅰ. 개요

- **정의/개념**: TDD는 요구를 실패하는 테스트로 먼저 표현하고 최소 구현과 리팩터링을 짧게 반복하는 개발 기법임
- **배경/필요성**: 요구 변경 후 회귀를 즉시 확인하고 동작을 유지하며 코드 구조를 개선할 개발 주기가 필요함

## Ⅱ. 특징

- 요구를 실행 가능한 테스트 형태로 구체화함
- 작은 요구 단위마다 동작과 코드 구조를 반복 검증함
- 테스트 품질이 낮으면 개발 속도만 늦추고 보호망 역할은 못할 수 있음
- 리팩터링과 CI 회귀 테스트가 없으면 테스트와 구현 구조가 함께 갱신되지 않음

## Ⅲ. 종류 및 비교

| 판단 기준 | 사후 테스트 | TDD |
|:---|:---|:---|
| 테스트 시점 | 구현 후에 테스트를 작성함 | 구현 전에 실패하는 테스트를 먼저 작성함 |
| 요구·회귀 검증 | 구현 후 선택한 기능을 테스트 | 실패 테스트로 수용 조건을 정하고 구현 후 회귀 테스트로 유지 |
| 구조상 한계 | 설계 피드백이 늦고 테스트가 빠지기 쉬움 | 학습 비용과 규율이 필요하고 느린 테스트에 취약함 |
| 설계 영향 | 구현을 검증하는 역할에 머무르기 쉬움 | 구현 과정 자체에 설계 피드백을 줌 |

> 요약: 구현 후 동작을 확인하면 사후 테스트, 실패 테스트부터 작성해 구현과 설계를 이끌면 TDD 방식임.

## Ⅳ. 구성요소 및 구조

| 구성요소 | 설명 |
|:---|:---|
| 실패 테스트 | 요구를 구체 행동으로 표현해 무엇을 만들어야 하는지 분명히 함 |
| 최소 구현 | 테스트를 통과할 최소 코드만 작성해 과잉 설계를 줄임 |
| 리팩터링 단계 | 동작을 유지한 채 중복과 결합이 누적되지 않도록 구조를 개선함 |
| 회귀 테스트 묶음 | 누적된 테스트가 이후 변경의 안전망이 됨 |

> 요약: 실패 테스트로 요구를 정하고 최소 구현으로 통과한 뒤 회귀 테스트를 유지하며 구조를 개선함.

## Ⅴ. 원리 및 절차 흐름도

```text
+-------------+     +-------------+     +-------------+     +-------------+
| 실패 테스트 작성 | --> | 최소 구현      | --> | 테스트 통과    | --> | 리팩터링      |
+-------------+     +-------------+     +-------------+     +-------------+
```

1. **실패 테스트 작성**: 새 요구를 테스트로 표현함
2. **최소 구현**: 테스트를 통과할 만큼만 코드를 작성함
3. **테스트 통과**: 회귀 여부와 요구 충족 여부를 확인함
4. **리팩터링**: 중복과 결합을 줄이도록 구조를 정리함

> 요약: 실패 테스트 작성, 최소 구현, 테스트 통과, 리팩터링을 반복해 동작과 구조를 함께 개선함.

## Ⅵ. 실무 사례

1. 핵심 업무 로직은 TDD로 변경을 구현하고 테스트 실행시간·회귀 결함률을 확인함
2. 레거시 모듈은 보호 테스트 후 리팩터링하고 보호 테스트 통과율·수정 후 결함 수를 확인함

## Ⅶ. 결론

TDD는 실패 테스트·최소 구현·리팩터링을 반복해 요구 구현과 코드 구조를 함께 개선하는 방식임
