# 📖 【암기용】 개념 완전 이해

> 목적: 이 개념을 처음 보는 사람도 완벽히 이해하게 만든다. 시험 답안 양식이 아니라, 이해를 위한 친절한 설명이다.

## 한눈에
- **개요**: **TDD(테스트 주도 개발)**는 코딩의 순서를 미친 듯이 뒤집어버린 철학이다. "본체 코드 100줄을 먼저 짜고 -> 잘 돌아가는지 테스트한다"라는 상식을 깨고, **"실패하는 테스트 코드를 먼저 짜고 -> 그 테스트를 통과할 만큼만 본체 코드를 짠다"**는 미친(하지만 위대한) 접근법이다.
- **왜 필요한가**: 일반적인 개발자는 코드를 다 짜놓고(수천 줄) 마지막에 테스트 코드를 짜려고 하면 너무 귀찮아서 대충 짜거나 아예 안 짠다(테스트 커버리지 0%). 결국 나중에 버그가 터져서 회사가 망한다. TDD는 "테스트를 안 짜면 아예 본체 코드를 단 1줄도 치지 마라"라고 멱살을 잡고 강제하여, 태어날 때부터 100% 방탄복을 입은 코드를 찍어내기 위함이다.
- **핵심 직관 (Red-Green-Refactor 3단계)**: 
  - **Red (빨강/실패)**: 컴파일도 안 되는 실패하는 테스트 코드를 무작정 먼저 짠다. "1+1을 넣으면 2가 나오겠지?"
  - **Green (초록/성공)**: 방금 만든 테스트를 어떻게든 통과시키기 위해 최소한의(때론 쓰레기 같은) 본체 코드를 짠다. `return 2;`
  - **Refactor (파랑/리팩터링)**: 테스트 통과(초록불)를 확인했으니, 이제 안심하고 쓰레기 같던 코드를 디자인 패턴을 써서 예쁘고 우아하게 다듬는다.

## 깊이 이해
- **배경·문제의식**: 개발자들은 항상 "시간이 없어서 테스트를 못 짰어요"라고 변명한다. 켄트 벡(Kent Beck)은 익스트림 프로그래밍(XP)을 주창하며 "테스트는 나중에 하는 검열이 아니라, 코드를 설계(Design)하는 나침반이다"라고 선언했다. 테스트를 먼저 짜면, 코드가 얼마나 우아하고 테스트하기 쉬운 모양(느슨한 결합)으로 나오는지 깨달았기 때문이다.
- **작동 원리 (YAGNI와 오버엔지니어링 차단)**:
  - 개발자 특: "나중에 할인 정책 복잡해질지 모르니까, 인터페이스 3개 파놓고 팩토리 패턴 떡칠해 놔야지!" (오버엔지니어링).
  - TDD 특: "테스트 코드가 '10% 할인해 줘'라고만 요구하잖아? 그럼 딱 10% 할인하는 단순 if문 하나만 짜!" (YAGNI: You Aren't Gonna Need It). **TDD는 미래의 쓸데없는 설계를 강제로 막아버린다.**
- **비유**: 
  - 일반 개발: 집을 일단 다 짓는다. 다 짓고 나서 흔들어(테스트) 본다. 무너지면 지붕부터 다시 뜯어야 한다.
  - TDD: "진도 7의 지진을 견뎌라(테스트 코드)"라는 철근 강도 기준을 먼저 세운다. 그리고 철근 한 가닥을 세울 때마다 진도 7로 흔들어본다. 안 무너지면 다음 철근을 올린다. 절대 안 무너진다.
- **흔한 오해·주의점**: "TDD 하면 개발 속도가 2배 느려지는 거 아닌가요?" 맞다. **처음 1달은 미치도록 느리다.** 1줄 짤 걸 2줄(본체+테스트) 짜야 하니까. 하지만 1년 뒤 유지보수(버그 수정)할 때, 남들이 에러 1개 잡느라 밤샐 때 TDD 코드는 10초 만에 에러 위치를 찾아낸다. 단기 속도를 희생해 장기 생존력(유지보수성)을 사는 보험이다.

## 연결 개념
- **CI/CD 파이프라인**: TDD로 만들어진 100%짜리 테스트 코드는 CI(지속적 통합) 서버 젠킨스의 완벽한 먹잇감이다. 젠킨스가 이 테스트들을 0.1초 만에 돌려보고 초록불이면 무인 배포해 버린다.
- **단위 테스트 (Unit Test) / Mock**: TDD의 99%는 단위 테스트로 굴러간다. DB에 접속하는 통합 테스트를 먼저 짜면 느려서 Red-Green 루프가 멈춰버리기 때문이다.

# 📝 【답안용】 시험 답안 템플릿

> 목적: 시험장에서 25분에 그대로 쓰는 답안 양식. 작성방식(추상표현 금지·수치·도식·문제유형 전환)을 엄격히 지킨다.
> 핵심: 이 시험은 정보를 많이 나열하는 시험이 아니라, 문제 신호어에서 출제자 의도를 읽고 핵심 논점을 선별해 쓰는 시험이다.

## 핵심 인사이트 (3줄 요약)

> 1. **본질**: 프로덕션(본체) 코드를 작성하기 전에, 실패하는(Red) 자동화된 단위 테스트 코드를 먼저 작성하고, 이를 통과(Green)하기 위한 최소한의 코드만 구현한 뒤 구조를 개선(Refactoring)하는 역방향 설계(Design) 프랙티스다.
> 2. **가치**: 오버엔지니어링(YAGNI)을 원천 차단하여 코드를 극도로 가볍게 유지하며, 탄생부터 100%의 테스트 커버리지를 가진 모듈을 양산함으로써 리팩터링 시의 회귀 버그(Regression Bug) 공포를 100% 소거한다.
> 3. **판단 포인트**: 'Red -> Green -> Refactor'라는 3단계 짧은 피드백 루프(Micro-cycle) 도식을 반드시 그리고, TDD가 단순한 QA(검증) 기법이 아니라 객체 간 결합도를 낮추는 '설계(Architecture) 기법'임을 강하게 어필해야 한다.

## 출제 의도 및 답안 포인트

| 출제 의도 | 반드시 짚을 핵심 | 감점 회피 포인트 |
|:---|:---|:---|
| 기존 사후 테스트(Test-Last) 관행의 한계 극복 기전 | Test-First (사전 테스트 작성)를 통한 테스트 커버리지 강제 | TDD를 단순한 "단위 테스트 도구 모음" 정도로 얕게 묘사하는 맹점 |
| TDD를 관통하는 마이크로 피드백 루프 물리적 도식화 | **Red(실패) -> Green(통과) -> Refactor(리팩터링)** 3단계 | 가장 중요한 3번째 '리팩터링(구조 개선)' 단계를 누락하여 스파게티 양산 인정 |
| TDD가 소프트웨어 아키텍처(설계)에 미치는 엔지니어링적 영향 | **테스트 용이성(Testability)** 확보를 위한 인터페이스 의존성 주입(DI) 결합도 저하 유도 | 기능이 정상 작동하는지만 확인하는 QA 목적으로만 국한하여 서술 |

> 요약: TDD는 테스트 방법론이 아니다. "테스트하기 쉬운 코드 = 결합도(Coupling)가 낮고 좋은 코드"라는 절대 진리를 이용해, 개발자의 멱살을 잡고 '테스트하기 쉬운 좋은 구조'를 억지로 짜게 만드는 아키텍처 강제화(Design) 도구다.

## Ⅰ. 개요 및 필요성

- 정의: 켄트 벡(Kent Beck)이 창시한 익스트림 프로그래밍(XP)의 핵심 실천법으로, 실패하는 테스트 코드를 먼저 작성(Test-First)하여 코드의 명세(Specification)를 확립한 후 구현을 진행하는 주도적(Driven) 개발 방법론
- 배경: 코드를 모두 작성한 후(Test-Last) 테스트를 수행하려 하면, 모듈 간 강결합(Tightly Coupled)으로 인해 Mocking(가짜 객체 삽입)이 불가능하여 테스트 자체를 포기(Coverage 0%)하는 기술 부채 붕괴 도달
- 필요성: 테스트 커버리지를 100%에 가깝게 강제하여 언제든 코드를 뜯어고칠 수 있는 심리적 안정감(Safety Net)을 제공하고, 무분별한 오버엔지니어링(YAGNI)을 방지하여 애자일(Agile) 속도를 장기 사수하기 위함

## Ⅱ. TDD 마이크로 피드백 루프 (Red-Green-Refactor) 도식

이 사이클은 하루에 1번 도는 게 아니다. 개발자는 이 3단계 사이클을 하루에 수백 번 미친 듯이 빙글빙글 돈다(수 분 단위).

```text
[ TDD (Test-Driven Development) 생명주기 3단계 무한 루프 도식 ]

(1. 실패하는 테스트 작성)            (2. 최소 코드 구현)              (3. 중복 제거 및 구조 튜닝)
 🚨 [ 1. RED (실패) ]  --------->  ✅ [ 2. GREEN (통과) ]  --------->  ♻️ [ 3. REFACTOR (리팩터링) ]
(기능 명세의 인터페이스화)            (하드코딩을 해서라도 일단 통과)           (디자인 패턴 적용, 결합도 저하)
          ^                                                                        |
          | (새로운 기능 요구사항이 추가되면 다시 실패하는 테스트 추가 🚀)                      |
          +------------------------------------------------------------------------+
```

| TDD 사이클 | 아키텍처적(엔지니어링) 통제 메커니즘 | 실무 방어 효과 (Shift-Left) |
|:---|:---|:---|
| **1. RED** <br> (실패) | 구현부 로직은 비워둔 채, 호출할 함수명(`calculateDiscount`)과 반환값(`100`)만 기대하는 테스트 껍데기(Stub) 작성 (컴파일 에러 유발) | **YAGNI(오버엔지니어링) 방어**: 테스트 코드가 요구하는 인터페이스(명세) 외에는 절대 단 1줄의 잡다한 선제적 방어 코드(스파게티) 작성 금지 |
| **2. GREEN** <br> (통과) | 무조건 빨리 빨간불을 끄는 것이 목표. `return 100;` 처럼 하드코딩(상수 반환)이라는 쓰레기 코드를 써서라도 1분 내에 무조건 초록불 통과 쟁취 | 복잡한 설계를 고민하느라 코딩이 멈추는(마비) 현상을 막고, 일단 돌아가는(Working) 작은 상태를 극단적으로 빠르게 획득 |
| **3. REFACTOR** <br> (리팩터링) | 초록불(방어막)이 켜진 든든한 상태에서, 하드코딩된 쓰레기 코드를 지우고 전략 패턴(Strategy) 등을 투입하여 결합도(Coupling)를 끊고 클린 코드로 조각 | 언제든 코드 구조를 다 뜯어고쳐도 0.1초 만에 테스트 봇(JUnit)이 에러 유무를 즉각 통보하므로, 회귀 버그(Regression)의 공포 100% 증발 |

> 요약: TDD의 핵심은 "테스트를 통과하기 전까지는 절대 코드를 예쁘게 짤 생각(디자인)을 하지 마라"는 것이다. 완벽주의에 빠진 개발자의 손목을 묶고, 일단 진흙(하드코딩)으로 뼈대를 세운 뒤 나중에 예쁘게 다듬으라는 린(Lean) 사상이다.

## Ⅲ. 극복해야 할 시스템적 리스크 (데이터베이스 종속성 붕괴)

TDD 초보자들이 실패하는 유일한 이유는, 테스트를 짤 때 자꾸 DB나 프레임워크(Spring)를 물고 늘어지기 때문이다.

| 리스크 요인 | 발생 시나리오 및 시스템 붕괴 원인 (안티패턴) | 아키텍처 대응 방안 (실무 튜닝) |
|:---|:---|:---|
| **느린 테스트로 인한 TDD 루프 셧다운** | 단위 테스트 함수 하나에 JPA DB 조회 쿼리가 들어감. DB 접속 지연으로 테스트 1개에 5초 소요. 테스트가 1,000개가 되자 한 번 돌리는 데 1시간 반이 걸려 Red-Green 루프 완전 마비 및 TDD 포기 | **DB 및 외부 인프라의 100% 고립 (Mocking)**: 테스트 코드 내부에는 실제 DB(Oracle)나 Redis 접근을 100% 금지. `Mockito`나 `Stub` 가짜 객체를 강제 주입하여, 메모리(RAM) 상에서 0.001초 만에 테스트가 끝나도록 극단적 고립화(Isolation) 튜닝 |
| **테스트 코드 유지보수 지옥 (강결합)** | 본체(Production) 코드의 프라이빗(Private) 내부 메서드나 변수명 하나하나까지 모두 테스트 코드와 1:1로 엮어 짬(White-box). 본체 변수명을 바꾸자 테스트 코드 수백 개가 빨간불을 뿜으며 동반 붕괴 | **퍼블릭(Public) 인터페이스 중심의 행위(Behavior) 테스트 강제**: 클래스 내부 구현(How)이 아니라, 외부에 노출된 퍼블릭 API가 기대한 결과(What)를 반환하는지만 검증하도록 블랙박스 관점 튜닝 (결합도 완화) |

> 요약: TDD 루프는 무조건 0.1초 만에 빙글빙글 돌아야 한다. 테스트 하나 돌리는데 10초가 넘게 걸리면, 개발자는 짜증 나서 딴짓을 하러 가고 몰입감(Flow)이 박살 난다. 느린 테스트는 안 짠 테스트보다 악질이다.

## Ⅳ. TDD가 강제하는 아키텍처 진화 (Testability == Loosely Coupled)

테스트하기 쉬운 코드(Testable Code)를 억지로 만들려다 보니, 소프트웨어 구조 자체가 위대한 객체 지향으로 진화한다.

| 강제되는 아키텍처 설계 | 물리적 구현 메커니즘 (리팩터링 후) | 해결되는 엔지니어링 한계 (스파게티 방어) |
|:---|:---|:---|
| **의존성 주입 강제화** <br> (Dependency Injection) | 함수 내부에서 `new Database()`로 객체를 직접 강결합(Tightly Coupled)하면 테스트 시 가짜(Mock) 객체를 갈아 끼울 수가 없음. 결국 외부 생성자에서 интерфей스 타입으로 객체를 주입받도록(DI) 강제로 코드를 뜯어고침 | 내가 원해서 설계한 게 아니라 "테스트를 통과시키려다 보니" 어쩔 수 없이 **SOLID 원칙의 끝판왕인 DIP(의존성 역전 원칙)를 100% 완벽하게 준수하는 플러그인 아키텍처 완성** |

> 요약: TDD는 셜록 홈스(QA)가 아니라 건축가(Architect)다. 범인(버그)을 잡기 위해 태어난 게 아니라, 처음부터 범인이 숨어들 수 없는 반듯하고 투명한 통유리(느슨한 결합) 건물을 짓게 강제하는 채찍질이다.

## Ⅴ. 실무 적용 방안 및 결론

**적용 방안 3개:**
1. [Mockito 기반 도메인 로직(Core) 100% 고립 테스트망 구축] 헥사고날(Hexagonal) 아키텍처의 중심부인 비즈니스 도메인(`OrderService`) TDD 수행 시, 바깥쪽 인프라인 JPA Repository나 외부 결제 API를 `Mock` 객체로 완벽히 덮어씌워, 외부 벤더 통신 장애 시에도 0.01초 단위의 내부 도메인 로직 CI 파이프라인 검증 무결성 지속
2. [BDD (Behavior-Driven Development) 융합 시나리오 기반 TDD 전개] 개발자들만의 외계어 단위 테스트(`testCalculate_Returns100`)를 지양하고, 기획자와 합의한 `Given(조건) - When(행위) - Then(결과)` 포맷의 영어/한글 문장을 껍데기(`@DisplayName`)로 먼저 박아둔 뒤, 그 내부 시나리오를 통과시키는 TDD를 수행하여 기획서와 소스코드의 100% 동기화 획득
3. [자바스크립트/프론트엔드 TDD 적용 (Jest + React Testing Library)] 백엔드에 국한되던 TDD를 프론트엔드로 확장. 버튼 클릭 이벤트 시 특정 DOM 엘리먼트가 렌더링되는가(Red)에 대한 UI 렌더링 테스트 코드를 먼저 짜고, 빈 React 컴포넌트에 로직을 주입(Green)하여 프론트 스파게티 렌더링 버그 조기 멸균

**결론:**
- 기술사 판단: 테스트 주도 개발(TDD)은 단순한 테스팅 테크닉을 넘어, 소프트웨어의 설계(Design) 권한을 개발자의 모호한 뇌피셜(YAGNI)에서 명확한 사용자의 요구 명세(Test Spec)로 이관하는 엔지니어링 패러다임의 혁명이다. 도입 초기 단기적 생산성 저하(2배 소요)라는 매몰 비용이 발생하지만, 장기 유지보수 및 리팩터링 단계에서 회귀 버그(Regression)의 공포를 100% 소거하는 압도적인 투자 자본 수익률(ROI)을 반환한다.
- 향후 방향: 최근 대규모 엔터프라이즈 환경에서는 개발자에게 100% TDD를 강요하는 피로도(Boilerplate)를 낮추기 위해, AI(GitHub Copilot)에게 인터페이스(Red)를 주면 구현체(Green)를 즉각 생성하거나, 반대로 기존 코드를 분석하여 테스트 엣지 케이스를 자동 생성해 내는 'AI-Assisted TDD' 하이브리드 체제로 쾌속 진화하고 있다.
