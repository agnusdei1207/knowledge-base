# 📖 【암기용】 개념 완전 이해

> 목적: TDD를 테스트 작성 순서와 설계 피드백 관점에서 이해하게 만든다. 시험 답안 양식이 아니라, 이해를 위한 설명이다.

## 한눈에
- **개요**: 실패 테스트를 먼저 쓰고 최소 코드로 통과시킨 뒤 구조를 개선하는 개발 방식
- **왜 필요한가**: 코드를 먼저 작성하면 요구사항 해석, 경계값, 회귀 검증이 뒤로 밀림. TDD는 작은 실패 테스트를 통해 요구사항을 실행 가능한 형태로 고정함.
- **핵심 직관**: 목적지를 먼저 테스트로 찍어 놓고, 그 지점에 도달하는 가장 작은 코드를 만든 뒤 길을 정리함.

## 깊이 이해
- **배경·문제의식**: 요구사항이 불명확하거나 변경이 잦은 경우 구현 후 테스트는 누락과 재작업을 늘림. TDD는 테스트가 설계 기준이 되어 인터페이스, 책임 분리, 예외 처리를 조기에 드러냄.
- **작동 원리**: Red 단계에서 실패하는 테스트를 작성하고, Green 단계에서 통과를 위한 최소 코드를 구현하며, Refactor 단계에서 중복과 복잡도를 줄임. 이 순환이 회귀 테스트 묶음을 누적함.
- **비유**: 시험 문제의 채점 기준을 먼저 만들고 답안을 작성한 뒤 문장을 다듬는 방식임.
- **구체 예시**: 할인 계산 함수에서 10만원 이상 5% 할인 테스트를 먼저 실패시키고, 최소 조건문으로 통과시킨 뒤 정책 객체로 분리함.
- **흔한 오해·주의점**: TDD는 모든 결함을 제거하지 않음. UI, 성능, 외부 시스템 장애는 별도 통합 테스트와 탐색 테스트가 필요함.

## 연결 개념
- Unit Test: TDD 순환의 기본 검증 단위
- Refactoring: Green 이후 설계를 개선하는 단계
- Regression Suite: 누적 테스트가 변경 영향 검증 자산이 됨

# 📝 【답안용】 시험 답안 템플릿

> 목적: 시험장에서 25분에 그대로 쓰는 답안 양식. 작성방식(추상표현 금지·수치·도식·문제유형 전환)을 엄격히 지킨다.
> 핵심: TDD는 테스트를 먼저 작성하는 행위가 아니라 red-green-refactor 순환을 통해 요구사항과 설계를 검증하는 기법임.

## 핵심 인사이트 (3줄 요약)

> 1. **본질**: TDD는 실패 테스트 작성, 최소 구현, 리팩터링을 반복해 요구사항을 실행 가능한 검증 기준으로 바꾸는 개발 방식임.
> 2. **가치**: 회귀 테스트 묶음을 누적해 변경 영향 확인 시간을 줄이고 설계 결합도를 조기에 드러냄.
> 3. **판단 포인트**: 단위 테스트 적합 영역, mocking 범위, 외부 연동 테스트 한계를 함께 제시해야 함.

## 출제 의도 및 답안 포인트

| 출제 의도 | 반드시 짚을 핵심 | 감점 회피 포인트 |
|:---|:---|:---|
| TDD 순환 이해 확인 | red, green, refactor 단계 | 테스트 자동화와 TDD를 동일시 |
| 설계 피드백 판단 확인 | test first, 작은 단위, 낮은 결합도 | 테스트 후행 작성으로 설명 |
| 적용 한계 인식 확인 | 외부 의존성, UI, 성능 검증 보완 | 모든 테스트를 TDD로 처리한다고 단정 |

> 요약: TDD 문제는 순서, 설계 피드백, 적용 한계를 함께 써야 채점 포인트를 충족한다.

---

## Ⅰ. 개요 및 필요성

TDD는 테스트를 먼저 작성하고 이를 통과하는 코드를 구현한 뒤 구조를 개선하는 개발 방식이다. 요구사항이 변경될 때마다 회귀 확인이 필요하며, 테스트 후행 방식은 경계값 누락과 결합도 증가를 늦게 발견한다. TDD는 실행 가능한 테스트로 요구사항을 고정하고 작은 설계 결정을 반복 검증한다.

---

## Ⅱ. 구조 및 구성요소

```text
Requirement -> Failing Test(Red) -> Minimal Code(Green)
Minimal Code -> Refactor -> Regression Suite
Regression Suite -> Design Feedback -> Next Requirement
```

| 구성요소 | 역할 | 특이사항 |
|:---|:---|:---|
| Test Case | 요구사항을 실행 가능한 기대값으로 표현 | Arrange, Act, Assert |
| Production Code | 테스트 통과를 위한 최소 구현 | 과잉 설계 방지 |
| Refactoring | 중복 제거와 책임 분리 | 테스트 통과 상태 유지 |
| Test Double | 외부 의존성 대체 | mock, stub, fake 구분 |

> 요약: TDD 구조는 테스트, 최소 구현, 리팩터링, 회귀 테스트 묶음이 반복되며 설계 피드백을 제공한다.

---

## Ⅲ. 동작원리 및 흐름도

```text
요구사항 선택 -> 실패 테스트 작성(Red)
-> 최소 코드 구현(Green) -> 테스트 통과 확인
-> 리팩터링 -> 전체 회귀 테스트 -> 다음 요구사항
```

| 단계 | 처리 내용 | 검증 기준 |
|:---:|:---|:---|
| 1 | 작은 요구사항 하나를 테스트로 표현 | 실패 원인 1개 |
| 2 | 테스트 실패를 확인 | red 상태 재현 |
| 3 | 통과를 위한 최소 코드 작성 | green 상태 100% |
| 4 | 중복 제거, 책임 분리, naming 개선 | 모든 테스트 통과 |
| 5 | 회귀 테스트 묶음 누적 | CI pass rate 100% |

> 요약: TDD는 실패를 먼저 확인하고 최소 구현 후 리팩터링을 수행하며, 전체 테스트 통과를 다음 순환의 출발점으로 삼는다.

---

## Ⅳ. 특징

| 구분 | 테스트 후행 개발 | TDD | 수치·판단 포인트 |
|:---|:---|:---|:---|
| 작성 순서 | 구현 후 테스트 | 테스트 후 구현 | red-green-refactor 순서 |
| 설계 피드백 | 후반 발견 | 인터페이스 단위 조기 발견 | cyclomatic complexity 10 이하 |
| 회귀 검증 | 수동 또는 부분 자동 | 테스트 묶음 누적 | unit coverage 80% 목표 |
| 적용 한계 | 문서와 코드 괴리 | 외부 연동은 mock 한계 | contract/integration test 보완 |

> 요약: TDD는 요구사항을 테스트로 먼저 표현해 설계 피드백과 회귀 검증을 앞당기지만 외부 연동 검증은 보완이 필요하다.

---

## Ⅴ. 심화 비교 및 적용 판단

| 비교 축 | 기존/대안 | 본 키워드 | 선택 기준 |
|:---|:---|:---|:---|
| 구조 | 구현 후 테스트 | test first 순환 | 복잡한 도메인 규칙, 변경 잦은 모듈 |
| 비용/성능 | 초기 개발 시간 짧음 | 테스트 작성 시간 선투자 | 유지보수 기간 6개월 이상이면 적용 |
| 운영/위험 | 회귀 결함 후행 발견 | CI 회귀 묶음 자동 실행 | 배포 전 unit pass 100% |
| 설계 | 구현 중심 인터페이스 | 테스트 가능한 작은 책임 | mock 3개 초과 시 설계 점검 |

> 요약: TDD는 단기 구현보다 장기 변경 비용이 큰 도메인 로직과 라이브러리 코드에 우선 적용한다.

| 리스크 | 원인 | 대응 방안 | 확인 지표 |
|:---|:---|:---|:---|
| 과도한 mock | 의존성 분리 과잉 | contract test, fake 사용 | mock count per test 3개 이하 |
| 취약한 테스트 | 내부 구현 세부 검증 | public behavior 중심 assertion | refactor 후 실패율 5% 이하 |
| 낮은 가치 테스트 | getter/setter 위주 | risk-based test 선정 | mutation score 70% 이상 |
| 팀 적응 지연 | test first 경험 부족 | pair programming, kata 훈련 | red-green cycle 준수율 |

> 요약: TDD 리스크는 mock 과다, 구현 결합 테스트, 가치 낮은 케이스이며 행동 기반 assertion과 mutation score로 통제한다.

| 점검 항목 | 목표 기준 | 측정 방법 |
|:---|:---|:---|
| 회귀 품질 | unit pass rate 100% | CI report |
| 커버리지 | line 80%, branch 70% 이상 | coverage tool |
| 설계 복잡도 | cyclomatic complexity 10 이하 | static analysis |
| 결함 유출 | unit 관련 escaped defect 3% 이하 | defect RCA |

> 요약: TDD 적용 효과는 테스트 통과율, 커버리지, 복잡도, 결함 유출률로 판단한다.

## Ⅵ. 실무 적용 및 결론

**적용 방안 3개 (필수 — 단계별 또는 항목별):**
1. 도메인 서비스와 계산 로직부터 TDD를 적용하고 JUnit, pytest, Jest 중 언어별 표준 도구로 red-green-refactor 순환을 PR 기준에 포함함.
2. 외부 API, DB, 메시징은 mock 남용을 제한하고 Testcontainers 또는 contract test로 통합 검증을 별도 구성함.
3. CI에서 unit pass 100%, line coverage 80%, mutation score 70% 기준을 관찰하고 기준 미달 시 refactor backlog로 등록함.

**결론 (2줄):**
- 기술사 판단: 도메인 규칙이 복잡하고 장기 유지보수가 필요한 모듈은 TDD가 적합하며, 일회성 UI 조립 화면은 테스트 피라미드 기준으로 선별 적용함.
- 향후 방향: TDD는 AI 테스트 생성, property-based testing, contract testing과 결합해 회귀 검증 범위를 넓힘.
