## 미리 알고가기

- TDD는 실패하는 테스트를 먼저 작성한 뒤 최소 구현과 리팩터링을 반복하는 개발 방식임
- Red-Green-Refactor는 실패하는 테스트 작성, 최소 구현, 구조 정리의 짧은 반복 주기임
- 테스트를 많이 쓰는 것과 TDD를 실제로 수행하는 것은 같지 않음

## Ⅰ. 개요

- **정의/개념**: TDD는 요구를 먼저 실패하는 테스트로 표현하고 그 테스트를 통과시키는 최소 코드 구현과 구조 개선 리팩터링을 짧은 주기로 반복하는 개발 기법임.
- **배경/필요성**: 요구가 자주 바뀌는 환경에서는 변경이 두려우면 개발 속도가 떨어지므로, 회귀를 바로 확인하면서 설계를 조금씩 다듬는 안전한 개발 사이클이 필요함.

## Ⅱ. 특징

- 요구를 실행 가능한 테스트 형태로 구체화함
- 작은 주기를 반복해 과잉 설계를 줄이고 피드백 속도를 높임
- 테스트 품질이 낮으면 개발 속도만 늦추고 보호망 역할은 못할 수 있음
- 리팩터링 문화와 CI가 함께 있어야 장기 효과가 커짐

## Ⅲ. 종류 및 비교

| 구분 | 사후 테스트 | TDD |
|:---|:---|:---|
| 테스트 시점 | 구현 후에 테스트를 작성함 | 구현 전에 실패하는 테스트를 먼저 작성함 |
| 구조상 장점 | 초기 진입이 쉽고 빠르게 코드를 만들 수 있음 | 요구를 분명히 하고 회귀 보호망을 함께 쌓을 수 있음 |
| 구조상 한계 | 설계 피드백이 늦고 테스트가 빠지기 쉬움 | 학습 비용과 규율이 필요하고 느린 테스트에 취약함 |
| 설계 영향 | 구현을 검증하는 역할에 머무르기 쉬움 | 구현 과정 자체에 설계 피드백을 줌 |

> 요약: TDD의 핵심은 테스트를 먼저 쓴다는 형식보다 요구를 작고 검증 가능한 단위로 잘게 나누는 데 있음.

## Ⅳ. 구성요소 및 구조

| 구성요소 | 설명 |
|:---|:---|
| 실패 테스트 | 요구를 구체 행동으로 표현해 무엇을 만들어야 하는지 분명히 함 |
| 최소 구현 | 테스트를 통과할 최소 코드만 작성해 과잉 설계를 줄임 |
| 리팩터링 단계 | 동작을 유지한 채 구조를 개선해 코드 부패를 늦춤 |
| 회귀 테스트 묶음 | 누적된 테스트가 이후 변경의 안전망이 됨 |

## Ⅴ. 원리 및 절차 흐름도

```text
+-------------+     +-------------+     +-------------+     +-------------+
| 실패 테스트 작성 | --> | 최소 구현      | --> | 테스트 통과    | --> | 리팩터링      |
+-------------+     +-------------+     +-------------+     +-------------+
```

1. **실패 테스트 작성**: 새 요구를 테스트로 표현함
2. **최소 구현**: 테스트를 통과할 만큼만 코드를 작성함
3. **테스트 통과**: 회귀 여부와 요구 충족 여부를 확인함
4. **리팩터링**: 중복과 결합을 줄이도록 구조를 정리함

## Ⅵ. 실무 적용 및 유의점

1. 핵심 도메인 로직처럼 변경이 잦고 회귀 비용이 큰 영역에서는 TDD가 효과적이지만 테스트가 느리면 주기가 깨지므로 빠른 단위 테스트 중심으로 설계하고 테스트 피드백 시간과 회귀 결함 비율로 확인함
2. 레거시 개선 구간에서는 곧바로 이상적인 TDD를 적용하기보다 보호 테스트를 먼저 두고 행위 중심 테스트로 전환하며 테스트 깨짐 비율과 리팩터링 후 결함 건수로 확인함

## Ⅶ. 결론

TDD는 테스트를 많이 만드는 방법이 아니라 요구를 작은 검증 단위로 쪼개며 설계와 품질을 함께 다듬는 개발 방식임.
