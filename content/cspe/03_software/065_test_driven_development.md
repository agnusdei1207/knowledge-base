## 미리 알고가기

- TDD(Test-Driven Development): 실제 기능 코드를 작성하기 전에, 그 기능이 만족해야 할 실패하는 테스트 케이스를 먼저 작성하고 이를 통과시키며 개발하는 기법임
- Red-Green-Refactor: 실패하는 테스트 작성(Red), 테스트 통과를 위한 최소한의 구현(Green), 가독성 향상 및 중복 제거를 위한 코드 구조 개선(Refactor)의 TDD 3단계 주기임
- 리팩터링(Refactoring): 소프트웨어의 외부 동작 시나리오는 그대로 둔 채, 내부 구조를 개선하여 가독성을 높이고 유지보수 비용을 낮추는 리디자인 기법임
- 회귀 테스트(Regression Test): 기능 수정이나 리팩터링 후에도 기존 시스템에 부작용(Side Effect)이 발생하지 않았음을 확인하기 위해 이전에 작성된 테스트 묶음을 재가동하는 행위임
- 테스트 커버리지(Test Coverage): 작성된 테스트 세트가 소스 코드의 제어 흐름(구문, 분기, 조건 등)을 어느 수준까지 실제로 실행하여 검증했는지 나타내는 비율임

## 작성 근거(검토용)

- 핵심 키워드 선정 이유: TDD의 핵심 주기인 Red-Green-Refactor와 사후 테스트 기법의 차이를 비교해 단순 검증 수단에서 설계 유도 도구로서의 변화를 규명하고자 함.
- 절 구성·배치·전개 흐름 이유: Ⅰ절에서 TDD의 정의와 필요성을 밝히고, Ⅱ절에서 동작 및 구조 개선 등 특징을 설명함. Ⅲ절에서 일반적인 개발 방식(사후 테스트 작성)과 TDD를 테스트 시점, 설계 피드백, 유지보수 안전망 3가지 축으로 대비함. Ⅳ절과 Ⅴ절에서 테스트 케이스 중심의 정적 구조와 동적 리사이클 흐름을 도식화하고 상세 단계를 정렬함. Ⅵ절과 Ⅶ절에서 리팩터링 안전망으로서의 실무 적용과 공학적 활용 인사이트를 결론으로 도출함.
- 문장별 5회 전수 검수 근거: 제목, frontmatter, 미리 알고가기, 작성 근거, 본문, 표 헤더·셀, 요약, 결론을 한 줄도 빠뜨리지 않고 확인했으며 어색한 단어·조사·동사 결합·장황한 명사구를 교정했음을 병기함.

## Ⅰ. 개요

- **정의/개념**: TDD는 요구사항을 만족하는 실패 테스트를 먼저 정의하고, 이를 통과시키는 최소 구현과 리팩터링을 짧은 주기로 반복하여 동작하는 깔끔한 코드를 얻는 소프트웨어 개발 기법임
- **배경/필요성**: 개발 후반부의 복잡도 증가와 테스트 누락으로 인한 리팩터링 기피를 해결하고, 상시 가동되는 안전망을 확보해 변경에 유연한 아키텍처를 수립할 필요가 있음

### 쉽게 이해하기 (학습용)
- 과녁을 먼저 그려두고(테스트), 그 과녁에 화살이 꽂히도록 활을 쏜 뒤(구현), 자세를 교정해 더 부드럽게 쏠 수 있도록 자세를 다듬는(리팩터링) 개발 방식입니다.

## Ⅱ. 특징

- 요구사항을 구체적으로 동작 가능한 테스트 명세(Executable Specification) 형태로 변경함
- 테스트를 먼저 작성함으로써 구현할 객체 간의 인터페이스 및 협력 관계를 미리 고민하게 유도함
- 비즈니스 코드보다 테스트 코드의 양이 늘어남에 따라 테스트 자체의 유지보수 비용이 증가함
- 리팩터링 단계를 통해 기능을 깨뜨리지 않고 코드 중복 제거와 응집도(Cohesion) 향상을 연속 달성함

### 쉽게 이해하기 (학습용)
- 먼저 조립식 가구의 조립 설명서를 꼼꼼히 확인하고 나사가 들어갈 구멍을 판 다음, 조립해 보고 튼튼한지 흔든 뒤 마무리를 깔끔하게 깎아내는 특징이 있습니다.

## Ⅲ. 종류 및 비교

| 판단 기준 | 사후 테스트 | TDD |
|:---|:---|:---|
| 테스트 작성 시점 | 소스 코드 구현 완료 후 검증 수단으로 작성 | 기능 구현 전에 요구사항을 바탕으로 실패 테스트 작성 |
| 소프트웨어 설계 영향 | 이미 완성된 소스 구조에 맞춰 작성되므로 구조 개선에 기여도 낮음 | 테스트하기 쉬운 결합도 낮은 아키텍처(클래스 분리 등) 설계 유도 |
| 결함 예방 및 복잡도 | 코드 비대화 후 테스트하므로 원인 추적이 어렵고 복사-붙여넣기 중복 발생 | 최소 단위 개발로 결함을 즉각 식별하고 상시 리팩터링으로 복잡도 억제 |

> 요약: 사후 테스트는 단순 사후 결함 발견에 그치지만, TDD는 구현 전 테스트로 느슨한 결합도의 깨끗한 코드 설계를 견인함.

### 쉽게 이해하기 (학습용)
- 사후 테스트는 요리를 다 한 뒤에 간을 보고 소금을 치는 것이고, TDD는 요리할 물의 염도를 미리 정해두고 재료를 넣을 때마다 수치를 맞추는 요리법입니다.

## Ⅳ. 설계 요소 및 구조

| 설계 요소 | 설명 |
|:---|:---|
| 레드(Red) 단계 | 구현체가 존재하지 않아 컴파일이 실패하거나 어설션(Assertion)이 통과하지 못하는 첫 테스트 작성 단계 |
| 그린(Green) 단계 | 작성된 실패 테스트를 가장 빠르고 간단하게(상수 반환 등) 만족시키는 실제 소스 코드 작성 단계 |
| 리팩터(Refactor) 단계 | 그린 단계의 성공 동작을 깨뜨리지 않고 소스 코드의 중복을 제거하며 결합도를 낮추는 아키텍처 정교화 단계 |
| 회귀 테스트 스위트 | 요구사항별 작성된 모든 테스트 케이스를 자동화 실행해 기존 코드 변경에 따른 부작용을 원천 방어하는 보안망 |

> 요약: 레드, 그린, 리팩터의 삼단계 단주기 순환과 회귀 테스트 스위트가 모여 지속적인 아키텍처 정밀화를 실현함.

### 쉽게 이해하기 (학습용)
- 빨간 경고등(레드)을 켜고, 파란 불(그린)로 바꾸고, 복잡한 전선 배선을 예쁘게 다시 묶는(리팩터) 일련의 조립 라인입니다.

## Ⅴ. 원리 및 절차 흐름도

```text
  ┌──────────────────────────────────────────────┐
  ▼                                              │
[실패 테스트(Red)] → [최소한의 구현(Green)] → [리팩터링(Refactor)]
                           │                     ▲
                           └───── (테스트 통과) ──┘
```

1. **실패하는 테스트 케이스 작성**: 기획 요구사항을 기준으로 동작 가능한 인터페이스 명세와 결과값 검증 코드를 작성함
2. **테스트 패스를 위한 최소 구현**: 빠른 테스트 통과를 위해 가장 간단한 논리나 임시값(Hardcoding)을 사용해 코드를 가동함
3. **리팩터링 수행**: 테스트 성공을 유지하며 클린 코드 원칙을 적용해 구조 개선을 하고, 이 과정에서 코드 커버리지를 최적 수준으로 유지함
4. **점진적 기능 확장**: 작성된 테스트 묶음을 안전망으로 활용하며 다음 세부 요구사항에 대해 $1\sim3$단계를 무한 반복함

> 요약: 실패하는 테스트를 만든 후 이를 통과하는 코드를 빠르게 추가하고, 부작용 검출 안전망 하에서 설계를 리팩터링함.

### 쉽게 이해하기 (학습용)
- 채점기를 먼저 작동시켜 0점을 맞고, 100점을 받도록 답을 써넣은 뒤, 다음 시험을 위해 오답 없이 풀이 과정을 가장 예쁘게 정리해두는 순환 루프입니다.

## Ⅵ. 실무 사례

1. 계정 및 빌링 시스템 구축 시 핵심 도메인 로직에 JUnit을 이용한 TDD를 전면 적용해 신규 할인 정책 배포 시의 회귀 결함률을 $1\%$ 미만으로 방어함.
2. 장기 운영된 레거시 시스템 리팩터링에 앞서 중요 시나리오에 대해 보호 테스트(Characterization Test)를 구축하여 소스 내부 재구조화 시의 기능 마비를 예방함.

### 쉽게 이해하기 (학습용)
- 쇼핑몰 결제 시스템을 고칠 때 신용카드 할인 규칙을 먼저 시험지로 작성한 다음 코드를 고치고, 오래된 서버를 새것으로 교체하기 전 기존 동작을 백 장의 시험지로 묶어 감시하는 조치입니다.

## Ⅶ. 결론

- TDD는 레드-그린-리팩터의 짧은 피드백 루프를 반복함으로써 코드의 품질 보증과 아키텍처 유연성을 동시에 획득하는 진화적 설계 기법임.
- 복잡한 프레임워크나 외부 API 연동이 과도한 환경에서는 작성 비용이 구현 비용을 역전할 수 있으므로 핵심 비즈니스 영역 위주로 선택 적용해야 함.

### 쉽게 이해하기 (학습용)
- TDD는 지속적으로 품질과 설계를 끌어올려 주지만, 가짜 데이터를 많이 만들어야 하는 화면(UI) 개발 등에서는 실용성을 따져 선별해서 써야 한다는 인사이트입니다.
