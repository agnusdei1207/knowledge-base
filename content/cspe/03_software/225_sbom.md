## Ⅰ. 개요
- **정의**: SW를 구성하는 모든 컴포넌트·라이브러리·버전 정보를 기계 판독 가능 형식으로 기록한 목록임
- **배경/필요성**: SW 공급망 공격이 증가하면서 구성요소 투명성 확보가 취약점 대응의 전제 조건이 됨
- **비유**: 가공식품의 성분표처럼, SW에 포함된 모든 재료(컴포넌트)와 원산지(출처)를 명시하는 것과 유사함

| 출제 의도 | 반드시 짚을 핵심 | 감점 회피 포인트 |
|:---|:---|:---|
| SBOM 표준·생성·활용 이해 | SPDX, CycloneDX 표준 구분 | 단순 목록이 아닌 공급망 전체 투명성 도구로 설명 |

> 요약: SW 구성요소의 완전한 명세를 제공하여 공급망 투명성과 보안을 확보하는 장치임

## Ⅱ. 구성요소
```text
+------------------+
|      SBOM        |
+--------+---------+
         |
  +------+------+------+
  |      |      |      |
 패키지  관계   라이선스 취약점
 정보    정보   정보    참조
```

| 구성요소 | 설명 | 비유 |
|:---|:---|:---|
| 패키지 정보 | 컴포넌트명, 버전, 공급자, 해시값을 기록함 | 성분표 항목 |
| 관계 정보 | 컴포넌트 간 의존·포함 관계를 명시함 | 부품 조립도 |
| 라이선스 정보 | 각 컴포넌트에 적용된 라이선스를 식별함 | 원산지 표시 |
| 취약점 참조 | CVE 등 알려진 취약점과의 매핑 정보를 포함함 | 리콜 대상 목록 |

> 요약: 패키지·관계·라이선스·취약점 4개 정보 블록으로 구성됨

## Ⅲ. 절차
```text
생성 --> 저장 --> 공유 --> 소비
```
- 1단계: 생성 — 빌드 시점에 SCA 도구 또는 빌드 플러그인으로 SBOM 자동 생성
- 2단계: 저장 — SPDX 또는 CycloneDX 표준 형식으로 저장소에 보관
- 3단계: 공유 — 고객·규제기관·파트너에게 SBOM을 전달하여 투명성 제공
- 4단계: 소비 — 수신측이 SBOM을 분석하여 취약점 조회·라이선스 검증 수행

> 요약: 생성-저장-공유-소비 4단계로 공급망 전체에 투명성을 전파함

## Ⅳ. 문제점
- 생성 정확도: 빌드 도구별 메타데이터 품질이 상이 — 누락·오류 발생 가능
- 표준 파편화: SPDX와 CycloneDX 간 필드 매핑 불일치 — 상호운용성 저하
- 갱신 지연: 릴리스 후 의존성 변경 시 SBOM이 실시간 반영되지 않음 — 정보 정합성 저하

> 요약: 정확도, 표준 파편화, 갱신 지연이 SBOM 활용의 3대 과제임

## Ⅴ. 개선방안
1. 단기: 빌드 파이프라인 내 SBOM 생성을 필수 스텝으로 강제하여 정확도 확보
2. 중기: SPDX-CycloneDX 변환 도구를 도입하여 표준 간 상호운용성 확보
3. 장기: SBOM을 VEX(226 참조)·SLSA(227 참조)와 연계해 실시간 공급망 가시성 확보

> 요약: 빌드 내재화 → 표준 변환 → VEX/SLSA 연계 순으로 SBOM 성숙도 향상

## Ⅵ. 전망
- 발전 방향: 미국 EO 14028, EU CRA 등 규제에 의해 SBOM 제출이 법적 의무로 확대됨
- 기술사적 판단: SBOM은 SW 공급망 보안의 기초 데이터 레이어로 정착함
- 기술사 제언: SBOM 생성 자동화를 CI/CD에 내재화하고, 표준 선정 기준을 사전 확립할 것을 권고함
