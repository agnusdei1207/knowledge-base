# 📖 【암기용】 개념 완전 이해

> 목적: SBOM을 처음 봐도 완벽히 이해하게 만든다. 시험 답안 양식이 아니라, 이해를 위한 친절한 설명이다.

## 한눈에
- **개요**: SBOM(Software Bill of Materials, 소프트웨어 자재명세서)은 제품에 포함된 **구성요소**(라이브러리·패키지·컨테이너)의 이름·버전·라이선스·공급자·의존 관계를 기계가 읽을 수 있는 형식으로 적은 목록이다.
- **왜 필요한가**: 2021년 12월 Log4Shell(CVE-2021-44228, CVSS 10.0) 사태 때 기업들은 "우리 제품 중 어떤 것이 log4j-core 2.0~2.14.1을 포함하는가"에 몇 시간 안에 답해야 했다. SBOM이 없으면 이 질문에 답하는 데 수일~수주가 걸리고, 있으면 저장소 검색으로 수 분 안에 끝난다.
- **핵심 직관**: 제조업의 BOM(부품 명세서)이 자동차의 부품 목록이라면, SBOM은 소프트웨어 안에 어떤 '부품'(오픈소스·상용 라이브러리)이 들어있는지 적은 목록이다.

## 핵심 용어 정리 (내부에 등장하는 것들)

| 용어 | 의미 | 비유 |
|:---|:---|:---|
| SBOM | 제품의 소프트웨어 구성요소 전체 목록 | 자동차의 부품 명세서 |
| Component (구성요소) | 목록의 개별 항목 — 이름/버전/공급자/해시 | 부품 하나하나 |
| SPDX | Linux Foundation 주도, ISO/IEC 5962 국제표준 SBOM 형식 | 자재명세서 표준 양식 A |
| CycloneDX | OWASP 주도, 보안 중심으로 설계되고 VEX 확장을 지원하는 SBOM 형식 | 자재명세서 표준 양식 B(보안 특화) |
| package URL (purl) | `pkg:maven/...`처럼 패키지를 고유하게 가리키는 식별자 표기법 | 부품의 표준 일련번호 |
| CPE | NVD 등 취약점DB가 소프트웨어를 식별하는 규격 | 부품의 또 다른 방식 일련번호(구형 표준) |
| Direct/Transitive Dependency | 직접 설치한 의존성 / 그 의존성이 또 의존하는 간접 의존성 | 내가 산 물건 / 그 물건 안에 들어간 부품 |
| Attestation·서명(in-toto, cosign) | SBOM이 위변조되지 않았음을 암호학적으로 증명 | 명세서에 찍힌 봉인 인장 |
| CVE 매칭 | SBOM의 컴포넌트+버전을 취약점 DB와 대조하는 과정 | 리콜 부품 번호와 내 차 부품 대조 |

## 깊이 이해

### SBOM이 필요해진 계기 — Log4Shell 사례로 이해
- 숫자로 보면: log4j-core는 전 세계 수백만 개의 자바 애플리케이션이 로깅에 사용하는 라이브러리였다. 2.0-beta9부터 2.14.1까지 약 8년치 버전이 취약(JNDI Lookup을 통한 원격코드실행, CVSS 10.0/10.0)했다. SBOM이 갖춰진 조직은 `pkg:maven/org.apache.logging.log4j/log4j-core@2.14.1` 문자열로 저장소를 검색해 영향받는 제품을 30분~1시간 내에 특정했지만, SBOM이 없던 조직은 수백 개 제품의 빌드 설정을 하나씩 열어봐야 했다.

### SBOM은 언제, 어떻게 만들어지나
- 생성 시점은 셋 중 하나다 — 소스 코드 분석(package.json, pom.xml 등 매니페스트 파싱), 빌드 시점 분석(실제로 링크된 의존성 캡처), 컨테이너 이미지 분석(레이어별 설치된 패키지 스캔). 셋을 함께 써야 놓치는 컴포넌트가 줄어든다 — 예: Dockerfile에서 apt-get으로 설치한 OS 패키지는 소스 코드 분석만으로는 잡히지 않고 이미지 분석이 필요하다.
- 표준 형식(SPDX 또는 CycloneDX)으로 출력한 뒤 cosign·in-toto로 서명해, 이 SBOM이 실제로 해당 릴리스 빌드에서 나온 것이며 위변조되지 않았음을 증명한다.

### SBOM만으로는 부족한 이유 (VEX로 이어지는 한계)
- SBOM은 "무엇이 들어있는가"까지만 답한다. log4j-core가 포함되어 있어도 실행 코드 경로가 취약한 클래스(JndiLookup)를 호출하지 않으면 실제로는 안전할 수 있다. 이 "실제 영향 여부"는 SBOM만으로는 판단할 수 없고, VEX가 이 격차를 메운다.

### 비유와 흔한 오해
- **비유**: 식품 포장지의 원재료 표시가 "이 안에 밀가루·땅콩이 들어있다"고 알려주듯, SBOM은 "이 소프트웨어 안에 어떤 성분(라이브러리)이 들어있다"를 기계가 읽을 수 있게 적은 것이다.
- **오해 1**: SBOM 자체가 취약점 조치는 아니다 — 목록일 뿐이며, CVE 매칭·VEX·패치 SLA와 연결돼야 대응 체계가 완성된다.
- **오해 2**: 한 번 만들면 끝이 아니다 — 의존성은 릴리스마다 바뀌므로 SBOM도 릴리스마다 새로 생성해야 최신 상태를 유지한다.

## 연결 개념
- VEX — SBOM에 포함된 컴포넌트의 취약점이 실제로 악용 가능한지 답하는 문서
- 오픈소스 컴플라이언스 — SBOM을 입력으로 사용하는 상위 거버넌스 프로세스
- SLSA — SBOM이 위변조되지 않았음을 보증하는 빌드·서명 체계

# 📝 【답안용】 시험 답안 템플릿

> 목적: 시험장에서 25분에 그대로 쓰는 답안 양식. 작성방식(추상표현 금지·수치·도식·문제유형 전환)을 엄격히 지킨다.
> 핵심: SBOM은 파일 한 장이 아니라 생성, 저장, 서명, 배포, 취약점 매칭, 고객 제공까지 포함한 공급망 가시성 체계이다.

## 핵심 인사이트 (3줄 요약)

> 1. **본질**: SBOM은 소프트웨어 구성요소와 의존 관계를 SPDX, CycloneDX 등 표준 형식으로 표현한 명세서이다.
> 2. **가치**: CVE 영향 범위 분석, 라이선스 준수, 공급망 감사 대응 시간을 제품 단위에서 분 단위 검색으로 줄인다.
> 3. **판단 포인트**: 생성 시점, 표준 형식, 정확도, 서명, 저장소, VEX 연계, 고객 제공 정책을 함께 설계한다.

| 표준·도구 지식 확인 | SPDX, CycloneDX, package URL, SCA | 형식 표준과 생성 시점 누락 |
| 운영 적용 판단 확인 | 저장소, 서명, CVE 매칭, VEX 연계 | SBOM 생성 후 갱신·배포 정책 누락 |

> 요약: 이 문제는 SBOM 산출물보다 지속 생성·검증·활용 프로세스를 요구한다.

## Ⅰ. 개요 및 필요성

- 개요: SW 구성요소 명세서
- 배경: 오픈소스와 컨테이너 의존성이 늘면서 제품별 취약점 영향 범위 확인이 어려워졌다.
- 필요성: SPDX/CycloneDX 기반 목록으로 취약점 대응, 라이선스 준수, 고객 감사 증거를 확보해야 한다.

---

## Ⅱ. 구조 및 구성요소

```text
Source/Build/Image -> SBOM Generator -> SPDX/CycloneDX
-> Signature/Attestation -> SBOM Repository
-> CVE Matching -> VEX/Remediation -> Customer Disclosure
```

| 구성요소 | 역할 | 특이사항 |
|:---|:---|:---|
| Component | 패키지명, 버전, 공급자, 해시 | package URL, CPE |
| Relationship | direct/transitive dependency 관계 | dependsOn, contains |
| Format | 기계 판독 표준 | SPDX 2.x, CycloneDX 1.x |
| Repository | SBOM 저장·검색·제공 | 릴리스별 immutable 보관 |

> 요약: SBOM은 컴포넌트와 관계를 표준 형식으로 표현하고 검색 가능한 저장소에 보관해야 한다.

---

## Ⅲ. 동작원리 및 흐름도

```text
코드 변경 -> 의존성 해석 -> 빌드/이미지 분석
-> SBOM 생성 -> 서명/검증 -> 저장
-> CVE DB 매칭 -> 영향 제품 조회 -> 조치/VEX 발행
```

| 단계 | 처리 내용 | 검증 기준 |
|:---:|:---|:---|
| 1 | package manager와 container layer 분석 | direct/transitive 포함 100% |
| 2 | SPDX/CycloneDX 생성 | schema validation 통과 |
| 3 | SBOM 서명과 저장 | 릴리스 artifact 매핑 100% |
| 4 | CVE·라이선스 매칭 | critical CVE 24시간 내 영향 조회 |

> 요약: SBOM은 빌드 산출물과 함께 생성·서명·저장되고 CVE 매칭으로 실제 대응에 활용된다.

|:---|:---|:---|:---|
| 범위 파악 | 개발팀 수동 질의 | 저장소 검색 | 영향 제품 조회 30분 이하 |

> 요약: SBOM은 구성요소 가시성을 제공하지만 실제 악용 가능성 판단은 VEX와 런타임 분석이 보완해야 한다.

## Ⅵ. 실무 적용 및 결론

**적용 방안 3개 (필수 — 단계별 또는 항목별):**
1. CI에서 Syft, CycloneDX plugin, Maven/Gradle/npm scanner로 source, build, container image SBOM을 모두 생성
2. SPDX 또는 CycloneDX schema validation 후 cosign/in-toto로 서명하고 릴리스 artifact digest와 1:1 매핑
3. SBOM 저장소를 CVE feed, SCA, VEX와 연결해 critical CVE 발생 시 24시간 내 영향 제품과 조치 상태를 산출

**결론 (2줄):**
- 기술사 판단: 외부 배포 제품, 공공·금융 납품, 컨테이너 기반 서비스는 SBOM을 릴리스 필수 산출물로 지정
- 향후 방향: SBOM은 VEX, SLSA, 코드 서명, provenance와 결합되어 공급망 신뢰 증거로 확장
