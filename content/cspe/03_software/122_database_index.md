## Ⅰ. 개요
- **정의**: 테이블 검색 속도를 높이기 위해 키-포인터 쌍을 별도 자료구조로 유지하는 기법
- **배경/필요성**: Full Table Scan은 데이터 증가에 비례하여 검색 비용이 선형 증가하므로 효율적 탐색 경로가 필요함
- **비유**: 책의 목차·색인처럼 원하는 내용의 위치를 빠르게 찾는 구조와 유사함

| 출제 의도 | 반드시 짚을 핵심 | 감점 회피 포인트 |
|:---|:---|:---|
| 인덱스 유형별 특성 비교 | Clustered vs Non-Clustered 차이 | 인덱스 오버헤드(쓰기 비용) 누락 주의 |

> 요약: 키 기반 탐색 경로를 구성하여 데이터 접근 비용을 줄이는 기법임

## Ⅱ. 구성요소
```text
Query --> Index Lookup --> Leaf Node(Key+Pointer) --> Data Page
              |
         Index Root/Branch (탐색 경로 축소)
```

| 구성요소 | 설명 | 비유 |
|:---|:---|:---|
| Index Key | 정렬 기준이 되는 컬럼 값 | 사전의 표제어 |
| Pointer | 실제 데이터 행 위치(RID 또는 PK)를 가리키는 참조 | 페이지 번호 |
| Clustered Index | 데이터 자체를 키 순서로 물리 정렬하는 인덱스(테이블당 1개) | 사전 본문 순서 |
| Non-Clustered Index | 별도 구조에 키-포인터를 저장하고 원본은 정렬하지 않는 인덱스 | 책 뒤 색인 |

> 요약: Key-Pointer 구조로 탐색 범위를 축소하며 Clustered/Non-Clustered로 구분함

## Ⅲ. 절차
```text
SQL 수행 --> Optimizer 판단 --> Index Scan/Seek --> Data Page 접근
```
- 1단계: 옵티마이저가 WHERE 조건과 인덱스 컬럼을 매칭하여 사용 여부 판단함
- 2단계: Index Seek(등치·범위)로 루트에서 리프까지 트리 탐색 수행함
- 3단계: 리프 노드의 Pointer를 이용해 데이터 페이지에 접근함
- 4단계: Covering Index인 경우 데이터 페이지 접근 없이 리프에서 결과 반환함

> 요약: 옵티마이저 판단 후 트리 탐색-리프 도달-데이터 접근 순으로 처리함

## Ⅳ. 문제점
- 쓰기 성능 저하: INSERT/UPDATE/DELETE 시 인덱스 갱신 오버헤드가 누적됨
- 인덱스 비대화: 불필요 인덱스 남용 시 저장 공간 낭비와 옵티마이저 혼란 발생
- 카디널리티 부적합: 낮은 카디널리티 컬럼에 B-Tree 적용 시 선택도가 낮아 Full Scan 대비 이점 미미함

> 요약: 쓰기 오버헤드, 공간 낭비, 부적합 컬럼 적용이 주요 문제임

## Ⅴ. 개선방안
1. 단기: 사용 빈도 분석 후 미사용 인덱스 정리로 쓰기 부하 감소
2. 중기: 복합 인덱스·Covering Index 설계로 인덱스 수 최적화
3. 장기: 카디널리티 기반 인덱스 유형 선택(B-Tree, Hash, Bitmap) 가이드 수립(123, 124 참조)

> 요약: 인덱스 정리, 복합 설계, 유형별 선택 기준 수립으로 개선함

## Ⅵ. 전망
- 발전 방향: AI 기반 자동 인덱스 추천(Auto-Index Tuning) 기술 확산 추세
- 기술사적 판단: 쿼리 성능의 기본 수단으로 인덱스 설계 역량은 DB 설계의 핵심임
- 기술사 제언: 워크로드 패턴(읽기/쓰기 비율)에 따른 인덱스 전략 차별화 필요
