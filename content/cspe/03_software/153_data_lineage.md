# 📖 【암기용】 개념 완전 이해

> 목적: 데이터 계보를 처음 보는 사람도 완벽히 이해하게 만든다. 시험 답안 양식이 아니라, 이해를 위한 친절한 설명이다.

## 한눈에
- **개요**: 데이터 계보(Data Lineage)는 **메타데이터 관리**의 한 갈래로, 데이터가 어느 원천에서 생성되어 어떤 변환을 거쳐 어디까지 소비되는지 그 **의존 관계(dependency graph)**를 테이블·컬럼 단위로 기록한 것이다.
- **왜 필요한가**: 파이프라인이 많아지면 컬럼 하나를 바꿨을 때 어디까지 영향을 주는지 사람이 기억할 수 없다. 계보가 없으면 장애 원인 추적과 변경 전 영향 분석에 몇 시간~며칠이 걸린다.
- **핵심 직관**: 택배 송장처럼 "어디서 출발해 어느 허브를 거쳐 어디로 도착했는지"를 기록에 남겨, 문제가 생기면 경로를 거슬러 올라가 원인을 찾을 수 있게 한다.

## 핵심 용어 정리 (내부에 등장하는 것들)

| 용어 | 의미 | 비유 |
|:---|:---|:---|
| 메타데이터 관리 | 데이터에 대한 데이터(스키마·소유자·이력)를 체계적으로 관리하는 상위 분야 — 계보는 그 하위 산출물 | 도서관의 도서 카드 목록 |
| 의존 관계 그래프(노드/엣지) | 자산(테이블·컬럼·작업)을 노드로, 흐름을 엣지로 표현한 구조 | 지하철 노선도 |
| upstream / downstream | 특정 자산 기준으로 원천 쪽(upstream)과 소비 쪽(downstream) 방향 | 강물의 상류/하류 |
| 테이블 단위 계보 | 테이블·데이터셋 간 이동만 추적, 컬럼 내부 매핑은 모름 | 화물이 어느 창고를 거쳤는지만 앎 |
| 컬럼 단위 계보 | 특정 컬럼이 어떤 SQL 식으로 다른 컬럼에 매핑되는지까지 추적 | 화물 안 어떤 물건이 어디로 갔는지까지 앎 |
| 런타임 계보 | 실제 실행 로그(쿼리 실행 계획)에서 수집한 계보 — 정적 코드 분석보다 정확하지만 수집 비용이 큼 | 실제 이동 GPS 기록 |
| coverage(수집 범위) | 전체 파이프라인 중 계보가 실제로 수집된 비율 | 감시카메라가 커버하는 구역 비율 |
| OpenLineage/Marquez | 계보 수집 표준 규격과 대표 오픈소스 저장소 | 택배사 공통 배송 추적 포맷 |

## 깊이 이해

### 왜 계보가 필요해졌나 (배경)
파이프라인이 수십~수백 개로 늘어나면, 하나의 원천 테이블 변경이 아무도 인지하지 못한 채 여러 마트와 대시보드를 조용히 깨뜨린다. 사람이 문서나 기억으로 의존 관계를 관리하는 방식은 파이프라인 수가 늘수록 반드시 실패한다. 데이터 계보는 이 의존 관계를 시스템이 자동으로 수집해 그래프로 관리하는 방법이다.

### 어떻게 수집하나 (작동 원리)
ETL/ELT 도구(dbt, Spark, Airflow)와 BI 도구, SQL 실행 로그에서 "이 작업이 어떤 테이블을 읽어 어떤 테이블에 썼는가"를 추출한다. 정적 방식은 SQL·코드를 파싱해 얻고, 런타임 방식은 실제 실행 로그에서 얻는다. 이렇게 모은 관계를 노드(자산)와 엣지(흐름)로 이어 계보 저장소(OpenLineage/Marquez 등)에 저장하면, 특정 자산을 검색할 때 그 upstream/downstream을 즉시 조회할 수 있다.

### 테이블 단위 vs 컬럼 단위 — 왜 구분하나, 수치로 이해
테이블 단위 계보는 "A 테이블이 B 테이블로 흘러간다"까지만 안다. 컬럼 단위 계보는 "A.customer_id가 CAST(customer_id AS VARCHAR) 식을 거쳐 B.cust_no로 매핑됐다"까지 안다.
- **구체 예시**: `customer_id` 컬럼 타입을 INT에서 STRING으로 바꾸는 변경을 검토한다고 하자. 테이블 단위 계보만 있으면 "이 테이블을 참조하는 downstream 테이블이 25개"라는 사실만 안다 — 그중 실제로 customer_id를 쓰는 테이블이 몇 개인지는 모른다. 컬럼 단위 계보가 있으면 "customer_id를 실제로 참조하는 downstream은 테이블 18개, Airflow DAG 4개, 대시보드 7개"까지 정확히 좁혀진다. 컬럼 단위가 없으면 나머지 7개 테이블까지 불필요하게 점검해야 해서 영향 분석 시간이 늘어난다.
- **판별 원리**: PII 마스킹 대상 컬럼, 핵심 매출 지표처럼 "이 컬럼 하나"의 정확한 파급력이 중요하면 컬럼 단위까지 확보해야 하고, "이 테이블이 없어지면 뭐가 깨지나" 정도의 굵은 판단만 필요하면 테이블 단위로 충분하다.

### 정적 파싱 vs 런타임 수집 — 정확도와 비용의 트레이드오프
정적 파싱(SQL·코드를 읽어 계보를 뽑음)은 배포 전에도 계보를 알 수 있어 빠르지만, 문자열을 조립해 동적으로 만드는 SQL은 파싱이 실패한다. 런타임 수집(실제 실행된 쿼리의 실행 계획을 읽음)은 실제로 무엇이 일어났는지 정확히 알지만, 실행이 끝나야 알 수 있고 수집 비용이 크다. 그래서 실무에서는 정적 파싱을 기본으로 쓰고, 파싱 실패율이 높은 영역(예: 3% 초과)만 런타임 수집이나 수동 등록으로 보완한다.

### coverage가 낮으면 계보를 못 믿는다
coverage(수집 범위)가 90% 미만이면, 조회 결과 "downstream이 없다"가 "실제로 없다"인지 "수집이 안 됐을 뿐"인지 구분할 수 없다. 즉 계보는 100%에 가까운 coverage가 아니면 "안전하다"고 확신할 수 없는 도구다 — 계보 운영에서 가장 자주 놓치는 함정이다.

### 비유
전기 배선도와 같다. 스위치 하나를 교체하기 전에 그 스위치가 어느 조명·차단기와 연결됐는지 배선도로 확인하지 않으면, 교체 후 어디서 정전이 나는지 알 수 없다. 계보는 이 배선도를 데이터 파이프라인에 대해 자동으로 그려주는 도구다.

## 연결 개념
- 데이터 카탈로그 — 계보를 검색 화면에 노출하는 상위 도구
- ETL/ELT 파이프라인 — 계보 수집의 주요 데이터 원천
- 데이터 거버넌스 — 계보로 확보한 영향 범위를 변경 승인·감사에 활용

# 📝 【답안용】 시험 답안 템플릿

> 목적: 시험장에서 25분에 그대로 쓰는 답안 양식. 작성방식(추상표현 금지·수치·도식·문제유형 전환)을 엄격히 지킨다.
> 핵심: 데이터 계보 답안은 추적 개념 설명을 넘어 영향 분석, 장애 원인 추적, 규제 감사 대응 지표까지 연결해야 한다.

## 핵심 인사이트 (3줄 요약)

> 1. **본질**: 데이터 계보는 원천, 변환, 적재, 소비 자산 간 의존 관계를 테이블/컬럼 단위로 추적하는 메타데이터 그래프임.
> 2. **가치**: 변경 영향 분석 시간과 장애 원인 추적 시간을 줄이고, 개인정보 처리 경로와 감사 증적을 제공함.
> 3. **판단 포인트**: 테이블 단위, 컬럼 단위, 런타임 계보 중 업무 위험도에 맞는 깊이를 선택해야 함.

## 출제 의도 및 답안 포인트

| 출제 의도 | 반드시 짚을 핵심 | 감점 회피 포인트 |

> 요약: 데이터 계보는 장애 분석과 감사 대응을 위해 의존 관계를 그래프와 지표로 관리하는 체계임.

## Ⅰ. 개요 및 필요성

- 개요: 데이터 계보는 원천부터 소비까지의 흐름 추적 체계임.
- 배경: 데이터 기반 의사결정에서 지표 오류와 컬럼 변경은 다수 리포트에 영향을 준다.
- 필요성: 원천부터 소비까지의 의존 관계를 기록해 변경 영향, 장애 원인, 감사 증적을 제공한다.

## Ⅱ. 구조 및 구성요소

```text
Source Table -> Transform Job -> Target Table -> Data Mart -> BI/API
          +-> Column Mapping
          +-> Run Log/Owner
```

| 구성요소 | 역할 | 특이사항 |
|:---|:---|:---|
| 원천 자산 | DB, 파일, 이벤트의 시작점 | schema, owner 필요 |
| 변환 작업 | SQL, Spark, dbt, Airflow task | 코드와 실행 로그 연결 |
| 대상 자산 | 마트, 피처, 리포트 산출 | downstream 영향 분석 |
| 계보 저장소 | 노드/엣지 그래프 관리 | table, column, runtime 수준 |

> 요약: 계보는 원천, 변환, 대상, 사용처를 노드와 엣지로 연결한 메타데이터 그래프임.

## Ⅲ. 동작원리 및 흐름도

```text
메타데이터 수집 -> SQL/작업 파싱 -> 노드/엣지 생성 -> 영향 범위 조회 -> 변경/감사 기록
```

| 단계 | 처리 내용 | 검증 기준 |
|:---:|:---|:---|
| 1 | DB, ETL, BI 메타데이터 수집 | 주요 시스템 coverage 90% 이상 |
| 2 | SQL, DAG, Spark job 의존성 파싱 | 파싱 실패율 3% 이하 |
| 3 | 테이블/컬럼 노드와 엣지 생성 | 컬럼 매핑률 85% 이상 |
| 4 | 변경 전 downstream 영향 분석 | 영향 대상 조회 5분 이하 |
| 5 | 변경 승인과 감사 증적 보관 | 변경 이력 1년 이상 |

> 요약: 계보는 수집, 파싱, 그래프 생성, 영향 조회, 감사 기록의 절차로 운영됨.

## Ⅵ. 실무 적용 및 결론

**적용 방안 3개 (필수 - 단계별 또는 항목별):**
1. 수집 연계: dbt, Airflow, Spark, BI 메타데이터를 OpenLineage/Marquez로 수집해 테이블 계보 coverage 90% 이상 확보
2. 컬럼 계보: 핵심 지표와 PII 컬럼은 SQL 파서 기반 컬럼 매핑률 85% 이상을 목표로 owner 승인 절차 적용
3. 변경 통제: 컬럼 삭제, 타입 변경, 지표 산식 변경은 downstream 조회 결과를 변경 요청서에 첨부

**결론 (2줄):**
- 기술사 판단: 단순 영향 분석은 테이블 계보, 개인정보와 지표 감사는 컬럼 계보까지 적용함
- 향후 방향: 데이터 계약, 카탈로그, 품질 검증과 결합되어 변경 전 자동 차단 체계로 발전함
