# 📖 【암기용】 개념 완전 이해

## 한눈에
- **개요**: 소프트웨어 규모를 사용자 관점의 논리적 기능(Function) 개수와 복잡도로 수치화하는 측정 기법
- **왜 필요한가**: 과거에는 코드 라인 수(LOC)로 비용을 산정했으나 언어별로 기준이 달라, 사용자가 요구하는 '기능의 크기' 자체를 표준화해 비용을 객관적으로 산출하기 위해 등장했다.
- **핵심 직관**: 건물을 지을 때 "벽돌 몇 장(LOC) 들어갔나" 대신 "방이 몇 개고 화장실이 몇 개인가(FP)"를 세어 공사비를 계산하는 방식이다.

## 핵심 용어 정리

| 용어/표기 | 의미 | 비유·예 |
|:---|:---|:---|
| 데이터 기능 (Data) | 시스템이 유지·관리하는 논리적 데이터 그룹 (ILF, EIF) | 건물의 방, 창고 (내부 DB, 외부 연계 DB) |
| 트랜잭션 기능 (Transaction) | 사용자가 시스템에 입력하거나 출력하는 단위 작업 (EI, EO, EQ) | 문을 열고 닫거나 창밖을 보는 행위 (입력, 출력, 조회) |
| 미조정 기능점수 (UFP) | 복잡도(단순/보통/복잡)만 가중치로 곱해 단순 합산한 기본 점수 | 방 개수 × 방 크기에 따른 기본 단가 |
| 보정 계수 (VAF) | 성능, 다중 사이트, 분산 처리 등 시스템의 비기능적 특성을 14가지로 반영한 계수 | 고층 건물, 특수 자재 등 환경 난이도 할증 |

## 깊이 이해
- **배경·문제의식**: 개발자마다 짜는 코드 길이가 다르고, Java와 C언어의 생산성이 달라 LOC 기준 비용 산정은 갈등이 잦았다. 발주자는 코드 라인이 아니라 '결과물 기능'에 돈을 지불하고 싶어 한다.
- **작동 원리**: 사용자 관점에서 요구사항을 5가지 유형(ILF, EIF, EI, EO, EQ)으로 식별한다. 각 유형별로 데이터 요소(DET)와 레코드 요소(RET), 참조 파일(FTR) 개수를 세어 복잡도(단순/보통/복잡)를 판정하고 가중치를 곱해 UFP를 구한다. 이후 14개 시스템 특성 요인을 평가해 보정 계수를 곱하여 최종 FP를 산출한다.
- **비유**: 인테리어 견적을 낼 때 "목재 30합판"이 아니라, "거실 아트월 1개(단순), 안방 붙박이장 1개(복잡)"로 묶어 견적을 내면 누구나 이해하기 쉽다.
- **구체 예시**: 회원가입 화면(EI)에서 입력 항목 10개(DET)와 회원 DB 1개(FTR)를 참조하면 '보통' 복잡도로 4점을 부여하는 식이다.
- **흔한 오해·주의점**: 기능점수는 내부 알고리즘의 복잡성을 직접 반영하지 못한다. 화면 없는 백엔드 배치(Batch) 작업이나 고도화된 수학적 연산 로직은 사용자 기능 단위를 잡기 어려워 과소평가되기 쉽다.

## 연결 개념
- 간이법·정통법 (FP Estimation Method) — FP 측정 시점과 상세도에 따른 구분
- 소프트웨어 대가산정 (SW Cost Estimation) — FP 기반으로 최종 예산을 산출하는 실무 체계
- COCOMO — FP 이전 주류였던 코드 라인 수 기반 비용 산정 모델

# 📝 【답안용】 시험 답안 템플릿

## 핵심 인사이트 (3줄 요약)

> 1. **본질**: SW 규모를 물리적 코드 라인(LOC)이 아닌 사용자 관점의 논리적 기능(데이터, 트랜잭션)으로 정량화한 국제 표준(ISO/IEC 14143) 측정 방식이다.
> 2. **가치**: 개발 언어나 기술 환경에 독립적이며, 요구사항 명세 단계부터 객관적이고 일관된 SW 대가 산정 기준을 제공한다.
> 3. **판단 포인트**: 수학적 알고리즘이나 백엔드 중심 시스템에서는 기능이 과소평가될 수 있으므로, 내부 복잡도를 보완할 별도 보정 기준(시스템 연계, 성능 등) 적용이 필수적이다.

## 출제 의도 및 답안 포인트

| 출제 의도 | 반드시 짚을 핵심 | 감점 회피 포인트 |
|:---|:---|:---|
| 사용자 관점 SW 규모 산정 원리 이해 | 5가지 기능 유형(ILF, EIF, EI, EO, EQ), UFP 및 보정 계수 산식 | 개발자 관점(LOC, 공수)과 혼동 기술 |
| FP 산정 절차의 실무적 적용 역량 | 측정 유형 식별 → UFP 산정 → 보정 계수(VAF) 적용 → 최종 FP 산출 | 단순히 5개 구성요소만 나열하고 산정 절차 누락 |

> 요약: FP는 물리적 코드가 아닌 논리적 기능(데이터 2종, 트랜잭션 3종)의 복잡도 가중합과 보정 계수를 곱해 최종 규모를 산정하는 체계다.

## Ⅰ. 개요 및 필요성

- 개요: 소프트웨어의 규모를 사용자 관점에서 요구되는 논리적 기능의 양으로 측정하는 객관적 규모 산정 기법임
- 배경: 기존 LOC 방식은 개발 언어(C, Java 등)나 개발자 역량에 따라 동일 기능도 규모가 다르게 산출되는 문제 발생함
- 필요성: 발주자와 수주자 간 비용 분쟁 예방 및 언어·환경에 독립적인 일관된 예산 수립/대가 산정 기준 필요함 (국내 공공기관 의무화)

---

## Ⅱ. 구조 및 구성요소

```text
사용자 요구사항 -> 기능 식별 (Data / Transaction) -> 미조정 기능점수 (UFP) 산정
                      |                              |
                      +-> ILF, EIF                   +-> 복잡도 가중치 부여 (단순/보통/복잡)
                      +-> EI, EO, EQ
```

| 구성요소 | 역할 | 특이사항 |
|:---|:---|:---|
| 데이터 기능 (ILF/EIF) | 시스템 내부 유지(ILF) 및 외부 참조(EIF) 논리 데이터 | RET(레코드), DET(데이터) 개수로 복잡도 판정 |
| 트랜잭션 기능 (EI/EO/EQ) | 데이터 입력(EI), 출력(EO), 조회(EQ) 논리 처리 기능 | FTR(참조파일), DET(데이터) 개수로 복잡도 판정 |
| 미조정 점수 (UFP) | 복잡도 매트릭스에 의한 기능별 점수의 단순 총합 | 비기능적 요소를 배제한 순수 기능 크기 |
| 값 조정 계수 (VAF) | 14개 일반 시스템 특성(데이터 통신, 분산 처리 등) 반영 | (총 영향도 × 0.01) + 0.65 공식으로 산출 |

> 요약: FP 구성은 데이터 기능(ILF, EIF)과 트랜잭션 기능(EI, EO, EQ) 5개 유형으로 나뉘며, 복잡도(UFP)에 환경 보정(VAF)을 곱한다.

---

## Ⅲ. 동작원리 및 흐름도

```text
측정 유형 결정 -> 기능 식별 및 복잡도 판정 -> 미조정 점수(UFP) 산출 -> 조정 계수(VAF) 반영 -> 최종 FP 산출
```

- 1단계 [측정 유형 및 범위 결정]: 개발, 개선, 애플리케이션 측정 중 유형을 선택하고 측정 대상을 확정함
- 2단계 [기능 식별 및 복잡도 판정]: 사용자 요구사항에서 데이터/트랜잭션 기능을 식별하고 DET/RET/FTR 기준으로 복잡도(Low, Avg, High) 결정함
- 3단계 [미조정 점수(UFP) 산출]: 식별된 기능의 개수에 복잡도별 가중치를 곱하여 순수 기능점수 총합 산출함
- 4단계 [조정 계수 반영 및 최종 산출]: 14가지 시스템 특성 영향도(0~5점)를 평가하여 VAF 산출 후, 최종 FP = UFP × VAF 적용함

> 요약: 요구사항에서 5개 기능을 식별하여 복잡도별 가중치를 곱해 UFP를 구하고, 시스템 특성을 반영한 VAF를 곱해 최종 FP를 도출함.

---

## Ⅳ. 특징

- 사용자 관점 지향: 시스템 내부 로직보다 사용자가 인식하는 화면, 입력, 출력, 데이터 위주로 규모를 산정함
- 기술 독립성 확보: 구현 언어나 플랫폼, 하드웨어 아키텍처에 종속되지 않고 동일한 논리적 요구사항은 동일한 규모로 산정됨
- 산정 기준의 객관화: ISO/IEC 14143 국제 표준 및 IFPUG 매뉴얼 기반으로 산정 규칙이 명확하여 담당자 간 편차 최소화함
- 내부 로직 평가 한계: 복잡한 수학 연산, 배치(Batch) 처리 등 화면(UI)이 없는 내부 알고리즘의 복잡도는 기능점수로 환산하기 어려움

## Ⅴ. 심화 비교 및 적용 판단

| 비교 축 | LOC (코드 라인 수) | FP (기능 점수) | 선택 기준 |
|:---|:---|:---|:---|
| 측정 관점 | 개발자 관점 (물리적) | 사용자 관점 (논리적) | 예산 수립, 대외 계약 시 FP 필수 |
| 언어 의존성 | 매우 높음 (C > Java) | 독립적 (동일 요구사항 = 동일 규모) | 언어 확정 전 기획 단계 산정 가능 여부 |
| 측정 시기 | 구현 완료 후 또는 상세 설계 후 | 요구사항 분석 및 설계 단계 | 발주 전 조기 예산 확보 시 FP 활용 |

**도입 리스크 및 대응:**
- [알고리즘 과소평가]: 사용자 UI가 적고 복잡한 내부 로직 위주 시스템 산정 시 규모 축소 → 데이터 연계 복잡도 보정 및 소프트웨어 사업 대가산정 가이드 특수 요율 적용
- [산정자 편차 발생]: 측정자 주관에 따른 DET/RET 식별 오류 → IFPUG 공인 자격(CFPS) 보유자 검수 및 사내 FP 산정 표준 가이드라인 배포
- [유지보수 측정 난해]: 소규모 기능 개선 시 FP 산출 기준 모호 → 개별 기능점수(단가 기반) 또는 투입 공수(M/M) 혼합 방식 적용

**도입 후 점검 지표:**
- 산정 일관성: 교차 검증 시 측정자 간 FP 편차 5% 이내 — IFPUG 샘플 테스트 기준
- 예산 오차율: 기획 단계 산출 FP와 최종 구현 후 FP의 오차율 10% 미만 — 프로젝트 완료 후 실사

## Ⅵ. 실무 적용 및 결론

**적용 방안 3개:**
1. 공공사업 발주: 기획 단계에서 기능점수 간이법을 적용해 개략적 예산을 편성하고, 상세 설계 후 정통법으로 최종 대가를 확정함
2. MSA 환경 산정: 마이크로서비스 간 통신(API 호출)을 외부 연계 파일(EIF)과 외부 조회(EQ)로 매핑하여 모놀리식 대비 연계 복잡도를 정량 반영함
3. 보정 계수 최적화: 보안(시큐어코딩), 성능(대용량 트래픽), 분산 환경 등 비기능 요구사항을 14개 특성 외 공공 대가산정 가이드 보정 계수로 세분화 적용함

**결론 (2줄):**
- 기술사 판단: FP는 언어 독립적인 객관적 규모 산정 표준이나, AI/데이터 분석 등 내부 로직 중심 시스템에서는 과소평가될 수 있으므로 투입공수 방식과 교차 검증이 필요함
- 향후 방향: 요구사항 정의서(SRS)나 User Story에서 자연어 처리(NLP)와 LLM을 활용해 FP를 자동 추출하는 AI 기반 자동 산정 도구 도입이 확대될 것임
