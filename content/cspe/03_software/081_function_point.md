## 미리 알고가기

- 기능점수(Function Point): 소프트웨어가 사용자에게 제공하는 기능적 규모를 정량적으로 측정하는 표준 단위임
- 데이터 기능(Data Function): 내부논리파일($ILF$)과 외부연계파일($EIF$)로 구성되는 시스템 내부 및 외부의 데이터 저장 기능임
- 트랜잭션 기능(Transaction Function): 외부입력($EI$), 외부출력($EO$), 외부조회($EQ$)로 구성되는 데이터 처리 및 전송 기능임
- $DET$(Data Element Type): 사용자 관점에서 식별 가능하고 중복되지 않는 고유한 데이터 필드(열)의 개수임
- $RET$(Record Element Type): 사용자 관점에서 식별 가능한 내부논리파일($ILF$) 또는 외부연계파일($EIF$) 내부의 데이터 레코드 서브그룹 개수임
- $FTR$(File Type Referenced): 트랜잭션 기능 수행 중 참조하거나 갱신하는 데이터 파일($ILF$, $EIF$)의 개수임

## 작성 근거(검토용)

- 핵심 키워드 선정 이유: 기능점수($FP$)는 소프트웨어 대가 산정의 표준으로 126회 기출되었으며, 정량적 규모 측정을 위해 핵심 5대 기능 유형과 가중치 산정이 필수 키워드이기에 선정함
- 절 구성·전개 흐름 이유: 개요에서 개념을 정의하고, 특징에서 언어 독립성을, 비교에서 $LOC$와의 차이를 다룬 뒤, 구성요소(정적)와 측정 절차(동적)를 논리적으로 전개함
- 전수 검수 완료 근거: 제목, frontmatter, 미리 알고가기, 본문, 비교표, 텍스트 도식 및 결론을 한 줄도 빠뜨리지 않고 5회 전수 낭독하며 조사 및 전문 용어 결합의 자연스러움을 검증함

## Ⅰ. 개요

- **정의/개념**: 기능점수 $FP$는 소프트웨어의 구현 기술과 독립적으로 사용자 요구사항 기반의 기능 유형과 데이터 요소를 정량적으로 평가하여 규모를 산정하는 측정 기법임
- **배경/필요성**: 소스 코드 줄 수($LOC$) 방식의 물리적 구현 의존성과 언어별 편차를 극복하고 사용자 관점의 객관적인 규모 및 대가 산정을 위해 도입이 필요함

### 쉽게 이해하기 (학습용)
- 건물을 지을 때 들어간 벽돌의 개수가 아닌 방의 개수, 화장실 개수를 기준으로 건물의 크기와 가격을 매기는 방식과 유사함

## Ⅱ. 특징

- 구현 언어 및 개발 도구와 무관하게 사용자 요구사항만으로 기능 규모를 비교할 수 있음
- 외부 입력·출력·조회와 내부·외부 파일을 식별해 개발 초기 단계부터 규모 및 비용 추정이 가능함
- 측정자의 주관적 해석에 따라 측정 결과에 편차가 발생할 수 있으므로 표준 측정 가이드 준수가 요구됨

### 쉽게 이해하기 (학습용)
- 어떤 프로그래밍 언어로 작성했는지 상관없이 시스템이 사용자에게 제공하는 가치만을 평가하므로 대가 산정이 객관적임

## Ⅲ. 종류 및 비교

| 판단 기준 | $LOC$ 기반 규모 산정 | 기능점수 $FP$ |
|:---|:---|:---|
| 측정 기준 | 작성된 소스 코드 라인 수 | 제공되는 데이터 및 트랜잭션 기능 수 |
| 산정 시점 | 코딩 완료 후 최종 단계 | 요구사항 정의 및 설계 초기 단계 |
| 언어 의존성 | 프로그래밍 언어 및 코딩 스타일에 의존 | 구현 기술과 독립적으로 규모 일관성 유지 |

### 쉽게 이해하기 (학습용)
- 소설책의 가치를 글자 수로 세어 평가하는 것과 책 속에 담긴 핵심 에피소드의 개수로 세어 평가하는 것의 차이임

## Ⅳ. 구성요소 및 구조

```text
[사용자 / 외부 시스템]
       │ (EI / EO / EQ)
┌──────▼───────────────────────┐
│         시스템 경계          │
│  ┌──────────┐   ┌──────────┐ │
│  │   ILF    │   │   EIF    │ │
│  └──────────┘   └─────▲────┘ │
└───────────────────────┼──────┘
                        │ (참조)
                  [외부 시스템]
```

| 설계 요소 | 설명 |
|:---|:---|
| 외부 입력($EI$) | 경계 외부에서 내부로 데이터가 유입되어 내부 논리 파일($ILF$)을 등록·수정·삭제하는 기능 |
| 외부 출력($EO$) | 처리·계산을 거쳐 데이터나 정보를 시스템 경계 외부로 전달하는 기능 |
| 외부 조회($EQ$) | 데이터의 변경 없이 단순 검색을 통해 정보나 보고서를 외부로 출력하는 기능 |
| 내부 논리 파일($ILF$) | 해당 시스템 내부에서 유지·관리되는 사용자 식별 가능한 데이터 그룹 |
| 외부 인터페이스 파일($EIF$) | 다른 시스템에 의해 유지되며 해당 시스템은 단순 참조만 하는 데이터 그룹 |

### 쉽게 이해하기 (학습용)
- 회원 가입(EI), 보고서 출력(EO), 정보 조회(EQ)는 움직이는 기능이고, 회원 데이터베이스(ILF)와 날씨 API(EIF)는 보관하는 서랍장임

## Ⅴ. 원리 및 절차 흐름도

```text
┌──────────────┐     ┌──────────────┐     ┌──────────────┐     ┌──────────────┐
│ 1. 경계 정의 │  →  │ 2. 기능 식별 │  →  │ 3. 복잡도 가중│  →  │ 4. 점수 산정 │
└──────────────┘     └──────────────┘     └──────────────┘     └──────────────┘
```

1. **측정 범위 및 경계 정의**: 기능 점수를 측정할 대상 소프트웨어와 외부 사용자 및 외부 시스템의 경계를 명확히 획득함
2. **기능 식별 및 분류**: 경계 내의 요구사항을 데이터 기능($ILF$, $EIF$)과 트랜잭션 기능($EI$, $EO$, $EQ$)으로 식별하고 분류함
3. **복잡도 식별 및 가중치 결정**: 각 기능별 데이터 요소($DET$)와 참조 파일($FTR$/$RET$)의 개수를 기준으로 복잡도 가중치를 매김
4. **최종 기능점수 산정**: 가중치가 곱해진 기능별 점수를 합계하여 최종 미조정 기능점수($UFP$)를 계산하고 조정 계수를 적용함

### 쉽게 이해하기 (학습용)
- 견적서를 작성할 때 사업 범위를 획득하고, 기능들을 나열한 후, 각각의 복잡도에 따라 정해진 단가를 매겨 최종 금액을 합산하는 흐름임

## Ⅵ. 실무 사례

- 공공 소프트웨어 개발 사업 발주 시 기능점수 기반 대가산정 가이드를 활용해 정량적인 예산을 수립하고 요구사항 변경 시 추가 기능점수를 측정해 변경 대가를 지급함

### 쉽게 이해하기 (학습용)
- 공공기관 홈페이지를 만들 때 기획서에 명시된 기능의 개수로 예산을 책정하고, 개발 중 기능이 추가되면 추가 요금을 산정하여 정산함

## Ⅶ. 결론

- 기능점수는 코드 중심의 불확실한 생산성 측정을 배제하고 요구사항의 본질에 부합하는 소프트웨어 가치 중심의 척도를 제공함
- 공학적 관점에서 기능점수는 애자일 스프린트의 기능 규모 측정 및 소프트웨어 자산 관리 지표로서 정착되어야 함

### 쉽게 이해하기 (학습용)
- 기술이 바뀌어도 사용자가 얻는 기능의 가치는 같으므로 기능점수는 소프트웨어의 실제 크기를 재는 객관적인 자가 됨
