# 📖 【암기용】 개념 완전 이해

> 목적: 기능점수를 처음 보는 사람도 사용자 기능 관점의 규모 산정 방식을 이해하게 만든다. 시험 답안 양식이 아니라, 이해를 위한 설명이다.

## 한눈에
- **개요**: 기능점수(Function Point, FP)는 사용자가 실제로 받는 기능의 양을 EI·EO·EQ·ILF·EIF 5개 유형으로 세어 정하는 **소프트웨어 규모 산정** 단위임
- **왜 필요한가**: 소스코드 줄 수(LOC)는 같은 기능이라도 언어·프레임워크·개발자 스타일에 따라 천차만별로 달라져서, 아직 코드가 없는 요구사항 단계의 비용 산정 기준으로 쓸 수 없음
- **핵심 직관**: 건물의 규모를 벽돌 개수가 아니라 평수(면적)로 재듯, 소프트웨어의 규모도 코드 줄 수가 아니라 사용자가 쓰는 화면·조회·파일 개수로 잰다

## 핵심 용어 정리 (내부에 등장하는 것들)

| 용어 | 의미 | 비유 |
|:---|:---|:---|
| 소프트웨어 규모 산정 | 개발할 시스템의 크기를 숫자로 측정해 비용·일정 산정의 기준으로 삼는 활동 — FP가 속하는 **상위 개념** | 이사 견적을 내기 전 짐의 부피를 재는 것 |
| EI(External Input, 외부 입력) | 사용자가 데이터를 시스템 안으로 넣는 기능(등록·수정·삭제) | 회원가입 폼 제출 |
| EO(External Output, 외부 출력) | 시스템이 계산·가공을 거친 데이터를 사용자에게 내보내는 기능(집계 리포트, 통계) | 월별 매출 합계 리포트 |
| EQ(External Inquiry, 외부 조회) | 계산·가공 없이 저장된 데이터를 그대로 찾아 보여주는 기능(단순 목록·상세 조회) | 회원 목록을 그대로 화면에 뿌리는 것 |
| ILF(Internal Logical File, 내부논리파일) | 이 시스템이 직접 생성·수정·삭제하며 관리하는 데이터 그룹(테이블) | 이 회사가 직접 관리하는 회원 DB |
| EIF(External Interface File, 외부연계파일) | 다른 시스템이 관리하고 이 시스템은 조회만 하는 데이터 그룹 | 다른 부서 시스템의 인사 DB를 조회만 하는 경우 |
| DET(Data Element Type) | 사용자가 인식하는 고유 필드(항목) 개수 | 회원가입 폼의 이름·전화번호·이메일 등 입력칸 수 |
| RET(Record Element Type) | 파일(ILF/EIF) 안에서 사용자가 인식하는 하위 데이터 그룹(레코드) 개수 | 회원 정보 안의 "기본정보"와 "배송지 목록" 두 하위 그룹 |
| FTR(File Type Referenced) | 트랜잭션(EI/EO/EQ) 하나가 처리 중 참조하는 파일(ILF/EIF) 개수 | 주문 등록 시 "주문 테이블"과 "재고 테이블" 2개를 건드리면 FTR=2 |
| UFP(Unadjusted Function Point) | 복잡도 판정 전, 5개 기능유형에 가중치를 곱해 합산한 조정 전 기능점수 | 옵션 적용 전의 기본 견적 |

## 깊이 이해

### 복잡도를 판정하는 법 — 표준 가중치표로 수치 이해
- 같은 EI라도 필드가 3개뿐인 단순 등록 폼과 필드 20개짜리 복잡한 등록 폼은 규모가 다르다. 그래서 DET(필드 수)와 FTR(참조 파일 수)을 기준으로 낮음(Low)·보통(Average)·높음(High) 복잡도를 판정하고, 복잡도마다 다른 가중치를 곱한다.
- 트랜잭션 기능(EI/EO/EQ)의 표준 가중치는 다음과 같다.

| 기능유형 | 낮음(Low) | 보통(Average) | 높음(High) |
|:---|:---:|:---:|:---:|
| EI | 3 | 4 | 6 |
| EO | 4 | 5 | 7 |
| EQ | 3 | 4 | 6 |

- 데이터 기능(ILF/EIF)은 DET와 RET(하위 그룹 수)로 복잡도를 판정하며 가중치는 다음과 같다.

| 기능유형 | 낮음(Low) | 보통(Average) | 높음(High) |
|:---|:---:|:---:|:---:|
| ILF | 7 | 10 | 15 |
| EIF | 5 | 7 | 10 |

- 예: 회원가입 EI가 DET 12개(이름·전화번호·이메일 등)·FTR 1개(회원 테이블만 참조)면 보통(Average) 복잡도로 판정되어 4점, 회원 DB인 ILF가 DET 25개·RET 2개(기본정보+배송지)면 보통 복잡도로 10점이 매겨진다.

### UFP를 실제로 산정하는 워크드 예제
- 작은 회원관리 기능을 예로 들면: 회원등록 EI 1개(보통, 4점) + 회원수정 EI 1개(보통, 4점) + 회원목록 EQ 1개(보통, 4점) + 회원 통계 리포트 EO 1개(보통, 5점) + 회원 DB ILF 1개(보통, 10점) = UFP 합계 27점.
- 이렇게 사용자가 인지하는 기능 단위로 하나씩 세어 합산하면, 개발 언어가 Java든 Python이든 상관없이 "이 시스템은 27 기능점수 규모"라는 동일한 값이 나온다 — 이것이 LOC 대신 FP를 쓰는 이유다.

### EO와 EQ, ILF와 EIF를 헷갈리지 않는 판별법
- EO와 EQ의 차이는 "출력하기 전에 계산·가공 로직이 있는가"이다. 회원 목록을 그대로 뿌리면 EQ, 월 매출을 집계·합산해서 보여주면 EO다.
- ILF와 EIF의 차이는 "이 시스템이 그 데이터를 직접 생성·수정·삭제하는가"이다. 이 시스템이 직접 관리하면 ILF, 다른 시스템이 관리하고 이 시스템은 읽기만 하면 EIF다.

### 흔한 오해
- FP는 "개발자가 코딩하는 데 걸리는 시간"이 아니라 "사용자 눈에 보이는 기능의 양"을 재는 단위다. 같은 27 FP짜리 시스템도 개발팀 숙련도에 따라 실제 소요 시간은 다를 수 있다.
- 성능·보안 같은 비기능 요구사항은 FP 유형(EI/EO/EQ/ILF/EIF) 안에 임의로 끼워 넣지 않는다. 이런 요구는 별도의 보정계수나 SW 대가산정 문서의 다른 항목으로 반영한다(자세한 계수 산정은 별도 SW 대가산정 문서에서 다룸).

# 📝 【답안용】 시험 답안 템플릿

> 목적: 시험장에서 25분에 그대로 쓰는 답안 양식. 작성방식(추상표현 금지·수치·도식·문제유형 전환)을 엄격히 지킨다.
> 핵심: FP 문제는 항목 암기가 아니라 사용자 기능 식별, UFP 산정, 보정계수 적용, 과소추정 통제를 연결해야 한다.

## 핵심 인사이트 (3줄 요약)

> 1. **본질**: 기능점수(Function Point)는 사용자 관점 기능량을 EI·EO·EQ·ILF·EIF 5개 유형과 복잡도 가중치로 계량화하는 규모 산정 단위이다.
> 2. **가치**: 요구사항 단계에서 코드 없이도 UFP를 산출하여 공공 SW 대가산정, 일정, 투입공수 기준값을 제공한다.
> 3. **판단 포인트**: 기능 경계, 데이터 기능, 트랜잭션 기능을 잘못 나누면 FP가 20% 이상 흔들리므로 산정 근거 추적표가 필요하다.

## 출제 의도 및 답안 포인트

| 출제 의도 | 반드시 짚을 핵심 | 감점 회피 포인트 |
|:---|:---|:---|
| 요구사항 기반 규모 산정 역량 확인 | EI·EO·EQ·ILF·EIF, UFP, 보정계수 | LOC와 FP를 같은 기준으로 설명하지 않음 |
| 공공 SW 대가산정 연결 확인 | 기능유형별 가중치, 개발유형 보정, 재사용 조정 | 화면 수만 세고 데이터 기능을 누락하지 않음 |
| 과소추정 리스크 통제 확인 | 산정 경계, 복잡도 판정 근거, 변경관리 | 비기능 요구를 FP 내부에 임의 포함하지 않음 |
> 요약: FP 답안은 5개 기능유형으로 UFP를 산정하고 보정계수·리스크 통제로 비용 산정 신뢰도를 확보하는 구조가 핵심이다.

## Ⅰ. 개요 및 필요성

- 개요: 사용자 기능량 규모 단위
- 배경: 요구사항 단계에는 LOC와 상세 설계가 없으므로 화면, 출력, 조회, 내부논리파일, 외부연계파일 기준의 규모 산정 체계가 필요하다.
- 필요성: 공공 SW 사업은 기능점수(FP)로 개발비, 유지관리비, 변경 대가를 산정하므로 기능 경계와 복잡도 판정 근거가 필요하다.

## Ⅱ. 구조 및 구성요소

```text
사용자 요구사항 -> 애플리케이션 경계 설정 -> 데이터 기능 식별
사용자 요구사항 -> 트랜잭션 기능 식별 -> 복잡도 가중치 적용
EI/EO/EQ/ILF/EIF -> UFP -> 보정계수 -> 조정 FP
```

| 구성요소 | 역할 | 산정 포인트 |
|:---|:---|:---|
| EI | 외부 입력 처리 | 등록·수정·삭제, DET/FTR 기준 |
| EO | 외부 출력 생성 | 계산·파생 데이터 포함 보고서 |
| EQ | 외부 조회 응답 | 단순 조회, 입력과 출력 조합 |
| ILF/EIF | 내부·외부 논리파일 | 유지 주체와 애플리케이션 경계 |
> 요약: FP 구조는 트랜잭션 기능 3종과 데이터 기능 2종을 분리해 UFP를 산출하는 방식이다.

## Ⅲ. 동작원리 및 흐름도

```text
요구사항 수집 -> 기능 경계 확정 -> 기능 유형 분류
-> DET/RET/FTR 복잡도 판정 -> 가중치 적용 -> UFP 합산
-> 보정계수 적용 -> 산정 근거 검토
```

| 단계 | 처리 내용 | 검증 기준 |
|:---:|:---|:---|
| 1 | 애플리케이션 경계와 사용자 식별 | 시스템 간 책임분계서 |
| 2 | EI·EO·EQ·ILF·EIF 분류 | 기능목록과 데이터목록 1:1 추적 |
| 3 | 낮음·보통·높음 복잡도 판정 | DET/RET/FTR 산정표 |
| 4 | 기능유형별 가중치 곱셈 | UFP 합계 재계산 오차 0건 |
| 5 | 보정계수와 조정 FP 산출 | 변경·재사용·품질 요구 반영 |
> 요약: FP는 기능 식별, 복잡도 판정, 가중치 합산, 보정 적용 순서로 산정 근거를 남긴다.

## Ⅳ. 특징

| 구분 | LOC 방식 | FP 방식 | 수치·판단 기준 |
|:---|:---|:---|:---|
| 산정 시점 | 구현 이후 측정 가능 | 요구사항 단계 산정 가능 | RFP·분석 단계 적용 |

| 한계 | 초기 견적 근거 부족 | 기능 경계 해석 차이 | 산정자 간 편차 10~30% 관리 |
> 요약: FP는 초기 견적과 계약 기준에 맞지만 경계·복잡도 판정 편차를 검토회의로 줄여야 한다.

> 요약: FP는 계약·대가·변경관리의 공통 단위가 필요할 때 LOC보다 적용성이 높다.

| 변경비 누락 | 요구변경 FP 미분리 | 기준선 FP와 변경 FP 분리 | 변경 승인 추적률 100% |
> 요약: FP 리스크는 산정 기술보다 기능 경계 합의와 추적성 관리에서 발생한다.

| 점검 항목 | 목표 기준 | 측정 방법 |
|:---|:---|:---|
| 산정 완전성 | 요구사항 대비 기능 매핑 100% | 요구사항-FP 추적표 |

| 변경 통제 | 변경 FP 승인률 100% | 변경관리대장 |
> 요약: FP 도입 후에는 매핑률, 산정 편차, 단가 근거, 변경 FP 승인률로 신뢰도를 판단한다.

## Ⅵ. 실무 적용 및 결론

**적용 방안 3개:**
1. 요구사항 ID와 EI·EO·EQ·ILF·EIF를 연결한 추적표를 작성하고 미매핑 요구사항 0건 기준으로 검토함.
2. 산정자 2인이 독립 산정 후 FP 편차 15% 초과 항목은 DET·RET·FTR 근거를 재검토함.
3. 기준선 FP, 변경 FP, 재사용 FP를 분리하고 변경 승인 시 비용·일정 영향도를 5영업일 내 산출함.

**결론 (2줄):**
- 기술사 판단: 요구사항 단계 계약·대가 산정이면 FP를 기준으로 하고, 구현 완료 후 생산성 분석이면 LOC·투입공수 지표를 병행함.
- 향후 방향: FP 산정은 요구사항 관리도구와 연동해 기능 변경, 비용, 일정 영향도를 자동 추적하는 방향으로 발전함.
