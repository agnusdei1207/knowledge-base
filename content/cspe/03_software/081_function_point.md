## 핵심 인사이트 (3줄 요약)
- 소프트웨어의 크기(규모)를 '코드의 줄 수(LOC)'가 아닌, **'사용자 관점에서 제공되는 기능의 논리적 개수와 복잡도'**로 정량화하여 측정하는 소프트웨어 규모 산정 기법.
- 입력(EI), 출력(EO), 조회(EQ), 내부 논리 파일(ILF), 외부 인터페이스 파일(EIF)의 5가지 데이터/트랜잭션 유형을 식별하고 가중치를 곱해 점수를 산출함.
- "몇 줄을 짰느냐"가 아니라 "무슨 가치를 만들었느냐"를 측정하므로 언어(Java, Python)에 독립적이며, 대한민국 공공 SI 프로젝트의 소프트웨어 개발비 산정 시 100% 의무 적용되는 법적 표준임.

## Ⅰ. 개요 및 필요성
- **개요**: Allan Albrecht(IBM)가 1979년에 고안한 기법으로, 정보 시스템이 사용자에게 제공하는 기능적 요구사항을 크기로 변환하는 측정 방식 (ISO/IEC 20926).
- **필요성**: 과거에는 소프트웨어 견적을 낼 때 "코드 몇 줄(LOC) 짤 거냐?"로 계산했음. 그러자 C언어로 100줄 짜는 것과 Python으로 10줄 짜는 것의 가치가 다름에도, 코드를 길게 짜는 비효율적 개발자가 돈을 더 많이 받는 모순이 발생함. 언어나 기술에 상관없이 '기능의 가치' 자체를 공평하게 측정할 기준이 필요했음.
---
## Ⅱ. 아키텍처 및 핵심 원리
- **기능점수(FP) 5대 측정 요소**:
  - **데이터 기능 (Data Functions)**: 
    1. **ILF (내부 논리 파일)**: 시스템 내부에서 유지/관리되는 데이터베이스 테이블 (예: 회원 테이블).
    2. **EIF (외부 인터페이스 파일)**: 다른 시스템에서 읽어오기만 하는 참조 데이터 (예: 기상청 날씨 API).
  - **트랜잭션 기능 (Transaction Functions)**:
    3. **EI (외부 입력)**: 데이터베이스(ILF)에 데이터를 등록/수정/삭제하는 행위 (예: 회원가입, 정보수정).
    4. **EO (외부 출력)**: 수학적 계산이나 로직 처리를 거쳐 결과를 밖으로 내보내는 행위 (예: 이자율 계산 후 통계 보고서 출력).
    5. **EQ (외부 조회)**: 단순한 데이터 검색 및 조회 (계산 로직 없음) (예: 회원 목록 검색).

```text
[ 기능점수(FP)의 시스템 경계와 5대 요소 도식 ]

           (사용자 / User)
             |   |   |
      (EI) ⬇️  (EO)⬆️ (EQ)⬆️
  +--------------------------------+
  |  [ 소프트웨어 애플리케이션 경계 ]     |         (타 시스템)
  |                                |
  |       [(저장) ILF]   <======(참조)====== [ EIF ]
  |                                |
  +--------------------------------+
```

## Ⅲ. 비교 및 연결
| 구분 | LOC (Lines of Code) | FP (기능점수) |
|---|---|---|
| **측정 관점** | 개발자 관점 (물리적 코드 라인 수) | 사용자 관점 (논리적 기능 제공량) |
| **언어 종속성** | 종속적 (C, Java, Python마다 라인수 다름) | **독립적** (기능이 같으면 점수도 같음) |
| **산정 시점** | 개발이 다 끝나야 정확히 알 수 있음 | **기획/설계 단계(요구사항 분석)에서 산정 가능** |
| **활용** | 개인 프로그래머 생산성 측정용 | 프로젝트 예산 산정, 국가 공공 입찰 기준 |

## Ⅳ. 실무 적용 및 기술사 판단
- **정통법(상세법) vs 간이법**:
  - 정통법: 데이터 요소(DET)와 레코드(RET) 개수를 일일이 세어 복잡도(상/중/하)를 따짐 (매우 피곤함).
  - 간이법(평균 복잡도 가중치): 복잡도를 평균으로 고정하여 빠르게 점수를 냄. (예: EI=4.3, EO=5.4점). 현재 국내 공공 발주 시 '기획/예산 확보 단계'에서는 간이법을, 설계가 끝난 후 '확정 단계'에서는 정통법을 쓰는 것이 실무적 가이드라인임.
- **비기능 요구사항의 한계**: 기능점수는 순수하게 눈에 보이는 기능(CRUD)만 측정함. "응답속도를 0.1초로 맞추기 위한 튜닝 작업"이나 "최고 수준의 암호화 적용" 같은 비기능 요구사항은 FP로 산정되지 않아 SI 업체들이 손해를 보는 구조적 문제가 있음. 이를 보정하기 위해 규모 보정 계수(VAF)나 추가 단가 할증 제도가 활용됨.

## Ⅴ. 기대효과 및 결론
- "소프트웨어도 건축물처럼 면적(평수)을 잴 수 있다"는 패러다임을 확립하여, IT 프로젝트의 견적(비용)과 일정 산정에 과학적 객관성을 부여함.
- 발주자(예산 투명성)와 수주자(정당한 대가) 모두가 합의할 수 있는 유일한 글로벌 커뮤니케이션 잣대로서 기능하고 있음.

### 👶 어린이를 위한 3줄 비유 설명
1. 집을 지을 때 벽돌을 "1만 개 쌓았다(LOC)"고 해서 무조건 좋은 집이 아니에요. 벽돌이 크면 적게 쌓아도 되니까요.
2. 기능점수(FP)는 벽돌 개수 대신 "방이 몇 개야(ILF)? 문은 몇 개야(EI)? 창문은 몇 개야(EQ)?"라고 세어보는 거예요.
3. 이렇게 세면 나무로 집을 짓든 콘크리트로 짓든(프로그래밍 언어) 상관없이, '집의 진짜 크기'를 아주 공평하게 점수로 계산할 수 있답니다!
