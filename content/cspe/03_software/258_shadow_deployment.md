## Ⅰ. 개요
- **정의**: 신규 모델이 실제 트래픽을 수신하되 응답을 반환하지 않고 기록만 하는 배포 전략임
- **배경/필요성**: 운영 트래픽에 영향 없이 신규 모델의 실제 환경 성능을 검증할 수단이 필요함
- **비유**: 부조종사가 실제 비행 중 조종 연습을 하되 실제 조종은 기장이 하는 구조임

| 출제 의도 | 반드시 짚을 핵심 | 감점 회피 포인트 |
|:---|:---|:---|
| 무위험 모델 검증 전략 이해 | 응답 미반환(Dark Launch) 특성 | Canary(257)와 혼동 시 감점 |

> 요약: 사용자 영향 없이 실제 트래픽으로 신규 모델을 검증하는 배포 전략임

## Ⅱ. 구성요소
```text
User Request --> Primary Model (v1) --> Response to User
      |
      +-------> Shadow Model (v2) --> Log Only (no response)
                      |
                      v
               Offline Comparator --> Report
```

| 구성요소 | 설명 | 비유 |
|:---|:---|:---|
| Primary Model | 실제 사용자 응답을 담당하는 현행 모델 | 정조종사 |
| Shadow Model | 동일 입력을 받아 추론하되 결과를 기록만 함 | 부조종사 연습 비행 |
| Traffic Mirroring | 요청을 복제하여 Shadow에 전달하는 인프라 계층 | 영상 녹화 분배기 |
| Offline Comparator | Primary/Shadow 결과를 사후 비교·분석 | 비행 기록 분석관 |

> 요약: Primary·Shadow 이중 추론과 Offline 비교기·미러링으로 구성됨

## Ⅲ. 절차
```text
Mirror Traffic --> Shadow Inference --> Log Results --> Offline Compare
```
- 1단계: 트래픽 미러링 — 실제 요청을 복제하여 Shadow 모델에 전달
- 2단계: Shadow 추론 — Shadow 모델이 추론 수행, 결과를 로그 스토리지에 적재
- 3단계: 결과 기록 — Primary와 Shadow 응답을 동일 요청 ID로 매핑·저장
- 4단계: Offline 비교 — 배치 분석으로 정확도·지연시간·분포 차이를 비교·리포트

> 요약: 미러링 → 추론 → 기록 → 비교의 4단계로 무위험 검증을 수행함

## Ⅳ. 문제점
- 인프라 비용 2배: 동일 트래픽을 두 모델이 처리하므로 컴퓨팅 비용이 2배로 증가함
- 부작용 미검증: 사용자 반응(클릭·전환 등)은 Primary 기준이므로 Shadow 영향 측정 불가
- 상태 변경 위험: Shadow 추론이 외부 시스템(DB 쓰기 등)에 부작용을 일으킬 수 있음

> 요약: 비용 2배·사용자 반응 미측정·부작용 위험이 주요 한계임

## Ⅴ. 개선방안
1. 단기: 샘플링 비율 조절(전체 트래픽의 10~20%)로 인프라 비용 절감
2. 중기: 사후 A/B 테스트(259 참조) 전환으로 사용자 반응 데이터까지 수집
3. 장기: 외부 호출 격리(Sandbox/Mock) 적용으로 Shadow 부작용 원천 차단

> 요약: 샘플링·A/B 전환·호출 격리로 Shadow 배포 한계를 보완함

## Ⅵ. 전망
- 발전 방향: Service Mesh 기반 자동 미러링으로 Shadow 배포 설정이 간소화되는 추세임
- 기술사적 판단: 고위험 도메인(의료·금융)에서 사전 검증 필수 단계로 자리잡고 있음
- 기술사 제언: Canary(257) 전 단계로 Shadow를 배치하여 2단계 안전망을 구성해야 함
