# 📖 【암기용】 개념 완전 이해

> 목적: 섀도 배포를 처음 보는 사람도 완벽히 이해하게 만든다. 시험 답안 양식이 아니라, 이해를 위한 친절한 설명이다.

## 한눈에
- **개요**: 섀도 배포는 **점진적 배포 전략(Progressive Delivery)**의 하나로, 운영 트래픽을 신규 모델에도 그대로 복제해 실행하는 **트래픽 미러링(Traffic Mirroring)** 기법이다. 복제된 신규 모델의 결과는 기록만 되고, 사용자에게는 기존 모델 응답만 반환된다.
- **왜 필요한가**: 오프라인 테스트셋은 실제 운영의 요청 분포·크기·피크 부하를 반영하지 못한다. 신규 모델을 바로 노출하면 예측 오류가 그대로 사용자에게 전달되므로, 노출 전에 실제 트래픽으로 안전하게 리허설할 방법이 필요하다.
- **핵심 직관**: 신규 모델을 뒤에서 몰래 예행연습시키고 결과는 기록만 하며, 실제 고객에게는 기존 답을 제공하는 방식이다.

## 핵심 용어 정리 (내부에 등장하는 것들)

| 용어 | 의미 | 비유 |
|:---|:---|:---|
| 점진적 배포(Progressive Delivery) | 신규 버전을 한 번에 전체 노출하지 않고 단계적으로 검증·확산하는 배포 전략 총칭 — 섀도·카나리·블루그린·A/B가 하위 기법 | 신입사원을 정규직 전환 전 단계적으로 검증하는 수습 절차 |
| 트래픽 미러링(Traffic Mirroring) | 원본 요청 흐름은 그대로 두고, 동일 요청을 별도 목적지로 복제 전송하는 것 | 방송 원본은 그대로 내보내면서 녹화본도 동시에 뜨는 것 |
| Baseline Model | 사용자에게 실제 응답을 돌려주는 현재 운영 모델 | 지금 손님을 응대 중인 정직원 |
| Shadow Model | 복제된 요청을 받아 추론은 하지만, 결과가 사용자에게 나가지 않는 신규 후보 모델 | 옆에서 같이 답안만 써 보는 수습사원 |
| 동기 복제 / 비동기 복제 | 동기: 원 요청 처리가 shadow 응답까지 기다림(지연 전이). 비동기: 복제본을 큐에 던지고 원 요청 경로와 분리(fire-and-forget) | 손님 응대 중 뒤에 세워두고 기다리게 하는 것 vs 메모만 남기고 바로 보내는 것 |
| Compare Log (score diff, p95, 5xx) | baseline과 shadow 결과의 차이를 기록하는 로그 — 예측 점수차, 지연 백분위, 오류율 | 모의고사와 실제 답안을 나란히 놓은 채점표 |
| 카나리 배포 (대비 개념) | 실사용자 일부에게 신규 버전을 실제로 노출해 행동 지표까지 확인하는 기법 | 섀도가 "몰래 연습"이라면 카나리는 "일부 손님에게만 실전 투입" |

## 깊이 이해

### 왜 섀도가 필요한가 — 오프라인 평가의 한계
오프라인 테스트셋은 고정된 스냅샷이라 운영의 피크 시간대 요청 분포, 요청 크기 변동, 동시성 부하를 반영하지 못한다. 예를 들어 오프라인 정확도 95%인 사기탐지 모델도, 실제로 초당 500건 요청이 몰리는 결제 피크 시간대에는 GPU 큐잉이 발생해 p95 지연이 300ms까지 치솟을 수 있다. 이런 문제는 사용자에게 노출하기 전, 실제 트래픽으로만 드러난다.

### 트래픽 미러링의 동작 원리 — 동기 vs 비동기
Envoy·Istio 같은 서비스 메시나 API Gateway는 들어온 요청을 두 갈래로 나눈다. 원본 요청은 baseline model로 보내 사용자 응답을 만들고, 동시에 복제본을 shadow model로 보낸다. 이때 복제를 동기로 처리하면 원 요청이 shadow 응답까지 기다리게 되어(예: shadow 추론에 100ms가 걸리면 baseline 응답도 100ms 늦어짐) 사용자 체감 지연에 영향을 준다. 그래서 실무는 비동기(fire-and-forget) 복제를 쓴다 — 요청을 별도 큐에 던지고 원 응답 경로와 완전히 분리해, baseline 지연에 미치는 영향을 이론상 0ms에 가깝게 유지한다.

### 수치로 보는 판정 기준
사기탐지 v2를 7일간 섀도 실행한다고 하자. 기간을 7일 이상으로 잡는 이유는 주중·주말, 월초 결제 피크를 모두 포함해야 표본이 대표성을 갖기 때문이다. 결과가 v1 대비 score diff 평균 0.02, p95 지연 80ms(v1은 75ms로 5ms 증가 — 병렬 추론에 따른 GPU 자원 경합), shadow 자체 5xx 오류율 0.05%(목표 0.1% 이하)로 나오면 통과 기준을 만족한 것이고, 이때 비로소 카나리 단계로 전환한다.

### 판별 원리 — 언제 섀도인가, 카나리인가, A/B인가
세 기법은 "사용자에게 영향을 줄 수 있는가"와 "무엇을 측정하려는가"로 갈린다.
- **섀도**: 사용자 영향 0. 측정 가능한 건 시스템 지표(지연·오류·예측값 차이)뿐이다. 클릭률·전환율 같은 행동 지표는 애초에 사용자가 결과를 못 보므로 발생하지 않아 측정 자체가 불가능하다.
- **카나리**: 실사용자 일부(예: 5%)에게 신규 모델을 실제로 노출한다. 시스템 지표뿐 아니라 사용자 반응도 관찰할 수 있지만, 잘못되면 그 5%는 실제 영향을 받는다.
- **A/B**: 노출 방식은 카나리와 비슷하지만 목적이 다르다. 카나리는 "안전한가"를 확인하는 위험 완화가 목적이고, A/B는 "어느 쪽이 더 나은가"를 통계적으로 확정하는 효과 검증이 목적이다.

그래서 표준적인 순서는 섀도(무위험 검증) → 카나리(제한적 실노출로 안전성 재확인) → A/B(효과 검증)로 이어진다.

### 비유와 흔한 오해
- **비유**: 신입 상담원이 실제 상담을 옆에서 동시에 답안 작성해 보지만, 고객에게는 숙련 상담원의 답변만 전달되는 훈련과 같다.
- **오해 1**: "섀도 배포를 통과하면 A/B 테스트는 필요 없다" — 틀렸다. 섀도는 시스템이 안 죽는지만 보여줄 뿐, 사용자가 신규 모델의 답을 더 선호하는지는 전혀 알려주지 않는다.
- **오해 2**: 병렬 추론 비용을 간과하기 쉽다. baseline과 shadow를 동시에 돌리므로 GPU·CPU 추론 비용은 이론상 2배가 든다. 그래서 실무에서는 전체 트래픽이 아니라 일부(예: 10%)만 샘플링해 미러링하기도 한다.

## 연결 개념
- 카나리 배포: 섀도 검증 통과 후 일부 사용자에게 실노출해 안전성을 재확인하는 다음 단계
- A/B 테스트: 사용자 행동 기반 효과를 통계적으로 검증하는 단계 (섀도·카나리와 목적이 다름)
- 모델 모니터링: 섀도 단계에서 수집한 지연·오류·score diff를 운영 단계까지 이어서 비교하는 체계

# 📝 【답안용】 시험 답안 템플릿

> 목적: 시험장에서 25분에 그대로 쓰는 답안 양식. 작성방식(추상표현 금지·수치·도식·문제유형 전환)을 엄격히 지킨다.
> 핵심: 섀도 배포 답안은 실제 트래픽 복제, 사용자 미노출, 로그 비교, 부하 비용을 함께 제시해야 한다.

## 핵심 인사이트 (3줄 요약)

> 1. **본질**: 섀도 배포는 운영 요청을 신규 모델에도 복제해 실행하지만 사용자에게는 기존 모델 응답만 반환하는 무노출 검증 방식이다.
> 2. **가치**: 실제 트래픽 기반 지연, 오류, 예측 분포를 사용자 영향 없이 측정한다.
> 3. **판단 포인트**: 사용자 반응 KPI는 측정할 수 없으므로 섀도 후 카나리 또는 A/B로 이어지는 단계 설계가 필요하다.

## 출제 의도 및 답안 포인트

| 출제 의도 | 반드시 짚을 핵심 | 감점 회피 포인트 |
|:---|:---|:---|
| 배포 검증 방식 이해 | 요청 복제, 응답 미노출, 결과 비교 | 카나리와 동일시 |
| 리스크 통제 확인 | 사용자 영향 0, 지연·오류 측정 | 업무 KPI 검증 가능하다고 단정 |
| 운영 비용 판단 | 병렬 추론 비용, 로그 저장, 개인정보 | 부하 증가와 마스킹 누락 |

> 요약: 섀도 배포는 노출 전 운영 적합성 검증이며 효과 검증은 후속 실험이 필요하다.

## Ⅰ. 개요 및 필요성

- 개요: 섀도 배포는 신규 모델 무노출 운영 검증 방식이다.
- 배경: 실제 요청을 신규 모델에도 복제하되 사용자는 기존 모델 결과만 받는다.
- 필요성: 운영 데이터 기반 지연, 오류, 예측 분포를 확인해 사용자 노출 전 리스크를 검증해야 한다.

---

## Ⅱ. 구조 및 구성요소

```text
Client Request -> Request Mirror -> Baseline Model -> User Response
                              / Shadow Model -> Compare Log -> Metrics
```

| 구성요소 | 역할 | 통제 기준 |
|:---|:---|:---|
| Request Mirror | 운영 요청을 신규 모델로 복제 | 동기/비동기 복제 |
| Baseline Model | 실제 사용자 응답 생성 | 기존 Production |
| Shadow Model | 신규 모델 무노출 실행 | 결과 저장만 수행 |
| Compare Log | 예측 차이, 지연, 오류 비교 | score diff, p95, 5xx |

> 요약: 섀도 구조는 실제 응답 경로와 신규 모델 검증 경로를 분리한다.

---

## Ⅲ. 동작원리 및 흐름도

```text
모델 후보 준비 -> 요청 복제 설정 -> 기존 응답 반환 -> 신규 결과 저장 -> 차이 분석 -> 카나리 전환 판단
```

| 단계 | 처리 내용 | 검증 기준 |
|:---:|:---|:---|
| 1 | 신규 모델을 별도 엔드포인트에 배치 | 레지스트리 버전 확인 |
| 2 | 운영 요청을 비동기 복제 | 원응답 지연 영향 0ms 목표 |
| 3 | 신규 모델 결과와 지표 저장 | p95, 오류율, score diff |
| 4 | 통계 리포트 후 노출 여부 판단 | 7일 이상 피크 포함 |

> 요약: 섀도 배포는 실제 요청으로 신규 모델을 검증하되 사용자 응답 경로를 변경하지 않는다.

## Ⅴ. 심화 비교 및 적용 판단

| 비교 축 | 기존/대안 | 섀도 배포 | 선택 기준 |
|:---|:---|:---|:---|
| 구조 | 오프라인 테스트 | 실제 요청 복제 | 운영 분포 확인 필요 |
| 비용/성능 | 추가 추론 없음 | 병렬 추론 비용 발생 | GPU·CPU 여유 필요 |
| 운영/위험 | 노출 후 문제 발견 | 노출 전 오류 탐지 | 고객 영향 제한 |

> 요약: 실제 트래픽 적합성은 필요하지만 사용자 노출이 부담되는 모델은 섀도 배포가 적합하다.

| 리스크 | 원인 | 대응 방안 | 확인 지표 |
|:---|:---|:---|:---|
| 원서비스 지연 | 동기 복제로 응답 경로 영향 | 비동기 mirror, timeout | baseline latency delta |
| 비용 증가 | 두 모델 동시 추론 | 샘플링, 피크 시간 제한 | shadow cost |
| 개인정보 로그 | 요청 원문 저장 | 마스킹, 토큰화, 보존 기간 | PII 검출 0건 |

> 요약: 섀도 리스크는 원서비스 지연, 병렬 비용, 개인정보 로그이며 비동기 처리와 마스킹으로 통제한다.

| 점검 항목 | 목표 기준 | 측정 방법 |
|:---|:---|:---|
| 지연 영향 | 기존 응답 p95 변화 5ms 이하 | APM 비교 |
| 신규 모델 품질 | score diff 허용 범위 내 | 비교 리포트 |
| 운영 오류 | shadow 5xx 0.1% 이하 | Gateway log |

> 요약: 섀도 성공 여부는 기존 응답 영향, 신규 결과 차이, 오류율로 판단한다.

## Ⅵ. 실무 적용 및 결론

**적용 방안 3개:**
1. Envoy, Istio, API Gateway의 traffic mirroring으로 요청을 비동기 복제하고 원응답 경로 timeout을 분리함
2. 신규 모델의 예측값, 지연, 오류, model version을 로그로 저장하고 PII는 마스킹 후 30일 보존함
3. 7일 이상 섀도 실행 후 p95 100ms, 5xx 0.1% 이하, score diff 허용 범위 통과 시 카나리로 전환함

**결론 (2줄):**
- 기술사 판단: 사용자 영향이 큰 모델은 섀도 배포로 운영 적합성을 먼저 확인하고, 행동 KPI는 카나리·A/B에서 검증함
- 향후 방향: 섀도 배포는 자동 비교 리포트와 정책 기반 승격을 통해 MLOps 배포 게이트로 정착됨
