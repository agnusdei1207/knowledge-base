## 핵심 인사이트 (3줄 요약)
- 전통적인 오프셋(OFFSET/LIMIT) 기반 페이지네이션이 뒤로 갈수록 DB를 다 뒤져야 하는 치명적 성능 저하(O(N))를 해결하기 위해 등장한 **B-Tree 인덱스 기반의 스와이프 전용 초고속 탐색 기법**.
- "앞에서부터 N개 건너뛰어 줘"가 아니라, **"내가 마지막으로 본 글(Cursor)이 152번인데, 그 밑으로 20개만 더 줘!"**라고 DB에 요청하여 인덱스를 0.001초 만에 타게 만드는 것이 핵심.
- 트래픽이 몰리는 무한 스크롤(인스타그램, 당근마켓 피드) 환경에서 백엔드 서버가 뻗지 않고 일관된 응답 속도(O(1))를 유지하기 위한 현대 API 설계의 필수 교양임.
---
## Ⅰ. 개요 및 필요성
- **개요**: 클라이언트가 이전 페이지의 마지막 레코드 고유값(Cursor/Keyset)을 기억했다가, 다음 페이지 요청 시 기준점으로 삼아 그 이후의 데이터만 인덱스 스캔을 통해 빠르게 조회하는 페이징 기법.
- **필요성**: 기존의 `SELECT * FROM 게시판 ORDER BY ID DESC LIMIT 20 OFFSET 100000;` 쿼리는 DB가 앞선 10만 개의 데이터를 일단 다 읽어서 메모리에 올린 다음, 10만 개를 버리고 20개를 반환하는 무식한 짓(Table Full Scan)을 함. 게시물이 1,000만 개면 마지막 페이지 로딩에 10초가 넘게 걸림. "1페이지나 1000페이지나 로딩 속도가 똑같은" 페이징 기법이 절실했음.
---
## Ⅱ. 아키텍처 및 핵심 원리
- **1. 커서(Cursor)의 정의**:
  - 데이터의 특정 위치를 완벽히 가리킬 수 있는 고유하고 정렬 가능한 값(주로 Primary Key, Timestamp 등의 조합).
- **2. 인덱스 타기 (Index Scan)**:
  - `WHERE ID < 100000 ORDER BY ID DESC LIMIT 20;`
  - 이 쿼리가 실행되면 DBMS는 B-Tree 인덱스를 타고 10만 번 노드에 바로 꽂힌 뒤, 뒤쪽으로 단 20개의 리프(Leaf) 노드만 스캔하고 즉시 쿼리를 끝냄. (건너뛰는 연산 자체가 발생하지 않음).
- **3. 데이터 중복/누락 방지 (Data Anomaly 해소)**:
  - 오프셋 페이징은 내가 1페이지를 보는 사이에 누군가 글을 3개 쓰면, 다음 장(2페이지)으로 넘어갈 때 1페이지에서 봤던 글 3개가 또 밀려서 보이는 중복(Anomaly)이 발생함. 
  - 커서 페이징은 "내가 본 152번 글 이후"라는 절대적인 기준선이 있으므로, 위에서 새 글이 백만 개가 등록되든 말든 다음 글들이 절대 꼬이지 않음.

```text
[ Offset Paging vs Cursor Paging 성능 비교 ]

 🐢 [ Offset (전통적 방식): "1,000,000번째 글부터 10개 줘" ]
 데이터 읽기 ➡️ 1번, 2번... (계속 읽으면서 버림)... 999,999번 ➡️ [ 100만 ~ 100만 9번 반환 ]
 성능: O(N), 뒤로 갈수록 기하급수적으로 느려짐. DB CPU 사용량 폭발.

 🚀 [ Cursor (모던 방식): "마지막으로 본 글 번호가 1,000,000번이야. 그다음 10개 줘" ]
 데이터 읽기 ➡️ (인덱스 B-Tree 3 Depth 만에 100만 번 주소 바로 찾음!) ➡️ [ 100만 1번 ~ 100만 10번 반환 ]
 성능: O(1), 첫 페이지나 마지막 페이지나 0.01초 소요.
```

## Ⅲ. 비교 및 연결
| 구분 | 오프셋 페이징 (Offset / Limit) | 커서 페이징 (Cursor / Keyset) |
|---|---|---|
| **조회 성능** | 첫 페이지는 빠름, 뒤로 갈수록 극도로 느려짐 | **페이지 위치 상관없이 항상 초고속 (O(1))** |
| **새 글 등록 시 오류** | 중복된 글이 보이거나, 누락되는 현상 발생 | **정확한 기준점(Cursor)이 있어 오류 발생 안 함** |
| **UI/UX 적합성** | 하단에 [1] [2] [3]... 페이지 번호가 있는 게시판 | **인스타그램, 당근마켓 같은 무한 스크롤** |
| **단점 (한계)** | 성능이 나쁨 | **"50페이지로 바로 가기" 기능(Jump) 구현 불가능** |

## Ⅳ. 실무 적용 및 기술사 판단
- **정렬 컬럼의 중복 처리 문제**: 커서를 잡을 때 단순 '조회수'로만 잡으면, 조회수가 100인 글이 500개 있을 때 커서가 꼬여버림. 실무 아키텍트는 반드시 **`WHERE 조회수 < 100 OR (조회수 = 100 AND ID < 마지막글ID)`** 처럼, 고유값(PK)을 보조 커서로 결합하여(Tie-breaker) 어떤 상황에서도 절대적인 순서가 보장되도록 SQL을 작성해야 함.
- **Base64 인코딩으로 커서 은닉**: 클라이언트에 `last_id=152`라고 생짜 번호를 주면, 해커가 번호를 조작해 DB를 크롤링하거나 시스템 내부 키 구조를 유추함. 따라서 백엔드는 `{"id": 152, "views": 100}`를 Base64로 인코딩한 난수 문자열(`ey...`)을 커서로 던져주고(Opaque Cursor), 클라이언트는 그 뜻을 모른 채 그냥 서버로 다시 릴레이만 하도록 설계해야 보안이 유지됨.
---
## Ⅴ. 기대효과 및 결론
- 모바일 시대의 기본 UX인 '무한 스크롤(Infinite Scroll)'을 백엔드 DB가 견뎌내게 만든 가장 아름답고 효율적인 쿼리 최적화 기법.
- "모든 데이터를 일단 다 가져와서 버리는" 인간의 게으른 사고(Offset)에서 벗어나, "B-Tree 인덱스의 특성을 완벽히 이용해 점프(Cursor)"하는 데이터베이스 친화적 엔지니어링의 정수임.

### 👶 어린이를 위한 3줄 비유 설명
1. **오프셋(Offset) 방식**은 책에서 500쪽을 찾을 때, 1쪽부터 499쪽까지 한 장씩 다 넘기고 나서야 500쪽을 읽는 바보 같은 방법이에요 (엄청 오래 걸림).
2. **커서(Cursor) 방식**은 어제 읽은 499쪽에 '책갈피(커서)'를 딱 꽂아두는 거예요.
3. 다음 날 책을 펴면, 앞부분은 무시하고 책갈피를 꽂아둔 500쪽을 1초 만에 딱! 펼쳐서 바로 읽을 수 있는 아주 똑똑한 방법이랍니다!
