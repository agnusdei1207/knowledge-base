# 📖 【암기용】 개념 완전 이해

## 한눈에
- **개요**: 오프셋(Offset) 방식의 성능 저하와 데이터 중복/누락 문제를 해결하기 위해, 마지막 조회 데이터의 고유 키값을 기준으로 다음 페이지를 조회하는 데이터베이스 페이징 기법이다.
- **왜 필요한가**: 수천만 건의 데이터에서 `LIMIT 10 OFFSET 100000`을 호출하면 DB는 10만 건을 모두 읽고 버려 성능이 급격히 저하된다. 또한 조회 중 데이터가 삽입/삭제되면 사용자가 보는 페이지에 데이터가 중복되거나 누락된다.
- **핵심 직관**: "1000번째 글부터 10개 줘"가 아니라, "글 번호 950번 다음부터 10개 줘"라고 요청해 불필요한 데이터 스캔을 원천 차단한다.

## 핵심 용어 정리 (내부에 등장하는 것들)

| 용어/표기 | 의미 | 비유·예 |
|:---|:---|:---|
| 오프셋(Offset) 페이징 | 처음부터 지정된 개수만큼 건너뛰고 데이터를 가져오는 방식 | "책을 앞에서부터 100페이지 넘긴 후 읽기" |
| 커서(Cursor) / 키셋(Keyset) | 다음 페이지를 식별하기 위한 고유한 기준값 (예: 마지막 식별자) | "읽던 곳에 책갈피 꽂아두기" |
| 인덱스 스캔(Index Scan) | 인덱스를 타고 기준값 위치로 바로 이동해 데이터를 읽는 기법 | "책 목차를 보고 5장으로 바로 펼치기" |

## 깊이 이해
- **배경·문제의식**: 전통적인 게시판은 `LIMIT N OFFSET M` 방식을 주로 썼다. 하지만 SNS 피드나 무한 스크롤(Infinite Scroll) 환경에서는 뒤 페이지로 갈수록 M값이 커져 DB가 스캔해야 할 데이터량이 기하급수적으로 증가(O(N))하는 성능 문제가 발생한다. 또한, 조회 중 새 글이 등록되면 데이터가 밀려 같은 글을 두 번 보게 되는 정합성 문제가 생긴다.
- **작동 원리**: 커서 기반 페이징은 클라이언트가 이전 페이지의 마지막 데이터 식별자(Cursor)를 서버에 전달한다. 서버는 `WHERE id < :cursor LIMIT 10`과 같이 쿼리를 실행한다. 인덱스가 설정된 식별자를 조건으로 쓰기 때문에 DB는 B-Tree 인덱스를 타고 기준 위치를 O(log N) 만에 찾아 정확히 10건만 읽는다(O(1)의 데이터 스캔).
- **비유**: 줄 서 있는 10,000명의 학생 중 9,000번째부터 10명을 뽑을 때, 오프셋은 "1번부터 9,000명까지 하나하나 세고 버린 뒤 10명을 데려와"라는 방식이다. 반면 커서 페이징은 "학번 20230900번 학생 다음 10명 나와"라고 부르는 방식이다.
- **구체 예시**: `SELECT * FROM posts ORDER BY id DESC LIMIT 10 OFFSET 1000000` 쿼리는 100만 10건을 읽어 100만 건을 버린다. 이를 `SELECT * FROM posts WHERE id < 54321 ORDER BY id DESC LIMIT 10`로 바꾸면 딱 10건만 읽게 되어 수백 ms의 지연이 수 ms로 단축된다.
- **흔한 오해·주의점**: 커서 페이징이 만능은 아니다. 기준이 되는 커서 컬럼은 반드시 유니크(Unique)하고 정렬 가능해야 한다. 중복된 값이 많은 컬럼(예: 생성일시) 단독으로는 커서로 쓸 수 없으며, 반드시 고유 식별자(ID)와 결합하여 복합 인덱스를 구성해야 한다. 특정 페이지 번호(예: 75페이지)로 곧장 뛰어넘는 점프(Jump) 기능 구현이 어렵다는 한계가 있다.

# 📝 【답안용】 시험 답안 템플릿

## 핵심 인사이트 (3줄 요약)

> 1. **본질**: 커서/키셋 페이징은 연속적인 데이터 조회 시 오프셋을 쓰지 않고 인덱스된 고유 키값을 기준으로 다음 데이터를 조회하는 쿼리 최적화 기법이다.
> 2. **가치**: 무한 스크롤과 대용량 데이터 환경에서 O(N)의 스캔 오버헤드를 O(1) 수준으로 낮추고 실시간 데이터 변동에 따른 중복/누락을 방지한다.
> 3. **판단 포인트**: 페이지 이동 UI(점프)가 필요한지, 무한 스크롤 기반의 실시간 피드인지 서비스 요구사항에 맞춰 오프셋과 커서 방식을 취사선택해야 한다.

## 출제 의도 및 답안 포인트

| 출제 의도 | 반드시 짚을 핵심 | 감점 회피 포인트 |
|:---|:---|:---|
| 대용량 데이터 페이징 성능 병목 원인 이해 | Offset 방식의 Full Scan / 인덱스 미활용 문제 | 단순 쿼리 작성법만 나열 |
| 커서 기반 페이징의 성능 개선 원리 설명 | 인덱스 스캔(O(log N)), 데이터 정합성 유지 | 커서 컬럼의 Unique 속성 언급 누락 |
| UI/UX 요구사항에 따른 기술 적용 판단 | 무한 스크롤 vs 전통적 페이지네이션 (점프 제약) | 커서를 만능으로 묘사 |

> 요약: 오프셋 기반 페이징의 성능/정합성 한계를 지적하고 인덱스 탐색을 통한 커서 페이징의 구조적 우위를 설명해야 한다.

## Ⅰ. 개요 및 필요성

- 개요: 마지막으로 조회한 레코드의 식별자(Cursor/Keyset)를 조건절(`WHERE`)에 사용하여 다음 페이지를 조회하는 데이터베이스 쿼리 기법
- 배경: 기존 `OFFSET` 방식은 뒤 페이지로 갈수록 앞의 레코드를 모두 읽고 버려야 하므로 대규모 서비스에서 성능 저하가 극심함
- 필요성: 모바일 무한 스크롤 환경에서 실시간 데이터 삽입/삭제 시 발생하는 UI 데이터 중복/누락을 방지하고 p95 응답 지연을 50ms 이내로 보장하기 위함

---

## Ⅱ. 구조 및 구성요소

```text
Client (커서 값 보유) -> API Server -> DB Optimizer (B-Tree Index 탐색) -> Index Scan -> 결과 집합
                        [WHERE id < :cursor LIMIT n]
```

| 구성요소 | 역할 | 특이사항 |
|:---|:---|:---|
| Cursor (Keyset) | 현재 페이지의 마지막 레코드를 식별하는 고유 기준값 | 반드시 정렬 가능하고 유니크해야 함 |
| 조건절 (WHERE) | 커서 값을 인덱스 조건으로 활용해 스캔 시작점 지정 | 불필요한 레코드 스킵 연산 방지 |
| 복합 인덱스 | 정렬 조건(예: 날짜)과 고유키(ID)를 묶어 인덱스화 | 비고유 커서 사용 시 중복 데이터 누락 방지 |

> 요약: 클라이언트가 전달한 커서를 DB가 인덱스로 곧장 찾아가 데이터를 읽는 O(1) 스캔 구조다.

---

## Ⅲ. 동작원리 및 흐름도

```text
클라이언트 1페이지 요청 -> 커서 없이 조회 -> 결과 집합 반환 (마지막 ID=100)
-> 스크롤 이벤트 -> 클라이언트 2페이지 요청 (cursor=100) -> WHERE id < 100 LIMIT 조회 -> 결과 집합 반환
```

- 1단계 [최초 조회]: 클라이언트가 기준점 없이 1페이지 요청을 보내고 상위 N건과 마지막 레코드 식별자(커서)를 반환받음
- 2단계 [다음 요청]: 스크롤 하단 도달 시 클라이언트가 1단계의 커서를 포함하여 2페이지 요청
- 3단계 [인덱스 탐색]: DB 옵티마이저가 B-Tree 인덱스를 이용해 지정된 위치를 O(log N) 탐색 비용으로 직행
- 4단계 [데이터 반환]: 찾은 노드부터 잎(Leaf) 레벨을 순차 탐색해 정확히 N건만 스캔 후 클라이언트 반환

> 요약: 스캔 시작점을 명확히 지시하여 DB가 스킵(버림)해야 할 데이터를 읽지 않도록 최적화한다.

---

## Ⅳ. 특징
- [성능 최적화]: 페이지 깊이와 무관하게 일관된 빠른 조회 응답 시간 보장 (O(N) -> O(1) 수준 유지)
- [데이터 정합성]: 조회 중 새로운 데이터가 등록되거나 기존 데이터가 삭제되어도 페이징이 밀리지 않음
- [기능적 한계]: N번째 페이지로 직접 이동하는 임의 점프(Random Jump) 기능 구현 불가

> 요약: 성능과 데이터 안정성이 탁월하지만 특정 페이지 번호로 직행하는 UI 요구사항은 충족할 수 없다.

---

## Ⅴ. 심화 비교 및 적용 판단

| 비교 축 | 기존/대안 (Offset) | 본 키워드 (Cursor) | 선택 기준 |
|:---|:---|:---|:---|
| 성능 변동성 | 페이지 깊어질수록 O(N) 급증 | 페이지 깊이와 무관하게 일정 | 대규모 데이터 및 딥 페이징 여부 |
| 데이터 정합성 | 실시간 추가/삭제 시 중복·누락 발생 | 정합성 유지됨 | 실시간 데이터 변동(피드 등) 발생 여부 |
| 지원 UI | N번 페이지 번호 네비게이션 가능 | 더보기 버튼, 무한 스크롤만 가능 | 화면 기획의 네비게이션 방식 |

> 요약: 실시간 변동이 심하고 무한 스크롤을 쓰는 모바일 UI에는 커서를, 게시판의 번호 네비게이션에는 오프셋을 제한적 깊이로 쓴다.

**리스크·대응 (기본은 불릿):**
- [비고유 컬럼 정렬 시 누락]: 생성일시(Timestamp) 같은 비고유 값만 커서로 쓸 경우 초당 다수 건 등록 시 데이터 누락 발생 → Timestamp + ID 조합의 복합 인덱스와 다중 WHERE 조건 활용
- [커서 변조 취약점]: 클라이언트가 커서 값을 조작하여 비정상 쿼리 발생 → 커서 값을 Base64/암호화 인코딩하여 불투명 토큰(Opaque Token)으로 전달 (지표: 비정상 파라미터 에러율)

**도입 후 점검 지표 (기본은 불릿):**
- 성능/효율: 딥 페이징 구간(예: 10,000번째 이후)의 p95 쿼리 실행 시간 50ms 이내 유지 — 슬로우 쿼리 로그 모니터링
- 품질/운영: 스크롤 진행 중 데이터 중복 노출률 0% — 사용자 세션 기반 프론트엔드 로깅 분석

## Ⅵ. 실무 적용 및 결론

**적용 방안 3개:**
1. 아키텍처 전환: 소셜 피드, 댓글, 활동 내역 등 실시간성이 높은 무한 스크롤 도메인을 식별해 커서 기반 페이징 우선 전환
2. 커서 설계 표준화: 비즈니스 노출 정보 결합 방지를 위해 인덱스 기반 정렬 값들을 Base64 불투명 토큰으로 감싸는 API 표준 수립
3. 하이브리드 적용: B2B 관리자 페이지처럼 점프가 필수인 화면은 검색 조건 인덱스를 태우되 제한된 오프셋 상한선(예: 1,000건)을 둔다

**결론 (2줄):**
- 기술사 판단: 서비스 규모가 커지면 오프셋 페이징은 장애의 직접적 원인이 되므로, 실시간 대용량 서비스의 기본 페이징 설계는 커서 방식을 표준으로 삼아야 한다.
- 향후 방향: GraphQL과 결합된 Relay Cursor Connection 명세가 B2C 서비스 API의 글로벌 표준으로 자리 잡을 것이다.
