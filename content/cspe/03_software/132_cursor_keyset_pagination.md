## 미리 알고가기

- 오프셋 페이지네이션은 `OFFSET n LIMIT m`처럼 앞의 행을 건너뛰며 읽는 방식임
- 키셋 페이지네이션은 마지막으로 본 정렬 키를 기준으로 다음 페이지를 찾는 방식임
- 커서는 다음 페이지 위치를 나타내는 기준값으로 주로 정렬 키나 복합 키를 담음

## Ⅰ. 개요

- **정의/개념**: 커서·키셋 페이지네이션은 마지막으로 조회한 행의 정렬 기준값을 커서로 넘겨 다음 페이지를 읽는 방식으로, 큰 오프셋 비용과 중복·누락 문제를 줄이기 위한 조회 기법임
- **배경/필요성**: 데이터가 많아질수록 오프셋 방식은 앞쪽 행을 계속 건너뛰느라 느려지고 중간 삽입·삭제가 있으면 페이지 경계가 흔들려 안정적인 목록 조회가 필요해짐

## Ⅱ. 특징

- 큰 페이지 번호로 갈수록 오프셋이 느려지는 문제를 줄이기 좋음
- 마지막 정렬 키 이후 범위를 index로 읽어 앞선 행을 반복 scan하지 않음
- 시간·고유 ID 복합 키를 cursor로 사용해 무한 스크롤과 시간순 피드의 다음 구간을 조회함
- 임의 페이지 점프는 불편하므로 관리 화면과 사용자 피드의 요구를 구분해야 함

## Ⅲ. 종류 및 비교

| 판단 기준 | 오프셋 페이지네이션 | 커서·키셋 페이지네이션 |
|:---|:---|:---|
| 성능 | 뒤 페이지로 갈수록 느려질 수 있음 | 큰 데이터에서도 비교적 안정적임 |
| 데이터 변동 영향 | 앞 구간 삽입·삭제가 offset 위치 변경 | 안정된 정렬 키 이후 조건으로 다음 구간 유지 |
| 이동 방식 | 페이지 번호로 임의 offset 이동 | 이전 응답의 cursor로 다음·이전 구간 이동 |
| 주의점 | 큰 오프셋 비용 | 정렬 키와 커서 설계가 중요함 |

## Ⅳ. 구성요소 및 구조

| 구성요소 | 설명 |
|:---|:---|
| Sort Key | 시간이나 ID처럼 정렬과 비교 기준이 되는 컬럼임 |
| Cursor | 마지막 행의 정렬 키 값을 담아 다음 요청 기준으로 씀 |
| Query Predicate | `key < last_key` 같은 다음 범위 조건을 생성함 |
| Index | 정렬 키와 조건을 빠르게 처리하게 함 |
| Response Metadata | 다음 커서와 더 읽을 데이터 존재 여부를 함께 돌려줌 |

```text
이전 페이지 마지막 키 -> Cursor -> 다음 조건 생성 -> Index Lookup -> 다음 페이지
```

## Ⅴ. 원리 및 절차 흐름도

```text
첫 페이지 조회 -> 마지막 정렬 키 저장 -> 커서 전달 -> 다음 범위 재조회 -> 새 커서 발급
```

1. **첫 페이지 조회**: 정렬 기준으로 처음 `LIMIT` 만큼 읽음
2. **마지막 키 저장**: 마지막 행의 정렬 키를 커서로 저장함
3. **다음 요청 전달**: 클라이언트가 커서를 함께 보냄
4. **범위 재조회**: 서버가 커서를 기준으로 다음 범위를 읽음
5. **새 커서 발급**: 다시 마지막 키를 돌려주며 반복함

## Ⅵ. 실무 적용 및 유의점

1. 시간순 피드와 대용량 목록 API는 키셋 페이지네이션이 잘 맞지만 정렬 키가 중복되면 경계가 흔들릴 수 있으므로 복합 키 기준을 정하고 중복 조회 건수와 누락 건수와 평균 조회 시간으로 확인함
2. 관리자 화면처럼 특정 페이지로 바로 가야 하는 업무는 오프셋이 더 편하므로 사용자 피드와 운영 화면을 분리하고 깊은 페이지 응답 시간과 사용자 이동 패턴으로 확인함

## Ⅶ. 결론

- 커서·키셋 페이지네이션은 큰 목록을 안정적으로 넘기는 데 강하므로 정렬 키 설계와 화면 목적을 함께 맞춰 써야 함
