# 📖 【암기용】 개념 완전 이해

## 한눈에
- **개요**: 파일 시스템 저널링은 메타데이터(또는 데이터) 변경 사항을 메인 디스크에 반영하기 전 별도의 **저널(로그) 영역에 먼저 기록(WAL)**하여, 시스템 크래시 시 **전체 디스크 검사 없이 저널 재현만으로 복구**하는 무결성 보장 기법임.
- **왜 필요한가**: 비저널링 파일 시스템(ext2·FAT)은 파일 쓰기 중 정전 시 메타데이터와 데이터 간 불일치가 발생해, 재부팅 시 수십 분~수 시간의 전체 디스크 검사(fsck)가 필요했음. 서버 가용성에 치명적인 이 문제를 해결함.
- **핵심 직관**: 회계사가 원장(메인 FS)에 펜으로 적기 전에 포스트잇(저널)에 먼저 연필로 메모해두어, 중간에 정전이 나도 포스트잇만 보고 작업을 복구하는 원리임.

## 핵심 용어 정리 (내부에 등장하는 것들)

| 용어/표기 | 의미 | 비유·예 |
|:---|:---|:---|
| WAL (상위 키워드) | Write-Ahead Logging — 변경을 메인 데이터에 반영하기 전 로그에 먼저 기록하는 원칙 | 영수증 먼저 쓰고 장부 기입 |
| 저널 (Journal) | 디스크 내 별도 할당된 로그 기록 영역(링 버퍼 구조) | 회계 임시 메모장 |
| 트랜잭션 | 파일 시스템의 원자적(Atomic) 변경 단위 — 저널에 묶여 기록됨 | 1건의 이체 거래 |
| 커밋 (Commit) | 저널에 트랜잭션 기록이 완료됐음을 표시하는 마크 | 이체 완료 도장 |
| 체크포인트 (Checkpoint) | 커밋된 저널 내용을 메인 파일 시스템(Inode·데이터 블록)에 실제 반영하는 단계 | 메모를 정식 장부에 확정 기입 |
| Redo | 크래시 후 재부팅 시, 커밋 완료된 트랜잭션을 메인 FS에 다시 반영하는 복구 동작 | 메모를 보고 장부 누락분 재기입 |
| Writeback 모드 | 메타데이터만 저널, 데이터 기록 순서 무보장(최고 속도·최저 무결성) | 목차만 메모, 본문 순서 무관 |
| Ordered 모드 | 메타데이터만 저널, 반드시 데이터부터 먼저 기록(ext4 기본값, 균형) | 본문 먼저 쓰고 목차 메모 |
| Journal 모드 | 메타데이터+데이터 모두 저널(최저 속도·최고 무결성) | 본문과 목차 모두 메모 |

## 깊이 이해
- **배경·문제의식**: 022에서 다룬 파일 시스템의 쓰기 과정에서, 메타데이터 갱신(Inode 크기 변경, 블록 포인터 추가)과 데이터 쓰기는 별도의 디스크 위치에 수행됨. 두 쓰기 사이에 정전이 발생하면 메타데이터는 새 크기를 가리키지만 실제 데이터 블록은 비어 있거나(가비지 데이터), 데이터는 기록됐지만 메타데이터가 갱신되지 않아 고아 블록(Orphan)이 발생함. 이 불일치를 **원자적 트랜잭션**으로 묶어 해결하는 것이 저널링임.
- **작동 원리**: DB의 WAL(Write-Ahead Logging) 원리를 파일 시스템에 이식함.
  1. **저널 쓰기**: "A파일 Inode 크기를 100으로 변경" 등 변경 내역을 저널 영역에 순차 기록
  2. **커밋**: 저널 기록 완료 시 트랜잭션 커밋 마크를 기록
  3. **체크포인트**: 백그라운드 스레드가 커밋된 내용을 메인 FS의 Inode·데이터 블록에 실제 반영
  4. **Redo 복구**: 체크포인트 수행 중 정전 시, 재부팅 시 저널의 커밋 완료 트랜잭션만 스캔해 메인 FS에 재반영 — 전체 fsck 불필요
- **비유**: DB의 Redo/Undo 로그와 동일한 역할을 파일 시스템이 수행함. 차이점은 파일 시스템 저널링은 대부분 Redo만 수행하고 Undo는 하지 않음(커밋 안 된 트랜잭션은 무시).
- **구체 예시**: ext3/ext4(Linux, Ordered 기본), NTFS(Windows), XFS(대용량 서버), JFS(IBM). ext4의 저널 크기는 기본 128MB이며, 5초 간격으로 체크포인트를 수행함.
- **흔한 오해·주의점**: (1) 저널링은 데이터 손실을 "완전히" 방지하지 않음 — Ordered 모드에서도 커밋 전 데이터는 손실 가능함. (2) DBMS가 자체 Redo 로그를 관리하는 경우, 파일 시스템 저널링이 이중 WAL로 쓰기 증폭(Write Amplification)을 유발하므로 Writeback 모드로 하향 튜닝이 필요함. (3) CoW 파일 시스템(APFS·ZFS·Btrfs)은 저널링 없이도 원자적 업데이트를 보장함(022 참조).

## 연결 개념
- (022 파일 시스템) 저널링이 적용되는 파일 시스템의 전체 구조
- (095 트랜잭션 ACID) DB의 WAL과 동일 원리, ACID 중 Atomicity·Durability를 파일 시스템에 구현
- CoW 파일 시스템(APFS·ZFS) — 저널링의 Write Amplification을 근본적으로 제거하는 대안

# 📝 【답안용】 시험 답안 템플릿

## 핵심 인사이트 (3줄 요약)

> 1. **본질**: DB의 WAL(Write-Ahead Logging)을 파일 시스템에 이식해, 메타데이터 변경을 트랜잭션 단위로 저널에 선기록하는 무결성 보장 기법임.
> 2. **가치**: 크래시 시 전체 디스크 검사(fsck)를 생략하고 저널 재현(Redo)만으로 수 초 내 복구를 실현해 서버 가용성을 극대화함.
> 3. **판단 포인트**: 저널링 범위(메타데이터 vs 전체 데이터)에 따라 성능과 무결성의 트레이드오프가 발생하므로, 워크로드에 맞춰 Writeback/Ordered/Journal 모드를 선택해야 함.

## 출제 의도 및 답안 포인트

| 출제 의도 | 반드시 짚을 핵심 | 감점 회피 포인트 |
|:---|:---|:---|
| 비정상 종료 시 파일 시스템 복구 원리 이해 | WAL, 커밋·체크포인트·Redo 동작, 3가지 모드 비교 | "로그를 남긴다"는 추상 서술, DB WAL과의 연계 누락 |
| 저널링 모드별 성능·무결성 트레이드오프 | Writeback(속도)/Ordered(균형)/Journal(무결성) 대조 | DBMS와의 이중 WAL 리스크 누락 |

> 요약: WAL 원칙에 기반한 트랜잭션 단위 저널링의 동작 과정(저널 쓰기->커밋->체크포인트->Redo)을 모드별로 비교해야 함.

---

## Ⅰ. 개요 및 필요성

- 개요: 파일 시스템 변경을 메인 FS에 반영하기 전 저널에 선기록(WAL)하는 트랜잭션 기반 무결성 보장 기법임
- 배경: 비저널링 FS(ext2·FAT)는 정전 시 메타데이터 불일치로 fsck에 수 시간 소요, 서버 가용성 치명적 저하
- 필요성: 엔터프라이즈 서버에서 크래시 복구 시간(RTO)을 분/초 단위로 단축하고 데이터 무결성을 보장하기 위해 필수임

---

## Ⅱ. 구조 및 구성요소

```text
OS 버퍼 캐시 -> 1. 저널 쓰기(순차) -> 저널(Log) 영역 (링 버퍼)
                 |                        |
                 |                    2. Redo 복구 (크래시 시)
                 |
                 +-> 3. 체크포인트(비동기) -> 메인 FS (Inode / 데이터 블록)
```

| 구성요소 | 역할 | 비고 |
|:---|:---|:---|
| 저널 영역 | 변경 트랜잭션을 순차 기록하는 링 버퍼 | ext4 기본 128MB, 오래된 로그는 덮어씀 |
| 체크포인트 스레드 | 커밋된 저널 내용을 메인 FS에 비동기 반영 | ext4 기본 5초 간격 |
| 복구 데몬 | 재부팅 시 저널 스캔 후 커밋 완료 트랜잭션 Redo 실행 | fsck 대체, RTO 수 초 |

> 요약: 저널 영역에 트랜잭션 단위로 선기록하고, 체크포인트 스레드가 메인 FS에 비동기 반영하며, 크래시 시 Redo로 복구함.

---

## Ⅲ. 동작원리 및 흐름도

```text
쓰기 요청 -> 버퍼 캐시 적재 -> 트랜잭션 저널 기록(순차 쓰기)
  -> 커밋 마크 기록 -> 체크포인트(메인 FS 반영, 랜덤 쓰기)
    [크래시 발생] -> 재부팅 -> 저널 스캔 -> 커밋 완료 트랜잭션 Redo -> 복구 완료
```

1. 저널 기록: 버퍼 캐시의 변경 내역(메타데이터 또는 데이터)을 저널 영역에 순차 쓰기(Sequential Write)로 기록함
2. 트랜잭션 커밋: 저널 기록 완료 시 커밋 마크를 기록해 논리적 쓰기를 완료 처리함
3. 체크포인트 반영: 백그라운드 스레드가 저널 내용을 메인 FS의 Inode·데이터 블록에 랜덤 쓰기로 반영함
4. 크래시 복구(Redo): 체크포인트 중 정전 시, 재부팅 시 저널의 커밋 완료 트랜잭션만 메인 FS에 재반영(Redo)함

> 요약: [저널 쓰기 -> 커밋 -> 체크포인트]로 분리해, 어느 시점에 크래시가 나도 저널 Redo만으로 일관성을 복구함.

---

## Ⅳ. 특징

- 복구 시간 단축: 전체 fsck 대신 저널 영역(128MB)만 스캔하므로 디스크 용량과 무관하게 복구 시간이 수 초로 일정함
- 원자성 보장: 메타데이터 변경이 부분 반영되는 상태를 방지해 파일 시스템 구조적 일관성을 유지함
- 순차 쓰기 최적화: 저널은 순차 기록이므로 HDD의 헤드 이동 비용을 최소화함
- Write Amplification(단점): 동일 데이터를 저널 1회 + 메인 FS 1회 총 2회 기록해야 하므로 쓰기 처리량이 감소함(Journal 모드에서 약 50%)

## Ⅴ. 심화 비교 및 적용 판단

| 구분 | Writeback | Ordered (기본) | Journal | 선택 기준 |
|:---|:---|:---|:---|:---|
| 저널 대상 | 메타데이터만 | 메타데이터만 | 메타데이터 + 데이터 | 무결성 요구 수준 |
| 데이터 기록 순서 | 무보장 | 데이터 우선 -> 메타 저널 | 트랜잭션 단위 전체 | 가비지 데이터 방지 |
| 성능 | 최고 | 중간 | 최저(2x Write) | I/O 부하 허용 범위 |
| 무결성 | 메타만 보장 | 가비지 데이터 방지 | 전체 보장 | 데이터 손실 허용도 |

> 요약: 일반 서버는 성능·무결성 균형의 Ordered, DBMS 서버는 자체 WAL과 중복 방지를 위해 Writeback, 금융·의료는 Journal 모드를 적용함.

**리스크·대응:**
- DBMS 이중 WAL: DBMS Redo 로그 + FS 저널 이중 쓰기로 쓰기 증폭 -> FS를 Writeback 모드로 하향 또는 Direct I/O 적용 (지표: 쓰기 IOPS 감소율)
- 저널 영역 포화: 체크포인트 지연 시 저널이 링 버퍼 한계에 도달해 쓰기 차단 -> 저널 크기 조정(`-J size=`), 체크포인트 주기 단축 (지표: journal full 이벤트 빈도)

**도입 후 점검 지표:**
- 성능: 쓰기 대기 시간(Latency) — iostat await, 목표 10ms 이하
- 운영: 강제 재부팅 후 마운트 소요 시간 — 저널 리플레이 속도, 목표 10초 이내

---

## Ⅵ. 실무 적용 및 결론

**적용 방안 3개:**
1. DBMS 서버 튜닝: MySQL·PostgreSQL이 자체 WAL을 관리하므로 ext4를 Writeback 모드로 설정해 이중 저널링 오버헤드를 제거함
2. 저널 영역 분리: 로그 서버·백업 서버에서 저널을 고속 NVMe SSD에 별도 마운트(`-J device=`)해 순차 쓰기 성능을 극대화하고 메인 디스크 부하를 분산함
3. CoW 전환 검토: 저널링의 Write Amplification이 SSD 수명에 부담이 되는 환경에서 Btrfs·ZFS로 마이그레이션해 CoW 기반 원자적 업데이트 + 스냅샷을 동시 확보함

**결론:**
- 기술사 판단: 저널링은 I/O 성능을 희생해 가용성을 확보하는 설계이므로, 상위 앱(DBMS)의 자체 WAL과 중복되지 않도록 모드를 튜닝하는 것이 필수임
- 향후 방향: In-place 업데이트 기반 저널링에서 CoW 기반 파일 시스템으로 스토리지 패러다임이 전환되며, CXL·Persistent Memory 환경에서는 저널 자체가 불필요해지는 방향으로 진화 중임
