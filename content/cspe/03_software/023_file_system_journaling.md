# 📖 【암기용】 개념 완전 이해

## 한눈에
- **개요**: 파일 시스템의 변경 사항을 메인 디스크에 반영하기 전에 로그(Journal) 영역에 먼저 기록하여 시스템 크래시 시 데이터 무결성을 보장하는 기술이다.
- **왜 필요한가**: 작업 도중 정전이나 커널 패닉이 발생하면 파일의 메타데이터와 실제 데이터 간의 불일치가 생겨 전체 파일 시스템이 망가지는 것을 막기 위해 필요하다.
- **핵심 직관**: 회계사가 원장에 금액을 펜으로 적기 전에, 포스트잇(저널)에 먼저 연필로 메모해두어 중간에 정전이 나도 포스트잇만 보고 작업을 복구하는 원리다.

## 핵심 용어 정리

| 용어/표기 | 의미 | 비유·예 |
|:---|:---|:---|
| 저널 (Journal) | 디스크 내 별도로 할당된 로그 기록 영역 | 회계 장부 임시 메모장 |
| 체크포인트 (Checkpoint) | 저널에 기록된 내용이 메인 파일 시스템에 안전하게 덮어써져 완료된 상태 | 임시 메모를 정식 장부에 볼펜으로 확정 기입 |
| 메타데이터 저널링 | 파일 내용(데이터)은 빼고, 이름·크기 등 속성(메타데이터)만 저널에 기록하는 방식 | 책 제목과 위치만 메모 (내용 메모 생략) |

## 깊이 이해
- **배경·문제의식**: 옛날 ext2나 FAT 시스템은 파일 쓰기 중 정전이 되면 파일이 깨지거나 고아 파일(Orphan File)이 생겼다. 재부팅 시 수십 분~수 시간 동안 전체 디스크를 검사하는 `fsck`를 돌려야 했다. 이는 서버 가용성에 치명적이었다.
- **작동 원리**: 데이터베이스의 트랜잭션 복구 원리(Write-Ahead Logging)를 파일 시스템에 가져왔다.
  1. (저널 쓰기) "A파일 크기를 100으로 바꾼다"는 내역을 저널 영역에 쓴다.
  2. (커밋) 저널 기록이 완료되었음을 표시한다.
  3. (체크포인트) 실제 메타데이터 위치(Inode)를 100으로 수정한다.
  만약 3번 수행 중 정전이 나면, 재부팅 시 전체 디스크를 뒤질 필요 없이 저널 영역만 읽어 3번을 다시 실행(Redo)하면 된다.
- **모드 (ext3/ext4 기준)**:
  - `Writeback`: 메타데이터만 저널링, 데이터 기록 순서 무작위 (가장 빠름, 무결성 낮음)
  - `Ordered`: 메타데이터만 저널링, 반드시 데이터부터 먼저 쓰고 메타데이터 갱신 (성능과 무결성 균형, 디폴트)
  - `Journal`: 데이터+메타데이터 모두 저널링 (가장 느림, 최고 무결성)
- **비유**: 데이터베이스의 Undo/Redo 로그와 정확히 같은 역할을 파일 시스템이 수행하는 것.
- **구체 예시**: ext3/ext4(Linux), NTFS(Windows), XFS, JFS.

## 연결 개념
- 트랜잭션 ACID, WAL(Write-Ahead Logging), 복구 알고리즘(Redo/Undo)

# 📝 【답안용】 시험 답안 템플릿

## 핵심 인사이트 (3줄 요약)

> 1. **본질**: 데이터베이스의 WAL(Write-Ahead Logging) 메커니즘을 운영체제 파일 시스템 영역에 이식한 무결성 보장 기술.
> 2. **가치**: 시스템 크래시 시 전체 디스크 스캔(FSCK)을 생략하고 저널 재현만으로 초고속 복구(Fast Recovery)를 실현하여 가용성을 극대화.
> 3. **판단 포인트**: 저널링 범위(메타데이터 vs 전체 데이터)에 따라 성능과 무결성의 트레이드오프가 발생하므로, 워크로드에 맞춰 모드(Ordered/Journal)를 선택해야 한다.

## 출제 의도 및 답안 포인트

| 출제 의도 | 반드시 짚을 핵심 | 감점 회피 포인트 |
|:---|:---|:---|
| 비정상 종료 시 파일 시스템 복구 원리 이해 | WAL, 체크포인트, Redo/Undo 동작, 3가지 저널링 모드 비교 | 단순 "로그를 남긴다"는 추상적 표현 지양, 트랜잭션 원리와 매핑 |

> 요약: 메인 데이터 영역 반영 전 트랜잭션 단위로 저널에 선기록하여 데이터 일관성을 보장하는 동작 원리를 상세히 기술한다.

---

## Ⅰ. 개요 및 필요성

- 개요: 파일이나 디렉터리의 변경 사항을 파일 시스템 구조에 직접 반영하기 전, 별도의 로그 영역(저널)에 선기록(WAL)하는 복구 기법.
- 배경: 비저널링 파일 시스템(ext2, FAT)은 정전 시 파일 시스템 일관성이 붕괴되며, 이를 복구하기 위한 fsck 수행 시 수 시간의 서비스 중단 발생.
- 필요성: 엔터프라이즈 서버 환경에서 예기치 않은 시스템 장애 발생 시, 데이터 손실 방지(무결성) 및 복구 시간(RTO)을 분/초 단위로 단축하기 위해 필수적임.

---

## Ⅱ. 구조 및 구성요소

```text
[운영체제 버퍼 캐시] -> 1. 저널 쓰기 -> [저널 (Log) 영역]
                        |                   | 2. Redo 복구 (장애 시)
                        + 3. 체크포인트 -> [메인 파일 시스템 (Inode / 데이터 블록)]
```

| 구성요소 | 역할 | 특이사항 |
|:---|:---|:---|
| 저널 (Journal) 영역 | 파일 시스템 변경 트랜잭션을 순차적으로 기록하는 링 버퍼(Ring Buffer) | 크기가 제한되며 오래된 로그는 덮어씀 |
| 체크포인트 스레드 | 저널에 커밋된 변경 내역을 메인 디스크 영역에 비동기적으로 덮어쓰기 수행 | I/O 병목 방지를 위한 백그라운드 작업 |
| 복구 데몬 (Recovery) | 시스템 재부팅 시 저널을 스캔하여 커밋 완료된 트랜잭션을 재실행(Redo) | FSCK 대체로 RTO 획기적 단축 |

> 요약: 저널 영역을 통해 변경 사항을 원자적(Atomic) 트랜잭션으로 묶어 기록하며, 체크포인트 스레드가 실제 파일 시스템과 동기화한다.

---

## Ⅲ. 동작원리 및 흐름도 (정상 쓰기 및 장애 복구)

```text
쓰기 요청 -> 버퍼 캐시 적재 -> 트랜잭션 저널 기록 -> 커밋 -> 메인 FS 반영 (체크포인트)
                                  [장애 발생] -> 재부팅 -> 커밋 여부 확인 -> Redo 수행
```

- 1단계 [저널 기록]: 버퍼 메모리의 변경(메타데이터/데이터) 내역을 디스크의 저널 영역에 순차 쓰기(Sequential Write)로 기록.
- 2단계 [트랜잭션 커밋]: 저널 기록이 온전히 완료되면 트랜잭션 커밋 마크를 기록하여 논리적 쓰기 완료 처리.
- 3단계 [체크포인트 반영]: 백그라운드 스레드가 저널 내용을 메인 파일 시스템(실제 Inode 및 데이터 블록)에 랜덤 쓰기(Random Write)로 반영.
- 4단계 [장애 복구 (Redo)]: 3단계 수행 중 정전 발생 시, 재부팅 과정에서 저널 영역만 확인하여 커밋 마크가 있는 트랜잭션을 메인 영역에 다시 반영(Redo).

> 요약: 쓰기 작업을 [저널 쓰기 → 커밋 → 메인 반영] 3단계로 분리하여, 어느 시점에 장애가 나더라도 이전 상태 롤백이나 커밋 완료 분의 재실행이 보장된다.

---

## Ⅳ. 특징

- 순차 접근을 통한 오버헤드 최소화: 저널 영역은 순차적으로 기록되므로, 잦은 랜덤 I/O로 인한 디스크 헤드 이동 비용을 최소화함.
- 복구 시간(RTO) 획기적 단축: 전체 디스크를 스캔하는 무결성 검사(FSCK) 대신, 크기가 작은 저널 영역만 스캔하므로 복구 시간이 디스크 용량과 무관하게 일정함.
- 원자성(Atomicity) 보장: 메타데이터 변경(파일 크기 증가, 블록 할당 등)이 부분적으로만 반영되는 상태를 방지하여 구조적 일관성을 유지함.
- Write Amplification 발생 (단점): 동일한 데이터를 저널에 한 번, 메인 FS에 한 번, 총 두 번 기록해야 하므로 쓰기 성능 저하(오버헤드)가 발생함.

> 요약: 쓰기 오버헤드가 발생하지만, 트랜잭션 기반 복구를 통해 대용량 스토리지의 가용성과 일관성을 담보하는 핵심 아키텍처다.

---

## Ⅴ. 심화 비교 및 적용 판단

| 비교 축 | Writeback 모드 | Ordered 모드 (디폴트) | Journal 모드 | 선택 기준 |
|:---|:---|:---|:---|:---|
| 저널링 대상 | 메타데이터만 | 메타데이터만 | 메타데이터 + 실제 데이터 | 성능 vs 무결성 중요도 |
| 기록 순서 | 무작위 (데이터/메타) | 데이터 쓰기 후 메타 저널링 | 트랜잭션 단위로 전체 저널링 | 가비지 데이터 방지 여부 |
| 성능 / 무결성 | 최고 성능 / 최저 무결성 | 균형 (충돌 시 쓰레기 데이터 없음) | 최저 성능 / 최고 무결성 | 일반 서버는 Ordered 권장 |

> 요약: 실제 데이터까지 두 번 쓰는 Journal 모드는 심각한 성능 저하를 유발하므로, 순서를 보장하는 Ordered 모드가 실무에서 표준으로 쓰인다.

**도입 후 점검 지표:**
- 성능/효율: 파일 시스템 쓰기 대기 시간(Latency) (목표 10ms 이하) — iostat 및 블록 I/O 지표 측정
- 품질/운영: 강제 재부팅 시 마운트 소요 시간 (목표 10초 이내) — 저널 리플레이(Replay) 속도 측정

## Ⅵ. 실무 적용 및 결론

**적용 방안 3개:**
1. 데이터베이스 서버 최적화: MySQL 등 DBMS 자체가 트랜잭션 로그(Redo log)를 관리하므로, 파일 시스템 차원의 이중 저널링 오버헤드를 막기 위해 Writeback 모드로 하향 튜닝.
2. 대규모 정적 파일 서버: 로그 파일이나 백업 이미지만을 저장하는 스토리지의 경우, 메타데이터 손상 방지를 위해 Ordered 모드를 유지하되 저널 영역을 고속 NVMe SSD로 분리 마운트하여 성능 개선.
3. CoW 파일 시스템 도입: 저널링의 Write Amplification 한계를 극복하기 위해, Btrfs나 ZFS 같은 Copy-on-Write 기반 최신 파일 시스템으로 마이그레이션하여 성능과 스냅샷 기능 동시 확보.

**결론 (2줄):**
- 기술사 판단: 저널링은 I/O 성능을 다소 희생하여 가용성을 확보하는 설계이므로, 상위 애플리케이션(DBMS 등)의 무결성 보장 메커니즘과 중복되지 않도록 모드(Mode) 튜닝이 필수적임.
- 향후 방향: 전통적인 In-place 업데이트 기반 저널링 파일 시스템에서, 데이터 덮어쓰기 자체가 없는 CoW(Copy-on-Write) 기반 시스템으로 스토리지 패러다임이 전환될 것임.
