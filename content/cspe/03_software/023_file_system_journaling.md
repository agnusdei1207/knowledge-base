# 📖 【암기용】 개념 완전 이해

> 목적: 이 개념을 처음 보는 사람도 완벽히 이해하게 만든다. 시험 답안 양식이 아니라, 이해를 위한 친절한 설명이다.

## 한눈에
- **개요**: **저널링(Journaling)**은 파일 시스템이 정전이나 시스템 크래시(블루스크린)로 인해 장부(메타데이터)가 꼬이는 참사를 막기 위해, 진짜 장부에 쓰기 전에 **임시 수첩(Journal Log)**에 먼저 작업 내역을 꼼꼼히 적어두는 복구 기술이다.
- **왜 필요한가**: 컴퓨터에 파일을 저장하는 건 한순간에 짠! 하고 끝나는 게 아니다. 1. 빈 공간 찾기 2. 데이터 쓰기 3. 장부 갱신하기의 과정을 거치는데, 만약 2번까지 하고 3번 찰나에 정전이 나면 컴퓨터는 그 파일이 있는지 없는지 평생 모르는 좀비(고아) 상태가 되어 디스크가 망가진다.
- **핵심 직관**: 
  - 영수증(로그)을 먼저 쓰고 물건(데이터)을 내어준다.
  - 정전이 나서 깨어났을 때, 디스크 1TB를 전부 뒤져서 빈칸 찾기 퀴즈(fsck)를 풀려면 하루 종일 걸리지만, 저널링이 있으면 임시 수첩(영수증)만 쓱 보고 "아, 이거 쓰다 말았네. 다시 쓰거나 롤백(취소)하자"며 1초 만에 복구한다.

## 깊이 이해
- **배경·문제의식**: 옛날 FAT나 ext2 시절에는 정전이 나면 윈도우 부팅할 때 파란 화면에서 `chkdsk`(리스크 검사)가 미친 듯이 숫자를 올리며 하드디스크 전체를 몇 시간 동안 스캔했다. 디스크가 커질수록 이 복구 시간이 감당이 안 되어, DB 트랜잭션의 로그 복구 개념을 운영체제 커널에 훔쳐 온 것이 저널링이다.
- **작동 원리 (Write-Ahead Logging)**:
  1. **저널 쓰기**: "나 지금부터 파일 A 지울 거임"이라고 로그 영역(수첩)에 적는다.
  2. **커밋(Commit)**: 수첩에 다 적었다고 도장을 찍는다.
  3. **체크포인트(Checkpoint)**: 진짜 파일 시스템 장부(MFT, Inode)에 파일 A를 삭제 반영한다.
  4. 만약 3번 도중 뻗었다? 부팅 시 수첩만 펴보고 커밋 도장이 있으면 3번을 마저 실행(Redo)하고, 도장이 없으면 수첩 내용을 찢어버린다(Undo).
- **모드(Mode) 비유**: 
  - **데이터 저널링**: 내가 산 물건(진짜 데이터)과 영수증(메타데이터)을 수첩에 다 적음. (복구율 100%, 근데 물건을 수첩에 한 번, 창고에 한 번 총 2번 날라야 해서 속도 최악)
  - **메타데이터 저널링(Ordered)**: 영수증(이름표)만 수첩에 적음. 물건은 창고에 먼저 몰래 던져놓고 나중에 영수증을 씀. (속도 빠름, 대부분의 OS 기본값)
- **구체 예시**: 윈도우의 NTFS, 리눅스의 ext3, ext4, 애플의 HFS+ 등 오늘날 우리가 쓰는 99%의 OS는 이 저널링 파일 시스템을 기본으로 탑재하고 있다. 그래서 강제 종료(코드를 뽑아도)를 해도 다음 부팅이 10초 만에 끝나는 것이다.
- **흔한 오해·주의점**: 저널링은 내 '문서 내용(Data)'을 100% 살려주는 마법이 아니다. 장부가 꼬여서 하드디스크 전체가 먹통이 되는 **'파일 시스템 무결성(Integrity)'**을 살려주는 것이다. 워드 작성 중 날아간 내용은 저널링이 아니라 앱 자동 저장이 살리는 거다.

## 연결 개념
- **FSCK / CHKDSK**: 저널링이 없던 시절, 디스크 블록 전체를 순회하며 장부(Inode)와 실제 블록의 짝이 맞는지 전수 검사하던 끔찍한 복구 유틸리티.
- **WAL (Write-Ahead Logging)**: 오라클이나 MySQL 같은 관계형 데이터베이스가 데이터 날아가는 걸 막기 위해 쓰는 핵심 원리. 저널링 파일 시스템은 사실상 커널에 박혀있는 미니 DB다.

# 📝 【답안용】 시험 답안 템플릿

> 목적: 시험장에서 25분에 그대로 쓰는 답안 양식. 작성방식(추상표현 금지·수치·도식·문제유형 전환)을 엄격히 지킨다.
> 핵심: 이 시험은 정보를 많이 나열하는 시험이 아니라, 문제 신호어에서 출제자 의도를 읽고 핵심 논점을 선별해 쓰는 시험이다.

## 핵심 인사이트 (3줄 요약)

> 1. **본질**: 시스템 크래시나 전원 차단 시 파일 시스템 메타데이터의 논리적 훼손(Inconsistency)을 방지하기 위해, 트랜잭션의 WAL(Write-Ahead Logging) 기법을 커널 I/O 계층에 이식한 복구 아키텍처다.
> 2. **가치**: 부팅 시 디스크 전체를 블록 단위로 전수 검사하는 FSCK(File System Check)의 극심한 오버헤드를 원천 소거하고, 저널 로그 영역만 Replay하여 초단위(Second) 쾌속 복구를 보장한다.
> 3. **판단 포인트**: 데이터까지 이중 기록하여 I/O 병목을 부르는 'Data 모드'와 메타데이터만 래핑하는 'Ordered 모드'의 트레이드오프를 대조하고, 현대 SSD 환경에서 저널링이 낳는 마모도(Wear-out) 한계를 짚어야 한다.

## 출제 의도 및 답안 포인트

| 출제 의도 | 반드시 짚을 핵심 | 감점 회피 포인트 |
|:---|:---|:---|
| 시스템 복구 매커니즘의 아키텍처적 이해 | 저널 로그 기록 -> Commit -> 원본 갱신(Checkpoint) | 저널링이 사용자의 '파일 데이터(내용)' 백업/복구 기술이라고 착각하는 치명적 오개념 (메타 무결성 방어임) |
| 저널링 모드별 R/W 오버헤드 딜레마 규명 | Data Journaling(속도 저하) vs Ordered Journaling(타협) | 두 모드의 데이터 기록 순서 차이를 설명하지 못하고 뭉뚱그려 서술 |

> 요약: 저널링은 디스크가 뻗었을 때 1TB 전체를 뒤지는 바보짓(fsck)을 멈추고, 10MB짜리 임시 수첩(Log)만 슬쩍 보고 사태를 1초 만에 수습하는 커널의 마술이다.

## Ⅰ. 개요 및 필요성

- 정의: 파일 시스템의 변경 사항(트랜잭션)을 실제 디스크 블록에 반영하기 전에, 별도의 순차적 원형 버퍼 로그 영역(Journal)에 선(先) 기록하여 무결성을 방어하는 기법
- 배경: 파일 생성/삭제 시 Inode 할당, 비트맵 갱신, 데이터 블록 쓰기가 원자적(Atomic)으로 이루어지지 않아, 중간 크래시 발생 시 고아 블록(Orphan) 생성 및 구조적 파괴 유발
- 필요성: 시스템 비정상 종료 후 재기동 시, 수 시간에 달하는 `fsck` 전수 검사를 생략하고 로그 리플레이(Replay)만으로 일관성(Consistency)을 즉시 복원하기 위함

## Ⅱ. 저널링 트랜잭션 처리 메커니즘 및 복구 도식

```text
[ 정상 기록 흐름 (Write-Ahead Logging) ]
1. Journal Write: "블록 5에 A 저장, Inode 10 갱신" 내역을 저널 디스크 영역에 순차 쓰기
2. Journal Commit: 저널 기록 완료 트랜잭션 도장(Commit Record) 쾅!
3. Checkpoint: 실제 파일 시스템(ext4 본진)의 블록 5와 Inode 10에 덮어쓰기 (느린 랜덤 I/O)
4. Free: 저널 영역에서 해당 로그 삭제

[ 장애 발생 시 복구(Recovery) 로직 ]
- 2번 직전 뻗음 -> 수첩에 도장 없음 -> 미완성. 무시하고 폐기 (Undo)
- 3번 도중 뻗음 -> 수첩에 도장 있음 -> 수첩 보고 진짜 장부에 다시 밀어 넣음 (Redo) -> 복구 1초 컷!
```

| 복구 처리 기법 | 커널 스토리지 액션 | 보장하는 무결성 상태 |
|:---|:---|:---|
| **Redo (재실행)** | Commit 로그가 존재하나 Checkpoint 반영이 누락된 트랜잭션 재수행 | 데이터 및 메타데이터 갱신 완료 보장 (Forward Recovery) |
| **Undo (롤백)** | Commit 로그가 없어 불완전한 상태로 저널에 남은 쓰레기 찌꺼기 파기 | 파일 시스템 오염 원천 차단 (Backward Recovery) |

> 요약: 저널링의 핵심은 "영수증(저널)에 도장(Commit)이 찍혀 있는가?"이다. 도장이 없으면 가차 없이 버리고, 있으면 든든하게 복구한다.

## Ⅲ. 성능 vs 안정성의 딜레마: 저널링 3대 모드 비교 (ext4 기준)

저널링은 태생적으로 2번(저널 1번 + 본진 1번) 기록해야 하므로, 성능 저하(Write Penalty)가 필연적이다. 

| 저널링 모드 | 기록 아키텍처 및 순서 규칙 | 트레이드오프 (성능 및 안전성) |
|:---|:---|:---|
| **Data (데이터 모드)** | 파일 데이터(내용)와 메타데이터(이름표) **모두** 저널에 통째로 선 기록 | 완벽한 데이터 복구율 보장. 단, 1GB 영상을 쓰면 실제 디스크에 2GB를 쓰는 극악의 I/O 패널티 발생 |
| **Ordered (기본값)** | **데이터는 진짜 장부에 먼저 슬쩍 쓰고**, 메타데이터만 저널에 기록 (단, 데이터 쓰기가 완료되어야 저널 커밋 허용) | 속도와 무결성의 완벽한 타협. 대부분의 리눅스 배포판 기본 설정 (최악의 경우 휴지통 데이터 노출 방어) |
| **Writeback (비동기)** | 데이터와 메타데이터 기록 순서를 아예 보장하지 않고 커널 맘대로 비동기 처리 | 속도는 제일 빠름. 정전 시 옛날 데이터가 새 파일 이름표에 엮여 나오는 치명적 꼬임(오염) 발생 가능성 존재 |

> 요약: 리눅스 토발즈도 1GB짜리를 2번 옮기기는(Data 모드) 귀찮았다. 그래서 데이터 자체는 몰래 먼저 본진에 던져놓고(순서 강제), 영수증(메타데이터)만 저널에 적는 타협안(Ordered)이 세상을 지배했다.

## Ⅳ. 극복해야 할 시스템적 한계와 차세대 FS 패러다임

HDD 시절 바늘(헤더)을 움직이는 랜덤 I/O를 순차 로그 쓰기로 감추려던 저널링의 영광은 SSD 시대에 독이 되었다.

| 리스크 요인 | 발생 시나리오 | 차세대 아키텍처 대응 방안 (CoW) |
|:---|:---|:---|
| **SSD 마모 평준화 파괴** | 플래시 메모리(SSD)는 지우기/쓰기 횟수(P/E Cycle) 한계가 명확한데, 저널 영역만 미친 듯이 썼다 지웠다 반복하여 디스크 수명(Wear-out)을 갉아먹는 WAF(Write Amplification) 폭발 유발 | **저널링 폐기 및 Copy-on-Write (CoW)**: ZFS, Btrfs, APFS는 저널 수첩을 버렸다. 데이터를 수정할 때 덮어쓰지 않고 항상 '빈 블록'에 새 데이터를 쓴 뒤, 최상단 포인터만 원자적(Atomic)으로 틱 바꿔치기하여 복구율 100%와 수명 방어를 동시 달성 |
| DB 이중 로깅 오버헤드 | MySQL(InnoDB)은 자체 Redo 로그를 쓰는데, 밑바닥 ext4 커널도 저널 로그를 써서 1개의 쿼리가 디스크를 3~4번 타격하는 I/O 비효율 발생 | 커널 레벨 파일 시스템 튜닝 (ex. Direct I/O `O_DIRECT` 플래그 및 Journaling 비활성화)으로 데이터베이스 엔진의 독자적 WAL 무결성 신뢰 |

> 요약: SSD에게 저널링의 이중 쓰기는 생명을 단축시키는 저주다. 현대 파일 시스템 아키텍처는 "덮어쓰지 않으면 수첩에 적을 필요도 없다"는 위대한 철학(CoW)으로 완전히 궤도를 옮겼다.

## Ⅴ. 실무 적용 방안 및 결론

**적용 방안 3개:**
1. [Linux 마운트 성능 튜닝] DB 전용 볼륨을 마운트할 때 저널링으로 인한 이중 쓰기 지연을 타파하기 위해, ext4의 `/etc/fstab` 옵션에 `data=writeback`을 주어 메타데이터 갱신 비동기화를 허용하거나 아예 저널링을 끄는(`tune2fs -O ^has_journal`) 익스트림 튜닝 적용
2. [정전 대비 파일시스템 복구 스크립팅] 레거시 ext2 시스템 부팅 시 커널 패닉으로 쉘로 떨어질 경우, 당황하지 않고 수동 런레벨에서 `e2fsck -f /dev/sda1` 명령어를 통해 손상된 Inode 리스트를 검출하고 `/lost+found` 디렉토리로 고아(Orphan) 파일 강제 덤프 수행
3. [SSD 수명 방어를 위한 로그 구조 FS 탑재] 임베디드 디바이스나 IoT 블랙박스 개발 시, 빈번한 동영상 덮어쓰기로 인한 플래시 수명 단축 및 저널링 오버헤드를 막기 위해 낸드(NAND) 친화적인 로깅 전용 파일 시스템 F2FS(Flash-Friendly File System) 커널 컴파일 및 포맷 적용

**결론:**
- 기술사 판단: 파일 시스템 저널링은 DB 트랜잭션의 ACID 철학을 운영체제 스토리지 계층에 하방 전개한 엔지니어링의 위대한 크로스오버다. 성능(I/O 패널티)을 제물로 바쳐 시스템의 심장(메타데이터)을 사수하는 이 타협은 20년간 현대 IT 인프라의 가용성을 지탱해 왔다.
- 향후 방향: 하드웨어의 중심이 디스크(HDD)에서 플래시(SSD/NVMe)로 넘어가면서 저널링의 역할은 축소되고 있다. 앞으로는 쓰기 증폭(WAF)을 피하기 위해 ZFS의 CoW 방식이나, 스토리지 내부 펌웨어 컨트롤러가 파일 시스템 무결성을 하드웨어적으로 직접 관리하는 Computational Storage 기반으로 진화할 것이다.
