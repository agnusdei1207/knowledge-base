## Ⅰ. 개요
- **정의**: 컨테이너화된 워크로드의 배포·스케일링·자동복구를 관리하는 컨테이너 오케스트레이션 플랫폼
- **배경/필요성**: 컨테이너 수가 수백~수천 개로 증가하면 수동 관리가 불가하므로, 자동 스케줄링·복구·네트워킹을 통합 관리하는 플랫폼이 필요함
- **비유**: 항공 관제탑 — 수백 대 항공기(컨테이너)의 이착륙·경로를 자동 조율함

| 출제 의도 | 반드시 짚을 핵심 | 감점 회피 포인트 |
|:---|:---|:---|
| 오케스트레이션 필요성과 K8s 역할 | 선언적 관리, 자동 복구, 수평 확장 | Docker(065 참조) 자체와 혼동 금지 |

> 요약: 대규모 컨테이너의 배포·스케일링·자동복구를 선언적으로 관리하는 플랫폼임

## Ⅱ. 구성요소
```text
User --> API Server --> Scheduler --> Node
              |              |          |
              v              v          v
           etcd        Controller    Kubelet
                        Manager     + Runtime
```

| 구성요소 | 설명 | 비유 |
|:---|:---|:---|
| API Server | 모든 요청의 단일 진입점이자 인증·인가 처리 | 관제탑 교신 창구 |
| etcd | 클러스터 상태를 저장하는 분산 Key-Value 저장소 | 비행 기록부 |
| Scheduler | Pod를 적절한 Node에 배치하는 스케줄러 | 게이트 배정 담당 |
| Controller Manager | 선언 상태와 현재 상태의 차이를 조정하는 제어 루프 집합 | 정비 관리팀 |

> 요약: API Server-etcd-Scheduler-Controller로 선언 상태를 유지하는 제어 루프 구조임

## Ⅲ. 절차
```text
Declare YAML --> Submit to API --> Schedule Pod --> Reconcile State
```
- 1단계: 원하는 상태를 YAML 매니페스트로 선언함
- 2단계: `kubectl apply`로 API Server에 제출함
- 3단계: Scheduler가 자원 조건에 맞는 Node를 선택하여 Pod를 배치함
- 4단계: Controller가 지속적으로 현재 상태를 선언 상태에 수렴시킴

> 요약: 선언-제출-배치-수렴의 4단계 제어 루프로 클러스터를 관리함

## Ⅳ. 문제점
- 학습 복잡도: 100여 개 이상의 API 오브젝트와 개념 이해에 높은 진입 장벽이 있음
- etcd 장애 영향: etcd 클러스터 과반 손실 시 전체 컨트롤 플레인이 동작 불가함
- 네트워크 복잡성: Service·Ingress·NetworkPolicy 등 계층별 네트워크 설정이 복잡함

> 요약: 학습 곡선, etcd 가용성, 네트워크 복잡성이 주요 과제임

## Ⅴ. 개선방안
1. 단기: 관리형 K8s(EKS·AKS·GKE)를 사용하여 컨트롤 플레인 운영 부담을 줄임
2. 중기: etcd 백업·복원 자동화와 다중 AZ 배치로 가용성을 확보함
3. 장기: Service Mesh 도입으로 네트워크 정책을 애플리케이션 계층에서 추상화함

> 요약: 관리형 서비스, etcd 고가용성, Service Mesh로 개선함

## Ⅵ. 전망
- 발전 방향: K8s가 클라우드 OS로 자리잡으며 AI 워크로드·엣지 배포까지 확장됨
- 기술사적 판단: 아키텍처 이해(067 참조)와 핵심 오브젝트(068 참조) 숙지가 기술사 답안의 기본임
- 기술사 제언: 오케스트레이션 도입 시 조직의 운영 역량 수준에 맞는 관리 수준(자체 구축 vs 관리형)을 선택할 필요
