# 📖 【암기용】 개념 완전 이해

## 한눈에
- **개요**: **멱등성(Idempotency, 冪等性)**이란, 연산이나 작업을 한 번 수행하든 여러 번 반복해서 수행하든 최종 결과가 항상 같게 나오는 시스템의 성질이다.
- **왜 필요한가**: 모바일 앱에서 '결제' 버튼을 눌렀는데 네트워크 지연으로 로딩창이 멈춰서, 짜증 난 사용자가 결제 버튼을 세 번 더 눌렀다 치자. 이때 결제가 4번 중복 청구되면 안 된다. 네트워크 에러 시 무조건 '재시도(Retry)'를 해도 안전한 시스템을 만들기 위해 필요하다.
- **핵심 직관**: 곱하기 1이나, 절댓값 기호(|x|)와 같다. $5 \times 1 = 5$ 이고, 5에 1을 백 번 곱해도 여전히 5다. 스위치를 '켜기' 명령을 한 번 누르나 백 번 누르나 전등은 켜진 상태 그대로다(멱등함). 반면 '토글(딸깍)' 명령은 누를 때마다 상태가 바뀌므로 멱등하지 않다.

## 핵심 용어 정리

| 용어/표기 | 의미 | 비유·예 |
|:---|:---|:---|
| 멱등성 (Idempotency) | 1회 실행 = 다회 실행 (결과 불변) | 엘리베이터 '닫힘' 버튼 백 번 누르기 (닫힌 결과 동일) |
| 멱등 키 (Idempotency Key) | 동일한 요청임을 증명하는 고유 식별자 | 은행 송금 영수증 번호 (동일 번호면 중복 송금 안함) |
| Retry (재시도) | 네트워크 끊김 시 실패로 간주하고 다시 요청하는 로직 | 전화 끊기면 다시 전화 걸기 |
| 안전한 메서드 (Safe Method) | 실행해도 서버 상태를 전혀 바꾸지 않는(조회만 하는) 성질 | HTTP GET (게시글 백 번 조회해도 그대로) |

## 깊이 이해
- **배경·문제의식**: 분산 시스템(마이크로서비스 등)에서는 두 노드 간 통신에서 에러가 났을 때, "요청이 서버에 못 간 건지(Request Fail)" 아니면 "서버가 처리하고 응답을 보내주다 끊긴 건지(Response Fail)" 클라이언트는 구별할 수 없다. 해결책은 '다시 요청(Retry)'하는 수밖에 없는데, 중복 요청이 데이터 오염을 낳는다면 Retry를 쓸 수 없다.
- **작동 원리**:
  1. 클라이언트가 데이터를 요청할 때 **고유 식별자(Idempotency Key, 주로 UUID)**를 만들어 같이 보낸다.
  2. 서버는 이 Key를 받아 DB나 Redis에 저장(캐싱)하면서 요청을 처리한다.
  3. 클라이언트가 에러 때문에 같은 Key로 재요청하면, 서버는 캐시(DB)를 보고 "어? 이 Key는 이미 아까 처리해서 200 OK 내보냈어"라고 판단하여 실제 비즈니스 로직(예: 송금, DB Insert)을 생략하고 과거 성공 결과만 다시 반환한다.
- **비유**: 식당에서 "1번 테이블 삼겹살 2인분 추가요!"를 외쳤다. 시끄러워서 주방장이 못 들은 줄 알고 종업원이 3번 다시 외쳤다. 주방장이 똑똑(멱등성 설계)하다면, "아, 아까 그 1번 테이블 2인분 추가 주문 말하는 거구나" 하고 2인분만 내보낸다. 주방장이 바보(비멱등)라면 8인분을 줘서 돈을 다 내야 한다.
- **구체 예시**:
  - HTTP 메서드: `GET`, `PUT`(통째로 덮어쓰기), `DELETE`(없애버리기)는 멱등하다. `POST`(자원 새로 생성)는 누를 때마다 새 글이 생기므로 **비멱등**이다.
  - 결제 시스템: 사용자가 결제 버튼을 광클해도, 단말에서 생성한 `transaction_id`를 멱등 키로 삼아 단 한 번의 카드 승인만 일으킨다.
- **흔한 오해·주의점**: 멱등성은 응답 데이터까지 똑같다는 뜻이 아니다. `DELETE /user/1`을 처음 날리면 `200 OK`지만, 두 번째 날리면 이미 삭제되어 `404 Not Found`가 뜰 수 있다. 중요한 건 **서버의 상태 결과(유저 1은 지워져서 없다)**가 동일하게 유지된다는 것이다.

## 연결 개념
- 분산 트랜잭션 (Saga 등 에러 보상 시 멱등성 필수)
- 마이크로서비스 아키텍처 MSA (네트워크 단절 잦으므로 필수)
- 자동 재시도 (Circuit Breaker 및 Retry 패턴의 전제 조건)
- HTTP 메서드 멱등성 사양 (REST API 설계 원칙)

> 1. **본질**: 멱등성 설계는 연산을 단일 수행하든 다중 반복 수행하든 시스템의 최종 상태 결과가 항상 동일하게 유지되도록 보장하는 분산 시스템 아키텍처 원칙이다.
> 2. **가치**: 마이크로서비스 간의 통신에서 불가피하게 발생하는 네트워크 타임아웃 지연 시, 상태 오염(중복 결제 등) 걱정 없이 클라이언트가 안전하게 재시도(Retry)할 수 있게 해준다.
> 3. **판단 포인트**: HTTP 메서드(GET/PUT/DELETE) 레벨의 시맨틱 준수와 트랜잭션 단위의 고유 식별자(Idempotency Key) 캐싱 등 상태 관리 매커니즘을 핵심으로 적용해야 한다.

## Ⅰ. 개요 및 필요성

- 개요: 멱등성(Idempotency)은 동일한 작업을 여러 번 요청해도 첫 번째 요청과 똑같은 최종 서버 상태를 보장하는 속성을 뜻함
- 배경: 클라우드 분산 환경에서는 네트워크 단절, 패킷 로실(Loss) 등 통신 실패가 일상적이라 자동 재시도(Retry) 전략이 보편화됨
- 필요성: 클라이언트의 반복된 재시도 요청이 중복 주문, 이중 송금 등의 치명적 데이터 정합성 훼손으로 이어지지 않도록 시스템적 안전판 구축 필수

---

## Ⅱ. 구조 및 구성요소

```text
[Idempotency Key 기반 멱등성 보장 처리 아키텍처]
Client -> Request (with UUID Key) -> API Gateway -> Idempotent Interceptor (Key 검증)
                                                       | (Redis/DB)
                                                       +-> 최초 키 O -> 비즈니스 로직(Insert/Update)
                                                       +-> 최초 키 X -> 생략 & 이전 결과 즉시 반환
```

| 구성요소 | 역할 | 특이사항 |
|:---|:---|:---|
| Idempotency-Key | 클라이언트가 요청 생성 시 첨부하는 고유 식별 헤더 (예: UUID) | 재시도 요청 시에도 값이 불변해야 함 |
| 멱등 검증 레이어 | 요청 키 저장소를 조회하여 기처리된 키인지 확인하는 인터셉터 | Lock 기반 동시성 제어 병행 |
| Key 저장소 | 처리 이력을 기록하고 설정한 만료 시간(TTL) 동안 유지 | 보통 초고속 조회를 위해 Redis 사용 |
| 상태 안전 비즈니스 로직 | 절대값(Set) 설정, 조건부 업데이트 등 멱등 연산 기반 DB 쿼리 구조 | +1 연산(Add) 대신 =특정값 대입 선호 |

> 요약: 클라이언트가 보낸 고유 멱등 키를 중앙 저장소에 기록/대조함으로써 실제 비즈니스 핵심 로직의 다중 실행을 차단한다.

## Ⅲ. 동작원리 및 흐름도

```text
클라이언트 Key 헤더 삽입 -> 서버 캐시 조회 -> Lock 획득(동시성 제어) -> 1회 비즈니스 로직 처리 -> 상태 반환
```

- 1단계 [고유 식별자 할당]: 클라이언트가 결제 요청을 생성하며 `Idempotency-Key: e8c6-..` 생성 후 전송
- 2단계 [상태 저장소 검증]: 서버 수신단 인터셉터가 Redis 캐시 저장소에 해당 UUID가 존재하는지 우선 조회
- 3단계 [조건 분기 처리]:
  - 미존재 시: 신규 락(Lock)을 걸고 DB 처리, 결론을 UUID와 맵핑 저장 후 반환
  - 기존재 시: DB 로직을 수행하지 않고 저장소의 '성공 이력 응답(200 OK 등)' 데이터를 그대로 재반환
- 4단계 [만료 및 청소]: 일정 기한(예: 24시간) 후 TTL 만료로 메모리 낭비 방지

> 요약: 신규 식별자의 요청만 실제 저장소 트랜잭션을 실행하고, 중복 식별자는 앞서 기록해둔 결과만 즉시 리턴하여 상태 중복을 막는다.

## Ⅳ. 특징

- 정합성 보장(Consistency): 중복 이벤트나 메시지가 발행되는 Exactly-Once 보장이 어려운 메시지 브로커(Kafka 등) 환경에서 At-Least-Once 상황을 극복하는 최종 방어선
- 멱등 키 라이프사이클: 영구 저장이 불필요하므로 캐시 메모리에 만료(TTL) 정책을 주어 비즈니스 트랜잭션 유효 시간 동안만 방어
- HTTP/REST 규약 결합성: RESTful API 사양에서 GET, PUT, DELETE 메서드는 내재적 멱등성을 권고하며 POST, PATCH는 비멱등성을 기본으로 가정함

> 요약: 멱등성 설계는 분산 메시징의 한계(중복 전달)를 보완하며, 재시도 아키텍처를 안전하게 운용하기 위한 필수 트레이드오프 기법이다.

## Ⅴ. 심화 비교 및 적용 판단

| 비교 축 | 비멱등 시스템 (Non-Idempotent) | 멱등 시스템 (Idempotent Design) | 선택 기준 |
|:---|:---|:---|:---|
| 상태 변화 속성 | 누적형 상대 업데이트 (예: 잔고 = 잔고 + 1만 원) | 덮어쓰기 절대 업데이트 (예: 특정 트랜잭션 ID 완료 상태 세팅) | 트랜잭션 성격 (추가 vs 상태 변경) |
| 네트워크 단절 시 대응 | 재시도 금지 (에러 반환 후 관리자 개입) | 클라이언트 측 무한 재시도(Auto-Retry) 허용 | 클라이언트 사용자 체감(UX) |
| 구현 복잡도/비용 | 단순 DB Insert 로직 (비용 낮음) | 고유 키 생성, 캐시 통제 인프라(Redis) 필요 (비용 높음) | 결제 등 데이터 오염 민감도 |

> 요약: 단순 로깅이나 댓글 작성(POST) 등은 비멱등을 허용하나, 결제/재고/쿠폰 발급 등 무결성 훼손 손실이 치명적인 구간은 멱등 설계를 강제해야 한다.

**리스크·대응:**
- Race Condition (동시성 찰나 중복): 멱등 키가 Redis에 저장(SET)되기 직전 아주 짧은 틈에 똑같은 요청 여러 개가 인프라로 동시 쏟아질 때 병렬 처리됨 → DB Unique Constraint(유니크 제약조건) 추가 또는 Redis `SETNX` (분산 락) 활용 이중 방어
- 키 충돌 버그: 클라이언트의 UUID 생성기 버그나 타임스탬프 오류로 다른 유저의 요청에 동일 식별자 삽입 → 멱등 키 외에 User-ID, 주문 해시값을 조합(Composite Key)하여 검증

## Ⅵ. 실무 적용 및 결론

**적용 방안 3개:**
1. **API Gateway 내재화 통제**: 백엔드 마이크로서비스마다 멱등 로직을 짜는 대신, 진입점인 API Gateway에서 HTTP Header의 `Idempotency-Key` 유무를 일괄 검증하고 Redis와 연동하여 1차 트래픽 컷(Cut)
2. **분산 트랜잭션 Saga 패턴 복구 로직 결합**: 여러 도메인이 연계되는 Saga 패턴 실패 시, 기존 작업을 취소하는 보상 트랜잭션(Compensation) 또한 네트워크 지연으로 무한 재시도될 수 있으므로 보상 액션 구현에 멱등 함수 강제
3. **Kafka 이벤트 소비 단의 DB 유니크 키 매핑**: 스트림(Kafka) 컨슈머가 이벤트(메시지)를 2번 이상 수신(At-Least-Once)하더라도, 처리 대상 DB 테이블 파티션에 Event ID를 Primary Key/Unique Index로 설계하여 무시력 방어

**결론:**
- 기술사 판단: 클라우드 네이티브에서 '모든 네트워크 호출은 실패할 수 있다'는 대전제를 수용하기 위한 핵심 기술이 재시도(Retry)이며, 이 재시도의 치명적 부작용을 막아주는 안전판이 멱등성 설계임
- 향후 방향: 최근 Stripe, Square 등 글로벌 결제 API 제공업체들이 API 헤더에 멱등 키 폼을 표준으로 도입하듯, B2B Open API 표준 설계 원칙의 기본 요건으로 자리 잡고 있음
