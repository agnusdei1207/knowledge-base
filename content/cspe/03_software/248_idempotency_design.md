## Ⅰ. 개요
- **정의**: 동일 요청을 여러 번 실행해도 결과가 한 번 실행한 것과 동일하도록 보장하는 설계 원칙임
- **배경/필요성**: 네트워크 재시도, 메시지 중복 전달 등으로 동일 요청이 반복될 수 있으며, 이때 부작용(중복 결제 등)을 방지할 기준이 필요함
- **비유**: 엘리베이터 버튼을 여러 번 눌러도 한 번만 호출되는 것과 같음

| 출제 의도 | 반드시 짚을 핵심 | 감점 회피 포인트 |
|:---|:---|:---|
| 멱등성 구현 패턴과 적용 범위 | Idempotency Key, 상태 확인 후 처리 | HTTP 메서드별 멱등성 여부를 정확히 구분할 것 |

> 요약: 중복 요청에도 동일 결과를 보장하여 부작용을 방지하는 설계 원칙임

## Ⅱ. 구성요소
```text
Client --> [Idempotency Key] --> Server
                                   |
                              Key 존재?
                             /        \
                            v          v
                      캐시 응답 반환  신규 처리 후 저장
```

| 구성요소 | 설명 | 비유 |
|:---|:---|:---|
| Idempotency Key | 요청을 고유 식별하는 클라이언트 생성 키(UUID 등)임 | 주문번호 |
| Key Store | 처리 완료된 Key와 응답을 저장하는 저장소(Redis, DB)임 | 접수 대장 |
| 중복 판별 로직 | Key 존재 여부로 신규/중복 요청을 구분하는 로직임 | 중복 접수 확인 |
| 원자적 처리 | Key 저장과 비즈니스 로직을 단일 트랜잭션으로 실행함 | 동시 처리 잠금 |

> 요약: Idempotency Key, Key Store, 중복 판별, 원자적 처리로 멱등성을 구현함

## Ⅲ. 절차
```text
Key 수신 --> 중복 확인 --> 비즈니스 처리 --> Key+응답 저장
```
- 1단계: 클라이언트가 요청 헤더에 Idempotency Key를 포함하여 전송
- 2단계: 서버가 Key Store에서 해당 Key 존재 여부를 조회하여 중복 판별
- 3단계: 신규 요청이면 비즈니스 로직 실행, 중복이면 저장된 응답을 즉시 반환
- 4단계: 처리 결과와 Key를 원자적으로 Key Store에 저장하여 향후 중복 방지

> 요약: Key 수신 → 중복 확인 → 처리/반환 → 저장 순으로 멱등성을 보장함

## Ⅳ. 문제점
- Key 저장소 부하: 대량 트래픽 시 Key Store 조회·저장이 병목이 됨
- TTL 설정 어려움: Key 보관 기간이 짧으면 만료 후 중복 처리, 길면 저장 비용 증가함
- 동시성 경합: 동일 Key 요청이 동시에 도착하면 Race Condition이 발생함

> 요약: 저장소 부하, TTL 설정, 동시성 경합이 멱등성 구현의 주요 과제임

## Ⅴ. 개선방안
1. 단기: Redis 등 인메모리 저장소 활용으로 Key 조회 지연 최소화
2. 중기: 비즈니스 특성별 TTL 정책 수립(결제: 24h, 조회: 5min 등)
3. 장기: 분산 락(Distributed Lock) 또는 DB Unique 제약으로 동시성 경합 해소

> 요약: 인메모리 저장소, TTL 정책, 분산 락을 통해 멱등성 설계를 안정화함

## Ⅵ. 전망
- 발전 방향: API Gateway 수준에서 멱등성을 자동 제공하는 기능이 표준화될 전망임
- 기술사적 판단: 이벤트 소싱(249 참조), Outbox(250 참조) 패턴과 결합하여 메시지 중복 처리를 근본적으로 해결하는 것이 바람직함
- 기술사 제언: 결제·주문 등 부작용이 큰 API부터 우선 적용하고 점진적으로 확대하는 것이 필요함
