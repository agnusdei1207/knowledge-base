# 📖 【암기용】 개념 완전 이해

> 목적: 멱등성 설계를 처음 봐도 완전히 이해하게 만든다. 시험 답안 양식이 아니라, 이해를 위한 친절한 설명이다.

## 한눈에
- **개요**: 멱등성(Idempotency)은 **같은 연산을 여러 번 실행해도 결과가 한 번 실행한 것과 동일하게 유지되는 수학적 성질**이며, 멱등성 설계는 이 성질을 API·메시지 처리에 적용해 **재시도(retry)**로 인한 중복 부작용을 차단하는 설계 원칙이다.
- **왜 필요한가**: 분산 시스템은 네트워크 타임아웃, 메시지 큐 재전달(redelivery) 상황에서 "정확히 한 번(exactly-once)" 실행을 보장하기 어렵다. 그래서 최소 한 번(at-least-once) 전달을 허용하고, 중복이 오더라도 업무 결과는 1회만 반영되게 만드는 것이 멱등성 설계다.
- **핵심 직관**: ATM 출금 버튼처럼, 여러 번 눌러도 실제 출금은 한 번만 일어나는 안전장치다.

## 핵심 용어 정리 (내부에 등장하는 것들)

| 용어 | 의미 | 비유 |
|:---|:---|:---|
| 멱등성 (Idempotency) | f(f(x))=f(x) — 반복 적용해도 결과가 불변인 수학적 성질 | 이미 꺼진 스위치를 다시 꺼도 여전히 꺼짐 |
| 메시지 전달 보장 (Delivery Semantics) | at-most-once/at-least-once/exactly-once — 분산 시스템이 메시지를 몇 번 전달하는지의 기준 | 편지를 못 받을 수도, 두 번 받을 수도, 정확히 한 번 받을 수도 있음 |
| Idempotency-Key | 클라이언트가 발급하는 동일 업무 요청 식별자 | 은행 창구 번호표 |
| Request Hash | 같은 key로 들어온 요청의 payload 변경을 탐지하는 값 | 번호표는 같은데 주문 내용이 바뀌었는지 확인 |
| Key Store | key·처리 상태·응답을 저장하는 저장소(TTL 보유) | 번호표 처리 기록부 |
| Unique Constraint | DB 레벨에서 중복 삽입을 원천 차단하는 제약 | 같은 계좌번호로 통장 2개 발급 금지 |
| Race Condition | 동시에 같은 key로 요청이 들어와 중복 처리될 위험 | 같은 번호표를 두 창구가 동시에 부름 |
| 409 Conflict | 같은 key, 다른 payload일 때 반환하는 오류 응답 | 같은 번호표인데 다른 사람이 다른 용건으로 옴 |

## 깊이 이해

### 왜 "정확히 한 번"이 어려운가 (배경)
- 클라이언트가 결제 요청을 보내고 서버가 처리를 끝냈는데 응답 패킷이 유실되면, 클라이언트는 "성공했는지 실패했는지" 알 수 없다. 이때 안전하게 취할 수 있는 유일한 행동은 재시도뿐이다.
- 메시지 전달 방식은 세 가지다. **at-most-once**(최대 한 번, 유실 가능 — 재전송 안 함), **at-least-once**(최소 한 번, 중복 가능 — ack 실패 시 재전송), **exactly-once**(정확히 한 번, 분산 환경에서 완전 보장은 사실상 불가능하거나 비용이 매우 크다). 실무에서는 **at-least-once 전달 + 멱등 처리**를 조합해 exactly-once *효과*를 낸다.

### 멱등 여부 판별 원리 — HTTP 메서드로 이해
- HTTP 스펙 기준으로 GET, PUT, DELETE는 멱등이다. `PUT /account/123 {balance: 1000}`은 몇 번 호출해도 잔액은 항상 1000이다. 반면 POST는 멱등이 아니다. `POST /account/123/deposit {amount: 1000}`을 두 번 호출하면 잔액은 1000이 아니라 2000이 된다.
- 결제·주문 생성처럼 "생성" 의미의 POST는 원래 비멱등이므로, 여기에 멱등성을 **인위적으로 부여**하는 것이 바로 Idempotency-Key 설계다.

### 작동 원리와 수치로 보는 흐름
1. 클라이언트가 `Idempotency-Key: order-123-pay-1`을 헤더에 담아 결제 요청을 보낸다.
2. 서버는 Key Store에서 이 key를 조회한다. 없으면 신규 요청으로 판단해 락을 획득하고 업무 트랜잭션을 실행한 뒤, key·request hash·응답 결과를 TTL 24시간으로 저장한다.
3. 5초 후 클라이언트가 타임아웃으로 같은 key를 재전송하면, 서버는 Key Store에서 기존 결과를 찾아 **업무 로직을 다시 실행하지 않고** 저장된 응답을 그대로 반환한다. 이 경우 승인 거래는 1건만 생성된다.
4. 만약 같은 key로 amount가 10,000원에서 20,000원으로 바뀐 요청이 오면, request hash가 불일치하므로 서버는 409 Conflict를 반환해 잘못된 재사용을 막는다.

### 동시성 문제 — 왜 key 저장만으론 부족한가
- 두 요청이 거의 같은 순간(수 ms 이내)에 도착하면, 둘 다 Key Store 조회 시 "없음"으로 판단해 동시에 트랜잭션을 실행할 수 있다(Race Condition). 이를 막으려면 DB의 **unique index**(예: `order_id` unique)나 **분산 락**으로 동시 삽입 자체를 거부해야 한다. 애플리케이션 레벨의 key 조회만 믿으면 안 되는 이유다.

### 비유와 흔한 오해
- **비유**: ATM에서 출금 버튼을 두 번 눌러도 실제 출금은 한 번만 일어나야 하는 것과 같다. 두 번째 누름은 "확인"으로 처리될 뿐 새 출금이 아니다.
- **오해**: 멱등성은 "중복 요청을 무시하는 것"이 아니다. 무시하면 클라이언트는 두 번째 응답을 받지 못한다. 올바른 처리는 **동일 요청이면 저장된 동일 응답을 재반환**하고, **다른 payload면 명시적으로 거부(409)**하는 것이다.

## 연결 개념
- Retry Pattern — 재시도가 발생한다는 전제 자체가 멱등성 설계의 출발점
- Outbox Pattern — 이벤트 발행 시 중복 발행을 통제하는 짝 패턴
- Exactly-Once Semantics — 시스템 레벨에서 완전 보장이 어려운 이유와 멱등성으로 보완하는 관계
- Optimistic Locking — race condition을 버전 필드로 막는 대안적 동시성 제어

# 📝 【답안용】 시험 답안 템플릿

> 핵심: 멱등성 답안은 재시도 허용 구조와 중복 부작용 차단 기준을 함께 제시해야 한다.

## 핵심 인사이트 (3줄 요약)

> 1. **본질**: Idempotency Design은 동일 업무 요청의 반복 실행 결과를 1회 실행 결과와 같게 만드는 API·메시지 처리 설계이다.
> 2. **가치**: 타임아웃, 재시도, 큐 중복 전달 상황에서 결제·주문·재고 차감의 중복 부작용을 방지한다.
> 3. **판단 포인트**: idempotency key, 요청 hash, 결과 저장 TTL, 유니크 제약, 동시성 잠금이 핵심 설계 요소이다.

## 출제 의도 및 답안 포인트

| 출제 의도 | 반드시 짚을 핵심 | 감점 회피 포인트 |
|:---|:---|:---|
| 분산 재시도 이해 확인 | at-least-once, timeout, duplicate delivery | 재시도를 장애로만 취급 |
| API 설계 역량 확인 | Idempotency-Key, unique constraint, TTL | key 저장 없이 중복 체크 주장 |
| 데이터 정합성 판단 확인 | 요청 hash 비교, 결과 재반환, 충돌 처리 | 같은 key 다른 payload 처리 누락 |

> 요약: 멱등성은 중복 요청을 허용하되 업무 결과는 1회만 반영되도록 key와 저장소 제약을 설계하는 문제이다.

## Ⅰ. 개요 및 필요성

- 개요: 멱등성 설계는 반복 요청 결과를 한 번만 반영하는 방식이다.
- 배경: 분산 시스템에서는 네트워크 타임아웃과 메시지 재전달이 발생하므로 재시도 자체를 금지할 수 없다.
- 필요성: Idempotency-Key, 유니크 제약, 멱등 소비로 결제·주문 중복 반영을 차단해야 한다.

---

## Ⅱ. 구조 및 구성요소

```text
Client -> Idempotency-Key -> API Gateway -> Key Store
       -> Business Transaction -> Result Cache -> Response
```

| 구성요소 | 역할 | 특이사항 |
|:---|:---|:---|
| Idempotency-Key | 동일 업무 요청 식별 | 주문ID+시도번호, UUID |
| Request Hash | 같은 key의 payload 변경 탐지 | 불일치 시 409 Conflict |
| Key Store | 처리 상태와 결과 저장 | Redis/DB, TTL 24시간 |
| Unique Constraint | DB 중복 반영 차단 | order_id unique index |

> 요약: 멱등성은 key, payload hash, 처리 결과, DB 유니크 제약을 함께 사용한다.

---

## Ⅲ. 동작원리 및 흐름도

```text
요청 수신 -> key 조회 -> 신규면 잠금 획득
-> 업무 처리/결과 저장 -> 재요청이면 기존 결과 반환
```

| 단계 | 처리 내용 | 검증 기준 |
|:---:|:---|:---|
| 1 | Idempotency-Key와 payload hash 수신 | key 누락률 0% |
| 2 | key store에서 처리 상태 조회 | hit/miss 기록 |
| 3 | 신규 요청은 unique constraint로 1회 반영 | 중복 거래 0건 |
| 4 | 동일 재요청은 저장된 응답 반환 | 응답 일관성 100% |

> 요약: 신규 요청만 업무 트랜잭션을 수행하고 중복 요청은 저장 결과를 반환해 부작용을 차단한다.

## Ⅳ. 특징

| 구분 | 멱등성 없음 | 멱등성 설계 | 수치 판단 |
|:---|:---|:---|:---|
| 재시도 | 중복 결제·중복 주문 위험 | 동일 key 1회 반영 | 중복 거래 0건 |
| 저장 | 처리 결과 미보관 | key/result TTL 보관 | TTL 24~72시간 |
| 오류 처리 | timeout 후 상태 불명 | 기존 결과 조회 가능 | 5xx 재시도 허용 |

> 요약: 멱등성은 재시도를 금지하지 않고 중복 부작용을 0건으로 통제하는 설계이다.

## Ⅴ. 심화 비교 및 적용 판단

| 비교 축 | 기존/대안 | 본 키워드 | 선택 기준 |
|:---|:---|:---|:---|
| API | POST 단순 처리 | POST + Idempotency-Key | 결제·주문 생성 API |
| 메시지 | 소비 후 단순 ack | processed message table | at-least-once 큐 사용 시 |
| DB | application check | unique index + transaction | 동시 요청 경쟁 가능 시 |

> 요약: 금전·재고·권한 변경처럼 부작용이 있는 명령은 멱등성 key와 DB 제약을 동시에 적용한다.

| 리스크 | 원인 | 대응 방안 | 확인 지표 |
|:---|:---|:---|:---|
| Key 충돌 | client key 재사용 | payload hash 비교, 409 반환 | hash mismatch 0건 처리 |
| Race condition | 동시 재시도 | DB unique index, distributed lock | duplicate insert 0건 |
| 저장소 폭증 | key 무기한 저장 | TTL, partition cleanup | key store 사용률 70% 이하 |

> 요약: 멱등성 리스크는 key 충돌과 동시성 경쟁이며, hash와 DB 제약으로 통제한다.

| 점검 항목 | 목표 기준 | 측정 방법 |
|:---|:---|:---|
| 중복 처리 | 중복 거래 0건 | payment/order reconciliation |
| 재시도 처리 | 동일 key 응답 일관성 100% | API contract test |
| 저장소 | TTL 만료 정상 처리 | key count, memory metric |

> 요약: 멱등성 검증은 중복 거래, 응답 일관성, key 저장소 용량을 함께 점검한다.

## Ⅵ. 실무 적용 및 결론

**적용 방안 3개 (필수 — 단계별 또는 항목별):**
1. 결제·주문 생성 API에 `Idempotency-Key` 필수화, payload hash 저장, 동일 key 다른 payload는 409 반환
2. DB에 `order_id` 또는 `payment_request_id` unique index를 두고 트랜잭션 내 결과를 key store에 저장
3. 메시지 소비자는 `processed_message` 테이블과 TTL 72시간 정리를 적용해 at-least-once 중복 전달을 흡수

**결론 (2줄):**
- 기술사 판단: 재시도 가능한 API는 멱등성 없이는 운영할 수 없으며, key store만이 아니라 DB 유니크 제약까지 포함해야 한다
- 향후 방향: 결제·커머스·이벤트 기반 시스템은 멱등성, Outbox, Saga를 결합해 분산 트랜잭션 실패를 흡수한다
