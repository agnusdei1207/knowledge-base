## 미리 알고가기

- 요구사항 분석은 이해관계자 요구를 시스템 요구로 구조화하는 활동임
- 기능 요구와 비기능 요구를 분리해야 함
- 명세는 구현 이전의 계약 문서이자 검증 기준임

## Ⅰ. 개요

- **정의/개념**: 요구사항 분석과 명세는 이해관계자의 기대와 제약을 수집하고 충돌을 조정해 기능 요구와 비기능 요구와 수용 기준으로 구체화하는 소프트웨어 개발 초기 핵심 활동임
- **배경/필요성**: 요구가 모호하거나 누락되면 이후 설계와 구현과 시험이 모두 흔들리므로, 개발 시작 전 무엇을 왜 만들고 어떤 품질 수준을 만족해야 하는지 명확히 해야 함

## Ⅱ. 특징

- 사용자 언어를 시스템 언어로 번역하는 과정이라 해석 오류가 많음
- 기능 요구와 품질 속성과 제약 조건을 함께 다뤄야 함
- 명세 품질이 낮으면 뒤 단계 재작업 비용이 매우 커짐
- 요구는 고정값이 아니라 변경 관리 대상임

## Ⅲ. 종류 및 비교

| 판단 기준 | 기능 요구사항 | 비기능 요구사항 |
|:---|:---|:---|
| 초점 | 시스템이 무엇을 해야 하는가 | 얼마나 빠르고 안전하고 안정적인가 |
| 표현 방식 | 유스케이스, 시나리오, 업무 규칙 | 성능 수치, 보안 정책, 가용성 기준 |
| 검증 방법 | 기능 테스트와 시나리오 검증 | 성능, 보안, 운영 시험 |
| 누락 시 영향 | 기능 미완성 | 사용성 저하, 장애, 운영 실패 |

## Ⅳ. 구성요소 및 구조

| 구성요소 | 설명 |
|:---|:---|
| Stakeholder Need | 사용자와 운영자와 규제 요구가 서로 다른 관점을 제공해 분석 출발점이 됨 |
| Requirement Specification | 요구를 일관된 형식으로 정리해 설계와 테스트의 계약 기반을 만듦 |
| Acceptance Criteria | 요구 충족 여부를 시험 가능한 기준으로 바꿔 해석 차이를 줄임 |
| Change Control | 요구 변경의 영향과 우선순위를 관리해 범위 확산을 통제함 |

## Ⅴ. 원리 및 절차 흐름도

```text
+-------------+     +-------------+     +-------------+     +-------------+
| 요구 수집      | --> | 분석/충돌 조정 | --> | 명세 문서화    | --> | 검증/변경 관리 |
+-------------+     +-------------+     +-------------+     +-------------+
```

1. **요구 수집**: 이해관계자 요구와 제약을 모음
2. **분석 및 충돌 조정**: 모호점과 상충점을 정리함
3. **명세 문서화**: 기능과 비기능과 수용 기준으로 구조화함
4. **검증 및 변경 관리**: 리뷰와 추적성 관리로 명세를 유지함

## Ⅵ. 문제점 및 해결 방안

1. 문제: 이해관계자마다 용어와 기대 수준이 달라 요구가 같은 말로도 다르게 해석될 수 있음
   - 해결방안: 도메인 용어 사전과 워크숍을 운영하고 requirement ambiguity count와 review rework rate로 검증함
2. 문제: 비기능 요구를 늦게 정의하면 성능과 보안과 운영성 문제가 구현 말기에 폭발할 수 있음
   - 해결방안: 품질 속성을 초기 명세에 포함하고 nonfunctional coverage와 late defect ratio로 검증함
3. 문제: 요구 변경 통제가 약하면 범위가 지속 확대되어 일정과 비용이 무너질 수 있음
   - 해결방안: change board와 영향 분석을 운영하고 scope creep ratio와 change lead time으로 검증함

## Ⅶ. 적용 사례

- 금융 시스템 구축에서는 요구 워크숍을 운영하고 확인 지표는 requirement ambiguity count와 traceability coverage임
- 플랫폼 개발에서는 비기능 요구를 초기 명세에 반영하고 확인 지표는 nonfunctional coverage와 late defect ratio임
- 공공 프로젝트에서는 요구 변경 위원회를 운영하고 확인 지표는 scope creep ratio와 change lead time임

## Ⅷ. 결론

요구사항 분석의 품질은 문서 양이 아니라 해석 차이를 줄이고 설계와 테스트가 바로 이어질 수 있는 검증 가능한 명세를 만드는 데서 결정됨.
