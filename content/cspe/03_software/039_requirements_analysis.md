# 📖 【암기용】 개념 완전 이해

> 목적: 이 개념을 처음 보는 사람도 완벽히 이해하게 만든다. 시험 답안 양식이 아니라, 이해를 위한 친절한 설명이다.

## 한눈에
- **개요**: 요구사항 분석·명세는 **요구사항 공학(Requirements Engineering)**의 핵심 과정으로, 이해관계자의 모호한 니즈를 도출·분석·명세·확인의 4단계를 거쳐 개발자가 코드로 옮길 수 있는 **SRS(Software Requirements Specification)** 문서로 번역하는 작업이다.
- **왜 필요한가**: 요구사항 결함은 발견이 늦어질수록 수정 비용이 기하급수적으로 커진다. 개발이 시작되기 전, 즉 가장 비용이 저렴한 시점에 '무엇을 만들 것인가'를 명확히 합의해 두어야 후반부의 대규모 재작업을 막을 수 있다.
- **핵심 직관**: **기능적 요구사항**은 시스템이 "무엇을" 해야 하는가(예: 로그인 시 DB를 조회해야 한다)를, **비기능적 요구사항**은 그것을 "얼마나 잘" 해야 하는가(예: 1초 이내, 1만 명 동시 접속에도 정상 동작해야 한다)를 규정한다.

## 핵심 용어 정리 (내부에 등장하는 것들)

| 용어 | 의미 | 비유 |
|:---|:---|:---|
| 요구사항 공학(Requirements Engineering) | 이해관계자의 필요를 체계적으로 도출·분석·명세·확인하는 소프트웨어 공학 프로세스 전체 — 상위 개념 | 건축 설계 전 의뢰인과의 협의 과정 |
| 도출(Elicitation) | 인터뷰·설문·워크숍 등으로 이해관계자의 요구를 끌어내는 활동 | 손님의 취향을 묻는 과정 |
| 분석(Analysis) | 도출된 요구 간의 모순·중복·타당성을 걸러내는 활동 | 손님의 요청이 서로 모순되지 않는지 검토 |
| 명세(Specification) | 정제된 요구를 표준 형식의 문서(SRS)로 기록하는 활동 | 시공 도면으로 옮겨 적기 |
| 확인(Validation) | 작성된 명세가 실제 요구를 제대로 반영했는지 이해관계자가 검토·승인하는 활동 | 도면을 보여주고 서명받기 |
| SRS(Software Requirements Specification) | 요구사항을 표준 형식으로 정리한 공식 문서 | 시공 계약서 |
| IEEE 830 | SRS 문서의 목차·형식을 정한 국제 표준 | 계약서 양식 표준 |
| 기능적 요구사항(Functional Requirement) | 시스템이 "무엇을" 해야 하는가에 대한 요구 | 방이 몇 개 있어야 하는가 |
| 비기능적 요구사항(Non-Functional Requirement) | 시스템이 그 기능을 "얼마나 잘" 수행해야 하는가에 대한 요구(성능, 가용성, 보안 등) | 방음이 얼마나 잘 되어야 하는가 |
| 검증 가능성(Verifiable) | 요구사항이 참/거짓을 객관적으로 판정할 수 있는 형태로 쓰였는지 여부 | 합격선이 숫자로 정해져 있는가 |
| 추적성(Traceability) | 요구사항 하나가 설계·코드·테스트 케이스까지 연결되어 추적 가능한지 여부 | 주문 번호로 배송 상태를 조회하는 것 |
| 사용자 스토리(User Story) | 애자일에서 요구사항을 짧은 정형 문장으로 표현하는 경량 명세 기법 | 두꺼운 계약서 대신 메모 한 장 |

## 깊이 이해

### 왜 초기 단계가 중요한가 — 결함 수정 비용의 수치
- 요구사항 단계에서 결함(잘못되거나 누락된 요구)을 발견해 고치는 비용을 1이라 하면, 이미 개발이 끝나 운영 중인 시스템에서 같은 결함을 고치는 비용은 통상 100배 이상으로 커진다는 것이 소프트웨어 공학에서 널리 인용되는 경험칙이다(Barry Boehm의 비용 곡선).
- 이 때문에 요구사항 분석·명세는 귀찮은 서류 작업이 아니라, 후반부의 훨씬 큰 재작업 비용을 막는 가장 저렴한 방어선이다.

### 4단계 파이프라인을 예로 이해하기
- 도출: "회원 관리 기능이 필요합니다"라는 고객의 말을 인터뷰로 끌어낸다.
- 분석: "회원 가입은 이메일 인증이 필요한가, 아닌가"처럼 고객이 미처 말하지 않은 부분의 모순이나 누락을 찾아 질문하고 정리한다.
- 명세: "이메일 인증 링크는 발송 후 24시간 동안 유효하며, 만료 시 재발송 버튼이 노출되어야 한다"처럼 구체적이고 검증 가능한 문장으로 SRS에 기록한다.
- 확인: 작성된 SRS를 고객에게 보여주고, 실제 의도와 일치하는지 확인받아 베이스라인(기준선)으로 확정한다.

### 좋은 명세와 나쁜 명세를 가르는 판별 원리 — 검증 가능성
- 나쁜 예: "로그인 화면은 빨라야 한다." → '빠르다'는 사람마다 기준이 달라 테스트로 참/거짓을 가릴 수 없다.
- 좋은 예: "로그인 API의 평균 응답 시간은 300ms 이내, 동시 접속자 1만 명 기준 p99(상위 1% 지연) 응답 시간은 800ms 이내여야 한다." → 숫자로 되어 있어 테스트 결과를 통과/실패로 명확히 판정할 수 있다.
- 판별 기준은 하나다: "이 문장을 테스트 케이스로 바로 바꿀 수 있는가?" 바꿀 수 없다면 아직 명세가 아니라 의견이다.

### 기능 vs 비기능 요구사항 구분 예시
- 기능적 요구사항: "사용자가 결제 버튼을 누르면 장바구니 상태를 '결제완료'로 변경한다." — 시스템이 수행하는 동작 자체를 규정한다.
- 비기능적 요구사항: "결제 트랜잭션은 동시 사용자 1만 명 환경에서 p99 기준 1.5초 이내에 응답해야 한다." — 그 동작을 얼마나 잘 수행해야 하는지를 규정하며, 이 수치가 실제로는 서버를 몇 대 둘지, 캐시를 쓸지, DB를 어떻게 분산시킬지 같은 아키텍처 결정을 좌우한다.

### 비유
- 미용실에서 손님이 "너무 짧지 않게 해주세요"라고 말하면(도출), 미용사는 "지금 머리 길이로는 컷트만 가능하고 펌은 어렵다"고 판단하며(분석), "옆머리 12mm, 앞머리는 눈썹 위 1cm"로 구체적인 시술 계획을 세우고(명세), 손님에게 "이대로 자르면 되겠습니까"라고 확인받는다(확인). 네 단계 중 하나라도 생략하면 손님이 원하지 않는 머리 모양이 나올 위험이 커진다.

## 연결 개념
- **UML**: 텍스트로 된 요구사항을 유스케이스 다이어그램 등으로 시각화해 이해관계자 간 합의를 돕는 도구.
- **XP의 변경 비용 곡선**: 요구사항 결함을 늦게 발견할수록 수정 비용이 커진다는 원리는 XP가 극복하려는 문제의식과 같은 뿌리를 갖는다.
- **BDD(Behavior-Driven Development)**: 요구사항을 Given-When-Then 형식으로 써서 그대로 자동화 테스트 코드로 연결하는 기법으로, 명세와 테스트 간 추적성 단절 문제를 해결한다.

# 📝 【답안용】 시험 답안 템플릿

> 목적: 시험장에서 25분에 그대로 쓰는 답안 양식. 작성방식(추상표현 금지·수치·도식·문제유형 전환)을 엄격히 지킨다.
> 핵심: 이 시험은 정보를 많이 나열하는 시험이 아니라, 문제 신호어에서 출제자 의도를 읽고 핵심 논점을 선별해 쓰는 시험이다.

## 핵심 인사이트 (3줄 요약)

> 1. **본질**: 이해관계자의 모호하고 상충하는 비즈니스 니즈를 도출-분석-명세-확인(4단계)을 거쳐, 개발자와 테스트 엔지니어가 검증 가능한(Verifiable) 형태의 시스템 스펙(SRS)으로 변환하는 선행 공정이다.
> 2. **가치**: 소프트웨어 결함 원인의 80%를 차지하는 요구사항 오해를 초기에 차단하여(Shift-Left), 구현 및 통합 단계에서 발생하는 기하급수적 재작업(Re-work) 비용 곡선의 폭발을 원천 방어한다.
> 3. **판단 포인트**: 기능적 요구(비즈니스 로직)와 비기능적 요구(성능, 보안 품질 속성)의 분류 기준을 명확히 대조하고, 모호한 텍스트를 유스케이스(Usecase) 등 정형 모델링으로 전환하는 아키텍처적 기법을 짚어야 한다.

## 출제 의도 및 답안 포인트

| 출제 의도 | 반드시 짚을 핵심 | 감점 회피 포인트 |
|:---|:---|:---|
| 요구사항 공학의 4단계 라이프사이클 도식화 | 도출 -> 분석 -> 명세 -> 확인 (Validation) | 분석과 명세를 구분하지 못하고 문서 쓰는 작업 하나로 뭉뚱그려 설명 |
| 요구사항의 품질 속성(Criteria) 평가 척도 | 검증 가능성(Verifiability), 명확성, 추적성(Traceability) | "사용하기 편해야 한다" 같은 모호한 문장을 훌륭한 예시라고 적는 맹점 |
| 기능(Functional) vs 비기능(Non-functional) 분류 역량 | 비기능 요구사항을 성능, 가용성(99.9%), 보안 규제 등으로 정량화 | 비기능 요구사항의 중요도(아키텍처를 결정짓는 핵심 요소)를 누락 |

> 요약: 고객의 입(말)을 믿지 마라. 고객의 요구를 철저한 논리적 필터(분석)로 거른 뒤, 숫자가 박힌 법적 문서(명세서)로 만들어 도장을 받아내는 것이 생존의 제1원칙이다.

## Ⅰ. 개요 및 필요성

- 정의: 다양한 이해관계자의 비즈니스 니즈를 수집하여 시스템의 제약 조건과 목표를 분석하고, 이를 표준화된 문서(IEEE 830 등) 또는 모델(UML) 형태로 공식 베이스라인화 하는 공학 프로세스
- 배경: 폭포수 SDLC에서 초기 요구사항 결함(누락/모호성)이 발견되지 않고 테스트 단계까지 흘러갈 경우, 수정 비용이 초기 대비 최소 100배(Snowball Effect) 폭증
- 필요성: 시스템이 수행해야 할 '기능(What)'과 달성해야 할 '품질 속성(How well)'을 정량적이고 검증 가능(Verifiable)하게 못 박아 개발 및 인수 테스트(Acceptance Test)의 절대적 기준점 확립

## Ⅱ. 요구사항 공학 4단계 파이프라인 및 명세 도식

```text
[ 요구사항 엔지니어링 프로세스 ]

1. 도출(Elicitation) : 브레인스토밍, 인터뷰, 델파이 기법으로 뇌피셜 수집
        | (상충되는 니즈 발견)
2. 분석(Analysis) : 데이터 흐름(DFD)이나 객체지향(Usecase) 관점으로 타당성 필터링 및 논리 충돌 해결
        | (정제된 합의 도출)
3. 명세(Specification) : IEEE 830 표준 포맷에 맞춰 SRS(요구사항 정의서) 작성 (기능/비기능 분리)
        | (형상 관리 등록 전 최종 리뷰)
4. 확인(Validation) : 인스펙션(Inspection), 프로토타이핑을 통해 고객의 최종 서명(Baseline 🔒) 획득
```

| 요구사항 분류 체계 | 시스템 정의 본질 | 명세 작성 예시 (정량화/검증 가능성) |
|:---|:---|:---|
| **기능적 (Functional)** | 시스템이 "무엇을" 수행해야 하는가? (입력, 동작, 비즈니스 로직) | 사용자가 결제 버튼 클릭 시, 장바구니 DB 상태를 '결제완료'로 갱신해야 한다. |
| **비기능적 (Non-Functional)**| 시스템이 기능을 "얼마나 잘" 수행해야 하는가? (성능, 가용성, 보안, 제약) | 결제 트랜잭션 응답 시간은 동시 접속자 1만 명 환경에서 **99퍼센타일(p99) 기준 1.5초 이내**여야 한다. |

> 요약: 텍스트로 쓴 100장의 기획서보다, 수치가 명확히 박힌 비기능 요구사항 1줄이 서버 인프라 아키텍처(Scale-out, 로드밸런서)를 송두리째 결정짓는 진짜 뼈대다.

## Ⅲ. 좋은 명세서(SRS)가 갖춰야 할 5대 품질 속성 (Criteria)

아무리 문서를 예쁘게 써도 아래 조건에 미달하면 개발자는 코드를 짤 수 없고 테스터는 버그를 잡을 수 없다.

| 품질 속성 지표 | 개념적 정의 및 실패 시 치명적 리스크 | 공학적 교정 방향 |
|:---|:---|:---|
| **검증 가능성 (Verifiable)** | "화면이 빠르게 떠야 한다" -> 테스트 엔지니어가 T/F를 가릴 수 없어 인수 승인 마비 | "화면 렌더링이 0.5초 이내 완료"로 정량적 지표 강제 |
| **명확성 (Unambiguous)** | "기존 회원이나 신규 회원이면서 VIP인 자" -> 주어/술어 결합 모호로 개발자 마음대로 코딩 | (기존 OR 신규) AND VIP 형태로 논리식 기호화 적용 |
| **추적성 (Traceable)** | 요구사항 ID 번호(Req-001)가 소스코드 커밋 번호 및 테스트 케이스와 거미줄처럼 매핑되어야 함 | 요구사항 추적 매트릭스(RTM)를 작성해 누락(Omission) 완벽 색출 |

> 요약: 명세(Specification)는 시나 소설이 아니다. 주어, 동사, 조건문, 정량적 수치로만 구성된 차가운 법전이어야만 기계(컴퓨터)를 움직일 수 있다.

## Ⅳ. 극복해야 할 시스템적 리스크 및 애자일 패러다임 튜닝

폭포수 모델의 "완벽한 문서" 강박은 문서화 자체에 리소스를 매몰시키는 안티패턴을 부른다.

| 리스크 요인 | 발생 시나리오 및 프로젝트 붕괴 원인 | 아키텍처 대응 방안 (실무 튜닝) |
|:---|:---|:---|
| **Analysis Paralysis (분석 마비)** | 모든 엣지 케이스(예외)를 문서에 완벽히 다 담으려다가, 1년짜리 프로젝트에서 분석/설계만 6개월을 소모하여 정작 코딩할 시간이 증발(Time-to-Market 실기) | 폭포수를 과감히 버리고, **애자일 사용자 스토리(User Story)** 도입. "나는 [고객]으로서 [목적]을 위해 [기능]을 원한다" 포스트잇 1장으로 문서를 대체하고 직접 돌아가는 MVP로 빠른 피드백 유도 |
| **요구사항 휘발 (문서와 코드의 괴리)** | 오픈 이후 운영 단계에서 코드는 수백 번 바뀌었는데 워드 파일(SRS)은 업데이트가 안 되어, 문서를 믿고 유지보수하다가 시스템 장애 연쇄 폭발 | **BDD (행위 주도 개발)** 도구인 Cucumber 도입. 기획자가 `Given-When-Then` 영단어로 요구사항을 쓰면, 그것이 100% 실행 가능한 자동화 테스트 코드로 매핑되어 '살아 숨 쉬는 문서(Living Doc)' 체계 구축 |

> 요약: 종이에 적힌 설계서는 코드를 한 줄 짜는 순간 죽은 문서가 된다. 요구사항이 테스트 코드 자체가 되도록 강제(BDD)하지 않으면, 추적성(Traceability)은 결국 끊어지게 마련이다.

## Ⅴ. 실무 적용 방안 및 결론

**적용 방안 3개:**
1. [공공/국방 SI 프로젝트 요구사항 추적 매트릭스(RTM) 전산화] 방위사업청 무기 체계 SW 개발 시, 수천 개의 국방 규격(요구사항) 누락을 막기 위해 DOORS 같은 전용 요구사항 관리 솔루션을 연동하여 요구사항ID -> 형상관리 커밋 로그 -> 통합 테스트 케이스까지 양방향 추적망(RTM) 100% 강제화
2. [비기능 요구사항(NFR) 기반 클라우드 아키텍처 설계 튜닝] MSA 커머스 플랫폼 구축 전, "블랙프라이데이 이벤트 시 초당 10만 TPS 수용 및 RTO(복구 목표 시간) 1분"이라는 비기능 요구사항(NFR)을 기반으로, RDBMS 대신 DynamoDB(NoSQL) 선정 및 AWS Multi-AZ 이중화 아키텍처 토폴로지 사전 픽스
3. [프로토타이핑(Prototyping) 기반 Elicitation(도출) 수행] B2C 고객 앱 분석 단계에서, 고객이 구두로 설명하는 요구사항의 모호성을 타파하기 위해 Figma 등 와이어프레임 툴을 활용한 Throw-away(폐기형) 프로토타입 화면을 3일 만에 시연하여 시각적(Visual) 합의 도출 후 텍스트 명세 착수

**결론:**
- 기술사 판단: 요구사항 분석 및 명세는 소프트웨어 공학의 '나비효과(Butterfly Effect)'다. 이곳에서의 1도 각도 틀어짐은 수개월 뒤 구현과 테스트 단계에서 복구 불가능한 시스템 붕괴로 폭증한다. 좋은 명세란 고객의 말을 받아 적는 것이 아니라, 비즈니스 가치와 시스템 제약을 논리적으로 재단(Tailoring)하는 공학적 협상이다.
- 향후 방향: 최근 LLM(거대 언어 모델)의 도입으로, 자연어로 모호하게 작성된 기획 문서를 AI가 정형화된 유스케이스(UML) 다이어그램 코드(PlantUML)나 테스트 케이스 시나리오로 1초 만에 1차 역번역(Reverse Translation)해 주는 Requirements Engineering의 자동화 혁명이 가속화되고 있다.
