# 📖 【암기용】 개념 완전 이해

> 목적: 요구사항 분석을 처음 보는 사람도 이해관계자 요구를 검증 가능한 명세로 바꾸는 과정을 이해하게 만든다. 시험 답안 양식이 아니라, 이해를 위한 친절한 설명이다.

## 한눈에
- **개요**: 요구사항 분석은 이해관계자 요구를 기능·비기능 명세와 수용 기준으로 구체화하는 활동
- **왜 필요한가**: 요구사항이 모호하면 설계와 구현은 맞게 보이지만 고객이 원하는 결과와 달라진다. 분석 단계에서 요구 출처, 우선순위, 검증 기준을 확정해야 재작업을 줄일 수 있다.
- **핵심 직관**: 주문서를 "맛있는 음식"이 아니라 메뉴, 수량, 알레르기, 배송 시간으로 바꾸는 과정이다.

## 깊이 이해
- **배경·문제의식**: 개발 실패의 많은 원인은 기술 부족보다 요구사항 누락, 이해관계자 충돌, 비기능 요구 누락에서 발생한다. 요구사항 분석은 elicitation, analysis, specification, validation, management로 진행된다.
- **작동 원리**: 인터뷰, 워크숍, 관찰, 프로토타입으로 요구를 수집하고, 기능 요구사항과 품질속성 요구사항으로 분류한다. SRS, user story, use case, acceptance criteria로 명세화하고 RTM으로 설계·테스트까지 추적한다.
- **비유**: 병원 진료에서 환자 증상을 듣고 검사로 원인을 좁힌 뒤 처방전을 수치와 용량으로 쓰는 과정과 같다.
- **구체 예시**: "로그인이 쉬워야 함"은 모호하다. "사용자는 이메일+비밀번호로 3초 이내 로그인하고, 5회 실패 시 10분 잠금"처럼 기능, 성능, 보안 조건으로 바꿔야 검증 가능함.
- **흔한 오해·주의점**: 요구사항 분석은 고객 말을 받아 적는 일이 아니다. 충돌 요구 조정, 우선순위 결정, 검증 가능한 acceptance criteria 작성이 핵심이다.

## 연결 개념
- SRS: 요구사항을 체계적으로 명세한 문서
- Acceptance Criteria: 요구사항 완료 여부를 검증하는 조건
- RTM: 요구사항과 설계·코드·테스트를 연결하는 추적성 매트릭스

# 📝 【답안용】 시험 답안 템플릿

> 목적: 시험장에서 25분에 그대로 쓰는 답안 양식. 작성방식(추상표현 금지·수치·도식·문제유형 전환)을 엄격히 지킨다.
> 핵심: 요구사항 분석 답안은 수집 기법 나열이 아니라 모호한 요구를 검증 가능한 SRS·수용 기준·추적성으로 바꾸는 과정이 보여야 한다.

## 핵심 인사이트 (3줄 요약)

> 1. **본질**: 요구사항 분석은 이해관계자 요구를 기능·비기능 요구사항, 우선순위, 수용 기준으로 변환하는 활동이다.
> 2. **가치**: SRS와 RTM으로 설계·구현·테스트까지 추적성을 확보해 누락과 재작업을 줄인다.
> 3. **판단 포인트**: elicitation 기법, 요구 충돌 조정, NFR 수치화, acceptance criteria 품질이 답안의 핵심이다.

## 출제 의도 및 답안 포인트

| 출제 의도 | 반드시 짚을 핵심 | 감점 회피 포인트 |
|:---|:---|:---|
| 요구사항 공학 기본 이해 확인 | elicitation, analysis, specification, validation, management | 인터뷰·설문 등 수집 기법만 나열 |
| 품질 요구 수치화 역량 확인 | 기능/NFR, SRS, acceptance criteria | "사용자 친화" 같은 모호 표현 사용 |
| 추적성·변경 관리 판단 확인 | RTM, baseline, CCB, impact analysis | 요구사항 확정 후 변경 통제 누락 |

> 요약: 요구사항 분석 문제는 모호한 요구를 검증 가능한 명세와 추적성으로 전환하는 능력을 본다.

---

## Ⅰ. 개요 및 필요성

요구사항 분석은 요구를 검증 가능한 명세로 바꾸는 활동이다.
모호한 요구는 설계 오류, 범위 확산, 테스트 기준 부재로 이어진다.
따라서 이해관계자 식별, 기능·비기능 분류, SRS, RTM, 수용 기준이 필요함.

---

## Ⅱ. 구조 및 구성요소

```text
Stakeholder -> Elicitation -> Analysis/Prioritization -> Specification
            -> Validation -> Baseline -> Traceability -> Change Control
```

| 구성요소 | 역할 | 산출물·지표 |
|:---|:---|:---|
| Stakeholder | 요구 출처와 의사결정자 식별 | RACI, stakeholder map |
| Elicitation | 요구 수집 | interview, workshop, prototype |
| Specification | 요구사항 문서화 | SRS, user story, use case |
| Traceability | 설계·테스트 연결 | RTM, acceptance criteria |

> 요약: 요구사항 분석은 요구 출처부터 테스트 추적성까지 연결해야 변경 영향 분석이 가능하다.

---

## Ⅲ. 동작원리 및 흐름도

```text
이해관계자 식별 -> 요구 수집 -> 기능/NFR 분류 -> 우선순위 조정
-> SRS 작성 -> 검토·검증 -> 기준선 설정 -> RTM 연결
```

| 단계 | 처리 내용 | 검증 기준 |
|:---:|:---|:---|
| 1 | 이해관계자와 업무 목표 식별 | 누락 stakeholder 0건 |
| 2 | 인터뷰·워크숍·프로토타입 수행 | 요구 출처 기록률 100% |
| 3 | 기능·비기능 요구와 제약 분류 | NFR 수치화 비율 90% 이상 |
| 4 | SRS와 acceptance criteria 작성 | SMART, INVEST 기준 |
| 5 | baseline과 RTM 설정 | 요구-테스트 매핑 100% |

> 요약: 요구사항은 수집 후 분류·검증·기준선·추적성까지 완료되어야 개발 입력으로 사용할 수 있다.

---

## Ⅳ. 특징

| 구분 | 미흡한 요구 처리 | 요구사항 분석 적용 | 수치·판단 포인트 |
|:---|:---|:---|:---|
| 표현 | 모호한 자연어 | SRS, user story, acceptance criteria | SMART 충족률 90% 이상 |
| 품질속성 | 개발 중 해석 | 응답시간, 가용성, 보안 기준 수치화 | p95 300ms, 가용성 99.9% |
| 변경 | 구두 요청 반영 | CCB, impact analysis | 변경 승인 리드타임 2일 이내 |
| 검증 | 테스트 단계에서 해석 | RTM 기반 test case 연결 | 매핑률 100% |

> 요약: 요구사항 분석의 가치는 요구를 검증 가능한 문장과 테스트 기준으로 전환하는 데 있다.

---

## Ⅴ. 심화 비교 및 적용 판단

| 비교 축 | Traditional SRS | Agile User Story | 선택 기준 |
|:---|:---|:---|:---|
| 문서 형태 | 상세 요구사항 명세 | As a/I want/So that | 규제·계약이면 SRS |
| 변경 대응 | baseline과 CCB | backlog refinement | 요구 변경률 높으면 story 방식 |
| 검증 | 요구 ID별 테스트 | acceptance criteria | RTM은 두 방식 모두 필요 |

> 요약: 문서 형식은 달라도 검증 가능한 수용 기준과 추적성은 모든 방식의 공통 조건이다.

| 리스크 | 원인 | 대응 방안 | 확인 지표 |
|:---|:---|:---|:---|
| 요구 누락 | stakeholder 식별 부족 | stakeholder map, workshop | 누락 요구 발견 건수 |
| 범위 확산 | 우선순위 부재 | MoSCoW, WSJF, CCB | scope change rate 10% 이하 |
| 검증 불가 | NFR 미수치화 | 품질속성 scenario 작성 | NFR 수치화 비율 90% 이상 |

> 요약: 요구사항 리스크는 누락, 범위 확산, 검증 불가 요구를 지표로 관리해야 한다.

| 점검 항목 | 목표 기준 | 측정 방법 |
|:---|:---|:---|
| 명세 품질 | 모호 요구 0건, SMART 충족률 90% 이상 | SRS review checklist |
| 추적성 | 요구-설계-테스트 매핑 100% | RTM, ALM |
| 변경 관리 | 변경 승인 리드타임 2일 이내 | CCB log, impact report |

> 요약: 요구사항 품질은 명세 명확성, 추적성, 변경 통제 지표로 검증한다.

---

## Ⅵ. 실무 적용 및 결론

**적용 방안 3개 (필수 - 단계별 또는 항목별):**
1. Stakeholder map과 RACI를 먼저 작성하고 인터뷰·워크숍·프로토타입으로 요구 출처를 100% 기록
2. 기능 요구와 NFR을 분리하고 성능 p95, 가용성 99.9%, 접근통제 RBAC처럼 수치·기술 기준으로 명세
3. SRS, user story, acceptance criteria, test case를 RTM으로 연결해 변경 영향 분석과 회귀 테스트 범위를 산정

**결론 (2줄):**
- 기술사 판단: 규제·계약형은 SRS+RTM, 제품 탐색형은 user story+acceptance criteria를 적용하되 추적성은 공통으로 확보함
- 향후 방향: 요구사항 분석은 ALM, model-based engineering, AI 요구 분석 보조와 결합되어 누락 탐지와 영향 분석 자동화로 발전함
