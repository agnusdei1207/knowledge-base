# 📖 【암기용】 개념 완전 이해

## 한눈에
- **개요**: **고가용성(High Availability, HA)** 설계는 서버나 네트워크에 장애가 발생하더라도 사용자 서비스가 중단 없이 지속되도록 시스템을 다중(이중화) 구성하는 아키텍처 방식이다. 대표적으로 Active-Active와 Active-Standby가 있다.
- **왜 필요한가**: 하나의 서버로만 서비스를 운영(단일 장애점, SPOF)하면 해당 장비 고장 시 전체 비즈니스가 멈춘다. 특히 24시간 365일 무중단이 필요한 시스템에서는 중단 시간(Downtime)이 막대한 금전적 손실로 직결된다.
- **핵심 직관**: 식당의 요리사 배치에 비유할 수 있다. 요리사 두 명이 쉴 새 없이 주문을 나눠서 쳐내면 Active-Active. 한 명만 요리하고 다른 한 명은 옆에서 칼만 갈며 대기하다가, 첫 번째 요리사가 쓰러지면 바로 투입되는 것이 Active-Standby다.

## 핵심 용어 정리

| 용어/표기 | 의미 | 비유·예 |
|:---|:---|:---|
| Active-Active | 두 대 이상의 장비가 모두 서비스(부하)를 동시에 분산 처리하는 방식 | 양방향 4차선 도로 (두 차선 모두 주행 중) |
| Active-Standby | 한 대는 서비스, 나머지 장비는 대기 상태로 유지하다가 장애 시 전환되는 방식 | 예비 타이어 (펑크 나면 교체 투입) |
| Failover (페일오버) | 주 장비 장애 시 대기 장비로 서비스가 자동으로 넘어가는 동작 | 주전 선수 부상 시 후보 선수 즉각 투입 |
| Heartbeat (하트비트) | 장비 간에 서로 살아있는지 상태 체크하는 신호 | 주기적으로 "너 살아있니?" 핑을 보내는 것 |

## 깊이 이해
- **배경·문제의식**: 서비스 무결성을 보장하기 위해 하드웨어나 소프트웨어에 '단일 장애점(SPOF)'이 없도록 모든 계층(L4, 웹, WAS, DB)을 이중화해야 한다. 그러나 DB 같은 데이터 저장소의 이중화는 데이터 동기화(정합성) 문제로 인해 까다롭다.
- **작동 원리**:
  - **Active-Active (A-A)**: L4 로드밸런서가 트래픽을 두 대의 서버로 분산한다. 성능(처리량)이 2배가 되며 낭비되는 자원이 없다. 단, 두 서버 간의 세션 공유 및 DB 동기화 설계가 매우 복잡하고 비용이 높다.
  - **Active-Standby (A-S)**: 1대만 서비스하므로 세션이나 데이터 동기화 충돌 위험이 적다(설계 단순). 하지만 대기 서버 자원이 평소에 낭비되며, 장애 발생 시 전환(Failover)될 때 일시적인 세션 끊김이나 지연이 발생할 수 있다.
- **구체 예시**:
  - 웹 서버(무상태, Stateless) 계층은 쉽게 확장이 가능해 대부분 Active-Active 구조를 쓴다.
  - 관계형 DB(RDBMS) 계층은 데이터 쓰기 충돌을 막기 위해 주로 Active-Standby 구조를 채택한다 (읽기 부하 분산을 위한 Read-Replica는 예외). Oracle RAC처럼 DB단에서 A-A를 구현하려면 고가의 공유 스토리지와 복잡한 클러스터 소프트웨어가 필요하다.
- **흔한 오해·주의점**: Active-Active로 구성했다고 해서 두 서버 사용률을 90%씩 쓰면 안 된다. 한쪽 서버가 죽었을 때 나머지 한쪽이 전체 부하(180%)를 받아내야 하므로 연쇄 다운이 일어날 수 있다. 평소 부하를 40~50% 이하로 유지해야 진정한 고가용성이 보장된다.

## 연결 개념
- 자동 페일오버 (Auto Failover)
- 단일 장애점 SPOF 제거
- 재해 복구 RTO·RPO
- 무상태 아키텍처 (Stateless Architecture)

# 📝 【답안용】 시험 답안 템플릿

## 핵심 인사이트 (3줄 요약)

> 1. **본질**: 고가용성(HA) 설계는 단일 장애점(SPOF)을 제거하기 위해 리소스를 다중화하여, 장애 시에도 서비스 연속성을 보장(가용성 99.99% 이상)하는 아키텍처 원칙이다.
> 2. **가치**: 예측 불가능한 하드웨어 장애나 네트워크 단절 시나리오에서 시스템 중단 시간(Downtime)과 RTO(복구 목표 시간)를 최소화하여 비즈니스 손실을 방지한다.
> 3. **판단 포인트**: 시스템 레이어 특성(상태 유지 여부)과 예산에 맞춰 리소스 효율이 높은 Active-Active와 데이터 정합성 유지가 유리한 Active-Standby를 계층별로 전략 혼용해야 한다.

## 출제 의도 및 답안 포인트

| 출제 의도 | 반드시 짚을 핵심 | 감점 회피 포인트 |
|:---|:---|:---|
| HA 이중화 방식의 비교 판단 기준 이해 | Active-Active vs Active-Standby 구조 차이 및 특장점 비교 | 방식 이름만 쓰고 데이터 정합성/세션 동기화 이슈 누락 |
| 아키텍처 계층별 이중화 설계 역량 확인 | 무상태 Web/WAS 계층 (A-A) vs 상태 유지 DB 계층 (A-S/A-A) 매핑 | 모든 계층을 맹목적으로 Active-Active로 설계한다고 서술 |

> 요약: Active-Active와 Active-Standby의 트레이드오프(리소스 효율 vs 정합성)를 비교하고, 웹-앱-DB 계층별 최적 이중화 방안을 설계 관점에서 제시해야 한다.

## Ⅰ. 개요 및 필요성

- 개요: 고가용성 설계는 시스템 구성 요소를 다중화하여 일부 노드 장애 시에도 전체 서비스 가용성(Availability)을 보장하는 무중단 아키텍처 기법임
- 배경: 디지털 전환 심화로 시스템 중단이 대규모 금전 피해와 신뢰 하락으로 직결되며, SLA(서비스 수준 계약) 99.99% 이상 보장 요구 증대
- 필요성: 단일 장애점(SPOF) 제거, 트래픽 폭증 시 부하 분산, 재해 대비 신속한 페일오버 처리를 위해 철저한 이중화 설계가 요구됨

---

## Ⅱ. 구조 및 구성요소

```text
[계층별 고가용성 혼합 아키텍처]
클라이언트 -> L4 Switch (Active-Standby) -> 분산 처리
             |            |
         Web/WAS 1    Web/WAS 2 (Active-Active, 부하 분산)
             |            |
            DB 1 (주) -> DB 2 (대기) (Active-Standby, 동기화)
```

| 구성 방식 | 아키텍처 특징 | 주요 메커니즘 |
|:---|:---|:---|
| Active-Active (A-A) | 모든 노드가 동시에 서비스 트래픽을 처리함 | 로드 밸런싱 분산, 세션 클러스터링 필수 |
| Active-Standby (A-S) | Primary 노드 서비스 중 Secondary 노드는 대기 상태 유지 | Heartbeat 체크를 통한 상태 감시, Failover |
| Active-Standby (Mutually) | 서로 다른 서비스의 주 노드 역할을 교차로 수행 | 평소에는 각자 주 업무 처리, 장애 시 상호 인수 |

> 요약: 고가용성 구성은 트래픽을 분산 처리하는 Active-Active와 예비 자원을 대기시키는 Active-Standby 방식으로 구분된다.

---

## Ⅲ. 동작원리 및 흐름도

```text
Heartbeat 모니터링 -> 이상 징후/장애 감지 -> Failover 트리거 -> 트래픽 우회 및 서비스 재개
```

- 1단계 [상태 감시]: L4 스위치 또는 HA 클러스터 솔루션이 각 노드 간 Ping, Heartbeat 신호로 정상 가동 여부를 실시간 확인
- 2단계 [장애 인지]: 주 노드(Active)의 응답 지연 시간 초과 또는 포트 다운 시 장애 상황으로 선언
- 3단계 [페일오버 처리]:
  - (A-A) 장애 노드를 로드 밸런싱 풀에서 제외하고 정상 노드로 트래픽 전량 분배
  - (A-S) Standby 노드를 Active로 승격, 가상 IP(VIP) 및 스토리지 제어권 탈취(Takeover)
- 4단계 [서비스 지속]: 사용자 세션 끊김을 최소화하며 후속 트래픽 정상 처리 및 경보 발송

> 요약: 실시간 헬스 체크로 노드 다운을 인지한 즉시, 로드밸런싱 풀 제외 또는 가상 IP(VIP) 인계를 통해 가용 자원으로 트래픽을 자동 전환한다.

## Ⅳ. 특징

| 구분 | Active-Active 방식 | Active-Standby 방식 |
|:---|:---|:---|
| 성능/리소스 활용 | 전체 리소스 100% 활용, 성능 향상(Scale-out) 효과 | Standby 자원 유휴 상태 (비용 대비 비효율) |
| 장애 전환 지연(RTO) | 무중단 수준 (0초 근접), 세션 유지 시 영향 최소화 | VIP 전환 및 DB 복구 시간에 따른 일시적 중단 발생 |
| 설계/운영 복잡도 | 세션 공유/동기화(DB Lock 충돌 등) 고려 복잡 | 단일 처리로 정합성 보장 용이, 아키텍처 단순 |
| 적용 권장 계층 | Stateless 계층 (Web, API Gateway, 프론트엔드) | Stateful 계층 (RDBMS 쓰기 마스터, 방화벽) |

> 요약: Active-Active는 자원 효율과 복구 속도가 우수하나 설계가 복잡하며, Active-Standby는 리소스가 낭비되지만 데이터 무결성을 보장하기 쉽다.

## Ⅴ. 심화 비교 및 적용 판단

**아키텍처 적용 선택 기준:**
- 무상태 서버(Stateless) 인가? → 상태 비저장 Web/WAS는 조건 없이 **Active-Active** 적용 (쿠버네티스 ReplicaSet 활용)
- 데이터 쓰기 정합성이 핵심인가? → RDBMS 등 트랜잭션이 엄격한 저장소는 복잡도와 Split-Brain(양쪽 모두 마스터가 되는 현상) 회피를 위해 기본 **Active-Standby** 적용
- 읽기 부하가 압도적인가? → DB Master(쓰기, Active) - DB Slave 복수 대수(읽기 전용, Active) 기반의 **CQRS / Read Replica 혼합형** 적용

**리스크·대응 (기본 불릿):**
- Split-Brain 현상: 네트워크 단절 시 A-S 환경에서 양쪽 노드가 자신이 마스터라고 판단하여 데이터 변조 발생 → 제3의 판단 서버(Quorum/Tie-breaker) 구성 및 Fencing(스토리지 강제 격리) 도입
- A-A 캐스케이딩(연쇄) 다운 장애: A-A 환경에서 1개 노드 다운 시 남은 1개 노드에 2배 부하가 쏠려 동반 다운 발생 → 평시 노드당 자원 사용률 50% 미만 유지 여력 확보, 서킷 브레이커 도입

## Ⅵ. 실무 적용 및 결론

**적용 방안 3개:**
1. **클라우드 네이티브 기반 Multi-AZ 구성**: 퍼블릭 클라우드의 가용 영역(AZ) 2개 이상에 Web/WAS 인스턴스를 분산 배치(Active-Active)하여 단일 데이터센터 장애에 대비
2. **세션 외부 저장소 구성(Stateless화)**: Active-Active 환경에서 노드 간 세션 클러스터링 부하를 줄이기 위해 세션 정보를 애플리케이션 내부 메모리가 아닌 Redis/Memcached 기반 외부 캐시로 분리 설계
3. **오토 스케일링(HPA) 연계 무중단 확장**: 고정된 Active 대수에 얽매이지 않고, 트래픽 임계치 도달 시 컨테이너 파드를 자동 증설하여 A-A 자원을 유연하게 확장

**결론:**
- 기술사 판단: 완벽한 99.999% 시스템 가용성을 위해서는 단순 서버 이중화를 넘어 네트워크, 전력, 스토리지 전 계층의 SPOF를 검토하고 Stateless 사상에 기반한 설계를 우선해야 함
- 향후 방향: 모놀리식 아키텍처의 인프라 레벨 클러스터링(A-A/A-S) 중심에서 마이크로서비스(MSA) 기반의 소프트웨어적 자가 치유(Self-Healing) 및 글로벌 서버 부하 분산(GSLB) 기반 멀티 리전 아키텍처로 고도화되고 있음
