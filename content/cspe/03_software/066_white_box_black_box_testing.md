# 📖 【암기용】 개념 완전 이해

> 목적: 화이트박스와 블랙박스 테스트를 검증 관점 차이로 이해하게 만든다. 시험 답안 양식이 아니라, 이해를 위한 설명이다.

## 한눈에
- **개요**: **화이트박스 테스트**와 **블랙박스 테스트**는 테스트 케이스를 설계할 때 무엇을 **테스트 기준(Test Basis)**으로 삼는지에 따라 나뉘는 두 검증 관점이다 — 화이트박스는 소스코드의 내부 구조를, 블랙박스는 요구사항 명세를 기준으로 삼는다.
- **왜 필요한가**: 코드 내부 경로를 모두 실행해 보여도(화이트박스), 애초에 요구사항을 잘못 이해했거나 기능이 누락됐다면 발견하지 못한다. 반대로 명세대로 입출력만 확인해도(블랙박스), 코드 내부에 실행되지 않는 죽은 경로나 예외 처리 누락은 잡지 못한다. 두 관점을 함께 써야 테스트 케이스가 놓치는 사각지대가 줄어든다.
- **핵심 직관**: 화이트박스는 "코드가 갈 수 있는 모든 길을 다 밟아봤는가"를 묻고, 블랙박스는 "입력을 넣었을 때 명세서대로 결과가 나오는가"를 묻는다. 기준이 다르므로 같은 프로그램을 테스트해도 서로 다른 결함이 걸린다.

## 핵심 용어 정리
| 용어 | 의미 | 비유 |
|:---|:---|:---|
| 테스트 기준 (Test Basis) | 테스트 케이스를 만들 때 근거로 삼는 대상 — 코드 구조 또는 명세서 | 채점 기준표 |
| 화이트박스 테스트 | 소스코드 내부 구조(제어흐름·데이터흐름)를 기준으로 하는 테스트 | 투명한 상자 안을 보고 검사 |
| 블랙박스 테스트 | 내부 구조를 모른 채 입력·출력·명세만으로 하는 테스트 | 뚜껑 닫힌 상자를 겉에서 검사 |
| 테스트 오라클 (Test Oracle) | 실행 결과가 맞는지 판정하는 기준 — 요구사항, 설계서, 정책 등 | 정답지 |
| 커버리지 (Coverage) | 화이트박스 테스트가 코드를 얼마나 실행했는지의 비율 | 밟은 바닥의 비율 |
| 커버리지 착시 (Coverage Illusion) | 코드는 실행됐지만 결과 검증(assertion)이 없어 실제로는 결함을 못 잡는 상태 | 지나가기만 하고 채점은 안 함 |
| 요구사항 추적표 (RTM) | 각 요구사항이 어떤 테스트 케이스로 커버되는지 매핑한 표 | 항목별 체크리스트 |
| 뮤테이션 테스트 (Mutation Testing) | 코드를 일부러 변형(고장)시켜 테스트가 그 변형을 잡아내는지로 assertion 품질을 검증하는 기법 | 일부러 오답을 끼워넣고 채점자가 걸러내는지 확인 |
| 리스크 기반 테스트 (Risk-based Testing) | 결함 발생 시 영향이 큰 영역에 테스트 자원을 우선 배분하는 전략 | 위험한 곳부터 순찰 |

## 깊이 이해

### 왜 "기준(Basis)"이라는 틀로 구분하는가
화이트박스와 블랙박스는 테스트 단계(단위/시스템 같은)의 이름이 아니라, 테스트 케이스를 만들 때 "무엇을 보고 케이스를 뽑아내는가"의 기준 차이다. 화이트박스는 소스코드 자체가 기준이므로 코드를 열어볼 수 있어야 적용 가능하고, 블랙박스는 요구사항 명세서가 기준이므로 코드를 몰라도 적용할 수 있다. 같은 단위 테스트도 화이트박스 방식(내부 분기를 보고 케이스 설계)으로 만들 수 있고, 같은 시스템 테스트도 명세 기반(블랙박스)으로 만들 수 있어, 두 축은 테스트 레벨과는 독립적인 분류다.

### 커버리지 착시 — 실행됐다고 검증된 것은 아니다
화이트박스 테스트에서 구문 커버리지가 100%라는 것은 코드의 모든 줄이 최소 1번 실행됐다는 뜻일 뿐, 그 실행 결과가 기대값과 맞는지(assertion) 확인했다는 뜻은 아니다. 예를 들어 `result = calculate(x)`만 호출하고 `assertEquals` 검증을 빠뜨리면, 코드는 100% 실행되어도 결함은 하나도 못 잡는다. 이 문제를 검증하는 방법이 뮤테이션 테스트다 — 소스코드의 연산자를 하나 일부러 바꿔서(`+`를 `-`로) 고장 낸 코드를 만들고, 기존 테스트가 이 고장을 잡아내는지(테스트 실패로 이어지는지) 측정한다. 예를 들어 뮤테이션 100개 중 70개를 테스트가 잡아내면 뮤테이션 점수(Mutation Score)는 70%이며, 이 수치가 낮으면 구문·분기 커버리지 숫자가 높아도 assertion 품질이 부실하다는 뜻이다.

### 명세 기반 테스트와 요구사항 추적표(RTM)
블랙박스 테스트는 요구사항 명세서에 있는 항목 하나하나가 테스트 케이스로 커버됐는지를 요구사항 추적표(Requirements Traceability Matrix, RTM)로 관리한다. 예를 들어 요구사항이 50개인데 테스트 케이스가 30개 요구사항만 커버한다면 RTM 커버리지는 60%이며, 나머지 40%(20개 요구사항)는 검증되지 않은 채 남아 있다는 뜻이다. 화이트박스의 코드 커버리지가 "코드를 얼마나 밟았는가"를 재는 것과 대칭으로, RTM은 "요구사항을 얼마나 검증했는가"를 잰다.

### 리스크 기반으로 테스트 자원을 배분하는 이유
모든 코드 경로와 모든 요구사항을 똑같은 강도로 테스트하는 것은 비현실적이다(경로 수는 반복문이 있으면 사실상 무한대로 발산한다). 그래서 결함이 발생했을 때 피해가 큰 영역(예: 결제, 인증)에는 화이트박스의 분기 커버리지 기준을 높이고 블랙박스의 경계값 케이스를 촘촘히 두는 반면, 위험이 낮은 영역(단순 조회 화면)은 기준을 낮춰 테스트 자원을 리스크에 비례해 배분한다.

### 비유
화이트박스는 자동차를 만든 정비사가 보닛을 열고 부품 하나하나가 도면대로 조립됐는지 확인하는 것이고, 블랙박스는 구매자가 시동을 걸고 계기판이 카탈로그에 적힌 대로 작동하는지만 확인하는 것이다. 정비사가 아무리 부품을 꼼꼼히 봐도 카탈로그에 있는 기능 자체를 안 달았다면(요구사항 누락) 정비사 점검(화이트박스)으로는 못 잡고, 구매자가 그 기능을 써봤을 때(블랙박스)만 드러난다.

# 📝 【답안용】 시험 답안 템플릿

> 목적: 시험장에서 25분에 그대로 쓰는 답안 양식. 작성방식(추상표현 금지·수치·도식·문제유형 전환)을 엄격히 지킨다.
> 핵심: 화이트박스와 블랙박스는 우열 관계가 아니라 내부 구조 결함과 요구사항 결함을 서로 다른 기준으로 찾는 보완 관계임.

## 핵심 인사이트 (3줄 요약)

> 1. **본질**: 화이트박스 테스트는 내부 구조와 코드 경로를, 블랙박스 테스트는 명세와 입출력 행위를 기준으로 결함을 찾는 기법임.
> 2. **가치**: coverage와 명세 기반 기법을 조합해 코드 미실행 경로와 요구사항 누락을 동시에 줄임.
> 3. **판단 포인트**: statement/branch/path coverage와 equivalence/boundary/decision table을 비교축으로 제시해야 함.

## 출제 의도 및 답안 포인트

| 출제 의도 | 반드시 짚을 핵심 | 감점 회피 포인트 |
|:---|:---|:---|
| 테스트 관점 차이 확인 | 내부 구조 기반 vs 명세 기반 | 둘을 테스트 단계명으로 오해 |
| 기법 적용 역량 확인 | coverage, path, equivalence, boundary | 장단점만 추상 서술 |
| 선택 기준 확인 | 단위·통합·시스템 테스트별 조합 | 한 기법만 적용한다고 단정 |

> 요약: 이 문제는 테스트 관점별 설계 기준과 적용 위치를 비교하는 답안이 필요하다.

## Ⅰ. 개요 및 필요성

- 개요: 구조·명세 기반 테스트 구분
- 배경: 코드 실행 경로가 통과돼도 요구사항 해석이 틀릴 수 있고, 명세 기반 테스트만으로는 내부 예외 경로와 분기 누락이 남을 수 있다.
- 필요성: 화이트박스의 문장·분기 커버리지와 블랙박스의 동등분할·경계값 분석을 조합해 결함 발견 범위를 분리 검증한다.

---

## Ⅱ. 구조 및 구성요소

```text
Test Basis
  / Code Structure -> White-box -> Coverage/Path
  / Specification -> Black-box -> Input/Output/State
Test Result -> Defect Report -> Retest/Regression
```

| 구성요소 | 역할 | 특이사항 |
|:---|:---|:---|
| White-box | 코드 내부 제어흐름과 데이터흐름 검증 | statement, branch, path |
| Black-box | 명세 기반 입출력과 행위 검증 | equivalence, boundary |
| Test Oracle | 기대 결과 판단 기준 | 요구사항, 설계서, 정책 |
| Coverage/Defect | 수행 범위와 결함 기록 | coverage illusion 주의 |

> 요약: 두 기법은 테스트 기준을 코드 구조와 명세로 나누고 결과를 결함·커버리지 지표로 관리한다.

---

## Ⅲ. 동작원리 및 흐름도

```text
테스트 기준 선택 -> 케이스 설계 -> 데이터 준비
-> 실행 -> coverage/결과 측정 -> 결함 등록
-> 보완 케이스 추가
```

| 단계 | 처리 내용 | 검증 기준 |
|:---:|:---|:---|
| 1 | 코드 또는 명세 중 테스트 기준 선택 | 대상과 목적 명시 |
| 2 | 화이트박스는 경로·조건 기반 케이스 작성 | branch coverage 80% 이상 |
| 3 | 블랙박스는 동등분할·경계값 케이스 작성 | 경계값 2점 이상 포함 |
| 4 | 실행 결과와 기대 결과 비교 | 실패 재현 로그 확보 |
| 5 | 누락 영역 보완과 회귀 테스트 수행 | 신규 결함 재발 0건 |

> 요약: 테스트는 기준 선택 후 케이스를 설계하고 coverage와 결과를 측정해 누락 영역을 보완한다.

## Ⅳ. 특징

| 구분 | 화이트박스 테스트 | 블랙박스 테스트 | 수치·판단 포인트 |
|:---|:---|:---|:---|
| 기준 | 코드 내부 구조 | 요구사항·명세 | coverage vs requirement trace |
| 주요 기법 | statement, branch, path | equivalence, boundary, decision table | branch 80%, RTM 100% |
| 적용 위치 | 단위·컴포넌트 테스트 | 시스템·인수 테스트 | 테스트 피라미드 조합 |
| 한계 | 요구사항 오류 탐지 약함 | 내부 미실행 경로 확인 어려움 | 상호 보완 필요 |

> 요약: 화이트박스는 내부 경로, 블랙박스는 명세 충족을 확인하므로 단계별 조합이 필요하다.

## Ⅴ. 심화 비교 및 적용 판단

| 비교 축 | 기존/대안 | 본 키워드 | 선택 기준 |
|:---|:---|:---|:---|
| 구조 | 단일 관점 테스트 | 내부+명세 관점 조합 | 안전·금융처럼 결함 영향 큰 시스템 |
| 비용/성능 | E2E 명세 테스트 과다 | 단위 화이트박스+상위 블랙박스 | CI 10분 이하 유지 |
| 운영/위험 | 경계값 누락 | boundary와 branch 동시 확인 | 장애 RCA에서 조건 누락 반복 시 |
| 품질판정 | pass/fail 중심 | coverage+requirement trace | branch 80%, RTM 100% |

> 요약: 선택 기준은 테스트 목적, 위험도, 실행 시간이며 내부 경로와 외부 명세를 분리해 적용해야 한다.

| 리스크 | 원인 | 대응 방안 | 확인 지표 |
|:---|:---|:---|:---|
| Coverage 착시 | 실행만 되고 assertion 부족 | assertion 품질 점검, mutation test | mutation score 70% 이상 |
| 명세 누락 | 요구사항 불명확 | RTM, acceptance criteria 보완 | requirement coverage 100% |
| 경로 폭증 | path 조합 과다 | risk-based path 선정 | high-risk path 100% |
| 테스트 취약성 | 내부 구현 과도 검증 | public behavior 중심 테스트 | refactor 실패율 5% 이하 |

> 요약: 리스크는 커버리지 착시, 명세 누락, 경로 폭증이며 mutation score와 추적성으로 통제한다.

| 점검 항목 | 목표 기준 | 측정 방법 |
|:---|:---|:---|
| 구조 검증 | branch coverage 80% 이상 | JaCoCo, coverage.py |
| 명세 검증 | RTM coverage 100% | test management |
| 경계값 검증 | 주요 입력별 min/max±1 포함 | testcase review |
| 결함 유출 | escaped defect 5% 이하 | incident RCA |

> 요약: 화이트박스·블랙박스 조합 효과는 branch coverage, RTM, 경계값 포함률, 운영 유출 결함으로 확인한다.

## Ⅵ. 실무 적용 및 결론

**적용 방안 3개 (필수 — 단계별 또는 항목별):**
1. 단위 테스트는 branch coverage 80% 이상을 기준으로 화이트박스 케이스를 설계하고 복잡도 10 초과 함수는 리팩터링 대상으로 등록함.
2. 시스템·인수 테스트는 동등분할, 경계값, decision table을 사용해 요구사항별 RTM 100%를 확보함.
3. coverage 80% 이상이어도 mutation score 70% 미만이면 assertion 품질을 보완하고 결함 RCA 결과를 케이스에 추가함.

**결론 (2줄):**
- 기술사 판단: 내부 로직 위험은 화이트박스, 사용자 요구 충족은 블랙박스를 적용하며 고위험 업무는 두 기준을 모두 요구함.
- 향후 방향: AI 기반 테스트 생성도 내부 coverage와 명세 추적성을 함께 검증하는 방향으로 적용됨.
