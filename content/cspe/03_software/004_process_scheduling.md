# 📖 【암기용】 개념 완전 이해

> 목적: 이 개념을 처음 보는 사람도 완벽히 이해하게 만든다. 시험 답안 양식이 아니라, 이해를 위한 친절한 설명이다.

## 한눈에
- **개요**: **프로세스 스케줄링(Process Scheduling)**은 Ready 큐에 대기 중인 여러 프로세스 중 **어떤 프로세스에게 CPU를 넘길지 결정하는 커널의 정책**이다. CPU는 1개인데 실행 대기 프로세스는 여러 개 쌓여 있을 때 "다음 순번을 누구로 할 것인가"를 정하는 규칙이다.
- **왜 필요한가**: 순서만 지키면(먼저 온 순서대로) 실행 시간이 긴 프로세스 뒤에 짧은 프로세스들이 줄줄이 밀려 평균 대기시간이 폭발한다(호위 효과, Convoy Effect). 반대로 짧은 프로세스만 계속 우선 처리하면 긴 프로세스는 영원히 순서가 오지 않는다(기아 현상, Starvation). 이 둘의 균형을 맞추는 게 스케줄링 알고리즘의 존재 이유다.
- **핵심 직관**: FCFS는 온 순서대로(단순하지만 손해), SJF는 짧은 일부터(평균 대기 최소지만 미래를 모르면 불가능), RR은 짧은 시간씩 돌아가며(공평), MLFQ는 여러 등급의 줄을 두고 상황 따라 등급을 조정, CFS는 리눅스 표준으로 각자의 누적 실행 시간을 계속 비교해 가장 적게 실행된 프로세스를 우선한다.

## 핵심 용어 정리 (내부에 등장하는 것들)

| 용어 | 의미 | 비유 |
|:---|:---|:---|
| CPU 스케줄링 정책 | Ready 큐의 프로세스 중 다음 실행 대상을 고르는 규칙 | 은행 창구 번호표 규칙 |
| 선점(Preemptive) | 실행 중인 프로세스라도 조건이 되면 강제로 CPU를 뺏는 방식 | 발언 시간 초과 시 마이크 강제 회수 |
| 비선점(Non-preemptive) | 한 번 CPU를 잡으면 스스로 끝내거나 반납할 때까지 뺏지 않는 방식 | 발언자가 끝낼 때까지 기다림 |
| FCFS(First-Come First-Served) | 도착한 순서대로 실행하는 비선점 방식 | 번호표 순서대로 |
| SJF(Shortest Job First) | 실행 시간이 가장 짧은 프로세스부터 실행 | 짧은 용무부터 처리 |
| RR(Round Robin) | 고정된 타임 퀀텀만큼씩 돌아가며 실행하는 선점 방식 | 발언 시간을 똑같이 나눠 번갈아 발언 |
| 타임 퀀텀(Time Quantum) | RR에서 한 프로세스에게 한 번에 주는 최대 CPU 점유 시간 | 발언 제한 시간 |
| MLFQ(Multi-Level Feedback Queue) | 우선순위가 다른 여러 큐를 두고, 실행 이력에 따라 큐를 옮기는 방식 | VIP 줄·일반 줄로 나뉜 대기열 |
| CFS(Completely Fair Scheduler) | 리눅스 표준 스케줄러. 가상 실행 시간이 가장 적은 프로세스를 트리에서 골라 실행 | 지금까지 가장 적게 먹은 사람에게 먼저 배식 |
| vruntime | CFS가 계산하는 가상 실행 시간 — 우선순위(가중치)를 반영해 보정한 누적 실행량 | 보정된 식사량 장부 |
| 호위 효과(Convoy Effect) | 긴 프로세스 하나 때문에 뒤따르는 짧은 프로세스들이 줄줄이 대기가 길어지는 현상 | 트럭 한 대에 막힌 뒤차 행렬 |
| 기아 현상(Starvation) | 특정 프로세스가 계속 순번에서 밀려 CPU를 영원히 못 받는 현상 | 계속 새치기당해 못 들어가는 손님 |
| 에이징(Aging) | 오래 기다린 프로세스의 우선순위를 시간이 지날수록 높여 기아를 막는 기법 | 오래 기다린 손님부터 우선권 부여 |
| 대기시간(Waiting Time) | 프로세스가 Ready 큐에서 대기한 총 시간 | 줄 서서 기다린 시간 |
| 반환시간(Turnaround Time) | 프로세스가 도착해서 완료될 때까지 걸린 전체 시간 | 도착부터 볼일 끝까지 걸린 총 시간 |

## 깊이 이해

### FCFS의 한계 — 호위 효과를 수치로 보기
- 프로세스 A(실행시간 100), B(1), C(1)가 이 순서로 도착했다고 하자. FCFS는 도착 순서대로 실행하므로 A(0~100) → B(100~101) → C(101~102) 순으로 처리된다.
- 대기시간은 A=0, B=100, C=101이다. 평균 대기시간 = (0+100+101)/3 ≈ 33.7. B와 C는 각자 1만큼만 일하면 되는데 A 때문에 100 가까이 기다려야 한다 — 이것이 호위 효과다.

### SJF가 이론적으로 최적인 이유 — 같은 예로 비교
- 같은 A(100), B(1), C(1)를 실행 시간이 짧은 순서(B→C→A)로 바꿔 실행하면 대기시간은 B=0, C=1, A=2다. 평균 대기시간 = (0+1+2)/3 = 1.
- FCFS의 평균 33.7과 비교하면 압도적으로 짧다. 이것이 "SJF가 평균 대기시간을 최소화하는 이론적 최적 알고리즘"이라 불리는 이유다.
- 그러나 SJF는 실행하기 전에 "이 프로세스가 얼마나 걸릴지"를 미리 알아야 하는데, OS는 미래를 알 수 없다. 그래서 SJF는 실제 구현이 어려운 이론적 비교 기준이며, 실무에서는 과거 실행 이력으로 다음 실행 시간을 추정하는 근사 기법을 쓴다. 또한 짧은 프로세스가 계속 새로 들어오면 긴 프로세스는 영원히 순서가 안 와 기아 현상이 발생한다.

### RR — 타임 퀀텀 크기가 성능을 가른다
- 타임 퀀텀 4인 RR로 A(24), B(3), C(3)를 실행하면: A(0~4), B(4~7, 완료), C(7~10, 완료), A(10~24, 남은 14 실행). B와 C는 각각 4~7 이내에 끝나 응답이 빠르고, A도 결국 24 시점에 끝난다.
- 퀀텀을 아주 크게(예: 1000) 잡으면 사실상 FCFS와 같아져 호위 효과가 재현된다. 반대로 퀀텀을 극단적으로 작게(예: 0.1) 잡으면, 실행 시간보다 컨텍스트 스위칭(002) 자체에 드는 시간 비중이 커져 CPU가 실제 연산 대신 스위칭만 반복하는 스레싱이 발생한다. 그래서 실무에서는 퀀텀을 스위칭 비용의 수십~수백 배 수준(예: 10ms~100ms)으로 잡아 스위칭 오버헤드 비중을 1% 안팎으로 억제한다.

### MLFQ — 여러 큐로 나눠 CPU/I/O 성향을 자동 구분
- MLFQ는 우선순위가 다른 여러 개의 큐를 두고, 새 프로세스는 가장 높은 우선순위 큐에서 시작한다.
- 타임 퀀텀을 다 써버리면(=CPU를 오래 쓰는 연산 위주 프로세스로 판단) 한 단계 낮은 큐로 강등한다. 반대로 타임 퀀텀을 다 쓰기 전에 I/O 요청 등으로 스스로 CPU를 반납하면(=응답성이 중요한 대화형 프로세스로 판단) 원래 큐를 유지하거나 승격시킨다.
- 하위 큐에서 오래 대기한 프로세스는 기아를 막기 위해 일정 주기마다 최상위 큐로 강제 승격(부스트)시킨다 — 이것이 에이징의 구체적 구현이다.

### CFS — vruntime을 수치로 이해
- 리눅스 CFS는 프로세스마다 vruntime(가상 실행 시간)을 누적하고, 레드-블랙 트리에서 vruntime이 가장 작은 프로세스를 항상 다음 실행 대상으로 고른다.
- 우선순위가 기본값(`nice=0`, 가중치 1024)인 프로세스가 10ms를 실행하면 vruntime도 그대로 10ms만큼 증가한다. 반면 `nice`를 낮춰(우선순위를 높여) 가중치가 2048로 두 배가 된 프로세스는 같은 10ms를 실행해도 vruntime이 절반인 5ms만 증가한 것으로 계산된다 — 그만큼 트리에서 왼쪽(우선 실행 대상)에 더 오래 머문다.
- 오래 대기해 실행을 못 받은 프로세스는 vruntime이 상대적으로 작아진 채로 남아있으므로, 트리에서 자연스럽게 왼쪽(우선순위 1순위)으로 밀려나 자동으로 구제된다. 별도의 에이징 로직 없이 수식 자체가 기아를 방지하는 구조다.

### 비유와 흔한 오해
- **비유**: 은행 창구에서 1시간 걸리는 대출 상담 손님 뒤에 10초짜리 송금 손님 100명이 줄을 서면 폭동이 난다(FCFS의 호위 효과). 반대로 송금 손님만 계속 새치기시키면 대출 손님은 하루 종일 순서가 안 온다(SJF의 기아 현상). RR은 모든 손님에게 균등하게 발언 시간을 나눠 이 둘의 절충안을 취한다.
- **오해**: "SJF가 제일 좋으니 실무에서도 SJF를 쓰면 된다"는 착각이다. 실행 전 미래의 실행 시간을 정확히 알 방법이 없으므로 순수 SJF는 실무에서 구현 불가능한 이론적 하한선(비교 기준)일 뿐이며, 실제 OS는 RR·MLFQ·CFS 같은 근사·절충 알고리즘을 쓴다.

## 연결 개념
- **컨텍스트 스위칭(002)**: 선점형 알고리즘(RR·MLFQ·CFS)이 동작하려면 매 타임 퀀텀마다 컨텍스트 스위칭이 필요하다. 스위칭 비용과 퀀텀 길이의 트레이드오프가 스케줄러 튜닝의 핵심 변수다.
- **프로세스 생명주기(003)**: 스케줄링은 Ready 큐에 쌓인 프로세스 중 Dispatch(Ready→Running) 대상을 고르는 정책이며, Timeout(Running→Ready)이 선점형 스케줄링의 구체적 구현이다.
- **동시성(001)**: 스레드 단위로 스케줄링하는 현대 OS에서는, 프로세스 안 여러 스레드가 각각 독립적으로 CFS 등의 스케줄링 대상이 되어 멀티코어에 분산 배치된다.

# 📝 【답안용】 시험 답안 템플릿

> 목적: 시험장에서 25분에 그대로 쓰는 답안 양식. 작성방식(추상표현 금지·수치·도식·문제유형 전환)을 엄격히 지킨다.
> 핵심: 이 시험은 정보를 많이 나열하는 시험이 아니라, 문제 신호어에서 출제자 의도를 읽고 핵심 논점을 선별해 쓰는 시험이다.

## 핵심 인사이트 (3줄 요약)

> 1. **본질**: Ready Queue에 대기 중인 프로세스 중 어떤 프로세스에 CPU 제어권을 넘길지 결정하는 커널의 정책 결정자(Policy Maker)다.
> 2. **가치**: 처리량(Throughput) 극대화, 응답 시간(Response Time) 최소화, 그리고 기아 상태(Starvation) 방지라는 상충하는 목표 사이의 트레이드오프를 튜닝한다.
> 3. **판단 포인트**: 단순 비선점형(FCFS)의 호위 효과 한계를 짚고, 이를 선점형(RR)으로 분해한 뒤, 최종적으로 동적 우선순위 기반의 복합 모델(MLFQ, CFS)로 수렴하는 아키텍처 진화 과정을 증명해야 한다.

## 출제 의도 및 답안 포인트

| 출제 의도 | 반드시 짚을 핵심 | 감점 회피 포인트 |
|:---|:---|:---|
| 알고리즘별 맹점과 한계 진단 | 호위 효과(Convoy, FCFS), 기아 현상(Starvation, SJF) | 타임 퀀텀 극단값에 따른 RR의 성능 변화(FCFS화 vs 스레싱) 누락 |
| 현대 OS로의 진화 메커니즘 도출 | 응답성(I/O 바운드)과 처리량(CPU 바운드)의 융합 | CFS를 단순히 트리 자료구조로만 적고 vruntime 개념을 빼먹는 실수 |

> 요약: 스케줄링의 역사는 "긴 놈 때문에 짧은 놈이 피 보는 현상(호위)"을 막고, 반대로 "짧은 놈만 대우하다 긴 놈이 굶어 죽는 현상(기아)"을 막기 위한 위대한 핑퐁 게임이다.

## Ⅰ. 개요 및 필요성

- 정의: 다중 프로그래밍 환경에서 CPU라는 단일 자원을 여러 프로세스가 공유할 때, 실행 순서와 점유 시간(Time Quantum)을 결정하는 커널 알고리즘
- 배경: 일괄 처리(Batch) 중심의 비선점형 방식은 대화형 시스템(마우스, 키보드)의 즉각적인 응답성을 보장할 수 없었음
- 필요성: 시스템의 평균 대기시간을 수학적으로 최소화하면서도, 특정 프로세스가 무한 대기(Starvation)에 빠지는 불평등을 막기 위한 동적 피드백 로직 필수

## Ⅱ. 고전적 스케줄링 아키텍처 비교 (비선점 vs 선점)

```text
[ 호위 효과 (Convoy Effect) 발생 도식 ]
CPU --- [ 100초짜리 A ] --- [ 1초짜리 B ] --- [ 1초짜리 C ] (대기 큐)
* B와 C는 단 1초면 끝나는데 A 때문에 100초를 낭비함. 전체 평균 대기시간 폭발.

[ 라운드 로빈 (RR) 선점 분해 도식 ]
CPU --- [ A 10초 ] -> [ B 1초 (완료) ] -> [ C 1초 (완료) ] -> [ A 10초 ] ...
* B와 C가 10초 퀀텀 안에 즉시 응답을 받고 퇴장. 대화형 시스템의 승리.
```

| 기법 명칭 | 할당 및 선점 룰 | 한계점 및 치명적 버그 |
|:---|:---|:---|
| **FCFS** (First-Come) | 큐에 먼저 들어온 순서대로 무조건 끝까지 실행 (비선점) | 거대한 프로세스 하나가 큐 전체의 속도를 마비시키는 **호위 효과(Convoy Effect)** |
| **SJF** (Shortest-Job) | 미래의 남은 실행 시간이 가장 짧은 프로세스 먼저 (비선점/선점) | 긴 프로세스는 영원히 CPU를 받지 못하는 **기아 현상(Starvation)** 발생 |
| **RR** (Round Robin) | 고정된 타임 퀀텀(예: 10ms)마다 강제로 선점하여 큐 맨 뒤로 쫓아냄 | 타임 퀀텀이 너무 작으면 잦은 문맥 교환으로 **스위칭 스레싱(Thrashing)** 폭발 |

> 요약: 이론적으로 평균 대기시간은 SJF가 최고지만 미래를 예측할 수 없기에 불가능하다. 그래서 차악으로 선택한 것이 "조금씩 평등하게 자르는" RR이다.

---

## Ⅲ. 현대 운영체제의 융합 스케줄링 (MLFQ와 CFS)

단순 RR만으로는 I/O 대화형 프로세스(VIP)와 백그라운드 인코딩(일반)을 구분할 수 없다. 이를 극복한 현대 커널의 2대 표준이다.

| 최신 알고리즘 | 핵심 철학 및 동작 메커니즘 | 에이징 (Aging/구제책) 로직 |
|:---|:---|:---|
| **MLFQ** <br>(Multi-level Feedback Queue) | 여러 개의 큐를 층층이 쌓음. 타임 퀀텀을 다 쓰면(CPU 바운드) 하위 큐로 강등시키고, I/O로 반납하면 상위 큐 유지 (동적 신분 변화) | 하위 큐에서 오랫동안 굶은 프로세스를 특정 주기마다 최상단 큐로 일괄 부스트(Boost) |
| **CFS** <br>(Completely Fair Scheduler) | 우선순위(nice) 가중치를 반영한 '가상 실행 시간(`vruntime`)'을 계산하여, Red-Black 트리에 정렬 후 무조건 `vruntime`이 가장 작은 좌측 노드를 추출 (리눅스 커널 표준) | 오래 굶은 놈은 실행 누적 시간(`vruntime`)이 자연스럽게 작아지므로 트리 왼쪽 끝으로 이동하여 자동 구제됨 |

> 요약: MLFQ는 경험칙을 바탕으로 계급을 오르내리게 하는 동적 피드백 게임이고, 리눅스의 CFS는 1나노초의 실행 시간마저 장부에 적어 철저히 평등을 맞추는 수학적 분배기다.

## Ⅳ. 스케줄러 오버헤드 통제 및 실무 튜닝 방안

| 리스크 요인 | 발생 시나리오 | 아키텍처 대응 방안 (실무 튜닝) |
|:---|:---|:---|
| I/O 바운드 프로세스 반응성 지연 | RR 스케줄러 하에서 마우스 클릭(I/O) 프로세스와 무거운 렌더링(CPU) 로직이 동일 큐에서 경쟁 시 UI 프리징 현상 발생 | MLFQ의 도입 및 I/O 양보(Yield) 시 페널티 면제 로직을 통해 대화형 인터페이스 우선권 영구 보장 |
| 코어 간 캐시 핑퐁 (Cache Bouncing) | 멀티코어 환경에서 1개 스케줄러 큐(Global Queue)를 두면 코어 간 락(Lock) 경합과 L1/L2 캐시 무효화로 성능 급락 | **코어별 독립 큐 (Per-Core Queue)** 설계 및 워크 스틸링(Work Stealing)을 통해 지역성(Locality) 방어 |

> 요약: 알고리즘이 아무리 똑똑해도 락(Lock)이 걸리면 바보가 된다. 멀티코어 시대의 스케줄러는 단순히 순서를 정하는 것을 넘어, 캐시(Cache)가 식지 않도록 살던 코어에 계속 살게 하는 '공간 최적화'로 진화했다.

## Ⅴ. 실무 적용 방안 및 결론

**적용 방안 3개:**
1. [Linux CFS 스케줄러 튜닝] K8s 컨테이너 클러스터 배포 시, `cpu.cfs_quota_us`와 `cpu.cfs_period_us`를 조절하여 CPU 스로틀링(Throttling)을 통제하고, `nice` 값을 `-20`(최고)에서 `19`(최저)로 수동 부여하여 핵심 DB 프로세스의 `vruntime` 증가율 억제
2. [RTOS(실시간 OS) 락업 방어] 항공기/드론 등 엄격한 마감 시간(Deadline)이 필요한 제어기 환경에서는 공정성을 중시하는 CFS를 버리고, 주기가 가장 짧은 태스크에 절대 우선순위를 박는 Rate Monotonic(RM) 기반 선점 스케줄링으로 커스텀 빌드
3. [Nginx 이벤트 주도 아키텍처] 수만 개의 웹 커넥션 처리 시 OS 스케줄러의 타임 퀀텀 오버헤드 자체를 없애기 위해, 스레드를 코어 수만큼만 띄우고(FCFS적 속성) 사용자 공간(User-space)의 이벤트 루프에서 직접 비동기 디스패치 수행

**결론:**
- 기술사 판단: 스케줄링 알고리즘은 단순히 CPU를 나눠주는 분배기가 아니다. 제한된 자원 위에서 "반응성(I/O)을 살릴 것인가, 전체 처리량(CPU)을 뽑아낼 것인가"라는 영원한 딜레마를 타임 퀀텀과 동적 가중치로 타협해 낸 운영체제 철학의 결정체다.
- 향후 방향: 현대 데이터센터는 코어가 128개를 넘어가며 전통적인 SMP 큐 방식은 한계에 부딪혔다. 최근에는 NUMA 아키텍처를 인지하여 메모리 거리를 계산해 스케줄링하는 NUMA-aware 스케줄러와, 에너지 소모량(W)을 최소화하기 위한 전력 인지(EAS, Energy Aware Scheduling) 기법으로 진화의 방향이 넘어가고 있다.
