# 📖 【암기용】 개념 완전 이해

## 한눈에
- **개요**: Ready 큐에 있는 프로세스들 중 누구에게, 얼마 동안 CPU를 할당할지 결정하는 정책
- **왜 필요한가**: CPU는 제한적인데 실행할 프로세스는 많다. "가장 빨리 끝나는 애부터?", "공평하게 조금씩 돌아가며?" 등 목적(응답시간 단축 vs 처리량 극대화)에 따라 룰이 필요하다.
- **핵심 직관**: 식당 대기줄 관리와 같다. 먼저 온 사람 먼저(FCFS), 금방 먹을 사람 먼저(SJF), 10분씩만 먹고 다시 줄서기(RR), 단골/VIP 우대(MLFQ).

## 핵심 용어 정리

| 용어/표기 | 의미 | 비유·예 |
|:---|:---|:---|
| 선점형 (Preemptive) | 실행 중인 프로세스의 CPU를 강제로 뺏을 수 있음 | 응급 환자 오면 진료 중단 후 투입 |
| 비선점형 (Non-preemptive)| 끝날 때까지 뺏을 수 없음 | 먼저 들어간 환자 진료 끝날 때까지 대기 |
| 반환 시간 (Turnaround Time)| 큐 진입부터 최종 실행 완료까지 걸린 총 시간 | 식당 대기줄 서서 다 먹고 나올 때까지 시간 |
| 대기 시간 (Waiting Time) | Ready 큐에서 순서를 기다린 시간 총합 | 순수하게 줄 서서 대기한 시간 |

## 깊이 이해
- **배경·문제의식**: 일괄 처리(Batch) 시대에는 도착 순서(FCFS)면 충분했으나, 시분할 시대에는 사용자와 상호작용하는 빠른 응답(RR)이 중요해졌다. 현대 OS는 I/O 바운드와 CPU 바운드 프로세스를 영리하게 구분하고 공평성도 맞춰야 한다.
- **작동 원리**: FCFS는 도착순, SJF는 실행시간이 짧은 순, RR은 할당된 타임 퀀텀만큼씩 번갈아가며, MLFQ는 여러 개의 큐를 사용해 우선순위를 동적으로 조정한다. CFS는 가상 런타임을 기반으로 완벽한 공평성을 추구한다.
- **비유**: 처리시간 100ms인 작업 뒤에 1ms 작업이 도착했을 때, FCFS면 1ms 작업은 100ms를 기다려야 한다(Convoy Effect). SJF면 1ms 작업이 먼저 실행되어 평균 대기시간이 줄어든다.
- **구체 예시**: 처리시간 100ms인 프로세스 P1 뒤에 1ms짜리 P2, P3가 도착. FCFS면 평균 대기시간 (0 + 100 + 101)/3 = 67ms. SJF면 (100 + 0 + 1)/3 = 33.6ms로 확 줄어든다.
- **흔한 오해·주의점**: 기아(Starvation) 현상은 우선순위가 있는 선점형 방식에서 발생한다. RR이나 FCFS는 늦더라도 자기 차례가 반드시 오므로 기아가 없다.

## 연결 개념
- 프로세스 상태 전이 (003 참조) — 스케줄링이 작동하는 Ready -> Running 전이
- MLFQ (005 참조) — 현대적 스케줄링의 근간
- CFS (006 참조) — 리눅스 표준 스케줄러 심화

# 📝 【답안용】 시험 답안 템플릿

## 핵심 인사이트 (3줄 요약)

> 1. **본질**: CPU 스케줄링은 다중 프로그래밍 환경에서 프로세스의 Ready 큐 대기 순서와 할당 시간을 결정하는 정책이다.
> 2. **가치**: 배치 환경은 처리량, 대화형 환경은 응답 시간, 실시간 환경은 데드라인 준수 등 목적에 맞는 최적의 CPU 활용을 보장한다.
> 3. **판단 포인트**: 현대 OS는 단일 알고리즘 한계를 극복하기 위해 다단계 피드백 큐(MLFQ)나 완전 공정 스케줄러(CFS) 같은 복합·동적 알고리즘을 사용한다.

## 출제 의도 및 답안 포인트

| 출제 의도 | 반드시 짚을 핵심 | 감점 회피 포인트 |
|:---|:---|:---|
| 스케줄링 목표와 알고리즘 특성 매핑 | 선점/비선점 구분, FCFS/SJF/RR 핵심 특징 | 특정 알고리즘 하나만 과도하게 설명 |
| 단일 알고리즘의 한계와 진화 과정 이해 | Convoy Effect (FCFS), Starvation (SJF/Priority) | 한계 극복 방안(Aging, RR) 누락 |
| 현대 범용 OS 스케줄러 이해 | MLFQ 동적 우선순위, 리눅스 CFS 도입 | 고전적 알고리즘(SJF 등)만 나열 |

> 요약: 스케줄링 기법의 발전 흐름(FCFS → SJF → RR → MLFQ/CFS)과 각 기법이 해결하려 했던 트레이드오프(응답성 vs 오버헤드)를 제시한다.

---

## Ⅰ. 개요 및 필요성

- 개요: Ready 상태의 다수 프로세스 중 어떤 프로세스에 CPU를 언제, 얼마나 할당할지 결정하는 운영체제 커널의 핵심 기능
- 배경: 제한된 CPU 코어로 다수의 애플리케이션을 동시 실행하기 위해 시분할 처리와 공평한 자원 분배 필요
- 필요성: 시스템 목적(응답시간 단축, CPU 사용률 극대화, 오버헤드 최소화)에 부합하는 최적의 시스템 성능 도출

---

## Ⅱ. 구조 및 구성요소

```text
도착(Arrival) -> 대기(Waiting Time) -> 실행(CPU Burst Time) -> 완료
[-------------------- 반환 시간 (Turnaround Time) -----------------]
                 [--- 응답 시간 (Response Time) ---]
```

| 평가 지표 (Criteria) | 관점 | 최적화 목표 |
|:---|:---|:---|
| CPU Utilization (사용률) | 시스템 | CPU 유휴 시간을 최소화하여 가동률 극대화 |
| Throughput (처리량) | 시스템 | 단위 시간당 완료된 프로세스 수 극대화 |
| Turnaround Time (반환 시간) | 사용자 | 작업 제출부터 완료까지 총 소요 시간 최소화 |
| Response Time (응답 시간) | 사용자 | 대화형 시스템에서 첫 반응이 나올 때까지 시간 최소화 |
| Waiting Time (대기 시간) | 프로세스 | Ready 큐에서 대기한 총 시간 최소화 |

> 요약: 스케줄링 알고리즘은 시스템 관점(처리량)과 사용자 관점(응답성)의 트레이드오프를 조율한다.

---

## Ⅲ. 동작원리 및 흐름도

```text
프로세스 Ready Queue 진입 -> 스케줄러 알고리즘 실행
  -> [선점형] 퀀텀 만료 시 강제 회수 / 우선순위 높은 프로세스 도착 시 회수
  -> [비선점형] 자발적 I/O 또는 종료 시까지 대기
```

- 1단계 [비선점형 기본]: FCFS(First-Come First-Served)는 도착 순서대로 실행하며 호위 효과(Convoy Effect) 유발
- 2단계 [이론적 최적화]: SJF(Shortest Job First)는 짧은 작업을 먼저 처리해 대기시간을 최소화하나 기아(Starvation) 유발
- 3단계 [응답성 확보]: RR(Round Robin)은 타임 퀀텀 분배로 응답성을 높이지만 문맥 전환 오버헤드가 발생
- 4단계 [현대적 복합 설계]: MLFQ는 동적 우선순위 조정을, CFS는 가상 런타임 기반 공평성을 추구

> 요약: 과거 단일 큐 알고리즘들의 한계(Convoy, Starvation)를 상호 보완하며 다중 큐 및 피드백 구조로 진화하였다.

---

## Ⅳ. 특징

- MLFQ (다단계 피드백 큐): 하위 큐로 갈수록 타임 퀀텀을 길게 부여하여 CPU 바운드 작업의 문맥 전환 오버헤드를 줄이고, 기아를 방지(Aging)함
- CFS (Completely Fair Scheduler): 리눅스의 표준 스케줄러로 가상 런타임(`vruntime`)을 도입하여, 완벽한 공평성 추구
- 트레이드오프: 타임 퀀텀이 작을수록 응답성은 좋아지나 문맥 전환 오버헤드가 증가하며, 클수록 FCFS에 가까워짐

> 요약: 범용 OS는 프로세스의 특성을 동적으로 파악하는 MLFQ나 정밀한 공평성을 보장하는 CFS를 기본으로 채택한다.

## Ⅴ. 심화 비교 및 적용 판단

| 비교 축 | FCFS | Round Robin (RR) | MLFQ / CFS | 선택 기준 |
|:---|:---|:---|:---|:---|
| 선점 여부 | 비선점형 | 선점형 | 선점형 | 응답성 필요 여부 |
| 최적 환경 | 일괄 처리 (Batch) 시스템 | 대화형 (Interactive) 시스템 | 범용 (General-Purpose) OS | 워크로드 특성 (CPU vs I/O) |
| 주 발생 문제 | 호위 효과 (Convoy Effect) | 문맥 전환 오버헤드 | 튜닝 복잡성 (파라미터 수) | 한계 회피 방식 |

> 요약: 시스템 목적이 뚜렷한 경우(배치 등) 단순 알고리즘을, 일반 PC나 서버처럼 믹스된 환경에서는 복합 알고리즘을 사용한다.

**리스크·대응 (기본은 불릿):**
- 기아 상태(Starvation) 발생: 우선순위 기반 스케줄링 시 하위 프로세스 영구 대기 → 에이징(Aging) 기법 도입하여 우선순위 상향
- 우선순위 역전(Priority Inversion): 락(Lock) 점유에 의해 우선순위가 꼬임 → 우선순위 상속(Priority Inheritance) 프로토콜 적용

**도입 후 점검 지표 (기본은 불릿):**
- 성능/효율: 95th Percentile Response Time (SLA 충족 여부), CPU 큐 길이(Run Queue Length)
- 품질/운영: Context Switches / sec (`cs` 지표)

---

## Ⅵ. 실무 적용 및 결론

**적용 방안 3개 (필수 — 단계별 또는 항목별):**
1. I/O 바운드 프로세스 우대: DB 워커나 웹 서버 스레드의 우선순위를 상향(NICE 값 조정)해 응답성 유도
2. 타임 퀀텀(Time Quantum) 최적화: 스위칭 오버헤드(수십 us)를 고려하여 퀀텀을 10~100ms 사이로 설정해 Throughput 방어
3. 스케줄링 클래스 분리: 실시간 처리가 필요한 오디오 프로세스는 `SCHED_FIFO`로, 나머지는 CFS로 분리

**결론 (2줄):**
- 기술사 판단: 스케줄링은 "공평성"과 "성능(오버헤드 방어)" 사이의 트레이드오프이므로, 워크로드(CPU/IO 비율)에 맞춰 파라미터를 튜닝해야 한다.
- 향후 방향: 최근 멀티 코어 환경 확산에 따라 NUMA 인지(NUMA-aware) 스케줄링 및 캐시 친화도(Cache Affinity)를 고려하는 스케줄러 최적화가 필수적이다.
