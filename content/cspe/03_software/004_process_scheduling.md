# 📖 【암기용】 개념 완전 이해

## 한눈에
- **개요**: 프로세스 스케줄링(CPU 스케줄링)은 Ready 큐에 있는 여러 프로세스 중 **어느 것에 CPU를 언제·얼마 동안 줄지** 결정하는 운영체제 커널의 자원 할당 정책이다.
- **왜 필요한가**: CPU 코어 수는 적은데 실행 대기 프로세스는 많다. 순서를 잘못 정하면 짧은 작업이 긴 작업 뒤에서 하염없이 기다리거나(응답 지연), 문맥 전환을 너무 자주 해 CPU가 일 대신 교체에만 시간을 쓴다(오버헤드). 목적에 맞는 규칙이 필요하다.
- **핵심 직관**: 식당 대기줄 관리 규칙이다. 먼저 온 사람 먼저(FCFS), 금방 먹을 사람 먼저(SJF), 10분씩 먹고 다시 줄서기(RR), 손님 습관 보고 줄을 갈아 태우기(MLFQ), 지금까지 가장 적게 먹은 사람 우선(CFS).

## 핵심 용어 정리 (내부에 등장하는 것들)

아래 답안용에 등장하는 모든 용어를 비유와 함께 먼저 세운다. 맨 위 두 줄이 이 주제의 상위 핵심 키워드다.

| 용어/표기 | 의미 | 비유·예 |
|:---|:---|:---|
| CPU 스케줄링 (상위 키워드) | Ready 큐에서 다음 실행 프로세스를 고르는 정책 | 대기줄에서 다음 손님을 부르는 규칙 |
| 디스패처 (Dispatcher) | 스케줄러가 고른 프로세스에 실제로 CPU를 넘기는 커널 모듈 | "손님, 들어오세요"라고 안내하는 직원 |
| CPU 버스트 (CPU Burst) | 한 프로세스가 I/O 없이 CPU만 연속으로 쓰는 구간 | 자리에 앉아 밥만 먹는 한 타임 |
| I/O 바운드 | CPU를 짧게 쓰고 곧 입출력 대기로 빠지는 프로세스 | 한 입 먹고 물 뜨러 자주 일어나는 손님 |
| CPU 바운드 | 연산이 많아 CPU를 길게 붙잡는 프로세스 | 자리에서 오래 진득하게 먹는 손님 |
| 선점형 (Preemptive) | 실행 중인 프로세스의 CPU를 강제로 회수 가능 | 응급 환자 오면 진료 중단하고 교체 |
| 비선점형 (Non-preemptive) | 스스로 놓기 전엔 CPU를 못 뺏음 | 먼저 든 환자 진료 끝날 때까지 대기 |
| 타임 퀀텀 (Time Quantum) | 한 번에 CPU를 쓸 수 있는 최대 시간 조각 | 1인당 10분 식사 제한 타이머 |
| 문맥 전환 (Context Switch) | CPU를 A에서 B로 넘길 때 상태를 저장·복원하는 비용 | 손님 교대 때 자리 치우고 새로 세팅하는 시간 |
| 대기 시간 (Waiting Time) | Ready 큐에서 순서를 기다린 시간 총합 | 순수하게 줄 서서 기다린 시간 |
| 반환 시간 (Turnaround Time) | 도착부터 완료까지 걸린 총 시간(대기+실행) | 줄 서서 다 먹고 나올 때까지 전체 시간 |
| 응답 시간 (Response Time) | 도착 후 처음 CPU를 받기까지 걸린 시간 | 줄 서서 첫 숟갈 뜨기까지 시간 |
| 처리량 (Throughput) | 단위 시간당 완료한 프로세스 수 | 1시간에 받은 손님 수 |
| CPU 사용률 (Utilization) | 전체 시간 중 CPU가 논 시간을 뺀 가동 비율 | 식당 좌석이 빈 시간 없이 찬 정도 |
| 호위 효과 (Convoy Effect) | 긴 작업 하나가 뒤의 짧은 작업들을 막아 평균 대기가 폭증 | 대형 버스 한 대가 좁은 길 뒤 승용차를 다 막음 |
| 기아 (Starvation) | 우선순위에 밀려 특정 프로세스가 CPU를 영영 못 받음 | 새치기에 계속 밀려 못 먹는 손님 |
| 에이징 (Aging) | 오래 기다린 프로세스의 우선순위를 점점 올려 기아 해소 | 오래 기다린 손님을 순번 올려주기 |

## 깊이 이해
- **배경·문제의식**: 일괄 처리(Batch) 시대에는 도착 순서대로 돌리는 FCFS면 충분했다. 시분할(Time-Sharing) 시대가 오자 사용자가 타이핑하면 즉시 반응하는 **응답성**이 중요해졌고, 현대 범용 OS는 I/O 바운드·CPU 바운드가 섞인 워크로드를 동시에, 그것도 공평하게 처리해야 한다. 이 요구가 스케줄링 알고리즘을 계속 진화시킨 원동력이다.
- **작동 원리 (알고리즘별 한 줄 핵심)**:
  - FCFS: 도착 순서대로 비선점 실행. 단순하지만 긴 작업이 앞서면 호위 효과 발생.
  - SJF: 남은 CPU 버스트가 가장 짧은 것 먼저. 평균 대기 시간이 이론상 최소지만, 실행 시간을 미리 알 수 없고 긴 작업이 기아에 빠진다.
  - RR: 타임 퀀텀만큼만 쓰고 큐 맨 뒤로. 응답성은 좋아지나 퀀텀이 작으면 문맥 전환 오버헤드가 커진다.
  - MLFQ(005 심화): 여러 우선순위 큐 + 행동 이력 피드백으로 강등/승급. SJF를 실행 시간 예측 없이 근사한다.
  - CFS(006 심화): 가상 런타임(vruntime)이 가장 작은 프로세스 우선. 수학적 공평성을 추구하는 리눅스 표준.
- **비유**: 퀀텀 크기는 회의 발언 시간 제한과 같다. 1분씩 끊으면 모두 자주 말하지만(응답성↑) 진행자가 계속 끼어들어야 하고(오버헤드↑), 30분씩 주면 진행은 편하지만 뒷사람이 오래 기다린다.
- **구체 예시 (호위 효과)**: 처리 시간 100ms인 P1이 먼저 도착하고 1ms짜리 P2, P3가 뒤이어 도착. FCFS면 평균 대기 = (0 + 100 + 101)/3 ≈ 67ms. 순서를 SJF로 바꿔 P2·P3를 먼저 처리하면 평균 대기 = (2 + 0 + 1)/3 = 1ms로 급감한다. 같은 작업 집합이라도 순서 규칙만으로 응답 지연이 수십 배 갈린다.
- **흔한 오해·주의점**: 기아는 **우선순위가 개입하는 선점형** 방식(SJF·우선순위·MLFQ)에서 생긴다. RR·FCFS는 늦더라도 자기 차례가 반드시 오므로 구조적으로 기아가 없다. 또 "선점형이 항상 좋다"는 오해가 흔한데, 선점은 문맥 전환 비용을 대가로 응답성을 사는 트레이드오프다.

## 연결 개념
- 프로세스 상태 전이(003 참조): 스케줄링이 실제로 작동하는 Ready → Running 전이 지점.
- MLFQ(005): 004가 소개한 다단계 피드백 큐의 메커니즘 심화.
- CFS(006): 004가 소개한 리눅스 표준 스케줄러의 vruntime 심화.

# 📝 【답안용】 시험 답안 템플릿

## 핵심 인사이트 (3줄 요약)

> 1. **본질**: CPU 스케줄링은 Ready 큐의 다수 프로세스 중 CPU를 줄 대상과 할당량을 정하는 커널 정책으로, 순서 규칙이 응답성·처리량·공평성을 좌우함.
> 2. **가치**: 배치는 처리량, 대화형은 응답 시간, 실시간은 데드라인 등 시스템 목적에 맞는 CPU 활용을 보장함.
> 3. **판단 포인트**: 단일 알고리즘은 호위 효과·기아 등 한계가 있어, 현대 OS는 MLFQ·CFS 같은 동적·복합 기법으로 트레이드오프를 조율함.

## 출제 의도 및 답안 포인트

| 출제 의도 | 반드시 짚을 핵심 | 감점 회피 포인트 |
|:---|:---|:---|
| 스케줄링 목표와 알고리즘 특성 매핑 | 선점/비선점 구분, FCFS·SJF·RR의 핵심 특징 | 특정 알고리즘 하나만 과다 서술 |
| 단일 알고리즘의 한계와 진화 이해 | 호위 효과(FCFS)·기아(SJF)·오버헤드(RR) | 한계 극복 기법(에이징·퀀텀 조절) 누락 |
| 현대 범용 OS 스케줄러 이해 | MLFQ 동적 우선순위, 리눅스 CFS 도입 | 고전 알고리즘만 나열, 진화 맥락 부재 |

> 요약: 발전 흐름(FCFS→SJF→RR→MLFQ/CFS)과 각 단계가 해결한 트레이드오프(응답성 vs 오버헤드)를 함께 제시함.

## Ⅰ. 개요 및 필요성

- 개요: Ready 큐의 다수 프로세스 중 CPU 할당 대상·시점·시간을 정하는 커널 정책임
- 배경: 제한된 코어로 다수 작업을 동시 실행하려면 시분할과 공평한 자원 분배가 필요함
- 필요성: 시스템 목적(응답 시간 단축·처리량 극대화·오버헤드 최소화)에 맞는 순서 규칙이 성능을 결정함

## Ⅱ. 구조 및 구성요소

선형 구조도 (지표가 측정되는 구간):

    프로세스 도착 -> Ready 큐 대기 -> 디스패처가 CPU 할당 -> 실행(CPU Burst) -> 완료
    [------------------------- 반환 시간 -------------------------]
    [------- 대기 시간 -------]
    [-- 응답 시간(첫 CPU까지) --]

| 구성요소 | 역할 | 특이사항 |
|:---|:---|:---|
| Ready 큐 | 실행 대기 프로세스 보관 | 알고리즘마다 자료구조 상이(FIFO·트리 등) |
| 스케줄러 | 큐에서 다음 실행 프로세스 선택 | 선점/비선점 정책 반영 |
| 디스패처 | 선택된 프로세스에 CPU 실제 인계 | 문맥 전환 지연(Dispatch Latency) 발생 |
| 평가 지표 | 사용률·처리량·대기·반환·응답 시간 | 시스템 관점 vs 사용자 관점 상충 |

> 요약: 스케줄러가 대상을 고르고 디스패처가 CPU를 넘기며, 지표는 시스템(처리량)·사용자(응답성) 관점이 상충함.

## Ⅲ. 동작원리 및 흐름도

선형 흐름도:

    Ready 큐 진입 -> 스케줄러 선택 -> 디스패처 인계 -> 실행
      -> [선점형] 퀀텀 만료·상위 프로세스 도착 시 CPU 강제 회수
      -> [비선점형] 자발적 I/O·종료 시까지 점유 유지

- 1단계 [비선점 기본]: FCFS는 도착 순서대로 실행하여 긴 작업 뒤 짧은 작업이 밀리는 호위 효과 유발
- 2단계 [이론적 최적]: SJF는 짧은 작업 우선으로 평균 대기를 최소화하나 긴 작업의 기아 유발
- 3단계 [응답성 확보]: RR은 타임 퀀텀 분배로 응답성을 높이나 문맥 전환 오버헤드 증가
- 4단계 [현대 복합]: MLFQ는 피드백 기반 동적 우선순위를, CFS는 vruntime 기반 공평성을 구현

> 요약: 단일 큐의 한계(호위·기아·오버헤드)를 상호 보완하며 다중 큐·피드백 구조로 진화함.

## Ⅳ. 특징

- 선점 vs 비선점 트레이드오프: 선점은 응답성을 얻는 대신 문맥 전환 비용을 지불함
- 퀀텀 크기 민감성: 퀀텀이 작을수록 응답성은 좋아지나 오버헤드 증가, 클수록 FCFS로 수렴함
- 지표 상충: 처리량 극대화(시스템)와 응답 시간 단축(사용자)은 동시 최적화가 어려움
- 진화 방향: 실행 시간 예측 불가·기아 문제를 피드백(MLFQ)·가상 시간(CFS)으로 우회함

## Ⅴ. 심화 비교 및 적용 판단

주요 알고리즘을 선점·목표·고유 문제 축으로 종합 대조함(개별 심화는 005·006 참조).

| 구분 | FCFS | SJF | RR | MLFQ / CFS |
|:---|:---|:---|:---|:---|
| 선점 여부 | 비선점 | 비선점(선점형 SRTF 변형 존재) | 선점 | 선점 |
| 최적 환경 | 일괄 처리(Batch) | 평균 대기 최소화가 목표인 배치 | 대화형(Interactive) | 범용 OS(혼합 워크로드) |
| 고유 문제 | 호위 효과 | 기아·실행 시간 예측 불가 | 퀀텀 튜닝·문맥 전환 오버헤드 | 파라미터 튜닝(MLFQ)·연산량 O(log N)(CFS) |

> 요약: 목적이 뚜렷하면 단순 알고리즘을, PC·서버처럼 워크로드가 섞이면 MLFQ·CFS 같은 복합 알고리즘을 씀.

**리스크·대응:**
- 기아 발생: 우선순위 기반에서 하위 작업 영구 대기 → 에이징으로 대기 시간에 비례해 우선순위 상향
- 우선순위 역전: 락 점유로 저순위가 고순위를 막음 → 우선순위 상속(Priority Inheritance) 프로토콜 적용
- 오버헤드 폭증: 퀀텀 과소 설정으로 문맥 전환 급증 → 스위칭 비용 대비 10~100ms 범위로 퀀텀 조정

**점검 지표:**
- 성능: 대화형 작업 p95 응답 시간, Run Queue 길이
- 운영: 초당 문맥 전환 수(cs), CPU 사용률 대비 유효 처리량

## Ⅵ. 실무 적용 및 결론

**적용 방안:**
1. 워크로드 분류: I/O 바운드(웹·DB 워커)는 우선순위 상향(nice 값 하향), CPU 바운드 배치는 하향 배치
2. 타임 퀀텀 최적화: 스위칭 오버헤드(수십 μs)를 고려해 퀀텀을 10~100ms로 잡아 처리량 방어
3. 스케줄링 클래스 분리: 오디오·제어 등 실시간은 SCHED_FIFO로, 일반 작업은 CFS로 분리 운용

**결론:**
- 기술사 판단: 스케줄링은 공평성과 성능(오버헤드) 사이 트레이드오프이므로 워크로드 특성에 맞춘 파라미터 튜닝이 핵심임
- 향후 방향: 멀티코어 확산으로 NUMA 인지·캐시 친화도를 고려한 코어별 런큐 스케줄링이 필수로 자리 잡음
