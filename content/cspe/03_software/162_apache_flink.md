## Ⅰ. 개요
- **정의**: 이벤트 기반 스트림을 우선 처리하고 배치를 스트림의 특수 케이스로 다루는 분산 처리 엔진
- **배경/필요성**: 실시간 데이터 분석 수요 증가로 저지연 스트림 처리 전용 엔진이 필요함
- **비유**: 컨베이어 벨트 위 제품을 즉시 검수하는 품질관리 라인과 유사함

| 출제 의도 | 반드시 짚을 핵심 | 감점 회피 포인트 |
|:---|:---|:---|
| 스트림 처리 엔진 특성 비교 | Event Time 처리와 Exactly-Once 보장 | MapReduce(161 참조)와의 차이 명시 |

> 요약: 이벤트 시간 기반 저지연 스트림 처리를 Exactly-Once 보장으로 수행하는 엔진임

## Ⅱ. 구성요소
```text
Source --> Transformation --> Window --> Sink
             |                  |
          KeyBy/Map         Time-based
          Filter/Join       Count-based
```

| 구성요소 | 설명 | 비유 |
|:---|:---|:---|
| Source | Kafka·파일 등 외부 데이터를 스트림으로 수집함 | 공장 원재료 투입구 |
| Transformation | 데이터에 Map·Filter·Join 등 연산을 적용함 | 컨베이어 벨트 위 가공 공정 |
| Window | 시간·개수 기준으로 스트림을 유한 구간으로 분할함 | 일정 시간마다 묶어 검수하는 구간 |
| Sink | 처리 결과를 외부 저장소·시스템으로 출력함 | 완성품 출하 게이트 |
| Checkpoint | 상태를 주기적으로 스냅샷하여 장애 시 복구 지점을 제공함 | 게임 세이브 포인트 |

> 요약: Source-Transformation-Window-Sink 파이프라인과 Checkpoint로 구성됨

## Ⅲ. 절차
```text
Source 수집 --> Operator 변환 --> Window 집계 --> Sink 출력
     |               |               |              |
     v               v               v              v
  스트림 생성    연산 그래프 실행   구간별 집계    결과 저장
```
- 1단계: Source 커넥터가 외부 시스템에서 이벤트 스트림을 수집함
- 2단계: Operator Chain이 DAG 형태의 변환 연산을 병렬 실행함
- 3단계: Window 함수가 시간·개수 기준으로 데이터를 집계함
- 4단계: Sink 커넥터가 처리 결과를 목적지 시스템에 기록함

> 요약: 수집-변환-윈도우집계-출력 4단계로 스트림을 연속 처리함

## Ⅳ. 문제점
- 상태 관리 복잡성: 대규모 Stateful 연산 시 메모리·디스크 상태 관리 부담이 큼
- 운영 난이도: 클러스터 설정·모니터링·튜닝에 높은 전문성이 요구됨
- 소규모 부적합: 단순 배치 작업에는 운영 오버헤드 대비 이점이 적음

> 요약: 상태 관리·운영 복잡성·소규모 비효율이 주요 한계임

## Ⅴ. 개선방안
1. 단기: RocksDB 기반 증분 Checkpoint로 상태 관리 부담 경감
2. 중기: Kubernetes 기반 자동 스케일링·모니터링 체계 구축으로 운영 단순화
3. 장기: Flink SQL 등 선언적 인터페이스 확대로 소규모 작업 진입장벽 완화

> 요약: 증분 Checkpoint-자동화 운영-선언적 API 순으로 개선함

## Ⅵ. 전망
- 발전 방향: 배치-스트림 통합(Unified Processing) 표준 엔진으로 확산 중임
- 기술사적 판단: 실시간 데이터 파이프라인의 핵심 기술로 채택 범위가 확대됨
- 기술사 제언: 워크로드 지연 허용치에 따라 Flink·Spark 등 엔진 선정 기준을 수립할 필요
