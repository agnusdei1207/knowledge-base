# 📖 【암기용】 개념 완전 이해

> 목적: AI 코드 생성을 개발자 보조, 품질 검증, 라이선스·보안 통제의 결합으로 이해하게 만든다. 시험 답안 양식이 아니라, 이해를 위한 설명이다.

## 한눈에
- **개요**: AI 코드 생성은 **LLM(대규모 언어모델)** 이 개발자의 문맥(코드·주석·프롬프트)을 입력받아 다음 코드를 예측·제안하는 **AI 페어 프로그래밍** 방식이다.
- **왜 필요한가**: CRUD, DTO, 반복 API 호출, 테스트 초안처럼 창의적 설계보다 패턴 반복 비중이 큰 코드가 개발 시간의 상당 부분을 차지한다. 이런 코드는 자동 제안 후 사람이 확인하는 쪽이 더 빠르다.
- **핵심 직관**: 옆에 앉은 페어 프로그래머가 초안 코드를 먼저 쳐주는 것과 같다. 다만 이 페어는 가끔 없는 API를 있다고 우기므로, 최종 책임(리뷰·테스트·보안검증)은 여전히 사람에게 있다.

## 핵심 용어 정리 (내부에 등장하는 것들)

| 용어 | 의미 | 비유 |
|:---|:---|:---|
| LLM(대규모 언어모델) | 방대한 텍스트·코드로 학습해 다음 토큰을 확률적으로 예측하는 모델 — AI 코드 생성의 엔진 | 상위 키워드 |
| AI 페어 프로그래밍 | 사람과 AI가 번갈아 코드를 제안·검토하는 개발 방식 | 상위 키워드 |
| Context(문맥) | 현재 파일, 열린 탭, 주석 등 모델에 입력되는 주변 정보 | 참고자료를 펼쳐놓기 |
| Prompt(프롬프트) | 개발자가 의도를 담아 작성한 지시문(주석, 함수명, 이슈 설명) | 주문서 |
| Completion(제안/완성) | 모델이 생성한 코드·테스트·리팩터링 후보 | 초안 원고 |
| Hallucination(환각) | 존재하지 않는 API·라이브러리·메서드를 그럴듯하게 만들어내는 오류 | 없는 길을 있다고 우기는 안내판 |
| SAST(Static Application Security Testing) | 소스코드를 실행 없이 정적 분석해 보안 취약점을 찾는 검사 | 원고 사전 검수 |
| SCA(Software Composition Analysis) | 사용된 오픈소스 의존성의 라이선스·취약점을 분석하는 검사 | 재료 원산지·유통기한 확인 |
| Code Review | 사람이 생성된 코드를 최종 검토·승인하는 절차 | 편집장 최종 검토 |

## 깊이 이해

### 왜 필요했나 (배경)
- 신규 프레임워크 학습, 보일러플레이트 작성, 테스트 코드 작성은 업무 로직 설계보다 반복성이 높다. 개발자 시간의 상당 부분이 이런 반복 구현에 쓰인다는 문제의식에서, IDE에 통합된 LLM 코드 제안 도구(GitHub Copilot 등)가 확산됐다.

### 작동 원리 — Context에서 Completion까지
- IDE 확장이 현재 커서 위치의 앞뒤 코드, 열려 있는 다른 탭, 파일 내 주석을 모아 Context로 구성하고, 여기에 개발자가 입력한 Prompt(예: 함수명, 주석)를 더해 모델에 전달한다.
- 모델은 자기회귀(autoregressive) 방식으로 "이 문맥 다음에 올 가능성이 가장 높은 토큰"을 순서대로 예측해 코드를 완성한다. 예: `// GET 요청으로 id로 사용자 조회`라는 주석을 입력하면, 모델은 유사한 학습 패턴을 참고해 컨트롤러 메서드 시그니처, DTO 필드, try-catch 예외 처리, 단위 테스트 초안까지 순서대로 제안한다.
- GitHub가 공개한 2022년 통제 실험에서는 특정 과제(웹서버 구현)를 Copilot을 쓴 그룹이 쓰지 않은 그룹보다 더 빠르게(약 55% 단축) 완료했다고 보고됐다. 다만 이는 반복 패턴이 많은 과제에서의 결과이며, 모든 작업에 동일하게 적용되지는 않는다.

### Hallucination이 실제로 어떻게 발생하는가
- 모델은 "그럴듯한 다음 토큰"을 예측할 뿐 실제 패키지 레지스트리를 조회하지 않는다. 그래서 학습 데이터에 자주 등장한 이름 패턴을 조합해 `fast-json-utils` 같은 존재하지 않는 패키지의 import 문을 만들어낼 수 있다.
- 이런 문제는 컴파일·빌드 단계에서 걸러지긴 하지만, 존재하는 API를 잘못된 파라미터 순서로 호출하는 경우(빌드는 성공하지만 런타임에 오류)는 단위 테스트 없이는 걸러내지 못한다. 그래서 "AI 제안 → 로컬 테스트 실행 → SAST/SCA → 사람 리뷰"라는 다단계 검증이 필요하다.

### 왜 기존 자동완성과 다른가
- 기존 IDE 자동완성(사전 기반)은 타이핑 중인 "단어" 하나를 사전에서 찾아 완성한다. 반면 LLM 기반 completion은 문맥 전체를 이해해 함수 시그니처, 조건문, 테스트 블록 단위로 여러 줄을 한 번에 제안한다. 예측 단위가 "단어"에서 "코드 블록"으로 바뀐 것이 핵심 차이다.
- 공개된 사용 데이터에서는 제안된 코드의 상당수(약 30% 내외)가 수정 없이 그대로 채택된다고 보고되는데, 이는 나머지는 수정되거나 거부된다는 뜻이기도 하다. 즉 "AI가 다 짜준다"가 아니라 "AI가 초안을 주고 사람이 대부분 손본다"에 가깝다.

### 비유와 흔한 오해
- **비유**: 자동완성 사전이 "다음 단어"를 제안하던 수준에서, 문단 초안을 통째로 써주는 비서로 바뀐 것과 같다. 다만 비서가 쓴 초안의 사실관계(없는 API 사용 여부)와 문체(사내 코딩 컨벤션 준수 여부)는 작성자가 확인해야 한다.
- **오해**: "컴파일이 됐으니 맞는 코드"라는 생각이 가장 흔한 오해다. 컴파일 성공은 문법이 맞다는 뜻일 뿐, 업무 요구사항에 맞는지·보안 취약점이 없는지·라이선스가 충돌하지 않는지는 별개 문제다. SAST(취약점)와 SCA(라이선스)가 이 부분을 각각 담당한다.

## 연결 개념
- AI Pair Programming — 이 개념이 속하는 상위 개발 방법론
- SAST/SCA — 생성 코드의 보안·라이선스를 검증하는 자동화 도구
- GenAI DevOps Automation — 코드 생성 이후 CI/CD·운영 단계로 이어지는 AI 자동화

# 📝 【답안용】 시험 답안 템플릿

> 목적: 시험장에서 25분에 그대로 쓰는 답안 양식. 작성방식(추상표현 금지·수치·도식·문제유형 전환)을 엄격히 지킨다.
> 핵심: AI 코드 생성 문제는 생산성만 쓰면 감점이며, 환각, 보안, 라이선스, 리뷰 책임, 측정 지표를 함께 써야 한다.

## 핵심 인사이트 (3줄 요약)

> 1. **본질**: AI 코드 생성은 LLM이 개발 문맥을 기반으로 코드·테스트·문서 초안을 생성하는 AI pair programming 기술이다.
> 2. **가치**: 반복 코드와 테스트 초안 작성 시간을 줄이고 개발자는 설계, 검증, 리뷰, 예외 처리에 시간을 배분한다.
> 3. **판단 포인트**: 생성 코드는 hallucination, 취약 코드, 라이선스 충돌, 사내 코드 유출 리스크를 CI·리뷰·정책으로 통제해야 한다.

## 출제 의도 및 답안 포인트

| 출제 의도 | 반드시 짚을 핵심 | 감점 회피 포인트 |

> 요약: AI 코드 생성은 개발 보조 기술이며, 최종 품질은 사람의 리뷰와 자동 검증 파이프라인으로 보증해야 한다.

## Ⅰ. 개요 및 필요성

- 개요: LLM 기반 개발 보조 기술
- 배경: 반복 구현, 테스트 초안, API 사용 예시는 자동화 대상이지만 생성 코드의 업무 적합성, 보안 취약점, 라이선스 출처는 별도 검증이 필요하다.
- 필요성: AI 코드 생성 도입은 IDE Copilot, 코드 리뷰, SAST, OSS license scan, 책임소재 기준을 함께 둬야 한다.

## Ⅱ. 구조 및 구성요소

```text
IDE/Repository Context -> Prompt -> LLM Completion
-> Developer Review -> Unit Test/SAST/SCA
-> Pull Request -> Code Review -> Merge Policy
```

| 구성요소 | 역할 | 산정 포인트 |
|:---|:---|:---|
| Context | 주변 코드·주석·파일 정보 제공 | 민감정보 제외 정책 |
| Prompt | 의도와 제약 입력 | 테스트·예외 조건 명시 |
| Completion | 코드·테스트 초안 생성 | API 존재성, 컴파일 검증 |
| Guardrail | 리뷰·검사·정책 통제 | SAST, SCA, secret scan |
> 요약: AI 코드 생성 구조는 모델 제안과 개발자 검증, CI 통제가 결합된 개발 흐름이다.

---

## Ⅲ. 동작원리 및 흐름도

```text
개발 의도 작성 -> 모델이 코드 후보 생성 -> 개발자 수정
-> 로컬 테스트 실행 -> SAST/SCA/secret scan
-> PR 리뷰 -> 품질 지표 측정 -> 정책 개선
```

| 단계 | 처리 내용 | 검증 기준 |
|:---:|:---|:---|
| 1 | 주석·함수명·프롬프트 작성 | 요구사항 ID 또는 이슈 링크 |
| 2 | 코드·테스트 후보 생성 | 컴파일 오류 0건 |
| 3 | 개발자 의미 검토 | business rule review |
| 4 | 자동 검사 수행 | SAST high 0건, SCA 정책 통과 |
| 5 | PR 리뷰와 병합 | 리뷰 승인 2인 또는 CODEOWNERS |
> 요약: AI 생성 코드는 제안, 수정, 테스트, 보안·라이선스 검사, PR 리뷰를 통과해야 병합한다.

## Ⅵ. 실무 적용 및 결론

**적용 방안 3개:**
1. AI 사용 정책에 민감정보 입력 금지, 허용 저장소, 라이선스 검토 기준, PR 책임자를 명시함.
2. 생성 코드는 unit test, SAST high 0건, SCA 정책 통과, secret scan 0건을 병합 조건으로 설정함.
3. 4주 파일럿에서 PR 리드타임, coverage, 결함 재오픈율, 개발자 만족도 점수를 측정해 확대 여부를 판단함.

**결론 (2줄):**
- 기술사 판단: 반복 구현과 테스트 초안 비중이 큰 조직은 AI 코드 생성을 적용하되, 안전·라이선스·리뷰 정책이 없는 조직은 파일럿부터 시작함.
- 향후 방향: AI 코드 생성은 IDE 보조를 넘어 요구사항, 테스트, 리뷰, 배포 정책과 연결된 SDLC 자동화로 확장됨.
