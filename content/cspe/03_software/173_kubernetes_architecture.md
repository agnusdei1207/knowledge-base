## 핵심 인사이트 (3줄 요약)
- 수천 개의 도커 컨테이너를 지휘하는 **마스터 노드(Control Plane)**와, 그 명령을 받아 실제로 컨테이너를 돌리는 **워커 노드(Data Plane)**로 완벽하게 분리된 해전(Naval Battle) 사령부 아키텍처.
- "지금 로그인 서버 3대가 떠 있어야 해!"라는 상태(Desired State)를 장부(etcd)에 적어두면, 쿠버네티스 컨트롤 루프가 1초마다 감시하다가 1대가 죽으면 즉시 새 서버를 살려내어 '3대'를 무한정 유지해 주는(Self-healing) 자율 주행 시스템임.
- 구글이 15년간 자사 서버를 관리하던 노하우(Borg 프로젝트)를 오픈소스로 푼 것으로, 클라우드 컴퓨팅 시대의 분산 운영체제(Data Center OS)이자 사실상의 지구 표준임.

## Ⅰ. 개요 및 필요성
- **개요**: 수많은 컨테이너화된 애플리케이션의 배포, 확장, 관리를 자동화하는 오픈소스 컨테이너 오케스트레이션 플랫폼 (K8s).
- **필요성**: 도커가 좋아서 컨테이너 10개를 띄웠음. 근데 "만약 3번 서버가 죽으면 누가 다시 켜지?", "트래픽이 2배가 되면 컨테이너를 20개로 누가 늘려주지?", "로그인 컨테이너랑 결제 컨테이너 통신은 어떻게 시키지?" 사람이 수동으로 하다가 미쳐버림. **"내가 원하는 상태(선언)만 적어두면 알아서 무한정 관리해 주는 자동화된 로봇 군단장"**이 절실해짐.
---
## Ⅱ. 아키텍처 및 핵심 원리
- **1. 마스터 노드 (Control Plane - 사령부)**:
  - **kube-apiserver**: 쿠버네티스의 유일한 입구(관문). 사용자가 `kubectl`로 명령을 내리거나 다른 컴포넌트들이 통신할 때 무조건 거쳐야 하는 문지기.
  - **etcd**: 클러스터의 모든 상태 데이터(누가 어디서 도는지)를 저장하는 핵심 Key-Value 저장소(두뇌).
  - **kube-scheduler**: "이 컨테이너는 CPU 넉넉한 2번 노드에 배치해라"라고 결정하는 배정 담당관.
  - **kube-controller-manager**: 끊임없이 상태를 감시(Control Loop)하며, 3대 떠 있어야 하는데 2대면 1대를 다시 살려내는 치유 마법사.
- **2. 워커 노드 (Worker Node - 군함/일꾼)**:
  - **kubelet**: 마스터 노드의 명령을 받아, 자기 배(Node) 위에 컨테이너를 띄우고 상태를 보고하는 선장.
  - **kube-proxy**: 배(Node)로 들어오는 트래픽(네트워크)을 컨테이너로 잘 전달해 주는 교통경찰.
  - **Container Runtime**: 실제로 컨테이너를 실행하는 엔진 (Containerd 등).
  - **Pod (파드)**: 쿠버네티스에서 컨테이너를 묶어서 배포하는 가장 작은 단위. (고래 등 위의 컨테이너).

```text
[ 쿠버네티스의 자율 치유(Self-Healing) 작동 원리 ]

 📜 [ 선언적(Declarative) 명세서 작성 ]
 엔지니어: "야 API 서버야, Nginx 웹서버 파드(Pod) 3대 항상 유지해라." (YAML 제출).
 
 🧠 [ Control Plane (마스터) ]
 API Server ➡️ etcd 장부에 "Nginx 3대 목표" 저장.
 Controller ➡️ "지금 0대네? 3대 만들어!" ➡️ Scheduler ➡️ "Node 1, 2, 3에 하나씩 띄워!"

 ⚙️ [ Worker Node (일꾼) ]
 Node 1 (Kubelet): "파드 1 띄움 완료!" / Node 2: "파드 2 띄움 완료!" / Node 3: "파드 3 띄움 완료!"
 
 💥 [ 장애 발생! Node 2가 불타서 파드 2 죽음 ]
 Controller (1초 뒤): "어? 장부에는 3대인데 지금 2대밖에 없네? Node 4에 하나 다시 띄워!!" (무한 반복 치유)
```

## Ⅲ. 비교 및 연결
| 구분 | Docker Compose | Kubernetes (K8s) |
|---|---|---|
| **역할 범위** | **단일 호스트(컴퓨터 1대)** 내의 컨테이너 묶음 실행 | **수십~수천 대의 클러스터(컴퓨터 무리)** 통합 관리 |
| **복구(Self-healing)**| 서버가 죽으면 끝남 (자동 복구 불가) | **다른 서버에서 알아서 즉시 부활시킴** |
| **확장성** | 수동으로 스케일 아웃 제한적 | HPA를 통한 완벽한 자동 오토 스케일링 |
| **비유** | 동네 오케스트라 지휘자 | **수천 척의 항공모함 전단을 통제하는 제독** |

## Ⅳ. 실무 적용 및 기술사 판단
- **선언적(Declarative) 상태 유지 사상**: 쿠버네티스의 철학은 "서버를 띄워라(명령형, Imperative)"가 아니라 **"항상 3대인 상태로 유지해라(선언형)"**임. 실무 아키텍트는 쉘 스크립트로 순서를 짜는 습관을 버리고, 이 선언적 YAML 파일들을 Git에 올려서 관리하는 **GitOps(ArgoCD 등)** 아키텍처를 구축해야, 인프라의 버전을 관리하고 재해 발생 시 1초 만에 클러스터를 복원할 수 있음.
- **매니지드 서비스 (EKS, GKE, AKS) 도입 원칙**: Control Plane(마스터 노드)의 etcd나 API 서버가 죽으면 회사 시스템이 다 날아감. 이걸 직접 설치(Kubeadm)해서 운영하는 건 자살 행위임. 실무에서는 반드시 AWS EKS나 GCP GKE 같은 매니지드 쿠버네티스 서비스를 사용하여 마스터 노드의 관리 책임을 클라우드 벤더에게 떠넘기고, 엔지니어는 워커 노드의 비즈니스 로직에만 집중하는 것이 절대적 글로벌 표준임.

## Ⅴ. 기대효과 및 결론
- "죽으면 다시 살려내고, 부족하면 늘려라"는 개발자의 로망을 분산 시스템 환경에서 완벽하게 자동화해 낸 클라우드 시대의 걸작.
- 단순히 컨테이너를 관리하는 툴을 넘어, AWS, Azure, On-premise 등 인프라의 종류에 상관없이 **"쿠버네티스라는 표준 OS 위에서만 코딩하면 전 세계 어디서든 똑같이 돌아간다"**는 인프라 종속성 해방을 이룩함.

### 👶 어린이를 위한 3줄 비유 설명
1. 수천 마리의 양(컨테이너)을 키우는 목장이에요. 양들이 울타리를 넘어가거나 아프면 사람이 다 돌보기 너무 힘들죠.
2. **쿠버네티스**는 '천재 목동 로봇(마스터 노드)'과 그를 돕는 '로봇 강아지들(워커 노드)'이에요.
3. 내가 "항상 하얀 양 3마리가 풀을 뜯게 해 줘!"라고 메모장(YAML)에 적어주면, 로봇들이 밤새워 감시하다가 한 마리가 도망가면 즉시 다른 하얀 양을 데려와서 완벽하게 3마리를 맞춰준답니다!
