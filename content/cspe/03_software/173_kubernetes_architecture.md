## 미리 알고가기

- 원하는 상태는 사용자가 API 객체에 선언한 Pod 수·이미지·정책·배치 조건임
- 실제 상태는 노드와 워크로드가 현재 실행 중인 상태임
- 조정 루프는 두 상태의 차이를 감지하고 생성·수정·삭제 요청으로 차이를 줄임
- Control Plane은 API·상태 저장·스케줄링·제어 루프를 담당함
- Worker Node는 kubelet·컨테이너 런타임·서비스 네트워크로 Pod를 실행함
- etcd는 Kubernetes API 객체의 상태를 저장하는 일관된 키-값 저장소임

## 작성 근거(검토용)

- Kubernetes의 핵심은 컨테이너 실행보다 원하는 상태와 실제 상태의 지속 조정이므로 이를 중심 명제로 둠
- Control Plane과 Worker Node를 역할·구성·상태·입력·출력·장애 영향으로 비교함
- 제목부터 결론까지 5회 전수 검수하여 구성요소 설명과 조정 흐름의 선후 관계를 확인함

## Ⅰ. 개요

- **정의/개념**: 쿠버네티스는 API의 원하는 상태를 Control Plane 조정 루프와 Worker Node 실행으로 유지하는 오케스트레이션 구조임
- **배경/필요성**: 다수 노드에서 배포·확장·복구 상태를 일관되게 유지하기 위해 선언형 API와 지속 조정 구조가 필요함

## Ⅱ. 특징

- 모든 객체 변경은 API 서버를 통과하고 승인·검증 후 etcd에 저장됨
- 컨트롤러는 객체 상태를 감시하고 원하는 상태와 실제 상태의 차이를 조정함
- 스케줄러는 미배치 Pod의 자원·정책 제약을 확인해 실행 노드를 바인딩함
- kubelet은 배정된 Pod를 CRI로 실행하고 상태·프로브 결과를 API 서버에 보고함

## Ⅲ. Control Plane과 Worker Node 비교

| 판단 기준 | Control Plane | Worker Node |
|:---|:---|:---|
| 핵심 역할 | 클러스터 상태 저장·판정·조정 | 배정된 Pod 실행·상태 보고 |
| 주요 구성 | API 서버·etcd·스케줄러·컨트롤러 관리자 | kubelet·컨테이너 런타임·kube-proxy 또는 대체 구현 |
| 관리 상태 | 원하는 상태와 클러스터 전역 객체 | 컨테이너·볼륨·네트워크의 노드 실제 상태 |
| 입력 | API 요청·객체 이벤트·노드 상태 | Pod 명세·구성 데이터·프로브 설정 |
| 출력 | 노드 바인딩·생성·수정·삭제 요청 | 실행 상태·자원 상태·프로브 결과 |
| 장애 영향 | 객체 변경·스케줄링·조정 지연 | 해당 노드의 Pod 중단과 대체 필요 |

> 요약: Control Plane은 원하는 상태를 판정하고 Worker Node는 배정된 Pod를 실행해 상태를 반환함.

## Ⅳ. 구성요소 및 구조

| 구성요소 | 역할 |
|:---|:---|
| kube-apiserver | Kubernetes API를 노출하고 인증·인가·승인·저장을 중개함 |
| etcd | API 객체와 클러스터 상태를 일관된 키-값으로 저장함 |
| kube-scheduler | 미배치 Pod의 실행 가능 노드를 필터링·점수화해 바인딩함 |
| kube-controller-manager | 객체별 조정 루프로 원하는 상태와 실제 상태의 차이를 줄임 |
| kubelet | 노드에 배정된 Pod의 컨테이너·볼륨·프로브 상태를 관리함 |
| 컨테이너 런타임 | CRI 요청으로 이미지와 컨테이너 수명주기를 관리함 |
| 서비스 네트워크 | Service와 Pod 통신을 노드 규칙이나 데이터 경로로 구현함 |

```text
사용자 -> API 서버 <-> etcd
             |  +-> 스케줄러
             |  +-> 컨트롤러 관리자
             v
          kubelet -> CRI 런타임 -> Pod
```

> 요약: API 서버와 etcd가 상태 중심을 이루고 스케줄러·컨트롤러·kubelet이 상태를 조정함.

## Ⅴ. 조정 원리 및 절차

```text
객체 제출 -> 인증·검증·저장 -> 차이 감지 -> 노드 바인딩 -> Pod 실행 -> 상태 환류
```

1. **객체 제출**: 사용자가 원하는 상태를 Deployment·Service 같은 API 객체로 전송함
2. **인증·검증·저장**: API 서버가 요청을 통제하고 승인된 객체를 etcd에 저장함
3. **차이 감지**: 컨트롤러가 원하는 복제본과 실제 Pod 수의 차이를 찾아 생성 요청함
4. **노드 바인딩**: 스케줄러가 실행 가능 노드를 고르고 Pod에 노드 이름을 기록함
5. **Pod 실행**: kubelet이 컨테이너·네트워크·스토리지 플러그인을 호출해 실행 환경을 준비함
6. **상태 환류**: kubelet이 실행 상태를 보고하고 컨트롤러가 남은 차이를 다시 조정함

> 요약: API에 저장된 원하는 상태가 컨트롤러·스케줄러·kubelet을 거쳐 실제 상태로 수렴함.

## Ⅵ. 실무 사례

1. 애플리케이션 클러스터는 Control Plane을 다중화하고 API 지연·etcd 쓰기 지연을 확인함
2. 배포 워크로드는 조정 상태를 추적하고 미배치 Pod 수·준비 완료시간을 확인함

## Ⅶ. 결론

- 쿠버네티스는 API 상태 저장과 조정 루프, 노드 실행 경계를 분리해 설계·운영해야 함
