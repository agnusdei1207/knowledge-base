# 📖 【암기용】 개념 완전 이해

## 한눈에
- **개요**: 쿠버네티스(K8s)는 수많은 컨테이너화된 애플리케이션의 배포, 확장, 관리를 자동화하는 분산 오케스트레이션 플랫폼 아키텍처이다.
- **왜 필요한가**: 컨테이너 수백~수천 개를 수동으로 띄우고 모니터링하며 장애를 복구하는 것은 불가능하므로, 이를 자동 조율할 지휘자가 필요하다.
- **핵심 직관**: 대규모 교향악단(클러스터)에서 지휘부(Control Plane)가 악보(원하는 상태)를 보고 연주자들(Worker Nodes)의 연주 상태를 지속적으로 교정(Reconciliation)하는 시스템이다.

## 핵심 용어 정리

| 용어/표기 | 의미 | 비유·예 |
|:---|:---|:---|
| 컨트롤 플레인 (Control Plane) | 클러스터 전체의 상태를 제어하고 결정을 내리는 두뇌 | "오케스트라 지휘자" |
| 워커 노드 (Worker Node) | 실제 컨테이너(파드)가 구동되는 작업 서버 머신 | "실제 연주를 하는 단원" |
| 파드 (Pod) | K8s의 최소 배포 단위 (1개 이상의 컨테이너 그룹) | "하나의 악기 파트" |
| 선언적 API (Declarative API) | '어떻게'가 아니라 '어떤 상태'가 되기를 원하는지 선언 | "온도를 25도로 맞춰줘 (에어컨 자동 제어)" |

## 깊이 이해
- **배경·문제의식**: 마이크로서비스 확산으로 컨테이너 개수가 기하급수적으로 늘어나자, 노드 장애 시 파드를 재배치하고 트래픽을 분산할 자동화된 스케줄러가 절실해졌다. 구글의 내부 시스템(Borg) 노하우를 바탕으로 K8s가 오픈소스로 등장했다.
- **작동 원리**: K8s는 사용자가 YAML 파일로 "원하는 상태(Desired State)"를 API 서버에 선언하면, 컨트롤 플레인의 컨트롤러들이 "현재 상태(Current State)"와 비교하여 다를 경우 지속적으로 일치시키는 "조정 루프(Reconciliation Loop)"를 돈다.
- **비유**: 실내 온도 조절기와 같다. 희망 온도(Desired)를 24도로 맞추면, 센서가 현재 온도(Current)를 측정하여 에어컨이나 히터를 가동해 지속적으로 24도를 유지한다.
- **구체 예시**: 웹 서버 파드를 3개로 선언(ReplicaSet)했는데 노드 1개가 죽어 파드 1개가 사라지면, 컨트롤러 매니저가 이를 감지하고 스케줄러를 통해 살아있는 다른 노드에 새 파드를 띄워 즉시 3개를 복구한다.
- **흔한 오해·주의점**: K8s는 만능 해결사가 아니다. 애플리케이션 코드를 자동으로 컨테이너화해주거나 소스코드를 빌드(CI)해주지 않는다. 철저히 이미 빌드된 컨테이너 이미지를 잘 배치하고 살려두는 "실행 환경 관리" 역할에 집중한다.

## 연결 개념
- etcd — 클러스터의 모든 데이터를 저장하는 분산 키-값 저장소
- Kubelet — 각 노드에서 파드의 생명주기를 직접 관리하는 에이전트
- 서비스 메시 (Istio) — K8s 위에서 마이크로서비스 간의 통신과 보안을 정밀 제어

# 📝 【답안용】 시험 답안 템플릿

## 핵심 인사이트 (3줄 요약)

> 1. **본질**: 쿠버네티스는 선언적 API와 조정 루프(Reconciliation Loop)를 통해 컨테이너의 원하는 상태를 지속 유지하는 분산 오케스트레이터이다.
> 2. **가치**: 인프라 장애에 대한 자가 치유(Self-healing), 자동 스케일링, 무중단 배포를 제공하여 클라우드 네이티브 운영을 자동화한다.
> 3. **판단 포인트**: 컨트롤 플레인(두뇌)과 워커 노드(실행)의 컴포넌트별 역할을 명확히 이해하고, 고가용성을 위한 etcd 및 마스터 노드 다중화 방안을 설계해야 한다.

## 출제 의도 및 답안 포인트

| 출제 의도 | 반드시 짚을 핵심 | 감점 회피 포인트 |
|:---|:---|:---|
| 클러스터 전체 아키텍처 및 구성요소 역할 이해 | Control Plane(API, Scheduler, Controller, etcd) vs Worker Node(Kubelet, Proxy) 분리 | 마스터와 워커의 구성요소를 혼용하여 서술 |

> 요약: 쿠버네티스의 선언적 상태 유지 원리(Reconciliation)를 기반으로 컨트롤 플레인과 워커 노드의 유기적 상호작용 구조를 제시해야 한다.

---

## Ⅰ. 개요 및 필요성

- 개요: 수많은 컨테이너 애플리케이션의 자동 배포, 스케일링, 운영을 제공하는 오픈소스 오케스트레이션 아키텍처
- 배경: MSA 도입으로 컨테이너 수가 급증하면서 수동 관리가 한계에 도달, 구글의 Borg 시스템을 기반으로 표준화된 플랫폼 등장
- 필요성: 노드 장애 시 자가 치유, 부하에 따른 오토 스케일링, 서비스 디스커버리를 제공하여 대규모 분산 시스템의 신뢰성을 보장하기 위함

---

## Ⅱ. 구조 및 구성요소

```text
User / kubectl -> [Control Plane] API Server <-> etcd (상태 저장)
                                     |-> Scheduler (노드 할당)
                                     +-> Controller Manager (상태 유지)
                       | (CRI/네트워크 통신)
                  [Worker Node] Kubelet -> Container Runtime -> Pod
                                Kube-Proxy -> Network / iptables
```

| 구성요소 | 역할 | 특이사항 |
|:---|:---|:---|
| API Server | 클러스터 제어 진입점 및 모든 REST API 통신 중계 | Control Plane 핵심, 단일 접점 |
| etcd | 클러스터의 모든 설정과 현재 상태를 저장하는 분산 DB | 일관성 확보 (Raft 합의 알고리즘) |
| Controller | 원하는 상태(Desired)와 현재 상태(Current)를 일치시키는 조정 역할 | ReplicaSet, Node 컨트롤러 등 |
| Scheduler | 새 파드를 실행할 최적의 워커 노드를 조건 기반으로 필터링/선택 | 리소스, Affinity 제약조건 평가 |
| Kubelet / Proxy | (워커 노드) 파드 실행/감시(Kubelet) 및 네트워크 라우팅(Proxy) | 노드당 1개 데몬으로 실행 |

> 요약: 컨트롤 플레인이 클러스터의 전반적 상태를 제어 및 저장(etcd)하고, 워커 노드의 Kubelet이 지시를 받아 파드를 구동하는 마스터-워커 분리 구조이다.

---

## Ⅲ. 동작원리 및 흐름도

```text
YAML 배포 요청 -> API 검증/저장 -> 파드 할당(Scheduling) -> 노드에서 파드 구동(Kubelet)
```

- 1단계 [선언적 요청 접수]: 관리자가 kubectl로 YAML을 제출하면 API Server가 문법 검증 후 etcd에 원하는 상태(Desired State) 저장
- 2단계 [상태 조정 및 생성]: Controller Manager가 etcd 변경을 감지하고 부족한 파드 갯수만큼 논리적 파드 객체 생성
- 3단계 [노드 스케줄링]: Scheduler가 생성된 파드를 감지하고 리소스 여유 및 규칙을 계산하여 적합한 워커 노드에 바인딩
- 4단계 [실제 파드 구동]: 할당된 워커 노드의 Kubelet이 이를 인지하고 컨테이너 런타임(CRI)을 호출하여 실제 프로세스 실행 및 상태 보고

> 요약: 모든 동작은 API Server를 중심축으로 하는 이벤트 기반 비동기 아키텍처로, 각 컴포넌트가 자신이 맡은 역할에 따라 조정 루프를 실행한다.

---

## Ⅳ. 특징

- [선언적 상태 관리]: 명령형(Imperative) 스크립트 실행이 아닌 상태 선언(Declarative) 방식을 통해 멱등성 보장
- [자가 치유 기능]: 워커 노드 다운 시 컨트롤러가 파드 손실을 감지하고 즉각 다른 건강한 노드에 새 파드를 재배포(Self-healing)
- [복잡한 러닝 커브]: 네트워크(CNI), 스토리지(CSI), 런타임(CRI) 등 추상화 레이어가 많아 구축 및 운영 트러블슈팅 난이도가 높음

> 요약: 쿠버네티스는 강력한 자가 치유와 확장성을 제공하지만, 아키텍처의 복잡성으로 인해 초기 구축 및 운영 역량 확보가 큰 장벽이다.

## Ⅴ. 심화 비교 및 적용 판단

| 비교 축 | Docker Swarm | Kubernetes | 선택 기준 |
|:---|:---|:---|:---|
| 아키텍처 복잡도 | 단순함 (학습/구축 쉬움) | 복잡함 (학습 곡선 가파름) | 조직의 인프라 운영 역량 |
| 확장성 / 생태계 | 소규모 적합, 생태계 작음 | 대규모 클러스터 적합, 사실상 표준 | 서비스 규모 및 미래 확장성 |
| 세부 제어 수준 | 기본 네트워킹/디스커버리 제공 | 강력한 롤백, RBAC, CNI 등 정밀 제어 | 엔터프라이즈 보안 요구사항 |

> 요약: 스타트업의 단순 구성에는 Swarm이 빠를 수 있으나, 엔터프라이즈 환경의 대규모 서비스와 장기 운영을 위해서는 쿠버네티스를 선택해야 한다.

**리스크·대응:**
- Control Plane 단일 장애점(SPOF): 마스터 노드 장애 시 클러스터 제어 불능 → API Server 다중화(LB) 및 etcd 클러스터링(3/5 홀수 노드 구성) (지표: 컨트롤 플레인 가용성 99.99%)
- 워커 노드 자원 고갈: 무분별한 파드 배치로 노드 OOM 발생 → 네임스페이스별 ResourceQuota 설정 및 파드 리소스 Limit 강제화 (지표: 노드 메모리 사용률 85% 유지)

## Ⅵ. 실무 적용 및 결론

**적용 방안 3개:**
1. 관리형 서비스 활용: 초기 구축 부담 완화 및 컨트롤 플레인 안정성 확보를 위해 클라우드 사업자의 Managed K8s(EKS, GKE, AKS) 적극 도입
2. 인프라 코드화(IaC): Terraform과 ArgoCD(GitOps)를 결합하여 쿠버네티스 리소스의 버전 관리 및 자동 배포 파이프라인 구축
3. 통합 관측성(Observability) 구축: Prometheus(메트릭 수집)와 Grafana를 연동하여 복잡한 컨테이너 동적 환경의 병목과 장애를 실시간 시각화

**결론 (2줄):**
- 기술사 판단: 쿠버네티스는 단순한 배포 도구를 넘어 클라우드 네이티브 환경의 인프라 표준 OS로 자리 잡았으므로, 마스터 노드의 고가용성 설계가 아키텍처의 성패를 가른다.
- 향후 방향: eBPF 기반의 고성능 네트워크(Cilium)와 서비스 메시(Istio)의 결합을 통해 네트워크 성능과 보안이 애플리케이션 투명하게 발전할 것이다.
