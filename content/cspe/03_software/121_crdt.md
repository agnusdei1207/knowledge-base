# 📖 【암기용】 개념 완전 이해

## 한눈에
- **개요**: 네트워크 지연이나 단절 상태에서도 각 노드가 독립적으로 데이터를 수정하고, 연결 회복 시 충돌 없이 병합할 수 있는 분산 데이터 구조이다.
- **왜 필요한가**: 구글 문서도구나 피그마처럼 여러 명이 동시에 같은 문서를 편집할 때, 중앙 서버를 거치지 않고도 각자의 변경 사항이 결국 똑같은 상태로 안전하게 합쳐져야 한다.
- **핵심 직관**: 수학적 교환법칙(A+B=B+A)과 결합법칙이 성립하는 연산만 허용하여, 어떤 순서로 데이터가 도착하든 최종 결과가 항상 같아지도록 보장한다.

## 핵심 용어 정리

| 용어/표기 | 의미 | 비유·예 |
|:---|:---|:---|
| CRDT | 충돌 없이 병합 가능한 복제 데이터 타입 | 서로 다른 길로 가도 결국 같은 목적지에 도착하는 지도 |
| CvRDT (State-based) | 상태 기반 CRDT, 전체 상태를 전송하여 병합 | 완성된 퍼즐판 전체를 주고받으며 맞추기 |
| CmRDT (Op-based) | 연산 기반 CRDT, 변경 연산만 전송하여 병합 | "왼쪽 위에 빨간색 조각 놔라"는 지시서만 주고받기 |
| 최종 일관성 (Eventual Consistency) | 당장은 다를 수 있지만 결국에는 같아짐 | 각자 은행 앱 잔고가 잠시 달라도 자정에는 맞춰짐 |

## 깊이 이해
- **배경·문제의식**: 분산 시스템에서 동시 수정을 허용하면 필연적으로 충돌이 발생한다. 기존에는 락(Lock)을 걸어 한 번에 한 명만 수정하게 하거나(성능 저하), 충돌 시 중앙 서버가 해결(단일 장애점)해야 했다. 오프라인 상태에서도 수정이 가능하고 충돌을 수학적으로 방지하는 구조가 필요해졌다.
- **작동 원리**: 데이터 타입 자체에 교환법칙(Commutativity), 결합법칙(Associativity), 멱등성(Idempotency)을 내재화한다. 덧셈은 순서가 상관없으므로(교환법칙), 각 노드의 증가/감소 연산을 단순히 취합하기만 해도 최종 값이 같아진다. 텍스트 편집의 경우 글자의 '절대 위치' 대신 '문자 간의 상대적 순서(ID)'를 부여하여 중간에 삽입해도 충돌하지 않게 한다.
- **비유**: 칠판에 각자 정바른(正) 자를 그어 투표수를 세는 것과 같다. A가 먼저 긋든 B가 먼저 긋든 총 획수는 같다(순서 무관).
- **구체 예시**: 구글 문서에서 A는 1번째 줄에 "Hello"를, B는 2번째 줄에 "World"를 오프라인에서 동시에 쓴다. 온라인 연결 시 두 변경사항이 각자의 고유 ID와 상대적 위치를 기반으로 병합되어 "Hello\nWorld"로 똑같이 맞춰진다.
- **흔한 오해·주의점**: CRDT가 만능은 아니다. 데이터 크기가 무한히 커질 수 있으므로(가비지 컬렉션 필요) 텍스트 편집이나 카운터 같은 특정 데이터 타입에만 적용 가능하다. 은행 송금처럼 음수 잔고를 허용하지 않는 '불변 조건'이 있는 경우에는 적합하지 않다.

## 연결 개념
- OT(Operational Transformation) — CRDT 이전의 동시 편집 기술, 중앙 서버 의존적
- 최종 일관성 (Eventual Consistency) — 분산 DB의 일관성 모델
- PACELC 정리 — 분산 시스템 트레이드오프

# 📝 【답안용】 시험 답안 템플릿

## 핵심 인사이트 (3줄 요약)

> 1. **본질**: 분산 환경에서 동시 업데이트 충돌을 수학적 특성(교환·결합·멱등성)을 이용해 알고리즘적으로 해결하는 복제 데이터 구조이다.
> 2. **가치**: 락(Lock) 없는 동시성 제어로 네트워크 단절 시에도 로컬 수정이 가능하며, 높은 가용성과 최종 일관성을 보장한다.
> 3. **판단 포인트**: 상태 기반(CvRDT)과 연산 기반(CmRDT)의 트레이드오프를 이해하고, 공동 편집·분산 캐시 등 충돌 없는 병합이 필요한 도메인에 적용한다.

## 출제 의도 및 답안 포인트

| 출제 의도 | 반드시 짚을 핵심 | 감점 회피 포인트 |
|:---|:---|:---|
| 분산 시스템 동시성 제어 한계 극복 역량 확인 | 수학적 속성(교환·결합·멱등성), CvRDT/CmRDT 비교 | OT와의 차이 누락, 범용 DB 기술로 과장 |

> 요약: 락 없는 분산 동시성 제어 기법인 CRDT의 수학적 원리와 두 가지 접근법(상태/연산)을 비교 판단하는 것이 핵심이다.

---

## Ⅰ. 개요 및 필요성

- 개요: 네트워크 지연·단절 환경에서도 노드 간 독립적 수정을 허용하고, 연결 시 충돌 없이 상태를 병합하는 복제 데이터 타입
- 배경: 기존 분산 락(Lock)이나 OT(Operational Transformation)는 중앙 서버 통신 오버헤드와 단일 장애점(SPOF) 한계 존재
- 필요성: 실시간 협업 도구, 엣지 컴퓨팅 확산에 따라 오프라인 수정 허용 및 가용성 99.99% 보장을 위한 충돌 자동 해결 메커니즘 필요

---

## Ⅱ. 구조 및 구성요소

```text
Node A (Update) -> Local State A -> Network Sync -> Merge(A, B) -> Final State
                                                      |
Node B (Update) -> Local State B -> Network Sync -----+
```

| 구성요소 | 역할 | 특이사항 |
|:---|:---|:---|
| Local State | 각 노드가 유지하는 독립적인 데이터 상태 | 오프라인 수정 허용 |
| Update Operation | 상태를 변경하는 로컬 연산 | 즉각적인 응답성 제공 |
| Merge Function | 수신된 상태나 연산을 로컬과 병합 | 교환·결합·멱등성 보장 |

> 요약: 노드별 로컬 상태를 독립적으로 업데이트한 후, 수학적 병합 함수를 통해 최종 일관된 상태를 도출한다.

---

## Ⅲ. 동작원리 및 흐름도

```text
초기 상태 확보 -> 로컬 연산 수행 -> 상태/연산 전파 -> 충돌 없는 병합
```

- 1단계 [초기 상태 확보]: 노드 A와 B가 동일한 초기 상태(예: Counter=0)를 공유
- 2단계 [로컬 연산 수행]: 노드 A(+1)와 노드 B(+2)가 네트워크 단절 상태에서 각각 로컬 업데이트
- 3단계 [상태/연산 전파]: 네트워크 연결 복구 시 변경된 상태(CvRDT) 또는 연산 내역(CmRDT)을 상호 브로드캐스트
- 4단계 [충돌 없는 병합]: Merge 함수를 통해 순서와 무관하게 동일한 최종 상태(+3)로 수렴

> 요약: 로컬 수정 후 상태나 연산을 교환하고, 수학적 속성에 기반한 Merge 함수로 최종 일관성을 달성한다.

---

## Ⅳ. 특징

- 분산 노드 자율성 보장: 중앙 서버나 락(Lock) 없이 로컬에서 즉시 쓰기 연산 처리 (응답 지연 < 10ms)
- 오프라인 동작 지원: 네트워크 단절 시에도 정상 서비스 후 복구 시 자동 동기화
- 데이터 타입 제한: 카운터(G-Counter), 레지스터(LWW-Register), 집합(OR-Set) 등 수학적 병합이 가능한 구조로 한정

> 요약: 중앙 통제 없는 높은 가용성과 오프라인 동작을 지원하지만, 적용 가능한 데이터 구조가 제한적이다.

---

## Ⅴ. 심화 비교 및 적용 판단

| 비교 축 | CvRDT (상태 기반) | CmRDT (연산 기반) | 선택 기준 |
|:---|:---|:---|:---|
| 전송 대상 | 변경된 로컬 상태 전체 | 개별 업데이트 연산 | 네트워크 대역폭 여유도 |
| 병합 요구속성 | 교환·결합·멱등성 | 교환법칙 | 연산의 멱등성 확보 여부 |
| 네트워크 요구 | 신뢰성 낮아도 됨(재전송 용이) | 신뢰성 있는 채널(순서 무관, 유실 금지) | 인프라 신뢰도 및 메시지 브로커 유무 |

> 요약: 대역폭이 충분하면 구현이 단순한 CvRDT를, 네트워크 페이로드 최소화가 필요하면 CmRDT를 선택한다.

**리스크·대응 (기본은 불릿):**
- 상태 비대화(Metadata Bloat): 삭제(Tombstone) 누적으로 메모리 증가 → 가비지 컬렉션(GC) 주기적 수행 (지표: 메모리 사용량)
- 메시지 유실(CmRDT): 연산 누락 시 상태 불일치 → 신뢰성 있는 메시지 큐(Kafka 등) 연동 (지표: 메시지 전송 성공률)

**도입 후 점검 지표 (기본은 불릿):**
- 성능/효율: 99퍼센타일 동기화 지연시간 50ms 이하 — APM 트레이싱
- 품질/운영: 노드 간 최종 상태 불일치 비율 0% — 주기적 해시 비교

---

## Ⅵ. 실무 적용 및 결론

**적용 방안 3개:**
1. 실시간 협업 도구: 구글 문서, 피그마 등에서 동시 텍스트/객체 편집 시 문자열/트리 CRDT 적용하여 충돌 방지
2. 엣지 컴퓨팅 데이터 동기화: IoT 디바이스의 간헐적 네트워크 연결 환경에서 로컬 센서 데이터 수집 후 일괄 병합
3. 분산 캐시 정합성: 다중 리전 Redis Active-Active 아키텍처에 CRDT를 적용하여 리전 간 쓰기 충돌 자동 해결

**결론 (2줄):**
- 기술사 판단: CRDT는 충돌 없는 동시성을 제공하지만 메타데이터 오버헤드가 크므로, 강한 일관성이 필요한 금융 트랜잭션보다는 높은 가용성이 요구되는 협업 도구에 적용해야 한다.
- 향후 방향: JSON 등 복잡한 문서 구조를 지원하는 문서형 CRDT(Automerge, Yjs)의 표준화 및 WASM 기반 웹 클라이언트 통합이 가속화될 것이다.
