## 핵심 인사이트 (3줄 요약)
- 구글 독스(Docs)나 피그마(Figma)처럼 **여러 명의 사용자가 동시에 같은 문서를 실시간으로 수정할 때, 서버 간의 복잡한 동기화(Lock) 없이도 데이터의 충돌을 자동으로, 수학적으로 완벽하게 병합(Merge)해 주는 궁극의 분산 데이터 구조**.
- 기존의 OT(Operational Transformation) 알고리즘은 중앙 서버가 모든 편집 순서를 제어해야 해서 서버 부하가 컸지만, CRDT는 각 사용자의 기기(Client)에서 발생한 변경 사항들을 나중에 섞기만 해도 순서에 상관없이 똑같은 결과가 나옴 (교환법칙 성립).
- '최종 일관성(Eventual Consistency)'을 달성하기 위한 가장 우아하고 진보된 데이터 타입으로, 협업 툴(Collab)과 분산 NoSQL 데이터베이스(Riak, Redis)의 핵심 엔진으로 쓰임.

## Ⅰ. 개요 및 필요성
- **개요**: 네트워크 지연이나 단절 상태에서도 각 노드가 독립적으로 데이터를 수정하고, 다시 연결되었을 때 충돌 없이(Conflict-free) 병합되어 동일한 상태(수렴)에 도달함을 보장하는 데이터 타입.
- **필요성**: A와 B가 동시에 구글 독스의 같은 줄을 수정함. 서버가 없거나 네트워크가 끊겨서 "누가 먼저 썼는지(시간 순서)"를 알 수 없음. 과거에는 나중에 쓴 글로 덮어버리거나(데이터 유실), 사용자에게 충돌창(Git Conflict)을 띄웠음. 사람의 개입 없이, 오프라인 상태에서 막 편집한 내용조차 온라인이 되었을 때 기적처럼 스르륵 합쳐지는 마법의 자료구조가 필요했음.
---
## Ⅱ. 아키텍처 및 핵심 원리
- **CRDT의 수학적 원리 (수렴성)**:
  - **교환법칙(Commutativity)**: 덧셈(A+B = B+A)처럼, 철수의 수정 사항과 영희의 수정 사항이 어떤 순서로 서버에 도착하든 최종 결과는 무조건 동일해야 함.
  - **멱등성(Idempotency)**: 교집합(A ∩ A = A)처럼, 네트워크 에러로 똑같은 수정 메시지가 두세 번 중복 도착해도 한 번만 적용된 것처럼 처리되어야 함.
- **CRDT의 두 가지 방식**:
  1. **CvRDT (State-based CRDT)**:
     - 자신의 전체 상태(전체 문서)를 통째로 이웃 노드에게 보냄. 노드끼리 상태를 수학적 `Merge` 함수로 합침. (데이터가 작을 때 유리).
  2. **CmRDT (Operation-based CRDT)**:
     - "3번째 줄에 '가'를 추가했어"라는 '조작(Operation)' 이벤트만 보냄. 메시지 큐(네트워크)가 순서를 보장해야 하지만 페이로드가 가벼워 구글 독스 등 실시간 텍스트 에디터에 많이 쓰임.
- **대표적인 CRDT 자료구조**:
  - G-Counter (오직 증가만 하는 카운터), PN-Counter (증감 카운터, 유튜브 조회수), LWW-Element-Set (최종 시간 승자 세트).

```text
[ CRDT 작동 방식의 직관적 예시 (쇼핑몰 장바구니 합치기) ]

 🌐 [ 휴대폰 (오프라인 상태) ] ➡️ 장바구니에 [사과, 바나나] 추가
 💻 [ PC (온라인 상태) ] ➡️ 장바구니에 [포도, 사과] 추가
 
 (나중에 휴대폰이 온라인으로 연결됨!)
 🚨 일반 DB: PC가 나중에 쓴 줄 알고 폰 데이터 [바나나]가 증발하거나 충돌 창 띄움.
 
 🪄 [ CRDT (Set 구조) 병합 ]
 - 휴대폰 Set ∪ PC Set = {사과, 바나나} ∪ {포도, 사과} 
 - 결과: {사과, 바나나, 포도} ➡️ **중앙 서버 개입 없이 100% 충돌 없는 병합 성공!**
```

## Ⅲ. 비교 및 연결
| 구분 | Pessimistic Lock (RDBMS) | OT (Operational Transformation) | CRDT |
|---|---|---|---|
| **충돌 방지 원리** | 락(Lock)을 걸어 한 명씩 순서대로 씀 | 중앙 서버가 시간/인덱스 순서를 재계산함 | **수학적 집합 연산으로 무조건 병합됨** |
| **중앙 서버 의존도**| 100% 의존 (DB 락) | 100% 의존 (서버가 연산 다 해줘야 함) | **완전 분산형 (P2P 통신만으로도 가능)** |
| **속도 및 확장성**| 매우 느림 | 중앙 서버 병목 발생 (구형 구글 독스) | **압도적으로 빠르고 무한히 확장 가능** |
| **단점 (오버헤드)**| 동시 편집 불가 | 구현이 지옥처럼 복잡하고 버그 잡기 힘듦 | **삭제된 메타데이터를 계속 들고 있어 메모리가 뚱뚱해짐(Tombstone 문제)** |

## Ⅳ. 실무 적용 및 기술사 판단
- **협업 애플리케이션의 판도 변화**: 노션(Notion), 피그마(Figma), 애플 메모 앱 등 동시 편집 기능이 들어간 현대 SaaS 제품들은 대부분 밑바닥에 CRDT(또는 Yjs, Automerge 같은 오픈소스 라이브러리)를 깔고 있음. 기술사는 동시 편집 기능을 설계할 때, 서버 비용이 비싸고 구시대적인 OT 알고리즘 대신, 클라이언트 브라우저에서 병합 연산을 분산 처리하는 CRDT 아키텍처를 최우선으로 검토해야 함.
- **분산 DB에서의 활용**: Redis Enterprise의 Active-Active(멀티 마스터) 복제본이나, 분산 NoSQL인 Riak에서 데이터 충돌(Conflict)이 났을 때 사람이 개입하지 않고 시스템이 스스로 해결하게 만드는 기본 자료구조로 쓰이고 있음.

## Ⅴ. 기대효과 및 결론
- "사용자들은 오프라인 환경(비행기 안)에서도 문서를 편집하고 싶어 하고, 온라인이 되는 순간 다른 사람의 편집본과 완벽하게 융합되길 원한다"는 극한의 UX 요구사항을 수학적으로 해결한 컴퓨터 공학의 걸작임.
- 최종 일관성(Eventual Consistency)이라는 다소 뜬구름 잡는 철학을, 개발자가 라이브러리 형태로 직접 가져다 쓸 수 있도록 구현해 낸 '실전 자료구조'의 끝판왕임.

### 👶 어린이를 위한 3줄 비유 설명
1. 철수와 영희가 같은 도화지(문서)에 그림을 그리고 싶어요. 옛날 방식(DB 락)은 붓 하나를 두고 번갈아 가며 그려야 해서 답답했어요.
2. 그래서 투명한 셀로판지 2장을 주고, 철수와 영희가 각자 자기 방에서 맘대로 그림을 그리게 했어요.
3. 나중에 선생님이 그 두 장의 투명한 셀로판지를 겹치기(CRDT 병합)만 하면, 한 도화지에 그린 것처럼 훌륭한 그림이 완성된답니다! 싸울 일(충돌)이 전혀 없죠!
