# 📖 【암기용】 개념 완전 이해

## 한눈에
- **개요**: 운영체제 또는 런타임 환경이 스레드에게 CPU를 할당하는 방식과, 스레드 생성/소멸 오버헤드를 줄이는 스레드 풀 구조
- **왜 필요한가**: 스레드가 가볍다 해도 요청마다 생성/소멸을 반복하면 성능이 저하된다. 또한 커널이 관리하는 스레드와 사용자가 관리하는 스레드의 매핑 방식에 따라 동시성 효율이 크게 달라진다.
- **핵심 직관**: 스레드 풀은 "식당의 고정 직원(스레드)들"이다. 손님(요청)이 올 때마다 직원을 새로 뽑지(생성) 않고, 대기 중인 직원을 배정해 응대시킨다.

## 핵심 용어 정리

| 용어/표기 | 의미 | 비유·예 |
|:---|:---|:---|
| 커널 수준 스레드 (KLT) | 운영체제 커널이 직접 관리하고 스케줄링하는 스레드 | 국가 공인 면허증을 가진 직원 |
| 사용자 수준 스레드 (ULT) | 애플리케이션(라이브러리)이 관리하는 가벼운 스레드 | 사내에서 자체 관리하는 인턴 |
| 스레드 풀 (Thread Pool) | 미리 생성해 둔 스레드 집합 | 매장 대기 직원 그룹 |
| LWP (Lightweight Process)| ULT와 KLT를 연결해주는 중간 다리 | 사내 인턴을 공인 직원과 연결하는 관리자 |

## 깊이 이해
- **배경·문제의식**: KLT는 안정적이지만 생성/전환 시 커널 모드 진입이라는 오버헤드가 있다. 반면 ULT는 커널 개입이 없어 매우 빠르지만, 하나의 ULT가 I/O 대기에 빠지면 프로세스 전체가 멈추는(Block) 치명적 단점이 있다. 이를 해결하기 위해 여러 다대다(N:M) 모델이나 가상 스레드가 등장했다.
- **작동 원리 (스레드 풀)**:
  1. 서버 시작 시 일정 수(예: 10개)의 스레드를 생성해 둔다(Pool).
  2. 작업(Task) 큐에 요청이 들어오면 대기 중인 스레드가 가져가서 처리한다.
  3. 처리가 끝나면 스레드는 종료되지 않고 다시 Pool로 돌아와 대기한다.
- **구체 예시**: 1만 개의 동시 접속이 들어올 때 매번 `new Thread()`를 하면 메모리 고갈과 컨텍스트 스위칭으로 서버가 죽는다. 대신 200개의 스레드 풀을 두고, 나머지 9800개는 큐에서 대기시키면 안정적으로 모두 처리할 수 있다.
- **흔한 오해·주의점**: 스레드 풀을 무작정 크게(예: 10,000개) 잡으면 좋지 않다. 스레드 수가 코어 수를 너무 넘어서면 오히려 잦은 스위칭 비용(Thrashing) 때문에 전체 성능이 떨어진다. I/O 중심이냐 연산 중심이냐에 따라 풀 크기를 다르게 튜닝해야 한다.

# 📝 【답안용】 시험 답안 템플릿

## 핵심 인사이트 (3줄 요약)

> 1. **본질**: 스레드 스케줄링은 ULT와 KLT 간의 매핑 모델(1:1, N:1, N:M)을 결정하며, 스레드 풀은 재사용을 통해 생성/소멸 오버헤드를 제거하는 아키텍처 패턴이다.
> 2. **가치**: 대규모 동시성(Concurrency) 환경에서 시스템 자원 고갈을 방지하고 예측 가능한 응답 시간을 제공한다.
> 3. **판단 포인트**: CPU 바운드는 코어 수 수준으로, I/O 바운드는 대기 시간을 고려하여 넉넉하게 풀 사이즈를 튜닝하는 것이 핵심이다.

## 출제 의도 및 답안 포인트

| 출제 의도 | 반드시 짚을 핵심 | 감점 회피 포인트 |
|:---|:---|:---|
| 스레드 스케줄링 매핑 모델의 장단점 이해 | 커널/사용자 스레드, 1:1, N:1, N:M 모델 | 스레드 풀과 스케줄링 모델 혼동 |
| 스레드 풀의 필요성 및 동작 원리 | Task Queue, Worker Thread 재사용 메커니즘 | 단순 "빠르다"는 추상적 서술 |
| 워크로드 특성에 따른 최적화 방안 | I/O 바운드 vs CPU 바운드의 풀 사이즈 공식 | "무조건 스레드를 많이 만든다"는 단정 |

> 요약: 스레드 자원 관리는 KLT/ULT 매핑 모델로 OS 차원의 병목을 풀고, 스레드 풀로 애플리케이션 차원의 생성 오버헤드를 통제한다.

---

## Ⅰ. 개요 및 필요성

- 개요: 다중 스레드 환경에서 사용자 스레드와 커널 스레드를 매핑하여 CPU를 할당하는 방식과, 스레드를 사전 생성하여 재사용하는 자원 풀링 기법
- 배경: 요청마다 스레드를 동적 생성/소멸할 경우 발생하는 커널 호출 오버헤드와 메모리 단편화 문제
- 필요성: 고성능 웹 서버 및 대규모 트랜잭션 시스템에서 자원 고갈(OOM)을 막고 시스템 스루풋(Throughput)을 일정하게 방어하기 위해 필수

---

## Ⅱ. 구조 및 구성요소 (스레드 매핑 및 스레드 풀)

```text
[요청] -> Task Queue (대기열)
            |
[Thread Pool] -> Worker Thread 1 (User Level Thread) --(매핑)--> LWP/KLT
              -> Worker Thread 2 (User Level Thread) --(매핑)--> LWP/KLT
```

| 구성요소 | 역할 | 특이사항 |
|:---|:---|:---|
| 사용자 스레드 (ULT) | 애플리케이션 라이브러리(예: Pthreads, Green Thread)가 관리 | 커널 개입 없어 전환 빠름 |
| 커널 스레드 (KLT) | 운영체제 커널이 직접 관리하고 스케줄링 단위로 인식 | 1:1 매핑 시 병렬성 보장 |
| LWP (Lightweight Process) | ULT와 KLT 사이의 브리지 역할 수행 | 다대다(N:M) 모델에서 활용 |
| 스레드 풀 (Thread Pool) | 고정/유동 개수의 Worker Thread 집합과 작업 큐 | 자원 재사용 및 병목 완충 |

> 요약: 스레드 풀은 외부 요청을 큐로 완충하고, 워커 스레드는 LWP/KLT를 통해 실제 물리 코어에서 실행된다.

---

## Ⅲ. 동작원리 및 흐름도

```text
클라이언트 요청 -> [분기 1: 풀 내 유휴 스레드 존재 시] -> 즉시 할당
  -> [분기 2: 풀 가득 참] -> Task Queue 대기
  -> 워커 스레드 작업 완료 -> 스레드 반환 및 큐에서 다음 작업 인출
```

- 1단계 [초기화]: 서버 기동 시 설정된 Core/Max Thread 수치만큼 Worker Thread를 미리 생성하여 대기 상태로 유지
- 2단계 [태스크 인입]: 외부 요청이 들어오면 Task Queue에 적재되고, 유휴 상태인 워커 스레드가 이를 Fetch함
- 3단계 [매핑 및 실행]: 워커 스레드(ULT)는 OS에 의해 KLT와 매핑(1:1 또는 N:M)되어 CPU 코어에서 병렬 처리
- 4단계 [반환 및 대기]: 작업이 끝나면 스레드를 소멸시키지 않고 풀로 반환하여 다음 태스크를 기다림

> 요약: 스레드 생성 오버헤드를 시스템 부팅 시점으로 전가하고, 실행 시간에는 큐잉과 재사용만 수행하여 응답성을 극대화한다.

---

## Ⅳ. 특징

- 매핑 모델의 진화: 과거 N:1 모델은 하나의 I/O 블로킹이 전체를 멈추게 했으나, 현대 범용 OS는 관리 단순성과 진정한 병렬성을 위해 주로 1:1 매핑을 사용함
- 자원 통제(Throttling): 스레드 풀은 동시에 실행되는 태스크의 상한선을 강제하므로, 과부하(Spike) 시에도 시스템 전체의 크래시를 방지함
- 스위칭 오버헤드: 스레드 풀 크기를 코어 수에 비해 지나치게 크게 설정하면, 캐시 플러시 등 컨텍스트 스위칭 비용이 연산 이득을 압도(Thrashing)함

> 요약: 스레드 풀은 시스템을 안정화하는 방파제 역할을 하지만, 매핑 방식과 풀 사이즈에 따라 성능이 민감하게 변한다.

---

## Ⅴ. 심화 비교 및 적용 판단

| 비교 축 | 다대일 (N:1) 매핑 | 일대일 (1:1) 매핑 | 선택 기준 |
|:---|:---|:---|:---|
| 커널 개입 | 없음 (순수 ULT 스케줄링) | 높음 (KLT와 1:1 대응) | 스위칭 속도 vs 병렬성 |
| 멀티코어 활용 | 불가능 | 완전한 병렬 실행 가능 | 현대 하드웨어 아키텍처 |
| Blocking 영향 | 한 스레드 Block 시 전체 멈춤 | 독립적 실행 보장 | I/O 중심 여부 |

> 요약: 현대 범용 OS(Linux/Windows)는 1:1 모델을 기본 채택하되, 대규모 I/O 환경에서는 Go의 Goroutine 같은 N:M 경량 스레드로 회귀·발전 중이다.

**리스크·대응 (기본은 불릿):**
- 풀 사이즈 과다(Thrashing): 스레드가 너무 많아 스케줄링 오버헤드 폭증 → CPU 바운드 작업은 `코어 수 + 1`로 풀 사이즈 제한 (지표: Context Switch rate)
- 태스크 큐 OOM: 요청 폭증 시 큐가 무한정 커져 메모리 고갈 → Bounded Queue 적용 및 초과 요청에 대한 거절(Fail-fast / 429 Too Many Requests) 처리

**도입 후 점검 지표 (기본은 불릿):**
- 성능/효율: Active Thread 수, Task Queue 대기열 길이
- 품질/운영: 스레드 고갈(Thread Starvation) 발생 빈도, 평균 응답 시간

---

## Ⅵ. 실무 적용 및 결론

**적용 방안 3개 (필수 — 단계별 또는 항목별):**
1. 풀 사이즈 튜닝 공식 적용: I/O 바운드 작업의 경우 `코어 수 × [1 + (Wait Time / Compute Time)]` 공식을 활용해 대기 시간을 커버할 충분한 워커 확보
2. 격리된 스레드 풀(Bulkhead Pattern): 결제, 조회 등 업무 중요도나 지연율에 따라 스레드 풀을 물리적으로 분리하여 특정 서비스의 지연이 전체로 전파되지 않게 격리
3. 비동기 논블로킹 전환: 스레드 풀 튜닝만으로 한계 도달 시, Netty나 Node.js와 같은 이벤트 루프(Event Loop) 기반 아키텍처로 전환하여 스레드 점유 최소화

**결론 (2줄):**
- 기술사 판단: 스레드 풀은 자원 재사용의 핵심 패턴이나, I/O 블로킹 발생 시 유휴 스레드가 낭비되므로 애플리케이션의 워크로드 특성 파악이 선행되어야 한다.
- 향후 방향: Java 21의 가상 스레드(Virtual Thread) 도입처럼, 수백만 개의 ULT를 소수의 KLT에 N:M으로 동적 매핑하는 경량 런타임이 차세대 표준으로 자리잡고 있다.
