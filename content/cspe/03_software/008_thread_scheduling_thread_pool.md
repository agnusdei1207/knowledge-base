## Ⅰ. 개요
- **정의**: 다수 스레드에 CPU 시간을 배분하고 스레드 풀로 생성 비용을 절감하는 기법
- **배경/필요성**: 스레드 과다 생성에 따른 컨텍스트 스위칭 오버헤드와 자원 낭비 방지가 필요함
- **비유**: 매번 새 직원을 고용하는 대신 상주 인력 풀에서 업무를 배분하는 것임

| 출제 의도 | 반드시 짚을 핵심 | 감점 회피 포인트 |
|:---|:---|:---|
| ULT/KLT 차이와 스레드 풀 설계 | M:N 매핑 모델 구분 | 스레드 풀 크기 산정 근거 언급 필요 |

> 요약: 스레드 매핑 모델과 풀 기반 재사용으로 병렬 처리 효율을 높이는 기법임

## Ⅱ. 구성요소
```text
User Thread --> Thread Library --> Kernel Thread --> CPU Core
   (ULT)        (M:N Mapping)       (KLT)          (Dispatch)
                      |
               Thread Pool (Worker Reuse)
```

| 구성요소 | 설명 | 비유 |
|:---|:---|:---|
| ULT(User Level Thread) | 커널 개입 없이 라이브러리가 관리하는 스레드 | 팀 내부 업무 분담 |
| KLT(Kernel Level Thread) | OS 커널이 직접 스케줄링하는 스레드 | 본사 인사팀 배치 |
| M:N 매핑 | M개 ULT를 N개 KLT에 다중 사상하는 모델 | 다수 업무를 소수 담당자에 배분 |
| Thread Pool | 미리 생성한 워커 스레드를 큐 기반으로 재사용하는 구조 | 상주 인력 풀 |

> 요약: ULT-KLT 매핑과 스레드 풀 재사용이 핵심 구성요소임

## Ⅲ. 절차
```text
풀 초기화 --> 태스크 큐 등록 --> 워커 할당 --> 실행완료/반환
```
- 1단계: 시스템 기동 시 설정된 수의 워커 스레드를 미리 생성(풀 초기화)
- 2단계: 작업 요청이 도착하면 태스크 큐에 등록
- 3단계: 유휴 워커 스레드가 큐에서 태스크를 꺼내어 실행
- 4단계: 실행 완료 후 워커 스레드를 풀에 반환하여 재사용

> 요약: 사전 생성-큐 등록-워커 할당-반환 순환으로 스레드 생성 비용을 제거함

## Ⅳ. 문제점
- 풀 크기 부적정: 과소 설정 시 대기, 과대 설정 시 메모리 낭비 — 최적 크기 산정이 어려움
- ULT 블로킹 전파: ULT가 I/O 블로킹 시 매핑된 KLT 전체 차단 — 병렬성 손실 발생
- 태스크 큐 경합: 다수 워커가 단일 큐 접근 — 락 경합으로 처리량 저하

> 요약: 풀 크기 산정, 블로킹 전파, 큐 경합이 주요 성능 병목임

## Ⅴ. 개선방안
1. 단기: CPU 코어 수·I/O 대기 비율 기반 공식으로 풀 크기를 동적 산정
2. 중기: 비동기 I/O(epoll, io_uring)와 코루틴 결합으로 블로킹 전파 차단
3. 장기: Work-Stealing 큐(코어별 로컬 큐 + 도용) 도입으로 큐 경합 해소

> 요약: 동적 크기 산정, 비동기 I/O, Work-Stealing으로 스레드 풀 효율을 개선함

## Ⅵ. 전망
- 발전 방향: 가상 스레드(Java Virtual Thread), 코루틴 등 경량 동시성 모델로 전환 가속
- 기술사적 판단: 스레드 풀은 여전히 유효하나 경량 스레드와 결합하는 하이브리드 모델이 주류화됨
- 기술사 제언: 워크로드 특성(CPU-bound/IO-bound) 분석 후 동시성 모델을 선택할 필요
