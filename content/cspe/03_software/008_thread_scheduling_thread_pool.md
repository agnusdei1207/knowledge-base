# 📖 【암기용】 개념 완전 이해

## 한눈에
- **개요**: 스레드 스케줄링(Thread Scheduling)은 CPU에 배정할 대상을 프로세스가 아닌 **스레드 단위**로 고르는 것이고, 스레드 풀(Thread Pool)은 스레드를 매번 만들고 없애는 대신 **미리 만들어 둔 스레드를 재사용**하며 작업 큐로 일을 나눠 주는 실행 패턴이다.
- **왜 필요한가**: 스레드는 프로세스보다 가볍지만(001 참조) 그래도 생성·소멸에는 스택 할당·커널 등록 비용이 든다. 요청마다 스레드를 새로 만들면 부하가 몰릴 때 스레드가 폭증해 메모리가 고갈되고 문맥 전환만 하다 끝난다. 그래서 개수를 미리 제한해 재사용하는 구조가 필요하다.
- **핵심 직관**: 스레드 스케줄링은 "어느 작업자에게 다음 일을 줄까"이고, 스레드 풀은 콜센터의 고정 상담원 배치다. 전화(작업)가 오면 새 상담원을 채용(스레드 생성)하는 게 아니라, 대기 중인 상담원이 대기열(작업 큐)에서 하나씩 받아 처리하고 끝나면 다시 대기로 돌아간다.

## 핵심 용어 정리 (내부에 등장하는 것들)

아래 답안용에 나오는 스레드 매핑·풀·큐 용어를 비유와 함께 먼저 세운다. 맨 위가 이 주제의 상위 핵심 키워드다.

| 용어/표기 | 의미 | 비유·예 |
|:---|:---|:---|
| 스레드 스케줄링 (상위 키워드) | CPU 배정 대상을 스레드 단위로 고르는 것 | 어느 작업자에게 다음 일을 줄지 결정 |
| 커널 스레드 (Kernel-Level Thread) | OS 커널이 인지·직접 스케줄링하는 스레드 | 회사에 정식 등록된 직원 |
| 유저 스레드 (User-Level Thread) | 런타임 라이브러리가 사용자 영역에서 관리 | 반장이 사적으로 굴리는 인력 |
| 1:1 매핑 | 유저 스레드 1개당 커널 스레드 1개 | 직원마다 회사 등록증 1장 |
| M:N 매핑 | 유저 스레드 M개를 커널 스레드 N개에 다중화 | 반장이 인력 여럿을 소수 등록증에 돌려 씀 |
| 스레드 풀 (Thread Pool) | 미리 생성해 재사용하는 스레드 집합 | 상시 대기 상담원 팀 |
| 작업 큐 (Work Queue / Task Queue) | 처리 대기 중인 작업을 담는 대기열 | 콜센터 대기 통화 목록 |
| 워커 스레드 (Worker Thread) | 큐에서 작업을 꺼내 실행하는 풀 내 스레드 | 통화를 받는 개별 상담원 |
| 코어 풀 크기 (Core Pool Size) | 상시 유지하는 최소 스레드 수 | 항상 자리를 지키는 기본 상담원 수 |
| 최대 풀 크기 (Max Pool Size) | 부하 시 늘릴 수 있는 스레드 상한 | 성수기 최대 증원 한도 |
| 거부 정책 (Rejection Policy) | 큐·풀이 다 찼을 때 새 작업 처리 방식 | 대기열 만석 시 안내(거절·대기·되돌림) |
| 컨텍스트 스위칭 (Context Switching) | 실행 스레드 교체 시 상태 저장·복원 비용 (상세는 002) | 상담원 교대 인수인계 시간 |
| 워크 스틸링 (Work Stealing) | 한가한 워커가 바쁜 워커의 큐 뒤에서 작업을 훔쳐 감 | 한가한 직원이 옆 팀 일을 가져다 처리 |

## 깊이 이해
- **배경·문제의식**: 초기 서버는 요청마다 스레드를 하나씩 생성(Thread-per-Request)했다. 요청이 적으면 문제없지만, 트래픽이 폭증하면 수만 개 스레드가 만들어져 각 스레드 스택(수백 KB~1MB)이 메모리를 잠식하고, CPU가 실제 일보다 문맥 전환에 시간을 더 쓰는 지경에 이른다. "스레드 수를 CPU가 감당할 수준으로 고정하고 재사용하자"는 것이 스레드 풀의 출발점이다.
- **작동 원리(어떻게+왜)**:
  - **스케줄링 매핑**: 유저 스레드가 실제 CPU를 받으려면 커널 스레드에 실려야 한다. 1:1(리눅스 NPTL, 자바 플랫폼 스레드)은 커널이 직접 스케줄링해 블로킹에 안전하지만 스레드 수가 커널 부담이 된다. M:N(Go 고루틴, 자바 가상 스레드)은 유저 영역에서 수천~수백만 흐름을 소수 커널 스레드에 다중화해 경량화한다.
  - **스레드 풀**: 코어 풀 크기만큼 워커를 미리 띄워 두고, 들어온 작업을 작업 큐에 넣는다. 워커는 큐에서 작업을 꺼내 실행하고 끝나면 다시 큐를 기다린다. 큐가 차면 최대 풀 크기까지 워커를 늘리고, 그래도 넘치면 거부 정책이 발동한다.
- **비유**: 스레드 풀은 렌터카 회사다. 손님(작업)이 올 때마다 차를 새로 사는(스레드 생성) 게 아니라, 보유 차량(워커)을 빌려주고 반납받아 다음 손님에게 다시 준다. 차가 다 나가면 대기 명단(작업 큐)에 올리고, 명단도 꽉 차면 "지금은 불가"(거부 정책)라고 안내한다.
- **구체 예시**: 자바 `ThreadPoolExecutor(corePoolSize=10, maxPoolSize=50, queue=LinkedBlockingQueue)`. 평상시 10개 워커가 처리하다, 큐가 쌓이면 50개까지 늘고, 큐·풀이 모두 차면 `CallerRunsPolicy`로 호출 스레드가 직접 처리해 역압(backpressure)을 건다. CPU 바운드 작업은 풀 크기를 코어 수(N) 근처로, I/O 바운드는 대기 시간이 길어 N보다 훨씬 크게(예: N×(1+대기/연산)) 잡는 것이 통설이다.
- **흔한 오해·주의점**: (1) "풀 크기는 클수록 좋다"는 오해다. 스레드가 코어 수를 크게 넘으면 문맥 전환·캐시 오염으로 오히려 처리량이 떨어진다. (2) 무제한 큐(unbounded queue)는 거부 정책을 무력화해, 소비보다 생산이 빠르면 큐가 무한히 쌓여 메모리가 고갈(OOM)된다 — 반드시 큐에 상한을 둬야 한다. (3) 풀 안에서 서로의 결과를 기다리는 작업을 제출하면 풀 데드락(pool-induced deadlock)이 생길 수 있다.

## 연결 개념
- 프로세스 vs 스레드(001 참조) — 스레드의 자원 공유·경량성 등 기본 배경은 여기에 위임
- CPU 스케줄링 알고리즘(004 참조) — 스레드도 결국 커널 스케줄러(CFS 등)가 고르는 대상
- 가상 스레드(027 참조) — M:N 매핑으로 풀 없이도 대량 동시성을 처리하는 최신 흐름

# 📝 【답안용】 시험 답안 템플릿

## 핵심 인사이트 (3줄 요약)

> 1. **본질**: 스레드 스케줄링은 CPU 배정을 스레드 단위로 수행하는 것이고, 스레드 풀은 스레드를 재사용하며 작업 큐로 부하를 분산하는 실행 패턴임.
> 2. **가치**: 스레드 수를 상한으로 고정·재사용해 생성·소멸 비용과 문맥 전환 폭증을 억제하고 처리량과 안정성을 확보함.
> 3. **판단 포인트**: 풀 크기·큐 상한·거부 정책의 조합이 성능과 과부하 안전성을 좌우하며, 워크로드가 CPU/I/O 바운드인지에 따라 파라미터를 달리해야 함.

## 출제 의도 및 답안 포인트

| 출제 의도 | 반드시 짚을 핵심 | 감점 회피 포인트 |
|:---|:---|:---|
| 스레드 매핑 모델 이해 | 커널/유저 스레드, 1:1·M:N 매핑 | 매핑 모델과 블로킹 관계 누락 |
| 스레드 풀 구조·동작 이해 | 워커·작업 큐·풀 크기·거부 정책 | 무제한 큐 위험(OOM) 누락 |
| 워크로드별 파라미터 판단 | CPU 바운드 vs I/O 바운드 풀 크기 | 풀 크기 무조건 확대 단정 |

> 요약: 매핑 모델과 풀 구성요소를 정확히 짚고, 큐 상한·거부 정책으로 과부하를 통제하며 워크로드별 크기 산정을 제시함.

## Ⅰ. 개요 및 필요성

- 개요: CPU 배정을 스레드 단위로 수행하고, 미리 생성한 스레드를 작업 큐 기반으로 재사용하는 실행 구조임
- 배경: 요청마다 스레드를 생성하는 방식은 부하 급증 시 스레드 폭증으로 메모리 고갈·문맥 전환 과다를 초래함
- 필요성: 스레드 수를 상한으로 고정·재사용해 자원 사용을 예측 가능하게 만들고 처리량을 안정적으로 확보함이 필요함

## Ⅱ. 구조 및 구성요소

선형 구조도 (작업 제출부터 실행까지):

    작업 제출 -> 작업 큐 적재 -> 여유 워커가 큐에서 작업 인출 -> 실행 -> 워커 반환(재사용)
      -> 큐 포화 시 최대 풀 크기까지 워커 증설
      -> 큐·풀 모두 포화 시 거부 정책 발동

| 구성요소 | 역할 | 특이사항 |
|:---|:---|:---|
| 워커 스레드 | 큐에서 작업을 꺼내 실행 후 재대기 | 생성·소멸 없이 반복 재사용 |
| 작업 큐 | 처리 대기 작업 보관 | 상한 필수(무제한 시 OOM 위험) |
| 풀 크기 파라미터 | 코어·최대 크기로 병렬도 제어 | CPU/I/O 바운드에 따라 산정 |
| 거부 정책 | 포화 시 새 작업 처리 방식 결정 | Abort·CallerRuns·Discard 등 |

> 요약: 워커가 작업 큐에서 일을 꺼내 재사용 실행하고, 큐 상한과 거부 정책이 과부하 시 시스템을 보호함.

## Ⅲ. 동작원리 및 흐름도

선형 흐름도:

    유저 스레드 -> [1:1 또는 M:N] 커널 스레드 매핑 -> 커널 스케줄러가 CPU 배정
    작업 제출 -> 워커 여유 시 즉시 실행 / 부족 시 큐 대기 -> 워커가 인출·실행 -> 반환

- 1단계 [매핑]: 유저 스레드를 1:1 또는 M:N으로 커널 스레드에 실어 커널 스케줄러가 CPU를 배정함
- 2단계 [제출·적재]: 클라이언트가 작업을 제출하면 여유 워커가 없을 때 작업 큐에 적재함
- 3단계 [인출·실행]: 워커 스레드가 큐에서 작업을 꺼내 실행하고 완료 후 다시 대기 상태로 복귀함
- 4단계 [과부하 제어]: 큐가 상한에 도달하면 최대 풀 크기까지 워커를 늘리고, 그래도 넘치면 거부 정책으로 역압을 적용함

> 요약: 커널이 스레드를 스케줄링하고, 풀은 워커·큐·거부 정책의 3단 완충으로 부하를 흡수해 안정적으로 처리함.

## Ⅳ. 특징

- 재사용 경량화: 워커를 재사용해 스레드 생성·소멸 비용과 스택 재할당을 제거함
- 자원 상한 보장: 최대 풀 크기·큐 상한으로 동시 스레드 수를 통제해 메모리 고갈을 예방함
- 매핑 유연성: 1:1은 블로킹에 안전하나 커널 부담, M:N은 경량이나 블로킹 콜 처리에 런타임 지원이 필요함
- 과부하 대응: 거부 정책과 역압으로 소비 능력을 초과하는 유입을 통제함
- 부하 분산: 워크 스틸링으로 워커 간 작업 불균형을 완화해 유휴를 줄임

## Ⅴ. 심화 비교 및 적용 판단

스레드-요청 직접 생성 방식과 스레드 풀을 자원·안정성·확장 축으로 대조함.

| 구분 | 요청당 스레드 생성 (Thread-per-Request) | 스레드 풀 (Thread Pool) |
|:---|:---|:---|
| 스레드 수 | 요청 수에 비례해 무제한 증가 | 최대 풀 크기로 상한 고정 |
| 생성 비용 | 요청마다 스택 할당·커널 등록 | 초기 1회 생성 후 재사용 |
| 과부하 안전성 | 폭증 시 OOM·문맥 전환 과다 | 큐·거부 정책으로 역압 제어 |
| 지연 특성 | 부하 급증 시 급격 악화 | 큐 대기로 완만히 열화 |

> 요약: 트래픽이 예측 불가하거나 높은 서버는 스레드 풀이 필수이며, 극소량 단발 작업만 요청당 생성이 정당화됨.

**리스크·대응:**
- 스레드 폭증 — 요청당 무제한 생성으로 메모리 고갈 — 풀 크기 상한·비동기 I/O 전환(028 참조)
- 큐 무한 적재 — 무제한 큐로 소비 지연 시 OOM — 유계 큐(bounded)와 CallerRuns 역압 적용
- 풀 데드락 — 풀 내 작업이 같은 풀 작업 결과를 대기 — 상호 의존 작업은 별도 풀 분리·비동기 조합

**점검 지표:**
- 성능: 처리량(TPS), 작업 큐 대기 시간(Queue Latency)
- 운영: 활성 워커 수(Active Thread Count), 거부 작업 수(Rejected Count)

## Ⅵ. 실무 적용 및 결론

**적용 방안:**
1. 워크로드별 풀 크기: CPU 바운드는 코어 수(N) 근처, I/O 바운드는 N×(1+대기/연산)으로 산정해 유효 병렬도를 확보함
2. 유계 큐 + 역압: LinkedBlockingQueue에 상한을 두고 CallerRunsPolicy로 생산 속도를 눌러 OOM을 방지함
3. 병렬 처리 최적화: ForkJoinPool의 워크 스틸링으로 분할 작업의 워커 간 불균형을 줄여 유휴 코어를 활용함

**결론:**
