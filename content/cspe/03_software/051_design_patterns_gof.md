## 미리 알고가기

- GoF 디자인 패턴: 객체지향 설계 문제를 생성, 구조, 행위 관점으로 정리한 23가지 패턴 모음임
- 변동 지점(Variation Point): 비즈니스 요구사항이나 기술 환경의 변화가 집중되어 코드가 자주 수정되는 영역임
- 패턴 의도(Pattern Intent): 특정 패턴이 해결하려는 핵심 문제와 이를 적용해야 하는 구체적인 상황을 정의한 것임
- SOLID 원칙: 객체지향 설계의 5대 원칙(단일 책임, 개방-폐쇄, 리스코프 치환, 인터페이스 분리, 의존역전)임
- 결합도(Coupling): 모듈과 모듈 사이의 의존성 정도로, 결합도가 낮을수록 변경 영향 범위가 좁아짐

## 작성 근거(검토용)

- GoF 패턴은 해결 문제, 변경 분리 대상, 구조상 부담을 핵심 비교축으로 선정함
- 구성은 패턴 의도, 참여 역할, 변경 지점, 상충 관계를 중심으로 제시함
- 실무 판단은 변경 영향 범위, 추상화 계층 수, 연동 구현 중복률로 구체화함
- 제목, frontmatter, 미리 알고가기, 작성 근거, 본문, 표 헤더·셀, 요약, 결론을 한 줄도 빠뜨리지 않고 확인했으며 어색한 단어·조사·동사 결합·장황한 명사구를 교정함

## Ⅰ. 개요

- **정의/개념**: GoF 디자인 패턴은 반복되는 객체 생성·구조·행위 문제를 재사용 가능한 역할과 협력 구조로 정리한 23개 패턴임
- **배경/필요성**: 반복 설계 문제에 맞는 객체 역할과 협력 구조를 선택하고 이를 공통 언어로 공유할 기준이 필요함

### 쉽게 이해하기 (학습용)
- 자주 발생하는 코딩 문제에 대해 선배 개발자들이 미리 만들어 둔 표준 해결책 모음임

## Ⅱ. 특징

- 구체 코드보다 객체 역할과 협력 구조를 재사용함
- 생성, 구조, 행위 문제를 분리해 선택 맥락을 제공함
- 패턴 이름으로 반복 문제, 참여 객체, 책임 협력 구조를 공통 용어로 공유함
- 문제에 맞지 않게 적용하면 계층과 추상화만 늘어날 수 있음

### 쉽게 이해하기 (학습용)
- 코드를 그대로 복사하는 것이 아니라, 클래스들이 일하는 방식과 구조의 틀을 빌려 쓰는 것임

## Ⅲ. 종류 및 비교

| 판단 기준 | 생성 패턴 | 구조 패턴 | 행위 패턴 |
|:---|:---|:---|:---|
| 다루는 문제 및 예시 | 객체 생성 방식 분리 (Factory Method·Builder) | 클래스·객체 조합 구조 (Adapter·Decorator) | 객체 간 책임·협력 방식 (Strategy·Observer) |
| 변경 분리 대상 | 객체 생성 책임과 사용 책임 분리 | 기존 객체와 새 인터페이스·책임 연결 | 교체할 알고리즘·통지·요청을 객체로 분리 |
| 주의할 점 | 단순 생성에 적용하면 계층만 늘어남 | 래퍼 계층 증가로 인한 가동 지연 | 객체 간 흐름 추적 부담 및 디버깅 복잡도 |

> 요약: 객체 생성은 생성 패턴, 객체 조합은 구조 패턴, 책임과 협력은 행위 패턴으로 분리함.

### 쉽게 이해하기 (학습용)
- 집을 지을 때 벽돌 만드는 법(생성), 방과 거실을 연결하는 법(구조), 집안일 나누는 법(행위)처럼 성격별로 세 가지로 나눈 것임

## Ⅳ. 설계 요소 및 구조

```text
[요구사항/문제] ──> [패턴 의도 평가] ──> [변경 지점 식별] ──> [역할 협력 설계 (상충 관계 검토)]
```

| 설계 요소 | 설명 |
|:---|:---|
| 패턴 의도 | 해결할 문제와 적용 조건을 명시해 패턴 선택 기준을 제공함 |
| 역할 협력 | 참여 객체의 역할·책임·호출 관계를 정의함 |
| 변경 지점 | 자주 바뀌는 생성·구조·행위를 식별해 분리 대상을 정함 |
| 상충 관계 | 유연성 증가와 추상화 복잡도 증가를 함께 평가함 |

> 요약: 패턴 의도로 문제를 한정하고 역할 협력으로 변경 지점을 분리한 뒤 복잡도 증가를 검토함.

### 쉽게 이해하기 (학습용)
- 설계도를 그릴 때 무엇을 해결할지 목적을 정하고, 역할에 맞춰 방을 나누고 관계를 이어주는 정적인 구조임

## Ⅴ. 원리 및 절차 흐름도

```text
[1. 변경 탐지] ──> [2. 패턴 매핑] ──> [3. 인터페이스 정의] ──> [4. 구체 클래스 구현]
```

- **1. 변경 탐지**: 비즈니스 요구사항 분석을 통해 자주 바뀌는 변동 지점(Variation Point)을 식별함
- **2. 패턴 매핑**: GoF 23종 패턴 중 변동 지점의 특성(생성, 구조, 행위)에 적합한 패턴 의도(Pattern Intent)를 선택함
- **3. 인터페이스 정의**: 역할과 협력 관계를 정의하고 클라이언트가 의존할 추상화 인터페이스를 설계함
- **4. 구체 클래스 구현**: 인터페이스를 상속받아 세부 알고리즘이나 생성 방식을 구현하고 결합도를 낮춤

### 쉽게 이해하기 (학습용)
- 먼저 바뀔 부분을 찾고, 알맞은 도구(패턴)를 고른 뒤, 뼈대(인터페이스)를 세우고 실제 동작을 만드는 순서임

## Ⅵ. 실무 사례

- 결제 시스템에서 Strategy 패턴을 적용하여 결제 수단별 처리 로직을 캡슐화하고, 외부 연동 모듈은 Adapter 패턴을 통해 동일한 인터페이스로 처리하도록 조치함.

### 쉽게 이해하기 (학습용)
- 결제 시스템을 만들 때 카카오페이, 네이버페이 등 다른 결제 방식을 언제든 갈아끼울 수 있게 구조를 짠 것임

## Ⅶ. 결론

- GoF 패턴은 소프트웨어 설계에서 변경 지점과 역할 협력을 분리해 시스템 유연성과 확장성을 보장함.
- 불필요한 계층화와 오용으로 인한 가독성 저하를 방지하기 위해 가용 자원 내에서 복잡도와 유연성의 상충 관계를 검토해야 함.

### 쉽게 이해하기 (학습용)
- 유연한 프로그램을 만들기 위해 필수적인 약속이지만, 너무 복잡하게 쓰면 오히려 코드가 어려워지므로 알맞게 써야 함
