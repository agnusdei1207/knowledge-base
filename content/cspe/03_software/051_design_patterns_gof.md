# 📖 【암기용】 개념 완전 이해

> 목적: 이 개념을 처음 보는 사람도 완벽히 이해하게 만든다. 시험 답안 양식이 아니라, 이해를 위한 친절한 설명이다.

## 한눈에
- **개요**: **디자인 패턴**은 객체지향 설계에서 반복적으로 나타나는 문제에 대한 **재사용 가능한 해법**을 정리한 것으로, Erich Gamma 등 4인(GoF, Gang of Four)이 1994년 저서 『Design Patterns』에서 **생성(Creational)·구조(Structural)·행위(Behavioral)** 3범주, 총 23종으로 분류했다.
- **왜 필요한가**: 같은 설계 문제(객체 생성을 유연하게 하고 싶다, 호환 안 되는 인터페이스를 연결하고 싶다, 상태 변화를 여러 객체에 알리고 싶다)를 개발자마다 다른 방식으로 풀면 코드 리뷰와 협업 비용이 커진다. 디자인 패턴은 이런 문제-해법 쌍에 이름을 붙여 개발자 간 공통 어휘로 쓰게 한다.
- **핵심 직관**: 3범주는 "객체를 어떻게 만드는가(생성) → 만든 객체를 어떻게 조립하는가(구조) → 조립된 객체들이 어떻게 협력하는가(행위)"라는 순서를 따른다.

## 핵심 용어 정리 (내부에 등장하는 것들)

| 용어 | 의미 | 비유 |
|:---|:---|:---|
| 생성 패턴 (Creational, 5종) | 객체 생성 과정을 캡슐화해 호출부가 구체 클래스를 직접 new하지 않게 함 | 완성품만 받고 제조 공정은 공장에 맡김 |
| 구조 패턴 (Structural, 7종) | 클래스·객체를 조합해 더 큰 구조를 만들거나 호환되지 않는 인터페이스를 연결 | 레고 블록 조립, 어댑터 콘센트 |
| 행위 패턴 (Behavioral, 11종) | 객체 간 책임 분배와 통신(알고리즘 교체, 이벤트 전파) 방식을 정의 | 팀원 간 역할 분담과 보고 체계 |
| 싱글톤 (Singleton) | 클래스의 인스턴스를 1개만 생성하도록 보장 | 회사 대표이사는 1명 |
| 팩토리 메서드 (Factory Method) | 객체 생성을 서브클래스·팩토리 클래스에 위임해 호출부가 구체 타입을 모르게 함 | 주문서(문자열)만 넘기면 완성품이 나오는 주문 창구 |
| 어댑터 (Adapter) | 호환되지 않는 인터페이스 사이에 변환 계층을 끼워 연결 | 110V 플러그를 220V 콘센트에 꽂는 돼지코 |
| 전략 (Strategy) | 알고리즘군을 인터페이스로 캡슐화해 런타임에 교체 가능하게 함 | 상황에 맞게 무기를 바꿔 드는 것 |
| 옵저버 (Observer) | 한 객체의 상태 변화를 구독 중인 다수 객체에 자동 통지 | 유튜브 업로드 시 구독자 전원에게 알림이 가는 것 |

## 깊이 이해

### 배경 — 왜 23개로 정리됐나
- 1994년 Erich Gamma, Richard Helm, Ralph Johnson, John Vlissides(GoF)는 Smalltalk와 C++로 짠 여러 프로젝트를 검토하며 "도메인은 다른데 클래스 구조는 똑같은" 설계를 23개 뽑아 각각에 이름·의도·구조·장단점을 표준화해 카탈로그로 묶었다. 이후 이 이름들이 업계 공통 어휘(패턴 이름을 말하면 클래스 구조가 바로 그려지는 언어)로 정착했다.

### 분류 판별 원리 — 어떤 범주인지 어떻게 구분하나
- 질문이 "이 객체를 어떻게 만들지"면 생성 패턴, "이 객체(들)를 어떻게 조합·연결하지"면 구조 패턴, "이 객체들이 어떻게 협력·통신하지"면 행위 패턴이다. 예: 결제 모듈 교체는 "만드는 방식" 문제이므로 생성(Factory), 신구 API 연결은 "연결" 문제이므로 구조(Adapter), 할인 정책 교체는 "알고리즘 교체"이므로 행위(Strategy)다.

### 싱글톤 — 스레드 안전성까지 봐야 완성
- DB 커넥션 풀처럼 애플리케이션 전체에서 1개만 있어야 하는 객체에 쓴다. `if (instance == null) instance = new Connection();` 코드를 그대로 쓰면 스레드 2개가 동시에 `if`를 통과해 인스턴스가 2개 생성될 수 있다(경쟁 조건). 이를 막으려면 `synchronized` 키워드나 더블 체크 락킹(Double-Checked Locking), 또는 클래스 로딩 시점에 초기화되는 정적 필드 방식을 써야 정확히 1개만 보장된다.

### 전략(Strategy) — if-else 개수로 개선 효과를 잰다
- 할인 정책이 `if(등급=="VIP")...else if(등급=="GOLD")...` 형태로 N개 분기라면, 등급이 하나 늘 때마다 이 if-else 블록(파일 1개)을 열어 수정해야 한다. `DiscountStrategy` 인터페이스와 등급별 구현 클래스로 바꾸면, 새 등급 추가는 새 클래스 파일 1개 생성으로 끝나고 기존 파일 수정은 0줄이 된다(050 OCP와 같은 판별 기준).

### 옵저버(Observer) — 1:N 통지의 비용
- 주체(Subject) 하나가 상태를 바꿀 때 구독자(Observer) 리스트를 순회하며 `update()`를 호출한다. 구독자가 M명이면 통지 비용은 O(M)이다. 주체는 구독자의 구체 타입을 몰라도 되므로(인터페이스만 앎), 구독자를 몇 명 붙이든 주체 코드는 수정되지 않는다.

### 어댑터(Adapter) — 메서드 시그니처 불일치를 흡수
- 예: 레거시 결제 모듈은 `int pay(String amount)`(문자열 금액, 정수 반환)를 제공하는데, 신규 시스템은 `PaymentResult execute(Money money)`(값 객체 인자, 결과 객체 반환) 인터페이스를 기대한다. 두 시그니처를 직접 맞출 수 없으므로 `LegacyPaymentAdapter` 클래스가 `execute(Money money)`를 구현하면서 내부에서 `money`를 문자열로 변환해 `pay()`를 호출하고 반환값을 `PaymentResult`로 감싼다. 레거시 코드와 신규 인터페이스 어느 쪽도 수정하지 않는다.

### 오버엔지니어링 — 언제 쓰면 안 되나
- 판별 원리: 그 로직이 앞으로 바뀌거나 늘어날 가능성이 낮으면 패턴을 쓰지 않는다. 단순 로그인 로직에 팩토리·전략·파사드를 동시에 적용하면 클래스 파일 수만 늘고(1개에서 10여 개로) 실행 흐름을 추적하기 더 어려워진다. 패턴은 변경이 예상되는 지점에 대한 방어 비용이지, 모든 코드에 붙이는 장식이 아니다.

## 연결 개념
- SOLID 원칙 — 디자인 패턴이 실제로 구현하는 설계 목표(전략 패턴=OCP+DIP, 어댑터=ISP)
- Spring 프레임워크의 Bean(싱글톤), DispatcherServlet(프론트 컨트롤러+파사드) — 패턴이 프레임워크에 내장된 사례
- 반응형 프로그래밍(Reactive Streams) — 옵저버 패턴의 비동기 확장

# 📝 【답안용】 시험 답안 템플릿

> 목적: 시험장에서 25분에 그대로 쓰는 답안 양식. 작성방식(추상표현 금지·수치·도식·문제유형 전환)을 엄격히 지킨다.
> 핵심: 이 시험은 정보를 많이 나열하는 시험이 아니라, 문제 신호어에서 출제자 의도를 읽고 핵심 논점을 선별해 쓰는 시험이다.

## 핵심 인사이트 (3줄 요약)

> 1. **본질**: 객체 지향 프로그래밍(OOP) 설계에서 반복적으로 발생하는 문제들에 대한 검증된 해법(템플릿)으로, 생성/구조/행위 3가지 범주로 나뉜 23개의 아키텍처 전술 모음집이다.
> 2. **가치**: 개발자 간의 의사소통 비용(커뮤니케이션 리스크)을 혁신적으로 낮추며, 잦은 요구사항 변경에도 기존 코드의 수정을 최소화하는 유연성과 재사용성(OCP, 플러그인 아키텍처)을 극대화한다.
> 3. **판단 포인트**: 23개를 단순 암기하여 읊는 것이 아니라, 실무에서 가장 결합도 문제(Spaghetti)를 유발하는 로직을 어떤 패턴(예: Strategy, Observer)을 통해 인터페이스 기반의 느슨한 결합(Loose Coupling)으로 방어해 내는가에 초점을 맞춰야 한다.

## 출제 의도 및 답안 포인트

| 출제 의도 | 반드시 짚을 핵심 | 감점 회피 포인트 |
|:---|:---|:---|
| 소프트웨어 위기 타파를 위한 객체 간 관계(결합) 설계 기술 | 3대 범주 (생성/구조/행위) 분류 및 목적 맵핑 | 각 패턴이 객체 지향 원칙(SOLID)의 어느 부분을 만족시키는지 연결 고리 부재 |
| 자주 출제되는 핵심 빈출 패턴의 물리적 동작 메커니즘 도식화 | Singleton, Factory, Strategy, Observer의 UML/작동 도식 | 23개를 이름만 나열하고 "어떻게 코드를 덜 고치게 만드는지(다형성)"에 대한 설명 증발 |
| 실무(프레임워크) 융합 및 도입 시의 딜레마(Trade-off) | Spring 등 실제 프레임워크와의 매핑 및 오버엔지니어링 리스크 | 아무 데나 패턴을 남발하면 코드가 복잡해지는 단점(가독성 저하)을 누락한 무지성 찬양 |

> 요약: OCP(코드 수정 없이 확장)를 외치기는 쉽다. 하지만 막상 "어떻게?"라고 물었을 때, "네, 인터페이스를 하나 파서 전략(Strategy) 패턴으로 꽂아 넣으면 됩니다"라고 명확한 '도면'을 제시하는 것이 바로 디자인 패턴이다.

## Ⅰ. 개요 및 필요성

- 정의: 에릭 감마 등 4인의 학자(GoF)가 소프트웨어 설계 과정에서 발견한 23개의 공통된 객체 상호작용 및 아키텍처 설계 템플릿(정석) 카탈로그
- 배경: 객체를 `new` 키워드로 강결합(Tightly Coupled) 시키거나 무분별한 상속(LSP 위반)을 남발하여, 요구사항 변경 시 연쇄적인 코드 붕괴(Fragility)와 유지보수 마비 발생
- 필요성: 모듈 간의 결합도를 낮추고 다형성(Polymorphism)을 통한 플러그인 교체를 가능케 하여 시스템 확장성을 확보하고, 개발자 집단의 공통 설계 어휘(Vocabulary)를 확립하기 위함

## Ⅱ. GoF 23종 3대 범주(Category) 및 핵심 토폴로지 매핑

가장 강력하고 실무에 많이 쓰이는 5대장(Singleton, Factory, Adapter, Observer, Strategy)을 장착해야 한다.

```text
[ 1. Strategy (행위): if-else 지옥의 타파 (OCP 달성) ]
[ 주문 Client ] --> (의존) --> <<인터페이스>> [ DiscountStrategy (할인 정책) ]
                                          ^ (다형성 교체)
               +--------------------------+-----------------------+
               |                          |                       |
   [ VIP_할인 클래스 (전략A) ]   [ 신규_할인 클래스 (전략B) ]   [ 일반_할인 (전략C) ]

[ 2. Observer (행위): 발행-구독 메커니즘 (결합도 최소화) ]
[ 유튜버 (Subject / 발행자) ] ---> 1 : N (이벤트 Broadcast) ---> [ 옵저버 인터페이스 ]
   (영상을 올리면 루프를 돌림)                                   ^
                                                       +------+------+
                                                       |             |
                                            [ 구독자A 객체 ]  [ 구독자B 객체 ]
```

| 분류 카테고리 | 핵심 패턴 (엔지니어링 제어 기제) | 적용 시나리오 (해결되는 리스크) |
|:---|:---|:---|
| **생성 (Creational)** <br> : 객체 생성 캡슐화 | **1. Singleton (싱글톤)**: 전역 인스턴스를 단 1개만 생성하여 메모리 풀(Pool) 고갈 방어 <br> **2. Factory (팩토리)**: 객체 생성을 공장 클래스에 위임하여 구상 클래스 결합 끊기 | DB Connection Pool, 스레드 풀 생성 등 무거운 객체 생성 시 메모리 자원 폭주 차단 |
| **구조 (Structural)** <br> : 구조/인터페이스 조립 | **3. Adapter (어댑터)**: 호환되지 않는 레거시 인터페이스를 변환기(Wrapper)로 감싸 연결 <br> **4. Facade (파사드)**: 수십 개의 복잡한 서브시스템 API를 숨기고 통합된 정문 1개 제공 | 구형 결제 시스템(PG)을 신형 시스템에 이식할 때 레거시 코드를 뜯어고치는 위험 방어 |
| **행위 (Behavioral)** <br> : 객체 간 역할 및 통신 | **5. Strategy (전략)**: 알고리즘군을 캡슐화하여 런타임에 갈아 끼우는(다형성) 극강의 유연성 <br> **6. Observer (옵저버)**: 한 객체 상태 변경 시 종속된 모든 객체에 자동 알림(Decoupling) | 끝없는 할인 정책 추가, 실시간 푸시 알림 등에서 스파게티 코드(`if-else`) 원천 차단 |

> 요약: 초보자는 코드를 복사+붙여넣기 하지만, 시니어는 패턴을 적용한다. 신규 기능(할인 쿠폰)이 들어올 때마다 기존 클래스를 찢어발기는 건 아마추어다. 인터페이스라는 틀(Strategy)을 파놓고 껍데기만 갈아 끼우는 게 프로다.

## Ⅲ. 극복해야 할 시스템적 리스크 (안티패턴 및 Over-Engineering)

패턴은 만병통치약이 아니다. 23개를 다 써보겠다는 욕망이 오히려 프로젝트를 나락으로 떨어뜨린다.

| 리스크 요인 | 발생 시나리오 및 시스템 붕괴 원인 | 아키텍처 대응 방안 (실무 튜닝) |
|:---|:---|:---|
| **무지성 추상화(복잡도 폭발)** | 단순한 로그인 로직에 팩토리, 파사드, 전략 패턴을 3중첩으로 떡칠하여, 클래스 파일이 1개에서 20개로 폭증해 후임자가 디버깅을 포기함 | **YAGNI 원칙(You Aren't Gonna Need It) 적용**: 변경 가능성이 없거나 1회성에 불과한 로직은 패턴을 배제하고 직관적인 `if`문으로 타협. 오직 확장/변경의 고통이 실재하는 도메인 병목 구간에만 외과 수술적 패턴 투입 |
| **싱글톤(Singleton)의 역습** | 전역(Global) 상태를 가진 싱글톤 객체 내부 변수(전역 변수)를 멀티 스레드가 동시에 `WRITE` 하려다 동시성(Concurrency) 락 경합 및 데이터 오염(Race Condition) 폭발 | 상태(State)가 있는(Stateful) 싱글톤은 **절대 금지**. 싱글톤 내부는 오직 읽기 전용(Read-only) 불변(Immutable) 상태로 유지하거나, Spring 등 IoC 컨테이너에 관리를 일임하여 스레드-세이프(Thread-safe) 강제화 |

> 요약: 가장 멍청한 코드는 안 변할 곳에 패턴을 쓴 코드고, 두 번째로 멍청한 코드는 매일 변하는 곳에 패턴을 안 쓴 코드다.

## Ⅳ. 현대 아키텍처와 디자인 패턴의 진화 (Shift to Framework)

GoF 23종은 1994년 C++ 시절 유물이다. 2026년 현재 이 패턴들은 어떻게 살아남았는가?

| 현대적 진화 패러다임 | 물리적 구현 메커니즘 (프레임워크 흡수) |
|:---|:---|
| **Spring 컨테이너 (IoC/DI) 흡수** | 개발자가 `Singleton` 코드를 짤 필요 없이, Spring Bean으로 등록만 하면 컨테이너가 100% 싱글톤 스명주기를 관리함. 또한 어노테이션(`@Autowired`) 주입 자체가 **Factory 및 Strategy 패턴의 현대적 완성형**임 |
| **반응형(Reactive) 프로그래밍** | GoF의 **Observer(옵저버) 패턴**이 극단적으로 진화하여 RxJava, WebFlux (Publisher-Subscriber 메커니즘) 등의 리액티브 스트림(Reactive Streams) 비동기 처리 핵심 철학으로 승화됨 |
| **MSA 환경으로의 차원 이동** | 객체(Class) 간의 패턴을 넘어, 서버(Server) 단위의 분산 통신 패턴으로 스케일업됨. (예: Facade 패턴 -> API Gateway로 진화, Proxy 패턴 -> Service Mesh(Istio) 사이드카로 거대화) |

> 요약: 자바 코드 단에서 한 땀 한 땀 구현하던 디자인 패턴들은 이제 거대한 스프링(Spring)과 클라우드 인프라(K8s) 레이어에 "보이지 않는 공기"처럼 흡수되었다. 우리는 이미 패턴 위에서 숨을 쉬고 있다.

## Ⅴ. 실무 적용 방안 및 결론

**적용 방안 3개:**
1. [Strategy 패턴 기반 전자결제(PG) 연동 아키텍처] 수많은 PG사(카카오페이, 네이버페이, 토스)를 연동하는 이커머스에서, `PaymentStrategy` 인터페이스를 선언하고 클라이언트가 `pay(Money, Strategy)` 형식으로 실행 시점에 결제 모듈을 꽂아 넣게(Inject) 하여 OCP 100% 달성 및 신규 결제 수단 추가 시 기존 코드 방어
2. [템플릿 메서드(Template Method) 기반 공통 배치 처리] 데이터베이스(ETL) 마이그레이션 배치 시스템에서, 부모 클래스에 `(1)데이터 읽기 -> (2)가공(추상 메서드) -> (3)저장`이라는 전체 뼈대(Template)를 박아두고, 자식 클래스는 오직 (2)가공 로직만 오버라이딩(Overriding)하게 하여 코드 중복(DRY) 원천 제거
3. [Spring MVC의 Facade 및 Proxy 패턴 결합 활용] 트랜잭션 처리나 AOP(로깅)를 위해 비즈니스 객체를 직접 호출하지 않고 Spring의 CGLib Proxy(가짜 대리인 객체)가 앞단에서 트래픽을 가로채어 보안 검사를 수행하는(Proxy 패턴) 구조를 백엔드 컨트롤러 계층 설계에 적용

**결론:**
- 기술사 판단: 디자인 패턴(GoF)은 단순한 코딩 기법이 아니라 객체 지향의 5대 원칙(SOLID)이 빚어낸 가장 아름답고 실용적인 건축 도면이다. 이 패턴들은 수십 년의 세월을 거치며 프레임워크(Spring)나 클라우드 아키텍처(MSA)의 내장 철학으로 승화되었으며, 복잡성을 통제하고 다형성(Polymorphism)을 통한 생존력을 부여하는 엔지니어링의 정수다.
- 향후 방향: 최근 마이크로서비스(MSA)와 함수형 프로그래밍(FP) 패러다임이 주류가 되면서, 기존의 무거운 상속 위주의 패턴(Template Method 등)은 도태되고 조합(Composition)과 인터페이스 기반의 가벼운 패턴(Strategy)이나 비동기 스트림 제어를 위한 클라우드 디자인 패턴(CQRS, Saga 등)으로 진화의 축이 완벽히 이동하였다.
