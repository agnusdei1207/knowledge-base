## 미리 알고가기

- GoF 디자인 패턴은 생성·구조·행위 패턴으로 나뉨
- 패턴은 재사용 가능한 설계 해법이지 정답 코드는 아님
- 패턴 남용은 설계 복잡도를 오히려 높일 수 있음

## Ⅰ. 개요

- **정의/개념**: GoF 디자인 패턴은 객체지향 설계에서 반복적으로 발생하는 생성과 구조와 행위 문제에 대해 재사용 가능한 설계 해법을 정리한 23개 패턴 모음임
- **배경/필요성**: 비슷한 설계 문제가 프로젝트마다 반복되므로, 검증된 협력 구조를 공통 언어로 사용하면 설계 품질과 의사소통 효율을 높일 수 있음

## Ⅱ. 특징

- 구체 구현보다 협력 구조와 역할 분리를 재사용함
- 생성·구조·행위 문제를 분류해 선택 맥락을 제공함
- 패턴 이름만 공유해도 설계 의도를 빠르게 설명할 수 있음
- 문제에 맞지 않는 패턴 적용은 불필요한 계층과 추상화를 만든다

## Ⅲ. 종류 및 비교

| 판단 기준 | 생성 패턴 | 구조 패턴 | 행위 패턴 |
|:---|:---|:---|:---|
| 초점 | 객체 생성 방식 | 클래스/객체 조합 구조 | 객체 간 협력과 책임 분배 |
| 대표 예 | Factory, Builder | Adapter, Facade | Strategy, Observer |
| 장점 | 생성 책임 분리 | 결합 구조 개선 | 변경 가능한 동작 분리 |
| 주의점 | 단순 생성에도 과도 적용 가능 | 래퍼 계층 남용 가능 | 흐름 복잡도 증가 가능 |

## Ⅳ. 구성요소 및 구조

| 구성요소 | 설명 |
|:---|:---|
| Pattern Intent | 어떤 문제를 해결하려는지 명확히 해야 잘못된 패턴 선택을 줄일 수 있음 |
| Role Collaboration | 참여 객체 역할과 책임을 정의해 유지보수 시 구조 이해를 쉽게 만듦 |
| Variation Point | 무엇이 바뀌는지 식별해 패턴 적용 지점을 정하는 핵심 기준이 됨 |
| Trade-off | 유연성과 단순성 사이 비용을 함께 고려해야 패턴이 실제로 유용해짐 |

## Ⅴ. 원리 및 절차 흐름도

```text
+-------------+     +-------------+     +-------------+     +-------------+
| 반복 문제 식별  | --> | 패턴 분류 선택 | --> | 역할 설계      | --> | 과적용 검증    |
+-------------+     +-------------+     +-------------+     +-------------+
```

1. **반복 문제 식별**: 생성과 구조와 행위 중 무엇이 문제인지 구분함
2. **패턴 분류 선택**: 가장 맞는 패턴 계열을 좁힘
3. **역할 설계**: 참여 객체와 책임과 협력 구조를 정의함
4. **과적용 검증**: 패턴이 실제 복잡도를 줄였는지 확인함

## Ⅵ. 문제점 및 해결 방안

1. 문제: 패턴 이름만 외워서 적용하면 실제 문제보다 추상화가 앞서 코드가 과복잡해질 수 있음
   - 해결방안: variation point가 명확한 경우에만 적용하고 pattern payoff score와 abstraction overhead score로 검증함
2. 문제: 팀이 패턴 의도는 공유하지 않고 형태만 복사하면 유지보수자가 구조 이유를 이해하기 어려울 수 있음
   - 해결방안: 설계 의도를 기록하고 design rationale coverage와 onboarding comprehension time으로 검증함
3. 문제: 프레임워크가 이미 제공하는 구조 위에 패턴을 중복 적용하면 중첩 계층만 증가할 수 있음
   - 해결방안: framework native pattern을 우선 검토하고 redundancy pattern count와 maintenance lead time으로 검증함

## Ⅶ. 적용 사례

- 확장 가능한 결제 전략 설계에서는 Strategy 패턴을 사용하고, pattern payoff score와 defect coupling rate로 결과를 확인함
- 외부 시스템 연동 계층에서는 Adapter를 사용하고, integration defect count와 redundancy pattern count로 결과를 확인함
- 설계 리뷰에서는 패턴 의도를 문서화하고, design rationale coverage와 onboarding comprehension time로 결과를 확인함

## Ⅷ. 결론

디자인 패턴의 진짜 가치는 이름을 붙이는 데 있지 않고 반복되는 변경 지점을 더 적은 결합과 더 분명한 책임 구조로 다루는 데 있음.
