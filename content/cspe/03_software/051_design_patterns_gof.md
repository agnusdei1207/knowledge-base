## 핵심 인사이트 (3줄 요약)
- 소프트웨어 설계에서 자주 발생하는 문제들에 대해, 선배 개발자들이 발견하고 정리한 23개의 재사용 가능한 객체지향 솔루션 (GoF 23 패턴).
- 생성(생성 방식), 구조(클래스 조립), 행위(객체 간 통신)의 3가지 카테고리로 분류되며, SOLID 원칙을 실무 코드 레벨에서 구현하는 구체적인 기법.
- 개발자들 간에 "여기는 팩토리로 빼고 옵저버를 달자"라는 식의 고차원적 커뮤니케이션을 가능케 하는 설계 공통 언어.

## Ⅰ. 개요 및 필요성
- **개요**: 에리히 감마(Erich Gamma)를 비롯한 4인방(Gang of Four)이 정립한 23가지의 객체지향 소프트웨어 설계 패턴.
- **필요성**: 바퀴를 다시 발명하지 않기 위함. 수많은 시스템을 만들며 겪은 유사한 문제(객체 생성의 복잡성, 결합도 증가 등)를 해결하는 최적의 템플릿을 제공하여 설계 시간 단축과 유지보수성을 확보함.
---
## Ⅱ. 아키텍처 및 핵심 원리
- **패턴의 3대 분류**:
  1. **생성 패턴 (Creational)**: 객체의 생성과 참조 과정을 캡슐화. (5개)
     - `Singleton` (1개 인스턴스), `Factory Method` (생성 위임), `Builder` (복잡한 조립) 등.
  2. **구조 패턴 (Structural)**: 클래스나 객체들을 조합해 더 큰 구조를 만듦. (7개)
     - `Adapter` (호환 안 되는 인터페이스 연결), `Facade` (복잡한 서브시스템 통합 창구), `Decorator` (동적 기능 추가) 등.
  3. **행위 패턴 (Behavioral)**: 객체 간의 책임 분배와 알고리즘, 통신 방식 정의. (11개)
     - `Observer` (상태 변화 구독/알림), `Strategy` (알고리즘 캡슐화 및 교체), `Template Method` (뼈대 구현 후 하위 위임) 등.

```text
[ 대표적 행위 패턴: Observer Pattern 도식 ]

 [ Subject (발행자) ]  ---- 상태 변경 통지(notify) --->  [ Observer (구독자 Interface) ]
   - observers 목록                                         - update() 
   - attach() / detach()                                       ^  (구현)
                                                               |
                                                 +-------------+-------------+
                                                 |                           |
                                         [ ConcreteObserver A ]    [ ConcreteObserver B ]
```

## Ⅲ. 비교 및 연결
| 주요 비교 | Strategy 패턴 (전략) | Template Method 패턴 |
|---|---|---|
| **목적** | 런타임에 알고리즘(행위)을 통째로 교체 | 변하지 않는 뼈대를 두고 일부만 변경 |
| **기반 메커니즘** | 인터페이스 위임 (Composition) | 부모-자식 상속 (Inheritance) |
| **결합도** | 낮음 (객체 합성이므로 유연함) | 높음 (부모 클래스에 강하게 결합됨) |
| **적용 사례** | 결제 방식(카드, 카카오페이) 동적 변경 | 스프링의 `JdbcTemplate` 데이터 접근 처리 |
---
## Ⅳ. 실무 적용 및 기술사 판단
- **패턴 만능주의(Patternitis) 경계**: 헬로월드를 찍는데 팩토리와 싱글톤을 도입하는 등, 과도한 패턴 사용은 코드를 쓸데없이 복잡하게 만드는 오버엔지니어링의 주범임. "패턴을 적용할 합당한 이유(고통)가 있을 때만 리팩토링 과정에서 자연스럽게 적용하라"가 정석임.
- **현대적 프레임워크와의 융합**: 오늘날 Spring 프레임워크는 내부적으로 수많은 GoF 패턴(IoC 컨테이너=Factory, DispatcherServlet=Facade/FrontController)을 이미 내장하고 있으므로, 개발자는 이를 억지로 구현하기보다 프레임워크의 철학을 이해하는 도구로 활용해야 함.
---
## Ⅴ. 기대효과 및 결론
- 디자인 패턴은 SOLID 원칙이 추상적인 철학이라면, 이를 현실 세계의 코드로 구현해 낸 구체적인 전술서임.
- 완벽한 암기보다는 각 패턴이 '어떤 종류의 변경(Change)으로부터 시스템을 보호하려 했는가'라는 의도(Intent) 파악하는 것이 기술사적 통찰의 핵심임.
