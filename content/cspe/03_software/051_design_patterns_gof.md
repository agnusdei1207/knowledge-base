## 미리 알고가기

- GoF 디자인 패턴은 객체지향 설계 문제를 생성, 구조, 행위 관점으로 정리한 패턴 모음임
- Variation point는 요구 변화가 집중되는 지점을 뜻함
- Pattern intent는 패턴이 해결하려는 문제와 적용 이유를 뜻함

## Ⅰ. 개요

- **정의/개념**: GoF 디자인 패턴은 객체지향 설계에서 반복적으로 나타나는 생성, 구조, 행위 문제를 재사용 가능한 협력 구조로 정리한 23개 패턴 모음임.
- **배경/필요성**: 비슷한 설계 문제가 프로젝트마다 반복되므로, 검증된 역할 분담과 협력 방식을 공통 언어로 정리해 설계 품질과 의사소통 효율을 높일 필요가 있음.

## Ⅱ. 특징

- 구체 코드보다 객체 역할과 협력 구조를 재사용함
- 생성, 구조, 행위 문제를 분리해 선택 맥락을 제공함
- 패턴 이름만으로도 설계 의도를 빠르게 공유할 수 있음
- 문제에 맞지 않게 적용하면 계층과 추상화만 늘어날 수 있음

## Ⅲ. 종류 및 비교

| 구분 | 생성 패턴 | 구조 패턴 | 행위 패턴 |
|:---|:---|:---|:---|
| 다루는 문제 | 객체를 어떤 방식으로 만들지에 초점을 둠 | 클래스와 객체를 어떻게 조합할지에 초점을 둠 | 객체가 책임을 어떻게 나누고 협력할지에 초점을 둠 |
| 대표 예시 | Factory Method, Builder, Singleton이 대표적임 | Adapter, Facade, Decorator가 대표적임 | Strategy, Observer, Command가 대표적임 |
| 기대 효과 | 생성 책임을 분리해 생성 방식 변경을 쉽게 함 | 결합 구조를 정리해 인터페이스 충돌과 복잡도를 낮춤 | 동작 변경과 책임 분배를 유연하게 만듦 |
| 주의할 점 | 단순 생성에도 쓰면 구조만 무거워질 수 있음 | 래퍼 계층이 과도하게 늘어날 수 있음 | 흐름 추적이 복잡해질 수 있음 |

> 요약: 디자인 패턴은 정답 코드 모음이 아니라 반복되는 설계 문제를 더 적은 결합으로 다루는 공통 언어임.

## Ⅳ. 구성요소 및 구조

| 구성요소 | 설명 |
|:---|:---|
| Pattern Intent | 어떤 문제를 해결하려는지 먼저 분명히 해야 잘못된 패턴 선택을 줄일 수 있음 |
| Role Collaboration | 참여 객체의 역할과 책임을 정해 구조 이해와 유지보수를 쉽게 만듦 |
| Variation Point | 무엇이 자주 바뀌는지 식별해 패턴 적용 지점을 정하는 기준이 됨 |
| Trade-off | 유연성 증가와 구조 복잡도 증가를 함께 비교해야 실제 효과를 판단할 수 있음 |

## Ⅴ. 원리 및 절차 흐름도

```text
+-------------+     +-------------+     +-------------+     +-------------+
| 반복 문제 식별  | --> | 패턴 분류 선택 | --> | 역할 설계      | --> | 과적용 검증    |
+-------------+     +-------------+     +-------------+     +-------------+
```

1. **반복 문제 식별**: 생성, 구조, 행위 중 어떤 문제가 반복되는지 구분함
2. **패턴 분류 선택**: 가장 맞는 패턴 계열을 좁힘
3. **역할 설계**: 참여 객체와 책임과 협력 구조를 정의함
4. **과적용 검증**: 패턴이 실제로 복잡도를 줄였는지 확인함

## Ⅵ. 실무 적용 및 유의점

1. 확장 포인트가 분명한 도메인 모듈에서는 패턴이 유용하지만 이름만 외워 적용하면 추상화만 남으므로 변화 지점이 확인된 경우에만 도입하고 패턴 적용 효과와 추상화 비용으로 확인함
2. 외부 연동 계층이나 프레임워크 위에 패턴을 추가할 때는 기존 구조와 중복될 수 있으므로 설계 의도를 함께 기록하고 중복 패턴 수와 설계 의도 기록 범위로 확인함

## Ⅶ. 결론

디자인 패턴은 많이 아는 것이 아니라 반복되는 변경 지점에만 정확히 적용할 때 설계 가치가 생김.
