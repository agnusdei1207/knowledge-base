## Ⅰ. 개요
- **정의**: 반복 발생하는 설계 문제에 대한 재사용 가능한 객체지향 해법 카탈로그
- **배경/필요성**: 유사한 구조적 문제가 프로젝트마다 반복되므로, 검증된 해법을 패턴으로 분류해 설계 품질을 균일화할 필요
- **비유**: 건축 설계에서 반복 사용하는 평면도 템플릿과 유사함

| 출제 의도 | 반드시 짚을 핵심 | 감점 회피 포인트 |
|:---|:---|:---|
| 23개 패턴 분류 체계 이해 | 생성·구조·행위 3범주 구분 | 패턴 이름만 나열하지 말고 의도·적용 상황 서술 필요 |

> 요약: 객체지향 설계의 반복 문제를 생성·구조·행위 3범주 23개 패턴으로 체계화한 해법 카탈로그임

## Ⅱ. 구성요소
```text
+------------------+
|   GoF Patterns   |
+-----+-----+------+
      |     |
  +---v-+ +-v----+ +--v-----+
  |생성 | |구조  | |행위    |
  |5개  | |7개   | |11개   |
  +-----+ +------+ +--------+
```

| 구성요소 | 설명 | 비유 |
|:---|:---|:---|
| 생성(Creational) | 객체 생성 로직을 캡슐화하여 결합도를 낮춤 (Factory, Singleton 등) | 주문서만 내면 공장이 알아서 제품을 만드는 방식 |
| 구조(Structural) | 클래스·객체 합성으로 더 큰 구조를 형성함 (Adapter, Composite 등) | 레고 블록을 조합해 큰 모형을 만드는 방식 |
| 행위(Behavioral) | 객체 간 책임 분배와 통신 방식을 정의함 (Observer, Strategy 등) | 팀원 간 업무 분장 규칙표와 유사함 |

> 요약: 생성 5개, 구조 7개, 행위 11개로 총 23개 패턴이 분류됨

## Ⅲ. 절차
```text
문제식별 --> 패턴후보선정 --> 구조적용 --> 검증/리팩터링
```
- 1단계: 반복되는 설계 문제와 변경 지점을 식별함
- 2단계: 문제 유형에 맞는 패턴 후보를 선정하고 의도를 대조함
- 3단계: 클래스 다이어그램 기반으로 패턴 구조를 코드에 적용함
- 4단계: 단위 테스트로 패턴 적용 결과를 검증하고 과잉 설계를 리팩터링함

> 요약: 문제 식별부터 패턴 선정·적용·검증까지 4단계로 진행함

## Ⅳ. 문제점
- 과잉 적용: 단순 문제에 패턴을 강제 적용 — 불필요한 클래스 증가로 복잡도 상승
- 패턴 오용: 의도와 다른 패턴 선택 — 변경 용이성 확보 실패로 유지보수 비용 증가
- 학습 곡선: 23개 패턴의 구분과 조합 이해에 시간 소요 — 팀 내 설계 일관성 저하

> 요약: 과잉 적용, 오용, 학습 부담이 주요 문제임

## Ⅴ. 개선방안
1. 단기: 코드 리뷰 시 패턴 적용 타당성 체크리스트 도입으로 과잉 적용 방지
2. 중기: 도메인별 패턴 적용 가이드라인 수립으로 오용 감소
3. 장기: 사내 패턴 카탈로그·교육 체계 구축으로 학습 곡선 완화

> 요약: 체크리스트, 가이드라인, 교육 체계로 단계적 개선함

## Ⅵ. 전망
- 발전 방향: 함수형 프로그래밍 확산에 따라 기존 패턴의 재해석과 경량화 진행 중임
- 기술사적 판단: 패턴 자체보다 패턴이 해결하는 문제의 본질을 이해하는 역량이 중요함
- 기술사 제언: 마이크로서비스·리액티브 환경에 맞는 분산 패턴과 병행 학습 필요
