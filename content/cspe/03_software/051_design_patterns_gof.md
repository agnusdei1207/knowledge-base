# 📖 【암기용】 개념 완전 이해

> 목적: 디자인 패턴 GoF 23종을 처음 보는 사람도 완벽히 이해하게 만든다. 시험 답안 양식이 아니라, 이해를 위한 친절한 설명이다.

## 한눈에
- **개요**: 객체지향 설계에서 반복되는 문제에 대한 검증된 설계 해법
- **왜 필요한가**: 클래스와 객체가 늘어나면 생성, 결합, 책임 분배 문제가 반복된다. GoF 패턴은 이 반복 문제를 공통 언어로 만들어 설계 리뷰 시간을 줄인다.
- **핵심 직관**: 코드를 복사하는 방법이 아니라, 객체들이 어떤 책임으로 연결될지 정하는 설계 어휘이다.

## 깊이 이해
- **배경·문제의식**: 상속만으로 변경을 흡수하면 클래스 폭증과 결합 증가가 발생한다. GoF는 생성 5개, 구조 7개, 행위 11개 패턴으로 변경 지점을 분리한다.
- **작동 원리**: 생성 패턴은 객체 생성 책임을 캡슐화하고, 구조 패턴은 객체 조합 방식을 정리하며, 행위 패턴은 알고리즘과 협력 흐름을 분리한다.
- **비유**: 건축 도면에서 현관, 계단, 비상구 배치 원칙이 반복되듯, 소프트웨어도 객체 생성과 협력 배치 원칙이 반복된다.
- **구체 예시**: 결제 수단 5개가 있을 때 Strategy는 `PayStrategy` 인터페이스로 카드, 계좌, 포인트 알고리즘을 교체하고, Factory Method는 결제 객체 생성을 하위 클래스로 위임한다.
- **흔한 오해·주의점**: 패턴 이름을 많이 쓰는 것이 설계 품질을 보장하지 않는다. 기능 1개에 패턴 3개를 얹으면 클래스 수와 디버깅 경로가 증가한다.

## 연결 개념
- SOLID 원칙: 패턴 적용 전 책임 분리 기준
- 리팩터링: 중복과 조건문이 드러난 뒤 패턴으로 구조 개선
- 아키텍처 패턴: GoF는 클래스 수준, MVC·MSA는 시스템 수준 패턴

# 📝 【답안용】 시험 답안 템플릿

> 목적: 시험장에서 25분에 그대로 쓰는 답안 양식. 작성방식(추상표현 금지·수치·도식·문제유형 전환)을 엄격히 지킨다.
> 핵심: 패턴 23개 나열이 아니라, 생성·구조·행위 분류와 변경 지점 통제 기준을 연결한다.

## 핵심 인사이트 (3줄 요약)

> 1. **본질**: GoF 디자인 패턴은 객체지향 설계에서 반복되는 생성·구조·행위 문제를 재사용 가능한 설계 해법으로 정리한 것이다.
> 2. **가치**: 공통 설계 용어를 통해 코드 리뷰, 리팩터링, 변경 영향 분석 시간을 기능 단위 1~2시간에서 패턴 단위 20분 내외로 줄인다.
> 3. **판단 포인트**: 패턴 적용 여부는 클래스 수가 아니라 변경 빈도, 결합도, 테스트 격리 필요성으로 판단한다.

## 출제 의도 및 답안 포인트

| 출제 의도 | 반드시 짚을 핵심 | 감점 회피 포인트 |
|:---|:---|:---|
| 객체지향 설계 재사용 역량 확인 | 생성 5종, 구조 7종, 행위 11종 분류와 대표 예시 | 23개 이름만 나열하고 적용 의도 누락 |
| 변경 지점 분리 판단 확인 | Factory, Adapter, Strategy, Observer 등 변경 축 연결 | 패턴을 프레임워크 기능으로 오해 |
| 오남용 리스크 인식 확인 | 클래스 폭증, 간접 호출, 디버깅 비용, 팀 숙련도 | 모든 문제에 패턴 적용을 권장하는 답안 |
> 요약: 출제자는 패턴 암기보다 변경 축을 찾아 적정 패턴을 선택하는 설계 판단을 본다.

## Ⅰ. 개요 및 필요성

- 개요: 객체지향 설계 문제의 반복 해법
- 배경: 객체 생성 위치, 클래스 결합, 알고리즘 교체, 이벤트 통지 문제가 반복될 때 의존성 방향이 흐려지고 변경 영향 범위가 확대됨.
- 필요성: Creational, Structural, Behavioral pattern으로 변경 지점을 인터페이스와 객체 조합으로 분리해 수정 파일 수와 회귀 테스트 범위를 통제해야 함.

---

## Ⅱ. 구조 및 구성요소

```text
설계 문제 -> 생성 패턴 / 구조 패턴 / 행위 패턴
생성 패턴 -> Factory Method / Abstract Factory / Builder / Prototype / Singleton
구조 패턴 -> Adapter / Bridge / Composite / Decorator / Facade / Flyweight / Proxy
행위 패턴 -> Strategy / Observer / Command / Iterator / State / Template Method
적용 결과 -> 결합도 감소 -> 변경 영향 통제
```

| 구성요소 | 역할 | 대표 패턴 |
|:---|:---|:---|
| 생성 패턴 | 객체 생성 책임 분리 | Factory Method, Builder, Singleton |
| 구조 패턴 | 객체 조합과 인터페이스 변환 | Adapter, Facade, Decorator |
| 행위 패턴 | 알고리즘·상태·통지 흐름 분리 | Strategy, Observer, Command |
| 적용 맥락 | 변경 빈도와 결합도 기준 | 코드 리뷰, 리팩터링, 테스트 |
> 요약: GoF 23종은 생성·구조·행위 세 축으로 객체 생성, 연결, 협력 문제를 분리한다.

---

## Ⅲ. 동작원리 및 흐름도

```text
요구 변경 감지 -> 변경 지점 식별
변경 지점 -> 생성 / 구조 / 행위 분류
분류 결과 -> 후보 패턴 선택
선택 패턴 -> 인터페이스 추출 -> 객체 조합
테스트 -> 결합도 / 중복 / 분기 수 점검
```

| 단계 | 처리 내용 | 검증 기준 |
|:---:|:---|:---|
| 1 | 변경 빈도 높은 생성·분기·통지 코드 식별 | 조건문 3개 이상, 중복 클래스 2개 이상 |
| 2 | 생성·구조·행위 문제로 분류 | 생성 위치, 의존 방향, 알고리즘 교체성 |
| 3 | 후보 패턴과 단순 설계 비교 | 클래스 증가 수, 호출 단계, 테스트 격리 |
| 4 | 인터페이스와 구현 클래스 분리 | 순환 의존 0건, Mock 테스트 가능 |
| 5 | 회귀 테스트와 리뷰로 오남용 제거 | 커버리지 80% 이상, 복잡도 증가 확인 |
> 요약: 패턴 적용은 문제 식별, 분류, 후보 비교, 구현, 검증 순서로 진행한다.

## Ⅳ. 특징

| 구분 | 기존 임시 설계 | GoF 패턴 적용 | 수치·판단 포인트 |
|:---|:---|:---|:---|
| 생성 | `new` 호출 산재 | Factory·Builder로 생성 집중 | 생성 지점 10곳에서 1곳으로 축소 |
| 구조 | 직접 의존 | Adapter·Facade로 경계 완충 | 외부 API 변경 시 수정 모듈 1~2개 |
| 행위 | if/switch 분기 | Strategy·State로 알고리즘 교체 | 분기 5개 이상이면 후보 검토 |
| 테스트 | 실제 객체 결합 | 인터페이스 기반 대역 객체 | 단위 테스트 100ms 이하 목표 |
| 리스크 | 즉시 구현 가능 | 클래스·간접 호출 증가 | 신규 클래스 3개 초과 시 리뷰 |
> 요약: GoF 패턴은 변경 지점 통제에 유리하지만 클래스 증가와 호출 추적 비용을 함께 검토해야 한다.

## Ⅵ. 실무 적용 및 결론

**적용 방안 3개:**
1. 결제·배송·할인처럼 알고리즘이 월 2회 이상 바뀌는 영역은 Strategy와 Factory Method를 조합해 분기 수를 5개 이하로 통제한다.
2. 외부 PG·메일·문자 API는 Adapter와 Facade를 두어 공급사 SDK 변경 시 수정 범위를 어댑터 1개로 제한한다.
3. 이벤트 알림·캐시 무효화는 Observer 또는 Command로 비동기 처리하고, 큐 적체 길이와 실패 재시도 횟수를 대시보드화한다.

**결론 (2줄):**
- 기술사 판단: 변경 빈도가 낮고 코드 100라인 이하인 기능은 단순 구현, 변경 축이 2개 이상이면 GoF 패턴 적용이 타당함
- 향후 방향: 패턴은 DDD, Clean Architecture, 리팩터링과 결합되어 모듈 경계와 테스트 자동화 기준으로 발전함
