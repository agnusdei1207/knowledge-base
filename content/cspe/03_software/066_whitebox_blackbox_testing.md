# 📖 【암기용】 개념 완전 이해

> 목적: 이 개념을 처음 보는 사람도 완벽히 이해하게 만든다. 시험 답안 양식이 아니라, 이해를 위한 친절한 설명이다.

## 한눈에
- **개요**: **화이트박스 테스트**는 소스코드 내부의 제어 흐름을 직접 보면서 실행 경로를 검증하는 기법이고, **블랙박스 테스트**는 내부 구조를 모른 채 입력과 출력만으로 요구사항 충족 여부를 검증하는 기법이다. 두 기법은 코드 구조를 근거로 케이스를 뽑는지, 명세를 근거로 케이스를 뽑는지에 따라 세부 기법이 서로 다르게 발전했다.
- **왜 필요한가**: 개발자는 자신이 작성한 조건문·반복문이 의도대로 모든 경로를 타는지 확인해야 하고(화이트박스), QA나 사용자는 소스코드를 몰라도 "정해진 입력에 정해진 출력이 나오는가"만으로 결함을 찾아야 한다(블랙박스). 검증 주체와 관점이 다르기 때문에 검증 기법 자체도 별도로 발전했다.
- **핵심 직관**: 화이트박스는 `if(age >= 19)`라는 코드가 보이므로 참(True)·거짓(False) 두 갈래를 모두 지나가도록 값을 넣어 확인한다. 블랙박스는 코드는 안 보이고 "19세 이상만 가입 가능"이라는 명세만 보고, 그 문장을 깨뜨릴 수 있는 값(18, 19, 20)을 밖에서 넣어 확인한다.

## 핵심 용어 정리
| 용어 | 의미 | 비유 |
|:---|:---|:---|
| 화이트박스 테스트 | 소스코드 구조가 보이는 상태에서 실행 경로를 근거로 케이스를 설계 | 투명 상자 안을 보며 검사 |
| 블랙박스 테스트 | 소스코드가 안 보이는 상태에서 명세의 입출력을 근거로 케이스를 설계 | 불투명 상자를 겉에서 검사 |
| 구문 검사 (Statement) | 코드의 모든 문장을 최소 1번 실행해보는 화이트박스 기법 | 모든 바닥을 한 번씩 밟기 |
| 분기 검사 (Branch) | `if`문의 참/거짓 결과를 모두 실행해보는 화이트박스 기법 | 갈림길 양쪽 다 가보기 |
| 경로 검사 (Path) | 시작부터 끝까지 가능한 모든 실행 흐름 조합을 실행해보는 화이트박스 기법 | 미로의 모든 경로 탐색 |
| 동등 분할 (Equivalence Partitioning) | 같은 결과를 내는 입력 구간을 하나로 묶고 대표값 1개만 테스트하는 블랙박스 기법 | 반을 나눠 대표 1명만 검사 |
| 경계값 분석 (Boundary Value Analysis) | 입력 구간의 경계(최솟값·최댓값 부근)를 집중 테스트하는 블랙박스 기법 | 문턱 근처를 집중 점검 |
| 오류 예측 (Error Guessing) | 테스터의 경험을 바탕으로 결함이 있을 법한 곳을 짐작해 테스트하는 기법 | 경험으로 찔러보기 |
| 그레이박스 테스트 (Gray-box) | 내부 구조를 일부 아는 상태에서 외부 관점의 도구로 테스트하는 화이트+블랙박스 혼합 기법 | 반투명 상자 |
| 퍼징 (Fuzzing) | 무작위·비정상 입력을 대량으로 자동 주입해 예상 밖의 결함(특히 보안 취약점)을 찾는 블랙박스 확장 기법 | 무작위로 마구 두드려보기 |

## 깊이 이해

### 화이트박스 세부 기법을 구체 수치로 이해하기
`if (age >= 19)`라는 코드가 있을 때:
- **구문 커버리지**: `age=20`(참 경로) 한 값만 넣어도 그 줄은 실행되므로 100%를 채울 수 있다. 하지만 `age<19`일 때 실행되는 else 분기는 한 번도 안 밟혔을 수 있다.
- **분기 커버리지**: 참(`age=20`)과 거짓(`age=18`) 두 값을 모두 넣어야 100%가 된다.
- **경로 커버리지**: 조건문이 여러 개 중첩되거나 반복문이 있으면 조합 수가 급격히 늘어난다. 예를 들어 독립된 `if`문 3개가 연달아 있으면 가능한 경로는 2³=8가지이고, 반복문이 섞이면 사실상 무한대로 발산해 100% 달성이 현실적으로 불가능해진다.

### 블랙박스 세부 기법을 구체 수치로 이해하기
"나이는 0~150 사이의 정수만 입력 가능하고, 19세 이상만 가입 가능하다"는 명세가 있을 때:
- **동등 분할**: 0~150이라는 유효 구간 전체를 하나의 클래스로 보고 대표값(예: 50) 1개만 테스트한다. 1부터 150까지 150번 넣어보는 것은 비효율적이며, 같은 클래스 안의 값은 같은 코드 경로를 타므로 대표값 검증으로 충분하다는 것이 동등 분할의 논리다.
- **경계값 분석**: 결함은 실제로 경계 부근(구간이 바뀌는 지점)에서 가장 많이 발생한다. 이 명세라면 유효·무효 경계인 -1, 0, 18, 19, 150, 151 같은 값을 집중적으로 넣는다. 대표값 1개(동등 분할)와 경계값 여러 개(경계값 분석)를 합치면 적은 케이스 수로도 결함 검출력을 높일 수 있다.
- **오류 예측**: 테스터가 "빈 문자열을 넣으면 어떻게 될까", "숫자 대신 문자를 넣으면 어떻게 될까"처럼 명세에 명시되지 않은 예외적 입력을 경험적으로 짐작해 추가하는 기법이다.

### 화이트박스와 블랙박스의 한계를 보완하는 그레이박스
화이트박스는 내부를 다 보지만 명세와 대조하지 않으므로 "코드가 원래 하기로 한 일 자체가 잘못됐는지"는 놓치고, 블랙박스는 명세와 대조하지만 내부에 실행되지 않는 죽은 코드가 있어도 알 수 없다. 그레이박스 테스트는 개발자가 내부 구조(어떤 값이 경계인지, 어디가 취약한지)를 알고 있는 상태에서, 실제 테스트 실행은 UI 자동화 도구 같은 외부 관점 도구로 수행하는 절충 방식이다. 내부를 알기 때문에 블랙박스 테스트 케이스를 더 정확한 지점(진짜 경계)에 겨냥할 수 있다.

### 퍼징 — 블랙박스의 극단적 확장
경계값 분석이 사람이 예측한 몇 개의 값을 찌르는 것이라면, 퍼징은 사람이 미처 예측하지 못한 값(특수문자, 매우 긴 문자열, 깨진 바이너리 등)을 자동화 도구가 초당 수천~수만 개씩 무작위로 주입하는 기법이다. 사람의 직관으로는 떠올리기 힘든 극단적 입력에서 발생하는 버퍼 오버플로 같은 보안 취약점을 찾는 데 특히 효과적이다.

### 비유
화이트박스는 의사가 내시경으로 환자의 내부 장기를 직접 들여다보며 이상을 찾는 것과 같고, 블랙박스는 환자에게 증상을 물어보고(입력) 반응(출력)만으로 병을 진단하는 문진과 같다. 그레이박스는 이전 검사 기록(내부 정보)을 참고하면서 문진(외부 관점)을 더 정확하게 하는 것이고, 퍼징은 환자에게 무작위로 다양한 자극을 줘가며 예상 못한 반응을 찾는 것에 비유할 수 있다.

# 📝 【답안용】 시험 답안 템플릿

> 목적: 시험장에서 25분에 그대로 쓰는 답안 양식. 작성방식(추상표현 금지·수치·도식·문제유형 전환)을 엄격히 지킨다.
> 핵심: 이 시험은 정보를 많이 나열하는 시험이 아니라, 문제 신호어에서 출제자 의도를 읽고 핵심 논점을 선별해 쓰는 시험이다.

## 핵심 인사이트 (3줄 요약)

> 1. **본질**: 소프트웨어 결함을 도출하기 위해, 내부 소스코드 로직과 구조를 해부하는 **화이트박스(구조 기반)** 기법과, 내부 구조는 배제한 채 요구 명세서 기반의 입출력만 검증하는 **블랙박스(명세 기반)** 기법의 대조적 테스트 패러다임이다.
> 2. **가치**: 화이트박스는 코드 내부의 데드코드(사각지대)와 분기 로직의 치명적 결함을 조기에 적발하며, 블랙박스는 실제 사용자의 비즈니스 시나리오 결함과 기획 스펙(명세) 누락을 최종적으로 방어한다.
> 3. **판단 포인트**: 각 기법이 테스트 4단계 레벨(단위 -> 시스템)에서 어떻게 포지셔닝되는지 도식화하고, 동등 분할/경곗값 분석(블랙박스)과 제어 흐름(화이트박스) 등 구체적인 엔지니어링 테스팅 기법을 맵핑해야 한다.

## 출제 의도 및 답안 포인트

| 출제 의도 | 반드시 짚을 핵심 | 감점 회피 포인트 |
|:---|:---|:---|
| 소프트웨어 검증 시야(Visibility)에 따른 테스트 기법 분류 | **내부 로직(구조) 검증** vs **명세서 입출력(기능) 검증** 도식 | 뚜껑을 연다/닫는다 수준의 비유에 머물고 명세(Spec) 관점 누락 |
| 실무 테스팅 기법 세부 분류 매핑 | 화이트(구문/분기/경로 커버리지) vs 블랙(경계값/동등분할) | 화이트박스와 블랙박스의 기법을 섞어 쓰거나 혼동하여 서술 |
| SDLC(소프트웨어 생명주기) V-모델 융합 및 주체 매핑 | 화이트(개발자/단위테스트) vs 블랙(QA팀/시스템테스트) | 블랙박스가 시스템 테스트 단계에서만 쓰인다는 오해 (통합 테스트에서도 쓰임) |

> 요약: 화이트박스는 "코드를 맞게 짰는가(Build it right)?"를 묻고, 블랙박스는 "맞는 프로그램(기획)을 짰는가(Build the right thing)?"를 묻는다. 코드가 아무리 버그 없이 돌아가(화이트 완벽) 봤자, 기획자가 원한 결제 기능(블랙)이 빠져 있으면 그 시스템은 쓰레기다.

## Ⅰ. 개요 및 필요성

- 정의: **화이트박스**는 개발자가 시스템 내부 구조(Source Code)의 제어 흐름과 알고리즘을 분석하여 논리적 경로를 검증하는 기법이며, **블랙박스**는 내부 구조를 블랙박스로 취급하고 명세(Requirement Spec) 기반으로 입력(Input)에 대한 출력(Output) 결과값을 검증하는 기법
- 배경: 개발자 관점의 구조적 결함(메모리 누수, 무한 루프)과, 사용자 관점의 비즈니스 논리 결함(명세 누락)은 단일한 테스트 접근법으로는 상호 보완적(Mutually Exclusive) 커버가 불가
- 필요성: 시스템 내부 로직의 100% 실행 커버리지 보장(화이트박스)과, 사용자 인터페이스(UI) 및 외부 연동의 최종 비즈니스 요건 충족(블랙박스)을 이중(Dual) 렌즈로 교차 검증하여 결함 유출률(Defect Leakage)을 0%에 수렴시키기 위함

## Ⅱ. 화이트박스 vs 블랙박스 아키텍처 대조 도식

보이는가(투명), 보이지 않는가(불투명). 렌즈의 방향이 완전히 반대다.

```text
[ 1. 화이트박스 테스트 (White-box: 투명 유리 상자) ] 
                 +---------------------------------+
[ 입력값 10 ] ---> | 🔍 소스코드 로직 훤히 보임      |
                 |  if(x>5) { A경로 } else { B경로} | ---> (출력 결과 확인)
                 +---------------------------------+
                (개발자가 A경로, B경로 다 타보도록 입력값 설계)


[ 2. 블랙박스 테스트 (Black-box: 불투명 강철 상자) ]
                 +---------------------------------+
[ 입력값 10 ] ---> | ⬛ 내부 구조는 아예 안 보임     | ---> [ 출력 예상값 20 ]
                 |   명세서: "10 넣으면 20 나옴"   |      (출력이 20 맞는지 확인 ✅)
                 +---------------------------------+
               (테스터는 안에 if문이 10개든 100개든 관심 없음)
```

| 비교 축 (차이점) | 화이트박스 (White-box Testing) | 블랙박스 (Black-box Testing) |
|:---|:---|:---|
| **검증 기반 대상** | 소스코드(Source Code), 제어 흐름, 알고리즘 | 요구사항 명세서(Requirement Spec), 기획서 |
| **수행 주체 / 단계** | 소스코드를 짠 **개발자**. (주로 단위/통합 테스트 단계) | 전문 **QA 테스터, 고객**. (주로 시스템/인수 테스트 단계) |
| **장점 (발견 버그)**| 기획서에 없는 숨겨진 악성 코드(백도어), 절대 실행되지 않는 죽은 코드(Dead Code) 색출 | 개발자가 명세서를 오해해서 아예 개발을 누락해 버린 핵심 비즈니스 기능(기능 누락) 색출 |
| **단점 (맹점 리스크)**| 사용자가 원하는 버튼이 빠져있어도, 내부 로직만 돌면 "성공(Pass)" 처리되는 맹점 유발 | 내부에서 불필요한 메모리가 줄줄 새도 밖에서 결과값만 맞으면 통과(Pass)되는 성능 한계 |

> 요약: 화이트박스 테스트 100% 찍었다고 자랑하는 개발자에게 기획자가 "어, 근데 카카오페이 결제 버튼은 어딨어?"라고 물으면 개발자는 할 말이 없다. 코드를 안 짰으니 테스트 코드도 안 짰기 때문이다. 기능 누락은 오직 블랙박스(기획서 대조)로만 잡을 수 있다.

## Ⅲ. 세부 엔지니어링 테스팅 기법 (외과적 찌르기)

그냥 막 찌르는 게 아니다. 버그가 가장 많이 숨어있는 취약점을 확률적으로 난도질하는 공학적 기법이다.

| 테스트 유형 | 핵심 찌르기 기법 (공학적 접근) | 발생 시나리오 및 통제 효과 |
|:---|:---|:---|
| **화이트박스** <br> (구조 분석) | **구문(Statement) 검사**: 코드 모든 줄 1번씩 실행 <br> **분기(Branch) 검사**: `if`문의 참(T)/거짓(F) 다 타보기 <br> **경로(Path) 검사**: 루프(for)의 모든 흐름 조합 밟아보기 | `if`문 안쪽에 있는 희귀한 예외 처리(Exception) 코드가 실제 터졌을 때 버그를 뿜는지 사전에 100% 밟아보고 터뜨림 |
| **블랙박스** <br> (명세 분석) | **동등 분할 (Equivalence Partitioning)**: 1~100값이 정상이면 중간값 '50' 딱 1개만 찔러서 테스트 효율 극대화 <br> **경곗값 분석 (Boundary Value Analysis)**: 에러의 99%는 경계(0, 100, 101)에서 터지므로 끄트머리 맹폭격 <br> **오류 예측 (Error Guessing)**: 테스터의 짬(경험)으로 찌르기 | 고객 나이(0~150세) 입력 칸에 1살부터 150살까지 150번 누르는 멍청한 QA를 배제하고, `-1(경계), 15(동등), 151(경계)` 3번 클릭으로 버그 압살 |

> 요약: 신입 QA는 입력 칸에 1, 2, 3을 차례대로 넣어보며 퇴근을 늦춘다. 시니어 QA는 경계값(-1, 0, 최대값+1)만 3번 찌르고 버그를 5개 뽑아낸 뒤 퇴근한다.

## Ⅳ. 현대 애자일(Agile) 환경에서의 융합망 (회색상자)

화이트박스(느림)와 블랙박스(단편적)의 단점을 섞어 만든 혼종 무기가 등장했다.

| 융합/확장 기법 | 물리적 테스트 융합 메커니즘 | 해결되는 비즈니스/품질 한계 |
|:---|:---|:---|
| **회색상자 테스트** <br> (Gray-box Testing) | 개발자가 코드 내부(화이트)를 아는 상태에서, 사용자 관점(블랙)의 UI 테스트 툴(Selenium)을 돌리는 하이브리드 검증 | 내부 구조를 아니까 버그 찌를 곳(경계값)을 정확히 알고, 블랙박스 툴로 빠르게 자동화(UI 봇)하여 디버깅 속도 극강 수렴 |
| **퍼징 테스트** <br> (Fuzzing) | 블랙박스의 극단적 진화. 해킹 봇이 프로그램 입력구(API)에 1초당 1만 개의 미친 쓰레기값(특수문자, 10GB 문자열)을 무작위로 때려 부음 (무작위 융단폭격) | 사람 머리(경계값 분석)로는 도저히 상상할 수 없는 기괴한 버퍼 오버플로 메모리 붕괴(보안 취약점) 버그 0.1초 컷 색출 |

> 요약: 현대 파이프라인에서 테스트는 더 이상 사람이 엑셀 들고 체크하는 막일이 아니다. JUnit(화이트박스 자동화)과 Cypress(블랙박스 자동화) 봇들이 CI 서버 안에서 초당 1,000번씩 교차 융단폭격을 때리는 기계들의 전쟁터다.

## Ⅴ. 실무 적용 방안 및 결론

**적용 방안 3개:**
1. [JaCoCo 플러그인 기반 화이트박스 커버리지 CI 연동 차단] 개발자가 로컬에서 JUnit 화이트박스 테스트 수행 시, 소스코드의 몇 줄(Line)과 분기(Branch)를 밟았는지 JaCoCo 툴로 퍼센트(%)를 추출하고, 젠킨스 파이프라인에 80% 미만 시 빌드 Failed 처리 락인 (Shift-Left 통제)
2. [결정 테이블(Decision Table) 기반 복합 논리 블랙박스 설계] 금융권 여신 시스템(대출 심사) 등 `if-else` 조합이 수백 개인 복잡한 비즈니스 룰 검증 시, 개발자에게 코드를 묻지 않고 명세서 기준 입력 조건과 출력 결과의 조합(T/F)을 테이블로 매핑하여 빈틈없는 블랙박스 TC(Test Case) 무결성 추출
3. [REST API 엔드포인트 대상 경곗값/퍼징(Fuzzing) 자동화] MSA 아키텍처 환경에서 수십 개의 마이크로서비스 API(Controller)를 대상으로 Postman/Newman 스크립트를 구성. `id=-1`, `amount=9999999999` 등 블랙박스 경계값 데이터 페이로드를 매일 야간(Nightly) 배치로 쏘아 에러율(5xx) 감시

**결론:**
- 기술사 판단: 화이트박스와 블랙박스 테스트는 양립 불가능한 경쟁 기법이 아니라, 시야(Visibility)의 한계를 서로 상쇄하는 필수 교차 검증 도구다. 화이트박스가 시스템 내부의 혈관(로직)과 뼈대(구조)의 구조적 강건성을 입증한다면, 블랙박스는 그 시스템이 사용자의 세상(명세)과 제대로 호흡하는지를 최종적으로 인가하는 릴리즈(Release)의 게이트키퍼다.
- 향후 방향: 최근 클라우드 환경에서는 블랙박스 테스트의 막대한 수동(Manual) 노가다를 소거하기 위해, AI 비전(Vision) 봇이 화면을 캡처하고 버튼을 눌러보거나 LLM(거대언어모델)이 기획서를 읽고 블랙박스 BDD 테스트 코드(Cucumber)를 100% 자동 생성해 주는 극단적 자동화(Test Automation) 시대로 빠르게 전환되고 있다.
