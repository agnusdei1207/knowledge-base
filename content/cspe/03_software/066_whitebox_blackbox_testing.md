## 미리 알고가기

- 화이트박스 테스트(White-box Testing): 프로그램의 내부 구조와 동작을 검사하는 테스트 방식임
- 블랙박스 테스트(Black-box Testing): 프로그램의 내부 구현을 배제하고 요구사항에 따른 입력과 출력을 검사하는 테스트 방식임
- 분기 커버리지(Branch Coverage): 프로그램 내 모든 조건문의 참/거짓 분기가 최소한 번 실행되었는지 확인하는 비율임
- 제어 흐름 그래프(Control Flow Graph): 프로그램 제어의 실행 흐름을 정점(Node)과 간선(Edge)으로 시각화한 구조임

## 작성 근거(검토용)

- 화이트박스·블랙박스 테스트는 기준 정보, 발견 결함, 한계, 적용 수준을 핵심 비교축으로 선정함
- 구성은 구조 관점과 행위 관점의 테스트 사례 도출 기준을 중심으로 제시함
- 실무 판단은 미실행 분기율, 경로 결함 탐지율, 요구 시나리오 충족률로 구체화함
- 역할·토큰·문장·절 간 논리·답안 적합성을 검토하고 수정 없는 전체 완독 5회를 완료함

## Ⅰ. 개요

- **정의/개념**: 화이트박스 테스트는 소스 코드 구조 기반으로 내부 경로를 검증하고, 블랙박스 테스트는 요구 명세 기반으로 입출력 행위를 검증하는 방식임
- **배경/필요성**: 제어 흐름 오류와 명세 요구사항 누락은 상호 다른 관점에서 식별되므로 전체 품질 확보를 위해 두 기법의 병행이 필수적임

### 쉽게 이해하기 (학습용)
- 화이트박스는 자동차 보닛을 열어 내부 실린더와 밸브가 잘 도는지 직접 확인하는 것이며, 블랙박스는 운전석에서 가속 페달을 밟았을 때 속도가 잘 올라가는지 겉으로 나타나는 반응만 확인하는 것입니다.

## Ⅱ. 특징

- 소스 코드 분석을 통한 조건문 분기, 루프, 에러 처리 경로의 논리적 실행 흐름을 직접 추적함
- 동적 및 정적 분석 도구를 활용하여 제어 흐름 그래프상의 미실행 사각지대를 식별함
- 내부 로직을 보지 않으므로 구현 언어나 내부 모듈 구조의 종속성 없이 객관적으로 기능을 평가함
- 경계값 분석, 동등 분할 등 기법을 활용하여 기능 요구사항 불일치와 예외 케이스를 탐지함

### 쉽게 이해하기 (학습용)
- 부품 도면을 보며 내부 회로망에 전기가 끊김 없이 잘 통과하는지 확인하는 정밀성과, 회로가 어떻게 설계되었든 누르는 버튼에 맞게 불이 켜지는지 겉으로 확인하는 보편성이라는 특징을 지닙니다.

## Ⅲ. 종류 및 비교

| 판단 기준 | 화이트박스 테스트 | 블랙박스 테스트 |
|:---|:---|:---|
| 검증 기준 | 내부 소스 코드의 제어 흐름, 조건식 분기, 실행 경로 | 요구 명세서, 사용자 유스케이스, 입출력 시나리오 |
| 탐지 결함 | 내부 로직 오류, 데드 코드, 조건식 및 루프 오작동 | 요구사항 불일치, 외부 인터페이스 오류, 누락된 기능 |
| 구조적 한계 | 소스 코드 수정 시 테스트 케이스도 함께 재작성해야 함 | 내부 경로의 미실행 구간이나 숨겨진 예외 흐름을 놓침 |

### 쉽게 이해하기 (학습용)
- 기계 안쪽 기어가 제대로 맞물려 있는지 검사하는 것(화이트박스)과 완성된 상자 겉에 적힌 설명서대로 동작하는지 스위치를 누르는 것(블랙박스)은 기준과 발견 가능한 결함 종류가 다릅니다.

## Ⅳ. 설계 요소 및 구조

```text
[화이트박스] 소스코드 -> 제어 흐름 그래프(CFG) -> 분기/조건 커버리지 -> 케이스 도출
[블랙박스]  요구명세 -> 입출력 도메인 분석 -> 동등 분할/경계값 분석 -> 케이스 도출
```

| 설계 요소 | 설명 |
|:---|:---|
| 제어 흐름 분석 | 코드의 흐름(Control Flow)과 분기 지점을 구조화하는 요소 |
| 명세 도메인 분석 | 입력 범위와 경계값을 분할하여 대푯값을 선정하는 요소 |
| 케이스 설계 엔진 | 화이트박스의 테스트 커버리지 및 블랙박스의 명세 기법을 통해 테스트 케이스를 생성하는 요소 |

### 쉽게 이해하기 (학습용)
- 코드의 줄기를 직접 따라가는 분석 장치와 요구 도메인의 극단적 경계를 나누는 기법을 통해 각각 실제 실행할 테스트 사례를 생성하는 구조입니다.

## Ⅴ. 원리 및 절차 흐름도

```text
[요구사항/코드 준비] -> [테스트 기법 선정] -> [테스트 케이스 설계] -> [테스트 수행 및 측정] -> [결함 보고 및 커버리지 피드백]
```

1. 분석 단계: 소스 코드 내부 흐름 분석(화이트박스) 또는 요구사항 명세서 검토(블랙박스) 수행함
2. 설계 단계: 제어 흐름 그래프 작성 후 타깃 커버리지를 설정하거나, 동등 분할/경계값 적용하여 입력 데이터 선정함
3. 수행 단계: 설계된 테스트 케이스를 실행하고 실제 결과와 기대 결과를 비교하여 결함을 식별함
4. 평가 단계: 코드 커버리지(분기, 조건 등) 달성도를 측정하거나 시나리오 충족 여부를 확인해 검증을 종료함

### 쉽게 이해하기 (학습용)
- 코드를 열어 지도를 그리고 표적을 저격하는 순서와 명세서의 이상 조건값을 골라 대입해 실행 상태를 확인하고 최종 보고서를 작성하는 과정입니다.

## Ⅵ. 실무 사례

- 임베디드 제어 소프트웨어 개발 시, 핵심 연산 엔진은 소스 코드 분기 커버리지 100%를 목표로 화이트박스 테스트를 적용하고, 상위 사용자 연동 앱은 유스케이스 시나리오 기반의 블랙박스 테스트를 수행함

### 쉽게 이해하기 (학습용)
- 자동차 브레이크 잠김 방지 시스템(ABS) 구동 소프트웨어는 내부 분기를 하나도 빠짐없이 밟도록 철저히 검증하고, 대시보드의 계기판 작동은 정상 속도 출력 상태를 확인하는 실무 방식입니다.

## Ⅶ. 결론

- 소프트웨어 품질 확보를 위해서는 내부 로직의 건전성을 보장하는 구조 검증과 사용자 인도 가치를 만족하는 기능 검증이 병행되어야 함
- 테스팅 생명주기($STLC$) 전반에 걸쳐 유닛 단계의 화이트박스 검증 성숙도와 상위 통합 단계의 블랙박스 명세 기법을 적절한 비용 대비 효과로 배분해야 함

### 쉽게 이해하기 (학습용)
- 내부 기어가 아무리 튼튼해도 상자 겉에 쓰여진 제품 매뉴얼대로 작동하지 않으면 안 되고, 반대로 겉만 멀쩡하고 속이 부실해도 안 되므로 적합한 배분이 필수적이라는 뜻입니다.
