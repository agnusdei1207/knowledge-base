## 미리 알고가기

- 화이트박스 테스트는 내부 코드 구조와 분기를 기준으로 검증하는 방식임
- 블랙박스 테스트는 내부 구현을 보지 않고 입력과 출력과 요구 기준으로 검증하는 방식임
- 두 방식은 대체 관계가 아니라 서로 다른 위험을 맡는 보완 관계임

## Ⅰ. 개요

- **정의/개념**: 화이트박스 테스트는 제어 흐름과 조건 분기와 경로를 기준으로 내부 로직을 검증하는 방식이고, 블랙박스 테스트는 구현 세부를 숨긴 채 요구사항과 입출력 행위를 기준으로 외부 동작을 검증하는 방식임.
- **배경/필요성**: 내부 로직 결함과 요구 해석 오류는 서로 다른 방식으로 드러나므로, 한 가지 관점만으로는 품질 위험을 충분히 줄이기 어려워 두 접근을 구분해 써야 함.

## Ⅱ. 특징

- 화이트박스는 로직 누락과 희귀 분기 문제를 찾는 데 강함
- 블랙박스는 기능 요구와 사용자 시나리오 검증에 강함
- 화이트박스만 쓰면 요구 미스매치를 놓치기 쉽고 블랙박스만 쓰면 숨은 경로 문제를 놓치기 쉬움
- 테스트 수준과 모듈 특성에 따라 두 방식의 비중이 달라져야 함

## Ⅲ. 종류 및 비교

| 구분 | 화이트박스 테스트 | 블랙박스 테스트 |
|:---|:---|:---|
| 기준 정보 | 내부 코드 구조와 분기와 경로를 기준으로 삼음 | 요구사항과 입출력과 업무 시나리오를 기준으로 삼음 |
| 구조상 장점 | 실행되지 않은 로직과 조건 누락을 찾기 좋음 | 사용자 관점의 기능 오류와 요구 불일치를 찾기 좋음 |
| 구조상 한계 | 구현 의존이 커서 구조 변경 때 유지비가 늘 수 있음 | 내부 희귀 경로나 숨은 오류 처리 흐름은 놓칠 수 있음 |
| 적합한 수준 | 단위 테스트와 핵심 로직 검증에 잘 맞음 | 통합, 시스템, 인수 테스트에 잘 맞음 |

> 요약: 화이트박스와 블랙박스의 차이는 어느 쪽이 더 좋으냐가 아니라 어떤 위험을 어떤 관점으로 잡을 것이냐에 있음.

## Ⅳ. 구성요소 및 구조

| 구성요소 | 설명 |
|:---|:---|
| 구조 관점 | 제어 흐름과 분기와 조건을 분석해 코드 내부 위험 지점을 드러냄 |
| 행위 관점 | 사용 시나리오와 요구 명세를 기준으로 기대 결과를 검증함 |
| 테스트 케이스 도출 기준 | 구조 기반과 요구 기반으로 케이스 도출 기준을 달리해 공백을 줄임 |
| 결합 운영 전략 | 두 관점을 함께 운영해 기능 결함과 로직 결함을 균형 있게 잡음 |

## Ⅴ. 원리 및 절차 흐름도

```text
+-------------+     +-------------+     +-------------+     +-------------+
| 대상 분석      | --> | 케이스 도출    | --> | 실행/실패 관찰 | --> | 공백 보완      |
+-------------+     +-------------+     +-------------+     +-------------+
```

1. **대상 분석**: 구조 중심인지 요구 중심인지 관점을 정함
2. **케이스 도출**: 경로나 시나리오를 기준으로 테스트를 설계함
3. **실행 및 실패 관찰**: 결함 위치나 요구 위반을 확인함
4. **공백 보완**: 다른 관점 테스트로 누락 영역을 채움

## Ⅵ. 실무 적용 및 유의점

1. 핵심 계산 모듈이나 보안 검증 로직에서는 화이트박스 테스트가 중요하지만 구현 세부에 과도하게 묶이면 유지비가 커지므로 핵심 분기만 선별하고 미실행 분기 비율과 경로 결함 탐지율로 확인함
2. 사용자 업무 흐름과 계약 검증에서는 블랙박스 테스트가 필수지만 내부 오류 경로가 비어 있을 수 있으므로 구조 기반 테스트를 함께 두고 요구 시나리오 충족률과 운영 유출 결함 비율로 확인함

## Ⅶ. 결론

화이트박스와 블랙박스 테스트는 한쪽을 고르는 문제가 아니라 내부 구조 위험과 요구 위험을 역할 분담해 검증하는 문제임.
