## Ⅰ. 개요
- Barry Boehm이 제안한 프로그램 규모(LOC) 기반의 비용 산정 모델임
- 개발 노력(Effort)을 맨먼스(MM) 단위로 산출하며 프로젝트 유형별 계수를 적용함
| 구분 | 내용 | 비유 |
| --- | --- | --- |
| 출제의도 | COCOMO 유형(Organic/Semi/Embedded), COCOMO II, 비용 동인 | 건물 평당 공사비 계산 |

## Ⅱ. 구성요소
- 프로젝트 복잡도에 따른 3가지 개발 유형이 핵심임
[Organic] < [Semi-Detached] < [Embedded]
- 구성요소 표
| 구성요소 | 설명 | 비유 |
| --- | --- | --- |
| Organic | 5만 라인 이하, 소규모 팀, 익숙한 환경의 프로젝트 | 단독 주택 건축 |
| Semi-Detached | 30만 라인 이하, 중간 규모, 혼합된 기술 수준 | 빌라 단지 건축 |
| Embedded | 30만 라인 이상, 초대형, 하드웨어 연동 및 제약 극심 | 스마트 시티 건설 |
> 요약: 프로젝트의 성격에 따라 비용 산정 공식의 가중치를 달리함

## Ⅲ. 절차
- LOC 기반의 수리적 계산 및 보정 절차임
[규모 산정(LOC)] -> [유형 선정] -> [기본 노력 산출] -> [보정(비용동인)]
- 4단계 설명
1) LOC 추정: 기능 분할 후 예상 소스코드 라인수를 도출함
2) 기본 공식 적용: MM = a × (KDSI)^b 공식으로 기본 개발 노력 산출함
3) 비용 동인(Cost Drivers) 반영: 인력 역량, 제품 복잡도 등 15개 요소 곱함
4) 개발 기간 산정: TDEV = c * (MM)^d 공식을 통해 총 일정 도출함
> 요약: 코드 규모와 프로젝트 유형으로 기본 노력을 산정하고 비용 동인으로 보정함

## Ⅳ. 문제점
- 코드 라인수(LOC) 기반으로, 실제 가치나 난이도 반영에 한계가 있음 (원인: 측정 지표의 단순성)
- 요구사항과 설계가 확정되지 않은 초기에는 구현 언어별 LOC 예측 편차가 큼

## Ⅴ. 개선방안
- (단기) 요구사항 기반의 기능 점수(Function Point) 모델과 상호 보완 적용함
- (중기) 현대적 개발 환경(재사용, 자동화)을 반영한 COCOMO II로 전환함
- (장기) 머신러닝 기반의 유사 프로젝트 실적 데이터 연계 자동 산정 엔진 도입함

## Ⅵ. 전망
- 코드 자동 생성(Low-code/No-code) 확산으로 LOC 기반 산정의 의미가 퇴색될 것임
- 향후 '가치 중심 산정(Value-based Estimation)' 및 클라우드 자원 비용을 포함한 통합 모델이 주류가 될 것임
