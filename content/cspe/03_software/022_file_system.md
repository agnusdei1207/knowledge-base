# 📖 【암기용】 개념 완전 이해

> 목적: 이 개념을 처음 보는 사람도 완벽히 이해하게 만든다. 시험 답안 양식이 아니라, 이해를 위한 친절한 설명이다.

## 한눈에
- **개요**: **파일 시스템(File System)**은 디스크의 물리적 블록들 위에 파일·디렉터리라는 논리 구조와 **메타데이터**(이름, 크기, 권한, 위치)를 매핑해, 운영체제가 데이터를 체계적으로 저장·검색·삭제하게 해주는 커널의 저장장치 관리 계층이다. FAT·NTFS·ext4·APFS는 이 매핑 규칙을 서로 다르게 구현한 대표적 파일 시스템이다.
- **왜 필요한가**: 디스크는 그저 번호가 매겨진 블록의 나열일 뿐이라, 파일 시스템 없이는 어느 블록에 무엇이 저장됐는지 알 방법이 없다. 파일을 지울 때도 데이터를 실제로 지우지 않고 장부에서 "이 블록은 비었다"고 표시만 하려면, 블록과 파일을 연결하는 체계적인 메타데이터 관리가 필요하다.
- **핵심 직관**: FAT는 블록끼리 사슬처럼 연결한 연결 리스트 장부, ext4의 Inode는 파일마다 별도 색인표를 두는 방식, NTFS는 이 색인표들을 하나의 트리(MFT)로 통합 관리, APFS는 아예 덮어쓰지 않고 새 블록에 쓰는(CoW) 방식으로 SSD에 맞춰 설계됐다.

## 핵심 용어 정리 (내부에 등장하는 것들)

| 용어 | 의미 | 비유 |
|:---|:---|:---|
| 파일 시스템 | 디스크 블록에 파일·디렉터리 구조를 매핑하는 커널 계층 — 이 문서의 **상위 개념** | 도서관 전체 운영 규칙 |
| 메타데이터 | 파일 자체의 내용이 아닌, 이름·크기·권한·생성일 등 파일에 대한 부가 정보 | 책의 표지·바코드 정보 |
| 블록(클러스터) | 디스크를 나누는 최소 저장 단위(보통 4KB) | 서고의 칸막이 한 칸 |
| 연속 할당 | 파일 데이터를 디스크상에서 처음부터 끝까지 물리적으로 이어 붙여 저장 | 영화 필름을 한 줄로 이어 보관 |
| 연결 할당(FAT 방식) | 블록끼리 "다음 블록 번호"를 서로 가리키게 연결하는 방식 | 보물찾기 힌트 쪽지가 다음 위치를 알려줌 |
| 색인 할당(Inode 방식) | 파일마다 데이터 블록 위치를 모아둔 별도 색인 블록을 두는 방식 | 책 한 권의 목차 페이지 |
| 외부 단편화 | 파일이 지워지고 생기며 디스크에 자잘한 빈 공간이 흩어져 큰 파일을 못 넣는 현상 | 주차장에 차 1대 크기 빈자리만 여기저기 남음 |
| Inode | 파일의 메타데이터와 데이터 블록 포인터를 담은 구조체(파일 이름은 없음) | 책의 색인 카드(제목은 안 적혀 있음) |
| 디렉터리 엔트리 | "파일 이름 - Inode 번호" 쌍을 담은 목록 — 파일 이름은 여기서 관리 | 도서관 목록표(제목→서가 위치) |
| VFS(가상 파일 시스템) | 서로 다른 파일 시스템을 동일한 open/read/write API로 다루게 하는 커널 추상화 계층 | 여러 언어를 하나로 통역하는 통역사 |

## 깊이 이해

### 왜 필요했나 — 블록 관리 문제
- HDD 시절, 디스크는 물리적으로 회전하는 플래터 위를 바늘(헤드)이 오가며 읽는 구조였다. 파일을 처음부터 끝까지 이어 붙여 저장하면(연속 할당) 헤드 이동이 최소화돼 읽기 속도가 가장 빠르지만, 파일이 지워지고 새로 생기기를 반복하면 디스크에 자잘한 빈틈이 흩어져 남는 외부 단편화가 발생한다. 이를 해결하려고 파일을 여러 조각으로 나눠 장부로 연결하는 연결 할당·색인 할당이 등장했다.

### 세 가지 할당 기법 비교 — 수치로 이해
- **연속 할당**: 10블록짜리 파일을 5~14번 블록에 이어 담으면 읽기는 헤드 이동 없이 한 번에 끝난다. 하지만 6번 블록의 파일이 지워지면 그 자리에는 1블록짜리 빈틈만 남고, 다음에 8블록짜리 파일이 들어올 자리가 없어 못 쓰는 공간이 쌓인다.
- **연결 할당(FAT)**: 10블록을 디스크 전체에 흩어 담고 "5→77→3→...→끝"처럼 다음 블록 번호를 장부(FAT 테이블)에 적는다. 빈 공간은 낭비 없이 다 쓰지만, 파일의 8번째 블록만 읽으려 해도 1번부터 순서대로 7번을 거쳐야 하므로(순차 접근만 가능) 임의 접근이 느리다.
- **색인 할당(Inode)**: 파일 전용 색인 블록 하나에 "1번째 블록=5, 2번째=77, ..." 식으로 모든 위치를 미리 모아 둔다. 8번째 블록이 필요하면 색인 블록만 보고 바로 찾아가므로(임의 접근 가능) 오늘날 표준이 됐다.

### Inode 구조를 수치로 이해하기
- ext 계열 Inode는 데이터 블록 포인터를 직접(Direct) 12개까지 담는다. 블록 크기가 4KB라면 직접 포인터만으로 12 × 4KB = 48KB까지는 색인 블록을 한 번도 거치지 않고 바로 찾는다.
- 48KB를 넘으면 단일 간접 포인터(Single Indirect)를 쓴다. 이 포인터는 4KB 블록 하나를 가리키는데, 그 블록 안에 4바이트짜리 포인터를 4KB/4B = 1,024개 담을 수 있어 추가로 1,024 × 4KB = 4MB까지 커버한다.
- 그 이상은 이중 간접(포인터의 포인터, 1,024 × 4MB ≈ 4GB), 삼중 간접(1,024 × 4GB ≈ 4TB) 순으로 커버 범위가 기하급수로 늘어, 작은 파일은 빠르게 찾고 큰 파일도 수 TB까지 색인 하나로 다룰 수 있다.

### FAT·NTFS·ext4·APFS 판별 원리
- FAT32: 구조가 단순해 OS를 가리지 않고 호환되지만(USB에 쓰는 이유), 파일 하나 최대 4GB 제한과 접근 권한 관리 부재라는 한계가 뚜렷하다.
- NTFS: MFT(Master File Table)로 메타데이터를 트리 구조로 통합 관리하며 권한 제어·압축·저널링을 지원한다. 윈도우 표준이지만 Mac·Linux에서는 기본적으로 쓰기가 막혀 있다.
- ext4: Inode + Extent(연속 블록 구간을 통째로 가리키는 확장 포인터) 구조로 대용량 파일을 효율적으로 다뤄 리눅스 서버 표준으로 자리잡았다.
- APFS: 저널링 대신 CoW(Copy-on-Write, 원본을 덮어쓰지 않고 새 블록에 쓴 뒤 포인터만 교체)를 채택해, 플래시 메모리(SSD)의 쓰기 마모와 순간 스냅샷 요구에 최적화됐다.

### 비유와 흔한 오해
- 비유: 파일 시스템이 없는 디스크는 차를 아무 데나 대고 위치를 기억 못 하는 주차장과 같다. 파일 시스템은 차 번호(파일명)·차주(권한)·구역(블록 번호)을 장부에 적어, 나갈 때는 차를 부수는 게 아니라 장부에서 줄만 긋는(빠른 삭제) 관리자다.
- 오해 1: Inode에는 파일 이름이 없다. 이름은 디렉터리 파일 안의 "이름-Inode 번호" 목록에 별도로 저장된다.
- 오해 2: 포맷(Format)은 데이터를 지우는 것이 아니라 장부(파일 시스템)를 새로 만드는 것이다. 빠른 포맷 직후에도 실제 데이터는 물리 디스크에 남아 있어 포렌식 복구가 가능하다.

## 연결 개념
- 저널링(023) — FAT/NTFS/ext4가 장부 손상을 막기 위해 얹는 복구 기법
- VFS — 서로 다른 파일 시스템을 하나의 API로 통일하는 커널 추상화 계층
- exFAT — Windows·Mac 양쪽에서 읽고 쓸 수 있고 4GB 제한도 없는 이동식 매체용 절충 포맷

# 📝 【답안용】 시험 답안 템플릿

> 목적: 시험장에서 25분에 그대로 쓰는 답안 양식. 작성방식(추상표현 금지·수치·도식·문제유형 전환)을 엄격히 지킨다.
> 핵심: 이 시험은 정보를 많이 나열하는 시험이 아니라, 문제 신호어에서 출제자 의도를 읽고 핵심 논점을 선별해 쓰는 시험이다.

## 핵심 인사이트 (3줄 요약)

> 1. **본질**: 하드디스크의 물리적 블록 집합에 파일과 디렉토리라는 논리적 추상화를 덧씌우고, 메타데이터(Metadata)와 할당 테이블을 통해 데이터의 생명주기를 통제하는 커널 모듈이다.
> 2. **가치**: 단편화(Fragmentation) 억제를 통한 I/O 성능 방어 및, 정전이나 커널 패닉 시에도 파일의 무결성을 사수하는 저널링(Journaling) 등 고가용성을 보장한다.
> 3. **판단 포인트**: 연속-연결-색인 할당의 아키텍처 진화 과정과, OS 종속적인 상용 파일 시스템(FAT, NTFS, ext4, APFS)의 트레이드오프를 디바이스 물리적 특성(HDD vs SSD)과 연결해야 한다.

## 출제 의도 및 답안 포인트

| 출제 의도 | 반드시 짚을 핵심 | 감점 회피 포인트 |
|:---|:---|:---|
| 파일 시스템의 공간 할당(Allocation) 메커니즘 대조 | 연속(빠름/단편화) vs 연결(FAT) vs 색인(Inode) | Inode가 단순히 파일명만 담고 있다고 착각하는 서술 (Inode에는 파일명이 없음!) |
| 차세대 파일 시스템(APFS/ZFS)의 철학 차이 이해 | 기존 HDD 바늘 최적화(ext4) vs SSD 플래시 메모리 마모 평준화 및 CoW(APFS) | 윈도우/리눅스 비교에 매몰되어 SSD 전용 파일 시스템 트렌드를 누락하는 오류 |

> 요약: 파일 시스템의 역사는, 낭비되는 빈 공간(단편화)과의 전쟁에서 시작해 찰나의 정전(저널링)을 이겨내고, 결국 SSD 플래시 수명 연장(APFS)으로 귀결된 궤적이다.

## Ⅰ. 개요 및 필요성

- 정의: 디스크나 플래시 메모리 같은 블록 스토리지 위에 파일, 디렉토리 구조 및 접근 제어(ACL) 메타데이터를 매핑하여 운영체제가 데이터를 체계적으로 CRUD 할 수 있게 하는 커널 서브시스템
- 배경: 단순 연속 할당 시 파일 크기 변경에 따른 외부 단편화가 극심해지고, 디스크 용량이 PB(페타바이트)급으로 폭증하며 검색(Seek) I/O 딜레이가 시스템 전체 성능 병목 유발
- 필요성: 불연속적인 디스크 섹터들을 투명하게 하나로 묶어주는 색인 할당 구조를 구현하고, 다중 사용자 환경에서의 권한(rwx) 격리 및 무결성을 사수하기 위함

## Ⅱ. 파일 할당 및 메타데이터 아키텍처 (FAT vs Inode)

```text
[ FAT (연결 할당 기법) ] -> 윈도우 USB 종특
파일 A 시작 -> [ FAT 테이블 ] : "1번 블록 다음은 5번, 5번 다음은 끝(EOF)"
* 장점: 테이블 하나에 다 모여 있음. 단점: 파일 일부만 읽으려 해도 꼬리를 계속 물고 찾아가야 함 (임의 접근 불가).

[ ext4 Inode (색인 할당 기법) ] -> 리눅스 서버 종특
[ Inode 번호: 1023 ] -> 메타데이터(크기, 권한, 소유자) + [ 직접 블록 포인터 12개 ]
                                                   + [ 단일/이중 간접 포인터 ] -> (수 TB 확장)
* 장점: Inode 방 하나에 인덱스가 쫙 깔려 있어 특정 바이트(예: 파일 10GB 지점)로 다이렉트 접근 가능.
```

| 할당 기법 | 아키텍처 및 메타데이터 구조 | 치명적 한계점 및 디스크 성능 병목 |
|:---|:---|:---|
| **연결 할당** (Linked) | 데이터 블록끼리 링크드 리스트로 꼬리를 욺. (MS FAT 계열) | 파일 중간 위치를 읽으려면 1번 블록부터 전부 뒤져야 함. 헤더 이동 폭주 |
| **색인 할당** (Indexed) | 파일마다 목차 블록(Index Block, Inode) 유지. (Linux ext 계열) | 파일 크기가 작아도 반드시 목차 블록 1개를 낭비해야 하는 공간 오버헤드 |

> ⚠️ 주의: 리눅스 ext 파일 시스템의 심장인 `Inode`에는 파일의 소유자, 크기, 권한, 생성일은 다 있지만 정작 **'파일 이름'**은 없다! 파일 이름은 디렉토리 파일 내부의 리스트에 `[파일명 - Inode 번호]` 쌍으로 적혀 있다.

## Ⅲ. 현대 운영체제별 상용 파일 시스템 비교 (NTFS, ext4, APFS)

| 구분 | NTFS (Windows 표준) | ext4 (Linux 표준) | APFS (macOS/iOS 표준) |
|:---|:---|:---|:---|
| **핵심 철학** | 완벽한 권한 제어와 복구(저널링) | 서버 스토리지 대용량 처리 안정성 | **플래시 메모리(SSD) 맞춤형 최적화** |
| **데이터 구조** | MFT (Master File Table) 트리에 메타 보관 | Extents 기법 도입으로 대형 연속 블록 포인터 압축 할당 | 64비트 Inode 체계, Space Sharing (파티션 간 남는 공간 공유) |
| **저널링(복구)** | 메타데이터 저널링 기본 지원 | 데이터+메타데이터 전체 저널링 지원 | **저널링 제거**, 대신 CoW(Copy-on-Write)로 원본 훼손 100% 방지 |
| **치명적 약점** | Mac이나 Linux에서 쓰기(Write) 기본 미지원 | 윈도우 OS에서 마운트 원천 불가 | 애플 생태계 외에는 호환성 제로(0) |

> 요약: MS(NTFS)는 기업용 보안을, Linux(ext4)는 서버의 거대함을 쫓았다. 반면 Apple(APFS)은 모바일 시대의 SSD 수명을 연장하기 위해 아예 파일 시스템의 철학 자체를 뜯어고쳤다.

## Ⅳ. 시스템 리스크와 현대적 튜닝 극복 방안 (VFS와 CoW)

서로 다른 파일 시스템이 난무하면 OS는 어떻게 이를 통합하고 하드웨어 병목을 극복할까.

| 리스크 요인 | 아키텍처 원리 및 발생 시나리오 | 커널 및 하드웨어 튜닝 극복 방안 |
|:---|:---|:---|
| **이질적 FS 통합 병목** | HDD는 ext4, USB는 FAT32, 네트워크는 NFS를 쓸 때, 애플리케이션 개발자가 이 3가지 장부 조작법을 다 다르게 짜야 하는 비극 | **VFS (가상 파일 시스템)**: 리눅스 커널이 공통 객체 모델(Vnode)을 통해 모든 FS를 추상화. 개발자는 무지성으로 `open()`, `read()` API 1개만 호출하면 됨 |
| **저널링 디스크 마모 폭발** | SSD 환경에서 저널링(ext4)을 켜면, 임시 수첩에 1번, 진짜 장부에 1번 써서 쓰기 오버헤드 2배 폭발로 플래시 수명 단축 (Write Amplification) | **CoW (Copy-on-Write) 적용**: APFS나 ZFS처럼 수정 시 원본을 덮어쓰지 않고 무조건 새 빈 공간(블록)에 기록 후 마지막에 포인터만 스왑하여 복구와 수명 동시 확보 |

> 요약: VFS는 운영체제가 부리는 위대한 통역 마법이다. 덕분에 우리는 USB 포맷이 FAT인지 NTFS인지 신경 쓰지 않고 그냥 파일을 더블클릭할 수 있다.

## Ⅴ. 실무 적용 방안 및 결론

**적용 방안 3개:**
1. [Linux 대용량 로그 스토리지 튜닝] Elasticsearch 데이터 노드(ext4) 마운트 시, 파일 접근 시간(Access Time) 갱신으로 인한 불필요한 메타데이터 I/O 폭주를 막기 위해 `/etc/fstab`에 `noatime` 마운트 옵션을 강제 적용하여 디스크 성능 20% 이상 부스팅
2. [이기종 클라이언트 공유 볼륨 포맷] Mac 디자이너와 Windows 기획자가 수백 GB의 영상을 오가는 외장 SSD 포맷 시, 양쪽 OS에서 별도 서드파티 드라이버 없이 네이티브 R/W가 가능하며 파일 크기 4GB 제한이 없는 **exFAT**로 파티셔닝 표준화
3. [SSD 최적화 파일 시스템 (F2FS) 적용] 안드로이드 스마트폰 또는 임베디드 리눅스 시스템 개발 시, 잦은 랜덤 I/O로 인한 SSD 수명 단축 방지를 위해 삼성전자가 주도한 낸드 플래시 전용 펌웨어 친화적 로그 구조 파일 시스템(F2FS)을 루팅 커널에 탑재

**결론:**
- 기술사 판단: 파일 시스템은 "디스크라는 황무지에 폴더라는 건축물을 세우는 OS의 토목공사"다. FAT의 간결함에서 ext4의 웅장함을 거쳐, 이제는 하드웨어 자체의 물리적 특성(SSD)을 소프트웨어가 뼛속까지 이해해야만 살아남는 APFS 융합의 시대로 도래했다.
- 향후 방향: 로컬 디스크 파일 시스템의 기술적 진보는 임계점에 달했다. 앞으로의 화두는 S3 같은 오브젝트 스토리지와의 투명한 통합 커널 마운트(FUSE 기반) 및, 수백 대의 노드에서 수 페타바이트를 병렬로 쪼개어 읽어내는 하둡(HDFS), 러스터(Lustre) 류의 거대 분산 파일 시스템(DFS) 최적화로 넘어갔다.
