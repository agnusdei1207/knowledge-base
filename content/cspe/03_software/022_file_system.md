## Ⅰ. 개요
- 정의: 저장장치에 데이터를 효율적으로 저장, 관리, 검색하기 위한 논리적 구조
- 배경: 파일 단위 관리와 권한 제어, 데이터 정합성 보장을 위해 각 환경에 특화된 포맷 필요
- 출제 의도: 주요 파일 시스템의 메타데이터 관리 방식 및 성능/보안 기능 비교

## Ⅱ. 구성요소
```
[ FAT: Table Based ]      [ NTFS: B-Tree ]      [ EXT4: Extents ]
+-------+-------+         +--------------+      +---------------+
| Index | Next  |         | MFT Record   |      | Inode Table   |
+-------+-------+         +--------------+      +---------------+
| 001   | 003   |         | Data/Attr    |      | Data Blocks   |
+-------+-------+         +--------------+      +---------------+
```
| 구성요소 | 설명 | 비유 |
| :--- | :--- | :--- |
| FAT | 파일 할당 테이블을 링크드 리스트 형태로 관리 | 인덱스 카드 |
| MFT | 모든 파일 정보를 레코드 형태로 저장하는 NTFS 핵심 | 종합 장부 |
| Inode | 리눅스 파일의 메타데이터와 블록 주소를 저장하는 구조체 | 파일 꼬리표 |
> 요약: FAT는 단순함, NTFS는 대용량/보안, EXT4는 신뢰성과 성능에 집중함.

## Ⅲ. 절차
```
[Path Look-up] -> [Inode/MFT Access] -> [Block Address Find] -> [Data Read]
```
1. 사용자 요청 경로를 해석하여 디렉터리 항목(Dentry)을 탐색함
2. 해당 파일의 메타데이터 블록(Inode 또는 MFT 레코드)을 메모리에 로드
3. 실제 데이터가 저장된 물리적 블록 주소 리스트(Extents 등)를 확인
4. 디스크 I/O를 통해 해당 블록의 데이터를 읽어 사용자 버퍼에 전달
> 요약: 경로 해석을 통해 메타데이터를 찾고, 이를 통해 실제 데이터 위치를 파악함.

## Ⅳ. 문제점
- 원인: FAT32는 4GB 이상의 단일 파일을 지원하지 못하는 용량 한계 존재
- 원인: 비정상 종료 시 메타데이터와 실제 데이터 간의 불일치로 인한 손상 위험

## Ⅴ. 개선방안
- (단기) 저널링(Journaling) 기법을 활용하여 시스템 크래시 후 빠른 복구 보장
- (중기) B-Tree 및 Hashing 기반 디렉터리 검색으로 대규모 파일 처리 성능 강화
- (장기) Copy-on-Write(CoW) 방식의 Btrfs, ZFS 도입으로 데이터 정합성 및 스냅샷 지원

## Ⅵ. 전망
- SSD 및 비휘발성 메모리(NVM) 특성에 최적화된 F2FS 등 로그 구조 파일 시스템 확산
- 분산 파일 시스템(HDFS 등) 및 클라우드 객체 스토리지와의 통합 관리 계층 고도화
