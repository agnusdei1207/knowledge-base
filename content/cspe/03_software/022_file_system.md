## Ⅰ. 개요
- **정의**: 저장 장치 위에 데이터를 계층적으로 조직·저장·검색하는 소프트웨어 구조임
- **배경/필요성**: 블록 단위 원시 디스크를 사용자에게 논리적 파일·디렉터리로 추상화할 필요가 있음
- **비유**: 도서관의 분류 체계처럼 책(데이터 블록)을 서가(디렉터리)에 배치하고 색인(메타데이터)으로 찾는 구조임

| 출제 의도 | 반드시 짚을 핵심 | 감점 회피 포인트 |
|:---|:---|:---|
| 파일 시스템 내부 구조와 할당 방식 비교 | inode·블록 할당·디렉터리 구조 | FAT vs inode 기반 차이를 혼동하지 않을 것 |

> 요약: 디스크 블록을 논리적 파일 단위로 관리하는 계층적 구조임

## Ⅱ. 구성요소
```text
User Application
  |
  v
VFS (Virtual File System)
  |
  +-- File System Driver (ext4/XFS/NTFS)
  |     +-- Superblock
  |     +-- inode Table
  |     +-- Data Block
  |
  +-- Block I/O Layer -> Disk
```

| 구성요소 | 설명 | 비유 |
|:---|:---|:---|
| Superblock | 파일 시스템 전체 메타정보(블록 크기·총 블록 수) 저장 | 도서관 안내판 |
| inode | 파일별 메타데이터(크기·권한·블록 포인터) 보관 구조체 | 도서 카드 |
| Data Block | 실제 파일 내용이 저장되는 고정 크기 디스크 영역 | 서가의 책 |
| VFS | 다양한 파일 시스템을 단일 인터페이스로 추상화하는 커널 계층 | 통합 검색 시스템 |

> 요약: Superblock-inode-Data Block 3계층과 VFS 추상화로 구성됨

## Ⅲ. 절차
```text
open() -> inode 탐색 -> 블록 매핑 -> read()/write()
```
- 1단계: 애플리케이션이 `open()` 시스템 콜로 파일 경로를 전달함
- 2단계: 디렉터리 엔트리를 순회하여 해당 파일의 inode 번호를 탐색함
- 3단계: inode의 블록 포인터(직접·간접)를 통해 데이터 블록 위치를 매핑함
- 4단계: `read()`/`write()`로 블록 I/O를 수행하고 버퍼 캐시를 갱신함

> 요약: 경로 해석 후 inode 기반 블록 매핑으로 데이터 I/O를 수행함

## Ⅳ. 문제점
- 외부 단편화: 반복 삭제·생성으로 연속 블록 확보가 어려워 순차 읽기 성능이 저하됨
- 메타데이터 불일치: 쓰기 중 비정상 종료 시 inode와 데이터 블록 간 정합성이 깨짐
- 대용량 디렉터리 탐색 지연: 선형 디렉터리 구조에서 엔트리 수 증가 시 탐색 시간이 O(n)으로 증가함

> 요약: 단편화·정합성·탐색 성능이 주요 문제임

## Ⅴ. 개선방안
1. 단기: 익스텐트(Extent) 기반 할당으로 연속 블록 배치를 유도하여 단편화 완화
2. 중기: 저널링·CoW(Copy-on-Write) 기법으로 메타데이터 정합성 보장 (023 참조)
3. 장기: B-tree/HTree 디렉터리 인덱싱으로 탐색 복잡도를 O(log n)으로 단축

> 요약: 익스텐트·저널링·트리 인덱싱으로 각 문제를 해결함

## Ⅵ. 전망
- 발전 방향: 플래시 최적화 파일 시스템(F2FS)과 분산 파일 시스템(CephFS)이 확대됨
- 기술사적 판단: NVMe·SCM 등 저지연 매체에 맞는 경량 파일 시스템 설계가 중요함
- 기술사 제언: 워크로드 특성(순차/랜덤, 대용량/소용량)에 따라 파일 시스템을 선택할 필요가 있음
