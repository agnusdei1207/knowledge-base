# 📖 【암기용】 개념 완전 이해

## 한눈에
- **개요**: 운영체제가 보조기억장치에 데이터를 저장하고, 검색 및 관리하기 위한 논리적 구조와 알고리즘이다.
- **왜 필요한가**: 수많은 비트(Bit) 덩어리인 디스크 공간을 '파일'과 '디렉터리'라는 인간이 이해하기 쉬운 형태로 관리하고, 빠르게 접근하기 위해 필요하다.
- **핵심 직관**: 파일 시스템은 디스크라는 거대한 도서관의 책(파일) 위치를 빠르고 정확하게 찾아주는 '도서 목록 시스템(인덱스)'이다.

## 핵심 용어 정리

| 용어/표기 | 의미 | 비유·예 |
|:---|:---|:---|
| 클러스터(Cluster) | 파일 시스템이 디스크에 데이터를 할당하는 최소 논리 단위 (통상 4KB) | 물건을 담는 최소 크기의 상자 |
| 저널링(Journaling) | 메타데이터 변경 사항을 디스크에 반영하기 전 로그에 먼저 기록하는 기술 | 영수증(로그)을 먼저 쓰고 장부에 기입하는 회계 방식 |
| 메타데이터(Metadata) | 파일 이름, 크기, 권한, 생성일자, 디스크 상의 실제 위치 등의 관리 정보 | 책의 저자, 출판일, 청구기호가 적힌 도서 카드 |

## 깊이 이해
- **배경·문제의식**: 디스크는 단순히 섹터들의 연속일 뿐이다. OS가 특정 파일에 접근하려면 해당 파일이 어느 섹터에 분산되어 있는지 추적해야 한다. 파일 삭제와 생성이 반복되면 단편화(Fragmentation)가 발생하여 접근 속도가 저하되는 문제도 있다.
- **작동 원리**: 파일 생성 시, 파일 시스템은 사용 가능한 빈 클러스터를 찾아 데이터를 기록하고, 그 클러스터 주소 목록을 메타데이터(FAT 테이블, Inode 등)에 업데이트한다. 읽을 때는 메타데이터를 먼저 조회하여 디스크 내 실제 위치로 헤드를 이동시킨다.
- **주요 파일 시스템의 진화**:
  - **FAT (File Allocation Table)**: 단순 링크드 리스트 구조. 호환성이 좋아 USB 등에 쓰이나, 최대 파일 크기 제한(FAT32: 4GB)과 보안 기능 부재.
  - **NTFS (New Technology File System)**: Windows 표준. 저널링, 파일 암호화(EFS), 권한 관리(ACL) 지원. B-Tree 구조로 빠른 검색.
  - **ext4**: Linux 표준. 지연 할당(Delayed Allocation)으로 단편화 방지 및 엑스텐트(Extent) 기반 대용량 파일 관리.
  - **APFS (Apple File System)**: SSD에 최적화된 구조. Copy-on-Write 지원으로 스냅샷 생성이 순간적임.
- **흔한 오해·주의점**: 포맷(빠른 포맷)을 하면 데이터가 다 지워지는 줄 알지만, 실제로는 메타데이터 영역(목차)만 초기화될 뿐, 데이터 영역은 남아 있어 복구가 가능하다.

## 연결 개념
- 파일 시스템 저널링, 디스크 스케줄링, SSD FTL(Flash Translation Layer)

# 📝 【답안용】 시험 답안 템플릿

## 핵심 인사이트 (3줄 요약)

> 1. **본질**: 보조기억장치의 물리적 섹터를 논리적 클러스터/블록으로 추상화하고 메타데이터로 매핑하는 OS의 핵심 서브시스템.
> 2. **가치**: 대용량 저장매체의 효율적 공간 관리, 데이터 무결성(저널링) 보장, 파일 단위의 접근 제어(보안) 제공.
> 3. **판단 포인트**: OS 환경(Windows/Linux)과 저장 매체 특성(HDD/SSD)에 따라 최적화된 자료구조(B-Tree, Extent, CoW)를 가진 파일 시스템을 선택한다.

## 출제 의도 및 답안 포인트

| 출제 의도 | 반드시 짚을 핵심 | 감점 회피 포인트 |
|:---|:---|:---|
| 운영체제별 최신 파일 시스템의 구조적 특징과 진화 방향 이해 | FAT/NTFS/ext4 대조, 저널링, SSD 최적화 기법(CoW) | 단순 기능 나열 지양, 기술적 자료구조 매핑 |

> 요약: 파일 할당 관리 방식의 한계 극복 과정(FAT 테이블 → Inode → Extent)과 무결성 확보 기법을 중심으로 대조한다.

---

## Ⅰ. 개요 및 필요성

- 개요: 디스크의 물리적 저장 공간을 파일과 디렉터리라는 논리적 구조로 조직화하고 관리하는 운영체제 구성요소.
- 배경: 저장매체의 대용량화와 SSD의 보급으로, 기존 단순 리스트 기반 파일 시스템의 검색 성능 저하 및 수명 단축 문제 발생.
- 필요성: 시스템 크래시 시 데이터 복구(저널링), 대용량 파일의 연속 할당(Extent), 플래시 메모리 수명 연장(Trim 최적화)을 위해 고도화된 파일 시스템이 필요함.

---

## Ⅱ. 구조 및 구성요소

```text
사용자/애플리케이션 -> [VFS (Virtual File System)] -> [논리적 파일 시스템] -> [디바이스 드라이버] -> 물리 디스크
                                                      |
                                                      +-> 메타데이터 관리 + 데이터 블록 할당
```

| 구성요소 | 역할 | 특이사항 |
|:---|:---|:---|
| VFS (가상 파일 시스템) | 다양한 파일 시스템(ext4, NTFS 등)에 동일한 시스템 콜 인터페이스(POSIX) 제공 | 다형성(Polymorphism) 구현 |
| 메타데이터 영역 | 파일 속성(크기, 권한, MAC Time) 및 데이터 블록의 물리적 포인터 저장 | Inode(Linux), MFT(Windows) |
| 데이터 블록 영역 | 파일의 실제 데이터가 연속적 또는 분산되어 기록되는 물리적 공간 | 클러스터/블록 단위 (4KB) |

> 요약: VFS 계층을 통해 이기종 파일 시스템을 통합 지원하며, 실제 디스크는 메타데이터와 데이터 영역으로 엄격히 분리 관리된다.

---

## Ⅲ. 동작원리 및 흐름도 (파일 쓰기 과정)

```text
애플리케이션 쓰기 요청 -> VFS 시스템 콜 -> 가용 블록 탐색/할당 -> [저널 로그 기록] -> 실제 데이터 쓰기 -> 메타데이터 갱신
```

- 1단계 [시스템 콜 호출]: 애플리케이션이 `write()` 시스템 콜을 통해 논리적 파일 쓰기 요청.
- 2단계 [가용 공간 할당]: 파일 시스템이 Bitmap 등 공간 관리 구조를 참조해 빈 데이터 블록(클러스터) 할당.
- 3단계 [저널링 및 쓰기]: 정전 대비를 위해 변경 예정 메타데이터를 저널 영역에 선기록 후, 실제 데이터 블록에 기록.
- 4단계 [메타데이터 갱신]: 파일 크기 및 수정 시간, 할당된 포인터 정보를 Inode 또는 MFT에 최종 업데이트하고 저널 삭제.

> 요약: 시스템 콜을 통해 가용 공간을 할당받은 뒤, 데이터 무결성을 위해 저널링을 거쳐 메타데이터와 실제 데이터를 동기화한다.

---

## Ⅳ. 특징

- 자료구조 고도화 (NTFS/ext4): B-Tree, H-Tree 알고리즘을 적용하여 수백만 개의 파일 디렉터리 내 검색 속도를 O(log N) 수준으로 단축함.
- 연속 할당 최적화 (ext4 Extent): 대용량 파일 저장 시 블록 주소를 일일이 기록하지 않고 [시작 블록 + 길이] 형태로 기록해 메타데이터 크기를 축소함.
- 지연 할당 (Delayed Allocation): 쓰기 요청 시 즉시 디스크에 기록하지 않고 메모리에 모아두어, 최적의 연속된 블록을 한 번에 할당함으로써 단편화를 방지함.
- 스냅샷 및 CoW (APFS/ZFS): 데이터 수정 시 원본을 덮어쓰지 않고 새로운 블록에 기록(Copy-on-Write)하여, 디스크 공간 추가 소모 없이 즉각적인 스냅샷 생성을 지원함.

> 요약: 파일 시스템은 검색을 위한 트리 자료구조 적용과, 단편화 방지 및 무결성을 위한 지연 할당·CoW 메커니즘으로 진화하였다.

## Ⅴ. 심화 비교 및 적용 판단

| 비교 축 | FAT32 | NTFS (Windows) | ext4 (Linux) | APFS (macOS/iOS) |
|:---|:---|:---|:---|:---|
| 자료구조/할당 | 연결 리스트 (FAT) | B-Tree / MFT | H-Tree / Extent | B-Tree / CoW |
| 무결성 보장 | 없음 (손상 시 Chkdsk) | 저널링 기반 복구 | 저널링 기반 복구 | 충돌 방지 아키텍처 |
| 타겟 워크로드 | USB, 이동식 미디어 | 윈도우 기업/개인 환경 | 리눅스 서버/클라우드 | SSD 기반 모바일/데스크톱 |

> 요약: 보편적 호환성은 FAT32, 엔터프라이즈 환경은 NTFS/ext4, 플래시 최적화는 APFS를 채택한다.

**도입 후 점검 지표:**
- 성능/효율: 디스크 단편화 율 (목표 10% 미만) — 디스크 조각 모음 유틸리티 측정
- 품질/운영: 파일 시스템 크래시 복구 소요 시간 (목표 1분 이내) — 강제 리부팅 후 FSCK 소요 시간 측정

## Ⅵ. 실무 적용 및 결론

**적용 방안 3개:**
1. 엔터프라이즈 서버 볼륨 구성 (Linux): 데이터베이스 서버 등 고성능 I/O가 필요한 경우 ext4 또는 XFS를 적용하고, LVM(Logical Volume Manager)과 결합해 유연한 용량 확장을 구현.
2. 클라우드 스토리지 최적화: 대규모 클러스터 환경에서는 로컬 파일 시스템(ext4) 위에 Ceph, GlusterFS 같은 분산 파일 시스템을 얹어 수평 확장을 확보.
3. 플래시 메모리 기기 최적화: 모바일 및 IoT 기기는 쓰기 증폭(Write Amplification)을 최소화하기 위해 F2FS(Flash-Friendly File System)와 같은 SSD 전용 파일 시스템을 적용.

**결론 (2줄):**
- 기술사 판단: 파일 시스템 선택은 운영체제 호환성을 넘어 저장 매체(HDD vs SSD)의 물리적 특성 및 데이터 무결성 요건을 최우선으로 고려해야 함.
- 향후 방향: 로컬 파일 시스템의 경계를 넘어, 컨테이너 및 클라우드 네이티브 환경에 맞는 CSI(Container Storage Interface) 기반 동적 볼륨 프로비저닝과 결합하는 형태로 진화할 것임.
