# 📖 【암기용】 개념 완전 이해

## 한눈에
- **개요**: 파일 시스템(File System)은 운영체제가 보조기억장치(HDD·SSD)에 데이터를 **파일·디렉터리 단위로 저장·검색·관리**하기 위한 논리적 구조와 알고리즘임.
- **왜 필요한가**: 디스크는 물리적으로 섹터의 연속일 뿐이므로, 파일의 위치·크기·권한을 추적하는 메타데이터 관리 체계 없이는 데이터를 읽고 쓸 수 없음. 파일 삭제·생성이 반복되면 단편화(Fragmentation)가 발생해 접근 속도가 저하되므로 이를 방지하는 할당 전략도 필요함.
- **핵심 직관**: 파일 시스템은 디스크라는 거대한 도서관에서 책(파일)의 위치를 빠르고 정확하게 찾아주는 도서 목록 시스템(인덱스)임.

## 핵심 용어 정리 (내부에 등장하는 것들)

| 용어/표기 | 의미 | 비유·예 |
|:---|:---|:---|
| 파일 시스템 (상위 키워드) | 보조기억장치에 데이터를 논리적으로 조직화하는 OS 구성요소 | 도서관 목록 시스템 |
| 블록/클러스터 | 파일 시스템이 데이터를 할당하는 최소 논리 단위(통상 4KB) | 물건을 담는 최소 상자 |
| 메타데이터 | 파일 이름·크기·권한·물리 위치 등 관리 정보 | 도서 카드(저자·위치) |
| Inode | 리눅스 파일 시스템의 메타데이터 구조체(파일당 1개) | 도서 카드 1장 |
| MFT (Master File Table) | NTFS의 메타데이터 저장 구조(B-Tree 기반) | 카드 목록함 |
| Extent | [시작 블록 + 길이]로 연속 블록을 하나의 항목으로 기록하는 방식(ext4) | 주소를 1개만 적어도 연속 구간 전체 표현 |
| 저널링 (Journaling) | 메타데이터 변경을 디스크에 반영하기 전 로그에 먼저 기록해 정전 시 복구하는 기법(023 상세) | 영수증 먼저 쓰고 장부 기입 |
| Copy-on-Write (CoW) | 데이터 수정 시 원본을 덮어쓰지 않고 새 블록에 기록, 원본을 스냅샷으로 보존 | 원본 보존한 채 사본에 수정 |

## 깊이 이해
- **배경·문제의식**: 초기 파일 시스템(FAT)은 연결 리스트 기반 단순 구조로 소용량 디스크에 적합했으나, 디스크 대용량화와 파일 수 증가에 따라 검색 성능(O(N))이 한계에 부딪힘. 또한 정전 시 메타데이터 불일치로 데이터 손실이 빈번해 저널링 기법이 등장함. SSD 보급 이후에는 쓰기 증폭(Write Amplification)을 줄이는 CoW·Flash 친화적 설계가 필수가 됨.
- **작동 원리(파일 쓰기)**:
  - 앱이 `write()` 시스템 콜 호출 -> VFS가 파일 시스템 드라이버로 전달
  - 파일 시스템이 Bitmap·Free List로 빈 블록 탐색 -> 블록 할당
  - 저널링: 변경 예정 메타데이터를 저널 영역에 선기록(WAL)
  - 실제 데이터를 할당된 블록에 기록
  - Inode/MFT의 메타데이터(크기·수정시간·블록 포인터)를 갱신하고 저널 커밋
- **주요 파일 시스템 진화**:
  - **FAT32**: 연결 리스트(FAT 테이블) 기반, 최대 파일 4GB, 보안·저널링 없음 — USB·SD카드 호환용
  - **NTFS**: B-Tree 기반 MFT, 저널링, ACL 권한, EFS 암호화 — Windows 표준
  - **ext4**: H-Tree 디렉터리, Extent 기반 연속 할당, 지연 할당(Delayed Allocation)으로 단편화 방지 — Linux 서버 표준
  - **APFS**: CoW 기반, 스냅샷 즉시 생성, SSD 최적화(TRIM 네이티브) — macOS/iOS 표준
- **흔한 오해·주의점**: (1) 빠른 포맷은 메타데이터 영역(목차)만 초기화할 뿐 데이터 영역은 잔존해 복구 가능함. (2) ext4의 저널링은 메타데이터만 저널하는 것이 기본(data=ordered)이며, 전체 데이터 저널링(data=journal)은 성능 부담이 큼.

## 연결 개념
- (023 파일 시스템 저널링) 저널링의 상세 메커니즘(WAL, 체크포인트, 복구)
- (024 I/O 관리·디스크 스케줄링) 파일 시스템이 요청한 블록 I/O를 디스크 스케줄러가 최적화
- SSD FTL(Flash Translation Layer) — SSD 내부의 논리-물리 블록 매핑, 파일 시스템과 독립적으로 동작

# 📝 【답안용】 시험 답안 템플릿

## 핵심 인사이트 (3줄 요약)

> 1. **본질**: 보조기억장치의 물리 섹터를 논리 블록으로 추상화하고 메타데이터로 매핑하는 OS의 핵심 서브시스템임.
> 2. **가치**: 데이터 무결성(저널링), 대용량 파일 관리(Extent), 접근 제어(ACL)를 제공해 신뢰할 수 있는 저장 체계를 구현함.
> 3. **판단 포인트**: OS 환경·저장 매체 특성(HDD/SSD)에 따라 최적 자료구조(B-Tree·Extent·CoW)를 선택하고, 단편화·쓰기 증폭을 통제하는 것이 핵심임.

## 출제 의도 및 답안 포인트

| 출제 의도 | 반드시 짚을 핵심 | 감점 회피 포인트 |
|:---|:---|:---|
| OS별 파일 시스템의 구조적 특징과 진화 방향 이해 | FAT->NTFS->ext4->APFS 진화 축, 저널링·Extent·CoW 메커니즘 | 단순 기능 나열, 자료구조 매핑 누락 |
| 저장 매체별 최적화 기법 도출 | HDD 단편화 방지(Delayed Allocation), SSD 쓰기 증폭 최소화(CoW·TRIM) | 저장 매체 특성 무시한 일반론 |

> 요약: 파일 할당 구조의 진화(연결 리스트 -> B-Tree -> Extent)와 무결성 확보 기법(저널링·CoW)을 중심으로 비교해야 함.

---

## Ⅰ. 개요 및 필요성

- 개요: 보조기억장치의 물리 공간을 파일·디렉터리로 조직화하는 운영체제 구성요소임
- 배경: 디스크 대용량화·파일 수 증가로 단순 리스트 기반 검색 성능 한계, 정전 시 메타데이터 불일치 문제 발생
- 필요성: 검색 성능(O(log N)), 정전 복구(저널링), SSD 수명 관리(CoW·TRIM)를 위해 고도화된 파일 시스템이 필수임

---

## Ⅱ. 구조 및 구성요소

```text
사용자/애플리케이션 -> VFS(Virtual File System) -> 논리적 파일 시스템(ext4/NTFS/APFS)
                                                      |
                                                      +-> 메타데이터 관리(Inode/MFT)
                                                      +-> 데이터 블록 할당(Bitmap/Extent)
                                                      |
                                                  디바이스 드라이버 -> 물리 디스크(HDD/SSD)
```

| 구성요소 | 역할 | 비고 |
|:---|:---|:---|
| VFS (가상 파일 시스템) | 이기종 파일 시스템에 동일한 POSIX 시스템 콜 인터페이스 제공 | open/read/write/close 통합 |
| 메타데이터 영역 | 파일 속성·블록 위치 포인터·권한 정보 저장 | Inode(Linux), MFT(Windows) |
| 데이터 블록 영역 | 파일의 실제 데이터가 기록되는 물리 공간 | 4KB 블록/클러스터 단위 |
| 저널 영역 | 메타데이터 변경의 WAL(Write-Ahead Log) | 정전 시 복구 근거 |

> 요약: VFS로 이기종 파일 시스템을 통합 지원하며, 메타데이터·데이터·저널 영역으로 분리해 무결성과 성능을 동시에 확보함.

---

## Ⅲ. 동작원리 및 흐름도

```text
앱 write() 호출 -> VFS -> 파일 시스템 드라이버
  -> Bitmap으로 빈 블록 탐색/할당
    -> 저널 영역에 메타데이터 변경 선기록(WAL)
      -> 데이터 블록에 실제 기록
        -> Inode/MFT 메타데이터 갱신 -> 저널 커밋
```

1. 시스템 콜: 애플리케이션이 `write()` 시스템 콜로 파일 쓰기를 요청함
2. 블록 할당: Bitmap·Free List를 참조해 가용 블록을 탐색하고 할당함
3. 저널링: 변경 예정 메타데이터를 저널 영역에 선기록(정전 복구 대비)
4. 기록 완료: 실제 데이터 블록 기록 후 메타데이터를 갱신하고 저널을 커밋함

> 요약: 빈 블록 할당 후 저널링을 거쳐 데이터와 메타데이터를 동기화하는 과정으로 무결성을 보장함.

---

## Ⅳ. 특징

- 검색 고도화: NTFS(B-Tree), ext4(H-Tree)로 수백만 파일 디렉터리 내 검색을 O(log N)으로 단축함
- 연속 할당 최적화: ext4의 Extent([시작 블록+길이])로 대용량 파일의 메타데이터 크기를 축소하고 단편화를 억제함
- 지연 할당: 쓰기 요청을 메모리에 모았다가 연속 블록을 한 번에 할당해 단편화를 방지함(ext4 Delayed Allocation)
- CoW 기반 스냅샷: APFS·ZFS는 수정 시 새 블록에 기록하고 원본을 보존해 디스크 추가 소모 없이 즉각 스냅샷 생성 가능함

## Ⅴ. 심화 비교 및 적용 판단

| 구분 | FAT32 | NTFS | ext4 | APFS | 선택 기준 |
|:---|:---|:---|:---|:---|:---|
| 자료구조 | 연결 리스트(FAT) | B-Tree/MFT | H-Tree/Extent | B-Tree/CoW | 검색 성능 요구 |
| 무결성 | 없음 | 저널링 | 저널링 | CoW 충돌 방지 | 정전 복구 요구 |
| 최대 파일 크기 | 4GB | 16EB | 16TB | 8EB | 대용량 파일 지원 |
| 매체 최적화 | 범용 호환 | HDD 중심 | HDD/SSD 범용 | SSD 특화(TRIM) | HDD vs SSD |
| 적합 환경 | USB·SD카드 | Windows 서버 | Linux 서버·클라우드 | macOS·iOS | OS 환경 |

> 요약: 범용 호환은 FAT32, 엔터프라이즈 서버는 NTFS·ext4, SSD 모바일은 APFS가 최적이며, 저장 매체 특성이 선택의 핵심 축임.

**리스크·대응:**
- 단편화 누적: HDD에서 장기 운용 시 파일 분산으로 읽기 성능 저하 -> ext4 지연 할당 활용, 주기적 defrag 또는 XFS 채택 (지표: 단편화율 10% 미만)
- 저널링 성능 부담: 전체 데이터 저널링(data=journal)은 쓰기 처리량 50% 감소 -> data=ordered 기본 설정으로 메타데이터만 저널링 (지표: IOPS 대비 저널 오버헤드)

**도입 후 점검 지표:**
- 성능: 디스크 단편화율 — 목표 10% 미만, `e4defrag -c` 측정
- 운영: 파일 시스템 크래시 복구 시간 — 목표 fsck 1분 이내

---

## Ⅵ. 실무 적용 및 결론

**적용 방안 3개:**
1. Linux 서버 볼륨 구성: DB 서버에 ext4·XFS + LVM을 적용해 Extent 기반 연속 할당과 온라인 볼륨 확장을 동시에 확보함
2. 클라우드 분산 스토리지: 로컬 ext4 위에 Ceph·GlusterFS를 구성해 수평 확장 가능한 분산 파일 시스템을 구축함
3. SSD 수명 최적화: 모바일·IoT 기기에 F2FS(Flash-Friendly File System)를 적용해 쓰기 증폭을 최소화하고 TRIM을 네이티브 지원함

**결론:**
- 기술사 판단: 파일 시스템 선택은 OS 호환성을 넘어 저장 매체(HDD/SSD)의 물리 특성과 무결성 요건을 최우선으로 고려해야 하며, Extent·CoW·저널링의 트레이드오프를 워크로드에 맞춰 결정함
- 향후 방향: 로컬 파일 시스템의 경계를 넘어 CSI(Container Storage Interface) 기반 동적 볼륨 프로비저닝과 결합하고, CXL 메모리 계층의 새로운 저장 매체에 대응하는 형태로 진화 중임
