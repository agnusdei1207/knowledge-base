## Ⅰ. 개요
- 정의: 기존 애플리케이션의 핵심 로직은 유지하되 실행 환경을 클라우드 등에 맞게 변경함
- 배경: 레거시 시스템의 유지보수 한계 극복 및 클라우드 이점을 저비용으로 누리기 위해 필요
- 출제 의도: 리호스팅(Lift & Shift)과 리팩토링의 중간 단계로서의 전략적 가치 이해 평가

## Ⅱ. 구성요소
- ASCII 구조도
  [Legacy App] --(Modify Library/Config)--> [Cloud Native Platform]
         |                                           |
    (On-Premise)                                (Container/PaaS)
- 구성요소 표
| 구성요소 | 설명 | 비유 |
| :--- | :--- | :--- |
| 컨테이너화 | 애플리케이션을 도커 이미지로 패키징함 | 수출용 컨테이너 |
| 관리형 서비스 | DB 등을 클라우드 제공사 서비스(PaaS)로 교체 | 렌탈 가전 |
| 최소 변경 원칙 | 코드 수정을 최소화하여 전환 리스크를 낮춤 | 부품 호환 교체 |
> 요약: 구조적 큰 틀은 바꾸지 않고 인프라와 미들웨어를 최신 플랫폼으로 전환함

## Ⅲ. 절차
- ASCII 흐름도
  Assessment -> Platform Select -> Optimization -> Verification
- 4단계 설명
1. Assessment: 현대화 대상 시스템의 의존성 및 기술 부채 수준 분석함
2. Platform Select: 컨테이너(K8s)나 관리형 서비스(RDS) 등 대상 플랫폼 선정함
3. Optimization: 클라우드 환경에 맞게 설정 파일 및 라이브러리 일부 수정함
4. Verification: 기능 테스트 및 성능 벤치마킹을 통해 안정성 검증함
> 요약: 분석 후 대상 플랫폼을 선정하고 필요한 최소 수정을 거쳐 안정적으로 이전함

## Ⅳ. 문제점
- 원인이 명시된 문제/한계: 레거시의 강한 하드웨어 의존성으로 인해 플랫폼 호환성 문제 발생함

## Ⅴ. 개선방안
- Ⅳ의 문제에 대응하는 방안: 가상화 계층 도입 및 12-Factor App 원칙 점진적 적용함

## Ⅵ. 전망
- 발전 방향: AI 기반 레거시 코드 자동 분석 및 리플랫포밍 가능성 진단 도구 활성화
- CSF: 무리한 구조 변경보다는 플랫폼이 제공하는 자동 확장 및 가용성 혜택 확보가 우선임
