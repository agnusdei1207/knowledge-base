## 미리 알고가기

- 리액티브 프로그래밍은 데이터 흐름과 변화 전파를 중심에 두는 프로그래밍 모델임
- Publisher는 스트림을 발행하고 Subscriber는 수요 신호와 처리 결과를 반환함
- backpressure가 없으면 느린 소비자가 전체 시스템 병목이 됨

## 작성 근거(검토용)

- 동기 호출과 리액티브 스트림을 실행 단위·흐름 제어·오류 전파·스레드·제약·업무로 비교함
- 발행·연산·수요 신호·전달·완료를 Publisher와 Subscriber의 실제 메시지 흐름으로 유지함
- 알림 스트림과 순차 CRUD를 분리해 구독 지연·큐 깊이·오류 처리시간을 검증함

## Ⅰ. 개요

- **정의/개념**: 리액티브 프로그래밍은 데이터와 이벤트를 비동기 스트림으로 다루고 변화가 발생할 때마다 구독자에게 전파되도록 구성하는 프로그래밍 방식임
- **배경/필요성**: 이벤트 생산 속도가 소비 속도를 초과하면 큐와 메모리 사용량이 증가하므로 비동기 흐름과 backpressure를 명시할 모델이 필요함

## Ⅱ. 특징

- 데이터 흐름과 이벤트 전파를 선언적으로 표현할 수 있음
- 비동기 처리와 backpressure 설계를 함께 다룰 수 있음
- 연산 체인이 길어질수록 디버깅과 오류 추적이 어려워질 수 있음
- 순차 CRUD 업무에 적용하면 스트림 연산자·수요 제어·오류 전파 관리가 추가됨

## Ⅲ. 종류 및 비교

| 판단 기준 | 전통 동기 처리 | 리액티브 프로그래밍 |
|:---|:---|:---|
| 실행 모델 | 요청 단위 호출 | 스트림 단위 전파 |
| 흐름 제어 | 호출자가 순서와 반환값을 제어 | publisher·subscriber가 demand와 backpressure를 전달 |
| 한계 | 동시성 확장 제약 | 학습 비용과 추적 복잡도 큼 |
| 대표 업무 | 순차 요청·응답 업무 | 이벤트 스트림·비동기 I/O 서비스 |
| 오류 전달 | 호출 스택의 예외 | 스트림 오류 신호 |
| 실행 자원 | 호출 스레드 | 스케줄러·연산자별 실행 컨텍스트 |

> 요약: 동기 처리는 호출자가 순서를 제어하고, 리액티브 스트림은 구독자의 수요 신호로 발행량을 조절함.

## Ⅳ. 구성요소 및 구조

| 구성요소 | 설명 |
|:---|:---|
| Publisher | 데이터·완료·오류 신호를 스트림으로 발행함 |
| Subscriber | 처리 가능한 수량을 요청하고 데이터 신호를 소비함 |
| 연산자 체인 | map·filter·merge로 스트림을 변환·결합함 |
| 스케줄러 | 연산자를 실행할 스레드와 실행 컨텍스트를 정함 |

> 요약: Publisher가 신호를 발행하고 Subscriber가 수요를 전달하며 연산자·스케줄러가 처리 흐름을 구성함.

## Ⅴ. 원리 및 절차 흐름도

```text
+-------------+     +-------------+     +-------------+     +-------------+
| 이벤트 발행    | --> | 스트림 연산    | --> | 수요 조절      | --> | 구독 처리      |
+-------------+     +-------------+     +-------------+     +-------------+
```

1. **구독·수요 전달**: Subscriber가 Publisher에 처리 가능한 데이터 수를 요청함
2. **이벤트 발행**: Publisher가 수요 범위 안에서 데이터·오류·완료 신호를 보냄
3. **스트림 연산**: 연산자 체인이 변환·필터링·결합을 수행함
4. **구독 처리**: Subscriber가 결과를 처리하고 다음 수요를 전달함

## Ⅵ. 실무 사례

1. 실시간 알림 스트림은 수요 제어와 제한 큐를 적용하고 구독 지연과 큐 깊이를 확인함
2. API 조합 서비스는 스트림 오류 신호를 표준화하고 미처리 오류율과 오류 분석시간을 확인함

## Ⅶ. 결론

- 리액티브 프로그래밍은 이벤트 흐름과 소비 속도 차이를 수요 신호·backpressure·오류 전파로 통제함
