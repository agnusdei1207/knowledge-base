# 📖 【암기용】 개념 완전 이해

## 한눈에
- **개요**: 데이터의 흐름과 상태 변화를 '이벤트 스트림'으로 간주하고, 변화가 발생하면 비동기적으로 이를 전파하여 처리하는 선언적 프로그래밍 패러다임이다.
- **왜 필요한가**: 사용자는 폭증하고 데이터는 끊임없이 쏟아지는데, 기존 동기식 방식으로는 스레드가 대기(Blocking)하느라 응답성이 떨어졌다. 극도의 유연성과 확장성(응답성)을 유지하기 위해 필요하다.
- **핵심 직관**: 엑셀의 수식(A1+B1)과 같다. A1 셀의 값이 바뀌면 엑셀이 알아서(비동기적으로) 수식 셀의 값을 업데이트한다. 개발자가 매번 "값이 바뀌었니?" 묻지 않고 변화에 '반응(React)'만 하는 것이다.

## 핵심 용어 정리

| 용어/표기 | 의미 | 비유·예 |
|:---|:---|:---|
| 이벤트 스트림 (Event Stream) | 시간의 흐름에 따라 발생하는 데이터나 이벤트의 연속적인 흐름 | 수도관을 타고 끊임없이 흐르는 물 |
| 배압 (Backpressure) | 물이 너무 많이 쏟아질 때 넘치지 않도록 구독자(소비자)가 데이터 처리 속도를 제어하는 기술 | 하류 댐에서 상류 댐에 "물 좀 천천히 흘려보내"라고 신호 보내기 |
| 리액티브 선언문 (Reactive Manifesto) | 현대 애플리케이션이 갖춰야 할 4대 속성 (응답성, 탄력성, 유연성, 메시지 구동) | 최신 클라우드 건축 설계 십계명 |

## 깊이 이해
- **배경·문제의식**: 클라우드 시대, 넷플릭스나 트위터처럼 수천만 명의 동시 접속과 막대한 데이터 스트리밍을 처리해야 했다. 동기식 호출(Blocking)은 장애가 연쇄 전파되었고 스루풋에 한계가 뚜렷했다.
- **작동 원리 (옵저버 패턴의 진화)**:
  - 모든 데이터를 옵저버블(Observable)한 스트림으로 만든다. (DB 정적 쿼리 결과, 클릭 이벤트 등)
  - 개발자는 스트림을 필터링(`filter`), 변환(`map`)하는 체인을 선언한다.
  - 데이터가 발생(Push)하면 체인을 따라 데이터가 비동기/논블로킹으로 흐른다.
  - 처리 속도 차이가 나면, 소비자 측에서 배압(Backpressure)을 통해 생산자에게 요청량(n개만 줘)을 조절한다. (Pull 방식 결합)
- **비유**: 컨베이어 벨트. 물건(데이터)이 들어오면 각 공정(`map`, `filter`)을 거쳐 최종 포장(Subscriber)된다. 끝에서 처리 속도가 밀리면 벨트 속도를 늦춘다(배압).
- **구체 예시**: RxJava, Spring WebFlux, Project Reactor, Vue.js의 반응형 시스템.
- **흔한 오해·주의점**: 리액티브 코드는 흐름을 '선언'만 할 뿐 그 자리에서 실행되지 않는다. 반드시 누군가 `subscribe()`(구독)해야 비로소 데이터가 흐르기 시작한다. 콜백이 꼬리를 무는 비동기 로직이므로, 중간에 에러가 나면 스택 트레이스 추적이 끔찍하게 어렵다.

## 연결 개념
- 비동기 I/O(이벤트 루프), 옵저버 패턴, 마이크로서비스 아키텍처, 가상 스레드

# 📝 【답안용】 시험 답안 템플릿

## 핵심 인사이트 (3줄 요약)

> 1. **본질**: 데이터 스트림과 상태 변화의 비동기적 전파를 중심으로, 옵저버 패턴에 배압(Backpressure) 제어를 추가한 선언적 프로그래밍 패러다임.
> 2. **가치**: 논블로킹 I/O를 통한 시스템 처리량 극대화와 리액티브 선언문의 4대 원칙(응답성, 탄력성, 유연성, 메시지 구동) 달성.
> 3. **판단 포인트**: 스트리밍 처리 및 MSA 간 논블로킹 통신에 필수적이나, 가독성 저하와 디버깅의 어려움으로 인해 최근에는 코루틴 및 가상 스레드(Loom)와 비교/대체되는 추세다.

## Ⅰ. 개요 및 필요성

- 개요: 데이터의 흐름과 변화의 전파를 중심으로 설계되며, 데이터 생산자(Publisher)와 소비자(Subscriber) 간의 비동기 논블로킹 통신을 지향하는 프로그래밍 기법.
- 배경: 분산 시스템과 클라우드 환경에서 트래픽이 폭증함에 따라, 전통적 동기식 통신(Thread-per-request)에 의한 병목 현상 및 장애의 연쇄 전파(Cascading Failure) 발생.
- 필요성: 시스템 부하가 높거나 일부 장애가 발생해도 항상 일정 수준의 응답성(Responsiveness)을 유지하는 견고한 아키텍처를 위해 필수적임.

---

## Ⅱ. 구조 및 구성요소 (리액티브 선언문 4대 속성 결합)

```text
[비동기 메시지 구동 (Message Driven)] --------> [탄력성 (Elasticity): 부하 분산]
               |                                           |
               +-------------------------------------------+
               V                                           V
[유연성 (Resilience): 장애 격리] --------------> [응답성 (Responsiveness): 사용자 경험 (최종 목표)]
```

| 구성요소 (개념) | 역할 및 구현 기법 | 특이사항 |
|:---|:---|:---|
| 메시지 구동 | 비동기 메시지 패싱을 통해 컴포넌트 간 결합도를 낮춤 | 논블로킹 통신 메커니즘 제공 |
| 탄력성 | 작업 부하의 증감에 맞춰 시스템 자원을 자동으로 확장/축소함 | Auto-scaling 및 배압(Backpressure) 적용 |
| 유연성 (회복성) | 장애 발생 시 이를 격리하여 전체 시스템 붕괴를 막고 스스로 복구함 | 서킷 브레이커, 리트라이 패턴 결합 |
| 응답성 (목표) | 어떠한 상황(부하, 장애)에서도 신속하고 일관성 있게 응답함 | 리액티브 시스템의 최상위 지향점 |

> 요약: 메시지 구동이라는 기술적 뼈대 위에 장애 격리와 부하 조절을 더해, 어떠한 환경에서도 사용자 응답성을 유지하는 구조다.

## Ⅲ. 동작원리 및 흐름도 (스트림 처리 및 배압)

```text
Publisher (데이터 생성) -> 비동기 Push (이벤트) -> 데이터 변환 연산자(Map/Filter) -> Subscriber (구독 및 소비)
      ^                                                                                |
      +----------------------------- [Backpressure: n개 요청] -----------------------------+
```

- 1단계 [스트림 정의]: 컬렉션, 외부 API 호출, UI 이벤트 등을 Observable 객체(데이터 스트림)로 정의함 (선언 단계).
- 2단계 [구독 및 실행]: Subscriber가 `subscribe()`를 호출하여 스트림 연결을 활성화하고, 처리 가능한 데이터의 양(Request n)을 Publisher에 알림.
- 3단계 [비동기 Push]: Publisher는 요청받은 수량 내에서 데이터를 Non-Blocking 방식으로 전송하며, 중간 연산자들이 이를 순차적으로 변환/가공함.
- 4단계 [배압 제어 (Backpressure)]: Subscriber의 처리 속도가 느려질 경우 요청량을 줄이거나 일시 중단하여 OOM(Out of Memory) 방지 및 유량 통제.

> 요약: 데이터는 Push 방식으로 비동기적으로 흐르되, 시스템 부하 시 Subscriber가 Pull 방식으로 제동을 거는 하이브리드 제어(배압)를 수행한다.

---

## Ⅳ. 특징

- 처리량 극대화: 스레드가 I/O 대기를 하지 않는 Non-Blocking 기반이므로, 소수의 스레드 자원으로 대규모 동시 트래픽을 효율적으로 처리함.
- 연산의 조합과 선언적 설계: `map`, `filter`, `flatMap` 등 고차 함수를 체이닝(Chaining)하여 복잡한 비동기 분기 로직을 선언적으로 간결하게 조립.
- 높은 학습 곡선 (단점): 함수형 사고방식과 옵저버블 체인, 모나드(Monad) 개념에 대한 깊은 이해가 필요하여 개발팀의 생산성 저하 우려.
- 디버깅 복잡도 (단점): 스레드가 계속 전환되며 비동기로 실행되므로 콜 스택(Call Stack)이 끊어져 예외 발생 시 추적이 극도로 어려움.

> 요약: 압도적인 성능과 유연성을 제공하지만, 개발 난이도와 유지보수성 측면에서 가파른 진입 장벽(Trade-off)을 수반한다.

## Ⅴ. 심화 비교 및 적용 판단

| 비교 축 | 명령형 / 동기식 (Spring MVC) | 리액티브 (Spring WebFlux) | 코루틴 / 가상 스레드 (Loom) |
|:---|:---|:---|:---|
| 제어 흐름 | 코드 순서대로 직렬 실행 | 체이닝된 이벤트 스트림 | 동기식 코드 형태의 비동기 실행 |
| 스레드 점유 | 작업 완료 시까지 블로킹 | 논블로킹 (CPU 점유 극소화) | 블로킹 호출 시 내부적 Unmount |
| 백프레셔 (배압) | 필요 없음 (자연적 블로킹) | 완벽히 지원 (Reactive Streams) | 지원 미흡 / 구조적 동시성으로 대체 |

> 요약: 스루풋이 최우선이고 비동기 스트림 가공이 많으면 WebFlux를, 개발 직관성과 동기식 코드 유지가 필요하면 코루틴/가상 스레드를 채택한다.

**도입 시 리스크 및 대응 지표:**
- RDBMS 블로킹 병목: WebFlux를 써도 JDBC(DB 연결)가 블로킹이면 스레드 풀이 고갈됨 → 비동기 드라이버 R2DBC 적용 필수 (지표: 스레드 블로킹 타임 모니터링)
- 러닝커브 및 디버깅 지연: 장애 조치 시간(MTTR) 급증 → Blockhound 툴 도입을 통한 블로킹 코드 사전 탐지 및 리액티브 체인 내 로깅 컨텍스트(MDC) 전파 설계 (지표: 평균 결함 해결 시간)

## Ⅵ. 실무 적용 및 결론

**적용 방안 3개:**
1. MSA 기반 API 게이트웨이 및 BFF 구축: 수십 개의 백엔드 마이크로서비스를 동시다발적(Parallel)으로 호출하고 결과를 취합/합성하는 게이트웨이에 Spring Cloud Gateway(리액티브 기반)를 도입.
2. 실시간 데이터 스트리밍 파이프라인: Kafka나 RabbitMQ에서 쏟아지는 대용량 메시지를 소비할 때, 배압 조절 기능이 내장된 Project Reactor 기반 애플리케이션으로 OOM 방지 설계.
3. IoT 센서 데이터 수집 서버: 수만 대의 단말기가 초당 전송하는 작은 데이터 패킷들을 연결 종료 없이 처리하기 위해 넷티(Netty) 기반의 리액티브 서버 아키텍처 적용.

**결론 (2줄):**
- 기술사 판단: 리액티브 프로그래밍은 단순한 비동기 라이브러리가 아니라 장애 극복과 자원 효율성을 시스템 설계 단계부터 내재화하는 철학이자 아키텍처임.
- 향후 방향: 리액티브 체인의 가독성 문제를 해결하기 위해, 코틀린 코루틴(Coroutine)이나 Java 가상 스레드(Project Loom)처럼 동기식 코드 뷰(View)와 비동기 실행을 결합하는 방향으로 진화 중임.
