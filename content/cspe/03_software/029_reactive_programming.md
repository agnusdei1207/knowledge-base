## 미리 알고가기

- 리액티브 프로그래밍은 데이터 흐름과 변화 전파를 중심에 두는 프로그래밍 모델임
- publisher와 subscriber와 stream이 핵심 구성 요소임
- backpressure가 없으면 느린 소비자가 전체 시스템 병목이 됨

## Ⅰ. 개요

- **정의/개념**: 리액티브 프로그래밍은 데이터와 이벤트를 비동기 스트림으로 다루고 변화가 발생할 때마다 구독자에게 전파되도록 구성하는 프로그래밍 방식임
- **배경/필요성**: 이벤트 기반 서비스와 실시간 데이터 처리와 고동시성 환경이 늘어나면서, 비동기 흐름과 backpressure를 명시적으로 다루는 일관된 모델이 필요해짐

## Ⅱ. 특징

- 데이터 흐름과 이벤트 전파를 선언적으로 표현할 수 있음
- 비동기 처리와 backpressure 설계를 함께 다룰 수 있음
- 연산 체인이 길어질수록 디버깅과 오류 추적이 어려워질 수 있음
- I/O 중심 서비스와 스트림 처리에 강하고 단순 CRUD에는 과도할 수 있음

## Ⅲ. 종류 및 비교

| 판단 기준 | 전통 동기 처리 | 리액티브 프로그래밍 |
|:---|:---|:---|
| 실행 모델 | 요청 단위 호출 | 스트림 단위 전파 |
| 장점 | 흐름 이해가 단순 | 비동기 조합과 backpressure 유리 |
| 한계 | 동시성 확장 제약 | 학습 비용과 추적 복잡도 큼 |
| 적합 업무 | 단순 업무 로직 | 이벤트 스트림과 고동시성 서비스 |

## Ⅳ. 구성요소 및 구조

| 구성요소 | 설명 |
|:---|:---|
| Publisher | 데이터를 비동기 스트림으로 발행해 전체 흐름의 생산 측을 형성함 |
| Subscriber | 데이터를 구독하고 처리량 요구를 알려 backpressure 제어에 참여함 |
| Operator Chain | map과 filter와 merge 같은 연산을 통해 스트림 가공 로직을 선언적으로 조합함 |
| Scheduler | 어느 스레드와 실행 컨텍스트에서 흐름이 처리될지 정해 지연과 병렬성을 좌우함 |

## Ⅴ. 원리 및 절차 흐름도

```text
+-------------+     +-------------+     +-------------+     +-------------+
| 이벤트 발행    | --> | 스트림 연산    | --> | 수요 조절      | --> | 구독 처리      |
+-------------+     +-------------+     +-------------+     +-------------+
```

1. **이벤트 발행**: publisher가 데이터나 이벤트를 스트림으로 내보냄
2. **스트림 연산**: operator chain이 변환과 필터링과 결합을 수행함
3. **수요 조절**: subscriber가 처리 가능한 양을 알려 backpressure를 형성함
4. **구독 처리**: 최종 소비자가 결과를 받아 후속 동작을 수행함

## Ⅵ. 문제점 및 해결 방안

1. 문제: backpressure 설계가 약하면 느린 소비자가 전체 스트림을 막거나 메모리를 고갈시킬 수 있음
   - 해결방안: bounded queue와 demand control을 적용하고 queue depth와 subscriber lag로 검증함
2. 문제: 비동기 연산 체인이 길어질수록 오류 위치와 실행 문맥 추적이 어려워질 수 있음
   - 해결방안: tracing과 공통 에러 연산자를 적용하고 debug resolution time과 unhandled error rate로 검증함
3. 문제: 단순 CRUD 업무에 무리하게 적용하면 코드 복잡도만 늘고 실익이 적을 수 있음
   - 해결방안: 적용 대상을 이벤트 중심 흐름으로 제한하고 developer productivity와 latency gain으로 검증함

## Ⅶ. 적용 사례

- 실시간 알림 서비스에서는 publisher와 subscriber 구조를 사용하고 확인 지표는 subscriber lag와 message latency임
- 스트림 처리 파이프라인에서는 backpressure를 명시적으로 설계하고 확인 지표는 queue depth와 drop rate임
- API 게이트웨이 후단 비동기 조합에서는 operator chain을 활용하고 확인 지표는 unhandled error rate와 debug resolution time임

## Ⅷ. 결론

리액티브 프로그래밍은 비동기 문법이 아니라 데이터 흐름과 처리량 조절을 구조로 다루는 모델이므로, backpressure 설계 없이는 가치가 반감됨.
