# 📖 【암기용】 개념 완전 이해

> 목적: DORA 메트릭을 처음 봐도 완벽히 이해하게 만든다. 시험 답안 양식이 아니라, 이해를 위한 친절한 설명이다.

## 한눈에
- **개요**: DORA 메트릭은 **소프트웨어 전달 성과(Software Delivery Performance)**를 Git·CI/CD·인시던트 시스템의 실제 이벤트 데이터로 자동 계측하는 **측정 파이프라인(Measurement Pipeline)**이다. (지표 자체의 정의와 Elite 등급 기준은 038 문서에서 다루므로, 여기서는 그 지표를 실제 조직에서 어떻게 "정확한 데이터로 만들어내는가"에 집중한다.)
- **왜 필요한가**: 배포 빈도·리드타임·변경 실패율·복구 시간이라는 지표 이름을 아는 것과, 수백 개 서비스의 commit·PR·배포·장애 티켓을 자동으로 연결해 정확한 숫자를 뽑아내는 것은 전혀 다른 문제다. 이 연결이 끊기면 지표는 틀린 숫자를 보여준다.
- **핵심 직관**: 지표 정의가 온도계 눈금이라면, 계측 파이프라인은 온도계를 정확한 위치에 설치하고 보정하는 작업이다. 눈금을 안다고 온도계가 저절로 정확해지지 않는다.

## 핵심 용어 정리 (내부에 등장하는 것들)

| 용어 | 의미 | 비유 |
|:---|:---|:---|
| 소프트웨어 전달 성과(Software Delivery Performance) | DORA가 측정하려는 상위 대상 — 코드가 커밋되어 운영에 반영되고 안정적으로 유지되는 전체 능력 | 물류센터의 전체 배송 역량 |
| Deployment Frequency(배포 빈도) | 운영 환경 배포 횟수 — 얼마나 자주 배송하는가 | 하루 트럭 출고 횟수 |
| Lead Time for Changes(변경 리드타임) | commit부터 운영 반영까지 걸리는 시간 | 주문부터 배송 완료까지 시간 |
| Change Failure Rate(변경 실패율) | 배포 중 롤백·hotfix·incident로 이어진 비율 | 배송 중 파손·반품 비율 |
| Failed Deployment Recovery Time(복구 시간) | 실패한 배포를 정상으로 되돌리는 시간 | 사고 후 도로 재개통 시간 |
| change ID(변경 식별자) | commit·PR·배포·incident를 하나로 묶는 공통 키 — 없으면 네 지표를 서로 연결할 수 없다 | 택배 송장번호 |
| 매핑률(mapping rate) | 전체 이벤트 중 change ID로 정상 연결된 비율 | 바코드 스캔 성공률 |
| 데이터 파이프라인(Data Pipeline) | Git·CI/CD·incident 시스템에서 이벤트를 수집·정제·집계하는 자동화 구조 | 컨베이어 벨트와 바코드 스캐너 |
| 굿하트의 법칙(관련 개념) | 지표가 평가 목표가 되는 순간 왜곡된다는 원리 — 개인 KPI 연동을 금지하는 근거 | "시험에 나온다"고 하면 시험만 공부하는 것 |

## 깊이 이해

### change ID로 이벤트를 잇는 원리 — 수치로 이해
- 하나의 변경은 commit → PR → CI 빌드 → 배포 → (장애 발생 시) incident 티켓까지 여러 시스템에 흩어져 기록된다. 이 조각들을 하나의 change로 인식하려면 공통 키(change ID, 보통 commit SHA나 PR 번호)가 모든 시스템에 함께 남아야 한다.
- 예: 한 달 배포 200건 중 190건에서 commit SHA가 incident 티켓까지 정상적으로 남았다면 매핑률은 190/200=95%다. 매핑률이 낮아지면 나머지 10건은 성공인지 실패인지 판단할 데이터 자체가 없어, Change Failure Rate가 부정확해진다.
- 그래서 조직은 CI/CD가 배포 이벤트에 commit SHA를 자동 태깅하고, incident 티켓 생성 시 관련 배포의 change ID를 필수 입력 항목으로 강제한다.

### 지표 계산식과 워크드 예제
- Deployment Frequency = 기간 내 운영 배포 횟수 ÷ 기간. 예: 월 150회 배포면 하루 평균 5회.
- Change Failure Rate = (배포 후 rollback·hotfix·incident로 이어진 배포 건수) ÷ (전체 배포 건수) × 100. 예: 150건 배포 중 18건이 incident로 연결되면 CFR = 18/150 × 100 = 12%.
- Lead Time for Changes = 배포 시각 - 최초 commit 시각. 예: 커밋이 3월 1일 09:00, 배포가 3월 1일 11:00이면 리드타임 2시간.
- Failed Deployment Recovery Time = 정상화 시각 - incident 시작 시각. 예: incident 시작 14:00, 정상화 14:35 → 35분.

### 리드타임을 단계별로 쪼개 병목을 찾는 법
- 리드타임 총합만 보면 어디를 고쳐야 하는지 알 수 없다. 코드리뷰 대기, CI 실행, 배포 승인 대기, 실제 배포 소요로 쪼개야 병목이 보인다.
- 예: 총 리드타임 48시간 = 코드리뷰 대기 20시간 + CI 빌드/테스트 2시간 + 배포 승인 대기 20시간 + 실제 배포 6시간. 이 경우 승인 대기(20시간)가 코드리뷰 대기와 함께 절반을 차지하므로, CI를 더 빠르게 만드는 것보다 승인 프로세스를 자동화·병렬화하는 것이 리드타임 단축에 더 효과적이다.

### 지표를 개인 평가에 쓰면 데이터 자체가 오염되는 원리
- DORA 지표를 개인 KPI로 연결하면, 개발자는 배포 횟수를 늘리려고 의미 없는 PR을 쪼개 배포하거나(Deployment Frequency 부풀리기), 작은 장애를 incident로 등록하지 않고 조용히 수정한다(Change Failure Rate 축소 보고).
- 예: 실제 발생한 장애가 20건인데 평가를 의식해 5건만 incident 티켓으로 등록되면, 계산된 CFR은 실제값의 25%만 반영해 4배 가까이 과소평가된다. 지표는 좋아 보이지만 실제 시스템은 그대로 불안정한 상태다.
- 그래서 DORA는 반드시 팀·서비스 단위 개선 지표로만 쓰고, 개인 평가와 분리해야 데이터 자체의 신뢰성이 유지된다.

### 비유
- 물류센터의 각 공정(입고, 포장, 출고, 배송)마다 바코드 스캐너가 있다고 하자. 스캔 하나라도 빠지면 그 상자의 전체 이동 경로를 재구성할 수 없다. DORA 계측 파이프라인도 마찬가지로, commit부터 incident까지 모든 접점에서 change ID가 빠짐없이 기록되어야 정확한 지표가 나온다.

## 연결 개념
- 038 애자일 DORA 메트릭 — 지표 정의·계산식과 Elite/High/Medium/Low 등급 기준(이 문서는 그 지표를 실측하는 데이터 파이프라인 관점)
- SRE·온콜 인시던트 대응(289) — 복구 시간(MTTR)과 incident 데이터의 출처
- 변경 관리 — change ID 표준화와 배포 승인 절차

# 📝 【답안용】 시험 답안 템플릿

> 목적: 시험장에서 25분에 그대로 쓰는 답안 양식. 작성방식(추상표현 금지·수치·도식·문제유형 전환)을 엄격히 지킨다.
> 핵심: DORA를 단순 KPI로 쓰지 말고 배포 속도, 변경 품질, 복구 역량을 균형 있게 해석하는 답안으로 구성한다.

## 핵심 인사이트 (3줄 요약)

> 1. **본질**: DORA 메트릭은 배포 빈도, 변경 리드타임, 변경 실패율, 실패 배포 복구 시간으로 소프트웨어 전달 성과를 측정한다.
> 2. **가치**: DevOps 개선을 감각이 아니라 배포·장애·복구 데이터 기반으로 판단하게 한다.
> 3. **판단 포인트**: 속도 지표와 품질 지표를 함께 봐야 하며 개인 평가가 아니라 시스템 개선 지표로 써야 한다.

## 출제 의도 및 답안 포인트

| 출제 의도 | 반드시 짚을 핵심 | 감점 회피 포인트 |

| 운영 개선 판단 확인 | CI/CD, incident, Git 데이터 연계 | 지표를 개인 KPI로 사용하는 답안 |
| 균형 해석 역량 확인 | speed와 stability 동시 평가 | 배포 횟수 증가를 무조건 성공으로 해석 |

> 요약: DORA 문제는 네 지표를 정의하고, 지표 간 균형과 개선 액션을 제시해야 한다.

## Ⅰ. 개요 및 필요성

- 개요: DORA는 소프트웨어 전달 성과 측정 지표이다.
- 배경: 소프트웨어 조직은 배포 속도와 운영 품질을 동시에 관리해야 하므로 단일 산출량 지표만으로 개선 우선순위를 정하기 어렵다.
- 필요성: 배포 빈도, 리드타임, 변경 실패율, 복구 시간으로 DevOps 개선 우선순위를 판단해야 한다.

---

## Ⅱ. 구조 및 구성요소

```text
Git Commit -> CI/CD Deploy -> Production Change -> Incident/Recovery -> DORA Dashboard
                    +-> Deployment Frequency / Lead Time
                    +-> Change Failure Rate / Recovery Time
```

| 구성요소 | 역할 | 특이사항 |
|:---|:---|:---|
| Deployment Frequency | 운영 배포 횟수 측정 | 일/주/월 단위 |
| Lead Time for Changes | commit부터 운영 반영까지 시간 | PR, CI, 승인 대기 포함 |
| Change Failure Rate | 배포 후 장애·롤백 비율 | hotfix, rollback 포함 |
| Failed Deployment Recovery Time | 실패 배포 복구 시간 | incident start부터 restore까지 |
| Data Pipeline | Git, CI/CD, incident 데이터 수집 | 서비스·팀 단위 집계 |

> 요약: DORA는 배포 흐름과 장애 복구 흐름에서 네 가지 지표를 추출해 전달 역량을 측정한다.

---

## Ⅲ. 동작원리 및 흐름도

```text
이벤트 수집 -> 배포와 변경 매핑 -> 장애 여부 판정 -> 지표 계산 -> 병목 분석 -> 개선 실행
```

| 단계 | 처리 내용 | 검증 기준 |
|:---:|:---|:---|
| 1 | Git, CI/CD, incident 이벤트 수집 | 데이터 누락률 1% 이하 |
| 2 | commit, PR, deployment, incident 연결 | change ID 매핑률 95% 이상 |
| 3 | 4대 지표 산출 | 팀·서비스별 대시보드 |
| 4 | 병목과 실패 원인 분석 | lead time 단계별 분해 |
| 5 | 자동화·테스트·롤백 개선 | 월별 추세 개선 확인 |

> 요약: DORA는 이벤트 데이터를 연결해 지표를 만들고 병목 단계와 개선 액션을 찾는다.

## Ⅵ. 실무 적용 및 결론

**적용 방안 3개:**
1. Git commit, PR, build, deployment, incident ticket에 공통 change ID를 부여해 지표 매핑률 95% 이상을 확보함
2. 서비스별 DORA dashboard를 만들고 배포 빈도, 리드타임, 변경 실패율, 복구 시간을 월 단위 추세로 비교함
3. 변경 실패율 15% 초과 서비스는 테스트 자동화, feature flag, canary, rollback runbook을 우선 적용함

**결론 (2줄):**
- 기술사 판단: DORA는 개인 평가가 아니라 서비스 전달 시스템 개선 지표로 쓰며 speed와 stability를 동시에 본다
- 향후 방향: DORA는 SLO, error budget, platform engineering 지표와 결합해 개발 생산성 관리 체계로 확장됨
