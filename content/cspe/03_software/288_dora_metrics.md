# 📖 【암기용】 개념 완전 이해

> 목적: DORA 메트릭을 처음 봐도 완벽히 이해하게 만든다. 시험 답안 양식이 아니라, 이해를 위한 친절한 설명이다.

## 한눈에
- **개요**: 소프트웨어 전달 역량을 네 가지 운영 지표로 측정하는 체계
- **왜 필요한가**: 개발 조직은 배포를 많이 하는지, 변경이 자주 실패하는지, 장애를 얼마나 빨리 복구하는지를 수치로 봐야 개선 방향을 정할 수 있다.
- **핵심 직관**: DORA는 개발팀의 건강검진표다. 속도와 품질을 함께 측정해 어느 부분을 치료할지 알려준다.

## 깊이 이해
- **배경·문제의식**: 배포 횟수만 늘리면 장애가 늘 수 있고, 승인 절차만 늘리면 리드타임이 길어진다. DORA는 delivery speed와 operational resilience를 동시에 측정한다.
- **작동 원리**: Deployment Frequency, Lead Time for Changes, Change Failure Rate, Failed Deployment Recovery Time을 CI/CD, Git, incident 시스템에서 수집하고 팀·서비스 단위로 추세를 본다.
- **비유**: 택배 회사가 배송 건수, 주문부터 도착까지 시간, 반송률, 사고 복구 시간을 함께 보는 것과 같다.
- **구체 예시**: 하루 5회 배포, 변경 리드타임 2시간, 변경 실패율 10%, 복구 시간 30분이면 배포 속도와 복구 능력을 모두 설명할 수 있다.
- **흔한 오해·주의점**: DORA는 개인 평가 지표가 아니다. 팀과 시스템 병목을 찾는 지표이며, 숫자 달성을 위해 실패를 숨기면 지표 신뢰도가 깨진다.

## 연결 개념
- DevOps - 개발과 운영의 흐름 개선
- SRE - SLO와 장애 대응
- 변경 관리 - 변경 실패율과 복구 시간 통제

# 📝 【답안용】 시험 답안 템플릿

> 목적: 시험장에서 25분에 그대로 쓰는 답안 양식. 작성방식(추상표현 금지·수치·도식·문제유형 전환)을 엄격히 지킨다.
> 핵심: DORA를 단순 KPI로 쓰지 말고 배포 속도, 변경 품질, 복구 역량을 균형 있게 해석하는 답안으로 구성한다.

## 핵심 인사이트 (3줄 요약)

> 1. **본질**: DORA 메트릭은 배포 빈도, 변경 리드타임, 변경 실패율, 실패 배포 복구 시간으로 소프트웨어 전달 성과를 측정한다.
> 2. **가치**: DevOps 개선을 감각이 아니라 배포·장애·복구 데이터 기반으로 판단하게 한다.
> 3. **판단 포인트**: 속도 지표와 품질 지표를 함께 봐야 하며 개인 평가가 아니라 시스템 개선 지표로 써야 한다.

## 출제 의도 및 답안 포인트

| 출제 의도 | 반드시 짚을 핵심 | 감점 회피 포인트 |
|:---|:---|:---|
| DevOps 성과 측정 이해 확인 | 4대 지표 정의와 의미 | 배포 빈도만 쓰고 실패율·복구시간 누락 |
| 운영 개선 판단 확인 | CI/CD, incident, Git 데이터 연계 | 지표를 개인 KPI로 사용하는 답안 |
| 균형 해석 역량 확인 | speed와 stability 동시 평가 | 배포 횟수 증가를 무조건 성공으로 해석 |

> 요약: DORA 문제는 네 지표를 정의하고, 지표 간 균형과 개선 액션을 제시해야 한다.

---

## Ⅰ. 개요 및 필요성

DORA는 전달 성과 측정 지표이다. 소프트웨어 조직은 배포 속도와 운영 품질을 동시에 관리해야 한다. DORA는 배포 빈도, 리드타임, 변경 실패율, 복구 시간으로 DevOps 개선 우선순위를 데이터로 판단하게 한다.

---

## Ⅱ. 구조 및 구성요소

```text
Git Commit -> CI/CD Deploy -> Production Change -> Incident/Recovery -> DORA Dashboard
                    +-> Deployment Frequency / Lead Time
                    +-> Change Failure Rate / Recovery Time
```

| 구성요소 | 역할 | 특이사항 |
|:---|:---|:---|
| Deployment Frequency | 운영 배포 횟수 측정 | 일/주/월 단위 |
| Lead Time for Changes | commit부터 운영 반영까지 시간 | PR, CI, 승인 대기 포함 |
| Change Failure Rate | 배포 후 장애·롤백 비율 | hotfix, rollback 포함 |
| Failed Deployment Recovery Time | 실패 배포 복구 시간 | incident start부터 restore까지 |
| Data Pipeline | Git, CI/CD, incident 데이터 수집 | 서비스·팀 단위 집계 |

> 요약: DORA는 배포 흐름과 장애 복구 흐름에서 네 가지 지표를 추출해 전달 역량을 측정한다.

---

## Ⅲ. 동작원리 및 흐름도

```text
이벤트 수집 -> 배포와 변경 매핑 -> 장애 여부 판정 -> 지표 계산 -> 병목 분석 -> 개선 실행
```

| 단계 | 처리 내용 | 검증 기준 |
|:---:|:---|:---|
| 1 | Git, CI/CD, incident 이벤트 수집 | 데이터 누락률 1% 이하 |
| 2 | commit, PR, deployment, incident 연결 | change ID 매핑률 95% 이상 |
| 3 | 4대 지표 산출 | 팀·서비스별 대시보드 |
| 4 | 병목과 실패 원인 분석 | lead time 단계별 분해 |
| 5 | 자동화·테스트·롤백 개선 | 월별 추세 개선 확인 |

> 요약: DORA는 이벤트 데이터를 연결해 지표를 만들고 병목 단계와 개선 액션을 찾는다.

## Ⅳ. 특징

| 구분 | 단일 생산성 지표 | DORA 메트릭 | 수치·기술 포인트 |
|:---|:---|:---|:---|
| 측정 범위 | 코드량, 작업량 | 배포, 리드타임, 실패, 복구 | 4대 지표 |
| 관점 | 개인 산출 중심 | 시스템 흐름 중심 | team/service level |
| 품질 반영 | 결함 반영 부족 | 변경 실패율과 복구 시간 포함 | CFR 15% 이하 목표 |
| 활용 방식 | 평가 중심 오용 가능 | 병목 개선과 운영 회고 | CI/CD, incident data |

> 요약: DORA는 개인 평가가 아니라 팀의 전달 흐름과 운영 복원력을 개선하기 위한 시스템 지표이다.

## Ⅴ. 심화 비교 및 적용 판단

| 비교 축 | 기존/대안 | 본 키워드 | 선택 기준 |
|:---|:---|:---|:---|
| 구조 | 배포 횟수 수동 집계 | Git-CI-incident 자동 연결 | 서비스 수 5개 이상 |
| 비용/성능 | 릴리스 회고 중심 | 실시간 DORA dashboard | 배포 빈도 주 1회 이상 |
| 운영/위험 | 속도 지표 편향 | 실패율·복구시간 동시 측정 | 장애 SLA 운영 조직 |

> 요약: 배포와 장애 데이터가 분리된 조직은 DORA 데이터 모델부터 정비해야 지표 해석이 가능하다.

| 리스크 | 원인 | 대응 방안 | 확인 지표 |
|:---|:---|:---|:---|
| 지표 왜곡 | 개인 평가와 보상 연결 | 팀 단위 개선 지표로 제한 | 미보고 장애 0건 |
| 데이터 불일치 | 배포와 incident ID 미연결 | change ID 표준화 | 매핑률 95% 이상 |
| 속도 편향 | 배포 빈도만 목표화 | CFR, recovery time 동시 관리 | CFR 15% 이하 |

> 요약: DORA 운영은 지표 왜곡, 데이터 연결, 속도 편향을 통제해야 한다.

| 점검 항목 | 목표 기준 | 측정 방법 |
|:---|:---|:---|
| 배포 흐름 | deployment frequency 주 1회 이상 | CI/CD deploy event |
| 변경 품질 | change failure rate 15% 이하 | rollback, hotfix, incident link |
| 복구 역량 | recovery time 1시간 이하 | incident timeline |

> 요약: DORA 지표는 속도, 품질, 복구 역량을 동시에 충족하는지 확인하는 운영 계기판이다.

## Ⅵ. 실무 적용 및 결론

**적용 방안 3개:**
1. Git commit, PR, build, deployment, incident ticket에 공통 change ID를 부여해 지표 매핑률 95% 이상을 확보함
2. 서비스별 DORA dashboard를 만들고 배포 빈도, 리드타임, 변경 실패율, 복구 시간을 월 단위 추세로 비교함
3. 변경 실패율 15% 초과 서비스는 테스트 자동화, feature flag, canary, rollback runbook을 우선 적용함

**결론 (2줄):**
- 기술사 판단: DORA는 개인 평가가 아니라 서비스 전달 시스템 개선 지표로 쓰며 speed와 stability를 동시에 본다
- 향후 방향: DORA는 SLO, error budget, platform engineering 지표와 결합해 개발 생산성 관리 체계로 확장됨
