# 📖 【암기용】 개념 완전 이해

## 한눈에
- **개요**: 데이터베이스가 동시성 제어를 할 때, 잠금(Lock)을 거는 대신 데이터의 '과거 버전(Snapshot)'을 여러 개 만들어 읽기 작업과 쓰기 작업이 서로 방해하지 않게 하는 기술
- **왜 필요한가**: 과거에는 데이터를 쓸 때(Update) 다른 사람이 읽지 못하게 Lock을 걸어 대기시켰다. 이로 인해 시스템이 느려지자, "쓰는 동안 읽는 사람에겐 수정 전 '과거 데이터'를 보여주자!"는 아이디어로 동시성(성능)을 극대화하기 위해 등장했다.
- **핵심 직관**: 나무위키 문서(데이터)를 누군가 수정(Write)하고 있어도, 다른 사람들은 Lock에 걸려 기다리지 않고 직전 버전의 문서(Read)를 계속 볼 수 있는 것과 같다. (읽기는 쓰기를 막지 않고, 쓰기도 읽기를 막지 않는다)

## 핵심 용어 정리

| 용어/표기 | 의미 | 비유·예 |
|:---|:---|:---|
| MVCC | Multi-Version Concurrency Control (다중 버전 동시성 제어) | 문서 리비전(버전) 관리 시스템 |
| Undo Log (언두 로그) | 데이터를 변경하기 전의 원본 데이터를 저장해두는 공간 | 수정 전 문서 백업본 |
| Snapshot (스냅샷) | 특정 시점(트랜잭션 시작 시점)의 데이터 상태 | 찰칵 찍어둔 과거 사진 |

## 깊이 이해
- **배경·문제의식**: 기존 2PL(2 Phase Locking, 099 키워드) 방식은 완벽한 정합성을 주지만 읽기 락(S-Lock)과 쓰기 락(X-Lock)이 서로 충돌하여 엄청난 병목을 유발했다. 성능 향상을 위해 락 없는(Lock-free) 읽기가 절실했다.
- **작동 원리**: 
  - 트랜잭션 A가 데이터 X를 10에서 20으로 수정(Update)하면, 즉시 덮어쓰지 않고 변경 전 데이터(X=10)를 **Undo Log**에 복사해 둔다.
  - 트랜잭션 A가 커밋하기 전에 트랜잭션 B가 데이터 X를 조회(Select)하면, 현재 테이블의 X=20은 아직 '미확정'이므로 **Undo Log에 있는 버전(X=10)**을 가져와 보여준다.
  - 트랜잭션 B는 잠금(Lock) 대기 없이 즉시 과거 버전을 읽으므로 성능 저하가 없다.
- **비유**: 은행 직원이 장부를 수정하는 동안(Write), 지점장은 장부 복사본(Undo Log)을 들고 와서 대기 없이 감사(Read)를 진행하는 것.
- **흔한 오해·주의점**: "MVCC는 모든 락을 없앤다?" 아니다. 읽기와 쓰기 충돌은 없애주지만, 쓰기와 쓰기(Update vs Update) 충돌 시에는 여전히 배타적 잠금(X-Lock)을 걸어 순서를 맞춘다.

## 연결 개념
- **트랜잭션 격리 수준 (Isolation Level)**: MVCC가 스냅샷을 언제까지 유지해서 보여줄지를 결정하는 기준 (096 키워드)
- **2PL (2단계 잠금)**: MVCC 등장 이전에 주로 쓰이던 전통적 락 기반 제어 방식 (099 키워드)

# 📝 【답안용】 시험 답안 템플릿

## 핵심 인사이트 (3줄 요약)

> 1. **본질**: MVCC는 데이터를 변경할 때 Undo Log에 이전 버전을 저장하여 하나의 데이터에 여러 버전(Multi-Version)을 유지하는 동시성 제어 기술이다.
> 2. **가치**: "읽기 작업은 쓰기 작업을 대기하지 않고, 쓰기 작업도 읽기 작업을 대기하지 않는다"는 원칙을 구현하여 데이터 무결성과 동시 처리 성능(Throughput)을 획기적으로 높인다.
> 3. **판단 포인트**: 트랜잭션 격리 수준(Isolation Level) 구현의 핵심 기반 기술이나, 장기 트랜잭션 발생 시 Undo 공간 비대화로 인한 성능 저하(Garbage Collection 필요) 위험을 통제해야 한다.

## 출제 의도 및 답안 포인트

| 출제 의도 | 반드시 짚을 핵심 | 감점 회피 포인트 |
|:---|:---|:---|
| 기존 Lock 기반 제어의 한계와 MVCC 등장 배경 | 읽기/쓰기 상호 간섭 제거(Lock-free Read) | 모든 연산에서 Lock이 없어진다고 단정 (Write-Write는 여전히 Lock 필요) |
| MVCC의 핵심 동작 원리와 구성요소 매핑 | Undo Log (Rollback Segment), Snapshot, SCN/Transaction ID | Undo Log를 활용한 다중 버전 생성 원리 누락 |

> 요약: MVCC가 락 기반 제어의 단점을 극복한 원리(Undo Log 활용 스냅샷)와 격리 수준 구현 방식을 논리적으로 서술해야 한다.

---

## Ⅰ. 개요 및 필요성

- 개요: MVCC(다중 버전 동시성 제어)는 동시 접근이 일어날 때 데이터의 여러 버전을 유지하여, 잠금(Lock) 없이 일관된 읽기를 제공하는 트랜잭션 제어 기법임
- 배경: 전통적인 비관적 락(Pessimistic Lock) 방식은 Read/Write 간 경합으로 병목과 데드락(Deadlock)을 빈번히 유발함
- 필요성: 시스템 대기 시간을 최소화하고 병행 처리 성능(TPS)을 극대화하면서도 트랜잭션 ACID의 고립성(Isolation)을 보장하기 위해 필수적임

---

## Ⅱ. 구조 및 구성요소

```text
Tx B (Read) ----> [Undo Log / Rollback Segment] <----+
                           ^ (과거 버전 X=10)        | (변경 전 복사)
Tx A (Write) ---> [Data File / Table Space] ---------+
                     (최신 버전 X=20, 미커밋)
```

| 구성요소 | 역할 | 특이사항 |
|:---|:---|:---|
| Transaction ID (TxID) | 트랜잭션 시작 시 발급되는 고유 식별 번호 (시간 순서) | SCN(System Commit Number) |
| Data File (데이터 블록) | 가장 최근에 업데이트된 최신 상태의 데이터 저장 | 최신 버전 (변경 중) |
| Undo Log (언두 로그) | 데이터를 변경하기 전의 과거 상태(Snapshot)를 백업 보관 | 다중 버전 저장소, Rollback 시 사용 |
| CR (Consistent Read) | TxID를 비교하여 자신보다 미래에 변경된 데이터 대신 Undo 영역의 데이터를 읽는 행위 | 읽기 일관성 보장 |

> 요약: 데이터 갱신 시 최신본은 데이터 블록에 두고, 이전 버전을 언두 로그로 밀어내어 읽기/쓰기를 분리하는 구조다.

---

## Ⅲ. 동작원리 및 흐름도

```text
Tx A (Update) -> Undo에 과거 버전 복사 -> Data 블록 갱신 (미커밋) -> Tx B (Select) 진입
-> Tx B의 ID와 Data 블록의 변경 Tx ID 비교 -> 미커밋 확인 -> Undo Log의 과거 스냅샷 참조
```

- 1단계 [갱신 및 버저닝]: 트랜잭션 A(TxID 100)가 `Salary=5000`을 `6000`으로 갱신 시, `5000`을 Undo Log에 저장
- 2단계 [동시 조회]: 트랜잭션 B(TxID 101)가 `Salary`를 조회할 때, 데이터 블록의 `6000`이 아직 커밋되지 않음(또는 자신보다 늦게 시작됨)을 TxID로 확인
- 3단계 [CR(Consistent Read) 수행]: 트랜잭션 B는 락(Lock) 대기 없이 Undo Log를 추적하여 `5000`이라는 '일관된 과거 스냅샷'을 읽어감
- 4단계 [GC(Garbage Collection)]: 트랜잭션 A가 커밋되고, 더 이상 `5000`을 참조하는 트랜잭션이 없으면 DB 백그라운드 프로세스가 Undo 버전을 정리함

> 요약: 버전을 관리하여 "읽기는 쓰기를 막지 않고, 쓰기는 읽기를 막지 않는" 비차단(Non-blocking) 조회 환경을 완성한다.

---

## Ⅳ. 특징

- 동시성 극대화: Read 락(Shared Lock)을 사용하지 않으므로, 조회 위주의 웹 서비스 환경에서 트랜잭션 처리량(Throughput) 비약적 상승
- 데드락(Deadlock) 감소: 읽기와 쓰기 간의 경합이 원천 차단되므로 상호 대기로 인한 교착 상태 발생 확률 대폭 감소
- 공간 오버헤드: 다중 버전을 저장하기 위한 추가 스토리지(Undo/Rollback Segment) 공간이 지속적으로 소모됨

---

## Ⅴ. 심화 비교 및 적용 판단

| 비교 축 | Lock 기반 동시성 제어 (2PL) | MVCC 기반 제어 | 선택 기준 |
|:---|:---|:---|:---|
| 충돌 통제 방식 | Lock을 획득하여 타 트랜잭션 대기 강제 | Undo 로그 스냅샷 참조 (대기 없음) | 서비스 대기 시간 허용도 |
| Read/Write 충돌 | 서로 차단 (대기 발생) | 차단 안 함 (동시 진행) | 시스템 Read 비중 |
| Write/Write 충돌 | 서로 차단 (배타 락 대기) | 서로 차단 (배타 락 대기) | 쓰기 충돌은 양쪽 동일 |

> 요약: 현대의 주류 RDBMS(Oracle, MySQL, PostgreSQL)는 성능 최적화를 위해 MVCC 방식을 기본 동시성 제어 기법으로 채택하고 있다.

**리스크·대응 (기본은 불릿):**
- 장기 실행 트랜잭션(Long Transaction): 한 트랜잭션이 오래 열려 있으면 그동안 생성된 Undo 버전들을 지우지 못해 'Undo Space Full' 장애 발생 → 대용량 배치 처리 시 트랜잭션을 잘게 쪼개어(Chunking) 커밋 수행
- Lost Update (갱신 손실): 쓰기-쓰기 충돌 시 나중에 커밋한 데이터가 덮어씌워짐 → 애플리케이션 레벨의 낙관적 락(Version 컬럼) 또는 명시적 락(`SELECT FOR UPDATE`) 방어
- 가비지 컬렉션(GC) 부하: PostgreSQL의 경우 버전 관리를 원본 테이블에 같이 기록하여 Vacuum(청소) 작업 오버헤드 발생 → 오토 바큠(Auto Vacuum) 최적화 튜닝 필수

## Ⅵ. 실무 적용 및 결론

**적용 방안 3개:**
1. 적정 격리수준 설정: MySQL(InnoDB)은 Repeatable Read 환경에서 MVCC가 강력하게 동작하므로, NRR 방어를 위해 기본 설정을 유지하되 장기 쿼리 모니터링 강화
2. 배치 트랜잭션 분리: OLT 환경에서 1시간 이상 도는 집계 쿼리가 있으면 MVCC Undo 볼륨이 급증하므로, Read Replica(복제 DB)로 조회 쿼리를 라우팅하여 격리
3. Lost Update 애플리케이션 방어: MVCC는 읽기 충돌만 해결하므로, 재고 차감 같은 동시 쓰기 로직은 JPA `@Version` 등을 활용한 낙관적 락(Optimistic Lock)으로 애플리케이션 계층 통제 구현

**결론 (2줄):**
- 기술사 판단: MVCC는 RDBMS가 NoSQL의 높은 동시 처리 성능에 맞설 수 있게 해준 핵심 아키텍처이나, 무한정 늘어나는 과거 버전(Undo) 관리가 성능 저하의 뇌관임을 인지해야 한다
- 향후 방향: 전통적 MVCC를 개선하여 in-memory 환경이나 분산 트랜잭션에서도 스냅샷 격리(Snapshot Isolation)를 보장하는 NewSQL 데이터베이스(CockroachDB 등) 연구가 활발하다
