## 핵심 인사이트 (3줄 요약)
- **MVCC (Multi-Version Concurrency Control)**: 트랜잭션이 데이터를 수정할 때 기존 데이터를 덮어쓰지 않고, 과거 버전의 스냅샷(Undo Log)을 보관하여 **"읽기 작업(SELECT)과 쓰기 작업(UPDATE)이 서로 락(Lock)을 걸며 방해하지 않게 만드는"** 현대 DBMS의 핵심 기술.
- 누군가 데이터를 고치고 있어도(쓰기 락), 다른 사람은 기다릴 필요 없이 안전하게 '수정되기 전의 과거 데이터'를 읽을 수 있어 DB 성능(동시성)이 비약적으로 향상됨.
- Oracle과 MySQL(InnoDB)에서 채택한 기술로, 전통적인 2-Phase Locking(2PL)의 치명적 속도 저하 문제를 완벽히 극복한 데이터베이스 공학의 걸작임.

## Ⅰ. 개요 및 필요성
- **개요**: 데이터의 여러 버전을 유지하여, 읽기 트랜잭션과 쓰기 트랜잭션이 서로 차단(Blocking)되지 않고 동시에 실행될 수 있도록 하는 동시성 제어 프로토콜.
- **필요성**: 과거에는 누가 계좌 잔액을 수정(UPDATE)하고 있으면, 그 데이터에 쓰기 잠금(Write Lock)이 걸려서 다른 사람은 수정이 끝날 때까지 조회를 못 하고(Read Blocking) 멍하니 기다려야 했음. 트래픽이 몰리는 웹 환경에서 이런 '기다림(대기)'은 시스템 다운으로 이어짐. 읽기와 쓰기를 분리할 마법이 필요했음.
---
## Ⅱ. 아키텍처 및 핵심 원리
- **동작 원리 (MySQL InnoDB 기준)**:
  1. Tx_A가 `잔액=100`인 데이터를 `200`으로 수정(UPDATE)함.
  2. DB는 실제 데이터 블록을 `200`으로 갱신하되, 수정 전의 `100`이라는 값은 **Undo Log(언두 로그, 임시 공간)**에 복사해 둠. (이때 데이터에는 트랜잭션 ID가 박힘).
  3. 아직 Tx_A가 커밋을 안 했는데, Tx_B가 `잔액`을 조회(SELECT)하러 옴.
  4. DB는 Tx_B에게 현재 수정 중인 `200`을 보여주지 않고(Dirty Read 방지), **Undo Log에 있는 과거 스냅샷(`100`)을 읽어서 반환해 줌.**
- **핵심 철학**: "Readers do not block Writers, and Writers do not block Readers" (읽는 자는 쓰는 자를 막지 않고, 쓰는 자는 읽는 자를 막지 않는다).

```text
[ MVCC 스냅샷 읽기(Consistent Read) 도식 ]

 (트랜잭션 A - 쓰기)                           (트랜잭션 B - 읽기)
 UPDATE 계좌 SET 잔액 = 200;
        ⬇️
 [ 실제 디스크 Data ]                      [ SELECT 잔액 FROM 계좌; ]
  잔액 = 200 (Tx_A가 물고 있음)                 ⬇️ (Tx_A가 아직 커밋 안 했네?)
                                              ⬇️ (그럼 난 과거 버전을 읽을게!)
 [ Undo Log (과거 스냅샷) ] <-------------------+
  잔액 = 100 
  
  * 결과: Tx_B는 락을 기다리지 않고 즉시 '100'이라는 안전한 값을 조회해 감.
```

## Ⅲ. 비교 및 연결
| 구분 | 2PL (2-Phase Locking / 전통적 잠금) | MVCC (Multi-Version) |
|---|---|---|
| **동시성 제어 방식** | 무조건 자물쇠(Lock)를 채워 남의 접근 차단 | 버전을 여러 개 만들어 스냅샷을 제공 |
| **읽기와 쓰기 충돌** | **서로 대기함 (Blocking 발생)** | **서로 대기하지 않음 (Non-Blocking)** |
| **읽기 일관성 보장** | 락을 통해 물리적으로 강제 | Undo Log(스냅샷)를 통해 논리적으로 제공 |
| **단점 (오버헤드)** | 데드락(Deadlock) 발생 확률 극상 | Undo Log 저장 공간 낭비, Garbage Collection 필요 |

## Ⅳ. 실무 적용 및 기술사 판단
- **Undo Log 폭발과 성능 저하**: MVCC는 완벽해 보이지만 치명적인 약점이 있음. 개발자가 트랜잭션을 열어놓고(Begin) 외부 API를 호출하느라 10분 동안 커밋을 안 하면(Long Transaction), DB는 그 10분 동안 변경되는 모든 과거 데이터를 Undo Log에 산더미처럼 쌓아둬야 함. 결국 디스크 풀(Full)이나 메모리 장애로 이어지므로, **트랜잭션의 유지 시간은 극한으로 짧게 가져가는 것**이 아키텍처 설계의 기본임.
- **MySQL과 PostgreSQL의 차이**: MySQL은 별도의 영역(Undo Log)에 과거 데이터를 백업하지만, PostgreSQL은 기존 데이터가 있는 실제 테이블 공간에 새 버전을 추가(Append)함. 이 때문에 Postgres는 쌓인 과거 찌꺼기를 치워주는 VACUUM(청소기) 작업이 필수적이며, 이 VACUUM이 실패하면 DB 전체 성능이 마비되는 현상(Bloating)을 실무적으로 주의해야 함.
---
## Ⅴ. 기대효과 및 결론
- 쇼핑몰에서 누군가 상품을 결제(UPDATE)하고 있을 때, 수만 명의 다른 고객들이 상품 상세페이지(SELECT)를 지연 없이 볼 수 있게 해주는 현대 IT 비즈니스의 숨은 영웅임.
- "데이터를 덮어쓰지 않고 이력을 남긴다"는 MVCC의 철학은 훗날 Git(형상관리)이나 블록체인의 버전 관리 메커니즘과도 일맥상통하는 공학적 아름다움을 지님.

### 👶 어린이를 위한 3줄 비유 설명
1. 옛날에는 도서관에서 친구가 책(데이터)을 고치고 있으면, 친구가 다 고칠 때까지 나는 그 책을 아예 볼 수가 없었어요 (Lock 방식).
2. MVCC는 마법의 복사기예요. 친구가 원본 책에 막 낙서를 하며 고치고 있을 때, 복사기가 짠! 하고 '친구가 고치기 전의 깨끗한 복사본(Undo Log)'을 나에게 줘요.
3. 덕분에 나는 친구를 기다리지 않고 복사본을 읽으며 공부할 수 있고, 친구도 내 눈치 안 보고 마음껏 원본을 고칠 수 있답니다!
