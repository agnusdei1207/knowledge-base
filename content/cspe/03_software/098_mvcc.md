## 미리 알고가기

- MVCC(Multi-Version Concurrency Control): 동일한 데이터 행에 대해 다중 버전을 유지함으로써 읽기와 쓰기 작업이 서로 대기하지 않도록 제어하는 동시성 제어 기법임
- 스냅샷(Snapshot): 특정 시점에 존재하는 데이터베이스의 논리적인 일시적 복사본임
- Read View: 트랜잭션이 시작되었을 때 활성 상태인 트랜잭션 목록을 관리하여 읽기 가시성을 결정하는 제어 구조임
- Undo 로그: 변경 전 데이터를 저장하는 공간으로, MVCC의 이전 버전 데이터를 복원하고 롤백을 수행하는 데 사용됨
- Vacuum / Garbage Collection: 더 이상 어떠한 트랜잭션도 참조하지 않는 오래된 행 버전을 회수하여 디스크 공간을 확보하는 백그라운드 작업임

## 작성 근거(검토용)

- 핵심 키워드 선정 이유: 동시성 제어 기법 중 읽기-쓰기 간 병목을 원천적으로 해결하는 MVCC의 아키텍처 및 버전 관리 메커니즘을 상세화하여 DB 성능 극대화 방안을 제공하기 위함
- 절 구성 및 전개 흐름 이유: 개요에서 MVCC의 기본 작동 정의와 필요성을 제시한 뒤, 특징에서 잠금 없는 조회 성능을 도출함. 비교표를 통해 비관적 락과의 근본적 차이를 분석하고, 설계 구조에서 Read View와 Undo 로그의 정적 관계를 도식화함. 원리 단계에서는 버전 생성부터 소멸까지의 주기적 흐름을 다루고 실무 관리 지표로 결속함
- 전수 검수 완료 근거: 제목, frontmatter, 미리 알고가기, 본문, 표 헤더·셀, 요약, 결론의 전체 맞춤법 및 한국어 표현 자연스러움을 검사하고 5회 완독을 통과함

## Ⅰ. 개요

- **정의/개념**: MVCC는 데이터를 변경할 때 덮어쓰지 않고 이전 버전을 유지하면서, 각 트랜잭션이 자신의 스냅샷 기준에 부합하는 일관된 버전을 선택해 읽도록 보장하는 다중 버전 동시성 제어 기법임
- **배경/필요성**: 대용량 트랜잭션 환경에서 읽기 작업이 쓰기 작업에 의해 차단되거나 그 반대의 차단 현상을 방지하여 동시성 처리 성능(Throughput)을 획기적으로 향상시키기 위해 도입됨

### 쉽게 이해하기 (학습용)
- 칠판에 적힌 글씨를 지우고 새로 쓰는 대신, 매번 칠판의 사진을 찍어 보관함으로써 읽는 사람은 사진첩(스냅샷)을 보고 쓰는 사람은 칠판을 계속 고치는 방식임

## Ⅱ. 특징

- 읽기(SELECT) 트랜잭션이 공유 잠금을 획득하지 않고 스냅샷을 참조하여 쓰기(DML) 트랜잭션과 상호 차단(Blocking)되지 않음
- 데이터 행마다 고유한 생성 트랜잭션 식별자($TXID$)와 만료 식별자를 명시하여 버전 가시성을 동적으로 식별함
- 갱신이 누적됨에 따라 과거 버전 데이터가 과도하게 쌓이게 되므로 백그라운드 정리(Vacuum 또는 Garbage Collection) 프로세스가 동반되어야 함
- 동일 데이터에 대한 동시 쓰기(Write-Write) 충돌 시에는 비관적 락이나 롤백 후 재시도 기법을 활용하여 일관성을 보호함

### 쉽게 이해하기 (학습용)
- 쓰는 사람과 읽는 사람이 서로 줄을 서서 기다릴 필요가 없어서 속도가 매우 빠르지만, 옛날 사진들이 저장 공간을 차지하므로 정기적으로 휴지통을 비워야 함

## Ⅲ. 종류 및 비교

| 판단 기준 | 락 중심 제어 (2PL) | 다중 버전 동시성 제어 (MVCC) |
|:---|:---|:---|
| 읽기 대기 수준 | 쓰기 잠금이 설정된 경우 읽기 트랜잭션은 해제 시까지 대기함 | 쓰기 중에도 과거 버전을 조회하므로 대기 없이 즉시 응답함 |
| 일관성 기준 | 잠금 획득 시점의 물리적 데이터 상태를 직접 조회함 | 트랜잭션 시작 시점의 스냅샷($TXID$ 기준)을 조회함 |
| 주요 비용 부담 | 잠금 경쟁으로 인한 데드락 및 컨텍스트 스위칭 오버헤드 | 다중 버전 데이터 누적으로 인한 저장 공간 팽창 및 정리(Vacuum) 부하 |

> 요약: 락 중심 제어는 현재 값의 잠금을 기다리고 MVCC는 스냅샷에 보이는 행 버전을 읽음.

### 쉽게 이해하기 (학습용)
- 락 방식은 줄을 서서 차례대로 장부를 받아 쓰는 것이고, MVCC는 언제든 장부의 지난 복사본을 가져가 편하게 읽는 방식의 차이임

## Ⅳ. 설계 요소 및 구조

```text
+------------------------------------------------------------+
|                        MVCC 설계 구조                      |
+------------------------------------------------------------+
       │                              │
       ▼                              ▼
+──────────────────────+      +──────────────────────+
|   1. Read View       |      |   2. Undo 로그 영역  |
|   - 활성 트랜잭션 ID  |      |   - 롤백 세그먼트    |
|   - 가시성 경계 식별 |      |   - 과거 행 데이터   |
+──────────────────────+      +──────────────────────+
       │                              │
       +──────────────┬───────────────+
                      ▼
+────────────────────────────────────────────────────────────+
|                      3. 백그라운드 가비지 컬렉터            |
|   - Vacuum 엔진 (참조 안 되는 구버전 일괄 제거)            |
|   - 인덱스/테이블 공간 정리 및 디스크 조각 모음            |
+------------------------------------------------------------+
```

| 설계 요소 | 설명 |
|:---|:---|
| 행 헤더 버전 정보 | 각 릴레이션 튜플에 삽입된 생성 트랜잭션 식별자($xmin$, $TXID$) 및 삭제 식별자($xmax$) 메타데이터 |
| Undo 로그 레코드 | 기존 원본 데이터를 복구하기 위해 변경 내역을 롤백 세그먼트에 링크드 리스트로 유지하는 기록 |
| Read View / 스냅샷 | 특정 트랜잭션이 조회 가능한 활성 트랜잭션 범위를 지배하는 읽기 판단 영역 |
| 가비지 컬렉터 (Vacuum) | 활성 트랜잭션 범위 밖으로 밀려나 더 이상 읽을 필요가 없는 데드 튜플(Dead Tuple)을 회수하는 엔진 |

> 요약: 행 버전 정보와 스냅샷 뷰가 읽기 가시성을 정하고 충돌 규칙·정리 작업이 쓰기와 구버전을 처리함.

### 쉽게 이해하기 (학습용)
- 장부에 붙어 있는 꼬리표(버전 정보)와 옛날 일기장(Undo), 그리고 읽을 수 있는 기준 안경(Read View)을 사용하여 과거 버전을 구별하고 청소함

## Ⅴ. 원리 및 절차 흐름도

```text
[트랜잭션 시작] ── (Read View 생성 및 현재 TXID 획득)
       │
       ▼
[조회 쿼리 수행] ── (대상 행의 TXID와 Read View 경계 비교)
       │
       ▼
[버전 가시성 판정]
  ├─ (조회 가능) ─> [해당 행/Undo 버전 즉시 반환]
  └─ (조회 불가) ─> [롤백 포인터 추적하여 이전 버전 획득]
       │
       ▼
[종료 후 Vacuum] ── (커밋 후 더 이상 사용 안 하는 버전 정리)
```

1. **트랜잭션 시작 및 뷰 생성**: 트랜잭션이 기동되면 고유한 $TXID$를 부여받고, 활성 트랜잭션 목록이 기록된 Read View를 구성함
2. **조회 쿼리 수행**: 대상 행 데이터 헤더에 기록된 $xmin$(생성)과 $xmax$(삭제) 트랜잭션 식별자를 읽음
3. **가시성 비교 검증**: Read View 규칙에 따라 해당 행이 자신이 시작하기 전에 커밋된 데이터인지 판정함
4. **이전 버전 획득**: 만약 변경 중이거나 시작 후 커밋된 정보라면, 행의 롤백 포인터를 따라 Undo 로그 영역의 이전 버전을 복원하여 반환함
5. **참조 해제 및 가비지 컬렉션**: 트랜잭션들이 완료되어 더 이상 이전 버전을 참조할 수 있는 리더가 없으면 Vacuum 프로세스가 해당 공간을 회수함

> 요약: 스냅샷 시점의 버전을 읽고 갱신은 새 버전으로 기록한 뒤 참조가 끝난 구버전을 정리함.

### 쉽게 이해하기 (학습용)
- 내 트랜잭션 카드를 보여주고 장부를 펼쳤을 때, 나보다 늦게 쓴 내용은 숨기고(옛날 일기장을 찾아 읽음), 다 읽은 옛 일기는 청소부가 치우는 과정임

## Ⅵ. 실무 사례

1. 주문 조회 DB는 장기 트랜잭션 제한 시간을 설정하고 최대 스냅샷 유지 시간·버전 팽창률을 확인함
2. 재고 갱신 DB는 쓰기 충돌 재시도와 버전 정리를 적용하고 직렬화 실패율·정리 지연을 확인함

### 쉽게 이해하기 (학습용)
- 수시로 글을 고쳐서 메모리가 부족해지는 현상을 막기 위해, 청소 로직(Autovacuum)을 자주 돌리거나 오래 켜져 있는 조회를 강제 종료함

## Ⅶ. 결론

- MVCC는 동시성 제어의 효율성을 대폭 높인 혁신적 기법이나, 버전 관리 오버헤드와 저장 공간 팽창이라는 비용을 지불해야 하는 양면성이 존재함
- 따라서 대용량 시스템에서는 쿼리 수행 시간을 타이트하게 제한하고 백그라운드 Vacuum 동작 주기를 부하가 적은 시간대에 적극 활성화하는 지표 중심 관리가 요구됨

### 쉽게 이해하기 (학습용)
- 쓰기와 읽기의 벽을 허문 최적의 성능 기법이지만, 주기적인 쓰레기 정리(Autovacuum)를 감시하지 않으면 시스템이 멈출 수 있음을 명심해야 함
