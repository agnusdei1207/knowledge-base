## Ⅰ. 개요
- **정의**: HTTP 핸드셰이크 후 TCP 위에 전이중 양방향 채널을 유지하는 실시간 통신 프로토콜
- **배경/필요성**: HTTP 폴링은 불필요한 요청·응답 반복으로 지연과 대역폭 낭비를 유발하므로 상시 연결이 필요함
- **비유**: 매번 전화를 걸고 끊는 대신 수화기를 들고 있는 채로 대화를 이어가는 것과 유사함

| 출제 의도 | 반드시 짚을 핵심 | 감점 회피 포인트 |
|:---|:---|:---|
| 실시간 양방향 통신 구조 이해 | Upgrade 핸드셰이크, 프레임 구조, 연결 유지 | SSE·Long Polling과의 차이를 명확히 구분할 것 |

> 요약: HTTP에서 업그레이드하여 전이중 통신을 유지하는 실시간 프로토콜임

## Ⅱ. 구성요소
```text
Client                          Server
  |--HTTP GET (Upgrade)---------->|
  |<-101 Switching Protocols------|
  |<======= WebSocket Frame =====>|
  |       (full-duplex, binary/text)
  |--Close Frame----------------->|
  |<-Close Frame------------------|
```

| 구성요소 | 설명 | 비유 |
|:---|:---|:---|
| Upgrade Handshake | HTTP 101 응답으로 프로토콜을 WS로 전환하는 초기 협상 | 일반 전화를 화상 통화로 전환하는 절차 |
| WebSocket Frame | 페이로드를 감싸는 경량 헤더(opcode, length, mask) 단위 | 편지 봉투 — 내용물 종류·크기를 표시 |
| Ping/Pong | 연결 생존 여부를 확인하는 제어 프레임 쌍 | 수화기에 대고 "여보세요?"로 상대 확인 |
| Close Frame | 정상 종료를 위한 상태 코드·사유를 교환하는 프레임 | 통화 종료 전 "끊겠습니다" 안내 |

> 요약: 업그레이드 핸드셰이크 후 경량 프레임 단위로 양방향 데이터를 교환함

## Ⅲ. 절차
```text
HTTP Upgrade -> 101 응답 -> 프레임 교환 -> Close 핸드셰이크
```
- 1단계: 클라이언트가 `Upgrade: websocket` 헤더를 포함한 HTTP GET 요청 전송
- 2단계: 서버가 101 Switching Protocols 응답으로 WS 연결 수립
- 3단계: 양측이 텍스트·바이너리 프레임을 전이중으로 송수신
- 4단계: 한쪽이 Close 프레임을 전송하면 상대가 Close 응답 후 TCP 연결 해제

> 요약: HTTP 업그레이드 → 연결 수립 → 프레임 교환 → 정상 종료 순서로 동작함

## Ⅳ. 문제점
- 연결 관리 부하: 동시 접속 수만 개 이상 시 서버 파일 디스크립터·메모리 소모가 급증함
- 프록시 호환성: L7 로드밸런서·리버스 프록시가 WS 업그레이드를 차단하는 경우 존재
- 재연결 처리: 네트워크 단절 시 클라이언트 측 자동 재연결·메시지 유실 복구 로직이 필요함

> 요약: 대량 연결 부하, 프록시 호환, 재연결 복구가 주요 문제임

## Ⅴ. 개선방안
1. 단기: 이벤트 루프 기반 서버(Netty, Node.js)로 C10K 수준 연결 수용
2. 중기: L7 프록시(Nginx, Envoy)의 WS 업그레이드 설정 표준화 및 헬스체크 적용
3. 장기: 클라이언트 재연결 SDK에 지수 백오프·메시지 시퀀스 기반 갭 복구 내장

> 요약: 이벤트 루프 서버, 프록시 표준 설정, 재연결 SDK로 각 문제에 대응함

## Ⅵ. 전망
- 발전 방향: WebTransport(HTTP/3 기반) 등 차세대 실시간 프로토콜로 확장 추세
- 기술사적 판단: 실시간 협업·IoT 제어 등 양방향 스트림 수요가 지속 증가함
- 기술사 제언: SSE·WebSocket·WebTransport를 유스케이스별로 선택하는 기준을 수립할 필요
