## Ⅰ. 개요
- **정의**: API 변경 시 기존 소비자 호환성을 유지하면서 새 기능을 제공하기 위한 버전 관리 전략
- **배경/필요성**: API 변경이 다수 소비자에게 동시 영향을 주므로 하위 호환성 보장 체계 필요
- **비유**: 도로 확장 공사 시 기존 차선(v1)은 유지하고 신규 차선(v2)을 추가하는 방식

| 출제 의도 | 반드시 짚을 핵심 | 감점 회피 포인트 |
|:---|:---|:---|
| API 진화 전략 수립 능력 | URI/Header/Query 방식 비교, SemVer 적용 | Breaking Change 정의·식별 기준 명시 |

> 요약: API 변경 시 소비자 호환성을 보장하면서 점진적으로 진화시키는 버전 관리 전략임

## Ⅱ. 구성요소
```text
API Consumer
    |
    v
+-- Version Selector --+
|   (URI/Header/Query)  |
+-----------+-----------+
            |
     +------+------+
     |      |      |
   v1 API v2 API v3 API
```

| 구성요소 | 설명 | 비유 |
|:---|:---|:---|
| URI Versioning | 경로에 버전 포함(`/v1/users`) — 명시적·캐시 친화적 | 도로 번호 |
| Header Versioning | Accept 헤더에 버전 명시 — URI 오염 없음 | 차량 번호판 |
| Query Versioning | 쿼리 파라미터로 버전 전달(`?version=2`) — 구현 간편 | 출구 번호 |

> 요약: URI·Header·Query 방식으로 버전을 선택하여 다중 API 버전을 병행 운영함

## Ⅲ. 절차
```text
변경 분류 --> 버전 결정 --> 병행 운영 --> 구버전 폐기
```
- 1단계: API 변경사항을 Breaking/Non-Breaking으로 분류
- 2단계: Breaking Change 시 새 버전 번호 할당, Non-Breaking 시 기존 버전 내 확장
- 3단계: 신·구 버전 API를 병행 운영하며 소비자에게 마이그레이션 기간 제공
- 4단계: 사용량 모니터링 후 구버전 Deprecation 공지·폐기(Sunset) 수행

> 요약: 변경 분류, 버전 결정, 병행 운영, 구버전 폐기 4단계로 API 진화 관리함

## Ⅳ. 문제점
- 버전 파편화: 다수 버전 병행 시 유지보수 코드 중복 — 운영 비용 선형 증가
- 폐기 시점 합의: 소비자별 마이그레이션 속도 상이 — 구버전 Sunset 시점 결정 곤란
- 하위 호환성 판단: Breaking Change 여부 식별 기준 모호 — 의도치 않은 호환성 파괴

> 요약: 버전 파편화, 폐기 시점 합의, 호환성 판단 모호성이 주요 문제임

## Ⅴ. 개선방안
1. 단기: 최대 동시 운영 버전 수 제한(예: N-1 정책)으로 파편화 억제
2. 중기: Sunset 헤더·Deprecation 정책을 SLA에 명시하여 폐기 시점 사전 합의
3. 장기: 명세 Diff 자동화 도구(oasdiff 등) 도입으로 Breaking Change 자동 식별

> 요약: 버전 수 제한, Sunset 정책 SLA화, 명세 Diff 자동화로 단계적 개선함

## Ⅵ. 전망
- 발전 방향: API Evolution 패턴(필드 추가만 허용)으로 버저닝 빈도 자체를 축소하는 추세
- 기술사적 판단: OpenAPI 명세(204 참조)와 결합한 계약 기반 버전 관리가 핵심임
- 기술사 제언: API Gateway에서 버전 라우팅을 중앙 관리하여 서비스 코드와 분리 권장
