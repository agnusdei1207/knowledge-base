# 📖 【암기용】 개념 완전 이해

## 한눈에
- **개요**: API의 기능이나 응답 구조가 변경될 때(특히 호환성이 깨질 때), 기존 클라이언트에 장애를 주지 않기 위해 새로운 버전의 API를 식별·제공하는 전략
- **왜 필요한가**: 모바일 앱 클라이언트는 서버가 업데이트되었다고 사용자가 즉시 업데이트하지 않는다. 하위 호환성이 깨진(Breaking Change) 변경을 배포하면 구버전 앱 사용자는 서비스 불능에 빠지기 때문에 필수적이다.
- **핵심 직관**: 식당(서버)이 메뉴판을 완전히 갈아엎을 때, 예전 메뉴판을 보고 주문하는 단골손님(구버전 앱)을 위해 임시로 '구 메뉴판 전용 창구(v1)'와 '신 메뉴판 창구(v2)'를 동시에 열어두는 것이다.

## 핵심 용어 정리

| 용어/표기 | 의미 | 비유·예 |
|:---|:---|:---|
| Breaking Change | 기존 클라이언트 로직을 망가뜨리는 하위 호환성 위반 변경 | "이름" 필드를 "first_name"과 "last_name"으로 분리 |
| Non-breaking Change | 기존 클라이언트에 영향이 없는 안전한 변경 | 새로운 옵션 필드(주소) 추가 |
| URI 버저닝 | 주소 경로(Path)에 직접 버전을 명시 | `/api/v1/users` |
| Header 버저닝 | HTTP 커스텀 헤더에 버전을 명시 (주소는 동일) | `X-API-Version: 2.0` |

## 깊이 이해
- **배경·문제의식**: MSA 도입과 애자일 배포로 API 변경 주기가 매우 짧아졌다. 클라이언트(모바일, B2B 파트너) 통제권이 서버에 없는 상황에서, 무분별한 API 수정은 대규모 장애로 직결된다. 이를 해결하기 위해 버전 통제 거버넌스가 필요하다.
- **작동 원리**: 서버는 코드나 인프라(API Gateway) 레벨에서 여러 버전의 엔드포인트를 라우팅한다. 버전을 식별하는 위치(URI, 파라미터, 헤더, 미디어 타입)에 따라 4가지 대표 전략이 나뉜다. 신버전(v2) 출시 시 구버전(v1)은 즉시 폐기하지 않고 '일몰(Sunset) 기간'을 두어 클라이언트가 마이그레이션할 시간을 확보한다.
- **비유**: 고속도로 톨게이트에서 예전 하이패스 단말기를 든 차를 위해 1번 차로(v1)를 유지하면서, 신형 하이패스용 2번 차로(v2)를 뚫고 서서히 1번 차로를 줄여나가는(Deprecation) 과정이다.
- **구체 예시**: URI 방식은 `/v1/orders`와 `/v2/orders`를 분리한다. 브라우저 캐싱과 구분이 직관적이다. 반면 Accept 헤더 방식은 `Accept: application/vnd.company.v2+json`을 사용해 URI의 순수성(REST 원칙)을 지킨다.
- **흔한 오해·주의점**: "사소한 필드 하나 추가해도 무조건 v2로 올려야 한다"는 오해다. 필드 추가 같은 Non-breaking Change는 버전을 올리지 않고 기존 v1에 수용해야 버전 파편화를 막을 수 있다. 버저닝은 최후의 수단이다.

## 연결 개념
- **RESTful API**: 리소스 중심 설계로 인해 버전 정보 위치(URI vs 헤더)에 대한 철학적 논쟁이 있는 영역
- **API Gateway**: 라우팅 룰을 통해 클라이언트 요청 버전을 동적으로 분기해주는 핵심 인프라
- **Deprecation Policy**: 오래된 버전의 API 사용을 중단하고 클라이언트를 전환시키는 라이프사이클 정책

# 📝 【답안용】 시험 답안 템플릿

## 핵심 인사이트 (3줄 요약)

> 1. **본질**: API 구조에 하위 호환성을 깨는(Breaking Change) 변경이 발생했을 때, 다중 버전을 동시 지원하여 클라이언트의 장애를 방지하는 거버넌스 전략이다.
> 2. **가치**: 서버와 클라이언트 배포 주기를 디커플링(Decoupling)하여 독립적 릴리스를 보장하고 무중단 서비스 진화를 지원한다.
> 3. **판단 포인트**: REST 아키텍처 원칙(헤더 방식)과 개발자 편의성(URI 방식) 간의 트레이드오프를 고려해 일관된 전략을 정립하고, 철저한 Sunset 정책으로 백엔드 유지보수 부채를 통제해야 한다.

## 출제 의도 및 답안 포인트

| 출제 의도 | 반드시 짚을 핵심 | 감점 회피 포인트 |
|:---|:---|:---|
| 버저닝이 필요한 시점과 목적 인지 | 호환성 파괴(Breaking Change) 시점, 배포 디커플링 | 단순 변경 시에도 무조건 버저닝을 해야 한다고 단정 |
| 4대 버저닝 전략 비교 분석 역량 | URI, 쿼리 파라미터, Custom 헤더, Accept 헤더 | 각 기법의 캐싱 제약과 구현 복잡도 차이 누락 |
| 전체 라이프사이클(폐기) 관리 역량 | Deprecation 및 Sunset 정책, API Gateway 라우팅 | 새 버전 출시 방안만 쓰고 구버전 폐기 정책(부채) 방치 |

> 요약: 4가지 전략의 장단점을 명확히 비교하고, 단순 버전 생성이 아닌 '하위 호환성 훼손 판별'부터 '일몰(Sunset)'까지의 생명주기 관리 방안을 제시해야 한다.

## Ⅰ. 개요 및 필요성

- 개요: API의 인터페이스(파라미터, 응답 스키마 등)가 기존과 호환되지 않게 변경될 때, 구버전과 신버전을 구분하여 동시 제공하는 통제 기법
- 배경: 모바일 앱과 B2B 파트너 등 백엔드 통제권 밖에 있는 클라이언트 파편화로 동시 업데이트(Lock-step 릴리스) 불가능
- 필요성: Breaking Change로 인한 구버전 클라이언트의 크래시(장애)를 예방하고, 백엔드의 지속적 진화와 무중단 배포 보장

---

## Ⅱ. 4대 API 버저닝 전략 (구조 비교)

```text
클라이언트 요청 식별 위치 -> API Gateway 분기 -> 해당 버전 컨트롤러 (v1 / v2)
  1. URI Path : /api/v1/users
  2. Query Str: /api/users?version=2
  3. Header   : X-API-Version: 2
  4. Content  : Accept: application/vnd.company.v2+json
```

| 기법 (위치) | 캡처 예시 | REST 원칙 부합도 |
|:---|:---|:---|
| 1. URI Path | `https://api.domain.com/v1/users` | 낮음 (버전은 리소스 식별자가 아님) |
| 2. Query Parameter | `/users?version=1.0` | 중간 (URI는 유지, 파라미터로 속성 취급) |
| 3. Custom Header | `X-API-Version: 2` | 높음 (리소스 URI 유지) |
| 4. Content Negotiation | `Accept: application/vnd.v1+json` | 가장 높음 (미디어 타입으로 정확히 분리) |

> 요약: 버전 식별자를 어디에 두느냐(URI vs 파라미터 vs 헤더)에 따라 4가지 기법으로 분류되며, 철학과 편의성 트레이드오프가 존재한다.

---

## Ⅲ. 절차 흐름도 (API 생명주기 관리)

```text
변경 식별 -> Breaking Change 판정 -> 신버전 개발 및 배포 -> Deprecation 공지 -> Sunset(폐기)
```

- 1단계 [변경 영향도 판정]: 필드 삭제/타입 변경 등 하위 호환성이 깨지는 Breaking Change인지 판별 (필드 단순 추가는 버저닝 불필요)
- 2단계 [신버전 라우팅 배포]: API Gateway에 신규 버전 식별자 룰을 추가하고 v2 백엔드 컨트롤러 배포
- 3단계 [구버전 Deprecation]: 구버전 응답 헤더에 `Deprecation: true` 및 전환 가이드(Link 헤더) 포함하여 클라이언트 경고
- 4단계 [모니터링 및 Sunset]: 구버전 트래픽 비중이 목표치(예: 1% 미만) 이하로 떨어지면 해당 엔드포인트 영구 폐기(410 Gone)

> 요약: 신버전을 무한정 늘리면 코드 부채가 되므로, 반드시 호환성 판단부터 트래픽 모니터링 기반의 폐기(Sunset) 절차가 수반되어야 한다.

---

## Ⅳ. 특징
- 라우팅 명확성 (URI 기법): 브라우저 캐싱과 CDN 설정이 직관적이고 외부 개발자가 눈으로 쉽게 식별 가능하여 Public API에 유리함
- 리소스 순수성 (Accept 헤더): 리소스(`/users`)의 식별과 표현(버전)을 철학적으로 완벽히 분리하지만, 테스트와 브라우저 직접 호출이 어려움
- 코드 유지보수 부채: 구버전을 장기간 유지할 경우, DB 스키마 분기 처리와 백엔드 코드의 복잡도(If문 지옥)가 급격히 상승함

> 요약: URI 방식은 사용성과 캐싱에 직관적이나 철학적 흠결이 있고, 헤더 방식은 아키텍처 원칙에 충실하나 테스트 편의성이 떨어진다.

## Ⅴ. 심화 비교 및 적용 판단

| 비교 축 | URI Path 버저닝 | Content Negotiation 버저닝 | 선택 기준 |
|:---|:---|:---|:---|
| 접근성·편의성 | 브라우저 주소창 직접 테스트 가능 | 별도 클라이언트 툴(Postman 등) 헤더 세팅 필수 | 외부 파트너 제공 vs 내부 철저한 규약 |
| 브라우저 / CDN 캐싱 | 기본 캐싱 룰 완벽 호환 | `Vary: Accept` 설정 등 추가 복잡도 발생 | 대용량 읽기 위주 캐싱 중요도 |
| 실제 채택 트렌드 | Twitter, Stripe, GitHub(v3) 등 | GitHub(v4 에서는 URI 통합/GraphQL) 등 소수 | 범용적 성공 사례 (URI 승) |

> 요약: 실무 관점에서는 REST 순수성보다 개발자 경험(DX)과 인프라 캐싱이 압도적으로 중요하므로 URI Path 방식을 1순위로 채택한다.

**리스크·대응 (기본은 불릿):**
- DB 스키마 호환성 충돌: v1과 v2가 같은 DB를 쓰면서 필드 타입이 충돌 → CQRS 분리 또는 View 생성, 혹은 애플리케이션 레벨의 DTO 매퍼 격리
- 구버전 섀도우 트래픽 방치: 아무도 쓰지 않는데 인프라 자원을 점유 → API Gateway에서 버전별 트래픽 지표 추출 및 일정 기간(6개월) 후 410 에러 강제 전환
- 버전 파편화로 인한 장애: 너무 잦은 버저닝으로 클라이언트 파편화 → GraphQL 도입 검토(버전 없는 API) 또는 확장 가능한 JSON 구조 설계 원칙화

**도입 후 점검 지표 (기본은 불릿):**
- 운영/효율: 버전별 분당 요청 수(RPM), 구버전 Deprecation 도달 비율
- 품질/장애: Breaking Change 사전 검지율(CI/CD Pipeline Lint 100% 탐지), 신/구 버전 공존 기간(Time-to-Sunset)

## Ⅵ. 실무 적용 및 결론

**적용 방안 3개:**
1. 하이브리드 라우팅 적용: 외부 파트너용 Public API는 직관적인 URI 버저닝(`/v1/`)을, 내부 마이크로서비스 간 통신은 Custom Header 버저닝을 분리 적용
2. API Gateway 기반 동적 라우팅: 클라이언트 요청 시 Gateway 단에서 Header나 URI를 분석하여, 백엔드의 별도 K8s Pod(v1 배포본과 v2 배포본)로 물리적 트래픽 격리
3. OpenAPI 기반 Contract Testing: CI/CD 파이프라인에서 Swagger/OpenAPI 명세의 구버전과 신버전 Diff를 분석하여, 인가되지 않은 하위 호환성 위반(Breaking Change) 배포 강제 차단

**결론 (2줄):**
- 기술사 판단: REST 아키텍처의 철학적 우수성(헤더 방식)보다 클라이언트 개발자 경험(DX)과 CDN 캐싱 최적화가 더 큰 비즈니스 가치를 지니므로 URI 버저닝을 기본 표준으로 권장한다.
- 향후 방향: 버저닝 오버헤드 자체를 근본적으로 제거하기 위해, 단일 엔드포인트에서 필드 단위의 Deprecation 통제가 가능한 GraphQL 아키텍처로 점진적 전환을 고려해야 한다.
