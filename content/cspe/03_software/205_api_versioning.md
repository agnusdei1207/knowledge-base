## 미리 알고가기

- API 버전은 소비자가 기대하는 요청·응답·오류·보안 계약의 호환 경계를 식별함
- 연산·선택 필드 추가 같은 호환 변경은 기존 버전에 반영하고 필드 삭제·이름·타입 변경은 새 버전에서 제공함
- 버전 전달 위치는 URI Path·Header/Media Type·Query Parameter이며 Gateway·Cache·SDK가 해석할 위치와 같아야 함
- 새 버전은 구버전과 병행 운영하고 소비자별 호출량이 종료 기준에 도달한 뒤 폐기해야 함
- 버전 번호는 변경 크기를, 날짜는 계약 기준 시점을 표현하므로 한 API 안에서 식별 규칙을 고정해야 함

## 작성 근거(검토용)

- API 버저닝은 호환성 분류, 버전 식별·전달, 병행 라우팅, 소비자 전환, 폐기 정책으로 설명함
- 비교표는 Path·Header·Query 방식의 가시성·라우팅·캐시·문서·도구·적합 조건을 대비함
- 파트너 API와 내부 모델 API는 구버전 트래픽·소비자 전환율·계약 실패율로 검증함

## Ⅰ. 개요

- **정의/개념**: API 버저닝은 호환되지 않는 계약을 별도 식별자로 분리하고 구·신 구현을 병행해 소비자가 정해진 기간에 전환하도록 관리하는 인터페이스 진화 전략임
- **배경/필요성**: 제공자의 스키마·동작 변경이 이미 배포된 클라이언트를 중단하지 않도록 호환 변경과 파괴적 변경을 판정하고 라우팅·지원·폐기 경계를 명시해야 함

## Ⅱ. 특징

- 기존 선택 필드·연산 추가는 호환 변경으로, 필드 삭제·이름·타입 변경과 필수 입력 추가는 파괴적 변경으로 분류함
- Major 번호 또는 날짜 식별자를 Path·Header·Query 중 한 계약 위치에 전달함
- API Gateway가 버전 식별자를 구현·Schema·정책에 연결하고 미지원 버전의 오류를 명시함
- 구·신 버전의 계약 시험과 소비자 시험을 분리해 같은 요청의 응답 차이와 마이그레이션 결함을 확인함
- 소비자 식별·버전별 호출량·오류율을 수집하고 폐기 공지·종료일·대체 연산을 제공함
- 캐시가 버전별 표현을 섞지 않도록 URI 또는 Vary를 캐시 키에 반영함

## Ⅲ. 종류 및 비교

| 판단 기준 | URI Path | Header·Media Type | Query Parameter |
|:---|:---|:---|:---|
| 전달 예 | `/v2/orders` | `API-Version: 2`·버전 Media Type | `/orders?api-version=2` |
| 호출 가시성 | 링크·로그·브라우저 주소에 노출 | 요청 Header를 확인해야 식별 | URL Query에 노출 |
| 라우팅 기준 | Gateway Path 규칙 | Header·Accept 협상 규칙 | Query 값 규칙 |
| 캐시 분리 | URI가 버전별 캐시 키를 분리 | Vary·캐시 키에 Header 포함 필요 | Query를 포함한 캐시 키 필요 |
| 문서·SDK | 버전별 Base URL로 분리 | 공통 URI와 버전 Header를 생성 | 공통 URI와 필수 Query를 생성 |
| 적합 조건 | 공개 API의 명시적 Major 경계 | URI 유지와 표현·계약 협상 필요 | 날짜 버전·플랫폼 정책을 요청마다 지정 |

> 요약: Path는 URI, Header는 요청 메타데이터, Query는 매개변수로 버전을 전달하며 라우팅·캐시·SDK가 같은 위치를 해석해야 함.

## Ⅳ. 구성요소 및 구조

| 구성요소 | 설명 |
|:---|:---|
| 호환성 정책 | 허용할 추가 변경과 새 버전이 필요한 파괴적 변경을 정의함 |
| 버전 식별자 | Major 번호·날짜와 Path·Header·Query 전달 위치를 정함 |
| Gateway·Router | 식별자를 구현·Schema·인증·제한 정책에 연결함 |
| 버전별 계약·구현 | 구·신 요청·응답·오류 계약과 변환 계층을 병행 운영함 |
| 소비자 목록·Telemetry | 소비자별 버전 호출량·오류·마지막 사용 시점을 기록함 |
| 폐기 정책 | 공지 시점·지원 기간·종료일·대체 버전과 실패 응답을 정함 |

```text
Client -> Version Identifier -> API Gateway -> v1 Contract·Service
                                      └-----> v2 Contract·Service
```

> 요약: 버전 식별자가 Gateway의 계약·구현 경계를 선택하고 소비자 Telemetry가 구버전 종료 판단을 제공함.

## Ⅴ. 원리 및 절차 흐름도

```text
변경 분류 -> 새 계약 정의 -> 병행 배포 -> 소비자 전환 -> 구버전 폐기
```

1. **변경 분류**: 필드·연산·오류·보안 변경이 기존 소비자 계약을 깨는지 판정함
2. **새 계약 정의**: 파괴적 변경이면 새 식별자와 요청·응답 Schema·변환 규칙을 정의함
3. **병행 배포**: Gateway가 구·신 버전을 각각 라우팅하고 계약·회귀 시험을 수행함
4. **소비자 전환**: 변경 안내·SDK·시험 환경을 제공하고 소비자별 호출 버전을 추적함
5. **구버전 폐기**: 종료 기준을 충족하면 공지한 시점에 라우팅을 중단하고 대체 버전을 안내함

> 요약: 파괴적 변경만 새 버전으로 분리하고 병행 운영 중 소비자 전환을 확인한 뒤 구버전을 종료함.

## Ⅵ. 실무 사례

1. 파트너 주문 API는 URI Major 버전을 병행하고 구버전 트래픽 비율·소비자 전환율을 확인함
2. 내부 모델 API는 날짜 Header 버전과 계약 시험을 적용하고 미지원 버전 요청률·계약 실패율을 확인함

## Ⅶ. 결론

- API 버저닝은 파괴적 변경 판정·식별자 전달·캐시 분리·소비자 전환·폐기 기준을 하나의 정책으로 운영해야 함
