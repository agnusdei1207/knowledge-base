## 핵심 인사이트 (3줄 요약)
- 백엔드 개발자가 API 스펙을 바꿨을 때, 구형 스마트폰 앱(업데이트 안 한 사용자)이 에러를 뿜으며 죽는 대참사를 막기 위해 **"기존 API(v1)를 그대로 둔 채 새로운 API(v2)를 병렬로 추가하는 하위 호환성 유지 전략"**.
- URL 주소에 넣기(`/v1/users`), HTTP 헤더에 넣기(`X-API-Version: 1`), 쿼리 스트링에 넣기(`?version=1`) 등 다양한 방법이 있으며, 실무에서는 **URL 기반 버저닝**이 가장 직관적이고 널리 쓰임.
- "한 번 배포된 API는 영원한 계약(Contract)이다"라는 마이크로서비스 설계의 철학을 강제하며, 구버전 강제 종료(Deprecation) 정책과 함께 설계되어야 서버 유지보수 지옥을 피할 수 있음.
---
## Ⅰ. 개요 및 필요성
- **개요**: 클라이언트 측에 영향을 주지 않으면서 API의 변경 사항(구조, 데이터 타입 등)을 관리하고 배포하기 위해 API에 식별 가능한 버전을 부여하는 기법.
- **필요성**: 회원가입 API(`/users`)를 만들 때 `name` 필드를 필수로 받음. 근데 1년 뒤 기획팀이 "이름 대신 `firstName`과 `lastName`으로 쪼개서 받자!"라고 함. 개발자가 무심코 백엔드 API를 바꿈. ➡️ 다음 날, 앱스토어에서 최신 앱으로 업데이트 안 한 수백만 명의 스마트폰에서 회원가입이 전부 터짐(장애 발생). **"아, 구형 앱을 위한 옛날 API와 신형 앱을 위한 최신 API를 동시에 살려둬야 하는구나!"**
---
## Ⅱ. 아키텍처 및 핵심 원리
- **1. URL 방식 (URI Path Versioning)**:
  - 주소 자체에 버전을 박아버림.
  - `GET /v1/users` (구형 앱이 호출)
  - `GET /v2/users` (신형 앱이 호출)
  - **장점**: 눈에 제일 잘 띔. 브라우저에서도 바로 테스트 가능. (실무 표준).
- **2. 헤더 방식 (Header / Custom Request Header)**:
  - 주소는 `GET /users`로 똑같음. 대신 HTTP 헤더에 남몰래 적어서 보냄.
  - `Accept-Version: v1` 또는 `X-API-Version: 2`
  - **장점**: 주소가 안 더러워짐(REST 철학에 부합). **단점**: 눈에 안 보여서 디버깅이 빡셈.
- **3. 미디어 타입 방식 (Media Type / Content Negotiation)**:
  - 헤더 방식의 진화형. HTTP 표준인 `Accept` 헤더를 활용함.
  - `Accept: application/vnd.myname.v1+json`
  - GitHub API가 이 방식을 썼으나, 개발자들이 너무 어려워해서 결국 URL/헤더 방식으로 회귀함.

```text
[ API 버저닝을 통한 무중단 업데이트 시나리오 ]

 📱 구형 앱 (v1) ----요청----> [ API Gateway ] 
                                  ┣━━ 분기 ━━▶️ [ 백엔드 서버 v1 (구형 로직: name 처리) ]
 📱 신형 앱 (v2) ----요청---->      ┗━━ 분기 ━━▶️ [ 백엔드 서버 v2 (신형 로직: firstName 처리) ]

 * 구형 앱 사용자가 앱 업데이트를 할 때까지(약 3~6개월) 서버를 두 벌 다 살려둔다.
 * 6개월 뒤 구형 앱이 1% 미만으로 떨어지면? ➡️ 강제 업데이트 알림을 띄우고 v1 서버를 죽임(Deprecation).
```

## Ⅲ. 비교 및 연결
| 버저닝 방식 | 구현 방법 | 장점 | 단점 | 실무 사용 |
|---|---|---|---|---|
| **URL 경로** | `/v1/users` | 제일 직관적, 문서화(Swagger) 쉬움 | URL이 자주 바뀌어 캐싱 관리가 복잡 | **대세 (Stripe, Twilio 등)** |
| **커스텀 헤더** | `X-Version: 1` | 주소가 깔끔함 | 프론트엔드 코드 작성이 귀찮아짐 | 보통 |
| **쿼리 파라미터**| `/users?v=1` | 브라우저 테스트 쉬움 | REST API 자원(URL) 규칙을 깸 | 거의 안 씀 |

## Ⅳ. 실무 적용 및 기술사 판단
- **Major vs Minor 버저닝 전략**: 실무에서 `v1.2`처럼 소수점을 URL에 넣는 것은 안티 패턴임. API 버저닝은 오직 **호환성이 깨지는 변경(Breaking Change)**일 때만 `v1`에서 `v2`로 올려야 함. 단순히 필드를 하나 '추가'하는 것은 구형 앱을 망가뜨리지 않으므로(Non-breaking), 굳이 버전을 올릴 필요 없이 그냥 v1에 덧붙여도 됨. 기술사는 하위 호환성의 정의를 엄격하게 세워야 서버 버전의 파편화를 막을 수 있음.
- **API 게이트웨이 레벨의 라우팅**: 백엔드 코드 안에 `if (version == 1) { ... } else if (version == 2) { ... }` 같이 스파게티 코드를 짜면 유지보수 지옥이 됨. 올바른 클라우드 네이티브 아키텍처는 **API Gateway(Kong, Nginx) 단에서 URL의 `/v1/` 텍스트를 보고 알아서 구형 K8s 파드로 트래픽을 분기(Routing)**시켜 주는 것임. 백엔드 앱(파드) 자체는 자기가 몇 버전인지 몰라도 되게 디커플링(Decoupling) 해야 함.

## Ⅴ. 기대효과 및 결론
- 한 번 스토어에 올라가면 내 마음대로 지울 수 없는 모바일 앱의 태생적 한계를 서버 단에서 우아하게 커버해 줌.
- "기존 사용자를 버리지 않으면서도 시스템은 끝없이 진화해야 한다"는 백엔드 설계의 근본적인 모순을 해결하는, 마이크로서비스 설계의 필수 생존 규약임.

### 👶 어린이를 위한 3줄 비유 설명
1. 게임기(클라이언트)가 옛날 거면 네모 팩(v1 API)만 들어가고, 최신 거면 동그란 팩(v2 API)이 들어가요.
2. 게임회사(서버)가 갑자기 모양을 동그랗게 바꿔버리면 옛날 게임기 가진 친구들은 게임을 못 하게 되잖아요?
