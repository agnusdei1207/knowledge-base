## Ⅰ. 개요
- **정의**: 타임스탬프 기반 시간 순서 데이터의 입력·조회·집계에 최적화된 데이터베이스
- **배경/필요성**: IoT 센서·모니터링 등 시간축 데이터가 폭증하며 범용 DB로는 처리 한계가 있음
- **비유**: 날짜별로 정리된 일기장처럼 시간 순서로만 기록·검색하는 전용 장부와 유사함

| 출제 의도 | 반드시 짚을 핵심 | 감점 회피 포인트 |
|:---|:---|:---|
| 시계열 데이터 특성과 저장 전략 | 시간축 압축·다운샘플링·TTL 정책 | 범용 RDBMS 시계열 처리와의 차이 서술 필요 |

> 요약: 시간 순서 데이터에 특화된 쓰기·집계 최적화 DB임

## Ⅱ. 구성요소
```text
Data Source --> Ingestion Engine --> Time-Partitioned Storage --> Query Engine
                                         |
                                    Compaction / Retention
```

| 구성요소 | 설명 | 비유 |
|:---|:---|:---|
| Ingestion Engine | 대량 시계열 포인트를 고속 버퍼링·배치 삽입하는 계층 | 고속 접수 창구 |
| Time-Partitioned Storage | 시간 범위별로 분할 저장하는 컬럼형 스토리지 | 월별 파일 캐비닛 |
| Compaction/Retention | 오래된 데이터를 압축·다운샘플링·삭제하는 정책 엔진 | 오래된 서류 폐기 규정 |
| Query Engine | 시간 범위 필터·집계 함수에 최적화된 조회 엔진 | 기간별 통계 조회기 |

> 요약: 고속 수집-시간 분할 저장-보존 정책-시간 범위 조회 구조로 구성됨

## Ⅲ. 절차
```text
데이터 수집 --> 시간 파티션 적재 --> 압축/다운샘플링 --> 시간 범위 조회
```
- 1단계: 센서·메트릭 데이터를 타임스탬프와 함께 배치 수집
- 2단계: 시간 범위별 파티션에 컬럼 기반으로 적재
- 3단계: TTL 정책에 따라 오래된 데이터를 다운샘플링·압축
- 4단계: 시간 범위 필터와 집계 함수로 분석 쿼리 수행

> 요약: 수집-적재-압축-조회의 시간축 중심 파이프라인으로 동작함

## Ⅳ. 문제점
- 임의 갱신 비효율: Append-only 구조로 과거 데이터 수정 시 오버헤드가 큼
- 고카디널리티 문제: 태그 조합 폭발 시 인덱스 크기가 급증하여 조회 성능 저하됨
- 다차원 분석 한계: 시간축 외 복잡한 조인·서브쿼리 지원이 제한적임

> 요약: 갱신 비효율, 카디널리티 폭발, 다차원 분석 제약이 주요 과제임

## Ⅴ. 개선방안
1. 단기: 임의 갱신 → 변경분만 별도 오버레이 계층에 기록 후 병합
2. 중기: 고카디널리티 → 태그 설계 가이드라인 수립 및 인덱스 샤딩 적용
3. 장기: 다차원 분석 → 데이터 레이크(138 참조) 연계로 복합 분석 지원

> 요약: 오버레이 기록, 태그 설계, 레이크 연계로 단계적 개선함

## Ⅵ. 전망
- 발전 방향: AI 워크로드와 결합하여 실시간 이상 탐지·예측 분석 통합이 확대됨
- 기술사적 판단: IoT·옵저버빌리티 확산으로 시계열 DB 설계 역량 수요가 증가함
- 기술사 제언: 보존 기간·다운샘플링 정책을 비즈니스 SLA와 연계하여 설계할 것을 제언함
