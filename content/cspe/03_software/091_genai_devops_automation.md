# 📖 【암기용】 개념 완전 이해

> 목적: 생성형 AI 기반 DevOps 자동화를 코드 작성 이후의 빌드, 테스트, 배포, 운영 분석 자동화로 이해하게 만든다. 시험 답안 양식이 아니라, 이해를 위한 설명이다.

## 한눈에
- **개요**: GenAI DevOps 자동화는 **LLM**이 코드 변경, CI/CD 로그, 운영 메트릭·트레이스를 해석해 테스트·장애 대응·배포 문서의 초안을 생성하는 **AIOps 결합형 자동화**다.
- **왜 필요한가**: 배포 빈도와 마이크로서비스 수가 늘면 파이프라인 실패 로그, 알림, 메트릭이 사람이 다 읽기 어려운 양으로 쌓인다. 원인 파악이 늦어질수록 장애 복구 시간(MTTR)이 길어진다.
- **핵심 직관**: 관제센터에서 AI가 CCTV·센서 이벤트를 요약해 상황판을 띄우고, 실제 출동 여부는 지휘관(사람)이 결정하는 구조다. AI는 "분석과 제안"까지, "실행"은 승인받은 사람만 한다.

## 핵심 용어 정리 (내부에 등장하는 것들)

| 용어 | 의미 | 비유 |
|:---|:---|:---|
| CI/CD | 코드 변경을 자동으로 빌드·테스트·배포하는 파이프라인 — GenAI DevOps가 다루는 대상 | 상위 키워드 |
| AIOps | 로그·메트릭·트레이스를 AI/통계로 분석해 운영 이상을 탐지·요약하는 접근 | 상위 키워드 |
| Runbook | 특정 장애 유형이 발생했을 때 따라야 할 조치 절차서 | 소방 대응 매뉴얼 |
| RBAC(Role-Based Access Control) | 역할에 따라 실행 가능한 명령을 제한하는 접근 통제 모델 | 등급별 출입카드 |
| Approval Gate(승인 게이트) | 실행 직전 사람의 승인을 반드시 거치게 만드는 통제 지점 | 검문소 |
| Audit Log(감사로그) | 누가·언제·무엇을 실행했는지 남기는 불변 기록 | 블랙박스 |
| DORA 4대 지표 | 배포빈도·변경 리드타임·변경 실패율·MTTR로 DevOps 성과를 측정하는 지표 세트 | 성적표 |
| MTTR(Mean Time To Restore) | 장애 발생부터 정상 복구까지 걸린 평균 시간 | 응급실 처치 시간 |
| Hallucination(환각) | 로그 근거 없이 그럴듯한 원인·조치를 만들어내는 오류 | 근거 없는 추측성 진단 |

## 깊이 이해

### 왜 필요했나 (배경)
- 배포를 하루 한 번 하던 조직이 하루 수십~수백 번 배포하고, 서비스 하나가 수십~수백 개 마이크로서비스로 쪼개지면 실패 로그·알림 건수도 그만큼 는다. 사람이 로그를 한 줄씩 읽어 원인을 찾는 방식은 이 규모에서 한계에 부딪힌다.

### 작동 원리 — 분석과 실행의 분리
- AI 어시스턴트는 Git diff(무엇이 바뀌었는지), 이슈·티켓(왜 바뀌었는지), CI 로그(무엇이 실패했는지), 메트릭·트레이스(운영에서 무슨 일이 났는지)를 입력받아 실패 원인 후보, 영향받는 테스트, 조치용 runbook 초안을 생성한다.
- 이 결과는 곧바로 실행되지 않는다. Approval Gate(PR 승인, ChatOps 승인 등)를 거쳐야 하고, RBAC로 "누가 이 명령을 실행할 권한이 있는지"를 제한하며, 실행 이력은 전부 Audit Log에 남는다. "분석은 AI, 실행은 승인된 사람"이라는 구조가 핵심이다.

### 구체 시나리오로 이해하기 — 배포 후 오류율 급등
- 배포 직후 5xx 오류율이 평소 0.1%에서 8%로 뛰었다고 하자. AI는 최근 CI 로그에서 실패한 테스트 3건과 최근 변경된 의존성 버전 충돌 로그를 근거로 "의존성 버전 불일치가 원인 후보"라는 요약과 함께, 이전 정상 버전으로 되돌리는 rollback runbook을 제안한다.
- 배포 권한이 있는 담당자가 이 제안과 근거 로그를 확인하고 승인하면 롤백이 실행되고, 오류율 급등 감지부터 롤백 완료까지 걸린 시간(예: 10:00 감지 → 10:10 완료)이 MTTR 10분으로 기록된다. AI가 원인 파악 시간을 줄여준 만큼 MTTR이 단축되는 구조다.

### DORA 지표로 효과를 검증하는 법
- DORA(DevOps Research and Assessment)는 배포빈도, 변경 리드타임(코드 커밋~배포까지 시간), 변경 실패율, MTTR 4개를 핵심 지표로 삼는다. 예를 들어 AI 도입 전 리드타임이 평균 1일이었다가 로그 분석·테스트 영향도 제안으로 4시간으로 줄었다면, 이는 "AI가 원인 파악과 영향 범위 판단 시간을 줄였다"는 근거가 된다.
- 반대로 MTTR·변경 실패율이 개선되지 않으면, 아무리 자동화 건수가 늘어도 실질 효과가 없다는 뜻이므로 도입 판단은 자동화 횟수가 아니라 이 4개 지표로 해야 한다.

### 리스크와 흔한 오해
- **오조치 리스크**: AI가 로그의 우연한 상관관계를 인과관계로 착각해("이 로그가 뜬 직후 항상 재시작했으니 원인이다") 잘못된 조치를 제안할 수 있다. 그래서 제안에는 반드시 근거 로그·메트릭 링크를 남기게 하고, 사후에 postmortem으로 채택된 제안의 실제 성공률을 추적한다.
- **오해**: "자동화 = 무승인 배포"가 아니다. AI가 만드는 것은 조치 "제안"이며, RBAC와 Approval Gate 없이 AI가 직접 프로덕션 명령을 실행하게 하는 것은 권한 오남용 사고로 이어진다.

## 연결 개념
- AI 코드 생성 — 코드 작성 단계의 LLM 활용이 배포 이후 운영 단계로 확장된 것이 이 개념
- AIOps — 로그·메트릭·트레이스 기반 운영 분석이라는 더 넓은 상위 분야
- Platform Engineering IDP — 이 자동화가 실제로 얹히는 표준 배포·관측 경로

# 📝 【답안용】 시험 답안 템플릿

> 목적: 시험장에서 25분에 그대로 쓰는 답안 양식. 작성방식(추상표현 금지·수치·도식·문제유형 전환)을 엄격히 지킨다.
> 핵심: GenAI DevOps는 파이프라인 자동화 효과와 함께 hallucination, 권한 오남용, 변경 승인, 감사로그를 함께 써야 한다.

## 핵심 인사이트 (3줄 요약)

> 1. **본질**: GenAI DevOps 자동화는 LLM이 코드 변경, 테스트, CI/CD 로그, 운영 데이터를 해석해 DevOps 작업 초안을 생성하는 체계이다.
> 2. **가치**: 테스트 생성, 실패 원인 요약, 릴리스노트 작성, 장애 triage 시간을 줄여 배포 리드타임과 MTTR을 개선한다.
> 3. **판단 포인트**: AI의 제안은 승인된 파이프라인과 RBAC 안에서만 실행하고, 변경 이력과 감사로그를 남겨야 한다.

## 출제 의도 및 답안 포인트

| 출제 의도 | 반드시 짚을 핵심 | 감점 회피 포인트 |
|:---|:---|:---|
| DevOps 자동화 이해 확인 | CI/CD, 테스트, 로그 분석, runbook | AI 챗봇 도입만으로 설명하지 않음 |
| 운영 리스크 판단 확인 | hallucination, 권한, 승인, 감사 | 무인 배포를 기본값으로 쓰지 않음 |
| 성과 측정 역량 확인 | DORA, MTTR, change failure rate | 자동화 건수만 성과로 제시하지 않음 |
> 요약: GenAI DevOps 답안은 개발·배포·운영 자동화와 통제·감사 체계를 함께 제시해야 한다.

## Ⅰ. 개요 및 필요성

- 개요: GenAI DevOps는 LLM 기반 운영 자동화이다.
- 배경: 서비스 수와 배포 빈도 증가로 테스트 작성, 로그 분석, 장애 triage, 릴리스 문서 작성 시간이 커진다.
- 필요성: CI/CD 로그, Git diff, metric, trace를 LLM이 요약하되 배포 승인, RBAC, 감사로그로 실행 권한을 통제해야 한다.

---

## Ⅱ. 구조 및 구성요소

```text
Code/Issue/Diff -> LLM DevOps Assistant -> Test/CI Suggestion
Log/Metric/Trace -> Incident Summary -> Runbook Candidate
Policy/RBAC -> Approval Gate -> Audit Log
```

| 구성요소 | 역할 | 산정 포인트 |
|:---|:---|:---|
| Context Source | 코드·이슈·로그·메트릭 제공 | 민감정보 마스킹 |
| LLM Assistant | 테스트·원인·조치 초안 생성 | 근거 링크 포함 |
| Approval Gate | 실행 권한 통제 | PR, CAB, ChatOps 승인 |
| Audit Log | 변경·명령 이력 보존 | 누가, 언제, 무엇을 기록 |
> 요약: GenAI DevOps는 AI 분석 계층과 정책·승인·감사 계층을 분리해 구성한다.

---

## Ⅲ. 동작원리 및 흐름도

```text
변경 발생 -> AI가 테스트 영향도 분석 -> CI 파이프라인 실행
-> 실패 로그 요약 -> 수정/롤백 제안 -> 사람 승인
-> 배포/복구 실행 -> DORA·MTTR 지표 측정
```

| 단계 | 처리 내용 | 검증 기준 |
|:---:|:---|:---|
| 1 | 코드 변경과 이슈 문맥 수집 | 관련 파일·티켓 링크 |
| 2 | 테스트 영향도와 파이프라인 제안 | 추천 테스트 실행률 |
| 3 | CI 실패·운영 로그 요약 | 근거 로그 라인 링크 |
| 4 | 조치안 승인 후 실행 | RBAC·승인 기록 |
| 5 | DORA·MTTR 지표 반영 | lead time, CFR, MTTR |
> 요약: AI는 분석과 제안을 담당하고 실행은 승인 게이트와 감사로그를 거친다.

## Ⅳ. 특징

| 구분 | 기존 DevOps 자동화 | GenAI DevOps 자동화 | 수치·판단 기준 |
|:---|:---|:---|:---|
| 자동화 범위 | 스크립트·파이프라인 실행 | 로그 해석·테스트 제안·문서 생성 | MTTR 20% 단축 목표 |

| 통제 | CI 정책 | AI 권한·승인·감사 추가 | RBAC 위반 0건 |
| 한계 | 해석 자동화 제한 | 환각·오조치 리스크 | 사람 승인 단계 유지 |
> 요약: GenAI DevOps는 비정형 운영 정보를 해석하지만 실행 권한은 승인 체계 안에 묶어야 한다.

## Ⅴ. 심화 비교 및 적용 판단

| 구분 | 기존/대안 | 본 키워드 | 선택 기준 |
|:---|:---|:---|:---|

| 비용/규모 | 스크립트 유지비 | 모델 비용+보안 통제 | 월 장애·배포 이벤트 다수 |
| 운영/위험 | 운영자 해석 의존 | AI 제안과 사람 승인 | 고위험 변경은 수동 승인 |
| 품질 | 사후 원인 분석 | 테스트 영향도 선제 제안 | change failure rate 개선 |
> 요약: GenAI DevOps는 데이터가 충분하고 승인·감사 체계가 있는 조직에서 적용 가치가 크다.

| 리스크 | 원인 | 대응 방안 | 확인 지표 |
|:---|:---|:---|:---|
| 오조치 | 로그 환각·상관관계 오판 | 근거 링크와 승인 필수 | 잘못된 조치 건수 |
| 권한 오남용 | AI 명령 실행 권한 과다 | least privilege RBAC | 권한 위반 0건 |
| 정보 유출 | 로그·비밀값 prompt 포함 | 마스킹·secret scan | 노출 이벤트 0건 |
| 자동화 편향 | 추천만 반복 수용 | postmortem 검토 | AI 제안 채택 후 실패율 |
> 요약: 운영 자동화 리스크는 근거 제시, 최소권한, 민감정보 마스킹, 사후검토로 통제한다.

| 점검 항목 | 목표 기준 | 측정 방법 |
|:---|:---|:---|
| 배포 리드타임 | 20% 단축 | DORA lead time |
| MTTR | 30% 단축 | incident tracker |
| 변경 실패율 | 15% 이하 | deployment metric |
| 감사성 | AI 실행 이력 100% | audit log |
> 요약: 도입 성과는 DORA 지표와 감사로그 완전성으로 검증한다.

## Ⅵ. 실무 적용 및 결론

**적용 방안 3개:**
1. CI 로그 요약, 테스트 영향도 분석, 릴리스노트 생성부터 파일럿을 시작하고 운영 명령 실행은 제외함.
2. AI 제안에는 근거 로그·메트릭 링크를 필수로 포함하고 배포·롤백은 RBAC와 사람 승인 후 실행함.
3. DORA lead time, MTTR, change failure rate, AI 제안 채택 후 실패율을 4주 단위로 측정함.

**결론 (2줄):**
- 기술사 판단: 로그·이슈·runbook 데이터가 축적된 조직은 GenAI DevOps를 적용하고, 승인·감사 체계가 없으면 분석 보조부터 시작함.
- 향후 방향: GenAI DevOps는 AIOps, ChatOps, Policy as Code와 결합해 통제 가능한 운영 자동화로 발전함.
