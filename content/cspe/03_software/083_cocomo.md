# 📖 【암기용】 개념 완전 이해

> 목적: COCOMO를 규모(LOC) 기반 회귀식과 비용 동인 보정으로 공수·기간을 추정하는 경험적 모델로 완전히 이해하게 만든다. 시험 답안 양식이 아니라, 이해를 위한 설명이다.

## 한눈에
- **개요**: COCOMO(COnstructive COst MOdel)는 과거 프로젝트 실적 데이터로 도출한 회귀식에 예상 코드량(KLOC)을 대입해 **개발 공수(Person-Month)와 개발 기간을 산출하는 경험적(실증적) 소프트웨어 비용 산정 모델**이다.
- **왜 필요한가**: 요구사항조차 확정되지 않은 프로젝트 초기 단계에서 일정·인력·예산을 숫자로 제시해야 하는데, 담당자 감(感)에만 의존하면 항상 과소추정 쪽으로 치우쳐 후반 야근과 품질 저하로 이어진다.
- **핵심 직관**: 이사업체 견적이 "짐 부피(㎥) × 기본단가 × 난이도계수(사다리차 필요, 엘리베이터 없음 등)"로 나오듯, COCOMO도 "코드량(KLOC) × 회귀계수 × 비용 동인(난이도)"으로 공수를 계산한다.

## 핵심 용어 정리 (내부에 등장하는 것들)

| 용어 | 의미 | 비유 |
|:---|:---|:---|
| COCOMO | 경험적 회귀식 기반 SW 비용 산정 모델(이 개념의 상위 키워드) | 과거 시공 실적으로 만든 건축 견적 공식 |
| KLOC | 예상 소스코드 라인 수(1,000줄 단위) — 규모 입력값 | 건물의 연면적 |
| PM (Person-Month) | 산출되는 총 공수(인월) | 총 필요 인부 수 × 개월 수 |
| TDEV | 산출되는 개발 기간(월) | 준공까지 걸리는 기간 |
| a, b, c, d | 개발 유형별로 실적 데이터를 회귀분석해 정한 상수 | 지역별 평당 공사 단가표 |
| 개발 유형(Organic/Semi-detached/Embedded) | 팀 경험·제약 수준에 따른 3단계 난이도 분류 | 단독주택 / 연립주택 / 초고층 빌딩 시공 난이도 |
| EAF (Effort Adjustment Factor) | 비용 동인 15개의 등급값을 모두 곱해 만든 보정계수 | 지반 상태·자재 등급·인부 숙련도를 곱해 만든 공사비 할증률 |
| 비용 동인(Cost Driver) | 신뢰성·복잡도·인력 경험 등 공수에 영향을 주는 15개 요인 | 자재 등급, 현장 접근성, 감리 강도 |

## 깊이 이해

### 왜 COCOMO가 필요했나 (배경)
- Barry Boehm이 1981년 63개 실제 프로젝트의 KLOC-공수 실적을 회귀분석해 만들었다. 그전에는 견적이 순전히 전문가 개인 경험에 의존해 프로젝트마다 편차가 컸다. COCOMO는 "규모가 몇 배 늘면 공수가 몇 배 느는가"를 실적 데이터로 정량화한 초기 시도다.
- 핵심 관찰은 공수가 규모에 정비례하지 않는다는 것이다. 코드량이 커질수록 모듈 간 통합·소통 비용이 초선형으로 증가하기 때문에(브룩스의 법칙과 같은 맥락), 회귀식의 지수 b는 항상 1보다 크다.

### Basic COCOMO 계산 — 수치로 이해
- 기본식: PM = a × (KLOC)^b, TDEV = c × (PM)^d.
- 개발 유형별 계수(회귀분석으로 도출된 값):

| 개발 유형 | a | b | 특징 |
|:---|:---:|:---:|:---|
| Organic(유기형) | 2.4 | 1.05 | 소규모(대략 50KLOC 이하), 익숙한 도메인, 요구 유연 |
| Semi-detached(반분리형) | 3.0 | 1.12 | 중간 규모, 팀 경험 혼재 |
| Embedded(내장형) | 3.6 | 1.20 | 엄격한 하드웨어·실시간 제약 |

- **워크드 예제**: 업무 시스템 50KLOC를 Organic으로 추정하면 PM = 2.4 × 50^1.05 ≈ 2.4 × 60.8 ≈ **146 PM**. TDEV = 2.5 × 146^0.38 ≈ 2.5 × 6.6 ≈ **16.6개월**. 평균 투입 인력 = PM ÷ TDEV ≈ 146 ÷ 16.6 ≈ **8.8명**.
- b가 1보다 큰 이유를 같은 방식으로 확인할 수 있다: KLOC이 50 → 500(10배)으로 늘면 PM은 2.4 × 500^1.05 ≈ 2.4 × 665 ≈ 1,596PM으로 약 **10.9배** 는다. 규모가 10배 늘 때 공수는 정확히 10배가 아니라 그 이상으로 늘어난다는 뜻이다.

### Basic → Intermediate → Detailed, 무엇이 다른가
- **Basic**: KLOC만 넣는다. 초기 개략 견적용이다.
- **Intermediate**: 15개 비용 동인(제품 신뢰성 RELY, DB 크기 DATA, 복잡도 CPLX, 실행시간 제약 TIME, 저장공간 제약 STOR, 분석가 역량 ACAP, 응용경험 AEXP, 프로그래머 역량 PCAP, 언어경험 LEXP, 도구 사용 TOOL, 일정 단축 SCED 등)을 각각 Very Low ~ Extra High 등급으로 매겨 모두 곱하면 EAF가 나온다. 조정 후 PM = Basic PM × EAF.
  - 예: Basic PM=146에 EAF=1.2(전반적으로 난이도가 다소 높은 프로젝트)를 곱하면 조정 PM = 146 × 1.2 ≈ **175 PM**. EAF가 1보다 크면 원래보다 더 어려운 프로젝트, 1보다 작으면 더 쉬운 프로젝트라는 뜻이다.
- **Detailed**: Intermediate의 비용 동인을 요구분석·설계·코딩·테스트 등 개발 단계별로 따로 적용해, 단계마다 EAF가 달라지는 것까지 반영한다. 가장 정밀하지만 그만큼 각 단계 상세 정보가 있어야 쓸 수 있다.

### 개발 유형(Organic/Semi-detached/Embedded) 판별 원리
- 판별 기준은 세 축이다. ① 팀이 해당 도메인에 얼마나 익숙한가 ② 요구사항이 얼마나 유연한가(자주 바뀌어도 되는가) ③ 하드웨어·실시간·인터페이스 제약이 얼마나 빡빡한가.
- 익숙한 팀 + 유연한 요구 + 소규모 → Organic. 낯선 요소가 섞여 있으면 → Semi-detached. 항공전자·차량 제어처럼 실시간·안전 제약이 강하면 → Embedded. 같은 KLOC이라도 유형이 다르면 a, b가 달라 PM이 크게 벌어진다 — 위 표에서 a가 2.4→3.6, b가 1.05→1.20으로 커지므로, Embedded는 규모가 커질수록 Organic보다 공수가 더 가파르게 증가한다.

### 흔한 오해와 주의점
- COCOMO는 정확한 미래 예측이 아니라 "과거 유사 프로젝트라면 이 정도"라는 통계적 추정이다. KLOC 자체를 개발 전에 정확히 알기 어렵다는 것이 근본 한계이며, 그래서 실무에서는 Function Point로 규모를 먼저 잡고 언어별 변환표로 KLOC을 역산하기도 한다.
- 애자일·노코드·생성형 AI 코딩이 보편화된 현재는 "KLOC당 실적"이라는 전제 자체가 흔들린다. 그대로 쓰기보다 조직 자체 실적 데이터로 a, b, EAF를 재보정(캘리브레이션)해야 신뢰도가 유지된다.

## 연결 개념
- SW 대가산정(084) — COCOMO는 대가산정에서 쓰는 여러 규모·공수 산정 방식 중 하나로 참고되며, 국내 공공사업 대가산정은 기능점수(FP) 방식이 우선 적용된다
- Function Point — LOC을 모르는 초기 단계에 규모를 먼저 잡는 대안(FP → LOC 변환표로 COCOMO 입력값 생성)
- Putnam 모델(Rayleigh 곡선) — COCOMO와 다른 접근의 경험적 비용 모델(시간에 따른 인력 투입 분포를 곡선으로 표현)

# 📝 【답안용】 시험 답안 템플릿

> 목적: 시험장에서 25분에 그대로 쓰는 답안 양식. 작성방식(추상표현 금지·수치·도식·문제유형 전환)을 엄격히 지킨다.
> 핵심: COCOMO 답안은 모델 단계, 개발 유형, 비용 동인, 현대 적용 한계를 함께 써야 한다.

## 핵심 인사이트 (3줄 요약)

> 1. **본질**: COCOMO는 KLOC와 비용 동인(EAF)을 이용해 노력(PM), 기간(TDEV), 인력(People)을 추정하는 경험 기반 비용 모델이다.
> 2. **가치**: Basic, Intermediate, Detailed 단계를 통해 초기 견적부터 상세 단계별 견적까지 산정 근거를 체계화한다.
> 3. **판단 포인트**: LOC 예측 오차와 비용 동인 주관성을 줄이기 위해 FP 변환, 실적 데이터 보정, 민감도 분석이 필요하다.

## 출제 의도 및 답안 포인트

| 출제 의도 | 반드시 짚을 핵심 | 감점 회피 포인트 |
|:---|:---|:---|
| 비용 산정 모델 이해 확인 | Organic·Semi-detached·Embedded, PM, TDEV | 단순 LOC 계산식만 쓰고 비용 동인을 누락하지 않음 |
| 적용 한계 판단 확인 | EAF, 보정계수, 실적 기반 캘리브레이션 | 현대 개발 환경에 무조건 적용한다고 단정하지 않음 |
| FP·공공 대가산정 비교 확인 | LOC 기반 vs 기능 기반 | FP와 COCOMO 목적을 혼동하지 않음 |
> 요약: COCOMO 문제는 수식보다 규모, 난이도, 비용 동인을 결합해 견적 신뢰도를 높이는 설명이 필요하다.

## Ⅰ. 개요 및 필요성

- 개요: 비용 동인 기반 공수 산정
- 배경: 프로젝트 초기에는 일정, 인력, 예산을 수치로 제시해야 하나 경험식만 사용하면 규모 증가와 난이도 차이가 견적에 반영되지 않는다.
- 필요성: COCOMO는 KLOC, effort multiplier, scale factor로 공수와 일정을 산정해 견적 근거와 민감도 분석을 제시한다.

---

## Ⅱ. 구조 및 구성요소

```text
규모 추정(KLOC) -> 개발 유형 선택 -> 비용 동인 평가
Basic/Intermediate/Detailed -> PM 산정 -> TDEV 산정
PM/TDEV -> 평균 인력 -> 일정·예산 계획
```

| 구성요소 | 역할 | 산정 포인트 |
|:---|:---|:---|
| KLOC | 규모 입력 | FP-LOC 변환 또는 유사 프로젝트 LOC |
| 개발 유형 | 난이도 분류 | Organic, Semi-detached, Embedded |
| 비용 동인 | 노력 조정 | 제품·플랫폼·인력·프로젝트 요인 |
| 산출값 | 계획 기준 | PM, TDEV, 평균 투입인력 |
> 요약: COCOMO는 규모, 개발 유형, 비용 동인을 결합해 공수와 기간을 산출한다.

## Ⅲ. 동작원리 및 흐름도

```text
요구사항/설계 -> KLOC 추정 -> 개발 유형 판정
-> Basic PM 계산 -> 비용 동인 EAF 적용
-> TDEV 계산 -> 인력·예산 배분 -> 실적 보정
```

| 단계 | 처리 내용 | 검증 기준 |
|:---:|:---|:---|
| 1 | KLOC 또는 FP-LOC 변환값 산정 | 유사 프로젝트 대비 편차 20% 이하 |
| 2 | Organic·Semi-detached·Embedded 분류 | 팀 경험·제약·복잡도 근거 |
| 3 | 비용 동인 등급 평가 | EAF 산정 근거 100% 첨부 |
| 4 | PM·TDEV·평균 인력 계산 | 계산식 재현 가능 |
| 5 | 실적 데이터로 보정 | 완료 프로젝트 MRE 25% 이하 |
> 요약: COCOMO는 최초 계산보다 비용 동인 평가와 실적 기반 보정으로 견적 오차를 줄이는 절차가 핵심이다.

## Ⅵ. 실무 적용 및 결론

**적용 방안 3개:**
1. 요구사항 단계 FP를 언어별 LOC 환산표로 변환하고 KLOC 범위를 낙관·기준·비관 3점으로 산정함.
2. 제품 복잡도, 플랫폼 제약, 인력 경험, 도구 성숙도 비용 동인을 평가해 EAF 근거표를 작성함.
3. 완료 프로젝트의 계획 PM·실적 PM·MRE를 축적하고 분기별로 COCOMO 계수를 보정함.

**결론 (2줄):**
- 기술사 판단: LOC 예측 가능성과 실적 데이터가 있으면 COCOMO를 쓰고, 요구사항 단계 공공 대가산정은 FP를 우선 적용함.
- 향후 방향: COCOMO는 DevOps·AI 코드 생성 생산성 데이터를 반영한 조직별 보정 모델로 운영되어야 함.
