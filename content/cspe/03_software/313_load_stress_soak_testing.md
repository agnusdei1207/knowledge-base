# 📖 【암기용】 개념 완전 이해

> 목적: 세 테스트를 목적과 판정 기준으로 구분해 이해하게 만든다.

## 한눈에
- **개요**: 부하 테스트·스트레스 테스트·소크 테스트는 **성능 테스트(Performance Testing)**의 3대 하위 유형으로, 각각 "정상 목표 부하를 견디는가(Load)", "한계를 넘으면 어떻게 무너지는가(Stress)", "오래 켜두면 서서히 망가지는가(Soak)"를 검증한다.
- **왜 필요한가**: 목표 TPS 통과만 확인하면 임계점 이후 장애 양상과 장시간 운전 후 누적되는 결함(메모리 누수 등)을 놓친다. 실제 장애의 상당수는 정상 범위 안에서는 안 터지다가 트래픽 급증이나 장시간 가동 후에 터지는 유형이다.
- **핵심 직관**: 자동차 검사는 정속 주행 연비, 최고 속도·급제동 한계, 장거리 연속 주행 내구성을 따로 측정한다. 성능 시험도 부하 크기(정상/한계 초과)와 시간 축(짧게/오래)이라는 두 변수를 조합해 세 가지로 나눈 것이다.

## 핵심 용어 정리 (내부에 등장하는 것들)

| 용어 | 의미 | 비유 |
|:---|:---|:---|
| 성능 테스트 (상위 개념) | 시스템이 부하 조건에서 응답성·처리량·안정성 기준을 만족하는지 검증하는 시험 전체 | 자동차 종합 검사 |
| 부하 테스트 (Load Test) | 예상 운영 피크 수준의 부하에서 SLA(응답시간·오류율) 충족 여부를 확인 | 정원만큼 태우고 정속 주행 |
| 스트레스 테스트 (Stress Test) | 부하를 목표치 이상으로 계속 올려 시스템이 무너지는 지점(임계점)과 무너지는 방식을 확인 | 짐을 계속 실어 차축이 부러지는 순간을 보기 |
| 소크 테스트 (Soak/Endurance Test) | 일정한 중간 부하를 장시간(수십 시간) 유지해 누적성 결함을 확인 | 장거리 무정차 주행으로 엔진 과열·오일 소모 확인 |
| TPS (Transactions Per Second) | 초당 처리하는 트랜잭션 수 — 부하 크기의 기준 단위 | 시간당 통과 차량 수 |
| Ramp-up / Steady / Ramp-down | 부하를 서서히 올리는 구간 / 목표치로 유지하는 구간 / 서서히 내리는 구간 | 가속 → 정속 주행 → 감속 |
| p95 지연시간 | 요청 100건 중 95번째로 느린 건의 응답시간 — 평균이 아니라 "느린 축" 체감 지표 | 100명 중 95등의 대기시간 |
| Graceful Degradation | 한계를 넘어도 전체가 죽지 않고 일부 기능을 줄이며 버티는 동작 | 정전 시 비상등만 켜고 버티는 건물 |
| 메모리 누수 (Memory Leak) | 사용이 끝난 메모리가 회수되지 않고 계속 쌓여 가용 메모리가 줄어드는 결함 | 설거지를 안 해 그릇이 계속 쌓이는 싱크대 |
| 커넥션 풀 고갈 | DB·외부 연결을 반납하지 않아 재사용 가능한 연결이 바닥나는 현상 | 회의실 예약을 안 지우고 계속 잡아 빈 방이 없어지는 상황 |

## 깊이 이해

### 왜 세 가지로 쪼갰나 (문제의식)
- 단일 부하 테스트(목표 TPS·1시간)만 하면 "정상 범위에서는 통과한다"는 사실만 안다. 실무 장애는 크게 두 갈래다. 하나는 **순간적으로 부하가 목표를 초과**했을 때(이벤트·프로모션 트래픽 폭주), 다른 하나는 **정상 부하라도 오래 켜뒀을 때**(재시작 없이 며칠 운영) 발생한다. 이 두 갈래를 각각 스트레스 테스트, 소크 테스트로 분리해 검증한다.

### 부하 테스트 — 목표선 통과 여부 (수치 예)
- 조건: 동시 사용자 5,000명, 목표 1,000TPS, 1시간 유지.
- 판정: p95 500ms 이하, 오류율 0.1% 이하면 통과. 이 조건을 못 넘으면 "정상 트래픽조차 못 견딘다"는 뜻이므로 스트레스·소크로 넘어갈 필요도 없이 우선 튜닝해야 한다.

### 스트레스 테스트 — 임계점 찾기 (ramp-up 수치)
- 방법: 1,000TPS(목표)에서 시작해 10분마다 20%씩 부하를 올린다. 1,000 → 1,200 → 1,440 → 1,728 → ... 식으로 증가시키다가 오류율이 급등하는 지점(예: 1,500TPS에서 오류율이 0.1%→5%로 급증)을 임계점으로 기록한다.
- 판정 관점이 부하 테스트와 다르다: "통과/실패"가 아니라 "몇 TPS에서 무너지는가, 무너질 때 전체가 다운되는가 아니면 일부 기능만 느려지며 버티는가(Graceful Degradation)"를 본다. 즉 **실패 시점 자체가 결과**다.
- 예: 임계점 1,500TPS 도달 시 응답 지연이 느는 대신 신규 요청을 429(Too Many Requests)로 거절하며 기존 요청은 정상 처리한다면 바람직한 Graceful Degradation이다. 반대로 전체 프로세스가 OOM으로 죽는다면 설계 결함이다.

### 소크 테스트 — 시간이 만드는 결함 (수치 예)
- 조건: 목표보다 낮은 중간 부하(예: 500TPS, 목표의 절반)를 24~72시간 유지한다. 부하 크기가 아니라 시간 누적이 변수이기 때문에 부하를 낮게 잡는다.
- 관측: 1시간 단위로 heap 사용량, GC pause 시간, 열린 DB 커넥션 수를 기록한다. heap이 시간당 2%씩 늘어 24시간 후 48% 증가했다면 메모리 누수 신호다(정상이라면 GC 이후 기준선으로 되돌아와야 한다).
- 판정 기준 예: 24시간 후 메모리 증가율 5% 이하, 커넥션 풀 사용량이 요청 종료 후 원래 수준으로 복귀. 이를 넘으면 코드에서 리스너·캐시·커넥션을 반납하지 않는 지점을 찾아야 한다.

### 세 테스트를 언제 조합하나 (판별 원리)
- 정상 운영만 확인하면 되는 저위험 시스템: 부하 테스트만으로 충분할 수 있다.
- 이벤트성 트래픽 급증이 있는 시스템(쇼핑몰 특가, 티켓 예매): 스트레스 테스트로 임계점과 방어 로직(rate limit, circuit breaker)을 반드시 확인한다.
- 24시간 상시 가동되는 시스템(뱅킹, 통신 코어망): 소크 테스트로 누적 결함을 반드시 확인한다.
- 세 조건(부하 크기 정상/초과, 시간 짧음/김)을 하나의 시험표로 섞으면 어느 조건에서 실패했는지가 뒤섞여 원인 분석이 불가능해진다 — 그래서 조건을 분리해 각각 실행한다.

## 연결 개념
- 성능 테스트 지표 — TPS·p95·오류율이라는 공통 측정 단위를 세 테스트가 공유
- APM(314) — 세 테스트 실행 중 병목 구간과 메모리 추이를 Trace·Metric으로 실시간 확인
- 카오스 엔지니어링 — 스트레스·소크에서 확인한 한계·복구 경로를 실제 운영계에서 장애 주입으로 재검증하는 다음 단계

# 📝 【답안용】 시험 답안 템플릿

> 목적: 부하·스트레스·소크 테스트의 목적, 조건, 판정 기준을 비교형 답안으로 전개한다.
> 핵심: 세 테스트는 부하 크기와 시간 축이 다르므로 같은 결과표로 판단하면 안 된다.

## 핵심 인사이트 (3줄 요약)

> 1. **본질**: Load는 목표 부하 검증, Stress는 한계·복구 확인, Soak는 장시간 누수성 결함 탐지 시험이다.
> 2. **가치**: 정상 처리, 임계점, 장기 운전 문제를 분리해 운영 장애 가능성을 시험 단계에서 드러낸다.
> 3. **판단 포인트**: 테스트별 부하 패턴, 지속 시간, 성공 기준, 실패 해석을 구분해야 한다.

## 출제 의도 및 답안 포인트

| 출제 의도 | 반드시 짚을 핵심 | 감점 회피 포인트 |
|:---|:---|:---|
| 성능 시험 유형 구분 확인 | Load·Stress·Soak 목적과 조건 차이 | 부하 테스트와 스트레스 테스트 혼용 |
| 운영 리스크 판단 확인 | 한계점, 복구, 메모리 누수, 커넥션 고갈 | TPS만 쓰고 시간 축 누락 |
| 검증 계획 수립 역량 확인 | ramp-up, steady, ramp-down, 관측 지표 | 도구명 나열 후 판정 기준 미제시 |

> 요약: 이 문제는 성능 시험을 부하 크기와 시간 축으로 나누고, 각 결과를 운영 판단으로 연결하는지를 본다.

## Ⅰ. 개요 및 필요성

- 개요: 성능 검증의 3가지 시험 축
- 배경: 정상 목표 부하, 한계 초과, 장시간 운전 조건은 발견 가능한 결함 유형이 서로 다름
- 필요성: Load, Stress, Soak 테스트로 병목, 복구 경로, 메모리 누수성 결함을 운영 전 검증해야 함

---

## Ⅱ. 구조 및 구성요소

```text
성능 목표 -> Load Test -> Stress Test -> Soak Test -> 운영 판정
             / 정상 부하 / 한계 초과 / 장시간 지속
```

| 구성요소 | 역할 | 특이사항 |
|:---|:---|:---|
| Load Test | 목표 부하에서 기준 충족 확인 | 예: 1,000TPS, p95 500ms |
| Stress Test | 한계점과 장애 양상 확인 | 임계 TPS, 오류 증가 구간 |
| Soak Test | 장시간 운전 결함 탐지 | 24~72시간 메모리·커넥션 관측 |
| 관측 체계 | 병목 원인 추적 | APM, DB wait, Prometheus |

> 요약: 세 테스트는 목표 부하, 초과 부하, 장시간 부하라는 다른 질문에 답한다.

---

## Ⅲ. 동작원리 및 흐름도

```text
시나리오 작성 -> 부하 패턴 설정 -> 테스트 실행 -> 지표 관측 -> 결과 판정
```

| 단계 | 처리 내용 | 검증 기준 |
|:---:|:---|:---|
| 1 | 운영 로그 기반 업무 비율 정의 | 조회 70%, 등록 20%, 기타 10% |
| 2 | Load 조건 실행 | 목표 TPS, p95, 오류율 충족 |
| 3 | Stress 조건 상승 | 임계점, failover, throttle 확인 |
| 4 | Soak 조건 유지 | 메모리 증가율, GC pause, connection leak |
| 5 | 병목과 조치 계획 도출 | CPU, DB, 네트워크, 코드 경로 |

> 요약: 테스트는 같은 시나리오를 부하 크기와 시간 조건만 바꿔 실행해 결과를 비교한다.

## Ⅳ. 특징

| 구분 | Load Test | Stress Test | Soak Test |
|:---|:---|:---|:---|
| 목적 | 목표 부하 통과 | 한계점·복구 확인 | 장시간 결함 탐지 |
| 부하 조건 | 예상 피크 수준 | 피크 초과 단계 상승 | 일정 부하 장시간 유지 |
| 수치 예 | 1,000TPS, 1시간 | 1,500TPS까지 증가 | 500TPS, 24시간 |
| 판정 | SLA 충족 여부 | graceful degradation | 메모리 증가량 5% 이하 |

> 요약: Load는 통과 여부, Stress는 한계, Soak는 시간 누적 결함을 판정한다.

## Ⅴ. 심화 비교 및 적용 판단

| 비교 축 | 기존/대안 | 본 키워드 | 선택 기준 |
|:---|:---|:---|:---|
| 구조 | 단일 부하 시험 | 3종 시험 조합 | 운영 리스크 범위 |
| 비용/성능 | 짧은 피크 시험 | 장시간 Soak 포함 | 장애 비용과 시험 시간 |
| 운영/위험 | 목표 통과 중심 | 임계점·복구·누수 확인 | 출시 전 장애 허용도 |

> 요약: 운영 영향이 큰 시스템은 Load만으로 부족하며 Stress와 Soak를 묶어 판정해야 한다.

| 리스크 | 원인 | 대응 방안 | 확인 지표 |
|:---|:---|:---|:---|
| 한계 미파악 | 목표 부하까지만 시험 | Stress ramp-up 수행 | 최대 TPS, 오류 증가점 |
| 장기 장애 | 메모리·커넥션 누수 | Soak 24시간 이상 | heap usage, open connection |
| 시험 왜곡 | 운영 데이터 미반영 | 로그 기반 시나리오 | 업무별 요청 비율 |

> 요약: 성능 시험 리스크는 부하 크기, 시간, 데이터 대표성을 분리해 통제한다.

| 점검 항목 | 목표 기준 | 측정 방법 |
|:---|:---|:---|
| Load | p95 500ms, 오류율 0.1% 이하 | k6/JMeter 리포트 |
| Stress | 임계 TPS와 복구 시간 식별 | ramp-up 그래프, APM |
| Soak | 24시간 메모리 증가 5% 이하 | heap dump, Prometheus |

> 요약: 도입 후 성공 여부는 정상 통과, 한계 식별, 장기 누수 부재를 모두 확인해 판단한다.

## Ⅵ. 실무 적용 및 결론

**적용 방안 3개:**
1. Load: 운영 피크 120% 조건으로 1시간 실행하고 TPS, p95, 오류율 기준을 인수 조건으로 고정
2. Stress: TPS를 10분 단위로 20%씩 상승시켜 임계점, throttle, circuit breaker 동작 확인
3. Soak: 24시간 이상 일정 부하에서 heap dump, GC pause, DB connection pool 사용률을 수집

**결론 (2줄):**
- 기술사 판단: 금융·공공 핵심 업무는 Load 통과 후 Stress 임계점과 Soak 누수 지표까지 확인해야 출시 판정 가능
- 향후 방향: 성능 시험은 APM·SLO·배포 게이트와 연결되어 릴리스별 회귀 탐지 체계로 확장된다
