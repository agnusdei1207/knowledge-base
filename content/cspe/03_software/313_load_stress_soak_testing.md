## Ⅰ. 개요
- **정의**: 시스템에 다양한 부하 패턴을 인가하여 한계·안정성을 검증하는 성능 테스트 유형임
- **배경/필요성**: 정상 부하만 테스트하면 피크·장시간 운영 시 장애 예측 불가하므로 유형별 검증 필요
- **비유**: 다리를 일상 교통량(부하)·태풍(스트레스)·수십 년 풍화(내구성)로 각각 검증하는 것과 같음

| 출제 의도 | 반드시 짚을 핵심 | 감점 회피 포인트 |
|:---|:---|:---|
| 3가지 테스트 유형의 목적·차이 구분 | 부하 수준×시간축 기준 분류 | Load와 Stress 혼용 시 감점 |

> 요약: 부하 수준과 지속 시간 축으로 Load·Stress·Soak 3유형을 구분하여 품질을 검증함

## Ⅱ. 구성요소
```text
Performance Testing
  +-- Load Test : 예상 최대 부하까지 점진 인가
  +-- Stress Test : 한계 초과 부하 인가
  +-- Soak Test : 일정 부하 장시간 지속
```

| 구성요소 | 설명 | 비유 |
|:---|:---|:---|
| Load Test | 예상 피크 부하까지 점진 증가시켜 목표 TPS 충족 여부 확인 | 만석까지 좌석 채우기 |
| Stress Test | 시스템 한계 초과 부하 인가로 장애 지점·복구 능력 확인 | 제한 하중 초과 적재 시험 |
| Soak Test | 정상 부하를 12~72시간 유지하여 메모리 누수·성능 저하 탐지 | 장기 내구성 주행 시험 |

> 요약: 부하 강도·지속 시간 조합으로 시스템의 용량·한계·내구성을 각각 검증함

## Ⅲ. 절차
```text
테스트 계획 -> 환경/시나리오 준비 -> 유형별 부하 실행 -> 결과 분석/튜닝
```
- 1단계: SLA 기준·테스트 유형·목표 지표(TPS, 응답시간) 정의
- 2단계: 운영 유사 환경 구성, 부하 스크립트·모니터링 에이전트 배치
- 3단계: Load → Stress → Soak 순서로 부하 인가 및 지표 수집(312 참조)
- 4단계: 병목 구간 식별, 자원 튜닝 후 재테스트로 개선 효과 검증

> 요약: 계획 → 준비 → 실행 → 분석 4단계를 유형별로 반복 수행함

## Ⅳ. 문제점
- 환경 차이: 테스트 환경 축소 구성 — 운영 환경 대비 부하 분산 특성 상이
- 시나리오 편향: 단순 반복 요청 위주 — 실 사용자 행위 패턴 미반영
- 내구성 테스트 생략: 일정 부족으로 Soak 미실시 — 메모리 누수 미탐지

> 요약: 환경 차이·시나리오 편향·Soak 생략이 테스트 신뢰성을 저해함

## Ⅴ. 개선방안
1. 단기: 컨테이너 기반 운영 동일 환경 구축으로 테스트 환경 격차 최소화
2. 중기: 운영 로그 기반 사용자 행위 모델링으로 시나리오 현실성 확보
3. 장기: CI/CD 파이프라인에 야간 Soak 테스트 자동 편성으로 생략 방지

> 요약: 환경 일치 → 행위 모델링 → Soak 자동화로 테스트 커버리지를 확보함

## Ⅵ. 전망
- 발전 방향: 카오스 엔지니어링과 결합하여 장애 주입+부하 복합 테스트 확산
- 기술사적 판단: 클라우드 오토스케일링 환경에서도 한계점 검증은 여전히 필수임
- 기술사 제언: 테스트 유형별 목적을 명확히 구분하고 SLA 기준과 연계하여 수행 필요
