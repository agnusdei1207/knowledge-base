## 미리 알고가기

- At-Most-Once는 이벤트 결과가 한 번 이하로 반영되어 장애 시 손실될 수 있는 보장임
- At-Least-Once는 이벤트 결과가 한 번 이상 반영되어 손실은 억제하지만 중복될 수 있는 보장임
- Exactly-Once는 장애·재시도 후에도 각 이벤트의 논리적 결과가 한 번만 반영되는 보장임
- 재생 가능한 소스는 체크포인트 이전 위치부터 이벤트를 다시 읽을 수 있음
- 멱등 연산은 같은 요청을 반복해도 최종 상태가 한 번 수행한 결과와 같음
- 2단계 커밋은 준비와 확정 단계를 나눠 상태와 외부 결과를 원자적으로 반영함

## 작성 근거(검토용)

- Exactly-Once는 처리 횟수가 아니라 결과 반영 횟수라는 의미와 종단 간 보장 조건을 핵심으로 선정함
- 비교표는 손실·중복·복구 위치·필요 구조·비용·적합 업무를 세 전달 보장에 동일하게 적용함
- 절차는 소스 위치·연산 상태·싱크 결과를 하나의 커밋 경계로 묶는 실제 복구 원리를 설명함
- 제목부터 결론까지 모든 문장·표 셀·요약을 5회 전수 검수해 내부 상태와 종단 간 보장을 구분함

## Ⅰ. 개요

- **정의/개념**: Exactly-Once는 실패·재실행 후에도 입력 위치·연산 상태·싱크 결과를 복구해 논리적 결과를 한 번만 반영하는 처리 보장임
- **배경/필요성**: 장애 재처리에서 집계 중복과 상태 손실을 방지하기 위해 입력 재생과 상태·출력의 원자적 커밋 기준이 필요함

## Ⅱ. 특징

- 이벤트가 물리적으로 한 번만 실행된다는 뜻이 아니라 최종 상태에 한 번만 영향을 준다는 의미임
- 재생 가능한 소스와 처리 위치가 있어야 실패 시 확정된 지점부터 이벤트를 다시 읽을 수 있음
- 연산 상태와 소스 위치를 같은 체크포인트에 저장해야 일부 상태만 복구되는 불일치를 방지함
- 외부 싱크까지 보장하려면 트랜잭션 커밋·멱등 쓰기·중복 제거 키 중 하나가 필요함
- 장벽 정렬·상태 스냅샷·분산 커밋은 지연과 저장·조정 비용을 추가함

## Ⅲ. 종류 및 비교

| 판단 기준 | At-Most-Once | At-Least-Once | Exactly-Once |
|:---|:---|:---|:---|
| 장애 시 결과 | 미처리 이벤트가 손실될 수 있음 | 이벤트를 다시 처리해 중복될 수 있음 | 재처리해도 논리적 결과를 한 번 반영 |
| 처리 위치 | 이벤트 처리 전에 위치를 확정 | 이벤트 처리 후 위치를 확정해 실패 구간 재생 | 상태·출력과 연계해 위치 확정 |
| 필요 구조 | 재시도 없는 전달·처리 | 재생 가능한 입력과 재시도 | 일관된 스냅샷과 원자적·멱등 싱크 |
| 외부 부수 효과 | 실패 시 누락 가능 | 중복 호출 가능 | 트랜잭션 또는 중복 제거 키 필요 |
| 처리 비용 | 복구 조정 비용이 작음 | 재처리와 중복 제거 비용 발생 | 스냅샷·정렬·커밋 조정 비용 발생 |
| 적합 업무 | 일부 손실을 허용하는 상태 통계 | 중복 제거 가능한 이벤트 처리 | 결제·재고·정산처럼 중복 결과를 허용하지 않는 처리 |

> 요약: Exactly-Once는 재생 가능한 입력과 일관된 상태 스냅샷, 원자적·멱등 싱크로 결과 중복과 손실을 통제함.

## Ⅳ. 구성요소 및 구조

| 구성요소 | 설명 |
|:---|:---|
| Replayable Source | 이벤트와 처리 위치를 보존해 실패 구간을 다시 제공함 |
| Offset·Checkpoint | 확정된 입력 위치와 연산자 상태를 같은 복구 지점으로 기록함 |
| Stateful Operator | 이벤트를 결정적으로 처리하고 상태 버전을 스냅샷에 포함함 |
| Transaction Coordinator | 상태와 출력의 준비·확정 여부를 조정함 |
| Transactional·Idempotent Sink | 결과를 원자적으로 커밋하거나 이벤트 키로 중복 반영을 제거함 |

```text
재생 가능한 입력 -> 상태 연산 -> 준비된 출력
        |              |             |
        +------ Checkpoint Commit ----+
```

> 요약: 입력 위치·연산 상태·출력 커밋이 같은 복구 경계에 들어가야 종단 간 Exactly-Once가 성립함.

## Ⅴ. 원리 및 절차 흐름도

```text
이벤트·위치 읽기 -> 상태 갱신 -> 출력 준비 -> 체크포인트 확정 -> 출력 커밋
```

1. **입력 읽기**: 소스가 이벤트와 재생 가능한 위치를 연산자에 전달함
2. **상태 갱신**: 연산자가 이벤트를 처리하고 변경 상태를 체크포인트 후보에 포함함
3. **출력 준비**: 싱크가 결과를 외부에 노출하지 않은 트랜잭션 상태로 저장함
4. **복구점 확정**: 입력 위치와 모든 연산자 상태의 스냅샷 완료를 기록함
5. **결과 커밋**: 완료된 체크포인트에 대응하는 싱크 트랜잭션을 확정함

> 요약: 입력 위치와 상태 스냅샷이 확정된 뒤 대응하는 싱크 결과를 커밋해 한 번의 논리적 효과를 만듦.

## Ⅵ. 실무 사례

1. 결제 이벤트 집계는 거래 ID 멱등 키와 상태 체크포인트를 적용하고 중복 반영 건수·복구 시간을 확인함
2. 재고 변경 스트림은 트랜잭션 싱크를 적용하고 누락 이벤트 수·커밋 실패 건수를 확인함

## Ⅶ. 결론

- Exactly-Once는 소스 재생·상태 스냅샷·싱크 원자성의 종단 간 충족 여부와 조정 비용을 기준으로 선택해야 함
