## Ⅰ. 개요
- **정의**: 구조화된 데이터를 언어 중립적 IDL로 정의하고 바이너리로 직렬화하는 데이터 교환 포맷
- **배경/필요성**: JSON/XML 대비 직렬화 크기·파싱 속도 개선이 대량 서비스 간 통신에서 요구됨
- **비유**: 사전 약속된 약어표(스키마)로 전보를 보내면 수신자가 약어를 풀어 원문 복원하는 방식

| 출제 의도 | 반드시 짚을 핵심 | 감점 회피 포인트 |
|:---|:---|:---|
| 직렬화 포맷 비교·선택 기준 | 필드 번호 기반 인코딩, Varint 가변길이 정수 | 하위 호환성 규칙(필드 번호 유지, reserved 사용) |

> 요약: IDL로 스키마를 정의하고 바이너리 직렬화로 크기·속도를 최적화하는 데이터 포맷임

## Ⅱ. 구성요소
```text
.proto 파일 --protoc--> 생성 코드 (Stub/Message Class)
                            |
                   +--------+--------+
                   |        |        |
               Serialize  Deserialize  Reflection
```

| 구성요소 | 설명 | 비유 |
|:---|:---|:---|
| .proto 파일 | 메시지 타입·필드 번호·서비스를 정의하는 IDL | 약어표 |
| protoc 컴파일러 | .proto를 대상 언어 코드로 변환하는 코드 생성기 | 번역기 |
| Wire Format | 필드번호+타입 태그+값으로 구성된 바이너리 인코딩 규격 | 전보 문법 |

> 요약: .proto IDL을 protoc로 컴파일하여 Wire Format 기반 바이너리 직렬화 코드를 생성함

## Ⅲ. 절차
```text
스키마 정의 --> 코드 생성 --> 직렬화 --> 역직렬화
```
- 1단계: .proto 파일에 `message`, `service`, 필드 번호·타입 정의
- 2단계: protoc로 대상 언어의 메시지 클래스·서비스 Stub 코드 자동 생성
- 3단계: 송신 측에서 메시지 객체를 Wire Format 바이너리로 직렬화하여 전송
- 4단계: 수신 측에서 바이너리를 역직렬화하여 타입 안전한 메시지 객체로 복원

> 요약: 스키마 정의, 코드 생성, 직렬화, 역직렬화 4단계로 바이너리 데이터 교환 수행함

## Ⅳ. 문제점
- 가독성 부재: 바이너리 포맷으로 네트워크 캡처 시 내용 육안 확인 불가
- 스키마 필수 의존: .proto 파일 없이는 메시지 해석 불가 — 스키마 배포·관리 부담
- 필드 번호 충돌: 팀 간 독립 개발 시 동일 번호 재사용으로 하위 호환성 파괴 위험

> 요약: 가독성 부재, 스키마 필수 의존, 필드 번호 충돌이 주요 문제임

## Ⅴ. 개선방안
1. 단기: grpcurl·protoc decode 활용으로 바이너리 메시지 텍스트 변환 디버깅 지원
2. 중기: 스키마 레지스트리(Buf Schema Registry 등) 도입으로 중앙 집중 스키마 관리
3. 장기: CI에 buf breaking 검사 통합으로 필드 번호 충돌·호환성 파괴 자동 차단

> 요약: 디버깅 도구, 스키마 레지스트리, CI 호환성 검사로 단계적 개선함

## Ⅵ. 전망
- 발전 방향: proto3 Edition 기반으로 기능 플래그(feature) 체계 도입, 언어별 커스터마이징 유연성 확대
- 기술사적 판단: gRPC(202 참조)의 핵심 직렬화 계층으로 마이크로서비스 통신 표준 지위 유지
- 기술사 제언: JSON 대비 크기 50~80% 절감 효과를 정량적으로 제시하여 도입 근거 확보 권장
