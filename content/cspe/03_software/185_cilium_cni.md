## 미리 알고가기

- CNI는 컨테이너 생성·삭제 시 네트워크 인터페이스와 주소를 구성하는 규격임
- Cilium은 eBPF 데이터 플레인으로 Pod 연결·서비스 주소 변환·네트워크 정책을 처리함
- 보안 신원은 변동하는 IP 대신 워크로드 라벨을 정책 식별자로 사용함
- eBPF 맵은 엔드포인트·서비스·정책·연결 상태를 커널 데이터 플레인과 공유함
- Hubble은 Cilium의 eBPF 흐름 이벤트를 수집해 노드·클러스터 통신을 관측함

## 작성 근거(검토용)

- Cilium은 CNI 호출, 에이전트, eBPF 데이터 플레인, 보안 신원, Hubble을 핵심 축으로 설명함
- 비교표는 데이터 경로·정책과 관측·적용 전제의 정확히 3개 축을 대비함
- 절차는 Pod 배치로 CNI가 호출되고 eBPF 상태가 구성된 뒤 패킷과 흐름 이벤트가 처리되는 순서를 따름

## Ⅰ. 개요

- **정의/개념**: Cilium은 Kubernetes CNI 호출에 따라 eBPF 데이터 플레인을 구성하고 Pod 연결·서비스 로드밸런싱·신원 기반 정책·흐름 관측을 제공함
- **배경/필요성**: Pod IP가 바뀌는 클러스터에서 연결과 정책을 워크로드 신원에 맞춰 갱신하기 위해 프로그래머블 데이터 플레인이 필요함

### 쉽게 이해하기 (학습용)
- Kubernetes 상태를 eBPF 프로그램과 맵으로 바꿔 네트워크·정책·관측에 적용함

## Ⅱ. 특징

- 노드의 Cilium 에이전트가 Kubernetes 상태를 eBPF 프로그램과 맵에 반영함
- 워크로드 라벨에서 생성한 보안 신원으로 L3·L4·L7 정책 대상을 식별함
- 서비스 주소 변환과 로드밸런싱을 eBPF 훅에서 처리할 수 있음
- Hubble이 정책 허용·거부와 DNS·TCP·HTTP 흐름 이벤트를 수집함

### 쉽게 이해하기 (학습용)
- 라벨 기반 신원으로 정책을 적용하고 Hubble로 판정 결과를 관측함

## Ⅲ. 종류 및 비교

| 판단 기준 | Cilium eBPF 구성 | iptables·route 기반 구성 |
|:---|:---|:---|
| 데이터 경로 | eBPF 프로그램·맵으로 연결·서비스 분산 처리 | 라우팅 규칙·iptables 체인과 kube-proxy로 처리 |
| 정책과 관측 | 라벨 기반 신원 정책과 Hubble 흐름·판정 수집 | IP·CIDR·포트 정책과 별도 패킷·로그 도구 연동 |
| 적용 전제 | 지원 Linux 커널과 eBPF 기능·권한 필요 | 커널 라우팅·iptables 기능 필요 |

> 요약: Cilium은 Kubernetes 상태를 eBPF 맵과 프로그램에 반영해 연결·서비스·정책·관측을 처리함.

### 쉽게 이해하기 (학습용)
- 커널의 프로그래머블 경로에서 서비스 연결과 보안 정책을 함께 처리함

## Ⅳ. 구성요소 및 구조

| 구성요소 | 설명 |
|:---|:---|
| Cilium CNI 플러그인 | Pod 생성·삭제 시 노드 에이전트에 네트워크 구성을 요청함 |
| Cilium 에이전트 | Kubernetes 이벤트를 수신하고 eBPF 프로그램·맵·정책을 관리함 |
| eBPF 데이터 플레인 | Pod 패킷의 전달·서비스 주소 변환·정책 판정을 수행함 |
| Cilium Operator | 클러스터 범위의 IP 할당과 보안 신원·노드 상태 정리를 수행함 |
| Hubble Server·Relay | 노드 흐름 이벤트를 수집하고 클러스터 범위 조회를 제공함 |

```text
Kubernetes API -> Cilium 에이전트 -> eBPF 프로그램·맵 -> Pod 패킷
                         |                  |
CNI 플러그인 ------------+                  +-> Hubble Server -> Relay
```

> 요약: 에이전트가 CNI·Kubernetes 상태를 eBPF 데이터 플레인에 반영하고 Hubble이 흐름을 수집함.

### 쉽게 이해하기 (학습용)
- 에이전트가 상태를 커널 맵에 반영하고 Hubble이 실제 패킷 결과를 보여줌

## Ⅴ. 원리 및 절차 흐름도

```text
Pod 배치 -> CNI 호출 -> 엔드포인트·신원 생성 -> eBPF 맵 갱신 -> 패킷 처리 -> 흐름 기록
```

1. **CNI 호출**: Pod 배치 시 런타임이 Cilium CNI 플러그인을 실행함
2. **엔드포인트 구성**: 에이전트가 인터페이스·IP·보안 신원을 생성함
3. **데이터 플레인 갱신**: 에이전트가 엔드포인트·서비스·정책 정보를 eBPF 맵에 반영함
4. **패킷 처리**: eBPF 프로그램이 전달·서비스 주소 변환·정책 허용 여부를 판정함
5. **흐름 기록**: Hubble이 통신 결과와 정책 판정을 수집함

> 요약: Pod 생성 정보가 eBPF 엔드포인트·신원·정책 상태로 변환된 뒤 패킷 경로에 적용됨.

### 쉽게 이해하기 (학습용)
- Pod 생성부터 신원·정책·패킷 판정·관측까지 이어짐

## Ⅵ. 실무 사례

1. 마이크로서비스 API 간 통신은 Cilium 신원 정책을 적용하고 허용·거부 흐름 수를 확인함
2. 서비스 경로는 eBPF 로드밸런싱을 적용하고 p99 요청 지연·패킷 드롭률을 확인함

### 쉽게 이해하기 (학습용)
- 정책 거부와 장애를 구분하고 서비스 경로 성능을 측정함

## Ⅶ. 결론

- Cilium은 eBPF 커널 지원을 확인하고 신원 정책·서비스 경로·흐름 관측을 통합할 때 적용함

### 쉽게 이해하기 (학습용)
- 커널 호환성과 정책·관측 운영 역량을 먼저 확인해야 함
