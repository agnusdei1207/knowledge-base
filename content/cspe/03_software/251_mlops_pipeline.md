# 📖 【암기용】 개념 완전 이해

> 목적: MLOps 파이프라인을 처음 보는 사람도 완벽히 이해하게 만든다. 시험 답안 양식이 아니라, 이해를 위한 친절한 설명이다.

## 한눈에
- **개요**: MLOps(Machine Learning Operations)는 **DevOps의 CI/CD 원칙을 데이터·모델까지 확장**해, 데이터 수집부터 학습·검증·배포·모니터링·재학습까지 머신러닝 모델의 전체 생명주기를 자동화하고 통제하는 운영 체계다.
- **왜 필요한가**: ML 모델은 코드가 그대로여도 **입력 데이터의 분포**가 바뀌면 성능이 떨어진다(코드만 관리하는 일반 DevOps로는 잡히지 않는 변화다). 수작업 배포는 학습 데이터 버전, 모델 파일, 서비스 코드 버전이 어긋나는 사고를 만든다.
- **핵심 직관**: 소프트웨어 CI/CD 파이프라인에 "데이터 검증", "모델 성능 평가", "운영 중 분포 변화(드리프트) 감시" 단계를 추가로 붙인 ML 전용 생산 라인이다.

## 핵심 용어 정리 (내부에 등장하는 것들)

| 용어 | 의미 | 비유 |
|:---|:---|:---|
| DevOps (상위 개념) | 코드를 빌드·테스트·배포까지 자동화하는 개발-운영 통합 체계 | MLOps가 확장하는 원형 |
| CI/CD/CT | Continuous Integration/Delivery에 **Continuous Training**(주기적 재학습)을 더한 개념 | 코드뿐 아니라 모델도 계속 새로 만들어 검증 |
| 피처 스토어 (Feature Store) | 학습 때 쓴 피처와 추론 때 쓸 피처를 동일하게 유지하는 저장소 | 레시피의 재료 규격을 학습·생산 라인이 똑같이 참조 |
| 모델 레지스트리 (Model Registry) | 모델 버전, 평가 지표, 승인 상태(Staging/Production)를 관리하는 저장소 | 출하 가능 제품만 등록하는 창고 대장 |
| 데이터 드리프트 / 모델 드리프트 | 운영 데이터 분포가 학습 때와 달라져 성능이 떨어지는 현상 | 여름 옷 만드는 공식을 겨울에도 그대로 씀 |
| PSI (Population Stability Index) | 두 분포(학습 시점 vs 운영 시점)가 얼마나 달라졌는지 수치화한 지표 | 인구 구성비 변화를 하나의 숫자로 요약 |
| Canary / Shadow 배포 | 신규 모델을 일부 트래픽에만 노출하거나, 실제 응답에 영향 없이 병행 실행해보는 배포 전략 | 신제품을 일부 매장에서만 먼저 판매 |

## 깊이 이해

### 왜 일반 DevOps만으로는 부족한가 (배경)
- 일반 소프트웨어는 "코드가 바뀌지 않으면 동작도 바뀌지 않는다"는 전제가 성립한다. 반면 ML 모델은 코드(추론 로직)가 그대로여도 **입력 데이터의 통계적 분포**가 바뀌면 예측 품질이 떨어진다. 예를 들어 소비 패턴이 급변하는 시기(할인 행사, 계절 변화)에는 코드 변경 없이도 추천 모델의 정확도가 떨어질 수 있다.
- 게다가 노트북에서 실험한 모델은 "어떤 데이터 버전, 어떤 코드 커밋, 어떤 하이퍼파라미터로 만들었는지"가 기록되지 않으면 나중에 같은 모델을 재현할 수 없다(재현성 문제). MLOps는 이 두 가지 — 데이터 변화 감시와 학습 재현성 — 를 파이프라인으로 강제한다.

### 판별 원리 — 드리프트를 수치로 판정하는 법 (PSI)
- PSI는 학습 시점 데이터 분포(Expected)와 현재 운영 데이터 분포(Actual)를 구간별로 나눠 `Σ (Actual% - Expected%) × ln(Actual% / Expected%)`로 계산한다.
- 판정 기준은 실무적으로 다음과 같다: **PSI < 0.1**이면 안정(재학습 불필요), **0.1 ≤ PSI < 0.25**이면 주의 관찰, **PSI ≥ 0.25**이면 심각한 드리프트로 간주해 재학습 티켓을 자동 생성한다. 예를 들어 어떤 피처의 PSI가 0.3으로 나왔다면, 이는 "이 피처의 분포가 학습 때와 크게 달라져 모델이 더는 신뢰할 수 없다"는 뜻이다.

### 작동 원리 — 데이터 적재부터 재학습까지
1. 원천 데이터를 적재한 뒤 스키마 일치 여부와 결측률(예: 1% 이하)을 검증한다. 검증을 통과하지 못하면 파이프라인은 여기서 중단된다.
2. 피처를 생성해 학습을 실행하고, 이때 코드 커밋 SHA, 데이터 버전, 하이퍼파라미터를 메타데이터로 함께 기록한다(재현성 확보).
3. 오프라인 평가 지표(예: 추천 모델 AUC 0.78 이상)를 통과한 모델만 레지스트리에 `Staging` 상태로 등록되고, 승인 후 `Production`으로 전환돼 CI/CD로 배포된다.
4. 배포된 모델은 p95 추론 지연(예: 100ms 이하)과 PSI(예: 0.2 미만)를 실시간으로 감시하며, 임계값을 넘으면 재학습 파이프라인이 다시 1번부터 시작된다.

### 비유와 흔한 오해
- **비유**: 연구실에서 완성한 레시피를 공장 생산 라인으로 옮길 때, 원재료 검사(데이터 검증)·공정 기록(학습 메타데이터)·품질 검사(평가 게이트)·출하 후 불량 추적(모니터링)을 추가로 붙이는 것과 같다.
- **오해**: MLOps는 MLflow·Kubeflow 같은 도구를 설치하는 것이 아니다. 데이터 계약(스키마 합의), 모델 승인 권한자, 운영 중 감시 지표, 재학습 트리거 기준이 없으면, 도구가 있어도 실질은 단순 배치 스크립트 실행에 머문다.

## 연결 개념
- 피처 스토어 — 학습·추론 간 피처 정의 불일치(training-serving skew)를 막는 핵심 구성요소
- 모델 레지스트리 — 모델 버전과 승인 상태를 관리해 배포 원자성을 확보
- 모델 모니터링 — PSI·p95 지연 등으로 드리프트를 실시간 탐지하는 운영 축
- LLMOps — MLOps의 원칙(평가 게이트·모니터링·재학습)을 생성형 AI 특유의 프롬프트·RAG 운영으로 확장한 상위 응용

# 📝 【답안용】 시험 답안 템플릿

> 목적: 시험장에서 25분에 그대로 쓰는 답안 양식. 작성방식(추상표현 금지·수치·도식·문제유형 전환)을 엄격히 지킨다.
> 핵심: MLOps 답안은 CI/CD 나열이 아니라 데이터, 모델, 서비스, 모니터링을 하나의 통제 흐름으로 묶어야 한다.

## 핵심 인사이트 (3줄 요약)

> 1. **본질**: MLOps 파이프라인은 ML 모델의 데이터 준비, 학습, 검증, 배포, 감시, 재학습을 자동화하는 운영 생명주기다.
> 2. **가치**: 재현 가능한 학습 실행, 승인 기반 배포, 드리프트 감시로 모델 변경 리스크를 지표 기반으로 통제한다.
> 3. **판단 포인트**: 모델 정확도만 보지 말고 데이터 품질, p95 추론 지연, 롤백 시간, 드리프트 임계값을 함께 설계해야 한다.

## 출제 의도 및 답안 포인트

| 출제 의도 | 반드시 짚을 핵심 | 감점 회피 포인트 |
|:---|:---|:---|
| ML 운영 생명주기 이해 확인 | DataOps, CI/CD, CT, 모델 레지스트리, 모니터링 | 학습 자동화만 설명하고 운영 감시 누락 |
| 현업 적용 판단 확인 | 데이터 검증, 평가 게이트, 승인, 배포 전략 | 정확도 수치만 제시하고 지연·비용·롤백 누락 |

## Ⅰ. 개요 및 필요성

- 개요: MLOps는 ML 모델 생명주기 자동화 체계다.
- 배경: ML 서비스는 코드 변경 외에 데이터 분포, 피처 정의, 모델 파라미터가 예측 결과를 바꾼다.
- 필요성: 학습 재현성, 평가 게이트, 배포 승인, 운영 감시를 파이프라인으로 통제해야 한다.

---

## Ⅱ. 구조 및 구성요소

```text
Data Source -> Data Validation -> Feature Pipeline -> Training -> Evaluation -> Registry -> Serving -> Monitoring
                                      / Metadata Store
                                      / Approval Gate
```

| 구성요소 | 역할 | 통제 기준 |
|:---|:---|:---|
| 데이터 검증 | 스키마, 결측치, 이상치 확인 | Great Expectations, TFDV |
| 학습 파이프라인 | 피처 생성, 학습, 튜닝 실행 | Kubeflow, Airflow, MLflow |
| 모델 레지스트리 | 버전, 지표, 승인 상태 관리 | Staging, Production, Archived |
| 서빙·모니터링 | API 배포, 지연, 드리프트 감시 | p95, PSI, 오류율 |

> 요약: MLOps 구조는 데이터 검증부터 운영 감시까지 모델 변경을 추적 가능한 단계로 나눈다.

---

## Ⅲ. 동작원리 및 흐름도

```text
데이터 변경 감지 -> 검증 통과 -> 학습 실행 -> 평가 기준 확인 -> 승인 -> 배포 -> 지표 감시 -> 재학습 트리거
```

| 단계 | 처리 내용 | 검증 기준 |
|:---:|:---|:---|
| 1 | 원천 데이터 적재와 품질 검증 | 결측률 1% 이하, 스키마 일치 |
| 2 | 피처 생성과 학습 실행 | 코드 SHA, 데이터 버전, 파라미터 기록 |
| 3 | 오프라인 평가와 배포 승인 | AUC, F1, RMSE 목표 충족 |
| 4 | 온라인 서빙과 감시 | p95 지연 100ms, PSI 0.2 미만 |

> 요약: MLOps는 검증 기준을 통과한 모델만 승인 배포하고 운영 지표가 임계값을 넘으면 재학습을 시작한다.

> 요약: 핵심 리스크는 재현성, 드리프트, 배포 불일치이며 버전 추적과 임계값 기반 운영으로 통제한다.

| 점검 항목 | 목표 기준 | 측정 방법 |
|:---|:---|:---|
| 모델 품질 | AUC, F1, RMSE 기준 충족 | 검증 데이터, 교차검증 |
| 서비스 지표 | p95 지연 100ms, 오류율 0.1% 이하 | APM, 서빙 로그 |
| 운영 통제 | 승인 이력 100%, 감사로그 보존 | 레지스트리, CI/CD 로그 |

> 요약: MLOps 도입 여부는 모델 품질, 서비스 지표, 승인 증적을 함께 측정해 판단한다.

## Ⅵ. 실무 적용 및 결론

**적용 방안 3개:**
1. MLflow 또는 Kubeflow로 학습 Run, 데이터 버전, 모델 아티팩트, 평가지표를 단일 메타데이터로 기록함
2. 레지스트리에 Staging, Production 단계를 두고 AUC 0.78 이상, p95 100ms 이하 조건 통과 모델만 배포함
3. Prometheus, Evidently, OpenTelemetry로 지연, 오류율, PSI를 감시하고 PSI 0.2 이상 시 재학습 티켓을 생성함

**결론 (2줄):**
- 기술사 판단: 운영 예측 결과가 업무 의사결정에 쓰이면 MLOps를 필수 적용하고, 실험성 모델은 추적과 평가 게이트부터 적용함
- 향후 방향: MLOps는 LLMOps, Feature Store, Model Governance와 결합해 모델 공급망 통제 체계로 확장됨
