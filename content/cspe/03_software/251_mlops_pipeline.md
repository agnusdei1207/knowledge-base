## Ⅰ. 개요
- **정의**: ML 모델의 학습·배포·운영을 자동화하는 CI/CD 파이프라인임
- **배경/필요성**: 모델 개발과 운영 사이 수작업 병목이 배포 지연과 품질 저하를 유발하므로 자동화 파이프라인이 필요함
- **비유**: 자동차 조립 라인처럼 데이터 수집부터 모델 배포까지 컨베이어 벨트로 연결한 구조임

| 출제 의도 | 반드시 짚을 핵심 | 감점 회피 포인트 |
|:---|:---|:---|
| ML 운영 자동화 체계 이해 | CT(Continuous Training) 포함 여부 | DevOps CI/CD와 CT 차이 누락 주의 |

> 요약: ML 생명주기 전체를 자동화하여 모델 품질과 배포 속도를 확보하는 파이프라인임

## Ⅱ. 구성요소
```text
Data Source --> Data Pipeline --> Feature Engineering
      |                                    |
      v                                    v
Model Training --> Model Validation --> Model Registry
                                            |
                                            v
                   Monitoring <-- Serving Infra
```

| 구성요소 | 설명 | 비유 |
|:---|:---|:---|
| Data Pipeline | 원천 데이터 수집·정제·버전 관리 수행 | 원재료 입고 검수 라인 |
| Model Training | 하이퍼파라미터 탐색·학습 자동 실행 | 조립 공정 자동화 |
| Model Validation | 정확도·공정성 등 품질 게이트 통과 검증 | 출하 전 품질 검사 |
| Serving Infra | REST/gRPC 엔드포인트로 모델 서빙 | 완성품 배송 시스템 |
| Monitoring | 입력 분포·예측 성능 실시간 감시 | 출하 후 리콜 감시 체계 |

> 요약: 데이터 수집부터 서빙·모니터링까지 5개 핵심 컴포넌트로 구성됨

## Ⅲ. 절차
```text
Data Ingestion --> Feature Build --> Train + Validate --> Deploy + Monitor
```
- 1단계: 데이터 수집·검증 — 스키마 드리프트 탐지 및 데이터 품질 게이트 적용
- 2단계: 피처 엔지니어링 — Feature Store(253 참조)에서 피처 생성·재사용
- 3단계: 학습·검증 — CT 트리거로 모델 재학습 후 성능 임곗값 기반 승인
- 4단계: 배포·모니터링 — 카나리/섀도 배포(257, 258 참조) 후 드리프트 감시

> 요약: 데이터 → 피처 → 학습 → 배포의 4단계를 자동 트리거로 연결함

## Ⅳ. 문제점
- 파이프라인 복잡도 증가: 컴포넌트 간 의존성이 늘어 장애 전파 범위가 확대됨
- 학습-서빙 불일치: 학습 환경과 서빙 환경 피처 계산 로직 차이로 예측 오차 발생
- 재현성 부족: 데이터·코드·환경 버전 중 하나라도 누락 시 실험 재현 불가

> 요약: 복잡도·불일치·재현성 세 축에서 운영 안정성 저하 위험이 존재함

## Ⅴ. 개선방안
1. 단기: DAG 기반 오케스트레이터 도입으로 컴포넌트 간 의존성 명시·격리
2. 중기: Feature Store 일원화로 학습-서빙 피처 계산 로직 통합
3. 장기: 데이터·코드·환경을 통합 버전 관리하는 Lineage 시스템 구축

> 요약: 오케스트레이션·피처 통합·리니지 관리로 단계적 성숙도를 높임

## Ⅵ. 전망
- 발전 방향: LLMOps(252 참조) 확장으로 대규모 언어 모델 파이프라인 통합 추세임
- 기술사적 판단: ML 시스템 성숙도 평가 시 파이프라인 자동화 수준이 핵심 지표임
- 기술사 제언: 조직 규모에 맞는 점진적 자동화 로드맵 수립이 필요함
