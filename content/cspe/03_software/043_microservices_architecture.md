## Ⅰ. 개요
- 정의: 애플리케이션을 비즈니스 경계(Bounded Context)에 따라 작고 독립적인 서비스 집합으로 구성.
- 출제 의도: 모놀리식의 한계를 극복하기 위한 분산 아키텍처의 설계 원칙 및 트레이드오프 이해도 평가.

## Ⅱ. 구성요소
- ASCII 구조도
  [ User ] -> [ API Gateway ]
                   |
  [ Service A ] [ Service B ] [ Service C ]
    (DB A)        (DB B)        (DB C)
- 구성요소 표
| 구성요소 | 설명 | 비유 |
| :--- | :--- | :--- |
| 독립된 DB | 서비스마다 전용 DB를 보유하여 데이터 결합도 제거 | 각자 지갑 관리 |
| 폴리글랏 | 서비스 특성에 맞는 최적의 언어와 기술 스택 선택 | 적재적소 인재 배치 |
| API Gateway | 모든 서비스의 단일 진입점으로 라우팅 및 공통 기능 처리 | 백화점 안내 데스크 |
> 요약: '작게 나누고, 각자 운영하며, API로 소통한다'는 핵심 사상을 기반으로 함.

## Ⅲ. 절차
- ASCII 흐름도
  [도메인 분석] -> [경계 설정] -> [독립 개발/배포] -> [API 기반 협업]
- 4단계 설명
1. 전략적 설계를 통해 비즈니스 도메인을 분석하고 하위 도메인 도출함.
2. 느슨한 결합을 유지할 수 있도록 각 서비스의 경계(Context)를 확정함.
3. 각 팀이 독립적인 생명주기를 가지고 서비스를 개발 및 지속 배포함.
4. HTTP/REST, gRPC, 메시지 큐 등을 통해 서비스 간 데이터를 교환함.
> 요약: 비즈니스 가치 단위로 팀과 시스템을 일치시키는 과정임.

## Ⅳ. 문제점
- 트랜잭션 관리: 분산 DB 구조에서 ACID 트랜잭션 보장이 어렵고 정합성 이슈 발생함.
- 테스트 복잡도: 단일 기능 확인을 위해 연관된 다수 서비스가 함께 구동되어야 함.

## Ⅴ. 개선방안
- Saga 패턴 적용: 보상 트랜잭션을 통해 분산 환경에서 결과적 정합성(Eventual Consistency) 유지함.
- 계약 테스트(Contract Test): CDC 등을 활용해 API 변경에 따른 영향도를 사전에 검증함.

## Ⅵ. 전망
- 서비스 메쉬와 결합하여 네트워크 관리의 복잡성을 인프라 레벨로 위임하는 구조 고착화됨.
- 'Database per Service' 원칙을 넘어 서버리스 DB 등 현대적 데이터 플랫폼과의 결합 가속화됨.
- 대규모 MSA의 관리 한계를 극복하기 위해 다시 일부를 통합하는 마크로서비스(Macro-services) 회귀 현상도 병행됨.
