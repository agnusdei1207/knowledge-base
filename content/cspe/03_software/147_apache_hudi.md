## 핵심 인사이트 (3줄 요약)
- 3대 오픈 테이블 포맷 중 유일하게 **"실시간 스트리밍(CDC) 데이터의 빈번한 UPDATE와 UPSERT(있으면 수정, 없으면 삽입)" 처리에 극단적으로 최적화**된 레이크하우스 스토리지 계층.
- 데이터 삽입 방식을 Copy-on-Write(안전하고 느림)와 Merge-on-Read(빠르게 쓰고 나중에 합침) 두 가지로 완벽히 분리 지원하여, 우버(Uber)처럼 매초 수백만 건의 위치 정보가 갱신되는 리얼타임 데이터 레이크에 최적화됨.
- Iceberg나 Delta Lake에 비해 설정이 복잡하고 무겁지만, RDB의 변경분(CDC)을 데이터 레이크로 가장 빠르고 정확하게 싱크(Sync) 맞추는 데 있어서는 절대적인 우위를 점함.

## Ⅰ. 개요 및 필요성
- **개요**: Hadoop Upserts Deletes and Incrementals의 약자로, HDFS나 클라우드 스토리지(S3) 위에서 레코드 수준의 삽입, 갱신, 삭제를 지원하는 데이터 레이크용 스토리지 프레임워크.
- **필요성**: 우버(Uber)는 전 세계 택시 위치가 1초마다 바뀌고, 요금이 취소(Delete)되기도 함. 기존 하둡(HDFS)에선 이 데이터를 갱신하려면 테라바이트급 파일을 몽땅 지우고 다시 써야 했음. "RDB처럼 딱 1줄만 빠르게 UPDATE 치고(Upsert), 어제부터 지금까지 변경된 데이터만 쏙 빼서(Incremental Pull) 스트리밍처럼 읽을 수 없을까?"라는 분노가 Hudi를 탄생시킴.
---
## Ⅱ. 아키텍처 및 핵심 원리
- **1. 타임라인 (Timeline) 기반 메타데이터**:
  - Hudi의 모든 동작은 '언제 무슨 일이 일어났는가'를 기록하는 타임라인(Commit Log)을 중심으로 돌아감.
  - 이 장부를 통해 "어제 오전 9시 이후에 UPDATE 된 데이터만 가져와 줘(Incremental Query)"라는 스트리밍스러운 쿼리를 데이터 레이크 위에서 수행할 수 있음.
- **2. 두 가지 스토리지 타입 (CoW vs MoR)**:
  - **Copy-on-Write (CoW)**: 데이터가 들어오면 기존 파일을 복사해서 새 파일로 씀. 쓸 때는 엄청 느리지만(Write 튜닝), 읽을 때는 디스크에서 쫙 읽으면 되므로 가장 빠름. (배치 분석용).
  - **Merge-on-Read (MoR)**: 데이터가 들어오면 정규 파일(Parquet)을 안 건드리고, 변경된 내역만 아주 가벼운 로그 파일(Avro)에 잽싸게 씀(Write 초고속). 나중에 읽을 때(Read) 두 파일을 메모리에서 합쳐서 보여줌. (실시간 대시보드용).
- **3. 인덱싱 (Indexing)**:
  - 레이크에서 특정 유저 1명의 데이터를 업데이트하려면 그 유저가 100만 개 파일 중 어디 있는지 찾아야 함.
  - Hudi는 Bloom Filter 인덱스나 자체 Record-level 인덱스를 내장하여, 전체 파일을 뒤지지 않고 정확히 그 파일만 콕 집어서 업데이트함.

```text
[ Hudi의 Merge-on-Read(MoR) 실시간 업데이트 원리 ]

 🚕 [ 우버 기사 위치 1초마다 변경됨 (CDC 스트림) ]
 
 1. 기존 방식 (Copy-on-Write):
 "위치 1건 바뀌었네? 1GB짜리 원본 파일 메모리에 올려서 1줄 고치고 다시 1GB 저장해!" ➡️ (1초마다 이 짓을 하면 서버 터짐 💥)

 2. Hudi MoR 방식:
 원본 파일(1GB Parquet)은 그냥 놔둠.
 "위치 1건 바뀌었네? 옆에 조그만 '변경 로그 파일(Avro)'에 0.1초 만에 쓱 적어놔!" 📝
 
 📊 [ 분석가가 쿼리 날릴 때 (Read) ]
 Hudi 엔진: "잠깐! 원본 1GB 읽고, 변경 로그 파일 쓱 합쳐서(Merge) 최신 뷰로 보여줄게!" 🚀
```

## Ⅲ. 비교 및 연결
| 구분 | Delta Lake | Apache Iceberg | Apache Hudi |
|---|---|---|---|
| **설계 철학** | ACID 트랜잭션, 데이터 정제 | **메타데이터 관리, 엔진 독립성** | **스트리밍(CDC), UPSERT 최적화** |
| **특화 기능** | Time Travel, Z-Ordering | Hidden Partitioning | **Incremental Query (증분 쿼리)** |
| **스토리지 타입**| Copy-on-Write 기본 | Copy-on-Write / Merge-on-Read | **CoW, MoR 완벽히 분리 지원** |
| **태생 / 후원** | Databricks | Netflix, Apple | **Uber, AWS** |

## Ⅳ. 실무 적용 및 기술사 판단
- **스트리밍 데이터 레이크 (Streaming Data Lake) 구축**: 기술사가 실무에서 카프카(Kafka)와 디비지움(Debezium)을 통해 운영 DB의 변경분(CDC)을 실시간으로 S3에 때려 붓는 아키텍처를 설계한다면, Iceberg나 Delta보다 Hudi가 압도적으로 유리함. Hudi의 `UPSERT`와 `MoR` 테이블을 활용하면 DB와 레이크 간의 동기화 지연(Latency)을 1~5분 이내로 극단적으로 단축시킬 수 있음.
- **컴팩션 (Compaction) 운영의 고통**: MoR 방식을 쓰면 쓰기는 빠르지만, 변경 로그 파일이 수백만 개로 쪼개져서 나중에 읽을 때(Read) 지옥처럼 느려짐. 따라서 엔지니어는 반드시 새벽 시간에 이 자잘한 로그 파일들을 원본 파일과 뭉쳐서 하나의 거대한 파일로 합쳐주는 '컴팩션(Compaction)' 배치를 주기적으로 돌려주어야 Hudi 클러스터가 뻗지 않음.
---
## Ⅴ. 기대효과 및 결론
- "데이터 레이크(S3)는 한 번 저장하면 수정하기 힘들다"는 편견을 완벽하게 부수고, 대규모 업데이트(Upsert)와 삭제(Delete)를 자유자재로 다루게 만든 빅데이터 튜닝의 결정체.
- 배치 중심의 레이크하우스를 넘어, 변경된 데이터만 쏙쏙 뽑아내어 후속 파이프라인으로 흘려보내는 진정한 '실시간(Real-time) 데이터 레이크' 시대를 개막한 주역임.

### 👶 어린이를 위한 3줄 비유 설명
1. 아주 두꺼운 백과사전(데이터 레이크)이 있는데, 매일매일 내용이 바뀌어서 수정테이프로 지우고 새로 쓰려면(CoW) 너무 팔이 아파요.
2. **아파치 후디(Hudi MoR)**는 아주 똑똑한 방법이에요. 백과사전은 안 건드리고, 바뀐 내용만 포스트잇(로그 파일)에 적어서 그 페이지에 쓱 붙여두는(Upsert) 거예요!
3. 나중에 책을 읽을 때는 백과사전 내용에 포스트잇 내용을 합쳐서(Merge) 읽으면 되니까, 글 쓰는 속도가 엄청나게 빠르답니다!
