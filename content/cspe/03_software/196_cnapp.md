# 📖 【암기용】 개념 완전 이해

> 목적: CNAPP을 처음 보는 사람도 왜 여러 보안 도구가 하나의 플랫폼으로 통합되어야 하는지, 위험 우선순위를 어떻게 계산하는지 완전히 이해하게 만든다. 시험 답안 양식이 아니라, 이해를 위한 설명이다.

## 한눈에
- **개요**: CNAPP(Cloud Native Application Protection Platform)은 **CSPM·CWPP·CIEM**을 하나의 **위험 그래프(Risk Graph)**로 통합해 공격 경로 기준으로 우선순위를 매기는 클라우드 네이티브 보안 플랫폼이다.
- **왜 필요한가**: CSPM, CWPP, CIEM, IaC 스캔이 따로 운영되면 같은 위험을 도구마다 다르게 보고해 무엇부터 조치할지 판단하기 어렵다.
- **핵심 직관**: 클라우드 보안용 조각 도구를 하나의 위험 그래프와 정책 게이트로 묶는 관제·통제 플랫폼이다.

## 핵심 용어 정리 (내부에 등장하는 것들)

| 용어 | 의미 | 비유 |
|:---|:---|:---|
| CSPM (클라우드 보안 상태 관리) | 클라우드 설정 오류(공개 버킷, 암호화 누락)를 찾는 기능 | 집안 문단속 점검 |
| CWPP (클라우드 워크로드 보호) | 컨테이너·VM·서버리스 런타임을 보호하는 기능 | 실시간 CCTV·경보 |
| CIEM (클라우드 권한 관리) | 과권한·미사용 IAM 권한을 분석하는 기능 | 안 쓰는 열쇠 회수 |
| IaC 스캔 | Terraform 등 인프라 코드를 배포 전 단계에서 검사 | 설계도 단계 검수 |
| 위험 그래프 (Risk Graph) | 노출·취약점·권한을 연결해 공격 경로를 계산하는 모델 | 여러 단서를 잇는 수사망 |
| Shift-Left | 취약점을 배포 전(코드·CI/CD) 단계에서 미리 차단하는 접근 | 완공 전에 하자 잡기 |
| SBOM (소프트웨어 자재명세서) | 소프트웨어에 포함된 구성요소 목록 | 식품 성분표 |

## 깊이 이해

### 왜 통합이 필요했나 (배경)
- 클라우드 네이티브 애플리케이션은 코드·컨테이너·Kubernetes·IAM·데이터 저장소가 빠르게 바뀐다. CSPM은 클라우드 설정만, CWPP는 런타임만, CIEM은 권한만 본다. 각 도구가 따로 알림을 울리면 담당자는 "이 셋이 사실은 같은 공격 경로의 일부"라는 것을 놓친다.

### 위험 우선순위 계산 — CVSS 단독과 무엇이 다른가
- 전통 방식은 CVSS(취약점 심각도 점수) 단독으로 우선순위를 매긴다. 예를 들어 CVSS 9.8짜리 Critical CVE가 있는 이미지라도, 그 컨테이너가 외부에 노출되지 않고 저권한으로 실행된다면 실제 악용 가능성은 낮다.
- CNAPP은 여기에 **노출 여부(인터넷 접근 가능한가?)**와 **권한 수준(과권한 IAM Role을 가졌는가?)**을 함께 본다. 같은 CVSS 9.8 취약점이라도, ① 인터넷에 노출된 Kubernetes Service, ② Critical CVE 이미지, ③ 과권한 IAM Role이 동시에 성립하면, 개별 항목보다 훨씬 높은 우선순위로 올라간다. 이것이 "위험 그래프" 방식이다.

### 위험 그래프의 동작 — 경로로 이해
- ① 자산 인벤토리(어떤 계정·클러스터·레지스트리가 있는가)를 만든다. ② 설정·권한·취약점을 수집한다. ③ "이 자산에서 저 자산으로 이동 가능한가"를 그래프의 연결선으로 표시한다. ④ 그래프상에서 "외부 진입점"에서 "민감 자산"까지 경로가 존재하는 조합을 Critical로 표시한다.
- 예: 공개 인터넷 → 노출된 Service(진입점) → 취약한 컨테이너(경유) → 과권한 IAM Role(권한 획득) → 프로덕션 DB(민감 자산)로 경로가 이어지면, 이 4개 요소는 개별 조치보다 경로 차단(진입점을 막거나 권한을 낮춤)이 우선이다.

### CI/CD 게이트 — Shift-Left의 수치 기준
- Code·IaC 단계에서 Critical CVE 0건, Secret 0건 같은 정책을 배포 차단 조건으로 건다. 예: 자산 커버리지 95% 이상을 목표로 신규 계정·클러스터를 자동 온보딩하지 않으면, 그 5%의 사각지대가 공격 경로 계산에서 빠진다.

### 비유
- 공항 보안에서 여권, 수하물, 탑승구, 관제 정보를 따로따로 보지 않고 한 승객의 전체 위험 점수로 판단하는 방식과 같다. 개별 서류는 정상이어도 조합이 이상하면 걸러낸다.

## 연결 개념
- 클라우드 네이티브 보안 4C: CNAPP이 포괄하는 계층 모델
- CSPM·CWPP·CIEM: CNAPP을 구성하는 세 기능 축
- DevSecOps: CI/CD 단계에서 정책 게이트를 적용하는 실천 방법론

# 📝 【답안용】 시험 답안 템플릿

> 목적: CNAPP을 제품명이 아니라 CSPM·CWPP·CIEM·CI/CD 보안을 결합한 플랫폼 관점으로 작성한다.
> 핵심: 출제자는 통합 플랫폼의 기능 나열보다 공격 경로 기반 우선순위와 정책 자동화 설계를 본다.

## 핵심 인사이트 (3줄 요약)

> 1. **본질**: CNAPP은 클라우드 네이티브 애플리케이션의 설정, 워크로드, 권한, 코드 보안을 통합 분석하는 보호 플랫폼이다.
> 2. **가치**: 취약점, 노출, 과권한을 공격 경로 그래프로 연결해 Critical 위험을 우선 조치한다.
> 3. **판단 포인트**: CI/CD 게이트와 런타임 탐지를 모두 포함해야 하며, SIEM·SOAR와 연계해 대응까지 이어져야 한다.

## 출제 의도 및 답안 포인트

| 출제 의도 | 반드시 짚을 핵심 | 감점 회피 포인트 |
|:---|:---|:---|
| 클라우드 통합 보안 플랫폼 이해 확인 | CSPM, CWPP, CIEM, IaC, 이미지, 런타임 | CSPM 하나로 축소 설명 |
| 위험 우선순위 판단 확인 | 노출+취약점+권한 기반 공격 경로 | CVE 점수만 기준으로 조치 |
| DevSecOps 연계 확인 | CI/CD 정책 게이트, 런타임 탐지 | 운영 단계 탐지 누락 |

> 요약: CNAPP 답안은 분산된 클라우드 보안 점검을 위험 그래프와 정책 게이트로 통합하는 구조를 제시해야 한다.

## Ⅰ. 개요 및 필요성

- 개요: 클라우드 앱 보호 플랫폼
- 배경: Kubernetes, 서버리스, IaC, 멀티 클라우드 환경은 설정 오류와 권한 위험이 누적된다.
- 필요성: CSPM, CIEM, CWPP, IaC scan을 통합해 개발부터 운영까지 위험 우선순위와 조치 기준을 제공한다.

---

## Ⅱ. 구조 및 구성요소

```text
IaC/Code -> Image Scan -> CSPM/CIEM -> CWPP/Runtime
                         +-> Risk Graph -> Policy Gate/SIEM/SOAR
```

| 구성요소 | 역할 | 특이사항 |
|:---|:---|:---|
| CSPM | 클라우드 설정 오류 탐지 | 공개 버킷, 암호화 누락 |
| CWPP | 워크로드 보호 | 컨테이너, VM, 서버리스 런타임 |
| CIEM | 권한 분석 | 과권한 IAM, 미사용 권한 |
| DevSecOps Gate | 코드·IaC·이미지 배포 차단 | Critical CVE 0건 정책 |
| Risk Graph | 노출·취약점·권한 연결 | 공격 경로 우선순위 |

> 요약: CNAPP은 코드와 런타임, 설정과 권한을 하나의 위험 그래프로 연결해 조치 순서를 정한다.

---

## Ⅲ. 동작원리 및 흐름도

```text
자산 식별 -> 설정/권한/취약점 수집 -> 공격 경로 분석
-> 위험 점수 산정 -> CI/CD 차단 또는 티켓 생성 -> 런타임 대응
```

| 단계 | 처리 내용 | 검증 기준 |
|:---:|:---|:---|
| 1 | 멀티 클라우드 자산 인벤토리 | 자산 태깅률 95% 이상 |
| 2 | 설정·권한·취약점 수집 | Critical CVE, 공개 노출 |
| 3 | 위험 상관분석 | 인터넷 노출+과권한 조합 |
| 4 | 정책 게이트 적용 | 배포 차단, 승인 예외 |
| 5 | 대응 연계 | SIEM 이벤트, SOAR 플레이북 |

> 요약: CNAPP은 개별 취약점이 아니라 공격 가능 경로를 계산하고 CI/CD와 운영 대응에 연결한다.

## Ⅴ. 심화 비교 및 적용 판단

| 구분 | 기존/대안 | 본 키워드 | 선택 기준 |
|:---|:---|:---|:---|
| 구조 | CSPM, CWPP, CIEM 분리 | CNAPP 통합 플랫폼 | 멀티 클라우드·K8s 운영 시 |
| 비용/성능 | 도구별 라이선스와 중복 알림 | 통합 점검과 우선순위 | 중복 경보 30% 이상 시 |
| 운영/위험 | 보안팀 수동 조치 | 정책 게이트와 SOAR 연계 | DevSecOps 성숙도 필요 |

> 요약: CNAPP은 클라우드 보안 도구가 분산되고 위험 우선순위 산정이 어려운 조직에서 선택한다.

| 리스크 | 원인 | 대응 방안 | 확인 지표 |
|:---|:---|:---|:---|
| 과잉 차단 | 정책 기준 과도 | 예외 승인과 만료일 적용 | 배포 차단 오탐률 |
| 자산 누락 | 계정·클러스터 미연동 | 조직 계정 자동 온보딩 | 자산 커버리지 95% 이상 |
| 플랫폼 종속 | 단일 벤더 정책 언어 | OPA, SARIF, SBOM 표준 연계 | 정책 이식률 |

> 요약: CNAPP 운영 리스크는 자산 누락과 과잉 차단이므로 커버리지와 예외 만료를 통제해야 한다.

| 점검 항목 | 목표 기준 | 측정 방법 |
|:---|:---|:---|
| 위험 조치 | Critical 경로 24시간 내 조치 | CNAPP 대시보드 |
| 권한 | 미사용 고권한 0건 | CIEM 분석 |
| 배포 통제 | Critical CVE 배포 0건 | CI/CD 정책 로그 |

> 요약: CNAPP 성과는 Critical 공격 경로 조치 시간, 과권한 제거, 배포 차단 준수율로 확인한다.

## Ⅵ. 실무 적용 및 결론

**적용 방안 3개:**
1. CSPM, CWPP, CIEM, IaC 스캔을 CNAPP에 통합하고 계정·클러스터·레지스트리 자산 커버리지 95% 이상을 확보함
2. 인터넷 노출, Critical CVE, 과권한 IAM이 동시에 존재하는 경로를 1순위로 두고 24시간 내 조치 SLA를 운영함
3. CI/CD에서 Critical CVE, Secret, 공개 스토리지 정책 위반을 차단하고 예외는 승인자·만료일·감사 로그를 남김

**결론 (2줄):**
- 기술사 판단: 멀티 클라우드와 Kubernetes를 함께 운영하면 CNAPP 통합이 필요하고, 단일 계정 소규모 환경은 CSPM부터 단계 적용함
- 향후 방향: SBOM, SLSA, OPA, SOAR 연계로 공급망 보안과 자동 대응까지 확장함
