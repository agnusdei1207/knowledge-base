## Ⅰ. 개요
- **정의**: 장애 발생 시 DB를 일관된 상태로 복원하는 기법이며, ACID 중 Durability를 구현함
- **배경/필요성**: 시스템 충돌·미디어 장애 시 커밋된 데이터 손실을 방지해야 함
- **비유**: 게임의 세이브 포인트에서 복원하여 진행 상태를 되살리는 것과 같음

| 출제 의도 | 반드시 짚을 핵심 | 감점 회피 포인트 |
|:---|:---|:---|
| 장애 유형별 회복 기법 이해 | Redo/Undo 구분, WAL 원칙 | 체크포인트의 회복 시간 단축 효과 |

> 요약: 로그 기반 Redo/Undo로 장애 후 DB 정합성을 복원하는 기법임

## Ⅱ. 구성요소
```text
DB Recovery
 +-- Redo Log ------- 커밋된 변경 재적용
 +-- Undo Log ------- 미완료 변경 취소
 +-- Checkpoint ----- 회복 시작점 설정
 +-- WAL ------------ 데이터 변경 전 로그 선기록
```

| 구성요소 | 설명 | 비유 |
|:---|:---|:---|
| Redo Log | 커밋되었으나 디스크 미반영 변경을 재적용 | 작업 일지 재실행 |
| Undo Log | 커밋되지 않은 트랜잭션의 변경을 원복 | 되감기 |
| Checkpoint | 메모리-디스크 동기화 시점, 회복 범위를 축소 | 세이브 포인트 |

> 요약: Redo·Undo 로그와 Checkpoint가 회복의 3대 메커니즘임

## Ⅲ. 절차
```text
장애 발생 --> 로그 분석 --> Redo --> Undo
```
- 1단계: 장애 감지 후 마지막 체크포인트 위치 확인
- 2단계: 체크포인트 이후 로그를 순방향 스캔하여 Redo/Undo 대상 분류
- 3단계: 커밋된 트랜잭션의 변경을 Redo(재적용)하여 데이터 복원
- 4단계: 미커밋 트랜잭션의 변경을 Undo(취소)하여 일관성 확보

> 요약: 체크포인트 기준 로그분석-Redo-Undo 3단계로 DB를 복원함

## Ⅳ. 문제점
- 회복 시간 장기화: 체크포인트 간격이 넓으면 Redo/Undo 대상 로그 증가
- 로그 저장 비용: 모든 변경을 로그로 기록하므로 I/O 오버헤드와 저장 공간 소모
- 미디어 장애: 디스크 자체 손상 시 로그만으로는 복구 불가

> 요약: 회복 지연, 로그 비용, 미디어 장애가 DB 회복의 주요 과제임

## Ⅴ. 개선방안
1. 단기: 체크포인트 주기를 단축하여 Redo/Undo 범위 축소
2. 중기: 로그 압축·아카이빙으로 I/O 부하와 저장 비용 절감
3. 장기: 이중화(미러링)·원격 백업으로 미디어 장애에 대비

> 요약: 체크포인트 최적화, 로그 압축, 이중화로 회복력을 강화함

## Ⅵ. 전망
- 발전 방향: NVM(비휘발성 메모리) 기반 로그리스 회복 기법 연구 확대
- 기술사적 판단: WAL 기반 회복은 RDBMS 안정성의 핵심 기반 기술임
- 기술사 제언: RPO/RTO 요건에 맞춰 회복 전략(로그·백업·복제)을 설계할 필요
