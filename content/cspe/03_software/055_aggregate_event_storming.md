# 📖 【암기용】 개념 완전 이해

## 한눈에
- **개요**: 이벤트 스토밍은 비즈니스 이벤트를 중심으로 도메인 전문가와 개발자가 모여 시스템 흐름을 파악하는 워크숍 기법이며, 애그리게이트는 관련된 객체들을 묶은 데이터 변경의 논리적 단위이다.
- **왜 필요한가**: 기획자는 화면으로, 개발자는 DB 테이블로 이야기하면 평행선을 달린다. 이를 "어떤 사건(이벤트)이 일어나는가?"라는 시간순 흐름으로 맞추면 소통이 폭발적으로 개선된다. 여기서 도출된 '데이터 변경 묶음'이 애그리게이트가 된다.
- **핵심 직관**: 영화 스토리보드 작성과 같다. 벽에 포스트잇을 시간순으로 붙인다. 중요한 사건(도메인 이벤트)을 먼저 붙이고, 그 사건을 누가/왜(커맨드) 일으켰는지 추적하며, 어떤 데이터 묶음(애그리게이트) 단위로 변하는지 찾는다.

## 핵심 용어 정리

| 용어/표기 (포스트잇 색상) | 의미 | 비유·예 |
|:---|:---|:---|
| 도메인 이벤트 (주황색) | 시스템에서 발생한 의미 있는 비즈니스 사실 (과거형) | "주문이 결제됨", "배송이 시작됨" |
| 커맨드 (파란색) | 이벤트를 발생시키는 시스템을 향한 명령/요청 | "결제 승인 요청", "주문 취소" |
| 애그리게이트 (노란색) | 커맨드를 받아 상태를 변경하고 이벤트를 발생시키는 응집된 도메인 객체의 묶음 | 트랜잭션을 함께 처리해야 하는 '주문서+주문항목' 묶음 |
| 액터/시스템 (작은 노란색/분홍색) | 커맨드를 실행하는 사용자나 외부 연동 시스템 | "고객", "PG사 결제 모듈" |

## 깊이 이해
- **배경·문제의식**: 요구사항 분석을 다이어그램(UML) 기반으로 하면, 비개발자가 이해하기 어려워 형식적인 문서 작업으로 전락한다. 이를 타파하기 위해 Alberto Brandolini가 제안한 가볍고 직관적인 워크숍이 이벤트 스토밍이다. 
- **작동 원리 (이벤트 스토밍)**: 넓은 벽과 포스트잇만 있으면 된다.
  1. 먼저 시간순으로 '무슨 일이 벌어졌는지(도메인 이벤트)'를 주황색 포스트잇으로 나열한다.
  2. 그 사건을 일으킨 원인(커맨드)을 파란색으로 붙인다.
  3. 이 커맨드가 수행될 때 변경되어야 하는 데이터의 묶음(애그리게이트)을 노란색으로 붙인다.
- **작동 원리 (애그리게이트)**: (053 DDD 전술적 설계) 애그리게이트는 단일 트랜잭션으로 처리되어야 하는 일관성 경계다. 애그리게이트 내부의 객체는 반드시 하나의 '애그리게이트 루트(Root Entity)'를 통해서만 제어된다. 외부에서는 루트만 참조할 수 있고 내부 객체를 직접 건드릴 수 없다.
- **구체 예시**: `주문(Order)`과 `주문 상세 항목(OrderLine)`은 하나의 애그리게이트다. '주문 취소' 커맨드가 오면, 반드시 `Order` 루트 객체를 통해서 전체 항목의 상태를 일관성 있게 변경해야 한다.

## 연결 개념
- 도메인 주도 설계 (DDD) — 이벤트 스토밍은 DDD의 유비쿼터스 언어와 바운디드 컨텍스트를 도출하는 가장 실용적인 도구
- 마이크로서비스 아키텍처 (MSA) — 이벤트 스토밍으로 식별된 바운디드 컨텍스트가 곧 MSA 서비스 후보가 됨
- 트랜잭션 경계 (Transaction Boundary) — 애그리게이트는 데이터베이스 트랜잭션이 한 번에 묶이는 범위

# 📝 【답안용】 시험 답안 템플릿

## 핵심 인사이트 (3줄 요약)

> 1. **본질**: 이벤트 스토밍은 비즈니스 흐름을 도메인 이벤트 중심으로 시각화하는 워크숍 기법이며, 애그리게이트는 트랜잭션 일관성을 보장하는 도메인 모델의 군집 단위이다.
> 2. **가치**: 복잡한 UML 없이 도메인 전문가와 개발자 간의 소통 장벽을 제거하고, MSA 서비스 도출 및 트랜잭션 경계 설정을 직관적으로 해결한다.
> 3. **판단 포인트**: 애그리게이트를 너무 크게 잡으면 동시성 충돌(DB 락)이 발생하므로, 반드시 단일 트랜잭션 내에서 처리해야 할 최소한의 범위를 애그리게이트로 산정해야 한다.

## 출제 의도 및 답안 포인트

| 출제 의도 | 반드시 짚을 핵심 | 감점 회피 포인트 |
|:---|:---|:---|
| 요구사항 분석 및 소통 기법 역량 확인 | 이벤트, 커맨드, 애그리게이트의 도출 순서 및 관계 | 포스트잇 색상만 나열하고 객체 설계와의 연결성 누락 |
| 전술적 모델링 트랜잭션 설계 파악 | 애그리게이트 루트, 단일 트랜잭션 일관성 경계 | 애그리게이트가 단순한 데이터 묶음(테이블 조인)이라는 단정 |
| MSA 연계 활용 방안 제시 | 이벤트 기반 아키텍처(EDA), 바운디드 컨텍스트 도출 | 모놀리식 글로벌 트랜잭션 처리 방식으로 오답 기재 |

> 요약: 비즈니스 사건 중심의 요구사항 도출부터 응집된 트랜잭션 객체 설계, 최종적으로 MSA 서비스 분할로 이어지는 일련의 흐름을 보여주어야 한다.

## Ⅰ. 개요 및 필요성

- 개요: 이벤트 스토밍은 비즈니스 이벤트를 중심으로 도메인 지식을 시각화하는 기법이며, 애그리게이트는 이를 기반으로 도출된 트랜잭션 일관성 유지 객체 군집임
- 배경: 전통적 요구사항 분석 기법(UML 등)은 비개발자의 참여를 방해하여, 비즈니스 룰과 코드가 괴리되는 현상 발생
- 필요성: 직관적 워크숍을 통해 유비쿼터스 언어를 단기에 확립하고, 데이터 변경 시 무결성을 보장하기 위한 최소 트랜잭션 단위 식별 필수

---

## Ⅱ. 구조 및 구성요소

```text
액터/시스템 -> 커맨드 -> [ 애그리게이트 (루트 엔티티 + 내부 엔티티) ] -> 도메인 이벤트 -> 읽기 모델/정책
  (사용자)    (명령)                          (상태 변경 묶음)             (결과 사실)     (화면/규칙)
```

| 구성요소 | 역할 | 매핑 산출물 |
|:---|:---|:---|
| 도메인 이벤트 (주황) | 비즈니스상 의미 있는 사실을 과거형으로 정의 | 메시지 큐 이벤트 페이로드 |
| 커맨드 (파랑) | 특정 사용자가 이벤트를 발생시키기 위해 내리는 명령 | REST API Endpoint (Controller) |
| 애그리게이트 (노랑) | 커맨드를 처리하여 상태를 변경하고 무결성을 유지하는 객체 묶음 | 트랜잭션 경계, 도메인 클래스 망 |
| 애그리게이트 루트 | 외부에서 애그리게이트 내부로 접근하는 유일한 진입점 | Repository 접근 단위 |

> 요약: 커맨드는 애그리게이트의 상태를 변경하여 도메인 이벤트를 발생시키며, 이 묶음은 완벽한 트랜잭션 경계가 된다.

---

## Ⅲ. 동작원리 및 흐름도

```text
이벤트 도출 -> 커맨드 및 액터 매핑 -> 애그리게이트 식별 -> 바운디드 컨텍스트 획정
```

- 1단계 [도메인 이벤트 도출]: 시간 흐름(좌->우)에 따라 시스템에서 발생하는 모든 과거형 이벤트를 주황색 포스트잇으로 나열
- 2단계 [커맨드 및 액터 식별]: 해당 이벤트를 트리거하는 사용자(액터)의 명령(커맨드)을 파란색 포스트잇으로 매핑
- 3단계 [애그리게이트 식별]: 커맨드 수행 시 상태가 함께 변해야 하는 객체들의 군집을 찾아 노란색 애그리게이트로 정의
- 4단계 [바운디드 컨텍스트 획정]: 연관된 이벤트와 애그리게이트를 묶어 응집도 높은 바운디드 컨텍스트(경계) 설정 후 마이크로서비스 도출

> 요약: 시간순 이벤트 식별에서 시작하여, 명령과 주체를 파악한 뒤 데이터의 묶음(애그리게이트)과 시스템 경계(컨텍스트)로 구체화된다.

---

## Ⅳ. 특징

- 최상의 커뮤니케이션 툴: 기술적 용어(DB 등)를 철저히 배제하고 비즈니스 흐름 자체에 집중하여 전 직군의 합의 도출 비용 최소화
- 단일 트랜잭션 경계: 애그리게이트 1개당 1개의 데이터베이스 트랜잭션을 강제하여 교착 상태(Deadlock) 방지 및 무결성 확보
- 복잡도 병목: 워크숍 참여 인원이 많거나 도메인이 너무 방대하면 이벤트의 파편화가 발생하여 퍼실리테이터(조정자)의 역량에 크게 의존

> 요약: 요구사항 도출과 초기 아키텍처 뼈대를 잡는 데 압도적으로 효율적이나, 퍼실리테이터의 리딩 역량이 성패를 좌우한다.

## Ⅴ. 심화 비교 및 적용 판단

| 비교 축 | 글로벌 트랜잭션 (기존) | 애그리게이트 단위 트랜잭션 | 선택 기준 |
|:---|:---|:---|:---|
| 데이터 잠금 범위 | 연관된 여러 테이블 동시 Lock 처리 | 단일 애그리게이트 루트 단위 Lock | 성능 및 동시성 처리 요구 수준 |
| 일관성 모델 | 강한 일관성 (ACID 동시 보장) | 애그리게이트 내 강한 일관성 + 외부 최종 일관성 | 실시간 반영 필수 여부 |
| 객체 참조 방식 | 모든 엔티티를 포인터(참조)로 직접 연결 | 다른 애그리게이트는 식별자(ID)로만 간접 참조 | 메모리/성능 최적화 및 결합도 제어 |

> 요약: 애그리게이트를 넓게 잡으면 데이터 일관성은 강해지나 동시성 병목이 생기므로, 반드시 필요한 최소 범위로 축소해야 한다.

**리스크·대응:**
- 거대 애그리게이트(Fat Aggregate) 병목: 불필요한 연관관계까지 묶어 빈번한 DB 충돌 발생 → '결과적 일관성'이 허용되는 부분은 이벤트를 발행하여 다른 애그리게이트로 로직 비동기 위임 (지표: 낙관적 락 충돌률)
- 외부 직접 참조 오염: 외부에서 애그리게이트 내부 객체를 직접 수정하여 무결성 파괴 → 오직 '애그리게이트 루트'를 통해서만 상태 변경을 허용하도록 코드 캡슐화 (지표: 내부 객체에 대한 외부 의존성 수)

## Ⅵ. 실무 적용 및 결론

**적용 방안 3개:**
1. MSA 서비스 식별 및 분할 가이드: 이벤트 스토밍으로 도출된 바운디드 컨텍스트 경계를 기준으로 레거시 시스템의 서비스 분할(Strangler Pattern) 선행 지표로 활용
2. 이벤트 드리븐 아키텍처(EDA) 연계: 도출된 '도메인 이벤트'를 Kafka 메시지 페이로드 명세로 직결하여, 마이크로서비스 간 비동기 통합 아키텍처 설계
3. 저장소 패턴(Repository Pattern) 매핑: ORM(JPA 등) 적용 시 1개의 애그리게이트 루트당 1개의 Repository만 생성하도록 제한하여 데이터 무결성 보장

**결론 (2줄):**
- 기술사 판단: 이벤트 스토밍은 MSA 설계를 위한 가장 빠르고 강력한 기법이며, 도출된 애그리게이트 크기의 적절성이 향후 시스템 동시성 성능을 결정하는 핵심 지표가 됨
- 향후 방향: 단순 워크숍을 넘어 도출된 이벤트를 직접 소스 코드로 자동 스캐폴딩(Scaffolding)하는 LLM 기반 자동화 도구 연계로 발전 중임
