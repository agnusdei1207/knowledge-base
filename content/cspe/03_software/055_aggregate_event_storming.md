## 핵심 인사이트 (3줄 요약)
- **이벤트 스토밍(Event Storming)**: 기획자부터 개발자까지 모든 이해관계자가 모여, 주황색 포스트잇(도메인 이벤트)을 벽에 붙이며 비즈니스 흐름을 단숨에 시각화하고 바운디드 컨텍스트를 도출하는 워크숍 기법.
- **애그리거트(Aggregate)**: DDD의 전술적 패턴으로, 관련된 객체(엔티티와 값 객체)들을 하나의 군집으로 묶고 '루트(Root)'를 통해서만 데이터 변경을 허용하여 **트랜잭션의 일관성**을 보장하는 단위.
- 복잡한 비즈니스 요구사항을 시각화(스토밍)하여 경계를 나눈 뒤, 그 내부를 단단한 데이터 군집(애그리거트)으로 구현하는 환상의 조합임.

## Ⅰ. 개요 및 필요성
- **개요**: 도메인 분석을 위한 실천적 워크숍(Event Storming)과, 도메인 모델을 실제 코드로 구현하기 위한 데이터 일관성 경계(Aggregate).
- **필요성**: DDD를 책으로만 배우면 "그래서 실제로 어떻게 시작하라는 거냐?"라는 막막함에 빠짐. Alberto Brandolini가 창안한 이벤트 스토밍은 가벼운 포스트잇만으로 비즈니스를 파악하게 해 주며, 도출된 모델을 코드로 짤 때 데이터베이스의 무결성을 깨뜨리지 않을 캡슐화 단위(애그리거트)가 필수적임.
---
## Ⅱ. 아키텍처 및 핵심 원리
- **이벤트 스토밍의 주요 포스트잇(색상)**:
  1. 🟧 **Domain Event (주황)**: "주문이 생성됨", "결제가 승인됨" (과거 분사형). 모든 흐름의 시작.
  2. 🟦 **Command (파랑)**: 이벤트를 발생시키는 사용자 또는 시스템의 행동 ("주문하기").
  3. 🟨 **Aggregate (노랑)**: 커맨드를 받아 이벤트를 발생시키는 비즈니스 상태/데이터의 주체 ("주문").
  4. 🟪 **Policy (보라)**: 이벤트 발생 시 뒤이어 실행되어야 할 규칙 ("결제 승인 시 영수증 발송").
- **애그리거트 설계 원칙**:
  - **Aggregate Root (루트 엔티티)**: 군집의 대장. 외부에서는 오직 루트를 통해서만 내부 데이터에 접근할 수 있음. (예: `Order` 객체를 통해서만 `OrderLine(주문항목)`을 추가/삭제 가능).
  - **1트랜잭션 1애그리거트**: 하나의 DB 트랜잭션 안에서는 반드시 1개의 애그리거트만 수정되어야 함 (Lock 범위 최소화, 성능 향상).

```text
[ 이벤트 스토밍 시각화 흐름 (벽면의 포스트잇) ]

 [👤 User] ➡️ (명령/파랑) ➡️  { 애그리거트 / 노랑 }  ➡️ (결과/주황) ➡️ [ 보라 / 정책 ]
                [ 주문 생성 ]      { Order (주문) }     [ 주문 완료됨 ]   (알림톡 발송)
                                        |  (캡슐화)
                          +-------------+-------------+
                          |                           |
                  (루트) [ Order ] (상태/금액)        [ OrderLine (항목) ]
```

## Ⅲ. 비교 및 연결
| 구분 | ERD 기반 데이터 모델링 | 이벤트 스토밍 기반 모델링 (Event Storming) |
|---|---|---|
| **초점** | 데이터 구조와 테이블 관계 (명사 중심) | 시스템에서 발생하는 사건/흐름 (동사 중심) |
| **참여자** | DBA, 시스템 아키텍트 중심 | 기획, 디자인, 영업, 개발 전 직군 참여 |
| **상태 관리** | DB 외래키(FK)로 전체 무결성 강제 | **애그리거트** 단위로만 무결성 보장 (느슨한 결합) |
| **결과물** | 정적인 테이블 스키마 | MSA 분리를 위한 바운디드 컨텍스트 지도 |

## Ⅳ. 실무 적용 및 기술사 판단
- **애그리거트 크기의 딜레마**: 애그리거트를 너무 크게 잡으면(예: '주문' 안에 '배송', '결제'까지 다 넣음) 여러 사용자가 동시에 접근할 때 낙관적 잠금(Optimistic Lock) 충돌이 미친 듯이 발생함. 반대로 너무 작게 잡으면 데이터 정합성을 맞추기 위해 복잡한 Saga 패턴을 써야 함. "한 번의 트랜잭션으로 반드시 같이 변해야 하는 최소한의 단위"로 작게 유지하는 것이 핵심 실무 원칙임.
- **참조는 ID로만**: 애그리거트 간에는 직접 객체를 참조(Object Reference)하지 않고, 무조건 `ID(식별자)`로만 참조해야 함. 이는 훗날 MSA로 DB 파편화 시 코드를 뜯어고칠 필요가 없게 만드는 신의 한 수임.
---
## Ⅴ. 기대효과 및 결론
- 이벤트 스토밍은 IT 업계에서 비즈니스 도메인을 분석하는 가장 빠르고 협력적인 '살아있는 문서화' 도구로 정착함.
- 설계된 애그리거트는 동시성 문제와 DB 락(Lock) 문제를 해결해 주며, 대규모 트래픽을 견디는 확장 가능한(Scalable) 클라우드 시스템 아키텍처의 근간 코드가 됨.

### 👶 어린이를 위한 3줄 비유 설명
1. 이벤트 스토밍은 친구들이 다 같이 큰 화이트보드에 모여, "그다음엔 무슨 일(이벤트)이 일어나지?" 하면서 색깔 포스트잇을 붙여가며 이야기꽃을 피우는 놀이예요.
2. 애그리거트는 '포도송이'와 같아요. 알맹이(작은 데이터)들이 가지(루트)에 단단히 붙어있죠.
3. 알맹이를 떼어먹으려면 억지로 파고들지 않고 무조건 가장 위에 있는 굵은 가지(루트)를 통해서만 가져가야 포도송이가 망가지지 않는답니다!
