# 📖 【암기용】 개념 완전 이해

> 목적: 애그리게이트와 이벤트 스토밍을 처음 보는 사람도 완벽히 이해하게 만든다. 시험 답안 양식이 아니라, 이해를 위한 친절한 설명이다.

## 한눈에
- **개요**: 이벤트 스토밍으로 도메인 흐름을 발견하고 애그리게이트로 일관성 경계를 잡는 DDD 기법
- **왜 필요한가**: 복잡한 업무는 화면과 테이블만 보면 숨은 정책, 예외, 책임자가 드러나지 않는다. 이벤트를 시간순으로 놓으면 업무 변화와 트랜잭션 경계가 보인다.
- **핵심 직관**: "무슨 데이터가 있나"보다 "업무에서 무슨 일이 일어났나"를 먼저 나열해 모델을 찾는다.

## 깊이 이해
- **배경·문제의식**: 요구사항 회의가 기능 목록 중심이면 결제 실패, 재고 부족, 승인 반려 같은 예외 흐름이 늦게 발견된다.
- **작동 원리**: Domain Event를 시간순으로 놓고, Command, Actor, Policy, External System, Hot Spot을 붙인 뒤, 불변식을 함께 지켜야 하는 객체 묶음을 Aggregate로 정한다.
- **비유**: 사고 조사를 할 때 결과 보고서보다 시간대별 사건 기록을 먼저 맞춰 원인과 책임 경계를 찾는 과정과 같다.
- **구체 예시**: `주문생성됨 -> 결제승인됨 -> 재고예약됨 -> 배송요청됨` 이벤트에서 주문 취소 가능 상태와 재고 예약 수량을 한 트랜잭션으로 묶을지 분리할지 판단한다.
- **흔한 오해·주의점**: 모든 이벤트를 시스템 이벤트로 구현할 필요는 없다. 워크숍 산출물과 운영 이벤트는 목적이 다르다.

## 연결 개념
- Aggregate: 불변식을 지키는 트랜잭션 경계
- Domain Event: 도메인에서 의미 있는 상태 변화
- Saga·Outbox: 애그리게이트 간 최종 일관성 처리

# 📝 【답안용】 시험 답안 템플릿

> 목적: 시험장에서 25분에 그대로 쓰는 답안 양식. 작성방식(추상표현 금지·수치·도식·문제유형 전환)을 엄격히 지킨다.
> 핵심: 이벤트 스토밍은 워크숍이고, 애그리게이트는 트랜잭션 경계라는 차이를 명확히 쓴다.

## 핵심 인사이트 (3줄 요약)

> 1. **본질**: 이벤트 스토밍은 도메인 이벤트 중심으로 업무 흐름을 탐색하는 협업 기법이며, 애그리게이트는 불변식을 보호하는 일관성 경계이다.
> 2. **가치**: 숨은 정책과 예외를 조기에 드러내고, MSA·DDD 설계에서 트랜잭션 경계와 이벤트 통합 기준을 제공한다.
> 3. **판단 포인트**: 같은 트랜잭션에서 지켜야 할 규칙은 애그리게이트 내부, 지연 허용 규칙은 이벤트 기반 통합으로 분리한다.

## 출제 의도 및 답안 포인트

| 출제 의도 | 반드시 짚을 핵심 | 감점 회피 포인트 |
|:---|:---|:---|
| DDD 모델 발견 역량 확인 | Domain Event, Command, Policy, Hot Spot, Aggregate | 이벤트를 로그 메시지로만 설명 |
| 일관성 경계 판단 확인 | Aggregate Root, 불변식, 트랜잭션 경계 | 모든 객체를 하나의 Aggregate로 묶음 |
| MSA 통합 설계 확인 | Domain Event, Saga, Outbox, 최종 일관성 | 분산 트랜잭션 2PC만 제시 |
> 요약: 출제자는 이벤트 탐색에서 트랜잭션 경계와 통합 방식을 도출하는 능력을 본다.

## Ⅰ. 개요 및 필요성

이벤트 스토밍은 도메인 이벤트 기반 모델 탐색 기법이다.
요구사항을 기능 목록으로만 정리하면 정책, 예외, 책임 경계가 누락된다.
이벤트 흐름을 통해 Command, Policy, Aggregate를 식별하고 일관성 경계를 설계한다.

---

## Ⅱ. 구조 및 구성요소

```text
Actor -> Command -> Aggregate -> Domain Event
Domain Event -> Policy -> Command
Domain Event -> External System
Hot Spot -> Risk / Question / Decision
Aggregate -> Transaction Boundary -> Consistency Rule
```

| 구성요소 | 역할 | 특이사항 |
|:---|:---|:---|
| Domain Event | 이미 발생한 업무상 사실 | 과거형 명명, 시간순 배치 |
| Command | 이벤트를 유발하는 의도 | Actor와 입력 조건 연결 |
| Policy | 이벤트 후 실행되는 업무 규칙 | 자동 명령 또는 의사결정 |
| Aggregate | 불변식과 트랜잭션 경계 | Aggregate Root로 접근 |
| Hot Spot | 불확실성·갈등·리스크 표시 | 후속 분석 항목 |
> 요약: 이벤트 스토밍 산출물은 이벤트, 명령, 정책, 핫스팟을 통해 애그리게이트 경계를 찾게 한다.

---

## Ⅲ. 동작원리 및 흐름도

```text
Big Picture Event Storming -> 이벤트 나열
이벤트 나열 -> Command / Actor / Policy 연결
Policy 검토 -> Hot Spot 식별
불변식 분석 -> Aggregate 후보 도출
Aggregate 경계 -> 트랜잭션 / 이벤트 통합 설계
```

| 단계 | 처리 내용 | 검증 기준 |
|:---:|:---|:---|
| 1 | 업무 이벤트를 시간순으로 30~100개 도출 | 과거형 이벤트명 사용 |
| 2 | 이벤트를 발생시킨 Command와 Actor 연결 | Command당 담당자 1개 이상 |
| 3 | 정책, 외부 시스템, 핫스팟 표시 | 미결정 이슈 목록화 |
| 4 | 불변식 기준 Aggregate 후보 지정 | 트랜잭션 내 보호 규칙 명시 |
| 5 | Aggregate 간 통합 방안 결정 | 이벤트 지연 허용 시간 명시 |
> 요약: 이벤트 스토밍은 사건 흐름을 통해 정책과 불변식을 발견하고 애그리게이트 경계로 수렴한다.

## Ⅳ. 특징

| 구분 | 기능 목록 회의 | 이벤트 스토밍·Aggregate | 수치·판단 포인트 |
|:---|:---|:---|:---|
| 탐색 단위 | 화면, 기능 | Domain Event, Command | 이벤트 30개 이상 도출 |
| 참여자 | 개발자 중심 | 업무, 개발, 운영 공동 | 2~3시간 워크숍 |
| 경계 | 테이블·화면 | 불변식·트랜잭션 | Aggregate당 Root 1개 |
| 통합 | 동기 호출 중심 | Domain Event 기반 | 지연 p95 1초 이하 |
| 리스크 | 예외 늦게 발견 | 핫스팟 조기 표시 | 핫스팟별 담당자 지정 |
> 요약: 이벤트 스토밍은 숨은 정책과 예외를 조기에 드러내고 Aggregate는 일관성 보호 범위를 제한한다.

## Ⅴ. 심화 비교 및 적용 판단

| 비교 축 | ERD 중심 분석 | 이벤트 스토밍 기반 DDD | 선택 기준 |
|:---|:---|:---|:---|
| 대상 | 데이터 구조 | 업무 사건과 정책 | 상태 전이 5개 이상 |
| 산출물 | 테이블, 관계 | Event, Command, Aggregate | 도메인 전문가 참여 가능 |
| 일관성 | FK, 트랜잭션 | Aggregate 불변식 | 동시성 충돌 발생 영역 |
| MSA 연계 | 테이블 기준 분리 | 이벤트·컨텍스트 기준 분리 | 서비스 분해 필요 시 |
> 요약: 상태 전이와 정책이 복잡한 업무는 ERD보다 이벤트 흐름이 경계 발견에 적합하다.

| 리스크 | 원인 | 대응 방안 | 확인 지표 |
|:---|:---|:---|:---|
| 이벤트 과다 | 모든 CRUD를 이벤트로 작성 | 업무 의미 있는 상태 변화만 선택 | 이벤트 중복률 |
| Aggregate 비대화 | 여러 불변식을 한 객체에 묶음 | 트랜잭션 경계 재검토 | Aggregate 필드 수 |
| 정합성 누락 | 지연 허용 시간 미정 | Saga, Outbox, 보상 정책 | 미처리 이벤트 건수 |
| 워크숍 공백 | 업무 담당자 불참 | 도메인 전문가 2명 이상 참여 | 미확정 핫스팟 수 |
> 요약: 과도한 이벤트와 비대한 Aggregate는 지연 시간, 필드 수, 핫스팟 수로 통제한다.

| 점검 항목 | 목표 기준 | 측정 방법 |
|:---|:---|:---|
| 이벤트 품질 | 과거형 Domain Event 30개 이상 | 워크숍 보드 리뷰 |
| 경계 품질 | Aggregate당 Root 1개, 트랜잭션 1개 | 모델 리뷰 |
| 정합성 | 이벤트 처리 실패율 0.1% 이하 | 메시지 브로커 로그 |
| 검증성 | 불변식 테스트 80% 이상 | 단위 테스트 |
> 요약: 성공 여부는 이벤트 품질, Aggregate 경계, 이벤트 처리 실패율, 불변식 테스트로 판단한다.

## Ⅵ. 실무 적용 및 결론

**적용 방안 3개:**
1. Big Picture Event Storming으로 주요 Domain Event를 30개 이상 도출하고 Command, Actor, Policy를 같은 보드에 배치한다.
2. 주문, 재고, 결제처럼 동시성 충돌이 있는 영역은 Aggregate Root와 불변식을 정하고 트랜잭션 1개로 보호한다.
3. Aggregate 간 처리는 Domain Event, Outbox, Saga로 분리하고 이벤트 지연 p95 1초 이하와 실패율 0.1% 이하를 운영 지표로 둔다.

**결론 (2줄):**
- 기술사 판단: 단순 CRUD는 ERD 중심 분석, 상태 전이·정책·예외가 많은 도메인은 이벤트 스토밍과 Aggregate 설계가 타당함
- 향후 방향: 이벤트 스토밍 산출물은 Event Sourcing, CQRS, MSA 경계 설계의 초기 입력으로 활용됨
