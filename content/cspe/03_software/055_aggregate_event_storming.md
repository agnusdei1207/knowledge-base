# 📖 【암기용】 개념 완전 이해

> 목적: 이 개념을 처음 보는 사람도 완벽히 이해하게 만든다. 시험 답안 양식이 아니라, 이해를 위한 친절한 설명이다.

## 한눈에
- **개요**: **이벤트 스토밍**은 복잡한 비즈니스(회사 업무)를 컴퓨터 시스템(MSA)으로 만들 때, 기획자·개발자·디자이너가 다 같이 모여 벽에 오렌지색 포스트잇(이벤트)을 미친 듯이 이어 붙이며 회의하는 워크숍이다. 그 회의의 최종 목표는 **애그리게이트(트랜잭션을 묶을 데이터 덩어리)**를 찾아내서 서버를 어떻게 쪼갤지 결정하는 것이다.
- **왜 필요한가**: 개발자 혼자 키보드 잡고 "테이블은 10개로 쪼개야지"라고 설계하면 무조건 망한다. 기획자가 원하는 건 테이블이 아니라 '업무 흐름'이기 때문이다. 그래서 다 같이 모여서 "결제가 완료되면 -> 배송이 시작된다"라는 행동(이벤트)을 벽에 붙여놓고 시각적으로 시스템의 뼈대를 뽑아내는 것이다.
- **핵심 직관**: 
  - **이벤트 (오렌지 포스트잇)**: 이미 벌어진 과거의 일. (예: 결제됨, 배송됨).
  - **커맨드 (파란 포스트잇)**: 이벤트를 일으키는 스위치. (예: 결제 승인 요청 버튼).
  - **애그리게이트 (노란/보라 포스트잇)**: 파란 포스트잇(명령)을 받아서 오렌지 포스트잇(결과)을 뱉어내는 **'핵심 데이터 덩어리(본체)'**. (예: '주문서'라는 덩어리가 결제 명령을 받아서 결제 완료를 뱉어냄).

## 깊이 이해
- **배경·문제의식**: 도메인 주도 설계(DDD)라는 철학은 훌륭했지만, "그래서 구체적으로 어디서부터 어떻게 쪼개라는(설계하라는) 거냐?"라는 비판이 많았다. 2013년 알베르토 브란돌리니가 "어렵게 하지 말고, 다 같이 빈 화이트보드에 색깔 포스트잇을 시간순으로 붙여보자"고 제안한 것이 대박이 나며 전 세계 MSA 설계의 표준 기법이 되었다.
- **작동 원리 (워크숍의 4단계 진화)**:
  1. **혼돈의 도메인 이벤트 (Orange)**: 일단 오렌지색(과거형 행동)을 닥치는 대로 벽에 붙인다. (`주문 접수됨` -> `결제 승인됨` -> `포인트 차감됨`).
  2. **명령과 액터 추가 (Blue, Yellow)**: 누가 이 일을 시켰는지 찾는다. 고객(노란색)이 `결제 버튼(파란색)`을 눌러서 `결제 승인됨(오렌지색)`이 발생했다.
  3. **애그리게이트 발굴 (Purple)**: ⭐️(가장 중요) 파란색(명령)과 오렌지색(결과) 사이에 **'진짜 주어(데이터 군집)'**를 끼워 넣는다. 결제 버튼을 누르면 무엇의 상태가 변하는가? 바로 **`[주문서]`**다. 이 `[주문서]`가 바로 우리가 코딩할 핵심 객체 덩어리(애그리게이트)다.
  4. **바운디드 컨텍스트 묶기**: 포스트잇 덩어리들을 보고 "어? 이쪽은 돈 얘기(정산)고 저쪽은 물건 얘기(배송)네?" 하며 매직펜으로 큰 원(울타리)을 치면, 그게 바로 서버(MSA)를 찢는 기준이 된다.
- **비유**: 
  - 공장 컨베이어 벨트 그리기 대회. 기계 설계도(DB 스키마)부터 그리는 게 아니라, "사과가 들어간다(이벤트) -> 씻는다(커맨드) -> 상자에 담긴다(이벤트)"라는 '동작 과정'을 먼저 스케치북에 그리고, 나중에 그 동작을 수행할 세탁기계, 포장기계(애그리게이트)를 덧그려 넣는 방식.
- **흔한 오해·주의점**: "포스트잇 색깔이 그렇게 중요한가요?" 엄청 중요하다. 색깔은 기획자와 개발자를 연결하는 **'규격(프로토콜)'**이다. 오렌지 포스트잇은 나중에 개발자가 `Kafka Event Message` 코드로 만들고, 파란 포스트잇은 `REST API (Controller)` 엔드포인트 코드가 된다. 포스트잇이 곧 아키텍처 도면이다.

## 연결 개념
- **CQRS (명령/조회 분리)**: 이벤트 스토밍에서는 초록색 포스트잇(Read Model)도 붙인다. 사용자가 화면을 보기(조회) 위해 필요한 데이터 뷰를 정의하는 건데, 이게 CQRS 아키텍처로 직결된다.
- **트랜잭션 바운더리 (ACID)**: 도출해 낸 1개의 애그리게이트는 절대 찢어지지 않는 1개의 DB 트랜잭션 단위(`Commit` 단위)가 된다.

# 📝 【답안용】 시험 답안 템플릿

> 목적: 시험장에서 25분에 그대로 쓰는 답안 양식. 작성방식(추상표현 금지·수치·도식·문제유형 전환)을 엄격히 지킨다.
> 핵심: 이 시험은 정보를 많이 나열하는 시험이 아니라, 문제 신호어에서 출제자 의도를 읽고 핵심 논점을 선별해 쓰는 시험이다.

## 핵심 인사이트 (3줄 요약)

> 1. **본질**: 비즈니스 도메인의 복잡성을 타파하기 위해, 이벤트 스토밍(시각적 워크숍)으로 업무 흐름을 도출하고, 상태 변경의 주체이자 트랜잭션의 절대 단위인 애그리게이트(Aggregate)를 식별하여 MSA의 경계를 획정하는 실천 기법이다.
> 2. **가치**: 기존 데이터베이스(테이블) 중심의 상향식(Bottom-up) 구조 설계를 탈피하여, 비즈니스 이벤트(행위) 중심의 하향식(Top-down) 설계를 강제함으로써 기획과 소스코드 간의 추적성(Traceability) 갭(Gap)을 소거한다.
> 3. **판단 포인트**: 오렌지색(Event)과 파란색(Command) 사이에 보라색(Aggregate)이 도출되는 논리적 매커니즘을 도식화하고, 1개의 애그리게이트가 왜 1개의 ACID 트랜잭션 경계가 되어야 하는지 데이터 무결성 원리를 짚어내야 한다.

## 출제 의도 및 답안 포인트

| 출제 의도 | 반드시 짚을 핵심 | 감점 회피 포인트 |
|:---|:---|:---|
| MSA 분할을 위한 실무적(Tactical) 워크숍 기법 이해 | 이벤트(Event) -> 커맨드(Command) -> 애그리게이트(Aggregate) 도출 흐름 | 포스트잇 붙이는 회의라고만 적고, 각 색상이 어떤 소프트웨어 컴포넌트(API, DB)로 치환되는지 누락 |
| 애그리게이트(Aggregate)의 아키텍처적(엔지니어링) 의미 | **단일 트랜잭션(ACID) 보장 및 동시성 제어 단위** | 단순히 '객체 묶음'이라고 치부하여 트랜잭션/데이터 무결성 방어 관점의 서술 증발 |
| 도메인 주도 설계(DDD)의 전략적/전술적 브릿지(Bridge) | 식별된 군집들을 묶어 바운디드 컨텍스트(Bounded Context)로 확장 | 전략적 설계와 전술적 설계를 완전히 분리된 별개 개념으로 잘못 기술 |

> 요약: 백엔드 개발자에게 애그리게이트는 목숨과 같다. 내가 짠 서버 안에서 이 '군집'이 무너지면, 트랜잭션 락(Lock) 경합으로 DB가 터지거나 데드락이 발생한다. 이벤트 스토밍은 이 폭탄(애그리게이트)들을 안전한 크기로 잘라내는 지뢰 탐지 워크숍이다.

## Ⅰ. 개요 및 필요성

- 정의: **이벤트 스토밍(Event Storming)**은 도메인 전문가와 개발자가 참여해 비즈니스 흐름을 시간순의 이벤트(포스트잇)로 시각화하는 기법이며, 이를 통해 식별된 **애그리게이트(Aggregate)**는 데이터 일관성을 유지하는 트랜잭션 군집 단위
- 배경: 기획 문서만으로는 복잡한 비즈니스 엣지 케이스(Edge Case)를 파악하기 불가능하고, 개발자가 테이블 위주로 섣불리 짠 모델은 트래픽 병목 시 무결성(Integrity) 붕괴를 초래
- 필요성: 비즈니스 관계자 전원이 합의하는 유비쿼터스 언어(Ubiquitous Language)를 시각적으로 확립하고, 분산 환경(MSA)에서 쪼개질 데이터베이스와 트랜잭션 바운더리를 명확히 획정하기 위함

## Ⅱ. 이벤트 스토밍 워크숍: 소프트웨어 아키텍처 추출 도식

단순한 포스트잇 회의가 아니다. 각 포스트잇 색상은 백엔드(Spring) 코드 뼈대와 1:1로 정확히 치환(맵핑)된다.

```text
[ 이벤트 스토밍 포스트잇 부착 흐름 및 백엔드 코드 치환 도식 ]

(사용자) ---> [ 1. Command API (명령: 파란색 🟦) ]
                     |
            (비즈니스 룰 및 상태 변경 위임)
           [ 2. Aggregate (주어/데이터 본체: 보라색 🟪) ]
                     |
            (상태가 변경되면 과거분사형 이벤트 뱉어냄)
          [ 3. Domain Event (결과: 오렌지색 🟧) ] 
                     |
            (4. 비동기 이벤트 발행 - Publish)
            [ Kafka / Event Bus ]  (다른 바운디드 컨텍스트로 전파 🚀) 
```

| 포스트잇 색상 | 비즈니스(도메인) 관점 의미 | 아키텍처(소스코드) 맵핑 (엔지니어링) |
|:---|:---|:---|
| 🟧 **Domain Event** | 시스템에서 발생한 유의미한 상태 변화. 무조건 과거분사형 명명 (`주문 완료됨`) | RabbitMQ / **Kafka (메시지 큐) 토픽**에 쏘아 올릴 JSON 메시지 포맷 명세 |
| 🟦 **Command** | 이벤트를 유발하는 트리거. 사용자 행동이나 외부 시스템 호출 (`결제 승인해라`) | 외부에서 들어오는 **Inbound REST API (Controller의 엔드포인트 URI)** |
| 🟨 **Actor/System** | 커맨드를 누르는 사용자나 외부 API 시스템 (`고객`, `PG 결제사`) | API 호출 주체 인증(Auth) 및 연동 대상 **외부 레거시 시스템(Adapter)** |
| 🟪 **Aggregate** | 커맨드를 받아 검증하고 이벤트를 발생시키는 **진짜 상태(State)를 가진 주체(주어)** | JPA `@Entity` 덩어리이자 비즈니스 로직(Method)을 품은 **핵심 도메인 객체** |

> 요약: 화이트보드에 🟦`결제요청` -> 🟪`주문서` -> 🟧`결제됨` 포스트잇이 붙는 순간, 백엔드 아키텍트는 머릿속에서 `Controller(POST)` -> `Domain Entity(save)` -> `Kafka(Produce)` 코드 뼈대를 0.1초 만에 자동 생성해 낸다.

## Ⅲ. 애그리게이트(Aggregate)의 절대 원칙: 트랜잭션 무결성 방어

애그리게이트는 단순히 객체(클래스)를 묶어놓은 폴더가 아니다. 동시성 제어(Concurrency Control)의 방어선이다.

| 리스크 요인 | 발생 시나리오 및 시스템 붕괴 원인 (안티패턴) | 애그리게이트 설계 대응 원칙 (실무 튜닝) |
|:---|:---|:---|
| **트랜잭션 바운더리 붕괴** <br> (데드락 폭발) | `주문(Aggregate)`의 상태를 바꾸는 김에(하나의 DB 세션 안에서) 연관된 `회원(Aggregate)`의 쿠폰 데이터까지 동시에 `UPDATE`를 때리다, 타 스레드와 DB Lock(잠금) 경합 발생 및 시스템 마비 | **원칙 1: 1 트랜잭션 당 단 1개의 애그리게이트만 수정할 것**. 내 애그리게이트만 수정하고, 남의 애그리게이트(`회원`) 변경은 도메인 이벤트를 발행하여 **최종적 일관성(Eventual Consistency, 비동기)**으로 처리 강제 |
| **은닉성 파괴에 의한 무결성 오염** | 외부 `Service` 클래스에서 `주문(Aggregate)` 덩어리 안에 있는 `배송지(하위 Entity)` 객체를 직접 끄집어내어 주소를 변경해 버려 도메인 검증 룰 완전 패스 | **원칙 2: 오직 루트(Aggregate Root)를 통해서만 접근할 것**. 외부에서는 대장(Root) 객체만 참조 가능하며, 대장이 하위 객체의 변경 룰(예: 배송 출발 전인지)을 검증한 뒤 내부 상태를 변경하는 파사드(Facade) 통제 강제 |

> 요약: 애그리게이트는 "함께 죽고 함께 사는 공동 운명체"다. 하나의 애그리게이트 내부가 부분적으로만 수정(Commit)되는 일은 결코 없어야 한다. 데이터베이스의 ACID 특성을 소프트웨어 객체 레벨로 끌어올린 것이 바로 애그리게이트다.

## Ⅳ. 이벤트 스토밍 확장: CQRS 아키텍처 도출 (녹색 포스트잇)

데이터를 입력(쓰기)하는 것과 화면에 뿌려주는(조회) 것은 완벽히 다르다. 워크숍에서 이를 분리한다.

| 워크숍 확장 컴포넌트 | 아키텍처적 도출 메커니즘 | 해결되는 비즈니스/운영 한계 |
|:---|:---|:---|
| 🟩 **Read Model** <br> (조회/뷰 모델) | 사용자가 `커맨드(결제)`를 누르기 위해(의사결정) **화면에서 확인해야 하는 정보** (예: 내 쿠폰 목록, 장바구니 총액). 녹색 포스트잇으로 도출 | 1개의 트랜잭션 단위로 찢어진(정규화) 애그리게이트들 때문에 화면 렌더링 시 다중 DB 조인(Join) 지연(Latency)이 폭발하는 한계 방어 |
| CQRS 연계 설계 | 위에서 식별된 녹색 뷰(Read Model)를 성능 최적화하기 위해, 오렌지색 이벤트(Event)들을 구독하여 미리 **역정규화(조인)된 조회 전용 DB(Elasticsearch, Redis)를 비동기로 구워내는 아키텍처 확정** | 무거운 쓰기(RDBMS) 모델과 가벼운 읽기(NoSQL) 모델의 **물리적 분할 완벽 매핑** |

> 요약: 화면에 띄워줄 데이터(녹색)를 애그리게이트(보라색)에서 SQL로 미친 듯이 긁어오면(Join) 성능이 박살 난다. 그래서 이벤트 스토밍 단계에서부터 "아, 이 화면용 데이터는 따로 비동기로 구워둬야겠구나(CQRS)"라고 아키텍처 결정을 끝내버린다.

## Ⅴ. 실무 적용 방안 및 결론

**적용 방안 3개:**
1. [Miro / Mural 도구 기반 리모트(Remote) 이벤트 스토밍 수행] 글로벌 분산 팀 환경에서 MSA 신규 구축 시, 물리적 화이트보드 대신 화상 회의 툴과 가상 보드(Miro)를 활용하여 기획-개발 20명이 동시 접속해 4시간 동안 수백 개의 오렌지색(Event) 포스트잇을 쏟아내는 빅뱅 도메인 추출(Discovery) 적용
2. [JPA Aggregate Root 매핑 및 객체 그래프 제한 튜닝] 추출된 애그리게이트를 Spring Data JPA로 코딩할 때, 다른 애그리게이트를 멤버 변수(객체 참조)로 가지는 것을 아키텍처 룰(ArchUnit)로 금지시키고, 오직 식별자(ID, Long 타입) 필드만 참조하게 하여 ORM N+1 문제 원천 차단 및 트랜잭션 바운더리 철통 분리
3. [Outbox(아웃박스) 패턴 결합 이벤트 유실 방어] 애그리게이트가 상태를 변경(DB Commit)함과 동시에 오렌지색 이벤트(Kafka Message)를 100% 안전하게 발행하기 위해, 애그리게이트 Root 엔티티 저장 시 `Outbox` 테이블에도 이벤트를 동일 트랜잭션 락(Lock)으로 함께 묶어 저장(CDC 활용)하는 신뢰성 전파 튜닝

**결론:**
- 기술사 판단: 과거의 폭포수(Waterfall) 모델과 ERD(테이블) 중심 설계는 비즈니스의 역동성(흐름)을 박제된 데이터(상태)로 가둬버렸다. 이벤트 스토밍은 소프트웨어 설계의 패러다임을 '명사(Table)'에서 '동사(Event)'로 바꾸었으며, 이 과정에서 벼려진 애그리게이트(Aggregate)는 분산 환경에서 데이터 붕괴를 막아내는 가장 강력한 트랜잭션 방파제다.
- 향후 방향: 최근 클라우드 네이티브 설계에서는 이벤트 스토밍 산출물을 그대로 Serverless(서버리스) 아키텍처나 상태 머신(AWS Step Functions) 코드로 1:1 자동 변환(Code Generation) 하려는 시도(Event Modeling)가 활발해지며, 기획과 아키텍처 구현 간의 간극이 제로(Zero)에 수렴하는 시대로 진화하고 있다.
