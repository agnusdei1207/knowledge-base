## Ⅰ. 개요
- **정의**: 애그리게이트는 일관성 경계를 형성하는 도메인 객체 클러스터이고, 이벤트 스토밍은 도메인 이벤트 중심으로 이를 도출하는 워크숍 기법
- **배경/필요성**: 복잡한 도메인에서 트랜잭션 경계와 모델 구조를 감각적으로 파악하기 어려우므로, 시각적 협업 기법으로 빠르게 도출할 필요
- **비유**: 포스트잇으로 업무 흐름을 벽에 붙여가며 팀이 함께 퍼즐을 맞추는 과정과 유사함

| 출제 의도 | 반드시 짚을 핵심 | 감점 회피 포인트 |
|:---|:---|:---|
| Aggregate 설계 원칙과 이벤트 스토밍 절차 | Aggregate Root, 일관성 경계 | 이벤트 스토밍을 단순 브레인스토밍과 혼동하지 말 것 |

> 요약: 이벤트 스토밍으로 도메인 이벤트를 도출하고, 애그리게이트로 일관성 경계를 확정하는 기법임

## Ⅱ. 구성요소
```text
Domain Event --> Command --> Aggregate --> Policy --> Read Model
 (주황)        (파랑)      (노랑)       (보라)     (초록)
```

| 구성요소 | 설명 | 비유 |
|:---|:---|:---|
| Domain Event | 비즈니스에서 발생한 사실을 과거형으로 표현한 기록 | 일지에 기록된 사건 |
| Command | 이벤트를 유발하는 사용자·시스템의 의도적 행위 | 버튼 클릭(주문하기) |
| Aggregate | 단일 트랜잭션으로 일관성을 보장하는 객체 묶음, Root를 통해서만 접근 | 가족 단위(가장을 통해 대외 소통) |
| Policy | 이벤트 발생 시 자동 실행되는 후속 규칙 | 화재 감지 시 스프링클러 자동 작동 |

> 요약: 이벤트·커맨드·애그리게이트·폴리시가 이벤트 스토밍의 핵심 구성요소임

## Ⅲ. 절차
```text
이벤트나열 --> 커맨드/액터매핑 --> 애그리게이트군집화 --> BC경계확정
```
- 1단계: 도메인 이벤트를 시간순으로 포스트잇에 나열함
- 2단계: 각 이벤트를 유발하는 커맨드와 액터를 매핑함
- 3단계: 관련 이벤트·커맨드를 묶어 애그리게이트를 군집화함
- 4단계: 애그리게이트 군집을 기준으로 바운디드 컨텍스트(054 참조) 경계를 확정함

> 요약: 이벤트 나열부터 BC 경계 확정까지 4단계로 진행함

## Ⅳ. 문제점
- 과대 애그리게이트: 너무 많은 엔티티를 하나로 묶음 — 트랜잭션 경합과 성능 저하 발생
- 워크숍 편향: 참여자 구성에 따라 결과 편향 — 특정 도메인 영역 누락 위험
- 이벤트 폭증: 세밀한 이벤트 도출 시 관리 대상 급증 — 모델 복잡도 상승

> 요약: 과대 애그리게이트, 워크숍 편향, 이벤트 폭증이 주요 문제임

## Ⅴ. 개선방안
1. 단기: 애그리게이트 크기를 4~5 엔티티 이내로 제한하는 가이드라인 적용
2. 중기: 도메인 전문가·개발자·QA 등 다양한 역할의 참여를 의무화하여 편향 방지
3. 장기: 이벤트 카탈로그 관리 도구를 도입해 이벤트 분류·버전 관리 체계 구축

> 요약: 크기 제한, 다직군 참여, 이벤트 카탈로그로 개선함

## Ⅵ. 전망
- 발전 방향: CQRS·Event Sourcing과 결합하여 이벤트 기반 아키텍처의 설계 도구로 확산 중임
- 기술사적 판단: MSA 전환 프로젝트에서 서비스 경계 도출의 사실상 표준 워크숍 기법임
- 기술사 제언: DDD(053 참조) 전술 설계와 병행하여 모델-코드 일치도를 지속 검증 필요
