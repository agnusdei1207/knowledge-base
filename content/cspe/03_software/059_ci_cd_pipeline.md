## 핵심 인사이트 (3줄 요약)
- **CI(Continuous Integration)**: 여러 개발자가 작성한 코드를 중앙 저장소에 수시로 병합(Merge)하고, 자동화된 빌드와 단위 테스트를 통해 코드 충돌을 즉각적으로 발견하는 실천법.
- **CD(Continuous Deployment/Delivery)**: CI를 통과한 검증된 코드를 스테이징 또는 프로덕션 환경까지 사람의 수동 개입 없이(혹은 최소한의 승인으로) 안전하게 릴리즈하는 자동화 파이프라인.
- "배포가 두려운 일 행사"에서 "하루에 수십 번 일어나는 숨쉬기 같은 일상"으로 바꾸어, 소프트웨어 개발의 리드 타임을 극단적으로 단축하는 데브옵스(DevOps)의 심장임.

## Ⅰ. 개요 및 필요성
- **개요**: 코드의 커밋(Commit)부터 사용자에게 릴리즈(Release)되기까지의 전 과정을 자동화하는 소프트웨어 공학의 파이프라인 프로세스.
- **필요성**: 과거에는 한 달 동안 각자 개발한 코드를 배포 전날 합치려다(Merge Hell) 수많은 충돌과 버그가 터졌고, 수동 배포 중 휴먼 에러로 서버가 다운되는 일이 잦았음. 기계가 이 반복 작업을 대신하여 빠르고 예측 가능하게 배포할 체계가 필요했음.
---
## Ⅱ. 아키텍처 및 핵심 원리
- **CI/CD 파이프라인 흐름도**:
  1. **Commit / PR**: 개발자가 Git에 코드를 올림.
  2. **CI (Build & Test)**: Jenkins나 GitHub Actions가 소스를 컴파일하고, 단위 테스트(Unit Test)와 정적 코드 분석(SonarQube)을 수행함. (실패 시 즉각 Slack 알림).
  3. **Package & Store**: 빌드된 산출물(Docker Image 등)을 레지스트리에 저장.
  4. **CD (Delivery / Deployment)**: ArgoCD 등을 통해 K8s 클러스터 등 실제 인프라에 배포.

```text
[ 전형적인 CI/CD 파이프라인 아키텍처 ]

 [ Developer ]
      ⬇️ (1. Code Push)
 [ Git Repository (GitHub) ] 
      ⬇️ (2. Webhook Trigger)
 [ CI Server (Jenkins) ]  ➡️ 🔴 [ 컴파일/테스트 실패 ] ➡️ (개발자 피드백)
      ⬇️ 🟢 [ 테스트 성공 ]
 [ Build Docker Image ] ➡️ [ Image Registry ]
      ⬇️ 
 [ CD Server (ArgoCD) ] ➡️ [ Production K8s Cluster ] (3. 무중단 자동 배포)
```

## Ⅲ. 비교 및 연결
| 구분 | Continuous Integration (CI) | Continuous Delivery (CD) | Continuous Deployment (CD) |
|---|---|---|---|
| **우리말 번역** | 지속적 통합 | 지속적 제공 | 지속적 배포 |
| **주요 목적** | 빌드와 테스트 자동화 (버그 방지) | 언제든 배포 가능한 상태(Artifact) 유지 | 프로덕션까지 100% 자동 릴리즈 |
| **프로덕션 릴리즈** | 해당 안 됨 (테스트 환경까지만) | 배포 시 **사람의 승인(버튼 클릭)** 필요 | 사람의 개입 없이 **완전 자동 배포** |
| **요구되는 성숙도**| 필수적 (기본) | 높음 (자동화된 E2E 테스트 필요) | 매우 높음 (완벽한 테스트 커버리지) |
---
## Ⅳ. 실무 적용 및 기술사 판단
- **CI 극장 (CI Theater) 경계**: 젠킨스(Jenkins) 파이프라인만 구축해 두고, 정작 개발자들은 브랜치를 한 달씩 쥐고 있다가 병합한다면 이는 무늬만 CI인 'CI 극장'임. 진정한 CI는 도구가 아니라 "하루에 최소 1회 이상 메인라인에 코드를 병합"하는 개발 조직의 **행위 문화**를 의미함.
- **테스트 없는 CD의 위험성**: 탄탄한 TDD(테스트 주도 개발)나 자동화된 인수 테스트(Test Suite) 없이 껍데기만 CD 파이프라인을 구축하면, "버그를 빛의 속도로 고객에게 배달하는 자동화 시스템"으로 전락함. 파이프라인의 핵심은 '배포 속도'가 아니라 '안전망'임.
---
## Ⅴ. 기대효과 및 결론
- CI/CD는 아이디어가 사용자에게 전달되는 리드 타임(Lead Time)을 수개월에서 수십 분으로 단축하여, 시장의 변화에 애자일(Agile)하게 대응할 수 있는 무기가 됨.
- 개발자를 인프라 세팅과 배포 스트레스로부터 해방시켜 '코딩'이라는 본연의 가치 창출에만 몰입하게 만드는 클라우드 네이티브 생태계의 척추(Backbone)임.

### 👶 어린이를 위한 3줄 비유 설명
1. 학교 숙제를 낼 때, 한 달 치를 모아서 한 번에 내면 선생님한테 혼나고 틀린 것도 많아서 엉망이 되죠?
2. CI/CD는 매일매일 한 장씩 숙제를 내고, 로봇 선생님(Jenkins)이 1초 만에 채점해서 틀린 걸 바로 알려주는 거예요 (CI).
3. 숙제가 100점을 맞으면 로봇이 알아서 교장 선생님(프로덕션) 책상 위에 예쁘게 올려놔 주기까지 하니까(CD), 우리는 맘 편하게 숙제만 하면 된답니다!
