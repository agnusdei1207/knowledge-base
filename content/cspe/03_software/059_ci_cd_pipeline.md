# 📖 【암기용】 개념 완전 이해

## 한눈에
- **개요**: CI/CD 파이프라인은 개발자의 소스 코드 병합(CI)부터 빌드, 자동화 테스트, 운영 환경 배포(CD)까지의 전 과정을 자동화하여 소프트웨어를 신속하게 제공하는 파이프라인이다.
- **왜 필요한가**: 과거에는 금요일 밤에 개발자, 서버 관리자, QA가 모여 수동으로 코드를 복사하고 서버를 껐다 켜며 배포했다. 이 수작업 과정은 실수(Human Error)가 잦고 시간이 오래 걸려 비즈니스 속도를 갉아먹는다.
- **핵심 직관**: 자동차 공장의 조립 컨베이어 벨트. 개발자가 나사(코드)를 레일 위에 올리기만 하면, 컨베이어 벨트(파이프라인)가 굴러가며 자동으로 로봇이 조립(빌드)하고 검사(테스트)해서 매장에 전시(배포)까지 끝낸다.

## 핵심 용어 정리

| 용어/표기 | 의미 | 비유·예 |
|:---|:---|:---|
| CI (Continuous Integration, 지속적 통합) | 다수 개발자의 코드를 하루에 여러 번 공유 저장소에 병합하고 자동 빌드/테스트 | 퇴근 전 무조건 내 코드를 메인 폴더에 섞어보고 에러 확인하기 |
| CD (Continuous Delivery/Deployment) | 테스트 통과 코드를 스테이징/운영 환경까지 자동 릴리스(제공/배포) | 완성된 제품을 트럭에 실어 고객에게 전달 |
| 빌드 아티팩트 (Artifact) | 소스 코드를 컴파일하여 만들어진 실행 가능한 결과물 바이너리 | .jar, .war 파일 또는 Docker 이미지 |
| 파이프라인 오케스트레이션 도구 | 이 자동화 과정의 단계와 순서를 지휘하는 소프트웨어 | Jenkins, GitHub Actions, GitLab CI |

## 깊이 이해
- **배경·문제의식**: 애자일(Agile)이 유행하며 개발 속도는 빨라졌지만, 배포를 인프라 운영팀이 수동으로 하다 보니 결국 배포 병목(Bottleneck)이 발생했다. 개발(Dev)과 운영(Ops)의 벽을 허무는 DevOps 철학을 기술적으로 구현한 것이 CI/CD다.
- **작동 원리 (흐름)**: 개발자가 Git에 코드를 Push한다 -> Webhook이 Jenkins를 깨운다 -> 소스를 가져와 컴파일(Build)한다 -> 단위/통합 테스트를 자동 실행한다 -> 성공하면 Docker 이미지(Artifact)로 굽는다 -> 쿠버네티스(또는 서버)에 이미지를 배포(Deploy)한다.
- **구체 예시**: 개발자가 로그인 버그를 고치고 `git push`를 하면, 화장실에 다녀오는 5분 사이에 이미 테스트 서버에 배포가 완료되어 테스터가 확인 가능한 상태가 된다.
- **흔한 오해·주의점**: "Jenkins만 깔면 CI/CD가 완성된다"는 엄청난 착각이다. 가장 중요한 뼈대는 '자동화 테스트 코드'다. 테스트 코드가 없으면 버그가 있는 코드가 초고속으로 운영 서버에 배포되는 '자동화된 재앙 파이프라인'이 될 뿐이다.

## 연결 개념
- 테스트 주도 개발 (TDD) / 커버리지 — 파이프라인의 신뢰성을 담보하는 안전망
- 무중단 배포 (Blue-Green, Canary) — 사용자 접속이 끊기지 않게 배포하는 CD 단계의 필수 전략
- GitOps — CI/CD의 배포(CD) 단계를 Git 저장소의 상태 동기화 메커니즘으로 대체하는 진화된 형태

# 📝 【답안용】 시험 답안 템플릿

## 핵심 인사이트 (3줄 요약)

> 1. **본질**: 소스 코드 통합(CI)부터 빌드, 테스트, 운영 서버 릴리스(CD)까지의 소프트웨어 딜리버리 생명주기 전체를 자동화한 DevOps의 핵심 기술 프랙티스이다.
> 2. **가치**: 수동 배포로 인한 인적 오류(Human Error)를 제거하고 빠른 피드백 루프를 구축하여 비즈니스 타임투마켓(TTM)을 획기적으로 단축한다.
> 3. **판단 포인트**: 파이프라인의 성패는 자동화 도구 자체가 아니라, 병목이 없는 빠른 빌드 최적화와 견고한 테스트 커버리지 확보 여부에 달려있다.

## 출제 의도 및 답안 포인트

| 출제 의도 | 반드시 짚을 핵심 | 감점 회피 포인트 |
|:---|:---|:---|
| DevOps 자동화 파이프라인 흐름 파악 역량 | CI(통합/빌드/테스트)와 CD(배포)의 명확한 단계 구분 | 단순 툴(Jenkins) 설명으로 축소 기재 |
| 배포 안전성과 품질 통제 수단 이해 | 테스트 자동화 커버리지 통과, 아티팩트 불변성(Immutable) | 테스트 없는 무조건적인 자동 배포 위험성 간과 |
| 병목 해소 및 최적화 판단 확인 | 파이프라인 소요 시간 10분 내 통제, 캐싱, 병렬 테스트 | 파이프라인 구동 속도 지연(병목) 리스크 누락 |

> 요약: 코드가 커밋되어 사용자에게 도달하기까지의 전 과정을 시각화하고, 각 구간별 품질 게이트(Quality Gate)를 어떻게 통제할 것인가가 핵심이다.

---

## Ⅰ. 개요 및 필요성

- 개요: 소스 코드 병합 시 자동 빌드와 테스트를 수행하는 CI(지속적 통합)와, 이를 운영 환경까지 자동 릴리스하는 CD(지속적 배포/제공)가 결합된 자동화 파이프라인임
- 배경: 전통적 수동 배포 방식은 스크립트 실행 오류 등 휴먼 에러를 유발하고 개발-운영 간의 단절된 사일로(Silo) 현상을 악화시킴
- 필요성: 마이크로서비스(MSA) 확산으로 배포해야 할 서비스 개수가 폭증함에 따라, 수작업을 완전히 배제한 기계적이고 반복 가능한 자동화 릴리스 체계 필수

---

## Ⅱ. 구조 및 구성요소

```text
[ Git 저장소 ] -> (Webhook) -> [ CI 서버 ] -> [ 아티팩트 저장소 ] -> [ CD 배포 서버 ] -> [ 스테이징 / 운영 환경 ]
(코드 커밋)                 (빌드 및 테스트)   (도커 이미지 보관)     (무중단 배포)        (사용자 트래픽 수신)
```

| 구성요소 | 역할 | 특이사항 |
|:---|:---|:---|
| CI (Continuous Integration) | 소스 병합 후 컴파일, 단위/통합 테스트, 정적 분석 실행 | 조기 버그 발견(Fail Fast) 및 품질 게이트 통과 |
| 아티팩트 레지스트리 | 빌드된 바이너리 또는 컨테이너(Docker) 이미지 불변 저장 | 스테이징과 운영 환경에 동일 이미지 배포 보장 |
| CD (Continuous Delivery/Deployment) | 테스트 통과 산출물을 각 배포 환경에 자동 또는 수동 승인 릴리스 | 블루-그린, 카나리 등 무중단 배포 전략 수행 |

> 요약: 소스 코드가 주입되면 테스트라는 필터를 거쳐 불변 아티팩트로 구워지고 최종 타깃 환경으로 자동 운반된다.

---

## Ⅲ. 동작원리 및 흐름도

```text
Code Commit -> Build -> Unit/Integration Test -> Artifact Registry -> Staging Deploy -> Production Deploy
```

- 1단계 [통합 및 빌드]: 개발자가 기능 브랜치를 병합하면, Webhook을 통해 파이프라인이 트리거되어 의존성 패키지를 다운로드하고 소스 컴파일
- 2단계 [자동화 테스트 및 분석]: 단위 테스트, 정적 코드 분석(SonarQube), 보안 스캔(SAST)을 자동 수행하고 실패 시 즉시 파이프라인 중단(Fail Fast)
- 3단계 [아티팩트 생성]: 테스트를 통과한 결과물을 Docker 이미지로 패키징하여 Registry(Docker Hub, Harbor 등)에 태그와 함께 저장
- 4단계 [CD 릴리스]: 생성된 이미지를 Staging 환경에 배포하여 인수 테스트를 거친 후, 로드밸런서를 교체(블루-그린)하여 운영(Production) 무중단 배포

> 요약: 모든 단계는 이전 단계의 성공을 전제로만 다음 단계로 넘어가며, 에러 발생 시 개발자에게 즉각 알림을 보낸다.

---

## Ⅳ. 특징

- 신속한 피드백 루프: 코드 결함이 통합 단계(CI)에서 수 분 내에 발견되므로, 배포 당일 발생할 심각한 장애를 예방하고 수정 비용 최소화
- 아티팩트 불변성(Immutable): 스테이징에서 검증된 도커 이미지를 환경 설정값(Config)만 교체하여 운영에 그대로 띄우므로 "내 PC에선 되는데 서버에선 안 됨" 문제 원천 차단
- 자동화 함정 (Garbage in, Garbage out): 자동화된 테스트 코드가 빈약하면, 런타임 버그가 포함된 코드가 초고속으로 운영 서버로 직행하는 위험 도래

> 요약: 자동화의 속도를 누리기 위해서는 높은 수준의 테스트 커버리지라는 무거운 전제 조건이 필수적으로 요구된다.

## Ⅴ. 심화 비교 및 적용 판단

| 비교 축 | 수동/스크립트 배포 | CI/CD 파이프라인 배포 | 선택 기준 |
|:---|:---|:---|:---|
| 배포 주체 | 인프라/운영 엔지니어의 수작업 | 트리거에 의한 서버 데몬 자동 수행 | 휴먼 에러 통제 및 배포 빈도 |
| 검증 방식 | QA 인력의 수동 화면 테스트 | xUnit 기반 단위/통합 테스트 자동화 | 비즈니스 변경 속도 (TTM) 요구 수준 |
| 롤백(Rollback) | 재빌드 또는 백업본 수동 복구 복잡 | 이전 버전 아티팩트 지정 즉시 롤백 | 장애 복구 시간 (MTTR) |

> 요약: 현대 애자일 및 MSA 환경에서 잦은 배포를 감당하려면 수동 배포는 유지 불가능하며 CI/CD 파이프라인은 선택이 아닌 필수다.

**리스크·대응:**
- 파이프라인 병목 (지연): 테스트와 빌드 시간이 30분을 초과하여 개발자의 대기 시간(Context Switching) 폭증 → 의존성 모듈 로컬 캐싱(Cache) 적용 및 테스트 병렬 분산 실행으로 파이프라인 10분 내 단축 (지표: 파이프라인 리드 타임)
- 배포 스파이크 장애: 신규 배포 직후 캐시 워밍업(Warming-up) 부재로 인한 트래픽 지연 및 장애 → 운영 트래픽의 5%만 먼저 흘려보내는 카나리(Canary) 배포로 초기 지표 모니터링 후 점진적 확대 (지표: 배포 직후 에러율 및 응답 속도)

## Ⅵ. 실무 적용 및 결론

**적용 방안 3개:**
1. 선언적 파이프라인(Pipeline as Code) 도입: 파이프라인 구축 스크립트(Jenkinsfile, .github/workflows) 자체를 Git 형상 관리에 올려 이력 추적과 복원 자동화
2. 파이프라인 내 보안 통합 (DevSecOps): CI 단계에 정적 분석(SAST) 및 컨테이너 이미지 취약점 스캔(Trivy)을 강제 편입하여 보안 취약점 사전 차단 (Shift-Left)
3. GitOps 기반 CD 분리 적용: ArgoCD를 도입하여, CI는 이미지만 생성하고 배포(CD)는 쿠버네티스 클러스터가 Git의 상태를 스스로 당겨가는(Pull 방식) 선언적 동기화 구축

**결론 (2줄):**
- 기술사 판단: CI/CD의 도입 성과는 파이프라인 도구의 화려함이 아니라, 10분 내에 끝나는 병목 없는 실행 속도와 80% 이상의 신뢰성 높은 테스트 커버리지에 달려있음
- 향후 방향: 최근에는 배포 파이프라인에 AI를 결합하여 과거 배포 실패 패턴을 학습해 위험한 커밋을 사전 경고하는 지능형 파이프라인으로 고도화되는 추세임
