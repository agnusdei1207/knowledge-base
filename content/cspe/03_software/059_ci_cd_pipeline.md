## 미리 알고가기

- CI는 작은 변경을 자주 통합해 변경 후 결함을 검증하는 개발 방식임
- CD는 검증된 변경을 배포 가능한 상태나 실제 운영 배포까지 자동화하는 흐름임
- 불변 아티팩트는 한 번 만든 산출물을 환경마다 다시 빌드하지 않고 그대로 승격하는 방식임

## 작성 근거(검토용)

- CI/CD는 검증 방식, 전달 흐름, 자동화 부담, 적용 환경을 핵심 비교축으로 선정함
- 구성과 절차는 변경 감지부터 빌드·테스트·품질 게이트·배포까지의 흐름을 중심으로 제시함
- 실무 판단은 파이프라인 소요시간, 불안정 테스트 비율, 환경 불일치 건수, 롤백률로 구체화함

## Ⅰ. 개요

- **정의/개념**: CI/CD 파이프라인은 코드 변경을 빌드·테스트·품질 검증·배포 단계로 자동 전달하는 소프트웨어 전달 체계임
- **배경/필요성**: 배포 빈도가 높아질수록 수동 검증과 배포의 오류·지연이 커지므로 반복 가능한 자동 전달 경로가 필요함

## Ⅱ. 특징

- 작은 변경을 자주 검증해 통합 리스크를 줄임
- 배포 절차의 재현성과 추적성을 높임
- 테스트 결과가 반복 실행마다 달라지면 수동 재실행과 파이프라인 우회가 늘어남
- 품질과 보안 기준을 파이프라인 안에서 강제할 수 있음

## Ⅲ. 종류 및 비교

| 판단 기준 | 수동 배포 흐름 | CI/CD 파이프라인 |
|:---|:---|:---|
| 실행 주체 | 담당자가 빌드·테스트·배포 명령을 수행함 | 저장소 변경이 자동 단계를 실행함 |
| 검증·배포 흐름 | 담당자가 단계별 명령과 확인 수행 | commit부터 빌드·테스트·품질 게이트·배포를 동일 절차로 실행 |
| 구조상 한계 | 수동 단계 누락과 승인 대기시간이 발생함 | 자동화 구성과 유지 비용이 듦 |
| 대표 환경 | 변경·배포 빈도가 낮은 내부 시스템 | 동일 검증 절차로 반복 배포하는 제품·플랫폼 조직 |

> 요약: 변경·배포 빈도가 낮으면 수동 흐름, 같은 검증 절차로 반복 배포하면 CI/CD 파이프라인이 적합함.

## Ⅳ. 구성요소 및 구조

| 구성요소 | 설명 |
|:---|:---|
| 변경 감지 | 커밋과 병합을 감지해 파이프라인 실행을 시작함 |
| 빌드와 테스트 단계 | 컴파일·단위 테스트·정적 검사를 수행해 코드 결함을 걸러냄 |
| 품질 게이트 | 품질과 보안과 정책 기준을 통과한 변경만 다음 단계로 넘김 |
| 배포 단계 | 동일한 산출물을 환경별로 승격 배포해 재현성을 유지함 |

> 요약: 변경을 감지해 빌드·테스트하고 품질 게이트를 통과한 같은 산출물을 환경별로 승격함.

## Ⅴ. 원리 및 절차 흐름도

```text
+-------------+     +-------------+     +-------------+     +-------------+
| 코드 변경      | --> | 빌드/테스트    | --> | 품질 게이트    | --> | 배포/승격      |
+-------------+     +-------------+     +-------------+     +-------------+
```

1. **코드 변경**: 커밋이나 병합이 자동 흐름을 시작함
2. **빌드 및 테스트**: 산출물을 만들고 핵심 검증을 수행함
3. **품질 게이트**: 실패 조건과 승인 기준을 확인함
4. **배포 및 승격**: 같은 산출물을 환경별로 배포함

> 요약: 저장소 변경이 빌드·테스트·품질 검증을 통과하면 같은 산출물을 다음 환경으로 배포함.

## Ⅵ. 실무 사례

1. 웹서비스 개발팀은 테스트 단계를 병렬화하고 파이프라인 소요시간·불안정 테스트 비율을 확인함
2. 다중 환경 배포는 같은 산출물을 승격하고 환경 불일치 건수·배포 롤백률을 확인함

## Ⅶ. 결론

CI/CD 파이프라인은 코드 변경을 반복 가능한 검증 절차로 운영 환경까지 전달하는 자동화 체계임
