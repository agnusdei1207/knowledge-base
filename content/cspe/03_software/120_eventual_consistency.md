# 📖 【암기용】 개념 완전 이해

## 한눈에
- **개요**: 분산 시스템에서 데이터가 업데이트되었을 때 모든 노드에 즉각 반영되지는 않지만, 시간이 지나면(결국에는) 모든 노드가 동일한 최신 데이터를 갖게 됨을 보장하는 속성
- **왜 필요한가**: 수십 대의 서버에 동시에 데이터를 완벽히 맞추려다가는(강한 일관성) 락(Lock) 대기 때문에 시스템 속도가 1/100로 느려지거나 다운되기 때문이다.
- **핵심 직관**: 인터넷 뉴스 기사에 달린 '좋아요' 숫자. 내가 누른 직후에는 내 폰에서 100개로 보이지만, 친구 폰에서는 99개로 보일 수 있다. 하지만 5초 뒤 새로고침하면 모두가 100개를 보게 된다.

## 핵심 용어 정리

| 용어/표기 | 의미 | 비유·예 |
|:---|:---|:---|
| 강한 일관성 (Strong) | 업데이트 직후 어느 노드에서 읽든 항상 최신값을 반환함 | "은행 계좌 송금액 확인" (절대 안 틀림, 느림) |
| Stale Read | 동기화가 끝나기 전에 읽기 요청을 해서 옛날(Stale) 데이터를 읽는 현상 | "친구 폰에서 아까 99개인 좋아요를 보는 것" |
| 쿼럼 (Quorum) | 동기화나 읽기 시 '이 정도 개수의 노드가 동의하면 인정'하는 정족수 | "5명 중 3명(과반수)이 확인했으면 OK" |
| Anti-Entropy (가십 프로토콜) | 노드들끼리 주기적으로 수다를 떨며 서로 누락된 최신 데이터를 맞춰보는 백그라운드 동기화 과정 | "야 너 아까 100번 데이터 못 받았지? 이거야" |

## 깊이 이해
- **배경·문제의식**: 클라우드 시대에 아마존(Amazon)이 글로벌 쇼핑몰을 운영할 때, 미국 서버와 한국 서버의 장바구니 데이터를 100% 실시간 일치시키려면 태평양 해저케이블의 물리적 빛의 속도 한계 때문에 결제 버튼을 누르고 수 초간 멈춰 있어야 했다(PA/EC). 아마존은 "가끔 장바구니에 옛날 물건이 보여도 상관없으니, 절대 멈추지 말고 0.1초 만에 응답하자"는 Dynamo 아키텍처를 발표하며 최종 일관성을 업계 표준으로 만들었다.
- **작동 원리**:
  1. 클라이언트가 A 노드에 쓰기(Write) 요청을 한다. A 노드는 일단 자신의 디스크에 쓰고 클라이언트에게 즉시 "성공!"이라고 응답한다. (매우 빠름)
  2. B 노드, C 노드에는 비동기 백그라운드 메시지 큐나 복제 스트림을 통해 데이터가 천천히 전달된다.
  3. 전파되기 전 찰나의 순간에 누군가 B 노드를 읽으면 옛날 데이터가 나간다 (Inconsistency 윈도우).
  4. 수 밀리초~수 초 뒤, B와 C 노드에도 적용이 끝나 결국(Eventual) 모든 상태가 같아진다.
- **비유**: DNS(도메인 네임 서버) 전파. 내가 새 도메인(www.abc.com)을 사서 IP를 연결해도 전 세계 컴퓨터에 즉각 반영되지 않는다. 하루 이틀 지나면 '결국' 전 세계가 다 접속 가능해지는 것이 완벽한 최종 일관성의 예다.
- **흔한 오해·주의점**: 최종 일관성이 데이터 결함이나 유실을 의미하는 것이 아니다. 시스템은 데이터 유실을 막기 위한 재시도 로직(Retry)과 메시지 큐를 완벽히 갖추고 있으며, 단지 "사용자에게 응답을 지연시키면서까지 동기화를 기다리지 않겠다"는 설계적 결단일 뿐이다.

## 연결 개념
- BASE 철학: Eventual Consistency는 BASE 철학의 'E'에 해당하는 핵심 행동 원리다.
- 낙관적 병행 제어(Optimistic Concurrency Control): 동기화를 기다리지 않기 때문에 충돌(Conflict)이 날 확률이 존재한다. 이를 LWW(마지막 쓰기 승리)나 버전 관리를 통해 사후에 병합하는 기술이 동반된다.

# 📝 【답안용】 시험 답안 템플릿

## 핵심 인사이트 (3줄 요약)

> 1. **본질**: 최종 일관성(Eventual Consistency)은 분산 시스템에서 쓰기 직후의 일시적 불일치(Stale Read)를 허용하되, 비동기 복제를 통해 최종적인 데이터 정합성을 보장하는 아키텍처 모델이다.
> 2. **가치**: 글로벌 분산 환경에서 글로벌 락(Global Lock)과 동기화 대기를 제거하여, 시스템의 가용성(Availability)과 초고속 응답 성능(Low Latency)을 극대화한다.
> 3. **판단 포인트**: 이커머스의 '장바구니'나 소셜 미디어 '피드'처럼 수 초 내외의 불일치를 비즈니스적으로 수용 가능한 도메인에 적용해야 하며, 버전 충돌 해소 로직(Conflict Resolution) 설계가 병행되어야 한다.

## 출제 의도 및 답안 포인트

| 출제 의도 | 반드시 짚을 핵심 | 감점 회피 포인트 |
|:---|:---|:---|
| 분산 DB 동기화 패러다임 이해 | 강한 일관성(Strong)과의 차이, Stale Read 윈도우 | 단순 "늦게 반영된다"는 피상적 서술 |
| BASE 및 CAP/PACELC 이론 연계 | AP(가용성) 확보를 위한 필연적 선택이자 BASE의 핵심 구현체 | 최종 일관성 환경에서 2PC(완벽 동기화)를 적용한다는 모순 |
| 정합성 보완을 위한 아키텍처 대응 방안 | Quorum(W+R>N) 튜닝을 통한 세션 일관성 확보, Anti-Entropy | 충돌 발생 시 데이터가 유실된다고 단정 |

> 요약: 최종 일관성은 결함이 아니라 성능(가용성)을 위한 의도적 설계이며, 이로 인해 발생하는 찰나의 '불일치 구간(Inconsistency Window)'을 시스템이 어떻게 통제하고 병합하는지 설명해야 한다.

## Ⅰ. 개요 및 필요성

- 개요: 다중 노드 분산 시스템에서 데이터 갱신 시 즉각적인 완벽 동기화를 포기하고, 비동기 전파를 통해 일정 시간 후 모든 노드의 값이 수렴됨을 보장하는 특성
- 배경: 분산 환경에서 강한 일관성(Strong Consistency)을 위해 2-Phase Commit 연산을 수행하면 네트워크 지연 및 락(Lock) 대기로 대규모 트래픽 처리가 불가능
- 필요성: 시스템 가용성(Availability)과 응답 속도(Low Latency)를 극대화하기 위해, 일시적 정합성 불일치를 비즈니스 레벨에서 수용하는 타협적 아키텍처 필요

## Ⅱ. 구조 및 구성요소

```text
[ Client Write ] --> [ Node A (Master/Leader) ] ----(응답)----> Client (10ms 내외 초고속 응답)
                           |
                     (비동기 Replication) --> Inconsistency Window (불일치 발생 구간)
                           |
                     +-- [ Node B (Replica) ] --> (지연 반영 후 최종 일치)
                     +-- [ Node C (Replica) ] --> (지연 반영 후 최종 일치)
```

| 구성요소 | 역할 | 특이사항 |
|:---|:---|:---|
| Inconsistency Window | 업데이트 후 모든 복제본에 전파되기까지의 시차(Time Window) | 통상 수백 ms 이내, 이 구간 내 읽기 시 구형 데이터 노출 |
| 가십 프로토콜(Anti-Entropy) | 노드 간 백그라운드 P2P 통신으로 누락된 최신 데이터 동기화 | 메시지 유실 시에도 최종 수렴을 강제하는 복구 매커니즘 |
| 쿼럼 (Quorum) / N-W-R | 복제본 수(N), 쓰기 인정 수(W), 읽기 요구 수(R) 설정 메트릭 | R+W 설정에 따라 최종 일관성 강도를 동적으로 조절 |

> 요약: 쓰기 트랜잭션의 클라이언트 응답 경로에서 타 노드로의 복제(동기화) 단계를 분리하여 백그라운드 비동기로 위임하는 구조다.

---

## Ⅲ. 동작원리 및 흐름도

```text
쓰기 발생 -> 리더 노드 로컬 기록 후 선응답 -> 백그라운드 이벤트 발행 
-> 워커 스레드 비동기 복제 -> 타 노드 반영 (충돌 발생 시 해소 병합) -> 최종 수렴 상태
```

- 1단계 [비동기 쓰기]: 클라이언트의 쓰기 요청 시 1개 또는 최소 노드(W=1)에만 데이터를 기록하고 락 없이 즉시 200 OK 응답 반환
- 2단계 [Stale Read 상황]: 동기화가 완료되지 않은 복제 노드에 읽기 요청이 인입될 경우 업데이트 이전의 구형(Stale) 데이터 반환
- 3단계 [이벤트 전파]: 메시지 큐(Kafka) 또는 자체 로그 스트리밍을 통해 나머지 N개의 복제 노드로 변경 이벤트 전파 및 재현(Replay)
- 4단계 [충돌 해소 및 수렴]: 동시다발적 쓰기로 인한 버전 충돌 감지 시, 타임스탬프 기반 LWW(Last Write Wins) 룰 등으로 병합하여 최종 상태 도달

> 요약: 네트워크 대기 시간을 사용자 경험(UX) 밖으로 빼내어 백그라운드로 처리함으로써 병목을 완벽히 제거한다.

## Ⅳ. 특징

- 극단적 가용성: 장애 발생 시 복제 노드의 상태를 묻지 않고 로컬 단독으로 작동하므로, 네트워크가 파티션(P)되어도 쓰기/읽기 서비스 중단 차단
- 스케일아웃 친화적: 락(Lock) 경합 오버헤드가 없으므로, 노드 개수(N)를 늘리는 만큼 정비례하여 초당 처리량(TPS) 선형 증가
- 클라이언트 보상 책임: DB가 완벽한 최신성을 보장하지 않으므로, 클라이언트 세션 캐시나 멱등성(Idempotency) 설계 등 애플리케이션 레벨의 방어 로직 필수

## Ⅴ. 심화 비교 및 적용 판단

| 비교 축 | 강한 일관성 (Strong) | 최종 일관성 (Eventual) | 인과적 일관성 (Causal) |
|:---|:---|:---|:---|
| 데이터 갱신 후 읽기 | 어느 노드든 반드시 최신값 100% 반환 | 일시적으로 과거(Stale) 값 반환 가능 | 인과관계(댓글의 대댓글 등) 있는 데이터는 순서 보장 |
| 분산 통신 오버헤드 | 분산 락(2PC) 통신으로 막대한 지연 발생 | 통신 대기가 없어 지연 시간 제로 수렴 | 인과 관계 추적을 위한 벡터 시계(Vector Clock) 오버헤드 |
| 적용 도메인 (Fit) | 은행 계정 원장, 재고 차감, 포인트 차감 | 상품 조회수, 통계, 추천 피드, 장바구니 | SNS 대화형 댓글 트리 시스템 |

> 요약: 결제/정산처럼 1원의 오차도 불허하는 코어 트랜잭션 외의, 대다수 트래픽 헤비(Heavy) 도메인은 최종 일관성 채택이 사실상 클라우드 표준이다.

**리스크·대응:**
- Read-Your-Writes 불일치: 사용자가 자신이 방금 올린 글을 못 보고 "등록 실패"로 착각해 중복 등록 시도 → 세션 핀닝(Session Pinning) 또는 쓰기 직후 일정 시간은 Primary 노드 강제 조회(Read-after-Write 보장)
- 양방향 업데이트 충돌: 동일 키에 대해 두 노드에서 동시 수정 발생(Split-Brain) → 애플리케이션 레벨의 분쟁 해결 로직(CRDT 자료구조 적용 등) 병합
- 장기 Inconsistency 위험: 백그라운드 큐 장애로 영구적 불일치 발생 상태 고착화 → 주기적인 Read Repair 쿼리와 Anti-Entropy 배치 잡 스케줄링으로 데이터 무결성 자체 감사

## Ⅵ. 실무 적용 및 결론

**적용 방안 3개:**
1. MSA 기반 데이터 동기화 아키텍처: 서비스 간 통신 시 직접 API 조회를 피하고, Kafka 기반의 CDC(Change Data Capture) 이벤트를 발행하여 구독(Subscribe) 서비스들이 자체 읽기 모델(Materialized View)을 비동기로 갱신하는 CQRS 패턴 구현
2. Quorum 레벨 동적 조정: Cassandra나 DynamoDB 환경에서 일관성 강도를 조절하기 위해 읽기 정족수(R)와 쓰기 정족수(W)를 합산하여 리플리카 수(N)보다 크게 설정(`W + R > N`)하여 필요 시 강한 일관성 흉내 구현
3. 보상 트랜잭션 설계: 최종 일관성 하에서 이미 진행된 마이크로서비스 트랜잭션이 논리적 오류(재고 부족 등)를 만날 경우, 이벤트를 거꾸로 발행해 되돌리는 Saga 패턴의 보상(Compensation) 로직 구현

**결론 (2줄):**
- 기술사 판단: 최종 일관성은 RDBMS의 ACID 제약을 부수고 무한 수평 확장을 이끌어낸 클라우드 아키텍처의 위대한 타협이며, 이로 인해 발생하는 '시간차'는 기술적 장애가 아닌 비즈니스 정책으로 통제해야 할 대상이다.
- 향후 방향: 모바일, IoT 환경으로 접어들며 단말기의 오프라인 동기화 이슈까지 겹쳐, 최종 일관성을 자동으로 병합해주는 CRDT(Conflict-free Replicated Data Type) 구조가 차세대 NoSQL의 핵심 분산 기법으로 확산되고 있다.
