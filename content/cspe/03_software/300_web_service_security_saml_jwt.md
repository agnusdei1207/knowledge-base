## 핵심 인사이트 (3줄 요약)
- 회사 포털에 한 번만 로그인하면 메일, 전자결재, 메신저를 다 쓸 수 있는 **SSO(단일 로그인)**를 구현할 때, "이 사람은 인증된 직원이다!"라는 **증명서(토큰)**를 시스템끼리 어떻게 주고받을지가 핵심임.
- **SAML(샘엘)**은 주로 B2B 기업 환경에서 쓰이는 크고 무거운 **'XML 기반의 여권'**. 회사의 중앙 인증 서버(IdP)가 구글 워크스페이스나 세일즈포스 같은 외부 서비스에 "우리 직원이니 통과시켜 줘!"라고 보증을 서주는 전통적인 표준임.
- 반면 **JWT(제이더블유티)**는 크기가 작고 가벼운 **'JSON 기반의 모바일 탑승권'**. 무거운 XML 파싱 없이, 모바일 앱과 최신 REST API 서버 간에 빠르고 콤팩트하게 인증 정보를 주고받는 현대 클라우드 네이티브의 절대 표준임.

## Ⅰ. 개요 및 필요성
- **개요**: 분산된 웹 환경과 마이크로서비스 간에 사용자 인증(Authentication) 및 인가(Authorization) 정보를 안전하게 교환하기 위한 보안 표준 프로토콜 및 데이터 포맷.
- **필요성**: 우리 회사 직원이 사내망(포털)에 로그인함. 그리고 사외망인 '세일즈포스(영업 툴)' 버튼을 누름. 세일즈포스 서버는 이 사람이 우리 직원인지 모름. **"아니, 직원이 매번 비밀번호를 또 치게 하지 말고, 우리 회사 서버가 세일즈포스 서버한테 '얘 우리 직원 맞고 등급은 과장임!' 이라는 위조 불가능한 인증서를 쏴줄 순 없을까?"** ➡️ SAML, JWT의 탄생.
---
## Ⅱ. 핵심 아키텍처 및 원리 (SAML vs JWT)
두 기술 모두 서명(Signature)을 통해 위조를 방지함. 형태와 쓰임새가 다를 뿐임.

### 1. SAML (Security Assertion Markup Language) - 기업용 묵직한 XML
- **방식**: 브라우저를 통해 통신함. 사용자가 서비스(SP)에 접근 ➡️ 서비스가 인증 서버(IdP)로 튕겨냄(리다이렉트) ➡️ 인증 서버가 로그인 후 **XML 형태의 보증서(Assertion)**를 만들어 브라우저를 통해 서비스로 다시 던짐.
- **특징**: 보안은 철저하나 XML 파싱이 무겁고 브라우저 리다이렉트에 크게 의존하므로, 모바일 앱이나 백엔드 서버 간의 API 통신에는 쓰기 너무 힘듦.

### 2. JWT (JSON Web Token) - 모바일용 가벼운 JSON
- **방식**: `Header(알고리즘) . Payload(사용자 정보) . Signature(서명)` 세 부분으로 나뉜 **Base64 인코딩 문자열**.
- **특징 (무상태성, Stateless)**: 세일즈포스 서버가 JWT 토큰을 받으면, 굳이 우리 회사 서버에 "이 토큰 진짜야?"라고 물어볼 필요가 없음. 토큰 맨 뒤에 달린 **'서명(Signature)'을 자체적으로 암호학적 검증(해독)**해서 위조되지 않았음만 확인하고 바로 통과시킴. DB 조회가 필요 없어 API 속도가 미친 듯이 빠름.

```text
[ 인증 패러다임의 변화 ]

 🏢 [ 전통적 B2B (SAML 기반 SSO) ]
 사원 ➡️ (1. 구글독스 접속) ➡️ (2. 회사 포털로 튕김) ➡️ (3. 로그인 성공) ➡️ (4. "이 사람 우리 직원임" 이라는 XML 덩어리 들고 다시 구글독스 통과!)

 📱 [ 현대 B2C / MSA (JWT 기반 API) ]
 앱 ➡️ (1. 로그인 ➡️ 100글자짜리 짧은 텍스트 JWT 발급받음)
 앱 ➡️ (2. 결제 API 서버) : "나 결제할래! 여기 내 JWT 토큰!"
 결제 서버 ➡️ "서명 확인 완료! DB 안 봐도 네가 누군지 알겠다 통과!" (초고속)
```

## Ⅲ. 오해와 진실
| 오해 | 진실 |
|---|---|
| "JWT 안에 주민번호나 비밀번호 넣어도 되죠? 어차피 서명되어 있으니까!" | **큰일 날 소리.** JWT는 서명(위조 방지)만 되어 있을 뿐, **내용물(Payload)은 누구나 Base64 디코딩 사이트에서 평문으로 다 읽어볼 수 있음.** (암호화가 아님). 절대로 민감한 개인정보를 넣으면 안 되고, User ID와 만료 시간만 최소한으로 넣어야 함. |
| "JWT는 토큰을 탈취당하면 끝 아닌가요?" | 맞음. 한 번 발급된 JWT는 서버에서 '강제 폐기(Revoke)'하기가 구조적으로 불가능함 (무상태성 때문). 그래서 **Access Token 수명은 5분~1시간으로 매우 짧게** 주고, 길게 유지할 땐 Refresh Token을 섞어 쓰는 보안 아키텍처가 필수임. |

## Ⅳ. 실무 적용 및 기술사 판단
- **클라우드 네이티브와 OAuth 2.0 / OIDC 연동**: 기술사는 최신 시스템을 설계할 때 낡은 SAML 대신, OAuth 2.0 인가(Authorization) 체계 위에 얹혀진 **OIDC(OpenID Connect)** 표준을 채택해야 함. OIDC는 사용자 '신원'을 알려줄 때 무거운 XML 대신 **가벼운 JWT(ID Token)를 사용하여 모바일 앱, SPA(React), K8s 마이크로서비스 등 전 영역에 걸쳐 완벽한 호환성을 제공**하기 때문임.
- **MSA에서의 중앙 집중식 인가(API Gateway 연계)**: 백엔드의 파드(Pod) 50개가 매번 JWT 서명을 검증하면 비효율적임. 기술사는 **API Gateway 계층에서 JWT 서명을 1차로 일괄 검증(Offloading)**하여 유효하지 않은 트래픽을 커팅하고, 100% 안전한 사용자 ID만 내부 마이크로서비스로 넘겨주는 Zero Trust 아키텍처를 설계해야 함.
---
## Ⅴ. 기대효과 및 결론
- 한 번의 로그인으로 수십 개의 흩어진 시스템을 끊김 없이 넘나들게 만들어주는 최고의 사용자 경험(UX)이자 필수 기업 거버넌스 도구.
- 수백 대의 분산 서버가 중앙 DB를 매번 찌르며 세션(Session)을 확인하던 병목 현상을 타파하고, 토큰 그 자체만으로 증명이 끝나는(Stateless) JWT를 통해 클라우드의 무한 확장성(Scalability)을 뒷받침하는 핵심 보안 기반임.

### 📌 관련 개념 맵
- Identity and Access Management (IAM) ➡️ SSO (Single Sign-On) ➡️ SAML (XML, B2B) ➡️ OAuth 2.0 / OIDC ➡️ JWT (JSON, Stateless API)

### 📈 관련 키워드 및 발전 흐름도
- 쿠키/세션(Session) 기반의 단일 서버 로그인 ➡️ 시스템이 분산되면서 쿠키를 공유할 수 없는 문제 발생 ➡️ 2000년대 초 XML 기반의 강력한 기업용 연동 표준 **SAML** 등장 ➡️ 모바일 시대가 열리며 XML과 브라우저 리다이렉트의 한계 봉착 ➡️ REST API에 특화된 가벼운 **JWT**와 이를 활용한 OIDC의 등장 ➡️ 현재는 사실상 모든 MSA와 모바일/웹 통신이 JWT 기반으로 천하통일 됨 (현재)

### 👶 어린이를 위한 3줄 비유 설명
1. 롯데월드에 가서 기구를 탈 때마다 돈을 내면(매번 로그인) 귀찮죠? 그래서 아침에 입구에서 표를 사면 **'자유이용권 팔찌(토큰)'**를 채워줘요.
2. **SAML**은 '종이로 된 두꺼운 확인서'예요. 보여줄 때마다 직원이 한참 읽어봐야 하지만, 회사 어른들(B2B)끼리 확실하게 약속할 때 써요.
3. **JWT**는 '홀로그램 스티커가 붙은 팔찌'예요. 직원이 스티커(서명)만 슬쩍 봐도 위조가 아닌 걸 1초 만에 알 수 있어서, 사람이 엄청 몰려도 기구를 빨리빨리 태워줄 수 있답니다!

### 🔀 문제 유형별 목차 전환 (이 키워드 출제 시)
- **개념/비교형 (Ⅱ·Ⅲ 강조)**: SAML 2.0(IdP, SP, XML Assertion 기반 브라우저 리다이렉트 흐름)과 JWT(Header, Payload, Signature 암호화 구조 및 Stateless)의 아키텍처 차이점 비교표 제시.
- **아키텍처/실무형 (Ⅳ·Ⅴ 강조)**: 마이크로서비스(MSA) 아키텍처에서 Session 대신 JWT를 채택하는 이유(무상태성 및 확장성). 토큰 탈취 방지를 위한 Access/Refresh 토큰 듀얼 라이프사이클 설계 및 API Gateway를 활용한 중앙 집중적 서명 검증 전략.
