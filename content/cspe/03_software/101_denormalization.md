# 📖 【암기용】 개념 완전 이해

> 목적: 반정규화를 처음 보는 사람도 읽기 성능과 정합성 비용의 교환 관계를 이해하게 만든다. 시험 답안 양식이 아니라, 이해를 위한 설명이다.

## 한눈에
- **개요**: 정규화된 데이터를 조회 목적에 맞게 의도적으로 중복 저장하는 설계
- **왜 필요한가**: 5개 이상 테이블을 매번 조인하면 OLTP 화면 p95 지연이 200ms에서 800ms 이상으로 늘 수 있다. 자주 읽는 결과를 미리 붙여 저장해 조인 비용을 줄인다.
- **핵심 직관**: 매번 재료를 사서 요리하지 않고, 점심 피크 전에 도시락을 미리 만들어 두는 방식이다.

## 깊이 이해
- **배경·문제의식**: 정규화는 중복과 이상 현상을 줄이지만, 주문·회원·상품·쿠폰·배송을 묶는 화면처럼 읽기 경로가 길면 조인 비용과 락 대기가 증가한다.
- **작동 원리**: 원본 테이블은 정규화 상태로 유지하고, 조회 빈도가 높은 속성만 반정규화 컬럼·집계 테이블·Materialized View·캐시에 복제한다. 쓰기 시점에는 트리거, CDC, 배치, 애플리케이션 이벤트로 복제본을 갱신한다.
- **비유**: 도서관 원본 장부는 한 권만 두되, 입구에는 인기 도서 위치표를 붙여 방문자가 서가를 전부 돌지 않게 하는 구조이다.
- **구체 예시**: 주문 목록에서 고객명·상품명·최근 배송상태를 함께 보여줄 때 4-way join 대신 `order_summary`를 두면 1회 조회 logical read를 40,000에서 3,000 page로 줄일 수 있다.
- **흔한 오해·주의점**: 반정규화는 정규화를 포기하는 것이 아니다. 읽기 SLA p95 300ms, 쓰기 정합성 지연 5초 이하처럼 수치 기준을 두고 제한적으로 적용해야 한다.

## 연결 개념
- 정규화 — 중복 제거와 이상 현상 방지의 기준선
- Materialized View — DBMS가 관리하는 사전 계산 결과
- Cache Aside — 애플리케이션 계층의 읽기 경로 단축 방식

# 📝 【답안용】 시험 답안 템플릿

> 목적: 시험장에서 25분에 그대로 쓰는 답안 양식. 작성방식(추상표현 금지·수치·도식·문제유형 전환)을 엄격히 지킨다.
> 핵심: 반정규화는 조인 제거 기법이 아니라 읽기 SLA와 쓰기 정합성 비용을 수치로 교환하는 설계 판단이다.

## 핵심 인사이트 (3줄 요약)

> 1. **본질**: 반정규화는 정규화 모델의 일부 데이터를 조회 패턴에 맞춰 중복·집계·복제 저장하는 물리 설계 기법이다.
> 2. **가치**: 다중 조인, 집계, 원격 조회를 줄여 p95 지연, logical read, DB CPU 사용률을 낮춘다.
> 3. **판단 포인트**: 읽기 빈도, 쓰기 빈도, 허용 정합성 지연, 복구 절차를 함께 계산해야 한다.

## 출제 의도 및 답안 포인트

| 출제 의도 | 반드시 짚을 핵심 | 감점 회피 포인트 |
|:---|:---|:---|
| DB 물리 설계 판단 역량 확인 | 정규화 기준선, 조인 비용, 읽기/쓰기 트레이드오프 | 반정규화를 무조건 적용 대상으로 서술 |
| 정합성 리스크 통제 확인 | 트리거, CDC, 배치, Materialized View 갱신 방식 | 중복 데이터 불일치 감시 지표 누락 |
| 실무 성능 개선 절차 확인 | Explain Plan, p95 지연, buffer hit, slow query 검증 | 인덱스 튜닝과 반정규화 적용 순서 혼동 |

> 요약: 이 문제는 중복 허용 여부가 아니라 읽기 SLA와 정합성 통제 비용을 조건부로 판단하는 역량을 요구한다.

---

## Ⅰ. 개요 및 필요성

- 개요: 반정규화는 조회 경로용 중복 저장이다.
- 배경: 정규화 모델은 이상 현상을 줄이나 대량 조회, 집계, 다중 조인 화면에서 CPU와 I/O 비용이 커진다.
- 필요성: 읽기 p95 지연, TPS, 정합성 지연 허용치, CDC·트리거 갱신 기준으로 제한 적용해야 한다.

---

## Ⅱ. 구조 및 구성요소

```text
정규화 원본 테이블 -> 변경 이벤트 -> 반정규화 저장소 -> 조회 API -> 화면/리포트
                    / 트리거 갱신
                    / CDC 스트림
                    / 배치 재계산
```

| 구성요소 | 역할 | 특이사항 |
|:---|:---|:---|
| 원본 테이블 | 3NF 기준 업무 정합성 보관 | PK, FK, UNIQUE로 기준 데이터 보호 |
| 반정규화 컬럼 | 조인 빈도 높은 속성 복제 | 고객명, 상품명, 상태명 등 변경 빈도 낮은 값 |
| 집계 테이블 | 합계·건수·순위 사전 계산 | 일/월 단위 배치 또는 증분 집계 |
| Materialized View | DBMS 관리 조회 결과 저장 | refresh complete, fast refresh 선택 |
| 캐시 | 초단기 읽기 부하 흡수 | TTL 30초, invalidation 이벤트 필요 |

> 요약: 반정규화 구조는 정규화 원본을 기준으로 두고, 조회 경로에 필요한 복제본을 갱신 메커니즘과 함께 배치한다.

---

## Ⅲ. 동작원리 및 흐름도

```text
쿼리 병목 식별 -> 접근 패턴 분석 -> 중복 대상 선정 -> 갱신 방식 결정 -> 검증 지표 측정
```

| 단계 | 처리 내용 | 검증 기준 |
|:---:|:---|:---|
| 1 | Slow query, Explain Plan, 조인 수 확인 | p95 300ms 초과, full scan 발생 |
| 2 | 읽기/쓰기 비율과 변경 빈도 산정 | read:write 10:1 이상 후보 |
| 3 | 컬럼 복제, 요약 테이블, Materialized View 선택 | logical read 50% 이상 감소 목표 |
| 4 | 트리거, CDC, 배치, 캐시 TTL 결정 | 정합성 지연 5초 이하 또는 업무 허용치 |
| 5 | 성능 회귀와 데이터 불일치 감시 | diff count 0건, DB CPU 70% 이하 |

> 요약: 반정규화는 병목 식별, 중복 대상 선정, 갱신 방식 결정, 지표 검증 순서로 수행한다.

---

## Ⅳ. 특징

| 구분 | 정규화 중심 | 반정규화 적용 | 판단 포인트 |
|:---|:---|:---|:---|
| 읽기 비용 | 조인 3~6회, 랜덤 I/O 증가 | 조인 제거, summary scan | p95 지연 300ms 이하 |
| 쓰기 비용 | 단일 원본 갱신 | 원본+복제본 갱신 | write amplification 2~5배 |
| 정합성 | DB 제약으로 즉시 보장 | 지연 정합성 발생 가능 | 허용 지연 0초/5초/1분 구분 |
| 운영 | 모델 단순 | 재계산·검증 작업 필요 | 야간 rebuild, diff job 필요 |

> 요약: 반정규화는 읽기 비용을 줄이는 대신 쓰기 증폭과 정합성 검증 비용을 추가하는 물리 설계 선택이다.

## Ⅴ. 심화 비교 및 적용 판단

| 비교 축 | 기존/대안 | 본 키워드 | 선택 기준 |
|:---|:---|:---|:---|
| 구조 | 정규화+인덱스 | 중복 컬럼, 집계 테이블, Materialized View | 인덱스 추가 후에도 p95 300ms 초과 |
| 비용/성능 | 조인 최적화 의존 | 사전 계산으로 CPU·I/O 감소 | 조회 빈도 1,000 QPM 이상 |
| 운영/위험 | 데이터 원본 단일 | 복제본 불일치 가능 | diff 검사, 재처리 큐 확보 |

> 요약: 인덱스와 쿼리 튜닝으로 목표 지연을 맞추지 못하고 읽기 비중이 높은 경우 반정규화를 선택한다.

| 리스크 | 원인 | 대응 방안 | 확인 지표 |
|:---|:---|:---|:---|
| 데이터 불일치 | 원본 갱신 후 복제본 갱신 실패 | CDC 재처리, idempotent update | source-target diff 0건 |
| 쓰기 지연 증가 | 트리거·동기 갱신 과다 | 비동기 이벤트, outbox pattern | write p95 100ms 이하 |
| 오래된 캐시 | TTL·무효화 누락 | cache key versioning, event invalidation | stale read rate 0.1% 이하 |

> 요약: 핵심 리스크는 중복 데이터 불일치이며, 재처리 가능한 이벤트와 정합성 비교 작업으로 통제한다.

| 점검 항목 | 목표 기준 | 측정 방법 |
|:---|:---|:---|
| 조회 성능 | p95 300ms 이하, logical read 50% 감소 | APM, DB execution statistics |
| 정합성 | diff count 0건, 지연 5초 이하 | reconciliation job, CDC lag |
| 운영 비용 | refresh 실패 0건, 재계산 30분 이하 | 배치 로그, 알림, runbook |

> 요약: 도입 효과는 지연시간만 보지 않고 정합성 지연과 refresh 복구 시간을 함께 측정해야 한다.

## Ⅵ. 실무 적용 및 결론

**적용 방안 3개 (필수 — 단계별 또는 항목별):**
1. 주문 목록·대시보드처럼 read:write 10:1 이상인 화면에 summary table을 두고 p95 300ms, DB CPU 70% 이하를 목표로 측정함
2. 원본 변경은 outbox+CDC로 발행하고 복제본 갱신은 idempotent upsert로 구현해 재처리 시 중복 반영을 방지함
3. 매 5분 source-target checksum 비교와 야간 full rebuild 절차를 두어 불일치 1건 이상 발생 시 알림·재계산을 수행함

**결론 (2줄):**
- 기술사 판단: 정합성 즉시성이 필요한 계좌·재고 차감은 정규화 우선, 조회 지연이 매출·운영 지표를 막는 화면은 반정규화 적용
- 향후 방향: HTAP, Column Store, Materialized View 자동 갱신과 함께 반정규화 범위를 지표 기반으로 축소·관리해야 함
