## 핵심 인사이트 (3줄 요약)
- 정규화된 데이터베이스가 조인(JOIN)으로 인해 읽기(SELECT) 성능이 저하되는 것을 막기 위해, **의도적으로 정규화 원칙을 위반하고 데이터의 중복을 허용하는 성능 최적화 기법**.
- 테이블 통합, 테이블 분할(파티셔닝), 중복 컬럼 추가 등의 기법을 사용하며, "데이터 정합성(무결성)의 위험"을 감수하고 "조회 성능 향상"을 얻어내는 전형적인 트레이드오프(Trade-off) 설계임.
- 역정규화는 무작정 엑셀처럼 합치는 것이 아님. 반드시 완벽한 3NF/BCNF 정규화를 먼저 끝낸 뒤, 병목 구간을 수치로 증명하고 최후의 수단으로 신중하게(Prudent) 적용해야 함.

## Ⅰ. 개요 및 필요성
- **개요**: 시스템의 성능 향상, 개발/운영의 단순화를 위해 데이터 모델을 통합, 분할, 중복시키는 과정.
- **필요성**: 정규화를 완벽히 마친 쇼핑몰 DB에서 '이번 달 최고 매출 고객 TOP 10'을 뽑으려면 고객, 주문, 결제, 배송 테이블 등 5개를 무겁게 JOIN해야 함. 대용량 트래픽 상황에서 DB CPU가 버티지 못하므로, 차라리 고객 테이블에 `총_구매액`이라는 컬럼을 중복으로 박아버려 한 번에 읽게 만들 현실적 타협이 필요했음.
---
## Ⅱ. 아키텍처 및 핵심 원리
- **반정규화의 주요 기법**:
  1. **컬럼 반정규화 (중복 컬럼 추가)**:
     - 조인 감소를 위해 부모 테이블의 컬럼을 자식 테이블에 중복으로 넣거나, 계산된 파생 값(`총_주문금액`, `댓글_개수`)을 컬럼으로 미리 저장해 둠.
  2. **테이블 병합 (통합)**:
     - 1:1 관계나 1:M 관계의 두 테이블을 아예 하나의 테이블로 뭉쳐서 조인을 원천 제거함.
  3. **테이블 분할 (수직/수평 파티셔닝)**:
     - **수직 분할**: 컬럼이 100개인 거대 테이블을, 자주 읽는 컬럼과 안 읽는 컬럼(BLOB 등)으로 물리적으로 찢어 디스크 I/O를 줄임.
     - **수평 분할**: 10년 치 로그 데이터가 든 1억 건 테이블을 연도별(2023년, 2024년)로 쪼개어 검색 속도를 극대화함.

```text
[ 컬럼 반정규화 (중복/파생 컬럼) 설계 도식 ]

 [ 완벽히 정규화된 DB (조회 시 매번 COUNT/SUM 연산 필요) ]
 게시글 테이블 (ID, 제목, 내용)  <=====(JOIN)===== 댓글 테이블 (ID, 게시글_ID, 내용)
 
 ⬇️ [ 반정규화 수행: "댓글 개수"라는 중복/파생 컬럼을 의도적으로 추가 ]
 
 [ 반정규화된 DB (조인 없이 게시글 테이블만 읽으면 끝!) ]
 게시글 테이블 (ID, 제목, 내용, 🚨댓글_총_개수(중복))
 
 * 부작용(Trade-off): 누군가 댓글을 삭제하면, 댓글 테이블뿐만 아니라 게시글 테이블의 
   `댓글_총_개수` 숫자도 -1 해줘야 하는 '쓰기 오버헤드'와 '동기화 버그' 리스크가 생김.
```

## Ⅲ. 비교 및 연결
| 구분 | 정규화 (Normalization) | 반정규화 (Denormalization) |
|---|---|---|
| **주요 목적** | 데이터 중복 방지, **무결성(정확도) 확보** | 조인 최소화, **조회(SELECT) 성능 향상** |
| **적용 대상 시스템** | OLTP (온라인 트랜잭션, 금융/결제) | OLAP (데이터 웨어하우스, 통계 분석), 대형 SNS |
| **트레이드오프** | 쓰기는 빠르나 읽기가 무거움 (JOIN 발생) | **읽기는 빠르나 쓰기(UPDATE) 시 2배로 느리고 위험함** |
| **설계 순서** | 프로젝트 초기 개념/논리 설계 단계 | **물리 설계 단계에서 제한적으로 적용** |
---
## Ⅳ. 실무 적용 및 기술사 판단
- **반정규화의 선행 조건 (최후의 수단)**: 성능이 느리다고 무턱대고 컬럼을 합치면 기술 부채(Technical Debt)의 지옥이 열림. 테이블을 합치기 전에 반드시 1) 인덱스(Index) 튜닝을 해보았는가? 2) 애플리케이션 단에서 Redis 캐시(Cache)를 적용할 수 있는가? 3) DB 서버의 Memory/CPU를 스케일업할 수 있는가?를 묻고, 모두 실패했을 때 최후의 물리적 수단으로 역정규화를 선택해야 함.
- **데이터 정합성 파괴 방지(Trigger)**: 중복 컬럼(`댓글_총_개수`)을 유지하기 위해서는 트랜잭션이 완벽하게 묶여야 함. 실무에서는 개발자가 애플리케이션 단에서 UPDATE를 치는 것을 까먹는 실수를 막기 위해, DB 자체의 트리거(Trigger)나 배치(Batch) 프로그램을 통해 백그라운드에서 동기화 로직을 강제하는 안전장치가 필수적임.
---
## Ⅴ. 기대효과 및 결론
- 교과서적인 완벽함(정규화)을 고집하다가 서비스가 멈추는 비즈니스적 재앙을 막고, 시스템의 현실적인 응답 속도(SLA)를 달성하게 해주는 실용적 아키텍처 기법임.
- 데이터의 정합성을 약간 희생하더라도 폭발적인 읽기 속도를 얻어내는 이 철학은, 훗날 넷플릭스/인스타그램이 채택하는 NoSQL 데이터 모델링(처음부터 무한 중복을 허용)의 근간 사상으로 이어짐.

### 👶 어린이를 위한 3줄 비유 설명
1. 책(데이터)을 주제별로 1층, 2층, 3층에 완벽하게 분리해서 꽂아두는 게 '정규화'예요. 정리하기엔 최고죠!
2. 그런데 손님들이 "해리포터 1, 2, 3권을 세트로 빨리 줘요!"라고 할 때마다 사서가 1~3층을 뛰어다녀야 해서(JOIN) 쓰러지기 일보 직전이에요.
3. 반정규화는 도서관 규칙을 살짝 어기고, 1층 카운터 옆에 '해리포터 세트 코너(중복 데이터)'를 하나 더 만들어 두는 거예요. 책이 두 권씩 생겨서 공간은 차지하지만, 손님에게 1초 만에 책을 찾아줄 수 있답니다!
