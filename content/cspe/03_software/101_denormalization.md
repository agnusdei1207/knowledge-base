# 📖 【암기용】 개념 완전 이해

> 목적: 반정규화를 처음 보는 사람도 읽기 성능과 정합성 비용의 교환 관계를 이해하게 만든다. 시험 답안 양식이 아니라, 이해를 위한 설명이다.

## 한눈에
- **개요**: 반정규화(Denormalization)는 **정규화**된 데이터 모델의 일부를 조회 성능을 높이기 위해 의도적으로 중복·집계해 저장하는 **물리적 데이터베이스 설계** 기법이다.
- **왜 필요한가**: 정규화된 스키마는 중복은 줄이지만, 여러 테이블을 매번 Join해야 하므로 조회가 많은 화면에서는 CPU와 I/O 비용이 커진다. 반정규화는 자주 함께 조회되는 데이터를 미리 붙여 저장해 이 Join 비용을 줄인다.
- **핵심 직관**: 매번 재료를 사서 요리하지 않고, 점심 피크 시간 전에 인기 메뉴를 도시락으로 미리 만들어 두는 방식이다.

## 핵심 용어 정리

| 용어 | 의미 | 비유 |
|:---|:---|:---|
| 정규화(Normalization) | 반정규화가 되돌리는 기준선 — 함수 종속 기반으로 중복을 제거한 원본 모델(100 참고) | 원본 장부 |
| 반정규화 컬럼 | 다른 테이블의 자주 조회되는 값(고객명, 상품명 등)을 복제해 같은 테이블에 함께 저장한 컬럼 | 계산서에 상품명을 코드 대신 바로 적어둠 |
| 집계 테이블(Summary Table) | 합계·건수·순위 등을 미리 계산해 저장한 테이블 | 영수증 대신 월간 매출 요약표를 미리 뽑아둠 |
| Materialized View(구체화 뷰) | DBMS가 쿼리 결과를 실제 데이터로 저장하고 주기적으로 갱신하는 뷰 | 매번 계산하지 않고 결과를 사진처럼 저장해 둠 |
| 캐시(Cache) | 애플리케이션 계층에서 조회 결과를 짧은 시간 동안 메모리에 보관하는 저장소 | 자주 찾는 서류를 책상 위에 꺼내둠 |
| CDC(Change Data Capture) | 원본 테이블의 변경 이력(트랜잭션 로그)을 실시간으로 읽어 다른 저장소에 반영하는 기법 | 은행 거래 내역을 실시간으로 다른 장부에 옮겨 적음 |
| Outbox Pattern | 원본 데이터 변경과 "변경됐다는 이벤트 기록"을 같은 트랜잭션 안에서 함께 저장해, 이벤트 발행 유실을 막는 패턴 | 소포를 보내면서 동시에 발송 대장에 기록해 둠(둘 다 안 하거나 둘 다 함) |
| Write Amplification(쓰기 증폭) | 원본 1건 갱신이 복제본까지 갱신하면서 실제 쓰기 횟수가 몇 배로 늘어나는 현상 | 편지 1통을 보내려고 사본을 여러 곳에 더 보내야 함 |
| 지연 정합성(Eventual Consistency) | 원본과 복제본이 즉시 같아지지 않고, 일정 시간 후에는 같아짐을 허용하는 정합성 모델 | 뉴스 속보가 방송국마다 몇 초 시차를 두고 나감 |
| Idempotent Update(멱등 갱신) | 같은 갱신을 여러 번 반복 적용해도 결과가 한 번 적용한 것과 같은 성질 | 스위치를 "켜짐"으로 여러 번 눌러도 결과는 항상 켜짐 |

## 깊이 이해

### Join 비용을 페이지 단위로 계산해보기
주문 목록 화면이 주문·고객·상품·쿠폰·배송 5개 테이블을 Join한다고 하자. 10,000건의 주문을 조회할 때, 정규화된 구조에서는 행마다 각 테이블을 인덱스로 랜덤 접근해야 하므로 대략 행당 4번(고객·상품·쿠폰·배송)씩 총 40,000회의 페이지 읽기(logical read)가 발생할 수 있다. 반면 미리 계산해 둔 `order_summary` 테이블 하나를 순차 스캔하면 같은 조회가 약 3,000 페이지 읽기로 끝난다 — 랜덤 I/O를 순차 I/O로 바꾸고 Join 자체를 없앴기 때문이다. 이 차이(약 13배)가 반정규화를 적용하는 실질적 이유다.

### 쓰기 증폭을 수치로 이해하기
반정규화는 공짜가 아니다. 원본 주문 테이블에 1건을 INSERT하면, 이를 참조하는 `order_summary`, 상품별 통계, 고객별 통계까지 갱신해야 한다면 실제 쓰기는 최소 4배(원본 1 + 복제본 3)로 늘어난다. 이를 write amplification이라 하며, 쓰기가 많은 테이블일수록 반정규화 대상 수를 신중히 제한해야 한다. 트리거로 동기 갱신하면 쓰기 지연이 즉시 늘고, 비동기(CDC·이벤트)로 갱신하면 지연은 줄지만 일시적 불일치 구간이 생긴다.

### Outbox 패턴이 필요한 이유 — 이중 쓰기 문제
원본 테이블에 쓴 뒤 별도 메시지 큐에 이벤트를 발행하는 방식(이중 쓰기)은, 원본 쓰기는 성공했는데 이벤트 발행이 실패하면 복제본이 영원히 갱신되지 않는 문제가 생긴다. Outbox Pattern은 원본 데이터 변경과 이벤트 기록을 같은 DB 트랜잭션 안에서 같이 커밋해, "원본은 바뀌었는데 이벤트가 안 나가는" 상황을 구조적으로 없앤다. 이후 별도 프로세스가 outbox 테이블을 읽어(또는 CDC로 트랜잭션 로그를 읽어) 복제본에 반영한다.

### 지연 정합성의 허용 범위를 수치로 정하기
반정규화는 "즉시 일치"를 포기하는 대신 "언젠가 일치"를 목표로 한다. 예를 들어 캐시는 TTL 30초로 설정해, 최악의 경우 30초 동안 오래된(stale) 값을 보여줄 수 있다. 목표는 이 stale read 비율을 0.1% 이하로 관리하는 것이다. CDC 기반 복제본은 지연 5초 이내를 목표로 하고, 5분마다 원본-복제본 checksum을 비교해 불일치가 1건이라도 발견되면 알림을 보내고 재계산(rebuild)한다. 이런 수치 기준이 없으면 "언젠가 일치"가 "영원히 불일치"로 방치될 위험이 있다.

### 멱등 갱신이 필요한 이유
CDC나 메시지 큐는 네트워크 재시도로 같은 이벤트를 두 번 이상 전달할 수 있다(at-least-once delivery). 복제본 갱신 로직이 "잔액에 +1000을 더한다"처럼 누적 연산이면, 같은 이벤트가 중복 적용될 때 값이 실제보다 커지는 오류가 생긴다. 대신 "잔액을 1000으로 설정한다"처럼 최종 상태를 그대로 덮어쓰는 UPSERT로 구현하면, 같은 이벤트가 여러 번 와도 결과가 달라지지 않는다(멱등성).

## 연결 개념
- 정규화(100) — 반정규화가 전제로 삼는 원본 모델과 기준선
- Materialized View, CDC — 반정규화 복제본을 갱신하는 대표 기술 수단
- 이상현상(102) — 반정규화로 재도입될 수 있는 불일치 위험과 대비되는 개념

# 📝 【답안용】 시험 답안 템플릿

> 목적: 시험장에서 25분에 그대로 쓰는 답안 양식. 작성방식(추상표현 금지·수치·도식·문제유형 전환)을 엄격히 지킨다.
> 핵심: 반정규화는 조인 제거 기법이 아니라 읽기 SLA와 쓰기 정합성 비용을 수치로 교환하는 설계 판단이다.

## 핵심 인사이트 (3줄 요약)

> 1. **본질**: 반정규화는 정규화 모델의 일부 데이터를 조회 패턴에 맞춰 중복·집계·복제 저장하는 물리 설계 기법이다.
> 2. **가치**: 다중 조인, 집계, 원격 조회를 줄여 p95 지연, logical read, DB CPU 사용률을 낮춘다.
> 3. **판단 포인트**: 읽기 빈도, 쓰기 빈도, 허용 정합성 지연, 복구 절차를 함께 계산해야 한다.

## 출제 의도 및 답안 포인트

| 출제 의도 | 반드시 짚을 핵심 | 감점 회피 포인트 |
|:---|:---|:---|
| DB 물리 설계 판단 역량 확인 | 정규화 기준선, 조인 비용, 읽기/쓰기 트레이드오프 | 반정규화를 무조건 적용 대상으로 서술 |
| 정합성 리스크 통제 확인 | 트리거, CDC, 배치, Materialized View 갱신 방식 | 중복 데이터 불일치 감시 지표 누락 |
| 실무 성능 개선 절차 확인 | Explain Plan, p95 지연, buffer hit, slow query 검증 | 인덱스 튜닝과 반정규화 적용 순서 혼동 |

> 요약: 이 문제는 중복 허용 여부가 아니라 읽기 SLA와 정합성 통제 비용을 조건부로 판단하는 역량을 요구한다.

## Ⅰ. 개요 및 필요성

- 개요: 반정규화는 조회 경로용 중복 저장이다.
- 배경: 정규화 모델은 이상 현상을 줄이나 대량 조회, 집계, 다중 조인 화면에서 CPU와 I/O 비용이 커진다.
- 필요성: 읽기 p95 지연, TPS, 정합성 지연 허용치, CDC·트리거 갱신 기준으로 제한 적용해야 한다.

---

## Ⅱ. 구조 및 구성요소

```text
정규화 원본 테이블 -> 변경 이벤트 -> 반정규화 저장소 -> 조회 API -> 화면/리포트
                    / 트리거 갱신
                    / CDC 스트림
                    / 배치 재계산
```

| 구성요소 | 역할 | 특이사항 |
|:---|:---|:---|
| 원본 테이블 | 3NF 기준 업무 정합성 보관 | PK, FK, UNIQUE로 기준 데이터 보호 |
| 반정규화 컬럼 | 조인 빈도 높은 속성 복제 | 고객명, 상품명, 상태명 등 변경 빈도 낮은 값 |
| 집계 테이블 | 합계·건수·순위 사전 계산 | 일/월 단위 배치 또는 증분 집계 |
| Materialized View | DBMS 관리 조회 결과 저장 | refresh complete, fast refresh 선택 |
| 캐시 | 초단기 읽기 부하 흡수 | TTL 30초, invalidation 이벤트 필요 |

> 요약: 반정규화 구조는 정규화 원본을 기준으로 두고, 조회 경로에 필요한 복제본을 갱신 메커니즘과 함께 배치한다.

## Ⅲ. 동작원리 및 흐름도

```text
쿼리 병목 식별 -> 접근 패턴 분석 -> 중복 대상 선정 -> 갱신 방식 결정 -> 검증 지표 측정
```

| 단계 | 처리 내용 | 검증 기준 |
|:---:|:---|:---|
| 1 | Slow query, Explain Plan, 조인 수 확인 | p95 300ms 초과, full scan 발생 |
| 2 | 읽기/쓰기 비율과 변경 빈도 산정 | read:write 10:1 이상 후보 |
| 3 | 컬럼 복제, 요약 테이블, Materialized View 선택 | logical read 50% 이상 감소 목표 |
| 4 | 트리거, CDC, 배치, 캐시 TTL 결정 | 정합성 지연 5초 이하 또는 업무 허용치 |
| 5 | 성능 회귀와 데이터 불일치 감시 | diff count 0건, DB CPU 70% 이하 |

> 요약: 반정규화는 병목 식별, 중복 대상 선정, 갱신 방식 결정, 지표 검증 순서로 수행한다.

## Ⅳ. 특징

| 구분 | 정규화 중심 | 반정규화 적용 | 판단 포인트 |
|:---|:---|:---|:---|
| 읽기 비용 | 조인 3~6회, 랜덤 I/O 증가 | 조인 제거, summary scan | p95 지연 300ms 이하 |
| 쓰기 비용 | 단일 원본 갱신 | 원본+복제본 갱신 | write amplification 2~5배 |
| 정합성 | DB 제약으로 즉시 보장 | 지연 정합성 발생 가능 | 허용 지연 0초/5초/1분 구분 |
| 운영 | 모델 단순 | 재계산·검증 작업 필요 | 야간 rebuild, diff job 필요 |

> 요약: 반정규화는 읽기 비용을 줄이는 대신 쓰기 증폭과 정합성 검증 비용을 추가하는 물리 설계 선택이다.

## Ⅴ. 심화 비교 및 적용 판단

| 구분 | 기존/대안 | 본 키워드 | 선택 기준 |
|:---|:---|:---|:---|
| 구조 | 정규화+인덱스 | 중복 컬럼, 집계 테이블, Materialized View | 인덱스 추가 후에도 p95 300ms 초과 |
| 비용/성능 | 조인 최적화 의존 | 사전 계산으로 CPU·I/O 감소 | 조회 빈도 1,000 QPM 이상 |
| 운영/위험 | 데이터 원본 단일 | 복제본 불일치 가능 | diff 검사, 재처리 큐 확보 |

> 요약: 인덱스와 쿼리 튜닝으로 목표 지연을 맞추지 못하고 읽기 비중이 높은 경우 반정규화를 선택한다.

| 리스크 | 원인 | 대응 방안 | 확인 지표 |
|:---|:---|:---|:---|
| 데이터 불일치 | 원본 갱신 후 복제본 갱신 실패 | CDC 재처리, idempotent update | source-target diff 0건 |
| 쓰기 지연 증가 | 트리거·동기 갱신 과다 | 비동기 이벤트, outbox pattern | write p95 100ms 이하 |
| 오래된 캐시 | TTL·무효화 누락 | cache key versioning, event invalidation | stale read rate 0.1% 이하 |

> 요약: 핵심 리스크는 중복 데이터 불일치이며, 재처리 가능한 이벤트와 정합성 비교 작업으로 통제한다.

| 점검 항목 | 목표 기준 | 측정 방법 |
|:---|:---|:---|
| 조회 성능 | p95 300ms 이하, logical read 50% 감소 | APM, DB execution statistics |
| 정합성 | diff count 0건, 지연 5초 이하 | reconciliation job, CDC lag |
| 운영 비용 | refresh 실패 0건, 재계산 30분 이하 | 배치 로그, 알림, runbook |

> 요약: 도입 효과는 지연시간만 보지 않고 정합성 지연과 refresh 복구 시간을 함께 측정해야 한다.

## Ⅵ. 실무 적용 및 결론

**적용 방안 3개 (필수 — 단계별 또는 항목별):**
1. 주문 목록·대시보드처럼 read:write 10:1 이상인 화면에 summary table을 두고 p95 300ms, DB CPU 70% 이하를 목표로 측정함
2. 원본 변경은 outbox+CDC로 발행하고 복제본 갱신은 idempotent upsert로 구현해 재처리 시 중복 반영을 방지함
3. 매 5분 source-target checksum 비교와 야간 full rebuild 절차를 두어 불일치 1건 이상 발생 시 알림·재계산을 수행함

**결론 (2줄):**
- 기술사 판단: 정합성 즉시성이 필요한 계좌·재고 차감은 정규화 우선, 조회 지연이 매출·운영 지표를 막는 화면은 반정규화 적용
- 향후 방향: HTAP, Column Store, Materialized View 자동 갱신과 함께 반정규화 범위를 지표 기반으로 축소·관리해야 함
