# 📖 【암기용】 개념 완전 이해

## 한눈에
- **개요**: 애플리케이션을 실제로 실행한 상태에서 외부 공격자의 시각으로 해킹 페이로드를 주입해보고 응답을 분석하는 블랙박스 테스트
- **왜 필요한가**: 소스코드만으로는 알 수 없는 런타임 환경 설정 오류, 인증 우회, 메모리 누수 등을 실제 서비스와 동일한 상태에서 잡아내기 위함
- **핵심 직관**: 건물 완공 후 보안요원이 외부에서 창문을 흔들어보고 잠금장치가 뚫리는지 직접 침입을 시도해보는 것

## 핵심 용어 정리

| 용어/표기 | 의미 | 비유·예 |
|:---|:---|:---|
| DAST (동적 분석) | 실행 중인 서비스에 공격 페이로드를 쏘아 테스트 | 모의 침투 훈련 (방패 찌르기) |
| 블랙박스 (Black-box) | 내부 소스코드를 전혀 모른 채 외부에서 찌름 | 닫힌 상자 흔들어보기 |
| 퍼징 (Fuzzing) | 무작위로 비정상 데이터를 대량 주입하여 시스템 마비 유도 | 문에 돌 던져서 부서지는지 확인 |

## 깊이 이해
- **배경·문제의식**: SAST(정적 분석)로 코드를 깨끗하게 짜도, 배포 후 Nginx 설정 오류나 DB 권한 설정 실수로 해킹당하는 경우가 빈번함. 런타임 결함은 코드를 백날 분석해도 안 보임.
- **작동 원리**: 웹 취약점 스캐너(OWASP ZAP, Burp Suite)가 크롤링으로 공격 표면(URL 파라미터 등)을 수집하고, 수만 개의 악성 페이로드(SQLi, XSS 스크립트)를 쏴서 서버가 에러를 뱉는지 분석함.
- **비유**: 전투기를 다 만든 뒤, 직접 공중에서 미사일 모의탄을 쏴보면서 회피 기동이 제대로 되는지 확인하는 테스트.
- **구체 예시**: 회원가입 폼 ID 입력칸에 `' OR 1=1 --` 이라는 페이로드를 전송했더니 정상 로그인이 뚫리는 것을 확인하고 취약점 경고 발생.
- **흔한 오해·주의점**: DAST는 소스코드를 알지 못하므로, 취약점을 찾아도 "어느 파일 몇 번째 줄을 고쳐라"라고 알려주지 못함. "로그인 API 응답에 XSS 취약점 있음" 정도로만 알려줘서 디버깅이 어려움.

## 연결 개념
- **SAST, 퍼징(Fuzzing), 모의해킹, 블랙박스 테스트**

# 📝 【답안용】 시험 답안 템플릿

## 핵심 인사이트 (3줄 요약)

> 1. **본질**: 실행 중인 애플리케이션을 외부(블랙박스)에서 타격하여 런타임 결함을 식별하는 테스트
> 2. **가치**: 환경 설정 오류 탐지, 실제 해커 시점의 공격 표면 검증, 낮은 오탐률 보장
> 3. **판단 포인트**: 정확한 소스코드 위치를 제공하지 못하므로 SAST와의 결합 또는 IAST로 진화가 필수적임

## 출제 의도 및 답안 포인트

| 출제 의도 | 반드시 짚을 핵심 | 감점 회피 포인트 |
|:---|:---|:---|
| 런타임 보안 테스팅의 필요성 인식 | 블랙박스, 퍼징 주입, 환경 설정 결함 식별 | 소스코드 분석으로 혼동 금지 |
| SAST와의 상호보완 관계 | 각 방법의 한계(DAST의 디버깅 어려움) 보완 체계 | SAST만으로 완벽하다는 서술 단정 |

> 요약: 실제 실행 환경에서 취약점을 유발하여 높은 신뢰성(낮은 오탐률)을 확보하나 근본 원인(코드 라인) 추적에는 한계가 있음

---

## Ⅰ. 개요 및 필요성

- 개요: DAST는 애플리케이션이 구동 중인 상태에서 예상치 못한 입력값이나 공격 페이로드를 주입하여 취약점을 탐지하는 블랙박스 테스트 기법임
- 배경: 클라우드 인프라의 복잡성 증가로 소스코드 외적인 런타임 환경(웹 서버, DB 설정 등)의 보안 결함 탐지가 요구됨
- 필요성: 모의해킹(Penetration Test)을 자동화하여 실제 공격 관점에서의 방어 기재 정상 작동 여부 검증 필요

---

## Ⅱ. 구조 및 구성요소 (DAST 구동 아키텍처)

```text
[DAST 스캐너] -> (크롤링/공격표면 수집) -> [대상 웹 서비스] -> (응답 반환) -> [취약점 패턴 분석] -> [결과 리포트]
                   |                                                              |
                   +-> 악성 페이로드(SQLi, XSS 등) 주입                             +-> 에러 여부, 지연시간 체크
```

| 구성요소 | 역할 | 특이사항 |
|:---|:---|:---|
| 크롤러 (Crawler) | 대상 사이트의 URL, 폼, 파라미터 구조 수집 | 공격 표면(Attack Surface) 자동 매핑 |
| 퍼징 엔진 (Fuzzing Engine) | 경계값, 무작위 데이터, 악성 패턴(Payload) 자동 주입 | Time-based 맹목적 공격 탐지 |
| 프록시 에이전트 | 스캐너와 서버 사이의 HTTP 트래픽 가로채기 및 변조 | Burp Suite 등 활용 |
| 응답 분석기 | HTTP Status Code 500, 비정상 데이터 노출 등 분석 | 실제 성공한 취약점만 식별 |

> 요약: 공격 표면을 매핑하고 악성 데이터를 대량 주입한 뒤, 서버의 비정상적 반환 결과를 분석함

---

## Ⅲ. 동작원리 및 흐름도

```text
대상 인프라 구동 -> 크롤링 및 타겟 식별 -> 악성 페이로드 주입 -> 응답 검증 및 취약점 확정
```

- 1단계 [실행 환경 준비]: 애플리케이션을 QA 또는 스테이징 환경에 배포하여 런타임 상태 대기
- 2단계 [공격 표면 매핑]: 웹 스파이더링을 통해 입력 가능한 파라미터, 헤더, 쿠키, API 엔드포인트 수집
- 3단계 [페이로드 인젝션]: 수집된 포인트에 OWASP Top 10 기반의 결함 유발 데이터 수만 건 동시 전송
- 4단계 [반응 분석]: DB 에러 노출, 응답 지연(Time-based SQLi), 인증 우회 등이 발생하면 취약점 확정

> 요약: 실제 해커의 공격 프로세스를 자동화하여 실행 상태의 시스템 약점을 외부에서 타격함

---

## Ⅳ. 특징

- 환경 기반 테스트: 소스코드에 종속되지 않으므로 제3자 솔루션(서드파티 컴포넌트), 서버 설정 오류(Misconfiguration)까지 모두 탐지
- 낮은 오탐률(True Positive): 실제 공격이 성공한 결과(응답)만을 바탕으로 보고하므로 허위 경보가 적어 개발자 신뢰도 높음
- 코드 위치 미제공: "HTTP 파라미터 `id`가 취약함"은 알려주나 소스코드 어느 라인을 고쳐야 하는지는 제공 불가 (디버깅 지연)
- 스캔 시간 소요: 모든 경로를 크롤링하고 수많은 페이로드를 쏘아야 하므로 규모에 따라 수 시간~수십 시간 소요

> 요약: 실환경 결함을 정확히 짚어내어 오탐이 적으나, 런타임이 필수적이라 테스트 시점이 늦고 디버깅이 어려움

---

## Ⅴ. 심화 비교 및 적용 판단

| 비교 축 | SAST (정적 분석) | DAST (동적 분석) | 선택/적용 기준 |
|:---|:---|:---|:---|
| 테스트 기법 / 타이밍 | 화이트박스 / 개발 초기(Coding, Build) | 블랙박스 / 테스트 후반(QA, Staging) | 파이프라인 단계 |
| 커버리지 대상 | 소스 코드 파일 전수 검사 | 크롤링 가능한 실행 경로(API, UI) | 숨겨진 백도어 식별 한계 |
| 언어 종속성 | 파서 지원 언어만 분석 가능 | 언어 무관 (HTTP 기반 검증) | 다양한 기술 스택 혼재 시 |

> 요약: 각기 다른 시점과 방식으로 약점을 탐지하므로 상호 대체재가 아닌 보완재(Complementary) 관계임

**리스크·대응:**
- 운영(Prod) 환경 스캔 리스크: DAST 페이로드가 실제 DB 데이터를 오염시키거나 서비스 마비(DDoS화) 유발 → 반드시 스테이징/QA 전용 환경에서만 격리 실행 (지표: 인프라 격리 수준)
- 마이크로서비스(API) 크롤링 한계: UI가 없는 RESTful API는 크롤러가 경로 수집 불가 → OpenAPI(Swagger) 명세 파일을 DAST 도구에 주입하여 타겟 강제 지정 (지표: API 커버리지율)

---

## Ⅵ. 실무 적용 및 결론

**적용 방안 (DevSecOps 내 DAST 구현):**
1. CI/CD 파이프라인 후반 통합: 소스 빌드(SAST 완료) 후 스테이징 서버로 자동 배포(Deploy)가 완료되면 젠킨스가 OWASP ZAP을 트리거하여 야간 배치 테스트 수행
2. 인증 스캐닝(Authenticated Scan) 설정: 로그인 세션(토큰, 쿠키) 정보를 DAST에 주입하여, 권한이 필요한 내부 페이지의 인가 우회(IDOR) 취약점 심층 검증
3. IAST (상호작용형 보안 테스팅) 진화: DAST의 페이로드 주입(외부 타격)과 SAST의 코드 내부 추적 에이전트를 결합하여, 공격받는 순간 어떤 코드가 실행되었는지 라인 번호를 찾아내는 IAST 도입

**결론:**
- 기술사 판단: 클라우드 네이티브 환경에서는 소스코드 오류보다 인프라 설정 오류(S3 버킷 오픈 등)가 치명적이므로 DAST의 런타임 검증 가치가 더 높아짐
- 향후 방향: 전통적 웹 크롤링 방식에서 벗어나, 모바일 앱과 마이크로서비스 API 보안에 특화된 API-DAST 및 Fuzzing 자동화 기술로 고도화 중임
