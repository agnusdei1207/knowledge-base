## 핵심 인사이트 (3줄 요약)
- **DAST (Dynamic Application Security Testing)**: 실제 **실행 중(Run-time)인 서버**를 외부에서 찔러보며(해커의 시각), 비정상적인 입력값을 무작위로 던져 시스템의 보안 취약점을 찾아내는 블랙박스 보안 테스트.
- 소스코드를 전혀 보지 않고 HTTP 요청/응답 결과만 분석하므로, 개발 언어(Java, Python 등)에 독립적이며 런타임 환경(서버 설정, DB 연결 오류)에서만 발생하는 치명적 버그를 색출함.
- SAST(정적 검사)의 약점인 '환경 설정 오류'를 보완하지만, 어느 코드에서 문제가 터졌는지(Line Number) 알려주지 못하고 테스트 실행 시간이 오래 걸리는 것이 단점임.

## Ⅰ. 개요 및 필요성
- **개요**: 해커가 공격하는 것과 동일한 방식으로 작동하는 웹 애플리케이션을 외부에서 스캐닝하고 공격 시뮬레이션을 수행하는 도구.
- **필요성**: 소스 코드를 아무리 꼼꼼히 점검(SAST)해도, 코드가 실제 서버(Linux, Apache) 위에 올라가면 권한 설정이나 인증 쿠키(Cookie) 문제 등 '런타임'에서만 드러나는 구멍이 발생함. 진짜 해커의 관점에서 '문이 잠겨 있는지 직접 손잡이를 돌려보는' 실전 테스트가 필요했음.
---
## Ⅱ. 아키텍처 및 핵심 원리
- **크롤링과 퍼징 (Crawling & Fuzzing)**:
  1. **크롤링 (Discovery)**: DAST 도구(OWASP ZAP, Burp Suite 등)가 웹사이트의 모든 링크, 폼, API 엔드포인트를 돌아다니며 지도를 그림.
  2. **공격/퍼징 (Attack/Fuzzing)**: 알아낸 입력 폼(로그인 창, 검색창)에 `1' OR '1'='1` 같은 SQL 인젝션 공격 페이로드나 XSS 스크립트를 수만 개 던져봄.
  3. **분석 (Analysis)**: 서버가 "Database Error" 같은 민감한 로그를 뱉어내는지, 아니면 스크립트가 실행되어 버리는지 응답(Response)을 분석하여 취약점 판별.

```text
[ DAST의 블랙박스 공격 원리 ]

 (DAST Tool - 해커 빙의)                      (운영/테스트 중인 Web Server)
 
 [ 1. 크롤링 ] "로그인 폼 발견!"       ➡️ (HTTP GET)     [ Web + WAS + DB ]
                                                             |
 [ 2. Fuzzing ] "해킹 문자열 주입!"  ➡️ (HTTP POST)    (코드 내부 안 보임)
   - payload: <script>alert(1)</script>                      |
                                                             ⬇️
 [ 3. 응답 분석 ] "어라? 서버가       ⬅️ (HTTP 200 OK)  [ XSS 취약점 폭발! ]
     알림창을 그대로 띄워주네? 해킹 성공!"  (스크립트 포함)
```

## Ⅲ. 비교 및 연결
| 구분 | SAST (정적 테스트) | DAST (동적 테스트) |
|---|---|---|
| **접근 방식** | 화이트박스 (소스 코드 분석) | **블랙박스** (외부 HTTP 공격) |
| **언어 종속성** | 개발 언어(Java, Go)마다 다른 룰 필요 | 언어 무관 (HTTP 기반 모든 웹 커버) |
| **발견하는 취약점**| 코드 작성 결함 (로직 오류) | **환경 설정, 인증/인가 우회, 런타임 오류** |
| **결과 피드백** | "Controller.java 45번 줄을 고치시오" | "게시판 검색창이 XSS에 뚫립니다" (코드 위치 모름) |
---
## Ⅳ. 실무 적용 및 기술사 판단
- **CI/CD 파이프라인 통합의 난관**: SAST는 1~2분이면 끝나서 빌드 파이프라인에 넣기 좋지만, DAST는 수만 개의 폼을 크롤링하고 찔러보느라 수 시간이 걸림. 따라서 실무(DevSecOps)에서는 DAST를 메인 배포 파이프라인에 동기적(Synchronous)으로 넣지 않고, 주말이나 야간(Nightly)에 별도 환경(Staging)에서 돌리는 비동기 전략을 취함.
- **IAST (Interactive AST)의 부상**: SAST(정확한 줄 번호)와 DAST(런타임 검증 및 오탐 감소)의 장점만 결합한 '그레이박스' 테스트인 IAST가 차세대 도구로 각광받고 있음. 앱 내부에 에이전트를 심어놓고 DAST처럼 밖에서 찌를 때 내부 코드 흐름을 캡처하는 방식임.
---
## Ⅴ. 기대효과 및 결론
- 실제 공격자(해커)가 맞닥뜨리는 것과 완벽히 동일한 환경에서 취약점을 찾아내므로, 발견된 보안 결함이 가짜(False Positive)일 확률이 매우 낮음 (발견되면 진짜 터지는 것).
- 현대 마이크로서비스(MSA)와 API 경제 시대에서, 수많은 외부 API와 얽혀 돌아가는 런타임 환경의 복합적 보안 결함을 색출하는 최후의 방패 역할을 수행함.

### 👶 어린이를 위한 3줄 비유 설명
1. SAST가 폭탄의 '설계도'를 책상에서 돋보기로 보는 거라면, DAST는 진짜 만들어진 폭탄을 방탄유리 방에 넣고 밖에서 직접 막대기로 찔러보는 거예요!
2. 설계도만 봤을 때는 몰랐는데, 직접 찔러보니까 엉뚱한 곳에서 연기가 칙! 하고 나는 걸 발견할 수 있죠 (런타임 에러).
3. 막대기로 찔러서 불이 난 건 확인했지만, 폭탄 안의 '어떤 파란색 전선'이 잘못된 건지(코드 줄 번호)는 안 뜯어봐서 모른다는 단점이 있답니다!
