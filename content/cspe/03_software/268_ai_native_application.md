# 📖 【암기용】 개념 완전 이해

> 목적: AI 네이티브 애플리케이션을 처음 봐도 이해하게 만든다. 시험 답안 양식이 아니라, 이해를 위한 설명이다.

## 한눈에
- **개요**: AI 네이티브 애플리케이션은 **AI 모델 추론**과 **데이터 피드백 루프**가 검색·추천·생성·판단·실행 같은 핵심 업무 로직 자체를 수행하도록 설계된 애플리케이션 아키텍처다.
- **왜 필요한가**: 기존 앱에 챗봇 위젯만 얹으면 AI는 부가 기능에 머물러, AI가 실패해도 업무는 그대로 돌아간다. AI 네이티브는 AI 출력이 곧 핵심 기능 결과이므로, 설계 단계부터 컨텍스트 수집·정책 검증·피드백 평가를 구조에 포함시켜야 한다.
- **핵심 직관**: 내비게이션을 나중에 붙인 자동차가 아니라, 경로 판단과 자율 주행 보조가 애초에 차량 제어 계통에 통합된 형태이다.

## 핵심 용어 정리 표 (내부에 등장하는 것들)

| 용어 | 의미 | 비유 |
|:---|:---|:---|
| AI 네이티브 애플리케이션 | AI 추론이 핵심 업무 로직을 수행하는 앱 구조 (상위 개념) | 내비게이션이 내장된 자동차 |
| RAG (Retrieval-Augmented Generation) | 외부 지식을 검색해 LLM 프롬프트에 근거로 주입, 이를 바탕으로 답변 생성 | 답변 전에 참고 자료부터 찾아보는 것 |
| AI Agent | 목표를 세분화해 도구를 호출하고 실행까지 자동화하는 주체 | 스스로 계획을 세워 심부름하는 비서 |
| 가드레일 (Guardrail) | 모델 출력이 정책·권한·근거 기준을 만족하는지 실행 전 검증하는 계층 | 출고 전 품질 검수대 |
| 컨텍스트 계층 | 사용자 권한·세션·업무 상태를 모델이 쓸 형태로 수집·전달 | 상담원에게 미리 건네는 고객 카드 |
| LLMOps | 모델 버전·평가·비용·지연을 지속 관리하는 운영 체계 | 모델을 위한 DevOps |
| 환각 (Hallucination) | 모델이 근거 없는 내용을 사실처럼 생성하는 오류 | 없는 기억을 확신에 차서 말하는 것 |
| Human-in-the-loop | 위험도 높은 액션을 실행 전 사람이 승인하는 절차 | 최종 서명은 사람이 한다 |

## 깊이 이해

### 왜 '부가 기능형 AI'로는 부족한가
- 업무 앱은 원래 고정 화면과 규칙 기반 로직(if-else, 워크플로 엔진)으로 만들어졌다. 여기에 챗봇 API 호출을 한 줄 추가하면, 챗봇이 오류를 내도 업무 흐름 자체는 살아있다 — AI가 실패해도 앱은 안 죽는 구조다.
- AI 네이티브는 반대다. 추천·분류·생성 결과가 곧 화면에 노출되는 값이므로, AI가 틀리면 업무 결과 자체가 틀린다. 그래서 설계 단계부터 "모델이 틀렸을 때 무엇으로 막을 것인가"(가드레일·human-in-the-loop)를 구조에 넣어야 한다.

### 요청 처리 흐름을 숫자로 따라가기
- 사용자가 "이번 달 환불 가능한 주문 알려줘"라고 물으면: ① 컨텍스트 계층이 로그인 사용자 ID와 권한을 확인(수 ms) → ② RAG가 벡터DB에서 관련 주문 문서 top-5를 검색(약 50~100ms) → ③ 검색 문서(문서당 약 300토큰 × 5건 = 1,500토큰)를 프롬프트에 넣어 LLM이 답변 생성(입력 약 1,550토큰, 출력 약 200토큰, 추론 0.5~2초) → ④ 가드레일이 "실제 계정 소유 주문만 언급했는가"를 대조 검증 → ⑤ 사용자의 만족/불만족 클릭이 평가 데이터셋에 적재된다.
- 이 전체가 한 요청 안에서 순차로 일어나며, 총 응답 시간이 p95 2초를 넘으면 SLO 위반으로 잡힌다.

### 토큰 비용을 구체 수치로 이해하기
- LLM 비용은 토큰 단위로 청구된다. 예를 들어 입력 100만 토큰당 3,000원, 출력 100만 토큰당 15,000원인 모델을 쓴다면, 위 예시 요청(입력 1,550토큰, 출력 200토큰)의 비용은 입력 1,550/1,000,000×3,000 ≈ 4.65원 + 출력 200/1,000,000×15,000 = 3원 → 약 7.65원이다.
- 이런 요청이 하루 10만 건이면 월 약 2,300만 원의 변동비가 발생한다. 그래서 캐싱, 프롬프트 압축, 저비용 모델로의 라우팅이 AI 네이티브 앱의 필수 원가 통제 수단이 된다.

### 환각을 판별하는 법
- 환각은 "모델이 검색된 근거 문서에 없는 사실을 답변에 포함시켰는가"로 판별한다. 예를 들어 정답이 있는 평가용 질문(골든셋) 500건을 배포 전마다 실행해 근거 문서와 답변을 대조했을 때, 근거 없는 진술이 10건 나오면 환각률은 10/500 = 2%다.
- RAG로 근거를 주더라도 모델이 근거를 무시하고 자체 지식으로 답할 수 있으므로, 답변에 인용(citation)을 강제하고 "근거가 없으면 답변을 거부"하는 정책이 환각률을 낮추는 핵심 대응이다.

### 비유로 정리
- 매뉴얼만 읽는 상담원(규칙 기반 앱)과, 고객 이력·상품 지식·과거 상담 결과를 실시간으로 조회해 답하고 그 상담 결과가 다음 추천 모델 학습에 반영되는 상담원(AI 네이티브 앱)의 차이다. 후자는 스스로 판단하되, 환불 승인처럼 위험한 결정은 상급자 승인(human-in-the-loop)을 거친다.

### 흔한 오해
- "AI 네이티브 = LLM API를 호출하는 앱"이 아니다. API 호출 한 줄은 부가 기능일 뿐이다. 데이터 접근 권한 설계, 평가 데이터셋 운영, 관측성(토큰 비용·지연·환각률 로그), 모델 응답이 없을 때의 폴백 로직까지 갖춰야 AI 네이티브 구조라 부를 수 있다.

## 연결 개념
- RAG — AI 네이티브 앱에서 컨텍스트 계층과 모델을 잇는 핵심 기법
- AI Agent — 판단을 넘어 도구 호출·실행까지 자동화하는 확장형
- LLMOps — AI 네이티브 앱을 지속 운영하기 위한 평가·배포 체계

# 📝 【답안용】 시험 답안 템플릿

> 목적: 시험장에서 25분에 그대로 쓰는 답안 양식. 작성방식(추상표현 금지·수치·도식·문제유형 전환)을 엄격히 지킨다.
> 핵심: AI 네이티브 앱은 챗봇 추가가 아니라 데이터, 모델, 정책, 피드백 루프가 제품 구조에 포함된 애플리케이션이다.

## 핵심 인사이트 (3줄 요약)

> 1. **본질**: AI 네이티브 애플리케이션은 AI 모델과 데이터 피드백 루프가 핵심 비즈니스 기능을 수행하는 앱 구조이다.
> 2. **가치**: 검색, 추천, 생성, 자동 분류, 의사결정 지원을 사용자 흐름 안에 배치해 업무 처리 시간을 수치로 관리한다.
> 3. **판단 포인트**: 정확도, 환각률, 비용, 지연, 개인정보, human-in-the-loop 범위를 기준으로 설계한다.

## Ⅰ. 개요 및 필요성

- 개요: AI 네이티브 애플리케이션은 AI가 핵심 기능을 수행하는 앱이다.
- 배경: 생성, 추천, 검색, 분류가 제품 흐름에 들어오면 출력이 확률적이고 비용이 호출량에 비례한다.
- 필요성: 데이터 컨텍스트, 모델 품질, 정책 검증, 피드백 운영을 애플리케이션 아키텍처에 포함해야 한다.

## Ⅱ. 구조 및 구성요소

```text
User Context -> Retrieval/Feature Store -> Model/Agent
             -> Policy/Guardrail -> Action/API -> Feedback/Evaluation
```

| 구성요소 | 역할 | 특이사항 |
|:---|:---|:---|
| 컨텍스트 계층 | 사용자, 권한, 세션, 업무 상태 수집 | 개인정보 최소 수집 필요 |
| AI 실행 계층 | LLM, 예측 모델, Agent, 도구 호출 | 지연·비용 관리 필요 |
| 정책·가드레일 | 금칙어, 권한, 근거, 승인 조건 검증 | 위험 액션은 사람 승인 |
| 평가·피드백 | 정확도, 환각률, 사용자 평가 수집 | 지속 평가 데이터셋 운영 |

> 요약: AI 네이티브 앱은 컨텍스트, 모델, 정책, 피드백 루프가 핵심 구성요소이다.

## Ⅲ. 동작원리 및 흐름도

```text
사용자 요청 -> 권한/컨텍스트 확인 -> 검색 또는 특징 생성
-> 모델 추론/도구 호출 -> 가드레일 검증 -> 응답/액션 -> 피드백 수집
```

| 단계 | 처리 내용 | 검증 기준 |
|:---:|:---|:---|
| 1 | 요청·권한·컨텍스트 식별 | RBAC, 데이터 등급 확인 |
| 2 | 검색·특징 생성 | 근거 문서 top-k, feature freshness |
| 3 | 모델 추론과 액션 생성 | p95 지연, 토큰 비용 측정 |
| 4 | 검증·피드백 | 환각률, 승인율, 사용자 평가 |

> 요약: AI 네이티브 앱은 모델 호출 전후에 권한 확인과 출력 검증을 배치해야 한다.

## Ⅴ. 심화 비교 및 적용 판단

| 구분 | 기존/대안 | 본 키워드 | 선택 기준 |
|:---|:---|:---|:---|
| 구조 | CRUD+규칙 엔진 | AI 모델+정책+피드백 | 비정형 입력·추천·생성 필요 |
| 비용/성능 | 서버 처리량 중심 | 토큰 비용+p95 지연 | 요청당 비용 50원 이하 등 정의 |
| 운영/위험 | 예외 처리 명확 | 확률 출력·환각 | 환각률 2% 이하 목표 |

> 요약: AI 네이티브 선택은 업무가 확률적 판단을 허용하는지와 검증 루프를 운영할 수 있는지로 결정한다.

| 리스크 | 원인 | 대응 방안 | 확인 지표 |
|:---|:---|:---|:---|
| 환각 응답 | 근거 부족·모델 추론 오류 | RAG, citation, 답변 거부 정책 | hallucination rate 2% 이하 |
| 비용 폭주 | 긴 프롬프트·반복 호출 | 캐시, 라우팅, 토큰 예산 | 요청당 비용 |
| 권한 위반 | 컨텍스트 필터 누락 | RBAC, ABAC, 감사 로그 | 권한 위반 0건 |

> 요약: 환각, 비용, 권한 위반은 AI 네이티브 앱의 3대 운영 리스크이다.

| 점검 항목 | 목표 기준 | 측정 방법 |
|:---|:---|:---|
| 품질 | 정확도 90%, 환각률 2% 이하 | 평가 데이터셋 |
| 성능/비용 | p95 2초 이하, 요청당 비용 50원 이하 | APM, 비용 로그 |
| 운영/보안 | 승인 로그 100%, 권한 위반 0건 | 감사 로그 |

> 요약: AI 네이티브 앱은 품질, 지연·비용, 권한 지표가 모두 릴리스 기준이 된다.

## Ⅵ. 실무 적용 및 결론

**적용 방안 3개 (필수 - 단계별 또는 항목별):**
1. 아키텍처 설계: RAG, 모델 라우터, 정책 엔진, human-in-the-loop 승인 경로를 기본 구성으로 배치
2. 품질 운영: 골든셋 500건, 환각률 2% 이하, p95 2초 이하, 요청당 비용 50원 이하를 릴리스 기준으로 설정
3. 책임 통제: 개인정보 마스킹, RBAC/ABAC, 출력 감사 로그, 위험 액션 승인 절차를 업무 규정에 반영

**결론 (2줄):**
- 기술사 판단: 단순 질의응답은 AI 부가기능, 업무 판단과 실행이 제품 흐름에 포함되면 AI 네이티브 구조를 선택함
- 향후 방향: AI 네이티브 앱은 Agent, RAG, LLMOps, 정책 엔진이 결합된 자율 업무 애플리케이션으로 발전함
