## Ⅰ. 개요
- **정의**: 대규모 언어 모델의 미세조정·배포·운영을 체계화하는 운영 프레임워크임
- **배경/필요성**: 기존 MLOps(251 참조)로는 프롬프트 관리·RAG 파이프라인·토큰 비용 제어가 불가하여 전용 운영 체계가 필요함
- **비유**: 대형 화물선 전용 항만 시스템처럼 일반 항만으로 처리 불가한 규모에 맞춘 운영 체계임

| 출제 의도 | 반드시 짚을 핵심 | 감점 회피 포인트 |
|:---|:---|:---|
| MLOps 대비 LLM 특화 운영 차별점 | 프롬프트 버전 관리·RAG·비용 최적화 | MLOps와 동일하게 서술 시 감점 |

> 요약: LLM 고유 특성에 맞춘 운영 자동화 프레임워크임

## Ⅱ. 구성요소
```text
Prompt Mgmt --> RAG Pipeline --> Fine-tuning
      |              |               |
      v              v               v
Evaluation --> Gateway/Router --> Serving
                                    |
                                    v
                              Cost Monitoring
```

| 구성요소 | 설명 | 비유 |
|:---|:---|:---|
| Prompt Management | 프롬프트 템플릿 버전 관리·A/B 테스트 | 레시피북 버전 관리 |
| RAG Pipeline | 외부 지식 검색·증강 파이프라인 운영 | 참고서 색인 시스템 |
| Gateway/Router | 모델 라우팅·Rate Limit·토큰 사용량 제어 | 교통 관제탑 |
| Evaluation | Hallucination·Toxicity 등 LLM 품질 평가 | 출하 전 안전 검사 |
| Cost Monitoring | 토큰 소비·API 호출 비용 실시간 추적 | 전기 요금 계량기 |

> 요약: 프롬프트·RAG·게이트웨이·평가·비용 5개 축으로 LLM 운영을 관리함

## Ⅲ. 절차
```text
Prompt Design --> RAG/Fine-tune --> Evaluate --> Deploy + Monitor
```
- 1단계: 프롬프트 설계·버전 등록 — 템플릿 파라미터화 및 테스트 케이스 작성
- 2단계: RAG 구성 또는 미세조정 — 도메인 지식 임베딩·벡터 DB 연동
- 3단계: 평가 — Hallucination 비율·응답 지연·비용 기준 품질 게이트 통과
- 4단계: 배포·모니터링 — 게이트웨이 라우팅 설정 후 토큰 비용·응답 품질 감시

> 요약: 프롬프트 설계 → 지식 증강 → 평가 → 배포의 4단계로 운영함

## Ⅳ. 문제점
- 평가 기준 부재: 정량 지표 정의가 어려워 품질 게이트 자동화가 곤란함
- 토큰 비용 폭증: 사용량 예측 불확실성으로 운영 비용이 급증할 수 있음
- Hallucination 통제 한계: 모델 내부 추론 과정이 불투명하여 사실 오류 검출이 제한적임

> 요약: 평가·비용·Hallucination 세 가지가 LLMOps 고유 난제임

## Ⅴ. 개선방안
1. 단기: 도메인별 평가 벤치마크 셋 구축으로 정량 품질 게이트 확보
2. 중기: 토큰 사용량 예측 모델·캐싱·모델 경량화로 비용 최적화
3. 장기: RAG 기반 Grounding 강화 및 Citation 검증 파이프라인 내재화

> 요약: 평가 체계·비용 제어·Grounding 강화로 단계적 성숙도를 높임

## Ⅵ. 전망
- 발전 방향: 멀티모달 모델 확산으로 LLMOps 범위가 텍스트 외 이미지·음성으로 확장됨
- 기술사적 판단: LLM 서비스 안정성 확보에 LLMOps 성숙도가 결정적 요인임
- 기술사 제언: 기존 MLOps 자산 위에 LLM 특화 계층을 점진적으로 추가하는 전략이 필요함
