## Ⅰ. 개요
- **정의**: 단일 애플리케이션과 필요한 OS 라이브러리만 결합하여 하이퍼바이저 위에서 실행하는 특수 목적 VM 이미지
- **배경/필요성**: 범용 OS는 불필요한 서비스·드라이버를 포함하여 공격 표면과 부팅 시간이 과다함
- **비유**: 풀코스 식당 대신 메뉴 1개만 파는 푸드트럭처럼 필요한 기능만 탑재한 경량 머신

| 출제 의도 | 반드시 짚을 핵심 | 감점 회피 포인트 |
|:---|:---|:---|
| 컨테이너와 VM의 중간 포지션 이해 | 라이브러리 OS 개념·단일 주소 공간 | 범용 워크로드 부적합 한계 언급 필요 |

> 요약: 최소 OS 기능만 포함한 단일 목적 이미지로 보안·성능을 극대화하는 경량 가상화 방식임

## Ⅱ. 구성요소
```text
+------------------+
| Application      |
+------------------+
| Library OS       |
| (Net/FS/Sched)   |
+------------------+
| Hypervisor       |
+------------------+
| Hardware         |
+------------------+
```

| 구성요소 | 설명 | 비유 |
|:---|:---|:---|
| Application | 단일 목적 애플리케이션 바이너리 | 푸드트럭의 단일 메뉴 |
| Library OS | 네트워크·파일시스템 등 필요 OS 기능을 라이브러리로 링크 | 주방 장비 세트 |
| Hypervisor | Xen·KVM 등 유니커널 이미지를 실행하는 가상화 계층 | 주차 공간 제공자 |

> 요약: 애플리케이션과 Library OS가 단일 바이너리로 결합되어 하이퍼바이저 위에서 실행됨

## Ⅲ. 절차
```text
설정 --> 컴파일 --> 빌드 --> 배포
```
- 1단계: 애플리케이션에 필요한 OS 라이브러리 구성 요소 선택(네트워크·블록 등)
- 2단계: 애플리케이션 코드와 선택된 Library OS를 단일 주소 공간으로 크로스 컴파일
- 3단계: 하이퍼바이저 타겟에 맞는 부팅 가능 VM 이미지(unikernel image) 생성
- 4단계: 하이퍼바이저에 이미지 배포 후 수 밀리초 내 부팅·서비스 개시

> 요약: 필요 라이브러리 선택-컴파일-이미지 빌드-배포의 4단계로 경량 VM을 구성함

## Ⅳ. 문제점
- 디버깅 곤란: 셸·로깅 도구가 없어 런타임 문제 진단이 어려움
- 범용성 부족: 멀티프로세스·동적 라이브러리 로딩 미지원으로 적용 범위 제한
- 생태계 미성숙: 빌드 도구·패키지 관리자 등 개발 생태계가 컨테이너 대비 부족

> 요약: 디버깅·범용성·생태계 측면에서 실무 채택 장벽이 존재함

## Ⅴ. 개선방안
1. 단기: 원격 GDB 연결·시리얼 로깅 등 디버깅 인터페이스 보강
2. 중기: 언어 런타임(Go·Rust) 통합으로 적용 가능 워크로드 확대
3. 장기: OCI 호환 유니커널 이미지 표준화로 컨테이너 생태계와 도구 공유

> 요약: 디버깅 도구 보강-언어 지원 확대-표준화 순으로 실무 채택을 촉진하는 방향임

## Ⅵ. 전망
- 발전 방향: 서버리스·엣지 환경에서 초경량·초고속 부팅 수요와 결합하여 확산 전망
- 기술사적 판단: 컨테이너와 경쟁보다 보안 민감·초저지연 영역의 보완재로 포지셔닝
- 기술사 제언: 특정 워크로드(IoT·엣지·함수형) 적합성을 기준으로 도입 타당성 평가 필요
