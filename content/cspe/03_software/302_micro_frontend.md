# 📖 【암기용】 개념 완전 이해

> 목적: 마이크로프론트엔드를 처음 봐도 화면 분해와 조직 독립 배포의 의미를 이해하게 만든다. 시험 답안 양식이 아니라, 이해를 위한 설명이다.

## 한눈에
- **개요**: 마이크로프론트엔드는 **프론트엔드**를 업무 도메인 단위의 **독립 배포 단위(Remote)**로 쪼개고, 이를 **런타임에 조립**해 하나의 화면으로 보여주는 아키텍처다.
- **왜 필요한가**: 단일 SPA가 커지면 빌드 시간, 릴리스 조율, 프레임워크 업그레이드, 장애 영향 범위가 한 팀이 감당할 수 없는 수준으로 커진다. 백엔드는 MSA로 팀을 나눴는데 프론트엔드가 단일 배포로 남으면, 결국 프론트엔드 릴리스 일정이 전체 조직의 병목이 된다.
- **핵심 직관**: 하나의 웹 화면을 여러 팀의 독립 앱 조각이 조립한 결과로 보는 방식이다 — 백화점 건물의 안내·보안은 공통 운영팀이 맡고, 매장별 진열·재고 화면은 각 매장이 독립적으로 운영하는 구조와 같다.

## 핵심 용어 정리 (내부에 등장하는 것들)

| 용어 | 의미 | 비유 |
|:---|:---|:---|
| 마이크로프론트엔드 | 프론트엔드를 도메인 단위 독립 배포 단위로 쪼개는 아키텍처(상위 개념) | 백화점 매장별 독립 운영 |
| Shell (Host) App | 라우팅·공통 레이아웃·인증 상태를 관리하고 Remote를 불러 붙이는 진입점 | 백화점 안내데스크·보안·공용 통로 |
| Remote App | 도메인별 UI 기능을 독립적으로 빌드·배포하는 조각 | 개별 매장 |
| Module Federation | 런타임에 서로 다른 빌드의 JS 모듈을 동적으로 불러와 공유하는 webpack 5 기능 | 매장이 필요할 때마다 본사 재고를 실시간으로 가져다 쓰는 것 |
| Web Component | 브라우저 표준 Custom Element로 만든, 프레임워크 독립적인 UI 조각 | 어느 매장에나 꽂을 수 있는 표준 규격 진열대 |
| iframe | 브라우저가 완전히 격리된 별도 문서로 렌더링하는 삽입 방식 | 건물 안에 있지만 출입구가 따로인 별채 매장 |
| BFF (Backend for Frontend) | 화면(또는 Remote)별로 필요한 API를 모아 제공하는 백엔드 집약 계층 | 매장 전용 물류 창고 |
| Design System | 여러 Remote가 공유하는 시각·접근성 규칙(토큰, 컴포넌트) | 백화점 전체 공통 간판·조명 규정 |
| SemVer (Semantic Versioning) | `주.부.수` 형식으로 변경 영향을 표시하는 버전 규칙 — Remote 간 호환성 판단 기준 | 부품 규격 번호 — 같은 "주" 버전끼리는 호환 보장 |
| SRI (Subresource Integrity) | 불러오는 스크립트가 변조되지 않았음을 해시로 검증하는 브라우저 기능 | 택배 봉인씰 확인 |

## 깊이 이해

### 통합 방식 4가지를 격리 수준으로 비교하기
- **iframe**: DOM·CSS·JS 실행 컨텍스트가 완전히 분리된다. 격리는 가장 강하지만(한 Remote가 죽어도 다른 영역에 전혀 영향 없음), 전역 상태 공유가 어렵고 페이지 전환·스크롤·SEO 처리가 번거로우며 로딩이 느리다.
- **Web Component**: 브라우저 표준 Custom Element로, DOM은 분리(Shadow DOM)되지만 같은 페이지 컨텍스트에서 실행된다. 프레임워크에 상관없이(React든 Vue든) 붙일 수 있어 이식성이 좋다.
- **Module Federation**: JS 모듈을 런타임에 동적으로 공유한다. React 같은 공통 라이브러리를 중복 로딩하지 않고 공유(shared dependency)할 수 있어 번들이 가볍지만, 같은 JS 컨텍스트를 쓰므로 한 Remote의 전역 오류가 다른 Remote에 전파될 위험이 iframe보다 크다 — 그래서 Error Boundary로 감싸는 게 필수다.
- **서버/엣지 조합(SSI, Edge-side composition)**: 브라우저가 아니라 서버/CDN 엣지에서 여러 Remote의 HTML을 미리 합쳐 응답한다. 초기 로딩이 빠르지만 클라이언트 런타임 상호작용(예: 로그인 상태 즉시 반영)은 별도 설계가 필요하다.

### Module Federation을 설정값으로 이해하기
- Remote(예: 상품 화면) 쪽 webpack 설정: `exposes: { "./ProductList": "./src/ProductList" }` — 이 컴포넌트를 외부에 공개한다.
- Shell 쪽 webpack 설정: `remotes: { product: "product@https://cdn.example.com/product/remoteEntry.js" }` — 빌드 시점이 아니라 **런타임**에 이 URL에서 최신 코드를 가져온다.
- 핵심은 Shell과 Remote가 **서로 다른 시점에 독립적으로 빌드·배포**되고도, 브라우저가 페이지를 열 때 최신 `remoteEntry.js`를 가져와 조립한다는 점이다. Remote 팀이 배포하면 Shell을 재배포하지 않아도 사용자는 새 버전을 즉시 보게 된다.

### 번들 예산을 숫자로 관리하기
- 초기 번들 예산을 250KB로 잡았다고 하자. Shell 자체(라우팅, 인증, 공통 레이아웃)가 100KB, 첫 진입 Remote(예: 상품 목록)가 150KB면 합계 250KB로 예산을 딱 채운다.
- 만약 상품·주문·결제 Remote 각각이 React를 중복 포함하면(공유 안 함) React 45KB(gzip 기준)가 3번 로딩되어 135KB가 추가로 낭비된다. Module Federation의 shared dependency 설정으로 React를 한 번만 로딩하게 하면 이 135KB를 아낄 수 있다 — 이것이 "공유 의존성 관리"가 성능 지표에 직접 걸리는 이유다.

### 장애 격리와 조직 경계의 연결
- Shell이 각 Remote를 Error Boundary로 감싸면, 결제 Remote에서 JS 오류가 나도 상품·주문 화면은 정상 동작한다. Error Boundary가 없으면 하나의 Remote 오류가 전체 화면을 하얗게(white screen) 만들 수 있다 — Module Federation처럼 같은 JS 컨텍스트를 공유하는 방식일수록 이 격리 장치가 더 중요하다.
- 조직 관점에서는 "팀 경계 = Remote 경계"가 성립해야 실익이 있다. 상품·주문·결제 3개 팀이 각자 Remote를 갖고 독립 배포하면, 결제 팀의 긴급 수정이 상품 팀의 릴리스 일정을 기다릴 필요가 없어진다 — 이것이 컴포넌트 라이브러리 분리(빌드는 하나, 배포도 하나)와 마이크로프론트엔드(빌드도 배포도 독립)를 가르는 핵심 차이다.

### 비유와 흔한 오해
- **비유**: 백화점에서 안내·보안·주차는 공통 운영팀(Shell)이 맡고, 매장별 진열·재고·판매 화면은 각 매장(Remote)이 독립적으로 꾸미고 운영하되, 매장 간판 규격(Design System)만은 백화점 전체 규정을 따르는 구조다.
- **오해**: 컴포넌트를 npm 패키지로 뽑아 여러 화면에서 import해 쓰는 것은 "코드 재사용"이지 마이크로프론트엔드가 아니다. 마이크로프론트엔드는 독립 빌드 + 독립 배포 + **런타임 통합 책임**(버전 호환, 장애 격리, manifest 로딩)까지 포함해야 성립한다.

## 연결 개념
- Module Federation: 런타임 원격 모듈 로딩(마이크로프론트엔드의 대표 구현 기술)
- BFF: 화면별 API 집약 계층(Remote가 필요한 데이터를 효율적으로 받는 백엔드 대응 구조)
- Design System: 독립 UI의 시각·접근성 일관성 기준(Remote 간 UX 파편화를 막는 장치)

# 📝 【답안용】 시험 답안 템플릿

> 목적: 시험장에서 25분에 그대로 쓰는 답안 양식. 마이크로프론트엔드는 기술 분해가 아니라 조직 경계, 배포 독립성, 사용자 경험 일관성의 트레이드오프를 중심으로 답한다.

## 핵심 인사이트 (3줄 요약)

> 1. **본질**: 마이크로프론트엔드는 프론트엔드를 도메인 단위 Remote 앱으로 분리하고 Shell이 런타임 조립하는 독립 배포 아키텍처이다.
> 2. **가치**: 팀별 릴리스 주기를 분리하고, 단일 SPA의 빌드·테스트·배포 병목과 장애 전파 범위를 축소한다.
> 3. **판단 포인트**: 조직이 도메인 팀으로 나뉘고 릴리스 충돌이 월 2회 이상이면 검토하며, 소규모 제품은 모노리식 SPA를 유지한다.

## 출제 의도 및 답안 포인트

| 출제 의도 | 반드시 짚을 핵심 | 감점 회피 포인트 |
|:---|:---|:---|
| 프론트엔드 아키텍처 분해 이해 확인 | Shell, Remote, 라우팅, 공통 인증, 디자인 시스템 | 컴포넌트 재사용과 동일시 |
| 조직·배포 트레이드오프 판단 확인 | 독립 배포, 팀 자율성, 런타임 통합 복잡도 | 프레임워크 혼용을 장점으로만 서술 |
| 운영 리스크 통제 확인 | 번들 크기, 공통 의존성, 관측성, 장애 격리 | Core Web Vitals와 E2E 테스트 누락 |

> 요약: 이 문제는 화면 분해 기법보다 조직 경계와 사용자 경험 품질을 함께 판단하는 답안이 필요하다.

## Ⅰ. 개요 및 필요성

- 개요: UI를 도메인 단위로 분리한 구조
- 배경: 대규모 SPA는 팀 수 증가에 따라 빌드 시간, 릴리스 승인, 회귀 테스트 범위가 커짐
- 필요성: Shell-Remote 구조와 공통 UX 거버넌스로 독립 배포, 장애 격리, 채널별 릴리스를 통제해야 함

---

## Ⅱ. 구조 및 구성요소

```text
Browser -> Shell App -> Route -> Remote App -> Domain API
  / Shared Auth
  / Design System
  / Observability
```

| 구성요소 | 역할 | 특이사항 |
|:---|:---|:---|
| Shell App | 라우팅, 레이아웃, 인증 상태 보관 | 공통 장애 시 전체 화면 영향 |
| Remote App | 도메인별 UI 기능 제공 | 독립 빌드·배포 단위 |
| Integration Layer | Module Federation, Web Component, iframe | 통합 방식별 격리 수준 차이 |
| Shared Platform | 디자인 토큰, 로깅, 실험 SDK | 버전 호환성 관리 필요 |

> 요약: Shell은 공통 흐름을 잡고, Remote 앱은 도메인 기능을 제공하며, 공유 플랫폼이 UX와 운영 기준을 맞춘다.

---

## Ⅲ. 동작원리 및 흐름도

```text
사용자 접속 -> Shell 로딩 -> Route 판별 -> Remote Manifest 조회 -> Remote 렌더링 -> Metric 수집
```

| 단계 | 처리 내용 | 검증 기준 |
|:---:|:---|:---|
| 1 | Shell HTML·공통 번들 로딩 | LCP 2.5초 이하 |
| 2 | 라우트와 권한 판별 | 인증 상태, RBAC Role |
| 3 | Remote manifest와 버전 확인 | SemVer 호환, SRI 해시 |
| 4 | Remote 컴포넌트 렌더링 | Error Boundary, fallback 화면 |
| 5 | 사용자 행동·오류 수집 | Web Vitals, JS error rate |

> 요약: 런타임 통합은 Shell 진입, Remote 버전 확인, 렌더링, 관측 데이터 수집 순서로 동작한다.

| 리스크 | 원인 | 대응 방안 | 확인 지표 |
|:---|:---|:---|:---|

| 장애 추적 난해 | 런타임 Remote 조립 | Trace ID, source map, Error Boundary | Remote별 error rate |

> 요약: 주요 리스크는 번들 중복, UX 편차, 장애 추적이며 예산·토큰·관측성으로 통제한다.

| 점검 항목 | 목표 기준 | 측정 방법 |
|:---|:---|:---|
| 사용자 경험 | LCP 2.5초, INP 200ms 이하 | RUM, Lighthouse CI |
| 배포 독립성 | Remote 단독 롤백 10분 이내 | CI/CD 로그 |
| 품질 | E2E 핵심 시나리오 통과율 100% | Playwright, Cypress |

> 요약: 성공 여부는 Web Vitals, 단독 롤백 시간, 핵심 시나리오 테스트로 판정한다.

## Ⅵ. 실무 적용 및 결론

**적용 방안 3개 (필수):**
1. Shell은 인증, 라우팅, Error Boundary만 보유하고 상품·주문·결제 Remote는 Module Federation으로 독립 배포함.
2. 디자인 시스템은 토큰, 접근성 규칙, 공통 이벤트 스키마를 SemVer로 배포하고 CI에서 토큰 버전 불일치를 차단함.
3. Remote별 Web Vitals, JS error rate, 배포 버전, Trace ID를 수집해 장애 시 10분 이내 롤백 절차를 운영함.

**결론 (2줄):**
- 기술사 판단: 팀 수 2개 이하·릴리스 월 1회 제품은 단일 SPA, 도메인 팀 다수·릴리스 충돌 반복 제품은 마이크로프론트엔드를 선택함.
- 향후 방향: 런타임 Module Federation과 Edge-side composition이 결합되어 배포 독립성과 사용자 경험 지표를 함께 관리하는 방향으로 발전함.
