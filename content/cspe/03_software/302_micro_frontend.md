## Ⅰ. 개요
- **정의**: 프론트엔드를 독립 배포 가능한 소규모 단위로 분할하여 팀별 자율 개발을 가능하게 하는 아키텍처임
- **배경/필요성**: 백엔드 마이크로서비스 전환 후에도 모놀리식 프론트엔드가 병목이 되어 분할이 필요함
- **비유**: 하나의 신문을 여러 편집부(정치·경제·스포츠)가 독립적으로 만들어 합치는 것과 같음

| 출제 의도 | 반드시 짚을 핵심 | 감점 회피 포인트 |
|:---|:---|:---|
| 프론트엔드 분할 전략과 통합 방식 | 빌드 타임 vs 런타임 통합 구분 | SPA와의 차이를 명확히 서술 |

> 요약: 프론트엔드를 팀 단위로 분리·독립 배포하여 개발 자율성과 배포 속도를 확보하는 아키텍처임

## Ⅱ. 구성요소
```text
[Shell App (Container)]
    |           |           |
  [Team A]   [Team B]   [Team C]
  Fragment   Fragment   Fragment
    |           |           |
  독립 빌드   독립 빌드   독립 빌드
```

| 구성요소 | 설명 | 비유 |
|:---|:---|:---|
| Shell App | 각 Fragment를 로드·라우팅하는 컨테이너 역할을 수행함 | 신문 편집장 |
| Fragment | 팀별 독립 개발·배포되는 UI 단위임 | 개별 지면(섹션) |
| Module Federation | 런타임에 원격 모듈을 동적으로 로드하는 통합 메커니즘임 | 실시간 기사 송고 |
| Shared Library | 공통 UI·유틸을 버전 관리하여 중복을 방지함 | 공통 서체·레이아웃 |

> 요약: Shell App이 독립 Fragment를 런타임 통합하여 하나의 화면으로 구성함

## Ⅲ. 절차
```text
도메인 분할 --> Fragment 개발 --> 통합 전략 선택 --> Shell 연동/배포
```
- 1단계: 비즈니스 도메인 기준으로 프론트엔드 영역을 팀별로 분할함
- 2단계: 각 팀이 독립 기술 스택으로 Fragment를 개발·테스트함
- 3단계: 빌드 타임(NPM) 또는 런타임(Module Federation, iframe) 통합 방식을 선택함
- 4단계: Shell App에 Fragment를 연동하고 독립 배포 파이프라인을 구성함

> 요약: 도메인 분할 → 독립 개발 → 통합 전략 → 연동 배포의 4단계로 구축함

## Ⅳ. 문제점
- 번들 크기 증가: Fragment별 중복 의존성으로 전체 로딩 용량이 커짐
- 일관성 저하: 팀별 상이한 기술 스택으로 UX 일관성이 깨질 수 있음
- 통합 복잡도: Fragment 간 상태 공유·이벤트 전파 설계가 복잡해짐

> 요약: 번들 비대화·UX 불일치·통합 복잡도가 마이크로 프론트엔드의 주요 과제임

## Ⅴ. 개선방안
1. 단기: 공유 라이브러리 싱글턴 로딩으로 중복 번들을 제거함
2. 중기: 디자인 시스템(Design Token)을 공유하여 팀 간 UX 일관성을 확보함
3. 장기: 이벤트 버스·Custom Event 표준화로 Fragment 간 통신 복잡도를 낮춤

> 요약: 싱글턴 공유 → 디자인 시스템 → 이벤트 표준화로 단계적 개선함

## Ⅵ. 전망
- 발전 방향: Server Component와 결합하여 서버 측 Fragment 렌더링이 확산될 전망임
- 기술사적 판단: 대규모 조직에서 프론트엔드 확장성 확보의 표준 패턴으로 정착 중임
- 기술사 제언: 팀 규모·도메인 복잡도에 따라 모놀리스와 마이크로 프론트엔드를 선별 적용할 것을 권고함
