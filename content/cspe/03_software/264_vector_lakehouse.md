# 📖 【암기용】 개념 완전 이해

> 목적: Vector Lakehouse를 처음 봐도 이해하게 만든다. 시험 답안 양식이 아니라, 이해를 위한 설명이다.

## 한눈에
- **개요**: Vector Lakehouse는 **레이크하우스(Lakehouse)** 위에 임베딩 저장·**벡터 검색(ANN)**·거버넌스를 결합해, 원문 데이터와 벡터를 한 관리 체계에서 다루는 AI 데이터 플랫폼이다.
- **왜 필요한가**: RAG·추천 서비스는 원문, 임베딩, 메타데이터, 권한을 함께 관리해야 하는데, 벡터 DB만 따로 쓰면 원본과 임베딩이 이중 저장되어 권한·최신성·계보가 어긋난다.
- **핵심 직관**: 책 원문과 색인 카드를 다른 서고에 따로 두지 않고, 같은 도서관 시스템 안에서 책·색인·대출 권한을 함께 관리하는 방식이다.

## 핵심 용어 정리 (내부에 등장하는 것들)

| 용어 | 의미 | 비유 |
|:---|:---|:---|
| 레이크하우스(Lakehouse) | 데이터 레이크(저비용 대용량 저장)와 웨어하우스(스키마·트랜잭션)의 기능을 결합한 저장 구조 — Vector Lakehouse가 얹히는 **기반** | 창고(레이크)와 정리된 매장 진열대(웨어하우스)를 합친 물류센터 |
| 테이블 포맷(Delta/Iceberg/Hudi) | 레이크 위에서 트랜잭션·버전 관리를 가능하게 하는 파일 포맷 | 창고 재고를 버전별로 기록하는 장부 |
| 임베딩(Embedding) | 텍스트·이미지를 의미가 가까울수록 가까운 좌표에 놓이는 고정 길이 숫자 벡터로 바꾼 것 | 책 내용을 좌표 하나로 요약한 태그 |
| 청크(Chunk) | 긴 문서를 검색 단위로 잘라낸 조각(예: 512 토큰 단위) | 책 한 권을 챕터 단위로 나눠 색인 |
| ANN(근사 최근접 탐색) | 모든 벡터를 다 비교하지 않고 질의 벡터와 가까운 것을 빠르게 근사로 찾는 탐색 방식 | 도서관 전체를 뒤지지 않고 분류 코드 근처만 찾아보는 것 |
| HNSW / IVF / PQ | ANN을 구현하는 대표 인덱스 알고리즘(그래프 탐색 / 군집 분할 / 벡터 압축) | 색인 카드를 조직하는 서로 다른 방식들 |
| 카탈로그(Catalog) | 테이블·컬럼·소유자·등급을 등록해 어떤 데이터가 어디 있는지 기록하는 장부 | 도서관 전체 장서 목록 |
| 계보(Lineage) | 데이터가 어디서 와서 어떻게 가공됐는지의 이력 | 상품의 생산·유통 이력 추적표 |
| ACL(접근통제 목록) | 누가 어떤 데이터에 접근 가능한지 정한 권한 규칙 | 열람실 출입증 등급 |
| RAG | 벡터 검색으로 찾은 근거 문서를 LLM 프롬프트에 넣어 답변을 생성하는 기법 | 시험 볼 때 참고자료를 찾아 펼쳐놓고 답을 쓰는 것 |
| top-k / recall@k | 검색 결과 상위 k개를 반환 / 정답이 그 k개 안에 포함된 비율 | 관련 자료 10개 중 진짜 필요한 자료가 몇 개 들어있는가 |

## 깊이 이해

### 왜 필요했나 — 벡터 DB만 쓸 때 생기는 이중 저장 문제
- 기업 데이터는 이미 Delta·Iceberg·Hudi 같은 테이블 포맷으로 레이크하우스에 저장되어 있다. RAG를 위해 임베딩만 별도 벡터 DB에 복제하면, 원문이 수정돼도 임베딩이 그대로인 "낡은 임베딩(stale embedding)" 문제, 원문에는 있던 접근권한이 벡터 DB 복제본에는 빠지는 "권한 불일치" 문제가 생긴다.
- Vector Lakehouse는 원문 테이블·청크 테이블·임베딩 테이블을 같은 카탈로그 안에 문서 ID로 연결해, 원문이 바뀌면 재색인 대상이 되고 권한도 원문 기준 ACL을 그대로 물려받게 만든다.

### 작동 원리 — 적재부터 검색까지
- 원천 데이터를 레이크하우스 테이블에 적재하고 카탈로그에 등록한다(소유자·등급 기록).
- 문서를 청크(예: 512 토큰)로 나누고 임베딩 모델로 벡터화해 임베딩 테이블에 버전과 함께 저장한다.
- HNSW 같은 ANN 인덱스를 벡터 위에 구축한다.
- 질의가 오면 질의 텍스트도 같은 모델로 임베딩하고, ACL 필터(권한)와 벡터 유사도 검색을 함께 적용해 top-k 문서를 반환한다.

### 구체 수치로 보는 ANN의 효과 — 전수 비교 vs 근사 탐색
- 문서 100만 건을 512 토큰 청크로 나누고 768차원 임베딩으로 저장했다고 하자. 질의 하나마다 모든 벡터와 거리를 전수 비교(brute force)하면 100만 × 768 ≈ 7억 6,800만 번의 곱셈이 필요하다.
- HNSW 같은 그래프 기반 ANN 인덱스는 계층 그래프를 타고 내려가며 후보를 좁히는 방식이라, 탐색 단계 수가 대략 log₂(100만) ≈ 20 단계 수준으로 줄어든다. 전수 비교 대비 후보 비교 횟수가 수만 분의 1로 줄어드는 대신, 최적해를 100% 보장하지 못하는 "근사"라는 대가를 치른다(그래서 recall@10 90% 같은 정확도 지표로 품질을 관리한다).
- 이 검색 결과 중 상위 top-k(예: 10개)만 골라 부서 권한·문서 등급 SQL 필터를 통과한 것만 LLM에 전달한다.

### 판별 원리 — 언제 전용 벡터 DB, 언제 Vector Lakehouse인가
- 단일 애플리케이션이 초저지연(p95 50ms 이하) 검색만 필요하고 원문 거버넌스가 중요하지 않다면 전용 벡터 DB가 더 가볍다.
- 여러 부서가 같은 데이터를 RAG·분석에 함께 쓰고, 문서 등급별 접근통제·계보 추적·감사가 필요하면 Vector Lakehouse가 적합하다. 판단 기준 수치 예: ACL 위반 0건 요구, 계보 100% 등록 요구가 있는 조직이면 Lakehouse 통합이 우선이다.

### 비유와 흔한 오해
- **비유**: 상품 창고와 검색 색인을 따로 운영하지 않고, 재고표·바코드·분류표를 하나의 물류 시스템에서 관리하는 구조다.
- **오해**: Vector Lakehouse는 "이름만 바뀐 벡터 DB"가 아니다. 원문·임베딩·메타데이터·거버넌스·분석 워크로드를 함께 다루는 아키텍처이며, 검색 지연만 놓고 보면 전용 벡터 DB보다 느릴 수 있다(예: p95 50ms vs 200ms).

## 연결 개념
- RAG - 벡터 검색 결과를 LLM 프롬프트에 결합 (Vector Lakehouse의 대표 활용처)
- Lakehouse - 데이터 레이크와 웨어하우스 기능 결합 (Vector Lakehouse가 얹히는 기반 저장 구조)
- Data Governance - 카탈로그, 권한, 계보, 품질 관리 (Vector Lakehouse가 벡터 DB 단독 사용과 차별화되는 지점)

# 📝 【답안용】 시험 답안 템플릿

> 2. **가치**: RAG에서 원문, 청크, 임베딩, 권한, 품질 지표를 같은 데이터 계보로 관리해 검색 결과의 근거성과 접근통제를 확보한다.

## Ⅰ. 개요 및 필요성

- 개요: Vector Lakehouse는 레이크하우스와 벡터 검색의 통합 구조이다.
- 배경: 기업 RAG는 원문 데이터와 임베딩 복제본의 권한·버전·계보가 맞지 않으면 정보 유출과 답변 오류가 발생한다.
- 필요성: 레이크하우스 기반 통합 관리로 데이터 최신성, 접근통제, 감사 추적을 함께 처리해야 한다.

## Ⅱ. 구조 및 구성요소

```text
Raw Data -> Lakehouse Table -> Chunk/Embedding Pipeline -> Vector Index
                         -> Catalog/ACL/Lineage -> Retrieval API -> LLM App
```

| 구성요소 | 역할 | 특이사항 |
|:---|:---|:---|
| 레이크하우스 저장소 | 원문, 청크, 메타데이터 저장 | Delta, Iceberg, Hudi |
| 임베딩 파이프라인 | 청크 분할, 임베딩 생성, 버전 기록 | 모델 버전과 생성일 관리 |
| 벡터 인덱스 | ANN 기반 top-k 검색 | HNSW, IVF, PQ 등 선택 |
| 거버넌스 계층 | 카탈로그, ACL, 계보, 품질 관리 | 부서·등급 필터 필수 |

> 요약: Vector Lakehouse는 저장소, 임베딩, 인덱스, 거버넌스를 하나의 검색 흐름으로 연결한다.

## Ⅲ. 동작원리 및 흐름도

```text
문서 적재 -> 청크 분할 -> 임베딩 생성 -> 인덱스 생성
-> 질의 임베딩 -> 권한 필터+벡터 검색 -> 근거 문서 반환
```

| 단계 | 처리 내용 | 검증 기준 |
|:---:|:---|:---|
| 1 | 원천 데이터 적재와 카탈로그 등록 | 스키마, 소유자, 등급 기록 |
| 2 | 청크·임베딩 생성 | 청크 256~1024 토큰, 모델 버전 기록 |
| 3 | 벡터 인덱스 생성 | recall@10, p95 검색 지연 측정 |
| 4 | 권한 필터 후 검색 | ACL 위반 0건, 근거 문서 반환 |

> 요약: 검색 전 권한 필터와 임베딩 버전 관리가 Vector Lakehouse의 운영 핵심이다.

## Ⅵ. 실무 적용 및 결론

**적용 방안 3개 (필수 - 단계별 또는 항목별):**
1. 데이터 모델: 원문 테이블, 청크 테이블, 임베딩 테이블을 문서 ID와 임베딩 모델 버전으로 연결
2. 검색 설계: ACL 선필터, Hybrid Search, top-k 10개 반환, p95 200ms 목표로 API SLO 정의
3. 운영 관리: 문서 변경 이벤트 기반 재색인, stale embedding 1% 이하, 카탈로그 계보 100% 등록 점검

**결론 (2줄):**
- 기술사 판단: 단일 앱 검색은 전용 벡터 DB, 기업 RAG·감사·권한 통제가 핵심이면 Vector Lakehouse를 선택함
- 향후 방향: Vector Lakehouse는 Data Catalog, Feature Store, RAG Evaluation과 결합한 AI 데이터 운영 플랫폼으로 발전함
