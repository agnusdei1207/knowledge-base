# 📖 【암기용】 개념 완전 이해

> 목적: Vector Lakehouse를 처음 봐도 이해하게 만든다. 시험 답안 양식이 아니라, 이해를 위한 설명이다.

## 한눈에
- **개요**: 데이터 레이크하우스에 벡터 임베딩 저장·검색·거버넌스를 결합한 AI 데이터 플랫폼
- **왜 필요한가**: RAG와 추천 서비스는 원문 데이터, 임베딩, 메타데이터, 권한을 함께 관리해야 한다. 벡터 DB만 쓰면 데이터 계보, 품질, 접근통제가 분리된다.
- **핵심 직관**: 도서관에 책 원문과 색인카드를 따로 두지 않고, 같은 관리 체계에서 책·색인·대출 권한을 함께 관리하는 방식이다.

## 깊이 이해
- **배경·문제의식**: 기업 데이터는 Delta/Iceberg/Hudi 같은 테이블 포맷으로 관리되지만, RAG용 임베딩은 별도 벡터 DB에 복제되는 경우가 많다. 이중 저장은 권한 불일치, 데이터 최신성 지연, 계보 추적 누락을 만든다.
- **작동 원리**: 원천 데이터를 레이크하우스 테이블에 저장하고, 청크와 임베딩을 같은 카탈로그에 등록한다. 검색 시 벡터 유사도와 SQL 필터를 결합해 권한·시간·도메인 조건을 함께 적용한다.
- **비유**: 상품 창고와 검색 색인을 따로 운영하지 않고, 재고표·바코드·분류표를 하나의 물류 시스템에서 관리하는 구조이다.
- **구체 예시**: 문서 100만 건을 512 토큰 청크로 분할해 768차원 임베딩을 저장하고, 부서 권한과 문서 등급을 SQL 필터로 적용한 뒤 top-k 10개만 LLM에 전달한다.
- **흔한 오해·주의점**: Vector Lakehouse는 벡터 DB의 대체 이름이 아니다. 원문·임베딩·메타데이터·거버넌스·분석 워크로드를 함께 다루는 아키텍처이다.

## 연결 개념
- RAG - 벡터 검색 결과를 LLM 프롬프트에 결합
- Lakehouse - 데이터 레이크와 웨어하우스 기능 결합
- Data Governance - 카탈로그, 권한, 계보, 품질 관리

# 📝 【답안용】 시험 답안 템플릿

> 목적: 시험장에서 25분에 그대로 쓰는 답안 양식. 작성방식(추상표현 금지·수치·도식·문제유형 전환)을 엄격히 지킨다.
> 핵심: Vector Lakehouse는 벡터 검색 성능보다 원문-임베딩-권한-계보를 일관되게 관리하는 데이터 아키텍처로 답해야 한다.

## 핵심 인사이트 (3줄 요약)

> 1. **본질**: Vector Lakehouse는 레이크하우스 저장·카탈로그·거버넌스 위에 임베딩 저장과 ANN 검색을 통합한 AI 데이터 플랫폼이다.
> 2. **가치**: RAG에서 원문, 청크, 임베딩, 권한, 품질 지표를 같은 데이터 계보로 관리해 검색 결과의 근거성과 접근통제를 확보한다.
> 3. **판단 포인트**: 벡터 DB 단독 사용과 비교해 최신성, 권한 필터링, 검색 지연, 비용, 운영 복잡도를 평가해야 한다.

## 출제 의도 및 답안 포인트

## Ⅰ. 개요 및 필요성

Vector Lakehouse는 레이크하우스에 벡터 임베딩과 검색 기능을 통합한 아키텍처이다. 기업 RAG는 원문 데이터와 임베딩 복제본의 권한·버전·계보가 맞지 않으면 정보 유출과 답변 오류가 발생한다. 레이크하우스 기반 통합 관리로 데이터 최신성, 접근통제, 감사 추적을 함께 처리한다.

---

## Ⅱ. 구조 및 구성요소

```text
Raw Data -> Lakehouse Table -> Chunk/Embedding Pipeline -> Vector Index
                         -> Catalog/ACL/Lineage -> Retrieval API -> LLM App
```

| 구성요소 | 역할 | 특이사항 |
|:---|:---|:---|
| 레이크하우스 저장소 | 원문, 청크, 메타데이터 저장 | Delta, Iceberg, Hudi |
| 임베딩 파이프라인 | 청크 분할, 임베딩 생성, 버전 기록 | 모델 버전과 생성일 관리 |
| 벡터 인덱스 | ANN 기반 top-k 검색 | HNSW, IVF, PQ 등 선택 |
| 거버넌스 계층 | 카탈로그, ACL, 계보, 품질 관리 | 부서·등급 필터 필수 |

> 요약: Vector Lakehouse는 저장소, 임베딩, 인덱스, 거버넌스를 하나의 검색 흐름으로 연결한다.

---

## Ⅲ. 동작원리 및 흐름도

```text
문서 적재 -> 청크 분할 -> 임베딩 생성 -> 인덱스 생성
-> 질의 임베딩 -> 권한 필터+벡터 검색 -> 근거 문서 반환
```

| 단계 | 처리 내용 | 검증 기준 |
|:---:|:---|:---|
| 1 | 원천 데이터 적재와 카탈로그 등록 | 스키마, 소유자, 등급 기록 |
| 2 | 청크·임베딩 생성 | 청크 256~1024 토큰, 모델 버전 기록 |
| 3 | 벡터 인덱스 생성 | recall@10, p95 검색 지연 측정 |
| 4 | 권한 필터 후 검색 | ACL 위반 0건, 근거 문서 반환 |

> 요약: 검색 전 권한 필터와 임베딩 버전 관리가 Vector Lakehouse의 운영 핵심이다.

> 요약: Vector Lakehouse는 검색 전용 성능보다 기업 데이터 관리 일관성을 우선하는 선택지이다.

## Ⅴ. 심화 비교 및 적용 판단

| 비교 축 | 기존/대안 | 본 키워드 | 선택 기준 |
|:---|:---|:---|:---|
| 구조 | 별도 벡터 DB | Lakehouse 통합 벡터 인덱스 | 원문·권한·계보 통합 필요 시 |
| 비용/성능 | 검색 지연 p95 50ms 목표 | 분석+검색, p95 200ms 허용 | 실시간 검색 요구 여부 |
| 운영/위험 | 데이터 복제 | 카탈로그 중심 관리 | ACL 위반 0건 요구 |

> 요약: 초저지연 검색은 전용 벡터 DB, 거버넌스 중심 RAG는 Vector Lakehouse가 적합하다.

| 리스크 | 원인 | 대응 방안 | 확인 지표 |
|:---|:---|:---|:---|
| 권한 우회 | 검색 후 필터링 | 검색 전 ACL 필터 적용 | ACL 위반 0건 |
| 임베딩 불일치 | 모델 교체 후 부분 재색인 | 임베딩 버전 컬럼, 재색인 배치 | stale embedding 비율 |
| 검색 품질 저하 | 청크 크기·인덱스 파라미터 부적합 | recall@k 평가, hybrid search | recall@10 90% 이상 |

> 요약: 권한, 임베딩 버전, 검색 품질을 운영 지표로 관리해야 한다.

| 점검 항목 | 목표 기준 | 측정 방법 |
|:---|:---|:---|
| 검색 품질 | recall@10 90% 이상 | 정답 질의셋 평가 |
| 지연 | p95 검색 200ms 이하 | API/APM 측정 |
| 거버넌스 | 계보·소유자·등급 100% 등록 | Data Catalog 점검 |

> 요약: Vector Lakehouse 도입은 검색 품질, 지연, 거버넌스 등록률을 함께 본다.

## Ⅵ. 실무 적용 및 결론

**적용 방안 3개 (필수 - 단계별 또는 항목별):**
1. 데이터 모델: 원문 테이블, 청크 테이블, 임베딩 테이블을 문서 ID와 임베딩 모델 버전으로 연결
2. 검색 설계: ACL 선필터, Hybrid Search, top-k 10개 반환, p95 200ms 목표로 API SLO 정의
3. 운영 관리: 문서 변경 이벤트 기반 재색인, stale embedding 1% 이하, 카탈로그 계보 100% 등록 점검

**결론 (2줄):**
- 기술사 판단: 단일 앱 검색은 전용 벡터 DB, 기업 RAG·감사·권한 통제가 핵심이면 Vector Lakehouse를 선택함
- 향후 방향: Vector Lakehouse는 Data Catalog, Feature Store, RAG Evaluation과 결합한 AI 데이터 운영 플랫폼으로 발전함
