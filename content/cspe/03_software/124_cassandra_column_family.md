## 미리 알고가기

- 와이드 컬럼 DB는 파티션 키로 행을 분산하고 파티션마다 가변 컬럼을 저장하는 NoSQL 계열임
- 파티션 키는 데이터의 담당 복제본을, 클러스터링 키는 파티션 내부 정렬·범위 조회 순서를 결정함
- 복제 계수 $N$은 파티션 사본 수이며 읽기 수준 $R$과 쓰기 수준 $W$가 확인할 복제본 수를 정함
- Memtable은 메모리 쓰기 구조, SSTable은 변경하지 않는 디스크 파일, Compaction은 여러 SSTable을 병합하는 작업임
- Tombstone은 삭제·만료 사실을 복제본에 전파하기 위한 삭제 표식이며 조회·Compaction 비용에 영향을 줌

## 작성 근거(검토용)

- Cassandra는 파티션·클러스터링 키, LSM 쓰기 경로, 복제 계수, 일관성 수준, 복구를 핵심 축으로 설명함
- 비교표는 관계형 DB와 데이터 모델·질의·트랜잭션·분산 확장 구조를 같은 기준에서 대비함
- 실무 사례는 로그 적재와 다중 리전 이벤트 저장에서 파티션 크기·쓰기 지연·복구 적체로 검증함

## Ⅰ. 개요

- **정의/개념**: Cassandra는 파티션 키로 데이터를 대등 노드에 분산하고 LSM 쓰기 경로·복제·조정 가능한 일관성으로 확장하는 와이드 컬럼 NoSQL 데이터베이스임
- **배경/필요성**: 여러 노드·리전의 연속 쓰기를 단일 주 노드 없이 수용하고 장애 중에도 복제본으로 처리하기 위해 분산 파티션·복제 구조가 필요함

## Ⅱ. 특징

- 모든 노드가 클라이언트 요청의 조정자가 될 수 있어 고정 주 노드 없이 읽기·쓰기를 분산함
- 쓰기를 Commit Log와 Memtable에 순차 반영하고 SSTable Flush·Compaction으로 디스크 구조를 정리함
- 토큰 범위와 복제 계수로 파티션 복제본을 배치하고 Gossip·복구 작업으로 노드 상태와 사본을 관리함
- 파티션 키 없는 임의 질의·조인보다 미리 정의한 접근 패턴에 맞춰 테이블을 비정규화해야 함

## Ⅲ. 종류 및 비교

| 판단 기준 | 관계형 DB | Cassandra |
|:---|:---|:---|
| 데이터 모델 | 정규화된 테이블·행·외래키 | 파티션별 가변 컬럼과 조회별 비정규화 테이블 |
| 질의 경로 | SQL 조건·조인·집계로 관계를 탐색 | 파티션 키와 클러스터링 범위로 대상 파티션을 조회 |
| 트랜잭션 범위 | 다중 행·테이블 ACID 트랜잭션 | 단일 파티션 원자 연산 중심이며 조건부 갱신은 합의 비용 발생 |
| 일관성 통제 | 트랜잭션 격리 수준과 복제 구성을 설정 | 요청별 읽기·쓰기 일관성 수준과 복제 계수를 설정 |
| 수평 확장 | 샤딩·분산 DB 구성을 별도 설계 | 토큰 범위를 노드에 재분배해 용량·처리량을 확장 |
| 적합 조건 | 관계·조인·복합 트랜잭션이 중심인 업무 | 파티션 키가 명확하고 연속 분산 쓰기가 많은 데이터 |

> 요약: 관계형 DB는 관계·조인·다중 행 트랜잭션에, Cassandra는 파티션 키 중심 질의·분산 쓰기·요청별 일관성에 초점을 둠.

## Ⅳ. 구성요소 및 구조

| 구성요소 | 설명 |
|:---|:---|
| 조정자 노드·토큰 범위 | 요청을 수신하고 파티션 키의 토큰으로 담당 복제본을 선택함 |
| 파티션·클러스터링 키 | 복제본 위치와 파티션 내부 정렬·범위 조회 경로를 정함 |
| Commit Log·Memtable·SSTable | 쓰기 내구성, 메모리 갱신, 불변 디스크 저장을 단계별로 담당함 |
| Gossip·장애 감지 | 노드 생존·토큰 정보를 공유해 요청 경로와 복구 대상을 판단함 |
| 복제·일관성·복구 | 복제 계수와 확인 복제본 수를 적용하고 사본 차이를 수선함 |

```text
클라이언트 -> 조정자 노드 -> 토큰별 복제본
                              |
                Commit Log -> Memtable -> SSTable
```

> 요약: 조정자 노드는 파티션 키의 토큰으로 복제본을 선택하고 각 복제본은 Commit Log·Memtable·SSTable 경로로 저장함.

## Ⅴ. 원리 및 절차 흐름도

```text
쓰기 요청 -> 복제본 선택 -> 로그·메모리 기록 -> 일관성 확인 -> Flush·Compaction
```

1. **쓰기 요청 수신**: 조정자 노드가 파티션 키·값·일관성 수준을 수신함
2. **복제본 선택**: 토큰 범위와 복제 계수로 쓰기를 전달할 노드를 결정함
3. **로그·메모리 기록**: 각 복제본이 Commit Log와 Memtable에 변경을 반영함
4. **일관성 확인**: 지정한 쓰기 수준을 충족한 복제본 수가 응답하면 완료를 반환함
5. **디스크 정리**: Memtable을 SSTable로 Flush하고 Compaction으로 파일·Tombstone을 병합함

> 요약: Cassandra는 파티션 복제본의 로그·메모리에 쓰고 지정한 복제본 수가 확인하면 완료한 뒤 SSTable을 병합함.

## Ⅵ. 실무 사례

1. 로그 적재 플랫폼은 시간 버킷을 포함한 파티션 키를 적용하고 최대 파티션 크기·p99 쓰기 지연을 확인함
2. 다중 리전 이벤트 저장소는 LOCAL_QUORUM과 정기 복구를 적용하고 최신 값 미반영 조회율·복구 적체량을 확인함

## Ⅶ. 결론

- Cassandra는 접근 패턴·파티션 크기·복제 계수·일관성 수준과 복구 비용을 기준으로 적용해야 함
