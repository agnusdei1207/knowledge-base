## 미리 알고가기

- 컬럼 패밀리 DB는 행과 컬럼 개념을 쓰지만 실제 저장과 접근은 분산 키-값에 가까운 NoSQL 계열임
- 파티션 키는 데이터를 어느 노드에 둘지 정하고 클러스터링 키는 파티션 안의 정렬 순서를 정함
- 일관성 수준은 읽기와 쓰기마다 얼마나 많은 복제본 확인을 요구할지 정하는 옵션임

## Ⅰ. 개요

- **정의/개념**: Cassandra는 분산 환경에서 대량 쓰기와 높은 가용성을 우선하도록 설계된 컬럼 패밀리 기반 NoSQL 데이터베이스로, 파티션 키 중심 접근과 복제 분산을 특징으로 함
- **배경/필요성**: 여러 지역의 쓰기와 노드 장애를 처리하려면 파티션 키 기반 분산, 복제 계수, quorum 일관성 수준을 조정할 수 있는 저장 구조가 필요함

## Ⅱ. 특징

- 여러 노드가 대등하게 동작해 특정 마스터 장애점이 없음
- 쓰기는 commit log와 memtable에 기록된 뒤 SSTable로 flush되고 compaction으로 병합됨
- 파티션 키의 token으로 데이터를 노드에 분산하고 복제 계수만큼 여러 노드에 저장함
- 쿼리 자유도가 낮아 설계 초기에 접근 패턴을 잘못 잡으면 구조를 다시 바꾸기 어려움

## Ⅲ. 종류 및 비교

| 판단 기준 | 관계형 DB | Cassandra |
|:---|:---|:---|
| 정합성 중심 | 강한 트랜잭션과 조인에 강함 | 가용성과 분산 쓰기에 강함 |
| 질의 방식 | SQL 조건·조인·집계 | partition key와 clustering column 중심 조회 |
| 확장 방식 | 단일 인스턴스 확장·복제·별도 sharding | token range를 신규 노드에 재분배 |
| 주의점 | 대규모 분산 쓰기 부담이 큼 | 모델링 실패 시 조회 제약이 큼 |

## Ⅳ. 구성요소 및 구조

| 구성요소 | 설명 |
|:---|:---|
| Node / Ring | 여러 노드가 링 구조로 데이터를 분산 보관함 |
| Partition Key | 어떤 노드에 데이터를 둘지 정하는 핵심 키임 |
| Clustering Columns | 같은 파티션 안에서 정렬 순서와 범위 조회를 정함 |
| Commit Log / Memtable / SSTable | 쓰기 내구성과 메모리 적재와 디스크 저장을 담당함 |
| Replication / Consistency Level | 복제본 수와 읽기·쓰기 확인 수준을 조정함 |

```text
클라이언트 -> Partition Key 계산 -> 여러 노드 분산 저장
                           |
            Commit Log -> Memtable -> SSTable
```

## Ⅴ. 원리 및 절차 흐름도

```text
데이터 모델링 -> 파티션 키 결정 -> 쓰기 적재 -> SSTable 병합 -> 읽기/복구
```

1. **데이터 모델링**: 조회 패턴에 맞춰 파티션 키와 컬럼 구성을 정함
2. **쓰기 적재**: Commit Log와 Memtable에 먼저 기록함
3. **디스크 저장**: 메모리 데이터가 SSTable로 내려감
4. **병합 정리**: Compaction으로 여러 SSTable을 정리함
5. **읽기와 복구**: 필요한 복제본에서 읽고 수선 작업을 수행함

## Ⅵ. 실무 적용 및 유의점

1. 로그 수집과 IoT 적재처럼 쓰기 부하가 큰 서비스는 Cassandra가 잘 맞지만 파티션 키가 한쪽으로 몰리면 특정 노드만 과열되므로 파티션 분포와 핫파티션 비율과 쓰기 지연시간으로 확인함
2. 여러 지역 복제를 쓰는 환경은 가용성은 높아도 읽기 일관성이 흔들릴 수 있으므로 일관성 수준과 복구 정책을 함께 정하고 오래된 읽기 건수와 복구 지연 시간과 노드 불균형 정도로 확인함

## Ⅶ. 결론

- Cassandra는 대량 분산 쓰기와 고가용성에 강하지만 파티션 키와 일관성 수준을 업무 패턴에 맞게 설계해야 장점이 살아남음
