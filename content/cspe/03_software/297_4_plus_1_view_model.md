# 📖 【암기용】 개념 완전 이해

> 목적: 4+1 뷰 모델을 처음 보는 사람도 개념과 내부 용어를 완전히 이해하게 만든다. 시험 답안 양식이 아니라, 이해를 위한 친절한 설명이다.

## 한눈에
- **개요**: 4+1 뷰 모델은 **소프트웨어 아키텍처 기술(記述) 방법론**의 하나로, 하나의 시스템을 이해관계자별 4개의 독립된 구조 뷰(논리·개발·프로세스·물리)와, 그 넷을 하나로 묶어 검증하는 유스케이스 시나리오(+1)로 나누어 표현한다.
- **왜 필요한가**: 클래스 다이어그램 하나만으로는 기능(무엇을 하는가), 코드 구조(어떻게 나뉘는가), 동시성(런타임에 어떻게 돌아가는가), 배포(어느 서버에 올라가는가)를 동시에 담을 수 없다. 이해관계자마다 필요한 정보가 다르기 때문에, 하나의 다이어그램을 억지로 겸용하면 누구에게도 충분하지 않다.
- **핵심 직관**: 건물 설계를 평면도(기능 배치)·배선도(내부 구조)·공정표(시공 진행)·배치도(대지 위 위치)로 나눠 그리고, 마지막에 "사용자가 문을 열고 들어가 화장실까지 가는 동선"으로 넷이 앞뒤가 맞는지 확인하는 것과 같다.

## 핵심 용어 정리 (내부에 등장하는 것들)

| 용어 | 의미 | 비유 |
|:---|:---|:---|
| 다중 관점 아키텍처 기술 | 하나의 시스템을 여러 독립된 뷰로 나눠 기술하는 상위 방법론 | 4+1이 속한 큰 범주 |
| Logical View(논리 뷰) | 시스템이 사용자에게 제공하는 기능과 도메인 객체·관계 — UML 클래스·상태 다이어그램으로 표현 | 최종 사용자·분석가가 보는 "무엇을 하는가" |
| Development View(개발 뷰) | 소스 코드가 모듈·패키지·레이어로 어떻게 조직되는지 — UML 컴포넌트·패키지 다이어그램 | 개발자·형상관리자가 보는 "코드가 어떻게 나뉘는가" |
| Process View(프로세스 뷰) | 런타임에 프로세스·스레드가 어떻게 동시에 실행되고 통신하는지 — UML 액티비티·시퀀스 다이어그램 | 성능·가용성 담당자가 보는 "실행 중 무슨 일이 벌어지는가" |
| Physical View(물리 뷰, 배포 뷰) | 소프트웨어 요소가 어떤 서버·네트워크 노드에 배치되는지 — UML 배포 다이어그램 | 운영자·네트워크 담당자가 보는 "어디서 도는가" |
| Scenario(+1 뷰) | 대표 유스케이스로 위 4개 뷰를 하나로 관통시켜 일관성을 검증 | 네 도면이 실제로 맞물리는지 확인하는 준공 점검 |

## 깊이 이해

### 왜 "4+1"인가 — +1이 별도 뷰가 아닌 이유
- Philippe Kruchten이 1995년 IEEE Software에 발표한 논문 "Architectural Blueprints — The '4+1' View Model of Software Architecture"에서 제안했다.
- +1(Scenario)은 다섯 번째로 독립된 구조 뷰가 아니라, **앞의 네 뷰가 서로 모순 없이 맞물리는지 검증하는 도구**다. 그래서 이름이 "5개 뷰"가 아니라 "4+1"이다 — 4개는 구조를 그리고, +1은 그 구조가 실제로 동작함을 대표 시나리오로 확인한다.
- 검증 방식: 하나의 유스케이스(예: "고객이 주문을 결제한다")를 골라, 그 흐름이 논리 뷰의 어떤 객체를 거쳐(Order, Payment 객체), 개발 뷰의 어떤 모듈을 통해(order-service, payment-service 패키지), 프로세스 뷰의 어떤 스레드·메시지로(Kafka consumer thread), 물리 뷰의 어떤 노드에서(Kubernetes pod) 실행되는지 끝까지 추적한다. 이 추적이 끊기지 않고 완결되면 네 뷰가 일관된 것이다.

### 4개 뷰를 구체 사례(온라인 주문)로 끝까지 추적하기
- **논리 뷰**: `Order`(주문 상태를 가진 도메인 객체)가 `Payment`를 참조하고, `Order.confirm()` 호출 시 상태가 `PENDING → CONFIRMED`로 바뀌는 클래스·상태 다이어그램으로 표현한다.
- **개발 뷰**: 이 로직은 `order-service`라는 별도 패키지(모듈)에 있고, `payment-service`는 별도 패키지로 분리돼 있어 두 패키지 간 의존 방향(order → payment API 호출)이 컴포넌트 다이어그램에 드러난다.
- **프로세스 뷰**: 런타임에는 `order-service`가 결제 완료 이벤트를 Kafka 토픽에 발행하고, `payment-service`의 별도 컨슈머 스레드가 이를 비동기로 소비한다 — 이 비동기·동시성 구조는 논리 뷰의 클래스 다이어그램만 봐서는 전혀 드러나지 않는다.
- **물리 뷰**: `order-service`와 `payment-service`는 서로 다른 Kubernetes 파드로 배포되고, 파드 간 통신은 클러스터 내부 네트워크를 거친다 — 물리 뷰가 없으면 "네트워크 장애 시 어디가 끊기는가"를 답할 수 없다.
- **+1 시나리오**: "결제 중 payment-service 파드가 죽으면?"이라는 장애 시나리오로 네 뷰를 다시 훑으면, 프로세스 뷰의 Kafka는 메시지를 재시도 큐에 보관하고, 물리 뷰의 replica가 재시작되며, 논리 뷰의 `Order` 상태는 `PENDING`으로 유지된다는 것이 사슬처럼 확인된다. 이 확인이 없으면 네 다이어그램은 그냥 따로 그린 그림일 뿐이다.

### 뷰와 UML 다이어그램의 대응, 그리고 왜 4개나 필요한가
- 각 뷰는 특정 UML 다이어그램 유형과 자연스럽게 짝지어진다: 논리 뷰 ↔ 클래스·상태 다이어그램, 개발 뷰 ↔ 컴포넌트·패키지 다이어그램, 프로세스 뷰 ↔ 액티비티·시퀀스 다이어그램, 물리 뷰 ↔ 배포 다이어그램. 이 대응 때문에 4+1은 "UML을 이해관계자 관점별로 배치하는 틀"로도 이해된다.
- 왜 하나로 합치면 안 되나: 클래스 다이어그램(논리)에 서버 배치(물리)까지 욱여넣으면, 기능을 보고 싶은 기획자는 서버 아이콘에 압도되고, 배포를 보고 싶은 운영자는 클래스 상속 관계에 압도된다. 관심사별로 분리해야 각 독자가 필요한 정보만 빠르게 얻는다.

### 비유와 흔한 오해
- **비유**: 병원 시스템을 설계할 때 의사는 진료 흐름(논리), 개발자는 모듈 구조(개발), 시스템 엔지니어는 동시 접속·큐 처리(프로세스), 인프라 담당자는 서버·네트워크 배치(물리)를 각각 보고 싶어 하는 것을 하나의 체계로 담은 것이다.
- **오해 1**: "4개 다이어그램을 항상 다 그려야 한다"가 아니다. 소규모 CRUD 시스템처럼 동시성·배포가 단순하면 프로세스·물리 뷰는 간략화하거나 생략할 수 있다 — 이해관계자 질문에 답하는 데 필요한 뷰만 고른다.
- **오해 2**: 4+1은 C4 모델(Context-Container-Component-Code)과 혼동되기 쉬운데, C4는 "하나의 관점(구조)을 확대 배율로 쪼개는" 방식이고, 4+1은 "관심사(기능·코드·동시성·배포) 자체를 나누는" 방식이라는 점에서 분류 축이 다르다.

## 연결 개념
- UML — 각 뷰를 실제로 그릴 때 쓰는 표기법(클래스·컴포넌트·시퀀스·배포 다이어그램)
- ATAM — 품질속성 시나리오로 아키텍처를 평가하는 기법, 4+1의 Scenario(+1)와 같은 "시나리오 기반 검증" 철학을 공유
- C4 Model — Context·Container·Component·Code로 확대 배율을 나누는 대안적 다중 관점 모델

# 📝 【답안용】 시험 답안 템플릿

> 목적: 시험장에서 25분에 그대로 쓰는 답안 양식. 뷰 명칭보다 이해관계자 관심사와 품질속성 검증을 연결한다.

## 핵심 인사이트 (3줄 요약)

> 1. **본질**: 4+1 뷰는 소프트웨어 아키텍처를 이해관계자 관심사별 4개 구조 뷰와 시나리오로 설명하는 모델이다.
> 2. **가치**: 기능, 모듈, 동시성, 배포 구조를 분리해 변경 영향과 품질속성을 검증한다.
> 3. **판단 포인트**: +1 시나리오가 네 뷰의 일관성을 검증하므로 유스케이스 없이 뷰만 나열하면 답안 가치가 낮다.

## 출제 의도 및 답안 포인트

| 출제 의도 | 반드시 짚을 핵심 | 감점 회피 포인트 |
|:---|:---|:---|
| 아키텍처 표현 관점 이해 확인 | Logical, Development, Process, Physical, Scenario | 뷰 이름만 나열 |
| 이해관계자별 설계 판단 확인 | 사용자, 개발자, 운영자, 성능 담당 관심사 | UML 다이어그램 종류와 혼동 |
| 품질속성 검증 확인 | 성능, 가용성, 배포, 변경 영향 | +1 시나리오 누락 |

> 요약: 이 문제는 다이어그램 암기가 아니라 관점별 설계 근거와 시나리오 검증을 요구한다.

## Ⅰ. 개요 및 필요성

- 개요: 4+1 뷰 모델은 아키텍처를 4개 뷰와 시나리오로 설명하는 방법이다.
- 배경: 단일 모델은 기능, 코드 구조, 동시성, 배포 환경을 동시에 표현하기 어렵다.
- 필요성: 이해관계자별 관심사를 분리하고 시나리오로 뷰 간 일관성을 검증해야 한다.

---

## Ⅱ. 구조 및 구성요소

```text
Use Case Scenario
  / Logical View -> 기능·도메인 구조
  / Development View -> 모듈·패키지 구조
  / Process View -> 동시성·통신 구조
  / Physical View -> 노드·배포 구조
```

| 구성요소 | 역할 | 특이사항 |
|:---|:---|:---|
| Logical View | 주요 기능·객체·도메인 관계 | 사용자·분석가 관점 |
| Development View | 모듈·패키지·컴포넌트 구조 | 개발자·형상관리 관점 |
| Process View | 프로세스·스레드·IPC·동시성 | 성능·가용성 관점 |
| Physical View | 서버·네트워크·배포 노드 | 운영자·인프라 관점 |
| Scenario | 유스케이스로 뷰 일관성 검증 | +1, 품질속성 확인 |

> 요약: 4+1 뷰는 기능, 코드, 런타임, 배포를 분리하고 시나리오로 연결해 아키텍처를 검증한다.

---

## Ⅲ. 동작원리 및 흐름도

```text
품질 요구 식별 -> 시나리오 선정 -> 4개 뷰 작성 -> 뷰 간 추적성 확인 -> 리스크 보완
```

| 단계 | 처리 내용 | 검증 기준 |
|:---:|:---|:---|
| 1 | 주요 이해관계자와 품질속성 식별 | 성능·가용성·변경성 목록 |
| 2 | 핵심 유스케이스와 장애 시나리오 선정 | 상위 5개 시나리오 |
| 3 | 4개 뷰별 구조 모델 작성 | 뷰별 책임 중복 최소화 |
| 4 | 시나리오로 뷰 간 추적성 검증 | 요구사항 추적률 100% |

> 요약: 동작은 요구 식별, 시나리오 선정, 뷰 작성, 추적성 검증 순서로 설계 누락을 줄인다.

## Ⅳ. 특징

| 구분 | 단일 다이어그램 | 4+1 뷰 | 수치·판단 기준 |
|:---|:---|:---|:---|
| 표현 범위 | 한 관점 중심 | 기능·개발·런타임·배포 분리 | 이해관계자 4그룹 이상 |
| 검증 | 문서 리뷰 중심 | 시나리오 기반 일관성 확인 | 주요 시나리오 5개 이상 |
| 변경 영향 | 추적 어려움 | 뷰 간 매핑으로 분석 | 요구 추적률 100% |
| 한계 | 작성 부담 낮음 | 문서 최신성 관리 필요 | 릴리스마다 업데이트 |

> 요약: 4+1 뷰는 복잡한 시스템의 관점 분리를 제공하지만, 시나리오와 추적성 없이는 문서 부담만 증가한다.

## Ⅴ. 심화 비교 및 적용 판단

| 비교 축 | 기존/대안 | 본 키워드 | 선택 기준 |
|:---|:---|:---|:---|
| 구조 | UML 단일 모델 | 4개 뷰 + 시나리오 | 대규모·다중 이해관계자 프로젝트 |
| 비용/성능 | 문서 작성 적음 | 뷰별 산출물 필요 | 변경 영향 분석 빈도 높음 |
| 운영/위험 | 운영 배포 누락 | 물리·프로세스 뷰 포함 | 가용성·성능 요구 명확 |

> 요약: 이해관계자와 품질속성이 많은 시스템은 단일 모델보다 4+1 뷰가 설계 근거를 분명히 한다.

| 리스크 | 원인 | 대응 방안 | 확인 지표 |
|:---|:---|:---|:---|
| 문서 불일치 | 뷰별 별도 관리 | ADR, 모델 저장소, 리뷰 gate | 불일치 결함 건수 |
| 과도한 모델링 | 모든 세부 클래스 표현 | 핵심 시나리오 중심 작성 | 다이어그램 수 제한 |
| 품질속성 누락 | 기능 중심 작성 | ATAM 시나리오 병행 | 품질 요구 추적률 |

> 요약: 문서 불일치와 과도한 모델링은 시나리오 중심 범위 지정과 리뷰 게이트로 통제한다.

| 점검 항목 | 목표 기준 | 측정 방법 |
|:---|:---|:---|
| 추적성 | 주요 요구사항 100% 매핑 | traceability matrix |
| 최신성 | 릴리스 변경 반영 100% | architecture review |

## Ⅵ. 실무 적용 및 결론

**적용 방안 3개 (필수 - 단계별 또는 항목별):**
