## 핵심 인사이트 (3줄 요약)
- 63빌딩을 지을 때 배관공에게 주는 도면, 전기기사에게 주는 도면, 인테리어 업자에게 주는 도면이 다 다름. 소프트웨어도 마찬가지임!
- **4+1 뷰**는 하나의 복잡한 소프트웨어 아키텍처를 **고객(기획자), 프로그래머, 시스템 통합자, 엔지니어라는 4가지 서로 다른 사람들의 시선(View)**으로 나눠서 그리고, 마지막으로 이 모든 뷰를 하나로 관통하는 **유스케이스(시나리오)**로 검증하는 표준 도면 그리기 기법임.
- 각자의 관심사(Concern)가 섞여서 혼란스러워지는 것을 막고, 서로 다른 이해관계자들이 자기 역할에 맞는 도면만 보고 완벽하게 의사소통할 수 있게 해주는 설계의 기본 뼈대임.
---
## Ⅰ. 개요 및 필요성
- **개요**: 1995년 필립 크루첸(Philippe Kruchten)이 제안한 모델로, 소프트웨어 아키텍처를 논리적, 프로세스, 구현, 배포의 4가지 관점으로 기술하고, 이를 유스케이스(시나리오)로 엮어 통합 검증하는 다중 관점(Multi-View) 아키텍처 프레임워크.
- **필요성**: 개발자가 클래스 다이어그램 하나 덜렁 그려옴. 기획자는 "이거 서버 10대에서 잘 도는 거 맞아요?" 물어봄. 인프라팀은 "이거 배포할 땐 폴더 구조 어떻게 돼요?" 물어봄. 다이어그램 하나로는 이 모든 질문에 답할 수 없음. **"아니, 보는 사람 직업(관심사)에 따라서 맞춤형 도면을 4개로 쪼개서 그려주고, 이 4개가 제대로 맞물려 돌아가는지 '사용자 스토리'로 검사해보면 안 돼?"**
---
## Ⅱ. 핵심 아키텍처 (4대 뷰 + 1 검증)

### [4개의 기본 도면 (관점)]
- **1. 논리 뷰 (Logical View) - "설계자/개발자"**
  - **관심사**: 시스템의 기능적 요구사항(로직). "무슨 클래스가 있고 어떻게 상호작용하지?"
  - **산출물**: 클래스 다이어그램, 상태 다이어그램.
- **2. 프로세스 뷰 (Process View) - "시스템 통합자"**
  - **관심사**: 비기능적 요구사항(동시성, 성능, 스레드). "트래픽이 몰릴 때 스레드와 통신이 안 죽고 잘 돌아가나?"
  - **산출물**: 시퀀스 다이어그램, 활동 다이어그램.
- **3. 구현 뷰 (Implementation / Development View) - "프로그래머/빌드 매니저"**
  - **관심사**: 실제 소스코드와 파일의 물리적 구조. "패키지 폴더 구성은 어떻게 되고, 라이브러리 관리는 어떻게 하지?"
  - **산출물**: 컴포넌트 다이어그램, 패키지 다이어그램.
- **4. 배포 뷰 (Deployment / Physical View) - "네트워크 엔지니어/운영자"**
  - **관심사**: 하드웨어, 네트워크, 서버 토폴로지. "어느 클라우드 서버, 어느 DB 장비에 이 소프트웨어를 설치할까?"
  - **산출물**: 배포 다이어그램.

### [+1 : 이 모든 걸 묶는 접착제]
- **+1. 유스케이스 뷰 (Use Case / Scenario View) - "모든 이해관계자"**
  - **관심사**: 아키텍처 검증. "사용자가 결제 버튼을 누르면 이 4개의 도면이 제대로 맞물려서 움직이는가?"
  - **산출물**: 유스케이스 다이어그램. (나머지 4개 뷰를 도출하고 검증하는 핵심 동인).

```text
[ 4+1 뷰의 구조도 ]

       (논리 뷰) ---------- (프로세스 뷰)
           \                    /
            \                  /
             +--[ +1 유스케이스 뷰 ]--+
            /                  \
           /                    \
     (구현 뷰) -------------- (배포 뷰)
```

## Ⅲ. 오해와 진실
| 오해 | 진실 |
|---|---|
| "무조건 5개(4+1)의 도면을 다 그려야 하나요?" | **아님.** 작은 단일 서버(모놀리틱) 프로젝트라면 네트워크 복잡도가 없으므로 배포 뷰를 생략하거나 가볍게 그릴 수 있음. 프로젝트의 규모와 특성에 맞게 필요한 뷰만 테일러링(Tailoring)해서 쓰는 것이 실무의 정석임. |
| "4+1 뷰는 UML로만 그려야 하나요?" | 필립 크루첸이 UML의 발전에 기여하긴 했지만, 4+1 뷰 사상 자체는 특정 표기법(UML)에 종속되지 않음. 최근엔 아키텍처를 코드로 그리는 C4 모델이나 다이어그램 툴(Draw.io 등)을 자유롭게 섞어 쓰며 사상만 유지함. |
---
## Ⅳ. 실무 적용 및 기술사 판단
- **MSA(마이크로서비스) 환경에서의 다중 관점 적용**: 기술사는 복잡한 MSA를 설계할 때 4+1 뷰를 적극 차용해야 함. 예를 들어, 서비스 분할 전략은 '논리 뷰'에서 도메인 주도 설계(DDD)를 통해 정의하고, 컨테이너 간의 gRPC/API 통신과 서킷 브레이커 전략은 '프로세스 뷰'에서 정의하며, 쿠버네티스 노드 배치는 '배포 뷰'에서 정의하여 **설계의 사각지대(누락)**를 원천 차단해야 함.
- **최신 대안 프레임워크와의 융합 (C4 Model)**: 4+1 뷰가 다소 낡고 추상적이라는 비판에 따라, 최근엔 줌-인(Zoom-in) 방식의 직관적인 **C4 모델(Context ➡️ Container ➡️ Component ➡️ Code)**이 유행함. 기술사는 4+1 뷰의 철저한 '이해관계자 분리 철학'은 유지하되, 표현 방식은 애자일 환경에 맞는 C4 모델이나 구조화된 ADR(아키텍처 결정 기록) 문서로 대체하여 실용성을 높여야 함.
---
## Ⅴ. 기대효과 및 결론
- 개발자, 기획자, 운영자가 각자 다른 소리를 하며 싸우는 바벨탑의 비극을 막고, **이해관계자별 맞춤형 소통(Separation of Concerns)**을 가능케 함.
- "기능은 잘 돌아가는데 1만 명이 접속하니 뻗어버렸다(비기능적 요구사항 누락)" 같은 대형 설계 사고를, 프로세스 뷰와 배포 뷰를 통해 사전에 완벽히 식별하고 방어할 수 있는 건축 도면의 바이블임.

### 📌 관련 개념 맵
- Software Architecture ➡️ View / Viewpoint ➡️ 4+1 View Model ➡️ UML (Unified Modeling Language) ➡️ C4 Model / ADR

### 📈 관련 키워드 및 발전 흐름도
- 주먹구구식 개발 (도면 없이 집 짓기) ➡️ 시스템이 거대해지면서 다양한 관점의 도면 필요성 대두 ➡️ 1995년 필립 크루첸이 RUP(Rational Unified Process)의 일환으로 **4+1 View Model** 제안 ➡️ 이를 시각화하기 위한 표준 언어로 UML 등장 ➡️ 현대에 이르러 너무 복잡한 UML 4+1뷰 대신, 직관성을 극대화한 **C4 Model**이나 애자일 아키텍처 문서화로 단순하게 진화 중 (현재)

### 👶 어린이를 위한 3줄 비유 설명
1. 거대한 자동차를 만들 때, "엔진 도면"만 가지고는 시트 색깔이나 바퀴 크기를 알 수 없어요.
2. **4+1 뷰**는 자동차를 "1. 전기 배선(엔지니어), 2. 부품 구조(조립가), 3. 디자인(고객), 4. 생산 라인(공장장)"이라는 **4가지 다른 안경**을 끼고 도면을 나눠 그리는 거예요.
3. 그리고 마지막 **+1(유스케이스)**은 "운전자가 시동을 걸고 앞으로 간다!"라는 테스트 시나리오로, 저 4개의 도면이 제대로 만들어졌는지 마지막으로 확인하는 마법의 접착제랍니다!

### 🔀 문제 유형별 목차 전환 (이 키워드 출제 시)
- **개념/도식형 (Ⅱ·Ⅲ 강조)**: 4+1 뷰의 구조 도식화. 논리, 프로세스, 구현, 배포 뷰의 각각의 주요 이해관계자(Stakeholder)와 매핑되는 UML 산출물(클래스, 시퀀스, 컴포넌트, 배포 다이어그램) 설명. 유스케이스 뷰(+1)의 검증(Validation) 역할 강조.
- **아키텍처 비교/적용형 (Ⅳ·Ⅴ 강조)**: 최신 소프트웨어 아키텍처 문서화 트렌드인 C4 모델과의 철학적 공통점 및 직관성 차이 비교. 마이크로서비스(MSA) 및 클라우드 네이티브 설계 시 각 뷰를 어떻게 활용하여 비기능적 요구사항을 만족시킬 것인지 실무 적용 전략 제시.
