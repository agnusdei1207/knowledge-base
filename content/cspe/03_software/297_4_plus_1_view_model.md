# 📖 【암기용】 개념 완전 이해

> 목적: 4+1 뷰 모델을 처음 봐도 완전히 이해하게 만든다. 시험 답안 양식이 아니라, 이해를 위한 설명이다.

## 한눈에
- **개요**: 소프트웨어 아키텍처를 논리, 개발, 프로세스, 물리 뷰와 시나리오로 나누어 설명하는 모델
- **왜 필요한가**: 이해관계자마다 관심사가 달라 하나의 다이어그램으로 기능, 코드 구조, 동시성, 배포를 모두 설명하기 어렵다.
- **핵심 직관**: 건물을 평면도, 배선도, 공정표, 배치도, 사용 시나리오로 나눠 보는 것과 같다.

## 깊이 이해
- **배경·문제의식**: 아키텍처 문서가 클래스도 하나로 끝나면 운영자는 배포 구조를 모르고, 개발자는 모듈 책임을 모르며, 고객은 기능 흐름을 확인하기 어렵다.
- **작동 원리**: 논리 뷰는 주요 기능과 도메인 객체, 개발 뷰는 모듈·패키지, 프로세스 뷰는 런타임 스레드·프로세스, 물리 뷰는 노드 배치를 나타낸다. +1 시나리오가 네 뷰를 검증한다.
- **비유**: 병원 시스템을 의사는 진료 흐름, 개발자는 모듈, 운영자는 서버 배치, 보안 담당자는 통신 경로로 보는 차이를 한 체계에 담는다.
- **구체 예시**: 온라인 주문은 논리 뷰에서 주문·결제 객체, 개발 뷰에서 order-service 패키지, 프로세스 뷰에서 Kafka 소비자, 물리 뷰에서 Kubernetes pod 배치로 표현된다.
- **흔한 오해·주의점**: 4개 다이어그램을 모두 그리는 것이 목적이 아니다. 이해관계자 질문에 답하는 뷰를 선택하고 시나리오로 일관성을 검증해야 한다.

## 연결 개념
- UML - 클래스·컴포넌트·배포 다이어그램 표현 수단
- ATAM - 품질속성 기반 아키텍처 평가
- C4 Model - Context, Container, Component, Code 관점 모델

# 📝 【답안용】 시험 답안 템플릿

> 목적: 시험장에서 25분에 그대로 쓰는 답안 양식. 뷰 명칭보다 이해관계자 관심사와 품질속성 검증을 연결한다.

## 핵심 인사이트 (3줄 요약)

> 1. **본질**: 4+1 뷰는 소프트웨어 아키텍처를 이해관계자 관심사별 4개 구조 뷰와 시나리오로 설명하는 모델이다.
> 2. **가치**: 기능, 모듈, 동시성, 배포 구조를 분리해 변경 영향과 품질속성을 검증한다.
> 3. **판단 포인트**: +1 시나리오가 네 뷰의 일관성을 검증하므로 유스케이스 없이 뷰만 나열하면 답안 가치가 낮다.

## 출제 의도 및 답안 포인트

| 출제 의도 | 반드시 짚을 핵심 | 감점 회피 포인트 |
|:---|:---|:---|
| 아키텍처 표현 관점 이해 확인 | Logical, Development, Process, Physical, Scenario | 뷰 이름만 나열 |
| 이해관계자별 설계 판단 확인 | 사용자, 개발자, 운영자, 성능 담당 관심사 | UML 다이어그램 종류와 혼동 |
| 품질속성 검증 확인 | 성능, 가용성, 배포, 변경 영향 | +1 시나리오 누락 |

> 요약: 이 문제는 다이어그램 암기가 아니라 관점별 설계 근거와 시나리오 검증을 요구한다.

---

## Ⅰ. 개요 및 필요성

- 개요: 4+1 뷰 모델은 아키텍처를 4개 뷰와 시나리오로 설명하는 방법이다.
- 배경: 단일 모델은 기능, 코드 구조, 동시성, 배포 환경을 동시에 표현하기 어렵다.
- 필요성: 이해관계자별 관심사를 분리하고 시나리오로 뷰 간 일관성을 검증해야 한다.

---

## Ⅱ. 구조 및 구성요소

```text
Use Case Scenario
  / Logical View -> 기능·도메인 구조
  / Development View -> 모듈·패키지 구조
  / Process View -> 동시성·통신 구조
  / Physical View -> 노드·배포 구조
```

| 구성요소 | 역할 | 특이사항 |
|:---|:---|:---|
| Logical View | 주요 기능·객체·도메인 관계 | 사용자·분석가 관점 |
| Development View | 모듈·패키지·컴포넌트 구조 | 개발자·형상관리 관점 |
| Process View | 프로세스·스레드·IPC·동시성 | 성능·가용성 관점 |
| Physical View | 서버·네트워크·배포 노드 | 운영자·인프라 관점 |
| Scenario | 유스케이스로 뷰 일관성 검증 | +1, 품질속성 확인 |

> 요약: 4+1 뷰는 기능, 코드, 런타임, 배포를 분리하고 시나리오로 연결해 아키텍처를 검증한다.

---

## Ⅲ. 동작원리 및 흐름도

```text
품질 요구 식별 -> 시나리오 선정 -> 4개 뷰 작성 -> 뷰 간 추적성 확인 -> 리스크 보완
```

| 단계 | 처리 내용 | 검증 기준 |
|:---:|:---|:---|
| 1 | 주요 이해관계자와 품질속성 식별 | 성능·가용성·변경성 목록 |
| 2 | 핵심 유스케이스와 장애 시나리오 선정 | 상위 5개 시나리오 |
| 3 | 4개 뷰별 구조 모델 작성 | 뷰별 책임 중복 최소화 |
| 4 | 시나리오로 뷰 간 추적성 검증 | 요구사항 추적률 100% |

> 요약: 동작은 요구 식별, 시나리오 선정, 뷰 작성, 추적성 검증 순서로 설계 누락을 줄인다.

## Ⅳ. 특징

| 구분 | 단일 다이어그램 | 4+1 뷰 | 수치·판단 기준 |
|:---|:---|:---|:---|
| 표현 범위 | 한 관점 중심 | 기능·개발·런타임·배포 분리 | 이해관계자 4그룹 이상 |
| 검증 | 문서 리뷰 중심 | 시나리오 기반 일관성 확인 | 주요 시나리오 5개 이상 |
| 변경 영향 | 추적 어려움 | 뷰 간 매핑으로 분석 | 요구 추적률 100% |
| 한계 | 작성 부담 낮음 | 문서 최신성 관리 필요 | 릴리스마다 업데이트 |

> 요약: 4+1 뷰는 복잡한 시스템의 관점 분리를 제공하지만, 시나리오와 추적성 없이는 문서 부담만 증가한다.

## Ⅴ. 심화 비교 및 적용 판단

| 비교 축 | 기존/대안 | 본 키워드 | 선택 기준 |
|:---|:---|:---|:---|
| 구조 | UML 단일 모델 | 4개 뷰 + 시나리오 | 대규모·다중 이해관계자 프로젝트 |
| 비용/성능 | 문서 작성 적음 | 뷰별 산출물 필요 | 변경 영향 분석 빈도 높음 |
| 운영/위험 | 운영 배포 누락 | 물리·프로세스 뷰 포함 | 가용성·성능 요구 명확 |

> 요약: 이해관계자와 품질속성이 많은 시스템은 단일 모델보다 4+1 뷰가 설계 근거를 분명히 한다.

| 리스크 | 원인 | 대응 방안 | 확인 지표 |
|:---|:---|:---|:---|
| 문서 불일치 | 뷰별 별도 관리 | ADR, 모델 저장소, 리뷰 gate | 불일치 결함 건수 |
| 과도한 모델링 | 모든 세부 클래스 표현 | 핵심 시나리오 중심 작성 | 다이어그램 수 제한 |
| 품질속성 누락 | 기능 중심 작성 | ATAM 시나리오 병행 | 품질 요구 추적률 |

> 요약: 문서 불일치와 과도한 모델링은 시나리오 중심 범위 지정과 리뷰 게이트로 통제한다.

| 점검 항목 | 목표 기준 | 측정 방법 |
|:---|:---|:---|
| 추적성 | 주요 요구사항 100% 매핑 | traceability matrix |
| 최신성 | 릴리스 변경 반영 100% | architecture review |
| 품질 검증 | 주요 시나리오 5개 이상 | ATAM workshop |

> 요약: 성공 여부는 요구 추적성, 문서 최신성, 품질 시나리오 검증 수로 판단한다.

## Ⅵ. 실무 적용 및 결론

**적용 방안 3개 (필수 - 단계별 또는 항목별):**
1. 결제, 주문, 장애 복구 등 상위 5개 시나리오를 먼저 선정하고 4개 뷰의 추적성 기준으로 사용
2. Logical은 도메인 모델, Development는 모듈·API, Process는 비동기·동시성, Physical은 Kubernetes·DB 배치로 산출물 분리
3. ADR과 CI 문서 lint를 적용해 릴리스마다 변경된 서비스·노드·의존성을 뷰에 반영

**결론 (2줄):**
- 기술사 판단: 이해관계자가 많고 품질속성 충돌이 있는 시스템은 4+1 뷰를 적용하고, 소규모 CRUD는 C4 Context·Container 수준으로 축소
- 향후 방향: 모델 문서와 코드·IaC를 연결해 architecture as code 형태로 최신성 검증을 자동화해야 함
