## Ⅰ. 개요
- **정의**: 소스에서 목적지까지 데이터의 수집·변환·적재를 자동화된 흐름으로 연결하는 아키텍처임
- **배경/필요성**: 데이터 소스가 다양해지고 분석 주기가 짧아지며 수작업 데이터 이동의 한계가 드러남
- **비유**: 원유를 정제소까지 운반하는 송유관처럼, 원시 데이터를 분석 가능한 형태로 운반하는 관로임

| 출제 의도 | 반드시 짚을 핵심 | 감점 회피 포인트 |
|:---|:---|:---|
| 파이프라인 아키텍처 설계 역량 확인 | 단계별 역할과 오류 처리 메커니즘 | ETL/ELT(141 참조)와의 관계를 혼동하지 않음 |

> 요약: 데이터 흐름을 자동화·표준화하여 분석 적시성을 확보하는 구조임

## Ⅱ. 구성요소
```text
[Ingestion] --> [Staging] --> [Transform] --> [Serving] --> [Monitoring]
```

| 구성요소 | 설명 | 비유 |
|:---|:---|:---|
| Ingestion | 다양한 소스에서 데이터를 수집하는 입구 계층 | 수도관 취수구 |
| Staging | 원시 데이터를 임시 저장하여 검증 대기하는 버퍼 영역 | 정수장 침전지 |
| Transform | 정제·집계·조인 등 비즈니스 로직을 적용하는 처리 계층 | 정수 필터 |
| Serving | 분석·BI·API 등 소비자에게 결과를 제공하는 계층 | 수도꼭지 |
| Monitoring | 지연·실패·데이터 품질을 감시하는 관제 계층 | 수압 계기판 |

> 요약: 수집-버퍼-변환-제공-감시 5개 계층이 파이프라인을 구성함

## Ⅲ. 절차
```text
소스식별 --> 수집설계 --> 변환개발 --> 오케스트레이션
```
- 1단계: 소스식별 — 데이터 소스 목록화 및 스키마·주기·볼륨 조사
- 2단계: 수집설계 — 배치/스트림(144 참조) 방식 선택 및 커넥터 구성
- 3단계: 변환개발 — 정제·매핑·집계 로직 구현 및 단위 테스트
- 4단계: 오케스트레이션 — DAG 기반 스케줄링, 재시도·알림 정책 설정

> 요약: 소스 파악부터 오케스트레이션까지 단계적으로 구축함

## Ⅳ. 문제점
- 스키마 드리프트: 소스 스키마가 사전 통보 없이 변경됨 — 파이프라인 실패 유발
- 관측성 부족: 중간 단계 데이터 품질 검증이 미흡함 — 오류가 하류까지 전파
- 단일 장애점: 오케스트레이터 장애 시 전체 파이프라인 중단 — 복구 시간 증가

> 요약: 스키마 변동, 관측성 부족, 단일 장애점이 운영 안정성을 위협함

## Ⅴ. 개선방안
1. 단기: 스키마 레지스트리 도입 및 호환성 자동 검증으로 드리프트 조기 탐지
2. 중기: 단계별 데이터 품질 게이트(null 비율·범위 검사) 삽입으로 오류 전파 차단
3. 장기: 오케스트레이터 이중화 및 이벤트 드리븐 아키텍처 전환으로 장애 내성 확보

> 요약: 스키마 관리·품질 게이트·이중화로 파이프라인 신뢰성을 높임

## Ⅵ. 전망
- 발전 방향: 선언적 파이프라인 정의와 자동 최적화 엔진이 결합하는 추세임
- 기술사적 판단: 파이프라인은 단순 데이터 이동 도구가 아니라 데이터 품질 보증 체계로 확장 중임
- 기술사 제언: 데이터 계약(Data Contract) 기반의 소스-소비자 간 SLA 설계를 우선 검토할 필요
