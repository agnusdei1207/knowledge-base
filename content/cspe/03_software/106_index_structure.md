# 📖 【암기용】 개념 완전 이해

## 한눈에
- **개요**: 데이터베이스에서 데이터를 빠르게 찾기 위해 키 값과 디스크 주소를 매핑해 둔 자료구조다.
- **왜 필요한가**: 수백만 건의 데이터를 디스크 처음부터 훑는(Full Scan) 끔찍한 속도 저하를 막기 위해 필요하다.
- **핵심 직관**: 전공 서적 뒤편에 있는 '색인(찾아보기)'과 같아 단어 옆에 적힌 페이지 번호로 단번에 이동한다.

## 핵심 용어 정리

| 용어/표기 | 의미 | 비유·예 |
|:---|:---|:---|
| B+Tree 인덱스 | 범용적으로 쓰이는 트리 인덱스. 리프 노드에만 데이터 주소가 있고 리프끼리 연결됨 | 책의 목차를 타고 내려가는 방식 |
| 해시 (Hash) 인덱스 | 해시 함수를 통해 버킷 주소를 계산하는 인덱스로 동등(=) 검색에 특화 | 물품 번호를 주면 바로 위치를 찍어줌 |
| 복합 (Composite) | 두 개 이상의 컬럼을 합쳐 만든 다중 조건 인덱스 | 전화번호부에서 '지역' 찾고 '이름' 찾기 |
| 블록 (Block) 분할 | 데이터 삽입으로 노드가 꽉 차면 쪼개지는 현상 (성능 저하 요인) | 꽉 찬 서랍 서류를 반으로 나눠 새 서랍에 담기 |

## 깊이 이해
- **배경·문제의식**: 디스크 I/O는 CPU 연산보다 압도적으로 느리다. 튜닝의 핵심은 "어떻게 디스크 블록 접근을 최소화할 것인가"다.
- **작동 원리**: B+Tree는 대소 비교로 브랜치를 타서 리프 노드에 도달하며, 리프들이 연결되어 범위 검색(BETWEEN)에 유리하다. 해시 인덱스는 해시 함수로 즉시 주소를 찾지만 크기 비교가 안 돼 범위 검색을 못 한다.
- **비유**: B+Tree는 "50보다 커?" 하며 스무고개로 찾는 것이고, 해시는 자판기 버튼을 누르면 바로 물건이 나오는 것이다.
- **구체 예시**: 회원가입일(범위 조건) 조회는 B+Tree, 단일 회원ID(= 조건) 조회는 해시 인덱스가 최적이다.
- **흔한 오해·주의점**: 인덱스를 무작정 만들면 조회는 빠르나 DML 갱신 시 트리 밸런스 유지를 위한 오버헤드로 쓰기 성능이 급락한다.

## 연결 개념
- **클러스터드 인덱스**: 인덱스 구조 리프 자체가 실제 테이블 데이터인 물리적 정렬 방식.
- **실행 계획**: DB 옵티마이저가 수많은 인덱스 중 어떤 것을 탈지 결정하는 과정.

# 📝 【답안용】 시험 답안 템플릿

## 핵심 인사이트 (3줄 요약)

> 1. **본질**: 디스크 I/O 횟수를 획기적으로 줄이기 위해 정렬된 키 값과 물리적 주소를 매핑한 자료구조
> 2. **가치**: 대용량 트랜잭션 환경에서 특정 조건에 부합하는 데이터를 즉시 도출해 쿼리 응답시간 보장
> 3. **판단 포인트**: B+Tree, 해시, 복합 구조 차이와 쿼리 접근 패턴(범위 검색 여부)에 맞춘 취사선택

## 출제 의도 및 답안 포인트

| 출제 의도 | 반드시 짚을 핵심 | 감점 회피 포인트 |
|:---|:---|:---|
| 인덱스 내부 구조의 수학적 이해 및 활용 평가 | B+Tree 리프 연결성(범위검색 유리)과 해시 O(1) 탐색 | 무조건 인덱스가 좋다는 단순 서술 지양(갱신 부하 명시) |

> 요약: 쿼리의 접근 패턴에 따라 최적의 인덱스 자료구조를 선택 및 설계해야 한다.

---

## Ⅰ. 개요 및 필요성

- 개요: DB 테이블 검색 속도 향상을 위해 특정 컬럼 키와 레코드 물리적 주소를 구성한 별도 자료구조
- 배경: 데이터 볼륨 증가에 따른 Full Table Scan의 치명적 디스크 I/O 병목 해소 요구
- 필요성: 조인, 정렬, 조건 검색(Where) 시 데이터 접근 경로 최적화로 빠른 쿼리 응답시간 확보

---

## Ⅱ. 구조 및 구성요소

```text
[B+Tree 인덱스 구조]
         [ Root 노드 ]
        /              [ 브랜치 ]       [ 브랜치 ]
   /       \         /       [리프] <-> [리프] <-> [리프] (링크드 리스트 순차 연결)
   ↓         ↓         ↓ 
(데이터 ROWID 주소 매핑)
```

| 인덱스 종류 | 자료구조 핵심 | 주요 용도 |
|:---|:---|:---|
| B+Tree 인덱스 | 밸런스 트리, 리프 노드만 포인터 보유, 순차 링크 | 범위 검색, 정렬 연산 (RDBMS 표준) |
| 해시 (Hash) | 해시 함수 연산으로 버킷 주소 도출, $O(1)$ | 단일 동등 조건(`=`) 검색 (메모리 DB) |
| 복합 (Composite) | 둘 이상의 컬럼 결합 (순서에 따라 분기 결정) | 다중 컬럼 `WHERE` 조건, 커버링 인덱스 |
| 비트맵 (Bitmap) | 키 값을 Bit 배열(0,1)로 변환해 논리 연산 | 성별 등 카디널리티가 낮은 OLAP 환경 |

> 요약: B+Tree는 범용적 범위 탐색을, 해시는 극단적 동등 탐색을, 복합 인덱스는 다중 조건 탐색을 지원한다.

---

## Ⅲ. 동작원리 및 흐름도

```text
쿼리 유입 -> 옵티마이저 평가 -> 인덱스 수직 탐색(Seek) -> 리프 노드 도달 -> 테이블 디스크 룩업
```

- 1단계 실행계획: 옵티마이저가 조건 및 선택도를 평가해 최적 인덱스 채택
- 2단계 수직적 탐색(Seek): B+Tree 루트부터 브랜치를 거쳐 조건에 맞는 첫 번째 리프 노드 도달
- 3단계 수평적 탐색(Scan): 리프 노드 간 링크드 리스트를 따라 순차 이동하며 범위 조건 키 값 수집
- 4단계 물리적 룩업: 수집된 키에 매핑된 ROWID를 이용해 실제 테이블의 데이터 블록 읽어옴

> 요약: 수직 탐색으로 시작점을 찾고 수평 탐색으로 데이터를 모은 뒤 실제 디스크를 룩업한다.

---

## Ⅳ. 특징
- 순차 접근성: B+Tree 리프 노드가 양방향 리스트로 연결되어 순/역방향 범위 검색에 압도적 효율
- Trade-off 구조: 검색은 빠르지만, 삽입/삭제 시 트리를 쪼개고 맞추는 분할(Split) 쓰기 오버헤드 유발
- 선택도 의존성: 인덱스 컬럼의 선택도가 10~15%를 넘어가면 랜덤 액세스 부하로 Full Scan이 더 유리함
- 복합 인덱스 제약: 선행 컬럼이 조건에서 누락되면 후행 컬럼은 인덱스 구조를 타지 못함

> 요약: 읽기(Read) 성능 최적화에 필수적이나 갱신(Write) 부하와 분포도 제약을 동반한다.

---

## Ⅴ. 심화 비교 및 적용 판단

| 비교 축 | B+Tree 인덱스 | Hash 인덱스 | 선택 기준 |
|:---|:---|:---|:---|
| 시간 복잡도 | $O(\log n)$ (트리 깊이 의존) | $O(1)$ (충돌 제외) | 단건 조회 여부 |
| 지원 연산 | `=`, `<`, `>`, `BETWEEN`, `LIKE 'A%'` | 오직 `=` 연산만 가능 | 범위 검색 필요성 |
| 주 활용처 | 디스크 기반 RDBMS 기본 인덱스 | Redis 등 인메모리 스토어 | 데이터 저장 위치 |

> 요약: RDBMS에서는 범위 검색이 필수적이므로 B+Tree 계열을 기본 구조로 사용한다.

**리스크·대응:**
- 인덱스 단편화: 대량 `DELETE/UPDATE`로 트리 노드에 빈 공간(Fragmentation) 생겨 성능 저하 → 정기적 인덱스 재구성(`REBUILD`) 수행 (지표: 인덱스 단편화율)
- 복합 인덱스 비효율: 무분별한 남발로 공간 낭비 및 옵티마이저 혼란 → 공통 사용 가능 인덱스 병합(Merge) (지표: 캐시 히트율)

**도입 후 점검 지표:**
- 성능/효율: 특정 핵심 쿼리의 논리적 읽기 횟수 감소 — 실행계획상 스캔 블록 수 급감
- 품질/운영: DB 쓰기 작업 지연 시간 — DML 성능 하락 SLA 이내 확인

---

## Ⅵ. 실무 적용 및 결론

**적용 방안 3개:**
1. 카디널리티 기반 선정: 값 종류가 많은(선택도 5% 미만, 예: 주문번호) 컬럼을 단일 인덱스 후보 1순위로 지정
2. 복합 인덱스 순서 최적화: `=` 조건으로 범위를 가장 많이 좁히는 컬럼을 복합 인덱스의 선행 컬럼으로 전진 배치
3. 힌트(Hint) 적용: 통계 정보 오류로 옵티마이저가 Full Scan을 할 경우 소스코드에 `/*+ INDEX() */` 힌트를 명시해 강제

**결론:**
- 기술사 판단: 인덱스는 하드웨어 증설 없이 I/O를 수백 배 개선하는 핵심 기법이므로 데이터베이스 설계 시 1순위로 고려해야 한다.
- 향후 방향: 최근 컬럼 스토어 DB 발달로 인덱스 의존도가 줄고 있으나, OLTP 환경에서의 중요성은 지속될 것이다.
