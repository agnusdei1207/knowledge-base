## 핵심 인사이트 (3줄 요약)
- **인덱스(Index)**는 데이터베이스에서 검색 속도를 비약적으로 높이기 위해, 책의 '맨 뒤 색인(찾아보기)'처럼 `<키 값, 물리적 주소>`를 별도의 파일로 정렬하여 저장해 두는 자료구조임.
- 거의 모든 관계형 DB는 인덱스를 저장할 때 탐색 깊이가 항상 일정한 **B-Tree (또는 B+Tree)** 구조를 사용하여, 수억 건의 데이터라도 단 3~4번의 디스크 I/O만으로 원하는 값을 찾아냄.
- 읽기(SELECT) 속도는 폭발적으로 빨라지지만, 새로운 데이터를 쓰거나(INSERT) 지울(DELETE) 때마다 인덱스 트리도 정렬하고 쪼개야(Page Split) 하므로 **쓰기 성능이 저하되는 치명적인 트레이드오프**가 존재함.

## Ⅰ. 개요 및 필요성
- **개요**: 검색 조건을 만족하는 레코드를 빠르게 찾기 위해 구성된 별도의 데이터 구조(주로 B+Tree 계열 활용).
- **필요성**: 책에서 '데이터베이스'라는 단어를 찾고 싶은데 색인(Index)이 없으면, 첫 페이지부터 1,000페이지까지 모든 글자를 다 읽어야 함(Full Table Scan). 1억 건의 회원 테이블에서 '김철수' 한 명을 찾기 위해 디스크를 처음부터 끝까지 뒤지면 DB 서버가 터지므로, O(log N) 속도로 찾을 수 있는 지름길이 필요했음.
---
## Ⅱ. 아키텍처 및 핵심 원리
- **B-Tree (Balanced Tree)의 핵심 특징**:
  - 이진 탐색 트리와 달리 하나의 노드에 여러 개의 키(Key)를 저장하여 트리의 높이(Depth)를 납작하게 유지함. (디스크 I/O 횟수를 최소화하기 위함).
  - 루트(Root) 노드에서 리프(Leaf) 노드까지 가는 경로의 길이가 항상 같아, 어떤 데이터를 찾든 **검색 시간이 균일하게 보장됨**.
- **B+Tree (B-Tree의 진화형, 현대 DB의 표준)**:
  - 중간 노드들(Branch)은 '길잡이(이정표)' 역할만 하고, **실제 데이터 주소는 오직 맨 밑바닥의 리프(Leaf) 노드에만 저장**함.
  - 가장 큰 특징: 리프 노드들끼리 **연결 리스트(Linked List)**로 가로로 쭉 이어져 있음.
  - "나이 20살~30살 찾기(Range Scan)" 같은 범위 검색을 할 때, B+Tree는 20살 리프 노드만 찾은 뒤, 옆으로 쭉 타고 가면서(순차 읽기) 30살까지 한 번에 긁어오므로 범위 검색 성능이 압도적임.

```text
[ B+Tree 인덱스 구조 모식도 ]

          [ 루트 노드 ] (50 이상은 오른쪽, 미만은 왼쪽으로 가라)
             /      \
      [ 브랜치 ]      [ 브랜치 ]
       /    \         /    \
 [리프(10)]-[리프(30)]-[리프(50)]-[리프(80)] ⬅️ (리프 노드끼리 링크드 리스트로 연결됨!)
    |        |        |        |
 (데이터 주소)(데이터 주소)(데이터 주소)(데이터 주소)
 
 * 30~80까지 범위 검색(BETWEEN): 리프(30)을 찾은 뒤, 옆으로 줄줄이 읽어 리프(80)까지 감.
```

## Ⅲ. 비교 및 연결
| 구분 | B-Tree | B+Tree (대부분의 RDBMS) | Hash Index |
|---|---|---|---|
| **데이터 저장 위치** | 모든 노드(루트, 브랜치, 리프) | **오직 리프(Leaf) 노드에만 저장** | 해시 버킷 |
| **순차/범위 검색** | 트리를 계속 오르락내리락 해야 함 | **리프 노드 연결 리스트로 초고속 스캔** | **절대 불가능 (점 검색만 가능)** |
| **트리 높이** | 다소 높음 (노드에 데이터가 섞여서) | **매우 낮음 (브랜치에 키만 꽉 채움)** | 트리 구조 아님 |
| **적합한 용도** | 과거 구형 시스템 | **부등호(>, <), BETWEEN, 정렬 쿼리** | 메모리 DB(Redis), 동등(=) 조건 |

## Ⅳ. 실무 적용 및 기술사 판단
- **과도한 인덱스의 저주**: "검색이 느리네? 인덱스 걸자!"라며 테이블에 인덱스를 10개씩 만들어 두면, 데이터를 1줄 INSERT 할 때마다 10개의 B+Tree를 모두 업데이트하고 쪼개야(Page Split/디스크 단편화) 함. 결국 쓰기 성능이 바닥을 기게 됨. 실무 아키텍트는 **조회(SELECT)와 쓰기(DML)의 비율을 분석하여 핵심 인덱스 3~4개만 남기는 인덱스 다이어트**를 수행해야 함.
- **인덱스 스캔 vs 풀 테이블 스캔**: 옵티마이저(Optimizer)는 조회할 데이터가 전체의 20%를 넘어가면(손익 분기점), 인덱스를 타는 것(랜덤 I/O)보다 차라리 테이블 전체를 무식하게 처음부터 읽는 것(Full Table Scan, 순차 I/O)이 더 빠르다고 판단하고 인덱스를 무시함. 기술사는 무조건 인덱스가 빠르다는 맹신을 버리고, 디스크 I/O의 물리적 원리를 기반으로 튜닝해야 함.
---
## Ⅴ. 기대효과 및 결론
- 수십 테라바이트에 달하는 데이터의 바다에서, 개발자가 원하는 단 하나의 레코드를 0.001초 만에 건져 올리게 해주는 데이터베이스 엔진의 가장 강력한 무기임.
- 디스크 접근 횟수(I/O Block)를 최소화하기 위해 고안된 B+Tree는, 메모리보다 10만 배 느린 하드 디스크 시대의 병목을 극복한 컴퓨터 공학 최고의 자료구조 혁명임.

### 👶 어린이를 위한 3줄 비유 설명
1. 1,000페이지짜리 두꺼운 사전에서 '호랑이'를 찾을 때, 1쪽부터 다 읽으면 며칠이 걸려요 (풀 스캔).
2. 인덱스는 사전 맨 뒤에 있는 '가나다순 찾아보기'예요. 'ㅎ' 코너로 바로 점프해서 '호랑이... 520쪽'을 단숨에 찾아낼 수 있죠!
3. 하지만 사전에 새로운 단어를 계속 추가(INSERT)해야 한다면, 그때마다 맨 뒤의 '찾아보기' 글자 순서도 다 지우고 다시 써야 해서 너무 힘들어진답니다(쓰기 속도 저하).
