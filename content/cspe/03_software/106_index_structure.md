## 미리 알고가기

- 인덱스는 테이블 전체를 다 읽지 않고 필요한 행을 빨리 찾기 위한 보조 구조임
- 선택도는 조건으로 거를 수 있는 정도를 뜻하며, 선택도가 높을수록 인덱스 효과가 커지는 경우가 많음
- 복합 인덱스는 여러 컬럼을 한 순서로 묶은 인덱스라 선두 컬럼 순서가 중요함

## Ⅰ. 개요

- **정의/개념**: 인덱스 구조는 검색 키와 행 위치 정보를 별도 구조에 유지해 전체 스캔을 줄이고 조회와 정렬과 범위 검색을 빠르게 수행하게 만드는 데이터 접근 최적화 구조임.
- **배경/필요성**: 데이터가 커질수록 모든 질의를 전체 스캔으로 처리할 수 없으므로, 질의 조건과 정렬 방식에 맞는 접근 경로를 미리 설계해야 응답 시간을 안정적으로 유지할 수 있음.

## Ⅱ. 특징

- B+Tree는 범위 검색과 정렬과 일반 조회에 두루 쓰이는 범용 구조임
- 해시 인덱스는 해시값으로 동일 키 bucket을 찾으며 키 순서를 보존하지 않아 범위·정렬 탐색에 사용하지 못함
- 복합 인덱스는 여러 조건이 함께 쓰이는 질의에서 효과가 크지만 컬럼 순서에 민감함
- 인덱스를 늘릴수록 조회는 빨라질 수 있어도 쓰기 비용과 저장 공간과 통계 관리 부담이 커짐

## Ⅲ. 종류 및 비교

| 판단 기준 | B+Tree | 해시 인덱스 | 복합 인덱스 |
|:---|:---|:---|:---|
| 잘 맞는 질의 | 등치 조회와 범위 조회와 정렬 | 정확히 같은 값을 찾는 질의 | 여러 컬럼 조건이 함께 나오는 질의 |
| 접근 방식 | 정렬 트리에서 등치·범위·순서 탐색 | 해시값으로 동일 키 bucket 탐색 | 선두 컬럼부터 복합 키 순서로 탐색 |
| 한계 | 쓰기 시 분할과 재정렬 비용이 생길 수 있음 | 범위 검색과 순서 기반 조회에 약함 | 선두 컬럼이 맞지 않으면 효과가 급격히 떨어짐 |
| 선택 기준 | 일반 온라인 트랜잭션 처리의 기본 선택지 | 키 기반 단순 조회가 많은 경우 | 대표 질의 패턴이 명확한 경우 |

## Ⅳ. 구성요소 및 구조

| 구성요소 | 설명 |
|:---|:---|
| 검색 키 | 어떤 컬럼 값을 기준으로 행을 찾을지 정해 인덱스 효과를 좌우함 |
| 탐색 구조 | 트리 정렬 구조나 해시 버킷이 실제 탐색 방식과 범위 처리 가능 여부를 결정함 |
| 행 위치 정보 | 인덱스에서 찾은 결과를 실제 테이블 행으로 연결함 |
| 통계 정보 | 값 분포와 선택도를 기록해 옵티마이저가 인덱스 사용 여부를 판단하게 함 |

## Ⅴ. 원리 및 절차 흐름도

```text
+-------------+     +-------------+     +-------------+     +-------------+
| 질의 패턴 분석  | --> | 구조와 컬럼 선택 | --> | 인덱스 생성    | --> | 계획/성능 검증  |
+-------------+     +-------------+     +-------------+     +-------------+
```

1. **질의 패턴 분석**: 등치 조건과 범위 조건과 정렬 사용 빈도를 확인함
2. **구조와 컬럼 선택**: B+Tree와 해시와 복합 인덱스 중 적합한 방식을 고름
3. **인덱스 생성**: 컬럼과 순서를 정해 인덱스를 만듦
4. **계획과 성능 검증**: 실행 계획과 응답 시간과 쓰기 부하를 함께 확인함

## Ⅵ. 실무 적용 및 유의점

1. 주문 조회처럼 조건과 정렬이 반복되는 온라인 거래 업무에서는 대표 질의에 맞춰 인덱스를 설계하되 선두 컬럼 순서가 틀리면 효과가 거의 없으므로 실행 계획의 인덱스 사용 여부와 평균 조회 시간을 기준으로 확인함.
2. 쓰기 빈도가 높은 테이블에서는 인덱스를 과도하게 늘리면 삽입과 수정이 느려지므로 실제 사용되는 인덱스만 남기고 쓰기 지연 시간과 미사용 인덱스 수로 확인함.

## Ⅶ. 결론

인덱스 구조 선택의 핵심은 많이 만드는 데 있지 않고 질의 패턴과 갱신 부담에 맞는 접근 경로를 정확히 설계하는 데 있음.
