## 미리 알고가기

- 인덱스는 테이블 전체 스캔을 줄여 필요한 행에 접근하는 보조 구조임
- 선택도는 조건으로 거를 수 있는 정도를 뜻하며, 선택도가 높을수록 인덱스 효과가 커지는 경우가 많음
- 복합 인덱스의 선두 컬럼 순서가 사용할 수 있는 질의 조건을 결정함

## 작성 근거(검토용)

- 제목·frontmatter·미리 알고가기·본문·표·요약·결론을 5회 전수 검수해 어색한 단어·조사·동사 결합·장황한 명사구를 교정함
- 인덱스는 탐색 구조·검색 조건·복합 키 순서를 핵심 축으로 설명함
- 비교표는 B+Tree·해시·복합 인덱스의 분류 관점과 적용 조건을 대비함
- 업무 DB는 인덱스 사용률·p95 조회 지연으로 검증함

## Ⅰ. 개요

- **정의/개념**: 인덱스는 검색 키와 행 위치를 별도 구조로 관리해 전체 스캔을 줄이는 데이터 접근 구조임
- **배경/필요성**: 데이터 규모가 증가해도 조회 지연을 유지하기 위해 질의 조건·정렬 방식·갱신 빈도에 맞는 인덱스 구조와 키 순서를 설계해야 함

## Ⅱ. 특징

- B+Tree는 범위 검색과 정렬과 일반 조회에 두루 쓰이는 범용 구조임
- 해시 인덱스는 해시값으로 동일 키 버킷을 찾으며 키 순서를 보존하지 않아 범위·정렬 탐색에 적합하지 않음
- 복합 인덱스는 여러 조건이 함께 쓰이는 질의에서 효과가 크지만 컬럼 순서에 민감함
- 인덱스를 늘릴수록 조회는 빨라질 수 있어도 쓰기 비용과 저장 공간과 통계 관리 부담이 커짐

## Ⅲ. 종류 및 비교

| 판단 기준 | B+Tree | 해시 인덱스 | 복합 인덱스 |
|:---|:---|:---|:---|
| 분류 관점 | 정렬 트리 기반 탐색 구조 | 해시 기반 탐색 구조 | 둘 이상 컬럼을 묶는 키 구성 |
| 적합 조건 | 등치·범위 조회와 정렬 | 단일 키 등치 조회 | 여러 컬럼 조건이 함께 사용되는 조회 |
| 접근 방식 | 정렬 트리에서 등치·범위·순서 탐색 | 해시값으로 동일 키 버킷 탐색 | 선두 컬럼부터 복합 키 순서로 탐색 |
| 설계 핵심 | 키 분포와 페이지 분할 | 해시 충돌과 버킷 분포 | 선두 컬럼과 조건·정렬 순서 |
| 주요 한계 | 쓰기 시 페이지 분할 비용이 발생함 | 범위 검색과 정렬에 사용할 수 없음 | 선두 컬럼 조건이 없으면 사용 범위가 제한됨 |

> 요약: B+Tree와 해시는 탐색 구조를, 복합 인덱스는 키 구성을 뜻하므로 질의 조건과 키 순서에 따라 함께 설계함.

## Ⅳ. 구성요소 및 구조

| 구성요소 | 설명 |
|:---|:---|
| 검색 키 구성 | 대상 컬럼과 복합 키 순서를 정해 사용할 수 있는 질의 조건을 결정함 |
| 탐색 구조 | 트리 정렬 구조나 해시 버킷이 실제 탐색 방식과 범위 처리 가능 여부를 결정함 |
| 행 위치 정보 | 인덱스에서 찾은 결과를 실제 테이블 행으로 연결함 |
| 통계 정보 | 값 분포와 선택도를 기록해 옵티마이저가 인덱스 사용 여부를 판단하게 함 |

> 요약: 검색 키와 탐색 구조가 접근 경로를 만들고 행 위치와 통계 정보가 실제 조회와 계획 선택을 지원함.

## Ⅵ. 실무 사례

1. 주문 조회 DB는 조건·정렬 순서에 맞춘 복합 인덱스를 적용하고 인덱스 사용률·p95 조회 지연을 확인함
2. 쓰기 집약 DB는 미사용 인덱스를 제거하고 쓰기 지연·인덱스 저장 용량을 확인함

## Ⅶ. 결론

- 인덱스는 질의 조건·정렬 순서·갱신 부담에 맞춰 탐색 구조와 검색 키를 설계해야 함
