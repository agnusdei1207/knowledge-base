## 미리 알고가기

- 인덱스는 검색 조건을 빠르게 찾기 위한 보조 데이터 구조임
- B+Tree와 해시와 복합 인덱스는 탐색 방식과 적합 질의가 다름
- 인덱스는 조회를 빠르게 하지만 저장 공간과 갱신 비용을 늘림

## Ⅰ. 개요

- **정의/개념**: 인덱스 구조는 테이블 데이터를 직접 전수 탐색하지 않고 검색 키와 저장 위치를 보조 구조에 유지해 조회와 정렬과 범위 검색을 더 빠르게 수행하도록 만드는 데이터 접근 최적화 구조임
- **배경/필요성**: 데이터가 커질수록 전체 스캔 비용이 급증하므로, 질의 패턴에 맞는 탐색 구조를 선택해 응답 시간을 줄일 필요가 있음

## Ⅱ. 특징

- B+Tree는 범위 검색과 정렬에 강하고 범용성이 높음
- 해시 인덱스는 등치 검색에 매우 빠르지만 범위 조건에 약함
- 복합 인덱스는 다중 조건 질의 최적화에 유리하지만 컬럼 순서 영향이 큼
- 인덱스 수가 많아질수록 쓰기와 저장 공간과 통계 관리 부담이 커짐

## Ⅲ. 종류 및 비교

| 판단 기준 | B+Tree | 해시 | 복합 인덱스 |
|:---|:---|:---|:---|
| 적합 질의 | 범위·정렬·등치 | 등치 중심 | 다중 조건 질의 |
| 강점 | 범용성 높음 | 매우 빠른 key lookup | 조건 결합 최적화 |
| 한계 | 랜덤 쓰기 비용 존재 | 범위 검색 부적합 | 컬럼 순서 의존 큼 |
| 선택 기준 | 일반 OLTP | 고정 key 조회 | 대표 질의 패턴 존재 |

## Ⅳ. 구성요소 및 구조

| 구성요소 | 설명 |
|:---|:---|
| Search Key | 인덱스가 정렬하거나 해시화할 기준 컬럼으로 탐색 효율을 좌우함 |
| Access Path Structure | B+Tree 노드나 해시 버킷 같은 탐색 구조가 실제 접근 속도를 결정함 |
| Row Locator | 인덱스에서 찾은 결과를 실제 테이블 행 위치로 연결함 |
| Statistics Metadata | 선택도와 분포 정보를 유지해 옵티마이저가 인덱스 사용 여부를 판단하게 함 |

## Ⅴ. 원리 및 절차 흐름도

```text
+-------------+     +-------------+     +-------------+     +-------------+
| 질의 패턴 분석  | --> | 인덱스 구조 선택 | --> | 인덱스 생성    | --> | 실행 계획 검증  |
+-------------+     +-------------+     +-------------+     +-------------+
```

1. **질의 패턴 분석**: 등치와 범위와 정렬 사용 빈도를 확인함
2. **인덱스 구조 선택**: 조건 특성에 맞는 구조를 고름
3. **인덱스 생성**: 컬럼과 순서를 설계해 생성함
4. **실행 계획 검증**: 실제 사용 여부와 효과를 확인함

## Ⅵ. 문제점 및 해결 방안

1. 문제: 질의 패턴 분석 없이 인덱스를 남발하면 조회 이득보다 쓰기 지연과 저장 공간 부담이 더 커질 수 있음
   - 해결방안: hotspot query 기반으로 인덱스를 설계하고 index hit rate와 write amplification ratio로 검증함
2. 문제: 복합 인덱스 컬럼 순서를 잘못 잡으면 만들어도 실제 계획에서 거의 사용되지 않을 수 있음
   - 해결방안: predicate selectivity 순서를 반영하고 plan usage ratio와 filter residual rate로 검증함
3. 문제: 통계 정보가 오래되면 좋은 인덱스가 있어도 옵티마이저가 잘못된 경로를 선택할 수 있음
   - 해결방안: statistics refresh policy를 운영하고 stale stats ratio와 plan misprediction count로 검증함

## Ⅶ. 적용 사례

- 주문 조회 시스템에서는 hotspot query 기준으로 인덱스를 설계하고 확인 지표는 index hit rate와 write amplification ratio임
- 복합 검색 서비스에서는 컬럼 순서를 최적화하고 확인 지표는 plan usage ratio와 filter residual rate임
- 대규모 운영 DB에서는 통계 갱신 정책을 운영하고 확인 지표는 stale stats ratio와 plan misprediction count임

## Ⅷ. 결론

인덱스 구조 선택의 본질은 많이 만드는 데 있지 않고 질의 패턴과 갱신 비용에 맞는 접근 경로를 정확히 설계하는 데 있음.
