## 핵심 인사이트 (3줄 요약)
- 도커 엔진과 그 위에서 도는 컨테이너 프로세스를, 해킹당하면 서버 전체가 멸망하는 슈퍼 관리자(`root`) 권한이 아니라, **아무 힘도 없는 일반 사용자(`user`) 권한으로 실행하게 만드는 혁신적인 보안 아키텍처**.
- 기존 도커 데몬은 항상 `root`로 돌아갔기 때문에, 해커가 웹 컨테이너를 뚫고 도커의 빈틈(취약점)을 타면 순식간에 호스트 서버의 신(God)이 되는 '컨테이너 탈옥(Breakout)'이 발생했음.
- 루트리스 컨테이너를 적용하면 해커가 컨테이너를 뚫고 나와봤자 "일반 사용자 A"에 불과하므로, 다른 사용자의 데이터나 시스템 핵심 파일을 절대 건드릴 수 없는 완벽한 방어벽이 형성됨.

## Ⅰ. 개요 및 필요성
- **개요**: 루트(root) 권한 없이도 컨테이너 엔진(Docker, Podman 등)을 실행하고 컨테이너를 생성/관리할 수 있게 해주는 리눅스 네임스페이스 기반의 보안 기술.
- **필요성**: 개발자가 도커를 설치하고 `sudo docker run`을 쳤음. 도커 엔진은 커널 기능을 써야 하니 무조건 `root`로 돌아야 했음. 그런데 컨테이너 안의 해커가 취약점을 뚫고 밖(호스트)으로 나와보니, 자기를 띄워준 부모(도커 데몬)가 `root`니까 해커도 그대로 호스트의 `root`가 되어버림! **"도커 엔진 자체를 그냥 찌질한 일반 유저 권한으로 돌릴 순 없을까? 그럼 뚫려도 피해가 적을 텐데!"**라는 궁극의 보안 니즈에서 탄생함.
---
## Ⅱ. 아키텍처 및 핵심 원리
- **1. User Namespace (사용자 네임스페이스) 매핑의 마법**:
  - 리눅스 커널의 핵심 기능. '컨테이너 밖(진짜 세상)'과 '컨테이너 안(가짜 세상)'의 신분증을 다르게 맵핑해 줌.
  - **밖에서는 찌질이, 안에서는 왕**: 호스트(서버)에서는 아무 권한 없는 UID 1000번(일반 유저) 프로세스지만, User Namespace를 통해 컨테이너 내부에서는 자기가 UID 0번(root)인 것처럼 완벽하게 속여버림.
  - 앱(Nginx 등)은 자기가 `root`인 줄 알고 기분 좋게 80번 포트도 열고 파일도 만지지만, 실제 서버 입장에서는 일반 유저가 노는 것에 불과함.
- **2. 데몬리스(Daemonless) 및 루트리스(Rootless) 런타임 (Podman)**:
  - 도커(Docker)는 중앙에 무거운 `dockerd` 데몬이 항상 `root`로 떠 있어야 했음.
  - 레드햇(RedHat)이 만든 **Podman(포드맨)**은 아예 중앙 데몬 자체가 없음! 일반 유저가 명령어 칠 때만 딱 실행되고 컨테이너를 띄움. 루트리스 보안의 대명사로 자리 잡음.
- **3. 네트워킹과 포트의 한계 극복**:
  - 리눅스는 보안상 일반 유저가 1024번 이하의 포트(예: 80번 HTTP)를 열지 못함.
  - 루트리스 컨테이너는 내부적으로 `slirp4netns` 같은 사용자 공간 네트워킹 마법을 부려, 일반 유저 권한으로도 외부 포트와 통신할 수 있게 우회 처리함.

```text
[ Rootful (기존) vs Rootless (루트리스) 해킹 시나리오 비교 ]

 💣 [ 기존: Rootful 도커 (해커의 천국) ]
 1. 해커가 컨테이너 내부 쉘(Shell) 획득! 
 2. 도커 취약점(Escape)을 통해 호스트(서버)로 탈출!
 3. 호스트에 나와보니 내 부모(도커)가 **Root(왕)**이네? ➡️ 해커 = Root 👑
 4. 서버 포맷, 디스크 삭제, 백도어 설치 가능! (대재앙)

 🛡️ [ 진화: Rootless 컨테이너 (해커의 절망) ]
 1. 해커가 컨테이너 내부 쉘 획득! (안에서는 자기가 Root인 줄 앎).
 2. 취약점을 통해 호스트(서버)로 탈출!
 3. 호스트에 나와보니 내 부모(Podman)가 **일반 유저 'app_user'**네? ➡️ 해커 = app_user 🧑‍🌾
 4. 서버 시스템 폴더 접근? 거절당함(Permission Denied). 다른 파드 공격? 불가능! 
```

## Ⅲ. 비교 및 연결
| 구분 | 기존 도커 (Rootful) | 루트리스 컨테이너 (Rootless) |
|---|---|---|
| **도커 데몬 권한** | 호스트의 `root` 권한 필요 | **호스트의 일반 `user` 권한만 사용** |
| **User Namespace** | 기본적으로 미사용 | **필수 사용 (밖=일반유저, 안=Root로 맵핑)** |
| **탈옥(Breakout) 피해**| **서버 전체 장악 (심각)** | **해당 유저의 권한으로 격리 (피해 최소화)** |
| **대표 툴** | Docker Engine | **Podman**, Docker Rootless 모드 |

## Ⅳ. 실무 적용 및 기술사 판단
- **금융권/공공기관의 Podman 전환 트렌드**: 보안 컴플라이언스가 극도로 깐깐한 금융권이나 공공기관에서는 "서버에 도커(Root 데몬) 설치 금지"라는 지침이 내려옴. 기술사는 이에 대응하여, 도커와 명령어가 100% 똑같으면서 데몬도 없고 루트 권한도 필요 없는 **Podman 기반의 루트리스 컨테이너 아키텍처**로 사내 개발 및 배포 표준을 전면 교체하는 전략을 세워야 함. (명령어도 `docker run` 대신 `podman run` 치면 똑같이 돎).
- **특권(Privileged) 컨테이너 원천 차단 정책**: 쿠버네티스 환경에서도 파드를 띄울 때 `securityContext: runAsNonRoot: true` 속성을 강제하여, 파드 내부의 메인 프로세스가 `root`로 켜지는 것을 원천적으로 차단해야 함. 주니어 개발자들이 편하다고 `privileged: true`를 주는 행위는 인프라 레벨의 OPA/Gatekeeper 정책으로 막아버려야 함.
---
## Ⅴ. 기대효과 및 결론
- 컨테이너 보안의 가장 치명적인 아킬레스건이었던 '호스트 권한 탈취' 문제를 근본적으로(Architecture Level) 틀어막아 버린 혁명.
- "모든 프로세스는 필요한 최소한의 권한만 가져야 한다(Least Privilege)"는 보안의 대원칙을 컨테이너 생태계에 완벽히 구현하여, 기업들이 해킹 공포 없이 안심하고 클라우드 네이티브로 넘어갈 수 있는 면죄부를 제공함.

### 👶 어린이를 위한 3줄 비유 설명
1. 옛날 도커는 '은행장님(Root)' 신분증을 차고 일했어요. 강도가 도커를 협박해서 신분증을 뺏으면 은행 전체 금고를 다 열 수 있었죠.
2. **루트리스 컨테이너**는 도커에게 그냥 '청소부 아저씨(일반 유저)' 신분증만 주고 일하게 하는 거예요.
3. 강도가 쳐들어와서 신분증을 뺏어봤자 청소 도구함밖에 못 여니까 은행의 진짜 돈(서버 데이터)은 완벽하게 안전하답니다!
