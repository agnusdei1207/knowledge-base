## Ⅰ. 개요
- 정의: 프로세스에게 특정 이벤트가 발생했음을 알리는 비동기적 알림 메커니즘
- 배경: 비정상 종료, 인터럽트 처리, 프로세스 간 간단한 상태 통지 기능 수행 필요
- 출제 의도: 시그널의 전달 과정과 시그널 핸들러를 통한 예외 처리 기법 이해

## Ⅱ. 구성요소
```
[ Source ] --(Signal Number)--> [ Target Process ]
                                       |
    +----------------------------------+
    v (Action)
 [ Ignore ]  [ Default (Term/Core) ]  [ Handler Run ]
```
| 구성요소 | 설명 | 비유 |
| :--- | :--- | :--- |
| 시그널 번호 | SIGKILL(9), SIGTERM(15) 등 이벤트 식별자 | 신호등 색상 |
| 시그널 핸들러 | 특정 시그널 수신 시 실행되는 사용자 정의 함수 | 긴급 호출 처리반 |
| 시그널 마스크 | 특정 시그널의 수신을 일시적으로 차단하는 비트맵 | 수신 거부 목록 |
> 요약: 소프트웨어 인터럽트로서 프로세스의 실행 흐름을 가로챔.

## Ⅲ. 절차
```
[Signal Raise] -> [Pending] -> [Kernel Context Switch] -> [Handler Exec]
```
1. 하드웨어(Ctrl+C), 커널(예외), 또는 타 프로세스가 시그널을 발생시킴
2. 대상 프로세스의 PCB 내 시그널 대기(Pending) 비트에 기록됨
3. 프로세스가 커널 모드에서 사용자 모드로 복귀하는 시점에 시그널 확인
4. 등록된 핸들러가 있으면 호출하고, 없으면 기본 동작(종료 등) 수행
> 요약: 전달된 신호를 확인하여 즉각적 또는 지연된 대응 조치를 수행함.

## Ⅳ. 문제점
- 원인: 시그널 핸들러 내에서 비재진입(Non-reentrant) 함수 사용 시 교착상태 위험
- 원인: SIGKILL과 같이 포착이나 무시가 불가능한 강력한 시그널로 인한 데이터 유실

## Ⅴ. 개선방안
- (단기) 핸들러 내에서는 비동기-시그널-안전(Async-signal-safe) 함수만 사용 권장
- (중기) 시그널을 파일 디스크립터로 변환하여 처리하는 `signalfd` 기법으로 이벤트 루프 통합
- (장기) 실시간 시그널(Real-time Signal)을 활용하여 시그널의 유실 방지 및 순서 보장

## Ⅵ. 전망
- 클라우드 컨테이너의 '우아한 종료(Graceful Shutdown)' 구현을 위한 시그널 처리 중요성 증대
- 비동기 프로그래밍 모델(Node.js 등)과의 정교한 결합을 위한 라이브러리 수준의 최적화 지속
