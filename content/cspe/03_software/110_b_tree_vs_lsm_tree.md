## 핵심 인사이트 (3줄 요약)
- **B-Tree**가 디스크의 임의 위치에 데이터를 덮어쓰는(In-place Update, Random I/O) '읽기(Read)'에 최적화된 전통적 RDB의 자료구조라면, **LSM-Tree**는 데이터를 무조건 파일 끝에 순차적으로 덧붙이는(Append-only, Sequential I/O) **'쓰기(Write)'에 최적화된 NoSQL 시대의 자료구조**.
- 엄청난 속도의 로깅, 실시간 센서 데이터 수집 등 쓰기 트래픽이 폭주하는 현대 빅데이터 환경(Cassandra, RocksDB, Kafka)에서는 B-Tree의 구조가 버티지 못하므로 LSM-Tree가 산업 표준으로 자리 잡음.
- "쓰기를 극단적으로 빠르게 만드는 대신, 읽을 때 파편화된 파일들을 뒤져야 해서 느려진다"는 약점이 있으며, 이를 보완하기 위해 백그라운드 병합(Compaction)과 블룸 필터(Bloom Filter)를 필수적으로 사용함.

## Ⅰ. 개요 및 필요성
- **개요**: 하드 디스크 및 SSD 환경에서 읽기와 쓰기 성능 트레이드오프의 양극단에 서 있는 데이터베이스의 두 가지 핵심 스토리지 엔진 자료구조.
- **필요성**: 카카오톡 메시지나 넷플릭스 로그처럼 1초에 10만 건씩 새로운 데이터가 쏟아져 들어오는 시대가 옴. 기존 B-Tree는 데이터가 들어올 때마다 트리를 반으로 쪼개고 정렬하느라(Page Split) 디스크 병목에 걸려 쓰기 속도가 처참하게 무너짐. 디스크는 랜덤 쓰기보다 '순차 쓰기'가 100배 빠르다는 물리적 성질을 이용해, 무조건 뒤에 갖다 붙이는 새로운 트리 구조가 필요했음.
---
## Ⅱ. 아키텍처 및 핵심 원리
- **LSM-Tree의 동작 원리 (쓰기 과정)**:
  1. **MemTable (메모리)**: 데이터가 들어오면 디스크에 안 쓰고 일단 메모리 트리(Red-Black 트리 등)에 빠르게 씀.
  2. **SSTable (디스크 플러시)**: 메모리가 꽉 차면, 정렬된 상태 그대로 디스크에 파일(SSTable)로 쭉 내려씀(Flush). 이때 기존 데이터를 덮어쓰지 않고 새로운 파일을 계속 만듦(Append-only, 순차 I/O의 마법).
  3. **Compaction (병합)**: 놔두면 디스크에 자잘한 SSTable 파일이 수백 개 생겨서 읽기 속도가 박살 남. 백그라운드 프로세스가 이 파일들을 묶어 큰 파일로 합치고, 삭제된 데이터(Tombstone)를 진짜로 날려버림.
- **읽기 과정 (Read)**:
  - 메모리(MemTable)를 뒤짐 ➡️ 없으면 디스크에 있는 수많은 SSTable 파일을 최신순으로 뒤져야 함. (B-Tree보다 훨씬 무겁고 느림).

```text
[ 스토리지 엔진의 물리적 I/O 차이점 ]

 [ 전통적 B-Tree (RDBMS) - 주차장 방식 ]
 - 주차장(디스크) 5번 자리에 차(데이터)를 댐.
 - 차를 바꿀 때 5번 자리에 가서 기존 차를 빼고 새 차를 넣음 (Random I/O ➡️ 느림).
 - 단점: 빈자리를 만들려고 주차장 전체를 공사해야 할 때가 있음 (Page Split).

 [ 최신 LSM-Tree (NoSQL) - 블랙박스 녹화 방식 ]
 - 주차장을 찾지 않고 무조건 비디오테이프 맨 뒤에 계속 이어 붙여서 씀 (Sequential I/O ➡️ 빛의 속도).
 - 데이터를 지울 때도 지우지 않고 맨 뒤에 "철수 삭제함"이라고 추가로 씀.
 - 나중에 청소부(Compaction)가 와서 테이프를 처음부터 보며 지워진 걸 정리해 새로 묶음.
```

## Ⅲ. 비교 및 연결
| 구분 | B-Tree (B+Tree) | LSM-Tree (Log-Structured Merge) |
|---|---|---|
| **디스크 I/O 방식** | In-place Update (덮어쓰기) ➡️ **Random I/O** | Append-Only (이어쓰기) ➡️ **Sequential I/O** |
| **최고 성능 영역**| **Read (조회 연산)** 극도로 빠름 | **Write (쓰기/수정 연산)** 빛의 속도 |
| **단점 (오버헤드)**| Page Split(트리 쪼개짐) 시 쓰기 지연 발생 | Read Amplification(읽기 증폭) 현상, Compaction 부하 |
| **적용 데이터베이스**| MySQL(InnoDB), Oracle, PostgreSQL | Cassandra, RocksDB, LevelDB, HBase |
---
## Ⅳ. 실무 적용 및 기술사 판단
- **블룸 필터(Bloom Filter)의 필수 적용**: LSM-Tree의 최대 약점인 "데이터를 읽을 때 수십 개의 SSTable 파일을 다 까봐야 한다"는 문제를 해결하기 위해 도입됨. 블룸 필터는 메모리상에서 "이 파일에는 철수라는 데이터가 **절대 없음(100% 확신)**"을 확률적으로 계산해 주어 헛고생(디스크 읽기)을 막아줌. LSM 기반 NoSQL을 설계할 때는 이 블룸 필터 메모리 튜닝이 핵심임.
- **Compaction 튜닝과 Write Stall**: 백그라운드에서 파일들을 병합(Compaction)하는 작업은 CPU와 디스크 I/O를 엄청나게 잡아먹음. 너무 잦은 데이터 쓰기로 인해 Compaction이 따라가지 못하면, 엔진이 쓰기 작업을 강제로 중단시켜 버리는 Write Stall 현상이 발생하므로, 기술사는 트래픽에 맞춰 Level / Size-Tiered Compaction 전략을 정교하게 세팅해야 함.
---
## Ⅴ. 기대효과 및 결론
- 모바일과 IoT 기기의 등장으로 인류가 만들어내는 데이터의 양(Write)이 소비하는 양(Read)을 압도하는 시대적 변화에 발맞춰, 스토리지 엔진의 패러다임을 바꾼 혁명적 자료구조임.
- 어떤 시스템에 B-Tree(RDB)를 쓰고 LSM-Tree(NoSQL)를 쓸 것인지 결정하는 것은, "우리 서비스가 읽기가 많냐(게시판), 쓰기가 많냐(로그/센서)"라는 본질적인 비즈니스 도메인 분석에서 출발해야 함.

### 👶 어린이를 위한 3줄 비유 설명
1. **B-Tree**는 '다이어리'예요. 10월 5일 칸을 정확히 찾아서 글씨를 예쁘게 쓰고, 틀리면 지우개로 빡빡 지우고 다시 써요. 읽을 땐 편한데 쓸 때 오래 걸리죠.
2. **LSM-Tree**는 '포스트잇'이에요. 날짜 찾을 필요 없이 빈 포스트잇에 막 갈겨써서 책상에 팍팍 붙여요! 쓰는 건 1초면 되죠 (Append-only).
3. 책상에 포스트잇이 너무 많아져서 나중에 읽기 힘들어지면, 주말에 한 번 싹 모아서 다이어리에 예쁘게 옮겨 적는 정리 작업(Compaction)을 한답니다!
