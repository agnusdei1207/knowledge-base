# 📖 【암기용】 개념 완전 이해

## 한눈에
- **개요**: **자동 페일오버(Auto Failover)**는 메인 시스템(운영 서버, 네트워크 등)에 장애가 발생했을 때, 관리자의 수동 개입 없이 대기 중인 예비 시스템(Standby)으로 서비스 권한과 트래픽을 즉시 넘겨 무중단 서비스를 유지하는 기술이다.
- **왜 필요한가**: 시스템을 2대로 구축(고가용성 설계)해 두었더라도, 1번이 죽었을 때 관리자가 경고를 보고 새벽에 출근해서 2번으로 트래픽을 넘기는 스크립트를 수동으로 실행한다면 수십 분~수 시간의 장애(Downtime)가 발생한다. 이 시간을 0(제로)에 가깝게 만들기 위함이다.
- **핵심 직관**: 야구 경기 중 주전 투수(운영 서버)가 갑자기 다치면 감독이 나가서 직접 교체하는 대신, 룰에 따라 불펜에 있던 구원 투수(대기 서버)가 시스템적으로 1초 만에 마운드에 올라와 경기를 이어가는 자동화된 메커니즘이다.

## 핵심 용어 정리

| 용어/표기 | 의미 | 비유·예 |
|:---|:---|:---|
| Failover (페일오버) | 주 시스템의 장애로 예비 시스템으로 서비스가 넘어가는 것 | 비상 발전기 가동 (주 전력 끊길 시) |
| Failback (페일백) | 장애가 난 주 시스템을 수리한 후, 임시 가동 중이던 예비 시스템에서 다시 주 시스템으로 서비스를 원상 복구하는 것 | 주 전력 복구 시 발전기를 끄고 본선으로 복귀 |
| Heartbeat (하트비트) | 메인 시스템이 정상 작동 중임을 알리기 위해 주고받는 주기적 신호 | "나 아직 살아있어" (규칙적인 심장 박동) |
| VIP (Virtual IP, 가상 IP) | 클라이언트가 바라보는 단일 IP 주소. 장애 시 이 IP가 대기 서버로 넘겨진다 | 대표 전화번호 (받는 직원의 직통번호가 바뀌어도 대표번호는 같음) |

## 깊이 이해
- **배경·문제의식**: 클라우드 인프라와 컨테이너 환경에서는 서버 생성이 매우 쉽다. 하지만 IP 주소가 바뀌거나 데이터베이스 커넥션이 끊어지면 클라이언트 애플리케이션은 장애를 인지하고 오류를 뿜는다. 따라서 클라이언트가 알아채기 전에 **백그라운드에서 노드 전환이 완전히 이루어져야 한다.**
- **작동 원리**:
  1. 감시 노드(또는 클러스터 소프트웨어)가 Active 장비와 주기적으로 Heartbeat를 주고받는다.
  2. Heartbeat가 특정 시간(예: 3초 내 3회 실패) 오지 않으면 해당 노드를 Death로 판단한다.
  3. Standby 노드를 Active로 승격(Promotion)시킨다.
  4. Active 노드가 쥐고 있던 **가상 IP(VIP) 주소**의 MAC 주소 테이블(ARP)을 갱신하여 뺏어오고(Takeover), 공용 스토리지 권한도 가져와 서비스를 재개한다.
- **비유**: 은행 창구 직원이 갑자기 쓰러지면, 대기하던 다른 직원이 그 자리표(VIP)를 달고 손님 응대를 곧바로 이어받아 손님 줄이 끊기지 않게 하는 것이다.
- **흔한 오해·주의점**: 자동 페일오버는 "만능 자동 복구"가 아니다. 가장 무서운 사고는 네트워크 일시 단절로 인해 1번 서버가 멀쩡히 살아있는데 Heartbeat만 끊기는 경우다. 이 경우 2번 서버가 자기도 마스터라고 선언해 **두 명의 마스터가 데이터를 덮어쓰는 뇌사 상태(Split-Brain)**가 일어난다. 그래서 제3의 판단자(Quorum)가 필수다.

## 연결 개념
- 고가용성 설계 — Active-Active·Active-Standby (페일오버의 기반 아키텍처)
- 단일 장애점 SPOF 제거 (자동 페일오버의 궁극적 목표)
- 쿼럼 알고리즘 (Quorum, 스플릿 브레인 방지 원리)

# 📝 【답안용】 시험 답안 템플릿

## 핵심 인사이트 (3줄 요약)

> 1. **본질**: 자동 페일오버는 장애 발생 시 관리자 개입 없이 헬스 체크, 역할 승격(Promotion), 자원 인계(Takeover) 과정을 통해 대기 노드로 트래픽을 자동 전환하는 고가용성 메커니즘이다.
> 2. **가치**: MTTR(평균 복구 시간)을 극단적으로 단축하여 RTO(목표 복구 시간) 제로화에 근접하고 연속적인 고객 경험과 SLA 요구사항을 충족시킨다.
> 3. **판단 포인트**: 전환 속도와 더불어, 네트워크 단절 시 양쪽이 마스터로 동작하여 데이터를 훼손하는 스플릿 브레인(Split-Brain) 방지 장치(Quorum, Fencing) 설계가 성공의 핵심이다.

## 출제 의도 및 답안 포인트

| 출제 의도 | 반드시 짚을 핵심 | 감점 회피 포인트 |
|:---|:---|:---|
| 무중단 서비스 복구 메커니즘 원리 이해 | Heartbeat 감시 -> VIP 전환(Takeover) -> 상태 승격 등 세부 절차 기술 | 그냥 "죽으면 넘겨준다" 수준의 단순 서술 |
| 페일오버 발생 시의 치명적 리스크 대처 역량 | Split-Brain 현상과 Fencing, Quorum(과반수) 합의 아키텍처 적용 | 기능 자체의 편리함만 강조하고 데이터 정합성 리스크 누락 |

> 요약: 장애 감지(Heartbeat)와 자원 강탈(VIP Takeover)의 기술적 프로세스를 명시하고, 오동작(스플릿 브레인) 방지 설계안을 필수적으로 제시해야 한다.

## Ⅰ. 개요 및 필요성

- 개요: 자동 페일오버(Auto Failover)는 주 시스템(Primary)의 비정상 종료 시 대기 시스템(Secondary/Standby)으로 서비스 제어권과 트래픽을 자동으로 인계하는 무중단 전환 기술임
- 배경: 야간/휴일 장애 발생 시 관리자 수동 개입 방식(Manual Failover)은 필연적인 복구 지연 타임을 유발하여 비즈니스 손실 초래
- 필요성: 시스템 이중화(HA) 아키텍처의 효용성을 극대화하고, 사용자 세션 단절을 최소화하며 99.99% 이상의 고가용성을 유지하기 위해 자동화된 전환 메커니즘이 필수적임

## Ⅱ. 구조 및 구성요소

```text
[자동 페일오버 시스템의 전환 논리 구조]
클라이언트 요청 -> 가상 IP (VIP: 10.0.0.1) --(MAC 라우팅 변경)--> [장애 감지 후 트래픽 인계]
                      |                                       |
           [Active 노드 (장애 발생!)]                    [Standby 노드 (정상)]
                      |          <- Heartbeat 끊김 ->         |
                 [Quorum(감시/중재자)] -> "Active Down 선언" -> Standby를 Active로 승격
```

| 구성요소 | 역할 | 특이사항 |
|:---|:---|:---|
| Heartbeat / Health Check | 노드 간 상태 감시 신호 (TCP/UDP Ping, 상태 쿼리) | 네트워크 단절 시 오탐지 가능성 존재 |
| VIP (가상 IP 주소) | 클라이언트가 접근하는 고정 엔드포인트 IP | 페일오버 시 대기 서버로 바인딩(ARP 갱신) |
| 클러스터 매니저 | 상태 감시 및 승격(Promotion) 로직 수행 SW | Pacemaker, Keepalived, DB 고유 클러스터 SW |
| Quorum / Tie-breaker | 노드 간 단절 시 누가 진짜 마스터인지 결정하는 제3 감시자 | 과반수(Majority) 투표 알고리즘 사용 |

> 요약: 클러스터 매니저가 하트비트로 장애를 감지하면, 쿼럼 합의를 거쳐 대기 노드를 활성 노드로 승격하고 가상 IP(VIP)를 이전한다.

---

## Ⅲ. 동작원리 및 흐름도

```text
정상 감시(Heartbeat) -> 타임아웃 장애 탐지 -> Split-Brain 방어 판정(Quorum) -> VIP Takeover -> Failback(옵션)
```

- 1단계 [장애 인지]: Active 노드의 시스템 크래시, 포트 데드 등으로 설정된 임계시간(예: 3초) 내 Heartbeat 신호 단절
- 2단계 [격리 및 합의]: 클러스터 노드 간 통신 단절 시 Quorum 서버 과반수 합의로 기존 Active 노드를 좀비로 판정하고 스토리지 접근 차단(Fencing)
- 3단계 [역할 승격]: Standby 노드가 데이터 동기화 최신성을 확인한 후 Primary(마스터) 역할로 스스로 상태 승격(Promotion)
- 4단계 [서비스 인계]: 클라이언트 단절을 막기 위해 가상 IP(VIP) 주소에 대한 Gratuitous ARP(GARP)를 네트워크에 브로드캐스트하여 트래픽 탈취

> 요약: 신호 단절 인지 시 스플릿 브레인 검증(과반 합의)을 먼저 거치고, 대기 서버를 주 서버로 승격한 뒤 네트워크 IP 맵핑을 갱신해 트래픽을 넘겨받는다.

## Ⅳ. 특징

- 복구 시간(RTO) 최적화: 관리자가 인지하기 전에 시스템 레벨에서 수 초~수 분 내 스위칭을 완료하여 사용자 체감 서비스 중단을 없앰
- 네트워크 의존성: 노드 장애가 아닌 단순 스위치/네트워크 단절에도 페일오버가 발동(False Positive)될 수 있어 정밀한 헬스체크 설계 요구
- 상태 유지 한계점: 페일오버 발생 찰나의 미응답 트랜잭션과 메모리 캐시는 유실될 수 있어, 클라이언트단의 재시도(Retry) 로직과 결합 필수

> 요약: 복구 시간을 비약적으로 단축하지만 네트워크 오진단에 취약하며 클라이언트 레벨의 보완 로직이 함께 필요하다.

## Ⅴ. 심화 비교 및 적용 판단

| 비교 축 | 수동 페일오버 (Manual Failover) | 자동 페일오버 (Auto Failover) | 선택 기준 |
|:---|:---|:---|:---|
| 전환 속도 (RTO) | 수십 분 ~ 수 시간 (관리자 개입) | 수 초 ~ 수 분 이내 (시스템 자체 판단) | 서비스 SLA 요구 수준 |
| 데이터 정합성 리스크 | 관리자가 양쪽 상태 확인 후 수동 제어 (안전) | 네트워크 오작동 시 Split-Brain으로 데이터 변조 | 과반수 Quorum 아키텍처 투자 여부 |
| 운영/복잡도 | 시스템 설계 단순, 장애 복구 후 수동 Failback | VIP 이전, Fencing 스크립트 등 복잡한 설정 필요 | 운영 인력의 24/365 모니터링 여력 |

> 요약: 자동 페일오버는 RTO 단축에 압도적 강점이 있으나, 스플릿 브레인에 의한 데이터 오염 리스크를 억제하는 복잡한 중재 기술 투자가 수반되어야 한다.

**리스크·대응:**
- 스플릿 브레인(Split-Brain): 하트비트용 LAN선만 단절되고 양쪽 서버는 정상일 때 둘 다 마스터로 승격하여 DB 쓰기 충돌 발생 → 3대 이상의 홀수 노드로 Quorum(과반 합의 투표) 구성 또는 STONITH(기존 마스터 장비 전원 강제 차단) 기술 적용
- 플래핑(Flapping) 현상: 네트워크 불안정으로 페일오버와 페일백이 초 단위로 무한 반복되어 서비스 전면 마비 → 페일백(원상복구)은 자동이 아닌 관리자 수동 승인(Manual) 모드로 설정 운영

## Ⅵ. 실무 적용 및 결론

**적용 방안 3개:**
1. **데이터베이스 무중단 전환 (MHA, Redis Sentinel)**: RDBMS 환경에서 마스터 장애 시 슬레이브 중 데이터 트랜잭션 번호(GTID)가 가장 최신인 노드를 자동으로 찾아 마스터로 승격시키고 가상 IP 맵핑 갱신
2. **클라우드 네이티브 환경 쿠버네티스 자가 치유(Self-Healing)**: 물리적 VIP 이전을 쓰지 않고, 쿠버네티스 레플리카셋(ReplicaSet) 기반 헬스체크(Liveness Probe) 실패 시 문제 파드(Pod)를 강제 종료하고 타 노드에 새 파드를 자동 스케줄링(재배치)
3. **글로벌 재해 복구(GSLB 페일오버)**: 단일 데이터센터 화재 시 DNS 기반의 글로벌 로드 밸런싱(GSLB) 헬스체크 연동을 통해, 접속 IP 쿼리를 재해 복구(DR) 센터 IP 주소로 실시간 우회 응답 처리

**결론:**
- 기술사 판단: 무분별한 자동 페일오버 구성은 네트워크 단절 시 최악의 데이터 변조(Split-Brain)를 부르므로, 헬스 체크 다중화 및 확실한 Fencing(강제 차단) 방안이 없는 단순 Active-Standby 구조에서는 수동 전환이 더 안전할 수 있음
- 향후 방향: 레거시 환경의 L2 VIP 맵핑 이전 방식에서 벗어나, 서비스 디스커버리(Service Discovery)와 클라이언트 사이드 로드밸런싱 중심의 클라우드 네이티브 라우팅 페일오버 방식으로 전환되고 있음
