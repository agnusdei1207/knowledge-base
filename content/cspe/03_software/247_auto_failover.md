# 📖 【암기용】 개념 완전 이해

> 목적: 자동 페일오버를 처음 봐도 완전히 이해하게 만든다. 시험 답안 양식이 아니라, 이해를 위한 친절한 설명이다.

## 한눈에
- **개요**: 자동 페일오버(Auto Failover)는 **고가용성(HA)** 구조에서 장애 감지(Failure Detection) 이후 사람의 개입 없이 대체 노드로 트래픽과 쓰기 권한을 자동으로 넘기는 전환 메커니즘이다.
- **왜 필요한가**: 대체 자원(스탠바이 노드, 여분 리전)이 있어도 사람이 장애를 확인하고 전환 명령을 내리는 방식이면 판단·연락에 걸리는 시간만큼 RTO가 길어지고, 특히 야간·휴일에는 대응이 느려지거나 누락된다. 자동 페일오버는 장애 판정과 전환 실행을 미리 정한 규칙으로 표준화해 이 시간을 없앤다.
- **핵심 직관**: 주전 선수가 쓰러지면 심판의 수신호를 기다리지 않고, 미리 정해둔 규칙에 따라 예비 선수가 스스로 들어오는 자동 교체 시스템이다.

## 핵심 용어 정리 (내부에 등장하는 것들)

| 용어 | 의미 | 비유 |
|:---|:---|:---|
| 고가용성(HA) | 자동 페일오버가 달성 수단이 되는 상위 목표(245) | 이 개념이 섬기는 목적지 |
| 헬스체크(Health Check) | 노드 상태를 주기적으로 확인하는 절차 — 장애 판정의 입력 신호 | 정기 맥박 체크 |
| Failure Detector(장애 판정기) | 헬스체크 결과를 모아 "장애로 확정"할지 판정하는 로직(임계값 기반) | 화재감지기의 판정 회로 |
| Quorum(정족수) | 과반수 노드가 동의해야 장애·승격을 확정하는 규칙 — 오탐·split-brain 방지 | 이사회 의결 정족수 |
| Fencing/STONITH | 장애로 판정된 기존 주 노드의 쓰기 권한을 강제로 차단하는 조치(Shoot The Other Node In The Head) | 고장난 기계의 전원 플러그를 강제로 뽑음 |
| Leader Election(리더 선출) | 살아있는 노드들 사이에서 새 주 노드를 합의로 뽑는 절차 | 회의에서 새 팀장을 투표로 뽑음 |
| Split-brain | fencing 없이 승격이 일어나 옛 주 노드와 새 주 노드가 동시에 존재하는 상태(245 참고) | 지휘관 두 명이 동시에 명령 |
| Failback(원복) | 장애가 복구된 후 원래 주 노드로 다시 되돌리는 절차 | 도로 공사가 끝나 원래 차선으로 복귀 |

## 깊이 이해

### 왜 "자동"이어야 하는가 (배경)
고가용성 구성에는 대체 자원이 이미 준비돼 있다. 그런데 전환을 사람이 판단해서 실행하면, 장애 인지→담당자 호출→상황 확인→전환 명령이라는 절차 각각에 수 분~수십 분이 걸린다. SLA 99.99%는 월 4.3분만 허용하는데(245 참고), 사람이 개입하는 순간 이 예산을 이미 넘긴다. 그래서 목표 가용성이 높을수록 감지부터 전환까지를 미리 정한 규칙으로 자동화해야 한다.

### 동작 원리 — 4단계와 그 사이의 순서가 중요한 이유
1. **감지(Health Check)**: 노드·DB·애플리케이션 상태를 주기적으로 확인한다.
2. **판정(Failure Detector + Quorum)**: 임계값(예: 5초 간격 3회 연속 실패)을 넘으면 장애를 의심하되, quorum(과반수 동의)으로 확정한다 — 네트워크 순간 지연을 장애로 오판(false positive)하지 않기 위해서다.
3. **차단(Fencing)**: 새 노드를 승격하기 **전에** 기존 주 노드의 쓰기 권한부터 강제로 차단한다. 이 순서를 지키지 않고 승격을 먼저 하면, 네트워크가 잠시 회복된 기존 주 노드가 여전히 쓰기를 계속해 새 주 노드와 동시에 쓰는 split-brain이 발생한다.
4. **승격과 라우팅(Promotion + Traffic Switch)**: 대체 노드를 주 노드로 올리고 DNS/LB/route를 전환한다.

이 순서 — 판정 후 반드시 차단이 승격보다 먼저 — 가 자동 페일오버 설계에서 가장 자주 틀리는 지점이다.

### RTO 60초는 어떻게 쪼개지는가 — 워크드 예제
목표 RTO 60초를 구성 요소별로 분해할 수 있다.
- 헬스체크 간격 5초 × 3회 연속 실패 확인 = **15초** (판정 소요)
- quorum 확인(3노드 중 2노드 동의 수집) = **약 5초**
- 기존 주 노드 fencing(쓰기 권한 차단, 네트워크 격리) = **약 10초**
- 대체 노드 승격(리더 선출, standby → primary 전환) = **약 15초**
- DNS/LB 전환 및 전파(TTL 30초 설정 시 클라이언트 반영까지) = **약 15초**
- 합계 ≈ **60초**

각 단계에 시간 예산을 배분해야 "RTO 60초"라는 목표가 실현 가능한지 검증할 수 있다. 판정 단계를 너무 짧게(예: 1회 실패로 즉시 판정) 잡으면 RTO는 줄지만 오탐(false failover)이 늘어난다 — RTO와 오탐률은 트레이드오프 관계다.

### 비유
철도 신호 시스템이 선로 고장을 감지하면 그 구간을 자동으로 차단하고 열차를 우회 선로로 보내는 것과 같다. 여기서 중요한 것은, 신호가 틀리면(오탐) 정상 선로의 열차까지 멈춰 세우는 큰 사고로 이어지므로, 판정 조건(quorum)을 엄격하게 걸어야 한다는 점이다 — 빠른 전환보다 정확한 판정이 우선이다.

### 흔한 오해·주의점
자동 전환은 항상 이득이 아니다. 네트워크 순간 지연이나 GC 일시정지를 장애로 오판(false positive)하면, 멀쩡한 노드를 죽이고 불필요한 전환과 데이터 충돌(split-brain)을 일으킬 수 있다. 그래서 판정에는 유예 시간(grace period)과 synthetic transaction(단순 ping이 아니라 실제 애플리케이션 동작 확인)을 함께 쓴다. 또한 전환 후 원래 노드가 복구되면 즉시 원복(failback)하지 않고, 데이터 재동기화가 끝난 뒤 계획된 시점에 원복해야 한다 — 즉시 원복하면 재동기화 중인 노드로 트래픽이 다시 몰려 두 번째 장애가 날 수 있다.

## 연결 개념
- High Availability — 자동 페일오버가 달성 수단이 되는 상위 목표(245)
- SPOF Elimination — 페일오버가 전환할 "대체 경로"를 미리 준비해두는 작업(246)
- Split-brain — fencing 없는 자동 전환이 일으키는 대표적 위험(245 참고)

# 📝 【답안용】 시험 답안 템플릿

> 목적: 시험장에서 25분에 그대로 쓰는 답안 양식. 작성방식(추상표현 금지·수치·도식·문제유형 전환)을 엄격히 지킨다.
> 핵심: 자동 페일오버 답안은 감지 정확도, 전환 시간, 데이터 정합성, 원복 절차를 함께 다뤄야 한다.

> 1. **본질**: Auto Failover는 장애 감지 후 대체 자원으로 트래픽과 쓰기 권한을 자동 이전하는 복구 메커니즘이다.
> 2. **가치**: 수동 판단 시간을 제거해 RTO를 30~120초 수준으로 줄이고 야간 장애 대응 편차를 줄인다.
> 3. **판단 포인트**: health check 오탐, quorum, fencing, replication lag, failback 절차가 설계 품질을 결정한다.

## Ⅰ. 개요 및 필요성

- 개요: 자동 페일오버는 장애 감지 후 대체 자원 전환 기능이다.
- 배경: 서비스 가용성 목표가 높아지면 운영자 수동 판단만으로 RTO 목표를 맞추기 어렵다.
- 필요성: 장애 감지 임계값, 전환 시간, 데이터 정합성 리스크를 함께 설계해야 한다.

---

## Ⅱ. 구조 및 구성요소

```text
Health Check -> Failure Detector -> Quorum/Fencing
             -> Promotion -> Traffic Switch -> Validation
```

| 구성요소 | 역할 | 특이사항 |
|:---|:---|:---|
| Health Check | 노드·DB·애플리케이션 상태 확인 | TCP, HTTP, synthetic |
| Failure Detector | 장애 판정과 임계값 적용 | 5초 간격, 3회 실패 |
| Quorum/Fencing | 이중 primary 방지 | 과반수, lease, STONITH |
| Traffic Switch | LB, DNS, route 전환 | TTL 30초 이하 권장 |

> 요약: 자동 페일오버는 감지, 판정, 승격, 라우팅, 검증 요소가 순서대로 작동해야 한다.

---

## Ⅲ. 동작원리 및 흐름도

```text
상태 점검 -> 장애 임계값 초과 -> 기존 노드 차단
-> 대체 노드 승격 -> 트래픽 전환 -> 복구 확인
```

| 단계 | 처리 내용 | 검증 기준 |
|:---:|:---|:---|
| 1 | health check와 synthetic test 수집 | 오탐률 1% 이하 |
| 2 | quorum으로 장애 확정 | 3노드 중 2노드 동의 |
| 3 | 기존 primary fencing 후 standby 승격 | dual primary 0건 |
| 4 | LB/DNS 전환 후 서비스 확인 | RTO 60초 이하 |

> 요약: 자동 페일오버는 기존 노드 차단을 먼저 수행한 뒤 승격과 라우팅을 진행해야 데이터 충돌을 막는다.

## Ⅴ. 심화 비교 및 적용 판단

| 구분 | 기존/대안 | 본 키워드 | 선택 기준 |
|:---|:---|:---|:---|
| 판정 | 운영자 확인 | 임계값·quorum 자동 판정 | RTO 5분 이하 요구 시 |
| 전환 | 수동 DNS/LB 변경 | controller 기반 route 변경 | 24x7 무중단 요구 시 |
| 원복 | 즉시 failback | 동기화 완료 후 planned failback | 데이터 재동기화 필요 시 |

> 요약: RTO가 짧고 장애 대응 시간이 업무 손실로 이어지는 시스템은 자동 페일오버를 우선 적용한다.

| 리스크 | 원인 | 대응 방안 | 확인 지표 |
|:---|:---|:---|:---|
| 오탐 전환 | 네트워크 지연, health check 단순성 | synthetic check, grace period | false failover 1% 이하 |
| Split-brain | fencing 누락 | lease, STONITH, write lock | dual primary 0건 |
| 원복 실패 | 데이터 재동기화 누락 | planned failback 절차 | failback 성공률 95% 이상 |

> 요약: 자동 페일오버의 핵심 통제는 오탐 억제, fencing, 원복 검증이다.

| 점검 항목 | 목표 기준 | 측정 방법 |
|:---|:---|:---|
| 전환 시간 | RTO 60초 이하 | 장애 주입 timestamp |
| 판정 품질 | false failover 1% 이하 | incident review |
| 데이터 정합성 | replication lag 1초 이하 | DB metric, checksum |

> 요약: 전환 시간만 보지 말고 판정 품질과 데이터 정합성을 함께 측정해야 한다.

## Ⅵ. 실무 적용 및 결론

**적용 방안 3개 (필수 — 단계별 또는 항목별):**
1. health check를 TCP가 아니라 `/ready`와 synthetic transaction으로 구성해 애플리케이션 장애를 판정
2. DB failover에는 quorum 3노드, fencing, replication lag 1초 이하 조건을 적용해 dual primary를 방지
3. 월 1회 장애 주입으로 failover 60초 이하, failback 성공률 95% 이상을 측정

**결론 (2줄):**
- 기술사 판단: RTO 5분 이하 업무는 자동 페일오버가 필요하나, 데이터 쓰기 시스템은 fencing 없는 자동 승격을 금지한다
- 향후 방향: Kubernetes operator, managed DB, service mesh가 자동 전환을 제공하더라도 업무별 검증 지표는 별도로 운영해야 한다
