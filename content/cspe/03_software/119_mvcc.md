## Ⅰ. 개요
- **정의**: 데이터의 여러 버전을 유지하여 읽기와 쓰기가 서로 차단하지 않는 동시성 제어 기법임
- **배경/필요성**: 잠금 기반 제어(118 참조)는 읽기도 쓰기를 대기시켜 처리량이 저하됨
- **비유**: 도서관에서 원본을 잠그지 않고 복사본을 배포하여 동시 열람을 허용하는 것임

| 출제 의도 | 반드시 짚을 핵심 | 감점 회피 포인트 |
|:---|:---|:---|
| 잠금 없는 동시 읽기 원리 | 스냅샷 격리·버전 체인 구조 | Phantom Read 등 격리 수준별 한계 |

> 요약: 다중 버전 유지로 읽기-쓰기 비차단을 실현하는 동시성 제어 기법임

## Ⅱ. 구성요소
```text
MVCC
 +-- Version Chain ---- 행별 과거 버전 연결 리스트
 +-- Snapshot --------- 트랜잭션 시작 시점 가시 범위
 +-- Undo Segment ----- 이전 버전 저장 공간
 +-- Visibility Check -- 버전 유효성 판단 규칙
```

| 구성요소 | 설명 | 비유 |
|:---|:---|:---|
| Version Chain | 행의 갱신 이력을 링크드 리스트로 연결 | 문서 수정 이력 |
| Snapshot | 트랜잭션 시작 시점의 일관된 데이터 뷰 제공 | 특정 시점 사진 |
| Visibility Check | 트랜잭션 ID 비교로 어떤 버전을 읽을지 결정 | 유효기간 확인 |

> 요약: 버전 체인·스냅샷·가시성 검사가 MVCC의 핵심 메커니즘임

## Ⅲ. 절차
```text
읽기 요청 --> 스냅샷 생성 --> 가시 버전 탐색 --> 결과 반환
```
- 1단계: 트랜잭션 시작 시 현재 활성 트랜잭션 목록 기반 스냅샷 생성
- 2단계: 읽기 요청 시 대상 행의 버전 체인을 탐색
- 3단계: Visibility Check로 스냅샷에 유효한 버전(커밋 완료·자기보다 이전)을 선택
- 4단계: 유효 버전 데이터를 반환(쓰기 트랜잭션과 무관하게 비차단)

> 요약: 스냅샷 기반 가시성 판단으로 잠금 없이 일관된 읽기를 수행함

## Ⅳ. 문제점
- 버전 누적: 오래된 버전이 정리되지 않으면 Undo 세그먼트 비대화
- Write Skew: Snapshot Isolation에서 두 트랜잭션이 서로 다른 행을 갱신 시 논리적 불일치
- Vacuum 부하: 만료 버전 정리(Vacuum/Purge) 시 I/O 부하 발생

> 요약: 버전 비대화, Write Skew, 정리 부하가 MVCC의 운용 과제임

## Ⅴ. 개선방안
1. 단기: 주기적 Vacuum/Purge 스케줄링으로 버전 누적 억제
2. 중기: Write Skew 방지를 위해 Serializable Snapshot Isolation(SSI) 적용
3. 장기: 인라인 버전 관리(Append-Only 스토리지) 도입으로 Vacuum 부하 제거

> 요약: 정리 자동화, SSI 적용, 스토리지 구조 개선으로 MVCC를 고도화함

## Ⅵ. 전망
- 발전 방향: 분산 DB(Spanner, CockroachDB)에서 글로벌 MVCC 적용 확대
- 기술사적 판단: 읽기 중심 워크로드에서 잠금 대비 처리량 우위가 검증됨
- 기술사 제언: MVCC 격리 수준의 한계를 이해하고 업무 요건에 맞게 선택할 필요
