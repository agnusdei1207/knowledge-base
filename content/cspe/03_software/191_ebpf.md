## Ⅰ. 개요
- **정의**: 커널 소스 변경 없이 커널 공간에서 사용자 정의 프로그램을 안전하게 실행하는 기술
- **배경/필요성**: 커널 모듈 방식은 충돌·보안 위험이 크므로 샌드박스 기반 커널 확장 메커니즘이 필요함
- **비유**: 커널이라는 공항 활주로에 전용 검문소(Verifier)를 거친 드론만 진입시키는 구조

| 출제 의도 | 반드시 짚을 핵심 | 감점 회피 포인트 |
|:---|:---|:---|
| 커널 확장의 안전성 원리 | Verifier·JIT·Map 삼각 구조 | BPF와 eBPF 차이 명시 필요 |

> 요약: 커널 재컴파일 없이 관찰·네트워크·보안 기능을 안전하게 삽입하는 인커널 VM 기술임

## Ⅱ. 구성요소
```text
User Space        Kernel Space
+-----------+     +-------------+
| BPF Prog  | --> | Verifier    |
| (C/Rust)  |     +------+------+
+-----------+            |
                   +-----v-----+
                   | JIT Comp  |
                   +-----+-----+
                         |
                   +-----v-----+     +----------+
                   | BPF VM    |<--->| BPF Map  |
                   +-----------+     +----------+
```

| 구성요소 | 설명 | 비유 |
|:---|:---|:---|
| Verifier | 프로그램 로드 시 무한루프·메모리 초과 등 안전성 정적 검증 | 공항 보안 검색대 |
| JIT Compiler | 바이트코드를 네이티브 기계어로 변환하여 실행 성능 확보 | 동시통역사 |
| BPF Map | 커널-유저 간 데이터 공유용 키-값 저장소 | 공유 게시판 |
| Hook Point | kprobe·tracepoint·XDP 등 프로그램 부착 지점 | 감시카메라 설치 위치 |

> 요약: Verifier 검증 후 JIT 컴파일된 프로그램이 Hook Point에서 실행되며 Map으로 데이터를 교환함

## Ⅲ. 절차
```text
작성 --> 컴파일 --> 검증 --> 부착/실행
```
- 1단계: C/Rust로 BPF 프로그램 작성 후 LLVM으로 바이트코드 컴파일
- 2단계: `bpf()` 시스콜로 커널에 로드, Verifier가 안전성 정적 분석 수행
- 3단계: JIT 컴파일러가 바이트코드를 네이티브 코드로 변환
- 4단계: 지정 Hook Point(XDP·kprobe 등)에 부착되어 이벤트 발생 시 실행

> 요약: 작성-검증-컴파일-부착의 4단계를 거쳐 커널 내부에서 안전하게 동작함

## Ⅳ. 문제점
- 디버깅 난이도: Verifier 거부 메시지가 난해하여 개발 생산성 저하
- 커널 버전 의존: BTF·CO-RE 미지원 구버전에서 이식성 확보 곤란
- 권한 요구: CAP_BPF 등 특권이 필요하여 비특권 환경 적용 제한

> 요약: 디버깅·이식성·권한 측면에서 진입 장벽이 존재함

## Ⅴ. 개선방안
1. 단기: libbpf·bpftool 등 표준 도구 체계화로 디버깅 경험 개선
2. 중기: CO-RE(Compile Once Run Everywhere) 확산으로 커널 버전 간 이식성 확보
3. 장기: Unprivileged eBPF 안전 모델 확립으로 비특권 사용자 접근 허용

> 요약: 도구 표준화-이식성 확대-권한 모델 개선 순으로 진입 장벽을 낮추는 방향임

## Ⅵ. 전망
- 발전 방향: Observability·네트워킹·보안 전 영역에서 커널 모듈 대체 가속
- 기술사적 판단: 서비스메시(Cilium) 등 클라우드 네이티브 인프라의 핵심 기반 기술로 정착 중
- 기술사 제언: eBPF 기반 관측·보안 아키텍처 설계 역량 확보 필요
