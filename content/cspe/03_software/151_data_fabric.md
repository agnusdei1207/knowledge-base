# 📖 【암기용】 개념 완전 이해

> 목적: 데이터 패브릭을 처음 보는 사람도 완벽히 이해하게 만든다. 시험 답안 양식이 아니라, 이해를 위한 친절한 설명이다.

## 한눈에
- **개요**: 데이터 패브릭은 여러 시스템에 흩어진 데이터를 **메타데이터**와 **자동화**로 연결해, 물리적으로 옮기지 않고도 검색·접근·거버넌스를 하나의 흐름으로 제공하는 **데이터 통합 아키텍처**다.
- **왜 필요한가**: 온프레미스 DB, 클라우드 DW, 데이터 레이크, SaaS로 데이터가 흩어지면 사용자는 매번 "이 데이터가 어디 있고 누가 권한을 주는지"부터 알아내야 한다. 데이터 패브릭은 위치 차이를 메타데이터 뒤로 숨긴다.
- **핵심 직관**: 여러 창고를 하나의 물류망처럼 연결해, 사용자는 물건이 어느 창고에 있는지 몰라도 주문·추적 규칙만 따르면 물건을 받는 구조다.

## 핵심 용어 정리 (내부에 등장하는 것들)

| 용어 | 의미 | 비유 |
|:---|:---|:---|
| 데이터 통합 아키텍처 | 데이터 패브릭이 속하는 상위 범주 — 흩어진 데이터를 하나의 접근 체계로 묶는 설계 | 통합 물류망 |
| 메타데이터(기술/업무/운영) | 기술: 스키마·타입 / 업무: 용어·의미 / 운영: 접근이력·품질점수 — 패브릭이 다루는 3종 정보 | 상품표(기술)+카테고리(업무)+판매이력(운영) |
| 데이터 카탈로그 | 메타데이터를 검색 가능하게 정리한 하위 구성요소(152 데이터 카탈로그와 직결) | 도서관 검색 시스템 |
| 데이터 계보(Lineage) | 데이터가 어디서 와서 어떻게 변환되어 어디로 쓰였는지 추적하는 정보 | 제품 이력 추적표 |
| 데이터 가상화(Data Virtualization) | 데이터를 복제하지 않고 질의 시점에 원천에서 직접 읽어와 통합 뷰를 제공하는 기술 | 여러 창고 재고를 한 화면에서 실시간 조회 |
| 정책 엔진(Policy Engine) | RBAC/ABAC, PII 마스킹 같은 접근 규칙을 자동 적용하는 구성요소 | 출입 게이트 자동 검문 |
| 오케스트레이션 계층 | 배치·스트리밍·가상화 중 지연 요구에 맞는 이동 경로를 선택·실행 | 배송수단(트럭/항공/직배송) 선택 |

## 깊이 이해

### 배경 — ETL 파이프라인 폭발(N x M) 문제
- 시스템이 N개, 소비 대상이 M개면 점대점 ETL 파이프라인은 이론상 N×M개까지 늘어날 수 있다. 시스템 하나가 추가될 때마다 연결을 새로 짜야 하는 구조다. 데이터 패브릭은 각 시스템을 공통 메타데이터 계층에 한 번만 연결하고 소비자는 그 계층을 통해 접근하게 해, 연결 수를 N+M 수준으로 줄인다.

### 작동 원리 4단계
- **① 수집(harvest)**: 커넥터가 DB·Lake·SaaS의 스키마와 사용 로그를 자동 수집한다.
- **② 카탈로그/계보**: 수집된 기술 메타데이터에 업무 용어를 연결하고, 변환 이력(계보)을 추적한다.
- **③ 정책 적용**: RBAC/ABAC와 PII 마스킹을 정책 엔진이 자동 적용한다.
- **④ 접근 경로 선택**: 지연 허용치에 따라 가상화(실시간 조회)·ETL/ELT(배치 적재)·스트리밍(이벤트 단위) 중 하나로 실제 데이터를 이동시킨다.

### 데이터 가상화 vs 물리적 복제 — 언제 어떤 경로인가
- 실시간 조회(p95 3초 이내)가 필요하면 가상화(예: Trino federated query가 여러 원천에 쿼리를 push-down)로 원천에서 바로 읽는다.
- 조회가 반복적이고 무겁거나 원천 부하를 줄여야 하면 ELT로 물리 적재해 캐시처럼 쓴다.
- 1분 이내 최신성이 필요한 이벤트는 Kafka 같은 스트리밍 경로로 흘려보낸다.
- **수치 예**: 고객 360 분석에서 CRM, 결제 DB, 로그 레이크, 콜센터 SaaS를 매번 전체 복제하는 대신, 카탈로그·계보·품질 점수 95점 이상인 자산만 가상화로 연결하면 별도 복제 파이프라인 없이 통합 조회가 가능하다.

### 언제 데이터 패브릭이 필요한가 (판별원리)
- 데이터 자산이 500개를 넘고 소유자가 여러 팀에 흩어져 있으며, 규제상 원본을 특정 지역·시스템 밖으로 이동시키기 어려운 경우 데이터 패브릭이 적합하다. 자산 수가 적고 단일 저장소로 충분하면 레이크하우스 하나로 끝내는 게 낫다.

### 비유와 흔한 오해
- **비유**: 도시 지하철 노선도 — 승객(사용자)은 차량기지(원천 시스템) 위치를 몰라도 환승 규칙과 도착 정보(메타데이터)만 보고 목적지에 간다.
- **오해**: 데이터 패브릭은 특정 제품명이 아니라 아키텍처 패턴이다. 카탈로그 도구 하나만 도입하거나 반대로 모든 데이터를 한 저장소로 복제하는 것은 패브릭의 일부만 구현한 것이지 전체가 아니다.

## 연결 개념
- 데이터 카탈로그: 데이터 패브릭의 검색·의미 메타데이터를 제공하는 핵심 구성요소
- 데이터 메시: 조직·책임 구조 중심의 보완 개념 — 패브릭은 기술 자동화, 메시는 도메인 조직 책임에 초점
- 데이터 거버넌스: 정책·권한·품질 기준을 조직적으로 통제하는 상위 체계

> 2. **가치**: 데이터 복제 중심 통합을 줄이고, 검색 시간, 권한 검토 시간, 계보 추적 시간을 SLA 지표로 관리함.

## Ⅰ. 개요 및 필요성

- 개요: 데이터 패브릭은 분산 데이터 통합 아키텍처임.
- 배경: 기업 데이터는 DW, Lake, SaaS, 운영 DB로 분산되어 검색, 접근권한, 품질 확인 시간이 증가한다.
- 필요성: 메타데이터 중심 연결 계층으로 데이터 위치 변경 시에도 분석, AI, 보고 체계의 접근 기준을 유지한다.

---

## Ⅱ. 구조 및 구성요소

```text
Source DB/SaaS/Lake -> Metadata Harvest -> Catalog/Lineage -> Policy Engine -> Access API/BI/AI
                                      +-> Quality Rule
                                      +-> Orchestration
```

| 구성요소 | 역할 | 특이사항 |
|:---|:---|:---|
| 메타데이터 수집 | 스키마, 소유자, 품질, 사용 이력 수집 | Apache Atlas, OpenMetadata 연계 |
| 카탈로그/계보 | 검색, 의미 연결, 변환 추적 제공 | 업무 용어와 SQL 계보 동시 관리 |
| 정책 엔진 | 권한, 마스킹, 보존기간 적용 | RBAC/ABAC, PII 태그 기반 |
| 접근 계층 | API, SQL, BI, AI 질의 연결 | 가상화 또는 물리 적재 선택 |

> 요약: 데이터 패브릭은 저장소가 아니라 메타데이터와 정책을 중심으로 데이터 접근 경로를 조정하는 계층형 구조임.

## Ⅲ. 동작원리 및 흐름도

```text
자산 등록 -> 메타데이터 수집 -> 품질/권한 태깅 -> 접근 경로 선택 -> 사용/계보 기록
```

| 단계 | 처리 내용 | 검증 기준 |
|:---:|:---|:---|
| 1 | 데이터 자산 등록 및 소유자 지정 | owner 100%, SLA 등급 부여 |
| 2 | 스키마, 태그, 사용 로그 수집 | 24시간 이내 카탈로그 반영 |
| 3 | PII, 품질, 보존 규칙 적용 | 마스킹 정책 누락 0건 |
| 4 | 가상화, ETL, 스트리밍 경로 선택 | p95 질의 3초 또는 배치 SLA 준수 |
| 5 | 사용 이력과 계보 자동 기록 | lineage coverage 90% 이상 |

> 요약: 데이터 패브릭은 등록, 수집, 정책 적용, 접근, 기록의 반복 루프로 데이터 활용과 통제를 함께 수행함.

> 요약: 주요 리스크는 메타데이터 부정확, 권한 우회, 질의 지연이며 자동 수집과 접근 통제로 낮춘다.

| 점검 항목 | 목표 기준 | 측정 방법 |
|:---|:---|:---|
| 메타데이터 | owner 100%, lineage 90% 이상 | 카탈로그 리포트 |
| 접근 통제 | PII 마스킹 누락 0건 | 정책 테스트, 감사로그 |
| 활용 | 데이터 검색 성공률 80% 이상 | 검색 로그, BI 사용 이력 |

> 요약: 도입 후에는 자산 등록률, 정책 준수율, 사용자 검색 성공률로 판단함.

## Ⅵ. 실무 적용 및 결론

**적용 방안 3개 (필수 - 단계별 또는 항목별):**
1. 메타데이터 수집: OpenMetadata/Apache Atlas로 DB, Lake, Kafka 스키마를 24시간 주기로 수집하고 owner 필수값 적용
2. 정책 통제: PII 태그, RBAC/ABAC, 동적 마스킹으로 주민번호, 계좌번호 조회를 감사로그에 기록
3. 접근 경로 분리: p95 3초 이하 질의는 캐시/가상화, T+1 보고는 ELT, 1분 이하 이벤트는 Kafka 스트림으로 배치

**결론 (2줄):**
- 기술사 판단: 저장소 수가 많고 규제 데이터가 섞이면 데이터 패브릭, 단일 분석 저장소 중심이면 레이크하우스를 우선 선택함
- 향후 방향: AI 학습 데이터와 기업 검색 품질 확보를 위해 데이터 패브릭은 데이터 계약, 카탈로그, 계보 자동화와 결합됨
