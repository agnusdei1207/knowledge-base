## Ⅰ. 개요
- **정의**: 비즈니스 행위를 자연어 시나리오(Given-When-Then)로 기술하고 이를 자동 테스트로 실행하는 개발 기법
- **배경/필요성**: TDD(086)의 테스트가 기술 중심이라 비개발자와의 요구사항 소통에 한계가 있음
- **비유**: 요리 레시피(Given 재료, When 조리, Then 완성 요리)를 그대로 자동 검증하는 것

| 출제 의도 | 반드시 짚을 핵심 | 감점 회피 포인트 |
|:---|:---|:---|
| TDD와의 차이·확장 관계 | Given-When-Then 문법, 유비쿼터스 언어 | Acceptance Test와의 관계를 언급할 것 |

> 요약: 자연어 시나리오를 실행 가능한 테스트로 변환해 요구사항과 코드를 동기화하는 기법임

## Ⅱ. 구성요소
```text
Feature File (.feature)
 |
 v
Step Definition (코드 매핑)
 |
 v
Test Runner --> 실행 결과
```

| 구성요소 | 설명 | 비유 |
|:---|:---|:---|
| Feature File | Given-When-Then 형식으로 비즈니스 시나리오를 기술한 명세 파일 | 레시피 카드 |
| Step Definition | 자연어 스텝을 실행 코드에 매핑하는 글루 코드 | 레시피 해석 로봇 |
| Test Runner | Feature File을 파싱해 Step Definition을 호출·검증하는 실행기 | 주방 자동화 시스템 |

> 요약: Feature File-Step Definition-Test Runner 3요소로 시나리오를 자동 검증함

## Ⅲ. 절차
```text
시나리오 작성 --> Step 매핑 --> 실패 확인 --> 구현·통과
```
- 1단계: 시나리오 작성—PO·개발자가 Given-When-Then 형식으로 인수 기준을 공동 작성
- 2단계: Step 매핑—각 스텝을 실행 코드(Step Definition)에 연결
- 3단계: 실패 확인—아직 구현이 없으므로 테스트 실패를 확인(TDD Red에 해당)
- 4단계: 구현·통과—시나리오를 통과시키는 코드를 구현하고 리팩터링

> 요약: 시나리오-매핑-실패-구현 4단계로 TDD 사이클을 비즈니스 수준에서 수행함

## Ⅳ. 문제점
- 시나리오 폭발: 모든 엣지 케이스를 자연어로 기술하면 Feature File이 비대해짐
- 글루 코드 유지 비용: UI·도메인 변경 시 Step Definition 수정이 연쇄적으로 발생함
- 형식적 채택: Given-When-Then 문법만 도입하고 PO 참여 없이 개발자만 작성하면 소통 효과가 없음

> 요약: 시나리오 폭발, 글루 코드 유지, 형식적 채택이 실효성을 저해함

## Ⅴ. 개선방안
1. 단기: 핵심 비즈니스 흐름만 BDD 시나리오로 작성하고 엣지 케이스는 Unit Test로 위임
2. 중기: Step 재사용 라이브러리를 구축해 글루 코드 중복·수정 범위를 축소
3. 장기: Three Amigos(PO·Dev·QA) 세션을 스프린트 프로세스에 정착시켜 실질적 협업 보장

> 요약: 범위 한정-Step 재사용-Three Amigos 순으로 BDD 실효성을 확보함

## Ⅵ. 전망
- 발전 방향: LLM 기반 자연어 시나리오 자동 생성·Step Definition 자동 매핑
- 기술사적 판단: DDD 유비쿼터스 언어와 BDD 시나리오가 결합해 도메인 모델 검증에 활용되는 추세임
- 기술사 제언: BDD는 도구 도입보다 팀 문화(PO 참여·공동 작성)가 성패를 좌우하므로 프로세스 설계가 우선임
