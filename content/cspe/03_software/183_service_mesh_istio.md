# 📖 【암기용】 개념 완전 이해

## 한눈에
- **개요**: 마이크로서비스 아키텍처(MSA)에서 서비스 간 통신(네트워크, 보안, 관측)을 비즈니스 로직과 분리하여 제어하는 인프라 계층 기술이다.
- **왜 필요한가**: 수십 개의 서비스가 얽힌 MSA에서는 서비스 통신 실패, 암호화, 로깅 처리 코드를 모든 서비스에 중복 구현해야 하는 복잡성 문제가 발생한다. 이를 인프라 레벨로 분리해 해결한다.
- **핵심 직관**: 모든 사무실(서비스) 문 앞에 전담 비서(사이드카 프록시)를 배치하여, 직원들은 일(비즈니스 로직)만 하고 서류 전달과 신원 확인(통신, 암호화)은 비서가 알아서 처리하게 만드는 것이다.

## 핵심 용어 정리

| 용어/표기 | 의미 | 비유·예 |
|:---|:---|:---|
| Data Plane | 실제 트래픽을 가로채고 전달하는 역할을 수행 (Envoy 프록시) | 실제 서류를 배달하는 비서 |
| Control Plane | 프록시들의 트래픽 라우팅 규칙, 인증서, 정책을 중앙 관리 (Istiod) | 비서들에게 지시를 내리는 중앙 통제실 |
| 사이드카 (Sidecar) | 애플리케이션 컨테이너 옆에 별도 컨테이너로 프록시를 띄우는 배포 패턴 | 오토바이(앱) 옆에 붙은 보조석(프록시) |

## 깊이 이해
- **배경·문제의식**: MSA 초기에는 넷플릭스 OSS처럼 서비스 코드 내부에 라이브러리 형태로 서킷 브레이커, 라우팅을 구현했다. 이는 언어 종속성(Java만 가능)과 애플리케이션 비대화라는 한계를 가져왔다.
- **작동 원리**: 애플리케이션 Pod에 Envoy 프록시를 사이드카로 자동 주입(Inject)한다. 애플리케이션이 다른 서비스를 호출할 때, 네트워크 트래픽은 반드시 사이드카를 거친다. Control Plane(Istiod)은 이 사이드카들에게 mTLS 인증서를 배포하고 카나리 배포 같은 라우팅 룰을 주입한다.
- **비유**: 편지를 보낼 때 주소만 쓰면, 우체통(사이드카)이 알아서 암호화 봉투에 담아 최적 경로로 분류장(Control Plane 지시)을 거쳐 수신자 우체통에 안전하게 전달하는 시스템이다.
- **구체 예시**: A 서비스가 B 서비스를 호출할 때, Istio 설정 하나만으로 트래픽의 10%만 B 서비스의 v2 버전으로 보내는 카나리 배포(Canary)를 애플리케이션 코드 수정 1줄 없이 구현할 수 있다.
- **흔한 오해·주의점**: 만능이 아니다. 모든 통신이 2개의 프록시(송신/수신)를 거치므로 홉(Hop)이 늘어나 지연(Latency)과 자원 소모(CPU/Mem)가 발생한다. 규모가 작은 아키텍처에서는 오히려 오버헤드가 더 크다.

## 연결 개념
- **eBPF / Cilium**: 사이드카의 오버헤드를 줄이기 위해 커널 레벨에서 네트워크를 제어하는 차세대 대안
- **API Gateway**: 외부 클라이언트 트래픽을 제어(North-South)한다면, 서비스 메시는 내부 트래픽(East-West)을 제어한다.
- **분산 추적(Distributed Tracing)**: Istio가 자동으로 요청 헤더를 전파하여 서비스 간 호출 추적을 돕는다.

# 📝 【답안용】 시험 답안 템플릿

## 핵심 인사이트 (3줄 요약)

> 1. **본질**: 서비스 메시는 MSA 환경에서 애플리케이션 코드 수정 없이 서비스 간 통신(트래픽, 보안, 관측)을 통제하는 사이드카 프록시 기반 인프라 계층이다.
> 2. **가치**: 통신 복잡도를 Data Plane(Envoy)과 Control Plane(Istiod)으로 분리하여 다형성(언어 독립)과 일관된 마이크로서비스 거버넌스를 제공한다.
> 3. **판단 포인트**: mTLS 및 카나리 배포 구현에 탁월하나, 프록시 체이닝으로 인한 지연(Latency) 증가와 자원 오버헤드라는 트레이드오프 통제가 필수적이다.

## 출제 의도 및 답안 포인트

| 출제 의도 | 반드시 짚을 핵심 | 감점 회피 포인트 |
|:---|:---|:---|
| MSA 통신 복잡성 해결 메커니즘 이해 | Control Plane / Data Plane 분리, Sidecar 패턴 | API Gateway와 서비스 메시의 역할(N-S vs E-W) 혼동 |
| Istio의 3대 핵심 기능 명시 | 트래픽 제어, 보안(mTLS), 관측성(Telemetry) | 내부 라우팅 알고리즘 등 불필요한 딥 다이브 |
| 부작용 인지 및 아키텍처 개선 방향 판단 | 프록시 오버헤드(지연/메모리), eBPF 등 차세대 발전 방향 | 무조건 도입해야 한다는 맹목적 긍정 표현 |

> 요약: 애플리케이션 코드와 인프라 로직의 분리 원리를 명확히 하고, 도입 시 발생하는 오버헤드 통제 및 eBPF 기반 발전 방향을 함께 제시해야 한다.

## Ⅰ. 개요 및 필요성

- 개요: 서비스 메시는 MSA에서 서비스 간 네트워크 통신(보안, 라우팅, 관측)을 애플리케이션 외곽의 독립 인프라 계층에서 처리하는 아키텍처임
- 배경: 기존 코드 기반 라이브러리(Spring Cloud 등) 방식은 언어 종속성과 비즈니스 로직과 통신 로직의 결합으로 유지보수 한계 발생
- 필요성: 서비스 간 복잡한 East-West 트래픽을 중앙에서 정책적으로 통제하고, 무중단 배포 및 제로 트러스트 보안을 일관되게 적용해야 함

---

## Ⅱ. 구조 및 구성요소

```text
[Control Plane: Istiod (설정, 인증서, 텔레메트리 중앙 관리)]
       | (xDS API)                          | (xDS API)
[Data Plane: Pod A] ---------------> [Data Plane: Pod B]
(App <-> Envoy Proxy)    mTLS 통신    (Envoy Proxy <-> App)
```

| 구성요소 | 역할 | 특이사항 |
|:---|:---|:---|
| Data Plane (Envoy) | 서비스 인접 사이드카로 배치되어 실제 인입/인출 트래픽 가로채기 및 제어 | L7 트래픽 파싱, 로드밸런싱 |
| Control Plane (Istiod) | 설정 관리(Pilot), 인증서 발급(Citadel), 정책 주입을 수행 | 프록시로 라우팅 규칙 배포 |
| Sidecar Injection | Pod 생성 시 쿠버네티스 Mutating Webhook을 통해 Envoy 자동 주입 | 코드 수정 0(Zero) 보장 |
| xDS API | Control Plane이 Envoy로 동적 설정을 밀어넣는(Push) 통신 규격 | 설정 갱신 시 재시작 불필요 |

> 요약: 구조는 크게 실제 패킷을 나르는 Data Plane 프록시와 이를 중앙에서 지휘하는 Control Plane 데몬으로 엄격히 분리된다.

---

## Ⅲ. 동작원리 및 흐름도

```text
App A 전송 -> A 사이드카 캡처/암호화 -> 네트워크 전달 -> B 사이드카 수신/복호화 -> App B 전달
```

- 1단계 [설정 주입]: Istiod가 전체 Envoy 프록시 노드에 트래픽 룰(VirtualService) 및 보안 정책 배포
- 2단계 [트래픽 캡처]: App A가 목적지로 요청 시, iptables 규칙에 의해 동일 Pod 내 Envoy로 트래픽 리다이렉션
- 3단계 [통제 및 암호화]: Envoy가 목적지 상태 평가, 서킷 브레이킹 적용 및 트래픽을 mTLS로 암호화하여 전송
- 4단계 [수신 및 관측]: 목적지 Envoy가 복호화 후 App B로 전달하며, 통신 메트릭(Latency 등)을 수집해 외부로 전송

> 요약: 모든 서비스 간 호출이 2개의 사이드카를 거치는 구조(Hop-by-hop)로 동작하며, 투명하게 암호화와 트래픽 제어가 이뤄진다.

---

## Ⅳ. 특징
- [트래픽 관리 (Traffic Management)]: VirtualService/DestinationRule 기반 카나리(Canary), A/B 테스트, 타임아웃, 재시도 제어
- [보안 (Security)]: 서비스 간 상호 인증(mTLS) 자동화 및 인가(AuthorizationPolicy) 통제로 제로 트러스트 달성
- [관측성 (Observability)]: 분산 추적(Trace ID 전파), 로깅, RED(Rate, Error, Duration) 메트릭 자동 수집 지원
- [성능 오버헤드]: 통신마다 프록시 레이어를 추가로 거치므로 p99 응답 지연(Latency) 증가 및 컨테이너 메모리 점유율 상승

> 요약: 트래픽 제어·보안·관측성 3대 기능을 코드 수정 없이 제공하지만, 사이드카 증식으로 인한 자원/지연 오버헤드가 발생한다.

## Ⅴ. 심화 비교 및 적용 판단

| 비교 축 | Library 방식 (Spring Cloud) | Service Mesh (Istio) | 선택 기준 |
|:---|:---|:---|:---|
| 기술 종속성 | 특정 언어/프레임워크 종속 | 언어 독립적 (Agnostic) | 다형성(Polyglot) 구성 여부 |
| 배포/수정 | 정책 변경 시 앱 재빌드/재배포 | 인프라 설정(YAML)만 변경 | 민첩한 롤아웃 필요성 |
| 성능 영향 | 내부 라이브러리라 지연 낮음 | 프록시 홉 추가로 지연 발생 | 오버헤드 허용 한계(Latency) |

> 요약: 다국어(Polyglot) MSA 환경과 잦은 정책 변경에는 Istio가 필수적이나, 극단적인 저지연(Low Latency) 환경에서는 부적합할 수 있다.

**리스크·대응 (기본은 불릿):**
- [프록시 지연 오버헤드]: 홉 추가로 인한 밀리초 지연 증가 → eBPF 기반 사이드카리스(Ambient Mesh) 구조 도입 검토 (지표: Request Latency p99)
- [Control Plane 과부하]: 대규모 클러스터에서 설정 동기화 지연 → Sidecar 리소스 범위를 특정 네임스페이스로 제한(exportTo) (지표: xDS 동기화 지연 시간)

**도입 후 점검 지표 (기본은 불릿):**
- 보안/통신: mTLS 적용률 100% (STRICT 모드) — Kiali 대시보드 보안 뷰 확인
- 성능/안정성: 프록시에 의한 추가 지연 5ms 이하 유지 — 분산 추적(Jaeger) 구간 지연 분석

## Ⅵ. 실무 적용 및 결론

**적용 방안 3개 (필수 — 단계별 또는 항목별):**
1. [관측성 우선 도입]: 트래픽 제어나 mTLS 이전에, Istio를 통해 전체 마이크로서비스의 서비스 맵(Kiali)과 분산 추적 환경 구축
2. [카나리 배포 파이프라인 구현]: ArgoRollouts와 Istio VirtualService를 연동하여 가중치(Weight) 기반 점진적 트래픽 전환 자동화 적용
3. [제로 트러스트 네트워크 적용]: 클러스터 내 모든 서비스 통신을 PERMISSIVE에서 STRICT mTLS로 단계적 강제화하여 내부 스니핑 원천 차단

**결론 (2줄):**
- 기술사 판단: 서비스 메시는 MSA 성숙도를 높이는 필수 인프라지만, 노드 수 50대 이하의 소규모 환경에서는 복잡도가 이점을 상회하므로 신중해야 함
- 향후 방향: 프록시 기반의 지연 한계를 극복하기 위해, 사이드카 없이 노드 단위 eBPF 프록시를 사용하는 Istio Ambient Mesh 형태로 진화 중임
