# 📖 【암기용】 개념 완전 이해

> 목적: 이 개념을 처음 보는 사람도 완벽히 이해하게 만든다. 시험 답안 양식이 아니라, 이해를 위한 친절한 설명이다.

## 한눈에
- **개요**: **소프트웨어 테스트**는 소프트웨어가 명세대로 동작하는지 확인(Verification)하고 사용자 의도를 충족하는지 검증(Validation)하기 위해, 검사 범위를 단위→통합→시스템→인수 순으로 단계적으로 넓혀가는 **테스트 레벨(Test Level)** 체계다. 이 4단계는 **V-모델**이라는 개발 생명주기 모델에서 각 개발 단계와 대칭으로 짝지어진다.
- **왜 필요한가**: 코드를 모두 완성한 뒤 한꺼번에 검사하는 빅뱅(Big-Bang) 테스트는 결함이 어느 모듈에서 시작됐는지 추적하기 어렵게 만든다. 결함은 발견 시점이 늦어질수록 수정 비용이 급격히 커지므로(널리 인용되는 결함비용 곡선에 따르면 요구사항 단계 대비 릴리즈 후 수정은 수십~수백 배 수준으로 알려져 있다), 작은 단위에서부터 촘촘히 걸러내는 단계적 구조가 필요하다.
- **핵심 직관**: 나사못 1개(단위) → 나사못을 조립한 부품 뭉치(통합) → 완성된 제품 전체(시스템) → 고객이 실제로 써보고 승인(인수) 순으로, 검사 범위를 부품에서 완제품으로 점차 넓혀가는 것이다.

## 핵심 용어 정리
| 용어 | 의미 | 비유 |
|:---|:---|:---|
| 테스트 레벨 (Test Level) | 검사 범위를 단계적으로 넓혀가는 4단계 체계 — 단위/통합/시스템/인수 | 부품 → 조립 → 완제품 → 고객 인수 |
| 검증 (Verification) | "만든 것을 올바르게 만들었는가" — 설계·명세와 구현이 일치하는지 확인 | 도면대로 지었는지 확인 |
| 확인 (Validation) | "올바른 것을 만들었는가" — 사용자 요구를 충족하는지 확인 | 고객이 원하던 집이 맞는지 확인 |
| V-모델 | 개발 단계(왼쪽 사선)와 테스트 레벨(오른쪽 사선)을 대칭으로 짝짓는 생명주기 모델 | 알파벳 V자 모양 |
| 단위 테스트 (Unit) | 함수·클래스 등 최소 단위를 개발자가 독립적으로 검증 | 나사못 1개 검사 |
| 통합 테스트 (Integration) | 모듈 간 인터페이스·데이터 흐름 정합성 검증 | 조립한 부품이 서로 안 맞는지 확인 |
| 시스템 테스트 (System) | 완성된 전체를 실제와 유사한 환경에서 기능+비기능 검증 | 완성차 시운전 |
| 인수 테스트 (Acceptance) | 고객·사용자가 비즈니스 목적 달성 여부를 최종 승인 | 계약서 서명 |
| Mock/Stub | 외부 의존성(DB·API)을 가짜 객체로 대체해 테스트를 독립시키는 기법 | 촬영용 대역 |
| Shift-Left | 결함 발견 시점을 개발 초기(왼쪽) 단계로 앞당기는 전략 | 조기 발견 |
| 테스트 피라미드 | 저렴하고 빠른 단위 테스트를 많이, 비싸고 느린 시스템/UI 테스트를 적게 두는 비율 구조 | 밑변이 넓은 피라미드 |

## 깊이 이해

### V-모델 — 왜 개발 단계와 테스트 레벨을 대칭으로 짝짓는가
요구사항 분석 단계에서 "이것을 어떻게 검증할지"를 미리 정해두면 그것이 인수 테스트 시나리오가 되고, 상세(모듈) 설계 단계에서 정한 내용이 단위 테스트 케이스가 된다. 즉 설계를 그릴 때 이미 어떤 테스트로 검증할지 함께 정해두자는 것이 V-모델의 철학이다. 매핑은 다음과 같다: 요구사항 분석 ↔ 인수 테스트, 시스템 설계 ↔ 시스템 테스트, 기본(아키텍처) 설계 ↔ 통합 테스트, 상세(모듈) 설계 ↔ 단위 테스트.

### 4단계 테스트 레벨을 수치로 이해하기
- **단위 테스트**: 함수 하나를 DB 접속 없이 Mock으로 대체해 검증한다. 테스트 1건 실행에 약 0.001~0.1초가 걸려, 1,000건을 돌려도 CI 파이프라인에서 수 초~수십 초면 끝난다. 테스트 자산 중 개수 비중이 가장 커서, 테스트 피라미드에서 흔히 전체의 70% 내외로 잡는다.
- **통합 테스트**: 실제 DB·외부 API를 붙여 인터페이스 정합성을 확인하므로 단위보다 느리다(건당 수백ms~수초).
- **시스템 테스트**: 실제와 유사한 스테이징 환경에서 기능+비기능(성능·보안·부하)을 검증한다. UI 자동화 테스트는 1건에 수 초~수십 초가 걸리고, 전체 스위트는 수십 분이 걸리기도 한다.
- **인수 테스트**: 알파(내부 인력), 베타(제한된 외부 사용자) 테스트로 나뉘며, 기계적 통과가 아니라 사람의 최종 승인(Sign-off)이 통과 기준이다.

### 결함은 늦게 발견될수록 비싸다 — Shift-Left가 필요한 이유
요구사항 단계에서 잡는 결함의 수정 비용을 1이라 할 때, 설계 단계는 약 5~10배, 구현(코딩) 단계는 약 10~100배, 릴리즈 이후(운영 중) 발견은 수십~수백 배까지 치솟는다고 알려져 있다. 그래서 결함을 최대한 이른 단계(왼쪽)에서, 가장 작은 단위(단위 테스트)부터 잡아내려는 것이 Shift-Left 전략이며, 이것이 테스트 레벨을 4단계로 나누는 근본 이유다.

### 테스트 피라미드 — 왜 단위 테스트를 가장 많이 만드는가
단위 테스트는 싸고(작성에 수 분) 빠르다(0.1초 미만). 시스템/UI 테스트는 비싸고(환경 구성에 수일) 느리다(건당 수십 초~수 분). 그래서 저렴하고 빠른 단위 테스트를 매우 많이(피라미드 밑변), 비싸고 느린 시스템/UI 테스트는 핵심 시나리오 위주로 적게(피라미드 꼭짓점) 두는 것이 테스트 피라미드 구조다. 반대로 단위 테스트를 거의 짜지 않고 UI 테스트에만 의존하면 "역피라미드(아이스크림콘 안티패턴)"가 되어, 화면 요소 하나만 바뀌어도 느린 UI 테스트를 전부 다시 돌려야 하는 배포 병목이 생긴다.

### 비유
자동차 생산 라인에 비유하면, 나사못 1개(단위)의 강도를 개별로 검사하고, 나사못으로 조립한 엔진 뭉치(통합)가 잘 맞물리는지 보고, 완성된 자동차 전체(시스템)를 시운전한 뒤, 마지막으로 구매 고객이 시승 후 계약서에 서명(인수)하는 4단계와 같다.

## 연결 개념
- V-모델 — 검증 대상과 명세를 함께 정의하는 상위 생명주기 모델
- 065 TDD — 단위 테스트를 극단적으로 앞당겨 본체 코드보다 먼저 작성하는 방법론
- 066 화이트박스/블랙박스 테스트 — 단위·통합은 주로 화이트박스, 시스템·인수는 주로 블랙박스 기법을 사용
- 067 테스트 커버리지 — 단위(화이트박스) 테스트가 코드를 얼마나 실행했는지 측정하는 지표

# 📝 【답안용】 시험 답안 템플릿

> 목적: 시험장에서 25분에 그대로 쓰는 답안 양식. 작성방식(추상표현 금지·수치·도식·문제유형 전환)을 엄격히 지킨다.
> 핵심: 이 시험은 정보를 많이 나열하는 시험이 아니라, 문제 신호어에서 출제자 의도를 읽고 핵심 논점을 선별해 쓰는 시험이다.

## 핵심 인사이트 (3줄 요약)

> 1. **본질**: 소프트웨어 결함(Defect)을 식별하고 품질을 보증(QA)하기 위해, 가장 작은 모듈(단위)부터 전체 비즈니스 요구사항(인수)에 이르기까지 검증의 스코프를 점진적으로 확대하는 4단계 테스트 레벨 아키텍처다.
> 2. **가치**: 버그 발견 시점을 폭포수의 맨 끝단에서 코딩 직후(단위 테스트)로 극한까지 당겨오는 **시프트 레프트(Shift-Left)**를 통해 수정 비용(Cost of Defect)을 1/100 수준으로 압축한다.
> 3. **판단 포인트**: V-모델 기반의 4단계 테스트 레벨(단위/통합/시스템/인수)과 개발 단계(설계/분석) 간의 대칭적 매핑 도식을 명확히 그리고, 현대 CI/CD 파이프라인에서 자동화(Test Automation) 구간과 수동(Manual) 구간의 경계를 구분해야 한다.

## 출제 의도 및 답안 포인트

| 출제 의도 | 반드시 짚을 핵심 | 감점 회피 포인트 |
|:---|:---|:---|
| 소프트웨어 생명주기(SDLC) 내 검증(Validation)과 확인(Verification)의 체계화 | **V-모델 대칭 도식화** (단위-상세설계, 통합-기본설계, 시스템-시스템설계, 인수-요구분석) | 4가지 테스트의 이름만 나열하고, 각 테스트가 검증하는 '대상(문서)'의 연결고리 누락 |
| 테스트 커버리지 및 책임(Responsibility)의 물리적 주체 맵핑 | 단위/통합(개발자 주도, White-box) vs 시스템/인수(QA/사용자, Black-box) | 누가(Who) 어떤 기법(기계/수동)으로 테스트하는지 실무적 렌즈 결여 |
| 고전적 V-모델과 현대 CI/CD (테스트 피라미드) 통제망 융합 | 하위(단위) 테스트의 압도적 비중(70%)을 통한 애자일 배포(Agile) 속도 사수 | 시스템/UI 테스트가 짱짱맨이라고 쓰는 구시대적(역피라미드 안티패턴) 오답 |

> 요약: 주니어는 시스템 전체를 빌드해 놓고 웹페이지를 마우스로 클릭하며 버그를 찾는다(10분 소요). 시니어는 함수 1개만 고립시켜 Mock 객체를 물리고 기계(JUnit)로 버그를 잡는다(0.1초 소요). 단위(Unit) 레벨의 장악력 차이가 소프트웨어의 배포 속도(Agility)를 결정한다.

## Ⅰ. 개요 및 필요성

- 정의: 소프트웨어가 명세서(요구사항)대로 정확히 동작하는지 확인(Verification)하고 사용자의 의도를 만족하는지 검증(Validation)하기 위해, V-모델 생명주기에 따라 검사 스코프를 단계적으로 확장하는 체계적 품질 통제 프랙티스
- 배경: 모든 코드가 결합된 후 릴리즈 직전에 수행하는 빅뱅(Big-bang) 테스트는, 결함의 근원지(Root Cause) 식별을 불가능하게 만들어 디버깅 비용 폭발 및 런타임 장애(SPOF) 리스크 야기
- 필요성: 모듈 단위의 고립된 테스트(단위)부터 시작하여 결함의 파급을 극초기(Shift-left)에 절연(Isolation)하고, 상위 단계(시스템/인수)에서 비기능(성능/보안) 및 비즈니스 목적 달성 여부를 최종 승인(Sign-off)받기 위함

## Ⅱ. V-모델 기반 테스트 레벨(Test Levels) 매핑 도식

테스트는 코드를 짜기 전, '요구사항과 설계도'를 그릴 때 이미 무엇을 검사할지 결정되어야 한다. (대칭 매핑).

```text
[ SDLC (소프트웨어 생명주기) V-모델 아키텍처 대조 도식 ]

(개발 프로세스: 무엇을 만들까?)                     (테스트 프로세스: 잘 만들었나?)
[ 요구사항 분석 ]  ------------------- (Validation) ------------------>  [ 4. 인수 테스트 (Acceptance) ]
      |                                                                       ^
  [ 시스템 설계 ]  ------------------ (Verification) ----------------->  [ 3. 시스템 테스트 (System) ]
         |                                                                    |
     [ 기본(아키텍처) 설계 ]  ---------- (Verification) ----------->  [ 2. 통합 테스트 (Integration) ]
            |                                                                 |
        [ 상세(모듈) 설계 ]  ---------- (Verification) --------->  [ 1. 단위 테스트 (Unit) ]
                                |                             |
                                +----> [ 소스코드 구현 (Code) ] ----+
```

| 테스트 레벨 | 검증 대상 (엔지니어링 메커니즘) | 주체 및 기법 (품질 방어) |
|:---|:---|:---|
| **1. 단위 (Unit)** | 독립된 모듈(함수/클래스) 내부의 엣지 케이스 및 분기(If/Else) 로직. 외부 DB/API 연동은 모의 객체(Mock/Stub)로 완벽히 차단하여 독립성 확보 | **개발자 (White-box 기법)** <br> JUnit, NUnit 코드로 작성. CI 파이프라인에서 0.1초 만에 1만 개 수행 |
| **2. 통합 (Integration)** | 단위 모듈들을 조립(Assemble)했을 때 모듈 간 인터페이스(API) 및 데이터 흐름 정합성 검사 (하향식 Stub, 상향식 Driver 사용) | **개발자/아키텍트 (White-box/Black)** <br> 실제 DB나 외부 MSA를 붙여 데이터 I/O 정합성 검증 |
| **3. 시스템 (System)** | 완전한 하드웨어/운영체제(Staging) 환경에서 시스템 전체의 기능(기획서 일치) 및 비기능(성능, 보안, 부하, 회복성) 요구사항 충족 검열 | **전문 QA팀 (Black-box 기법)** <br> 스트레스 툴(JMeter), 침투 테스트(Pen-test) 등 비기능 초점 |
| **4. 인수 (Acceptance)** | 인도 전 비즈니스 목적을 달성하는지 실제 사용자 시나리오 기반 검증. 알파(사내), 베타(제한된 외부 사용자) 테스트 | **고객/최종 사용자 (Black-box)** <br> 버그 색출보다는 "내가 쓸 만한가(Sign-off)" 비즈니스 판단 |

> 요약: "단위 테스트 통과했으니 완벽합니다"는 헛소리다. 창문(단위) 잘 열리고 차체(단위)가 튼튼해도, 조립(통합)을 잘못하면 비가 샌다. 하지만 단위 테스트조차 안 짠 코드는 비가 새는 수준이 아니라 바퀴가 빠져 죽는다.

## Ⅲ. 극복해야 할 시스템적 리스크 (역피라미드 붕괴)

기계(코드)가 해야 할 단위 테스트를 무시하고, 인간이 화면을 클릭하는 테스트(시스템/UI)에 의존하면 애자일은 망한다.

| 리스크 요인 | 발생 시나리오 및 시스템 붕괴 원인 (안티패턴) | 아키텍처 대응 방안 (실무 튜닝) |
|:---|:---|:---|
| **테스트 역피라미드** <br> (Ice Cream Cone 안티패턴) | 개발자는 단위 테스트(Unit Test)를 0개 짜고, QA팀 100명이 달라붙어 매일 마우스로 클릭하는 UI/시스템(System) 테스트에 올인. 화면 버튼 하나 바뀌면 QA가 밤새 클릭 노가다를 다시 해야 하는 배포 병목 지옥 발생 | **테스트 피라미드(Test Pyramid) 사수**: 기계가 0.1초 만에 돌리는 **단위(Unit) 테스트 비중을 70%**로 극단적 강제화. 비싸고 느린(10분 소요) UI/E2E 시스템 테스트는 핵심 시나리오 10% 미만으로 억제(Shift-Left)하여 애자일 속도 확보 |
| **단위 테스트의 DB 종속성 오염** | 단위 테스트 함수가 실행될 때마다 진짜 Oracle DB에 붙어서 `INSERT`를 때림. DB 락(Lock)이 걸리거나 네트워크가 느려지면, 단위 테스트 1,000개 도는 데 30분이 걸려 CI/CD(Jenkins) 배포 마비 | **순수 격리 (Mocking & Stubbing)**: 단위 테스트 내부에는 스프링(Spring) 컨테이너 구동이나 실제 DB 연결 100% 금지. 외부 인프라는 무조건 `Mockito` 가짜 객체로 갈아 끼워(Dependency Injection) 메모리 상에서 광속 연산 |

> 요약: 단위 테스트(Unit Test)는 싸고(코딩 1분) 빠르다(0.1초). 시스템 테스트(E2E)는 비싸고(환경 세팅 3일) 끔찍하게 느리다(10분). 싼 걸(단위 테스트) 미친 듯이 많이 만들어서 방어막을 치는 것, 그것이 애자일 테스트 피라미드의 진리다.

## Ⅳ. 테스트 기법과 최신 트렌드 융합 (자동화와 TDD)

V-모델의 사상은 애자일(Agile) 시대로 오며 '자동화 코드'와 결합하여 TDD로 극적 진화했다.

| 진화 패러다임 | 아키텍처 융합 메커니즘 | 해결되는 비즈니스/운영 한계 |
|:---|:---|:---|
| **TDD** <br> (테스트 주도 개발) | 구현 코드를 짜기 전에, 실패하는(Red) 단위 테스트 코드부터 먼저 작성하고, 이를 통과(Green)하기 위한 최소한의 본체 코드만 작성하는 역방향 엔지니어링 | 불필요한 오버엔지니어링(YAGNI)을 방지하고, 탄생부터 100% 테스트 커버리지를 가진 견고한 단위 모듈을 양산 (디버깅 비용 제로화) |
| **CI 파이프라인 블로킹** <br> (Quality Gate) | 개발자가 `Git Push` 시, SonarQube와 연동된 파이프라인이 **단위 테스트 커버리지(Line Coverage) 80% 미만일 경우 빌드 자체를 킬(Kill)하여 강제 차단** | 개발자 개인의 양심에 맡기던 '단위 테스트 작성'을 젠킨스(기계)의 검열 시스템으로 물리적 강제화하여 스파게티 레거시 유입 원천 봉쇄 |

> 요약: 단위/통합 테스트는 인간(개발자)이 눈으로 하는 게 아니다. 코드로 짜놓고 파이프라인 봇(Bot)에게 "내가 깃허브에 코드 올릴 때마다 이거 천 번씩 실행해서 에러 잡어"라고 시키는 자동화 도면(Blueprint)이다.

## Ⅴ. 실무 적용 방안 및 결론

**적용 방안 3개:**
1. [테스트 더블(Test Double) 기반 단위 테스트 순수성 보장] MSA 환경의 결제 마이크로서비스 테스트 시, 외부의 카카오페이 API나 내부 결제 DB를 호출하지 못하도록 `Mockito`와 `WireMock`을 투입해 네트워크/DB 계층을 100% 절연(Isolation). 메모리 상에서 초당 1,000개의 Mock 연산 쾌속 통과 유도
2. [카오스 엔지니어링(Chaos Engineering) 기반 시스템 비기능 방어] 시스템 테스트(System Test) 단계에서 넷플릭스의 `Chaos Monkey` 사상을 도입. 스테이징(Staging) 환경에서 무작위로 K8s Pod(서버) 3개를 강제로 죽여보며(Kill), 서비스가 뻗지 않고 오토스케일링과 서킷 브레이커(차단기)가 즉각 작동하는지 런타임 회복력(Resilience) 가혹 검증
3. [BDD (Behavior Driven Development) 기반 인수 테스트 자동화] 기획자(사용자)가 엑셀로 짜준 "Given-When-Then(상황-행동-결과)" 형태의 비즈니스 시나리오를 `Cucumber` 프레임워크를 통해 영어 문장 그대로 시스템 인수 테스트 코드로 직결 매핑. 기획서 자체가 자동화된 테스트 코드가 되는 마법 구현

**결론:**
- 기술사 판단: 단위부터 인수로 이어지는 V-모델의 4단계 테스트 레벨은 50년의 소프트웨어 공학이 증명한 가장 완벽한 품질 통제 아키텍처다. 현대 클라우드/애자일 시대에는 이 4단계를 무시하는 것이 아니라, 오히려 하위 레이어(단위/통합)의 실행 권한을 인간에게서 기계(CI/CD)로 100% 이관함으로써 무한 배포(Continuous Deployment)를 쟁취하는 근원적 신뢰(Trust) 자본으로 활용하고 있다.
- 향후 방향: 최근 현업에서는 단위 테스트 작성을 극도로 귀찮아하는 개발자들을 구제하기 위해, 생성형 AI(GitHub Copilot)가 소스코드 구조를 읽고 엣지(Edge) 케이스를 포함한 `JUnit` 단위 테스트 코드를 5초 만에 100% 자동 생성(Auto-generation)해 내는 방향으로 테스트 비용이 극한 수렴(0원)하고 있다.
