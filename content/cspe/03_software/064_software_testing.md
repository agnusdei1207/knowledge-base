## 미리 알고가기

- 테스트는 결함 존재를 드러내는 검증 활동임
- 단위와 통합과 시스템과 인수 테스트는 범위와 목적이 다름
- 상위 테스트로 갈수록 실제 사용자 가치 검증 비중이 커짐

## Ⅰ. 개요

- **정의/개념**: 소프트웨어 테스트는 코드와 컴포넌트와 시스템과 사용자 요구 수준에서 기능과 품질을 검증해 결함과 위험을 식별하는 활동이며, 범위에 따라 단위와 통합과 시스템과 인수 테스트로 구분됨
- **배경/필요성**: 결함은 개발 단계마다 다른 형태로 나타나므로 하나의 테스트로 모든 위험을 잡을 수 없으며, 검증 레벨별 역할 분담이 필요함

## Ⅱ. 특징

- 단위 테스트는 가장 빠르고 국소적인 결함 탐지에 유리함
- 통합 테스트는 인터페이스와 데이터 흐름 문제를 검증함
- 시스템 테스트는 비기능을 포함한 전체 동작을 확인함
- 인수 테스트는 사용자와 계약 관점에서 최종 수용 여부를 판정함

## Ⅲ. 종류 및 비교

| 판단 기준 | 단위 테스트 | 통합 테스트 | 시스템 테스트 | 인수 테스트 |
|:---|:---|:---|:---|:---|
| 범위 | 함수/클래스 | 컴포넌트 간 연결 | 전체 시스템 | 사용자 요구 수용 |
| 속도 | 빠름 | 중간 | 느림 | 상대적으로 느림 |
| 장점 | 빠른 회귀 방지 | 인터페이스 오류 탐지 | 전체 동작 확인 | 비즈니스 적합성 확인 |
| 핵심 질문 | 코드가 맞는가 | 연결이 맞는가 | 시스템이 동작하는가 | 사용자가 받아들일 수 있는가 |

## Ⅳ. 구성요소 및 구조

| 구성요소 | 설명 |
|:---|:---|
| Test Scope Layer | 각 테스트 레벨이 다른 위험을 다뤄 전체 품질망을 형성함 |
| Test Environment | 레벨별로 필요한 목과 실환경 비중이 달라 신뢰성과 비용을 좌우함 |
| Expected Result or Oracle | 합격 기준이 명확해야 자동화와 회귀 검증이 가능해짐 |
| Defect Feedback Loop | 발견 결함이 원인 단계로 빠르게 돌아가야 테스트 비용 대비 효과가 커짐 |

## Ⅴ. 원리 및 절차 흐름도

```text
+-------------+     +-------------+     +-------------+     +-------------+
| 범위 선정      | --> | 테스트 설계    | --> | 실행/결함 수집 | --> | 수정/회귀 검증 |
+-------------+     +-------------+     +-------------+     +-------------+
```

1. **범위 선정**: 어떤 레벨에서 어떤 위험을 검증할지 정함
2. **테스트 설계**: 입력과 기대 결과와 환경을 정의함
3. **실행 및 결함 수집**: 테스트를 수행하고 실패를 기록함
4. **수정 및 회귀 검증**: 결함 수정 후 관련 테스트를 다시 수행함

## Ⅵ. 문제점 및 해결 방안

1. 문제: 테스트 레벨별 책임이 섞이면 단위 테스트는 느려지고 시스템 테스트는 중복만 많아질 수 있음
   - 해결방안: 테스트 피라미드 기준을 운영하고 test distribution balance와 suite execution time으로 검증함
2. 문제: 기대 결과가 모호하면 자동화가 어려워지고 테스트 실패 해석 비용이 커질 수 있음
   - 해결방안: 수용 기준과 oracle을 명확히 하고 flaky test rate와 assertion clarity score로 검증함
3. 문제: 인수 테스트가 늦게 수행되면 비즈니스 요구 미스매치가 말기에 폭발할 수 있음
   - 해결방안: 시나리오 기반 검증을 앞당기고 acceptance defect discovery timing과 rework rate로 검증함

## Ⅶ. 적용 사례

- 백엔드 모듈 개발에서는 단위 테스트를 강화하고 확인 지표는 suite execution time과 mutation score임
- 서비스 통합 프로젝트에서는 통합 테스트를 운영하고 확인 지표는 integration defect rate와 environment stability score임
- 고객 검수형 프로젝트에서는 인수 테스트를 조기 설계하고 확인 지표는 acceptance defect discovery timing과 rework rate임

## Ⅷ. 결론

소프트웨어 테스트의 본질은 테스트 종류를 많이 나열하는 데 있지 않고 각 레벨이 서로 다른 위험을 중복 없이 분담하게 만드는 데 있음.
