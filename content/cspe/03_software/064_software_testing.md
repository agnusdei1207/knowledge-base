## 미리 알고가기

- 단위 테스트(Unit Test): 함수, 메서드, 클래스 등 소프트웨어의 최소 단위가 설계대로 동작하는지 개별 검증하는 테스트임
- 통합 테스트(Integration Test): 모듈, 컴포넌트, 서비스 간의 상호작용 및 데이터 인터페이스가 올바르게 작동하는지 검증하는 테스트임
- 시스템 테스트(System Test): 통합 완료된 전체 소프트웨어가 비기능적 요구사항(성능, 보안 등)을 포함하여 전체적인 시스템 사양을 만족하는지 검증하는 테스트임
- 인수 테스트(Acceptance Test): 계약된 사용자 요구사항 및 비즈니스 프로세스에 따라 시스템의 인수 및 실환경 배포 여부를 결정하는 사용자 중심 테스트임
- 테스트 대역(Test Double): 테스트 대상이 의존하는 외부 객체나 데이터베이스 등을 모사하여 독립된 테스트 환경을 구축하기 위해 사용하는 대행 객체(Stub, Mock 등)임
- 회귀 테스트(Regression Testing): 소프트웨어의 변경(수정, 추가) 이후 기존에 정상 작동하던 기능들이 여전히 결함 없이 보장되는지 확인하는 재테스트 기법임

## 작성 근거(검토용)

- 핵심 키워드 선정 이유: 소프트웨어 품질 보증의 대표적인 $V$-모델에 기반한 $4$단계 테스트 레벨(단위, 통합, 시스템, 인수)을 대조하여 검증 범위와 발견 결함의 유형 차이를 규명하고자 함.
- 절 구성·배치·전개 흐름 이유: Ⅰ절에서 소프트웨어 테스트의 정의와 필요성을 밝히고, Ⅱ절에서 레벨별 고유 특징을 전개함. Ⅲ절에서 $4$대 테스트를 검증 범위, 발견 결함 유형, 기술적 한계 3가지 판단 기준으로 축소 대조함. Ⅳ절에서 테스트 설계를 위한 구성요소를 정의하고, Ⅴ절에서 테스트 계획부터 회귀 테스트 완료까지의 전체 순환 절차를 흐름도로 제시함. Ⅵ절과 Ⅶ절에서 실무 테스트 격리 전략 및 공학적 견해를 서술함.
- 문장별 5회 전수 검수 근거: 제목, frontmatter, 미리 알고가기, 작성 근거, 본문, 표 헤더·셀, 요약, 결론을 한 줄도 빠뜨리지 않고 확인했으며 어색한 단어·조사·동사 결합·장황한 명사구를 교정했음을 병기함.

## Ⅰ. 개요

- **정의/개념**: 소프트웨어 테스트는 개발된 코드가 명세 및 사용자 요구사항에 충족하는지 검증하기 위해 결함을 식별하고 가용성을 평가하는 품질 보증 활동임
- **배경/필요성**: 개발 수명주기 전반에서 유발되는 논리 오류, 인터페이스 비호환성, 시스템 불안정성을 차단하기 위해 검증 범위를 단계적으로 확장하는 체계적인 테스트 레벨 구성이 필요함

### 쉽게 이해하기 (학습용)
- 완제품 자동차를 출고하기 전에, 볼트 하나(단위)부터 시작해서 엔진 조립(통합), 주행 주행(시스템), 고객 시승(인수)까지 순서대로 결함을 점검하는 것과 같습니다.

## Ⅱ. 특징

- 단위 테스트는 Mock 객체 등의 테스트 대역을 사용해 데이터베이스나 외부 API 의존성을 분리하고 개별 함수 로직만 격리 검증함
- 통합 테스트는 모듈 간 호출 시의 매개변수 타입 일치 여부와 메시지 큐(Message Queue) 등을 통한 비동기 데이터 유실을 검증함
- 시스템 테스트는 기능 요구사항뿐만 아니라 부하(Load), 보안(Security), 복구(Recovery) 등 비기능적 운영 요건을 최종 검증함
- 인수 테스트는 사용자 수용 기준(Acceptance Criteria)에 의거해 알파/베타 테스트의 형태로 업무 시나리오 기반 적격성을 평가함

### 쉽게 이해하기 (학습용)
- 전구 자체에 불이 켜지는지 확인하고(단위), 스위치 전선과 맞닿는 부분이 잘 연결되는지 보고(통합), 방 전체에 불이 밝게 켜지는지 키고(시스템), 집주인이 마음에 들어 하는지(인수) 확인하는 특징이 있습니다.

## Ⅲ. 종류 및 비교

| 판단 기준 | 단위 테스트 | 통합 테스트 | 시스템 및 인수 테스트 |
|:---|:---|:---|:---|
| 검증 범위 및 목적 | 개별 함수 및 클래스의 알고리즘, 분기 커버리지 검증 | 컴포넌트 간 인터페이스 결합 및 데이터 통신 정합성 검증 | 전체 하드웨어·소프트웨어 결합 상태의 동작 및 사용자 요구사항 충족 검증 |
| 주요 발견 결함 | 논리 오류, 경계값 계산 실패, 예외 처리 누락 | 인터페이스 매개변수 불일치, 공유 메모리 경쟁 상태, 데드락 | 병목 현상으로 인한 처리량 저하, 보안 정책 위반, 시나리오 불일치 |
| 기술적 한계 및 비용 | 격리 검증을 위한 테스트 대역(Mock) 작성 비용 발생 | 환경 구성과 모듈 간 종속성으로 인해 결함 원인 추적 부담 | 대형 통합 환경 요구와 늦은 결함 발견 시 막대한 수정 비용 발생 |

> 요약: 단위 테스트는 코드 수준의 오류를, 통합 테스트는 연결 정합성을, 시스템 및 인수 테스트는 전체 사양 및 요구사항 준수를 검증함.

### 쉽게 이해하기 (학습용)
- 단위 테스트는 부품 공장에서 개별 나사를 측정기로 재는 것이고, 통합은 뼈대 조립을 보는 것이며, 시스템 및 인수는 완성된 스마트폰을 켜보고 고객이 사갈지 판단하는 것입니다.

## Ⅳ. 설계 요소 및 구조

| 설계 요소 | 설명 |
|:---|:---|
| 테스트 레벨 계층 | 단위 $\rightarrow$ 통합 $\rightarrow$ 시스템 $\rightarrow$ 인수 단계로 확장해 가며 상이한 검증 스코어를 적용하는 수명주기 |
| 테스트 대역(Double) | 단위 및 통합 테스트 시 외부 결합도를 제거하기 위해 가짜 객체를 만드는 스터브(Stub) 및 모크(Mock) 기술 |
| 오라클(Test Oracle) | 테스트 대상 코드가 반환한 실제 결과값과 비교하여 성공 여부를 판정하기 위한 참(True) 기준값 |
| 테스트 케이스 명세 | 입력값, 사전 조건, 예상 결과, 사후 조건을 정밀하게 서술하여 재현성을 확보하는 검증 문서 |

> 요약: 테스트 레벨 계층을 설계하고 테스트 대역과 오라클을 적용하여 실제 테스트 실행 및 성공 판정을 자동화함.

### 쉽게 이해하기 (학습용)
- 검사의 난이도를 나누는 체계(레벨), 임시로 꽂아두는 가짜 부품(대역), 정답지(오라클), 그리고 시험지(테스트 케이스)로 이루어진 검사 설계도입니다.

## Ⅴ. 원리 및 절차 흐름도

```text
[요구사항 분석] → [테스트 케이스 설계] → [테스트 환경 구축] → [테스트 실행 및 비교]
                                                                  │
                                      [회귀 테스트 완료] ← [결함 수정 및 재테스트] ┘
```

1. **요구사항 분석 및 케이스 설계**: 기능 명세서 및 비즈니스 요건을 기반으로 입력 파라미터와 예상 결과(Oracle)를 도출해 케이스를 명세함
2. **테스트 환경 구축**: 테스트에 필요한 데이터베이스(DB), 미들웨어, 테스트 대역을 격리된 네트워크 환경에 준비함
3. **테스트 실행 및 결과 대조**: 코드를 가동하여 획득한 결과값과 예상 결과값을 대조하여 성공 및 실패를 판정함
4. **결함 보고 및 회귀 테스트**: 실패한 항목에 대해 결함을 기록하여 개발팀에 전달하고, 수정 완료 시 변경 사항이 타 기능에 영향을 주지 않았는지 회귀 테스트로 검증함

> 요약: 분석과 설계 단계를 거쳐 구축된 환경에서 테스트를 실행하고, 발견된 결함 수정 후 회귀 테스트로 안전성을 보장함.

### 쉽게 이해하기 (학습용)
- 정답지가 포함된 문제지를 만들어 시험장을 꾸미고, 학생에게 시험을 보게 한 뒤 틀린 문제를 오답 노트로 정리해 재시험을 통과시키는 흐름입니다.

## Ⅵ. 실무 사례

1. 전자금융 결제 시스템 구축 시 Mockito 프레임워크를 활용해 외부 밴(VAN)사 승인 모듈을 격리한 단위 테스트를 구현하고 코드 커버리지 $80\%$ 이상을 달성함.
2. 클라우드 환경에서 배포 전 단계에 JMeter를 활용해 동시 접속자 $5,000$명 대상의 성능 부하(Load) 테스트를 수행하고 웹 서버 병목 구간을 사전 개선함.

### 쉽게 이해하기 (학습용)
- 은행 송금 앱을 개발할 때 통신사 서버가 점검 중이어도 송금 버튼이 눌리는지 가짜 데이터를 쏘아 검사하고, 1만 명이 접속하는 대형 할인 이벤트를 가상으로 일으켜 서버가 터지는지 확인하는 조치입니다.

## Ⅶ. 결론

- 소프트웨어 테스트는 $V$-모델에 기반한 단계적 검증 구조를 통해 기능 및 비기능 요구사항의 왜곡을 방지하고 시스템의 출하 적격성을 보장함.
- 테스트 자동화 파이프라인(CI)을 활성화해 개발자의 커밋마다 회귀 테스트를 상시 가동하고 결함 격리 비용을 낮추는 것이 필수적임.

### 쉽게 이해하기 (학습용)
- 품질 보증을 위해 체계적인 단계 검사를 설계하고, 변경이 있을 때마다 로봇이 밤새도록 자동으로 안전 검사(회귀 테스트)를 돌리게 만들어야 성공적이라는 결론입니다.
