# 📖 【암기용】 개념 완전 이해

## 한눈에
- **개요**: 소프트웨어가 요구사항을 만족하는지, 예상된 결과를 출력하는지 검증하고 결함을 찾는 활동
- **왜 필요한가**: 완벽한 코드는 존재하지 않는다. 출시 후 발견되는 버그는 개발 과정에서 찾는 것보다 수십~수백 배의 비용을 초래하므로, 체계적인 검증이 필수다.
- **핵심 직관**: 건물을 지을 때 벽돌 하나가 단단한지(단위), 기둥과 지붕이 잘 맞물리는지(통합), 전체 건물이 안 무너지는지(시스템), 건축주가 맘에 들어하는지(인수)를 단계별로 확인하는 과정이다.

## 핵심 용어 정리

| 용어/표기 | 의미 | 비유·예 |
|:---|:---|:---|
| V-모델 (V-Model) | 개발 단계와 테스트 단계를 1:1로 매핑한 고전적 검증 모델 | 거울에 비친 개발의 역방향 |
| 검증 (Verification) | 제품을 올바르게 만들고 있는가? (명세서 충족 여부) | 설계도대로 나사가 조여졌는가? |
| 확인 (Validation) | 올바른 제품을 만들고 있는가? (사용자 요구 충족 여부) | 고객이 이 자동차를 타기 편한가? |
| 디버깅 (Debugging) | 테스트로 발견된 결함의 원인을 찾아 수정하는 활동 | 병을 진단(테스트)하고 치료(디버깅)함 |

## 깊이 이해
- **배경·문제의식**: 코드를 다 짜고 나서 한 번에 테스트하려면 어디서 버그가 났는지 추적하기가 거의 불가능하다. 이를 방지하기 위해 개발 생명주기 전체에 걸쳐 계층적이고 체계적인 테스트 전략이 필요해졌다.
- **작동 원리**: V-모델에 따라 4단계로 진행된다. ① **단위(Unit)**: 가장 작은 모듈(함수) 하나가 독립적으로 잘 도는지 확인. ② **통합(Integration)**: 모듈들을 합쳤을 때 인터페이스 간 통신이 잘 되는지 확인. ③ **시스템(System)**: 완성된 소프트웨어 전체가 성능, 보안 등 비기능 요구사항까지 충족하는지 확인. ④ **인수(Acceptance)**: 실제 사용 환경에서 고객이 OK 도장을 찍을 수 있는지 확인.
- **비유**: 자동차 제조. 나사와 바퀴 하나하나 검사(단위) -> 엔진과 변속기를 연결해 테스트(통합) -> 완성된 차를 트랙에서 주행(시스템) -> 고객이 직접 시승(인수).
- **구체 예시**: `로그인 함수` 단독 실행 시 비밀번호 암호화가 잘 되는지(단위) -> `로그인 모듈`이 `DB`와 연결되어 쿼리를 주고받는지(통합) -> 동시 접속 1만 명을 버티는지(시스템) -> 기획자가 화면 UI와 흐름을 승인하는지(인수).
- **흔한 오해·주의점**: "테스트를 많이 하면 버그가 0이 될 것이다?" 불가능하다. 파레토 법칙에 따라 20%의 모듈에 80%의 결함이 집중된다. 테스트는 버그가 없음을 증명하는 게 아니라, 버그가 있음을 보여주는 활동이다 (Dijkstra).

## 연결 개념
- TDD (Test-Driven Development): 단위 테스트를 먼저 작성하고 코드를 짜는 개발 방법론
- 화이트박스 / 블랙박스 테스트: 테스트 내부 구조를 아느냐 모르느냐에 따른 기법 분류
- 테스트 커버리지: 코드의 어느 정도를 테스트했는지 측정하는 지표

# 📝 【답안용】 시험 답안 템플릿

## 핵심 인사이트 (3줄 요약)

> 1. **본질**: 소프트웨어 테스트는 개발 과정의 각 산출물이 요구사항(명세)과 사용자 의도(목적)를 충족하는지 계층적으로 검증(Verification) 및 확인(Validation)하는 활동이다.
> 2. **가치**: 결함을 조기 발견하여 수정 비용을 기하급수적으로 낮추고(Shift-Left 효과), 소프트웨어의 신뢰성을 정량적으로 보증한다.
> 3. **판단 포인트**: V-모델 기반의 4단계(단위-통합-시스템-인수)와 각 단계별 테스트 목적, 검증(Verification)과 확인(Validation)의 차이를 명확히 비교해야 한다.

## 출제 의도 및 답안 포인트

| 출제 의도 | 반드시 짚을 핵심 | 감점 회피 포인트 |
|:---|:---|:---|
| 소프트웨어 테스트 기본 원리 이해 | 결함 발견, 완벽한 테스트 불가능, V&V 차이 | 디버깅과 테스트의 개념 혼용 |
| V-모델 기반 단계별 매핑 역량 | 요구사항-인수, 아키텍처-통합, 상세설계-단위 매핑 | 단계별 목적을 구별하지 못하고 나열 |
| 실무적 테스트 적용 방안 | 자동화(CI/CD 연동), 테스트 커버리지 확보 | 수동 테스트 위주의 비효율적 방안 제시 |

> 요약: 테스트는 단순히 "버그를 잡는 일"이 아니라, 개발 각 단계의 산출물을 V-모델에 따라 체계적·계층적으로 검증하는 프로세스임을 보여주어야 한다.

---

## Ⅰ. 개요 및 필요성

- 개요: 소프트웨어의 결함을 식별하고, 명세서(Verification)와 사용자 요구사항(Validation)을 충족하는지 검증하는 체계적 활동
- 배경: 소프트웨어 규모와 복잡도 증가로 인해, 출시 후 발견되는 결함의 수정 비용이 기하급수적으로 증가(Boehm의 법칙)
- 필요성: 시스템 품질 및 신뢰성 확보, 유지보수 비용 절감, 무결점 서비스 제공을 통한 비즈니스 연속성 보장

---

## Ⅱ. 구조 및 구성요소

```text
[요구사항 분석] ------------------------------------> [인수 테스트 (Validation)]
      \                                                  /
    [아키텍처 설계] ----------------------------> [시스템 테스트 (Verification)]
          \                                          /
        [상세 설계] ------------------------> [통합 테스트 (Verification)]
              \                                  /
            [코딩] --------------------> [단위 테스트 (Verification)]
```

| 구성요소 | 매핑되는 개발 단계 | 주요 검증 내용 |
|:---|:---|:---|
| 단위 테스트 (Unit) | 상세 설계 | 개별 모듈(함수/클래스)의 독립적 기능 및 논리적 오류 |
| 통합 테스트 (Integration) | 아키텍처 (기본) 설계 | 모듈 간 인터페이스 및 데이터 교환 오류 (상향식/하향식) |
| 시스템 테스트 (System) | 시스템 설계 | 기능 및 비기능(성능/보안) 전체 요구사항 충족 여부 |
| 인수 테스트 (Acceptance) | 요구사항 분석 | 최종 사용자의 비즈니스 시나리오 및 만족도 (알파/베타) |

> 요약: V-모델을 기준으로 개발의 구체화 단계와 테스트의 추상화 단계가 1:1로 대응되며 검증 책임을 분할한다.

---

## Ⅲ. 동작원리 및 흐름도

```text
테스트 계획 수립 -> 테스트 케이스/스크립트 설계 -> 테스트 환경 구축 -> 테스트 실행 -> 결함 추적 및 보고
```

- 1단계 [계획 및 설계]: 요구사항 명세서를 바탕으로 테스트 전략을 세우고, 입력값-기대결과가 포함된 테스트 케이스(TC) 작성
- 2단계 [환경 구축]: 실제 운영 환경과 유사한 스테이징(Staging) 환경 및 테스트 데이터(Mock, Stub) 준비
- 3단계 [실행 및 결함 발견]: 단위부터 인수 단계까지 TC를 실행(수동/자동)하고, 기대결과와 실제결과의 불일치(결함) 식별
- 4단계 [결함 추적 및 회귀]: BTS(Bug Tracking System)에 결함을 등록하고, 수정 후 기존 기능이 깨지지 않았는지 회귀 테스트(Regression Test) 수행

> 요약: 체계적인 테스트 케이스 설계 기반으로 실행되며, 결함 수정 후에는 반드시 회귀 테스트를 거쳐 품질을 재검증한다.

---

## Ⅳ. 특징
- [완벽한 테스트 불가능]: 무한 경로와 입력값 조합으로 인해 100% 결함 없는 소프트웨어 증명은 불가능 (리스크 기반 테스트 필요)
- [살충제 패러독스(Pesticide Paradox)]: 동일한 테스트 케이스를 반복하면 새로운 버그를 찾지 못하므로 정기적 TC 리뷰 및 업데이트 필수
- [결함 집중(Defect Clustering)]: 파레토 법칙에 따라 20%의 핵심 모듈에 80%의 결함이 집중되므로 우선순위 할당 필요
- [정황 의존성(Context Dependent)]: 금융, 의료, 게임 등 도메인과 시스템 특성에 따라 테스트 전략과 기법이 다르게 적용되어야 함

> 요약: 테스트의 7가지 기본 원리를 내포하며, 한정된 자원 속에서 리스크가 높은 곳을 집중 공략하는 것이 특징이다.

## Ⅴ. 심화 비교 및 적용 판단

| 비교 축 | 검증 (Verification) | 확인 (Validation) | 선택 기준 |
|:---|:---|:---|:---|
| 핵심 질문 | Are we building the product right? | Are we building the right product? | 품질 통제 관점 vs 비즈니스 관점 |
| 기준 문서 | 소프트웨어 요구 명세서(SRS), 설계도 | 사용자 요구사항, 비즈니스 목표 | 기술적 정확성 vs 사용자 만족도 |
| 수행 단계 | 단위, 통합, 시스템 테스트 단계 | 인수 테스트 단계 | 수행 주체 (개발팀 vs 고객/QA) |

> 요약: 검증(Verification)은 설계대로 잘 만들었는지를, 확인(Validation)은 고객이 진짜 원하는 것인지를 따진다.

**리스크·대응:**
- [테스트 환경과 운영 환경 불일치]: 테스트 통과 후 운영에서 장애 발생 → IaC(Terraform) 및 컨테이너를 활용해 스테이징과 프로덕션 환경의 100% 동기화 (지표: 환경 설정 오류로 인한 장애 건수)
- [테스트 병목화]: 수동 테스트로 인해 CI/CD 파이프라인 지연 → 단위/통합 테스트의 80% 이상을 자동화 스크립트(JUnit, Selenium)로 대체 (지표: 테스트 자동화율)

**도입 후 점검 지표:**
- 결함 발견율(DRE): (테스트 단계 발견 결함 수) / (전체 발견 결함 수) — 테스팅 효과성
- 코드 커버리지(Code Coverage): 구문, 분기 등 소스코드가 실행된 비율 (목표 80% 이상) — 테스팅 충분성

## Ⅵ. 실무 적용 및 결론

**적용 방안 3개:**
1. 테스트 피라미드 전략: 비용이 적고 빠른 단위 테스트의 비중을 전체의 70%로 높이고, 느리고 비싼 UI/인수 테스트는 10%로 최소화하여 CI/CD 속도 확보
2. Shift-Left 테스팅: 코딩 완료 후 테스트하는 것이 아니라, 요구사항 분석 단계부터 QA가 참여해 테스트 시나리오를 선제 도출
3. 회귀 테스트 자동화: 결함 수정 및 기능 추가 시마다 기존 기능의 오작동 여부를 젠킨스(Jenkins) 파이프라인의 야간 배치(Nightly Build)를 통해 100% 자동 검증

**결론 (2줄):**
- 기술사 판단: 한정된 자원 속에서 완벽한 테스트는 불가능하므로, 리스크 기반 테스트(RBT)와 자동화를 통해 비즈니스 크리티컬 영역에 검증 역량을 집중해야 한다.
- 향후 방향: 최근 AI를 활용한 자동 테스트 케이스 생성 및 뮤테이션 테스트(Mutation Testing)가 발전하고 있어, 테스트 엔지니어링의 지능화가 요구된다.
