# 📖 【암기용】 개념 완전 이해

> 목적: 소프트웨어 테스트를 품질 확인과 결함 발견 흐름으로 이해하게 만든다. 시험 답안 양식이 아니라, 이해를 위한 설명이다.

## 한눈에
- **개요**: 요구사항 대비 결함과 품질 위험을 발견하는 검증 활동
- **왜 필요한가**: 코드는 작성자의 의도대로 보일 수 있으나 실제 요구사항, 연계 시스템, 사용자 환경에서는 다른 결과가 나올 수 있음. 테스트는 결함이 운영으로 유출되기 전 위험을 낮춤.
- **핵심 직관**: 완제품을 한 번만 검사하지 않고 부품, 조립, 완성품, 고객 승인 단계마다 다른 관점으로 확인함.

## 깊이 이해
- **배경·문제의식**: 요구사항 누락, 인터페이스 오류, 경계값 처리 실패는 개발 후반으로 갈수록 수정 비용이 증가함. V-model은 개발 산출물마다 대응 테스트를 배치해 조기 검증을 유도함.
- **작동 원리**: 단위 테스트는 함수와 클래스, 통합 테스트는 모듈 간 인터페이스, 시스템 테스트는 전체 요구사항, 인수 테스트는 사용자 승인 기준을 검증함. 테스트 피라미드는 자동화 단위 테스트를 넓게 두고 E2E 테스트를 제한함.
- **비유**: 자동차 제조에서 부품 검사, 엔진 조립 검사, 주행 시험, 고객 인도 검사를 나누는 것과 같음.
- **구체 예시**: 결제 서비스는 세금 계산 단위 테스트 500건, PG 연동 통합 테스트 80건, 주문 E2E 20건, UAT 승인 시나리오 10건을 단계별로 수행함.
- **흔한 오해·주의점**: 테스트는 결함이 없음을 증명하지 않음. 우선순위와 커버리지 기준으로 결함 발견 확률을 높이는 활동임.

## 연결 개념
- V-model: 개발 산출물과 테스트 단계를 대응
- Test Pyramid: 단위, 통합, E2E 테스트 비율 설계
- Defect Leakage: 결함이 상위 단계 또는 운영으로 유출되는 비율

# 📝 【답안용】 시험 답안 템플릿

> 목적: 시험장에서 25분에 그대로 쓰는 답안 양식. 작성방식(추상표현 금지·수치·도식·문제유형 전환)을 엄격히 지킨다.
> 핵심: 소프트웨어 테스트는 단계명 암기가 아니라 요구사항, 위험, 결함 유출률을 기준으로 검증 범위를 설계하는 활동임.

## 핵심 인사이트 (3줄 요약)

> 1. **본질**: 소프트웨어 테스트는 요구사항 대비 결함을 발견하고 품질 위험을 수치로 낮추는 검증·확인 활동임.
> 2. **가치**: 단위·통합·시스템·인수 테스트를 계층화해 결함 유출률과 운영 장애 가능성을 줄임.
> 3. **판단 포인트**: V-model, test pyramid, defect leakage, risk-based testing을 연결해야 정보 나열형 답안을 피할 수 있음.

## 출제 의도 및 답안 포인트

| 출제 의도 | 반드시 짚을 핵심 | 감점 회피 포인트 |
|:---|:---|:---|
| 테스트 단계 이해 확인 | unit, integration, system, acceptance 역할 | 단계명만 쓰고 산출물·검증 기준 누락 |
| 품질 관리 판단 확인 | V-model, test pyramid, defect leakage | 테스트를 개발 후 최종 활동으로 설명 |
| 실무 적용 역량 확인 | 자동화, 우선순위, 결함 추적 지표 | 커버리지 수치와 결함 지표 미제시 |

> 요약: 테스트 문제는 단계별 목적과 결함 유출 통제 지표를 연결하는 답안이 필요하다.

---

## Ⅰ. 개요 및 필요성

소프트웨어 테스트는 요구사항 충족 여부와 결함 존재 가능성을 확인하는 품질 검증 활동이다. 복잡한 시스템은 모듈, 인터페이스, 사용자 시나리오별 결함 양상이 다르므로 단일 테스트로 품질을 판단할 수 없다. 단계별 테스트와 자동화 지표를 통해 운영 전 결함 유출률을 관리해야 한다.

---

## Ⅱ. 구조 및 구성요소

```text
Requirement -> Test Basis -> Test Design -> Test Case
Test Case -> Execution -> Defect Report -> Retest/Regression
Unit/Integration/System/Acceptance -> Quality Decision
```

| 구성요소 | 역할 | 특이사항 |
|:---|:---|:---|
| Test Basis | 요구사항, 설계서, 사용자 스토리 | 추적성 matrix 기준 |
| Test Design | 기법 선택과 케이스 작성 | 경계값, 동등분할, 경로 |
| Test Execution | 자동/수동 테스트 수행 | CI 연계, test data 관리 |
| Defect Management | 결함 등록, 우선순위, 재시험 | severity, priority 분리 |

> 요약: 테스트 구조는 요구사항을 테스트 기준으로 바꾸고 실행 결과를 결함 관리와 품질 판정으로 연결한다.

---

## Ⅲ. 동작원리 및 흐름도

```text
요구사항 분석 -> 테스트 설계 -> 환경/데이터 준비
-> 테스트 실행 -> 결함 기록 -> 수정/재시험
-> 회귀 테스트 -> 종료 판정
```

| 단계 | 처리 내용 | 검증 기준 |
|:---:|:---|:---|
| 1 | 요구사항과 위험 분석 | 추적성 100% |
| 2 | 단위·통합·시스템·인수 테스트 설계 | priority P1 케이스 포함 |
| 3 | CI 또는 테스트 환경에서 실행 | pass rate 95% 이상 |
| 4 | 결함 수정 후 재시험과 회귀 테스트 | reopened defect 5% 이하 |
| 5 | 종료 기준과 잔여 위험 보고 | critical defect 0건 |

> 요약: 테스트는 요구사항 추적에서 시작해 실행, 결함 수정, 회귀 확인, 종료 판정 순서로 품질 위험을 줄인다.

---

## Ⅳ. 특징

| 구분 | 단일 후행 테스트 | 계층형 소프트웨어 테스트 | 수치·판단 포인트 |
|:---|:---|:---|:---|
| 검증 범위 | 완성품 중심 | unit, integration, system, acceptance | 요구사항 추적성 100% |
| 비용 구조 | 후반 결함 수정 비용 증가 | 조기 발견으로 재작업 감소 | 결함 유출률 5% 이하 목표 |
| 자동화 | 수동 시나리오 중심 | CI 기반 회귀 테스트 | 단위 테스트 70% 이상 비중 |
| 의사결정 | 감각적 출시 판단 | 종료 기준과 잔여 위험 보고 | critical defect 0건 |

> 요약: 계층형 테스트는 결함 발견 위치를 앞당기고 출시 판단을 추적성, pass rate, defect leakage 수치로 전환한다.

---

## Ⅴ. 심화 비교 및 적용 판단

| 비교 축 | 기존/대안 | 본 키워드 | 선택 기준 |
|:---|:---|:---|:---|
| 구조 | Big-bang 테스트 | V-model 기반 단계 검증 | 요구사항 변경률 10% 이상이면 추적성 필수 |
| 비용/성능 | E2E 과다 자동화 | test pyramid | CI 10분 이하 유지 |
| 운영/위험 | 결함 사후 대응 | defect leakage 추적 | 운영 결함 월 3건 이상이면 강화 gate 필요 |
| 품질판정 | 담당자 경험 | 종료 기준, 잔여 위험 | P1 결함 0건, P2 5건 이하 |

> 요약: 테스트 전략은 개발 단계, 변경 빈도, 결함 유출률, CI 실행 시간을 기준으로 선택한다.

| 리스크 | 원인 | 대응 방안 | 확인 지표 |
|:---|:---|:---|:---|
| 결함 유출 | 경계값·예외 케이스 누락 | risk-based testcase 보강 | defect leakage 5% 이하 |
| 테스트 취약성 | UI locator 변화, timing 의존 | 계약 테스트, 안정 locator 사용 | flaky test 2% 이하 |
| 데이터 오염 | 운영 유사 데이터 부재 | test data management, masking | 재현률 90% 이상 |
| 자동화 과부하 | E2E 비중 과다 | pyramid 비율 조정 | CI duration 10분 이하 |

> 요약: 테스트 리스크는 누락, 취약성, 데이터, 실행 시간이며 결함 유출률과 flaky 비율로 관리한다.

| 점검 항목 | 목표 기준 | 측정 방법 |
|:---|:---|:---|
| 요구사항 추적 | requirement coverage 100% | RTM, test management |
| 결함 관리 | critical defect 0건 | defect tracker |
| 자동화 품질 | regression pass rate 95% 이상 | CI report |
| 운영 유출 | escaped defect 5% 이하 | incident, RCA |

> 요약: 테스트 성공 여부는 요구사항 커버리지, 결함 심각도, 회귀 통과율, 운영 유출 결함으로 판단한다.

## Ⅵ. 실무 적용 및 결론

**적용 방안 3개 (필수 — 단계별 또는 항목별):**
1. 요구사항별 RTM을 작성해 단위, 통합, 시스템, 인수 테스트 케이스를 연결하고 누락 항목을 sprint 종료 전 보완함.
2. CI에서 단위 테스트 70%, 통합 테스트 20%, E2E 테스트 10% 비율을 목표로 회귀 테스트를 10분 내 실행하도록 구성함.
3. 결함은 severity와 priority를 분리하고 critical 0건, high 24시간 내 수정 SLA로 출시 gate를 운영함.

**결론 (2줄):**
- 기술사 판단: 변경 빈도와 장애 영향이 큰 시스템은 자동화 피라미드와 결함 유출률 관리를 적용하고, 탐색 테스트는 고위험 시나리오에 집중함.
- 향후 방향: 테스트는 AI 기반 테스트 생성, contract testing, observability 기반 운영 검증으로 확대됨.
