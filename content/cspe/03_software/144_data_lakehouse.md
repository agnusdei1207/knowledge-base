## 미리 알고가기

- 레이크하우스는 객체 스토리지 데이터에 테이블 메타데이터와 트랜잭션 기능을 결합한 구조임
- ACID는 트랜잭션의 원자성·일관성·격리성·지속성을 뜻함
- 오픈 테이블 포맷은 데이터 파일과 스냅샷·스키마·파티션 메타데이터의 관리 규칙을 정의함
- 스냅샷은 특정 커밋에서 유효한 데이터 파일 집합과 테이블 상태를 나타냄
- 낙관적 동시성 제어는 충돌이 없다고 가정해 쓰고 커밋 시 변경 충돌을 검사함
- Time Travel은 과거 스냅샷이나 버전의 테이블을 조회하는 기능임
- Compaction은 작은 파일이나 변경 로그를 큰 데이터 파일로 병합하는 유지관리 작업임

## 작성 근거(검토용)

- 레이크하우스는 객체 저장·테이블 메타데이터·ACID·다중 엔진·배치·스트림 통합을 핵심으로 선정함
- 비교표는 레이크·웨어하우스·레이크하우스를 저장·데이터·관리·처리·적합 업무로 대비함
- 절차는 데이터 파일 작성부터 메타데이터 커밋과 스냅샷 조회까지 테이블 상태 전이를 설명함
- 제목부터 결론까지 모든 문장·표 셀·요약을 5회 전수 검수해 세 구조의 분석 수준을 통일함

## Ⅰ. 개요

- **정의/개념**: 레이크하우스는 객체 스토리지에 테이블 포맷의 ACID·스키마·스냅샷 관리를 적용해 BI·배치·스트림·ML이 데이터를 공유하는 분석 구조임
- **배경/필요성**: 레이크와 웨어하우스 사이의 데이터 복제와 최신성 차이를 줄이고 다양한 엔진이 일관된 테이블을 공유하기 위해 메타데이터 계층이 필요함

## Ⅱ. 특징

- 데이터 파일은 객체 스토리지에 두고 스냅샷·스키마·파티션을 별도 메타데이터로 관리함
- 원자적 커밋과 일관된 스냅샷으로 동시 읽기·쓰기 중 부분 결과 노출을 방지함
- 스키마 강제·진화와 파티션 메타데이터로 데이터 변경과 질의 계획을 통제함
- SQL·배치·스트림·ML 엔진이 동일한 테이블 파일과 메타데이터를 읽을 수 있음
- 파일 압축·스냅샷 만료·통계 갱신을 수행하지 않으면 파일 수와 메타데이터 탐색 비용이 증가함

## Ⅲ. 종류 및 비교

| 판단 기준 | 데이터 레이크 | 데이터 웨어하우스 | 데이터 레이크하우스 |
|:---|:---|:---|:---|
| 저장 기반 | 객체 스토리지 파일 | 관리형 분석 저장 엔진 | 객체 스토리지와 테이블 메타데이터 |
| 데이터 범위 | 원천·반구조화·비구조화 포함 | 정제된 구조화 분석 데이터 | 원천 파일과 관리형 분석 테이블 공존 |
| 테이블 관리 | 파일·디렉터리와 카탈로그 중심 | 엔진이 트랜잭션·스키마 관리 | 오픈 테이블 포맷이 스냅샷·스키마 관리 |
| 처리 엔진 | 파일·SQL·ML 엔진별 해석 | 웨어하우스 SQL 엔진 중심 | SQL·배치·스트림·ML 엔진 공유 |
| 적합 업무 | 원천 보존·탐색 분석 | 정형 BI·공통 지표 | BI·ML·스트림이 같은 테이블을 공유하는 분석 |

> 요약: 레이크하우스는 객체 저장의 개방성과 테이블 메타데이터의 트랜잭션·스키마 관리를 결합함.

## Ⅳ. 구성요소 및 구조

| 구성요소 | 설명 |
|:---|:---|
| Object Storage·Data File | Parquet 같은 열 파일로 원천·분석 데이터를 저장함 |
| Table Format | 스냅샷·스키마·파티션·데이터 파일 참조와 커밋 규칙을 관리함 |
| Catalog | 테이블 이름과 현재 메타데이터 위치를 엔진에 제공함 |
| Compute Engine | SQL·배치·스트림·ML 작업이 같은 테이블 스냅샷을 읽고 씀 |
| Governance·Lineage | 소유자·분류·접근 정책·변환 계보를 테이블과 연결함 |
| Maintenance | 파일 압축·스냅샷 만료·통계 갱신으로 읽기 계획을 관리함 |

```text
SQL·Batch·Stream·ML
          |
     Catalog·Table Format
          |
Object Storage·Data Files
```

> 요약: 카탈로그와 테이블 포맷이 다중 연산 엔진을 객체 스토리지의 일관된 스냅샷에 연결함.

## Ⅴ. 원리 및 절차 흐름도

```text
데이터 파일 작성 -> 새 메타데이터 생성 -> 충돌 검사 -> 원자적 커밋 -> 스냅샷 조회
```

1. **파일 작성**: Writer가 기존 파일을 변경하지 않고 새 데이터·변경 파일을 객체 스토리지에 기록함
2. **메타데이터 생성**: 새 파일 집합·스키마·파티션·통계를 참조하는 스냅샷을 만듦
3. **충돌 검사**: 현재 테이블 버전과 Writer의 기준 버전을 비교해 동시 변경 충돌을 확인함
4. **원자적 커밋**: 카탈로그나 트랜잭션 로그가 새 메타데이터를 현재 버전으로 확정함
5. **스냅샷 조회**: Reader가 선택한 버전의 유효 파일만 계획해 일관된 결과를 읽음

> 요약: 레이크하우스 쓰기는 새 파일과 메타데이터를 만든 뒤 충돌 검사와 원자적 커밋으로 스냅샷을 전환함.

## Ⅵ. 실무 사례

1. 주문 CDC 테이블은 키 기반 병합과 파일 압축을 적용하고 커밋 충돌·평균 파일 크기를 확인함
2. 모델 학습 테이블은 스냅샷 버전을 고정하고 입력 행 수·체크섬을 대사함

## Ⅶ. 결론

- 레이크하우스는 엔진 호환성·트랜잭션 보장·스키마 진화와 파일 유지관리 비용으로 판단해야 함
