# 📖 【암기용】 개념 완전 이해

## 한눈에
- **개요**: 데이터 레이크의 유연성·저비용 스토리지와 데이터 웨어하우스(DW)의 트랜잭션 관리·성능을 결합한 통합 데이터 아키텍처다.
- **왜 필요한가**: 레이크는 비정형 데이터를 싸게 저장하지만 품질 통제가 안 되고, DW는 성능이 좋지만 비싸고 정형 데이터만 다룬다. 데이터를 두 번 복사할 필요 없이 한 곳에서 두 장점을 모두 얻기 위함이다.
- **핵심 직관**: 호수(Lake) 위에 튼튼한 집(House)을 지은 것이다. 물(원시 데이터)은 밑에 그대로 두고, 집 안에서는 깨끗한 물을 정돈된 선반(트랜잭션/스키마)에 올려두고 편하게 꺼내 쓴다.

## 핵심 용어 정리

| 용어/표기 | 의미 | 비유·예 |
|:---|:---|:---|
| 데이터 레이크하우스 (Lakehouse) | DW의 성능·트랜잭션 + 레이크의 저비용·유연성 | 호수 위의 집 |
| 오픈 테이블 포맷 (Open Table Format) | 레이크의 파일들에 RDB 같은 트랜잭션과 스키마를 부여하는 메타데이터 계층 | 파일들을 묶어주는 튼튼한 파일철 |
| ACID 트랜잭션 | 데이터의 무결성을 보장하는 성질 (원자성, 일관성 등) | 은행 송금처럼 안전한 데이터 기록 |
| 스토리지/컴퓨팅 분리 | 데이터를 저장하는 곳과 연산하는 곳을 물리적으로 나누어 각각 확장하는 구조 | 창고와 작업장을 따로 두기 |

## 깊이 이해
- **배경·문제의식**: 기존에는 비정형 데이터를 레이크에 쌓고, 이 중 일부를 ETL로 정제해 DW로 다시 복사(이중 아키텍처)했다. 이로 인해 데이터 중복, 높은 유지보수 비용, 데이터 최신성(지연) 문제가 발생했다.
- **작동 원리**: 저비용 객체 스토리지(S3 등)에 원시 데이터를 저장하는 것은 레이크와 동일하다. 그 위에 Delta Lake, Apache Iceberg 같은 **오픈 테이블 포맷**을 올려 메타데이터를 관리한다. 이 계층 덕분에 DW처럼 ACID 트랜잭션을 지원하고, Time Travel(과거 시점 조회)이 가능해진다.
- **비유**: 과거엔 지저분한 창고(레이크)에서 쓸만한 물건만 골라 비싼 진열장(DW)으로 매번 옮겼다면, 이제는 창고 한가운데에 스마트 재고 관리 시스템(오픈 테이블 포맷)을 달아 창고 자체를 진열장처럼 쓰는 것이다.
- **구체 예시**: Databricks가 이 개념을 창시했다. AWS S3에 Parquet 파일로 저장하고, 그 위에 Delta Lake를 얹어 Spark SQL이나 Athena로 즉시 DW 수준의 분석을 수행한다.
- **흔한 오해·주의점**: 물리적으로 새로운 하드웨어가 아니다. 기존 데이터 레이크 환경에 메타데이터 관리 계층(소프트웨어)을 추가하여 DW처럼 동작하게 만든 아키텍처 패러다임이다.

## 연결 개념
- 오픈 테이블 포맷 (Iceberg, Delta Lake, Hudi) — 레이크하우스를 구현하는 핵심 기반 기술
- 데이터 웨어하우스 (DW) — 레이크하우스가 흡수하고자 하는 트랜잭션/성능 특성의 원형
- 데이터 레이크 (Data Lake) — 레이크하우스의 스토리지 근간

# 📝 【답안용】 시험 답안 템플릿

## 핵심 인사이트 (3줄 요약)

> 1. **본질**: 저비용 객체 스토리지(데이터 레이크) 위에 ACID 트랜잭션, 스키마 관리, 인덱싱 기능을 제공하는 메타데이터 계층을 결합한 통합 데이터 플랫폼 아키텍처다.
> 2. **가치**: DW와 Data Lake 간의 이중 데이터 복제를 제거하여 파이프라인의 복잡성을 줄이고, 단일 저장소에서 BI와 AI/ML 워크로드를 동시 지원한다.
> 3. **판단 포인트**: 레이크하우스의 성패는 기반이 되는 오픈 테이블 포맷(Iceberg, Delta Lake, Hudi)의 선택과 성능(Compaction, Z-Ordering) 최적화 역량에 달려 있다.

## 출제 의도 및 답안 포인트

| 출제 의도 | 반드시 짚을 핵심 | 감점 회피 포인트 |
|:---|:---|:---|
| 차세대 데이터 플랫폼 아키텍처의 필요성과 특징 이해 | 이중 아키텍처 한계 극복, ACID 트랜잭션, 오픈 테이블 포맷 | DW나 데이터 레이크 중 하나로만 오해하는 추상적 서술 |

> 요약: 데이터 중복과 ETL 비용 문제를 해결하기 위해, 레이크 스토리지 위에 트랜잭션 관리 계층을 얹은 구조를 명확히 서술해야 한다.

---

## Ⅰ. 개요 및 필요성

- 개요: 데이터 레이크하우스는 데이터 레이크의 저비용·확장성과 데이터 웨어하우스의 데이터 관리·ACID 트랜잭션 기능을 결합한 차세대 데이터 아키텍처다.
- 배경: 기존의 Data Lake + DW 이중 아키텍처는 데이터 복사로 인한 스토리지 비용 증가, 긴 ETL 지연 시간, 거버넌스 파편화를 유발함
- 필요성: 단일 데이터 저장소에서 정형 데이터 기반 BI(Business Intelligence)와 비정형 데이터 기반 머신러닝(ML) 워크로드를 모두 처리할 통합 플랫폼 필수

---

## Ⅱ. 구조 및 구성요소

```text
Data Sources -> Lakehouse Storage (S3/HDFS) -> Metadata & Transaction Layer -> Compute Engines
(정형/비정형)   (Parquet/ORC 파일 저장)         (Delta Lake / Iceberg)        (Spark/Presto/BI)
```

| 구성요소 | 역할 | 특이사항 |
|:---|:---|:---|
| Lakehouse Storage | 정형·비정형 원천 데이터를 분산 객체 스토리지에 저장 | 컴퓨팅과 물리적 분리 |
| Open Data Format | 컬럼형 스토리지 포맷으로 데이터 파일 구성 | Apache Parquet, ORC |
| Transaction Layer | 파일 기반 스토리지에 ACID 트랜잭션 및 스키마 진화 지원 | 오픈 테이블 포맷(Iceberg 등) |
| Compute Layer | 메타데이터를 참조하여 분석 및 머신러닝 워크로드 수행 | Spark, Trino 연동 |

> 요약: 데이터 레이크하우스는 객체 스토리지 위에 테이블 포맷(메타데이터 계층)을 두어 트랜잭션 무결성을 보장하는 것이 핵심 구조다.

---

## Ⅲ. 동작원리 및 흐름도

```text
원시 데이터 인입 -> 객체 스토리지 저장 -> 메타데이터 갱신(트랜잭션) -> BI 및 ML 엔진 쿼리
```

- 1단계 [스토리지 저장]: 스트리밍 또는 배치 데이터가 클라우드 객체 스토리지에 Parquet 포맷의 파일로 분산 저장됨
- 2단계 [메타 갱신]: 데이터 적재와 동시에 Transaction Layer가 매니페스트(Manifest) 파일을 갱신하여 ACID 커밋 수행
- 3단계 [스키마 진화]: 스키마 변경 발생 시 데이터 재작성 없이 메타데이터 레벨에서 스키마 진화(Evolution) 처리
- 4단계 [쿼리 실행]: 분석 엔진(Trino 등)이 메타데이터를 읽어 필요한 파일만 정확히 타겟팅(Pruning)하여 고속 스캔

> 요약: 파일 조작에 트랜잭션 로그를 동반함으로써 동시 쓰기/읽기 상황에서도 데이터 정합성과 버전 관리(Time Travel)를 지원한다.

---

## Ⅳ. 특징
- ACID 트랜잭션 지원: 분산 객체 스토리지 상에서 원자성(Atomicity)을 보장하여 읽기/쓰기 충돌 및 실패 시 데이터 오염 방지
- Time Travel (시간 여행): 트랜잭션 로그를 기반으로 과거 특정 시점의 데이터 스냅샷을 조회하거나 복구(Rollback) 가능
- 스키마 관리 및 진화(Schema Evolution): 데이터 구조 변경(컬럼 추가/삭제) 시 전체 파일 재작성 없이 메타데이터 변경만으로 즉각 반영
- BI 및 ML 동시 지원: 정형 데이터의 빠른 쿼리 성능(DW 기능)과 비정형 데이터의 직접 접근(ML 기능)을 하나의 스토리지에서 처리

> 요약: 레이크하우스는 별도의 DW 적재 파이프라인 없이도 데이터 무결성과 강력한 쿼리 성능을 제공하여 플랫폼 복잡도를 획기적으로 낮춘다.

---

## Ⅴ. 심화 비교 및 적용 판단

| 비교 축 | Data Warehouse | Data Lake | Data Lakehouse | 선택 기준 |
|:---|:---|:---|:---|:---|
| 데이터 구조 | 정형 위주 | 모든 형태 (비정형 포함) | 모든 형태 (비정형 포함) | 데이터 다양성 |
| 트랜잭션/품질 | 완벽 지원 | 미지원 (스키마 온 리드) | 메타데이터 계층을 통해 지원 | 데이터 정합성 요구 수준 |
| 아키텍처 비용 | 높음 (스토리지/컴퓨팅 종속) | 낮음 | 중간~낮음 | TCO 절감 요건 |

> 요약: 단일 시스템으로 정형/비정형 데이터를 모두 통제하고, 데이터 엔지니어링 비용을 줄이려면 Data Lakehouse를 선택한다.

**리스크·대응 (기본 불릿):**
- Small File Problem: 잦은 스트리밍 쓰기로 작은 파일이 양산되어 메타데이터 오버헤드 발생 → 정기적인 Compaction(파일 병합) 작업 스케줄링 (지표: 평균 파일 사이즈)
- 쿼리 성능 한계: 전통적 DW 대비 복잡한 조인 성능 부족 → Z-Ordering, Min-Max 통계 기반의 데이터 프루닝(Pruning) 적극 활용 (지표: 쿼리 프루닝 비율)
- 벤더 종속성: 특정 클라우드의 관리형 레이크하우스 서비스 종속 → Iceberg, Delta 등 오픈 테이블 포맷(Open Format) 채택으로 회피 (지표: 멀티 클라우드 이식성)

**도입 후 점검 지표 (기본 불릿):**
- 성능/효율: 파티션 및 파일 프루닝 최적화 후의 95백분위수(p95) 조회 지연 시간 — 쿼리 프로파일링 분석
- 품질/운영: Compaction 및 Vacuum(과거 버전 삭제) 수행 후 확보된 객체 스토리지 절감 비율 — 스토리지 비용 모니터링

---

## Ⅵ. 실무 적용 및 결론

**적용 방안 3개:**
1. 이중 아키텍처 통합: 기존 AWS S3(Lake) + Redshift(DW) 구조를 S3 + Apache Iceberg 아키텍처로 통합하여 ETL 파이프라인(AWS Glue 등) 비용 및 시간 절감
2. 스트리밍과 배치 통합 분석: 클릭스트림(스트리밍)과 일일 매출(배치) 데이터를 하나의 메달리온 아키텍처(Bronze-Silver-Gold) 파이프라인으로 융합
3. ML Feature Store 활용: 레이크하우스의 Time Travel 기능을 이용해 머신러닝 모델 학습 시점의 피처(Feature) 스냅샷을 정확히 재현하여 모델 재학습

**결론:**
- 기술사 판단: 폭증하는 비정형 데이터 분석과 AI/ML 파이프라인 강화를 위해, 데이터 웨어하우스로의 2차 복제를 지양하고 데이터 레이크하우스 기반의 단일 저장소 전략을 수립해야 한다.
- 향후 방향: 오픈 테이블 포맷 간 상호 운용성을 높이기 위한 OneTable(XTable) 같은 통합 카탈로그 기술 발전으로, 벤더 종속성 없는 데이터 생태계가 구축될 것이다.
