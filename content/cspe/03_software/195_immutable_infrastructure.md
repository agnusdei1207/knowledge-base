## Ⅰ. 개요
- **정의**: 배포된 서버·컨테이너를 수정하지 않고, 변경이 필요하면 새 이미지를 빌드하여 교체하는 인프라 운영 모델
- **배경/필요성**: 가변 인프라에서 수작업 패치가 누적되면 서버 간 구성 편차(Configuration Drift)가 발생하여 장애 재현이 곤란함
- **비유**: 고장 난 전구를 수리하지 않고 새 전구로 교체하는 방식

| 출제 의도 | 반드시 짚을 핵심 | 감점 회피 포인트 |
|:---|:---|:---|
| 가변 vs 불변 인프라 비교 | Configuration Drift 제거 원리 | 상태 저장(DB 등) 처리 방안 언급 필요 |

> 요약: 인프라 구성 요소를 수정 불가로 취급하여 일관성과 재현성을 확보하는 운영 패러다임임

## Ⅱ. 구성요소
```text
Code Repo --> Image Build --> Image Registry --> Deploy(Replace)
                                                     |
                                               Old Instance
                                               (Terminate)
```

| 구성요소 | 설명 | 비유 |
|:---|:---|:---|
| Golden Image | OS·런타임·앱을 포함한 변경 불가 기준 이미지 | 공장 출하 완제품 |
| Image Registry | 버전별 이미지를 저장·배포하는 중앙 저장소 | 제품 창고 |
| Blue-Green/Canary | 신규 이미지로 교체 시 무중단 전환을 보장하는 배포 전략 | 교대 근무 |
| External State Store | DB·객체 스토리지 등 상태를 인스턴스 외부에 분리 저장 | 별도 금고 |

> 요약: Golden Image를 빌드·저장·배포하고, 상태는 외부 저장소에 분리하는 구조임

## Ⅲ. 절차
```text
변경요청 --> 이미지빌드 --> 테스트 --> 교체배포
```
- 1단계: 코드 또는 구성 변경 사항을 VCS에 커밋하여 변경 요청 발생
- 2단계: CI 파이프라인에서 새 Golden Image(AMI·컨테이너 이미지) 빌드
- 3단계: 스테이징 환경에서 이미지 기능·보안 검증 수행
- 4단계: Blue-Green 또는 Rolling 방식으로 운영 인스턴스를 새 이미지로 교체, 구 인스턴스 종료

> 요약: 커밋-빌드-검증-교체의 4단계로 인프라 변경을 이미지 단위로 관리함

## Ⅳ. 문제점
- 빌드 시간 증가: 사소한 변경에도 전체 이미지를 재빌드해야 하므로 배포 리드타임 증가
- 상태 관리 복잡: 로컬 디스크 의존 레거시 앱의 상태 외부화 리팩토링 부담 발생
- 이미지 누적 비용: 버전별 이미지가 레지스트리에 누적되어 스토리지 비용 증가

> 요약: 빌드 시간·상태 분리·이미지 누적이 실무 도입의 주요 과제임

## Ⅴ. 개선방안
1. 단기: 레이어 캐싱·멀티스테이지 빌드로 이미지 빌드 시간 단축
2. 중기: 상태 저장소(RDS·S3 등) 표준 패턴 가이드 수립으로 레거시 상태 외부화 촉진
3. 장기: 수명 주기 정책 기반 이미지 자동 정리(Lifecycle Policy)로 누적 비용 관리

> 요약: 빌드 최적화-상태 패턴 가이드-자동 정리 순으로 불변 인프라 실효성을 높이는 방향임

## Ⅵ. 전망
- 발전 방향: GitOps와 결합하여 인프라 변경의 선언적 관리·자동 롤백이 표준화
- 기술사적 판단: 클라우드 네이티브 운영의 기본 전제로서 가변 인프라 대비 우위 확립
- 기술사 제언: 상태 분리 설계와 CI/CD 파이프라인 통합을 전제로 도입 전략 수립 필요
