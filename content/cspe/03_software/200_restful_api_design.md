## 미리 알고가기

- REST는 클라이언트-서버·무상태·캐시·균일 인터페이스·계층화 제약을 적용하는 아키텍처 스타일임
- 자원은 URI로 식별하고 HTTP 메서드는 자원에 수행할 표준 의미를 나타냄
- GET은 안전하고 멱등적이며 PUT·DELETE는 멱등적이지만 POST는 같은 요청 반복의 결과가 같다고 보장하지 않음
- 상태 코드는 처리 결과, 미디어 타입은 표현 형식, ETag와 조건부 요청은 캐시 재검증·동시성 조건을 전달함
- 무상태는 서버가 데이터를 저장하지 않는다는 뜻이 아니라 각 요청이 처리에 필요한 클라이언트 문맥을 포함한다는 뜻임
- 균일 인터페이스는 자원 식별·표현 조작·자기 서술 메시지·하이퍼미디어 기반 상태 전이를 포함함

## 작성 근거(검토용)

- RESTful API는 자원 식별, 메서드 의미, 무상태, 표현, 상태 코드, 캐시, 오류 계약을 핵심 축으로 설명함
- 비교표는 RPC식 HTTP와 자원·행위·상태·캐시·결합·적합 조건을 같은 수준에서 대비함
- 주문 생성과 상품 조회는 중복 생성률·p95 지연·캐시 적중률·응답 크기로 검증함

## Ⅰ. 개요

- **정의/개념**: RESTful API는 자원을 URI로 식별하고 HTTP 메서드·상태 코드·헤더·표현을 균일 인터페이스로 사용하며 요청 무상태와 캐시 제약을 적용한 API임
- **배경/필요성**: 클라이언트마다 별도 연산 규칙을 학습하는 결합을 줄이고 HTTP 중계·캐시·인증 계층이 메시지 의미를 해석할 수 있도록 공통 인터페이스가 필요함

## Ⅱ. 특징

- URI는 `/orders/{id}`처럼 자원을 나타내고 생성·조회·전체 교체·삭제를 HTTP 메서드 의미로 구분함
- 요청마다 인증 정보·자원 식별자·처리 조건을 포함해 서버 세션에 의존하지 않는 처리를 구성함
- 성공·클라이언트 오류·서버 오류를 상태 코드로 구분하고 오류 본문에 코드·설명·추적 식별자를 제공함
- Accept·Content-Type으로 표현 형식을 협상하고 ETag·If-Match로 캐시 재검증과 조건부 갱신을 수행함
- 목록 API는 필터·정렬·페이지네이션 순서를 고정하고 다음 페이지 토큰과 결과 한도를 계약에 포함함
- 링크 관계를 표현에 포함하면 클라이언트가 URI 문자열을 조합하지 않고 가능한 다음 상태 전이를 선택할 수 있음

## Ⅲ. 종류 및 비교

| 판단 기준 | RPC식 HTTP API | RESTful API |
|:---|:---|:---|
| 인터페이스 대상 | URI에 실행할 연산을 표현 | URI에 자원을 표현 |
| 행위 표현 | 요청명·본문의 명령으로 구분 | HTTP 메서드의 안전성·멱등성 의미 사용 |
| 요청 문맥 | 서버 세션이나 연산별 상태에 의존 가능 | 각 요청에 처리 문맥을 포함 |
| 응답 의미 | 응용별 성공·오류 코드 정의 | HTTP 상태 코드와 표현 계약 사용 |
| 캐시 조건 | 연산별로 별도 캐시 규칙 구현 | GET·Cache-Control·ETag 의미 활용 |
| 결합 지점 | 클라이언트가 연산명과 인자 계약에 결합 | 클라이언트가 자원·표현·링크 계약에 결합 |
| 적합 조건 | 명령 중심 내부 호출과 행위별 계약 필요 | 자원 수명주기와 HTTP 중계·캐시 활용 필요 |

> 요약: RESTful API는 자원을 URI로 식별하고 HTTP 메서드·상태 코드·캐시 의미를 균일 인터페이스로 사용함.

## Ⅳ. 구성요소 및 구조

| 구성요소 | 설명 |
|:---|:---|
| 자원 URI | 업무 개체와 계층 관계를 명사형 경로로 식별함 |
| HTTP 메서드 | GET·POST·PUT·PATCH·DELETE로 조회·생성·변경·삭제 의미를 전달함 |
| 상태 코드 | 성공·리다이렉션·요청 오류·서버 오류의 처리 결과를 구분함 |
| 표현·미디어 타입 | JSON·XML 등 자원 상태의 전송 형식과 스키마를 정의함 |
| 헤더·조건부 요청 | 인증·콘텐츠 협상·캐시·ETag 기반 갱신 조건을 전달함 |
| 링크 관계 | 자원 표현에 가능한 다음 상태 전이와 대상 URI를 제공함 |
| 오류·목록 계약 | 오류 코드·추적 식별자와 필터·정렬·페이지 토큰을 정의함 |

```text
Client -> URI + Method + Headers + Representation
       -> Stateless API -> Domain Resource
       <- Status + Headers + Representation
```

> 요약: URI·메서드·헤더가 요청 의미와 조건을 전달하고 상태 코드·표현이 처리 결과와 자원 상태를 반환함.

## Ⅴ. 원리 및 절차 흐름도

```text
요청 식별 -> 인증·조건 확인 -> 메서드 의미 적용 -> 자원 처리 -> 상태·표현 반환
```

1. **요청 식별**: 라우터가 URI·메서드·미디어 타입으로 대상 자원과 처리기를 결정함
2. **인증·조건 확인**: 토큰 권한과 If-Match·If-None-Match 등 요청 조건을 검증함
3. **메서드 의미 적용**: 안전성·멱등성·부분 또는 전체 변경 계약에 따라 요청을 해석함
4. **자원 처리**: 도메인 규칙과 저장소 트랜잭션으로 자원을 조회·생성·변경함
5. **상태·표현 반환**: 처리 결과에 맞는 상태 코드·헤더·자원 또는 오류 표현을 반환함

> 요약: RESTful 요청은 URI·HTTP 의미·조건을 검증한 뒤 자원을 처리하고 표준 상태 코드와 표현으로 결과를 전달함.

## Ⅵ. 실무 사례

1. 주문 생성 API는 POST와 멱등성 토큰을 적용하고 중복 주문률·p95 응답 시간을 확인함
2. 상품 목록 API는 커서 페이지네이션과 ETag를 적용하고 캐시 적중률·응답 크기를 확인함

## Ⅶ. 결론

- RESTful API는 자원 경계·HTTP 메서드 의미·무상태·오류·캐시 계약을 클라이언트 수명주기와 함께 설계해야 함
