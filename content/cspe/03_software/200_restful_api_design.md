# 📖 【암기용】 개념 완전 이해

> 목적: RESTful API 설계 원칙을 처음 보는 사람도 URI, HTTP 메서드, 상태 코드, 버전 관리가 왜 필요한지 완전히 이해하게 만든다. 시험 답안 양식이 아니라, 이해를 위한 친절한 설명이다.

## 한눈에
- **개요**: RESTful API 설계는 **REST(Representational State Transfer) 아키텍처 스타일**의 제약 조건을 실제 API에 구현하는 원칙이며, 핵심은 리소스를 URI로 식별하고 행위를 HTTP 메서드로, 처리 결과를 상태 코드로 표현하는 것이다.
- **왜 필요한가**: API가 함수 호출처럼 제각각 설계되면 클라이언트가 동작을 예측하기 어렵고, 캐시·재시도·버전 변경 시 장애가 발생하기 쉽다.
- **핵심 직관**: 서버 기능명을 부르는 것(RPC식)이 아니라, 웹상의 자원 주소(URI)에 표준 동작(HTTP 메서드)을 적용하는 방식이다.

## 핵심 용어 정리 (내부에 등장하는 것들)

| 용어 | 의미 | 비유 |
|:---|:---|:---|
| REST (상위 아키텍처 스타일) | 자원 중심으로 시스템을 설계하는 제약 조건의 모음 — RESTful API는 이를 구현한 결과물 | 건축 양식(REST)과 실제로 지은 건물(RESTful API) |
| 리소스 (Resource) | URI로 식별되는 자원 — 주문, 고객, 상품 같은 명사 | 도서관의 책 한 권 |
| URI | 리소스를 가리키는 주소 — 계층 구조의 명사형 경로 | 책의 청구기호 |
| HTTP 메서드 | 리소스에 가할 행위를 표현하는 표준 동사(GET/POST/PUT/PATCH/DELETE) | "본다/등록한다/통째로 바꾼다/일부 고친다/반납한다" |
| 상태 코드 (Status Code) | 처리 결과를 숫자로 알리는 3자리 코드 — 2xx 성공, 4xx 클라이언트 오류, 5xx 서버 오류 | 택배 배송 상태(배송중/배송완료/주소오류/창고화재) |
| 멱등성 (Idempotency) | 같은 요청을 여러 번 보내도 서버 상태가 한 번 보낸 것과 같은 성질 | 엘리베이터 버튼 — 여러 번 눌러도 도착 층은 같다 |
| 무상태성 (Stateless) | 서버가 요청 간 클라이언트 상태를 기억하지 않는 성질 | 매번 신분증을 다시 보여줘야 하는 창구 |
| 버전 관리 (Versioning) | API가 바뀌어도 기존 클라이언트가 깨지지 않도록 구버전을 유지하는 정책 | 앱을 업데이트해도 구버전 사용자를 당분간 계속 지원하는 것 |

## 깊이 이해

### 명사형 URI vs 동사형 URI (판별 원리 + 워크드 예제)
- RPC식(안티패턴): `GET /getOrder?id=123`, `POST /updateOrderStatus?id=123&status=SHIPPED` — URI 자체에 동작(get, update)이 들어있어, 새 기능을 추가할 때마다 새 함수명을 계속 만들어야 한다.
- RESTful(권장): `GET /orders/123`(조회), `PUT /orders/123`(전체 수정), `PATCH /orders/123`(부분 수정), `DELETE /orders/123`(삭제) — URI는 항상 `/orders/123`으로 고정되고, **행위는 HTTP 메서드가 표현**한다. 자원이 늘어나도 규칙은 그대로 재사용된다.
- 판별 원리: URI에 동사(get, update, delete 등)가 보이면 RPC식으로 오염된 것이다. "이 URI가 명사만으로 자원을 가리키는가?"가 자가 점검 기준이다.

### HTTP 메서드별 멱등성 표 (구체 예제로 확인)
| 메서드 | 멱등성 | 안전성(서버 상태 불변) | 예시 |
|:---|:---|:---|:---|
| GET | 멱등 | 안전 | `GET /orders/123` 몇 번 조회해도 데이터 안 바뀜 |
| POST | 비멱등 | 불안전 | `POST /orders` 두 번 보내면 주문 2건 생성됨 |
| PUT | 멱등 | 불안전 | `PUT /orders/123 {status:"SHIPPED"}` 두 번 보내도 결과는 SHIPPED로 동일 |
| PATCH | 보통 비멱등 | 불안전 | `PATCH /orders/123 {qty:+1}`처럼 상대값 수정이면 보낼 때마다 값이 누적되어 바뀜 |
| DELETE | 멱등 | 불안전 | `DELETE /orders/123` 두 번 보내도(두 번째는 404) 최종 상태는 "삭제됨"으로 동일 |

여기서 "멱등"은 여러 번 보내도 **서버 최종 상태가 같다**는 뜻이지, 응답 코드까지 같다는 뜻은 아니다(DELETE 두 번째 호출은 404를 반환할 수 있다).

### 상태 코드를 숫자대로 이해하기
- **2xx (성공)**: `200 OK`(조회·수정 성공), `201 Created`(생성 성공, Location 헤더에 새 URI 포함), `204 No Content`(성공했지만 응답 본문 없음, 예: DELETE)
- **4xx (클라이언트 잘못)**: `400 Bad Request`(요청 형식 오류), `401 Unauthorized`(인증 안 됨), `403 Forbidden`(인증됐지만 권한 없음), `404 Not Found`(리소스 없음), `409 Conflict`(이미 처리된 요청과 충돌, 예: 중복 생성), `429 Too Many Requests`(요청 한도 초과)
- **5xx (서버 잘못)**: `500 Internal Server Error`(서버 내부 오류), `503 Service Unavailable`(일시적 과부하·점검)
- 판별 원리: "누구 책임인가"로 앞자리를 정한다 — 클라이언트가 잘못 보냈으면 4xx, 서버가 처리하다 실패했으면 5xx.

### 버전 관리 3가지 방식 비교
| 방식 | 예시 | 장점 | 단점 |
|:---|:---|:---|:---|
| URI 버전 | `/v1/orders`, `/v2/orders` | 눈으로 바로 보여 직관적 | URI가 "같은 자원"을 가리키지 못하게 됨(REST 원칙과 충돌 논쟁) |
| 헤더 버전 | `Accept-Version: 2` | URI는 그대로 유지 | 클라이언트가 헤더를 놓치면 기본 버전으로 동작해 혼란 |
| 미디어 타입 버전 | `Accept: application/vnd.company.v2+json` | HTTP 표준 협상 메커니즘 그대로 사용 | 헤더 문법이 복잡해 실무 진입장벽이 있음 |

실무에서는 이해하기 쉬운 URI 버전을 가장 많이 쓰고, 구버전은 폐기 일정(Deprecation)을 공지 후 제거한다.

### 비유와 흔한 오해
- **비유**: 도서관에서 책의 청구기호가 URI, 대출·반납·조회 규칙이 HTTP 메서드, 처리 결과 영수증이 상태 코드다.
- **오해**: RESTful은 URL만 예쁘게 만드는 일이 아니다. 무상태성, 캐시 가능성, 멱등성, 인증, 일관된 오류 응답 형식, 버전 정책까지 함께 설계해야 "RESTful"이라 부를 수 있다. 명사형 URI만 지키고 GET으로 데이터를 수정하는 식이면 겉모습만 REST일 뿐이다.

## 연결 개념
- SOAP vs REST — RESTful 설계 원칙이 REST 아키텍처 스타일에서 파생되는 배경
- OpenAPI — REST API 계약을 문서화하고 테스트를 자동화하는 표준
- API Gateway — 인증·라우팅·제한·관측성을 적용하는 지점

# 📝 【답안용】 시험 답안 템플릿

> 목적: RESTful API를 원칙, 구조, 오류 처리, 보안, 운영 지표까지 포함해 답안화한다.
> 핵심: 출제자는 URI 규칙 암기가 아니라 리소스 모델링과 HTTP 의미론을 지키는 설계 판단을 본다.

## 핵심 인사이트 (3줄 요약)

> 1. **본질**: RESTful API는 리소스를 URI로 식별하고 HTTP 메서드, 상태 코드, 헤더를 표준 의미에 맞게 사용하는 API 설계 원칙이다.
> 2. **가치**: 클라이언트 예측성, 캐시 활용, 게이트웨이 정책, 문서화, 테스트 자동화를 통해 API 변경 위험을 줄인다.
> 3. **판단 포인트**: 명사형 리소스, 무상태성, 멱등성, 상태 코드, 버전 관리, 인증·인가, 오류 형식을 함께 설계해야 한다.

## 출제 의도 및 답안 포인트

| 출제 의도 | 반드시 짚을 핵심 | 감점 회피 포인트 |
|:---|:---|:---|
| REST 설계 원칙 이해 확인 | 리소스 URI, HTTP 메서드, 상태 코드 | URL 규칙만 설명 |
| API 품질 판단 확인 | 멱등성, 캐시, 버전, 오류 형식 | GET으로 수정 처리 |
| 실무 적용 역량 확인 | OpenAPI, Gateway, OAuth2, Rate Limit | 보안과 운영 지표 누락 |

> 요약: RESTful API 답안은 리소스 모델링과 HTTP 의미론을 운영·보안 설계까지 연결해야 한다.

## Ⅰ. 개요 및 필요성

- 개요: HTTP 기반 리소스 설계 원칙
- 배경: API 사용자가 늘수록 URI, 메서드, 상태 코드, 오류 응답이 일관되어야 장애와 변경 비용을 줄일 수 있다.
- 필요성: HTTP method, status code, OpenAPI, versioning 기준으로 MSA와 외부 API 계약을 관리한다.

---

## Ⅱ. 구조 및 구성요소

```text
Client -> API Gateway -> Resource URI -> HTTP Method
                    +-> Auth/Rate Limit -> Service -> Response/Status Code
```

| 구성요소 | 역할 | 특이사항 |
|:---|:---|:---|
| Resource URI | 자원 식별 | 명사형, 계층 구조, 복수형 |
| HTTP Method | 행위 표현 | GET, POST, PUT, PATCH, DELETE |
| Status Code | 처리 결과 표현 | 200, 201, 400, 401, 404, 409, 500 |
| Representation | JSON 응답 모델 | Content-Type, pagination |
| API Policy | 보안·운영 통제 | OAuth2, Rate Limit, CORS |

> 요약: RESTful API는 URI, 메서드, 상태 코드, 표현, 정책이 일관될 때 클라이언트 예측성이 생긴다.

---

## Ⅲ. 동작원리 및 흐름도

```text
리소스 모델링 -> URI 설계 -> 메서드/멱등성 매핑
-> 상태 코드/오류 형식 정의 -> OpenAPI 문서화 -> Gateway 정책 적용
```

| 단계 | 처리 내용 | 검증 기준 |
|:---:|:---|:---|
| 1 | 리소스와 관계 식별 | 주문, 고객, 결제 등 명사 |
| 2 | HTTP 메서드 매핑 | GET 조회, POST 생성, PUT 전체 수정 |
| 3 | 상태 코드와 오류 모델 정의 | 4xx/5xx 구분, error code |
| 4 | 보안·제한 정책 적용 | OAuth2, JWT, 1000 req/min |
| 5 | 문서화와 계약 테스트 | OpenAPI, contract test |

> 요약: RESTful 설계는 리소스 모델링에서 시작해 HTTP 의미론, 오류 모델, 문서화, 게이트웨이 정책으로 이어진다.

## Ⅳ. 특징

| 구분 | RPC식 API | RESTful API | 판단 포인트 |
|:---|:---|:---|:---|
| URI | `/getOrder` 동사형 | `/orders/{id}` 명사형 | 리소스 중심 |
| 행위 | 함수명에 포함 | HTTP 메서드 사용 | 멱등성 준수 |
| 결과 | 임의 코드 | HTTP 상태 코드 | 클라이언트 처리 |
| 운영 | 개별 구현 | Gateway 정책 적용 | 인증·제한·관측성 |
| 변경 | 암묵적 계약 | OpenAPI와 버전 | 호환성 관리 |

> 요약: RESTful API는 기능 호출을 리소스 조작으로 전환해 표준 HTTP 동작과 운영 정책을 활용한다.

## Ⅴ. 심화 비교 및 적용 판단

| 비교 축 | 기존/대안 | 본 키워드 | 선택 기준 |
|:---|:---|:---|:---|
| 구조 | RPC, SOAP | RESTful API | 웹·모바일·MSA 공개 API |
| 비용/성능 | 메서드 의미 불명확 | 캐시·Gateway·CDN 활용 | 조회 비율 70% 이상 |
| 운영/위험 | 문서와 구현 불일치 | OpenAPI 계약 테스트 | 다수 클라이언트 존재 |

> 요약: RESTful API는 웹 표준과 클라이언트 다양성이 필요한 서비스에서 우선 선택한다.

| 리스크 | 원인 | 대응 방안 | 확인 지표 |
|:---|:---|:---|:---|
| URI 난립 | 리소스 모델 부재 | API 스타일 가이드와 리뷰 | 신규 API 규칙 위반 건수 |
| 멱등성 위반 | POST/PUT/PATCH 혼용 | 메서드별 의미 정의 | 중복 요청 장애 건수 |
| 버전 충돌 | 호환성 정책 부재 | `/v1`, Header 버전, Deprecation | 계약 테스트 통과율 |

> 요약: RESTful API 리스크는 설계 일관성, 멱등성, 버전 관리에서 발생하므로 스타일 가이드와 계약 테스트가 필요하다.

| 점검 항목 | 목표 기준 | 측정 방법 |
|:---|:---|:---|
| API 품질 | OpenAPI 커버리지 100% | 문서 빌드, lint |
| 성능 | p95 지연 300ms, 5xx 0.1% 이하 | APM, Gateway 로그 |
| 보안/운영 | OAuth2 적용 100%, Rate Limit 위반 추적 | Gateway, IAM 로그 |

> 요약: RESTful API는 문서화, 지연시간, 오류율, 인증·제한 정책 준수로 운영 품질을 점검한다.

## Ⅵ. 실무 적용 및 결론

**적용 방안 3개:**
1. URI는 명사형 복수 리소스로 표준화하고 GET/POST/PUT/PATCH/DELETE의 멱등성 규칙을 API 스타일 가이드에 명시함
2. 오류 응답은 `code`, `message`, `traceId`, `details` 형식으로 통일하고 HTTP 400, 401, 403, 404, 409, 429, 500을 구분함
3. OpenAPI 기반 계약 테스트, OAuth2/JWT 인증, Rate Limit 1000 req/min, API Gateway 로그를 CI/CD와 운영 대시보드에 연결함

**결론 (2줄):**
- 기술사 판단: RESTful API는 웹·모바일·MSA의 기본 선택지이며, 실시간 양방향은 WebSocket, 고성능 내부 호출은 gRPC를 별도 검토함
- 향후 방향: API Gateway, OpenAPI, Backward Compatibility, Zero Trust 인증을 결합해 API 제품 관리 체계로 확장함
