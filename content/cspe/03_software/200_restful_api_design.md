## 핵심 인사이트 (3줄 요약)
- 아무렇게나 주소를 파서 데이터를 주고받는 게 아니라, **"URL은 100% 명사(자원)로만 짓고, 행위는 오직 HTTP 메서드(GET/POST/PUT/DELETE)로만 표현하라"**는 현대 웹의 절대적인 약속.
- 잘 설계된 REST API는 개발자가 문서를 보지 않고도 주소와 메서드만 보면 "아, 이 URL에 GET을 날리면 123번 유저 정보가 나오겠구나"라고 직관적으로 짐작할 수 있는 **자기 서술성(Self-descriptiveness)**을 가짐.
- HATEOAS(하이퍼미디어 기반 상태 전이)를 통해 응답 결과 안에 "다음에 누를 수 있는 버튼(URL 링크)"까지 서버가 전부 내려주는 형태가 REST 창시자(로이 필딩)가 원했던 진정한 REST(성숙도 레벨 3)의 궁극적 모습임.
---
## Ⅰ. 개요 및 필요성
- **개요**: 분산 시스템 환경에서 웹(HTTP)의 본래 설계 사상을 철저히 따르며, 자원(Resource)의 상태(State)를 주고받는 애플리케이션 프로그래밍 인터페이스 설계 원칙.
- **필요성**: A 개발자는 `/getUsers`로 만들고, B 개발자는 `/delete-user?id=1`로 만들고, C 개발자는 데이터를 삭제하는데 무조건 `POST` 메서드를 씀. 프론트엔드 개발자는 빡쳐서 퇴사함. **"제발 주소창(URL)에 동사 좀 쓰지 마! 전 세계 개발자가 공통으로 이해할 수 있는 아름답고 통일된 주소 규칙을 만들자!"**라며 RESTful 설계 원칙이 확립됨.
---
## Ⅱ. 아키텍처 및 핵심 원리
- **1. URL은 오직 명사(자원)로만**:
  - ❌ 나쁜 예 (동사 포함): `POST /createArticle`, `GET /getArticleList`
  - ⭕ 좋은 예 (명사만): `POST /articles` (생성), `GET /articles` (목록 조회)
  - 자원의 계층 관계는 슬래시(`/`)로 표현함: `GET /users/123/orders/456` (123번 유저의 456번 주문 내역).
- **2. 행위는 HTTP 메서드로**:
  - `GET`: 조회 (안전하고, 100번 눌러도 결과가 같은 멱등성을 가짐).
  - `POST`: 생성 (새로운 자원 등록).
  - `PUT`: 전체 수정 (기존 데이터를 통째로 덮어씌움).
  - `PATCH`: 부분 수정 (이름만 쏙 바꿀 때).
  - `DELETE`: 삭제.
- **3. 리처드슨 성숙도 모델 (Richardson Maturity Model)**:
  - **Level 0**: 그냥 HTTP 하나(POST)로 다 처리함. (SOAP 수준)
  - **Level 1**: 명사 자원(URL)을 쪼개기 시작함.
  - **Level 2**: HTTP 메서드(GET/POST/PUT)와 상태 코드(200, 404, 500)를 정확히 사용함. (보통 현업에서 말하는 REST).
  - **Level 3 (HATEOAS)**: 응답 데이터(JSON) 안에 다음 행동을 할 수 있는 링크(Link)를 포함함. (진정한 REST).

```text
[ REST API 통신 예시: 리처드슨 레벨 2 vs 레벨 3(HATEOAS) ]

 📊 [ 레벨 2 수준의 응답 (현재 실무 대세) ]
 GET /accounts/12345
 {
    "account": { "id": "12345", "balance": 100 }
 }
 -> 클라이언트: "잔액이 100원이네. 입금하려면 /deposit을 내가 알아서 찾아야지."

 🔗 [ 레벨 3 수준의 응답 (진정한 REST - HATEOAS) ]
 GET /accounts/12345
 {
    "account": { "id": "12345", "balance": 100 },
    "links": [
       { "rel": "deposit", "href": "/accounts/12345/deposit" },
       { "rel": "withdraw", "href": "/accounts/12345/withdraw" }
    ]
 }
 -> 클라이언트: "아하! 서버가 입금, 출금 버튼(URL)을 친절하게 다 내려줬네? 이것만 누르면 되겠다!"
```

## Ⅲ. 비교 및 연결
| 메서드 | 멱등성 (Idempotency, 여러 번 눌러도 같은가?) | 주 사용처 | 잘못된 사용 예 |
|---|---|---|---|
| **GET** | O (100번 조회해도 데이터 안 변함) | 데이터 조회 | `GET /deleteUser?id=1` (조회로 삭제하면 대참사 남) |
| **POST** | X (100번 누르면 게시글 100개 생김) | 데이터 생성 | 데이터를 조회할 때 검색 조건이 길다고 POST로 던짐 |
| **PUT** | O (100번 덮어씌워도 결국 똑같음) | 데이터 전체 교체 | 이름만 바꿀 때 PUT 쓰면 다른 필드가 다 Null로 날아감 |
| **PATCH** | X (상황에 따라 다름) | 데이터 일부 수정 | - |
| **DELETE**| O (100번 삭제해도 지워진 상태로 똑같음)| 데이터 삭제 | - |

## Ⅳ. 실무 적용 및 기술사 판단
- **HTTP 상태 코드의 엄격한 반환**: 신입 백엔드 개발자들의 가장 큰 죄악은 에러가 났을 때 HTTP 응답 코드는 200(성공)으로 던지면서, JSON 본문에 `{"status": "error", "message": "못 찾음"}`이라고 쓰는 것임. 기술사는 **"HTTP 상태 코드 자체가 메시지다"**라는 REST 철학을 강제해야 함. 찾을 수 없으면 404, 권한이 없으면 403, 서버가 죽었으면 500을 HTTP 헤더 레벨에서 정확히 반환해야 API 게이트웨이나 모니터링 툴(Datadog)이 시스템 상태를 정상적으로 집계할 수 있음.
- **REST의 한계와 대안 (Over-fetching 문제)**: REST는 무조건 정해진 형태의 전체 JSON 데이터를 다 내려줌. 모바일 화면에서 회원의 '이름'만 필요한데, REST를 호출하면 이름, 주소, 나이, 결제 내역까지 1MB를 통째로 받아와서 데이터를 낭비(Over-fetching)함. 따라서 최신 실무에서는 클라이언트가 **"원하는 데이터만 쏙쏙 골라서 쿼리하는" GraphQL**을 프론트엔드용 차세대 API로 섞어 쓰는(BFF 패턴) 추세임.

## Ⅴ. 기대효과 및 결론
- "URL만 봐도 무슨 데이터가 오갈지 뻔히 보이는" 극강의 직관성을 제공하여, 전 세계 프론트엔드와 백엔드 개발자 간의 소통 비용(API 문서 해독 시간)을 거의 0으로 만듦.
- SOAP의 끔찍한 복잡성을 무너뜨리고 클라우드 네이티브와 마이크로서비스(MSA) 생태계의 가장 튼튼한 통신 대동맥으로 자리 잡은 IT 역사상 가장 성공적인 설계 철학임.

### 👶 어린이를 위한 3줄 비유 설명
1. 장난감 가게에 가서 "로봇 하나 만들어줘! 로봇 줘! 로봇 부숴줘!"라고 매번 문장을 다르게 쓰면 직원이 헷갈려요.
2. **RESTful API**는 "앞으로 무조건 [행동] + [장난감 이름]으로만 짧게 말하자!"는 전 세계 약속이에요.
3. 예를 들어 `[만들기(POST)] + [로봇]` 하면 찰떡같이 알아듣고, `[가져오기(GET)] + [로봇]` 하면 로봇을 꺼내주는 똑똑하고 깔끔한 대화법이랍니다!
