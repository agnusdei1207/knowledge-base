# 📖 【암기용】 개념 완전 이해

> 목적: RESTful API 설계 원칙을 처음 보는 사람도 URL, HTTP 메서드, 상태 코드, 버전 관리가 왜 필요한지 이해하게 만든다. 시험 답안 양식이 아니라, 이해를 위한 설명이다.

## 한눈에
- **개요**: RESTful API는 리소스를 URI로 식별하고 HTTP 메서드와 상태 코드로 조작하는 API 설계 방식이다.
- **왜 필요한가**: API가 호출 함수처럼 제각각 설계되면 클라이언트가 예측하기 어렵고 버전 변경 때 장애가 발생한다.
- **핵심 직관**: 서버 기능명을 부르는 것이 아니라 웹상의 자원 주소에 표준 동작을 적용하는 방식이다.

## 깊이 이해
- **배경·문제의식**: 모바일, 웹, MSA가 같은 백엔드를 호출하면서 API 일관성, 캐시, 인증, 오류 처리, 문서화가 필요해졌다.
- **작동 원리**: `/orders/{id}` 같은 명사형 URI로 리소스를 나타내고 GET, POST, PUT, PATCH, DELETE를 의미에 맞게 사용한다. 상태 코드는 2xx, 4xx, 5xx로 결과를 표현한다.
- **비유**: 도서관에서 책 번호가 URI, 대출·반납·조회 규칙이 HTTP 메서드, 처리 결과 영수증이 상태 코드이다.
- **구체 예시**: 주문 조회는 `GET /orders/123`, 주문 생성은 `POST /orders`, 부분 수정은 `PATCH /orders/123`, 없는 주문은 `404 Not Found`로 표현한다.
- **흔한 오해·주의점**: RESTful은 URL만 예쁘게 만드는 일이 아니다. 무상태성, 캐시, 멱등성, 인증, 오류 형식, 버전 정책까지 포함한다.

## 연결 개념
- SOAP vs REST: RESTful 설계의 선택 배경
- OpenAPI: REST API 계약 문서화와 테스트 자동화
- API Gateway: 인증, 라우팅, 제한, 관측성 적용 지점

# 📝 【답안용】 시험 답안 템플릿

> 목적: RESTful API를 원칙, 구조, 오류 처리, 보안, 운영 지표까지 포함해 답안화한다.
> 핵심: 출제자는 URI 규칙 암기가 아니라 리소스 모델링과 HTTP 의미론을 지키는 설계 판단을 본다.

## 핵심 인사이트 (3줄 요약)

> 1. **본질**: RESTful API는 리소스를 URI로 식별하고 HTTP 메서드, 상태 코드, 헤더를 표준 의미에 맞게 사용하는 API 설계 원칙이다.
> 2. **가치**: 클라이언트 예측성, 캐시 활용, 게이트웨이 정책, 문서화, 테스트 자동화를 통해 API 변경 위험을 줄인다.
> 3. **판단 포인트**: 명사형 리소스, 무상태성, 멱등성, 상태 코드, 버전 관리, 인증·인가, 오류 형식을 함께 설계해야 한다.

## 출제 의도 및 답안 포인트

| 출제 의도 | 반드시 짚을 핵심 | 감점 회피 포인트 |
|:---|:---|:---|
| REST 설계 원칙 이해 확인 | 리소스 URI, HTTP 메서드, 상태 코드 | URL 규칙만 설명 |
| API 품질 판단 확인 | 멱등성, 캐시, 버전, 오류 형식 | GET으로 수정 처리 |
| 실무 적용 역량 확인 | OpenAPI, Gateway, OAuth2, Rate Limit | 보안과 운영 지표 누락 |

> 요약: RESTful API 답안은 리소스 모델링과 HTTP 의미론을 운영·보안 설계까지 연결해야 한다.

---

## Ⅰ. 개요 및 필요성

RESTful API는 HTTP 기반 리소스 설계 원칙이다. API 사용자가 늘수록 URI, 메서드, 상태 코드, 오류 응답이 일관되어야 장애와 변경 비용을 줄일 수 있다. MSA와 외부 API에서는 계약 문서화와 버전 관리가 필수이다.

---

## Ⅱ. 구조 및 구성요소

```text
Client -> API Gateway -> Resource URI -> HTTP Method
                    +-> Auth/Rate Limit -> Service -> Response/Status Code
```

| 구성요소 | 역할 | 특이사항 |
|:---|:---|:---|
| Resource URI | 자원 식별 | 명사형, 계층 구조, 복수형 |
| HTTP Method | 행위 표현 | GET, POST, PUT, PATCH, DELETE |
| Status Code | 처리 결과 표현 | 200, 201, 400, 401, 404, 409, 500 |
| Representation | JSON 응답 모델 | Content-Type, pagination |
| API Policy | 보안·운영 통제 | OAuth2, Rate Limit, CORS |

> 요약: RESTful API는 URI, 메서드, 상태 코드, 표현, 정책이 일관될 때 클라이언트 예측성이 생긴다.

---

## Ⅲ. 동작원리 및 흐름도

```text
리소스 모델링 -> URI 설계 -> 메서드/멱등성 매핑
-> 상태 코드/오류 형식 정의 -> OpenAPI 문서화 -> Gateway 정책 적용
```

| 단계 | 처리 내용 | 검증 기준 |
|:---:|:---|:---|
| 1 | 리소스와 관계 식별 | 주문, 고객, 결제 등 명사 |
| 2 | HTTP 메서드 매핑 | GET 조회, POST 생성, PUT 전체 수정 |
| 3 | 상태 코드와 오류 모델 정의 | 4xx/5xx 구분, error code |
| 4 | 보안·제한 정책 적용 | OAuth2, JWT, 1000 req/min |
| 5 | 문서화와 계약 테스트 | OpenAPI, contract test |

> 요약: RESTful 설계는 리소스 모델링에서 시작해 HTTP 의미론, 오류 모델, 문서화, 게이트웨이 정책으로 이어진다.

---

## Ⅳ. 특징

| 구분 | RPC식 API | RESTful API | 판단 포인트 |
|:---|:---|:---|:---|
| URI | `/getOrder` 동사형 | `/orders/{id}` 명사형 | 리소스 중심 |
| 행위 | 함수명에 포함 | HTTP 메서드 사용 | 멱등성 준수 |
| 결과 | 임의 코드 | HTTP 상태 코드 | 클라이언트 처리 |
| 운영 | 개별 구현 | Gateway 정책 적용 | 인증·제한·관측성 |
| 변경 | 암묵적 계약 | OpenAPI와 버전 | 호환성 관리 |

> 요약: RESTful API는 기능 호출을 리소스 조작으로 전환해 표준 HTTP 동작과 운영 정책을 활용한다.

---

## Ⅴ. 심화 비교 및 적용 판단

| 비교 축 | 기존/대안 | 본 키워드 | 선택 기준 |
|:---|:---|:---|:---|
| 구조 | RPC, SOAP | RESTful API | 웹·모바일·MSA 공개 API |
| 비용/성능 | 메서드 의미 불명확 | 캐시·Gateway·CDN 활용 | 조회 비율 70% 이상 |
| 운영/위험 | 문서와 구현 불일치 | OpenAPI 계약 테스트 | 다수 클라이언트 존재 |

> 요약: RESTful API는 웹 표준과 클라이언트 다양성이 필요한 서비스에서 우선 선택한다.

| 리스크 | 원인 | 대응 방안 | 확인 지표 |
|:---|:---|:---|:---|
| URI 난립 | 리소스 모델 부재 | API 스타일 가이드와 리뷰 | 신규 API 규칙 위반 건수 |
| 멱등성 위반 | POST/PUT/PATCH 혼용 | 메서드별 의미 정의 | 중복 요청 장애 건수 |
| 버전 충돌 | 호환성 정책 부재 | `/v1`, Header 버전, Deprecation | 계약 테스트 통과율 |

> 요약: RESTful API 리스크는 설계 일관성, 멱등성, 버전 관리에서 발생하므로 스타일 가이드와 계약 테스트가 필요하다.

| 점검 항목 | 목표 기준 | 측정 방법 |
|:---|:---|:---|
| API 품질 | OpenAPI 커버리지 100% | 문서 빌드, lint |
| 성능 | p95 지연 300ms, 5xx 0.1% 이하 | APM, Gateway 로그 |
| 보안/운영 | OAuth2 적용 100%, Rate Limit 위반 추적 | Gateway, IAM 로그 |

> 요약: RESTful API는 문서화, 지연시간, 오류율, 인증·제한 정책 준수로 운영 품질을 점검한다.

---

## Ⅵ. 실무 적용 및 결론

**적용 방안 3개:**
1. URI는 명사형 복수 리소스로 표준화하고 GET/POST/PUT/PATCH/DELETE의 멱등성 규칙을 API 스타일 가이드에 명시함
2. 오류 응답은 `code`, `message`, `traceId`, `details` 형식으로 통일하고 HTTP 400, 401, 403, 404, 409, 429, 500을 구분함
3. OpenAPI 기반 계약 테스트, OAuth2/JWT 인증, Rate Limit 1000 req/min, API Gateway 로그를 CI/CD와 운영 대시보드에 연결함

**결론 (2줄):**
- 기술사 판단: RESTful API는 웹·모바일·MSA의 기본 선택지이며, 실시간 양방향은 WebSocket, 고성능 내부 호출은 gRPC를 별도 검토함
- 향후 방향: API Gateway, OpenAPI, Backward Compatibility, Zero Trust 인증을 결합해 API 제품 관리 체계로 확장함
