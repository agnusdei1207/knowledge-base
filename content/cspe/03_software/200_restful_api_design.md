# 📖 【암기용】 개념 완전 이해

## 한눈에
- **개요**: HTTP 기반 웹 서비스를 만들 때, 누구나 직관적으로 자원의 위치와 행위를 이해할 수 있도록 규정한 일관된 설계 제약과 가이드라인
- **왜 필요한가**: API 설계자마다 자기 마음대로 주소(`/create_user_now`, `/deleteUser`)를 만들면, 수백 개의 API를 관리하고 연동하는 개발자들이 대혼란에 빠지기 때문
- **핵심 직관**: "명사(자원)는 주소(URI)에, 동사(행위)는 HTTP 메서드에!" 이것이 가장 중요한 규칙이다.

## 핵심 용어 정리

| 용어/표기 | 의미 | 비유·예 |
|:---|:---|:---|
| Resource (자원) | API가 다루는 데이터나 객체 | `/users` (회원들) |
| HTTP Method (메서드) | 자원에 대해 수행할 구체적인 행위 | `GET` (조회), `POST` (생성) |
| HATEOAS (하이퍼미디어) | 다음 상태로 전이할 수 있는 링크를 응답에 포함 | "회원 정보와 함께 '수정 버튼' 링크를 같이 줌" |

## 깊이 이해
- **배경·문제의식**: SOAP의 복잡성에 질린 개발자들은 가벼운 REST를 환영했다. 하지만 너무 자유로운 나머지 주소 표기법이 중구난방이 되었다. 진정한 REST(RESTful)의 이점을 얻으려면 모두가 합의할 수 있는 표준적인 제약(Constraint)이 필요했다.
- **작동 원리**: RESTful API는 자원의 식별, 메시지를 통한 조작, 자기 서술적 메시지(Self-descriptive), 애플리케이션 상태의 엔진으로서 하이퍼미디어(HATEOAS)라는 엄격한 제약을 갖는다. 이를 실무에 적용하면 주소에는 행위를 나타내는 동사를 쓰지 않고 복수형 명사를 쓰며, 행위는 오직 GET, POST, PUT/PATCH, DELETE로만 표현한다.
- **비유**: 웹사이트의 일관된 내비게이션 바와 같다. 어디를 가든 '홈', '장바구니', '마이페이지' 구조가 같아야 헤매지 않듯, API 주소도 룰이 같아야 기계와 사람이 헷갈리지 않는다.
- **구체 예시**: 
  - ❌ 나쁜 예: `GET /updateUser?id=1` (동사 사용, GET으로 수정 행위)
  - ⭕ 좋은 예: `PUT /users/1` (명사 복수형, PUT으로 수정, 경로로 식별)
- **흔한 오해·주의점**: JSON을 HTTP로 주고받는다고 다 RESTful한 것은 아니다. Richardson 성숙도 모델에 따르면, 리소스별로 URI를 나누고 HTTP 메서드를 제대로 써야 레벨 2이며, HATEOAS 링크까지 응답에 포함해야 진정한 레벨 3 (RESTful)로 인정받는다.

## 연결 개념
- HTTP 상태 코드 (Status Code) — 응답의 결과를 명확히 알리는 규칙
- GraphQL — REST의 오버페칭(Over-fetching) 단점을 보완한 대안 쿼리 언어
- 멱등성 (Idempotency) — 여러 번 호출해도 결과가 같은 속성 (GET, PUT, DELETE)

# 📝 【답안용】 시험 답안 템플릿

## 핵심 인사이트 (3줄 요약)

> 1. **본질**: RESTful API는 분산 시스템 통합을 위해 자원 식별, 무상태성, 균일한 인터페이스 등 REST 아키텍처 제약 조건을 철저히 준수하는 설계 기법임
> 2. **가치**: 클라이언트와 서버 간의 독립성을 보장하고, 직관적인 URI와 HTTP 표준 활용으로 API 가독성 및 유지보수성을 극대화함
> 3. **판단 포인트**: 동사 사용을 배제한 명사 복수형 URI 설계와 상황에 맞는 정확한 HTTP 상태 코드(2xx, 4xx, 5xx) 반환이 실무 적용의 핵심임

## 출제 의도 및 답안 포인트

| 출제 의도 | 반드시 짚을 핵심 | 감점 회피 포인트 |
|:---|:---|:---|
| 확장성 있고 일관된 API 구조 설계 역량 확인 | URI 구조 원칙, HTTP 메서드 매핑, HATEOAS | JSON 전송 기술로만 얕게 서술하고 설계 원칙(제약조건) 누락 |

> 요약: RESTful API는 HTTP 프로토콜의 본래 목적과 제약 조건을 준수하여 서비스 인터페이스의 직관성을 보장하는 설계 표준임

---

## Ⅰ. 개요 및 필요성

- 개요: HTTP URI를 통해 자원(Resource)을 명시하고, HTTP Method를 통해 해당 자원에 대한 CRUD 연산을 정의하는 아키텍처 설계 원칙임
- 배경: 모바일 기기와 이기종 클라이언트 확산으로 느슨하게 결합된 백엔드 인터페이스 요구 증가
- 필요성: 개발자 간 의사소통 혼선을 줄이고 OpenAPI 제공 시 서드파티의 빠르고 직관적인 연동을 보장할 일관된 규칙 절실

---

## Ⅱ. 구조 및 구성요소

```text
클라이언트 요청 -> [ HTTP Method + URI + Header ] -> API 서버 라우팅
                   |                          |
                   +-> [ 상태 코드 + JSON + HATEOAS ] <- DB 처리 응답
```

| 구성요소 | 설계 원칙 | 올바른 예시 |
|:---|:---|:---|
| 자원 (Resource) | 동사 배제, 명사 복수형 사용 | `/users`, `/orders/123/items` |
| 행위 (Method) | 비즈니스 로직을 HTTP 메서드에 매핑 | `GET`(조회), `POST`(생성), `PUT`(수정) |
| 응답 결과 (Status) | 정확한 HTTP 상태 코드로 결과 표현 | `201 Created`, `404 Not Found` |
| 하이퍼미디어 | 연관된 다음 작업의 링크 제공 (HATEOAS) | `"links": [{"rel": "next", "href": "..."}]` |

> 요약: RESTful 설계는 주소를 명사로, 행위를 메서드로, 결과를 상태 코드로 철저히 분리하여 구성함

---

## Ⅲ. 동작원리 및 흐름도 (Richardson 성숙도 모델 적용)

```text
단일 엔드포인트(Lv0) -> 자원 분리(Lv1) -> HTTP 메서드 적용(Lv2) -> HATEOAS 적용(Lv3)
```

- 1단계 [Level 0 (The Swamp)]: 모든 요청을 단일 URI(예: `/api`)로 POST 전송 (REST 아님)
- 2단계 [Level 1 (Resources)]: 개별 자원마다 고유한 URI를 부여하여 식별성 확보 (`/users/1`)
- 3단계 [Level 2 (HTTP Verbs)]: 자원 조작 행위를 올바른 HTTP 메서드(GET, POST, PUT, DELETE)로 매핑
- 4단계 [Level 3 (Hypermedia)]: 응답 JSON 안에 클라이언트가 전이 가능한 다음 행동 링크(HATEOAS)를 포함하여 자체 서술성 완성

> 요약: RESTful 설계는 단순히 자원을 나누는 것을 넘어, HTTP 특성 활용과 상태 전이 링크를 제공하는 완숙 단계로 진화함

---

## Ⅳ. 특징
- 무상태성 (Stateless): 서버는 클라이언트의 상태(세션)를 저장하지 않으며, 각 요청은 독립적으로 처리 가능한 모든 정보를 포함해야 함
- 멱등성 (Idempotency) 준수: GET, PUT, DELETE 메서드는 여러 번 연속해서 호출해도 서버의 상태가 동일하게 유지됨을 보장하여 재시도 로직을 단순화함
- 캐싱 가능 (Cacheable): 명시적인 URI와 GET 메서드 활용으로 HTTP 인프라 내장 캐시(ETag, Cache-Control)를 별도 개발 없이 즉시 활용 가능

---

## Ⅴ. 심화 비교 및 적용 판단

| HTTP 메서드 | 역할 (행위) | 멱등성 (Idempotency) | 트래픽 제어 기준 |
|:---|:---|:---|:---|
| GET | 자원의 단순 조회 | O (부작용 없음) | 캐싱 적극 활용, Read 노드 부하 분산 |
| POST | 새로운 자원 생성 | X (요청마다 신규 생성) | 이중 서밋(중복 결제) 방지 토큰 필요 |
| PUT / PATCH | 자원 전체 교체 / 부분 수정 | O / (PATCH는 설계에 따라 다름) | 낙관적 락(Version) 기반 동시성 제어 |
| DELETE | 자원 삭제 | O | 실제 삭제(Hard) vs 상태 변경(Soft) 결정 |

> 요약: 각 HTTP 메서드의 멱등성 여부에 따라 클라이언트의 재시도(Retry) 전략과 서버의 데이터 정합성 통제 방식이 달라짐

**리스크·대응 (기본은 불릿):**
- 오버페칭(Over-fetching) 발생: 화면엔 이름만 필요한데 API가 불필요한 전체 회원 정보를 모두 반환하여 대역폭 낭비 → URI 쿼리스트링 활용(필터링 `?fields=name`) 또는 GraphQL 도입 고려 (지표: API 평균 응답 페이로드 크기)
- 하위 호환성 붕괴: API 스펙 변경 시 기존 구버전 클라이언트 앱에서 크래시 발생 → URI 버저닝(`/v1/users`) 또는 Header 버저닝 채택 의무화 (지표: API 버전 충돌 오류 건수)

**도입 후 점검 지표 (기본은 불릿):**
- 상태 코드 표준화율: 성공 시 무조건 200만 반환하는지 검사하여 201(생성), 204(내용 없음) 등 의미별 분리 반환 여부 점검 — API 로그 통계
- API 문서화 커버리지: Swagger(OpenAPI Spec)에 자동화된 최신 스펙 반영률 100% 확보 — CI 파이프라인 검증

## Ⅵ. 실무 적용 및 결론

**적용 방안 3개:**
1. 명명 규칙 표준 수립: URI는 소문자와 하이픈(-)만 사용하고, 컬렉션(목록)은 명사 복수형(`/users`), 문서는 단수형(`/users/123/profile`)으로 조직 내 설계 가이드 제정
2. 복잡한 행위의 예외 처리: 명사로 표현하기 힘든 비즈니스 행위(예: 회원 활성화)는 자원의 서브 리소스로 표현하거나 동사를 제한적으로 허용 (`POST /users/123/activate`)
3. 페이지네이션(Pagination) 표준화: 대량 데이터 조회 시 쿼리 파라미터(`?limit=20&offset=40`)와 응답 메타데이터에 HATEOAS 링크(next_page_url)를 조합해 제공

**결론 (2줄):**
- 기술사 판단: RESTful API 설계는 단순한 코딩 스타일이 아니라, 시스템의 확장성과 클라이언트 결합도를 낮추는 분산 아키텍처의 핵심 인프라임
- 향후 방향: REST의 단점인 언더페칭/오버페칭을 극복하기 위해 데이터를 클라이언트가 원하는 모양으로 쿼리할 수 있는 GraphQL과의 하이브리드 구성이 확대될 것임
