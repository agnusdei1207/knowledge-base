# 📖 【암기용】 개념 완전 이해

> 목적: BFF를 처음 봐도 왜 클라이언트별 백엔드가 필요한지 이해하게 만든다. 시험 답안 양식이 아니라, 이해를 위한 설명이다.

## 한눈에
- **개요**: 웹·모바일·파트너 채널별 화면 요구에 맞춘 전용 백엔드 계층
- **왜 필요한가**: 하나의 공통 API가 모든 화면을 만족시키려 하면 과다 응답, 다중 호출, 채널별 분기 로직이 클라이언트에 누적됨
- **핵심 직관**: 주방은 같아도 매장, 배달, 드라이브스루 주문 창구가 각각 필요한 것과 같음

## 깊이 이해
- **배경·문제의식**: MSA는 도메인 API를 잘게 나누지만 화면은 여러 도메인 데이터를 한 번에 필요로 함. 모바일은 작은 응답과 배터리 사용량을, 웹은 풍부한 화면 데이터를 요구함.
- **작동 원리**: BFF는 클라이언트 요청을 받아 인증·인가를 확인하고 여러 내부 API를 호출·조합·변환하여 화면 DTO로 반환함. GraphQL, REST Aggregation, gRPC Gateway 형태로 구현 가능함.
- **비유**: 고객은 세트 메뉴를 주문하고 주방 내부 조리 순서는 몰라도 됨. BFF는 화면이 필요한 세트 메뉴를 만들어 주는 주문 창구임.
- **구체 예시**: 모바일 주문 화면은 상품, 재고, 쿠폰, 배송비 API 4개를 BFF가 병렬 호출해 1개 JSON으로 합쳐 p95 300ms 이내 응답을 목표로 함.
- **흔한 오해·주의점**: BFF는 비즈니스 핵심 규칙을 복제하는 계층이 아님. 도메인 규칙은 내부 서비스에 두고 화면 조합과 채널 정책만 담당해야 함.

## 연결 개념
- API Gateway: 공통 진입점과 라우팅
- GraphQL: 클라이언트 주도 조회와 타입 스키마
- MSA: 도메인 API 분해와 조합 필요성

# 📝 【답안용】 시험 답안 템플릿

> 목적: 시험장에서 25분에 그대로 쓰는 답안 양식. BFF는 API Gateway와 구분하여 채널별 화면 조합, 보안 위임, 성능 지표를 중심으로 답한다.

## 핵심 인사이트 (3줄 요약)

> 1. **본질**: BFF는 프론트엔드 유형별 요구에 맞춰 내부 API를 조합·변환하는 클라이언트 전용 백엔드 패턴이다.
> 2. **가치**: 화면별 다중 호출을 줄이고, 모바일·웹·파트너 채널의 응답 크기, 인증 방식, DTO를 분리한다.
> 3. **판단 포인트**: API Gateway는 공통 정책, BFF는 화면 조합과 채널 최적화 계층으로 역할을 분리한다.

## 출제 의도 및 답안 포인트

| 출제 의도 | 반드시 짚을 핵심 | 감점 회피 포인트 |
|:---|:---|:---|
| BFF와 Gateway 차이 확인 | Gateway 공통 정책, BFF 채널별 조합 | 둘을 동일 계층으로 서술 |
| MSA API 조합 판단 확인 | Aggregation, DTO 변환, 병렬 호출, 캐시 | 도메인 로직 복제 허용 |
| 운영 품질 확인 | p95 지연, payload 크기, 오류 격리 | BFF 수 증가에 따른 중복 관리 누락 |

> 요약: BFF 답안은 채널별 화면 요구와 내부 도메인 API의 경계를 분명히 하는 것이 핵심이다.

---

## Ⅰ. 개요 및 필요성

- 개요: 클라이언트별 전용 백엔드 패턴
- 배경: MSA 화면은 여러 도메인 API를 조합하며, 클라이언트 직접 조합은 호출 수와 보안 로직을 증가시킴
- 필요성: 채널별 DTO, 캐시, 인증 정책을 BFF에서 통제해 모바일·웹별 응답 형식과 권한 검증을 분리해야 함

---

## Ⅱ. 구조 및 구성요소

```text
Web/Mobile Client -> API Gateway -> Web BFF/Mobile BFF -> Domain Services -> DB
  / Auth Context
  / DTO Mapping
  / Cache
```

| 구성요소 | 역할 | 특이사항 |
|:---|:---|:---|
| Client BFF | 채널별 API 조합과 응답 변환 | Web, iOS, Android 분리 가능 |
| API Gateway | 인증 전처리, 라우팅, Rate Limit | 공통 정책 담당 |
| Domain Service | 핵심 비즈니스 규칙 제공 | BFF에 규칙 복제 금지 |
| Cache/Resilience | 응답 캐시, Timeout, Retry | p95 지연과 오류율 관리 |

> 요약: Gateway는 공통 관문, BFF는 채널별 조합, Domain Service는 규칙 원천으로 역할을 나눈다.

---

## Ⅲ. 동작원리 및 흐름도

```text
화면 요청 -> 인증 컨텍스트 확인 -> 내부 API 병렬 호출 -> DTO 조합 -> 캐시 저장 -> 응답 반환
```

| 단계 | 처리 내용 | 검증 기준 |
|:---:|:---|:---|
| 1 | 클라이언트 요청 수신 | JWT subject, device type |
| 2 | 내부 서비스 호출 계획 생성 | fan-out 3~5개 이하 |
| 3 | 병렬 호출·Timeout 적용 | timeout 200ms, retry 1회 |
| 4 | DTO 조합·필드 필터링 | payload 30% 축소 목표 |
| 5 | 로그·메트릭 저장 | p95 latency, error rate |

> 요약: BFF는 인증 컨텍스트를 유지한 채 내부 API를 병렬 호출하고 화면 DTO로 압축 반환한다.

---

## Ⅳ. 특징

| 구분 | 공통 API 직접 호출 | BFF | 수치·판단 포인트 |
|:---|:---|:---|:---|
| 호출 수 | 화면당 4~8회 호출 | 서버 측 1회 응답 | 모바일 RTT 절감 |
| 응답 구조 | 범용 DTO | 화면 전용 DTO | payload 30~50% 축소 |
| 보안 | 클라이언트별 분기 | 서버 측 권한 필터링 | 403 정책 일관성 |
| 운영 | 단일 API 변경 영향 | 채널별 배포 | BFF 중복 코드 20% 이하 |

> 요약: BFF는 화면 응답을 줄이고 보안 정책을 서버에 모으지만, BFF 간 중복과 버전 관리를 관리해야 한다.

---

## Ⅴ. 심화 비교 및 적용 판단

| 비교 축 | 기존/대안 | 본 키워드 | 선택 기준 |
|:---|:---|:---|:---|
| Gateway | 공통 인증·라우팅 | 채널별 API 조합 | 화면 데이터 조합 필요 시 BFF |
| GraphQL | 클라이언트 쿼리 주도 | 서버 주도 DTO | 쿼리 유연성 vs 서버 통제 |
| Monolith API | 단일 백엔드 | BFF+MSA | 도메인 API가 5개 이상 분리 |

> 요약: BFF는 Gateway 대체물이 아니라 채널별 화면 조합을 담당하는 MSA 보완 계층이다.

| 리스크 | 원인 | 대응 방안 | 확인 지표 |
|:---|:---|:---|:---|
| 로직 중복 | BFF에 업무 규칙 작성 | 규칙은 Domain Service로 이동 | 중복 함수 수, 코드 리뷰 |
| 장애 전파 | 내부 API fan-out | Timeout, Bulkhead, fallback | downstream error rate |
| 버전 불일치 | 앱 버전별 DTO 차이 | API versioning, contract test | contract test 통과율 100% |

> 요약: BFF의 위험은 업무 규칙 복제와 fan-out 장애이며 계약 테스트와 격리 패턴으로 통제한다.

| 점검 항목 | 목표 기준 | 측정 방법 |
|:---|:---|:---|
| 지연시간 | p95 300ms 이하 | APM trace |
| 응답 크기 | 모바일 payload 100KB 이하 | Gateway 로그 |
| 품질 | consumer contract 100% 통과 | Pact, CI |

> 요약: BFF 효과는 p95 지연, 응답 크기, 계약 테스트 지표로 판단한다.

## Ⅵ. 실무 적용 및 결론

**적용 방안 3개 (필수):**
1. 모바일 주문 화면은 Mobile BFF에서 상품·재고·쿠폰·배송비 API를 병렬 호출하고 timeout 200ms, retry 1회로 제한함.
2. Gateway는 OAuth 토큰 검증과 Rate Limit을 담당하고, BFF는 scope 기반 필드 필터링과 화면 DTO 변환만 수행함.
3. BFF별 OpenAPI/GraphQL schema와 consumer contract test를 CI에 연결해 앱 릴리스 전 호환성을 검증함.

**결론 (2줄):**
- 기술사 판단: 클라이언트별 화면 요구가 다르고 내부 API fan-out이 3개 이상이면 BFF를 적용, 단순 CRUD는 공통 API를 유지함.
- 향후 방향: BFF는 GraphQL Federation, Edge BFF, 서버 컴포넌트와 결합해 화면 근접 데이터 조합 계층으로 발전함.
