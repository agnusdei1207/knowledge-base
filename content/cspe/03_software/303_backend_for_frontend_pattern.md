# 📖 【암기용】 개념 완전 이해

> 목적: BFF를 처음 봐도 왜 클라이언트별 백엔드가 필요한지 이해하게 만든다. 시험 답안 양식이 아니라, 이해를 위한 설명이다.

## 한눈에
- **개요**: BFF(Backend for Frontend)는 **MSA(마이크로서비스 아키텍처)**의 **API 조합(Aggregation) 계층**에 속하는 패턴으로, 클라이언트 유형(웹·모바일·파트너)별로 전용 백엔드를 두어 여러 도메인 서비스의 API를 화면에 맞게 조합·변환한다.
- **왜 필요한가**: 하나의 공통 API가 모든 화면을 만족시키려 하면 화면마다 여러 번 호출해야 하고(N+1 호출 문제), 클라이언트별 분기 로직이 코드에 누적된다.
- **핵심 직관**: 주방(도메인 서비스)은 하나여도, 매장·배달·드라이브스루 주문 창구(BFF)는 각각 다르게 손님을 응대하는 것과 같다.

## 핵심 용어 정리 (내부에 등장하는 것들)

| 용어 | 의미 | 비유 |
|:---|:---|:---|
| MSA (마이크로서비스 아키텍처) | 하나의 앱을 도메인 단위 작은 서비스로 쪼갠 구조 — BFF가 조합해야 할 대상 | 큰 공장을 여러 전문 공방으로 나눈 것 |
| API 조합(Aggregation) | 여러 서비스의 응답을 하나로 합쳐 반환하는 동작 — BFF의 핵심 기능 | 여러 부서 서류를 한 장 보고서로 합치기 |
| API Gateway | 모든 클라이언트가 거치는 공통 진입점 — 인증·라우팅·Rate Limit 담당 | 건물 정문 경비 |
| BFF (Backend for Frontend) | 클라이언트 유형별 전용 백엔드 — 화면 요구에 맞춘 API 조합·변환 | 매장·배달·드라이브스루 각각의 주문 창구 |
| DTO (Data Transfer Object) | 화면에 필요한 필드만 담아 전달하는 응답 객체 | 세트 메뉴 포장 |
| fan-out | 요청 하나가 여러 내부 서비스 호출로 퍼지는 것 | 주문 하나가 여러 조리대로 나뉨 |
| p95 지연시간 | 요청의 95%가 이 시간 이내에 처리됨을 뜻하는 지표 | 100명 중 95번째로 느린 손님까지 이 시간 안에 서빙 |
| Contract Test (계약 테스트) | BFF와 도메인 서비스 간 API 스펙이 깨지지 않았는지 자동 검증 | 계약서대로 납품됐는지 검수 |

- BFF는 API Gateway를 대체하는 게 아니라, Gateway 뒤에서 "화면별로 다른 조합"을 담당하는 계층이다.

## 깊이 이해

### 왜 필요했나 (배경 — N+1 호출 문제)
- MSA는 도메인별로 API를 쪼갠다. 화면 하나가 상품·재고·쿠폰·배송비 등 4개 도메인 데이터를 필요로 하면, 클라이언트가 직접 4번 호출해야 한다. 모바일 호출 1회 RTT(왕복시간)가 150ms라면, 순차 호출 시 4×150ms=600ms가 걸린다.
- 웹은 풍부한 화면 정보를, 모바일은 배터리·데이터 절약을 위한 축소 정보를 원한다. 공통 API 하나로 이 상반된 요구를 다 만족시키려 하면 응답에 옵셔널 필드가 계속 늘고, 클라이언트마다 분기 로직(`if platform == mobile`)이 코드에 누적된다.

### 작동 원리 (요청 조합의 3단계)
- BFF는 ① 클라이언트 요청을 받아 인증 컨텍스트를 확인하고 ② 필요한 내부 API를 병렬로 fan-out 호출한 뒤 ③ 응답을 합쳐 화면 전용 DTO로 변환해 반환한다.
- 수치 예: 모바일 주문 화면에 필요한 4개 API를 순차 호출하면 4×150ms=600ms이지만, BFF가 병렬로 fan-out 호출하면 가장 느린 API 기준 약 150~200ms로 줄어든다. 그 결과 p95 300ms 이내 응답 목표를 달성할 수 있다.

### API Gateway와의 판별 원리
- Gateway는 모든 클라이언트가 공유하는 "공통 관문"이다 — 인증, 라우팅, Rate Limit처럼 화면 종류와 무관한 정책을 처리한다.
- BFF는 클라이언트 "유형별로 다르게" 존재한다 — 웹 BFF와 모바일 BFF는 서로 다른 DTO와 조합 로직을 가진다. "이 로직이 화면마다 달라지는가?"가 Gateway와 BFF를 가르는 판별 기준이다.
- 실무 계층 순서: Client → API Gateway(공통 인증·라우팅) → BFF(화면별 조합) → Domain Service.

### 비유와 흔한 오해
- 비유: 주방(Domain Service)은 하나지만, 매장 주문대·배달 앱·드라이브스루 창구(BFF)는 각각 다르게 주문을 받아 같은 주방에 전달한다. 창구가 다르다고 조리법(비즈니스 규칙)이 달라지지는 않는다.
- 오해 1: BFF는 별도의 마이크로서비스가 아니라 "조합·변환 계층"이다. 할인 계산, 재고 차감 같은 비즈니스 핵심 규칙을 BFF에 복제하면 도메인 서비스에 있어야 할 로직이 흩어져 정합성이 깨진다.
- 오해 2: BFF가 채널마다(웹·iOS·Android) 늘어나면 공통 코드가 중복되기 쉽다. BFF 간 중복 코드 비율(예: 20% 이하)을 관리 지표로 둬야 한다.

## 연결 개념
- API Gateway (상위 관문 — BFF는 그 뒤에서 화면별 조합을 담당)
- GraphQL (클라이언트 주도 조회로 BFF를 대체·보완하는 방식)
- MSA (BFF가 조합해야 하는 대상 — 도메인 API 분해)

# 📝 【답안용】 시험 답안 템플릿

> 목적: 시험장에서 25분에 그대로 쓰는 답안 양식. BFF는 API Gateway와 구분하여 채널별 화면 조합, 보안 위임, 성능 지표를 중심으로 답한다.

## 핵심 인사이트 (3줄 요약)

> 1. **본질**: BFF는 프론트엔드 유형별 요구에 맞춰 내부 API를 조합·변환하는 클라이언트 전용 백엔드 패턴이다.
> 2. **가치**: 화면별 다중 호출을 줄이고, 모바일·웹·파트너 채널의 응답 크기, 인증 방식, DTO를 분리한다.
> 3. **판단 포인트**: API Gateway는 공통 정책, BFF는 화면 조합과 채널 최적화 계층으로 역할을 분리한다.

## 출제 의도 및 답안 포인트

| 출제 의도 | 반드시 짚을 핵심 | 감점 회피 포인트 |
|:---|:---|:---|
| BFF와 Gateway 차이 확인 | Gateway 공통 정책, BFF 채널별 조합 | 둘을 동일 계층으로 서술 |
| MSA API 조합 판단 확인 | Aggregation, DTO 변환, 병렬 호출, 캐시 | 도메인 로직 복제 허용 |
| 운영 품질 확인 | p95 지연, payload 크기, 오류 격리 | BFF 수 증가에 따른 중복 관리 누락 |

> 요약: BFF 답안은 채널별 화면 요구와 내부 도메인 API의 경계를 분명히 하는 것이 핵심이다.

## Ⅰ. 개요 및 필요성

- 개요: 클라이언트별 전용 백엔드 패턴
- 배경: MSA 화면은 여러 도메인 API를 조합하며, 클라이언트 직접 조합은 호출 수와 보안 로직을 증가시킴
- 필요성: 채널별 DTO, 캐시, 인증 정책을 BFF에서 통제해 모바일·웹별 응답 형식과 권한 검증을 분리해야 함

---

## Ⅱ. 구조 및 구성요소

```text
Web/Mobile Client -> API Gateway -> Web BFF/Mobile BFF -> Domain Services -> DB
  / Auth Context
  / DTO Mapping
  / Cache
```

| 구성요소 | 역할 | 특이사항 |
|:---|:---|:---|
| Client BFF | 채널별 API 조합과 응답 변환 | Web, iOS, Android 분리 가능 |
| API Gateway | 인증 전처리, 라우팅, Rate Limit | 공통 정책 담당 |
| Domain Service | 핵심 비즈니스 규칙 제공 | BFF에 규칙 복제 금지 |
| Cache/Resilience | 응답 캐시, Timeout, Retry | p95 지연과 오류율 관리 |

> 요약: Gateway는 공통 관문, BFF는 채널별 조합, Domain Service는 규칙 원천으로 역할을 나눈다.

---

## Ⅲ. 동작원리 및 흐름도

```text
화면 요청 -> 인증 컨텍스트 확인 -> 내부 API 병렬 호출 -> DTO 조합 -> 캐시 저장 -> 응답 반환
```

| 단계 | 처리 내용 | 검증 기준 |
|:---:|:---|:---|
| 1 | 클라이언트 요청 수신 | JWT subject, device type |
| 2 | 내부 서비스 호출 계획 생성 | fan-out 3~5개 이하 |
| 3 | 병렬 호출·Timeout 적용 | timeout 200ms, retry 1회 |
| 4 | DTO 조합·필드 필터링 | payload 30% 축소 목표 |
| 5 | 로그·메트릭 저장 | p95 latency, error rate |

> 요약: BFF는 인증 컨텍스트를 유지한 채 내부 API를 병렬 호출하고 화면 DTO로 압축 반환한다.

## Ⅳ. 특징

| 구분 | 공통 API 직접 호출 | BFF | 수치·판단 포인트 |
|:---|:---|:---|:---|
| 호출 수 | 화면당 4~8회 호출 | 서버 측 1회 응답 | 모바일 RTT 절감 |
| 응답 구조 | 범용 DTO | 화면 전용 DTO | payload 30~50% 축소 |
| 보안 | 클라이언트별 분기 | 서버 측 권한 필터링 | 403 정책 일관성 |
| 운영 | 단일 API 변경 영향 | 채널별 배포 | BFF 중복 코드 20% 이하 |

> 요약: BFF는 화면 응답을 줄이고 보안 정책을 서버에 모으지만, BFF 간 중복과 버전 관리를 관리해야 한다.

## Ⅴ. 심화 비교 및 적용 판단

| 비교 축 | 기존/대안 | 본 키워드 | 선택 기준 |
|:---|:---|:---|:---|
| Gateway | 공통 인증·라우팅 | 채널별 API 조합 | 화면 데이터 조합 필요 시 BFF |
| GraphQL | 클라이언트 쿼리 주도 | 서버 주도 DTO | 쿼리 유연성 vs 서버 통제 |
| Monolith API | 단일 백엔드 | BFF+MSA | 도메인 API가 5개 이상 분리 |

> 요약: BFF는 Gateway 대체물이 아니라 채널별 화면 조합을 담당하는 MSA 보완 계층이다.

| 리스크 | 원인 | 대응 방안 | 확인 지표 |
|:---|:---|:---|:---|
| 로직 중복 | BFF에 업무 규칙 작성 | 규칙은 Domain Service로 이동 | 중복 함수 수, 코드 리뷰 |
| 장애 전파 | 내부 API fan-out | Timeout, Bulkhead, fallback | downstream error rate |
| 버전 불일치 | 앱 버전별 DTO 차이 | API versioning, contract test | contract test 통과율 100% |

> 요약: BFF의 위험은 업무 규칙 복제와 fan-out 장애이며 계약 테스트와 격리 패턴으로 통제한다.

| 점검 항목 | 목표 기준 | 측정 방법 |
|:---|:---|:---|
| 지연시간 | p95 300ms 이하 | APM trace |
| 응답 크기 | 모바일 payload 100KB 이하 | Gateway 로그 |
| 품질 | consumer contract 100% 통과 | Pact, CI |

> 요약: BFF 효과는 p95 지연, 응답 크기, 계약 테스트 지표로 판단한다.

## Ⅵ. 실무 적용 및 결론

**적용 방안 3개 (필수):**
1. 모바일 주문 화면은 Mobile BFF에서 상품·재고·쿠폰·배송비 API를 병렬 호출하고 timeout 200ms, retry 1회로 제한함.
2. Gateway는 OAuth 토큰 검증과 Rate Limit을 담당하고, BFF는 scope 기반 필드 필터링과 화면 DTO 변환만 수행함.
3. BFF별 OpenAPI/GraphQL schema와 consumer contract test를 CI에 연결해 앱 릴리스 전 호환성을 검증함.

**결론 (2줄):**
- 기술사 판단: 클라이언트별 화면 요구가 다르고 내부 API fan-out이 3개 이상이면 BFF를 적용, 단순 CRUD는 공통 API를 유지함.
- 향후 방향: BFF는 GraphQL Federation, Edge BFF, 서버 컴포넌트와 결합해 화면 근접 데이터 조합 계층으로 발전함.
