## Ⅰ. 개요
- **정의**: 클라이언트 유형별 전용 백엔드 계층을 두어 각 프론트엔드에 최적화된 API를 제공하는 패턴임
- **배경/필요성**: 모바일·웹·IoT 등 클라이언트 특성이 달라 단일 API로는 응답 최적화가 어려움
- **비유**: 같은 식재료로 한식·양식·일식 셰프가 각 고객 취향에 맞춰 별도 요리를 만드는 것과 같음

| 출제 의도 | 반드시 짚을 핵심 | 감점 회피 포인트 |
|:---|:---|:---|
| 클라이언트별 API 최적화 전략 | API Gateway와 BFF의 역할 차이 | BFF는 비즈니스 로직이 아닌 표현 로직을 담당함 |

> 요약: 클라이언트 유형별 전용 백엔드를 두어 응답 형식·필드·호출 횟수를 최적화하는 패턴임

## Ⅱ. 구성요소
```text
[Mobile App]    [Web App]    [IoT Device]
     |              |              |
[Mobile BFF]   [Web BFF]    [IoT BFF]
     |              |              |
     +------+-------+------+------+
            |               |
     [Service A]      [Service B]
```

| 구성요소 | 설명 | 비유 |
|:---|:---|:---|
| BFF 서버 | 특정 클라이언트에 맞춰 데이터를 집계·변환하는 중간 계층임 | 전담 셰프 |
| 백엔드 서비스 | 도메인 로직을 처리하는 공통 마이크로서비스임 | 공용 식재료 창고 |
| 클라이언트 | 각기 다른 화면 크기·네트워크·기능 요구를 가진 소비자임 | 취향이 다른 고객 |

> 요약: 클라이언트 → BFF → 백엔드 서비스의 3계층으로 표현 로직과 도메인 로직을 분리함

## Ⅲ. 절차
```text
클라이언트 분류 --> BFF 설계 --> 서비스 연동 --> 독립 배포
```
- 1단계: 클라이언트를 유형(모바일·웹·IoT)별로 분류하고 요구 차이를 식별함
- 2단계: 각 유형에 맞는 BFF를 설계하여 필요한 필드·집계 로직을 정의함
- 3단계: BFF가 다수 백엔드 서비스를 호출하고 결과를 클라이언트 형식으로 조합함
- 4단계: 각 BFF를 독립 배포 파이프라인으로 운영하여 클라이언트별 릴리스 주기를 분리함

> 요약: 클라이언트 분류 → BFF 설계 → 서비스 연동 → 독립 배포의 4단계로 구축함

## Ⅳ. 문제점
- 코드 중복: BFF 간 유사 로직이 반복 구현되어 유지보수 부담이 증가함
- 운영 복잡도: BFF 수가 클라이언트 유형만큼 증가하여 인프라 관리 비용이 높아짐
- 지연 누적: BFF 계층 추가로 네트워크 홉이 증가하여 응답 지연이 발생함

> 요약: 코드 중복·운영 복잡도·지연 누적이 BFF 패턴의 주요 트레이드오프임

## Ⅴ. 개선방안
1. 단기: 공통 로직을 Shared Library로 추출하여 BFF 간 코드 중복을 줄임
2. 중기: BFF를 컨테이너 기반으로 운영하고 자동 스케일링을 적용하여 운영 부담을 경감함
3. 장기: GraphQL Federation을 도입하여 단일 엔드포인트로 BFF 역할을 통합함

> 요약: 공통 라이브러리 → 컨테이너 운영 → GraphQL 통합으로 단계적 개선함

## Ⅵ. 전망
- 발전 방향: GraphQL·서버리스 BFF가 경량 BFF의 대안으로 확산될 전망임
- 기술사적 판단: 클라이언트 다양성이 증가할수록 BFF의 가치가 높아지나 과도 분리는 경계 필요함
- 기술사 제언: 클라이언트 유형이 3개 이상일 때 도입을 검토하고, 그 미만이면 API Gateway로 충분함
