# 📖 【암기용】 개념 완전 이해

## 한눈에
- **개요**: 기술부채는 빠른 출시를 위해 타협한 품질 저하가 이자로 쌓이는 현상이며, 리팩터링은 외부 동작 변경 없이 내부 구조를 개선하여 부채를 갚는 활동임
- **왜 필요한가**: 부채를 방치하면 새 기능을 추가하는 비용(이자)이 기하급수적으로 늘어나 최종적으로 파산(재개발 불가피)에 이름
- **핵심 직관**: 소프트웨어의 신용카드 할부(기술부채)와 할부원금 상환(리팩터링)

## 핵심 용어 정리

| 용어/표기 | 의미 | 비유·예 |
|:---|:---|:---|
| 기술부채 (Technical Debt) | 단기적 이득(빠른 출시)을 위해 장기적 품질을 희생한 결과물 | 마이너스 통장 대출 |
| 리팩터링 (Refactoring) | 외부 동작은 그대로 둔 채 코드 가독성과 구조를 개선하는 작업 | 건물 뼈대 보수 공사 |
| 코드 스멜 (Code Smell) | 코드에 잠재적 문제가 있음을 암시하는 징후 | 음식에서 나는 쉰내 |

## 깊이 이해
- **배경·문제의식**: 비즈니스 요구사항은 계속 변하고 일정은 촉박함. 개발자는 복붙(Copy&Paste)이나 땜질식 코드를 작성하게 되며, 이것이 쌓이면 유지보수가 불가능한 스파게티 코드가 됨.
- **작동 원리 (리팩터링 과정)**: 테스트 코드가 작성된 상태에서 → 조금씩 코드를 변경하고 → 매번 테스트를 돌려 기능이 깨지지 않았는지 확인하며 구조를 개선함.
- **비유**: 엉망으로 꼬인 이어폰 줄. 처음에는 그냥 듣지만(기술부채), 나중에는 줄을 푸는 데(리팩터링) 음악 듣는 시간보다 더 오래 걸림.
- **구체 예시**: `calculatePrice` 함수가 500줄짜리 덩어리일 때, 이를 `applyDiscount`, `addTax` 등 10줄짜리 함수 여러 개로 분리하여 가독성을 높임(Extract Method 기법).
- **흔한 오해·주의점**: "리팩터링 = 버그 수정 또는 새 기능 추가"로 오해함. 리팩터링은 절대 기능이나 동작을 변경하지 않으며, 오직 '구조 개선'만 수행함.

## 연결 개념
- **코드 스멜, 클린 코드, TDD, 기술부채 사분면**

# 📝 【답안용】 시험 답안 템플릿

## 핵심 인사이트 (3줄 요약)

> 1. **본질**: 내부 구조 개선(리팩터링)을 통한 소프트웨어 엔트로피(기술부채) 통제
> 2. **가치**: 코드 가독성 향상, 유지보수 비용 절감, 시스템 수명 연장
> 3. **판단 포인트**: 테스트 자동화(회귀 테스트)가 뒷받침되지 않은 리팩터링은 치명적 장애 유발

## 출제 의도 및 답안 포인트

| 출제 의도 | 반드시 짚을 핵심 | 감점 회피 포인트 |
|:---|:---|:---|
| 부채와 리팩터링의 인과관계 | 외부 동작 불변 원칙, 원인과 상환의 대응 | 리팩터링을 기능 추가로 오해 누락 |
| 실무 적용 가능성 확인 | TDD 연계, 지속적 리팩터링, 코드 스멜 식별 | 구체적인 기법(Extract 등) 누락 |

> 요약: 기술부채 상환을 위해 외부 동작 불변을 원칙으로 내부 구조를 점진적으로 개선하는 과정임

---

## Ⅰ. 개요 및 필요성

- 개요: 기술부채는 단기 목표 달성을 위해 누적된 구조적 결함이며, 리팩터링은 외부 동작 변경 없이 내부 논리를 개선해 부채를 상환하는 활동임
- 배경: 소프트웨어 생명주기 장기화로 인해 변경 요구가 누적되며 아키텍처 부식(Architecture Erosion) 현상 발생
- 필요성: 유지보수 비용(부채 이자)이 신규 개발 가치를 초과하는 임계점 도달을 방지하기 위함

---

## Ⅱ. 구조 및 구성요소

```text
[요구사항/코드 스멜] -> [리팩터링 대상 식별] -> [테스트 구축/검증] -> [코드 구조 변환] -> [동작 불변 확인]
                          |                         |                      |
                          +-> 메트릭/정적분석         +-> 단위/회귀테스트      +-> CI/CD 병합
```

| 구성요소 | 역할 | 특이사항 |
|:---|:---|:---|
| 코드 스멜 식별 | 중복 코드, 거대 클래스 등 부채의 징후 탐지 | SonarQube 등 활용 |
| 회귀 테스트 셋 | 코드 변경 전후의 외부 동작 동일성 보장 | 리팩터링의 필수 전제 |
| 구조 변환 기법 | Extract Method, Rename Variable 등 구체적 패턴 적용 | 스몰 스텝(Small Step) 진행 |
| 지속적 통합 (CI) | 변경된 코드가 전체 시스템에 미치는 영향 자동 검증 | 데일리 빌드·테스트 |

> 요약: 부채를 식별하고, 안전망(테스트) 위에서 점진적 코드 변환을 수행하여 무결성을 유지함

---

## Ⅲ. 동작원리 및 흐름도

```text
스멜 감지 -> 테스트 작성 -> 구조 변환 수행 -> 회귀 테스트 검증 -> 리팩터링 완료
```

- 1단계 [부채/스멜 감지]: 정적 분석 도구 및 코드 리뷰를 통해 복잡도(CC)가 높거나 중복된 코드 식별
- 2단계 [테스트 안전망 구축]: 변경 대상 코드에 대한 단위 테스트 및 통합 테스트 작성 (커버리지 확보)
- 3단계 [점진적 구조 변환]: 마틴 파울러의 72개 기법(메서드 추출, 클래스 이동 등)을 소규모 단위로 적용
- 4단계 [검증 및 통합]: 자동화된 테스트를 실행하여 기존 동작과 100% 동일함이 확인되면 메인 브랜치 병합

> 요약: 결함 탐지 후 반드시 테스트를 통해 외부 동작 불변을 증명하며 코드를 개선함

---

## Ⅳ. 특징

- 외부 동작 불변: 사용자가 체감하는 기능이나 인터페이스는 변경되지 않고 캡슐화와 응집도만 향상됨
- 점진적 접근: 빅뱅(Big-bang) 방식의 재개발이 아닌, 일상적인 개발 과정에서 소규모로 지속 수행됨
- 품질 향상: 클래스와 메서드 크기를 줄여 코드 가독성을 높이고, 잠재적 버그 발생 확률을 낮춤
- 오버헤드 존재: 초기 테스트 코드 작성 및 검증 환경 구축에 시간과 자원이 소요됨

> 요약: 외부 기능은 유지한 채 내부 품질을 높이는 상시 활동이나, 테스트 구축 비용이 수반됨

---

## Ⅴ. 심화 비교 및 적용 판단

| 비교 축 | 리팩터링 (Refactoring) | 재설계/재개발 (Re-engineering) | 선택 기준 |
|:---|:---|:---|:---|
| 변경 대상 | 코드 블록, 클래스, 모듈 내부 | 시스템 전체 아키텍처 및 프레임워크 | 시스템 노후화 정도 |
| 외부 동작 | 100% 동일 유지 (기능 추가 없음) | 변경될 수 있음 (새로운 UI/UX 등) | 비즈니스 요구사항 |
| 투입 리스크 | 낮음 (테스트로 상시 검증 가능) | 매우 높음 (빅뱅 도입에 따른 장애 위험) | 가용 예산 및 시간 |

> 요약: 모듈 단위의 부채는 리팩터링으로, 아키텍처 한계 도달 시 재개발로 접근해야 함

**리스크·대응:**
- 기능 결함 유입: 코드 변환 중 실수로 로직 훼손 → 변경 전 반드시 80% 이상 테스트 커버리지 확보 (지표: 분기 커버리지)
- 일정 지연: 리팩터링에 과도한 시간 투입으로 릴리스 지연 → 스프린트 20%를 기술부채 상환 스파이크로 할당 (지표: 부채 처리 리드타임)

---

## Ⅵ. 실무 적용 및 결론

**적용 방안 (지속적 기술부채 상환):**
1. 정량적 부채 측정: SonarQube를 CI/CD 파이프라인에 통합하여 코드 복잡도, 스멜, 중복률을 가시화하고 기술부채 지수(SQALE) 관리
2. 보이스카우트 규칙 적용: 개발자가 코드를 수정할 때 자신이 체크아웃한 상태보다 항상 더 깨끗한 상태로 커밋하도록 정책화
3. 리팩터링 기법 내재화: 중복 코드에는 Extract Method, 조건문이 복잡할 때는 Replace Conditional with Polymorphism 등 표준 패턴 적용

**결론:**
- 기술사 판단: 기술부채는 무조건 나쁜 것이 아니라 비즈니스 속도를 위한 전략적 도구이나, 통제되지 않는 부채는 시스템 파산을 부르므로 상시 리팩터링이 필수임
- 향후 방향: 최근 생성형 AI(GitHub Copilot 등)를 활용한 자동 리팩터링 제안 및 코드 스멜 탐지 영역으로 고도화 중임
