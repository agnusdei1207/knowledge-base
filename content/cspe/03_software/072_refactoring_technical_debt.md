## 미리 알고가기

- 리팩터링은 외부 동작을 유지한 채 내부 구조를 개선하는 활동임
- 기술부채는 빠른 선택의 대가로 미래 변경 비용이 커진 상태를 뜻함
- 보호 테스트는 구조를 바꿔도 기존 동작이 유지되는지 확인하는 회귀 방지 테스트임

## Ⅰ. 개요

- **정의/개념**: 리팩터링은 소프트웨어 외부 동작을 바꾸지 않으면서 내부 구조를 개선하는 활동이고, 기술부채는 단기 생산성을 위해 미뤄 둔 설계와 품질 문제 때문에 이후 변경 비용과 위험이 누적된 상태임.
- **배경/필요성**: 빠른 개발이 필요한 현실에서는 부채를 완전히 없애기 어렵기 때문에, 어떤 부채를 언제 갚고 어떤 영역을 먼저 구조 개선할지 판단할 기준이 필요함.

## Ⅱ. 특징

- 리팩터링은 변경 속도와 테스트 용이성과 가독성을 높이는 개선 활동임
- 기술부채는 시간이 지날수록 기능 개발 속도와 결함률에 영향을 축적함
- 테스트 보호망 없이 리팩터링하면 회귀 위험이 커짐
- 변경 범위가 큰 일괄 리팩터링은 기능 개발 일정과 회귀 검증 범위를 함께 늘림

## Ⅲ. 종류 및 비교

| 구분 | 리팩터링 | 기술부채 |
|:---|:---|:---|
| 성격 | 구조를 개선하는 실행 활동임 | 미래 변경 비용을 키우는 누적 상태임 |
| 직접 목적 | 가독성과 변경 용이성과 테스트 가능성을 높임 | 어떤 비용과 위험이 쌓였는지 인식하고 관리하게 함 |
| 관리 결과 | 중복·결합·복잡도를 줄이고 외부 동작 유지 | 부채 원인·영향·상환 비용을 기록해 우선순위 결정 |
| 주된 한계 | 테스트 없이 수행하면 회귀 결함을 만들 수 있음 | 측정과 기록이 없으면 추상적 불만으로만 남기 쉬움 |

> 요약: 리팩터링과 기술부채 관리는 코드 미관이 아니라 미래 변경 비용을 낮추기 위한 투자 판단임.

## Ⅳ. 구성요소 및 구조

| 구성요소 | 설명 |
|:---|:---|
| 동작 보호망 | 자동 테스트가 있어야 리팩터링의 회귀 위험을 통제할 수 있음 |
| 부채 항목 목록 | 부채 항목을 기록해 감정이 아니라 근거 기반 우선순위를 가능하게 함 |
| 영향 지표 | 변경 속도와 결함률과 복잡도를 함께 봐 부채 비용을 설명하게 함 |
| 리팩터링 투입 시점 | 기능 개발 중 어느 시점에 구조 개선을 넣을지 운영 리듬을 정함 |

## Ⅴ. 원리 및 절차 흐름도

```text
+-------------+     +-------------+     +-------------+     +-------------+
| 부채 식별      | --> | 우선순위 평가  | --> | 보호 테스트 확보 | --> | 리팩터링 실행  |
+-------------+     +-------------+     +-------------+     +-------------+
```

1. **부채 식별**: 복잡도와 중복과 취약 구조를 찾음
2. **우선순위 평가**: 변경 빈도와 영향도를 기준으로 정렬함
3. **보호 테스트 확보**: 회귀 방지 테스트를 준비함
4. **리팩터링 실행**: 구조를 개선하고 결과를 측정함

## Ⅵ. 실무 적용 및 유의점

1. 레거시 핵심 모듈에서는 기술부채를 단순 불편함이 아니라 변경 비용 증가 요인으로 다뤄야 하므로 부채 항목을 목록화하고 기능 반영 시간 변화와 반복 결함 비율로 확인함
2. 스프린트 안에서 구조 개선을 수행할 때는 큰 정리 작업보다 작은 배치 리팩터링이 안전하므로 보호 테스트를 먼저 두고 리팩터링 단위 크기와 회귀 결함 건수로 확인함

## Ⅶ. 결론

리팩터링과 기술부채 관리는 당장 보이는 속도보다 이후 변경 비용을 더 낮출 수 있는지로 판단해야 함.
