## 미리 알고가기

- 리팩터링은 외부 동작을 유지한 채 내부 구조를 개선하는 활동임
- 기술부채는 빠른 선택의 대가로 미래 변경 비용이 증가한 상태를 뜻함
- 둘은 반대 개념이 아니라 지속 개선 관계에 있음

## Ⅰ. 개요

- **정의/개념**: 리팩터링은 소프트웨어 외부 동작을 바꾸지 않으면서 내부 구조를 개선하는 활동이고, 기술부채는 단기 생산성을 위해 미뤄둔 설계·품질 문제로 인해 미래 변경 비용과 위험이 누적된 상태임
- **배경/필요성**: 빠른 개발이 필요한 현실에서는 부채가 완전히 없어질 수 없으므로, 누적된 부채를 언제 어떻게 갚으며 변경 비용을 관리할지 전략이 필요함

## Ⅱ. 특징

- 리팩터링은 변경 속도와 테스트 용이성과 가독성을 높이는 예방 활동임
- 기술부채는 당장 보이지 않아도 변경 속도와 결함률에 영향을 축적함
- 무계획 리팩터링은 기능 개발을 밀어내고 가치 설명이 어려울 수 있음
- 테스트 보호망 없이 리팩터링하면 회귀 위험이 커진다

## Ⅲ. 종류 및 비교

| 판단 기준 | 리팩터링 | 기술부채 |
|:---|:---|:---|
| 성격 | 개선 활동 | 누적된 문제 상태 |
| 목적 | 구조 품질 향상 | 비용과 위험 인식 대상 |
| 장점 | 변경 용이성 증가 | 우선순위화 대상 제공 |
| 한계 | 테스트 없이 위험 | 측정 안 하면 방치되기 쉬움 |

## Ⅳ. 구성요소 및 구조

| 구성요소 | 설명 |
|:---|:---|
| Behavior Safety Net | 자동 테스트가 있어야 리팩터링의 회귀 위험을 통제할 수 있음 |
| Debt Item Registry | 부채 항목을 목록화해 감정이 아니라 근거 기반 우선순위를 가능하게 함 |
| Impact Metric | 변경 속도와 결함률과 복잡도로 부채 비용을 계량해 설득력을 높임 |
| Refactoring Window | 기능 개발 중 어느 시점에 구조 개선을 삽입할지 운영 리듬을 정함 |

## Ⅴ. 원리 및 절차 흐름도

```text
+-------------+     +-------------+     +-------------+     +-------------+
| 부채 식별      | --> | 우선순위 평가  | --> | 보호 테스트 확보 | --> | 리팩터링 실행  |
+-------------+     +-------------+     +-------------+     +-------------+
```

1. **부채 식별**: 복잡도와 중복과 취약 구조를 찾음
2. **우선순위 평가**: 변경 빈도와 영향도를 기준으로 정렬함
3. **보호 테스트 확보**: 회귀 방지 테스트를 준비함
4. **리팩터링 실행**: 구조를 개선하고 결과를 측정함

## Ⅵ. 문제점 및 해결 방안

1. 문제: 기술부채를 추상적 불편함으로만 다루면 사업 우선순위에 밀려 계속 방치될 수 있음
   - 해결방안: 변경 비용 지표를 함께 제시하고 debt interest rate와 cycle time delta로 검증함
2. 문제: 테스트 없이 대규모 리팩터링을 하면 구조는 좋아져도 회귀 결함이 급증할 수 있음
   - 해결방안: 안전망 확보 후 작은 단위로 수행하고 regression defect count와 refactoring batch size로 검증함
3. 문제: 모든 코드를 완벽히 정리하려 하면 실질 가치보다 내부 정리 자체가 목적이 될 수 있음
   - 해결방안: 고변경 영역 우선 전략을 적용하고 hotspot coverage와 delivery impact score로 검증함

## Ⅶ. 적용 사례

- 레거시 핵심 모듈에서는 기술부채 목록을 운영하고 확인 지표는 debt interest rate와 hotspot coverage임
- 스프린트 내 개선 활동에서는 소규모 리팩터링을 수행하고 확인 지표는 refactoring batch size와 regression defect count임
- 아키텍처 개선 제안에서는 부채 비용을 계량하고 확인 지표는 cycle time delta와 delivery impact score임

## Ⅷ. 결론

리팩터링과 기술부채 관리는 코드 미관이 아니라 미래 변경 비용을 낮추기 위한 투자 의사결정으로 다뤄야 함.
