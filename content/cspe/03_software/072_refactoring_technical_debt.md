# 📖 【암기용】 개념 완전 이해

> 목적: 리팩터링과 기술부채를 처음 봐도 외부 동작 보존과 부채 이자 관점에서 이해하게 만든다. 시험 답안 양식이 아니라, 이해를 위한 설명이다.

## 한눈에
- **개요**: 리팩터링은 외부 동작을 유지하며 내부 구조를 개선하는 활동이고, 기술부채는 단기 선택이 장기 변경 비용으로 남은 상태임
- **왜 필요한가**: 기능 추가만 반복하면 수정 위치 예측이 어려워지고 결함 수정 시간이 증가함. 리팩터링은 변경 비용 상승을 제어함.
- **핵심 직관**: 지저분한 창고에서 물건은 그대로 두고 선반과 동선을 다시 짜서 다음 작업 시간을 줄이는 일임.

## 깊이 이해
- **배경·문제의식**: 일정 압박, 요구 변경, 임시 설계는 중복 코드·복잡한 조건·낮은 테스트 커버리지로 남음. 시간이 지날수록 수정 한 건에 필요한 파일 수와 회귀 결함이 증가함.
- **작동 원리**: 테스트로 현재 동작을 고정하고, 작은 단계로 이름 변경·메서드 추출·의존성 분리·중복 제거를 수행함. 각 단계 후 테스트를 실행해 외부 동작 보존을 확인함.
- **비유**: 영업 중인 식당의 메뉴와 손님 경험은 그대로 두고, 주방 배치와 재료 보관 위치를 바꾸는 작업임.
- **구체 예시**: 800라인 결제 메서드를 검증·승인·정산 모듈로 분리하고 단위 테스트 120개를 추가해 변경 파일 수를 12개에서 4개로 줄임.
- **흔한 오해·주의점**: 리팩터링은 기능 추가가 아님. 테스트 없이 구조를 바꾸면 개선 활동이 아니라 동작 변경 위험이 큰 재작성에 가까움.

## 연결 개념
- Code Smell — 리팩터링을 촉발하는 구조적 징후
- Technical Debt Quadrant — 부채 발생 의도와 상환 전략 분류
- Regression Test — 외부 동작 보존 검증 수단

# 📝 【답안용】 시험 답안 템플릿

> 목적: 시험장에서 25분에 그대로 쓰는 답안 양식. 작성방식(추상표현 금지·수치·도식·문제유형 전환)을 엄격히 지킨다.
> 핵심: 리팩터링은 미화 작업이 아니라 동작 보존 테스트를 전제로 기술부채 이자를 낮추는 위험 기반 개선 활동이다.

## 핵심 인사이트 (3줄 요약)

> 1. **본질**: 리팩터링은 외부 행위는 유지하고 내부 구조를 변경해 유지보수 비용을 줄이는 소프트웨어 설계 개선 활동이다.
> 2. **가치**: 기술부채 이자는 변경 리드타임, 결함 재발률, 코드 복잡도, 테스트 공백으로 측정하며 우선순위에 따라 상환함.
> 3. **판단 포인트**: 테스트 없는 대규모 재작성보다 위험 지점의 작은 리팩터링과 회귀 테스트 자동화가 우선임.

## 출제 의도 및 답안 포인트

| 출제 의도 | 반드시 짚을 핵심 | 감점 회피 포인트 |
|:---|:---|:---|
| 리팩터링 개념 이해 확인 | external behavior preserving, small step, test first | 기능 변경·재개발과 혼동 |
| 기술부채 관리 판단 확인 | debt principal, debt interest, repayment backlog | 부채를 나쁜 코드 일반론으로만 설명 |
| 개선 우선순위 역량 확인 | 복잡도, 변경 빈도, 장애 영향도 기반 선정 | 전체 재작성 제안으로 일정·위험 누락 |

> 요약: 이 문제는 구조 개선 활동을 테스트·지표·상환 전략과 연결하는 판단력을 요구한다.

---

## Ⅰ. 개요 및 필요성

- 개요: 동작 보존형 구조 개선
- 배경: 단기 일정, 임시 설계, 테스트 부족은 미래 변경 비용으로 전가되고 변경 시 회귀 결함과 리뷰 지연을 반복 발생시킨다.
- 필요성: 리팩터링은 테스트 통과 상태에서 중복 제거, 결합도 축소, 모듈 경계 정리로 변경 리드타임 2배 증가 같은 부채 누적을 통제한다.

---

## Ⅱ. 구조 및 구성요소

```text
Business Change -> Code Smell Detection -> Debt Backlog
  -> Risk Scoring -> Refactoring Plan -> Test Safety Net
  -> Small Change -> Regression Test -> Merge
```

| 구성요소 | 역할 | 특이사항 |
|:---|:---|:---|
| Code Smell | 구조 문제의 관찰 가능한 징후 | Long Method, Duplicated Code |
| Debt Backlog | 부채 항목·원인·영향 기록 | ADR, 이슈, 소유자 연결 |
| Risk Scoring | 상환 우선순위 산정 | 변경 빈도, 장애 영향도, 복잡도 |
| Test Safety Net | 동작 보존 검증 | 단위·통합·회귀 테스트 |
| Refactoring Catalog | 적용 기법 목록 | Extract Method, Move Class |

> 요약: 리팩터링 구조는 부채 식별, 위험 점수화, 테스트 안전망, 작은 변경, 회귀 검증으로 구성된다.

---

## Ⅲ. 동작원리 및 흐름도

```text
Smell Found -> Characterization Test -> Refactoring Step
  -> Unit Test -> Static Analysis
  -> Review -> Merge -> Debt Metric Update
```

| 단계 | 처리 내용 | 검증 기준 |
|:---:|:---|:---|
| 1 | 변경 빈도 높은 파일과 코드 스멜 식별 | churn 상위 20%, complexity 15 초과 |
| 2 | 현재 동작을 테스트로 고정 | 회귀 테스트 pass, 커버리지 70% 이상 |
| 3 | 메서드 추출·중복 제거·의존성 역전 수행 | 공개 API와 응답값 동일 |
| 4 | 정적 분석과 리뷰로 구조 개선 확인 | duplication 5% 이하, critical smell 0건 |
| 5 | 부채 백로그와 ADR 업데이트 | 상환 상태, 잔여 리스크 기록 |

> 요약: 리팩터링은 테스트로 현재 동작을 고정한 뒤 작은 구조 변경과 지표 갱신을 반복한다.

---

## Ⅳ. 특징

| 구분 | 단순 수정 | 리팩터링 | 정량 기준 |
|:---|:---|:---|:---|
| 목적 | 결함·기능 처리 | 내부 구조 개선 | 외부 API 결과 동일 |
| 검증 | 변경 기능 테스트 | 회귀 테스트 전체 실행 | pass rate 100% |
| 범위 | 요구사항 단위 | 냄새·부채 단위 | complexity, duplication |
| 위험 | 국소 결함 | 광범위 회귀 가능 | 변경 파일 수, 테스트 커버리지 |
| 산출물 | 코드 변경 | 코드+부채 기록+지표 | ADR, SonarQube 리포트 |

> 요약: 리팩터링은 동작 동일성 검증과 구조 지표 개선이 동시에 확인되어야 한다.

## Ⅴ. 심화 비교 및 적용 판단

| 비교 축 | 기존/대안 | 본 키워드 | 선택 기준 |
|:---|:---|:---|:---|
| 구조 | Big Rewrite | Incremental Refactoring | 운영 중 서비스는 작은 단계 우선 |
| 비용/성능 | 기능 개발 우선 | 부채 이자 절감 | 변경 리드타임 30% 이상 증가 시 상환 |
| 운영/위험 | 장애 후 수정 | 선제적 부채 백로그 | 장애 빈도·변경 빈도 높은 모듈 우선 |
| 조직 | 개인 판단 | ADR·리뷰·지표 기반 | 팀 공통 기준 필요 시 도입 |

> 요약: 리팩터링은 전체 재작성보다 변경 빈도와 장애 영향도가 높은 영역부터 점진 상환하는 선택이 타당하다.

| 리스크 | 원인 | 대응 방안 | 확인 지표 |
|:---|:---|:---|:---|
| 기능 회귀 | 테스트 없이 구조 변경 | characterization test 선행 | 회귀 테스트 pass 100% |
| 일정 지연 | 과도한 범위 확대 | 1~2일 단위 slice | PR당 변경 라인 400 이하 |
| 가치 불명확 | 부채 이자 미측정 | lead time, defect rate 추적 | 변경 리드타임 감소율 |
| 설계 왜곡 | 패턴 과잉 적용 | 리뷰 체크리스트, ADR | 신규 추상화 사용률 |

> 요약: 리팩터링 리스크는 테스트 안전망, 작은 PR, 부채 이자 지표, 설계 리뷰로 통제한다.

| 점검 항목 | 목표 기준 | 측정 방법 |
|:---|:---|:---|
| 복잡도 | cyclomatic complexity 10~15 이하 | SonarQube, IDE 분석 |
| 중복 | duplicated lines 5% 이하 | 정적 분석 리포트 |
| 변경 비용 | lead time 30% 감소 | Jira, Git commit, DORA |
| 품질 | 회귀 결함 0건, 테스트 pass 100% | CI, 결함 추적 |

> 요약: 성공 여부는 복잡도, 중복률, 변경 리드타임, 회귀 결함으로 판단한다.

## Ⅵ. 실무 적용 및 결론

**적용 방안 3개 (필수 — 단계별 또는 항목별):**
1. 변경 빈도 상위 20% 파일을 대상으로 complexity 15 초과, duplication 5% 초과, flaky test 존재 여부를 점수화해 부채 백로그를 작성함.
2. 리팩터링 전 characterization test와 계약 테스트를 추가하고 CI에서 unit·integration·SAST를 PR gate로 실행함.
3. 2주 단위로 부채 상환 capacity 10~20%를 배정하고 ADR에 원인, 선택안, 상환 기한, 잔여 리스크를 기록함.

**결론 (2줄):**
- 기술사 판단: 변경 빈도·장애 영향도·테스트 안전망이 모두 확보된 영역은 점진 리팩터링을 선택하고, 제품 방향이 바뀐 영역은 별도 재설계를 검토함.
- 향후 방향: 리팩터링 관리는 SonarQube, CodeQL, DORA 지표, ADR을 결합한 엔지니어링 거버넌스로 전환됨.
