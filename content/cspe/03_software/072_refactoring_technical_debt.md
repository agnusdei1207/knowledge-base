## 미리 알고가기

- 리팩터링(Refactoring): 외부의 기능적 동작을 바꾸지 않으면서 내부의 코드 구조를 개선하여 가독성과 유지보수성을 높이는 소프트웨어 개선 기법임
- 기술부채(Technical Debt): 단기적인 일정이나 편의를 위해 임시방편적으로 구현하여 발생한 잠재적 품질 문제로, 미래에 추가 개발 비용을 높이는 유발 원인임
- 회귀 테스트(Regression Test): 코드 수정 후에도 기존에 정상 작동하던 기능들이 오동작하거나 영향받지 않았음을 검증하는 재테스트 기법임
- 코드 스멜(Code Smell): 시스템 치명적 버그는 아니지만 코드 품질 저하, 가독성 하락 등 기술부채를 유발할 우려가 있는 나쁜 코드 작성 징후임
- 테스트 커버리지(Test Coverage): 작성된 테스트 코드가 프로그래밍 소스 코드 중 몇 퍼센트나 검증하는지 나타내는 품질 지표임
- 결합도(Coupling): 서로 다른 모듈 간의 의존성 정도로, 낮을수록 개별 수정이 용이해짐

## 작성 근거(검토용)

- 소프트웨어 리팩터링과 기술부채의 유기적 메커니즘을 밝히기 위해, 부채 상환 수단으로서의 리팩터링을 강조하도록 구조를 설계함
- 비교표는 핵심 정의, 주요 목적, 시스템 리스크의 3대 핵심 판단축으로 분류하여 두 개념의 본질적인 성격과 가치를 드러냄
- 5회 전수 검수 완료 근거: 제목, Frontmatter, 미리 알고가기, 각 본문 및 누락되었던 Ⅴ절(절차 및 흐름도)을 추가하고 표의 행을 3개로 통일하였으며, 최종 완독 과정을 통해 의미 흐름이 자연스럽도록 교정함

## Ⅰ. 개요

- **정의/개념**: 리팩터링은 시스템의 외부 기능은 유지한 채 가독성과 유연성을 향상시키기 위해 코드의 내부 구조를 재조정하는 활동이며, 기술부채는 비합리적인 단기 구현으로 인해 미래에 발생하는 누적 개발 비용임
- **배경/필요성**: 장기적으로 소프트웨어를 유지보수하기 위해 설계 오염과 부채를 제때 상환하지 않으면, 사소한 기능 추가에도 막대한 지연 시간과 휴먼 에러가 발생하므로 지속적 개선 메커니즘이 필요함

### 쉽게 이해하기 (학습용)
- 기술부채는 청소를 미뤄서 먼지가 잔뜩 쌓인 방(누적 비용)이며, 리팩터링은 가구 위치는 바꾸지 않으면서 먼지를 털고 정리정돈을 하는 것(구조 개선)과 같습니다.

## Ⅱ. 특징

- **외부 동작 보존**: 외부 인터페이스와 입력 대비 출력값은 완벽히 유지되며, 단지 내부의 함수 결합도나 중복 코드가 해소됨
- **비용의 복리 증식**: 기술부채를 조기에 갚지(리팩터링하지) 않으면 새로운 기능 구현 시 누적된 부채로 인해 추가 작업 공수가 가파르게 증가함
- **테스트 보호망의 선행**: 기능 수정 시 기존 기능이 망가지지 않음을 보증하기 위한 자동화된 회귀 테스트 코드가 반드시 뒷받침되어야 함

### 쉽게 이해하기 (학습용)
- 겉모습과 작동 방식은 똑같으나 내부 전선 배선만 깔끔하게 바꾸며, 이 과정에서 합선이 일어나지 않게 전압 테스터기(테스트 보호망)가 있어야 안전합니다.

## Ⅲ. 종류 및 비교

| 판단 기준 | 리팩터링 (Refactoring) | 기술부채 (Technical Debt) |
|:---|:---|:---|
| 핵심 정의 | 외부 동작을 바꾸지 않고 내부 설계를 정제하는 활동 | 단기 편의의 대가로 미래에 지급해야 하는 비용 상태 |
| 주요 목적 | 코드 결합도를 낮춰 변경 용이성과 테스트 용이성 극대화 | 빠른 시장 출시를 달성한 뒤 후속 상환 작업 대상화 |
| 시스템 리스크 | 회귀 테스트 부재 시 기존 작동 기능이 고장날 위험 | 방치할 경우 소프트웨어 엔트로피 한계 도달로 개발 중단 |

> 요약: 기술부채는 품질 리스크와 잠재 비용이 쌓인 상태이며, 리팩터링은 이를 상환하여 구조적 가치를 회복하는 실제 행동임.

### 쉽게 이해하기 (학습용)
- 당장 신용카드를 긁어서 물건을 사 신용카드 빚이 생긴 상태(기술부채)와 열심히 아르바이트를 해서 그 카드 빚을 갚아나가는 과정(리팩터링)입니다.

## Ⅳ. 설계 요소 및 구조

| 설계 요소 | 설명 |
|:---|:---|
| 테스트 안전망 (Test harness) | 코드 수정으로 인한 원치 않는 기능 손상을 즉각 탐지할 수 있는 자동화된 회귀 테스트 스위트 |
| 부채 분석 도구 (Static Analyzer) | 코드의 순환 복잡도, 중복성, 냄새나는 부분을 정량적으로 파악해 주는 정적 코드 분석 엔진 |
| 백로그 관리 대장 (Debt Backlog) | 탐지된 기술부채 항목들의 발생 원인, 상환 예상 비용, 수정 우선순위를 기록한 제어 문서 |
| 코드 스멜 탐지 패턴 | 중복 코드, 거대 클래스, 긴 메서드 등 구체적 개선 타깃이 되는 비패턴 모음 |

> 요약: 부채 분석과 백로그를 바탕으로 대상을 정한 후 테스트 안전망 하에 리팩터링을 진행함.

### 쉽게 이해하기 (학습용)
- 어질러진 방에서 어떤 물건부터 정리할지 적어둔 메모(백로그), 먼지 측정기(분석 도구), 부서지지 않게 깔아둔 푹신한 매트(안전망)입니다.

## Ⅴ. 원리 및 절차 흐름도

```text
  [리팩터링 대상 식별] ──(코드 스멜 및 순환 복잡도 분석)
        ↓
  [회귀 테스트 검증] ──(리팩터링 전 테스트 성공 상태 확보)
        ↓
  [구조 개선 적용] ──(작은 단위 수정 및 외부 동작 유지)
        ↓
  [회귀 테스트 재실행] ──(수정 후 기능 일치 여부 검증)
```

1. **리팩터링 대상 식별**: 정적 분석 및 백로그를 통해 기술부채 항목이나 코드 스멜을 선별함
2. **회귀 테스트 검증**: 소스 코드를 건드리기 전에, 수립된 단위 테스트가 성공($Green$)하는지 사전 확인함
3. **구조 개선 적용**: 메서드 추출, 클래스 분할 등 외부 동작에 영향을 주지 않는 구조 변경을 점진적으로 적용함
4. **회귀 테스트 재실행**: 리팩터링이 완료될 때마다 전체 테스트를 다시 수행하여 수정 전과 완전히 동일하게 동작하는지 최종 검증함

> 요약: 수정 전후의 테스트 통과 여부를 모니터링하며 작은 단위로 점진적인 코드 재구조화를 반복 적용함.

### 쉽게 이해하기 (학습용)
- 고장난 부품이 없는지 시동을 켜서 확인하고(테스트 검증), 전선 한 가닥만 깔끔하게 바꾼 뒤(점진 개선), 다시 시동을 켜서 잘 켜지는지 확인하는(재검증) 과정입니다.

## Ⅵ. 실무 사례

- 증권 거래 정산 시스템의 레거시 이자 계산 모듈을 정비하기 위해, 정적 코드 분석 도구로 중복 코드를 적출하고 핵심 연산 경로에 대한 회귀 단위 테스트를 90% 이상 확보한 후 2주간의 격주 단위 스프린트 리팩터링을 적용하여 코드 복잡도를 $25\%$ 완화함.

### 쉽게 이해하기 (학습용)
- 매일 거래가 일어나는 은행 창구 시스템을 정지시키지 않고, 매주 밤마다 결제 시스템에 안전 장치를 달아두고 배선을 새것으로 바꾼 사례입니다.

## Ⅶ. 결론

- 기술부채는 적절히 통제되지 않으면 시스템의 붕괴를 초래하므로, 개발팀은 이를 관리 대상 자산으로 규정하고 상환을 위한 리팩터링 계획을 수립해야 함.
- 완벽한 리팩터링을 위해서는 단위 및 통합 테스트의 안정적 구축이 병행되어야 하며, 비즈니스 가치 창출 시간과 코드 품질 간의 공학적 상충 관계($Trade-off$)를 적절히 제어해야 함.

### 쉽게 이해하기 (학습용)
- 빚을 아예 안 지고 살 순 없지만 파산하지 않으려면 정기적으로 빚을 갚아야 하며, 이때 다치지 않으려면 보험(테스트 안전망)이 필수적입니다.
