# 📖 【암기용】 개념 완전 이해

> 목적: 이 개념을 처음 보는 사람도 완벽히 이해하게 만든다. 시험 답안 양식이 아니라, 이해를 위한 친절한 설명이다.

## 한눈에
- **개요**: SDLC(Software Development Lifecycle, 소프트웨어 개발 생명주기)는 소프트웨어를 요구사항 정의부터 폐기까지 체계적으로 개발·운영하기 위해 표준화한 **개발 프로세스(공정) 모델**이다. 요구사항 분석·설계·구현·테스트·유지보수 단계로 구성되며, 이 단계들을 어떤 순서·반복 방식으로 수행할지를 정한 구체적 절차가 폭포수·애자일 같은 개발 방법론이다.
- **왜 필요한가**: 1960년대 하드웨어 성능은 빠르게 발전했지만 소프트웨어 개발 생산성이 이를 따라가지 못해 납기 지연·예산 초과·품질 저하가 반복되는 소프트웨어 위기(Software Crisis)가 발생했다. 설계 없이 코딩부터 시작하는 주먹구구식(Build-and-Fix) 개발은 요구사항이 바뀔 때마다 코드 전체를 다시 짜야 하는 비용 폭발을 낳았다. SDLC는 제조·건축업의 공정 관리 개념을 소프트웨어에 적용해, 각 단계마다 산출물과 검토 절차를 두어 이 위험을 통제한다.
- **핵심 직관**: SDLC의 각 단계는 "제대로 된 것을 만들고 있는가(Validation, 고객 요구 충족 여부)"와 "만드는 방식이 올바른가(Verification, 설계·명세 준수 여부)"를 단계마다 검증하기 위한 체크포인트다.

## 핵심 용어 정리 (내부에 등장하는 것들)

| 용어 | 의미 | 비유 |
|:---|:---|:---|
| SDLC | 요구사항부터 폐기까지 소프트웨어 개발 전 과정을 표준화한 단계 체계 | 건축의 표준 공정 순서 |
| 소프트웨어 위기(Software Crisis) | 개발 생산성이 하드웨어·요구사항 복잡도 증가를 따라가지 못해 발생한 납기·품질·비용 문제 | 설계도 없이 짓다가 무너지는 건물 |
| 요구사항 분석(Requirements) | 고객이 원하는 기능·제약을 문서(SRS 등)로 정의하는 단계 — "무엇을 만들 것인가" | 건축주의 요구사항 청취 |
| 설계(Design) | 요구사항을 아키텍처·DB 스키마·UI 등 구현 가능한 형태로 변환 — "어떻게 만들 것인가" | 설계 도면 작성 |
| 구현(Implementation) | 설계를 실제 코드로 작성하는 단계 | 시공 |
| 테스트(Testing) | 단위→통합→시스템→인수 테스트 순으로 결함을 검증하는 단계 | 준공 감리 |
| 유지보수(Maintenance) | 운영 중 발견된 결함 수정, 기능 추가·개선 | 입주 후 하자 보수 |
| Verification(검증) | 각 단계 산출물이 이전 단계의 명세(설계·요구사항)대로 만들어졌는지 확인 — "올바르게 만들었는가" | 도면대로 시공됐는지 확인 |
| Validation(확인) | 완성된 결과물이 실제 고객의 요구를 충족하는지 확인 — "올바른 것을 만들었는가" | 완공된 집이 애초 원하던 집이 맞는지 확인 |
| V-Model | SDLC 각 개발 단계를 대응하는 테스트 단계와 짝지어 검증 흐름을 시각화한 모델 | 개발-테스트 대응표를 V자로 그린 것 |

## 깊이 이해

### 소프트웨어 위기와 SDLC의 등장 배경
1968년 소프트웨어 공학이라는 용어가 처음 논의된 자리에서 공식화된 소프트웨어 위기는, 프로젝트가 예산을 수 배 초과하거나 납기를 넘기고도 품질이 낮은 상태로 인도되는 현상을 가리켰다. 원인은 코딩을 개인의 손기술로 취급해 문서화·검증 절차 없이 진행했다는 데 있었다. SDLC는 이 문제를 "코딩 전에 무엇을 만들지 합의하고 기록한다(요구사항)", "코딩 전에 어떻게 만들지 설계하고 기록한다(설계)", "코딩 후 명세대로 됐는지 검증한다(테스트)"는 단계별 게이트로 구조화한 것이다.

### 5단계가 실제로 하는 일과 순서가 중요한 이유
요구사항 분석 단계에서 결함이 발생하면(예: 고객이 원하는 기능을 잘못 파악) 그 결함은 설계·구현·테스트를 모두 거친 뒤에야 발견되는 경우가 많다. 소프트웨어 공학에서 널리 인용되는 경험칙에 따르면, 요구사항 단계에서 잡을 결함을 유지보수 단계에서 잡으면 수정 비용이 수십~수백 배로 커진다 — 앞 단계에서 결함을 조기에 잡을수록 이후 단계의 재작업을 막을 수 있다는 것이 단계를 나누고 각 단계마다 산출물 검토(리뷰)를 강제하는 근거다.

### Verification과 Validation을 V-Model로 구분하기
V-Model은 왼쪽 내림차순(요구사항→시스템 설계→상세 설계→구현)과 오른쪽 오름차순(단위 테스트→통합 테스트→시스템 테스트→인수 테스트)을 짝짓는다. 상세 설계는 단위 테스트와 짝지어 "설계서대로 코드가 짜였는가(Verification)"를 확인하고, 요구사항 분석은 인수 테스트와 짝지어 "고객이 원했던 것이 맞는가(Validation)"를 확인한다. 이 매핑의 핵심은 테스트 시나리오를 코딩이 끝난 뒤가 아니라 대응하는 개발 단계와 동시에 미리 작성해 두는 것이다 — 예를 들어 요구사항 분석 단계에서 이미 인수 테스트 시나리오 초안을 함께 작성한다.

### SDLC와 개발 방법론의 관계 — 왜 같은 개념이 아닌가
SDLC는 "어떤 단계를 거칠 것인가"를 정의하는 개념적 골격이고, 폭포수(Waterfall)·애자일(Agile)·나선형(Spiral) 모델은 "이 단계들을 몇 번, 얼마나 빠르게 반복할 것인가"를 정하는 구체적 방법론이다. 폭포수는 5단계를 처음부터 끝까지 1회만 순서대로 진행하며 각 단계 종료 시 산출물에 승인(베이스라인)을 받는다. 애자일(스크럼 기준)은 같은 5단계(요구사항-설계-구현-테스트)를 2~4주 스프린트 단위로 압축해 여러 번 반복하며, 매 스프린트 종료 시 동작하는 증분(Increment)을 고객에게 검토받는다. 즉 폭포수와 애자일은 SDLC 자체가 다른 것이 아니라, SDLC를 실행하는 반복 주기와 속도가 다른 것이다.

### 요구사항 변경이 프로젝트를 붕괴시키는 구체 경로
설계와 구현이 끝난 뒤 요구사항이 바뀌면(Scope Creep), 이미 확정된 설계·코드·테스트 케이스를 모두 되짚어 수정해야 한다. 예를 들어 회원 정보 항목 하나가 추가되면 DB 스키마, API 명세, 화면, 관련 테스트 케이스가 연쇄적으로 바뀐다. 폭포수 모델은 이런 변경을 변경 통제 위원회(CCB)를 통한 공식 절차로 억제하려 하고, 애자일 모델은 애초에 변경을 상수로 받아들여 매 스프린트마다 우선순위를 다시 정하는 방식으로 대응한다.

## 연결 개념
- 폭포수 모델(Waterfall) — SDLC 5단계를 순차적으로 1회 수행하는 가장 고전적인 방법론.
- 애자일(Agile)/스크럼 — SDLC를 짧은 반복 주기(스프린트)로 압축해 여러 번 도는 현대적 방법론.
- DevOps/CI·CD — 구현과 테스트 단계를 자동화된 파이프라인으로 연결해, 유지보수(운영) 단계와 개발 단계의 경계를 허무는 확장.

# 📝 【답안용】 시험 답안 템플릿

> 목적: 시험장에서 25분에 그대로 쓰는 답안 양식. 작성방식(추상표현 금지·수치·도식·문제유형 전환)을 엄격히 지킨다.
> 핵심: 이 시험은 정보를 많이 나열하는 시험이 아니라, 문제 신호어에서 출제자 의도를 읽고 핵심 논점을 선별해 쓰는 시험이다.

## 핵심 인사이트 (3줄 요약)

> 1. **본질**: 소프트웨어의 타당성 검토부터 폐기까지 전 과정에 공학적(Engineering) 원리를 적용하여, 고품질의 산출물을 예산과 기한 내에 인도하기 위한 표준화된 공정(Process) 뼈대다.
> 2. **가치**: 프로젝트의 가시성(Visibility)을 확보하여 각 마일스톤(Milestone)별 통제와 리스크 관리를 가능케 하고, 주먹구구식 코딩이 낳는 유지보수 비용의 폭발적 증가(소프트웨어 위기)를 방어한다.
> 3. **판단 포인트**: 요구사항-설계-구현-테스트-유지보수의 정적 5단계를 나열하는 데 그치지 않고, 이 파이프라인을 다루는 철학적 관점(Waterfall vs Agile vs DevOps)으로의 진화 흐름을 반드시 짚어야 한다.

## 출제 의도 및 답안 포인트

| 출제 의도 | 반드시 짚을 핵심 | 감점 회피 포인트 |
|:---|:---|:---|
| 소프트웨어 공학의 공정 통제 및 산출물 관리 역량 | 각 단계별 명확한 목적(What vs How)과 산출물 맵핑 | SDLC와 폭포수 모델을 완전히 동일한 개념으로 혼용하여 서술하는 기본기 오류 |
| V-Model(테스트 매핑) 등 품질 보증(QA) 연계 | 요구사항->인수테스트, 설계->통합테스트 교차 검증 | 단순히 5단계를 암기해 적고, 각 단계 간의 피드백 루프(Verification)를 누락 |
| 현대 IT 환경에 맞춘 SDLC의 패러다임 진화 방향 | 정적(Waterfall) -> 반복(Agile) -> 운영 융합(DevOps) | 최신 트렌드를 무시하고 폭포수 5단계만 찬양하는 올드한 결론 |

> 요약: 집을 지을 때 도면(설계) 없이 벽돌(코딩)부터 쌓는 미친 짓을 막기 위해, 인류가 도입한 '강제 휴식 및 점검 구간(Phase Gate)'들의 집합이다.

## Ⅰ. 개요 및 필요성

- 정의: 소프트웨어 위기(Software Crisis)를 극복하기 위해 소프트웨어의 탄생(요구사항)부터 죽음(폐기)까지의 전 과정을 추적/통제/관리할 수 있도록 세분화한 공정(Phase) 체계
- 배경: 비즈니스 요구사항의 복잡도가 극증하고 프로젝트 규모가 커짐에 따라, 산출물 없는 주먹구구식(Build and Fix) 개발로 인한 납기 지연 및 예산 초과(Overrun) 파국 발생
- 필요성: 각 공정별 명확한 진입/탈출 조건(Entry/Exit Criteria)과 산출물(Artifact) 베이스라인을 통제하여 프로젝트 가시성을 확보하고, 추적성(Traceability)을 통한 품질 보증을 위함

## Ⅱ. SDLC 핵심 5단계 파이프라인 및 산출물 매핑

```text
[ SDLC 기본 뼈대 아키텍처 (Baseline 통제) ]
(What)   [ 1. 요구사항 분석 ] ---> 요구사항 정의서, SRS (고객 서명 완료 🔒 베이스라인)
                | 
(How)    [ 2. 아키텍처 설계 ] ---> 시스템 구조도, DB ERD, 화면 설계서
                | 
(Do)     [ 3. 구현 (코딩)   ] ---> 소스 코드 (형상 관리 대상)
                | 
(Verify) [ 4. 테스팅 (QA)   ] ---> 결함 보고서, 테스트 시나리오/결과서
                | 
(Oper)   [ 5. 유지보수 및 폐기 ] ---> 릴리즈 노트, 운영 매뉴얼, 패치 내역
```

| 개발 공정 단계 | 수행 주체 및 엔지니어링 롤(Role) | 치명적 맹점 및 리스크 요인 |
|:---|:---|:---|
| **1. 요구사항 분석** | 비즈니스 분석가(BA), 기획자 | 고객 본인도 자기가 뭘 원하는지 정확히 모름. 여기서 1% 틀어지면 구현 단계 복구 비용 100배 폭발 (Snowball Effect) |
| **2. 설계** | 소프트웨어 아키텍트, DBA | 비즈니스 요구를 벗어난 과도한 기술적 오버엔지니어링(Over-engineering) 또는 추상화 실패 |
| **3. 구현** | 백엔드/프론트엔드 개발자 | 코딩 컨벤션(표준) 위반 및 스파게티 코드 양산 |
| **4. 테스트** | QA 엔지니어, 테스터 | 개발자가 본인 코드를 직접 테스트하는 '확증 편향' 맹점 |

> 요약: 위 5단계를 폭포수(Waterfall)처럼 한 큐에 쭉 내려가며 도장을 찍을지, 애자일(Agile)처럼 이 5단계를 2주 단위로 쪼개서 수십 번 빙글빙글 돌릴지가 프로젝트의 성패를 가른다.

## Ⅲ. 품질 보증(QA)을 위한 역방향 검증: V-Model (V-모델)

SDLC는 코딩으로 흘러내리기만 해선 안 된다. 각 개발 단계는 상응하는 테스트 단계와 완벽한 거울 쌍(Mirror)을 이뤄야 한다.

```text
[ V-Model 추적성 도식 ]
(요구사항 분석) -----------------------------------> (인수 테스트 : 고객이 O.K. 하는가?)
    \                                                   /
     (시스템 설계) -----------------------------> (시스템 테스트 : 전체 성능/보안이 맞는가?)
         \                                           /
          (상세 설계) ----------------------> (통합 테스트 : 모듈끼리 통신이 되는가?)
              \                                   /
               (코딩/구현) ------------> (단위 테스트 : 함수 1개가 잘 도는가?)
```

| 교차 검증(Verification) 포인트 | 아키텍처적 가치 및 테스트 커버리지 |
|:---|:---|
| **요구사항 <-> 인수(Acceptance)** | 시스템이 "고객의 원래 비즈니스 목적(What)"을 달성했는지 확인 (Validation) |
| **상세설계 <-> 단위(Unit)** | 시스템이 "설계서대로 정확하게(How)" 코딩되었는지 소스코드 뎁스에서 확인 (Verification, TDD/JUnit) |

> 요약: V-모델의 핵심은 "코딩 다 해놓고 그때 가서 부랴부랴 테스트 계획 세우지 말고, 요구사항 분석할 때 인수 테스트 시나리오도 같이 짜라"는 선제적 방어 철학이다.

## Ⅳ. 극복해야 할 공정 리스크 및 현대적 튜닝 기법

| 리스크 요인 | 발생 시나리오 및 프로젝트 붕괴 원인 | 아키텍처 대응 방안 (실무 공학 기법) |
|:---|:---|:---|
| **Big Bang 통합 파국** | 6개월 동안 각자 짠 코드(구현)를 마지막 테스트 단계에서 한 번에 뭉쳤더니(Big Bang), 서로의 모듈이 충돌해 에러 1만 개가 터지며 릴리즈 무한 연기 | **CI/CD (지속적 통합/배포)**: 하루에 수십 번씩 코드를 푸시(Push)할 때마다 젠킨스(Jenkins)가 자동으로 빌드하고 단위/통합 테스트를 돌려 핏(Fit) 어긋남을 1초 만에 감지 |
| 요구사항 변경 지옥 (Scope Creep) | 설계와 코딩이 다 끝났는데 고객이 갑자기 "화면 엎어주세요" 시전. 재작업 비용이 수직 상승하여 개발팀 사기 저하 및 예산 탕진 | 변경 통제 위원회(CCB)를 통한 베이스라인(Baseline) 강제 통제, 혹은 차라리 변경을 수용하는 **애자일(Scrum)** 방법론으로의 패러다임 시프트 |

> 요약: 소프트웨어는 건축물(건물)이 아니다. 건물을 짓다가 화장실을 안방으로 옮길 순 없지만, 소프트웨어는 클릭 한 번으로 고쳐지길 기대받는다. SDLC는 이 태생적 유연성을 방어하는 최후의 바리케이드다.

## Ⅴ. 실무 적용 방안 및 결론

**적용 방안 3개:**
1. [Agile(Scrum) 기반 2주 스프린트 SDLC 압축 적용] 스타트업 B2C 앱 개발 시, 거대한 Waterfall SDLC를 폐기하고 2주짜리 스프린트 안에 요구사항-설계-구현-테스트 전 주기를 압축하여 포함시킴으로써, 매 2주마다 고객(PO)이 터치 가능한 작동 소프트웨어(MVP) 인크리먼트 배포
2. [DevSecOps (보안 SDLC) 파이프라인 내재화] 금융/핀테크 서비스 구축 시, 다 만들어 놓고 마지막 테스트 단계에서 모의 해킹을 하는 레거시(사후 약방문)를 폐기하고, 구현(코딩) 단계 즉시 SonarQube 정적 분석(SAST)과 CI/CD 종속성(CVE) 검사를 강제하는 Shift-Left 보안 전략 이식
3. [산출물 테일러링(Tailoring) 최적화] 소규모 SI 프로젝트 수행 시, 무거운 SDLC 프로세스가 요구하는 40종의 산출물 작성에 개발 리소스가 매몰되는 것을 방지하기 위해, 발주처와 합의하여 요구사항 정의서, 화면 설계서, ERD, API 명세서 등 핵심 산출물 10종으로 과감히 테일러링(재단) 수행

**결론:**
- 기술사 판단: SDLC는 소프트웨어 공학의 '법전'이다. 그러나 법이 시대를 따라가지 못하면 족쇄가 된다. 요구사항이 고정된 우주선이나 국방 시스템에서는 폭포수(Waterfall)의 철저한 베이스라인 통제가 진리지만, 비즈니스가 요동치는 모바일/웹 생태계에서는 빠르고 반복적인 애자일(Agile) 사이클로의 전환이 생존 필수 조건이다.
- 향후 방향: 현대 소프트웨어 개발은 Development(개발)와 Operations(운영)의 경계가 무너진 DevOps 시대를 지나, 인공지능(LLM)이 요구사항 분석부터 코드 생성(Copilot) 및 테스트 케이스 도출까지 SDLC 전 구간을 자동화하는 AIOps 파이프라인으로 진화하고 있다.
