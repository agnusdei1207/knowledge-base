# 📖 【암기용】 개념 완전 이해

> 목적: 이 개념을 처음 보는 사람도 완벽히 이해하게 만든다. 시험 답안 양식이 아니라, 이해를 위한 친절한 설명이다.

## 한눈에
- **개요**: **ISO/IEC 25010**은 추상적인 **소프트웨어 품질**을 8개의 **품질 특성(Quality Characteristics)**으로 쪼개, 아키텍처 설계 단계에서 "어떤 품질을 얼마나 확보하고 무엇을 희생할지" 저울질할 수 있게 만든 **국제 품질 모델**이다.
- **왜 필요한가**: 품질 속성은 서로 공짜로 얻어지지 않는다. 암호화를 강하게 걸면 응답 속도가 느려지고, 기능을 계속 추가하면 유지보수성이 떨어진다. 아키텍트가 이 상충 관계를 근거 있게 조율하려면, 먼저 품질을 측정 가능한 8개 축으로 나눠야 한다.
- **핵심 직관**: 자동차를 "좋다/나쁘다"로 뭉뚱그리지 않고 연비·안전성·정비성·승차감을 따로 채점하듯, 소프트웨어도 8개 축으로 나눠 채점하고 그중 무엇에 가중치를 둘지 결정하는 것이다.

## 핵심 용어 정리 (내부에 등장하는 것들)

| 용어 | 의미 | 비유 |
|:---|:---|:---|
| 품질 모델 (Quality Model) | 품질을 측정 가능한 하위 특성으로 분해한 체계 — ISO 25010이 속한 상위 개념 | 성적표를 과목별로 나눠 채점하는 방식 |
| SQuaRE | ISO/IEC 25000번대 품질 표준군의 총칭(Software product Quality Requirements and Evaluation) — 25010은 그중 품질 모델 파트 | 품질 관련 법 조항을 모아놓은 법전 |
| 제품 품질 (Product Quality) | 시스템 자체가 내재적으로 갖춘 8개 특성 — 엔지니어 관점의 품질 | 자동차 부품 자체의 스펙 |
| 사용 품질 (Quality in Use) | 실제 사용 맥락에서 사용자가 목표를 달성했는지 보는 5개 특성 | 그 자동차를 몰아본 운전자의 만족도 |
| 기능 적합성 (Functional Suitability) | 명세된 기능을 완전하고 정확하게 수행하는 정도 | 주문서대로 다 만들었는가 |
| 성능 효율성 (Performance Efficiency) | 자원 사용 대비 응답 속도·처리량 | 기름을 얼마나 먹고 얼마나 빨리 가는가 |
| 호환성 (Compatibility) | 다른 시스템과 정보를 교환하고 공존하는 능력 — 9126 대비 신규 | 다른 브랜드 부품과도 잘 맞물리는가 |
| 사용성 (Usability) | 사용자가 쉽게 배우고 조작할 수 있는 정도 | 설명서 없이도 운전할 수 있는가 |
| 신뢰성 (Reliability) | 정해진 조건에서 기능을 지속 수행하는 정도 | 장거리를 가도 퍼지지 않는가 |
| 보안성 (Security) | 정보와 데이터를 권한 있는 접근으로만 보호하는 정도 — 9126 대비 신규 | 도난 방지 잠금장치가 튼튼한가 |
| 유지보수성 (Maintainability) | 결함 수정·기능 변경이 쉬운 정도 | 부품 교체가 쉬운가 |
| 이식성 (Portability) | 다른 환경으로 옮겨도 잘 동작하는 정도 | 다른 도로·기후에서도 잘 달리는가 |
| ATAM (Architecture Trade-off Analysis Method) | 품질 속성 간 상충 관계를 시나리오로 분석해 아키텍처 결정을 내리는 기법 | 예산 안에서 옵션 8개 중 무엇을 넣을지 정하는 회의 |

## 깊이 이해

### 9126에서 25010으로 — 무엇이 왜 늘었나
과거 표준 ISO/IEC 9126은 기능성·신뢰성·사용성·효율성·유지보수성·이식성 6개 특성으로 구성됐다. 이 시절에는 시스템 대부분이 한 회사 안에서 닫힌 채로 돌아갔기 때문에 외부 시스템과의 연동이나 외부 공격 노출이 크지 않았다. 그런데 클라우드·마이크로서비스(MSA) 구조가 퍼지면서 시스템은 다른 서비스의 API를 수시로 호출해야 했고(→ **호환성** 신설), 동시에 외부에 열린 API 표면이 늘며 해킹 노출도 커졌다(→ **보안성** 신설). 이 두 특성이 추가되며 6개가 8개로 늘어난 것이 9126 대비 25010의 핵심 변화다.

### 투트랙 구조 — 제품 품질(8개)과 사용 품질(5개)는 왜 나뉘는가
25010은 품질을 두 층으로 나눈다. **제품 품질**(기능 적합성, 성능 효율성, 호환성, 사용성, 신뢰성, 보안성, 유지보수성, 이식성)은 시스템 자체를 뜯어봤을 때의 스펙이고, **사용 품질**(효과성, 효율성, 만족도, 위험 회피, 상황 포괄성)은 실제 사용자가 특정 맥락에서 그 시스템으로 목표를 달성했는지를 본다. 예를 들어 앱의 응답 속도(성능 효율성, 제품 품질)가 아무리 빨라도, 출퇴근 지하철에서 네트워크가 끊겨 결제를 못 마쳤다면(상황 포괄성 실패, 사용 품질) 사용자는 품질이 나쁘다고 느낀다. 두 층을 분리해야 "시스템은 문제없는데 왜 고객 불만이 나오는가"를 구분해서 진단할 수 있다.

### 트레이드오프를 숫자로 보기
보안성을 높이려고 모든 API 트래픽에 AES-256 암호화와 TLS 핸드셰이크를 강제하면, 암호화·복호화 연산이 추가되어 평균 응답 시간이 늘어난다. 예를 들어 암호화 없이 80ms이던 API 응답이 암호화 적용 후 150ms로 늘었다면, 보안성을 얻은 대신 성능 효율성의 응답 시간 목표(가령 p95 200ms 이하)에 여유가 줄어든 것이다. 8개 특성을 전부 만점으로 만들 수 없는 이유가 이것이다 — 하나를 강화하면 다른 하나의 예산(시간·자원)을 갉아먹는다.

### ATAM으로 우선순위를 정하는 절차
1. 이해관계자들이 "품질 속성 시나리오"를 구체적으로 적는다. 예: "결제 트래픽이 평소의 3배로 몰려도 응답 시간이 500ms를 넘지 않아야 한다"(성능 시나리오), "개인정보 테이블에 대한 모든 접근은 감사 로그로 남아야 한다"(보안 시나리오).
2. 각 시나리오가 다른 품질 속성과 충돌하는 지점(Trade-off point)을 찾는다. 위 두 시나리오는 로깅 연산이 늘수록 성능이 떨어지는 지점에서 충돌한다.
3. 비즈니스 우선순위에 따라 어느 쪽에 더 많은 예산을 배정할지 결정한다. 은행 앱이라면 신뢰성·보안성을 1순위로, 스트리밍 앱이라면 가용성·성능을 1순위로 두는 식이다.

### 흔한 오해
"8개 특성을 다 100점 맞아야 좋은 품질"이라는 생각은 틀렸다. 오히려 아키텍트의 역할은 어떤 특성을 의도적으로 낮게 잡을지 근거를 대는 것이다. 넷플릭스가 결제 시스템 장애 중에도 영상 재생 서비스는 계속 띄우는 것은, 신뢰성(모든 기능 완전 동작)보다 가용성(핵심 기능 지속 제공)에 가중치를 둔 의도적 트레이드오프다.

## 연결 개념
- ISO/IEC 9126 — 25010의 전신, 6개 특성에서 호환성·보안성이 추가되며 확장됨
- ATAM — 품질 속성 간 상충을 조율해 아키텍처 결정을 내리는 분석 기법
- 비기능 요구사항(NFR) — 25010의 8개 특성은 NFR을 표준화된 언어로 표현하는 틀

# 📝 【답안용】 시험 답안 템플릿

> 목적: 시험장에서 25분에 그대로 쓰는 답안 양식. 작성방식(추상표현 금지·수치·도식·문제유형 전환)을 엄격히 지킨다.
> 핵심: 이 시험은 정보를 많이 나열하는 시험이 아니라, 문제 신호어에서 출제자 의도를 읽고 핵심 논점을 선별해 쓰는 시험이다.

## 핵심 인사이트 (3줄 요약)

> 1. **본질**: 기존 ISO 9126을 대체/확장하여 소프트웨어의 생명주기 전반에 걸친 품질 요구사항과 평가(SQuaRE)를 규정한 국제 표준 프레임워크다.
> 2. **가치**: 추상적인 '품질(Quality)'을 정량적으로 측정 가능한 하부 특성들로 분해(Decomposition)하여, 이해관계자(개발자, 테스터, 고객) 간의 명확한 품질 계약(SLA) 및 트레이드오프(Trade-off) 협의 기준을 제공한다.
> 3. **판단 포인트**: 기존 모델(9126) 대비 새롭게 격상된 핵심 속성인 **보안성(Security)과 호환성(Compatibility)**을 클라우드/MSA 트렌드와 반드시 결부시켜 서술하고, 제품 품질(8개)과 사용 품질(5개)의 이원화 구조를 도식화해야 한다.

## 출제 의도 및 답안 포인트

| 출제 의도 | 반드시 짚을 핵심 | 감점 회피 포인트 |
|:---|:---|:---|
| 기존 ISO 9126 대비 25010 모델의 진화(변경) 포인트 식별 | **보안성(Security), 호환성(Compatibility) 추가 신설** | 9126 시절의 '기신사효유이(6개)'를 25010의 8개로 착각하여 쓰는 뼈아픈 실수 |
| 투트랙(Two-track) 품질 평가 프레임워크 체계 | **제품 품질 (8대 특성)** vs **사용 품질 (5대 특성)** 분리 | 사용 품질(Quality in Use)을 제품 특성의 하위 요소로 혼동 배치하는 오류 |
| 아키텍처 설계 단계에서의 비기능 요구사항 융합 | 품질 속성(Quality Attributes) 간의 트레이드오프 (예: 보안 강화 시 성능 저하) | 단순히 8개 항목의 뜻만 달달 외워 적고 실무적 엔지니어링 활용(ATAM 등) 누락 |

> 요약: "품질 좋은 코드를 짜라"는 말은 개소리다. "응답 속도 0.5초 이하(성능), SonarQube 결합도 지수 10점 이하(유지보수성), AES-256 암호화 통과(보안성)를 달성해라." 이것이 ISO 25010이 말하는 진정한 공학적(Engineering) 품질 기준이다.

## Ⅰ. 개요 및 필요성

- 정의: 소프트웨어 제품의 품질 요구사항 정의 및 평가(SQuaRE: Software product Quality Requirements and Evaluation)를 위해 ISO/IEC에서 제정한 국제 표준 품질 메타 모델
- 배경: 기존 ISO/IEC 9126(6대 특성) 모델은 클라우드, 마이크로서비스(MSA), 악의적 해킹 공격이 폭증하는 현대 IT 환경의 복합적 비기능 요구사항을 온전히 커버하기에 한계 노출
- 필요성: 시스템 내부의 구조적 엔지니어링 품질(제품 품질)과 고객이 체감하는 비즈니스 만족도(사용 품질)를 분리 측정하고, 현대 아키텍처의 필수 요건인 **호환성**과 **보안성**을 1급 객체(First-class attribute)로 격상하여 철저히 통제하기 위함

## Ⅱ. ISO/IEC 25010 투트랙(Two-Track) 품질 아키텍처 도식

개발자가 보는 품질(코드)과 사용자가 보는 품질(경험)은 태생부터 다르다.

```text
[ SQuaRE (ISO/IEC 25000 시리즈) 25010 품질 모델 이원화 체계 ]

(1. 엔지니어/시스템 관점)                           (2. 최종 사용자/비즈니스 관점)
[ 제품 품질 (Product Quality) ]                    [ 사용 품질 (Quality in Use) ]
: 시스템 덩어리 자체가 내재적으로 우수한가?          : 특정 맥락(Context)에서 유저의 목표를 달성했나?

 1. ⚙️ 기능 적합성 (Functional Suitability)
 2. ⚡ 성능 효율성 (Performance Efficiency)          1. 🎯 효과성 (Effectiveness)
 3. 🧩 호환성 (Compatibility) ---------> (신규)      2. ⏱️ 효율성 (Efficiency) 
 4. 🖱️ 사용성 (Usability)                           3. 😃 만족도 (Satisfaction)
 5. 🛡️ 신뢰성 (Reliability)                         4. 🛑 위험 회피 (Freedom from Risk) --> (신규)
 6. 🔒 보안성 (Security) --------------> (신규)      5. 🌐 상황 포괄성 (Context Coverage) -> (신규)
 7. 🛠️ 유지보수성 (Maintainability)
 8. 📦 이식성 (Portability)
```

| 제품 품질 (8대 속성) | 핵심 엔지니어링 메커니즘 (세부 특성) | 측정 및 통제 기법 (QA/아키텍처) |
|:---|:---|:---|
| **기능 적합성** | 완전성, 정확성, 적절성 | 기획 명세서 기반 BDD 인수 테스트 및 블랙박스 테스트 커버리지 100% 검증 |
| **성능 효율성** | 시간 동작(응답 속도), 자원 활용(CPU/RAM 낭비 최소화) | JMeter / nGrinder 기반 부하(Load) 테스트 및 APM(Datadog) 병목 구간 병렬 처리 튜닝 |
| **호환성 🌟(신규)** | 공존성(충돌 없음), 상호운용성(데이터 교환) | 외부 Open API 통신 페이로드 포맷(JSON) 검증 및 구형 OS/DB 하위 호환(Backward) 테스트 |
| **사용성** | 타당성 인식, 학습성, 조작성, 오류 방지 통제 | A/B 테스트 및 사용자 모니터링(UX/UI), 접근성(웹 표준) 검수 가이드 준수 |
| **신뢰성** | 성숙성, 가용성, 결함 허용성(Fault Tolerance) | 서킷 브레이커(Circuit Breaker) 차단 방어 및 Chaos Monkey 기반 복구(MTTR) 테스트 |
| **보안성 🌟(신규)** | 기밀성, 무결성, 부인 방지, 책임 추적성(Audit) | SAST/DAST/SCA 스캐닝 및 SSL/TLS 암호화, OAuth 2.0 기반 권한(RBAC) 우회 타격 |
| **유지보수성** | 모듈성, 재사용성, 분석성, 수정성(Refactoring) | SonarQube 정적 분석 기반 `순환 복잡도 10 미만`, `결합도 최소화`, TDD 테스트 커버리지 80% 락인 |
| **이식성** | 적응성, 설치성, 대체성 | Docker 컨테이너 및 K8s 표준 매니페스트(YAML) 기반 OS/환경 종속성 제로화(Zero) 달성 |

> 요약: 신규 추가된 **보안성과 호환성**은 마이크로서비스(MSA)를 정조준한다. MSA는 남의 서버와 쉴 새 없이 API를 주고받아야 하므로 상호운용(호환)이 안 되면 망하고, 수백 개의 통신 포트가 열려있으므로 방어(보안)가 안 되면 뚫린다.

## Ⅲ. 극복해야 할 시스템적 리스크 (품질 속성 간 상충 및 파산)

8개를 다 100점 맞으려다간 개발 기간이 10년 걸려 회사가 파산한다. (Trade-off의 딜레마).

| 리스크 요인 | 발생 시나리오 및 시스템 붕괴 원인 (안티패턴) | 아키텍처 대응 방안 (실무 튜닝) |
|:---|:---|:---|
| **품질 속성 간 상충(Trade-off) 충돌** | '보안성(Security)'을 극대화하려고 모든 데이터 트래픽에 256bit 암호화를 걸었더니, CPU 연산이 폭발하여 응답 속도가 3초로 느려져 '성능 효율성(Performance)'이 붕괴함 | **ATAM (아키텍처 트레이드오프 분석법)**: 8개 속성에 가중치(우선순위) 부여. 비디오 스트리밍 앱이라면 보안성을 3순위로 내리고 **성능(응답 속도)을 1순위로 강제하여 비대칭적 아키텍처 리소스 투입(비용 최적화)** |
| **과도한 유지보수성 집착(오버엔지니어링)** | '유지보수성(모듈성)'을 100점 맞겠다고, 단순한 CRUD 앱에 디자인 패턴 10개를 바르고 인터페이스를 3단계로 쪼개어(YAGNI 위반), 배포 지연 및 성능 효율성 붕괴 야기 | **적시 출시(Time-to-market) 기반 기술 부채 허용**: 초기 스타트업 단계에서는 유지보수성(Refactoring)을 의도적 기술 부채로 남겨두고, '기능 적합성(출시)'에 몰빵하여 생존 후 이자를 상환하는 린(Lean) 스탠스 취득 |

> 요약: 아키텍트의 실력은 "어떤 걸 포기할지" 결정하는 데서 나온다. 넷플릭스는 '신뢰성(결제 완벽)'보다 '가용성(영화 재생 우선)'을 택해 결제 DB가 뻗어도 영화는 나오게 설계했다. 이것이 비즈니스 요구에 맞춘 ISO 25010 커스터마이징이다.

## Ⅳ. 현대 애자일(DevOps) 파이프라인과의 정량적 융합망

추상적인 8대 품질 기준을 파이프라인(기계)의 숫자로 강제 맵핑하여 퀄리티 게이트를 닫아버린다.

| ISO 25010 속성 | DevSecOps 파이프라인 자동화 융합(Mapping) 메커니즘 | 통제(Blocking) 임계치 |
|:---|:---|:---|
| **기능 적합성** | BDD 프레임워크(Cucumber) 기반 비즈니스 기능(인수) 테스트 CI 결합 | 인수 TC 100% `Pass` 필수 |
| **성능 효율성** | 배포 파이프라인 상에 nGrinder(성능 테스트) 봇을 태워 응답 지연 측정 | API p95 응답 `200ms 이하` |
| **유지보수성** | SonarQube(SAST) 정적 분석 봇을 통한 아키텍처 기술 부채 추적 | 라인 커버리지 `80% 이상` |
| **보안성** | Dependency-Check(SCA) 컨테이너 취약점 검증 OPA 폴리시 차단 | Critical CVE 검출 시 `0건` |

> 요약: ISO 25010은 감리(QA)팀 문서에 갇혀 있으면 쓸모없는 휴지조각이다. 8대 기준을 젠킨스(Jenkins) 파이프라인의 `if`문(Quality Gate)으로 코딩해서 넣어야만 진짜 살아 숨 쉬는 소프트웨어 품질 표준이 된다.

## Ⅴ. 실무 적용 방안 및 결론

**적용 방안 3개:**
1. [마이크로서비스(MSA) 특화 호환성/이식성 CI 자동 검증망 구축] 독립적인 배포가 일어나는 MSA 환경에서 타 서비스 간 통신 장애(호환성 결여)를 막기 위해, Pact 프레임워크 기반의 `소비자 주도 계약 테스트(CDC)`를 CI 파이프라인에 삽입. 남의 API 스펙이 변하는 순간 빌드를 차단하여 '호환성(상호운용성)' 무결성 강제 보장
2. [SRE(사이트 신뢰성 엔지니어링) 기반 신뢰성(Reliability) 정량 통제] 구글 SRE 프레임워크를 도입하여, 신뢰성의 하위 특성인 가용성(Availability)을 `99.99%(한 달 4분 다운타임 허용)` SLI/SLO 지표로 확정. 에러 버짓(Error Budget)이 소진되면 신기능 배포를 올스톱(Freeze)시키고 '유지보수성(리팩터링)'에만 리소스를 강제 투입하는 권력 통제 기전 확립
3. [사용 품질(Quality in Use) 피드백 텔레메트리(Telemetry) 최적화] 배포 후(Post-release) 실제 유저 폰에 Firebase Analytics 및 Crashlytics를 부착. 고객이 특정 목표(결제 완료)를 1분 내에 도달하는지(효율성), 앱 크래시 없이 만족스럽게 이탈하지 않는지(위험 회피)를 실시간 메트릭으로 수집하여 다음 스프린트 백로그(Plan) 최우선 순위로 피드백 루프(Loop) 융합

**결론:**
- 기술사 판단: ISO/IEC 25010은 추상화된 소프트웨어 품질을 엔지니어링 렌즈(제품 품질)와 비즈니스 렌즈(사용 품질)로 정밀하게 분해한 인류 소프트웨어 공학의 결정체다. 특히 보안성(Security)과 호환성(Compatibility)의 독립은 현대 클라우드/오픈 API 생태계의 복잡성을 정확히 관통하는 진화다. 시스템 구축 시 이 8대 특성은 단순 점검표(Checklist)를 넘어, 한정된 자원 속에서 아키텍처의 트레이드오프(Trade-off) 우선순위를 결정하는 나침반이자 CI/CD 퀄리티 게이트의 절대 임계치로 활용되어야 한다.
- 향후 방향: 최근 생성형 AI(LLM)가 양산하는 코드와 인공지능 기반 소프트웨어(AI-Infused System)가 폭증함에 따라, 기존의 결정론적(Deterministic) 25010 모델로는 AI의 '환각(Hallucination)'이나 '데이터 편향성' 같은 새로운 리스크를 통제하기 어려워, AI 시스템 품질 전용 확장 표준인 **ISO/IEC 25059** 기반의 차세대 품질 패러다임으로 진화가 격변하고 있다.
