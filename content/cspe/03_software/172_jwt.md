## Ⅰ. 개요
- **정의**: JSON 형식으로 클레임을 표현하고 서명하여 전달하는 자기 완결형 토큰 표준
- **배경/필요성**: 서버 측 세션 저장 없이 토큰 자체에 인증 정보를 포함해야 무상태 확장이 가능함
- **비유**: 위조 방지 도장이 찍힌 신분증처럼, 토큰 자체로 소지자 정보를 검증할 수 있음

| 출제 의도 | 반드시 짚을 핵심 | 감점 회피 포인트 |
|:---|:---|:---|
| 토큰 구조와 무상태 인증 이해 | Header.Payload.Signature 3파트 구조 | 암호화(JWE)와 서명(JWS) 구분 필요 |

> 요약: 서버 세션 없이 토큰 자체에 클레임과 서명을 담아 무상태 인증을 구현하는 표준임

## Ⅱ. 구성요소
```text
+----------+   +----------+   +-----------+
| Header   |-->| Payload  |-->| Signature |
| (alg,typ)|   | (claims) |   | (verify)  |
+----------+   +----------+   +-----------+
      Base64URL . Base64URL . Base64URL
```

| 구성요소 | 설명 | 비유 |
|:---|:---|:---|
| Header | 서명 알고리즘(`alg`)과 토큰 타입(`typ`) 명시 | 신분증 발급 기관 표시 |
| Payload | `sub`, `exp`, `iat` 등 클레임 데이터 포함 | 신분증 인적사항 |
| Signature | Header+Payload를 비밀키로 서명한 무결성 검증값 | 위조 방지 도장 |
| Registered Claims | `iss`, `exp`, `sub` 등 표준 예약 클레임 | 공통 기재사항 |
| Custom Claims | 애플리케이션별 비즈니스 데이터 | 추가 기재란 |

> 요약: Header·Payload·Signature 3파트를 Base64URL로 인코딩하여 점(`.`)으로 연결한 구조임

## Ⅲ. 절차
```text
Client -> Auth Server : 인증 요청
Auth Server -> Client : JWT 발급 (서명 포함)
Client -> API Server  : JWT를 Authorization 헤더에 첨부
API Server             : Signature 검증 후 Payload 클레임으로 인가 판단
```
- 1단계: 클라이언트가 인증 서버에 자격증명을 제출함
- 2단계: 인증 서버가 클레임을 담은 JWT를 서명하여 발급함
- 3단계: 클라이언트가 API 요청 시 JWT를 `Authorization: Bearer` 헤더에 첨부함
- 4단계: API 서버가 Signature를 검증하고 Payload의 `exp`, 권한 클레임을 확인함

> 요약: 발급-첨부-검증의 흐름으로 서버 세션 조회 없이 인증·인가를 처리함

## Ⅳ. 문제점
- 토큰 즉시 폐기 불가: 서버에 상태가 없어 발급된 JWT를 만료 전 무효화하기 어려움
- Payload 평문 노출: Base64URL은 인코딩일 뿐이므로 민감 정보가 디코딩으로 노출됨
- 토큰 크기 증대: 클레임 추가 시 토큰 크기가 커져 매 요청마다 네트워크 부하가 증가함

> 요약: 즉시 폐기 불가·평문 노출·크기 증대가 주요 한계임

## Ⅴ. 개선방안
1. 단기: 토큰 블랙리스트(Redis 등) 운영으로 즉시 폐기 기능 보완
2. 중기: 민감 데이터는 Payload에서 제외하고 JWE 암호화 적용
3. 장기: 클레임 최소화 설계 및 토큰 분리(ID Token + Access Token) 운영

> 요약: 블랙리스트·JWE 암호화·클레임 최소화로 단계적 보완이 필요함

## Ⅵ. 전망
- 발전 방향: OAuth 2.0·OIDC 표준과 결합하여 마이크로서비스 간 인증 토큰으로 확산 중임
- 기술사적 판단: 무상태 아키텍처 확대에 따라 JWT 활용 범위가 지속 확장됨
- 기술사 제언: 토큰 수명 최소화와 키 로테이션 정책을 병행하는 운영 설계가 필요함
