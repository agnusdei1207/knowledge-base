## 미리 알고가기

- SOLID는 객체지향 설계 품질을 높이기 위한 다섯 가지 원칙 묶음임
- DIP는 상위 정책이 구체 구현이 아니라 추상화에 의존하게 하는 원칙임
- Mockability는 테스트에서 의존 대상을 대역 객체로 교체할 수 있는 정도를 뜻함

## 작성 근거(검토용)

- SOLID는 책임, 확장 방식, 치환 가능성, 의존 방향을 핵심 축으로 선정함
- 구성은 다섯 원칙이 변경 범위와 테스트 대체성에 미치는 영향을 중심으로 제시함
- 실무 판단은 변경 영향 범위, 모듈 결합도, 외부 연동 없는 단위 테스트 비율로 구체화함

## Ⅰ. 개요

- **정의/개념**: SOLID는 객체지향 설계에서 책임·확장·치환·인터페이스·의존 방향을 정하는 다섯 원칙임
- **배경/필요성**: 클래스 책임이 섞이고 구현 의존이 강해지면 변경 범위와 테스트 비용이 커지므로 이를 통제할 설계 기준이 필요함

## Ⅱ. 특징

- 책임 분리와 추상화와 의존성 방향 제어를 함께 다룸
- 재사용 자체보다 변경 용이성과 테스트 가능성에 초점을 둠
- 변경 가능성이 낮은 코드까지 추상화하면 인터페이스와 구현 계층만 늘어날 수 있음
- 설계 원칙이므로 개별 패턴이나 프레임워크보다 상위 기준으로 작동함

## Ⅲ. 종류 및 비교

| 판단 기준 | 원칙 미적용 구조 | SOLID 지향 구조 |
|:---|:---|:---|
| 책임 배치 | 하나의 클래스가 여러 변경 이유를 함께 떠안기 쉬움 | 변경 이유가 다른 책임을 분리해 수정 범위를 줄임 |
| 의존 방향 | 상위 로직이 구체 구현에 직접 묶이기 쉬움 | 추상화에 의존해 구현 교체와 테스트가 쉬워짐 |
| 변경 영향 | 작은 수정도 연쇄 수정으로 번질 가능성이 큼 | 국소 수정으로 끝날 가능성이 높아짐 |
| 테스트 대체 | 구체 구현과 외부 연동을 함께 생성 | 인터페이스 경계에서 외부 구현을 대역 객체로 교체 |

> 요약: SOLID는 책임을 분리하고 추상화에 의존해 변경 범위와 외부 구현 결합을 줄이는 설계 기준임.

## Ⅳ. 구성요소 및 구조

| 구성요소 | 설명 |
|:---|:---|
| 단일 책임 원칙 | 클래스가 하나의 변경 이유만 갖도록 책임을 분리함 |
| 개방·폐쇄 원칙 | 기존 코드를 수정하기보다 확장으로 새 요구를 수용함 |
| 리스코프 치환 원칙 | 하위 타입이 상위 타입의 계약을 지켜 대체 가능하게 함 |
| 인터페이스 분리 원칙 | 사용자가 필요하지 않은 기능에 의존하지 않도록 인터페이스를 나눔 |
| 의존 역전 원칙 | 상위 정책과 하위 구현이 추상화에 의존하도록 경계를 형성함 |

> 요약: 단일 책임으로 변경 이유를 나누고 치환·분리·의존 역전으로 구현 교체 범위를 제한함.

## Ⅵ. 실무 사례

1. 복합 업무 모듈은 변경 이유별로 책임을 분리하고 변경 영향 범위·모듈 결합도를 확인함
2. 외부 연동 모듈은 의존 역전을 적용하고 외부 연동 없는 단위 테스트 비율·회귀 결함률을 확인함

## Ⅶ. 결론

SOLID는 객체지향 코드의 책임과 의존 방향을 정해 변경 범위와 테스트 비용을 줄이는 설계 기준임
