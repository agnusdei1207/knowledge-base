## 미리 알고가기

- SOLID는 객체지향 설계 품질을 높이기 위한 다섯 가지 원칙임
- 단일 책임과 개방 폐쇄와 리스코프 치환과 인터페이스 분리와 의존 역전으로 구성됨
- 원칙 자체보다 변경 용이성과 결합도 개선이 목적임

## Ⅰ. 개요

- **정의/개념**: SOLID 원칙은 객체지향 소프트웨어에서 변경에 강하고 결합이 낮고 테스트가 쉬운 구조를 만들기 위해 제시된 다섯 가지 설계 원칙 집합임
- **배경/필요성**: 요구 변경이 잦은 시스템에서는 클래스 책임이 뒤섞이고 의존성이 강해지면 유지보수 비용이 폭증하므로, 변경 영향 범위를 줄이는 설계 기준이 필요함

## Ⅱ. 특징

- 책임 분리와 추상화와 의존성 방향 제어를 강조함
- 코드 재사용보다 변경 용이성과 테스트 가능성에 초점을 둠
- 원칙을 과도하게 적용하면 추상화만 늘고 복잡도가 증가할 수 있음
- 설계 원칙이므로 패턴이나 프레임워크보다 상위 기준으로 작동함

## Ⅲ. 종류 및 비교

| 판단 기준 | 원칙 미적용 구조 | SOLID 지향 구조 |
|:---|:---|:---|
| 책임 배치 | 하나의 클래스에 기능 집중 | 책임과 인터페이스 분리 |
| 의존 방향 | 구체 구현에 직접 의존 | 추상화 중심 의존 |
| 변경 영향 | 연쇄 수정 가능성 큼 | 국소 변경 가능성 높음 |
| 테스트 용이성 | 목킹과 대체 어려움 | 교체와 테스트 수월 |

## Ⅳ. 구성요소 및 구조

| 구성요소 | 설명 |
|:---|:---|
| Single Responsibility | 클래스와 모듈이 하나의 변경 이유만 갖도록 해 수정 파급을 줄임 |
| Open Closed | 확장은 열고 기존 코드는 닫아 새 요구를 추가할 때 안정성을 높임 |
| Liskov and Interface Segregation | 치환 가능성과 인터페이스 최소화를 통해 사용처별 결합을 낮춤 |
| Dependency Inversion | 상위 정책이 구체 구현이 아닌 추상화에 의존하게 해 테스트와 교체를 쉽게 만듦 |

## Ⅴ. 원리 및 절차 흐름도

```text
+-------------+     +-------------+     +-------------+     +-------------+
| 변경 축 식별    | --> | 책임 분리      | --> | 추상화 설계    | --> | 의존성 검증    |
+-------------+     +-------------+     +-------------+     +-------------+
```

1. **변경 축 식별**: 무엇이 자주 바뀌는지 파악함
2. **책임 분리**: 서로 다른 변경 이유를 모듈 단위로 나눔
3. **추상화 설계**: 교체 가능한 인터페이스와 경계를 만듦
4. **의존성 검증**: 상위 정책이 구체 구현에 묶이지 않는지 확인함

## Ⅵ. 문제점 및 해결 방안

1. 문제: SOLID를 규칙 암기로만 적용하면 작은 시스템에도 과도한 추상화와 인터페이스가 늘어날 수 있음
   - 해결방안: 변경 가능성이 높은 경로에 한정 적용하고 abstraction overhead score와 change impact radius로 검증함
2. 문제: 단일 책임 분리가 부족하면 하나의 클래스 수정이 여러 기능 회귀로 이어질 수 있음
   - 해결방안: 변경 이유 기준 리팩터링을 수행하고 class responsibility count와 defect coupling rate로 검증함
3. 문제: 의존 역전을 하지 않으면 테스트 대역체와 구현 교체가 어려워 배포 속도가 느려질 수 있음
   - 해결방안: 추상화 주입 구조를 적용하고 mockability score와 test execution speed로 검증함

## Ⅶ. 적용 사례

- 핵심 도메인 모듈 리팩터링에서는 SOLID 기준을 적용하고, change impact radius와 defect coupling rate로 결과를 확인함
- 테스트 자동화 강화 프로젝트에서는 의존 역전을 적용하고, mockability score와 test execution speed로 결과를 확인함
- 프레임워크 추상화 설계에서는 과도 추상화를 경계하고, abstraction overhead score와 maintenance lead time로 결과를 확인함

## Ⅷ. 결론

SOLID는 객체지향 미학이 아니라 변경이 자주 일어나는 코드에서 수정 범위와 결합도를 줄이기 위한 실용 설계 기준임.
