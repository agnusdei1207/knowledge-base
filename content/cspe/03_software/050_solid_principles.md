# 📖 【암기용】 개념 완전 이해

> 목적: 이 개념을 처음 보는 사람도 완벽히 이해하게 만든다. 시험 답안 양식이 아니라, 이해를 위한 친절한 설명이다.

## 한눈에
- **개요**: SOLID는 **결합도(Coupling)를 낮추고 응집도(Cohesion)를 높여** 객체지향 설계의 유지보수성과 확장성을 확보하기 위해 로버트 C. 마틴이 2000년대 초 정리한 5가지 설계 원칙(SRP·OCP·LSP·ISP·DIP)이다.
- **왜 필요한가**: 요구사항은 계속 바뀐다. 클래스들이 서로 강하게 얽혀 있으면(강결합) 한 곳을 고칠 때마다 관련 없어 보이는 다른 곳까지 깨진다. SOLID는 "무엇을 바꿔도 다른 부분이 안 깨지게" 클래스 사이의 의존 방향과 책임 경계를 설계하는 규칙이다.
- **핵심 직관**: 5개 중 4개(SRP·LSP·ISP·DIP)는 수단이고, **OCP(개방-폐쇄 원칙)가 목표**다. "기존 코드를 고치지 않고(Closed) 새 기능을 추가(Open)할 수 있는가"가 SOLID를 지켰는지 판별하는 최종 기준이다.

## 핵심 용어 정리 (내부에 등장하는 것들)

| 용어 | 의미 | 비유 |
|:---|:---|:---|
| 결합도 (Coupling) | 한 모듈이 다른 모듈의 내부 구현에 얼마나 의존하는가 | 두 톱니바퀴가 딱 맞물려, 하나를 바꾸면 다른 하나도 다시 깎아야 하는 정도 |
| 응집도 (Cohesion) | 한 모듈 내부 요소들이 하나의 목적에 얼마나 집중되어 있는가 | 한 서랍에 관련 물건만 들어있는 정도 |
| 추상화 (Abstraction) | 구현을 감추고 "무엇을 하는가"만 드러낸 인터페이스 | 리모컨의 버튼(내부 회로는 몰라도 조작 가능) |
| 다형성 (Polymorphism) | 같은 인터페이스 호출이 실제 구현체에 따라 다르게 동작 | 같은 "재생" 버튼이 어떤 기기를 꽂았느냐에 따라 다른 결과를 냄 |
| SRP (단일 책임 원칙) | 클래스가 변경되어야 할 이유는 오직 1개여야 함 | 한 직원에게 한 가지 업무만 맡기기 |
| OCP (개방-폐쇄 원칙) | 확장에는 열려있고 기존 코드 수정에는 닫혀있어야 함 | 콘센트 규격은 고정, 꽂는 가전제품만 바뀜 |
| LSP (리스코프 치환 원칙) | 자식 타입은 부모 타입을 완전히 대체할 수 있어야 함 | 매장 점원이 교체돼도 손님이 차이를 못 느껴야 함 |
| ISP (인터페이스 분리 원칙) | 클라이언트가 쓰지 않는 메서드에 의존하지 않도록 인터페이스를 잘게 쪼갬 | 만능 리모컨보다 필요한 버튼만 있는 리모컨 |
| DIP (의존성 역전 원칙) | 상위 모듈과 하위 모듈이 모두 추상화에 의존, 구체 클래스에 직접 의존하지 않음 | 전원 콘센트 규격(추상)에 맞추면 되지, 특정 발전소(구체)에 직접 선을 안 대도 됨 |

## 깊이 이해

### 배경 — 왜 5개나 필요했나
- 1990년대 이후 객체지향 코드가 대형화되면서 "기능 하나 고쳤는데 무관한 다른 기능이 깨진다"는 문제(파급 효과, Fragility)가 반복됐다. 로버트 C. 마틴은 이 문제의 원인을 결합도·응집도 관점에서 분석해 5개 원칙으로 정리했고, 이후 마이클 페더스가 SOLID라는 약어로 묶었다.
- 5개는 독립된 규칙이 아니라 인과관계로 엮여 있다. SRP는 클래스를 작게 쪼개 응집도를 높이고, ISP는 인터페이스를 작게 쪼개며, LSP는 다형성이 깨지지 않게 상속을 통제하고, DIP는 의존 방향을 추상화로 돌린다 — 이 넷이 함께 작동해야 OCP(기존 코드 무수정 확장)가 실제로 가능해진다.

### SRP — "책임이 몇 개인가"로 판별한다
- 판별 원리: 이 클래스가 변경되어야 할 이유(요구 주체)가 몇 개인가를 센다. 이유가 2개 이상이면 위반이다.
- 예: `User` 클래스가 회원 정보 필드(이름·나이) 외에 `saveToDb()`(DB 저장)와 `sendWelcomeEmail()`(메일 발송)까지 갖고 있다면, DB 스키마 변경과 메일 발송 정책이라는 서로 다른 두 요구 주체가 같은 클래스를 건드리게 된다. 메일 템플릿만 바꾸려 해도 `User` 클래스 전체를 재컴파일·재배포해야 하고, 이 과정에서 DB 저장 로직에 실수로 손을 댈 위험이 생긴다.
- 해결: `User`(데이터), `UserRepository`(저장), `NotificationService`(발송) 3개로 분리하면 메일 정책 변경은 `NotificationService` 1개 파일만 건드리고 끝난다.

### OCP — 기존 파일 수정 라인 수로 위반을 판별한다
- 판별 원리: 새 케이스를 추가할 때 기존 파일의 수정 diff가 0줄인가를 본다. 0줄이면 OCP 준수, 1줄이라도 기존 로직을 고쳐야 하면 위반이다.
- 예(위반): 할인 정책이 `if(등급=="VIP") 10% else if(등급=="GOLD") 5% else if(등급=="일반") 0%`로 3개 분기라 하자. 4번째 등급(VVIP)을 추가하려면 이 if-else 블록 자체를 열어 4번째 분기를 끼워 넣어야 한다. 등급이 늘어날수록 이 메서드의 분기 수가 선형으로 늘고 수정 지점은 항상 같은 곳(이 메서드)에 몰린다.
- 예(준수): `DiscountPolicy` 인터페이스와 `VipDiscount`, `GoldDiscount`, `NormalDiscount` 클래스로 분리하고 호출부는 `policy.discount(price)`만 호출한다(전략 패턴). VVIP 추가 시 `VvipDiscount` 클래스 파일 1개만 새로 생성하면 되고, 기존 3개 클래스와 호출부 코드는 한 줄도 바뀌지 않는다.

### LSP — 다형성이 깨지는 조건을 특정한다
- 판별 원리: 자식 클래스가 부모의 사전조건(입력 제약)을 강화하거나 사후조건(반환 보장)을 약화하면 위반이다. 부모 타입으로 작성된 코드가 자식 객체로 바뀌었을 때 예외를 던지거나 다른 결과를 내면 안 된다.
- 대표 사례(직사각형-정사각형 문제): `Rectangle`은 `setWidth(w)`와 `setHeight(h)`가 서로 독립적으로 동작한다는 계약을 갖는다. `Square`가 `Rectangle`을 상속하며 `setWidth(w)` 호출 시 `height`까지 함께 바꾸도록 오버라이드하면 이 계약을 깬다. `Rectangle r = new Square(); r.setWidth(5); r.setHeight(10);` 실행 후 `r.area()`는 사각형이 기대하는 50이 아니라 100을 반환해, 부모 타입만 보고 작성된 테스트가 자식 객체에서 실패한다.
- 해결: `Square`를 `Rectangle`의 자식으로 두지 않고 공통 상위 `Shape` 인터페이스 아래 형제로 둔다. "~은 ~의 일종이다"라는 관계가 자연스러워 보여도, 행동 계약까지 일치하는지 별도로 확인해야 한다.

### ISP — 인터페이스 메서드 개수로 판별한다
- 판별 원리: 구현 클래스가 인터페이스 메서드 중 일부만 실제로 쓰고 나머지는 빈 구현이나 예외로 채워야 한다면 위반이다.
- 예: `Machine` 인터페이스에 `print()`, `scan()`, `fax()` 3개 메서드가 있다고 하자. 프린트 전용 기기 클래스 `SimplePrinter`는 `print()`만 구현할 수 있고 `scan()`, `fax()`는 `throw new UnsupportedOperationException()`으로 채워야 한다. 클라이언트가 실수로 `simplePrinter.scan()`을 부르면 컴파일은 되지만 런타임에 깨진다.
- 해결: `Printer`, `Scanner`, `Fax` 3개 인터페이스로 쪼갠다. `SimplePrinter`는 `Printer` 1개만 구현하면 되고, 복합기 클래스만 3개를 모두 구현한다.

### DIP — 의존 방향을 화살표로 확인한다
- 판별 원리: 상위(정책) 계층의 소스 코드에 `new 구체클래스()`가 나타나면 위반이다. 상위 모듈과 하위 모듈이 모두 인터페이스를 바라보아야 한다.
- 예: `OrderService`(상위) 안에서 `new KakaoPayClient()`(하위, 구체 구현)를 직접 생성하면, 결제사를 `NaverPay`로 바꿀 때 `OrderService` 코드 자체를 열어 `new NaverPayClient()`로 고쳐야 한다.
- 해결: `PayGateway` 인터페이스를 두고 `OrderService`는 `PayGateway` 타입 필드만 갖는다. 어떤 구현체를 넣을지는 외부(생성자·설정)에서 결정해 주입한다(의존성 주입, DI). Spring 같은 프레임워크의 IoC 컨테이너가 이 주입을 대신한다.

### 비유와 흔한 오해
- 비유: 건전지를 랜턴에 직접 납땜하면(구체 의존) 방전 시 랜턴째로 버려야 한다. AA 규격(인터페이스)에 맞춰 갈아 끼우게 만들면 어느 제조사 건전지든(구현체) 랜턴(기존 코드)을 바꾸지 않고 계속 쓴다.
- 오해: 인터페이스를 많이 만드는 것 자체가 SOLID는 아니다. 인터페이스가 100개여도 기능을 바꿀 때마다 여러 클래스 내부를 함께 고쳐야 한다면(수정 diff가 여러 파일에 퍼짐) OCP는 지켜지지 않은 것이다. 판별 기준은 항상 "새 케이스 추가 시 기존 파일 수정 여부"다.

## 연결 개념
- 디자인 패턴(GoF) — SOLID(원칙)를 실제 클래스 구조로 구현한 결과물(전략 패턴=OCP+DIP, 어댑터 패턴=ISP 등)
- 의존성 주입(DI)과 IoC 컨테이너 — DIP를 프레임워크 차원에서 자동화하는 메커니즘
- 결합도·응집도(Coupling/Cohesion) — SOLID 5원칙이 공통으로 최적화하려는 두 축

# 📝 【답안용】 시험 답안 템플릿

> 목적: 시험장에서 25분에 그대로 쓰는 답안 양식. 작성방식(추상표현 금지·수치·도식·문제유형 전환)을 엄격히 지킨다.
> 핵심: 이 시험은 정보를 많이 나열하는 시험이 아니라, 문제 신호어에서 출제자 의도를 읽고 핵심 논점을 선별해 쓰는 시험이다.

## 핵심 인사이트 (3줄 요약)

> 1. **본질**: 응집도(Cohesion)를 높이고 결합도(Coupling)를 낮추어, 소프트웨어의 요구사항 변경 시 기존 코드의 수정(파급 효과)을 최소화하기 위한 객체 지향 5대 설계 패러다임이다.
> 2. **가치**: 모듈 간의 강결합(Tightly Coupled)을 인터페이스를 통한 느슨한 결합(Loosely Coupled)으로 역전시켜, 레고 블록 같은 플러그인(Plug-in) 확장이 가능한 유연한 아키텍처 생태계를 구축한다.
> 3. **판단 포인트**: 5개 원칙의 단순 나열을 넘어, 5개가 결국 지향하는 최종 목표인 **OCP(확장엔 열려있고 수정엔 닫혀있는 아키텍처)**를 중심으로, DIP와 다형성이 이를 어떻게 기술적으로 지원하는지 유기적 인과 도식을 그려야 한다.

## 출제 의도 및 답안 포인트

| 출제 의도 | 반드시 짚을 핵심 | 감점 회피 포인트 |
|:---|:---|:---|
| SOLID 5원칙의 개념 및 상호 보완적 융합 메커니즘 | OCP 중심의 설계와 DIP/LSP에 의한 다형성(Polymorphism) 보장 | 5가지를 완전히 분절된 별개의 개념으로 따로따로 기계적 암기 서술 |
| 강결합(Tightly Coupled) 스파게티 코드의 리스크 도출 | OCP 위반 및 의존성 강결합(구상 클래스 의존) | 원칙 적용에 따른 Trade-off(클래스 수 증가, 구조 복잡화) 누락 |
| 실무 프레임워크(Spring) 적용 사상과의 연계 | DI(Dependency Injection) 메커니즘으로 DIP 완벽 구현 | DI 컨테이너 없이 순수 Java만으로 DIP를 완벽히 통제한다고 서술 |

> 요약: 건전지를 납땜해서 랜턴을 파는 회사는 망한다. 랜턴(기존 코드)은 건드리지 않고, 규격(인터페이스)에 맞는 새로운 건전지(기능)를 외부에서 무한히 갈아 끼우는 것. 그것이 소프트웨어 생존의 알파이자 오메가인 OCP다.

## Ⅰ. 개요 및 필요성

- 정의: 로버트 C. 마틴이 정리한, 소프트웨어의 유지보수성과 확장성을 극대화하기 위한 객체 지향 프로그래밍(OOP) 및 설계의 5가지 핵심 원칙 (SRP, OCP, LSP, ISP, DIP)
- 배경: 비즈니스 기획 변경에 따라 코드 한 줄을 수정했을 뿐인데 시스템 전체에 버그가 연쇄 폭발(Fragility)하고, 모듈 재사용이 불가능해져 소프트웨어의 기술 부채(Technical Debt)가 붕괴 수준에 도달
- 필요성: 구체적인 구현(Implementation)이 아닌 추상화(Abstraction/Interface)에 의존하여, 소스코드의 수정(Modification) 없이 기능의 확장(Extension)을 이뤄내는 플러그인 아키텍처 달성을 위함

## Ⅱ. SOLID 5대 원칙 메커니즘: OCP 중심의 유기적 방어망

SOLID는 각자 노는 게 아니다. OCP라는 성(Castle)을 지키기 위해 나머지 4개가 벽돌이 되어준다.

```text
[ OCP(개방-폐쇄 원칙) 완성을 위한 SOLID 유기적 융합 도식 ]

                          (역할을 작게 분리)
                  +-------------------------------+
                  | SRP (단일 책임) : 주방장, 계산원 | (클래스 비대화 억제)
                  +-------------------------------+
                                  |
                                  V 
(기존 코드 수정 X) 👑 [ OCP (개방-폐쇄 원칙) : 궁극적 목표 ] 👑 (새 기능 추가 플러그인)
                                  ^ 
                                  |
      +---------------------------+---------------------------+
      |                           |                           |
[ ISP (인터페이스 분리) ]  [ DIP (의존성 역전) ]   [ LSP (리스코프 치환) ]
(필요한 것만 찢어서 상속)   (구체 클래스 의존 금지)  (자식은 부모를 배신하지 않음)
      |                           |                           |
      +------> (인터페이스와 다형성을 통한 느슨한 결합 달성) <------+
```

| 원칙 (Principle) | 아키텍처적(엔지니어링) 제어 메커니즘 및 철학 |
|:---|:---|
| **S**RP (단일 책임) | 클래스가 변경되어야 하는 **이유(책임/역할)는 오직 하나뿐**이어야 함. `Employee` 객체가 급여 계산과 DB 접속을 동시에 하면 안 됨 (응집도 극대화) |
| **O**CP (개방-폐쇄)| **확장에는 열려(Open) 있고, 변경에는 닫혀(Closed) 있어야 함**. 카카오페이 결제가 추가되어도, 기존 `OrderService` 내부 코드는 0줄(Zero) 수정됨 |
| **L**SP (리스코프 치환)| 자식 객체는 부모 객체의 동작(규약)을 **완벽히 치환(대체)**해야 함. (직사각형-정사각형 문제 방어). 다형성(Polymorphism)이 깨지지 않는 안전장치 |
| **I**SP (인터페이스 분리)| 거대(Fat) 인터페이스를 클라이언트가 딱 쓸 만큼만 작게 찢어냄. 복합기(`Machine`) 대신 `Printer`, `Scanner`, `Fax` 3개로 분리 (인터페이스 응집도) |
| **D**IP (의존성 역전)| 고수준 모듈(비즈니스)이 저수준 모듈(Oracle DB)에 의존하면 안 됨. **둘 다 추상화(Interface)에 의존해야 함**. 인터페이스 껍데기만 바라보게 뒤집기 |

> 요약: 운전자(고수준)가 소나타(저수준)에 직접 의존하면 벤츠로 바꿀 때 운전면허증(기존 코드)을 찢어야 한다. DIP를 통해 '자동차'라는 인터페이스(추상화)에 의존해야 평생 코드를 안 고치고(OCP) 차를 무한히 갈아탈 수 있다.

## Ⅲ. 극복해야 할 시스템적 리스크 (안티패턴 및 위반 시나리오)

이 룰을 어기는 순간, 당신의 코드는 내일 당장 지옥불 폭탄이 되어 돌아온다.

| 리스크 요인 (위반) | 발생 시나리오 및 시스템 붕괴 원인 (안티패턴) | 아키텍처 대응 방안 (실무 튜닝) |
|:---|:---|:---|
| **DIP 위반 파국** <br> (구상 클래스 결합) | `OrderService` 내부에서 `new KakaoPay()`를 직접 생성함. 나중에 `NaverPay`로 바꿀 때, 기존 OrderService 클래스 파일을 까서 `new NaverPay()`로 하드코딩 뜯어고치다 버그 연쇄 폭발 | `Pay` 인터페이스를 선언하고 외부에서 주입(DI). **Spring Framework의 IoC(Inversion of Control) 컨테이너**가 런타임 시점에 `NaverPay` 객체를 대신 생성해 주입하도록 애플리케이션 라이프사이클 이관 |
| **LSP 위반 딜레마** <br> (상속의 오용) | 부모인 `새(Bird)`에 `fly()` 메서드가 있음. 자식 `펭귄(Penguin)`이 상속받은 뒤 `fly()`를 호출하면 런타임 에러(`UnsupportedException`)를 던지도록 코딩하여 다형성 계약을 완전 파기 | **상속(IS-A)을 버리고 합성(HAS-A/Composition) 선호**. 공통 코드를 재사용하려고 억지로 상속하지 말고, 차라리 `Flyable`, `Walkable` 인터페이스로 찢어서(ISP) 행동을 조립하도록 아키텍처 리팩토링 |

> 요약: OCP와 DIP를 완벽히 지키려면 코드에 `new` 키워드가 멸종해야 한다. 내가 쓸 객체를 내 손으로 만들지(new) 말고, 누군가(Spring Container)가 밖에서 넣어주는 것(DI). 이것이 제어의 역전(IoC)이다.

## Ⅳ. SOLID 원칙의 실무 적용 트레이드오프 (Trade-off)

아름다운 원칙도 맹목적으로 쓰면 복잡성의 늪(Over-engineering)에 빠져 회사를 망친다.

| 아키텍처 선택 | 엔지니어링 한계 (발생 리스크) | 균형점 튜닝 (아키텍트 판단) |
|:---|:---|:---|
| **극단적 인터페이스(DIP) 맹신** | 단순 CRUD 게시판을 짜는데도 `Board`, `BoardImpl`, `BoardService`, `BoardServiceImpl` 식으로 쓸데없는 인터페이스 파일을 무한 양산하여 폴더가 쓰레기장(Class Explosion)이 됨 | **YAGNI (You Aren't Gonna Need It) 원칙과의 타협**. 무조건 인터페이스를 뽑지 말고, 향후 1년 내에 교체될 가능성(결제 모듈, 외부 API 등 변동성)이 명백한 도메인(Domain) 경계선에만 전략적으로 인터페이스 방어막 구축 |

> 요약: 모든 코드에 억지로 인터페이스를 달아 SOLID를 맞추려는 건 디자인 패턴 병(병)이다. 변하는 것(정책)과 변하지 않는 것(엔티티)을 구분해서 칼을 대야 한다.

## Ⅴ. 실무 적용 방안 및 결론

**적용 방안 3개:**
1. [Facade 패턴을 결합한 SRP(단일 책임) 리팩토링] 3,000줄짜리 통짜 `UserService`(God Class 안티패턴)에서 DB 로직, 파일 업로드 로직, 알림 발송 로직을 각각 `UserRepository`, `FileUploader`, `NotificationService` 클래스로 칼같이 찢어내어 응집도를 극대화
2. [전략(Strategy) 패턴을 활용한 OCP 달성] 쇼핑몰의 복잡한 VIP 할인 정책 적용 시, 수십 개의 `if-else if(등급=='VIP')` 지옥을 타파하기 위해, `DiscountStrategy` 인터페이스를 만들고 `VIPDiscount`, `NormalDiscount` 클래스로 캡슐화하여, 신규 등급(VVIP) 추가 시 기존 코드를 0줄 고치고 클래스 파일 1개만 플러그인처럼 추가
3. [Spring DI 기반 의존성 주입 생태계 구축] 컨트롤러가 서비스에 의존할 때 `@Autowired`와 `Interface` 조합을 통해, 로컬 개발 시에는 DB를 찌르지 않는 `MockService`(더미)를 주입하고 운영 배포 시에만 `RealService`가 꽂히도록 DIP를 통한 완벽한 유닛 테스트(Unit Test) 고립(Isolation) 환경 구성

**결론:**
- 기술사 판단: SOLID 원칙은 코드를 짜는 가이드라인이 아니라, 10년 뒤에 후임 개발자가 내 코드를 보고 욕을 할지 찬사를 보낼지를 결정하는 '아키텍처의 지속가능성(Sustainability)' 보증 수표다. 이 5원칙을 이해하지 못하고 짠 코드는 단기적으로 동작할지 몰라도, 한 번의 요구사항 변경에 산산조각 나는 유리성에 불과하다.
- 향후 방향: 최근 마이크로서비스(MSA)와 함수형 프로그래밍(FP) 패러다임이 확산되면서, 객체 지향의 무거운 상속(LSP)보다는 인터페이스 조립(ISP)과 순수 함수(Side-effect 없는 상태)를 조합(Composition)하여 부수 효과를 격리하는 현대적(Modern) 패러다임으로 진화의 결을 맞추고 있다.
