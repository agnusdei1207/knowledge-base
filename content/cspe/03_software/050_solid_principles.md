# 📖 【암기용】 개념 완전 이해

## 한눈에
- **개요**: **SOLID 원칙**은 유지보수와 확장이 쉬운 객체지향 소프트웨어를 만들기 위해 지켜야 할 5가지 핵심 설계 원칙(SRP, OCP, LSP, ISP, DIP)의 앞 글자를 딴 것이다.
- **왜 필요한가**: 원칙 없이 코드를 짜면, 기능 하나를 수정할 때 연관된 수십 개의 파일이 깨지는 '스파게티 코드'가 된다. 변경에 유연하게 대처하려면 클래스 간의 결합도를 낮추고 응집도를 높이는 가이드라인이 필요하다.
- **핵심 직관**: 레고 블록 장난감. 각 블록은 하나의 색상과 크기만 가지고(단일 책임), 블록을 부수지 않고도 위로 계속 쌓을 수 있으며(개방-폐쇄), 표준 구멍(인터페이스)에만 맞으면 어떤 블록이든 교체 결합할 수 있다.

## 핵심 용어 정리

| 용어/표기 | 의미 | 비유·예 |
|:---|:---|:---|
| 응집도 (Cohesion) | 하나의 모듈 내부 요소들이 얼마나 밀접하게 관련되어 있는가의 정도 | 요리사가 요리 도구만 모아둔 가방 (높을수록 좋음) |
| 결합도 (Coupling) | 서로 다른 모듈 간에 얼마나 강하게 의존하고 있는가의 정도 | 리모컨이 특정 브랜드 TV에만 납땜된 상태 (낮을수록 좋음) |
| 다형성 (Polymorphism) | 같은 인터페이스를 통해 서로 다른 구현체를 실행할 수 있는 객체지향의 특성 | '운전하다'라는 버튼으로 아반떼도 몰고 포르쉐도 묾 |
| 추상화 (Abstraction) | 복잡한 내부 구현은 숨기고, 외부에는 필요한 공통 인터페이스만 노출하는 것 | 커피 머신의 내부 배관을 숨기고 버튼만 빼둠 |

## 깊이 이해
- **배경·문제의식**: 로버트 C. 마틴(Uncle Bob)이 제안한 것으로, 소프트웨어는 '한 번 짜고 끝'이 아니라 평생 요구사항이 변경(유지보수)된다는 데서 출발했다. 변경의 여파(Side Effect)를 최소화하는 것이 객체지향의 궁극적 목표다.
- **작동 원리 (5원칙)**:
  - **S (단일 책임, SRP)**: 클래스는 단 하나의 변경 이유만 가져야 한다. (요리사는 요리만, 서빙은 서빙만)
  - **O (개방-폐쇄, OCP)**: 확장에는 열려 있고, 수정에는 닫혀 있어야 한다. (새로운 기능을 추가할 때 기존 코드를 뜯어고치지 않음)
  - **L (리스코프 치환, LSP)**: 자식 클래스는 언제나 부모 클래스를 대체할 수 있어야 한다. (독수리가 새를 상속받았는데 날지 못하면 안 됨)
  - **I (인터페이스 분리, ISP)**: 자신이 쓰지 않는 인터페이스에 의존하지 않도록 잘게 쪼갠다. (복합기 대신 프린터, 스캐너, 팩스 기능별 스위치 분리)
  - **D (의존성 역전, DIP)**: 구체적인 클래스에 의존하지 말고, 추상화된 인터페이스에 의존해라. (운전자는 벤츠 엔진이 아니라 '엔진 인터페이스'를 다뤄야 차를 바꿀 수 있음)
- **비유**: USB 포트(DIP/OCP). 컴퓨터(고수준)와 마우스(저수준)가 직접 전선으로 묶여 있지 않고, USB라는 추상적 인터페이스에 의존한다. 덕분에 컴퓨터를 안 뜯고도 키보드나 프린터로 무한 확장이 가능하다.
- **흔한 오해·주의점**: "SOLID를 무조건 지켜야 한다"는 오해다. 지나치게 원칙에 얽매이면 인터페이스와 클래스가 쓸데없이 많아져 코드가 과도하게 복잡해진다(Over-engineering). 실무에서는 '변경이 자주 일어날 것 같은 축'을 중심으로 선택적 적용이 필요하다.

## 연결 개념
- 디자인 패턴 (GoF 23종) — SOLID 원칙을 실제로 구현하는 23가지 코드 템플릿
- 애자일 (Agile) — 요구사항 변화를 수용하기 위해 SOLID와 같은 유연한 설계가 필수적임
- MSA (Microservice Architecture) — 단일 책임 원칙(SRP)을 클래스 단위에서 서비스 단위로 확장한 구조

# 📝 【답안용】 시험 답안 템플릿

## 핵심 인사이트 (3줄 요약)

> 1. **본질**: SOLID 원칙은 객체지향 프로그래밍에서 높은 응집도(High Cohesion)와 낮은 결합도(Low Coupling)를 달성하기 위한 5가지 필수 설계 가이드라인이다.
> 2. **가치**: 소프트웨어의 노후화를 막고 요구사항 변경 시 기존 코드의 수정을 최소화(Side Effect 방지)하여, 안정적인 기능 확장과 유지보수성을 극대화한다.
> 3. **판단 포인트**: 각 원칙은 독립적인 것이 아니라 서로 보완적이며, 다형성(Polymorphism)과 추상화(Abstraction)라는 무기를 통해 궁극적으로 OCP(개방-폐쇄 원칙)를 달성하는 데 목적이 있다.

## 출제 의도 및 답안 포인트

| 출제 의도 | 반드시 짚을 핵심 | 감점 회피 포인트 |
|:---|:---|:---|
| 객체지향의 근본적인 설계 철학 이해 | SRP, OCP, LSP, ISP, DIP의 정확한 정의와 적용 목적 | 5개의 이름만 나열하고 각 원칙이 해결하는 문제(결합도 등) 누락 |
| 설계 원칙 간의 상호 작용 및 실무 적용 | DIP, LSP를 통한 OCP 달성, 추상화와 인터페이스 | 특정 프로그래밍 언어(Java 등)의 문법적 설명으로만 축소 |

> 요약: SOLID는 소프트웨어의 유지보수 비용을 낮추기 위한 설계 방침으로, 각 원칙이 객체지향의 다형성/추상화를 어떻게 활용하는지 증명해야 한다.

## Ⅰ. 개요 및 필요성

- 개요: 소프트웨어의 유지보수성과 확장성을 높이기 위해 로버트 C. 마틴이 정립한 객체지향 설계의 5가지 핵심 원칙 (SRP, OCP, LSP, ISP, DIP)
- 배경: 기능 추가 시 연관된 다른 클래스들까지 연쇄적으로 수정해야 하는 '경직성(Rigidity)'과 잦은 버그 유발(스파게티 코드) 문제 대두
- 필요성: 모듈 간 결합도를 낮추고 응집도를 높여, 요구사항 변경 시 기존 코드를 건드리지 않고 플러그인(Plug-in)처럼 기능을 안전하게 확장하기 위해 필수

---

## Ⅱ. 구조 및 구성요소 (5원칙 상세)

```text
[ 기반 원칙 ]                  [ 확장 원칙 ]                   [ 궁극적 목표 ]
SRP (변경의 축 단일화) -> ISP (인터페이스 분리)
                         LSP (상속 치환성 보장) ----(다형성)----> OCP (확장 개방 / 수정 폐쇄)
                         DIP (추상화 의존)
```

| 구성요소 | 역할 (의미) | 적용 효과 |
|:---|:---|:---|
| S (단일 책임, SRP) | 클래스는 단 하나의 변경 이유(책임)만 가져야 한다. | 모듈의 응집도 향상, 사이드 이펙트 최소화 |
| O (개방-폐쇄, OCP) | 확장에는 열려 있고(Open), 변경에는 닫혀 있어야(Closed) 한다. | 다형성/인터페이스를 통한 기존 코드 수정 방지 |
| L (리스코프 치환, LSP) | 하위 타입은 상위 타입의 규약(행위)을 완벽히 대체할 수 있어야 한다. | 다형성의 신뢰성 확보, 상속 오용 방지 |
| I (인터페이스 분리, ISP) | 클라이언트는 자신이 사용하지 않는 메서드에 의존하지 않아야 한다. | 범용 인터페이스의 비대화(Fat) 방지 |
| D (의존성 역전, DIP) | 고수준 모듈은 저수준 모듈의 구체적 구현이 아닌 추상화에 의존해야 한다. | 클래스 간 강결합 제거, 제어의 역전(IoC) 기반 |

> 요약: SRP와 ISP는 크기를 작게 나누어 응집도를 높이고, LSP와 DIP는 다형성을 보장하여, 최종적으로 유연한 확장(OCP)을 완성한다.

## Ⅲ. 동작원리 및 흐름도 (SOLID가 적용된 리팩토링 흐름)

```text
(Before) 강결합 레거시 코드 -> SRP 분리 -> DIP/ISP 추상화 -> LSP 검증 -> (After) OCP 기반 확장
```

- 1단계 [책임 분리 (SRP/ISP)]: 비대한 클래스(God Object)를 역할별로 쪼개고, 범용 인터페이스를 클라이언트 목적에 맞게 잘게 분할
- 2단계 [추상화 도출 (DIP)]: A클래스가 B클래스(구현체)를 직접 생성(new)하지 않도록, 둘 사이에 추상 인터페이스를 도출하여 의존성을 역전
- 3단계 [다형성 검증 (LSP)]: 추상 인터페이스를 상속받는 다양한 구현체들이 부모의 의도(사전/사후 조건)를 어기지 않고 동작하는지 검증
- 4단계 [기능 확장 (OCP)]: 새로운 기능 요구 시, 기존 코드는 전혀 수정하지 않고 새로운 구현체(자식 클래스)를 추가하여 시스템 동작 확장

> 요약: 기존 강결합 코드를 역할과 추상화 기준으로 분해한 뒤, 인터페이스를 매개로 느슨하게 조립하여 유연한 확장을 달성한다.

## Ⅳ. 특징
- 유연성과 재사용성: 변화가 예상되는 곳(구현)과 고정된 곳(인터페이스)을 분리하여, 모듈을 레고 블록처럼 타 프로젝트에 쉽게 재사용 가능
- 테스트 용이성 (Testability): DIP와 ISP를 통해 구체적인 DB나 네트워크 객체 대신 모의 객체(Mock)를 쉽게 주입할 수 있어 단위 테스트(Unit Test) 극대화
- 구조적 복잡도 증가: 원칙을 엄격하게 적용할수록 인터페이스와 클래스 개수가 기하급수적으로 늘어나 소규모 프로젝트에서는 오버엔지니어링(Over-engineering) 유발

> 요약: 단기적인 개발 속도를 희생하여 장기적인 유지보수 비용을 획기적으로 낮추는 트레이드오프를 갖는다.

## Ⅴ. 심화 비교 및 적용 판단

| 비교 축 | 절차지향 설계 | 객체지향 기반 일반 설계 | SOLID 적용 설계 | 선택 기준 |
|:---|:---|:---|:---|:---|
| 코드 구조 | 함수 단위의 순차 실행 | 데이터와 행위를 묶음 | 역할과 책임을 극도로 분리 | 시스템 생명 주기 |
| 변경 영향도 | 파급 효과 큼 (전체 재작성 위험) | 상속 오용 시 취약점 존재 | OCP 달성으로 변경 영향 최소화 | 요구사항 변경 빈도 |
| 다형성 활용 | 분기문 (if-else, switch) 남발 | 기본적 오버라이딩 적용 | 인터페이스 기반 전략 패턴 활용 | 코드의 조건문 복잡도 |

> 요약: 수명이 짧고 단발성인 스크립트는 절차지향이 유리하나, 수년간 유지보수되며 확장해야 하는 엔터프라이즈 시스템은 SOLID 원칙이 필수다.

**리스크·대응:**
- 무분별한 상속(LSP 위반): 단순히 코드를 재사용하기 위해 억지로 상속하여 리스코프 치환 원칙 훼손 → 'IS-A' 관계가 아니면 상속 대신 '합성(Composition)' 활용
- 불필요한 추상화(복잡도 증가): 변경 가능성이 전혀 없는 유틸리티 클래스까지 인터페이스를 뽑는 오버엔지니어링 → YAGNI(You Aren't Gonna Need It) 원칙을 병행하여 불확실한 미래를 위한 과도한 설계 자제

**도입 후 점검 지표:**
- 결합도 및 응집도: 정적 분석 도구(SonarQube 등)를 통한 순환 참조(Cyclomatic Complexity) 10 이하 유지
- 테스트 커버리지: 의존성 역전(DIP)을 통한 Mocking 활용으로 단위 테스트 커버리지 80% 이상 달성

## Ⅵ. 실무 적용 및 결론

**적용 방안 3개:**
1. 아키텍처 레벨 (MSA 전환): 단일 책임 원칙(SRP)을 비즈니스 도메인 단위로 확장 적용하여, 각각 독립적인 데이터와 책임을 갖는 마이크로서비스로 분해 (Bounded Context)
2. 프레임워크 활용 (DIP 적용): Spring 프레임워크의 의존성 주입(DI - Dependency Injection) 컨테이너를 활용하여, 객체의 생성과 의존성 관리를 제어의 역전(IoC)으로 시스템화
3. 디자인 패턴 적용: 잦은 기능 변경 요구(예: 결제 수단 추가)에 분기문(if-else)을 쓰지 않고, 전략 패턴(Strategy Pattern)을 도입하여 OCP를 실무 코드에 구현

**결론 (2줄):**
- 기술사 판단: SOLID 원칙은 완벽한 코드를 만드는 절대적 규칙이 아니라, 소프트웨어 부패(Software Rot)를 막기 위해 실무적 트레이드오프를 판단하는 기준점이다.
- 향후 방향: 최근 클린 아키텍처와 헥사고날 아키텍처 등 현대 아키텍처 모델들은 모두 이 SOLID 원칙(특히 DIP)을 시스템 수준 거시적 구조로 확정한 결과물이다.
