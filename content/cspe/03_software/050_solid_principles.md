# 📖 【암기용】 개념 완전 이해

> 목적: SOLID 원칙을 처음 봐도 완벽히 이해하게 만든다. 시험 답안 양식이 아니라, 이해를 위한 친절한 설명이다.

## 한눈에
- **개요**: 객체지향 설계에서 변경 영향과 테스트 비용을 줄이는 5대 원칙
- **왜 필요한가**: 요구사항 변경 때 한 클래스가 여러 이유로 수정되고, 하위 타입 교체가 깨지고, 거대한 인터페이스가 테스트를 어렵게 만들면 결함이 늘어남.
- **핵심 직관**: 부품의 역할과 연결 규격을 잘 나누면 한 부품을 바꿔도 전체 기계를 다시 만들지 않아도 됨.

## 깊이 이해
- **배경·문제의식**: 객체지향은 캡슐화와 다형성을 제공하지만, 원칙 없이 상속과 의존성을 쓰면 변경 영향이 넓어짐. SOLID는 변경 이유와 의존 방향을 통제함.
- **작동 원리**: SRP는 변경 이유를 하나로 줄임. OCP는 확장에는 열고 수정에는 닫음. LSP는 하위 타입 대체 가능성을 지킴. ISP는 클라이언트별 인터페이스를 작게 나눔. DIP는 구체 클래스가 아니라 추상에 의존함.
- **비유**: 콘센트 규격이 표준이면 가전제품을 바꿔도 벽 배선을 뜯지 않음. DIP와 OCP는 이런 교체 가능성을 코드에 적용하는 원칙임.
- **구체 예시**: 결제 로직에서 `PaymentService`가 `CardPayment`, `KakaoPay` 구현체에 직접 의존하지 않고 `PaymentPort` 인터페이스에 의존하면 새 결제수단 추가 시 기존 주문 코드를 수정하지 않음.
- **흔한 오해·주의점**: SOLID는 클래스를 무조건 많이 나누는 규칙이 아님. 변경 이유와 테스트 경계를 줄이는 데 필요한 만큼만 적용해야 함.

## 연결 개념
- Design Pattern: SOLID 원칙의 반복 적용 사례
- Clean Architecture: DIP와 의존성 방향 적용
- Testability: mock, stub, contract test로 변경 영향 검증

# 📝 【답안용】 시험 답안 템플릿

> 목적: 시험장에서 25분에 그대로 쓰는 답안 양식. 작성방식(추상표현 금지·수치·도식·문제유형 전환)을 엄격히 지킨다.
> 핵심: SOLID 답안은 유지보수성이라는 추상어보다 변경 영향 범위, 테스트 가능성, 의존성 방향, 대체 가능성을 중심으로 작성한다.

## 핵심 인사이트 (3줄 요약)

> 1. **본질**: SOLID는 SRP, OCP, LSP, ISP, DIP로 객체지향 설계의 변경 영향과 의존성 방향을 통제하는 원칙이다.
> 2. **가치**: 요구사항 변경 시 수정 파일 수, 회귀 테스트 범위, mocking 비용을 줄이고 확장 지점을 명확히 함.
> 3. **판단 포인트**: 변경 이유, 추상화 경계, 하위 타입 계약, 인터페이스 크기, 의존성 역전 여부를 코드 지표로 확인해야 함.

## 출제 의도 및 답안 포인트

| 출제 의도 | 반드시 짚을 핵심 | 감점 회피 포인트 |
|:---|:---|:---|
| 객체지향 설계 원칙 이해 확인 | SRP/OCP/LSP/ISP/DIP 각각의 변경 통제 의미 | 약어 풀이만 작성 |
| 변경 영향 판단 확인 | 수정 파일 수, 테스트 범위, 의존성 방향 | 유지보수성 표현만 반복 |
| 적용 능력 확인 | 결제수단, 저장소, 알림 채널 등 확장 예시 | 원칙 과잉 적용과 클래스 폭증 누락 |

> 요약: 이 문제는 SOLID 약어 암기가 아니라 변경 영향과 테스트 가능성을 수치·구조로 설명하는 능력을 요구한다.

---

## Ⅰ. 개요 및 필요성

SOLID는 객체지향 5대 설계 원칙이다. 소프트웨어 변경 비용은 코드량보다 의존성 방향과 변경 영향 범위에 의해 결정된다. SOLID는 역할 분리와 추상 의존으로 수정 범위와 테스트 비용을 통제한다.

---

## Ⅱ. 구조 및 구성요소

```text
Requirement Change -> Class Responsibility -> Interface Contract
                   -> Abstraction Dependency -> Implementation
SOLID -> SRP / OCP / LSP / ISP / DIP
Test -> Unit Test / Contract Test / Regression Scope
```

| 구성요소 | 역할 | 특이사항 |
|:---|:---|:---|
| SRP | 변경 이유를 하나로 제한 | God Class 방지 |
| OCP | 새 기능은 확장으로 추가 | strategy, plugin 구조 |
| LSP | 하위 타입 대체 가능성 유지 | pre/post condition 위반 금지 |
| ISP/DIP | 작은 인터페이스와 추상 의존 | mock, adapter, port 활용 |

> 요약: SOLID는 책임, 확장, 대체, 인터페이스, 의존성 방향을 나눠 변경 영향을 제한한다.

---

## Ⅲ. 동작원리 및 흐름도

```text
변경 요구 발생 -> 변경 이유 분석 -> 책임 분리
-> 확장 지점 추상화 -> 인터페이스 분리
-> 구현체 주입 -> 단위/계약 테스트 실행
-> 수정 파일 수와 회귀 범위 측정
```

| 단계 | 처리 내용 | 검증 기준 |
|:---:|:---|:---|
| 1 | 변경 이유와 책임 식별 | 클래스당 책임 1개 |
| 2 | 확장 가능 지점 도출 | 기존 코드 수정 0~1개 |
| 3 | 인터페이스와 추상 타입 설계 | 메서드 5개 이하, client별 분리 |
| 4 | 구현체를 DI로 주입 | 구체 클래스 직접 new 감소 |
| 5 | 단위·계약 테스트 수행 | 변경 관련 테스트 90% 이상 통과 |

> 요약: SOLID 적용은 변경 요구를 책임과 추상화로 분리하고 테스트로 대체 가능성과 영향 범위를 검증하는 절차이다.

---

## Ⅳ. 특징

| 구분 | 원칙 미적용 | SOLID 적용 | 수치·판단 포인트 |
|:---|:---|:---|:---|
| 변경 영향 | 다수 클래스 연쇄 수정 | 책임별 수정 범위 제한 | 변경 1건당 수정 파일 3개 이하 |
| 확장 방식 | if/switch 추가 | strategy, factory, plugin | 기존 핵심 로직 수정 0건 |
| 테스트 | 통합 테스트 의존 | mock 기반 단위 테스트 | 단위 테스트 실행 5분 이하 |
| 의존성 | 구체 구현 직접 의존 | interface, port 의존 | 순환 의존 0건 |

> 요약: SOLID는 변경 범위와 테스트 비용을 지표로 관리하게 해 설계 품질을 검증 가능하게 만든다.

## Ⅴ. 심화 비교 및 적용 판단

| 비교 축 | 기존/대안 | 본 키워드 | 선택 기준 |
|:---|:---|:---|:---|
| 구조 | 절차형 조건 분기 | 역할·추상화 기반 객체 설계 | 변경 유형 3개 이상 반복 |
| 비용/성능 | 클래스 수 적음 | 추상 계층 추가 | 런타임 overhead보다 변경 비용 우선 |
| 운영/위험 | 결합도 증가 | 인터페이스 관리 필요 | 순환 의존 0건, coverage 80% 이상 |

> 요약: SOLID는 변경 빈도가 높고 테스트 격리가 필요한 도메인 로직에 우선 적용한다.

| 리스크 | 원인 | 대응 방안 | 확인 지표 |
|:---|:---|:---|:---|
| 과설계 | 변경 가능성 낮은 곳까지 추상화 | YAGNI, ADR로 근거 기록 | 미사용 interface 수 |
| LSP 위반 | 하위 타입이 부모 계약 변경 | contract test, invariant 명시 | subtype test failure |
| 인터페이스 비대화 | 여러 client 요구 혼합 | ISP 적용, port 분리 | interface method count |

> 요약: SOLID 리스크는 과설계와 계약 위반이며, 사용 근거와 contract test로 통제한다.

| 점검 항목 | 목표 기준 | 측정 방법 |
|:---|:---|:---|
| 변경 영향 | 수정 파일 3개 이하, 순환 의존 0건 | dependency graph, PR diff |
| 테스트성 | 단위 테스트 80% 이상, 실행 5분 이하 | coverage report, CI time |
| 설계 품질 | class fan-in/fan-out 임계치 관리 | static analysis, SonarQube |

> 요약: SOLID 적용 품질은 변경 파일 수, 테스트 지표, 의존성 그래프로 판단한다.

## Ⅵ. 실무 적용 및 결론

**적용 방안 3개 (필수 - 단계별 또는 항목별):**
1. 변경 빈도가 높은 결제, 알림, 할인 정책에 Strategy와 DIP를 적용하고 port interface를 도입함.
2. LSP 검증을 위해 구현체 공통 contract test를 만들고 CI에서 모든 subtype에 동일 테스트를 실행함.
3. SonarQube, ArchUnit, dependency-cruiser로 순환 의존 0건, test coverage 80% 이상, class fan-out 임계치를 점검함.

**결론 (2줄):**
- 기술사 판단: 변경 빈도와 테스트 격리 요구가 높은 도메인은 SOLID를 적용하고, 일회성 CRUD에는 과도한 추상화를 제한함.
- 향후 방향: SOLID는 Clean Architecture, Hexagonal Architecture, DDD와 결합해 의존성 방향을 도메인 중심으로 고정하는 설계 기준으로 활용됨.
