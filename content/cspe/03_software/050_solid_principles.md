## 미리 알고가기

- SOLID는 객체지향 설계 품질을 높이기 위한 다섯 가지 원칙 묶음임
- DIP는 상위 정책이 구체 구현이 아니라 추상화에 의존하게 하는 원칙임
- Mockability는 테스트에서 대역 객체로 쉽게 교체할 수 있는 정도를 뜻함

## Ⅰ. 개요

- **정의/개념**: SOLID 원칙은 객체지향 소프트웨어에서 변경 영향 범위를 줄이고 결합을 낮추고 테스트를 쉽게 만들기 위해 제시된 다섯 가지 설계 원칙 집합임.
- **배경/필요성**: 요구 변경이 잦은 시스템에서는 클래스 책임이 뒤섞이고 구현 의존이 강해질수록 유지보수 비용이 급격히 늘어나므로, 변경에 강한 구조를 만드는 설계 기준이 필요함.

## Ⅱ. 특징

- 책임 분리와 추상화와 의존성 방향 제어를 함께 다룸
- 재사용 자체보다 변경 용이성과 테스트 가능성에 초점을 둠
- 작은 시스템에 과도하게 적용하면 추상화만 늘어날 수 있음
- 설계 원칙이므로 개별 패턴이나 프레임워크보다 상위 기준으로 작동함

## Ⅲ. 종류 및 비교

| 구분 | 원칙 미적용 구조 | SOLID 지향 구조 |
|:---|:---|:---|
| 책임 배치 | 하나의 클래스가 여러 변경 이유를 함께 떠안기 쉬움 | 변경 이유가 다른 책임을 분리해 수정 범위를 줄임 |
| 의존 방향 | 상위 로직이 구체 구현에 직접 묶이기 쉬움 | 추상화에 의존해 구현 교체와 테스트가 쉬워짐 |
| 변경 영향 | 작은 수정도 연쇄 수정으로 번질 가능성이 큼 | 국소 수정으로 끝날 가능성이 높아짐 |
| 테스트 용이성 | 대역 객체로 교체하기 어려워 단위 테스트가 무거워짐 | 인터페이스와 분리된 책임 덕분에 테스트가 단순해짐 |

> 요약: SOLID는 객체지향 문법을 예쁘게 쓰는 규칙이 아니라 변경과 테스트 비용을 줄이는 설계 기준임.

## Ⅳ. 구성요소 및 구조

| 구성요소 | 설명 |
|:---|:---|
| Single Responsibility | 클래스와 모듈이 하나의 변경 이유만 갖도록 해 수정 파급을 줄임 |
| Open Closed | 새 요구는 확장으로 수용하고 기존 안정 코드는 자주 건드리지 않게 함 |
| Liskov and Interface Segregation | 치환 가능성과 인터페이스 최소화를 통해 사용처 결합을 낮춤 |
| Dependency Inversion | 상위 정책이 추상화에 의존하게 해 구현 교체와 테스트를 쉽게 만듦 |

## Ⅴ. 원리 및 절차 흐름도

```text
+-------------+     +-------------+     +-------------+     +-------------+
| 변경 축 식별    | --> | 책임 분리      | --> | 추상화 설계    | --> | 의존성 검증    |
+-------------+     +-------------+     +-------------+     +-------------+
```

1. **변경 축 식별**: 무엇이 자주 바뀌는지 먼저 파악함
2. **책임 분리**: 서로 다른 변경 이유를 모듈 단위로 나눔
3. **추상화 설계**: 교체 가능해야 하는 지점에 인터페이스와 경계를 둠
4. **의존성 검증**: 상위 정책이 구체 구현에 묶이지 않는지 확인함

## Ⅵ. 실무 적용 및 유의점

1. 핵심 도메인 모듈 리팩터링에서는 SOLID가 효과적이지만 모든 클래스에 인터페이스를 강제로 만들면 구조만 무거워지므로 변경 가능성이 높은 경로에 한정 적용하고 변경 영향 범위와 추상화 비용으로 확인함
2. 테스트 자동화 강화 프로젝트에서는 DIP와 책임 분리가 중요하므로 외부 연동 경계를 추상화로 분리하고 대역 객체 대체 용이성과 결함 연쇄 비율로 확인함

## Ⅶ. 결론

SOLID는 객체지향 원칙 암기가 아니라 자주 바뀌는 코드를 더 적은 결합과 더 작은 수정 범위로 관리하기 위한 기준임.
