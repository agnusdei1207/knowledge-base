## 미리 알고가기

- SOLID 원칙(SOLID Principles): 객체지향 소프트웨어의 유지보수성과 확장성을 높이기 위한 다섯 가지 핵심 설계 원칙의 머리글자 조합임
- 단일 책임 원칙(SRP): 하나의 클래스는 단 하나의 변경 이유(책임)만 가져야 한다는 원칙임
- 개방·폐쇄 원칙(OCP): 확장에는 열려 있어야 하고 변경에는 닫혀 있어야 한다는 원칙임
- 리스코프 치환 원칙(LSP): 프로그램의 객체는 프로그램의 정확성을 깨뜨리지 않으면서 하위 타입의 인스턴스로 바꿀 수 있어야 한다는 원칙임
- 인터페이스 분리 원칙(ISP): 범용 인터페이스 하나보다 클라이언트를 위한 여러 개의 구체적인 인터페이스가 낫다는 원칙임
- 의존 역전 원칙(DIP): 고수준 모듈은 저수준 모듈에 의존해서는 안 되며, 둘 다 추상화에 의존해야 한다는 원칙임
- 결합도와 응집도(Coupling and Cohesion): 모듈 간 상호 의존성을 나타내는 결합도는 낮추고, 모듈 내부의 연관성을 나타내는 응집도는 높여야 설계 품질이 향상됨

## 작성 근거(검토용)

- SOLID는 책임, 확장 방식, 치환 가능성, 의존 방향을 핵심 축으로 선정함
- 구성은 다섯 원칙이 변경 범위와 테스트 대체성에 미치는 영향을 중심으로 제시함
- 실무 판단은 변경 영향 범위, 모듈 결합도, 외부 연동 없는 단위 테스트 비율로 구체화함
- 전수 검수 완료 근거: 제목, frontmatter, 미리 알고가기, 작성 근거, 본문, 표 헤더·셀, 요약, 결론을 한 줄도 빠뜨리지 않고 확인했으며 어색한 단어·조사·동사 결합·장황한 명사구를 교정함.

## Ⅰ. 개요

- **정의/개념**: SOLID는 객체지향 설계에서 책임·확장·치환·인터페이스·의존 방향을 정하는 다섯 원칙임
- **배경/필요성**: 클래스 책임이 섞이고 구현 의존이 강해지면 변경 범위와 테스트 비용이 커지므로 이를 통제할 설계 기준이 필요함

### 쉽게 이해하기 (학습용)
- 복잡한 기계 장치를 만들 때 모든 부품을 통째로 용접하지 않고 표준 규격의 콘센트와 선으로 연결해 고장 난 부품만 쉽게 교체할 수 있도록 돕는 5가지 조립 규칙임.

## Ⅱ. 특징

- 책임 분리와 추상화와 의존성 방향 제어를 함께 다룸
- 재사용 자체보다 변경 용이성과 테스트 가능성에 초점을 둠
- 변경 가능성이 낮은 코드까지 추상화하면 인터페이스와 구현 계층만 늘어날 수 있음
- 설계 원칙이므로 개별 패턴이나 프레임워크보다 상위 기준으로 작동함

### 쉽게 이해하기 (학습용)
- 프로그램을 잘게 쪼개고 결합을 느슨하게 만들어 코드 수정이 다른 곳에 미치는 영향을 최소화하고, 테스트를 쉽게 만들어 주지만, 너무 쪼개면 부품 종류가 지나치게 많아질 수 있음.

## Ⅲ. 종류 및 비교

| 판단 기준 | 원칙 미적용 구조 | SOLID 지향 구조 |
|:---|:---|:---|
| 모듈 응집도와 결합도 | 하나의 클래스에 다수의 책임이 혼재되어 응집도가 낮고 결합도가 높음 | SRP를 적용해 책임별로 클래스를 분리하여 높은 응집도와 낮은 결합도를 실현함 |
| 의존성과 확장 방식 | 구체 구현 클래스에 직접 의존하여 새로운 요구사항 반영 시 기존 코드 수정이 필요함 | 인터페이스를 통한 추상화와 OCP·DIP를 적용해 기존 코드 수정 없이 동적 확장이 가능함 |
| 단위 테스트 용이성 | 구체 클래스 간의 강결합으로 인해 외부 연동 모듈을 격리한 고립 테스트가 불가능함 | 의존성 주입(DI)과 LSP를 활용해 모의 객체($Mock\ Object$)로 대체하여 개별 단위 테스트가 용이함 |

> 요약: SOLID는 책임을 분리하고 추상화에 의존해 변경 범위와 외부 구현 결합을 줄이는 설계 기준임.

### 쉽게 이해하기 (학습용)
- 하나의 만능 리모컨에 모든 기능을 욱여넣어 고장 나면 통째로 버려야 하는 구식 설계와, 기능별 단자를 분리해 확장 단자로 기능을 추가하는 유연한 설계의 대조임.

## Ⅳ. 설계 요소 및 구조

```text
[클라이언트 클래스] ───> [인터페이스 (추상화)]
                             ▲
                             │ (LSP 만족 구현)
                    ┌────────┴────────┐
            [구체 구현 A]       [구체 구현 B]
```

| 설계 요소 | 설명 |
|:---|:---|
| SRP (Single Responsibility) | 하나의 모듈이 오직 하나의 액터와 변경 사유에만 책임지도록 구성함 |
| OCP (Open-Closed) | 추상화 인터페이스를 경계로 설정해 소스 코드의 직접 수정을 방지함 |
| LSP (Liskov Substitution) | 상위 인터페이스가 정의한 명세 계약을 하위 구현체가 완벽히 준수함 |
| ISP (Interface Segregation) | 클라이언트가 필요로 하는 최소한의 메서드만 노출하도록 다중 인터페이스로 분할함 |
| DIP (Dependency Inversion) | 구체 클래스 간의 결합을 끊고 고수준과 저수준 모두 추상 인터페이스에 의존함 |

> 요약: 단일 책임으로 변경 이유를 나누고 치환·분리·의존 역전으로 구현 교체 범위를 제한함.

### 쉽게 이해하기 (학습용)
- 할 일은 하나씩(SRP), 문은 열어두고 벽은 닫기(OCP), 아들이 부모 역할 대신하기(LSP), 필요한 만큼만 콘센트 뚫기(ISP), 플러그를 꽂아 쓰기(DIP)의 다섯 구조임.

## Ⅴ. 원리 및 절차 흐름도

```text
구체 의존성 식별 ──> 인터페이스 추출 ──> 의존 역전 결합 ──> 의존성 주입 처리
```

1. **구체 의존성 식별**: 상위 모듈이 하위 구체 클래스를 직접 생성하거나 호출하는 결합부를 탐색함
2. **인터페이스 추출**: 하위 클래스의 핵심 동작 명세를 담은 공통 인터페이스를 선언하고 하위 클래스가 이를 구현하게 함
3. **의존 역전 결합**: 상위 모듈의 참조 대상을 구체 클래스에서 추출된 인터페이스로 교체하여 컴파일 타임 의존성을 역전시킴
4. **의존성 주입 처리**: 외부 조립기를 통해 런타임에 구체 인스턴스를 동적으로 바인딩함

> 요약: 구체 의존성을 식별해 인터페이스를 추출하고, 이를 상위 모듈에 바인딩하여 런타임에 구체 클래스를 주입함.

### 쉽게 이해하기 (학습용)
- 철저히 붙어 있던 부품 사이의 연결을 끊고 중간에 어댑터(인터페이스)를 끼워 넣은 다음, 필요할 때마다 알맞은 부품을 외부에서 주입해 연결을 완성하는 과정임.

## Ⅵ. 실무 사례

전자결제 및 세금 계산 모듈 개발 시 외부 밴더사 API 규격 변경에 따른 기존 코드 수정을 차단하기 위해 OCP와 DIP를 활용하여 공통 결제 게이트웨이 인터페이스를 설계함. 결제 서비스가 구체 결제 대행 모듈이 아닌 공통 인터페이스에 의존하도록 구현하여 신규 결제 수단 추가 시 기존 결제 처리 흐름의 안전성을 확보함.

### 쉽게 이해하기 (학습용)
- 쇼핑몰의 카드 결제 시스템을 만들 때, 각 카드사 프로그램에 직접 코드를 맞추지 않고 '공통 카드 단말기' 인터페이스를 만들어 새 카드가 추가되어도 기존 코드를 안 고치게 함.

## Ⅶ. 결론

- SOLID 원칙은 객체지향 설계의 근본 목적인 변경 유연성과 테스트 용이성을 극대화하여 장기적인 유지보수 비용을 제어하는 설계 지침임.
- 불필요한 과잉 추상화로 인한 복잡도 증가를 방지하기 위해 비즈니스 도메인의 변경 빈도와 결합도 임계점을 합리적으로 따져 선택 적용해야 함.

### 쉽게 이해하기 (학습용)
- SOLID는 프로그램의 장기적인 생존과 유지보수를 보장하는 표준 가이드라인이며, 비즈니스의 특성과 변경 주기에 맞춰 적절한 깊이로 추상화를 조절해야 함.
