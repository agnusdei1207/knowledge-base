# 📖 【암기용】 개념 완전 이해

> 목적: 소프트웨어 라이선스를 처음 봐도 완벽히 이해하게 만든다. 시험 답안 양식이 아니라, 이해를 위한 친절한 설명이다.

## 한눈에
- **개요**: 소프트웨어 라이선스는 **저작권**에 근거해 저작권자가 코드의 사용·복제·수정·배포 조건을 정한 법적 허가이며, 크게 **Permissive**(관대형)와 **Copyleft**(전염형) 계열로 나뉜다.
- **왜 필요한가**: 소스코드는 작성되는 순간 저작권이 자동 발생한다. 허락 없이 코드를 가져다 쓰면 저작권 침해이고, 라이선스가 있어도 그 조건(고지·소스공개·특허)을 어기면 계약 위반·소송 리스크로 이어진다.
- **핵심 직관**: 라이선스는 "이 코드를 갖다 써도 되는 범위"와 "그 대가로 지켜야 할 의무"를 적은 사용 설명서다. "공짜(free of charge)"와 "자유(free as in freedom)"는 다른 축이며, 라이선스는 후자를 규정한다.

## 핵심 용어 정리 (내부에 등장하는 것들)

| 용어 | 의미 | 비유 |
|:---|:---|:---|
| 저작권 (Copyright) | 창작물에 자동 발생하는 배타적 권리 — 라이선스를 발급할 수 있는 근거 | 건물주가 있어야 임대 계약(라이선스)을 맺을 수 있음 |
| 라이선스 (License) | 저작권자가 특정 조건 하에 타인의 이용을 허락하는 문서 | 임대 계약서에 적힌 이용 규칙 |
| Permissive (관대형) | 원저작자 고지만 유지하면 재배포·수정·비공개화가 자유로움 | "출처만 밝히면 마음대로 써도 됨" |
| Copyleft (카피레프트) | 파생물도 동일 라이선스로 배포해야 하는 전염 의무 | "이 레시피로 만든 요리를 팔려면 레시피도 같이 공개" |
| MIT License | 가장 단순한 permissive — 저작권·라이선스 고지문 보존만 요구 | 최소 조건의 통행증 |
| Apache License 2.0 | permissive + 명시적 특허 허여(patent grant) + NOTICE 파일 요구 | 통행증 + 특허 소송 안 걸겠다는 각서 |
| GPL (GNU GPL) | Strong copyleft — 파생저작물 전체를 동일 라이선스로 소스공개할 의무 | 강한 전염 규칙(섞이면 전체가 같은 색) |
| LGPL | GPL의 완화판 — 동적 링크로 쓰면 소스공개 의무가 면제됨 | "빌려 쓰는 것"은 허용, "한 몸으로 합치는 것"만 제한 |
| AGPL | GPL + 네트워크 서비스(SaaS)로 제공해도 소스공개 의무 발생 | 서버 뒤에 숨어도 공개 의무는 피할 수 없음 |
| NOTICE 파일 | Apache 계열이 요구하는 고지 파일(원저작자·변경 이력 명시) | 포장지의 원산지 표시 |
| 정적 링크 / 동적 링크 | 라이브러리를 실행파일에 통째로 합치는 방식 / 실행 중 분리 로드하는 방식 — GPL 전염 범위 판단 기준 | 벽돌을 시멘트로 붙임(정적) vs 못으로 걸어둠(동적) |
| SPDX 식별자 | 라이선스를 기계 판독 표준 코드로 표기하는 규격(예: MIT, Apache-2.0, GPL-3.0-only) | 라이선스의 표준 바코드 |

## 깊이 이해

### Permissive와 Copyleft를 가르는 판별 원리
- 판별 기준은 하나다 — "파생저작물(수정본·결합물)을 배포할 때도 원래 조건을 강제하는가?" MIT·Apache는 강제하지 않는다(고지만 하면 비공개 상용화 가능). GPL은 강제한다(같은 라이선스로 소스를 공개해야 함).
- 수치로 보면: 100만 줄짜리 상용 제품에 GPL 라이브러리 1만 줄(전체의 1%)을 정적 링크해 배포하면, 이론적으로 나머지 99%까지 포함한 전체 100만 줄이 GPL 소스공개 대상이 될 수 있다 — copyleft는 "섞인 비율"이 아니라 "결합 여부" 자체로 전염 범위를 판단하기 때문이다.

### 링크 방식이 전염 범위를 가른다 (LGPL 예시)
- 순수 GPL 라이브러리를 정적 링크(라이브러리 코드를 실행파일 안에 통째로 넣음)하면 실행파일 전체가 하나의 파생저작물로 간주돼 GPL 의무가 걸린다.
- LGPL은 이를 완화한다 — 동적 링크(.so/.dll을 실행 시점에 분리 로드)로 사용하면 응용 프로그램 자체는 비공개로 유지하면서 LGPL 라이브러리 부분만 소스공개 의무를 진다. 예: 상용 앱이 LGPL 라이브러리를 동적 링크로만 쓰면 앱 소스는 비공개 가능하지만, 그 라이브러리 코드를 앱에 정적으로 합치면 앱도 LGPL 의무 범위에 들어올 수 있다.

### AGPL이 막으려 한 "ASP 허점"
- GPL의 소스공개 의무는 "배포(distribute)"할 때 발동한다. SaaS 사업자는 서버에서 GPL 코드를 실행만 하고 사용자에게 바이너리를 배포하지 않으므로, GPL 프로그램을 개조해 서비스로만 제공하면 소스공개 의무를 피할 수 있었다 — 이를 ASP 허점(Application Service Provider loophole)이라 부른다.
- AGPL(Affero GPL)은 "네트워크로 상호작용하는 사용자에게도 소스 제공 의무"를 추가해 이 허점을 막았다. 이 때문에 다수 기업이 AGPL 코드 사용을 사내 정책으로 아예 금지한다.

### 실제 분쟁 사례로 보는 리스크 규모
- 2021년 Elasticsearch·Kibana는 Apache-2.0에서 SSPL(Server Side Public License)로 라이선스를 변경했다 — 클라우드 사업자가 소스코드를 그대로 관리형 서비스로 재판매하면서도 코드 기여는 하지 않는 문제에 대한 대응이었다. permissive 라이선스라도 사업 모델 차원의 리스크(무임승차)가 있음을 보여준 사례다.
- 기업 제품 하나에 npm·Maven·PyPI 의존성이 수백~수천 개 포함되는 것이 일반적이며, 그중 하나라도 GPL·AGPL이 섞여 있으면 제품 전체의 배포 방식을 재검토해야 하는 상황이 실무에서 반복된다.

### 비유와 흔한 오해
- **비유**: MIT는 "출처만 표시하면 뭘 해도 되는 통행증", Apache는 "통행증 + 특허 안전 보증서", GPL은 "빌려온 것을 고쳐서 다시 나눠줄 땐 같은 조건으로 공개해야 하는 공유 규칙"이다.
- **오해 1**: 오픈소스는 무조건 무료라는 생각은 틀렸다 — 비용이 아니라 사용·배포·특허·고지 "조건"이 핵심이다.
- **오해 2**: "회사 내부에서만 쓰면 라이선스 의무가 없다"는 것도 절반만 맞다 — GPL은 배포 시에만 발동하므로 내부 사용은 대체로 안전하지만, AGPL은 내부 서버라도 외부 사용자가 접속하면 의무가 발동한다.

## 연결 개념
- 오픈소스 컴플라이언스 — 라이선스 조건을 조직 프로세스로 준수·검증하는 상위 활동
- SBOM — 제품에 포함된 컴포넌트와 그 라이선스를 식별하는 근거 자료
- SPDX — 라이선스 표기를 표준화하는 식별자 규격

## Ⅱ. 구조 및 구성요소

```text
Source Component -> License Identification -> Obligation Analysis
-> Approval Policy -> Notice/Source Offer -> Product Release
-> Audit Evidence
```

| 구성요소 | 역할 | 특이사항 |
|:---|:---|:---|
| MIT License | 저작권 고지와 라이선스 문구 보존 | permissive, 조건 최소 |
| Apache License 2.0 | 저작권 고지, NOTICE, 특허 허여 | patent grant, termination |
| GPL | 파생저작물 배포 시 동일 라이선스 적용 | strong copyleft, source offer |
| License Policy | 사용 금지·검토·허용 등급화 | 예: GPL 서버 배포 별도 승인 |

> 요약: 라이선스 판단은 유형별 의무와 제품 배포 방식의 결합으로 결정된다.

## Ⅲ. 동작원리 및 흐름도

```text
의존성 수집 -> 라이선스 자동 식별 -> 수동 검토
```

| 단계 | 처리 내용 | 검증 기준 |

| 4 | NOTICE, LICENSE, source offer 포함 | 배포 산출물 누락 0건 |

> 요약: 라이선스 준수는 식별, 의무 판단, 승인, 고지 산출물의 순서로 진행된다.

## Ⅵ. 실무 적용 및 결론

**적용 방안 3개 (필수 — 단계별 또는 항목별):**
1. SCA 도구로 npm, Maven, PyPI 의존성을 SPDX 기준으로 식별하고 unknown license 0건 전 릴리스 차단
2. 라이선스를 허용(MIT/BSD), 검토(Apache/MPL/LGPL), 제한(GPL/AGPL/상용금지) 3등급으로 정책화
3. 제품 배포물에 LICENSE, NOTICE, source offer, SBOM을 포함하고 릴리스별 증적을 3년 이상 보관

**결론 (2줄):**
- 기술사 판단: 내부 사용은 위험이 작지만 외부 배포 제품은 GPL·AGPL·특허 조항을 법무 승인 대상으로 지정
- 향후 방향: 라이선스 관리는 SBOM, SCA, 공급망 보안, VEX와 통합된 릴리스 거버넌스로 확장
