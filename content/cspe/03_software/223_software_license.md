## Ⅰ. 개요
- **정의**: SW 사용·복제·배포·수정에 대한 권리와 제한을 규정하는 법적 허가 조건임
- **배경/필요성**: SW 자산 가치가 증가하면서 저작권 보호와 합법적 활용 범위를 명확히 할 필요가 있음
- **비유**: 도서관 대출 규정처럼, 빌려 쓸 수 있는 범위와 반납·복사 조건을 명시하는 것과 유사함

| 출제 의도 | 반드시 짚을 핵심 | 감점 회피 포인트 |
|:---|:---|:---|
| 라이선스 유형별 의무 차이 | Copyleft vs Permissive 구분 | 오픈소스 라이선스와 상용 라이선스 혼동 금지 |

> 요약: SW 이용 권한과 의무를 법적으로 정의하여 저작권 분쟁을 예방하는 장치임

## Ⅱ. 구성요소
```text
+----------------+
|  License Type  |
+-------+--------+
        |
   +----+----+
   |         |
+--+--+   +--+---+
|상용 |   |오픈소스|
+-----+   +--+---+
              |
        +-----+-----+
        |           |
   +----+---+  +----+----+
   |Copyleft|  |Permissive|
   +--------+  +----------+
```

| 구성요소 | 설명 | 비유 |
|:---|:---|:---|
| 상용 라이선스 | 사용 대수·기간·기능 범위를 계약으로 제한함 | 유료 정기구독 |
| Copyleft | 파생 저작물도 동일 라이선스로 공개 의무 부과(GPL 등) | 기부 조건부 후원 |
| Permissive | 최소 조건(고지 의무)만 부과, 파생물 라이선스 자유(MIT, Apache 등) | 자유 이용 허가 |
| 듀얼 라이선스 | 오픈소스와 상용 조건을 동시에 제공하여 수익 모델 확보 | 무료 체험+유료 프리미엄 |

> 요약: 상용·Copyleft·Permissive·듀얼 유형에 따라 의무 범위가 달라짐

## Ⅲ. 절차
```text
식별 --> 분류 --> 검증 --> 준수
```
- 1단계: 식별 — 프로젝트 내 사용 중인 SW 구성요소와 라이선스 목록 수집
- 2단계: 분류 — 각 라이선스를 Copyleft/Permissive/상용으로 분류
- 3단계: 검증 — 라이선스 간 호환성과 의무 충돌 여부를 법률 검토
- 4단계: 준수 — 고지문 포함, 소스 공개, 사용 범위 제한 등 의무 사항 이행

> 요약: 식별-분류-검증-준수 4단계로 라이선스 컴플라이언스를 확보함

## Ⅳ. 문제점
- 라이선스 충돌: Copyleft와 상용 코드 혼합 시 법적 의무 상충 — 배포 자체가 불가능해질 위험
- 식별 누락: 간접 의존성(transitive dependency)의 라이선스가 파악되지 않음 — 잠재 위반 발생
- 조건 해석 모호: 라이선스 문구의 법적 해석이 국가별로 상이 — 글로벌 배포 시 리스크 증가

> 요약: 충돌, 누락, 해석 모호성이 라이선스 준수의 3대 과제임

## Ⅴ. 개선방안
1. 단기: SBOM(225 참조) 기반 자동 라이선스 식별 도구 도입으로 충돌 사전 탐지
2. 중기: 오픈소스 정책 게이트를 CI/CD에 통합하여 미식별 컴포넌트 빌드 차단
3. 장기: 법무·개발 협업 거버넌스 체계 수립으로 국가별 해석 차이 대응

> 요약: 자동 식별 → CI 정책 게이트 → 거버넌스 체계 순으로 준수 역량 강화

## Ⅵ. 전망
- 발전 방향: SPDX 표준 기반 기계 판독 가능 라이선스 메타데이터가 보편화됨
- 기술사적 판단: SW 공급망 규제 강화로 라이선스 관리는 선택이 아닌 법적 의무로 전환됨
- 기술사 제언: 개발 초기 단계부터 라이선스 정책을 정의하고 자동화 도구를 적용할 것을 권고함
