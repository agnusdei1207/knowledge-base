# 📖 【암기용】 개념 완전 이해

> 목적: 소프트웨어 라이선스를 처음 봐도 완벽히 이해하게 만든다. 시험 답안 양식이 아니라, 이해를 위한 친절한 설명이다.

## 한눈에
- **개요**: 소프트웨어 사용·복제·수정·배포 조건을 정한 법적 허가 조건
- **왜 필요한가**: 오픈소스 코드는 무료 다운로드와 별개로 저작권, 고지, 소스 공개, 특허 조건을 지켜야 한다
- **핵심 직관**: 라이선스는 "코드를 써도 되는 범위와 배포할 때 해야 할 의무"를 적은 계약 규칙이다

## 깊이 이해
- **배경·문제의식**: 기업 SW는 npm, Maven, PyPI 패키지를 수백~수천 개 포함한다. 라이선스 검토 없이 배포하면 소스 공개 의무 위반, 특허 보복 조항 위반, 저작권 고지 누락이 발생한다.
- **작동 원리**: MIT는 고지 보존 중심, Apache-2.0은 특허 허여와 NOTICE 조건, GPL은 파생저작물 배포 시 동일 라이선스와 소스 공개 의무가 붙는다.
- **비유**: MIT는 출처 표시 후 사용 허가, Apache는 출처와 특허 조건이 붙은 허가, GPL은 다시 나눠줄 때 같은 조건으로 공개해야 하는 공유 규칙에 가깝다.
- **구체 예시**: 상용 서버 제품에 GPL 라이브러리를 정적 링크해 배포하면 제품 소스 공개 의무 논쟁이 생긴다. Apache-2.0 라이브러리는 NOTICE와 라이선스 사본을 포함해야 한다.
- **흔한 오해·주의점**: 오픈소스는 무조건 무료가 아니다. 비용보다 배포 조건, 특허, 고지, 소스 공개 의무가 판단 기준임.

## 연결 개념
- 오픈소스 컴플라이언스 - 라이선스 의무 준수 프로세스
- SBOM - 포함 컴포넌트와 라이선스 식별 근거
- SCA - 의존성 라이선스와 취약점 자동 분석

# 📝 【답안용】 시험 답안 템플릿

> 목적: 시험장에서 25분에 그대로 쓰는 답안 양식. 작성방식(추상표현 금지·수치·도식·문제유형 전환)을 엄격히 지킨다.
> 핵심: 라이선스 명칭 암기가 아니라 배포 조건, 소스 공개 의무, 특허 조항, 고지 의무를 제품 유형과 연결한다.

## 핵심 인사이트 (3줄 요약)

> 1. **본질**: 소프트웨어 라이선스는 저작권자가 코드 사용·수정·배포 조건을 정한 법적 허가 체계이다.
> 2. **가치**: 라이선스 식별과 의무 이행으로 제품 배포 중단, 소스 공개 분쟁, 손해배상 리스크를 줄인다.
> 3. **판단 포인트**: Permissive(MIT·Apache)와 Copyleft(GPL)의 배포 의무 차이를 제품 아키텍처와 결합 방식 기준으로 판단한다.

| 배포 리스크 판단 확인 | 정적 링크, 수정 배포, SaaS, NOTICE | 내부 사용과 외부 배포 조건 혼동 |

> 요약: 이 문제는 라이선스 설명보다 제품 배포 조건별 의무 판단을 요구한다.

## Ⅰ. 개요 및 필요성

소프트웨어 라이선스는 코드 사용 조건이다. 오픈소스 사용량이 늘면서 제품 하나에 수백 개 의존성이 포함된다. 라이선스 검토 없이 배포하면 GPL 소스 공개, Apache NOTICE, MIT 고지 의무를 놓쳐 법무·영업 리스크가 발생한다.

---

## Ⅱ. 구조 및 구성요소

```text
Source Component -> License Identification -> Obligation Analysis
-> Approval Policy -> Notice/Source Offer -> Product Release
-> Audit Evidence
```

| 구성요소 | 역할 | 특이사항 |
|:---|:---|:---|
| MIT License | 저작권 고지와 라이선스 문구 보존 | permissive, 조건 최소 |
| Apache License 2.0 | 저작권 고지, NOTICE, 특허 허여 | patent grant, termination |
| GPL | 파생저작물 배포 시 동일 라이선스 적용 | strong copyleft, source offer |
| License Policy | 사용 금지·검토·허용 등급화 | 예: GPL 서버 배포 별도 승인 |

> 요약: 라이선스 판단은 유형별 의무와 제품 배포 방식의 결합으로 결정된다.

## Ⅲ. 동작원리 및 흐름도

```text
의존성 수집 -> 라이선스 자동 식별 -> 수동 검토
-> 제품 결합 방식 판단 -> 의무 산출물 생성
-> 법무 승인 -> 배포 후 증적 보관
```

| 단계 | 처리 내용 | 검증 기준 |
|:---:|:---|:---|
| 1 | 패키지와 transitive dependency 수집 | SBOM 생성률 100% |
| 2 | 라이선스 SPDX 식별 | unknown license 0건 |
| 3 | GPL·AGPL·상용금지 조항 검토 | high risk 승인 100% |
| 4 | NOTICE, LICENSE, source offer 포함 | 배포 산출물 누락 0건 |

> 요약: 라이선스 준수는 식별, 의무 판단, 승인, 고지 산출물의 순서로 진행된다.

## Ⅳ. 특징

| 구분 | MIT | Apache-2.0 | GPL |
|:---|:---|:---|:---|
| 유형 | permissive | permissive+patent | copyleft |
| 주요 의무 | 저작권·라이선스 고지 | NOTICE, 특허 허여, 변경 고지 | 소스 공개, 동일 라이선스 |
| 제품 영향 | 상용 제품 포함 가능 | 특허 조항 확인 필요 | 배포 모델·링크 방식 검토 |
| 판단 수치 | 고지 누락 0건 | NOTICE 포함 100% | GPL 승인 100% |

> 요약: MIT와 Apache는 고지 중심, GPL은 배포 시 소스 공개와 동일 조건 적용 여부가 판단 축이다.

> 요약: 라이선스 관리는 사후 검토보다 개발 pipeline에서 자동 식별·승인하는 구조가 필요하다.

> 요약: 라이선스 리스크는 copyleft, 고지, 특허 조항이며 정책과 자동 산출물로 통제한다.

> 요약: 준수 수준은 식별률, 승인 기록, 배포 산출물 포함률로 측정한다.

## Ⅵ. 실무 적용 및 결론

**적용 방안 3개 (필수 — 단계별 또는 항목별):**
1. SCA 도구로 npm, Maven, PyPI 의존성을 SPDX 기준으로 식별하고 unknown license 0건 전 릴리스 차단
2. 라이선스를 허용(MIT/BSD), 검토(Apache/MPL/LGPL), 제한(GPL/AGPL/상용금지) 3등급으로 정책화
3. 제품 배포물에 LICENSE, NOTICE, source offer, SBOM을 포함하고 릴리스별 증적을 3년 이상 보관

**결론 (2줄):**
- 기술사 판단: 내부 사용은 위험이 작지만 외부 배포 제품은 GPL·AGPL·특허 조항을 법무 승인 대상으로 지정
- 향후 방향: 라이선스 관리는 SBOM, SCA, 공급망 보안, VEX와 통합된 릴리스 거버넌스로 확장
