## 미리 알고가기

- 서킷 브레이커는 실패가 누적될 때 하위 호출을 잠시 차단하는 회복성 패턴임
- Closed, Open, Half-open은 호출 허용과 차단을 제어하는 대표 상태임
- Bulkhead는 장애가 한 자원 풀을 넘어 번지지 않게 격리하는 방식임

## Ⅰ. 개요

- **정의/개념**: 서킷 브레이커 패턴은 외부 서비스 호출 실패가 일정 기준을 넘으면 하위 호출을 일시 차단하고, 일정 시간이 지난 뒤 제한적으로 재시도해 장애 전파를 줄이는 회복성 제어 패턴임.
- **배경/필요성**: 분산 환경에서는 느린 하위 서비스 하나가 스레드 고갈과 재시도 폭증을 일으켜 전체 장애로 번질 수 있으므로, 실패를 빨리 끊고 복구 여부를 신중히 확인하는 보호 장치가 필요함.

## Ⅱ. 특징

- 장애 서비스로 향하는 불필요한 호출을 줄여 자원 고갈을 막음
- 상태 전이 기반으로 차단과 복구 확인을 체계적으로 제어함
- timeout, retry, bulkhead, fallback과 함께 설계할 때 효과가 커짐
- 임계치가 부정확하면 정상 서비스도 과도하게 차단할 수 있음

## Ⅲ. 종류 및 비교

| 구분 | 단순 재시도 | 서킷 브레이커 |
|:---|:---|:---|
| 실패 대응 방식 | 오류가 나도 같은 호출을 계속 다시 시도함 | 실패가 누적되면 일정 시간 호출 자체를 막음 |
| 호출 영향 | 재시도 횟수만큼 하위 호출과 대기 자원 증가 | Open 상태에서 하위 호출을 차단해 대기 자원 점유 제한 |
| 주요 위험 | 장애 시 요청 폭주가 더 심해질 수 있음 | 임계치가 맞지 않으면 과차단이나 복구 지연이 생길 수 있음 |
| 적용 조건 | 재시도로 회복 가능한 일시 오류 | 하위 장애가 상위 스레드·연결 풀을 고갈시키는 호출 경로 |

> 요약: 서킷 브레이커는 실패를 더 많이 시도하는 방식이 아니라 실패가 번지는 경로를 끊는 방식임.

## Ⅳ. 구성요소 및 구조

| 구성요소 | 설명 |
|:---|:---|
| Failure Counter | 오류율과 timeout 횟수를 집계해 차단 여부 판단 기준을 제공함 |
| State Machine | Closed, Open, Half-open 상태를 관리해 호출 허용과 차단을 결정함 |
| Fallback Logic | 차단 중에도 기본 응답이나 대체 흐름을 제공해 사용자 영향을 줄임 |
| Recovery Probe | Half-open 상태에서 제한된 요청만 통과시켜 실제 복구 여부를 점검함 |

## Ⅴ. 원리 및 절차 흐름도

```text
+-------------+     +-------------+     +-------------+     +-------------+
| 호출 시도      | --> | 실패율 판단    | --> | 차단 또는 통과  | --> | 복구 재확인    |
+-------------+     +-------------+     +-------------+     +-------------+
```

1. **호출 시도**: 상위 서비스가 하위 서비스 호출을 시작함
2. **실패율 판단**: timeout과 오류 횟수를 누적해 임계치를 확인함
3. **차단 또는 통과**: 임계치를 넘으면 Open 상태로 바꿔 호출을 차단함
4. **복구 재확인**: 일정 시간이 지난 뒤 Half-open 상태에서 제한 호출로 복구 여부를 점검함

## Ⅵ. 실무 적용 및 유의점

1. 결제나 외부 API 연동처럼 하위 장애가 바로 상위 장애로 번지는 호출에서는 서킷 브레이커를 적용하되 타임아웃과 격리 풀을 함께 두지 않으면 보호 효과가 약하므로 서비스별 임계치를 분리 운영하고 차단 동작 발생 비율과 스레드 풀 포화율로 확인함
2. 사용자 대체 응답이 필요한 채널 서비스에서는 대체 응답을 함께 설계하되 업무 의미와 맞지 않는 응답을 내보내지 않도록 도메인별 정책을 정의하고 잘못된 대체 응답 건수와 대체 응답 적합률로 확인함

## Ⅶ. 결론

서킷 브레이커는 장애를 숨기는 장치가 아니라 실패가 전체 시스템으로 번지는 경로를 끊는 회복성 제어 장치임.
