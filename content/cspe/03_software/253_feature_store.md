# 📖 【암기용】 개념 완전 이해

> 목적: 피처 스토어를 처음 보는 사람도 완벽히 이해하게 만든다. 시험 답안 양식이 아니라, 이해를 위한 친절한 설명이다.

## 한눈에
- **개요**: 피처 스토어는 ML 모델이 사용하는 피처를 표준 정의, 저장, 재사용, 서빙하는 중앙 저장소다.
- **왜 필요한가**: 학습 때 계산한 피처와 운영 추론 때 계산한 피처가 다르면 모델 예측이 흔들린다. 팀마다 피처를 따로 만들면 중복과 품질 차이가 커진다.
- **핵심 직관**: 모델이 먹는 재료를 공용 레시피와 냉장고로 관리해 학습과 추론이 같은 재료를 쓰게 하는 장치다.

## 깊이 이해
- **배경·문제의식**: 추천, 신용평가, 이상탐지 모델은 사용자 행동 집계, 최근 거래 수, 평균 금액 같은 피처를 반복 사용한다. 피처 정의가 흩어지면 재현성과 감사가 어렵다.
- **작동 원리**: 배치 데이터에서 피처를 계산해 Offline Store에 저장하고, 실시간 추론용 최신 값은 Online Store에 둔다. 피처 정의와 메타데이터는 Registry에서 관리한다.
- **비유**: 여러 요리사가 각자 양념장을 만드는 대신 중앙 주방에서 표준 양념장을 만들어 레시피와 유통기한을 붙여 공급하는 방식이다.
- **구체 예시**: `user_7d_purchase_count`는 7일 구매 건수로 정의하고, 학습용 Parquet과 온라인 Redis에 같은 변환 로직으로 적재한다.
- **흔한 오해·주의점**: 피처 스토어는 단순 DB가 아니다. point-in-time join, 피처 신선도, lineage, 접근권한이 빠지면 학습·추론 일관성을 보장하지 못한다.

## 연결 개념
- MLOps 파이프라인: 피처 생성과 학습 자동화 연결
- 데이터 드리프트: 피처 분포 변화 감시
- 데이터 거버넌스: 소유자, 계보, 접근통제 관리

# 📝 【답안용】 시험 답안 템플릿

> 목적: 시험장에서 25분에 그대로 쓰는 답안 양식. 작성방식(추상표현 금지·수치·도식·문제유형 전환)을 엄격히 지킨다.
> 핵심: 피처 스토어 답안은 Offline/Online Store, 피처 정의, point-in-time join, 학습·추론 일관성을 반드시 연결한다.

## 핵심 인사이트 (3줄 요약)

> 1. **본질**: 피처 스토어는 ML 피처를 정의, 생성, 저장, 검색, 재사용하는 중앙 관리 계층이다.
> 2. **가치**: 학습과 추론의 피처 불일치를 줄이고 피처 중복 개발, 계보 추적, 접근통제 문제를 해결한다.
> 3. **판단 포인트**: 배치 학습용 Offline Store와 저지연 추론용 Online Store의 일관성, 신선도, 권한을 함께 설계해야 한다.

## 출제 의도 및 답안 포인트

| 출제 의도 | 반드시 짚을 핵심 | 감점 회피 포인트 |
|:---|:---|:---|
| ML 데이터 운영 이해 확인 | Feature Registry, Offline Store, Online Store | 피처를 단순 컬럼으로만 설명 |
| 학습·추론 일관성 판단 | point-in-time join, training-serving skew | Redis 캐시와 동일시 |
| 거버넌스 확인 | 소유자, lineage, PII 접근권한 | 피처 재사용 장점만 나열 |

> 요약: 피처 스토어는 모델 성능보다 피처 정의와 서빙 일관성을 묻는 문제다.

---

## Ⅰ. 개요 및 필요성

- 개요: 피처 스토어는 ML 피처 중앙 관리 플랫폼이다.
- 배경: 모델 품질은 피처 정의와 품질에 직접 영향을 받으며, 학습·추론 피처 불일치는 예측 오류를 만든다.
- 필요성: 피처 정의, 저장, 재사용, 권한, 계보를 통합 관리해 학습·추론 일관성을 확보해야 한다.

---

## Ⅱ. 구조 및 구성요소

```text
Raw Data -> Feature Engineering -> Feature Registry -> Offline Store -> Training
                                      / Online Store -> Real-time Serving
                                      / Monitoring
```

| 구성요소 | 역할 | 통제 기준 |
|:---|:---|:---|
| Feature Registry | 피처 정의, 소유자, 버전 관리 | 이름 규칙, 데이터 타입 |
| Offline Store | 학습과 배치 추론용 피처 저장 | Parquet, Delta, BigQuery |
| Online Store | 실시간 추론용 피처 제공 | Redis, DynamoDB, Cassandra |
| Feature Pipeline | 배치·스트림 피처 생성 | Airflow, Spark, Flink |

> 요약: 피처 스토어는 정의 관리, 배치 저장, 온라인 제공, 생성 파이프라인을 묶어 피처 생명주기를 통제한다.

---

## Ⅲ. 동작원리 및 흐름도

```text
피처 정의 등록 -> 원천 데이터 처리 -> Offline 적재 -> Online 동기화 -> 학습/추론 호출 -> 품질 감시
```

| 단계 | 처리 내용 | 검증 기준 |
|:---:|:---|:---|
| 1 | 피처 이름, 타입, 계산 로직 등록 | 소유자, SLA, 민감정보 태그 |
| 2 | 배치·스트림으로 피처 계산 | null rate, freshness |
| 3 | 학습 데이터 point-in-time join 생성 | leakage 0건 |
| 4 | 온라인 추론 API로 피처 조회 | p95 조회 10ms, hit rate 99% |

> 요약: 피처 스토어는 같은 정의에서 학습 데이터와 온라인 피처를 생성해 training-serving skew를 줄인다.

---

## Ⅳ. 특징

| 구분 | 개별 피처 개발 | 피처 스토어 | 판단 포인트 |
|:---|:---|:---|:---|
| 정의 | 모델별 SQL·코드 분산 | Registry 기반 표준 정의 | 재사용률 측정 |
| 저장 | 학습 데이터셋에 종속 | Offline/Online 분리 | 지연과 신선도 동시 고려 |
| 통제 | 담당자 문서 의존 | lineage, 권한, 품질 지표 | 감사 대상 피처 관리 |

> 요약: 피처 스토어는 피처를 모델 내부 산출물이 아니라 조직 공용 데이터 제품으로 관리한다.

## Ⅴ. 심화 비교 및 적용 판단

| 비교 축 | 기존/대안 | 피처 스토어 | 선택 기준 |
|:---|:---|:---|:---|
| 구조 | 모델별 ETL | 중앙 Registry와 Store | 모델 5개 이상 피처 공유 |
| 비용/성능 | 중복 계산 | 재사용, 캐시, 온라인 조회 | 피처 재사용률 30% 이상 |
| 운영/위험 | 스키마 변경 전파 누락 | 버전, lineage, 알림 | 규제·PII 피처 포함 |

> 요약: 다수 모델이 같은 피처를 쓰거나 온라인 추론 지연 기준이 있으면 피처 스토어를 선택한다.

| 리스크 | 원인 | 대응 방안 | 확인 지표 |
|:---|:---|:---|:---|
| 데이터 누수 | 미래 시점 데이터 조인 | point-in-time join 강제 | leakage 테스트 통과 |
| 피처 신선도 저하 | 스트림 지연, 배치 실패 | freshness SLA, 재처리 큐 | feature age |
| 권한 위반 | 민감 피처 무단 사용 | RBAC, column tag, 승인 | 접근 거부 이벤트 |

> 요약: 피처 스토어 리스크는 데이터 누수, 신선도, 권한이며 시간 기준 조인과 접근통제로 통제한다.

| 점검 항목 | 목표 기준 | 측정 방법 |
|:---|:---|:---|
| 일관성 | 학습·추론 피처 정의 100% 동일 | Registry diff |
| 조회 성능 | 온라인 p95 10ms, hit rate 99% | API 로그, APM |
| 품질 | null rate 1% 이하, freshness SLA 준수 | 데이터 품질 리포트 |

> 요약: 피처 스토어 운영 평가는 정의 일관성, 온라인 조회 지연, 품질 SLA로 판단한다.

---

## Ⅵ. 실무 적용 및 결론

**적용 방안 3개:**
1. Feast, Tecton, Vertex AI Feature Store 중 환경에 맞는 도구를 선정하고 Registry에 피처 소유자와 버전을 등록함
2. Offline Store는 Parquet/Delta, Online Store는 Redis/DynamoDB로 구성하고 p95 조회 10ms 기준을 설정함
3. point-in-time join 테스트, null rate 1% 이하, freshness SLA 위반 알림을 CI와 모니터링에 연결함

**결론 (2줄):**
- 기술사 판단: 실시간 추론과 다수 모델 피처 공유가 있으면 피처 스토어를 도입하고, 단일 배치 모델은 Registry부터 적용함
- 향후 방향: 피처 스토어는 데이터 계약, 모델 모니터링, AI 거버넌스와 결합해 ML 데이터 제품 관리 체계로 확장됨
