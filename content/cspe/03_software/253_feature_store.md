# 📖 【암기용】 개념 완전 이해

> 목적: 피처 스토어를 처음 보는 사람도 완벽히 이해하게 만든다. 시험 답안 양식이 아니라, 이해를 위한 친절한 설명이다.

## 한눈에
- **개요**: 피처 스토어는 ML 모델의 입력값인 **피처(Feature)**를 정의·저장·서빙하는 중앙 저장소로, **학습(Offline)과 추론(Online)이 항상 같은 피처 값을 쓰도록 보장**하는 MLOps 데이터 계층이다.
- **왜 필요한가**: 같은 피처라도 학습 파이프라인(배치 Spark job)과 서빙 API(실시간 코드)가 계산 로직을 각자 따로 구현하면, 반올림·시간대·결측치 처리 같은 사소한 차이만으로도 학습 때 본 값과 운영에서 보는 값이 달라진다. 이 불일치를 training-serving skew라 하며 모델 성능 저하의 대표 원인이다.
- **핵심 직관**: 여러 요리사가 각자 양념장을 담그지 않고, 중앙 주방에서 표준 레시피로 만든 양념장을 학습용 창고(Offline)와 즉석 조리대(Online) 양쪽에 똑같이 공급하는 방식이다.

## 핵심 용어 정리 (내부에 등장하는 것들)

| 용어 | 의미 | 비유 |
|:---|:---|:---|
| 피처 엔지니어링 (상위 개념) | 원본 데이터를 모델이 학습할 수 있는 입력값으로 가공하는 과정 — 피처 스토어가 관리하는 결과물 | 식재료를 손질해 반찬으로 만드는 과정 |
| Feature Registry | 피처의 이름·타입·계산 로직·소유자·버전을 등록하는 메타데이터 카탈로그 | 레시피 북(재료 목록+조리법) |
| Offline Store | 배치로 계산한 대용량 피처 이력을 저장(학습·배치추론용). Parquet, BigQuery 등 | 재고 창고 |
| Online Store | 실시간 서빙을 위해 "지금 값"만 저장하는 저지연 KV DB(Redis, DynamoDB) | 즉석 조리대 냉장고 |
| Feature Pipeline | 원천 데이터에서 피처를 계산해 Offline/Online에 동일 로직으로 적재하는 배치·스트림 작업 | 조리 공정 |
| Point-in-time Join | 학습 데이터를 만들 때 레이블이 발생한 "그 시점" 기준으로, 그 이전에 존재했던 피처 값만 결합하는 기법 | 사건 당일자 신문만 스크랩 |
| Training-Serving Skew | 학습 때 계산한 피처 값과 운영 추론 때 계산한 피처 값이 어긋나는 현상 | 다른 저울로 잰 몸무게 |
| Feature Freshness(신선도) | 온라인 피처가 최신 실제 상태를 얼마나 지연 없이 반영하는가 | 우유 유통기한 |
| Lineage(계보) | 이 피처가 어떤 원본 테이블·코드·버전에서 만들어졌는지 추적하는 정보 | 족보 |

## 깊이 이해

### 왜 생겨났나 — training-serving skew의 실제 모습
대출 승인 모델이 `user_7d_avg_txn_amount`(최근 7일 평균 거래액)를 피처로 쓴다고 하자. 데이터 과학자는 학습 시 Spark 배치로 이 값을 계산하고, 백엔드 개발자는 운영 API에서 별도 SQL로 "최근 7일" 평균을 즉석 계산한다. 두 로직이 "7일"의 기준(UTC vs KST, 당일 포함 여부)만 달라도 값이 어긋난다. 오프라인 검증에서는 AUC 0.85로 잘 나왔지만, 운영에서는 입력값 자체가 미묘하게 달라 AUC가 0.78까지 떨어지는 식으로 나타난다. 피처 스토어는 이 계산 로직을 Feature Pipeline 한 곳에서만 정의해 Offline·Online에 동일하게 적재함으로써 이 격차를 없앤다.

### Offline / Online 두 저장소로 나누는 이유 — 갱신주기와 지연이 다르다
Offline Store는 학습에 쓸 대량 이력을 다루므로 배치(예: 1일 1회) 갱신에 최적화된 컬럼형 저장소(Parquet, BigQuery)를 쓴다. 반면 온라인 추론은 요청마다 수 ms 안에 최신 피처를 조회해야 하므로 Online Store는 KV 구조의 저지연 DB(Redis, DynamoDB)를 쓴다. 목표 수치 예: Online 조회 p95 10ms 이하, hit rate 99% 이상. 두 저장소가 같은 Feature Pipeline에서 나온 같은 값을 담아야 skew가 사라진다.

### Point-in-time Join — 데이터 누수를 막는 핵심 원리
학습 데이터셋을 만들 때 가장 흔한 실수는 "지금 시점 기준 최신 피처"를 레이블에 그냥 붙이는 것이다. 예: 사용자가 2026-06-15에 대출을 신청해 부도 여부(레이블)가 확정됐다면, `user_7d_avg_balance` 피처는 반드시 2026-06-08~06-14(신청 이전 7일) 데이터로만 계산해야 한다. 실수로 06-16 이후 데이터(신청 이후, 즉 미래 정보)까지 포함하면 데이터 누수(leakage)가 발생해 오프라인 성능(예: AUC 0.95)이 비정상적으로 높게 나오지만, 실제 서비스에는 그 미래 정보가 없으므로 이 성능은 재현되지 않는다. Point-in-time join은 각 레이블의 타임스탬프 기준으로 "그 이전"에 존재했던 값만 골라 붙이는 조인 방식으로 이 누수를 원천 차단한다.

### 판별·선택 기준 — 언제 피처 스토어가 필요한가
모델이 1~2개뿐이고 배치 추론만 한다면 피처 스토어 없이도 운영 가능하다. 그러나 (1) 3개 이상 모델이 같은 피처(예: 사용자 7일 구매건수)를 재사용하거나, (2) 실시간 추론이 필요해 온라인 조회가 요구되거나, (3) 규제상 피처의 계보·접근권한 감사가 필요하면 피처 스토어 도입이 정당화된다.

## 연결 개념
- 피처 엔지니어링(상위 개념) — 피처 스토어는 그 산출물을 저장·서빙하는 계층
- MLOps 파이프라인: 피처 생성과 학습 자동화 연결
- 데이터 드리프트(256) — 피처 분포 변화 감시가 피처 스토어의 모니터링과 맞닿음

# 📝 【답안용】 시험 답안 템플릿

> 목적: 시험장에서 25분에 그대로 쓰는 답안 양식. 작성방식(추상표현 금지·수치·도식·문제유형 전환)을 엄격히 지킨다.
> 핵심: 피처 스토어 답안은 Offline/Online Store, 피처 정의, point-in-time join, 학습·추론 일관성을 반드시 연결한다.

## 핵심 인사이트 (3줄 요약)

> 1. **본질**: 피처 스토어는 ML 피처를 정의, 생성, 저장, 검색, 재사용하는 중앙 관리 계층이다.
> 2. **가치**: 학습과 추론의 피처 불일치를 줄이고 피처 중복 개발, 계보 추적, 접근통제 문제를 해결한다.
> 3. **판단 포인트**: 배치 학습용 Offline Store와 저지연 추론용 Online Store의 일관성, 신선도, 권한을 함께 설계해야 한다.

## 출제 의도 및 답안 포인트

| 출제 의도 | 반드시 짚을 핵심 | 감점 회피 포인트 |
|:---|:---|:---|
| ML 데이터 운영 이해 확인 | Feature Registry, Offline Store, Online Store | 피처를 단순 컬럼으로만 설명 |
| 학습·추론 일관성 판단 | point-in-time join, training-serving skew | Redis 캐시와 동일시 |

> 요약: 피처 스토어는 모델 성능보다 피처 정의와 서빙 일관성을 묻는 문제다.

## Ⅰ. 개요 및 필요성

- 개요: 피처 스토어는 ML 피처 중앙 관리 플랫폼이다.
- 배경: 모델 품질은 피처 정의와 품질에 직접 영향을 받으며, 학습·추론 피처 불일치는 예측 오류를 만든다.
- 필요성: 피처 정의, 저장, 재사용, 권한, 계보를 통합 관리해 학습·추론 일관성을 확보해야 한다.

---

## Ⅱ. 구조 및 구성요소

```text
Raw Data -> Feature Engineering -> Feature Registry -> Offline Store -> Training
                                      / Online Store -> Real-time Serving
                                      / Monitoring
```

| 구성요소 | 역할 | 통제 기준 |
|:---|:---|:---|
| Feature Registry | 피처 정의, 소유자, 버전 관리 | 이름 규칙, 데이터 타입 |
| Offline Store | 학습과 배치 추론용 피처 저장 | Parquet, Delta, BigQuery |
| Online Store | 실시간 추론용 피처 제공 | Redis, DynamoDB, Cassandra |
| Feature Pipeline | 배치·스트림 피처 생성 | Airflow, Spark, Flink |

> 요약: 피처 스토어는 정의 관리, 배치 저장, 온라인 제공, 생성 파이프라인을 묶어 피처 생명주기를 통제한다.

---

## Ⅲ. 동작원리 및 흐름도

```text
피처 정의 등록 -> 원천 데이터 처리 -> Offline 적재 -> Online 동기화 -> 학습/추론 호출 -> 품질 감시
```

| 단계 | 처리 내용 | 검증 기준 |
|:---:|:---|:---|
| 1 | 피처 이름, 타입, 계산 로직 등록 | 소유자, SLA, 민감정보 태그 |
| 2 | 배치·스트림으로 피처 계산 | null rate, freshness |
| 3 | 학습 데이터 point-in-time join 생성 | leakage 0건 |
| 4 | 온라인 추론 API로 피처 조회 | p95 조회 10ms, hit rate 99% |

> 요약: 피처 스토어는 같은 정의에서 학습 데이터와 온라인 피처를 생성해 training-serving skew를 줄인다.

## Ⅳ. 특징

| 구분 | 개별 피처 개발 | 피처 스토어 | 판단 포인트 |

> 요약: 피처 스토어는 피처를 모델 내부 산출물이 아니라 조직 공용 데이터 제품으로 관리한다.

## Ⅴ. 심화 비교 및 적용 판단

| 구분 | 기존/대안 | 피처 스토어 | 선택 기준 |
|:---|:---|:---|:---|
| 구조 | 모델별 ETL | 중앙 Registry와 Store | 모델 5개 이상 피처 공유 |
| 비용/성능 | 중복 계산 | 재사용, 캐시, 온라인 조회 | 피처 재사용률 30% 이상 |
| 운영/위험 | 스키마 변경 전파 누락 | 버전, lineage, 알림 | 규제·PII 피처 포함 |

> 요약: 다수 모델이 같은 피처를 쓰거나 온라인 추론 지연 기준이 있으면 피처 스토어를 선택한다.

| 리스크 | 원인 | 대응 방안 | 확인 지표 |
|:---|:---|:---|:---|
| 데이터 누수 | 미래 시점 데이터 조인 | point-in-time join 강제 | leakage 테스트 통과 |
| 피처 신선도 저하 | 스트림 지연, 배치 실패 | freshness SLA, 재처리 큐 | feature age |
| 권한 위반 | 민감 피처 무단 사용 | RBAC, column tag, 승인 | 접근 거부 이벤트 |

> 요약: 피처 스토어 리스크는 데이터 누수, 신선도, 권한이며 시간 기준 조인과 접근통제로 통제한다.

| 점검 항목 | 목표 기준 | 측정 방법 |
|:---|:---|:---|
| 일관성 | 학습·추론 피처 정의 100% 동일 | Registry diff |
| 조회 성능 | 온라인 p95 10ms, hit rate 99% | API 로그, APM |
| 품질 | null rate 1% 이하, freshness SLA 준수 | 데이터 품질 리포트 |

> 요약: 피처 스토어 운영 평가는 정의 일관성, 온라인 조회 지연, 품질 SLA로 판단한다.

## Ⅵ. 실무 적용 및 결론

**적용 방안 3개:**
1. Feast, Tecton, Vertex AI Feature Store 중 환경에 맞는 도구를 선정하고 Registry에 피처 소유자와 버전을 등록함
2. Offline Store는 Parquet/Delta, Online Store는 Redis/DynamoDB로 구성하고 p95 조회 10ms 기준을 설정함
3. point-in-time join 테스트, null rate 1% 이하, freshness SLA 위반 알림을 CI와 모니터링에 연결함

**결론 (2줄):**
- 기술사 판단: 실시간 추론과 다수 모델 피처 공유가 있으면 피처 스토어를 도입하고, 단일 배치 모델은 Registry부터 적용함
- 향후 방향: 피처 스토어는 데이터 계약, 모델 모니터링, AI 거버넌스와 결합해 ML 데이터 제품 관리 체계로 확장됨
