# 📖 【암기용】 개념 완전 이해

## 한눈에
- **개요**: **도메인 주도 설계(DDD, Domain-Driven Design)**는 복잡한 소프트웨어를 비즈니스 도메인(영역) 단위로 나누어 설계하는 MSA의 핵심 분해 기법이다.
- **왜 필요한가**: MSA를 도입할 때 "서비스를 얼마나, 어떻게 작게 나눌 것인가?"가 가장 큰 난제다. 테이블 단위로 너무 잘게 쪼개면 네트워크 지연 폭탄을 맞고, 너무 크게 쪼개면 분산된 모놀리스(Distributed Monolith)가 된다.
- **핵심 직관**: 백화점을 층별로 나눌 때 "데이터 구조"가 아니라 "고객의 비즈니스 목적"(남성복, 여성복, 식품관)에 따라 전문화된 경계를 나누는 것.

## 핵심 용어 정리

| 용어/표기 | 의미 | 비유·예 |
|:---|:---|:---|
| 유비쿼터스 언어 | 도메인 전문가와 개발자가 공통으로 사용하는 표준 용어 | 의사와 간호사가 쓰는 공통 의학 용어 |
| 바운디드 컨텍스트 | 특정 도메인 모델이 적용되는 논리적 경계 (이 경계가 마이크로서비스 1개가 됨) | '상품'이 결제팀에선 결제대상, 배송팀에선 박스내용물 |
| 애그리게이트 (Aggregate) | 트랜잭션의 일관성을 유지하기 위해 하나로 묶은 엔티티의 군집 | '주문'과 '주문상세항목' 묶음 |
| 이벤트 스토밍 | 도메인 전문가와 개발자가 모여 비즈니스 이벤트를 포스트잇으로 붙이며 흐름을 파악하는 기법 | 프로젝트 팀 전체의 칠판 브레인스토밍 |

## 깊이 이해
- **배경·문제의식**: 개발자 중심의 DB 테이블 기반 설계나 기능 기반 분해는 비즈니스 로직의 변경에 취약하다. 결합도는 낮추고 응집도를 높이는 가장 이상적인 기준이 바로 "비즈니스 도메인"이라는 깨달음에서 출발했다.
- **작동 원리**: 
  1. 이벤트 스토밍을 통해 비즈니스 흐름과 이벤트를 식별한다.
  2. 도메인 간의 유비쿼터스 언어를 정의하여 의사소통 오류를 없앤다.
  3. 바운디드 컨텍스트(Bounded Context)를 정의하여 컨텍스트 내에서 응집도 높은 모델을 설계한다. 이 바운디드 컨텍스트 단위가 1개의 마이크로서비스 단위로 분할된다.
- **비유**: 한 명의 '사람'이 병원에서는 '환자', 은행에서는 '고객', 학교에서는 '학생'이다. 하나의 통합 DB로 '사람' 테이블을 만들면 모든 부서가 이 테이블을 수정하려다 충돌한다. 부서(바운디드 컨텍스트)별로 각자의 모델을 따로 갖게 분리하는 것이다.
- **구체 예시**: e-커머스 분해 시, '주문 도메인'과 '배송 도메인'을 분리한다. 주문 바운디드 컨텍스트 내의 '주문' 모델은 가격과 결제상태에 집중하고, 배송 바운디드 컨텍스트의 '배송' 모델은 주소와 운송장번호에 집중한다.
- **흔한 오해·주의점**: "DDD는 코딩 기법이나 프레임워크다"라는 오해. DDD는 비즈니스를 이해하고 논리적 경계를 긋는 설계 철학이자 방법론이지 기술 종속적인 코딩 패턴이 아니다.

## 연결 개념
- 마이크로서비스 아키텍처 (MSA) — DDD를 통해 도출된 바운디드 컨텍스트가 물리적 MSA로 구현됨
- 이벤트 소싱 (Event Sourcing) — 도메인 이벤트를 저장소에 기록하는 패턴
- 헥사고날 아키텍처 — DDD의 도메인 모델을 외부 인프라로부터 보호하는 아키텍처

# 📝 【답안용】 시험 답안 템플릿

## 핵심 인사이트 (3줄 요약)

> 1. **본질**: 도메인 주도 설계(DDD)는 비즈니스 도메인 중심의 유비쿼터스 언어와 바운디드 컨텍스트를 통해 복잡한 시스템을 논리적으로 분해하는 방법론이다.
> 2. **가치**: 데이터베이스나 기술 중심이 아닌 비즈니스 가치 중심으로 MSA의 최적의 크기와 서비스 간 경계를 명확하게 식별할 수 있다.
> 3. **판단 포인트**: 이벤트를 추출하는 이벤트 스토밍부터 논리적 모델을 그리는 바운디드 컨텍스트, 그리고 이를 물리적 MSA로 전환하는 일련의 분할 프로세스 정립이 핵심이다.

## 출제 의도 및 답안 포인트

| 출제 의도 | 반드시 짚을 핵심 | 감점 회피 포인트 |
|:---|:---|:---|
| 적절한 MSA 분해 전략과 방법론 이해 | 비즈니스 도메인 중심 분해, Bounded Context, 유비쿼터스 언어 | 분해 전략(DDD) 없이 MSA 구성요소만 나열 |
| 이벤트 스토밍을 통한 실무 적용 역량 | Event Storming 절차(Event -> Command -> Aggregate -> Bounded Context) | 도메인 모델을 ERD(데이터 모델)로 착각하여 서술 |

> 요약: DDD는 MSA를 "어떻게 나눌 것인가"에 대한 해답으로, 비즈니스 경계(Bounded Context)와 서비스 경계를 일치시키는 것이 핵심이다.

---

## Ⅰ. 개요 및 필요성

- 개요: 소프트웨어의 복잡성을 통제하기 위해 비즈니스 도메인 중심으로 시스템의 경계(Bounded Context)를 분할하고 설계하는 아키텍처 방법론
- 배경: 기술 주도의 분할(예: 컨트롤러, 서비스, DB 계층 분리)이나 단일 데이터 모델은 잦은 비즈니스 변경 시 잦은 수정과 높은 결합도 유발
- 필요성: MSA 전환 시 너무 작게(통신 비용 증가) 혹은 너무 크게(모놀리스 잔존) 나누지 않도록, 응집도와 결합도의 최적 분할 기준(비즈니스) 제공 필요

---

## Ⅱ. 구조 및 구성요소

```text
비즈니스 요구 -> 이벤트 스토밍(Event Storming) -> 도메인 모델 식별
                 |
                 +-> Bounded Context 식별 -> Microservice 1:1 매핑 설계
```

| 구성요소 | 역할 | 특이사항 |
|:---|:---|:---|
| 유비쿼터스 언어 | 도메인 전문가와 개발자 간의 의사소통 갭을 줄이는 공통 언어 | 코드 네이밍 규약과 직접 일치 |
| 바운디드 컨텍스트 | 도메인 모델이 유효한 논리적 경계 및 규칙 적용 범위 | 보통 1개의 마이크로서비스로 매핑 |
| 애그리게이트 | 트랜잭션 일관성을 유지하는 엔티티와 값 객체(Value Object)의 묶음 | 하나의 단위로만 CRUD 보장 |
| 컨텍스트 맵 | Bounded Context 간의 관계와 통신 구조를 정의한 지도 | 동기/비동기 통신 설계 근거 |

> 요약: 비즈니스 공통 언어를 바탕으로 도메인의 경계인 바운디드 컨텍스트를 나누고, 이를 트랜잭션 단위인 애그리게이트로 구체화한다.

---

## Ⅲ. 동작원리 및 흐름도 (이벤트 스토밍 기반 분해 절차)

```text
도메인 전문가 협력 -> 1. 도메인 이벤트 도출 -> 2. 커맨드 및 액터 식별
-> 3. 애그리게이트 정의 -> 4. 바운디드 컨텍스트 구획 -> 마이크로서비스 분할
```

- 1단계 [이벤트 도출]: 시스템 내에서 발생한 상태 변화("주문이 생성됨", "결제가 완료됨")를 오렌지색 포스트잇으로 시간순 나열
- 2단계 [커맨드 식별]: 이벤트를 트리거하는 사용자 액션이나 시스템 명령("주문하기", "결제 승인요청")을 파란색 포스트잇으로 부착
- 3단계 [애그리게이트 정의]: 관련된 커맨드와 이벤트를 처리하는 상태 변경의 주체(엔티티 묶음)를 노란색으로 그룹화하여 도출
- 4단계 [컨텍스트 구획]: 연관성 높은 애그리게이트들을 큰 경계선(Bounded Context)으로 묶고, 이를 독립적인 마이크로서비스로 확정

> 요약: 비즈니스 이벤트를 시작으로 커맨드, 애그리게이트를 거쳐 논리적 경계(Bounded Context)를 도출하는 바텀업 방식의 분할 기법이다.

---

## Ⅳ. 특징
- 비즈니스 정렬: 도메인 로직과 비즈니스 요구사항이 아키텍처와 코드 구조에 그대로 반영되어 유지보수성 극대화
- 높은 응집도, 낮은 결합도: 바운디드 컨텍스트 간에는 느슨한 결합을 유지하고, 내부적으로는 강한 응집력을 갖게 하여 독립 배포(Deploy) 최적화
- 데이터 분리 (DB per Service): 하나의 통합 DB(통합 스키마) 모델을 지양하고, 컨텍스트별 독립적인 데이터 모델을 설계하여 자율성 보장

> 요약: 기술 계층이 아닌 도메인 중심으로 응집도를 높여, 마이크로서비스의 철학인 '독립 배포와 자율성'을 가장 정확하게 구현한다.

## Ⅴ. 심화 비교 및 적용 판단

| 비교 축 | 데이터 주도 설계 (Data-Driven) | 도메인 주도 설계 (DDD) | 선택 기준 |
|:---|:---|:---|:---|
| 초점 | 정규화된 테이블 스키마 중심 | 비즈니스 로직과 행위(Event) 중심 | 핵심 비즈니스 복잡도 |
| 모델 분리 | 전사 통합 데이터 모델링 | 컨텍스트별 독립 모델링 보장 | MSA 전환 여부 |
| 의사소통 | ERD 산출물 통한 개발자 중심 | 유비쿼터스 언어를 통한 현업 협업 | 현업 요구사항 변경 빈도 |

> 요약: 데이터 무결성이 최우선인 전통적 레거시 시스템은 데이터 주도 설계를, 비즈니스 민첩성과 MSA 분할이 필요하면 DDD를 선택한다.

**리스크·대응:**
- 너무 작은 단위의 서비스 분할(Nano Service): 네트워크 오버헤드와 분산 트랜잭션 급증 → 트랜잭션 빈도가 높은 애그리게이트는 단일 컨텍스트로 통합
- 도메인 지식 부재: 현업(도메인 전문가) 참여 저조 시 개발자 뇌피셜의 잘못된 경계 생성 → 이벤트 스토밍 워크숍 필수 수행 및 유비쿼터스 언어 사전 정의 명문화

**도입 후 점검 지표:**
- 결합도 점검: 바운디드 컨텍스트 간 동기식 API 호출 비율 (권장 20% 이하, 비동기 이벤트 80% 이상 지향)
- 코드-비즈니스 일치도: 유비쿼터스 언어가 실제 소스코드의 클래스·메서드명에 100% 반영되었는지 코드 리뷰 시 검증

## Ⅵ. 실무 적용 및 결론

**적용 방안 3개:**
1. 분석 단계: 모든 이해관계자(기획, 개발, 운영)가 참여하는 이벤트 스토밍(Event Storming) 워크숍을 통해 시스템 이벤트를 시각적으로 도출
2. 설계 단계: 식별된 바운디드 컨텍스트 간의 관계(Context Map)를 정의하고, 강결합을 막기 위해 Anti-Corruption Layer(ACL) 배치
3. 구현 단계: 헥사고날 아키텍처(포트 앤 어댑터)를 적용하여 인프라 종속성을 제거하고 순수 도메인 모델을 보호하는 MSA 백엔드 구현

**결론 (2줄):**
- 기술사 판단: MSA 전환의 가장 큰 실패 원인은 '잘못 나눈 경계'에 있으므로, 반드시 DDD 기반의 바운디드 컨텍스트 식별이 선행되어야 단일 장애점을 방지할 수 있다.
- 향후 방향: 최근 도메인 모델 설계에 생성형 AI를 활용하여 이벤트 스토밍 결과물로부터 초안 컨텍스트 맵을 자동 생성하는 기법(AI-assisted DDD)이 연구되고 있다.
