# 📖 【암기용】 개념 완전 이해

> 목적: DDD로 정한 경계를 실제 서비스로 쪼개는 절차와 실행 규칙을 처음 봐도 완벽히 이해하게 만든다. 시험 답안 양식이 아니라, 이해를 위한 친절한 설명이다.

## 한눈에
- **개요**: **MSA 분해(Decomposition)**는 043(DDD 개념)에서 정의한 바운디드 컨텍스트를 실제 서비스 단위로 확정하기까지의 **실행 절차**다 — 이벤트 스토밍으로 경계 후보를 찾고, 애그리거트로 트랜잭션 경계를 정하고, 컨텍스트 매핑으로 서비스 간 통신 방식을 정하고, 팀 소유권까지 정렬하는 일련의 작업이다.
- **왜 필요한가**: 바운디드 컨텍스트라는 개념을 알아도 실제로 "이 수십 개 화면과 테이블을 몇 개의 서비스로 나눌 것인가"는 별개의 문제다. 기준 없이 감으로 나누면 서비스가 너무 잘게 쪼개져(과분해) 서비스 간 호출이 폭증하거나, 반대로 너무 크게 묶여 원래 문제(배포 병목)가 재발한다.
- **핵심 직관**: 절차는 "이벤트(무슨 일이 일어났나) 수집 → 경계 후보 클러스터링 → 트랜잭션 단위(애그리거트) 확정 → 서비스 간 관계(컨텍스트 매핑) 확정 → 팀 배정"의 5단계로 좁혀간다.

## 핵심 용어 정리 (내부에 등장하는 것들)

| 용어 | 의미 | 비유 |
|:---|:---|:---|
| 이벤트 스토밍 (Event Storming) | 도메인 이벤트를 포스트잇으로 늘어놓고 클러스터링해 경계 후보를 찾는 워크숍 | 화이트보드에 업무 흐름을 시간순으로 붙이기 |
| 도메인 이벤트 | "~됨"(과거형)으로 표현하는, 업무상 실제 발생한 사건(예: 주문접수됨, 결제승인됨) | 사건 일지의 한 줄 |
| 애그리거트 (Aggregate) | 하나의 트랜잭션에서 일관성을 지켜야 하는 객체들의 묶음, 대표(Root)를 통해서만 접근 | 계약서 한 장에 묶인 관련 조항들 |
| 애그리거트 루트 (Aggregate Root) | 애그리거트 내부로 들어가는 유일한 출입구 역할의 대표 객체 | 부서의 대표 결재자 |
| 컨텍스트 매핑 (Context Map) | 바운디드 컨텍스트끼리의 관계 유형(누가 주도하는가)을 표시한 지도 | 부서 간 갑/을 관계도 |
| Partnership / Customer-Supplier | 컨텍스트 매핑의 관계 유형 — 대등하게 협의(Partnership) vs 한쪽이 요구사항을 정함(Customer-Supplier) | 공동 프로젝트 vs 발주-수주 관계 |
| ACL (Anti-Corruption Layer) | 외부·레거시 모델이 내 도메인으로 오염되어 들어오지 않도록 번역해주는 방어막 | 통역사를 거쳐야만 들어오는 외부 손님 |
| Saga 패턴 | 여러 서비스에 걸친 트랜잭션을 로컬 트랜잭션 체인 + 보상 트랜잭션으로 처리 | 실패하면 이전 단계를 하나씩 되돌리는 절차 |
| Team Topology | 서비스 경계와 팀 소유권을 일치시키는 조직 설계(스트림 정렬 팀 등) | 서비스 1개 = 담당 팀 1개 |

## 깊이 이해

### 1단계 — 이벤트 스토밍: 몇 개를 모아 몇 개로 묶는가
- 참가자(기획자·개발자·QA 등 8~15명)가 시간순으로 업무에서 일어나는 모든 사건을 주황색 포스트잇에 과거형으로 적어 벽에 붙인다. 커머스 시스템이라면 "장바구니담김", "주문접수됨", "결제승인됨", "재고차감됨", "배송시작됨" 등 보통 수십~수백 개(예: 80개)의 이벤트가 나온다.
- 이 80개 이벤트를 시간 흐름과 업무 응집도를 기준으로 묶으면 보통 5~15개의 클러스터(예: 8개)로 수렴한다. 이 클러스터 하나하나가 바운디드 컨텍스트, 곧 서비스의 후보가 된다. 이벤트 개수가 아니라 **"어떤 이벤트들이 같은 트랜잭션·같은 팀 책임 안에서 함께 바뀌는가"**가 클러스터링 기준이다.

### 2단계 — 애그리거트: 트랜잭션 경계를 수치로 판단하기
- 애그리거트는 "한 트랜잭션에서 함께 일관성을 지켜야 하는 최소 단위"다. 잘못 넓게 잡으면 동시성 문제가 생긴다.
- 예: '주문' 애그리거트 안에 '주문 항목'뿐 아니라 '쿠폰 재고'까지 묶어 하나의 트랜잭션으로 처리한다고 하자. 초당 100건의 주문이 같은 쿠폰 1개의 재고 로우를 동시에 잠그면(비관적 락), 락 대기 행렬이 쌓여 평소 50ms이던 응답 시간이 수백 ms~수 초로 늘어질 수 있다. 쿠폰 재고 차감을 별도 애그리거트(별도 서비스)로 분리하고 이벤트로 비동기 처리하면, 주문 트랜잭션은 쿠폰 재고와 무관하게 즉시 커밋된다.
- 원칙: **"1 트랜잭션 = 1 애그리거트 수정"**. 여러 애그리거트를 동시에 갱신해야 하면 그 자체가 "이 둘은 서로 다른 서비스로 분리하고 이벤트로 연결하라"는 신호다.

### 3단계 — 컨텍스트 매핑: 관계 유형으로 통신 방식을 정한다
- 두 컨텍스트가 대등하게 서로 협의하며 함께 진화하면 **Partnership**, 한쪽(예: 결제)이 다른 쪽(PG사 외부 시스템)의 요구사항에 그대로 따라야 하면 **Customer-Supplier** 또는 **Conformist**(순응자) 관계다.
- 외부 시스템의 데이터 모델이 지저분하거나(필드명 불일치, 구식 스키마) 우리 도메인 언어와 다르면, 직접 연결하지 않고 **ACL(부패 방지 계층)**을 하나 세워 외부 모델을 우리 유비쿼터스 언어로 번역한 뒤 받아들인다. 예: PG사가 `stat_cd=1`처럼 숫자 코드로 응답해도, ACL이 이를 우리 도메인의 `PaymentStatus.APPROVED`로 변환해 내부에는 원본 코드가 노출되지 않게 한다.

### 4단계 — 컨텍스트 간 트랜잭션: Saga로 정합성 복구
- 애그리거트 원칙대로 쪼개면 "주문 확정 + 재고 차감 + 결제 승인"을 하나의 DB 트랜잭션으로 묶을 수 없다(서로 다른 서비스, 다른 DB). Saga 패턴은 각 단계를 로컬 트랜잭션으로 순차 실행하고, 중간에 실패하면 이미 끝난 단계를 역순으로 취소하는 **보상 트랜잭션(Compensating Transaction)**을 실행한다.
- 예: 주문 확정(성공) → 재고 차감(성공) → 결제 승인(실패) 순서면, "재고 차감 취소"라는 보상 이벤트를 발행해 앞 단계를 되돌린다. 이 과정에서 이벤트 발행과 DB 커밋을 하나로 묶기 위해 Outbox 패턴(이벤트를 같은 트랜잭션 안의 아웃박스 테이블에 기록한 뒤 별도 프로세스가 발행)을 함께 쓴다.

### 5단계 — 팀 소유권 정렬 (Team Topology)
- 서비스 경계가 팀 경계와 어긋나면(예: 서비스 1개를 3개 팀이 공동 소유) 결국 배포 조율 병목이 되살아난다. 클러스터링으로 얻은 서비스 후보 하나하나에 **정확히 1개의 스트림 정렬 팀(Stream-aligned Team)**을 배정하는 것이 마지막 단계다.

### 비유와 흔한 오해
- **비유**: 이벤트 스토밍은 범죄 수사에서 타임라인 보드에 사건을 순서대로 붙이며 용의자(경계)를 좁혀가는 것과 비슷하다. 사건(이벤트)을 다 붙이고 나서야 어디서 어디까지가 하나의 사건(서비스)인지 보인다.
- **오해**: "애그리거트는 그냥 연관된 테이블 묶음이다" — 아니다. 테이블이 연관되어 있어도 같은 트랜잭션에서 함께 바뀔 필요가 없으면 서로 다른 애그리거트다. 기준은 스키마 연관성이 아니라 **업무 불변식(트랜잭션에서 반드시 함께 지켜야 하는 규칙)**이다.

## 연결 개념
- 043(DDD 개념) — 이 파일이 실행하는 바운디드 컨텍스트·유비쿼터스 언어 개념의 정의는 그 파일 참조
- 042 MSA — 이 절차의 최종 산출물(서비스 경계)이 실제로 배포되는 대상
- 045 서킷 브레이커 — Saga로 연결된 서비스 중 하나가 응답하지 않을 때 장애 전파를 막는 보완 기제

# 📝 【답안용】 시험 답안 템플릿

> 목적: 시험장에서 25분에 그대로 쓰는 답안 양식. 작성방식(추상표현 금지·수치·도식·문제유형 전환)을 엄격히 지킨다.
> 핵심: DDD 기반 분해 답안은 bounded context, aggregate, context map, team topology, 데이터 분리를 한 흐름으로 제시해야 한다.

## 핵심 인사이트 (3줄 요약)

> 1. **본질**: DDD 기반 MSA 분해는 업무 언어와 책임 경계를 bounded context로 나누고 서비스·데이터·팀 소유권을 정렬하는 전략이다.
> 2. **가치**: 변경 영향 범위를 context 내부로 제한하고, 서비스별 독립 배포와 DB per Service의 근거를 제공함.
> 3. **판단 포인트**: aggregate 경계, context map 관계, cross-service transaction 처리 방식이 분해 품질을 결정함.

## 출제 의도 및 답안 포인트

| 출제 의도 | 반드시 짚을 핵심 | 감점 회피 포인트 |
|:---|:---|:---|
| MSA 분해 기준 확인 | bounded context, aggregate, ubiquitous language | 화면·테이블 기준 분해로 설명 |
| 데이터 분리 역량 확인 | DB per Service, event, Saga, Outbox | 공유 DB를 유지한 채 MSA라고 주장 |
| 조직 설계 관점 확인 | stream-aligned team, platform team, ownership | 기술 구조만 쓰고 팀 책임 누락 |

> 요약: 이 문제는 서비스를 몇 개로 쪼개는지가 아니라 업무 경계와 데이터 소유권을 맞추는지를 묻는다.

---

## Ⅰ. 개요 및 필요성

- 개요: 도메인 경계 기반 서비스 분해
- 배경: MSA는 서비스 수가 아니라 변경 이유가 같은 모델을 묶고 다른 모델을 분리하는 경계 품질에 따라 배포 충돌과 데이터 정합성 문제가 달라짐.
- 필요성: Ubiquitous Language, Aggregate, Bounded Context, Context Map으로 서비스 후보와 API 계약을 도출해 변경 결합도와 분산 트랜잭션 수를 줄여야 함.

---

## Ⅱ. 구조 및 구성요소

```text
Business Domain -> Subdomain -> Bounded Context -> Aggregate
                               -> Service Boundary -> DB per Service
Context Map -> API/Event Contract -> Team Ownership
```

| 구성요소 | 역할 | 특이사항 |
|:---|:---|:---|
| Subdomain | 핵심·지원·일반 도메인 구분 | core domain에 설계 역량 집중 |
| Bounded Context | 모델과 용어의 경계 | 같은 단어도 context별 의미 분리 |
| Aggregate | 트랜잭션 불변식 경계 | aggregate root를 통해 변경 |
| Context Map | context 간 의존 관계 표시 | upstream/downstream, ACL, conformist |

> 요약: DDD 분해는 subdomain에서 context를 찾고 aggregate와 데이터 소유권으로 서비스 경계를 확정한다.

---

## Ⅲ. 동작원리 및 흐름도

```text
Event Storming -> 업무 이벤트 수집 -> Command/Policy 도출
-> Bounded Context 후보 도출 -> Aggregate 경계 결정
-> Context Map 작성 -> API/Event 계약 설계
-> Team Ownership과 배포 단위 확정
```

| 단계 | 처리 내용 | 검증 기준 |
|:---:|:---|:---|
| 1 | 도메인 이벤트와 명령 수집 | 핵심 업무 이벤트 30개 이상 도출 |
| 2 | 용어 충돌과 책임 경계 식별 | context별 ubiquitous language 분리 |
| 3 | aggregate와 트랜잭션 경계 결정 | 단일 aggregate transaction 유지 |
| 4 | API/Event contract 설계 | backward compatibility, schema version |
| 5 | 팀 소유권과 CI/CD 매핑 | 서비스 owner 1개 팀 명시 |

> 요약: DDD 분해는 이벤트와 언어를 모아 context를 찾고, aggregate와 팀 소유권으로 실행 가능한 서비스 경계를 만든다.

---

## Ⅳ. 특징

| 구분 | 기술 기준 분해 | DDD 기반 분해 | 수치·판단 포인트 |
|:---|:---|:---|:---|
| 경계 기준 | Controller/Service/DAO 계층 | bounded context, aggregate | 변경 1건당 context 1개 목표 |
| 데이터 | 공유 DB, cross join | DB per Service | 직접 DB 접근 0건 |
| 조직 | 기능별 팀 | stream-aligned team | 서비스 owner 1개 팀 |
| 정합성 | 단일 트랜잭션 의존 | Saga, 이벤트 정합성 | 보상 실패율 1% 이하 |

> 요약: DDD 기반 분해는 기술 계층이 아니라 업무 책임과 데이터 소유권을 기준으로 서비스 경계를 만든다.

## Ⅴ. 심화 비교 및 적용 판단

| 구분 | 기존/대안 | 본 키워드 | 선택 기준 |
|:---|:---|:---|:---|
| 구조 | 테이블 중심 CRUD 서비스 | bounded context 서비스 | 변경 사유가 context 내부에 머무를 때 |
| 비용/성능 | 단일 DB join | API/event 조합 | p95 300ms 초과 호출 경로는 병합 검토 |
| 운영/위험 | 경계 불명확 | context map과 ownership | 공동 owner 서비스 0개 목표 |

> 요약: 서비스 경계는 기술 편의가 아니라 변경 응집도와 팀 소유권으로 검증해야 한다.

| 리스크 | 원인 | 대응 방안 | 확인 지표 |
|:---|:---|:---|:---|
| 과분해 | aggregate를 엔티티 단위로 오해 | event storming 재수행, 서비스 병합 | 서비스당 월 변경 건수 |
| 공유 DB 회귀 | 레거시 join 의존 | CDC, anti-corruption layer, API 전환 | cross DB query 0건 |
| 팀 경계 불일치 | 기능별 조직 유지 | Team Topologies 적용 | 서비스 owner 명확도 100% |

> 요약: DDD 분해 리스크는 과분해와 공유 DB 회귀이며, context map과 owner 지표로 통제한다.

| 점검 항목 | 목표 기준 | 측정 방법 |
|:---|:---|:---|
| 경계 품질 | 변경 1건당 수정 서비스 2개 이하 | issue, pull request 분석 |
| 데이터 독립성 | 서비스별 DB owner 100% | DB 권한, schema ownership 점검 |
| 계약 품질 | breaking change 월 0건 | contract test, schema registry |

> 요약: 분해 품질은 변경 영향, 데이터 소유권, 계약 호환성 지표로 판단한다.

## Ⅵ. 실무 적용 및 결론

**적용 방안 3개 (필수 - 단계별 또는 항목별):**
1. Event storming 워크숍으로 command, event, policy를 수집하고 core/supporting/generic subdomain을 구분함.
2. Bounded context별 aggregate root, DB owner, API/Event contract, SLA를 ADR과 context map으로 문서화함.
3. Consumer-driven contract test, schema registry, OpenTelemetry trace로 context 간 결합과 호출 지연을 측정함.

**결론 (2줄):**
- 기술사 판단: 서비스 경계가 업무 책임과 팀 소유권에 맞으면 MSA 분해를 진행하고, 용어·데이터 경계가 불명확하면 모듈형 모놀리스로 유예함.
- 향후 방향: DDD 분해는 Team Topologies와 플랫폼 자동화를 결합해 조직 구조와 소프트웨어 구조를 함께 설계하는 방향임.
