## 미리 알고가기

- 서비스 분해는 기술 계층이 아니라 변경 이유와 책임 경계를 기준으로 해야 함
- Bounded context는 하나의 모델과 용어가 일관되게 적용되는 범위임
- Context map은 컨텍스트 사이 관계와 통합 방식을 정리한 지도임

## 작성 근거(검토용)

- MSA 분해는 변경 이유, 데이터 소유권, 팀 책임을 같은 서비스 경계에 배치하는 문제로 설명함
- 기술 계층 분해와 DDD 기반 분해는 경계 기준, 초기 분석, 변경 영향, 적용 조건으로 비교함
- 실무 판단은 용어 충돌 건수, 교차 변경 비율, 서비스 소유권 누락, 팀 간 조정 시간으로 구체화함

## Ⅰ. 개요

- **정의/개념**: MSA 분해 전략은 바운디드 컨텍스트와 공통 언어로 비즈니스 책임·데이터 소유·팀 경계를 서비스 단위로 정하는 활동임
- **배경/필요성**: 기술 계층별 분리로 생기는 교차 변경과 서비스 간 조정을 줄이기 위해 도메인 의미에 따른 경계가 필요함

## Ⅱ. 특징

- 서비스 경계가 비즈니스 책임과 함께 정의되어 변경 충돌을 줄임
- 컨텍스트별 데이터 소유와 용어를 분리해 의미 충돌을 줄임
- 초기 경계는 운영 중 발생하는 동시 변경·교차 호출·용어 충돌을 근거로 분할·병합해야 함
- 조직 구조와 팀 책임이 경계 품질에 직접 영향을 줌

## Ⅲ. 종류 및 비교

| 판단 기준 | 기술 계층 분해 | DDD 기반 분해 |
|:---|:---|:---|
| 경계 기준 | 화면, API, DB 같은 기술 층을 기준으로 나눔 | 비즈니스 능력과 도메인 의미를 기준으로 나눔 |
| 초기 분석 | 화면·API·DB 구조로 경계를 정함 | 도메인 탐색과 용어 정리로 경계를 정함 |
| 변경 영향 | 기능이 여러 업무 규칙을 포함하면 교차 변경 증가 | 같은 업무 규칙과 용어를 bounded context 안에 배치 |
| 대표 환경 | 임시 기능 분리·전환 단계 | 여러 업무 규칙과 팀 책임이 공존하는 복합 도메인 |

> 요약: 기술 계층 분해는 화면·API·DB, DDD 기반 분해는 비즈니스 능력·도메인 의미를 경계로 삼음.

## Ⅳ. 구성요소 및 구조

| 구성요소 | 설명 |
|:---|:---|
| 바운디드 컨텍스트 | 같은 용어와 규칙이 유효한 범위로 서비스 경계를 정함 |
| 공통 언어 | 도메인 용어와 의미를 통일해 모델·계약의 해석 차이를 줄임 |
| 도메인 이벤트 | 컨텍스트 사이의 상태 변화를 이벤트로 전달함 |
| 컨텍스트 맵 | 컨텍스트 간 의존 관계와 통합 방식을 표시함 |

> 요약: 바운디드 컨텍스트와 공통 언어로 내부 모델을 묶고 도메인 이벤트·컨텍스트 맵으로 경계 간 관계를 정의함.

## Ⅴ. 원리 및 절차 흐름도

```text
+-------------+     +-------------+     +-------------+     +-------------+
| 도메인 탐색      | --> | 컨텍스트 정의  | --> | 데이터·계약 분리 | --> | 경계 검증·조정 |
+-------------+     +-------------+     +-------------+     +-------------+
```

1. **도메인 탐색**: 핵심 업무 흐름과 용어와 규칙을 식별함
2. **컨텍스트 정의**: bounded context 단위로 경계를 설정함
3. **데이터 및 계약 분리**: 소유 데이터와 API와 이벤트를 분리함
4. **경계 검증 및 조정**: 변경 빈도와 호출 패턴을 보며 경계를 보정함

> 요약: 도메인 용어와 규칙에서 컨텍스트를 찾고 데이터·계약을 분리한 뒤 변경·호출 패턴으로 경계를 조정함.

## Ⅵ. 실무 사례

1. 주문 플랫폼은 주문·결제·배송 컨텍스트를 분리하고 용어 충돌 건수·교차 변경 비율을 확인함
2. 서비스 조직 개편은 컨텍스트별 소유 팀을 지정하고 소유권 누락 건수·팀 간 조정 시간을 확인함

## Ⅶ. 결론

MSA 분해는 변경 이유·데이터 소유·팀 책임을 같은 서비스 경계에 배치해야 함
