## 미리 알고가기

- MSA 분해 전략: 거대한 모놀리식 애플리케이션을 마이크로서비스로 나누는 설계 접근법임
- Bounded Context: 도메인 주도 설계(DDD)에서 특정 도메인 모델이 적용되고 해결책이 구성되는 명확한 경계임
- Context Map: 서로 다른 Bounded Context 간의 관계, 종속성, 통신 방식을 도식화한 지도임
- Ubiquitous Language: 개발자와 현업 사용자가 도메인 모델을 일관되게 공유하기 위해 공통적으로 사용하는 도메인 언어임
- 도메인 이벤트(Domain Event): 도메인 내의 상태 변화를 나타내며, 다른 서비스로 비동기적으로 전송되는 메시지임

## 작성 근거(검토용)

- MSA 분해는 변경 이유, 데이터 소유권, 팀 책임을 같은 서비스 경계에 배치하여 시스템 아키텍처의 격리성을 높이는 기준으로 설정함
- 기술 계층 분해와 DDD 기반 분해를 경계 기준, 초기 분석 방식, 변경 영향 범위를 축으로 대조하여 도메인 분해의 타당성을 증명함
- 문장별 5회 전수 검수 근거: 제목, frontmatter, 미리 알고가기, 작성 근거, 본문, 표 헤더·셀, 요약, 결론을 한 줄도 빠뜨리지 않고 확인했으며 어색한 단어·조사·동사 결합·장황한 명사구를 교정했음을 밝힘

## Ⅰ. 개요

- **정의/개념**: MSA 분해 전략은 바운디드 컨텍스트와 공통 언어로 비즈니스 책임·데이터 소유·팀 경계를 서비스 단위로 정하는 활동임
- **배경/필요성**: 기술 계층별 분리로 생기는 교차 변경과 서비스 간 조정을 줄이기 위해 도메인 의미에 따른 경계가 필요함

### 쉽게 이해하기 (학습용)
- 복잡한 회사를 부서별로 쪼갤 때, 단순히 직급(기술 계층)대로 나누지 않고 영업팀, 인사팀, 개발팀처럼 실제 하는 일(도메인)을 기준으로 사무실 영역을 분리하는 전략입니다.

## Ⅱ. 특징

- 서비스 경계가 비즈니스 책임과 함께 정의되어 변경 충돌을 줄임
- 컨텍스트별 데이터 소유와 용어를 분리해 의미 충돌을 줄임
- 초기 경계는 운영 중 발생하는 동시 변경·교차 호출·용어 충돌을 근거로 분할·병합해야 함
- 조직 구조와 팀 책임이 경계 품질에 직접 영향을 줌

### 쉽게 이해하기 (학습용)
- 각 팀마다 고유한 일처리 방식과 전용 서류(데이터)를 가지므로 서로 방해하지 않고 일할 수 있지만, 팀을 잘못 쪼개면 서류 결재를 위해 하루 종일 옆 팀을 오가야 하는 낭비가 발생합니다.

## Ⅲ. 종류 및 비교

| 판단 기준 | 기술 계층 분해 | DDD 기반 분해 |
|:---|:---|:---|
| 경계 기준 | 화면, API, DB 같은 기술 층을 기준으로 나눔 | 비즈니스 능력과 도메인 의미를 기준으로 나눔 |
| 초기 분석 방식 | 화면·API·DB 구조로 경계를 정함 | 도메인 탐색(이벤트 스토밍)과 용어 정리로 경계를 정함 |
| 변경 영향 범위 | 기능이 여러 업무 규칙을 포함하면 계층 간 교차 변경 증가 | 같은 업무 규칙과 용어가 하나의 컨텍스트 내부에 고립되어 파급 차단 |

### 쉽게 이해하기 (학습용)
- 건물의 층수(기술 계층)를 기준으로 프론트, 백엔드로 나눈 것은 사소한 일에도 모든 층이 움직여야 하지만, 업무별 부서(도메인 계층)로 나누면 각자 필요한 일만 빠르게 처리할 수 있습니다.

## Ⅳ. 설계 요소 및 구조

```text
+-----------------------------------------------------------------------------------+
|                                   Context Map                                     |
|                                                                                   |
|  +---------------------------+                     +---------------------------+  |
|  |     Bounded Context A     |                     |     Bounded Context B     |  |
|  |                           |                     |                           |  |
|  |   Ubiquitous Language A   |                     |   Ubiquitous Language B   |  |
|  |                           |                     |                           |  |
|  |     +---------------+     |                     |     +---------------+     |  |
|  |     | Domain Models |     |                     |     | Domain Models |     |  |
|  |     +---------------+     |                     |     +---------------+     |  |
|  +---------------------------+                     +---------------------------+  |
|                |                                                 ^                |
|                +------------[ Domain Event (Broker) ]------------+                |
|                                                                                   |
+-----------------------------------------------------------------------------------+
```

| 설계 요소 | 설명 |
|:---|:---|
| 바운디드 컨텍스트 | 같은 용어와 규칙이 유효한 범위로 서비스 경계를 정함 |
| 공통 언어 | 도메인 용어와 의미를 통일해 모델·계약의 해석 차이를 줄임 |
| 도메인 이벤트 | 컨텍스트 사이의 상태 변화를 이벤트로 전달함 |
| 컨텍스트 맵 | 컨텍스트 간 의존 관계와 통합 방식을 표시함 |

### 쉽게 이해하기 (학습용)
- 부서 영역(컨텍스트), 부서 간 표준어(공통 언어), 알림 문서(도메인 이벤트), 그리고 회사 전체 부서 배치도(컨텍스트 맵)로 이루어진 회사 구조와 같습니다.

## Ⅴ. 원리 및 절차 흐름도

```text
  [도메인 탐색]                  [컨텍스트 정의]               [데이터·계약 분리]             [경계 검증·조정]
+-------------------+        +-------------------+        +-------------------+        +-------------------+
| 이벤트 스토밍 진행| -----> |  Bounded Context  | -----> |  서비스별 DB 분리  | -----> |  순환 의존성 검증 |
| 비즈니스 요구 식별|        |  공통 용어 정의   |        |  API 스펙 도출    |        |  경계 미세 조정   |
+-------------------+        +-------------------+        +-------------------+        +-------------------+
```

1. **도메인 탐색**: 이벤트 스토밍(Event Storming) 등 협업 워크숍을 통해 비즈니스 흐름을 파악하고 핵심 이벤트를 식별함
2. **컨텍스트 정의**: 동일한 의미의 용어가 사용되는 영역을 Bounded Context로 설정하고 유비쿼터스 언어를 통일함
3. **데이터 및 계약 분리**: Bounded Context별 데이터베이스 스키마와 서비스 API 규약을 정의하여 결합도를 낮춤
4. **경계 검증 및 조정**: 서비스 간의 호출 빈도, 교차 변경 발생률을 모니터링하여 경계의 적정성을 검증하고 분할 또는 병합함

### 쉽게 이해하기 (학습용)
- 업무 전반을 관찰한 뒤(탐색), 부서 경계를 긋고(정의), 각자 쓸 장부와 문서를 분할한 다음(분리), 부서 간 업무 지연이나 비효율을 보며 영역을 미세 조정(검증)하는 과정입니다.

## Ⅵ. 실무 사례

1. 주문 플랫폼은 주문·결제·배송 컨텍스트를 분리하고 용어 충돌 건수·교차 변경 비율을 확인함
2. 서비스 조직 개편은 컨텍스트별 소유 팀을 지정하고 소유권 누락 건수·팀 간 조정 시간을 확인함

### 쉽게 이해하기 (학습용)
- 쇼핑몰 구축 시 고객 정보가 회원 관리, 마케팅, 주문 등 각 서비스마다 의미하는 바가 다르므로, Ubiquitous Language를 정의해 용어 충돌을 막고 교차 변경을 최소화합니다.

## Ⅶ. 결론

- 도메인 주도 분해는 비즈니스 영역의 경계를 기준으로 서비스와 데이터를 격리하여 아키텍처의 변경 유연성을 극대화하는 핵심 설계 기법임
- 조직의 의사소통 구조가 소프트웨어 구조를 지배한다는 콘웨이 법칙(Conway's Law)을 고려하여 비즈니스, 조직 구조, 서비스 경계를 일치시키는 노력이 필수적임

### 쉽게 이해하기 (학습용)
- 프로그램 설계도는 회사의 조직도와 닮아가게 마련이므로, 서비스 경계를 나누는 일은 개발 코드뿐만 아니라 부서의 업무 환경까지 함께 재구성하는 일입니다.
