## 미리 알고가기

- 서비스 분해는 기술 계층이 아니라 변경 이유와 책임 경계를 기준으로 해야 함
- Bounded context는 하나의 모델과 용어가 일관되게 적용되는 범위임
- Context map은 컨텍스트 사이 관계와 통합 방식을 정리한 지도임

## Ⅰ. 개요

- **정의/개념**: MSA 분해 전략은 시스템을 어떤 서비스 경계로 나눌지 정하는 설계 활동이며, DDD는 bounded context와 공통 언어를 이용해 비즈니스 의미 단위로 경계를 찾는 대표 접근임.
- **배경/필요성**: UI, API, DB 같은 기술 계층만 기준으로 자르면 서비스 간 조정 비용이 오히려 커질 수 있으므로, 변경 이유와 데이터 소유와 팀 책임이 맞는 도메인 기준 분해가 필요함.

## Ⅱ. 특징

- 서비스 경계가 비즈니스 책임과 함께 정의되어 변경 충돌을 줄임
- 컨텍스트별 데이터 소유와 용어를 분리해 의미 충돌을 줄임
- 처음부터 완벽한 경계를 찾기 어렵기 때문에 운영 중 보정이 필요함
- 조직 구조와 팀 책임이 경계 품질에 직접 영향을 줌

## Ⅲ. 종류 및 비교

| 구분 | 기술 계층 분해 | DDD 기반 분해 |
|:---|:---|:---|
| 경계 기준 | 화면, API, DB 같은 기술 층을 기준으로 나눔 | 비즈니스 능력과 도메인 의미를 기준으로 나눔 |
| 시작 난이도 | 구조를 빨리 나눌 수 있어 초기 착수는 쉬움 | 도메인 탐색과 용어 정리가 필요해 초기 분석 비용이 듦 |
| 장기 효과 | 서비스 간 결합이 다시 커질 가능성이 높음 | 변경 이유와 책임이 맞아 장기 운영에 유리함 |
| 적합한 환경 | 단순 분리나 임시 전환 작업에 맞음 | 장기 운영형 복합 도메인에 맞음 |

> 요약: MSA 분해는 코드를 기능별로 흩어 놓는 일이 아니라 비즈니스 의미가 다른 경계를 실제 서비스 경계로 만드는 일임.

## Ⅳ. 구성요소 및 구조

| 구성요소 | 설명 |
|:---|:---|
| Bounded Context | 같은 용어와 규칙이 유효한 범위를 정해 서비스 경계 기준을 만듦 |
| Ubiquitous Language | 도메인 용어를 통일해 팀 간 해석 차이와 계약 오류를 줄임 |
| Domain Event | 경계 사이 상태 변화를 이벤트로 표현해 직접 결합을 줄임 |
| Context Map | 컨텍스트 간 관계와 통합 방식을 드러내 의존 구조를 가시화함 |

## Ⅴ. 원리 및 절차 흐름도

```text
+-------------+     +-------------+     +-------------+     +-------------+
| 도메인 탐색      | --> | 컨텍스트 정의  | --> | 데이터/계약 분리 | --> | 경계 검증/조정 |
+-------------+     +-------------+     +-------------+     +-------------+
```

1. **도메인 탐색**: 핵심 업무 흐름과 용어와 규칙을 식별함
2. **컨텍스트 정의**: bounded context 단위로 경계를 설정함
3. **데이터 및 계약 분리**: 소유 데이터와 API와 이벤트를 분리함
4. **경계 검증 및 조정**: 변경 빈도와 호출 패턴을 보며 경계를 보정함

## Ⅵ. 실무 적용 및 유의점

1. 주문·결제·배송처럼 업무 의미가 분명히 다른 영역을 나눌 때는 DDD 기반 분해가 유효하지만 용어가 섞이면 서비스 경계가 무너지므로 컨텍스트 맵과 공통 언어를 함께 관리하고 용어 충돌 건수와 중복 변경 비율로 확인함
2. 조직 재편과 함께 서비스를 나누는 경우에는 팀 책임이 경계와 어긋나면 무단 의존성이 쌓이므로 서비스 소유권을 동시에 조정하고 소유권 명확도와 팀 간 의존 조정 시간으로 확인함

## Ⅶ. 결론

MSA 분해 전략의 성패는 서비스 개수보다 변경 이유와 데이터 소유와 팀 책임이 같은 경계 위에 놓이는지에 달려 있음.
