## 핵심 인사이트 (3줄 요약)
- **CNI(Container Network Interface)**: 수천 개의 파드(Pod)가 서로 통신할 수 있게 IP를 나눠주고 길을 뚫어주는 쿠버네티스의 '네트워크 공사 업체' (플러그인 표준). Calico, Cilium, Flannel 등이 있음.
- **네트워크 정책(NetworkPolicy)**: CNI가 기본적으로 모든 길을 다 뚫어놓는(Any Open) 위험을 막기 위해, "DB 파드는 웹 파드한테만 연락받고 나머지는 다 차단해!"라고 방화벽을 치는 보안 규칙.
- "내부망에 들어왔으니 다 안전하다"는 낡은 생각을 버리고, 파드와 파드 사이의 통신(East-West 트래픽)도 깐깐하게 차단하는 **마이크로 세그멘테이션(Micro-segmentation) 및 제로 트러스트(Zero Trust)**의 핵심 구현체임.

## Ⅰ. 개요 및 필요성
- **개요**: 클러스터 내의 파드 간, 노드 간 통신을 가능하게 하는 네트워크 플러그인 인터페이스(CNI)와, 그 위에서 트래픽의 흐름을 IP/Port 레벨에서 통제하는 방화벽 규칙(NetworkPolicy).
- **필요성**: 쿠버네티스를 처음 설치하면, 1번 노드의 A 파드와 2번 노드의 B 파드가 서로 핑(Ping)이 안 나감. 네트워크가 안 깔려 있기 때문. 그래서 **CNI**라는 네트워크 모듈을 깔면 모든 통신이 뻥 뚫림. 그런데 해커가 웹 파드를 하나 털고 들어오니, 이 웹 파드가 사내 핵심 DB 파드까지 아무 제약 없이 쑥 뚫고 들어감. **"어? 이거 내부망 통신도 방화벽(NetworkPolicy)을 쳐야겠는데?"**라는 보안 니즈가 발생함.
---
## Ⅱ. 아키텍처 및 핵심 원리
- **1. CNI (통신의 기본 인프라)**:
  - 쿠버네티스는 네트워크 기능을 직접 만들지 않고, CNI라는 '규격'만 열어둠.
  - 외부 업체(Calico 등)가 이 규격에 맞춰 플러그인을 설치하면, 파드가 뜰 때마다 Kubelet이 CNI를 호출해서 "얘 IP 좀 줘!"라고 함. 
  - 오버레이(Overlay) 네트워크 기술(VXLAN 등)을 사용하여, 물리적으로 다른 서버(노드)에 있는 파드들이 마치 같은 허브에 꽂힌 것처럼 통신하게 해줌.
- **2. K8s의 기본 네트워크 철학 (Default Allow)**:
  - "모든 파드는 NAT 없이 다른 모든 파드와 통신할 수 있어야 정답."
  - 초기 설정은 완전히 열려있음(기본 허용). 편하지만 보안상 치명적임.
- **3. NetworkPolicy (파드 레벨의 방화벽)**:
  - **Ingress 규칙**: "나(DB 파드)한테 들어올 수 있는 트래픽" 정의 (예: 프론트엔드 라벨을 가진 파드의 3306 포트 접근만 허용).
  - **Egress 규칙**: "나(웹 파드)에서 나갈 수 있는 트래픽" 정의 (예: 외부 인터넷망 코인 채굴 서버로 나가는 트래픽 원천 차단).
  - **Default Deny (기본 차단)**: 실무에서는 특정 네임스페이스에 텅 빈 NetworkPolicy를 걸어서 모든 통신을 싹 막아버린 후, 필요한 길만 화이트리스트(Whitelist) 방식으로 하나씩 열어주는 방식을 씀.

```text
[ 쿠버네티스 내부 해킹 방어 (NetworkPolicy 유무 비교) ]

 🔓 [ NetworkPolicy 없을 때 (Default Allow) ]
 해커 ➡️ [ 웹 서버 (Web Pod) 탈취! ] 
        ⬇️ (아무런 방화벽이 없음)
 [ 핵심 데이터베이스 (DB Pod) ] ➡️ 해커가 고객 정보 싹 다 털어감! 🚨

 🛡️ [ NetworkPolicy 적용 (Micro-segmentation) ]
 해커 ➡️ [ 웹 서버 (Web Pod) 탈취! ]
        ✖️ (NetworkPolicy: "Web은 결제(Pay)랑만 통신 가능해. DB는 접근 금지!")
 [ 핵심 데이터베이스 (DB Pod) ] ➡️ 안전하게 보호됨! 😌
```

## Ⅲ. 비교 및 연결
| 주요 CNI 플러그인 | 특징 및 사용처 | NetworkPolicy 지원 여부 |
|---|---|---|
| **Flannel** | 가장 단순함. 설정이 쉽지만 기능이 빈약함. (테스트용) | 지원 안 함 (방화벽 못 침) |
| **Calico** | 가장 널리 쓰임. BGP 라우팅 등 강력한 기능. | **완벽 지원 (실무 표준)** |
| **Cilium** | 차세대 CNI. eBPF 기술을 써서 커널 레벨에서 초고속 처리. | **지원 및 L7 라우팅까지 가능** |
| **AWS VPC CNI** | AWS EKS의 기본 CNI. 파드에 실제 AWS VPC의 IP를 직접 꽂아줌. | 보안 그룹(Security Group)과 연동 |

## Ⅳ. 실무 적용 및 기술사 판단
- **네임스페이스(Namespace) 격리의 한계와 NetworkPolicy**: 주니어 엔지니어는 쿠버네티스의 'Namespace'를 쪼개면 네트워크도 격리되는 줄 착각함 (예: `dev` 네임스페이스와 `prod` 네임스페이스). 하지만 쿠버네티스는 기본적으로 네임스페이스를 넘나드는 통신을 허용함. 기술사는 반드시 **NetworkPolicy를 작성하여 "dev 파드들은 절대 prod 파드들에게 핑(Ping)조차 보내지 못하도록" 네트워크 단절(Isolation) 설정을 강제해야** 함.
- **eBPF 기반의 차세대 CNI 도입 (Cilium)**: 전통적인 CNI(Calico)는 리눅스의 iptables를 이용해 방화벽 규칙을 짬. 파드가 1만 개가 되면 규칙이 10만 줄이 넘어가면서 트래픽이 멈추는 병목 현상이 생김. 최근 대규모 엔터프라이즈는 리눅스 커널 안에서 빛의 속도로 네트워크 패킷을 제어하는 **eBPF 기반의 Cilium**으로 CNI 생태계를 완전히 옮겨가고 있는 트렌드를 주목해야 함.
---
## Ⅴ. 기대효과 및 결론
- 복잡한 하드웨어 스위치나 라우터 설정 없이, 소프트웨어 코드로 선언적(Declarative) 네트워크 토폴로지를 1초 만에 구성하는 SDN(Software Defined Network)의 결정판.
- 파드라는 가장 작은 단위에 방화벽을 촘촘히 두르는 마이크로 세그멘테이션을 통해, 한 컨테이너가 뚫려도 옆 컨테이너로 감염이 번지지 않는 강력한 제로 트러스트(Zero Trust) 보안 아키텍처를 완성함.

- 도커의 단순 브리지 네트워크 ➡️ 쿠버네티스 도입에 따른 오버레이 네트워크(Flannel) 등장 ➡️ 보안 니즈 폭발로 Calico와 NetworkPolicy(마이크로 세그멘테이션) 대중화 ➡️ iptables 한계 봉착 ➡️ eBPF 기반의 Cilium이 차세대 CNI 표준으로 등극

### 👶 어린이를 위한 3줄 비유 설명
1. 쿠버네티스 마을(클러스터)을 지으면, 처음엔 집(파드)들 사이에 길이 없어서 서로 놀러 갈 수가 없어요.
2. **CNI**라는 도로 공사 업체가 와서 모든 집을 쌩쌩 달릴 수 있는 고속도로로 연결해 줘요! (하지만 도둑도 마음대로 돌아다니는 단점이 생겼죠).
3. 그래서 **네트워크 정책(NetworkPolicy)**이라는 경찰 아저씨를 세워서, "우리 집에는 엄마랑 아빠만 들어올 수 있어!"라고 규칙을 정해서 도둑을 막는 거랍니다.
