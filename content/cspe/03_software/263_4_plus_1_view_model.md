## Ⅰ. 개요
- 정의: 4개의 주요 관점(View)과 1개의 사용 사례(Use Case)로 아키텍처를 기술하는 모델
- 배경: 이해관계자마다 시스템을 보는 관점이 달라 발생하는 소통 격차 해소 필요
- 출제 의도: 각 뷰의 역할, 대상, 산출물에 대한 정확한 구분 및 연관성 이해

## Ⅱ. 구성요소
- 구조도
       [Logical View]     [Process View]
              \          /
               [Use Case View]
              /          \
    [Development View]    [Physical View]

- 구성요소 표
| 뷰 명칭 | 설명 | 대상 |
| :--- | :--- | :--- |
| Logical | 기능적 요구사항, 객체 모델 | 설계자, 고객 |
| Process | 비기능적 속성(성능, 확장성) | 시스템 통합자 |
| Development | SW 모듈 구조, 컴포넌트 | 개발자 |
| Physical | HW 매핑, 배포 구조 | 인프라 엔지니어 |
> 요약: Use Case View가 중심이 되어 나머지 4개 뷰의 정합성을 검증함

## Ⅲ. 절차
- 흐름도
  시나리오 식별 -> 뷰별 설계 -> 뷰 간 통합 -> 아키텍처 검증
- 4단계 설명
1. 시나리오 식별: 시스템의 핵심 가치를 보여주는 Use Case 선정
2. 뷰별 설계: 논리적/물리적/개발/프로세스 관점에서 설계도 작성
3. 뷰 간 통합: 각 뷰 사이의 상호작용 및 매핑 관계 정의
4. 아키텍처 검증: 시나리오를 통해 각 뷰가 요구사항을 충족하는지 테스트
> 요약: 다각도 분석을 통해 아키텍처의 완전성과 품질 확보

## Ⅳ. 문제점
- 특정 뷰에만 치중할 경우 비기능적 요구사항(성능 등) 누락 가능성
- 프로젝트 규모 대비 과도한 문서화로 인한 개발 기민성 저하

## Ⅴ. 개선방안
- 프로젝트 특성에 따라 필수 뷰를 선별하여 경량화된 모델링 수행
- 모델 기반 설계(MBD) 도구 활용으로 뷰 간 자동 동기화 및 가시성 증대

## Ⅵ. 전망
- 인프라 코드화(IaC) 확산에 따라 Physical View와 실제 환경 간의 격차 해소
- CSF: 비즈니스 가치 흐름(Value Stream) 중심의 뷰 통합 및 지속적 업데이트
