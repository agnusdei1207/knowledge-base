# 📖 【암기용】 개념 완전 이해

## 한눈에
- **개요**: 코드 배포 없이 특정 기능의 활성화 여부를 동적으로 제어하는 소프트웨어 개발 기법
- **왜 필요한가**: 기능을 배포하는 것(Deployment)과 고객에게 노출하는 것(Release)을 분리하여 장애 위험을 줄이고 빠른 피드백을 얻어야 함
- **핵심 직관**: 런타임에 작동하는 소프트웨어 스위치

## 핵심 용어 정리

| 용어/표기 | 의미 | 비유·예 |
|:---|:---|:---|
| 배포 (Deployment) | 서버에 코드를 올리는 행위 | 물건을 창고에 들여놓음 |
| 릴리스 (Release) | 사용자에게 기능을 공개하는 행위 | 진열대에 물건을 전시함 |
| 킬 스위치 (Kill Switch) | 장애 발생 시 해당 기능만 즉시 끄는 플래그 | 누전 차단기 |

## 깊이 이해
- **배경·문제의식**: 과거에는 새로운 기능을 배포하려면 모든 코드가 완벽히 준비된 상태여야 했고, 문제가 생기면 전체 시스템을 롤백해야 했음. 이는 배포 주기를 길게 만들고 위험도를 높임.
- **작동 원리**: 코드 내부에 분기문(`if feature_enabled:`)을 심고, 외부 설정 파일이나 원격 플래그 관리 시스템에서 해당 값을 읽어와 런타임에 실행 경로를 결정함.
- **비유**: 놀이공원의 놀이기구 운행 스위치. 기구 자체(코드)는 설치되어 있지만, 중앙 통제실(플래그 서버)에서 스위치를 켜야만 관람객(사용자)이 탑승할 수 있음.
- **구체 예시**: 넷플릭스는 새로운 추천 알고리즘을 1%의 사용자에게만 켜서 반응을 본 뒤, 문제가 없으면 점진적으로 100%까지 늘리는 롤아웃을 수행함.
- **흔한 오해·주의점**: 피처 플래그를 단순히 '개발 편의 기능'으로 오해하기 쉬움. 하지만 플래그를 제때 제거하지 않으면 코드 내 분기문이 기하급수적으로 늘어나 심각한 기술부채(코드 스멜)로 전락함.

## 연결 개념
- **CI/CD, 프로그레시브 딜리버리, 다크 론칭, 기술부채**

# 📝 【답안용】 시험 답안 템플릿

## 핵심 인사이트 (3줄 요약)

> 1. **본질**: 배포와 릴리스를 디커플링하여 런타임 제어권 확보
> 2. **가치**: 무중단 롤아웃, A/B 테스트, 신속한 장애 복구(롤백) 지원
> 3. **판단 포인트**: 플래그 수명 주기 관리(수명 완료 플래그 삭제) 미흡 시 기술부채 급증

## 출제 의도 및 답안 포인트

| 출제 의도 | 반드시 짚을 핵심 | 감점 회피 포인트 |
|:---|:---|:---|
| 프로그레시브 딜리버리 구현 역량 | 배포/릴리스 분리, 런타임 토글, 킬 스위치 | 단순 if문으로 축소 설명 단정 |
| 기술부채 관점의 부작용 이해 | 플래그 수명 주기 관리, 플래그 제거 전략 | 부작용(코드 복잡도 증가) 누락 |

> 요약: 안전한 릴리스를 위한 핵심 기법이되, 생명주기 통제(사후 제거)가 필수적임을 제시함

---

## Ⅰ. 개요 및 필요성

- 개요: 코드 배포 없이 특정 기능의 활성 상태를 런타임에 동적으로 변경하는 소프트웨어 분기 제어 기법임
- 배경: 무중단 배포 환경에서 새 기능 릴리스에 따른 장애 리스크와 롤백 비용이 급증함
- 필요성: 시스템 배포 주기(Deployment)와 비즈니스 공개 주기(Release)를 분리하여 지속적 통합(CI) 효과 극대화 필요

---

## Ⅱ. 구조 및 구성요소

```text
[요구사항] -> [플래그 관리 서버] -> (플래그 상태 전달) -> [애플리케이션(SDK)] -> (분기 실행) -> [사용자 노출]
                 |                                      |
                 +-> 통제(개발자/운영자)                  +-> 관측(이벤트/로그)
```

| 구성요소 | 역할 | 특이사항 |
|:---|:---|:---|
| 토글 라우터 (Toggle Router) | 플래그 상태에 따라 코드 실행 경로 결정 | `if-else` 구조 캡슐화 |
| 토글 컨텍스트 (Toggle Context) | 사용자의 식별자(ID, 지역 등) 정보 | 타겟팅 릴리스 판단 기준 |
| 플래그 저장소 (Store) | 플래그의 활성화 여부 및 메타데이터 저장 | Redis 등 인메모리 활용 |
| 평가 엔진 (Evaluation Engine) | 컨텍스트와 정책을 비교하여 최종 활성 여부 판단 | SDK 내장 또는 원격 API |

> 요약: 관리 서버가 정책을 배포하면 애플리케이션의 라우터가 컨텍스트 기반으로 런타임 분기를 수행함

---

## Ⅲ. 동작원리 및 흐름도

```text
기능 요청 -> 컨텍스트 수집 -> 플래그 상태 평가 -> 활성 기능 분기 -> 결과 반환
```

- 1단계 [기능 요청/컨텍스트 수집]: 사용자 접속 시 ID, 디바이스, 지역 등 컨텍스트 정보 식별
- 2단계 [상태 평가]: 로컬 캐시 또는 플래그 서버에 해당 기능의 토글 정책 질의
- 3단계 [런타임 분기]: 평가 결과(True/False)에 따라 기존 로직 또는 신규 로직으로 실행 경로 라우팅
- 4단계 [결과 반환 및 관측]: 분기된 결과를 반환하고, 해당 플래그 노출 이벤트를 애널리틱스 서버로 전송

> 요약: 사용자 컨텍스트를 기반으로 런타임에 신속하게 상태를 평가하고 실행 경로를 라우팅함

---

## Ⅳ. 특징

- 지속적 통합 지원: 미완성 코드를 메인 브랜치에 병합하더라도 사용자 노출을 차단하여 브랜치 관리 비용 최소화
- 운영 안정성: 장애 발생 시 코드를 롤백할 필요 없이 킬 스위치(Kill Switch)를 통해 즉각적인 복구 가능
- 비즈니스 민첩성: 개발자 개입 없이 기획·운영 부서가 직접 A/B 테스트 및 타겟 사용자 롤아웃 수행 가능
- 복잡도 리스크: 수명이 다한 플래그를 방치할 경우 스파게티 코드가 되어 기술부채로 전환됨

> 요약: 신속한 배포와 안전한 릴리스를 보장하나, 코드 내 분기문 증가로 인한 관리 복잡도가 수반됨

---

## Ⅴ. 심화 비교 및 적용 판단

| 비교 축 | 브랜치 기반 배포 (Feature Branch) | 피처 플래그 기반 배포 | 선택 기준 |
|:---|:---|:---|:---|
| 통합 시점 | 기능 개발 완료 후 (지연 병합) | 개발 중 상시 (지속 병합) | CI/CD 성숙도 |
| 장애 롤백 | 이전 버전으로 재배포 (수 분~수 시간) | 플래그 토글 OFF (즉각) | 서비스 크리티컬리티 |
| 릴리스 제어 | 배포와 릴리스가 1:1 매핑됨 | 사용자 타겟팅 및 점진적 릴리스 | 비즈니스 마케팅 요구 |

> 요약: 무중단 빠른 배포와 점진적 사용자 타겟팅이 필요한 경우 피처 플래그 도입이 필수적임

**리스크·대응:**
- 기술부채 누적: 임시 플래그 방치로 로직 복잡도 증가 → 플래그 생명주기 관리 프로세스 도입 (지표: 만료 플래그 개수)
- 상태 일관성 훼손: 분산 환경에서 서버 간 플래그 상태 불일치 → 캐시 동기화 및 중앙집중형 관리(LaunchDarkly 등) 적용 (지표: 동기화 지연 시간)

---

## Ⅵ. 실무 적용 및 결론

**적용 방안 (생명주기 기반 관리):**
1. 플래그 생성: 단기 토글(릴리스, 실험)과 장기 토글(운영, 권한)을 명확히 구분하여 메타데이터에 수명 만료일 지정
2. 타겟팅 적용: 사내 개발자 1% → 베타 테스터 10% → 전체 100% 순으로 점진적 카나리 롤아웃 수행
3. 플래그 제거: 스프린트 종료 시 또는 기능 100% 롤아웃 2주 후, 만료된 플래그와 데드 코드를 강제 삭제하는 리팩터링 수행

**결론:**
- 기술사 판단: 피처 플래그는 CI/CD 고도화의 핵심 도구이나, '부채 상환(제거)' 프로세스가 없으면 독이 되므로 자동화된 스캔과 정책 강제가 동반되어야 함
- 향후 방향: 최근에는 코드 형상과 플래그 상태를 통합 관리하는 GitOps 기반의 토글 관리 및 AI 예측 롤아웃 기술로 진화 중임
