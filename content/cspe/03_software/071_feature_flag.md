# 📖 【암기용】 개념 완전 이해

> 목적: 피처 플래그를 처음 봐도 배포·릴리스 분리 관점에서 이해하게 만든다. 시험 답안 양식이 아니라, 이해를 위한 설명이다.

## 한눈에
- **개요**: 코드에 기능 스위치를 심어 사용자·환경별 노출을 제어하는 방식
- **왜 필요한가**: 배포는 코드를 서버에 올리는 행위이고, 릴리스는 사용자가 기능을 쓰게 여는 행위임. 둘을 분리하면 장애 기능을 재배포 없이 차단 가능함.
- **핵심 직관**: 전기 배선은 이미 깔아두고, 스위치로 어느 방에 불을 켤지 결정하는 방식임.

## 깊이 이해
- **배경·문제의식**: 전통 배포는 코드 반영과 사용자 노출이 동시에 발생해 장애 시 전체 롤백이 필요함. 피처 플래그는 런타임 조건으로 기능 경로를 선택해 릴리스 위험을 작은 집단으로 제한함.
- **작동 원리**: 애플리케이션은 플래그 저장소에서 `on/off`, 사용자 세그먼트, 비율, 만료일을 읽고 분기함. 운영자는 콘솔 또는 API로 값을 변경해 Canary, A/B Test, Kill Switch를 수행함.
- **비유**: 공연장은 무대를 완성해 두지만, 조명 콘솔에서 장면별 조명을 켜고 끄며 관객에게 보이는 범위를 조절함.
- **구체 예시**: 신규 결제 모듈을 `payment_v2` 플래그로 내부 직원 1%, 베타 고객 10%, 전체 100% 순서로 확대하고 오류율 1% 초과 시 30초 내 off 처리함.
- **흔한 오해·주의점**: 피처 플래그는 임시 분기임. 만료일 없이 남기면 flag debt가 누적되어 테스트 조합과 코드 복잡도가 증가함.

## 연결 개념
- Canary Release — 피처 플래그의 점진 노출 전략
- Blue-Green Deployment — 배포 인프라 전환과 릴리스 제어 비교 대상
- Technical Debt — 제거되지 않은 플래그가 만드는 운영 부채

# 📝 【답안용】 시험 답안 템플릿

> 목적: 시험장에서 25분에 그대로 쓰는 답안 양식. 작성방식(추상표현 금지·수치·도식·문제유형 전환)을 엄격히 지킨다.
> 핵심: 피처 플래그는 기능 분기 문법이 아니라 release와 deploy를 분리해 장애 반경과 실험 범위를 통제하는 운영 메커니즘이다.

## 핵심 인사이트 (3줄 요약)
> 1. **본질**: 피처 플래그는 런타임 설정으로 기능 노출을 제어해 배포 완료와 사용자 릴리스를 분리하는 소프트웨어 전달 기법이다.
> 2. **가치**: Kill Switch, Targeting, 점진 노출로 장애 발생 시 재배포 없이 1분 이내 기능 차단과 영향 사용자 1~10% 제한을 목표로 함.
> 3. **판단 포인트**: 플래그 유형·소유자·만료일·감사 로그가 없으면 flag debt와 테스트 조합 폭증이 발생함.

## 출제 의도 및 답안 포인트
| 출제 의도 | 반드시 짚을 핵심 | 감점 회피 포인트 |
|:---|:---|:---|
| DevOps 릴리스 통제 역량 확인 | release vs deploy 분리, targeting, kill switch | 단순 if문 또는 환경변수 설명으로 축소 |
| 장애 반경 축소 판단 확인 | Canary 1/10/50/100%, 오류율·p95 기준 자동 차단 | 롤백과 플래그 off의 차이 누락 |
| 운영 거버넌스 확인 | 플래그 소유자, TTL, 제거 PR, 감사 로그 | flag debt와 테스트 매트릭스 증가 누락 |

> 요약: 이 문제는 기능 스위치 구현보다 릴리스 위험을 지표 기반으로 통제하는 운영 설계를 요구한다.

---

## Ⅰ. 개요 및 필요성

피처 플래그는 런타임 기능 노출 제어 장치이다.
배포와 릴리스가 결합되면 장애 기능을 끄기 위해 전체 배포 롤백이 필요함.
플래그 기반 릴리스는 사용자 세그먼트·비율·환경별로 기능을 열어 MTTR 10분 이하와 영향 범위 10% 이하를 목표로 함.

---

## Ⅱ. 구조 및 구성요소

```text
Code Path -> Flag SDK -> Flag Store -> Rule Engine -> User Experience
                 +-> Metrics
                 +-> Audit Log
Operator Console -> Rule Change -> Kill Switch / Targeting
```

| 구성요소 | 역할 | 특이사항 |
|:---|:---|:---|
| Flag SDK | 애플리케이션 내부에서 플래그 평가 | 캐시 TTL 30~60초, 장애 시 기본값 필요 |
| Flag Store | 플래그 값·규칙·만료일 저장 | DB, SaaS, GitOps 저장소 사용 |
| Rule Engine | 사용자 속성·비율·환경 기준 판정 | cohort, percentage rollout |
| Operator Console | 운영자가 값 변경·승인 수행 | RBAC, 감사 로그, 2인 승인 |
| Telemetry | 노출군별 오류·전환율 관측 | p95, error rate, conversion rate |

> 요약: 피처 플래그 구조는 SDK 평가, 규칙 저장, 운영 변경, 지표 관측이 결합되어 런타임 릴리스를 제어한다.

---

## Ⅲ. 동작원리 및 흐름도

```text
Feature Commit -> Deploy Hidden Code -> Evaluate Flag
  -> Target User Match / Percentage Match
  -> Feature On or Off
  -> Metrics Check -> Expand / Disable / Remove Flag
```

| 단계 | 처리 내용 | 검증 기준 |
|:---:|:---|:---|
| 1 | 기능 코드를 플래그 분기로 감싸 배포 | 기본값 off, 단위 테스트 80% 이상 |
| 2 | 내부 사용자 또는 1% cohort에 노출 | 오류율 기준군 대비 0.5%p 이내 |
| 3 | 10/50/100%로 점진 확대 | p95 지연 200ms 이하, 전환율 하락 2%p 이내 |
| 4 | 장애 감지 시 kill switch 실행 | off 반영 60초 이내, 감사 로그 생성 |
| 5 | 릴리스 완료 후 플래그 제거 | 만료일 30일 이내, 제거 PR 병합 |

> 요약: 피처 플래그는 숨김 배포, 제한 노출, 지표 판정, 확대 또는 차단, 플래그 제거 순서로 동작한다.

## Ⅳ. 특징

| 구분 | 기존 릴리스 | 피처 플래그 | 정량 기준 |
|:---|:---|:---|:---|
| 배포·릴리스 | 배포 즉시 전체 노출 | deploy와 release 분리 | 노출 비율 1/10/50/100% |
| 장애 대응 | 전체 롤백 또는 hotfix | kill switch로 기능 off | 차단 반영 60초 이내 |
| 실험 | 별도 브랜치·별도 배포 | cohort 기반 A/B Test | 표본 n, 전환율, p-value |
| 운영 비용 | 분기 잔존 위험 낮음 | flag debt 관리 필요 | TTL 30~90일 |
| 감사 | 배포 이력 중심 | 플래그 변경 이력 포함 | RBAC, 변경자, 사유 기록 |

> 요약: 피처 플래그는 릴리스 위험을 낮추지만 플래그 수명주기와 테스트 조합을 통제해야 한다.

## Ⅴ. 심화 비교 및 적용 판단

| 비교 축 | 기존/대안 | 본 키워드 | 선택 기준 |
|:---|:---|:---|:---|
| 구조 | Blue-Green은 환경 전환 | 플래그는 기능 단위 노출 | 기능별 실험·차단 필요 시 플래그 |
| 비용/성능 | 단순 배포는 분기 비용 없음 | 플래그 평가 지연·SDK 의존 | p95 평가 5ms 이하 유지 |
| 운영/위험 | 롤백은 전체 변경 되돌림 | kill switch는 기능만 차단 | 장애 기능 국소화 필요 시 선택 |
| 거버넌스 | 배포 승인 중심 | 플래그 승인·만료·삭제 관리 | 플래그 100개 초과 시 자동 점검 |

> 요약: 기능 단위 위험 통제가 필요하면 피처 플래그를, 환경 단위 전환이 목적이면 Blue-Green을 선택한다.

| 리스크 | 원인 | 대응 방안 | 확인 지표 |
|:---|:---|:---|:---|
| flag debt | 만료일 없는 플래그 잔존 | owner, TTL, 제거 티켓 자동 생성 | 만료 초과 0건 |
| 잘못된 노출 | 타깃 규칙 오류 | dry-run, 세그먼트 샘플 검증 | 예상/실제 노출 차이 1%p 이하 |
| SDK 장애 | 플래그 저장소 장애·네트워크 지연 | 로컬 캐시, 기본값, timeout 50ms | fallback 발생률 |
| 테스트 폭증 | on/off 조합 증가 | permanent/release/experiment 분류 | 필수 조합 커버리지 100% |

> 요약: 피처 플래그 리스크는 수명주기, 타깃 정확도, SDK 장애, 테스트 조합을 지표로 통제한다.

| 점검 항목 | 목표 기준 | 측정 방법 |
|:---|:---|:---|
| 릴리스 안전 | 오류율 기준군 대비 0.5%p 이내 | APM, 로그, cohort 비교 |
| 전환 성과 | 전환율 하락 2%p 이내 | 실험 대시보드, 통계 검정 |
| 운영 통제 | 변경 감사 로그 100%, TTL 초과 0건 | 플래그 콘솔, 주간 리포트 |
| 복구 시간 | kill switch 반영 60초 이내 | synthetic check, 알림 타임라인 |

> 요약: 도입 성공은 오류율, 전환율, 감사 로그, 차단 반영 시간으로 판단한다.

## Ⅵ. 실무 적용 및 결론

**적용 방안 3개 (필수 — 단계별 또는 항목별):**
1. `release`, `experiment`, `ops`, `permission` 유형을 분리하고 각 플래그에 owner·TTL·기본값·삭제 조건을 필수 필드로 등록함.
2. Canary 정책을 1% -> 10% -> 50% -> 100%로 표준화하고 error rate 1%, p95 200ms 초과 시 자동 off 규칙을 설정함.
3. PR 템플릿에 플래그 제거 날짜와 테스트 조합을 기재하고, 만료 7일 전 Slack·이슈 자동 알림으로 flag debt를 차단함.

**결론 (2줄):**
- 기술사 판단: 배포 빈도 주 1회 이상·사용자 영향 리스크가 큰 서비스는 피처 플래그를 적용하고, 정적 설정 변경 수준이면 배포 승인으로 충분함.
- 향후 방향: 플래그 거버넌스는 GitOps, OpenFeature, OPA 정책과 결합해 감사 가능한 릴리스 제어 체계로 발전함.
