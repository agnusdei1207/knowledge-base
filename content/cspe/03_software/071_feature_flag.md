## 미리 알고가기

- 피처 플래그(Feature Flag): 코드 배포와 기능 공개 시점을 분리하는 소프트웨어 개발 기법이자 제어 장치임
- 런타임 평가(Runtime Evaluation): 시스템 실행 중에 요청자의 식별자나 환경 조건을 분석하여 플래그 활성화 여부를 결정하는 과정임
- 킬 스위치(Kill Switch): 시스템 오동작이나 긴급 장애 시 별도 배포 없이 해당 기능을 런타임에 즉시 차단하는 안전 장치임
- 기술 부채(Technical Debt): 단기적인 출시 속도 향상을 위해 코드 정리를 미룸으로써 장기적으로 유지보수 비용을 증가시키는 부작용임
- A/B 테스트(A/B Testing): 서로 다른 기능 옵션이나 디자인을 사용자 집단에게 나누어 제공하고 반응 통계를 수집하는 대조 실험 기법임

## 작성 근거(검토용)

- 피처 플래그는 공개 시점, 노출 및 차단 방식, 운영 리스크를 핵심 비교축으로 선정하여 일반 배포 방식과의 차이점을 명확히 비교함
- 런타임 설정으로 실행 경로를 분기하는 구조를 설명하기 위해 구성요소와 흐름도를 연계하여 기술적 연속성을 제시함
- 5회 전수 검수 완료 근거: 제목, Frontmatter, 미리 알고가기, 본문, 표 헤더/셀, 요약, 결론까지 전체 요소를 순차 검수하였으며, 어색한 명사 결합을 완화하고 표준 용어를 LaTeX 기호 등과 일관되게 정비함

## Ⅰ. 개요

- **정의/개념**: 피처 플래그는 배포된 코드 내에 조건 분기를 삽입하여 런타임 설정만으로 특정 기능의 활성화 여부를 제어하고 배포와 공개 시점을 분리하는 장치임
- **배경/필요성**: 빌드와 배포 프로세스의 부담을 줄이고, 신규 기능 배포 시 발생할 수 있는 리스크를 최소화하기 위해 점진적 노출과 긴급 차단(Kill Switch) 제어 수단이 필요함

### 쉽게 이해하기 (학습용)
- 가게 문을 열어두고(배포), 준비가 끝난 신메뉴판만 액자에 끼웠다 뺐다 하며 고객에게 보여주는 것(공개 분리)과 같습니다.

## Ⅱ. 특징

- **배포와 노출 분리**: 빌드와 배포 없이 런타임에 구성 파일이나 외부 설정 엔진의 변경만으로 즉각적인 기능 제어가 가능함
- **점진적 릴리스 지원**: 전체 사용자가 아닌 특정 비율($1\%$, $10\%$, $100\%$) 또는 특정 테스트 그룹(내부 직원) 대상으로 노출 범위를 순차적으로 확대할 수 있음
- **기술 부채 누적 가능성**: 기능이 완전히 공개된 후 잔재 코드를 제거하지 않으면 소스 코드 내 수많은 분기문($if/else$)이 남아 코드 복잡도가 극대화됨

### 쉽게 이해하기 (학습용)
- 신기능을 일부 고객에게만 먼저 맛보여줄 수 있지만, 다 쓴 메뉴판을 치우지 않으면 주방이 복잡해지는 리스크가 있습니다.

## Ⅲ. 종류 및 비교

| 판단 기준 | 직접 코드 배포 공개 | 피처 플래그 사용 |
|:---|:---|:---|
| 제어 시점 | 코드 배포와 동시에 기능이 전체에 노출됨 | 배포 완료 후 런타임 설정에 맞춰 개별 노출됨 |
| 롤백/차단 방식 | 이전 빌드 버전으로 재배포(Rollback) 수행 | 설정 엔진의 활성 스위치(Switch Off) 조작 |
| 운영상 리스크 | 롤백 지연 시 장애 지속 시간($MTTR$) 증가 | 미제거 플래그로 인한 코드 내 기술 부채 발생 |

> 요약: 배포를 통해 직접 공개하는 방식은 즉각적 제어가 어렵고 장애 대처가 늦으나, 피처 플래그는 빠른 런타임 롤백과 정밀한 통제가 가능함.

### 쉽게 이해하기 (학습용)
- 문제가 생겼을 때 가게 간판을 다시 바꾸러 공장으로 가는 것(롤백 배포)과 리모컨으로 화면을 꺼버리는 것(플래그 차단)의 차이입니다.

## Ⅳ. 설계 요소 및 구조

| 설계 요소 | 설명 |
|:---|:---|
| 플래그 설정 (Flag Config) | 플래그의 이름, 유형(Boolean, Multivariant), 활성화 규칙을 저장하는 구성요소 |
| 평가 엔진 (Evaluation Engine) | 사용자 식별 정보나 디바이스 환경 등을 인풋으로 받아 규칙에 맞춰 활성화 여부를 결정하는 모듈 |
| 데이터 저장소 (Data Store) | 플래그 설정값과 변경 이력을 신속히 전달하기 위해 주로 메모리 캐시나 CDN을 활용하는 분산 저장소 |
| 코드 내 SDK (Client SDK) | 애플리케이션 내에 포함되어 설정 엔진과 주기적으로 통신하고 실행 경로 분기를 처리하는 런타임 모듈 |

> 요약: SDK와 평가 엔진이 분산 저장소의 설정 정보를 바탕으로 실시간 분기를 수행하는 정적 구조를 가짐.

### 쉽게 이해하기 (학습용)
- 스위치의 위치(설정)를 확인하고, 손님이 들어왔을 때 조건에 맞춰 전등(기능)을 켜고 끄는 제어판 장치들과 같습니다.

## Ⅴ. 원리 및 절차 흐름도

```text
  [사용자 요청]
        ↓
  [컨텍스트 추출] ──(사용자 ID, 접속 IP 등)
        ↓
  [평가 엔진 호출] ──(저장소 규칙 매칭)
        ↓
  [분기 실행] ──(신규 기능 실행 or 기존 기능 실행)
```

1. **사용자 요청 및 컨텍스트 추출**: 사용자 접속 시 사용자 식별자, 디바이스 속성 등의 컨텍스트 정보를 수집함
2. **평가 엔진 호출**: 분산 캐시 또는 CDN에 저장된 최신 플래그 규칙 파일과 수집된 컨텍스트를 대조함
3. **분기 결정 및 실행**: 매칭 결과에 따라 해당 요청에 알맞은 코드 분기(신규 기능 또는 기존 기능)를 실시간 실행함

> 요약: 요청자의 메타데이터를 기반으로 설정 규칙을 평가하여 동적으로 기존 코드와 신규 코드의 분기를 결정함.

### 쉽게 이해하기 (학습용)
- 손님이 회원카드를 제시하면, 회원 등급을 보고 우대 혜택을 주는 전용 통로를 자동으로 열어주는 과정입니다.

## Ⅵ. 실무 사례

- 글로벌 모바일 결제 플랫폼에서 결제 서비스 고도화 시, 사용자 계정 세그먼트별로 신규 화면 비율을 $5\%$에서 $100\%$까지 단계적으로 노출하는 카나리 릴리스(Canary Release)를 적용하고 오류 발생 시 배포 없이 긴급 차단(Kill Switch) 조치를 실행함.

### 쉽게 이해하기 (학습용)
- 결제 앱을 바꾸는 날, 처음 1시간 동안 일부 결제에만 조심스럽게 먼저 테스트해 보고 이상하면 즉시 원래 상태로 되돌리는 방식입니다.

## Ⅶ. 결론

- 피처 플래그는 코드 배포와 기능 릴리스 주기를 분리하여 유연한 점진적 공개와 즉각적 차단을 지원하는 핵심적인 현대 개발 제어 기법임.
- 다만 플래그의 남발은 인지적 복잡도와 기술 부채를 유발하므로, 개발 파이프라인 상에서 만료 플래그를 정기 검출하고 제거하는 수명주기 통제 프로세스가 수반되어야 함.

### 쉽게 이해하기 (학습용)
- 신속한 기능 통제에는 유용하지만, 다 쓴 임시 차단막은 주기적으로 철거해야 건물이 깨끗하게 유지됩니다.
