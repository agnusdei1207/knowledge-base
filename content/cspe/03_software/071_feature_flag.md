## 핵심 인사이트 (3줄 요약)
- 소스 코드를 수정하거나 서버를 재배포하지 않고도, **시스템의 특정 기능을 외부 설정(UI 버튼)으로 켜거나 끌 수 있는(On/Off) 개발 기법**.
- "코드를 배포(Deployment)하는 것"과 "기능을 사용자에게 노출(Release)하는 것"을 완벽하게 분리하는 점진적 딜리버리(Progressive Delivery)의 핵심 기술.
- A/B 테스트, 특정 VIP 고객 대상 선공개, 심각한 장애 발생 시 1초 만에 해당 기능 차단(Kill Switch) 등 현대 SaaS 비즈니스 운영의 필수 무기임.

## Ⅰ. 개요 및 필요성
- **개요**: 런타임에 코드의 실행 흐름(If-Else 분기)을 동적으로 제어하기 위해 사용하는 설정 값.
- **필요성**: 기존에는 기능을 감추려면 코드를 주석 처리하고 다시 빌드해서 배포해야 했음(수십 분 소요). 이벤트 트래픽이 폭주하여 결제 모듈이 죽어갈 때, 추천 상품 UI만 임시로 꺼서 DB 부하를 살려내는 식의 '런타임 실시간 제어'가 불가능했음.
---
## Ⅱ. 아키텍처 및 핵심 원리
- **동작 원리 (간단한 If문)**:
  ```java
  if (FeatureFlagManager.isOn("NEW_CHECKOUT_PAGE")) {
      return renderNewPage(); // 기능 On (새로운 결제창)
  } else {
      return renderOldPage(); // 기능 Off (기존 결제창)
  }
  ```
- **Flag의 종류 (수명 주기별)**:
  1. **Release Toggle**: 미완성 기능을 숨긴 채 Main 브랜치에 코드를 통합하기 위해 사용 (CI/CD 용이, 수일~수주 수명).
  2. **Experiment Toggle**: A/B 테스트를 위해 사용자 그룹(A군/B군)을 나누어 적용 (데이터 수집 완료 시 폐기).
  3. **Ops Toggle (Kill Switch)**: 특정 API의 성능 저하 시 해당 기능을 꺼버려 시스템 전체 다운을 막음 (영구적 수명).
  4. **Permission Toggle**: 프리미엄 회원(VIP), 사내 직원에게만 특정 기능을 열어줌 (영구적 수명).

```text
[ Feature Flag를 활용한 배포와 릴리즈의 분리 ]

 (개발자)               (피처 플래그 서버: LaunchDarkly 등)      (일반 고객군)
 [ 코드 배포 완료 ] ➡️  [ 새 버튼 UI: OFF 상태 ] ----------------> (안 보임)
 (프로덕션 환경)             ⬇️ 
                        [ 사내 직원만 ON 설정 ] ----------------> (사내 직원만 테스트)
                             ⬇️ 
                        [ 10% 유저 ON 설정 ] ------------------> (카나리 노출)
                             ⬇️ 
                        [ 에러 발생! 긴급 OFF! ] ---------------> (1초 만에 롤백/사라짐)
```
---
## Ⅲ. 비교 및 연결
| 구분 | 브랜치 기반 개발 (Feature Branch) | 피처 플래그 기반 개발 (Trunk-Based) |
|---|---|---|
| **코드 통합 시점** | 기능이 완벽히 완성된 후 (수 주 소요) | 기능이 미완성이어도 매일 Main에 병합 |
| **기능 숨김 방식** | 브랜치를 분리해 둠 | 코드는 합치되 Flag(If문)로 덮어 둠 |
| **장애 롤백 방법** | 이전 Git 커밋으로 Revert 후 재배포 | 플래그 대시보드에서 마우스로 'OFF' 클릭 (1초) |
| **운영 복잡도** | 코드 충돌(Merge Hell)의 늪 | 소스 코드 내에 If문 쓰레기(Tech Debt) 증가 |
---
## Ⅳ. 실무 적용 및 기술사 판단
- **If문 지옥과 기술 부채 (Tech Debt)**: 피처 플래그의 가장 큰 치명타는 소스 코드가 온통 `if(flag)`로 도배된다는 점임. 실험이 끝난(100% 릴리즈된) 낡은 플래그를 삭제하지 않고 방치하면 코드는 스파게티가 됨(Knight Capital의 4억 달러 손실 사건 원인). 플래그 생성 시 반드시 **'삭제 티켓(만료일)'**을 함께 발행하는 거버넌스가 필수임.
- **Trunk-Based Development 완성**: 피처 플래그가 있어야만 모든 개발자가 하나의 Main(Trunk) 브랜치에 코드를 밀어 넣어도(CI) 서비스가 망가지지 않음. 즉, 궁극의 지속적 통합(CI)을 달성하기 위한 필수 조건임.
---
## Ⅴ. 기대효과 및 결론
- 엔지니어링 리소스 없이도, 기획자(PM)나 마케터가 대시보드에서 직접 스위치를 켜며 비즈니스 릴리즈 타이밍을 조절할 수 있게 됨.
- 배포(Deploy)의 기술적 리스크와 릴리즈(Release)의 비즈니스 리스크를 분리함으로써, 넷플릭스/토스 등 선도적 IT 기업이 하루에 수십 번씩 실험(A/B Test)을 할 수 있는 든든한 밑바탕이 됨.

### 👶 어린이를 위한 3줄 비유 설명
1. 거실에 엄청나게 화려한 크리스마스트리(새로운 기능)를 사 왔어요.
2. 예전에는 트리를 거실에 꺼내두는 순간 모두가 볼 수밖에 없었는데, 피처 플래그는 트리를 '투명 망토'로 덮어두는 거예요.
3. 코드는 이미 배포되어 우리 집에 있지만, 아빠(개발자)가 리모컨 버튼(플래그)을 딱! 누르는 순간에만 망토가 벗겨지면서 짠! 하고 나타난답니다!
