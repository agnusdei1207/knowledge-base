# 📖 【암기용】 개념 완전 이해

> 목적: 프로세스와 스레드를 처음 봐도 완벽히 이해하게 만든다. 시험 답안 양식이 아니라, 이해를 위한 친절한 설명이다.

## 한눈에
- **개요**: 프로세스는 자원 소유 단위, 스레드는 CPU 실행 단위
- **왜 필요한가**: 운영체제는 프로그램마다 독립 주소공간을 주면서도, 한 프로그램 내부 작업은 여러 흐름으로 나누어 CPU를 공유시킨다.
- **핵심 직관**: 프로세스는 사무실 전체, 스레드는 그 안에서 같은 서류함을 공유하며 일하는 직원이다.

## 깊이 이해
- **배경·문제의식**: 프로세스만으로 동시성을 만들면 주소공간과 파일 핸들 복제가 커서 생성·전환 비용이 증가한다. 스레드는 같은 주소공간에서 스택과 레지스터만 분리해 응답시간을 줄인다.
- **작동 원리**: 프로세스는 코드·데이터·힙·파일 디스크립터·권한을 보유하고, 스레드는 PC·레지스터·스택·스케줄링 상태를 가진다. 같은 프로세스의 스레드는 힙을 공유하므로 IPC 없이 데이터 접근이 가능하나, 동기화 누락 시 race condition이 발생한다.
- **비유**: 프로세스는 벽으로 나뉜 방이다. 다른 방과 대화하려면 문서 전달 절차가 필요하지만, 같은 방의 직원들은 같은 책상을 보며 일한다.
- **구체 예시**: 웹 서버가 프로세스 4개를 띄우면 포트와 메모리 격리가 쉽고, 스레드 200개를 쓰면 요청별 스택 1MB 기준 약 200MB로 연결을 처리한다.
- **흔한 오해·주의점**: 스레드는 프로세스보다 항상 우월하지 않다. 스레드 1개가 힙을 오염시키면 같은 프로세스 전체가 종료될 수 있어 fault isolation은 프로세스가 유리하다.

## 연결 개념
- PCB·TCB: 프로세스와 스레드 상태 저장 구조
- 컨텍스트 스위칭: CPU 실행 주체 전환 비용
- 동기화 객체: mutex, semaphore, monitor로 공유 데이터 보호

# 📝 【답안용】 시험 답안 템플릿

> 목적: 시험장에서 25분에 그대로 쓰는 답안 양식. 작성방식(추상표현 금지·수치·도식·문제유형 전환)을 엄격히 지킨다.
> 핵심: 프로세스·스레드 차이 나열이 아니라 주소공간, 자원 소유, 스케줄링, IPC, 장애 격리의 trade-off로 답안을 구성한다.

## 핵심 인사이트 (3줄 요약)

> 1. **본질**: 프로세스는 독립 주소공간과 자원을 보유하는 보호 단위이고, 스레드는 프로세스 내부에서 CPU를 배정받는 실행 단위이다.
> 2. **가치**: 프로세스는 장애 격리와 권한 분리에 유리하고, 스레드는 메모리 공유와 컨텍스트 전환 비용 감소에 유리하다.
> 3. **판단 포인트**: 격리 요구, 공유 데이터량, 응답시간 목표, 동기화 비용을 함께 보고 프로세스·스레드·혼합 모델을 선택한다.

## 출제 의도 및 답안 포인트

| 출제 의도 | 반드시 짚을 핵심 | 감점 회피 포인트 |
|:---|:---|:---|
| OS 자원 관리 단위 구분 확인 | 주소공간·파일·권한은 프로세스, PC·레지스터·스택은 스레드 | 실행 단위와 자원 소유 단위를 혼동 |
| 동시성 구현 방식 판단 확인 | IPC 비용, 공유 메모리, mutex 경쟁, context switch 비용 | 스레드를 무조건 선택하는 단정 |
| 장애 격리와 처리량 trade-off 확인 | 프로세스 격리 vs 스레드 공유, crash blast radius | fault isolation 누락 |

> 요약: 이 문제는 단순 비교가 아니라 CPU 시간과 메모리 보호 경계의 분리 여부를 판단하게 한다.

---

## Ⅰ. 개요 및 필요성

- 개요: 프로세스는 자원 단위, 스레드는 실행 단위이다.
- 배경: 운영체제는 프로세스로 주소공간·권한을 분리하고, 스레드로 같은 자원 안에서 여러 제어 흐름을 실행한다.
- 필요성: 서버·브라우저·DBMS는 fault isolation, p95 응답시간, IPC 비용 기준에 따라 프로세스와 스레드를 혼합 설계한다.

---

## Ⅱ. 구조 및 구성요소

```text
Program Image -> Process Address Space -> Thread 1 / Thread 2 / Thread N
Process: code/data/heap/file/permission
Thread: PC/register/stack/scheduling state
```

| 구성요소 | 역할 | 판단 포인트 |
|:---|:---|:---|
| 프로세스 주소공간 | code, data, heap, mmap 분리 | MMU page table 기준 격리 |
| 프로세스 자원 | 파일 디스크립터, signal, credential 보유 | 권한·감사 단위 |
| 스레드 실행 상태 | PC, register, stack, TCB 보유 | 스케줄러가 CPU 배정 |
| 공유 데이터 | 같은 프로세스 heap 접근 | mutex, RW-lock 필요 |

> 요약: 프로세스는 보호 경계와 자원 묶음, 스레드는 CPU를 받는 독립 실행 흐름이다.

---

## Ⅲ. 동작원리 및 흐름도

```text
프로그램 시작 -> 프로세스 생성 -> 주소공간 할당
-> 주 스레드 생성 -> 추가 스레드 생성
-> CPU 스케줄링 -> 공유 데이터 동기화 -> 종료/정리
```

| 단계 | 처리 내용 | 검증 기준 |
|:---:|:---|:---|
| 1 | fork/exec 또는 CreateProcess로 주소공간 구성 | PID, page table 생성 |
| 2 | main thread에 PC·SP·register 초기값 부여 | TCB, kernel stack 생성 |
| 3 | pthread_create 등으로 추가 스레드 생성 | thread count, stack size |
| 4 | scheduler가 runnable thread에 time slice 배정 | context switch rate |
| 5 | join/exit로 스레드·프로세스 자원 회수 | zombie 0건, FD leak 0건 |

> 요약: 프로세스 생성은 보호 경계 형성이고, 스레드 생성은 같은 보호 경계 안에 실행 흐름을 추가하는 절차이다.

---

## Ⅳ. 특징

| 구분 | 프로세스 | 스레드 | 수치·기술 포인트 |
|:---|:---|:---|:---|
| 주소공간 | 독립 page table | 같은 page table 공유 | TLB flush 가능성 |
| 전환 비용 | page table·TLB 영향 큼 | register·stack 중심 | Linux switch 수 us 단위 |
| 통신 방식 | pipe, socket, shared memory | heap 직접 공유 | IPC copy 비용 vs lock 비용 |
| 장애 범위 | 프로세스 단위 종료 | 프로세스 전체 영향 | 브라우저 tab process 격리 |

> 요약: 프로세스는 격리 비용을 지불하고, 스레드는 공유 비용과 동기화 리스크를 지불한다.

## Ⅴ. 심화 비교 및 적용 판단

| 비교 축 | 기존/대안 | 본 키워드 | 선택 기준 |
|:---|:---|:---|:---|
| 구조 | 단일 프로세스 단일 스레드 | 멀티 프로세스/멀티 스레드 | 동시 연결 수, 격리 요구 |
| 비용/성능 | 프로세스 전환과 IPC | 스레드 전환과 lock contention | p95 응답시간, CPU run queue |
| 운영/위험 | 장애 격리 높음 | 공유 오염 가능 | crash 1건의 영향 범위 |

> 요약: 처리량만 보면 스레드, 장애 격리와 권한 분리를 보면 프로세스 기준으로 선택한다.

| 리스크 | 원인 | 대응 방안 | 확인 지표 |
|:---|:---|:---|:---|
| race condition | 공유 heap 동시 갱신 | mutex, atomic, lock ordering | ThreadSanitizer 0건 |
| 과도한 전환 | thread 수가 CPU core 초과 | pool size core×2 기준 조정 | context switch/sec |
| 장애 전파 | 스레드 crash가 process 종료 | process isolation, supervisor | crash blast radius |

> 요약: 스레드 설계의 리스크는 공유 메모리 오염과 전환 폭증이며, lock 검증과 pool 제한으로 통제한다.

| 점검 항목 | 목표 기준 | 측정 방법 |
|:---|:---|:---|
| 응답시간 | p95 100ms 이하 | APM latency histogram |
| CPU 사용 | run queue/core 1~2 유지 | vmstat, perf sched |
| 메모리 | thread stack 총량 상한 설정 | pmap, smaps, RSS |

> 요약: 도입 효과는 p95 응답시간, run queue, stack 메모리 총량으로 판단한다.

## Ⅵ. 실무 적용 및 결론

**적용 방안 3개 (필수 — 단계별 또는 항목별):**
1. 외부 장애 격리가 필요한 브라우저·플러그인은 프로세스 분리와 seccomp/AppContainer로 권한 범위 제한
2. 같은 데이터 구조를 반복 접근하는 웹 서버는 worker thread pool을 CPU core×2 내외로 설정하고 mutex 경쟁률 측정
3. 대용량 IPC는 socket copy 대신 shared memory+ring buffer를 사용하고, producer/consumer 지연을 p99 기준 측정

**결론 (2줄):**
- 기술사 판단: 권한 분리·fault isolation이면 프로세스, 공유 데이터 기반 응답시간 단축이면 스레드, 양쪽 요구가 있으면 process pool+thread pool을 선택함
- 향후 방향: 멀티코어 환경에서는 OS scheduler, NUMA affinity, lock-free 구조를 함께 설계해야 처리량과 격리 요구를 동시에 만족함
