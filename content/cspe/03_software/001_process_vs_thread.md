# 📖 【암기용】 개념 완전 이해

## 한눈에
- **개요**: 운영체제의 실행 단위인 프로세스와, 그 내부의 더 작은 실행 흐름인 스레드 비교
- **왜 필요한가**: CPU 자원을 어떻게 할당하고 문맥을 전환할지(스케줄링) 결정하는 기본 단위이므로, 성능과 자원 공유의 트레이드오프를 이해해야 한다.
- **핵심 직관**: 프로세스는 독립된 공장(자원 소유)이고, 스레드는 그 공장 안에서 일하는 작업자들(자원 공유)이다.

## 핵심 용어 정리

| 용어/표기 | 의미 | 비유·예 |
|:---|:---|:---|
| 프로세스 (Process) | 실행 중인 프로그램 (자원 소유의 단위) | 독립된 건물(공장), 보안 철저 |
| 스레드 (Thread) | 프로세스 내의 제어 흐름 (스케줄링의 단위) | 공장 내의 작업자들(자원 공유) |
| 주소 공간 (Address Space) | 코드, 데이터, 힙, 스택 영역 | 공장의 작업 공간 |
| TCB (Thread Control Block) | 스레드 단위의 상태 정보 저장 블록 | 작업자의 개인 수첩 |

## 깊이 이해
- **배경·문제의식**: 프로세스만으로 다중 작업을 하면 매번 새로운 공장을 짓는 것과 같아 생성 비용(메모리 할당)과 전환 비용(컨텍스트 스위칭)이 크다. 이를 극복하기 위해 공장(프로세스) 내에서 메모리를 공유하는 작업자(스레드) 개념이 등장했다.
- **작동 원리**: 프로세스는 Code, Data, Heap, Stack 영역을 모두 독립적으로 할당받지만, 스레드는 하나의 프로세스 안에서 Code, Data, Heap은 공유하고 각자의 Stack과 PC(Program Counter)만 독립적으로 가진다.
- **비유**: 크롬 브라우저(프로세스)를 여러 개 띄우면 메모리를 많이 먹지만, 하나의 크롬 안에서 여러 탭(스레드)을 띄우면 메모리를 아낄 수 있다(다만 탭 하나가 죽으면 전체가 죽을 수 있는 구조가 멀티스레드).
- **구체 예시**: 웹 서버가 요청을 받을 때마다 프로세스를 포크(`fork()`)하면 오버헤드가 크므로, 스레드 풀을 만들어 요청마다 스레드를 할당해 처리한다.
- **흔한 오해·주의점**: 멀티프로세스가 항상 멀티스레드보다 나쁜 것은 아니다. 멀티스레드는 자원을 공유하므로 동기화(뮤텍스, 세마포어) 문제가 발생하고 하나의 스레드 충돌이 전체 프로세스를 죽일 수 있어 안정성이 중요할 땐 멀티프로세스(크롬의 각 탭은 실제로는 멀티프로세스 구조 채택)를 쓴다.

## 연결 개념
- PCB·컨텍스트 스위칭 (002 참조) — 전환 시 저장되는 정보
- 교착상태 (009 참조) — 자원 공유로 인한 문제

# 📝 【답안용】 시험 답안 템플릿

## 핵심 인사이트 (3줄 요약)

> 1. **본질**: 프로세스는 자원 소유의 단위(독립적)이며, 스레드는 프로세스 내 CPU 스케줄링의 기본 단위(공유)이다.
> 2. **가치**: 스레드는 프로세스 대비 생성·전환 오버헤드를 대폭 줄여 시스템 처리량을 향상시킨다.
> 3. **판단 포인트**: 성능(오버헤드 감소)을 원하면 멀티스레드를, 격리성(장애 영향도 축소)을 원하면 멀티프로세스를 선택한다.

## 출제 의도 및 답안 포인트

| 출제 의도 | 반드시 짚을 핵심 | 감점 회피 포인트 |
|:---|:---|:---|
| 운영체제 자원 관리 및 실행 흐름의 기본 구조 이해 | 메모리 영역(Code/Data/Heap/Stack) 공유 여부 차이점 | 프로세스·스레드 특징만 나열 |
| 멀티프로세스와 멀티스레드 아키텍처 선택 기준 확인 | 컨텍스트 스위칭 오버헤드, 동기화(IPC), 격리성 | 단순 성능 비교 단정 |
| 병렬 처리 모델 적용 방안 도출 | 상태 동기화 기법, 스레드 안전성(Thread-Safe) 확보 | 추상적인 "안정성" 서술 |

> 요약: 스레드는 프로세스 내 자원을 공유하여 전환 비용을 낮추는 반면, 동기화 및 장애 격리 문제가 수반된다.

---

## Ⅰ. 개요 및 필요성

- 개요: 프로세스는 운영체제로부터 자원을 할당받는 작업 단위이며, 스레드는 프로세스 내에서 할당된 자원을 공유하는 실행 흐름 단위
- 배경: 멀티 태스킹 요구 증가에 따라, 무거운 프로세스 생성 및 전환(Context Switching) 오버헤드를 극복할 경량화된 실행 모델 필요
- 필요성: 고성능 웹 서버 및 대규모 트랜잭션 시스템에서 응답 지연 감소 및 처리량(Throughput) 극대화를 위해 멀티스레드 모델 채택 필수

---

## Ⅱ. 구조 및 구성요소

```text
프로세스 주소 공간 (Process Address Space)
  |-- Code, Data, Heap (모든 스레드가 공유)
  |-- 스레드 1 (독립적인 Stack 1, PC 1, Register 1)
  |-- 스레드 2 (독립적인 Stack 2, PC 2, Register 2)
```

| 구성요소 | 프로세스 (Process) | 스레드 (Thread) |
|:---|:---|:---|
| 기본 단위 | 자원 할당 및 보호 단위 | CPU 스케줄링 단위 |
| 주소 공간 | 독립된 Code, Data, Heap, Stack | Stack만 독립, 나머지 공유 |
| 상태 제어 | PCB (Process Control Block) | TCB (Thread Control Block) |

> 요약: 스레드는 프로세스의 코드·데이터·힙 영역을 공유하고 스택과 레지스터만 독립적으로 유지하여 가벼운 상태 관리를 구현한다.

---

## Ⅲ. 동작원리 및 흐름도

```text
프로세스 생성 -> 스레드 풀 초기화 -> 요청 인입
  -> 여유 스레드 할당 -> 공유 자원(Data/Heap) 접근(동기화)
  -> 처리 완료 후 스레드 반환
```

- 1단계 [생성]: 프로세스가 기동되며 OS로부터 가상 메모리 공간과 PCB를 할당받음
- 2단계 [스레드 분기]: 프로세스 내에서 여러 스레드를 생성하며, 공유 자원 포인터와 독립된 스택을 구성 (TCB 생성)
- 3단계 [실행 및 동기화]: 각 스레드가 CPU를 점유하며 실행하고, 공유 자원 접근 시 Mutex 등으로 상호 배제 처리
- 4단계 [종료]: 스레드 종료 시 Stack 등 로컬 자원 반환, 최종 프로세스 종료 시 공유 자원 일괄 회수

> 요약: 프로세스가 큰 틀의 자원을 확보하면, 스레드들이 그 자원을 공유하며 실제 명령어 흐름을 병렬로 처리한다.

---

## Ⅳ. 특징

- 생성 오버헤드 축소: 스레드는 주소 공간 복사(`fork()`) 없이 TCB 및 스택만 할당하므로 생성 및 종료가 빠름
- 컨텍스트 스위칭 비용 감소: 스레드 전환 시 캐시 및 TLB(Translation Lookaside Buffer) 플러시가 불필요하여 지연 최소화
- 자원 공유: 스레드 간 메모리를 공유하므로, IPC(Inter-Process Communication) 없이 데이터 교환 가능
- 동기화 이슈: 자원 공유로 인해 Race Condition 발생 가능성이 있으며, Thread-Safe 설계 필수

> 요약: 스레드는 생성과 전환 비용이 낮고 통신이 빠르지만, 동기화 및 하나의 스레드 오류가 전체에 영향을 미치는 한계가 있다.

---

## Ⅴ. 심화 비교 및 적용 판단

| 비교 축 | 멀티 프로세스 (Multi-Process) | 멀티 스레드 (Multi-Thread) | 선택 기준 |
|:---|:---|:---|:---|
| 격리성(안정성) | 독립 공간으로 장애 격리 우수 | 하나의 스레드 크래시가 전체 영향 | 고가용성 vs 고성능 요구 여부 |
| 통신 방식 | IPC (파이프, 소켓, 공유메모리 등) | 공유 메모리 직접 접근 | 데이터 교환 빈도 및 지연 요구사항 |
| 전환(Switching) 오버헤드 | 크다 (TLB/Cache Flush 수반) | 작다 (Stack/Register만 교체) | 문맥 전환 빈도 |

> 요약: 장애 격리 및 보안이 중요하면 멀티프로세스를, 빠른 응답성 및 자원 효율성이 중요하면 멀티스레드를 선택한다.

**리스크·대응 (기본은 불릿):**
- 교착상태(Deadlock): 스레드 간 자원 점유 대기 발생 → 락(Lock) 순서 강제, 타임아웃 적용 (지표: Lock wait time)
- 스레드 폭증: 스레드 무한 생성 시 메모리 고갈 → 스레드 풀(Thread Pool) 제한, 비동기 I/O 전환 (지표: Active thread count)

**도입 후 점검 지표 (기본은 불릿):**
- 성능/효율: 스레드 전환 지연 시간(Context Switch Time), Throughput (TPS)
- 품질/운영: 메모리 사용률 변화, 캐시 적중률(Cache Hit Ratio)

---

## Ⅵ. 실무 적용 및 결론

**적용 방안 3개 (필수 — 단계별 또는 항목별):**
1. 아키텍처 선정: I/O 바운드 작업 시 스레드 풀 기반 비동기 처리 적용으로 CPU 활용률 극대화
2. 동기화 기법 적용: 공유 데이터 접근 시 Mutex, Semaphore, 또는 Lock-free 알고리즘 적용하여 Thread-Safe 환경 구축
3. 안정성 보완: 크롬 브라우저와 같이 메인 렌더러 등 크래시 영향도가 큰 영역은 멀티프로세스로 분리하여 장애 격리(Fault Isolation)

**결론 (2줄):**
- 기술사 판단: 성능 지향적 시스템은 멀티스레드를 기본으로 하되, 상태 공유를 최소화하는 함수형 프로그래밍 기법이나 비동기 이벤트 루프(Node.js 등)와 결합해 병목을 통제한다.
- 향후 방향: 최근 자바의 Virtual Thread나 Go의 Goroutine처럼 OS 스레드보다 가벼운 사용자 수준 경량 스레드를 활용하여 컨텍스트 스위칭 비용을 극단적으로 줄이는 추세다.
