# 📖 【암기용】 개념 완전 이해

> 목적: 이 개념을 처음 보는 사람도 완벽히 이해하게 만든다. 시험 답안 양식이 아니라, 이해를 위한 친절한 설명이다.

## 한눈에
- **개요**: **프로세스(Process)**는 운영체제로부터 자원(메모리)을 할당받아 실행 중인 '프로그램의 인스턴스(공장)'이며, **스레드(Thread)**는 그 공장 안에서 실제로 일을 하는 '일꾼(실행 흐름)'이다.
- **왜 필요한가**: 과거에는 공장(프로세스) 하나당 일꾼(스레드)이 한 명뿐이었다. 일을 더 하려면 공장을 하나 더 지어야 했는데(멀티 프로세스), 공장을 짓는 건 돈(메모리)이 너무 많이 들었다. 그래서 "공장은 하나만 짓고, 그 안에 일꾼을 여러 명 고용하자(멀티 스레드)!"라는 발상으로 스레드가 탄생했다.
- **핵심 직관**: 워드 프로세서(공장)를 켰다. 글자를 화면에 그리는 일꾼(스레드 A), 맞춤법을 백그라운드에서 검사하는 일꾼(스레드 B), 자동 저장을 하는 일꾼(스레드 C)이 모여 하나의 워드 공장을 굴린다.

## 깊이 이해
- **배경·문제의식**: 두 개의 프로세스가 통신하려면 서로 완전히 격리된 메모리 벽을 뚫기 위해 복잡한 파이프나 메시지 큐(IPC)를 써야 했다. 이는 오버헤드가 너무 컸다. 스레드는 같은 프로세스 안에서 힙(Heap) 메모리를 공유하므로 통신 비용이 제로(0)에 가깝다.
- **작동 원리 (메모리 구조)**:
  - 프로세스는 고유의 코드(Code), 데이터(Data), 힙(Heap), 스택(Stack) 영역을 가진다.
  - 스레드는 자신만의 독자적인 **스택(Stack)**과 **PC(Program Counter) 레지스터**만 가지고, 나머지 코드/데이터/힙은 소속된 프로세스의 것을 형제 스레드들과 함께 쓴다. (스택을 따로 갖는 이유는 함수 호출을 독립적으로 하기 위함이다.)
- **비유**: 
  - 프로세스 생성 = 구글 크롬 브라우저를 켤 때 탭마다 완전히 새로운 프로세스가 뜬다. (탭 하나가 죽어도 다른 탭은 멀쩡함)
  - 스레드 생성 = 탭 하나 안에서 동영상을 재생하고, 댓글을 스크롤하고, 광고가 움직이는 각각의 일들이다.
- **구체 예시**: 웹 서버(Apache)가 클라이언트 1000명의 요청을 받을 때, 프로세스 1000개를 띄우면 램이 10GB(10MB x 1000) 필요하지만, 스레드 1000개를 띄우면 1GB면 떡을 친다. (스레드는 훨씬 가볍다)
- **흔한 오해·주의점**: "스레드가 무조건 좋다?" 아니다. 힙(Heap) 메모리를 공유한다는 것은 양날의 검이다. 스레드 A가 실수로 전역 변수를 망가뜨리면, 아무 죄 없는 스레드 B도 같이 죽어버린다(공멸). 안정성을 위해서는 브라우저 탭처럼 스레드 대신 별도 프로세스로 격리하는 게 맞다.

## 연결 개념
- **PCB와 TCB (Process/Thread Control Block)**: OS가 공장(프로세스)을 관리하는 장부가 PCB, 일꾼(스레드)을 관리하는 더 얇은 장부가 TCB다.
- **컨텍스트 스위칭 (Context Switching)**: 스레드 간 교체는 공장 안에서 일꾼만 교대하는 거라 캐시를 비울 필요가 없어 매우 빠르다. 하지만 프로세스 간 교체는 아예 다른 공장으로 이동하는 거라 캐시(TLB)를 다 비워야 해서 엄청 무겁다.

# 📝 【답안용】 시험 답안 템플릿

> 목적: 시험장에서 25분에 그대로 쓰는 답안 양식. 작성방식(추상표현 금지·수치·도식·문제유형 전환)을 엄격히 지킨다.
> 핵심: 이 시험은 정보를 많이 나열하는 시험이 아니라, 문제 신호어에서 출제자 의도를 읽고 핵심 논점을 선별해 쓰는 시험이다.

## 핵심 인사이트 (3줄 요약)

> 1. **본질**: 프로세스는 OS로부터 자원을 할당받는 격리된 '자원 소유의 단위'이며, 스레드는 프로세스 내에서 CPU를 점유하는 '실행 흐름의 최소 단위'다.
> 2. **가치**: 스레드 모델은 메모리 공간(Code/Data/Heap)을 공유하여 컨텍스트 스위칭 비용을 최소화하고 높은 처리량(Throughput)을 달성한다.
> 3. **판단 포인트**: 자원 공유에 따른 동시성(Race Condition) 리스크와 프로세스 격리 기반의 안정성(Fault Tolerance) 사이의 트레이드오프를 아키텍처 관점에서 대조해야 한다.

## 출제 의도 및 답안 포인트

| 출제 의도 | 반드시 짚을 핵심 | 감점 회피 포인트 |
|:---|:---|:---|
| 프로세스와 스레드의 본질적 차이 규명 | 자원 소유(메모리 격리) vs 제어 흐름(메모리 공유) | 두 개념을 병행성(Concurrency)의 수단으로만 뭉뚱그려 서술하는 오류 |
| 메모리 아키텍처 및 공유 범위 대조 | 스레드는 Stack/Register만 독립, Code/Data/Heap 공유 | 스레드가 Heap을 독자적으로 가진다고 적는 치명적 오개념 |

> 요약: 공장을 통째로 새로 지을 것인지(멀티 프로세스), 기존 공장 안에 일꾼만 늘릴 것인지(멀티 스레드)에 대한 성능과 안정성의 양자택일이다.

## Ⅰ. 개요 및 필요성

- 정의: 프로세스는 실행 파일이 램(RAM)에 적재되어 OS의 통제를 받는 동적인 엔티티이며, 스레드는 프로세스 내부에 존재하는 경량화(Light-weight)된 제어의 흐름
- 배경: 과거 1-Process 1-Thread 모델은 병렬 처리를 위해 프로세스를 포크(`fork`)할 때마다 막대한 메모리 복제 오버헤드와 IPC 통신 비용을 유발
- 필요성: 현대 다중 코어(Multi-core) 아키텍처의 성능을 100% 끌어내기 위해, 컨텍스트 스위칭이 빠르고 자원 공유가 자유로운 동시성 프로그래밍 모델 필수

---

## Ⅱ. 프로세스와 스레드의 메모리 아키텍처 구조도

```text
[ 프로세스 (자원 격리 아키텍처) ]
+-------------------------------------------------------+
|  Code (명령어)  |  Data (전역변수)  |  Heap (동적할당)     | <-- 스레드 간 100% 공유
|-------------------------------------------------------|
|  [ Thread 1 ]         [ Thread 2 ]         [ Thread 3 ]   |
|   - Stack 1            - Stack 2            - Stack 3     | <-- 함수 호출용 지역변수 (격리)
|   - PC, Registers      - PC, Registers      - PC, Regs    | <-- CPU 실행 문맥 (격리)
+-------------------------------------------------------+
* 형제 스레드는 힙(Heap) 영역 주소 공간을 직접 공유하여 즉시 데이터 교환 가능
```

| 구분 | 프로세스 (Process) | 스레드 (Thread) |
|:---|:---|:---|
| 자원 소유 | OS로부터 고유한 4GB(32bit) 주소 공간 할당받음 | 부모 프로세스의 주소 공간 내에 기생(공유)함 |
| 독립 요소 | 페이지 테이블, 파일 디스크립터(FD), 통신 포트 등 | 스택(Stack), 프로그램 카운터(PC), 레지스터 상태 |
| 컨텍스트 스위칭 | 캐시 메모리(TLB)가 모두 Flush(초기화)되어 패널티 극심 | 주소 공간이 같아 캐시를 그대로 유지(Cache Warm)하여 초고속 |

> 요약: 스레드는 오직 자신이 '어디까지 실행했는지(PC)'와 '지역 변수(Stack)'만 들고 다니며, 나머지 거대한 자원은 프로세스(공장)의 것을 공용으로 쓴다.

## Ⅲ. 멀티 프로세스 vs 멀티 스레드 심화 비교 및 트레이드오프

| 비교 축 | 멀티 프로세스 아키텍처 | 멀티 스레드 아키텍처 | 선택 기준 |
|:---|:---|:---|:---|
| 성능/효율 (Overhead) | 프로세스 간 통신 시 파이프, 소켓 등 IPC를 써야 하므로 직렬화/역직렬화 비용 발생 (무거움) | 힙(Heap) 변수 직접 접근으로 데이터 교환 비용 0. 컨텍스트 스위칭 초고속 (가벼움) | 처리량(Throughput) 극대화 시 스레드 |
| 안정성/격리 (Fault Tolerance) | A 프로세스가 죽어도 B 프로세스는 100% 생존 (독립 메모리). 브라우저 탭 구조 | 하나의 스레드가 잘못된 포인터(SegFault)로 힙을 망치면, 전체 프로세스 공멸(Crash) | 단일 장애 차단(샌드박스) 시 프로세스 |
| 개발 복잡도 (Concurrency) | 프로세스 단위 격리로 인해 병행성 버그가 적음 | 공유 자원(Data/Heap) 접근 시 Race Condition 발생. Mutex, Semaphore 등 동기화 필수 | 데드락 리스크 감수 및 숙련된 엔지니어링 |

> 요약: 스레드는 가볍고 빠르지만 한 놈의 실수가 공장 전체를 날려 먹는 연대 책임을 지며, 프로세스는 무겁지만 완벽한 방화벽(격리)을 제공한다.

## Ⅳ. 현대 시스템의 융합 및 발전 동향

| 기술 동향 | 아키텍처 해결책 | 실무 적용 사례 |
|:---|:---|:---|
| 크롬(Chrome) 브라우저의 프로세스 격리 | 멀티 스레드의 공멸 리스크를 피하기 위해, 탭 하나당 스레드가 아닌 '프로세스'를 띄움 | 악성 JS 코드가 다른 탭의 뱅킹 세션 힙을 훔쳐보는 것을 OS 차원의 샌드박스로 원천 차단 |
| 가상 스레드 (Virtual Thread) | OS 커널 스레드의 컨텍스트 스위칭 오버헤드조차 아끼기 위해, 1개의 커널 스레드 위에 수백만 개의 유저 레벨 스레드를 얹음 | Java 21 Project Loom, Go의 Goroutine (메모리 2KB 수준 초경량화) |

> 요약: 단순 성능을 위해서는 스레드를 쓰되, 최신 아키텍처는 극강의 안정성을 위해 프로세스 격리를 도입하거나, 아예 수백만 개를 띄우는 가상 스레드로 한 단계 더 진화했다.

## Ⅴ. 실무 적용 방안 및 결론

**적용 방안 3개:**
1. [웹 서버 아키텍처 선택] Apache HTTP Server의 구동 방식을 설계할 때, 완벽한 격리가 필요한 PHP 구 버전 구동 시에는 멀티 프로세스(Prefork MPM)를 적용하고, 고성능 정적 파일 서빙 시에는 멀티 스레드(Worker MPM)를 적용하여 트레이드오프 최적화
2. [스레드 풀(Thread Pool) 사이징] Java Spring Boot에서 스레드 무한 생성으로 인한 램 고갈(OOM)을 막기 위해, CPU 바운드 작업은 `코어 수 + 1`, I/O 바운드 작업은 `(대기시간/서비스시간) * 코어 수`로 Tomcat 스레드 풀 상한(MaxThreads)을 수학적으로 제한
3. [Thread-Local 변수 활용] 멀티 스레드 환경에서 Mutex 동기화 병목을 없애기 위해, 전역 힙 변수 대신 각 스레드의 전용 저장소(`ThreadLocal` in Java)에 사용자 세션 객체를 저장하여 락 프리(Lock-free) 설계 달성

**결론:**
- 기술사 판단: 프로세스가 "무엇을 실행할 것인가(프로그램)"의 단위라면, 스레드는 "얼마나 동시에 실행할 것인가(병행성)"의 단위다. 스레드는 메모리 공유라는 강력한 무기를 주었지만, 경쟁 상태(Race Condition)와 데드락이라는 거대한 기술 부채를 함께 안겨주었다.
- 향후 방향: 최근 클라우드 환경에서는 컨테이너(Docker)라는 가벼운 프로세스 격리 기술이 발달하면서, 거대한 멀티 스레드 모놀리식 앱을 짜는 대신, 여러 개의 작은 프로세스(마이크로서비스)로 나누어 통신하는 MSA 아키텍처로 회귀·진화하는 추세다.
