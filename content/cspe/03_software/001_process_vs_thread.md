# 📖 【암기용】 개념 완전 이해

## 한눈에
- **개요**: 프로세스는 운영체제가 자원을 할당하는 **실행 단위(자원 소유의 단위)**이고, 스레드는 그 프로세스 안에서 CPU를 배정받는 더 작은 **실행 흐름(스케줄링의 단위)**이다.
- **왜 필요한가**: 한 프로그램 안에서 여러 일을 동시에(동시성) 처리하되, 프로세스를 통째로 복제하는 무거운 비용을 피하려고 자원을 공유하는 경량 실행 흐름이 필요했다.
- **핵심 직관**: 프로세스는 담장·경비원이 있는 독립된 공장(자원 독점)이고, 스레드는 그 공장 하나 안에서 같은 창고·기계를 함께 쓰며 일하는 작업자들(자원 공유)이다.

## 핵심 용어 정리 (내부에 등장하는 것들)

이 키워드를 이해하려면 "실행 단위"라는 상위 개념과, 그 안에서 나뉘는 주소 공간·제어 블록 용어를 먼저 잡아야 한다.

| 용어/표기 | 의미 | 비유·예 |
|:---|:---|:---|
| 실행 단위 (Unit of Execution) | OS가 자원을 주고 CPU를 배정하는 대상의 총칭 (상위 키워드) | "누구에게 일을 시킬지"의 대상 |
| 동시성 (Concurrency) | 여러 흐름을 번갈아/동시에 진행시켜 처럼 보이게 하는 성질 | 요리사가 냄비 여러 개를 번갈아 젓기 |
| 프로세스 (Process) | 메모리에 적재되어 실행 중인 프로그램, 자원 소유·보호의 단위 | 독립 건물(공장), 옆 건물과 벽으로 격리 |
| 스레드 (Thread) | 프로세스 내부의 제어 흐름, CPU 스케줄링의 단위 | 공장 안에서 일하는 작업자 |
| 주소 공간 (Address Space) | 프로세스가 보는 메모리 전체 = Code·Data·Heap·Stack | 공장 부지 전체 |
| Code / Data | 실행 명령어 / 전역·정적 변수 (스레드 간 **공유**) | 공용 작업 매뉴얼·게시판 |
| Heap | 실행 중 동적 할당 영역 (`malloc`, `new`) (스레드 간 **공유**) | 공용 창고 |
| Stack | 함수 호출·지역 변수 저장 영역 (스레드마다 **독립**) | 작업자 개인 작업대 |
| PCB (Process Control Block) | 프로세스 상태를 담는 OS 자료구조 (상세는 002) | 공장 전체의 관리 대장 |
| TCB (Thread Control Block) | 스레드별 상태(PC·레지스터·스택 포인터) 저장 블록 | 작업자 개인 수첩 |
| 컨텍스트 스위칭 (Context Switching) | 실행 대상을 바꾸며 상태를 저장/복원하는 작업 (상세는 002) | 작업자 교대 인수인계 |
| 커널 스레드 / 유저 스레드 | OS 커널이 인지·스케줄링하는 스레드 / 라이브러리가 사용자 영역에서 관리하는 스레드 | 정식 직원(회사 등록) / 반장이 사적으로 굴리는 인력 |
| IPC (Inter-Process Communication) | 격리된 프로세스끼리 데이터를 주고받는 수단 | 건물 간 우편·전용선 |
| 경쟁 상태 (Race Condition) | 공유 자원에 여러 스레드가 동시 접근해 결과가 순서에 좌우되는 오류 | 두 명이 같은 장부에 동시에 기입 |
| 스레드 안전 (Thread-Safe) | 여러 스레드가 동시 접근해도 결과가 정확하도록 보장된 설계 | 한 명씩만 장부를 쓰게 하는 규칙 |

## 깊이 이해
- **배경·문제의식**: 초기 OS는 작업마다 프로세스를 새로 만들었는데, 프로세스 생성은 주소 공간 전체를 확보·복사(`fork()` 시 Copy-on-Write 이전엔 전체 복사)해야 해 무겁다. 웹 서버처럼 초당 수천 요청을 받으면 요청마다 프로세스를 띄우는 비용을 감당할 수 없어, 주소 공간은 공유하고 실행 흐름만 늘리는 스레드가 도입됐다.
- **작동 원리(어떻게+왜)**: 프로세스는 Code·Data·Heap·Stack을 모두 독립 할당받아 서로의 메모리를 못 본다(그래서 안전하지만 통신이 비쌈). 스레드는 한 프로세스의 Code·Data·Heap을 **공유**하고, 함수 호출 문맥이 흐름마다 달라야 하므로 Stack과 PC(Program Counter)·레지스터만 **독립**으로 가진다. 공유가 있으니 통신이 공짜지만, 같은 Heap을 동시에 건드리면 경쟁 상태가 생겨 동기화가 필요해진다.
- **비유**: 크롬 창을 여러 개 띄우면 메모리를 많이 먹지만(멀티프로세스), 창 하나 안에서 탭을 여러 개 여는 것은 가볍다(멀티스레드). 다만 순수 멀티스레드는 탭 하나가 죽으면 창 전체가 죽는다 — 그래서 실제 크롬은 렌더러를 프로세스로 분리해 안정성을 택했다.
- **구체 예시**: Linux에서 프로세스 생성은 수백 µs~ms대, 스레드 생성은 수십 µs대로 대략 한 자릿수 이상 저렴하다. 스레드 전환은 주소 공간(페이지 테이블)이 그대로라 TLB를 비우지 않지만, 프로세스 전환은 페이지 테이블이 바뀌어 TLB 플러시가 동반돼 더 비싸다.
- **흔한 오해·주의점**: "멀티스레드가 항상 낫다"는 오해다. 자원 공유는 경쟁 상태·데드락 위험과 "한 스레드 크래시 → 프로세스 전체 종료"라는 취약점을 낳는다. 격리·보안이 우선이면 멀티프로세스가 옳다. 또 커널이 모르는 유저 스레드는 하나가 블로킹 시스템콜을 하면 프로세스 전체가 멈출 수 있어, 매핑 모델(1:1 / M:N)을 함께 봐야 한다.

## 연결 개념
- PCB·컨텍스트 스위칭 (002 참조) — 전환 시 저장/복원되는 상태와 그 오버헤드
- 프로세스 상태 전이 (003 참조) — 실행 단위가 Ready·Running·Blocked를 오가는 생애주기
- 세마포어·뮤텍스·모니터 (012 참조) — 스레드 공유 자원의 동기화 수단

# 📝 【답안용】 시험 답안 템플릿

## 핵심 인사이트 (3줄 요약)

> 1. **본질**: 프로세스는 자원 소유·보호의 단위, 스레드는 그 내부 CPU 스케줄링의 단위이며, 차이의 핵심은 주소 공간(Code·Data·Heap) 공유 여부임.
> 2. **가치**: 스레드는 주소 공간을 공유해 생성·전환 오버헤드와 통신 비용을 낮춰 처리량을 높임.
> 3. **판단 포인트**: 성능·자원 효율이면 멀티스레드, 장애 격리·보안이면 멀티프로세스이며 실무는 둘을 계층적으로 혼용함.

## 출제 의도 및 답안 포인트

| 출제 의도 | 반드시 짚을 핵심 | 감점 회피 포인트 |
|:---|:---|:---|
| 자원 소유와 실행 흐름의 분리 이해 | Code·Data·Heap 공유 / Stack·PC·레지스터 독립 | 공유·독립 영역 반대 서술 |
| 멀티프로세스·멀티스레드 선택 기준 | 오버헤드, 통신(IPC vs 공유메모리), 격리성 | 성능 우위 일방 단정 |
| 병행 처리 시 위험 통제 방안 | 경쟁 상태·데드락, 스레드 안전 설계 | 추상적 "안정성" 서술 |

> 요약: 공유 영역과 독립 영역을 정확히 구분하고, 오버헤드 이득과 동기화·격리 비용의 트레이드오프로 선택 기준을 제시함.

## Ⅰ. 개요 및 필요성

- 개요: 프로세스는 OS가 자원을 할당하는 실행 단위, 스레드는 그 내부에서 자원을 공유하는 CPU 스케줄링 단위임
- 배경: 프로세스 단위 다중작업은 주소 공간 복제로 생성·전환 비용이 커, 공유 기반 경량 실행 흐름이 요구됨
- 필요성: 대규모 웹·트랜잭션 서버에서 요청당 오버헤드를 줄이고 처리량(Throughput)을 확보하려면 멀티스레드 모델이 필수임

---

## Ⅱ. 구조 및 구성요소

- 주소 공간 구성(선형 구조도):

```text
프로세스 주소 공간
  -> Code / Data / Heap  (한 프로세스 내 모든 스레드가 공유)
  -> Thread 1: Stack 1 / PC 1 / Registers 1  (독립)
  -> Thread 2: Stack 2 / PC 2 / Registers 2  (독립)
```

| 구성요소 | 프로세스 (Process) | 스레드 (Thread) |
|:---|:---|:---|
| 성격 | 자원 할당·보호의 단위 | CPU 스케줄링의 단위 |
| 주소 공간 | Code·Data·Heap·Stack 모두 독립 | Code·Data·Heap 공유, Stack만 독립 |
| 상태 제어 블록 | PCB (Process Control Block) | TCB (Thread Control Block) |
| 통신 수단 | IPC(파이프·소켓·공유메모리) | 공유 메모리 직접 접근 |
| 매핑 모델 | - | 커널/유저 스레드, 1:1·M:N 매핑 |

> 요약: 스레드는 Code·Data·Heap을 공유하고 Stack·PC·레지스터만 독립으로 유지해 상태 관리를 경량화함.

---

## Ⅲ. 동작원리 및 흐름도

```text
프로세스 기동(주소공간·PCB 확보) -> 스레드 풀 초기화
  -> 요청 인입 -> 여유 스레드 배정(TCB) -> 공유 Data/Heap 접근(동기화)
  -> 처리 완료 -> 스레드 반환 / 프로세스 종료 시 공유자원 일괄 회수
```

- 1단계 [프로세스 생성]: OS가 가상 주소 공간과 PCB를 할당해 실행 단위를 확보함
- 2단계 [스레드 분기]: 프로세스 내에서 공유 자원 포인터와 독립 스택을 갖는 스레드를 생성(TCB 등록)함
- 3단계 [실행·동기화]: 각 스레드가 CPU를 점유해 실행하고, 공유 자원 접근 시 뮤텍스 등으로 상호 배제함
- 4단계 [종료·회수]: 스레드 종료 시 스택 등 로컬 자원 반환, 프로세스 종료 시 공유 자원 일괄 회수함

> 요약: 프로세스가 큰 틀의 자원을 확보하고, 스레드들이 그 자원을 공유하며 실제 명령어 흐름을 병행 처리함.

---

## Ⅳ. 특징

- 생성 경량화: 스레드는 주소 공간 복제 없이 TCB·스택만 할당해 생성·종료가 프로세스 대비 한 자릿수 이상 빠름
- 전환 비용 절감: 스레드 전환은 페이지 테이블 유지로 TLB 플러시가 없어 컨텍스트 스위칭 지연이 작음
- 통신 효율: 공유 메모리 직접 접근으로 IPC 없이 데이터 교환이 가능함
- 트레이드오프: 자원 공유로 경쟁 상태가 발생하고, 한 스레드 크래시가 프로세스 전체를 종료시킬 수 있어 스레드 안전 설계가 전제됨

---

## Ⅴ. 심화 비교 및 적용 판단

| 구분 | 멀티 프로세스 (Multi-Process) | 멀티 스레드 (Multi-Thread) | 선택 기준 |
|:---|:---|:---|:---|
| 격리성 | 주소 공간 분리로 장애 격리 우수 | 한 스레드 크래시가 전체 영향 | 고가용성·보안 요구 여부 |
| 통신 | IPC(파이프·소켓·공유메모리) | 공유 메모리 직접 접근 | 데이터 교환 빈도·지연 요구 |
| 전환 오버헤드 | 큼(TLB·캐시 플러시 동반) | 작음(스택·레지스터만 교체) | 문맥 전환 빈도 |

> 요약: 격리·보안이 우선이면 멀티프로세스, 응답성·자원 효율이 우선이면 멀티스레드를 택함.

**리스크·대응 (불릿):**
- 경쟁 상태·데드락: 공유 자원 동시 접근·상호 대기 → 락 획득 순서 강제, 타임아웃 적용 (지표: Lock wait time)
- 스레드 폭증: 무제한 생성으로 메모리 고갈 → 스레드 풀 상한, 비동기 I/O 전환 (지표: Active thread count)

**점검 지표 (불릿):**
- 성능: 컨텍스트 스위칭 지연, 처리량(TPS)
- 운영: 메모리 사용률, 캐시 적중률(Cache Hit Ratio)

---

## Ⅵ. 실무 적용 및 결론

**적용 방안 3개:**
1. 아키텍처 선정: I/O 바운드 작업은 스레드 풀 + 비동기 논블로킹(epoll)로 처리해 CPU 활용률을 높임
2. 동기화 설계: 공유 데이터에 뮤텍스·세마포어 또는 Lock-free 자료구조를 적용해 스레드 안전을 확보함
3. 계층적 격리: 크롬 렌더러처럼 장애 영향이 큰 영역은 프로세스로 분리하고, 내부는 스레드로 병행 처리함

**결론 (2줄):**
- 기술사 판단: 성능 지향 시스템은 멀티스레드를 기본으로 하되, 공유 상태를 최소화(불변 객체·메시지 전달)해 동기화 병목을 통제함
- 향후 방향: Java Virtual Thread·Go Goroutine 등 M:N 매핑 경량 스레드로 커널 개입과 전환 비용을 극단적으로 낮추는 추세임
