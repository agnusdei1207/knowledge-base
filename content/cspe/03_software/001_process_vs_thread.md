# 📖 【암기용】 개념 완전 이해

## 한눈에
- **정의**: 프로세스는 OS로부터 독립된 자원을 할당받는 **'자원 소유의 단위'**이며, 스레드는 프로세스 내부에서 CPU를 배정받아 실행되는 **'스케줄링의 단위'**임.
- **핵심 직관**: 프로세스는 독립된 설비와 창고를 가진 '공장'이고, 스레드는 그 공장 안에서 설비를 공유하며 움직이는 '작업자'임.
- **왜 필요한가**: 프로세스 생성/교체는 무겁고(Heavy-weight) 통신이 어려움. 스레드는 자원을 공유해 가볍고(Light-weight) 빠른 협업이 가능함.

## 깊이 이해
- **배경 (격리 vs 효율)**: 초기 OS는 멀티태스킹을 위해 프로세스를 통째로 복제(`fork`)했으나, 메모리 낭비와 문맥 전환(Context Switch) 부하가 심각했음. 이를 해결하기 위해 "자원은 공유하되 실행 흐름만 분리"하는 스레드 개념이 도입됨.
- **메모리 구조의 마법**: 
    - **프로세스**: Code, Data, Heap, Stack을 모두 독립적으로 가짐. (MMU가 각 프로세스에게 가상 메모리 공간을 통째로 빌려줌)
    - **스레드**: Code, Data, Heap은 공유하고 **Stack과 Register(PC 포함)만 독립적**으로 가짐. 
- **작동 원리 (Copy-on-Write)**: 프로세스 생성 시 부모 자원을 그대로 복사하는 대신, 쓰기 작업이 발생할 때만 실제 복사하는 CoW 기술을 통해 프로세스 생성 비용을 최적화하기도 함.
- **비유 (크롬 브라우저)**: 크롬의 탭 하나가 죽어도 전체가 안 죽는 이유는 각 탭을 '프로세스'로 띄웠기 때문(격리). 반면 한 탭 내에서 자바스크립트가 실행되고 이미지를 다운로드하는 등 병렬 작업은 '스레드'가 담당함.

## 연결 개념
- **PCB/TCB (002)**: 관리 장부의 차이.
- **임계 구역 (014)**: 스레드가 자원을 공유할 때 발생하는 '동시성 지옥'의 입구.
- **가상 스레드 (027)**: 커널 스레드의 한계를 넘는 수백만 개의 초경량 흐름.

# 📝 【답안용】 시험 답안 템플릿

## 핵심 인사이트 (3줄 요약)
> 1. **본질**: 프로세스는 '자원 보호와 독립성'을 지향하고, 스레드는 '자원 공유와 성능 효율'을 지향하는 실행 단위임.
> 2. **가치**: 스레드는 TCB 기반의 경량 문맥 전환과 공유 메모리를 통한 고속 통신(IPC 불필요)으로 시스템 처리량을 극대화함.
> 3. **판단**: 안정성·보안이 중시되면 멀티프로세스(Chrome), 응답성·자원 효율이 중시되면 멀티스레드(Web Server) 모델을 채택함.

## Ⅰ. 자원 소유와 실행 흐름의 분리, 프로세스와 스레드 개요
- **프로세스(Process)**: 실행 중인 프로그램의 인스턴스로, OS가 메모리, 파일 핸들 등을 할당하는 독립적인 **자원 소유의 단위**.
- **스레드(Thread)**: 프로세스 내에서 할당된 자원을 공유하며 실제 명령어를 실행하는 **CPU 스케줄링 및 제어 흐름의 단위**.

## Ⅱ. 프로세스와 스레드의 구조적 차이 및 비교

### 1. 프로세스와 스레드의 메모리 맵(Memory Map) 구조
```text
┌───────────────── 프로세스 (Process) ────────────────┐
│ ┌──────────── 공유 영역 (Shared) ────────────┐      │
│ │ Code (명령어) | Data (전역) | Heap (동적) │      │
│ └────────────────────────────────────────────┘      │
│ ┌── 스레드 1 ──┐   ┌── 스레드 2 ──┐   ┌── 스레드 3 ──┐ │
│ │ Stack | PC   │   │ Stack | PC   │   │ Stack | PC   │ │
│ └──────────────┘   └──────────────┘   └──────────────┘ │
└─────────────────────────────────────────────────────┘
```

### 2. 기술적 속성 상세 비교
| 구분 | 프로세스 (Process) | 스레드 (Thread) | 비고 |
|:---:|:---|:---|:---|
| **할당 단위** | OS 자원(메모리, I/O) 할당 단위 | CPU 실행 시간 할당 단위 | - |
| **자원 공유** | 독립적 (공유하려면 IPC 필요) | 동일 프로세스 내 Heap 등 공유 | **핵심 차이** |
| **전환 비용** | 높음 (Cache/TLB Flush 발생) | 낮음 (Stack/Register만 교체) | 성능 영향 |
| **장애 영향** | 프로세스 간 격리 (안전) | 한 스레드 오류가 전체 종료 | 안정성 |
| **관리 구조** | PCB (Process Control Block) | TCB (Thread Control Block) | 002 연계 |

## Ⅲ. 문맥 전환(Context Switching) 메커니즘의 차이

### 1. 프로세스 문맥 전환 (Heavy-weight)
- MMU의 페이지 테이블 교체, **TLB(Translation Lookaside Buffer) 캐시 Flush** 발생.
- 캐시 미스(Cache Miss) 확률 급증으로 인한 성능 저하 심화.

### 2. 스레드 문맥 전환 (Light-weight)
- 가상 메모리 공간을 공유하므로 페이지 테이블 교체 불필요.
- 캐시 데이터 유지가 가능하며, 레지스터와 스택 포인터만 복원하여 고속 전환.

## Ⅳ. 병행 처리 모델의 트레이드오프 (Trade-off)

- **멀티프로세싱 (Multi-Processing)**:
    - **장점**: 강한 격리성으로 보안 및 안정성 우수. 좀비 프로세스 방지 용이.
    - **단점**: IPC(Inter-Process Communication) 비용(Pipe, Message Queue) 발생, 메모리 소모 큼.
- **멀티스레딩 (Multi-Threading)**:
    - **장점**: 경제성(Resource Economy), 데이터 교환의 편리성, 빠른 응답성.
    - **단점**: 동기화 문제(Race Condition), 교착 상태(Deadlock), 디버깅 난해.

## Ⅴ. 실무적 고려사항 및 심화 기술

### 1. 스레드 안전(Thread-Safe) 확보 방안
- **상호 배제(Mutex/Semaphore)**: 공유 자원에 대한 원자적 접근 보장.
- **불변 객체(Immutable)**: 상태를 변경하지 않아 락(Lock) 없이 안전하게 공유.
- **Thread Local Storage (TLS)**: 스레드 전용 저장소를 사용하여 간섭 제거.

### 2. 최신 동향: User-level 경량 스레드
- **Java Virtual Thread**: 플랫폼 스레드(1:1)의 한계를 극복하여 수만 개의 동시성 처리.
- **Go Goroutine**: M:N 매핑을 통해 커널 개입을 최소화한 스케줄링 구현.

## Ⅵ. 기술사 관점의 결론
- 시스템 설계 시 **'격리성(Isolation)'**이 필요하면 프로세스를, **'성능(Performance)'**과 협업이 중요하면 스레드를 선택함.
- 최근에는 마이크로서비스(MSA)와 컨테이너 환경 확산에 따라 프로세스 단위의 격리와 내부 스레드 단위의 효율을 계층적으로 조합하는 **Hybrid 방식**이 표준임.
