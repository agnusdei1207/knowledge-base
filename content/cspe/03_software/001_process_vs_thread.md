# 📖 【암기용】 개념 완전 이해

> 목적: 이 개념을 처음 보는 사람도 완벽히 이해하게 만든다. 시험 답안 양식이 아니라, 이해를 위한 친절한 설명이다.

## 한눈에
- **개요**: **프로세스(Process)**와 **스레드(Thread)**는 운영체제가 제공하는 **동시성(Concurrency) 실행 단위**다. 프로세스는 OS로부터 메모리·파일 등 자원을 독립적으로 할당받는 '자원 소유의 단위'이고, 스레드는 그 프로세스 안에서 CPU 명령어를 실제로 실행하는 '제어 흐름의 최소 단위'다.
- **왜 필요한가**: 프로세스만 있던 시절엔 일을 하나 더 시키려면 프로세스를 통째로 하나 더 만들어야 했다(멀티 프로세스). 그런데 프로세스 생성은 메모리 전체 공간을 새로 마련하고 부모와 통신(IPC)까지 별도로 뚫어야 해서 비용이 크다. "메모리 공간은 하나만 만들고, 그 안에서 일하는 흐름만 여러 개 두자"는 발상이 스레드다.
- **핵심 직관**: 워드 프로세서 프로그램 하나를 켰다. 이것이 프로세스 1개다. 그 안에서 화면에 글자를 그리는 흐름, 맞춤법을 백그라운드에서 검사하는 흐름, 자동 저장을 하는 흐름이 각각 스레드다. 셋 다 같은 문서(메모리)를 보고 있어서 서로 데이터를 즉시 주고받을 수 있다.

## 핵심 용어 정리 (내부에 등장하는 것들)

| 용어 | 의미 | 비유 |
|:---|:---|:---|
| 동시성(Concurrency) | 여러 실행 흐름을 번갈아·동시에 진행시키는 능력 — 프로세스·스레드가 이를 구현하는 단위 | 한 사람이 여러 일을 번갈아 처리 |
| 프로세스(Process) | OS로부터 독립된 주소 공간(메모리)을 할당받아 실행 중인 프로그램 인스턴스 | 독채 건물 한 채 |
| 스레드(Thread) | 프로세스 내부에서 코드를 실제로 실행하는 흐름의 단위. 한 프로세스에 여러 개 존재 가능 | 건물 안에서 각자 일하는 사람 |
| 코드(Code) 영역 | 실행할 명령어(기계어)가 저장된 영역 — 프로세스 내 모든 스레드가 공유 | 건물의 설계도(공용) |
| 데이터(Data) 영역 | 전역 변수·정적 변수가 저장된 영역 — 스레드 간 공유 | 건물의 공용 게시판 |
| 힙(Heap) | `malloc`/`new`로 동적 할당한 메모리 — 스레드 간 공유 | 건물의 공용 창고 |
| 스택(Stack) | 함수 호출 시 지역 변수·리턴 주소가 쌓이는 영역 — 스레드마다 독립 | 각자의 개인 작업 수첩 |
| PC(Program Counter) 레지스터 | "다음에 실행할 명령어 주소"를 가리키는 레지스터 — 스레드마다 독립 | 각자 읽고 있는 페이지 번호 |
| IPC(Inter-Process Communication) | 서로 다른 프로세스가 데이터를 주고받는 통신 방법(파이프·소켓·메시지 큐 등) | 다른 건물끼리 우편으로 연락 |
| 경쟁 상태(Race Condition) | 여러 스레드가 같은 데이터를 동시에 건드려 결과가 실행 순서에 따라 달라지는 오류 | 공용 창고에서 두 사람이 동시에 같은 재고를 고침 |
| 뮤텍스/세마포어 | 공유 자원에 한 번에 하나(또는 정해진 수)만 접근하도록 막는 동기화 도구 | 창고 문 열쇠 하나만 존재 |

## 깊이 이해

### 왜 프로세스만으로는 부족했나 (배경)
- 두 프로세스는 메모리 공간이 완전히 분리돼 있어, 서로 데이터를 주고받으려면 커널을 거치는 IPC(파이프, 소켓, 공유 메모리, 메시지 큐)를 써야 한다. 이는 커널 모드 전환과 데이터 복사가 필요해 오버헤드가 크다.
- 반면 같은 프로세스 안의 스레드들은 힙·데이터 영역을 이미 공유하고 있어, 포인터 하나만 넘기면 통신이 끝난다. 통신 비용이 사실상 0에 가깝다.
- **구체 수치로 보는 무게 차이**: 리눅스 프로세스를 하나 만드는 `fork()`는 페이지 테이블 등 프로세스 메타데이터를 복제해 보통 수백 마이크로초가 걸리는 반면, 같은 프로세스 안에서 스레드를 만드는 `pthread_create()`는 새 스택(가상 주소 공간, 보통 기본 8MB를 예약하되 실제 사용한 페이지만 물리 메모리에 적재)만 준비하면 되어 수십 마이크로초 수준으로 훨씬 빠르다.

### 메모리 구조 — 무엇을 공유하고 무엇을 독립적으로 갖는가
- 프로세스는 코드(Code)·데이터(Data)·힙(Heap)·스택(Stack) 4대 영역을 가진다.
- 프로세스 안의 스레드들은 코드·데이터·힙은 **형제 스레드와 100% 공유**한다. 반면 스택과 PC 레지스터, 그 외 CPU 레지스터 상태는 **스레드마다 독립적으로 소유**한다.
- 스택을 독립적으로 갖는 이유는 함수 호출이 스레드마다 독립적이어야 하기 때문이다. 스레드 A가 함수를 5단계 깊이로 호출 중인데, 스레드 B도 같은 스택을 쓴다면 두 흐름의 지역 변수와 리턴 주소가 뒤섞여 함수 호출 자체가 불가능해진다. PC도 마찬가지로 "각 스레드가 지금 어느 명령어를 실행 중인지"를 독립적으로 기억해야 한다.

### 구체 예시로 보는 무게 차이
- 웹 서버가 동시 접속자 1,000명을 처리한다고 하자. 클라이언트 1명당 프로세스 1개를 띄우는 방식(예: 구형 Apache prefork)이면, 프로세스 1개가 메모리·페이지 테이블을 포함해 대략 수 MB~십수 MB를 차지하므로 1,000개면 수 GB 단위 메모리가 필요하다. 반면 클라이언트 1명당 스레드 1개(스레드 풀)로 처리하면, 스레드는 코드·데이터·힙을 공유하고 스택(보통 수백 KB~1MB 수준으로 조절 가능)만 추가로 필요하므로 총 메모리 소모가 프로세스 방식의 몇 분의 1로 줄어든다.
- **경쟁 상태를 수치로 보기**: 전역 변수 `count = 0`에 스레드 A와 B가 동시에 `count++`를 실행한다고 하자. `count++`는 실제로 ① 메모리에서 count 읽기 ② +1 계산 ③ 다시 저장, 3단계로 쪼개진다. A와 B가 모두 count=0을 읽은 뒤 각자 1로 계산해서 저장하면, 두 번 증가시켰는데도 최종값은 기대한 2가 아니라 1이 되어버린다. 이것이 힙·전역 변수 공유가 낳는 경쟁 상태이며, 뮤텍스로 이 3단계를 한 스레드씩만 통과하도록 막아야 해결된다.

### 판별 원리 — 언제 프로세스, 언제 스레드인가
- **격리(안정성)가 우선**이면 프로세스를 선택한다. 한 흐름이 죽어도 다른 흐름에 영향을 주면 안 되는 경우(예: 브라우저 탭, 플러그인 실행)다.
- **성능(가벼움)과 데이터 공유가 우선**이면 스레드를 선택한다. 짧은 시간에 대량의 작업을 처리하며 데이터를 자주 주고받아야 하는 경우(예: 이미지 처리 워커, I/O 처리 워커)다.
- 판별 질문: "이 실행 흐름이 죽었을 때 나머지가 같이 죽어도 괜찮은가?" 괜찮으면 스레드, 안 되면 프로세스다.

### 비유와 흔한 오해
- **비유**: 프로세스는 독채 건물, 스레드는 그 건물 안에서 일하는 직원이다. 직원끼리는 같은 사무실(힙)의 서류를 바로 주고받지만, 옆 건물(다른 프로세스) 직원과는 우편(IPC)을 보내야 한다.
- **오해**: "스레드가 무조건 좋다"는 착각이다. 힙을 공유한다는 것은 양날의 검이라, 스레드 하나가 잘못된 포인터로 힙을 훼손하면 같은 프로세스의 다른 스레드까지 전부 크래시난다(공멸). 그래서 크롬 브라우저는 오히려 탭마다 스레드가 아닌 별도 프로세스를 쓴다 — 악성 탭 하나가 죽어도 다른 탭은 살리기 위해서다.

## 연결 개념
- **PCB와 TCB(002)**: OS가 프로세스를 관리하는 장부가 PCB, 스레드를 관리하는 더 가벼운 장부가 TCB다. 프로세스 안 스레드들은 같은 PCB(주소 공간 정보)를 공유하되, 스택·PC는 각자의 TCB에 따로 기록된다.
- **컨텍스트 스위칭(002)**: 스레드 간 교체는 같은 주소 공간 안의 이동이라 캐시(TLB)를 비울 필요가 없어 빠르다. 프로세스 간 교체는 주소 공간 자체가 바뀌므로 캐시를 전부 비워야 해서 훨씬 무겁다.
- **프로세스 스케줄링(004)**: 스케줄러가 CPU를 배분하는 대상은 원래 프로세스였으나, 현대 OS는 스레드 단위로 스케줄링한다 — 그래서 한 프로세스 안 여러 스레드가 멀티코어에서 동시에 돌 수 있다.

# 📝 【답안용】 시험 답안 템플릿

> 목적: 시험장에서 25분에 그대로 쓰는 답안 양식. 작성방식(추상표현 금지·수치·도식·문제유형 전환)을 엄격히 지킨다.
> 핵심: 이 시험은 정보를 많이 나열하는 시험이 아니라, 문제 신호어에서 출제자 의도를 읽고 핵심 논점을 선별해 쓰는 시험이다.

## 핵심 인사이트 (3줄 요약)

> 1. **본질**: 프로세스는 OS로부터 자원을 할당받는 격리된 '자원 소유의 단위'이며, 스레드는 프로세스 내에서 CPU를 점유하는 '실행 흐름의 최소 단위'다.
> 2. **가치**: 스레드 모델은 메모리 공간(Code/Data/Heap)을 공유하여 컨텍스트 스위칭 비용을 최소화하고 높은 처리량(Throughput)을 달성한다.
> 3. **판단 포인트**: 자원 공유에 따른 동시성(Race Condition) 리스크와 프로세스 격리 기반의 안정성(Fault Tolerance) 사이의 트레이드오프를 아키텍처 관점에서 대조해야 한다.

## 출제 의도 및 답안 포인트

| 출제 의도 | 반드시 짚을 핵심 | 감점 회피 포인트 |
|:---|:---|:---|
| 프로세스와 스레드의 본질적 차이 규명 | 자원 소유(메모리 격리) vs 제어 흐름(메모리 공유) | 두 개념을 병행성(Concurrency)의 수단으로만 뭉뚱그려 서술하는 오류 |
| 메모리 아키텍처 및 공유 범위 대조 | 스레드는 Stack/Register만 독립, Code/Data/Heap 공유 | 스레드가 Heap을 독자적으로 가진다고 적는 치명적 오개념 |

> 요약: 공장을 통째로 새로 지을 것인지(멀티 프로세스), 기존 공장 안에 일꾼만 늘릴 것인지(멀티 스레드)에 대한 성능과 안정성의 양자택일이다.

## Ⅰ. 개요 및 필요성

- 정의: 프로세스는 실행 파일이 램(RAM)에 적재되어 OS의 통제를 받는 동적인 엔티티이며, 스레드는 프로세스 내부에 존재하는 경량화(Light-weight)된 제어의 흐름
- 배경: 과거 1-Process 1-Thread 모델은 병렬 처리를 위해 프로세스를 포크(`fork`)할 때마다 막대한 메모리 복제 오버헤드와 IPC 통신 비용을 유발
- 필요성: 현대 다중 코어(Multi-core) 아키텍처의 성능을 100% 끌어내기 위해, 컨텍스트 스위칭이 빠르고 자원 공유가 자유로운 동시성 프로그래밍 모델 필수

## Ⅱ. 프로세스와 스레드의 메모리 아키텍처 구조도

```text
[ 프로세스 (자원 격리 아키텍처) ]
+-------------------------------------------------------+
|  Code (명령어)  |  Data (전역변수)  |  Heap (동적할당)     | <-- 스레드 간 100% 공유
|-------------------------------------------------------|
|  [ Thread 1 ]         [ Thread 2 ]         [ Thread 3 ]   |
|   - Stack 1            - Stack 2            - Stack 3     | <-- 함수 호출용 지역변수 (격리)
|   - PC, Registers      - PC, Registers      - PC, Regs    | <-- CPU 실행 문맥 (격리)
+-------------------------------------------------------+
* 형제 스레드는 힙(Heap) 영역 주소 공간을 직접 공유하여 즉시 데이터 교환 가능
```

| 구분 | 프로세스 (Process) | 스레드 (Thread) |
|:---|:---|:---|
| 자원 소유 | OS로부터 고유한 4GB(32bit) 주소 공간 할당받음 | 부모 프로세스의 주소 공간 내에 기생(공유)함 |
| 독립 요소 | 페이지 테이블, 파일 디스크립터(FD), 통신 포트 등 | 스택(Stack), 프로그램 카운터(PC), 레지스터 상태 |
| 컨텍스트 스위칭 | 캐시 메모리(TLB)가 모두 Flush(초기화)되어 패널티 극심 | 주소 공간이 같아 캐시를 그대로 유지(Cache Warm)하여 초고속 |

> 요약: 스레드는 오직 자신이 '어디까지 실행했는지(PC)'와 '지역 변수(Stack)'만 들고 다니며, 나머지 거대한 자원은 프로세스(공장)의 것을 공용으로 쓴다.

## Ⅲ. 멀티 프로세스 vs 멀티 스레드 심화 비교 및 트레이드오프

| 구분 | 멀티 프로세스 아키텍처 | 멀티 스레드 아키텍처 | 선택 기준 |
|:---|:---|:---|:---|
| 성능/효율 (Overhead) | 프로세스 간 통신 시 파이프, 소켓 등 IPC를 써야 하므로 직렬화/역직렬화 비용 발생 (무거움) | 힙(Heap) 변수 직접 접근으로 데이터 교환 비용 0. 컨텍스트 스위칭 초고속 (가벼움) | 처리량(Throughput) 극대화 시 스레드 |
| 안정성/격리 (Fault Tolerance) | A 프로세스가 죽어도 B 프로세스는 100% 생존 (독립 메모리). 브라우저 탭 구조 | 하나의 스레드가 잘못된 포인터(SegFault)로 힙을 망치면, 전체 프로세스 공멸(Crash) | 단일 장애 차단(샌드박스) 시 프로세스 |
| 개발 복잡도 (Concurrency) | 프로세스 단위 격리로 인해 병행성 버그가 적음 | 공유 자원(Data/Heap) 접근 시 Race Condition 발생. Mutex, Semaphore 등 동기화 필수 | 데드락 리스크 감수 및 숙련된 엔지니어링 |

> 요약: 스레드는 가볍고 빠르지만 한 놈의 실수가 공장 전체를 날려 먹는 연대 책임을 지며, 프로세스는 무겁지만 완벽한 방화벽(격리)을 제공한다.

## Ⅳ. 현대 시스템의 융합 및 발전 동향

| 기술 동향 | 아키텍처 해결책 | 실무 적용 사례 |
|:---|:---|:---|
| 크롬(Chrome) 브라우저의 프로세스 격리 | 멀티 스레드의 공멸 리스크를 피하기 위해, 탭 하나당 스레드가 아닌 '프로세스'를 띄움 | 악성 JS 코드가 다른 탭의 뱅킹 세션 힙을 훔쳐보는 것을 OS 차원의 샌드박스로 원천 차단 |
| 가상 스레드 (Virtual Thread) | OS 커널 스레드의 컨텍스트 스위칭 오버헤드조차 아끼기 위해, 1개의 커널 스레드 위에 수백만 개의 유저 레벨 스레드를 얹음 | Java 21 Project Loom, Go의 Goroutine (메모리 2KB 수준 초경량화) |

> 요약: 단순 성능을 위해서는 스레드를 쓰되, 최신 아키텍처는 극강의 안정성을 위해 프로세스 격리를 도입하거나, 아예 수백만 개를 띄우는 가상 스레드로 한 단계 더 진화했다.

## Ⅴ. 실무 적용 방안 및 결론

**적용 방안 3개:**
1. [웹 서버 아키텍처 선택] Apache HTTP Server의 구동 방식을 설계할 때, 완벽한 격리가 필요한 PHP 구 버전 구동 시에는 멀티 프로세스(Prefork MPM)를 적용하고, 고성능 정적 파일 서빙 시에는 멀티 스레드(Worker MPM)를 적용하여 트레이드오프 최적화
2. [스레드 풀(Thread Pool) 사이징] Java Spring Boot에서 스레드 무한 생성으로 인한 램 고갈(OOM)을 막기 위해, CPU 바운드 작업은 `코어 수 + 1`, I/O 바운드 작업은 `(대기시간/서비스시간) * 코어 수`로 Tomcat 스레드 풀 상한(MaxThreads)을 수학적으로 제한
3. [Thread-Local 변수 활용] 멀티 스레드 환경에서 Mutex 동기화 병목을 없애기 위해, 전역 힙 변수 대신 각 스레드의 전용 저장소(`ThreadLocal` in Java)에 사용자 세션 객체를 저장하여 락 프리(Lock-free) 설계 달성

**결론:**
- 기술사 판단: 프로세스가 "무엇을 실행할 것인가(프로그램)"의 단위라면, 스레드는 "얼마나 동시에 실행할 것인가(병행성)"의 단위다. 스레드는 메모리 공유라는 강력한 무기를 주었지만, 경쟁 상태(Race Condition)와 데드락이라는 거대한 기술 부채를 함께 안겨주었다.
- 향후 방향: 최근 클라우드 환경에서는 컨테이너(Docker)라는 가벼운 프로세스 격리 기술이 발달하면서, 거대한 멀티 스레드 모놀리식 앱을 짜는 대신, 여러 개의 작은 프로세스(마이크로서비스)로 나누어 통신하는 MSA 아키텍처로 회귀·진화하는 추세다.
