## Ⅰ. 개요
- **정의**: 균형 다진 탐색 트리 구조로 키를 정렬 유지하여 O(log N) 탐색을 보장하는 인덱스
- **배경/필요성**: 디스크 I/O 최소화를 위해 노드당 다수의 키를 저장하여 트리 높이를 낮출 필요가 있음

| 출제 의도 | 반드시 짚을 핵심 | 감점 회피 포인트 |
|:---|:---|:---|
| B-Tree 구조와 탐색 원리 | B+Tree 리프 연결 리스트 특성 | B-Tree vs B+Tree 차이 혼동 주의 |

> 요약: B-Tree 인덱스는 한 노드에 여러 키와 자식 포인터를 저장해 트리 높이를 제한하고 등치·범위 검색을 지원함

## Ⅱ. 구성요소
```text
        [Root Node]
       /     |     \
  [Branch]  [Branch]  [Branch]
   / \       / \       / \
 [Leaf]-[Leaf]-[Leaf]-[Leaf]  (B+Tree: Leaf간 연결)
```

| 구성요소 | 설명 | 비유 |
|:---|:---|:---|
| Root Node | 탐색 시작점으로 하위 Branch 분기 키를 보유함 | 건물 안내판 |
| Branch Node | 중간 경로로 탐색 범위를 축소하는 내부 노드 | 층별 안내 표지 |
| Leaf Node | 실제 키-포인터(또는 키-데이터)를 저장하는 최하위 노드 | 서가의 책 위치표 |
| Fan-out | 한 노드가 가질 수 있는 자식 수, 높을수록 트리 높이 감소 | 복도당 방 개수 |

> 요약: Root·branch에서 키 범위를 비교해 자식 페이지를 선택하고 leaf에서 키와 행 위치를 찾음

## Ⅲ. 절차
```text
Search Key --> Root 비교 --> Branch 선택 --> Leaf 도달 --> Data 접근
```
- 1단계: 검색 키를 Root Node의 키들과 비교하여 하위 Branch 방향 결정함
- 2단계: Branch Node에서 키 범위를 좁혀 다음 하위 노드로 이동함
- 3단계: Leaf Node에 도달하여 키 일치 여부를 확인하고 Pointer를 획득함
- 4단계: Pointer로 데이터 페이지에 접근하여 결과를 반환함(범위 검색 시 Leaf 순차 탐색)

> 요약: Root에서 Leaf까지 키 비교 분기를 반복하여 O(log N)에 탐색 완료함

## Ⅳ. 문제점
- 삽입/삭제 시 분할·병합: 노드 Split/Merge 발생 시 I/O와 잠금 비용 증가
- 순차 삽입 편향: 단조 증가 키(Auto-Increment) 삽입 시 우측 리프에 경합 집중
- 낮은 카디널리티 비효율: 선택도가 낮은 컬럼에서는 다수 리프를 스캔하여 이점 감소(124 참조)

> 요약: Split/Merge 비용, 편향 경합, 저카디널리티 비효율이 주요 문제임

## Ⅴ. 개선방안
1. 단기: Fill Factor 조정으로 Split 빈도를 사전 억제함
2. 중기: Reverse Key Index 또는 파티셔닝으로 우측 경합 분산
3. 장기: 저카디널리티 컬럼은 Bitmap Index(124 참조)로 대체하여 유형별 최적화

> 요약: Fill Factor 조정, 키 역순화, 인덱스 유형 전환으로 B-Tree 한계를 보완함

## Ⅵ. 전망
- 발전 방향: LSM-Tree 기반 인덱스(쓰기 최적화)와의 하이브리드 구조 연구 확대
- 기술사적 판단: RDBMS 기본 인덱스로서 범위 검색·정렬 요구가 있는 한 대체 불가한 위치임
- 기술사 제언: 워크로드별 B-Tree vs LSM-Tree 선택 기준을 정량적으로 수립할 필요
