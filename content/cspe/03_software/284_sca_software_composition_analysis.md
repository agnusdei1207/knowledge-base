## Ⅰ. 개요
- **정의**: 오픈소스·서드파티 컴포넌트의 라이선스와 보안 취약점을 식별·관리하는 기법
- **배경/필요성**: 현대 소프트웨어의 70~90%가 오픈소스 구성으로 공급망 보안 관리가 필요함
- **비유**: 식품 원재료 표시제처럼 소프트웨어 구성 재료를 투명하게 관리하는 것과 유사함

| 출제 의도 | 반드시 짚을 핵심 | 감점 회피 포인트 |
|:---|:---|:---|
| 공급망 보안·SBOM 연계 | CVE 매핑·라이선스 컴플라이언스 | SAST(282)/DAST(283)와 분석 대상 차이 명시 |

> 요약: 오픈소스 구성요소의 취약점·라이선스 위험을 관리하는 공급망 보안 기법임

## Ⅱ. 구성요소
```text
프로젝트 --> 의존성 스캔 --> CVE DB 조회 --> SBOM 생성
                |                               |
                v                               v
         라이선스 식별                    취약점 리포트
```

| 구성요소 | 설명 | 비유 |
|:---|:---|:---|
| 의존성 스캐너 | 패키지 매니저·바이너리에서 컴포넌트 목록 추출 | 재료 성분표 추출기 |
| CVE 데이터베이스 | 공개 취약점 정보와 컴포넌트 버전 매핑 | 리콜 대상 부품 목록 |
| SBOM | Software Bill of Materials, 구성요소 명세서 | 식품 원재료 목록표 |
| 라이선스 분석기 | GPL·MIT 등 라이선스 유형별 의무사항 식별 | 저작권 조건 확인 절차 |

> 요약: 의존성 추출→CVE 매핑→SBOM 생성→라이선스 확인의 공급망 분석 체계임

## Ⅲ. 절차
```text
빌드 트리거 --> 의존성 추출 --> 취약점 매핑 --> 정책 판정
```
- 1단계: CI 빌드 시 SCA 도구 자동 실행 트리거
- 2단계: `pom.xml`, `package.json` 등에서 직접·전이 의존성 전수 추출
- 3단계: NVD·OSS Index 등 CVE DB와 버전 매칭으로 취약점 식별
- 4단계: 조직 보안 정책 기반 빌드 차단·경고·허용 자동 판정

> 요약: 빌드 연동→의존성 추출→CVE 매핑→정책 판정으로 공급망 위험을 자동 관리함

## Ⅳ. 문제점
- 전이 의존성 누락: 간접 참조 컴포넌트 미식별 — 숨겨진 취약점 잔존
- 오탐·미탐 혼재: 버전 범위 불일치 시 CVE 매핑 정확도 저하 — 신뢰성 감소
- 라이선스 충돌 복잡성: 다수 컴포넌트 간 라이선스 호환성 판단 어려움 — 법적 리스크 잔존

> 요약: 전이 의존성 누락·매핑 부정확·라이선스 충돌이 주요 한계임

## Ⅴ. 개선방안
1. 단기: 의존성 트리 전체 해석으로 전이 의존성 완전 추출
2. 중기: CPE·PURL 표준 식별자 기반 정밀 버전 매칭 적용
3. 장기: 라이선스 호환성 자동 추론 엔진 도입으로 법적 리스크 사전 차단

> 요약: 전이 해석·정밀 매칭·라이선스 자동화로 SCA 정확도 향상 필요

## Ⅵ. 전망
- 발전 방향: SBOM 의무화(미 행정명령 등) 확대로 SCA 도입 가속
- 기술사적 판단: 공급망 공격(SolarWinds 등) 이후 SCA가 보안 필수 도구로 격상 중임
- 기술사 제언: SAST·DAST·SCA 통합 AppSec 플랫폼 구축으로 전방위 보안 확보 필요
