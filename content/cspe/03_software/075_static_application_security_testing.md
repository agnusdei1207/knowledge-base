## 미리 알고가기

- SAST는 애플리케이션을 실행하지 않고 소스 코드나 바이트코드를 분석하는 보안 검사임
- DAST는 실행 중인 애플리케이션을 대상으로 외부에서 취약점을 점검하는 방식임
- 오탐은 실제 취약점이 아닌데 도구가 위험으로 잘못 판단한 결과임

## 작성 근거(검토용)

- SAST·DAST는 분석 시점, 발견 정보, 탐지 한계, 수행 단계를 핵심 비교축으로 선정함
- 구성과 절차는 코드 변경부터 정적 분석·경고 분류·정책 보강까지의 흐름을 중심으로 제시함
- 실무 판단은 오탐률, 경고 처리율, 취약점 체류시간, 수정시간으로 구체화함

## Ⅰ. 개요

- **정의/개념**: SAST는 소스 코드·바이트코드·설정 파일을 실행하지 않고 분석해 취약 패턴을 찾는 정적 보안 테스트임
- **배경/필요성**: 배포 후 발견한 보안 결함은 수정 범위와 비용이 커지므로 개발 단계에서 취약점을 탐지할 필요가 있음

## Ⅱ. 특징

- 소스·바이트코드·설정을 실행하지 않고 분석하므로 커밋·CI 단계에서 수행함
- 데이터 흐름과 규칙 패턴으로 취약 API·입력 검증 누락·비밀 정보 노출 후보를 탐지함
- 실행 흐름과 실제 악용 가능성 판단에는 한계가 있음
- 오탐이 누적되면 개발자가 경고를 무시하거나 검사를 우회할 수 있음

## Ⅲ. 종류 및 비교

| 판단 기준 | SAST | DAST |
|:---|:---|:---|
| 필요 환경 | 소스·바이트코드·설정 파일 | 실행 중인 애플리케이션과 테스트 환경 |
| 발견 정보 | 소스 위치·데이터 흐름·취약 규칙 후보 | 실행 요청·응답에서 재현되는 취약 동작 |
| 구조상 한계 | 런타임 도달 가능성과 악용 동작을 재현하지 못함 | 통합 테스트 이후 발견되며 테스트 환경이 필요함 |
| 수행 시점 | 커밋·빌드·CI 단계 | 통합 테스트·스테이징·출시 전 점검 |

> 요약: 소스·설정의 취약 후보는 SAST, 실행 중 재현되는 취약 동작은 DAST로 탐지함.

## Ⅳ. 구성요소 및 구조

| 구성요소 | 설명 |
|:---|:---|
| 분석 규칙 | 취약 패턴과 금지 API와 정책 기준을 정의해 분석 기준을 만듦 |
| 코드 분석기 | 저장소와 빌드 산출물을 분석해 위험 위치를 식별함 |
| 경고 분류 절차 | 경고를 위험도·노출 범위·오탐 여부로 분류함 |
| 수정 피드백 | 수정 결과를 추적해 반복 취약점과 미조치 항목을 관리함 |

> 요약: 분석 규칙과 코드 분석기가 취약 후보를 찾고 경고 분류 결과를 수정·규칙 보강으로 연결함.

## Ⅴ. 원리 및 절차 흐름도

```text
+-------------+     +-------------+     +-------------+     +-------------+
| 코드 변경      | --> | 정적 스캔      | --> | 경고 분류      | --> | 수정/정책 보강 |
+-------------+     +-------------+     +-------------+     +-------------+
```

1. **코드 변경**: 커밋이나 병합 요청이 분석 대상이 됨
2. **정적 스캔**: 도구가 취약 패턴과 정책 위반을 찾음
3. **경고 분류**: 실제 위험과 오탐과 예외를 구분함
4. **수정 및 정책 보강**: 취약점 수정과 규칙 개선을 수행함

> 요약: 코드 변경을 정적 분석해 경고를 분류하고 실제 취약점은 수정하며 오탐은 규칙을 보정함.

## Ⅵ. 실무 사례

1. 금융 개발 파이프라인은 SAST 규칙을 위험도별로 적용하고 오탐률·경고 처리율을 확인함
2. 레거시 코드베이스는 수정 기한과 예외 기준을 운영하고 취약점 체류시간·수정시간을 확인함

## Ⅶ. 결론

SAST는 코드 실행 전 취약 후보를 탐지해 개발 단계에서 수정·차단하는 정적 보안 테스트임
