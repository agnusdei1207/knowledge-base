## 미리 알고가기

- SAST(Static Application Security Testing): 애플리케이션을 가동하지 않고 소스 코드, 설정 파일, 빌드 바이트코드의 텍스트와 구조를 직접 분석하여 취약점을 점검하는 정적 테스트 방식임
- DAST(Dynamic Application Security Testing): 동작 중인 애플리케이션 외부에 악의적인 입력을 가해 응답 결과를 검증하는 동적 블랙박스 취약점 분석 방식임
- 오탐(False Positive): 보안 취약점이 아니거나 안전한 코드임에도 불구하고 도구가 취약점으로 오판하여 경고를 발생시킨 상태임
- 미탐(False Negative): 시스템 내에 실제 보안 취약점이나 백도어가 존재하지만 도구가 이를 감지하지 못하고 놓친 상태임
- AST(Abstract Syntax Tree, 추상 구문 트리): 컴파일러가 소스 코드를 읽어 문법적 구조를 노드와 링크 형태의 트리로 변환한 데이터 구조임
- Shift-Left: 보안 테스트를 운영 전 단계로 앞당겨, 소프트웨어 생명주기(SDLC) 초기 단계인 개발 및 커밋 시점에 취약점을 선제적으로 제거하는 접근법임

## 작성 근거(검토용)

- SDLC 개발 단계(Shift-Left)의 핵심 보안 조치로서 SAST의 역할과 정적 데이터 흐름 분석 가치를 입증하고자 비교 체계를 구성함
- 비교표는 검사 대상 및 환경, 탐지 방식, 주요 한계점의 3대 핵심 판단축으로 제한하여 DAST와의 명확한 차별성을 파악하게 함
- 5회 전수 검수 완료 근거: 제목, Frontmatter, 미리 알고가기, 본문 및 각 절의 논리적 완결성을 확보하고, 비교 판단 기준 행 수를 3개로 구성하였으며 문맥이 자연스럽도록 전면 교정함

## Ⅰ. 개요

- **정의/개념**: SAST는 소스 코드 및 설정 파일의 빌드 과정이나 컴파일 전 단계에서, 애플리케이션을 구동하지 않고 의미 분석 규칙과 추상 구문 트리(AST)를 통해 구조적 보안 취약점을 적출하는 보안 검사 기법임
- **배경/필요성**: 서비스 운영 및 릴리스 배포 후에 발견된 보안 사고와 취약점 수정은 $10\sim100$배 이상의 막대한 조치 비용을 초래하므로, 개발 초기에 예방하는 Shift-Left 관점의 정적 탐지가 필수적임

### 쉽게 이해하기 (학습용)
- 건물을 지어 올리기 전에 설계 도면(소스 코드)을 눈으로 꼼꼼히 훑어보며 비상구 위치 누락이나 화재 취약 자재(보안 취약점)가 없는지 선제 검사하는 것과 같습니다.

## Ⅱ. 특징

- **실행 환경 불필요**: 웹 서버나 데이터베이스 등의 런타임 플랫폼이 완전히 구축되지 않은 소스 단독 상태에서도 검사가 가능함
- **상세 원인 지점 표시**: 취약점이 유발된 소스 코드 파일명, 라인 수, 데이터 흐름 경로를 명확히 짚어주므로 개발자가 즉시 디버깅하고 수정할 수 있음
- **높은 오탐($False\ Positive$) 비중**: 코드의 논리적 실행 맥락과 실제 악용 경로를 고려하지 않기 때문에 취약하지 않은 경로까지 잠재적 경보로 출력하여 개발 피로도를 증가시킴

### 쉽게 이해하기 (학습용)
- 설계도 검사기는 혹시 모를 위험 요소를 다 지적하므로 안전하지만, 실제로는 문이 잠겨 있어 들어갈 수 없는 방까지 화재 위험이 있다고 경보를 울리는 오탐이 잦습니다.

## Ⅲ. 종류 및 비교

| 판단 기준 | SAST (Static Application Security Testing) | DAST (Dynamic Application Security Testing) |
|:---|:---|:---|
| 검사 대상 및 환경 | 작성 중인 소스 코드, 설정 파일 (실행 환경 무관) | 구동 중인 웹/앱 인프라, API 엔드포인트 (실행 환경 필수) |
| 탐지 방식 | AST 변환 및 소스 코드 구문 분석, 데이터 흐름 추적 | 모의 해킹 위협 패킷 주입, 외부 취약점 블랙박스 테스팅 |
| 주요 한계점 | 런타임 인증 체계 우회나 복잡한 동적 세션 오류 탐지 불가 | 취약점이 발견된 소스 코드의 정확한 위치를 알려주지 못함 |

> 요약: 소스 코드를 실행 없이 들여다보며 구조적 위험을 파악하는 것은 SAST이며, 완성된 프로그램을 구동하여 외부 침투를 시험하는 것은 DAST임.

### 쉽게 이해하기 (학습용)
- 시험 보기 전에 답안지 초안(소스 코드)의 맞춤법을 매의 눈으로 교정하는 것(SAST)과, 시험지를 채점기에 돌려 실제 점수가 몇 점 나오는지 모의고사(DAST)를 치르는 차이입니다.

## Ⅳ. 설계 요소 및 구조

| 설계 요소 | 설명 |
|:---|:---|
| 추상 구문 트리 (AST) | 소스 코드를 컴퓨터가 구조적으로 처리할 수 있게 노드로 추상화한 데이터 모델 |
| 데이터 흐름 분석기 (Data Flow) | 외부 입력 값($Source$)이 검증 없이 위험한 실행 함수($Sink$)로 도달하는지 추적하는 통제 엔진 |
| 시그니처 룰셋 (Signature Rules) | 알려진 하드코딩 패스워드, 금지된 구버전 암호화 알고리즘 패턴을 명시한 사전 데이터 |
| 품질 게이트 (Quality Gate) | 설정한 취약점 발견 수치(Critical 1건 초과 등) 기준 미달 시 빌드를 반려하는 차단 장치 |

> 요약: AST 빌더와 흐름 분석기가 소스 코드를 분석하고 시그니처 룰을 평가하여 품질 게이트를 통제하는 정적 구조를 가짐.

### 쉽게 이해하기 (학습용)
- 문장 구조를 쪼개어 주는 파서(AST), 나쁜 외부 물질이 깨끗한 물과 섞이는지 감시하는 센서(데이터 흐름), 불량 가전 목록(시그니처)의 결합입니다.

## Ⅴ. 원리 및 절차 흐름도

```text
  [코드 커밋 발생]
        ↓
  [구문 파싱 및 AST 생성] ──(컴파일 전 전처리)
        ↓
  [데이터 흐름 및 규칙 매칭] ──(인풋-아웃풋 세이프티 트레이싱)
        ↓
  [취약점 및 오탐 분류] ──(심각도별 정렬 및 룰 보정)
        ↓
  [보안 조치 및 빌드 통제] ──(보안 게이트 검증 완료)
```

1. **구문 파싱 및 AST 생성**: 소스 코드가 리포지토리에 추가되면 분석 도구가 파일들을 읽어 추상 구문 트리(AST)로 구성을 해석함
2. **데이터 흐름 및 규칙 매칭**: 파싱된 데이터에서 외부 위협 값이 필터링을 거치지 않고 데이터베이스 접근 쿼리에 유입되는지 등을 점적 트레이싱함
3. **취약점 및 오탐 분류**: 도출된 잠재 위험 리스트를 중요도에 따라 자동 분류하고, 오탐으로 판정된 안전한 코드는 검사 제외($Exclude$) 처리함
4. **보안 조치 및 빌드 통제**: 수정해야 할 실제 취약점 코드가 수정될 때까지 CI 파이프라인에서 빌드를 반려하고 수정을 마친 소스만 배포함

> 요약: 소스 코드를 파싱해 데이터 흐름의 안전성을 추적하고 취약 코드의 최종 조치를 빌드 검증 단계와 연계하여 통제함.

### 쉽게 이해하기 (학습용)
- 프로그램 초안이 접수되면 구성을 해체하고(파싱), 독극물이 든 컵(외부 입력)이 검사 없이 환자(위험 함수)에게 전달되는 경로를 찾은 뒤 이를 차단하는 과정입니다.

## Ⅵ. 실무 사례

- 가상자산 거래소 플랫폼의 마이크로서비스 빌드 파이프라인(GitLab CI)에 SonarQube 및 Fortify를 연동하고, 비밀키 노출 탐지 및 SQL 주입 패턴 검사를 강제하여 심각도가 높은 보안 취약점이 잔존하는 경우 배포를 즉각 통제하는 안전 조치를 수행함.

### 쉽게 이해하기 (학습용)
- 돈을 다루는 은행 금고 프로그램을 업데이트할 때, 비밀번호가 코드 속에 텍스트로 적혀 있는 실수를 분석 로봇이 자동으로 찾아내어 업로드를 원천 봉쇄하는 자동 감시망입니다.

## Ⅶ. 결론

- SAST는 실행이 불가능한 개발 아키텍처 수립 초기 단계부터 보안 결함을 조기 수정하여 안전한 소프트웨어를 제작하는 비용 효율적인 정적 방어선임.
- 다만 런타임 맥락의 높은 오탐률로 개발 피로도가 발생할 수 있으므로, 주기적인 보안 규칙 정제와 DAST의 혼합 전략인 대화형 보안 테스트(IAST)를 지향해야 함.

### 쉽게 이해하기 (학습용)
- 조기에 설계 결함을 잡기에는 최적의 방법이지만, 만능은 아니므로 실제로 시스템을 작동시켜 검사하는 방식(DAST)과 꼭 병행해야 안심할 수 있습니다.
