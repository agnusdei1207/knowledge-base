## 미리 알고가기

- SAST는 애플리케이션을 실행하지 않고 소스 코드나 바이트코드를 분석하는 보안 검사임
- DAST는 실행 중인 애플리케이션을 대상으로 외부에서 취약점을 점검하는 방식임
- 오탐은 실제 취약점이 아닌데 도구가 위험으로 잘못 판단한 결과임

## Ⅰ. 개요

- **정의/개념**: 정적 애플리케이션 보안 테스트 SAST는 소스 코드와 바이트코드와 설정 파일을 실행 없이 분석해 보안 취약 패턴과 위험한 코딩 관행을 조기에 탐지하는 보안 검증 기법임.
- **배경/필요성**: 배포 후 보안 결함 수정은 비용과 영향 범위가 크므로, 개발 단계에서 취약점을 먼저 찾아 수정 비용을 줄일 필요가 있음.

## Ⅱ. 특징

- 개발 초기와 CI 단계에서 빠르게 적용할 수 있음
- 취약한 API 사용과 입력 검증 누락과 비밀 정보 노출 탐지에 효과적임
- 실행 흐름과 실제 악용 가능성 판단에는 한계가 있음
- 오탐이 많으면 개발자 수용성이 급격히 떨어짐

## Ⅲ. 종류 및 비교

| 구분 | SAST | DAST |
|:---|:---|:---|
| 분석 시점 | 코드를 실행하기 전에 소스와 설정을 분석함 | 실행 중인 애플리케이션을 대상으로 동작을 분석함 |
| 구조상 장점 | 취약점을 개발 초기에 찾고 빠르게 피드백하기 좋음 | 실제 실행 경로에서 드러나는 취약점을 확인하기 좋음 |
| 구조상 한계 | 런타임 맥락과 실제 도달 가능성 판단은 약함 | 늦게 발견되고 시험 환경 구성이 필요함 |
| 적합한 환경 | 개발과 CI 단계의 조기 차단에 맞음 | 통합 시험과 출시 전 보안 점검에 맞음 |

> 요약: SAST의 가치는 경고를 많이 만드는 데 있지 않고 수정이 가장 싼 시점에 의미 있는 취약점을 드러내는 데 있음.

## Ⅳ. 구성요소 및 구조

| 구성요소 | 설명 |
|:---|:---|
| 분석 규칙 | 취약 패턴과 금지 API와 정책 기준을 정의해 분석 기준을 만듦 |
| 코드 분석기 | 저장소와 빌드 산출물을 분석해 위험 위치를 식별함 |
| 경고 분류 절차 | 경고를 실제 위험과 오탐으로 구분해 개발 흐름에 맞게 정리함 |
| 수정 피드백 | 수정 결과를 추적해 반복 취약점과 미조치 항목을 관리함 |

## Ⅴ. 원리 및 절차 흐름도

```text
+-------------+     +-------------+     +-------------+     +-------------+
| 코드 변경      | --> | 정적 스캔      | --> | 경고 분류      | --> | 수정/정책 보강 |
+-------------+     +-------------+     +-------------+     +-------------+
```

1. **코드 변경**: 커밋이나 병합 요청이 분석 대상이 됨
2. **정적 스캔**: 도구가 취약 패턴과 정책 위반을 찾음
3. **경고 분류**: 실제 위험과 오탐과 예외를 구분함
4. **수정 및 정책 보강**: 취약점 수정과 규칙 개선을 수행함

## Ⅵ. 실무 적용 및 유의점

1. 금융과 공공 개발 파이프라인에서는 SAST가 조기 차단에 효과적이지만 오탐이 많으면 결과가 무시되므로 규칙 튜닝과 위험도 우선순위를 함께 운영하고 오탐 비율과 개발자 확인 처리율로 확인함
2. 대규모 레거시 코드베이스에서는 경고가 쌓이기만 하면 개선이 멈추므로 수정 기한과 예외 기준을 함께 두고 미해결 취약점 체류 시간과 취약점 수정 리드타임으로 확인함

## Ⅶ. 결론

SAST는 보안 검사를 앞당겨 수정 비용을 줄일 필요가 큰 조직에서 특히 효과적인 조기 차단 수단임.
