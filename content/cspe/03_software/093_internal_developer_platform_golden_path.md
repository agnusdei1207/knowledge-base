# 📖 【암기용】 개념 완전 이해

> 목적: Golden Path를 개발자가 권장 경로로 서비스를 만들고 운영하도록 돕는 표준 경로로 이해하게 만든다. 시험 답안 양식이 아니라, 이해를 위한 설명이다.

## 한눈에
- **개요**: Golden Path는 내부 플랫폼에서 검증된 개발·배포·운영 표준 경로
- **왜 필요한가**: 표준이 없으면 팀마다 저장소 구조, CI/CD, 보안 설정, 관측성 방식이 달라져 지원 비용이 증가한다.
- **핵심 직관**: 산길을 막는 것이 아니라 안전한 포장도로를 만들어 대부분의 이동을 그 길로 유도하는 방식임.

## 깊이 이해
- **배경·문제의식**: DevOps 자율성이 커지면 도구 선택 편차와 운영 품질 편차가 생기고 신규 팀의 온보딩 시간이 길어짐.
- **작동 원리**: 플랫폼팀이 서비스 템플릿, CI/CD, IaC, 보안 검사, 관측성, 런북을 하나의 표준 경로로 묶어 제공하고 예외는 승인 경로로 처리함.
- **비유**: 회사에서 표준 노트북 이미지와 계정 발급 절차를 제공해 직원이 첫날 업무 환경을 바로 갖추는 것과 같음.
- **구체 예시**: Spring Boot API golden path는 repo 생성, Dockerfile, Helm chart, GitHub Actions, SAST, OpenTelemetry, SLO 대시보드를 포함함.
- **흔한 오해·주의점**: Golden Path는 강제 규칙만이 아니라 개발자 경험을 낮추지 않는 권장 경로이며, escape hatch가 있어야 특수 요구를 수용함.

## 연결 개념
- IDP: Golden Path를 제공하는 내부 플랫폼
- Paved Road: 권장 표준 경로 개념
- Scorecard: 표준 경로 준수 점검 지표

# 📝 【답안용】 시험 답안 템플릿

> 목적: 시험장에서 25분에 그대로 쓰는 답안 양식. 작성방식(추상표현 금지·수치·도식·문제유형 전환)을 엄격히 지킨다.
> 핵심: Golden Path 답안은 템플릿 설명이 아니라 paved road, escape hatch, scorecard, developer experience를 함께 써야 한다.

## 핵심 인사이트 (3줄 요약)

> 1. **본질**: Golden Path는 내부 개발자 플랫폼에서 서비스 생성, 배포, 관측, 보안 통제를 표준화한 권장 경로이다.
> 2. **가치**: 개발팀은 검증된 경로를 self-service로 사용하고 플랫폼팀은 보안·품질·운영 요구를 기본값으로 내장한다.
> 3. **판단 포인트**: 강제 표준만 앞세우면 채택률이 낮아지므로 paved road, escape hatch, scorecard, 피드백 루프가 필요하다.

## 출제 의도 및 답안 포인트

| 출제 의도 | 반드시 짚을 핵심 | 감점 회피 포인트 |
|:---|:---|:---|
| IDP 운영 패턴 이해 확인 | golden path, paved road, self-service | 단순 프로젝트 템플릿으로 축소하지 않음 |
| 거버넌스와 자율성 균형 확인 | scorecard, policy, escape hatch | 표준 강제만으로 해결한다고 쓰지 않음 |
| DevEx 측정 확인 | lead time, adoption, onboarding time | 개발자 만족도와 운영 지표를 누락하지 않음 |
> 요약: Golden Path는 표준 경로를 매력적인 기본값으로 제공해 개발자 경험과 운영 통제를 동시에 달성하는 패턴이다.

---

## Ⅰ. 개요 및 필요성

Golden Path는 검증된 개발·운영 표준 경로이다.
팀별 도구 선택과 파이프라인 구현이 달라지면 온보딩 지연, 보안 누락, 운영 대시보드 부재가 발생한다.
Golden Path는 표준 템플릿과 정책을 권장 경로에 내장해 대부분의 서비스를 일관된 품질로 생성하게 한다.

---

## Ⅱ. 구조 및 구성요소

```text
Developer Need -> Golden Path Template -> Repository/CI/CD
-> IaC/Runtime -> Security/Policy -> Observability/SLO
-> Scorecard -> Feedback/Escape Hatch
```

| 구성요소 | 역할 | 산정 포인트 |
|:---|:---|:---|
| Template | 서비스 골격 생성 | 언어·프레임워크별 표준 |
| Pipeline | 빌드·테스트·배포 자동화 | SAST, SCA, unit test |
| Observability | 운영 지표 기본 제공 | logs, metrics, traces, SLO |
| Escape Hatch | 예외 처리 경로 | 승인 사유와 만료일 |
> 요약: Golden Path는 템플릿, 파이프라인, 관측성, 예외 경로를 하나의 권장 개발 흐름으로 묶는다.

---

## Ⅲ. 동작원리 및 흐름도

```text
서비스 유형 선택 -> 템플릿 실행 -> 저장소와 파이프라인 생성
-> 보안·품질 검사 기본 적용 -> 배포와 SLO 연결
-> scorecard 평가 -> 예외 승인 또는 경로 개선
```

| 단계 | 처리 내용 | 검증 기준 |
|:---:|:---|:---|
| 1 | 서비스 유형과 기술 스택 선택 | 표준 템플릿 매핑 |
| 2 | 코드·IaC·CI/CD 생성 | 생성 실패율 5% 이하 |
| 3 | 보안·품질 검사 실행 | SAST high 0건, coverage 80% |
| 4 | 관측성·SLO 등록 | dashboard 자동 생성 |
| 5 | Scorecard와 피드백 반영 | 표준 경로 채택률 80% |
> 요약: Golden Path는 생성, 검사, 배포, 관측, 점검을 기본 경로로 제공하고 예외를 관리한다.

## Ⅳ. 특징

| 구분 | 규정 중심 표준화 | Golden Path | 수치·판단 기준 |
|:---|:---|:---|:---|
| 접근 방식 | 문서로 준수 요구 | 사용 가능한 경로 제공 | 신규 서비스 생성 10분 이하 |
| 개발자 경험 | 승인·요청 중심 | self-service 중심 | onboarding 1일 이내 |

| 한계 | 자율성 제한 | 예외 경로 관리 필요 | escape hatch 만료관리 |
> 요약: Golden Path는 규정 설명보다 실제로 작동하는 기본 경로를 제공해 표준 채택률을 높인다.

## Ⅴ. 심화 비교 및 적용 판단

| 비교 축 | 기존/대안 | 본 키워드 | 선택 기준 |
|:---|:---|:---|:---|
| 구조 | 문서 표준 | 실행 가능한 템플릿·파이프라인 | 신규 서비스 빈도 높음 |
| 비용/규모 | 팀별 구축 | 플랫폼팀 공통 유지 | 개발팀 5개 이상 |
| 운영/위험 | 표준 이탈 사후 발견 | scorecard 사전 감지 | 규제·보안 요구 존재 |
| 품질 | 프로젝트별 편차 | 기본 검사와 SLO 내장 | DORA·SLO 목표 관리 |
> 요약: Golden Path는 서비스 생성 빈도와 표준 이탈 비용이 큰 조직에서 우선 적용한다.

| 리스크 | 원인 | 대응 방안 | 확인 지표 |
|:---|:---|:---|:---|
| 채택 저조 | 경로가 개발자 요구와 불일치 | 사용자 리서치와 피드백 루프 | 채택률 80% 이상 |
| 표준 노후화 | 프레임워크·런타임 변화 | 분기별 템플릿 갱신 | 템플릿 버전 최신률 |
| 예외 남발 | escape hatch 통제 부족 | 만료일·승인자·대체 계획 | 만료 예외 0건 |
| 플랫폼 의존 | IDP 장애 시 생성 불가 | 캐시·수동 절차·DR | 플랫폼 SLO 99.9% |
> 요약: Golden Path 리스크는 채택률, 템플릿 갱신, 예외 만료, 플랫폼 SLO로 관리한다.

| 점검 항목 | 목표 기준 | 측정 방법 |
|:---|:---|:---|
| 생성 시간 | 신규 서비스 10분 이하 | IDP telemetry |
| 채택률 | 대상 서비스 80% 이상 | service catalog |
| 준수율 | scorecard 95% 이상 | 정책 검사 |
| 예외 관리 | 만료 예외 0건 | escape hatch registry |
> 요약: Golden Path 성과는 생성 시간, 채택률, 준수율, 예외 만료관리로 판단한다.

## Ⅵ. 실무 적용 및 결론

**적용 방안 3개:**
1. 가장 빈도가 높은 API 서비스 1종을 대상으로 저장소, CI/CD, IaC, 관측성, SLO를 포함한 golden path를 먼저 제공함.
2. Scorecard에 owner, SAST, SCA, coverage 80%, SLO, runbook 항목을 넣고 배포 전 자동 점검함.
3. Escape hatch는 승인자, 만료일, 대체 계획을 필수로 두고 월 1회 만료 예외를 정리함.

**결론 (2줄):**
- 기술사 판단: 표준 이탈과 온보딩 지연이 큰 조직은 Golden Path를 적용하고, 특수 요구가 많은 조직은 escape hatch를 함께 설계함.
- 향후 방향: Golden Path는 AI 코드 생성, 정책 자동화, FinOps, 보안 검사를 포함한 동적 개발 경로로 발전함.
