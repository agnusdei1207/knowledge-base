# 📖 【암기용】 개념 완전 이해

> 목적: Golden Path를 개발자가 권장 경로로 서비스를 만들고 운영하도록 돕는 표준 경로로 이해하게 만든다. 시험 답안 양식이 아니라, 이해를 위한 설명이다.

## 한눈에
- **개요**: Golden Path(골든 패스)는 **내부 개발자 플랫폼(IDP, Internal Developer Platform)**이 제공하는, 검증된 **paved road**(포장도로형) 표준 개발·배포·운영 경로다.
- **왜 필요한가**: 팀마다 저장소 구조·CI/CD·보안 설정·관측성 방식을 처음부터 다시 만들면 온보딩이 느려지고 팀별 운영 품질 편차가 커진다. 플랫폼팀이 미리 검증한 경로를 깔아 두면, 개발자는 그 위로만 가도 보안·품질·관측성 요구가 기본값으로 충족된다.
- **핵심 직관**: 산길 여기저기를 막아 통제하는 것이 아니라, 가장 안전하고 빠른 길 하나를 포장도로로 깔아서 대부분의 이동이 자연스럽게 그 길을 타게 만드는 것 — "강제"가 아니라 "가장 매력적인 기본값"이다.

## 핵심 용어 정리 (내부에 등장하는 것들)

| 용어 | 의미 | 비유 |
|:---|:---|:---|
| IDP (Internal Developer Platform) | Golden Path·셀프서비스·관측성을 하나로 묶어 제공하는 내부 플랫폼 — Golden Path의 **상위 개념** | 사내 "제품"으로 만든 개발 인프라 |
| Platform Engineering | IDP를 하나의 내부 제품처럼 설계·운영하는 조직 활동 — IDP를 만드는 **상위 활동** | 사내 인프라팀을 "고객(개발자) 있는 제품팀"으로 바꾸는 것 |
| Golden Path | 검증된 표준 개발·배포·운영 경로 (본 개념) | 포장도로 |
| Paved Road | Golden Path와 같은 뜻으로 쓰이는 원어 표현 — "강제 규칙"이 아니라 "가장 편한 기본 선택지" | 자갈길도 갈 수 있지만 다들 포장도로로 다님 |
| Self-Service | 개발자가 승인 대기 없이 템플릿을 즉시 실행해 서비스를 만드는 방식 | 무인 자판기처럼 바로 이용 |
| Escape Hatch | 표준 경로를 벗어나야 할 때 쓰는 예외 승인 경로 | 비상구 — 있지만 아무나 상시로 쓰면 안 됨 |
| Scorecard | 서비스가 표준(보안·품질·관측성)을 얼마나 준수하는지 점수화한 지표 | 성적표 |
| Service Template | 저장소·CI/CD·IaC 골격을 자동 생성하는 틀 | 서류 양식 |
| DevEx (Developer Experience) | 개발자가 표준 경로를 얼마나 편하고 빠르게 쓰는지에 대한 만족도·생산성 | 고객 경험(UX)의 개발자 버전 |
| SLO (Service Level Objective) | 서비스 응답시간·가용성 등의 목표치, Golden Path에 기본 내장 | 품질 보증서에 적힌 목표 수치 |

## 깊이 이해

### 왜 등장했나 (배경)
- DevOps 이후 "만든 사람이 직접 운영한다(You build it, you run it)"는 원칙으로 팀 자율성이 커졌다. 그런데 자율성이 커질수록 저장소 구조, CI/CD 방식, 보안 검사 여부, 로그·메트릭 연결 방식을 팀마다 처음부터 다시 만들게 되고, 이 반복 작업이 팀 수만큼 곱해진다.
- Platform Engineering은 이 반복 작업을 플랫폼팀이 "내부 제품"으로 한 번만 만들어 여러 팀에 셀프서비스로 제공하자는 접근이고, 그 결과물이 IDP다. IDP 안에서 "이 길로 가면 다 된다"는 표준 경로가 Golden Path다.

### 무엇이 표준화되는가 — 구성 요소
- 저장소 템플릿(언어·프레임워크별 보일러플레이트), CI/CD 파이프라인(빌드·테스트·SAST·SCA), IaC 모듈(인프라 코드), 보안 정책(시크릿 관리·권한), 관측성(로그·메트릭·트레이스 자동 연결), SLO 대시보드, 장애 대응 런북 — 이 7가지를 하나의 실행 가능한 경로로 묶는다.
- 예: Spring Boot API 서비스를 만들 때 개발자가 템플릿 하나를 실행하면 repo, Dockerfile, Helm chart, GitHub Actions 파이프라인, SAST 스캔, OpenTelemetry 연동, SLO 대시보드가 자동으로 생성된다.

### 수치로 보는 효과
- Golden Path가 없으면: 저장소 생성, CI/CD 설정, 보안 스캐너 연동, 로그·메트릭 연결을 팀이 각자 수동으로 하는 데 평균 1~2주가 걸린다.
- Golden Path가 있으면: 템플릿 실행부터 첫 배포까지 약 10분 이내로 끝난다. 온보딩(신규 인력이 첫 서비스를 배포하기까지)도 수 주에서 1일 이내로 줄어든다.
- Scorecard 채점 예: owner 필드 명시(10점) + SAST 통과(20점) + 테스트 커버리지 80% 이상(20점) + SLO 대시보드 연결(20점) + 런북 존재(10점) + 시크릿 하드코딩 없음(20점) = 100점 만점 중 95점 이상만 "표준 준수"로 인정하는 식으로 정량화한다.

### Escape Hatch가 반드시 필요한 이유
- 모든 서비스가 표준 경로에 맞는 것은 아니다(레거시 연동, 특수 성능 요구 등). 이때 예외를 무기한 허용하면 표준 자체가 무너지므로, Escape Hatch는 반드시 승인자·만료일·대체 계획을 함께 요구한다. 예를 들어 "3개월 후 재검토"처럼 만료일이 없는 예외가 쌓이면 결국 아무도 표준 경로를 쓰지 않게 된다.

### 비유와 흔한 오해
- **비유**: 신입 사원에게 표준 노트북 이미지와 계정 발급 절차를 미리 준비해 두면 첫날부터 바로 업무를 시작할 수 있는 것과 같다. 표준 이미지를 강제로 쓰게 하는 것이 아니라, 그것이 가장 빠르고 편한 선택지이기 때문에 자연스럽게 채택되는 것이다.
- **오해**: Golden Path는 "지켜야 하는 규정 문서"가 아니다. 규정만 있고 실행 가능한 경로가 없으면 개발자는 각자 방식대로 만들고 나중에 감사에서 적발된다. Golden Path의 핵심은 규정을 문서가 아니라 "실행하면 바로 되는 템플릿"으로 제공해, 준수가 곧 가장 쉬운 길이 되게 만드는 데 있다.

## 연결 개념
- IDP (Internal Developer Platform): Golden Path를 제공하는 상위 플랫폼
- Platform Engineering: IDP를 내부 제품으로 설계·운영하는 조직 활동
- Paved Road: Golden Path와 동의어로 쓰이는 원어 표현
- Scorecard: 표준 경로 준수 여부를 점수로 측정하는 지표

# 📝 【답안용】 시험 답안 템플릿

> 목적: 시험장에서 25분에 그대로 쓰는 답안 양식. 작성방식(추상표현 금지·수치·도식·문제유형 전환)을 엄격히 지킨다.
> 핵심: Golden Path 답안은 템플릿 설명이 아니라 paved road, escape hatch, scorecard, developer experience를 함께 써야 한다.

## 핵심 인사이트 (3줄 요약)

> 1. **본질**: Golden Path는 내부 개발자 플랫폼에서 서비스 생성, 배포, 관측, 보안 통제를 표준화한 권장 경로이다.
> 2. **가치**: 개발팀은 검증된 경로를 self-service로 사용하고 플랫폼팀은 보안·품질·운영 요구를 기본값으로 내장한다.
> 3. **판단 포인트**: 강제 표준만 앞세우면 채택률이 낮아지므로 paved road, escape hatch, scorecard, 피드백 루프가 필요하다.

## 출제 의도 및 답안 포인트

| 출제 의도 | 반드시 짚을 핵심 | 감점 회피 포인트 |
|:---|:---|:---|
| IDP 운영 패턴 이해 확인 | golden path, paved road, self-service | 단순 프로젝트 템플릿으로 축소하지 않음 |
| 거버넌스와 자율성 균형 확인 | scorecard, policy, escape hatch | 표준 강제만으로 해결한다고 쓰지 않음 |
| DevEx 측정 확인 | lead time, adoption, onboarding time | 개발자 만족도와 운영 지표를 누락하지 않음 |
> 요약: Golden Path는 표준 경로를 매력적인 기본값으로 제공해 개발자 경험과 운영 통제를 동시에 달성하는 패턴이다.

## Ⅰ. 개요 및 필요성

- 개요: Golden Path는 검증된 개발 표준 경로이다.
- 배경: 팀별 저장소 구조, CI/CD, 보안 검사, 관측성 설정이 다르면 온보딩 지연과 운영 누락이 발생한다.
- 필요성: 표준 템플릿, SAST, OpenTelemetry, SLO 대시보드를 권장 경로에 내장해 서비스 생성 기준을 통일해야 한다.

---

## Ⅱ. 구조 및 구성요소

```text
Developer Need -> Golden Path Template -> Repository/CI/CD
-> IaC/Runtime -> Security/Policy -> Observability/SLO
-> Scorecard -> Feedback/Escape Hatch
```

| 구성요소 | 역할 | 산정 포인트 |
|:---|:---|:---|
| Template | 서비스 골격 생성 | 언어·프레임워크별 표준 |
| Pipeline | 빌드·테스트·배포 자동화 | SAST, SCA, unit test |
| Observability | 운영 지표 기본 제공 | logs, metrics, traces, SLO |
| Escape Hatch | 예외 처리 경로 | 승인 사유와 만료일 |
> 요약: Golden Path는 템플릿, 파이프라인, 관측성, 예외 경로를 하나의 권장 개발 흐름으로 묶는다.

## Ⅲ. 동작원리 및 흐름도

```text
서비스 유형 선택 -> 템플릿 실행 -> 저장소와 파이프라인 생성
-> 보안·품질 검사 기본 적용 -> 배포와 SLO 연결
-> scorecard 평가 -> 예외 승인 또는 경로 개선
```

| 단계 | 처리 내용 | 검증 기준 |
|:---:|:---|:---|
| 1 | 서비스 유형과 기술 스택 선택 | 표준 템플릿 매핑 |
| 2 | 코드·IaC·CI/CD 생성 | 생성 실패율 5% 이하 |
| 3 | 보안·품질 검사 실행 | SAST high 0건, coverage 80% |
| 4 | 관측성·SLO 등록 | dashboard 자동 생성 |
| 5 | Scorecard와 피드백 반영 | 표준 경로 채택률 80% |
> 요약: Golden Path는 생성, 검사, 배포, 관측, 점검을 기본 경로로 제공하고 예외를 관리한다.

## Ⅵ. 실무 적용 및 결론

**적용 방안 3개:**
1. 가장 빈도가 높은 API 서비스 1종을 대상으로 저장소, CI/CD, IaC, 관측성, SLO를 포함한 golden path를 먼저 제공함.
2. Scorecard에 owner, SAST, SCA, coverage 80%, SLO, runbook 항목을 넣고 배포 전 자동 점검함.
3. Escape hatch는 승인자, 만료일, 대체 계획을 필수로 두고 월 1회 만료 예외를 정리함.

**결론 (2줄):**
- 기술사 판단: 표준 이탈과 온보딩 지연이 큰 조직은 Golden Path를 적용하고, 특수 요구가 많은 조직은 escape hatch를 함께 설계함.
- 향후 방향: Golden Path는 AI 코드 생성, 정책 자동화, FinOps, 보안 검사를 포함한 동적 개발 경로로 발전함.
