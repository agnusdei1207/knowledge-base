## 핵심 인사이트 (3줄 요약)
- **SAST (Static Application Security Testing)**: 소프트웨어를 **실행(Run)하지 않고**, 소스 코드 내부를 정적으로 스캐닝하여 보안 취약점(SQL 인젝션, XSS 등)을 찾아내는 화이트박스 보안 테스트 기법.
- CI/CD 파이프라인의 '코드 커밋' 및 '빌드' 단계 등 개발 극초기(Shift-Left)에 적용되어, 버그 수정 비용을 드라마틱하게 낮춰줌.
- 하지만 소스 코드만 보고 추론하기 때문에 "위험하지 않은데 위험하다고 경고하는" **오탐(False Positive)** 확률이 매우 높아, 개발자의 피로도를 유발하는 것이 치명적 단점임.

## Ⅰ. 개요 및 필요성
- **개요**: 소스 코드나 바이트코드를 파싱하여 제어 흐름(Control Flow)과 데이터 흐름(Data Flow)을 분석하고 보안 결함을 식별하는 자동화 도구.
- **필요성**: 시스템을 모두 완성한 뒤(DAST)에 보안 결함이 발견되면, 개발자는 수만 줄의 코드 중 어디서 문제가 시작되었는지 추적해야 함. 코드를 타이핑하는 순간(IDE)이나 빌드하는 즉시 결함을 알려주어 "취약점의 정확한 소스코드 라인(Line Number)"을 짚어줄 도구가 필요했음.
---
## Ⅱ. 아키텍처 및 핵심 원리
- **분석 원리**:
  1. **구문 분석 (Lexical Analysis)**: 소스 코드를 토큰(Token)과 추상 구문 트리(AST)로 변환.
  2. **데이터 흐름 분석 (Taint Analysis)**: 외부 입력(사용자 입력창)이 오염(Taint)되었다고 가정하고, 이 오염된 값이 검증 과정(Sanitization) 없이 DB 쿼리나 웹 화면까지 도달하는지(Sink) 추적. (SQL 인젝션 탐지의 핵심).
- **파이프라인 통합 (Shift-Left)**:
  - 개발자의 IntelliJ/VSCode 플러그인 형태로 실시간 피드백 (SonarLint).
  - Git Push 시 Jenkins/GitLab CI에서 SonarQube, Checkmarx, Fortify 등을 구동하여 Quality Gate 설정.

```text
[ SAST의 오염 분석(Taint Analysis) 원리 ]

 [ 외부 입력 (Source) ] ➡️ String userId = request.getParameter("id"); (오염됨!)
            ⬇️
 [ 데이터 흐름 추적 ]   ➡️ if (userId != null) { ... } (검증 로직 없음!)
            ⬇️
 [ 치명적 도착점 (Sink)] ➡️ db.execute("SELECT * FROM users WHERE id = " + userId);
            
 * SAST 도구가 3번째 줄을 스캔하며 "SQL Injection 취약점 탐지 (Line 45)" 경고 발생!
```

## Ⅲ. 비교 및 연결
| 구분 | SAST (정적 테스트) | DAST (동적 테스트) |
|---|---|---|
| **분석 대상** | 내부 소스 코드 (화이트박스) | 실행 중인 웹 애플리케이션 (블랙박스) |
| **적용 시점** | 개발 초기 (코딩, 빌드 단계) | 개발 후기 (테스트, 스테이징 서버) |
| **취약점 위치** | 소스코드의 '정확한 줄 번호' 제공 | HTTP 요청/응답 형태 (코드 위치 모름) |
| **탐지율 특징** | **오탐(False Positive)**이 매우 많음 | **미탐(False Negative)**이 발생할 수 있음 |
---
## Ⅳ. 실무 적용 및 기술사 판단
- **오탐(False Positive) 관리의 예술**: SAST를 도입하고 초기에 규칙(Rule)을 너무 빡빡하게 세팅하면, 수천 개의 가짜 알림이 쏟아져 개발자들이 SAST를 '늑대소년' 취급하며 아예 꺼버림(Bypass). 실무 도입 시 반드시 **'심각도(Critical/High) 수준만 먼저 차단'**하고 점진적으로 강도를 높이는 튜닝 거버넌스가 SAST 성공의 핵심 열쇠임.
- **SCA와의 조합 필수**: SAST는 '우리 회사 개발자가 짠 소스코드'의 결함만 잡음. 하지만 현대 소프트웨어의 80%는 외부 오픈소스임(Log4j 등). 따라서 SAST 단독으로는 안전할 수 없으며, 서드파티 라이브러리를 검사하는 **SCA(Software Composition Analysis)**와 묶어서(DevSecOps) 사용해야 진정한 방패가 됨.
---
## Ⅴ. 기대효과 및 결론
- 버그 수정 비용이 기하급수적으로 커지는 프로덕션 배포 전에 보안 문제를 색출함으로써, 막대한 금전적/시간적 리소스를 절감함.
- 개발자에게 "내가 짠 코드가 왜 보안에 취약한지"를 IDE 단에서 실시간으로 교육(Edu)하는 효과를 주어, 조직 전체의 시큐어 코딩 역량을 상향 평준화시킴.

### 📈 관련 키워드 및 발전 흐름도
- 수동 코드 리뷰 ➡️ Lint 도구 (구문 오류 확인) ➡️ SAST (보안 취약점 시그니처 분석, Checkmarx/Fortify) ➡️ AI-SAST (LLM 기반 오탐률 감소)

### 👶 어린이를 위한 3줄 비유 설명
1. 폭탄(해킹)을 막기 위해, 폭탄이 '설계도(소스 코드)' 상태일 때 돋보기로 꼼꼼히 살펴보는 게 SAST예요.
2. 폭탄을 직접 터뜨리지 않고 종이만 보니까 엄청 안전하고 "3페이지 5번째 줄이 틀렸어!"라고 바로 알려줄 수 있죠.
3. 하지만 가끔 장난감 시계를 보고도 "폭탄이다!"라고 엉뚱한 경고(오탐)를 너무 많이 울려서 사람들을 피곤하게 만들 때가 있답니다.
