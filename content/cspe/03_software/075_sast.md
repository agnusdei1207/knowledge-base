# 📖 【암기용】 개념 완전 이해

## 한눈에
- **개요**: 프로그램을 실행하지 않고, 소스 코드 자체를 분석하여 보안 취약점과 구조적 결함(코드 스멜)을 찾는 화이트박스 테스트 기법
- **왜 필요한가**: 취약점을 코드 작성 단계(초기)에 발견하여, 배포 후 수정하는 것보다 수정 비용을 수십 배 절감할 수 있음(Shift-Left)
- **핵심 직관**: 건물 완공 전에 설계도면만 보고 부실 공사 가능성을 찾아내는 작업

## 핵심 용어 정리

| 용어/표기 | 의미 | 비유·예 |
|:---|:---|:---|
| SAST (정적 분석) | 실행 없이 코드/바이너리를 스캔하는 테스트 | 맞춤법 검사기, 엑스레이 촬영 |
| Shift-Left | 소프트웨어 생명주기 초반(왼쪽)에 테스트를 당겨서 수행함 | 병 걸리기 전 건강검진 |
| False Positive (오탐) | 문제없는 코드를 취약점이라고 잘못 탐지함 | 정상 조직을 암으로 오진 |

## 깊이 이해
- **배경·문제의식**: 과거 보안 검사는 배포 직전에야 이루어져(DAST, 모의해킹) 결함 발견 시 전체 로직을 뜯어고쳐야 하는 재작업(Rework) 비용이 막대했음.
- **작동 원리**: SAST 도구(SonarQube, Checkmarx 등)가 소스 코드를 구문 트리(AST)나 데이터 흐름 그래프로 변환한 뒤, 미리 정의된 취약점 패턴(SQL 인젝션, XSS 등)과 대조하여 일치하는 곳을 찾아냄.
- **비유**: 영어 작문 숙제를 냈을 때, 선생님이 글을 직접 소리내어 읽어보지 않고도(실행 안 함) 문법이 틀린 곳이나 금지어를 찾아내어 빨간 펜을 긋는 것.
- **구체 예시**: 소스 코드에 `SELECT * FROM users WHERE id = ` + `userInput` 형태로 문자열을 덧붙이는 구문이 있으면, 실행하지 않아도 SQL 인젝션 취약점이 발생할 것임을 100% 확신하고 경고함.
- **흔한 오해·주의점**: 런타임 환경 설정 오류나 로직의 문맥적(비즈니스) 오류는 잡지 못함. 또한, 안전한 코드 패턴을 이해하지 못해 '오탐(False Positive)'이 매우 잦아 개발자의 피로도를 높일 수 있음.

## 연결 개념
- **DAST, DevSecOps, 시큐어 코딩, 기술부채**

# 📝 【답안용】 시험 답안 템플릿

## 핵심 인사이트 (3줄 요약)

> 1. **본질**: 비실행 상태에서 소스코드의 구문, 의미, 데이터 흐름을 추적하는 화이트박스 보안 테스팅
> 2. **가치**: Shift-Left 보안 실현, 코드 수준의 정확한 결함 위치 제공, 초기 수정 비용 절감
> 3. **판단 포인트**: 치명적인 한계인 오탐(False Positive) 관리 및 런타임 검증을 위해 DAST와의 상호보완(IAST)이 필수적임

## 출제 의도 및 답안 포인트

| 출제 의도 | 반드시 짚을 핵심 | 감점 회피 포인트 |
|:---|:---|:---|
| SW 개발 주기 내 보안 내재화(Shift-Left) 이해 | 소스코드/바이너리 대상, 비실행, 화이트박스 | DAST와 개념 혼동(실행 중으로 서술) |
| 정적 분석의 기술적 한계 인식 | 높은 오탐률(False Positive), 런타임 오류 탐지 불가 | 오탐 방지 방안 누락 단정 |

> 요약: 개발 초기 단계에 구문 트리를 기반으로 결함을 식별하나 런타임 문맥 부족으로 높은 오탐률을 수반함

---

## Ⅰ. 개요 및 필요성

- 개요: SAST는 애플리케이션을 실행하지 않고 소스 코드, 바이트 코드, 바이너리를 구문 및 의미론적으로 분석하여 취약점을 탐지하는 기법임
- 배경: SDLC 후반부에 취약점이 발견될 경우, 설계부터 수정해야 하는 재작업(Rework) 비용이 기하급수적으로 증가함
- 필요성: 개발자의 코딩 단계에서 실시간 피드백을 제공하여 보안을 조기에 내재화(Shift-Left Security)하기 위함

---

## Ⅱ. 구조 및 구성요소 (SAST 분석 아키텍처)

```text
[소스 코드/저장소] -> [어휘/구문 분석기] -> [추상구문트리(AST) 변환] -> [규칙 엔진 매칭] -> [취약점 리포트]
                                               |                          |
                                               +-> 데이터/제어 흐름 분석    +-> CWE/OWASP Top 10 패턴
```

| 구성요소 | 역할 | 특이사항 |
|:---|:---|:---|
| 추상 구문 트리 (AST) | 소스 코드를 계층적 트리 구조로 변환 | 코드 문법의 논리적 표현 |
| 제어 흐름 분석 (CFA) | 프로그램 실행 경로의 순서와 분기 추적 | 도달 불가능 코드 식별 |
| 데이터 흐름 분석 (DFA) | 외부 입력값(Taint)이 위험한 함수(Sink)로 도달하는지 추적 | 오염 분석(Taint Analysis) 적용 |
| 정책 룰셋 (Ruleset) | SQLi, XSS 등 알려진 취약점 시그니처 데이터베이스 | 커스텀 룰셋 확장 가능 |

> 요약: 소스 코드를 구조화된 트리로 변환 후 데이터의 오염 경로(Taint)를 추적하여 패턴과 대조함

---

## Ⅲ. 동작원리 및 흐름도 (Taint Analysis 중심)

```text
오염원 식별 -> 데이터 전파 경로 추적 -> 위험 함수 도달 검증 -> 취약점 판정 및 로깅
```

- 1단계 [Source(오염원) 식별]: HTTP Request, 파일 읽기 등 신뢰할 수 없는 외부 입력 지점을 스캔함
- 2단계 [경로 전파 추적]: 해당 입력값이 변수에 할당되거나 함수 파라미터로 전달되는 제어/데이터 흐름 분석
- 3단계 [Sink(위험점) 도달 검증]: 필터링 로직(Sanitization) 없이 DB 쿼리 실행, 화면 출력 등 위험 함수에 도달하는지 확인
- 4단계 [취약점 판정]: 도달 시 CWE 코드와 함께 소스 파일명 및 라인 번호를 명시하여 결과 반환

> 요약: 신뢰할 수 없는 데이터가 검증 로직 없이 시스템의 치명적 함수로 흘러가는 경로를 수학적으로 증명함

---

## Ⅳ. 특징

- 조기 탐지 (Shift-Left): 개발 환경(IDE)이나 코드 병합(PR) 단계에서 즉각 탐지하여 수정 비용을 최소화함
- 정확한 위치 지정: 취약점이 존재하는 정확한 파일명과 소스코드 라인 번호를 제공하여 빠른 패치 지원
- 미지원 언어 한계: 분석 도구가 해당 프로그래밍 언어의 구문 파서(Parser)를 지원하지 않으면 분석이 불가능함
- 런타임 문맥 부재: 환경 설정(DB 연결 권한 등)이나 실제 실행 환경 특성을 몰라 오탐(False Positive)이 다수 발생함

> 요약: 개발 주기의 가장 앞단에서 코드 레벨 피드백을 주지만 런타임 특성을 배제하므로 오탐률이 높음

---

## Ⅴ. 심화 비교 및 적용 판단

| 비교 축 | SAST (정적 분석) | DAST (동적 분석) | 선택 기준 |
|:---|:---|:---|:---|
| 분석 방식 / 시점 | 비실행(화이트박스) / 개발(Coding) 단계 | 실행(블랙박스) / 테스트(QA) 단계 | 도입 SDLC 단계 |
| 결함 위치 정확도 | 매우 높음 (정확한 라인 번호 제시) | 낮음 (HTTP 요청/응답 패턴만 제시) | 디버깅 지원 요구 수준 |
| 환경·설정 오류 탐지 | 불가능 (코드 로직만 검증) | 가능 (서버 환경 결함 탐지) | 운영 인프라 종속성 |

> 요약: SAST는 코드 내부 로직 결함을, DAST는 런타임 응답 결함을 탐지하므로 상호 보완 적용이 필수적임

**리스크·대응:**
- 높은 오탐(False Positive)으로 인한 피로도: 개발자가 경고를 무시하는 양치기 소년 효과 → AI/ML 기반 오탐 필터링 및 베이스라인(Baseline) 설정 (지표: 오탐률 저하 추이)
- 빌드 파이프라인 지연: 거대 모놀리식 코드 스캔 시 수십 분 소요 → 증분 스캔(변경된 코드만 스캔) 및 야간 풀 스캔 이원화 (지표: CI/CD 빌드 시간)

---

## Ⅵ. 실무 적용 및 결론

**적용 방안 (DevSecOps 파이프라인 통합):**
1. IDE 통합 (Pre-commit): 개발자 로컬 PC의 IDE(IntelliJ, VSCode) 플러그인 형태로 연동하여 작성 즉시 피드백 제공 (SonarLint 활용)
2. CI 게이트키퍼 (Build 단계): PR(Pull Request) 시 정적 분석을 강제하고, 치명적(Critical) 취약점 검출 시 병합 차단 (Quality Gate 설정)
3. 룰셋 최적화 튜닝: 초기 도입 시 조직의 프레임워크 표준(예: 커스텀 XSS 필터)을 인식하지 못해 오탐이 발생하므로, 해당 필터를 안전 함수(Sanitizer)로 등록하는 커스텀 룰 튜닝 수행

**결론:**
- 기술사 판단: SAST는 시큐어 코딩의 핵심 엔진이나 100% 탐지를 보장할 수 없으므로, DAST 및 SCA(오픈소스 취약점 분석)와 결합된 통합 플랫폼(CNAPP 등) 활용이 필요함
- 향후 방향: 최근에는 정적/동적 분석의 장점을 합친 대화형 보안 테스트(IAST)와 LLM 기반 소스코드 자동 수정 기술로 발전하고 있음
