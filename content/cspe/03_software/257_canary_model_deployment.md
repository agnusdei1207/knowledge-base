# 📖 【암기용】 개념 완전 이해

> 목적: 카나리 모델 배포를 처음 보는 사람도 완벽히 이해하게 만든다. 시험 답안 양식이 아니라, 이해를 위한 친절한 설명이다.

## 한눈에
- **개요**: 카나리 모델 배포는 신규 모델을 **일부 트래픽에만 점진적으로 노출**하며 지표를 검증하는 **점진적 배포(Progressive Delivery)** 전략이다.
- **왜 필요한가**: 오프라인 검증을 통과한 모델도 실제 운영 트래픽에서는 응답 지연, 입력 분포, 인프라 문제로 다른 결과를 낼 수 있다. 전체 배포 전에 노출 범위를 작게 제한해 피해를 억제한다.
- **핵심 직관**: 새 모델을 전 사용자에게 한 번에 적용하지 않고 1% 사용자에게 먼저 적용해 이상 징후를 관찰하는 방식이다.

## 핵심 용어 정리 (내부에 등장하는 것들)

| 용어 | 의미 | 비유 |
|:---|:---|:---|
| 점진적 배포 (Progressive Delivery, 상위 개념) | 변경사항을 한 번에 전체 적용하지 않고 단계적으로 넓혀가며 위험을 제한하는 배포 방식군 — 카나리가 속한 상위 범주 | 계단식으로 수문 열기 |
| Traffic Router | 요청을 버전별로 정해진 비율로 분배하는 구성요소 | 갈림길의 신호수 |
| Baseline(대조군) | 기존에 운영 중이던 안정 버전 모델 | 기존 제품 |
| Canary(카나리아) | 새로 배포해 소수 트래픽으로 먼저 검증받는 신규 모델 | 광산의 카나리아 새 |
| Decision Gate | 각 확대 단계에서 지표 기준 충족 여부로 확대·중단을 판정하는 지점 | 검문소 |
| Rollback | 기준 미달 시 카나리 트래픽 비율을 0%로 되돌리는 것 | 원상복구 |
| Blue/Green 배포 | 신·구 버전을 통째로 전환하는 방식(카나리와 대비되는 개념) | 스위치 한 번에 전체 전환 |

## 깊이 이해

### 왜 필요한가 — 오프라인 검증만으로 부족한 이유
학습·검증 단계에서 AUC 0.86으로 통과한 모델도 실제 운영 트래픽에서는 다른 문제가 생길 수 있다. 응답 지연이 목표(p95 100ms)를 못 맞추거나, 실제 사용자 입력 분포가 검증셋과 달라 예측이 틀리거나, 신규 서빙 인프라가 특정 입력에서 예외를 던질 수 있다. 전체 트래픽에 한 번에 배포하면 이 문제가 전체 고객에게 즉시 퍼진다. 카나리는 이 노출 범위를 처음엔 1%로 제한해 피해를 억제한다.

### 단계별 확대 원리 — 수치로 이해
전형적인 확대 시퀀스는 1% → 5% → 25% → 50% → 100%다. 각 단계마다 일정 관찰 시간(예: 30분~1시간, 또는 최소 요청 1,000건)을 두고, 사전에 정의한 기준(예: p95 지연 150ms 이하, 5xx 오류율 0.1% 이하, 업무 KPI인 클릭률이 기준 모델 대비 2%p 이내 하락)을 통과해야 다음 단계로 넘어간다. 예: 추천 모델 v2를 5% 트래픽에 배포했는데 클릭률이 v1 대비 2%p 이상 하락하거나 p95가 150ms를 넘으면, 즉시 라우팅 비율을 0%로 되돌리는 자동 롤백이 실행된다(목표 롤백 시간 10분 이하).

### 카나리 vs A/B 테스트 vs Blue/Green — 판별 기준
세 방식 모두 "일부만 먼저 적용"한다는 점에서 헷갈리기 쉽지만 목적이 다르다. 카나리는 배포 위험 축소가 목적이라 지표가 나쁘면 즉시 롤백하고 끝낸다. A/B 테스트는 통계적으로 어느 쪽이 더 나은지 검증하는 것이 목적이라 두 그룹을 충분한 표본과 기간 동안 유지하며 유의성 검정을 한다. Blue/Green은 신·구 버전을 전량 병렬로 띄워두고 트래픽을 한 번에 전환하는 방식으로, 점진적 비율 조정이 없다는 점에서 카나리와 다르다.

### 오탐과 편향을 막는 원리
트래픽 비율이 너무 작으면(예: 1%가 하루 100건뿐인 서비스) 표본이 부족해 우연한 변동을 실패로 오판할 수 있다. 그래서 최소 요청 수(예: 1,000건 이상)를 관찰 조건에 넣는다. 또한 라우팅을 무작위로 하지 않아 특정 세그먼트(특정 지역, VIP 고객 등)에만 카나리가 몰리면 그 세그먼트의 특성이 전체 판단을 왜곡하므로, 무작위 샘플링으로 세그먼트 균형을 유지해야 한다.

## 연결 개념
- 점진적 배포(상위 개념), Blue/Green 배포(대비 개념)
- 모델 레지스트리(254) — Production Stage로 승인된 모델이 카나리 대상이 됨
- 모델 모니터링(256) — 카나리 단계별 지표(p95, 오류율, KPI)를 실시간 감시하는 주체

# 📝 【답안용】 시험 답안 템플릿

> 목적: 시험장에서 25분에 그대로 쓰는 답안 양식. 작성방식(추상표현 금지·수치·도식·문제유형 전환)을 엄격히 지킨다.
> 핵심: 카나리 모델 배포 답안은 점진 트래픽, 자동 판정 기준, 롤백 조건을 함께 제시해야 한다.

## 핵심 인사이트 (3줄 요약)

> 1. **본질**: 카나리 모델 배포는 신규 모델을 제한된 트래픽에 적용해 운영 지표를 검증한 뒤 단계적으로 확대하는 배포 전략이다.
> 2. **가치**: 전체 장애와 잘못된 예측 확산을 막고 p95 지연, 오류율, 업무 KPI 기준으로 배포 지속 여부를 판단한다.
> 3. **판단 포인트**: 트래픽 비율, 관찰 시간, 성공·중단 임계값, 롤백 절차를 사전에 수치로 정의해야 한다.

## 출제 의도 및 답안 포인트

| 출제 의도 | 반드시 짚을 핵심 | 감점 회피 포인트 |
|:---|:---|:---|
| 배포 전략 이해 | 1%에서 100%까지 단계 확대 | 단순 부분 배포로만 설명 |
| 운영 판단 확인 | 지연, 오류율, KPI, 롤백 기준 | 정확도 지표만 제시 |
| A/B와 구분 확인 | 위험 축소 목적 vs 효과 검증 목적 | 카나리와 A/B를 동일시 |

> 요약: 카나리 배포는 신규 모델 운영 리스크를 제한된 트래픽과 자동 판정 기준으로 통제한다.

## Ⅰ. 개요 및 필요성

- 개요: 카나리 모델 배포는 점진적 모델 릴리스 전략이다.
- 배경: 신규 모델은 오프라인 검증 후에도 운영 트래픽에서 지연, 오류, 업무 KPI 차이가 발생할 수 있다.
- 필요성: 1~10% 트래픽부터 적용해 피해 범위를 제한하고 지표 기준 충족 시 확대해야 한다.

---

## Ⅱ. 구조 및 구성요소

```text
Client Request -> Traffic Router -> Baseline Model
                                / Canary Model -> Metrics -> Decision Gate -> Rollback/Promote
```

| 구성요소 | 역할 | 통제 기준 |
|:---|:---|:---|
| Traffic Router | 요청 비율을 모델 버전별로 분배 | 1%, 5%, 25%, 50%, 100% |
| Canary Model | 신규 모델 제한 적용 | version, registry stage |
| Metrics Collector | 품질·지연·오류 수집 | p95, 5xx, KPI |
| Decision Gate | 확대·중단·롤백 판단 | 임계값과 관찰 시간 |

> 요약: 카나리 구조는 라우터와 지표 게이트를 통해 신규 모델 노출 범위를 단계적으로 늘린다.

---

## Ⅲ. 동작원리 및 흐름도

```text
모델 승인 -> 1% 라우팅 -> 지표 수집 -> 임계값 판정 -> 비율 확대 -> 전체 전환 또는 롤백
```

| 단계 | 처리 내용 | 검증 기준 |
|:---:|:---|:---|
| 1 | 레지스트리 Production 후보 모델 승인 | 오프라인 지표 통과 |
| 2 | 1% 또는 내부 사용자에 노출 | p95, 오류율 관찰 |
| 3 | 단계별 트래픽 확대 | KPI 하락 2%p 이내 |
| 4 | 전체 전환 또는 자동 롤백 | 롤백 10분 이하 |

> 요약: 카나리 배포는 각 확대 단계에서 성공 기준을 통과할 때만 다음 비율로 진행한다.

## Ⅳ. 특징

| 구분 | 전체 배포 | 카나리 모델 배포 | 판단 포인트 |
|:---|:---|:---|:---|
| 노출 범위 | 모든 트래픽 즉시 적용 | 일부에서 점진 확대 | 피해 범위 제한 |
| 판정 기준 | 배포 성공 여부 | 품질, 지연, 업무 KPI | 자동 중단 조건 |
| 롤백 | 전체 복구 필요 | 라우팅 비율 0% 전환 | RTO 10분 이하 |

> 요약: 카나리 배포는 모델 변경의 영향 범위를 줄이고 운영 지표로 확대 여부를 판단한다.

## Ⅴ. 심화 비교 및 적용 판단

| 구분 | 기존/대안 | 카나리 모델 배포 | 선택 기준 |
|:---|:---|:---|:---|
| 구조 | Blue/Green 전체 전환 | 단계별 트래픽 라우팅 | 사용자 영향 큰 모델 |
| 비용/성능 | 병렬 운영 짧음 | 두 모델 병렬 관찰 필요 | 리소스 2배 여유 |
| 운영/위험 | 장애 시 전체 영향 | 영향 범위 제한 | 자동 롤백 가능성 |

> 요약: 카나리는 병렬 운영 비용을 감수하고 신규 모델 위험을 제한할 때 선택한다.

| 리스크 | 원인 | 대응 방안 | 확인 지표 |
|:---|:---|:---|:---|
| 표본 부족 | 낮은 트래픽 비율 | 최소 요청 수와 관찰 시간 설정 | sample size |
| 사용자 편향 | 특정 세그먼트만 노출 | 무작위 라우팅, 세그먼트 균형 | segment ratio |
| 롤백 지연 | 수동 승인 대기 | 자동 롤백 정책 | rollback time |

> 요약: 카나리 리스크는 표본 부족, 세그먼트 편향, 롤백 지연이며 사전 정책으로 통제한다.

| 점검 항목 | 목표 기준 | 측정 방법 |
|:---|:---|:---|
| 서비스 지표 | p95 150ms, 오류율 0.1% 이하 | APM, gateway log |
| 업무 KPI | 기준 모델 대비 2%p 이내 | 실시간 대시보드 |
| 배포 통제 | 단계별 승인 로그 100% | CI/CD, registry log |

> 요약: 카나리 성공 여부는 서비스 지표, 업무 KPI, 배포 통제 로그로 판단한다.

## Ⅵ. 실무 적용 및 결론

**적용 방안 3개:**
1. Istio, NGINX, KServe 라우팅으로 v1 99%, v2 1%부터 시작하고 5%, 25%, 50%, 100% 단계를 정의함
2. p95 150ms 초과, 5xx 0.1% 초과, KPI 2%p 하락 중 하나 발생 시 자동으로 v2 트래픽을 0%로 전환함
3. 모델 레지스트리와 배포 로그를 연결해 각 단계의 승인자, 지표, 롤백 사유를 감사 증적으로 보존함

**결론 (2줄):**
- 기술사 판단: 사용자 영향이 큰 온라인 모델은 카나리를 적용하고, 내부 배치 모델은 배치 샘플 검증 후 전환해도 된다
- 향후 방향: 카나리는 모델 모니터링과 자동 롤백 정책을 결합해 지표 기반 릴리스 자동화로 발전함
