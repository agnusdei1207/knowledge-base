# 📖 【암기용】 개념 완전 이해

## 한눈에
- **개요**: 두 개 이상의 테이블을 연결하여 데이터를 조회할 때, DBMS 실행 엔진이 물리적으로 데이터를 매칭시키는 3대 연산 방식이다.
- **왜 필요한가**: 데이터 볼륨과 인덱스 환경에 따라 조인 방식을 다르게 적용해야 디스크 I/O와 메모리 부하를 줄일 수 있기 때문이다.
- **핵심 직관**: 
  - **NLJ**: 이중 루프. 명단을 들고 집마다 직접 찾아가 확인하는 방식(소량/인덱스 필수)
  - **Sort Merge**: 양쪽을 정렬 후 비교 병합하는 방식(무식하지만 확실함)
  - **Hash Join**: 한쪽을 칠판(메모리)에 적어놓고 다른 쪽 명부를 스캔하며 한 번에 맞추는 방식(대용량)

## 핵심 용어 정리

| 용어/표기 | 의미 | 비유·예 |
|:---|:---|:---|
| Nested Loop Join (NLJ) | 외부 테이블 건수마다 내부 테이블을 인덱스로 탐색하는 이중 For문 방식 | `for (A) { for (B) { 매칭; } }` |
| Hash Join | 작은 테이블로 메모리에 해시맵을 만들고 큰 테이블 스캔하여 매칭 | 해시 테이블 생성 후 즉각 조회 |
| Sort Merge Join | 조인 키 기준으로 양쪽 정렬 후 순차 스캔 병합 | 양쪽 명부를 가나다 정렬 후 비교 |
| 드라이빙 테이블 | 루프의 바깥쪽에서 먼저 훑어보는 테이블(작을수록 유리) | 찾아갈 대상을 쥔 최초 기준 명부 |

## 깊이 이해
- **배경·문제의식**: 두 테이블(100건 × 100만 건) 조인 시 1억 번을 무식하게 비교하면 시스템이 정지한다. 인덱스가 있다면 점프(NLJ)가 좋고, 양쪽 다 대용량이면 메모리를 활용한 해시 방식이 필수다.
- **작동 원리**: 
  - NLJ는 내부 테이블의 조인 컬럼 인덱스가 반드시 있어야 하며 랜덤 액세스를 유발해 건수가 많으면 불리하다.
  - 해시 조인은 인덱스 없이도 동작하며 큰 대용량 테이블 스캔을 시퀀셜 I/O로 빠르게 처리한다.
- **비유**: VIP 10명과 10만 명 전체 명부 매칭 시, VIP 1명씩 인덱스로 찾는 게 NLJ고, 전체 명부 10만과 10만을 매칭할 땐 한쪽을 메모리에 외우고 맞추는 해시 조인이 낫다.
- **구체 예시**: 온라인 화면 단건 상세 조회(OLTP)는 NLJ, 야간 수천만 건 통계 집계(OLAP)는 Hash 조인으로 실행 계획이 잡힌다.
- **흔한 오해·주의점**: 해시 조인이 무조건 빠른 게 아니다. 메모리 소모가 크고 초기 해시 테이블 생성 비용이 들기 때문에 소량 데이터에서는 NLJ가 훨씬 응답이 빠르다.

## 연결 개념
- **실행 계획**: 옵티마이저가 3가지 알고리즘 중 비용 계산을 통해 결정하는 결과물.
- **랜덤 액세스와 시퀀셜 스캔**: 물리적 I/O 동작 패턴.

# 📝 【답안용】 시험 답안 템플릿

## 핵심 인사이트 (3줄 요약)

> 1. **본질**: RDBMS 옵티마이저가 테이블 결합(Join) 시 비용 산정에 의해 선택하는 내부 물리적 탐색 알고리즘
> 2. **가치**: 데이터 볼륨, 인덱스 환경, 업무 패턴(OLTP/OLAP)에 맞춰 디스크 I/O와 메모리를 최적 타협
> 3. **판단 포인트**: 랜덤 액세스 기반 NLJ와 메모리 기반 해시 조인의 상반된 아키텍처 특성과 튜닝 지점 명시

## 출제 의도 및 답안 포인트

| 출제 의도 | 반드시 짚을 핵심 | 감점 회피 포인트 |
|:---|:---|:---|
| 데이터 특성에 맞춘 조인 메커니즘 설계 역량 파악 | NLJ(인덱스 랜덤 액세스)와 Hash Join(메모리 시퀀셜) 작동 구조 차이 | 논리적 조인(Inner, Outer Join) 개념과 혼용하는 서술 지양 |

> 요약: 논리적 조인을 위해 내부 엔진이 가동하는 3가지 무기의 원리와 한계 조건을 명확히 비교해야 한다.

---

## Ⅰ. 개요 및 필요성

- 개요: RDBMS에서 2개 이상 릴레이션 연결 시 DBMS 엔진이 사용하는 물리적 탐색/매칭 알고리즘 (NLJ, Hash, Sort Merge)
- 배경: 테이블 크기 비대화 및 인덱스 환경 불균형에 따라 단일 결합 방식(이중 루프)만으로는 병목 해소 불가
- 필요성: 시스템 가용 자원(메모리)과 조인 대상 건수 분포를 종합하여 최적 I/O 알고리즘을 선택해 응답 속도 SLA 보장

---

## Ⅱ. 구조 및 구성요소

```text
Driving Table ---------(매칭 방식 선택)---------> Driven Table
  +-> 1. 소량, 인덱스 보유 ---------> [ Nested Loop Join (랜덤 룩업) ]
  +-> 2. 대량, 인덱스 무관, 동등(=) -> [ Hash Join (메모리 맵 매칭) ]
  +-> 3. 대량, 인덱스 무관, 범위(>) -> [ Sort Merge Join (정렬 병합) ]
```

| 조인 방식 | 동작 핵심 | 주요 제약 및 단점 |
|:---|:---|:---|
| Nested Loop (NLJ) | 드라이빙 건수만큼 내부 테이블 인덱스를 이중 루프 반복 탐색 | 대량 조인 시 심각한 랜덤 디스크 액세스 부하 |
| Hash Join | 작거나 필터링된 테이블로 메모리(PGA) 해시맵 구성 후 큰 테이블 룩업 | 동등(`=`) 조건만 가능, 메모리 초과 시 Temp 공간 스왑 병목 |
| Sort Merge Join | 양쪽 데이터를 조인 키 기준으로 정렬(Sort)한 뒤 차례대로 병합 | 엄청난 정렬 CPU/메모리 부하 유발 |

> 요약: NLJ는 소량 핀포인트 탐색에, 해시 조인은 대용량 동등 매칭에 강점을 지닌다.

---

## Ⅲ. 동작원리 및 흐름도

```text
(해시 조인 동작 기준)
빌드 테이블 Read -> 해시 함수 적용 -> PGA 메모리 적재 -> 프로브 테이블 Read -> 해시 충돌 매칭 -> 병합 결과 출력
```

- 1단계 NLJ 작동: 선행(드라이빙) 테이블 레코드마다 후행 테이블의 조인 키 인덱스로 핑퐁 치듯 점프(Random I/O) 수행
- 2단계 Sort Merge 작동: 인덱스가 부족할 때 양 테이블을 Sort Area로 퍼 올려 키 기준으로 정렬 후 톱니바퀴처럼 순차 병합
- 3단계 Hash Build: 메모리 적재가 유리한 작은 테이블을 Full Scan 하여 키 값 해시 맵핑 구조물(PGA 내)을 생성
- 4단계 Hash Probe: 대용량 테이블 스캔 시 건마다 해시 맵에 프로빙하여 일치 레코드를 고속으로 결합 출력

> 요약: 각각 루프 인덱스(NLJ), 정렬공간(Sort), 해시영역(Hash)을 도구로 활용해 매칭 비용을 최적화한다.

---

## Ⅳ. 특징
- 드라이빙 크기 민감도(NLJ): NLJ는 바깥 루프 반복 횟수 자체가 총 성능이므로 선행 필터링 테이블 크기가 극도로 작아야 유리함
- 인덱스 종속성 차이: NLJ는 이너(Inner) 테이블 인덱스 부재 시 성능이 파괴되나, Hash/Sort는 어차피 Full Scan을 타므로 인덱스 영향이 적음
- 등가 조건 한계(Hash): 해싱 알고리즘 특성 상 `WHERE A=B` 조건만 지원하며 범위 조인(`BETWEEN, >, <`)에는 적용 불가능
- 메모리 의존 병목: 해시와 소트 방식 모두 할당된 메모리 한계(WorkArea)를 넘으면 느린 디스크 Temp 영역으로 스왑(Spill)되어 급격한 성능 저하 발생

> 요약: 각 알고리즘은 뚜렷한 리소스 편향(I/O, 메모리, CPU)을 지니고 있어 쿼리 성격과 맞지 않으면 악성 플랜이 된다.

---

## Ⅴ. 심화 비교 및 적용 판단

| 비교 축 | Nested Loop Join | Hash Join | 선택 기준 |
|:---|:---|:---|:---|
| 최적 쿼리 | 단건 화면 상세조회 (OLTP) | 대용량 통계 배치 조회 (OLAP) | 추출 예상 건수 |
| 인덱스 필요성 | 내부 테이블 인덱스 **필수** | 조인 키 인덱스 **불필요** | 데이터 모델 스키마 환경 |
| I/O 엑세스 패턴 | Random I/O 반복 발현 | 양쪽 Sequential I/O | 스토리지 물리 특성 |

> 요약: 화면 단건 반응(OLTP)은 인덱스 NLJ로 처리하고 심야 대량 집계(OLAP)는 무조건 Hash를 유도한다.

**리스크·대응:**
- 잘못된 드라이빙 (NLJ): 100만 건 테이블이 선행이 되어 루프를 100만 번 도는 참사 유발 → `/*+ LEADING(작은테이블) USE_NL(A B) */` 힌트 강제 고정 (지표: 논리적 I/O 증가 폭)
- 해시 메모리 스왑 (Temp Spill): 해시 맵 크기가 PGA를 초과해 디스크 I/O 발생 지연 → 선행 조건문 추가로 빌드 크기 압축 및 PGA 설정 상향 검토 (지표: 디스크 템프 영역 사용량)

**도입 후 점검 지표:**
- 성능/효율: `EXPLAIN` 실행계획 노드 확인 — 10만 건 이상 쿼리 시 NLJ 미발생 체크
- 품질/운영: DB CPU 및 Temp 테이블스페이스 모니터링 — 무분별한 Sort Merge 발생 감지

---

## Ⅵ. 실무 적용 및 결론

**적용 방안 3개:**
1. OLTP 화면 조회 NLJ 고정: 페이징 쿼리나 단건 상세조회 시 옵티마이저가 착각해 Hash를 타면 1건 응답속도가 크게 늦어지므로 명시적 NL 힌트를 통한 반응성 확보
2. OLAP 야간 배치 Hash 유도: 인덱스가 존재해도 수백만 건 처리 시 랜덤 점프가 마비 부하를 일으키므로 `/*+ FULL(A) FULL(B) USE_HASH(A B) */` 해시 조인 힌트 적용
3. 조인 회피 반정규화 튜닝: 조인 알고리즘 튜닝 한계를 넘어서는 초대용량 핵심 엔티티 간 조인은 아키텍처 관점 물리적 테이블 반정규화 병합으로 선제 해결

**결론:**
- 기술사 판단: 조인 알고리즘은 SQL 튜닝 최후의 보루다. 데이터 양, 인덱스 상태, 할당 가능 메모리를 종합 분석해 옵티마이저가 틀린 길을 갈 때 개발자가 최적 기법을 강제해야 한다.
- 향후 방향: 빅데이터 프레임워크(Spark)에서는 단일 노드 해시 조인을 넘어 셔플링을 동반한 Broadcast Hash Join 등 분산 클러스터 조인 기법이 텍스트 데이터 매칭의 핵심으로 자리 잡았다.
