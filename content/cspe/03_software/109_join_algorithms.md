## 핵심 인사이트 (3줄 요약)
- 흩어져 있는 2개 테이블을 묶어서(JOIN) 하나의 결과로 가져올 때, DB 엔진(옵티마이저)이 내부적으로 사용하는 **3대 물리적 결합 방식**.
- **Nested Loop (NL) 조인**은 이중 For문처럼 한 줄씩 비교하므로 데이터가 적거나 인덱스가 완벽할 때 빠르고, **Hash 조인**은 대용량 데이터에서 메모리 해시 테이블을 띄워 일괄 처리하는 현대 데이터 웨어하우스의 꽃임.
- 어떤 알고리즘이 무조건 좋은 것은 없으며, 조인되는 양쪽 테이블의 크기(Row 건수)와 인덱스 유무에 따라 옵티마이저가 최적의 무기를 런타임에 선택함.
---
## Ⅰ. 개요 및 필요성
- **개요**: RDBMS에서 두 릴레이션 간의 교집합(Join)을 계산하기 위해 디스크와 메모리를 활용하는 실행 엔진의 내부 알고리즘.
- **필요성**: 회원 테이블 100만 건과 주문 테이블 100만 건을 합치려면 최악의 경우 100만 × 100만 = 1조 번의 비교 연산이 필요함. 이 무식한 카테시안 곱(Cartesian Product)을 피하고, 제한된 메모리와 디스크 I/O 환경에서 가장 빨리 매칭되는 짝을 찾을 수학적/자료구조적 해법이 필요했음.
---
## Ⅱ. 아키텍처 및 핵심 원리
- **1. Nested Loop Join (NL 조인)**:
  - **원리**: 프로그래밍의 이중 For문(`for i in A: for j in B:`)과 똑같음. 외부 테이블(Driving)을 먼저 1줄 읽고, 내부 테이블(Driven)을 쭉 뒤져서 매칭함.
  - **조건**: 반드시 내부 테이블(Driven)의 조인 컬럼에 **인덱스**가 있어야 함. 인덱스가 없으면 내부 테이블 풀스캔을 반복해야 하므로 지옥이 펼쳐짐. (OLTP 환경 특화).
- **2. Sort Merge Join (정렬 병합 조인)**:
  - **원리**: 두 테이블을 조인 컬럼 기준으로 일단 메모리상에서 쫙 정렬(Sort)함. 그 후 양쪽을 한 줄씩 훑어 내려가며(Merge) 짝을 맞춤.
  - **특징**: 조인 컬럼에 인덱스가 없을 때 사용함. 하지만 대용량 데이터를 정렬하는 것 자체가 엄청난 CPU/메모리 비용(Temp DB 사용)을 잡아먹음.
- **3. Hash Join (해시 조인)**:
  - **원리**: 둘 중 작은 테이블(Build Input)을 메모리에 올려 해시 테이블(`Key: 조인 컬럼 값, Value: 데이터`)을 만듦. 그다음 큰 테이블(Probe Input)을 한 줄씩 읽으며 메모리 해시 함수에 던져서 매칭함.
  - **특징**: 동등 조인(`=`)에서만 사용 가능. 대용량 데이터(수백만 건 이상)를 조인할 때 정렬(Sort)도 안 하고, 인덱스도 안 타므로 압도적으로 가장 빠름. (OLAP 통계 쿼리 특화).

```text
[ NL 조인과 Hash 조인의 동작 방식 비교 ]

 🐌 [ NL 조인 (Nested Loop) - 낚시 방식 ]
 회원테이블(Driving) 1번 고객 읽음 ➡️ 주문테이블(Driven) 인덱스 타고 주문 내역 가져옴
 회원테이블(Driving) 2번 고객 읽음 ➡️ 주문테이블(Driven) 인덱스 타고 주문 내역 가져옴
 * 특징: OLTP(온라인 결제)에서 1~2건 소량 조회 시 번개처럼 빠름. 10만 건 넘어가면 기어감.

 🚀 [ Hash Join - 그물망 방식 ]
 1단계: (작은 쪽인) 회원테이블 10만 명을 메모리에 Hash 맵으로 싹 다 올려버림!
 2단계: 주문테이블 1,000만 건을 풀스캔하면서 한 줄씩 Hash 맵에 찔러봄. (탁, 탁, 탁 맞춤!)
 * 특징: 디스크 랜덤 I/O를 없애고 메모리 연산으로 승부. 대용량 통계 배치 작업의 제왕.
```

## Ⅲ. 비교 및 연결
| 구분 | Nested Loop Join | Sort Merge Join | Hash Join |
|---|---|---|---|
| **메커니즘** | 이중 루프 (For문) | 양쪽 정렬 후 병합 | 메모리 해시맵 생성 후 스캔 |
| **최적 환경** | 데이터 건수가 적을 때 | 인덱스 없고 동등(=) 조건 아닐 때 | **대용량 데이터, 동등(=) 조인** |
| **필수 조건** | **내부 테이블에 인덱스 필수** | 메모리(PGA) 여유 공간 | **해시맵을 띄울 메모리 공간 필수** |
| **성능 병목** | 랜덤 디스크 I/O 폭발 | 정렬(Sort) 작업의 오버헤드 | 작은 테이블이 너무 크면 디스크 스왑 발생 |

## Ⅳ. 실무 적용 및 기술사 판단
- **Driving 테이블 튜닝 (NL Join)**: NL 조인에서 최악의 튜닝 실수는 "데이터가 100만 건인 테이블을 먼저 읽고(Driving), 10건인 테이블을 나중에 뒤지게(Driven)" 짜는 것임. 이러면 100만 번의 루프가 돎. 실무에서는 옵티마이저가 멍청할 경우 힌트(`/*+ LEADING(A B) */`)를 주어, 무조건 10건짜리 작은 테이블이 먼저 반복문의 바깥 루프(Driving)를 돌도록 강제해야 함.
- **MySQL의 한계와 Hash Join의 등장**: 과거 MySQL은 무식하게 100% NL Join만 지원하여 대용량 데이터 웨어하우스(통계 DB) 용도로는 폐급 취급을 받았음. 그러나 MySQL 8.0부터 드디어 Hash Join 알고리즘을 도입하면서, 대용량 분석 환경에서도 Oracle 부럽지 않은 극강의 퍼포먼스를 낼 수 있게 됨.
---
## Ⅴ. 기대효과 및 결론
- "관계형 DB는 조인(JOIN) 때문에 느리다"는 NoSQL 진영의 비판을 방어해 내는 핵심 기술로, 알고리즘의 진화(Hash Join 등)를 통해 대용량 빅데이터 환경에서도 RDB의 수명을 연장시켰음.
- 데이터베이스 개발자는 단순히 `JOIN` 키워드를 쓰는 데 그쳐서는 안 되며, 내가 짠 조인이 메모리 해시를 탈지 이중 루프를 돌지 실행 계획(Explain)을 보며 예측하고 튜닝할 수 있어야 함.

### 👶 어린이를 위한 3줄 비유 설명
1. **Nested Loop (NL 조인)**: 반 친구들(A) 이름을 한 명씩 부를 때마다, 도서관 장부(B)를 뒤져서 빌린 책이 있는지 30번 반복해서 찾아보는 거예요.
2. **Sort Merge (정렬 병합)**: 학생 이름과 장부를 아예 둘 다 '가나다순'으로 쫙 정렬해 놓고, 양쪽을 손가락으로 동시에 짚어 내려가며 짝을 맞추는 거예요.
3. **Hash Join (해시 조인)**: 학생 명단 30명을 머릿속(메모리)에 완벽히 다 외워버린 다음, 수만 건의 장부를 넘기면서 눈에 띄는 족족 머릿속 명단과 번개처럼 맞추는 최고급 기술이랍니다!
