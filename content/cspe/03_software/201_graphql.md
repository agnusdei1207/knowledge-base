## 핵심 인사이트 (3줄 요약)
- REST API의 가장 큰 고질병인 **"너무 많이 주거나(Over-fetching), 너무 적게 줘서 여러 번 호출해야 하는(Under-fetching)" 문제를 해결하기 위해 페이스북이 만든 차세대 쿼리 언어**.
- 서버가 일방적으로 내려주는 데이터 형태를 클라이언트가 수동적으로 받는 것이 아니라, **클라이언트(프론트엔드)가 "나는 이름, 이메일, 그리고 최근 작성한 글 3개만 딱 줘!"라고 쿼리를 날려서 원하는 데이터만 골라 먹는 뷔페식 API**임.
- REST처럼 `/users`, `/posts` 같이 주소가 수십 개 파편화되지 않고, 오직 `/graphql` 이라는 **단 하나의 엔드포인트**를 통해 세상 모든 데이터를 엮어서(그래프) 가져올 수 있음.

## Ⅰ. 개요 및 필요성
- **개요**: 클라이언트가 서버로부터 데이터를 효율적으로 가져오기 위해 사용하는 데이터 쿼리 언어 및 런타임 환경.
- **필요성**: 페이스북 모바일 앱을 만듦. 유저 프로필 화면을 그리려면 "유저 정보", "친구 목록", "최근 글" 데이터가 필요함. REST API를 쓰면 `/users/1`, `/users/1/friends`, `/users/1/posts` 총 3번이나 통신(Round-trip)을 해야 하고 3G 망에서 너무 느림(Under-fetching). 반대로 하나의 큰 API를 만들었더니 필요 없는 데이터까지 10MB씩 날아옴(Over-fetching). **"아니, 프론트엔드가 필요한 데이터만 체크해서 한 번에 주문서(Query)를 보내면, 백엔드가 딱 그것만 묶어서 한 번에 배달해 주면 안 돼?"**라며 GraphQL이 탄생함.
---
## Ⅱ. 아키텍처 및 핵심 원리
- **1. 단일 엔드포인트 (Single Endpoint)**:
  - REST는 자원마다 URL이 다름. GraphQL은 무조건 `POST /graphql` 주소 딱 하나만 씀. 
  - 요청의 'Body' 안에 내가 무엇을 원하는지 쿼리를 담아서 던짐.
- **2. 스키마와 타입 시스템 (Schema & Type System)**:
  - 백엔드 개발자는 사전에 "우리가 가진 데이터는 User, Post, Comment가 있고 서로 이렇게 연결되어 있어"라는 명세서(Schema)를 강타입(Strongly Typed)으로 쫙 정의해 둠.
- **3. 클라이언트 주도 쿼리 (Client-Driven Query)**:
  - 프론트엔드 개발자는 스키마를 보고 뷔페에서 음식 담듯 쿼리를 짬.
  - "User 1번 주세요. 아, 근데 다 주지 말고 `이름`이랑, 그 사람이 쓴 `Post의 제목`만 가져오세요."
- **4. 리졸버 (Resolver)**:
  - 백엔드에 있는 조립 공장. 프론트의 쿼리를 받으면, `User` 정보는 DB에서 캐오고, `Post` 정보는 옆 부서 API에서 캐와서 하나로 예쁘게 조립한 뒤 JSON으로 던져줌.

```text
[ REST API vs GraphQL 데이터 요청 비교 ]

 📦 [ REST API (정식 세트 메뉴만 팔아요) ]
 - 클라이언트: "유저 1번 세트 주세요." (`GET /users/1`)
 - 서버 응답: { "id": 1, "name": "철수", "age": 20, "address": "서울", "phone": "010-...", ... }
 * 불만: "난 이름만 필요한데 왜 주소랑 전화번호까지 줘서 데이터를 낭비하지? (Over-fetching)"

 🛒 [ GraphQL (원하는 것만 담는 뷔페) ]
 - 클라이언트: "유저 1번에서 이름만, 그리고 걔가 쓴 글 제목만 줘." (단일 쿼리 요청)
   query { user(id: 1) { name, posts { title } } }
 - 서버 응답: { "user": { "name": "철수", "posts": [ { "title": "안녕!" } ] } }
 * 만족: 단 한 번의 통신으로 원하는 데이터만 100% 깔끔하게 받아옴! 🎉
```

## Ⅲ. 비교 및 연결
| 구분 | REST API | GraphQL |
|---|---|---|
| **엔드포인트(URL)** | 데이터마다 다름 (`/users`, `/posts`) | **오직 1개 (`/graphql`)** |
| **데이터 결정권** | **서버(Backend)가 결정** | **클라이언트(Frontend)가 결정** |
| **네트워크 통신** | 여러 번 호출 발생 (Under-fetching) | **단 한 번의 호출로 끝남 (효율 극대화)** |
| **단점 (Trade-off)**| 오버페칭, 언더페칭 발생 | HTTP 캐싱(CDN)이 매우 어려움, N+1 쿼리 문제 발생 |
| **주요 사용처** | 범용 B2B API, 마이크로서비스 간 통신 | **데이터 복잡도가 높은 모바일/프론트엔드 통신** |

## Ⅳ. 실무 적용 및 기술사 판단
- **BFF (Backend for Frontend) 패턴의 핵심 엔진**: MSA로 쪼개진 20개의 백엔드 서버를 프론트엔드가 일일이 호출하는 것은 미친 짓임. 기술사는 프론트엔드와 백엔드 사이에 **GraphQL을 BFF(중간 게이트웨이)로 세우는 아키텍처**를 설계해야 함. 프론트엔드가 GraphQL에 쿼리 하나만 던지면, GraphQL 서버(리졸버)가 뒤에 있는 20개의 MSA를 동시에 찔러서 데이터를 긁어모은 뒤 조립해서 프론트엔드로 전달하는 '오케스트레이터' 역할을 수행하게 함.
- **캐싱(Caching)과 N+1 문제 방어**: GraphQL의 치명적 약점. REST는 URL이 다 달라서 웹 브라우저나 CDN이 캐싱하기 좋음. 근데 GraphQL은 무조건 `POST /graphql`만 쓰므로 기존 방식의 캐싱이 안 됨. 또한, 리졸버가 생각 없이 DB를 찌르면 쿼리 1번에 DB 셀렉트가 100번 날아가는 **'N+1 문제'**가 터짐. 실무에서는 반드시 `Dataloader`라는 툴을 써서 DB 쿼리를 한 방에 묶어서(Batch) 보내도록 최적화해야 함.
---
## Ⅴ. 기대효과 및 결론
- 프론트엔드 개발자가 화면에 새로운 데이터를 하나 추가하려고 할 때마다 백엔드 개발자에게 "API 좀 수정해 주세요"라고 아쉬운 소리를 해야 했던 수십 년의 굴레를 끊어냄.
- 데이터의 요구사항이 시시각각 변하는 모바일 시대에, 네트워크 페이로드를 극단적으로 줄이면서도 개발 생산성을 폭발적으로 높여준 가장 현대적인 프론트-백엔드 간의 통신 규약임.

### 👶 어린이를 위한 3줄 비유 설명
1. **REST API 식당**은 '정식 세트'만 팔아요. 김밥만 먹고 싶은데 무조건 떡볶이와 튀김까지 같이 나와서 돈(데이터)이 낭비되죠.
2. **GraphQL 식당**은 '뷔페'예요. 식판(쿼리)을 들고 가서 "나는 김밥 2개, 콜라 1잔만 줘"라고 말하면 딱 그것만 담아줘요.
3. 내가 원하는 것만 한 번에, 남기지 않고 깔끔하게 받아올 수 있어서 스마트폰이 데이터 요금을 덜 쓰게 해 준답니다!
