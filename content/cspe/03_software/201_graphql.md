## Ⅰ. 개요
- **정의**: 클라이언트가 필요한 데이터 구조를 질의로 명시하여 서버에서 정확히 해당 형태로 응답받는 API 질의 언어
- **배경/필요성**: REST에서 엔드포인트별 고정 응답으로 인한 Over-fetching·Under-fetching 문제 해소 필요
- **비유**: 뷔페(REST)에서 세트메뉴 전부 받는 대신, 단품 주문서(Query)로 원하는 요리만 받는 방식

| 출제 의도 | 반드시 짚을 핵심 | 감점 회피 포인트 |
|:---|:---|:---|
| REST 대비 구조적 차이 이해 | 단일 엔드포인트, 스키마 기반 타입 시스템 | Query·Mutation·Subscription 세 연산 구분 |

> 요약: 클라이언트 주도 질의로 필요한 데이터만 정확히 수신하는 API 질의 언어임

## Ⅱ. 구성요소
```text
Client --Query/Mutation--> [GraphQL Server]
                              |
                     +--------+--------+
                     |        |        |
                  Schema   Resolver  DataSource
```

| 구성요소 | 설명 | 비유 |
|:---|:---|:---|
| Schema | 타입·필드·관계를 정의하는 계약 명세 | 메뉴판 |
| Resolver | 각 필드 요청을 실제 데이터 소스에 매핑하는 함수 | 주방장 |
| DataSource | DB·REST·외부 서비스 등 실제 데이터 저장소 | 식재료 창고 |

> 요약: 스키마로 계약을 정의하고 리졸버가 데이터 소스에서 값을 조회하여 반환함

## Ⅲ. 절차
```text
Query 작성 --> Schema 검증 --> Resolver 실행 --> 응답 조립
```
- 1단계: 클라이언트가 필요한 필드를 명시한 Query 또는 Mutation 작성
- 2단계: 서버가 스키마 타입 시스템으로 질의 구문·타입 유효성 검증
- 3단계: 검증 통과 시 각 필드에 매핑된 Resolver 함수 실행
- 4단계: Resolver 결과를 질의 구조에 맞춰 JSON 응답으로 조립·반환

> 요약: 질의 작성부터 스키마 검증, 리졸버 실행, 응답 조립까지 4단계로 처리함

## Ⅳ. 문제점
- N+1 쿼리: 중첩 필드마다 개별 DB 호출 발생 — 응답 지연 급증
- 복잡 질의 공격: 깊은 중첩 질의 허용 시 서버 자원 고갈 — 가용성 저하
- 캐싱 난이도: 단일 엔드포인트·가변 응답 구조로 HTTP 캐시 적용 곤란

> 요약: N+1 쿼리, 복잡 질의 공격, 캐싱 난이도가 주요 문제임

## Ⅴ. 개선방안
1. 단기: DataLoader 패턴으로 배치·캐시 처리하여 N+1 쿼리 해소
2. 중기: 질의 깊이·비용 제한(Query Complexity Analysis) 적용으로 악의적 질의 차단
3. 장기: Persisted Query·CDN 엣지 캐싱 도입으로 응답 캐시 체계 구축

> 요약: 배치 로딩, 질의 복잡도 제한, 영속 질의 캐싱으로 단계적 개선함

## Ⅵ. 전망
- 발전 방향: Federation 기반 분산 스키마 통합으로 마이크로서비스 간 단일 그래프 제공
- 기술사적 판단: BFF(Backend For Frontend) 패턴과 결합 시 프론트엔드 생산성 극대화 가능
- 기술사 제언: REST·gRPC와 용도별 혼용 전략 수립이 현실적 접근임
