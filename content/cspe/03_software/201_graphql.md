## 미리 알고가기

- GraphQL은 스키마의 타입·필드·인자를 기준으로 클라이언트가 필요한 결과 필드를 선택하는 질의 언어와 실행 규격임
- Query는 조회, Mutation은 변경, Subscription은 시간에 따라 발생하는 결과 스트림을 표현함
- 요청은 구문 분석·스키마 검증·변수 강제 변환을 통과한 뒤 필드별 Resolver에서 실행됨
- 응답은 선택 집합과 같은 형태의 `data`를 반환하며 필드 실행 오류는 `errors`와 부분 결과로 표현할 수 있음
- GraphQL 규격은 특정 전송 프로토콜·URL 개수·저장소를 강제하지 않으므로 HTTP·단일 엔드포인트는 구현 선택임

## 작성 근거(검토용)

- GraphQL은 타입 스키마, 선택 집합, 검증·실행, Resolver, 부분 오류, 질의 비용 통제를 핵심 축으로 설명함
- 비교표는 REST와 계약·결과 형태·연관 조회·변경·캐시·권한·적합 조건을 같은 수준에서 대비함
- 상품 상세 집계와 다중 클라이언트 API는 Resolver 호출 수·p95 지연·응답 크기·차단률로 검증함

## Ⅰ. 개요

- **정의/개념**: GraphQL은 타입 스키마에 정의된 필드를 클라이언트가 선택하고 실행기가 Resolver 결과를 선택 집합 형태로 조합하는 API 질의 언어·실행 체계임
- **배경/필요성**: 화면마다 필요한 필드·연관 개체가 다를 때 고정 자원 표현과 여러 요청의 결합을 줄이고 하나의 타입 계약에서 조회 형태를 조정하기 위해 필요함

## Ⅱ. 특징

- 강타입 스키마가 Object·Scalar·Enum·Interface·Union과 필드 인자·Null 가능성을 정의함
- 클라이언트는 Query·Mutation·Subscription의 선택 집합으로 반환 필드와 중첩 관계를 지정함
- 실행 전 스키마 검증으로 존재하지 않는 필드·잘못된 인자·타입 불일치를 거부함
- Resolver가 필드별 데이터를 가져오므로 중첩 목록에서 N+1 호출이 발생하면 배치·요청 범위 캐시가 필요함
- 깊이·별칭·목록 크기에 따라 실행 비용이 증가하므로 깊이·복잡도·시간 제한과 필드별 권한을 적용함
- 필드를 추가하고 기존 필드를 폐기 예정으로 표시해 스키마를 진화시키되 소비자 사용량 확인 후 제거함

## Ⅲ. 종류 및 비교

| 판단 기준 | REST API | GraphQL API |
|:---|:---|:---|
| 계약 단위 | URI·HTTP 메서드·자원 표현 | 타입 스키마·필드·인자 |
| 결과 형태 | 서버가 엔드포인트별 표현을 결정 | 클라이언트가 선택 집합으로 필드를 결정 |
| 연관 데이터 | 자원 링크를 따라 추가 요청하거나 전용 표현 제공 | 중첩 필드를 한 연산에 기술 |
| 변경 방식 | POST·PUT·PATCH·DELETE 의미 사용 | Mutation 필드와 입력 타입 사용 |
| 캐시 기준 | URI·메서드·HTTP 캐시 헤더 | 연산·변수·개체 식별자 기반 응용 캐시 |
| 권한·비용 통제 | 엔드포인트·자원 단위 정책 | 타입·필드 권한과 질의 깊이·복잡도 제한 |
| 적합 조건 | 자원 표현·HTTP 캐시·공개 인터페이스가 중심 | 화면별 필드 조합·연관 데이터 탐색이 중심 |

> 요약: REST는 자원별 표현을 제공하고, GraphQL은 타입 스키마에서 클라이언트가 필요한 필드와 관계를 선택함.

## Ⅳ. 구성요소 및 구조

| 구성요소 | 설명 |
|:---|:---|
| 타입 스키마 | 질의 가능한 타입·필드·인자·Null 가능성과 진입 타입을 정의함 |
| Operation·Selection Set | Query·Mutation·Subscription과 반환할 필드 구조를 기술함 |
| Parser·Validator | 문서를 구문 트리로 만들고 스키마·변수·연산 규칙을 검사함 |
| Execution Engine | 선택 집합을 순회하고 필드 결과를 응답 형태로 조합함 |
| Resolver·DataLoader | 데이터 원천을 호출하고 같은 요청의 키 조회를 배치·캐시함 |
| 응답·오류 | `data`·`errors`·확장 메타데이터로 결과와 필드 오류를 전달함 |

```text
Operation + Variables -> Parse -> Validate -> Execute Resolvers -> data + errors
                                                   └-> DB·API·Cache
```

> 요약: GraphQL 실행기는 연산을 스키마로 검증하고 Resolver 결과를 선택 집합과 같은 응답 구조로 조합함.

## Ⅴ. 원리 및 절차 흐름도

```text
문서 구문 분석 -> 스키마 검증 -> 변수 변환 -> 필드 실행 -> 결과·오류 조합
```

1. **문서 구문 분석**: Query 문서와 Fragment를 추상 구문 트리로 변환함
2. **스키마 검증**: 선택 필드·인자·변수 타입과 연산 이름을 타입 체계에 대조함
3. **변수 변환**: 입력 값을 선언 타입과 기본값에 맞게 강제 변환함
4. **필드 실행**: 진입 타입부터 Resolver를 호출하고 목록·중첩 선택을 순회함
5. **결과·오류 조합**: 필드 결과를 `data`에 배치하고 실행 오류의 경로를 `errors`에 기록함

> 요약: GraphQL은 질의를 스키마로 검증한 뒤 필드 Resolver를 실행하고 선택 집합 형태의 데이터와 오류를 반환함.

## Ⅵ. 실무 사례

1. 상품 상세 BFF는 GraphQL과 DataLoader로 서비스 결과를 묶고 Resolver 호출 수·p95 지연을 확인함
2. 모바일·웹 공통 API는 필드 권한과 질의 비용 제한을 적용하고 응답 크기·고비용 질의 차단률을 확인함

## Ⅶ. 결론

- GraphQL은 화면별 데이터 조합 요구와 스키마 진화 능력이 있고 Resolver 비용·필드 권한을 통제할 때 적용해야 함
