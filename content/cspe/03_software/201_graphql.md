# 📖 【암기용】 개념 완전 이해

## 한눈에
- **개요**: 클라이언트가 필요한 데이터의 구조를 직접 지정하여 단일 엔드포인트에서 조회하는 API 질의어
- **왜 필요한가**: REST API는 정해진 구조로만 응답하므로 불필요한 데이터까지 받는 오버패칭(Over-fetching)이나, 필요한 데이터를 다 얻기 위해 여러 번 요청하는 언더패칭(Under-fetching) 문제가 발생한다.
- **핵심 직관**: 식당(서버)에서 정해진 세트 메뉴(REST)를 시키는 대신, 뷔페에서 원하는 음식(필드)만 정확히 접시(쿼리)에 담아오는 방식이다.

## 핵심 용어 정리

| 용어/표기 | 의미 | 비유·예 |
|:---|:---|:---|
| Schema (스키마) | API가 제공하는 데이터 타입과 관계의 명세 | 뷔페 메뉴판 |
| Query (질의) | 데이터 조회 (REST의 GET) | "샐러드 1개, 고기 2점 주세요" |
| Mutation (변이) | 데이터 생성·수정·삭제 (REST의 POST/PUT/DELETE) | "고기 굽기 정도를 미디엄으로 변경" |
| Resolver (리졸버) | 각 필드의 데이터를 실제로 가져오는 백엔드 함수 | 요리사가 주문받은 음식을 조리하는 과정 |

## 깊이 이해
- **배경·문제의식**: 모바일 환경에서는 네트워크 대역폭 제한과 배터리 문제로 요청 횟수를 줄이는 것이 중요하다. 페이스북은 모바일 앱의 복잡한 UI를 구성하기 위해 기존 REST 방식의 비효율(엔드포인트 폭증, 오버/언더패칭)을 극복하고자 GraphQL을 개발했다.
- **작동 원리**: 클라이언트는 JSON 형태와 유사한 쿼리로 원하는 필드(예: 사용자 이름, 이메일, 친구 목록)를 단일 엔드포인트(`/graphql`)로 POST 요청한다. 서버의 GraphQL 엔진은 스키마를 검증하고, 각 필드에 연결된 리졸버를 호출해 정확히 요청된 구조대로 JSON 응답을 조립해 반환한다.
- **비유**: REST API가 완성된 햄버거 세트를 주는 드라이브스루라면, GraphQL은 서브웨이처럼 빵, 채소, 소스를 하나하나 지정해 단 한 번의 주문으로 원하는 샌드위치를 받는 방식이다.
- **구체 예시**: 블로그 글과 작성자 정보를 얻기 위해 REST는 `/posts/1`과 `/users/2`를 각각 호출하지만, GraphQL은 `query { post(id: 1) { title, author { name } } }` 한 번으로 해결한다.
- **흔한 오해·주의점**: "GraphQL이 REST보다 무조건 빠르다"는 오해다. 단일 요청은 맞지만, 서버 측에서 리졸버가 중첩 호출되며 N+1 문제가 발생하기 쉬워 데이터베이스 부하는 오히려 증가할 수 있다. DataLoader 같은 최적화 도구가 필수다.

## 연결 개념
- **RESTful API**: 기존의 자원 중심 다중 엔드포인트 구조 (비교 대상)
- **BFF (Backend for Frontend)**: 프론트엔드 맞춤형 API를 제공한다는 점에서 GraphQL과 목적이 유사함
- **N+1 문제**: 1개의 쿼리로 N개의 연관 데이터를 가져올 때 발생하는 DB 쿼리 폭증 현상

# 📝 【답안용】 시험 답안 템플릿

## 핵심 인사이트 (3줄 요약)

> 1. **본질**: 단일 엔드포인트를 통해 클라이언트가 필요한 데이터 형식을 주도적으로 명세하는 API 질의어(Query Language)이다.
> 2. **가치**: 오버패칭과 언더패칭을 제거하여 네트워크 페이로드를 최소화하고 프론트엔드의 생산성을 극대화한다.
> 3. **판단 포인트**: 자유도가 높은 만큼 서버 측의 N+1 문제, 복잡도 공격(DoS), 캐싱 어려움이라는 트레이드오프를 수반하므로 DataLoader와 깊이 제한(Depth Limit) 통제가 필수적이다.

## 출제 의도 및 답안 포인트

| 출제 의도 | 반드시 짚을 핵심 | 감점 회피 포인트 |
|:---|:---|:---|
| REST API 한계와 GraphQL 극복 방안 이해 | 오버패칭/언더패칭, 단일 엔드포인트, 스키마, 리졸버 | REST와의 단순 정의 나열 (비교 지표 부재) |
| 도입 시 서버 측의 잠재적 리스크 파악 | N+1 문제, HTTP 캐싱 한계, 보안(복잡도) 위협 | 장점만 나열하고 성능 저하 원인 누락 |
| 실무 아키텍처 적용 방안 판단 | DataLoader 도입, Query Complexity 제한, APM 모니터링 | 구체적 해결 기술 없이 "최적화 필요"로 추상화 |

> 요약: REST의 한계를 극복하는 클라이언트 주도형 통신 방식임을 명시하고, 서버 부하와 캐싱 한계에 대한 아키텍처적 대응 방안을 제시해야 한다.

---

## Ⅰ. 개요 및 필요성

- 개요: 클라이언트가 단일 엔드포인트(`/graphql`)로 필요한 데이터의 구조와 필드를 명시하여 요청하는 API 쿼리 언어 및 런타임
- 배경: 모바일 환경 확산과 UI 복잡도 증가로 기존 REST API의 오버패칭(불필요 데이터 수신) 및 언더패칭(다중 요청) 한계 직면
- 필요성: 네트워크 요청 횟수와 페이로드 크기를 줄여 모바일 체감 성능(p95 지연시간)을 개선하고 UI 변경 시 백엔드 의존성 제거 필요

---

## Ⅱ. 구조 및 구성요소

```text
[클라이언트] -> (단일 엔드포인트 POST) -> [GraphQL 엔진] -> (Resolver 호출) -> [DB / 마이크로서비스]
   쿼리 명세                                  | 스키마 검증                      | 데이터 패치
```

| 구성요소 | 역할 | 특이사항 |
|:---|:---|:---|
| Schema (스키마) | API의 데이터 타입(Type)과 구조를 정의하는 명세서 | 강타입(Strong Type) 언어 기반 검증 |
| Query / Mutation | 데이터의 조회(Query) 및 수정·생성·삭제(Mutation) 정의 | 클라이언트가 원하는 반환 필드 명시 |
| Resolver (리졸버) | 스키마 필드별로 실제 데이터를 가져오는 백엔드 함수 | MSA 환경에서 여러 서비스를 통합 조회 |

> 요약: 클라이언트가 쿼리를 전송하면 서버의 GraphQL 엔진이 스키마를 검증하고 리졸버를 통해 연관 데이터를 취합한다.

---

## Ⅲ. 동작원리 및 흐름도

```text
클라이언트 쿼리 요청 -> 1. 스키마 유효성 검사 -> 2. 구문 분석 및 AST 생성 -> 3. 리졸버 트리 실행 -> 조립된 JSON 응답 반환
```

- 1단계 [쿼리 유효성 검증]: 수신된 쿼리가 서버에 정의된 스키마 타입과 일치하는지 검사
- 2단계 [구문 분석·AST 생성]: 쿼리 문자열을 파싱하여 추상 구문 트리(AST, Abstract Syntax Tree)로 변환
- 3단계 [리졸버 연쇄 호출]: AST의 각 노드에 매핑된 리졸버 함수를 병렬 또는 순차적으로 실행하여 데이터 패치
- 4단계 [결과 조립 및 반환]: 모든 리졸버의 실행 결과를 쿼리가 요구한 계층적 JSON 구조로 매핑하여 HTTP 200 OK 응답

> 요약: 쿼리는 스키마 기반 유효성 검사를 거친 후 AST로 변환되며, 각 필드 리졸버가 반환한 데이터를 조립해 JSON으로 응답한다.

---

## Ⅳ. 특징
- 단일 엔드포인트: `/graphql` 경로 하나만 노출하여 API 라우팅 복잡도를 낮추고 API 버저닝 불필요 (필드 단위 Deprecated 처리)
- 강타입 시스템 보장: 스키마를 통한 엄격한 타입 검사로 클라이언트-서버 간 데이터 불일치(Type Mismatch) 사전 차단
- N+1 문제 유발 가능성: 중첩된 객체(예: 게시글 10개 -> 각 작성자 10번 조회) 요청 시 DB I/O가 기하급수적으로 폭증

> 요약: 단일 엔드포인트와 유연성을 제공하지만, 내부적으로 리졸버 중첩 실행에 따른 데이터베이스 부하 리스크를 동반한다.

## Ⅴ. 심화 비교 및 적용 판단

| 비교 축 | REST API | GraphQL | 선택 기준 |
|:---|:---|:---|:---|
| 데이터 요청 | 오버패칭 / 언더패칭 | 클라이언트가 필요한 필드만 지정 | 네트워크 대역폭 제한 및 모바일 중심 서비스 |
| HTTP 캐싱 | URI 레벨의 브라우저 기본 캐싱 용이 | 단일 URI(POST) 사용으로 HTTP 캐싱 불가 | 데이터 변경 주기가 짧고 개인화된 실시간 렌더링 |
| 에러 처리 | HTTP 상태 코드(404, 500 등) 활용 | 항상 HTTP 200 반환, 응답 내 errors 객체 | 부분 실패(Partial Failure)를 허용하는 복합 UI |

> 요약: 복잡한 연관 데이터와 모바일 최적화가 중요할 때는 GraphQL을, 단순 자원 CRUD와 글로벌 CDN 캐싱이 핵심일 때는 REST를 선택한다.

**리스크·대응 (기본은 불릿):**
- N+1 쿼리 폭증: 리졸버 개별 실행으로 DB 부하 → DataLoader를 도입하여 리졸버 요청을 배칭(Batching) 및 애플리케이션 레벨 캐싱
- 악의적 복잡도 쿼리(DoS): 깊게 중첩된 재귀 쿼리 요청으로 서버 마비 → Query Depth Limit(예: 5단계) 설정 및 Query Cost 분석 통제
- 브라우저 HTTP 캐싱 불가: GET과 URI 기반 캐싱 우회 → Apollo Client의 정규화된 캐시(Normalized Cache) 또는 Persisted Queries 적용

**도입 후 점검 지표 (기본은 불릿):**
- 성능/효율: 클라이언트 페이로드 크기 감소율 30% 이상, DataLoader 적용 후 DB Query QPS 감소량
- 품질/운영: 리졸버 단위 지연시간(Resolver-level Latency) 모니터링, Query Depth 초과 차단 비율

## Ⅵ. 실무 적용 및 결론

**적용 방안 3개:**
1. MSA 통합을 위한 API Gateway 연동: 여러 마이크로서비스의 REST/gRPC 응답을 GraphQL 엔진(예: Apollo Federation)에서 단일 스키마로 통합 제공
2. DataLoader 패턴 필수 적용: Node.js/Spring 환경에서 연관 객체 조회 시 N+1 문제를 방지하기 위해 ID 배칭으로 In-clause(`WHERE id IN (...)`) 쿼리 튜닝
3. 보안 통제 파이프라인 구축: WAF 단에서 GraphQL 특화 공격 패턴 탐지 룰셋 추가 및 서버 단 쿼리 복잡도 상한 1,000점 이하 제한 통제

**결론 (2줄):**
- 기술사 판단: 모바일 중심의 다종 UI 대응과 네트워크 최적화가 필수라면 GraphQL이 적합하나, 사내 관리자 화면 등 단순 CRUD 환경에서는 REST를 유지하는 것이 비용 효율적이다.
- 향후 방향: 마이크로서비스 생태계 확장에 따라 단일 서버의 GraphQL을 넘어, 여러 서비스 스키마를 분산 조합하는 Apollo Federation 같은 GraphQL Federation 아키텍처로 진화해야 한다.
