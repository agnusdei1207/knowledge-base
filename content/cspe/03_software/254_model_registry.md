## Ⅰ. 개요
- **정의**: ML 모델 아티팩트와 메타데이터를 버전 관리하는 중앙 저장소임
- **배경/필요성**: 모델 파일이 개인 환경에 산재하면 배포 추적·롤백이 불가하므로 중앙 레지스트리가 필요함
- **비유**: 소프트웨어 패키지 저장소(npm, PyPI)처럼 모델을 등록·조회·배포하는 체계임

| 출제 의도 | 반드시 짚을 핵심 | 감점 회피 포인트 |
|:---|:---|:---|
| 모델 거버넌스·배포 추적 방안 | 스테이지 전이(Staging→Production) | 단순 파일 저장소와 혼동 주의 |

> 요약: 모델 버전·스테이지·메타데이터를 중앙 관리하여 배포 거버넌스를 확보하는 저장소임

## Ⅱ. 구성요소
```text
Experiment Tracking(255) --> Model Registry --> Serving
                                  |
                    +-------------+-------------+
                    |             |             |
                 Version     Stage Mgmt    Metadata
                 Control    (Dev/Stg/Prd)   Store
```

| 구성요소 | 설명 | 비유 |
|:---|:---|:---|
| Version Control | 모델 아티팩트·가중치 파일의 버전별 스냅샷 관리 | 소스코드 Git 커밋 |
| Stage Management | None→Staging→Production 단계 전이 승인 관리 | 소프트웨어 릴리스 게이트 |
| Metadata Store | 학습 파라미터·데이터셋·성능 지표 등 부가 정보 저장 | 제품 성적서 |
| API/UI | 모델 검색·비교·배포 트리거 인터페이스 제공 | 패키지 매니저 CLI |

> 요약: 버전 관리·스테이지 전이·메타데이터 저장·API로 구성됨

## Ⅲ. 절차
```text
Register Model --> Review + Approve --> Promote Stage --> Deploy + Rollback
```
- 1단계: 모델 등록 — 학습 완료 모델을 아티팩트·메타데이터와 함께 등록
- 2단계: 리뷰·승인 — 성능 지표·공정성 검증 결과 기반 승인 게이트 통과
- 3단계: 스테이지 승격 — Staging 환경 테스트 후 Production으로 전이
- 4단계: 배포·롤백 — 서빙 인프라에 배포, 문제 발생 시 이전 버전 즉시 복원

> 요약: 등록 → 승인 → 승격 → 배포/롤백의 4단계로 모델 생명주기를 관리함

## Ⅳ. 문제점
- 대용량 아티팩트 관리: 모델 파일 크기(수 GB~수백 GB)로 저장·전송 비용이 증가함
- 스테이지 기준 부재: 승격 판단 기준이 명문화되지 않으면 수동 승인에 의존하게 됨
- 리니지 단절: 모델-데이터-코드 간 연결 정보가 누락되면 재현·감사가 불가함

> 요약: 아티팩트 크기·승격 기준·리니지 세 측면에서 거버넌스 한계가 존재함

## Ⅴ. 개선방안
1. 단기: 오브젝트 스토리지 연동·중복 제거로 대용량 아티팩트 저장 비용 절감
2. 중기: 정량 성능 임곗값 기반 자동 승격 정책 정의·적용
3. 장기: Experiment Tracking(255 참조)·Feature Store(253 참조)와 리니지 통합

> 요약: 스토리지 최적화·자동 승격·리니지 통합으로 거버넌스를 강화함

## Ⅵ. 전망
- 발전 방향: LLM 어댑터(LoRA 등) 관리까지 레지스트리 범위가 확장되는 추세임
- 기술사적 판단: 규제 산업(금융·의료)에서 모델 감사 추적성 확보의 핵심 인프라임
- 기술사 제언: CI/CD 파이프라인과 레지스트리 승격을 연동하는 자동화 설계가 필요함
