# 📖 【암기용】 개념 완전 이해

> 목적: 모델 레지스트리를 처음 보는 사람도 완벽히 이해하게 만든다. 시험 답안 양식이 아니라, 이해를 위한 친절한 설명이다.

## 한눈에
- **개요**: 모델 레지스트리는 학습된 모델의 버전, 메타데이터, 평가 지표, 승인 상태, 배포 이력을 관리하는 저장소다.
- **왜 필요한가**: 운영 중인 모델이 어떤 데이터와 코드로 학습됐는지 모르면 장애 분석, 롤백, 감사 대응이 어렵다.
- **핵심 직관**: 모델 파일 창고가 아니라 제품 출하 전 품질 검사표와 승인 도장을 함께 보관하는 모델 관리대장이다.

## 깊이 이해
- **배경·문제의식**: ML 모델은 같은 알고리즘이라도 데이터 버전, 하이퍼파라미터, 피처 정의에 따라 결과가 달라진다. 운영 배포에는 승인된 모델만 사용해야 한다.
- **작동 원리**: 학습 완료 모델을 artifact와 메타데이터로 등록하고, Staging에서 검증한 뒤 Production 단계로 승격한다. 문제 발생 시 이전 Production 버전으로 롤백한다.
- **비유**: 의약품 제조번호, 성분표, 시험 성적서, 출하 승인 이력을 보관하는 시스템과 같다.
- **구체 예시**: `fraud-model v23`은 데이터 스냅샷 2026-06-01, F1 0.86, p95 40ms, 승인자, 배포 시각을 함께 가진다.
- **흔한 오해·주의점**: 단순 객체 저장소에 모델 파일만 두는 것은 레지스트리가 아니다. 승인 상태, 계보, 배포 대상, 폐기 정책이 함께 있어야 한다.

## 연결 개념
- 실험 추적: 모델 후보의 학습 Run과 지표 관리
- MLOps 파이프라인: 평가 통과 모델의 승인 배포 연결
- 모델 거버넌스: 감사, 책임자, 규제 대응

# 📝 【답안용】 시험 답안 템플릿

> 목적: 시험장에서 25분에 그대로 쓰는 답안 양식. 작성방식(추상표현 금지·수치·도식·문제유형 전환)을 엄격히 지킨다.
> 핵심: 모델 레지스트리 답안은 버전 저장보다 승인 단계, lineage, 롤백, 감사 증적을 중심으로 구성해야 한다.

## 핵심 인사이트 (3줄 요약)

> 1. **본질**: 모델 레지스트리는 모델 아티팩트와 메타데이터를 버전별로 관리하고 배포 단계 전환을 통제하는 저장소다.
> 2. **가치**: 어떤 모델이 어떤 데이터, 코드, 지표, 승인으로 운영됐는지 추적해 장애 분석과 감사 대응 시간을 줄인다.
> 3. **판단 포인트**: Staging, Production, Archived 단계와 승인자, 지표 기준, 롤백 절차를 함께 설계해야 한다.

## 출제 의도 및 답안 포인트

| 출제 의도 | 반드시 짚을 핵심 | 감점 회피 포인트 |
|:---|:---|:---|
| 모델 운영 통제 이해 | 버전, 메타데이터, stage, 승인 | 파일 저장소와 혼동 |
| 배포·롤백 판단 확인 | Production 승격, rollback, audit trail | 배포 자동화만 설명 |
| 거버넌스 확인 | lineage, 책임자, 폐기 정책 | 평가 지표와 승인 기준 누락 |

> 요약: 모델 레지스트리는 운영 모델의 품질 게이트와 감사 추적을 담당하는 통제 지점이다.

---

## Ⅰ. 개요 및 필요성

모델 레지스트리는 ML 모델 버전 관리 저장소다. 운영 모델은 데이터, 코드, 피처, 파라미터, 지표가 함께 추적되어야 재현과 롤백이 가능하다. 모델 승인과 배포 이력을 관리해 운영 리스크를 줄인다.

---

## Ⅱ. 구조 및 구성요소

```text
Training Run -> Model Artifact -> Metadata -> Registry Stage -> Deployment Target -> Audit Log
                         / Evaluation Metrics
                         / Approval Workflow
```

| 구성요소 | 역할 | 통제 기준 |
|:---|:---|:---|
| Model Artifact | 모델 파일, 서빙 이미지 저장 | pickle, ONNX, Docker image |
| Metadata | 데이터 버전, 코드 SHA, 파라미터 기록 | lineage 완전성 |
| Stage 관리 | Staging, Production, Archived 단계 전환 | 승인자, 변경 사유 |
| Audit Log | 등록, 승인, 배포, 폐기 이력 | 변경 불변 로그 |

> 요약: 모델 레지스트리는 모델 산출물과 승인 상태를 묶어 운영 배포 가능한 버전을 식별한다.

---

## Ⅲ. 동작원리 및 흐름도

```text
학습 완료 -> 모델 등록 -> 지표 검증 -> 승인 요청 -> Production 승격 -> 서빙 배포 -> 이력 보존
```

| 단계 | 처리 내용 | 검증 기준 |
|:---:|:---|:---|
| 1 | 학습 Run에서 모델과 메타데이터 등록 | 코드 SHA, 데이터 버전 |
| 2 | 평가 지표와 서빙 테스트 확인 | F1, RMSE, p95 지연 |
| 3 | 승인자가 Stage 전환 | 2인 승인, 변경 사유 |
| 4 | 배포 시스템이 Production 버전 조회 | 배포 성공률, 롤백 가능성 |

> 요약: 모델 레지스트리는 학습 결과를 운영 배포 전 승인 가능한 상태로 만들고 배포 시스템의 단일 참조점이 된다.

## Ⅳ. 특징

| 구분 | 객체 저장소 | 모델 레지스트리 | 판단 포인트 |
|:---|:---|:---|:---|
| 관리 대상 | 파일 위치 | 모델, 메타데이터, Stage | 운영 버전 식별 |
| 변경 통제 | 수동 덮어쓰기 위험 | 승인 기반 승격 | 감사 로그 |

> 요약: 모델 레지스트리는 파일 보관을 넘어 승인·배포·롤백 상태를 관리한다.

## Ⅴ. 심화 비교 및 적용 판단

| 비교 축 | 기존/대안 | 모델 레지스트리 | 선택 기준 |
|:---|:---|:---|:---|
| 구조 | S3 경로와 문서 관리 | Registry API와 Stage | 운영 모델 2개 이상 |
| 비용/성능 | 관리 비용 낮음 | 메타데이터와 승인 워크플로 추가 | 감사·재현 요구 존재 |
| 운영/위험 | 잘못된 모델 배포 위험 | 승인 버전만 배포 | 업무 영향 모델 |

> 요약: 운영 배포와 감사 책임이 있는 모델은 레지스트리를 적용하고, 분석용 모델은 실험 추적부터 적용한다.

| 리스크 | 원인 | 대응 방안 | 확인 지표 |
|:---|:---|:---|:---|
| 잘못된 모델 승격 | 지표 기준 미정의 | 승격 조건 자동 검사 | 승인 실패 사유 |
| 계보 누락 | 데이터·코드 버전 미기록 | 필수 메타데이터 스키마 | lineage completeness |
| 롤백 실패 | 이미지와 모델 버전 불일치 | 모델+서빙 이미지 매핑 | 롤백 성공 시간 |

> 요약: 레지스트리 리스크는 승격 기준, 계보, 배포 매핑이며 필수 메타데이터와 자동 검사로 줄인다.

| 점검 항목 | 목표 기준 | 측정 방법 |
|:---|:---|:---|
| 메타데이터 완전성 | 필수 필드 100% | Registry validation |
| 승인 통제 | Production 2인 승인 | 감사 로그 |
| 롤백 | 이전 버전 전환 10분 이하 | 배포 리허설 |

> 요약: 모델 레지스트리 품질은 메타데이터 완전성, 승인 통제, 롤백 시간으로 평가한다.

---

## Ⅵ. 실무 적용 및 결론

**적용 방안 3개:**
1. MLflow Model Registry 또는 SageMaker Model Registry에 모델 파일, 데이터 버전, 코드 SHA, 평가지표를 필수 등록함
2. Staging에서 F1 0.85 이상, p95 100ms 이하, 편향 점검 통과 시 Production 승격을 허용함
3. 배포 시스템은 Registry Production alias만 참조하고 이전 alias로 10분 이하 롤백 절차를 검증함

**결론 (2줄):**
- 기술사 판단: 운영 의사결정 모델은 레지스트리 기반 승인 배포를 적용하고, 실험 모델은 아티팩트와 메타데이터 기록부터 적용함
- 향후 방향: 모델 레지스트리는 SBOM, AI 감사, 정책 기반 배포와 연결되어 모델 공급망 관리로 확장됨
