# 📖 【암기용】 개념 완전 이해

> 목적: 모델 레지스트리를 처음 보는 사람도 완벽히 이해하게 만든다. 시험 답안 양식이 아니라, 이해를 위한 친절한 설명이다.

## 한눈에
- **개요**: 모델 레지스트리는 학습된 모델의 **버전 관리**와 메타데이터를 다루며, **배포 단계(Stage)** 전환을 통제하는 MLOps 모델 관리 저장소다.
- **왜 필요한가**: 운영 중인 모델이 어떤 데이터 버전과 코드로 학습됐는지, 누가 배포를 승인했는지 모르면 장애 원인 분석, 롤백, 감사 대응이 모두 막힌다.
- **핵심 직관**: 모델 파일 창고가 아니라 제품 출하 전 성분표·시험 성적서·출하 승인 도장을 함께 보관하는 모델 관리대장이다.

## 핵심 용어 정리 (내부에 등장하는 것들)

| 용어 | 의미 | 비유 |
|:---|:---|:---|
| 모델 버전 관리 (상위 개념) | 학습마다 달라지는 모델 산출물을 구분해 추적하는 것 — 레지스트리가 다루는 대상 | 문서 버전 이력 |
| Model Artifact | 학습이 끝난 모델 파일 자체(가중치, 직렬화 객체, 서빙 이미지) | 완성된 제품 |
| Stage(Staging/Production/Archived) | 모델이 검증 → 운영 → 폐기로 이동하는 배포 단계 | 신입 → 정직원 → 퇴사 단계 |
| Metadata(lineage) | 이 모델이 어떤 데이터 버전·코드 커밋·피처로 학습됐는지 추적 정보 | 제품 원료 이력서 |
| Approval Workflow(승인 워크플로) | Stage 전환 전 사람이 지표를 확인하고 승인하는 절차 | 결재 라인 |
| Rollback(롤백) | 문제가 생긴 신규 모델을 이전 Production 버전으로 되돌리는 것 | 이전 버전 소프트웨어로 복구 |
| Audit Log(감사 로그) | 등록·승인·배포·폐기 이력을 변경 불가능하게 남긴 기록 | 항해 일지 |

## 깊이 이해

### 왜 단순 파일 저장소로는 부족한가
S3에 `model_v23.pkl`을 올려두는 것만으로는 이 모델이 어떤 데이터로, 어떤 하이퍼파라미터로 학습됐는지, 누가 운영 배포를 승인했는지 알 수 없다. "어제 배포된 모델이 왜 이상 동작하나"를 조사하려면 데이터 버전, 코드 SHA, 평가지표, 승인자가 함께 있어야 한다. 예: `fraud-model v23`이 데이터 스냅샷 2026-06-01, 코드 커밋 a1b2c3, F1 0.86, p95 40ms, 승인자 홍길동, 배포시각 2026-06-02 09:00으로 등록되어 있으면, 장애 시 직전 버전 v22와 지표·데이터 차이를 즉시 비교할 수 있다.

### Stage 전환 — 승격과 롤백의 구체적 동작
모델은 보통 세 단계를 거친다. ① None(등록만 됨) → ② Staging(검증 환경 배포, 성능·부하 테스트) → ③ Production(실 트래픽 서빙). 예: F1 0.85 이상, p95 지연 100ms 이하, 편향 검사 통과라는 기준을 Staging에서 만족해야 Production으로 승격된다. 문제가 생기면 "production"이라는 alias(별칭)가 가리키는 버전을 v23에서 v22로 즉시 재지정하는 것이 롤백이며, 목표는 10분 이내 완료다. alias 방식을 쓰면 배포 시스템 코드를 바꾸지 않고도 즉시 롤백된다.

### 판별 기준 — 언제 레지스트리가 필요한가
운영 배포되는 모델이 1개뿐이고 재현성 요구가 없다면 폴더 관리로도 버틸 수 있다. 그러나 (1) 운영 모델이 2개 이상이거나, (2) 규제·감사 대응이 필요하거나(예: 금융권 모델 설명 의무), (3) 잘못된 모델 배포 시 피해가 크다면 승인 기반 레지스트리가 필요하다.

### 실험 추적과의 관계
학습 단계에서 여러 후보를 비교하는 것은 실험 추적(255)의 역할이고, 그 중 선택된 모델이 운영 배포 자격을 얻어 등록되는 것이 모델 레지스트리의 역할이다. 즉 실험 추적의 Run들 중 하나가 레지스트리의 Model Artifact로 "승격"된다.

## 연결 개념
- 모델 버전 관리(상위 개념)
- 실험 추적(255) — 후보 모델의 학습 Run과 지표에서 레지스트리로 승격
- 카나리 모델 배포(257) — 레지스트리 Production 버전을 실제 트래픽에 단계적으로 노출

# 📝 【답안용】 시험 답안 템플릿

> 목적: 시험장에서 25분에 그대로 쓰는 답안 양식. 작성방식(추상표현 금지·수치·도식·문제유형 전환)을 엄격히 지킨다.

## 핵심 인사이트 (3줄 요약)

> 1. **본질**: 모델 레지스트리는 모델 아티팩트와 메타데이터를 버전별로 관리하고 배포 단계 전환을 통제하는 저장소다.
> 2. **가치**: 어떤 모델이 어떤 데이터, 코드, 지표, 승인으로 운영됐는지 추적해 장애 분석과 감사 대응 시간을 줄인다.
> 3. **판단 포인트**: Staging, Production, Archived 단계와 승인자, 지표 기준, 롤백 절차를 함께 설계해야 한다.

| 출제 의도 | 반드시 짚을 핵심 | 감점 회피 포인트 |

> 요약: 모델 레지스트리는 운영 모델의 품질 게이트와 감사 추적을 담당하는 통제 지점이다.

## Ⅰ. 개요 및 필요성

- 개요: 모델 레지스트리는 ML 모델 버전 관리 저장소다.
- 배경: 운영 모델은 데이터, 코드, 피처, 파라미터, 지표가 함께 추적되어야 재현과 롤백이 가능하다.
- 필요성: 모델 승인, stage 전환, 배포 이력을 관리해 재현·롤백 기준을 확보해야 한다.

---

## Ⅱ. 구조 및 구성요소

```text
Training Run -> Model Artifact -> Metadata -> Registry Stage -> Deployment Target -> Audit Log
                         / Evaluation Metrics
                         / Approval Workflow
```

| 구성요소 | 역할 | 통제 기준 |
|:---|:---|:---|
| Model Artifact | 모델 파일, 서빙 이미지 저장 | pickle, ONNX, Docker image |
| Metadata | 데이터 버전, 코드 SHA, 파라미터 기록 | lineage 완전성 |
| Stage 관리 | Staging, Production, Archived 단계 전환 | 승인자, 변경 사유 |
| Audit Log | 등록, 승인, 배포, 폐기 이력 | 변경 불변 로그 |

> 요약: 모델 레지스트리는 모델 산출물과 승인 상태를 묶어 운영 배포 가능한 버전을 식별한다.

---

## Ⅲ. 동작원리 및 흐름도

```text
학습 완료 -> 모델 등록 -> 지표 검증 -> 승인 요청 -> Production 승격 -> 서빙 배포 -> 이력 보존
```

| 단계 | 처리 내용 | 검증 기준 |
|:---:|:---|:---|
| 1 | 학습 Run에서 모델과 메타데이터 등록 | 코드 SHA, 데이터 버전 |
| 2 | 평가 지표와 서빙 테스트 확인 | F1, RMSE, p95 지연 |
| 3 | 승인자가 Stage 전환 | 2인 승인, 변경 사유 |
| 4 | 배포 시스템이 Production 버전 조회 | 배포 성공률, 롤백 가능성 |

> 요약: 모델 레지스트리는 학습 결과를 운영 배포 전 승인 가능한 상태로 만들고 배포 시스템의 단일 참조점이 된다.

## Ⅴ. 심화 비교 및 적용 판단

| 비교 축 | 기존/대안 | 모델 레지스트리 | 선택 기준 |
|:---|:---|:---|:---|
| 구조 | S3 경로와 문서 관리 | Registry API와 Stage | 운영 모델 2개 이상 |
| 비용/성능 | 관리 비용 낮음 | 메타데이터와 승인 워크플로 추가 | 감사·재현 요구 존재 |
| 운영/위험 | 잘못된 모델 배포 위험 | 승인 버전만 배포 | 업무 영향 모델 |

> 요약: 운영 배포와 감사 책임이 있는 모델은 레지스트리를 적용하고, 분석용 모델은 실험 추적부터 적용한다.

| 리스크 | 원인 | 대응 방안 | 확인 지표 |
|:---|:---|:---|:---|
| 잘못된 모델 승격 | 지표 기준 미정의 | 승격 조건 자동 검사 | 승인 실패 사유 |
| 계보 누락 | 데이터·코드 버전 미기록 | 필수 메타데이터 스키마 | lineage completeness |
| 롤백 실패 | 이미지와 모델 버전 불일치 | 모델+서빙 이미지 매핑 | 롤백 성공 시간 |

> 요약: 레지스트리 리스크는 승격 기준, 계보, 배포 매핑이며 필수 메타데이터와 자동 검사로 줄인다.

| 점검 항목 | 목표 기준 | 측정 방법 |
|:---|:---|:---|
| 메타데이터 완전성 | 필수 필드 100% | Registry validation |
| 승인 통제 | Production 2인 승인 | 감사 로그 |
| 롤백 | 이전 버전 전환 10분 이하 | 배포 리허설 |

> 요약: 모델 레지스트리 품질은 메타데이터 완전성, 승인 통제, 롤백 시간으로 평가한다.

## Ⅵ. 실무 적용 및 결론

**적용 방안 3개:**
1. MLflow Model Registry 또는 SageMaker Model Registry에 모델 파일, 데이터 버전, 코드 SHA, 평가지표를 필수 등록함
2. Staging에서 F1 0.85 이상, p95 100ms 이하, 편향 점검 통과 시 Production 승격을 허용함
3. 배포 시스템은 Registry Production alias만 참조하고 이전 alias로 10분 이하 롤백 절차를 검증함

**결론 (2줄):**
- 기술사 판단: 운영 의사결정 모델은 레지스트리 기반 승인 배포를 적용하고, 실험 모델은 아티팩트와 메타데이터 기록부터 적용함
- 향후 방향: 모델 레지스트리는 SBOM, AI 감사, 정책 기반 배포와 연결되어 모델 공급망 관리로 확장됨
