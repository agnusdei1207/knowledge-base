# 📖 【암기용】 개념 완전 이해

## 한눈에
- **개요**: 데이터베이스에서 데이터를 조작하는 논리적 작업의 한 단위(트랜잭션)가 무조건 지켜야 하는 4가지 핵심 성질(원자성, 일관성, 고립성, 지속성)
- **왜 필요한가**: A계좌에서 돈을 빼고 B계좌에 넣는 도중에 서버가 다운되면 돈이 증발한다. 시스템 오류나 동시 접근 속에서도 데이터를 완벽하게 보호하기 위한 철칙이다.
- **핵심 직관**: "전부 다 성공(Commit)하거나, 아예 아무 일도 없었던 것처럼 되돌리거나(Rollback)." 어중간한 상태는 절대 허용하지 않는다.

## 핵심 용어 정리

| 용어/표기 | 의미 | 비유·예 |
|:---|:---|:---|
| 트랜잭션 (Transaction) | 쪼갤 수 없는 하나의 논리적 작업 단위 | 계좌이체 (출금+입금 세트) |
| 원자성 (Atomicity) | All or Nothing. 모두 성공하거나 모두 실패해야 함 | 출금만 되고 입금이 안 되면 전체 취소 |
| 일관성 (Consistency) | 트랜잭션 전후에 DB의 제약조건(규칙)이 유지됨 | 잔고는 마이너스가 될 수 없다는 규칙 유지 |
| 고립성 (Isolation) | 다른 트랜잭션이 작업 중간에 끼어들거나 볼 수 없음 | 송금 중에 다른 사람이 잔고 조회 시 이전 금액만 보임 |
| 지속성 (Durability) | 한 번 성공(Commit)한 데이터는 영원히 보존됨 | DB 서버 전원 코드를 뽑아도 송금 기록은 남음 |

## 깊이 이해
- **배경·문제의식**: 수많은 사용자가 동시에 데이터를 읽고 쓰고 시스템이 언제 다운될지 모르는 환경에서, 데이터베이스가 스스로 데이터의 신뢰성을 보장해야만 애플리케이션 개발자가 안심하고 코드를 짤 수 있다.
- **작동 원리 (DB는 어떻게 ACID를 지키는가)**:
  - **A (원자성)**: Undo Log를 활용해 실패 시 과거 상태로 Rollback.
  - **C (일관성)**: 무결성 제약조건(PK, FK, Check 등)을 위반하면 트랜잭션 거부.
  - **I (고립성)**: Lock(잠금)과 MVCC(다중 버전 동시성 제어) 기법으로 트랜잭션 간 간섭 차단.
  - **D (지속성)**: Redo Log를 디스크에 먼저 기록(WAL: Write-Ahead Logging)하여 장애 발생 시 복구.
- **비유**: 결혼식(트랜잭션)과 같다. "신랑 신부 모두 서약해야(A) 부부로 인정(C)되며, 중간에 방해받지 않고(I), 한 번 부부가 되면 혼인신고서에 영구 기록(D)된다."
- **흔한 오해·주의점**: 고립성(I)을 100% 지키면(완전 직렬화) 동시 처리가 안 돼서 DB가 엄청나게 느려진다. 그래서 현실의 DB는 고립성을 조금 포기하고 속도를 챙기는 '트랜잭션 격리 수준(Isolation Level)' 타협안을 둔다. (096 키워드로 연계)

## 연결 개념
- **트랜잭션 격리 수준 (Isolation Levels)**: 고립성(I)과 동시성 성능 간의 트랜잭트 오프 (096 키워드)
- **MVCC**: 고립성을 지키면서도 Lock 없이 동시성을 높이는 기술 (098 키워드)

# 📝 【답안용】 시험 답안 템플릿

## 핵심 인사이트 (3줄 요약)

> 1. **본질**: 트랜잭션 ACID는 논리적 작업 단위가 데이터 정합성을 보장하기 위해 반드시 충족해야 하는 원자성, 일관성, 고립성, 지속성 4대 속성이다.
> 2. **가치**: 동시성 제어와 장애 복구 메커니즘을 DB 엔진이 책임짐으로써, 데이터의 무결성을 지키고 치명적인 논리 오류를 방지한다.
> 3. **판단 포인트**: 완전한 ACID는 성능(동시성)과 트레이드오프 관계에 있으므로, 실무에서는 격리 수준 조절 및 BASE(최종 일관성) 아키텍처와의 선택 판단이 필요하다.

## 출제 의도 및 답안 포인트

| 출제 의도 | 반드시 짚을 핵심 | 감점 회피 포인트 |
|:---|:---|:---|
| 트랜잭션 4대 특성의 개념 및 구현 메커니즘 매핑 | ACID 속성 각각의 정의 + 이를 구현하는 DB 엔진의 기술 요소(Undo, Redo, Lock) | 속성 이름만 나열하고 구현 원리 누락 |
| 장애 복구와 병행 제어 관점 이해 | WAL(Write-Ahead Logging), MVCC 메커니즘 언급 | 일반적이고 추상적인 서술 |

> 요약: ACID 속성을 단답형으로 외우는 것을 넘어, DBMS가 이를 어떻게 물리적으로 보장(Log, Lock 등)하는지 메커니즘을 매핑해야 한다.

---

## Ⅰ. 개요 및 필요성

- 개요: 트랜잭션 ACID는 데이터베이스 내에서 수행되는 논리적 작업 단위(Transaction)가 무결성을 유지하기 위해 갖춰야 할 4가지 본질적 속성임
- 배경: 다중 사용자 환경의 동시 접근과 시스템 장애(Crash) 상황에서 데이터의 손실 및 부정합 발생 위험 존재
- 필요성: 시스템 오류 시에도 복구(Recovery)를 보장하고, 병행 처리(Concurrency) 시 데이터 간섭을 통제하여 100% 신뢰할 수 있는 데이터 정합성 확보 필수

---

## Ⅱ. 구조 및 구성요소 (ACID 속성)

```text
Transaction Request -> [ A ] All or Nothing (원자성)
                    -> [ C ] Constraints Check (일관성) 
                    -> [ I ] Concurrency Control (고립성)
                    -> [ D ] Logging to Disk (지속성) -> Commit / Rollback
```

| 속성 | 개념 | DB 보장 메커니즘 |
|:---|:---|:---|
| 원자성 (Atomicity) | 트랜잭션 내의 모든 연산은 100% 성공하거나 100% 실패해야 함 | Commit / Rollback, Undo Log |
| 일관성 (Consistency) | 트랜잭션 실행 전후 데이터베이스 무결성 제약조건은 유지됨 | 무결성 제약조건, 트리거 검증 |
| 고립성 (Isolation) | 실행 중인 트랜잭션 결과는 완료 전까지 타 트랜잭션이 참조 불가 | 2PL (Lock), MVCC (다중 버전) |
| 지속성 (Durability) | 성공적으로 완료(Commit)된 결과는 시스템 장애 시에도 영구 보존 | Redo Log, WAL(Write-Ahead Logging) |

> 요약: ACID는 논리적 속성일 뿐만 아니라, DBMS 내부의 복구 관리자와 병행 제어 관리자가 Undo/Redo/Lock을 통해 물리적으로 강제하는 규칙이다.

---

## Ⅲ. 동작원리 및 흐름도

```text
Begin -> 연산/변경(Memory) & WAL 기록 -> 제약조건/Lock 검증 -> Commit -> 디스크 영구 반영(Redo)
   |                                                   +-> (장애/오류 시) -> Undo Log로 Rollback
```

- 1단계 [트랜잭션 시작 및 갱신]: 데이터를 변경할 때 즉시 디스크의 데이터 파일을 수정하지 않고 메모리(Buffer) 갱신 및 로그 버퍼에 기록
- 2단계 [고립성·일관성 통제]: 갱신 데이터에 Lock을 걸어 타 트랜잭션 접근을 막고, 무결성 제약(일관성) 위반 검사
- 3단계 [지속성 로그 기록 (WAL)]: Commit 요청 시, 실제 데이터 파일보다 먼저 Redo Log(복구 정보)를 디스크에 강제 저장
- 4단계 [Commit/Rollback 완료]: 성공 시 영구 반영을 확정(Commit)하고 Lock 해제, 실패나 오류 시 Undo Log를 사용해 원상 복구(Rollback)

> 요약: 변경 사항을 로그(WAL)로 먼저 안전하게 남기고 메모리상에서 제약을 검증한 뒤 일괄 반영하는 방식으로 ACID를 달성한다.

---

## Ⅳ. 특징

- 상호 보완적: 원자성과 고립성이 확보되어야 일관성이 유지되고, 지속성이 바탕이 되어야 트랜잭션의 결과가 신뢰됨
- 성능 트레이드오프: 고립성(I)을 엄격히 보장하는 직렬화(Serializable) 방식은 대기(Lock)로 인해 동시성(성능)을 심각하게 저하시킴
- NoSQL 환경의 한계: 분산 노드 환경에서는 ACID를 완벽히 보장하기 어려워 CAP 정리 상 가용성을 택하고 BASE(최종 일관성) 모델을 대안으로 사용

## Ⅴ. 심화 비교 및 적용 판단

| 비교 축 | ACID (RDBMS) | BASE (NoSQL) | 선택 기준 |
|:---|:---|:---|:---|
| 데이터 정합성 | 강한 일관성 (Strong Consistency) | 최종 일관성 (Eventual Consistency) | 비즈니스 정합성 중요도 |
| 확장성 | 단일 노드 스케일업 중심 (제한적 분산) | 다중 노드 수평 확장 (Scale-Out) 용이 | 데이터 분산 규모 |
| 적용 도메인 | 금융, 결제, 재고 관리 시스템 | 로그 수집, 추천 시스템, SNS 피드 | 가용성(성능) 우선 여부 |

> 요약: 결제 시스템처럼 한 치의 오차도 허용 불가한 경우 ACID를, SNS 피드처럼 약간의 지연 표시가 허용되는 대용량 시스템은 BASE를 선택한다.

**리스크·대응 (기본은 불릿):**
- 성능 병목(Lock 경합): 엄격한 고립성 보장 시 데드락(Deadlock) 및 대기 시간 급증 → 비관적 락 대신 낙관적 락 또는 MVCC 기반 격리 수준(Read Committed 이하) 적용
- 디스크 I/O 오버헤드: 지속성(D)을 위한 빈번한 동기적 로그 디스크 기록(fsync) 병목 → Group Commit 방식 적용 및 SSD NVMe 기반 로그 볼륨 분리

## Ⅵ. 실무 적용 및 결론

**적용 방안 3개:**
1. 적절한 격리 수준 설정: 시스템 요구사항에 맞춰 고립성을 타협하여 MySQL의 기본인 Repeatable Read 또는 Oracle의 Read Committed로 격리 수준 하향 설정
2. 트랜잭션 범위 최소화: 네트워크 I/O(외부 API 호출)나 대용량 파일 처리 작업을 트랜잭션 범위 밖으로 분리하여 DB Connection Lock 점유 시간 단축
3. 분산 트랜잭션 대응 (MSA): 마이크로서비스 환경에서는 단일 DB의 ACID 적용이 불가능하므로, Saga 패턴이나 2PC(2 Phase Commit) 기반의 보상 트랜잭션 설계 도입

**결론 (2줄):**
- 기술사 판단: ACID는 데이터베이스 신뢰성의 근간이지만, 성능과의 상충 관계를 고려해 MVCC와 격리 수준(Isolation Level)을 통해 동시성과 정합성의 최적점을 찾아야 한다
- 향후 방향: 클라우드 분산 환경에서도 강한 일관성(ACID)과 확장성을 동시에 제공하려는 Spanner, TiDB 등 NewSQL 패러다임이 부상하고 있다
