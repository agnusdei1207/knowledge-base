## 핵심 인사이트 (3줄 요약)
- **트랜잭션(Transaction)**: 데이터베이스의 상태를 변화시키는 하나의 "논리적 작업 단위(Unit of Work)". (예: 은행 계좌 이체).
- 이 작업 단위가 안전하게 처리되기 위해 DB가 반드시 보장해야 하는 4가지 불가침의 룰이 바로 **ACID (원자성, 일관성, 격리성, 영속성)**임.
- MSA(마이크로서비스) 환경에서 DB가 여러 개로 찢어지면 이 완벽한 ACID를 유지하는 것이 불가능해지며, 이를 해결하기 위해 사가(Saga) 패턴 등 복잡한 분산 트랜잭션 기술이 도입됨.

## Ⅰ. 개요 및 필요성
- **개요**: 트랜잭션의 안전한 수행을 보장하기 위한 4가지 핵심 특성(Atomicity, Consistency, Isolation, Durability).
- **필요성**: A계좌에서 1만 원을 빼고 B계좌에 1만 원을 더하는 과정(계좌 이체) 중, 시스템 전원이 꺼지면 A 돈만 날아가는 대형 사고가 발생함. 여러 개의 SQL 쿼리문들을 '하나의 묶음'으로 처리하여, 모두 성공하거나 모두 실패하게 만들 거대한 방어막이 필요했음.
---
## Ⅱ. 아키텍처 및 핵심 원리
- **ACID의 4대 속성**:
  1. **원자성 (Atomicity / All or Nothing)**: 
     - 트랜잭션 내의 모든 연산은 완벽히 수행(Commit)되거나, 전혀 수행되지 않아야(Rollback) 함. (회복 기법인 Undo Log로 보장).
  2. **일관성 (Consistency)**:
     - 트랜잭션이 성공적으로 완료되면, 언제나 데이터베이스의 무결성 제약조건(예: 잔액은 마이너스가 될 수 없음)을 만족하는 일관된 상태가 유지되어야 함.
  3. **격리성 (Isolation / 고립성)**:
     - 둘 이상의 트랜잭션이 동시에 실행될 때, 서로의 중간 연산 결과에 끼어들거나 엿볼 수 없어야 함. (동시성 제어 기법인 락(Lock)이나 MVCC로 보장).
  4. **영속성 (Durability / 지속성)**:
     - 한 번 성공(Commit)한 트랜잭션의 결과는 DB 서버가 폭발하고 정전이 나더라도 영원히 DB에 기록되어야 함. (Redo Log로 보장).

```text
[ 계좌 이체 트랜잭션 (All or Nothing) 원리 ]

 [ 트랜잭션 시작 (BEGIN) ]
    ⬇️
 1. A 계좌 잔액 = A 잔액 - 10,000원 (UPDATE 성공)
    ⬇️ ⚡ [시스템 다운(Crash) 발생!] ⚡
 2. B 계좌 잔액 = B 계좌 + 10,000원 (수행 실패)
    ⬇️
 [ 트랜잭션 롤백 (ROLLBACK) ]
    ⬇️
 A 계좌의 -10,000원 차감 내역을 취소하고 원상복구(Atomicity 보장)
```

## Ⅲ. 비교 및 연결
| 속성 | 위반 시 문제점 (장애 현상) | DBMS의 보장 메커니즘 (해결책) |
|---|---|---|
| **Atomicity (원자성)** | 돈은 빠져나갔는데 상대방은 못 받음 | **Undo Log** (이전 상태로 롤백) |
| **Consistency (일관성)**| 잔액이 0원인데 1만 원이 더 빠져나감 | **제약조건, Trigger** (무결성 룰 검사) |
| **Isolation (격리성)** | 내가 돈을 빼는 중인데 다른 사람이 동시에 뺌 | **Lock, MVCC**, Transaction Isolation Level |
| **Durability (영속성)** | 결제 완료 떴는데 DB 서버 재부팅 후 날아감 | **Redo Log** (디스크에 영구 기록 후 Commit) |

## Ⅳ. 실무 적용 및 기술사 판단
- **격리성(Isolation)과 성능의 트레이드오프**: ACID 중에서 가장 완벽하게 지키기 힘든 것이 '격리성'임. 수만 명이 동시에 수강신청을 할 때 완벽한 격리(직렬화, Serializable)를 보장하려면 한 번에 한 명씩만 DB에 접근하도록 락(Lock)을 걸어야 하므로 시스템이 마비됨. 따라서 실무에서는 '약간의 데이터 불일치를 눈감아주는 대신 동시 처리 속도를 높이는' 격리 수준(Isolation Level) 튜닝(예: Read Committed)이 아키텍트의 핵심 역량임.
- **분산 트랜잭션 (2PC vs Saga)**: 클라우드 MSA 환경에서는 주문 DB와 결제 DB가 물리적으로 나뉨. 전통적인 2-Phase Commit(2PC)은 두 DB에 모두 락을 걸어 성능이 죽어버림. 이에 대한 대안으로, 트랜잭션을 잘게 쪼개고 실패 시 '보상 트랜잭션(환불 로직)'을 실행하여 최종적인 일관성(Eventual Consistency, BASE)을 맞추는 Saga 패턴이 표준 기술로 쓰이고 있음.

## Ⅴ. 기대효과 및 결론
- 개발자가 하드웨어 장애나 동시성 제어의 늪에 빠지지 않고, 오직 '비즈니스 로직(이체 로직)'에만 집중할 수 있도록 RDBMS가 제공하는 최고의 선물임.
- ACID 원칙 덕분에 전 세계 은행망, 주식 거래, 항공권 예약 시스템이 단 1원의 오차 없이 24시간 안전하게 돌아가고 있음.

- RDB ➡️ 트랜잭션 (ACID) ➡️ 격리 수준 (Isolation Level) / 동시성 제어 ➡️ 분산 트랜잭션 (Saga)

### 📈 관련 키워드 및 발전 흐름도
- 단일 DB 트랜잭션 (ACID) ➡️ 분산 DB 확장 ➡️ CAP 정리 (일관성과 가용성의 충돌) ➡️ BASE 속성 (NoSQL) ➡️ 분산 트랜잭션(Saga)
