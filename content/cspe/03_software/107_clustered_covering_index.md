## 미리 알고가기

- 클러스터드 인덱스는 데이터 저장 순서 자체를 인덱스 키 기준으로 정렬함
- 커버링 인덱스는 질의에 필요한 컬럼을 인덱스만으로 충족하는 구조임
- 둘 다 I/O를 줄이지만 적용 목적과 부작용이 다름

## Ⅰ. 개요

- **정의/개념**: 클러스터드 인덱스는 테이블 데이터의 물리적 또는 논리적 저장 순서를 인덱스 키 기준으로 정렬해 접근 효율을 높이는 구조이고, 커버링 인덱스는 특정 질의가 필요한 컬럼을 인덱스 내부에서 모두 얻도록 구성해 테이블 본문 접근을 줄이는 최적화 방식임
- **배경/필요성**: 범위 조회와 반복 조회가 많은 업무에서는 일반 보조 인덱스만으로 I/O를 충분히 줄이기 어려우므로, 저장 정렬과 인덱스 포함 컬럼 설계를 추가로 고려할 필요가 있음

## Ⅱ. 특징

- 클러스터드 인덱스는 범위 조회와 정렬 일치 질의에 강함
- 커버링 인덱스는 bookmark lookup을 줄여 랜덤 I/O를 낮춤
- 클러스터드 인덱스는 키 변경과 페이지 분할 비용이 민감함
- 커버링 인덱스는 포함 컬럼이 과도하면 저장 공간과 유지 비용이 증가함

## Ⅲ. 종류 및 비교

| 판단 기준 | 클러스터드 인덱스 | 커버링 인덱스 |
|:---|:---|:---|
| 핵심 목적 | 저장 순서 최적화 | 테이블 접근 제거 |
| 강점 | 범위·정렬 조회 효율 | point lookup과 짧은 조회 효율 |
| 한계 | 삽입 위치 이동과 분할 비용 | 컬럼 추가에 따른 비대화 |
| 적합 질의 | 날짜 범위·순차 조회 | 조회 컬럼이 고정된 API 질의 |

## Ⅳ. 구성요소 및 구조

| 구성요소 | 설명 |
|:---|:---|
| Clustered Key | 데이터 정렬 순서를 결정해 범위 탐색 비용에 직접 영향을 줌 |
| Leaf Page Layout | 리프 페이지가 실제 데이터나 포인터를 담아 I/O 특성을 결정함 |
| Included Column Set | 커버링 목적의 추가 컬럼이 질의 충족 범위를 넓힘 |
| Split and Maintenance Policy | 페이지 분할과 재구성 정책이 쓰기 부담을 통제함 |

## Ⅴ. 원리 및 절차 흐름도

```text
+-------------+     +-------------+     +-------------+     +-------------+
| 대표 질의 선정  | --> | 키/포함 컬럼 설계 | --> | 인덱스 생성    | --> | I/O 감소 검증   |
+-------------+     +-------------+     +-------------+     +-------------+
```

1. **대표 질의 선정**: 범위 조회와 반복 조회 질의를 고름
2. **키와 포함 컬럼 설계**: 정렬 키와 필요한 조회 컬럼을 정함
3. **인덱스 생성**: 저장 구조와 포함 컬럼을 반영함
4. **I/O 감소 검증**: lookup 감소와 분할 비용을 확인함

## Ⅵ. 문제점 및 해결 방안

1. 문제: 변동이 잦은 컬럼을 클러스터드 키로 선택하면 페이지 분할과 재정렬 비용이 급증할 수 있음
   - 해결방안: stable monotonic key를 우선 선택하고 page split rate와 fragmentation ratio로 검증함
2. 문제: 커버링 인덱스에 너무 많은 컬럼을 넣으면 조회 이득보다 메모리와 쓰기 비용이 더 커질 수 있음
   - 해결방안: frequently selected column만 포함하고 index size growth와 lookup elimination ratio로 검증함
3. 문제: 대표 질의가 바뀌었는데 인덱스 구성을 그대로 두면 과거 최적화가 현재 병목이 될 수 있음
   - 해결방안: query portfolio review를 운영하고 unused covering index count와 critical query latency로 검증함

## Ⅶ. 적용 사례

- 시계열 주문 조회 DB에서는 안정적 클러스터드 키를 선택하고, page split rate와 fragmentation ratio로 결과를 확인함
- API 응답 최적화에서는 커버링 인덱스를 적용하고, index size growth와 lookup elimination ratio로 결과를 확인함
- 장기 운영 시스템에서는 질의 포트폴리오를 재검토하고, unused covering index count와 critical query latency로 결과를 확인함

## Ⅷ. 결론

클러스터드와 커버링 인덱스는 모두 I/O를 줄이지만 저장 순서 최적화와 테이블 접근 제거라는 목적 차이를 구분해 써야 효과가 유지됨.
