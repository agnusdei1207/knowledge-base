# 📖 【암기용】 개념 완전 이해

## 한눈에
- **개요**: 인덱스의 한계를 뛰어넘어, 디스크 데이터 블록 접근(랜덤 I/O) 자체를 제거하는 심화 최적화 기법이다.
- **왜 필요한가**: 일반 인덱스로 찾아도 디스크 본 데이터로 점프(Random Access)하는 과정이 대량 조회 시 치명적 병목이 되기 때문이다.
- **핵심 직관**: **클러스터드**는 단어 순으로 본문이 적힌 '영어 사전'이고, **커버링**은 요약본에 다 적혀 있어 '본문을 안 봐도 되는 메모장'이다.

## 핵심 용어 정리

| 용어/표기 | 의미 | 비유·예 |
|:---|:---|:---|
| 넌-클러스터드 (일반 인덱스) | 별도 공간에 키와 주소를 두고 데이터를 찾아가는 방식 | 책 뒤편의 찾아보기 색인 |
| 클러스터드 인덱스 | 실제 데이터 자체가 인덱스 정렬 순서대로 물리적 저장됨 | 영어 사전 본문 |
| 커버링 인덱스 | 쿼리에서 요구하는 모든 컬럼이 인덱스 안에 다 들어있는 상태 | 필요한 정보가 요약 목차에 다 있어 본문을 안 읽어도 됨 |
| 랜덤 액세스 (Random Access) | 인덱스에서 주소를 얻어 디스크 곳곳을 점프하며 읽는 물리적 부하 | 페이지 번호 15, 300을 번갈아 펴는 비효율 |

## 깊이 이해
- **배경·문제의식**: 인덱스로 20만 건을 찾았다면, 디스크 데이터 블록으로 20만 번 점프(랜덤 액세스)해야 한다. 이 부하가 너무 커 Full Scan보다 느려지는 한계가 존재한다.
- **작동 원리**: 클러스터드 인덱스는 리프 노드가 테이블 데이터 자체이므로 점프가 발생하지 않고 순차 읽기를 수행한다. 커버링 인덱스는 복합 인덱스에 출력할 컬럼까지 다 넣어두어, 인덱스만 읽고 디스크 조회를 아예 안 한다.
- **비유**: 클러스터드는 서류를 사번 순으로 아예 물리적으로 꽂아둔 것이고, 커버링은 직원의 이름/직급 질문에 캐비닛을 안 열고 내 수첩 메모만 보고 바로 답하는 것이다.
- **구체 예시**: `LIMIT 100000, 10` 같은 깊은 페이징은 느리다. 이때 날짜 인덱스로 커버링 인덱스를 타서 10만 번째 PK 10개만 인덱스상에서 구한 뒤 본 테이블과 조인하면 압도적으로 빨라진다.
- **흔한 오해·주의점**: 클러스터드 인덱스는 테이블당 1개만 생성 가능(주로 PK)하므로 신중해야 한다. 커버링 인덱스는 만능이 아니라, 무분별하게 컬럼을 추가하면 인덱스 크기 비대화로 성능이 떨어진다.

## 연결 개념
- **인덱스 구조 (B+Tree)**: 두 기법 모두 B+Tree 베이스 위에서 동작한다.
- **옵티마이저 실행계획**: 커버링 성립 시 `Index Only Scan`을 출력한다.

# 📝 【답안용】 시험 답안 템플릿

## 핵심 인사이트 (3줄 요약)

> 1. **본질**: 일반 인덱스 룩업 시 발생하는 디스크 랜덤 액세스(Random I/O) 병목을 제거하는 최적화 기법
> 2. **가치**: 클러스터드는 물리적 데이터 정렬로, 커버링은 쿼리 충족 설계로 디스크 I/O를 극단적으로 최소화
> 3. **판단 포인트**: 테이블 당 1개 제한(클러스터드)과 인덱스 비대화(커버링) 제약을 이해하고 악성 쿼리에 한정 적용

## 출제 의도 및 답안 포인트

| 출제 의도 | 반드시 짚을 핵심 | 감점 회피 포인트 |
|:---|:---|:---|
| 쿼리 성능 고도화 기법 이해 | 디스크 랜덤 액세스 제거 메커니즘 2가지(순차화 vs 접근 회피) 도식화 | 커버링 인덱스를 특정 DB 벤더의 고유 인덱스 타입으로 오해하는 서술 |

> 요약: 일반 인덱스의 치명적 약점인 디스크 점프 부하를 아키텍처와 쿼리 수준에서 각각 해결하는 전략이다.

---

## Ⅰ. 개요 및 필요성

- 개요: 디스크 랜덤 액세스를 회피하기 위해, 데이터를 물리적으로 정렬 저장(클러스터드)하거나 요구 컬럼을 인덱스에 포함(커버링)하는 기법
- 배경: 인덱스 추출 건수가 전체의 15%를 초과할 경우 랜덤 액세스 부하로 인해 Full Scan보다 응답이 느려지는 한계 봉착
- 필요성: 초대용량 데이터베이스 환경에서 디스크 I/O 횟수를 획기적으로 줄여 다량 범위 집계나 페이징 응답시간 보장

---

## Ⅱ. 구조 및 구성요소

```text
[일반 인덱스 (점프 부하)]               [클러스터드 / 커버링 (접근 최적화)]
인덱스 트리 -> 리프 (디스크 주소)         인덱스 트리 -> 리프 (데이터 자체)
                 ↓ (랜덤 I/O 발생)                       (테이블 점프 생략)
              테이블 디스크                           쿼리 즉시 반환
```

| 기법 명칭 | 구조적 특징 | 주요 역할 및 한계 |
|:---|:---|:---|
| 클러스터드 인덱스 | 데이터 자체가 인덱스의 리프 노드에 물리적 정렬 저장됨 | 넓은 범위 조회 압도적 우위, 테이블 당 1개 제한 |
| 넌-클러스터드 | 별도의 B+Tree 공간에 키와 주소(ROWID)만 저장 | 여러 개 생성 가능, 랜덤 액세스 부하 유발 |
| 커버링 인덱스 | 쿼리에서 요구하는 모든 컬럼이 인덱스 키 내에 포함된 상태 | 디스크 룩업 완전 제거, 인덱스 비대화 리스크 |

> 요약: 클러스터드는 테이블 구조 자체를 정렬하고 커버링은 인덱스에 정보를 몰아넣어 디스크 룩업을 생략한다.

---

## Ⅲ. 동작원리 및 흐름도

```text
쿼리 유입 -> 옵티마이저 평가 -> (커버링 성립 시) Index Only Scan -> 반환
                             |
                             +-> (미성립 시) 클러스터드 PK 탐색 -> 리프 레벨 스캔 후 반환
```

- 1단계 쿼리 파싱: 쿼리의 SELECT, WHERE 구문 접수
- 2단계 커버링 판별: 요구 컬럼 전체가 포함된 복합 인덱스 존재 여부를 옵티마이저가 확인
- 3단계 Index Only Scan (커버링): 판별 성공 시, 디스크 본 데이터 접근 없이 메모리 내 인덱스 블록만 읽어 결과 리턴
- 4단계 Clustered Scan (클러스터드): 커버링 미충족 시, PK 탐색 후 리프 노드의 데이터 블록을 그대로 순차(Sequential) 읽기 반환

> 요약: 디스크 본 블록 점프를 생략(커버링)하거나 순차 탐색(클러스터드)으로 물리적 I/O 패턴을 바꾼다.

---

## Ⅳ. 특징
- 디스크 I/O 최적화: 디스크 성능 최대 적혈인 랜덤 액세스를 완전히 제거하거나 시퀀셜(Sequential) I/O로 전환
- 쓰기 페널티(클러스터드): `INSERT/UPDATE` 시 물리적인 정렬 순서 유지를 위한 대량 레코드 이동(Page Split) 발생
- 크기 증가(커버링): 쿼리 튜닝을 위해 컬럼이 과도하게 추가되면 인덱스 스토리지 낭비 및 메모리 적재 효율 급감
- 페이지 락(Page Lock) 경합: 클러스터드 구조에서 물리적으로 인접한 값들이 동시 인입될 때 블록 락 경합 리스크 상승

> 요약: 읽기(Read)의 궁극적 성능을 제공하나 잦은 쓰기(Write) 발생 시 시스템을 둔화시키는 양날의 검이다.

## Ⅴ. 심화 비교 및 적용 판단

| 비교 축 | 클러스터드 인덱스 | 커버링 인덱스 | 선택 기준 |
|:---|:---|:---|:---|
| 테이블 당 개수 | 오직 1개 (물리적 정렬은 하나만) | 다수 생성 가능 (복합 조합) | 구조적 제한 |
| 최적 쿼리 패턴 | 다량의 데이터 범위(`BETWEEN`) 조회 | 전용 요약/통계 단일 쿼리 튜닝 | 요구 쿼리 성격 |
| 성능 저하 원인 | 삽입 시 데이터 물리적 이동(Split) 분산 | 갱신 시 복수 컬럼 인덱스 수정 오버헤드 | DML 패턴과 빈도 |

> 요약: 주된 범위 검색은 클러스터드(PK)로 처리하고, 이를 보완하는 악성 병목 쿼리는 커버링으로 튜닝한다.

**리스크·대응:**
- 클러스터드 키 비대화: PK 크기가 크면 이를 참조하는 모든 넌-클러스터드 인덱스 크기도 연쇄 비대화 → PK는 정수형(Auto Increment) 최소 크기로 설계 (지표: 전체 인덱스 용량)
- 커버링 컬럼 남용: 단일 쿼리만을 위한 커버링 남발 시 쓰기 과부하 → 여러 쿼리를 공통 커버할 수 있는 최소 복합 인덱스로 병합(Merge) (지표: 인덱스 중복도)

**도입 후 점검 지표:**
- 성능/효율: 실행계획 상 `Index Only Scan` 노출 여부 — 커버링 인덱스 의도적 작동 검증
- 품질/운영: 트랜잭션 갱신 시간 및 Page Split 횟수 모니터링

## Ⅵ. 실무 적용 및 결론

**적용 방안 3개:**
1. 시계열 테이블 클러스터드 설계: 등록일시 범위 조회가 잦은 로그/이력 테이블은 날짜를 PK(클러스터드)로 구성하여 시퀀셜 읽기 극대화 적용
2. 오프셋 페이징 최적화: 깊은 페이지(`LIMIT 100000, 10`) 조회 시 서브쿼리 커버링 인덱스로 PK 10개만 고속 추출한 뒤 본 테이블과 조인(Deferred Join)하는 기법 도입
3. 통계 뷰(View) 대체 용도: 통계 화면 등에서 3~4개 컬럼만 반복 조회 시 묶어서 커버링 인덱스를 생성하여 별도 배치 요약 테이블 없이 실시간 조회

**결론:**
- 기술사 판단: 클러스터드 인덱스는 데이터 아키텍처 설계의 뼈대이며 커버링은 악성 쿼리 튜닝의 마스터키다. 두 기법을 적절히 결합해 초대용량 데이터 I/O 병목을 해결해야 한다.
- 향후 방향: 컬럼 스토어 데이터베이스 발달로 특정 컬럼 묶음 스캔이 기본 제공되면서 OLAP에서는 커버링 인덱스 기능이 데이터 웨어하우스 엔진으로 흡수되는 추세다.
