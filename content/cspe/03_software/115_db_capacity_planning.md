## 미리 알고가기

- DB 용량 산정은 저장 공간만이 아니라 CPU와 메모리와 디스크 입출력까지 함께 예측하는 작업임
- TPS는 초당 트랜잭션 수이고, 피크 부하는 특정 시간대에 가장 많이 몰리는 요청 수준을 뜻함
- 인덱스와 로그와 백업과 복제본까지 포함해야 실제 필요한 자원을 계산할 수 있음

## 작성 근거(검토용)

- 제목·frontmatter·미리 알고가기·본문·표·요약·결론을 5회 전수 검수해 어색한 단어·조사·동사 결합·장황한 명사구를 교정함
- DB 용량 산정은 데이터 성장·피크 부하·운영 오버헤드를 핵심 축으로 설명함
- 비교표는 저장 용량 중심 산정과 종합 용량 산정의 고려 범위를 대비함
- 운영 DB는 용량 예측 오차율·피크 자원 사용률로 검증함

## Ⅰ. 개요

- **정의/개념**: DB 용량 산정은 데이터 증가율·트랜잭션 부하·보관 기간·복제 구조를 기준으로 저장 공간·CPU·메모리·I/O와 증설 시점을 예측하는 활동임
- **배경/필요성**: 데이터 성장과 피크 부하로 인한 자원 포화와 장애를 방지하기 위해 운영 오버헤드와 여유율을 반영한 용량 계획이 필요함

## Ⅱ. 특징

- 데이터 양과 요청 부하와 성장 속도를 함께 봐야 함
- 인덱스와 로그와 백업과 복제본을 빼면 실제 필요 자원을 과소평가하기 쉬움
- 이벤트·배치·월말 마감의 동시 요청량과 작업 시간이 CPU·I/O·lock 피크를 결정함
- 한 번 계산하고 끝내면 성장 속도 변화에 대응하지 못함

## Ⅲ. 종류 및 비교

| 판단 기준 | 저장 용량 중심 산정 | 종합 용량 산정 |
|:---|:---|:---|
| 고려 범위 | 데이터 파일 크기 위주로 계산함 | 데이터와 인덱스와 로그와 부하를 함께 계산함 |
| 산정 결과 | 데이터 파일의 개략 저장 용량 | 데이터·인덱스·로그·복제·백업 용량과 CPU·메모리·I/O 부하 |
| 한계 | 성능 병목과 복제 비용을 놓치기 쉬움 | 입력 정보 수집과 추정 과정이 더 필요함 |
| 사용 시점 | 초기 개략 추정 | 실제 인프라 계획과 증설 판단 |

> 요약: 저장 용량 중심 산정은 데이터 파일을 추정하고, 종합 용량 산정은 부하와 운영 오버헤드까지 포함함.

## Ⅳ. 구성요소 및 구조

| 구성요소 | 설명 |
|:---|:---|
| 데이터 성장 모델 | 일별 증가량과 보관 기간을 바탕으로 저장 공간 수요를 예측함 |
| 부하 프로파일 | TPS와 조회 패턴과 피크 시간대가 CPU와 입출력 요구를 결정함 |
| 오버헤드 항목 | 인덱스와 로그와 백업과 복제본을 포함해 실제 필요 자원을 보정함 |
| 증설 기준선 | 자원별 최소 여유율과 조달 시간을 반영해 증설 시점을 결정함 |

> 요약: 데이터 성장과 부하 프로파일로 자원 수요를 계산하고 운영 오버헤드와 증설 기준선으로 여유 용량을 결정함.

## Ⅴ. 원리 및 절차 흐름도

1. **성장과 부하 수집**: 데이터 증가량과 피크 트랜잭션과 조회 패턴을 측정함
2. **자원 수요 계산**: 저장 공간과 메모리와 CPU와 입출력 요구를 산정함
3. **여유율 반영**: 장애 복구와 이벤트 부하와 복제 비용까지 포함함
4. **증설 시점 설정**: 임계치를 정하고 정기적으로 다시 점검함

> 요약: 성장·피크 부하를 측정해 자원 수요를 계산하고 운영 여유율을 반영해 증설 시점을 정함.

## Ⅵ. 실무 사례

1. 거래 DB는 데이터·인덱스·로그·복제본을 포함해 산정하고 용량 예측 오차율·저장소 여유율을 확인함
2. 이벤트 DB는 피크 부하로 증설 시점을 정하고 최대 자원 사용률·잔여 여유율을 확인함

## Ⅶ. 결론

- DB 용량 산정은 데이터 성장·피크 부하·운영 오버헤드를 반영해 자원 규모와 증설 시점을 결정함
