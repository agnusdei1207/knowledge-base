## 미리 알고가기

- DB 용량 산정은 저장 공간뿐 아니라 CPU와 메모리와 I/O와 성장률까지 함께 본다
- 현재 사용량이 아니라 피크와 보관 정책과 복제본까지 포함해 계산해야 함
- 과소 산정은 장애로 이어지고 과대 산정은 비용 낭비로 이어짐

## Ⅰ. 개요

- **정의/개념**: 데이터베이스 용량 산정은 데이터 크기와 트랜잭션 부하와 성장률과 보관 기간과 복제 구조를 기준으로 저장 공간과 메모리와 CPU와 I/O 요구량을 예측해 적정 인프라와 확장 시점을 계획하는 활동임
- **배경/필요성**: 데이터베이스는 자원 부족 시 성능 저하가 곧 서비스 장애로 이어지므로, 현재 사용량이 아닌 미래 성장과 피크 부하를 고려한 용량 계획이 필요함

## Ⅱ. 특징

- 데이터량과 트래픽량과 성장률을 함께 고려함
- 인덱스와 로그와 백업과 복제본까지 포함해야 실제 규모가 보임
- 계절성 이벤트와 배치 작업이 피크 부하를 크게 바꿀 수 있음
- 정적 1회 계산으로 끝내면 서비스 성장 속도를 따라가지 못함

## Ⅲ. 종류 및 비교

| 판단 기준 | 저장 용량 중심 산정 | 종합 용량 산정 |
|:---|:---|:---|
| 고려 범위 | 데이터 파일 위주 | 데이터·인덱스·로그·부하 전체 |
| 강점 | 계산 단순 | 운영 현실 반영 |
| 한계 | 성능 병목 누락 | 입력 데이터 수집 필요 |
| 적합 상황 | 초기 러프 추정 | 실제 인프라 계획 |

## Ⅳ. 구성요소 및 구조

| 구성요소 | 설명 |
|:---|:---|
| Data Growth Model | 일별 증가량과 보관 기간을 기준으로 저장 공간 수요를 예측함 |
| Workload Profile | TPS와 QPS와 피크 패턴이 CPU와 I/O 요구를 결정함 |
| Overhead Factor | 인덱스와 로그와 백업과 복제를 포함해 실제 필요 자원을 보정함 |
| Scale Trigger | 임계치와 증설 시점을 정의해 선제 대응 근거를 마련함 |

## Ⅴ. 원리 및 절차 흐름도

```text
+-------------+     +-------------+     +-------------+     +-------------+
| 성장/부하 수집  | --> | 자원 수요 계산  | --> | 여유율 반영     | --> | 증설 시점 설정  |
+-------------+     +-------------+     +-------------+     +-------------+
```

1. **성장과 부하 수집**: 데이터 증가량과 피크 트랜잭션을 측정함
2. **자원 수요 계산**: 저장과 메모리와 CPU와 I/O를 산정함
3. **여유율 반영**: 장애와 이벤트와 복제 비용을 포함함
4. **증설 시점 설정**: 임계치를 정하고 모니터링함

## Ⅵ. 문제점 및 해결 방안

1. 문제: 순수 데이터 크기만 보고 인덱스와 로그와 복제 오버헤드를 빼면 실제 운영 시점에 용량 부족이 빨리 발생할 수 있음
   - 해결방안: full footprint model을 적용하고 storage forecast error와 overhead coverage ratio로 검증함
2. 문제: 평균 부하만 기준으로 삼으면 이벤트나 배치 피크에서 CPU와 I/O 포화가 반복될 수 있음
   - 해결방안: peak-aware sizing을 수행하고 peak resource saturation rate와 headroom ratio로 검증함
3. 문제: 산정 결과를 일회성 문서로만 남기면 성장 추세 변화에 맞춘 증설 타이밍을 놓칠 수 있음
   - 해결방안: rolling capacity review를 운영하고 capacity review cadence와 scale trigger accuracy로 검증함

## Ⅶ. 적용 사례

- 대용량 거래 DB에서는 전체 footprint 모델을 적용하고, storage forecast error와 overhead coverage ratio로 결과를 확인함
- 이벤트성 트래픽 서비스에서는 피크 기준 산정을 수행하고, peak resource saturation rate와 headroom ratio로 결과를 확인함
- 운영 DBA 조직에서는 정기 용량 리뷰를 운영하고, capacity review cadence와 scale trigger accuracy로 결과를 확인함

## Ⅷ. 결론

DB 용량 산정은 디스크 크기 계산이 아니라 성장과 피크와 오버헤드를 반영해 장애 이전에 증설 시점을 잡는 운영 계획 작업임.
