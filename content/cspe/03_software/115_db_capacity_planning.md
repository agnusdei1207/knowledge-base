# 📖 【암기용】 개념 완전 이해

> 목적: 데이터베이스 용량 산정을 처음 보는 사람도 완전히 이해하게 만든다. 시험 답안 양식이 아니라, 이해를 위한 설명이다.

## 한눈에
- **개요**: 업무량(트래픽)과 데이터 증가량을 수치로 환산해 필요한 **컴퓨팅 자원**(CPU·메모리·IOPS·스토리지·커넥션)을 미리 계산하는 **용량 계획(Capacity Planning)** 활동이다.
- **왜 필요한가**: DB는 사용자가 몰리는 순간에야 부족함이 드러나면 이미 늦다. TPS/QPS, 데이터 크기, 피크 배수를 미리 계산해 두지 않으면 피크 시간에 지연·장애가 발생한다.
- **핵심 직관**: 식당이 손님이 다 차고 나서 화구와 재료를 늘리지 않듯, 예상 손님 수와 회전율로 좌석·주방·창고를 미리 계산해 두는 일이다.

## 핵심 용어 정리 (내부에 등장하는 것들)

| 용어 | 의미 | 비유 |
|:---|:---|:---|
| 용량 계획(Capacity Planning) | 미래 수요를 예측해 자원을 미리 확보하는 활동 — 이 산정의 **목적** | 예상 손님 수로 좌석·재료를 미리 계산 |
| TPS/QPS | 초당 처리하는 트랜잭션/쿼리 수 — 업무량을 나타내는 **기본 단위** | 초당 주문 접수·조회 건수 |
| Peak Factor(피크 배수) | 평균 대비 순간 최대 부하의 배수 | 평소 대비 러시아워 승객 배수 |
| Row Size / Index Size | 행 하나의 저장 크기 / 인덱스가 차지하는 추가 크기 | 서류 한 장 크기 / 서류를 찾기 위한 색인 카드 크기 |
| IOPS | 초당 디스크 읽기·쓰기 처리 횟수 | 초당 창고에서 물건을 꺼내고 넣는 횟수 |
| Buffer Pool | 자주 쓰는 데이터·인덱스를 메모리에 캐싱해 두는 DB 내부 영역 | 자주 찾는 서류를 책상 위에 올려둠 |
| Working Set | 실제로 반복 접근되는 데이터의 부분집합 | 전체 서류 중 매일 꺼내 보는 서류 묶음 |
| Connection Pool | 동시에 열어 둘 수 있는 DB 연결 개수 | 창구(카운터) 개수 |

## 깊이 이해

### 왜 평균이 아니라 피크로 산정하는가 (배경)
- 지하철은 하루 평균 승객이 아니라 출근 시간(피크) 승객을 기준으로 배차를 정한다. DB도 마찬가지로, 평균 QPS로 서버를 맞추면 피크 시간에 connection 고갈·IOPS 포화·buffer pool miss가 먼저 터진다. 용량 산정은 항상 "평균 × 피크 배수"로 순간 최대치를 계산하는 데서 시작한다.

### 업무량을 QPS로 바꾸는 계산 (수치로 이해)
- DAU(일일 활성 사용자) 100만 명, 사용자당 주문 조회 20회/일이면 하루 총 조회는 100만×20 = 2,000만 건이다.
- 이 중 10%가 출퇴근 시간대 1시간에 몰린다고 하면, 피크 시간 조회는 2,000만×0.1 = 200만 건이고, 이를 3,600초로 나누면 **피크 QPS ≈ 556건/초**다(`100만×20×0.1/3600=556`).
- 만약 캐시 hit ratio 90%를 적용해 실제 DB까지 도달하는 요청만 남기면, DB가 받는 실질 QPS는 556×(1-0.9) ≈ **56건/초**로 줄어든다. 이렇게 캐시·복제 등 앞단 흡수율까지 반영해야 DB가 실제로 처리할 부하가 나온다.

### 저장 공간을 계산하는 법 (수치로 이해)
- 행 하나가 500바이트이고, 인덱스가 원본 데이터의 1.5배 부가 공간을 차지한다고 하면 실효 저장 크기는 500×1.5 = 750바이트/행이다.
- 하루 신규 100만 행이 쌓인다면 월간 증가량은 100만×750바이트×30일 ≈ **22.5GB/월**이다. 여기에 복제본(replica) 2대와 30일치 백업을 더하면, 실제 필요한 총 스토리지는 원본 데이터의 3~6배까지 늘어날 수 있다.

### Buffer Pool을 working set으로 판단하기 (파레토 원리)
- 전체 데이터가 100GB라도 실제로 반복 조회되는 부분(working set)이 20GB(20%)뿐이라면, buffer pool을 20GB 이상으로만 잡아도 buffer hit ratio 95% 이상을 달성할 수 있다 — 전체를 메모리에 올릴 필요는 없다는 뜻이다.
- 반대로 buffer pool이 working set보다 작으면 매 조회마다 디스크 랜덤 IO가 발생해, 스토리지가 넉넉해도 IOPS 병목으로 지연이 커진다. "스토리지만 넉넉하면 된다"는 판단이 위험한 이유다.

### 비유와 흔한 오해
- **비유**: 출퇴근 시간 지하철은 하루 평균 승객이 아니라 8시 피크 승객을 기준으로 배차를 정한다 — DB 용량도 평균이 아니라 피크로 잡아야 한다.
- **오해 1**: CPU 사용률만 보고 여유가 있다고 판단하면 안 된다. 실제 병목은 CPU보다 IOPS, connection pool 고갈, lock 대기에서 먼저 나타나는 경우가 많다.
- **오해 2**: 산정값을 한 번 계산하고 끝내는 게 아니라, 부하테스트와 운영 지표로 오차(통상 20% 이내 목표)를 검증하고 주기적으로 재산정해야 한다.

## 연결 개념
- TPS/QPS·Peak Factor — 업무량을 자원 요구량으로 바꾸는 기본 단위와 배수
- 캐시 계층(114) — DB까지 도달하는 실질 QPS를 낮추는 앞단 흡수 장치
- 데이터베이스 복제(113) — 산정된 읽기 QPS를 여러 노드에 분산하는 수단
- IOPS·Buffer Pool·Working Set — 저장공간이 아니라 접근 패턴이 병목을 좌우한다는 원리

## Ⅰ. 개요 및 필요성

- 개요: DB 용량 산정은 자원 수요 예측이다.
- 배경: 사용자 증가, 데이터 보관기간, 피크 트래픽을 반영하지 않으면 connection 부족, IOPS 포화, 저장공간 부족이 발생한다.
- 필요성: TPS/QPS, row size, index size, peak factor, 여유율 30%를 기준으로 CPU, 메모리, IOPS, 스토리지를 산정해야 한다.

---

## Ⅱ. 구조 및 구성요소

```text
Business Forecast -> Workload Model
  / TPS/QPS -> CPU and connection
  / Row size and growth -> storage
  / Read/write pattern -> IOPS and buffer pool
Peak Factor -> HA/Backup Margin -> Capacity Plan
```

| 구성요소 | 역할 | 특이사항 |
|:---|:---|:---|
| 업무량 모델 | 사용자 수와 거래 빈도 산출 | DAU, MAU, 요청/사용자/일 |
| 데이터 모델 | 행 크기와 인덱스 크기 계산 | row overhead, index multiplier 포함 |
| IO 모델 | random/sequential IO 산정 | read/write ratio, WAL 반영 |
| 메모리 모델 | buffer pool·sort·connection 메모리 산정 | working set 크기 기준 |
| 성장 모델 | 피크·월 성장률·보관기간 반영 | 12~36개월 전망 필요 |

> 요약: DB 용량 산정은 업무량, 데이터량, IO, 메모리, 성장률 모델을 결합해 자원 요구량을 도출한다.

## Ⅲ. 동작원리 및 흐름도

```text
업무 예측 수집 -> TPS/QPS 산정
  / read path -> cache hit 반영 -> DB QPS
  / write path -> WAL and index write 반영 -> IOPS
데이터 증가 계산 -> 피크 배수 적용 -> 여유율 반영 -> 검증
```

| 단계 | 처리 내용 | 검증 기준 |
|:---:|:---|:---|
| 1 | 사용자 수, 거래 빈도, 피크 시간대 수집 | DAU/MAU, peak hour ratio |
| 2 | TPS/QPS와 read/write 비율 계산 | p95 목표 지연과 비교 |
| 3 | row size, index size, 보관기간으로 저장공간 계산 | 월 증가량 GB |
| 4 | working set과 buffer pool 크기 산정 | buffer hit ratio 95% 이상 |
| 5 | PoC·부하테스트로 산정값 보정 | 예상 대비 오차 20% 이하 |

> 요약: 용량 산정은 예측값을 계산한 뒤 부하테스트와 운영 지표로 오차를 줄이는 반복 절차이다.

## Ⅵ. 실무 적용 및 결론

**적용 방안 3개 (필수 - 단계별 또는 항목별):**
1. 업무량 산식화: `피크 QPS = DAU * 요청수 * 피크집중률 / 3600`으로 계산하고 캐시 hit ratio·read/write 비율을 반영함
2. 자원 모델링: row size, index multiplier 1.5~3배, replica 2개, backup 7~30일을 포함해 저장공간과 IOPS를 산정함
3. 검증·운영: JMeter/k6와 production trace replay로 p95 지연, lock wait, buffer hit를 검증하고 70% 임계치에서 증설 알람을 설정함

**결론 (2줄):**
- 기술사 판단: 신규 DB는 피크 부하 1.3배와 12개월 성장률을 기준으로 산정하고, 운영 DB는 실제 지표로 월 1회 보정해야 함
- 향후 방향: 클라우드 DB에서는 autoscaling이 가능하지만 connection, lock, index bloat는 자동 증설만으로 해결되지 않으므로 모델 기반 관리가 필요함
