## Ⅰ. 개요
- **정의**: 생산자와 소비자 간 비동기 메시지 전달을 중개하는 미들웨어
- **배경/필요성**: 서비스 간 직접 호출은 결합도가 높아 장애 전파·부하 집중 문제가 발생하므로 완충 계층이 필요함
- **비유**: 우체통에 편지를 넣으면 수신자가 자기 속도로 꺼내 읽는 구조와 유사함

| 출제 의도 | 반드시 짚을 핵심 | 감점 회피 포인트 |
|:---|:---|:---|
| 비동기 통신 아키텍처 이해 | 디커플링·버퍼링·보장 수준 | Pub/Sub(164 참조)과의 차이 구분 |

> 요약: 생산자-소비자를 분리하여 비동기로 메시지를 전달하는 미들웨어임

## Ⅱ. 구성요소
```text
Producer --> [Queue (Broker)] --> Consumer
               |
          Persistence / ACK
```

| 구성요소 | 설명 | 비유 |
|:---|:---|:---|
| Producer | 메시지를 생성하여 큐에 전송하는 발신 측 | 편지를 우체통에 넣는 발신자 |
| Queue(Broker) | 메시지를 저장·관리하며 소비자에게 전달하는 중개자 | 우체통 겸 우체국 |
| Consumer | 큐에서 메시지를 수신·처리하는 수신 측 | 우체통에서 편지를 꺼내는 수신자 |
| ACK | 소비자가 처리 완료를 큐에 통보하는 확인 응답 | 수취 서명 |

> 요약: Producer-Queue-Consumer-ACK 구조로 비동기 메시지를 중개함

## Ⅲ. 절차
```text
Producer 발행 --> Broker 저장 --> Consumer 수신 --> ACK 응답
      |               |               |              |
      v               v               v              v
   메시지 생성    큐 영속 저장     Pull/Push 수신   처리 완료 확인
```
- 1단계: Producer가 메시지를 직렬화하여 Broker에 전송함
- 2단계: Broker가 메시지를 큐에 영속 저장하고 순서를 보장함
- 3단계: Consumer가 Pull 또는 Push 방식으로 메시지를 수신·처리함
- 4단계: Consumer가 ACK를 전송하면 Broker가 해당 메시지를 제거함

> 요약: 발행-저장-수신-확인 4단계로 메시지 전달 신뢰성을 확보함

## Ⅳ. 문제점
- 메시지 유실: Broker 장애 시 영속화되지 않은 메시지가 소실될 수 있음
- 순서 보장 한계: 다중 Consumer 환경에서 메시지 처리 순서가 뒤바뀔 수 있음
- 모니터링 부담: 큐 적체·Dead Letter 등 운영 상태를 지속 감시해야 함

> 요약: 메시지 유실·순서 역전·운영 모니터링이 주요 과제임

## Ⅴ. 개선방안
1. 단기: 디스크 영속화 + 복제(Replication)로 메시지 유실 방지
2. 중기: 파티션 키 기반 순서 보장 전략 적용
3. 장기: 통합 모니터링·알림 체계 구축으로 큐 적체·DLQ 자동 대응

> 요약: 영속화-파티션 순서-모니터링 자동화 순으로 개선함

## Ⅵ. 전망
- 발전 방향: 이벤트 스트리밍 플랫폼(Kafka 등)과 경계가 수렴 중임
- 기술사적 판단: MSA 환경에서 서비스 간 통신의 표준 패턴으로 정착됨
- 기술사 제언: 메시지 보장 수준(At-Least-Once/Exactly-Once)을 요구사항에 맞게 설계할 필요
