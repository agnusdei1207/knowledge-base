## 미리 알고가기

- WIP는 동시에 진행 중인 작업 수를 뜻함
- Pull 방식은 다음 단계에 여유가 생겼을 때만 새 작업을 가져오는 운영 방식임
- Cycle time은 작업 착수부터 완료까지 걸린 시간을 뜻함

## 작성 근거(검토용)

- 스크럼과 칸반을 주기·계획·작업 이동·통제·지표·적용 업무로 비교함
- 카드 등록·단계 이동·WIP 판정·완료·흐름 개선을 실제 작업 상태 전이로 유지함
- 운영 지원과 플랫폼 팀을 분리해 작업 체류시간과 WIP 위반 수를 검증함

## Ⅰ. 개요

- **정의/개념**: 칸반은 작업 단계를 시각화하고 단계별 WIP 한도와 Pull 규칙으로 작업 흐름을 제어하는 관리 방식임
- **배경/필요성**: 여러 작업의 동시 착수로 생기는 대기와 컨텍스트 전환을 줄이기 위해 단계별 작업 수와 이동 기준이 필요함

## Ⅱ. 특징

- 고정 스프린트 대신 연속 흐름으로 작업을 착수·이동·완료함
- WIP 제한은 단계별 작업 수를 제한해 병목과 과부하를 보드에 표시함
- 작업이 완료되면 우선순위가 높은 다음 항목을 pull하므로 지속 유입 업무의 순서 변경을 반영함
- WIP 한도와 Pull 규칙이 없으면 보드가 작업 상태만 기록하고 신규 착수량을 통제하지 못함

## Ⅲ. 종류 및 비교

| 구분 | 스크럼 | 칸반 |
|:---|:---|:---|
| 운영 주기 | 정해진 스프린트 안에서 목표를 관리함 | 고정 주기 없이 연속 흐름으로 작업을 관리함 |
| 계획 방식 | 스프린트 시작 시 작업 범위를 묶어서 계획함 | 수요와 우선순위 변화에 맞춰 다음 작업을 계속 끌어옴 |
| 통제 수단 | 스프린트 목표와 팀 약속으로 진행을 통제함 | WIP 제한과 흐름 지표로 병목을 통제함 |
| 대표 환경 | sprint 목표와 반복 일정을 운영하는 제품팀 | 운영 지원·유지보수처럼 작업 유입 시점이 일정하지 않은 조직 |
| 작업 이동 | 스프린트 범위 안에서 진행 | 다음 단계의 여유가 있을 때 Pull |
| 측정 지표 | 스프린트 목표·이월률 | cycle time·throughput·blocked time |

> 요약: 칸반은 단계별 WIP 한도와 Pull 규칙으로 작업 착수·이동 수를 제한함.

## Ⅳ. 구성요소 및 구조

| 구성요소 | 설명 |
|:---|:---|
| 칸반 보드 | 작업 카드의 단계·담당·차단 상태를 표시함 |
| WIP 한도 | 단계별 진행 중 작업 수의 상한을 정함 |
| Pull 규칙 | 다음 단계의 WIP 여유가 있을 때 작업을 이동함 |
| 흐름 지표 | cycle time·throughput·blocked time으로 단계별 대기를 측정함 |

> 요약: 보드가 작업 상태를 표시하고 WIP 한도·Pull 규칙이 단계 이동을 통제하며 흐름 지표가 대기를 측정함.

## Ⅴ. 원리 및 절차 흐름도

```text
+-------------+     +-------------+     +-------------+     +-------------+
| 작업 등록      | --> | 단계별 시각화   | --> | WIP 제한 운영   | --> | 흐름 개선      |
+-------------+     +-------------+     +-------------+     +-------------+
```

1. **작업 등록**: 처리할 업무와 우선순위·완료 조건을 카드로 정의함
2. **단계 이동 요청**: 앞 단계 작업이 끝나면 다음 단계의 WIP를 확인함
3. **Pull·완료**: WIP 여유가 있으면 작업을 이동하고 마지막 단계에서 완료 처리함
4. **흐름 조정**: 단계별 체류시간과 차단 상태로 WIP 한도·규칙을 조정함

## Ⅵ. 실무 사례

1. 운영 지원팀은 긴급 작업 전용 규칙과 WIP 한도를 적용하고 작업 완료시간과 WIP 위반 수를 확인함
2. 플랫폼 팀은 차단 작업을 별도 표시하고 차단 체류시간과 주간 완료 건수를 확인함

## Ⅶ. 결론

- 칸반은 작업 유입 변동과 단계별 처리능력에 맞춰 WIP 한도·Pull 규칙·흐름 지표를 운영함
