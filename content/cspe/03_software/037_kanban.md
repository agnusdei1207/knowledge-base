## 미리 알고가기

- WIP는 동시에 진행 중인 작업 수를 뜻함
- Pull 방식은 다음 단계에 여유가 생겼을 때만 새 작업을 가져오는 운영 방식임
- Cycle time은 작업 착수부터 완료까지 걸린 시간을 뜻함

## Ⅰ. 개요

- **정의/개념**: 칸반은 작업 흐름을 단계별로 시각화하고 각 단계의 진행 중 작업 수를 제한해 병목을 드러내고 완료 속도를 높이는 업무 관리 방식임.
- **배경/필요성**: 할 일을 많이 시작하는 조직은 완료보다 착수에 치우쳐 지연과 컨텍스트 전환이 늘어나므로, 시작량이 아니라 흐름과 완료량을 통제하는 체계가 필요함.

## Ⅱ. 특징

- 스프린트보다 연속 흐름과 작업 완료 속도를 더 중시함
- WIP 제한으로 병목과 과부하를 눈에 띄게 드러냄
- 우선순위 변동이 잦은 운영 조직에서도 바로 적용하기 쉬움
- 규칙 없이 보드만 쓰면 단순 현황판으로 끝날 수 있음

## Ⅲ. 종류 및 비교

| 구분 | 스크럼 | 칸반 |
|:---|:---|:---|
| 운영 주기 | 정해진 스프린트 안에서 목표를 관리함 | 고정 주기 없이 연속 흐름으로 작업을 관리함 |
| 계획 방식 | 스프린트 시작 시 작업 범위를 묶어서 계획함 | 수요와 우선순위 변화에 맞춰 다음 작업을 계속 끌어옴 |
| 핵심 통제 | 스프린트 목표와 팀 약속으로 진행을 통제함 | WIP 제한과 흐름 지표로 병목을 통제함 |
| 적합한 환경 | 기능 단위 반복 개발과 일정 약속이 중요한 제품팀에 맞음 | 운영 지원, 유지보수, 지속 개선처럼 유입이 계속 바뀌는 조직에 맞음 |

> 요약: 칸반의 핵심은 보드를 그리는 일이 아니라 진행 중 작업 수를 줄여 완료 흐름을 안정시키는 데 있음.

## Ⅳ. 구성요소 및 구조

| 구성요소 | 설명 |
|:---|:---|
| Kanban Board | 작업 단계를 시각화해 어디서 병목이 생기는지 바로 보이게 함 |
| WIP Limit | 각 단계의 진행 중 작업 수를 제한해 몰림과 컨텍스트 전환을 줄임 |
| Pull Rule | 다음 단계가 감당할 수 있을 때만 새 작업을 가져오게 해 흐름 균형을 유지함 |
| Flow Metric | cycle time, throughput, blocked time을 함께 보며 개선 효과를 판단함 |

## Ⅴ. 원리 및 절차 흐름도

```text
+-------------+     +-------------+     +-------------+     +-------------+
| 작업 등록      | --> | 단계별 시각화   | --> | WIP 제한 운영   | --> | 흐름 개선      |
+-------------+     +-------------+     +-------------+     +-------------+
```

1. **작업 등록**: 처리할 업무를 카드 단위로 정의함
2. **단계별 시각화**: 분석, 개발, 검토, 배포 같은 흐름 단계를 보드에 배치함
3. **WIP 제한 운영**: 각 단계 한도를 넘지 않도록 pull 방식으로 작업을 이동함
4. **흐름 개선**: 병목과 지연 원인을 지표로 보고 규칙을 조정함

## Ⅵ. 실무 적용 및 유의점

1. 운영 지원 조직에서는 칸반으로 상시 유입 업무를 다루되 긴급 요청이 계속 끼어들면 정상 흐름이 무너지므로 긴급 요청 전용 처리 규칙과 단계별 진행 중 작업 한도를 함께 운영하고 작업 완료 시간과 지연 작업 체류 시간으로 확인함
2. 플랫폼 개선 팀에서는 보드를 현황판으로만 쓰지 않도록 정기 흐름 리뷰를 수행하고 병목 단계별 개선 실험을 연결하며 완료 건수 추이와 실제 처리 시간 비율로 확인함

## Ⅶ. 결론

칸반은 일을 많이 시작하는 조직을 일을 꾸준히 끝내는 조직으로 바꾸기 위한 흐름 관리 방식임.
