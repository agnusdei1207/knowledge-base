# 📖 【암기용】 개념 완전 이해

## 한눈에
- **개요**: 네트워크 장애(P) 상황에서의 CAP 정리를 확장하여, **장애가 없는 평상시(E)**에도 지연 시간(L)과 일관성(C) 사이의 트레이드오프가 존재함을 설명하는 분산 시스템 최신 이론
- **왜 필요한가**: CAP 정리는 "네트워크가 끊어졌을 때(P) 어떻게 할래?"만 설명한다. 하지만 실제 시스템은 99.9% 평상시 상태로 동작하는데, 평상시에도 데이터를 빡빡하게 동기화(C)하면 속도가 느려지고(L), 속도(L)를 높이면 데이터 불일치(C 붕괴)가 생기는 현실을 설명해야 했다.
- **핵심 직관**: 식당 매니저가 본사에 매출을 보고할 때, 전화가 안 될 때(P)의 대처가 CAP라면, 전화가 잘 될 때(E)도 매번 1건 결제마다 본사에 확인받고 승인(C)할지, 일단 손님을 빨리 보내고 나중에 몰아서 보고할지(L 단축) 고민하는 것이 PACELC다.

## 핵심 용어 정리

| 용어/표기 | 의미 | 비유·예 |
|:---|:---|:---|
| P (Partition) | 네트워크 통신 단절 등 시스템의 분할 상태 (장애) | "전화선이 끊어진 상태" |
| A / C (Availability / Consistency) | 장애(P) 시 가용성(A)을 택할지, 일관성(C)을 택할지 | "옛날 정보로 영업(A) vs 일단 멈춤(C)" |
| E (Else) | 네트워크 단절이 없는 평상시 상태 (정상 상태) | "전화선이 쌩쌩하게 잘 터지는 평상시" |
| L / C (Latency / Consistency) | 평상시(E) 응답 속도(L)를 택할지, 일관성(C)을 택할지 | "빠른 처리(L) vs 완벽한 동기화 대기(C)" |

## 깊이 이해
- **배경·문제의식**: 클라우드 시대에 "우리 시스템은 무조건 CA입니다"라고 주장하는 오해를 불식시키고자 Daniel Abadi가 제안. 시스템이 평상시(Else)에 동작할 때, 분산된 노드 간에 데이터를 100% 동기화하려면 네트워크 왕복 시간 때문에 지연(Latency)이 발생한다.
- **작동 원리 (PACELC 공식)**:
  - **If P (장애 시)**: 네트워크가 끊기면 **A**vailability(가용성)와 **C**onsistency(일관성) 중 하나 선택 (CAP 정리와 동일).
  - **E**lse (평상시): 네트워크가 정상이면, **L**atency(낮은 지연시간)와 **C**onsistency(강한 일관성) 중 하나 선택.
- **분류 체계**:
  - **PC/EC**: 장애 시 C 선택, 평상시도 동기화 대기하여 C 선택 (예: HBase, 빡빡한 정합성)
  - **PA/EL**: 장애 시 A 선택, 평상시엔 동기화 안 기다리고 빨리 응답(L) (예: Cassandra, DynamoDB, 스피드 우선)
  - **PA/EC**: 장애 시엔 A 선택, 하지만 평상시엔 빡빡하게 동기화(C) (예: MongoDB의 기본 설정)
- **비유**: 글로벌 물류창고.
  - PC/EC: 서울 지점과 뉴욕 지점 장부가 완벽히 똑같을 때까지 트럭 출발 불가. (정확하지만 느림)
  - PA/EL: 물건만 들어오면 장부 동기화 안 기다리고 바로바로 배송 출발. (빠르지만 나중에 재고 안 맞을 수 있음)
- **흔한 오해·주의점**: L은 '낮은 지연시간(Low Latency)'을 의미한다. 지연시간을 높인다는 뜻이 아니라 지연시간을 줄이기 위해 일관성을 희생한다는 뜻이다.

## 연결 개념
- CAP 정리: PACELC의 전반부(PAC)에 해당하는 이론으로 분산 시스템 이론의 조상.
- Dynamo 아키텍처: 아마존이 만든 분산 저장 모델로, PA/EL을 극단적으로 추구하여 응답 속도를 10ms 이내로 방어하는 것이 최우선 목표다.

# 📝 【답안용】 시험 답안 템플릿

## 핵심 인사이트 (3줄 요약)

> 1. **본질**: PACELC 정리는 분산 시스템이 네트워크 파티션(P) 시 A와 C 중 하나를 택해야 하고, 평상시(E)에도 레이턴시(L)와 일관성(C) 중 하나를 택해야 한다는 포괄적 아키텍처 이론이다.
> 2. **가치**: 장애 상황에 국한된 CAP 정리의 한계를 극복하고, 시스템 런타임의 99.9%를 차지하는 정상(E) 상태에서의 성능(L) 튜닝 가이드라인을 제공한다.
> 3. **판단 포인트**: 클라우드 NoSQL 도입 시, 단순한 정합성 여부를 넘어 평상시 글로벌 노드 간 복제 지연을 비즈니스가 수용할 수 있는지(EL) 아니면 대기해야 하는지(EC)를 평가 기준으로 삼아야 한다.

## 출제 의도 및 답안 포인트

| 출제 의도 | 반드시 짚을 핵심 | 감점 회피 포인트 |
|:---|:---|:---|
| 최신 분산 시스템 설계 원리 이해 | CAP 정리의 한계(평상시 성능 설명 불가)와 E(Else)의 의미 | CAP 정리와 동일한 내용으로만 서술 |
| PACELC 요소 및 조합 역량 | PA/EL, PC/EC 등 NoSQL 아키텍처의 4가지 조합 설명 | L을 "지연 발생"이 아닌 "지연 단축(성능)"으로 설명 못함 |
| 실무 응용 및 성능 튜닝 판단 | 평상시 분산 노드 간 동기화 비용(네트워크 오버헤드)에 따른 지연 | 단일 서버 RDBMS로 PACELC를 설명하려 함 |

> 요약: 분산 시스템 설계의 본질적 난제가 장애(P)뿐 아니라 평상시(E)의 물리적 거리와 네트워크 왕복에 따른 동기화 지연(L)과 일관성(C) 간의 상충 관계에 있음을 정확히 규명해야 한다.

## Ⅰ. 개요 및 필요성

- 개요: CAP 정리를 확장하여, 네트워크 파티션(P) 상황 외의 평상시(E)에도 일관성(C)과 지연시간(L) 간의 트레이드오프가 발생함을 명시한 분산 시스템 원리
- 배경: CAP 정리는 장애 시나리오에만 초점을 맞춰, 99.9%의 정상 운영 환경에서 발생하는 복제 비용과 성능 저하의 상관관계를 설명하기 부족함
- 필요성: 빅데이터와 글로벌 멀티 리전(Region) 아키텍처에서 읽기/쓰기 응답 속도(Latency)를 보장하기 위한 분산 DB 설계 및 선택 기준 필요

---

## Ⅱ. 구조 및 구성요소

```text
[ PACELC Theorem ]
If (네트워크 파티션 장애 발생 시: P)
   -> 선택: [ 가용성 (A) ] or [ 일관성 (C) ]
Else (장애가 없는 평상시: E)
   -> 선택: [ 낮은 지연시간 (L) ] or [ 강한 일관성 (C) ]
```

| 구성요소 | 역할 | 특이사항 |
|:---|:---|:---|
| P (Partition) | 노드 간 네트워크 통신 두절 등 장애 상황 | CAP 정리의 P와 동일한 분산 시스템 상수 |
| A / C (장애 시) | 가용성(Availability)과 일관성(Consistency)의 트레이드오프 | 응답 중단 vs 불일치 응답의 양자택일 |
| E (Else) | 모든 노드가 정상 통신하는 평상시 런타임 상태 | PACELC 이론이 도입한 새로운 맥락 |
| L / C (평상시) | 지연시간 최적화(Latency)와 일관성(Consistency)의 트레이드오프 | 노드 간 데이터 동기화 대기 여부 |

> 요약: 시스템은 P 상황에서는 A와 C를 저울질하고, 정상적인 E 상황에서는 성능(L)과 정합성(C)을 저울질하는 연속적인 상태 기계(State Machine)이다.

---

## Ⅲ. 동작원리 및 흐름도

```text
Client Write -> Node 1 수신 
  -> (상태 판단) 네트워크 정상(E)인가? 단절(P)인가?
  |
  +-> [E: 정상] -> Node 2/3로 복제 전송 
  |     +-> (EL 선택): 복제 완료 안 기다리고 즉시 Client 응답 (지연시간 ↓, 일관성 ↓)
  |     +-> (EC 선택): Node 2/3의 복제 완료 ACK를 기다린 후 응답 (지연시간 ↑, 일관성 ↑)
  |
  +-> [P: 단절] -> Node 2/3 통신 불가
        +-> (PA 선택): 옛날 데이터라도 Client 응답 (가용성 보장)
        +-> (PC 선택): 동기화 불가로 Client 에러 반환 (일관성 방어)
```

- 1단계 [상태 분기]: 시스템이 현재 클러스터 쿼럼(Quorum) 통신이 정상(Else)인지 파티션(Partition) 상태인지 감지
- 2단계 [평상시 동작 - EL]: 응답 속도가 중요하면 분산 노드의 쓰기 완료를 기다리지 않고 비동기 백그라운드로 미루어 응답 반환
- 3단계 [평상시 동작 - EC]: 정합성이 중요하면 Two-Phase Commit(2PC)처럼 타 노드의 디스크 기록 확인 후 응답하여 수십 ms 지연 발생
- 4단계 [장애 시 동작]: P 상태 감지 시 CAP 정리의 룰에 따라 설정된 PA 또는 PC 정책 실행

> 요약: 데이터 쓰기(Write) 시점에 글로벌 복제 동기화를 동기로 할지(EC), 비동기로 할지(EL)에 따라 평상시 응답 속도가 극명하게 갈린다.

## Ⅳ. 특징

- 상시적 트레이드오프: 장애라는 극단적 상황이 없더라도, 빛의 속도와 물리적 거리에 제약받는 글로벌 분산 환경에서는 동기화 비용(L)이 상존함
- 유연한 조합: PC/EC, PA/EL 등 비즈니스 요구에 따라 NoSQL 아키텍처의 패러다임을 4가지 사분면으로 명확히 분류 가능
- 튜너블 일관성 (Tunable Consistency): 최신 NoSQL은 Read/Write Quorum 개수를 런타임에 조절하여 EL에서 EC로 시스템 동작을 동적으로 변경 가능

## Ⅴ. 심화 비교 및 적용 판단

| 비교 축 | PA/EL (Cassandra, Dynamo) | PC/EC (HBase, Spanner) | PA/EC (MongoDB) |
|:---|:---|:---|:---|
| 설계 철학 | "무조건 빠르고 멈추지 않는다" | "느리거나 멈춰도 데이터는 100% 정확하다" | "장애 땐 응답하지만 평소엔 일치시킨다" |
| 평상시(E) | 동기화 대기 없이 즉각 응답 (L) | 과반수 노드 쓰기 완료 후 응답 (C) | 마스터-슬레이브 간 동기적 일관성 추구 (C) |
| 주요 Use Case | 장바구니, IoT 로그 수집, 실시간 피드 | 금융 결제 트랜잭션, 재고 원장 관리 | 사용자 세션 관리, 메타데이터 스토어 |

> 요약: 글로벌 멀티 리전 아키텍처에서 대량의 이벤트를 수집할 때는 PA/EL 기반의 카산드라가 압도적 성능을 낸다.

**리스크·대응:**
- EL 조합의 Read Stale 문제: 비동기 복제 중 읽기 요청 시 낡은 데이터 노출 → 클라이언트 레벨에서 'Read-Your-Writes' 세션 일관성을 강제하여 본인이 쓴 글은 보이게 처리
- EC 조합의 글로벌 지연(Latency): 리전 간(예: 서울-미국) 동기화 시 수백 ms 응답 지연 발생 → 코어 트랜잭션만 EC로 처리하고, 부가 정보는 이벤트 드리븐 기반 비동기(EL)로 격리(CQRS)
- 튜닝 실패 리스크: W+R 설정 오류로 시스템 전체 성능 저하 → 쿼럼 공식을 `W + R > N` (강한 일관성)에서 `W=1, R=1` (극단적 L 최적화)로 도메인 분리 적용

---

## Ⅵ. 실무 적용 및 결론

**적용 방안 3개:**
1. 아키텍처 분리(CQRS) 결합: 시스템 전체를 하나의 조합으로 묶지 않고, 결제 커맨드 모델은 PC/EC(HBase)로 설계하고 조회용 Read 모델은 비동기 파생된 PA/EL(Redis)로 분리 구축
2. 튜너블 Consistency 동적 적용: Cassandra 환경에서 평시 장바구니 담기는 `LOCAL_ONE`(EL 극대화)으로 설정하고, 최종 주문 결제 시점에만 쿼럼을 `EACH_QUORUM`(EC 추구)으로 상향하여 코드 레벨에서 통제
3. 멀티 리전 복제 튜닝: 글로벌 서비스 시 AWS DynamoDB의 Global Table을 활용하되, 리전 간은 Eventual Consistency(PA/EL)로 두고 리전 내부는 Strong Consistency(EC)로 계층화 설계

**결론 (2줄):**
- 기술사 판단: PACELC 정리는 분산 데이터베이스 아키텍트에게 "동기화의 물리적 비용(Latency)"을 계산하도록 강제하며, 100% 동기화라는 RDBMS의 향수를 버려야 Scale-out이 가능함을 증명한다.
- 향후 방향: 최근 클라우드 인프라의 네트워크 속도 발전으로 E 환경에서의 L(지연) 비용이 감소하고 있어, 합의 알고리즘(Raft) 기반 튜닝으로 EC 성능을 비약적으로 높인 아키텍처가 부상하고 있다.
