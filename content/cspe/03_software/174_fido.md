## Ⅰ. 개요
- **정의**: 비밀번호 없이 생체정보·보안키 기반 공개키 암호로 인증하는 국제 표준
- **배경/필요성**: 비밀번호는 피싱·유출·재사용 공격에 취약하여 비밀번호 의존도를 낮출 수단이 필요함
- **비유**: 열쇠(개인키)는 본인만 소유하고, 자물쇠(공개키)는 서버에 설치하여 대조하는 구조임

| 출제 의도 | 반드시 짚을 핵심 | 감점 회피 포인트 |
|:---|:---|:---|
| 패스워드리스 인증 원리 이해 | 공개키 기반 챌린지-응답 메커니즘 | UAF·U2F·FIDO2 프로토콜 구분 필요 |

> 요약: 공개키 암호 기반으로 비밀번호 없이 안전한 인증을 구현하는 국제 표준임

## Ⅱ. 구성요소
```text
User ---> Authenticator ---> Client(Browser/App) ---> FIDO Server
          (개인키 보관)        (CTAP/WebAuthn)         (공개키 보관)
```

| 구성요소 | 설명 | 비유 |
|:---|:---|:---|
| Authenticator | 개인키를 생성·저장하고 챌린지에 서명하는 장치 | 본인만 가진 열쇠 |
| FIDO Server | 등록 시 공개키를 저장하고 서명을 검증하는 서버 | 자물쇠가 설치된 금고 |
| WebAuthn | 브라우저-서버 간 FIDO 인증 API 표준 | 자물쇠 규격 표준 |
| CTAP | 클라이언트-인증기 간 통신 프로토콜(USB/NFC/BLE) | 열쇠와 자물쇠 연결 통로 |
| Passkey | FIDO2 자격증명을 클라우드 동기화하는 방식 | 열쇠 복제 보관함 |

> 요약: Authenticator·FIDO Server 간 공개키 쌍을 WebAuthn/CTAP로 연동하는 구조임

## Ⅲ. 절차
```text
[등록]  User -> Authenticator : 키쌍 생성
        Authenticator -> Server : 공개키 전송 + 저장

[인증]  Server -> Client : Challenge 전송
        Client -> Authenticator : Challenge 서명(개인키)
        Authenticator -> Server : 서명값 전송 -> 공개키로 검증
```
- 1단계: 등록 시 Authenticator가 키쌍을 생성하고 공개키를 서버에 전송함
- 2단계: 인증 요청 시 서버가 임의의 Challenge를 클라이언트에 전달함
- 3단계: Authenticator가 개인키로 Challenge에 서명하여 응답함
- 4단계: 서버가 저장된 공개키로 서명을 검증하여 인증을 완료함

> 요약: 키쌍 등록 후 챌린지-서명-검증의 공개키 기반 인증 흐름을 수행함

## Ⅳ. 문제점
- 장치 분실 시 복구 어려움: 개인키가 장치에 바인딩되어 분실 시 인증 수단이 상실됨
- 레거시 호환성 부족: WebAuthn 미지원 브라우저·시스템에서는 FIDO 인증이 불가함
- 플랫폼 종속성: Passkey 동기화가 특정 OS 생태계에 한정될 수 있음

> 요약: 장치 분실 복구·레거시 호환·플랫폼 종속이 확산의 주요 장벽임

## Ⅴ. 개선방안
1. 단기: 복수 인증기 등록 및 복구 코드 발급으로 분실 시 접근성 확보
2. 중기: 점진적 도입 전략으로 레거시 시스템에 비밀번호+FIDO 병행 인증 적용
3. 장기: 크로스 플랫폼 Passkey 동기화 표준 확산으로 생태계 종속 해소

> 요약: 복수 인증기·병행 인증·크로스 플랫폼 동기화로 단계적 확산이 필요함

## Ⅵ. 전망
- 발전 방향: Passkey 보급으로 패스워드리스 인증이 소비자 서비스까지 확대 추세임
- 기술사적 판단: 피싱 저항성이 내재된 유일한 인증 표준으로 채택 가속화됨
- 기술사 제언: MFA(175 참조)와 FIDO를 결합하여 인증 보증 수준(AAL)을 높이는 설계 필요함
