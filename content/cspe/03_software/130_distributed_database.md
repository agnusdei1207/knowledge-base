## 핵심 인사이트 (3줄 요약)
- 1대의 슈퍼컴퓨터가 모든 데이터를 독점하던 중앙 집중형 DB에서 벗어나, **물리적으로 멀리 떨어진 여러 대의 컴퓨터(노드)에 데이터를 쪼개고 복사해 두지만, 사용자는 마치 1대의 DB를 쓰는 것처럼 느끼게 만드는 마법의 시스템**.
- 이 마법이 성립하려면 데이터 위치, 중복, 단편화(쪼개짐)를 사용자가 전혀 몰라도 되는 **'4대 투명성(Transparency)'** 조건이 100% 충족되어야 함.
- 무한한 확장성과 장애 내성(Fail-over)을 얻었지만, 서울과 뉴욕에 있는 DB 간의 데이터 동기화(2PC, 트랜잭션 충돌)라는 엄청난 네트워크 비용과 복잡성을 감당해야 하는 CAP 정리의 전쟁터임.
---
## Ⅰ. 개요 및 필요성
- **개요**: 논리적으로는 하나의 시스템에 속하지만 물리적으로는 컴퓨터 네트워크를 통해 여러 지역(노드)에 분산되어 있는 데이터베이스의 모음.
- **필요성**: 글로벌 기업(예: 넷플릭스)이 한국 유저의 로그인 요청을 매번 미국 본사 DB까지 보내면 로딩에 3초가 걸림(Latency 지옥). 한국 유저 데이터는 한국 서버에, 미국 유저 데이터는 미국 서버에 두되, 글로벌 통계나 조인(JOIN)을 할 때는 두 DB가 알아서 데이터를 모아 1초 만에 결과를 뱉어내는 똑똑한 시스템이 필요했음.
---
## Ⅱ. 아키텍처 및 핵심 원리
- **분산 데이터베이스의 4대 투명성 (핵심 암기 요결: 분-위-지-중)**:
  1. **단편화/분할 투명성 (Fragmentation Transparency)**:
     - 1억 건짜리 회원 테이블이 A, B, C 서버로 찢어져(Sharding) 있어도, 사용자는 `SELECT * FROM 회원`이라고 던지면 엔진이 알아서 합쳐줌.
  2. **위치 투명성 (Location Transparency)**:
     - 데이터가 한국(IP:192.x)에 있는지 미국(IP:10.x)에 있는지 사용자는 몰라도 됨. 그냥 테이블 이름만 부르면 됨.
  3. **지역사상 투명성 (Local Mapping Transparency)**:
     - 한국 서버가 MySQL을 쓰고 미국 서버가 Oracle을 써도(이기종 DB), 사용자는 통일된 규칙으로 쿼리를 날릴 수 있음.
  4. **중복 투명성 (Replication Transparency)**:
     - 장애 대비용으로 데이터가 3벌 복사되어 있어도, 사용자는 똑같은 데이터가 3개라고 느끼지 않고 1개만 있다고 느낌.
- **분산 트랜잭션 동기화 기법**:
  - **2-Phase Commit (2PC)**: 모든 분산 노드가 "커밋할 준비 됐어?"(1단계) ➡️ "응, 모두 커밋해!"(2단계)라고 합의하는 기법. 정합성은 완벽하나 네트워크 블로킹(Lock)으로 성능이 처참함.

```text
[ 분산 데이터베이스의 투명성 동작 예시 ]

 🙋‍♂️ [ 한국 지사 사장님의 쿼리 ] 
 ➡️ SELECT SUM(매출) FROM 글로벌매출;

 🧠 [ 분산 DB 미들웨어 (Distributed Query Engine) 의 뇌내 회로 ]
 1. 위치 투명성: '글로벌매출' 테이블은 서울 노드, 뉴욕 노드에 나뉘어 있군!
 2. 분할 투명성: 서울에서 100억, 뉴욕에서 200억 따로 계산해서 긁어와!
 3. 중복 투명성: 뉴욕 1번 노드가 죽었네? 몰래 복제된 뉴욕 2번 노드에서 긁어와야지.
 4. 결과 병합: (내부적으로 300억 합산 완료)
 
 📈 [ 사장님 화면 ] ➡️ 300억. (사장님은 미국 서버에 장애가 있었는지, 찢어져 있었는지 1%도 모름! 완벽한 투명성!)
```

## Ⅲ. 비교 및 연결
| 구분 | 중앙 집중형 DB | 분산 데이터베이스 (Distributed DB) |
|---|---|---|
| **물리적 구조** | 단일 서버 + 거대한 디스크 | **네트워크로 연결된 다수의 서버(노드)** |
| **장애 영향** | 서버 죽으면 전사 시스템 All Stop | **A서버 죽어도 B서버가 계속 서비스 (고가용성)** |
| **응답 속도 (Latency)**| 멀리 있는 유저는 무조건 느림 | **유저와 가까운 노드(Local)에서 처리하여 초고속** |
| **단점** | 하드웨어 확장(Scale-Up) 비용 한계 | **데이터 동기화 지연, 트랜잭션 꼬임, 설계 복잡도 폭발** |
---
## Ⅳ. 실무 적용 및 기술사 판단
- **2PC의 한계와 Saga 패턴으로의 선회**: 초창기 분산 DB 학자들은 완벽한 ACID 트랜잭션을 분산 환경에서 구현하려 2PC(Two-Phase Commit)를 만들었음. 그러나 실무에서 노드 1개가 네트워크 지연에 걸리면 전체 시스템이 Lock에 걸려 다운되는 재앙(CAP 정리에 의한 필연적 결과)이 터짐. 결국 현대 실무(MSA)에서는 분산 트랜잭션을 포기하고, 메시지 큐(Kafka)를 이용해 비동기로 맞추는 '최종 일관성(Saga Pattern)'으로 완전히 노선을 갈아탔음.
- **NewSQL의 등장 (Google Spanner)**: 하지만 인류는 포기하지 않았음. 구글은 각 분산 서버에 'GPS와 원자시계(TrueTime API)'를 달아서, 지구 반대편 서버와 완벽하게 0.0001초의 시간 동기화를 맞춰 분산 환경에서도 2PC의 병목 없이 완벽한 ACID를 제공하는 Spanner(NewSQL)를 창조하며 분산 DB의 새 역사를 씀.
---
## Ⅴ. 기대효과 및 결론
- 한 바구니(중앙 DB)에 모든 계란을 담지 않음으로써 엔터프라이즈 시스템의 '확장성(Scalability)'과 '가용성(Availability)'이라는 두 마리 토끼를 잡아낸 분산 시스템 공학의 꽃.
- "모든 것이 흩어져 있지만, 겉보기엔 완벽하게 하나처럼 움직여야 한다"는 4대 투명성의 철학은 오늘날 클라우드 컴퓨팅과 마이크로서비스 아키텍처(MSA)를 관통하는 핵심 정신임.

### 👶 어린이를 위한 3줄 비유 설명
1. 100만 권의 책이 있는 거대한 도서관 1개(중앙 DB)를 지으면, 부산 사는 친구는 책 빌리러 서울까지 오기 너무 힘들어요.
2. 그래서 전국 각지에 작은 도서관(노드) 100개를 지어 책을 나눠 놨어요 (분산 데이터베이스).
3. 친구는 동네 도서관에서 책을 검색(투명성)만 하면 돼요! 그 책이 제주도 도서관에 있든 강원도에 있든, 사서(DB 엔진)가 알아서 1초 만에 배달해서 친구 손에 딱 쥐여주는 마법의 도서관 시스템이랍니다!
