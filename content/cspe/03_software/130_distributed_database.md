# 📖 【암기용】 개념 완전 이해

> 목적: 분산 데이터베이스를 처음 봐도 완벽히 이해하게 만든다. 시험 답안 양식이 아니라, 이해를 위한 친절한 설명이다.

## 한눈에
- **개요**: 데이터를 여러 노드에 나눠 저장하는 **샤딩(파티셔닝)**과 같은 데이터를 여러 노드에 복제하는 **복제(Replication)**를 결합해, 물리적으로는 여러 대이지만 사용자에게는 하나의 논리적 DB처럼 보이게 하는 **분산 데이터베이스**다.
- **왜 필요한가**: 단일 서버는 CPU·메모리를 아무리 늘려도(scale-up) 디스크 IOPS·네트워크 대역폭 같은 물리적 한계에 부딪힌다. 분산 DB는 데이터를 쪼개 여러 노드가 나눠 갖게 하고(샤딩), 복제로 한 노드가 죽어도 서비스가 유지되게 한다(가용성). 대신 여러 노드에 걸친 일관성·트랜잭션·운영 복잡도라는 비용을 치른다.
- **핵심 직관**: 한 금고에 모든 문서를 넣지 않고 여러 지점 금고에 나눠 보관하되(샤딩), 각 지점 금고는 사본을 여러 개 둬서(복제) 한 지점이 문을 닫아도 서비스가 끊기지 않게 하는 구조다.

## 핵심 용어 정리 (내부에 등장하는 것들)

| 용어 | 의미 | 비유 |
|:---|:---|:---|
| 샤딩(파티셔닝, Sharding) | 데이터를 수평으로 나눠 여러 노드에 분산 저장하는 것 | 전국 물류센터에 화물을 지역별로 나눠 보관 |
| 복제(Replication) | 같은 데이터를 여러 노드에 복사해 장애 대비·읽기 분산에 쓰는 것 | 같은 문서를 지점마다 사본으로 비치 |
| 샤드 키(Shard Key) | 어느 샤드에 저장할지 정하는 기준 컬럼 | 우편번호로 배송 지역 창고 결정 |
| 라우터/코디네이터(Router/Coordinator) | 요청을 올바른 샤드로 안내하고 결과를 모으는 중개자 | 택배 접수처에서 목적지 허브를 찾아줌 |
| 복제 계수(Replication Factor, RF) | 같은 데이터를 몇 개 노드에 복제해 두는지 나타내는 수 | 사본을 몇 부 만들어 각 지점에 배치할지 |
| 쿼럼(Quorum) | 전체 복제본 중 과반수의 응답을 성공 기준으로 삼는 합의 규칙 | 이사회 의결정족수 — 과반 찬성이면 통과 |
| 2단계 커밋(2PC) | 여러 노드에 걸친 트랜잭션을 준비(prepare)-확정(commit) 2단계로 처리하는 프로토콜 | 여러 지점이 모두 "준비됐다"고 답한 뒤에야 동시에 도장을 찍음 |
| CAP 정리 | 분산 시스템은 일관성(C)·가용성(A)·분단 내성(P)을 동시에 완전히 만족할 수 없다는 정리 | 셋 중 둘만 고를 수 있는 딜레마 |
| 스플릿 브레인(Split Brain) | 네트워크 단절로 리더(대표 노드)가 둘 이상 생기는 장애 | 본사와 연락이 끊긴 두 지점이 각자 자기가 본사라 주장 |

## 깊이 이해

### 왜 분산 DB가 필요했나 (배경)
- 단일 서버는 CPU·메모리·디스크를 아무리 늘려도(scale-up) 물리적 한계에 부딪힌다. 예를 들어 하루 신규 데이터 1TB, 초당 쓰기 5만 건을 요구하는 서비스는 단일 노드의 디스크 IOPS와 네트워크 대역폭만으로 감당하기 어렵다. 분산 DB는 데이터를 쪼개(샤딩) 여러 노드가 나눠 갖게 하고, 복제로 한 노드가 죽어도 서비스가 유지되게 한다.

### 샤딩 — 구체 수치 예제
- 사용자 1억 명을 `user_id` 해시값 기준 64개 샤드로 나누면, 샤드 1개당 평균 약 156만 명이 배정된다. 만약 샤드 키를 국가코드(값이 5개뿐)로 잡으면 데이터가 5개 샤드에만 몰려 64개 노드 중 59개가 거의 놀게 된다 — 값의 종류(카디널리티)가 낮은 컬럼은 샤드 키로 부적합하다. 해시 함수로 고르게 섞는 이유가 여기에 있다.

### 복제와 쿼럼 — 수치로 이해
- 복제 계수 RF=3이면 같은 데이터가 3개 노드에 저장된다. 쓰기 쿼럼 W=2, 읽기 쿼럼 R=2로 설정하면 W+R=4 > RF=3이 되어, 쓰기 쪽 쿼럼과 읽기 쪽 쿼럼이 항상 최소 1개 노드에서 겹치므로 읽을 때 항상 가장 최근 쓰기 결과를 보게 된다(강한 일관성 보장 조건). 노드 1대가 죽어도 나머지 2대로 쿼럼(2/3)을 채울 수 있어 서비스는 계속된다.

### cross-shard 트랜잭션이 비싼 이유 — 구체 예제
- 하나의 트랜잭션이 샤드 A와 샤드 B에 걸친 데이터를 동시에 수정해야 하면, 2단계 커밋(2PC)으로 관련된 모든 샤드가 "준비 완료"를 응답한 뒤에야 동시에 커밋한다. 관련 샤드가 10개면 코디네이터는 10개 노드의 응답을 모두 기다려야 하므로, 하나의 샤드 안에서 끝나는 로컬 트랜잭션(수 ms)보다 지연이 수배에서 수십배까지 늘어난다. 그래서 설계 원칙은 "하나의 비즈니스 단위(Aggregate, 예: 주문+주문항목)가 한 샤드 안에 들어가도록" 샤드 키를 잡는 것이다.

### 흔한 오해
- 분산 DB가 곧 무한 확장을 보장하지 않는다. 샤드 키를 잘못 잡거나, cross-shard 트랜잭션·글로벌 보조 인덱스(여러 샤드를 다 뒤져야 하는 인덱스)가 많으면, 여러 노드를 오가는 네트워크 통신 비용 때문에 오히려 단일 DB보다 느려질 수 있다.

## 연결 개념
- CAP/PACELC 정리 — 분산 DB의 일관성-가용성 트레이드오프를 판단하는 틀
- NewSQL(131) — 분산 DB에 SQL·ACID를 결합한 발전형
- 커서/키셋 페이지네이션(132) — 분산 환경에서 목록 조회 시 흔히 함께 쓰이는 기법

# 📝 【답안용】 시험 답안 템플릿

> 목적: 시험장에서 25분에 그대로 쓰는 답안 양식. 작성방식(추상표현 금지·수치·도식·문제유형 전환)을 엄격히 지킨다.
> 핵심: 분산 DB 답안은 파티셔닝·복제·분산 트랜잭션·CAP 선택을 하나의 구조로 묶어야 함.

## 핵심 인사이트 (3줄 요약)

> 1. **본질**: 분산 DB는 데이터를 여러 노드에 분산·복제하고 단일 논리 DB처럼 제공하는 시스템임.
> 2. **가치**: 저장 용량, 처리량, 지역 지연, 장애 허용을 노드 확장과 복제로 처리함.
> 3. **판단 포인트**: shard key, replication, consensus/2PC, consistency level, cross-shard query 비용이 설계 핵심임.

## 출제 의도 및 답안 포인트

| 출제 의도 | 반드시 짚을 핵심 | 감점 회피 포인트 |
|:---|:---|:---|
| 분산 저장 구조 이해 확인 | partition, replication, coordinator | 단순 백업 DB와 혼동하지 않음 |
| 일관성 트레이드오프 판단 확인 | CAP, quorum, consensus, 2PC | 가용성과 강한 일관성을 동시에 무제한 제공한다고 쓰지 않음 |
| 운영 리스크 확인 | hot shard, split brain, rebalance | 샤드 키와 장애조치 기준 누락 방지 |

> 요약: 분산 DB 문제는 확장 이점보다 일관성·장애·운영 비용 판단이 채점 핵심임.

## Ⅰ. 개요 및 필요성

- 개요: 분산 DB는 여러 노드에 데이터를 배치한 DB이다.
- 배경: 단일 DB는 저장량, 처리량, 지역 지연, 장애 허용에서 한계를 가진다.
- 필요성: 파티셔닝과 복제로 확장성을 확보하되 일관성, 장애 복구, 운영 통제 기준을 함께 설계한다.

---

## Ⅱ. 구조 및 구성요소

```text
Client -> Router/Coordinator -> Shard/Partition -> Replica Group -> Storage
                         +-> Metadata/Catalog
                         +-> Transaction/Consensus
```

| 구성요소 | 역할 | 특이사항 |
|:---|:---|:---|
| Router/Coordinator | 요청 라우팅과 결과 병합 | scatter-gather 비용 |
| Shard/Partition | 데이터 수평 분할 | shard key 분포 필요 |
| Replica Group | 장애 허용과 읽기 분산 | leader/follower, quorum |
| Metadata/Catalog | 샤드 위치와 스키마 관리 | 장애 시 라우팅 영향 |

> 요약: 분산 DB는 라우터, 샤드, 복제그룹, 메타데이터 계층으로 단일 논리 DB를 구성함.

---

## Ⅲ. 동작원리 및 흐름도

```text
Request -> Shard Key Resolve -> Replica Select -> Local Execute -> Consensus/Commit -> Merge Result
```

| 단계 | 처리 내용 | 검증 기준 |
|:---:|:---|:---|
| 1 | 요청에서 shard key 추출 | single-shard 비율 |
| 2 | 메타데이터로 대상 노드 결정 | routing latency |
| 3 | 복제그룹에서 읽기·쓰기 수행 | quorum 충족 여부 |
| 4 | 필요 시 2PC 또는 consensus 수행 | commit latency p95 |
| 5 | cross-shard 결과 병합 | fan-out shard count |

> 요약: 분산 DB는 샤드 위치 결정 후 로컬 실행을 우선하고, 필요 시 분산 합의와 결과 병합을 수행함.

## Ⅳ. 특징

| 구분 | 단일 DB | 분산 DB | 판단 포인트 |
|:---|:---|:---|:---|
| 확장 | 수직 증설 중심 | 수평 분할·복제 | 데이터·요청 증가율 |
| 일관성 | 단일 노드 ACID | quorum, 2PC, consensus | CAP/PACELC 선택 |
| 운영 | 장애 범위 단순 | rebalance, failover, split brain | 자동화·관측성 필요 |

> 요약: 분산 DB는 확장과 가용성을 얻는 대신, 일관성 지연과 운영 복잡도를 감수함.

## Ⅴ. 심화 비교 및 적용 판단

| 비교 축 | 기존/대안 | 본 키워드 | 선택 기준 |
|:---|:---|:---|:---|
| 구조 | 단일 RDB | sharding + replication | 저장량 TB 단위, TPS 증가율 |
| 비용/성능 | 고사양 서버 | 노드 수평 확장 | cross-shard 비율 10% 이하 |
| 운영/위험 | 단일 장애 도메인 | 노드·네트워크 장애 도메인 | quorum, failover 자동화 |

> 요약: 분산 DB는 single-shard 접근 비율이 높고 노드 장애 통제가 가능한 업무에 적합함.

| 리스크 | 원인 | 대응 방안 | 확인 지표 |
|:---|:---|:---|:---|
| Hot Shard | 편향된 shard key | 해시 키, composite key, rebalance | shard별 QPS 편차 |
| Cross-Shard 지연 | 트랜잭션·조인 분산 | aggregate 단위 설계, saga | distributed transaction rate |
| Split Brain | 네트워크 분할 | quorum, fencing token | leader count, election log |

> 요약: 분산 DB 리스크는 키 편향, 분산 트랜잭션, 네트워크 분할을 중심으로 통제함.

| 점검 항목 | 목표 기준 | 측정 방법 |
|:---|:---|:---|
| 라우팅 | single-shard query 90% 이상 | query router log |
| 복제 | replication lag p95 2초 이하 | replica metrics |
| 장애 | failover RTO 5분 이하 | chaos test, drill |

> 요약: 분산 DB는 단일 샤드 비율, 복제 지연, 장애조치 시간으로 운영 적합성을 평가함.

## Ⅵ. 실무 적용 및 결론

**적용 방안 3개 (필수 — 단계별 또는 항목별):**
1. 도메인 aggregate와 접근 패턴을 기준으로 shard key를 정하고, cross-shard transaction 비율을 10% 이하로 관리함.
2. RF=3, quorum read/write, fencing token으로 장애조치와 split brain을 통제함.
3. 리밸런싱, 백업 복구, 장애조치 훈련을 자동화하고 shard별 QPS·용량 편차를 대시보드화함.

**결론 (2줄):**
- 기술사 판단: 단일 DB 한계가 명확하고 shard key가 안정되면 분산 DB, 복잡 조인·강한 ACID 중심이면 단일 RDB 확장을 우선함.
- 향후 방향: NewSQL과 서버리스 분산 DB는 consensus와 자동 리밸런싱을 결합해 운영 부담을 낮추는 방향으로 발전함.
