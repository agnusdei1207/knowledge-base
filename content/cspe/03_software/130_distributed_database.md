# 📖 【암기용】 개념 완전 이해

## 한눈에
- **개요**: 네트워크상에 물리적으로 떨어져 있는 여러 개의 데이터베이스를 논리적으로는 하나의 데이터베이스처럼 사용할 수 있게 만든 시스템이다.
- **왜 필요한가**: 글로벌 서비스(예: 아마존, 넷플릭스)에서 전 세계 사용자가 미국에 있는 하나의 DB 서버에만 접속하면 속도가 너무 느리고 서버가 터진다. 한국 유저는 한국 DB에, 미국 유저는 미국 DB에 접속하게 하면서도 전체 데이터는 하나로 관리되어야 한다.
- **핵심 직관**: 대형 프랜차이즈 도서관과 같다. 서울 지점과 부산 지점에 책이 나뉘어 보관되어 있지만, 사용자는 도서관 앱 하나에서 검색(논리적 단일화)하면 책이 어디에 있든 알아서 찾아준다.

## 핵심 용어 정리

| 용어/표기 | 의미 | 비유·예 |
|:---|:---|:---|
| 투명성 (Transparency) | 내부 분산 구조를 몰라도 사용자가 마치 하나의 DB처럼 쓸 수 있는 성질 | 은행 지점이 달라도 내 통장 앱은 하나인 것 |
| 단편화 (Fragmentation) | 거대한 테이블을 작은 조각으로 나누어 분산시키는 기법 | 전국 주소록을 서울, 경기, 부산 편으로 쪼개기 |
| 할당 (Allocation) | 단편화된 조각들을 어느 지역 노드에 위치시킬지 결정 | 서울 주소록은 서울 서버에, 부산 주소록은 부산에 두기 |
| 2PC (Two-Phase Commit) | 분산된 여러 노드의 트랜잭션을 동시에 반영하거나 취소하는 합의 프로토콜 | 결혼식에서 신랑, 신부 양쪽 다 "네" 해야 결혼 성립 |

## 깊이 이해
- **배경·문제의식**: 중앙집중형 DB는 데이터가 커질수록 하드웨어 증설(Scale-up) 한계에 부딪혔고, 단일 장애점(SPOF) 위험이 있었다. 데이터를 여러 대의 서버에 나누어 저장(Scale-out)하면서도, 사용자에게는 한 대의 DB처럼 보이게 하는 분산 처리 기술이 요구되었다.
- **작동 원리**: 데이터를 지역 특성에 맞게 쪼개고(단편화) 복제하여 각 로컬 DB에 배치한다. 사용자가 쿼리를 던지면, 분산 트랜잭션 관리자(분산 DBMS)가 데이터의 물리적 위치를 파악하여 여러 노드에 쿼리를 나누어 보내고 결과를 취합(병합)해 반환한다.
- **비유**: 회사의 부서별로 엑셀 파일을 따로 관리하지만, 사장님이 "전체 매출 가져와"라고 하면 비서(분산 DBMS)가 각 부서 엑셀을 알아서 합쳐서 한 장짜리 보고서로 보여준다. 사장님(사용자)은 부서별 엑셀 파일 존재를 몰라도 된다.
- **구체 예시**: 글로벌 이커머스에서 사용자 정보 테이블을 아시아 유저(한국 서버)와 북미 유저(미국 서버)로 수평 단편화(행 기준 분할)한다. 마케팅팀에서 `SELECT * FROM User` 쿼리를 날리면, 시스템이 알아서 양쪽 서버에서 데이터를 조회해 와 하나의 결과로 보여준다(위치 투명성).
- **흔한 오해·주의점**: 분산 DB는 장점만 있는 마법이 아니다. 물리적으로 떨어져 있으므로 네트워크 지연이 발생하고, 노드 간 데이터 일관성을 맞추기 위한 트랜잭션(2PC) 오버헤드가 엄청나다. 잘못 설계하면 오히려 중앙집중형보다 훨씬 느려진다.

## 연결 개념
- CAP 정리 — 분산 시스템이 가질 수 없는 완벽한 3가지 속성
- 데이터베이스 샤딩 (Sharding) — 분산 DB의 수평 단편화(Horizontal Fragmentation) 기법
- 분산 트랜잭션 — 서로 다른 DB 간의 원자성(ACID) 보장

## 핵심 인사이트 (3줄 요약)

> 1. **본질**: 네트워크로 연결된 여러 노드에 데이터를 단편화 및 복제하여 분산 저장하면서도, 사용자에게는 논리적으로 단일한 데이터베이스처럼 보이게 하는 시스템이다.
> 2. **가치**: 데이터의 지역성을 높여 로컬 처리 성능을 극대화하고, 다중 노드를 통한 시스템 고가용성 및 무한한 수평 확장(Scale-out)을 제공한다.

| 출제 의도 | 반드시 짚을 핵심 | 감점 회피 포인트 |

## Ⅰ. 개요 및 필요성

- 개요: 물리적으로 여러 위치에 분산된 데이터베이스를 네트워크로 연결하여, 논리적으로는 하나의 통합된 데이터베이스처럼 제공하는 시스템
- 배경: 단일 DBMS의 수직 확장(Scale-up) 한계, 중앙 서버 장애 시 전체 시스템 마비(SPOF), 지역별 데이터 접근 지연(Latency) 발생
- 필요성: 시스템 가용성(Fault Tolerance) 확보, 지역적 트래픽 지역성(Locality) 극대화를 통한 성능 향상, 수평 확장(Scale-out) 아키텍처 필요

---

## Ⅱ. 구조 및 구성요소 (분산 데이터베이스 구성도)

```text
       [ 사용자 / 응용 프로그램 ]
                  | (전역 질의)
[ Global Data Dictionary ] <-> [ 분산 트랜잭션 관리자 (DTM) ]
                                   | (네트워크 분산 질의)
      +----------------------------+-----------------------------+
      V                            V                             V
[ Local DBMS 1 ]             [ Local DBMS 2 ]              [ Local DBMS 3 ]
(단편화/복제 데이터)           (단편화/복제 데이터)            (단편화/복제 데이터)
```

| 구성요소 | 역할 | 특이사항 |
|:---|:---|:---|
| 전역 데이터 사전 (GDD) | 분산된 데이터의 단편화 상태, 위치, 복제 메타데이터 저장 | 투명성 제공의 핵심 참조처 |
| 분산 트랜잭션 관리자 (DTM) | 전역 질의를 로컬 질의로 분할하고 로컬 결과를 취합 | 2PC 등 동시성/회복 제어 |
| 지역 (Local) DBMS | 각 노드에서 물리적 데이터를 관리하고 로컬 쿼리 실행 | 자율성(Autonomy) 보유 |

> 요약: 전역 데이터 사전을 바탕으로 DTM이 컨트롤 타워 역할을 수행하여, 다수의 자율적인 로컬 DBMS를 하나로 묶어낸다.

---

## Ⅲ. 동작원리 및 흐름도

```text
전역 쿼리 입력 -> 위치 파악(GDD) -> 분산 질의 최적화 -> 로컬 실행 및 취합 -> 2PC 커밋
```

- 1단계 [질의 분해]: 사용자가 입력한 전역 SQL을 전역 데이터 사전(GDD)을 참조하여 물리적으로 분할된 여러 로컬 서브 쿼리로 분해
- 2단계 [질의 최적화]: 네트워크 데이터 전송 비용(통신량)을 최소화하도록 데이터가 있는 로컬 DBMS로 연산 푸시다운(Push-down) 수행
- 3단계 [로컬 질의 실행]: 각 노드의 Local DBMS가 병렬로 쿼리를 실행하여 결과 집합 도출
- 4단계 [결과 병합 및 커밋]: DTM이 로컬 결과들을 병합해 응답하며, 갱신 트랜잭션의 경우 2PC(Two-Phase Commit)로 원자성(All-or-Nothing) 보장

> 요약: 쿼리를 쪼개어 해당 지역으로 보내 연산하게 하고, 그 결과를 네트워크로 취합하여 단일 응답과 트랜잭션 원자성을 달성한다.

---

## Ⅳ. 특징 (6대 투명성 - 핵심 조건)

- 분할(단편화) 투명성: 데이터가 여러 조각으로 쪼개져 있음을 사용자가 인식하지 못함 (가장 높은 수준의 투명성)
- 위치 투명성: 데이터의 물리적인 서버/지역 위치를 몰라도 테이블명만으로 접근 가능
- 지역사상/중복(복제) 투명성: 지역 DBMS의 종류를 모르며, 동일 데이터가 복제되어 있어도 갱신 시 모두 동기화됨을 보장
- 장애/병행 투명성: 특정 노드 장애 시 타 노드 대체, 다수 트랜잭션 동시 수행 시에도 이상 현상 없음

> 요약: 투명성(Transparency)은 분산 DB의 가장 큰 목적이자 성공 요인으로, 이를 완벽히 지원할수록 분산 오버헤드는 증가한다.

## Ⅴ. 심화 비교 및 적용 판단 (단편화 기법 비교)

| 비교 축 | 수평 단편화 (Horizontal) | 수직 단편화 (Vertical) | 선택 기준 (데이터 접근 패턴) |
|:---|:---|:---|:---|
| 분할 기준 | 특정 튜플(행) 단위 분할 (예: 지사별) | 특정 속성(열) 단위 분할 (예: 부서별) | 레코드의 지역적 독립성 여부 |
| 재조립 연산 | 합집합 연산 (UNION) 필요 | 조인 연산 (JOIN) 필요 | 복원 시 연산 비용 부담 |
| 적용 사례 | 전국 고객 테이블을 지역별 노드 배치 | 직원 테이블을 인사팀용/재무팀용 분리 | 샤딩(Sharding), 컬럼형 분산 |

> 요약: 데이터의 특정 속성만 자주 조회하면 수직으로, 데이터 건수 자체가 방대하고 지역성이 크면 수평으로 단편화한다.

**리스크·대응 (기본은 불릿):**
- 분산 교착상태(Deadlock): 여러 노드에 걸쳐 락(Lock)을 획득하는 과정에서 글로벌 데드락 발생 → Wait-Die / Wound-Wait 타임아웃 기법 적용 (지표: 트랜잭션 롤백 비율)
- 2PC 병목 현상: 코디네이터 장애 시 참여 노드들이 무한 대기(Blocking) 상태 빠짐 → 3PC(Three-Phase Commit) 도입 또는 Saga 패턴 기반 최종 일관성 아키텍처로 우회

**도입 후 점검 지표 (기본은 불릿):**
- 성능/효율: 분산 쿼리의 네트워크 데이터 전송량(Bytes) 최소화 여부 (데이터가 아닌 쿼리를 노드로 이동)
- 품질/운영: 특정 노드 장애 시 전체 시스템 파급 영향(Blast Radius) 격리 수준 확인

## Ⅵ. 실무 적용 및 결론

**적용 방안 3개:**
1. 대규모 서비스 데이터베이스 샤딩(Sharding): RDBMS의 수평 단편화 기법을 응용하여 유저 ID를 해싱, 트래픽을 수십 대의 분산 DB(Shard)로 분배하여 부하 해소
2. 글로벌 데이터 다중 리전 복제 (Multi-Region Replication): Active-Active 형태의 분산 DB를 구축하여 북미, 유럽, 아시아 유저가 각자의 로컬 DB에 고속 접근하도록 지역성 확보
3. 분산 트랜잭션 처리 최적화: 강한 결합의 2PC로 인한 마이크로서비스 병목을 해소하기 위해, 이벤트 드리븐 기반의 보상 트랜잭션(Saga Pattern)으로 최종 일관성 지향 설계

**결론 (2줄):**
- 기술사 판단: 분산 데이터베이스는 시스템 가용성과 성능 한계를 극복하는 근본 해결책이나, 투명성을 보장하기 위한 분산 제어 오버헤드가 크므로 데이터 지역성(Locality) 극대화 설계가 선행되어야 한다.
- 향후 방향: 최근에는 RDBMS의 강한 정합성(SQL)과 NoSQL의 무한 확장성(분산)을 결합한 NewSQL(Google Spanner, CockroachDB) 아키텍처로 발전하며 기존의 한계를 넘어서고 있다.
