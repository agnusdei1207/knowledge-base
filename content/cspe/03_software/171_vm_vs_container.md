# 📖 【암기용】 개념 완전 이해

> 목적: VM과 컨테이너 차이를 처음 보는 사람도 완벽히 이해하게 만든다. 시험 답안 양식이 아니라, 이해를 위한 친절한 설명이다.

## 한눈에
- **개요**: **가상화(Virtualization)** 기법을 하드웨어 계층에서 하느냐(**하드웨어 가상화** = VM), OS 커널 계층에서 하느냐(**OS 가상화** = 컨테이너)로 나눈 비교 개념이다.
- **왜 필요한가**: 한 물리 서버에서 여러 업무를 나눠 돌리려면 격리 강도, 자원 밀도, 배포 속도, 운영 비용 사이의 균형이 필요하다. 어느 하나가 항상 우월하지 않고 요구 조건에 따라 선택이 갈린다.
- **핵심 직관**: VM은 집마다 기초 공사와 배관까지 따로 두는 것이고, 컨테이너는 한 건물 안에서 방과 출입 권한만 나누는 것이다.

## 핵심 용어 정리 (내부에 등장하는 것들)

| 용어 | 의미 | 비유 |
|:---|:---|:---|
| 가상화(Virtualization) | 물리 자원을 논리적으로 나눠 여러 실행 환경을 만드는 기술 전체 — VM·컨테이너의 상위 개념 | 큰 건물을 여러 용도로 나눠 쓰는 것 |
| 하드웨어 가상화 | 하이퍼바이저가 CPU·메모리·디스크·NIC 자체를 가상 장치로 나눠줌 — VM 방식 | 땅을 나눠 집을 각각 지음 |
| OS 가상화 | 하나의 커널 위에서 프로세스·네트워크·파일시스템만 격리 — 컨테이너 방식 | 한 건물에서 방만 나눔 |
| 하이퍼바이저(Hypervisor) | VM에 가상 하드웨어를 제공하고 스케줄링하는 계층 | 건물 관리사무소 |
| Type-1(Bare-metal) 하이퍼바이저 | 물리 서버에 직접 설치(ESXi, KVM, Hyper-V, Xen) | 관리사무소가 건물주 직속 |
| Type-2(Hosted) 하이퍼바이저 | 이미 떠 있는 Host OS 위의 애플리케이션으로 설치(VirtualBox, VMware Workstation) | 세입자가 임시로 차린 관리실 |
| Guest OS | VM 안에 통째로 설치되는 별도의 완전한 OS | 각 집마다 독립된 전체 살림 |
| Host OS | 컨테이너들이 공유하는 물리 서버의 커널 | 건물 전체의 공용 기초·배관 |
| namespace / cgroup | 컨테이너가 프로세스를 격리(namespace)하고 자원을 제한(cgroup)하는 커널 기능 | 방문 잠금(namespace) + 전기 사용량 계약(cgroup) |

## 깊이 이해

### 배경 — 서버를 나눠 쓰는 두 갈래 접근
- 물리 서버 한 대를 여러 팀·업무가 나눠 쓰려는 요구는 오래됐다. 첫 번째 답은 "하드웨어 자체를 가짜로 여러 벌 복제"하는 것(하이퍼바이저·VM)이었고, 두 번째 답은 "커널은 하나만 두고 그 위의 프로세스만 서로 안 보이게" 하는 것(namespace·cgroup·컨테이너)이었다. 격리 강도와 오버헤드가 정반대로 갈리는 두 접근이다.

### VM 구조 — 수치로 이해
- Type-1 하이퍼바이저(ESXi, KVM 등)는 물리 서버에 직접 설치돼 오버헤드가 작고, Type-2(VirtualBox 등)는 Host OS 위의 앱으로 설치돼 개발용으로 주로 쓴다.
- VM 하나는 완전한 Guest OS를 포함한다. 최소 구성 Linux Guest OS도 약 1~2GB, Windows Guest OS는 커널·서비스만으로 수 GB를 차지한다. 부팅은 BIOS/UEFI POST → 부트로더 → 커널 로드 → OS 초기화 → 서비스 기동까지 전체 OS 부트 사이클을 거치므로 수십 초에서 수 분이 걸린다.

### 컨테이너 구조 — 수치로 이해
- 컨테이너는 별도 커널을 부팅하지 않고 이미 떠 있는 Host OS 커널 위에서 namespace로 격리된 프로세스 하나를 fork/exec 한다. 그래서 이미지 크기는 애플리케이션과 의존성만 담아 수십~수백 MB 수준(예: `python:3.12-slim` 약 150MB)이고, 시작 시간도 커널 부팅 과정이 없어 1초 미만~수 초에 그친다.

### 밀도 비교 — 워크드 예제
- 64GB RAM 물리 서버를 가정하자. VM 방식으로 각 VM에 Guest OS 오버헤드 포함 4GB씩 배정하면 하이퍼바이저 자체 오버헤드(약 2GB)를 뺀 62GB에서 약 15대의 VM을 띄울 수 있다.
- 같은 애플리케이션을 컨테이너로 배치하면 Guest OS가 없으므로 컨테이너 하나당 실질 메모리는 앱 자체 사용량(예: 200MB~1GB)만 차지한다. 같은 64GB에서 앱당 500MB로 잡으면 산술적으로 100개 이상을 띄울 수 있다 — VM 대비 자원 밀도가 훨씬 높다.

### 언제 무엇을 쓰나 — 판별 원리
- 다중 테넌트 격리가 법적·보안적으로 강해야 하거나(금융·의료 규제), 서로 다른 OS·커널 버전이 함께 필요하거나, 커널 취약점이 테넌트 간에 넘어가면 안 되는 경우 → **VM**.
- 배포 빈도가 높고, 같은 OS 계열에서 마이크로서비스 단위로 자주 배포·수평 확장해야 하는 경우 → **컨테이너**.
- 실무에서는 대립이 아니라 결합이 표준이다. IaaS의 VM 노드 위에 Kubernetes를 얹고, 그 안에서 컨테이너가 도는 구조를 가장 널리 쓴다.

### 비유와 흔한 오해
- **비유**: VM은 개인 주택 여러 채를 짓는 것과 같아 기초·배관까지 전부 따로 두므로 분리 비용이 크고, 컨테이너는 같은 아파트 건물 안에서 세대만 나누는 것과 같아 공용 설비(커널)를 함께 쓰되 출입문(namespace)만 따로 잠근다.
- **오해**: 컨테이너가 VM을 완전히 대체한다는 것은 사실이 아니다. 컨테이너는 호스트 커널을 공유하므로 VM만큼 강한 격리 경계를 제공하지 않는다. 그래서 실무에서는 VM(강한 격리, 노드 단위) 위에 컨테이너(빠른 배포, 앱 단위)를 얹는 혼합 구조가 표준이다.

## 연결 개념
- 하이퍼바이저 - Type 1/Type 2 방식으로 하드웨어 자원 가상화
- 컨테이너 런타임 - 이미지 실행과 namespace/cgroup 적용
- 쿠버네티스 - 컨테이너 배포, 스케줄링, 복구 자동화

# 📝 【답안용】 시험 답안 템플릿

> 목적: 시험장에서 25분에 그대로 쓰는 답안 양식. 작성방식(추상표현 금지·수치·도식·문제유형 전환)을 엄격히 지킨다.
> 핵심: VM과 컨테이너는 어느 하나의 우열이 아니라 격리 강도, 시작 시간, 운영 단위, 규제 요구에 따라 선택하는 구조임.

## 핵심 인사이트 (3줄 요약)

> 1. **본질**: VM은 하드웨어 가상화, 컨테이너는 OS 커널 공유 기반 프로세스 격리 기술임.
> 2. **가치**: VM은 강한 격리와 이기종 OS, 컨테이너는 이미지 단위 배포와 고밀도 실행에 적합함.
> 3. **판단 포인트**: 선택 기준은 격리 수준, 시작 시간, 패치 범위, 운영 자동화, 규제 통제임.

## 출제 의도 및 답안 포인트

| 출제 의도 | 반드시 짚을 핵심 | 감점 회피 포인트 |
|:---|:---|:---|
| 가상화 계층 구분 확인 | Hypervisor vs namespace/cgroup | 컨테이너를 경량 VM으로만 설명 |
| 운영 선택 기준 확인 | 격리, 밀도, 배포, OS 호환성 | 컨테이너가 항상 우월하다고 단정 |
| 클라우드 전환 판단 확인 | VM, Container, Kubernetes 조합 | 보안 경계와 커널 공유 리스크 누락 |

> 요약: 이 문제는 구조 차이보다 업무 조건별 배치 전략을 제시하는 판단형 답안이 필요함.

## Ⅰ. 개요 및 필요성

- 개요: VM은 하드웨어 가상화, 컨테이너는 OS 가상화임.
- 배경: 서버 통합과 클라우드 배포에서는 격리 강도와 배포 속도 요구가 함께 발생한다.
- 필요성: 격리 경계, 시작 시간, 이미지 크기 기준으로 레거시 이전, MSA 배포, 규제 시스템 분리를 설계한다.

---

## Ⅱ. 구조 및 구성요소

```text
Physical Server -> Hypervisor -> Guest OS -> App
Physical Server -> Host OS -> Container Runtime -> Container App
  / VM: hardware virtualization
  / Container: OS kernel sharing
```

| 구성요소 | VM | 컨테이너 |
|:---|:---|:---|
| 격리 계층 | Hypervisor, Guest OS | namespace, cgroup, seccomp |
| 실행 단위 | VM image, OS 포함 | container image, app dependency 포함 |
| 운영 도구 | vSphere, KVM, Hyper-V | containerd, CRI-O, Kubernetes |

> 요약: VM은 게스트 OS를 포함하고 컨테이너는 호스트 커널을 공유하므로 격리 경계와 운영 단위가 다름.

---

## Ⅲ. 동작원리 및 흐름도

```text
요구 식별 -> 격리 수준 판단 -> 실행 계층 선택 -> 자원 할당 -> 배포/관측
  / 강한 격리 필요 -> VM
  / 고밀도 배포 필요 -> Container
```

| 단계 | 처리 내용 | 검증 기준 |
|:---:|:---|:---|
| 1 | 업무 OS, 라이브러리, 규제 요구 식별 | OS 종속성, 감사 요구 |
| 2 | VM 또는 컨테이너 실행 계층 선택 | 격리 경계, 시작 시간 |
| 3 | CPU, Memory, Storage quota 설정 | vCPU, cgroup limit |
| 4 | 이미지 배포와 관측 구성 | image scan, log/metric |

> 요약: VM과 컨테이너 선택은 기술 선호가 아니라 격리 요구와 배포 운영 기준으로 결정함.

## Ⅳ. 특징

| 구분 | VM | 컨테이너 | 수치/판단 포인트 |
|:---|:---|:---|:---|
| 시작 시간 | 수십 초~분 | 초 단위 | autoscaling 반응 |
| 격리 | 게스트 OS 단위 | 커널 공유 프로세스 단위 | 다중 테넌트 |
| 이미지 크기 | GB 단위 | MB~수백 MB | registry 비용 |
| 적용 대상 | 레거시, 이기종 OS | MSA, CI/CD | 변경 빈도 |

> 요약: VM은 격리와 호환성, 컨테이너는 배포 단위와 자원 밀도에서 선택 가치가 갈림.

## Ⅴ. 심화 비교 및 적용 판단

| 구분 | 기존/대안 | 본 키워드 | 선택 기준 |
|:---|:---|:---|:---|
| 구조 | 물리 서버 전용 배치 | VM/Container 통합 배치 | 서버 사용률 20% 이하 개선 대상 |
| 비용/처리 | VM 중심 운영 | 컨테이너 오케스트레이션 | 배포 빈도 일 1회 이상 |
| 운영/위험 | OS 패치 단위 큼 | 이미지·런타임 패치 단위 | CVE 대응 SLA 7일 |

> 요약: 배포 빈도와 자원 밀도 요구가 높으면 컨테이너, OS 격리와 규제 경계가 우선이면 VM을 선택함.

| 리스크 | 원인 | 대응 방안 | 확인 지표 |
|:---|:---|:---|:---|
| 커널 공유 취약점 | 컨테이너가 호스트 커널 의존 | seccomp, AppArmor, gVisor | critical CVE 0건 |
| VM 자원 낭비 | Guest OS 중복 | right sizing, template 표준화 | CPU 사용률 40~70% |
| 운영 복잡도 | VM과 컨테이너 도구 병행 | IaC, CMDB, 통합 관측 | 변경 실패율 5% 이하 |

> 요약: 혼합 운영의 리스크는 격리 경계와 패치 단위가 달라지는 지점에서 발생함.

| 점검 항목 | 목표 기준 | 측정 방법 |
|:---|:---|:---|
| 배포 시간 | 컨테이너 5분 이하, VM 30분 이하 | CI/CD 로그 |
| 자원 사용률 | CPU 40~70%, Memory OOM 0건 | APM, cAdvisor |
| 보안 통제 | image scan critical 0건, CIS benchmark | Trivy, kube-bench |

> 요약: 도입 후 배포 시간, 자원 사용률, 취약점 잔여 건수로 선택 결과를 검증함.

## Ⅵ. 실무 적용 및 결론

**적용 방안 3개 (필수 - 단계별 또는 항목별):**
1. 레거시·상용 패키지: OS 종속성과 라이선스 제약이 있는 업무는 VM으로 분리하고 vCPU/Memory right sizing 적용
2. MSA·배치 업무: Dockerfile 표준, OCI image, Kubernetes Deployment로 배포 시간을 5분 이하로 관리
3. 보안 경계: VM은 네트워크 세그먼트, 컨테이너는 seccomp·AppArmor·readOnlyRootFilesystem을 기본 정책으로 적용

**결론 (2줄):**
- 기술사 판단: 강한 격리와 이기종 OS는 VM, 빈번한 배포와 수평 확장은 컨테이너를 선택함
- 향후 방향: VM 기반 IaaS 위에 Kubernetes를 운영하는 혼합 구조가 기업 클라우드 전환의 표준 패턴이 됨

| 요구사항 명시형 | "비교하시오", "전환 방안을 제시하시오" | 업무 조건별 선택 흐름 | 레거시/클라우드/보안 경계 선택 기준 |
