# 📖 【암기용】 개념 완전 이해

> 목적: APM을 모니터링 도구명이 아니라 애플리케이션 병목을 추적하는 관측 체계로 이해하게 만든다.

## 한눈에
- **개요**: APM(Application Performance Management)은 **관측성(Observability)**의 한 실행 체계로, 애플리케이션 내부의 요청 흐름을 Trace·Metric·Log로 수집해 지연·오류의 원인 지점을 찾는다.
- **왜 필요한가**: MSA에서 요청 하나가 5~6개 서비스를 거치면 어느 서버 CPU를 봐도 전체 중 어디가 느린지는 보이지 않는다. 요청을 끝까지 따라가야 원인을 좁힐 수 있다.
- **핵심 직관**: 병원 종합검진처럼 심전도(Trace)·혈압(Metric)·혈액검사(Log)를 함께 봐야 어디가 아픈지 안다.

## 핵심 용어 정리 (내부에 등장하는 것들)

| 용어 | 의미 | 비유 |
|:---|:---|:---|
| 관측성 (Observability, 상위 개념) | 시스템 외부에서 관찰되는 신호(Trace·Metric·Log)만으로 내부 상태를 추론할 수 있는 성질 | 계기판만 보고 엔진 내부 상태를 짐작하기 |
| Trace | 하나의 요청이 여러 서비스를 거치며 남기는 전체 경로 기록 | 택배 하나의 전체 이동 이력 |
| Span | Trace를 구성하는 개별 처리 단위(서비스 호출·DB 쿼리 등)의 시작~끝 기록 | 택배가 거친 물류센터 한 곳에서의 체류 기록 |
| trace id | 요청이 여러 서비스를 넘어갈 때도 동일하게 유지되는 식별자 | 택배 송장번호 |
| Metric | 지연·처리량·오류율 등 시계열로 집계되는 수치 지표 | 시간대별 평균 배송 소요시간 그래프 |
| Log | 특정 시점에 발생한 이벤트의 텍스트 기록 | 물류센터 작업 일지 |
| Agent/SDK (OpenTelemetry) | 애플리케이션 코드에 심어 요청·쿼리·오류를 자동 수집하는 계측기 | 택배 상자에 부착된 GPS 센서 |
| Collector | 여러 Agent가 보낸 Trace/Metric/Log를 모아 가공·저장소로 전달하는 중계자 | 물류 데이터를 모으는 중앙 관제센터 |
| 샘플링 (Sampling) | 모든 요청을 다 저장하지 않고 일부(또는 이상 신호가 있는 것)만 골라 저장하는 정책 | 모든 택배 대신 지연 의심 건만 정밀 조사 |
| SLO / 오류 예산 (Error Budget) | 목표 가용성(SLO) 대비 허용되는 장애 시간·오류 비율의 한도 | 한 달간 허용된 지각 총량 |
| MTTR (Mean Time To Repair) | 장애 발생부터 복구까지 걸리는 평균 시간 | 사고 발생 후 정상 운행까지 걸리는 시간 |

## 깊이 이해

### 왜 APM이 필요해졌나 (배경)
- 단일 서버 시절에는 서버 로그 하나만 보면 원인을 알 수 있었다. MSA·클라우드에서는 주문 요청 하나가 API 게이트웨이 → 주문 서비스 → 재고 서비스 → 결제 서비스 → 메시지 큐 → 알림 서비스처럼 5~6개 서비스를 순차·병렬로 거친다. "느리다"는 신고가 오면 서비스마다 로그를 열어 시간을 맞춰보는 것은 사실상 불가능하다. 그래서 요청을 끝까지 하나로 꿰어 보는 도구가 필요해졌다.

### trace id가 요청을 꿰는 원리
- 요청이 API 게이트웨이에 들어오는 순간 고유한 trace id가 생성되고, 이후 호출하는 모든 서비스의 HTTP 헤더(또는 메시지 attribute)에 이 id가 실려 전파된다. 각 서비스는 자신이 처리한 구간을 span으로 기록하면서 같은 trace id를 태그로 붙인다.
- 수집 후에는 같은 trace id를 가진 span들을 시간순으로 모아 하나의 트리(Trace)로 재구성한다. 예: 주문 API 전체 p95가 1.2초일 때 span을 뜯어보면 API 게이트웨이 50ms + 주문 서비스 로직 50ms + 결제 API 호출 700ms + DB 쿼리 300ms + 메시지 발행 100ms로 나뉜다. 700ms를 차지하는 결제 API 호출이 병목이라는 게 한 번에 드러난다 — 결제사 응답 지연이나 타임아웃 설정, fallback 로직을 우선 점검해야 한다는 뜻이다.

### 샘플링 — 다 저장하면 왜 안 되나 (수치)
- 초당 1,000건 요청을 모두 Trace로 저장하면 하루(86,400초) 기준 약 8,640만 건의 Trace가 쌓여 저장 비용과 조회 성능이 감당되지 않는다.
- 그래서 정상 응답은 1%만 저장(head sampling)하고, 오류가 나거나 지연이 임계치(예: 1초)를 넘는 요청은 100% 저장(tail sampling)하는 정책을 쓴다. 저장량은 크게 줄이면서도 봐야 할 사고 건은 놓치지 않는다.

### SLO와 오류 예산 — 숫자로 이해
- 가용성 목표(SLO)를 99.9%로 잡으면 허용되는 장애 시간은 한 달(43,200분) 중 0.1% = 약 43.2분이다. 이 43.2분이 오류 예산이다.
- 오류 예산을 다 쓰기 전에 미리 경고하기 위해 "번 레이트(burn rate)"를 본다. 예: 1시간 동안 오류율이 평소의 10배로 치솟으면 이 속도로는 오류 예산이 하루 안에 소진된다는 계산이 나와 즉시 경보를 울린다. 단순히 "오류율 5% 넘으면 경보"보다 정교해 불필요한 경보 피로를 줄인다.

### MTTR을 줄이는 실제 흐름
- 장애 신고 → APM 대시보드에서 어떤 API의 p95가 튀었는지 확인(1분) → 해당 API의 Trace를 열어 어느 span이 느려졌는지 확인(2분) → 최근 배포 이력과 시간을 대조해 원인 배포를 특정(2분) → 롤백 또는 fallback 적용(수 분). 이 흐름이 갖춰지면 MTTR을 30분 이하로 관리할 수 있다. Trace가 없으면 로그를 서비스별로 뒤지는 데만 수십 분이 걸린다.

### 흔한 오해
- APM은 장애가 터진 뒤에 켜보는 대시보드가 아니다. 평상시 p95 추이를 기준선으로 잡아두고 배포 직후 30분간 자동으로 회귀(regression)를 비교하는 등 상시 운영 체계로 붙여야 가치가 난다.
- Agent 설치만으로 APM이 완성되지 않는다. trace id가 비동기 메시지 큐를 건널 때 끊기지 않게 전파 규칙을 표준화하지 않으면 중간에 끊긴 "반쪽 Trace"가 된다.

## 연결 개념
- Observability(관측성) — Trace·Metric·Log 세 신호로 시스템 내부 상태를 추론하는 상위 개념, APM은 그 응용
- SRE — SLO·오류 예산을 운영 의사결정(배포 중단 여부 등)에 쓰는 조직 원칙
- 313 부하·스트레스·소크 테스트 — 성능 시험 중 병목 구간을 APM Trace로 실시간 확인

# 📝 【답안용】 시험 답안 템플릿

> 목적: APM 구성요소, 수집 흐름, 운영 판단 기준을 시험 답안으로 전개한다.
> 핵심: APM은 로그 수집이 아니라 요청 단위 추적과 SLO 기반 경보 체계다.

## 핵심 인사이트 (3줄 요약)

> 1. **본질**: APM은 애플리케이션 요청의 Trace, Metric, Log를 수집·상관분석해 지연·오류 원인을 찾는 성능 관리 체계다.
> 2. **가치**: p95 지연, error rate, DB wait, 외부 API time-out을 서비스별로 분리해 MTTR 30분 이하 같은 운영 목표를 지원한다.
> 3. **판단 포인트**: Agent 설치 여부보다 trace id 전파, 샘플링 정책, SLO 경보, 배포 이력 연동이 핵심이다.

## 출제 의도 및 답안 포인트

| 출제 의도 | 반드시 짚을 핵심 | 감점 회피 포인트 |
|:---|:---|:---|
| 관측성 구성 이해 확인 | Trace·Metric·Log, agent, collector | 서버 모니터링과 혼동 |
| 장애 원인 분석 역량 확인 | span, DB query, external call, error rate | 평균 지연만 제시 |
| 운영 적용 판단 확인 | SLO, alert, dashboard, 배포 이력 | 제품명 중심 답안 |

> 요약: 이 문제는 APM 도구 소개가 아니라 요청 단위 병목 분석과 운영 의사결정 연결을 요구한다.

## Ⅰ. 개요 및 필요성

- 개요: 애플리케이션 성능 관측 체계
- 배경: MSA와 클라우드 환경은 요청 경로가 여러 서비스로 분산되어 로그만으로 장애 위치를 찾기 어려움
- 필요성: Metrics, Logs, Traces와 SLO 알람으로 지연·오류·자원 사용률을 수집해 병목 구간을 식별해야 함

---

## Ⅱ. 구조 및 구성요소

```text
Client Request -> App Agent -> Trace/Metric/Log Collector -> Storage -> Dashboard/Alert
                                      / DB Query / External API / Error Event
```

| 구성요소 | 역할 | 특이사항 |
|:---|:---|:---|
| Agent/SDK | 요청·메서드·SQL 지연 수집 | OpenTelemetry, Java Agent |
| Collector | Trace·Metric·Log 수신·가공 | 샘플링, 필터링, 태그 표준 |
| Storage/Index | 시계열·Trace 검색 저장 | 보관 기간, 카디널리티 관리 |
| Dashboard/Alert | SLO, 오류율, p95 지연 표시 | 경보 피로 방지 필요 |

> 요약: APM은 수집 Agent, Collector, 저장소, 대시보드·경보가 요청 단위 관측을 수행하는 구조다.

## Ⅲ. 동작원리 및 흐름도

```text
요청 수신 -> Trace ID 생성 -> Span 수집 -> Metric 집계 -> Alert/분석
```

| 단계 | 처리 내용 | 검증 기준 |
|:---:|:---|:---|
| 1 | 요청 진입 시 trace id 생성·전파 | HTTP header, message attribute |
| 2 | 서비스·DB·외부 호출 span 기록 | span duration, error tag |
| 3 | 지표 집계와 로그 상관분석 | p95, error rate, throughput |
| 4 | SLO 위반 경보 발송 | burn rate, threshold |
| 5 | 원인 구간과 배포 변경 이력 확인 | release tag, owner mapping |

> 요약: APM은 요청을 trace id로 연결하고 span별 지연을 쪼개 병목과 오류 원인을 찾는다.

## Ⅴ. 심화 비교 및 적용 판단

| 비교 축 | 기존/대안 | 본 키워드 | 선택 기준 |
|:---|:---|:---|:---|
| 구조 | 로그·메트릭 분리 | Trace 중심 상관분석 | MSA 호출 깊이 |
| 비용/성능 | 전체 요청 수집 | 샘플링·tail sampling | 저장 비용과 누락 위험 |
| 운영/위험 | 임계값 경보 | SLO burn rate 경보 | 경보 피로와 장애 영향도 |

> 요약: APM은 모든 데이터를 많이 모으는 방식보다 SLO와 샘플링 정책을 설계하는 방식이 필요하다.

| 리스크 | 원인 | 대응 방안 | 확인 지표 |
|:---|:---|:---|:---|
| 누락 Trace | 비동기·메시지 trace id 미전파 | header/attribute 표준화 | trace coverage 95% 이상 |
| 저장 비용 증가 | 고카디널리티 tag 남용 | tag whitelist, sampling | GB/day, series count |
| 경보 피로 | 낮은 임계값 경보 과다 | SLO burn rate 적용 | alert per service |

> 요약: APM 운영 리스크는 Trace 전파율, tag 관리, SLO 기반 경보로 통제한다.

| 점검 항목 | 목표 기준 | 측정 방법 |
|:---|:---|:---|
| 지연 | 주요 API p95 300ms 이하 | APM percentile |
| 오류 | error rate 0.1% 이하 | 5xx, exception count |
| 복구 | MTTR 30분 이하 | incident timeline |

> 요약: APM 성과는 지연·오류·복구 시간 지표가 서비스별로 관측되는지로 판단한다.

## Ⅵ. 실무 적용 및 결론

**적용 방안 3개:**
1. OpenTelemetry 기반 Trace 표준 수립: trace id, service.name, deployment.version, user journey tag 정의
2. SLO 대시보드 구성: availability 99.9%, p95 300ms, error rate 0.1%를 서비스별 burn rate로 표시
3. 배포와 연동: CI/CD release tag를 Trace에 주입하고 배포 후 30분간 p95·error rate 회귀 여부 확인

**결론 (2줄):**
- 기술사 판단: 단일 서버 애플리케이션은 메트릭 중심, MSA·외부 API 연계 업무는 Trace 중심 APM을 우선 적용한다
- 향후 방향: APM은 OpenTelemetry 표준과 AIOps 이상 탐지로 확장되어 장애 원인 후보를 자동 제시하는 체계로 발전한다
