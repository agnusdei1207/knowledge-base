# 📖 【암기용】 개념 완전 이해

> 목적: 샤딩을 처음 보는 사람도 완전히 이해하게 만든다. 시험 답안 양식이 아니라, 이해를 위한 설명이다.

## 한눈에
- **개요**: 샤딩(Sharding)은 동일한 스키마를 가진 데이터를 **샤드 키** 기준으로 여러 개의 독립된 DB 노드(서버)에 나누어 저장하는 **수평 확장(Horizontal Scaling)** 아키텍처다.
- **왜 필요한가**: 단일 DB 서버는 CPU, IOPS, 저장 공간에 물리적 상한이 있다. 스케일업(더 좋은 서버로 교체)만으로는 언젠가 한계에 부딪히므로, 데이터를 여러 서버로 쪼개 쓰기·저장 부하 자체를 나눠야 한다.
- **핵심 직관**: 계산대 하나에 모든 손님을 세우지 않고, 손님 번호 끝자리 같은 규칙으로 여러 계산대에 미리 배정하는 것과 같다. 문제는 "번호가 없는 손님"(샤드 키 없는 조회)이 오면 모든 계산대를 다 확인해야 한다는 점이다.

## 핵심 용어 정리 (내부에 등장하는 것들)

| 용어 | 의미 | 비유 |
|:---|:---|:---|
| 샤딩(Sharding) | 데이터를 여러 물리 노드로 수평 분산 저장하는 것 — 이 개념 자체 | 계산대를 여러 대로 늘려 손님을 분산 |
| 샤드 키(Shard Key) | 어느 노드에 데이터를 둘지 정하는 기준 컬럼(user_id, tenant_id 등) | 손님을 어느 계산대로 보낼지 정하는 번호표 규칙 |
| 샤드 맵(Shard Map) | 샤드 키(또는 그 범위·해시 슬롯)와 실제 노드를 연결한 매핑 테이블 | "몇 번대 손님은 몇 번 계산대"라고 적힌 안내판 |
| 라우터(Router) | 들어온 요청에서 샤드 키를 뽑아 샤드 맵을 보고 올바른 노드로 전달하는 계층 | 안내판을 보고 손님을 계산대로 안내하는 직원 |
| 스캐터-개더(Scatter-Gather) | 샤드 키가 없는 요청을 모든 샤드에 흩뿌려(scatter) 각각 조회한 뒤 결과를 모으는(gather) 방식 | 번호표 없는 손님을 찾으러 모든 계산대에 물어보고 다니기 |
| 리샤딩(Resharding) | 샤드 수를 늘리거나 매핑 규칙을 바꿔 데이터를 재배치하는 작업 | 계산대 수를 늘리며 손님 배정 규칙을 다시 짜는 것 |
| Cross-shard Transaction | 하나의 트랜잭션이 여러 샤드에 걸친 데이터를 함께 갱신해야 하는 상황 | 한 주문이 계산대 두 곳에 걸쳐 처리돼야 하는 상황 — 원자성 보장이 어려움 |
| 핫스팟(Hotspot)·Skew | 특정 샤드 키(대형 고객 등)에 트래픽이 몰려 그 샤드만 과부하되는 현상 | 유독 한 계산대에만 줄이 길게 서는 것 |

## 깊이 이해

### 왜 필요한가 — 숫자로 보는 단일 노드의 한계
- 서비스가 커지며 단일 DB writer의 CPU 사용률이 지속적으로 70% 이상, 쓰기 p95 지연이 200ms를 넘는 상태가 이어진다고 하자. 더 큰 서버로 스케일업해도 언젠가 한 대가 감당할 수 있는 IOPS·CPU의 물리적 상한에 부딪힌다. 이때 데이터를 여러 대의 writer로 나누면, 이론상 N대에 나누면 노드당 부하는 1/N로 준다.

### 샤드 키 매핑 — 해시 방식의 구체 예
- `user_id % 16`으로 16개 샤드를 구성하면, user_id가 결정되는 순간 어느 샤드로 갈지 계산으로 즉시 정해진다(별도 조회 없이도 계산 가능). 이 방식은 대체로 균등하게 분산되지만, **행 개수가 균등해도 부하가 균등하다는 뜻은 아니다** — 예를 들어 특정 대형 고객 하나가 전체 쓰기 트래픽의 30%를 차지하면, 그 고객이 속한 샤드 하나만 과부하(핫스팟)에 빠진다. 이럴 땐 그 고객만 별도 "가상 샤드"로 분리하는 등의 추가 설계가 필요하다.

### 샤드 키 있는 요청 vs 없는 요청 — 비용 차이
- 요청에 샤드 키(예: `WHERE user_id = 12345`)가 포함되면, 라우터가 계산 한 번으로 정확히 1개 샤드에만 질의해 로컬 트랜잭션으로 끝난다.
- 반대로 샤드 키가 없는 요청(예: "이메일이 x인 사용자 찾기"처럼 검색 조건이 다른 컬럼)은 어느 샤드에 있는지 알 수 없어 **모든 샤드에 동시에 질의(scatter)**하고 결과를 모아야(gather) 한다. 샤드가 16개면 요청 1건이 16건의 하위 질의로 증폭되고, 전체 응답 시간은 가장 느린 샤드의 응답 시간에 좌우된다(tail latency 문제). 그래서 설계 초기에 "가장 빈번한 조회 조건"을 샤드 키로 골라야 한다.

### Cross-shard Transaction — 왜 어려운가
- 단일 DB에서는 트랜잭션이 ACID를 자동으로 보장하지만, 주문이 샤드 A의 재고와 샤드 B의 결제 정보를 동시에 갱신해야 한다면 하나의 로컬 트랜잭션으로 묶을 수 없다. 이때는 2단계 커밋(2PC)처럼 무겁고 가용성을 해치는 방식을 피하고, 보통 Saga 패턴(각 단계를 로컬 트랜잭션으로 나누고 실패 시 보상 트랜잭션으로 되돌림)이나 outbox 패턴 + 멱등성 키(idempotency key)로 최종 일관성을 확보한다.
- 그래서 샤딩 설계의 성패는 "cross-shard 트랜잭션이 얼마나 드문가"에 달려 있다. 업무 경계(예: 한 테넌트의 모든 데이터가 항상 같은 샤드에 있음)를 샤드 키와 일치시키면 cross-shard 비율을 낮출 수 있다.

### 리샤딩 — 왜 운영이 어려운가
- 샤드 수를 8개에서 16개로 늘리면 `user_id % 8`이던 매핑이 `user_id % 16`으로 바뀌어 거의 모든 데이터의 위치가 달라진다. 서비스를 멈추지 않고 이동하려면 ① 새 노드에도 동시에 쓰는 dual-write, ② 기존 데이터를 백그라운드로 옮기는 backfill, ③ 이동 전후 데이터가 일치하는지 checksum으로 검증, ④ 트래픽을 새 매핑으로 전환하는 cutover 순서를 거친다. 이 중 하나라도 빠지면 데이터 유실·불일치가 발생한다.

### 파티셔닝과의 차이 — 판별 원리
- 파티셔닝은 한 서버 안에서 저장 단위만 나누므로 서버 한 대의 CPU·IOPS 상한을 넘지 못한다. 샤딩은 여러 서버로 나누므로 그 상한 자체를 늘린다.
- 그래서 통상 순서는: 먼저 파티셔닝으로 단일 서버 내 관리 비용을 줄이고, 그래도 서버 한 대의 물리적 한계(CPU·IOPS 지속 고부하)에 도달하면 그때 샤딩을 검토한다. 반대로 조회 성능만 부족하다면 샤딩보다 읽기 복제(read replica)나 캐시를 먼저 검토하는 것이 비용 대비 효과적이다 — 샤딩은 트랜잭션·조인·백업·운영 전체를 바꾸는 무거운 결정이기 때문이다.

## 연결 개념
- 파티셔닝(111) — 단일 노드 내부 분할, 샤딩의 전 단계로 먼저 검토하는 대상
- 샤드 키 — 데이터 위치와 부하 분포, cross-shard 비율을 함께 결정하는 가장 중요한 설계 요소
- Cross-shard Transaction — Saga·outbox·2PC 등 분산 트랜잭션 기법과 직결되는 문제

# 📝 【답안용】 시험 답안 템플릿

> 목적: 시험장에서 25분에 그대로 쓰는 답안 양식. 작성방식(추상표현 금지·수치·도식·문제유형 전환)을 엄격히 지킨다.
> 핵심: 샤딩은 수평 확장 기법이지만, 출제 답안은 샤드 키·라우팅·리샤딩·트랜잭션 제약을 조건부로 판단해야 한다.

## 핵심 인사이트 (3줄 요약)

> 1. **본질**: 샤딩은 동일 논리 데이터셋을 샤드 키에 따라 여러 DB 노드로 분산 저장하는 수평 분할 아키텍처이다.
> 2. **가치**: writer 부하, IOPS, 저장공간을 여러 노드로 분산해 단일 DB 한계를 넘긴다.
> 3. **판단 포인트**: 샤드 키 분포, cross-shard 쿼리, 리샤딩 비용, 트랜잭션 경계를 설계 초기에 고정해야 한다.

## 출제 의도 및 답안 포인트

| 출제 의도 | 반드시 짚을 핵심 | 감점 회피 포인트 |
|:---|:---|:---|
| 대규모 DB 수평 확장 설계 확인 | shard key, routing, horizontal split, resharding | 샤딩과 파티셔닝을 같은 개념으로 설명 |
| 분산 트랜잭션 제약 이해 확인 | cross-shard transaction, 2PC, saga, idempotency | 조인·트랜잭션 비용을 누락 |
| 운영 리스크 판단 확인 | hotspot, skew, scatter-gather, shard map 관리 | 샤드 수 증가만으로 처리량 선형 증가 단정 |

> 요약: 이 문제는 분산 저장 구조보다 샤드 키가 만드는 조회·트랜잭션·운영 제약을 평가하는 문제이다.

## Ⅰ. 개요 및 필요성

- 개요: 샤딩은 DB 노드 수평 분산 기법이다.
- 배경: 단일 writer의 CPU, IOPS, 스토리지 한계가 지속되면 스케일업만으로 쓰기 부하를 감당하기 어렵다.
- 필요성: shard key, shard map, router, resharding 기준으로 장애 격리, 조회 지연, cross-shard transaction 비용을 설계해야 한다.

---

## Ⅱ. 구조 및 구성요소

```text
Client -> Shard Router
  / Shard Map: key range or hash slot
  / Shard 0: user_id group A
  / Shard 1: user_id group B
  / Shard N: user_id group N
Router -> Target Shard -> Result Merge
```

| 구성요소 | 역할 | 특이사항 |
|:---|:---|:---|
| 샤드 키 | 데이터 배치 기준 | `user_id`, `tenant_id`, `order_id` 등 cardinality 확인 |
| 라우터 | 요청을 대상 샤드로 전달 | 애플리케이션 라이브러리, 프록시, DB 미들웨어 |
| 샤드 맵 | 키 범위와 노드 매핑 저장 | 변경 시 캐시 무효화와 롤백 절차 필요 |
| 리샤딩 도구 | 샤드 수 변경·데이터 이동 | dual-write, backfill, cutover 단계 필요 |
| 병합 계층 | cross-shard 결과 취합 | 정렬·집계·페이지네이션 비용 증가 |

> 요약: 샤딩 구조는 샤드 키, 라우터, 샤드 맵, 리샤딩 절차가 결합되어 데이터 위치와 운영 복잡도를 결정한다.

---

## Ⅲ. 동작원리 및 흐름도

```text
Request 수신 -> shard key 추출
  / key 있음 -> shard map 조회 -> target shard 질의
  / key 없음 -> scatter query -> shard별 질의
결과 병합 -> 트랜잭션 경계 확인 -> 응답 반환
```

| 단계 | 처리 내용 | 검증 기준 |
|:---:|:---|:---|
| 1 | 요청에서 샤드 키 추출 | 키 누락률 1% 이하 |
| 2 | 해시 슬롯 또는 범위 기준으로 샤드 결정 | shard map 조회 지연 p95 5ms 이하 |
| 3 | 대상 샤드에서 로컬 트랜잭션 수행 | 단일 샤드 트랜잭션 비율 95% 이상 |
| 4 | 다중 샤드 요청은 fan-out 후 병합 | scatter-gather p95 지연 |
| 5 | 리샤딩 시 dual-write와 검증 후 cutover | row checksum 일치율 100% |

> 요약: 샤딩은 키가 있는 요청을 단일 샤드로 보내고, 키가 없는 요청은 여러 샤드 fan-out 비용을 감수한다.

## Ⅳ. 특징

| 구분 | 단일 DB/파티셔닝 | 샤딩 적용 | 수치·판단 기준 |
|:---|:---|:---|:---|
| 쓰기 처리 | 단일 writer 중심 | 샤드별 writer 분산 | 노드 수 대비 TPS 증가율 측정 |
| 저장공간 | 단일 인스턴스 제한 | 샤드별 스토리지 분산 | shard당 사용률 70% 이하 |
| 트랜잭션 | 로컬 ACID 용이 | cross-shard 원자성 비용 증가 | 단일 샤드 거래 95% 이상 |
| 조회 | 조인·집계 단순 | scatter-gather 발생 | fan-out 샤드 수 제한 |
| 운영 | 백업·복구 단순 | 샤드별 백업·리샤딩 필요 | cutover 오류율 0건 목표 |

> 요약: 샤딩은 writer와 저장공간 한계를 분산하지만, cross-shard 쿼리와 운영 자동화가 설계 난도를 높인다.

## Ⅴ. 심화 비교 및 적용 판단

| 비교 축 | 기존/대안 | 본 키워드 | 선택 기준 |
|:---|:---|:---|:---|
| 확장 방식 | 스케일업, 읽기 복제 | 수평 샤딩 | writer CPU 70% 이상 지속 |
| 데이터 분포 | 단일 노드 | 키 기반 다중 노드 | 키 cardinality 높고 skew 낮음 |
| 트랜잭션 | 단일 DB ACID | 로컬 ACID + 보상 거래 | cross-shard 비율 5% 이하 |
| 운영 | 단일 백업 | 샤드별 백업·복구 | 자동화와 runbook 확보 |

> 요약: 샤딩은 단일 노드 한계가 계측으로 확인되고 단일 샤드 업무 경계가 명확할 때 선택한다.

| 리스크 | 원인 | 대응 방안 | 확인 지표 |
|:---|:---|:---|:---|
| 핫샤드 | 특정 고객·지역 트래픽 집중 | virtual shard, 복합 키, tenant split | shard별 QPS 편차 |
| 리샤딩 장애 | 대량 데이터 이동 중 이중 쓰기 오류 | backfill, checksum, shadow read | 데이터 불일치 건수 |
| cross-shard 비용 | 키 없는 검색·전역 집계 | 검색 인덱스 분리, CQRS | fan-out 샤드 수 |

> 요약: 샤딩 리스크는 핫샤드와 리샤딩이며, 샤드별 부하 편차와 데이터 검증 지표로 통제한다.

| 점검 항목 | 목표 기준 | 측정 방법 |
|:---|:---|:---|
| 부하 균등성 | shard별 QPS 편차 20% 이하 | DB metrics, router log |
| 단일 샤드 비율 | 요청 95% 이상이 단일 샤드 | trace span 분석 |
| 리샤딩 검증 | checksum 일치율 100% | row count, hash compare |
| 장애 격리 | 단일 샤드 장애 영향 1/N 범위 | 장애 훈련, SLO 측정 |

> 요약: 샤딩 성공 여부는 부하 균등성, 단일 샤드 비율, 리샤딩 검증, 장애 격리 범위로 판단한다.

## Ⅵ. 실무 적용 및 결론

**적용 방안 3개 (필수 - 단계별 또는 항목별):**
1. 키 선정: `tenant_id` 또는 `user_id` 기반으로 cardinality, skew, 주요 조회 조건을 분석하고 핫 고객은 virtual shard로 분리함
2. 트랜잭션 축소: 주문·결제처럼 cross-shard 가능성이 있는 흐름은 Saga, outbox, idempotency key로 보상 거래를 설계함
3. 리샤딩 절차: dual-write, backfill, checksum, read shadow, cutover, rollback 순서로 데이터 이동 runbook을 고정함

**결론 (2줄):**
- 기술사 판단: writer 병목과 저장공간 한계가 계측되고 업무 경계가 키로 나뉘면 샤딩, 조회 중심 병목이면 복제·캐시를 우선 검토함
- 향후 방향: 클라우드 분산 SQL과 shard-aware ORM은 라우팅·리샤딩 자동화를 확대하지만 키 설계 책임은 업무 모델에 남음
