## 핵심 인사이트 (3줄 요약)
- 폭발적으로 증가하는 데이터를 단일 데이터베이스(Scale-Up)로 감당할 수 없을 때, **거대한 테이블을 물리적으로 완전히 다른 여러 대의 DB 서버(Scale-Out)로 쪼개어 분산 저장하는 아키텍처 기법**.
- 어떤 데이터를 어느 서버에 넣을지 결정하는 라우팅 규칙(Shard Key)이 핵심이며, 주로 `해시(Hash) 분할`이나 `범위(Range) 분할`을 사용함.
- 무한한 확장성을 얻는 대신, "여러 서버에 걸쳐 있는 데이터 간의 조인(JOIN) 불가능", "분산 트랜잭션 처리의 지옥", "데이터 쏠림(Hotspot) 현상"이라는 치명적인 기술적 복잡성을 떠안게 됨.
---
## Ⅰ. 개요 및 필요성
- **개요**: 관계형 데이터베이스 환경에서 대용량 데이터를 수평 분할(Horizontal Partitioning)하여 서로 다른 물리적 DB 인스턴스(Node)에 분산 저장하고 조회하는 기술.
- **필요성**: 수천만 명의 유저가 동시에 접속하는 라인/카카오톡 같은 서비스는 DB 서버의 CPU나 메모리, 디스크 I/O가 물리적 한계에 부딪힘. "가장 비싼 슈퍼컴퓨터 1대를 사는 것(Scale-Up)"보다 "값싼 일반 서버 100대를 묶어서 쓰는 것(Scale-Out)"이 비용 대비 성능이 압도적이므로 샤딩이 필수적임.
---
## Ⅱ. 아키텍처 및 핵심 원리
- **샤딩의 주요 라우팅 (Shard Key 분할) 방식**:
  1. **해시 샤딩 (Hash Sharding)**:
     - `해시함수(PK) % 서버 대수`의 나머지 값으로 서버를 결정함. (예: `User_ID` 해시값이 1이면 A서버, 2면 B서버).
     - **장점**: 데이터가 모든 서버에 아주 균등하게 분산됨 (Hotspot 방지).
     - **단점**: 서버를 1대 추가(Scale-Out)하면, 분모(나머지 연산)가 바뀌어 기존 100대의 데이터 위치를 다 바꿔야 하는 리밸런싱(Rebalancing) 지옥이 열림 (➡️ Consistent Hashing으로 해결해야 함).
  2. **레인지 샤딩 (Range Sharding)**:
     - 날짜나 회원번호 범위를 기준으로 서버를 나눔. (1월 가입자는 A서버, 2월은 B서버).
     - **장점**: "1월 데이터를 다 지워" 같은 관리가 매우 쉽고, 서버 추가가 유연함.
     - **단점**: 1월은 지나간 달이라 쿼리가 없고, 이번 달 가입자 서버에만 모든 트래픽이 몰리는 데이터 쏠림(Hotspot) 현상이 터짐.
  3. **디렉토리/라우팅 샤딩 (Directory Sharding)**:
     - 별도의 '조회용 매핑 DB(라우터)'를 두어, "이 ID는 3번 서버에 있다"고 매핑 테이블을 직접 관리함. 매우 유연하지만 라우터 자체가 단일 장애점(SPOF)이 됨.

```text
[ 샤딩(Sharding) 아키텍처의 논리적 흐름 ]

 (사용자 요청: "User_ID 501번 정보 줘!")
        ⬇️
 [ 애플리케이션 (또는 샤딩 프록시 L4) ]
   (Shard Key 분석 ➡️ 501 % 3대 = 2번 샤드!)
      ↙️               ⬇️               ↘️
[ DB 샤드 1 ]      [ DB 샤드 2 ]      [ DB 샤드 3 ]
 (0~333번)        (334~666번)       (667~999번)
                   (501번 리턴!)
```

## Ⅲ. 비교 및 연결
| 구분 | 파티셔닝 (Partitioning) | 샤딩 (Sharding) |
|---|---|---|
| **물리적 구조** | 1대의 DB 인스턴스 안에서 디스크 분할 | **N대의 독립적인 DB 인스턴스**로 분할 |
| **확장성 방향** | Scale-Up (DB 자체 스펙 향상) | **Scale-Out (서버 대수 증가)** |
| **조인 (JOIN)** | 자유롭게 가능 | **샤드 간 JOIN 절대 불가 (핵심 단점)** |
| **애플리케이션 영향**| 거의 없음 (투명함) | 쿼리 및 트랜잭션 코드 대규모 수정 필요 |
---
## Ⅳ. 실무 적용 및 기술사 판단
- **샤딩 도입의 마지노선 (최후의 보루)**: 샤딩을 도입하는 순간, RDB가 주던 달콤한 축복(JOIN, ACID 트랜잭션, FK 제약조건)이 모두 깨짐. 따라서 샤딩은 **1) 쿼리 튜닝 ➡️ 2) 스케일 업 ➡️ 3) 레플리케이션(Read 분산) ➡️ 4) 파티셔닝**을 모두 해보고도 서버가 터질 때 선택하는 최후의 독약임.
- **애플리케이션 샤딩 vs 미들웨어 샤딩**: 과거에는 Java 코드 안에서 `DataSource`를 여러 개 들고 `if`문으로 분기(Application Level Sharding)했으나 코드가 지저분해짐. 최근에는 데이터베이스 앞단에 **Apache ShardingSphere**나 **Vitess**(유튜브가 만든 MySQL 샤딩 미들웨어) 같은 프록시 계층을 두어, 개발자는 1대의 DB처럼 쿼리를 치면 미들웨어가 알아서 찢어주는 구조가 실무 아키텍처의 대세임.
---
## Ⅴ. 기대효과 및 결론
- 단일 서버의 물리적 한계를 부수고, 넷플릭스나 구글처럼 전 세계 수십억 명의 데이터를 무한대로 수용할 수 있는 수평 확장의 근간임.
- 샤딩의 복잡한 리밸런싱과 트랜잭션 문제를 개발자가 직접 푸는 것에 지친 결과, "알아서 샤딩을 해주는" MongoDB, Cassandra 같은 분산형 NoSQL, 혹은 Google Spanner 같은 NewSQL이 탄생하는 결정적 계기가 됨.
