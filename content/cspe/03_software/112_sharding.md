# 📖 【암기용】 개념 완전 이해

## 한눈에
- **개요**: 같은 테이블 스키마를 가진 데이터를 여러 대의 독립적인 데이터베이스 서버(Shard)에 수평적으로 분산 저장하는 기법
- **왜 필요한가**: 단일 DB(Scale-up)로는 CPU, 메모리, 디스크 I/O의 물리적 한계에 부딪혀 수천만 명의 동시 접속과 페타바이트급 데이터를 감당할 수 없다.
- **핵심 직관**: 대형 도서관이 꽉 차면, '가~마' 저자 책은 1관에, '바~하' 책은 2관에 배치(서버 분리)하여 방문객을 분산시키는 것과 같다.

## 핵심 용어 정리

| 용어/표기 | 의미 | 비유·예 |
|:---|:---|:---|
| 샤드 (Shard) | 데이터를 쪼개어 저장하는 개별 물리적 DB 노드 | 도서관 1관, 2관 |
| 샤드 키 (Shard Key) | 데이터를 어느 샤드에 보낼지 결정하는 기준 컬럼 | '회원ID' (예: ID 1~1000은 1번 샤드) |
| 라우터 / 브로커 | 애플리케이션의 요청을 적절한 샤드로 전달해주는 중간 계층 | 안내데스크 직원 |
| 크로스 샤드 조인 | 서로 다른 샤드에 있는 데이터를 조인하는 연산 | 1관 책과 2관 책을 동시에 가져와 대조함 (매우 느림) |

## 깊이 이해
- **배경·문제의식**: RDBMS는 태생적으로 단일 서버 수직 확장(Scale-up)에 맞춰져 있다. 하지만 모바일 트래픽 폭증으로 단일 마스터 DB에 Write 부하가 집중되면 락(Lock) 경합과 디스크 한계로 시스템이 멈춘다. 이를 해결하기 위해 저렴한 범용 서버 여러 대를 묶어 쓰는 수평 확장(Scale-out)이 필수적이게 되었다.
- **작동 원리**: 애플리케이션이 데이터를 쓸 때, 샤딩 라우터가 '샤드 키'를 검사한다. 해시 함수를 거치거나 매핑 테이블을 확인하여 해당 데이터가 저장될 특정 DB 인스턴스(서버)를 찾아 연결(Connection)을 맺고 쿼리를 던진다.
- **샤딩 기법**:
  - **Range Sharding**: 1~100만은 A서버, 100만~200만은 B서버. 특정 구간에 부하가 몰릴 수 있다.
  - **Hash Sharding**: 회원ID를 해시(Hash)하여 서버 수로 나눈 나머지(Modulo)로 분배. 고르게 분산되지만, 서버를 추가/삭제할 때 기존 데이터의 해시값이 틀어져 대대적인 데이터 이동(Rebalancing)이 필요하다.
  - **Directory (Lookup) Sharding**: '라우팅 테이블'을 따로 두고, ID 5는 A서버, ID 6은 C서버식으로 자유롭게 매핑. 유연하지만 라우팅 테이블이 단일 장애점(SPOF)이 될 수 있다.
- **구체 예시**: 카카오톡이나 라인의 메시지 DB는 사용자 ID를 해시로 샤딩하여, 수만 대의 DB 서버에 사용자를 균등하게 쪼개어 초당 수백만 건의 메시지를 처리한다.
- **흔한 오해·주의점**: 샤딩을 도입하면 분산 트랜잭션(2PC) 처리와 샤드 간 조인(Join)이 사실상 불가능해진다. 따라서 샤딩은 '은탄환'이 아니며, 애플리케이션 단에서 로직을 복잡하게 변경해야 하는 최후의 수단이다.

## 연결 개념
- 파티셔닝 (Partitioning): 샤딩은 여러 서버에 분산하지만, 파티셔닝은 단일 서버 내에서 데이터를 논리/물리적으로 쪼갠다.
- 일관성 해시 (Consistent Hashing): 서버 증설 시 데이터 리밸런싱을 최소화하기 위해 해시 링(Ring)을 사용하는 기법. 해시 샤딩의 단점을 보완한다.

# 📝 【답안용】 시험 답안 템플릿

## 핵심 인사이트 (3줄 요약)

> 1. **본질**: 샤딩은 초대용량 데이터를 동일한 스키마를 가진 다수의 독립적인 물리적 데이터베이스 노드로 수평 분할(Scale-out)하는 분산 저장 기법이다.
> 2. **가치**: 단일 마스터 DB의 Read/Write 병목과 스토리지 한계를 극복하고, 저비용 범용 서버를 통해 선형적인 성능 확장을 제공한다.
> 3. **판단 포인트**: 샤드 키 선정에 따라 데이터 쏠림(Hotspot) 여부가 결정되며, 샤드 간 조인 제약 및 분산 트랜잭션의 복잡도를 애플리케이션 아키텍처에서 흡수해야 한다.

## 출제 의도 및 답안 포인트

| 출제 의도 | 반드시 짚을 핵심 | 감점 회피 포인트 |
|:---|:---|:---|
| 대규모 시스템 수평 확장 전략 이해 | 파티셔닝(단일 노드)과 샤딩(다중 노드)의 구조적 차이 명시 | 단순 테이블 분할 기법으로만 서술 |
| 샤딩 매커니즘과 분류 역량 | Range, Hash, Directory(Lookup) 샤딩 기법의 장단점 비교 | 해시 샤딩 시 서버 증설 리스크 누락 |
| 아키텍처 제약 및 극복 방안 제시 | Cross-shard Join 한계 및 리밸런싱 부하에 대한 대응 방안 | 분산 트랜잭션을 RDBMS처럼 쉽게 처리된다고 단정 |

> 요약: 샤딩은 단일 DB의 한계를 극복하는 강력한 수단이나, 분산 트랜잭션과 데이터 재분배(Rebalancing)라는 막대한 트레이드오프를 동반함을 논증해야 한다.

---

## Ⅰ. 개요 및 필요성

- 개요: VLDB 환경에서 동일 스키마 데이터를 다수의 물리적 독립 노드(Shard)에 분산 저장하여 처리하는 데이터베이스 수평 확장 기법
- 배경: 서비스 트래픽 폭증으로 단일 데이터베이스 서버의 Scale-up 한계(CPU, 디스크 I/O) 및 RDBMS 쓰기(Write) 병목 발생
- 필요성: 물리적 제약 탈피를 위한 Scale-out 구조 전환 및 시스템 전체의 가용성과 처리량(Throughput)의 선형적 증가 필요

---

## Ⅱ. 구조 및 구성요소

```text
Application -> Shard Router (Broker / Proxy) -> [Shard Key 분석]
                                                  |
                                                  +-> Shard Node 1 (Master/Slave)
                                                  +-> Shard Node 2 (Master/Slave)
                                                  +-> Shard Node 3 (Master/Slave)
```

| 구성요소 | 역할 | 특이사항 |
|:---|:---|:---|
| 샤드 키 (Shard Key) | 데이터를 특정 샤드에 할당하기 위한 파티셔닝 기준 값 | 균등 분포도(Cardinality)가 높은 속성 선정 필수 |
| 라우터 (Router) | 애플리케이션 쿼리의 샤드 키를 분석해 적절한 샤드로 연결 | Middleware 또는 App 내장 Library(JDBC 등) 형태 |
| 샤드 노드 (Shard Node) | 분할된 데이터가 저장되는 독립적인 물리 DB 인스턴스 | 각 샤드는 자체적인 복제(Replication) 구성으로 HA 보장 |

> 요약: 애플리케이션은 투명하게 라우터에 접근하고, 라우터가 샤드 키 규칙에 따라 물리적으로 분리된 여러 샤드 노드로 요청을 분산시킨다.

---

## Ⅲ. 동작원리 및 흐름도

```text
Query Request -> Shard Key Parsing -> Routing Table Match 
-> Target Shard Connection -> Execute Query -> Result Merge & Return
```

- 1단계 [요청 인입 및 분석]: 라우터가 앱의 쿼리를 수신하고 WHERE 절에서 특정 샤드 키 값 식별
- 2단계 [라우팅 결정]: 해시 연산 또는 매핑 테이블(Directory)을 참조하여 대상 샤드 노드의 IP/Port 매핑
- 3단계 [대상 샤드 실행]: 특정 샤드 노드로 커넥션을 맺고 쿼리 전송 및 로컬 트랜잭션 실행
- 4단계 [결과 병합 반환]: 여러 샤드에 분산된 쿼리일 경우, 라우터가 각 샤드의 결과를 수합(Merge)하여 앱으로 응답

> 요약: 쿼리에 포함된 샤드 키를 기반으로 라우터가 물리적 위치를 찾아 단일/다중 샤드 쿼리를 수행하고 결과를 조합한다.

---

## Ⅳ. 특징

- 처리량 극대화: 쓰기(Write) 쿼리가 여러 서버로 완벽히 분산되어 단일 마스터의 락 경합 및 디스크 I/O 한계 극복
- 선형 확장성: 트래픽 증가 시 새로운 샤드 노드(범용 x86 서버)를 추가하여 성능과 용량을 비례하여 증설 가능
- SPOF 완화: 특정 샤드 장애 시 전체 시스템 중단이 아닌, 해당 샤드 영역의 데이터 서비스만 일시 제한되는 부분 장애로 격리

---

## Ⅴ. 심화 비교 및 적용 판단

| 비교 축 | 해시 샤딩 (Hash) | 범위 샤딩 (Range) | 디렉터리 샤딩 (Directory) |
|:---|:---|:---|:---|
| 라우팅 방식 | 샤드 키의 해시 연산 값 (Hash Modulo) | 연속된 키 값의 구간 (예: 날짜, ID 대역) | 별도의 매핑 테이블(Lookup) 유지 |
| 장점 | 데이터가 모든 서버에 가장 균등하게 분산됨 | 특정 범위 대상의 범위 검색(Range Scan)에 유리 | 룰 적용이 자유로워 특정 서버에 동적 할당 용이 |
| 단점 | 노드 추가/삭제 시 대규모 리밸런싱 발생 | 특정 최신 대역으로 트래픽 쏠림(Hotspot) 발생 | 매핑 서버 자체가 단일 장애점(SPOF)이 될 위험 |

> 요약: 균등 분산이 핵심이면 해시 샤딩(안정성 확보 위해 Consistent Hashing 병행)을, 시계열 조회가 잦으면 범위 샤딩을 채택한다.

**리스크·대응:**
- Cross-shard Join 제약: 다른 샤드 간 조인 시 막대한 네트워크 비용 발생 → 비정규화(Denormalization) 설계 적용 및 앱 단에서 분리 조회(App Join)
- 데이터 리밸런싱 부하: 노드 증설 시 데이터 대량이동으로 인한 서비스 지연 → 초기 설계 시 논리적 샤드 개수를 충분히 크게 잡고 맵핑만 분산(Virtual Sharding)
- 분산 트랜잭션 한계: RDBMS의 ACID 보장 불가 → Saga 패턴 적용 및 보상 트랜잭션 기반의 최종 일관성(Eventual Consistency) 구조 도입

## Ⅵ. 실무 적용 및 결론

**적용 방안 3개:**
1. 데이터 특성에 따른 샤드 키 선정: 회원 ID 등 고유 카디널리티가 높은 값을 키로 해시 샤딩을 구성하여 I/O 부하 쏠림 완전 해소
2. 무중단 확장을 위한 Consistent Hashing 적용: 노드 추가/삭제 시 인접 노드의 데이터만 이동시켜 리밸런싱 트래픽을 전체 데이터의 1/N로 통제
3. 아키텍처 재설계: Cross-shard 연산을 피하기 위해 도메인 주도 설계(DDD)를 적용해 연관 데이터를 하나의 샤드로 묶는 Bounded Context 매핑 설계

**결론 (2줄):**
- 기술사 판단: 샤딩은 획기적인 확장성을 제공하지만 쿼리 복잡도와 트랜잭션 제약이라는 큰 대가를 요구하므로, Scale-up과 Read-Replica 확장이 한계에 달했을 때 최후에 도입해야 한다.
- 향후 방향: 최근에는 애플리케이션의 복잡도를 낮추기 위해 Spanner, CockroachDB와 같은 분산 저장과 트랜잭션을 자체 지원하는 NewSQL 도입을 적극 검토해야 한다.
