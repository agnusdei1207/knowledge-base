# 📖 【암기용】 개념 완전 이해

> 목적: 샤딩을 처음 보는 사람도 완전히 이해하게 만든다. 시험 답안 양식이 아니라, 이해를 위한 설명이다.

## 한눈에
- **개요**: 같은 스키마의 데이터를 샤드 키 기준으로 여러 DB 노드에 나누는 수평 분할 방식
- **왜 필요한가**: 단일 DB 서버의 CPU·IOPS·스토리지 한계가 지속되면 스케일업만으로 쓰기 부하를 감당하기 어렵다. 샤딩은 데이터를 여러 노드에 분산해 쓰기 처리량과 저장공간을 확장한다.
- **핵심 직관**: 한 계산대에 모든 고객을 세우지 않고 고객 번호 기준으로 여러 계산대에 배정하는 구조이다.

## 깊이 이해
- **배경·문제의식**: 사용자·주문·메시지 데이터가 테넌트별로 증가하면 단일 인스턴스의 writer CPU 70% 이상, p95 쓰기 지연 200ms 이상 상태가 지속될 수 있다. 샤딩은 데이터 위치를 애플리케이션 또는 미들웨어가 결정해 여러 writer로 분산한다.
- **작동 원리**: 샤드 키를 해시·범위·디렉터리 방식으로 매핑하고, 라우터가 요청을 해당 샤드로 보낸다. 키가 없는 조회는 scatter-gather로 여러 샤드를 조회한 뒤 병합한다.
- **비유**: 택배 물류를 우편번호별 허브로 나누면 해당 지역 물량은 가까운 허브에서 처리하지만, 전국 통합 조회는 허브별 결과를 모아야 한다.
- **구체 예시**: `user_id % 16`으로 16개 샤드를 구성하면 사용자별 쓰기 부하를 분산할 수 있다. 단, 특정 대형 고객이 전체 쓰기의 30%를 차지하면 핫샤드가 발생한다.
- **흔한 오해·주의점**: 샤딩은 단순 분할이 아니라 트랜잭션·조인·백업·리샤딩·관측성을 함께 바꾸는 아키텍처 전환이다.

## 연결 개념
- 파티셔닝 — 단일 DB 내부 분할, 샤딩 전 단계로 검토
- 샤드 키 — 데이터 위치와 부하 분포를 결정하는 핵심 컬럼
- 리샤딩 — 샤드 수 변경 또는 키 재배치 작업
- Cross-shard transaction — 여러 샤드에 걸친 원자성 보장 문제

# 📝 【답안용】 시험 답안 템플릿

> 목적: 시험장에서 25분에 그대로 쓰는 답안 양식. 작성방식(추상표현 금지·수치·도식·문제유형 전환)을 엄격히 지킨다.
> 핵심: 샤딩은 수평 확장 기법이지만, 출제 답안은 샤드 키·라우팅·리샤딩·트랜잭션 제약을 조건부로 판단해야 한다.

## 핵심 인사이트 (3줄 요약)

> 1. **본질**: 샤딩은 동일 논리 데이터셋을 샤드 키에 따라 여러 DB 노드로 분산 저장하는 수평 분할 아키텍처이다.
> 2. **가치**: writer 부하, IOPS, 저장공간을 여러 노드로 분산해 단일 DB 한계를 넘긴다.
> 3. **판단 포인트**: 샤드 키 분포, cross-shard 쿼리, 리샤딩 비용, 트랜잭션 경계를 설계 초기에 고정해야 한다.

## 출제 의도 및 답안 포인트

| 출제 의도 | 반드시 짚을 핵심 | 감점 회피 포인트 |
|:---|:---|:---|
| 대규모 DB 수평 확장 설계 확인 | shard key, routing, horizontal split, resharding | 샤딩과 파티셔닝을 같은 개념으로 설명 |
| 분산 트랜잭션 제약 이해 확인 | cross-shard transaction, 2PC, saga, idempotency | 조인·트랜잭션 비용을 누락 |
| 운영 리스크 판단 확인 | hotspot, skew, scatter-gather, shard map 관리 | 샤드 수 증가만으로 처리량 선형 증가 단정 |

> 요약: 이 문제는 분산 저장 구조보다 샤드 키가 만드는 조회·트랜잭션·운영 제약을 평가하는 문제이다.

## Ⅰ. 개요 및 필요성

샤딩은 데이터를 여러 DB 노드에 수평 분산하는 기법이다. 단일 writer의 CPU·IOPS·스토리지 한계가 명확할 때 샤드별 writer를 두어 부하를 나눈다. 대규모 서비스에서는 샤드 키 설계가 장애 격리, 조회 지연, 리샤딩 비용을 좌우한다.

---

## Ⅱ. 구조 및 구성요소

```text
Client -> Shard Router
  / Shard Map: key range or hash slot
  / Shard 0: user_id group A
  / Shard 1: user_id group B
  / Shard N: user_id group N
Router -> Target Shard -> Result Merge
```

| 구성요소 | 역할 | 특이사항 |
|:---|:---|:---|
| 샤드 키 | 데이터 배치 기준 | `user_id`, `tenant_id`, `order_id` 등 cardinality 확인 |
| 라우터 | 요청을 대상 샤드로 전달 | 애플리케이션 라이브러리, 프록시, DB 미들웨어 |
| 샤드 맵 | 키 범위와 노드 매핑 저장 | 변경 시 캐시 무효화와 롤백 절차 필요 |
| 리샤딩 도구 | 샤드 수 변경·데이터 이동 | dual-write, backfill, cutover 단계 필요 |
| 병합 계층 | cross-shard 결과 취합 | 정렬·집계·페이지네이션 비용 증가 |

> 요약: 샤딩 구조는 샤드 키, 라우터, 샤드 맵, 리샤딩 절차가 결합되어 데이터 위치와 운영 복잡도를 결정한다.

---

## Ⅲ. 동작원리 및 흐름도

```text
Request 수신 -> shard key 추출
  / key 있음 -> shard map 조회 -> target shard 질의
  / key 없음 -> scatter query -> shard별 질의
결과 병합 -> 트랜잭션 경계 확인 -> 응답 반환
```

| 단계 | 처리 내용 | 검증 기준 |
|:---:|:---|:---|
| 1 | 요청에서 샤드 키 추출 | 키 누락률 1% 이하 |
| 2 | 해시 슬롯 또는 범위 기준으로 샤드 결정 | shard map 조회 지연 p95 5ms 이하 |
| 3 | 대상 샤드에서 로컬 트랜잭션 수행 | 단일 샤드 트랜잭션 비율 95% 이상 |
| 4 | 다중 샤드 요청은 fan-out 후 병합 | scatter-gather p95 지연 |
| 5 | 리샤딩 시 dual-write와 검증 후 cutover | row checksum 일치율 100% |

> 요약: 샤딩은 키가 있는 요청을 단일 샤드로 보내고, 키가 없는 요청은 여러 샤드 fan-out 비용을 감수한다.

---

## Ⅳ. 특징

| 구분 | 단일 DB/파티셔닝 | 샤딩 적용 | 수치·판단 기준 |
|:---|:---|:---|:---|
| 쓰기 처리 | 단일 writer 중심 | 샤드별 writer 분산 | 노드 수 대비 TPS 증가율 측정 |
| 저장공간 | 단일 인스턴스 제한 | 샤드별 스토리지 분산 | shard당 사용률 70% 이하 |
| 트랜잭션 | 로컬 ACID 용이 | cross-shard 원자성 비용 증가 | 단일 샤드 거래 95% 이상 |
| 조회 | 조인·집계 단순 | scatter-gather 발생 | fan-out 샤드 수 제한 |
| 운영 | 백업·복구 단순 | 샤드별 백업·리샤딩 필요 | cutover 오류율 0건 목표 |

> 요약: 샤딩은 writer와 저장공간 한계를 분산하지만, cross-shard 쿼리와 운영 자동화가 설계 난도를 높인다.

## Ⅴ. 심화 비교 및 적용 판단

| 비교 축 | 기존/대안 | 본 키워드 | 선택 기준 |
|:---|:---|:---|:---|
| 확장 방식 | 스케일업, 읽기 복제 | 수평 샤딩 | writer CPU 70% 이상 지속 |
| 데이터 분포 | 단일 노드 | 키 기반 다중 노드 | 키 cardinality 높고 skew 낮음 |
| 트랜잭션 | 단일 DB ACID | 로컬 ACID + 보상 거래 | cross-shard 비율 5% 이하 |
| 운영 | 단일 백업 | 샤드별 백업·복구 | 자동화와 runbook 확보 |

> 요약: 샤딩은 단일 노드 한계가 계측으로 확인되고 단일 샤드 업무 경계가 명확할 때 선택한다.

| 리스크 | 원인 | 대응 방안 | 확인 지표 |
|:---|:---|:---|:---|
| 핫샤드 | 특정 고객·지역 트래픽 집중 | virtual shard, 복합 키, tenant split | shard별 QPS 편차 |
| 리샤딩 장애 | 대량 데이터 이동 중 이중 쓰기 오류 | backfill, checksum, shadow read | 데이터 불일치 건수 |
| cross-shard 비용 | 키 없는 검색·전역 집계 | 검색 인덱스 분리, CQRS | fan-out 샤드 수 |

> 요약: 샤딩 리스크는 핫샤드와 리샤딩이며, 샤드별 부하 편차와 데이터 검증 지표로 통제한다.

| 점검 항목 | 목표 기준 | 측정 방법 |
|:---|:---|:---|
| 부하 균등성 | shard별 QPS 편차 20% 이하 | DB metrics, router log |
| 단일 샤드 비율 | 요청 95% 이상이 단일 샤드 | trace span 분석 |
| 리샤딩 검증 | checksum 일치율 100% | row count, hash compare |
| 장애 격리 | 단일 샤드 장애 영향 1/N 범위 | 장애 훈련, SLO 측정 |

> 요약: 샤딩 성공 여부는 부하 균등성, 단일 샤드 비율, 리샤딩 검증, 장애 격리 범위로 판단한다.

## Ⅵ. 실무 적용 및 결론

**적용 방안 3개 (필수 - 단계별 또는 항목별):**
1. 키 선정: `tenant_id` 또는 `user_id` 기반으로 cardinality, skew, 주요 조회 조건을 분석하고 핫 고객은 virtual shard로 분리함
2. 트랜잭션 축소: 주문·결제처럼 cross-shard 가능성이 있는 흐름은 Saga, outbox, idempotency key로 보상 거래를 설계함
3. 리샤딩 절차: dual-write, backfill, checksum, read shadow, cutover, rollback 순서로 데이터 이동 runbook을 고정함

**결론 (2줄):**
- 기술사 판단: writer 병목과 저장공간 한계가 계측되고 업무 경계가 키로 나뉘면 샤딩, 조회 중심 병목이면 복제·캐시를 우선 검토함
- 향후 방향: 클라우드 분산 SQL과 shard-aware ORM은 라우팅·리샤딩 자동화를 확대하지만 키 설계 책임은 업무 모델에 남음
