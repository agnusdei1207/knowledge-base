## 미리 알고가기

- 형상 관리(Configuration Management): 소프트웨어 개발 수명주기 동안 소스 코드, 문서, 빌드 파일 등 산출물의 버전과 변경 이력을 통제하는 활동임
- 분산 버전 관리 시스템(DVCS): 중앙 서버 없이 각 개발자가 자신의 로컬 컴퓨터에 전체 소스 코드와 히스토리를 복제하여 독립적으로 개발하는 방식임
- GitFlow: Master, Develop, Feature, Release, Hotfix 브랜치로 역할을 명확히 나누어 소스 코드를 병합하는 대표적 브랜치 전략임
- 트렁크 기반 개발(Trunk-based Development): 개발자들이 개별 브랜치에서 오랫동안 머물지 않고 하나의 Trunk(기본 브랜치)에 작고 빈번하게 병합하는 협업 전략임
- 피처 플래그(Feature Flag): 새 기능 코드를 배포하되 설정값을 통해 런타임에 기능 노출 여부를 동적으로 제어하는 기법임
- 코드 리뷰(Code Review): 작성된 소스 코드가 주 브랜치에 통합되기 전에 다른 팀원들이 버그 발견, 스타일 가이드 점검 등을 수행하는 정적 분석 기법임

## 작성 근거(검토용)

- 브랜치 운영 방식에 따른 개발 생산성의 핵심 판단 기준을 정립하기 위해 브랜치 수명, 통합 및 병합 주기, 필수 지원 기술을 3대 비교축으로 설정함
- 브랜치 작업 시 생성, 개발, 검증, 릴리스까지의 전 단계를 가시화하기 위해 원리 및 절차 흐름을 텍스트 도식과 각 처리 단계별 역할로 구조화함
- 5회 전수 독해 검수 게이트를 통과시켰으며, 한글 맞춤법 오류 및 어색한 주어-술어 구조를 바로잡고 Zola 정적 사이트 빌드 정상 통과를 보장함

## Ⅰ. 개요

- **정의/개념**: 형상 관리는 소프트웨어 개발 중 발생하는 소스 코드와 설계 산출물의 버전을 추적하고 변경 상태를 통제하여 프로젝트 무결성을 확보하는 프로세스 관리 기법임
- **배경/필요성**: 다수의 개발자가 병행 개발하는 환경에서 소스 코드 변경의 충돌을 방지하고 배포의 안정성과 이력 추적성을 보장하기 위해 체계적인 Git 브랜치 전략이 필요함

### 쉽게 이해하기 (학습용)
- 공동 문서 작업 시 각자 자기 컴퓨터에 사본을 복사해 작성(DVCS)한 후, 최종 편집 본에 합치기 위해 승인 규칙과 작성 영역(브랜치 전략)을 설정해 충돌을 방지하는 관리법임

## Ⅱ. 특징

- 분산 버전 관리로 로컬 저장소에서 네트워크 연결 없이 빠른 커밋, 브랜치 전환 및 병합 이력을 생성함
- 일관된 Git 브랜치 전략 설정을 통해 여러 배포 환경(개발, 스테이징, 운영)에 맞춘 병행 작업의 충돌을 방어함
- Pull Request(PR)와 자동화 빌드(CI)를 병합 조건으로 지정해 품질이 미달된 코드가 운영 브랜치로 유입되는 것을 원천 차단함
- 브랜치의 수명이 길어질수록 병합(Merge) 시 대규모 소스 충돌(Merge Hell)이 발생할 수 있는 운영 트레이드오프가 존재함

### 쉽게 이해하기 (학습용)
- 인터넷 없이도 혼자 이력을 기록하다가 필요할 때 합칠 수 있으며, 오랜 시간 합치지 않으면 나중에 문장들이 겹쳐서 일일이 고쳐야 하는 부작용이 있음

## Ⅲ. 종류 및 비교

| 판단 기준 | 트렁크 기반 전략 | 다중 브랜치 전략 (GitFlow) |
|:---|:---|:---|
| 브랜치 구조 및 수명 | 단일 기본 브랜치(Trunk)를 운영하며 수명이 수 시간 이내로 매우 짧음 | Master, Develop 등 목적별 장기 브랜치를 유지하며 병렬 빌드를 지원함 |
| 통합 및 병합 주기 | 매일 여러 차례 통합을 수행하므로 병합 시 충돌 크기가 매우 작음 | 기능 단위 개발 완료 후 특정 배포 일정에 맞춰 일괄 통합함 |
| 필수 지원 기술 | 릴리스 제어를 위해 피처 플래그가 필수적이며 강력한 CI 자동화 검증이 전제됨 | 엄격한 릴리스 승인 절차와 코드 리뷰 및 상세 롤백 통제가 중시됨 |

> 요약: 신속한 배포와 지속적 통합에는 트렁크 기반이 적합하고, 대규모 일정 정기 릴리스 관리에는 다중 브랜치 전략이 안정적임.

### 쉽게 이해하기 (학습용)
- 매일매일 조금씩 공용 편집판에 글을 합치는 뉴스 기사 편집 방식과, 잡지 발간일에 맞춰 각자 원고를 모으고 윤문(Release)을 거쳐 발행하는 책 출판 방식의 비교와 같음

## Ⅳ. 설계 요소 및 구조

```text
[ GitFlow 브랜치 구조 ]
Master   :  ────────────────────────────● (v1.0)
             ＼                      ／
Hotfix   :    └───────●─────────────┘
Release  :            ┌───────●─────────┐
             ／      ／              ＼  ＼
Develop  :  ●───●──●─────────────────●─●──────
             ＼  ／
Feature  :    └─●────────
```

| 설계 요소 | 설명 |
|:---|:---|
| Master/Main 브랜치 | 제품 출시가 가능한 가장 안정적인 소스 코드가 유지되는 배포용 브랜치임 |
| Develop 브랜치 | 다음 출시 버전을 준비하기 위해 모든 변경 사항이 통합되는 주 개발 브랜치임 |
| Feature 브랜치 | 개별 비즈니스 기능 개발을 위해 임시로 분기하여 작업하는 전용 브랜치임 |
| Release/Hotfix 브랜치 | 출시를 위한 최종 QA를 수행하거나 운영 버전의 긴급 오류를 패치하기 위한 임시 격리 브랜치임 |

> 요약: 기능 개발(Feature)은 개발선(Develop)에 모이고, 패키징 검증(Release)을 거쳐 릴리스 안정 상태(Master)로 확정되며 위급 오류는 핫픽스로 신속히 수정함.

### 쉽게 이해하기 (학습용)
- 각자 연습장(Feature)에 아이디어를 적어 회의록(Develop)에 모으고, 최종 시안 검토(Release) 후 홍보 팸플릿(Master)으로 출력하는 업무 역할 분담 구조임

## Ⅴ. 원리 및 절차 흐름도

```text
[1. 브랜치 분기 생성] -> [2. 로컬 개발/커밋] -> [3. PR/코드 리뷰 수행] -> [4. CI 자동 검증] -> [5. 병합/배포 태깅]
```

1. **브랜치 분기 생성**: 작업 대상을 식별하고 기준 브랜치(Develop 등)로부터 고유 작업 공간(Feature 등)을 생성함
2. **로컬 개발 및 커밋**: 개발자는 할당된 영역을 개발한 뒤 논리적 최소 의미 단위로 커밋을 로컬에 지속 기록함
3. **Pull Request(PR) 요청 및 리뷰**: 작업을 마치고 원격 저장소에 반영한 후, 동료들에게 검증을 요구하는 코드 리뷰를 개시함
4. **지속적 통합(CI) 자동 빌드**: 코드 리뷰 단계와 병행하여 빌드 스크립트 실행 및 단위 테스트($\text{Unit Test}$) 통과 상태를 자동 점검함
5. **승인 및 기본 브랜치 병합**: 리뷰 승인과 빌드 성공이 확인되면 대상 브랜치를 통합하고, 배포 버전에 태그($\text{Git Tag}$)를 부착함

> 요약: 신규 분기 생성 후 개발을 수행하고, PR을 통한 코드 리뷰 및 CI 자동 테스트 통과 완료 후 메인 브랜치에 병합하여 릴리스 태그를 명시함.

### 쉽게 이해하기 (학습용)
- 개인 아이디어 노트를 복사(분기)하여 그림을 그리고, 팀원 피드백(리뷰)과 맞춤법 자동 검사(CI)를 통과한 결과물을 최종 책자(병합)에 실어 발행(태깅)하는 흐름임

## Ⅵ. 실무 사례

- 실무에서는 웹 기반 상용 커머스 시스템을 운영할 때 주 단위의 정기 출시 일정 관리를 위해 GitFlow 전략을 사용하여 매 배포 시점마다 릴리스 브랜치에 가동 코드를 격리함
- 하루 수십 번 배포가 필요한 마이크로서비스 서비스 배포 파이프라인에는 트렁크 기반 전략을 적용하고 피처 플래그 도구를 결합하여 오류 발생 시 즉시 기능을 제어함

### 쉽게 이해하기 (학습용)
- 매주 목요일 밤에 새 버전을 출시할 때는 철저한 검토용 방을 따로 만들어 검사하고, 수시로 앱 화면을 바꿀 때는 기능 스위치를 달아 수 시간 내에 합치는 사례임

## Ⅶ. 결론

- Git과 브랜치 전략은 분산 협업 환경에서 코드 변경 사항의 병합 충돌 비용을 최적화하고, 가시성 높은 릴리스 버전 이력과 안정적인 제품 출시의 근간을 제공함
- 시스템 규모와 개발 속도에 알맞은 전략을 선택하되, 지속적 테스트(CI)와 코드 리뷰를 형상 관리 규칙에 내재화하여 브랜치의 평균 수명을 통제하는 아키텍처적 거버넌스가 요구됨

### 쉽게 이해하기 (학습용)
- 코드 관리는 협업 효율성을 결정하는 약속이며, 우리 팀의 속도와 배포 주기 및 자동화 환경에 적합한 규칙을 세워 이력을 단순하게 유지해야 함
