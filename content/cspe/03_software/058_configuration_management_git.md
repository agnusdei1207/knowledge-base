## Ⅰ. 개요
- **정의**: 소프트웨어 산출물의 변경 이력을 체계적으로 식별·통제·추적하는 관리 활동
- **배경/필요성**: 다수 개발자가 동시에 코드를 변경하면 충돌·유실이 발생하므로, 버전 단위로 변경을 추적하고 통제할 필요
- **비유**: 문서의 변경 이력을 남기는 위키 시스템과 유사하며, Git은 분산형 위키에 해당함

| 출제 의도 | 반드시 짚을 핵심 | 감점 회피 포인트 |
|:---|:---|:---|
| 형상 관리 4대 활동과 Git 분산 모델 이해 | 식별·통제·감사·기록, 분산 저장소 | Git의 기능 나열이 아닌 형상 관리 프로세스 관점 서술 필요 |

> 요약: 변경 이력의 식별·통제·추적을 수행하며, Git은 분산형 형상 관리 도구임

## Ⅱ. 구성요소
```text
Working Dir --> Staging Area --> Local Repo --> Remote Repo
  (수정)       (git add)       (git commit)   (git push)
                                  |
                              Branch/Merge
```

| 구성요소 | 설명 | 비유 |
|:---|:---|:---|
| 형상 항목(CI) | 관리 대상으로 식별된 소스코드·문서·설정 파일 등 | 도서관의 관리 대상 도서 |
| 베이스라인 | 공식 승인된 형상 항목의 스냅샷, 변경 기준점 | 출판된 도서 초판 |
| 브랜치/머지 | 병렬 개발 경로를 생성하고 통합하는 메커니즘 | 갈림길에서 다른 길로 갔다가 합류 |
| 형상 통제 위원회(CCB) | 변경 요청을 검토·승인하는 의사결정 조직 | 편집 위원회 |

> 요약: 형상 항목·베이스라인·브랜치·CCB가 형상 관리의 핵심 요소임

## Ⅲ. 절차
```text
형상식별 --> 형상통제(변경요청/승인) --> 형상감사 --> 형상기록/보고
```
- 1단계: 관리 대상 형상 항목을 식별하고 베이스라인을 설정함
- 2단계: 변경 요청(CR)을 CCB가 검토·승인하고, 브랜치 전략에 따라 변경을 통제함
- 3단계: 베이스라인 대비 실제 산출물의 일치 여부를 형상 감사로 검증함
- 4단계: 변경 이력과 상태를 기록·보고하여 추적성을 확보함

> 요약: 식별·통제·감사·기록의 4대 활동으로 형상을 관리함

## Ⅳ. 문제점
- 브랜치 난립: 브랜치 전략 미수립 — 머지 충돌 빈발과 통합 지연
- 커밋 품질 저하: 대규모·무의미 커밋 — 변경 추적성과 리뷰 효과 감소
- 감사 누락: 형상 감사 미수행 — 베이스라인과 실제 산출물 간 괴리 미발견

> 요약: 브랜치 난립, 커밋 품질 저하, 감사 누락이 주요 문제임

## Ⅴ. 개선방안
1. 단기: Git Flow·Trunk-Based 등 팀 규모에 맞는 브랜치 전략을 수립·적용
2. 중기: 커밋 메시지 규약(Conventional Commits)과 PR 리뷰를 의무화하여 커밋 품질 확보
3. 장기: CI/CD 파이프라인(059 참조)에 자동 형상 감사 단계를 포함하여 베이스라인 일치 검증

> 요약: 브랜치 전략, 커밋 규약, 자동 감사로 개선함

## Ⅵ. 전망
- 발전 방향: GitOps로 인프라 형상까지 Git 기반으로 관리하는 영역 확대 중임
- 기술사적 판단: 소스코드뿐 아니라 IaC·정책·문서까지 형상 관리 범위를 확장하는 추세임
- 기술사 제언: CI/CD(059 참조)·지속적 배포(060 참조)와 연계한 통합 형상 관리 체계 구축 필요
