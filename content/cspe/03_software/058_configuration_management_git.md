# 📖 【암기용】 개념 완전 이해

## 한눈에
- **개요**: 소프트웨어 형상 관리(SCM)는 소스 코드 및 산출물의 변경 이력을 체계적으로 추적하고 통제하는 관리 활동이며, Git은 이를 구현한 사실상의 표준 분산형 버전 관리 시스템이다.
- **왜 필요한가**: 여럿이 같은 파일을 수정하면 코드가 덮어씌워져 날아가거나, 어떤 버전이 배포된 진짜 버전인지 알 수 없는 대혼란(버전 지옥)이 발생한다.
- **핵심 직관**: 코드 타임머신. 코드를 작성하다 완전히 망쳐도 언제든 과거의 특정 시점(커밋)으로 되돌아갈 수 있고, 평행 우주(브랜치)를 만들어 안전하게 새 기능을 실험한 뒤 원래 세계와 합칠(병합) 수 있다.

## 핵심 용어 정리

| 용어/표기 | 의미 | 비유·예 |
|:---|:---|:---|
| 형상 항목 (Configuration Item) | 관리가 필요한 소스코드, 문서, DB 스키마 등의 모든 식별 대상 | 도서관에서 라벨이 붙어 관리되는 책 |
| 기준선 (Baseline) | 특정 시점에 공식적으로 검토되고 합의되어 릴리스의 기준이 되는 상태 | "v1.0.0 출시 버전" (스냅샷) |
| 로컬/원격 저장소 (Local/Remote) | 내 PC의 저장소(로컬)와 서버의 저장소(원격)를 분리 관리 (분산형) | 내 컴퓨터 작업 폴더 vs GitHub 서버 |
| Git Flow / GitHub Flow | 협업을 위해 브랜치(분기)를 어떻게 나누고 합칠지 정한 표준 전략 | 팀 내 교통정리 규칙 |

## 깊이 이해
- **배경·문제의식**: 과거 SVN 같은 중앙집중형 관리 시스템은 중앙 서버가 죽으면 아무도 커밋을 할 수 없었다. 분산형인 Git은 모든 개발자가 전체 저장소의 복사본을 로컬에 가지므로 서버 장애와 무관하게 오프라인 작업이 가능하다.
- **작동 원리 (Git 내부)**: 파일의 변화를 차이(Delta)로 저장하지 않고, 커밋할 때마다 파일들의 전체 스냅샷(Snapshot)을 생성한다. 변하지 않은 파일은 이전 스냅샷의 링크만 유지하여 속도를 극대화한다.
- **작동 원리 (Git Flow 전략)**: 5개의 브랜치로 나눈다. `master`(항상 배포 가능), `develop`(다음 출시 개발), `feature`(개별 기능 개발), `release`(출시 전 QA), `hotfix`(운영 긴급 패치).
- **흔한 오해·주의점**: "코드를 무조건 원격에 자주 푸시하면 형상 관리가 잘 되는 것이다"는 오해다. 의미 없는 커밋이 쌓이면 기준선 추적이 불가능해진다. 기능 단위의 논리적 커밋과 명확한 브랜치 전략이 필수다.

## 연결 개념
- CI/CD 파이프라인 — Git 저장소에 코드가 푸시되는 시점을 트리거로 자동 빌드/배포가 시작됨
- 소프트웨어 기준선 (Baseline) — 형상 관리의 4대 활동(식별, 통제, 상태보고, 감사) 중 핵심 통제 기준
- GitOps — 인프라 설정 자체를 Git 형상 관리에 올려 관리하는 최신 클라우드 네이티브 트렌드

# 📝 【답안용】 시험 답안 템플릿

## 핵심 인사이트 (3줄 요약)

> 1. **본질**: 소프트웨어 생명주기 전반의 산출물 변경 사항을 식별, 통제, 감사하여 무결성을 보장하는 관리 기법 및 분산 버전 관리 도구이다.
> 2. **가치**: 기준선(Baseline)을 통한 릴리스 통제와 브랜치 분리를 통해 다수 개발자의 동시 협업(충돌 방지)을 가능하게 한다.
> 3. **판단 포인트**: Git 자체의 도입보다 조직 규모와 릴리스 주기에 맞는 브랜치 전략(Git Flow vs GitHub Flow) 선택이 생산성 향상의 핵심 결괏값을 만든다.

## 출제 의도 및 답안 포인트

| 출제 의도 | 반드시 짚을 핵심 | 감점 회피 포인트 |
|:---|:---|:---|
| 형상 관리의 관리적/기술적 통제 역량 파악 | 식별/통제/보고/감사 활동, 분산형 저장소 | 버전 관리(Git) 기술적 명령어 나열에만 치중 |
| 협업 프로세스와 브랜치 전략 선택 기준 제시 | Git Flow(정기 배포) vs GitHub Flow(지속 배포) | 특정 브랜치 전략이 모든 팀에 최선이라는 단정 |
| CI/CD 및 DevOps 파이프라인과의 연계 | 커밋 트리거, 기준선(Baseline) 보장 구조 | 형상 관리를 개발 단계만의 활동으로 한정 |

> 요약: Git은 단순한 백업 도구가 아니라 코드 품질 통제와 자동화 파이프라인(CI/CD)을 가동하는 핵심 인프라임을 명시해야 한다.

## Ⅰ. 개요 및 필요성

- 개요: 소프트웨어 산출물(코드, 문서 등)의 변경 이력을 형상 항목으로 식별하고 통제하여 기준선(Baseline)의 무결성을 유지하는 분산 환경 관리 체계임
- 배경: 다수 개발자 동시 작업 시 소스코드 충돌(Conflict) 및 추적 불가 문제로 인해 릴리스 버전의 품질 저하 및 롤백 불가 위험 발생
- 필요성: 변경 사항의 추적성 보장과 무중단 병렬 개발을 위해 분산 저장소 기반의 체계적인 브랜치 병합(Merge) 전략 적용 필수

---

## Ⅱ. 구조 및 구성요소

```text
[ Working Directory ] -> (git add) -> [ Staging Area ] -> (git commit) -> [ Local Repo ] -> (git push) -> [ Remote Repo (GitHub) ]
    (로컬 작업 파일)                    (커밋 대기열/인덱스)                  (내 PC 스냅샷)                (중앙 협업 저장소)
```

| 구성요소 관점 | 세부 요소 | 특이사항 / 역할 |
|:---|:---|:---|
| 관리 활동 4요소 | 식별, 통제(Baseline), 상태보고, 감사 | ISO/IEC 12207 등 SW 품질 관리 표준 기반 |
| Git 내부 계층 | 작업 디렉터리, Staging(인덱스), 로컬/원격 저장소 | 커밋 전 중간 검증 단계(Staging)가 존재 |
| 분산 저장소 | 완전한 이력을 가진 복제본 (Peer to Peer) | 중앙 서버 장애 시에도 로컬에서 형상 관리 가능 |

> 요약: Git은 Staging Area라는 완충 지대를 두어 논리적 커밋 단위를 구성하고, 로컬 저장소를 통해 중앙 종속성을 제거한다.

---

## Ⅲ. 동작원리 및 흐름도 (Git Flow 브랜치 전략 기준)

```text
[master] 기준선 -> (분기) -> [develop] 기능 통합 -> (분기) -> [feature] 개별 개발 -> (병합) -> [develop] -> [release] -> [master] 병합/태깅
```

- 1단계 [기능 분기]: 운영 버전(`master`)에서 복제된 개발 브랜치(`develop`)로부터 개별 작업용 `feature` 브랜치 분기
- 2단계 [개발 및 병합]: 로컬에서 작업 완료 후 Staging 및 커밋 수행, 이후 `develop` 브랜치로 병합(Merge) 및 충돌 해결
- 3단계 [릴리스 준비]: QA 및 배포 테스트를 위해 `release` 브랜치를 생성하여 버그 픽스 수행 (신규 기능 추가 금지)
- 4단계 [운영 배포 및 태깅]: 테스트 완료 시 `master` 브랜치로 병합하고 태그(버전 번호)를 부여하여 기준선(Baseline) 확립

> 요약: 기능 개발, 품질 검증, 운영 배포의 생명주기를 5개의 명시적인 브랜치로 물리적 분리하여 통제한다.

---

## Ⅳ. 특징

- 분산형 토폴로지 (Distributed): 중앙 서버(SVN)와 달리 모든 클라이언트가 전체 히스토리를 보유하여 오프라인 커밋 및 빠른 브랜칭(Branching) 지원
- 스냅샷 기반 저장 (Snapshot): 델타(변경점) 방식이 아닌 파일 시스템 스냅샷을 저장하여 브랜치 생성 및 전환 시 I/O 오버헤드 최소화 (포인터 이동)
- 브랜치 관리 오버헤드 (Overhead): 과도하게 브랜치 생명주기를 길게 가져가면(Long-lived Branch), 병합 시 대규모 충돌(Merge Conflict) 해결 지연 발생

> 요약: 오프라인 작업과 빠른 브랜칭이라는 압도적 장점이 있으나, 지속적 병합(CI) 훈련이 안 된 조직에서는 충돌 지옥이 열린다.

## Ⅴ. 심화 비교 및 적용 판단

| 비교 축 | Git Flow (전통적) | GitHub Flow (경량화) | 선택 기준 |
|:---|:---|:---|:---|
| 브랜치 구조 | 5개 브랜치 (master, dev, feature 등) | 2개 브랜치 (master, feature) | 릴리스의 정기성 및 복잡도 |
| 배포 주기 | 정기 배포 (월간/주간 릴리스) | 지속적 배포 (하루 여러 번) | CI/CD 파이프라인의 성숙도 |
| 테스트 주체 | 별도 QA(release 브랜치) 거침 | PR(Pull Request) 시 자동화 테스트 | 무중단 배포 및 극단적 자동화 여부 |

> 요약: 금융/엔터프라이즈의 정기 배포는 Git Flow가 안전하나, 애자일 기반의 SaaS 기업은 브랜치를 간소화한 GitHub Flow가 압도적으로 유리하다.

**리스크·대응:**
- 대규모 병합 충돌 (Merge Conflict): `feature` 브랜치를 며칠씩 유지하다 한 번에 병합 시 심각한 충돌 발생 → 최소 하루 1회 이상 코드를 중앙 브랜치에 병합(CI)하는 지속적 통합 프랙티스 강제 (지표: 브랜치 체류 시간)
- 민감 정보 하드코딩 유출: 코드에 평문 비밀번호나 AWS Key를 포함하여 원격 저장소에 푸시 → Pre-commit Hook(예: GitLeaks)을 적용하여 커밋 단계에서 시크릿 문자열 정적 검사 및 차단 (지표: 시크릿 노출 감지 건수)

## Ⅵ. 실무 적용 및 결론

**적용 방안 3개:**
1. Pull Request (PR) 기반 코드 리뷰 의무화: 원격 저장소의 `master` 보호 룰을 설정하여, PR 및 동료 2명 이상의 Approve(승인) 없이는 병합되지 않도록 통제
2. CI/CD 트리거 연동 자동화: `release` 또는 `master` 브랜치에 푸시되는 즉시 Jenkins/GitHub Actions 파이프라인이 구동되도록 Webhook 기반 자동화 구축
3. Trunk-Based Development 전환: 브랜치 관리 복잡도를 줄이기 위해, 피처 플래그(Feature Flag) 기술과 결합하여 단일(Trunk) 브랜치 중심의 지속적 병합 적용

**결론 (2줄):**
- 기술사 판단: 형상 관리는 단순한 코드 백업이 아니라 소프트웨어 무결성을 증명하는 감사 통제(Audit) 수단이므로, 커밋 메시지 표준화와 리뷰 문화를 시스템으로 강제해야 함
- 향후 방향: 인프라 구성 코드(IaC)까지 형상 관리에 올려 시스템 전체의 상태를 Git으로 통제하는 GitOps(예: ArgoCD)가 클라우드 네이티브의 핵심 표준으로 자리잡음
