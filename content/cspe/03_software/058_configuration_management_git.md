## 핵심 인사이트 (3줄 요약)
- **형상 관리(SCM)**: 소프트웨어의 변경 사항(소스코드, 문서)을 체계적으로 추적하고 통제하여, 언제든 과거의 특정 상태로 복구할 수 있게 하는 베이스라인 관리 기법.
- **Git**: 리누스 토르발스가 만든 분산형 버전 관리 시스템(DVCS)으로, 오프라인에서도 커밋이 가능하고 브랜치(Branch) 생성/병합이 빛의 속도로 이루어지는 현대 소프트웨어 개발의 절대적 표준.
- 단순한 코드 백업 도구를 넘어, Git-Flow 같은 브랜치 전략을 통해 수만 명의 개발자가 충돌 없이 비동기적으로 협업하게 만드는 데브옵스(DevOps)의 출발점임.
---
## Ⅰ. 개요 및 필요성
- **개요**: 소프트웨어 생명주기(SDLC) 전반에 걸쳐 생성되는 산출물의 무결성을 유지하고 변경을 관리하는 활동.
- **필요성**: 과거에는 코드를 `최종.c`, `진짜최종.c` 식으로 압축해서 공유하다가 소스가 날아가거나 덮어써지는 대참사가 빈번했음. 중앙집중형(SVN)을 쓰기도 했으나 서버가 죽으면 아무도 일을 못 하는 치명적 단점이 있어 분산형(Git)이 탄생함.
---
## Ⅱ. 아키텍처 및 핵심 원리
- **형상 관리의 4단계 절차**:
  1. **형상 식별**: 관리 대상을 정의하고 베이스라인(Baseline) 부여.
  2. **형상 통제**: 변경 요청(CR)을 심사하고 승인 후 반영 (버전 업그레이드).
  3. **형상 감사**: 요구사항대로 잘 변경되었는지 무결성 검증.
  4. **형상 기록**: 변경 이력(Commit log)을 산출하고 보고.
- **Git의 분산형 아키텍처**:
  - 로컬 컴퓨터(Local)에 완벽한 전체 저장소(Repository) 복사본을 가짐.
  - **Working Directory** (작업 공간) ➡️ `git add` ➡️ **Staging Area** (인덱스) ➡️ `git commit` ➡️ **Local Repo** ➡️ `git push` ➡️ **Remote Repo** (GitHub).

```text
[ SVN(중앙집중형) vs Git(분산형) 구조 비교 ]

 (SVN - Centralized)                  (Git - Distributed)
       [ 서버 저장소 ]                       [ 원격 저장소 (GitHub) ]
         /      \                              / (Push/Pull) \
  [개발자 A]    [개발자 B]          [개발자 A의 로컬 저장소]  [개발자 B의 로컬 저장소]
  (서버 끊기면 커밋 불가)                (오프라인에서도 자유롭게 커밋/브랜치 생성)
```

## Ⅲ. 비교 및 연결
| 구분 | CVS / SVN (중앙집중형) | Git (분산형) |
|---|---|---|
| **저장소 위치** | 중앙 서버에만 1개 존재 | 서버 1개 + 모든 개발자 PC에 각각 복제됨 |
| **작업 속도(Commit)**| 네트워크를 타야 하므로 느림 | 로컬 디스크에 저장하므로 매우 빠름 |
| **단일 장애점(SPOF)**| 중앙 서버 장애 시 작업 전면 중단 | 중앙 서버가 죽어도 로컬에서 계속 작업 가능 |
| **브랜치(Branch)** | 생성과 병합이 매우 무겁고 위험함 | 생성과 병합이 극도로 가볍고 일상적임 |
---
## Ⅳ. 실무 적용 및 기술사 판단
- **Git 브랜치 전략 (Git-Flow vs GitHub-Flow)**:
  - **Git-Flow**: `master`, `develop`, `feature`, `release`, `hotfix` 5개 브랜치를 엄격히 관리. (정기 배포가 있는 앱/솔루션에 적합).
  - **GitHub-Flow**: `main` 브랜치 하나만 두고 기능별로 브랜치를 따서 빠르게 Merge하는 방식. (하루에도 수십 번 배포하는 웹/SaaS에 적합). 트렌드는 CI/CD와 결합된 가벼운 GitHub-Flow나 Trunk-based Development로 이동 중임.
- **형상 통제와 코드 리뷰(PR)**: 실무에서 `main` 브랜치에 직접 Push하는 것은 엄격히 금지됨. 반드시 Pull Request(PR)를 올려 동료 2명 이상의 Approve를 받아야만 병합되게 하는 'Zero-Trust' 기반의 형상 통제가 필수적임.
---
## Ⅴ. 기대효과 및 결론
- "코드는 거짓말을 하지 않는다." 누군가 시스템을 망가뜨렸을 때 `git blame`과 `git bisect`를 통해 장애의 원인을 분 단위로 추적하고 롤백할 수 있는 강력한 복원력을 제공함.
- Git은 단순한 툴을 넘어 오픈소스 생태계(GitHub)를 폭발시킨 일등 공신이며, 향후 인프라 구성(GitOps)까지 품으며 클라우드 시대의 '단일 진실 공급원(SSOT)'으로 군림하고 있음.
