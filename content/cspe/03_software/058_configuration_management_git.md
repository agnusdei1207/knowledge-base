# 📖 【암기용】 개념 완전 이해

> 목적: 이 개념을 처음 보는 사람도 완벽히 이해하게 만든다. 시험 답안 양식이 아니라, 이해를 위한 친절한 설명이다.

## 한눈에
- **개요**: **형상 관리(SCM)**는 한마디로 "코드 백업 및 타임머신"이다. 개발자들이 소스코드를 짜다 보면 어제 짠 코드로 돌아가야 할 때가 있고, 10명이 동시에 짤 때 코드가 꼬이는 걸 막아야 한다. 이걸 완벽하게 통제해 주는 도구가 **Git(깃)**이고, 여럿이 싸우지 않게 룰을 정하는 게 **브랜치 전략(Branch Strategy)**이다.
- **왜 필요한가**: 옛날에는 코드를 USB에 담아서 "최종.zip", "진짜최종.zip", "내가수정_진짜마지막.zip" 이렇게 주고받았다. 누군가 내 코드를 덮어쓰면 1주일 치 작업이 날아갔다. Git은 이 비극을 막고, 누가(Who), 언제(When), 왜(Why) 코드 몇 번째 줄을 수정했는지 완벽하게 박제한다.
- **핵심 직관**: 
  - **Git**: 코드 타임머신 (분산형). 내 컴퓨터(로컬)와 클라우드(원격)에 백업본을 동시에 둔다.
  - **브랜치(Branch)**: 평행 우주. 원본 코드(Main)는 놔두고, 내 작업용 우주(Branch)를 하나 파서 맘대로 코딩하다가, 다 끝나면 원본 우주랑 합친다(Merge).

## 깊이 이해
- **배경·문제의식**: 과거에는 SVN이라는 중앙집중형 툴을 썼다. 회사 중앙 서버가 죽으면 모든 개발자가 일을 못 했고, 기차 타고 오프라인 출장 가면 커밋(저장)을 못 했다. 그래서 리눅스 창시자인 리누스 토발즈가 빡쳐서 "중앙 서버 없이 내 컴퓨터에 전체 복사본(타임머신)을 다 들고 있자!"며 만든 게 **분산 버전 관리 시스템(DVCS)인 Git**이다.
- **작동 원리 (Git의 3가지 상태 공간)**:
  1. **워킹 디렉토리 (Working Directory)**: 그냥 내가 지금 키보드 치면서 코드 수정하는 폴더.
  2. **스테이징 에어리어 (Staging Area)**: "음, 이 3개 파일만 묶어서 백업(세이브)해야지" 하고 장바구니에 담아두는 곳. (`git add`)
  3. **로컬 저장소 (Local Repository)**: "최종 세이브 완료!"하고 내 노트북의 타임머신 공간에 영구 저장하는 곳. (`git commit`) -> 이후에 원격 서버(GitHub)로 밀어 올림(`git push`).
- **비유**: 
  - SVN (중앙집중형) = 은행 금고. 돈(코드)을 넣고 뺄 때마다 은행에 무조건 가야 함. 은행 문 닫으면 거래 불가.
  - Git (분산형) = 개인 지갑 + 클라우드. 내 지갑(로컬)에서 맘대로 돈 썼다 지웠다(커밋) 하다가, 인터넷 연결될 때 쓱 동기화(Push)만 하면 됨. 
- **브랜치 전략 (Git Flow vs GitHub Flow)**: 
  - **Git Flow**: 브랜치를 5개(Master, Develop, Feature, Release, Hotfix)로 복잡하게 나눠서 깐깐하게 관리. (오래 걸리는 대형 프로젝트용).
  - **GitHub Flow**: 브랜치가 딱 2개(Main, Feature). 내 기능 만들면 바로 Main에 때려 넣고 하루에 10번 배포. (빠른 스타트업, 웹 개발용).

## 연결 개념
- **CI/CD 파이프라인**: Git 원본(Main 브랜치)에 코드가 딱 합쳐지는(Merge) 순간, 젠킨스(Jenkins) 기계가 그 코드를 낚아채서 자동으로 빌드하고 5분 만에 라이브 서버에 배포해 버리는 궁극의 자동화 콤보.
- **코드 스멜 & 리팩터링**: 브랜치 전략을 쓸 때, 남의 코드를 Main에 합쳐주기 전에 시니어가 눈으로 코드를 째려보고 검사하는 과정(Code Review, Pull Request)이 필수다. 이때 구린 코드(스멜)를 잡아낸다.

# 📝 【답안용】 시험 답안 템플릿

> 목적: 시험장에서 25분에 그대로 쓰는 답안 양식. 작성방식(추상표현 금지·수치·도식·문제유형 전환)을 엄격히 지킨다.
> 핵심: 이 시험은 정보를 많이 나열하는 시험이 아니라, 문제 신호어에서 출제자 의도를 읽고 핵심 논점을 선별해 쓰는 시험이다.

## 핵심 인사이트 (3줄 요약)

> 1. **본질**: 소프트웨어 생명주기(SDLC) 전반에 걸쳐 생성되는 소스코드와 산출물의 가시성, 추적성(Traceability), 무결성을 통제하고 변경 이력을 관리하는 '분산 버전 관리 아키텍처(DVCS)'다.
> 2. **가치**: 중앙 집중식(SVN)의 단일 장애점(SPOF) 리스크를 없애고 로컬 오프라인 커밋(Commit)을 지원하며, 샌드박스 격리인 브랜치(Branch)를 통해 다수 개발자의 동시성(병렬 개발) 충돌 비용을 제로화한다.
> 3. **판단 포인트**: Git의 3단계 로컬 구조(Working/Staging/Repository) 맵핑을 기본으로 깔고, 거대 프로젝트(Git Flow)와 클라우드 애자일 배포(GitHub Flow/Trunk-Based)에 적합한 브랜치 전략의 트레이드오프를 규명해야 한다.

## 출제 의도 및 답안 포인트

| 출제 의도 | 반드시 짚을 핵심 | 감점 회피 포인트 |
|:---|:---|:---|
| 레거시 형상관리(CVCS/SVN) 대비 분산 환경(DVCS/Git)의 아키텍처 우위 | 로컬/원격 저장소의 물리적 분리와 오프라인 독립성 | SVN과 Git의 구조 차이(Staging Area)를 모른 채 단순히 기능 나열 |
| 대규모 협업 충돌 방지를 위한 브랜치(Branch) 브랜치 전략 대조 | **Git Flow** (안정성) vs **GitHub Flow** (민첩성/CI연계) | "무조건 브랜치를 많이 쪼개는 게 좋다"고 쓰는 DevOps 철학 역행 서술 |
| 품질 통제를 위한 리뷰 메커니즘 맵핑 | Pull Request (PR) 및 코드 리뷰 강제화 통제 | 형상 관리 시스템을 단순한 백업(Backup) 툴로만 얕게 치부 |

> 요약: "어제까진 잘 됐는데 오늘 왜 안 되지?" 이 말 한마디 때문에 전 세계 소프트웨어 회사가 날린 돈이 수백조다. Git은 누가(Who) 어떤 줄(Line)을 건드려서 이 폭탄이 터졌는지(Blame) 정확히 찾아내 즉시 롤백 시키는 완벽한 방어막이다.

## Ⅰ. 개요 및 필요성

- 정의: 애플리케이션 요구사항 변경에 따른 소스코드, 문서 등의 산출물 변경(Change) 사항을 식별하고, 버전(Version)을 부여하여 베이스라인(Baseline)의 무결성(Integrity)을 통제하는 관리 활동
- 배경: 기존 중앙집중형(CVCS/SVN) 환경에서는 네트워크 단절 시 커밋(Commit)이 불가능하고, 수십 명이 동시에 코드를 수정할 시 충돌(Conflict)과 덮어쓰기로 인한 데이터 유실 참사 발생
- 필요성: 클라우드 분산 환경(DVCS/Git)을 통해 로컬에 전체 히스토리를 복제하여 오프라인 작업(Agility)을 보장하고, 브랜치 기반 병렬 개발로 CI/CD 배포 파이프라인의 원천 소스(Single Source of Truth)를 제공하기 위함

## Ⅱ. Git (분산 버전 관리) 아키텍처: 3단계 논리적 격리 도식

Git은 코드를 바로 저장소에 박지 않는다. 검수장(Staging Area)이라는 완충 지대를 두어 찌꺼기 코드를 거른다.

```text
[ Git 분산 토폴로지 및 3-Stage 커밋 메커니즘 도식 ]

(1. 코드 타이핑)         (2. 묶음 검수 준비)           (3. 타임머신 기록)
[ Working Directory ] --(git add)--> [ Staging Area ] --(git commit)--> [ Local Repository (내 PC) ]
  (실제 수정 폴더)                   (Index 완충 지대)                      (로컬 타임머신/오프라인)
                                                                                  | 
                               (네트워크 끊겨도 내 PC에서 맘대로 작업 가능)            | (git push)
                                                                                  V
                                                                    [ Remote Repository (GitHub) ]
                                                                       (클라우드 원격 중앙 저장소)
```

| 논리적 격리 구역 | 아키텍처적(엔지니어링) 통제 메커니즘 | 실무 품질 방어 효과 |
|:---|:---|:---|
| **Working Directory** <br> (작업 공간) | 개발자의 로컬 파일 시스템. 아직 Git의 추적(Track)을 받거나 확정되지 않은 원시 코드(Raw code) 덩어리 | 임시 테스트용 스크립트나 빌드 찌꺼기(`*.class`)가 난무해도 안전. `.gitignore`로 쓰레기 배제 강제 |
| **Staging Area** <br> (스테이징 엣지) | 수정된 파일 중 "이번 논리적 버그 수정"에 해당하는 파일 2개만 선별하여(Index) 커밋 대기열에 올리는 완충 큐(Queue) | "로그인 버그 수정"과 "디자인 변경"이 뒤섞인 쓰레기 커밋(Spaghetti Commit)을 막고, **단일 책임 커밋 분할 유도** |
| **Local Repository** <br> (로컬 타임머신) | 원격(GitHub)과 완벽히 격리된 나만의 분산 DB. SHA-1 해시 알고리즘으로 스냅샷(Snapshot)을 생성하여 위변조 절대 불가 구조(Immutable) | **네트워크 종속성 0%**. 출장 중 비행기 안에서도 브랜치를 파고 커밋을 찍으며 무중단 생산성 극대화 |

> 요약: SVN 쓰던 시절엔 회사 중앙 서버가 터지면 개발자 100명이 커피 마시며 놀았다. Git은 내 노트북에 서버(Repository)를 복붙해서 들고 다니는 괴물이라 서버가 터져도 코딩은 계속 굴러간다.

## Ⅲ. 엔터프라이즈 코드 통제: 형상 관리 브랜치(Branch) 전략 비교

100명이 1개의 코드 베이스를 만질 때 교통정리(Rule)를 안 하면 코드가 꼬여 폭발한다.

| 브랜치 전략 패턴 | 맵핑 도식 및 프로세스 메커니즘 | 최적 적용 도메인 (엔지니어링 트레이드오프) |
|:---|:---|:---|
| **Git Flow** <br> (무거운 정통파) | `Master(운영)`, `Develop(통합)`, `Feature(기능)`, `Release(테스트)`, `Hotfix(긴급수정)` 5개의 엄격한 격리 레이어 운용 | 금융권, 패키지 소프트웨어 등 **출시 주기가 길고(월 1회) 절대적 안정성**이 필요한 레거시 인프라 (속도 느림) |
| **GitHub Flow** <br> (초경량/민첩) | `Main(항상 배포 가능)`과 `Feature` 딱 2개. 기능 만들면 PR(리뷰) 거쳐 바로 Main에 박고 즉시 자동 배포(Deploy) | 웹/SaaS 서비스 등 **하루 10번씩 무중단 릴리즈**를 해야 하는 클라우드 네이티브(CI/CD) 조직 (테스트 자동화 필수) |
| **Trunk-Based** <br> (트렁크 기반) | 브랜치를 아예 파지 않거나 반나절 만에 Main(Trunk)에 합침. 코드 충돌(Merge Conflict)을 피하기 위한 극단적 잦은 병합 강제 | MSA 환경 극한의 속도전. 피처 플래그(Feature Flag)를 심어서, 미완성 기능도 Main에 박아놓고 사용자 화면에서만 숨겨둠 |

> 요약: 스타트업에서 남들 다 쓴다고 `Git Flow` 5단계 브랜치 룰을 도입하면, 배포 한 번 하려다 결재(Merge)만 3번 받아야 해서 속도전에서 밀려 망한다. 배포가 잦으면 무조건 2단계짜리 `GitHub Flow`로 갈아타야 한다.

## Ⅳ. 극복해야 할 시스템적 리스크 (형상 붕괴 및 보안 사고)

형상 관리 도구가 뚫리면 소스코드(지적 재산) 유출을 넘어 AWS 서버 인프라 전체가 해커에게 털린다.

| 리스크 요인 | 발생 시나리오 및 시스템 붕괴 원인 (안티패턴) | 아키텍처 대응 방안 (DevSecOps 튜닝) |
|:---|:---|:---|
| **Secret(시크릿) 하드코딩 유출** | AWS 접근 Key나 DB 패스워드를 텍스트로 적은 채 GitHub Public(공개) 레포지토리에 푸시(Push). 3초 뒤 봇(Bot)이 긁어가서 가상화폐 채굴 서버 수천 대를 띄워 10억 과금 폭탄 | **Pre-commit Hook (정적 분석) 강제**: Git 훅(Hook)이나 GitHub Actions에 `TruffleHog`나 `Gitleaks` 같은 스캐닝 툴을 달아서, 코드에 `password=` 문열이 있으면 **아예 커밋(Push) 자체를 에러 내며 차단** (Shift-Left 보안) |
| **거대 브랜치 병합 폭발** <br> (Merge Hell) | 3주 동안 나 혼자 `Feature` 브랜치에 틀어박혀 5천 줄을 짠 뒤 `Main`에 합치려(Merge) 했더니, 동료가 이미 고친 코드와 300군데서 충돌(Conflict)이 나 시스템 파일 다 깨짐 | **지속적 통합(CI) 원칙 준수**: 브랜치 수명은 **최대 1~2일로 극단적 축소**. 완성되지 않은 코드라도 매일 퇴근 전 Main에 욱여넣고 합쳐서 충돌의 눈덩이(Snowball) 파국을 원천 조기 진화 |

> 요약: 주니어 개발자의 최악의 버릇은 "완벽하게 다 짠 다음에 커밋해야지"라며 며칠 동안 코드를 안 올리는 것이다. 코드는 매일 합쳐서 싸워야(충돌) 나중에 병합 지옥(Merge Hell)을 피할 수 있다.

## Ⅴ. 실무 적용 방안 및 결론

**적용 방안 3개:**
1. [Pull Request (PR) 기반 코드 리뷰 의무화 락인] GitHub/GitLab 환경에서 `Main` 브랜치에 대한 다이렉트 푸시(Direct Push) 권한을 물리적으로 차단(Branch Protection Rule)하고, 무조건 신규 `Feature` 브랜치를 파서 시니어 개발자 2명 이상의 Approve(승인)를 받아야만 병합(Merge)이 뚫리도록 품질 게이트(Quality Gate) 강제화
2. [GitOps(깃옵스) 아키텍처 기반 인프라 배포 자동화] 애플리케이션 소스코드뿐만 아니라, 쿠버네티스 배포 설정 파일(YAML)까지 별도의 Git 레포에 통째로 형상 관리(IaC)하고, ArgoCD 데몬이 이 Git의 변경 감지(Sync) 시 실서버(K8s)의 인프라 형상을 똑같이 일치시키는 클라우드 무인 자동화 구축 (Declarative 인프라)
3. [커밋 메시지(Commit Message) 컨벤션 린트(Lint) 강제] "수정완료", "버그잡음" 같은 쓰레기 이력(History)이 쌓이는 것을 막기 위해, 커밋 텍스트에 무조건 `feat: [JIRA-123] 장바구니 로직 수정` 형태의 접두어(Prefix)와 JIRA 이슈 트래커 티켓 번호를 매핑하지 않으면 커밋이 튕겨 나가도록 `Commitlint` 후크 삽입 통제

**결론:**
- 기술사 판단: 형상 관리(Git)는 단순한 백업 폴더가 아니다. 누구의 코드가 시스템을 망가뜨렸는지 단 1초 만에 찾아내는(Git Blame) 거대한 **감사 트레일(Audit Trail)이자, CI/CD 배포 기계를 작동시키는 트리거(방아쇠)**다. 브랜치 전략(규칙) 없이 Git을 쓰는 것은 면허 없이 스포츠카를 모는 것과 같으며, 팀 규모와 배포 속도에 맞춘 정확한 토폴로지(Flow) 튜닝이 필수적이다.
- 향후 방향: 최근 클라우드 네이티브(DevOps) 환경에서는 코드를 넘어 인프라(Terraform), 보안 정책, 기계학습 모델(MLOps) 데이터까지 시스템의 모든 것을 Git으로 통제하는 **'GitOps(Everything as Code)'** 사상으로 형상 관리의 헥사고날(Hexagonal) 영토가 무한히 확장되고 있다.
