## 미리 알고가기

- 형상 관리는 코드와 문서와 빌드 산출물의 버전과 변경 이력을 통제하는 활동임
- Git은 분산 버전 관리 시스템으로 각 개발자가 로컬 이력을 가지고 협업할 수 있게 함
- 브랜치 전략은 어떤 흐름으로 작업하고 병합하고 릴리스할지 정한 규칙임

## 작성 근거(검토용)

- 형상 관리는 작업 흐름, 통합 방식, 브랜치 유지 부담, 적용 환경을 핵심 비교축으로 선정함
- 구성과 절차는 변경 이력 생성부터 리뷰·병합과 릴리스 식별까지의 흐름을 중심으로 제시함
- 실무 판단은 브랜치 수명, 병합 충돌률, 리뷰 대기시간, 버전 추적률로 구체화함

## Ⅰ. 개요

- **정의/개념**: 형상 관리는 소프트웨어 산출물의 버전·변경 이력·승인 상태를 통제하는 활동이며 Git과 브랜치 전략으로 구현함
- **배경/필요성**: 동시 개발에서 변경 충돌과 배포 혼선을 줄이고 특정 릴리스의 변경 이력을 추적할 기준이 필요함

## Ⅱ. 특징

- Git은 각 개발자가 로컬 저장소에서 커밋을 만들고 브랜치·병합으로 변경 이력을 통합함
- 브랜치 전략이 변경 통합 주기와 릴리스 관리 방식을 결정함
- 코드 리뷰와 CI로 병합 전에 결함과 정책 위반을 확인함
- 팀 규모와 자동화 수준에 맞지 않는 전략은 브랜치 수명과 병합 충돌을 늘림

## Ⅲ. 종류 및 비교

| 판단 기준 | 트렁크 기반 전략 | 다중 브랜치 전략 |
|:---|:---|:---|
| 변경 통합 | 짧은 작업 브랜치를 기본 브랜치에 지속 병합함 | 기능 브랜치를 개발 브랜치에 병합함 |
| 릴리스 관리 | 기본 브랜치와 태그로 릴리스 버전을 관리함 | 릴리스·핫픽스 브랜치를 별도로 유지함 |
| 구조상 한계 | 강한 CI와 리뷰 규율이 없으면 기본 브랜치가 불안정해짐 | 장기 브랜치가 남으면 충돌과 병합 지연이 커짐 |
| 대표 환경 | CI와 피처 플래그로 기본 브랜치를 유지하는 제품팀 | 다중 버전·고객별 릴리스 브랜치를 유지하는 조직 |

> 요약: 짧은 주기 통합은 트렁크 기반, 여러 릴리스를 병행 유지하면 다중 브랜치 전략이 적합함.

## Ⅳ. 구성요소 및 구조

| 구성요소 | 설명 |
|:---|:---|
| 저장소 | 소스와 이력과 협업 기준을 보관하는 단일 기준점이 됨 |
| 브랜치 전략 | 기능 개발과 릴리스와 긴급 수정 흐름을 정의해 병행 작업 충돌을 줄임 |
| 리뷰와 병합 규칙 | 승인과 테스트 기준이 병합 품질과 배포 안정성을 좌우함 |
| 태그와 릴리스 기록 | 특정 버전을 명확히 식별해 배포 추적성과 롤백 근거를 남김 |

> 요약: 저장소 변경은 브랜치와 리뷰 규칙으로 통합하고 태그·릴리스 기록으로 배포 버전을 식별함.

## Ⅴ. 원리 및 절차 흐름도

```text
+-------------+     +-------------+     +-------------+     +-------------+
| 작업 분기 생성  | --> | 개발/커밋      | --> | 리뷰/병합      | --> | 태그/릴리스 관리 |
+-------------+     +-------------+     +-------------+     +-------------+
```

1. **작업 분기 생성**: 작업 목적에 맞는 브랜치를 만듦
2. **개발 및 커밋**: 작은 단위로 변경 이력을 남김
3. **리뷰 및 병합**: 승인과 테스트를 거쳐 기준 브랜치에 합침
4. **태그 및 릴리스 관리**: 버전을 고정하고 배포 기록을 남김

> 요약: 작업 브랜치의 커밋을 검토해 기준 브랜치에 병합하고 태그로 릴리스 버전을 고정함.

## Ⅵ. 실무 사례

1. 제품 개발팀은 트렁크 기반으로 짧게 통합하고 브랜치 수명·병합 충돌률을 확인함
2. 다중 버전 제품은 릴리스 브랜치와 태그를 운영하고 버전 추적률·리뷰 대기시간을 확인함

## Ⅶ. 결론

형상 관리는 변경 이력을 검토·통합하고 배포 가능한 버전을 식별·추적하는 통제 활동임
