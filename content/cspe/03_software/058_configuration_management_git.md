## 미리 알고가기

- 형상 관리는 코드와 문서와 빌드 산출물의 버전과 변경 이력을 통제하는 활동임
- Git은 분산 버전 관리 시스템으로 각 개발자가 로컬 이력을 가지고 협업할 수 있게 함
- 브랜치 전략은 어떤 흐름으로 작업하고 병합하고 릴리스할지 정한 규칙임

## Ⅰ. 개요

- **정의/개념**: 형상 관리는 소프트웨어 산출물의 버전과 변경 이력과 승인 상태를 통제하는 활동이며, Git과 브랜치 전략은 이를 실무에서 구현하는 대표 도구와 운영 규칙임.
- **배경/필요성**: 여러 개발자가 동시에 작업하는 환경에서는 변경 충돌과 배포 혼선과 추적성 부족이 쉽게 생기므로, 변경 단위와 병합 기준과 릴리스 기준을 명확히 해야 함.

## Ⅱ. 특징

- Git은 로컬 작업과 병합이 유연해 병렬 개발에 강함
- 브랜치 전략은 배포 속도와 안정성에 직접 영향을 줌
- 코드 리뷰와 CI를 함께 붙일 때 형상 관리 효과가 커짐
- 규칙이 팀 규모와 자동화 수준에 맞지 않으면 병합 비용만 커질 수 있음

## Ⅲ. 종류 및 비교

| 구분 | 트렁크 기반 전략 | 다중 브랜치 전략 |
|:---|:---|:---|
| 작업 흐름 | 짧은 작업 브랜치를 빠르게 기본 브랜치에 통합함 | 기능, 릴리스, 핫픽스 브랜치를 나눠 병행 작업을 운영함 |
| 구조상 장점 | 통합 속도가 빠르고 브랜치 관리가 단순함 | 여러 버전 유지와 릴리스 분리가 쉬움 |
| 구조상 한계 | 강한 CI와 리뷰 규율이 없으면 기본 브랜치가 불안정해짐 | 장기 브랜치가 남으면 충돌과 병합 지연이 커짐 |
| 적합한 환경 | 자동화가 성숙한 SaaS 제품팀에 잘 맞음 | 다중 버전 유지나 고객사별 릴리스가 필요한 조직에 잘 맞음 |

> 요약: 형상 관리의 핵심은 Git 명령 자체보다 어떤 기준으로 변경을 합치고 릴리스 가능한 상태로 만드는지에 있음.

## Ⅳ. 구성요소 및 구조

| 구성요소 | 설명 |
|:---|:---|
| 저장소 | 소스와 이력과 협업 기준을 보관하는 단일 기준점이 됨 |
| 브랜치 전략 | 기능 개발과 릴리스와 긴급 수정 흐름을 정의해 병행 작업 충돌을 줄임 |
| 리뷰와 병합 규칙 | 승인과 테스트 기준이 병합 품질과 배포 안정성을 좌우함 |
| 태그와 릴리스 기록 | 특정 버전을 명확히 식별해 배포 추적성과 롤백 근거를 남김 |

## Ⅴ. 원리 및 절차 흐름도

```text
+-------------+     +-------------+     +-------------+     +-------------+
| 작업 분기 생성  | --> | 개발/커밋      | --> | 리뷰/병합      | --> | 태그/릴리스 관리 |
+-------------+     +-------------+     +-------------+     +-------------+
```

1. **작업 분기 생성**: 작업 목적에 맞는 브랜치를 만듦
2. **개발 및 커밋**: 작은 단위로 변경 이력을 남김
3. **리뷰 및 병합**: 승인과 테스트를 거쳐 기준 브랜치에 합침
4. **태그 및 릴리스 관리**: 버전을 고정하고 배포 기록을 남김

## Ⅵ. 실무 적용 및 유의점

1. 빠른 제품 개발 조직에서는 트렁크 기반 전략이 유리하지만 작은 변경을 자주 통합하지 않으면 기본 브랜치가 불안정해지므로 짧은 브랜치 수명을 유지하고 병합 충돌 비율과 리뷰 대기 시간으로 확인함
2. 여러 버전을 동시에 유지하는 조직에서는 릴리스 브랜치가 필요하지만 태그와 산출물 기록이 약하면 롤백 근거가 흐려지므로 릴리스 기록을 표준화하고 버전 추적 연결률과 롤백 준비 상태로 확인함

## Ⅶ. 결론

형상 관리는 Git 사용법보다 변경이 언제 어떤 기준으로 합쳐지고 배포 가능한 버전으로 고정되는지 통제하는 활동으로 봐야 함.
