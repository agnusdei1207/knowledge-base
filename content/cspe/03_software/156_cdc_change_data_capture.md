## Ⅰ. 개요
- **정의**: 소스 시스템의 데이터 변경분만 식별하여 타겟에 실시간 전파하는 기술
- **배경/필요성**: 전체 데이터를 주기적으로 복제하면 네트워크·처리 비용이 과다하므로 변경분만 전파하는 방식이 필요함
- **비유**: 신문 전체를 매일 다시 인쇄하지 않고 변경된 기사만 호외로 발행하는 것과 같음

| 출제 의도 | 반드시 짚을 핵심 | 감점 회피 포인트 |
|:---|:---|:---|
| 실시간 데이터 동기화 이해 | 로그 기반 vs 트리거 기반 vs 타임스탬프 기반 방식 | CDC와 ETL의 역할 차이 구분 |

> 요약: 데이터 변경분을 감지하여 실시간으로 타겟 시스템에 전파하는 기술임

## Ⅱ. 구성요소
```text
[소스 DB] --> [변경 감지기] --> [변경 이벤트 스트림] --> [타겟 시스템]
                  |                    |
             [DB 로그/WAL]       [메시지 큐]
```

| 구성요소 | 설명 | 비유 |
|:---|:---|:---|
| 변경 감지기 | DB 로그·트리거·타임스탬프로 변경을 포착하는 모듈 | 감시 카메라 |
| DB 로그/WAL | 트랜잭션 변경 이력이 기록되는 데이터베이스 내부 로그 | 거래 원장 |
| 이벤트 스트림 | 변경 이벤트를 순서 보장하여 전달하는 메시지 채널 | 컨베이어 벨트 |
| 타겟 시스템 | 변경분을 수신하여 반영하는 소비측 시스템 | 수신 창고 |

> 요약: DB 로그에서 변경을 감지하고 이벤트 스트림으로 타겟에 전파하는 구조임

## Ⅲ. 절차
```text
변경 발생 --> 로그 감지 --> 이벤트 발행 --> 타겟 반영
```
- 1단계: 변경 발생 — 소스 DB에서 INSERT/UPDATE/DELETE 트랜잭션이 커밋됨
- 2단계: 로그 감지 — 변경 감지기가 WAL/binlog에서 변경 레코드를 읽음
- 3단계: 이벤트 발행 — 변경 레코드를 표준 이벤트 포맷으로 메시지 큐에 발행함
- 4단계: 타겟 반영 — 소비자가 이벤트를 수신하여 타겟 시스템에 적용함

> 요약: 변경발생-로그감지-이벤트발행-타겟반영의 4단계로 실시간 동기화를 수행함

## Ⅳ. 문제점
- 소스 부하: 로그 읽기가 소스 DB I/O에 영향 — 운영 워크로드 성능 저하
- 스키마 변경 대응: DDL 변경 시 이벤트 포맷 불일치 — 파이프라인 중단
- 순서 보장 복잡성: 파티션 분산 시 이벤트 순서 역전 — 데이터 정합성 훼손

> 요약: 소스 부하, 스키마 변경, 순서 보장 문제가 주요 제약 요인임

## Ⅴ. 개선방안
1. 단기: 로그 리더 스로틀링 적용으로 소스 DB 부하 제어
2. 중기: 스키마 레지스트리 도입으로 DDL 변경 시 자동 포맷 호환 처리
3. 장기: 파티션 키 기반 순서 보장 프로토콜 적용으로 정합성 확보

> 요약: 스로틀링, 스키마 레지스트리, 순서 보장 프로토콜로 개선이 필요함

## Ⅵ. 전망
- 발전 방향: Debezium 등 오픈소스 CDC 생태계 확대 및 클라우드 매니지드 서비스 확산
- 기술사적 판단: 이벤트 기반 아키텍처의 핵심 인프라로 CDC 수요 지속 증가
- 기술사 제언: CDC를 데이터 통합(157 참조) 전략의 실시간 계층으로 설계할 필요
