## Ⅰ. 개요
- **정의**: 현실 세계의 데이터를 체계적으로 구조화하여 DB 스키마로 변환하는 과정임
- **배경/필요성**: 데이터 구조 없이 저장하면 중복·불일치가 발생하여 정합성 유지가 불가함
- **비유**: 건물 설계도처럼 데이터를 어떤 구조로 쌓을지 미리 도면을 그리는 작업임

| 출제 의도 | 반드시 짚을 핵심 | 감점 회피 포인트 |
|:---|:---|:---|
| 3단계 모델링 과정 이해 | 개념-논리-물리 구분 | 각 단계의 산출물 차이 명시 |

> 요약: 현실 데이터를 개념-논리-물리 3단계로 정제하여 DB에 매핑하는 설계 과정임

## Ⅱ. 구성요소
```text
DB Modeling
 +-- Conceptual Model --- 업무 중심 엔티티/관계 도출
 +-- Logical Model ------ 정규화된 테이블/속성/키 설계
 +-- Physical Model ----- DBMS 종속 스키마/인덱스 정의
```

| 구성요소 | 설명 | 비유 |
|:---|:---|:---|
| 개념 모델 | 엔티티·관계를 업무 관점에서 도출(ERD) | 건축 기본 구상 |
| 논리 모델 | 속성·키·정규화 적용한 DBMS 독립 설계 | 상세 설계도 |
| 물리 모델 | 테이블스페이스·인덱스·파티션 등 DBMS 종속 구현 | 시공 도면 |

> 요약: 개념-논리-물리 3계층으로 추상에서 구현까지 점진 구체화함

## Ⅲ. 절차
```text
요구분석 --> 개념 설계 --> 논리 설계 --> 물리 설계
```
- 1단계: 업무 요구사항 분석하여 핵심 엔티티와 관계 식별
- 2단계: ER 모델(114 참조)로 개념 스키마 작성
- 3단계: 정규화(115 참조) 적용하여 논리 스키마 도출
- 4단계: 대상 DBMS에 맞춰 인덱스·파티션·타입 등 물리 스키마 구현

> 요약: 요구분석-개념-논리-물리 순으로 점진적 상세화함

## Ⅳ. 문제점
- 요구 불일치: 업무 분석 부족 시 개념 모델이 현실을 반영하지 못함
- 과도한 정규화: 논리 설계에서 분해가 과하면 조인 증가로 조회 성능 저하
- 물리 설계 누락: 인덱스·파티션 미설계 시 대용량 데이터에서 응답 시간 급증

> 요약: 분석 부족, 과정규화, 물리 설계 미흡이 모델링 실패 원인임

## Ⅴ. 개선방안
1. 단기: 현업 참여 워크숍으로 요구사항-개념 모델 간 정합성 확보
2. 중기: 정규화 후 성능 병목 지점에 반정규화(116 참조) 선별 적용
3. 장기: 물리 모델 자동 생성·성능 시뮬레이션 도구 도입

> 요약: 현업 참여, 선별적 반정규화, 자동화 도구로 모델링 품질을 높임

## Ⅵ. 전망
- 발전 방향: 클라우드 네이티브 환경에서 스키마리스 DB와 병행 설계 증가
- 기술사적 판단: 관계형 모델링은 여전히 기업 핵심 데이터의 표준 설계 방법임
- 기술사 제언: 업무 특성에 따라 관계형·비관계형 모델을 혼합 설계할 필요
