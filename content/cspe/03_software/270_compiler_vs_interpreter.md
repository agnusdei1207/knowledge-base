# 📖 【암기용】 개념 완전 이해

> 목적: 컴파일러와 인터프리터의 차이를 실행 방식, 오류 발견 시점, 배포 구조 관점에서 이해하게 만든다.

## 한눈에
- **개요**: 컴파일러와 인터프리터는 사람이 쓴 고급 언어 소스코드를 CPU가 실행 가능한 형태로 바꾸는 **언어 처리(번역) 방식**이며, 번역을 실행 전에 통째로 끝내는가(컴파일) 실행 중에 조금씩 하는가(인터프리트)로 나뉜다.
- **왜 필요한가**: 어떤 언어를 선택하든 소스코드 자체는 CPU가 이해하지 못한다. 번역 시점의 차이가 배포 파일 형태, 오류를 언제 발견하는지, 실행 속도, 디버깅 방식을 좌우하므로 반드시 구분해야 한다.
- **핵심 직관**: 책 한 권을 미리 통째로 번역해 출판하는 것이 컴파일이고, 통역사가 발언을 들으면서 그 자리에서 한 문장씩 옮기는 것이 인터프리트다.

## 핵심 용어 정리 표 (내부에 등장하는 것들)

| 용어 | 의미 | 비유 |
|:---|:---|:---|
| 컴파일러 | 소스 전체를 실행 전에 목적 코드로 번역하는 프로그램 (상위 개념) | 책 전체를 미리 번역해 출판 |
| 인터프리터 | 소스나 중간 표현을 실행하면서 그때그때 해석하는 프로그램 (상위 개념) | 동시통역사 |
| 렉서(Lexer)/토크나이저 | 문자열을 의미 단위 토큰으로 쪼개는 첫 단계 | 문장을 단어로 끊어 읽기 |
| 파서(Parser) | 토큰을 문법 규칙에 맞춰 트리 구조로 재구성 | 단어를 문법에 맞게 문장 구조도로 그리기 |
| AST (추상 구문 트리) | 소스코드의 문법 구조를 표현한 트리 자료구조 | 문장의 뼈대만 남긴 구조도 |
| IR (중간 표현) | 특정 CPU에 종속되지 않은 중간 단계의 코드 형태 | 어느 언어로도 옮기기 쉬운 중립 초안 |
| 바이트코드 | VM이 실행하도록 설계된, 기계어보다 추상화된 명령 형식 | 방언이 아닌 표준어 대본 |
| 목적 코드(Object Code) | 특정 CPU가 직접 실행 가능한 기계어 코드 | 최종 인쇄된 번역본 |
| VM (가상 머신) | 바이트코드를 해석·실행하는 소프트웨어 실행 환경 | 어디서든 같은 대본을 읽는 통역 부스 |
| JIT / AOT | 실행 중 컴파일(JIT) vs 배포 전 컴파일(AOT) | 현장 즉석 번역 vs 사전 번역 출판 |

## 깊이 이해

### 왜 번역이 필요한가 (배경)
- CPU는 오직 0과 1로 이루어진 기계어 명령만 실행한다. C, Python, Java 같은 고급 언어는 사람이 읽기 위한 것이므로 실행되려면 반드시 기계어나 그에 준하는 형태로 바뀌어야 한다. 이 변환을 "실행 전에 한 번에 끝낼 것인가, 실행하면서 그때그때 할 것인가"의 선택이 컴파일과 인터프리트의 근본 차이다.

### 공통 앞단계, 다른 뒷단계
- 두 방식 모두 렉서가 소스를 토큰으로 쪼개고, 파서가 토큰을 AST로 만드는 과정(프론트엔드)을 공유한다. 차이는 그다음이다. 컴파일러는 AST를 IR로 낮추고 최적화(불필요한 연산 제거, 반복문 언롤링 등)를 거쳐 목적 코드나 바이트코드를 파일로 저장한다. 인터프리터는 AST나 바이트코드를 저장하지 않고 그 자리에서 한 명령씩 읽어 즉시 실행한다.

### 구체 사례로 확인
- C는 `gcc -O2 main.c -o app` 실행 시 소스 전체가 분석되어 ELF 실행 파일 하나가 만들어지고, 이후 실행할 때는 더 이상 번역 과정 없이 CPU가 목적 코드를 바로 돌린다.
- Python은 `.py` 파일을 실행할 때마다 CPython VM이 소스를 바이트코드(`.pyc`)로 바꾼 뒤 한 줄씩 해석하며 실행한다 — 실행 시점마다 해석 비용이 매번 낀다.
- Java는 `javac`가 소스를 바이트코드(`.class`)로 미리 컴파일하지만, 실행은 JVM이 이 바이트코드를 해석하다가 자주 도는 부분만 네이티브 코드로 다시 컴파일(JIT)한다 — 컴파일과 해석이 섞인 혼합형이다.

### 오류 발견 시점의 차이를 수치로 이해
- 컴파일러는 실행 전 전체 코드를 분석하므로, 실행되지도 않을 코드 경로의 타입 오류까지 빌드 시점에 잡아낸다. 예를 들어 100개 함수 중 5개 함수에 타입 오류가 있으면, 그 5개 함수가 한 번도 호출 안 돼도 컴파일이 실패한다.
- 인터프리터는 실행된 코드 경로만 검사하므로, 같은 오류가 있어도 그 함수가 호출되지 않는 한 프로그램은 오류 없이 돈다 — 배포 후 특정 조건에서만 터지는 런타임 오류의 원인이 여기 있다.

### 실행 속도 차이를 체감 수치로 이해
- 똑같이 1,000만 번 반복하는 단순 덧셈 루프를 돌리면, 네이티브 컴파일된 C 코드는 CPU가 목적 코드를 그대로 실행하므로 수십 ms 안에 끝나는 반면, 순수 인터프리터로 실행하는 CPython은 매 반복마다 바이트코드 해석 오버헤드(타입 확인, 객체 조회)가 붙어 같은 작업에 수백 ms~1초 이상 걸릴 수 있다 — 대략 수십~수백 배 차이가 인터프리터 오버헤드의 실체다. 이 격차를 줄이려는 기술이 JIT이다(271 참조).

### 비유와 흔한 오해
- 계약서를 미리 완역해 양쪽에 배포하면 컴파일, 회의장에서 발언마다 통역하면 인터프리트다.
- 흔한 오해는 "컴파일 언어는 무조건 빠르고 인터프리트 언어는 무조건 느리다"는 단정이다. 실제로는 Java·JavaScript·.NET처럼 바이트코드+JIT을 함께 쓰는 언어가 다수이며, 최적화 수준과 실행 환경에 따라 격차가 크게 좁혀진다.

## 연결 개념
- JIT 컴파일 — 인터프리터로 실행하다가 핫스팟만 네이티브 코드로 바꾸는 혼합 기법 (271에서 상세)
- 정적/동적 타입 검사 — 오류를 컴파일 시점에 잡을지 실행 시점에 잡을지의 문제와 직결
- VM·바이트코드 — 플랫폼 독립성과 실행 최적화를 동시에 노리는 중간 계층

# 📝 【답안용】 시험 답안 템플릿

> 목적: 시험장에서 25분에 그대로 쓰는 답안 양식. 실행 구조, 오류 시점, 배포·운영 판단을 비교 축으로 고정한다.

## 핵심 인사이트 (3줄 요약)

> 1. **본질**: 컴파일러는 소스 전체를 목적 코드로 변환 후 실행하고, 인터프리터는 실행 시점에 명령을 해석하는 언어 처리 방식이다.
> 2. **가치**: 실행 전 최적화와 배포 단순성은 컴파일러, 대화형 실행과 런타임 유연성은 인터프리터가 담당한다.
> 3. **판단 포인트**: 시험 답안은 속도 단정이 아니라 번역 시점, 오류 발견 시점, 플랫폼 종속성, 최적화 가능성으로 비교해야 한다.

## 출제 의도 및 답안 포인트

| 출제 의도 | 반드시 짚을 핵심 | 감점 회피 포인트 |
|:---|:---|:---|
| 언어 처리 방식 비교 역량 확인 | 번역 시점, 실행 단위, 목적 코드, VM·바이트코드 | C는 컴파일, Python은 해석이라는 단순 암기만 제시 |
| 실행·배포 구조 판단 확인 | 네이티브 실행 파일, 런타임 의존성, 플랫폼 이식성 | 실행 지연만 쓰고 오류 검출·최적화 축 누락 |
| 현대 런타임 이해 확인 | JVM, CLR, JavaScript JIT 등 혼합형 구조 | 컴파일러와 인터프리터를 상호 배타 구조로 단정 |

> 요약: 이 문제는 두 방식의 장단점 나열이 아니라 번역 시점과 운영 조건별 선택 기준을 묻는다.

## Ⅰ. 개요 및 필요성

- 개요: 컴파일러와 인터프리터는 고급언어 실행 방식이다.
- 배경: 컴파일러는 실행 전 전체 번역을 수행하고 인터프리터는 실행 중 문장 또는 중간 표현을 해석한다.
- 필요성: 언어 플랫폼, 배포 단위, 오류 검출 시점, 런타임 최적화 전략을 결정하기 위해 비교해야 한다.

---

## Ⅱ. 구조 및 구성요소

```text
Source Code -> Lexer/Parser -> IR/AST
  / Compiler -> Optimizer -> Object/Bytecode -> Runtime
  / Interpreter -> Runtime Evaluator -> Immediate Execution
```

| 구성요소 | 역할 | 판단 포인트 |
|:---|:---|:---|
| 프론트엔드 | 토큰화, 구문 분석, 의미 분석 | 공통 처리 단계 |
| 컴파일러 백엔드 | IR 최적화, 목적 코드 생성 | 실행 전 최적화 가능 |
| 인터프리터 엔진 | AST·바이트코드 해석 실행 | REPL, 스크립트 실행에 적합 |
| 런타임 | 메모리, 표준 라이브러리, 예외 처리 | GC·JIT 포함 가능 |

> 요약: 두 방식은 프론트엔드를 공유할 수 있으나, 실행 전 코드 생성 여부와 런타임 해석 비중이 다르다.

---

## Ⅲ. 동작원리 및 흐름도

```text
소스 입력 -> 구문/의미 분석 -> 실행 방식 선택
  / 컴파일: 최적화 -> 목적 코드 -> 실행
  / 인터프리트: 문장 해석 -> 즉시 실행 -> 런타임 검사
```

| 단계 | 처리 내용 | 검증 기준 |
|:---:|:---|:---|
| 1 | 소스 코드 토큰화·파싱 | 문법 오류 검출 |
| 2 | 타입·심볼 의미 분석 | 정적 오류 검출 범위 |
| 3 | 목적 코드 생성 또는 해석 | 바이너리 생성 여부 |
| 4 | 실행 및 런타임 처리 | 예외·메모리·라이브러리 처리 |

> 요약: 컴파일러는 실행 전 검증과 코드 생성을 앞당기고, 인터프리터는 실행 시점에 해석과 검사를 수행한다.

## Ⅳ. 특징

| 구분 | 컴파일러 | 인터프리터 | 정량·기술 포인트 |
|:---|:---|:---|:---|
| 번역 시점 | 실행 전 전체 번역 | 실행 중 단위 해석 | build time vs runtime |
| 산출물 | ELF, PE, JVM bytecode | AST, bytecode, VM state | 배포 파일·런타임 의존성 |
| 오류 발견 | 정적 오류 조기 검출 | 실행 경로 도달 시 검출 | test coverage와 연결 |
| 최적화 | `-O2`, inlining, vectorization | profiling, adaptive optimization | JIT 결합 가능 |

> 요약: 선택 기준은 언어 이름이 아니라 번역 시점, 산출물, 오류 검출 범위, 런타임 최적화 구조다.

## Ⅴ. 심화 비교 및 적용 판단

| 비교 축 | 기존/대안 | 본 키워드 | 선택 기준 |
|:---|:---|:---|:---|
| 시스템 SW | 네이티브 컴파일 | C/C++/Rust | OS, DB, 드라이버처럼 지연 예산 1ms 이하 |
| 스크립트 자동화 | 인터프리터 | Python, Bash | 배포보다 수정 주기가 짧은 운영 작업 |
| 엔터프라이즈 | 바이트코드+JIT | JVM, CLR | 이식성과 런타임 최적화 동시 요구 |

> 요약: 시스템 SW는 네이티브 컴파일, 운영 자동화는 인터프리터, 대규모 서버는 VM+JIT 혼합형이 선택 기준이다.

| 리스크 | 원인 | 대응 방안 | 확인 지표 |
|:---|:---|:---|:---|
| 배포 실패 | 런타임·라이브러리 버전 불일치 | container image, SBOM, lockfile | 재현 빌드 성공률 100% |
| 런타임 오류 | 동적 타입·실행 경로 미검증 | unit test, type checker, coverage | branch coverage 80% 이상 |
| 최적화 역효과 | 과도한 컴파일 옵션·JIT warm-up | benchmark, profile guided optimization | p95 latency, warm-up time |

> 요약: 실행 방식 선택 후에는 재현 빌드, 테스트 커버리지, 지연 지표로 운영 리스크를 통제한다.

| 점검 항목 | 목표 기준 | 측정 방법 |
|:---|:---|:---|
| 실행 지연 | p95 API 100ms 이하 등 업무 SLO | APM, benchmark |
| 빌드 재현성 | 동일 commit 동일 artifact hash | CI artifact 검증 |
| 오류 검출 | 정적 분석 violation 0건, test pass 100% | compiler warning, lint, CI |

> 요약: 도입 효과는 실행 지연, 재현 빌드, 오류 검출률로 판단한다.

## Ⅵ. 실무 적용 및 결론

**적용 방안 3개 (필수 — 단계별 또는 항목별):**
1. 시스템 컴포넌트는 Rust/C++ 컴파일러와 `-O2`, LTO, ASan 테스트로 CPU·메모리 결함을 배포 전 검출함.
2. 운영 스크립트는 Python 인터프리터와 `venv`, `pip-tools`, type checker로 런타임 의존성을 고정함.
3. 서버 애플리케이션은 JVM/CLR JIT warm-up, container readiness probe, p95 latency 측정으로 초기 지연을 통제함.

**결론 (2줄):**
- 기술사 판단: 지연 예산과 배포 통제가 우선이면 컴파일러, 수정 주기와 대화형 실행이 우선이면 인터프리터 선택.
