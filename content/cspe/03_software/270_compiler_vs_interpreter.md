# 📖 【암기용】 개념 완전 이해

> 목적: 컴파일러와 인터프리터의 차이를 실행 방식, 오류 발견 시점, 배포 구조 관점에서 이해하게 만든다.

## 한눈에
- **개요**: 컴파일러는 전체 번역 후 실행하고, 인터프리터는 문장을 해석하며 실행한다.
- **왜 필요한가**: 언어 런타임 선택, 배포 파일 형식, 디버깅 방식, 실행 지연을 판단할 때 두 방식의 차이가 기준이 된다.
- **핵심 직관**: 책 전체를 번역해 출판하는 방식이 컴파일, 통역사가 문장마다 바로 말해 주는 방식이 인터프리트다.

## 깊이 이해
- **배경·문제의식**: 고급언어는 CPU가 직접 실행할 수 없으므로 기계어, 바이트코드, 런타임 호출 형태로 바뀌어야 한다.
- **작동 원리**: 컴파일러는 소스 전체를 분석해 목적 코드나 바이트코드를 만들고, 인터프리터는 소스 또는 중간 표현을 읽으며 즉시 실행한다.
- **비유**: 계약서를 미리 완역해 배포하면 컴파일, 회의장에서 발언마다 통역하면 인터프리터다.
- **구체 예시**: C는 `gcc -O2`로 ELF 실행 파일 생성, Python은 CPython VM이 `.py`를 바이트코드로 해석, Java는 `javac` 후 JVM에서 JIT까지 결합한다.
- **흔한 오해·주의점**: 현대 언어는 순수 컴파일·순수 해석으로만 나뉘지 않는다. Java, JavaScript, .NET은 바이트코드와 JIT을 함께 사용한다.

## 연결 개념
- JIT 컴파일 — 인터프리터 실행 중 핫스팟을 네이티브 코드로 변환
- 정적/동적 타입 검사 — 오류 발견 시점과 런타임 검증 비용에 영향
- VM·바이트코드 — 플랫폼 독립성과 실행 최적화의 중간 계층

# 📝 【답안용】 시험 답안 템플릿

> 목적: 시험장에서 25분에 그대로 쓰는 답안 양식. 실행 구조, 오류 시점, 배포·운영 판단을 비교 축으로 고정한다.

## 핵심 인사이트 (3줄 요약)

> 1. **본질**: 컴파일러는 소스 전체를 목적 코드로 변환 후 실행하고, 인터프리터는 실행 시점에 명령을 해석하는 언어 처리 방식이다.
> 2. **가치**: 실행 전 최적화와 배포 단순성은 컴파일러, 대화형 실행과 런타임 유연성은 인터프리터가 담당한다.
> 3. **판단 포인트**: 시험 답안은 속도 단정이 아니라 번역 시점, 오류 발견 시점, 플랫폼 종속성, 최적화 가능성으로 비교해야 한다.

## 출제 의도 및 답안 포인트

| 출제 의도 | 반드시 짚을 핵심 | 감점 회피 포인트 |
|:---|:---|:---|
| 언어 처리 방식 비교 역량 확인 | 번역 시점, 실행 단위, 목적 코드, VM·바이트코드 | C는 컴파일, Python은 해석이라는 단순 암기만 제시 |
| 실행·배포 구조 판단 확인 | 네이티브 실행 파일, 런타임 의존성, 플랫폼 이식성 | 실행 지연만 쓰고 오류 검출·최적화 축 누락 |
| 현대 런타임 이해 확인 | JVM, CLR, JavaScript JIT 등 혼합형 구조 | 컴파일러와 인터프리터를 상호 배타 구조로 단정 |

> 요약: 이 문제는 두 방식의 장단점 나열이 아니라 번역 시점과 운영 조건별 선택 기준을 묻는다.

## Ⅰ. 개요 및 필요성

- 개요: 컴파일러와 인터프리터는 고급언어 실행 방식이다.
- 배경: 컴파일러는 실행 전 전체 번역을 수행하고 인터프리터는 실행 중 문장 또는 중간 표현을 해석한다.
- 필요성: 언어 플랫폼, 배포 단위, 오류 검출 시점, 런타임 최적화 전략을 결정하기 위해 비교해야 한다.

---

## Ⅱ. 구조 및 구성요소

```text
Source Code -> Lexer/Parser -> IR/AST
  / Compiler -> Optimizer -> Object/Bytecode -> Runtime
  / Interpreter -> Runtime Evaluator -> Immediate Execution
```

| 구성요소 | 역할 | 판단 포인트 |
|:---|:---|:---|
| 프론트엔드 | 토큰화, 구문 분석, 의미 분석 | 공통 처리 단계 |
| 컴파일러 백엔드 | IR 최적화, 목적 코드 생성 | 실행 전 최적화 가능 |
| 인터프리터 엔진 | AST·바이트코드 해석 실행 | REPL, 스크립트 실행에 적합 |
| 런타임 | 메모리, 표준 라이브러리, 예외 처리 | GC·JIT 포함 가능 |

> 요약: 두 방식은 프론트엔드를 공유할 수 있으나, 실행 전 코드 생성 여부와 런타임 해석 비중이 다르다.

---

## Ⅲ. 동작원리 및 흐름도

```text
소스 입력 -> 구문/의미 분석 -> 실행 방식 선택
  / 컴파일: 최적화 -> 목적 코드 -> 실행
  / 인터프리트: 문장 해석 -> 즉시 실행 -> 런타임 검사
```

| 단계 | 처리 내용 | 검증 기준 |
|:---:|:---|:---|
| 1 | 소스 코드 토큰화·파싱 | 문법 오류 검출 |
| 2 | 타입·심볼 의미 분석 | 정적 오류 검출 범위 |
| 3 | 목적 코드 생성 또는 해석 | 바이너리 생성 여부 |
| 4 | 실행 및 런타임 처리 | 예외·메모리·라이브러리 처리 |

> 요약: 컴파일러는 실행 전 검증과 코드 생성을 앞당기고, 인터프리터는 실행 시점에 해석과 검사를 수행한다.

---

## Ⅳ. 특징

| 구분 | 컴파일러 | 인터프리터 | 정량·기술 포인트 |
|:---|:---|:---|:---|
| 번역 시점 | 실행 전 전체 번역 | 실행 중 단위 해석 | build time vs runtime |
| 산출물 | ELF, PE, JVM bytecode | AST, bytecode, VM state | 배포 파일·런타임 의존성 |
| 오류 발견 | 정적 오류 조기 검출 | 실행 경로 도달 시 검출 | test coverage와 연결 |
| 최적화 | `-O2`, inlining, vectorization | profiling, adaptive optimization | JIT 결합 가능 |

> 요약: 선택 기준은 언어 이름이 아니라 번역 시점, 산출물, 오류 검출 범위, 런타임 최적화 구조다.

## Ⅴ. 심화 비교 및 적용 판단

| 비교 축 | 기존/대안 | 본 키워드 | 선택 기준 |
|:---|:---|:---|:---|
| 시스템 SW | 네이티브 컴파일 | C/C++/Rust | OS, DB, 드라이버처럼 지연 예산 1ms 이하 |
| 스크립트 자동화 | 인터프리터 | Python, Bash | 배포보다 수정 주기가 짧은 운영 작업 |
| 엔터프라이즈 | 바이트코드+JIT | JVM, CLR | 이식성과 런타임 최적화 동시 요구 |

> 요약: 시스템 SW는 네이티브 컴파일, 운영 자동화는 인터프리터, 대규모 서버는 VM+JIT 혼합형이 선택 기준이다.

| 리스크 | 원인 | 대응 방안 | 확인 지표 |
|:---|:---|:---|:---|
| 배포 실패 | 런타임·라이브러리 버전 불일치 | container image, SBOM, lockfile | 재현 빌드 성공률 100% |
| 런타임 오류 | 동적 타입·실행 경로 미검증 | unit test, type checker, coverage | branch coverage 80% 이상 |
| 최적화 역효과 | 과도한 컴파일 옵션·JIT warm-up | benchmark, profile guided optimization | p95 latency, warm-up time |

> 요약: 실행 방식 선택 후에는 재현 빌드, 테스트 커버리지, 지연 지표로 운영 리스크를 통제한다.

| 점검 항목 | 목표 기준 | 측정 방법 |
|:---|:---|:---|
| 실행 지연 | p95 API 100ms 이하 등 업무 SLO | APM, benchmark |
| 빌드 재현성 | 동일 commit 동일 artifact hash | CI artifact 검증 |
| 오류 검출 | 정적 분석 violation 0건, test pass 100% | compiler warning, lint, CI |

> 요약: 도입 효과는 실행 지연, 재현 빌드, 오류 검출률로 판단한다.

## Ⅵ. 실무 적용 및 결론

**적용 방안 3개 (필수 — 단계별 또는 항목별):**
1. 시스템 컴포넌트는 Rust/C++ 컴파일러와 `-O2`, LTO, ASan 테스트로 CPU·메모리 결함을 배포 전 검출함.
2. 운영 스크립트는 Python 인터프리터와 `venv`, `pip-tools`, type checker로 런타임 의존성을 고정함.
3. 서버 애플리케이션은 JVM/CLR JIT warm-up, container readiness probe, p95 latency 측정으로 초기 지연을 통제함.

**결론 (2줄):**
- 기술사 판단: 지연 예산과 배포 통제가 우선이면 컴파일러, 수정 주기와 대화형 실행이 우선이면 인터프리터 선택.
- 향후 방향: WASM, GraalVM, AOT/JIT 혼합 구조로 실행 방식 경계가 런타임 정책 중심으로 이동함.
