## Ⅰ. 개요
- **정의**: 해시 함수 기반 O(1) 등치 검색과 비트 벡터 기반 다중 조건 필터링을 제공하는 인덱스 유형
- **배경/필요성**: B-Tree(123 참조)가 범위 검색에 강한 반면, 등치 전용 탐색이나 저카디널리티 다중 조건에는 구조적 비효율이 존재함
- **비유**: 해시는 사물함 번호로 물건을 즉시 찾는 것, 비트맵은 체크리스트 여러 장을 겹쳐 공통 항목을 찾는 것과 유사함

| 출제 의도 | 반드시 짚을 핵심 | 감점 회피 포인트 |
|:---|:---|:---|
| 인덱스 유형별 적합 시나리오 구분 | 해시=등치, 비트맵=저카디널리티+다조건 | 해시의 범위 검색 불가 명시 필요 |

> 요약: 등치 검색은 해시, 저카디널리티 다중 조건은 비트맵이 B-Tree 대비 유리한 인덱스임

## Ⅱ. 구성요소
```text
[Hash Index]                    [Bitmap Index]
Key --> Hash(Key) --> Bucket    Key Value --> Bit Vector
         |                      Gender=M : 1 0 1 1 0
      Pointer --> Row           Gender=F : 0 1 0 0 1
                                AND/OR 연산으로 결합
```

| 구성요소 | 설명 | 비유 |
|:---|:---|:---|
| Hash Function | 키를 버킷 주소로 변환하는 함수 | 사물함 번호 배정 규칙 |
| Bucket | 동일 해시 값의 키-포인터를 저장하는 슬롯 | 사물함 칸 |
| Bit Vector | 각 행의 존재 여부를 0/1로 표현한 비트열 | 출석부 체크 |
| Bitwise 연산 | AND/OR/NOT으로 다중 조건 결합 수행 | 체크리스트 겹치기 |

> 요약: 해시는 버킷 직접 접근, 비트맵은 비트 벡터 논리 연산으로 검색을 수행함

## Ⅲ. 절차
```text
[Hash] Key --> Hash() --> Bucket Lookup --> Row 반환
[Bitmap] 조건1 Bit Vector AND 조건2 Bit Vector --> 결과 Row 집합
```
- 1단계: 해시 인덱스는 키에 해시 함수를 적용하여 버킷 주소를 산출함
- 2단계: 버킷 내 키-포인터 목록에서 일치 항목을 탐색하여 데이터 행에 접근함
- 3단계: 비트맵 인덱스는 각 조건별 Bit Vector를 조회함
- 4단계: 다중 Bit Vector를 AND/OR 연산으로 결합하여 최종 결과 행 집합을 산출함

> 요약: 해시는 함수-버킷 직접 접근, 비트맵은 비트 벡터 결합으로 결과를 도출함

## Ⅳ. 문제점
- 해시 충돌: 버킷 오버플로 발생 시 체인 탐색으로 O(1) 보장이 깨짐
- 비트맵 갱신 비용: INSERT/DELETE 시 전체 Bit Vector 갱신으로 OLTP 환경에 부적합함
- 해시 범위 검색 불가: 해시 값 순서와 키 순서가 무관하여 범위·정렬 쿼리 지원 불가

> 요약: 해시 충돌, 비트맵 갱신 부하, 범위 검색 불가가 주요 제약임

## Ⅴ. 개선방안
1. 단기: Extendible/Linear Hashing으로 충돌 시 버킷 동적 확장
2. 중기: 비트맵은 OLAP·배치 환경에 한정 적용하고 OLTP는 B-Tree(123 참조) 병용
3. 장기: 범위 검색 요구 시 해시+B-Tree 복합 인덱스 또는 Adaptive Hash Index 도입

> 요약: 동적 해싱, 워크로드별 적용 구분, 복합 인덱스 전략으로 한계를 보완함

## Ⅵ. 전망
- In-Memory DB에서 해시 인덱스 활용 확대, 컬럼 스토어와 비트맵 결합 심화
- 기술사적 판단: B-Tree 만능이 아닌 워크로드 특성별 인덱스 선택이 설계 역량의 차별점임
- 기술사 제언: 등치·범위·다조건 쿼리 비율을 분석하여 인덱스 유형을 혼합 적용할 필요
