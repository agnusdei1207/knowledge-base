## 미리 알고가기

- 도큐먼트 DB는 행 대신 JSON과 비슷한 문서 단위로 데이터를 저장하는 NoSQL 계열임
- BSON은 MongoDB가 쓰는 이진 문서 형식으로 중첩 구조와 다양한 타입을 담기 쉬움
- 샤딩은 데이터를 여러 노드에 나누어 저장하는 방식이고 레플리카셋은 복제와 장애 조치를 맡는 구조임

## Ⅰ. 개요

- **정의/개념**: MongoDB는 문서 단위로 데이터를 저장하고 중첩 구조와 가변 스키마를 자연스럽게 다루도록 설계된 도큐먼트 지향 NoSQL 데이터베이스임
- **배경/필요성**: 상품 정보와 사용자 프로필처럼 구조가 자주 바뀌고 중첩 속성이 많은 데이터는 테이블 정규화보다 문서 저장이 개발 속도와 변경 대응에 유리해 도큐먼트 DB가 필요해짐

## Ⅱ. 특징

- 문서 안에 배열과 객체를 함께 담을 수 있어 애플리케이션 객체 구조와 잘 맞음
- 스키마를 유연하게 바꿀 수 있어 요구사항 변화에 빠르게 대응하기 좋음
- 보조 인덱스와 집계 파이프라인을 지원해 조회와 분석을 함께 처리하기 쉬움
- 문서 크기와 중복 필드가 커지면 저장 비용과 갱신 비용이 빠르게 늘 수 있음

## Ⅲ. 종류 및 비교

| 판단 기준 | 관계형 DB | MongoDB |
|:---|:---|:---|
| 데이터 구조 | 정해진 컬럼과 조인 중심 | 문서와 중첩 구조 중심 |
| 스키마 변경 | 사전 설계와 마이그레이션 부담이 큼 | 변경이 비교적 유연함 |
| 강점 | 강한 정합성과 복잡한 조인 | 빠른 개발과 문서 단위 조회 |
| 주의점 | 구조가 복잡하면 개발 속도가 느려질 수 있음 | 문서 중복과 비정규화 관리가 필요함 |

## Ⅳ. 구성요소 및 구조

| 구성요소 | 설명 |
|:---|:---|
| Database / Collection | 테이블 대신 컬렉션 단위로 문서를 묶어 관리함 |
| Document | 상품, 사용자, 주문처럼 한 개체를 BSON 문서로 저장함 |
| Index | 자주 쓰는 조회 조건과 정렬 기준을 빠르게 찾게 함 |
| Replica Set | 주 노드와 보조 노드 복제로 가용성과 읽기 분산을 맡음 |
| Shard | 샤드 키를 기준으로 대용량 데이터를 여러 노드에 나눔 |

```text
애플리케이션 -> Collection -> Document -> Index
                        |
                 Replica Set / Shard
```

## Ⅴ. 원리 및 절차 흐름도

```text
문서 설계 -> 컬렉션 저장 -> 인덱스 생성 -> 조회/집계 -> 복제/샤딩 운영
```

1. **문서 설계**: 함께 읽고 함께 바꾸는 속성을 한 문서에 묶음
2. **컬렉션 저장**: BSON 문서를 컬렉션에 적재함
3. **인덱스 생성**: 자주 쓰는 필드에 보조 인덱스를 둠
4. **조회와 집계**: 조건 검색과 집계 파이프라인으로 데이터를 읽음
5. **복제와 분산**: 레플리카셋과 샤딩으로 가용성과 확장성을 확보함

## Ⅵ. 실무 적용 및 유의점

1. 상품 카탈로그와 사용자 프로필처럼 속성 변화가 잦은 서비스는 MongoDB가 잘 맞지만 문서 중복이 커지면 수정 누락이 생기므로 문서 경계와 갱신 책임을 먼저 정하고 평균 조회 시간과 중복 필드 변경 누락 건수로 확인함
2. 대용량 운영 환경은 샤딩만 먼저 늘리기보다 샤드 키가 접근 패턴과 맞는지 검토하고 샤드별 데이터 편차와 핫샤드 비율과 재균형 시간을 기준으로 확인함

## Ⅶ. 결론

- MongoDB는 문서 구조와 변화가 많은 데이터를 빠르게 다루는 데 강하지만 문서 경계와 샤드 키와 중복 관리 원칙을 함께 세워야 장점이 유지됨
