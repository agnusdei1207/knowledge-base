## 미리 알고가기

- 이벤트 브로커는 생산자와 처리기를 분리하고 이벤트를 파티션 로그에 보존함
- 스트림 처리 엔진은 필터·조인·윈도·집계를 연속 데이터에 적용함
- 이벤트 시간은 이벤트 발생 시각이며 워터마크가 시간 진행과 윈도 종료를 판단함
- 상태 저장소는 키별 집계·조인·패턴 탐지의 중간 상태를 보존함
- 서빙 계층은 처리 결과를 DB·검색 색인·캐시·분석 저장소에 제공함
- 소비 지연량은 브로커의 최신 오프셋과 처리 완료 오프셋의 차이임

## 작성 근거(검토용)

- 실시간 플랫폼은 수집·영속 버퍼·상태 처리·서빙·복구를 하나의 종단 간 구조로 설명함
- 비교표는 Kafka·Flink·Spark Structured Streaming의 역할과 위치·실행과 시간 처리·상태와 복구를 구분함
- 절차는 이벤트 기록부터 상태 연산과 싱크 반영까지 데이터 상태가 실제로 변하는 순서를 사용함
- 제목부터 결론까지 모든 문장·표 셀·요약을 5회 전수 검수해 계층별 역할과 선택 기준을 연결함

## Ⅰ. 개요

- **정의/개념**: 실시간 스트리밍 플랫폼은 계속 유입되는 이벤트를 수집·보존·연산하고 결과를 운영 시스템과 분석 저장소에 전달하는 처리 구조임
- **배경/필요성**: 이벤트 발생과 업무 판단 사이의 지연을 줄이고 장애 후 입력·상태·결과를 복구하기 위해 영속 버퍼와 상태 처리 계층이 필요함

## Ⅱ. 특징

- 이벤트 브로커가 생산 속도와 처리 속도의 차이를 흡수하고 재처리 가능한 로그를 제공함
- 파티션 키가 이벤트 순서 범위와 처리 병렬도를 함께 결정함
- 처리 엔진이 이벤트 시간·워터마크·키별 상태로 윈도·조인·패턴을 계산함
- 체크포인트와 싱크 커밋이 장애 후 상태 복구 지점과 중복 결과 범위를 결정함
- 스키마 호환성과 계보로 생산자 변경 영향을 찾고 소비 지연량·역압력으로 처리 병목을 확인함

## Ⅲ. 종류 및 비교

| 판단 기준 | Apache Kafka | Apache Flink | Spark Structured Streaming |
|:---|:---|:---|:---|
| 역할·위치 | 이벤트 영속 저장·전달을 담당하는 수집·버퍼·이벤트 허브 | 상태 기반 연속 스트림 처리를 담당하는 저지연 상태 연산 계층 | SQL 기반 증분 스트림 처리를 담당하는 배치·SQL 통합 처리 계층 |
| 실행·시간 처리 | 파티션 로그의 생산·소비로 이벤트 시각을 레코드로 전달 | 레코드·연산자 Subtask 단위로 워터마크·타이머가 윈도를 제어 | 마이크로배치·파티션 Task 단위로 워터마크·트리거가 결과를 갱신 |
| 상태·복구 | 소비 오프셋·트랜잭션 상태를 복제 로그와 커밋 오프셋으로 복구 | Keyed State·Checkpoint를 상태 스냅샷과 소스 재생으로 복구 | State Store·Checkpoint를 체크포인트와 입력 로그 재실행으로 복구 |

> 요약: 실시간 플랫폼은 Kafka가 이벤트를 보존하고 Flink나 Spark가 상태를 계산한 뒤 싱크에 결과를 반영하는 구조로 구성함.

## Ⅳ. 구성요소 및 구조

| 구성요소 | 설명 |
|:---|:---|
| 생산자·커넥터 | 응용·DB·로그의 이벤트를 공통 스키마로 수집함 |
| 브로커·파티션 로그 | 이벤트를 키별 파티션에 보존하고 처리 계층과 생산자를 분리함 |
| 스트림 처리기 | 필터·조인·윈도·패턴 연산을 병렬 실행함 |
| 상태·체크포인트 | 키별 중간 결과와 복구 가능한 입력 위치를 저장함 |
| 싱크·서빙 저장소 | 처리 결과를 운영 DB·색인·분석 테이블에 반영함 |
| 스키마 레지스트리 | 이벤트 스키마 버전과 생산자·소비자 호환성을 관리함 |
| 관측 계층 | 소비 지연량·역압력·실패·재처리 상태를 수집함 |

```text
응용·DB -> 브로커·파티션 -> 스트림 처리기 -> 서빙 저장소
               |                    |
          스키마·오프셋        상태·체크포인트
```

> 요약: 브로커가 이벤트를 영속 버퍼링하고 처리 엔진이 상태 연산한 결과를 서빙 저장소에 전달함.

## Ⅴ. 원리 및 절차 흐름도

```text
이벤트 수집 -> 파티션 로그 기록 -> 상태 연산 -> 복구점 확정 -> 싱크 반영
```

1. **이벤트 수집**: 생산자가 스키마와 키를 포함한 이벤트를 브로커에 전송함
2. **로그 기록**: 브로커가 키로 파티션을 정하고 복제 로그에 이벤트를 보존함
3. **상태 연산**: 처리 엔진이 이벤트 시간과 키별 상태로 필터·조인·윈도를 계산함
4. **복구점 확정**: 입력 위치와 처리 상태를 체크포인트로 저장함
5. **결과 반영**: 싱크가 트랜잭션 또는 멱등 쓰기로 서빙 저장소에 결과를 기록함

> 요약: 입력 위치와 처리 상태를 체크포인트에 저장한 뒤 싱크 결과를 서빙 저장소에 반영함.

## Ⅵ. 실무 사례

1. 서버 이상 탐지는 로그를 서비스별로 파티셔닝하고 이벤트 처리 지연·역압력 시간을 확인함
2. 주문 상태 집계는 이벤트 시간 윈도와 멱등 싱크를 적용하고 종단 간 지연·중복 건수를 확인함

## Ⅶ. 결론

- 실시간 플랫폼은 이벤트 순서·지연 목표·상태 크기·장애 복구 수준과 싱크 반영 방식을 기준으로 구성해야 함
