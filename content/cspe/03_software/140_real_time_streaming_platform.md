# 📖 【암기용】 개념 완전 이해

## 한눈에
- **개요**: 끝없이 발생하는 방대한 이벤트 데이터를 저장소에 쌓아두기 전에, 흘러가는 찰나의 순간에 포착하여 분석하고 즉시 대응하는 엔드투엔드(End-to-End) 아키텍처다.
- **왜 필요한가**: 과거의 일괄 처리(배치)는 "어제 무슨 일이 있었지?"를 알려주지만, 현대 비즈니스는 "지금 이 순간 고객이 무엇을 찾고, 어디서 신용카드 사기가 발생하고 있는가?"를 수 초 내에 알아야 하기 때문이다.
- **핵심 직관**: 거대한 저수지에 물이 꽉 찰 때까지 기다렸다가 수질을 검사하는 게 아니라, 상수도관에 탐지기를 달아 물이 지나가는 즉시 수질을 측정하고 문제가 있으면 바로 차단기를 내리는 시스템.

## 핵심 용어 정리 (내부에 등장하는 것들)

| 용어/표기 | 의미 | 비유·예 |
|:---|:---|:---|
| Ingestion (수집) | 다양한 소스(DB, 웹, 모바일)에서 발생하는 이벤트를 실시간으로 빨아들임 | "강물이 모이는 취수구" |
| Message Broker (버퍼링) | 쏟아지는 데이터를 잃어버리지 않게 충격을 흡수하고 순서를 기록함 (Kafka 등) | "유량을 조절하는 임시 댐" |
| Stream Engine (연산) | 지나가는 데이터에 필터링, 집계, 패턴 매칭(CEP) 등 로직을 실시간 적용 | "흐르는 물의 수질을 실시간 검사하는 필터/센서" |
| Sink / Serving (표출) | 분석된 결과를 알림으로 쏘거나 대시보드 및 실시간 조회 DB에 저장 | "정수된 물을 각 가정으로 내보내고 계기판에 표시" |

## 깊이 이해
- **배경·문제의식**: 스마트폰과 IoT 등장으로 데이터 생성 주기가 '일' 단위에서 '밀리초' 단위로 단축되었다. 하둡 같은 배치 시스템은 디스크에 다 저장한 뒤에 쿼리를 돌려 응답 지연(Latency)이 몇 시간에 달했다. 실시간 추천, 게임 부정 사용자 적발, 금융 이상 거래 탐지(FDS) 등 골든 타임이 중요한 업무를 위해 "데이터를 먼저 처리하고 나중에 저장하자"는 패러다임 전환이 일어났다.
- **작동 원리**: 데이터 파이프라인은 크게 3단계다.
  1. **소스/수집**: 앱 로그나 RDBMS의 변경분(CDC)을 잡아채 카프카 같은 브로커에 쏜다.
  2. **스트림 연산**: Spark Streaming, Flink가 브로커에서 이벤트를 1건 단위(또는 아주 짧은 윈도우)로 꺼내 조건에 맞는지, 5분 내 3번 시도가 있었는지 패턴을 검사(Stateful 연산)한다. 지연된 데이터(Late arrival)도 워터마크 기술을 이용해 제자리에 끼워 넣는다.
  3. **결과 서빙**: 결과를 Redis나 Elasticsearch 같은 빠른 인메모리/검색 DB에 꽂아 대시보드로 보여주거나, 푸시 알림 서버로 넘긴다.
- **비유**: 공항 보안 검색대. 승객 1만 명이 탈 때까지 기다렸다가 한 번에 명단을 검사(배치)하는 게 아니라, 엑스레이 검색대를 통과하는 즉시 수하물 안에 위험물이 있는지 확인하고 경보를 울린다(스트리밍).
- **구체 예시**: 넷플릭스가 사용자의 시청 멈춤, 되감기 버튼 클릭 이벤트를 실시간 수집해 카프카로 보내면, Flink가 이를 5분 단위로 집계해 "이 지역 통신망에 동영상 버퍼링 장애가 발생했다"는 경보를 실시간 CDN 서버에 띄워 트래픽 우회 경로를 자동 설정한다.
- **흔한 오해·주의점**: 실시간 플랫폼 구축은 돈과 인프라가 매우 많이 든다. 브로커, 스트림 엔진, 빠른 서빙 DB까지 다기종 서버를 24시간 띄워놔야 하므로, 1시간 지연 정도는 허용되는 단순 리포트 업무라면 굳이 비싼 스트리밍 플랫폼을 도입할 필요가 없다.

# 📝 【답안용】 시험 답안 템플릿

## 핵심 인사이트 (3줄 요약)

> 1. **본질**: 실시간 스트리밍 플랫폼은 무한히 생성되는 이벤트 데이터를 저장소 적재 전 인플라이트(In-flight) 상태에서 즉시 연산하여 가치를 추출하는 파이프라인 아키텍처다.
> 2. **가치**: 빅데이터의 응답 지연(Latency)을 밀리초(ms) 단위로 줄여, 사기 탐지(FDS), 초개인화 추천, 이상 징후 자동 복구 등 데이터 기반의 즉각적 비즈니스 액션을 가능하게 한다.
> 3. **판단 포인트**: 메시지 버퍼(Broker)와 연산 엔진(Stream Processor) 간의 정합성(Exactly-once) 유지와 시스템 복잡도 증가에 따른 TCO(총소유비용) 최적화가 성패를 가른다.

## 출제 의도 및 답안 포인트

| 출제 의도 | 반드시 짚을 핵심 | 감점 회피 포인트 |
|:---|:---|:---|
| 데이터 처리 패러다임 전환 이해 | In-flight 처리, Latency 감축, 파이프라인 구성 요소 | 배치 아키텍처 기술(HDFS 등)을 중심으로 서술 |
| 실시간 아키텍처 구성 요소 및 연계 역량 | 수집(CDC/Log) - 버퍼(Kafka) - 연산(Flink) - 서빙(NoSQL) | 특정 솔루션 기능 설명에만 치중 |
| 스트림 처리의 기술적 난제 통제 방안 | 지연 도착 데이터 처리(Watermark), 상태 관리 보존 | 실시간 처리를 맹목적으로 무결하다고 포장 |

> 요약: 실시간 플랫폼은 단순히 속도가 빠른 것이 아니라, 끊임없는 데이터를 끊김 없이 통제하기 위한 3단계(수집-버퍼-연산) 인프라의 유기적 결합임을 보여야 한다.

## Ⅰ. 개요 및 필요성

- 개요: 다양한 소스에서 끝없이 발생하는 방대한 이벤트 스트림을 수집부터 분석, 활용까지 종단 간(End-to-End) 저지연으로 처리하는 통합 시스템
- 배경: 과거 데이터를 분석하는 배치 중심 아키텍처로는 시시각각 변하는 고객 행동과 시스템 이상 징후에 대한 '골든 타임' 내 대응 불가능
- 필요성: 모바일, IoT 등 실시간 이벤트 폭증 환경에서 데이터가 지닌 비즈니스 가치의 급격한 반감(Time-Value Decay)을 막기 위한 즉각적 액션 체계 필수

---

## Ⅱ. 구조 및 구성요소

```text
[Sources] -> [Ingestion / Buffer] -> [Stream Processing] -> [Serving / Sink]
Web Log         Apache Kafka            Apache Flink           Redis / Elasticsearch
DB CDC    --->  (토픽 버퍼링, 복제) ---> (Stateful 윈도우 연산) ---> 실시간 대시보드
IoT Sensor      (스파이크 흡수)         (Event-Time 처리)      알림/트리거 API
```

| 구성요소 | 역할 | 특이사항 |
|:---|:---|:---|
| Source & Ingestion | RDBMS 변경분(CDC) 및 앱 로그를 경량 에이전트로 실시간 추출 | 시스템 부하 최소화가 핵심 |
| Message Buffer | 트래픽 스파이크를 흡수(Shock Absorber)하고 이벤트 순서 영속화 보장 | 분산 브로커(Kafka 등)의 내결함성 의존 |
| Stream Processing | 데이터 스트림을 필터링, 조인, 집계 및 복잡 이벤트 패턴(CEP) 탐지 | 상태(State) 보존 및 지연 데이터 제어 |
| Serving / Action | 처리된 결과를 빠른 읽기용 인메모리 DB나 검색 엔진에 적재 후 표출 | 타 시스템 API 호출(Webhook) 병행 |

> 요약: 생성 즉시 버퍼로 받아내고 스트림 엔진이 연산한 뒤 빠른 DB로 표출하는 물 흐르듯 끊임없는 구조다.

---

## Ⅲ. 동작원리 및 흐름도

```text
이벤트 발생 -> CDC / Agent 수집 -> 브로커 파티션 분산 저장 -> 스트림 윈도우 집계 및 상태 보존 -> 결과 NoSQL 적재
```

- 1단계 [고속 수집 및 버퍼링]: 발생한 이벤트를 Kafka 토픽에 순차 기록하여 수집 속도와 분석 속도의 격차(Backpressure)를 해소
- 2단계 [인플라이트(In-flight) 연산]: 디스크에 데이터를 영구 저장하기 전에 메모리를 지나는 시점에 Flink/Spark가 즉각적으로 필터 및 집계 연산 수행
- 3단계 [시간·상태 보정]: 네트워크 지연으로 늦게 도착한 데이터는 워터마크(Watermark)로 적합한 시간 윈도우에 재배치하고, 연산 중단 대비 스냅샷 기록
- 4단계 [실시간 서빙 및 액션]: 최종 뷰를 조회 성능이 수 밀리초인 Redis에 업데이트하거나, FDS/추천 서버에 직접 트리거 신호 전송

> 요약: 스토리지 적재 후 읽는 병목을 없애고, 데이터가 메모리에 떠 있는 상태에서 계산과 알림을 종료한다.

---

## Ⅳ. 특징
- [비즈니스 민첩성]: 고객 이탈 징후, 장바구니 방치, 시스템 임계치 초과 등을 즉시 인지하여 실시간 마케팅 및 자동 복구 달성
- [내결함성(Fault Tolerance)]: 스트림 엔진이 다운되어도 메시지 버퍼에 데이터가 남아있고 상태 스냅샷이 있어 재시작 시 유실 없이(Exactly-Once) 복원
- [높은 운영 복잡도]: 브로커 클러스터, 분산 엔진 클러스터, 인메모리 DB를 모두 무중단으로 관리해야 하므로 인프라 TCO와 장애 대응 난이도가 급증

> 요약: 강력한 실시간 비즈니스 무기를 얻는 대가로, 다기종 분산 시스템을 24시간 감시해야 하는 고난도 운영 역량이 요구된다.

## Ⅴ. 심화 비교 및 적용 판단

| 비교 축 | 대안 (Data Warehouse) | 본 키워드 (Streaming Platform) | 선택 기준 |
|:---|:---|:---|:---|
| 데이터 패러다임 | Data at Rest (정지된 데이터 풀) | Data in Motion (움직이는 흐름) | 비즈니스 가치 산출의 시간 임계성 |
| 최적화 지표 | Throughput (대량 처리량) 중심 | Latency (밀리초 지연율) 중심 | 사용자 응답성 SLA |
| 질의(Query) 구조 | 저장된 데이터에 정적 쿼리 수행 | 정지된 쿼리에 데이터가 지속 통과 | 분석 패턴의 고정 여부 (룰 기반 감지 등) |

> 요약: 전체 트렌드 분석과 재무 정산은 데이터 웨어하우스(배치)에 맡기고, 이상 탐지와 즉각적 대응은 스트리밍 플랫폼에 분리 위임해야 단다.

**리스크·대응 (기본은 불릿):**
- [백프레셔(Backpressure) 폭증]: 연산 엔진 처리 속도보다 데이터 유입 속도가 빠를 경우 메모리 마비 → 버퍼(Kafka) 파티션 스케일아웃 및 연산 엔진 동적 리소스 확장, 중요도 낮은 스트림 드랍 정책 도입 (지표: Consumer Lag 차트)
- [지연 도착 데이터 유실]: 모바일 음영 지역 등으로 과거 시간대 이벤트가 늦게 도달해 집계 오류 발생 → Allowed Lateness 옵션 적용 및 워터마크 임계치 조정을 통한 지연 데이터 윈도우 재계산

**도입 후 점검 지표 (기본은 불릿):**
- 성능/효율: 이벤트 발생(소스)부터 대시보드 반영(서빙)까지의 End-to-End 레이턴시 p95 기준 1초 이내 달성 여부 — 분산 트레이싱 APM 연동
- 품질/운영: 스트리밍 인프라 장애 발생 후 자동 복구 소요 시간 및 데이터 무결성 — 카오스 테스트를 통한 복구 RTO 측정

## Ⅵ. 실무 적용 및 결론

**적용 방안 3개:**
1. 아키텍처 카파(Kappa) 전환: 데이터 파이프라인 복잡도 감소를 위해 람다(배치+스트림 이중화) 구조를 폐기하고, Kafka+Flink 조합의 단일 스트림 기반 통합 아키텍처 구축
2. CDC 연동 고도화: 메인 RDBMS의 트랜잭션 로그를 Debezium 같은 도구로 실시간 캡처(CDC)해 스트림 파이프라인 소스로 편입하여 운영 DB 부하 없이 데이터 복제 및 캐시 무효화 자동 수행
3. KSQL / Flink SQL 도입: 데이터 엔지니어뿐 아니라 분석가도 실시간 뷰를 즉각 생성할 수 있도록 선언적 SQL 인터페이스 환경 제공으로 스트림 분석 접근성 확대

**결론 (2줄):**
- 기술사 판단: 실시간 스트리밍 플랫폼은 현대 비즈니스의 '순발력'을 담보하는 필수 인프라지만, 높은 도입 비용을 고려해 FDS나 초개인화 타겟팅 등 명확한 ROI가 나오는 도메인에 선별적으로 적용해야 한다.
- 향후 방향: 인프라 복잡도를 숨겨주는 클라우드 네이티브 기반 매니지드 서버리스 스트리밍 서비스(e.g., Kinesis, Confluent)와 AI 모델을 스트림 상에서 직접 추론하는 AI-Streaming 융합으로 발전할 것이다.
