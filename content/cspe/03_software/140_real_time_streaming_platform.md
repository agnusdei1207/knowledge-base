## 미리 알고가기

- 이벤트 브로커는 생산자와 처리기를 분리하고 이벤트를 파티션 로그에 보존함
- 스트림 처리 엔진은 필터·조인·윈도·집계를 연속 데이터에 적용함
- 이벤트 시간은 이벤트 발생 시각이며 워터마크가 시간 진행과 윈도 종료를 판단함
- 상태 저장소는 키별 집계·조인·패턴 탐지의 중간 상태를 보존함
- 서빙 계층은 처리 결과를 DB·검색 색인·캐시·분석 저장소에 제공함
- 소비 지연량은 브로커의 최신 오프셋과 처리 완료 오프셋의 차이임

## 작성 근거(검토용)

- 실시간 플랫폼은 수집·영속 버퍼·상태 처리·서빙·복구를 하나의 종단 간 구조로 설명함
- 비교표는 Kafka·Flink·Spark Structured Streaming의 역할·실행·시간·상태·복구·적합 위치를 구분함
- 절차는 이벤트 기록부터 상태 연산과 싱크 반영까지 데이터 상태가 실제로 변하는 순서를 사용함
- 제목부터 결론까지 모든 문장·표 셀·요약을 5회 전수 검수해 계층별 역할과 선택 기준을 연결함

## Ⅰ. 개요

- **정의/개념**: 실시간 스트리밍 플랫폼은 지속 이벤트를 수집·보존·연산하고 결과를 운영 시스템과 분석 저장소에 전달하는 처리 구조임
- **배경/필요성**: 이벤트 발생과 업무 판단 사이의 지연을 줄이고 장애 후 입력·상태·결과를 복구하기 위해 영속 버퍼와 상태 처리 계층이 필요함

## Ⅱ. 특징

- 이벤트 브로커가 생산 속도와 처리 속도의 차이를 흡수하고 재처리 가능한 로그를 제공함
- 파티션 키가 이벤트 순서 범위와 처리 병렬도를 함께 결정함
- 처리 엔진이 이벤트 시간·워터마크·키별 상태로 윈도·조인·패턴을 계산함
- 체크포인트와 싱크 커밋이 장애 후 상태 복구와 중복 결과 범위를 결정함
- 스키마·계보·소비 지연량·역압력을 함께 관찰해 생산자부터 소비자까지 변경 범위를 통제함

## Ⅲ. 종류 및 비교

| 판단 기준 | Apache Kafka | Apache Flink | Spark Structured Streaming |
|:---|:---|:---|:---|
| 주 역할 | 이벤트 영속 저장·전달 | 상태 기반 연속 스트림 처리 | SQL 기반 증분 스트림 처리 |
| 실행 단위 | 파티션 로그의 생산·소비 | 레코드와 연산자 Subtask | 마이크로배치와 파티션 Task |
| 시간 처리 | 이벤트 시각을 레코드로 전달 | 워터마크·타이머로 윈도 제어 | 워터마크·트리거로 결과 갱신 |
| 상태 관리 | 소비 오프셋과 트랜잭션 상태 | Keyed State·Checkpoint | State Store·Checkpoint |
| 장애 복구 | 복제 로그와 커밋 오프셋 | 상태 스냅샷과 소스 재생 | 체크포인트와 입력 로그 재실행 |
| 플랫폼 위치 | 수집·버퍼·이벤트 허브 | 저지연 상태 연산 계층 | 배치·SQL과 통합한 처리 계층 |

> 요약: 실시간 플랫폼은 Kafka가 이벤트를 보존하고 Flink나 Spark가 상태를 계산한 뒤 싱크에 결과를 반영하는 구조로 구성함.

## Ⅳ. 구성요소 및 구조

| 구성요소 | 설명 |
|:---|:---|
| Producer·Connector | 응용·DB·로그의 이벤트를 공통 스키마로 수집함 |
| Broker·Partition Log | 이벤트를 키별 파티션에 보존하고 처리 계층과 생산자를 분리함 |
| Stream Processor | 필터·조인·윈도·패턴 연산을 병렬 실행함 |
| State·Checkpoint | 키별 중간 결과와 복구 가능한 입력 위치를 저장함 |
| Sink·Serving Store | 처리 결과를 운영 DB·색인·분석 테이블에 반영함 |
| Schema Registry | 이벤트 스키마 버전과 생산자·소비자 호환성을 관리함 |
| Observability | 소비 지연량·역압력·실패·재처리 상태를 수집함 |

```text
응용·DB -> Broker·Partition -> Stream Processor -> Serving Store
               |                    |
          Schema·Offset       State·Checkpoint
```

> 요약: 브로커가 이벤트를 영속 버퍼링하고 처리 엔진이 상태 연산한 결과를 서빙 저장소에 전달함.

## Ⅴ. 원리 및 절차 흐름도

```text
이벤트 수집 -> 파티션 로그 기록 -> 상태 연산 -> 복구점 확정 -> 싱크 반영
```

1. **이벤트 수집**: Producer가 스키마와 키를 포함한 이벤트를 브로커에 전송함
2. **로그 기록**: 브로커가 키로 파티션을 정하고 복제 로그에 이벤트를 보존함
3. **상태 연산**: 처리 엔진이 이벤트 시간과 키별 상태로 필터·조인·윈도를 계산함
4. **복구점 확정**: 입력 위치와 처리 상태를 체크포인트로 저장함
5. **결과 반영**: 싱크가 결과를 원자적 또는 멱등 방식으로 서빙 저장소에 기록함

> 요약: 수집 이벤트는 파티션 로그와 상태 연산을 거쳐 복구점과 연계된 싱크 결과로 확정됨.

## Ⅵ. 실무 사례

1. 서버 이상 탐지는 로그를 서비스 키로 분할하고 이벤트 처리 지연·역압력 시간을 확인함
2. 주문 상태 집계는 이벤트 시간 윈도와 멱등 싱크를 적용하고 종단 간 지연·중복 건수를 확인함

## Ⅶ. 결론

- 실시간 플랫폼은 이벤트 순서·지연 목표·상태 크기·복구 보장과 싱크 반영 방식을 기준으로 구성해야 함
