## Ⅰ. 개요
- **정의**: API 변경 시 하위 호환성을 유지하면서 신·구 버전을 공존시키는 관리 전략
- **배경/필요성**: API 스키마 변경이 기존 소비자를 중단시키지 않도록 버전 전환 체계가 필요함
- **비유**: 도로를 확장할 때 기존 차선은 유지하면서 새 차선을 추가하는 것과 유사함

| 출제 의도 | 반드시 짚을 핵심 | 감점 회피 포인트 |
|:---|:---|:---|
| API 진화 전략 이해 | URI·Header·Query 방식 비교 | 버전 관리와 하위 호환성 관계 명시 |

> 요약: 하위 호환성을 보장하면서 API를 점진적으로 진화시키는 관리 전략임

## Ⅱ. 구성요소
```text
Client --> [API Gateway] --v1--> Service v1
                          --v2--> Service v2
                |
         Version Router
```

| 구성요소 | 설명 | 비유 |
|:---|:---|:---|
| Version Identifier | URI·Header·Query 등에 포함되는 버전 식별 값 | 차선 번호 |
| API Gateway | 버전별 요청을 적절한 서비스 인스턴스로 라우팅하는 진입점 | 톨게이트 |
| Deprecation Policy | 구버전 폐기 일정·공지 절차를 규정하는 정책 | 차선 폐쇄 예고 안내 |
| Compatibility Layer | 신·구 버전 간 데이터 변환을 담당하는 어댑터 | 차선 합류 유도선 |

> 요약: Version ID-Gateway-Deprecation-Compatibility 4요소로 버전 공존을 관리함

## Ⅲ. 절차
```text
버전 전략 수립 --> 신버전 배포 --> 병행 운영 --> 구버전 폐기
      |                |              |             |
      v                v              v             v
  방식 선택       라우팅 설정     마이그레이션 안내   Sunset 처리
```
- 1단계: URI Path·Header·Query 중 버전 관리 방식을 선택함
- 2단계: API Gateway에 신버전 라우팅 규칙을 등록하고 배포함
- 3단계: 신·구 버전을 병행 운영하며 소비자에게 마이그레이션을 안내함
- 4단계: Deprecation 기간 경과 후 구버전을 Sunset(폐기)함

> 요약: 전략수립-배포-병행운영-폐기 4단계로 API 버전을 관리함

## Ⅳ. 문제점
- 다중 버전 유지 비용: 동시 운영 버전이 늘어날수록 테스트·운영 부담이 증가함
- 소비자 마이그레이션 지연: 구버전 소비자가 전환하지 않아 폐기 시점이 지연됨
- 전략 불일치: 팀별 상이한 버전 방식(URI/Header 혼재)이 일관성을 저해함

> 요약: 유지 비용·마이그레이션 지연·전략 불일치가 주요 과제임

## Ⅴ. 개선방안
1. 단기: 동시 운영 버전 수 상한(예: 최대 2개)을 정책으로 제한
2. 중기: 소비자별 사용 버전 모니터링 + 자동 알림으로 전환 촉진
3. 장기: 조직 전체 버전 관리 표준(Semantic Versioning 등) 수립으로 일관성 확보

> 요약: 버전 상한-전환 모니터링-표준화 순으로 개선함

## Ⅵ. 전망
- 발전 방향: API-First 설계와 결합하여 계약 기반 버전 관리가 표준화 중임
- 기술사적 판단: API 경제 확산으로 버전 관리 거버넌스의 중요성이 증가함
- 기술사 제언: OpenAPI Spec과 CI/CD 파이프라인 내 호환성 자동 검증 체계를 구축할 필요
