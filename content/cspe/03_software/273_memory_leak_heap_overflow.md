## Ⅰ. 개요
- **정의**: 더 이상 사용하지 않는 메모리가 해제되지 않아 가용 힙이 점진적으로 고갈되는 현상
- **배경/필요성**: GC 환경에서도 의도치 않은 참조 유지로 누수가 발생하므로 탐지·예방 체계가 필요함
- **비유**: 쓰지 않는 물건을 버리지 않아 창고가 꽉 차서 새 물건을 넣지 못하는 상황과 유사함

| 출제 의도 | 반드시 짚을 핵심 | 감점 회피 포인트 |
|:---|:---|:---|
| 누수 원인·탐지·방지 기법 | 참조 유지 패턴, 힙 덤프 분석 | 메모리 누수와 버퍼 오버플로(보안 취약점)를 구분할 것 |

> 요약: 불필요 참조가 유지되어 힙이 고갈되는 현상이며, GC 언어에서도 발생함

## Ⅱ. 구성요소
```text
Application
  +-- Object Graph
  |     +-- Live Ref (정상)
  |     +-- Stale Ref (누수 원인)
  +-- Heap
        +-- Used (증가)
        +-- Free (감소) --> OOM
```

| 구성요소 | 설명 | 비유 |
|:---|:---|:---|
| Stale Reference | 로직상 불필요하나 컬렉션·캐시 등에 남아 있는 참조 | 퇴사자 사물함 키를 회수하지 않은 상태 |
| Heap Dump | 특정 시점의 힙 메모리 스냅샷으로 객체 참조 그래프를 분석 | 창고 재고 목록 전수 조사표 |
| Dominator Tree | 특정 객체 해제 시 함께 회수 가능한 객체 트리 | 나무 뿌리를 뽑으면 따라 빠지는 가지들 |
| Allocation Tracker | 객체 할당 위치·빈도를 기록하는 프로파일링 도구 | 물건 반입 기록을 남기는 입고 대장 |

> 요약: 잔류 참조가 누수의 근원이며, 힙 덤프·도미네이터 트리로 식별함

## Ⅲ. 절차
```text
증상 감지 -> 힙 덤프 수집 -> 누수 객체 식별 -> 참조 경로 제거
```
- 1단계: 힙 사용량 모니터링에서 우상향 추세(Sawtooth 미복귀) 감지
- 2단계: `jmap`·`heapdump` 등으로 두 시점의 힙 덤프를 수집하여 비교
- 3단계: 도미네이터 트리에서 Retained Size가 큰 객체의 GC Root 경로를 추적
- 4단계: 잔류 참조를 제거하고(`WeakReference` 전환, 컬렉션 `clear` 등) 재검증

> 요약: 모니터링 → 덤프 비교 → 루트 경로 추적 → 참조 제거 순서로 해결함

## Ⅳ. 문제점
- 지연 발현: 누수가 누적되어 OOM이 발생하기까지 수 시간~수 일 소요되어 재현이 어려움
- 탐지 비용: 힙 덤프 수집 시 STW가 발생하고 덤프 파일이 수 GB에 달함
- 원인 모호성: 서드파티 라이브러리 내부의 잔류 참조는 소스 수정이 불가함

> 요약: 지연 발현, 탐지 비용, 서드파티 원인 모호성이 주요 문제임

## Ⅴ. 개선방안
1. 단기: 연속 힙 사용률 모니터링 알림을 설정하여 조기 감지 체계 구축
2. 중기: CI 파이프라인에 메모리 프로파일링 테스트를 통합하여 회귀 방지
3. 장기: `WeakReference`·`PhantomReference` 기반 캐시 설계로 구조적 누수 차단

> 요약: 조기 감지, CI 통합 프로파일링, 약한 참조 설계로 각 문제에 대응함

## Ⅵ. 전망
- 발전 방향: APM 도구의 실시간 누수 탐지 자동화와 AI 기반 이상 패턴 탐지 확산
- 기술사적 판단: 컨테이너 메모리 제한 환경에서 누수 1건이 Pod 재시작으로 직결됨
- 기술사 제언: 메모리 버짓을 설계 단계에서 정의하고 부하 테스트 시 힙 추세를 검증할 필요
