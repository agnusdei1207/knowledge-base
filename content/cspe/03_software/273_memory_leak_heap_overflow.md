# 📖 【암기용】 개념 완전 이해

> 목적: 이 개념을 처음 보는 사람도 완벽히 이해하게 만든다. 시험 답안 양식이 아니라, 이해를 위한 친절한 설명이다.

## 한눈에
- **개요**: 메모리 누수와 힙 오버플로우는 **동적 메모리 관리**(Dynamic Memory Management)의 두 가지 대표 결함으로, 둘 다 **힙**(Heap)이라는 동적 할당 영역에서 발생하지만 원인은 정반대다 — 누수는 "안 지운 것", 오버플로우는 "경계를 넘은 것".
- **왜 필요한가**: 장시간 실행되는 서버 프로세스에서 누수는 서서히 메모리를 고갈시켜 OOM을 만들고, 오버플로우는 즉각적인 크래시뿐 아니라 원격 코드 실행(RCE) 취약점으로 이어질 수 있어 원인별로 다른 탐지·대응 체계가 필요하다.
- **핵심 직관**: 누수는 "다 쓴 렌탈 장비를 반납 목록에서 안 지워 창고가 계속 차는 문제"이고, 오버플로우는 "상자 크기보다 큰 짐을 억지로 밀어 넣어 옆 상자까지 망가뜨리는 문제"다.

## 핵심 용어 정리 (내부에 등장하는 것들)

| 용어 | 의미 | 비유 |
|:---|:---|:---|
| 동적 메모리 관리 | 실행 중 필요한 만큼 메모리를 할당·해제하는 방식 — 이 문서 전체의 상위 주제 | 그때그때 필요한 만큼 창고 공간을 빌리고 반납 |
| 힙(Heap) | 런타임에 크기가 정해지는 객체·버퍼를 담는 메모리 영역(스택과 대비) | 자유롭게 칸을 빌려 쓰는 대형 창고 |
| 참조(Reference)/도달 가능성 | GC가 "이 객체가 아직 쓰이는가"를 판단하는 유일한 기준 — 어딘가에서 가리키고 있으면 도달 가능 | 창고 대장에 이름이 남아 있으면 아직 쓰는 물건 |
| 가비지 컬렉션(GC) | 도달 불가능한 객체를 자동으로 찾아 회수하는 런타임 기능(Java, Go 등) | 대장에서 지워진 물건만 자동으로 치워주는 관리인 |
| 메모리 누수(Memory Leak) | 더는 쓰지 않는데도 참조가 남아 GC가 회수하지 못하는 객체가 누적되는 것 | 반납 안 된 렌탈 장비가 대장에 계속 남아 창고를 잠식 |
| 버퍼(Buffer) | 정해진 크기로 할당된 연속 메모리 블록(배열, 문자열 등) | 정해진 칸 크기의 상자 |
| 힙 오버플로우(Heap Overflow) | 버퍼에 할당된 크기를 넘어서 쓰는 것 — 경계 검사가 없는 언어(C/C++)에서 주로 발생 | 상자 크기보다 큰 짐을 억지로 밀어 넣어 옆 상자를 침범 |
| 힙 메타데이터 | 할당기가 각 청크의 크기·다음 빈 블록 위치를 기록해 두는 관리 정보 — 오버플로우가 이걸 덮으면 free() 시 임의 주소 조작까지 가능 | 창고 관리대장 — 이게 찢기면 다음에 뭘 어디 둘지 알 수 없음 |
| OOM(Out Of Memory) | 가용 힙이 모두 소진되어 프로세스가 강제 종료되는 상태 | 창고가 꽉 차 더는 물건을 못 받는 상태 |
| ASan/Valgrind | 실행 중 경계 위반·누수를 탐지하는 계측 도구 | 상자 앞뒤에 CCTV를 달아 침범을 즉시 잡아냄 |
| retained heap / dominator tree | 특정 객체 하나를 없애면 함께 사라질 메모리 총량을 계산해 누수 원흉을 찾는 분석 기법 | "이 물건 하나 치우면 딸려 나가는 짐이 얼마나 되나" 추적 |

## 깊이 이해

### 메모리 누수가 쌓이는 속도 — 수치로 확인
- GC는 "쓸모없음"을 판단하지 못하고 오직 "도달 가능한가"만 판단한다. `static Map<String, Request>`처럼 프로세스 생존 기간 내내 살아있는 객체(static 필드, 리스너, ThreadLocal, 캐시)에 요청 객체를 넣고 지우지 않으면, GC 입장에서는 여전히 "도달 가능"하므로 절대 회수되지 않는다.
- 예: 초당 100건의 요청을 처리하며 매번 1KB 객체를 static Map에 추가하고 안 지우면, 초당 100KB, 시간당 360MB, 하루(86,400초)면 약 8.6GB가 누적된다. 힙 상한이 4GB인 프로세스라면 몇 시간 안에 old generation이 가득 차 Full GC가 반복되다 결국 OOM으로 죽는다.
- 판별 지표: heap dump를 두 시점(예: 1시간 간격)에 뜬 뒤 diff하면 어떤 클래스의 인스턴스 수가 계속 증가하는지 보인다. dominator tree 상위 항목이 누수 원흉일 확률이 높다.

### 힙 오버플로우가 나는 지점 — 수치로 확인
- C의 `char buf[64]; strcpy(buf, input);`에서 input이 100바이트라면, 64바이트 경계를 36바이트 초과해서 쓴다. 할당기는 각 청크 앞뒤에 크기·링크 정보를 담은 메타데이터(보통 8~16바이트)를 두는데, 이 36바이트 초과분이 바로 다음 청크의 헤더를 덮으면 `free()` 호출 시 조작된 포인터를 따라가 임의 주소에 쓰기가 발생할 수 있다(CWE-122 계열) — 이것이 오버플로우가 크래시를 넘어 RCE로 이어지는 경로다.
- 판별 원리: C/C++는 배열 접근에 컴파일 타임·런타임 경계 검사가 없다(포인터 산술이 그대로 허용됨). 반면 Java 배열, Rust 슬라이스는 접근 시 런타임 경계 검사를 강제해 범위를 넘으면 예외를 던지고 즉시 중단시킨다 — 애초에 "조용한 메모리 손상"이 불가능한 구조다.
- ASan은 할당된 버퍼 앞뒤에 접근 불가 영역(redzone)을 둬서, 경계를 1바이트만 넘어도 그 즉시 프로세스를 중단시켜 오버플로우 지점을 정확히 잡아낸다.

### 판별·탐지 원리 정리
- 누수: "추세"로 판별한다. RSS/old gen이 시간에 비례해 계속 우상향하면(예: 시간당 200MB 증가) 누수 의심 — 정상은 GC 후 baseline으로 돌아오는 톱니 패턴이다.
- 오버플로우: "즉시성"으로 판별한다. 정적 분석은 경계 검사 없는 패턴(strcpy, memcpy 등)을 코드 단계에서 잡고, ASan/fuzzing은 실행 중 실제 침범이 일어나는 순간을 잡는다.

### 비유
- 누수: 다 쓴 렌탈 장비를 반납 목록에서 지우지 않아 창고가 서서히 차오르는 것.
- 오버플로우: 상자 크기를 무시하고 짐을 밀어 넣어 옆 상자(메타데이터)까지 찢어버리는 것 — 찢긴 관리대장 때문에 다음에 어디에 물건을 둘지도 엉망이 된다.

### 흔한 오해·주의점
- "GC가 있으면 누수가 없다"는 틀렸다 — GC는 도달 불가능만 회수하지, 도달 가능하지만 안 쓰는 객체는 절대 못 건드린다.
- "오버플로우는 그냥 크래시"라는 것도 틀렸다 — 메타데이터나 인접 객체(함수 포인터, vtable)를 덮으면 공격자가 실행 흐름을 바꾸는 RCE로 악용할 수 있다.

## 연결 개념
- 가비지 컬렉션 — 누수 탐지 시 retained heap·dominator tree 분석의 기반이 되는 자동 회수 메커니즘
- 버퍼 오버플로우(스택 오버플로우 포함) — 경계 초과 쓰기라는 더 큰 취약점 범주 중 힙에서 일어나는 사례
- 정적·동적 분석(ASan, Valgrind, heap dump) — 두 결함을 코드 단계와 실행 단계에서 각각 잡아내는 도구 체계

# 📝 【답안용】 시험 답안 템플릿

> 목적: 메모리 누수와 힙 오버플로우를 장애·보안 리스크로 구분하고 탐지, 예방, 복구 방안을 제시한다.

## 핵심 인사이트 (3줄 요약)

> 1. **본질**: 메모리 누수는 회수 대상 메모리의 참조 유지 또는 해제 누락이고, 힙 오버플로우는 할당 경계를 초과한 쓰기다.
> 2. **가치**: 두 결함은 OOM, 지연 증가, 데이터 손상, 원격 코드 실행으로 이어지므로 코드·런타임·운영 통제가 필요하다.
> 3. **판단 포인트**: 누수는 사용량 추세와 retained heap, 오버플로우는 경계 검사와 sanitizer 검출 결과로 판단한다.

## 출제 의도 및 답안 포인트

| 출제 의도 | 반드시 짚을 핵심 | 감점 회피 포인트 |
|:---|:---|:---|
| 메모리 결함 구분 확인 | leak vs overflow 원인·증상·영향 차이 | 두 용어를 OOM으로만 동일시 |
| 장애·보안 연결 역량 확인 | OOM, fragmentation, metadata corruption, RCE | 보안 영향 또는 복구 절차 누락 |
| 실무 예방 방안 확인 | RAII, ASan, heap dump, limit, restart policy | 도구 이름만 나열하고 지표 미제시 |

> 요약: 이 문제는 결함 유형별 원인과 탐지 지표를 구분해 예방·대응 체계를 쓰는 것이 핵심이다.

## Ⅰ. 개요 및 필요성

- 개요: 메모리 누수·힙 오버플로우는 동적 메모리 관리 결함이다.
- 배경: 누수는 해제되지 않거나 참조가 유지된 메모리 누적이고 힙 오버플로우는 할당 영역 경계 초과 쓰기다.
- 필요성: 서버 장애와 보안 침해를 막기 위해 정적 분석, ASan, 런타임 메모리 지표를 전 구간에 적용해야 한다.

---

## Ⅱ. 구조 및 구성요소

```text
Application Code -> Heap Allocator/GC -> Heap Object
  / Leak: reference retained -> heap growth -> OOM
  / Overflow: boundary write -> metadata corruption -> crash/RCE
  -> Monitor/Analyzer -> Fix/Guard
```

| 구성요소 | 역할 | 특이사항 |
|:---|:---|:---|
| Heap Allocator | 동적 메모리 할당·해제 | malloc, jemalloc, JVM heap |
| Reference Owner | 객체 수명 결정 | cache, listener, ThreadLocal |
| Boundary Check | 버퍼 길이 검증 | C/C++ 수동 검증 필요 |
| Analyzer | 결함 탐지 | ASan, Valgrind, heap dump |

> 요약: 누수는 소유권·참조 관리 문제이고, 오버플로우는 할당 경계 검증 문제다.

---

## Ⅲ. 동작원리 및 흐름도

```text
요청 처리 -> 객체/버퍼 할당 -> 사용 완료
  / 정상: 참조 제거 또는 free -> heap 회수
  / 누수: 참조 유지 -> live set 증가 -> OOM
  / 오버플로우: 경계 초과 쓰기 -> 손상 -> crash/RCE
```

| 단계 | 처리 내용 | 검증 기준 |
|:---:|:---|:---|
| 1 | 힙 객체 또는 버퍼 할당 | allocation rate, malloc count |
| 2 | 수명 종료 조건 도달 | owner scope, reference count |
| 3 | 해제·참조 제거 또는 경계 검사 | free call, bounds check |
| 4 | 오류 발생 시 분석 | heap dump, sanitizer report |

> 요약: 수명 종료 후 회수되지 않으면 누수, 할당 크기 밖 쓰기가 발생하면 힙 오버플로우다.

## Ⅳ. 특징

| 구분 | 메모리 누수 | 힙 오버플로우 | 정량·기술 포인트 |
|:---|:---|:---|:---|
| 원인 | 참조 유지, free 누락 | 버퍼 경계 초과 쓰기 | retained heap vs invalid write |
| 증상 | RSS·old gen 지속 증가 | crash, corruption, exploit | OOMKilled, SIGSEGV |
| 탐지 | heap dump, leak sanitizer | ASan, fuzzing, bounds checker | CI sanitizer 100% pass |
| 대응 | 수명 단축, cache TTL | safe API, length validation | `strncpy`, span, Rust borrow |

> 요약: 누수는 추세 분석, 오버플로우는 경계 위반 검출 중심으로 대응한다.

## Ⅴ. 심화 비교 및 적용 판단

| 구분 | 기존/대안 | 본 키워드 | 선택 기준 |
|:---|:---|:---|:---|
| GC 언어 | 자동 회수 | 참조 유지 누수 가능 | retained heap 기준 분석 |
| C/C++ | 수동 해제 | use-after-free·overflow 가능 | RAII, smart pointer, sanitizer |
| Rust | 소유권 검사 | unsafe 블록 관리 필요 | FFI·unsafe code review |

> 요약: 언어별 통제 지점은 GC 언어의 참조, C/C++의 경계·소유권, Rust의 unsafe 영역이다.

| 리스크 | 원인 | 대응 방안 | 확인 지표 |
|:---|:---|:---|:---|
| OOM 장애 | leak 누적, heap limit 초과 | heap dump, cache TTL, restart budget | RSS 증가율, OOM count |
| 보안 침해 | heap overflow로 metadata 손상 | ASLR, DEP, ASan, safe API | sanitizer finding 0건 |
| 진단 지연 | 재현 조건 불명확 | memory profiler, canary deploy | leak slope MB/hour |

> 요약: 운영 리스크는 OOM 빈도, sanitizer 검출, 시간당 힙 증가율로 통제한다.

| 점검 항목 | 목표 기준 | 측정 방법 |
|:---|:---|:---|
| 누수 | 24시간 soak test 후 RSS 증가 5% 이하 | load test, heap dump diff |
| 경계 위반 | ASan/UBSan finding 0건 | CI sanitizer job |
| 복구 | OOM 후 MTTR 10분 이하 | alert, runbook, restart policy |

> 요약: 품질 게이트는 장시간 부하, sanitizer, 복구 시간 지표로 구성한다.

## Ⅵ. 실무 적용 및 결론

**적용 방안 3개 (필수 — 단계별 또는 항목별):**
1. Java는 heap dump 2회와 dominator tree로 retained heap 상위 10개 객체를 식별하고 cache TTL·listener 해제를 적용함.
2. C/C++는 ASan, UBSan, fuzzing을 CI에 추가하고 unsafe copy API 사용을 code review block 기준으로 지정함.
3. 운영은 container memory limit, OOM alert, heap usage 80% 경보, canary soak test 24시간을 배포 기준으로 둠.

**결론 (2줄):**
- 기술사 판단: 누수는 수명·참조 관리, 오버플로우는 경계·소유권 검증으로 분리해 통제.
- 향후 방향: memory safe language, sanitizer, eBPF 기반 메모리 관측이 결합된 예방 중심 운영으로 이동함.
