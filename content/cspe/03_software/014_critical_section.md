# 📖 【암기용】 개념 완전 이해

> 목적: 이 개념을 처음 보는 사람도 완벽히 이해하게 만든다. 시험 답안 양식이 아니라, 이해를 위한 친절한 설명이다.

## 한눈에
- **개요**: **임계 구역(Critical Section)**은 동시성 제어(Concurrency Control)의 핵심 대상으로, 여러 프로세스·스레드가 동시에 접근하면 데이터가 깨지는 '공유 자원을 갱신하는 코드 구간'이다. 이 구간에 한 번에 하나의 실행 흐름만 들어가도록 강제하는 규칙이 **상호 배제(Mutual Exclusion)**다.
- **왜 필요한가**: 잔액 10,000원인 계좌에서 두 스레드가 동시에 "10,000원 출금"을 실행한다고 하자. 둘 다 잔액을 10,000원으로 읽고 각자 계산해 0원으로 덮어쓰면, 실제로는 한 번만 나가야 할 돈이 두 번 나간 것처럼 데이터가 깨진다(Race Condition, 경쟁 상태). 잔액을 확인하고 빼는 로직만큼은 한 번에 하나씩 순서를 세워야 한다.
- **핵심 직관**: 임계 구역 = 1인용 화장실(같이 들어가면 사고), 상호 배제 = 문을 안에서 '사용 중'으로 걸어 잠그는 행위(Lock).

## 핵심 용어 정리 (내부에 등장하는 것들)

| 용어 | 의미 | 비유 |
|:---|:---|:---|
| 동시성 제어 (Concurrency Control) | 여러 실행 흐름이 공유 자원에 안전하게 접근하도록 순서를 통제하는 상위 개념 | 교차로 신호등 시스템 전체 |
| 임계 구역 (Critical Section) | 공유 자원을 읽고 쓰는, 동시 접근 시 위험한 코드 구간 | 1인용 화장실 |
| 상호 배제 (Mutual Exclusion) | 한 번에 하나의 실행 흐름만 임계 구역에 두는 원칙 | 화장실 문 잠금 |
| 경쟁 상태 (Race Condition) | 실행 순서(타이밍)에 따라 최종 결과가 달라지는 결함 | 같은 서류를 두 사람이 동시에 고쳐 씀 |
| 진행 (Progress) | 구역이 비어 있고 진입 희망자가 있으면, 그중 하나는 반드시 유한 시간 안에 들어가야 함 | 빈 화장실 앞에서 서로 양보만 하다 아무도 못 들어가면 안 됨 |
| 한정된 대기 (Bounded Waiting) | 특정 프로세스가 무한정 밀리지 않도록 다른 프로세스의 진입 횟수에 상한을 둠 | 새치기로 한 사람만 영원히 못 들어가면 안 됨 |
| 원자성 (Atomicity) | 연산이 중간 상태 없이 한 번에 끝나는 성질 | 스위치 On/Off, 중간값이 없음 |
| TAS (Test-And-Set) | 읽기+쓰기를 하드웨어가 1클럭에 묶어 처리하는 원자 명령어 | 문 확인과 잠금을 동시에 하는 자동문 센서 |
| Peterson 알고리즘 | 소프트웨어만으로 2개 프로세스의 상호 배제를 구현한 고전 기법 | 서로 "네가 먼저" 깃발을 드는 양보 약속 |

## 깊이 이해

### 왜 임계 구역이 문제가 되나 (배경 — 명령어 레벨로 보기)
- 고급 언어의 `count++` 한 줄은 기계어로는 ① `LOAD R1, count`(메모리→레지스터) ② `ADD R1, 1` ③ `STORE count, R1`(레지스터→메모리), 3단계의 비원자적 명령으로 쪼개진다.
- 스레드 A가 ①②까지 끝내고 ③(저장)을 하기 전에 문맥 교환(Context Switch)이 일어나 스레드 B가 끼어들면, B는 A가 아직 저장하지 않은 옛날 값을 읽어간다. 결과적으로 두 스레드가 각각 1씩 더했는데 최종값은 1만 늘어나는 **갱신 손실(Lost Update)**이 발생한다.
- 수치로 보면: 두 스레드가 각각 `counter++`를 100만 번씩 수행하면 기대값은 200만이다. 락이 없으면 문맥 교환 타이밍에 따라 실제 결과는 150만~199만대처럼 들쭉날쭉하게 나온다. 이 손실분이 곧 임계 구역 미보호의 증거다.

### 임계 구역 문제 해결의 3대 필수 조건
1. **상호 배제**: Pi가 구역 안에 있으면 Pj는 절대 진입할 수 없다. 위반하면 위에서 본 갱신 손실이 그대로 발생한다.
2. **진행**: 구역이 비었고 진입 희망자가 있다면, 누가 들어갈지의 결정은 유한 시간 안에 끝나야 한다. 위반하면 서로 양보만 하다 아무도 못 들어가는 라이브락(Livelock)이 생긴다.
3. **한정된 대기**: 어떤 프로세스가 진입을 요청한 후, 다른 프로세스들이 먼저 진입할 수 있는 횟수에는 반드시 상한(예: 프로세스가 n개면 최대 n-1번)이 있어야 한다. 상한이 없으면 특정 프로세스가 영원히 밀리는 기아 상태(Starvation)가 된다.

### Peterson 알고리즘으로 3조건을 확인
- 핵심 코드: `flag[i]=true; turn=j; while (flag[j] && turn==j) { /* 대기 */ }`
- P0이 진입하려면 `flag[0]=true, turn=1`을 세팅한 뒤, `flag[1]`이 false이거나 `turn`이 이미 0으로 바뀌어 있어야 while을 빠져나간다. 두 프로세스가 동시에 진입을 시도해도 `turn`은 마지막에 쓴 값 하나만 남으므로 반드시 한쪽만 통과한다 — 상호 배제 성립.
- 상대가 임계 구역에 관심이 없으면(`flag[j]=false`) 즉시 통과하므로 진행 조건도 성립하고, 서로 많아야 한 번씩만 양보하므로 대기 횟수도 1회로 한정된다.

### 왜 소프트웨어 해결책이 현대 CPU에서 무너지나
- Peterson은 `flag[i]=true`를 쓴 뒤 `turn=j`를 쓰는 순서에 의존한다. 그런데 컴파일러 최적화나 CPU의 비순차 실행(Out-of-Order Execution)이 이 두 대입문의 실제 실행 순서를 뒤바꿀 수 있다.
- 순서가 뒤바뀌면 두 프로세스가 동시에 `turn`을 자기 자신의 값으로 읽어버려 상호 배제가 깨지고, 둘 다 임계 구역에 진입한다. 메모리 배리어(Memory Barrier) 없이는 소프트웨어만으로 이 문제를 막을 수 없다.

### 하드웨어 원자 명령어(TAS)로 1클럭에 해결
```
boolean TestAndSet(boolean *lock) {
    boolean old = *lock;  // 이전 상태 읽기
    *lock = true;         // 잠금
    return old;           // 이 3줄이 CPU 안에서 분리 불가능한 1개 명령으로 실행됨
}
```
- 위 3줄을 CPU가 "메모리 읽기+쓰기"를 하나의 버스 트랜잭션으로 묶어 실행하므로, 다른 스레드가 끼어들 문맥 교환 지점 자체가 물리적으로 없다. 소프트웨어처럼 순서가 뒤바뀔 여지가 사라진다.
- `while (TestAndSet(&lock));`처럼 락을 얻을 때까지 반복 검사하는 방식이 스핀락(Spinlock)이며, Mutex·Semaphore·Java Monitor는 이 위에 "실패하면 잠들고, 락이 풀리면 깨워주는" 대기 큐를 얹어 CPU 낭비 없이 쓰기 쉽게 포장한 것이다.

### 비유와 흔한 오해
- 비유: 은행 창구 셔터에 가깝다. 손님(스레드) 한 명이 셔터를 내리고(Lock) 업무(임계 구역)를 처리하는 동안 다음 손님은 줄을 서고, 업무가 끝나면 셔터를 올려(Unlock) 다음 사람을 들여보낸다.
- 오해: 임계 구역은 함수 전체가 아니다. `withdraw()` 함수 전체에 락을 걸면 DB 조회·로그 기록 같은 무관한 코드까지 다른 스레드를 막아 성능이 급락한다. 실제로 보호해야 할 곳은 `balance = balance - amount`처럼 공유 데이터를 갱신하는 딱 그 줄뿐이다 — 임계 구역은 좁을수록(최소화) 시스템이 빨라진다.

## 연결 개념
- 데드락 (Deadlock) — 상호 배제가 여러 자원에 걸릴 때, 두 프로세스가 서로 상대의 자원을 기다리며 영원히 멈추는 치명적 그림자
- Mutex, Semaphore, Java Monitor — TAS 위에 대기 큐를 얹어 개발자가 쓰기 쉽게 포장한 OS·언어 수준 동기화 도구
- 014_critical_section_mutual_exclusion(같은 폴더) — 이 파일이 3대 조건과 SW→HW 진화 원리를 다룬다면, 그 파일은 Entry/Exit Section 구조와 데드락·기아·락 범위 같은 구현 리스크를 다룬다

> 핵심: 이 시험은 정보를 많이 나열하는 시험이 아니라, 문제 신호어에서 출제자 의도를 읽고 핵심 논점을 선별해 쓰는 시험이다.

## 핵심 인사이트 (3줄 요약)

> 1. **본질**: 다중 스레드 환경에서 동시 접근 시 무결성이 훼손(Race Condition)되는 공유 데이터 갱신 코드 블록(임계 구역)과, 이를 보호하는 통제 원칙(상호 배제)이다.
> 2. **가치**: 상호 배제, 진행, 한정된 대기라는 3대 조건을 엄수하여 데이터 정합성을 지키면서도 병행성(Concurrency)을 잃지 않게 설계한다.
> 3. **판단 포인트**: 순수 소프트웨어 해결책(Peterson)의 한계와 비순차 실행(Out-of-order) 구조를 짚고, 이를 원자적(Atomic) 하드웨어 명령어(TAS/CAS)로 극복한 흐름을 증명해야 한다.

## 출제 의도 및 답안 포인트

| 출제 의도 | 반드시 짚을 핵심 | 감점 회피 포인트 |
|:---|:---|:---|
| 임계 구역 문제 해결을 위한 필수 조건 이해 | 3대 조건: 상호 배제, 진행, 한정된 대기 | 3조건 중 하나라도 누락하거나 의미를 혼동하는 실수 |
| SW 기반 락의 한계와 HW 지원 필요성 규명 | 원자성(Atomicity) 파괴 문제와 TAS 명령어의 역할 | 피터슨 알고리즘이 현대 멀티코어에서도 완벽하다고 적는 오류 |

> 요약: 이론가들이 머리로 짠 도덕적 룰(소프트웨어)이 멀티코어의 속도전(명령어 재배치) 앞에서 무너졌고, 결국 물리적 하드웨어 락(TAS)이 등판한 역사적 한계점을 꼬집는다.

## Ⅰ. 개요 및 필요성

- 정의: 임계 구역(Critical Section)은 둘 이상의 프로세스가 공유 자원에 접근할 때 경쟁 상태(Race Condition)를 유발하는 코드 영역이며, 상호 배제(Mutual Exclusion)는 한 번에 한 프로세스만 진입하도록 보장하는 보호 원칙
- 배경: 어셈블리어 레벨에서 데이터 갱신은 `Load -> Add -> Store`의 3단계 비원자적(Non-Atomic) 명령어로 나뉘어 있어 문맥 교환 시 데이터 유실 버그 상존
- 필요성: 시스템의 데이터 무결성(Integrity)을 사수하면서도, 지나친 잠금(Lock)으로 인한 데드락과 성능 병목을 피하기 위한 최소 단위의 격리 메커니즘 필수

## Ⅱ. 임계 구역 문제 해결의 3대 필수 조건

완벽한 동기화 메커니즘으로 인정받으려면 다음 3가지 수학적 조건을 모두 만족해야 한다.

| 필수 조건 (Requirements) | 판단 기준 (동작 룰) | 위반 시 발생하는 치명적 버그 |
|:---|:---|:---|
| 1. 상호 배제 (Mutual Exclusion) | 임계 구역 안에 프로세스 Pi가 있다면, 다른 어떤 프로세스 Pj도 절대 진입할 수 없음 | **경쟁 상태 (Race Condition)**: 계좌 잔고가 증발하거나 데이터 덮어쓰기 오염 발생 |
| 2. 진행 (Progress) | 임계 구역이 텅 비어있고 진입을 원하는 스레드들이 있다면, 반드시 그중 하나는 즉시 진입을 허가받아야 함 | **교착 상태 (Deadlock)** / **라이브락 (Livelock)**: 서로 양보만 하다가 아무도 못 들어감 |
| 3. 한정된 대기 (Bounded Waiting) | 진입을 요청한 스레드는 무한정 기다리지 않고, 유한한 횟수(시간) 안에 반드시 진입 기회를 보장받아야 함 | **기아 상태 (Starvation)**: 특정 프로세스만 우선순위에 밀려 100만 년 동안 큐에 갇힘 |

> 요약: 하나만 들어갈 것(배제), 비었으면 빨리 넣을 것(진행), 언젠가는 내 차례가 올 것(대기). 이 3조건은 OS 동기화 기법의 바이블이다.

## Ⅲ. 상호 배제 구현 아키텍처: 소프트웨어 vs 하드웨어 도식

```text
[ 소프트웨어 (피터슨 알고리즘)의 한계 ]
flag[me] = true;
turn = you;
while (flag[you] && turn == you) { /* 대기 */ }
// 🚨 컴파일러/CPU가 속도 최적화를 위해 위 두 줄의 순서를 뒤바꾸면(Out-of-order) 
// 두 스레드가 동시에 임계 구역에 진입하는 대참사 발생

[ 하드웨어 지원 (Test-And-Set 명령어)의 해결 ]
// CPU가 메모리 읽기+쓰기를 '단일 버스 트랜잭션'으로 묶어버림
boolean TestAndSet(boolean *lock) {
   boolean old = *lock;  // 이전 상태 백업
   *lock = true;         // 문 잠금
   return old;           // 🚨 이 모든 게 1클럭 사이클에 '절대 방해받지 않고' 끝남
}
```

| 접근 방식 | 대표 기법 및 원리 | 실무적 한계 및 평가 |
|:---|:---|:---|
| 소프트웨어 로직 기반 | Dekker, Peterson (플래그 변수 교차 체크) | 최신 CPU의 명령어 재배치(Reordering) 구조에서는 데이터 장벽(Memory Barrier) 없이는 완벽 붕괴됨 (실무 사장) |
| 하드웨어 지원 명령어 | TAS (Test-And-Set), CAS (Compare-And-Swap) | 원자성(Atomicity)이 물리적으로 보장됨. 스핀락(Spinlock) 구현의 핵심 코어 기반 |
| 운영체제/언어 지원 | Mutex, Semaphore, Java Monitor | 하드웨어 TAS를 포장하여 개발자가 쓰기 쉽게 큐(Queue) 대기 구조(Sleep)로 만들어준 최종 종착지 |

> 요약: 종이에 쓴 약속(소프트웨어)은 속도에 미친 현대 CPU가 무시하므로, 메모리 버스 자체를 잠가버리는 하드웨어의 무식한 원자성(TAS)이 필수 기반이다.

## Ⅳ. 극복해야 할 리스크 및 임계 구역 최적화 방안

임계 구역을 무분별하게 크게(Coarse-grained) 잡으면 시스템은 싱글 코어 시절의 속도로 전락한다.

| 리스크 요인 | 발생 시나리오 | 아키텍처 대응 방안 (최소화 튜닝) |
|:---|:---|:---|
| 병행성(Concurrency) 폭락 | `pop()`으로 큐에서 꺼낸 뒤, DB에 저장(100ms)하는 전체 함수를 임계 구역으로 설정해 나머지 스레드 99개 정지 | **임계 구역 최소화 (Fine-grained Lock)**: 큐 조작(`pop`) 로직 단 1줄에만 락을 걸고, 남의 눈치를 볼 필요 없는 `DB I/O`는 락 밖(Remainder Section)으로 빼내어 병렬 실행 |
| 빈번한 락 경합 병목 | 1만 개의 스레드가 하나의 전역 변수(방문자 수 카운터)에 접근하느라 CAS 락 루프에서 엄청난 CPU 사이클 허비 | **스레드 로컬 (Thread-Local) 통계화**: 스레드별로 임시 변수 배열을 각자 쪼개어(분할) 사용한 뒤, 일정 주기에 한 번만 전역 변수 락을 걸고 머지(Merge)하여 경합 99% 축소 |

> 요약: 가장 좋은 임계 구역은 아예 존재하지 않게 데이터를 복제해 쓰는 것이고, 어쩔 수 없다면 수술용 메스처럼 공유 자원을 건드리는 단 1줄만 정확히 도려내 잠가야 한다.

## Ⅴ. 실무 적용 방안 및 결론

**적용 방안 3개:**
1. [RDBMS 낙관적 락(Optimistic Lock)] 티켓 예매 시스템 등 충돌이 드문 환경에서 상호 배제(비관적 락)를 걸고 기다리는 대신, 임계 구역 없이 일단 갱신 시도 후 `Version/Timestamp` 칼럼을 비교해 충돌 시 롤백하는 논블로킹(CAS 기반) 처리 패턴 적용
2. [캐시 라인(Cache Line) 거짓 공유 방지] C++로 주식 호가 매칭 엔진 작성 시, 서로 다른 임계 구역을 가진 변수 A와 B가 CPU 캐시 1개 라인(64Byte)에 같이 묶여 무의미한 락 경합 패널티(False Sharing)를 겪지 않도록 패딩(Padding)을 삽입하여 메모리 주소 격리
3. [불변 객체(Immutability) 아키텍처 도입] Scala나 Java 14+ Record를 활용한 다중 스레드 도메인 설계 시, 상태 변경 메서드(Setter)를 없애고 값을 복사한 새 객체를 반환하도록 강제하여 `synchronized` 임계 구역 자체를 시스템에서 박멸

**결론:**
- 기술사 판단: 임계 구역은 멀티스레딩의 필요악이다. 이를 소프트웨어적 양보(Peterson)로 풀려던 시도는 하드웨어 명령어(TAS/CAS)의 등장으로 해결되었고, 현대 엔지니어링은 락을 잘 거는 것을 넘어 어떻게 하면 락 프리(Lock-Free)로 아키텍처를 진화시킬지에 사활을 걸고 있다.
- 향후 방향: 최근 인텔 TSX(Transactional Synchronization Extensions) 같은 하드웨어 트랜잭셔널 메모리(HTM) 기술은 락을 걸지 않고 일단 병렬로 임계 구역을 실행한 뒤, 덮어쓰기 충돌이 났을 때만 하드웨어가 롤백을 쳐버리는 혁신으로 임계 구역의 패러다임을 통째로 뒤바꾸고 있다.
