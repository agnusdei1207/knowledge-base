# 📖 【암기용】 개념 완전 이해

## 한눈에
- **임계 구역 (Critical Section)**: 여러 스레드가 동시에 접근하면 안 되는 **공유 자원 접근 코드 영역**.
- **상호 배제 (Mutual Exclusion)**: 한 번에 한 놈만 임계 구역에 들어가게 보장하는 원칙.
- **Race Condition (경쟁 상태)**: 상호 배제가 깨져서, 실행 순서에 따라 결과가 매번 달라지는 **동기화 오류**.
- **해결 3조건 (상진한)**:
    1. **상**호 배제 (Mutual Exclusion): 한 명만 진입.
    2. **진**행 (Progress): 비어 있으면 들어갈 놈이 들어가야 함.
    3. **한**정 대기 (Bounded Waiting): 무한정 기다리게 하면 안 됨.

## 깊이 이해
- **왜 발생하는가? (Atomicity의 부재)**: `count++`라는 코드는 겉보기엔 한 줄이지만, CPU 레지스터 수준에서는 [1. 읽기, 2. 증가, 3. 쓰기]의 3단계로 나뉨. 1단계와 3단계 사이에 다른 스레드가 개입하면 데이터가 꼬임.
- **소프트웨어적 해법**:
    - **Dekker 알고리즘**: flag와 turn 변수를 사용한 최초의 해법. 복잡함.
    - **Peterson 알고리즘**: Dekker보다 단순화된 해법. 여전히 2개 프로세스로 제한.
- **하드웨어적 해법**:
    - **Interrupt Disable**: 인터럽트를 아예 꺼버림. (단일 코어에서만 유효, 위험함)
    - **TSL (Test-and-Set)**: "읽고 쓰기"를 하나의 원자적 명령으로 수행. 현대 동기화의 토대.
- **고수준 해법**: 세마포어, 뮤텍스, 모니터 (012 연계).

## 연결 개념
- **Semaphore/Mutex (012)**: 임계 구역 문제를 해결하는 도구.
- **Spinlock (013)**: 임계 구역 대기 방식의 일종.
- **Deadlock (009)**: 상호 배제를 지키려다 발생하는 부작용.

# 📝 【답안용】 시험 답안 템플릿

## 핵심 인사이트 (3줄 요약)
> 1. **본질**: 다중 프로그래밍 환경에서 공유 자원의 **무결성(Integrity)**과 데이터의 **일관성(Consistency)**을 보장하기 위한 접근 제어의 핵심 원리임.
> 2. **기술적 핵심**: 원자적(Atomic) 연산 보장을 위해 하드웨어적 지원(TSL, CAS)과 소프트웨어적 알고리즘(Peterson 등)을 결합하여 **상호 배제, 진행, 한정 대기**를 달성함.
> 3. **판단**: 임계 구역의 길이에 따라 락의 입도(Granularity)를 조정하여 동기화 성능과 병렬 처리량 사이의 최적점을 찾아야 함.

## Ⅰ. 동시성 제어의 근간, 임계 구역(Critical Section)의 개요
- **정의**: 멀티 스레드 프로그램에서 공유 자원(변수, 파일, DB 등)에 접근하여 실행 결과가 접근 순서에 따라 달라질 수 있는 코드 영역.
- **상호 배제(Mutual Exclusion)**: 한 프로세스가 임계 구역에서 수행 중이면 다른 프로세스는 해당 구역에 들어갈 수 없게 차단하는 기법.

## Ⅱ. 임계 구역 문제 해결을 위한 3대 필요조건 (상·진·한)

| 조건 | 상세 설명 | 미충족 시 발생하는 문제 |
|:---:|:---|:---|
| **상호 배제** (Mutual Exclusion) | 임계 구역 내에는 단 하나의 프로세스만 존재해야 함 | Race Condition (데이터 오염) |
| **진행** (Progress) | 임계 구역 외부에 있는 프로세스가 다른 프로세스의 진입을 방해해서는 안 됨 | Deadlock (착한 바보 현상) |
| **한정 대기** (Bounded Waiting) | 어떤 프로세스도 임계 구역 진입을 무한정 기다려서는 안 됨 | Starvation (기아 현상) |

## Ⅲ. 임계 구역 해결 알고리즘 및 메커니즘

### 1. 소프트웨어적 해결 (Peterson's Algorithm)
- **특징**: `flag`와 `turn` 변수를 혼합하여 상진한 3조건을 모두 충족.
- **Pseudo Code**:
```c
flag[i] = true; turn = j;
while (flag[j] && turn == j); // 상대방 차례고 상대가 원하면 대기
// Critical Section
flag[i] = false;
```

### 2. 하드웨어적 해결 (Test-and-Set)
- **특징**: "메모리 읽기 + 값 쓰기"를 중간에 끊을 수 없는 **원자적(Atomic)** 연산으로 처리.
- **한계**: Busy-waiting(Spinlock) 발생 가능.

## Ⅳ. Race Condition과 동기화 오버헤드

- **Race Condition 발생 시나리오**:
    1. Thread A가 공유 변수 `count=10`을 로드.
    2. Context Switch 발생.
    3. Thread B가 `count=10`을 로드 후 1 증가시켜 `11`로 저장.
    4. Thread A가 복귀하여 (이미 읽어둔 10에서) 1 증가시켜 `11`로 덮어씀. (결과적으로 1회 손실)
- **해결 방안**: 락 입도(Lock Granularity) 최소화, Lock-free 자료구조 사용.

## Ⅴ. 기술적 심화: 락 입도(Lock Granularity)와 성능

| 구분 | 굵은 입도 (Coarse-grained) | 가는 입도 (Fine-grained) |
|:---:|:---|:---|
| **방식** | 전체 자료구조에 하나의 락 | 자료구조의 각 노드/섹션마다 락 |
| **장점** | 구현 단순, 오버헤드 적음 | 높은 병렬성, 경합 감소 |
| **단점** | 병목 현상 발생 심함 | 구현 복잡, 데드락 위험 증가 |
| **비유** | 화장실 전체에 문 하나 | 각 칸마다 문 하나 |

## Ⅵ. 기술사 관점의 결론 및 제언
- 임계 구역 문제는 단순한 '잠금'을 넘어 시스템의 **확장성(Scalability)**과 직결됨.
- **실무 제언**: 락 경합(Lock Contention)을 줄이기 위해 공유 상태를 최소화하는 **함수형 프로그래밍** 기법이나, 쓰기보다 읽기가 압도적으로 많은 경우 **Read-Write Lock**을 도입하여 성능 최적화를 꾀해야 함.
