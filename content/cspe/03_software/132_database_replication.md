## Ⅰ. 개요
- **정의**: DB의 데이터를 다수 노드에 실시간 복제하여 가용성과 읽기 성능을 높이는 기법
- **배경/필요성**: 단일 DB 장애 시 서비스 중단을 방지하고 읽기 부하를 분산할 필요가 있음
- **비유**: 원본 문서를 여러 부서에 사본으로 배포해 동시 열람을 가능하게 하는 것과 유사함

| 출제 의도 | 반드시 짚을 핵심 | 감점 회피 포인트 |
|:---|:---|:---|
| 고가용성 아키텍처 설계 | 동기/비동기 복제 차이와 일관성 트레이드오프 | 샤딩(131 참조)과 레플리케이션 목적 구분 필요 |

> 요약: 데이터 복제를 통해 가용성·읽기 확장성을 확보하는 기법임

## Ⅱ. 구성요소
```text
Client(Write) --> Primary --+--> Replica-1 (Read)
                            +--> Replica-2 (Read)
                            +--> Replica-3 (Read)
```

| 구성요소 | 설명 | 비유 |
|:---|:---|:---|
| Primary | 쓰기를 처리하고 변경 로그를 생성하는 원본 노드 | 원본 대장 |
| Replica | Primary 변경분을 수신하여 읽기를 담당하는 복제 노드 | 사본 열람실 |
| Replication Log | Primary에서 Replica로 전파되는 변경 이벤트 스트림 | 변경 알림 문서 |
| Failover Manager | Primary 장애 감지 시 Replica를 승격시키는 관리자 | 비상 대리인 지정 담당 |

> 요약: Primary-Replica 구조에서 변경 로그 기반으로 데이터를 복제함

## Ⅲ. 절차
```text
Primary 쓰기 --> 로그 생성 --> Replica 전파 --> Replica 적용
```
- 1단계: Primary가 트랜잭션 커밋 시 변경 로그(binlog 등) 생성
- 2단계: 동기/비동기 방식으로 Replica에 로그 전파
- 3단계: Replica가 로그를 수신하여 로컬 데이터에 적용
- 4단계: 읽기 요청을 Replica로 라우팅하여 부하 분산 수행

> 요약: 로그 생성-전파-적용-라우팅의 4단계로 복제가 동작함

## Ⅳ. 문제점
- 복제 지연: 비동기 복제 시 Primary-Replica 간 데이터 불일치 발생 — 읽기 정합성 저하됨
- 쓰기 병목: 모든 쓰기가 단일 Primary에 집중 — 쓰기 확장성 한계 존재함
- Failover 데이터 손실: 비동기 모드에서 승격 시 미전파 트랜잭션 유실 가능함

> 요약: 복제 지연, 쓰기 병목, 장애 전환 시 데이터 손실이 핵심 과제임

## Ⅴ. 개선방안
1. 단기: 복제 지연 → 반동기(Semi-Sync) 복제로 최소 1개 Replica 확인 후 커밋
2. 중기: 쓰기 병목 → Multi-Primary 구성 또는 샤딩(131 참조) 병행
3. 장기: Failover 손실 → Raft/Paxos 기반 합의 복제로 무손실 전환 보장

> 요약: 반동기 복제, Multi-Primary, 합의 프로토콜로 단계적 개선함

## Ⅵ. 전망
- 발전 방향: 합의 기반 복제가 기본이 되어 동기/비동기 구분이 약화되는 추세임
- 기술사적 판단: 가용성과 일관성 트레이드오프 설계는 분산 시스템 핵심 역량임
- 기술사 제언: RPO/RTO 요구사항에 따라 복제 모드를 선정할 것을 제언함
