## Ⅰ. 개요
- **정의**: 분산 시스템에서 여러 서비스 간 데이터 일관성을 보장하는 트랜잭션 패턴
- **배경/필요성**: 마이크로서비스 환경에서 단일 DB 트랜잭션이 불가능하므로 서비스 간 일관성 조정 메커니즘이 필요함
- **비유**: 2PC는 지휘자가 모든 연주자에게 동시에 신호를 보내는 오케스트라, Saga는 릴레이 주자가 바톤을 넘기는 이어달리기

| 출제 의도 | 반드시 짚을 핵심 | 감점 회피 포인트 |
|:---|:---|:---|
| 두 패턴의 일관성 수준과 적용 조건 비교 | 2PC는 강한 일관성, Saga는 최종 일관성 | Saga는 격리성을 보장하지 않음을 명시할 것 |

> 요약: 분산 트랜잭션의 일관성 보장을 위한 두 가지 대표 패턴임

## Ⅱ. 구성요소
```text
[2PC]                         [Saga]
Coordinator                   Orchestrator / Choreography
  |                             |
  +--Prepare-->Participant    Step1 --> Step2 --> Step3
  +--Commit/Rollback            |        |        |
                             Comp1 <-- Comp2 <-- Comp3
```

| 구성요소 | 설명 | 비유 |
|:---|:---|:---|
| Coordinator(2PC) | 모든 참여자에게 Prepare/Commit 명령을 전달하는 중앙 조정자 | 오케스트라 지휘자 |
| Compensating Tx(Saga) | 실패 시 이전 단계 결과를 논리적으로 취소하는 보상 트랜잭션 | 실수한 퍼즐 조각 되돌리기 |
| Participant | 각 서비스의 로컬 트랜잭션 실행 단위 | 릴레이 주자 |

> 요약: 2PC는 중앙 조정자 기반, Saga는 보상 트랜잭션 기반으로 일관성을 확보함

## Ⅲ. 절차
```text
2PC: Prepare --> Vote --> Commit/Abort
Saga: T1 --> T2 --> T3 (실패 시 C3 --> C2 --> C1)
```
- 1단계: 트랜잭션 시작 — 2PC는 Coordinator가 Prepare 전송, Saga는 첫 로컬 Tx 실행
- 2단계: 투표/진행 — 2PC는 참여자 Vote 수집, Saga는 다음 서비스로 이벤트 전파
- 3단계: 확정/보상 — 2PC는 전원 동의 시 Commit, Saga는 실패 시 역순 보상 Tx 실행
- 4단계: 완료 — 2PC는 잠금 해제, Saga는 최종 상태 기록 및 이벤트 발행

> 요약: 2PC는 동기 투표-확정, Saga는 비동기 진행-보상 방식으로 처리함

## Ⅳ. 문제점
- 2PC 가용성 저하: Coordinator 단일 장애점으로 전체 트랜잭션이 블로킹됨
- Saga 격리성 부재: 중간 상태가 외부에 노출되어 dirty read 가능함
- Saga 보상 복잡도: 보상 트랜잭션 설계 오류 시 데이터 불일치가 영구화됨

> 요약: 2PC는 가용성, Saga는 격리성과 보상 설계의 복잡도가 핵심 문제임

## Ⅴ. 개선방안
1. 단기: 2PC Coordinator 이중화 및 타임아웃 설정으로 블로킹 완화
2. 중기: Semantic Lock·Commutative Update 등 Saga 격리성 대응 패턴 적용
3. 장기: 이벤트 소싱 기반 보상 로직 자동 생성 프레임워크 도입

> 요약: 이중화, 격리 패턴, 자동화 순으로 각 문제를 해소함

## Ⅵ. 전망
- 발전 방향: 서비스 메시와 결합한 분산 트랜잭션 자동 조정 기술 확산 전망
- 기술사적 판단: 강한 일관성이 요구되면 2PC, 고가용성이 우선이면 Saga 선택이 합리적임
- 기술사 제언: 비즈니스 요건별 일관성 수준을 정의한 후 패턴을 선택할 필요
