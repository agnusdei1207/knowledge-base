# 📖 【암기용】 개념 완전 이해

> 목적: Saga와 2PC를 처음 봐도 완벽히 이해하게 만든다. 시험 답안 양식이 아니라, 이해를 위한 친절한 설명이다.

## 한눈에
- **개요**: MSA에서 여러 서비스에 걸친 작업의 원자성을 다루는 두 가지 **분산 트랜잭션(Distributed Transaction)** 기법 — 2PC는 강한 일관성(ACID)을, Saga는 최종 일관성(Eventual Consistency)을 택한다
- **왜 필요한가**: MSA는 서비스별로 DB를 따로 소유(Database per Service)하므로 주문·결제·재고를 하나의 로컬 트랜잭션(BEGIN~COMMIT)으로 묶을 수 없다. 여러 DB에 걸친 작업을 "전부 성공 또는 전부 실패"로 만드는 방법이 필요하다
- **핵심 직관**: 2PC는 모든 부서가 동시에 결재 도장을 찍어야 문서가 확정되는 절차, Saga는 일단 단계별로 진행하다 실패하면 이미 한 일을 취소 거래로 되돌리는 절차다

## 핵심 용어 정리 (내부에 등장하는 것들)

| 용어 | 의미 | 비유 |
|:---|:---|:---|
| ACID | 원자성·일관성·고립성·지속성 — 단일 DB 트랜잭션이 보장하는 성질, 2PC가 여러 DB로 확장하려는 대상 | 계약서 안의 모든 조항이 한 번에 발효되거나 전부 무효가 되는 것 |
| 분산 트랜잭션 | 둘 이상의 독립된 DB·서비스에 걸친 작업을 하나의 논리적 단위로 묶는 것 | 여러 은행 지점에 걸친 송금을 하나의 거래로 처리하는 것 |
| 2PC(Two-Phase Commit) | Coordinator가 Prepare·Commit 두 단계로 모든 참가자의 동의를 받아야 확정하는 프로토콜 | 모든 부서가 동시에 결재해야 문서가 완료되는 절차 |
| Coordinator | 2PC에서 prepare 요청과 commit·rollback 지시를 내리는 중앙 조정자 | 결재를 총괄하는 총무부 |
| Participant | 2PC에서 prepare 응답 후 실제 커밋·롤백을 수행하는 각 DB | 결재란에 도장 찍는 각 부서 |
| Prepare Phase | 모든 참가자가 "커밋 준비 완료"를 보고하고 락을 건 채 대기하는 1단계 | 모든 부서가 서명 직전까지 검토를 마치고 대기하는 단계 |
| Commit Phase | 전원이 준비 완료를 보고하면 Coordinator가 실제 확정을 지시하는 2단계 | 총무부가 "이제 도장 찍으세요"라고 일괄 지시하는 단계 |
| Saga Pattern | 각 서비스가 로컬 트랜잭션을 순차 실행하고 실패 시 보상 트랜잭션으로 되돌리는 패턴 | 배송·결제·포장을 진행하다 문제가 생기면 환불·회수·취소를 실행하는 것 |
| Local Transaction | Saga의 각 단계 — 단일 서비스 내부에서만 완결되는 일반 ACID 트랜잭션 | 한 부서 안에서만 끝나는 결재 |
| Compensating Transaction(보상 트랜잭션) | 이전 단계를 업무적으로 되돌리는 반대 동작(완전한 롤백이 아닐 수 있음) | 이미 부친 편지를 취소할 수 없어 "정정 편지"를 다시 보내는 것 |
| Orchestration / Choreography | Saga 진행 방식 — 중앙 지휘자가 순서 지시 vs 각 서비스가 이벤트를 듣고 알아서 다음 단계 실행 | 지휘자가 있는 오케스트라 vs 각자 눈치껏 맞추는 재즈 잼 세션 |
| Outbox Pattern | DB 갱신과 이벤트 발행을 원자적으로 묶기 위한 보조 테이블 기법 | 계약서 작성과 동시에 발송 대장에 기록해 "쓰고 안 보내는" 실수를 막는 것 |
| Idempotency(멱등성) | 같은 요청을 여러 번 보내도 결과가 한 번 보낸 것과 같은 성질 | 같은 버튼을 여러 번 눌러도 주문이 한 번만 들어가는 것 |

## 깊이 이해

### 2PC 동작을 숫자로 — 왜 "블로킹" 문제가 생기나
- 3개 참가자(재고 DB, 결제 DB, 배송 DB)가 있다고 하자. Coordinator가 Prepare 요청을 보내면 각 참가자는 변경 사항을 임시 반영하고 락을 건 채 "준비 완료" 응답을 보낸다 — 이 왕복에 각 50ms가 걸린다면 1단계에 약 50ms.
- 전원이 "준비 완료"를 보고하면 Coordinator가 Commit을 지시하고 참가자들이 확정하며 락을 푼다 — 다시 약 50ms. 총 2번의 네트워크 왕복(2 RTT)이 필요하고, 그 사이 참가자들은 계속 락을 쥔 채 대기한다.
- 문제는 Prepare가 끝나고 Commit 지시 직전에 **Coordinator가 죽으면** 참가자들은 "커밋해야 할지 롤백해야 할지" 알 수 없어 락을 풀지 못한 채 무한 대기(블로킹)에 빠질 수 있다는 점이다. 이것이 2PC의 근본적 약점이며, 락 지속 시간이 길어질수록(원거리 네트워크, 참가자 수 증가) 이 위험 구간도 함께 늘어난다.

### Saga 동작을 숫자로 — 실패 시 보상의 순서
- 주문 흐름: ① 재고 예약(로컬 트랜잭션, 20ms 완료) → ② 결제 승인(로컬 트랜잭션 시도, 200ms 후 "잔액 부족"으로 실패) → ③ 결제 실패 이벤트 발행.
- 실패가 감지되면 Saga는 **역순으로 보상**을 실행한다: 결제는 애초에 성공하지 않았으니 보상 불필요, 그 앞 단계인 재고 예약에 대해 "재고 예약 해제"라는 보상 트랜잭션을 실행하고, 주문 상태를 `PENDING`에서 `CANCELLED`로 전환한다.
- 이 전체 과정(주문 생성 → 재고 예약 → 결제 실패 → 재고 해제 → 상태 CANCELLED)이 완료되기까지 예를 들어 300ms가 걸린다면, 그 사이 다른 사용자가 주문 목록을 조회하면 잠깐 `PENDING` 상태를 볼 수 있다 — 이것이 Saga가 최종 일관성(eventual consistency, 208 참고)인 이유다. 2PC처럼 명시적 락으로 다른 트랜잭션을 막지 않기 때문에, 확정되기 전까지의 중간 상태가 외부에 노출될 수 있다.

### 보상 트랜잭션이 "완전한 롤백"이 아닌 이유 — 판별 원리
- DB 트랜잭션의 ROLLBACK은 커밋 전 상태로 물리적으로 되돌리지만, Saga의 보상은 이미 커밋되어 외부에 노출된 결과를 업무적으로 "취소"하는 별도의 순방향 작업이다. 예를 들어 이메일 발송은 취소할 수 없으므로 "정정 안내 메일"을 보상으로 보낸다.
- 그래서 보상 트랜잭션을 설계할 때는 "이 작업이 업무적으로 완전히 원복 가능한가"를 반드시 검증해야 한다 — 배송 완료 후 취소는 반품 프로세스이지, 배송 자체를 없던 일로 만드는 게 아니다.

### Orchestration vs Choreography — 언제 무엇을 쓰나
- **Orchestration**: 중앙 오케스트레이터가 상태 머신으로 "다음에 무엇을 할지"를 직접 지시한다. 흐름 추적이 쉽고 단계가 많거나 복잡할 때 유리하지만, 오케스트레이터가 단일 장애점이자 결합점이 될 수 있다.
- **Choreography**: 각 서비스가 이벤트를 구독하고 스스로 다음 행동을 결정한다(재고 서비스가 "결제 실패" 이벤트를 듣고 알아서 재고를 해제). 서비스 간 결합은 느슨하지만, 단계가 많아지면 "지금 전체 흐름이 어디까지 왔는지" 추적하기 어려워진다.

### 비유와 흔한 오해
- 비유: 2PC는 모든 부서가 동시에 결재 도장을 찍어야 문서가 확정되는 절차이고, Saga는 여행 예약처럼 항공권·호텔·렌터카를 순서대로 예약하다 하나가 실패하면 이미 예약한 것들을 순서대로 취소하는 절차다.
- 오해: Saga는 단순 "try-catch로 롤백하는 것"이 아니다. 이미 커밋되어 다른 서비스·사용자에게 노출된 결과를 보상 트랜잭션이라는 별도의 순방향 비즈니스 로직으로 되돌리는 것이라, 보상 자체가 실패할 수 있고(예: 환불 API 장애) 이 실패까지 재시도·DLQ로 다뤄야 한다.

## 연결 개념
- Outbox Pattern - Saga의 각 단계에서 DB 갱신과 이벤트 발행을 원자적으로 묶는 보완 기법
- Eventual Consistency - Saga가 택하는 일관성 모델 (208 참고)
- Idempotency - 재시도·중복 이벤트 처리 시 안전성을 보장하는 전제조건

# 📝 【답안용】 시험 답안 템플릿

> 목적: 시험장에서 25분에 그대로 쓰는 답안 양식. 작성방식(추상표현 금지·수치·도식·문제유형 전환)을 엄격히 지킨다.
> 핵심: 2PC와 Saga의 정의보다 도메인 정합성, 장애 복구, 락 지속 시간 기준으로 선택한다.

## 핵심 인사이트 (3줄 요약)

> 1. **본질**: 2PC는 Coordinator 기반 원자 커밋, Saga는 Local Transaction과 보상 트랜잭션의 연쇄이다.
> 2. **가치**: MSA에서 서비스별 DB 독립성과 비즈니스 정합성을 동시에 다루는 설계 판단 기준 제공.
> 3. **판단 포인트**: 금융 원장처럼 강한 일관성이 필요하면 2PC/단일 DB, 장기 업무 프로세스는 Saga를 선택한다.

## 출제 의도 및 답안 포인트

| 출제 의도 | 반드시 짚을 핵심 | 감점 회피 포인트 |
|:---|:---|:---|
| 분산 트랜잭션 선택 역량 확인 | ACID, 최종 일관성, 보상 트랜잭션, Coordinator | Saga를 rollback과 동일하게 설명 |
| MSA 데이터 정합성 판단 확인 | DB per Service, Outbox, idempotency, 상태 머신 | 2PC 성능 저하만 쓰고 가용성·락 문제 누락 |
| 장애 복구 설계 확인 | 재시도, 중복 방지, 보상 실패, 관측성 | 실패 시나리오와 검증 지표 누락 |

> 요약: 이 문제는 "무엇이 더 낫다"가 아니라 업무 정합성 요구와 장애 복구 모델별 선택을 묻는다.

## Ⅰ. 개요 및 필요성

- 개요: 분산 트랜잭션 정합성 기법
- 배경: MSA는 서비스별 데이터 소유권 때문에 하나의 DB 트랜잭션으로 업무를 닫기 어렵다.
- 필요성: 주문·결제·재고 업무는 일관성 수준과 장애 복구 절차를 명시해야 한다.

---

## Ⅱ. 구조 및 구성요소

```text
Business Request
  / 2PC: Coordinator -> Prepare Participants -> Commit/Rollback
  / Saga: Orchestrator/Choreography -> Local Tx -> Event -> Compensation
DB per Service -> Outbox -> Message Broker -> Observability
```

| 구성요소 | 역할 | 특이사항 |
|:---|:---|:---|
| Coordinator | 2PC prepare/commit 제어 | 단일 장애 지점과 락 지속 시간 관리 |
| Saga Orchestrator | 단계 순서와 보상 흐름 제어 | 중앙 상태 머신으로 추적 용이 |
| Local Transaction | 서비스 내부 DB 변경 | ACID 범위는 단일 서비스 |
| Compensation | 취소·환불·예약 해제 | 업무 의미상 보상 가능성 검증 |

> 요약: 2PC는 전역 커밋 제어, Saga는 서비스별 완료와 보상 흐름 제어가 구조의 중심이다.

---

## Ⅲ. 동작원리 및 흐름도

```text
Order Request -> Reserve Inventory -> Authorize Payment -> Create Shipment
  / Success -> Order Confirmed -> Event Publish
  / Failure -> Cancel Shipment -> Refund Payment -> Release Inventory
-> State/Audit Log Collect
```

| 단계 | 처리 내용 | 검증 기준 |
|:---:|:---|:---|
| 1 | 업무 단계와 보상 단계 정의 | 상태 전이표 100% 작성 |
| 2 | Local Tx 수행 후 이벤트 발행 | Outbox 미발행 0건 |
| 3 | 실패 감지 후 보상 트랜잭션 실행 | 재시도 3회, DLQ 격리 |
| 4 | 최종 상태 확정과 감사 로그 기록 | saga_id 기준 추적 가능 |

> 요약: Saga는 성공 경로보다 실패 경로의 보상 순서와 중복 실행 방지가 설계의 핵심이다.

## Ⅳ. 특징

| 구분 | 2PC | Saga | 판단 수치 |
|:---|:---|:---|:---|
| 일관성 | 강한 원자 커밋 | 최종 일관성 | 정합성 허용 지연 1~5초 여부 |
| 장애 영향 | Participant prepared 상태 락 | 단계별 보상·재시도 | 락 지속 100ms 초과 시 2PC 부담 증가 |
| 적용 업무 | 짧은 DB 트랜잭션 | 장기 업무 프로세스 | 결제·배송처럼 외부 API 포함 시 Saga |
| 운영 복잡도 | Coordinator 복구 필요 | 상태 머신·보상 설계 필요 | saga failure rate 0.1% 이하 목표 |

> 요약: 2PC는 강한 일관성, Saga는 가용성과 업무 보상을 선택하는 구조이다.

## Ⅴ. 심화 비교 및 적용 판단

| 비교 축 | 기존/대안 | Saga vs 2PC | 선택 기준 |
|:---|:---|:---|:---|
| 구조 | 단일 DB ACID | 서비스별 DB + 이벤트/Coordinator | 서비스 소유권 분리 여부 |
| 비용/성능 | 전역 락·동기 커밋 | 비동기 이벤트·보상 | p95 업무 완료 3초 이하, 락 최소화 |
| 운영/위험 | 커밋 실패 복구 | 보상 실패·중복 이벤트 | audit trail과 idempotency 필수 |

> 요약: 서비스별 DB와 외부 API가 있으면 Saga, 단일 데이터 경계와 강한 원자성이 핵심이면 2PC가 맞다.

| 리스크 | 원인 | 대응 방안 | 확인 지표 |
|:---|:---|:---|:---|
| 보상 실패 | 환불 API 장애, 재고 해제 실패 | 재시도, DLQ, 수동 보정 큐 | compensation failure 0.1% 이하 |
| 중복 처리 | 메시지 재전송, 타임아웃 | idempotency key, unique constraint | duplicate reject count |
| 상태 불일치 | 이벤트 발행 누락 | Transactional Outbox, CDC | outbox lag 5초 이하 |

> 요약: Saga 운영은 보상 실패, 중복 처리, 이벤트 발행 누락을 지표로 통제한다.

| 점검 항목 | 목표 기준 | 측정 방법 |
|:---|:---|:---|
| 정합성 지연 | 최종 상태 도달 p95 3초 이하 | saga state metric |
| 실패 복구 | DLQ 15분 이내 처리 | broker, runbook |
| 감사성 | saga_id 기반 100% 추적 | distributed tracing, audit log |

> 요약: 성공 여부는 최종 상태 도달 시간, 실패 복구 시간, 업무 추적성으로 판정한다.

## Ⅵ. 실무 적용 및 결론

**적용 방안 3개 (필수 — 단계별 또는 항목별):**
1. 업무 분류: 원장·잔액 차감은 단일 DB 또는 2PC, 주문·배송·알림은 Saga로 분리하고 정합성 허용 지연 3초 기준 설정
2. Saga 구현: Orchestration 상태 머신, Outbox, idempotency key, DLQ를 기본 구성으로 적용
3. 검증 체계: 보상 실패 0.1% 이하, outbox lag 5초 이하, saga_id 추적률 100%를 운영 지표로 등록

**결론 (2줄):**
- 기술사 판단: 강한 원자성이 업무 불변조건이면 2PC/단일 DB, 장기 업무 흐름과 서비스 자율성이 우선이면 Saga 선택
- 향후 방향: Event Sourcing, CDC, Workflow Engine을 결합해 보상 상태와 감사 추적을 자동화하는 방향으로 발전
