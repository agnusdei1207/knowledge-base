# 📖 【암기용】 개념 완전 이해

## 한눈에
- **개요**: 분산된 여러 데이터베이스에 걸친 트랜잭션의 데이터 일관성을 보장하는 두 가지 대표적 설계 패턴
- **왜 필요한가**: MSA 환경에서는 서비스마다 각자의 DB를 가지므로(DB per Service), 하나의 비즈니스 요청(예: 주문->결제->재고 차감)이 여러 DB를 수정할 때 모두 성공하거나 모두 실패(Rollback)하도록 보장해야 한다.
- **핵심 직관**: 2PC는 "모두 준비됐어? 그럼 한 번에 쏴!"(강한 일관성), Saga는 "일단 각자 하고, 문제 생기면 취소 작업(보상 트랜잭션)을 해라!"(최종 일관성).

## 핵심 용어 정리

| 용어/표기 | 의미 | 비유·예 |
|:---|:---|:---|
| 분산 트랜잭션 | 물리적으로 분리된 여러 시스템에서 수행되는 하나의 논리적 작업 단위 | 쇼핑몰 주문 (주문 DB + 결제 DB + 재고 DB) |
| 2PC (Two-Phase Commit) | 모든 참여 노드를 동시에 Lock 걸어 커밋을 준비·실행하는 동기식 프로토콜 | 결혼식 서약 "이의 없습니까? -> 네 -> 선언합니다" |
| Saga 패턴 (Saga Pattern) | 로컬 트랜잭션들을 비동기 이벤트로 연결하여 일관성을 맞추는 패턴 | 이어달리기 바톤 터치, 문제 생기면 거꾸로 달림 |
| 보상 트랜잭션 (Compensating Transaction) | Saga에서 앞선 로컬 트랜잭션의 결과를 논리적으로 취소하는 작업 | 결제 완료 후 재고 부족 시 '환불 처리' 실행 |

## 깊이 이해
- **배경·문제의식**: 모놀리식에서는 단일 DB의 ACID 속성을 쓰면 되지만, 분산 환경에서는 불가능하다. 2PC는 강한 일관성을 주지만 모든 노드가 준비될 때까지 락(Lock)이 걸려 대용량 트래픽에서 심각한 병목을 유발한다.
- **작동 원리**:
  - **2PC**: 코디네이터가 1단계(Prepare)에서 모든 노드에 가능 여부를 묻고 락을 건다. 모두 OK면 2단계(Commit)로 완료. 하나라도 No면 모두 Abort. 노드 장애 시 무한 대기(Blocking) 문제 발생.
  - **Saga**: 코디네이터(Orchestration) 또는 이벤트(Choreography)를 통해 순차적으로 로컬 트랜잭션을 실행한다. 중간에 실패하면 역순으로 보상 트랜잭션을 발행하여 이전 상태로 되돌린다.
- **비유**: 2PC는 친구 5명이 메뉴를 통일할 때까지 아무도 주문 못하는 짬뽕집. Saga는 각자 시키되 품절이면 그 사람만 환불받는 푸드코트.
- **구체 예시**: 항공권+호텔+렌터카 예약 패키지. 2PC라면 세 시스템 모두 응답할 때까지 다른 예약을 막음. Saga는 비행기 예약 후 이벤트 발행 -> 호텔 예약 후 이벤트 발행 -> 렌터카 실패 시 호텔 취소 이벤트 -> 비행기 취소 이벤트 발행.
- **흔한 오해·주의점**: Saga 패턴은 ACID 중 '격리성(Isolation)'이 완벽하지 않다(중간 상태 노출). 따라서 최종 일관성(Eventual Consistency)으로 만족할 수 있는 도메인인지 반드시 판단해야 한다.

## 연결 개념
- 마이크로서비스 아키텍처 MSA
- 트랜잭션 ACID
- 이벤트 기반 아키텍처 (EDA)

# 📝 【답안용】 시험 답안 템플릿

## 핵심 인사이트 (3줄 요약)

> 1. **본질**: 2PC는 분산 노드 간 강한 일관성(Strong Consistency)을 보장하는 동기식 제어 프로토콜이며, Saga는 이벤트 기반의 최종 일관성(Eventual Consistency) 모델이다.
> 2. **가치**: 대규모 MSA 트래픽 환경에서 2PC의 동기식 Lock 병목을 제거하고, 시스템 가용성과 독립성을 확보하기 위해 Saga 패턴으로 전환한다.
> 3. **판단 포인트**: 데이터 정합성이 즉시 완벽해야 하는 금융 원장은 2PC(또는 TCC), 가용성과 응답 속도가 중요한 커머스 환경은 Saga를 선택한다.

## 출제 의도 및 답안 포인트

| 출제 의도 | 반드시 짚을 핵심 | 감점 회피 포인트 |
|:---|:---|:---|
| MSA 분산 트랜잭션 해결 역량 | 2PC의 Prepare/Commit 구조, Saga의 보상 트랜잭션 | 2PC와 Saga를 상호 보완재가 아닌 단순 우열 관계로 단정 |
| 시스템 특성에 따른 트레이드오프 판별 | 일관성(Consistency) vs 가용성(Availability) 관점의 대조 | Saga 적용 시 격리성(Isolation) 부재로 인한 더티 리드 리스크 누락 |

> 요약: 분산 환경에서 강한 일관성을 좇으면 가용성이 무너지므로(CAP 정리), 비즈니스 성격에 따라 2PC와 Saga 중 적합한 타협점을 찾아야 한다.

## Ⅰ. 개요 및 필요성

- 개요: 물리적으로 분리된 여러 DB 인스턴스에 걸친 트랜잭션을 하나의 원자적 작업 단위로 제어하기 위한 아키텍처 설계 패턴
- 배경: MSA의 DB per Service 구조 도입으로 단일 DBMS가 제공하던 ACID 트랜잭션 보장 불가
- 필요성: 글로벌 동기화 병목 제거(Saga), 혹은 엄격한 즉시 정합성(2PC) 보장 요구

---

## Ⅱ. 구조 및 구성요소

```text
[2PC 구조] Coordinator -> Prepare(Lock) -> 노드 응답 -> Commit/Abort -> 노드 반영
[Saga 구조] Service A(로컬 Tx) -> Event -> Service B(로컬 Tx) -> 실패 시 보상 Event -> Service A(보상 Tx)
```

| 구분 | 구성요소 | 역할 |
|:---|:---|:---|
| 2PC | Transaction Coordinator | 분산 트랜잭션의 Prepare/Commit 단계를 중앙 통제 |
| 2PC | Participant (Node) | 로컬 자원 락(Lock) 점유 및 Coordinator 명령 수행 |
| Saga | Local Transaction | 각 마이크로서비스 내 단위 DB 상태 변경 |
| Saga | Compensating Transaction | 이전 단계의 로컬 트랜잭션 결과를 논리적으로 취소(Undo) |

> 요약: 2PC는 중앙 코디네이터가 락을 쥐고 통제하며, Saga는 독립적인 로컬 트랜잭션과 실패 복구용 보상 트랜잭션으로 구성된다.

---

## Ⅲ. 동작원리 및 흐름도

```text
요청 수신 -> 로컬 처리(또는 Prepare) -> 후속 노드 호출 -> 실패 판정 -> Commit 또는 보상(Abort)
```

- 1단계 [요청 진입]: 단일 비즈니스 트랜잭션을 시작하는 코디네이터 서비스가 요청을 수신
- 2단계 [처리 전개]: 2PC는 전 노드 Prepare 수행, Saga는 순차적 로컬 트랜잭션 커밋 및 이벤트 발행
- 3단계 [검증·통제]: 대상 노드 전체 성공 여부 확인, 하나라도 실패 시 복구 프로세스 트리거
- 4단계 [결과 반영]: 2PC는 일괄 Rollback(Abort), Saga는 역순으로 보상 트랜잭션 발행하여 최종 복구

> 요약: 2PC는 자원을 묶은 상태에서 한 번에 결정을 내리고, Saga는 쪼개서 실행하다 실패 시 논리적 되감기를 수행한다.

---

## Ⅳ. 특징
- 2PC: [강한 일관성] 원자성과 격리성이 보장되나, 한 노드 지연 시 전체 시스템이 대기 상태(Blocking)에 빠짐
- Saga: [최종 일관성] Lock을 점유하지 않아 가용성·확장성이 뛰어나나, 중간 상태 노출(Lack of Isolation) 문제 발생
- 구현 복잡도: [설계 부담] 2PC는 미들웨어(XA 프로토콜) 지원이 필요하고, Saga는 비즈니스 로직(보상 트랜잭션)을 직접 개발해야 함

> 요약: 2PC는 동기식 병목이라는 성능적 한계를, Saga는 격리성 부재와 보상 로직 구현이라는 복잡성을 트레이드오프한다.

---

## Ⅴ. 심화 비교 및 적용 판단

| 비교 축 | 2PC (Two-Phase Commit) | Saga 패턴 | 선택 기준 |
|:---|:---|:---|:---|
| 일관성 수준 | 강한 일관성 (Strong Consistency) | 최종 일관성 (Eventual Consistency) | 비즈니스 허용 오차 |
| 트랜잭션 제어 | 동기식 차단 (Blocking) | 비동기식 비차단 (Non-Blocking) | 시스템 트래픽 규모 |
| 실패 복구 방식 | 락 기반 일괄 Rollback | 논리적 보상 트랜잭션 (Compensating) | 상태 복원 가능성 |

> 요약: 트래픽이 집중되는 B2C 커머스 환경은 Saga를, 정합성이 최우선인 백오피스 금융 원장은 2PC 계열을 선택한다.

**리스크·대응 (기본은 불릿):**
- Saga 격리성 부족 (Dirty Read): 보상 트랜잭션 완료 전에 타 서비스가 데이터 접근 → Semantic Lock (상태 플래그 'PENDING' 추가) (지표: 정합성 오류 건수)
- Saga 보상 트랜잭션 실패: 복구 중 인프라/네트워크 장애 → 이벤트 재시도(Retry) 메커니즘 및 멱등성(Idempotency) 설계 보장 (지표: Dead Letter Queue 누적)
- 2PC 코디네이터 SPOF: 코디네이터 다운 시 참여자 무한 대기 → 코디네이터 이중화 및 Timeout 기반 Abort 전략 (지표: Tx Blocking 타임아웃 횟수)

## Ⅵ. 실무 적용 및 결론

**적용 방안 3개:**
1. Choreography vs Orchestration: 서비스가 3개 이하로 적으면 이벤트 기반(Choreography) 적용, 4개 이상 복잡하면 오케스트레이터(Orchestration) 전용 서비스 구축
2. 멱등성(Idempotency) 키 적용: Saga 보상 트랜잭션이 네트워크 이슈로 중복 호출되더라도 안전하게 복구되도록 고유 트랜잭션 ID 기반 설계
3. 타협적 TCC 패턴 적용: 2PC의 병목과 Saga의 중간상태 노출을 절충하기 위해 비즈니스 레벨의 Try-Confirm/Cancel 패턴 도입 검토

**결론:**
- 기술사 판단: MSA 환경에서 데이터 동기화 문제를 인프라(2PC)에 의존하면 가용성이 저해되므로, 도메인 주도 설계(DDD) 관점에서 비즈니스 로직(Saga)으로 풀어내는 것이 권장된다.
- 향후 방향: 최근에는 Outbox 패턴과 CDC(Change Data Capture)를 결합하여 Saga의 이벤트 발행 안정성을 보장하는 방식이 표준 아키텍처로 자리잡고 있다.
