# 📖 【암기용】 개념 완전 이해

## 한눈에
- **개요**: 웹 환경에서 서버와 클라이언트 간의 실시간 양방향·단방향 통신을 구현하는 기술
- **왜 필요한가**: 기존 HTTP는 클라이언트가 요청해야만 서버가 응답하는 단방향 방식이므로 실시간 채팅이나 주식 알림 등에 부적합하기 때문
- **핵심 직관**: 웹 소켓은 양방향 전화선이고, SSE는 서버가 클라이언트에게 라디오 방송을 지속해서 쏴주는 것

## 핵심 용어 정리

| 용어/표기 | 의미 | 비유·예 |
|:---|:---|:---|
| WebSocket | 클라이언트와 서버가 연결을 유지하며 양방향 통신 | 실시간 채팅, 1:1 전화 통화 |
| SSE (Server-Sent Events) | 서버가 클라이언트에게 단방향으로 이벤트 스트림 전송 | 주식 시세 알림, 라디오 방송 |
| HTTP Long Polling | 요청을 열어두고 응답이 올 때까지 대기 | "응답 올 때까지 기다릴게요" |

## 깊이 이해
- **배경·문제의식**: HTTP/1.1은 stateless하며 요청/응답 기반이다. 실시간성을 위해 polling을 쓰면 오버헤드가 크고, long polling도 지연과 자원 낭비가 발생한다.
- **작동 원리**:
  - **웹 소켓**: HTTP 80/443 포트를 통해 Handshake를 수행한 후, `ws://` 또는 `wss://` 프로토콜로 전환하여 연결을 유지하며 프레임을 양방향으로 주고받는다.
  - **SSE**: HTTP 프로토콜 위에서 `text/event-stream` MIME 타입을 사용하여, 서버가 연결을 끊지 않고 계속 데이터를 밀어넣어준다(Push). 클라이언트는 수신만 한다.
- **비유**: 웹 소켓은 전화기(서로 말하기), SSE는 서버가 말하고 클라이언트가 듣는 확성기 방송.
- **구체 예시**: 주식 시세 티커는 SSE가 유리하고(서버 -> 수많은 클라이언트), 온라인 게임이나 채팅은 웹 소켓(클라이언트 ↔ 서버 실시간 데이터 교환)이 필수다.
- **흔한 오해·주의점**: 무조건 양방향인 웹 소켓이 좋다고 생각하기 쉬우나, 클라이언트에서 서버로 보낼 데이터가 거의 없는 단방향 알림 시스템에서는 SSE가 HTTP 인프라(캐싱, 자동 재연결)를 그대로 활용할 수 있어 훨씬 효율적이다.

## 연결 개념
- 리액티브 프로그래밍 (Reactive Programming)
- 비동기 I/O·이벤트 루프
- HTTP/2, HTTP/3

# 📝 【답안용】 시험 답안 템플릿

## 핵심 인사이트 (3줄 요약)

> 1. **본질**: WebSocket은 양방향 실시간 통신 표준이며, SSE는 서버 주도의 단방향 이벤트 스트리밍 기술이다.
> 2. **가치**: HTTP Polling 방식의 불필요한 네트워크 오버헤드를 제거하여 실시간 웹 애플리케이션의 성능과 자원 효율성을 극대화한다.
> 3. **판단 포인트**: 통신의 방향성(단방향 vs 양방향)과 기존 인프라(L4/L7 로드밸런서, 방화벽) 호환성을 기준으로 선택한다.

## 출제 의도 및 답안 포인트

| 출제 의도 | 반드시 짚을 핵심 | 감점 회피 포인트 |
|:---|:---|:---|
| 실시간 통신 프로토콜의 원리 및 한계 파악 | Handshake, Event Stream, 단방향 vs 양방향 비교축 | WebSocket을 단순히 HTTP 대체로 단정 |
| 시스템 요구사항에 따른 기술 선택 역량 | 요구사항(채팅 vs 알림)에 맞춘 WebSocket/SSE 적용 기준 | 두 기술의 프로토콜 계층(TCP vs HTTP 위) 혼동 |

> 요약: 실시간 통신의 요구사항(방향성)과 인프라 호환성을 비교하여 최적의 프로토콜을 제시할 수 있어야 한다.

---

## Ⅰ. 개요 및 필요성

- 개요: HTTP 환경의 단방향 요청-응답 한계를 극복하기 위해 설계된 실시간 양방향(WebSocket) 및 단방향(SSE) 통신 프로토콜
- 배경: REST API와 Polling 기반 아키텍처에서는 잦은 헤더 교환과 연결 수립으로 네트워크 오버헤드와 지연 발생
- 필요성: 밀리초(ms) 단위 지연시간 보장, 수만 명 동시 접속 처리, 서버 리소스 최적화

---

## Ⅱ. 구조 및 구성요소

```text
클라이언트 (Browser) <-> L7 Load Balancer <-> 서버 (Node.js/Spring)
         |                                       |
         +-> WebSocket: TCP 소켓 위 양방향 프레임 교환
         +-> SSE: HTTP 응답 지속 (text/event-stream)
```

| 기술 | 역할 | 특이사항 |
|:---|:---|:---|
| WebSocket Handshake | HTTP로 최초 연결 후 `Upgrade` 헤더로 프로토콜 전환 | 80/443 포트 사용, 방화벽 통과 용이 |
| WebSocket Frame | 텍스트 및 바이너리 데이터를 작은 프레임 단위로 송수신 | Ping/Pong 프레임으로 연결 유지 |
| SSE EventSource | 브라우저 내장 API로 서버 이벤트 스트림 수신 대기 | 연결 끊김 시 자동 재연결(Auto-Reconnect) 내장 |

> 요약: WebSocket은 HTTP Handshake 후 독립적인 양방향 채널을 열고, SSE는 HTTP 프로토콜 위에서 응답을 지속하는 구조다.

---

## Ⅲ. 동작원리 및 흐름도

```text
[WebSocket] Handshake 요청 -> Protocol Upgrade -> 양방향 Frame 송수신 -> Close
[SSE]       HTTP GET 요청 -> 연결 유지 -> 서버가 Event 연속 Push -> (끊기면 재연결)
```

- 1단계 [연결 요청]: 클라이언트가 서버에 WebSocket Upgrade 헤더 또는 SSE GET 요청
- 2단계 [연결 수립]: 서버가 프로토콜 전환(101 Switching Protocols) 또는 Event-Stream(200 OK) 응답
- 3단계 [데이터 전송]: WebSocket은 양방향 프레임 교환, SSE는 서버가 텍스트 스트림 연속 Push
- 4단계 [종료·복구]: 명시적 연결 종료(Close Frame) 또는 네트워크 단절 시 SSE는 자동 재연결 시도

> 요약: WebSocket은 최초 연결 시에만 HTTP를 거친 후 양방향 통신하고, SSE는 HTTP 연결을 연 채로 서버가 계속 데이터를 밀어낸다.

---

## Ⅳ. 특징
- 실시간 양방향 (WebSocket): [채팅·게임] 바이너리 지원, 오버헤드 최소화로 밀리초 단위 지연시간 달성
- 단방향 푸시 (SSE): [시세·알림] HTTP 인프라 캐싱 재사용, 자동 재연결(Auto-Reconnect) 내장
- 상태 유지 한계: [공통] 스케일 아웃 시 세션 클러스터링이나 메시지 브로커(Redis Pub/Sub 등) 연동 필수

> 요약: WebSocket은 양방향 저지연 통신에, SSE는 단방향 알림과 기존 HTTP 인프라 활용에 강점이 있다.

## Ⅴ. 심화 비교 및 적용 판단

| 비교 축 | WebSocket | SSE (Server-Sent Events) | Long Polling | 선택 기준 |
|:---|:---|:---|:---|:---|
| 방향성 | 양방향 전이중 (Full-Duplex) | 서버 -> 클라이언트 (단방향) | 반이중 (요청 후 대기) | 송수신 비율 |
| 프로토콜 | 최초 HTTP 이후 독립 프로토콜 | 순수 HTTP 기반 | 순수 HTTP 기반 | 인프라 호환성 |
| 적합 사례 | 실시간 채팅, 멀티플레이어 게임 | 주식 티커, 뉴스 피드, 알림 | 호환성이 극도로 필요한 구형 환경 | 비즈니스 요구 |

> 요약: 클라이언트 송신이 빈번하면 WebSocket을, 서버 푸시 위주면 SSE를 선택하는 것이 아키텍처 원칙이다.

**리스크·대응 (기본은 불릿):**
- 연결 과부하: 포트 고갈·메모리 부족 → 커넥션 수 제한, Nginx Worker/포트 튜닝 (지표: Active Connection 수)
- 스케일 아웃 시 세션 단절: 서버 간 메시지 전달 불가 → Redis Pub/Sub, Kafka 메시지 브로커 도입 (지표: 메시지 유실률)
- 로드밸런서 타임아웃: L4/L7 장비가 idle 커넥션을 끊음 → Ping/Pong Keep-Alive 설정, Timeout 연장 (지표: 의도치 않은 연결 종료 횟수)

---

## Ⅵ. 실무 적용 및 결론

**적용 방안 3개:**
1. 하이브리드 아키텍처: 일반적인 데이터 조회는 REST API를 사용하고, 실시간 이벤트나 알림 수신 구간에만 SSE를 국소 적용
2. 인프라 설정 고도화: Nginx 등 리버스 프록시에서 `proxy_read_timeout` 및 `Connection: Upgrade` 헤더 릴레이 설정 적용
3. 브로커 기반 스케일 아웃: 여러 WAS 서버에 접속한 클라이언트들에게 메시지를 전파하기 위해 Redis Pub/Sub을 백엔드 메시지 버스로 연동

**결론:**
- 기술사 판단: 클라이언트 발송이 잦지 않은 90% 이상의 '알림' 업무는 SSE가 HTTP 인프라(L7, 보안장비) 호환성 면에서 WebSocket보다 유리하다.
- 향후 방향: HTTP/3 확산에 따라 단일 UDP 커넥션 위에서 WebTransport API가 WebSocket과 SSE의 장점을 통합 대체할 것으로 전망된다.
