## 핵심 인사이트 (3줄 요약)
- 브라우저가 먼저 물어봐야만 대답해 주는 콧대 높은 HTTP(단방향)의 한계를 깨고, **"서버가 클라이언트에게 먼저 데이터를 밀어 넣어주는(Push)" 실시간 통신 기술의 양대 산맥**.
- **WebSocket**은 전화 통화처럼 **'양방향'** 파이프를 뚫어놓고 서로 쉴 새 없이 데이터를 주고받는 기술(채팅, 멀티플레이 게임에 필수).
- **SSE(Server-Sent Events)**는 라디오 방송처럼 서버가 클라이언트에게 **'단방향'**으로 데이터만 계속 쏴주는 기술(주식 호가 창, 알림 푸시, ChatGPT의 타자 치듯 나오는 응답에 최적).

## Ⅰ. 개요 및 필요성
- **개요**: 클라이언트와 서버 간의 실시간 데이터 전송을 구현하기 위해 사용하는 웹 프로토콜 기술. (HTTP Polling/Long-Polling의 한계를 극복함).
- **필요성**: 카카오톡 웹 버전을 만듦. 클라이언트(브라우저)가 "새 메시지 왔어?"라고 1초에 한 번씩 서버에 HTTP로 계속 물어봄(Polling). 친구가 1분 동안 카톡을 안 보내면 서버는 60번이나 "안 왔어!"라고 허공에 대답하며 CPU와 네트워크를 엄청 낭비함. **"아니, 브라우저는 가만히 냅두고, 진짜 새 카톡이 도착했을 때만 서버가 브라우저를 콕 찔러서(Push) 알려주면 안 돼?"**라며 WebSocket과 SSE가 등장함.
---
## Ⅱ. 아키텍처 및 핵심 원리
- **1. WebSocket (웹소켓) - 양방향 고속도로**:
  - **Handshake**: 처음에 브라우저가 일반 HTTP로 "우리 웹소켓으로 통신하자"고 요청(Upgrade). 서버가 "콜!" 하면, 그 HTTP 파이프가 '웹소켓 전용 파이프(TCP)'로 변신함.
  - **양방향 (Bi-directional)**: 이때부터는 누가 먼저랄 것 없이 파이프를 통해 서로 데이터를 마음대로 던짐. HTTP 헤더(쓸데없는 껍데기)도 없어져서 엄청 가볍고 빠름.
  - 주소 체계: `ws://` 또는 `wss://` (보안).
- **2. SSE (Server-Sent Events) - 단방향 라디오 방송**:
  - 철저하게 HTTP 프로토콜 안에서 돎. (별도의 프로토콜 아님).
  - 브라우저가 "나 구독할래"라고 HTTP 요청을 던짐. 
  - 서버는 응답(Response)을 닫지 않고 파이프를 열어둔 채, 이벤트가 생길 때마다 텍스트 덩어리를 툭, 툭, 툭 떨어뜨림.
  - **단방향 (Uni-directional)**: 서버 ➡️ 클라이언트로만 가능. 클라이언트가 말을 걸려면 별도의 일반 HTTP POST(API)를 쏴야 함.

```text
[ 실시간 통신 기술 비교: Polling vs WebSocket vs SSE ]

 🔄 [ HTTP Polling (과거의 멍청한 방식) ]
 클라이언트: "새 카톡 왔어?" ➡️ 서버: "아니" (연결 끊김)
 클라이언트: "새 카톡 왔어?" ➡️ 서버: "아니" (연결 끊김) -> 서버 터짐 💥

 ☎️ [ WebSocket (전화 통화 - 양방향) ]
 클라이언트 ↔️ (전용 파이프 연결 유지) ↔️ 서버 
 클라이언트: "나 게임 캐릭터 앞으로 간다!" ➡️ 서버: "오케이!"
 서버: "앗! 괴물이 나타났다!" ➡️ 클라이언트: "도망쳐!" (동시 다발 통신)

 📻 [ SSE (라디오 방송 - 단방향 Push) ]
 클라이언트 ➡️ "나 ChatGPT 대답 들을래!" (연결 유지)
 서버 ➡️ "안"
 서버 ➡️ "녕"
 서버 ➡️ "하"
 서버 ➡️ "세" ... (서버가 일방적으로 스트리밍 쏴줌)
```

## Ⅲ. 비교 및 연결
| 구분 | WebSocket (웹소켓) | SSE (Server-Sent Events) |
|---|---|---|
| **통신 방향** | **양방향 (Full-Duplex)** | **단방향 (서버 ➡️ 클라이언트)** |
| **프로토콜** | 독자적 프로토콜 (`ws://`) | 기존 HTTP (`http://`) 기반 |
| **데이터 포맷** | 텍스트(JSON) 및 바이너리 모두 가능 | 오직 텍스트(UTF-8)만 가능 |
| **재연결(Reconnection)**| 끊기면 개발자가 직접 다시 맺는 코드 짜야 함 | 브라우저가 알아서 **자동 재연결(Built-in)** 해줌 |
| **적합한 유스케이스**| 줌(Zoom), 멀티플레이 게임, 카카오톡 | 주식 차트 갱신, 알림, **LLM(ChatGPT) 스트리밍 응답** |
---
## Ⅳ. 실무 적용 및 기술사 판단
- **LLM 스트리밍 응답을 위한 SSE의 부활**: 과거에는 무조건 'WebSocket'이 최고인 줄 알았음. 하지만 ChatGPT 같은 생성형 AI가 등장하면서 트렌드가 바뀜. LLM의 답변은 "서버가 클라이언트에게 일방적으로 타이핑 치듯 내려주는 것"임. 여기에 복잡한 WebSocket을 쓰는 건 닭 잡는 데 소 잡는 칼을 쓰는 격임. 기술사는 **"단방향 텍스트 스트리밍에는 HTTP 인프라(L7 로드밸런서 등)를 그대로 재사용할 수 있고 구현이 10배 쉬운 SSE를 채택하라"**고 아키텍처 결정을 내려야 함.
- **WebSocket의 로드밸런싱 문제 (Sticky Session)**: WebSocket은 L4/L7 스위치를 거칠 때 파이프가 끊어지면 안 됨. 로드밸런서가 연결을 1번 서버로 맺어줬으면, 그 통신이 끝날 때까지 무조건 1번 서버로만 패킷을 보내야 함(Sticky Session). 만약 중간에 Nginx 설정이 잘못되어 연결을 자꾸 리셋하면, 유저들은 10초마다 튕기는 끔찍한 게임을 경험하게 됨. 프록시(Proxy) 타임아웃 설정을 무한대로 늘려주는 인프라 세팅이 필수임.

## Ⅴ. 기대효과 및 결론
- "새로고침(F5)을 눌러야만 화면이 바뀌던" 정적인 웹 브라우저의 한계를 부수고, 살아 숨 쉬는 실시간 양방향 웹 애플리케이션 시대를 엶.
- 기술의 우열이 아니라 용도(양방향 게임 vs 단방향 알림/스트리밍)에 따라 WebSocket과 SSE를 적재적소에 하이브리드로 활용하는 것이 현대 프론트엔드 아키텍처의 핵심임.

### 👶 어린이를 위한 3줄 비유 설명
1. **폴링(Polling)**은 엄마한테 "다 됐어? 다 됐어? 다 됐어?"라고 1초마다 계속 물어봐서 엄마를 화나게 하는 거예요.
2. **웹소켓(WebSocket)**은 엄마랑 '무전기'를 켜놓고, 내가 말할 때 엄마도 동시에 말할 수 있는 양방향 대화 채널이에요. (게임할 때 좋아요).
3. **SSE(Server-Sent Events)**는 '라디오'예요. 나는 듣기만 하고, 엄마 방송국에서 "이제 밥 먹어~"라고 알림이 올 때까지 그냥 스피커만 켜두면 된답니다! (ChatGPT 응답 들을 때 최고예요!).
