## 핵심 인사이트 (3줄 요약)
- 과거엔 해커가 완성된 '은행 앱'을 직접 공격했다면, 이제는 **그 앱을 만들 때 개발자가 무심코 다운로드하는 오픈소스나 앱을 굽는 '빌드 서버(CI/CD)'를 먼저 해킹해서 바이러스를 섞어버리는 우회 공격**의 총칭.
- 개발 환경(IDE) ➡️ 코드 저장소(Git) ➡️ 패키지 매니저(npm, Maven) ➡️ 빌드 서버(Jenkins) ➡️ 배포(K8s)로 이어지는 **길고 복잡한 '컨베이어 벨트' 전 구간**을 방어해야 함.
- 이 거대한 위험을 막기 위한 3대 핵심 무기가 바로 **SBOM(무엇을 썼는가?), VEX(진짜 위험한가?), SLSA(공정이 깨끗한가?)**이며, 현재 전 세계 사이버 보안 1순위 과제임.
---
## Ⅰ. 개요 및 필요성
- **개요**: 소프트웨어가 기획, 개발, 빌드, 테스트, 배포되는 전체 생명주기(Supply Chain) 과정에서 침투할 수 있는 악성코드 주입, 소스코드 변조, 권한 탈취 등의 위협을 방어하는 종합 보안 체계.
- **필요성**: 은행 보안팀이 방화벽을 수십억 원어치 샀음. 근데 정작 은행 개발자가 앱을 만들 때 깃허브에서 가져온 '달력 라이브러리(오픈소스)' 안에 해커가 심어놓은 백도어가 들어있었음. 앱이 배포되자마자 방화벽 안쪽에서부터 털리기 시작함. **"아무리 성벽을 높게 쌓아도, 성 안으로 들어오는 식량(오픈소스)과 수레(빌드 서버)가 오염되면 끝이다! 개발부터 배포까지의 모든 경로(공급망)를 의심하고 검증해야 한다!"**
---
## Ⅱ. 3대 주요 공격 벡터와 방어 원리
소프트웨어가 만들어지는 컨베이어 벨트는 크게 3곳에서 털림.

- **1. 코드 의존성 중독 (Dependency Poisoning)**:
  - 공격: 해커가 정상적인 오픈소스(예: `react-color`)의 관리자 계정을 털어서 악성코드를 몰래 업데이트함. 전 세계 개발자들이 `npm install`을 치는 순간 다 감염됨. (타이포스쿼팅: `react-colr`처럼 이름만 비슷하게 만들어서 낚기도 함).
  - 방어: **SBOM**을 통해 내가 쓴 라이브러리를 100% 추적하고, 취약점 스캐너로 실시간 감시.
- **2. 빌드 파이프라인 타협 (Pipeline Compromise)**:
  - 공격: 젠킨스(Jenkins)나 GitHub Actions 서버 자체를 해킹함. 소스코드는 정상인데, 컴파일되는 순간에 악성코드를 끼워 넣음. (SolarWinds 사태).
  - 방어: **SLSA** 프레임워크를 도입하여 빌드 환경을 격리(Isolated)하고, 결과물에 암호학적 서명(Provenance)을 강제.
- **3. 코드 저장소 변조 (Source Code Modification)**:
  - 공격: 개발자의 GitHub 계정을 탈취하여 악성 커밋을 푸시함.
  - 방어: 강력한 **MFA(다중 인증)**, 브랜치 보호 규칙(Branch Protection), 반드시 2명 이상의 **코드 리뷰(Code Review)**를 거쳐야만 머지되도록 통제.

```text
[ 소프트웨어 공급망의 라이프사이클과 공격 포인트 ]

 🌍 인터넷/오픈소스 (공격지점 1: 의존성 중독) ➡️ 방어: SBOM / SCA 툴
   ⬇️ (개발자가 다운로드)
 💻 개발자 노트북 / Git (공격지점 2: 계정 탈취) ➡️ 방어: MFA / 코드 리뷰 의무화
   ⬇️ (코드 Push)
 ⚙️ 빌드 서버 (CI) (공격지점 3: 빌드서버 해킹) ➡️ 방어: SLSA / 클린룸 빌드 / 서명
   ⬇️ (도커 이미지 배포)
 🚢 운영 서버 (K8s) (공격지점 4: 위조된 이미지 배포) ➡️ 방어: OPA를 통한 서명 검증 / Zero Trust
```

## Ⅲ. 기존 보안(AppSec)과 공급망 보안(SSCS) 비교
| 구분 | 기존 애플리케이션 보안 (AppSec) | 소프트웨어 공급망 보안 (SSCS) |
|---|---|---|
| **초점** | **내가 짠 코드**에 버그(SQL 인젝션 등)가 없는가? | **내가 가져다 쓴 코드와 빌드 과정**이 안전한가? |
| **방어 위치** | 주로 완성된 앱 (WAF, 모의해킹) | **개발 시작부터 배포까지의 모든 단계 (DevSecOps)** |
| **주요 위협** | 코드 로직 결함, 해커의 직접 공격 | **서드파티 오픈소스 취약점, CI/CD 파이프라인 오염** |
| **해결 도구** | SAST, DAST, 방화벽 | **SBOM, SLSA, VEX, SCA(Software Composition Analysis)** |

## Ⅳ. 실무 적용 및 기술사 판단
- **DevSecOps의 완성, Shift-Left**: 기술사는 공급망 보안을 '보안팀'만의 업무로 두면 절대 막을 수 없음을 알아야 함. 보안 검사를 맨 마지막 배포 직전에 하는 것이 아니라, 개발자의 IDE(코드 작성 단계)와 Git Commit 단계로 최대한 왼쪽으로 당기는 **Shift-Left** 철학을 구현해야 함. 코드를 올리자마자 스캐너가 돌아서 취약한 오픈소스를 뱉어내게 만드는 파이프라인 자동화가 필수임.
- **Zero Trust 아키텍처와의 융합**: 공급망 보안의 끝판왕은 결국 '아무도 믿지 않는 것'임. 내부망에 있는 젠킨스(Jenkins) 서버가 만든 도커 이미지라고 해서 무조건 K8s에 배포해주면 안 됨. **"이 이미지가 정말 젠킨스가 만든 게 맞는지(Sigstore 서명 확인), 취약점은 없는지(SBOM 검사)"**를 배포 직전에 한 번 더 검증하는 'Zero Trust 기반의 Admission Control' 체계를 구축해야 완전한 방어가 됨.

## Ⅴ. 기대효과 및 결론
- 한 기업의 담장을 넘어, 전 세계 소프트웨어 생태계가 얽히고설킨 현대 클라우드 환경에서 '연쇄적인 사이버 대재앙'을 막아내는 최후의 보루.
- 코드를 짜는 개발자, 파이프라인을 만드는 DevOps, 정책을 세우는 보안팀이 하나의 파이프라인 위에서 강제로 협업하게 만들어 전사적인 보안 수준을 극적으로 끌어올림.

### 👶 어린이를 위한 3줄 비유 설명
1. 옛날엔 도둑이 우리 집 창문을 깨고 들어오는 것(직접 해킹)만 막으면 됐어요.
2. 요즘 도둑들은 창문을 깨는 대신, 우리가 시켜 먹는 '피자 배달부(오픈소스)'나 피자를 굽는 '식당 주방장(빌드 서버)'을 몰래 매수해서 피자에 독을 타게 만들어요. (공급망 공격).
3. **공급망 보안**은 피자 재료는 안전한지(SBOM), 주방에 도둑이 숨어있진 않은지(SLSA) 처음부터 끝까지 깐깐하게 감시하는 위생 검사 시스템이랍니다!
