## 미리 알고가기

- 코드 스멜은 당장 버그는 아니지만 유지보수 문제를 예고하는 구조 신호임
- 긴 메서드와 중복 코드와 큰 클래스가 대표 예시임
- 변경 빈도·결함 이력·결합 범위가 큰 코드 스멜부터 리팩터링 우선순위를 높임

## Ⅰ. 개요

- **정의/개념**: 코드 스멜은 코드가 지금 바로 오동작하지 않더라도 가독성과 변경 용이성과 테스트 가능성을 해쳐 향후 결함과 기술부채로 이어질 가능성을 알려 주는 구조적 징후임.
- **배경/필요성**: 유지보수 문제는 갑자기 생기기보다 작은 구조 악화가 누적되며 나타나므로, 조기 신호를 찾아 개선 우선순위를 정할 기준이 필요함.

## Ⅱ. 특징

- 버그가 아니라 구조 악화 신호라는 점이 핵심임
- 여러 스멜이 함께 나타날수록 변경 비용과 결합 위험이 커짐
- 정적 분석과 코드 리뷰로 비교적 일찍 발견할 수 있음
- 모든 스멜을 즉시 고칠 필요는 없고 변경 맥락을 함께 봐야 함

## Ⅲ. 종류 및 비교

| 구분 | 코드 스멜 | 실제 버그 |
|:---|:---|:---|
| 성격 | 미래 유지보수 위험을 알려 주는 구조 신호임 | 현재 기능 오동작을 만드는 결함임 |
| 발견 방식 | 리뷰·정적 분석에서 중복·복잡도·책임 집중 확인 | 테스트 실패·운영 장애에서 실제 기능 오류 확인 |
| 대응 방식 | 변경 위험을 평가해 리팩터링하고 외부 동작 유지 | 결함 원인을 수정하고 회귀 테스트 수행 |
| 주된 영향 | 이후 변경 비용과 이해 비용을 높임 | 현재 기능 실패와 사용자 피해를 만듦 |

> 요약: 코드 스멜은 고쳐야 할 코드 목록이 아니라 미래 변경 비용이 높아질 지점을 알려 주는 경고 신호임.

## Ⅳ. 구성요소 및 구조

| 구성요소 | 설명 |
|:---|:---|
| 구조 스멜 | 긴 메서드와 큰 클래스와 중복 코드처럼 구조 비대화를 드러냄 |
| 의존성 스멜 | 순환 의존과 과도한 결합처럼 변경 파급을 키우는 냄새를 보여줌 |
| 이름과 가독성 스멜 | 의미가 불명확한 이름과 숨은 의도가 코드 이해 비용을 높임 |
| 변경 집중 영역 | 자주 바뀌는 영역에 존재하는 스멜일수록 우선순위가 더 높아짐 |

## Ⅴ. 원리 및 절차 흐름도

```text
+-------------+     +-------------+     +-------------+     +-------------+
| 스멜 탐지      | --> | 영향도 평가    | --> | 리팩터링 선택  | --> | 회귀 검증      |
+-------------+     +-------------+     +-------------+     +-------------+
```

1. **스멜 탐지**: 정적 분석과 코드 리뷰로 냄새를 찾음
2. **영향도 평가**: 변경 빈도와 결합도와 위험도를 확인함
3. **리팩터링 선택**: 적절한 개선 방법을 정함
4. **회귀 검증**: 테스트로 동작 보존을 확인함

## Ⅵ. 실무 적용 및 유의점

1. 레거시 서비스처럼 변경이 잦은 영역에서는 코드 스멜을 방치하면 기능 개발이 더 느려지므로 변경 빈도가 높은 모듈부터 정리하고 스멜 집중 영역 비율과 기능 반영 시간으로 확인함
2. 리뷰어마다 스멜 판단이 달라 논쟁이 생기는 팀에서는 공통 예시와 기준을 먼저 맞추고 리뷰 판단 일치도와 같은 스멜 재발 비율로 확인함

## Ⅶ. 결론

코드 스멜은 버그와 달리 미래 위험을 예고하므로 변경이 잦은 영역부터 구조 개선 우선순위를 정하는 데 써야 함.
