## 핵심 인사이트 (3줄 요약)
- 아직 에러가 나거나 버그가 발생한 것은 아니지만, **"뭔가 설계가 잘못되었음을 직관적으로 알려주는 코드의 나쁜 냄새(징후)"**.
- 마틴 파울러의 책 『리팩토링』에서 켄트 벡이 창안한 용어로, 거대한 클래스, 긴 메서드, 중복된 코드 등이 대표적인 냄새임.
- 코드 스멜은 리팩토링을 '언제, 어디서부터 시작해야 하는지' 알려주는 나침반 역할을 하며, 최근에는 SonarQube 등 정적 분석 도구가 이를 기계적으로 탐지함.
---
## Ⅰ. 개요 및 필요성
- **개요**: 컴퓨터는 컴파일을 통과하면 기계어로 읽어내지만, 인간(유지보수자)이 읽기에는 고통스러운 구조적 결함의 징후.
- **필요성**: 기술 부채를 갚아야 한다는 것은 알지만, 수십만 줄의 코드에서 어디를 리팩토링해야 할지 막막할 때가 많음. 객체지향 원칙(SOLID)을 위반한 패턴들을 카테고리화하여, "이런 형태가 보이면 즉시 수정해라"라는 명확한 가이드를 제공하기 위함.
---
## Ⅱ. 아키텍처 및 핵심 원리
- **대표적인 코드 스멜 유형 (Bloaters: 비대해진 코드)**:
  1. **긴 메서드 (Long Method)**: 한 메서드가 수십~수백 줄에 달해 도대체 무슨 역할을 하는지 파악 불가 (해결: `Extract Method`).
  2. **거대한 클래스 (Large Class)**: 너무 많은 필드와 메서드를 가져 단일 책임 원칙(SRP)을 위반함 (해결: `Extract Class`).
  3. **긴 매개변수 목록 (Long Parameter List)**: 함수를 호출할 때 인자가 5~6개를 넘어감 (해결: 매개변수들을 하나의 객체로 묶어 전달).
- **객체지향 남용 유형 (Object-Orientation Abusers)**:
  1. **Switch 문 (Switch Statements)**: 동일한 조건의 Switch문이 코드 여기저기 산재해 있음 (해결: 다형성(Polymorphism)으로 대체).
- **변화 방해 유형 (Change Preventers)**:
  1. **산탄총 수술 (Shotgun Surgery)**: 기능 하나를 수정하려고 5개의 서로 다른 클래스를 조금씩 다 수정해야 함 (응집도 부족).
  2. **뒤엉킨 변경 (Divergent Change)**: 하나의 클래스 안에서 3가지 서로 다른 이유로 코드가 수정됨.

```text
[ 코드 스멜의 발견과 리팩토링 과정 ]

 [ Bad Code ]                        [ Refactoring ]                   [ Clean Code ]
 public void doAll() {               +---------------+
   // 1. DB 연결 (20줄)  <-- (냄새!)--> | Extract Method | --------> public void connectDB()
   // 2. 데이터 파싱 (30줄) <--(냄새!)--> | Extract Method | --------> public void parseData()
   // 3. 파일 저장 (20줄)  <-- (냄새!)--> | Extract Method | --------> public void saveFile()
 }                                   +---------------+
```

## Ⅲ. 비교 및 연결
| 구분 | 버그 (Bug / Defect) | 코드 스멜 (Code Smell) |
|---|---|---|
| **정의** | 명세대로 동작하지 않는 **기능적 치명타** | 돌아는 가지만 설계가 지저분한 **구조적 결함** |
| **영향도** | 당장 시스템이 멈추거나 잘못된 결과를 냄 | 당장은 잘 돌아감 (미래의 유지보수자를 괴롭힘) |
| **발견 방법**| 테스트 코드(TDD), QA, 사용자 제보 | 코드 리뷰(PR), SonarQube 등 정적 분석 |
| **해결 방법**| 디버깅 후 패치 (Hotfix) | 리팩토링 기법 적용 (구조 개선) |
---
## Ⅳ. 실무 적용 및 기술사 판단
- **SonarQube를 통한 자동화 제어**: 실무에서 개발자의 주관적인 '감'으로 냄새를 맡는 것은 한계가 있음. CI 파이프라인에 SonarQube를 연동하여, 새롭게 추가된 코드(New Code)에 코드 스멜이 X개 이상 발생하면 아예 Main 브랜치로의 Merge(병합)를 차단(Quality Gate Fail)하는 강제 거버넌스가 가장 효과적임.
- **주석(Comments)도 냄새다**: "주석은 나쁜 코드를 변명하기 위해 존재한다(로버트 C. 마틴)". 코드가 너무 더러워서 주석을 장황하게 달고 싶어진다면, 그것은 주석을 쓸 때가 아니라 메서드 이름을 명확하게 바꾸거나(Rename) 함수를 추출(Extract)해야 하는 가장 강력한 코드 스멜임.
---
## Ⅴ. 기대효과 및 결론
- 코드 스멜을 식별하는 능력은 '초급 코더'와 '시니어 소프트웨어 엔지니어'를 가르는 가장 결정적인 기준임.
- 악취가 나는 코드를 방치하면 '깨진 유리창 법칙'에 의해 전체 시스템이 빠르게 부패하므로, 악취가 감지되는 즉시 닦아내는 '클린 코드(Clean Code)' 문화가 조직을 살림.

### 👶 어린이를 위한 3줄 비유 설명
1. 냉장고를 열었는데 아직 썩은 음식(버그)은 없지만, 어딘가 시큼한 냄새(코드 스멜)가 날 때가 있죠?
2. 당장 먹고 배탈이 나지는 않겠지만, 냄새나는 반찬통을 그대로 방치하면 며칠 뒤에 냉장고 전체가 썩어버릴 거예요.
3. 코드 스멜은 개발자에게 "빨리 냉장고를 청소(리팩토링)해서 반찬통을 예쁘게 정리해!"라고 알려주는 훌륭한 알람이랍니다!
