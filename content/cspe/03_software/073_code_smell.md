# 📖 【암기용】 개념 완전 이해

> 목적: 코드 스멜을 처음 봐도 결함 자체가 아니라 리팩터링 신호라는 관점에서 이해하게 만든다. 시험 답안 양식이 아니라, 이해를 위한 설명이다.

## 한눈에
- **개요**: 코드 스멜은 동작은 가능하지만 구조상 변경 비용과 결함 가능성을 높이는 징후임
- **왜 필요한가**: 결함이 터진 뒤 고치는 방식은 원인 구조를 방치함. 스멜을 조기에 찾으면 리팩터링 대상과 우선순위를 정할 수 있음.
- **핵심 직관**: 냄새가 난다고 불이 난 것은 아니지만, 전기 과열·누수처럼 점검해야 할 신호를 주는 상태임.

## 깊이 이해
- **배경·문제의식**: 기능 추가가 누적되면 긴 메서드, 거대 클래스, 중복 코드, 흩어진 수정 지점이 생김. 이런 구조는 작은 요구 변경에도 여러 파일을 동시에 건드리게 함.
- **작동 원리**: 코드 스멜은 정적 분석, 리뷰, 변경 이력으로 탐지함. 탐지 후 Extract Method, Move Method, Replace Conditional with Polymorphism 같은 리팩터링을 적용함.
- **비유**: 건물 벽의 균열은 즉시 붕괴를 뜻하지 않지만, 균열 위치와 크기를 기록해 보강 공사를 결정하는 근거가 됨.
- **구체 예시**: 900라인 `OrderService`가 주문, 결제, 재고, 알림을 모두 처리하면 god class 스멜임. 변경 1건에 8개 테스트가 깨지면 분리 우선순위가 높음.
- **흔한 오해·주의점**: 스멜은 버그와 다름. 동작 오류가 없어도 변경 빈도와 복잡도가 높은 스멜은 기술부채 이자를 만든다.

## 연결 개념
- Refactoring — 스멜을 제거하는 구조 개선 기법
- Technical Debt — 스멜이 누적되어 미래 변경 비용으로 전가된 상태
- Static Analysis — 스멜을 자동 탐지하는 도구 기반 접근

# 📝 【답안용】 시험 답안 템플릿

> 목적: 시험장에서 25분에 그대로 쓰는 답안 양식. 작성방식(추상표현 금지·수치·도식·문제유형 전환)을 엄격히 지킨다.
> 핵심: 코드 스멜은 버그 목록이 아니라 변경 비용과 설계 침식의 조기 신호이며, 리팩터링 우선순위 선별 입력이다.

## 핵심 인사이트 (3줄 요약)

> 1. **본질**: 코드 스멜은 기능 동작은 유지되지만 구조·응집도·결합도 측면에서 유지보수 위험을 나타내는 코드 징후이다.
> 2. **가치**: Long Method, God Class, Duplicated Code, Shotgun Surgery를 탐지해 결함 발생 전 리팩터링 대상을 선별함.
> 3. **판단 포인트**: 스멜 제거는 냄새 개수보다 변경 빈도, 장애 영향도, 테스트 안전망 기준으로 우선순위를 정해야 함.

## 출제 의도 및 답안 포인트

| 출제 의도 | 반드시 짚을 핵심 | 감점 회피 포인트 |
|:---|:---|:---|
| 코드 품질 징후 이해 확인 | long method, god class, duplicated code, shotgun surgery | 스멜을 결함 또는 보안 취약점과 동일시 |
| 리팩터링 연계 확인 | smell -> refactoring trigger -> regression test | 탐지만 쓰고 제거 기법 누락 |
| 품질 지표 판단 확인 | complexity, coupling, churn, coverage | 냄새 개수만으로 우선순위 결정 |

> 요약: 이 문제는 코드 스멜 유형 나열보다 구조 리스크를 리팩터링 의사결정으로 연결하는 답안을 요구한다.

---

## Ⅰ. 개요 및 필요성

- 개요: 리팩터링 필요 징후
- 배경: 기능 추가가 반복되면 Long Method, Duplicate Code, God Class처럼 응집도 저하와 결합도 증가를 드러내는 구조 징후가 누적된다.
- 필요성: SonarQube, 정적 분석, 코드 리뷰로 스멜을 식별해 변경 리드타임, 회귀 결함, 리뷰 비용 증가 구간을 선제 관리한다.

---

## Ⅱ. 구조 및 구성요소

```text
Source Code -> Static Analysis / Review / Churn Data
  -> Smell Catalog -> Severity Scoring
  -> Refactoring Candidate -> Regression Test -> Quality Gate
```

| 구성요소 | 역할 | 특이사항 |
|:---|:---|:---|
| Long Method | 하나의 메서드가 과도한 책임 수행 | 50~100라인 초과 시 점검 |
| God Class | 클래스 하나가 다수 책임을 집중 | LCOM, fan-in/fan-out 확인 |
| Duplicated Code | 동일 로직이 여러 위치에 반복 | duplication 5% 초과 시 개선 후보 |
| Shotgun Surgery | 변경 1건이 여러 파일에 분산 | churn과 변경 파일 수로 탐지 |
| Data Clumps | 여러 매개변수가 반복 동행 | Value Object 추출 후보 |

> 요약: 코드 스멜은 구조 징후별로 탐지 기준과 대응 리팩터링 기법이 연결되어야 한다.

---

## Ⅲ. 동작원리 및 흐름도

```text
Commit / Review -> Smell Detection -> Severity Score
  -> Test Safety Check -> Refactoring Select
  -> PR Gate -> Metric Trend Update
```

| 단계 | 처리 내용 | 검증 기준 |
|:---:|:---|:---|
| 1 | 정적 분석과 코드 리뷰로 스멜 탐지 | critical smell 0건, major trend 확인 |
| 2 | 변경 빈도와 장애 영향도를 점수화 | churn 상위 20%, incident 연계 |
| 3 | 대응 리팩터링 기법 선정 | Extract Method, Extract Class |
| 4 | 테스트 실행 후 외부 동작 보존 확인 | 단위·회귀 테스트 pass 100% |
| 5 | 품질 게이트와 추세 리포트 갱신 | complexity, duplication 감소 |

> 요약: 코드 스멜 관리는 탐지, 위험 점수화, 리팩터링, 회귀 검증, 품질 추세 갱신 순서로 수행된다.

## Ⅳ. 특징

| 구분 | 결함 관리 | 코드 스멜 관리 | 정량 기준 |
|:---|:---|:---|:---|
| 대상 | 실행 오류 | 구조적 징후 | complexity, coupling |
| 시점 | 장애·테스트 실패 후 | 개발·리뷰·CI 중 | PR gate, nightly scan |

> 요약: 코드 스멜 관리는 실행 오류가 아니라 미래 변경 비용을 줄이기 위한 구조 리스크 관리이다.

## Ⅴ. 심화 비교 및 적용 판단

| 비교 축 | 기존/대안 | 본 키워드 | 선택 기준 |
|:---|:---|:---|:---|
| 구조 | 리뷰어 경험 의존 | 카탈로그·지표 기반 탐지 | 팀 규모 5명 이상이면 표준화 |
| 비용/성능 | 결함 후 수정 | 사전 리팩터링 | 변경 리드타임 증가 시 적용 |
| 운영/위험 | 스멜 방치 | PR gate 통제 | critical smell 병합 차단 |
| 품질 | 기능 테스트 중심 | 구조 지표 병행 | coverage 70% 이상 확보 |

> 요약: 코드 스멜은 변경 빈도와 품질 지표가 나쁜 모듈부터 관리할 때 리팩터링 효과를 검증할 수 있다.

| 리스크 | 원인 | 대응 방안 | 확인 지표 |
|:---|:---|:---|:---|
| 과잉 리팩터링 | 낮은 위험 스멜까지 제거 | churn·incident 기반 우선순위 | 상위 20% 모듈 집중도 |
| 회귀 결함 | 테스트 없이 구조 변경 | characterization test 작성 | 회귀 결함 0건 |
| 도구 오탐 | 언어·프레임워크 맥락 미반영 | rule tuning, suppress 사유 기록 | false positive 비율 |
| 리뷰 피로 | 경고 과다 | critical/major 기준 분리 | PR 차단 항목 수 |

> 요약: 스멜 관리는 도구 경고를 그대로 따르지 말고 위험 점수와 테스트 안전망으로 통제해야 한다.

| 점검 항목 | 목표 기준 | 측정 방법 |
|:---|:---|:---|
| 복잡도 | cyclomatic complexity 10~15 이하 | 정적 분석 |
| 중복 | duplicated lines 5% 이하 | SonarQube, PMD CPD |
| 결합도 | fan-out 임계값 초과 0건 | 아키텍처 분석 |
| 유지보수 | PR lead time 30% 감소 | Git, Jira, DORA |

> 요약: 코드 스멜 개선 성과는 복잡도, 중복률, 결합도, PR 리드타임으로 확인한다.

## Ⅵ. 실무 적용 및 결론

**적용 방안 3개 (필수 — 단계별 또는 항목별):**
1. SonarQube·ESLint·PMD 규칙을 PR gate에 연결하고 blocker/critical 스멜은 병합 차단, major는 스프린트 백로그로 이관함.
2. Long Method는 Extract Method, God Class는 Extract Class, Duplicated Code는 Template Method 또는 공통 모듈 추출로 대응함.
3. 변경 빈도 상위 20% 파일에 대해 complexity 15 초과, duplication 5% 초과, coverage 70% 미만 조건을 리팩터링 우선순위로 사용함.

**결론 (2줄):**
- 기술사 판단: 코드 스멜은 결함이 아니라 리팩터링 신호이므로 변경 빈도·장애 영향도·테스트 보유 여부를 함께 보고 제거 순서를 정함.
- 향후 방향: 코드 스멜 관리는 AI code review, 정적 분석, ADR, DORA 지표와 결합한 지속적 설계 관리로 확장됨.
