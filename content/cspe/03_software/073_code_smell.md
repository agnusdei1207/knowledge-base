# 📖 【암기용】 개념 완전 이해

## 한눈에
- **개요**: 소스 코드에서 심각한 문제(버그 등)를 일으킬 가능성이 높은, 이해하기 어렵거나 유지보수가 힘든 구조적 징후
- **왜 필요한가**: 리팩터링을 해야 하는 정확한 위치와 시점을 알려주는 경고등 역할을 함
- **핵심 직관**: 상한 음식에서 나는 '냄새' (당장 먹고 죽진 않지만 곧 탈이 남)

## 핵심 용어 정리

| 용어/표기 | 의미 | 비유·예 |
|:---|:---|:---|
| 코드 스멜 (Code Smell) | 코드 안의 설계적 결함 징후 | 벽에 생긴 미세한 금 |
| 더플리케이트 코드 (Duplicated Code) | 여러 곳에 복사-붙여넣기 된 똑같은 로직 | 복제 인간 |
| 롱 메서드 (Long Method) | 수백 줄에 달하는 너무 긴 함수 | 500페이지짜리 원패스 메뉴얼 |

## 깊이 이해
- **배경·문제의식**: 개발 일정 압박 등으로 인해 '일단 돌아만 가는' 코드를 짜게 됨. 당장 버그는 없지만, 코드가 읽기 어렵고 한 번 고칠 때 수십 곳을 함께 고쳐야 하는 상황이 벌어짐.
- **작동 원리**: 코드 스멜 자체는 컴파일 에러를 내지 않음. 하지만 유지보수성을 극도로 떨어뜨려 기술부채를 가중시킴. 이를 정적 분석이나 코드 리뷰로 찾아내어 리팩터링으로 제거함.
- **비유**: 방 정리를 안 해서 물건이 산더미처럼 쌓인 방. 방을 쓰는 데는 문제없지만, 찾고 싶은 물건을 찾는 데 하루 종일 걸림.
- **구체 예시**: `switch-case` 문이 10개가 넘고 매번 분기가 추가되는 'Switch Statements' 스멜. 이는 객체지향의 다형성(Polymorphism)으로 리팩터링하여 해결해야 함.
- **흔한 오해·주의점**: 코드 스멜은 그 자체로 '버그(Bug)'가 아님. 동작은 정상이지만, 설계 원칙(SOLID 등)을 위반하여 미래에 버그를 양산할 징후에 불과함.

## 연결 개념
- **리팩터링, 클린 코드, 정적 분석(SAST), 기술부채**

# 📝 【답안용】 시험 답안 템플릿

## 핵심 인사이트 (3줄 요약)

> 1. **본질**: 시스템 내부에 잠재된 설계 결함 및 유지보수성 저하의 징후
> 2. **가치**: 리팩터링 대상 식별 기준 제공, 소프트웨어 엔트로피 사전 차단
> 3. **판단 포인트**: 정적 분석 자동화를 통해 스멜을 조기에 탐지하고 지속적 리팩터링과 연계해야 함

## 출제 의도 및 답안 포인트

| 출제 의도 | 반드시 짚을 핵심 | 감점 회피 포인트 |
|:---|:---|:---|
| 결함 징후 식별 및 개선 역량 | 징후(스멜)와 해결책(리팩터링 기법) 매핑 | 스멜을 단순 문법 에러로 설명 단정 |
| 코드 품질 지표 이해 | 주요 스멜 유형 (중복 코드, 긴 메서드 등) | 원인 없이 종류만 단순 나열 |

> 요약: 코드 스멜은 버그가 아닌 설계 결함의 징후이므로 적절한 리팩터링 패턴 매핑이 필수임

---

## Ⅰ. 개요 및 필요성

- 개요: 코드 스멜은 정상적으로 동작하나 가독성·확장성을 저해하여 향후 치명적 오류를 유발할 수 있는 소스 코드 내의 구조적 결함 징후임
- 배경: 비즈니스 요구의 잦은 변경과 땜질식(Quick & Dirty) 개발로 인해 소프트웨어 설계가 지속적으로 부식됨
- 필요성: 기술부채가 통제 불능 상태로 빠지기 전에 리팩터링의 정확한 타겟팅 및 리스크 조기 식별 필요

---

## Ⅱ. 구조 및 구성요소 (코드 스멜의 발생 구조)

```text
[요구사항 변경] -> [임시방편 코딩] -> [코드 스멜 생성] -> [응집도↓/결합도↑] -> [유지보수 불능]
                                       |
                                       +-> 중복, 방대함, 과도한 결합 등
```

| 구성요소 (스멜 분류) | 역할 및 징후 | 특이사항 |
|:---|:---|:---|
| Bloaters (거대화) | 클래스나 메서드가 비대해져 관리가 불가한 상태 | Long Method, Large Class |
| Object-Orientation Abusers | 객체지향 원칙(다형성 등)을 불완전하게 적용한 상태 | Switch Statements |
| Change Preventers | 하나를 수정할 때 연쇄적인 수정을 강제하는 상태 | Shotgun Surgery |
| Dispensables (불필요) | 의미 없는 주석, 죽은 코드 등 제거해도 무방한 요소 | Dead Code, Data Class |

> 요약: 발생 원인에 따라 클래스 비대화, 변경 방해, 불필요 코드 등으로 분류되며 유지보수성을 저하함

---

## Ⅲ. 동작원리 및 흐름도 (스멜 탐지 및 제거 절차)

```text
소스코드 분석 -> 코드 스멜 유형 식별 -> 리팩터링 기법 매핑 -> 코드 변환 -> 품질 지표 개선 확인
```

- 1단계 [소스 분석]: CI/CD 파이프라인에서 정적 분석(SonarQube 등) 도구를 통해 복잡도, 중복도 스캔
- 2단계 [스멜 식별]: '중복 코드', '파라미터 과다' 등 패턴 기반으로 경고 알림 및 부채 지수 산정
- 3단계 [기법 매핑]: 스멜 유형에 맞는 마틴 파울러의 리팩터링 기법(Extract Method, Rename 등) 선정
- 4단계 [변환·확인]: 회귀 테스트 안전망 내에서 코드를 수정하고, 복잡도(Cyclomatic) 하락 여부 확인

> 요약: 자동화 도구로 징후를 식별하고 정형화된 리팩터링 기법을 적용하여 품질을 복원함

---

## Ⅳ. 특징

- 사전 징후성: 현재 시스템 동작에는 영향을 주지 않지만, 잠재적인 결함과 유지보수 비용 증가를 예고함
- 객관적 측정 한계: 일부 스멜은 정량적 도구로 탐지 가능(길이, 중복률)하나, 명명 규칙 등은 주관적 판단(코드 리뷰)이 필요함
- 기법 매핑: 각각의 스멜은 그에 대응하는 구체적인 리팩터링 해결책(Solution Pattern)을 명확히 가짐
- 엔트로피 가속: 방치할 경우 '깨진 유리창 법칙'에 따라 다른 개발자들도 나쁜 코드를 모방하여 품질 저하가 가속화됨

> 요약: 당장의 버그는 아니나 시스템 부식을 예고하므로 대응되는 리팩터링 패턴 적용이 필수적임

---

## Ⅴ. 심화 비교 및 적용 판단

| 비교 축 | 코드 스멜 (Code Smell) | 소프트웨어 버그 (Bug) | 판단 기준 |
|:---|:---|:---|:---|
| 정상 동작 여부 | 100% 정상 동작함 | 오동작 또는 비정상 종료됨 | 테스트 통과 여부 |
| 발견 방식 | 정적 분석, 코드 리뷰 | 런타임 에러, 동적 테스트 | 탐지 도구 |
| 조치 방법 | 리팩터링 (내부 구조 변경) | 디버깅 및 패치 (로직 변경) | 외부 동작 변경 유무 |

> 요약: 스멜은 미래의 위험(설계 결함)을, 버그는 현재의 장애(동작 결함)를 의미하므로 조치 방법이 다름

**리스크·대응:**
- 맹목적 제거에 따른 일정 지연: 모든 스멜을 제거하려다 릴리스 일정 차질 → 임계치(Complexity > 15 등) 초과 항목만 선별적 처리 (지표: 처리 우선순위 룰셋)
- 기능 훼손: 스멜 제거 과정에서 기존 로직 파괴 → 수정 전 단위 테스트 커버리지 80% 이상 확보 강제 (지표: 테스트 성공률)

---

## Ⅵ. 실무 적용 및 결론

**적용 방안 (스멜과 리팩터링 매핑):**
1. Duplicated Code (중복 코드): 여러 모듈에 산재된 동일 로직을 식별하고, `Extract Method`로 별도 함수화하여 단일 진실 공급원(SSOT) 확보
2. Long Method (거대 메서드): 줄 수가 과도하게 긴 함수를 의미 단위로 분리하고, 주석 없이도 이해 가능하도록 명확한 이름 부여
3. Shotgun Surgery (산탄총 수술): 하나의 변경이 여러 클래스 수정으로 이어지는 경우, `Move Method`로 관련 책임을 한 곳으로 응집

**결론:**
- 기술사 판단: 코드 스멜은 개발 속도와 품질 간 타협의 산물이므로, 이를 죄악시하기보다 정량적으로 가시화하고 지속적 상환 체계를 만드는 것이 중요함
- 향후 방향: AI 코딩 어시스턴트가 IDE 내에서 실시간으로 스멜을 탐지하고, 원클릭 리팩터링을 제안하는 Shift-Left 품질 관리로 진화하고 있음
