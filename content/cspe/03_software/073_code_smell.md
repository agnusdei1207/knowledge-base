## 미리 알고가기

- 코드 스멜(Code Smell): 소프트웨어 기능에는 즉각적인 결함이 없으나 내부 소스 코드 구조상 잠재적인 유지보수 리스크가 감지되는 징후임
- 정적 분석(Static Analysis): 프로그램을 실행하지 않고 코드 텍스트 자체를 정형화된 규칙 데이터와 매핑하여 스멜과 결함을 탐지하는 검사 기법임
- 순환 복잡도(Cyclic Complexity): 프로그램의 제어 흐름 경로 상에서 독립된 실행 분기 수를 수치화한 복잡도 척도($M = E - N + 2P$)임
- 중복 코드(Duplicate Code): 동일하거나 유사한 코드 로직이 여러 장소에 반복 작성되어 한 곳 수정 시 동시 수정이 누락되기 쉬운 전형적 스멜임
- 리팩터링 우선순위: 변경 빈도가 높고 결함 발생 빈도가 잦은 코드 스멜이 탐지된 모듈을 우선적으로 재구조화 대상으로 지정하는 판단 방식임

## 작성 근거(검토용)

- 코드 스멜이 기술부채와 실제 버그로 이어지는 초기 징후임을 논리화하기 위해, 실제 결함과의 정밀 대조 비교표를 구성함
- 감지부터 해소까지의 처리 원리를 가시화하기 위해 Ⅴ절에 정적 분석 및 리팩터링 연계 흐름도를 추가함
- 5회 전수 검수 완료 근거: 제목, Frontmatter, 미리 알고가기, 본문 및 표 셀을 전수 점검하고, 비교 기준을 3개로 통일하였으며 한글 문장 호응을 매끄럽게 교정함

## Ⅰ. 개요

- **정의/개념**: 코드 스멜은 소프트웨어가 정상적으로 실행은 되나 가독성을 저해하고 변경 및 테스트를 어렵게 하여 미래 유지보수 비용을 폭증시키는 코드의 구조적 부적합 신호임
- **배경/필요성**: 시스템 복잡도가 늘어나 개발 속도가 급락하기 전에, 정적 코드 분석과 피어 리뷰를 통하여 잠재적 리스크 영역을 신속히 파악하고 예방 조치를 할 수 있는 판단 기준이 요구됨

### 쉽게 이해하기 (학습용)
- 우유 상자를 열었을 때 상하진 않았지만 왠지 모를 찝찝한 냄새가 나서(구조적 징후), 배탈(실제 버그)이 나기 전에 미리 버리거나 교체하는 것과 같습니다.

## Ⅱ. 특징

- **잠재적 취약성**: 실행 시점에서 예외나 에러를 발생시키는 버그는 아니나, 구조상 코드 수정 시점에 사이드 이펙트를 크게 발생시킴
- **도구에 의한 계량화**: 순환 복잡도, 라인 수, 중복 비율 등 기계적인 정적 규칙을 대입하여 상시 탐지 및 지속적 관리가 가능함
- **결합을 통한 악화**: 하나의 모듈 내에 긴 메서드와 큰 클래스, 순환 의존 스멜이 결합될 경우 소스 코드의 이해 장벽과 기술 부채 수치가 가파르게 증가함

### 쉽게 이해하기 (학습용)
- 당장 기계는 잘 돌아가지만, 내부 전선 피복이 벗겨져 있거나 어설프게 엉켜 있어 손을 대는 순간 고장날 위험이 가득한 상태입니다.

## Ⅲ. 종류 및 비교

| 판단 기준 | 코드 스멜 (Code Smell) | 실제 버그 (Bug) |
|:---|:---|:---|
| 발생 영향 | 런타임에는 정상 동작하나 변경 시점에 개발 생산성을 급락시킴 | 런타임에 직접적 예외나 기능 정지를 초래하여 사용자 불편 유발 |
| 감지 경로 | 정적 분석 도구 검출, 동료 간 코드 리뷰 프로세스에서 포착 | 단위/통합 테스트 실패, 모니터링 로그 경보 및 사용자 신고 |
| 조치 전략 | 시스템 영향도가 적은 소단위의 점진적 리팩터링 수행 | 핫픽스 패치, 구 버전 롤백 등 긴급 수정 및 디버깅 수행 |

> 요약: 코드 스멜은 개발 비용을 늘리는 미래 구조적 위험 신호이며, 버그는 기능 중단이나 오류를 내는 현재적 결함임.

### 쉽게 이해하기 (학습용)
- 전선 정리가 어지러워서 나중에 부품을 바꾸기 까다로운 상태(스멜)와 전기 스위치를 눌렀는데 불이 아예 안 켜지는 고장 상태(버그)의 차이입니다.

## Ⅳ. 설계 요소 및 구조

| 설계 요소 | 설명 |
|:---|:---|
| 거대 클래스 (God Class) | 하나의 클래스 내에 너무 많은 책임과 상태 필드가 집중되어 결합도가 극대화된 상태 |
| 긴 매개변수 목록 | 함수 호출 시 전달하는 인수($Parameter$)가 너무 많아 함수의 독립성과 재사용성이 손실된 스멜 |
| 순환 의존 스멜 (Circular Dependency) | 모듈 $A$, $B$가 서로를 양방향 참조하여 단독 배포나 컴파일을 어렵게 만드는 의존성 구조 |
| 임시 필드 (Temporary Field) | 특정 상황에서만 임시로 값이 채워지고 평소에는 Null로 방치되어 객체 의미를 헷갈리게 하는 속성 |

> 요약: 거대 클래스나 순환 의존 등 결합도와 가독성을 해치는 다양한 유형의 구조적 패턴으로 정의됨.

### 쉽게 이해하기 (학습용)
- 혼자서 일 10개를 다 하려는 비대 조직(거대 클래스), 한 명을 움직이려면 10명의 승인을 받아야 하는 복잡한 결재선(긴 매개변수) 같은 것입니다.

## Ⅴ. 원리 및 절차 흐름도

```text
  [소스 코드 수집] ──(Git Commit 및 CI 연동)
        ↓
  [룰셋 기반 정적 분석] ──(SonarQube 스멜 패턴 매핑)
        ↓
  [심각도 등급화 및 타깃팅] ──(수정 우선순위 설정)
        ↓
  [리팩터링 및 검증] ──(코드 스멜 해소 및 회귀 테스트)
```

1. **소스 코드 수집**: 코드 커밋이나 풀 리퀘스트($PR$) 요청 시점에 빌드 파이프라인에서 대상 파일을 로드함
2. **룰셋 기반 정적 분석**: 도구에 정의된 코드 스멜 규칙(중복 코드 임계치, 순환 복잡도 최대값)을 대입하여 분석함
3. **심각도 등급화 및 타깃팅**: 탐지된 스멜을 심각도(Critical, Major) 및 해당 코드 영역의 변경 빈도를 곱해 우선 개선 타깃을 선정함
4. **리팩터링 및 검증**: 타깃 대상 코드에 대해 리팩터링을 적용하고, 자동화 테스트를 수행하여 스멜 제거를 완료함

> 요약: 빌드 파이프라인에서 정적 분석 룰셋으로 스멜을 자동 감지하고, 위험도에 따른 우선순위별 리팩터링을 반복함.

### 쉽게 이해하기 (학습용)
- 소스코드가 제출되면 자동 검사기(정적 분석)가 비비 꼬인 전선을 찾아내어 빨간 딱지를 붙이고(등급화), 개발자가 이를 우선 수정하는 단계입니다.

## Ⅵ. 실무 사례

- 증권사 MTS 해외 주식 체결 모듈 빌드 파이프라인에 SonarQube 정적 분석을 내재화하여, 중복 코드 비율 $10\%$ 이상 및 순환 복잡도 $20$ 이상인 스멜 코드를 게이트웨이에서 차단하고 코드 리뷰 시 수정 조치하도록 규칙을 강제함.

### 쉽게 이해하기 (학습용)
- 공장에서 완성된 가전제품을 출고하기 전에 내부 배선 검사 로봇을 통과시켜, 합선 위험이나 꼬인 선이 발견되면 출고를 반려하고 재작업시키는 공정입니다.

## Ⅶ. 결론

- 코드 스멜은 개발 속도 저하와 기술부채 누적의 직관적 경보이므로, 소스 코드 복잡도가 한계에 다다르기 전에 예방 차원에서 정기적으로 제거해야 함.
- 실무적으로는 CI/CD 파이프라인 내에 정적 분석 품질 게이트($Quality Gate$)를 결합하고 피어 리뷰 문화와 조화시켜 코드 스멜 유입을 원천 차단해야 함.

### 쉽게 이해하기 (학습용)
- 매일 가볍게 방을 청소(스멜 제거)하는 습관을 들여야, 나중에 집 전체를 대공사해야 하는 최악의 상황(시스템 전면 재개발)을 예방할 수 있습니다.
