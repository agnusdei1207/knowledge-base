## 미리 알고가기

- 코드 스멜은 즉시 버그는 아니지만 유지보수 문제를 예고하는 신호임
- 긴 메서드와 중복 코드와 큰 클래스가 대표 예시임
- 스멜은 리팩터링 우선순위 판단 단서로 봐야 함

## Ⅰ. 개요

- **정의/개념**: 코드 스멜은 코드가 당장 오동작하지 않더라도 가독성과 변경 용이성과 테스트 가능성을 해치는 설계 냄새로서 향후 결함과 기술부채로 이어질 가능성을 알려주는 징후임
- **배경/필요성**: 유지보수 문제는 갑자기 생기기보다 작은 구조 악화가 누적되며 나타나므로, 조기 신호를 찾아 개선할 기준이 필요함

## Ⅱ. 특징

- 버그가 아니라 구조 악화 신호라는 점이 핵심임
- 단일 냄새보다 여러 스멜이 함께 나타날 때 위험이 커짐
- 정적 분석과 리뷰로 비교적 일찍 발견 가능함
- 모든 스멜이 즉시 수정 대상은 아니며 변경 맥락을 봐야 함

## Ⅲ. 종류 및 비교

| 판단 기준 | 코드 스멜 | 실제 버그 |
|:---|:---|:---|
| 성격 | 유지보수 위험 신호 | 명백한 오동작 |
| 발견 방식 | 리뷰와 정적 분석 | 테스트와 운영 장애 |
| 대응 | 리팩터링 우선순위화 | 즉시 수정 |
| 영향 | 미래 변경 비용 증가 | 현재 기능 실패 |

## Ⅳ. 구성요소 및 구조

| 구성요소 | 설명 |
|:---|:---|
| Structural Smell | 긴 메서드와 큰 클래스와 중복 코드처럼 구조 비대화를 드러냄 |
| Dependency Smell | 순환 의존과 과도한 결합처럼 변경 파급을 키우는 냄새를 보여줌 |
| Naming and Clarity Smell | 의미 불명 이름과 숨은 의도는 코드 이해 비용을 높이는 신호임 |
| Hotspot Context | 자주 바뀌는 영역에 존재하는 스멜일수록 우선순위가 더 높아짐 |

## Ⅴ. 원리 및 절차 흐름도

```text
+-------------+     +-------------+     +-------------+     +-------------+
| 스멜 탐지      | --> | 영향도 평가    | --> | 리팩터링 선택  | --> | 회귀 검증      |
+-------------+     +-------------+     +-------------+     +-------------+
```

1. **스멜 탐지**: 정적 분석과 코드 리뷰로 냄새를 찾음
2. **영향도 평가**: 변경 빈도와 결합도와 위험도를 확인함
3. **리팩터링 선택**: 적절한 개선 패턴을 정함
4. **회귀 검증**: 테스트로 동작 보존을 확인함

## Ⅵ. 문제점 및 해결 방안

1. 문제: 스멜을 버그처럼 모두 즉시 수정하려 하면 실제 가치보다 정리 비용이 커질 수 있음
   - 해결방안: hotspot 기반 우선순위를 적용하고 smell hotspot ratio와 delivery impact score로 검증함
2. 문제: 리뷰어마다 스멜 판단 기준이 다르면 개선 활동이 감정 논쟁으로 흐를 수 있음
   - 해결방안: 팀 기준과 예시를 공유하고 review consistency score와 dispute rate로 검증함
3. 문제: 스멜을 발견만 하고 후속 리팩터링과 연결하지 않으면 지식만 쌓이고 코드 상태는 유지될 수 있음
   - 해결방안: debt backlog와 연계하고 remediation throughput과 smell recurrence rate로 검증함

## Ⅶ. 적용 사례

- 레거시 서비스 리뷰에서는 스멜 목록을 수집하고, smell hotspot ratio와 remediation throughput으로 결과를 확인함
- 팀 코드 리뷰 가이드에서는 스멜 기준을 공유하고, review consistency score와 dispute rate로 결과를 확인함
- 정적 분석 도입 조직에서는 스멜을 backlog와 연계하고, smell recurrence rate와 delivery impact score로 결과를 확인함

## Ⅷ. 결론

코드 스멜은 고쳐야 할 코드 목록이 아니라 미래 변경 비용이 높아질 지점을 조기에 알려주는 설계 경고 신호로 써야 함.
