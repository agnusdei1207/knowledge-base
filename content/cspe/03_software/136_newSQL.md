## Ⅰ. 개요
- **정의**: RDBMS의 ACID 트랜잭션과 NoSQL의 수평 확장성을 동시에 제공하는 분산 관계형 DB
- **배경/필요성**: NoSQL은 확장성을 확보했으나 트랜잭션 일관성 포기 문제가 있어 양쪽 장점 결합이 필요함
- **비유**: 은행의 정확한 장부 관리와 편의점의 빠른 확장을 동시에 갖춘 금융 플랫폼과 유사함

| 출제 의도 | 반드시 짚을 핵심 | 감점 회피 포인트 |
|:---|:---|:---|
| RDBMS/NoSQL 한계 극복 전략 | 분산 트랜잭션·합의 프로토콜·SQL 호환성 | RDBMS·NoSQL·NewSQL 3자 비교 시 축 명확히 제시 필요 |

> 요약: ACID와 수평 확장성을 동시에 달성하는 분산 관계형 DB임

## Ⅱ. 구성요소
```text
SQL Layer --> Distributed TX Manager --> Consensus (Raft/Paxos)
                                              |
                                     Distributed Storage
```

| 구성요소 | 설명 | 비유 |
|:---|:---|:---|
| SQL Layer | 표준 SQL 파싱·최적화를 수행하는 쿼리 처리 계층 | 은행 창구 |
| Distributed TX Manager | 분산 노드 간 ACID 트랜잭션을 조율하는 관리자 | 본점 감사 부서 |
| Consensus Engine | Raft/Paxos로 데이터 복제 일관성을 보장하는 합의 엔진 | 다수결 의사결정 위원회 |
| Distributed Storage | 데이터를 범위 기반으로 분산 저장하는 KV 스토리지 | 지역별 금고 |

> 요약: SQL 호환 계층 아래 합의 기반 분산 트랜잭션·스토리지로 구성됨

## Ⅲ. 절차
```text
SQL 파싱 --> 분산 TX 시작 --> 합의/복제 --> 커밋/응답
```
- 1단계: 클라이언트 SQL을 파싱하고 분산 실행 계획 수립
- 2단계: 관련 샤드에 분산 트랜잭션 시작(2PC 또는 합의 기반)
- 3단계: Raft/Paxos로 다수 노드에 복제 후 합의 확인
- 4단계: 합의 완료 시 커밋하고 클라이언트에 응답 반환

> 요약: SQL 파싱-분산 TX-합의 복제-커밋의 4단계로 처리함

## Ⅳ. 문제점
- 쓰기 지연: 합의 프로토콜의 다수 노드 확인 과정으로 단일 노드 대비 쓰기 지연 증가함
- 지리 분산 오버헤드: 원격 데이터센터 간 합의 시 네트워크 왕복 시간이 누적됨
- 운영 복잡성: 분산 노드 관리·모니터링·업그레이드의 운영 부담이 큼

> 요약: 쓰기 지연, 지리 분산 오버헤드, 운영 복잡성이 주요 과제임

## Ⅴ. 개선방안
1. 단기: 쓰기 지연 → 리더 로컬리티 설정으로 핫 데이터의 합의 홉 최소화
2. 중기: 지리 분산 → 리전별 파티셔닝과 Follower Read로 원격 합의 빈도 감소
3. 장기: 운영 복잡성 → 클라우드 매니지드 서비스(CockroachDB Cloud 등) 전환

> 요약: 리더 로컬리티, 리전 파티셔닝, 매니지드 서비스로 단계적 개선함

## Ⅵ. 전망
- 발전 방향: 글로벌 분산 OLTP 표준 아키텍처로 자리잡는 추세임
- 기술사적 판단: CAP 이론 내에서 CP 강화와 가용성 보완 설계 역량이 요구됨
- 기술사 제언: 워크로드 특성(읽기/쓰기 비율, 지리 분포)에 맞는 구성 전략 수립을 제언함
