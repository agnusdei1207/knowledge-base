# 📖 【암기용】 개념 완전 이해

> 목적: 멀티 클라우드 전략을 처음 봐도 완벽히 이해하게 만든다. 시험 답안 양식이 아니라, 이해를 위한 친절한 설명이다.

## 한눈에
- **개요**: 멀티 클라우드는 **클라우드 배포 모델**의 한 유형으로, 서로 다른 **CSP**(Cloud Service Provider, 클라우드 사업자) 2개 이상을 업무 목적별로 나눠 쓰는 전략이다.
- **왜 필요한가**: 단일 CSP에만 의존하면 **벤더 종속(Vendor Lock-in)** — 특정 CSP 전용 API·서비스에 묶여 다른 CSP로 옮기기 어려워지는 현상 — 이 생기고, 그 CSP의 리전 장애가 곧 전사 장애로 직결된다.
- **핵심 직관**: 멀티 클라우드는 "여러 CSP에 흩뿌리기"가 아니라, 업무별로 어느 CSP의 어떤 서비스를 쓸지 정하는 포트폴리오 관리다.

## 핵심 용어 정리 (내부에 등장하는 것들)

| 용어 | 의미 | 비유 |
|:---|:---|:---|
| 클라우드 배포 모델 | 퍼블릭·프라이빗·하이브리드·멀티 클라우드처럼 클라우드를 어떻게 구성해 쓰는지의 상위 분류 — 멀티 클라우드는 이 분류의 한 유형 | 집을 자가·전세·월세 중 어떻게 소유·운영할지의 큰 틀 |
| CSP | AWS·Azure·GCP·네이버클라우드 같은 클라우드 사업자 | 건물주 |
| 벤더 종속(Vendor Lock-in) | 특정 CSP 전용 API·서비스·데이터 포맷에 의존해 다른 CSP로 옮기기 어려워지는 현상 | 한 통신사 전용 요금제에 묶여 번호이동이 번거로워짐 |
| 워크로드 포트폴리오 | 회사가 운영하는 시스템들을 업무 성격별로 분류한 목록 — 각 업무를 어느 CSP에 배치할지의 기준이 됨 | 자산을 주식·채권·현금으로 나눠 담는 투자 포트폴리오 |
| 랜딩존(Landing Zone) | CSP별로 미리 표준화해 둔 계정·네트워크·보안 기본 구성 | 이사 갈 집에 미리 깔아둔 전기·수도 배선 |
| IAM Federation | 여러 CSP의 로그인 체계를 사내 SSO 한 곳으로 묶어 인증하는 것 | 여러 건물 출입증을 사원증 하나로 통합 |
| Policy as Code | 보안·네트워크 정책을 코드로 정의해 CSP마다 동일하게 자동 적용하는 방식 | 회사 규정집을 코드화해 어느 지사든 동일 적용 |
| Active-Active / Active-Passive | 두 CSP를 동시에 운영(Active-Active)하거나, 평소엔 하나만 쓰고 나머지는 대기(Active-Passive)시키는 이중화 방식 | 두 매장을 동시에 여는 것 vs 본점+비상 대기점 |
| RTO / RPO | 장애 후 서비스 복구까지 걸리는 최대 허용 시간(RTO)과 데이터 손실 허용 범위(RPO) | RTO=응급실 도착 목표 시간, RPO=되돌아가도 되는 최대 시점 |
| IaC(Terraform) | 인프라 구성을 코드로 작성해 CSP별로 동일 절차로 배포하는 도구 | 같은 설계도로 여러 지점 매장을 짓는 것 |

## 깊이 이해

### 왜 멀티 클라우드가 필요한가 — 벤더 종속의 실제 비용
- 워크드 예: 연 클라우드 비용 50억 원인 회사가 특정 CSP 전용 관리형 서비스로 시스템을 설계하면, 나중에 CSP를 바꾸려 할 때 재설계 비용이 수개월~1년, 인건비만 수억 원대로 커질 수 있다. 반면 표준 API(Kubernetes, 표준 SQL 호환 DB 등)로 설계하면 전환 비용이 수 주 단위로 줄어든다.
- CSP 리전 장애가 1시간 발생했을 때 초당 매출이 큰 서비스라면 그 자체가 직접 손실이다. 두 번째 CSP에 DR을 구성해두면 이 손실을 RTO 목표(예: 1시간 이내) 안으로 제한할 수 있다.

### 워크로드 배치 판단 — 어떤 기준으로 CSP를 고르나
- 지연시간: 사용자가 몰린 지역에 가까운 리전을 지원하는 CSP 우선
- 데이터 등급: 개인정보·금융 데이터는 규제상 특정 리전·CSP가 강제되는 경우가 있음
- 특화 서비스: GPU 확보가 쉬운 CSP에 AI 학습, 기존 사내 인증(AD) 연동이 쉬운 CSP에 업무 시스템 배치
- 비용: 동일 사양 VM이라도 CSP별 단가 차이가 10~30% 나는 경우가 흔해, 비용 민감 워크로드는 견적 비교 후 배치

### Active-Active와 Active-Passive의 차이 — 수치로 이해
- Active-Passive: 평소 CSP-A만 트래픽을 처리하고 CSP-B는 최소 사양으로 대기하다가 장애 시 전환한다. DNS 전환 등이 필요해 RTO가 보통 수십 분~1시간이다.
- Active-Active: CSP-A·CSP-B가 동시에 트래픽을 처리(예: 50:50 분산)한다. 한쪽 장애 시 트래픽을 즉시 다른 쪽으로 몰기만 하면 되어 RTO가 수 분 이내로 줄지만, 데이터를 양쪽에서 실시간 동기화해야 해 구현 난이도와 비용이 훨씬 크다.
- 그래서 핵심 업무(RTO 1시간 이내 요구)만 Active-Active로, 나머지는 Active-Passive나 백업 수준으로 차등 적용하는 것이 실무적이다.

### 흔한 오해
- "여러 CSP에 같은 앱을 복제해두면 멀티 클라우드 전략이 완성된다"는 오해가 흔하다. 실제로는 IAM Federation, Policy as Code, 로그 통합, 비용 태그 표준화 같은 공통 제어면이 없으면 CSP가 늘수록 관리 포인트만 늘어 운영 비용과 사고 위험이 오히려 커진다.

## 연결 개념
- 클라우드 배포 모델 — 멀티 클라우드는 배포 모델의 한 축(퍼블릭·프라이빗·하이브리드·멀티)
- 하이브리드 클라우드 — 온프레미스+퍼블릭 연계라는 다른 축, 멀티 클라우드와 조합 가능
- FinOps — CSP별 비용 비교와 태그 표준화의 실행 체계
- 컨테이너·쿠버네티스 — 이식성을 확보해 벤더 종속을 낮추는 기술 수단

# 📝 【답안용】 시험 답안 템플릿

> 목적: 시험장에서 25분에 그대로 쓰는 답안 양식. 작성방식(추상표현 금지·수치·도식·문제유형 전환)을 엄격히 지킨다.
> 핵심: 멀티 클라우드는 벤더 종속 완화 구호가 아니라 워크로드 배치, 공통 통제, 장애 전환, 비용 지표를 설계하는 전략이다.

## 핵심 인사이트 (3줄 요약)

> 1. **본질**: 멀티 클라우드 전략은 둘 이상 CSP를 목적별로 조합해 종속, 장애, 비용, 규제 리스크를 관리하는 운영 전략이다.
> 2. **가치**: CSP별 특화 서비스와 지역 리전을 활용하면서 단일 사업자 장애와 가격 정책 변경 영향을 줄인다.
> 3. **판단 포인트**: 이식성, 데이터 복제, 통합 관측성, IAM federation, FinOps 체계가 없으면 운영 비용이 증가한다.

## 출제 의도 및 답안 포인트

| 출제 의도 | 반드시 짚을 핵심 | 감점 회피 포인트 |
|:---|:---|:---|
| 멀티 클라우드 도입 목적 확인 | 종속 완화, DR, 특화 서비스, 규제 대응 | CSP 수 증가를 전략으로 오해 |
| 아키텍처 운영 역량 확인 | 공통 IAM, 네트워크, 로그, IaC, 비용 태그 | 운영 통합 없이 장점만 서술 |
| 리스크 대응 판단 확인 | 데이터 일관성, 장애 전환, 비용 중복 | active-active 난이도와 검증 지표 누락 |

> 요약: 이 문제는 여러 CSP 사용 여부가 아니라 다중 환경을 하나의 통제 체계로 운영하는 판단을 요구한다.

## Ⅰ. 개요 및 필요성

- 개요: 멀티 클라우드는 둘 이상 CSP 조합 운영 전략임.
- 배경: 단일 CSP 장애, 가격 변경, 전용 API 종속, 지역 규제에 대응하기 위해 도입한다.
- 필요성: 공통 IAM, 네트워크, 관측성, 비용 태그 기준으로 비용, 보안, 장애 대응 복잡도를 통제한다.

---

## Ⅱ. 구조 및 구성요소

```text
Workload Portfolio -> CSP A / CSP B / CSP C
                  -> Common IAM / Network / IaC / Observability
                  -> FinOps / DR / Compliance Control
```

| 구성요소 | 역할 | 특이사항 |
|:---|:---|:---|
| 워크로드 포트폴리오 | 업무별 CSP 배치 기준 정의 | 지연시간, 데이터 등급, 서비스 적합도 |
| 공통 제어면 | IAM, 네트워크, 정책, 로그 통합 | SSO, Terraform, SIEM |
| 데이터·DR 계층 | 복제, 백업, 장애 전환 | RPO/RTO와 정합성 선택 |
| FinOps 체계 | CSP별 비용 가시화 | 태그 표준, 예산 알림 |

> 요약: 멀티 클라우드는 여러 CSP 위에 공통 제어면과 비용·DR 통제 체계를 얹는 구조다.

---

## Ⅲ. 동작원리 및 흐름도

```text
업무 요구 수집 -> CSP 적합도 평가 -> 배치/연결 설계
-> IaC 배포 -> 로그/비용 통합 -> DR 전환 훈련
```

| 단계 | 처리 내용 | 검증 기준 |
|:---:|:---|:---|
| 1 | 업무별 요구와 규제 조건 식별 | 데이터 위치, p95 지연, SLA |
| 2 | CSP 서비스와 비용 비교 | GPU, DB, AI, 네트워크 단가 |
| 3 | 공통 통제 배포 | IAM federation, policy as code |
| 4 | 운영 검증 | 장애 전환 시간, 태그 적용률, 로그 수집률 |

> 요약: 멀티 클라우드는 배치 결정 후 공통 통제와 장애 전환 훈련으로 운영성을 검증한다.

## Ⅳ. 특징

| 구분 | 단일 클라우드 | 멀티 클라우드 | 수치·판단 포인트 |
|:---|:---|:---|:---|
| 종속 | 단일 CSP API·계약 의존 | CSP별 대체 경로 확보 | 반출 리허설 연 1회 |
| 가용성 | 단일 CSP 장애 영향 | 다중 CSP DR 설계 가능 | RTO 1시간, RPO 15분 |
| 비용 | 단일 과금 체계 | CSP별 단가 비교와 중복 비용 | 예산 편차 10% 이하 |
| 운영 | 도구 일관성 | 도구·정책 통합 필요 | 로그 수집률 95% 이상 |

> 요약: 멀티 클라우드는 종속과 DR 리스크를 낮추지만 공통 운영 체계 없이는 비용과 정책 편차가 증가한다.

## Ⅴ. 심화 비교 및 적용 판단

| 구분 | 단일 CSP | 멀티 클라우드 | 선택 기준 |
|:---|:---|:---|:---|
| 구조 | 단일 landing zone | CSP별 landing zone + 공통 제어면 | 규제·DR·특화 서비스 요구 |
| 비용/성능 | 단가 협상 집중 | CSP별 서비스 단가와 지연 비교 | 월 비용 15% 이상 차이 시 검토 |
| 운영/위험 | 단일 장애 도메인 | 정책 편차와 데이터 복제 부담 | 운영 인력과 자동화 수준 |

> 요약: 멀티 클라우드는 DR·규제·서비스 차별성이 비용과 운영 부담을 초과할 때 선택한다.

| 리스크 | 원인 | 대응 방안 | 확인 지표 |
|:---|:---|:---|:---|
| 정책 편차 | CSP별 IAM·네트워크 모델 차이 | policy as code, 표준 landing zone | 정책 위반 0건 |
| 데이터 정합성 | 이기종 DB와 비동기 복제 | CDC, 충돌 정책, RPO 등급화 | 복제 지연 5분 이하 |
| 비용 불투명 | 과금 항목과 태그 체계 차이 | FinOps 태그 표준, 비용 배부 | 태그 커버리지 95% 이상 |

> 요약: 주요 리스크는 정책, 데이터, 비용의 불일치이며 자동화된 표준으로 통제한다.

| 점검 항목 | 목표 기준 | 측정 방법 |
|:---|:---|:---|
| 가용성 | 다중 CSP DR RTO 1시간 이하 | 전환 훈련, runbook |
| 이식성 | IaC 적용률 90% 이상 | Terraform state, 배포 기록 |
| 비용 | 예산 편차 10% 이하, 미사용 리소스 월 1회 제거 | Billing Export, FinOps 회의 |

> 요약: 멀티 클라우드 성패는 DR 전환 가능성, IaC 적용률, 비용 가시성으로 판정한다.

## Ⅵ. 실무 적용 및 결론

**적용 방안 3개 (필수 - 단계별 또는 항목별):**
1. 배치 원칙 수립: 업무별 CSP 선택 기준을 지연시간 100ms, 데이터 등급, 월 비용, 전용 서비스 의존도로 점수화
2. 공통 제어면 구축: SSO, Terraform, 중앙 로그, KMS 정책을 CSP별 landing zone에 적용
3. 운영 검증: DR 전환 훈련 반기 1회, 비용 태그 95% 이상, 정책 위반 0건을 경영 지표로 보고

**결론 (2줄):**
- 기술사 판단: 멀티 클라우드는 DR·규제·특화 서비스 요구가 명확하고 공통 운영 자동화가 준비된 경우 채택함
- 향후 방향: 쿠버네티스, Crossplane, OpenTelemetry 기반 공통 제어면으로 CSP별 운영 편차를 줄이는 방향으로 전개됨
