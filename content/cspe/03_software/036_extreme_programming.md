# 📖 【암기용】 개념 완전 이해

> 목적: 이 개념을 처음 보는 사람도 완벽히 이해하게 만든다. 시험 답안 양식이 아니라, 이해를 위한 친절한 설명이다.

## 한눈에
- **개요**: **XP(eXtreme Programming)**는 **애자일(Agile) 소프트웨어 개발 방법론**의 하나로, 페어 프로그래밍·TDD·리팩토링·지속적 통합(CI) 같은 검증된 개발 기법들을 이름 그대로 극단(Extreme)적인 수준까지 밀어붙여 적용하는 경량 방법론이다.
- **왜 필요한가**: 스크럼(Scrum) 같은 애자일 관리 프레임워크는 "회의 주기와 조직 운영을 어떻게 짤 것인가"에 초점을 맞춘다. 하지만 실제로 코드가 썩어가는 것(기술 부채 누적)을 막는 것은 관리 방식이 아니라 개발자가 코드를 짜는 방식 자체다. XP는 이 코딩 방식을 규율화해서 속도를 유지하면서도 품질 저하를 막는다.
- **핵심 직관**: 좋다고 알려진 기법을 적당히 도입하는 게 아니라 극단까지 밀어붙인다. 코드 리뷰가 좋다 → 아예 처음부터 둘이 같이 짠다(페어 프로그래밍). 테스트가 좋다 → 아예 코드를 짜기 전에 테스트부터 짠다(TDD). 잦은 통합이 좋다 → 아예 하루에도 여러 번 통합한다(CI).

## 핵심 용어 정리 (내부에 등장하는 것들)

| 용어 | 의미 | 비유 |
|:---|:---|:---|
| 애자일(Agile) | 짧은 주기로 반복 개발하며 변화에 대응하는 개발 철학 — XP가 속한 상위 범주 | 큰 지도 한 장 대신 구간별 내비게이션 안내 |
| XP(eXtreme Programming) | 애자일 중에서도 개발자의 코딩 실천 기법(엔지니어링 프랙티스)에 집중하는 방법론 | 애자일이라는 큰 우산 아래 '코딩 규율' 파트 |
| 변경 비용(Cost of Change) | 요구사항을 프로젝트 후반에 바꿀수록 커지는 수정 비용 | 집 골조를 다 세운 뒤 방 위치를 바꾸는 공사비 |
| 페어 프로그래밍(Pair Programming) | 두 사람이 모니터 한 대로 함께 코딩 — 드라이버(입력)와 내비게이터(검토)가 실시간으로 역할을 교대 | 운전자와 조수석의 실시간 길 안내 |
| TDD(Test-Driven Development) | 테스트 코드를 먼저 작성하고, 그것을 통과시키는 순서로 구현하는 개발 방식 | 과녁부터 그려놓고 화살을 쏘는 것 |
| Red-Green-Refactor | TDD의 3단계 사이클: 실패하는 테스트 작성(Red) → 최소 구현으로 통과(Green) → 구조 개선(Refactor) | 초안 작성 → 통과선 넘기기 → 다듬기 |
| 리팩토링(Refactoring) | 외부 동작은 그대로 두고 코드 내부 구조만 개선하는 작업 | 이사 없이 집 안 가구만 재배치 |
| CI(Continuous Integration) | 각자 작업한 코드를 하루에도 여러 번 공용 브랜치에 합치고 자동 테스트로 검증하는 관행 | 매일 소규모로 정산해 연말 결산 부담을 줄이는 것 |
| YAGNI(You Aren't Gonna Need It) | 지금 필요하지 않은 기능은 미리 만들지 않는다는 원칙 | 다음 달 이사 갈 집의 가구를 미리 사두지 않기 |
| 공동 코드 소유(Collective Code Ownership) | 코드의 특정 구역을 특정 개발자 개인 소유로 두지 않고 누구나 수정할 수 있게 하는 관행 | 개인 사물함이 아니라 공용 창고 |
| 켄트 벡(Kent Beck) | XP를 1990년대 후반 제안한 소프트웨어 엔지니어 | XP의 창시자 |

## 깊이 이해

### 변경 비용 곡선 — 왜 XP는 테스트에 집착하는가
- 폭포수(Waterfall) 모델에서는 프로젝트 후반부로 갈수록 요구사항 변경 비용이 기하급수적으로 커진다. 예컨대 코딩이 끝난 9개월 차에 핵심 DB 설계를 바꾸면, 그 영향이 시스템 전체로 파급되어 재작업 비용이 초기 대비 100배 수준(1백만 원 → 1억 원)으로 뛸 수 있다.
- XP는 이 곡선을 평평하게 만드는 것이 목표다. TDD로 축적된 자동화 테스트가 수천~수만 개 항상 돌아가고 있으면, 9개월 차에 아키텍처 일부를 뜯어고쳐도 테스트가 즉시 회귀(Regression) 오류를 잡아준다. 그래서 변경 비용이 프로젝트 시점과 무관하게 낮게 유지된다.
- 즉 XP의 실천 수칙들은 결국 "변경을 두려워하지 않아도 되는 상태"를 만드는 데 공통 목적이 있다.

### TDD 사이클을 예로 이해하기
- 예: "두 수를 더하는 함수"를 만든다고 하자.
  1. **Red**: `assert add(2, 3) == 5`라는 테스트를 먼저 작성한다. 아직 `add` 함수가 없으므로 테스트는 실패(또는 컴파일 에러)한다.
  2. **Green**: 테스트를 통과시키기 위해 가장 단순한 구현을 한다. 극단적으로는 `return 5;`처럼 하드코딩해도 이 단계에서는 허용된다 — 목표는 오직 "빨간불을 초록불로" 바꾸는 것이다.
  3. **Refactor**: 테스트가 통과한 상태를 유지하면서 `return a + b;`처럼 코드를 올바르고 일반적인 형태로 다듬는다. 이미 테스트가 있으므로 고치다가 실수해도 즉시 빨간불로 알려준다.
- 이 순서(테스트 → 최소 구현 → 개선)를 지키면 테스트하기 쉬운 코드만 짜게 되므로, 자연히 함수가 작고 단순해진다. TDD가 "테스트 기법"이 아니라 "설계 기법"으로도 불리는 이유다.

### 페어 프로그래밍의 판별 원리
- 페어 프로그래밍은 단순히 "옆에서 지켜보는 것"이 아니라, 드라이버(키보드를 잡고 코드를 입력하는 사람)와 내비게이터(한 발 떨어져서 논리적 오류·설계 방향을 검토하는 사람)의 역할이 명확히 구분되고 주기적으로 교대되는 것이 핵심이다.
- 핑퐁(Ping-pong) 방식이라는 변형도 있다: A가 실패하는 테스트를 작성하면(Red), 키보드를 넘겨받은 B가 그 테스트를 통과시키는 구현을 하고(Green) 다음 테스트를 작성한다. 이렇게 하면 리뷰가 코드 작성과 동시에, 실시간으로 일어난다.

### CI가 필요한 이유 — 통합 지옥(Merge Hell)
- 개발자 여러 명이 각자 브랜치에서 1~2주씩 작업하다가 한꺼번에 합치면, 서로 건드린 코드가 충돌(Merge Conflict)할 확률이 커진다. 예를 들어 5명이 2주간 독립적으로 작업하면 마지막 날 하루에 5개 브랜치를 동시에 병합해야 하고, 충돌 지점을 찾는 데만 며칠이 걸릴 수 있다.
- CI는 이를 막기 위해 하루에도 여러 번(이상적으로는 몇 시간에 한 번) 작은 단위로 메인 브랜치에 통합하고, 그때마다 자동화된 테스트를 돌려 문제를 즉시 발견한다. 충돌이 나더라도 변경 범위가 작으므로 원인 파악이 쉽다.

### 비유
- 일반적인 개발: 혼자 방에 틀어박혀 며칠에 걸쳐 큰 기능을 완성한 뒤 한 번에 제출한다. 중간에 잘못된 방향으로 갔다면 되돌리는 비용이 크다.
- XP식 개발: 둘이 대화하며(페어) 짧은 주기로 조금씩 만들고, 만들기 전에 검증 기준(테스트)부터 세우고, 만든 것은 그날 안에 전체와 합친다. 잘못된 방향은 몇 시간 안에 드러난다.

## 연결 개념
- **스크럼(Scrum)**: 애자일의 또 다른 축으로, XP가 "어떻게 코딩할 것인가"(엔지니어링 프랙티스)를 다룬다면 스크럼은 "어떻게 팀을 운영하고 일정을 관리할 것인가"(프로젝트 관리 프레임워크)를 다룬다. 실무에서는 스크럼(관리)과 XP(개발 기법)를 함께 쓰는 경우가 많다.
- **DevOps·CI/CD**: XP가 제안한 지속적 통합(CI)은 이후 지속적 배포(CD)로 확장되어 현대 DevOps 파이프라인의 기본 요소가 되었다.
- **YAGNI와 단순설계**: XP의 단순성 가치를 실천하는 구체적 원칙으로, 오버엔지니어링을 막는 판단 기준이다.

# 📝 【답안용】 시험 답안 템플릿

> 목적: 시험장에서 25분에 그대로 쓰는 답안 양식. 작성방식(추상표현 금지·수치·도식·문제유형 전환)을 엄격히 지킨다.
> 핵심: 이 시험은 정보를 많이 나열하는 시험이 아니라, 문제 신호어에서 출제자 의도를 읽고 핵심 논점을 선별해 쓰는 시험이다.

## 핵심 인사이트 (3줄 요약)

> 1. **본질**: 요구사항 변화에 따른 '변경 비용(Cost of Change)'의 기하급수적 상승을 타파하기 위해, 소프트웨어 공학의 우수 프랙티스(테스트, 코드 리뷰)를 극한(Extreme)의 수준으로 강제하는 애자일 개발 방법론이다.
> 2. **가치**: 스크럼(Scrum)이 덮어둔 코드 레벨의 기술 부채(Technical Debt)를 TDD(테스트 주도)와 리팩토링으로 방어하며, 페어 프로그래밍을 통한 실시간 피드백으로 결함(Defect)을 원천 차단한다.
> 3. **판단 포인트**: XP의 5대 가치(의사소통/단순성/피드백/용기/존중)를 뼈대로 잡고, 이를 실현하는 12가지 실천 수칙 중 TDD(Red-Green-Refactor)와 CI(지속적 통합)의 아키텍처적 시너지를 대조해야 한다.

## 출제 의도 및 답안 포인트

| 출제 의도 | 반드시 짚을 핵심 | 감점 회피 포인트 |
|:---|:---|:---|
| 폭포수 대비 XP의 비용 곡선(Cost of Change) 차이 규명 | 폭포수(기하급수적 증가) vs XP(수평 유지) | 단순히 XP를 코딩 규칙 모음으로만 얕게 치부하고 공학적 비용 곡선 누락 |
| XP의 5대 핵심 가치와 12대 실천 수칙(Practice) 매핑 | 용기->리팩토링, 피드백->TDD/CI, 의사소통->Pair | 12개를 다 외워 나열하려다 TDD의 Red-Green-Refactor 메커니즘을 못 적는 실수 |
| TDD (테스트 주도 개발)의 작동 원리와 방어력 | 비즈니스 로직 작성 '이전'에 테스트 코드 선행 작성 | TDD를 코딩 '후'에 테스트하는 기존 QA로 혼동하는 치명적 맹점 |

> 요약: 스크럼이 "빨리 달리는 법"이라면, XP는 "달리다 자빠지지 않게 무릎 보호대를 차는 법"이다. 코드 품질이 썩으면 애자일은 3개월 안에 스스로 붕괴한다.

## Ⅰ. 개요 및 필요성

- 정의: 켄트 벡(Kent Beck)이 제안한 경량 방법론으로, 5가지 핵심 가치(의사소통, 단순성, 피드백, 용기, 존중)를 12가지 실천 수칙(Practices)으로 구체화하여 고품질 코드를 신속 인도하는 애자일 기법
- 배경: 폭포수 모델에서는 프로젝트 후반부로 갈수록 설계 변경 비용이 천문학적으로 폭발(Exponential)하여, 비즈니스 요구 변화에 둔감한 레거시 산출물 양산
- 필요성: 테스트 자동화(TDD)와 지속적 리팩토링을 통해 프로젝트 후반부에도 변경 비용을 수평(Flat)으로 유지하고, 단기 배포(Small Releases)로 고객과 시장의 피드백을 실시간 수용하기 위함

## Ⅱ. XP 핵심 가치와 TDD (Test-Driven Development) 도식

```text
[ TDD (테스트 주도 개발) 워크플로우 : Red -> Green -> Refactor ]

1. [ Red (실패) ] 🚨 : 실제 기능 코드는 없는데, "이 함수에 2와 3을 넣으면 5가 나와야 해"라는 테스트 코드부터 먼저 작성 (당연히 컴파일 실패/에러 발생)
       |
2. [ Green (성공) ] ✅ : 테스트를 통과하기 위해 가장 멍청하고 지저분한 방법으로 실제 코드(Business Logic) 작성 (예: return 5;)
       |
3. [ Refactor (리팩토링) ] 🛠️ : 코드를 우아하게(중복 제거, 패턴 적용) 수정. 수정 후에도 아까 짠 테스트 코드가 지켜주므로 버그 날 걱정 0%!
```

| XP의 5대 가치 | 대응하는 핵심 실천 수칙 (Practices) | 아키텍처적(엔지니어링) 효과 |
|:---|:---|:---|
| **의사소통** (Comm.) | **페어 프로그래밍 (Pair Programming)** | 내비게이터와 드라이버의 실시간 코드 리뷰로 결함 밀도(Defect Density) 50% 단축 |
| **피드백** (Feedback) | **TDD** 및 **지속적 통합 (CI, Continuous Integration)** | 하루 10번 메인 브랜치 병합 시 자동화된 회귀 테스트(Regression Test)가 빅뱅 에러 억제 |
| **단순성** (Simplicity) | **디자인 단순화 (Simple Design, YAGNI)** | 미래를 대비한 과도한 추상화(Over-engineering) 금지. 10줄이면 될 코드를 100줄로 짜지 않음 |
| **용기** (Courage) | **리팩토링 (Refactoring)** | 썩은 레거시 코드를 언제든 갈아엎어 기술 부채 상환. (TDD 안전망이 있어 가능함) |
| **존중** (Respect) | **공동 코드 소유 (Collective Code Ownership)** | A의 코드를 B가 맘대로 고칠 수 있음(사일로 파괴). 특정 개발자 퇴사 시 시스템 마비 방어 |

> 요약: TDD는 테스트 기술이 아니라 '설계 기법'이다. 쓸데없이 복잡한 코드는 테스트 코드를 짜기가 너무 어렵기 때문에, TDD를 강제하면 개발자는 스스로 코드를 가장 단순한 단위로 쪼개게(Simplicity) 된다.

---

## Ⅲ. 기존 폭포수(Waterfall) 대비 변경 비용(Cost of Change) 곡선

XP가 애자일 공학의 정점이라 불리는 이유는 경제학적(비용) 궤적을 꺾었기 때문이다.

| 리스크 요인 | 폭포수 모델의 비용 궤적 (기하급수 상승) | XP의 비용 궤적 (수평/Flat) 유지 비결 |
|:---|:---|:---|
| **요구사항 변경(수정)** | 코딩 다 끝난 9개월 차에 DB 설계를 바꾸려면, 시스템 전체가 폭발하므로 재작업 비용 100배(1억 원) 증가 | TDD 기반 자동화 테스트 1만 개가 **회귀(Regression) 오류**를 1초 만에 잡아주므로, 9개월 차에 아키텍처를 갈아엎어도 변경 비용이 1배(1백만 원)로 유지됨 |

> 요약: XP는 용기(Courage)의 방법론이다. "지금 이 코드를 엎으면 다 박살 나지 않을까?"라는 개발자의 본능적 공포를, 1만 개의 촘촘한 테스트 코드(TDD) 그물망으로 없애버린 것이다.

## Ⅳ. 극복해야 할 시스템적 리스크 및 인프라 튜닝

XP의 실천 수칙들은 극한(Extreme)을 요구하므로, 도입 시 조직 문화와 충돌하여 파국을 맞기 쉽다.

| 리스크 요인 | 발생 시나리오 및 시스템 붕괴 원인 | 아키텍처 대응 방안 (실무 튜닝) |
|:---|:---|:---|
| **페어 프로그래밍 인건비 낭비론** | 경영진이 "개발자 두 명이 모니터 한 대를 보면 생산성이 반 토막 나는 것 아니냐"며 페어를 금지시켜 결함 폭증 | 핑퐁(Ping-pong) 페어 프로그래밍 도입: A가 테스트 코드를 짜면(Red), B가 키보드를 넘겨받아 구현(Green)하는 릴레이 방식으로 몰입도와 성과 가시화 입증 |
| CI(지속적 통합) 서버 병목 | 10명의 개발자가 하루 5번씩 코드를 올리는데 자동화 테스트를 돌리는 빌드 서버가 뻗어버려(1시간 대기) 퇴근 불가 | **GitOps 및 젠킨스(Jenkins) 파이프라인 튜닝**: 빌드 잡(Job)을 도커(Docker) 컨테이너 기반 병렬 테스트 워커(Worker) 분산 아키텍처로 찢어 빌드 3분 컷 사수 |

> 요약: XP는 훈련된 특수부대의 전술이다. 주니어끼리 페어 프로그래밍을 시키면 서로 잡담만 하고, CI 서버 없이 쉘 스크립트로 빌드를 돌리면 매일 빌드 깨짐(Broken Build)으로 싸우다 끝난다.

## Ⅴ. 실무 적용 방안 및 결론

**적용 방안 3개:**
1. [마이크로서비스(MSA) 백엔드 TDD 강제화] 결제 연동(PG) 코어 모듈 개발 시, UI나 DB가 아직 없더라도 Mockito 등 목(Mock) 객체를 활용한 단위 테스트(Unit Test)를 먼저 작성하도록 강제하여(Test-First), 타 서비스 의존성 없이 순수 비즈니스 로직 무결성 100% 검증
2. [On-boarding 페어 프로그래밍 안착] 신규 입사자 투입 시 사수-부사수 간 의무적인 1일 2시간 페어 프로그래밍 타임박스를 설정하여, 별도의 문서(인수인계서) 교육 없이 암묵지(Tacit Knowledge)인 사내 코드 컨벤션과 도메인 지식을 실시간 전수
3. [지속적 리팩토링과 SonarQube 정적 분석 결합] XP의 '용기 있는 리팩토링'을 객관적 지표로 뒷받침하기 위해, CI 파이프라인에 SonarQube를 연동하고 코드 커버리지(Test Coverage) 80% 미만이거나 Code Smell(중복 코드) 발생 시 메인 브랜치 병합을 원천 차단(Quality Gate)

**결론:**
- 기술사 판단: XP(eXtreme Programming)는 기획이나 일정 관리에 치중하던 소프트웨어 공학을 다시 '개발자의 코드'라는 가장 뜨거운 본질로 끌어내린 실리주의의 극치다. 페어 프로그래밍과 TDD는 단순한 룰이 아니라 기술 부채(Technical Debt)를 억제하는 공학적 보험(Insurance)이다.
- 향후 방향: 현대 IT 기업에서 XP라는 용어 자체는 덜 쓰이지만, XP가 주장했던 CI(지속적 통합), TDD, 리팩토링은 이미 DevOps와 클라우드 네이티브(CI/CD) 생태계의 숨 쉬듯 당연한 디팩토(De facto) 표준으로 완벽히 녹아들어 세상을 지배하고 있다.
