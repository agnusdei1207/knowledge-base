## 미리 알고가기

- XP는 애자일 원칙을 코드 작성 습관까지 끌고 내려온 개발 방법임
- TDD는 실패하는 테스트를 먼저 쓰고 구현으로 통과시키는 개발 방식임
- 페어 프로그래밍은 두 개발자가 한 작업을 함께 수행하며 설계와 코드를 동시에 검토하는 실천임
- 리팩터링(Refactoring): 외부 동작을 바꾸지 않고 코드 내부 구조를 개선하는 활동임
- 지속 통합(Continuous Integration): 작은 변경을 공용 저장소에 자주 통합하고 자동 시험으로 검증하는 방식임

## 작성 근거(검토용)

- 전통 관행과 XP를 품질 검증 시점·협업과 통합 방식·적용 조건으로 비교함
- 실패 테스트·최소 구현·리팩터링·통합을 코드와 테스트 상태가 바뀌는 실제 반복으로 유지함
- 제품팀과 레거시 개선을 분리해 변이 테스트 점수와 변경 실패율을 검증함

## Ⅰ. 개요

- **정의/개념**: XP는 작은 개발 주기·고객 피드백·자동 테스트·리팩터링·페어 프로그래밍을 결합한 애자일 개발 방법론임
- **배경/필요성**: 요구 변경마다 회귀 결함을 확인하고 코드 구조를 유지하기 위해 테스트 우선과 지속 통합 방식이 필요함

## Ⅱ. 특징

- 테스트와 리팩터링을 변경 단위마다 수행함
- 페어 프로그래밍과 공동 코드 소유로 지식 편중과 리뷰 지연을 줄임
- 변경 단위마다 회귀 시험을 실행해 통합 시점에 결함을 확인함
- 자동화 범위와 실천 규칙이 팀마다 다르면 XP 적용 결과를 같은 기준으로 비교하기 어려움

## Ⅲ. 종류 및 비교

| 구분 | 전통 개발 관행 | XP |
|:---|:---|:---|
| 품질 검증 시점 | 구현을 먼저 끝낸 뒤 테스트 단계에서 결함을 모아 확인함 | 테스트와 리팩터링을 개발 과정 안에 넣어 작은 변경마다 품질을 확인함 |
| 협업·통합 방식 | 개발자가 기능을 개별적으로 맡고 단계 종료 후 통합함 | 페어 프로그래밍으로 지식을 공유하고 작은 변경마다 지속 통합함 |
| 적용 조건 | 요구 기준선이 안정된 프로젝트에 적합, 후반 결함 발견·통합 충돌 위험 | 짧은 주기로 요구가 바뀌는 제품 개발에 적합, 자동 테스트·팀 규율·협업 시간 확보 필요 |

> 요약: XP는 작은 변경마다 자동 테스트·페어 프로그래밍·리팩터링·지속 통합을 적용함.

## Ⅳ. 구성요소 및 구조

| 구성요소 | 설명 |
|:---|:---|
| 페어 프로그래밍 | 드라이버와 내비게이터가 구현·설계·검토 역할을 교대함 |
| 테스트 주도 개발 | 실패 테스트를 작성하고 최소 구현과 리팩터링을 반복함 |
| 리팩터링 | 외부 동작을 유지하며 중복·결합도·가독성을 개선함 |
| 지속 통합 | 작은 변경을 공용 저장소에 통합하고 자동 시험을 실행함 |

> 요약: XP는 페어 검토·테스트 우선·리팩터링·지속 통합을 변경 단위마다 반복함.

## Ⅴ. 원리 및 절차 흐름도

```text
+-------------+     +-------------+     +-------------+     +-------------+
| 작은 요구 선택  | --> | 테스트 먼저 작성 | --> | 구현/리팩터링  | --> | 자주 통합      |
+-------------+     +-------------+     +-------------+     +-------------+
```

1. **작은 요구 선택**: 테스트와 구현을 한 번에 검증할 범위를 정함
2. **실패 테스트 작성**: 요구를 실행 가능한 실패 조건으로 표현함
3. **최소 구현·리팩터링**: 테스트를 통과시킨 뒤 중복과 결합을 줄임
4. **지속 통합**: 변경을 통합하고 전체 회귀 시험 결과를 확인함

## Ⅵ. 실무 사례

1. 제품팀은 페어 교대 규칙과 TDD를 적용하고 변이 테스트 점수와 운영 유입 결함률을 확인함
2. 레거시 개선은 회귀 시험을 먼저 구축하고 변경 실패율과 리팩터링 소요시간을 확인함

## Ⅶ. 결론

- XP는 자동 테스트·리팩터링·페어 프로그래밍·지속 통합을 반복해 요구 변경에 따른 회귀 결함을 통제하는 방법론임
