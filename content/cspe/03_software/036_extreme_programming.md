## 미리 알고가기

- XP는 짧은 피드백 주기와 코드 품질 강화를 중시하는 애자일 실천 방법임
- 페어 프로그래밍과 TDD와 리팩터링과 지속적 통합이 핵심 실천 항목임
- 프로세스보다 개발자 협업과 코드 수준 규율이 중심임

## Ⅰ. 개요

- **정의/개념**: XP는 요구 변화에 빠르게 대응하기 위해 짧은 개발 주기와 고객 피드백과 강한 코드 품질 규율을 결합한 애자일 개발 방법론이며, 대표 실천으로 페어 프로그래밍과 TDD와 리팩터링을 사용함
- **배경/필요성**: 변경이 잦고 품질 결함 비용이 큰 소프트웨어 프로젝트에서는 문서 중심 통제만으로는 대응이 어렵기 때문에, 코드 작성 단계에서부터 품질과 학습 속도를 끌어올리는 방식이 필요함

## Ⅱ. 특징

- 개발자 수준의 실천 규율이 방법론 핵심이어서 품질 개선 효과가 직접적임
- 테스트를 먼저 두어 변경 안전성과 리팩터링 가능성을 높임
- 페어 프로그래밍으로 지식 공유와 결함 조기 발견을 유도함
- 팀 숙련도와 문화 수용성이 낮으면 형식만 남고 생산성 저하로 보일 수 있음

## Ⅲ. 종류 및 비교

| 판단 기준 | 전통 개발 관행 | XP |
|:---|:---|:---|
| 품질 확보 시점 | 개발 후 테스트 중심 | 개발 중 지속 품질 확보 |
| 협업 방식 | 개인 작업 비중 큼 | 페어와 공동 소유 강조 |
| 변경 대응 | 설계 변경 비용 큼 | 테스트 보호망 기반 대응 용이 |
| 적합 환경 | 요구 안정 프로젝트 | 변화 빠르고 품질 민감한 제품 개발 |

## Ⅳ. 구성요소 및 구조

| 구성요소 | 설명 |
|:---|:---|
| Pair Programming | 두 개발자가 함께 작업해 실시간 리뷰와 지식 전파와 설계 품질 향상을 동시에 노림 |
| Test-Driven Development | 테스트를 먼저 작성해 요구를 실행 가능한 기준으로 바꾸고 회귀 방지 기반을 만듦 |
| Refactoring | 외부 동작은 유지하면서 내부 구조를 지속 개선해 코드 부패를 늦춤 |
| Continuous Integration | 작은 변경을 자주 통합해 충돌과 결함을 초기에 드러내는 운영 리듬을 형성함 |

## Ⅴ. 원리 및 절차 흐름도

```text
+-------------+     +-------------+     +-------------+     +-------------+
| 작은 요구 선택  | --> | 테스트 먼저 작성 | --> | 구현/리팩터링  | --> | 자주 통합      |
+-------------+     +-------------+     +-------------+     +-------------+
```

1. **작은 요구 선택**: 구현 범위를 작게 나눠 즉시 검증 가능한 단위로 정함
2. **테스트 먼저 작성**: 요구를 실패하는 테스트로 표현함
3. **구현 및 리팩터링**: 테스트를 통과시키고 구조를 정리함
4. **자주 통합**: 작은 변경을 CI에 올려 회귀 여부를 확인함

## Ⅵ. 문제점 및 해결 방안

1. 문제: 페어 프로그래밍을 형식적으로 운영하면 두 사람 시간이 동시에 소비되면서도 학습과 리뷰 효과가 약할 수 있음
   - 해결방안: 과제 유형과 숙련도에 맞춰 페어 범위를 조정하고 pair rotation coverage와 review defect catch rate로 검증함
2. 문제: TDD가 테스트 양만 늘리고 설계 의도와 경계 조건을 담지 못하면 유지비만 커질 수 있음
   - 해결방안: 테스트 설계 기준과 리팩터링 규칙을 병행하고 mutation score와 flaky test rate로 검증함
3. 문제: 팀이 CI와 자동화 없이 XP만 도입하면 작은 변경을 자주 통합할 안전망이 부족할 수 있음
   - 해결방안: CI 파이프라인을 선행 구축하고 build stability와 change failure rate로 검증함

## Ⅶ. 적용 사례

- 스타트업 제품팀에서는 TDD와 짧은 배포 주기를 결합하고 확인 지표는 change failure rate와 build stability임
- 신규 입사자 온보딩 팀에서는 페어 프로그래밍을 적용하고 확인 지표는 pair rotation coverage와 onboarding lead time임
- 핵심 도메인 모듈 개발에서는 리팩터링과 자동 테스트를 강화하고 확인 지표는 mutation score와 defect escape rate임

## Ⅷ. 결론

XP의 실질 가치는 애자일 구호가 아니라 코드 수준에서 변경 비용을 줄이는 규율을 팀 일상에 뿌리내리는 데 있음.
