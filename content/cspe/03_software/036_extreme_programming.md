## 미리 알고가기

- XP는 애자일 원칙을 코드 작성 습관까지 끌고 내려온 개발 방법임
- TDD는 실패하는 테스트를 먼저 쓰고 구현으로 통과시키는 개발 방식임
- 페어 프로그래밍은 두 개발자가 한 작업을 함께 수행하며 설계와 코드를 동시에 검토하는 실천임

## Ⅰ. 개요

- **정의/개념**: XP는 요구 변화에 빠르게 대응하기 위해 작은 개발 주기, 고객 피드백, 자동 테스트, 리팩터링을 묶어 운영하는 애자일 개발 방법론임.
- **배경/필요성**: 요구가 자주 바뀌고 결함 수정 비용이 큰 프로젝트에서는 개발 후반의 일괄 테스트만으로 품질을 지키기 어려우므로, 코드를 작성하는 순간부터 변경 안전성을 확보하는 방식이 필요함.

## Ⅱ. 특징

- 테스트와 리팩터링을 일상 작업으로 두어 코드가 오래 버티는 구조를 만듦
- 페어 프로그래밍과 공동 코드 소유로 지식 편중과 리뷰 지연을 줄임
- 작은 단위로 구현하고 자주 통합하므로 결함을 늦게 발견할 가능성이 낮아짐
- 자동화와 팀 규율이 약하면 실천 항목만 남고 생산성 논란이 커질 수 있음

## Ⅲ. 종류 및 비교

| 구분 | 전통 개발 관행 | XP |
|:---|:---|:---|
| 품질 확보 시점 | 구현을 먼저 끝낸 뒤 테스트 단계에서 결함을 모아 확인함 | 테스트와 리팩터링을 개발 과정 안에 넣어 작은 변경마다 품질을 확인함 |
| 협업 방식 | 개발자가 기능을 개별적으로 맡고 리뷰를 뒤에서 수행하는 경우가 많음 | 두 개발자가 함께 코드를 다루고 지식을 계속 공유함 |
| 변경 대응 | 요구가 바뀌면 설계와 코드 영향 범위가 한꺼번에 커지기 쉬움 | 자동 테스트를 보호막으로 삼아 작은 단위로 안전하게 수정함 |
| 적합한 환경 | 요구가 비교적 안정적이고 단계 통제가 중요한 프로젝트에 맞음 | 요구 변화가 잦고 품질 결함 비용이 큰 제품 개발에 맞음 |

> 요약: XP는 일정 관리 기법이라기보다 변경이 많은 개발에서 테스트와 협업 규율로 품질을 지키는 방식임.

## Ⅳ. 구성요소 및 구조

| 구성요소 | 설명 |
|:---|:---|
| Pair Programming | 두 개발자가 한 코드를 함께 다루며 설계 판단과 결함을 즉시 검토함 |
| Test-Driven Development | 실패하는 테스트를 먼저 작성해 요구를 실행 가능한 기준으로 바꾸고 회귀 결함을 막음 |
| Refactoring | 외부 동작은 유지한 채 내부 구조를 계속 정리해 코드 부패를 늦춤 |
| Continuous Integration | 작은 변경을 자주 통합해 충돌과 결함을 초기에 드러냄 |

## Ⅴ. 원리 및 절차 흐름도

```text
+-------------+     +-------------+     +-------------+     +-------------+
| 작은 요구 선택  | --> | 테스트 먼저 작성 | --> | 구현/리팩터링  | --> | 자주 통합      |
+-------------+     +-------------+     +-------------+     +-------------+
```

1. **작은 요구 선택**: 구현 범위를 짧게 나눠 바로 검증할 수 있는 단위로 정함
2. **테스트 먼저 작성**: 요구를 실패하는 테스트로 표현해 완료 기준을 분명히 함
3. **구현 및 리팩터링**: 테스트를 통과시키고 중복과 결합을 줄이도록 구조를 다듬음
4. **자주 통합**: 작은 변경을 CI에 올려 회귀 여부와 충돌을 바로 확인함

## Ⅵ. 실무 적용 및 유의점

1. 요구 변경이 잦은 제품팀에서는 핵심 업무 흐름에 XP를 적용하되 형식적인 페어 작업으로 끝나지 않도록 페어 교대 규칙과 테스트 설계 기준을 함께 운영하고 빌드 성공률과 변이 테스트 점수로 확인함
2. 레거시 개선 프로젝트에서는 리팩터링과 TDD를 함께 도입하되 자동화 없이 관행만 먼저 들여오면 효과가 약하므로 CI 파이프라인을 먼저 구축하고 운영 유입 결함 비율과 변경 실패율로 확인함

## Ⅶ. 결론

XP는 변화가 잦은 개발에서 테스트와 리팩터링과 협업 규율을 코드 수준에 정착시킬 때 가장 큰 효과를 내는 방법론임.
