# 📖 【암기용】 개념 완전 이해

> 목적: 블루-그린과 카나리 배포를 네트워크 계층의 트래픽 라우팅 메커니즘과 인프라 구성 관점에서 이해하게 만든다. 시험 답안 양식이 아니라, 이해를 위한 설명이다.

## 한눈에
- **개요**: **블루-그린 배포**와 **카나리 배포**는 로드밸런서 같은 네트워크 계층에서 신버전으로 향하는 트래픽 라우팅을 어떻게 바꾸느냐로 구분되는 두 가지 **무중단 배포** 기법이다.
- **왜 필요한가**: 서버를 잠깐이라도 내리고 배포하면(In-place 배포) 그 시간만큼 요청이 유실된다. 서버를 한 대씩 차례로 교체하는 롤링(Rolling) 배포는 다운타임은 없지만 구버전과 신버전이 동시에 트래픽을 받는 구간이 생겨, 세션·API 응답 구조가 다르면 오류가 난다. 블루-그린과 카나리는 이 혼재 구간을 각기 다른 방식으로 없애거나 통제한다.
- **핵심 직관**: 블루-그린은 신버전(Green) 환경을 구버전(Blue)과 같은 규모로 완전히 별도로 띄워두고, 로드밸런서의 라우팅 대상을 한 번에 Blue에서 Green으로 바꾼다(전환 순간 혼재 구간이 0에 가깝다). 카나리는 환경을 늘리지 않고, 같은 로드밸런서가 트래픽의 일부(예: 10%)만 신버전 인스턴스로 나눠 보내며 서서히 비율을 늘린다.

## 핵심 용어 정리
| 용어 | 의미 | 비유 |
|:---|:---|:---|
| 무중단 배포 | 서비스 중단 없이 신버전을 반영하는 배포 방식군 | 문을 안 닫고 하는 리모델링 |
| 롤링(Rolling) 배포 | 서버를 1대씩 순차적으로 내렸다 올리며 교체하는 방식 — 블루-그린·카나리 이전의 방식 | 한 줄로 선 사람을 한 명씩 교체 |
| 블루(Blue) | 현재 트래픽을 처리하는 기존(구) 버전 환경 | 지금 살고 있는 집 |
| 그린(Green) | 신버전을 미리 배포해둔, 아직 트래픽을 받지 않는 대기 환경 | 이사 갈 새집 |
| 로드밸런서(L4/L7) | 트래픽을 어느 서버로 보낼지 결정하는 네트워크 장비 또는 소프트웨어 | 교차로의 신호 담당자 |
| 카나리(Canary) | 광부들이 유독가스 감지를 위해 탄광에 먼저 들여보낸 카나리아 새에서 유래한 이름 — 소수의 신버전 인스턴스로 위험을 먼저 감지 | 탄광의 카나리아 새 |
| L7 가중치 라우팅 | HTTP 요청 단위로 트래픽 비율(예: 90:10)을 나누는 라우팅 방식 | 물줄기 비율을 조절하는 밸브 |
| Expand-Contract 마이그레이션 | DB 스키마 변경을 "추가 → 신구 공존 → 기존 삭제"로 나눠 하위 호환을 지키는 기법 | 헌 다리를 부수기 전에 새 다리부터 놓기 |

## 깊이 이해

### 배경 — 롤링 배포의 한계
- 롤링 배포는 서버를 한 대씩 순차 교체하므로 다운타임은 없지만, 교체가 끝날 때까지 구버전과 신버전이 동시에 살아 트래픽을 나눠 받는 구간이 반드시 생긴다. 이 구간에서 신버전이 API 응답 구조를 바꾸거나 세션 저장 방식을 바꾸면, 같은 사용자가 요청마다 다른 버전 서버로 튈 때 오류가 난다.
- 블루-그린은 이 혼재 구간을 "전환 순간"으로 압축해 없애고, 카나리는 혼재 구간 자체를 받아들이되 그 비율을 통제해 위험을 줄인다.

### 작동 원리 — 라우팅 관점
- **블루-그린**: Green 환경을 Blue와 동일한 규모(예: 서버 100대)로 미리 구축하고 스모크 테스트로 정상 동작을 확인한다. 검증이 끝나면 로드밸런서의 라우팅 대상을 Blue에서 Green으로 스위치 하나 바꾸듯 전환한다. 문제가 생기면 라우팅을 다시 Blue로 되돌리면 되므로 복구가 매우 빠르다.
- **카나리**: 별도 환경을 새로 만들지 않고, 기존 환경 안에 신버전 인스턴스를 소수 추가하거나 L7 라우팅 규칙으로 트래픽 비율을 나눈다. 예를 들어 서버 100대 중 90대는 구버전, 10대는 신버전으로 두고 로드밸런서가 요청의 10%만 신버전으로 보낸다.

### 수치로 보는 인프라 비용과 위험 노출의 트레이드오프
- 블루-그린은 전환 직전 한순간 Blue 100대 + Green 100대, 총 200대(2배) 인프라가 동시에 필요하다. 대신 전환 이후 결함이 발견되면 라우팅만 되돌리면 되어 복구까지 걸리는 시간은 보통 수 분 이내다. 다만 전환이 100% 단위로 일어나므로, 결함이 발견되기 전까지는 전체 트래픽이 신버전에 노출된다.
- 카나리는 추가 인프라 없이(또는 소량만 추가해) 기존 100대 규모 안에서 10대만 신버전으로 바꾸므로, 결함이 있어도 최대 트래픽의 10%만 영향을 받는다. 대신 90%에서 10%로, 다시 100%로 늘려가는 전체 과정에 수 시간이 걸릴 수 있고, 그동안 구버전과 신버전이 계속 혼재한다.

### 판별 원리 — 어느 축으로 고를 것인가
- "전환을 순간적으로 할 것인가, 점진적으로 할 것인가"가 두 기법을 가르는 축이다. 데이터베이스 스키마처럼 신구 버전이 오래 혼재하면 위험한 자원을 다루면 블루-그린처럼 혼재 구간을 최소화하는 쪽이 유리하고, 트래픽 규모가 커서 결함의 사용자 영향을 최소 단위로 쪼개고 싶으면 카나리가 유리하다.

### DB 스키마 호환성 문제
- 서버를 2배로 띄우는 것은 쉽지만, 뒤에 붙은 DB는 보통 하나뿐이라 블루와 그린이 같은 DB를 공유한다. 신버전이 컬럼명을 바꾸거나 삭제해 버리면, 아직 트래픽을 받는 구버전(카나리 중인 90% 또는 블루-그린 롤백 대상인 Blue)이 그 컬럼을 읽지 못해 오류가 난다. 이를 막는 Expand-Contract 마이그레이션의 3단계는 다른 070 파일(카나리 블루-그린 배포, SLO/메트릭 관점)을 참조한다.

### 현대적 구현 — 쿠버네티스와 서비스 메시
- 쿠버네티스의 기본 로드밸런싱은 파드(Pod) 개수 비율로만 트래픽을 나눈다(10%를 원하면 구버전 9개, 신버전 1개처럼 물리적으로 맞춰야 한다). Istio 같은 서비스 메시를 쓰면 파드 개수와 무관하게 HTTP 헤더 단위로 90:10 같은 논리적 비율을 지정할 수 있어 더 정밀한 카나리가 가능하다. Argo Rollouts 같은 컨트롤러는 "10% 투입 → 10분 대기 → 지표 이상 없으면 50% 투입"처럼 단계적 전환을 선언적 설정으로 자동화한다.

### 비유
- 블루-그린은 이사 갈 새집을 완전히 다 꾸며놓고 이삿날 가족 전체가 한 번에 이동하는 것과 같다. 카나리는 가족 중 한 명이 먼저 새집에서 하루 자보고 이상이 없으면 나머지 가족이 뒤따라 이사하는 것과 같다.

## 연결 개념
- 롤링 배포 — 블루-그린·카나리 이전 세대의 순차 교체 방식으로, 두 기법이 극복하려는 비교 대상.
- 서비스 메시(Istio) / Argo Rollouts — L7 가중치 라우팅과 단계적 전환을 자동화하는 쿠버네티스 생태계 도구.
- Feature Flag — 인프라 라우팅이 아니라 애플리케이션 코드 레벨에서 기능 노출을 제어하는 보완 기법.

# 📝 【답안용】 시험 답안 템플릿

> 목적: 시험장에서 25분에 그대로 쓰는 답안 양식. 작성방식(추상표현 금지·수치·도식·문제유형 전환)을 엄격히 지킨다.
> 핵심: 이 시험은 정보를 많이 나열하는 시험이 아니라, 문제 신호어에서 출제자 의도를 읽고 핵심 논점을 선별해 쓰는 시험이다.

## 핵심 인사이트 (3줄 요약)

> 1. **본질**: 클라우드 네이티브 환경에서 서비스의 중단 시간(Downtime)을 0(Zero)으로 수렴시키고, 신규 버전 배포 시 발생하는 장애의 폭발 반경(Blast Radius)을 극단적으로 통제하는 무중단 배포 아키텍처다.
> 2. **가치**: 블루-그린은 스위칭 방식을 통해 '가장 빠른 롤백'과 '버전 혼재 방지'를 제공하며, 카나리는 '점진적 트래픽 라우팅'을 통해 실서버 버그의 피해자를 전체 사용자의 1% 미만으로 한정 방어한다.
> 3. **판단 포인트**: 기존 롤링(Rolling) 배포가 가진 '구/신버전 혼재'의 맹점을 비판하고, 로드밸런서(L4/L7) 단에서의 트래픽 스위칭(Blue-Green) 및 가중치 분할(Canary) 메커니즘을 명확히 도식화해야 한다.

## 출제 의도 및 답안 포인트

| 출제 의도 | 반드시 짚을 핵심 | 감점 회피 포인트 |
|:---|:---|:---|
| 기존 배포(Rolling) 방식의 한계 타파를 위한 무중단 배포 아키텍처 도출 | 구/신 버전 동시 존재(혼재)로 인한 DB 스키마/세션 충돌 문제 방어 | 단지 "서버가 안 꺼져서 좋다" 수준의 얕은 서술 |
| 블루-그린과 카나리 배포의 엔지니어링 스위칭 메커니즘 맵핑 | L4/L7 로드밸런서를 통한 **단번 스위칭(100%) vs 가중치 라우팅(1%->10%)** 차이점 도식 | 카나리 배포와 A/B 테스트(마케팅 실험)의 목적을 혼동하는 치명적 안티패턴 |
| 대규모 MSA / 클라우드 환경에서의 비용 및 롤백 한계 조율 | 클라우드의 탄력성(Elasticity)을 활용한 블루-그린 리소스 2배 오버헤드 극복 | 두 배포의 장단점 비교 없이 단순히 개념만 나열 |

> 요약: 배포(Deployment)는 버튼을 누르는 행위가 아니다. 배포는 "이 코드가 터졌을 때 얼마나 많은 고객이 죽어나가고, 내가 몇 초 만에 이전 상태로 시간을 되돌릴(Rollback) 수 있는가?"를 설계하는 리스크 통제 예술이다.

## Ⅰ. 개요 및 필요성

- 정의: **무중단 배포(Zero-downtime Deployment)**는 클라이언트의 요청 유실 없이 신버전 소프트웨어를 실서버에 반영하는 기법이며, 이를 달성하는 대표적 패턴이 **블루-그린(동일 규모 스위칭)**과 **카나리(점진적 가중치 분할)** 배포임
- 배경: 기존 In-place(덮어쓰기) 배포는 긴 다운타임을 유발했고, 롤링(Rolling) 배포는 배포 중 구버전과 신버전 트래픽이 50:50으로 섞여 들어가며 API 응답 구조 불일치 붕괴(Session 꼬임) 유발
- 필요성: 시스템 가용성(Availability) 99.99%를 유지하면서, 신규 결함으로 인한 비즈니스 타격을 최소화하고 즉각적인 롤백(MTTR 1초 컷) 파이프라인을 확보하기 위함

## Ⅱ. 무중단 배포 아키텍처 대조 맵핑 (Blue-Green vs Canary)

네트워크 단(Load Balancer)에서 트래픽의 물줄기를 어떻게 꺾느냐의 차이다.

```text
[ 1. 블루-그린 배포 (스위치 엎어치기) ] 
                 +--> [ Blue (v1.0) 100대 ] -- (유휴 상태 대기) 
[ 트래픽 100% ] ---> LB 
                 +--> [ Green (v2.0) 100대 ] -- (전체 서비스 중 🟢)
(특징: 스위치 하나로 100% 트래픽 일괄 전환. 롤백 시 스위치만 위로 올리면 0.1초 만에 복구)


[ 2. 카나리 배포 (점진적 물꼬 트기) ]
[ 트래픽 90% ] ----> LB ----> [ 구버전 (v1.0) 90대 ] -- (대다수 안전하게 사용)
[ 트래픽 10% ] ----> LB ----> [ 신버전 (v2.0) 10대 ] -- (독가스 탐지용 카나리아 🐤)
(특징: L7 라우팅 가중치(Weight) 조절을 통해 1% -> 10% -> 50% -> 100% 점진적 확대)
```

| 비교 축 (차이점) | 블루-그린 (Blue-Green Deployment) | 카나리 (Canary Deployment) |
|:---|:---|:---|
| **트래픽 전환 방식** | 로드밸런서(LB) 엔드포인트를 신버전으로 **100% 일괄 전환(Big-bang 전환)** | 라우팅 가중치 룰을 통해 **1%에서 100%로 점진적(Progressive) 전환** |
| **인프라(리소스) 요구량** | 구버전(100대) + 신버전(100대) = **순간적으로 2배(200대)의 인프라** 필수. 비용 최고 | 전체 100대를 유지하면서 비율만 90:10으로 나누므로 추가 인프라 불필요 |
| **장점 (품질 방어)**| 구/신 버전 혼재 구간이 0초(Zero). 롤백은 LB 스위치 복귀로 **가장 빠름 (1초)** | 버그가 발생해도 **타격을 입는 사용자가 전체의 1% 미만**으로 통제됨 (가장 안전) |
| **단점 (운영 맹점)**| 신버전 100% 전환 직후 버그가 터지면 전체 사용자가 100% 장애를 맞이함 | 배포 완료까지 오랜 시간(수 시간) 소요. 구/신 버전이 장시간 섞여 돌아감 |

> 요약: 돈이 넘쳐나고(2배 인프라) 데이터베이스(DB) 충돌이 걱정되면 한 방에 끊어 치는 블루-그린이 짱이다. 넷플릭스처럼 트래픽이 미쳐 날뛰어서 한 방에 엎어쳤다간 서버가 녹아내릴 거 같으면 카나리로 간을 보며 넘어가는 게 정답이다.

## Ⅲ. 극복해야 할 시스템적 리스크 (데이터베이스 스키마 충돌)

서버(App)를 2배로 띄우는 건 쉽다. 하지만 백엔드에 묶인 DB(Oracle)는 2개로 복제할 수가 없다. (단일 장애점 붕괴).

| 리스크 요인 | 발생 시나리오 및 시스템 붕괴 원인 (안티패턴) | 아키텍처 대응 방안 (실무 튜닝) |
|:---|:---|:---|
| **배포 시 DB 스키마 하위 호환성 단절** | V1(구버전)은 DB의 `name` 컬럼을 쓰고, 배포 중인 V2(신버전)는 `first_name` 컬럼을 쓰도록 DB를 ALTER(수정)해 버림. 카나리 배포 중에 V1 서버들이 바뀐 DB를 읽지 못해 앱 전체 크래시 붕괴 | **Expand & Contract 패턴 (하위 호환성 DB 튜닝)**: 배포를 1번이 아닌 2번에 나눠서 진행. 1) 기존 `name`을 놔두고 `first_name` 컬럼을 추가만(Expand) 함. 2) V1과 V2가 동시에 잘 돌아감. 3) 배포가 100% V2로 끝나면 그때 기존 `name`을 삭제(Contract)하는 무중단 DB 마이그레이션 적용 |
| **카나리 로그 및 메트릭 파편화 (가시성 상실)** | 트래픽 1%를 신버전으로 보냈는데, 그 1% 유저가 에러를 뿜는지 안 뿜는지 전체 로그(99%)에 파묻혀 모니터링 담당자가 식별 불가 (독가스를 먹고 죽었는지 모름) | **APM(Datadog/Prometheus) 기반 버전별 메트릭 태깅**: 모든 로그와 에러 발생률에 `app_version=v2` 태그를 부착하여 대시보드를 이원화. 신버전 에러율이 구버전 대비 5%를 초과하면 CI 파이프라인이 즉각 **자동 롤백(Automated Rollback)** 발동 |

> 요약: 무중단 배포의 진짜 적은 트래픽이 아니다. 백엔드에서 묵직하게 버티고 있는 상태 저장소(Stateful DB)다. DB의 생김새(스키마)를 바꾸면서 무중단 배포를 하려면 코드 배포보다 10배는 치밀한 마이그레이션 작전이 필요하다.

## Ⅳ. 쿠버네티스(K8s)와 서비스 메시 기반의 모던 배포 융합

과거 Nginx 쉘 스크립트로 하던 노가다를 이제 K8s가 완벽한 선언적(Declarative)으로 대체했다.

| 융합 패러다임 | 물리적 인프라 제어 메커니즘 | 해결되는 오퍼레이션(Ops) 한계 |
|:---|:---|:---|
| **Istio (Service Mesh) 기반** <br> 정밀 라우팅 튜닝 | 기존 K8s의 순정 로드밸런싱은 "팟(Pod) 개수 비율"로만 트래픽을 나눔(10%를 원하면 무조건 구90대:신10대를 띄워야 함). Istio(Envoy)를 도입하면 서버가 1대:1대만 있어도, HTTP 헤더를 뜯어보고 **L7 트래픽 가중치를 90%:10%로 논리적 조율 가능** | 서버 리소스 낭비(물리적 스케일아웃) 없이 극한의 마이크로 트래픽 제어 달성 |
| **Argo Rollouts** <br> (점진적 딜리버리) | K8s 내부에 컨트롤러를 심어, "10% 투입 -> 10분 대기 -> 에러 없으면 50% 투입"이라는 카나리 배포의 시간적 흐름(Step)을 YAML 파일 몇 줄로 선언형 자동화 제어 | 사람이 지켜보다가 롤백 버튼을 누르는 장애 인지 시간(Time-to-Detect) 지연을 0초 컷 무인 자동화로 소거 |

> 요약: 블루-그린과 카나리는 결국 **"스위치를 얼마나 부드럽게 꺾을 것인가"**의 싸움이다. 서비스 메시(Istio)라는 최강의 스위치를 달게 되면, 사용자(VIP 유저)나 지역(서울)별로 특정 트래픽만 정확히 발라내서 10% 카나리를 돌리는 마법이 가능해진다.

## Ⅴ. 실무 적용 방안 및 결론

**적용 방안 3개:**
1. [Route53 (DNS) 가중치 기반 멀티 리전 블루-그린 롤아웃] 서울 리전(Blue)이 완벽히 가동 중일 때, 도쿄 리전(Green)에 신규 버전을 풀 세팅하고 AWS Route53 DNS 스위치를 0% -> 100%로 엎어치는 대규모 글로벌 블루-그린 적용으로 리전(Region) 단위 재해 복구(DR)급 무중단 릴리즈 달성
2. [다크 런칭(Dark Launching) 융합 카나리 섀도잉 튜닝] 트래픽 1%를 신서버로 꺾는 것조차 두려울 때, 사용자 몰래 구서버(V1)로 들어온 요청 패킷을 똑같이 **복제(Mirroring)**하여 신서버(V2)로 백그라운드에서 찔러보는(Shadowing) 기법 적용. 사용자 응답은 무조건 V1으로 나가므로 고객 피해는 0%이면서 신서버의 런타임 성능 가혹 검증 완료
3. [ArgoCD 기반 GitOps 파이프라인 자동 롤백 결합] ArgoCD가 GitHub의 `v2` 태그를 읽고 블루-그린 배포를 시작함. 만약 프로메테우스(Prometheus) 모니터링 알람이 `HTTP 500 에러 임계치 폭발`을 감지하면, 인간 승인 없이 ArgoCD가 즉각 `v1` 롤백 스크립트를 기동하는 Self-healing 통제망 구축

**결론:**
- 기술사 판단: 클라우드 시대에 "다운타임(점검 시간)"을 요구하는 시스템은 설계부터 실패한 레거시다. 블루-그린과 카나리 배포는 단순히 서버를 교체하는 툴이 아니라, 폭발 반경(Blast Radius)을 통제하고 개발자에게 "언제 배포해도 터지지 않는다"는 심리적 안전망(Safety Net)을 부여하는 데브옵스의 핵심 엔진(Engine)이다.
- 향후 방향: 최근 현업에서는 이 두 기법의 맹점(인프라 비용, 느린 배포)을 모두 소거하기 위해, 트래픽 라우팅 없이 서버 자체에 `Feature Flag(피처 플래그)`를 박아두고 배포(Deploy)와 릴리즈(Release) 시점을 완전히 분리하여, 런타임에 if문 토글 스위치 하나로 0.1초 만에 신기능을 끄고 켜는 마이크로 제어 시대로 진화하고 있다.
