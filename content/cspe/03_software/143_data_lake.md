# 📖 【암기용】 개념 완전 이해

> 목적: 데이터 레이크를 처음 보는 사람도 완벽히 이해하게 만든다. 시험 답안 양식이 아니라, 이해를 위한 친절한 설명이다.

## 한눈에
- **개요**: 데이터 레이크는 정형·반정형·비정형 **원시 데이터**를 객체 스토리지에 원본 그대로 적재하고, 저장이 아니라 **조회 시점에 스키마를 해석**하는 **schema-on-read** 방식의 빅데이터 저장 아키텍처다.
- **왜 필요한가**: 데이터 웨어하우스(DW)는 적재 전에 테이블 스키마를 먼저 확정하는 **schema-on-write** 방식이라, 로그·이미지·센서처럼 형태가 자주 바뀌거나 정형화가 어려운 데이터를 받아들이기 어렵다. 레이크는 "일단 저장, 해석은 나중에"로 이 문제를 푼다.
- **핵심 직관**: 정수하지 않은 강물을 통째로 호수에 모아둔 뒤, 마실 물·농업용·공업용으로 나중에 정수·분류하는 방식이다.

## 핵심 용어 정리 (내부에 등장하는 것들)

| 용어 | 의미 | 비유 |
|:---|:---|:---|
| 원시 데이터(Raw Data) | 가공·정제 이전의 원본 그대로 데이터 — 데이터 레이크가 다루는 **대상** | 채집한 그대로의 원목 |
| schema-on-read | 저장 시점엔 스키마를 강제하지 않고, 읽을 때 엔진이 스키마를 해석 — 데이터 레이크의 **정체성**을 이루는 핵심 개념 | 라벨 없이 쌓아두고, 열어볼 때 내용물을 확인 |
| schema-on-write | DW처럼 저장 전에 테이블 구조를 먼저 확정 — 레이크와 대조되는 개념 | 상자에 라벨을 미리 붙이고 정해진 칸에만 넣기 |
| 객체 스토리지 | 파일을 key-value 형태로 저장하는 대용량 저장소(S3, ADLS, GCS, HDFS) | 번호표만 있으면 어떤 짐이든 맡아주는 초대형 물류창고 |
| Raw(Bronze) Zone | 원천 그대로 적재하는 구역, 가공하지 않음 | 창고 입고장 — 검수 전 상태 그대로 |
| Curated(Silver) Zone | 정제·표준화된 중간 데이터 구역 | 1차 분류·포장을 마친 재고 구역 |
| Analytics(Gold) Zone | 집계·분석용으로 가공된 최종 구역 | 매장 진열대 — 바로 판매 가능한 상태 |
| Catalog | 파일 위치·스키마·소유자 등 메타데이터를 기록하는 목록(Hive Metastore, Glue Catalog) | 도서관 검색 시스템 — 책이 어디 있는지 알려줌 |
| Partition | 날짜·업무 기준으로 파일을 물리적으로 나눠 저장하는 방식 | 창고를 요일별 구역으로 나눠, 필요한 요일 구역만 뒤짐 |
| 데이터 늪(Data Swamp) | 카탈로그·소유자·품질 기준 없이 방치되어 활용 불가능해진 레이크 | 관리 안 된 창고 — 뭐가 어디 있는지 아무도 모름 |

## 깊이 이해

### 왜 레이크가 필요했나 (DW의 한계 — 수치로 이해)
- DW는 테이블을 만들기 전에 컬럼·타입을 확정해야 한다. 로그 스키마에 필드 하나가 추가되면 DW는 ALTER TABLE, ETL 코드 수정, 재적재까지 보통 수일이 걸린다.
- 반면 레이크는 JSON·Parquet 원본을 그대로 객체 스토리지에 넣기만 하면 되므로, 스키마 변경 자체가 "새 필드가 파일에 섞여 들어옴" 수준으로 즉시 반영된다. 스키마가 주 단위로 바뀌는 클릭 로그·센서 데이터일수록 이 차이가 누적 비용을 크게 벌린다.

### 저장 포맷과 용량 — 구체 수치
- 예: 하루 5TB의 웹 로그를 원본 CSV(텍스트) 그대로 저장하면 5TB가 그대로 쌓인다. 이를 컬럼 지향 포맷인 **Parquet + Snappy 압축**으로 저장하면 컬럼 단위 압축·인코딩 효과로 대략 30~70% 절감되어 1.5~3.5TB 수준으로 줄어든다.
- 조회 시에도 효과가 있다: 전체 20개 컬럼 중 2개만 쓰는 쿼리라면, CSV는 행 전체(모든 컬럼)를 읽어야 하지만 Parquet는 해당 2개 컬럼 블록만 읽으므로 이론상 I/O가 1/10 수준으로 줄어든다.

### 파티션과 조회 범위 축소 — 워크드 예제
- 1년치(365일) 로그가 날짜 파티션 없이 한 폴더에 있으면, "어제 데이터만" 조회해도 엔진은 전체 파일 목록을 스캔해야 할 수 있다.
- `year=2026/month=07/day=03/` 형태로 날짜 파티션을 적용하면, 특정 날짜를 찾는 쿼리는 365개 파티션 중 1개(약 0.27%)만 스캔하면 된다. 이것이 partition pruning이다.

### Zone 구조로 품질을 계층화하는 이유
- Raw(Bronze) → Curated(Silver) → Analytics(Gold) 3단 구조는 "원본 보존"과 "활용 편의성"을 동시에 만족시키기 위함이다. Raw는 원본을 손대지 않아 재처리·감사가 가능하고, Silver는 중복 제거·타입 정제를 거치며, Gold는 BI 도구가 바로 쓸 집계 테이블이다.
- 예: 원본 로그에 결측치·중복이 15% 섞여 있어도 Raw Zone에는 그대로 두고, Silver Zone에서 정제 규칙(품질 통과율 목표 99%)을 적용해 걸러낸다 — Raw를 건드리지 않으므로 정제 로직에 버그가 있어도 원본에서 다시 시작할 수 있다.

### 데이터 늪으로 전락하는 판별 기준
- 레이크가 늪이 되는 조건은 "저장량"이 아니라 "찾을 수 있는가"다. 예를 들어 카탈로그 등록률이 30%뿐이라면, 나머지 70%는 파일이 존재해도 검색·활용이 불가능해 사실상 죽은 데이터가 된다.
- 판별 기준 예: 카탈로그 등록률 95% 미만, 소유자(owner) 미지정 테이블 다수, 수명주기(lifecycle) 정책 없이 무기한 보관 — 이 세 조건이 겹치면 늪으로 진단한다.

### 비유와 흔한 오해
- **비유**: 빗물·강물·지하수를 종류 구분 없이 일단 호수에 모아두고, 이후 용도(식수·농업·공업)에 맞게 정수·분류하는 것과 같다. 정수 안 된 물을 무작정 마시면 안 되듯, 레이크의 Raw 데이터도 카탈로그·품질 규칙 없이 바로 신뢰하면 안 된다.
- **오해 1**: "레이크는 그냥 파일 저장소다" — 아니다. 카탈로그·접근권한·품질 등급·수명주기 정책이 없는 저장소는 레이크가 아니라 늪이다.
- **오해 2**: "레이크가 있으면 DW는 필요 없다" — 아니다. 정형 KPI·고정 리포트처럼 스키마가 안정적인 영역은 여전히 DW(또는 레이크하우스)가 유리하다.

## 연결 개념
- 데이터 웨어하우스(DW): schema-on-write로 미리 모델링하는 대조 개념
- 데이터 레이크하우스: 레이크 저장소에 ACID 트랜잭션과 테이블 관리를 더한 상위 발전 구조 (144에서 상세)
- 메달리온 아키텍처(Bronze/Silver/Gold): 레이크 품질을 계층으로 관리하는 표준 패턴

# 📝 【답안용】 시험 답안 템플릿

> 목적: 시험장에서 25분에 그대로 쓰는 답안 양식. 작성방식(추상표현 금지·수치·도식·문제유형 전환)을 엄격히 지킨다.
> 핵심: 데이터 레이크 답안은 대용량 저장소가 아니라 schema-on-read, 거버넌스, 데이터 늪 방지 방안을 포함해야 한다.

## 핵심 인사이트 (3줄 요약)

> 1. **본질**: 데이터 레이크는 다양한 형식의 원시 데이터를 저비용 저장소에 수집하고 읽을 때 스키마를 적용하는 구조이다.
> 2. **가치**: 로그·IoT·문서·이미지 등 사전 모델링이 어려운 데이터를 분석·ML 실험에 활용한다.
> 3. **판단 포인트**: 저장보다 카탈로그, 품질 등급, 접근통제, 수명주기 정책이 데이터 늪 방지의 기준이다.

## 출제 의도 및 답안 포인트

| 출제 의도 | 반드시 짚을 핵심 | 감점 회피 포인트 |
|:---|:---|:---|
| DW와 레이크 차이 확인 | schema-on-read, 원시 데이터, 객체 스토리지 | 단순 파일 저장소로 설명 |
| 빅데이터 처리 구조 이해 | Spark, Parquet, partition, catalog | 처리 엔진과 메타데이터 누락 |
| 거버넌스 판단 | 권한, 품질 등급, lineage, lifecycle | 데이터 늪 리스크 미기재 |

> 요약: 데이터 레이크 문제는 저장 확장보다 원시 데이터 활용과 거버넌스 통제 구조를 요구한다.

## Ⅰ. 개요 및 필요성

- 개요: 데이터 레이크는 원시 데이터 중심 분석 저장 구조이다.
- 배경: 로그, JSON, 이미지, 센서 데이터는 정형 테이블로 먼저 모델링하기 어렵고 분석 시점에 스키마 적용이 필요하다.
- 필요성: ML, 탐색 분석, 장기 보관 요구를 수용하기 위해 객체 스토리지 기반 DW 보완 구조로 활용된다.

---

## Ⅱ. 구조 및 구성요소

```text
Source -> Ingestion -> Raw Zone -> Curated Zone -> Analytics / ML
                    +-> Catalog / Lineage
                    +-> Access Control / Lifecycle
```

| 구성요소 | 역할 | 특이사항 |
|:---|:---|:---|
| Object Storage | 원시·가공 데이터 저장 | S3, ADLS, GCS, HDFS |
| Ingestion | 배치·스트림 수집 | Kafka, Flume, Glue, Dataflow |
| Processing Engine | 정제·변환·분석 | Spark, Flink, Trino |
| Catalog | 메타데이터와 검색 | Hive Metastore, Glue Catalog |

> 요약: 데이터 레이크는 저장소, 수집, 처리 엔진, 카탈로그를 분리해 다양한 데이터를 수용한다.

---

## Ⅲ. 동작원리 및 흐름도

```text
원천 수집 -> 원시 저장 -> 메타데이터 등록 -> 스키마 적용 읽기
-> 정제 / 변환 -> 분석 / ML 제공 -> 수명주기 관리
```

| 단계 | 처리 내용 | 검증 기준 |
|:---:|:---|:---|
| 1 | 파일·로그·스트림을 Raw Zone에 적재 | 적재 누락 0건, checksum |
| 2 | 파티션, 포맷, 스키마 정보를 catalog에 등록 | partition discovery |
| 3 | Spark/Trino가 schema-on-read로 분석 | query failure rate 1% 이하 |
| 4 | Curated Zone으로 정제 후 ML·BI 제공 | 품질 규칙 통과율 99% |

> 요약: 데이터 레이크는 원시 저장 후 메타데이터를 붙이고, 분석 시점에 스키마를 적용해 활용한다.

## Ⅳ. 특징

| 구분 | 데이터 웨어하우스 | 데이터 레이크 | 수치·판단 포인트 |
|:---|:---|:---|:---|
| 스키마 | schema-on-write | schema-on-read | 변경 빈도 높은 JSON·로그에 적합 |
| 데이터 | 정형·정제 중심 | 정형·반정형·비정형 | 파일, 이벤트, 이미지 수용 |
| 저장 비용 | 고성능 분석 DB 비용 | 객체 스토리지 GB당 비용 | cold tier 수명주기 적용 |
| 위험 | 모델 변경 비용 | 데이터 늪 | catalog coverage 95% 이상 |

> 요약: 데이터 레이크는 데이터 형태 수용 범위가 넓지만, 메타데이터와 품질 관리 없이는 분석 신뢰도가 하락한다.

|:---|:---|:---|:---|
| 구조 | DW 선모델링 | 원시 저장 후 해석 | 스키마 변경 주 1회 이상 |
| 비용/성능 | 분석 DB에 원시 데이터 보관 | 객체 스토리지+분산 처리 | 원시 로그 일 1TB 이상 |
| 운영/위험 | 품질 기준 명확 | 품질 등급 분산 | catalog, zone, lifecycle 필수 |

> 요약: 데이터 레이크는 원시 대용량 데이터와 탐색 분석에 맞고, 정형 KPI는 DW 또는 레이크하우스와 결합한다.

| 리스크 | 원인 | 대응 방안 | 확인 지표 |
|:---|:---|:---|:---|
| 데이터 늪 | 소유자·스키마·품질 미등록 | catalog mandatory, owner 지정 | catalog 등록률 95% 이상 |
| 비용 증가 | 무제한 보관, 중복 파일 | lifecycle, compaction, 중복 탐지 | 월 저장 증가율, 중복률 |
| 권한 오남용 | 파일 단위 접근통제 미흡 | IAM, Lake Formation, Ranger | 권한 위반 0건, audit log |

> 요약: 레이크 운영은 저장보다 메타데이터, 비용, 접근통제 지표를 지속 점검해야 한다.

| 점검 항목 | 목표 기준 | 측정 방법 |
|:---|:---|:---|
| 메타데이터 | catalog 등록률 95% 이상 | catalog scan |
| 품질 | Curated Zone 품질 규칙 통과율 99% | Great Expectations, DQ job |
| 비용 | 미사용 데이터 cold tier 90일 이동 | storage analytics |

> 요약: 데이터 레이크의 성공 기준은 저장량이 아니라 등록률, 품질 통과율, 비용 통제율이다.

## Ⅵ. 실무 적용 및 결론

**적용 방안 3개 (필수 — 단계별 또는 항목별):**
1. Raw, Curated, Analytics Zone을 분리하고 Parquet+Snappy, 날짜·업무 파티션으로 일 1TB 이상 로그를 저장
2. Glue Catalog/Hive Metastore에 owner, schema, retention, PII 등 메타데이터를 필수 등록하고 catalog coverage 95% 이상 유지
3. IAM/Ranger 기반 권한, 90일 cold tier lifecycle, 월 1회 중복 파일 compaction으로 비용·권한 리스크 통제

**결론 (2줄):**
- 기술사 판단: 원시·비정형·ML 데이터 수용이면 데이터 레이크, 감사 가능한 KPI 분석이면 DW 또는 레이크하우스 선택
- 향후 방향: 데이터 레이크는 ACID 테이블 포맷과 메달리온 아키텍처를 통해 레이크하우스로 확장
