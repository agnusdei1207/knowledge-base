# 📖 【암기용】 개념 완전 이해

## 한눈에
- **개요**: 정형, 반정형, 비정형 등 모든 종류의 원시 데이터(Raw Data)를 가공하지 않고 원본 형태 그대로 대규모로 저장하는 중앙 집중식 저장소다.
- **왜 필요한가**: 데이터 웨어하우스(DW)는 스키마를 먼저 정의하고 정제된 데이터만 넣어야 해서 새 유형의 데이터(로그, 이미지, 센서 데이터)를 수용하기 너무 느리고 비싸다.
- **핵심 직관**: 정수된 물만 병에 담아 파는 생수 공장(DW)과 달리, 산에서 내려오는 계곡물, 빗물, 지하수를 가리지 않고 거대한 호수(Lake)에 일단 다 받아두고, 필요할 때 퍼서 각자 용도에 맞게 정수해 쓰는 구조다.

## 핵심 용어 정리

| 용어/표기 | 의미 | 비유·예 |
|:---|:---|:---|
| 데이터 레이크 (Data Lake) | 모든 종류의 원시 데이터를 저장하는 무한한 저장소 | 거대한 저수지 |
| 원시 데이터 (Raw Data) | 추출 후 변환이나 필터링을 거치지 않은 원본 데이터 | 정수되지 않은 빗물 |
| Schema-on-Read | 데이터를 저장할 때는 그냥 두고, 읽을(분석할) 때 구조를 부여하는 방식 | 쓸 때 모양 맞추기 |
| 데이터 늪 (Data Swamp) | 관리가 안 되어 어떤 데이터가 있는지 모르는 방치된 데이터 레이크 | 오염된 늪지대 |
| 클라우드 객체 스토리지 | 데이터 레이크의 주 저장소 (Amazon S3, HDFS 등) | 저렴한 초대형 창고 |

## 깊이 이해
- **배경·문제의식**: 모바일 기기, IoT, 소셜 미디어의 발달로 기업이 처리해야 할 비정형/반정형 데이터가 폭증했다. 기존 DW의 엄격한 ETL 과정과 비싼 스토리지 비용으로는 이 모든 데이터를 감당할 수 없었다.
- **작동 원리**: 데이터를 가져와 AWS S3 같은 분산 객체 스토리지에 그대로 저장(ELT 혹은 EL)한다. 이때 RDB처럼 테이블 구조(Schema-on-Write)를 강제하지 않는다. 분석가나 데이터 사이언티스트가 분석 툴(Spark, Athena)을 사용해 데이터를 꺼내어 읽을 때 구조를 적용(Schema-on-Read)하여 분석한다.
- **비유**: 여행 다녀와서 찍은 수천 장의 사진, 동영상, 영수증, 메모를 일단 '하드디스크 새 폴더'에 전부 복사해두는 것이다. 나중에 인스타그램용, 블로그용으로 필요할 때 꺼내서 보정(변환)한다.
- **구체 예시**: AWS S3에 JSON 형식의 웹 클릭 로그, CSV 형태의 센서 데이터, 원본 이미지 파일을 계층적 폴더(년/월/일) 구조로 쌓아두고, AWS Glue(카탈로그)와 Athena로 필요할 때 쿼리한다.
- **흔한 오해·주의점**: "DW를 대체하는 기술이다" -> 틀렸다. 레이크는 원시 데이터 탐색 및 머신러닝에 적합하고, DW는 정형화된 빠른 BI 집계에 적합하여 보통 함께(하이브리드) 사용된다.

## 연결 개념
- 스키마 온 리드 (Schema-on-Read) — 데이터 레이크의 핵심 저장/조회 패러다임
- 하둡 (Hadoop HDFS) — 초기 데이터 레이크를 구현했던 분산 파일 시스템 기술
- 데이터 늪 (Data Swamp) — 데이터 카탈로그 및 거버넌스 부재로 레이크가 통제 불능이 되는 현상

# 📝 【답안용】 시험 답안 템플릿

## 핵심 인사이트 (3줄 요약)

> 1. **본질**: 데이터의 형식(정형/반정형/비정형)에 구애받지 않고 원천 시스템의 원시 데이터(Raw Data)를 그대로 보존하는 대규모 중앙 집중식 스토리지 아키텍처다.
> 2. **가치**: 값비싼 ETL 사전 작업 없이 신속하게 데이터를 적재하며, 데이터 사이언티스트에게 탐색적 데이터 분석(EDA)과 머신러닝을 위한 거대한 원형 데이터를 제공한다.
> 3. **판단 포인트**: 데이터 레이크의 최대 리스크는 데이터 거버넌스 부재로 인한 '데이터 늪(Data Swamp)' 현상이므로, 구축 시 데이터 카탈로그와 메타데이터 관리가 필수적이다.

## 출제 의도 및 답안 포인트

| 출제 의도 | 반드시 짚을 핵심 | 감점 회피 포인트 |
|:---|:---|:---|
| 빅데이터 저장 아키텍처 특성 이해 확인 | Schema-on-Read, 비정형 데이터, 데이터 늪(Data Swamp), ELT | DW 특성(Schema-on-Write)과 혼동, 메타데이터 관리의 중요성 누락 |

> 요약: 기존 DW의 한계를 극복하는 Schema-on-Read 특성과 원시 데이터 보존의 이점을 서술하고, Data Swamp 방지 대책을 요구한다.

## Ⅰ. 개요 및 필요성

- 개요: 데이터 레이크는 구조화된 데이터부터 비구조화된 데이터까지 기업의 모든 원시 데이터(Raw Data)를 가공 없이 한곳에 저장하는 거대한 데이터 리포지토리다.
- 배경: 모바일, IoT, 로그 데이터 등 비정형/반정형 데이터의 폭증으로 기존 DW의 엄격한 Schema-on-Write 방식과 비싼 스토리지로는 확장이 불가능해짐
- 필요성: 미처 활용도를 알지 못하는 데이터를 사전 정의 없이 저비용으로 적재하고, AI/ML 및 탐색적 분석을 수행할 유연한 플랫폼 필수

---

## Ⅱ. 구조 및 구성요소

```text
Data Sources -> Data Ingestion -> Data Lake (Object Storage) -> Data Catalog -> Analytics / ML
(모든 형식)     (Kafka/배치)       (Raw, 정제된 영역 분리)      (메타데이터)     (Spark/Athena)
```

| 구성요소 | 역할 | 특이사항 |
|:---|:---|:---|
| Data Ingestion | 스트리밍 및 배치 방식으로 원시 데이터를 레이크로 이관 | AWS Kinesis, Apache Kafka |
| Object Storage | 파일 시스템 기반 무한 확장이 가능한 저비용 주 저장소 | AWS S3, HDFS, Azure ADLS |
| Data Catalog | 저장된 파일의 위치, 스키마 형태, 계보 메타데이터 관리 | Data Swamp 방지의 핵심 |
| Compute Engine | 레이크에 저장된 데이터에 Schema-on-Read로 접근하여 분석 | Apache Spark, Presto |

> 요약: 스토리지와 컴퓨팅 자원을 물리적으로 분리하여 스토리지 확장 비용을 최소화하고 유연한 컴퓨팅 툴 연동을 지원한다.

---

## Ⅲ. 동작원리 및 흐름도

```text
원시 데이터 그대로 수집 -> 객체 스토리지 적재 -> 카탈로그/메타데이터 등록 -> 필요시 스키마 부여(읽기) -> 분석/머신러닝
```

- 1단계 [무가공 수집]: 정형(DB), 반정형(JSON, XML), 비정형(이미지, 텍스트) 데이터를 별도 변환(Transform) 없이 그대로 수집
- 2단계 [적재(ELT)]: 수집된 데이터를 클라우드 객체 스토리지에 파티션 규칙(년/월/일 등)에 따라 적재(Load)
- 3단계 [메타 등록]: 새로 적재된 파일의 형태와 스키마를 크롤링하여 Data Catalog에 논리적 테이블로 등록
- 4단계 [Schema-on-Read]: 분석 시점에 컴퓨팅 엔진이 카탈로그를 참조하여 파일에 스키마를 투영하고 쿼리 실행

> 요약: 적재 단계의 병목을 없애 모든 데이터를 일단 보존하고, 분석 목적이 구체화된 시점에 읽어 들이면서 구조를 적용한다.

---

## Ⅳ. 특징
- Schema-on-Read (읽기 시 스키마 부여): 데이터 구조를 저장 시점이 아닌 읽는(분석하는) 시점에 정의하여 적재 속도 극대화
- 다양한 데이터 포맷 수용: RDBMS 데이터뿐만 아니라 로그, SNS 텍스트, 이미지, 오디오 등 비정형 데이터 원형 유지
- 저비용 대용량 확장성: HDFS나 클라우드 객체 스토리지를 사용하여 DW 대비 스토리지 비용을 기가바이트당 획기적으로 절감
- 컴퓨팅과 스토리지 분리: 스토리지만 독자적으로 무한 확장 가능하며, 쿼리가 필요할 때만 컴퓨팅 자원을 할당(Serverless 분석)

> 요약: 데이터 레이크는 저비용, 유연성, 비정형 데이터 수용력이라는 장점 덕분에 머신러닝 파이프라인의 핵심 인프라가 되었다.

## Ⅴ. 심화 비교 및 적용 판단

| 비교 축 | Data Warehouse | Data Lake | 선택 기준 |
|:---|:---|:---|:---|
| 데이터 구조 | 사전 정의된 스키마 (정형 위주) | 구조 없이 파일로 저장 (정형/반정형/비정형) | 분석 대상 데이터의 성격 |
| 스키마 적용 시점 | Schema-on-Write (적재 시) | Schema-on-Read (조회 시) | 적재 속도 vs 쿼리 성능 |
| 주 사용자 | 비즈니스 분석가 (BI/SQL) | 데이터 사이언티스트 (ML/탐색적 분석) | 데이터 활용 목적 및 기술 수준 |

> 요약: 정해진 지표의 빠른 집계(BI)에는 DW를 선택하고, 알려지지 않은 패턴 탐색 및 ML 모델 학습에는 Data Lake를 선택한다.

**리스크·대응 (기본 불릿):**
- 데이터 늪 (Data Swamp): 메타데이터 관리 부재로 방치된 쓰레기 데이터 양산 → Data Catalog 의무 도입 및 데이터 거버넌스(수명주기, 접근권한) 통제 적용 (지표: 카탈로그 미매핑 파일 비율)
- 보안 및 권한 제어 부족: 세밀한 컬럼 수준 권한 제어 어려움 → IAM 기반 객체 접근 제어 및 통합 보안 계층(Lake Formation) 적용 (지표: 비정상 데이터 접근 탐지 건수)
- 성능 저하 문제: 무수히 많은 작은 파일(Small Files)이 조회 성능을 저하시킴 → 주기적인 파일 컴팩션(Compaction) 처리 및 Parquet 등 컬럼형 포맷 적용 (지표: 쿼리 I/O 대기 시간)

**도입 후 점검 지표 (기본 불릿):**
- 성능/효율: Cold 데이터를 저렴한 아카이브 스토리지로 이동시키는 수명주기 정책(Lifecycle Policy) 반영률 90% 이상 — 스토리지 비용 최적화 점검
- 품질/운영: 스토리지에 적재된 파일 중 데이터 카탈로그에 등록된 논리 테이블 비율 95% 이상 — 메타데이터 관리 시스템 점검

## Ⅵ. 실무 적용 및 결론

**적용 방안 3개:**
1. 존(Zone) 기반 아키텍처 설계: Raw Zone(원본 저장) -> Cleansed Zone(포맷 변환 및 정제) -> Curated Zone(분석 및 집계 완료)으로 계층화하여 데이터 늪 방지
2. 오픈 컬럼형 파일 포맷 적용: JSON/CSV 대신 Apache Parquet, ORC 포맷으로 압축 저장하여 쿼리 스캔량(비용) 획기적 절감 및 속도 향상
3. 데이터 레이크와 DW 연동(Lakehouse): 레이크에 쌓인 원시 데이터를 Spark로 정제한 뒤, 집계 분석이 필요한 데이터만 DW(Redshift, Snowflake)로 이관하는 하이브리드 아키텍처 구축

**결론:**
- 기술사 판단: 비정형 데이터 활용과 AI 모델링을 위해서는 데이터 레이크 도입이 필수이나, 데이터 카탈로그와 존(Zone) 기반 분리가 선행되지 않으면 반드시 '데이터 늪'으로 전락한다.
- 향후 방향: 최근에는 데이터 레이크의 유연성에 데이터 웨어하우스의 트랜잭션(ACID) 처리 능력을 결합한 '데이터 레이크하우스(Data Lakehouse)' 아키텍처로 빠르게 진화하고 있다.

### 🔀 문제 유형별 목차 전환 (이 키워드 출제 시)

| 유형 | 문제 신호어 | Ⅱ·Ⅲ 강조 | Ⅴ·Ⅵ 강조 |
|:---|:---|:---|:---|
| 포괄형 | "설명하시오" | Schema-on-Read 원리와 레이크 구성요소 | 데이터 늪 방지 대책, Parquet 적용 방안 |
| 비교형 | "DW와 비교하시오" | Schema-on-Write vs Read 메커니즘 차이 | 특성 비교표, 하이브리드 아키텍처 설계 제언 |
| 방안형 | "데이터 늪 방지 방안을 제시하시오" | 카탈로그 부재 및 권한 관리 실패 구조 | 거버넌스 적용, Zone 분리, 메타데이터 자동 크롤링 대책 |
