## 핵심 인사이트 (3줄 요약)
- 텍스트, 이미지, 로그, 테이블 등 포맷을 가리지 않고 **기업의 모든 원시 데이터(Raw Data)를 늪지대처럼 일단 무식하게 다 때려 넣고 보는 무한대의 중앙 스토리지**.
- DW(데이터 웨어하우스)가 "표(Table) 모양으로 예쁘게 깎아야만" 저장을 허락했다면, 데이터 레이크는 "일단 그대로 저장하고, 나중에 분석가가 꺼내 읽을 때 알아서 가공해라(Schema-on-Read)"라는 180도 다른 철학을 가짐.
- 싸이월드 사진, 카카오톡 텍스트 등 과거엔 버려졌던 '비정형 데이터'를 머신러닝/AI의 먹이로 삼아 숨겨진 가치를 발굴하기 위한 2010년대 빅데이터 시대의 심장임. (주로 AWS S3나 HDFS를 사용함).

## Ⅰ. 개요 및 필요성
- **개요**: 정형(RDB), 반정형(JSON, 로그), 비정형(이미지, 음성) 데이터를 원래 형태 그대로 저장하는 단일 중앙 집중식 리포지토리(저장소).
- **필요성**: 데이터 웨어하우스(DW)에 데이터를 넣으려면 ETL 변환 과정이 필요하고, 비용이 너무 비쌌음. 그래서 회사들은 CCTV 영상이나 클릭 로그 같은 덩치 큰 데이터는 분석할 엄두도 못 내고 그냥 삭제해 버림. "스토리지(S3) 값이 껌값이 되었으니, 나중에 어떻게 쓸지 몰라도 일단 몽땅 다(Lake) 원본 그대로 저장해 두자!"는 발상에서 시작됨.
---
## Ⅱ. 아키텍처 및 핵심 원리
- **1. 스키마 온 리드 (Schema-on-Read)**:
  - DW (Schema-on-Write): "저장하려면 회원 번호는 숫자 8자리, 이름은 20자 규격에 맞춰서 와!" (저장 전 가공).
  - Data Lake (Schema-on-Read): "규격? 그딴 거 없어. 그냥 로그 파일 통째로 덤프 쳐. 나중에 AI 모델러가 파이썬 코드로 읽어갈 때 그때 구조 맞춰서 해석할게."
- **2. 데이터 늪 (Data Swamp) 현상**:
  - 아무 구조 없이 데이터를 쑤셔 넣다 보니, 결국 3년 뒤에는 "이 'test_123.csv' 파일이 도대체 무슨 데이터야?" 아무도 모르는 쓰레기장(늪)으로 전락함.
  - 이를 막기 위해 데이터 카탈로그(Data Catalog)와 메타데이터 관리가 데이터 레이크 생존의 절대적인 필수 요소가 됨.
- **3. ELT 아키텍처로의 전환**:
  - 과거: 밖에서 변환해서 가져옴 (ETL).
  - 현재: 일단 레이크(S3)에 다 쏟아부어 놓고(Extract, Load), 스파크(Spark) 같은 강력한 엔진으로 레이크 안에서 지지고 볶음 (Transform).

```text
[ 데이터 웨어하우스(DW) vs 데이터 레이크(DL) 비유 ]

 🍱 [ 데이터 웨어하우스 (DW) ] = 정수기 (마시기 좋게 완벽히 정제됨)
 - 비싸고(비용 높음), 깨끗한 물(정형 데이터)만 나옴.
 - 경영진: "오, 깔끔하고 보기 좋군!" (BI 리포트).

 🏞️ [ 데이터 레이크 (Data Lake) ] = 거대한 호수 (있는 그대로 다 때려 넣음)
 - 흙탕물(로그), 나뭇가지(텍스트), 물고기(이미지)가 원형 그대로 다 섞여 있음. 매우 쌈(S3).
 - 데이터 사이언티스트: "내가 파이썬 뜰채로 물고기만 건져서 AI한테 먹여야지!" (머신러닝/AI).
 - 관리 안 하면 썩은 늪(Data Swamp)이 됨.
```

## Ⅲ. 비교 및 연결
| 구분 | 데이터 웨어하우스 (Data Warehouse) | 데이터 레이크 (Data Lake) |
|---|---|---|
| **저장 데이터** | 고도로 정제된 관계형 데이터 (표) | **모든 원시(Raw) 데이터 (로그, 이미지 등)** |
| **처리 방식** | Schema-on-Write (ETL) | **Schema-on-Read (ELT)** |
| **스토리지 비용** | 천문학적으로 비쌈 (기가바이트 당) | **극도로 저렴함 (오브젝트 스토리지 S3)** |
| **주요 소비자** | BI 툴, 데이터 분석가(SQL) | **데이터 사이언티스트, ML 엔지니어 (Python)** |
---
## Ⅳ. 실무 적용 및 기술사 판단
- **데이터 패브릭과 카탈로그 (Data Catalog)**: 실무에서 S3 깡통 하나만 파놓고 데이터 레이크라고 부르면 1년 안에 100% 쓰레기장(Data Swamp)이 됨. 기술사는 반드시 AWS Glue나 Apache Atlas 같은 '데이터 카탈로그'를 도입하여, "이 JSON 파일은 언제 누가 올렸고, 컬럼 구조는 이렇다"는 꼬리표(메타데이터)를 자동으로 붙이도록 아키텍처를 강제해야 함.
- **오브젝트 스토리지(S3)의 한계와 진화**: 데이터 레이크는 보통 클라우드의 S3를 쓰는데, S3는 "방금 올린 파일 중 3번째 줄만 삭제해 줘(UPDATE/DELETE)"라는 기능이 없음(파일 통째로 덮어쓰기만 가능). 그래서 데이터 수정이나 ACID 트랜잭션 처리가 안 되는 치명적 단점이 있었고, 이를 극복하기 위해 '데이터 레이크하우스(Lakehouse)'라는 다음 세대의 아키텍처로 진화하게 됨.
---
## Ⅴ. 기대효과 및 결론
- "미래에 인공지능(AI)이 어떤 데이터를 필요로 할지 모르니, 일단 기업 내의 모든 바이트(Byte) 조각을 가장 싼 곳에 영구 보존하자"는 딥러닝 시대의 필수 인프라 철학.
- BI 리포팅 중심의 정형 데이터 분석 시대를 끝내고, 비정형 데이터 속에서 숨겨진 비즈니스 인사이트와 AI 예측 모델을 뽑아내는 진정한 빅데이터 르네상스를 열어젖힘.
---
### 📌 관련 개념 맵
- Data Warehouse ➡️ 정형 데이터의 한계 ➡️ Data Lake ➡️ Schema-on-Read / Data Swamp ➡️ Data Catalog / Lakehouse

### 📈 관련 키워드 및 발전 흐름도
- DW의 높은 비용 ➡️ Hadoop(HDFS) 기반 Data Lake 대유행 ➡️ 데이터 늪(Data Swamp) 문제 발생 ➡️ 클라우드(S3/Blob) 스토리지로 이전 ➡️ 트랜잭션 처리 부재로 Lakehouse 등장

### 👶 어린이를 위한 3줄 비유 설명
1. 데이터 웨어하우스(DW)는 '정리된 레고 상자'예요. 빨간색 4칸짜리, 파란색 2칸짜리 블록이 예쁘게 분류되어 있어서 바로 로봇을 만들기 편하죠.
2. **데이터 레이크**는 거대한 '잡동사니 창고'예요. 레고뿐만 아니라 찰흙, 물감, 나무젓가락까지 상자째로 일단 다 때려 넣어둔 곳이에요.
3. 보기엔 지저분해 보이지만, 아주 똑똑한 과학자(AI)가 들어가서 찰흙과 나뭇가지를 조합해 상상도 못 했던 멋진 우주선을 만들어낼 수 있는 보물창고랍니다!
