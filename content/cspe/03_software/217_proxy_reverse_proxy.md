# 📖 【암기용】 개념 완전 이해

## 한눈에
- **개요**: 클라이언트와 서버 사이에서 트래픽을 중계하며, 통신을 대리(Proxy)하는 네트워크 애플리케이션 계층 서버
- **왜 필요한가**: 통신 주체를 숨기거나(보안), 캐싱·로드밸런싱 등 중개자 역할을 통해 양 끝단(클라이언트와 서버)의 부하와 복잡성을 줄이기 위함이다.
- **핵심 직관**: 프록시는 "직원들이 바깥 인터넷을 나갈 때 대리하는 문지기", 리버스 프록시는 "외부 고객들이 우리 회사 서버로 들어올 때 대리하는 안내데스크".

## 핵심 용어 정리

| 용어/표기 | 의미 | 비유·예 |
|:---|:---|:---|
| 프록시 (Forward Proxy) | 클라이언트 측에 위치하여 외부 인터넷으로 나가는 요청을 대리 | 학교/회사 사내망 인터넷 필터링 PC |
| 리버스 프록시 (Reverse Proxy) | 서버 측에 위치하여 외부에서 들어오는 요청을 받아 내부 서버로 분배 | Nginx 웹 서버, 안내데스크 직원 |
| 투명 프록시 (Transparent) | 클라이언트 모르게 트래픽을 가로채서 중계 | 통신사 캐시 서버 |

## 깊이 이해
- **배경·문제의식**: 클라이언트와 내부 백엔드 서버가 직접 통신(Direct Connection)하면 보안 위협 노출, 포트 관리 어려움, 스케일 아웃 라우팅 불가능 등 관리 통제가 되지 않는다.
- **작동 원리**:
  - **포워드 프록시**: Client -> Proxy -> Internet. 사용자는 Proxy 주소만 안다. 목적지 서버는 진짜 클라이언트가 누군지 모른다. (캐싱, 접속 차단 용도)
  - **리버스 프록시**: Internet -> Reverse Proxy -> 내부 Server. 외부 사용자는 Proxy 주소만 안다. 내부에 어떤 서버들이 있는지 모른다. (로드밸런싱, SSL 암호화, 캐싱 용도)
- **비유**: 포워드 프록시는 비서(내가 비서에게 "A사 장부 받아와"). 리버스 프록시는 백화점 안내원(고객이 "구두 매장 어디?" 하면 안내원이 내부 매장으로 연결해줌).
- **구체 예시**: 사내망에서 도박 사이트 접속 막는 것은 포워드 프록시. 웹사이트 접속 시 트래픽을 Nginx가 받아서 내부 8080 포트의 Spring 서버나 3000 포트의 Node.js로 분배하는 것은 리버스 프록시.
- **흔한 오해·주의점**: Nginx나 HAProxy를 단순 '웹 서버'로만 인식하지만, 현대 아키텍처에서는 보안(SSL 오프로딩)과 스케일링을 위한 완벽한 '리버스 프록시' 장비로 쓰인다.

## 연결 개념
- 로드 밸런싱 전략
- 서비스 디스커버리
- API 게이트웨이

# 📝 【답안용】 시험 답안 템플릿

## 핵심 인사이트 (3줄 요약)

> 1. **본질**: 클라이언트와 서버 간의 직접 연결을 끊고, 중간에서 요청/응답을 대리하여 통제권과 라우팅 역량을 확보하는 중계 아키텍처다.
> 2. **가치**: 포워드 프록시는 내부 클라이언트의 익명성과 통제를 보장하고, 리버스 프록시는 내부 서버의 보안(IP 은닉), SSL 오프로딩, 로드밸런싱을 전담하여 인프라 유연성을 극대화한다.
> 3. **판단 포인트**: 현대 백엔드 아키텍처에서는 비즈니스 로직과 비기능적 요건(보안, 캐싱, 압축)을 분리하기 위해 리버스 프록시(Nginx, Envoy)를 필수 앞단 계층으로 배치한다.

## 출제 의도 및 답안 포인트

| 출제 의도 | 반드시 짚을 핵심 | 감점 회피 포인트 |
|:---|:---|:---|
| 프록시의 방향성과 아키텍처상 역할 구분 | 포워드(Client 대리) vs 리버스(Server 대리) 배치 차이 | 두 프록시의 적용 목적과 위치를 반대로 서술 |
| 리버스 프록시를 통한 시스템 최적화 역량 | 보안 은닉, SSL Offloading, 캐싱, 로드밸런싱 연계 | 프록시를 단순 패킷 전달기로 치부 |

> 요약: 통신을 대리하여 주체를 은닉한다는 공통점 위에서, 누구를 보호하는지(포워드=클라이언트, 리버스=서버)에 따른 구조 차이를 명확히 해야 한다.

## Ⅰ. 개요 및 필요성

- 개요: 네트워크 통신에서 클라이언트와 서버 사이를 중계하며 보안, 캐싱, 로드밸런싱 등의 부가 기능을 수행하는 대리 서버 시스템
- 배경: 내부 자산의 공인 IP 직접 노출 시 보안 위협 극대화 및 백엔드 애플리케이션의 비기능적 부하(SSL 복호화 등) 가중
- 필요성: 네트워크 토폴로지 은닉, 인증/보안 계층 통합 관리, 트래픽 제어 및 라우팅 유연성 확보

---

## Ⅱ. 구조 및 구성요소

```text
[포워드 프록시] 클라이언트 망 내부 배치
내부 Client -> Forward Proxy -> (인터넷 망) -> 외부 Web Server

[리버스 프록시] 서버 망 앞단 배치
외부 Client -> (인터넷 망) -> Reverse Proxy -> 내부 WAS / DB
```

| 구분 | 주요 역할 | 혜택 및 특이사항 |
|:---|:---|:---|
| 포워드 프록시 (Forward) | 내부 사용자의 아웃바운드 인터넷 트래픽 중계 및 필터링 | 접속 통제(URL 필터링), 클라이언트 IP 은닉 |
| 리버스 프록시 (Reverse) | 인바운드 트래픽을 수신하여 내부 백엔드 인스턴스로 라우팅 | 서버 IP 은닉, 부하 분산, 무중단 배포 |
| SSL Offloading | 리버스 프록시가 SSL/TLS 암호화·복호화 연산을 전담 | 백엔드 WAS의 CPU 연산 부하 획기적 경감 |
| Caching & Compression | 정적 자원 응답 캐싱 및 Gzip 등 응답 데이터 압축 전송 | 응답 지연 단축 및 대역폭 절감 |

> 요약: 포워드 프록시는 조직 내부망의 통제력을 높이고, 리버스 프록시는 서비스 제공자의 방어막이자 분산기 역할을 한다.

---

## Ⅲ. 동작원리 및 흐름도

```text
클라이언트 (외부) -> [HTTPS] -> 리버스 프록시 (SSL 복호화/검사) -> [HTTP] -> 내부 분산 서버
```

- 1단계 [요청 수신]: 리버스 프록시가 클라이언트의 인바운드 트래픽을 80/443 포트로 수신
- 2단계 [검증 및 해독]: SSL 인증서를 기반으로 트래픽을 복호화(Offloading)하고 악성 페이로드 필터링
- 3단계 [라우팅 분석]: HTTP 헤더, URI, 쿠키 정보를 분석하여 적절한 내부 백엔드 서버 그룹 도출
- 4단계 [내부 전달]: 사설 IP망을 통해 평문(HTTP) 형태로 타겟 서버에 로드밸런싱 전달
- 5단계 [응답 가공]: 백엔드 응답을 수신 후 필요 시 캐싱·압축하여 클라이언트에게 암호화 반환

> 요약: 리버스 프록시는 복잡한 암호화와 공통 라우팅 로직을 흡수하여 백엔드가 순수 비즈니스 로직에만 집중하게 만든다.

---

## Ⅳ. 특징
- 아키텍처 디커플링: 클라이언트는 내부 마이크로서비스 구조나 IP 체계를 알 필요 없이 프록시 VIP 하나만 바라봄
- 단일 진입점 통제: 인증, CORS, Rate Limiting 등의 공통 횡단 관심사(Cross-Cutting Concerns)를 프록시 레벨에서 일괄 처리
- 병목 한계: 모든 트래픽이 프록시 노드를 관통하므로, 프록시 장비 자체가 네트워크 병목 및 단일 장애점(SPOF)이 될 수 있음

> 요약: 아키텍처의 복잡성을 낮추고 보안을 높이지만, 프록시 계층 자체의 고가용성 설계가 강제된다.

---

## Ⅴ. 심화 비교 및 적용 판단

| 비교 축 | 포워드 프록시 (Forward Proxy) | 리버스 프록시 (Reverse Proxy) | API 게이트웨이 (API Gateway) | 선택 기준 |
|:---|:---|:---|:---|:---|
| 은닉 대상 | 클라이언트 (Client 보호) | 백엔드 서버 (Server 보호) | 마이크로서비스 토폴로지 | 보호 주체 |
| 주요 기능 | 사이트 차단, 아웃바운드 캐싱 | 인바운드 로드밸런싱, SSL 처리 | 인증/인가, Rate Limit, 프로토콜 변환 | 라우팅 목적 |
| 배치 위치 | 기업 사내망 출구 | 데이터센터 DMZ / 인그레스 앞단 | 마이크로서비스 클러스터 진입점 | 토폴로지 위치 |

> 요약: 프록시의 진화 형태로, 리버스 프록시의 라우팅 기능에 비즈니스 특화 제어를 덧붙인 것이 API 게이트웨이다.

**리스크·대응 (기본은 불릿):**
- X-Forwarded-For 누락: 프록시가 패킷을 재조립하며 원래 클라이언트 IP가 서버에 전달되지 않음 → 프록시 설정에 X-Forwarded-For (또는 Proxy Protocol) 헤더 삽입 의무화 (지표: 백엔드 접근 로그의 출발지 IP)
- 리버스 프록시 SPOF: Nginx 단일 노드 장애 시 전체 인바운드 차단 → Keepalived (VRRP) 기반 Active-Standby 이중화 및 DNS 라운드로빈 구성 (지표: 프록시 Failover 소요 시간)
- SSL 암호화 병목: 프록시 노드의 CPU 연산 한계 도달 → SSL 가속 하드웨어 도입 또는 SSL 종료 후 사설망 통신 신뢰 아키텍처 구성 (지표: 프록시 CPU Utilization)

## Ⅵ. 실무 적용 및 결론

**적용 방안 3개:**
1. 마이크로서비스 사이드카(Sidecar) 패턴 적용: 중앙 집중형 프록시 대신 Envoy 같은 경량 리버스 프록시를 각 서비스 컨테이너 옆에 붙여 서비스 메시(Service Mesh) 통제 구현
2. 무중단 배포(Blue-Green) 라우팅: 리버스 프록시의 Upstream 설정을 동적으로 변경(Reload)하여 사용자 단절 없이 신규 버전 서버로 트래픽 즉시 전환
3. 보안 캐싱 아키텍처: 정적 에셋(이미지, CSS)은 리버스 프록시 레벨에서 캐싱하여 바로 응답하게 하고, 동적 API만 WAS로 흘려보내 백엔드 스레드 고갈 방어

**결론:**
- 기술사 판단: 인프라 아키텍처에서 리버스 프록시 계층 없는 WAS 직접 노출은 보안과 확장성 측면에서 금기이며, 성능 최적화의 1차 관문으로 필수 배치해야 한다.
- 향후 방향: 최근 클라우드 네이티브 환경에서는 정통 웹 서버형 프록시(Nginx)에서, 동적 설정 변경에 최적화되고 클라우드 API와 잘 붙는 차세대 프록시(Envoy, Traefik)로 표준이 이동 중이다.
