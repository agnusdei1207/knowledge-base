## Ⅰ. 개요
- **정의**: 클라이언트와 서버 사이에서 요청을 중계하는 중간 서버로, 방향에 따라 Forward/Reverse로 구분됨
- **배경/필요성**: 클라이언트-서버 직접 통신은 보안 노출, 부하 집중, 캐시 부재 등 운영 한계가 존재함
- **비유**: Forward Proxy는 비서가 대신 전화하는 것, Reverse Proxy는 대표 전화 교환원

| 출제 의도 | 반드시 짚을 핵심 | 감점 회피 포인트 |
|:---|:---|:---|
| Forward vs Reverse 차이와 활용 시나리오 | 보호 대상이 클라이언트인지 서버인지 구분 | Reverse Proxy와 LB의 역할 차이를 명확히 할 것 |

> 요약: 통신 중계를 통해 보안·성능·유연성을 확보하는 중간 계층 기술임

## Ⅱ. 구성요소
```text
[Forward Proxy]                [Reverse Proxy]
Client --> Proxy --> Server    Client --> Proxy --> Server A
  (클라이언트 은닉)                        --> Server B
                                    (서버 은닉)
```

| 구성요소 | 설명 | 비유 |
|:---|:---|:---|
| Forward Proxy | 클라이언트를 대리하여 외부 서버에 요청, 클라이언트 IP를 은닉함 | 비서 대리 전화 |
| Reverse Proxy | 서버를 대리하여 클라이언트 요청을 수신, 백엔드 구조를 은닉함 | 대표번호 교환원 |
| SSL Termination | Reverse Proxy에서 TLS 복호화를 처리하여 백엔드 부담을 경감함 | 현관 보안 검색 |

> 요약: Forward는 클라이언트를, Reverse는 서버를 보호하는 중계 구조임

## Ⅲ. 절차
```text
요청 수신 --> 정책 판단 --> 중계/캐시 --> 응답 반환
```
- 1단계: 요청 수신 — 프록시가 클라이언트(Forward) 또는 외부 요청(Reverse)을 수신
- 2단계: 정책 판단 — 접근 제어, URL 필터링, 인증 등 보안 정책 적용
- 3단계: 중계/캐시 — 캐시 히트 시 즉시 반환, 미스 시 대상 서버로 요청 전달
- 4단계: 응답 반환 — 서버 응답을 클라이언트에 전달하고 필요 시 캐시 저장

> 요약: 수신-정책-중계-반환의 4단계로 요청을 처리함

## Ⅳ. 문제점
- 단일 장애점: 프록시 장애 시 전체 통신 경로가 차단됨
- 지연 추가: 중계 단계가 추가되어 왕복 시간이 증가함
- 설정 복잡도: 다수 백엔드 라우팅 규칙 관리가 운영 부담으로 작용함

> 요약: 가용성, 지연 증가, 운영 복잡도가 주요 과제임

## Ⅴ. 개선방안
1. 단기: Active-Standby 이중화로 단일 장애점 제거
2. 중기: 커넥션 재사용(keep-alive) 및 HTTP/2 멀티플렉싱으로 중계 지연 최소화
3. 장기: 선언적 설정(IaC) 기반 라우팅 규칙 자동 생성으로 운영 부담 경감

> 요약: 이중화, 프로토콜 최적화, 자동화 순으로 문제를 해소함

## Ⅵ. 전망
- 발전 방향: API Gateway와 서비스 메시 사이드카가 Reverse Proxy 역할을 흡수하는 추세
- 기술사적 판단: 제로트러스트 아키텍처에서 프록시 기반 접근 제어가 핵심 요소로 부상함
- 기술사 제언: 보안·성능·운영 요건을 종합한 프록시 계층 설계 표준 수립이 필요
