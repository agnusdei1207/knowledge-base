## 핵심 인사이트 (3줄 요약)
- **프록시(Proxy)**는 "나를 대신해서 요청을 전달해 주는 대리인(중계기)"임. 내가 누구인지 숨기고 싶거나, 회사에서 직원들의 인터넷 접속을 통제할 때 씀.
- **포워드 프록시 (Forward Proxy)**는 '클라이언트(사용자)' 앞에 서서 사용자의 IP를 감춰주는 방패임. (사내망 보안, 우회 접속용).
- **리버스 프록시 (Reverse Proxy)**는 '백엔드 서버' 앞에 서서 서버의 진짜 IP를 감춰주고, 로드밸런싱과 보안을 책임지는 방패임. (Nginx, API Gateway가 대표적).

## Ⅰ. 개요 및 필요성
- **개요**: 클라이언트와 서버 사이에서 중계기 역할을 하는 서버 똔느 소프트웨어. (Forward Proxy와 Reverse Proxy로 나뉨).
- **필요성**: (1) 회사 직원이 야동 사이트에 접속하는 걸 막고 싶다. ➡️ 직원 PC에서 나가는 모든 인터넷 선을 하나의 문지기(Forward Proxy)를 거치게 해서 필터링하자! (2) 우리 회사 서버가 해커에게 직접 IP를 노출 당해 털리는 걸 막고 싶다. ➡️ 서버 앞에 가짜 문지기(Reverse Proxy)를 세워두고, 해커가 문지기를 때리면 뒤에 숨은 진짜 서버로 몰래 전달하게 만들자!
---
## Ⅱ. 아키텍처 및 핵심 원리
- **1. 포워드 프록시 (Forward Proxy - 클라이언트의 대리인)**:
  - 클라이언트 쪽에 위치함.
  - "나 구글에 가고 싶어. 근데 내 IP를 구글에 남기기 싫어."
  - 클라이언트 ➡️ [ 포워드 프록시 ] ➡️ 구글 서버
  - 구글 서버는 요청이 '포워드 프록시'에서 온 줄만 알고, 실제 뒤에 숨은 클라이언트가 누군지 모름(익명성 보장). 사내망에서 외부망으로 나갈 때 보안/캐싱 용도로 씀.
- **2. 리버스 프록시 (Reverse Proxy - 서버의 대리인)**:
  - 백엔드 서버(WAS) 쪽에 위치함. (현대 백엔드 인프라의 필수품).
  - 사용자는 `www.naver.com`을 쳤지만, 실제로 접속한 건 네이버의 '리버스 프록시(Nginx)'임.
  - 클라이언트 ➡️ [ 리버스 프록시 ] ➡️ 백엔드 1번 서버 (진짜 WAS)
  - 사용자는 진짜 뒤에 있는 1번 서버의 IP를 평생 모름. 해커가 공격해도 리버스 프록시만 맞음(서버 보호). 

```text
[ Forward Proxy vs Reverse Proxy 아키텍처 방향 비교 ]

 🛡️ [ Forward Proxy (사용자를 숨겨줌) ]
 👨‍💻 직원 PC (192.168.x.x) ➡️ [ 사내 Forward Proxy ] ➡️ (인터넷) ➡️ 🌐 외부 구글 서버
 * 구글은 직원의 존재를 모른다. 프록시 서버가 접속한 줄 안다. (사용자 익명성)

 🏰 [ Reverse Proxy (서버를 숨겨줌) ]
 🌐 외부 사용자들 ➡️ (인터넷) ➡️ [ Nginx Reverse Proxy (80포트) ] ➡️ 💻 사내 WAS 서버 (8080포트)
                                                                 ➡️ 💻 사내 DB 서버 (3306포트)
 * 사용자는 사내 진짜 서버의 IP나 8080 포트를 모른다. (서버 익명성/보안)
```

## Ⅲ. 비교 및 연결
| 구분 | 포워드 프록시 (Forward Proxy) | 리버스 프록시 (Reverse Proxy) |
|---|---|---|
| **위치** | **클라이언트(사용자) 앞**에 위치 | **서버 앞**에 위치 |
| **누구를 숨기는가?**| **클라이언트(나)**를 숨김 (구글이 내 IP를 모름) | **백엔드 서버**를 숨김 (사용자가 서버 IP를 모름) |
| **주요 목적** | 캐싱, 사내망 접속 통제(야동 차단), IP 우회 | **로드밸런싱, 보안(SSL 해독), 내부 아키텍처 은닉** |
| **대표 소프트웨어**| Squid, 사내 방화벽 장비 | **Nginx, HAProxy, Apache, API Gateway** |
---
## Ⅳ. 실무 적용 및 기술사 판단
- **SSL Termination (오프로딩)의 마법**: 옛날에는 백엔드 서버(Tomcat) 10대가 각각 HTTPS 암호화를 풀고 조이느라 CPU를 엄청 썼음. 기술사는 리버스 프록시(Nginx)를 아키텍처 전면에 세워, **프록시가 사용자들과의 복잡한 HTTPS(인증서) 암호화/복호화 노동을 혼자 다 뒤집어쓰게(SSL Termination)** 만들어야 함. 그리고 프록시 뒷단에 있는 사내망 Tomcat들과는 가벼운 일반 HTTP로 통신하게 설계하면, 백엔드 서버의 CPU 부담을 획기적으로 줄일 수 있음.
- **Nginx 기반의 마이크로서비스 관문 (API Gateway)**: MSA 환경에서는 프론트엔드가 수십 개의 파드 IP를 다 알 수 없음. 그래서 실무에서는 리버스 프록시를 고도화시킨 'API Gateway'를 전면에 둠. 사용자가 `[API Gateway]` 하나만 치고 들어오면, 프록시가 URL을 보고 `/users`면 A파드로, `/orders`면 B파드로 길을 찾아주는 단일 진입점(Single Point of Entry) 역할을 수행함.
---
## Ⅴ. 기대효과 및 결론
- 클라이언트와 서버가 서로의 민낯(진짜 IP와 포트)을 보지 않고 통신하게 만듦으로써, 인터넷 통신의 양방향 익명성과 보안을 확보함.
- 특히 리버스 프록시는 단순히 서버를 숨기는 것을 넘어, 로드밸런싱, 캐싱, 압축, SSL 해독 등 서버가 하기 귀찮고 무거운 인프라 작업들을 앞단에서 다 처리해 주는 현대 클라우드 아키텍처의 필수 '관문(Gateway)'임.

### 👶 어린이를 위한 3줄 비유 설명
1. **프록시**는 '심부름꾼'이에요. 내가 직접 가기 부끄러울 때 대신 다녀와 주는 역할을 해요.
2. **포워드 프록시**는 "나 대신 저 장난감 가게 가서 물건 좀 사 와"라고 시키는 거예요. (가게 사장님은 내 얼굴을 몰라요).
3. **리버스 프록시**는 회사 사장님(진짜 서버)을 지키는 '비서'예요. 손님이 오면 비서가 먼저 응대하고, 필요한 서류만 사장님 방에 몰래 들어가서 결재받아오는 거랍니다! (손님은 사장님 얼굴을 절대 못 봐요).
