## 미리 알고가기

- 문서형은 한 건의 데이터를 JSON 같은 문서 단위로 저장하는 방식임
- 키값형은 고유 키 하나로 값을 바로 찾는 방식임
- 컬럼형은 넓은 테이블을 분산 저장해 대량 쓰기와 집계에 맞춘 방식임
- 그래프형은 정점과 간선으로 관계를 저장해 연결 탐색에 맞춘 방식임

## Ⅰ. 개요

- **정의/개념**: NoSQL 유형은 관계형 데이터베이스처럼 한 가지 구조로 모든 데이터를 다루지 않고, 데이터 모양과 조회 방식에 맞춰 저장 모델을 나눈 비관계형 데이터 저장 방식임
- **배경/필요성**: 속성이 자주 바뀌는 데이터, 대량 세션 데이터, 대규모 로그, 복잡한 관계 데이터는 같은 구조로 처리하면 비효율이 커지므로 업무별로 맞는 저장 방식이 필요함

## Ⅱ. 특징

- 저장 모델이 달라지면 조회 방식과 확장 방식도 함께 달라짐
- 스키마 제약이 약해 데이터 변화에 유연하게 대응하기 쉬움
- 조인과 강한 트랜잭션 기능은 약한 경우가 많아 업무 경계를 분명히 나눠야 함
- 유형을 잘못 고르면 응용 프로그램에서 우회 로직이 급격히 늘어남

## Ⅲ. 종류 및 비교

- **문서형**: 한 문서 안에 관련 속성을 함께 넣어 속성 추가와 화면 중심 조회에 잘 맞음
- **키값형**: 키 하나로 바로 읽고 쓰는 구조라 캐시와 세션 처리에 유리함
- **컬럼형**: 같은 행이라도 필요한 열만 읽기 쉽고 분산 쓰기량을 크게 처리하기 좋음
- **그래프형**: 사람, 상품, 경로처럼 관계를 여러 단계 따라가는 질의에 강함

| 판단 기준 | 문서형 | 키값형 | 컬럼형 | 그래프형 |
|:---|:---|:---|:---|:---|
| 저장 단위 | 문서 | 키와 값 | 행 키와 컬럼 묶음 | 정점과 간선 |
| 잘 맞는 조회 | 객체 단위 조회 | 단건 조회 | 대량 집계와 범위 조회 | 관계 추적과 경로 탐색 |
| 강점 | 속성 변경에 유연함 | 구조가 단순하고 빠름 | 분산 확장에 강함 | 관계 표현이 자연스러움 |
| 주의점 | 큰 문서가 생기기 쉬움 | 조건 검색이 제한됨 | 모델링이 낯설 수 있음 | 범용 집계 업무는 비효율적일 수 있음 |

## Ⅳ. 구성요소 및 구조

| 구성요소 | 설명 |
|:---|:---|
| 데이터 모델 | 문서, 키와 값, 컬럼 묶음, 그래프처럼 저장 단위를 정함 |
| 파티션 기준 | 어떤 키로 데이터를 나눌지 정해 확장성과 쏠림을 좌우함 |
| 복제 정책 | 읽기 성능과 장애 복구 수준을 결정함 |
| 질의 방식 | 키 조회, 문서 조회, 범위 집계, 관계 탐색처럼 접근 방식을 정함 |

```text
+-------------+     +-------------+     +-------------+
| 업무 데이터 성격 | --> | 저장 모델 선택  | --> | 파티션/복제 설계 |
+-------------+     +-------------+     +-------------+
        \                                         |
         \-------------------------------------->|
                  조회 방식과 운영 지표 검증
```

## Ⅴ. 원리 및 절차 흐름도

```text
+-------------+     +-------------+     +-------------+     +-------------+
| 데이터 형태 파악 | --> | 조회 패턴 정리  | --> | 유형별 후보 비교 | --> | 운영 구조 확정  |
+-------------+     +-------------+     +-------------+     +-------------+
```

1. **데이터 형태 파악**: 속성이 자주 바뀌는지, 관계가 많은지, 단건 조회가 중심인지 확인함
2. **조회 패턴 정리**: 단건 조회, 범위 집계, 관계 탐색 중 무엇이 많은지 정함
3. **유형별 후보 비교**: 문서형, 키값형, 컬럼형, 그래프형 중 맞는 구조를 고름
4. **운영 구조 확정**: 파티션 기준, 복제 방식, 일관성 수준을 함께 정함

## Ⅵ. 실무 적용 및 유의점

1. 상품 카탈로그처럼 속성이 자주 바뀌는 데이터는 문서형이 잘 맞지만 문서가 지나치게 커지면 갱신과 전송 부담이 커지므로 문서 크기와 조회 응답 시간으로 구조 적합성을 계속 확인함
2. 추천이나 사기 탐지처럼 관계를 여러 단계 따라가야 하는 업무는 그래프형이 유리하지만 범용 집계까지 한 저장소에 몰면 복잡해지므로 관계 탐색 횟수와 질의 처리 시간으로 역할 분리가 맞는지 점검함

## Ⅶ. 결론

NoSQL 유형의 핵심은 유행하는 제품을 고르는 데 있지 않고 데이터 모양과 조회 패턴에 맞는 저장 모델을 정확히 맞추는 데 있음.
