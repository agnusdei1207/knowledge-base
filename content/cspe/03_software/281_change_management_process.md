# 📖 【암기용】 개념 완전 이해

> 목적: 소프트웨어 변경관리 프로세스를 처음 보는 사람도, RFC부터 CAB·PIR까지 각 용어와 판정 기준을 완전히 이해하게 만든다.

## 한눈에
- **개요**: 변경관리(Change Management)는 **ITSM(IT서비스관리)**의 핵심 프랙티스(ITIL Change Enablement)로, 운영 중인 시스템의 소스·설정·인프라 변경을 **요청 → 평가 → 승인 → 구현 → 검증**하는 통제된 프로세스이다.
- **왜 필요한가**: 구두 승인이나 임의 배포는 영향 분석 없이 실행돼 운영 장애로 직결된다. "누가, 왜, 무엇을, 언제, 어떤 영향으로 바꿨는가"를 기록해야 장애 원인 추적, 롤백, 감사 대응이 가능하다.
- **핵심 직관**: 병원에서 수술 전 동의서·검사·집도의 확인을 거치고, 수술 후 회복을 관찰하는 절차와 같다 — 코드 변경도 사전 승인과 사후 확인이 필요하다.

## 핵심 용어 정리 (내부에 등장하는 것들)

| 용어 | 의미 | 비유 |
|:---|:---|:---|
| 변경관리(ITIL Change Enablement) | 운영 변경을 통제 가능한 워크플로로 관리하는 ITSM 프랙티스 | 병원의 수술 전후 관리 체계 |
| RFC(Request for Change, 변경요청서) | 변경 목적·범위·일정·담당자를 등록하는 신청 문서 | 수술 동의서 |
| 표준변경(Standard Change) | 사전 승인된 저위험·반복 변경 — 자동/즉시 승인 | 정기 검진 |
| 일반변경(Normal Change) | CAB 심사를 거쳐야 하는 변경 | 정밀 진단 후 진행하는 수술 |
| 긴급변경(Emergency Change) | 장애 대응을 위해 절차를 단축해 신속 처리하는 변경(사후 승인 가능) | 응급 수술 |
| CAB(Change Advisory Board, 변경자문위원회) | 일반·고위험 변경을 심사·승인하는 조직 | 수술 승인 위원회 |
| 영향분석(Impact Analysis) | 변경이 서비스·SLA·보안에 미치는 영향을 평가하는 절차 | 수술 전 정밀 검사 |
| 롤백계획 | 변경 실패 시 이전 상태로 되돌리는 절차 | 회복 실패 시 대응 매뉴얼 |
| PIR(Post Implementation Review, 사후검토) | 배포 후 계획 대비 결과를 검토하는 절차 | 수술 후 경과 관찰 |
| MTTR(Mean Time To Repair) | 장애 발생부터 복구까지 평균 소요 시간 | 회복까지 걸리는 평균 시간 |

## 깊이 이해

### 왜 변경관리가 통제 프로세스로 발전했나 (배경)
- 초기에는 운영자가 직접 서버에 접속해 설정을 바꾸는 방식이 흔했다. 이 방식은 영향 분석 없이 실행되므로 "이 변경 때문에 장애가 났는지" 나중에 추정만 가능했다. ITIL, ISO/IEC 20000, CMMI는 이 문제를 해결하기 위해 변경을 RFC 등록부터 사후검토까지 이어지는 워크플로로 표준화했다.

### 변경 유형을 어떻게 판별하는가
- 표준변경: 과거에 100회 이상 무사고로 반복된 저위험 변경(예: 설정값 조정, 정기 배치 스케줄 변경)은 미리 카탈로그에 등록해두고 CI/CD가 자동 승인한다.
- 일반변경: DB 스키마 변경, 신규 기능 배포처럼 영향 범위가 크거나 처음 하는 변경은 CAB 심사를 거친다.
- 긴급변경: P1 장애(서비스 전면 중단) 대응처럼 즉시 조치가 필요한 변경은 먼저 실행하고 사후에 CAB 승인을 받는다.
- 판별 기준은 "위험도 × 반복 빈도"다. 위험도가 낮고 반복 빈도가 높을수록 표준변경으로 밀어 넣어 승인 병목을 줄인다.

### 워크드 예제 — 타임아웃 값 변경의 영향분석
- 결제 API의 타임아웃을 3초에서 5초로 늘리는 변경을 검토한다고 하자. 영향분석에서 확인할 항목: ① p95 응답 지연이 얼마나 늘어나는지, ② 타임아웃 대기 중 재시도가 몰려 트래픽이 폭증하지 않는지, ③ 커넥션이 오래 점유되어 DB 커넥션 풀 사용률이 80%를 넘지 않는지.
- 배포는 카나리(전체 트래픽의 5%)로 먼저 적용하고, 위 세 지표가 기준을 벗어나지 않으면 단계적으로 100%까지 확대한다. 기준을 벗어나면 즉시 롤백계획을 실행한다.

### 변경 실패율을 수치로 판정하기
- 공식: `변경 실패율 = (실패·롤백된 배포 건수 ÷ 전체 배포 건수) × 100`.
- 예: 이번 달 배포 200건 중 12건이 롤백됐다면 변경 실패율 = 12/200×100 = 6%. 목표 기준(15% 이하)을 충족하므로 현재 승인 체계는 적정 수준으로 판단한다. 반대로 실패율이 20%를 넘으면 CAB 심사 기준이나 영향분석 항목을 다시 점검해야 한다.

### 흔한 오해
- 변경관리는 배포 속도를 늦추는 문서 작업이 아니다. 표준변경을 자동 승인으로 분리하지 않고 모든 변경을 CAB에 올리면 승인 대기 시간만 늘어난다. 표준변경 자동화(속도)와 고위험 변경 CAB 심사(안전)를 함께 설계해야 배포 지연과 운영 위험을 동시에 줄일 수 있다.

## 연결 개념
- 형상관리 기준선(280편) — 변경 대상이 되는 버전과 이력을 추적하는 기준
- CI/CD 파이프라인 — 표준변경의 자동 승인·실행·검증을 담당
- ITIL Change Enablement — 변경관리가 속한 상위 운영 프로세스 표준

# 📝 【답안용】 시험 답안 템플릿

> 목적: 시험장에서 25분에 그대로 쓰는 답안 양식. 작성방식(추상표현 금지·수치·도식·문제유형 전환)을 엄격히 지킨다.
> 핵심: 변경 절차 나열이 아니라 위험 등급, 승인 경로, 검증 지표를 연결해 운영 장애를 통제하는 답안으로 구성한다.

## 핵심 인사이트 (3줄 요약)

> 1. **본질**: 변경 관리는 소프트웨어 변경을 요청, 평가, 승인, 구현, 검증, 기록하는 통제 프로세스이다.
> 2. **가치**: 변경 실패율, MTTR, 감사 추적성, 장애 재발률을 지표로 관리한다.
> 3. **판단 포인트**: 표준 변경, 일반 변경, 긴급 변경을 분리하고 위험 등급별 승인과 롤백 기준을 달리해야 한다.

## 출제 의도 및 답안 포인트

| 출제 의도 | 반드시 짚을 핵심 | 감점 회피 포인트 |
|:---|:---|:---|
| 변경 통제 프로세스 이해 확인 | RFC, 영향 분석, CAB, 배포 승인, 사후 검토 | 승인 절차만 쓰고 영향도·롤백 기준 누락 |
| DevOps와 ITSM 균형 판단 확인 | 자동화된 표준 변경과 고위험 변경 심사 분리 | 모든 변경을 수동 CAB로 처리한다고 단정 |
| 운영 장애 예방 역량 확인 | 변경 실패율, MTTR, 배포 후 모니터링 | 변경 이력만 관리하고 검증 지표 누락 |

> 요약: 변경 관리는 승인 체계보다 위험 등급별 검증·롤백·감사 추적을 설계하는 문제가 핵심이다.

## Ⅰ. 개요 및 필요성

- 개요: 변경 관리는 운영 변경을 통제하는 절차이다.
- 배경: 소프트웨어 운영 환경에서는 코드, 설정, DB 스키마, 인프라 변경이 장애 원인이 된다.
- 필요성: 변경요청부터 사후 검토까지 표준화해 변경 실패율 15% 이하, MTTR 30분 이하 같은 운영 목표를 관리해야 한다.

---

## Ⅱ. 구조 및 구성요소

```text
변경 요청 -> 영향 분석 -> 승인/CAB -> 구현/배포 -> 검증/기록
              +-> 위험 등급 분류
              +-> 롤백 계획 수립
```

| 구성요소 | 역할 | 판단 기준 |
|:---|:---|:---|
| RFC | 변경 목적, 범위, 일정, 담당자 등록 | 요구사항·장애번호·릴리스번호 연결 |
| 영향 분석 | 서비스, DB, 보안, SLA 영향 평가 | p95 지연, 오류율, RTO 영향 |
| 승인 체계 | 표준·일반·긴급 변경별 승인 | CAB, 자동 승인, 사후 승인 분리 |
| 검증 기록 | 배포 후 결과와 감사 로그 보관 | 변경 실패율, 롤백 횟수, 승인 이력 |

> 요약: 변경 관리는 RFC와 영향 분석을 중심으로 승인, 실행, 검증 기록을 하나의 추적 체계로 묶는다.

---

## Ⅲ. 동작원리 및 흐름도

```text
요청 접수 -> 위험도 산정 -> 승인 경로 선택 -> 배포 실행 -> 모니터링 -> 종료/재검토
```

| 단계 | 처리 내용 | 검증 기준 |
|:---:|:---|:---|
| 1 | RFC 등록 및 변경 유형 분류 | 표준·일반·긴급 변경 구분 |
| 2 | 영향도와 위험도 평가 | 사용자 수, SLA, 보안 영향 점수 |
| 3 | 승인 및 배포 계획 확정 | CAB 승인, 릴리스 캘린더 충돌 0건 |
| 4 | 배포와 롤백 준비 | 배포 로그, 롤백 스크립트, 백업 시각 |
| 5 | 사후 검증과 PIR 수행 | 오류율 1% 이하, MTTR, 재발 액션 |

> 요약: 변경 관리는 위험도에 따라 승인 경로를 고르고 배포 후 지표로 종료 여부를 판단한다.

## Ⅳ. 특징

| 구분 | 기존 임의 변경 | 변경 관리 프로세스 | 수치·기술 포인트 |
|:---|:---|:---|:---|
| 통제 방식 | 담당자 판단 중심 | RFC와 CAB 기반 승인 | ITIL Change Enablement |
| 추적성 | 배포 로그 단편 보관 | 요청, 승인, 커밋, 배포 이력 연결 | Git SHA, ticket ID |
| 장애 대응 | 장애 후 원인 추정 | 변경 단위별 롤백 계획 보유 | MTTR 30분 목표 |
| 속도 처리 | 모든 변경 동일 절차 | 표준 변경 자동 승인 | low-risk change 24시간 이내 |

> 요약: 변경 관리는 모든 변경을 막는 절차가 아니라 위험 등급별 승인과 검증을 다르게 적용하는 운영 통제이다.

## Ⅴ. 심화 비교 및 적용 판단

| 비교 축 | 기존/대안 | 본 키워드 | 선택 기준 |
|:---|:---|:---|:---|
| 구조 | 릴리스 담당자 수동 승인 | RFC, CAB, 자동화 게이트 | SOX, ISMS-P, 내부감사 요구 |
| 비용/성능 | 승인 대기 증가 | 표준 변경 자동화와 고위험 심사 병행 | 배포 빈도 주 1회 이상 |
| 운영/위험 | 장애 원인 추적 지연 | 변경 단위 감사 로그와 PIR | 장애 재발률 월 1건 이하 |

> 요약: 규제와 배포 빈도가 모두 있는 조직은 자동화된 변경 기록과 위험 기반 승인 체계를 함께 적용한다.

| 리스크 | 원인 | 대응 방안 | 확인 지표 |
|:---|:---|:---|:---|
| 승인 병목 | 모든 변경을 CAB 상정 | 표준 변경 카탈로그와 자동 승인 | 승인 리드타임 4시간 이하 |
| 무단 변경 | 운영 서버 직접 수정 | GitOps, RBAC, 변경 창 통제 | 승인 없는 변경 0건 |
| 롤백 실패 | 복구 절차 미검증 | 배포 전 롤백 리허설 | 롤백 성공률 100% |

> 요약: 변경 관리의 리스크는 승인 과다와 통제 누락이므로 자동 승인과 강제 추적을 동시에 설계한다.

| 점검 항목 | 목표 기준 | 측정 방법 |
|:---|:---|:---|
| 변경 실패율 | 15% 이하 | 배포 건수 대비 장애·롤백 건수 |
| 복구 시간 | MTTR 30분 이하 | incident ticket, APM 타임라인 |
| 감사 추적 | RFC-commit-build-deploy 100% 연결 | ITSM, Git, CI/CD 로그 대조 |

> 요약: 도입 효과는 변경 실패율, MTTR, 감사 추적 연결률로 판단한다.

## Ⅵ. 실무 적용 및 결론

**적용 방안 3개:**
1. 표준 변경 카탈로그를 정의해 설정값, 배치 스케줄, 무중단 배포는 CI/CD 자동 승인으로 처리함
2. 고위험 변경은 CAB에서 SLA 영향, DB 마이그레이션, 개인정보 처리 영향, 롤백 시간을 검토함
3. ServiceNow/Jira, Git SHA, Jenkins/GitHub Actions 배포 로그를 연결해 변경 추적률 100%를 목표로 운영함

**결론 (2줄):**
- 기술사 판단: 규제 산업은 CAB와 감사 로그 중심, 배포 빈도 높은 서비스는 표준 변경 자동화와 정책 게이트 중심으로 설계함
- 향후 방향: 변경 관리는 ITSM 수동 승인에서 GitOps, Policy as Code, DORA 지표 기반 변경 통제로 이동함
