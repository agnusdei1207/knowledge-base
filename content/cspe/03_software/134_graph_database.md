## Ⅰ. 개요
- **정의**: 노드와 엣지로 데이터 간 관계를 직접 저장·탐색하는 관계 중심 데이터베이스
- **배경/필요성**: 소셜 네트워크·추천·지식그래프 등 다대다 관계 탐색 시 RDBMS JOIN 성능 한계가 있음
- **비유**: 지하철 노선도처럼 역(노드)과 노선(엣지)으로 최단 경로를 찾는 것과 유사함

| 출제 의도 | 반드시 짚을 핵심 | 감점 회피 포인트 |
|:---|:---|:---|
| 관계 탐색 최적화 원리 | Index-free Adjacency와 그래프 탐색 알고리즘 | RDBMS JOIN과 그래프 순회 성능 차이 근거 제시 필요 |

> 요약: 노드-엣지 구조로 관계 탐색을 O(1) 인접 참조로 수행하는 DB임

## Ⅱ. 구성요소
```text
Node --[Edge]--> Node
  |                |
Property         Property
```

| 구성요소 | 설명 | 비유 |
|:---|:---|:---|
| Node | 엔티티를 표현하는 정점, 라벨과 속성 보유 | 지하철 역 |
| Edge | 노드 간 관계를 표현하는 간선, 방향·타입·속성 보유 | 노선 구간 |
| Property | 노드·엣지에 부착된 키-값 속성 | 역 이름·구간 소요시간 |
| Index-free Adjacency | 각 노드가 인접 노드를 포인터로 직접 참조하는 저장 방식 | 역마다 연결 역 목록 보유 |

> 요약: 노드-엣지-속성의 그래프 모델을 포인터 기반 인접 참조로 저장함

## Ⅲ. 절차
```text
그래프 모델링 --> 노드/엣지 적재 --> 탐색 쿼리 수행 --> 결과 반환
```
- 1단계: 도메인 엔티티와 관계를 노드·엣지·속성으로 모델링
- 2단계: 노드·엣지를 생성하고 인접 참조 구조로 저장
- 3단계: Cypher·Gremlin 등 그래프 쿼리 언어로 경로·패턴 탐색
- 4단계: 탐색 결과를 서브그래프·경로·집계값으로 반환

> 요약: 모델링-적재-탐색-반환의 4단계로 그래프 질의를 수행함

## Ⅳ. 문제점
- 수평 확장 어려움: 그래프 파티셔닝 시 엣지 절단으로 탐색 성능 저하됨
- 대규모 집계 비효율: 전체 노드 스캔이 필요한 집계 연산에 컬럼 스토어 대비 느림
- 표준화 미흡: 그래프 쿼리 언어가 벤더별로 상이하여 이식성 제약이 있음

> 요약: 수평 확장, 집계 성능, 쿼리 표준화가 주요 과제임

## Ⅴ. 개선방안
1. 단기: 수평 확장 → 커뮤니티 기반 파티셔닝으로 엣지 절단 최소화
2. 중기: 집계 비효율 → 집계 전용 뷰를 별도 컬럼 스토어에 물리화
3. 장기: 표준화 → GQL(ISO/IEC 39075) 표준 채택 및 전환

> 요약: 파티셔닝 최적화, 뷰 물리화, 표준 쿼리 언어로 단계적 개선함

## Ⅵ. 전망
- 발전 방향: 지식그래프·RAG 기반 AI 응용과 결합하여 활용 범위가 확대됨
- 기술사적 판단: 관계 중심 데이터 증가로 그래프 모델링 역량 수요가 지속 성장함
- 기술사 제언: 관계 탐색 깊이·빈도 분석 후 그래프 DB 도입 타당성을 판단할 것을 제언함
