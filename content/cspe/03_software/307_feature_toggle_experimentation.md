# 📖 【암기용】 개념 완전 이해

> 목적: 피처 토글과 실험 플랫폼을 처음 봐도 배포와 공개를 분리하는 원리를 이해하게 만든다. 시험 답안 양식이 아니라, 이해를 위한 설명이다.

## 한눈에
- **개요**: 피처 토글·실험 플랫폼은 **CI/CD**에서 **배포(Deploy)와 공개(Release)를 분리**하는 **Progressive Delivery(점진적 배포)** 기법으로, 이미 배포된 코드의 활성화 여부와 노출 대상을 런타임 설정으로 제어한다.
- **왜 필요한가**: 코드를 배포했다고 모든 사용자에게 즉시 공개하면 장애 범위가 커지고, 기능 효과를 데이터로 검증하기 어렵다.
- **핵심 직관**: 전등 스위치처럼 배선(코드)은 이미 설치해 두고, 대상 사용자와 비율만 조절해 켜는 방식이다.

## 핵심 용어 정리 (내부에 등장하는 것들)

| 용어 | 의미 | 비유 |
|:---|:---|:---|
| Deploy(배포) vs Release(공개) | 코드를 서버에 올리는 것과 사용자에게 보이게 하는 것을 분리하는 개념 — 토글의 존재 이유 | 창고에 신제품을 들여놓는 것과 매대에 진열하는 것의 차이 |
| Progressive Delivery(점진적 배포) | 기능을 일부 사용자부터 단계적으로 넓혀가며 공개하는 배포 전략(상위 개념) | 신제품을 5개 매장에서 먼저 팔아보기 |
| Release Toggle | 미완성 기능을 배포는 하되 숨겨두는 토글 | 완성 전 전시품에 커튼 치기 |
| Ops Toggle | 장애 시 즉시 끌 수 있는 운영용 킬 스위치 | 비상 차단기 |
| Experiment Toggle | A/B 실험군을 나누는 토글 | 신약 임상시험의 대조군·실험군 배정 |
| Permission Toggle | 특정 고객군에게만 기능을 파는 토글 | VIP 전용 라운지 출입증 |
| Rule Engine | 사용자 속성·비율을 보고 어느 variant를 보여줄지 결정하는 엔진 | 규칙대로 뽑는 추첨함 |
| SRM(Sample Ratio Mismatch) | 실험군·대조군 배정 비율이 설계와 다르게 틀어졌는지 검증하는 통계 검정 | 동전 던지기가 50:50이 아니라 70:30으로 나온 걸 발견 |
| Guardrail Metric(보호 지표) | 실험이 목표 지표를 개선해도 절대 악화되면 안 되는 안전 지표(오류율 등) | 신약이 효과 있어도 부작용은 절대 넘으면 안 되는 기준선 |

## 깊이 이해

### 왜 필요했나 (배경 — Deploy와 Release의 분리)
- CI/CD는 배포 빈도를 높이지만, "배포=즉시 전체 공개"라면 새 코드의 버그가 모든 사용자에게 한 번에 노출된다. 예: 하루 10번 배포하는 팀이 매번 100% 즉시 공개하면, 버그 하나가 전체 트래픽에 영향을 준다.
- Feature Toggle은 "코드는 이미 배포됐지만 스위치가 꺼져 있어 아무도 그 경로를 타지 않는" 상태를 만들어, 배포(deploy)와 공개(release)를 분리한다. 이러면 배포 자체의 위험과 기능 공개의 위험을 따로 관리할 수 있다.

### 작동 원리 (SDK가 매 요청마다 판정하는 방식)
- 사용자가 요청하면 Toggle SDK가 사용자 ID를 일관 해시(consistent hashing)해 0~99 사이 숫자로 변환하고, 이 숫자가 토글의 공개 비율(rollout percentage) 미만이면 새 기능을 켠다. 같은 사용자는 항상 같은 해시값을 받으므로, 한 번 A안을 본 사용자는 계속 A안을 본다(실험 일관성 보장).
- 수치 워크드 예제: 결제 UI 개편을 5%로 시작한다고 하자. 하루 사용자 100만 명 중 5만 명이 신규 UI를 본다. 7일간 전환율, 결제 실패율, p95 응답 시간을 신규 vs 기존 그룹으로 비교한다. 결제 실패율이 guardrail 기준(예: 0.1% 초과)을 넘지 않고 전환율이 통계적으로 유의미하게(p-value < 0.05) 개선되면, 5% → 50% → 100% 순으로 확대한다.

### 실험의 판별 원리 — SRM과 Guardrail
- SRM(Sample Ratio Mismatch) 검정: 설계상 50:50으로 나눴는데 실제로는 52:48처럼 사소해 보이는 차이도, 표본이 크면(예: 각 그룹 수만 명) 통계적으로 유의미한 배정 오류를 뜻할 수 있다. 이는 실험 시스템 자체의 버그(예: 특정 브라우저가 한쪽 그룹에 더 잘 걸리는 해시 편향)를 의심해야 하는 신호다. SRM이 발견되면 그 실험의 결과는 신뢰할 수 없다 — 폐기하고 재설계해야 한다.
- Guardrail Metric: 실험의 목표 지표(전환율)만 보면 안 된다. 전환율이 올라가도 오류율이나 p95 응답 시간이 정해진 한계(예: 오류율 0.1%, p95 300ms)를 넘으면, 목표 지표와 무관하게 즉시 실험을 중단(kill switch)한다.

### 토글 부채(Toggle Debt) — 왜 위험한가
- 토글 하나가 늘어날 때마다 코드 경로(if-분기)가 2배로 늘어난다. 토글 3개가 동시에 살아있으면 이론상 2³=8가지 조합을 테스트해야 하는데, 실무에서는 이걸 다 검증하지 못해 예상치 못한 조합에서 버그가 난다.
- 그래서 모든 토글에 owner(담당자)와 expiry(만료일, 예: 60~90일)를 강제하고, 만료된 토글이 남아있으면 CI가 merge를 막는 방식으로 "임시 스위치가 영구 설정이 되는 것"을 방지한다.

### 비유와 흔한 오해
- 비유: 전등 스위치처럼 배선(코드)은 이미 다 깔아뒀고, 스위치를 켜는 대상(방·비율)만 조절한다. 배선 공사(배포)와 불을 켜는 것(공개)은 별개의 행위다.
- 오해 1: 피처 토글은 단순 if문 플래그가 아니다. Release/Ops/Experiment/Permission처럼 목적별로 종류가 다르고, 각각 생명주기(생성→평가→분석→제거)가 다르게 관리돼야 한다.
- 오해 2: 실험에서 전환율만 좋아지면 성공이라고 오해하기 쉽다. Guardrail(오류율, 지연시간)이 함께 지켜지지 않으면 실험은 실패로 간주해야 한다.

## 연결 개념
- Progressive Delivery (피처 토글이 속하는 상위 배포 전략 — 비율 기반 점진적 공개)
- A/B Testing (Experiment Toggle이 구현하는 실험 방법론)
- Canary Deployment/Blue-Green (배포 자체를 점진화하는 인프라 레벨 기법 — 토글은 애플리케이션 레벨)

# 📝 【답안용】 시험 답안 템플릿

> 목적: 시험장에서 25분에 그대로 쓰는 답안 양식. 피처 토글은 릴리스 제어와 실험 검증, 토글 부채 관리까지 포함해 답한다.

## 핵심 인사이트 (3줄 요약)

> 1. **본질**: 피처 토글·실험 플랫폼은 배포된 코드를 사용자 속성·비율·실험군 기준으로 런타임 제어하는 릴리스 통제 체계이다.
> 2. **가치**: 배포와 공개를 분리해 장애 반경을 제한하고, A/B 실험으로 전환율·오류율·지연시간을 데이터로 판단한다.
> 3. **판단 포인트**: 토글 유형, 실험 설계, 지표 수집, 토글 만료일을 함께 관리하지 않으면 코드 복잡도가 누적된다.

## 출제 의도 및 답안 포인트

| 출제 의도 | 반드시 짚을 핵심 | 감점 회피 포인트 |
|:---|:---|:---|
| 릴리스 제어 이해 확인 | Release, Ops, Experiment, Permission toggle | if문 플래그로만 설명 |
| 실험 플랫폼 판단 확인 | 대상군, 무작위 배정, 지표, 통계 검정 | 전환율만 보고 오류율 누락 |
| 운영 부채 관리 확인 | owner, expiry, 제거 자동화 | 오래된 토글 방치 |

> 요약: 답안은 기능 공개 제어와 실험 검증을 분리하고, 토글 생명주기까지 제시해야 한다.

## Ⅰ. 개요 및 필요성

- 개요: 기능 공개를 런타임에 제어
- 배경: CI/CD 환경에서 배포와 사용자 공개를 분리하지 않으면 장애 영향이 전체 사용자로 확산됨
- 필요성: Toggle, Segment, A/B Test로 공개 비율과 실험군을 제어해 전환율·오류율 기준으로 기능 효과를 검증해야 함

---

## Ⅱ. 구조 및 구성요소

```text
User Request -> Toggle SDK -> Rule Engine -> Variant Decision -> App Response -> Event Pipeline
  / Targeting Rule
  / Experiment Metric
  / Admin Console
```

| 구성요소 | 역할 | 특이사항 |
|:---|:---|:---|
| Toggle SDK | 앱 코드에서 정책 평가 | fallback 기본값 필요 |
| Rule Engine | 사용자 속성·비율·variant 결정 | 일관 해시로 군 고정 |
| Admin Console | 토글 생성·승인·만료 관리 | owner, expiry 필수 |
| Event Pipeline | 노출·클릭·전환·오류 수집 | 실험 분석 원천 |

> 요약: SDK가 정책을 평가하고 Rule Engine이 variant를 결정하며 Event Pipeline이 실험 결과를 수집한다.

## Ⅲ. 동작원리 및 흐름도

```text
토글 생성 -> 대상 규칙 설정 -> SDK 평가 -> Variant 노출 -> 이벤트 수집 -> 지표 분석 -> 토글 종료
```

| 단계 | 처리 내용 | 검증 기준 |
|:---:|:---|:---|
| 1 | 토글 목적·owner·expiry 등록 | 만료일 30~90일 |
| 2 | 대상군·비율 설정 | 사용자 ID 해시, 5% 시작 |
| 3 | 런타임 평가·노출 | fallback path 테스트 |
| 4 | 지표 수집·분석 | 전환율, 오류율, p95 latency |
| 5 | 확대·중단·제거 결정 | 통계 유의성, guardrail |

> 요약: 피처 토글은 생성부터 제거까지 생명주기를 갖고, 실험은 노출 지표와 보호 지표를 함께 본다.

## Ⅵ. 실무 적용 및 결론

**적용 방안 3개 (필수):**
1. 토글 생성 시 type, owner, expiry 60일, fallback 값을 필수화하고 CI에서 만료 토글 merge를 차단함.
2. 기능 공개는 1%, 5%, 25%, 50%, 100% 단계로 진행하고 오류율 0.1% 초과 또는 p95 300ms 초과 시 자동 off함.
3. 실험은 노출 이벤트, 전환 이벤트, guardrail metric을 동일 trace ID로 수집하고 SRM·통계 유의성 검정을 적용함.

**결론 (2줄):**
- 기술사 판단: 장애 반경 제어와 제품 실험이 목표이면 토글 플랫폼을 적용하고, 단발성 설정값은 환경 변수로 관리함.
- 향후 방향: 피처 토글은 프로그레시브 딜리버리, 자동 실험 분석, 정책 기반 접근제어와 통합됨.
