## Ⅰ. 개요
- **정의**: 코드 배포와 기능 릴리스를 분리하여 런타임에 기능 활성화 여부를 제어하는 기법임
- **배경/필요성**: 배포와 릴리스가 결합되면 롤백 범위가 넓어지고 A/B 테스트 등 실험이 어려움
- **비유**: 건물의 전등 스위치처럼 배선(배포)은 완료하되 점등(릴리스) 시점을 별도 제어하는 것과 같음

| 출제 의도 | 반드시 짚을 핵심 | 감점 회피 포인트 |
|:---|:---|:---|
| 배포-릴리스 분리 전략과 실험 설계 | 토글 유형(Release/Ops/Experiment/Permission) 구분 | 기술 부채로서의 토글 관리 이슈 언급 필요 |

> 요약: 피처 토글은 배포와 릴리스를 분리하여 기능 노출을 런타임에 제어하는 기법임

## Ⅱ. 구성요소
```text
[Config Store] --> [Toggle Router] --> Feature ON / OFF
                        |
                   [User Context]
                   (ID, segment, %)
```

| 구성요소 | 설명 | 비유 |
|:---|:---|:---|
| Config Store | 토글 상태(ON/OFF)와 조건을 저장하는 중앙 저장소임 | 전등 스위치 패널 |
| Toggle Router | 요청 컨텍스트와 토글 조건을 평가하여 분기하는 로직임 | 자동 조명 센서 |
| User Context | 사용자 ID·세그먼트·비율 등 토글 판단의 입력 정보임 | 방 안 재실자 정보 |
| Experiment Engine | A/B 테스트 트래픽 분배와 통계적 유의성 검증을 수행함 | 임상시험 프로토콜 |

> 요약: Config Store의 토글 상태를 Toggle Router가 사용자 컨텍스트 기반으로 평가·분기함

## Ⅲ. 절차
```text
토글 정의 --> 코드 분기 삽입 --> 점진 활성화 --> 결과 평가/정리
```
- 1단계: 토글 이름·유형·만료 일자·대상 세그먼트를 Config Store에 정의함
- 2단계: 코드에 토글 분기(`if toggle.isEnabled`)를 삽입하고 배포함
- 3단계: 대상 사용자 비율을 점진적으로 확대하며 메트릭을 모니터링함
- 4단계: 실험 결과를 평가하고 토글을 제거(코드 정리)하거나 전면 활성화함

> 요약: 토글 정의 → 코드 삽입 → 점진 활성화 → 결과 평가/정리의 4단계로 운영함

## Ⅳ. 문제점
- 기술 부채 누적: 만료된 토글이 제거되지 않으면 분기 코드가 영구 잔류함
- 테스트 폭발: 토글 조합이 `2^n`으로 증가하여 테스트 커버리지 확보가 어려움
- 설정 오류: Config Store의 잘못된 값이 전파되면 대규모 장애가 발생함

> 요약: 토글 잔류·테스트 조합 폭발·설정 오류가 피처 토글의 주요 리스크임

## Ⅴ. 개선방안
1. 단기: 토글에 만료 일자를 설정하고 CI에서 만료 토글을 자동 경고함
2. 중기: 토글 조합 테스트를 우선순위 기반으로 선별하여 핵심 조합만 검증함
3. 장기: GitOps 기반 설정 관리와 변경 승인 프로세스를 도입하여 설정 오류를 방지함

> 요약: 만료 자동화 → 선별 테스트 → GitOps 설정 관리로 토글 리스크를 통제함

## Ⅵ. 전망
- 발전 방향: 실험 플랫폼이 ML 기반 자동 최적화(MAB 알고리즘)로 발전할 전망임
- 기술사적 판단: Progressive Delivery(308 참조)의 핵심 구성 요소로서 중요성이 증가함
- 기술사 제언: 토글 수를 조직 규모에 비례하여 상한을 관리하고, 정기 청소 프로세스를 수립할 것을 권고함
