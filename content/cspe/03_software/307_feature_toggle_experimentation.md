# 📖 【암기용】 개념 완전 이해

> 목적: 피처 토글과 실험 플랫폼을 처음 봐도 배포와 공개를 분리하는 원리를 이해하게 만든다. 시험 답안 양식이 아니라, 이해를 위한 설명이다.

## 한눈에
- **개요**: 기능 공개 여부와 실험군 배정을 런타임 설정으로 제어하는 플랫폼
- **왜 필요한가**: 코드를 배포했다고 모든 사용자에게 즉시 공개하면 장애 범위가 커지고, 기능 효과를 데이터로 검증하기 어렵다.
- **핵심 직관**: 전등 스위치처럼 코드는 이미 설치해 두고, 대상 사용자와 비율만 조절해 켜는 방식임

## 깊이 이해
- **배경·문제의식**: CI/CD는 배포 빈도를 늘리지만 공개 통제 없이 배포하면 장애와 실험 실패가 전체 사용자에게 노출됨. 실험은 사용자군, 지표, 기간, 통계 검정 기준이 필요함.
- **작동 원리**: SDK가 사용자 ID, 속성, 비율 정책을 평가해 기능 on/off 또는 variant A/B를 결정함. 이벤트 수집 파이프라인이 노출, 클릭, 전환, 오류 지표를 집계함.
- **비유**: 신제품을 전국 판매 전에 5개 매장, 10% 고객에게만 진열하고 판매 데이터를 보고 확대하는 방식과 같음.
- **구체 예시**: 결제 UI 개편을 사용자 5%에 노출하고 전환율, 결제 실패율, p95 응답을 7일간 비교한 뒤 50%, 100%로 확대함.
- **흔한 오해·주의점**: 토글은 임시 제어 장치임. 오래된 토글을 제거하지 않으면 코드 경로가 폭증하고 테스트 조합이 감당하기 어려워짐.

## 연결 개념
- Progressive Delivery: 비율 기반 기능 공개
- A/B Testing: 실험군과 대조군 비교
- Technical Debt: 만료된 토글의 코드 부채

# 📝 【답안용】 시험 답안 템플릿

> 목적: 시험장에서 25분에 그대로 쓰는 답안 양식. 피처 토글은 릴리스 제어와 실험 검증, 토글 부채 관리까지 포함해 답한다.

## 핵심 인사이트 (3줄 요약)

> 1. **본질**: 피처 토글·실험 플랫폼은 배포된 코드를 사용자 속성·비율·실험군 기준으로 런타임 제어하는 릴리스 통제 체계이다.
> 2. **가치**: 배포와 공개를 분리해 장애 반경을 제한하고, A/B 실험으로 전환율·오류율·지연시간을 데이터로 판단한다.
> 3. **판단 포인트**: 토글 유형, 실험 설계, 지표 수집, 토글 만료일을 함께 관리하지 않으면 코드 복잡도가 누적된다.

## 출제 의도 및 답안 포인트

| 출제 의도 | 반드시 짚을 핵심 | 감점 회피 포인트 |
|:---|:---|:---|
| 릴리스 제어 이해 확인 | Release, Ops, Experiment, Permission toggle | if문 플래그로만 설명 |
| 실험 플랫폼 판단 확인 | 대상군, 무작위 배정, 지표, 통계 검정 | 전환율만 보고 오류율 누락 |
| 운영 부채 관리 확인 | owner, expiry, 제거 자동화 | 오래된 토글 방치 |

> 요약: 답안은 기능 공개 제어와 실험 검증을 분리하고, 토글 생명주기까지 제시해야 한다.

---

## Ⅰ. 개요 및 필요성

- 개요: 기능 공개를 런타임에 제어
- 배경: CI/CD 환경에서 배포와 사용자 공개를 분리하지 않으면 장애 영향이 전체 사용자로 확산됨
- 필요성: Toggle, Segment, A/B Test로 공개 비율과 실험군을 제어해 전환율·오류율 기준으로 기능 효과를 검증해야 함

---

## Ⅱ. 구조 및 구성요소

```text
User Request -> Toggle SDK -> Rule Engine -> Variant Decision -> App Response -> Event Pipeline
  / Targeting Rule
  / Experiment Metric
  / Admin Console
```

| 구성요소 | 역할 | 특이사항 |
|:---|:---|:---|
| Toggle SDK | 앱 코드에서 정책 평가 | fallback 기본값 필요 |
| Rule Engine | 사용자 속성·비율·variant 결정 | 일관 해시로 군 고정 |
| Admin Console | 토글 생성·승인·만료 관리 | owner, expiry 필수 |
| Event Pipeline | 노출·클릭·전환·오류 수집 | 실험 분석 원천 |

> 요약: SDK가 정책을 평가하고 Rule Engine이 variant를 결정하며 Event Pipeline이 실험 결과를 수집한다.

---

## Ⅲ. 동작원리 및 흐름도

```text
토글 생성 -> 대상 규칙 설정 -> SDK 평가 -> Variant 노출 -> 이벤트 수집 -> 지표 분석 -> 토글 종료
```

| 단계 | 처리 내용 | 검증 기준 |
|:---:|:---|:---|
| 1 | 토글 목적·owner·expiry 등록 | 만료일 30~90일 |
| 2 | 대상군·비율 설정 | 사용자 ID 해시, 5% 시작 |
| 3 | 런타임 평가·노출 | fallback path 테스트 |
| 4 | 지표 수집·분석 | 전환율, 오류율, p95 latency |
| 5 | 확대·중단·제거 결정 | 통계 유의성, guardrail |

> 요약: 피처 토글은 생성부터 제거까지 생명주기를 갖고, 실험은 노출 지표와 보호 지표를 함께 본다.

## Ⅳ. 특징

| 구분 | 단순 배포 | 피처 토글·실험 | 수치·판단 포인트 |
|:---|:---|:---|:---|
| 공개 방식 | 배포 즉시 전체 공개 | 1%·5%·50% 단계 공개 | 장애 반경 제한 |
| 검증 | 배포 성공 여부 | 전환율·오류율·지연 비교 | guardrail 오류율 0.1% |
| 롤백 | 재배포 필요 | 토글 off 즉시 차단 | 1분 이내 비활성화 |
| 부채 | 코드 경로 단순 | 토글 누적 위험 | 만료 토글 0건 |

> 요약: 토글은 장애 반경과 실험 검증을 제어하지만, 만료 관리 없이는 코드 경로 부채가 증가한다.

## Ⅴ. 심화 비교 및 적용 판단

| 비교 축 | 기존/대안 | 본 키워드 | 선택 기준 |
|:---|:---|:---|:---|
| 릴리스 | Blue/Green 배포 | 사용자 비율 제어 | 기능 단위 공개 필요 |
| 실험 | 로그 사후 분석 | A/B variant 배정 | 제품 지표 검증 필요 |
| 권한 | Role 기반만 사용 | Permission toggle | 고객군별 기능 판매 |

> 요약: 피처 토글은 배포 전략보다 더 세밀한 사용자·기능 단위 공개 제어가 필요할 때 선택한다.

| 리스크 | 원인 | 대응 방안 | 확인 지표 |
|:---|:---|:---|:---|
| 토글 부채 | 만료일 부재 | expiry, owner, CI 경고 | expired toggle 0건 |
| 실험 왜곡 | 사용자군 불균형 | 무작위 배정, SRM 검정 | sample ratio mismatch |
| 장애 확대 | guardrail 미설정 | 오류율·p95 자동 중단 | auto kill switch 횟수 |

> 요약: 토글 운영은 부채, 실험 왜곡, 장애 확대를 owner·검정·자동 중단으로 통제한다.

| 점검 항목 | 목표 기준 | 측정 방법 |
|:---|:---|:---|
| 공개 제어 | 토글 off 1분 이내 반영 | SDK polling, audit log |
| 실험 품질 | SRM p-value 0.01 이상 | 실험 분석 도구 |
| 운영 부채 | 만료 토글 0건 | repo scan, platform report |

> 요약: 공개 반영 시간, 실험 무결성, 만료 토글 수가 플랫폼 운영 점검 기준이다.

---

## Ⅵ. 실무 적용 및 결론

**적용 방안 3개 (필수):**
1. 토글 생성 시 type, owner, expiry 60일, fallback 값을 필수화하고 CI에서 만료 토글 merge를 차단함.
2. 기능 공개는 1%, 5%, 25%, 50%, 100% 단계로 진행하고 오류율 0.1% 초과 또는 p95 300ms 초과 시 자동 off함.
3. 실험은 노출 이벤트, 전환 이벤트, guardrail metric을 동일 trace ID로 수집하고 SRM·통계 유의성 검정을 적용함.

**결론 (2줄):**
- 기술사 판단: 장애 반경 제어와 제품 실험이 목표이면 토글 플랫폼을 적용하고, 단발성 설정값은 환경 변수로 관리함.
- 향후 방향: 피처 토글은 프로그레시브 딜리버리, 자동 실험 분석, 정책 기반 접근제어와 통합됨.
