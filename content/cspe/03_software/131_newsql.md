# 📖 【암기용】 개념 완전 이해

## 한눈에
- **개요**: 관계형 데이터베이스(RDBMS)의 ACID 트랜잭션 보장과 NoSQL의 수평적 확장성을 동시에 제공하는 분산 데이터베이스다.
- **왜 필요한가**: NoSQL은 확장성은 좋지만 복잡한 트랜잭션 처리가 어렵고, 기존 RDBMS는 확장에 한계가 있어 거대 서비스의 금융·결제 데이터를 다루기 어렵다.
- **핵심 직관**: RDBMS와 NoSQL의 장점만 융합해, 데이터가 여러 서버에 나뉘어 있어도 마치 하나의 정합성 있는 데이터베이스처럼 작동하게 만든다.

## 핵심 용어 정리 (내부에 등장하는 것들)

| 용어/표기 | 의미 | 비유·예 |
|:---|:---|:---|
| NewSQL | RDBMS의 정합성과 NoSQL의 확장성을 결합한 분산 DB | "확장이 무한히 되는 오라클 DB" |
| ACID 보장 | 트랜잭션의 원자성, 일관성, 고립성, 지속성 보장 | "계좌 이체 중 실패하면 원상 복구" |
| 수평적 확장 (Scale-out) | 서버(노드)를 추가해 처리 용량을 늘림 | "계산대를 늘려 손님을 더 많이 받음" |
| 분산 합의 알고리즘 | 여러 노드 간의 데이터 일치를 보장하는 기법 (Raft, Paxos) | "결정 전 다수결 투표로 합의" |
| TrueTime API | 구글 Spanner에서 사용하는 GPS/원자시계 기반 시간 동기화 | "전 세계 모든 노드의 시계를 완벽히 맞춤" |

## 깊이 이해
- **배경·문제의식**: 글로벌 스케일의 웹 서비스가 등장하면서 RDBMS의 수직적 확장 한계를 극복하기 위해 NoSQL(Cassandra, MongoDB 등)이 등장했다. 하지만 NoSQL은 최종 일관성(Eventual Consistency)만 보장하므로 결제, 재고 관리 등 강력한 데이터 정합성이 필요한 업무에 적용하기에는 트랜잭션 제어가 너무 복잡해졌다.
- **작동 원리**: NewSQL은 데이터를 자동으로 여러 노드에 분산(Sharding)하고, 노드 간 복제와 트랜잭션을 분산 합의 알고리즘(Raft, Paxos)을 통해 관리한다. 특히 여러 샤드에 걸친 분산 트랜잭션을 2PC(Two-Phase Commit)와 논리적 시계(TrueTime 등)를 결합하여 단일 DB처럼 일관되게 처리한다.
- **비유**: 전통 은행 창구(RDBMS)는 정확하지만 손님이 많아지면 줄이 길어진다. 자율 배식 식당(NoSQL)은 빠르지만 계산이 안 맞을 수 있다. NewSQL은 수백 개의 창구를 두되 본점과 실시간으로 장부를 대조하여 빠르고 정확하게 처리하는 대형 스마트 은행이다.
- **구체 예시**: Google Spanner는 원자 시계와 GPS를 활용한 TrueTime API로 전 세계 데이터센터 간의 트랜잭션 순서를 완벽히 보장하며 10,000 TPS 이상의 분산 결제를 ACID하게 처리한다. CockroachDB는 Raft 알고리즘을 사용해 생존성과 일관성을 확보한다.
- **흔한 오해·주의점**: NewSQL이 기존 RDBMS를 완전히 대체할 수 있다고 오해하기 쉽지만, 조인(Join)이 많은 복잡한 분석 쿼리나 단일 노드 내에서의 단순 트랜잭션은 전통적인 RDBMS가 더 빠를 수 있다. NewSQL은 분산 환경의 네트워크 지연(Latency) 페널티를 감수해야 한다.

# 📝 【답안용】 시험 답안 템플릿

## 핵심 인사이트 (3줄 요약)

> 1. **본질**: NewSQL은 RDBMS의 강력한 트랜잭션(ACID) 지원과 NoSQL의 수평적 확장성(Scale-out)을 결합한 차세대 분산 데이터베이스 아키텍처다.
> 2. **가치**: 마이크로서비스(MSA)와 글로벌 서비스 환경에서 분산 트랜잭션의 복잡도를 DB 엔진 레벨로 숨겨, 애플리케이션 개발자의 생산성과 데이터 신뢰성을 동시에 확보한다.
> 3. **판단 포인트**: 기존 RDBMS의 샤딩 복잡도, NoSQL의 정합성 포기 비용, NewSQL의 도입 비용 및 네트워크 지연을 종합 비교하여 적용을 결정해야 한다.

## 출제 의도 및 답안 포인트

| 출제 의도 | 반드시 짚을 핵심 | 감점 회피 포인트 |
|:---|:---|:---|
| RDBMS와 NoSQL의 한계 극복 원리 확인 | ACID 보장, 수평 확장, 분산 합의(Raft/Paxos), 2PC | RDBMS나 NoSQL의 특징만 나열 |
| 아키텍처 및 핵심 기술에 대한 이해도 검증 | 분산 트랜잭션, 시계 동기화(TrueTime), 자동 샤딩 | 단 수 증가를 성능 향상으로 단정 (지연 존재) |
| 도입 환경 판단 및 적용 역량 평가 | CAP 정리 트레이드오프, 적용 사례 (CockroachDB, Spanner) | NoSQL과 NewSQL 용어 혼용 |

> 요약: NewSQL은 확장성과 일관성의 트레이드오프를 분산 합의 및 글로벌 시간 동기화 기술로 극복한 DB임을 명시해야 한다.

## Ⅰ. 개요 및 필요성

- 개요: RDBMS의 ACID 트랜잭션 속성과 NoSQL의 수평적 확장성을 동시에 만족하는 분산 관계형 데이터베이스
- 배경: 글로벌 서비스 확장에 따라 기존 RDBMS는 스케일업 한계에, NoSQL은 금융·결제 도메인의 정합성 요구 한계에 직면
- 필요성: 글로벌 10,000 TPS 이상의 고성능 결제·주문 트랜잭션을 분산 환경에서 무결하게 처리하기 위해 도입

---

## Ⅱ. 구조 및 구성요소

```text
Client Request -> SQL Engine (파싱/최적화) -> Distributed Execution Plan
                                                |
                                                +-> Transaction Coordinator (2PC, 시간 동기화)
                                                +-> Storage Node (Raft Group) -> 분산 합의/복제
```

| 구성요소 | 역할 | 특이사항 |
|:---|:---|:---|
| SQL Engine | ANSI SQL 지원, 분산 실행 계획 수립 | RDBMS 호환성 제공 |
| Transaction Coordinator | 분산 트랜잭션 관리, 2PC 수행 | 시계 동기화(TrueTime 등) 활용 |
| Distributed Storage | 데이터를 청크 단위로 자동 분할 및 복제 | Raft/Paxos 기반 데이터 일관성 보장 |
| 분산 합의 알고리즘 | 다수결을 통한 노드 간 상태 일치 보장 | 스플릿 브레인 방지 및 고가용성 |

> 요약: NewSQL은 SQL 인터페이스를 유지하면서, 하단 스토리지 계층에 분산 합의와 자동 샤딩을 적용한 구조다.

---

## Ⅲ. 동작원리 및 흐름도

```text
Client Tx 요청 -> 트랜잭션 코디네이터 할당 -> 타임스탬프 기반 순서 부여
-> 관여 노드 2PC 준비(Prepare) -> Raft 다수결 합의 -> 트랜잭션 커밋(Commit) -> 응답
```

- 1단계 [트랜잭션 시작]: 코디네이터가 요청을 수신하고 전역 타임스탬프를 할당해 직렬화 순서 확정
- 2단계 [분산 실행 준비]: 2PC(Two-Phase Commit)의 Prepare 단계로 참여 노드에 잠금 및 로그 기록 요청
- 3단계 [분산 합의]: 각 스토리지 노드의 Raft/Paxos 그룹이 리더 중심 다수결로 로그 복제 합의
- 4단계 [커밋 및 응답]: 코디네이터가 2PC Commit을 지시하여 상태를 확정하고 클라이언트에 결과 반환

> 요약: 분산 환경의 동시성 제어를 위해 논리적 시계와 분산 합의 알고리즘을 2PC에 결합해 일관성을 보장한다.

---

## Ⅳ. 특징
- [ACID 보장]: 금융권 수준의 강한 일관성(Strong Consistency) 유지
- [수평 확장성]: 노드 추가 시 선형적으로 초당 처리량(TPS) 확장
- [SQL 호환성]: 기존 RDBMS 생태계와 높은 호환성 유지 및 마이그레이션 비용 절감
- [지연 시간 한계]: 네트워크 다수결 통신으로 인해 단일 노드 RDBMS 대비 응답 지연(Latency) 발생

> 요약: NewSQL은 글로벌 확장성과 강력한 정합성을 제공하지만, 분산 합의 과정에서 네트워크 지연 페널티가 존재한다.

---

## Ⅴ. 심화 비교 및 적용 판단

| 비교 축 | RDBMS | NoSQL | 본 키워드 | 선택 기준 |
|:---|:---|:---|:---|:---|
| 확장성 | Scale-Up 중심 | 수평적 Scale-Out | 수평적 Scale-Out | 데이터 증가율 및 노드 추가 유연성 |
| 일관성 | 강한 일관성 (ACID) | 최종 일관성 (Eventual) | 강한 일관성 (ACID) | 비즈니스 정합성 중요도 |
| 스키마 유연성 | 엄격한 정적 스키마 | 동적 유연한 스키마 | 정적 스키마 중심 | 데이터 구조 변경 빈도 |

> 요약: 금융/결제 등 ACID가 필수이면서 대규모 확장이 필요한 경우 NewSQL이 최적의 선택지다.

**리스크·대응 (기본은 불릿):**
- [네트워크 파티션 장애]: 노드 간 통신 단절 시 가용성 저하 → 다중 가용영역(Multi-AZ) 분산 배치 및 다수결 정족수 확보 (지표: 클러스터 생존 노드 수)
- [분산 조인 성능 저하]: 노드 간 데이터 이동으로 인한 지연 → 인터리브(Interleave) 테이블 설계로 연관 데이터 동일 노드 배치 (지표: 복합 쿼리 응답 시간)

**도입 후 점검 지표 (기본은 불릿):**
- 성능/효율: 글로벌 트랜잭션 p99 지연 시간 100ms 이하 — 분산 트레이싱 툴 모니터링
- 품질/운영: 리더 노드 장애 시 자동 페일오버 시간(RTO) 10초 이내 — 카오스 엔지니어링 주입 테스트

## Ⅵ. 실무 적용 및 결론

**적용 방안 3개:**
1. 아키텍처 진단: 현재 RDBMS의 수동 샤딩 복잡도 비용과 NewSQL 라이선스/운영 비용의 TCO 정량 비교
2. 데이터 모델링: 분산 트랜잭션을 최소화하도록 바운디드 컨텍스트에 맞춰 파티션 키 및 인터리브 테이블 설계
3. 점진적 마이그레이션: 읽기 전용 쿼리와 비핵심 마이크로서비스부터 시범 적용 후 메인 결제 시스템으로 확대

**결론 (2줄):**
- 기술사 판단: MSA 환경에서 정합성과 확장성 간의 트레이드오프를 해결하는 실용적 대안이나, 분산 합의 지연을 상쇄할 아키텍처 설계가 동반되어야 한다.
- 향후 방향: Cloud Native 트렌드에 맞춰 HTAP(Hybrid Transaction/Analytical Processing)를 지원하는 통합 데이터 플랫폼으로 진화할 것이다.
