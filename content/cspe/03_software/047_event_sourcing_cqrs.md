## 미리 알고가기

- 이벤트 소싱(Event Sourcing): 현재 상태 대신 발생한 상태 변경 이벤트를 순차 기록하는 방식임
- CQRS(Command Query Responsibility Segregation): 읽기(조회) 작업과 쓰기(명령) 작업을 각각 독립된 모델로 분리하는 구조임
- 프로젝션(Projection): 누적된 이벤트를 읽어 조회 목적에 맞춘 데이터 모델로 재구성한 결과임
- 이벤트 스토어(Event Store): 추가만 가능한(Append-only) 구조로 이벤트를 기록하고 조회하는 특화 데이터베이스임
- 스냅샷(Snapshot): 상태 재생 속도를 높이기 위해 특정 시점의 누적 상태를 미리 저장해두는 최적화 기법임
- 결과적 일관성(Eventual Consistency): 일시적으로 일관성이 깨지더라도 시간이 흐르면 최종적으로 모든 복제본이 일치하게 되는 정합성 모델임

## 작성 근거(검토용)

- 이벤트 소싱·CQRS는 저장 기준, 명령·조회 모델, 일관성 부담을 핵심 비교축으로 선정함
- 구성는 명령 처리, 이벤트 저장, 조회 모델 갱신의 데이터 흐름을 중심으로 제시함
- 실무 판단은 이벤트 재생 성공률, 조회 모델 반영 지연, 최신 상태 미반영 조회율로 구체화함
- 전수 검수 완료 근거: 제목, frontmatter, 미리 알고가기, 작성 근거, 본문, 표 헤더·셀, 요약, 결론을 한 줄도 빠뜨리지 않고 확인했으며 어색한 단어·조사·동사 결합·장황한 명사구를 교정함.

## Ⅰ. 개요

- **정의/개념**: 이벤트 소싱은 상태 변화를 이벤트로 저장하고, CQRS는 명령 모델과 조회 모델을 분리하는 아키텍처 패턴임
- **배경/필요성**: 변경 이력 보존과 서로 다른 명령·조회 요구를 단일 CRUD 모델로 충족하기 어려워 저장과 조회 구조를 분리할 필요가 있음

### 쉽게 이해하기 (학습용)
- 통장 잔액을 표시할 때 단순히 현재 잔액만 적는 것과 다르게 입출금 내역을 모두 적는 일지(이벤트 소싱)와, 은행 입구의 창구와 잔액 조회 기계를 따로 두는 구조(CQRS)의 결합임.

## Ⅱ. 특징

- 상태 변경 이벤트를 append-only 로그에 순서대로 저장해 변경 이력과 상태 재생 근거를 남김
- CQRS는 쓰기 규칙과 조회 성능을 서로 다른 모델로 최적화할 수 있음
- 조회 모델은 이벤트 반영이 늦어 최신 상태와 잠시 어긋날 수 있음
- 이벤트 버전 관리와 재생 비용이 커서 단순 업무에는 부담이 됨

### 쉽게 이해하기 (학습용)
- 과거 행동을 차례대로 기록하므로 언제든지 과거의 시점으로 복구하여 상황을 파악할 수 있지만, 조회용 모델에 정보가 반영되기까지 잠깐의 시간차가 발생함.

## Ⅲ. 종류 및 비교

| 판단 기준 | 전통 CRUD | 이벤트 소싱·CQRS |
|:---|:---|:---|
| 상태 저장 방식 | 현재 상태를 최신 값으로 덮어쓰며 저장함 | 상태 변화 이벤트를 시간 순서대로 기록(Append-only)함 |
| 처리 모델 구조 | 하나의 통합 데이터 모델로 읽기와 쓰기를 동시에 처리함 | 명령(쓰기) 모델과 조회(읽기) 모델을 완전히 분리함 |
| 데이터 일관성 | 트랜잭션 완료 즉시 강한 일관성($Strong\ Consistency$)을 가짐 | 비동기 프로젝션에 의한 결과적 일관성($Eventual\ Consistency$)을 가짐 |

> 요약: 현재값 중심 처리는 CRUD, 변경 이력 보존과 명령·조회 분리는 이벤트 소싱·CQRS가 적합함.

### 쉽게 이해하기 (학습용)
- 일반 일기장은 매일의 마지막 기분만 쓰지만, 상세 기록은 감정의 변화를 하나씩 남기고, 글을 쓰는 일과 그 내용을 읽는 행동을 서로 방해받지 않도록 물리적으로 분리함.

## Ⅳ. 설계 요소 및 구조

```text
[명령 수신] ──> [명령 모델] ──(이벤트 생성)──> [이벤트 저장소]
                                                 │
                                                 │ (비동기 전파)
                                                 ▼
[조회 수행] <── [조회 모델] <──(프로젝션) ───────┘
```

| 설계 요소 | 설명 |
|:---|:---|
| 명령 모델 | 비즈니스 규칙을 검증하고 상태 변경 이벤트를 생성함 |
| 이벤트 저장소 | 이벤트를 순서대로 보관해 감사·재생·복구 기준을 제공함 |
| 프로젝션·조회 모델 | 이벤트를 조회 목적에 맞는 데이터 구조로 구성함 |
| 이벤트 버전 관리 | 스키마 변경 후에도 과거 이벤트를 해석할 수 있게 함 |

> 요약: 명령 모델이 만든 이벤트를 저장한 뒤 프로젝션이 조회 모델에 반영함.

### 쉽게 이해하기 (학습용)
- 명령을 접수하는 주체(명령부), 역사를 기록하는 일기장(이벤트 저장소), 일기장을 요약해 보기 좋게 정리하는 비서(프로젝션)가 각자 맡은 역할을 수행함.

## Ⅴ. 원리 및 절차 흐름도

```text
명령 수신 ──> 이벤트 기록 ──> 프로젝션 갱신 ──> 조회 제공
```

1. **명령 수신**: 명령 모델이 비즈니스 명령을 받음
2. **이벤트 기록**: 규칙 검증 후 상태 변경 이벤트를 저장함
3. **Projection 갱신**: 이벤트를 읽기 모델에 반영함
4. **조회 제공**: 클라이언트는 조회에 최적화된 모델을 사용함

> 요약: 상태 변경은 이벤트로 보존하고 조회는 이벤트를 반영한 별도 모델에서 처리함.

### 쉽게 이해하기 (학습용)
- 사용자가 돈을 보내면 거래 사실을 일지에 적어 저장하고, 이를 읽어 통장 정보판을 업데이트하며, 다른 사용자는 업데이트된 정보판을 조회함.

## Ⅵ. 실무 사례

인터넷 은행의 여신 및 수신 계좌 관리 시스템에서 거래 내역을 위변조 불가능한 상태 변경 이벤트로 보존하기 위해 이벤트 소싱 아키텍처를 도입함. 또한 대용량 주문 처리가 빈번한 전자상거래 플랫폼에서 쓰기 성능 지연을 방지하고 조회 성능을 극대화하고자 Kafka와 Redis를 활용하여 명령 모델과 조회 모델을 비동기 프로젝션으로 분리 운영함.

### 쉽게 이해하기 (학습용)
- 증권사 거래 시스템에서 모든 체결 이력을 이벤트로 저장하고, 거래 화면(조회)과 체결 처리(명령)를 분리하여 대량의 조회 요청으로 인한 거래 처리 지연을 방지함.

## Ⅶ. 결론

- 이벤트 소싱과 CQRS는 데이터의 완벽한 변경 이력 감사와 고성능 조회가 요구되는 분산 아키텍처에 적합한 기법임.
- 비동기 전파에 따른 결과적 일관성 지연과 이벤트 데이터의 스키마 변경 시 호환성 제어 방안을 사전에 수립하여 설계 완성도를 확보해야 함.

### 쉽게 이해하기 (학습용)
- 이 구조는 완벽한 이력 추적과 고속 조회가 필요한 대형 웹 서비스에 유용하며, 이벤트 반영 지연 시간과 과거 기록의 스키마 변경 규칙을 명확히 관리하는 것이 핵심임.
