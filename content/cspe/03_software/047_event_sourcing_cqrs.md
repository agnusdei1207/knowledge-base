# 📖 【암기용】 개념 완전 이해

## 한눈에
- **개요**: **이벤트 소싱**은 데이터의 '최종 상태' 대신 '상태를 변경한 이벤트들의 역사'를 저장하는 방식이며, **CQRS**는 상태를 변경하는 모델(명령)과 조회하는 모델(조회)을 완벽히 분리하는 패턴이다. 이 둘은 MSA에서 데이터 동기화와 조회 성능을 극대화하기 위해 보통 짝꿍으로 쓰인다.
- **왜 필요한가**: 은행 계좌 잔액(상태)만 저장하면 "왜 잔액이 이렇게 됐지?"를 추적할 수 없다. 또한 읽기 트래픽(조회 90%)과 쓰기 트래픽(결제 10%)의 요구사항이 다른데 하나의 DB 모델로 처리하면 양쪽 다 병목이 온다.
- **핵심 직관**: 통장 거래 내역(이벤트 소싱). 입금/출금 '내역'을 순서대로 적어두고(Event Store), 필요할 때 내역을 쭉 더해서 현재 잔액(View)을 보여주는 방식이다.

## 핵심 용어 정리

| 용어/표기 | 의미 | 비유·예 |
|:---|:---|:---|
| 이벤트 소싱 (Event Sourcing) | 상태 덮어쓰기 없이, 변경 이벤트들의 불변(Immutable) 스트림만 저장 | 장기판의 기보 (말의 위치 대신 이동 기록) |
| 이벤트 스토어 (Event Store) | 발생한 이벤트를 순서대로 영구 저장하는 추가 전용(Append-Only) 데이터베이스 | 회계 장부의 기입란 |
| CQRS | Command(명령-쓰기)와 Query(조회-읽기)의 책임 분리 | 요리사(쓰기)와 메뉴판(조회)의 분리 |
| Materialized View (구체화된 뷰) | 이벤트 스트림을 구독하여 조회를 위해 미리 만들어둔 읽기 전용 데이터 상태 | 장부 내역을 엑셀로 요약해둔 보고서 |

## 깊이 이해
- **배경·문제의식**: 기존 CRUD 방식은 UPDATE 쿼리로 이전 상태를 지워버리므로 데이터의 히스토리가 소실된다. 또한 복잡한 조회를 위해 JOIN을 남발하면 쓰기 성능까지 저하된다. MSA에서는 도메인 단위로 DB가 쪼개져 있어 여러 도메인의 데이터를 조합해 조회(JOIN)하는 것이 불가능에 가깝다.
- **작동 원리**:
  1. (쓰기) 사용자가 "주문 생성"을 요청하면, 시스템은 상태를 UPDATE하지 않고 "OrderCreatedEvent"를 이벤트 스토어에 추가(Append)한다. (이벤트 소싱)
  2. (동기화) 비동기 메시지 브로커(Kafka 등)가 이 이벤트를 읽기 전용 DB 쪽으로 퍼블리싱한다.
  3. (읽기) 읽기 전용 DB는 이벤트를 받아 자신만의 테이블(또는 NoSQL) 구조로 데이터를 미리 조합해둔다(Materialized View). 클라이언트는 복잡한 연산 없이 이 읽기 DB만 단순 조회한다. (CQRS)
- **비유**: 은행에서 입출금(명령)은 철저한 기록 장부(이벤트 스토어)에 순서대로 적히고, 고객이 폰뱅킹으로 잔액을 조회(쿼리)할 때는 장부에서 미리 계산해둔 가벼운 캐시 데이터(읽기 모델)를 보여준다.
- **구체 예시**: 장바구니 시스템. "상품 A 추가", "상품 A 1개 삭제", "상품 B 추가" 이벤트를 모두 저장하면, 나중에 "사용자가 어떤 상품을 뺐는지" 행동 패턴까지 분석할 수 있다. 조회를 위해서는 이 이벤트를 구독하여 최종 장바구니 리스트 형태의 MongoDB 문서를 만들어 둔다.
- **흔한 오해·주의점**: "모든 MSA에 CQRS를 해야 한다"는 오해다. 이벤트 통신으로 인해 필연적으로 '최종 일관성(Eventual Consistency)'이 발생하므로, 방금 쓴 글이 조회 안 되는 1~2초의 지연(Delay)을 비즈니스가 허용하지 못한다면 도입할 수 없다.

## 연결 개념
- 마이크로서비스 아키텍처 (MSA) — CQRS가 필수적으로 요구되는 분산 환경
- 최종 일관성 (Eventual Consistency) — CQRS 읽기 모델의 데이터 지연 특성
- 카프카 (Apache Kafka) — 이벤트를 전달하는 대표적인 메시지 브로커

# 📝 【답안용】 시험 답안 템플릿

## 핵심 인사이트 (3줄 요약)

> 1. **본질**: 이벤트 소싱은 데이터의 변경 내역을 불변의 이벤트 스트림으로 저장하며, CQRS는 쓰기(Command) 모델과 읽기(Query) 모델을 물리적·논리적으로 분리하는 패턴이다.
> 2. **가치**: 데이터의 완벽한 이력 추적과 복원(Replay)을 제공하고, 읽기와 쓰기의 스케일링을 독립적으로 최적화하여 MSA의 조인(JOIN) 한계와 성능 병목을 해결한다.
> 3. **판단 포인트**: 강력한 조회 성능과 히스토리 보존을 제공하지만, 시스템 복잡도 급증과 최종 일관성(Eventual Consistency)으로 인한 데이터 동기화 지연 리스크를 반드시 고려해야 한다.

## 출제 의도 및 답안 포인트

| 출제 의도 | 반드시 짚을 핵심 | 감점 회피 포인트 |
|:---|:---|:---|
| MSA 분산 데이터 환경의 한계 돌파 방안 이해 | 쓰기/읽기 분리(CQRS), 이벤트의 불변성(Append-Only) | 이벤트 소싱과 CQRS를 같은 개념으로 섞어 서술 |
| 궁극적 일관성과 동기화 구조 설계 역량 | Message Broker, Materialized View, Eventual Consistency | 데이터가 "즉시" 일치한다고 서술하는 사실 오류 |

> 요약: 단일 데이터베이스의 트랜잭션과 조인에 의존하던 모놀리식 방식을 버리고, 이벤트를 매개로 읽기와 쓰기의 책임을 극단적으로 분리하는 아키텍처 설계다.

---

## Ⅰ. 개요 및 필요성

- 개요: 상태 변경의 이력을 순차적 이벤트로 저장하는 이벤트 소싱과, 명령(쓰기)과 조회(읽기)의 책임을 분리하는 CQRS(Command and Query Responsibility Segregation)의 결합 아키텍처
- 배경: MSA 환경에서는 DB per Service로 인해 타 서비스 데이터와의 JOIN이 불가하며, 복잡한 조회 API가 쓰기 DB의 성능을 저하시키는 병목 현상 발생
- 필요성: 쓰기와 읽기의 리소스 비대칭(일반적으로 1:10 이상)을 독립적으로 확장하고, 분산 환경에서 다른 도메인 데이터들을 조합한 빠른 뷰(View) 제공 필수

---

## Ⅱ. 구조 및 구성요소

```text
[ Client ] -> (Command: 쓰기) -> Command Model -> [ Event Store ] (Append)
              |                                            |
              |                                     (Message Broker / Kafka)
              v                                            v
         (Query: 조회) <- Query Model (Materialized View) <- (이벤트 프로젝션)
```

| 구성요소 | 역할 | 특이사항 |
|:---|:---|:---|
| Command Model | 비즈니스 로직 수행 및 상태 변경 이벤트 발행 | 무결성 검증, RDBMS/Append-Only 스토어 사용 |
| Event Store | 상태 변경 내역을 불변(Immutable)의 이벤트로 순차 저장 | 삭제/수정 불가, 모든 상태의 단일 진실 공급원 |
| Event Bus | 저장된 이벤트를 Query 시스템으로 비동기 전달 | Kafka, RabbitMQ 등 메시징 브로커 활용 |
| Query Model | 이벤트를 구독(Projection)하여 조회에 최적화된 View 유지 | 빠른 조회를 위해 NoSQL(MongoDB 등) 주로 사용 |

> 요약: 쓰기 요청은 이벤트 스토어에 순차 기록되고, 이 이벤트가 비동기로 전달되어 조회용 모델(Materialized View)을 비동기 갱신한다.

---

## Ⅲ. 동작원리 및 흐름도

```text
사용자 명령 -> Command 처리 및 이벤트 생성 -> Event Store 저장 (쓰기 완료)
-> Event Bus로 이벤트 발행 -> Query Model 구독 및 View 갱신 -> 사용자 조회 (CQRS)
```

- 1단계 [명령 수신 및 검증]: 클라이언트의 상태 변경 요청(Command)을 Command Model이 수신하여 비즈니스 유효성 검증
- 2단계 [이벤트 저장]: 상태를 UPDATE 하는 대신, "ItemAddedEvent"와 같은 명시적 이벤트를 Event Store에 순차적(Append-only)으로 기록
- 3단계 [이벤트 프로젝션]: 기록된 이벤트를 Event Bus를 통해 발행하고, Query Model의 프로젝터(Projector)가 이를 수신하여 읽기 전용 DB 갱신
- 4단계 [조회 서비스]: 클라이언트가 뷰(Query)를 요청하면, 조인 연산 없이 이미 갱신된 Query Model(Materialized View)에서 데이터를 즉시 반환

> 요약: 쓰기와 읽기가 분리된 경로로 동작하며, 쓰기 시점의 이벤트를 기반으로 읽기 데이터가 비동기적으로(Eventual Consistency) 동기화된다.

---

## Ⅳ. 특징
- 100% 이력 추적 및 복원력(Replay): 상태 덮어쓰기가 없으므로 과거 임의의 시점 상태로 완벽한 롤백이 가능하고, 버그 발생 시 이벤트를 재실행(Replay)하여 데이터 복구 가능
- 독립적 스케일링: 트래픽이 몰리는 Query 모델만 독립적으로 스케일아웃(Scale-out)하거나 클라우드 엣지(CDN 등)에 캐싱하여 성능 극대화
- 최종 일관성 (Eventual Consistency) 허용: 이벤트를 발행하고 Query DB가 갱신되기까지 수 밀리초~수 초의 지연(Delay)이 발생하여 즉각적인 데이터 일관성은 보장되지 않음

> 요약: 데이터의 감사(Audit)와 극한의 조회 성능을 보장하지만, 강한 일관성(Strong Consistency)을 포기하고 최종 일관성을 수용해야 한다.

## Ⅴ. 심화 비교 및 적용 판단

| 비교 축 | 전통적 CRUD (단일 DB) | 이벤트 소싱 + CQRS | 선택 기준 |
|:---|:---|:---|:---|
| 데이터 저장 | 최종 상태만 덮어쓰기 (UPDATE) | 상태 변경 이력 전체 누적 (APPEND) | 이력 추적 및 감사(Audit) 중요도 |
| 읽기/쓰기 모델 | 동일 테이블, 동일 모델 (JOIN 사용) | 쓰기 모델과 조회 모델의 물리적 분리 | 읽기/쓰기 부하 비대칭성 |
| 데이터 일관성 | 강한 일관성 (ACID 트랜잭션 보장) | 최종 일관성 (Eventual Consistency) | 비즈니스의 지연(Delay) 허용 범위 |

> 요약: 단순한 관리자 페이지는 CRUD가 유리하지만, 대규모 트래픽의 쇼핑몰 상품 전시나 금융 원장 시스템은 이벤트 소싱과 CQRS가 적합하다.

**리스크·대응:**
- 최종 일관성으로 인한 사용자 UX 저하: 사용자가 방금 변경한 데이터를 조회 시 지연으로 못 보는 현상 발생 → 클라이언트 캐시로 임시 처리(Optimistic UI) 또는 API에 버저닝(ETag) 도입
- 이벤트 스토어 용량 폭증 및 Replay 지연: 수년 치 이벤트 재실행 시 극심한 병목 → 특정 주기(예: 1,000건마다)로 현재 상태의 스냅샷(Snapshot)을 생성하여 스냅샷 이후 이벤트만 재생

**도입 후 점검 지표:**
- 동기화 지연 시간 (Replication Lag): Command 처리 후 Query Model 반영까지의 지연 시간 p99 기준 1초 이내 방어
- 이벤트 메시지 유실률: 카프카 등 브로커 내 이벤트 전달 보장(At-least-once) 모니터링 — 유실률 0% 유지

## Ⅵ. 실무 적용 및 결론

**적용 방안 3개:**
1. 아키텍처 분리 적용: 전체 시스템이 아닌, 이력 보존이 핵심인 '결제/주문 도메인'과 조회 트래픽이 막대한 '상품 전시 도메인'에만 선택적(Tactical) 도입
2. Materialized View 최적화: Query Model로 Elasticsearch, Redis, MongoDB 등을 용도에 맞게 다중 구성하여 검색 뷰, 캐시 뷰, 상세 뷰 제공
3. 장애 복구 체계 구축 (Replay): 인덱싱 에러나 요구사항 변경으로 새로운 뷰(View)가 필요할 때, 기존 이벤트를 0번부터 다시 Replay하여 신규 Query DB를 무중단 재구축

**결론 (2줄):**
- 기술사 판단: CQRS와 이벤트 소싱은 MSA의 데이터 분산 한계를 극복하는 가장 강력한 패턴이지만, 아키텍처 복잡도를 극도로 높이므로 반드시 비즈니스의 '최종 일관성 허용' 여부를 먼저 검증해야 한다.
- 향후 방향: 최근에는 이벤트 스트리밍 플랫폼(Kafka) 기능이 고도화되면서 ksqlDB 등을 활용해 실시간 스트림 처리 위에서 CQRS의 Query View를 동적으로 구성하는 추세다.
