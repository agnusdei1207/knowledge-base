## 미리 알고가기

- 이벤트 소싱은 상태가 아니라 상태 변화 이벤트를 저장하는 방식임
- CQRS는 명령 처리 모델과 조회 모델을 분리하는 구조임
- 둘은 자주 함께 쓰이지만 같은 개념은 아님

## Ⅰ. 개요

- **정의/개념**: 이벤트 소싱은 도메인 상태 변경을 이벤트 로그로 저장해 현재 상태를 재구성하는 저장 방식이고, CQRS는 쓰기 모델과 읽기 모델을 분리해 각각 다른 구조와 최적화를 적용하는 아키텍처 패턴임
- **배경/필요성**: 감사 추적과 복잡한 상태 변화 기록과 읽기·쓰기 요구가 크게 다른 시스템에서는 단일 CRUD 모델보다 이벤트 중심 저장과 모델 분리가 더 적합할 수 있음

## Ⅱ. 특징

- 모든 상태 변화를 이벤트로 남겨 감사성과 재생 가능성이 높음
- CQRS는 조회 최적화와 명령 검증을 독립적으로 설계할 수 있음
- 읽기 모델이 eventual consistency를 가지기 쉬움
- 이벤트 버전 관리와 재생 비용과 복구 설계가 복잡함

## Ⅲ. 종류 및 비교

| 판단 기준 | 전통 CRUD | 이벤트 소싱·CQRS |
|:---|:---|:---|
| 저장 기준 | 현재 상태 저장 | 상태 변화 이벤트 저장 |
| 읽기/쓰기 모델 | 동일 모델 사용 | 분리 모델 사용 가능 |
| 장점 | 단순 구현 | 감사성과 조회 최적화 |
| 한계 | 이력 재구성 어려움 | 복잡도와 정합성 관리 필요 |

## Ⅳ. 구성요소 및 구조

| 구성요소 | 설명 |
|:---|:---|
| Command Model | 비즈니스 규칙을 검증하고 상태 변경 이벤트를 생성하는 쓰기 측 핵심임 |
| Event Store | 모든 이벤트를 순서대로 보관해 감사와 재생과 복구의 기준을 제공함 |
| Projection or Read Model | 이벤트를 소비해 조회에 최적화된 별도 뷰를 구성함 |
| Event Versioning | 스키마 변화에도 과거 이벤트를 해석하게 하는 장기 운영 핵심 장치임 |

## Ⅴ. 원리 및 절차 흐름도

```text
+-------------+     +-------------+     +-------------+     +-------------+
| 명령 수신      | --> | 이벤트 기록    | --> | projection 갱신 | --> | 조회 제공      |
+-------------+     +-------------+     +-------------+     +-------------+
```

1. **명령 수신**: 쓰기 모델이 비즈니스 명령을 받음
2. **이벤트 기록**: 검증 후 상태 변경 이벤트를 저장함
3. **projection 갱신**: 이벤트를 읽기 모델에 반영함
4. **조회 제공**: 클라이언트는 최적화된 조회 모델을 사용함

## Ⅵ. 문제점 및 해결 방안

1. 문제: 읽기 모델 반영 지연이 길어지면 사용자 입장에서 최신 상태 불일치가 크게 느껴질 수 있음
   - 해결방안: projection 지연을 모니터링하고 projection lag와 stale read ratio로 검증함
2. 문제: 이벤트 스키마가 자주 바뀌면 장기 보관 이벤트 재생과 호환성이 급격히 어려워질 수 있음
   - 해결방안: versioning 전략과 upcaster를 적용하고 replay success rate와 schema compatibility coverage로 검증함
3. 문제: 단순 업무에 무리하게 도입하면 이벤트 저장과 projection 운영 비용만 증가할 수 있음
   - 해결방안: 감사성과 복합 조회 요구가 큰 영역에 한정하고 architecture fit score와 operational overhead로 검증함

## Ⅶ. 적용 사례

- 금융 거래 이력 시스템에서는 이벤트 소싱을 적용하고 확인 지표는 replay success rate와 audit trace completeness임
- 조회 부하가 큰 주문 시스템에서는 CQRS를 적용하고 확인 지표는 projection lag와 query latency임
- 장기 운영 플랫폼에서는 이벤트 버전 전략을 운영하고 확인 지표는 schema compatibility coverage와 stale read ratio임

## Ⅷ. 결론

이벤트 소싱과 CQRS의 가치는 멋진 패턴 적용이 아니라 이력 보존과 읽기·쓰기 분리 이점이 복잡도 비용을 이길 때만 성립함.
