## 핵심 인사이트 (3줄 요약)
- **이벤트 소싱**: 데이터의 최종 상태(State)만 저장하지 않고, 상태를 변화시킨 모든 '이벤트(Event)'의 이력을 순서대로 저장하여 언제든 과거 상태를 재구성할 수 있는 기법.
- **CQRS**: 명령(Command, 쓰기)과 조회(Query, 읽기)의 책임과 모델을 완벽히 분리하여, 복잡한 조인(Join) 없이 읽기 성능을 극대화하는 아키텍처 패턴.
- 이 둘은 MSA 환경에서 분산된 데이터의 정합성을 맞추고 대규모 트래픽의 읽기 성능을 보장하기 위해 영혼의 단짝처럼 결합하여 사용됨.
---
## Ⅰ. 개요 및 필요성
- **개요**: 전통적인 CRUD 방식의 한계를 극복하기 위해 제안된 두 가지 강력한 데이터 아키텍처 패턴.
- **필요성**: MSA 환경에서는 서비스마다 DB가 찢어져 있어, 여러 서비스의 데이터를 모아서 보여주기(Query)가 극도로 어려움. 또한 기존 CRUD는 데이터가 덮어씌워져 "왜 이 상태가 되었는지"에 대한 감사(Audit) 트레일을 남기기 힘들었음.
---
## Ⅱ. 아키텍처 및 핵심 원리
- **이벤트 소싱 작동 원리**:
  1. 잔고가 100원이 되는 과정을 `Update 잔고=100`으로 덮어쓰지 않음.
  2. `[입금 100], [출금 50], [입금 50]`이라는 이벤트를 Append-only(추가 전용) 저장소에 기록.
  3. 현재 상태가 필요하면 이벤트를 처음부터 재생(Replay)하여 상태를 도출 (성능을 위해 스냅샷 활용).
- **CQRS 작동 원리**:
  1. 사용자가 쓰기 DB에 데이터를 저장.
  2. 쓰기 DB에 저장된 변경 사항이 '이벤트' 형태로 읽기 DB로 비동기 전파됨.
  3. 읽기 DB는 클라이언트가 조회하기 가장 좋은 형태(NoSQL, View)로 미리 가공되어 저장됨.

```text
[ Event Sourcing + CQRS 아키텍처 ]

 (Command: 쓰기 요청)                          (Query: 읽기 요청)
        ⬇️                                            ⬇️
 [ Command Service ]                           [ Query Service ]
        ⬇️                                            ⬇️
 [ Event Store (쓰기 DB) ]                     [ Read DB (NoSQL/캐시) ]
 (Append-only 이벤트 저장)                            (미리 조인된 데이터)
        |                                             ^
        +------ (Event Message Bus / Kafka) ----------+
                  (비동기 데이터 동기화)
```
---
## Ⅲ. 비교 및 연결
| 특성 | 기존 CRUD 구조 | Event Sourcing + CQRS |
|---|---|---|
| **상태 저장 방식** | 최종 상태만 덮어쓰기 (Update/Delete) | 발생한 모든 이벤트를 순차 기록 (Insert Only) |
| **읽기/쓰기 모델** | 동일한 모델(Entity) 공유 | 완벽히 분리된 모델 (Write Model vs Read Model) |
| **성능 최적화** | 조인(Join), 인덱스 의존 | 읽기 전용 뷰(Materialized View)를 통한 O(1) 검색 |
| **데이터 일관성** | 강한 일관성 (ACID) | 최종 일관성 (Eventual Consistency) |
---
## Ⅳ. 실무 적용 및 기술사 판단
- **최종 일관성(Eventual Consistency) 딜레마**: 쓰기 DB에서 읽기 DB로 이벤트가 전파되는 데 0.1초의 지연(Delay)이 발생할 수 있음. "내가 쓴 글이 바로 안 보여요"라는 클레임을 막기 위해 UI 단에서 낙관적 업데이트(Optimistic UI) 처리가 필수적임.
- **도입 비용**: 모든 상태 변화를 이벤트로 설계하고 두 개의 DB를 동기화하는 인프라(Kafka 등) 구축 비용이 매우 큼. 단순한 상태 관리라면 기존 CRUD가 정답이며, 금융/장바구니 등 추적성이 중요한 도메인에만 제한적으로 도입해야 함.
---
## Ⅴ. 기대효과 및 결론
- 이벤트 소싱은 완벽한 감사(Audit) 로그와 시점 복구(Time Travel)를 가능하게 하며, CQRS는 10배 이상의 트래픽이 몰리는 읽기(Query) 작업의 병목을 완벽히 해소함.
- 두 패턴의 결합은 MSA의 데이터 분산 문제를 해결하는 가장 진보된 설계이자, 이벤트 기반 아키텍처(EDA)의 정수임.

### 👶 어린이를 위한 3줄 비유 설명
1. 용돈 기입장을 쓸 때, 예전에는 지우개로 지우고(Update) '현재 5천 원'이라고만 썼어요. (CRUD)
2. 이벤트 소싱은 '엄마한테 1만 원 받음', '과자 5천 원 삼'을 지우지 않고 계속 밑으로 적어 내려가는 거예요. 
3. CQRS는 용돈 기입장(쓰기)과 별개로, 내 지갑에 얼마 있는지 큼지막하게 써둔 포스트잇(읽기)을 따로 만들어서 친구가 물어보면 포스트잇만 보고 1초 만에 대답하는 방식이에요!
