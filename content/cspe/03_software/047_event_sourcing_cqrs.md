## 미리 알고가기

- 이벤트 소싱은 현재 상태 대신 상태 변화 이벤트를 저장하는 방식임
- CQRS는 명령 처리 모델과 조회 모델을 분리하는 구조임
- Projection은 이벤트를 읽어 조회용 모델로 다시 구성한 결과임

## Ⅰ. 개요

- **정의/개념**: 이벤트 소싱은 도메인 상태 변화를 이벤트 로그로 저장해 현재 상태를 재구성하는 저장 방식이고, CQRS는 쓰기 모델과 읽기 모델을 분리해 각각 다른 구조와 최적화를 적용하는 아키텍처 패턴임.
- **배경/필요성**: 감사 추적이 중요하고 읽기와 쓰기 요구가 크게 다른 시스템에서는 단일 CRUD 모델만으로 이력 보존과 조회 최적화를 동시에 만족하기 어려우므로, 이벤트 중심 저장과 모델 분리가 필요할 수 있음.

## Ⅱ. 특징

- 모든 상태 변화를 이벤트로 남겨 감사와 재생 가능성이 높음
- CQRS는 쓰기 규칙과 조회 성능을 서로 다른 모델로 최적화할 수 있음
- 조회 모델은 이벤트 반영이 늦어 최신 상태와 잠시 어긋날 수 있음
- 이벤트 버전 관리와 재생 비용이 커서 단순 업무에는 부담이 됨

## Ⅲ. 종류 및 비교

| 구분 | 전통 CRUD | 이벤트 소싱·CQRS |
|:---|:---|:---|
| 저장 기준 | 현재 상태를 최신 값으로 덮어쓰며 저장함 | 상태 변화 이벤트를 시간 순서대로 저장함 |
| 읽기/쓰기 모델 | 같은 데이터 모델을 읽기와 쓰기에 함께 사용함 | 명령 처리 모델과 조회 모델을 분리할 수 있음 |
| 얻는 장점 | 구조가 단순하고 구현이 빠름 | 감사 추적과 조회 최적화와 상태 재생에 유리함 |
| 주된 한계 | 과거 상태와 변경 이유를 재구성하기 어려움 | 지연 정합성과 버전 관리와 운영 복잡도를 감당해야 함 |

> 요약: 이벤트 소싱과 CQRS는 이력 보존과 모델 분리 이점이 단순 CRUD보다 클 때 선택하는 구조임.

## Ⅳ. 구성요소 및 구조

| 구성요소 | 설명 |
|:---|:---|
| Command Model | 비즈니스 규칙을 검증하고 상태 변경 이벤트를 생성하는 쓰기 측 핵심임 |
| Event Store | 모든 이벤트를 순서대로 보관해 감사와 재생과 복구의 기준을 제공함 |
| Projection or Read Model | 이벤트를 소비해 조회에 맞는 별도 모델을 구성함 |
| Event Versioning | 스키마가 바뀌어도 과거 이벤트를 해석할 수 있게 하는 장기 운영 장치임 |

## Ⅴ. 원리 및 절차 흐름도

```text
+-------------+     +-------------+     +-------------+     +-------------+
| 명령 수신      | --> | 이벤트 기록    | --> | projection 갱신 | --> | 조회 제공      |
+-------------+     +-------------+     +-------------+     +-------------+
```

1. **명령 수신**: 쓰기 모델이 비즈니스 명령을 받음
2. **이벤트 기록**: 규칙 검증 후 상태 변경 이벤트를 저장함
3. **Projection 갱신**: 이벤트를 읽기 모델에 반영함
4. **조회 제공**: 클라이언트는 조회에 최적화된 모델을 사용함

## Ⅵ. 실무 적용 및 유의점

1. 금융 거래나 감사 추적이 중요한 시스템에서는 이벤트 소싱이 유리하지만 이벤트 스키마가 자주 바뀌면 장기 재생이 어려워지므로 버전 관리와 이벤트 변환 규칙을 함께 운영하고 이벤트 재생 성공률과 스키마 호환 범위로 확인함
2. 조회 부하가 큰 주문·이력 서비스에서는 CQRS로 읽기 모델을 분리하되 읽기 모델 반영 지연이 길어지면 사용자 불일치가 커지므로 비동기 반영 지연을 모니터링하고 조회 모델 반영 지연과 오래된 조회 비율로 확인함

## Ⅶ. 결론

이벤트 소싱과 CQRS는 이력 보존과 읽기 최적화가 핵심 요구인 영역에서만 복잡도 비용을 감수할 가치가 생김.
