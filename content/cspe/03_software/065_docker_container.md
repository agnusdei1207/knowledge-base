## Ⅰ. 개요
- **정의**: 리눅스 커널의 namespace·cgroup을 활용하여 프로세스를 격리 실행하는 컨테이너 플랫폼
- **배경/필요성**: VM 기반 격리는 OS 전체를 복제하여 자원 낭비가 크므로, 커널을 공유하면서 프로세스 수준 격리를 제공하는 경량 방식이 필요함
- **비유**: 칸막이가 있는 공유 주방 — 주방 설비(커널)는 공유하되 각 칸(컨테이너)은 독립 작업 공간임

| 출제 의도 | 반드시 짚을 핵심 | 감점 회피 포인트 |
|:---|:---|:---|
| VM과 컨테이너 차이 | 이미지 레이어, namespace/cgroup | Docker와 컨테이너 개념 자체를 동일시 금지 |

> 요약: 커널 공유 기반 프로세스 격리로 경량·빠른 배포를 제공하는 컨테이너 플랫폼임

## Ⅱ. 구성요소
```text
Dockerfile --> docker build --> Image --> docker run --> Container
                                  |                        |
                                  v                        v
                             Registry               Host Kernel
                                                  (namespace/cgroup)
```

| 구성요소 | 설명 | 비유 |
|:---|:---|:---|
| Dockerfile | 이미지 빌드 절차를 선언한 텍스트 파일 | 조리 레시피 |
| Image | 읽기 전용 레이어로 구성된 실행 환경 스냅샷 | 냉동 밀키트 |
| Container | 이미지 위에 쓰기 가능 레이어를 추가한 실행 인스턴스 | 조리 중인 요리 |
| Registry | 이미지를 저장·배포하는 원격 저장소 | 식재료 창고 |

> 요약: Dockerfile-Image-Container-Registry의 4요소로 빌드-실행-배포 생명주기를 관리함

## Ⅲ. 절차
```text
Write Dockerfile --> Build Image --> Push Registry --> Run Container
```
- 1단계: Dockerfile에 베이스 이미지·의존성·실행 명령을 정의함
- 2단계: `docker build`로 레이어별 캐시를 활용하여 이미지를 생성함
- 3단계: `docker push`로 이미지를 Registry에 업로드함
- 4단계: `docker run`으로 컨테이너를 생성·실행함

> 요약: 정의-빌드-푸시-실행의 4단계로 컨테이너 생명주기를 관리함

## Ⅳ. 문제점
- 이미지 비대화: 불필요 패키지 포함 시 이미지 크기가 수 GB로 증가하여 배포 시간이 늘어남
- 보안 취약점: 베이스 이미지의 알려진 CVE가 상속되어 컨테이너 전체에 전파됨
- 단일 호스트 한계: Docker 단독으로는 다중 호스트 스케일링·장애 복구가 불가함

> 요약: 이미지 비대화, 보안 취약점 상속, 단일 호스트 한계가 주요 문제임

## Ⅴ. 개선방안
1. 단기: 멀티스테이지 빌드·경량 베이스(Alpine 등)로 이미지 크기를 최소화함
2. 중기: Trivy·Grype 등 이미지 스캐너를 CI 파이프라인에 통합하여 CVE를 사전 차단함
3. 장기: Kubernetes(066 참조) 등 오케스트레이션 플랫폼으로 다중 호스트 관리를 위임함

> 요약: 경량 빌드, 이미지 스캐닝, 오케스트레이션 도입으로 개선함

## Ⅵ. 전망
- 발전 방향: OCI 표준 기반으로 런타임(070 참조)이 다양화되며 Docker 의존도가 낮아짐
- 기술사적 판단: 컨테이너는 클라우드 네이티브의 기본 배포 단위로 정착함
- 기술사 제언: 이미지 경량화·보안 스캐닝을 CI에 내재화하고 오케스트레이션 전략을 병행 설계할 필요
