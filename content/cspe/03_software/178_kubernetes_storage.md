## 핵심 인사이트 (3줄 요약)
- "파드는 언제든 죽고 새로 태어난다"는 쿠버네티스의 룰 때문에, 데이터베이스(DB)처럼 **데이터가 절대 날아가면 안 되는 앱을 위해 외부의 안전한 하드디스크를 끌어와 붙여주는 스토리지 아키텍처**.
- **PV(Persistent Volume)**는 "우리 회사에 100GB짜리 하드가 있어"라는 물리적 저장소이고, **PVC(Persistent Volume Claim)**는 개발자가 "나 10GB짜리 하드 좀 줘"라고 요청하는 쿠폰(청구서)임. 
- 개발자가 하드디스크 종류(AWS EBS인지, NFS인지)를 몰라도, K8s가 알아서 요청(PVC)에 맞는 디스크(PV)를 짝지어(Binding) 파드에 마운트해 주는 완벽한 역할 분담 사상임.
---
## Ⅰ. 개요 및 필요성
- **개요**: 쿠버네티스 환경에서 컨테이너의 생명주기와 독립적으로 데이터를 영구적으로 보존(Persistence)하기 위한 추상화된 스토리지 객체 시스템.
- **필요성**: 파드 안에 MySQL DB를 띄우고 회원 가입을 1,000명 받았음. 근데 노드가 재부팅되면서 파드가 죽고 새 파드가 떴더니 데이터가 0명으로 초기화됨 (컨테이너 내장 디스크는 파드와 함께 삭제됨). **"파드가 1번 서버에서 죽고 2번 서버에서 살아나더라도, 고객 데이터는 절대 안 날아가게 바깥쪽(공유 스토리지)에 저장해 둬야 해!"**
---
## Ⅱ. 아키텍처 및 핵심 원리
- **1. PV (Persistent Volume - 영구 볼륨)**:
  - **인프라 관리자(Ops)**가 만들어 두는 실제 저장 공간.
  - "여기 AWS EBS(클라우드 하드디스크) 100GB짜리 3개 만들어 놨어. 누구든 가져다 써."
  - 파드가 죽어도 PV 안의 데이터는 절대 날아가지 않음.
- **2. PVC (Persistent Volume Claim - 볼륨 요청권)**:
  - **개발자(Dev)**가 작성하는 요구사항 명세서.
  - "내 웹서버 파드에 10GB짜리 빠릿빠릿한(SSD) 디스크 하나 연결해 주세요!"
- **3. Binding (바인딩 - 짝짓기)**:
  - 쿠버네티스의 마스터 노드가 수시로 감시하다가, 개발자의 PVC 요청(10GB)을 만족하는 관리자의 잉여 PV(100GB 중 하나)를 찾아내서 둘을 **영구적으로 묶어버림**.
  - 파드는 이 PVC(쿠폰)를 들고 가서 PV(디스크)에 데이터를 읽고 씀.
- **4. StorageClass (스토리지 클래스 - 동적 할당의 마법)**:
  - 과거엔 관리자가 수동으로 PV 100개를 미리 만들어 놔야 했음(정적 프로비저닝).
  - 너무 귀찮아서 생긴 기술. 관리자가 `StorageClass=AWS-SSD`라는 자동 응답기만 켜두면, 개발자가 PVC를 날리는 순간 **K8s가 알아서 AWS에 API를 쏴서 10GB짜리 하드를 자동 생성(동적 프로비저닝, Dynamic Provisioning)**해 줌.

```text
[ 스토리지 동적 프로비저닝 (Dynamic Provisioning) 흐름 ]

 👨‍💻 [ 개발자 (Dev) ] : "저기, MySQL용으로 50GB짜리 하드 하나만 주세요!" (PVC 생성)
        ⬇️
 🤖 [ StorageClass (K8s 자동 응답기) ] : "오케이, 너의 요구사항 접수 완료."
        ⬇️ API 호출
 ☁️ [ AWS 인프라 (EBS) ] : 위잉~ (AWS에서 실제로 50GB 하드가 자동으로 만들어짐! = PV 생성)
        ⬇️
 🫛 [ MySQL 파드 ] : 새로 만들어진 하드를 파드 배에 착! 붙여서(Mount) 데이터 저장 시작.
 💥 만약 파드가 죽어도 하드는 남고, 파드가 다른 서버에서 부활하면 하드도 그 서버로 따라가서 다시 붙음!
```

## Ⅲ. 비교 및 연결
| 스토리지 타입 | 특징 | 접근 모드 (Access Mode) | 용도 |
|---|---|---|---|
| **emptyDir** | 파드 안의 임시 저장소. **파드 죽으면 데이터 싹 다 날아감.** | 파드 내부 컨테이너끼리만 공유 | 로그 임시 저장, 메모리 캐시 |
| **hostPath** | 노드(물리 서버)의 C드라이브를 씀. 노드 죽으면 답 없음. | 해당 노드에 뜬 파드만 접근 가능 | DaemonSet 로그 수집 등 |
| **PV / PVC** | 클러스터 외부에 존재하는 **진짜 영구 데이터 저장소.** | 여러 노드에서 동시 읽기/쓰기 가능(NFS 등) | **핵심 데이터베이스(DB)**, 유저 업로드 이미지 등 |

## Ⅳ. 실무 적용 및 기술사 판단
- **CSI (Container Storage Interface) 표준의 이해**: 옛날 쿠버네티스는 소스 코드 안에 AWS, GCP 스토리지를 연결하는 코드가 지저분하게 얽혀 있었음(In-tree). 쿠버네티스가 너무 무거워지자, 런타임을 CRI로 쳐냈듯 스토리지도 **CSI**라는 표준 플러그인 인터페이스로 쳐냄(Out-of-tree). 기술사는 "StorageClass가 외부 스토리지를 제어할 수 있는 것은 바로 이 CSI 드라이버 덕분"이라는 아키텍처의 확장성을 짚어야 함.
- **클라우드 네이티브 스토리지(Ceph / Rook) 도입**: 사내 전산실(온프레미스)에서 K8s를 쓸 때 AWS EBS 같은 게 없음. 이때는 여러 서버의 남는 하드디스크를 영혼까지 끌어모아 하나의 거대한 가상 스토리지 풀(Pool)로 만들어주는 분산 스토리지 **Ceph**와, 이를 K8s 안에서 오퍼레이터로 자동 관리해 주는 **Rook**을 조합하는 것이 엔터프라이즈의 표준 아키텍처임.
---
## Ⅴ. 기대효과 및 결론
- 개발자(PVC)와 인프라 관리자(PV)의 역할을 완벽하게 분리하여, 개발자가 복잡한 클라우드 스토리지 API를 몰라도 YAML 한 줄로 디스크를 할당받을 수 있게 해줌.
- "상태가 없는(Stateless)" 웹 서버 중심의 쿠버네티스 초기 생태계를 "상태를 유지하는(Stateful)" 데이터베이스와 빅데이터 시스템까지 포용하는 엔터프라이즈 통합 플랫폼으로 진화시킨 핵심 퍼즐 조각임.

### 📌 관련 개념 맵
- Stateful 앱 ➡️ PV (Persistent Volume) / PVC (Persistent Volume Claim) ➡️ StorageClass (동적 프로비저닝) ➡️ CSI (Container Storage Interface)

### 📈 관련 키워드 및 발전 흐름도
- 도커 볼륨(임시)의 한계 ➡️ K8s PV/PVC의 정적 매칭 시스템 도입 ➡️ 수동 매칭의 귀찮음으로 StorageClass(동적 프로비저닝) 대세화 ➡️ 인트리(In-tree) 코드의 무거움을 해소하기 위한 CSI 표준 도입 ➡️ StatefulSet 컨트롤러와의 완벽한 앙상블

### 👶 어린이를 위한 3줄 비유 설명
1. 파드(캠핑카) 안에 있는 서랍(emptyDir)은 캠핑카가 고장 나서 버려지면 안에 든 물건이 다 날아가요.
2. 그래서 은행 금고(**PV**, 영구 볼륨)에 진짜 중요한 물건을 보관하기로 했어요.
3. 캠핑카 주인이 "나 금고 1칸 쓸래!"라고 신청서(**PVC**)를 내면, 쿠버네티스 은행장님이 딱 맞는 금고를 연결해 줘요. 캠핑카가 부서져서 새 차를 사도 은행 금고의 물건은 그대로 남아있답니다!
