# 📖 【암기용】 개념 완전 이해

> 목적: 이 개념을 처음 보는 사람도 완벽히 이해하게 만든다. 시험 답안 양식이 아니라, 이해를 위한 친절한 설명이다.

## 한눈에
- **개요**: **DAST(Dynamic Application Security Testing, 동적 분석)**는 소스코드를 전혀 열어보지 않고, **실행 중(Runtime)인 애플리케이션**에 외부 해커처럼 공격 페이로드를 주입해 응답을 관찰함으로써 취약점을 찾는 **블랙박스(Black-box) 동적 보안 테스트**다.
- **왜 필요한가**: 코드 자체(SAST)가 완벽해도, 서버 방화벽 포트가 열려 있거나 웹서버 설정 실수로 디렉터리 목록이 그대로 노출되는 등 "프로그램을 실제로 켜봐야만 드러나는" 런타임 결함은 소스코드 분석만으로는 절대 잡히지 않는다.
- **핵심 직관**: 설계도(코드)를 검토하는 게 아니라, 이미 지어진 건물(가동 중인 서버)에 실제로 침입을 시도해 문이 열리는지 확인하는 것이다.

## 핵심 용어 정리 (내부에 등장하는 것들)

| 용어 | 의미 | 비유 |
|:---|:---|:---|
| 동적 분석 (Dynamic Analysis) | 프로그램을 실제로 실행한 상태에서 관찰·검증하는 분석 방식 — DAST가 속한 상위 범주 | 정지 사진이 아니라 실제로 틀어본 동영상 |
| 블랙박스 테스트 (Black-box Test) | 내부 구조(소스코드)를 모르는 채 입력·출력만으로 판단하는 테스트 방식 | 뚜껑을 열지 않고 버튼만 눌러 결과를 확인 |
| SAST (정적 분석) | 소스코드·바이트코드를 실행 없이 코드 자체에서 취약 패턴을 찾는 테스트 — DAST의 보완 기법 | 설계도만 보고 배선 오류를 찾는 것 |
| 페이로드 (Payload) | 취약점을 유발하기 위해 서버에 실제로 전송하는 공격용 입력값 | 자물쇠를 시험하는 다양한 모양의 열쇠 |
| 퍼징 (Fuzzing) | 다량의 무작위·변형 입력값을 자동으로 대량 주입해 예외·오류를 유도하는 기법 | 자물쇠에 수천 개의 열쇠를 기계적으로 넣어보는 것 |
| XSS (Cross-Site Scripting) | 악성 스크립트를 입력값에 심어 다른 사용자 브라우저에서 실행시키는 취약점 | 방명록에 몰래 폭죽을 심어 다음 방문자가 열 때 터뜨림 |
| SQL Injection | SQL 구문을 조작하는 입력값을 넣어 DB 쿼리 로직을 변경하는 취약점 | 신청서 빈칸에 새로운 명령문을 몰래 끼워 넣는 것 |
| 크롤러 (Crawler) | 애플리케이션의 화면·링크·API를 자동으로 탐색해 공격 대상 목록을 수집하는 모듈 | 도면 없이 문이란 문은 다 열어보며 지도를 그리는 정찰병 |
| 오탐/미탐 (False Positive/Negative) | 오탐은 취약하지 않은데 취약하다고 오판, 미탐은 실제 취약한데 못 찾는 것 | 화재경보기가 불이 안 났는데 울림(오탐) / 불이 났는데 안 울림(미탐) |
| IAST (Interactive AST) | 애플리케이션 내부에 에이전트를 심어 DAST의 공격 결과와 SAST의 코드 위치 추적을 결합한 하이브리드 기법 | 침입 시험을 하면서 건물 내부 CCTV로 어느 방이 뚫렸는지 동시에 확인 |

## 깊이 이해

### SAST가 놓치는 지점 — 왜 실제로 실행해봐야만 아는가
개발자가 소스코드를 완벽히 짜서 SAST를 통과했다고 하자. 그런데 배포 담당자가 클라우드 방화벽에서 관리용 포트(예: 22, 3306)를 외부에 열어두거나, 웹서버(Nginx·Apache) 설정 실수로 `/admin`, `/.git` 같은 디렉터리 목록이 그대로 노출될 수 있다. 이런 결함은 소스코드 어디에도 적혀 있지 않고, 서버를 실제로 띄워 외부에서 요청을 보내봐야만 드러난다. DAST는 바로 이 "배포·설정·런타임 단계에서만 발현되는 결함"을 노린다.

### 퍼징이 취약점을 찾는 절차 — 구체적 수치로
1. DAST 스캐너(OWASP ZAP, Burp Suite 등)가 크롤러로 로그인 화면·게시판 입력창·API 엔드포인트를 수집한다. 중형 웹 서비스라면 화면과 API를 합쳐 수백 개의 입력 지점이 나오는 것이 보통이다.
2. 입력 지점마다 알려진 공격 패턴을 자동으로 대입한다. 예를 들어 게시판 글쓰기 칸 하나에 `<script>alert(1)</script>`(XSS), `' OR 1=1 --`(SQL Injection), 대용량 문자열(버퍼 오버플로우 유도) 등 수백 개의 변종 페이로드를 순차적으로 주입한다.
3. 입력 지점이 200개, 지점당 페이로드가 300개라면 단순 계산으로도 6만 건의 HTTP 요청이 발생한다. DAST 스캔 1회에 통상 수 시간이 걸리는 이유다.

### 취약점 판별 원리 — 응답을 어떻게 읽는가
- **에러 기반**: 페이로드 주입 후 응답 본문에 `SQL syntax error`나 스택 트레이스 같은 내부 정보가 그대로 노출되면 취약으로 판정한다.
- **반사 기반**: XSS 페이로드를 넣었는데 응답 HTML에 스크립트가 그대로 삽입되어 브라우저에서 실행 가능한 형태로 반사되면 취약으로 판정한다.
- **시간 기반(Blind)**: 화면에 아무 변화가 없어도 판별할 수 있다. 예를 들어 평소 응답이 50ms인 API에 `' OR SLEEP(5)--`를 주입했을 때 응답이 5,000ms 이상으로 늘어나면, DB가 그 SQL 구문을 실제로 실행했다는 뜻이므로 SQL Injection이 있다고 판정한다.

### 블랙박스이기 때문에 생기는 태생적 한계
DAST는 "결제 페이지에서 SQL Injection이 뚫렸다"는 사실은 알려주지만, 소스코드의 `Order.java` 34번째 줄이 원인이라고는 알려주지 못한다. 개발자는 취약점을 재현할 수 있는 파라미터 조합만 받아, 수만 줄의 코드를 거슬러 올라가며 원인을 찾아야 한다. 이 역추적 비용 때문에 DAST가 찾은 버그 1건을 고치는 시간이 SAST가 찾은 버그보다 훨씬 오래 걸리는 경우가 많다. 이 한계를 메우려고 나온 것이 IAST다 — 애플리케이션 메모리에 에이전트를 심어 DAST 공격이 발생한 순간 내부 코드 경로까지 함께 기록한다.

### CI/CD 파이프라인에서의 위치
퍼징은 수만 건의 요청을 실제로 서버에 보내야 하므로 완료까지 수 시간이 걸린다. 반면 SAST·SCA는 코드만 정적으로 훑으므로 수 분 내에 끝난다. 그래서 커밋마다 도는 메인 파이프라인에는 SAST·SCA만 넣어 빠르게 배포를 진행하고, DAST는 스테이징 서버를 대상으로 야간 배치(Nightly)나 별도 파이프라인으로 분리해 돌리는 구성이 일반적이다.

## 연결 개념
- SAST (정적 분석) — 코드 레벨 위치는 정확히 짚지만 런타임 결함은 못 잡는 상호 보완 기법
- IAST — DAST의 공격과 SAST의 위치 추적을 내부 에이전트로 결합한 하이브리드 기법
- 퍼징(Fuzzing) — DAST의 핵심 취약점 탐지 메커니즘

# 📝 【답안용】 시험 답안 템플릿

> 목적: 시험장에서 25분에 그대로 쓰는 답안 양식. 작성방식(추상표현 금지·수치·도식·문제유형 전환)을 엄격히 지킨다.
> 핵심: 이 시험은 정보를 많이 나열하는 시험이 아니라, 문제 신호어에서 출제자 의도를 읽고 핵심 논점을 선별해 쓰는 시험이다.

## 핵심 인사이트 (3줄 요약)

> 1. **본질**: 애플리케이션을 스테이징(Staging) 등 실제 환경에 가동(Runtime)시켜 놓고, 소스코드 지식 없이 외부에서 다양한 악의적 페이로드를 주입하여 취약점을 식별하는 블랙박스(Black-box) 보안 기법이다.
> 2. **가치**: SAST(정적 분석)가 절대 잡을 수 없는 런타임 인프라 설정 오류(Misconfiguration), 인증/인가 세션 우회 로직을 실전(Real-world) 관점에서 색출하며, 낮은 오탐률(Low False Positive)을 자랑한다.
> 3. **판단 포인트**: Fuzzing(퍼징) 기반의 악성 페이로드 주입 도식을 그리고, 소스코드 라인 추적이 불가(Blind)하여 디버깅 비용이 치솟는 태생적 한계를 극복하기 위한 **'아웃오브밴드(Out-of-band) 비동기 파이프라인'** 설계 방안을 맵핑해야 한다.

## 출제 의도 및 답안 포인트

| 출제 의도 | 반드시 짚을 핵심 | 감점 회피 포인트 |
|:---|:---|:---|
| 정적 분석(SAST) 한계와 DAST의 상호 보완성 규명 | **런타임 환경 오설정(Infra) 및 인증 로직 에러** 탐지 특화 | SAST와 DAST가 같은 버그를 잡는 경쟁 도구라고 쓰는 오개념 |
| DAST의 엔지니어링 메커니즘 (블랙박스/퍼징) | **퍼징(Fuzzing) 주입과 응답(Response) 분석** 도식화 | 소스코드를 읽어 들여서 분석한다는 (화이트박스와의) 혼동 |
| CI/CD 통합 시 타임 병목(Bottleneck) 리스크 조율 | 수 시간 소요되는 DAST의 **비동기 야간(Nightly) 배치 튜닝** | DAST를 개발자 커밋(Push) 직후 실시간 차단막으로 쓴다는 맹점 |

> 요약: DAST는 개발자가 아무리 코드를 예쁘게 짰어도 "AWS 포트가 다 열려있는데요?"를 잡아내는 자비 없는 외부 감사관이다. 건물의 설계도(SAST)가 완벽해도, 막상 지어놨더니 뒷문(Nginx) 자물쇠를 안 잠가둔 바보짓을 잡아내는 유일한 실전 방패다.

## Ⅰ. 개요 및 필요성

- 정의: 소프트웨어 개발 생명주기(SDLC)의 통합/시스템 테스트 단계에서, 구동 중인 애플리케이션(Runtime)에 외부 해커와 동일한 블랙박스 스캐너를 투입해 동적인 취약점(XSS, 런타임 에러)을 검증하는 기법
- 배경: 소스코드(AST) 분석 기반의 SAST 기법은 서버 컴포넌트 간 통신, 인프라 컨피그(Config), 서드파티 라이브러리 연동 시 런타임에 발현되는 결함을 구조적으로 탐지할 수 없는 맹점 노출
- 필요성: 시스템이 조립(Assembly)된 완전체 상태에서 해킹 시뮬레이션을 돌려 '실제 폭발하는(Exploitable)' 정교한 취약점을 색출하고, 오탐(가짜 경보)으로 인한 보안 피로도를 극단적으로 억제하기 위함

## Ⅱ. DAST 동적 분석 아키텍처 및 퍼징(Fuzzing) 도식

코드가 뭔지 모른다. 그냥 API 멱살을 잡고 무한대의 쓰레기값(Payload)을 부어버린다.

```text
[ DAST 분석 파이프라인: 블랙박스 퍼징 융단폭격 도식 ]

(1. 악성 페이로드 투척: Fuzzing)        (2. 런타임 가동 환경: 블랙박스)         (3. 반응 수집 및 판독)
+-------------------------+         +----------------------------+        +---------------------------+
| 🤖 DAST 스캐너 (ZAP)    |         | 🏢 스테이징(Staging) 서버  |        | 🔍 HTTP Response 분석     |
|                         | =====>  | (내부 소스코드 안 보임 ⬛)   | =====> | - HTTP 500 에러 노출? (✅) |
| Payload: `<script>...`  | HTTP    | (웹서버 + WAS + DB 연동)   | HTTP   | - DB 쿼리문 노출? (✅)    |
| Payload: `' or 1=1 -- ` | 요청     |                            | 응답   | - 200 OK 무시 (통과)      |
+-------------------------+         +----------------------------+        +---------------------------+
  | (수만 개의 페이로드 난사)                  (실제 런타임 동작)                    | 🛑 [ 취약점 리포트 생성 ]
```

| 분석 엔지니어링 메커니즘 | 물리적 통제 방식 (런타임 타격) | 탐지하는 취약점(Vulnerability) 유형 |
|:---|:---|:---|
| **퍼징 (Fuzzing) 공격** | 예측을 벗어난 무작위 쓰레기값(특수문자, 대용량 버퍼)을 HTTP 파라미터/헤더에 쑤셔 넣고 서버 크래시(Crash) 유도 | 버퍼 오버플로우 메모리 붕괴, **SQL 인젝션 및 XSS 응답(Response) 반사** 확인 사살 |
| **인증(Auth) 세션 우회** | 쿠키(Cookie)나 JWT 토큰을 조작하여 인가되지 않은 관리자 페이지(admin)나 타 사용자의 리소스 탈취 찌르기 | 수평/수직적 **권한 상승 우회**, 비보안 통신(HTTP 노출) 등 로직 버그 |
| **인프라 설정(Config) 점검** | 오픈 포트 스캔, 사용 중인 WAS(Tomcat 버전) 핑거프린팅 탈취 및 구형 암호화(TLS 1.0) 알고리즘 사용 여부 점검 | SAST가 볼 수 없는 **인프라 보안 오설정 (Security Misconfiguration)** |

> 요약: SAST는 범죄를 저지를 '가능성'이 있는 소스코드를 체포한다면, DAST는 진짜 창문(포트)을 부수고 침입해 보고 성공했을 때(현행범)만 빨간 딱지를 붙인다. 그래서 DAST가 뱉은 에러 리포트는 100% 팩트(낮은 오탐)다. 무조건 고쳐야 한다.

## Ⅲ. 극복해야 할 시스템적 리스크 (사후 디버깅 헬과 스캔 타임)

확실하게 잡아주는 건 좋은데, "어디서 터졌는지" 안 알려주고 3시간 동안 스캔만 돌면 애자일은 망한다.

| 리스크 요인 | 발생 시나리오 및 시스템 붕괴 원인 (안티패턴) | 아키텍처 대응 방안 (실무 튜닝 최적화) |
|:---|:---|:---|
| **블라인드 디버깅 (Blind Debugging)** | DAST가 "결제창에 SQL 인젝션 뚫림!"이라고 통보함. 소스코드를 100만 줄 뒤지며 어디서 뚫렸는지 찾아야 하므로(추적 불가), 버그 수정(MTTR)에만 3주일이 증발함 | **IAST(상호작용 분석) 및 RASP 패러다임 융합**: 앱 심장부(메모리)에 IAST 에이전트(`javaagent`)를 심어둠. 밖에서 DAST가 때려서 에러가 나면, 내부에 심어둔 에이전트가 "그 에러 `Order.java` 53번째 줄에서 터졌어!"라고 소스 레벨 위치를 SAST처럼 매핑 전달(시너지 폭발) |
| **CI 파이프라인 런타임 셧다운 (병목)** | 모든 HTTP 엔드포인트에 1만 개의 해킹 공격을 던져야 하므로(크롤링), DAST 스캔 1회에 4시간이 걸림. 하루 10번 배포해야 하는 애자일(CI/CD) 파이프라인 완전 마비 유발 | **Out-of-band(비동기 야간 배치) 파이프라인 분리**: 메인 파이프라인은 SAST/SCA(1분 컷)만 붙여서 광속 배포하고, 무거운 DAST는 밤 12시에 도는 별도의 Cron(야간 배치) 서버로 완전히 찢어서(Decoupling) 파이프라인 병목 완벽 소거 |

> 요약: DAST를 주간(낮) 메인 배포 파이프라인 한가운데에 `Blocking(차단)`으로 걸어두면 그날 부로 데브옵스 조직은 파업한다. 런타임 스캔은 무조건 '야간(Nightly) 백그라운드'로 빼는 것이 엔터프라이즈 아키텍처의 절대 룰이다.

## Ⅳ. DevSecOps 기반 투트랙(Two-Track) 보안 아키텍처

SAST와 DAST는 서로 대체재가 아니다. 완전한 보완재다. 방패(정적)와 창(동적)을 다 들어야 방어가 끝난다.

| 융합 파이프라인 | 방어 스코프 및 타겟(Target) | 치명적 결함 유출 0% 달성 메커니즘 |
|:---|:---|:---|
| **Shift-Left (좌측)** <br> `[ SAST + SCA ]` | **소스코드 문법** (SQLi, 하드코딩) <br> **오픈소스 취약점** (Log4j CVE) | 코드 저장(Push) 즉시 수초 내에 검열하여, 문법적/태생적 해킹 소스를 1차(In-band) 차단 압살 |
| **Shift-Right (우측)** <br> `[ DAST ]` | **인프라 런타임 오설정** (Nginx/DB) <br> **인증 우회 / 비즈니스 로직 플로우** | 실제 조립된 덩어리(Staging)에 창을 던져, 1차 방어를 뚫고 올라온 거시적 컨텍스트(Context) 맹점 2차(Out-band) 붕괴 방어 |

> 요약: 도면(코드)을 그릴 땐 SAST가 감리하고, 지어놓은 모델하우스(스테이징)에는 DAST가 불을 질러본다. 이 듀얼 코어(Dual-core) 보안망이 현존하는 DevSecOps의 최종 테크 트리다.

## Ⅴ. 실무 적용 방안 및 결론

**적용 방안 3개:**
1. [OWASP ZAP 연동 GitHub Actions 야간(Nightly) 스캐닝 튜닝] MSA 50개 환경에서 배포 병목을 막기 위해, 메인 CI는 통과시키되 매일 새벽 3시(Cron) 스테이징 K8s 클러스터를 향해 ZAP 봇(Docker)이 DAST 크롤링을 수행하도록 세팅. 아침 9시 출근 시 슬랙(Slack)으로 요약된 해킹 취약점 리포트만 받아보는 비동기(Asynchronous) 보안망 구축
2. [OAS(Swagger) 명세 주입 기반 API DAST 타겟팅 최적화] 현대의 REST API는 숨겨진 파라미터가 많아 봇이 멍청하게 크롤링하면 스캔율이 10% 미만으로 떨어짐. 이를 타파하기 위해 백엔드의 `Swagger(OpenAPI Spec)` JSON 파일을 DAST 스캐너에 직결(Injection). 스캐너가 API 스펙을 100% 인지하고 빈틈없이 퍼징 공격(Fuzzing)을 박아 넣는 API 중심 방어망(API-Sec) 전개
3. [IAST 융합형 에이전트(Agent) 배포로 디버깅 지옥 타파] DAST의 치명적 단점인 '위치 추적 불가'를 잡기 위해, 스테이징 WAS(Tomcat/Node) JVM에 IAST 에이전트를 부착. 밖에서 DAST가 때려 에러가 날 때 내부 에이전트가 호출 스택(Call Stack)을 가로채어 "Controller.java 55번 줄 SQL 변수"라고 정확히 포인팅(Pointing)해 주는 궁극의 화이트/블랙박스 하이브리드 결합

**결론:**
- 기술사 판단: 동적 분석(DAST)은 애플리케이션 보안의 최종 수비수(Sweeper)다. 코드의 구조만 파고드는 정적 분석(SAST)의 시야 맹점(Runtime, Infra Config)을 외부 공격자(Hacker)의 시야로 타격하여, 이론적 취약점이 아닌 '실제로 뚫리는 리얼 결함'을 증명해 낸다. 디버깅의 어려움과 막대한 스캔 시간이라는 무거운 비용이 따르지만, MSA와 클라우드 인프라가 유기적으로 엮인 현대 시스템에서 런타임 검증을 건너뛰는 것은 방화문 없이 건물을 오픈하는 자살 행위와 같다.
- 향후 방향: 최근 마이크로서비스 간 통신(API)이 폭증함에 따라, 전통적인 웹 화면 UI 크롤링(Selenium 연동) 중심의 DAST는 도태되고, API 스펙(Swagger/GraphQL)을 기계적으로 읽어 API 엔드포인트만 광속으로 퍼징(Fuzzing)하는 **API-DAST(또는 API Security Testing)**로 스캐닝의 축이 급격히 이동하고 있다.
