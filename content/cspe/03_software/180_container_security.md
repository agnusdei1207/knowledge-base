## 핵심 인사이트 (3줄 요약)
- 0.1초 만에 앱을 띄우는 컨테이너의 기동성은 **'호스트 OS의 커널(심장)을 모든 컨테이너가 공유한다'**는 구조적 특성에서 오며, 이는 곧 **한 놈이 털리면 전체 서버가 털릴 수 있는 치명적 보안 취약점**을 의미함.
- 이를 막기 위해 ①이미지 자체의 악성코드 검사(Shift Left), ②컨테이너 실행 시 권한 박탈(Rootless), ③비정상 행위 차단(Runtime Security)이라는 3단계 방어선을 구축해야 함.
- "내가 만든 도커 이미지는 안전하다"는 오만을 버리고, 컨테이너 라이프사이클 전체(Build ➡️ Ship ➡️ Run)에 걸쳐 보안을 자동화하는 DevSecOps 체계를 내재화하는 것이 핵심임.

## Ⅰ. 개요 및 필요성
- **개요**: 컨테이너 이미지 빌드부터 레지스트리 저장, 런타임 실행까지 컨테이너 생명주기 전반에 걸친 보안 위협을 식별하고 방어하는 기술 체계.
- **필요성**: 개발자가 아무 생각 없이 인터넷(Docker Hub)에서 다운받은 `mysql` 이미지 안에 몰래 비트코인 채굴기가 심어져 있었음. 이 컨테이너가 사내 쿠버네티스에서 실행되자, 호스트 서버의 '루트(root) 권한'을 탈취(Container Breakout)하여 사내망 전체를 쑥대밭으로 만듦. 가상머신(VM)과 달리 격리벽이 얇은 컨테이너 아키텍처만의 특화된 보안 대책이 절실해짐.
---
## Ⅱ. 아키텍처 및 핵심 원리 (생명주기별 보안)
- **1. Build 단계 (이미지 보안 - Shift Left)**:
  - **이미지 취약점 스캐닝**: 개발자가 코드를 `git push`할 때(CI 과정), Trivy나 Clair 같은 도구가 도커 이미지를 뜯어보고 "여기에 오래된 파이썬 해킹 취약점(CVE)이 있어!"라고 경고하며 배포를 막아버림.
  - **경량 베이스 이미지 사용**: 우분투(Ubuntu) 같은 거대한 OS 이미지 대신, 꼭 필요한 파일만 있는 `Alpine` 리눅스나 아예 껍데기만 있는 `Distroless` 이미지를 써서 해커가 들어와도 쓸 툴(쉘 스크립트 등)이 없게 만듦.
- **2. Ship 단계 (레지스트리 및 유통 보안)**:
  - **이미지 서명 (Image Signing)**: "이 이미지는 우리 회사 공식 빌드 서버가 구운 진품이 맞다!"라고 도장(Notary)을 찍음.
  - 쿠버네티스는 도장(서명)이 없는 불법 이미지는 아예 다운로드조차 하지 않도록 설정함.
- **3. Run 단계 (런타임 보안 - 실행 통제)**:
  - **루트 권한 박탈 (Non-Root)**: 컨테이너 안의 앱을 `root(관리자)` 계정으로 돌리면 해킹 시 서버 전체가 털림. 무조건 일반 `user` 계정으로 실행되도록 설정함.
  - **특권 탈취 방지 (Privilege Escalation)**: 컨테이너가 호스트의 커널을 건드리지 못하게 권한을 엄격하게 자름.
  - **런타임 감시 (Falco)**: 컨테이너 안에서 갑자기 `/etc/shadow(비밀번호 파일)`를 읽으려는 수상한 행동이 포착되면 즉시 차단하고 경고를 보냄.

```text
[ 컨테이너 생명주기별 방어 체계 (DevSecOps) ]

 🛠️ [ Build (코드 작성) ] ➡️ Shift Left (왼쪽으로 당겨서 미리 방어!)
 - 행동: 개발자가 Dockerfile 작성.
 - 보안: 베이스 이미지 축소 (Distroless), CI 파이프라인에서 이미지 취약점 스캔 (Trivy).

 📦 [ Ship (저장소 보관) ] 
 - 행동: Docker Hub / 사내 레지스트리에 저장.
 - 보안: 이미지 서명 (이거 진짜 우리 거 맞음!), 위변조 방지.

 🚀 [ Run (K8s에서 실행) ]
 - 행동: 쿠버네티스 파드로 실행.
 - 보안: root 권한 금지 (SecurityContext), 런타임 이상 행위 감지 (Falco).
```

## Ⅲ. 비교 및 연결
| 취약점 유형 | 발생 원인 | 핵심 방어 대책 (기술사 관점) |
|---|---|---|
| **이미지 취약점** | 낡은 라이브러리, 악성 베이스 이미지 사용 | CI/CD 파이프라인 연동 이미지 스캐닝, **Distroless 이미지** |
| **컨테이너 탈옥 (Breakout)**| 컨테이너가 Host OS의 커널 취약점을 공격하여 탈출 | **루트 권한 박탈 (Rootless/Non-root)**, 권한 축소 (Capabilities) |
| **비인가 이미지 실행** | 개발자가 임의로 외부 이미지를 가져와 K8s에 띄움 | OPA Gatekeeper를 통한 **서명된 이미지만 실행 허용** 규칙 강제 |
| **과도한 권한 (Privileged)**| Host의 모든 장치 접근 권한을 컨테이너에 줘버림 | `privileged: false` 강제화, 샌드박스 런타임(gVisor) 도입 |

## Ⅳ. 실무 적용 및 기술사 판단
- **Shift Left (보안의 좌측 이동)**: 기술사가 보안 아키텍처를 설계할 때 가장 강조해야 할 키워드. 옛날에는 운영 서버(오른쪽 끝)에 올린 뒤에야 방화벽으로 막으려 했음. 이제는 보안 검사를 개발자의 코딩/빌드 단계(왼쪽 시작점)로 끌어와서, 취약한 컨테이너 이미지는 아예 운영 서버 근처에도 못 가게 원천 차단하는 파이프라인을 구축해야 함.
- **쿠버네티스 Admission Controller (OPA/Gatekeeper)**: 개발자가 맘대로 `root` 권한으로 컨테이너를 띄우는 YAML을 K8s에 던졌음. 기술사는 K8s 문지기(Admission Controller)인 **OPA(Open Policy Agent)**를 설치하여, "루트 권한을 요구하는 파드는 쿠버네티스에 절대 들어올 수 없다(Deny)"라는 보안 정책(Policy as Code)을 인프라 레벨에서 강제해야 함.
---
## Ⅴ. 기대효과 및 결론
- "컨테이너는 빠르고 편하지만 위험하다"는 경영진의 우려를 불식시키고, 기업이 클라우드 네이티브 환경으로 안전하게 전환할 수 있는 강력한 보안 방패를 제공함.
- 수동적인 보안 점검에서 벗어나, 코드 빌드부터 배포, 실행까지 모든 과정에 보안이 물 흐르듯 자동화되는 **진정한 DevSecOps의 완성**을 이끌어냄.

### 👶 어린이를 위한 3줄 비유 설명
1. 컨테이너(앱)들은 하나의 큰 아파트(서버)를 나눠 쓰는데, 벽이 얇아서 한 집에 강도가 들면 옆집까지 쉽게 뚫려요(탈옥).
2. 그래서 ①집에 들어오기 전에 짐 검사를 철저히 하고(이미지 스캔), ②집 안에서는 날카로운 칼(루트 권한)을 못 쓰게 뺏어버려요.
3. ③그리고 방마다 CCTV(런타임 감시)를 달아서 이상한 행동을 하면 바로 경찰을 부르는 완벽한 3중 보안 시스템이랍니다!
