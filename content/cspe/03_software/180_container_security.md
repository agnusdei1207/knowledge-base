# 📖 【암기용】 개념 완전 이해

## 한눈에
- **개요**: 컨테이너 환경의 근본적 취약점인 '호스트 커널 공유' 리스크를 방어하기 위해, 시스템 호출(Syscall) 제어와 접근 권한을 세밀하게 통제하는 보안 매커니즘들이다.
- **왜 필요한가**: 컨테이너 안에서 루트(Root) 권한을 뺏기면, 가상머신(VM)과 달리 커널이 하나뿐이므로 호스트 전체가 장악될 수 있다. 컨테이너가 할 수 있는 행동 반경을 철저히 묶어둬야 한다.
- **핵심 직관**: Seccomp은 "이 단어(Syscall)는 쓰지 마", AppArmor는 "이 방(파일/네트워크)엔 들어가지 마", OPA는 "이 건물(클러스터)의 출입 규정(Policy)은 이렇다"고 통제하는 보안 요원들이다.

## 핵심 용어 정리

| 용어/표기 | 의미 | 비유·예 |
|:---|:---|:---|
| Seccomp (Secure Computing) | 프로세스가 커널에 요청하는 시스템 콜(Syscall) 종류를 제한 | "위험한 명령어(예: 권한 상승) 사용 금지" |
| AppArmor | 리눅스 커널 보안 모듈로, 프로그램 단위로 파일/네트워크 접근 권한 제어 | "특정 앱은 /etc/ 폴더 접근 금지" |
| OPA (Open Policy Agent) | 클러스터 전체 리소스 배포 규정을 검증하는 범용 정책 엔진 (Rego 언어 사용) | "사내 배포 규정 심사 위원회" |
| 컨테이너 탈옥 (Escape) | 컨테이너 내의 권한을 이용해 호스트 OS 권한까지 탈취하는 행위 | "감방(컨테이너)에서 간수실(호스트)로 침투" |

## 깊이 이해
- **배경·문제의식**: 컨테이너는 VM 대비 격리성이 약하다. 해커가 웹 컨테이너를 뚫고 루트 권한을 얻으면 `mount`, `chown` 같은 시스템 콜을 날려 호스트 커널을 공격할 수 있다(컨테이너 탈옥). 이를 막으려면 컨테이너 실행 환경 자체를 하드닝(Hardening)해야 한다.
- **작동 원리**:
  - **Seccomp**: 리눅스 커널 기능으로, 300여 개의 시스템 콜 중 컨테이너에 꼭 필요한 70여 개만 허용(화이트리스트)하고 나머지는 차단한다.
  - **AppArmor**: 프로파일을 씌워 Nginx 컨테이너가 `/var/www` 외의 디렉토리를 읽거나 쓰지 못하게 MAC(Mandatory Access Control) 방식으로 통제한다.
  - **OPA**: 위 두 가지가 노드(OS) 단의 통제라면, OPA는 K8s API 서버 단에서 "Root 권한 컨테이너는 배포 자체를 불허한다"는 클러스터 전체 규정을 강제한다.
- **비유**: Seccomp은 작업자(컨테이너)의 도구 상자에서 망치나 톱(시스템 콜)을 뺏는 것이고, AppArmor는 작업자가 들어갈 수 있는 방(파일 경로)을 제한하는 것이며, OPA는 위험한 작업자를 현장에 아예 출입시키지 않는(API 거부) 게이트키퍼다.
- **구체 예시**: `securityContext: seccompProfile: type: RuntimeDefault`를 K8s 파드 YAML에 넣으면, 도커가 정의한 기본 Seccomp 프로파일이 적용되어 위험한 시스템 콜이 즉각 차단(Kill)된다.
- **흔한 오해·주의점**: 세 기술 중 하나만 쓰면 안전하다고 착각하기 쉽다. OPA는 배포 전 검증이고, Seccomp/AppArmor는 런타임 제어이므로 다층 방어(Defense in Depth) 차원에서 결합해야 한다.

## 연결 개념
- Rootless 컨테이너 — 컨테이너 엔진 자체를 호스트의 루트 권한 없이 실행하여 원천적 탈옥 위험 방지
- Trivy / Clair — 컨테이너 이미지 내부의 라이브러리 취약점(CVE)을 스캔하는 도구
- eBPF / Falco — 런타임에 커널 이벤트를 감시하여 비정상 행위(쉘 실행 등)를 실시간 탐지

# 📝 【답안용】 시험 답안 템플릿

## 핵심 인사이트 (3줄 요약)

> 1. **본질**: 컨테이너 보안은 커널 공유 아키텍처의 약점(탈옥)을 막기 위해 API(OPA), 시스템 콜(Seccomp), 자원 접근(AppArmor) 계층별로 통제하는 다층 방어 체계다.
> 2. **가치**: 코드 취약점으로 컨테이너가 침해당하더라도, 호스트 커널이나 클러스터 전체로 피해가 확산되는 측면 이동(Lateral Movement)을 원천 차단한다.
> 3. **판단 포인트**: K8s 파드 배포 단계에서 OPA(게이트키퍼)로 취약한 스펙을 쳐내고, 런타임에는 Seccomp과 AppArmor를 파드 단위로 강제하여 최소 권한 원칙을 실현해야 한다.

## 출제 의도 및 답안 포인트

| 출제 의도 | 반드시 짚을 핵심 | 감점 회피 포인트 |
|:---|:---|:---|
| 컨테이너 격리 한계와 보안 통제 메커니즘 이해 | 커널 공유 한계, Seccomp(Syscall)/AppArmor(자원)/OPA(API)의 역할 차이 | 세 기술을 구분 없이 모두 '방화벽' 류로 뭉뚱그려 서술 |

> 요약: 호스트 침해(Escape)를 막기 위해 K8s 배포 파이프라인부터 리눅스 커널 실행 단까지 이어지는 단계별 통제(Defense in Depth) 구조를 매핑해야 한다.

---

## Ⅰ. 개요 및 필요성

- 개요: 컨테이너의 호스트 커널 공유 취약점을 노린 탈옥(Escape) 공격을 막기 위해 클러스터 정책, 시스템 호출, 접근 권한을 제한하는 하드닝 보안 메커니즘
- 배경: 애플리케이션 취약점(예: Log4j)으로 컨테이너가 장악되었을 때, 무제한 시스템 콜과 Root 권한 구동 관행으로 인해 노드 전체가 장악되는 사고 빈발
- 필요성: 관리자의 수동 점검 한계를 벗어나, 클러스터 배포 시점(OPA)과 런타임 실행 시점(Seccomp/AppArmor)에 강제적인 최소 권한 통제(Zero Trust) 필수

---

## Ⅱ. 구조 및 구성요소

```text
Developer -> kubectl apply (Pod YAML)
                   |
             [Admission Control] -> OPA (Gatekeeper): 보안 정책 위반 시 거부 (Root 금지)
                   |
             [Kubelet & Runtime] -> AppArmor: 파드별 파일/네트워크 MAC 통제 적용
                   |             -> Seccomp: 컨테이너 프로세스의 Syscall 화이트리스트 적용
             [Host OS Kernel]
```

| 구성요소 | 통제 계층 | 주요 역할 및 특징 |
|:---|:---|:---|
| OPA (Gatekeeper) | API Server (Admission) | Rego 언어를 활용한 K8s 리소스 통합 보안 정책(예: Root 구동 불가) 검증/차단 |
| Seccomp | 리눅스 커널 (Syscall) | 프로세스가 커널에 요청하는 시스템 호출(예: `ptrace`, `chown`)을 식별하여 필터링 |
| AppArmor / SELinux | 리눅스 커널 (LSM) | 프로그램 단위로 파일 시스템, 네트워크, IPC 접근을 제한하는 강제 접근 통제(MAC) |

> 요약: K8s API 진입로에서는 OPA가 불량 파드를 걸러내고, 노드에 구동된 파드는 Seccomp과 AppArmor가 커널 단위에서 행동 반경을 통제한다.

---

## Ⅲ. 동작원리 및 흐름도

```text
Pod 배포 요청 -> OPA 검증(Admission) -> 통과 시 파드 구동 -> Seccomp 필터 셋업 -> AppArmor 프로파일 매핑
```

- 1단계 [배포 검증]: API Server의 Validating Webhook이 OPA Gatekeeper를 호출하여 "해당 파드가 Root 권한(`runAsRoot`)을 요구하는지" 검증하여 위반 시 배포 거부(Deny)
- 2단계 [정책 주입]: 정상 파드가 노드에 스케줄링되면, Kubelet이 파드의 `securityContext`에 정의된 Seccomp 및 AppArmor 프로파일 경로 확인
- 3단계 [Syscall 제한 (Seccomp)]: 컨테이너 런타임이 파드 프로세스를 띄울 때 커널에 BPF 필터를 적용, 화이트리스트 외의 시스템 콜 발생 시 커널이 해당 프로세스 즉시 Kill
- 4단계 [자원 통제 (AppArmor)]: 런타임이 호스트에 사전 로드된 AppArmor 프로파일을 컨테이너에 매핑, 특정 민감 경로(`/etc`, `/proc`) 읽기/쓰기 차단

> 요약: OPA로 컴플라이언스(배포 규정)를 강제하고, 런타임에는 리눅스 보안 모듈(Seccomp, AppArmor)을 주입하여 이중 삼중으로 격리성을 보완한다.

## Ⅳ. 심화 비교 및 적용 판단

| 비교 축 | Seccomp | AppArmor | OPA (Open Policy Agent) | 선택 기준 |
|:---|:---|:---|:---|:---|
| 통제 대상 | 시스템 콜 (Syscall) | 파일, 디렉토리, 네트워크 자원 | K8s 리소스 YAML 명세 (API) | 통제 타겟의 계층 |
| 통제 주체 | 호스트 리눅스 커널 | 호스트 리눅스 커널 모듈 | K8s 컨트롤 플레인 (Webhook) | 동작 발생 위치 |
| 방어 성격 | 런타임 행위 방어 (하드웨어 레벨) | 런타임 접근 방어 (파일 레벨) | 정적 설정 방어 (설계 레벨) | 사전 차단 vs 사후 격리 |

> 요약: 세 기술은 경쟁 관계가 아니라 상호 보완적인 다층 방어(Defense in Depth) 요소이므로 클라우드 네이티브 보안을 위해 모두 융합 적용해야 한다.

**리스크·대응:**
- 과도한 통제로 인한 앱 장애: 강제적인 Seccomp/AppArmor 프로파일 적용 시 합법적인 애플리케이션 동작까지 차단(False Positive) → `Audit`(감사) 모드로 선행 가동하여 차단 로그를 수집 후 정교한 프로파일 작성 후 `Enforce` 모드로 전환 (지표: 차단 정책 오탐률 0%)
- 프로파일 관리 파편화: 수백 개의 파드마다 다른 커널 보안 설정을 수동 적용하기 어려움 → K8s `PodSecurityAdmission`(또는 Kyverno)을 도입해 네임스페이스 단위로 기본 보안 표준(Baseline/Restricted) 일괄 강제 (지표: 보안 비준수 파드 생성 0건)

## Ⅴ. 실무 적용 및 결론

**적용 방안 3개:**
1. 시프트 레프트(Shift-Left) 정책 파이프라인: CI/CD 파이프라인(Jenkins, ArgoCD)에 Conftest(OPA 기반) 연동하여, 개발자가 Commit한 YAML이 클러스터 보안 규정에 맞는지 빌드 전 단계에서 자동 거부
2. RuntimeDefault 일괄 활성화: Kubelet 설정에서 `--seccomp-default` 플래그를 활성화하여, 별도 명시가 없는 모든 컨테이너에 기본 Seccomp 프로파일(약 300개 중 44개 위험 syscall 차단) 강제 적용
3. eBPF 기반 행위 기반 탐지(Falco) 연계: Seccomp으로 사전 차단하지 못한 미지의 악성 쉘 실행 이벤트 등을 커널 레벨(eBPF)에서 실시간 캡처하여 관제 시스템(SIEM)으로 알람 전송하는 런타임 보안 아키텍처 결합

**결론 (2줄):**
- 기술사 판단: 컨테이너의 민첩성은 호스트 커널 공유라는 구조적 리스크를 동반하므로, OPA 사전 차단과 Seccomp/AppArmor 런타임 통제를 결합한 '제로 트러스트' 보안 샌드박스 구축이 필수적이다.
- 향후 방향: 보안 프로파일 수동 설정의 어려움을 극복하기 위해, 머신러닝이 컨테이너의 정상 행위를 학습하여 AppArmor/Seccomp 프로파일을 자동 생성해주는 인텔리전스 보안 플랫폼으로 고도화될 것이다.
