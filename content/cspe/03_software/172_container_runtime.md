# 📖 【암기용】 개념 완전 이해

## 한눈에
- **개요**: 컨테이너 런타임은 호스트 시스템에서 컨테이너의 실행, 이미지 관리, 생명주기를 담당하는 저수준 및 고수준 소프트웨어 컴포넌트이다.
- **왜 필요한가**: 쿠버네티스(K8s) 등 오케스트레이터가 특정 컨테이너 엔진(Docker)에 종속되지 않고 표준화된 방식으로 컨테이너를 제어하기 위해 필요하다.
- **핵심 직관**: 오케스트레이터(지휘자)의 명령을 받아 실제로 악기(컨테이너)를 연주하는 연주자(런타임) 역할을 한다.

## 핵심 용어 정리

| 용어/표기 | 의미 | 비유·예 |
|:---|:---|:---|
| 컨테이너 런타임 | 컨테이너 생명주기를 관리하는 실행 계층 | "악기 연주자" |
| OCI (Open Container Initiative) | 컨테이너 런타임 및 이미지 표준 규격 | "악보 및 연주 표준" |
| CRI (Container Runtime Interface) | K8s와 컨테이너 런타임 간의 통신 표준 인터페이스 | "지휘자와 연주자 간 수신호" |
| runc | OCI 표준을 준수하여 실제로 컨테이너 프로세스를 띄우는 저수준 런타임 | "실제 소리를 내는 동작" |

## 깊이 이해
- **배경·문제의식**: 초기 K8s는 Docker만을 기본 런타임으로 지원하여 아키텍처가 무거웠다. 이후 Docker 종속성을 탈피하고 런타임 교체의 유연성을 얻기 위해 CRI 표준이 등장하며 containerd, CRI-O 등의 경량 런타임이 부상했다.
- **작동 원리**: K8s Kubelet이 CRI를 통해 고수준 런타임(containerd, CRI-O)에 명령을 내리면, 고수준 런타임은 이미지를 관리하고 저수준 런타임(runc)을 호출하여 호스트 커널(namespace, cgroups) 상에 프로세스를 격리 실행한다.
- **비유**: K8s가 "이런 컨테이너 띄워줘"라고 공통 양식(CRI)으로 주문하면, 주방장(containerd/CRI-O)이 재료(이미지)를 준비하고 조수(runc)에게 요리(프로세스 실행)를 시키는 과정이다.
- **구체 예시**: Docker 데몬 없이도 containerd만으로 K8s 노드를 운영하면 메모리 사용량이 크게 줄어들고 파드(Pod) 기동 속도가 단축된다. K8s v1.24부터 Docker shim 지원이 중단되었다.
- **흔한 오해·주의점**: "Docker가 K8s에서 퇴출되었다"는 말은 반은 맞고 반은 틀리다. K8s 런타임으로서의 Docker 데몬 지원이 중단된 것일 뿐, 개발자가 로컬에서 만든 Docker 이미지는 OCI 표준이므로 K8s(containerd)에서 정상 동작한다.

## 연결 개념
- 쿠버네티스 (Kubernetes) — CRI를 통해 런타임을 호출하는 오케스트레이터
- Docker — 초기 컨테이너 혁명을 이끌었으나 현재는 containerd로 핵심 기능 분리
- Kata Containers — runc 대신 가상 머신 기반으로 컨테이너를 띄우는 보안 런타임

## 핵심 인사이트 (3줄 요약)

> 1. **본질**: 컨테이너 런타임은 이미지 관리와 프로세스 격리 실행을 전담하는 소프트웨어로 OCI 및 CRI 표준을 준수한다.
> 2. **가치**: K8s의 Docker 종속성을 제거하여 플랫폼 경량화, 기동 속도 향상, 런타임 선택의 자율성을 제공한다.
> 3. **판단 포인트**: 운영 환경의 목적에 따라 범용성 높은 containerd, K8s 전용 초경량 CRI-O, 보안 중심의 Kata Containers 중 적합한 런타임을 선택해야 한다.

## Ⅰ. 개요 및 필요성

- 개요: 컨테이너 런타임은 OCI(이미지/런타임 규격) 표준을 준수하여 컨테이너 프로세스의 생성 및 생명주기를 전담하는 실행 환경
- 배경: K8s 생태계 발전 과정에서 특정 엔진(Docker)에 대한 강한 결합도를 낮추고 무거운 데몬 구조를 경량화할 필요성 대두
- 필요성: 다양한 런타임(보안형, 경량형)을 플러그인처럼 교체 사용할 수 있도록 CRI 기반의 표준화된 인터페이스 필수적임

---

## Ⅱ. 구조 및 구성요소

```text
Kubelet -> CRI -> 고수준 런타임 (containerd / CRI-O)
                   |-> 이미지 Pull 및 라이프사이클 관리
                   +-> 저수준 런타임 (runc) -> OS 커널 (namespace / cgroups) 격리
```

| 구성요소 | 역할 | 특이사항 |
|:---|:---|:---|
| CRI (Container Runtime Interface) | K8s Kubelet과 런타임 간의 gRPC 기반 통신 표준 | 런타임 디커플링 핵심 |
| 고수준 런타임 (High-level) | 이미지 다운로드, 압축 해제, 저수준 런타임 API 호출 제어 | containerd, CRI-O |
| 저수준 런타임 (Low-level) | 호스트 커널과 직접 통신하여 실제 격리된 프로세스(컨테이너) 구동 | runc, Kata, gVisor |

> 요약: Kubelet의 요청은 CRI를 거쳐 고수준 런타임이 이미지를 준비하고 저수준 런타임이 커널 자원을 할당해 컨테이너를 기동하는 3단계 계층 구조를 갖는다.

---

## Ⅲ. 동작원리 및 흐름도

```text
Pod 실행 요청 -> Kubelet (CRI 호출) -> 이미지 준비(고수준 런타임) -> 컨테이너 생성(저수준 런타임)
```

- 1단계 [Pod 요청 수신]: API Server의 요청을 받은 Kubelet이 CRI gRPC API를 통해 런타임에 Pod 생성 명령 전달
- 2단계 [이미지 및 스토리지 준비]: containerd 또는 CRI-O가 OCI 레지스트리에서 이미지를 Pull 하고 RootFS 샌드박스 구성
- 3단계 [컨테이너 프로세스 기동]: 고수준 런타임이 runc를 호출하여 config.json 기반 커널 격리 공간(네임스페이스) 생성
- 4단계 [상태 모니터링]: 런타임이 컨테이너의 구동 상태(UP)를 감지하고 Kubelet에 상태 동기화 보고

> 요약: 런타임 기동은 Kubelet의 CRI 호출에서 시작하여 이미지 적재, runc 커널 격리, 상태 보고 순으로 동작한다.

---

## Ⅳ. 특징

- [표준화 기반 확장성]: CRI와 OCI 분리 설계로 K8s 핵심 코드 수정 없이 다양한 런타임을 자유롭게 플러그인 교체 가능
- [구조 경량화 효과]: Docker 데몬(dockerd) 레이어를 제거하여 CPU/Memory 오버헤드 감소 및 파드 기동 지연 단축
- [보안 격리 한계]: 기본 runc는 커널을 공유하므로 단일 커널 패닉 시 노드 전체 마비 리스크가 상존함

> 요약: 표준화를 통해 런타임 교체의 유연성과 성능 경량화를 확보하였으나, 호스트 커널 공유에 따른 근본적 보안 취약점은 여전하다.

## Ⅴ. 심화 비교 및 적용 판단

| 비교 축 | containerd | CRI-O | Kata Containers | 선택 기준 |
|:---|:---|:---|:---|:---|
| 구조/목적 | 범용적 고수준 런타임 | K8s 전용 초경량 런타임 | 경량 가상머신(MicroVM) 기반 | 도입 목적 및 생태계 |
| 성능/가벼움 | 중간 수준 (다양한 기능 지원) | 매우 가벼움 (CRI 최소 충족) | 상대적으로 무거움 (VM 부팅) | 집적도 요구사항 |
| 보안 격리성 | 커널 공유 (일반 런타임) | 커널 공유 (일반 런타임) | 하드웨어 수준 완전 격리 | 멀티 테넌시 민감도 |

> 요약: 범용적인 운영에는 containerd, 극한의 성능 최적화에는 CRI-O, 멀티 테넌시 보안 환경에는 Kata Containers를 선택한다.

**리스크·대응:**
- 호스트 침해 위협: 악성 컨테이너가 커널 취약점을 통해 노드 권한 탈취 → gVisor, Kata Containers 같은 샌드박스 런타임 혼용 배치 (지표: 무단 권한 상승 건수 0건)
- 레거시 호환성 장애: K8s v1.24 이후 Docker shim 제거로 인한 이전 스크립트 오류 → containerd 전환 전 CI 파이프라인 사전 테스트 (지표: 배포 성공률 100%)

## Ⅵ. 실무 적용 및 결론

**적용 방안 3개:**
1. 표준 런타임 전환: 신규 K8s 클러스터 구축 시 기본 런타임을 Docker에서 containerd로 전면 전환하여 워커 노드 리소스 절감
2. RuntimeClass 적용: K8s의 RuntimeClass 리소스를 활용하여 일반 파드는 runc로, 보안 파드는 Kata Containers로 노드 내 혼용 배포 체계 구축
3. 이미지 최적화 연계: OCI 호환 레지스트리(Harbor)와 연계하여 런타임에서 이미지 Pull 시 취약점 스캔(Trivy)을 강제화하는 방안 적용

**결론 (2줄):**
- 기술사 판단: 컨테이너 런타임 표준화(OCI/CRI)는 플랫폼 벤더 종속성을 끊어내고 인프라 운영의 경량화와 안정성을 동시에 높이는 아키텍처 진화의 핵심이다.
- 향후 방향: 앞으로의 런타임은 eBPF 기반의 관측성 내재화와 WASM(WebAssembly) 지원을 통해 컨테이너보다 가벼운 실행 환경으로 영역이 확장될 것이다.
