## 미리 알고가기

- 서비스 메시는 서비스 간 통신 제어를 애플리케이션 코드와 분리하는 인프라 계층임
- 데이터 플레인은 서비스 트래픽을 중계하며 라우팅·보안 정책과 텔레메트리를 처리함
- 제어 플레인은 서비스·정책 정보를 데이터 플레인 프록시에 배포함
- 사이드카 모드는 워크로드마다 프록시를 배치하고 L4·L7 트래픽을 처리함
- 앰비언트 모드는 노드 단위 L4 프록시와 선택적 L7 웨이포인트를 사용함
- mTLS는 워크로드 신원을 인증하고 서비스 간 트래픽을 암호화함

## 작성 근거(검토용)

- Istio는 제어·데이터 플레인 분리, 트래픽 정책, 워크로드 신원, 텔레메트리를 핵심 축으로 설명함
- 비교표는 사이드카와 앰비언트의 프록시 배치·L7 처리·도입·자원·운영 주체를 대비함
- 절차는 정책이 Istiod를 거쳐 프록시에 배포되고 요청 경로에서 집행되는 순서를 따름

## Ⅰ. 개요

- **정의/개념**: Istio는 제어 플레인이 서비스 통신 정책을 배포하고 데이터 플레인 프록시가 라우팅·mTLS·인가·텔레메트리를 집행하는 서비스 메시임
- **배경/필요성**: 마이크로서비스마다 재시도·트래픽 분할·서비스 인증 코드를 중복 구현하지 않기 위해 통신 제어 계층이 필요함

## Ⅱ. 특징

- Istiod가 서비스 발견과 정책을 프록시 설정으로 변환해 데이터 플레인에 배포함
- 가중치 라우팅·재시도·타임아웃·회로 차단을 애플리케이션 배포와 분리함
- 워크로드 신원 기반 mTLS와 인가 정책으로 서비스 간 호출 범위를 통제함
- 프록시는 요청률·오류율·지연을 수집하며 분산 추적은 애플리케이션의 문맥 전파가 필요함

## Ⅲ. 종류 및 비교

| 판단 기준 | 사이드카 모드 | 앰비언트 모드 |
|:---|:---|:---|
| 프록시 배치 | 각 Pod에 Envoy 프록시 배치 | 노드 L4 프록시와 선택적 L7 웨이포인트 배치 |
| 기본 처리 범위 | 각 프록시가 L4·L7 처리 | 노드 프록시가 L4 처리, 웨이포인트가 L7 처리 |
| 워크로드 편입 | 사이드카 주입 후 Pod 재시작 | 레이블 설정으로 편입하며 Pod 재시작 불필요 |
| 자원 단위 | Pod마다 프록시 CPU·메모리 할당 | 노드·웨이포인트 단위로 자원 할당 |
| 운영 주체 | 애플리케이션과 프록시 수명주기 결합 | 플랫폼이 공유 프록시 수명주기 관리 |
| 적합 조건 | 워크로드별 L7 기능과 격리가 필요 | L4 보안을 기본 적용하고 L7 기능을 선택할 때 |

> 요약: 사이드카는 Pod마다 L4·L7 프록시를 두고, 앰비언트는 L4와 선택적 L7 프록시를 분리함.

## Ⅳ. 구성요소 및 구조

| 구성요소 | 설명 |
|:---|:---|
| Istiod | 서비스 발견·트래픽·보안 정책을 프록시 설정과 인증서로 배포함 |
| 사이드카 프록시 | 각 워크로드의 L4·L7 트래픽과 정책·텔레메트리를 처리함 |
| ztunnel | 노드에서 워크로드의 L4 연결·mTLS·인가를 처리함 |
| 웨이포인트 프록시 | 앰비언트 모드에서 L7 라우팅·인가·텔레메트리를 처리함 |
| 인그레스·이그레스 게이트웨이 | 메시 경계의 외부 유입·유출 트래픽에 정책을 적용함 |
| 정책 리소스 | 라우팅·복구·인증·인가 조건을 선언함 |
| 텔레메트리 연동 | 프록시 메트릭·로그·추적 정보를 관측 백엔드로 전달함 |

```text
정책 리소스 -> Istiod -> 사이드카 또는 ztunnel·웨이포인트
                              |
클라이언트 서비스 ---------->+----------> 대상 서비스
                              |
                              +-> 메트릭·로그·추적
```

> 요약: Istiod가 선언 정책을 프록시에 배포하고 프록시가 서비스 호출 경로에서 정책과 텔레메트리를 처리함.

## Ⅴ. 원리 및 절차 흐름도

```text
정책 등록 -> Istiod 검증·변환 -> 프록시 설정 배포 -> 요청 중계·정책 집행 -> 텔레메트리 기록
```

1. **정책 등록**: 운영자가 라우팅·mTLS·인가 정책을 선언함
2. **검증·변환**: Istiod가 서비스 정보와 정책을 데이터 플레인 설정으로 변환함
3. **설정 배포**: Istiod가 변경된 설정과 인증서를 대상 프록시에 전달함
4. **정책 집행**: 프록시가 요청을 중계하며 라우팅·인증·인가 조건을 적용함
5. **관측 기록**: 프록시가 요청 결과와 지연을 텔레메트리 백엔드로 전송함

> 요약: 선언 정책은 Istiod에서 프록시 설정으로 변환되고 서비스 요청 경로에서 집행됨.

## Ⅵ. 실무 사례

1. API 카나리는 Istio 가중치 라우팅을 적용하고 버전별 오류율·p99 지연을 확인함
2. 내부 API는 워크로드 mTLS·인가 정책을 적용하고 인증 실패·정책 거부 건수를 확인함

## Ⅶ. 결론

- Istio는 서비스 통신 정책을 코드와 분리하고 프록시 자원·L7 요구에 따라 데이터 플레인 모드를 선택함
