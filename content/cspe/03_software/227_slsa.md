## Ⅰ. 개요
- **정의**: SW 빌드 과정의 무결성을 검증 가능하게 보장하는 공급망 보안 프레임워크임
- **배경/필요성**: 소스에서 빌드·배포까지의 경로에서 변조가 발생하면 최종 산출물 전체가 오염됨
- **비유**: 식품 HACCP처럼 원재료 입고부터 출하까지 각 단계의 위생(무결성)을 인증하는 체계와 유사함

| 출제 의도 | 반드시 짚을 핵심 | 감점 회피 포인트 |
|:---|:---|:---|
| 공급망 빌드 무결성 보장 방법 | SLSA 레벨(1~4) 단계별 요구사항 | SBOM(225 참조)과 역할 차이 명시 — SBOM은 구성 목록, SLSA는 빌드 무결성 |

> 요약: 소스→빌드→배포 경로의 변조를 방지하기 위한 단계별 보안 성숙도 프레임워크임

## Ⅱ. 구성요소
```text
+--------+    +--------+    +----------+
| Source |    | Build  |    | Artifact |
+---+----+    +---+----+    +----+-----+
    |             |              |
    +------+------+------+-------+
           |             |
      +----+----+   +----+-----+
      |Provenance|   |Verification|
      +---------+   +-----------+
```

| 구성요소 | 설명 | 비유 |
|:---|:---|:---|
| Source | 버전 관리된 소스 코드 저장소임 | 원재료 창고 |
| Build | 격리된 빌드 환경에서 산출물을 생성하는 과정임 | 밀봉 제조 공정 |
| Provenance | 빌드 입력·환경·출력을 서명하여 기록한 메타데이터임 | 생산 이력 증명서 |
| Verification | 소비자가 Provenance를 검증하여 변조 여부를 확인하는 단계임 | 이력 대조 검수 |

> 요약: Source-Build-Provenance-Verification 4요소로 빌드 경로의 무결성을 증명함

## Ⅲ. 절차
```text
Source --> Build --> Sign --> Verify
```
- 1단계: Source — 코드 변경을 리뷰하고 버전 관리 시스템에 커밋
- 2단계: Build — 격리된(hermetic) 빌드 환경에서 산출물 생성
- 3단계: Sign — 빌드 시스템이 Provenance 문서를 자동 생성하고 서명
- 4단계: Verify — 소비자가 서명과 Provenance를 검증하여 변조 없음을 확인

> 요약: Source-Build-Sign-Verify 4단계로 빌드 무결성 증거 체인을 형성함

## Ⅳ. 문제점
- 빌드 격리 비용: Hermetic 빌드 환경 구축에 인프라·운영 비용이 증가 — 소규모 조직 도입 장벽
- Provenance 위조 위험: 빌드 시스템 자체가 침해되면 서명된 Provenance도 신뢰 불가 — 신뢰 근원 문제
- 레벨 달성 복잡도: SLSA Level 3~4 요구사항 충족을 위한 파이프라인 재설계 부담 — 점진적 전환 필요

> 요약: 격리 비용, 빌드 시스템 침해 위험, 높은 레벨 달성 복잡도가 주요 과제임

## Ⅴ. 개선방안
1. 단기: GitHub Actions/Cloud Build 등 관리형 CI에서 SLSA Level 1 Provenance 자동 생성
2. 중기: 빌드 시스템 접근 제어와 감사 로그를 강화하여 신뢰 근원(Root of Trust) 보호
3. 장기: Hermetic 빌드와 2인 리뷰를 조직 표준으로 정착시켜 Level 3 이상 달성

> 요약: 관리형 CI 활용 → 빌드 시스템 보호 → Hermetic 빌드 표준화 순으로 레벨 향상

## Ⅵ. 전망
- 발전 방향: SBOM+VEX+SLSA 3종 세트가 SW 공급망 보안의 표준 스택으로 수렴함
- 기술사적 판단: 빌드 무결성 증명은 제로 트러스트 공급망의 핵심 요구사항임
- 기술사 제언: Level 1부터 점진적으로 도입하고, Provenance 검증을 배포 게이트로 운영할 것을 권고함
