# 📖 【암기용】 개념 완전 이해

> 목적: 소프트웨어 형상관리 기준선을 처음 보는 사람도, 기준선의 종류와 CCB·감사 절차까지 완전히 이해하게 만든다.

## 한눈에
- **개요**: 소프트웨어 기준선(Baseline)은 **형상관리(SCM, Software Configuration Management)**에서 요구사항·설계·코드·테스트·배포 산출물, 즉 **형상항목(CI, Configuration Item)의 특정 시점 버전 집합을 공식 승인해 이후 변경의 비교·통제 기준으로 고정한 것**이다.
- **왜 필요한가**: 무엇이 배포됐고 어떤 변경이 승인됐는지 기록이 없으면 결함이 어느 버전에서 들어왔는지 추적할 수 없고, 감사·롤백·재현 빌드가 모두 불가능해진다.
- **핵심 직관**: 건설 현장에서 승인 도면 번호를 기준으로 공사를 진행하고, 이후 변경은 반드시 변경 신청서(CR)로 관리하는 것과 같다.

## 핵심 용어 정리 (내부에 등장하는 것들)

| 용어 | 의미 | 비유 |
|:---|:---|:---|
| 형상관리(SCM) | 소프트웨어 산출물의 버전·변경·이력을 체계적으로 관리하는 활동 — 기준선이 소속되는 상위 개념 | 공사 전체의 도면·변경 관리 체계 |
| 형상항목(CI, Configuration Item) | 형상관리 대상이 되는 개별 산출물 단위(요구사항, 코드, 설정, 테스트) | 관리 번호가 붙은 개별 부품 |
| 기준선(Baseline) | 특정 시점 CI 집합을 승인해 고정한 참조점 | 승인된 공사 도면 |
| 기능기준선(Functional Baseline) | 요구사항 분석 완료·승인 시점의 기준선 | 설계 착수 전 확정한 스펙서 |
| 할당기준선(Allocated Baseline) | 상세설계 완료·승인 시점의 기준선 | 부품별로 나눠 그린 설계도 |
| 제품기준선(Product Baseline) | 개발·테스트 완료 후 인수 시점의 기준선 | 완성품 최종 도면 |
| CCB(형상통제위원회, Configuration Control Board) | 변경 요청을 심사해 승인·반려하는 의사결정 주체 | 공사 변경 결재 라인 |
| FCA(기능형상감사, Functional Configuration Audit) | 요구사항 대비 실제 기능이 충족됐는지 확인하는 감사 | 스펙대로 만들어졌는지 검사 |
| PCA(물리형상감사, Physical Configuration Audit) | 문서(설계)와 실제 산출물(코드·바이너리)이 일치하는지 확인하는 감사 | 도면과 실물 대조 |
| SBOM(Software Bill of Materials) | 산출물에 포함된 구성요소·라이브러리 목록 | 제품 성분표 |

## 깊이 이해

### 왜 기준선이 필요했나 (배경)
- 요구사항·설계·코드는 프로젝트 내내 계속 바뀐다. 기준이 되는 승인 시점이 없으면 "이 버그가 어느 요구사항 버전, 어느 코드 버전에서 들어왔는지"를 되짚을 수 없다. 이 문제는 군수·항공 소프트웨어(MIL-STD-483, IEEE 828)에서 먼저 표준화됐고, 이후 일반 SW 프로젝트의 릴리스 관리로 확산됐다.

### 3종 기준선을 시점으로 구분하기
- 기능기준선: 요구사항 명세서가 승인된 시점(예: 요구사항 명세서 v1.4 승인) — "무엇을 만들 것인가"가 고정된다.
- 할당기준선: 상세설계(API 설계 v2.1 등)가 승인된 시점 — "어떻게 나눠 만들 것인가"가 고정된다.
- 제품기준선: 코드·빌드·테스트가 모두 완료돼 배포 가능한 상태가 승인된 시점 — "실제로 무엇을 배포했는가"가 고정된다.

### 워크드 예제 — 릴리스 기준선 구성
- `release v2.3.0` 제품기준선은 다음을 하나로 묶어 승인한다: 요구사항 명세서 v1.4, API 설계문서 v2.1, Git tag `v2.3.0`, DB 마이그레이션 스크립트 `20260701`, 테스트 리포트(전체 통과율 100%).
- 이 5가지 중 하나라도 다른 버전이면 "같은 기준선"이라 부를 수 없다. 예를 들어 Git tag는 `v2.3.0`인데 DB 마이그레이션이 누락됐다면, 롤백 시 코드는 v2.3.0으로 되돌려도 DB 스키마가 맞지 않아 장애가 재발할 수 있다.

### 변경은 어떻게 기준선을 갱신하는가 (판별 원리)
- 절차: 형상항목 식별 → 버전 부여 → 기준선 승인 → (이후) 변경요청(CR) 접수 → 영향분석(요구사항·코드·테스트 중 몇 개가 영향받는지) → CCB 승인/반려 → 반영 → 검증 → 새 기준선으로 재설정.
- FCA/PCA 워크드 예: FCA에서 요구사항 120개 중 118개가 테스트로 충족 확인되면 2개는 결함으로 등록해 다음 기준선 전에 해결한다. PCA에서는 배포된 컨테이너 이미지의 checksum과 빌드 로그의 해시를 대조해, 실제 배포물이 승인된 코드와 정확히 일치하는지 확인한다.

### 비유와 흔한 오해
- 비유: 시험 답안 제출본을 기준으로 채점하고, 제출 이후 수정본은 별도의 정정 신청(재제출 승인)이 있어야만 반영되는 방식과 같다.
- 오해: 기준선을 Git tag 하나로 착각하기 쉽다. 하지만 기준선은 요구사항·설계·코드·빌드·테스트·배포 설정까지 연결된 "승인 상태" 전체를 의미하며, Git tag는 그중 코드 버전을 표시하는 수단 하나일 뿐이다.

## 연결 개념
- 형상항목(CI) — 기준선을 구성하는 관리 대상 산출물 단위
- 변경관리(CCB, 281편) — 기준선을 변경하기 위한 승인 절차
- 릴리스 관리 — 제품기준선을 기반으로 한 배포·롤백 실행

> 목적: 기준선을 식별, 승인, 변경 통제, 감사, 재현 빌드 관점으로 답안화한다.

## 핵심 인사이트 (3줄 요약)

> 1. **본질**: 소프트웨어 형상 관리 기준선은 승인된 형상 항목의 특정 버전 집합으로, 변경 통제와 추적의 기준점이다.
> 2. **가치**: 요구사항부터 배포 산출물까지 추적성을 확보해 감사, 결함 원인 분석, 롤백, 재현 빌드를 가능하게 한다.
> 3. **판단 포인트**: 기준선은 tag가 아니라 문서·코드·빌드·테스트·환경 설정을 연결한 변경 통제 단위로 작성해야 한다.

| 출제 의도 | 반드시 짚을 핵심 | 감점 회피 포인트 |

> 요약: 기준선 문제는 산출물 버전 고정과 변경 통제 절차를 함께 제시해야 한다.

## Ⅰ. 개요 및 필요성

- 개요: 소프트웨어 기준선은 승인된 산출물 버전 기준점이다.
- 배경: 요구사항, 설계, 코드, 테스트, 배포 환경이 계속 바뀌므로 기준선 없이는 변경 영향 분석과 감사가 어렵다.
- 필요성: 기준선 식별, 변경 통제, 상태 기록으로 재현 빌드와 장애 롤백 기준을 확보해야 한다.

---

## Ⅱ. 구조 및 구성요소

```text
Configuration Item -> Version Identification -> Baseline Approval
  -> Change Request -> Impact Analysis -> CCB Approval
  -> Baseline Update -> Audit/Release
```

| 구성요소 | 역할 | 특이사항 |
|:---|:---|:---|
| 형상 항목(CI) | 관리 대상 산출물 | 요구사항, 코드, 설정, 테스트 |
| 기준선 | 승인된 CI 버전 집합 | functional, allocated, product baseline |
| 변경 요청(CR) | 기준선 변경 제안 | 영향·비용·위험 포함 |
| 형상 감사 | 기준선 일치 확인 | FCA, PCA |

> 요약: 기준선은 형상 항목 식별, 버전 승인, 변경 요청, 감사 절차로 유지된다.

---

## Ⅲ. 동작원리 및 흐름도

```text
산출물 식별 -> 버전 부여 -> 기준선 승인
  -> 변경 요청 접수 -> 영향 분석 -> 승인/반려
  -> 변경 반영 -> 검증 -> 기준선 재설정
```

| 단계 | 처리 내용 | 검증 기준 |
|:---:|:---|:---|
| 1 | 형상 항목과 버전 체계 정의 | CI list 100% 등록 |
| 2 | 산출물 검토 후 기준선 승인 | approval record |
| 3 | 변경 요청·영향 분석 수행 | traceability matrix |
| 4 | 변경 후 감사·릴리스 반영 | build reproducibility |

> 요약: 기준선은 승인 후 고정되고, 변경은 요청·분석·승인·검증을 거쳐 새 기준선으로 갱신된다.

> 요약: 기준선 리스크는 불일치, 무단 변경, 재현 실패로 나누어 통제한다.

| 점검 항목 | 목표 기준 | 측정 방법 |
|:---|:---|:---|
| 추적성 | 요구사항-코드-테스트 연결률 100% | ALM trace report |
| 변경 통제 | 승인 없는 변경 0건 | audit log, branch rule |
| 재현성 | 동일 기준선 rebuild 성공률 100% | CI artifact hash |

> 요약: 기준선 관리는 추적성, 승인 통제, 재현 빌드 성공률로 판단한다.

## Ⅵ. 실무 적용 및 결론

**적용 방안 3개 (필수 — 단계별 또는 항목별):**
1. 요구사항 ID, 설계 문서 버전, Git tag, build artifact hash, DB migration, 테스트 리포트를 release manifest로 묶음.
2. 변경 요청은 Jira CR, 영향 분석, CCB 승인, protected branch merge, signed tag 순서로 통제함.
3. 릴리스 후 SBOM, lockfile, container digest, IaC version을 보관해 동일 기준선 재빌드 100%를 검증함.

**결론 (2줄):**
- 기술사 판단: 기준선은 Git tag가 아니라 요구사항부터 운영 설정까지 묶은 승인된 변경 통제 단위로 관리.
- 향후 방향: DevSecOps 환경에서는 SBOM, signed artifact, policy-as-code가 기준선 감사의 핵심 자료가 됨.
