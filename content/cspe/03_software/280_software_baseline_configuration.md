## 핵심 인사이트 (3줄 요약)
- **기준선(Baseline)**은 소프트웨어 생명주기(SDLC)에서 특정 시점마다 쾅쾅 찍는 **'공식 통과 도장(승인된 버전의 묶음)'**임. 이 도장이 찍힌 이후에는 누구도 함부로 내용을 바꿀 수 없음.
- 요구사항 분석이 끝나면 기능 기준선, 설계가 끝나면 분배 기준선, 테스트가 끝나면 제품 기준선을 설정하여, 거대한 프로젝트가 산으로 가지 않도록 통제하는 핵심 나침반임.
- 단순히 "Git Tag 달기"가 아니라, 요구사항 문서, 소스 코드, 테스트 결과물 전체가 **100% 일치함을 보장**하여, 1년 전의 버전을 완벽하게 재현(재현 빌드)하거나 버그 원인을 추적할 수 있게 만드는 품질 관리의 근간임.

## Ⅰ. 개요 및 필요성
- **개요**: 소프트웨어 개발 과정에서 공식적으로 검토되고 승인된 형상 항목(Configuration Item)들의 명세서이자, 향후 변경을 통제하기 위한 비교 기준점.
- **필요성**: 프로젝트 중간에 기획자가 구두로 "결제 버튼 빨간색으로 바꿔줘"라고 함. 개발자가 바꿈. 나중에 테스트팀이 "기획서엔 파란색인데 왜 빨개?"라며 에러 처리함. 기획자는 자기가 말한 걸 까먹음. **"아니, 수십 명이 일하는 프로젝트에서 특정 시점에 서로 합의된 공식 문서(코드)를 꽉 잠가버리고(Freeze), 이거 바꿀 땐 무조건 공식 결재를 받게 할 순 없을까?"**
---
## Ⅱ. 형상 관리 기준선의 핵심 유형 (통과 도장의 종류)
SDLC 진행 단계에 따라 3대(또는 4대) 기준선으로 나뉨.

### 1. 기능 기준선 (Functional Baseline)
- **시점**: 요구사항 분석 단계 종료 후.
- **내용**: 고객과 합의된 '요구사항 명세서'. "이대로 기능 만들어 줄게요!" 도장 쾅.

### 2. 분배/할당 기준선 (Allocated Baseline)
- **시점**: 시스템 설계 단계 종료 후.
- **내용**: 요구사항을 구현하기 위한 '설계 문서'. H/W와 S/W로 분배된 구조.

### 3. 제품/시험 기준선 (Product Baseline)
- **시점**: 구현 및 테스트(QA) 완료 후.
- **내용**: 실제 배포될 '소스 코드, 테스트 결과, 매뉴얼'. 완제품 도장 쾅.

```text
[ 기준선(Baseline)과 변경 통제의 원리 ]

 📄 [ V1.0 기능 기준선 승인 (도장 쾅!) ]
   ⬇️ (이 상태에서 누군가 수정을 원하면?)
 ❌ 개발자 맘대로 수정 불가 (형상 통제)
   ⬇️
 📝 공식 변경 요청서(CR, Change Request) 작성
   ⬇️
 ⚖️ 형상통제위원회(CCB)의 영향도 분석 및 승인 회의
   ⬇️ (승인 시)
 🛠️ 수정 반영 후 ➡️ 📄 [ V1.1 새로운 기준선 수립 ]
```
---
## Ⅲ. 실무 적용 및 기술사 판단
- **무결성 검증 (FCA/PCA 감사)**: 기준선이 잘 지켜졌는지 확인하기 위해 기술사는 감리를 수행함. **FCA(기능적 형상 감사)**를 통해 요구사항이 코드와 테스트로 100% 구현되었는지 추적성 매트릭스(RTM)를 확인하고, **PCA(물리적 형상 감사)**를 통해 설계서와 소스코드가 물리적으로 일치하는지, 승인 없는 코드가 섞이지 않았는지(MD5/SHA256 해시 검증) 확인해야 함.
- **현대적 기준선(Baseline) 관리 - GitOps**: 과거엔 엑셀과 워드로 기준선을 관리했다면, 현대 클라우드 네이티브 환경에서는 인프라 설정, 소스코드, 테스트 코드를 모두 **Git 저장소의 특정 커밋 해시(Commit Hash)나 Tag**로 묶어 '코드형(As-a-Code) 기준선'을 확립하고, CI/CD 파이프라인에서 자동으로 변조 여부를 통제하는 아키텍처를 구축해야 함.
---
## Ⅳ. 기대효과 및 결론
- "아, 그거 내가 저번에 말했잖아" 같은 주먹구구식 개발 문화를 청산하고, 모든 산출물이 완벽한 추적성(Traceability)을 가지도록 보장함.
- 장애가 발생했을 때 기준선 기반으로 즉각적인 롤백(Rollback)이 가능해지며, 10년이 지난 시스템도 당시 환경과 동일하게 100% 재현 빌드할 수 있는 강력한 무결성을 확보함.

### 📌 관련 개념 맵
- SDLC ➡️ Configuration Management (형상 관리) ➡️ Configuration Item (CI) ➡️ Baseline (기능/할당/제품) ➡️ Change Control Board (CCB) ➡️ FCA/PCA Audit

### 📈 관련 키워드 및 발전 흐름도
- 옛날: 압축파일(`최종.zip`, `진짜최종.zip`)로 코드 백업 관리 ➡️ 소프트웨어 공학의 발전으로 군수/항공 분야에서 엄격한 CMMI 기반 형상관리 체계 정립 (SVN, ClearCase 도입) ➡️ 중앙 집중식에서 분산 환경으로 진화 (Git의 등장) ➡️ 현재는 Immutable Infrastructure와 결합되어 소스, 인프라 컨테이너 이미지 전체를 묶어 배포 기준선으로 삼는 GitOps 시대로 진화 (현재)

### 👶 어린이를 위한 3줄 비유 설명
1. 레고 성을 만들 때, "1층 완성!" 하고 사진을 딱 찍어서 보관해 두는 게 바로 **기준선(Baseline)**이에요.
2. 기준선을 찍어두면, 2층을 만들다가 실수로 성이 무너져도 다시 사진(기준선)을 보고 1층 상태로 똑같이 복구할 수 있죠.
3. 그리고 1층을 다르게 고치고 싶을 때는 내 맘대로 부수면 안 되고, 반드시 '가족 회의(CCB)'를 열어서 허락을 받아야 한답니다!

### 🔀 문제 유형별 목차 전환 (이 키워드 출제 시)
- **설명/비교형 (Ⅱ·Ⅲ 강조)**: 형상 관리의 4단계(식별-통제-상태기록-감사) 중 통제와 감사의 기준점으로서 기준선의 역할을 강조. 기능/할당/제품 기준선의 시점과 특징 도식화.
- **실무/전략형 (Ⅳ·Ⅴ 강조)**: 형상통제위원회(CCB)의 역할, FCA/PCA 감사 절차, 현대 Agile/DevOps 환경에서 잦은 배포 시 기준선을 어떻게 자동화(Git Tag, Docker Image Digest)하여 관리할 것인지 서술.
