# 📖 【암기용】 개념 완전 이해

> 목적: 소프트웨어 형상 관리 기준선을 변경 통제의 기준이 되는 승인된 산출물 집합으로 이해하게 만든다.

## 한눈에
- **개요**: 기준선은 요구사항, 설계, 코드, 테스트, 배포 산출물을 특정 시점에 승인·고정한 참조점이다.
- **왜 필요한가**: 무엇이 배포됐고 어떤 변경이 승인됐는지 모르면 결함 추적, 감사, 롤백, 재현 빌드가 어렵다.
- **핵심 직관**: 건설 현장에서 승인 도면 번호를 기준으로 공사를 진행하고 변경은 변경 신청서로 관리하는 것과 같다.

## 깊이 이해
- **배경·문제의식**: 프로젝트 산출물은 계속 변한다. 변경 전후 기준이 없으면 요구사항 누락, 테스트 불일치, 배포 파일 혼선이 발생한다.
- **작동 원리**: 형상 항목을 식별하고, 특정 버전을 기준선으로 승인한 뒤, 변경 요청과 영향 분석을 거쳐 기준선을 갱신한다.
- **비유**: 시험 답안 제출본을 기준으로 채점하고, 이후 수정본은 별도 기록이 있어야 반영되는 방식이다.
- **구체 예시**: release `v2.3.0` 기준선은 요구사항 명세서 1.4, API 설계 2.1, Git tag `v2.3.0`, DB migration 20260701, 테스트 리포트 100% pass를 묶는다.
- **흔한 오해·주의점**: 기준선은 Git tag만이 아니다. 요구사항·설계·코드·빌드·테스트·배포 설정을 연결한 승인 상태다.

## 연결 개념
- 형상 항목(CI) — 관리 대상 산출물 단위
- 변경 통제(CCB) — 기준선 변경 승인 절차
- 릴리스 관리 — 기준선 기반 배포·롤백

---

# 📝 【답안용】 시험 답안 템플릿

> 목적: 기준선을 식별, 승인, 변경 통제, 감사, 재현 빌드 관점으로 답안화한다.

## 핵심 인사이트 (3줄 요약)

> 1. **본질**: 소프트웨어 형상 관리 기준선은 승인된 형상 항목의 특정 버전 집합으로, 변경 통제와 추적의 기준점이다.
> 2. **가치**: 요구사항부터 배포 산출물까지 추적성을 확보해 감사, 결함 원인 분석, 롤백, 재현 빌드를 가능하게 한다.
> 3. **판단 포인트**: 기준선은 tag가 아니라 문서·코드·빌드·테스트·환경 설정을 연결한 변경 통제 단위로 작성해야 한다.

## 출제 의도 및 답안 포인트

| 출제 의도 | 반드시 짚을 핵심 | 감점 회피 포인트 |
|:---|:---|:---|
| 형상 관리 기본 이해 확인 | CI, baseline, change control, audit | Git 브랜치 전략으로만 답변 |
| 변경 통제 절차 확인 | CR, impact analysis, CCB, versioning | 승인·추적·감사 절차 누락 |
| 실무 적용 판단 확인 | release baseline, build artifact, rollback | 문서 기준선과 배포 기준선 분리 누락 |

> 요약: 기준선 문제는 산출물 버전 고정과 변경 통제 절차를 함께 제시해야 한다.

---

## Ⅰ. 개요 및 필요성

소프트웨어 형상 관리 기준선은 승인된 산출물 버전의 기준점이다. 요구사항, 설계, 코드, 테스트, 배포 환경이 계속 바뀌므로 기준선 없이는 변경 영향 분석, 감사, 재현 빌드, 장애 롤백이 어렵다.

---

## Ⅱ. 구조 및 구성요소

```text
Configuration Item -> Version Identification -> Baseline Approval
  -> Change Request -> Impact Analysis -> CCB Approval
  -> Baseline Update -> Audit/Release
```

| 구성요소 | 역할 | 특이사항 |
|:---|:---|:---|
| 형상 항목(CI) | 관리 대상 산출물 | 요구사항, 코드, 설정, 테스트 |
| 기준선 | 승인된 CI 버전 집합 | functional, allocated, product baseline |
| 변경 요청(CR) | 기준선 변경 제안 | 영향·비용·위험 포함 |
| 형상 감사 | 기준선 일치 확인 | FCA, PCA |

> 요약: 기준선은 형상 항목 식별, 버전 승인, 변경 요청, 감사 절차로 유지된다.

---

## Ⅲ. 동작원리 및 흐름도

```text
산출물 식별 -> 버전 부여 -> 기준선 승인
  -> 변경 요청 접수 -> 영향 분석 -> 승인/반려
  -> 변경 반영 -> 검증 -> 기준선 재설정
```

| 단계 | 처리 내용 | 검증 기준 |
|:---:|:---|:---|
| 1 | 형상 항목과 버전 체계 정의 | CI list 100% 등록 |
| 2 | 산출물 검토 후 기준선 승인 | approval record |
| 3 | 변경 요청·영향 분석 수행 | traceability matrix |
| 4 | 변경 후 감사·릴리스 반영 | build reproducibility |

> 요약: 기준선은 승인 후 고정되고, 변경은 요청·분석·승인·검증을 거쳐 새 기준선으로 갱신된다.

---

## Ⅳ. 특징

| 구분 | 비통제 변경 | 기준선 기반 형상관리 | 정량·기술 포인트 |
|:---|:---|:---|:---|
| 추적성 | 변경 이유 불명확 | CR·commit·test 연결 | 요구사항 추적률 100% |
| 재현성 | 빌드 결과 불일치 | tag, artifact, lockfile | artifact hash 검증 |
| 감사 | 문서·코드 불일치 | FCA/PCA 수행 | audit finding 0건 |
| 롤백 | 대상 버전 혼선 | release baseline 기준 | RTO 30분 이하 |

> 요약: 기준선은 추적성, 재현성, 감사, 롤백을 가능하게 하는 변경 통제 기준이다.

---

## Ⅴ. 심화 비교 및 적용 판단

| 비교 축 | 기존/대안 | 본 키워드 | 선택 기준 |
|:---|:---|:---|:---|
| 개발 기준선 | 임시 문서 | 요구사항·설계 승인 | 외주·감리·규제 프로젝트 |
| 릴리스 기준선 | 단순 Git tag | artifact+config+test 묶음 | 운영 배포·롤백 필요 |
| 제품 기준선 | 코드 중심 | 사용자 문서·운영 절차 포함 | 장기 유지보수 계약 |

> 요약: 프로젝트 성격에 따라 기능·할당·제품 기준선을 나누고, 릴리스에는 artifact와 설정까지 포함해야 한다.

| 리스크 | 원인 | 대응 방안 | 확인 지표 |
|:---|:---|:---|:---|
| 기준선 불일치 | 문서·코드·배포 설정 분리 | traceability matrix, release manifest | mismatch count |
| 무단 변경 | 승인 없는 hotfix | CCB, protected branch, signed commit | unauthorized change 0건 |
| 재현 빌드 실패 | 의존성 버전 유동 | lockfile, artifact repository, SBOM | rebuild hash match |

> 요약: 기준선 리스크는 불일치, 무단 변경, 재현 실패로 나누어 통제한다.

| 점검 항목 | 목표 기준 | 측정 방법 |
|:---|:---|:---|
| 추적성 | 요구사항-코드-테스트 연결률 100% | ALM trace report |
| 변경 통제 | 승인 없는 변경 0건 | audit log, branch rule |
| 재현성 | 동일 기준선 rebuild 성공률 100% | CI artifact hash |

> 요약: 기준선 관리는 추적성, 승인 통제, 재현 빌드 성공률로 판단한다.

---

## Ⅵ. 실무 적용 및 결론

**적용 방안 3개 (필수 — 단계별 또는 항목별):**
1. 요구사항 ID, 설계 문서 버전, Git tag, build artifact hash, DB migration, 테스트 리포트를 release manifest로 묶음.
2. 변경 요청은 Jira CR, 영향 분석, CCB 승인, protected branch merge, signed tag 순서로 통제함.
3. 릴리스 후 SBOM, lockfile, container digest, IaC version을 보관해 동일 기준선 재빌드 100%를 검증함.

**결론 (2줄):**
- 기술사 판단: 기준선은 Git tag가 아니라 요구사항부터 운영 설정까지 묶은 승인된 변경 통제 단위로 관리.
- 향후 방향: DevSecOps 환경에서는 SBOM, signed artifact, policy-as-code가 기준선 감사의 핵심 자료가 됨.
