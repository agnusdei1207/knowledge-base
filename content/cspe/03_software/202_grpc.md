## Ⅰ. 개요
- **정의**: HTTP/2 기반으로 Protocol Buffers 직렬화를 사용하는 고성능 원격 프로시저 호출 프레임워크
- **배경/필요성**: 마이크로서비스 간 통신에서 JSON/REST 대비 직렬화 크기·지연 시간 절감 필요
- **비유**: 택배(REST)는 박스 포장(JSON)으로 부피가 크지만, 압축 택배(gRPC)는 진공포장(Protobuf)으로 소형·고속 배송

| 출제 의도 | 반드시 짚을 핵심 | 감점 회피 포인트 |
|:---|:---|:---|
| 서비스 간 통신 최적화 이해 | HTTP/2 멀티플렉싱, IDL 기반 코드 생성 | 4가지 통신 패턴(Unary/Server/Client/Bi-Stream) 구분 |

> 요약: Protobuf·HTTP/2 기반으로 서비스 간 저지연·고처리량 통신을 제공하는 RPC 프레임워크임

## Ⅱ. 구성요소
```text
Client Stub --HTTP/2--> [gRPC Server]
                            |
                   +--------+--------+
                   |        |        |
                .proto   Serializer  Service Impl
```

| 구성요소 | 설명 | 비유 |
|:---|:---|:---|
| .proto 파일 | 서비스·메시지 구조를 정의하는 IDL 명세 | 계약서 |
| Stub | .proto에서 자동 생성된 클라이언트 측 호출 코드 | 대리인 |
| Channel | 클라이언트-서버 간 HTTP/2 연결 관리 객체 | 전용 회선 |

> 요약: .proto IDL로 계약을 정의하고 자동 생성된 Stub이 Channel을 통해 호출함

## Ⅲ. 절차
```text
IDL 정의 --> 코드 생성 --> Stub 호출 --> 응답 역직렬화
```
- 1단계: .proto 파일에 서비스 메서드·요청·응답 메시지 타입 정의
- 2단계: protoc 컴파일러로 서버 인터페이스·클라이언트 Stub 코드 자동 생성
- 3단계: 클라이언트가 Stub을 통해 원격 메서드 호출, Protobuf 바이너리로 직렬화 전송
- 4단계: 서버 처리 후 응답을 Protobuf로 반환, 클라이언트가 역직렬화하여 사용

> 요약: IDL 정의, 코드 생성, Stub 호출, 역직렬화 4단계로 원격 호출 수행함

## Ⅳ. 문제점
- 브라우저 호환성: 브라우저에서 HTTP/2 트레일러 미지원 — 웹 클라이언트 직접 호출 불가
- 디버깅 난이도: 바이너리 페이로드로 인해 네트워크 패킷 육안 확인 곤란
- 스키마 진화 비용: 필드 번호 관리 실수 시 하위 호환성 파괴 위험

> 요약: 브라우저 비호환, 바이너리 디버깅 난이도, 스키마 진화 비용이 주요 문제임

## Ⅴ. 개선방안
1. 단기: gRPC-Web 프록시 도입으로 브라우저 호환성 확보
2. 중기: grpcurl·리플렉션 서비스 활용으로 바이너리 메시지 인간 가독형 변환
3. 장기: Buf 등 스키마 레지스트리 도입으로 필드 호환성 자동 검증 체계 구축

> 요약: gRPC-Web, 리플렉션 도구, 스키마 레지스트리로 단계적 개선함

## Ⅵ. 전망
- 발전 방향: xDS 프로토콜 기반 서비스 메시 연동으로 트래픽 제어 자동화 확대
- 기술사적 판단: 내부 서비스 통신은 gRPC, 외부 API는 REST/GraphQL 혼용이 현실적임
- 기술사 제언: Protobuf 직렬화 상세는 (210 참조)로 분리하여 학습 권장
