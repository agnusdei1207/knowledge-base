# 📖 【암기용】 개념 완전 이해

## 한눈에
- **개요**: 구글이 개발한 HTTP/2 기반의 고성능 오픈소스 원격 프로시저 호출(RPC) 프레임워크
- **왜 필요한가**: 마이크로서비스(MSA) 간의 통신에서 기존 REST(JSON+HTTP/1.1)는 텍스트 직렬화 오버헤드와 연결 비용이 커서 대규모 트래픽 처리에 병목이 된다.
- **핵심 직관**: 다른 서버에 있는 함수를 마치 내 로컬 컴퓨터에 있는 함수(`user.getAge()`)처럼 빠르게 바로 호출해서 결과를 받아오는 통신 고속도로다.

## 핵심 용어 정리

| 용어/표기 | 의미 | 비유·예 |
|:---|:---|:---|
| RPC (Remote Procedure Call) | 네트워크 너머의 원격 함수를 로컬 함수처럼 호출하는 통신 모델 | 서울 지점에서 부산 지점 직원의 전화번호 검색기를 내 자리에서 실행함 |
| Protocol Buffers (Protobuf) | gRPC의 기본 데이터 직렬화 포맷으로, 데이터를 이진(Binary)으로 압축함 | 텍스트 서류를 고압축 바코드로 변환해 전송 |
| HTTP/2 | gRPC의 전송 프로토콜, 다중화(Multiplexing)와 서버 푸시 지원 | 1차선 도로(HTTP/1.1)를 다차선 고속도로로 확장 |
| Stub (스텁) | 원격 함수를 로컬에서 호출할 수 있게 해주는 인터페이스 코드 (자동 생성됨) | 리모컨 |

## 깊이 이해
- **배경·문제의식**: MSA 환경에서는 서비스 간 내부 통신(East-West 통신)이 폭증한다. JSON은 사람이 읽기엔 좋지만, 파싱이 느리고 용량이 커서 수천 번의 내부 API 호출 시 CPU와 네트워크 대역폭을 심각하게 낭비한다.
- **작동 원리**: 개발자는 `.proto` 파일에 주고받을 데이터 구조와 서비스(함수명)를 정의한다. gRPC 컴파일러(protoc)가 이 파일을 읽어 각 언어(Java, Go, Python 등)에 맞는 Stub 코드를 자동 생성한다. 클라이언트가 Stub을 호출하면 데이터는 Protobuf로 이진 직렬화되어 HTTP/2 스트림을 통해 서버로 전송되고, 역직렬화되어 실행된다.
- **비유**: REST가 매번 주소를 적어 편지(JSON)를 보내는 방식이라면, gRPC는 두 서비스 간에 전용 광케이블(HTTP/2)을 깔고 번역기 없이 모스 부호(Protobuf)로 초고속 통신을 하는 것과 같다.
- **구체 예시**: `{"name": "Kim", "age": 30}`이라는 JSON 텍스트는 약 30바이트지만, Protobuf 바이너리로 압축하면 필드명 없이 값과 태그만 전송해 절반 이하의 크기로 줄고 직렬화 속도는 5배 이상 빠르다.
- **흔한 오해·주의점**: "웹 브라우저 프론트엔드 통신도 다 gRPC로 바꾸면 빠르다"는 오해다. 브라우저는 기본적으로 HTTP/2 프레임에 직접 접근하지 못해 gRPC를 바로 쓸 수 없다. 브라우저용은 gRPC-Web을 별도 사용해야 하므로 주로 백엔드 서버 간 통신에 쓰인다.

## 연결 개념
- **Protocol Buffers**: gRPC의 짝꿍인 구글의 직렬화 포맷 (210번 참조)
- **MSA (Microservice Architecture)**: gRPC가 가장 빛을 발하는 분산 아키텍처 환경
- **HTTP/2 & HTTP/3**: gRPC의 기반 프로토콜, 다중화와 헤더 압축 제공

# 📝 【답안용】 시험 답안 템플릿

## 핵심 인사이트 (3줄 요약)

> 1. **본질**: Protocol Buffers 이진 직렬화와 HTTP/2 프로토콜을 결합한 고성능 다국어 원격 프로시저 호출(RPC) 프레임워크다.
> 2. **가치**: 텍스트(JSON) 기반 통신 대비 페이로드 크기를 대폭 줄이고 직렬화 속도를 높여 MSA 내부 통신 지연을 최소화한다.
> 3. **판단 포인트**: 성능 이점은 확실하나 페이로드가 사람이 읽을 수 없고(Unreadable) 브라우저 지원이 제한적이므로, External API보다 Internal 마이크로서비스 간 통신에 적합하다.

## 출제 의도 및 답안 포인트

| 출제 의도 | 반드시 짚을 핵심 | 감점 회피 포인트 |
|:---|:---|:---|
| gRPC의 성능 향상 메커니즘 이해 | Protocol Buffers(바이너리), HTTP/2(멀티플렉싱), Stub | "속도가 빠르다"는 추상적 서술 (기술명 누락) |
| REST와 gRPC의 트레이드오프 판단 | JSON vs 바이너리, 사람 가독성 유무, 스트리밍 지원 여부 | 모든 통신을 gRPC로 대체 가능하다는 단정 |
| 스트리밍 통신 방식 이해 | Unary, Server/Client/Bidirectional 스트리밍 | 양방향 통신 방식을 단방향으로만 서술 |

> 요약: gRPC는 HTTP/2 다중화와 이진 직렬화를 통해 통신 병목을 해소하므로, REST와의 성능 비교와 적합한 적용 계층(내부 통신)을 구분해 제시해야 한다.

## Ⅰ. 개요 및 필요성

- 개요: 구글이 개발한 Protocol Buffers 직렬화 기반 HTTP/2 전송 규격을 사용하는 오픈소스 원격 프로시저 호출 프레임워크
- 배경: MSA로 아키텍처가 전환되면서 서비스 간 내부 통신 빈도가 기하급수적으로 증가하여 JSON 파싱 오버헤드가 CPU 병목 유발
- 필요성: 직렬화 속도를 높이고 네트워크 페이로드를 압축하여 통신 지연(Latency)을 마이크로초 단위로 단축하고 양방향 스트리밍 구현 필요

---

## Ⅱ. 구조 및 구성요소

```text
[클라이언트 앱] -> (Client Stub 호출) -> [직렬화/Protobuf] -> (HTTP/2 스트림) -> [역직렬화] -> (Server Stub) -> [서버 앱]
  (Java/Go 등)                                                                                         (C++/Python 등)
```

| 구성요소 | 역할 | 특이사항 |
|:---|:---|:---|
| Protocol Buffers (.proto) | 서비스 인터페이스 및 주고받을 메시지 구조(IDL) 정의 | 언어 중립적인 스키마 명세서 |
| protoc 컴파일러 | `.proto` 파일을 기반으로 각 언어별 Stub 코드 자동 생성 | 다국어(Polyglot) MSA 환경 지원 |
| Client/Server Stub | 통신 복잡성을 캡슐화하여 로컬 함수처럼 호출 가능케 하는 프록시 | 네트워크 I/O 및 직렬화/역직렬화 대행 |

> 요약: `.proto` 스키마로 인터페이스를 정의하면 컴파일러가 스텁을 생성하여, 다국어 서비스 간 이진 데이터 고속 통신을 지원한다.

---

## Ⅲ. 동작원리 및 흐름도

```text
IDL 정의 -> 컴파일러 스텁 생성 -> 클라이언트 스텁 호출 -> Protobuf 직렬화 -> HTTP/2 전송 -> 서버 역직렬화 및 실행
```

- 1단계 [IDL 명세 및 생성]: `.proto` 파일에 메시지 포맷과 RPC 메서드(스트리밍 등 4가지 타입)를 정의하고 protoc로 스텁 생성
- 2단계 [원격 호출 및 직렬화]: 클라이언트 애플리케이션이 스텁 함수를 호출하면 파라미터를 Protobuf 바이너리 형식으로 직렬화
- 3단계 [다중화 전송]: HTTP/2의 멀티플렉싱(Multiplexing)을 활용해 단일 TCP 연결 내 여러 스트림으로 바이너리 프레임 동시 전송
- 4단계 [역직렬화 및 반환]: 서버 스텁이 수신 데이터를 역직렬화하여 실제 비즈니스 로직에 전달하고, 결과를 다시 역순으로 반환

> 요약: 스텁을 통한 로컬 함수 호출은 직렬화되어 HTTP/2 스트림을 타고 서버로 전달되며, 서버는 이를 역직렬화해 실행한다.

---

## Ⅳ. 특징
- 4가지 통신 패턴 지원: Unary(단일 요청-응답), Server Streaming, Client Streaming, Bidirectional Streaming을 모두 기본 지원
- HTTP/2 헤더 압축(HPACK): 매 요청마다 반복되는 HTTP 헤더를 압축 전송하여 네트워크 대역폭 점유율 획기적 감소
- 가독성 희생(Unreadable): 이진 포맷이므로 와이어샤크(Wireshark) 등 패킷 스니핑 시 사람이 디버깅하기 어려워 별도 툴(gRPCurl) 필요

> 요약: 스트리밍 통신과 이진 압축으로 극강의 성능을 내지만, 페이로드 가독성이 없어 디버깅 편의성은 감소한다.

## Ⅴ. 심화 비교 및 적용 판단

| 비교 축 | RESTful API | gRPC | 선택 기준 |
|:---|:---|:---|:---|
| 전송 프로토콜/페이로드 | HTTP/1.1 (주로), JSON 텍스트 | HTTP/2, Protobuf 이진 데이터 | 대규모 트래픽 병목 여부 및 직렬화 성능 |
| 통신 방향 | 단방향 요청-응답 | 단방향 + 양방향 스트리밍 | 실시간 데이터 스트리밍 필요성 |
| 적용 계층 | 브라우저-서버 (External API) | 서버-서버 내부 통신 (Internal API) | 클라이언트 환경(브라우저 제약) 및 스키마 필요성 |

> 요약: 브라우저와 통신하는 외부 노출형 API는 범용성 높은 REST를, 백엔드 마이크로서비스 간 내부 고속 통신은 gRPC를 선택한다.

**리스크·대응 (기본은 불릿):**
- 로드밸런싱 한계: L4 로드밸런서 사용 시 HTTP/2 롱커넥션으로 인해 특정 서버에 트래픽이 집중(Sticky) → L7 로드밸런서(Envoy 등) 적용 또는 Client-side 로드밸런싱 구현
- 브라우저 클라이언트 연동 제한: 일반 웹 브라우저에서 직접 HTTP/2 프레임 조작 불가 → gRPC-Web 프록시 도입 또는 외부 API는 REST(API Gateway 변환) 유지
- 디버깅 비용 증가: 평문 확인 불가로 에러 추적 지연 → gRPC Server Reflection 활성화 및 Postman/gRPCurl 활용한 검증 파이프라인 구축

**도입 후 점검 지표 (기본은 불릿):**
- 성능/효율: 내부 통신 지연시간(p99 Latency) 감소율, 노드당 CPU 사용량(JSON 파싱 대비) 감소 추이
- 품질/운영: gRPC 상태 코드(Status Code, 예: 14 UNAVAILABLE) 오류 발생률, L7 로드밸런서의 스트림 분배 균등성

## Ⅵ. 실무 적용 및 결론

**적용 방안 3개:**
1. MSA 내부 통신 표준화: 서비스 간 동기 호출(East-West) 구간을 gRPC로 대체하여 평균 Latency를 50ms에서 10ms 이하로 최적화
2. Envoy 기반 API Gateway 구성: 외부는 REST(JSON)로 받고 내부는 gRPC(Protobuf)로 변환하는 트랜스코딩(gRPC-JSON Transcoding) 패턴 적용
3. 실시간 양방향 스트리밍 구현: 주식 호가 데이터, 채팅 등 지속 연결이 필요한 도메인에서 Bidirectional Streaming을 활용해 웹소켓 대체

**결론 (2줄):**
- 기술사 판단: 다국어 폴리글랏(Polyglot) MSA를 구성할 때 gRPC는 필수 인프라 요소이며, 통신 오버헤드를 물리적 한계까지 쥐어짤 수 있는 최적의 선택지다.
- 향후 방향: 최근 HTTP/3(QUIC) 기반 통신이 대두됨에 따라 TCP의 Head-of-Line Blocking 한계마저 극복하는 차세대 gRPC(gRPC over QUIC)로 진화할 것이다.
