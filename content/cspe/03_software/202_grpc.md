## 핵심 인사이트 (3줄 요약)
- 마이크로서비스(MSA) 수십 개가 서로 쉴 새 없이 통신하는 백엔드 환경에서, **REST(JSON)의 텍스트 파싱 속도 한계를 극복하기 위해 구글이 만든 빛의 속도를 자랑하는 RPC 프레임워크**.
- 데이터를 무거운 텍스트(JSON) 대신 `0101` 같은 초경량 바이너리(Protocol Buffers, Protobuf)로 압축해서 쏘기 때문에, 네트워크 페이로드가 절반으로 줄고 직렬화 속도는 10배 이상 빠름.
- HTTP/2를 기본으로 사용하여 '양방향 스트리밍(동시 통신)'을 지원하며, "서로 다른 언어로 짠 서버끼리 마치 내 컴퓨터 안에 있는 함수를 부르듯이(RPC)" 호출하게 해주는 백엔드 통신의 끝판왕임.
---
## Ⅰ. 개요 및 필요성
- **개요**: 구글에서 개발한 고성능 오픈소스 범용 원격 프로시저 호출(RPC) 프레임워크로, HTTP/2와 Protocol Buffers를 기반으로 동작함.
- **필요성**: 쿠팡 결제 한 번에 파드 10개가 통신함. 전부 REST(JSON)로 통신함. JSON은 텍스트라서 사람이 읽긴 좋지만, 컴퓨터가 `{ "name": "John" }`을 읽고 파싱하는데 생각보다 CPU를 엄청나게 잡아먹고 용량도 큼. 이 찰나의 낭비가 파드 10개를 거치면 눈덩이처럼 불어나 지연시간(Latency)이 터짐. **"사람이 읽을 필요 없어! 백엔드 기계들끼리만 알아듣게 데이터를 0101 바이너리로 압축해서 빛의 속도로 쏘는 통신망을 만들자!"**라며 구글이 gRPC를 공개함.
---
## Ⅱ. 아키텍처 및 핵심 원리
- **1. 프로토콜 버퍼 (Protocol Buffers, Protobuf)**:
  - gRPC의 심장이자 데이터 직렬화 포맷. JSON 대신 사용함.
  - `.proto`라는 파일에 "1번 필드는 이름(String), 2번 필드는 나이(Int)"라고 룰을 적어둠.
  - 이 규칙에 따라 데이터를 바이너리로 꽉꽉 눌러 담아서 쏘므로, JSON에 있는 쓸데없는 괄호 `{ }`나 띄어쓰기가 없어서 용량이 엄청 작음.
- **2. 코드 자동 생성 (Code Generation)**:
  - `.proto` 명세서를 컴파일러에 넣으면, Java 서버용 코드와 Go 서버용 통신 코드를 알아서 다 짜줌(마법!). 
  - 개발자는 생성된 함수를 그냥 `calculatePrice()`처럼 호출만 하면, 알아서 네트워크를 타고 다른 서버에서 실행됨.
- **3. HTTP/2 기반 (스트리밍)**:
  - REST는 HTTP/1.1을 써서 한 번 질문하면 한 번 대답하고 통신이 끊김.
  - gRPC는 HTTP/2를 써서 파이프 하나를 뚫어놓고, **양방향(Bi-directional)으로 데이터를 물 흐르듯 실시간으로 쏟아부을 수 있음** (채팅이나 대용량 데이터 전송에 최적).

```text
[ REST (JSON) vs gRPC (Protobuf) 백엔드 통신 비교 ]

 🐌 [ REST 서버 간 통신 (무겁고 느림) ]
 서버 A (Java) ➡️ JSON 변환(CPU 소모 💦) ➡️ [ { "id": 123, "status": "OK" } ] ➡️ 네트워크 전송 ➡️ 서버 B (Python) 파싱(CPU 소모 💦)
 - 단점: 텍스트 읽고 쓰느라 컴퓨터가 고생함. 용량 큼.

 ⚡ [ gRPC 서버 간 통신 (가볍고 초고속) ]
 서버 A (Java) ➡️ Protobuf 압축 ➡️ [ 01010011 11001010 (바이너리) ] ➡️ 네트워크 슝~ ➡️ 서버 B (Python) 즉시 해제
 - 장점: 텍스트가 아닌 기계어 수준의 바이너리 압축! 속도 10배 증가! 네트워크 비용 절반 감소!
```

## Ⅲ. 비교 및 연결
| 구분 | REST (JSON) | GraphQL (JSON) | gRPC (Protobuf) |
|---|---|---|---|
| **통신 속도** | 보통 | 보통 | **압도적으로 빠름 (바이너리)** |
| **데이터 포맷** | 텍스트 기반 (사람이 읽기 쉬움) | 텍스트 기반 | **바이너리 기반 (사람이 못 읽음)** |
| **네트워크 프로토콜**| HTTP/1.1 | HTTP/1.1 | **HTTP/2 (필수)** |
| **동시 스트리밍**| 미지원 (매번 끊김) | 일부 지원 | **완벽한 양방향 스트리밍 지원** |
| **주요 타겟(위치)** | **외부 프론트엔드 (웹, 앱)** | 프론트엔드 (모바일 화면) | **오직 백엔드 내부 K8s 파드끼리!** |

## Ⅳ. 실무 적용 및 기술사 판단
- **B2B(Backend to Backend) 통신의 표준 아키텍처**: 기술사가 마이크로서비스(MSA) 아키텍처를 설계할 때, 가장 완벽한 콤비네이션은 프론트와 백엔드 사이의 통신(External)은 **REST나 GraphQL**로 열어두고, 백엔드 클러스터 내부(Internal)의 100개 파드끼리 찔러대는 통신은 전부 **gRPC**로 묶어버리는 것임. 이렇게 하면 외부 개발자와의 연동(호환성)은 챙기면서, 내부 클라우드 네트워크 비용과 지연시간을 극한으로 깎아낼 수 있음.
- **로드밸런싱의 주의점 (L7 로드밸런서 필수)**: gRPC는 HTTP/2를 쓰기 때문에 TCP 연결(파이프)을 한 번 맺으면 끊지 않고 계속 씀. 이걸 멍청한 L4 로드밸런서(IP 기반)에 물려놓으면 트래픽 분산이 하나도 안 되고 한 서버에만 꽂힘. 따라서 실무에 gRPC를 도입하려면 반드시 K8s Ingress나 Istio(Envoy 프록시) 같은 **L7 레벨의 로드밸런서**를 통해 HTTP/2 스트림을 패킷 단위로 잘게 쪼개서 분산시켜야 서버가 안 터짐.
---
## Ⅴ. 기대효과 및 결론
- "JSON 텍스트 기반 통신"이라는 클라우드 네이티브의 숨겨진 병목(Bottleneck)을 바이너리 압축이라는 강력한 무기로 박살 낸 혁신 기술.
- 서로 다른 수십 개의 언어(Polyglot)로 만들어진 MSA 환경에서, 서버 간 통신 규약을 `.proto` 파일 하나로 강력하게 통제하고 코드를 자동 생성해 주는 백엔드 인프라의 필수 표준임.
