## Ⅰ. 개요
- **정의**: 레거시 시스템을 점진적으로 신규 시스템으로 교체하여 리스크를 최소화하는 마이그레이션 패턴임
- **배경/필요성**: 빅뱅 방식의 전면 전환은 실패 시 복구가 어렵고 서비스 중단 위험이 큼
- **비유**: 교살 무화과(Strangler Fig)가 숙주 나무를 서서히 감싸며 대체하는 것과 같음

| 출제 의도 | 반드시 짚을 핵심 | 감점 회피 포인트 |
|:---|:---|:---|
| 레거시 현대화 전략 이해 | Facade를 통한 트래픽 분기 메커니즘 | 단순 리팩토링이 아닌 시스템 교체 패턴임을 명시 |

> 요약: Facade 계층을 통해 레거시와 신규 시스템을 공존시키며 점진적으로 전환하는 패턴임

## Ⅱ. 구성요소
```text
Client --> [Facade/Router]
               |          |
          [New Service]  [Legacy System]
           (점진 확대)    (점진 축소)
```

| 구성요소 | 설명 | 비유 |
|:---|:---|:---|
| Facade/Router | 요청을 분석하여 신규 또는 레거시로 라우팅하는 전환 계층임 | 교차로 신호등 |
| New Service | 레거시 기능을 대체하기 위해 신규 구현된 서비스임 | 새로 자라는 덩굴 |
| Legacy System | 점진적으로 기능이 이관되어 축소되는 기존 시스템임 | 숙주 나무 |

> 요약: Facade가 트래픽을 분기하여 New Service 비율을 점진적으로 확대함

## Ⅲ. 절차
```text
기능 식별 --> 신규 구현 --> 트래픽 전환 --> 레거시 제거
```
- 1단계: 레거시 시스템의 기능을 모듈 단위로 분류하고 전환 우선순위를 결정함
- 2단계: 우선순위가 높은 기능부터 신규 서비스로 재구현함
- 3단계: Facade에서 해당 기능의 트래픽을 신규 서비스로 점진 전환함
- 4단계: 전환 완료된 레거시 기능을 비활성화하고 최종 제거함

> 요약: 기능 식별 → 신규 구현 → 트래픽 전환 → 레거시 제거의 4단계 반복으로 진행함

## Ⅳ. 문제점
- 이중 운영 비용: 전환 기간 동안 신규·레거시 양쪽을 동시 운영해야 함
- 데이터 정합성: 양 시스템 간 데이터 동기화가 실패하면 불일치가 발생함
- 전환 지연: 레거시 의존성이 복잡하면 제거 시점이 무기한 연장됨

> 요약: 이중 운영·데이터 정합성·전환 지연이 스트랭글러 패턴의 주요 리스크임

## Ⅴ. 개선방안
1. 단기: 전환 기간에 대한 명확한 일정과 비용 예산을 사전 확보함
2. 중기: CDC(Change Data Capture)를 도입하여 양 시스템 간 데이터 실시간 동기화를 보장함
3. 장기: 기능별 전환 완료 기준(트래픽 100% 전환 + 1개월 안정화)을 정의하여 레거시 제거를 강제함

> 요약: 일정 확보 → 데이터 동기화 → 제거 기준 강제로 전환 리스크를 관리함

## Ⅵ. 전망
- 발전 방향: AI 기반 코드 분석으로 레거시 기능 분류와 의존성 파악이 자동화될 전망임
- 기술사적 판단: 클라우드 마이그레이션과 결합하여 레거시 현대화의 표준 접근법으로 활용됨
- 기술사 제언: 빅뱅 전환 대비 스트랭글러 패턴의 TCO를 비교 분석한 후 적용을 결정할 것을 권고함
