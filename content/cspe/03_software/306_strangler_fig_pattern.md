## 핵심 인사이트 (3줄 요약)
- 10년 된 거대한 레거시 시스템을 하룻밤 사이에 최신 마이크로서비스(MSA)로 싹 바꾸는 '빅뱅(Big-bang) 방식'은 100% 확률로 서버가 터지고 회사가 망하는 지름길임.
- **스트랭글러 패턴**은 호주에 있는 덩굴식물(스트랭글러 무화과나무)이 원래 있던 큰 나무를 서서히 타고 올라가 결국 원래 나무를 죽이고 자기가 본체가 되는 자연 현상에서 착안한 **'레거시 ➡️ MSA 점진적 전환 아키텍처'**임.
- 앞단에 API Gateway(라우터)를 세워두고, 이번 달엔 '결제' 기능만 새 서버로 이사 ➡️ 트래픽을 새 서버로 돌림. 다음 달엔 '장바구니' 이사... 이렇게 야금야금 트래픽을 빼앗아 오다가, **몇 년 뒤 레거시 깡통만 남으면 전원 코드를 뽑아버리는 궁극의 안전 이사법**임.

## Ⅰ. 개요 및 필요성
- **개요**: 모놀리식(Monolithic) 레거시 시스템을 새로운 마이크로서비스로 전환할 때, 새로운 서비스를 점진적으로 교체하여 최종적으로 레거시 시스템을 고사(Strangulate)시키는 아키텍처 리팩터링 패턴.
- **필요성**: 은행 차세대 프로젝트. 기존 코볼(COBOL) 메인프레임을 자바 스프링 기반 K8s로 바꿈. 개발 완료 후 새벽 2시에 옛날 서버 끄고 새 서버 켬(빅뱅 릴리스). 아침 9시 고객 폭주 ➡️ 새 서버 결제 로직에 버그 있어서 전국 ATM기 먹통 됨. 롤백 불가. **"아니, 한 번에 다 갈아엎지 말고, 안전하게 기능 하나씩 하나씩만 새 서버로 옮기면서 테스트해 보는 '야금야금 이사' 전략 없을까?"**
---
## Ⅱ. 핵심 아키텍처 및 동작 원리 (3단계 교살 프로세스)
마틴 파울러가 정립한 이 패턴의 핵심은 **'파사드 라우터(API Gateway)'**를 꽂는 것임.

- **1단계: 라우터 차단막 설치 (Transform)**:
  - 사용자와 레거시 사이에 무조건 거쳐야 하는 **L7 라우터(API Gateway)**를 세움. 초기엔 100% 트래픽을 옛날 레거시로 흘려보냄.
- **2단계: 새 서비스 구축 및 라우팅 변경 (Coexist)**:
  - 새로운 K8s 환경에 '사용자 리뷰' 기능만 떼어내서 만듦.
  - 라우터의 설정을 변경함. `URL이 /review 로 들어오면 -> K8s 새 서버로 보냄`.
  - `나머지 URL로 들어오면 -> 여전히 레거시 서버로 보냄`. (신/구 시스템의 평화로운 공존).
- **3단계: 레거시 제거 (Eliminate)**:
  - '결제', '주문' 등 모든 기능을 점진적으로 새 서버로 파냄.
  - 라우터가 레거시로 트래픽을 1건도 안 보냄. 깡통이 된 레거시 서버의 플러그를 뽑아버림 (완전한 대체).

```text
[ 빅뱅 전환 vs 스트랭글러 패턴 ]

 💥 [ 빅뱅 방식 (Big Bang) ]
 금요일 자정: 레거시 스위치 끔 ➡️ 신규 서버 스위치 켬 ➡️ 에러 발생! ➡️ 시스템 통째로 마비 ➡️ 기사 남.

 🌱 [ 스트랭글러 패턴 (점진적 질식사) ]
 API Gateway: "손님, /api/old는 왼쪽 낡은 건물(레거시)로, /api/new는 오른쪽 새 건물(MSA)로 가세요~"
 1개월 차: 새 건물(10%), 낡은 건물(90%)
 6개월 차: 새 건물(80%), 낡은 건물(20%)
 1년 차: 새 건물(100%), 낡은 건물 철거 완료! (무장애 전환 성공)
```

## Ⅲ. 오해와 진실
| 오해 | 진실 |
|---|---|
| "데이터베이스는 어떻게 해요? 결국 데이터 때문에 얽히지 않나요?" | **스트랭글러 패턴의 가장 어려운 난제임.** 코드는 쪼갰지만 DB가 옛날 오라클 1개로 통짜라면 반쪽짜리 분리임. 그래서 코드를 쪼갤 때 뷰(View), 트리거(Trigger)를 통해 신/구 DB 데이터를 동기화하는 '데이터베이스 쪼개기(Database Strangler)' 패턴을 병행해야 진정한 독립이 완성됨. |
| "무조건 이 패턴이 최고네! 작은 앱도 이렇게 옮기자!" | 스트랭글러 패턴의 1단계(API Gateway 구축) 자체가 비용이고 인프라 오버헤드임. 만약 기존 레거시가 코드가 적고 1달이면 다 다시 짤 수 있는 작은 시스템이라면, 그냥 한 방에 덮어쓰는 게 훨씬 경제적임. 이 패턴은 **'절대 한 번에 갈아엎을 수 없는 초거대 엔터프라이즈'**를 위한 전략임. |

## Ⅳ. 실무 적용 및 기술사 판단
- **무중단 점진적 롤백 아키텍처**: 기술사는 차세대 마이그레이션 전략을 세울 때 무조건 스트랭글러 패턴을 베이스로 깔아야 함. '리뷰 기능'을 K8s로 옮겼는데 장애가 발생했다? 코드를 고칠 필요 없이, **API Gateway의 라우팅 룰을 다시 1초 만에 `레거시`로 원복(Rollback)**시키면 됨. 이처럼 '전환 리스크를 최소화'하는 롤백 안전망을 확보하는 것이 핵심 가치임.
- **이벤트 차단 패턴 (Event Interception) 적용**: 레거시 내부에서 꽉 엉켜있는 배치(Batch) 작업은 밖으로 빼기 힘듦. 기술사는 데이터가 레거시 DB에 쓰일 때 발생하는 CDC(Change Data Capture) 로그를 Kafka로 낚아채서, 신규 MSA 서버가 그 이벤트를 받아 점진적으로 로직을 대체하게 만드는 진화된 데이터 스트랭글러 패턴을 설계해야 함.

## Ⅴ. 기대효과 및 결론
- "수천억을 들이고도 뚜껑을 열 때까지 성공 여부를 모르는" 차세대 IT 프로젝트의 가장 거대한 리스크를, 조각조각 내어 통제 가능한 수준으로 낮춤.
- 개발팀은 레거시 전체 코드를 파악할 필요 없이 떼어낼 한 조각의 도메인(Domain)에만 집중하여 현대화할 수 있으며, 서비스 무중단을 보장하며 클라우드 네이티브로 이주할 수 있는 모범 답안임.

### 📈 관련 키워드 및 발전 흐름도
- 옛날 시스템 차세대(Next-Gen) 마이그레이션의 상징이었던 '빅뱅 방식' 대실패 사례 속출 ➡️ 2004년 세계적 구루 마틴 파울러(Martin Fowler)가 호주 무화과나무를 보고 **'Strangler Fig Application' 패턴** 제안 ➡️ 모놀리식 아키텍처를 MSA로 쪼개는 마이크로서비스 붐이 일면서 이 패턴이 클라우드 전환의 절대 표준으로 부활 ➡️ AWS, Azure 등 모든 퍼블릭 클라우드의 공식 마이그레이션 아키텍처로 채택 (현재)

### 👶 어린이를 위한 3줄 비유 설명
1. 거대한 낡은 성(레거시)을 부수고 새 성(MSA)을 짓고 싶은데, 한 번에 부수면 왕과 기사들이 길바닥에 나앉게 돼요.
2. **스트랭글러 패턴**은 낡은 성문 앞에 '표지판 요정(API 게이트웨이)'을 세워두고, 먼저 옆에 '새로운 식당' 건물 하나만 짓는 거예요.
3. 요정이 "식사하실 분은 새 식당으로, 잠잘 분은 낡은 성으로 가세요!" 안내해 주고, 나중에 새 화장실, 새 침실을 다 지으면 낡은 성을 쾅 무너뜨리는 가장 안전한 집짓기 방법이랍니다!

### 🔀 문제 유형별 목차 전환 (이 키워드 출제 시)
- **개념/프로세스형 (Ⅱ·Ⅲ 강조)**: 스트랭글러 패턴의 핵심 3단계(Transform/Facade 구축 ➡️ Coexist/라우팅 분리 ➡️ Eliminate/고사) 프로세스 도식화. API Gateway 및 Facade 패턴을 이용한 트래픽 분기 메커니즘 설명.
- **MSA 전환/전략형 (Ⅳ·Ⅴ 강조)**: 대규모 차세대 시스템 전환 시 빅뱅(Big Bang) 릴리스 리스크를 회피하는 전략. 데이터베이스 분리 난제(Shared Database 문제) 해결을 위한 Anti-Corruption Layer(ACL) 적용 및 뷰/싱크를 활용한 단계적 DB 마이그레이션 아키텍처 제시.
