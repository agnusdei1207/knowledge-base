# 📖 【암기용】 개념 완전 이해

> 목적: 스트랭글러 패턴을 처음 봐도 레거시 시스템을 한 번에 교체하지 않는 이유를 이해하게 만든다. 시험 답안 양식이 아니라, 이해를 위한 설명이다.

## 한눈에
- **개요**: 스트랭글러 무화과 패턴은 **레거시 시스템 현대화(Legacy Modernization)** 전략 중 하나로, 시스템 전체를 한 번에 교체하는 빅뱅(Big Bang) 방식 대신 **기능 단위로 점진적으로 신규 서비스로 대체**해 나가는 패턴이다.
- **왜 필요한가**: 빅뱅 전환은 일정 지연, 데이터 불일치, 업무 중단 위험이 크므로 기능 단위로 라우팅을 바꾸며 위험을 나눠야 한다.
- **핵심 직관**: 새 식물이 기존 나무를 감싸며 자라듯, 새 시스템이 기능별로 기존 시스템을 대체한다.

## 핵심 용어 정리 (내부에 등장하는 것들)

| 용어 | 의미 | 비유 |
|:---|:---|:---|
| 레거시 현대화(Legacy Modernization) | 오래된 시스템을 안전하게 새 시스템으로 바꾸는 전략 전반 — 스트랭글러는 그중 점진적 방식 | 낡은 집을 고치는 여러 방법 중 하나 |
| 빅뱅(Big Bang) 전환 | 시스템 전체를 한 번에 새 시스템으로 교체하는 방식 — 스트랭글러가 피하려는 대안 | 이사 하루 만에 집 전체를 통째로 바꾸기 |
| Facade/Gateway | 요청을 받아 기능별로 신규·레거시 중 어디로 보낼지 정하는 라우팅 계층 | 리모델링 중인 건물의 임시 안내데스크 |
| CDC(Change Data Capture) | 레거시 DB의 변경 사항을 실시간으로 감지해 신규 시스템에 반영하는 기법 | 원본 장부에 적히는 순간 사본에도 자동 기록 |
| Dual-write(이중 쓰기) | 신규·레거시 두 시스템에 동시에 데이터를 쓰는 방식 | 영수증을 원본·사본 두 장 동시에 작성 |
| Reconciliation(정합성 검증) | 신규·레거시 데이터가 서로 일치하는지 주기적으로 대조·확인하는 절차 | 두 장부의 잔액이 맞는지 대조 |
| Sunset date(제거 예정일) | 레거시 기능을 완전히 끄기로 정한 날짜 — 이중 운영 종료 기준 | 임시 건물 철거 예정일 |

## 깊이 이해

### 왜 "스트랭글러"라는 이름인가 (배경)
- 이름은 열대 식물인 스트랭글러 피그(교살자 무화과)에서 왔다. 이 식물은 씨앗이 큰 나무 위에 떨어져 뿌리를 뻗어 내려가며 서서히 숙주 나무를 감싸고, 결국 숙주가 죽어 사라져도 자기 형태(빈 공간)를 유지하며 독립적으로 선다. 마틴 파울러가 2004년 이 생태 비유를 소프트웨어 마이그레이션에 붙였다.
- 핵심 업무 레거시는 수년~수십 년간 누적된 업무 규칙과 데이터 의존성을 갖고 있어, 전체를 한 번에 재작성하면 요구사항 누락·일정 지연·데이터 이관 실패 위험이 시스템 전체로 번진다 — 빅뱅 전환이 실패로 끝난 사례가 실무에서 다수 보고된 이유다.

### 작동 원리 (Facade가 트래픽을 가르는 방식)
- Facade(또는 Gateway)가 요청 경로(URL, 헤더, 사용자 그룹)를 보고 "이 기능은 이전됐는가?"를 판단해 신규 서비스 또는 레거시로 라우팅한다.
- 수치 워크드 예제: 주문 조회 기능을 이전한다고 하자. 1주차엔 read traffic의 5%만 신규 API로 보내고 나머지 95%는 레거시로 보낸다. 오류율이 0.1% 이하로 안정되면 2주차에 25%, 3주차에 50%, 최종적으로 100%까지 단계적으로 늘린다. 이 과정에서 신규·레거시 응답을 동시에 비교하는 "shadow traffic"으로 안전성을 미리 검증하기도 한다.
- 쓰기(주문 생성) 기능은 조회보다 리스크가 크다 — 신규·레거시 양쪽에 데이터가 있어야 하므로 Dual-write 또는 CDC로 동기화하고, Reconciliation(정합성 검증)에서 mismatch(불일치) 비율이 0.1% 이하일 때만 다음 단계 전환을 승인한다.

### 판별 원리 — 언제 레거시를 완전히 제거하는가
- "신규 서비스로 가는 트래픽 비율이 100%에 도달"하고 "정합성 검증에서 일정 기간(예: 1개월) mismatch가 0건"이면 레거시 기능의 sunset date(제거 예정일)를 정한다. 제거 전에는 반드시 백업을 일정 기간(예: 1년) 보관해 롤백 경로를 남긴다.
- 이 기준이 없으면 레거시를 무기한 병행 운영하게 되어, 신규·레거시 두 시스템을 동시에 유지보수하는 이중 비용이 계속 쌓인다 — 이것이 스트랭글러의 가장 흔한 실패 패턴이다.

### 비유와 흔한 오해
- 비유: 오래된 상가 건물을 통째로 철거하지 않고, 층별로 순서대로 영업하면서 리모델링하고, 완전히 새 층으로 바뀌면 옛 자재를 치우는 것과 같다. 건물(서비스)은 그사이에도 계속 운영된다.
- 오해 1: 스트랭글러는 단순히 "요청을 두 곳으로 나누는 리버스 프록시"가 아니다. 기능 경계를 어떻게 나눌지, 데이터 소유권을 누가 가질지, 실패 시 롤백을 어떻게 할지, 레거시를 언제 제거할지가 함께 설계되어야 진짜 스트랭글러 패턴이다.
- 오해 2: 점진 전환이 항상 빅뱅보다 낫다는 뜻은 아니다. 기능 경계가 명확히 분리되지 않거나 핵심 업무가 아닌 주변 시스템이라면, 오히려 오랜 이중 운영 비용이 빅뱅보다 클 수 있다.

## 연결 개념
- Anti-Corruption Layer (레거시 모델과 신규 모델을 분리하는 번역 계층 — 스트랭글러 전환 중 자주 함께 쓰임)
- Feature Toggle (전환 비율과 롤백을 제어하는 실행 장치)
- CDC/Dual-write (데이터 정합성을 유지하는 구체 기법)

# 📝 【답안용】 시험 답안 템플릿

> 목적: 시험장에서 25분에 그대로 쓰는 답안 양식. 스트랭글러는 레거시 현대화의 위험 분할, 기능 라우팅, 데이터 정합성 검증을 중심으로 답한다.

## 핵심 인사이트 (3줄 요약)

> 1. **본질**: 스트랭글러 패턴은 Facade가 요청을 기능별로 라우팅하고 신규 서비스가 레거시 기능을 단계적으로 대체하는 현대화 방식이다.
> 2. **가치**: 빅뱅 전환의 업무 중단 위험을 기능 단위로 나누고, 전환 중에도 운영 서비스와 롤백 경로를 유지한다.
> 3. **판단 포인트**: 기능 경계, 데이터 소유권, 정합성 검증, 레거시 제거 기준을 먼저 정하지 않으면 이중 운영 비용이 누적된다.

## 출제 의도 및 답안 포인트

| 출제 의도 | 반드시 짚을 핵심 | 감점 회피 포인트 |
|:---|:---|:---|
| 레거시 현대화 전략 이해 확인 | Facade, 점진 라우팅, 신규 서비스, 레거시 제거 | 단순 재개발 방법론으로 서술 |
| 위험 관리 역량 확인 | 기능별 전환, rollback, reconciliation | 데이터 정합성 검증 누락 |
| 전환 운영 판단 확인 | 전환 지표, 중복 비용, 제거 기준 | 레거시를 무기한 병행 |

> 요약: 이 문제는 교체 기술보다 업무 중단 없이 전환하는 절차와 검증 지표를 묻는다.

## Ⅰ. 개요 및 필요성

- 개요: 레거시 기능의 점진 대체 패턴
- 배경: 빅뱅 전환은 요구 누락과 데이터 이관 실패 시 업무 중단 범위가 전체 시스템으로 확대됨
- 필요성: 기능별 라우팅, 병행 운영, 데이터 정합성 검증으로 전환 단위를 분할해야 함

---

## Ⅱ. 구조 및 구성요소

```text
Client -> Facade/Gateway -> Routing Rule -> New Service
                         / Legacy System
                         / Reconciliation
```

| 구성요소 | 역할 | 특이사항 |
|:---|:---|:---|
| Facade/Gateway | 기능별 요청 라우팅 | URL, Header, 사용자 그룹 기준 |
| New Service | 이전 대상 기능 구현 | 도메인 모델 재설계 |
| Legacy System | 미전환 기능 처리 | 변경 최소화 원칙 |
| Data Sync | CDC, 이중 쓰기, 검증 | 정합성 오류 허용치 정의 |

> 요약: Facade가 트래픽을 분기하고 신규 서비스와 레거시가 전환 기간 동안 기능별로 공존한다.

---

## Ⅲ. 동작원리 및 흐름도

```text
기능 목록화 -> 경계 선정 -> Facade 배치 -> 신규 기능 전환 -> 정합성 검증 -> 레거시 제거
```

| 단계 | 처리 내용 | 검증 기준 |
|:---:|:---|:---|
| 1 | 레거시 기능·데이터 의존성 분석 | 기능 목록 100%, 호출 맵 |
| 2 | 전환 우선순위 선정 | 변경 빈도, 장애 빈도, 업무 영향 |
| 3 | Facade 라우팅 적용 | canary 5%부터 시작 |
| 4 | 데이터 정합성 검증 | reconciliation 오류 0.1% 이하 |
| 5 | 레거시 기능 제거 | 호출량 0, 백업 보관 |

> 요약: 스트랭글러는 분석, 라우팅, 전환, 검증, 제거 순서로 진행하며 정합성 지표가 전환 승인 조건이다.

## Ⅳ. 특징

| 구분 | 빅뱅 전환 | 스트랭글러 패턴 | 수치·판단 포인트 |
|:---|:---|:---|:---|
| 전환 방식 | 일괄 오픈 | 기능별 단계 전환 | 5% -> 25% -> 50% -> 100% |
| 위험 | 장애 시 전체 롤백 | 기능 단위 롤백 | RTO 30분 이하 |
| 데이터 | 일회성 이관 | CDC·검증 병행 | mismatch 0.1% 이하 |
| 비용 | 단기 집중 | 이중 운영 기간 발생 | 병행 기간 6~12개월 제한 |

> 요약: 스트랭글러는 전환 위험을 줄이지만 이중 운영 기간과 데이터 동기화 비용을 계획해야 한다.

## Ⅴ. 심화 비교 및 적용 판단

| 구분 | 기존/대안 | 본 키워드 | 선택 기준 |
|:---|:---|:---|:---|
| 재개발 | Big Bang rewrite | 점진 기능 대체 | 핵심 업무 24x7 운영 |
| 데이터 | 전체 이관 | 단계별 CDC·검증 | 데이터 규모 TB 단위 |
| 조직 | 단일 프로젝트 | 도메인별 이전팀 | 기능 소유팀 분리 가능 |

> 요약: 업무 중단 비용이 크고 기능 경계가 분리 가능하면 스트랭글러가 빅뱅보다 적합하다.

| 리스크 | 원인 | 대응 방안 | 확인 지표 |
|:---|:---|:---|:---|
| 정합성 오류 | Dual-write 실패 | Outbox, CDC, reconciliation | mismatch rate |
| 이중 운영 장기화 | 제거 기준 부재 | sunset date, 호출 차단 | legacy traffic 0% |
| 라우팅 오류 | 기능 경계 불명확 | contract test, shadow traffic | routing error rate |

> 요약: 정합성, 장기 병행, 라우팅 오류가 핵심 리스크이며 제거 기준을 지표로 고정해야 한다.

| 점검 항목 | 목표 기준 | 측정 방법 |
|:---|:---|:---|
| 전환 품질 | 신규 기능 오류율 0.1% 이하 | APM, 로그 |
| 데이터 정합성 | reconciliation 99.9% 이상 | 배치 검증, CDC lag |
| 제거 진행 | 레거시 호출량 주간 20% 감소 | Gateway metric |

> 요약: 성공 여부는 신규 기능 오류율, 데이터 정합성, 레거시 호출량 감소로 판단한다.

## Ⅵ. 실무 적용 및 결론

**적용 방안 3개 (필수):**
1. Facade/Gateway를 먼저 배치하고 조회 기능부터 5%, 25%, 50%, 100% 단계로 트래픽 전환함.
2. 쓰기 기능은 Outbox+CDC를 적용하고 신규·레거시 데이터 reconciliation mismatch 0.1% 이하를 전환 승인 기준으로 설정함.
3. 레거시 제거 계획은 기능별 sunset date, 호출 차단 정책, 백업 보관 1년 기준으로 운영함.

**결론 (2줄):**
- 기술사 판단: 업무 중단 허용 시간이 짧고 레거시 기능 경계가 식별되면 스트랭글러, 단순 주변 시스템은 일괄 교체를 선택함.
- 향후 방향: API Gateway, Feature Toggle, CDC, Observability를 결합한 지속적 현대화 방식으로 발전함.
