## Ⅰ. 개요
- **정의**: 다수의 프로그램을 메모리에 동시 적재하여 CPU 유휴 시간을 최소화하는 운영 방식
- **배경/필요성**: 단일 프로그램 실행 시 I/O 대기 중 CPU가 유휴 상태가 되므로 자원 활용률을 높일 수단이 필요함
- **비유**: 세탁기 돌리는 동안 요리하고, 요리 끓는 동안 청소하는 가사 병행 방식과 유사함

| 출제 의도 | 반드시 짚을 핵심 | 감점 회피 포인트 |
|:---|:---|:---|
| CPU 활용률 극대화 원리 | 다중프로그래밍 vs 다중처리 vs 다중태스킹 구분 | 동시 실행이 아닌 CPU 공유(시분할)임을 명확히 |

> 요약: CPU 유휴 시간을 줄이기 위해 여러 프로그램을 메모리에 동시 적재하는 운영 기법임

## Ⅱ. 구성요소
```text
Memory: | Program A | Program B | Program C | OS |
              |             |             |
CPU:     [Run A] --I/O--> [Run B] --I/O--> [Run C] --> ...
```

| 구성요소 | 설명 | 비유 |
|:---|:---|:---|
| Job Scheduler | 디스크의 작업을 메모리에 적재할 순서를 결정 | 대기실에서 진료실로 부르는 접수 담당 |
| CPU Scheduler | 메모리 내 프로세스 중 CPU 할당 대상을 선정 | 진료실에서 환자 순서 결정 |
| Degree of Multiprogramming | 메모리에 동시 적재되는 프로세스 수 | 대기실 좌석 수 |
| Context Switch | CPU 할당 프로세스 전환 시 상태 저장·복원 | 책갈피 꽂고 다른 책 펴기 |

> 요약: 작업 스케줄러, CPU 스케줄러, 적재 수준, 문맥 전환이 핵심 구성요소임

## Ⅲ. 절차
```text
작업 도착 --> 메모리 적재 --> CPU 할당 --> I/O 대기 시 전환
```
- 1단계: Job Scheduler가 디스크 대기 큐에서 작업을 선정하여 메모리에 적재
- 2단계: CPU Scheduler가 Ready Queue에서 프로세스 선택 후 CPU 할당
- 3단계: 실행 중 I/O 요청 발생 시 해당 프로세스를 대기 상태로 전환
- 4단계: 대기 중인 다른 프로세스에 CPU를 할당하여 유휴 시간 제거

> 요약: 적재-할당-대기 전환-재할당 4단계로 CPU 활용률을 극대화함

## Ⅳ. 문제점
- 메모리 부족: 적재 프로세스 수 증가 시 물리 메모리 고갈 — Thrashing 유발(018 참조)
- 문맥 전환 비용: 전환 빈도 증가 시 레지스터·캐시 저장 오버헤드 — 유효 처리량 감소
- 보호 위반 위험: 다수 프로세스 공존 시 메모리 보호 미비 — 프로세스 간 데이터 침범 가능

> 요약: 메모리 고갈, 문맥 전환 비용, 보호 위반이 주요 문제임

## Ⅴ. 개선방안
1. 단기: 가상 메모리(016 참조) 도입으로 물리 메모리 한계 극복
2. 중기: 경량 문맥 전환 기법(레지스터 뱅크, 하드웨어 스레드) 적용으로 전환 비용 절감
3. 장기: MMU 기반 주소 공간 격리 및 하드웨어 보호 키(MPK) 적용으로 보호 강화

> 요약: 가상 메모리, 경량 전환, 하드웨어 보호 순으로 개선 필요

## Ⅵ. 전망
- 발전 방향: 멀티코어·멀티스레드 환경에서 다중프로그래밍은 OS 기본 전제로 내재화됨
- 기술사적 판단: 컨테이너·서버리스 환경에서 적재 밀도 관리가 비용 최적화의 핵심으로 부상 중임
- 기술사 제언: 워크로드 특성별 적재 수준(Degree)을 동적으로 조정하는 자동화 정책 수립이 필요함
