# 📖 【암기용】 개념 완전 이해

## 한눈에
- **개요**: CPU를 놀리지 않기 위해 메모리에 여러 프로그램을 올려 번갈아 실행하는 **다중 프로그래밍(Multiprogramming)**과, 여러 개의 CPU 코어를 장착해 진짜로 동시에 연산하는 **다중 처리(Multiprocessing)**의 비교.
- **왜 필요한가**: 
  - 과거: CPU는 엄청 빠른데 하드 디스크에서 데이터를 읽어오는 시간이 너무 느려, 프로그램 1개만 실행하면 CPU가 I/O 완료를 기다리느라 놀았다(비효율 극치).
  - 현재: 물리적 한계로 CPU 클럭 속도를 무한정 올릴 수 없어, 코어를 여러 개 박아 병렬 연산 성능을 높인다.
- **핵심 직관**: 
  - **다중 프로그래밍**: 요리사 1명이 가스레인지 불을 올려놓고(I/O 대기) 그 틈에 재료를 써는(CPU 연산) 등 3가지 요리를 번갈아 하는 것 (동시성, Concurrency).
  - **다중 처리**: 요리사 3명이 주방에 모여 각자 1가지씩 요리를 병렬로 만들어 내는 것 (병렬성, Parallelism).

## 핵심 용어 정리

| 용어/표기 | 의미 | 비유·예 |
|:---|:---|:---|
| **다중 프로그래밍 (Multiprogramming)** | 단일 CPU에서 여러 프로세스를 메모리에 올려 I/O 대기 시간에 다른 프로세스를 실행 | "한 사람이 여러 일을 번갈아 처리 (멀티태스킹)" |
| **다중 처리 (Multiprocessing)** | 2개 이상의 프로세서(CPU/Core)가 메모리를 공유하며 여러 프로세스를 동시 병렬 실행 | "여러 사람이 동시에 각자의 일을 처리" |
| **시분할 (Time Sharing)** | 다중 프로그래밍의 발전형으로, 사용자 응답성을 높이기 위해 CPU 시간을 아주 짧게 분할(타임 슬라이스)하여 번갈아 실행 | "0.01초 단위로 번갈아 작업해 동시에 하는 것처럼 속임" |
| **SMP (Symmetric Multiprocessing)** | 모든 CPU 코어가 동등한 권한으로 주 메모리를 공유하는 대칭적 다중 처리 아키텍처 | "주방의 모든 요리사가 평등하게 모든 도구 사용" |

## 깊이 이해
- **배경·문제의식**: 
  - 다중 프로그래밍은 CPU 이용률(Utilization)을 극대화하는 목적에서 출발했다. 
  - 다중 처리는 절대적인 연산량(Throughput) 한계를 극복하기 위해 하드웨어를 확장한 것이다.
- **작동 원리**:
  - **다중 프로그래밍**: 프로세스 A가 파일 읽기를 요청하면 디스크 I/O가 끝날 때까지 A를 Block 상태로 두고, 즉시 프로세스 B에 CPU를 할당한다. 
  - **다중 처리**: 코어1은 프로세스 A를, 코어2는 프로세스 B를 실시간으로 완전 동시에 실행한다. 이때 가장 큰 난제는 두 코어가 공유 메모리를 조작할 때 발생하는 캐시 일관성(Cache Coherence)과 동기화 문제다.
- **구체 예시**: 
  - 싱글 코어 시절 윈도우에서 음악을 들으며 워드 작업을 하는 것은 **다중 프로그래밍(시분할)** 덕분이다.
  - 현대의 옥타(8) 코어 스마트폰에서 게임 그래픽 연산과 AI 음성 인식을 동시에 처리하는 것은 **다중 처리** 덕분이다.
- **흔한 오해·주의점**: 두 용어를 혼용하면 안 된다. 다중 프로그래밍은 '소프트웨어적 스케줄링(동시성)'이고, 다중 처리는 '하드웨어적 병렬 실행(병렬성)'이다. 현대 OS는 두 기법을 모두 통합하여 다중 프로세서 위에서 다중 프로그래밍(시분할)을 수행한다.

# 📝 【답안용】 시험 답안 템플릿

## 핵심 인사이트 (3줄 요약)

> 1. **본질**: 다중 프로그래밍은 I/O 대기 시간을 활용해 CPU 이용률을 높이는 단일 코어 기반의 동시성(Concurrency) 기법이며, 다중 처리는 다수 코어로 연산을 분산하는 병렬성(Parallelism) 기법이다.
> 2. **가치**: 다중 프로그래밍은 시분할과 결합하여 사용자 응답성과 자원 효율을 극대화하고, 다중 처리는 무어의 법칙 한계를 넘어 물리적 처리량(Throughput)을 선형적으로 확장한다.
> 3. **판단 포인트**: 현대 시스템 설계는 단순히 코어 수를 늘리는 다중 처리에 그치지 않고, 캐시 일관성(Cache Coherence), NUMA 아키텍처, 병행 제어(Locking) 리스크를 어떻게 아키텍처 레벨에서 통제하느냐가 핵심이다.

## 출제 의도 및 답안 포인트

| 출제 의도 | 반드시 짚을 핵심 | 감점 회피 포인트 |
|:---|:---|:---|
| 운영체제의 발전 과정과 자원 활용 메커니즘 차이 이해 | 동시성(Concurrency) vs 병렬성(Parallelism)의 명확한 구조적 차이 묘사 | 두 개념의 용어를 혼용하거나 차이를 모호하게 서술 |
| 현대 멀티코어 환경의 과제와 해결 방안 도출 | SMP 구조의 캐시 일관성 문제(MESI 프로토콜), 락 경합 병목 | 개념 나열에 그치고, 다중 처리로 발생하는 런타임 리스크 누락 |

> 요약: 다중 프로그래밍은 스케줄링(S/W) 최적화로, 다중 처리는 버스·메모리 공유(H/W) 아키텍처로 접근하여 각자의 목적과 기술적 허들을 대비시켜야 한다.

---

## Ⅰ. 개요 및 필요성

- 개요: 다중 프로그래밍은 메모리에 복수 프로세스를 적재하여 CPU 유휴 시간을 없애는 기법이며, 다중 처리는 2개 이상의 코어로 물리적 동시 연산을 수행하는 구조
- 배경: 프로세스의 I/O 바운드 작업 시 발생하는 CPU 낭비를 막고, 단일 코어의 물리적 클럭 한계(발열 및 전력)를 돌파하기 위함
- 필요성: 시스템의 단위 시간당 처리량 극대화, 다수 사용자의 대화형 응답 시간 단축, 대규모 연산 워크로드의 스케일업(Scale-up)을 위해 두 기술의 통합 필수

---

## Ⅱ. 구조 및 구성요소

```text
[다중 프로그래밍 (단일 코어)]
CPU (1개) -> 프로세스 A (실행) -> (I/O 대기) -> 프로세스 B (실행) -> Context Switch

[다중 처리 (멀티 코어 SMP)]
코어 1 -> 프로세스 A 실행 \ 
                          +-> 시스템 버스 -> 공유 물리 메모리 (캐시 일관성 통제)
코어 2 -> 프로세스 B 실행 /
```

| 기법 분류 | 핵심 구성요소 | 메커니즘 특성 |
|:---|:---|:---|
| 다중 프로그래밍 | 메모리 관리자, CPU 스케줄러 | 문맥 교환(Context Switching), 시분할 타임 슬라이스 관리 |
| 다중 처리 | 다중 코어, 시스템 버스, 공유 캐시 | SMP(대칭형)/ASMP(비대칭형) 구조, MESI 캐시 프로토콜 적용 |

> 요약: 다중 프로그래밍은 단일 프로세서의 시공간 분할(논리적 동시성)에 의존하고, 다중 처리는 H/W 레벨의 버스 및 메모리 공유(물리적 병렬성)에 의존한다.

---

## Ⅲ. 동작원리 및 흐름도

```text
(현대 OS의 통합 동작 흐름)
Ready Queue -> 다중 프로세서 스케줄러(Load Balancer)가 코어 할당
  -> 코어 1: 프로세스 A 할당 -> 타임 퀀텀 만료 또는 I/O 발생 -> 프로세스 C로 교환 (다중 프로그래밍)
  -> 코어 2: 프로세스 B 할당 -> 프로세스 B 지속 연산 (다중 처리)
  -> 캐시 일관성 유지 (Snooping) 및 공유 데이터 락(Lock) 검증
```

- 1단계 [작업 배분]: 큐에 대기 중인 프로세스들을 여러 CPU 코어에 균형 있게 분산(Load Balancing, 다중 처리)
- 2단계 [논리적 교환]: 개별 코어 내에서 I/O 요청 시 블로킹하고 다른 레디 프로세스 투입(다중 프로그래밍)
- 3단계 [공유 자원 통제]: 여러 코어가 동일한 메모리 주소를 참조·수정할 때 캐시 스누핑(Snooping)으로 정합성 유지
- 4단계 [확장 실행]: 두 기법의 융합으로 전체 스루풋이 코어 수에 비례에 근접하여 선형 향상됨

> 요약: 다중 처리가 물리적 실행 공간(Core)을 제공하면, 각 공간 내에서 다중 프로그래밍이 시간(Time)을 분할하여 종합적 효율을 낸다.

## Ⅳ. 비교 (목적 및 한계)

| 비교 축 | 다중 프로그래밍 (Multiprogramming) | 다중 처리 (Multiprocessing) | 아키텍처 판단 |
|:---|:---|:---|:---|
| 달성 목표 | CPU 이용률(Utilization) 및 대기 시간 최소화 | 시스템 전체 처리량(Throughput)의 절대적 증가 | 자원 한계 튜닝 vs 연산 자원 증설 |
| 동시성 성격 | 동시성 (Concurrency, 빠른 교대로 속임) | 병렬성 (Parallelism, 물리적 완전 동시 실행) | H/W 스펙에 따른 S/W 설계 패러다임 차이 |
| 발생 병목 | 문맥 교환(Context Switch) 오버헤드 | 메모리 버스 경합 및 락(Lock) 경합 | 스케줄러 최적화 vs 캐시 일관성 및 Lock-free 구조 |
| 메모리 상태 | 프로세스 간 메모리 독립, 가상 메모리 스왑 | 코어 간 물리 메모리 100% 공유 (캐시 동기화 지연) | IPC(통신) 오버헤드 vs 메모리 락 지연 |

> 요약: 다중 프로그래밍의 한계는 문맥 교환 비용이며, 다중 처리의 한계는 암달의 법칙(Amdahl's Law)에 따른 직렬화 병목과 메모리 경합이다.

## Ⅴ. 심화 비교 및 적용 판단

**리스크·대응:**
- 캐시 핑퐁 및 거짓 공유(False Sharing): 다중 처리 시 인접한 변수를 서로 다른 코어가 갱신하여 전체 캐시 라인이 무효화되는 지연 발생 → 패딩(Padding) 기법으로 변수 간 메모리 간격을 벌려 캐시 라인을 분리 (지표: Cache Miss Rate)
- 버스 포화 및 확장성 한계: 코어가 8~16개를 넘어가면 단일 시스템 버스의 병목으로 인해 코어 추가 시 오히려 성능이 정체됨(SMP 한계) → CPU마다 독립된 로컬 메모리를 부여하는 NUMA(Non-Uniform Memory Access) 아키텍처로 분산 

**도입 후 점검 지표:**
- 성능: 코어 수 증가에 따른 처리량 확장의 선형성 (Scalability Factor) 측정 — 암달의 법칙 계산치 대비 실측치 비교
- 품질: 락 경합(Lock Contention) 시간 및 컨텍스트 스위치 횟수(cs/s) 안정 유지

---

## Ⅵ. 실무 적용 및 결론

**적용 방안 3개:**
1. CPU 친화도(Affinity) 설정: 프로세스가 잦은 문맥 교환으로 이 코어 저 코어 옮겨 다녀 L1/L2 캐시를 잃는 것을 막기 위해, 특정 프로세스를 고정된 코어에 할당(Pinning)하여 캐시 히트율 극대화
2. NUMA-Aware 스케줄러 튜닝: 다중 처리 확장 시, 커널 스케줄러 및 DB(Oracle, MS-SQL 등)가 원격 메모리 대신 자신의 노드(Local Memory)에 할당된 메모리만 우선 사용토록 아키텍처 맞춤 설정
3. Lock-Free 자료구조 도입: 스핀락이나 뮤텍스 등 직렬화 구간이 성능 발목을 잡는 다중 처리 환경에서, CAS(Compare-And-Swap) 원자적 명령어 기반의 무잠금 로직으로 병렬성 이점 확보

**결론 (2줄):**
- 기술사 판단: 코어만 늘린다고 다중 처리 성능이 비례하지 않으므로, S/W 레벨의 직렬화 구간(락) 제거와 H/W 레벨의 캐시/메모리 지역성(Affinity, NUMA) 보장을 동시에 튜닝해야 한다.
- 향후 방향: 전통적 CPU 다중 처리를 넘어 수천 개의 코어로 극단적 병렬성을 구현하는 GPU, NPU 기반의 이기종(Heterogeneous) 다중 처리 패러다임으로 워크로드가 이전 중이다.
