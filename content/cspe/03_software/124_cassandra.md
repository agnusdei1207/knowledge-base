# 📖 【암기용】 개념 완전 이해

## 한눈에
- **개요**: 단일 장애점(SPOF)이 없는 완벽한 분산 링(Ring) 아키텍처를 기반으로, 막대한 양의 쓰기 데이터를 멈춤 없이 빠르게 받아내는 대용량 NoSQL 데이터베이스이다.
- **왜 필요한가**: 전 세계 수백만 대의 기기에서 초당 수만 건씩 쏟아지는 센서 로그나 메신저 대화 기록을 저장할 때, 마스터-슬레이브 구조는 마스터 노드에 쓰기 부하가 집중되어 터지기 쉽다. 모든 노드가 동등하게 쓰기를 분담할 구조가 필요했다.
- **핵심 직관**: 리더(Master) 없이 팀원 모두가 똑같은 권한을 가진 원탁회의와 같다. 누구에게 데이터를 줘도 알아서 저장하고, 동기화(Gossip)하여 거대한 분산 저장소를 형성한다.

## 핵심 용어 정리

| 용어/표기 | 의미 | 비유·예 |
|:---|:---|:---|
| Wide Column Store | 행마다 가질 수 있는 열(Column)의 수와 이름이 유동적인 구조 | 사람마다 항목 갯수가 맘대로 늘어나는 엑셀 표 |
| Masterless Ring | 마스터 노드 없이 모든 노드가 동등한 링 형태 구조 | 반장 없이 모두가 평등하게 일감을 나누는 팀 |
| Gossip Protocol | 노드 간 상태 정보를 주기적으로 교환하는 통신 방식 | 쉬는 시간에 서로 "A노드는 살아있대" 소문내기 |
| SSTable / Memtable | 메모리(Memtable)에 썼다가 디스크(SSTable)로 순차 저장 | 칠판에 적다가 꽉 차면 공책 한 장으로 박제하기 |

## 깊이 이해
- **배경·문제의식**: RDBMS나 일반적인 마스터 기반 DB는 쓰기(Write) 작업을 한 노드(마스터)가 독점하므로 쓰기 확장에 한계가 뚜렷했다. Amazon Dynamo의 분산 해시 테이블(DHT) 아키텍처와 Google Bigtable의 컬럼 기반 저장 방식을 결합하여, 쓰기 성능이 극대화된 분산 DB가 탄생했다(페이스북에서 개발).
- **작동 원리**: 데이터가 들어오면 파티션 키(Partition Key)를 해싱하여 링(Ring) 상의 어느 노드에 저장할지 결정한다(일관된 해싱). 저장은 디스크의 임의 위치를 찾는 대신(Random I/O), 메모리(Memtable)에 쌓았다가 디스크에 순차적으로 한 번에 기록(Sequential I/O, SSTable)하여 쓰기 속도가 압도적으로 빠르다.
- **비유**: 편지 수만 통을 우체통 번호(해시)에 맞춰 바로바로 던져 넣는 것. 우체통이 많을수록(노드 추가) 담는 속도는 무한히 빨라진다. 단, 나중에 특정 편지 뭉치를 다시 찾아올(읽기) 때는 최적화가 안 되어 있으면 꽤 고생한다.
- **구체 예시**: 애플, 넷플릭스 등에서 사용자 활동 로그, 타임라인 데이터 등을 저장할 때 쓴다. 초당 수십만 건의 "좋아요", "재생 위치" 기록이 병목 없이 노드들에 분산 저장된다.
- **흔한 오해·주의점**: "조인(Join)과 트랜잭션이 가능하다?" 불가능하다. 데이터를 넣을 때부터 읽을 화면(Query)에 맞춰 중복 저장(비정규화)해야 한다. 쿼리 유연성이 매우 떨어지므로, 오직 "빠른 대량 쓰기"와 "패턴이 정해진 읽기"에만 특화된 무기다.

## 연결 개념
- 일관된 해싱 (Consistent Hashing) — 데이터 분산 원리
- LSM-Tree — 고속 쓰기를 위한 저장 구조
- CAP 정리 — Cassandra는 AP(가용성/분할 내성) 시스템, Eventual Consistency 지향

# 📝 【답안용】 시험 답안 템플릿

## 핵심 인사이트 (3줄 요약)

> 1. **본질**: 마스터-슬레이브 구조의 한계를 탈피한 마스터리스(Masterless) 링 아키텍처와 와이드 컬럼(Wide Column) 데이터 모델을 결합한 분산 NoSQL DB이다.
> 2. **가치**: 일관된 해싱(Consistent Hashing)과 LSM-Tree 기반 저장소로 선형적인 수평 확장성과 압도적인 쓰기(Write) 성능, 무중단 고가용성을 제공한다.
> 3. **판단 포인트**: 강력한 쓰기 성능을 얻는 대신 유연한 조회가 불가능하므로, 철저하게 쿼리 중심(Query-driven)으로 데이터를 비정규화하는 모델링 전환이 필수적이다.

## 출제 의도 및 답안 포인트

| 출제 의도 | 반드시 짚을 핵심 | 감점 회피 포인트 |
|:---|:---|:---|
| 고가용성 대용량 쓰기 분산 아키텍처 이해 확인 | Masterless Ring, Gossip, LSM-Tree, Tunable Consistency | RDBMS식 데이터 모델링(정규화) 적용으로 서술 |

> 요약: 단일 장애점이 없는 완벽한 분산 구조의 원리와, 쓰기에 최적화된 내부 저장 메커니즘을 튜닝 가능한 일관성(Tunable Consistency) 관점에서 설명한다.

## Ⅰ. 개요 및 필요성

- 개요: 구글 Bigtable의 데이터 모델과 아마존 Dynamo의 완전 분산 아키텍처를 결합하여 대규모 쓰기 부하를 처리하는 컬럼 패밀리 NoSQL
- 배경: 마스터 기반 시스템은 쓰기 병목과 단일 장애점(SPOF)을 가지며, 빅데이터 환경에서 데이터 노드의 선형적 확장이 어려움
- 필요성: 노드 장애 시에도 중단 없는 서비스(고가용성), 수십만 TPS의 대량 로그 및 시계열 데이터의 고속 분산 저장을 보장하는 아키텍처 필요

---

## Ⅱ. 구조 및 구성요소

```text
Client -> Coordinator Node (Ring 내 임의 노드)
            | (해싱 라우팅)
            +-> Node A (Replica 1)
            +-> Node B (Replica 2) -> Gossip 통신 -> Node C (Replica 3)
```

| 구성요소 | 역할 | 특이사항 |
|:---|:---|:---|
| Masterless Ring | 모든 노드가 동등한 권한으로 링 구조로 배치 | SPOF 없음, 병목 제거 |
| Gossip Protocol | 노드 상태 및 메타데이터를 P2P로 비동기 교환 | 중앙 제어 없는 분산 코디네이션 |
| Coordinator | 클라이언트 요청을 받아 해시 키 기반 타겟 노드로 분배 | 요청받은 노드가 동적 코디네이터 역할 수행 |

> 요약: 마스터가 없는 피어 투 피어(P2P) 링 구조로, 어떤 노드에 접속하든 코디네이터가 되어 투명한 수평 확장을 이룬다.

---

## Ⅲ. 동작원리 및 흐름도

```text
Write Request -> Commit Log 기록 -> Memtable 적재 -> (임계치 도달) -> SSTable Flush
```

- 1단계 [분산 라우팅]: 코디네이터가 파티션 키를 해싱하여 데이터가 저장될 대상 노드들(Replicas) 식별
- 2단계 [로그 및 메모리 기록]: 각 대상 노드는 장애 복구를 위해 Commit Log(디스크)에 순차 기록 후, Memtable(메모리)에 데이터 적재
- 3단계 [디스크 플러시]: Memtable이 가득 차면 불변(Immutable)의 SSTable(Sorted String Table) 형태로 디스크에 순차 쓰기(Sequential I/O) 수행
- 4단계 [백그라운드 병합]: 읽기 성능 저하를 막기 위해 여러 SSTable을 백그라운드에서 병합 및 파편화 제거(Compaction) 수행

> 요약: Random I/O를 배제하고 메모리 적재와 디스크 순차 쓰기를 결합(LSM-Tree)하여 압도적인 쓰기 처리량을 달성한다.

---

## Ⅳ. 특징

- 튜닝 가능한 일관성 (Tunable Consistency): 데이터 읽기/쓰기 시 응답을 기다릴 복제본의 수(Quorum, All, One)를 조정하여 강한 일관성(CP)과 고가용성(AP) 간의 균형을 런타임에 결정
- 선형적 확장성: 노드를 추가할수록 데이터 재분배가 백그라운드에서 이루어지며, 쓰기/읽기 처리량이 거의 1:1로 선형 증가
- 쿼리 지향 모델링 (Query-Driven Modeling): 조인 연산이 없으므로, 애플리케이션의 조회 패턴(SELECT)을 먼저 정의하고 이에 맞춰 데이터를 중복 저장(비정규화)하도록 테이블 설계

> 요약: 일관성 수준을 개발자가 조율할 수 있으며, 빠른 쓰기를 위해 RDBMS와는 완전히 반대되는 비정규화 중심 모델링이 요구된다.

## Ⅴ. 심화 비교 및 적용 판단

| 비교 축 | HBase (Master/Slave) | Cassandra (Masterless) | 선택 기준 |
|:---|:---|:---|:---|
| 아키텍처 | 마스터(HMaster) 중심 구조 | P2P 링 기반 완벽 분산 | 단일 장애점 민감도 및 운영 복잡성 |
| 일관성 모델 | 강한 일관성 (CP 보장) | 최종 일관성 지향 (AP 중심, 조율 가능) | 쓰기 가용성 vs 데이터 즉시 정합성 |
| 데이터 저장 체계 | HDFS (Hadoop 생태계 의존) | 자체 로컬 파일 시스템 (독립 실행) | 기존 하둡 인프라 연동 여부 |

> 요약: 완벽한 정합성과 하둡 연동이 중요하면 HBase를, 다중 데이터센터 간 활성 복제와 무중단 고가용성이 중요하면 Cassandra를 선택한다.

**리스크·대응 (기본은 불릿):**
- 툼스톤(Tombstone) 누적: 삭제 연산 시 즉시 지우지 않고 마커(Tombstone)만 남기므로, 잦은 삭제/업데이트 시 읽기 성능 급감 → TTL 활용 및 Compaction 전략 최적화 (지표: Read Latency 및 Tombstone 스캔 비율)
- 핫 파티션(Hot Partition): 파티션 키 설계 오류로 특정 노드에 데이터 집중 → 복합 파티션 키 설계로 균등 분산 (지표: 노드별 디스크 및 CPU 불균형)

**도입 후 점검 지표 (기본은 불릿):**
- 성능/효율: 클러스터 Write 응답시간 p95 10ms 이하 유지 — 노드 JMX 메트릭 분석
- 품질/운영: 노드 간 데이터 불일치를 해소하는 Read Repair 및 Hinted Handoff 동작 건수 모니터링

## Ⅵ. 실무 적용 및 결론

**적용 방안 3개:**
1. 시계열 IoT 센서 데이터 수집: 수백만 디바이스에서 초당 수만 건씩 유입되는 센서 시계열 데이터를 타임스탬프 기반 파티셔닝으로 고속 적재
2. 다중 리전(Multi-Region) 무중단 서비스: 글로벌 스트리밍 서비스(넷플릭스 등)에서 리전 단위의 장애가 발생해도 타 리전에서 멈춤 없이 개인화 프로필 데이터 서빙
3. 대규모 메시징 및 로그 저장소: 카카오톡, 라인 등 메시징 플랫폼에서 대화 내용과 유저 상태(Presence) 로그를 조인 없이 쿼리 기반 구조로 중복 저장

**결론 (2줄):**
- 기술사 판단: Cassandra는 극강의 쓰기 처리량과 고가용성을 제공하지만, 유연한 쿼리나 즉각적인 강한 정합성이 필요한 업무에는 부적합하므로 목적이 명확한 로그/이벤트 저장소로 한정해야 한다.
- 향후 방향: 클라우드 네이티브 환경에 맞춰 컨테이너화 및 k8s 연동(K8ssandra)이 강화되고 있으며, 분산 트랜잭션의 한계를 극복하기 위한 확장 합의 프로토콜 도입 논의가 진행 중이다.
