# 📖 【암기용】 개념 완전 이해

## 한눈에
- **개요**: 기업 내부의 프라이빗 클라우드(온프레미스)와 외부의 퍼블릭 클라우드를 전용 네트워크로 연결해 하나의 인프라처럼 사용하는 모델이다.
- **왜 필요한가**: 금융·공공 등 보안 규제가 강한 핵심 데이터는 내부에 둬야 하지만, 대규모 트래픽이 몰릴 때는 퍼블릭 클라우드의 무한한 확장성도 필요하다. 두 마리 토끼를 다 잡기 위해 도입한다.
- **핵심 직관**: "평소에는 내 차(프라이빗)를 타고, 가족 여행이나 짐이 많을 때는 렌터카(퍼블릭)를 추가로 빌려 타는 것"과 같다.

## 핵심 용어 정리

| 용어/표기 | 의미 | 비유·예 |
|:---|:---|:---|
| 프라이빗 클라우드 | 기업 방화벽 내부에 자체 구축한 폐쇄형 클라우드 | "자체 금고" (보안은 강하나 확장 제한) |
| 클라우드 버스팅 (Cloud Bursting) | 평소엔 내부 자원을 쓰다, 임계치 초과 시 퍼블릭 클라우드로 워크로드 확장 | "매장 꽉 차면 야외 테라스(퍼블릭) 개방" |
| 전용선 (Direct Connect) | 온프레미스와 퍼블릭 클라우드를 연결하는 보안된 고속 사설망 | "두 건물 사이를 잇는 외부와 차단된 지하 터널" |

## 깊이 이해
- **배경·문제의식**: (162 배포 모델 참조) 기존 데이터센터(온프레미스)는 피크 타임에 맞춰 장비를 샀다가 유휴 자원 낭비(Over-provisioning)가 컸다. 반면 퍼블릭 전면 전환은 규제와 레거시 연동 문제로 막혔다.
- **작동 원리**: 프라이빗과 퍼블릭 간에 IPSec VPN이나 Direct Connect(전용선)를 연결한다. 데이터베이스와 코어 시스템은 프라이빗에 남겨 규제를 충족하고, 상태가 없는(Stateless) 웹 서버나 이벤트 처리기만 퍼블릭에 배치해 확장성을 확보한다.
- **비유**: 핵심 요리법과 메인 주방(프라이빗)은 본점에 두고, 주문이 밀리는 연말에는 배달 전문 공유 주방(퍼블릭)을 임시로 빌려 음식을 쳐내는 식이다.
- **구체 예시**: 대학 수강신청 시스템. 학생 정보 DB(프라이빗)는 학교 전산실에 두고, 수강신청 당일 10만 명이 몰리는 웹 서버(퍼블릭)는 AWS EC2 오토스케일링으로 일시 확장해 처리한다.
- **흔한 오해·주의점**: 멀티 클라우드(163)와 헷갈리기 쉽다. 하이브리드는 **'온프레미스(프라이빗) + 퍼블릭'**으로 통제력과 확장성의 결합이고, 멀티는 '퍼블릭 + 퍼블릭'으로 종속성 회피 목적이다.

## 연결 개념
- 멀티 클라우드(Multi Cloud) — 다른 CSP 조합(163 참조)
- 엣지 컴퓨팅(Edge Computing) — 중앙 클라우드와 현장(온프레미스 엣지)을 연계하는 물리적 확장
- 클라우드 마이그레이션(Cloud Migration) — 온프레미스에서 클라우드로 넘어가는 과도기적 단계

# 📝 【답안용】 시험 답안 템플릿

## 핵심 인사이트 (3줄 요약)

> 1. **본질**: 하이브리드 클라우드는 보안성이 높은 프라이빗 클라우드(온프레미스)와 확장성이 뛰어난 퍼블릭 클라우드를 네트워크로 연동하여 워크로드를 분산하는 배포 아키텍처이다.
> 2. **가치**: 민감한 데이터의 규제 준수(Compliance)를 달성하면서도, 클라우드 버스팅을 통해 IT 인프라 투자의 비용 효율성(CAPEX 최소화)을 극대화한다.
> 3. **판단 포인트**: 도입 시 프라이빗과 퍼블릭 간의 네트워크 지연(Latency), 이기종 환경 통합 관리(CMP), 그리고 데이터 이동 시의 보안 터널링 및 암호화를 설계해야 한다.

## 출제 의도 및 답안 포인트

| 출제 의도 | 반드시 짚을 핵심 | 감점 회피 포인트 |
|:---|:---|:---|
| 배포 모델 간 결합 시너지 이해 | 보안(프라이빗) + 탄력성(퍼블릭)의 상호 보완적 이점 | 멀티 클라우드와 개념 혼용 (차이 명시 필요) |
| 하이브리드 아키텍처 실무 구성 패턴 | 클라우드 버스팅, DR(재해복구) 구성, 분리형(계층별 분리) | 단지 두 클라우드를 같이 쓴다는 수준의 단순 설명 |
| 네트워크 및 통합 운영 리스크 제어 | 전용선(Direct Connect), VPN, CMP(Cloud Mgmt Platform) 도입 | 데이터 동기화 병목과 네트워크 지연 간과 |

> 요약: 보안 규제와 확장성 요구라는 비즈니스 모순을 해결하는 아키텍처 구성과 함께, 네트워크 연동 병목 리스크 대응 방안을 제시해야 한다.

## Ⅰ. 개요 및 필요성

- 개요: 자체 인프라를 활용하는 프라이빗 클라우드와 외부 자원인 퍼블릭 클라우드를 상호 연결(Orchestration)하여 워크로드와 데이터를 공유하는 컴퓨팅 환경
- 배경: 퍼블릭 전면 마이그레이션 시 기존 레거시 시스템 연동의 어려움과 데이터 주권(Data Sovereignty), 개인정보보호법 규제 충돌
- 필요성: 핵심 자산 보호와 규제 준수를 프라이빗으로 해결하고, 가변적인 트래픽 대응 및 신속한 리소스 확장을 퍼블릭으로 해결하는 전략적 혼용 필요

---

## Ⅱ. 구조 및 구성요소

```text
[ Private Cloud (On-Prem) ] <=====================> [ Public Cloud (CSP) ]
- Core Database / Legacy     (Direct Connect/VPN)   - Web / AI Analytics
- Compliance Data           - API / IAM Sync      - Scalable Compute
          \                                               /
           +------------> [ CMP / K8s Federation ] <-----+
```

| 구성요소 | 역할 | 특이사항 |
|:---|:---|:---|
| 프라이빗 환경 (Private) | 민감 데이터 저장, 인증(AD), 레거시 시스템 운영 | 보안 통제 100%, 자원 한계 존재 |
| 퍼블릭 환경 (Public) | 채널계 서비스, 대용량 데이터 처리, 컨테이너 런타임 | 탄력적 확장(Auto Scaling), 종량제 |
| 네트워크 연동 (Network) | 이기종 환경 간 고속/보안 통신 경로 제공 | IPSec VPN(저비용) 또는 전용선(고성능) |
| 통합 관리 평면 (CMP) | 자원 배포, 모니터링, 과금 가시성을 단일 UI로 제공 | K8s 기반 멀티 클러스터 관리(Anthos 등) |

> 요약: 프라이빗의 데이터 계층과 퍼블릭의 프레젠테이션/컴퓨팅 계층을 전용 네트워크로 묶고 CMP로 통합 제어한다.

---

## Ⅲ. 동작원리 및 흐름도

```text
워크로드 분류(DB vs Web) -> 네트워크/인증 연동 -> 컨테이너 오케스트레이션 -> 클라우드 버스팅
```

- 1단계 [워크로드 티어링]: 데이터 보안 등급을 분류하여 코어(DB)는 프라이빗에, 프론트엔드(Web)는 퍼블릭에 배치 설정
- 2단계 [인프라 연동]: Direct Connect(AWS) 또는 ExpressRoute(Azure)를 개통하고 사내 AD(Active Directory)와 퍼블릭 IAM 연합(SSO) 구성
- 3단계 [애플리케이션 배포]: 쿠버네티스(K8s) 연합을 통해 동일한 컨테이너 이미지를 프라이빗과 퍼블릭 워커 노드에 동시 배포
- 4단계 [동적 트래픽 처리]: 프라이빗 자원 임계치(예: CPU 80%) 도달 시, GSLB가 퍼블릭 클라우드로 트래픽을 넘겨(Bursting) 지연 방지

> 요약: 데이터는 안전한 내부에 남겨둔 상태에서, 연동된 네트워크를 통해 트래픽에 따라 퍼블릭의 연산 자원을 동적으로 빌려 쓴다.

---

## Ⅳ. 특징

- 규제 샌드박스 역할: 금융망 분리 규제, 의료 데이터 등 데이터 로컬리티(Data Locality) 제약을 물리적으로 완벽히 충족
- 유휴 자원 방지: 최대 피크 트래픽을 위해 온프레미스 서버를 대량 구매할 필요 없이 기본 워크로드 수준의 장비만 유지 가능(TCO 절감)
- 점진적 마이그레이션: 레거시 시스템을 단번에 퍼블릭으로 옮기는 '빅뱅' 방식의 위험을 피하고 10년 이상 장기 공존하는 과도기 전략 제공
- 네트워크 의존성 심화: 프라이빗 DB와 퍼블릭 Web 간 통신 시 전용선 대역폭 초과나 네트워크 장애가 시스템 전체 병목(Bottleneck) 유발

## Ⅴ. 심화 비교 및 적용 판단

| 비교 축 | 멀티 클라우드 (Multi) | 하이브리드 클라우드 (Hybrid) |
|:---|:---|:---|
| 구성 조합 | 퍼블릭 + 퍼블릭 | 프라이빗(온프레미스) + 퍼블릭 |
| 주요 동인 | 벤더 종속성(Lock-in) 회피 | 데이터 규제 준수 및 기존 레거시 연동 |
| 데이터 위치 | 다수의 외부 CSP 분산 | 핵심 데이터는 내부(프라이빗) 보관 |
| 최적 적용처 | 글로벌 서비스, 최신 AI 융합 | 금융권 하이브리드 인프라, 공공기관 |

> 요약: 하이브리드는 '내부와 외부의 결합'으로 보안 통제력을 중시하고, 멀티는 '외부와 외부의 결합'으로 종속성 회피를 중시한다.

**리스크·대응:**
- 네트워크 지연(Latency)에 따른 DB 병목: 퍼블릭의 App이 프라이빗의 DB에 질의 시 수십 ms 지연 발생 → 퍼블릭 측에 In-memory Cache(Redis) 배치 및 읽기 복제본(Read Replica) 운영 (지표: DB 응답 Latency 5ms 유지)
- 단절된 보안 경계: 퍼블릭으로 열린 포트가 내부망 침투의 교두보가 됨 → Zero Trust Architecture 적용 및 세그멘테이션 격리 (지표: 침해 사고 수)

**도입 후 점검 지표:**
- 버스팅 성공률: 임계치 도달 후 퍼블릭 자원 스핀업(Spin-up) 및 트래픽 전환 완료까지 걸린 시간 — Auto Scaling 지표 모니터링
- 인프라 TCO 절감률: 기존 온프레미스 풀 증설 대비 하이브리드 운영 비용 비교 — FinOps 대시보드

---

## Ⅵ. 실무 적용 및 결론

**적용 방안 3개:**
1. 데이터-처리 분리 (Data Tiering): DB 및 고객 정보는 프라이빗에 격리하고, AI 분석 모델링 작업이나 웹 렌더링 서버만 퍼블릭 클라우드의 무한 연산 자원으로 구동
2. 클라우드 버스팅 (Cloud Bursting): 이커머스의 '블랙 프라이데이' 등 특정 기간에만 퍼블릭 클라우드 인스턴스를 임대하여 트래픽 흡수 후 반납
3. 클라우드 백업 및 DR (Disaster Recovery): 프라이빗 데이터센터 화재 등 재해 시, 퍼블릭 클라우드 스토리지(S3 등) 백업본을 활용해 즉시 퍼블릭 리전에서 서비스 복구

**결론 (2줄):**
- 기술사 판단: 하이브리드 클라우드는 보안과 확장성을 동시에 잡는 엔터프라이즈의 표준 아키텍처이지만, 온-오프 간 네트워크 대역폭 한계와 지연 시간 극복 설계가 성패를 가른다.
- 향후 방향: 하이브리드 구성을 쉽게 하기 위해 CSP가 온프레미스에 자체 하드웨어 어플라이언스를 설치해주는 AWS Outposts, Azure Stack 등의 관리형 엣지 솔루션이 확산되고 있다.
