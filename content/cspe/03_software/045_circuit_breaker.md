# 📖 【암기용】 개념 완전 이해

> 목적: 이 개념을 처음 보는 사람도 완벽히 이해하게 만든다. 시험 답안 양식이 아니라, 이해를 위한 친절한 설명이다.

## 한눈에
- **개요**: **서킷 브레이커**는 분산 시스템에서 특정 서비스 호출의 실패율이 임계치를 넘으면 후속 호출을 즉시 차단(Fast Fail)해 장애가 다른 서비스로 번지는 것을 막는 **내결함성(Fault Tolerance) 디자인 패턴**이다.
- **왜 필요한가**: 모놀리식은 함수 호출 중 에러가 나면 그 자리에서 멈추지만, MSA(042)는 서비스 간 호출이 네트워크(HTTP)를 탄다. 상대 서비스가 응답하지 않으면 호출한 쪽은 타임아웃까지 스레드를 붙잡고 기다리고, 이 대기가 쌓이면 호출한 서비스의 자원(스레드 풀)까지 고갈되어 정상이던 서비스까지 함께 멈춘다(연쇄 장애).
- **핵심 직관**: 가정용 누전 차단기와 같다. 회로에 과전류가 흐르면(에러율 급증) 차단기가 내려가 이후 전류를 아예 흘리지 않고(Open), 원인이 해결됐는지 소량만 흘려보며 확인한 뒤(Half-Open) 정상이면 다시 회로를 연결한다(Closed).

## 핵심 용어 정리 (내부에 등장하는 것들)

| 용어 | 의미 | 비유 |
|:---|:---|:---|
| Closed (닫힘) | 정상 상태 — 호출이 그대로 통과됨 | 차단기가 내려가지 않은 평소 상태 |
| Open (열림) | 차단 상태 — 호출을 시도하지 않고 즉시 실패 처리 | 차단기가 내려가 전기가 끊긴 상태 |
| Half-Open (반열림) | 일정 시간 후 소수의 요청만 흘려보내 복구 여부를 시험하는 상태 | 전기 기사가 소량 전류로 테스트하는 상태 |
| 슬라이딩 윈도우 (Sliding Window) | 최근 N번의 호출(또는 최근 N초)만 기준으로 실패율을 계산하는 방식 | 최근 100개 시험 답안만 보고 합격률 계산 |
| 임계치 (Threshold) | Open으로 전환되는 기준 실패율(예: 50%) | 불량률 기준선 |
| Fast Fail (빠른 실패) | 응답을 기다리지 않고 즉시 실패로 처리해 자원 낭비를 막는 것 | 통화 중 신호를 듣자마자 바로 끊는 것 |
| Fallback (폴백) | 차단 시 에러 대신 반환하는 대체 응답(캐시된 값, 기본값 등) | 정전 시 비상등으로 대체 |
| Bulkhead (벌크헤드) | 서비스별로 스레드 풀을 물리적으로 분리해 한쪽 고갈이 다른 쪽에 안 번지게 함 | 배의 방수 격벽 |
| Timeout / Retry | 응답 대기 한도 / 실패 시 재시도 — 서킷 브레이커와 함께 쓰이지만 역할이 다른 별개 기법 | 벨을 몇 초 기다리고, 안 되면 몇 번 다시 누르는 것 |

## 깊이 이해

### 배경 — 넷플릭스가 겪은 연쇄 장애
- 넷플릭스는 수백 개의 마이크로서비스를 운영하며, 부가 기능(예: 리뷰 서비스) 하나의 장애가 영화 재생이라는 핵심 기능까지 막아버리는 연쇄 장애(Cascading Failure)를 겪었다. 리뷰가 없어도 영화는 재생돼야 하는데, 리뷰 서비스 호출이 타임아웃 없이 계속 대기하면서 그 스레드를 쥔 채 재생 요청 처리까지 막았기 때문이다. 이를 막기 위해 만든 라이브러리가 Hystrix이며, 이후 Resilience4j 등으로 이어졌다.

### 연쇄 장애의 메커니즘 — 스레드 풀 고갈을 수치로 보기
- 결제 서비스의 스레드 풀이 200개이고, 정상 상태에서 요청 하나를 200ms에 처리한다고 하자. 초당 100건이 유입되면 평균적으로 동시에 붙잡혀 있는 스레드는 100건 × 0.2초 = 20개 수준으로 여유가 있다.
- 이제 결제 서비스가 호출하는 PG(외부 결제대행) 서버가 응답 없이 멈췄고, 타임아웃 설정이 5초라고 하자. 요청 하나가 스레드를 5초씩 붙잡으므로, 초당 100건이 계속 유입되면 100건 × 5초 = 500개의 스레드가 필요해진다. 풀은 200개뿐이므로 약 2초(200/100) 만에 풀이 고갈되고, 이후 유입되는 모든 요청(결제와 무관한 다른 요청 포함)이 스레드를 못 받아 대기·거부된다 — 장애가 결제 서비스 전체로, 나아가 결제를 호출하는 상위 서비스로 번진다.
- 서킷 브레이커가 있으면, 실패가 임계치를 넘는 순간 이후 요청은 PG 서버를 아예 호출하지 않고(Fast Fail) 즉시 에러·폴백을 반환하므로 스레드가 5초씩 묶이는 일 자체가 사라진다.

### 상태 전이 — 구체적 파라미터로 보는 동작
- Resilience4j 기본값을 예로 들면: 슬라이딩 윈도우 크기 100회, 실패율 임계치 50%. 최근 100번의 호출 중 51번 이상이 실패(5xx, 예외, 타임아웃)하면 Closed → Open으로 전환한다.
- Open 상태는 설정된 대기 시간(예: 60초) 동안 유지되며, 이 동안의 모든 호출은 실제 네트워크를 타지 않고 즉시 예외·폴백을 반환한다.
- 60초가 지나면 Half-Open으로 전환해 설정된 수(예: 10회)의 요청만 실제로 흘려보낸다. 이 10회 중 성공률이 임계치 이상이면 Closed로 복귀하고, 임계치 미만이면 다시 Open으로 되돌아가 대기 시간을 재시작한다.

### 판별 원리 — Circuit Breaker vs Timeout/Retry vs Bulkhead
- Timeout은 "얼마나 기다릴지"를, Retry는 "실패 시 몇 번 다시 시도할지"를 정하는 것으로, 서킷 브레이커와 별개의 축이다. Retry를 무분별하게 쓰면 이미 죽은 서비스에 재시도 요청까지 겹쳐 트래픽이 더 폭증할 수 있어, 서킷 브레이커가 Open이면 Retry 자체를 건너뛰게 조합해야 한다.
- Bulkhead는 "장애가 나도 그 여파가 다른 기능으로 안 번지게" 스레드 풀을 서비스별로 물리적으로 나누는 것이고, 서킷 브레이커는 "장애가 난 대상 호출 자체를 끊는" 것이다. Bulkhead는 격리, 서킷 브레이커는 차단으로 역할이 다르며 실무에서는 함께 적용한다.

### 비유와 흔한 오해
- **비유**: 맛집에 불이 나서 줄 선 사람들이 안 빠지고 있으면, 경찰이 바리케이드를 쳐서 신규 손님의 진입을 막는다(Open). 사람들은 헛되이 기다리지 않고 바로 다른 식당으로 간다(Fast Fail). 시간이 지나 불이 꺼졌는지 한 사람만 먼저 들여보내 확인한다(Half-Open).
- **오해**: "Open(열림)이니까 통신이 되는 것 아닌가?" — 전기 회로 용어에서 유래한 이름이라 반대다. 회로가 열리면(Open) 전선이 끊어져 전류가 흐르지 않는다. Closed(닫힘)가 회로가 이어진 정상 통신 상태다.

## 연결 개념
- 042 MSA — 서킷 브레이커가 막는 연쇄 장애는 서비스 간 네트워크 호출이 전제인 MSA 환경에서 발생한다
- 044 API 게이트웨이 — 게이트웨이 단에서도 백엔드별로 서킷 브레이커를 적용할 수 있다
- 046 서비스 메시(Service Mesh) — 서킷 브레이커 로직을 애플리케이션 코드가 아니라 사이드카 프록시(인프라)로 옮긴 것

# 📝 【답안용】 시험 답안 템플릿

> 목적: 시험장에서 25분에 그대로 쓰는 답안 양식. 작성방식(추상표현 금지·수치·도식·문제유형 전환)을 엄격히 지킨다.
> 핵심: 이 시험은 정보를 많이 나열하는 시험이 아니라, 문제 신호어에서 출제자 의도를 읽고 핵심 논점을 선별해 쓰는 시험이다.

## 핵심 인사이트 (3줄 요약)

> 1. **본질**: 분산 시스템(MSA) 환경에서 특정 서비스의 결함이나 타임아웃(Timeout) 지연이 연쇄적으로 상위 호출 서비스로 전파되는 것(Cascading Failure)을 물리적으로 차단(Fast Fail)하는 복원력(Resilience) 디자인 패턴이다.
> 2. **가치**: 장애가 발생한 서비스로의 무의미한 네트워크 I/O 호출을 차단하여, 정상적인 클라이언트 서비스의 스레드 풀(Thread Pool) 고갈과 서버 셧다운(SPOF화)을 원천 방어하고 빠른 복구(Self-healing)를 유도한다.
> 3. **판단 포인트**: Closed -> Open -> Half-Open의 유한 상태 머신(State Machine) 전이 도식을 완벽히 그리고, Open 시 클라이언트에게 디폴트(Default) 값을 반환하는 폴백(Fallback) 방어 기제를 맵핑해야 한다.

## 출제 의도 및 답안 포인트

| 출제 의도 | 반드시 짚을 핵심 | 감점 회피 포인트 |
|:---|:---|:---|
| 서킷 브레이커의 도입 배경 및 아키텍처 연쇄 붕괴 이해 | Timeout 대기로 인한 스레드 고갈 및 도미노(연쇄) 장애 | 단일 모놀리식 서버에서도 이걸 쓴다고 적는 MSA 개념 부재 에러 |
| 핵심 동작 원리 (유한 상태 머신 State Machine) | Closed(정상) / Open(차단) / Half-Open(테스트) 3단계 | Open(차단)을 "정상 개방"으로 착각하여 반대로 설명하는 최악의 단어 혼동 |
| 장애 허용(Fault Tolerance)을 위한 엔드 유저 방어 기법 | Fallback (폴백/대체 응답 반환) 적용 | 차단 후 그냥 HTTP 500 에러를 뿌리고 끝난다고 서술하는 기획 부재 |

> 요약: 서킷 브레이커는 "네가 죽었다고 내가 같이 죽어줄 순 없다"는 꼬리 자르기(디커플링)의 철학이다. 썩은 꼬리(장애 서버)를 즉시 잘라내야 본체(전체 시스템)가 산다.

## Ⅰ. 개요 및 필요성

- 정의: 마이크로서비스 간 통신 실패율(Error Rate)이나 응답 지연(Timeout)이 임계치(Threshold)를 초과할 경우, 대상 서비스로의 요청 프록시(Proxy)를 차단하여 장애 전파를 막는 소프트웨어 회로 차단기 패턴
- 배경: 분산 환경에서는 동기(Sync/REST) 통신 중 타겟 서버가 응답하지 않으면, 호출한(Caller) 서버의 스레드가 무한 대기(Block) 상태에 빠져 결국 전체 시스템 자원이 고갈되는 눈덩이(Snowball) 파국 발생
- 필요성: 타겟 서버의 복구 시간을 벌어주고(부하 경감), 호출자 측은 즉각적인 실패 처리(Fast Fail) 및 폴백(Fallback) 우회 로직을 타게 하여 전체 가용성(Availability) 99.9%를 사수하기 위함

## Ⅱ. 서킷 브레이커 아키텍처와 상태 전이(State Transition) 도식

차단기는 똑똑하다. 터지면 끊고(Open), 시간이 지나면 찔러보고(Half-Open), 고쳐지면 닫아(Closed) 준다.

```text
[ 서킷 브레이커 유한 상태 머신 (State Machine) 워크플로우 ]

            (2. 장애 발생: 에러율 50% 초과! "차단기 내려!") 🚨
        +--------------------------------------------------------+
        |                                                        |
        |                                                        V
[ Closed (닫힘) ] ✅                                      [ Open (열림) ] ❌
(정상 통신: API 호출이 통과됨)                             (차단: 통신 안 함. 즉시 Fallback 에러 반환)
        ^                                                        |
        |                                                        |
        +--------------------------------------------------------+
            (4. 찔러보기 성공! "다시 닫아!") ✅         (3. Timeout 30초 대기 후) ⏳
                                    |                   |
                               [ Half-Open (반열림) ] ⚠️
                             (몇 개만 찔러서 정상 복구됐는지 간보기)
                                     |
                          (찔러봤는데 또 실패! ❌ -> 다시 Open으로 롤백)
```

| 상태 (State) | 네트워크 제어 메커니즘 | 아키텍처적(엔지니어링) 생존 논리 |
|:---|:---|:---|
| **Closed (정상)** | 호출자의 요청이 타겟 서버로 그대로 Bypass 통과됨 | 평화로운 상태. 라이브러리(Resilience4j)가 에러 횟수와 응답 시간(ms)을 백그라운드 슬라이딩 윈도우(Sliding Window)로 계속 카운팅(감시) 중 |
| **Open (차단)** | 임계치 도달 시(예: 10초 내 50% 에러), 네트워크 I/O를 아예 끊어버리고 즉시 Exception 반환 | **Fast-Fail(빠른 실패)**. 안 되는 타겟 서버를 찔러보느라 내 소중한 스레드 풀(Thread Pool)을 1초라도 대기시키지 않음 |
| **Half-Open (간보기)** | 설정된 시간(WaitDuration)이 지나면 프록시가 딱 3번의 요청만 타겟 서버로 흘려보냄 (Test) | 죽었던 타겟 서버(DB)가 재기동할 시간을 벌어주고, 서서히 트래픽을 넣어주며 자가 치유(Self-healing) 여부 검증 |

> 요약: 서킷 브레이커가 없으면 주문 서버가 뻗었을 때, 결제 서버는 "주문 서버야, 살아있니?"를 물어보다가 타임아웃으로 같이 뻗는다. 차단기가 팍! 내려가면 결제 서버는 묻기도 전에 "안 되네" 하고 빠지기 때문에(Fast-Fail) 살아남는다.

## Ⅲ. 극복해야 할 시스템적 리스크 및 방어 기제 튜닝 (Fallback)

사용자는 화면에 "HTTP 500 서버 장애"가 뜨는 순간 앱을 삭제한다. 차단기가 내려가도 우아하게(Graceful) 대응해야 한다.

| 리스크 요인 | 발생 시나리오 및 시스템 붕괴 원인 | 아키텍처 대응 방안 (실무 튜닝) |
|:---|:---|:---|
| **사용자 경험(UX) 파괴** | '추천 상품(AI)' 마이크로서비스 차단기가 Open 상태가 되어, 메인 화면 전체에 시뻘건 에러 트레이스가 찍힘 | **Fallback(폴백) 메서드 구현**: 차단기가 내려갔을 때 예외를 캐치하여, 캐시(Redis)에 저장된 어제 자 추천 데이터를 뿌리거나 기본값(정적 베스트셀러)을 반환하는 대체 로직 바인딩 |
| **스레드 풀 경합 파국 (Bulkhead)** | 차단기가 내려가기 전(임계치 도달 직전)까지의 10초 동안, 결제 스레드 풀 100개가 모두 멈춰버려 사이트가 일시 마비 | **벌크헤드(Bulkhead) 패턴 병행 적용**: 배의 선창 격벽처럼 타겟 서비스별로 스레드 풀(Thread Pool)을 물리적으로 쪼개어, '배송 조회' 스레드가 다 멈춰도 '주문' 스레드에는 영향이 안 가도록 격리 튜닝 |

> 요약: 넷플릭스는 10년 전부터 이 튜닝을 썼다. 리뷰 서버가 뻗어서 차단기가 내려가면, 사용자 화면에는 "리뷰를 불러올 수 없습니다"라는 안내조차 안 뜬다. 그냥 평점(별) 아이콘 자체를 UI에서 조용히 숨겨(Fallback) 버린다.

## Ⅳ. MSA 인프라 진화: 소스코드 내재화에서 서비스 메시(Istio)로 

과거에는 개발자가 자바(Java) 코드로 차단기를 만들었지만, 이제는 인프라스트럭처가 알아서 차단기를 내린다.

| 패러다임 전환 | 물리적 구현 메커니즘 (어떻게 차단하는가) | 해결되는 한계점 (가치) |
|:---|:---|:---|
| **과거 (Library 방식)** <br> (Netflix Hystrix, Resilience4j) | Spring Boot 애플리케이션 소스코드 안에 `@CircuitBreaker` 어노테이션을 박아 넣고 Java로 직접 튜닝 | Python, Node.js 등 타 언어 서비스에는 자바 라이브러리(Hystrix)를 이식할 수 없는 '다언어(Polyglot) 족쇄' 한계 돌파 불가 |
| **현재 (Service Mesh)** <br> (Istio, Envoy) | 애플리케이션 코드는 1줄도 건드리지 않고, 쿠버네티스 포드(Pod) 옆에 붙은 **Envoy 프록시(사이드카)** 네트워크 L7단에서 즉시 회로 차단 (Shift-down) | 개발자는 더 이상 네트워크 장애 처리를 코딩할 필요가 없음(비즈니스 로직 100% 집중). 인프라 팀이 중앙(Control Plane)에서 YAML 파일 하나로 전체 서버의 서킷 임계치 일괄 제어 |

> 요약: 서킷 브레이커는 완벽히 '네트워크 인프라'의 영역이다. 이걸 개발자에게 자바 코드로 짜라고 시켰던 과거가 비정상이었고, 이제는 서비스 메시(Service Mesh)라는 사이드카(Sidecar) 프록시가 차단기 역할을 완전히 빼앗아갔다.

## Ⅴ. 실무 적용 방안 및 결론

**적용 방안 3개:**
1. [Spring Cloud Resilience4j 기반 폴백 방어막 구축] 쇼핑몰 검색 MSA 구축 시, 뒷단의 외부 검색 엔진(Elasticsearch) 서버가 CPU 100%를 치며 지연(Timeout 5초)될 때, 50% 이상 실패 시 서킷을 Open하고 `FallbackMethod`를 태워 RDBMS의 최신 상품 데이터 10건(임시 데이터)을 빠르게 반환하여 구매 전환율 이탈 방어
2. [Istio Outlier Detection (사이드카 차단) 튜닝] 쿠버네티스 클러스터 운영 시, 특정 결제 노드(Pod) 1개가 좀비 상태에 빠져 503 에러를 뿜을 때, 소스코드 수정 없이 Istio `DestinationRule` 얌(YAML)에 `consecutive5xxErrors: 3`을 선언하여 Envoy 프록시가 해당 썩은 파드를 30초(ejectionTime)간 즉시 라우팅 컷아웃(격리)
3. [Prometheus 연동 기반 슬라이딩 윈도우 모니터링] 단순히 차단기를 거는 것을 넘어, 차단기 상태(Closed/Open/Half-Open) 메트릭을 Micrometer로 수집하고 Grafana 대시보드와 Slack 얼럿을 연동시켜 "지금 배송 API 차단기 내려감!" 알람이 울려 인프라 팀(SRE)이 즉각 수동 조치에 투입되도록 관제 자동화

**결론:**
- 기술사 판단: 서킷 브레이커 패턴은 "분산 환경에서는 네트워크를 믿지 마라(Fallacies of Distributed Computing)"는 대명제를 소프트웨어적으로 구현한 최고의 생존술이다. 타겟 서버의 장애를 고치는 기술이 아니라, 그 장애가 내 집(내 서버)으로 불타 번지지 않게 꼬리를 자르는(Decoupling) 무자비한 방화벽이다.
- 향후 방향: 마이크로서비스 갯수가 100개를 돌파하면서 애플리케이션 계층(Hystrix)에서의 서킷 브레이커 패턴은 점차 레거시로 저물고 있으며, 사이드카(Sidecar) 프록시 기반의 서비스 메시(Service Mesh)로 완전히 이관(Shift-down)되는 클라우드 네이티브 아키텍처 정규화가 완료 단계에 접어들었다.
