# 📖 【암기용】 개념 완전 이해

## 한눈에
- **개요**: 전가상화(Full Virtualization)·반가상화(Paravirtualization)·컨테이너(Container)는 물리 자원을 논리적으로 분할해 다수의 독립 실행 환경을 제공하는 **가상화 기법의 3가지 발전 단계**임.
- **왜 필요한가**: 전가상화는 게스트 OS 수정 없이 완전 격리를 제공하지만 에뮬레이션 오버헤드가 크고, 반가상화는 커널 수정으로 오버헤드를 줄이지만 호환성이 제한되며, 컨테이너는 커널 공유로 경량·민첩하지만 격리 수준이 낮음. 워크로드 특성에 맞는 기법 선택이 필요함.
- **핵심 직관**: 전가상화는 H/W 전체를 속여 게스트 OS가 진짜라고 믿게 하는 것, 반가상화는 게스트 OS가 가상 환경임을 인지하고 직접 요청하는 것, 컨테이너는 OS를 공유하고 프로세스만 격리하는 것임.

## 핵심 용어 정리 (내부에 등장하는 것들)

| 용어/표기 | 의미 | 비유·예 |
|:---|:---|:---|
| 가상화 (상위 키워드) | 물리 자원을 논리적으로 추상화해 다수 인스턴스를 구동하는 기술(020 참조) | 1대를 N대처럼 |
| 전가상화 (Full Virtualization) | H/W를 100% 에뮬레이션해 게스트 OS 수정 없이 실행 | 통역사가 모든 대화를 몰래 번역 |
| 반가상화 (Paravirtualization) | 게스트 OS 커널을 수정해 하이퍼바이저에 Hypercall로 직접 요청 | 외국인이 최소 현지어를 배움 |
| 컨테이너 (Container) | 호스트 OS 커널을 공유하며 Namespace·Cgroups로 프로세스를 격리 | 셰어하우스(공용 화장실, 방만 분리) |
| Trap & Emulate | 게스트 OS의 특권 명령을 H/W가 가로채 하이퍼바이저가 대신 실행(020 참조) | 자물쇠를 관리인이 대신 열어줌 |
| Hypercall | 반가상화에서 수정된 게스트 OS가 하이퍼바이저를 직접 호출하는 인터페이스 | 관리인에게 직접 전화 |
| Namespace | 리눅스 커널이 PID·네트워크·파일시스템 등을 프로세스 그룹별로 격리하는 메커니즘 | 방마다 다른 주소·전화번호 |
| Cgroups | 프로세스 그룹별 CPU·메모리·I/O 사용량을 제한하는 커널 기능 | 방마다 전기·수도 사용량 한도 |

## 깊이 이해
- **배경·문제의식**: 020에서 다룬 하이퍼바이저 가상화는 서버 통합에 성공했지만, 게스트 OS를 통째로 올리는 무거움(부팅 수 분, 메모리 수 GB/VM)이 MSA·CI/CD 시대에 병목이 됨. 이를 극복하기 위해 세 가지 기법이 트레이드오프 축(격리성 vs 경량성)에서 각자의 위치를 점유함.
- **작동 원리**:
  - **전가상화**: 게스트 OS가 특권 명령(Ring 0)을 실행하면 H/W가 Trap을 발생시키고, 하이퍼바이저가 가로채 에뮬레이션 후 결과를 반환함. 게스트 OS는 수정 불필요하지만 에뮬레이션마다 CPU 사이클을 소모함(H/W 보조 VT-x 없이 15~30% 오버헤드).
  - **반가상화**: 게스트 OS 커널을 수정해 특권 명령 대신 Hypercall로 하이퍼바이저를 직접 호출함. Trap 과정이 생략되어 I/O 성능이 전가상화 대비 15~20% 향상됨. 단, 게스트 OS 소스 수정이 필요해 Windows 등 독점 OS에는 적용 불가함.
  - **컨테이너**: 호스트 OS의 Namespace로 PID·네트워크·파일시스템을 격리하고, Cgroups로 CPU·메모리 사용량을 제한함. 게스트 OS가 없으므로 부팅 수 초, 이미지 수 MB로 경량임. 단, 호스트 커널을 공유하므로 커널 취약점 시 전체 컨테이너가 침해됨.
- **비유**: 전가상화 = 완전 독립 별장(높은 비용·완전 프라이버시), 반가상화 = 최적화된 조립식 주택(비용 절감·일부 제약), 컨테이너 = 셰어하우스(경제적·공용 시설 의존).
- **구체 예시**: 전가상화 — VMware ESXi, KVM(VT-x 적용), 반가상화 — Xen(PV 모드), AWS Nitro의 virtio 드라이버, 컨테이너 — Docker(containerd), Podman.
- **흔한 오해·주의점**: (1) "컨테이너가 무조건 우수"는 오류 — 보안 격리·이종 OS 지원이 필요한 워크로드에는 VM이 필수임. (2) 현대 환경은 Kata Containers·Firecracker처럼 VM의 격리성 + 컨테이너의 경량성을 결합한 마이크로 VM으로 수렴 중임. (3) 반가상화는 단독보다 virtio 드라이버 형태로 전가상화(KVM) 안에서 I/O 최적화 용도로 활용됨.

## 연결 개념
- (020 가상화·하이퍼바이저) 전가상화·반가상화의 기반 기술인 하이퍼바이저 구조와 Trap & Emulate
- (170 Docker 컨테이너) 컨테이너의 구체적 아키텍처와 이미지·레이어 구조
- (171 VM vs 컨테이너 비교) 격리성·성능·운영 관점의 상세 비교

# 📝 【답안용】 시험 답안 템플릿

## 핵심 인사이트 (3줄 요약)

> 1. **본질**: H/W 에뮬레이션(전가상화) -> 커널 수정(반가상화) -> OS 레벨 격리(컨테이너)로 진화한 컴퓨팅 자원 추상화 기법임.
> 2. **가치**: 전가상화는 이종 OS 호환과 강한 격리, 반가상화는 I/O 성능 최적화, 컨테이너는 초고속 배포와 고집적도를 각각 제공함.
> 3. **판단 포인트**: 보안·격리 요구가 높으면 VM, 배포 민첩성·집적도가 우선이면 컨테이너를 선택하며, 마이크로 VM으로 양쪽을 결합하는 것이 현대 추세임.

## 출제 의도 및 답안 포인트

| 출제 의도 | 반드시 짚을 핵심 | 감점 회피 포인트 |
|:---|:---|:---|
| 3가지 가상화 기법의 기술적 차이 비교 | Trap & Emulate(전), Hypercall(반), Namespace·Cgroups(컨) 메커니즘 | "컨테이너가 무조건 우수"식 이분법적 단정 |
| 워크로드별 적정 기술 선택 기준 제시 | 격리성·호환성·오버헤드·배포 속도의 4축 비교 | 반가상화의 현대적 활용(virtio) 누락 |

> 요약: 각 기법의 제어 메커니즘 차이를 명확히 대비하고, 격리성 vs 경량성 축에서 워크로드별 선택 기준을 제시해야 함.

## Ⅰ. 개요 및 필요성

- 개요: 물리 자원을 논리적으로 분할해 다수 독립 실행 환경을 제공하는 가상화 기법의 3가지 발전 단계임
- 배경: 서버 통합(020 참조)은 달성했으나 게스트 OS 부팅·메모리 오버헤드가 MSA·CI/CD 환경에서 병목이 됨
- 필요성: 워크로드 특성(보안·호환성·배포 속도)에 맞는 가상화 기법 선택으로 자원 효율과 운영 민첩성을 동시에 확보해야 함

---

## Ⅱ. 구조 및 구성요소

```text
[전가상화·반가상화]                 [컨테이너]
H/W -> Hypervisor -> Guest OS    H/W -> Host OS(Kernel) -> Container Engine
                       |                                       |
                       +-> App                                 +-> App (격리 프로세스)

전가상화: Guest OS -> 특권 명령 -> Trap -> Hypervisor 에뮬레이션
반가상화: Guest OS(수정) -> Hypercall -> Hypervisor 직접 처리
컨테이너: App -> System Call -> Host Kernel(Namespace·Cgroups 격리)
```

| 구성요소 | 역할 | 비고 |
|:---|:---|:---|
| Hypervisor (VMM) | H/W 자원을 가상화·분배하고 게스트 OS를 격리 관리 | 전·반가상화 공통, Type 1·2 존재 |
| Guest OS | VM 내에서 구동되는 독립 운영체제 | 반가상화 시 커널 수정 필수 |
| Container Engine | Namespace·Cgroups로 프로세스 레벨 격리 환경 제공 | Docker(containerd), Podman |
| Namespace·Cgroups | 프로세스 그룹별 시스템 자원의 격리(NS)와 제한(CG) | 리눅스 커널 기능 |

> 요약: VM은 하이퍼바이저+게스트 OS로 H/W 레벨 격리를 제공하고, 컨테이너는 호스트 커널+엔진으로 프로세스 레벨 격리를 제공함.

---

## Ⅲ. 동작원리 및 흐름도

```text
애플리케이션 명령 발생 -> 특권 명령 판별
  / 전가상화: H/W Trap -> Hypervisor 에뮬레이션 -> 결과 반환 (오버헤드 대)
  / 반가상화: Guest OS가 Hypercall 발행 -> Hypervisor 직접 처리 (오버헤드 중)
  / 컨테이너: System Call -> Host Kernel 직접 실행(Namespace 격리) (오버헤드 소)
```

1. 명령 발생: 애플리케이션 또는 게스트 OS가 CPU·I/O 제어 명령을 호출함
2. 가상화 계층 개입: 전가상화는 Trap & Emulate, 반가상화는 Hypercall, 컨테이너는 직접 System Call로 분기함
3. H/W 실행: 물리 CPU·메모리에서 권한 검증 후 명령을 수행함
4. 격리 반환: 처리 결과를 요청 환경으로 격리해 반환하고 타 VM·컨테이너에 영향 차단함

> 요약: 전가상화는 에뮬레이션, 반가상화는 Hypercall, 컨테이너는 직접 시스템 콜로 오버헤드가 순차 감소함.

---

## Ⅳ. 특징

- 호환성(전가상화): 게스트 OS 수정 불필요로 Windows 등 독점 OS 구동이 가능함
- I/O 최적화(반가상화): Trap 과정 생략으로 전가상화 대비 I/O 성능 15~20% 향상됨(virtio 드라이버 형태로 KVM 내 활용)
- 초고속 배포(컨테이너): 게스트 OS 부팅 없이 수 초 내 기동, 이미지 수십 MB, 동일 H/W 집적도 VM 대비 3~5배
- 보안 격리 한계(컨테이너): 호스트 커널 공유로 커널 취약점(CVE) 시 전체 컨테이너가 침해 가능(Container Breakout 리스크)

## Ⅴ. 심화 비교 및 적용 판단

| 구분 | 전가상화 | 반가상화 | 컨테이너 | 선택 기준 |
|:---|:---|:---|:---|:---|
| 제어 메커니즘 | Trap & Emulate | Hypercall | Namespace·Cgroups | 동작 원리 차이 |
| 오버헤드 | 15~30%(VT-x 없이) | 5~10% | 1~3%(네이티브 근접) | 성능 요구 수준 |
| OS 종속성 | 수정 불필요 | 커널 수정 필수 | 호스트 커널(Linux) 의존 | 이종 OS 지원 여부 |
| 격리 수준 | H/W 레벨(강함) | H/W 레벨(강함) | 프로세스 레벨(약함) | 멀티테넌트 보안 요구 |
| 부팅 시간 | 수 분 | 수 분 | 수 초 | 배포 속도 요구 |

> 요약: 보안·이종 OS 호환이 필요하면 VM(전가상화), MSA 기반 민첩한 스케일링이 필요하면 컨테이너를 선택하며, 마이크로 VM으로 양쪽을 결합함.

**리스크·대응:**
- 컨테이너 탈출(Container Breakout): 커널 공유로 인한 권한 상승 공격 -> Kata Containers·gVisor 마이크로 VM 샌드박싱 적용 (지표: CVE 스캔 통과율)
- Noisy Neighbor: 특정 컨테이너의 CPU·메모리 독식 -> Cgroups 기반 CPU/Memory Limit 강제, K8s Resource Quota 설정 (지표: 노드 자원 사용률 편차)

**도입 후 점검 지표:**
- 성능: 가상화 오버헤드 비율 — 베어메탈 대비 처리량 손실률(VM: 5% 이내, 컨테이너: 2% 이내)
- 보안: 컨테이너 이미지 취약점 스캔 통과율 — Trivy·Snyk 기준 Critical 0건 유지

## Ⅵ. 실무 적용 및 결론

**적용 방안 3개:**
1. 레거시 리프트 앤 시프트: 온프레미스 모놀리식 앱을 전가상화 IaaS(AWS EC2·VMware)로 1차 전환해 물리 서버 종속성을 제거함
2. 클라우드 네이티브 전환: 신규 서비스는 Docker 이미지로 패키징하고 Kubernetes로 오케스트레이션해 자동 확장·롤링 업데이트 체계를 구축함
3. 마이크로 VM 하이브리드: 보안 민감 워크로드(금융·의료)에 AWS Firecracker(부팅 125ms + VM 격리)를 적용해 컨테이너 속도와 VM 보안을 동시 확보함

**결론:**
- 기술사 판단: 워크로드 특성(보안·호환·배포 속도)에 따라 VM과 컨테이너를 혼합 운용하되, 마이크로 VM으로 격리·경량의 교집합을 확보하는 것이 최적 아키텍처임
- 향후 방향: 컨테이너 보안 약점을 보완하는 마이크로 VM(Kata·Firecracker)과 WebAssembly(Wasm) 기반 초경량 샌드박스가 차세대 격리 모델로 부상 중임
