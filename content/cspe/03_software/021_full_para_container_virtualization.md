# 📖 【암기용】 개념 완전 이해

## 한눈에
- **개요**: 하드웨어 자원을 논리적으로 분할하여 다수의 운영체제나 애플리케이션을 격리 실행하는 기술 발전 단계이다.
- **왜 필요한가**: 물리 서버의 낮은 자원 활용률과 애플리케이션 간 충돌 문제를 해결하고, 배포 민첩성을 높이기 위해 필요하다.
- **핵심 직관**: 하드웨어 전체를 속이면 전가상화, 게스트 OS가 스스로 가상화됨을 알면 반가상화, OS를 공유하고 프로세스만 격리하면 컨테이너다.

## 핵심 용어 정리

| 용어/표기 | 의미 | 비유·예 |
|:---|:---|:---|
| 전가상화 (Full) | 하드웨어를 100% 에뮬레이션하여 게스트 OS를 수정 없이 실행하는 방식 | 통역사가 모든 대화를 몰래 번역해주는 것 |
| 반가상화 (Para) | 게스트 OS를 수정하여 하이퍼바이저와 직접 통신(Hypercall)하게 만드는 방식 | 외국인(게스트 OS)이 최소한의 현지어(Hypercall)를 배운 것 |
| 컨테이너 (Container) | 호스트 OS 커널을 공유하며 프로세스 수준에서 격리하는 가상화 방식 | 한 집에 방만 나누어 화장실(커널)을 같이 쓰는 셰어하우스 |

## 깊이 이해
- **배경·문제의식**: 초기 물리 서버는 "1서버 1애플리케이션" 구조로 낭비가 심했다. 이를 해결하기 위해 하이퍼바이저 기반 가상화(전가상화/반가상화)가 등장했으나, 여전히 무거운 게스트 OS를 띄워야 하는 오버헤드가 발생했다. 이를 극복하기 위해 커널을 공유하는 경량 가상화인 컨테이너가 대두되었다.
- **작동 원리**:
  - **전가상화**: 하이퍼바이저가 CPU, 메모리, I/O 디바이스를 전부 가상화한다. 게스트 OS의 특권 명령(Privileged Instruction)은 하이퍼바이저가 Trap & Emulate 방식으로 가로채어 처리한다.
  - **반가상화**: 게스트 OS 커널을 수정하여, 특권 명령이 필요할 때 직접 하이퍼바이저를 호출(Hypercall)한다. 번역 과정이 생략되어 전가상화보다 I/O 성능이 우수하다.
  - **컨테이너**: 호스트 OS의 Linux Namespace(격리)와 Cgroups(자원 제어)를 이용해 프로세스 그룹을 분리한다. 별도의 게스트 OS가 없어 부팅이 순식간이다.
- **비유**: 전가상화는 "별장(독립된 집)", 반가상화는 "조립식 주택(최적화된 집)", 컨테이너는 "고시원(공용 화장실을 쓰는 좁은 방)".
- **구체 예시**: 전가상화(VMware ESXi), 반가상화(Xen), 컨테이너(Docker, Podman).
- **흔한 오해·주의점**: 컨테이너는 가벼운 대신 호스트 커널을 공유하므로 커널 패닉 발생 시 모든 컨테이너가 동반 다운되는 단일 장애점(SPOF) 위험이 있다.

## 연결 개념
- 하이퍼바이저, 도커(Docker), 쿠버네티스(Kubernetes)

# 📝 【답안용】 시험 답안 템플릿

## 핵심 인사이트 (3줄 요약)

> 1. **본질**: 하드웨어 에뮬레이션(전가상화)에서 커널 수정(반가상화)을 거쳐 OS 레벨 격리(컨테이너)로 진화한 컴퓨팅 자원 추상화 기술.
> 2. **가치**: 자원 활용률 극대화(VM) 및 MSA 기반의 민첩한 애플리케이션 배포(컨테이너) 실현.
> 3. **판단 포인트**: 강력한 보안과 레거시 호환이 필요하면 VM(전가상화), 고집적도와 빠른 스케일링이 필요하면 컨테이너를 선택한다.

## 출제 의도 및 답안 포인트

| 출제 의도 | 반드시 짚을 핵심 | 감점 회피 포인트 |
|:---|:---|:---|
| 가상화 발전 단계와 기술적 차이점 비교 | Trap & Emulate(전), Hypercall(반), Namespace/Cgroup(컨) | "컨테이너가 무조건 좋다"식 단정 |

> 요약: 각 가상화 방식의 핵심 제어 메커니즘 차이와 워크로드에 따른 적정 기술 선택 기준을 제시한다.

---

## Ⅰ. 개요 및 필요성

- 개요: 물리적 하드웨어 자원을 논리적으로 분할하여 다수의 독립된 실행 환경을 제공하는 컴퓨팅 추상화 기술.
- 배경: 기존 물리 서버의 낮은 자원 활용률(평균 10~20%) 극복 및 서비스 배포 속도 향상 요구.
- 필요성: 클라우드 컴퓨팅의 기반 기술로서, 레거시 시스템 마이그레이션 및 MSA 기반 클라우드 네이티브 환경(탄력성 확보) 구현을 위해 필수적임.

---

## Ⅱ. 구조 및 구성요소

```text
[전가상화/반가상화]                    [컨테이너]
하드웨어 -> 하이퍼바이저 -> 게스트 OS  하드웨어 -> 호스트 OS -> 컨테이너 엔진
                             |                               |
                             +-> 애플리케이션                 +-> 애플리케이션 (격리 프로세스)
```

| 구성요소 | 역할 | 특이사항 |
|:---|:---|:---|
| 하이퍼바이저 (VMM) | 하드웨어 자원을 가상화하고 다수의 게스트 OS를 관리·격리 | Type 1(베어메탈), Type 2(호스트형) 존재 |
| Guest OS | VM 내에서 구동되는 독립된 운영체제 | 반가상화 시 커널 수정 필수 (Hypercall) |
| 컨테이너 엔진 | Namespace/Cgroups를 활용해 프로세스 레벨 격리 환경 제공 | Docker daemon, containerd 등 |

> 요약: VM은 하이퍼바이저와 게스트 OS가 필수적이나, 컨테이너는 호스트 OS 위에 컨테이너 엔진만으로 애플리케이션을 구동한다.

---

## Ⅲ. 동작원리 및 흐름도

```text
명령어 발생 -> 특권 명령 판별 -> [가상화 계층 개입] -> 하드웨어 실행 -> 결과 반환
```

- 1단계 [명령어 발생]: 사용자 애플리케이션 또는 게스트 OS에서 CPU/메모리 제어 명령을 호출함.
- 2단계 [가상화 계층 개입]: 
  - (전가상화) 하이퍼바이저가 Trap하여 Emulation 수행.
  - (반가상화) 수정된 게스트 OS가 Hypercall로 하이퍼바이저에 직접 위임.
  - (컨테이너) 시스템 콜(System Call)을 호스트 OS 커널로 직접 전달(Namespace 통제).
- 3단계 [하드웨어 실행]: 물리적 CPU/메모리에서 권한 검증 후 명령어를 실제 수행함.
- 4단계 [결과 반환]: 처리 결과를 요청한 애플리케이션 또는 가상 환경으로 격리하여 반환함.

> 요약: 전가상화는 에뮬레이션 오버헤드가 발생하고, 반가상화는 Hypercall로 오버헤드를 줄이며, 컨테이너는 직접 시스템 콜을 호출해 네이티브에 가까운 성능을 낸다.

---

## Ⅳ. 특징

- 높은 호환성 (전가상화): 게스트 OS 수정이 불필요하여 Windows 등 독점 OS 구동이 용이함.
- I/O 성능 최적화 (반가상화): Trap & Emulate 과정 생략으로 전가상화 대비 I/O 성능이 약 15~20% 향상됨.
- 초고속 배포·집적도 (컨테이너): OS 부팅 과정이 생략되어 초 단위 배포가 가능하며, 동일 하드웨어 내 집적도가 VM 대비 3~5배 높음.
- 보안 격리 한계 (컨테이너): 호스트 커널을 공유하므로 커널 취약점 발생 시 전체 컨테이너가 침해될 위험이 있음.

> 요약: VM 방식은 강한 격리와 호환성을 제공하지만 무겁고, 컨테이너는 가볍고 민첩하지만 커널 공유에 따른 보안 리스크가 존재한다.

---

## Ⅴ. 심화 비교 및 적용 판단

| 비교 축 | 전가상화 (Full) | 반가상화 (Para) | 컨테이너 (Container) | 선택 기준 |
|:---|:---|:---|:---|:---|
| 자원 오버헤드 | 매우 높음 | 중간 | 매우 낮음 (네이티브 근접) | 밀집도 및 배포 속도 요구 수준 |
| OS 종속성 | OS 수정 불필요 | 게스트 커널 수정 필수 | 호스트 커널 (Linux) 의존 | 레거시 OS(Windows 등) 지원 여부 |
| 격리 및 보안 | 하드웨어 레벨의 강한 격리 | 하드웨어 레벨의 강한 격리 | 프로세스 레벨의 논리적 격리 | 보안 민감도 및 멀티테넌트 요건 |

> 요약: 레거시 OS 구동과 강력한 보안이 필요하면 VM을, MSA 기반의 빠른 확장이 필요하면 컨테이너를 선택한다.

**리스크·대응 (컨테이너 도입 시):**
- 보안 취약점 전파: 커널 공유에 따른 컨테이너 탈출(Container Breakout) 위험 → Kata Container, gVisor 등 마이크로VM 기반 샌드박싱 적용 (지표: 취약점 스캔 통과율)
- 자원 경합(Noisy Neighbor): 특정 컨테이너가 자원 독점 → Cgroups 기반 자원(CPU/Memory) 쿼터 및 Limit 엄격 설정 (지표: 노드 자원 사용률)

---

## Ⅵ. 실무 적용 및 결론

**적용 방안 3개:**
1. 레거시 마이그레이션 (VM): 기존 온프레미스의 모놀리식 애플리케이션을 AWS EC2, VMware 등 전가상화 기반 IaaS로 1차 리프트 앤 시프트(Lift & Shift) 전환.
2. 클라우드 네이티브 전환 (컨테이너): 신규 서비스는 도커(Docker) 기반으로 패키징하고 Kubernetes(K8s)로 오케스트레이션하여 자동 확장 체계 구축.
3. 보안 강화 하이브리드 (마이크로VM): 보안 요구사항이 높은 워크로드는 AWS Firecracker와 같은 마이크로VM을 적용해 컨테이너의 속도와 VM의 격리성을 결합.

**결론 (2줄):**
- 기술사 판단: 인프라 현대화는 전가상화(IaaS)를 거쳐 궁극적으로 컨테이너(PaaS/CaaS)로 이행해야 하며, 워크로드 특성에 맞는 혼합형 아키텍처 구성이 핵심임.
- 향후 방향: 컨테이너의 보안 약점을 보완하는 마이크로VM 기술과 WebAssembly(Wasm) 기반 초경량 가상화 기술로 진화할 것임.
