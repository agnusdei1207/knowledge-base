# 📖 【암기용】 개념 완전 이해

> 목적: 전가상화·반가상화·컨테이너를 처음 봐도 완벽히 이해하게 만든다. 시험 답안 양식이 아니라, 이해를 위한 친절한 설명이다.

## 한눈에
- **개요**: 하나의 물리 서버를 여러 실행 환경으로 나누는 격리 기술
- **왜 필요한가**: 서버 1대에 애플리케이션 1개만 올리면 CPU와 메모리 유휴율이 커진다. 가상화는 자원을 나누고, 컨테이너는 배포 단위를 작게 만들어 운영 속도를 높인다.
- **핵심 직관**: 전가상화는 건물 전체를 가짜로 복제하고, 반가상화는 세입자가 관리실 규칙을 알고 움직이며, 컨테이너는 같은 건물 안에서 방만 분리하는 방식이다.

## 깊이 이해
- **배경·문제의식**: x86 서버 통합은 OS 단위 격리가 필요했고, 클라우드는 VM 단위 과금과 이식성을 요구했다. 이후 마이크로서비스는 초 단위 배포와 이미지 표준화를 요구해 컨테이너가 확산됐다.
- **작동 원리**: 전가상화는 Guest OS가 하드웨어를 직접 쓰는 것처럼 보이게 하고 특권 명령을 trap-and-emulate로 처리한다. 반가상화는 Guest OS가 hypercall로 하이퍼바이저에 직접 요청한다. 컨테이너는 Host OS 커널을 공유하고 namespace와 cgroup으로 프로세스·네트워크·자원 사용량을 분리한다.
- **비유**: 전가상화는 각 세대에 별도 수도·전기 계량기를 둔 독립 주택, 컨테이너는 한 건물 안에서 출입문·방·전기 사용량만 분리한 기숙사에 가깝다.
- **구체 예시**: KVM VM은 게스트 커널까지 포함해 수 GB 이미지와 30~90초 부팅 시간이 필요할 수 있으나, Docker 컨테이너는 수백 MB 이미지와 1~3초 기동으로 API 서버를 늘린다.
- **흔한 오해·주의점**: 컨테이너는 VM이 아니다. 커널을 공유하므로 커널 취약점과 권한 상승을 seccomp, AppArmor, SELinux, rootless mode로 통제해야 한다.

## 연결 개념
- 하이퍼바이저 Type 1/Type 2 — VM 실행 계층 구분
- namespace/cgroup — 컨테이너 격리와 자원 제한의 기반
- Kubernetes — 컨테이너 배포·스케줄링·복구 자동화 계층

# 📝 【답안용】 시험 답안 템플릿

> 목적: 시험장에서 25분에 그대로 쓰는 답안 양식. 작성방식(추상표현 금지·수치·도식·문제유형 전환)을 엄격히 지킨다.
> 핵심: 세 기술을 이름으로 나열하지 않고, 격리 경계·커널 공유 여부·오버헤드·운영 위험을 비교해 선택 기준을 제시한다.

## 핵심 인사이트 (3줄 요약)

> 1. **본질**: 전가상화·반가상화·컨테이너는 물리 자원을 논리 실행 환경으로 분할하는 격리 기술이다.
> 2. **가치**: VM은 OS 단위 격리와 이기종 OS 실행, 컨테이너는 이미지 기반 배포와 초 단위 확장에 가치가 있다.
> 3. **판단 포인트**: 선택 기준은 커널 공유 여부, trap/hypercall 처리 비용, namespace/cgroup 격리 수준, 보안 경계 요구사항이다.

## 출제 의도 및 답안 포인트

| 출제 의도 | 반드시 짚을 핵심 | 감점 회피 포인트 |
|:---|:---|:---|
| 가상화 방식 비교 역량 확인 | trap-and-emulate, hypercall, namespace/cgroup | 전가상화와 컨테이너를 같은 OS 가상화로 설명 |
| 클라우드 실행 단위 선택 확인 | VM 격리, 컨테이너 밀도, 이미지 배포, 오버헤드 | 컨테이너의 커널 공유 위험 누락 |
| 운영 설계 판단 확인 | CPU steal time, memory limit, seccomp, RBAC | 기술명만 쓰고 적용 조건·지표 미제시 |

> 요약: 이 문제는 격리 경계와 운영 비용을 기준으로 VM·반가상화·컨테이너를 선택하는 판단력을 요구한다.

---

## Ⅰ. 개요 및 필요성

가상화는 물리 자원을 논리 실행 환경으로 분할하는 기술이다. 서버 통합, 클라우드 과금, 개발·운영 환경 일치를 위해 필요하다. 전가상화는 Guest OS를 수정하지 않고 실행하고, 반가상화는 hypercall로 오버헤드를 줄이며, 컨테이너는 Host 커널 공유로 배포 단위를 경량화한다.

---

## Ⅱ. 구조 및 구성요소

```text
Physical Server -> Hypervisor / Host Kernel -> VM or Container Runtime -> Workload
  / Full Virtualization: Guest OS -> trap-and-emulate -> Virtual HW
  / Para Virtualization: Modified Guest -> hypercall -> Hypervisor
  / Container: Process -> namespace/cgroup -> Host Kernel
```

| 구성요소 | 역할 | 특이사항 |
|:---|:---|:---|
| Hypervisor | CPU·메모리·I/O 가상 자원 제공 | KVM, Xen, VMware ESXi |
| Guest OS | VM 내부 커널·드라이버 실행 | OS 단위 격리, 이미지 수 GB |
| Container Runtime | 컨테이너 생성·격리·이미지 실행 | containerd, CRI-O, Docker |
| namespace/cgroup | 프로세스 공간·자원 사용량 분리 | PID, NET, IPC, mount, CPU quota |

> 요약: VM은 하이퍼바이저가 가상 하드웨어를 제공하고, 컨테이너는 Host 커널 위에서 프로세스 격리와 자원 제한을 수행한다.

---

## Ⅲ. 동작원리 및 흐름도

```text
Workload 요구 -> 실행 방식 선택 -> 특권 명령 처리 / 커널 호출
  -> 자원 할당 -> 격리 정책 적용 -> 모니터링 지표 수집
```

| 단계 | 처리 내용 | 검증 기준 |
|:---:|:---|:---|
| 1 | 워크로드 OS·격리 요구사항 식별 | Linux/Windows, 규제 분리 |
| 2 | 전가상화는 특권 명령 trap 후 에뮬레이션 | VM exit count, CPU steal time |
| 3 | 반가상화는 Guest가 hypercall 직접 호출 | virtio 처리량, context switch |
| 4 | 컨테이너는 namespace/cgroup 정책 적용 | CPU limit, memory OOM kill |
| 5 | 로그·메트릭 기반 용량 조정 | p95 지연, node utilization |

> 요약: 실행 방식별 차이는 특권 명령을 하이퍼바이저가 가로채는지, Guest가 직접 요청하는지, Host 커널을 공유하는지에 있다.

---

## Ⅳ. 특징

| 구분 | 기존/대안 | 본 기술 | 수치·판단 포인트 |
|:---|:---|:---|:---|
| 격리 | 물리 서버 분리 | VM은 OS 경계, 컨테이너는 프로세스 경계 | 보안 등급별 분리 기준 |
| 기동 | 베어메탈 수동 배포 | VM 30~90초, 컨테이너 1~3초 | 오토스케일 반응 시간 |
| 오버헤드 | 전용 자원 고정 | VM은 Guest OS 비용, 컨테이너는 커널 공유 | CPU steal 5% 이하 목표 |
| 이식성 | 서버별 환경 차이 | OCI 이미지, VM 이미지 | 이미지 서명·SBOM 적용 |

> 요약: VM은 격리 경계가 명확하고, 컨테이너는 배포 밀도와 기동 시간이 운영 판단의 중심이다.

## Ⅴ. 심화 비교 및 적용 판단

| 비교 축 | 기존/대안 | 본 키워드 | 선택 기준 |
|:---|:---|:---|:---|
| 구조 | 물리 서버 단독 배치 | VM·컨테이너 혼합 | OS 격리 필요 시 VM, 동일 커널 앱은 컨테이너 |
| 비용/성능 | 서버별 평균 CPU 10~20% | 통합 후 CPU 50~70% 목표 | 라이선스·노드 밀도·SLA 동시 판단 |
| 운영/위험 | 수동 패치·배포 | 이미지·스냅샷·오케스트레이션 | 취약 이미지 차단, 롤백 시간 5분 이하 |

> 요약: OS 격리와 규제 분리가 우선이면 VM, 배포 빈도와 밀도가 우선이면 컨테이너를 선택한다.

| 리스크 | 원인 | 대응 방안 | 확인 지표 |
|:---|:---|:---|:---|
| VM escape | 하이퍼바이저 취약점 | 패치 SLA 7일, vTPM, 보안 그룹 | CVE 미조치 0건 |
| 컨테이너 탈출 | 커널 공유·권한 과다 | rootless, seccomp, readOnlyRootFilesystem | privileged pod 0개 |
| 자원 고갈 | cgroup limit 누락 | request/limit, quota, eviction policy | OOMKill 월 3건 이하 |

> 요약: 가상화 위험은 격리 경계 침해와 자원 고갈이므로 패치·권한·쿼터 지표로 통제한다.

| 점검 항목 | 목표 기준 | 측정 방법 |
|:---|:---|:---|
| 성능/자원 | CPU steal 5% 이하, node CPU 50~70% | hypervisor metric, Prometheus |
| 품질/배포 | 컨테이너 기동 3초 이하, 롤백 5분 이하 | CI/CD 로그, kube event |
| 운영/보안 | 취약 이미지 차단율 100%, 감사로그 180일 | Trivy, admission controller |

> 요약: 도입 후에는 자원 사용률, 기동 시간, 취약 이미지 차단율로 실행 단위 선택의 타당성을 검증한다.

## Ⅵ. 실무 적용 및 결론

**적용 방안 3개 (필수 — 단계별 또는 항목별):**
1. 규제·OS 분리 워크로드는 KVM 기반 VM으로 배치하고 vTPM, 보안 그룹, 스냅샷 주기 24시간을 적용한다.
2. API·배치 워크로드는 Kubernetes 컨테이너로 배치하고 CPU request 500m, memory limit 512Mi 같은 쿼터를 선언한다.
3. 공통 보안 기준은 이미지 서명, SBOM, admission policy, 런타임 감사로그 180일 보관으로 통일한다.

**결론 (2줄):**
- 기술사 판단: OS 경계와 규제 분리가 조건이면 VM, 배포 빈도와 노드 밀도가 조건이면 컨테이너, I/O 오버헤드가 조건이면 반가상화 드라이버를 선택한다.
- 향후 방향: VM과 컨테이너는 Kata Containers, Firecracker 같은 경량 VM으로 수렴하며 격리와 기동 시간의 균형을 맞춘다.
