# 📖 【암기용】 개념 완전 이해

> 목적: AI 기반 로그 분석을 처음 봐도 이해하게 만든다. 시험 답안 양식이 아니라, 이해를 위한 설명이다.

## 한눈에
- **개요**: AI 기반 로그 분석은 **관측성(Observability)**의 세 축인 로그·메트릭·트레이스를 AI로 **상관분석(Correlation)**해 이상 징후와 원인 후보를 찾아내는 **AIOps** 기술이다.
- **왜 필요한가**: MSA·클라우드 환경에서는 서비스 하나가 수십~수백 개 컴포넌트로 쪼개져, 로그가 초당 수천 건씩 쏟아진다. 사람이 눈으로 검색해서 원인을 찾기엔 데이터량이 이미 넘어섰다.
- **핵심 직관**: CCTV 화면 수백 대를 사람이 다 보는 대신, AI가 평소와 다른 움직임이 찍힌 화면만 먼저 골라 보여주는 방식이다.

## 핵심 용어 정리 (내부에 등장하는 것들)

| 용어 | 의미 | 비유 |
|:---|:---|:---|
| 관측성(Observability) | 로그·메트릭·트레이스 세 신호만으로 시스템 내부 상태를 외부에서 추론하는 능력 — AI 로그 분석이 다루는 **대상** | 계기판의 속도·온도·연료 게이지로 차 상태를 아는 것 |
| AIOps | 운영(Ops) 데이터에 AI/ML을 적용해 이상탐지·상관분석·대응까지 자동화하는 체계 — AI 로그 분석이 속한 **상위 분야** | 관제센터에 AI 당직자를 추가 배치 |
| 로그(Log) | 특정 시점에 무슨 일이 있었는지 남긴 텍스트 기록(에러 메시지, 상태 코드) | 근무 일지 |
| 메트릭(Metric) | 일정 주기로 수치를 집계한 시계열 값(CPU 사용률, 지연시간, 오류율) | 계기판 눈금 |
| 트레이스(Trace) | 요청 하나가 여러 서비스를 거치는 호출 경로 전체 기록 | 택배 송장의 배송 경로 추적 |
| 이상탐지(Anomaly Detection) | 평소 패턴에서 벗어난 값을 통계·모델로 찾아내는 절차 | 평소와 다른 심박수에 울리는 경보 |
| 상관분석(Correlation) | 시간·서비스 의존관계로 흩어진 이벤트를 하나로 묶어 관련성을 찾는 절차 | 여러 목격자 진술을 시간순으로 맞춰보는 것 |
| RCA(Root Cause Analysis) | 상관된 이벤트 중 근본 원인 후보를 좁혀가는 절차 | 여러 용의자 중 진범을 좁혀가는 수사 |
| MTTD / MTTR | 장애를 탐지하기까지 걸리는 시간 / 복구까지 걸리는 시간 | 화재 감지 시간 / 진화 시간 |
| False Positive / Negative | 정상을 이상으로 잘못 판단(오탐) / 이상을 정상으로 놓침(미탐) | 도둑 없는데 경보가 울림 / 도둑이 있는데 경보가 안 울림 |
| Runbook | 특정 장애 유형에 대해 미리 정한 대응 절차(자동·반자동 실행 가능) | 화재 시 행동 요령이 적힌 대피 매뉴얼 |

## 깊이 이해

### 왜 필요했나 — 로그량이 사람 검토 한계를 넘었다
- 서비스가 50개인 MSA에서 서비스당 초당 100건씩만 로그를 남겨도 초당 5,000건, 하루로 환산하면 약 4억 3천만 건이다. 이 규모에서 키워드 검색(`grep`, ELK 쿼리)으로 원인을 찾으려면 어느 로그를 볼지부터 사람이 골라야 하는데, 장애 상황에서는 그 판단 자체가 늦어진다.
- 게다가 장애가 나면 여러 컴포넌트에서 동시에 알람이 튄다. 실제 원인은 하나인데 연쇄적으로 알람이 쏟아지는 "알람 폭풍(Alert Storm)"이 생기고, 이 중 상당수는 근본 원인 하나에서 파생된 중복 신호다.

### 작동 원리 — 수집부터 원인 후보까지
- 1단계 수집: OpenTelemetry, Fluent Bit 같은 수집기가 로그·메트릭·트레이스를 모은다.
- 2단계 정규화: 비정형 텍스트에서 서비스명, 시간, 상태 코드 같은 필드를 추출해 형식을 통일한다. 이 단계 품질이 나쁘면(예: 파싱 성공률 95% 미만) 뒤 단계 분석 정확도가 함께 떨어진다.
- 3단계 이상탐지: 정규화된 데이터를 임베딩하거나 시계열 모델(이동평균·계절성 분해 등)에 넣어 평소 패턴에서 벗어난 시점을 찾는다.
- 4단계 상관분석·RCA: 탐지된 이상 이벤트를 배포 이력, 서비스 의존관계, 트레이스 경로로 묶어 "무엇이 먼저 이상해졌는가"를 추정해 원인 후보를 제시한다.

### 구체 수치로 보는 알람 압축 효과
- 예: 서비스 50개, 하루 알람 500건이 발생하는 조직에서, 이 중 70%(350건)가 사실 배포 1건에서 파생된 연쇄 알람이라고 하자. 규칙 기반 시스템은 500건을 그대로 담당자에게 던지지만, AI 상관분석은 배포 이벤트·서비스 의존관계·시간 근접성을 기준으로 이를 5~10개의 "사건 클러스터"로 묶는다. 담당자가 검토할 단위가 500건에서 10건 이하로, 최대 50배 줄어드는 셈이다.
- 이 압축 덕분에 MTTD가 사람이 알람을 하나씩 열어보던 방식의 10분 안팎에서, 자동 상관분석 적용 후 1분 이내로 단축되는 것이 목표치로 흔히 제시된다.

### 판별 원리 — 언제 규칙 기반, 언제 AI 상관분석인가
- 장애 패턴이 이미 알려져 있고 조건이 명확하면(예: "CPU 90% 초과 시 알람") 규칙 기반 임계치만으로 충분하다.
- 서비스 수가 많아 의존관계가 복잡하거나, 처음 보는 장애 패턴을 잡아야 하면 규칙을 일일이 정의할 수 없다 — 이 경우가 AI 기반 이상탐지·상관분석이 필요한 지점이다.
- 판별 기준 수치 예: 서비스 50개 이상, 하루 알람 500건 이상이면 AI 상관분석 도입을 검토할 규모로 본다.

### 비유와 흔한 오해
- **비유**: 관제센터에서 신고 전화, CCTV, 출입 기록을 시간순으로 맞춰 사건 경로를 재구성하는 것과 같다. 하나의 증거만 보고 결론 내리지 않는다.
- **구체 예시**: 배포 5분 후 p95 지연이 80ms에서 420ms로 급증하고 `DB connection timeout` 로그가 특정 서비스에 집중되면, AI는 "최근 배포"와 "DB 커넥션 풀 설정"을 원인 후보로 제시한다. 이 후보가 곧 확정 원인은 아니다.
- **오해**: AI 로그 분석은 원인을 "확정"하지 않는다. 원인 후보를 좁혀줄 뿐이며, 실제 조치 전에는 변경 이력과 대시보드로 검증해야 한다. 이를 확정으로 오인해 자동으로 위험한 복구 작업(재시작, 롤백)을 실행하면 2차 장애로 이어질 수 있다.

## 연결 개념
- Observability - 로그·메트릭·트레이스 통합 관측 (AI 로그 분석이 다루는 데이터 기반)
- AIOps - AI 기반 운영 자동화와 이벤트 상관분석 (AI 로그 분석이 속한 상위 분야)
- SRE - SLO, Error Budget, MTTR 기반 운영 판단 (AI 로그 분석 결과를 실제 운영 판단에 쓰는 조직 체계)

# 📝 【답안용】 시험 답안 템플릿

> 목적: 시험장에서 25분에 그대로 쓰는 답안 양식. 작성방식(추상표현 금지·수치·도식·문제유형 전환)을 엄격히 지킨다.
> 핵심: AI 로그 분석은 로그 검색 도구가 아니라 장애 탐지, 상관분석, 원인 후보 제시, 대응 자동화를 연결한 운영 체계이다.

## 핵심 인사이트 (3줄 요약)

> 1. **본질**: AI 기반 로그 분석은 대규모 로그·메트릭·트레이스 데이터를 학습해 이상 징후와 원인 후보를 도출하는 AIOps 기술이다.
> 2. **가치**: 장애 탐지 시간을 10분에서 1분 수준으로 줄이고 MTTR, 알람 중복률, 미탐률을 관리 대상으로 만든다.
> 3. **판단 포인트**: 데이터 정규화, 상관분석 정확도, false positive, 대응 자동화 범위를 기준으로 설계해야 한다.

## 출제 의도 및 답안 포인트

| 출제 의도 | 반드시 짚을 핵심 | 감점 회피 포인트 |

> 요약: 이 문제는 AI 모델보다 관측 데이터 흐름과 장애 대응 지표를 중심으로 답해야 한다.

## Ⅰ. 개요 및 필요성

- 개요: AI 기반 로그 분석은 로그로 장애 징후와 원인 후보를 찾는 기술이다.
- 배경: 클라우드·MSA 환경은 로그 양과 의존 관계가 커져 수동 검색으로 장애 원인을 추적하기 어렵다.
- 필요성: 로그·메트릭·트레이스를 통합 분석해 MTTD와 MTTR을 관리해야 한다.

---

## Ⅱ. 구조 및 구성요소

```text
App/Infra Logs -> Collector -> Parser/Normalizer -> Feature/Embedding
               -> Anomaly Detection -> Correlation/RCA -> Alert/Runbook
```

| 구성요소 | 역할 | 특이사항 |
|:---|:---|:---|
| 수집기 | 로그, 메트릭, 트레이스, 이벤트 수집 | OpenTelemetry, Fluent Bit |
| 정규화 계층 | 필드 추출, 시간 동기화, 서비스 태그 부여 | 스키마 불일치 통제 |
| AI 분석 모델 | 이상 탐지, 군집화, 원인 후보 도출 | false positive 관리 필요 |
| 대응 연계 | 알림, 티켓, Runbook, 자동 조치 | 위험 작업은 승인 절차 필요 |

> 요약: AI 로그 분석은 수집·정규화·분석·대응 연계가 이어질 때 운영 가치가 생긴다.

---

## Ⅲ. 동작원리 및 흐름도

```text
로그 수집 -> 파싱/정규화 -> 기준 패턴 학습 -> 이상 탐지
-> 이벤트 상관분석 -> 원인 후보 제시 -> 알림/Runbook 실행
```

| 단계 | 처리 내용 | 검증 기준 |
|:---:|:---|:---|
| 1 | 로그·메트릭·트레이스 수집 | 수집 누락률 1% 이하 |
| 2 | 파싱과 서비스 태깅 | 파싱 성공률 95% 이상 |
| 3 | 이상 패턴 탐지 | false positive 10% 이하 |
| 4 | RCA와 대응 연계 | MTTR 30분 이하 목표 |

> 요약: 데이터 품질이 낮으면 AI 모델보다 파싱 오류가 장애 분석 실패 원인이 된다.

## Ⅳ. 특징

| 구분 | 규칙 기반 로그 분석 | AI 기반 로그 분석 | 판단 포인트 |
|:---|:---|:---|:---|
| 탐지 방식 | 키워드·임계치 | 패턴 변화·군집·이상치 | 미탐률, 오탐률 |
| 원인 분석 | 운영자 수동 검색 | 이벤트 상관분석 | RCA 후보 정확도 |
| 적용 범위 | 알려진 장애 | 신규 패턴 탐지 가능 | 학습 데이터 기간 |
| 한계 | 규칙 유지 부담 | 설명 가능성·데이터 편향 | 모델 근거 로그 제공 |

> 요약: AI 기반 방식은 신규 패턴 탐지에 유리하지만, 근거 로그와 오탐 통제가 함께 필요하다.

## Ⅴ. 심화 비교 및 적용 판단

| 비교 축 | 기존/대안 | 본 키워드 | 선택 기준 |
|:---|:---|:---|:---|
| 구조 | ELK 검색 중심 | Observability+AIOps | 서비스 50개 이상, 알람 1일 500건 이상 |
| 비용/성능 | 사람이 대시보드 확인 | AI 상관분석 자동화 | MTTD 1분, MTTR 30분 목표 |
| 운영/위험 | 규칙 투명 | 모델 오탐 가능 | 설명 로그와 승인형 조치 |

> 요약: 알람 규모와 장애 복잡도가 커질수록 AI 상관분석 도입 근거가 커진다.

| 리스크 | 원인 | 대응 방안 | 확인 지표 |
|:---|:---|:---|:---|
| 오탐 과다 | 계절성·배포 이벤트 미반영 | 배포 캘린더, SLO 컨텍스트 입력 | false positive 10% 이하 |
| 미탐 | 로그 누락·샘플링 과다 | 핵심 경로 100% 수집 | missed incident 건수 |
| 자동 조치 사고 | 원인 후보를 확정으로 오인 | 승인형 Runbook, rollback 기준 | 자동 조치 실패율 |

> 요약: AI 로그 분석은 오탐·미탐·자동 조치 사고를 운영 지표로 통제해야 한다.

| 점검 항목 | 목표 기준 | 측정 방법 |
|:---|:---|:---|
| 탐지 | MTTD 1분 이하 | 장애 타임라인 |
| 복구 | MTTR 30분 이하 | Incident 리뷰 |
| 데이터 품질 | 파싱 성공률 95% 이상 | 로그 파이프라인 리포트 |

> 요약: 탐지 시간, 복구 시간, 데이터 품질이 AI 로그 분석의 핵심 점검 축이다.

## Ⅵ. 실무 적용 및 결론

**적용 방안 3개 (필수 - 단계별 또는 항목별):**
1. 수집 표준화: OpenTelemetry Trace ID, 서비스명, 배포 버전, 사용자 영향 필드를 로그 표준으로 지정
2. 분석 운영: 기준 패턴 30일 학습, 배포 이벤트 제외 처리, false positive 티켓을 주 단위 재학습 데이터로 반영
3. 대응 연계: p95 지연 300ms 초과와 오류율 5% 초과 시 Runbook 제안, DB 재시작 등 위험 작업은 승인형으로 제한

**결론 (2줄):**
- 기술사 판단: 단일 시스템은 규칙 기반 로그 분석, MSA·클라우드 대규모 운영은 AI 상관분석을 결합함
- 향후 방향: AI 로그 분석은 Observability, SRE, 자동 Runbook을 연결한 AIOps 운영 체계로 발전함

### 🔀 문제 유형별 목차 전환 (이 키워드 출제 시)

|:---|:---|:---|:---|
| 포괄형 | "설명하시오", "기술하시오" | 수집-정규화-탐지-RCA 흐름 | 규칙 기반과 AI 기반 차이 |
| 요구사항 명시형 | "운영 방안을 제시하시오", "설계하시오" | SLO 기반 알림과 Runbook | MTTD·MTTR·오탐 통제 |
