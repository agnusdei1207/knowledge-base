# 📖 【암기용】 개념 완전 이해

> 목적: Neo4j 그래프 DB를 처음 봐도 완벽히 이해하게 만든다. 시험 답안 양식이 아니라, 이해를 위한 친절한 설명이다.

## 한눈에
- **개요**: Neo4j는 노드와 관계를 데이터베이스 안에 직접 저장하고 탐색하는 **그래프 데이터베이스**로, 데이터 모델은 노드·관계·속성으로 구성되는 **속성 그래프(Property Graph)** 방식이다.
- **왜 필요한가**: 추천, 사기 탐지, 지식 그래프, 영향도 분석은 데이터 자체보다 "무엇이 무엇과 연결됐는가"가 핵심이다. RDB는 이 연결을 외래키·조인으로 매번 다시 계산해야 하고, 연결 단계(hop)가 늘수록 조인 수가 곱으로 늘어난다. 그래프 DB는 연결 자체를 미리 저장해 이 비용을 없앤다.
- **핵심 직관**: 사람 명단 표를 놓고 조건에 맞는 사람을 매번 찾는 게 아니라, 사람 사이 친구선이 이미 그려진 관계망 지도를 손에 들고 선을 따라가는 방식이다.

## 핵심 용어 정리
| 용어 | 의미 | 비유 |
|:---|:---|:---|
| 속성 그래프(Property Graph) 모델 | 노드·관계·속성으로 데이터를 표현하는 그래프 데이터 모델 — Neo4j가 속하는 상위 분류 | 지도(노드=지점, 관계=도로) |
| Node(노드) | 사람·상품·계좌 등 개체를 표현하는 그래프의 점 | 지도 위의 지점 |
| Relationship(관계, 엣지) | 두 노드를 잇는 방향성 있는 연결, 자체 타입·속성을 가짐 | 지점 사이를 잇는 도로(일방통행 표시 포함) |
| Label(라벨) | 노드를 분류하는 태그(예: `Person`, `Account`) | 명찰 |
| Property(속성) | 노드·관계에 붙은 key-value 데이터(예: `name="Kim"`) | 명찰에 적힌 세부 정보 |
| Cypher | 패턴 매칭 기반 그래프 질의 언어(`MATCH`-`WHERE`-`RETURN`) | "이런 모양으로 연결된 걸 찾아줘"라고 그림으로 묻기 |
| Index-free Adjacency | 각 노드가 자신과 연결된 관계를 포인터로 직접 들고 있어, 이웃 조회가 전체 데이터 크기와 무관해지는 저장 구조 | 전화번호부를 뒤지지 않고 내 명함첩만 보면 됨 |
| Traversal(순회) | 시작 노드에서 관계를 따라 이웃 노드로 이동하며 탐색하는 과정 | 지도 따라 한 정거장씩 이동 |
| hop | 관계를 한 번 건너는 단위(1-hop=직접 연결, 2-hop=친구의 친구) | 징검다리 한 칸 |
| 차수(Degree) | 한 노드에 연결된 관계의 개수 | 한 사람의 친구 수 |
| 최단경로(Shortest Path) | 두 노드 사이 hop 수가 가장 적은 경로를 찾는 알고리즘 | 내비게이션 최단 길찾기 |
| 중심성(Centrality) | 그래프에서 얼마나 중요한/영향력 있는 노드인지 수치화하는 지표군 | 교통 요지 정도 |
| 커뮤니티 탐지(Community Detection) | 서로 밀접하게 연결된 노드 묶음을 찾아내는 알고리즘 | 친한 무리 찾기 |

## 깊이 이해

### 배경 — RDB 조인이 왜 느려지는가 (수치로 이해)
- RDB에서 "친구의 친구의 친구"(3-hop) 관계를 찾으려면 같은 테이블을 자기 자신과 3번 조인(self-join)해야 한다. 평균 친구가 50명인 사람 100만 명 규모에서 3-hop 후보 수는 최대 50×50×50=125,000명까지 늘고, 조인마다 인덱스 탐색·정렬·중복 제거 비용이 추가된다. 게다가 "몇 hop인지 모르는 가변 길이 경로" 질의는 SQL 조인으로는 표현조차 까다롭다.

### Index-free Adjacency — 판별 원리를 Big-O로 이해
- RDB의 조인 비용은 일반적으로 참여 행 수와 인덱스 크기(즉 전체 테이블 크기)에 비례해 커진다.
- Neo4j는 각 노드가 자신에게 연결된 관계의 포인터를 직접 갖고 있으므로, 한 노드에서 다음 노드로 이동하는 비용은 그 노드의 **차수(degree)** 에만 좌우되고 전체 그래프 크기 N과는 무관하다 — 이것이 "index-free adjacency"의 핵심 판별 원리다.
- 예: 노드 1억 개짜리 그래프에서 평균 차수 50인 노드를 3-hop 탐색해도, 방문 규모는 그래프가 1억이든 10억이든 대략 50×50×50=125,000 수준으로 유지된다. RDB라면 테이블 크기가 커질수록 조인 비용도 함께 커지는 것과 대비된다.

### Cypher 패턴 매칭 — 실제 질의 예
```
MATCH (a:Person {name:"Kim"})-[:FOLLOWS]->(b)-[:FOLLOWS]->(c)
RETURN c.name
```
- 이 질의는 "Kim이 팔로우하는 사람(b)이 팔로우하는 사람(c)"을 찾는다 — 즉 2-hop 관계다. `MATCH` 절이 그래프 모양(패턴) 자체를 그림처럼 표현하는 것이 SQL과의 가장 큰 차이다.

### 사기 탐지 워크드 예제 (수치로 이해)
- 카드, 단말(device), IP, 계정을 각각 노드로 두고, 결제·로그인마다 이들 사이에 관계를 만든다.
- 질의: 특정 단말 노드에서 2-hop 이내에 서로 다른 카드가 5개 이상 연결돼 있으면 의심 거래로 분류한다(정상적으로는 한 단말에 카드 1~2개가 보통이다). 이 패턴은 카드 테이블·단말 테이블을 여러 번 조인하는 RDB 질의보다, `MATCH (d:Device)<-[:USED_ON]-(c:Card) WHERE size(...) >= 5` 형태의 그래프 패턴 질의로 표현·실행하는 쪽이 자연스럽고 빠르다.

### 고차수 노드(Super Node) 문제
- 팔로워가 100만 명인 유명 계정처럼 차수가 극단적으로 큰 노드에서 hop 제한 없이 순회하면, 방문 노드 수가 폭발적으로 늘어 질의가 멈추지 않을 수 있다.
- 그래서 실무 Cypher에는 항상 `hop 상한(예: 2~3)`과 `LIMIT`을 명시한다. 이는 "질의 지연을 통제하는" 핵심 설계 원칙이며, hop 제한이 없는 질의는 실행계획(PROFILE)에서 반드시 걸러야 한다.

### 비유 정리
- 지하철 역 이름 목록만 보고 경로를 짜는 게 아니라, 환승선까지 다 그려진 노선도를 손에 들고 선을 따라 목적지까지 가는 것과 같다 — 관계(선)가 이미 지도에 그려져 있어 매번 "이 역과 저 역이 연결됐는지"를 다시 계산할 필요가 없다.

### 흔한 오해
- 그래프 DB가 모든 질의에 유리한 것은 아니다. 단순 집계(예: 전체 매출 합계)나 대량 순차 스캔은 컬럼형 분석 DB가 더 적합하다. 그래프 DB는 "연결 탐색"이 질의의 중심일 때, 즉 hop 수가 정해지지 않은 경로·패턴 질의에서 강점을 가진다.

## 연결 개념
- 속성 그래프(Property Graph) 모델 — Neo4j가 구현하는 상위 데이터 모델.
- Cypher — Neo4j의 패턴 매칭 질의 언어.
- 지식 그래프(Knowledge Graph) — 엔티티와 관계로 의미망을 구성하는 응용 형태.
- RDB 조인 — 3-hop 이상·가변 길이 경로 탐색에서 Neo4j와 비용 구조가 근본적으로 다른 대안(§배경 참조).

## Ⅰ. 개요 및 필요성

- 개요: Neo4j는 그래프 데이터베이스이다.
- 배경: 복잡한 관계 탐색이 많은 업무에서는 조인 기반 질의가 길어지고 경로 분석 비용이 증가한다.
- 필요성: 노드와 관계를 직접 저장해 Cypher 패턴 매칭과 경로 탐색을 수행한다.

---

## Ⅱ. 구조 및 구성요소

```text
Domain Entity -> Node(Label, Property) -> Relationship(Type, Direction, Property) -> Graph Pattern
Query -> Index Seek -> Traversal -> Path/Score Result
```

| 구성요소 | 역할 | 특이사항 |
|:---|:---|:---|
| Node | 사람·계정·상품 등 엔티티 표현 | label, property 보유 |
| Relationship | 엔티티 간 관계 표현 | 방향, 타입, 속성 보유 |
| Cypher | 패턴 매칭 질의 | MATCH, WHERE, RETURN |
| Graph Algorithm | 중심성·커뮤니티·경로 계산 | hop 제한과 비용 관리 |

> 요약: Neo4j는 노드와 관계를 저장하고 Cypher 패턴으로 관계 경로를 탐색함.

---

## Ⅲ. 동작원리 및 흐름도

```text
Cypher Query -> Start Node Index Seek -> Relationship Traversal -> Path Filter -> Result Projection
```

| 단계 | 처리 내용 | 검증 기준 |
|:---:|:---|:---|
| 1 | 라벨·속성 인덱스로 시작 노드 탐색 | index seek 사용 여부 |
| 2 | 관계 타입과 방향 기준으로 확장 | expanded relationship count |
| 3 | hop 수와 조건으로 경로 필터링 | max depth, row count |
| 4 | 경로·점수·노드 결과 반환 | query latency p95 |
| 5 | 필요 시 그래프 알고리즘 실행 | memory estimate, job time |

> 요약: Neo4j 질의는 좋은 시작점을 잡고 관계를 제한적으로 확장해야 탐색 비용을 통제할 수 있음.

## Ⅵ. 실무 적용 및 결론

**적용 방안 3개 (필수 — 단계별 또는 항목별):**
1. 업무 질문을 "누가 누구와 몇 hop으로 연결되는가" 형태로 정의한 뒤 노드·관계·속성 경계를 고정함.
2. Cypher는 시작 노드 인덱스, 관계 타입, hop 상한을 명시하고 PROFILE로 full graph scan을 제거함.
3. 추천·사기 탐지는 온라인 질의와 배치 그래프 알고리즘을 분리하고 결과 점수는 캐시·검색 계층에 배포함.

**결론 (2줄):**
- 기술사 판단: 관계 탐색이 업무 가치이면 Neo4j, 단순 집계·대량 스캔이면 분석 DB를 선택함.
- 향후 방향: 그래프 DB는 지식 그래프, RAG, 권한 그래프와 결합되어 의미 기반 탐색 계층으로 확대됨.
