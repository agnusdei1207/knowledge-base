# 📖 【암기용】 개념 완전 이해

> 목적: 불변 인프라를 처음 봐도 완벽히 이해하게 만든다. 시험 답안 양식이 아니라, 이해를 위한 친절한 설명이다.

## 한눈에
- **개요**: 불변 인프라(Immutable Infrastructure)는 운영 중인 서버(인스턴스)를 직접 수정하지 않고, 변경이 필요하면 검증된 새 이미지로 인스턴스 전체를 교체하는 **인프라 프로비저닝·배포 모델**이다.
- **왜 필요한가**: 운영 서버에 직접 SSH로 패치하면 서버마다 상태가 조금씩 달라지고(구성 편류), 몇 달 뒤 "이 서버가 왜 다른 서버와 다르게 동작하는지" 추적이 불가능해진다.
- **핵심 직관**: 고장 난 부품을 현장에서 납땜해 고치는 대신, 검증된 새 부품으로 통째 교체하는 방식이다.

## 핵심 용어 정리

| 용어 | 의미 | 비유 |
|:---|:---|:---|
| 인프라 프로비저닝 | 이 개념이 속한 상위 범주 — 서버·자원을 만들고 운영하는 방식 전반 | 건물을 짓고 관리하는 방법 자체 |
| Mutable Infrastructure | 운영 서버에 직접 접속해 패치·설정을 수정하는 전통 방식 | 살면서 계속 손보는 낡은 집 |
| Immutable Image | 애플리케이션·런타임·설정을 통째로 담은 배포 단위(AMI, 컨테이너 이미지) | 완성해서 봉인한 조립 부품 |
| Digest(SHA256) | 이미지 내용의 고유 해시값 — 같은 digest면 내용이 100% 동일함을 보장 | 제품의 고유 시리얼 번호 |
| Configuration Drift(구성 편류) | 같은 목적으로 만든 서버들이 시간이 지나며 조금씩 달라지는 현상 | 같은 도면으로 지었는데 수리 이력이 달라 서로 달라진 건물들 |
| 상태(State) 분리 | DB·세션·업로드 파일처럼 유지해야 할 데이터를 인스턴스 밖(외부 저장소)에 둠 | 이삿짐(중요 물건)은 따로 보관하고 집만 허문다 |
| Blue-Green Deployment | 새 인스턴스 그룹(Green)을 통째로 띄운 뒤 트래픽을 한 번에 전환 | 새 매장을 다 차려놓고 간판만 바꿔 여는 것 |
| Canary Deployment | 새 버전에 트래픽 일부(예: 5%)만 먼저 흘려 문제를 조기에 발견 | 신약을 소수에게 먼저 시험 투여 |
| Rollback | 문제가 생기면 이전 이미지로 즉시 되돌리는 것 | 이전 백업 부품으로 재교체 |

## 깊이 이해

### 왜 필요했나 — Mutable 운영의 실패 사례
- 전통적인 운영에서는 서버가 만들어진 이후 SSH로 접속해 패치를 적용하고 설정 파일을 고친다. 문제는 이 변경이 **서버마다 다른 시점에, 다른 사람이, 문서화 없이** 이루어진다는 점이다. 예를 들어 서버 A는 3개월 전 담당자가 수동으로 OpenSSL을 1.1.1로 패치했고, 서버 B는 어제 다른 담당자가 3.0으로 패치했다면, 같은 애플리케이션을 올려도 두 서버의 동작(TLS 핸드셰이크 결과 등)이 달라질 수 있다. 장애가 나면 "이 서버만 왜 다른가"부터 역추적해야 하므로 원인 파악에 시간이 오래 걸린다.

### 동작 원리 — 빌드 → 검증 → 교체 → 폐기
- 순서는 4단계다. ① 코드와 설정을 이미지(AMI, 컨테이너 이미지)로 빌드한다. ② 이미지에 대해 테스트·취약점 스캔·서명을 수행해 검증한다. ③ 검증된 이미지로 **새** 인스턴스를 생성하고, 헬스체크를 통과하면 트래픽을 그쪽으로 전환한다. ④ 트래픽이 완전히 넘어가면 기존(구버전) 인스턴스는 수정하지 않고 그대로 폐기한다.
- 핵심은 3단계에서 **기존 인스턴스를 절대 고치지 않는다**는 것이다. "이 서버가 어떤 상태인지"는 항상 "어떤 이미지 digest로 만들어졌는지"만 보면 알 수 있다 — 이것이 재현성(reproducibility)이다.

### 상태(State)는 왜 반드시 분리해야 하나 — 수치로 이해
- 불변 인프라는 인스턴스를 언제든 통째로 버릴 수 있다는 전제 위에 서 있다. 만약 사용자 세션이나 업로드 파일을 인스턴스 로컬 디스크에 저장한다면, 그 인스턴스를 교체하는 순간 데이터가 사라진다. 그래서 상태 데이터(DB 레코드, 세션, 파일)는 인스턴스 밖의 관리형 DB, Object Storage(S3 등), 또는 별도 Volume에 둔다. 예: 로그인 세션 10만 건을 로컬 메모리에 두면 배포 한 번에 전원 강제 로그아웃되지만, Redis 같은 외부 세션 저장소에 두면 인스턴스를 100대 교체해도 세션은 그대로 유지된다.

### Blue-Green과 Canary — 트래픽 전환 방식의 차이(수치 예)
- Blue-Green: 기존 20대(Blue)가 트래픽을 받는 동안 신규 이미지로 20대(Green)를 새로 띄우고 헬스체크가 100% 통과하면 로드밸런서 설정을 한 번에 Green으로 전환한다. 문제가 생기면 다시 Blue로 즉시 되돌릴 수 있어 롤백이 수 분 내(예: 3~5분)로 끝난다. 다만 순간적으로 인스턴스가 2배(40대) 필요해 비용이 일시적으로 늘어난다.
- Canary: 신규 이미지로 전체의 5%(예: 20대 중 1대)만 먼저 트래픽을 받게 하고 에러율·지연시간을 관찰한다. 에러율이 기준(예: 1% 이하)을 넘지 않으면 25%, 50%, 100%로 단계적으로 늘린다. 인스턴스를 한 번에 2배로 띄울 필요는 없지만, 전체 전환까지 시간이 더 걸린다.

### 비유와 흔한 오해
- **비유**: 식당 메뉴판을 손으로 계속 고쳐 쓰는 대신, 새로 인쇄한 메뉴판을 검수한 뒤 한 번에 교체하는 것과 같다. 옛 메뉴판은 버리지만 어떤 메뉴판이 언제 인쇄됐는지는 항상 기록에 남는다(digest).
- **오해 1**: "불변 인프라는 백업을 안 해도 된다"가 아니다. 오히려 상태를 반드시 외부화하고 백업해야 인스턴스를 마음 놓고 폐기할 수 있다.
- **오해 2**: "컨테이너만 쓰면 불변 인프라"가 아니다. 컨테이너를 띄운 뒤에도 `docker exec`로 컨테이너 안에 들어가 파일을 직접 고치면 mutable 운영과 다를 게 없다. 핵심은 도구가 아니라 "운영 중인 것을 절대 고치지 않는다"는 원칙이다.

## 연결 개념
- IaC — 새 인스턴스를 무엇으로, 어떻게 생성할지를 선언하는 코드(220에서 상세)
- Container Image — 불변 인프라를 구현하는 대표적인 배포 단위
- Ansible·Chef·Puppet — 불변 인프라와 반대로, 이미 떠 있는 서버 "내부"를 지속적으로 보정하는 접근(222에서 대조)

# 📝 【답안용】 시험 답안 템플릿

> 목적: 시험장에서 25분에 그대로 쓰는 답안 양식. 작성방식(추상표현 금지·수치·도식·문제유형 전환)을 엄격히 지킨다.
> 핵심: 불변 인프라는 서버 운영 방식 변화이며, 이미지 검증·상태 분리·교체 배포·rollback 지표가 답안 핵심이다.

## 핵심 인사이트 (3줄 요약)

> 1. **본질**: Immutable Infrastructure는 운영 서버를 직접 변경하지 않고 검증된 새 아티팩트로 교체하는 배포·운영 모델이다.
> 2. **가치**: 구성 편류, 수동 변경, 재현 불가 장애를 줄이고 배포와 rollback을 표준 절차로 만든다.
> 3. **판단 포인트**: 상태 분리, 이미지 서명, 취약점 스캔, blue-green/canary 전환, drift 탐지가 함께 필요하다.

## 출제 의도 및 답안 포인트

| 출제 의도 | 반드시 짚을 핵심 | 감점 회피 포인트 |
|:---|:---|:---|
| 클라우드 운영 모델 이해 확인 | mutable vs immutable, image, replacement, drift | 단순 컨테이너 사용으로만 설명 |
| 배포·복구 판단 확인 | blue-green, canary, rollback, 상태 분리 | DB schema와 persistent data 분리 누락 |
| 보안·감사 통제 확인 | image signing, SBOM, CVE scan, change audit | SSH 금지와 예외 접근 통제 누락 |

> 요약: 불변 인프라는 직접 수정 금지 원칙을 이미지·배포·감사 체계로 구현하는 운영 패턴이다.

## Ⅰ. 개요 및 필요성

- 개요: 운영 서버 비수정 배포 모델
- 배경: 서버 내 수동 변경은 구성 편류와 재현 불가 장애를 만든다.
- 필요성: 이미지 기반 교체, 상태 분리, 자동 rollback으로 변경 단위를 추적해야 한다.

---

## Ⅱ. 구조 및 구성요소

```text
Source Code -> Build Pipeline -> Immutable Image
-> Security Scan/Sign -> Provision New Instance
-> Traffic Switch -> Old Instance Terminate
State Data -> DB/Object Storage/Volume
```

| 구성요소 | 역할 | 특이사항 |
|:---|:---|:---|
| Immutable Image | 애플리케이션·런타임 포함 배포 단위 | AMI, OCI image, VM template |
| Provisioner | 새 인프라 생성 | Terraform, Packer, Kubernetes |
| Traffic Switch | 새 버전으로 요청 전환 | blue-green, canary, weighted routing |
| State Store | 상태 데이터 외부화 | DB, S3, PVC, managed service |

> 요약: 불변 인프라는 이미지, 프로비저닝, 트래픽 전환, 상태 분리로 구성된다.

---

## Ⅲ. 동작원리 및 흐름도

```text
Change Commit -> Build Image -> Test/Scan/Sign
-> Create New Runtime -> Health Check
-> Shift Traffic -> Monitor SLO -> Terminate Old Runtime
```

| 단계 | 처리 내용 | 검증 기준 |
|:---:|:---|:---|
| 1 | 코드와 설정을 이미지로 빌드 | digest 고정, SBOM 생성 |
| 2 | 테스트·CVE 스캔·서명 | critical CVE 0건 |
| 3 | 새 인프라 생성과 health check | readiness 100%, p95 기준 충족 |
| 4 | 트래픽 전환과 구버전 폐기 | rollback 5분 이내 |

> 요약: 운영 변경은 빌드된 아티팩트를 검증하고 새 런타임으로 교체하는 단일 흐름으로 통제된다.

## Ⅳ. 특징

| 구분 | Mutable Infrastructure | Immutable Infrastructure | 판단 수치 |
|:---|:---|:---|:---|
| 변경 방식 | 운영 서버 직접 수정 | 새 이미지·인스턴스 교체 | SSH 변경 0건 목표 |
| 재현성 | 서버별 상태 차이 가능 | image digest로 동일 환경 | drift 0건 |
| 복구 | 현장 수정·수동 복원 | 이전 이미지로 rollback | rollback 5분 이내 |
| 보안 | 수동 패치 이력 분산 | scan/sign/audit 중앙화 | critical CVE 0건 |

> 요약: 불변 인프라는 직접 수정 대신 검증된 교체를 통해 재현성과 감사성을 확보한다.

## Ⅴ. 심화 비교 및 적용 판단

| 구분 | 기존/대안 | Immutable Infrastructure | 선택 기준 |
|:---|:---|:---|:---|
| 구조 | 장기 운영 서버 | 폐기 가능한 runtime | auto scaling, container 환경 |
| 비용/성능 | 현장 패치 시간 | 빌드·배포 pipeline 시간 | 배포 10분 이하, rollback 5분 이하 |
| 운영/위험 | 구성 편류 | 이미지 공급망 리스크 | signing, SBOM, registry ACL |

> 요약: 배포 빈도와 환경 재현성이 요구될수록 불변 인프라가 적합하다.

| 리스크 | 원인 | 대응 방안 | 확인 지표 |
|:---|:---|:---|:---|
| 상태 손실 | 로컬 디스크 저장 | 상태 외부화, backup policy | local write audit 0건 |
| 이미지 취약점 | base image CVE | Trivy/Grype scan, patch rebuild | critical CVE 0건 |
| 교체 실패 | health check 부족 | canary, readiness, automatic rollback | failed rollout rate |

> 요약: 상태 분리, 이미지 보안, rollout 검증이 불변 인프라의 주요 통제이다.

| 점검 항목 | 목표 기준 | 측정 방법 |
|:---|:---|:---|
| 변경 통제 | SSH 직접 변경 0건 | IAM log, session manager |
| 배포 복구 | rollback 5분 이내 | CI/CD metric |
| 구성 편류 | drift 0건 | Terraform plan, config scanner |

> 요약: 직접 변경, rollback 시간, drift 건수로 운영 성숙도를 판단한다.

## Ⅵ. 실무 적용 및 결론

**적용 방안 3개 (필수 — 단계별 또는 항목별):**
1. Packer/OCI image로 런타임을 고정하고 digest, SBOM, cosign 서명을 배포 승인 조건으로 설정
2. Terraform/Kubernetes로 새 인프라를 생성한 뒤 blue-green 또는 canary 5% 트래픽부터 SLO 확인
3. 상태는 RDS, Object Storage, PVC로 분리하고 운영 서버 SSH는 break-glass 승인과 1시간 만료로 제한

**결론 (2줄):**
- 기술사 판단: 배포 빈도 주 1회 이상 또는 운영 편류가 반복되면 불변 인프라, 레거시 장비는 변경 동결·자동화부터 적용
- 향후 방향: GitOps, image signing, policy-as-code와 결합해 공급망 보안까지 포함한 운영 모델로 발전
