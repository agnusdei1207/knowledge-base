## Ⅰ. 개요
- **정의**: 배포된 인프라를 수정하지 않고, 변경 시 새 이미지로 교체하는 운영 모델
- **배경/필요성**: 운영 중 서버에 패치를 누적 적용하면 환경 편차(Configuration Drift)가 발생하여 장애 재현이 불가능해짐
- **비유**: 수리하지 않고 새 부품으로 통째 교체하는 자동차 정비 방식

| 출제 의도 | 반드시 짚을 핵심 | 감점 회피 포인트 |
|:---|:---|:---|
| Mutable vs Immutable 비교 | Configuration Drift 제거 원리 | 상태 저장(Stateful) 워크로드와의 관계를 설명할 것 |

> 요약: 환경 편차를 원천 차단하여 배포 신뢰성을 확보하는 인프라 운영 패러다임임

## Ⅱ. 구성요소
```text
Code --> Build Image --> Deploy New Instance --> Route Traffic
                                                    |
                                              Destroy Old Instance
```

| 구성요소 | 설명 | 비유 |
|:---|:---|:---|
| Golden Image | OS·런타임·앱이 포함된 변경 불가 머신 이미지(AMI, Container) | 완성품 모듈 |
| Blue-Green 배포 | 신규 인스턴스 그룹을 기동 후 트래픽을 전환하는 무중단 교체 방식 | 예비 라인 가동 |
| Image Registry | 버전별 이미지를 저장·관리하는 중앙 저장소 | 부품 창고 |

> 요약: 이미지 빌드-배포-교체를 중심으로 변경 불가 원칙을 실현하는 구조임

## Ⅲ. 절차
```text
이미지 빌드 --> 테스트 --> 배포 --> 구버전 폐기
```
- 1단계: 이미지 빌드 — 코드·설정을 포함한 Golden Image를 CI 파이프라인에서 생성
- 2단계: 테스트 — 빌드된 이미지를 스테이징 환경에서 검증
- 3단계: 배포 — 신규 이미지로 인스턴스를 생성하고 트래픽을 전환
- 4단계: 구버전 폐기 — 이전 인스턴스를 종료하고 자원을 회수

> 요약: 빌드-테스트-배포-폐기의 4단계로 인프라를 교체함

## Ⅳ. 문제점
- 이미지 빌드 시간: 전체 이미지를 매번 재생성하므로 배포 리드타임이 증가함
- 상태 관리 곤란: 로컬 디스크 상태가 인스턴스 폐기 시 유실됨
- 이미지 저장 비용: 버전별 이미지 누적으로 스토리지 비용이 증가함

> 요약: 빌드 시간, 상태 유실, 저장 비용이 주요 과제임

## Ⅴ. 개선방안
1. 단기: 레이어 캐싱(Docker layer cache) 활용으로 이미지 빌드 시간 단축
2. 중기: 외부 볼륨·객체 스토리지로 상태를 분리하여 인스턴스와 독립 관리
3. 장기: 이미지 수명주기 정책(자동 삭제) 적용으로 저장 비용 최적화

> 요약: 캐싱, 상태 외부화, 수명주기 관리 순으로 운영 효율을 확보함

## Ⅵ. 전망
- 발전 방향: 컨테이너·서버리스 환경에서 불변 인프라가 기본 운영 모델로 정착하는 추세
- 기술사적 판단: GitOps와 결합하여 선언적 인프라 관리의 기반 원칙으로 작용함
- 기술사 제언: IaC(220 참조)와 연계한 불변 인프라 파이프라인 표준화가 필요
