## 핵심 인사이트 (3줄 요약)
- 한 번 만들어진 서버는 **OS 패치나 설정 변경을 위해 접속(SSH)해서 뜯어고치는 짓을 절대 하지 않고, 뭔가 바꿀 일이 생기면 낡은 서버는 쓰레기통에 버리고 아예 새 서버를 찍어내어 교체한다는 패러다임**.
- 서버를 '반려동물(Pet)'처럼 정성스레 치료하며 키우던 옛날 방식에서 벗어나, 고장 나면 버리고 새것으로 교체하는 '가축(Cattle)'처럼 취급하는 클라우드 네이티브의 핵심 철학.
- 서버 운영 중 사람이 개입하여 생기는 설정 꼬임(Configuration Drift)을 원천 차단하며, **도커(Docker) 컨테이너** 기술이 이 불변 인프라 사상을 가장 완벽하게 구현한 결과물임.

## Ⅰ. 개요 및 필요성
- **개요**: 서버, 가상 머신, 컨테이너 등의 IT 인프라 구성 요소를 일단 배포한 후에는 절대 수정(Update/Modify)하지 않고, 변경이 필요할 경우 기존 인스턴스를 파기하고 새로운 인스턴스로 교체하는 운영 철학.
- **필요성**: 3년 된 리눅스 서버. A 개발자가 자바 업데이트를 하고, B 개발자가 파이썬을 깔고 며칠 뒤 퇴사함. 이 서버는 이제 **"돌아가긴 하는데 왜 돌아가는지 아무도 모르는, 절대 건드려선 안 되는 폭탄(Snowflake Server)"**이 됨. 여기서 뭔가 하나를 고치면 서버가 뻗음. **"아니, 서버에 들어가서 야금야금 설정을 바꾸니까 나중에 똑같은 서버를 2대 만들 수가 없잖아! 서버는 수정하는 게 아니야, 그냥 새로 찍어내는 거야!"**
---
## Ⅱ. 아키텍처 및 핵심 원리
- **1. Mutable (가변) vs Immutable (불변)**:
  - **가변(과거)**: v1 서버 운영 중 ➡️ SSH 접속 ➡️ `yum update` ➡️ 설정 파일 수정 ➡️ v2 서버로 변신. (업데이트 도중 에러 나면 서버 죽음).
  - **불변(현재)**: v1 서버 운영 중 ➡️ 변경점 발생 ➡️ 내 랩탑에서 v2 '이미지'를 새로 구움 ➡️ v2 서버를 띄움 ➡️ 트래픽을 v2로 돌림 ➡️ v1 서버 전원 뽑아버림 파괴💥.
- **2. 골든 이미지 (Golden Image / Container Image)**:
  - 붕어빵 틀. 운영체제, 라이브러리, 소스 코드가 완벽하게 세팅된 템플릿(예: Dockerfile)을 의미함.
  - 이 틀만 있으면 아마존 AWS든 내 노트북이든 언제나 100% 똑같은 쌍둥이 서버를 1초 만에 수백 개 찍어낼 수 있음.
- **3. 설정 표류 (Configuration Drift) 방지**:
  - 사람이 수동으로 서버를 만지면 시간이 지날수록 1번 서버와 2번 서버의 상태가 미세하게 달라짐(표류). 
  - 불변 인프라는 아무도 서버 내부로 못 들어가게 막기 때문에(Read-only), 1번과 100번 서버가 숨 막힐 정도로 완벽하게 동일함을 보장함.

```text
[ 서버를 대하는 철학의 변화: Pets vs Cattle ]

 🐶 [ 과거 (Mutable): 서버는 나의 반려동물 (Pets) ]
 - 서버 이름: '아폴로', '제우스' (애정 듬뿍)
 - 특징: 아프면(에러) 의사(엔지니어)가 밤새 매달려서 고치고 살려냄. 죽으면 회사가 눈물바다가 됨.

 🐄 [ 현재 (Immutable): 서버는 농장의 소 떼 (Cattle) ]
 - 서버 이름: 'web-node-48a9b', 'web-node-91c2f' (바코드 번호)
 - 특징: 48a9b 소가 병들었네? (에러 발생). 고치지 않음. 🔫 탕! (삭제). 그리고 1초 만에 건강한 새 소 'web-node-f7d1'를 복제해서 빈자리를 채움. 아무도 슬퍼하지 않음.
```

## Ⅲ. 비교 및 연결
| 구분 | Mutable Infrastructure (가변) | Immutable Infrastructure (불변) |
|---|---|---|
| **변경 방식** | 실행 중인 서버에 접속하여 수정 (In-place) | **새로운 서버 이미지를 생성하여 교체 (Replace)** |
| **운영 결과** | 시간이 지날수록 꼬임 (Snowflake 현상) | **항상 100% 깨끗한 초기 상태 보장** |
| **장애 복구** | 사람이 수동으로 롤백하거나 고쳐야 함 | **그냥 이전 버전 이미지(v1)로 다시 찍어내면 1초 컷** |
| **핵심 기술** | SSH 접속, 쉘 스크립트 | **Docker (컨테이너), Packer, Terraform** |
---
## Ⅳ. 실무 적용 및 기술사 판단
- **상태의 외부화 (Stateless Architecture)**: 초보 아키텍트는 도커(불변 인프라) 안에다가 유저들이 업로드한 사진(상태)을 저장함. 다음 날 코드 업데이트한다고 도커 컨테이너를 부수고 새로 찍어냈더니 유저 사진이 다 날아감(대참사). 기술사는 불변 인프라를 도입할 때 **"컨테이너 내부는 무조건 무상태(Stateless)로 비워두고, 지워지면 안 되는 진짜 데이터(사진, DB)는 외부에 있는 AWS S3나 RDS로 완벽하게 빼내라(Externalize)"**는 설계를 최우선으로 강제해야 함.
- **블루-그린 배포(Blue-Green Deployment)와의 결합**: 불변 인프라의 꽃은 무중단 배포임. 기존 V1 서버들(블루)을 냅둔 상태에서, 새로 찍어낸 V2 서버들(그린)을 옆에 쫙 띄움. 테스트해 보고 잘 돌아가면 로드밸런서의 스위치만 V2(그린)로 '딸깍' 돌림. 그리고 V1은 미련 없이 다 부숴버리는 것이 현대 CI/CD의 최고 모범 답안임.

## Ⅴ. 기대효과 및 결론
- "내 컴퓨터에서는 되는데 서버에선 안 되는데요?"라는 개발자와 운영자 간의 영원한 싸움을 단숨에 종식시킴.
- 인프라를 물리적인 하드웨어가 아닌 '찍어낼 수 있는 소프트웨어(코드)'로 대전환시킴으로써, 클라우드 스케일링과 컨테이너 오케스트레이션(K8s)이 동작할 수 있는 사상적 토대를 완성함.

### 👶 어린이를 위한 3줄 비유 설명
1. 옛날에는 레고 성을 만들었는데 벽돌 색깔을 바꾸고 싶으면, 성을 부수지 않고 아슬아슬하게 벽돌만 쏙 빼서 바꿔 끼우려고 했어요. (그러다 성이 와르르 무너지곤 했죠).
2. **불변 인프라**는 "그냥 놔둬! 옆에다가 새 레고 성을 처음부터 완벽하게 새로 조립하자!"라는 방법이에요.
3. 새 레고 성이 멋지게 완성되면 예전 성은 쿨하게 쓰레기통에 버리면 되니까, 성이 무너질까 봐 조마조마할 일이 전혀 없답니다!
