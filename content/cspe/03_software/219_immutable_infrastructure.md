# 📖 【암기용】 개념 완전 이해

## 한눈에
- **개요**: 한 번 생성된 서버나 인프라 환경은 절대 수정(업데이트, 패치)하지 않고, 변경이 필요할 때마다 아예 새로운 환경으로 교체하는 배포 패러다임
- **왜 필요한가**: 운영 중인 서버에 직접 접속해 설정과 패치를 반복하면(가변 인프라), 서버마다 상태가 미세하게 달라지는 '구성 드리프트(Configuration Drift)'가 생겨 예측 불가능한 장애를 낳기 때문
- **핵심 직관**: 낡은 옷을 계속 기워 입지 않는다. 구멍이 나거나 디자인을 바꾸려면, 옷을 수선(가변)하는 게 아니라 새 옷을 찍어내어 갈아입고 헌 옷은 버린다(불변).

## 핵심 용어 정리

| 용어/표기 | 의미 | 비유·예 |
|:---|:---|:---|
| Immutable (불변) | 한 번 배포되면 수명 주기 동안 내부 상태를 변경하지 않음 | 읽기 전용 CD, 컨테이너 이미지 |
| Mutable (가변) | 운영 중인 서버에 접속(SSH)하여 업그레이드, 설정 변경 수행 | 낡은 컴퓨터에 포맷 없이 프로그램 계속 덧깔기 |
| Configuration Drift | 수작업 패치로 인해 인스턴스 간 환경 설정이 파편화되는 현상 | "내 PC에선 되는데 서버에선 안 돼" |
| Golden Image / Container | OS, 라이브러리, 앱 코드가 완벽히 세팅된 템플릿 | 붕어빵 틀, Docker Image, AWS AMI |

## 깊이 이해
- **배경·문제의식**: 레거시 환경에서는 서버 한 대를 소중한 '반려동물(Pet)'처럼 다루며 장애 시 수리했다. 그러나 수백 대를 운영하는 클라우드 환경에서는 패치 이력이 꼬이고 롤백이 어려워지는 치명적 문제가 발생한다.
- **작동 원리**:
  1. 새 버전 배포 시: 소스코드 + 인프라 설정 -> 새 '컨테이너 이미지' 또는 '가상 머신 이미지' 통째로 빌드.
  2. 서버 구동: 새 이미지를 바탕으로 새로운 인스턴스를 무더기로 띄움.
  3. 교체: 로드밸런서 트래픽을 새 서버로 돌리고(Blue-Green), 이전 서버들은 삭제함(Kill).
- **비유**: 서버 = 팩토리에서 찍어내는 장난감(Cattle). 고장나면 고치지 않고 버린 뒤 새 상자를 뜯는다.
- **구체 예시**: Docker 컨테이너 배포. 앱을 업데이트할 때, 실행 중인 컨테이너에 접속해 `git pull` 하지 않는다. 새 이미지를 빌드해 컨테이너를 갈아치운다.
- **흔한 오해·주의점**: 불변 인프라라고 해서 영원히 안 바뀐다는 뜻이 아니다. "실행 중(Runtime)에 손대지 않는다"는 뜻이다. 변경은 오직 빌드(Build) 타임에 이미지 레벨에서 일어난다.

## 연결 개념
- 컨테이너 (Docker, Kubernetes)
- IaC 인프라스트럭처 코드
- CI/CD 파이프라인

# 📝 【답안용】 시험 답안 템플릿

## 핵심 인사이트 (3줄 요약)

> 1. **본질**: 인프라 컴포넌트(VM, 컨테이너)를 가변적 수정 대상이 아닌, 빌드 파이프라인에서 생성되는 교체 가능한 '읽기 전용 일회용품'으로 취급하는 패러다임이다.
> 2. **가치**: 운영 환경의 예기치 않은 구성 변경(Drift)을 차단하여 배포의 일관성, 재현성, 신속한 롤백을 100% 보장한다.
> 3. **판단 포인트**: 클라우드 네이티브(Cloud Native) 구조로의 전환을 위해 IaC(코드 기반 인프라)와 결합된 이미지 기반 프로비저닝 메커니즘을 확립해야 한다.

## 출제 의도 및 답안 포인트

| 출제 의도 | 반드시 짚을 핵심 | 감점 회피 포인트 |
|:---|:---|:---|
| 클라우드 시대 인프라 패러다임 변화 이해 | 가변(Mutable/Pet) vs 불변(Immutable/Cattle), Configuration Drift 방지 | 불변을 "설정을 아예 바꾸지 않는 것"으로 오해한 추상 서술 |
| 불변 인프라 구현을 위한 기술적 아키텍처 제시 | Golden Image(AMI, Docker Image), Blue-Green 배포, IaC 결합 | 불변 인프라와 컨테이너를 단순히 동의어로 취급 |

> 요약: 서버 접속 후 수동 패치가 야기하는 인프라 파편화를 지적하고, 런타임 변경 금지와 이미지 교체 기반의 자동화 아키텍처를 제시해야 한다.

---

## Ⅰ. 개요 및 필요성

- 개요: 런타임 환경에 배포된 인프라 인스턴스의 구성을 절대 변경(In-place update)하지 않고, 수정 시 새로운 이미지를 빌드하여 교체(Replace)하는 프로비저닝 전략
- 배경: 전통적 가변(Mutable) 인프라 운영 시, 수작업 패치 누적 및 에러로 인스턴스 간 설정이 어긋나는 구성 드리프트(Configuration Drift) 현상 심화
- 필요성: 일관되고 멱등성(Idempotent) 있는 환경 구축, 빠른 스케일아웃 및 장애 시 즉각 복구(Rollback)

---

## Ⅱ. 구조 및 구성요소

```text
[가변 인프라] 서버 구동 -> SSH 접속 -> App 복사 및 패치 업데이트 (환경 파편화 리스크)
[불변 인프라] 코드 Push -> CI/CD 이미지 빌드 -> 새 인스턴스 무리 띄움 -> 로드밸런서 스위칭 -> 구 인스턴스 폐기
```

| 구성요소 | 역할 | 특이사항 |
|:---|:---|:---|
| IaC (Infrastructure as Code) | 인프라 설정과 이미지 빌드 스펙을 코드로 정의 | Terraform, Packer, Dockerfile |
| Golden Image (Artifact) | OS, 의존성 라이브러리, 앱 코드가 완결된 배포 가능 패키지 | 클라우드 AMI, Docker Image |
| Image Registry | 빌드된 불변 이미지를 저장 및 버전 관리 | ECR, Docker Hub |
| Orchestrator | 구버전 인스턴스 종료 및 신규 이미지 기반 인스턴스 교체 통제 | Kubernetes, Auto Scaling Group |

> 요약: 사람이 서버를 만지는 경로를 차단하고, 코드로 정의된 이미지를 공장처럼 찍어내어 교체하는 자동화 구조다.

---

## Ⅲ. 동작원리 및 흐름도

```text
설정 코드 변경 -> 이미지 빌드 및 태깅 -> Registry 등록 -> 신규 인스턴스 배포 -> 헬스체크 성공 -> 라우팅 전환 및 구 인스턴스 삭제
```

- 1단계 [코드 기반 갱신]: 서버 업데이트 사항(OS 패치, 앱 배포)을 IaC 스크립트(Dockerfile 등) 코드로 커밋
- 2단계 [이미지 제빵]: CI 도구를 통해 런타임에 필요한 모든 것이 구워진(Baked) 완결형 이미지 생성
- 3단계 [교체 배포]: 기존 서버 인스턴스는 둔 채 신규 이미지를 기반으로 새 인스턴스 풀 생성
- 4단계 [원자적 스위칭]: Blue-Green 또는 Canary 배포로 트래픽 스위칭 후, 무결성 확인 시 이전 인스턴스(가축) 일괄 파기

> 요약: 서버는 수정(Update)의 대상이 아니라, 버리고(Destroy) 다시 띄우는(Recreate) 소모품(Cattle)으로 동작한다.

---

## Ⅳ. 특징
- 환경 일관성: 개발, 테스트, 운영 서버가 100% 동일한 이미지를 공유하므로 "내 로컬에선 되는데 운영에선 안 된다"는 문제 원천 차단
- 장애 복구 극대화: 장애 또는 악성 코드 감염 시 원인을 라이브 서버에서 분석하고 치료할 필요 없이, 검증된 이전 버전 이미지로 즉각 롤백(재배포)
- 외부 상태 분리 의무화: 인스턴스가 언제든 삭제될 수 있으므로 로그나 데이터(State)를 내부 디스크에 남기지 않고 외부 저장소(DB, S3)로 분리 필수

> 요약: 배포 안정성과 롤백 신뢰도를 비약적으로 높이지만, 상태 유지(Stateful) 데이터 아키텍처의 분리가 선결 조건이다.

## Ⅴ. 심화 비교 및 적용 판단

| 비교 축 | 가변 인프라 (Mutable / Pets) | 불변 인프라 (Immutable / Cattle) | 선택 기준 |
|:---|:---|:---|:---|
| 업데이트 방식 | In-place Update (현 위치 덮어쓰기) | Replace (신규 인스턴스로 통째 교체) | 인프라 구성 패러다임 |
| 서버 취급 방식 | 고유 이름 부여, 고장 시 수리 (반려동물) | 무작위 이름, 고장 시 즉각 폐기 (가축 떼) | 스케일 아웃 민첩성 |
| 트러블슈팅 | SSH 접속을 통한 라이브 패치 및 확인 | 중앙집중식 로그 분석 및 새 이미지 재배포 | 보안·접근 통제 수준 |
| 드리프트 가능성 | 높음 (패치 이력 꼬임 발생) | 없음 (모든 인스턴스가 복제본) | 신뢰성 및 재현성 |

> 요약: 장기 구동되는 레거시 DB나 소규모 서버는 가변이 남겠지만, 무상태(Stateless) 웹/WAS 아키텍처는 불변 인프라로의 전환이 글로벌 표준이다.

**리스크·대응 (기본은 불릿):**
- 데이터 유실(Stateful 분리 실패): 인스턴스 파기 시 내부 볼륨 데이터 날아감 → 로그의 외부 수집(Fluentd), DB 및 파일 시스템(NFS/S3) 물리적 분리 (지표: 로컬 디스크 I/O 의존도)
- 배포 속도 지연: 사소한 설정 변경에도 GB 단위의 무거운 VM 이미지를 매번 새로 구워야 함 → Packer로 베이스 이미지를 사전 캐싱하거나 경량 Docker 컨테이너 체제로 전환 (지표: CI/CD 파이프라인 빌드 타임)

## Ⅵ. 실무 적용 및 결론

**적용 방안 3개:**
1. 골든 이미지 파이프라인 구축: OS 베이스 이미지에 회사 표준 보안 에이전트와 미들웨어를 통합한 Golden AMI를 Packer로 자동 구워내어 전사 배포 표준 템플릿화
2. SSH 접속 전면 차단 (Zero Trust): 모든 운영 서버에 대한 SSH 포트 오픈과 수동 쉘(Shell) 접근을 차단하여 개발자가 임의로 가변(Mutable) 작업을 할 수 없도록 원천 강제
3. 컨테이너 기반 100% 불변 체제 전환: 가상 머신(VM)보다 가볍고 빠른 도커(Docker)와 쿠버네티스 생태계를 도입하여 수초 내 이미지 생성 및 파기 아키텍처 구현

**결론:**
- 기술사 판단: 불변 인프라는 인프라 엔지니어링의 패러다임을 '수동 운영'에서 '소프트웨어 개발 프로세스'로 편입시켜 조직의 데브옵스(DevOps) 성숙도를 완성하는 핵심 열쇠다.
- 향후 방향: IaC와 결합된 불변 인프라 모델은 서버리스(Serverless) 패러다임으로 진화하며, 인프라 관리 비용 자체를 0으로 수렴시키는 방향으로 발전하고 있다.
