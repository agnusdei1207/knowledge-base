## Ⅰ. 개요
- **정의**: 코드 배포와 기능 릴리스를 분리하는 조건 분기 토글 기법
- **배경/필요성**: 배포 시점과 기능 활성화 시점이 동일하면 장애 발생 시 롤백 비용이 큼
- **비유**: 건물 전등 스위치—전기(코드)는 연결돼 있지만 스위치(플래그)를 올려야 불이 켜짐

| 출제 의도 | 반드시 짚을 핵심 | 감점 회피 포인트 |
|:---|:---|:---|
| 배포-릴리스 분리 원리 이해 | 토글 유형별 수명·관리 주체 구분 | 기술 부채(미삭제 플래그)를 언급할 것 |

> 요약: 코드 변경 없이 런타임에서 기능 ON/OFF를 제어하는 조건 분기 기법임

## Ⅱ. 구성요소
```text
Client --> Flag Router --> [ON] --> New Feature Path
                      +--> [OFF] --> Legacy Path
Flag Router <-- Flag Store (DB / Config)
```

| 구성요소 | 설명 | 비유 |
|:---|:---|:---|
| Flag Store | 플래그 상태(ON/OFF·비율)를 저장하는 저장소 | 스위치 패널 |
| Flag Router | 요청마다 플래그 값을 평가해 분기하는 런타임 모듈 | 철도 분기기 |
| Targeting Rule | 사용자·환경 조건별로 플래그 값을 결정하는 규칙 | 초대장 명단 |

> 요약: 저장소-라우터-타겟팅 규칙 3요소로 런타임 분기를 수행함

## Ⅲ. 절차
```text
플래그 정의 --> 코드 분기 삽입 --> 점진 활성화 --> 플래그 제거
```
- 1단계: 플래그 정의—Flag Store에 키·기본값·타겟팅 규칙 등록
- 2단계: 코드 분기 삽입—`if (flag.isEnabled())` 형태로 신규 경로 래핑
- 3단계: 점진 활성화—비율 기반 롤아웃(1 % → 10 % → 100 %)으로 위험 최소화
- 4단계: 플래그 제거—완전 활성화 후 분기 코드·플래그 키를 삭제해 기술 부채 방지

> 요약: 정의-삽입-점진 활성화-제거의 4단계로 안전한 릴리스를 수행함

## Ⅳ. 문제점
- 기술 부채 누적: 사용 종료 후 플래그를 미삭제 시 분기 코드가 잔존해 복잡도 증가
- 테스트 조합 폭발: 플래그 N개 시 2^N 경로가 생겨 테스트 커버리지 확보가 곤란함
- 설정 불일치 장애: Flag Store와 코드 버전 간 동기화 실패 시 예기치 않은 경로 실행

> 요약: 미삭제 부채, 조합 폭발, 설정 불일치가 주요 위험임

## Ⅴ. 개선방안
1. 단기: 플래그 만료일 자동 경고·CI에서 미사용 플래그 감지 Lint 적용
2. 중기: 플래그 간 의존관계 그래프를 관리해 조합 테스트 범위를 축소
3. 장기: GitOps 기반 Flag Store 버전 관리로 코드-설정 동기화 자동 보장

> 요약: 만료 관리-의존 그래프-GitOps 순으로 부채와 불일치를 해소함

## Ⅵ. 전망
- 발전 방향: Feature Management Platform(LaunchDarkly 등)과 Observability 연동 확대
- 기술사적 판단: CI/CD 성숙도가 높을수록 플래그 거버넌스 체계가 필수임
- 기술사 제언: 플래그 생명주기 정책(생성-활성-폐기)을 조직 표준으로 수립할 필요
