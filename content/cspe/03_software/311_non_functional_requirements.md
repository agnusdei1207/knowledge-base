# 📖 【암기용】 개념 완전 이해

> 목적: 비기능 요구사항을 기능 목록과 구분하고, 왜 정확한 수치 하나가 아키텍처 전체를 바꾸는지 이해하게 만든다. 시험 답안 양식이 아니라, 이해를 위한 친절한 설명이다.
> 이 파일은 품질 속성의 8대 분류 체계 자체(ISO/IEC 25010 — 077 참조)는 다시 나열하지 않는다. 이 파일이 새로 다루는 것은 그 품질 속성을 **측정 가능한 요구사항 문장으로 바꾸는 방법**과 **그 수치가 설계를 어떻게 바꾸는가**다.

## 한눈에
- **개요**: **비기능 요구사항(NFR)**은 시스템이 "무엇을 하는가"가 아니라 **품질 속성**(성능·가용성·보안·확장성 등, ISO/IEC 25010 참조)을 "어느 수준으로 만족해야 하는가"를 **측정 가능한 수치**로 정의한 요구사항이다.
- **왜 필요한가**: 로그인 기능이 있어도 p95 300ms, MFA, 월 가용률 99.9%, HPA max20 같은 기준이 없으면 검수·운영·장애 책임을 판단할 수 없다. 수치가 없는 품질 요구는 나중에 "이 정도면 됐다"는 쪽과 "부족하다"는 쪽의 말싸움이 된다.
- **핵심 직관**: 기능 요구사항이 메뉴판이라면 비기능 요구사항은 조리 시간, 위생 기준, 좌석 수, 영업 중단 허용 시간을 정하는 계약 조건이다.

## 핵심 용어 정리 (내부에 등장하는 것들)

| 용어 | 의미 | 비유 |
|:---|:---|:---|
| 품질 속성 | 성능·보안·가용성·확장성 등 비기능 특성의 분류 체계(077 ISO/IEC 25010 참조) | 자동차의 속도·연비·안전성 |
| 품질 시나리오 | 품질 요구를 자극·환경·응답·측정값으로 구체화한 문장(079_atam.md 참조) | "동시 5,000명 접속 시 응답 2초 이내"처럼 숫자로 못 박은 요구 |
| SLO/SLA | 운영 단계에서 품질 목표를 계약·모니터링 기준으로 전환한 것(192 참조) | 계약서의 서비스 품질 조항 |
| RTO/RPO | 장애 시 복구까지 걸리는 시간(RTO)과 되돌릴 수 있는 데이터 손실 시점(RPO)(244 참조) | 정전 후 재가동 시간(RTO)과 백업 시점(RPO) |
| p95/p99, TPS | 응답시간 백분위수와 초당 처리 트랜잭션 수(312 성능 테스트 지표 참조) | 100명 중 95번째로 느린 사람의 대기시간 |
| 인수 기준(Acceptance Criteria) | 이 수치를 충족해야 "완료"로 인정한다는 검수 조건 | 준공 검사 통과 기준 |

## 깊이 이해

### 기능 요구 vs 비기능 요구를 가르는 판별법
- 질문 하나로 구분한다: "이 요구를 지우면 시스템이 그 업무를 아예 처리 못 하게 되는가, 아니면 처리는 하되 품질(속도·안정성)만 나빠지는가?" 전자는 기능 요구(예: 로그인 기능 자체), 후자는 비기능 요구(예: 로그인 응답시간, 로그인 가용성)다.
- 이 판별이 중요한 이유는, 기능 요구 누락은 즉시 발견되지만(버튼이 없다) 비기능 요구 누락은 개발 완료 시점까지 드러나지 않다가 운영 첫 피크 트래픽에서야 터지기 때문이다.

### 측정 불가능한 문장을 인수 기준으로 바꾸는 원리
- 나쁜 예: "응답 지연을 최소화한다" — 최소화의 기준이 없어 개발자와 검수자가 서로 다른 잣대를 댈 수 있다.
- 좋은 예: "주요 조회 API는 피크 시간대(평일 오전 9~11시) 기준 p95 300ms 이하, 오류율 0.1% 이하이며 k6로 측정한다" — 목표값, 측정 조건(시간대), 측정 도구가 모두 있어 누가 측정해도 같은 판정이 나온다.
- 이 변환 공식은 항상 네 요소를 채우는 것이다: ① 대상(어느 API·기능인가) ② 목표값(숫자) ③ 부하·측정 조건(피크인지 평시인지) ④ 측정 도구·방법.

### 수치 하나가 아키텍처를 바꾸는 원리 — 가용률을 예로
- 가용률 99.9%는 "1년 중 다운타임 허용 시간이 (1-0.999)×365.25일×24시간×60분 ≈ 526분(연간) ≈ **월 43.8분 이하**"라는 뜻이다. 이 정도는 단일 인스턴스에 모니터링·자동 재시작만 있어도 달성 가능한 수준이다.
- 반면 가용률 99.99%("포 나인")는 연간 다운타임이 약 52.6분, **월 4.4분 이하**로 10배 더 엄격해진다. 이 수준은 사람이 알람을 받고 대응하는 속도로는 못 맞추므로, 다중 AZ·자동 페일오버·헬스체크 기반 즉시 전환 같은 아키텍처 자체의 변경이 필요하다.
- 즉 "가용성을 높인다"는 말이 아니라 "99.9% → 99.99%"라는 숫자 하나가 바뀌면 필요한 아키텍처 패턴 자체가 달라진다 — 이것이 NFR을 정확한 수치로 못 박아야 하는 이유다.

### 비유와 흔한 오해
- **비유**: 엘리베이터 계약에서 "사람을 위아래로 이동"은 기능이고, "정원 15명, 대기 30초 이하, 정전 시 비상전원 30분"은 비기능 요구다. 후자가 없으면 설치는 됐어도 안전 검수를 통과할 수 없다.
- **오해**: 비기능 요구는 개발 후 튜닝 항목이 아니다. 캐시 구조, 이중화 여부, 암호화 방식, 예산 산정은 설계 초기에 비기능 요구를 반영해야 하는 결정들이다 — 가용률 99.99%를 개발 막바지에 요구하면 아키텍처를 처음부터 다시 짜야 하는 경우가 많다.

## 연결 개념
- 077 ISO/IEC 25010 (품질 속성 분류 체계, 선행 개념)
- 192 SLO/SLA/SLI (가용성·오류 예산을 운영 기준으로 전환)
- 244 재해복구 RTO/RPO (복구 목표 시간·데이터 손실 허용 기준)
- 312 성능 테스트 지표 (성능 관련 비기능 요구의 세부 정의, 후행)

# 📝 【답안용】 시험 답안 템플릿

> 목적: 시험장에서 25분에 그대로 쓰는 답안 양식. 작성방식(추상표현 금지·수치·도식·문제유형 전환)을 엄격히 지킨다.
> 핵심: 비기능 요구사항은 품질 속성 나열이 아니라 측정 가능한 검수 기준과 아키텍처 선택 기준으로 작성해야 한다.

## 핵심 인사이트 (3줄 요약)

> 1. **본질**: 비기능 요구사항은 성능·보안·가용성·확장성 등 품질 속성을 수치와 검증 절차로 정의한 계약형 요구사항이다.
> 2. **가치**: p95 지연, TPS, RTO/RPO, AES-256, HPA 범위 같은 기준을 명시해 설계·테스트·검수의 판정 근거를 제공한다.
> 3. **판단 포인트**: "처리 가능" 같은 표현을 배제하고 목표값, 부하 조건, 측정 도구, 예외 조건을 함께 써야 한다.

## 출제 의도 및 답안 포인트

| 출제 의도 | 반드시 짚을 핵심 | 감점 회피 포인트 |
|:---|:---|:---|
| 요구공학 품질 속성 분류 확인 | 성능·보안·가용성·확장성·운영성 분류와 수치화 | 기능 요구사항과 혼동 |
| 검수 가능 요구 정의 역량 확인 | SLO, SLA, NFR, acceptance criteria 연결 | "향상", "개선" 같은 측정 불가 표현 |
| 아키텍처 영향 판단 확인 | 캐시, 이중화, 암호화, 오토스케일링 설계 반영 | 테스트 단계 사후 보완으로 설명 |

> 요약: 이 문제는 비기능 요구를 품질 속성명에서 멈추지 않고 검증 가능한 수치와 설계 제약으로 바꾸는 역량을 본다.

## Ⅰ. 개요 및 필요성

- 개요: 시스템 품질의 검증 기준
- 배경: 기능 요구는 업무 처리 내용을 정하지만 성능·보안·가용성·확장성의 허용 수준은 별도 기준이 필요함
- 필요성: 응답시간 p95, 가용성 SLA, RTO/RPO, 암호화 기준을 요구정의 단계에서 인수 조건으로 명시해야 함

---

## Ⅱ. 구조 및 구성요소

```text
업무 요구 -> 품질 속성 분류 -> 정량 기준 -> 검증 방법 -> 인수 기준
            / 성능 / 보안 / 가용성 / 확장성 / 운영성
```

| 구성요소 | 역할 | 특이사항 |
|:---|:---|:---|
| 성능 요구 | TPS, p95 응답시간, 배치 처리시간 정의 | 피크 부하와 데이터 건수 병기 |
| 보안 요구 | 인증·인가·암호화·감사로그 정의 | AES-256, mTLS, RBAC 등 기술명 명시 |
| 가용성 요구 | 가용률, RTO, RPO, DR 수준 정의 | 월 99.9%, RTO 4시간 등 기준 |
| 확장성 요구 | 노드 증설, HPA 범위, 샤딩 조건 정의 | min2/max20, CPU 70% 임계값 |

> 요약: 비기능 요구는 품질 속성별 목표값과 검증 방법을 묶어 인수 판정 기준으로 만든다.

## Ⅲ. 동작원리 및 흐름도

```text
품질 요구 수집 -> 측정 지표 선정 -> 목표값 합의 -> 테스트 설계 -> 검수 판정
```

| 단계 | 처리 내용 | 검증 기준 |
|:---:|:---|:---|
| 1 | 업무 중요도와 피크 조건 식별 | 사용자 수, 데이터 건수, 업무 시간대 |
| 2 | 품질 속성별 지표 선정 | p95, TPS, 오류율, RTO/RPO |
| 3 | 목표값과 예외 조건 합의 | SLA, SLO, 보안 기준선 |
| 4 | 부하·보안·복구 테스트 수행 | JMeter, k6, DAST, DR Drill |
| 5 | 인수 기준 충족 여부 판정 | 결과 리포트, 결함 조치 증적 |

> 요약: 비기능 요구는 수집-지표화-목표 합의-시험-판정 순서로 요구사항에서 검수 증적으로 전환된다.

| 비교 축 | 기존/대안 | 본 키워드 | 선택 기준 |
|:---|:---|:---|:---|
| 요구 방식 | 자연어 품질 표현 | SLO·SLA 기반 정량 요구 | 검수 분쟁 가능성 |
| 비용/성능 | 과소 용량 산정 | 피크 기준 용량 산정 | TPS와 동시 사용자 예측 |
| 운영/위험 | 장애 후 책임 논쟁 | RTO/RPO와 DR 절차 명시 | 업무 중단 허용 시간 |

> 요약: 비기능 요구는 프로젝트 범위보다 운영 책임과 비용 산정까지 결정하는 기준이다.

| 리스크 | 원인 | 대응 방안 | 확인 지표 |
|:---|:---|:---|:---|
| 목표값 누락 | 품질 표현만 작성 | SLO 템플릿 적용 | 요구사항별 지표 매핑률 100% |
| 과도한 목표 | 업무 등급 미분류 | 중요도별 차등 SLO | 비용 증가율, 서버 수 |
| 검증 불가 | 측정 도구 미정 | k6, JMeter, APM 지정 | 테스트 리포트 존재 |

> 요약: 비기능 요구 리스크는 목표값, 업무 등급, 측정 도구를 요구서에 함께 명시해 통제한다.

| 점검 항목 | 목표 기준 | 측정 방법 |
|:---|:---|:---|
| 성능 | 주요 API p95 300ms, 오류율 0.1% 이하 | 부하 테스트, APM |
| 가용성 | 월 99.9%, RTO 4시간, RPO 15분 | 장애 훈련, 백업 복구 |
| 보안/운영 | AES-256, RBAC, 감사로그 1년 보관 | 보안 점검표, 로그 샘플 |

> 요약: 성공 여부는 품질 속성별 목표 기준과 시험 증적이 1:1로 대응하는지로 판단한다.

## Ⅵ. 실무 적용 및 결론

**적용 방안 3개:**
1. 요구정의서에 NFR 매트릭스 작성: 성능·보안·가용성·확장성별 목표값, 부하 조건, 측정 도구, 검수 기준 기재
2. 설계 단계 반영: Redis Cache, DB Read Replica, mTLS, RBAC, HPA min2/max20을 품질 속성별 설계 항목으로 연결
3. 인수 테스트 자동화: k6/JMeter 부하 스크립트, DR 복구 시나리오, OWASP ZAP 리포트를 검수 산출물로 제출

**결론 (2줄):**
- 기술사 판단: 업무 등급이 높은 핵심 거래는 p95·RTO·암호화 기준을 선행 확정하고, 내부 관리 기능은 비용 대비 차등 목표를 적용한다
- 향후 방향: NFR은 SRE SLO, DevSecOps, Observability와 결합해 요구정의에서 운영 지표까지 추적되는 형태로 발전한다
