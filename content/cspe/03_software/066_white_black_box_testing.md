## 핵심 인사이트 (3줄 요약)
- **화이트박스 테스트(White Box)**: 소프트웨어의 내부 소스코드(로직, 제어 흐름)를 훤히 들여다보며 테스트하는 기법 (구조 기반 테스트).
- **블랙박스 테스트(Black Box)**: 내부 코드는 전혀 모르고, 사용자의 관점에서 '입력값'을 넣었을 때 명세서대로 '출력값'이 나오는지 검증하는 기법 (명세 기반 테스트).
- 두 기법은 상호 배타적이 아니라 보완적이며, 개발자는 화이트박스(단위 테스트)를, QA/사용자는 블랙박스(시스템/인수 테스트)를 수행하여 품질을 이중으로 교차 검증함.

## Ⅰ. 개요 및 필요성
- **개요**: 소프트웨어 테스트 케이스(Test Case)를 설계하는 가장 대표적인 두 가지 접근 방식.
- **필요성**: 코드의 모든 분기문(If/Else)을 검증하려면 소스 코드를 아는(White) 방법이 필요하고, 사용자가 실수로 이상한 값을 넣었을 때 시스템이 안 죽는지 검증하려면 외부인의 시선(Black)이 필요하므로 두 기법이 모두 고안됨.
---
## Ⅱ. 아키텍처 및 핵심 원리
- **화이트박스 테스트 기법 (구조 기반)**:
  1. **구문 커버리지 (Statement)**: 코드의 모든 줄(Line)이 최소 한 번씩 실행되었는가?
  2. **결정/분기 커버리지 (Decision/Branch)**: If문의 참(True)/거짓(False) 분기가 모두 최소 한 번씩 실행되었는가? (실무에서 가장 많이 쓰이는 표준 기준).
  3. **조건 커버리지 (Condition)**: If문 내부의 개별 조건식들이 모두 참/거짓을 가졌는가?
  4. **경로 커버리지 (Path)**: 실행 가능한 모든 조합의 경로를 100% 테스트.
- **블랙박스 테스트 기법 (명세 기반)**:
  1. **동등 분할 (Equivalence Partitioning)**: 유효한 값(1~100)과 무효한 값(101~)을 그룹으로 묶어 대표값 1개씩만 테스트.
  2. **경곗값 분석 (Boundary Value Analysis)**: 에러는 주로 경계에서 터지므로, 범위의 끝단(0, 1, 100, 101)을 집중 테스트.
  3. **결정 테이블 (Decision Table)**: 복잡한 논리 조건을 표로 만들어 조합 테스트.
  4. **상태 전이 (State Transition)**: 시스템의 상태(로그인 ➡️ 로그아웃 ➡️ 만료) 변화를 테스트.

```text
[ 화이트박스와 블랙박스 테스트의 관점 차이 ]

 (화이트박스 - 개발자 관점)                 (블랙박스 - 사용자/QA 관점)
 
 [ Input: 5 ]                              [ Input: 5 ]
      ⬇️                                         ⬇️
 +---------------------+                   +---------------------+
 | if (x > 0) return X | (코드가 보임)      |      (안 보임)      |
 | else return -X      |                   |  ?? Magic Box ??    |
 +---------------------+                   +---------------------+
      ⬇️                                         ⬇️
 [ Output: 5 ]                             [ Output: 5 ]
 * 모든 조건(분기)을 타는지 확인             * 명세서대로 값이 나오는지만 확인
```

## Ⅲ. 비교 및 연결
| 구분 | 화이트박스 테스트 (White Box) | 블랙박스 테스트 (Black Box) |
|---|---|---|
| **기반/근거** | 소스 코드 (제어 구조, 데이터 흐름) | 요구사항 명세서 (기능 명세) |
| **수행 주체** | 소프트웨어 개발자 | 독립적인 테스터 (QA), 최종 사용자 |
| **적용 단계** | 단위 테스트, 통합 테스트 | 시스템 테스트, 인수 테스트 |
| **목적** | 논리적 오류, 불필요한 코드(Dead Code) 제거 | 기능 누락, 인터페이스 오류, 오작동 발견 |
---
## Ⅳ. 실무 적용 및 기술사 판단
- **커버리지 100%의 환상**: 소나큐브(SonarQube) 같은 도구로 분기 커버리지(Branch Coverage)를 측정할 때, 100%를 채우는 것은 비용 대비 효과가 매우 떨어짐. 실무적으로 핵심 비즈니스 로직은 80~90%를 강제하되, 단순 DTO나 UI 코드 등은 테스트에서 제외하는 현실적인 타협(Pragmatic Testing)이 필요함.
- **경곗값 분석의 파괴력**: 블랙박스 테스트 중 가장 가성비가 높은 기법은 단연 '경곗값 분석'임. 개발자들은 `>`와 `>=`를 혼동하는 실수(Off-by-one Error)를 가장 많이 저지르므로, 항상 임계값 근처(N-1, N, N+1)를 집요하게 테스트하는 습관을 들여야 함.
---
## Ⅴ. 기대효과 및 결론
- 개발자는 화이트박스로 구조적 결함을 막고, QA는 블랙박스로 기능적 결함을 찾아내어 완벽에 가까운 소프트웨어 퀄리티를 달성함.
- 최근에는 테스트 자동화 도구를 통해 이 두 가지 관점을 넘나드는 '그레이박스 테스트(Gray Box)'가 등장하며, 품질 검증의 속도와 정확도를 더욱 끌어올리고 있음.

### 👶 어린이를 위한 3줄 비유 설명
1. 화이트박스는 투명한 젤리 시계예요. 안에 톱니바퀴가 어떻게 맞물려 돌아가는지 눈으로 꼼꼼히 확인하며 고장 난 부품을 찾는 방법이죠.
2. 블랙박스는 속이 안 보이는 신비한 자판기예요. 안은 볼 수 없지만, 100원을 넣었을 때 정확히 사탕이 나오는지만 계속 눌러보며 확인하는 거예요.
3. 시계 고치는 아저씨(개발자)는 화이트박스, 자판기에서 과자를 빼먹는 손님(사용자)은 블랙박스 방식을 쓴답니다!
