# 📖 【암기용】 개념 완전 이해

## 한눈에
- **개요**: 테스트 대상을 어떻게 바라보고 결함을 찾을 것인지에 대한 두 가지 핵심 관점(테스트 기법)
- **왜 필요한가**: 내부 소스코드 구조를 모두 검증하려면 경우의 수가 너무 많고, 반대로 외부 결과값만 확인하면 숨겨진 논리 오류를 놓친다. 둘을 상호 보완적으로 써야 한다.
- **핵심 직관**: 투명한 유리상자(내부 기어 돌아가는 게 다 보임 = 화이트박스) vs 불투명한 검은상자(버튼 누르면 결과만 나옴 = 블랙박스)

## 핵심 용어 정리

| 용어/표기 | 의미 | 비유·예 |
|:---|:---|:---|
| 화이트박스 테스트 | 소스코드의 내부 논리, 제어 흐름, 분기를 모두 확인하는 구조 기반 테스트 | 기계 분해해서 부품끼리 맞물림 확인 |
| 블랙박스 테스트 | 내부 구조는 무시하고, 입력값에 대한 출력값이 명세와 맞는지 확인하는 명세 기반 테스트 | 자판기에 동전 넣고 콜라 잘 나오나 확인 |
| 구조적 커버리지 | 화이트박스에서 내부 코드를 얼마나 실행했는지 측정 (구문, 분기 등) | 미로의 모든 길을 한 번씩 밟아봤는가? |
| 동치 분할 (Equivalence Partitioning) | 블랙박스에서 결과가 동일할 입력값들을 그룹화하여 대푯값만 테스트 | 1~100점 시험에서 50점 하나만 넣어보기 |

## 깊이 이해
- **배경·문제의식**: 개발자는 코드를 짰기 때문에 내부 로직(if, while 등)의 결함을 찾고 싶어하고(화이트박스), 사용자와 QA는 코드는 모르겠고 요구사항 명세서대로 동작하는지(블랙박스)를 알고 싶어한다. 하나의 방식만으로는 소프트웨어 전체 품질을 보장할 수 없다.
- **작동 원리 (화이트박스)**: 소스 코드를 보면서 제어 흐름도(Control Flow Graph)를 그린다. 모든 구문(문장)을 최소 한 번은 실행하거나, if문의 참/거짓 분기를 모두 타보도록 입력값을 설계한다. (주로 개발자가 수행하는 단위 테스트)
- **작동 원리 (블랙박스)**: 코드는 안 본다. 요구사항 명세서를 보고 "나이 19세를 입력하면 '성인'이 출력되어야 한다"는 명세에 따라 입력값(18, 19, 20 등)을 넣고 기댓값과 일치하는지 확인한다. 경곗값 분석, 동치 분할 등을 사용한다. (주로 QA가 수행하는 통합/시스템 테스트)
- **구체 예시**: `if (age >= 18)` 코드가 있을 때. 화이트박스는 코드의 분기(T/F)를 타기 위해 `18`, `17`을 넣음. 블랙박스는 명세서의 경곗값인 `17`, `18`, `19`를 넣어 정확한 결과가 나오는지 확인.
- **흔한 오해·주의점**: "화이트박스 테스트를 100% 완료하면 버그가 없다?" 아니다. 코드가 잘 실행됨은 증명하지만, 애초에 '개발자가 빼먹고 안 짠 기능(요구사항 누락)'은 코드가 없으므로 화이트박스로는 찾을 수 없다. 블랙박스가 이를 보완한다.

## 연결 개념
- 테스트 커버리지: 화이트박스 테스트의 달성도를 정량적으로 측정하는 지표
- 단위 테스트 / 시스템 테스트: 화이트박스는 단위, 블랙박스는 시스템 단계에서 주로 사용
- 그레이박스 테스트: 두 기법을 혼합하여 내부 구조 일부를 알면서 명세도 확인하는 절충형 기법

# 📝 【답안용】 시험 답안 템플릿

## 핵심 인사이트 (3줄 요약)

> 1. **본질**: 화이트박스는 코드 내부 논리 구조를 검증하는 구조 기반 테스팅이며, 블랙박스는 입출력 결과와 요구사항을 검증하는 명세 기반 테스팅이다.
> 2. **가치**: 화이트박스는 논리적 결함과 데드코드(Dead code)를 색출하고, 블랙박스는 요구사항 누락과 기능적 오류를 사용자 관점에서 색출한다.
> 3. **판단 포인트**: 두 기법의 시각적 비교(구조 vs 명세), 주 수행 단계(단위 vs 시스템), 그리고 각각에 사용되는 구체적인 세부 기법(구문/분기 vs 동치분할/경곗값)을 짝지어 대비해야 한다.

## 출제 의도 및 답안 포인트

| 출제 의도 | 반드시 짚을 핵심 | 감점 회피 포인트 |
|:---|:---|:---|
| 구조 기반과 명세 기반의 차이 이해 | 내부 로직(제어흐름) vs 요구 명세(입출력) 비교 | 둘을 독립적/배타적 관계로 서술 (상호보완적임) |
| 세부 테스팅 기법 분류 역량 | 화이트박스(구문/분기/경로), 블랙박스(동치/경계/상태전이) 명시 | 세부 기법을 반대로 매핑하는 실수 |
| 실무 적용 단계의 매핑 | 단위 테스트(개발자) -> 화이트박스, 시스템/인수(QA) -> 블랙박스 | 단순히 기법 이름만 나열하고 목적을 누락 |

> 요약: 대상의 내부를 투명하게 보느냐(구조 제어 흐름), 불투명하게 보느냐(입출력 명세)의 관점 차이를 세부 기법과 함께 명확히 대비시킨다.

## Ⅰ. 개요 및 필요성

- 개요: 소프트웨어 결함을 도출하기 위해, 내부 소스코드 구조 기반으로 검증하는 화이트박스와 사용자 요구사항 명세 기반으로 검증하는 블랙박스 테스트 기법
- 배경: 내부 코드만 테스트하면 명세 누락을 찾지 못하고, 외부 입출력만 테스트하면 복잡한 내부 논리(Hidden path) 오류를 발견하기 어려움
- 필요성: 모듈 내 세밀한 논리 오류(오버플로우, 무한루프) 제거와 비즈니스 기능의 무결성을 동시에 확보하여 종합적인 품질 보증 달성

## Ⅱ. 구조 및 구성요소

```text
[화이트박스 테스트 관점]                [블랙박스 테스트 관점]
+-------------------------+         요구사항 명세서 (Specification)
| if (A > 10) { ... }     |           |
| else if (B < 5) { ... } |  입력  +---------+  출력
| while (C) { ... }       | -----> | Black-  | -----> 기대 결과 비교
| return D;               |        | Box     |
+-------------------------+        +---------+
 (제어 흐름도, 조건/분기)             (내부 로직은 은닉됨)
```

| 기법 유형 | 검증 대상 및 기준 | 주 수행 주체 및 단계 |
|:---|:---|:---|
| 화이트박스 (구조 기반) | 소스코드의 논리 경로, 분기, 조건, 루프 | 개발자 중심 / 단위 테스트 |
| 블랙박스 (명세 기반) | 요구사항 명세, 사용자 인터페이스 입출력 | 독립 QA, 사용자 / 시스템·인수 테스트 |
| 그레이박스 (혼합형) | 내부 구조 일부 인지 + 시스템 명세 결합 | 통합 테스트 |

> 요약: 화이트박스는 How(어떻게 구현되었나)를 따지고, 블랙박스는 What(무엇이 출력되나)을 따지는 상호보완적 프레임워크다.

## Ⅲ. 동작원리 및 세부 기법

**1. 화이트박스 테스트 세부 기법 (경로와 조건 기반)**
- [구문 커버리지(Statement)]: 프로그램 내의 모든 문장(Line)을 최소 한 번씩 실행되게 입력값 설계
- [분기 커버리지(Branch)]: if/while 등의 분기 조건이 참(True)과 거짓(False)을 최소 한 번씩 타도록 설계
- [조건 커버리지(Condition)]: 개별 조건식(예: A>0, B<0)이 각각 참/거짓을 갖도록 논리 조합 설계
- [경로 테스트(Path)]: 제어 흐름 그래프(CFG)를 그려 독립적인 수행 경로를 수학적으로 모두 순회

**2. 블랙박스 테스트 세부 기법 (입력값 그룹화 기반)**
- [동치 분할(Equivalence Partitioning)]: 입력 도메인을 결과가 같을 것으로 예상되는 유효/무효 클래스로 분할하여 대푯값만 테스트
- [경곗값 분석(Boundary Value Analysis)]: 동치 클래스의 경계(Boundary)에서 오류가 가장 많이 발생함을 이용해 경곗값(+1, 0, -1) 집중 테스트
- [상태 전이 테스트(State Transition)]: 시스템의 상태(State)와 상태를 변환시키는 이벤트 모델링 기반 검증
- [결정표(Decision Table) 테스트]: 다중 조건 논리 조합을 표 형태로 매핑하여 누락된 조건 규칙 검증

> 요약: 화이트박스는 커버리지율을 높이는 논리 조합으로, 블랙박스는 테스트 케이스 수를 최적화하는 입력값 그룹화로 동작한다.

## Ⅳ. 특징
- [화이트박스 - 강점]: 내부의 불필요한 코드(Dead Code)나 은닉된 보안 취약점을 정확히 짚어내고 디버깅이 쉬움
- [화이트박스 - 한계]: 요구사항 명세 자체가 누락되어 아예 구현되지 않은 기능은 코드가 없으므로 절대 찾을 수 없음
- [블랙박스 - 강점]: 코드 지식이 없는 도메인 전문가나 고객이 직접 수행 가능하며 명세 결함 발견에 탁월함
- [블랙박스 - 한계]: 100% 완벽한 테스트를 하려면 무한한 입력 조합이 필요하므로(불가능), 모든 내부 분기가 실행되었는지 보장 못함

> 요약: 두 기법은 서로의 맹점(구현 누락 vs 숨은 논리 오류)을 완벽히 상호 보완한다.

## Ⅴ. 심화 비교 및 적용 판단

| 비교 축 | 화이트박스 테스트 | 블랙박스 테스트 | 상호보완 전략 |
|:---|:---|:---|:---|
| 접근 방식 | 소스코드 구조 기반(Structural) | 요구 명세 기반(Functional) | V-모델 계층 교차 |
| 결함 종류 | 논리 에러, 루프 에러, 문법/타입 오류 | 기능 누락, 인터페이스 에러, 성능 오류 | 구현 오류+명세 오류 동시 차단 |
| 테스트 커버리지 | 정량적 커버리지 측정 가능(80% 등) | 요구사항 추적 매트릭스(RTM)로 측정 | 정량(코드) + 정성(명세) 만족도 보장 |

> 요약: 개발 초기(단위)에는 화이트박스로 논리 견고성을 챙기고, 통합 이후에는 블랙박스로 비즈니스 무결성을 검증하는 파이프라인이 필수다.

**리스크·대응:**
- [테스트 케이스 폭발]: 화이트박스의 모든 경로, 블랙박스의 모든 조합 시도 시 시간/비용 초과 → 화이트박스는 MC/DC(조건분기 혼합) 기법으로, 블랙박스는 직교 배열(Orthogonal Array) 기법으로 TC 개수 최적화 (지표: TC 개수 대비 결함 발견율)
- [기능 누락 방치]: 개발자가 짠 코드만 화이트박스 커버리지 100%를 달성하고 명세 결함을 방치 → 요구사항 추적 매트릭스(RTM)와 블랙박스 TC를 1:1 매핑하여 양방향 추적성 강제 (지표: 명세 기반 결함 유출률)

## Ⅵ. 실무 적용 및 결론

**적용 방안 3개:**
1. 기법별 담당자 및 단계 분리: 개발팀은 TDD와 SonarQube를 활용해 화이트박스 기반 분기 커버리지 80% 이상을 단위 단계에서 달성하도록 강제
2. 동치분할 + 경곗값 분석 우선 적용: QA팀은 블랙박스 테스팅 시, 무작위 입력(Ad-hoc)이 아닌 경곗값 분석을 최우선 적용하여 치명적인 Off-by-one 버그를 집중 색출
3. 그레이박스 테스팅 도입: API 서버 테스트 시, 블랙박스처럼 REST API 입출력을 테스트하되, DB나 로그 내부 데이터를 함께 모니터링하여(화이트박스 지식) 데이터 무결성을 동시 검증

**결론 (2줄):**
- 기술사 판단: 완벽한 소프트웨어 품질 보증을 위해서는 화이트박스의 "코드 투명성"과 블랙박스의 "명세 지향성" 중 어느 하나라도 결여되어서는 안 된다.
- 향후 방향: 최근 AI 기반 테스트 자동화 도구들이 화이트박스(제어 흐름 분석)와 블랙박스(퍼징, Fuzzing) 기법을 융합하여 스스로 TC를 생성하는 방향으로 진화 중이다.
