## Ⅰ. 개요
- 정의: 시스템 설계 시 데이터 구조를 우선할지, 업무 흐름을 우선할지에 대한 접근법
- 배경: 비즈니스 로직의 변동성과 데이터의 영속성 사이의 트레이드오프 발생
- 출제 의도: 설계 방식에 따른 아키텍처 특성 및 적합한 도메인 판단 능력 평가

## Ⅱ. 구성요소
- 구조도
  [Data Centric]    vs    [Process Centric]
  DB/Schema 중심           Work Flow/Logic 중심
  (Entity 기반)            (Action 기반)

- 구성요소 표
| 구성요소 | 설명 | 비유 |
| :--- | :--- | :--- |
| 데이터 중심 | DB 스키마 설계 후 애플리케이션 개발 | 서류 보관함(Index) |
| 프로세스 중심 | 업무 흐름(Flow) 정의 후 데이터 정의 | 컨베이어 벨트 |
| 하이브리드 | 데이터의 안정성과 프로세스 유연성 결합 | 스마트 팩토리 |
> 요약: 데이터 중심은 무결성에, 프로세스 중심은 비즈니스 흐름 변화에 강점

## Ⅲ. 절차
- 흐름도
  도메인 분석 -> 관점 선택 -> 모델링 -> 검증/확정
- 4단계 설명
1. 도메인 분석: 요구사항 내의 핵심 개체와 프로세스 식별
2. 관점 선택: 시스템 성격(정보계/운영계 등)에 따른 우선순위 결정
3. 모델링: ERD(데이터) 또는 Activity Diagram(프로세스) 작성
4. 검증/확정: 비즈니스 시나리오를 통한 모델의 완결성 및 적합성 검토
> 요약: 시스템의 영속성과 변화 빈도를 고려한 최적의 모델링 관점 적용

## Ⅳ. 문제점
- 데이터 중심: 로직이 여러 프로그램에 분산되어 비즈니스 변경 시 수정 범위 확대
- 프로세스 중심: 데이터 중복 발생 및 일관성 유지의 어려움, 성능 저하 가능성

## Ⅴ. 개선방안
- 데이터 중심: 공통 비즈니스 로직의 서비스 레이어 집중화 (Encapsulation)
- 프로세스 중심: 마스터 데이터 관리(MDM) 도입 및 표준화된 데이터 모델링 병행

## Ⅵ. 전망
- 클라우드 기반 EDA(Event Driven Architecture)에서 두 관점의 융합 가속화
- CSF: 도메인 주도 설계(DDD)를 통한 데이터와 행위의 유기적 결합 지향
