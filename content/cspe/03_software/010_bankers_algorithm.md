# 📖 【암기용】 개념 완전 이해

## 한눈에
- **정의**: 다익스트라(Dijkstra)가 제안한 데드락 **회피(Avoidance)** 알고리즘으로, 자원을 할당하기 전 **'안전 상태(Safe State)'**가 유지되는지 사전에 검사하는 기법.
- **핵심 직관**: 은행의 대출 심사. 모든 고객이 빌려달라는 최대 금액을 다 빌려줘도 은행이 망하지(데드락) 않고 모두에게 빌려줬다 돌려받을 수 있는 순서가 있는지 확인하고 대출을 해주는 것.
- **핵심 변수**:
    - **Available**: 현재 남은 자원량.
    - **Max**: 프로세스별 최대 요구량.
    - **Allocation**: 현재 할당된 양.
    - **Need**: 추가로 더 필요한 양 ($Need = Max - Allocation$).

## 깊이 이해
- **안전 상태 (Safe State)**: 모든 프로세스가 정상적으로 종료될 수 있는 **'안전 순서(Safe Sequence)'**가 하나라도 존재하는 상태.
- **불안전 상태 (Unsafe State)**: 데드락이 발생할 **가능성**이 있는 상태. (반드시 데드락은 아니지만 위험함)
- **작동 방식**:
    1. 프로세스가 자원 요청을 함.
    2. 빌려줬을 때를 가정하여 가상으로 할당함.
    3. 남은 자원(Available)으로 누군가의 Need를 채울 수 있는지 확인.
    4. 그놈이 끝나서 자원을 반납하면 Available이 늘어남.
    5. 이 과정을 반복해서 모든 프로세스가 끝날 수 있으면 '승인', 아니면 '대기'.

## 연결 개념
- **Deadlock (009)**: 해결 전략 중 '회피'에 해당함.
- **Dijkstra**: 이 알고리즘의 창시자이자 세마포어의 창시자.
- **Resource Allocation Graph (009)**: 자원이 한 종류일 때 쓰는 방식. 은행원은 자원이 여러 종류일 때 씀.

# 📝 【답안용】 시험 답안 템플릿

## 핵심 인사이트 (3줄 요약)
> 1. **본질**: 자원 할당 요청 시 시스템을 **안전 상태(Safe State)**로 유지할 수 있는지를 시뮬레이션하여 교착상태를 원천 차인하는 **동적 회피 알고리즘**임.
> 2. **기술적 핵심**: $Max, Allocation, Available, Need$의 4가지 행렬을 이용하며, 모든 프로세스가 자원을 반납할 수 있는 **안전 순서(Safe Sequence)** 존재 여부를 판단함.
> 3. **현실적 한계**: 프로세스 수와 최대 자원 요구량을 미리 알아야 하므로 오버헤드가 크며, 실제 범용 OS보다는 자원 관리가 엄격한 특수 시스템에 적합함.

## Ⅰ. 데드락 회피의 정수, 은행원 알고리즘의 개요
- **정의**: 리소스 할당 시 시스템이 항상 안전 상태에 머무르도록 제어하여 교착상태를 피하는 알고리즘.
- **기본 가정**: 
    - 각 프로세스의 최대 자원 요구량을 미리 알아야 함.
    - 프로세스 수는 고정되어야 함.
    - 자원 인스턴스 수는 유한함.

## Ⅱ. 은행원 알고리즘의 핵심 자료구조 및 수식

### 1. 4대 핵심 변수 (Data Structures)
| 변수명 | 의미 | 수식/설명 |
|:---:|:---|:---|
| **Available** | 가용 자원 | 현재 사용 가능한 각 자원의 종류별 개수 ($1 \times m$ 벡터) |
| **Max** | 최대 요구 | 각 프로세스가 필요로 하는 최대 자원 수 ($n \times m$ 행렬) |
| **Allocation** | 현재 할당 | 각 프로세스에 현재 할당된 자원 수 ($n \times m$ 행렬) |
| **Need** | 추가 필요 | 각 프로세스가 향후 더 요청할 자원 수 ($n \times m$ 행렬) |

### 2. 기본 관계식
- $Need[i, j] = Max[i, j] - Allocation[i, j]$
- 할당 후 $Available = Available - Request$

## Ⅲ. 알고리즘 동작 절차 (안전성 검사)

1. **초기화**: $Work = Available$, $Finish[i] = false$ (모든 프로세스).
2. **조건 탐색**: $Finish[i] == false$ 이면서 $Need_i \le Work$ 인 프로세스 $P_i$를 찾음.
3. **가상 실행 및 자원 회수**:
    - 찾았다면: $Work = Work + Allocation_i$, $Finish[i] = true$, 2단계로 이동.
    - 못 찾았다면: 4단계로 이동.
4. **결과 판단**: 모든 $i$에 대해 $Finish[i] == true$ 이면 **Safe State (안전)**, 하나라도 $false$면 **Unsafe State (불안전)**.

## Ⅳ. 안전 상태(Safe)와 불안전 상태(Unsafe)의 관계도

```text
┌──────────────────────────────────────┐
│          시스템 전체 상태             │
│  ┌──────────────────────────────┐    │
│  │        안전 상태 (Safe)       │    │ ◀── 데드락 절대 안 걸림
│  └──────────────────────────────┘    │
│  ┌──────────────────────────────┐    │
│  │      불안전 상태 (Unsafe)      │    │ ◀── 데드락 가능성 존재
│  │   ┌────────────────────────┐ │    │
│  │   │  교착 상태 (Deadlock)   │ │    │ ◀── 실제 데드락 발생
│  │   └────────────────────────┘ │    │
│  └──────────────────────────────┘    │
└──────────────────────────────────────┘
```

## Ⅴ. 은행원 알고리즘의 장점 및 한계

- **장점**:
    - 데드락 예방(Prevention)보다 자원 이용률이 높음.
    - 시스템 안정성을 수학적으로 보장함.
- **한계 (비현실성)**:
    - **정보 부족**: 프로세스가 시작할 때 최대 자원량을 선언하는 것이 실무적으로 어려움.
    - **오버헤드**: 자원 요청 시마다 안전성 검사 루프를 돌려야 함 (성능 저하).
    - **고정성**: 실행 중에 자원 총량이 바뀌거나 프로세스가 수시로 추가/삭제되는 환경에 취약.

## Ⅵ. 기술사 관점의 결론 및 제언
- 은행원 알고리즘은 현대 OS에서 직접 구현되기보다는, **자원 관리의 이론적 토대**로서 큰 의미를 가짐.
- **실무 제언**: 복잡한 분산 시스템이나 클라우드 인프라 자원 할당 시, 이 알고리즘의 개념을 응용하여 **Quota(쿼터) 관리** 및 **Admission Control(입입 제어)**을 수행함으로써 시스템 붕괴를 사전에 방지하는 전략이 필요함.
