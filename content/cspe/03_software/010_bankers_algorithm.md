# 📖 【암기용】 개념 완전 이해

## 한눈에
- **개요**: 은행원 알고리즘(Banker's Algorithm)은 다익스트라가 제안한 **교착상태 회피(Avoidance)** 기법으로, 자원 요청을 승인했을 때 시스템이 여전히 **안전 상태(Safe State)**를 유지하는 경우에만 할당을 허가한다.
- **왜 필요한가**: 교착 예방(009 참조)은 코프만 조건을 원천 차단해 자원 활용을 크게 희생한다. 은행원 알고리즘은 조건은 그대로 둔 채, 각 프로세스가 최대로 쓸 자원량(Max)을 미리 선언받아 **요청마다 안전한지 계산**함으로써 교착을 피하면서도 자원을 더 유연하게 쓴다.
- **핵심 직관**: 은행이 대출을 내줄 때, 모든 고객이 한도까지 인출해도 은행이 결국 모두를 만족시킬 현금 순서가 있으면 대출을 승인하고, 그 순서가 깨지면 거절하는 것과 같다. "지금 빌려줘도 결국 모두 갚게 만들 수 있는가"를 매번 따진다.

## 핵심 용어 정리 (내부에 등장하는 것들)

아래 답안용의 4대 행렬과 안전성 판정에 쓰는 모든 표기·계산식을 비유와 함께 먼저 세운다. 맨 위가 이 주제의 상위 핵심 키워드다.

| 용어/표기 | 의미 | 비유·예 |
|:---|:---|:---|
| 은행원 알고리즘 (상위 키워드) | 안전 상태 유지 시에만 자원을 할당하는 회피 기법 | 갚을 수 있을 때만 대출 승인하는 은행 |
| 안전 상태 (Safe State) | 모든 프로세스를 끝까지 실행시킬 순서가 하나 이상 존재 | 결국 모두 대출 상환 가능한 자금 배치 |
| 불안전 상태 (Unsafe State) | 그런 순서가 없음(교착은 아니나 위험 지대) | 잘못하면 부도날 수 있는 자금 상태 |
| 안전 순서 (Safe Sequence) | 자원 부족 없이 순차 완료 가능한 프로세스 나열 | 갚을 사람부터 차례로 회수하는 순번 |
| Available (가용 벡터) | 현재 할당 가능한 자원 여유분 (자원 유형별) | 은행 금고에 남은 현금 |
| Max (최대 요구 행렬) | 각 프로세스가 최대로 요구할 자원량 | 고객별 대출 한도 |
| Allocation (할당 행렬) | 각 프로세스에 현재 배정된 자원량 | 고객이 이미 빌린 금액 |
| Need (요구 행렬) | Need = Max − Allocation, 앞으로 더 필요할 양 | 한도까지 더 빌릴 수 있는 잔여 |
| Request (요청 벡터) | 특정 프로세스가 지금 새로 요청한 자원량 | 고객이 지금 추가로 신청한 대출액 |
| Work (작업 벡터) | 안전성 검사 중 회수된 자원을 누적하는 임시 가용분 | 회수되며 다시 채워지는 금고 |
| Finish (완료 플래그) | 각 프로세스의 완료 가능 여부 표시 | 상환 완료 체크리스트 |
| ≤ (벡터 비교) | 모든 자원 유형에서 좌변 ≤ 우변일 때 성립 | 모든 화폐 종류에서 부족하지 않음 |

## 깊이 이해
- **배경·문제의식**: 교착 예방은 확실하지만 "혹시 모를 상황"까지 막느라 자원을 놀린다. 다익스트라는 프로세스가 시작 전 **자신의 최대 자원 요구(Max)를 선언**할 수 있다는 가정을 두면, 매 요청마다 "이걸 줘도 최악의 경우 모두 완료 가능한가"를 계산해 위험한 요청만 거절할 수 있음을 보였다. 이것이 회피이며, 은행원 알고리즘이 그 대표 구현이다.
- **작동 원리(어떻게+왜)**: 두 개의 절차로 구성된다.
  - **안전성 알고리즘(Safety Algorithm)**: 현재 상태가 안전한지 판정한다. Work=Available로 시작해, Need ≤ Work인 미완료 프로세스를 찾아 그 Allocation을 Work에 더하고(완료 후 자원 반납 가정) Finish=true 처리하는 것을 반복한다. 모든 프로세스가 Finish=true면 안전 상태이며, 그 완료 순서가 안전 순서다.
  - **자원 요청 알고리즘(Resource-Request Algorithm)**: 요청이 오면 ① Request ≤ Need, ② Request ≤ Available를 확인한 뒤, 자원을 **가상으로 할당**(Available−Request, Allocation+Request, Need−Request)하고 안전성 알고리즘을 돌린다. 안전하면 실제 승인, 불안전하면 원상 복구 후 대기시킨다.
- **비유**: 은행원이 대출 신청을 받을 때마다, 모든 고객이 한도까지 빌린 최악의 상황을 가정하고 "그래도 한 명씩 갚게 만들어 전부 회수할 순번이 있는가"를 시뮬레이션한다. 순번이 있으면 승인, 없으면 보류다.
- **구체 예시(안전 순서 계산)**: 자원 A·B·C 총량이 (10,5,7)이고 프로세스 P0~P4가 있다. Allocation과 Max가 주어지면 Need=Max−Allocation으로 구한다. Available=(3,3,2)에서 시작해 Need≤Work를 만족하는 P1을 먼저 완료시켜 그 Allocation을 Work에 더하고, 이어 P3·P4·P0·P2가 차례로 완료 가능하면 안전 순서 <P1,P3,P4,P0,P2>가 나온다. 이런 순서가 하나라도 존재하면 현 상태는 안전이다.
- **흔한 오해·주의점**: (1) **불안전 상태 ≠ 교착**이다. 불안전은 교착으로 갈 수 *있는* 위험 지대일 뿐, 아직 교착은 아니다(009 참조). (2) 안전 순서는 **여러 개일 수 있고**, 하나만 찾으면 안전 판정으로 충분하다. (3) 실무 범용 OS는 은행원을 거의 안 쓴다 — 프로세스가 Max를 미리 알기 어렵고, 매 요청 O(m·n²) 계산 비용이 실이득보다 커서다. 자원 종류·수가 고정된 RTOS·임베디드에서 제한적으로 쓰인다.

## 연결 개념
- 교착상태(009 참조) — 은행원은 그 4대 전략 중 회피의 대표 구현이며 코프만 조건이 배경
- 기아와 에이징(011 참조) — 요청이 계속 불안전으로 판정돼 특정 프로세스가 밀리면 기아로 이어질 수 있음
- 자원 할당 그래프(RAG) — 자원 인스턴스가 1개뿐일 때 쓰는 회피 기법(은행원은 다중 인스턴스용)

# 📝 【답안용】 시험 답안 템플릿

## 핵심 인사이트 (3줄 요약)

> 1. **본질**: 은행원 알고리즘은 자원 요청 승인 후에도 안전 상태(안전 순서 존재)가 유지될 때만 할당하는 교착 회피 기법임.
> 2. **가치**: Max 사전 선언을 전제로 Need·Available를 계산해, 예방보다 자원 활용을 높이면서 교착을 사전 차단함.
> 3. **판단 포인트**: 매 요청 O(m·n²) 계산과 Max 사전 파악이 필요해, 자원 구성이 고정된 실시간·임베디드에 한정 적용함.

## 출제 의도 및 답안 포인트

| 출제 의도 | 반드시 짚을 핵심 | 감점 회피 포인트 |
|:---|:---|:---|
| 안전 상태 개념 이해 | 안전 순서 존재 여부로 안전/불안전 판정 | 불안전과 교착 동일시 |
| 4대 행렬과 계산 절차 | Available·Max·Allocation·Need=Max−Allocation | Need 산출식 누락 |
| 회피의 적용 한계 판단 | Max 사전 선언·O(m·n²) 계산 비용 | 범용 OS 상시 적용으로 단정 |

> 요약: 안전 순서 계산 절차를 정확히 제시하고, Max 선언 전제와 계산 비용이라는 적용 한계까지 판단으로 연결함.

## Ⅰ. 개요 및 필요성

- 개요: 자원 할당 후에도 안전 상태를 유지할 때만 승인하는 교착 회피 알고리즘임
- 배경: 교착 예방(009 참조)은 자원 활용을 과도하게 희생해 조건 유지형 회피 기법이 요구됨
- 필요성: 프로세스의 최대 요구(Max)를 미리 알면 요청별 안전성 계산으로 교착을 사전 차단 가능함

## Ⅱ. 구조 및 구성요소

선형 구조도 (4대 자료구조의 관계, m=자원 유형 수, n=프로세스 수):

    Max(n×m) - Allocation(n×m) = Need(n×m)
    총자원 - Σ Allocation = Available(1×m)
      -> 안전성 판정: Work(=Available) + 완료 프로세스의 Allocation 누적

| 구성요소 | 역할 | 특이사항 |
|:---|:---|:---|
| Available | 자원 유형별 현재 가용량 벡터 | 프로세스 완료 시 Allocation만큼 회수·증가 |
| Max | 프로세스별 최대 자원 요구 행렬 | 시작 전 사전 선언 필요(핵심 전제) |
| Allocation | 프로세스별 현재 할당 행렬 | 실제 점유 중인 자원량 |
| Need | Max − Allocation, 잔여 요구 행렬 | 안전성 검사의 비교 기준(Need ≤ Work) |

> 요약: 핵심은 Need=Max−Allocation과 Available이며, 이 둘의 비교로 완료 가능 프로세스를 판별함.

## Ⅲ. 동작원리 및 흐름도

선형 흐름도 (요청 처리 -> 안전성 검사):

    프로세스 Request 발생
      -> ① Request ≤ Need ? (아니면 오류: 선언 한도 초과)
      -> ② Request ≤ Available ? (아니면 대기: 자원 부족)
      -> 가상 할당(Available-=Req / Allocation+=Req / Need-=Req)
      -> 안전성 알고리즘 실행 -> 안전이면 승인 / 불안전이면 원복 후 대기

- 1단계 [요청 검증]: 스케줄러(은행원)가 요청 프로세스의 Request가 Need·Available를 모두 초과하지 않는지 확인함
- 2단계 [가상 할당]: 자원을 임시로 배정해 Available·Allocation·Need 세 행렬을 갱신함
- 3단계 [안전성 검사]: Work=Available로 두고 Need ≤ Work인 미완료 프로세스를 반복 선택해 그 Allocation을 Work에 누적함
- 4단계 [판정]: 모든 프로세스가 완료(Finish=true)되면 안전 순서 확정 후 요청을 승인하고, 불가하면 상태를 원복해 요청을 대기시킴

> 요약: 요청을 가상 반영한 뒤 안전 순서 존재 여부를 시뮬레이션해, 존재할 때만 실제 할당을 확정함.

## Ⅳ. 특징

- 낙관과 보수의 중간: 예방보다 자원 활용이 높고 탐지보다 안전하나, 매 요청 계산 비용을 지불함
- Max 사전 선언 전제: 프로세스가 최대 요구를 미리 알려야 성립해 동적 워크로드에 부적합함
- 다중 인스턴스 대응: 자원 유형별 여러 개(인스턴스)를 다뤄 RAG 방식보다 일반적임
- 계산 복잡도: 1회 안전성 검사가 O(m·n²)로 프로세스·자원 증가 시 부담이 큼
- 불안전 ≠ 교착: 불안전 판정은 위험 회피일 뿐 실제 교착 발생과 구별됨

## Ⅴ. 심화 비교 및 적용 판단

교착 회피의 두 대표 기법인 은행원 알고리즘과 자원 할당 그래프(RAG) 기법을 인스턴스·판정 방식 축으로 대조함(예방·탐지 전체 비교는 009 참조).

| 구분 | 은행원 알고리즘 | 자원 할당 그래프(RAG) 기법 |
|:---|:---|:---|
| 자원 인스턴스 | 유형별 다중 인스턴스 지원 | 유형별 단일 인스턴스만 가능 |
| 판정 방식 | 안전성 알고리즘(안전 순서 존재 계산) | 예약 간선(claim edge) 순환 검사 |
| 계산 복잡도 | O(m·n²)로 상대적 고비용 | 순환 탐지 O(n²)로 경량 |
| 적용 전제 | Max 행렬 사전 선언 필수 | 최대 요구를 예약 간선으로 사전 표현 |

> 요약: 자원 인스턴스가 여럿이면 은행원, 유형별 1개뿐이면 경량 RAG 기법을 택하며 둘 다 Max 사전 파악이 전제임.

**리스크·대응:**
- Max 과다 선언 — 안전 여유 확보 위해 한도를 부풀리면 가용 자원이 놀아 활용률 저하 — 실측 사용량 기반으로 Max 현실화
- 계산 오버헤드 — 요청 빈번 시 O(m·n²) 반복으로 지연 증가 — 자원 종류·프로세스 수가 고정된 환경에만 적용
- 지속적 거절로 인한 기아 — 특정 프로세스 요청이 반복 불안전 판정으로 밀림 — 에이징 병행으로 대기 시간 반영(011 참조)

**점검 지표:**
- 성능: 요청당 안전성 검사 시간, 요청 거절(대기) 비율
- 운영: 자원 평균 활용률, 안전 순서 산출 실패 빈도

## Ⅵ. 실무 적용 및 결론

**적용 방안:**
1. 실시간·임베디드 자원 관리: 자원 종류·수가 컴파일 타임에 고정된 RTOS에서 태스크별 Max를 선언해 안전성 기반 승인 적용
2. 정적 자원 풀 제어: DB 커넥션 풀·스레드 풀처럼 상한이 명확한 자원에 한해 요청 시 안전 상태 검사를 근사 적용
3. 대안 병행: 범용 시스템은 은행원 대신 lock timeout·순환 탐지(009 참조)로 대체하고, 은행원은 자원 고정 구간에만 국소 적용

**결론:**
- 기술사 판단: 자원 구성이 고정되고 Max를 알 수 있으면 은행원으로 사전 회피하고, 동적·대규모 시스템은 탐지·복구가 경제적임
- 향후 방향: 프로세스별 최대 요구를 정적으로 알기 어려운 클라우드·컨테이너 환경 확산으로, 사전 회피보다 타임아웃·재시도 기반 낙관적 해소가 주류로 자리 잡음
