## Ⅰ. 개요
- 네트워크 상의 다른 컴퓨터에 있는 함수나 객체를 로컬 함수처럼 호출하는 기술임
- 분산 시스템의 통신 복잡성을 숨기고 위치 투명성을 제공하는 것이 목적임
| 구분 | 내용 | 비유 |
| --- | --- | --- |
| 출제의도 | 스텁(Stub)과 스켈레톤(Skeleton), 마샬링, 언어 독립성 vs 자바 종속성 | 국제 전화 통화 |

## Ⅱ. 구성요소
- 호출 대행자인 Stub과 실제 실행 대행자인 Skeleton으로 구성됨
[Client] -> [Stub] --(Network)-- [Skeleton] -> [Server Method]
- 구성요소 표
| 구성요소 | 설명 | 비유 |
| --- | --- | --- |
| Stub | 클라이언트 측 대행자로 파라미터 직렬화 및 전송 담당 | 해외 지사 대리인 |
| Skeleton | 서버 측 대행자로 수신 데이터 역직렬화 및 실제 함수 호출 | 본사 현지 안내원 |
| 마샬링(Marshaling) | 데이터를 전송 규격(바이트 스트림)으로 변환하는 과정 | 수출품 포장 |
> 요약: RPC는 원격 프로시저 인터페이스를 호출하고 RMI는 자바 원격 객체의 메서드를 호출함

## Ⅲ. 절차
- 원격 호출의 요청 및 응답 메커니즘임
[로컬 호출] -> [Stub 마샬링] -> [원격 실행] -> [결과 언마샬링]
- 4단계 설명
1) 대행자 생성: 인터페이스 정의를 기반으로 Stub과 Skeleton 소스를 생성함
2) 데이터 패킹: 클라이언트 인자를 바이너리 형식으로 변환(Marshaling)하여 전송함
3) 네트워크 전달: TCP/IP 등 프로토콜을 통해 서버 측 포트로 데이터 전달함
4) 결과 리턴: 서버 실행 결과를 다시 패킹하여 클라이언트에 전달 후 반환함
> 요약: 네트워크 통신 코드를 개발자가 직접 작성하지 않고 자동 생성된 대행자를 활용함

## Ⅳ. 문제점
- 네트워크 지연(Latency) 및 불안정성으로 인한 예외 처리가 복잡함 (원인: 분산 환경)
- RMI의 경우 자바 환경에만 국한되어 이기종 언어 간 연동이 제한적임 (원인: 플랫폼 종속)

## Ⅴ. 개선방안
- (단기) 타임아웃 및 재시도(Retry) 로직을 통해 통신 안정성 보완함
- (중기) 언어 간 연동과 스트리밍이 필요하면 HTTP/2와 Protocol Buffers 기반 gRPC를 적용함
- (장기) 서비스 디스커버리와 연계하여 유동적인 엔드포인트에 대한 호출 자동화함

## Ⅵ. 전망
- 마이크로서비스 간의 고속 통신을 위해 REST API를 대체하는 RPC 기술이 재부각될 것임
- AI 모델 추론 서비스를 위한 원격 호출 최적화 및 보안 채널(mTLS) 적용이 CSF가 될 것임
