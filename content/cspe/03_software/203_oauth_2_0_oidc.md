## 핵심 인사이트 (3줄 요약)
- **OAuth 2.0은 "네이버 아이디로 로그인"할 때, 내 비밀번호를 생판 모르는 쇼핑몰에 주지 않고도, 쇼핑몰이 내 네이버 정보(권한)를 쓰도록 허락해 주는 '권한 위임(Authorization)' 표준**임.
- **OIDC(OpenID Connect)**는 OAuth 2.0 위에 올라탄 **'신원 인증(Authentication)' 표준**임. "네가 권한을 위임한 건 알겠고, 그래서 네 진짜 정체(ID)가 뭔데?"를 알려주기 위해 JWT(ID 토큰)를 추가로 발급해 줌.
- "비밀번호는 구글/카카오만 알고 있고, 다른 서비스들은 구글이 발행한 출입증(Token)만 믿고 들여보낸다"는 현대 인터넷 페더레이션(SSO) 보안 아키텍처의 근간임.

## Ⅰ. 개요 및 필요성
- **개요**: OAuth 2.0은 서드파티 애플리케이션이 사용자의 비밀번호 없이도 리소스 자원에 접근할 수 있게 해주는 인가(Authorization) 프레임워크. OIDC는 그 위에 구축된 인증(Authentication) 레이어.
- **필요성**: 옛날엔 '싸이월드'에서 '다음 카페' 주소록을 불러오려면, 싸이월드에 내 다음 아이디와 **비밀번호를 통째로 입력**해야 했음. 싸이월드가 털리면 내 다음 계정도 다 털리는 미친 짓(Anti-pattern)이었음. **"아니, 내 비밀번호를 쌩판 모르는 앱에 주지 않고도, 구글 주소록만 살짝 읽어갈 수 있는 안전한 임시 출입증(토큰) 발급 시스템을 만들자!"**라며 OAuth가 등장함.
---
## Ⅱ. 아키텍처 및 핵심 원리
- **1. 핵심 등장인물 (4 Roles)**:
  - **Resource Owner (사용자)**: 나. 구글 계정의 주인.
  - **Client (클라이언트 앱)**: 내가 지금 쓰려는 '배달의민족' 앱. 내 구글 정보가 필요함.
  - **Authorization Server (인가 서버)**: 구글의 로그인 인증 서버. 여기서 출입증(토큰)을 찍어냄.
  - **Resource Server (리소스 서버)**: 구글의 주소록 서버. 출입증을 보여주면 데이터를 줌.
- **2. 통신 흐름 (Authorization Code Grant 방식)**:
  - 내가 배민 앱에서 `[구글로 로그인]` 버튼을 누름.
  - 화면이 **구글 사이트**로 확 넘어감. (배민은 내 비밀번호를 구경도 못 함!).
  - 구글 화면에서 내가 아이디/비번을 치고 "배민이 네 이름 가져간대, 허락해?"에 `[동의]` 누름.
  - 구글이 배민에게 교환권(Authorization Code)을 던져줌.
  - 배민 서버가 구글 서버 뒷문으로 교환권을 내밀고 진짜 **액세스 토큰(Access Token)**을 받아옴!
- **3. OIDC의 결합 (ID 토큰)**:
  - OAuth의 목적은 권한(사진첩 보기)이었지 로그인(누구냐?)이 아님.
  - 그래서 로그인 기능을 완벽히 지원하기 위해 OIDC가 추가됨. 구글은 액세스 토큰을 줄 때 **ID 토큰(JWT)**이라는 신분증명서도 같이 줌. 여기엔 "이 사람의 이름은 철수고 이메일은 ~이다"가 적혀 있음.

```text
[ OAuth 2.0의 작동 원리: 발렛파킹 비유 ]

 🚗 내 차(데이터)의 마스터 키(비밀번호)를 식당 발렛파킹 직원(서드파티 앱)에게 다 주면? 
 -> 직원이 트렁크도 열고 차를 훔쳐 갈 수 있음! 😱

 🔑 [ OAuth 2.0의 방식: 발렛 전용 키(Token) ]
 1. 내 차(구글)에는 마스터 키(비번)와 '발렛 전용 키(토큰)'가 따로 있음.
 2. 식당 직원(배민 앱)에게는 마스터 키를 숨기고, "운전석 문만 열고 주차만 가능"한 발렛 키(Access Token)만 줌.
 3. 식당 직원은 차를 옮길 수(정보 조회)는 있지만, 트렁크(비밀번호 변경 등 민감 기능)는 절대 열 수 없음! 🛡️
```

## Ⅲ. 비교 및 연결
| 구분 | OAuth 2.0 | OIDC (OpenID Connect) |
|---|---|---|
| **핵심 목적** | **인가 (Authorization, 권한 위임)** | **인증 (Authentication, 신원 확인)** |
| **질문의 성격**| "이 앱이 내 사진첩을 봐도 되나요?" | "이 앱에 접속한 너, 진짜 철수 맞니?" |
| **발급되는 것**| Access Token (불투명한 임시 문자열) | **ID Token (내용이 훤히 보이는 JWT 포맷)** |
| **비유** | 호텔 수영장 출입용 **카드키** | 내 얼굴과 이름이 적힌 **주민등록증** |
| **결합** | 현대의 `소셜 로그인`은 무조건 **[OAuth 2.0 통신망 + OIDC 신분증]**의 결합체임. |

## Ⅳ. 실무 적용 및 기술사 판단
- **SSO (Single Sign-On) 아키텍처 구축**: 사내에 지라, 슬랙, 인트라넷 등 20개의 시스템이 있을 때 비밀번호를 다 따로 관리하면 보안의 최약점이 됨. 기술사는 **Keycloak**이나 **Okta** 같은 OAuth 2.0/OIDC 기반의 중앙 인가 서버(IdP)를 구축하여, 단 한 번의 사내 계정 로그인만으로 20개 시스템을 다 패스할 수 있는 전사적 SSO 아키텍처를 수립해야 제로 트러스트(Zero Trust)의 기반이 됨.
- **Implicit Grant의 폐기**: 과거 SPA(React/Vue) 프론트엔드에서는 Authorization Code 교환 과정 없이 구글이 프론트엔드에 직접 토큰을 꽂아주는 `Implicit Grant` 방식을 많이 썼음. 하지만 URL 해킹을 통해 토큰이 탈취되는 사고가 폭증함. 현재 기술 표준은 프론트엔드에서도 무조건 `Authorization Code with PKCE` 방식을 써서 중간 탈취를 수학적으로 원천 차단하도록 아키텍처를 강제하고 있음.

## Ⅴ. 기대효과 및 결론
- "사용자의 패스워드를 서비스마다 흩뿌리지 말라"는 보안의 대원칙을 인터넷 전역에 실현한 가장 위대한 발명품.
- 개발자들은 복잡한 비밀번호 암호화나 보안 로직을 짤 필요 없이 구글/카카오에 인증을 외주(Outsourcing) 줄 수 있게 되어 서비스 개발 속도가 획기적으로 빨라짐.

### 📌 관련 개념 맵
- Authentication vs Authorization ➡️ JWT (JSON Web Token) ➡️ OAuth 2.0 ➡️ OIDC (OpenID Connect) ➡️ SSO (Single Sign-On)

### 📈 관련 키워드 및 발전 흐름도
- 쿠키/세션 기반의 고립된 로그인 ➡️ SAML (기업 간 XML 기반 복잡한 SSO) ➡️ 트위터가 주도한 OAuth 1.0 (암호화 너무 복잡함) ➡️ 간소화된 OAuth 2.0 대통합 ➡️ 인증 규격의 부재로 인한 혼란 ➡️ OIDC(JWT 결합)의 등장으로 완벽한 글로벌 표준 완성

### 👶 어린이를 위한 3줄 비유 설명
1. 친구 집에 놀러 가려면 우리 집 열쇠(비밀번호)를 친구에게 줘야 하는 이상한 상황이었어요. 친구가 잃어버리면 큰일 나죠!
2. **OAuth 2.0**은 우리 집 열쇠를 숨기고, "1시간만 방문 가능"이라고 적힌 **'임시 출입증(토큰)'**만 친구에게 주는 마법이에요.
3. **OIDC**는 그 출입증에 내 증명사진과 이름(ID 토큰)까지 쾅 박아서 "나 진짜 맞으니까 들여보내 줘!"라고 증명하는 거랍니다.
