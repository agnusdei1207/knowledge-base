# 📖 【암기용】 개념 완전 이해

## 한눈에
- **개요**: 애플리케이션에 비밀번호를 주지 않고도, 외부 서비스(구글/카카오)의 권한을 위임받는 인가 표준(OAuth 2.0)과 그 위에서 인증을 처리하는 표준(OIDC)
- **왜 필요한가**: 새로운 앱에 가입할 때마다 구글 아이디/비밀번호를 입력하면 계정 탈취 위험이 크다. 비밀번호를 넘기지 않고 "이 앱이 내 정보에 접근해도 좋다"는 허가증(토큰)만 발급하기 위해 필요하다.
- **핵심 직관**: OAuth 2.0은 '호텔 출입 카드키(권한 위임)'이고, OIDC는 '주민등록증(신원 확인)'이다. 

## 핵심 용어 정리

| 용어/표기 | 의미 | 비유·예 |
|:---|:---|:---|
| Resource Owner | 자신의 정보에 대한 접근을 허가하는 사용자 | 나 (카카오톡 사용자) |
| Client | 내 정보에 접근하려는 제3자 애플리케이션 | "당근마켓" 앱 |
| Authorization Server | 사용자 동의를 받고 토큰을 발급하는 인가 서버 | 카카오 로그인 화면 및 발급 서버 |
| Access Token | 권한을 증명하는 무작위 문자열 (OAuth 2.0) | 유효기간 있는 "호텔 방 출입 카드키" |
| ID Token | 사용자의 신원 정보(이름, 이메일 등)를 담은 토큰 (OIDC) | 위조 불가능한 "디지털 신분증" (JWT 형태) |

## 깊이 이해
- **배경·문제의식**: 예전에는 A서비스가 B서비스의 친구 목록을 가져오려면 A에게 B의 비밀번호를 알려줘야 했다. 이는 극히 위험하다. OAuth 2.0은 비밀번호 공유 없이 '인가(Authorization)'를 해결하기 위해 등장했다. 하지만 많은 기업이 OAuth 2.0을 '인증(Authentication, 로그인)'용도로 오용했고, 파편화를 막기 위해 OAuth 2.0 위에 인증 계층인 OpenID Connect(OIDC)를 표준화했다.
- **작동 원리 (Authorization Code Grant 기준)**:
  1. 클라이언트(당근마켓)가 사용자를 인가 서버(카카오)로 리다이렉트
  2. 사용자가 카카오 로그인 후 권한 동의
  3. 인가 서버가 클라이언트에게 임시 코드(Authorization Code) 반환
  4. 클라이언트 백엔드가 임시 코드를 인가 서버로 보내 Access Token(과 ID Token)으로 교환
  5. 클라이언트가 Access Token으로 리소스 서버(친구목록 DB)에서 데이터 조회
- **비유**: 대리인(클라이언트)을 구청(리소스 서버)에 보낼 때 내 인감도장(비밀번호)을 주지 않고, 동사무소(인가 서버)에서 '등본 발급용 위임장(Access Token)'만 받아 대리인에게 쥐여주는 것이다.
- **구체 예시**: 카카오로 로그인 시 "프로필 사진, 닉네임 접근에 동의하십니까?" 화면이 OAuth 2.0의 동의 과정이다. 승인 시 카카오는 당근마켓에 Access Token을 준다.
- **흔한 오해·주의점**: "OAuth 2.0은 인증(로그인) 프로토콜이다"는 명백한 오해다. OAuth 2.0은 인가(인가된 권한 위임) 전용이며, 신원을 확인하는 인증 기능은 없다. 신원 확인(SSO 로그인)은 ID Token을 발급하는 OIDC(OpenID Connect)의 역할이다. 

## 연결 개념
- **JWT (JSON Web Token)**: OIDC의 ID Token이나 OAuth 2.0의 토큰 포맷으로 널리 쓰이는 자체 증명 방식 토큰
- **SSO (Single Sign-On)**: 한 번의 로그인으로 여러 서비스를 이용하는 메커니즘 (OIDC를 통해 구현)
- **SAML (Security Assertion Markup Language)**: 기업 환경에서 주로 쓰이는 XML 기반의 레거시 인증/인가 표준

# 📝 【답안용】 시험 답안 템플릿

## 핵심 인사이트 (3줄 요약)

> 1. **본질**: OAuth 2.0은 타사 서비스에 대한 접근 권한을 위임하는 인가(Authorization) 표준이며, OIDC는 그 위에서 ID Token을 통해 신원을 인증(Authentication)하는 프로토콜이다.
> 2. **가치**: 크레덴셜(비밀번호) 공유 없는 안전한 API 연동과 마이크로서비스·클라우드 환경의 유연한 통합 인증(SSO) 기반을 제공한다.
> 3. **판단 포인트**: OAuth 2.0 단독으로 인증을 구현하는 안티패턴을 피하고, 보안 요구사항(기기 신뢰도)에 따라 4가지 Grant Type(특히 Authorization Code + PKCE)을 올바르게 선택해야 한다.

## 출제 의도 및 답안 포인트

| 출제 의도 | 반드시 짚을 핵심 | 감점 회피 포인트 |
|:---|:---|:---|
| 인가와 인증의 본질적 차이 이해 | 인가(OAuth2)=Access Token, 인증(OIDC)=ID Token 구분 | OAuth 2.0을 '인증 기술'로 서술하는 치명적 오류 |
| 프로토콜 동작 원리 및 롤 파악 | 4개 참여자(RO, Client, AS, RS), 인가 코드 부여 방식 | 주체와 서버의 역할을 혼동하여 절차를 역전 서술 |
| 최신 보안 적용 역량 및 통제 방안 | PKCE(Proof Key for Code Exchange) 기반 탈취 방어 | 레거시 Implicit 방식을 권장 기법으로 제시 |

> 요약: 비밀번호 노출 없는 권한 위임(OAuth 2.0)과 디지털 신분증 발급(OIDC)의 역할을 명확히 분리하고, 탈취 방지 아키텍처를 제시해야 한다.

## Ⅰ. 개요 및 필요성

- 개요: 크레덴셜 직접 제공 없이 제3자 클라이언트에게 자원 접근 권한을 위임하는 개방형 인가 표준(OAuth 2.0)과 이를 확장한 인증 계층(OIDC)
- 배경: 서비스 연동 시 사용자 비밀번호 직접 위탁으로 인한 크레덴셜 유출 위험 방지 및 표준화된 토큰 기반 API 제어 필요
- 필요성: 모바일/SPA 환경에서 안전한 SSO(Single Sign-On)를 구현하고, 권한 오남용을 방지하기 위한 토큰 생명주기 및 스코프 통제 필수

---

## Ⅱ. 구조 및 구성요소

```text
[Resource Owner] -> 동의/승인 -> [Authorization Server] -> 토큰 발급 -> [Client]
                                                                        | 
                                      [Resource Server] <- 토큰 제시 ---+
```

| 구성요소 | 역할 | 특이사항 |
|:---|:---|:---|
| Resource Owner (RO) | 자원에 대한 소유권을 가진 주체 (사용자) | 권한 위임 동의 주체 |
| Client | 자원에 접근하려는 제3자 애플리케이션 | 인가 코드를 받아 토큰 획득 |
| Authorization Server (AS) | 사용자 신원을 확인하고 Access/ID Token 발급 | 토큰 생명주기 관리 |
| Resource Server (RS) | 토큰을 검증하고 실제 보호된 자원(API)을 제공 | Access Token 검증 인프라 |

> 요약: 사용자의 동의를 거쳐 인가 서버가 토큰을 발급하면, 클라이언트는 이를 통해 리소스 서버의 자원에 안전하게 접근한다.

---

## Ⅲ. 동작원리 및 흐름도 (Authorization Code Grant 기준)

```text
RO 접근 요청 -> Client가 AS로 리다이렉트 -> RO 동의 후 인가 코드 반환 -> Client가 인가 코드로 토큰 요청 -> AS가 토큰 발급 -> RS 접근
```

- 1단계 [인가 요청 및 리다이렉트]: Client가 RO를 AS의 인가 엔드포인트로 리다이렉트 (클라이언트 ID, 리다이렉트 URI 포함)
- 2단계 [인증 및 동의]: RO가 AS 환경에서 로그인 후, Client가 요구하는 권한 스코프(Scope)에 동의
- 3단계 [코드 발급 및 토큰 교환]: AS가 리다이렉트 URI로 임시 인가 코드(Code)를 반환하고, Client 백엔드는 이를 Access/ID Token으로 교환
- 4단계 [자원 요청 및 응답]: Client가 Access Token을 HTTP 헤더(Bearer)에 실어 RS에 API를 요청하고 자원 획득

> 요약: 인가 코드를 통한 백채널(Back-channel) 토큰 교환으로 브라우저(프론트채널) 노출 위험을 원천 차단하여 토큰을 안전하게 획득한다.

---

## Ⅳ. 특징
- OAuth 2.0 단일목적성 탈피(OIDC): OAuth 2.0의 `openid` 스코프 지정 시 인가 기능과 함께 JWT 형태의 ID Token을 발급받아 인증 달성
- Stateless 인증/인가 구조 확장: 토큰 자체에 권한 정보나 신원 정보를 담을 수 있어(JWT 활용 시), AS 병목을 줄이고 RS 단독 검증 가능
- 세분화된 스코프(Scope) 제어: 필요한 리소스 단위로 권한을 잘게 쪼개어(Least Privilege), 불필요한 과도한 권한 노출 방지

> 요약: 인가와 인증을 동시에 수행하면서, 상태를 저장하지 않는 유연하고 세밀한 권한 제어가 핵심 특징이다.

## Ⅴ. 심화 비교 및 적용 판단 (OAuth 2.0 Grant Type 선택)

| Grant Type | 특징 및 적용 환경 | 선택 기준 및 보안 고려사항 |
|:---|:---|:---|
| Authorization Code | 인가 코드를 서버 간 통신으로 토큰과 교환 | 백엔드 서버가 있는 정통 웹 애플리케이션 (가장 권장) |
| Implicit (비권장) | 인가 코드 없이 브라우저로 토큰 직접 전달 | 토큰 탈취 위험이 커서 최신 OAuth 2.1 스펙에서 삭제됨 |
| Client Credentials | 사용자 동의 없이 Client 자격증명만으로 토큰 발급 | 서버 대 서버 통신, 백그라운드 데몬 (M2M 연동) |

> 요약: 보안 강화를 위해 토큰이 프론트 채널에 노출되는 Implicit 방식은 폐기하고, Authorization Code 또는 PKCE 적용을 표준으로 삼는다.

**리스크·대응 (기본은 불릿):**
- 인가 코드 가로채기(Interception): 악성 앱이 동일한 커스텀 URL 스킴을 등록해 인가 코드 탈취 → PKCE(Code Verifier/Challenge)를 적용하여 요청자와 교환자가 동일한지 암호학적으로 검증
- CSRF(Cross-Site Request Forgery) 공격: 리다이렉트 단계에서 공격자 세션 삽입 → 인가 요청 시 난수화된 `state` 파라터를 전송하고 콜백 검증
- 토큰 탈취 및 무기한 악용: Access Token 유출 시 영구적 자원 접근 허용 → Access Token 수명(TTL)을 수십 분 단위로 짧게 하고, Refresh Token 통제

**도입 후 점검 지표 (기본은 불릿):**
- 보안/통제: PKCE 적용 비율 100%, Refresh Token 회전(Rotation) 적용 유무
- 운영/성능: 인가 서버 Token Introspection(토큰 검증) 엔드포인트 응답시간 50ms 이하 유지

## Ⅵ. 실무 적용 및 결론

**적용 방안 3개:**
1. 엔터프라이즈 SSO 통합 연동: 레거시 SAML 대신 Keycloak이나 Okta 기반의 OIDC Provider를 구축하여 사내 수십 개 애플리케이션의 인증 일원화
2. 모바일/SPA 보안 강제화: 모바일 앱과 React/Vue 기반 SPA 환경에서는 백엔드 서버 유무와 무관하게 Authorization Code Grant with PKCE 방식을 강제 표준으로 적용
3. JWT 기반 인가 아키텍처: Access Token을 불투명(Opaque) 문자열 대신 JWT로 발급하여 리소스 서버가 인가 서버 의존 없이 서명(Signature)만으로 자체 검증(Stateless)하도록 오프로딩

**결론 (2줄):**
- 기술사 판단: API 연동 시 인가와 인증을 명확히 분리해야 하며, OAuth 2.0의 빈틈(인증 결여)을 OIDC가 완벽히 메우므로 최신 서비스 설계 시 OIDC 채택은 필수다.
- 향후 방향: OAuth 2.1 스펙 확정에 따라 Implicit과 Password Grant가 전면 금지되고 PKCE가 필수화되므로, 레거시 인증 아키텍처의 전면 전환이 요구된다.
