# 📖 【암기용】 개념 완전 이해

## 한눈에
- **개요**: 시간에 따른 데이터의 변화를 저장하고 조회하는 데 특화된 데이터베이스이다. 모든 데이터가 '시간(Timestamp)'을 기준으로 정렬되어 저장된다.
- **왜 필요한가**: 수천 대의 서버 CPU 사용량이나 수백만 개의 IoT 센서 데이터를 매초 수집하려면 엄청난 쓰기(Write) 부하가 발생한다. 일반 RDBMS는 이를 감당하지 못하고 뻗어버리며, 과거 데이터를 주기적으로 지우는 작업(오래된 로그 삭제)도 몹시 비효율적이다.
- **핵심 직관**: 주식 차트를 그리기 위한 데이터를 모으는 거대한 공책이다. 시간순으로 계속 밑으로 적기만 하고(빠른 쓰기), 나중에 "어제 오전 9시부터 10시까지의 평균값"을 낼 때는 그 구간만 찢어서(빠른 스캔 및 집계) 보여준다.

## 핵심 용어 정리

| 용어/표기 | 의미 | 비유·예 |
|:---|:---|:---|
| TSDB | Time Series Database, 시계열 데이터베이스 | 주가 기록부, 온도 변화 기록부 |
| Timestamp | 데이터가 발생한 정확한 시간 값 | 일기장의 날짜와 시간 |
| Metric | 측정하려는 대상의 이름이나 범주 | "CPU 사용량", "거실 온도" |
| Retention Policy | 오래된 데이터를 자동으로 삭제하거나 압축하는 보존 정책 | "1년 지난 일기장은 버린다" |

## 깊이 이해
- **배경·문제의식**: 클라우드 인프라 모니터링, 자율주행차 센서 등에서 초당 수백만 건의 데이터가 쏟아진다. 이 데이터들은 대부분 한 번 쓰이면 수정될 일이 없는(Append-Only) 특징을 가진다. RDBMS의 B-Tree 인덱스는 무작위 쓰기에 맞춰져 있어 이런 시계열 데이터를 넣을 때 병목이 심했다.
- **작동 원리**: TSDB는 데이터를 시간순으로 차곡차곡 쌓는(LSM-Tree 구조 등) 방식을 써서 쓰기 속도를 극한으로 끌어올린다. 또한 데이터가 대부분 비슷한 숫자(예: 온도가 24.1, 24.2, 24.1)이므로 델타 인코딩(차이값만 저장) 같은 특수 압축을 사용해 저장 공간을 1/10 수준으로 줄인다.
- **비유**: 병원의 심전도 기록지와 같다. 시간이 흐름에 따라 펜이 계속 선을 그리고(Append-Only), 간호사는 특정 시간대의 파동(집계)만 살펴본다. 과거 기록은 한 달 뒤에 자동으로 폐기(Retention)된다.
- **구체 예시**: InfluxDB, Prometheus가 대표적이다. 서버 모니터링 시 각 서버에서 매 1초마다 보내는 CPU, 메모리 수치를 모두 저장한 뒤, 대시보드(Grafana)에서 "최근 1시간 동안의 5분 단위 평균"을 구하는 쿼리를 순식간에 처리한다.
- **흔한 오해·주의점**: "일반 로그(문자열) 저장에도 쓰면 좋지 않을까?" TSDB는 주로 '숫자(Metric)'를 시간순으로 저장하고 계산(평균, 최대값 등)하는 데 특화되어 있다. 복잡한 텍스트 로그 검색은 Elasticsearch 같은 검색 엔진이 낫다.

## 연결 개념
- LSM-Tree — TSDB의 고속 쓰기를 가능하게 하는 자료구조
- Prometheus — 시계열 기반 모니터링 시스템의 표준
- 데이터 압축 알고리즘(Delta-of-Delta) — 시계열 데이터 저장 최적화

# 📝 【답안용】 시험 답안 템플릿

## 핵심 인사이트 (3줄 요약)

> 1. **본질**: 타임스탬프(Timestamp)를 기본 축으로 삼아, 연속적으로 발생하는 메트릭(Metric) 데이터를 고속 적재하고 시간 기반으로 집계하는 데 특화된 데이터베이스이다.
> 2. **가치**: Append-Only 고속 쓰기, 델타 압축을 통한 공간 절약, 시간 구간 기반 다운샘플링 및 보존 정책(Retention)을 자체 지원하여 모니터링 인프라 비용을 최소화한다.
> 3. **판단 포인트**: 트랜잭션 업데이트(UPDATE)가 빈번한 업무에는 부적합하며, IoT 센서나 인프라 모니터링 등 삽입 중심의 스트리밍 데이터 처리에 적용한다.

## 출제 의도 및 답안 포인트

| 출제 의도 | 반드시 짚을 핵심 | 감점 회피 포인트 |
|:---|:---|:---|
| 대규모 시계열 데이터 처리 한계 극복 방안 | Timestamp 중심 아키텍처, Append-Only(LSM-Tree), 시계열 압축, Retention Policy | 단순 NoSQL로 뭉뚱그림, RDBMS B-Tree와의 쓰기 성능 차이 누락 |

> 요약: RDBMS가 감당하지 못하는 초당 수백만 건의 쓰기를 어떻게 해결(LSM-Tree, 시계열 압축)하고 관리(다운샘플링)하는지 기술적 차별성을 제시한다.

## Ⅰ. 개요 및 필요성

- 개요: 시간(Time)을 인덱스의 핵심 기준으로 삼아 끊임없이 생성되는 일련의 연속된 데이터를 효율적으로 저장, 조회, 분석하는 DB
- 배경: IoT, 클라우드 환경에서 서버 메트릭 및 센서 데이터가 폭발적으로 증가하여 기존 RDBMS의 B-Tree 인덱스 쓰기 병목 및 용량 한계 도달
- 필요성: Update 없는 지속적 삽입(Append-Only)에 최적화된 쓰기 성능, 시간 윈도우 기반 고속 집계, 자동화된 과거 데이터 관리(Lifecycle) 기법 필요

---

## Ⅱ. 구조 및 구성요소

```text
Data Source -> Data Ingestion (Write) -> Storage Engine (Time-Partitioned) -> Query Engine (Agg)
  (IoT/Log)          |                            |                               |
                     +-> 압축(Delta/Gorilla)      +-> 자동 만료(Retention)        +-> Downsampling
```

| 구성요소 | 역할 | 특이사항 |
|:---|:---|:---|
| Time-series Data Model | Timestamp, Metric, Tag, Field로 구성된 데이터 모델 | 다차원 식별자(Tag) 제공 |
| Storage Engine | 시간 파티션 기반 저장 및 시계열 특화 압축 (Gorilla 등) | LSM-Tree 등 Append-Only 구조 |
| Retention Manager | 설정된 보존 주기(TTL)에 따라 오래된 데이터 자동 삭제 | 디스크 풀(Full) 방지 및 자동화 |
| Aggregation Engine | 윈도우 함수, 이동 평균, 다운샘플링 등 쿼리 즉시 처리 | 시계열 특화 연산 내장 |

> 요약: 데이터 유입부터 시간 기반 스토리지 저장, 자동화된 보존 정책, 고속 집계까지 시계열 처리에 최적화된 파이프라인 구조다.

---

## Ⅲ. 동작원리 및 흐름도

```text
데이터 유입 -> 메모리 버퍼링 및 압축 -> 시간 파티션 디스크 기록 -> 윈도우 기반 질의 처리
```

- 1단계 [버퍼링 및 압축]: 연속된 센서 데이터를 메모리 버퍼에 적재하고, 이전 값과의 차이(Delta-of-Delta)를 이용해 비트 단위 압축 수행
- 2단계 [시간 파티셔닝]: 데이터를 일(Day) 또는 시간(Hour) 단위의 블록(Chunk)으로 분할하여 순차적으로 디스크에 플러시(LSM-Tree 구조)
- 3단계 [다운샘플링]: 백그라운드 프로세스가 오래된 초 단위 데이터를 분/시간 단위 평균값으로 요약하여 저장 공간 확보
- 4단계 [질의 응답]: 쿼리 엔진이 특정 시간 범위(Time Window) 블록만 스캔하여 불필요한 I/O를 배제하고 집계 결과를 반환

> 요약: 메모리 기반 압축과 순차 쓰기로 속도를 높이고, 시간 파티션 단위 관리로 검색 I/O를 최소화하며 생명주기를 자동 관리한다.

---

## Ⅳ. 특징

- Append-Only 모델: 업데이트(Update)와 개별 삭제(Delete)를 제한하거나 금지하여 락(Lock) 없이 순차 쓰기 성능을 극대화
- 시계열 특화 질의어: 시계열 보간(Interpolation), 이동 평균(Moving Average), 시간 버킷링(Bucketing) 등을 지원하는 전용 쿼리 (예: PromQL, Flux)
- 공간 최적화: 타임스탬프와 연속된 부동소수점 데이터 특성을 활용한 특수 압축 알고리즘으로 RDBMS 대비 스토리지 사용량을 크게 절감

> 요약: RDBMS의 무결성(ACID)이나 조인을 포기한 대신, 쓰기 성능과 시간 축 기반의 집계, 압축 효율에 모든 자원을 집중했다.

## Ⅴ. 심화 비교 및 적용 판단

| 비교 축 | RDBMS (B-Tree) | TSDB (LSM-Tree 계열) | 선택 기준 |
|:---|:---|:---|:---|
| 쓰기(Write) 특성 | Random I/O, 트랜잭션 로깅 | Sequential I/O, Append-Only | 쓰기 초당 건수 (TPS) |
| 과거 데이터 삭제 | 대량 `DELETE` 시 성능 저하 극심 | 시간 파티션 파일 통째로 삭제 (Drop) | 데이터 보존 정책(Retention) 빈도 |
| 집계 연산 | `GROUP BY` 기반 전체 스캔 | 시간 버킷 단위 고속 다운샘플링 | 실시간 대시보드(차트) 요구 여부 |

> 요약: 트랜잭션 갱신이 필요한 비즈니스 원장은 RDBMS를, 수정 없이 쌓이기만 하는 모니터링 수치는 TSDB를 선택한다.

**리스크·대응 (기본은 불릿):**
- 카디널리티(Cardinality) 폭발: Tag 조합(예: IP 주소, UUID)이 무한히 증가하면 메모리 인덱스 크기가 폭증하여 OOM 발생 → 무한한 식별자를 Tag가 아닌 Field에 저장하도록 스키마 설계 지침 강제 (지표: 시계열 시리즈 개수)
- 과거 데이터 수정/지연 도착: 센서 오프라인 후 지연 전송된 데이터(Out-of-order) 처리 시 파일 병합 오버헤드 발생 → 일정 시간(Window) 이내 지연만 허용하고 그 외는 버리거나 별도 배치 처리

**도입 후 점검 지표 (기본은 불릿):**
- 성능/효율: 초당 데이터 수집량(Ingestion Rate) 및 쿼리 응답시간 p95 지표 (대시보드 렌더링 시간)
- 품질/운영: 디스크 용량 증가 추이 및 데이터 보존 정책(Retention) 정상 동작 여부

## Ⅵ. 실무 적용 및 결론

**적용 방안 3개:**
1. IT 인프라 통합 모니터링: 프로메테우스(Prometheus)를 도입하여 MSA 환경의 수백 개 컨테이너 메트릭을 수집하고 그라파나(Grafana)와 연동하여 실시간 시각화
2. 스마트 팩토리 설비 예지 보전: 공장 내 센서 진동, 온도 데이터를 InfluxDB에 초 단위로 적재하고, 임계치 초과 시 알람을 발생하는 파이프라인 구축
3. 금융 틱(Tick) 데이터 분석: 주식/가상화폐 거래소의 초당 틱 데이터를 저장하고 다운샘플링하여 분봉/일봉 차트를 빠르게 렌더링

**결론 (2줄):**
- 기술사 판단: TSDB는 시계열 스트리밍 데이터의 쓰기 병목과 보존 관리 문제를 해결하는 필수 인프라지만, 높은 카디널리티 설계 오류 시 메모리 폭주를 유발하므로 태그(Tag) 모델링 통제가 핵심이다.
- 향후 방향: 최근 TSDB는 온프레미스를 넘어 클라우드 네이티브 아키텍처(오브젝트 스토리지 연동)로 진화하며 장기 보관 비용을 더욱 낮추고 있다.
