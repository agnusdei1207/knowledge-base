## 핵심 인사이트 (3줄 요약)
- **시간(Timestamp)의 흐름에 따라 연속적으로 생성되는 데이터**(주식 호가, 서버 CPU 사용률, 스마트 시티 IoT 센서 등)를 저장하고 분석하는 데 극단적으로 특화된 데이터베이스.
- 기존 RDBMS에 초당 수십만 건의 온도 데이터를 INSERT하면 인덱스가 깨지고 용량이 폭발함. TSDB는 시간에 따른 '순차적 쓰기(Append-only)' 성능을 극대화하고, 과거 데이터를 묶어서 압축(Downsampling)하는 기능이 내장되어 있음.
- InfluxDB, Prometheus, TimescaleDB 등이 대세이며, 시스템 모니터링 환경(Prometheus + Grafana 대시보드)과 인공지능 기반 이상 징후 탐지(AIOps) 시스템의 심장 역할을 수행함.

## Ⅰ. 개요 및 필요성
- **개요**: 시간(Time)과 해당 시간의 값(Value), 그리고 메타데이터(Tag)로 구성된 시계열 데이터를 초고속으로 수집, 압축, 조회하는 특수 목적 데이터베이스.
- **필요성**: 공장의 온도 센서가 0.1초마다 `[2026-07-05 10:00:00.100, 36.5도]` 데이터를 발사함. 센서가 1만 개면 1초에 10만 건임. RDB에 넣으면 하루 만에 디스크가 터지고, MongoDB에 넣어도 시간에 따른 "최근 1시간 평균 온도"를 구하려면 전체 문서를 뒤져야 해서 서버가 죽음. 시간에 최적화된 자료구조와 쿼리 엔진이 절실했음.
---
## Ⅱ. 아키텍처 및 핵심 원리
- **TSDB의 3대 핵심 구조**:
  1. **데이터 모델 (시간-값 구조)**:
     - `Timestamp`: 절대적인 기준 축 (시간표).
     - `Metrics/Value`: 실제 측정된 값 (예: CPU 사용률 85%, 주식 가격 100달러).
     - `Tags/Labels`: 데이터를 그룹화하기 위한 인덱스 (예: 서버_IP=192.168.0.1, 센서_위치=강남역).
  2. **다운샘플링 (Downsampling)과 압축**:
     - 오늘 들어온 데이터는 0.1초 단위 원본으로 들고 있지만, **한 달 전 데이터는 0.1초 단위가 의미 없음**.
     - TSDB가 백그라운드에서 한 달 전 데이터들을 1시간 단위 '평균값'으로 합쳐버리고 원본을 버림 (디스크 용량 90% 이상 절약).
  3. **시계열 특화 연속 쿼리 (Continuous Query)**:
     - "매 1분마다 지난 5분의 평균값을 구해서 새 테이블에 넣어라" 같은 윈도우(Window) 기반 스트림 쿼리를 자체적으로 계속 돌려줌.

```text
[ RDB와 TSDB의 디스크 저장(압축) 방식 차이 ]

 💾 [ RDBMS (수직적 저장) ] ➡️ 데이터가 들어오는 대로 무겁게 다 적음.
 10:00:01 | 센서1 | 온도 | 30.1도
 10:00:02 | 센서1 | 온도 | 30.2도
 10:00:03 | 센서1 | 온도 | 30.2도 (디스크 터짐)

 ⏱️ [ TSDB (델타 인코딩 압축 마법) ] ➡️ 변한 차이(Delta)만 저장함!
 [기본값] 10:00:01 (센서1 온도) = 30.1도
 [ 1초 뒤 ] 차이값 +0.1
 [ 2초 뒤 ] 차이값 0 
 ➡️ (메모리 1비트만 써서 저장 완료, RDB 대비 디스크 효율 수십 배 차이!)
```

## Ⅲ. 비교 및 연결
| 구분 | RDBMS | Time-Series DB (InfluxDB) |
|---|---|---|
| **기본 키 (Primary Key)** | 사용자 정의 PK (ID 번호 등) | **무조건 시간 (Timestamp) 중심** |
| **쓰기 작업 (INSERT)**| B-Tree 인덱스 쪼개짐 (느림) | **시간순 이어쓰기 (Append-only) 초고속** |
| **수정/삭제 (UPDATE/DELETE)**| 자유롭게 아무거나 바꿀 수 있음 | **거의 불가능 (과거 기록을 조작할 수 없다는 철학)** |
| **과거 데이터 관리** | 배치를 짜서 수동으로 삭제해야 함 | **Retention Policy로 알아서 압축/삭제됨** |

## Ⅳ. 실무 적용 및 기술사 판단
- **시계열 데이터의 카디널리티(Cardinality) 폭발 주의**: 프로메테우스(Prometheus) 같은 TSDB를 쓸 때 아키텍트가 저지르는 최악의 실수는 `Tag` 값에 '고객 ID'나 '세션 ID' 같은 무한대로 늘어나는 값을 넣는 것임. Tag 종류 하나마다 내부적으로 시계열 인덱스 트리가 생성되므로, 고유한 값이 100만 개인 고객 ID를 Tag로 넣으면 카디널리티가 폭발하여 서버의 메모리(OOM)가 즉사함. Tag에는 반드시 서버 IP, 지역명 같은 유한한(제한된) 열거형 값만 넣어야 함.
- **RDB와의 결합 (TimescaleDB)**: 기존에 익숙한 PostgreSQL 위에 시계열 압축 엔진을 플러그인 형태로 끼워 넣은 TimescaleDB가 실무에서 각광받음. 복잡한 모니터링 생태계를 배울 필요 없이, 평소 쓰던 일반 SQL(`JOIN` 등)을 그대로 쓰면서도 시계열 데이터의 압축 성능을 누릴 수 있어 기존 백엔드 시스템과의 통합이 매우 유연함.
---
## Ⅴ. 기대효과 및 결론
- 4차 산업혁명(IoT, 자율주행, 스마트 팩토리) 시대에 끊임없이 뿜어져 나오는 시계열 데이터를 싼값에 무한정 받아내고 실시간으로 대시보드에 뿌려줄 수 있는 인프라의 혈관임.
- 데이터베이스 설계 패러다임을 '수정(Update) 가능한 장부'에서, "과거는 바뀔 수 없다"는 '불변(Immutable)의 시간 기록물'로 전환시킨 철학적 진보를 보여줌.

### 👶 어린이를 위한 3줄 비유 설명
1. 기존 DB는 '일반 노트'예요. 이름, 전화번호, 주소 등등 이것저것 막 적고 나중에 수정 지우개질도 자유롭죠.
2. **TSDB(시계열 DB)**는 의사 선생님이 쓰는 '심전도 그래프 종이'예요. 무조건 시간 순서대로 지지직~ 선만 긋고(초고속), 옛날 기록을 중간에 지우개로 절대 수정할 수 없어요!
3. 대신 종이가 너무 길어지면, "저번 달 심장 박동은 1분에 60번이었음"이라고 요약(압축)해 두고 긴 종이는 버려버리니까 보관하기 아주 똑똑하답니다.
