## 미리 알고가기

- 캐시 계층은 자주 읽는 데이터를 메모리에 잠시 두어 원본 저장소 접근을 줄이는 구조임
- TTL은 캐시가 자동으로 만료되는 시간을 뜻함
- 캐시 스탬피드는 인기 데이터가 한꺼번에 만료돼 원본 저장소로 요청이 몰리는 현상임

## 작성 근거(검토용)

- 제목·frontmatter·미리 알고가기·본문·표·요약·결론을 5회 전수 검수해 어색한 단어·조사·동사 결합·장황한 명사구를 교정함
- 캐시 계층은 키·만료·무효화·원본 보호를 핵심 축으로 설명함
- 비교표는 Redis와 Memcached의 자료구조·운영 기능·적합 용도를 대비함
- 조회 서비스는 캐시 적중률·원본 요청 증가율로 검증함

## Ⅰ. 개요

- **정의/개념**: 캐시 계층은 반복 조회 결과를 메모리에 임시 저장해 응답 지연과 원본 저장소 부하를 줄이는 구조임
- **배경/필요성**: 조회 트래픽 증가에 따른 원본 병목을 줄이면서 데이터 신선도를 유지하기 위해 캐시 키·만료·무효화 정책이 필요함

## Ⅱ. 특징

- 응답 시간을 줄이고 원본 저장소 부하를 낮출 수 있음
- Redis는 문자열·목록·집합·정렬 집합과 영속성·복제를 제공하고, Memcached는 메모리 기반 키값 캐시에 집중함
- 키 설계와 TTL과 무효화 규칙이 캐시 품질을 좌우함
- 캐시 장애나 동시 만료를 대비하지 않으면 성능 최적화 계층이 전체 장애의 시작점이 될 수 있음

## Ⅲ. 종류 및 비교

| 판단 기준 | Redis | Memcached |
|:---|:---|:---|
| 제공 기능 | 문자열과 목록과 집합 등 다양한 자료구조를 제공함 | 단순 키-값 캐시에 집중함 |
| 활용 방식 | 자료구조 연산·세션·랭킹·분산 조정 | 조회 결과의 키값 저장·만료 |
| 한계 | 기능이 많은 만큼 운영 설정이 복잡해질 수 있음 | 자료구조와 부가 기능이 제한적임 |
| 대표 용도 | 캐시·세션·랭킹·자료구조 연산 | 단순 조회 결과·직렬화 객체 캐시 |

> 요약: Redis는 자료구조와 운영 기능을 제공하고, Memcached는 단순 키값 캐시에 집중함.

## Ⅳ. 구성요소 및 구조

| 구성요소 | 설명 |
|:---|:---|
| 캐시 키 설계 | 어떤 단위로 재사용할지 정해 적중률과 무효화 정확도를 좌우함 |
| 만료와 무효화 정책 | TTL과 수동 삭제 규칙으로 데이터 신선도와 적중률의 균형을 맞춤 |
| 적재 방식 | 캐시 어사이드·라이트 스루 방식이 조회와 갱신 시 일관성 특성을 결정함 |
| 보호와 우회 절차 | 동시 만료 방지와 원본 우회 경로를 두어 장애 전파를 줄임 |

> 요약: 캐시 키와 적재 방식이 재사용 단위를 정하고 만료·무효화와 보호 절차가 신선도와 원본 부하를 통제함.

## Ⅴ. 원리 및 절차 흐름도

1. **요청 수신**: 애플리케이션이 데이터를 요청함
2. **캐시 조회**: 키 기준으로 캐시 적중 여부를 확인함
3. **미적중 시 원본 조회**: 값이 없으면 원본 저장소에서 읽음
4. **캐시 적재와 만료**: 결과를 저장하고 만료 정책을 적용함

> 요약: 요청 키를 캐시에서 조회하고 미적중 시 원본 결과를 적재한 뒤 만료·무효화 정책을 적용함.

## Ⅵ. 실무 사례

1. 상품 조회 API는 캐시 어사이드와 TTL을 적용하고 적중률·과거 데이터 노출 건수를 확인함
2. 인기 콘텐츠 캐시는 만료 분산과 요청 병합을 적용하고 스탬피드 건수·원본 요청 증가율을 확인함

## Ⅶ. 결론

- 캐시 계층은 키·만료·무효화·원본 보호 정책으로 응답 지연과 데이터 신선도를 함께 통제해야 함
