## 미리 알고가기

- 3단계 스키마는 데이터베이스를 외부·개념·내부 계층으로 나누는 구조임
- 각 계층은 사용자 관점과 통합 논리 관점과 물리 저장 관점을 분리함
- 데이터 독립성을 실현하는 기본 틀임

## Ⅰ. 개요

- **정의/개념**: 3단계 스키마는 사용자별 뷰를 다루는 외부 스키마와 조직 전체 논리 구조를 정의하는 개념 스키마와 실제 저장 방식을 나타내는 내부 스키마로 데이터 표현을 분리해 변경 영향과 복잡도를 줄이는 데이터베이스 구조 모델임
- **배경/필요성**: 하나의 데이터베이스를 여러 사용자와 프로그램이 공유하는 환경에서는 요구가 다르고 저장 구조도 바뀌므로, 관점을 계층적으로 나누어 관리할 필요가 있음

## Ⅱ. 특징

- 사용자 요구와 전체 데이터 모델과 물리 저장을 분리함
- 각 계층 매핑을 통해 변경 영향 범위를 제한함
- 보안과 권한 관리에도 외부 스키마가 유용함
- 매핑 관리가 약하면 계층 분리 이점이 빠르게 사라질 수 있음

## Ⅲ. 종류 및 비교

| 판단 기준 | 외부 스키마 | 개념 스키마 | 내부 스키마 |
|:---|:---|:---|:---|
| 관점 | 사용자·응용 프로그램 | 조직 전체 논리 모델 | 저장 장치와 접근 구조 |
| 역할 | 필요한 데이터만 표현 | 전체 관계와 제약 정의 | 파일과 인덱스와 배치 정의 |
| 변경 영향 | 사용자 뷰 조정 | 논리 구조 변경 | 저장 최적화 변경 |
| 핵심 가치 | 보안·단순화 | 통합성 | 성능·효율 |

## Ⅳ. 구성요소 및 구조

| 구성요소 | 설명 |
|:---|:---|
| External Schema | 사용자별 필요한 컬럼과 형식만 제공해 복잡도와 노출 범위를 줄임 |
| Conceptual Schema | 데이터 의미와 관계와 제약을 통합적으로 정의해 공통 기준을 만든다 |
| Internal Schema | 파일 구조와 인덱스와 저장 배치를 정의해 성능을 최적화한다 |
| Schema Mapping | 계층 간 대응 관계를 유지해 변경 파급을 흡수한다 |

## Ⅴ. 원리 및 절차 흐름도

```text
+-------------+     +-------------+     +-------------+     +-------------+
| 사용자 요구 수집 | --> | 개념 모델 정리  | --> | 내부 저장 설계  | --> | 계층 매핑 유지  |
+-------------+     +-------------+     +-------------+     +-------------+
```

1. **사용자 요구 수집**: 필요한 데이터 표현과 권한 범위를 정함
2. **개념 모델 정리**: 전체 엔터티와 관계와 제약을 정의함
3. **내부 저장 설계**: 저장 구조와 인덱스를 배치함
4. **계층 매핑 유지**: 변경이 발생해도 상위 영향이 최소화되게 관리함

## Ⅵ. 문제점 및 해결 방안

1. 문제: 외부 스키마 없이 개념 스키마를 직접 노출하면 사용자별 요구와 보안 제어가 뒤섞여 변경 비용이 커질 수 있음
   - 해결방안: role-based view를 설계하고 exposed attribute ratio와 schema change impact scope로 검증함
2. 문제: 개념 스키마와 내부 스키마 매핑이 문서화되지 않으면 성능 튜닝 시 논리 구조 오해가 발생할 수 있음
   - 해결방안: schema mapping catalog를 유지하고 mapping completeness와 tuning defect count로 검증함
3. 문제: 계층 간 책임이 흐려지면 물리 최적화가 응용 프로그램 규약을 직접 깨뜨릴 수 있음
   - 해결방안: schema governance review를 운영하고 layer violation count와 backward compatibility rate로 검증함

## Ⅶ. 적용 사례

- 다부서 공용 DB에서는 역할 기반 뷰를 제공하고, exposed attribute ratio와 schema change impact scope로 결과를 확인함
- DBA 조직에서는 스키마 매핑 카탈로그를 유지하고, mapping completeness와 tuning defect count로 결과를 확인함
- 스키마 변경이 잦은 서비스에서는 계층 거버넌스를 운영하고, layer violation count와 backward compatibility rate로 결과를 확인함

## Ⅷ. 결론

3단계 스키마의 의미는 구조를 세 겹으로 외우는 데 있지 않고 사용자 요구와 논리 모델과 저장 최적화를 분리해 변경 비용을 줄이는 데 있음.
