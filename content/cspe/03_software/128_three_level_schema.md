# 📖 【암기용】 개념 완전 이해

> 목적: 3단계 스키마를 처음 봐도 완벽히 이해하게 만든다. 시험 답안 양식이 아니라, 이해를 위한 친절한 설명이다.

## 한눈에
- **개요**: **데이터 독립성**(Data Independence)을 확보하기 위해 DB를 사용자 관점(외부)·전사 논리 관점(개념)·물리 저장 관점(내부) 3단계로 나눈 **ANSI/SPARC 아키텍처**다.
- **왜 필요한가**: 사용자 화면, 업무 데이터 모델, 실제 저장 방식이 한 덩어리로 묶이면 저장 구조 하나만 바꿔도 그 구조를 아는 모든 응용 프로그램을 다시 짜야 한다(강결합). 3단계 스키마는 이 세 관점을 분리하고 그 사이를 매핑으로 이어, 한쪽이 바뀌어도 다른 쪽이 영향받지 않게 한다.
- **핵심 직관**: 같은 도시를 시민용 관광지도(외부), 행정구역 지적도(개념), 지하 상하수도 배관도(내부)로 나눠 관리하는 방식이다. 배관 공사(내부 변경)를 해도 관광지도(외부)는 다시 찍을 필요가 없다.

## 핵심 용어 정리 (내부에 등장하는 것들)

| 용어 | 의미 | 비유 |
|:---|:---|:---|
| 데이터 독립성 | 상위 계층을 손대지 않고 하위 계층을 바꿀 수 있는 성질 — 3단계 스키마의 목적 그 자체 | 배관을 바꿔도 수도꼭지 사용법은 그대로 |
| ANSI/SPARC 아키텍처 | 1975년 ANSI/X3/SPARC 연구 그룹이 제안한 DB 표준 3계층 구조 | DB 설계의 기본 골격 |
| 외부 스키마(External Schema) | 사용자·응용 프로그램마다 다르게 보이는 뷰(부분집합) | 메뉴판 — 손님마다 관심 메뉴만 봄 |
| 개념 스키마(Conceptual Schema) | 조직 전체가 공유하는 단 하나의 논리적 데이터 모델(엔티티·관계·제약) | 매장 전체 레시피 원본 |
| 내부 스키마(Internal Schema) | 실제 저장 파일·인덱스·페이지·파티션 구조 | 주방 재료 창고 배치도 |
| 외부/개념 매핑 | 뷰와 논리 모델을 잇는 연결 — 이게 끊어지지 않는 한 개념 스키마가 바뀌어도 외부 스키마는 그대로 둘 수 있음 | 레시피 이름이 바뀌어도 메뉴판 문구는 유지 |
| 개념/내부 매핑 | 논리 모델과 저장 구조를 잇는 연결 — 저장 방식이 바뀌어도 논리 모델은 그대로 둘 수 있음 | 창고 배치를 바꿔도 레시피 재료명은 유지 |
| 논리적 데이터 독립성 | 개념 스키마가 바뀌어도 외부 스키마(응용 프로그램)가 영향받지 않는 성질 | 레시피에 재료 하나 추가돼도 메뉴판은 그대로 |
| 물리적 데이터 독립성 | 내부 스키마가 바뀌어도 개념 스키마가 영향받지 않는 성질 | 창고 위치가 바뀌어도 레시피는 그대로 |

## 깊이 이해

### 왜 3단계로 나눴나 (배경)
- 1970년대 초기 파일 처리 시스템에서는 응용 프로그램이 레코드의 물리적 저장 순서, 필드 오프셋, 인덱스 구조까지 직접 알고 코드를 짰다. 저장 방식을 바꾸면(예: 필드 순서 변경, 인덱스 추가) 그 저장 방식을 아는 모든 프로그램을 함께 고쳐야 했다. 1975년 ANSI/X3/SPARC 연구 그룹이 이 강결합 문제를 "관점을 세 층으로 나누고 그 사이를 매핑으로만 연결한다"는 방식으로 풀었고, 이것이 3단계 스키마다.

### 세 스키마가 각각 관리하는 범위 — 구체 예시
- 쇼핑몰 DB를 예로 들면, 하나의 물리적 `customer` 테이블을 두고도 세 계층은 서로 다른 것을 본다.
- **외부 스키마**: 영업팀은 "고객명·등급·최근구매일" 3개 컬럼만 보는 뷰를 쓰고, 배송팀은 "주소·연락처·배송상태" 뷰를 쓴다. 같은 원본에서 부서별로 다른 컬럼 부분집합만 노출한다.
- **개념 스키마**: 전사 관점에서 고객(Customer)·주문(Order)·결제(Payment) 3개 엔티티와 FK 관계, NOT NULL 제약을 정의한다. 부서와 무관하게 조직 전체에 하나만 존재한다.
- **내부 스키마**: 고객 테이블 500만 행을 가입월 기준 12개 파티션으로 나누고, `customer_id`에 B+Tree 인덱스를 건다.

### 매핑이 데이터 독립성을 어떻게 실현하나 — 수치로 확인
- **물리적 독립성 예**: 고객이 500만 명일 때 `customer_id`로 한 명을 찾으려면, 인덱스가 없는 풀 스캔은 최악의 경우 500만 건을 다 훑어야 한다(O(n)). `customer_id`에 B+Tree 인덱스를 걸면 log₂(5,000,000) ≈ 23회 비교로 찾는다(O(log n)). 이렇게 내부 스키마에서 인덱스를 추가·삭제하거나 파티션을 재구성해도, 개념 스키마의 "고객은 customer_id로 식별된다"는 정의와 그 위의 응용 SQL은 한 글자도 바뀌지 않는다 — 이것이 물리적 데이터 독립성이며, 개념/내부 매핑이 그 변화를 흡수하기 때문에 가능하다.
- **논리적 독립성 예**: 개념 스키마에 "적립 포인트(point)" 컬럼을 새로 추가해도, 그 컬럼을 노출하지 않는 영업팀의 외부 스키마(뷰 정의)는 손댈 필요가 없다 — 이것이 논리적 데이터 독립성이다. 다만 논리 모델(엔티티·관계) 자체를 바꾸는 개념 스키마 변경은 저장 구조만 바꾸는 물리적 변경보다 응용에 미치는 파급이 크므로, 실무에서는 논리적 독립성 확보가 물리적 독립성보다 어렵다.

### 흔한 오해
- 3단계 스키마는 물리적으로 DB 서버가 세 대라는 뜻이 아니다. 하나의 DBMS 카탈로그 안에 세 개의 정의(뷰 정의·논리 모델 정의·저장 구조 정의)와 두 개의 매핑이 함께 존재하는 논리적 구조일 뿐이다.

## 연결 개념
- 데이터 독립성(Data Independence) — 3단계 스키마가 실현하려는 상위 목표
- 뷰(View) — 외부 스키마가 실제로 구현되는 형태
- B+Tree 인덱스, 파티셔닝 — 내부 스키마에서 물리적 독립성을 만드는 구체 수단

# 📝 【답안용】 시험 답안 템플릿

> 목적: 시험장에서 25분에 그대로 쓰는 답안 양식. 작성방식(추상표현 금지·수치·도식·문제유형 전환)을 엄격히 지킨다.
> 핵심: 3단계 스키마 답안은 각 계층 정의와 두 매핑, 데이터 독립성 효과를 함께 써야 함.

## 핵심 인사이트 (3줄 요약)

> 1. **본질**: 3단계 스키마는 외부·개념·내부 스키마로 DB 관점을 분리하는 ANSI/SPARC 구조임.
> 2. **가치**: 사용자 뷰, 전사 논리 모델, 물리 저장 구조 변경을 분리해 DB 변경 영향을 줄임.
> 3. **판단 포인트**: 외부/개념 매핑은 논리 독립성, 개념/내부 매핑은 물리 독립성과 연결됨.

## 출제 의도 및 답안 포인트

| 출제 의도 | 반드시 짚을 핵심 | 감점 회피 포인트 |
|:---|:---|:---|
| DBMS 기본 구조 확인 | external, conceptual, internal schema | 3계층 애플리케이션 구조와 혼동하지 않음 |
| 데이터 독립성 연결 확인 | 논리적·물리적 데이터 독립성 | 계층만 나열하고 매핑을 빠뜨리지 않음 |
| 실무 적용 이해 확인 | view, ER model, storage/index | 사용자별 권한·뷰 관점 누락 방지 |

> 요약: 3단계 스키마는 DB 관점 분리와 데이터 독립성을 설명하는 기본 구조임.

## Ⅰ. 개요 및 필요성

- 개요: 3단계 스키마는 DB 구조의 3관점 분리 모델이다.
- 배경: 사용자 요구, 전사 데이터 모델, 물리 저장 구조는 변경 주기와 책임자가 다르다.
- 필요성: 외부·개념·내부 스키마 분리로 응용 변경과 저장 구조 변경의 결합도를 낮춘다.

---

## Ⅱ. 구조 및 구성요소

```text
User/Application -> External Schema -> Conceptual Schema -> Internal Schema -> Physical Storage
                       +-> External/Conceptual Mapping
                                            +-> Conceptual/Internal Mapping
```

| 구성요소 | 역할 | 특이사항 |
|:---|:---|:---|
| 외부 스키마 | 사용자·응용별 데이터 뷰 | view, 권한, 화면별 projection |
| 개념 스키마 | 전사 논리 데이터 모델 | entity, relationship, constraint |
| 내부 스키마 | 저장 파일·인덱스·접근 경로 | page, partition, B+Tree |
| 매핑 | 계층 간 변환 관계 | 독립성 확보 지점 |

> 요약: 3단계 스키마는 사용자 뷰, 논리 모델, 물리 저장을 분리하고 매핑으로 연결함.

---

## Ⅲ. 동작원리 및 흐름도

```text
User Query -> External View Resolve -> Conceptual Model Map -> Internal Access Path -> Storage Read/Write
```

| 단계 | 처리 내용 | 검증 기준 |
|:---:|:---|:---|
| 1 | 사용자별 외부 스키마 확인 | view 권한, column mask |
| 2 | 외부 질의를 개념 스키마로 변환 | view expansion |
| 3 | 개념 객체를 내부 접근 경로로 매핑 | optimizer plan |
| 4 | 인덱스·파티션·페이지 접근 | I/O count, buffer hit |
| 5 | 결과를 외부 뷰 형태로 반환 | projection correctness |

> 요약: 질의는 외부 뷰에서 시작해 개념 모델과 내부 저장 경로로 변환된 뒤 결과로 반환됨.

## Ⅵ. 실무 적용 및 결론

**적용 방안 3개 (필수 — 단계별 또는 항목별):**
1. 외부 스키마는 업무 API·view·권한 정책과 연결하고, 민감 컬럼은 masking view로 노출함.
2. 개념 스키마는 ERD와 data dictionary를 기준으로 용어·엔티티·제약조건을 관리함.
3. 내부 스키마는 인덱스·파티션·압축 변경을 실행계획 검증 후 배포하고 응용 SQL 의미를 유지함.

**결론 (2줄):**
- 기술사 판단: 3단계 스키마는 데이터 독립성과 DB 거버넌스를 설명하는 기준 모델임.
- 향후 방향: 데이터 카탈로그, 스키마 레지스트리, 정책 기반 접근제어가 외부·개념 스키마 관리와 결합됨.
