## 핵심 인사이트 (3줄 요약)
- 복잡한 데이터베이스를 '사용자 관점(외부)', '조직 전체 관점(개념)', '기계 관점(내부)'의 **3개의 층(Level)으로 완벽하게 분리하여 설계하는 ANSI-SPARC 표준 아키텍처**.
- **외부 스키마**(사용자마다 보이는 뷰), **개념 스키마**(모든 데이터가 모인 통합 뼈대), **내부 스키마**(디스크에 저장되는 물리적 구조)로 나뉘며, 각 층 사이에 매핑(Mapping) 규칙을 두어 서로 영향을 주지 않도록 함.
- 이 3층 구조 덕분에, 밑단(디스크/테이블)을 뜯어고쳐도 윗단(사용자 화면)이 박살 나지 않는 **'데이터 독립성(논리적/물리적)'**이라는 마법이 기술적으로 완성됨.

## Ⅰ. 개요 및 필요성
- **개요**: 1975년 ANSI-SPARC(미국국립표준협회)에서 제안한 데이터베이스 시스템의 논리적/물리적 구조를 명확히 분리하기 위한 3계층 프레임워크.
- **필요성**: 수백 명이 쓰는 사내 시스템에서, 인사팀은 '연봉'을 보고 싶어 하고 마케팅팀은 '연봉'을 보면 안 됨. 모두가 한 통의 데이터를 보되 각자의 입맛에 맞는 껍데기를 씌워주고, 동시에 기계가 읽는 0과 1의 디스크 구조와는 철저히 격리할 표준 건축 설계도가 필요했음.
---
## Ⅱ. 아키텍처 및 핵심 원리
- **1. 외부 스키마 (External Schema / 서브 스키마)**:
  - **관점**: 개별 사용자, 응용 프로그래머 관점.
  - **특징**: 전체 DB 중 '자신에게 필요한' 일부분의 뷰(View)만 보여줌. (예: 마케팅팀 화면에는 고객의 '나이, 이름'만 보임. 연봉은 숨김). 하나의 DB에 여러 개의 외부 스키마가 존재함.
- **2. 개념 스키마 (Conceptual Schema / 논리 스키마)**:
  - **관점**: 조직 전체, 관리자(DBA) 관점.
  - **특징**: "우리 회사의 모든 데이터(테이블, 관계, 제약조건)는 이렇게 생겼다"를 정의한 **단 1개의 통합 뼈대**. (예: 전체 사원 테이블 설계도). 보안 및 무결성 규칙이 여기에 정의됨.
- **3. 내부 스키마 (Internal Schema / 물리 스키마)**:
  - **관점**: 기계, 시스템 엔지니어 관점.
  - **특징**: 개념 스키마의 데이터들이 '실제 하드 디스크'에 어떻게 물리적으로 저장될 것인가(B-Tree 인덱스, 레코드 크기, 파티셔닝, 해싱)를 정의함.

```text
[ 3층 스키마와 데이터 독립성의 관계도 ]

 🧑‍💻 [ 외부 스키마 A (인사팀 뷰) ]   👨‍💻 [ 외부 스키마 B (마케팅팀 뷰) ]
              ⬇️ (논리적 데이터 독립성: 개념이 바뀌어도 외부 뷰 매핑만 바꾸면 됨!)
 🏢 [ 개념 스키마 (DB 전체 논리적 테이블 구조 - 사원 전체 정보) ]
              ⬇️ (물리적 데이터 독립성: 디스크를 SSD로 바꿔도 논리 구조는 불변!)
 💾 [ 내부 스키마 (디스크 섹터, 인덱스, 블록 구조) ]
```

## Ⅲ. 비교 및 연결
| 구분 | 외부 스키마 (External) | 개념 스키마 (Conceptual) | 내부 스키마 (Internal) |
|---|---|---|---|
| **설계자** | 응용 프로그래머, 현업 | 데이터 아키텍트 (DA), DBA | 시스템 엔지니어, DBMS |
| **개수** | 다수 (여러 개의 View) | **오직 1개 (전체 통합)** | **오직 1개 (물리적 실체)** |
| **주요 내용**| 서브 쿼리, View 화면 | 테이블, PK/FK 제약조건 | 인덱스, 압축, 파티셔닝 |
| **관련 언어**| DML (SELECT), DDL(View) | DDL (CREATE TABLE) | 시스템 설정, DDL(Index) |

## Ⅳ. 실무 적용 및 기술사 판단
- **클라우드 시대의 내부 스키마 추상화**: 과거 온프레미스(On-premise) 환경의 DBA들은 내부 스키마(디스크 I/O 최적화, 스토리지 블록 사이즈 계산)에 엄청난 시간을 쏟았음. 그러나 AWS RDS, Aurora 같은 클라우드 DB 시대가 도래하면서, 내부 스키마 관리는 클라우드 벤더사(AWS)가 AI로 자동화해 줌. 현대의 데이터 아키텍트(DA)는 내부 스키마 튜닝보다 **비즈니스 도메인에 맞는 개념 스키마 설계(MSA DB 분할)와 보안 목적의 외부 스키마(View) 통제에 집중**하는 것이 트렌드임.
- **보안 격벽으로서의 View (외부 스키마)**: 실무에서 개발 외주 인력이나 분석가에게 DB 접근 권한을 줄 때 절대 '개념 스키마(원래 테이블)'를 통째로 열어주지 않음. 주민번호를 마스킹(`SUBSTR`) 처리한 뷰(View, 외부 스키마)만 따로 만들어서 제공(GRANT)하는 것이 기업 망 분리 및 개인정보보호법(보안) 준수의 기본 아키텍처임.
---
## Ⅴ. 기대효과 및 결론
- "하나의 데이터, 다양한 시선(One Data, Multiple Views)"을 가능하게 하여, 데이터의 중복 저장을 막고 보안성과 사용성을 동시에 만족시킨 불멸의 표준 아키텍처임.
- 모든 소프트웨어 아키텍처는 "변하는 것과 변하지 않는 것을 분리하라"는 원칙을 따르며, 3단계 스키마는 이 원칙을 데이터베이스 공학에 가장 완벽하게 적용한 교과서적 사례임.

### 👶 어린이를 위한 3줄 비유 설명
1. **내부 스키마**는 건물의 '철근과 시멘트 뼈대'예요. 아주 튼튼하게 땅(디스크)에 박혀 있죠.
2. **개념 스키마**는 건물의 '전체 도면'이에요. 이 건물에 방이 몇 개고 화장실이 어디 있는지(전체 데이터 구조) 한눈에 볼 수 있어요.
3. **외부 스키마**는 '각 방의 창문'이에요! 1층에 사는 사람은 주차장만 보이고, 5층에 사는 사람은 하늘만 보이듯, 같은 건물이지만 사람마다 필요한 것만 보여주는 마법 창문이랍니다.
