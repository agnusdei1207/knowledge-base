# 📖 【암기용】 개념 완전 이해

## 한눈에
- **개요**: 데이터베이스를 바라보는 관점을 사용자(외부), 조직 전체(개념), 물리적 저장장치(내부)의 3가지 계층으로 분리한 ANSI/SPARC 표준 아키텍처이다.
- **왜 필요한가**: 개발자, DBA, 일반 사용자가 DB를 바라보는 시각과 필요한 정보는 완전히 다르다. 모두가 복잡한 물리적 구조를 알아야 한다면 사용하기 너무 어렵고 보안상 위험하며, DB 구조를 조금만 바꿔도 모든 프로그램이 고장 난다(데이터 종속성).
- **핵심 직관**: 건물 하나를 지을 때 3가지 관점의 도면을 그리는 것이다. 입주자가 보는 '인테리어 조감도(외부)', 건물 전체의 '구조 설계도(개념)', 그리고 배관공이 보는 '전기/수도 배관도(내부)'로 나누어 각자의 역할에만 집중하게 한다.

## 핵심 용어 정리

| 용어/표기 | 의미 | 비유·예 |
|:---|:---|:---|
| 스키마 (Schema) | 데이터베이스의 논리적 구조, 제약조건 등의 명세 | 데이터베이스 설계도 |
| 외부 스키마 (External) | 개별 사용자나 응용 프로그램이 바라보는 뷰(View) | 영업팀이 보는 "고객 연락처 목록" 화면 |
| 개념 스키마 (Conceptual) | 조직 전체 관점의 통합된 논리적 구조 | 전체 "고객 테이블", "주문 테이블"과 그 관계 |
| 내부 스키마 (Internal) | 데이터가 실제 물리적 디스크에 저장되는 물리 구조 | "고객 테이블"이 저장된 파일 크기, B-Tree 인덱스 위치 |

## 깊이 이해
- **배경·문제의식**: 초기 파일 시스템은 데이터 구조가 응용 프로그램 내부에 하드코딩되어 있었다. 데이터 독립성을 확보하고 관점을 분리하기 위해, 1970년대 ANSI/SPARC 위원회에서 데이터베이스 시스템의 뼈대를 3단계로 나누는 표준을 제시했다.
- **작동 원리**: 사용자 쿼리가 들어오면 외부 스키마를 통해 들어온다. DBMS는 이를 '외부/개념 사상(Mapping)'을 통해 개념 스키마의 논리적 테이블 구조로 변환하고, 다시 '개념/내부 사상'을 통해 디스크의 어디를 읽을지(내부 스키마) 결정한다.
- **비유**: 은행 앱. 
  - 외부 스키마: 고객이 보는 '내 통장 잔고 화면'. 
  - 개념 스키마: 은행의 전체 '계좌 통합 마스터 원장'. 
  - 내부 스키마: 은행 서버 하드디스크의 3번 섹터에 있는 'Account.dat 파일과 해시 인덱스'.
- **구체 예시**: 인사팀은 '직원 테이블'과 '급여 테이블'을 합친 화면(외부 스키마)을 본다. DBA는 전사 테이블 명세서(개념 스키마)를 관리한다. 시스템 엔지니어는 해당 테이블들이 어떤 스토리지 공간(Tablespace)에 저장되고 어떤 인덱스가 걸렸는지(내부 스키마) 관리한다.
- **흔한 오해·주의점**: 3단계 스키마는 실제로 DB 안에 존재하는 3개의 서로 다른 데이터 덩어리가 아니다. 데이터는 디스크에 하나만 존재하고, 그것을 바라보는 '추상화된 관점(정의서)'이 3개인 것이다.

## 연결 개념
- 데이터 독립성 — 3단계 스키마가 존재하는 근본적인 목적 (논리/물리 독립성)
- 뷰 (View) — 외부 스키마를 구현하는 RDBMS의 기능
- ANSI/SPARC — 3단계 스키마를 제정한 미국 표준 위원회

# 📝 【답안용】 시험 답안 템플릿

## 핵심 인사이트 (3줄 요약)

> 1. **본질**: 데이터베이스의 논리적/물리적 구조를 사용자 관점, 전사적 관점, 시스템 관점으로 분리한 ANSI/SPARC 표준 추상화 아키텍처이다.
> 2. **가치**: 스키마 간의 사상(Mapping)을 통해 변경의 여파를 차단함으로써, 데이터의 논리적 독립성과 물리적 독립성을 완벽히 보장한다.
> 3. **판단 포인트**: 세 가지 계층(외부/개념/내부)의 명확한 역할 구분과, 그 사이를 이어주는 두 가지 사상(Mapping) 메커니즘을 구체적으로 설명하는 것이 핵심이다.

## 출제 의도 및 답안 포인트

| 출제 의도 | 반드시 짚을 핵심 | 감점 회피 포인트 |
|:---|:---|:---|
| 데이터 모델링 추상화 및 독립성 원리 이해 확인 | 외부, 개념, 내부 스키마, 2단계 사상(Mapping), 데이터 독립성 | 3단계를 실제 3개의 분리된 데이터로 오개념 서술 |

> 요약: 스키마의 3단계 계층 구조를 그리고, 각 계층이 매핑을 통해 어떻게 논리적·물리적 데이터 독립성을 구현하는지 연계하여 기술한다.

## Ⅰ. 개요 및 필요성

- 개요: 복잡한 데이터베이스 구조를 사용자, 설계자, 개발자의 관점에 따라 외부, 개념, 내부 3단계로 추상화한 ANSI/SPARC 아키텍처
- 배경: 응용 프로그램과 물리적 데이터가 강하게 결합된 과거 파일 시스템의 데이터 종속성 및 잦은 유지보수 비용 문제
- 필요성: 사용자의 복잡도 은닉, DB 보안(권한 통제) 강화, 그리고 하위 구조 변경이 상위에 영향을 주지 않는 데이터 독립성 확보 필요

---

## Ⅱ. 구조 및 구성요소

```text
[ 사용자 1 ]       [ 사용자 2 ]        <-- 개별 사용자 관점
      |                  |
[ 외부 스키마 A ]  [ 외부 스키마 B ]   <-- (논리적 데이터 독립성)
      +--------+---------+                 (외부/개념 사상)
               |
         [ 개념 스키마 ]               <-- 전사적 논리 관점 (DBA)
               |                           (개념/내부 사상)
         [ 내부 스키마 ]               <-- 물리적 관점 (물리적 독립성)
               |
         [ 실제 데이터 (DB) ]
```

| 구성요소 | 역할 | 특이사항 |
|:---|:---|:---|
| 외부 스키마 (External) | 개별 사용자/응용 프로그램이 필요로 하는 부분적 DB 구조 | 하나의 DB에 여러 개 존재 가능 (View) |
| 개념 스키마 (Conceptual) | 조직 전체 관점의 논리적 구조, 엔티티 및 제약조건 정의 | 하나의 DB에 오직 1개 존재 |
| 내부 스키마 (Internal) | 물리적 저장 장치 입장에서의 데이터 저장 구조 (인덱스 등) | 시스템 프로그래머/DBA가 관리 |

> 요약: 개별 뷰(외부), 통합 논리 모델(개념), 물리 스토리지 명세(내부)로 관점을 분리하여 시스템 복잡도를 낮춘다.

---

## Ⅲ. 동작원리 및 흐름도

```text
사용자 질의(외부) -> 외부/개념 사상 -> 개념 질의 변환 -> 개념/내부 사상 -> 내부 물리 접근
```

- 1단계 [질의 입력]: 사용자가 외부 스키마(View)를 기준으로 SQL 질의 요청 (예: `SELECT * FROM 영업_View`)
- 2단계 [외부/개념 사상]: DBMS가 외부 스키마 명세를 개념 스키마 명세로 변환 (View에 정의된 실제 통합 테이블 조인 조건 해석)
- 3단계 [개념/내부 사상]: 논리적 테이블 접근 요청을 내부 스키마의 물리적 파일/인덱스 접근 경로(Plan)로 변환
- 4단계 [데이터 추출/반환]: 실제 디스크(스토리지)에서 데이터를 추출한 후, 역순의 매핑을 거쳐 사용자에게 반환

> 요약: 스키마 간 매핑 디렉터리를 참조하여 추상화된 논리 질의를 물리적 디스크 I/O 연산으로 변환(Translation)한다.

---

## Ⅳ. 특징

- 추상화(Abstraction): 물리적 저장 매체의 복잡성을 사용자에게 완벽히 숨겨 비즈니스 로직에만 집중하게 함
- 사상(Mapping) 오버헤드: 계층 간 변환 과정이 필수적이므로 쿼리 해석 비용이 발생(옵티마이저의 최적화로 상쇄)
- 보안 접근 통제: 외부 스키마(View)를 통해 사용자에게 허가된 데이터(컬럼/행)만 노출함으로써 원천적인 데이터 보안 제공

> 요약: 완벽한 데이터 독립성과 보안을 얻는 대신 매핑 오버헤드가 발생하나, 현대 DBMS는 이를 고도화된 엔진으로 최적화한다.

---

## Ⅴ. 심화 비교 및 적용 판단

| 비교 축 | 외부 스키마 | 개념 스키마 | 내부 스키마 |
|:---|:---|:---|:---|
| 관점 (Perspective) | 개별 사용자, 응용 프로그래머 | 조직 전체, 데이터 설계자(DA) | 시스템 엔지니어, 물리 DBA |
| 독립성 관련 | 논리적 데이터 독립성의 방패막 | 양쪽 독립성의 기준(Hub) 역할 | 물리적 데이터 독립성의 대상 |
| 구현/적용 기술 | View, 프로그램 내 쿼리 | ER 모델, DDL (CREATE TABLE) | 인덱스(B-Tree), 파티셔닝, Tablespace |

> 요약: 외부 스키마는 유연성을, 개념 스키마는 전사적 무결성을, 내부 스키마는 성능 최적화를 담당한다.

**리스크·대응 (기본은 불릿):**
- 스키마 관리 일관성 결여: 무분별한 외부 스키마(View) 남발로 인한 의존성 얽힘 및 성능 저하 → 전사 데이터 아키텍처(DA) 조직의 엄격한 형상 관리 (지표: 안 쓰이는 Zombie View 개수)
- 사상 비용 증가: 너무 복잡한 뷰 내 조인이나 서브쿼리로 인한 외부/개념 사상 시 병목 → Materialized View(구체화된 뷰) 도입으로 물리적 연산 최소화

---

## Ⅵ. 실무 적용 및 결론

**적용 방안 3개:**
1. 레거시 현대화(Modernization): 개념 스키마를 MSA 도메인 단위로 재설계하면서, 기존 응용 프로그램을 위해 외부 스키마(API 또는 뷰)는 그대로 유지하여 빅뱅 배포 리스크 제거
2. 데이터 보안 컴플라이언스 준수: 민감 개인정보(주민번호 등)가 포함된 개념 스키마 테이블 위에, 민감 정보를 마스킹(Masking)하거나 제외한 외부 스키마를 구성하여 외부 파트너사에 제공
3. 대용량 데이터베이스 튜닝: 응용 프로그램(외부 스키마) 코드 수정 없이, 내부 스키마 레벨에서 해시 파티셔닝과 SSD 스토리지 재배치를 통해 배치(Batch) 성능 개선

**결론 (2줄):**
- 기술사 판단: 3단계 스키마는 DBMS의 가장 근본적인 아키텍처 원칙이며, 개발자는 비즈니스 로직에, DBA는 성능 및 구조 최적화에 병렬적으로 집중할 수 있게 하는 핵심 기반이다.
- 향후 방향: 최근 Data Mesh 아키텍처에서는 중앙 집중형 개념 스키마 대신, 도메인별 분산된 스키마 관리를 지향하면서 유연한 형태의 추상화 모델로 발전하고 있다.
