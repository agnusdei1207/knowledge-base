# 📖 【암기용】 개념 완전 이해

> 목적: BMT를 제품 비교 시연이 아니라 동일 조건에서 성능·기능·운영성을 검증하는 절차로 이해하게 만든다.

## 한눈에
- **개요**: BMT(벤치마크 테스트)는 **소프트웨어 기술성 평가**의 정량적 검증 수단으로, 후보 제품·솔루션을 동일한 환경·데이터·시나리오에서 실제로 실행해 성능·기능·운영성을 비교하는 시험이다.
- **왜 필요한가**: 제안서의 카탈로그 수치(초당 처리량, 지연시간)는 벤더의 최적 조건에서 측정된 값이라 실제 운영 데이터량·연계 방식·보안 정책이 적용된 환경에서는 다르게 나올 수 있다.
- **핵심 직관**: 여러 자동차를 같은 코스, 같은 연료, 같은 짐 무게로 주행시켜 연비·제동거리를 비교하는 것과 같다. 조건이 하나라도 다르면 비교 자체가 무의미해진다.

## 핵심 용어 정리 (내부에 등장하는 것들)

| 용어 | 의미 | 비유 |
|:---|:---|:---|
| 소프트웨어 기술성 평가 (상위 개념) | 제안사의 기술 역량 전반을 배점화해 검증하는 절차 — BMT는 그중 정량 실측을 담당하는 하위 수단 | 종합 면접(기술성 평가) 안의 실기 시험(BMT) |
| BMT (Benchmark Test) | 후보 제품을 동일 조건에서 실행해 실측값으로 비교하는 시험 | 여러 차량을 같은 코스에서 주행시켜 비교 |
| PoC (Proof of Concept) | 특정 기술이 이 목적에 쓸 수 있는가를 소규모로 먼저 검증하는 개념 검증 | 시제품으로 아이디어가 되는지만 확인 |
| 동일 조건 (Controlled Condition) | 후보 제품 간 하드웨어·데이터량·네트워크·시간대를 동일하게 맞추는 통제 원칙 | 같은 코스, 같은 연료, 같은 짐 무게 |
| 배점표 | 기능·성능·운영·비용 항목별 만점과 통과 기준을 정한 표 | 실기 시험 채점표 |
| TPS / p95 | 초당 처리량 / 95번째로 느린 응답시간 — 성능 비교의 정량 지표 | 시간당 처리 대수 / 100명 중 95등 대기시간 |
| 기능충족률 | 필수 기능 목록 중 실제로 동작을 확인한 비율 | 체크리스트 항목 중 실제로 확인 도장 찍은 비율 |
| 재현성 / 증적 | 동일 조건에서 다시 실행해도 같은 결과가 나오도록 설정·로그·데이터를 보존하는 것 | 실험 노트에 조건을 다 적어 재실험 가능하게 하기 |

## 깊이 이해

### 왜 제안서 수치를 그대로 믿으면 안 되나 (배경)
- 벤더가 제시하는 "TPS 10,000, 지연 50ms" 같은 카탈로그 수치는 대개 최적 조건(작은 데이터량, 캐시가 완전히 데워진 상태, 전용 고성능 서버)에서 측정한 값이다. 실제 운영 환경은 데이터량이 훨씬 크고(예: 색인 1억 건), 기존 시스템과 연계(레거시 API 호출)가 붙고, 보안 정책(암호화, 권한 필터링)이 추가돼 부하가 다르다. 이 간극을 메우려면 실제와 유사한 조건에서 실측해야 한다 — 그것이 BMT다.

### BMT 절차를 수치로 따라가기 (검색 솔루션 워크드 예제)
1. **요구 확정**: 발주기관이 "1억 건 색인, 동시 사용자 1,000명, p95 검색 300ms 이하, 색인 지연 5분 이하, 권한 필터링 정확도 100%"를 필수 기준으로 명시한다.
2. **동일 환경 구성**: 후보 A·B·C 제품에 동일 사양 서버(예: 16 vCPU, 64GB RAM), 동일 1억 건 색인 데이터, 동일 네트워크 대역폭을 배정한다. 한 후보만 SSD를 더 준다거나 하면 결과가 무효화된다.
3. **테스트 실행**: 동일 검색 질의 세트(예: 실제 운영 로그에서 추출한 상위 1,000개 질의)를 동시 사용자 1,000명 조건으로 3사 모두에 동일 시간대에 돌린다.
4. **결과 측정**: A사는 p95 280ms·색인 지연 4분, B사는 p95 350ms(기준 초과)·색인 지연 6분(기준 초과), C사는 p95 250ms·색인 지연 3분으로 나온다면, 이 시점에서 성능 기준으로는 A·C만 통과, B는 탈락 후보가 된다.
5. **기능·운영 항목 결합**: 성능과 별개로 권한 필터링 정확도(예: A는 100%, C는 99.7%로 일부 노출 사고)를 확인해 최종 점수에 반영한다.

### BMT vs PoC — 언제 어느 것을 쓰나 (판별 원리)
- PoC는 "이 기술이 우리 문제에 원리적으로 맞는가"를 소규모·단일 후보로 빠르게 확인하는 단계다(예: 벡터 검색이 우리 데이터에 통할지 소량 데이터로 먼저 테스트).
- BMT는 "여러 후보 중 무엇을 최종 선정할 것인가"를 동일 조건·정량 배점으로 비교하는 단계다. 후보가 1개뿐이거나 원리 검증이 목적이면 PoC로 충분하고, 후보가 2개 이상이고 비용이 큰 도입 결정이면 BMT가 필요하다.

### 동일 조건을 어떻게 보장하나 (통제 원리)
- 환경 체크리스트로 하드웨어 사양, 데이터 버전, 네트워크 구성, 테스트 시각, 담당 엔지니어 개입 여부를 모든 후보에 대해 동일하게 기록·서명한다.
- 시나리오는 특정 벤더에게 유리한 조건(예: 그 벤더의 강점 기능만 테스트)이 아니라 발주기관의 실제 운영 로그 기반으로 공개 작성해 이의 제기 소지를 없앤다.
- 모든 실행 로그, 설정 파일, 결과 리포트를 보관해 나중에 재현해서 다시 봐도 같은 결과가 나오는지를 감사에서 검증할 수 있게 한다.

### 흔한 오해
- BMT는 벤더가 준비한 시연(데모)이 아니다. 벤더가 자기 환경에서 미리 튜닝해온 결과를 보여주는 것은 동일 조건이 깨진 것이라 BMT로 인정하지 않는다.
- "정성적으로 좋아 보인다"는 BMT 결과가 아니다. 반드시 사전에 정한 정량 기준(TPS, p95, 기능충족률)과의 합격·불합격 비교로 판정한다.

## 연결 개념
- 315 소프트웨어 기술성 평가 — BMT는 그 안의 정량 실측 검증 항목으로 포함
- 313 부하·스트레스·소크 테스트 — BMT의 성능 측정 시나리오에 그대로 활용되는 시험 기법
- PoC — 후보를 좁히기 전 단계의 원리 검증, BMT는 좁혀진 후보 간 최종 비교

# 📝 【답안용】 시험 답안 템플릿

> 목적: BMT의 절차, 평가 항목, 공정성 통제 방안을 시험 답안으로 전개한다.
> 핵심: BMT는 제품명 비교가 아니라 동일 조건과 증적 기반 평가가 핵심이다.

## 핵심 인사이트 (3줄 요약)

> 1. **본질**: BMT는 후보 SW·솔루션을 동일 조건에서 시험해 기능·성능·운영·비용 적합성을 비교하는 검증 절차다.
> 2. **가치**: 제안서의 주장과 실제 운영 조건 간 차이를 줄이고 도입 후 부적합 위험을 사전에 드러낸다.
> 3. **판단 포인트**: 시나리오, 데이터, 하드웨어, 배점, 판정 기준, 증적 보관이 동일해야 비교 결과가 유효하다.

## 출제 의도 및 답안 포인트

| 출제 의도 | 반드시 짚을 핵심 | 감점 회피 포인트 |
|:---|:---|:---|
| BMT 목적과 절차 이해 확인 | 평가 항목, 동일 조건, 결과 분석 | 제품 시연과 혼동 |
| 정량 평가 설계 역량 확인 | TPS, p95, 기능 충족률, 장애 복구 | 정성 평가만 제시 |
| 공정성·감사 대응 확인 | 테스트 데이터, 로그, 평가표 보관 | 공급사별 조건 차이 누락 |

> 요약: 이 문제는 후보 제품을 같은 조건으로 시험하고 정량 증거로 선정 판단을 내리는지를 본다.

## Ⅰ. 개요 및 필요성

- 개요: 후보 제품의 실측 비교 테스트
- 배경: 제안서 기반 선정은 기능 적합성, 처리량, 운영 편의성, 라이선스 비용을 실제 환경에서 확인하기 어려움
- 필요성: 동일 시나리오, 동일 데이터, 동일 평가표로 기능·성능·운영성·비용 요소를 검증해야 함

## Ⅱ. 구조 및 구성요소

```text
평가 요구 -> BMT 시나리오 -> 동일 환경 구성 -> 후보 제품 테스트 -> 점수 산정
              / 기능 / 성능 / 운영 / 보안 / 비용
```

| 구성요소 | 역할 | 특이사항 |
|:---|:---|:---|
| 평가 항목 | 비교 기준과 배점 정의 | 필수·선택·가점 구분 |
| 테스트 환경 | 동일 서버·데이터·네트워크 제공 | 환경 차이 기록 |
| 시험 시나리오 | 업무·부하·장애 조건 실행 | 운영 로그 기반 구성 |
| 결과 증적 | 로그·리포트·평가표 보관 | 감사와 이의 제기 대응 |

> 요약: BMT는 평가 항목, 동일 환경, 시험 시나리오, 증적 관리가 결합된 비교 테스트다.

## Ⅲ. 동작원리 및 흐름도

```text
요구 분석 -> 평가 항목 배점화 -> 환경 준비 -> 테스트 실행 -> 결과 비교
```

| 단계 | 처리 내용 | 검증 기준 |
|:---:|:---|:---|
| 1 | 도입 목적과 필수 요구 도출 | 요구사항 대응표 |
| 2 | 기능·성능·운영 항목 배점 설계 | 평가표, 감점 기준 |
| 3 | 동일 데이터와 인프라 구성 | 데이터 건수, HW 스펙 |
| 4 | 후보별 테스트 실행 | TPS, p95, 오류율, 기능 통과 |
| 5 | 점수 집계와 리스크 분석 | 결과표, 로그, 회의록 |

> 요약: BMT는 요구를 배점으로 바꾸고 같은 환경에서 실행한 결과를 정량 비교하는 순서로 진행된다.

## Ⅵ. 실무 적용 및 결론

**적용 방안 3개:**
1. RFP에 BMT 항목을 명시하고 기능 40점, 성능 30점, 운영·보안 20점, 비용 10점처럼 배점 공개
2. 운영 로그 기반 대표 시나리오와 동일 테스트 데이터 세트를 제공해 후보별 환경 차이를 제거
3. 실행 로그, 설정값, 모니터링 화면, 결과 리포트를 평가표와 함께 보관해 감사·이의 대응 증적으로 활용

**결론 (2줄):**
- 기술사 판단: 단순 범용 도구는 문서 평가로 충분할 수 있으나, 핵심 업무 성능·연계 리스크가 큰 솔루션은 BMT를 수행한다
- 향후 방향: BMT는 클라우드 비용, 보안 통제, 운영 자동화까지 포함하는 총소유비용 검증으로 확장된다
