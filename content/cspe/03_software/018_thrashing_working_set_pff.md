# 📖 【암기용】 개념 완전 이해

> 목적: 이 개념을 처음 보는 사람도 완벽히 이해하게 만든다. 시험 답안 양식이 아니라, 이해를 위한 친절한 설명이다.

## 한눈에
- **개요**: **스레싱(Thrashing)**은 메모리(RAM)가 꽉 차서 하드디스크와 페이지를 교체(I/O)하느라 정작 CPU는 일(연산)을 못 하고 컴퓨터가 멈춘 것처럼 버벅대는 현상이다. 이를 막기 위한 커널의 핵심 구제책이 **워킹셋(Working Set)**과 **PFF(Page Fault Frequency)**다.
- **왜 필요한가**: 다중 프로그래밍 환경에서 CPU 이용률을 높이려고 프로그램(프로세스)을 계속 띄우다 보면, 어느 순간 각 프로세스에게 나눠줄 메모리가 턱없이 부족해진다. 방금 쫓아낸 페이지를 또 불러오고 다시 쫓아내는 짓을 무한 반복하게 되므로 OS 차원의 개입(프로세스 강제 킬/서스펜드)이 필요하다.
- **핵심 직관**: 
  - 스레싱 = 도서관 책상이 꽉 차서, 책 하나 읽으려고 다른 책을 가방에 넣었다가, 1초 뒤에 다시 가방에서 그 책을 꺼내느라 정작 공부는 1쪽도 못 하는 바보 같은 상태.
  - 워킹셋 = "이 사람 공부할 때 무조건 같이 펴놓는 기본 세트(교과서+노트+볼펜)는 절대로 안 뺏을게"라고 보장해 주는 정책.
  - PFF = "가방 뒤지는 횟수(결석률)가 너무 높으면 빈 책상을 더 주고, 너무 안 뒤지면 책상 하나 뺏을게"라고 동적으로 조절하는 정책.

## 깊이 이해
- **배경·문제의식**: OS는 CPU가 쉬는 꼴을 못 본다. CPU 이용률이 떨어지면 "아, 메모리에 프로그램이 몇 개 없어서 CPU가 노는구나!"라고 착각하고 새 프로그램을 더 메모리에 욱여넣는다(MPD 증가). 이 오판이 겹치면서 결국 모든 프로세스가 I/O 대기 상태에 빠지고 CPU 이용률이 0%로 곤두박질치는 치명적 붕괴가 바로 스레싱이다.
- **작동 원리 (해결책 2가지)**: 
  - **워킹셋 (지역성 기반)**: 특정 시간(Delta) 동안 프로세스가 실제로 참조한 페이지 번호들의 집합을 유지한다. OS는 이 워킹셋 크기만큼의 빈 프레임이 남아있을 때만 그 프로세스를 메모리에 통째로 올려주고, 빈 공간이 부족하면 프로세스 전체를 디스크로 내쫓는다(Swap Out).
  - **PFF (통계/비율 기반)**: 페이지 폴트(Page Fault) 발생 횟수를 감시한다. 폴트율이 상한선(Upper Bound)을 넘으면 프레임을 하나 더 주고, 하한선(Lower Bound) 밑으로 떨어지면 프레임을 회수한다. 워킹셋처럼 참조한 걸 다 외우지 않아도 되어서 훨씬 실용적이다.
- **비유**: 
  - 스레싱: 과유불급. 밥상(RAM)에 반찬(프로그램)을 너무 많이 올려서 젓가락질(CPU 연산)할 공간조차 사라진 뷔페 대참사.
  - 워킹셋: 식당 예약. "우리 5명이 밥 먹으려면 최소 의자 5개짜리 테이블은 비워놔야만 들어갈 겁니다."
  - PFF: 손들고 요청. "사장님 여기 반찬 둘 공간이 너무 부족한데요(폴트 상한선 돌파), 옆 테이블 하나 더 붙여주세요."
- **흔한 오해·주의점**: 워킹셋은 "미래에 쓸 페이지"를 예측하는 것이 아니라, 철저히 "방금 전까지(과거 창) 쓴 페이지들의 집합"을 의미한다. 지역성(Locality) 덕분에 과거의 세트가 미래에도 그대로 유지될 거라 믿는 경험적 접근이다.

## 연결 개념
- **전역 교체 vs 지역 교체**: 스레싱은 프로세스 A가 메모리가 부족해서 프로세스 B의 프레임을 뺏어버리는 '전역 교체(Global Replacement)' 정책 때문에 도미노처럼 전염되어 터진다.
- **지역성 (Locality)**: 스레싱 방지 정책들이 성립하는 근본 원리. 루프를 돌거나 배열을 순회할 때는 특정 페이지 '그룹'만 뭉쳐서 불리기 때문에, 그 그룹(워킹셋)만 램에 묶어두면 폴트가 안 난다.

# 📝 【답안용】 시험 답안 템플릿

> 목적: 시험장에서 25분에 그대로 쓰는 답안 양식. 작성방식(추상표현 금지·수치·도식·문제유형 전환)을 엄격히 지킨다.
> 핵심: 이 시험은 정보를 많이 나열하는 시험이 아니라, 문제 신호어에서 출제자 의도를 읽고 핵심 논점을 선별해 쓰는 시험이다.

## 핵심 인사이트 (3줄 요약)

> 1. **본질**: 스레싱은 다중 프로그래밍 환경에서 과도한 페이지 교체(디스크 I/O)로 인해 시스템의 CPU 이용률이 0%로 수렴하는 치명적 병목 현상이다.
> 2. **가치**: 이를 막기 위해 프로세스의 지역성 기반 메모리 요구량(Working Set)을 보장하거나, 결석 빈도(PFF)를 동적으로 추적하여 프레임 할당량을 통제한다.
> 3. **판단 포인트**: 다중 프로그래밍 정도(MPD) 증가가 낳는 CPU 이용률 붕괴 커브를 도식화하고, 워킹셋(지역성/과거 참조)과 PFF(상하한선/직접 조절)의 프레임 할당 철학 차이를 비교해야 한다.

## 출제 의도 및 답안 포인트

| 출제 의도 | 반드시 짚을 핵심 | 감점 회피 포인트 |
|:---|:---|:---|
| 스레싱 발생의 메커니즘 도식화 | MPD 증가와 CPU 이용률 급락 임계점 | 단순 메모리 부족이 아닌 디스크 I/O 대기 폭주로 인한 CPU 유휴 상태 규명 |
| 커널의 스레싱 방어 알고리즘 2종 대조 | Working Set(시간 창 추적) vs PFF(폴트율 추적) | 두 알고리즘이 궁극적으로 프로세스를 Swap Out 시키는 동일한 목적임을 누락하는 오류 |

> 요약: 스레싱은 "공간이 부족해서 일을 못 하는 것"을 "일거리가 없어서 노는 것"으로 착각한 OS 스케줄러의 오판이 부른 참사다.

## Ⅰ. 개요 및 필요성

- 정의: 스레싱(Thrashing)은 프로세스 처리 시간보다 페이지 교체(Swap I/O) 시간이 더 많아져 CPU 이용률이 급락하는 현상
- 배경: 전역 페이지 교체 정책 하에서 MPD(다중 프로그래밍 정도)를 무리하게 높이면, 프로세스들이 서로의 프레임을 뺏고 뺏기며 연쇄적인 Page Fault 폭증 유발
- 필요성: 시스템 붕괴를 막기 위해, 각 프로세스가 원활히 실행되기 위한 최소한의 프레임 할당량을 보장하고, 램이 부족하면 일부 프로세스를 완전히 내쫓는 통제 기법(Working Set, PFF) 필수

## Ⅱ. 스레싱(Thrashing) 발생 메커니즘과 CPU 이용률 붕괴

```text
[ 다중 프로그래밍 정도(MPD)와 CPU 이용률(Utilization) 커브 ]

CPU 100% |        /---(최적점)
이용률   |       /           \  🚨 임계점 돌파! 
         |      /             \ 
         |     /               \  (Thrashing 발생 구역)
   0%    |----/                 \______________
           낮음 <---- MPD 증가 ----> 매우 높음 (프로세스 수)

1. CPU 이용률 저하 -> 2. OS가 "프로세스가 부족해!" 착각 -> 3. 새 프로세스 투입 (MPD 증가)
4. 메모리 극도 부족 -> 5. 잦은 Page Fault -> 6. I/O 대기 폭증 -> 1번으로 악순환
```

| 동작 단계 | OS 스케줄러의 오판 | 물리적 시스템 현상 |
|:---|:---|:---|
| 초기 | MPD를 높일수록 CPU 가동률이 정비례 상승 | 램이 여유로워 Page Fault가 거의 없음 |
| 임계점 돌파 | I/O 대기로 CPU가 쉬는 것을 '일감 부족'으로 오해 | 할당 프레임 수 < 임계 구역 크기 (부족) |
| 스레싱 돌입 | 남의 프레임을 뺏기 위해 연쇄적 디스크 I/O 유발 | CPU 사용률 0% 수렴, 하드디스크 I/O 100% 폭주 |

> 요약: 너무 많은 태스크를 동시에 돌리려는 탐욕이 낳은, 전역 페이지 교체 시스템 고유의 도미노 재앙이다.

## Ⅲ. 스레싱 극복 아키텍처: 워킹셋(Working Set) vs PFF 심화 비교

| 비교 축 | 워킹 셋 (Working Set) | 페이지 부재 빈도 (PFF, Page Fault Frequency) |
|:---|:---|:---|
| **제어 철학 및 기준** | **참조 지역성 (Locality)**: 과거 $\Delta$(Window Size) 동안 참조된 페이지 번호 집합 유지 | **통계적 비율 (Fault Rate)**: 단위 시간당 Page Fault 발생 횟수 측정 |
| **프레임 할당 룰** | $\Sigma W_i$(요구 프레임 총합) > 물리 메모리 크기면, 특정 프로세스를 스왑 아웃(Swap-out) | 폴트율 > 상한선(Upper Bound)이면 프레임 추가 증정. 폴트율 < 하한선(Lower)이면 프레임 회수 |
| **운영체제 유지비용** | 매 참조마다 워킹 셋 윈도우를 갱신해야 하므로 타임스탬프 등 막대한 하드웨어 오버헤드 | Fault가 터질 때만 비율을 계산하면 되므로 실무적 구현 비용이 훨씬 저렴 |
| **해결의 본질** | "공부할 때 볼펜, 노트, 책 3개가 한 세트니 이 3개 공간은 무조건 보장해 줄게" | "가방에서 책 꺼내는 횟수가 너무 잦으면 책상을 하나 더 놔줄게" |

> 요약: 워킹 셋이 완벽한 이상주의(미시적 추적)라면, PFF는 적당히 눈치 보며 덩어리를 던져주는 실용주의(거시적 통제)다. 두 기법의 결론은 모두 "램이 부족하면 과감하게 프로세스 하나를 Kill/Suspend 하라"는 것이다.

## Ⅳ. 극복해야 할 한계와 실무 튜닝 방안

커널 레벨의 스레싱은 현대 대용량 램으로 억제되지만, 애플리케이션 레벨(JVM, 클라우드)에서 변형된 형태로 계속 출몰한다.

| 리스크 요인 | 발생 원인 | 아키텍처 대응 방안 (실무 튜닝) |
|:---|:---|:---|
| JVM GC 스레싱 | 힙(Heap) 메모리를 너무 작게 주어, 가비지 컬렉터(GC)가 객체를 지우느라 CPU 자원을 다 쓰고 정작 애플리케이션 코드는 정지하는 현상 | `XX:GCTimeRatio` 파라미터 조절 및 `Xmx`를 여유롭게 할당하여 처리량(Throughput) 방어 |
| OOM (Out Of Memory) 연쇄 킬 | Linux 환경에서 Swap 스레싱을 막고자 Swap을 아예 껐을 때(K8s 등), 트래픽 피크 시 커널이 OOM Killer를 띄워 핵심 DB 프로세스를 죽임 | 프로세스별 `/proc/<pid>/oom_score_adj` 값을 조절하여 SSH나 메인 DB는 죽지 않도록 방어 통제 |

> 요약: 현대 서버(K8s 기반 클라우드)는 스레싱으로 전체 노드가 느려져 연쇄 장애가 터지는 것보다 차라리 "Swap 메모리를 끄고 메모리 오버 시 빠르게 컨테이너를 죽여버리는(Kill)" 극단적 예방 조치를 선호한다.

## Ⅴ. 실무 적용 방안 및 결론

**적용 방안 3개:**
1. [클라우드 컨테이너(K8s) 스레싱 차단] 쿠버네티스 워커 노드 배포 시 리눅스 스왑(Swap) 파티션을 아예 비활성화(Kubelet 기본 정책)하여 디스크 I/O 스레싱 원천 차단 후, `limits.memory` 파라미터로 철저한 OOM 격리 적용
2. [Elasticsearch Heap 사이징] 검색 엔진 워킹셋 확보를 위해, 물리 메모리의 절반(최대 32GB)만 JVM Heap으로 주고, 나머지 절반은 운영체제의 Page Cache(파일 캐시)가 독점하도록 남겨두어 루씬(Lucene) 인덱스의 I/O 스레싱 방지
3. [국부 교체(Local Replacement) 정책 융합] 전역 교체가 부르는 도미노 스레싱을 막기 위해, 프로세스를 그룹(Cgroup) 단위로 묶어 자기 그룹 안에서만 페이지를 교체(Evict)하도록 리소스 쿼터(Quota)를 격리 할당

**결론:**
- 기술사 판단: 스레싱은 자원의 탐욕(다중 프로그래밍)이 부르는 파멸이다. 워킹 셋과 PFF는 "다 같이 부족하게 나눠 쓰다간 다 같이 죽는다. 살릴 놈만 확실히 살리고 나머지는 잠재워라"는 운영체제의 냉혹한 최적화 철학을 대변한다.
- 향후 방향: 최근 CXL(Compute Express Link) 메모리 확장 기술이나 비휘발성 메모리(NVDIMM)가 도입되면서, 램과 스토리지의 경계가 무너지고 있으며, Page Fault에 의한 스와핑 지연 자체가 하드웨어 속도로 은닉되는 새로운 메모리 티어링(Tiering) 아키텍처로 진화 중이다.
