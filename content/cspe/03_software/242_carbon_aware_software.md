## Ⅰ. 개요
- **정의**: 전력망 탄소 강도에 따라 워크로드 실행 시점·위치를 조절하는 SW 설계 방식임
- **배경/필요성**: 동일 전력이라도 재생에너지 비율에 따라 탄소 배출이 달라지므로, 저탄소 시간대·지역으로 작업을 이동시키는 전략이 필요함
- **비유**: 전기 요금이 저렴한 심야에 세탁기를 돌리는 것과 같은 원리임

| 출제 의도 | 반드시 짚을 핵심 | 감점 회피 포인트 |
|:---|:---|:---|
| 시간·공간 이동 전략 구분 | Temporal Shifting vs Spatial Shifting | Green Software(241 참조)와의 관계를 명확히 할 것 |

> 요약: 탄소 강도가 낮은 시간·지역으로 워크로드를 이동시켜 배출을 줄이는 설계 방식임

## Ⅱ. 구성요소
```text
+-- Carbon Aware Software --+
|                            |
|  Carbon API ---> Scheduler |
|                    |       |
|        +-----------+--+    |
|        v              v    |
|  Temporal Shift  Spatial Shift |
+----------------------------+
```

| 구성요소 | 설명 | 비유 |
|:---|:---|:---|
| Carbon Intensity API | 지역·시간대별 전력망 탄소 계수를 제공하는 외부 데이터 소스임 | 실시간 전기요금 조회 앱 |
| Scheduler | 탄소 데이터 기반으로 워크로드 실행 시점·위치를 결정하는 제어기임 | 요금 비교 후 예약하는 스케줄러 |
| Temporal Shifting | 저탄소 시간대로 배치 작업을 지연 실행하는 전략임 | 심야 전력 활용 |
| Spatial Shifting | 저탄소 지역의 데이터센터로 워크로드를 라우팅하는 전략임 | 전기료 싼 지역으로 공장 이전 |

> 요약: 탄소 API, 스케줄러, 시간·공간 이동 전략으로 구성됨

## Ⅲ. 절차
```text
탄소 데이터 수집 --> 최적 시점/위치 판단 --> 워크로드 스케줄링 --> 결과 모니터링
```
- 1단계: Carbon Intensity API로 향후 24~48시간 탄소 예측 데이터 수집
- 2단계: 배치 작업의 SLA 허용 범위 내에서 최저 탄소 시간대·지역 선정
- 3단계: 스케줄러가 선정된 시점·위치로 워크로드 디스패치
- 4단계: 실행 후 SCI(241 참조) 기반 탄소 절감량 측정 및 대시보드 반영

> 요약: 탄소 예측 → 최적 판단 → 디스패치 → 모니터링 순으로 수행함

## Ⅳ. 문제점
- SLA 충돌: 저탄소 시간대 대기가 응답 지연을 유발하여 서비스 품질 저하 가능함
- 예측 부정확: 재생에너지 발전량 예측 오차로 탄소 강도 예측 신뢰도가 제한적임
- 멀티 클라우드 복잡성: 이기종 클라우드 간 워크로드 이동 시 네트워크·데이터 이동 비용 증가함

> 요약: SLA 제약, 예측 오차, 멀티 클라우드 이동 비용이 주요 과제임

## Ⅴ. 개선방안
1. 단기: SLA 등급별 지연 허용 범위를 정의하여 탄소 최적화와 품질 간 균형 확보
2. 중기: ML 기반 탄소 강도 예측 모델 도입으로 예측 정확도 향상
3. 장기: 클라우드 간 워크로드 이동 표준 API 확립으로 전환 비용 최소화

> 요약: SLA 정책, ML 예측, 표준 API를 통해 탄소 인식 SW의 실용성을 높임

## Ⅵ. 전망
- 발전 방향: 실시간 탄소 인식이 OS·미들웨어 수준에 내장되는 방향으로 발전할 전망임
- 기술사적 판단: 지연 허용 워크로드(배치, 학습, CI/CD)부터 우선 적용하는 것이 현실적임
- 기술사 제언: 그린 SLA 개념을 도입하여 탄소 절감과 서비스 품질을 동시에 관리하는 체계 구축이 필요함
