# 📖 【암기용】 개념 완전 이해

## 한눈에
- **개요**: **탄소 인지 소프트웨어(Carbon-Aware Software)**는 전력망의 탄소 배출량 정보를 인지하고, 재생 에너지가 풍부하거나 탄소 배출이 적을 때(또는 그런 지역에서) 작동하도록 설계된 소프트웨어다.
- **왜 필요한가**: 전기를 적게 쓰는 것(에너지 효율)만으로는 부족하다. 풍력, 태양광 등 재생 에너지는 시간과 날씨에 따라 발전량이 변동하므로, 전기가 생산되는 '시점'과 '장소'에 맞춰 전력 수요(컴퓨팅 작업)를 이동시켜야 실제 탄소 배출을 줄일 수 있다.
- **핵심 직관**: 빨래를 할 때, 전기 요금이 가장 쌀 때를 기다려 세탁기를 돌리는 것과 같다. 이를 소프트웨어의 배치 작업이나 AI 학습에 적용한 것이다.

## 핵심 용어 정리

| 용어/표기 | 의미 | 비유·예 |
|:---|:---|:---|
| 탄소 집약도 (Carbon Intensity) | 1kWh의 전기를 생산하는 데 배출되는 탄소량 | 전기의 '오염도' 지수 |
| 공간 이동 (Spatial Shifting) | 워크로드를 탄소 집약도가 낮은 물리적 리전(데이터센터)으로 옮기는 것 | 해가 떠 있는 나라의 서버 사용하기 |
| 시간 이동 (Temporal Shifting) | 워크로드를 탄소 집약도가 낮은 시간대로 미뤄서 실행하는 것 | 바람이 강하게 불 때 야간 배치 작업 돌리기 |
| 수요 조절 (Demand Shaping) | 탄소 집약도에 따라 서비스 품질이나 연산량을 동적으로 조절하는 것 | 전기가 더러울 때 비디오 화질을 4K에서 1080p로 낮추기 |

## 깊이 이해
- **배경·문제의식**: 클라우드 데이터센터는 막대한 전력을 사용한다. 클라우드 제공자가 재생 에너지를 100% 구매(RE100)하더라도, 실제 특정 시간에 해당 데이터센터에 공급되는 전기는 화석 연료 기반일 수 있다. 진정한 넷제로(Net-Zero)를 달성하려면, 소프트웨어 워크로드 자체가 그리드의 실시간 탄소 데이터에 반응해야 한다.
- **작동 원리**: Carbon Aware SDK 같은 API를 통해 전력망의 실시간 예측 탄소 집약도 데이터를 받아온다. 소프트웨어의 스케줄러가 이를 판단하여, ① 탄소 배출이 적은 시간으로 작업 예약(시간 이동), ② 재생 에너지가 많은 리전으로 컨테이너 이주(공간 이동), ③ 실시간 스트리밍 화질 낮춤(수요 조절)을 수행한다.
- **비유**: 식당 예약 시스템이다. 손님(소프트웨어)이 식당(데이터센터)에 밥(전기)을 먹으러 갈 때, 혼잡한 시간(고탄소 배출 시간)을 피해 한가한 시간(저탄소 시간)에 가거나, 덜 혼잡한 지점(저탄소 리전)으로 발길을 돌리는 것이다.
- **구체 예시**: 머신러닝 모델 학습. 1주일이 걸리고 언제 끝나도 상관없는 AI 모델 학습 작업을 탄소 집약도 예측 API와 연동된 쿠버네티스 스케줄러에 맡긴다. 스케줄러는 낮 시간(태양광 발전)에 집중 학습하고 저녁에는 일시 정지한다.
- **흔한 오해·주의점**: 모든 소프트웨어가 탄소 인지형이 될 수는 없다. 실시간성이 필수적인 사용자 요청(웹서버 응답, 결제 처리 등)은 시간 이동이 불가능하다. 주로 배치 처리, AI 학습, 백업, 비디오 인코딩 같은 **지연 허용(Delay-Tolerant)** 워크로드에 적합하다.

## 연결 개념
- 소프트웨어 그린 엔지니어링 SCI 지수 (Carbon Awareness는 SCI 지수 중 I(탄소 집약도)를 낮추는 핵심 방법)
- 서버리스 컴퓨팅 (부하에 따른 유연한 확장이 수요 조절과 맞물림)
- 쿠버네티스 스케줄링 (Pod의 공간 이동 구현 기술)

> 1. **본질**: 탄소 인지 소프트웨어는 전력망의 실시간 탄소 집약도 데이터를 기반으로 컴퓨팅 워크로드의 실행 시간과 위치를 동적으로 조정하는 아키텍처이다.
> 2. **가치**: 단순한 에너지 절감을 넘어, 실제 재생 에너지 사용률을 극대화하여 소프트웨어의 실효적인 탄소 배출량을 감축한다.
> 3. **판단 포인트**: 공간 이동, 시간 이동, 수요 조절의 3대 핵심 기법을 지연 허용 워크로드 특성에 맞게 적용하는 설계 역량이 필수적이다.

| 출제 의도 | 반드시 짚을 핵심 | 감점 회피 포인트 |
|:---|:---|:---|

> 요약: 에너지 효율성 향상만으로는 부족하며, 전기의 '오염도'에 반응하여 작업의 시공간과 강도를 조절하는 메커니즘을 제시해야 한다.

## Ⅰ. 개요 및 필요성

- 개요: 탄소 인지 소프트웨어(Carbon-Aware Software)는 전력의 탄소 집약도(Carbon Intensity)에 반응하여 적을 때는 작업을 더 많이, 많을 때는 적게 수행하는 소프트웨어임
- 배경: 재생 에너지는 시간(일조량, 풍량)과 장소에 따라 발전량이 변동하므로, 전력 수요(컴퓨팅)도 이에 맞춰 유연하게 변동해야 함
- 필요성: 클라우드 환경에서 실질적인 탄소 중립(Net-Zero)을 달성하고 SCI(Software Carbon Intensity) 지수를 낮추기 위한 선제적 대응이 필요함

---

## Ⅱ. 구조 및 구성요소

```text
[탄소 인지 아키텍처 처리 구조]
External API (Grid Carbon Data) -> Carbon Aware Controller -> Workload Scheduler
                                                                |
           +--------------------+-------------------------+-----+
           |                    |                         |
    Temporal Shifting   Spatial Shifting          Demand Shaping
   (시간 지연 실행)       (타 리전 배포)         (서비스 품질 동적 조절)
```

| 구성요소 | 역할 | 특이사항 |
|:---|:---|:---|
| 외부 탄소 API | 지역/시간별 전력망의 실시간 및 예측 탄소 집약도 수집 | WattTime, Electricity Maps 등 활용 |
| 탄소 인지 컨트롤러 | 수집된 데이터를 분석하여 워크로드의 스케줄링 정책 결정 | 쿠버네티스 커스텀 스케줄러 형태로 구현 |
| 지연 허용 워크로드 | 배치 처리, AI 학습, 백업 등 시간/장소 제약이 적은 작업 | 유연성이 높을수록 최적화 효과 큼 |

> 요약: 실시간 탄소 데이터를 수집하는 컨트롤러가 스케줄러를 제어하여, 지연 허용 워크로드를 3가지 전략(시·공간 이동, 수요 조절)으로 최적화한다.

---

## Ⅲ. 동작원리 및 흐름도

```text
탄소 데이터 수집 -> 워크로드 특성 분석 -> 최적화 전략 결정(시간/공간/수요) -> 동적 실행 통제
```

- 1단계 [탄소 데이터 수집]: 탄소 집약도 API를 주기적으로 폴링하여 각 리전의 현재 및 예측 탄소 수치 획득
- 2단계 [워크로드 분석]: 큐에 대기 중인 작업의 데드라인, 리소스 요구량, 이동 가능성(상태 유지 여부) 분석
- 3단계 [전략 매핑]: 시간적 여유가 있으면 시간 이동, 다른 저탄소 리전 사용이 유리하면 공간 이동 선택
- 4단계 [실행 및 통제]: 워크로드 스케줄러(K8s)가 컨테이너를 목표 리전/시간에 할당하고 종료 시 SCI 점수 기록

> 요약: 탄소 예측 데이터와 워크로드의 SLA(데드라인)를 교차 분석하여 가장 탄소 배출이 적은 시점과 장소를 찾아 작업을 실행한다.

---

## Ⅳ. 특징

- 동적 적응성: 정적인 배포 아키텍처가 아닌, 외부 환경(전력망 상태) 변수에 따라 시스템 행위가 실시간으로 변함
- 트레이드오프 수용: 탄소 배출 감축을 위해 응답 시간 지연이나 서비스 품질 저하(예: 화질 저하)를 의도적으로 수용함
- 생태계 의존성: 클라우드 사업자가 제공하는 재생 에너지 리전과 투명한 탄소 데이터 인프라가 필수적임

> 요약: 성능 극대화 대신 친환경성에 가중치를 두어 성능·품질 트레이드오프를 수용하는 동적 적응형 시스템이다.

## Ⅴ. 심화 비교 및 적용 판단

| 비교 축 | 에너지 효율 소프트웨어 | 탄소 인지 소프트웨어 | 선택 기준 |
|:---|:---|:---|:---|
| 목적 | 소비 전력(kWh) 자체의 절대적 감축 | 배출되는 탄소량(gCO2)의 감축 | 전체 에너지 비용 절감 vs 탄소 중립 달성 |
| 주요 방법 | 알고리즘 최적화, 캐싱, 리소스 우측정 | 시공간 워크로드 이동, 수요 조절 | 워크로드 특성(실시간 vs 지연 허용) |
| 변동성 대응 | 하드웨어 부하 변동에 대응 | 외부 전력망 탄소 변동에 대응 | 적용 대상의 환경 제약 |

> 요약: 에너지 효율화는 언제 어디서나 전력을 덜 쓰는 코드 레벨 접근이며, 탄소 인지는 전기가 깨끗할 때 연산 능력을 집중하는 아키텍처 접근이다.

**리스크·대응:**
- 데이터 법적 규제: 공간 이동 시 데이터 주권(Data Sovereignty) 규정 위반 리스크 → 유럽 GDPR 등 데이터 국지화(Localization) 정책 기반 필터링 룰 적용
- SLA 위반: 과도한 시간 이동으로 인한 비즈니스 데드라인 초과 → Carbon Aware SDK에 최대 지연 허용 시간(Max Delay) 파라미터 필수 설정

## Ⅵ. 실무 적용 및 결론

**적용 방안 3개:**
1. **시간 이동(Temporal Shifting)**: 데이터 백업, 대규모 배치 리포팅, 주기적 웹 크롤링 작업을 일괄 자정 실행에서 탄소 예측 모델 기반의 최저 배출 시간대로 CronJob 재설정
2. **공간 이동(Spatial Shifting)**: 쿠버네티스 페더레이션(KubeFed)을 활용하여 탄소 집약도가 낮은 타 국가 리전으로 CI/CD 빌드 파이프라인 컨테이너 자동 마이그레이션
3. **수요 조절(Demand Shaping)**: 전력 피크 타임 및 고탄소 시간대에 AI 추천 알고리즘의 복잡도를 낮추거나, 사용자 스트리밍 서비스의 기본 해상도를 하향 조정하여 연산 부하 경감

**결론:**
- 기술사 판단: 탄소 인지 소프트웨어는 비즈니스 도메인의 SLA(응답성)와 탄소 감축(지속가능성) 간의 정밀한 조율이 필요하므로, 지연 허용 워크로드부터 단계적(Strangler)으로 분리 적용해야 함
- 향후 방향: 클라우드 네이티브 생태계는 FinOps와 결합하여 비용, 성능, 탄소 배출을 복합적으로 스케줄링하는 GreenOps 컨트롤 플레인 형태로 진화할 것임
