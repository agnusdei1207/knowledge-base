# 📖 【암기용】 개념 완전 이해

> 목적: 탄소 인지 소프트웨어를 처음 봐도 완전히 이해하게 만든다. 시험 답안 양식이 아니라, 이해를 위한 친절한 설명이다.

## 한눈에
- **개요**: Carbon-Aware Software는 **탄소 인지 컴퓨팅(Carbon-Aware Computing)**의 실행 기법으로, 전력망의 **탄소 집약도** 신호에 맞춰 작업의 실행 시점·지역·자원량을 조정하는 소프트웨어 설계 방식이다.
- **왜 필요한가**: 같은 워크로드도 언제·어디서 실행하느냐에 따라 배출 탄소량이 크게 달라진다. 하지만 사용자가 지금 당장 결과를 봐야 하는 작업(로그인, 결제)까지 늦출 수는 없다. 탄소 인지 설계는 "늦춰도 되는 작업"과 "늦추면 안 되는 작업"을 구분해, 늦출 수 있는 작업만 저탄소 시간·지역으로 옮긴다.
- **핵심 직관**: 세탁기를 지금 당장 돌리지 않아도 되면 전기요금과 탄소 배출이 적은 심야 시간에 예약 돌리는 것과 같다 — 단, 당장 써야 하는 정수기(실시간 서비스)는 예약 대상이 아니다.

## 핵심 용어 정리 (내부에 등장하는 것들)

| 용어 | 의미 | 비유 |
|:---|:---|:---|
| 탄소 인지 컴퓨팅 | 탄소 배출 신호를 시스템 운영 결정에 반영하는 전체 접근 방식(상위 개념) | "탄소를 계기판에 띄운 자동차" |
| 탄소 집약도(Carbon Intensity) | 전력 1kWh 생산 시 배출되는 탄소량, gCO2e/kWh(241 SCI의 I와 동일 개념, 시간·지역별로 변동) | 시간대별로 달라지는 "전기의 청정도" |
| 워크로드 분류(Workload Classifier) | 작업을 실시간(즉시 실행 필요)·지연 허용(배치)으로 나누는 판정 로직 | 우편물을 "특급"과 "일반"으로 구분 |
| deadline(마감시한) | 지연 허용 작업이 반드시 끝나야 하는 최종 시점 | 과제 제출 마감일 |
| latest start time(최종 시작 시각) | deadline을 지키기 위해 늦어도 시작해야 하는 시각 = deadline − 예상 소요시간 | "지금 출발 안 하면 지각"인 시각 |
| fallback(대체 실행) | 저탄소 조건을 못 찾았을 때 deadline을 지키기 위해 즉시 실행으로 전환하는 안전장치 | 예약 세탁이 안 되면 그냥 지금 돌리는 것 |
| 데이터 주권(Data Residency) | 특정 데이터를 특정 국가·리전 밖으로 옮기지 못하게 하는 규제 제약 | 여권 없이는 국경을 못 넘는 규칙 |

## 깊이 이해

### 241(SCI)과의 관계 — 측정에서 실행으로
- 241에서 다룬 SCI는 탄소 배출을 측정하고 비교하는 지표였다(241 Green Software SCI 참조). Carbon-Aware Software는 그 측정값(특히 탄소 집약도 I)을 실제 "언제·어디서 실행할지" 결정하는 운영 정책으로 바꾸는 실행 단계다. SCI가 성적표라면, 탄소 인지 스케줄링은 그 성적을 올리기 위한 실행 계획이다.

### 작업을 나누는 기준과 스케줄링 원리
- 모든 작업을 탄소 낮은 시간으로 미룰 수는 없다. 결제 API처럼 사용자가 즉시 응답을 기다리는 작업은 SLO(예: p95 200ms)를 우선하고 탄소 인지 정책에서 제외한다.
- 반대로 로그 집계, 배치 리포트, 모델 학습처럼 "정해진 시간 안에만 끝나면 되는" 작업은 deadline을 부여하고, 그 안에서 탄소 집약도가 가장 낮은 시간대를 골라 실행한다.
- **판별 원리**: 작업을 지연 허용으로 분류하려면 ① 사용자가 결과를 실시간으로 기다리지 않을 것 ② deadline이 최소 수십 분~수 시간 이상일 것 ③ 데이터 위치 제약이 없거나 허용 리전이 있을 것, 이 세 조건을 함께 충족해야 한다.

### latest start time을 숫자로 계산하기 (워크드 예제)
- 로그 집계 배치의 예상 소요시간이 30분, deadline이 05:00라면 latest start time = 05:00 − 30분 = 04:30이다. 즉 04:30까지는 실행을 미룰 수 있다.
- 이 배치를 00:00에 즉시 실행하면 그 시간대 탄소 집약도가 500gCO2e/kWh라고 하자. 반면 03:00~05:00 구간(재생에너지 비중이 높은 새벽 시간)의 탄소 집약도가 250gCO2e/kWh라면, 같은 30분 작업(전력 소비 1kWh 가정)을 이 구간으로 옮길 때 배출량은 500gCO2e에서 250gCO2e로 정확히 절반이 된다.
- 만약 예보상 03:00~05:00 구간에도 탄소 집약도가 낮아지지 않거나 큐가 밀려 04:30까지 자리가 없다면, latest start time인 04:30에는 무조건 fallback으로 즉시 실행해 deadline을 지킨다 — 탄소 절감보다 deadline 준수가 마지막 우선순위에서 이긴다.

### 리전 이동과 데이터 주권 제약
- 탄소 집약도는 지역마다도 다르므로 작업을 다른 리전으로 옮겨 실행하는 것도 방법이다. 하지만 개인정보나 금융 데이터는 국가별 규제로 특정 리전 밖으로 이동이 금지될 수 있다(데이터 주권). 그래서 리전 이동은 "허용 리전 목록"을 먼저 정의하고 그 안에서만 저탄소 후보를 고른다.
- 리전 이동은 물리적 거리만큼 응답 지연(RTT)도 늘어난다. 예: 같은 국가 내 리전 이동은 RTT가 수 ms~수십 ms 늘지만, 대륙 간 이동은 수백 ms까지 늘 수 있어 실시간 작업에는 적용하지 않는다.

### 비유와 흔한 오해
- **비유**: 전력 회사가 "지금은 석탄 발전 비중이 높으니 세탁기를 미뤄 달라"는 신호를 보내면, 탄소 인지 소프트웨어는 그 신호를 받아 "지금 당장 안 해도 되는 일"부터 자동으로 미루는 가전제품과 같다.
- **흔한 오해**: "모든 서비스를 저탄소 시간대로 옮기면 된다"는 생각은 틀렸다. 사용자 요청 경로(로그인, 결제, 조회)까지 지연시키면 서비스 품질(SLO)이 무너진다. 탄소 인지 설계는 지연 허용 작업에만 적용되는 선택적 최적화이지, 전체 시스템을 느리게 만드는 정책이 아니다.

## 연결 개념
- Green Software SCI (241) — 탄소 인지 정책의 개선 효과를 gCO2e/unit으로 검증하는 측정 지표
- Job Scheduler — deadline·latest start time 계산을 실제로 수행하는 실행 엔진
- Data Residency 규제 — 리전 이동 가능 범위를 제한하는 법적 제약

# 📝 【답안용】 시험 답안 템플릿

> 목적: 시험장에서 25분에 그대로 쓰는 답안 양식. 작성방식(추상표현 금지·수치·도식·문제유형 전환)을 엄격히 지킨다.
> 핵심: 탄소 인지 문제는 시간 이동, 지역 이동, 자원 조정 중 어떤 선택이 SLO와 규제를 만족하는지 판단하는 답안으로 구성한다.

## 핵심 인사이트 (3줄 요약)

> 1. **본질**: Carbon-Aware Software는 탄소 집약도 신호를 애플리케이션 스케줄링·배치·오토스케일링 정책에 반영하는 설계 방식이다.
> 2. **가치**: 지연 허용 워크로드를 저탄소 시간·리전으로 이동해 gCO2e/job을 줄이고, 사용자 경로는 SLO 기준으로 보호한다.
> 3. **판단 포인트**: deadline, 데이터 위치, 리전 규제, 탄소 예보 정확도, 비용·지연 트레이드오프를 함께 검토한다.

## 출제 의도 및 답안 포인트

| 출제 의도 | 반드시 짚을 핵심 | 감점 회피 포인트 |

| 클라우드 제약 판단 확인 | 데이터 주권, 지연시간, 리전별 계수 | 리전 이동 시 개인정보·규제 누락 |

## Ⅰ. 개요 및 필요성

- 개요: 탄소 인지 소프트웨어는 탄소 신호 기반 실행 설계이다.
- 배경: 클라우드 리전과 시간대별 gCO2e/kWh 차이가 커지면서 동일 워크로드도 운영 시점에 따라 배출량이 달라진다.
- 필요성: SLO와 규제 기준을 만족하는 범위에서 전력망 탄소 신호를 배치·스케줄링 정책에 반영해야 한다.

---

## Ⅱ. 구조 및 구성요소

```text
Carbon Signal API -> Policy Engine -> Workload Classifier
                  -> Scheduler / Router / Autoscaler -> Metrics
```

| 구성요소 | 역할 | 특이사항 |
|:---|:---|:---|
| Carbon Signal API | 리전·시간별 gCO2e/kWh 현재값·예보 제공 | Electricity Maps, WattTime 등 |
| Workload Classifier | 실시간·지연 허용·배치 작업 분류 | deadline, SLO, 데이터 위치 |
| Policy Engine | 탄소·비용·지연 조건을 정책으로 결정 | 우선순위와 제외 조건 명시 |
| Scheduler/Router | 실행 시간·리전·자원량 조정 | Kubernetes, queue worker 연계 |

> 요약: 탄소 인지 구조는 탄소 신호를 업무 분류와 정책 엔진에 넣고 스케줄러가 실행 위치와 시점을 선택한다.

---

## Ⅲ. 동작원리 및 흐름도

```text
워크로드 접수 -> SLO/deadline 판정 -> 탄소 계수 조회
-> 실행 후보 평가 -> 스케줄/라우팅 -> SCI 검증
```

| 단계 | 처리 내용 | 검증 기준 |
|:---:|:---|:---|
| 1 | 워크로드를 실시간 API와 배치로 분류 | SLO p95, deadline 보유 |
| 2 | 리전별 탄소 계수와 비용 조회 | 계수 갱신 주기 5~15분 |
| 3 | deadline 내 최저 gCO2e 후보 선택 | deadline miss 0.1% 이하 |
| 4 | 실행 후 gCO2e/job, p95, 비용 기록 | SCI 기준선 대비 비교 |

> 요약: 실행 후보는 탄소 계수만이 아니라 deadline과 SLO를 만족하는 조합으로 선택한다.

> 요약: 주요 리스크는 마감 초과와 리전 규제이며, fallback과 허용 리전 정책으로 통제한다.

| 점검 항목 | 목표 기준 | 측정 방법 |
|:---|:---|:---|
| 탄소 | gCO2e/job 기준선 대비 10% 이상 감소 | SCI 대시보드 |
| SLO | 실시간 API p95 200ms, 오류율 0.1% 이하 | APM, synthetic test |
| 스케줄 | deadline miss 0.1% 이하 | 큐 로그, 작업 이력 |

> 요약: 탄소 인지 도입은 탄소 지표, SLO, deadline miss를 함께 만족할 때 운영 기준을 통과한다.

## Ⅵ. 실무 적용 및 결론

**적용 방안 3개 (필수 — 단계별 또는 항목별):**
1. 워크로드를 실시간·지연 허용·장기 배치로 분류하고 지연 허용 작업에 deadline 메타데이터 부여
2. Carbon Signal API를 스케줄러에 연동해 리전별 gCO2e/kWh와 비용 상한을 정책 엔진에서 평가
3. 배치 실행 후 gCO2e/job, deadline miss, p95를 릴리스 대시보드에 기록하고 월 1회 정책 보정

**결론 (2줄):**
- 기술사 판단: 사용자 경로는 SLO 우선, 배치·비동기 경로는 탄소 신호 우선으로 분리해야 한다
- 향후 방향: Kubernetes scheduler, serverless queue, AI 학습 파이프라인에 carbon-aware policy가 기본 운영 옵션으로 결합된다
