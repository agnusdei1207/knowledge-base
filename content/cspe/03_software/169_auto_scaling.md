# 📖 【암기용】 개념 완전 이해

## 한눈에
- **개요**: 애플리케이션의 트래픽(부하)에 따라 클라우드 인스턴스(서버)의 수를 자동으로 늘리거나(Scale-Out) 줄여주는(Scale-In) 클라우드 핵심 기능이다.
- **왜 필요한가**: 수강신청이나 티켓 예매처럼 특정 시간에만 트래픽이 몰리는 서비스의 경우, 평소에도 서버를 100대 유지하면 엄청난 비용이 낭비된다. 반대로 서버가 1대일 때 트래픽이 몰리면 서버가 죽는다. 이를 자동으로 조절하기 위함이다.
- **핵심 직관**: 대형 마트의 계산대와 같다. 손님이 없을 때는 계산대 1개만 열어두다가, 손님 줄이 길어지면(CPU 사용률 증가) 매니저(Load Balancer)가 방송을 해서 직원들을 불러 계산대를 5개, 10개로 쫙 열어버리고, 다시 한산해지면 닫는 식이다.

## 핵심 용어 정리

| 용어/표기 | 의미 | 비유·예 |
|:---|:---|:---|
| 스케일 아웃 (Scale-Out) / 인 (In) | 서버의 '대수'를 늘리고(Out) 줄이는(In) 수평적 확장 방식 (오토 스케일링의 기본) | "계산대 개수 늘리기" |
| 스케일 업 (Scale-Up) / 다운 (Down) | 서버 자체의 '사양(CPU/RAM)'을 높이고(Up) 낮추는(Down) 수직적 확장 방식 | "동네 마트 건물을 2층으로 증축하기" |
| 쿨다운 (Cooldown Period) | 스케일링 이벤트 후 다음 스케일링이 발생하기 전까지 대기하는 안정화 시간 | "계산대 열고 나서 손님 줄어드는지 5분 지켜보기" |

## 깊이 이해
- **배경·문제의식**: 기존 온프레미스 환경에서는 최대 피크 트래픽을 예상해서 서버를 미리 샀다(Over-provisioning). 클라우드의 종량제(사용한 만큼 지불) 이점을 극대화하려면, 인간의 개입 없이 부하에 따라 인프라가 숨 쉬듯 수축/팽창해야 했다.
- **작동 원리**: CloudWatch(모니터링)가 CPU나 네트워크 트래픽 등의 지표를 감시하다가, 임계치(예: CPU 70% 초과)에 도달하면 알람을 발생시킨다. Auto Scaling 그룹은 미리 정의된 AMI(서버 템플릿)로 새 인스턴스를 찍어내고, 로드 밸런서(ELB)가 새 서버로 트래픽을 분산시킨다.
- **비유**: 온도 조절기(Thermostat). 실내 온도가 25도를 넘으면 에어컨이 켜지고(Scale-Out), 22도 밑으로 떨어지면 꺼지는(Scale-In) 피드백 루프다.
- **구체 예시**: 배달 앱에서 저녁 6시가 되어 주문 트래픽이 몰리면, 웹 서버 인스턴스가 2대에서 20대로 자동 증가하여 지연 없이 주문을 받고, 밤 11시가 되면 다시 2대로 줄어들어 야간 서버 비용을 아낀다.
- **흔한 오해·주의점**: "오토 스케일링만 켜면 모든 부하를 무제한 견딜 수 있다"는 오해. 1) 서버가 켜지고 부팅되는 데 시간(수 분)이 걸리기 때문에 급격한 스파이크(Spike) 부하엔 대응이 늦을 수 있고, 2) 뒤단의 DB가 못 버티면 앞단의 웹 서버 100대가 동시에 죽을 수 있다(병목 이전).

## 연결 개념
- 로드 밸런서(Load Balancer) — 늘어난 인스턴스에 트래픽을 고르게 분배하는 필수 짝꿍
- 상태 비저장(Stateless) — 스케일 아웃된 서버가 자유롭게 생성/삭제되려면 서버 내부에 세션을 저장하면 안 됨
- 서버리스(Serverless) — 오토 스케일링을 개발자가 설정할 필요 없이 인프라가 100% 자동 확장되는 궁극의 형태 (170 참조)

# 📝 【답안용】 시험 답안 템플릿

## 핵심 인사이트 (3줄 요약)

> 1. **본질**: 오토 스케일링은 모니터링 메트릭(CPU, 메모리 등) 임계치에 따라 가상 머신이나 컨테이너의 수를 동적으로 늘리거나 줄이는 수평적 확장(Scale-Out/In) 자동화 메커니즘이다.
> 2. **가치**: 트래픽 폭증 시에는 서비스 가용성을 보장하고, 유휴 시간대에는 불필요한 인프라 비용(TCO)을 획기적으로 절감한다.
> 3. **판단 포인트**: 성공적인 적용을 위해서는 골든 이미지(AMI/컨테이너) 준비, 쿨다운 타이머 설정(플래핑 방지), 그리고 애플리케이션의 상태 비저장(Stateless) 설계가 선행되어야 한다.

## 출제 의도 및 답안 포인트

| 출제 의도 | 반드시 짚을 핵심 | 감점 회피 포인트 |
|:---|:---|:---|
| 오토 스케일링의 동적 확장 원리 이해 | CloudWatch(모니터링) -> 알람 -> ASG -> 로드밸런서 흐름 | 단순히 "자동으로 서버가 늘어남"이라는 추상적 서술 |
| 스케일링 종류 및 적용 방식 | Scale Out/In(수평) vs Scale Up/Down(수직) 개념 비교 구분 | 데이터베이스(RDBMS)에 쉽게 Scale-Out이 가능하다고 단정 |
| 운영 시 발생 가능한 리스크 제어 | 플래핑(Flapping) 현상 방지(Cooldown 적용), 세션 유지 실패(Stateless) | 도입 시 부하 대응이 무조건 즉시(0초) 이루어진다고 과장 |

> 요약: 서버 대수를 늘리는 수평적 확장(Scale-Out)의 구조적 한계를 짚고, 이를 극복하기 위한 무상태(Stateless) 설계와 로드밸런서 결합을 강조해야 한다.

## Ⅰ. 개요 및 필요성

- 개요: 애플리케이션에 가해지는 워크로드(트래픽, CPU 사용량 등)의 변동에 대응하여 자동으로 컴퓨팅 리소스를 할당하고 회수하는 클라우드 인프라 관리 기술
- 배경: 서비스 이용 패턴이 시간대별로 뚜렷하게 다름에도 온프레미스의 프로비저닝은 고정되어 있어 극심한 자원 낭비 또는 피크 시 서비스 다운 초래
- 필요성: 성능 저하 없이 사용자 경험(SLA)을 유지하면서도, 유휴 인프라에 지출되는 클라우드 비용을 최소화(FinOps)하기 위해 필수 적용

## Ⅱ. 구조 및 구성요소

```text
               +----------------------------------+
               |  Auto Scaling Group (ASG)        |
[ User ] --> [ Load Balancer ] --> [ Instance A (Active) ]
                     |             [ Instance B (Active) ]
                     |             [ Instance C (Scale-out 대기) ]
                     +----------------------------------+
                             ^
                             | (Scale 액션 트리거)
[ CloudWatch (모니터링 알람) ] -- (CPU > 70% 임계치 초과 탐지)
```

| 구성요소 | 역할 | 특이사항 |
|:---|:---|:---|
| ASG (Auto Scaling Group) | 확장/축소될 인스턴스의 최소/최대/희망 용량(Capacity) 설정 그룹 | 시작 템플릿(AMI/설정)을 참조하여 인스턴스 생성 |
| Load Balancer (ELB) | 생성된 새 인스턴스를 자동으로 로드 밸런싱 풀(Pool)에 추가하고 트래픽 분산 | 헬스 체크(Health Check)로 비정상 노드 즉시 배제 |
| 모니터링 (CloudWatch 등) | CPU, 메모리, 네트워크 등의 메트릭을 수집하고 임계치 위반 시 알람 발생 | 사용자 정의(Custom) 메트릭(예: 큐 대기열 수) 활용 가능 |
| 쿨다운 (Cooldown Period) | 인스턴스가 생성되거나 삭제된 후 다음 액션이 실행되기 전까지의 대기 시간 | 플래핑(Flapping: 짧은 시간 반복 증감) 현상 방지 |

> 요약: 모니터링 시스템이 부하 감지 시 그룹(ASG) 내 템플릿으로 서버를 복제하고 로드밸런서에 투입하는 파이프라인이다.

---

## Ⅲ. 동작원리 및 흐름도

```text
메트릭 수집 -> 임계치 위반 알람 -> 인스턴스 프로비저닝 -> 로드 밸런서 연결 (서비스 투입)
```

- 1단계 [부하 감지]: 에이전트가 CPU 사용률 80% 상태를 3회 이상(예: 3분간) 연속 감지하여 알람(Alarm)을 트리거
- 2단계 [스케일 아웃 실행]: ASG가 시작 템플릿(AMI + 보안 그룹 + 인스턴스 타입)을 읽어 새 인스턴스(VM) 프로비저닝 시작
- 3단계 [서비스 투입]: OS 부팅 및 앱 구동이 완료되면(Health Check 통과), ELB가 새 인스턴스로 트래픽을 라우팅하기 시작
- 4단계 [스케일 인 (축소)]: 부하가 30% 이하로 떨어지면 가장 오래된 인스턴스부터 큐 드레인(Connection Draining) 후 안전하게 종료

> 요약: 임계치를 넘으면 템플릿 기반으로 서버를 복제하고 상태 확인을 거쳐 서비스에 투입하며, 부하가 해소되면 역순으로 회수한다.

---

## Ⅳ. 특징

- 동적 용량 관리(Dynamic Provisioning): 예측 스케일링(일정 기반)과 반응형 스케일링(지표 기반)을 조합하여 트래픽 스파이크에 대응
- 고가용성(HA) 자가 치유: 특정 인스턴스 하드웨어에 장애가 발생하면 상태 확인 실패를 감지해 기존 것을 삭제하고 정상 인스턴스로 교체(Self-Healing)
- 무상태(Stateless) 제약: 서버가 언제든 삭제될 수 있으므로, 로그인 세션 등은 서버 내부(메모리)가 아닌 외부 저장소(Redis, DynamoDB)에 분리해야 함
- 부팅 지연 시간(Warm-up Time): VM 기반 오토 스케일링은 부팅에 수 분이 걸리므로, 갑작스러운 트래픽 폭증 시에는 병목 방어가 늦어지는 한계 존재

## Ⅴ. 심화 비교 및 적용 판단

| 비교 축 | Scale-Out (수평 확장) | Scale-Up (수직 확장) |
|:---|:---|:---|
| 확장 방식 | 인스턴스(서버) 대수를 추가 | 단일 서버의 스펙(CPU/RAM)을 증설 |
| 중단 여부 | 무중단(Seamless) 트래픽 분산 | 재부팅 필요 (서비스 일시 중단) |
| 비용 구조 | 단위 인스턴스 단가 유지 (선형 증가) | 고사양 인스턴스일수록 기하급수적 단가 상승 |
| 적용 대상 | 웹 서버(Web), 애플리케이션 서버(WAS) | 데이터베이스(RDBMS, 단일 마스터 노드) |

> 요약: 오토 스케일링은 주로 상태가 없는(Stateless) 웹/앱 계층의 Scale-Out에 쓰이며, 상태를 공유하는 DB 계층은 물리적 한계로 Scale-Up에 의존한다.

**리스크·대응:**
- 플래핑(Flapping) 현상 발생: 스케일 인-아웃이 짧은 주기로 반복되며 시스템 부하와 과금이 발생 → 적절한 쿨다운(Cooldown Period) 타이머(예: 300초) 설정 및 인-아웃 임계치 격차 확대 (지표: 일일 스케일링 액션 횟수 안정화)
- 병목의 전이: WAS가 100대로 Scale-Out되어 트래픽을 받아도, 뒤에 있는 RDBMS가 쿼리를 못 버티고 다운됨 → 캐시(Redis) 계층 도입 및 DB 읽기 복제본(Read Replica) 구조 병행 설계 (지표: DB 연결 커넥션 고갈 횟수 0)

**도입 후 점검 지표:**
- 스케일링 반응 속도(Lead Time): 부하 감지부터 실제 새 인스턴스가 ELB에 붙어 트래픽 처리를 시작하기까지의 시간 (5분 이내 유지)
- 비용 절감률: 오토 스케일링 미적용 시 고정 최대 프로비저닝 비용 대비 실제 발생한 월 비용의 차이 — FinOps 대시보드

## Ⅵ. 실무 적용 및 결론

**적용 방안 3개:**
1. HPA (Horizontal Pod Autoscaler) 적용: 쿠버네티스(K8s) 환경에서 VM 단위가 아닌 컨테이너(Pod) 단위로 오토 스케일링을 수행하여 반응 속도를 수 초(초 단위)로 단축
2. 예측형 스케일링 (Predictive Scaling): 수강신청 등 트래픽 폭증 시간이 확정적인 경우, 부하 감지를 기다리지 않고 스케줄러 기반으로 트래픽 발생 30분 전에 미리 인스턴스를 Pre-warm(예열)
3. 스팟 인스턴스(Spot) 믹스: 확장되는 인스턴스(Scale-Out) 풀을 저렴한 스팟 인스턴스로 구성하여 클라우드 비용을 최대 90% 추가 절감 (단축 회수 대비 Stateless 아키텍처 필수)

**결론 (2줄):**
- 기술사 판단: 오토 스케일링의 핵심은 "서버를 늘리는 것"이 아니라, 서버가 수시로 죽고 살아나도 앱이 버틸 수 있도록 '결합도를 낮추고 상태를 외부에 저장하는 아키텍처'로 전환하는 데 있다.
- 향후 방향: 모니터링 기반의 반응형 확장을 넘어, AI/ML 트래픽 예측 모델을 활용하여 인프라 스스로 부하 발생 전에 자원을 준비하는 AIOps 기반 자율 스케일링으로 진화하고 있다.
