## 핵심 인사이트 (3줄 요약)
- 넷플릭스 신작이 풀려서 접속자가 10배 폭주할 때, 엔지니어가 수동으로 서버를 사는 게 아니라 **클라우드 시스템이 스스로 CPU 사용량을 감지하고 1분 만에 서버 대수를 늘려주는(Scale-out) 마법의 기술**.
- 반대로 밤이 되어 접속자가 줄어들면, 켜져 있던 서버들을 스스로 꺼버려서(Scale-in) 클라우드 비용 낭비를 완벽하게 막아줌. (탄력성, Elasticity의 상징).
- 온프레미스 시대에는 "명절 트래픽에 맞춰서 1년 내내 서버 100대를 사두는(Over-provisioning)" 멍청한 짓을 했지만, 오토 스케일링 덕분에 "필요할 때만 켜고 쓴 만큼만 낸다"는 클라우드의 진짜 가치가 실현됨.

## Ⅰ. 개요 및 필요성
- **개요**: 애플리케이션의 부하(트래픽, CPU, 메모리) 상태를 모니터링하여, 사전에 정의된 정책(Policy)에 따라 가상 서버(인스턴스)의 수를 자동으로 늘리거나(Scale-out) 줄이는(Scale-in) 클라우드 핵심 기능.
- **필요성**: 대학교 수강 신청 날, 아침 9시가 되자 서버가 펑 터짐. 학교는 욕을 먹고 서버를 10배 늘렸지만, 수강 신청이 끝난 오후 1시부터 그 비싼 서버 10대는 1년 내내 전력만 퍼먹는 고철 덩어리가 됨. "트래픽이 들어올 때만 고무줄처럼 늘어났다가, 안 쓸 때는 줄어들어서 돈을 아낄 수 없을까?"라는 가장 원초적인 클라우드의 철학에서 탄생함.
---
## Ⅱ. 아키텍처 및 핵심 원리
- **1. 모니터링 (CloudWatch)**:
  - 오토 스케일링의 눈(Eye) 역할. 
  - 현재 돌아가고 있는 3대의 웹서버 CPU 평균 사용률을 매분 체크함.
- **2. 스케일링 정책 (Scaling Policy)**:
  - **스텝 스케일링**: "CPU 평균이 70%를 넘으면 서버를 2대 더 띄워라."
  - **대상 추적(Target Tracking)**: 가장 많이 쓰임. "난 모르겠고, 넌 무조건 CPU 평균을 50%로 유지해. 트래픽 오면 네가 알아서 늘리고, 트래픽 빠지면 네가 알아서 줄여!" (에어컨 자동 온도 조절과 같음).
  - **예약 스케일링(Scheduled)**: "내일 아침 9시 수강 신청이니까, 트래픽 오기 전에 아침 8시 50분에 무조건 50대 미리 켜놔!"
- **3. 로드 밸런서 연동 (ALB)**:
  - 새로 뿅! 하고 태어난 4번, 5번 서버가 일을 하려면 트래픽을 나눠줘야 함.
  - 오토 스케일링 그룹은 서버가 켜지자마자 앞단의 로드 밸런서(Load Balancer)에게 "형, 나 새로 태어났어! 나한테도 트래픽 줘!"라고 자동으로 등록(Register)됨.

```text
[ 온프레미스 고정 서버 vs 오토 스케일링의 탄력성 비교 ]

 🏦 [ 과거: 고정 할당 (돈 낭비 + 장애) ]
 - 서버 5대 구매 (최대 처리량: 500명)
 - 평일 (접속자 100명): 서버 4대는 놀고 있음 (비용 낭비 💸).
 - 수강신청 (접속자 1000명): 서버 5대가 뻗어버림 (서비스 장애 💥).

 ☁️ [ 현재: 오토 스케일링 (완벽한 효율) ]
 - 정책: "CPU 70% 유지해!"
 - 평일 밤: (스르륵...) 서버 1대만 켜져 있음. (요금 최소화 🪙).
 - 수강신청 아침 9시: 트래픽 폭주! ➡️ (위잉!) 1분 만에 서버가 20대로 자가 증식! ➡️ 1000명 거뜬히 처리 🚀.
 - 오후 1시 (종료): (스르륵...) 다시 19대 서버 자동 삭제 ➡️ 과금 중지!
```

## Ⅲ. 비교 및 연결
| 구분 | Scale-Up (스케일 업 / 수직 확장) | Scale-Out (스케일 아웃 / 수평 확장) |
|---|---|---|
| **방식** | 기존 서버의 **사양(RAM, CPU)을 업그레이드** | **동일한 사양의 서버 대수를 옆으로 늘림** |
| **비유** | 오토바이 엔진을 버리고 스포츠카 엔진 교체 | 오토바이 1대로 안 되니 오토바이 10대를 부름 |
| **단점 (오토 스케일링 관점)**| 사양을 올리려면 필연적으로 서버를 껐다 켜야 함(다운타임) | 앞단에 로드 밸런서가 필수적으로 필요함 |
| **오토 스케일링의 적용**| 거의 안 쓰임 (DB 등에 제한적 적용) | **오토 스케일링의 핵심 원리 (무한 증식 가능)** |

## Ⅳ. 실무 적용 및 기술사 판단
- **무상태(Stateless) 아키텍처 필수 요건**: 기술사가 오토 스케일링을 구축할 때 마주하는 가장 흔한 장애는 '세션 불일치'임. 1번 서버에서 로그인한 유저가, 트래픽이 늘어 새로 띄워진 2번 서버로 접속 배정되면 "로그인하세요"라고 튕김. 오토 스케일링으로 띄워지는 서버들은 언제든 죽을 수 있는 일회용 종이컵이므로, 로그인 상태나 이미지 파일은 반드시 외부의 **Redis(세션용)**나 **S3(파일용)**에 저장하는 완벽한 Stateless 아키텍처가 전제되어야 함.
- **골든 이미지(Golden Image)와 부팅 속도 최적화**: 넷플릭스 신작이 떠서 트래픽이 1초 만에 폭주하는데, 서버가 켜지면서 OS 깔고 자바(Java) 깔고 소스코드 다운로드 받느라 5분이 걸리면 이미 장애가 난 거임. 실무에서는 OS와 애플리케이션 코드가 완벽하게 설치된 상태를 박제한 빵틀(AMI, Amazon Machine Image)이나 Docker 컨테이너를 구워놓고(Baking), 1초 만에 트래픽을 받을 수 있게 부팅 속도를 최적화해야 진정한 클라우드 탄력성을 얻을 수 있음.
---
## Ⅴ. 기대효과 및 결론
- "트래픽이 많으면 서버가 터지고, 트래픽이 없으면 돈이 아깝다"는 IT 인프라 50년 역사상 최대의 딜레마를 수학적 알고리즘으로 완벽하게 해결한 클라우드의 꽃.
- 비즈니스 흥행(트래픽)에 대한 두려움을 없애고, 기업이 인프라 용량 산정(Capacity Planning)이라는 노가다에서 해방되어 혁신에만 몰두하게 해주는 가장 핵심적인 아키텍처 패턴임.

### 👶 어린이를 위한 3줄 비유 설명
1. 햄버거 가게에 손님이 1명일 때는 알바생(서버) 1명만 일하면 돼요.
2. 그런데 점심시간에 손님이 100명이나 몰려오면? **오토 스케일링**이라는 마법사 점장이 즉시 마법을 부려서 똑같이 생긴 알바생 10명을 1초 만에 복제해서 카운터에 세워줍니다!
3. 손님이 다 먹고 집에 가면 마법을 풀어서 다시 알바생을 1명으로 줄이니까, 사장님은 시급(클라우드 비용)을 엄청나게 아낄 수 있답니다!
