# 📖 【암기용】 개념 완전 이해

## 한눈에
- **개요**: **서비스 메시(Service Mesh)**는 마이크로서비스 간의 통신(네트워크)을 안전하고 신뢰성 있게 제어하기 위해, 애플리케이션 코드 바깥에 배치하는 전용 인프라 계층이다.
- **왜 필요한가**: MSA 환경에서는 수천 개의 서비스가 서로 통신한다. 이때 재시도, 로드밸런싱, 암호화, 추적 등의 통신 로직을 모든 개발자가 자바, 파이썬 등 언어별로 직접 짜는 것은 불가능에 가깝다.
- **핵심 직관**: 건물 내 부서 간의 '전화 교환기망'과 같다. 직원은 수화기만 들면(비즈니스 로직) 교환기가 알아서 암호화, 녹음(로깅), 부재중 착신전환(서킷 브레이커)을 다 해주는 원리다.

## 핵심 용어 정리

| 용어/표기 | 의미 | 비유·예 |
|:---|:---|:---|
| 사이드카 패턴 (Sidecar) | 앱 컨테이너 바로 옆에 통신 전용 프록시 컨테이너를 붙여 띄우는 패턴 | 오토바이(앱) 옆에 붙은 보조석(프록시) |
| 데이터 플레인 | 실제 데이터(트래픽)가 오가는 사이드카 프록시들의 집합 | 각 직원의 전화기(Envoy) |
| 컨트롤 플레인 | 전체 데이터 플레인(프록시들)에게 정책과 라우팅 룰을 중앙에서 내려주는 통제소 | 중앙 전화 교환대 (Istiod) |
| mTLS (Mutual TLS) | 클라이언트와 서버 양방향으로 인증서를 주고받아 통신을 암호화하는 방식 | 쌍방향 신분증 검사 |

## 깊이 이해
- **배경·문제의식**: 초기 MSA는 Spring Cloud처럼 언어 종속적인 라이브러리(Netflix OSS)를 코드에 직접 임베딩하여 통신을 제어했다. 이는 폴리글랏(Polyglot) 환경에서 타 언어 지원이 어렵고, 라이브러리 업데이트 시 모든 서비스를 재빌드해야 하는 큰 단점이 있었다.
- **작동 원리**: 개발자는 순수 비즈니스 로직만 작성한다. 인프라 단에서 각 서비스 컨테이너(Pod)마다 Envoy 같은 경량 프록시를 사이드카로 주입한다. 서비스 A가 B를 호출할 때, 실제로는 A의 프록시가 B의 프록시와 통신하며 이 과정에서 서킷 브레이커, mTLS 암호화, 텔레메트리 수집이 투명하게(Transparent) 일어난다.
- **비유**: 넷플릭스 영화에 자막을 입힐 때, 원본 영상을 수정(라이브러리 방식)하는 게 아니라, 플레이어(사이드카)가 영상을 틀 때 외부에서 자막 파일을 덧씌워 주는 것과 같다.
- **구체 예시**: Istio가 대표적인 컨트롤 플레인이며, Envoy가 데이터 플레인이다. 쿠버네티스 환경에서 Istio를 설치하면, 개발자가 모르게(Zero-code change) 모든 Pod 간 통신이 mTLS로 암호화되고 에러율이 중앙에서 모니터링된다.
- **흔한 오해·주의점**: "API 게이트웨이와 같은 것 아닌가?"라는 오해. API 게이트웨이는 외부에서 들어오는 트래픽(North-South)을 처리하는 정문이고, 서비스 메시는 내부 서비스 간의 통신(East-West)을 처리하는 내부 도로망이다. 둘은 대체재가 아니라 보완재다.

## 연결 개념
- API Gateway — 외부 트래픽 처리 (North-South)
- 사이드카 패턴 (Sidecar Pattern) — 서비스 메시의 핵심 구현 패턴
- 관측성 (Observability) — 서비스 메시가 자동으로 수집해주는 메트릭, 로그, 트레이스

# 📝 【답안용】 시험 답안 템플릿

## 핵심 인사이트 (3줄 요약)

> 1. **본질**: 서비스 메시는 마이크로서비스 간의 내부 통신(East-West)을 제어, 보안, 관측하기 위해 애플리케이션 코드와 분리된 사이드카(Sidecar) 프록시 기반의 인프라 계층이다.
> 2. **가치**: 폴리글랏 환경에서 통신 제어 로직을 코드에서 분리(Zero-code change)하여 개발자는 비즈니스 로직에만 집중하고, 운영자는 중앙에서 트래픽과 보안 정책을 통제할 수 있게 한다.
> 3. **판단 포인트**: 강력한 제어력과 보안(mTLS)을 제공하지만, 2배로 증가하는 네트워크 홉(Hop)과 프록시 리소스 오버헤드가 발생하므로 클러스터 규모와 보안 요구수준에 따른 트레이드오프가 필수적이다.

## 출제 의도 및 답안 포인트

| 출제 의도 | 반드시 짚을 핵심 | 감점 회피 포인트 |
|:---|:---|:---|
| 라이브러리 방식(Spring Cloud) 대비 서비스 메시의 장점 확인 | 사이드카 패턴, 폴리글랏 지원, 비즈니스 로직과 통신 분리 | 데이터 플레인과 컨트롤 플레인의 개념적 혼동 |
| 서비스 메시의 핵심 아키텍처 및 통제 기능 이해 | 트래픽 제어(서킷브레이커), 보안(mTLS), 관측성(Telemetry) | API 게이트웨이(North-South)와의 차이 누락 |

> 요약: 서비스 메시는 MSA 통신 복잡성을 코드(Application)에서 인프라(Network) 계층으로 끌어내리는 가장 진보된 패러다임 전환이다.

## Ⅰ. 개요 및 필요성

- 개요: 서비스 간 통신, 보안, 트래픽 제어, 관측성을 애플리케이션 코드 수정 없이 투명하게 제공하는 사이드카 프록시 기반의 전용 인프라 계층
- 배경: 애플리케이션 라이브러리 방식(Netflix OSS 등)의 통신 제어는 언어 종속성(폴리글랏 한계)과 업데이트 시 전체 재빌드라는 유지보수 부담 초래
- 필요성: 개발자는 비즈니스 로직에 집중하고, 네트워크 제어와 제로 트러스트(Zero Trust) 보안 통제는 운영 인프라에서 중앙 집중화하여 처리 필요

## Ⅱ. 구조 및 구성요소

```text
[ Control Plane (Istiod 등) ] -- (정책 배포/텔레메트리 수집) --> [ Data Plane ]
                                                                     |
Service A Pod: [App Container] <--(Local)--> [Sidecar Proxy] <====(mTLS)====> [Sidecar Proxy] <--(Local)--> [App Container] :Service B Pod
```

| 구성요소 | 역할 | 특이사항 |
|:---|:---|:---|
| 데이터 플레인 (Data Plane) | 실제 서비스 간의 인바운드/아웃바운드 트래픽 처리 (Envoy 프록시) | 사이드카 형태로 App과 동일 Pod 내 배치 |
| 컨트롤 플레인 (Control Plane) | 데이터 플레인에 라우팅 룰, 보안 정책, 인증서 동적 프로비저닝 (Istiod) | 트래픽 자체는 직접 통과하지 않음 |
| 보안 (Security) | 양방향 인증(mTLS) 기반 트래픽 암호화 및 인가(RBAC) | 인프라 레벨의 Zero Trust 구현 |
| 관측성 (Observability) | 분산 추적(Trace), 메트릭, 로깅 데이터를 수집하여 외부 백엔드 전송 | Kiali, Jaeger 등과 연동 |

> 요약: 서비스 메시는 트래픽을 처리하는 분산된 데이터 플레인과, 이를 통제하는 중앙의 컨트롤 플레인으로 아키텍처가 분리된다.

## Ⅲ. 동작원리 및 흐름도

```text
서비스A 요청 -> (iptables 가로채기) -> A의 프록시 -> mTLS 암호화/라우팅
-> B의 프록시 수신 -> 인가 확인 -> 서비스B 전달 -> 텔레메트리 비동기 전송
```

- 1단계 [트래픽 가로채기]: 애플리케이션(Service A)이 발생시킨 외부 호출 패킷을 OS 레벨(iptables)에서 투명하게 사이드카 프록시(Envoy)로 리다이렉트
- 2단계 [정책 적용 및 발송]: 컨트롤 플레인에서 캐싱된 라우팅 룰(Canary 배포 등)과 서킷 브레이커 정책을 적용하고, 타겟으로 mTLS 암호화 패킷 전송
- 3단계 [수신 및 통제]: 목적지(Service B)의 프록시가 패킷을 수신하여 인증서를 검증하고 인가(Authorization)를 확인한 후 로컬의 애플리케이션 컨테이너로 전달
- 4단계 [관측성 데이터 수집]: 양쪽 프록시는 통신 성공 여부, 응답 지연 시간(Latency) 등의 메트릭과 트레이스 구간 정보를 모니터링 시스템으로 비동기 전송

> 요약: 애플리케이션 코드는 네트워크 통제를 인지하지 못한 채 로컬 호출만 수행하며, 프록시가 실제 암호화·제어·모니터링을 전담한다.

---

## Ⅳ. 특징
- 비즈니스와 인프라의 완벽한 디커플링: 폴리글랏 환경(Node.js, Go, Java 혼재)에서도 단일한 통신 및 보안 정책을 일관되게 적용
- 동적 트래픽 제어 (Traffic Management): 카나리 배포(Canary), 블루/그린 배포 시 가중치 기반 트래픽 시프팅(Weight-based Routing)을 인프라 레벨에서 수행
- 리소스 오버헤드: 모든 네트워크 홉이 프록시를 두 번(송·수신) 거치므로 지연 시간(Latency) 추가 및 프록시 구동을 위한 CPU/Memory 추가 소모 발생

> 요약: 서비스 메시는 강력한 중앙 통제력과 코드 독립성을 주지만, 네트워크 지연과 인프라 자원 소모라는 뚜렷한 비용을 요구한다.

## Ⅴ. 심화 비교 및 적용 판단

| 비교 축 | 라이브러리(Spring Cloud) 기반 통신 | 서비스 메시 (Istio/Envoy) 기반 통신 | 선택 기준 |
|:---|:---|:---|:---|
| 적용 방식 | 코드 내 종속성 추가 및 빌드 | 인프라 레벨 투명한 주입 (Sidecar) | 다형성(폴리글랏) 환경 여부 |
| 트래픽 제어 | 애플리케이션 프로세스 내부 실행 | 별도 프록시 프로세스에서 실행 | 개발자/운영자 역할 분리 여부 |
| 성능/오버헤드 | 로컬 실행으로 네트워크 추가 홉 없음 | 프록시 경유로 인한 홉 증가 및 지연 | 레이턴시 민감도 vs 보안/제어 필요성 |

> 요약: 단일 언어 기반의 소규모 MSA는 라이브러리 방식이 가볍지만, 대규모 폴리글랏 환경 및 보안 규제가 엄격한 환경은 서비스 메시가 필수다.

**리스크·대응:**
- 프록시 오버헤드(지연): 레이턴시에 극도로 민감한 시스템에서 병목 발생 → eBPF(Extended BPF)를 활용하여 iptables를 우회하는 커널 레벨 네트워킹(Cilium 등) 적용
- 운영 복잡도 폭증: 컨트롤 플레인 및 수많은 프록시 관리의 난이도 증가 → 완전 관리형 서비스(AWS App Mesh, GCP Anthos Service Mesh) 도입 또는 초기엔 핵심 기능(mTLS)만 선별 적용

**도입 후 점검 지표:**
- 네트워크 지연: 서비스 메시 도입 전후 p99 지연 시간(Latency) 차이 5ms 이내 방어 — 분산 추적(Jaeger) 분석
- 보안 컴플라이언스: 클러스터 내부 East-West 통신의 mTLS 적용률 100% 달성 여부 — 보안 대시보드 점검

## Ⅵ. 실무 적용 및 결론

**적용 방안 3개:**
1. 제로 트러스트 보안 구현: 내부망 해킹 방지를 위해 Istio를 통한 서비스 간 mTLS 상호 인증을 기본 적용하고, L7 레벨의 엄격한 인가 정책(AuthorizationPolicy) 설정
2. 무중단 롤아웃 체계: 카나리 배포 시 서비스 메시의 트래픽 라우팅 기능을 활용하여 V2 버전으로의 트래픽을 1% -> 10% -> 100%로 점진적 전환
3. 중앙 관측성(Observability) 확보: Kiali와 연동하여 마이크로서비스 간의 통신 토폴로지(Topology)를 시각화하고, 병목 구간과 서킷 브레이커 차단 상태를 실시간 관제

**결론 (2줄):**
- 기술사 판단: 서비스 메시는 MSA의 네트워크 통제 한계를 극복하는 표준 아키텍처이나, 인프라 오버헤드가 발생하므로 10개 이상의 마이크로서비스가 운영되는 복잡도 높은 환경에 도입을 권고한다.
- 향후 방향: 최근에는 사이드카 프록시의 리소스 낭비를 줄이기 위해 노드당 하나의 프록시를 두는 Ambient Mesh(사이드카 없는 메시)와 커널 수준의 eBPF 기술 결합으로 진화하고 있다.
