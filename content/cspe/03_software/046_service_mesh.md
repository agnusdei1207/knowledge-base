## 미리 알고가기

- 서비스 메시(Service Mesh): 서비스 간 통신 제어를 애플리케이션 코드 밖으로 분리하는 인프라 계층임
- 데이터 플레인(Data Plane): 실제 요청을 중계하며 정책을 실행하는 프록시 계층임
- 제어 플레인(Control Plane): 라우팅과 보안 정책을 배포하고 관리하는 제어 계층임
- 상호 TLS(mTLS): 양방향 인증과 암호화 통신을 보장하는 보안 프로토콜임
- 사이드카 패턴(Sidecar Pattern): 애플리케이션 컨테이너 옆에 프록시 컨테이너를 독립 실행하는 구조임
- 분산 추적(Tracing): 마이크로서비스 간 호출 경로와 응답 시간을 분석하는 기법임
- 카나리 배포(Canary Deployment): 신버전 서비스를 일부 트래픽에만 먼저 노출하여 검증하는 기법임

## 작성 근거(검토용)

- 서비스 메시는 통신 제어의 구현 위치, 정책 적용 범위, 운영 부담을 핵심 비교축으로 선정함
- 구조는 데이터 플레인과 제어 플레인의 역할을 중심으로 제시함
- 실무 판단은 자원 사용률, 정책 배포 실패율, 제어 계층 가용률로 구체화함
- 전수 검수 완료 근거: 제목, frontmatter, 미리 알고가기, 작성 근거, 본문, 표 헤더·셀, 요약, 결론을 한 줄도 빠뜨리지 않고 확인했으며 어색한 단어·조사·동사 결합·장황한 명사구를 교정함.

## Ⅰ. 개요

- **정의/개념**: 서비스 메시는 마이크로서비스 간 통신 제어·보안·관측 기능을 프록시와 제어 계층으로 분리하는 아키텍처임
- **배경/필요성**: 서비스별로 재시도·보안·추적 로직이 중복되므로 공통 통신 정책을 일관되게 적용할 계층이 필요함

### 쉽게 이해하기 (학습용)
- 배달원들이 손님 집을 찾아갈 때, 배달 주소와 결제 확인을 요리사가 직접 처리하는 대신 아파트의 공동 보안실과 전문 컨시어지가 대신 처리해주는 구조와 같음.

## Ⅱ. 특징

- 트래픽 제어와 보안 정책을 서비스 코드 밖에서 일관되게 적용함
- mTLS, retry, canary routing, tracing을 중앙 정책으로 운영할 수 있음
- 사이드카와 제어 계층이 추가되어 자원 사용량과 운영 복잡도가 커짐
- 서비스 수가 적고 공통 정책이 적으면 프록시·제어 계층 운영 비용이 편익을 초과할 수 있음

### 쉽게 이해하기 (학습용)
- 경비실이 입출입 통제와 안전 점검을 전담하여 각 가정은 주거에만 집중하게 되지만, 경비실을 짓고 경비원을 고용하는 유지 비용이 매달 고정적으로 발생함.

## Ⅲ. 종류 및 비교

| 판단 기준 | 라이브러리 기반 통신 제어 | 서비스 메시 |
|:---|:---|:---|
| 제어 메커니즘 | 재시도와 보안 로직을 애플리케이션 코드 안에 넣음 | 프록시와 제어 계층이 통신 정책을 대신 수행함 |
| 정책 관리 | 서비스 코드·라이브러리별 분산 구현 | 프록시와 제어 계층에 라우팅·mTLS·재시도 정책 일괄 배포 |
| 실무 부작용 | 언어와 서비스마다 구현 품질이 달라지고 중복이 커짐 | 프록시 오버헤드와 정책 운영 복잡도가 늘어남 |

> 요약: 공통 통신 정책이 적으면 라이브러리 방식, 다수 서비스에 같은 정책을 적용하면 서비스 메시가 적합함.

### 쉽게 이해하기 (학습용)
- 각 집 현관에 보안 장치를 일일이 다는 것은 쉽지만 고장 나면 따로 고쳐야 하는 반면, 중앙 통제실과 안내 데스크를 세우는 것은 설치가 어렵지만 중앙에서 일괄 보안 제어가 가능함.

## Ⅳ. 설계 요소 및 구조

```text
[제어 플레인 (Istio)]
       │ (정책 배포)
       ▼
[데이터 플레인 (Envoy)] ──(mTLS 통신)── [데이터 플레인 (Envoy)]
  (사이드카 프록시)                         (사이드카 프록시)
```

| 설계 요소 | 설명 |
|:---|:---|
| 데이터 플레인 프록시 | Envoy 같은 프록시가 서비스 옆에서 요청을 중계하며 통신 정책을 실행함 |
| 제어 플레인 | Istio 같은 제어 계층이 라우팅·보안 정책을 배포하고 관리함 |
| 트래픽 정책 | 재시도·타임아웃·카나리 규칙으로 호출과 전환 방식을 제어함 |
| 관측 파이프라인 | 로그·메트릭·트레이스를 수집해 분산 호출 상태를 추적함 |

> 요약: 제어 플레인이 정책을 배포하면 데이터 플레인 프록시가 요청별로 정책을 실행하고 관측 정보를 수집함.

### 쉽게 이해하기 (학습용)
- 중앙 통제실(제어부)에서 아파트 전체의 출입 보안 수칙을 세우고 지시하면, 각 동 입구에 서 있는 보안 요원(대행부)이 실제 수칙에 맞춰 주민과 외부인을 검문함.

## Ⅴ. 원리 및 절차 흐름도

```text
서비스 요청 ──> 출발지 프록시 ──> 정책 적용·중계 ──> 목적지·관측 계층
```

1. **서비스 요청**: 애플리케이션이 다른 서비스 호출을 시작함
2. **출발지 프록시**: 사이드카가 요청을 가로채고 대상과 정책을 조회함
3. **정책 적용·중계**: 프록시가 mTLS·라우팅·타임아웃 정책을 적용해 요청을 전달함
4. **목적지·관측 계층**: 목적지 프록시가 요청을 서비스에 전달하고 호출 지표를 수집함

> 요약: 출발지·목적지 프록시가 서비스 요청에 보안·라우팅 정책을 적용하고 호출 지표를 수집함.

### 쉽게 이해하기 (학습용)
- 주민이 배달을 요청하면 보안 요원이 이를 가로채 중앙 수칙에 따라 신원을 확인하고 암호화된 전용 통로를 통해 상대방 보안 요원에게 전달하여 통신이 이루어짐.

## Ⅵ. 실무 사례

금융 마이크로서비스 아키텍처 환경에서 개별 서비스의 변경 없이 공통 mTLS 통신 암호화 및 타임아웃 정책을 일관되게 적용하기 위해 Envoy 사이드카 프록시와 Istio 제어 플레인을 구축함. 서비스 메시 도입 후 프록시의 CPU·메모리 자원 점유량과 정책 동기화 가용성을 실시간 지표로 수집하고 분석하여 성능 병목에 대응함.

### 쉽게 이해하기 (학습용)
- 대단지 주상복합 아파트에서 모든 세대의 입출입 보안과 화재 대비 시스템을 중앙 관리실을 통해 일원화하고, 보안 수칙의 실시간 전송 속도를 감시하여 보안 공백을 방지함.

## Ⅶ. 결론

- 서비스 메시는 서비스 간의 통신 제어 로직을 인프라 계층으로 격리하여 마이크로서비스 간 결합도를 완화하고 공통 정책 관리를 효율화함.
- 프록시 추가에 따른 메모리 점유 및 네트워크 지연을 제어 계층과 데이터 계층의 자원 최적화 조치를 통해 지속 관리해야 함.

### 쉽게 이해하기 (학습용)
- 서비스 메시는 복잡한 마이크로서비스 환경에서 보안과 통신을 일괄 제어하는 효율적인 장치이며, 시스템이 커질수록 늘어나는 경비 비용과의 균형을 잘 맞춰 적용해야 함.
