## 미리 알고가기

- 서비스 메시는 서비스 간 통신 제어를 애플리케이션 코드 밖으로 분리하는 인프라 계층임
- Envoy는 대표적인 data plane 프록시임
- Istio는 정책과 라우팅과 보안을 관리하는 control plane을 제공함

## Ⅰ. 개요

- **정의/개념**: 서비스 메시는 마이크로서비스 간 통신에 필요한 트래픽 제어와 보안과 관측 기능을 사이드카 프록시와 중앙 제어 계층으로 분리해 애플리케이션 코드 변경 없이 네트워크 정책을 적용하는 아키텍처임
- **배경/필요성**: 서비스 수가 많아질수록 재시도와 TLS와 라우팅과 추적 로직이 각 서비스에 중복되므로, 이를 공통 통신 계층으로 분리할 필요가 커짐

## Ⅱ. 특징

- 트래픽 제어와 보안 정책을 서비스 코드 밖에서 일관되게 적용함
- mTLS와 리트라이와 카나리 라우팅과 관측 기능을 중앙 정책으로 운영할 수 있음
- 사이드카 오버헤드와 운영 복잡도가 추가됨
- 서비스 수가 적거나 단순 구조이면 과도한 도입이 될 수 있음

## Ⅲ. 종류 및 비교

| 판단 기준 | 라이브러리 기반 통신 제어 | 서비스 메시 |
|:---|:---|:---|
| 구현 위치 | 애플리케이션 코드 내부 | 프록시와 제어 평면 |
| 장점 | 단순하고 직접적 | 공통 정책 일관 적용 |
| 한계 | 중복과 언어별 차이 큼 | 오버헤드와 운영 복잡도 증가 |
| 적합 환경 | 소규모 서비스 | 대규모 MSA와 복잡한 정책 환경 |

## Ⅳ. 구성요소 및 구조

| 구성요소 | 설명 |
|:---|:---|
| Data Plane Proxy | Envoy 같은 프록시가 서비스 옆에서 실제 요청을 중계하며 통신 제어를 실행함 |
| Control Plane | Istio 같은 제어 계층이 라우팅과 보안과 정책 배포를 중앙에서 관리함 |
| Traffic Policy | 재시도와 timeout과 canary 규칙을 정의해 서비스 간 호출 품질을 조절함 |
| Telemetry Pipeline | 로그와 메트릭과 트레이스를 수집해 분산 호출 가시성을 확보함 |

## Ⅴ. 원리 및 절차 흐름도

```text
+-------------+     +-------------+     +-------------+     +-------------+
| 정책 정의      | --> | 프록시 배포      | --> | 요청 중계/제어 | --> | 관측/정책 조정 |
+-------------+     +-------------+     +-------------+     +-------------+
```

1. **정책 정의**: 보안과 라우팅과 회복성 정책을 선언함
2. **프록시 배포**: 각 서비스 옆에 사이드카 프록시를 배치함
3. **요청 중계 및 제어**: 프록시가 mTLS와 timeout과 라우팅을 실행함
4. **관측 및 정책 조정**: 수집된 지표를 바탕으로 정책을 보정함

## Ⅵ. 문제점 및 해결 방안

1. 문제: 사이드카 프록시 수가 많아지면 CPU와 메모리 사용량과 운영 복잡도가 빠르게 증가할 수 있음
   - 해결방안: 적용 대상을 선별하고 proxy overhead ratio와 node resource headroom으로 검증함
2. 문제: 제어 평면 장애나 정책 오류가 다수 서비스 통신에 동시에 영향을 줄 수 있음
   - 해결방안: control plane 이중화와 staged rollout을 적용하고 policy rollout failure rate와 control plane availability로 검증함
3. 문제: 네트워크 추상화가 깊어지면 원인 분석이 어려워 현장 장애 대응 시간이 길어질 수 있음
   - 해결방안: trace correlation과 표준 런북을 운영하고 MTTR와 telemetry completeness로 검증함

## Ⅶ. 적용 사례

- 대형 MSA 플랫폼에서는 서비스 메시를 도입하고, proxy overhead ratio와 control plane availability로 결과를 확인함
- 보안 민감 API 환경에서는 mTLS를 강제하고, certificate compliance와 unauthorized traffic block rate로 결과를 확인함
- 카나리 배포 운영에서는 메시 라우팅 정책을 활용하고, canary success rate와 telemetry completeness로 결과를 확인함

## Ⅷ. 결론

서비스 메시는 네트워크 기능을 멋지게 보이게 하는 도구가 아니라 공통 통신 정책을 코드 밖으로 끌어내는 대가로 오버헤드와 운영 복잡도를 감수하는 구조 선택임.
