## 미리 알고가기

- 서비스 메시는 서비스 간 통신 제어를 애플리케이션 코드 밖으로 분리하는 인프라 계층임
- Data plane은 실제 요청을 중계하는 프록시 계층임
- Control plane은 라우팅과 보안 정책을 배포하고 관리하는 제어 계층임

## Ⅰ. 개요

- **정의/개념**: 서비스 메시는 마이크로서비스 간 통신에 필요한 트래픽 제어, 보안, 관측 기능을 사이드카 프록시와 중앙 제어 계층으로 분리해 애플리케이션 코드 수정 없이 네트워크 정책을 적용하는 아키텍처임.
- **배경/필요성**: 서비스 수가 많아질수록 재시도, TLS, 라우팅, 추적 로직이 각 서비스에 중복되므로, 통신 정책을 공통 계층으로 빼서 일관되게 운영할 필요가 커짐.

## Ⅱ. 특징

- 트래픽 제어와 보안 정책을 서비스 코드 밖에서 일관되게 적용함
- mTLS, retry, canary routing, tracing을 중앙 정책으로 운영할 수 있음
- 사이드카와 제어 계층이 추가되어 자원 사용량과 운영 복잡도가 커짐
- 서비스 수가 적거나 구조가 단순하면 도입 비용이 더 크게 느껴질 수 있음

## Ⅲ. 종류 및 비교

| 구분 | 라이브러리 기반 통신 제어 | 서비스 메시 |
|:---|:---|:---|
| 구현 위치 | 재시도와 보안 로직을 애플리케이션 코드 안에 넣음 | 프록시와 제어 계층이 통신 정책을 대신 수행함 |
| 정책 적용 | 서비스 코드·라이브러리별 구현 | 프록시와 제어 계층에 라우팅·mTLS·재시도 정책 배포 |
| 운영 한계 | 언어와 서비스마다 구현 품질이 달라지고 중복이 커짐 | 프록시 오버헤드와 정책 운영 복잡도가 늘어남 |
| 대표 환경 | 공통 통신 정책이 적은 소규모 서비스 | 다수 서비스에 mTLS·트래픽 정책을 공통 적용하는 MSA |

> 요약: 서비스 메시는 통신 로직을 코드에서 빼내는 대신 프록시와 정책 운영 부담을 감수하는 선택임.

## Ⅳ. 구성요소 및 구조

| 구성요소 | 설명 |
|:---|:---|
| Data Plane Proxy | Envoy 같은 프록시가 서비스 옆에서 실제 요청을 중계하며 통신 정책을 실행함 |
| Control Plane | Istio 같은 제어 계층이 라우팅과 보안과 정책 배포를 중앙에서 관리함 |
| Traffic Policy | 재시도, timeout, canary 규칙을 정의해 호출 품질과 전환 방식을 제어함 |
| Telemetry Pipeline | 로그, 메트릭, 트레이스를 수집해 분산 호출 가시성을 확보함 |

## Ⅴ. 원리 및 절차 흐름도

```text
+-------------+     +-------------+     +-------------+     +-------------+
| 정책 정의      | --> | 프록시 배포      | --> | 요청 중계/제어 | --> | 관측/정책 조정 |
+-------------+     +-------------+     +-------------+     +-------------+
```

1. **정책 정의**: 보안과 라우팅과 회복성 정책을 선언함
2. **프록시 배포**: 각 서비스 옆에 사이드카 프록시를 배치함
3. **요청 중계 및 제어**: 프록시가 mTLS와 timeout과 라우팅을 수행함
4. **관측 및 정책 조정**: 수집된 지표를 바탕으로 정책을 보정함

## Ⅵ. 실무 적용 및 유의점

1. 대형 MSA 플랫폼에서는 서비스 메시로 보안과 트래픽 정책을 통합할 수 있지만 모든 서비스에 무차별 적용하면 오버헤드가 커지므로 적용 대상을 선별하고 프록시 자원 사용 비율과 노드 여유 자원으로 확인함
2. 보안 민감 서비스에서는 mTLS와 카나리 배포를 함께 운영하되 제어 계층 오류가 전체 통신에 번지지 않도록 단계적 배포와 이중화를 적용하고 정책 배포 실패율과 제어 계층 가용률로 확인함

## Ⅶ. 결론

서비스 메시는 공통 통신 정책을 코드 밖으로 빼낼 가치가 충분할 때 선택해야 하는 운영 중심 아키텍처임.
