## Ⅰ. 개요
- **정의**: 고정 스키마 없이 다양한 데이터 모델로 수평 확장성과 유연한 저장을 제공하는 비관계형 DB
- **배경/필요성**: 대규모 비정형 데이터와 수평 확장 요구가 증가하면서 RDBMS의 고정 스키마·수직 확장 한계를 보완할 필요가 있음
- **비유**: 정해진 칸에 맞춰 넣는 서류 캐비닛(RDBMS) 대신 자유 형식으로 보관하는 창고와 유사함

| 출제 의도 | 반드시 짚을 핵심 | 감점 회피 포인트 |
|:---|:---|:---|
| RDBMS 대비 NoSQL 특성 비교 | 4가지 데이터 모델 구분 | CAP(127 참조)와 연계 필수 |

> 요약: 스키마 유연성과 수평 확장으로 대규모 비정형 데이터 처리에 특화된 DB임

## Ⅱ. 구성요소
```text
Application --> NoSQL Engine --> Storage Layer
                   |
          +--------+--------+--------+
          |        |        |        |
       Key-Value Document  Column   Graph
```

| 구성요소 | 설명 | 비유 |
|:---|:---|:---|
| Key-Value | 키로 값을 조회하는 단순 구조(Redis, DynamoDB) | 사물함 번호-물건 |
| Document | JSON/BSON 문서 단위 저장(MongoDB, CouchDB) | 파일 폴더 |
| Column-Family | 행 키 아래 컬럼 패밀리를 그룹핑(Cassandra, HBase) | 스프레드시트 시트 |
| Graph | 노드-엣지 관계 중심 저장(Neo4j) | 인맥 지도 |

> 요약: 4가지 데이터 모델이 각각 다른 접근 패턴에 최적화되어 있음

## Ⅲ. 절차
```text
요구분석 --> 데이터 모델 선택 --> 스키마 설계 --> 클러스터 구성
```
- 1단계: 접근 패턴(읽기/쓰기 비율, 쿼리 유형)을 분석함
- 2단계: 패턴에 적합한 데이터 모델(KV, Document, Column, Graph) 선택함
- 3단계: 비정규화·임베딩·참조 전략으로 스키마(또는 데이터 구조)를 설계함
- 4단계: 샤딩·복제 정책을 설정하여 분산 클러스터를 구성함

> 요약: 접근 패턴 분석-모델 선택-스키마 설계-클러스터 구성 순으로 도입함

## Ⅳ. 문제점
- 일관성 제약: 분산 환경에서 강한 일관성 보장이 어려움(CAP 127 참조)
- 조인 부재: 다중 엔터티 관계 질의 시 애플리케이션 레벨 조인으로 복잡도 증가
- 트랜잭션 한계: 다중 문서/파티션 간 ACID 트랜잭션 지원이 제한적임

> 요약: 일관성 제약, 조인 부재, 트랜잭션 한계가 주요 문제임

## Ⅴ. 개선방안
1. 단기: 최종 일관성(129 참조) 수준 정의 및 읽기 정합성 보상 로직 구현
2. 중기: 뷰 사전 계산(Materialized View)으로 조인 대체 패턴 적용
3. 장기: 분산 트랜잭션 프로토콜(Saga, 2PC 변형) 도입으로 다중 파티션 원자성 확보

> 요약: 일관성 보상, 뷰 사전 계산, 분산 트랜잭션 도입으로 NoSQL 한계를 보완함

## Ⅵ. 전망
- 발전 방향: NewSQL·멀티 모델 DB로 RDBMS와 NoSQL 장점 융합 추세
- 기술사적 판단: RDBMS 대체가 아닌 보완 관계로, 워크로드별 적합 DB 선택이 핵심임
- 기술사 제언: CAP/PACELC(127, 128 참조) 이해 기반으로 데이터 모델-일관성 수준을 함께 결정할 필요
