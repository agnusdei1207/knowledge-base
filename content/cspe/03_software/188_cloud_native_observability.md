## 미리 알고가기

- 관측성은 시스템이 내보낸 신호로 내부 상태와 문제 원인을 질의·추론할 수 있는 성질임
- 메트릭은 일정 구간의 수치 상태를 집계해 추세·임계치·SLO를 확인함
- 로그는 특정 시점에 발생한 사건과 처리 문맥을 기록함
- 트레이스는 하나의 요청이 여러 서비스에서 만든 Span을 연결해 호출 경로를 나타냄
- 리소스 속성은 서비스·Pod·노드·클러스터처럼 신호를 생성한 대상을 식별함
- 카디널리티는 속성값 조합 수이며 저장·조회 비용과 신호 상세도의 균형을 결정함

## 작성 근거(검토용)

- 클라우드 네이티브 관측성은 메트릭·로그·트레이스의 역할과 상관관계를 핵심 축으로 설명함
- 비교표는 기록 단위·핵심 질문·수집과 활용의 정확히 3개 축을 대비함
- Ⅴ절은 관측 목표부터 계측·문맥 연결·수집·상관 분석·개선까지의 절차로 구성함
- 분산 API와 컨테이너 플랫폼에서 신호를 연결하고 사용자 영향 지표를 확인함

## Ⅰ. 개요

- **정의/개념**: 클라우드 네이티브 관측성은 메트릭·로그·트레이스를 서비스·워크로드 문맥으로 연결해 분산 시스템의 상태와 원인을 추론하는 능력임
- **배경/필요성**: 수명이 짧고 호출 경로가 분산된 워크로드의 장애 지점과 사용자 영향을 찾기 위해 상관 가능한 텔레메트리가 필요함

### 쉽게 이해하기 (학습용)
- 관측성은 외부에서 상태를 보는 데 그치지 않고 신호를 연결해 내부 원인을 찾는 능력임

## Ⅱ. 특징

- 수명이 짧은 서비스 인스턴스의 신호도 리소스 속성과 시간 정보로 연결함
- 메트릭의 이상 구간·트레이스의 호출 경로·로그의 사건 문맥을 상호 연결함
- 계측 범위·속성 카디널리티·샘플링·보존 기간이 분석 상세도와 수집 비용을 결정함
- 사용자 관점 SLI와 서비스 의존 경로를 함께 관측해 증상과 원인을 구분함

### 쉽게 이해하기 (학습용)
- 메트릭·로그·트레이스는 같은 서비스·요청 문맥으로 연결해야 원인을 좁힐 수 있음

## Ⅲ. 종류 및 비교

| 판단 기준 | 메트릭 | 로그 | 트레이스 |
|:---|:---|:---|:---|
| 기록 단위 | 시계열 수치와 구간 집계 | 시점별 사건 레코드 | 요청별 Span과 호출 관계 |
| 핵심 질문 | 어떤 비율·수준·추세인가 | 어떤 사건과 값이 기록됐는가 | 요청이 어디에서 지연·실패했는가 |
| 수집과 활용 | 주기·라벨을 제어해 SLO·추세 분석 | 수준·필드·보존을 제어해 사건 원인 확인 | 계측·샘플링을 제어해 의존성과 병목 분석 |

> 요약: 메트릭은 수치 추세, 로그는 사건 상세, 트레이스는 요청 경로를 보여주며 공통 문맥으로 연결됨.

### 쉽게 이해하기 (학습용)
- 메트릭은 이상을 알리고 로그는 사건을 설명하며 트레이스는 요청이 지나간 길을 보여줌

## Ⅳ. 구성요소 및 구조

| 구성요소 | 설명 |
|:---|:---|
| 계측 지점 | 애플리케이션·런타임·노드에서 메트릭·로그·Span을 생성함 |
| 문맥 전파 | Trace ID는 서비스 호출에 전파하고 리소스 속성은 신호에 부여함 |
| 수집·처리 계층 | 신호를 수신하고 필터·집계·샘플링·속성 보강을 수행함 |
| 신호 저장소 | 시계열·로그·트레이스를 조회 특성에 맞게 보존함 |
| 분석·경보 계층 | 대시보드·SLO·추적 조회·경보로 상태와 원인을 제시함 |

```text
애플리케이션·Pod·노드 -> 메트릭·로그·트레이스 -> 수집·처리 -> 신호 저장소
             |                                           |
             +----------- 공통 문맥 ---------------------+-> 분석·경보
```

> 요약: 계측 신호는 공통 문맥과 수집 계층을 거쳐 저장되며 분석 단계에서 서로 연결됨.

### 쉽게 이해하기 (학습용)
- 계측기·수집기·저장소·분석 도구가 세 신호를 같은 문맥으로 연결함

## Ⅴ. 원리 및 절차 흐름도

```text
사용자 SLI 선정 -> 메트릭·로그·트레이스 계측 -> 공통 문맥 연결 -> 수집·저장 -> 상관 분석 -> 개선
```

1. 사용자 영향과 서비스 목표를 나타낼 SLI를 정함
2. 필요한 지점에 세 신호를 계측하고 서비스·요청 식별자를 연결함
3. 수집 계층에서 필터·집계·샘플링·민감정보 제거를 적용함
4. 이상 메트릭에서 관련 로그와 트레이스를 찾아 원인을 확인함
5. 개선 결과를 SLI와 비용으로 재평가해 계측 범위를 조정함

> 요약: 사용자 영향 신호에서 출발해 같은 문맥의 로그·트레이스로 원인을 찾고 개선 결과를 다시 측정함.

### 쉽게 이해하기 (학습용)
- 이상 알림을 받은 뒤 같은 요청의 기록과 경로를 찾아 원인을 고치고 효과를 확인함

## Ⅵ. 실무 사례

1. 결제 API는 Trace ID로 로그·트레이스를 연결하고 오류율·p99 지연을 확인함
2. 컨테이너 플랫폼은 노드 메트릭과 OOM 로그를 연결하고 메모리 사용률·재시작 수를 확인함

### 쉽게 이해하기 (학습용)
- 지연과 재시작을 사용자 요청·오류 기록·노드 자원과 연결해 분석함

## Ⅶ. 결론

- 클라우드 네이티브 관측성은 사용자 SLI에 맞춰 세 신호를 계측하고 공통 문맥·수집 비용을 통제함

### 쉽게 이해하기 (학습용)
- 많이 수집하는 것보다 사용자 영향과 원인을 연결하는 신호를 적정 비용으로 유지해야 함
