# 📖 【암기용】 개념 완전 이해

## 한눈에
- **개요**: 시스템의 외부 출력 데이터(메트릭, 로그, 트레이스)를 기반으로 내부의 상태와 문제를 깊이 있게 이해하고 디버깅하는 역량이다.
- **왜 필요한가**: 수천 개의 컨테이너가 떴다 사라지는 MSA 환경에서는 과거처럼 서버 한 대에 접속해 로그를 뒤지는 모니터링이 불가능하다. "어디서, 왜 느려졌는지" 알려면 데이터가 하나로 엮여야 한다.
- **핵심 직관**: 모니터링이 계기판의 "속도가 떨어졌다(결과)"를 보여준다면, 관측성은 엔진 온도, 연료 분사량, 타이어 마찰 데이터를 엮어 "연료 펌프 고장으로 속도가 떨어졌다(원인)"고 진단해주는 정비 시스템이다.

## 핵심 용어 정리

| 용어/표기 | 의미 | 비유·예 |
|:---|:---|:---|
| MELT | 관측성의 4대 기둥: Metrics, Events, Logs, Traces | 건강검진의 혈압치, 증상기록, 엑스레이, 혈류추적 |
| 카디널리티 (Cardinality) | 특정 데이터 집합(예: 사용자 ID, IP)이 가질 수 있는 고유값의 개수 | "성별(2개, 낮음)" vs "주민번호(5천만, 높음)" |
| 분산 추적 (Trace) | 사용자의 1개 요청이 여러 마이크로서비스를 거치는 전체 경로와 지연 시간 | 배송 조회 시스템의 타임라인 |

## 깊이 이해
- **배경·문제의식**: 기존의 '모니터링(Monitoring)'은 "CPU가 90%다"처럼 미리 정의된 실패 조건(Known Unknowns)만 감시했다. 하지만 클라우드 네이티브의 분산 환경에서는 예측할 수 없는 기상천외한 오류(Unknown Unknowns)가 발생하므로, 질문을 던져 원인을 찾을 수 있는 '관측성'이 필요해졌다.
- **작동 원리**: 애플리케이션과 인프라에서 발생하는 모든 텔레메트리(MELT) 데이터를 수집(OpenTelemetry 등)하여 중앙 백엔드(Prometheus, Elasticsearch 등)로 보낸다. 중요한 것은 이 데이터들이 `TraceID` 같은 고유 식별자로 서로 **상관관계(Correlation)**를 맺어 엮여 있다는 점이다.
- **비유**: 범죄 수사에서 CCTV(로그), 카드 결제 내역(메트릭), 교통카드 승하차(트레이스)를 '용의자 신원(Trace ID)'이라는 하나의 선으로 연결해야 범행 동선(근본 원인)이 그려지는 것과 같다.
- **구체 예시**: 결제 실패 시, 알람(메트릭)이 울리면 대시보드에서 해당 시점의 분산 추적(Trace)을 열어 결제 서비스 -> 재고 서비스 사이의 지연을 발견하고, 그 구간의 에러 로그(Log)를 클릭해 "DB 커넥션 풀 고갈"이라는 원인을 찾아낸다.
- **흔한 오해·주의점**: 로그 플랫폼(Splunk)이나 메트릭 도구(Datadog)를 샀다고 관측성이 생기는 게 아니다. 데이터들이 서로 연결(Context Propagation)되어 있지 않으면 그냥 거대한 쓰레기통일 뿐이다.

## 연결 개념
- **OpenTelemetry**: 이 모든 관측 데이터를 특정 벤더(Datadog, New Relic) 종속 없이 표준화하여 수집하는 프레임워크 (189번)
- **SRE (사이트 신뢰성 공학)**: 관측성을 무기로 SLO(서비스 수준 목표)를 관리하고 인시던트에 대응하는 운영 방법론 (191번)
- **AIOps**: 방대한 관측 데이터를 AI로 분석해 이상 징후를 선제 탐지하는 자동화 기술 (194번)

# 📝 【답안용】 시험 답안 템플릿

## 핵심 인사이트 (3줄 요약)

> 1. **본질**: 클라우드 네이티브 관측성은 시스템이 생성하는 텔레메트리 데이터(MELT)를 수집, 연관 분석하여 예측 불가능한 시스템 상태(Unknown Unknowns)를 진단하는 역량이다.
> 2. **가치**: 마이크로서비스 환경에서 장애 발생 시, 메트릭(알림) → 트레이스(구간 특정) → 로그(원인 분석)로 이어지는 심리스한 인시던트 해결(MTTR 단축)을 제공한다.
> 3. **판단 포인트**: 데이터 폭증으로 인한 스토리지 비용과 고(High) 카디널리티 처리 병목이 발생하므로, 샘플링 전략과 OpenTelemetry 기반의 벤더 중립 아키텍처 설계가 필수적이다.

## 출제 의도 및 답안 포인트

| 출제 의도 | 반드시 짚을 핵심 | 감점 회피 포인트 |
|:---|:---|:---|
| 기존 모니터링 한계와 관측성의 패러다임 전환 이해 | Known Unknowns vs Unknown Unknowns | "모니터링의 최신 단어" 수준의 빈 추상 서술 |
| 3대(또는 4대) 필라(Pillar) 간의 상관관계(Correlation) 구성 | MELT(Metrics, Events, Logs, Traces), Trace ID 기반 맥락 전파 | 데이터 수집 자체만 나열하고 "연결성" 누락 |
| 대규모 관측 인프라 운영의 트레이드오프 파악 | 데이터 스토리지 비용, 카디널리티 폭증 방어 기법 | 툴 이름(Prometheus, ELK 등)만 단순 나열 |

> 요약: 관측성은 툴 도입이 아니라 데이터 간의 '문맥 연결(Context Propagation)'을 통한 장애 근본 원인 분석(RCA) 최적화 역량임을 증명해야 한다.

## Ⅰ. 개요 및 필요성

- 개요: 관측성(Observability)은 텔레메트리 데이터(메트릭, 로그, 트레이스)를 기반으로 시스템의 내부 상태와 근본 원인을 동적으로 추론하는 역량임
- 배경: 분산형 MSA와 단명(Ephemeral)하는 컨테이너 환경에서는 기존의 서버 단위 수동 로그 분석이나 사전 정의된 임계치 알람 룰만으로는 장애 대응 한계 발생
- 필요성: 시스템의 예측 불가능한 실패(Unknown Unknowns)에 대해 즉각적인 쿼리와 상관관계 분석을 수행하여 장애 복구 시간(MTTR)을 획기적으로 단축해야 함

---

## Ⅱ. 구조 및 구성요소

```text
[Applications / Infra] -> [Telemetry Collection] -> [Backend & Correlation] -> [Action]
 (App, K8s, Network)       (OpenTelemetry)           (Metric, Log, Trace)      (AIOps, SRE)
```

| 구성요소 | 역할 | 특이사항 |
|:---|:---|:---|
| Metrics (메트릭) | 시스템의 특정 시간대 수치 데이터 (CPU, 처리량, 오류율) | 이상 징후 탐지와 알람(Alerting)의 기준 |
| Traces (분산 추적) | 사용자 요청이 여러 서비스를 거치는 전체 라이프사이클 경로 | 병목 구간(Bottleneck) 특정에 필수 |
| Logs (로그) | 특정 시점, 특정 노드에서 발생한 구체적인 텍스트 이벤트 | 근본 원인(Root Cause) 상세 분석 |
| Correlation Engine | Trace ID, Span ID를 통해 위 세 가지 데이터를 상호 연결 | 사일로(Silo)화된 데이터 통합 |

> 요약: 메트릭으로 인지하고, 트레이스로 위치를 찾으며, 로그로 원인을 규명하는 3단계(MELT) 유기적 데이터 연결 구조를 갖는다.

---

## Ⅲ. 동작원리 및 흐름도

```text
계측(Instrumentation) -> 맥락 전파(Trace ID) -> 수집/정제(Collector) -> 상관 분석/시각화
```

- 1단계 [코드 계측]: 애플리케이션 라이브러리(또는 eBPF, 사이드카)를 통해 서비스 내부에 텔레메트리 생성 로직 삽입
- 2단계 [문맥 전파]: HTTP 헤더(W3C Trace Context)에 Trace ID를 주입하여, 서비스 간 통신 시 전체 요청 흐름 식별자 유지
- 3단계 [수집 및 정제]: 에이전트(Collector)가 데이터를 수집, 샘플링, PII(개인정보) 마스킹 처리 후 저장소 포맷으로 변환(OTLP 활용)
- 4단계 [상관 분석]: 중앙 대시보드(Grafana 등)에서 타임스탬프와 Trace ID를 기준으로 메트릭 급증 구간과 에러 로그를 교차 분석

> 요약: 단일 Trace ID를 매개로 분산된 환경의 모든 이벤트 맥락을 하나로 이어, 시스템 전체의 가시성을 확보한다.

---

## Ⅳ. 특징
- [Unknown Unknowns 탐지]: 사전에 정의된 임계치가 없어도, 다차원 데이터 쿼리를 통해 개발자가 예상치 못한 신규 장애 패턴 분석 가능
- [카디널리티 폭증 리스크]: 사용자 ID, 세션 등 고유값이 많은 라벨(High Cardinality)을 메트릭에 추가할 경우 시계열 DB(TSDB) 메모리 고갈 발생
- [벤더 중립성 과제]: Datadog, Splunk 등 상용 솔루션 고착화 시 데이터 마이그레이션 및 비용 통제가 불가능해짐
- [오버헤드 발생]: 모든 요청을 100% 트레이싱할 경우 네트워크 대역폭 및 스토리지 비용이 서비스 인프라 비용을 초과할 수 있음

> 요약: 강력한 심층 분석 능력을 제공하지만, 대규모 데이터 처리 비용과 고 카디널리티 병목을 수반하는 양날의 검이다.

## Ⅴ. 심화 비교 및 적용 판단

| 비교 축 | 전통적 Monitoring | Cloud Native Observability | 선택 기준 |
|:---|:---|:---|:---|
| 감시 대상 | Known Unknowns (예상된 장애) | Unknown Unknowns (예측불가 장애) | 아키텍처 복잡도 (Monolithic vs MSA) |
| 데이터 구조 | 사일로화된 대시보드 (DB 분리) | Trace ID 기반 상관관계(Correlation) 통합 | 인시던트 디버깅 연계성 요구 |
| 조사 방식 | 대시보드 수동 모니터링 확인 | 다차원 쿼리 및 탐험(Exploration) | MTTR(평균 복구 시간) 목표치 |

> 요약: 정적인 서버 환경에서는 모니터링으로 충분하나, 동적이고 유동적인 K8s 기반 MSA에서는 데이터가 연결된 관측성이 필수다.

**리스크·대응 (기본은 불릿):**
- [스토리지 비용 폭증]: 텔레메트리 데이터 급증으로 스토리지 리소스 고갈 → 꼬리 기반 샘플링(Tail-based Sampling)을 적용해 에러/지연 요청만 100% 저장 (지표: 일일 인제스트(Ingest) 데이터량)
- [TSDB 카디널리티 병목]: 메트릭 라벨 남용으로 쿼리 지연 및 메모리 OOM 발생 → Collector 단에서 무한대 라벨(User IP 등) Drop 처리 규칙 적용 (지표: TSDB Active Series 수)

**도입 후 점검 지표 (기본은 불릿):**
- 장애 대응: 인시던트 발생 후 근본 원인 파악 시간(MTTI) 70% 단축 — 포스트모템(Post-mortem) 리포트
- 데이터 품질: 전체 트레이스 중 로그/메트릭과 Trace ID가 연동된 비율 95% 달성 — 분산 추적 무결성 체크

## Ⅵ. 실무 적용 및 결론

**적용 방안 3개 (필수 — 단계별 또는 항목별):**
1. [표준 파이프라인 구축]: OpenTelemetry를 표준 텔레메트리 수집기로 전면 도입하여 특정 벤더(Vendor Lock-in) 종속성 제거 및 비용 최적화 통제권 확보
2. [상관관계 대시보드 통합]: 메트릭 스파이크 발생 시 클릭 한 번에 해당 시점의 분산 트레이스와 컨테이너 에러 로그로 드릴다운(Drill-down) 되는 통합 뷰 구현
3. [eBPF 기반 관측성 보완]: 애플리케이션 코드 수정이 어려운 레거시 컴포넌트는 eBPF 기반(Pixie 등) 도구를 활용해 커널 레벨 네트워크 지연 트레이스 자동 수집

**결론 (2줄):**
- 기술사 판단: 클라우드 네이티브 관측성은 도구의 도입이 아니라 "시스템이 스스로 상태를 설명하게 만드는" 아키텍처 설계 사상이자 문화임
- 향후 방향: 방대한 텔레메트리 데이터 분석의 인지 부하를 줄이기 위해, AIOps 기반의 이상 탐지(Anomaly Detection)와 자동 원인 추론으로 발전 중임

| 유형 | 문제 신호어 | Ⅱ·Ⅲ 강조 | Ⅴ·Ⅵ 강조 |
|:---|:---|:---|:---|
| 포괄형 | "관측성을 설명하시오" | MELT 구성요소와 상호 연결 동작 흐름 | 전통적 모니터링과의 비교 및 트레이드오프 |
| 요구사항 명시형 | "구축 방안을 제시하시오" | Trace ID 전파 및 데이터 정제 아키텍처 | 고 카디널리티/비용 통제 리스크, OTel 적용 방안 |

> 요약: 관측성의 본질은 '데이터의 상관관계(Trace ID)'에 있으므로, 이 연결 고리가 어떻게 디버깅을 혁신하는지에 초점을 맞춘다.
