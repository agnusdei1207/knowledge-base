# 📖 【암기용】 개념 완전 이해

> 목적: 이 개념을 처음 보는 사람도 완벽히 이해하게 만든다. 시험 답안 양식이 아니라, 이해를 위한 친절한 설명이다.

## 한눈에
- **개요**: **DORA 메트릭**은 구글(Google) 산하 연구팀인 DORA가 7년간 전 세계 수만 개 IT 조직을 분석해서 뽑아낸 **"소프트웨어 개발팀의 전투력을 측정하는 절대 4대 지표"**다. "우리 팀 애자일 잘해요!"라고 입으로만 떠들지 말고, 이 4가지 숫자로 랭크(Elite, High, Medium, Low)를 까보라는 것이다.
- **왜 필요한가**: 옛날에는 개발자의 실력을 '하루에 코드 몇 줄을 짰나(LOC)'나 '버그를 몇 개 잡았나'로 평가했다. 하지만 이건 꼼수를 쓰기 너무 쉬운 쓰레기 지표다. DORA는 **속도(얼마나 빨리 배포하나)**와 **안정성(얼마나 안 터지나)**이라는 모순된 두 마리 토끼를 동시에 측정하여, 개발팀과 데브옵스(DevOps) 인프라의 진짜 수준을 발가벗긴다.
- **핵심 직관**: 
  - 속도(Speed) 지표: 배포 빈도(DF), 변경 리드타임(LT)
  - 안정성(Stability) 지표: 변경 실패율(CFR), 서비스 복구 시간(MTTR)

## 깊이 이해
- **배경·문제의식**: 애자일과 데브옵스(DevOps)가 유행하면서 너도나도 "우리는 실리콘밸리처럼 일한다"고 자부했다. 하지만 진짜인지 가짜인지 측정할 객관적 표준 온도계가 없었다. 구글 DORA 팀은 "가짜 애자일 조직은 속도만 빠르고 맨날 서버가 터지거나, 아니면 안정성 핑계로 한 달에 한 번 배포한다"는 팩트를 데이터로 증명해 냈다.
- **작동 원리 (마법의 4대 지표)**:
  1. **배포 빈도 (Deployment Frequency, DF)**: "얼마나 자주 라이브(운영) 서버에 코드를 배포하는가?" (하루 10번? 한 달 1번?)
  2. **변경 리드타임 (Lead Time for Changes, LT)**: "개발자가 코드를 `git commit` 한 순간부터, 운영 서버에 올라갈 때까지 얼마나 걸리는가?" (1시간? 1주일?)
  3. **변경 실패율 (Change Failure Rate, CFR)**: "배포를 했을 때 서버가 뻗거나 롤백(Rollback) 해야 하는 비율이 몇 % 인가?" (0~15% 수준이 정상)
  4. **서비스 복구 시간 (Time to Restore Service, MTTR)**: "운영 서버가 뻗었을 때, 다시 살려내는 데 얼마나 걸리는가?" (1시간 이내? 하루 종일?)
- **비유**: F1 카레이싱 팀
  - 속도 지표(DF, LT): 타이어를 교체하는 빈도와 피트 스탑(Pit Stop)에 걸리는 찰나의 시간.
  - 안정성 지표(CFR, MTTR): 타이어를 바꿨는데 바퀴가 빠지는 사고 확률(실패율)과, 찌그러진 범퍼를 다시 고쳐서 트랙에 내보내는 속도(복구 시간).
- **구체 예시**: **엘리트(Elite) 조직**은 하루에 수십 번 배포(DF)하고, 커밋 후 배포까지 1시간(LT)이 채 안 걸린다. 그러면서도 배포 실패율(CFR)은 15% 미만이고 뻗어도 1시간(MTTR) 안에 무조건 복구한다. 쿠팡, 우아한형제들 같은 회사들의 CI/CD 파이프라인이 이 엘리트 등급을 조준하고 있다.
- **흔한 오해·주의점**: 속도와 안정성은 보통 '트레이드오프(하나가 오르면 하나가 떨어짐)'라고 생각한다. 하지만 DORA의 연구 결과는 충격적이었다. **엘리트 조직은 배포를 미친 듯이 빨리, 자주 하면서도(속도) 서버가 절대 터지지 않았다(안정성).** 자동화 테스트(CI)와 작게 쪼개서 배포(MSA)하는 기술력이 딜레마를 박살 낸 것이다.

## 연결 개념
- **DevOps (데브옵스)**: DORA 메트릭의 엘리트 등급을 찍으려면 젠킨스(Jenkins)로 코드를 10분 만에 배포하고(CI/CD), 쿠버네티스(k8s)로 터진 서버를 1초 만에 재생시키는(MTTR 단축) 데브옵스 인프라가 100% 필수다.
- **신뢰성(Reliability) 지표 보완**: 구글은 나중에 DORA 4개만으로는 '운영 품질'을 다 못 잰다며 SRE(사이트 신뢰성 공학) 철학을 섞어, '가용성 목표(SLO)' 같은 지표를 5번째 메트릭으로 슬쩍 얹기도 했다.

## Ⅰ. 개요 및 필요성

- 정의: 애자일 및 DevOps 조직의 퍼포먼스를 측정하기 위해 구글이 표준화한 4가지 핵심 성과 지표(배포 빈도, 변경 리드타임, 변경 실패율, 서비스 복구 시간)
- 배경: 기존의 스토리 포인트(Story Point)나 버그 발견율 지표는 팀 내부의 속도만 보여줄 뿐, 실제 고객에게 가치(Value)가 도달하는 병목(운영팀 이관 지연 등)을 가려버리는 치명적 착시 유발
- 필요성: 개발(Dev)과 운영(Ops)의 벽(Silo)을 허물고 배포 파이프라인의 엔드 투 엔드(End-to-End) 효율성을 객관화하여, 조직을 Elite 수준의 지속적 인도(Continuous Delivery) 체계로 혁신하기 위함

## Ⅱ. DORA 4대 핵심 메트릭 (속도 vs 안정성 아키텍처)

DORA는 속도 지표가 폭주하여 안정성이 박살 나는 것을 막기 위해 2:2 쌍(Pair)으로 브레이크를 건다.

```text
[ DORA Metrics: 배포 파이프라인 매핑 ]

[ 1. 개발 (Commit) ] -------- (CI/CD 파이프라인) --------> [ 2. 운영 (Production) ]
        |                                                       |
        +-- (지표 2: 변경 리드타임 LT) ----------------------> (도달 완료)
                                                                |
                                             (지표 1: 배포 빈도 DF) : 하루에 이걸 몇 번이나 쏘는가?
                                             (지표 3: 변경 실패율 CFR): 쐈을 때 뻗는 비율 (%)
                                             (지표 4: 복구 시간 MTTR) : 뻗었을 때 살려내는 시간
```

| 지표 범주 | 핵심 메트릭 (영문) | 측정의 본질적 의미와 이상적인 Elite 등급 기준 |
|:---|:---|:---|
| **속도 (Speed)** | **DF (Deployment Frequency)** <br> 배포 빈도 | 시장에 고객 가치를 얼마나 자주 던지는가? <br> 👉 Elite 기준: **온디맨드 (하루 다수 회)** |
| | **LT (Lead Time for Changes)** <br> 변경 리드타임 | Commit된 코드가 Production을 밟을 때까지의 시간 (결재 병목 색출) <br> 👉 Elite 기준: **1시간 미만** |
| **안정성 (Stability)**| **CFR (Change Failure Rate)** <br> 변경 실패율 | 배포 후 장애(핫픽스, 롤백, 타임아웃)가 터지는 비율 <br> 👉 Elite 기준: **0% ~ 15% 사이** |
| | **MTTR (Time to Restore Service)** <br> 서비스 복구 시간 | 사고 났을 때 패닉에 빠지지 않고 원래 상태로 복구하는 심폐소생 속도 <br> 👉 Elite 기준: **1시간 미만** |

> 요약: 배포 결재받는 데 1주일 걸리는 은행(LT 지연)은 애자일이 아니다. 배포는 하루에 10번 하는데 매일 1번씩 서버가 뻗는 스타트업(CFR 폭발)도 엘리트가 아니다. 네 개가 동시에 좋아야 진짜다.

## Ⅲ. 트레이드오프 파괴: 엘리트(Elite) 조직의 기술적 비밀

전통 공학에서는 속도를 높이면 불량률(실패율)이 오른다. DORA는 IT에서 이 법칙을 깬 요소가 **자동화**임을 밝혀냈다.

| 엘리트 4대 지표 동시 달성을 위한 데브옵스 핵심 프랙티스 (기술 맵핑) |
|:---|
| **1. DF & LT (속도) 견인 기제**: 마이크로서비스(MSA)와 모듈화 |
| 덩치가 큰 모놀리식 서버는 배포 한 번 하려면 전 부서가 모여 1달간 빅뱅 테스트를 해야 함 (DF/LT 하락). 도메인을 잘게 쪼갠 MSA로 진화해야 내가 고친 코드 100줄만 내 맘대로 하루 10번씩 자동(Jenkins) 배포 가능 |
| **2. CFR (변경 실패율) 방어 기제**: TDD 및 CI 자동화 테스트 커버리지 |
| 사람이 눈으로 하는 QA(Manual Test)를 맹신하면 속도를 올릴수록 서버가 뻗음. 소스 푸시(Push) 즉시 SonarQube 정적 분석과 JUnit 1만 개가 3분 안에 에러를 검출(Shift-Left)하여 썩은 코드의 Prod 진입을 원천 차단 |
| **3. MTTR (복구 시간) 압축 기제**: Blue-Green 배포 및 K8s 셀프 힐링 |
| 장애가 터졌을 때 SSH로 서버에 들어가서 로그(Log)를 뒤지면 복구에 3시간 걸림. 쿠버네티스(Kubernetes)의 선언적 롤백(`kubectl rollout undo`)이나 블루/그린 트래픽 스위칭으로 1초 만에 구버전으로 엎어버려 MTTR 극단 단축 |

> 요약: DORA 지표는 마법의 주문이 아니라 '성적표'다. 이 성적을 Elite로 올리려면 개발 문화를 바꾸는 립서비스로는 어림도 없고, CI/CD, 자동화 테스트, 컨테이너 인프라라는 막대한 현찰(투자)이 들어가야 한다.

## Ⅳ. 극복해야 할 시스템적 리스크 및 측정의 함정

메트릭(Metric)의 가장 큰 적은 '개발자들의 숫자 꼼수(Gaming the system)'다.

| 리스크 요인 | 발생 시나리오 및 시스템 붕괴 원인 | 아키텍처 대응 방안 (실무 튜닝) |
|:---|:---|:---|
| **메트릭 조작 (Gaming)** | 배포 빈도(DF)를 KPI 고과에 반영하자, 개발자들이 띄어쓰기 1줄 고치고 배포 100번을 날리며 가짜 엘리트 랭크를 찍어버리는 쓰레기 통계 오염 발생 | DORA 메트릭을 절대 **인사 평가(개인 KPI)와 연동하지 못하도록 조직 헌장으로 강제 금지**. 오직 팀 단위의 파이프라인 병목 탐지(블라인드) 용도로만 활용 |
| LT 측정 구간 왜곡 | LT를 '아이디어가 나온 순간'부터 재면 기획팀 병목(한 달)이 섞임. 반대로 '머지(Merge)'된 순간부터 재면 개발 병목이 숨겨짐 | Git 레포지토리(GitHub/GitLab)의 최초 `Commit` 발생 시간표와 CD 도구(ArgoCD)의 `Deploy` 완료 이벤트 웹훅(Webhook)을 연동하여, 인간의 개입이 불가능한 기계적 타임스탬프 로깅 추출 |

> 요약: 굿하트의 법칙(Goodhart's Law). "측정 지표가 목표가 되는 순간, 그것은 더 이상 좋은 지표가 아니다." DORA 메트릭은 개발팀을 쪼는 채찍이 아니라, 인프라의 구멍 난 타이어를 찾는 엑스레이(X-Ray) 기계여야 한다.

## Ⅴ. 실무 적용 방안 및 결론

**적용 방안 3개:**
1. [Jenkins + Prometheus 기반 DORA 대시보드 자동화] DevOps 성과 측정 시, 개발팀에게 엑셀로 기입하게 하는 수동 짓을 폐기하고 젠킨스의 빌드/배포 파이프라인 로그와 Datadog(또는 ELK) 장애 얼럿 로그를 연동시켜 4대 지표를 실시간 Grafana 대시보드에 무인(Automated) 시각화 튜닝
2. [CFR(변경 실패율) 하락 시 서킷 브레이커 발동] 배포 파이프라인 품질 게이트 설정 시, 최근 1주일간 특정 서비스의 CFR이 15%를 초과할 경우 해당 MSA 모듈의 CD(자동 배포) 파이프라인 밸브를 강제로 잠그고(Lock), 신규 개발 대신 '품질 안정화 스프린트' 강제 전환 정책 도입
3. [Feature Flag(피처 토글) 기반 리드타임 압축] 비즈니스 마케팅 날짜(오픈일)에 맞춰 코드를 묶어두느라 LT가 1개월로 늦어지는 현상을 타파하기 위해, 코드는 일단 매일 배포(DF 극대화)하되 사용자 화면에서만 가려두는 피처 플래그(Feature Toggle) 아키텍처를 삽입해 개발과 비즈니스 릴리즈를 완벽 분리

**결론:**
- 기술사 판단: DORA 메트릭은 소프트웨어 엔지니어링이 뜬구름 잡는 철학(Agile Manifesto)에서 벗어나, 데이터 중심(Data-driven) 과학으로 진화했음을 보여주는 완벽한 이정표다. 이 4개의 숫자는 조직의 CI/CD 수준, 자동화 테스트 커버리지, 그리고 사일로(Silo) 파괴 여부를 1%의 거짓도 없이 증명해 낸다.
- 향후 방향: 최근 DORA 모델은 속도와 안정성을 넘어 개발자의 행복도(Burnout)와 심리적 안전감을 측정하는 5번째 지표(문화 메트릭), 그리고 플랫폼 엔지니어링(Platform Engineering)을 통한 내부 개발자 경험(IDP) 지표 향상으로 그 생태계 철학을 더욱 거대하게 확장해 나가고 있다.
