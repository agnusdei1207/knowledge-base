# 📖 【암기용】 개념 완전 이해

## 한눈에
- **개요**: 우선순위가 다른 여러 개의 큐를 두고, 프로세스의 CPU 사용 패턴에 따라 큐 사이를 이동시키는 동적 스케줄링 기법
- **왜 필요한가**: 사전에 프로세스가 I/O 바운드인지 CPU 바운드인지 알 수 없는 상황에서, 둘 다 만족시키기(빠른 응답 + 기아 방지) 위함이다.
- **핵심 직관**: 놀이공원의 VIP(상위 큐)와 일반 대기줄(하위 큐) 시스템. 짧게 놀고 빠지는 애(I/O 바운드)는 VIP에 남기고, 진득하게 하루종일 타는 애(CPU 바운드)는 일반 대기줄로 내린다.

## 핵심 용어 정리

| 용어/표기 | 의미 | 비유·예 |
|:---|:---|:---|
| 우선순위 큐 | 각기 다른 타임 퀀텀을 가진 대기열 | VIP줄, 일반줄, 후순위줄 |
| 피드백 (Feedback) | 과거 동작 패턴을 바탕으로 우선순위를 조정 | 오래 놀면 일반줄로 강등 |
| I/O 바운드 | 입출력이 많아 CPU를 짧게 쓰는 프로세스 | 놀이기구 하나만 타고 밥 먹으러 가는 손님 |
| CPU 바운드 | 연산이 많아 CPU를 길게 쓰는 프로세스 | 롤러코스터 10번 연속 타려는 손님 |
| 에이징 (Aging) | 기아 방지를 위해 주기적으로 모든 프로세스를 최상위 큐로 올림 | 오래 기다린 일반 손님을 VIP로 승급 |

## 깊이 이해
- **배경·문제의식**: FCFS, SJF, RR 등 단일 큐 스케줄러는 완벽하지 않다. 대화형 작업(I/O 바운드)은 응답성이 중요하고, 배치 작업(CPU 바운드)은 문맥 전환(Context Switch) 비용을 줄이는 게 중요하다. 이를 동시에 달성하려면 여러 큐가 필요하다.
- **작동 원리**: 
  1. 새 프로세스는 가장 높은 우선순위 큐(Q0)에 들어간다. (타임 퀀텀 가장 짧음)
  2. 타임 퀀텀을 다 소진하면(CPU 바운드) 하위 큐(Q1)로 강등된다.
  3. 타임 퀀텀 이전에 I/O를 요청하면(I/O 바운드) 원래 큐 우선순위를 유지한다.
  4. 하위 큐일수록 타임 퀀텀을 길게 주어 오버헤드를 줄인다.
- **구체 예시**: Q0(퀀텀 10ms), Q1(퀀텀 20ms), Q2(퀀텀 40ms)가 있다. 프로세스가 15ms짜리 작업을 하면 Q0에서 10ms 실행 후 쫓겨나 Q1로 강등되고, Q1에서 남은 5ms를 실행 후 완료된다.
- **흔한 오해·주의점**: MLFQ 설계 시 프로세스가 I/O 직전에 자발적으로 CPU를 반납해(꼼수) 영원히 상위 큐에 머무르는 어뷰징(Gaming the system) 문제가 발생할 수 있다. 이를 막기 위해 '주기적 부스트(에이징)'나 '총 누적 사용량 기준 강등' 규칙을 도입한다.

## 연결 개념
- 스케줄링 (004 참조) — MLFQ 이전의 고전적 알고리즘의 한계
- 기아와 에이징 (011 참조) — 하위 큐의 무한 대기 문제 해결
- CFS (006 참조) — 리눅스의 또 다른 진화된 스케줄러

# 📝 【답안용】 시험 답안 템플릿

## 핵심 인사이트 (3줄 요약)

> 1. **본질**: MLFQ는 프로세스의 CPU 사용 이력을 바탕으로 우선순위 큐 사이를 이동시키는 적응형(Adaptive) 스케줄링 기법이다.
> 2. **가치**: I/O 바운드 프로세스의 응답성을 극대화하면서 동시에 CPU 바운드 프로세스의 문맥 전환 오버헤드를 최소화한다.
> 3. **판단 포인트**: 타임 퀀텀 크기, 큐의 개수, 강등/승급 조건 등 튜닝 파라미터가 시스템 성능을 좌우하므로 워크로드 특성에 맞는 파라미터 최적화가 필수적이다.

## 출제 의도 및 답안 포인트

| 출제 의도 | 반드시 짚을 핵심 | 감점 회피 포인트 |
|:---|:---|:---|
| 동적 스케줄링 원리 및 트레이드오프 이해 | 다단계 큐 구조, 타임 퀀텀의 차등 분배, 피드백 메커니즘 | 멀티레벨 큐(MLQ)와 혼동 (피드백 누락) |
| 단일 스케줄러 한계 극복 기법 확인 | CPU/I/O 바운드 동적 판별, 기아(Starvation)와 에이징 | 단순히 "우선순위가 변한다"는 추상 표현 |
| MLFQ의 설계 한계와 극복 방안 제시 | 스케줄러 어뷰징(Gaming), CPU 낭비 통제 기법 | 알고리즘 동작 설명에서만 멈춤 |

> 요약: MLFQ는 단일 큐의 한계를 다중 큐와 피드백으로 극복한 가장 대표적인 범용 OS 스케줄러로, 성능과 공평성을 조율한다.

---

## Ⅰ. 개요 및 필요성

- 개요: 우선순위가 다른 여러 개의 큐를 두고, 프로세스의 과거 CPU 점유 특성에 따라 동적으로 큐 사이를 이동시키는 스케줄링 알고리즘
- 배경: 프로세스의 실행 시간(CPU Burst)을 사전에 알 수 없는 현실 시스템에서 SJF(Shortest Job First)를 근사하기 위한 방식 도입
- 필요성: 대화형 작업(응답성 중시)과 배치 작업(처리량 중시)이 혼재된 환경에서, 각 작업 특성에 맞는 타임 퀀텀 차등 적용 필수

---

## Ⅱ. 구조 및 구성요소

```text
       [새 프로세스 진입]
               |
[큐 0: 상위] (Q0) [ p1 ] -> 타임 퀀텀 q=10ms (응답성 위주)
               | (퀀텀 소진 시 강등)
[큐 1: 중위] (Q1) [ p2 ] -> 타임 퀀텀 q=20ms
               | (퀀텀 소진 시 강등)
[큐 2: 하위] (Q2) [ p3 ] -> 타임 퀀텀 q=40ms (처리량 위주/FCFS)
               |
       (주기적 승급: Aging)
```

| 구성요소 | 역할 | 특이사항 |
|:---|:---|:---|
| 다중 큐 (Multi-Queue) | 우선순위에 따라 분리된 여러 개의 Ready Queue | 하위 큐일수록 퀀텀 길게 설정 |
| 강등 룰 (Demotion) | 주어진 퀀텀을 모두 소진한 프로세스의 우선순위 하향 | CPU 바운드 식별 기법 |
| 승급 룰 (Aging) | 일정 시간 대기한 프로세스의 우선순위 일괄 상향 | 기아(Starvation) 방지 |
| 스케줄러 엔진 | 항상 가장 높은 우선순위 큐의 프로세스를 먼저 선택 | 선점형(Preemptive) 기반 |

> 요약: 우선순위와 퀀텀 크기가 반비례하는 다중 큐 구조를 통해 다양한 워크로드를 효과적으로 통제한다.

---

## Ⅲ. 동작원리 및 흐름도

```text
프로세스 Q0 진입 -> CPU 할당 및 실행
  -> [분기 1] I/O 발생 -> 양보 후 기존 큐(Q0) 유지
  -> [분기 2] 타임 퀀텀 만료 -> 강제 선점 후 하위 큐(Q1)로 강등
  -> [주기적] S 시간 경과 -> 모든 프로세스를 Q0로 승급(Aging)
```

- 1단계 [진입]: 새로운 작업은 가장 높은 우선순위 큐(Q0)에 배치되어 가장 짧은 응답 시간을 보장받음
- 2단계 [강등]: CPU 연산에 집중해 퀀텀을 모두 소진하면 스케줄러가 이를 CPU 바운드로 판단하여 한 단계 아래 큐로 강등함
- 3단계 [유지]: 퀀텀 내에 I/O를 요청하면 I/O 바운드로 판단, 현재 우선순위를 유지하여 빠른 상호작용 지원
- 4단계 [승급/Aging]: 하위 큐의 기아(Starvation)를 막기 위해 설정된 임계 시간(S)마다 모든 프로세스를 최상위 큐로 이동

> 요약: 스케줄러가 프로세스의 행동 이력을 피드백으로 삼아 I/O 바운드는 높이고 CPU 바운드는 낮추며 우선순위를 동적 조정한다.

---

## Ⅳ. 특징

- 반응성 보장: 새로 진입한 프로세스는 무조건 최상위 큐에서 즉시 실행되므로 SJF를 근사한 응답성을 제공
- 문맥 전환 오버헤드 통제: 하위 큐(CPU 바운드)는 타임 퀀텀을 길게 부여하여 불필요한 스위칭(Context Switching) 최소화
- 파라미터 복잡성: 큐의 개수, 각 큐의 타임 퀀텀, 에이징 주기 등 세부 튜닝 파라미터가 전체 시스템 성능을 좌우함

> 요약: MLFQ는 최적의 범용 스케줄러이지만, 파라미터 설정에 따라 시스템 성능이 민감하게 변동하는 트레이드오프를 가진다.

---

## Ⅴ. 심화 비교 및 적용 판단

| 비교 축 | MLQ (Multi-Level Queue) | MLFQ (Multi-Level Feedback Queue) | 선택 기준 |
|:---|:---|:---|:---|
| 큐 간 이동 | 불가능 (고정 할당) | 가능 (동적 피드백) | 작업 특성의 변동성 |
| 우선순위 갱신 | 정적 (생성 시 결정) | 동적 (실행 패턴 기반) | 유연성과 기아 방지 요구 수준 |
| 오버헤드 | 낮음 (단순 구조) | 높음 (상태 감시 및 이동) | 커널 자원 가용량 |

> 요약: 작업 특성이 변하지 않는 특수 목적 시스템은 MLQ를, 일반적인 사용자 환경은 MLFQ를 적용한다.

**리스크·대응 (기본은 불릿):**
- 스케줄러 어뷰징(Gaming): 프로세스가 퀀텀 만료 직전에 I/O를 호출하여 우선순위 강등을 회피 → 할당 시간이 아닌 '해당 큐에서의 총 누적 실행 시간'을 기준으로 강등 룰 변경
- CPU 코어 낭비: 멀티 코어 환경에서 단일 MLFQ 사용 시 락(Lock) 경합 발생 → 코어별 개별 런큐(Run-Queue) 구조로 분산 전환

**도입 후 점검 지표 (기본은 불릿):**
- 성능/효율: 대화형 작업의 95p 응답 지연(Response Time), 시스템 전체 스루풋(Throughput)
- 품질/운영: 하위 큐에서의 평균 대기 시간(Starvation 여부 확인)

---

## Ⅵ. 실무 적용 및 결론

**적용 방안 3개 (필수 — 단계별 또는 항목별):**
1. 파라미터 동적 튜닝: 시스템 부하(Load Average) 모니터링을 통해 평상시에는 퀀텀을 짧게, 부하 폭증 시에는 퀀텀을 늘려 오버헤드 방어
2. 에이징(Aging) 임계값 S 조절: 하위 큐의 대기 시간을 주기적으로 샘플링하여, 기아 현상 발생 시 S 값을 단축시켜 승급 주기 가속
3. 최상위 큐의 실시간성 보완: MLFQ 상위에 Soft Real-Time(미디어 스트리밍 등)을 위한 별도 고정 큐를 두어 지터(Jitter) 발생 억제

**결론 (2줄):**
- 기술사 판단: MLFQ는 범용 OS의 성능과 공평성을 조율하는 핵심 기법이나, 현대의 복잡한 워크로드에서는 세밀한 튜닝의 한계가 있다.
- 향후 방향: 이러한 파라미터 튜닝의 복잡성을 극복하기 위해, 리눅스는 가상 런타임 기반으로 수학적 공평성을 보장하는 CFS(Completely Fair Scheduler)로 발전하였다.
