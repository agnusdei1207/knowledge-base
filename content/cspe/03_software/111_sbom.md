## Ⅰ. 개요
- **정의**: SW 구성요소의 명칭, 버전, 라이선스, 의존관계를 기록한 목록임
- **배경/필요성**: 오픈소스 사용 비율 증가로 구성요소 식별 없이는 취약점 추적이 불가함
- **비유**: 식품의 원재료 성분표처럼 SW에 포함된 모든 재료를 나열한 명세서임

| 출제 의도 | 반드시 짚을 핵심 | 감점 회피 포인트 |
|:---|:---|:---|
| SW 투명성 확보 방법 이해 | 표준 포맷(SPDX, CycloneDX) 구분 | 단순 목록이 아닌 의존관계 포함 강조 |

> 요약: SW 구성요소의 식별·추적을 위한 공식 명세 체계임

## Ⅱ. 구성요소
```text
SBOM
 +-- Component Name ---- 패키지 식별자
 +-- Version ----------- 정확한 버전 번호
 +-- Supplier ---------- 공급자 정보
 +-- Dependency Graph --- 의존 관계 트리
 +-- License ----------- 라이선스 유형
```

| 구성요소 | 설명 | 비유 |
|:---|:---|:---|
| Component Name | 각 SW 패키지의 고유 식별자 | 부품 번호표 |
| Dependency Graph | 직접·간접 의존관계를 트리로 표현 | 가계도 |
| License | 각 구성요소의 사용 허가 조건 | 계약서 |

> 요약: 이름, 버전, 의존관계, 라이선스가 SBOM의 핵심 항목임

## Ⅲ. 절차
```text
SW 빌드 --> 의존성 스캔 --> SBOM 생성 --> 취약점 대조
```
- 1단계: SW 빌드 시점에 패키지 매니저 정보 수집
- 2단계: SCA 도구로 직접·전이 의존성 자동 스캔
- 3단계: SPDX/CycloneDX 포맷으로 SBOM 문서 생성
- 4단계: CVE 데이터베이스와 대조하여 취약 구성요소 식별

> 요약: 빌드-스캔-생성-대조 4단계로 SBOM을 운용함

## Ⅳ. 문제점
- 전이 의존성 누락: 간접 참조 라이브러리가 스캔에서 빠지면 취약점 사각지대 발생
- 포맷 비호환: SPDX와 CycloneDX 간 변환 시 정보 손실 가능
- 갱신 지연: 배포 후 새 CVE 발생 시 기존 SBOM이 실시간 반영 못함

> 요약: 누락, 비호환, 갱신 지연이 SBOM 운용의 주요 장애임

## Ⅴ. 개선방안
1. 단기: 전이 의존성까지 재귀 탐색하는 SCA 도구 도입
2. 중기: SPDX-CycloneDX 양방향 변환 파이프라인 구축
3. 장기: CI/CD에 SBOM 자동 갱신·CVE 모니터링 연동 체계 확립

> 요약: 스캔 깊이 확대, 포맷 통합, 자동 갱신으로 개선함

## Ⅵ. 전망
- 발전 방향: 정부 조달·규제에서 SBOM 제출 의무화 확대 추세임
- 기술사적 판단: SW 공급망 투명성의 기반 기술로 정착 중임
- 기술사 제언: SBOM 생성·관리를 DevSecOps 파이프라인에 내재화할 필요
