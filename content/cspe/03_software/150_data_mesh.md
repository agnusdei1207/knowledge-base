# 📖 【암기용】 개념 완전 이해

> 목적: 데이터 메시를 처음 보는 사람도 완벽히 이해하게 만든다. 시험 답안 양식이 아니라, 이해를 위한 친절한 설명이다.

## 한눈에
- **개요**: 데이터 메시는 중앙 데이터팀이 모든 데이터를 소유하는 구조에서 벗어나 도메인 조직이 데이터 제품을 책임지는 분산 데이터 운영 아키텍처임
- **왜 필요한가**: 중앙 DW/레이크 팀이 모든 요청을 처리하면 병목이 생기고 도메인 지식이 부족해 품질 책임이 흐려짐. 데이터 생산 조직이 제품 품질과 SLA를 책임하게 함.
- **핵심 직관**: 본사 물류센터가 모든 상품 설명서를 쓰는 대신 각 상품 담당 팀이 표준 양식에 맞춰 설명서와 품질 보증을 제공하는 방식임.

## 깊이 이해
- **배경·문제의식**: 데이터 규모와 소비자가 늘면 중앙 플랫폼팀만으로 모든 모델링·품질·문의 대응을 처리하기 어렵다. 도메인 지식은 원천 시스템 담당 조직에 있음.
- **작동 원리**: 도메인은 데이터 제품을 소유하고, 플랫폼팀은 셀프서비스 인프라를 제공하며, 연합 거버넌스가 표준·보안·상호운용 규칙을 정함.
- **비유**: 대형 쇼핑몰에서 각 브랜드가 자기 상품 페이지와 재고 정확도를 책임지고, 쇼핑몰은 결제·검색·배송 표준을 제공하는 구조임.
- **구체 예시**: 고객 도메인은 `customer_profile_product`를 SLA 99%, freshness 15분, owner, schema, 품질 규칙과 함께 catalog에 등록함.
- **흔한 오해·주의점**: 데이터 메시는 기술 제품명이 아님. 조직 책임, 데이터 제품 계약, 셀프서비스 플랫폼, 연합 거버넌스가 함께 필요함.

## 연결 개념
- 데이터 제품: 도메인이 소유하고 SLA와 품질 계약을 제공하는 데이터 단위
- 데이터 레이크하우스: 데이터 제품을 저장·공유하는 기술 기반
- 데이터 거버넌스: 분산 소유권을 표준과 정책으로 조정하는 체계

# 📝 【답안용】 시험 답안 템플릿

> 목적: 시험장에서 25분에 그대로 쓰는 답안 양식. 작성방식(추상표현 금지·수치·도식·문제유형 전환)을 엄격히 지킨다.
> 핵심: 데이터 메시 답안은 플랫폼 기술보다 도메인 소유권, 데이터 제품, 셀프서비스, 연합 거버넌스 4원칙을 중심으로 구성해야 한다.

## 핵심 인사이트 (3줄 요약)

> 1. **본질**: 데이터 메시는 데이터를 도메인 소유의 제품으로 관리하고 플랫폼은 셀프서비스 형태로 제공하는 분산 데이터 아키텍처이다.
> 2. **가치**: 중앙 데이터팀 병목을 줄이고 도메인 지식 기반 품질·SLA 책임을 명확히 한다.
> 3. **판단 포인트**: 조직 성숙도, 표준 계약, 카탈로그, 플랫폼 자동화, 연합 거버넌스가 없으면 데이터 사일로가 늘어난다.

## 출제 의도 및 답안 포인트

| 출제 의도 | 반드시 짚을 핵심 | 감점 회피 포인트 |
|:---|:---|:---|
| 데이터 메시 원칙 이해 | domain ownership, data as product, self-service, federated governance | 레이크하우스 기술로만 설명 |
| 조직·아키텍처 판단 | 도메인 팀 책임, 플랫폼팀 역할, 거버넌스 표준 | 분산 소유가 무통제로 변하는 리스크 누락 |
| 적용 방안 제시 | 데이터 제품 계약, SLA, catalog, quality metric | 조직 변화와 운영 지표 미기재 |

> 요약: 데이터 메시 문제는 기술보다 책임 구조와 데이터 제품 운영 계약을 중심으로 답안화해야 한다.

## Ⅰ. 개요 및 필요성

데이터 메시는 도메인 중심 분산 데이터 아키텍처이다. 중앙 데이터팀이 모든 데이터를 통합·정제하는 방식은 대규모 조직에서 병목과 품질 책임 공백을 만든다. 데이터 메시는 도메인이 데이터 제품을 소유하고 플랫폼이 공통 인프라를 제공하는 방식으로 해결한다.

---

## Ⅱ. 구조 및 구성요소

```text
Domain Team -> Data Product -> Catalog / Contract -> Consumer
           +-> Self-Service Platform
           +-> Federated Governance
```

| 구성요소 | 역할 | 특이사항 |
|:---|:---|:---|
| Domain Ownership | 원천 지식 기반 데이터 책임 | owner, SLA, 품질 지표 |
| Data Product | 소비 가능한 데이터 단위 | schema, contract, documentation |
| Self-Service Platform | 적재·품질·배포 자동화 | pipeline template, catalog |
| Federated Governance | 표준·보안·상호운용 규칙 | 정책 자동검사, audit |

> 요약: 데이터 메시는 도메인 팀의 책임과 플랫폼 자동화, 연합 거버넌스를 결합해 분산 데이터 운영을 수행한다.

---

## Ⅲ. 동작원리 및 흐름도

```text
도메인 데이터 식별 -> 데이터 제품 정의 -> 계약 / SLA 등록
-> 플랫폼 파이프라인 배포 -> 소비자 사용 -> 품질 / 비용 / 권한 점검
```

| 단계 | 처리 내용 | 검증 기준 |
|:---:|:---|:---|
| 1 | 도메인이 데이터 제품 후보와 소비자 요구 정의 | owner 지정률 100% |
| 2 | schema, SLA, freshness, 품질 규칙 계약화 | contract test 통과 |
| 3 | 셀프서비스 플랫폼으로 배포·모니터링 | 배포 lead time 1일 이하 |
| 4 | 연합 거버넌스가 표준·권한·비용 점검 | 정책 위반 0건 |

> 요약: 데이터 메시는 도메인이 제품 계약을 정의하고 플랫폼이 배포·관측을 자동화하며 거버넌스가 표준을 검증한다.

## Ⅳ. 특징

| 구분 | 중앙집중 데이터 플랫폼 | 데이터 메시 | 수치·판단 포인트 |
|:---|:---|:---|:---|
| 소유권 | 중앙 데이터팀 | 도메인 팀 | owner 지정률 100% |
| 제공 단위 | 테이블·리포트 | 데이터 제품 | SLA, freshness, contract |
| 플랫폼 | 요청 기반 개발 | 셀프서비스 배포 | lead time 1일 이하 |
| 통제 | 중앙 승인 | 연합 거버넌스 | 정책 자동검사 통과율 99% |

> 요약: 데이터 메시는 중앙 통제를 없애는 방식이 아니라 도메인 책임과 표준 자동검사를 결합한 운영 모델이다.

## Ⅴ. 심화 비교 및 적용 판단

| 비교 축 | 기존/대안 | 데이터 메시 | 선택 기준 |
|:---|:---|:---|:---|
| 구조 | 중앙 DW/레이크 팀 | 도메인별 데이터 제품 | 도메인 5개 이상, 요청 backlog 증가 |
| 비용/성능 | 중앙팀 병목 | 플랫폼 표준화로 반복 작업 축소 | 데이터 제품 배포 lead time 측정 |
| 운영/위험 | 품질 책임 중앙화 | 도메인별 책임 분산 | 거버넌스 자동화 없으면 사일로 증가 |

> 요약: 데이터 메시는 조직 규모와 도메인 복잡도가 커질 때 적합하며, 표준 플랫폼 없이 도입하면 분산 혼란이 발생한다.

| 리스크 | 원인 | 대응 방안 | 확인 지표 |
|:---|:---|:---|:---|
| 데이터 사일로 | 도메인별 표준 불일치 | 공통 contract, catalog 필수화 | catalog 등록률 95% 이상 |
| 품질 편차 | 도메인 역량 차이 | 품질 템플릿, enablement program | DQ rule 통과율 |
| 비용 증가 | 제품 중복 생성 | product review, FinOps tag | 중복 제품 수, 월 비용 |

> 요약: 데이터 메시 리스크는 분산 자체가 아니라 표준·카탈로그·비용 통제 미흡에서 발생한다.

| 점검 항목 | 목표 기준 | 측정 방법 |
|:---|:---|:---|
| 제품성 | owner, SLA, schema 등록률 100% | data catalog |
| 품질 | freshness 위반 1% 이하 | observability metric |
| 운영 | 배포 lead time 1일 이하 | platform pipeline log |

> 요약: 데이터 메시 성공 여부는 제품 계약 등록률, freshness 위반률, 배포 lead time으로 판단한다.

## Ⅵ. 실무 적용 및 결론

**적용 방안 3개 (필수 — 단계별 또는 항목별):**
1. 고객·주문·상품 등 5개 내외 핵심 도메인부터 data product owner, SLA, schema contract, freshness 15분~24시간 기준을 등록
2. 셀프서비스 플랫폼에 pipeline template, 품질 검사, catalog publish, 권한 신청을 자동화해 배포 lead time 1일 이하 목표 설정
3. 연합 거버넌스 위원회가 PII, 명명규칙, 품질 지표, FinOps tag를 정책 코드로 관리하고 월 1회 제품 중복 점검

**결론 (2줄):**
- 기술사 판단: 도메인 수와 데이터 요청 backlog가 큰 조직은 데이터 메시, 소규모 단일 분석 조직은 중앙 DW/레이크가 비용 대비 적합
- 향후 방향: 데이터 메시는 레이크하우스, 데이터 계약, 관측성, 정책 자동화와 결합해 제품 중심 데이터 운영 모델로 발전
