# 📖 【암기용】 개념 완전 이해

> 목적: 데이터 메시를 처음 보는 사람도 완벽히 이해하게 만든다. 시험 답안 양식이 아니라, 이해를 위한 친절한 설명이다.

## 한눈에
- **개요**: 데이터 메시는 중앙 데이터팀이 모든 데이터를 소유하던 구조에서 벗어나 **도메인 오너십·데이터 제품·셀프서비스 플랫폼·연합 거버넌스** 4원칙으로 데이터를 관리하는 **분산 데이터 아키텍처**다.
- **왜 필요한가**: 조직이 커지면 중앙 데이터팀 혼자 모든 도메인의 모델링·정제·문의 대응을 감당할 수 없어 요청 대기열(backlog)이 쌓이는데, 정작 도메인 지식은 원천 시스템을 운영하는 팀에 있다. 데이터 생산에 가장 가까운 조직이 품질을 책임지게 하는 것이 해법이다.
- **핵심 직관**: 본사가 모든 상품 설명서를 대신 쓰는 대신, 각 브랜드 담당팀이 표준 양식에 맞춰 자기 상품 정보와 품질을 직접 책임지는 구조다.

## 핵심 용어 정리 (내부에 등장하는 것들)

| 용어 | 의미 | 비유 |
|:---|:---|:---|
| 분산 데이터 아키텍처 | 데이터 메시가 속하는 상위 개념 — 소유권과 처리를 여러 조직 단위로 나누는 구조 | 중앙집중 본사 vs 지사 분산 운영 |
| 도메인 오너십(Domain Ownership) | 원천을 가장 잘 아는 도메인 팀이 데이터 소유·품질 책임을 짐 | 상품팀이 직접 상품 정보를 책임 |
| 데이터 제품(Data as a Product) | 데이터셋을 API 제품처럼 문서·스키마·SLA·품질 계약과 함께 제공 | 사용설명서 딸린 완제품 |
| 셀프서비스 데이터 플랫폼 | 도메인팀이 인프라 전문지식 없이 파이프라인·카탈로그 등록을 스스로 할 수 있는 공통 플랫폼 | 클라우드 콘솔의 셀프 프로비저닝 |
| 연합 거버넌스(Federated Computational Governance) | 표준·보안 규칙은 정책-as-코드로 자동 강제하되, 표준을 정하는 의사결정은 도메인 대표 위원회가 함 | 지사는 자율 운영, 공통 규정은 본사가 감사 |
| 데이터 계약(Data Contract) | 제공자·소비자 간 스키마·SLA·품질 기준을 문서·코드로 합의한 것 | API 명세서 |
| 데이터 사일로 | 표준 없이 도메인이 각자 흩어져 서로 재사용 못 하는 안티패턴 상태 | 부서 이기주의로 정보 단절 |

## 깊이 이해

### 배경 — 중앙 데이터팀이 병목이 되는 이유
- 2019년 Zhamak Dehghani가 처음 제안한 개념이다. 조직이 커질수록 소비자(분석가·ML팀·타 도메인)가 늘어나는데, 모델링에 필요한 업무 지식은 원천 시스템을 운영하는 도메인 팀에 있다. 중앙 데이터팀이 모든 도메인 지식을 대신 배워 파이프라인을 만들면 도메인 하나가 추가될 때마다 병목이 커진다.

### 4원칙을 구체적으로 이해하기
- **도메인 오너십**: 예) 고객 데이터는 CRM을 운영하는 고객팀이, 주문 데이터는 주문 시스템 팀이 정제·품질까지 책임진다.
- **데이터 제품**: 단순 테이블이 아니라 스키마, freshness(신선도), SLA, owner, 사용 예제 문서를 갖춘 소비 가능한 단위다. Zhamak은 데이터 제품이 갖춰야 할 특성으로 검색 가능(discoverable)·주소 지정 가능(addressable)·신뢰 가능(trustworthy)·자기 서술적(self-describing)·상호운용 가능(interoperable)·안전(secure)함을 든다.
- **셀프서비스 플랫폼**: 도메인팀이 파이프라인 배포·카탈로그 등록·권한 신청을 표준 템플릿으로 스스로 처리한다. 플랫폼팀은 각 도메인을 대신 코딩하지 않고 도구만 제공한다.
- **연합 거버넌스**: PII 마스킹, 명명 규칙 같은 공통 표준은 정책 코드로 자동 검사(위반 시 배포 차단)하고, 표준 자체를 정하는 결정은 도메인 대표 위원회가 내린다 — 완전 자율도, 완전 중앙통제도 아닌 절충이다.

### 수치로 보는 데이터 제품 계약 예시
- 고객 도메인이 `customer_profile_product`라는 데이터 제품을 등록할 때: SLA 가용성 99%, freshness 15분 이내, owner 지정, 스키마·품질 규칙(예: null 비율 1% 이하)을 명시한다. 이 계약이 없으면 소비자는 이 데이터를 믿고 쓸 수 없다.

### 언제 데이터 메시가 필요한가 (판별원리)
- 도메인이 5개 이상이고 중앙팀 요청 backlog가 계속 늘고 있다면 데이터 메시 후보다. 반대로 도메인 1~2개짜리 소규모 조직에서 도입하면 셀프서비스 플랫폼과 거버넌스 위원회를 유지하는 비용이 더 커서 오히려 손해다.

### 비유와 흔한 오해
- **비유**: 대형 쇼핑몰에서 각 브랜드가 자기 상품 페이지와 재고 정확도를 책임지고, 쇼핑몰 운영사는 결제·검색·배송이라는 공통 인프라만 제공하는 구조다.
- **오해**: 데이터 메시는 특정 제품이나 기술 스택 이름이 아니다. 카탈로그 도구 하나 도입한다고 되는 게 아니라 조직 책임 구조 자체를 바꾸는 조직 변화(organizational change)다. 4원칙 중 하나라도 빠지면(예: 거버넌스 없는 완전 자율 분산) 데이터 사일로로 전락한다.

## 연결 개념
- 데이터 제품: 도메인이 소유하고 SLA·품질 계약을 제공하는 데이터 단위
- 데이터 패브릭: 메타데이터 자동화로 데이터 메시의 셀프서비스 플랫폼을 기술적으로 뒷받침하는 보완 개념
- 데이터 거버넌스: 분산 소유권을 표준·정책으로 조정하는 상위 체계

# 📝 【답안용】 시험 답안 템플릿

> 목적: 시험장에서 25분에 그대로 쓰는 답안 양식. 작성방식(추상표현 금지·수치·도식·문제유형 전환)을 엄격히 지킨다.
> 핵심: 데이터 메시 답안은 플랫폼 기술보다 도메인 소유권, 데이터 제품, 셀프서비스, 연합 거버넌스 4원칙을 중심으로 구성해야 한다.

## 핵심 인사이트 (3줄 요약)

> 1. **본질**: 데이터 메시는 데이터를 도메인 소유의 제품으로 관리하고 플랫폼은 셀프서비스 형태로 제공하는 분산 데이터 아키텍처이다.
> 2. **가치**: 중앙 데이터팀 병목을 줄이고 도메인 지식 기반 품질·SLA 책임을 명확히 한다.
> 3. **판단 포인트**: 조직 성숙도, 표준 계약, 카탈로그, 플랫폼 자동화, 연합 거버넌스가 없으면 데이터 사일로가 늘어난다.

## 출제 의도 및 답안 포인트

| 출제 의도 | 반드시 짚을 핵심 | 감점 회피 포인트 |
|:---|:---|:---|
| 데이터 메시 원칙 이해 | domain ownership, data as product, self-service, federated governance | 레이크하우스 기술로만 설명 |
| 조직·아키텍처 판단 | 도메인 팀 책임, 플랫폼팀 역할, 거버넌스 표준 | 분산 소유가 무통제로 변하는 리스크 누락 |
| 적용 방안 제시 | 데이터 제품 계약, SLA, catalog, quality metric | 조직 변화와 운영 지표 미기재 |

> 요약: 데이터 메시 문제는 기술보다 책임 구조와 데이터 제품 운영 계약을 중심으로 답안화해야 한다.

## Ⅰ. 개요 및 필요성

- 개요: 데이터 메시는 도메인 중심 분산 데이터 아키텍처이다.
- 배경: 중앙 데이터팀이 모든 데이터를 통합·정제하는 방식은 대규모 조직에서 병목과 품질 책임 공백을 만든다.
- 필요성: 도메인 소유 데이터 제품과 셀프서비스 플랫폼으로 소유권, 품질 기준, 공통 인프라를 분리한다.

---

## Ⅱ. 구조 및 구성요소

```text
Domain Team -> Data Product -> Catalog / Contract -> Consumer
           +-> Self-Service Platform
           +-> Federated Governance
```

| 구성요소 | 역할 | 특이사항 |
|:---|:---|:---|
| Domain Ownership | 원천 지식 기반 데이터 책임 | owner, SLA, 품질 지표 |
| Data Product | 소비 가능한 데이터 단위 | schema, contract, documentation |
| Self-Service Platform | 적재·품질·배포 자동화 | pipeline template, catalog |
| Federated Governance | 표준·보안·상호운용 규칙 | 정책 자동검사, audit |

> 요약: 데이터 메시는 도메인 팀의 책임과 플랫폼 자동화, 연합 거버넌스를 결합해 분산 데이터 운영을 수행한다.

---

## Ⅲ. 동작원리 및 흐름도

```text
도메인 데이터 식별 -> 데이터 제품 정의 -> 계약 / SLA 등록
-> 플랫폼 파이프라인 배포 -> 소비자 사용 -> 품질 / 비용 / 권한 점검
```

| 단계 | 처리 내용 | 검증 기준 |
|:---:|:---|:---|
| 1 | 도메인이 데이터 제품 후보와 소비자 요구 정의 | owner 지정률 100% |
| 2 | schema, SLA, freshness, 품질 규칙 계약화 | contract test 통과 |
| 3 | 셀프서비스 플랫폼으로 배포·모니터링 | 배포 lead time 1일 이하 |
| 4 | 연합 거버넌스가 표준·권한·비용 점검 | 정책 위반 0건 |

> 요약: 데이터 메시는 도메인이 제품 계약을 정의하고 플랫폼이 배포·관측을 자동화하며 거버넌스가 표준을 검증한다.

## Ⅴ. 심화 비교 및 적용 판단

| 비교 축 | 기존/대안 | 데이터 메시 | 선택 기준 |
|:---|:---|:---|:---|
| 구조 | 중앙 DW/레이크 팀 | 도메인별 데이터 제품 | 도메인 5개 이상, 요청 backlog 증가 |
| 비용/성능 | 중앙팀 병목 | 플랫폼 표준화로 반복 작업 축소 | 데이터 제품 배포 lead time 측정 |
| 운영/위험 | 품질 책임 중앙화 | 도메인별 책임 분산 | 거버넌스 자동화 없으면 사일로 증가 |

> 요약: 데이터 메시는 조직 규모와 도메인 복잡도가 커질 때 적합하며, 표준 플랫폼 없이 도입하면 분산 혼란이 발생한다.

| 리스크 | 원인 | 대응 방안 | 확인 지표 |
|:---|:---|:---|:---|
| 데이터 사일로 | 도메인별 표준 불일치 | 공통 contract, catalog 필수화 | catalog 등록률 95% 이상 |
| 품질 편차 | 도메인 역량 차이 | 품질 템플릿, enablement program | DQ rule 통과율 |
| 비용 증가 | 제품 중복 생성 | product review, FinOps tag | 중복 제품 수, 월 비용 |

> 요약: 데이터 메시 리스크는 분산 자체가 아니라 표준·카탈로그·비용 통제 미흡에서 발생한다.

| 점검 항목 | 목표 기준 | 측정 방법 |
|:---|:---|:---|
| 제품성 | owner, SLA, schema 등록률 100% | data catalog |
| 품질 | freshness 위반 1% 이하 | observability metric |
| 운영 | 배포 lead time 1일 이하 | platform pipeline log |

> 요약: 데이터 메시 성공 여부는 제품 계약 등록률, freshness 위반률, 배포 lead time으로 판단한다.

## Ⅵ. 실무 적용 및 결론

**적용 방안 3개 (필수 — 단계별 또는 항목별):**
1. 고객·주문·상품 등 5개 내외 핵심 도메인부터 data product owner, SLA, schema contract, freshness 15분~24시간 기준을 등록
2. 셀프서비스 플랫폼에 pipeline template, 품질 검사, catalog publish, 권한 신청을 자동화해 배포 lead time 1일 이하 목표 설정
3. 연합 거버넌스 위원회가 PII, 명명규칙, 품질 지표, FinOps tag를 정책 코드로 관리하고 월 1회 제품 중복 점검

**결론 (2줄):**
- 기술사 판단: 도메인 수와 데이터 요청 backlog가 큰 조직은 데이터 메시, 소규모 단일 분석 조직은 중앙 DW/레이크가 비용 대비 적합
- 향후 방향: 데이터 메시는 레이크하우스, 데이터 계약, 관측성, 정책 자동화와 결합해 제품 중심 데이터 운영 모델로 발전
