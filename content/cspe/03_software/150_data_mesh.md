# 📖 【암기용】 개념 완전 이해

## 한눈에
- **개요**: 중앙 집중식 데이터 관리(데이터 팀이 모든 걸 처리)의 병목을 해결하기 위해, 각 도메인(부서)이 자신의 데이터를 직접 소유하고 '하나의 제품(Data as a Product)'으로 서비스하는 분산형 데이터 아키텍처 사상이다.
- **왜 필요한가**: 데이터 팀 한 곳에 전사의 데이터 요청이 몰리니 파이프라인 구축이 수개월씩 밀리고, 데이터 팀은 현업의 비즈니스 맥락을 몰라 엉뚱한 데이터를 만들게 된다.
- **핵심 직관**: 거대한 중앙 주방(데이터 팀)에서 모든 요리를 하느라 주문이 밀리는 식당을, 여러 개의 전문 식당(도메인: 일식, 중식, 양식)들이 모인 '푸드코트(메시)'로 바꾸는 것이다. 각 식당은 자신의 요리(데이터 제품)를 알아서 만들고 책임지며 손님에게 제공한다.

## 핵심 용어 정리

| 용어/표기 | 의미 | 비유·예 |
|:---|:---|:---|
| 데이터 메시 (Data Mesh) | 도메인 주도의 분산형 데이터 아키텍처 패러다임 | 자율적인 푸드코트 시스템 |
| 도메인 주도 소유권 (Domain Ownership) | 데이터를 생산하는 현업 부서가 데이터의 소유와 관리까지 책임지는 것 | 주방장이 자기 요리를 책임짐 |
| 데이터 제품 (Data as a Product) | 데이터를 단순히 쌓아두는 게 아니라, 다른 부서가 쓰기 편하게 만든 '상품' | 예쁘게 포장된 밀키트 |
| 연합 거버넌스 (Federated Governance) | 분산된 환경에서 표준, 보안, 상호운용성을 맞추기 위한 전사적 규칙 | 푸드코트 위생 검사 및 결제 표준 |
| 셀프서비스 인프라 플랫폼 | 도메인 팀이 직접 데이터를 가공할 수 있게 중앙에서 제공하는 인프라/툴 | 주방 설비 대여 서비스 |

## 깊이 이해
- **배경·문제의식**: 기존 데이터 웨어하우스나 데이터 레이크는 아키텍처는 훌륭했지만 '사람과 조직'이 병목이었다. 소수 정예의 중앙 데이터 엔지니어링 팀은 회사의 모든 비즈니스 로직(마케팅, 재무, 물류)을 이해할 수 없어 품질 낮은 데이터를 양산하고 속도가 느려졌다.
- **작동 원리 (Zhamak Dehghani의 4대 원칙)**:
  1. 도메인 지향 데이터 소유: 마케팅 부서는 '캠페인 데이터' 파이프라인을 직접 만든다.
  2. 데이터 제품 (Data as a Product): 마케팅 부서는 이 데이터를 다른 팀이 바로 쓸 수 있도록 설명서(API/카탈로그)와 함께 SLA(신뢰도)를 보장하여 배포한다.
  3. 셀프서비스 인프라: 마케팅 부서에 엔지니어가 없어도 파이프라인을 짤 수 있게, 중앙 인프라 팀이 쓰기 쉬운 플랫폼을 제공한다.
  4. 연합 거버넌스: 각자 데이터를 만들더라도, 회사 전체의 보안 규칙(GDPR 등)과 메타데이터 표준은 통일한다.
- **비유**: 과거 모놀리식(Monolithic) 백엔드를 마이크로서비스(MSA)로 쪼갰던 것과 똑같다. **데이터 파이프라인의 MSA 버전**이 바로 데이터 메시다.
- **흔한 오해·주의점**: 데이터 메시는 Spark나 Snowflake 같은 '새로운 소프트웨어 기술'이 아니다. 조직의 일하는 방식과 권한을 분산시키는 **사회-기술적(Socio-technical) 패러다임 전환**이다. (Data Fabric이 기술적 접근이라면, Data Mesh는 조직적 접근이다.)

## 연결 개념
- 마이크로서비스 아키텍처 (MSA) — 데이터 메시 사상의 소프트웨어 아키텍처 버전
- 데이터 패브릭 (Data Fabric) — AI를 활용해 데이터를 중앙에서 엮어주는 기술적 접근 (메시와 종종 비교됨)
- 데이터 레이크하우스 — 데이터 메시의 '도메인'들이 개별적으로 구축할 수 있는 물리적 인프라

# 📝 【답안용】 시험 답안 템플릿

## 핵심 인사이트 (3줄 요약)

> 1. **본질**: 중앙 집중식 데이터 아키텍처의 조직적 병목을 해결하기 위해 제안된 도메인 주도의 탈중앙화(Decentralized) 데이터 아키텍처 및 조직 패러다임이다.
> 2. **가치**: 데이터를 생산하는 현업 도메인이 직접 데이터를 소유 및 제공(Data as a Product)하게 하여, 비즈니스 민첩성을 높이고 데이터 엔지니어링 팀의 병목 현상을 해소한다.
> 3. **판단 포인트**: 특정 벤더의 기술 솔루션이 아니라 조직의 역할, 책임, 거버넌스를 재정의하는 '사회-기술적(Socio-technical)' 접근법이라는 점을 강조해야 한다.

## 출제 의도 및 답안 포인트

| 출제 의도 | 반드시 짚을 핵심 | 감점 회피 포인트 |
|:---|:---|:---|
| 최신 분산 데이터 패러다임과 4대 핵심 원칙 이해 | 도메인 소유권, 데이터 제품, 셀프서비스 인프라, 연합 거버넌스 | 솔루션 도입(기술)으로만 설명하는 오류, Data Fabric과의 혼동 |

> 요약: 기술 아키텍처 이전에 모놀리식 조직의 한계를 지적하고, Data as a Product 사상을 통한 분산형 소유권 이관을 명확히 서술해야 한다.

## Ⅰ. 개요 및 필요성

- 개요: 데이터 메시(Data Mesh)는 데이터를 도메인별로 분산 소유하고 서비스(Data as a Product)로 제공하는 분산형 데이터 아키텍처 및 조직 패러다임이다.
- 배경: 기존 중앙 집중식 Data Lake/DW 환경에서는 비즈니스 맥락이 결여된 중앙 데이터 팀에 모든 파이프라인 요구사항이 집중되어 심각한 처리 병목 발생
- 필요성: 모놀리식 소프트웨어가 MSA로 진화했듯, 데이터 파이프라인도 도메인 지향적으로 분산하여 비즈니스 변화에 민첩하게 대응할 체계 필수

---

## Ⅱ. 구조 및 구성요소 (4대 핵심 원칙)

```text
[ 연합 거버넌스 (전사 표준 규약 및 보안) ]
   ---------------------------------
[ 도메인 A (결제) ]     [ 도메인 B (배송) ]     <-- 데이터 제품 (Data as a Product)
(직접 파이프라인 관리)  (직접 파이프라인 관리)  <-- 도메인 지향 소유권
   ---------------------------------
[ 셀프 서비스 데이터 인프라 플랫폼 (중앙 인프라 팀 제공) ]
```

| 4대 원칙 (구성요소) | 내용 및 역할 | 특이사항 |
|:---|:---|:---|
| 도메인 지향 소유권 | 데이터를 생성/소비하는 팀이 파이프라인과 품질을 직접 책임짐 | 병목 해소 |
| 데이터 제품 | 분석 가능한 품질의 데이터를 API나 테이블로 타 도메인에 서비스 | SLA 및 신뢰성 보장 |
| 셀프서비스 인프라 | 도메인 팀이 쉽게 데이터를 처리할 수 있도록 추상화된 플랫폼 제공 | 중앙 인프라 팀 담당 |
| 연합 거버넌스 | 상호 운용성을 위한 표준(포맷, 보안 등)을 중앙과 도메인이 합의 | 사일로(Silo) 방지 |

> 요약: 각 도메인이 셀프서비스 인프라 위에서 규칙(거버넌스)을 지키며 자신의 데이터 제품을 찍어내는 탈중앙화 구조다.

---

## Ⅲ. 동작원리 및 흐름도

```text
도메인 인프라 확보 -> 데이터 수집 및 정제 -> 데이터 제품 릴리스 -> 연합 데이터 탐색 및 활용
```

- 1단계 [인프라 확보]: A 도메인(결제팀)이 셀프서비스 플랫폼을 통해 저장소와 컴퓨팅 자원을 버튼 클릭으로 프로비저닝함
- 2단계 [가공 및 제품화]: 결제팀 내부의 비즈니스 지식을 활용해 원천 데이터를 정제하고 '일별 결제 요약 데이터'를 생성함
- 3단계 [제품 릴리스]: 생성된 데이터를 전사 데이터 카탈로그에 '데이터 제품'으로 등록하고 SLA(가동률, 지연시간)를 명시함
- 4단계 [탐색 및 활용]: B 도메인(마케팅팀)이 카탈로그에서 결제 데이터를 검색 후 권한을 인가받아 자사 마케팅 데이터와 조인하여 분석

> 요약: 중앙 팀의 개입 없이, 생산자와 소비자가 카탈로그와 표준 API를 매개로 직접 데이터를 교환한다.

---

## Ⅳ. 특징
- 사회-기술적(Socio-technical) 접근: 기술 솔루션 도입을 넘어 도메인 팀에 '데이터 프로덕트 오너(DPO)' 역할을 부여하는 조직 문화 혁신
- 비즈니스 민첩성 향상: 중앙 엔지니어링 팀의 작업 큐를 기다릴 필요 없이, 현업 부서가 필요 시 즉각적으로 파이프라인을 신설·수정
- 상호 운용성(Interoperability): 고립된 사일로가 되지 않도록 연합 거버넌스를 통해 데이터 식별자 및 포맷(표준) 강제
- MSA와의 완벽한 정렬: 애플리케이션 레벨의 마이크로서비스 팀이 분석용 데이터 제품까지 End-to-End로 책임지는 구조 완성

> 요약: 메시는 물리적 중앙화(레이크)의 한계를 논리적/조직적 분산(도메인)으로 풀어내어 전사 데이터 확장성을 높인다.

---

## Ⅴ. 심화 비교 및 적용 판단

| 비교 축 | 데이터 패브릭 (Data Fabric) | 데이터 메시 (Data Mesh) | 선택 기준 |
|:---|:---|:---|:---|
| 접근 방식 | 기술 중심 (AI/ML 기반 메타데이터 자동 연결) | 조직/아키텍처 중심 (도메인 주도 소유권 분산) | 해결하려는 문제의 근원 |
| 중앙화 여부 | 중앙 관리형 플랫폼 지향 | 탈중앙화, 도메인 단위 분산 지향 | 조직의 자율성 수준 |
| 핵심 동인 | 이기종 소스의 물리적 위치 은닉 및 자동 통합 | 중앙 데이터 팀의 사람/프로세스 병목 해소 | 툴 자동화 vs 구조 개편 |

> 요약: 기술(AI)로 사일로를 엮으려면 패브릭을, 조직 구조와 권한을 쪼개어 파이프라인 병목을 없애려면 메시를 선택한다.

**리스크·대응 (기본 불릿):**
- 현업 팀 역량 부족: 도메인 팀이 파이프라인을 구축할 인력 부족 → SQL 기반의 초직관적인 추상화 플랫폼(dbt 등) 제공 (지표: 인력 확보율)
- 데이터 사일로화 및 중복: 도메인이 비슷한 데이터를 중복 생성 → 연합 거버넌스를 통해 중복 통제 및 카탈로그 검색 활성화 (지표: 카탈로그 등록률)
- 거버넌스 통제 상실: 보안 및 규정(GDPR) 준수 불량 → 플랫폼 레벨에서 암호화, 접근 제어 등 보안 정책을 코드로 강제 (지표: 보안 정책 위반 수)

**도입 후 점검 지표 (기본 불릿):**
- 성능/효율: 데이터 요구사항 발생 시점부터 데이터 제품 배포(Time to Market)까지 걸리는 리드 타임 — 생산성 지표
- 품질/운영: 도메인이 선언한 데이터 제품의 SLA(데이터 최신성, 스키마 정확도) 준수율 달성도 — 품질 모니터링

---

## Ⅵ. 실무 적용 및 결론

**적용 방안 3개:**
1. 크로스 펑셔널 도메인 팀 구성: 기존 앱 개발자와 기획자만 있던 스쿼드(Squad)에 데이터 엔지니어를 배치하여 자체 데이터 생산 역량 확보
2. 전사 통합 데이터 카탈로그 포털 구축: 생산된 모든 도메인의 데이터 제품을 쇼핑몰처럼 검색하고 접근 권한 요청을 할 수 있는 포털 운영
3. 데이터 계약(Data Contract) 체결: 데이터 생산자와 소비자 간에 스키마 변경, SLA 유지에 대한 서면 계약(API 명세서 유사)을 도입하여 파이프라인 단절 방지

**결론:**
- 기술사 판단: 중앙 데이터 팀이 비즈니스 요구를 감당하지 못하는 티핑 포인트에 도달했을 때, 조직 구조 개편을 동반한 데이터 메시로의 전환을 결단해야 한다.
- 향후 방향: 데이터 패브릭과 데이터 메시는 상호 배타적이지 않으며, 데이터 메시 조직 환경 위에서 메타데이터를 자동화하는 데이터 패브릭 기술이 융합된 형태로 발전할 것이다.
