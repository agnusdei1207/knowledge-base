# 📖 【암기용】 개념 완전 이해

> 목적: 이 개념을 처음 보는 사람도 완벽히 이해하게 만든다. 시험 답안 양식이 아니라, 이해를 위한 친절한 설명이다.

## 한눈에
- **개요**: **아키텍처 패턴**은 소프트웨어 설계에서 반복적으로 나타나는 문제(컴포넌트를 어떻게 나누고 어떻게 통신시킬 것인가)에 대해, 검증된 구조와 상호작용 규칙을 제시하는 재사용 가능한 해법이다. 핵심은 **결합도(Coupling)는 낮추고 응집도(Cohesion)는 높이는 관심사 분리(Separation of Concerns)**다.
- **왜 필요한가**: 정형화된 구조 없이 코드를 쌓으면 화면 로직과 데이터 접근 코드가 한 클래스에 뒤섞여, 화면 하나를 고치다가 DB 연결 코드까지 건드리는 강한 결합(Tight Coupling)이 발생한다. 아키텍처 패턴은 "이 책임은 반드시 이 위치에만 둔다"는 규칙을 강제해 변경의 파급 범위(Ripple Effect)를 국소화한다.
- **핵심 직관**: 패턴마다 관심사를 자르는 축이 다르다. Layered·MVC는 **정적인 책임(역할)**을 기준으로 자르고, Pipe-Filter·Event-Driven은 **동적인 데이터 흐름**을 기준으로 자른다.

## 핵심 용어 정리 (내부에 등장하는 것들)

| 용어 | 의미 | 비유 |
|:---|:---|:---|
| 아키텍처 패턴 | 반복되는 설계 문제에 대한 재사용 가능한 구조 + 상호작용 규칙 | 건축의 표준 도면 |
| 결합도 (Coupling) | 모듈 간 의존이 강한 정도 — 낮을수록 한쪽 변경이 다른 쪽에 덜 번짐 | 나사 연결(약함) vs 용접(강함) |
| 응집도 (Cohesion) | 한 모듈 내부 책임이 서로 얼마나 밀접한가 — 높을수록 좋음 | 관련 물건만 한 서랍에 모아둠 |
| 관심사 분리 (SoC) | 서로 다른 종류의 책임(화면·로직·데이터)을 물리적으로 분리하는 원칙 | 부엌·거실·침실을 벽으로 나눔 |
| Layered (계층형) | 프레젠테이션 → 비즈니스 → 데이터 접근을 상하로 쌓고, 상위 계층이 바로 아래 계층만 호출 | 아파트 층간 이동은 계단으로만 |
| MVC | Model(데이터)·View(화면)·Controller(제어)로 3분할, Controller가 중재 | 식당의 손님-웨이터-주방 |
| Pipe-Filter | 독립된 필터(Filter)들을 파이프(Pipe)로 연결해 데이터를 순차 가공 | 정수기의 단계별 필터 |
| Event-Driven (이벤트 기반) | 발행자(Publisher)와 구독자(Subscriber)가 이벤트 버스를 통해 비동기로 소통 | 게시판에 공지를 붙이면 구독자가 알아서 확인 |
| Sinkhole 안티패턴 | 계층을 그냥 통과만 시키는 무의미한 호출이 누적되는 현상 | 내용물 없이 전달만 하는 배달원 여러 명 |
| Fat Controller | MVC에서 Controller에 로직이 과도하게 쌓여 비대해지는 현상 | 웨이터가 주방 일까지 다 떠맡음 |

## 깊이 이해

### Layered 패턴 — 의존 방향 규칙과 위반 비용을 수치로 보기
- 구조: 프레젠테이션(Controller) → 비즈니스(Service) → 데이터 접근(Repository)으로 쌓고, **상위 계층은 바로 아래 계층만 호출**한다(계층 건너뛰기 금지). Spring Boot의 `Controller → Service → Repository`가 이 구조다.
- **규칙 준수 시**: DB 스키마가 바뀌어도 그 영향은 Repository 1개와 그것을 감싸는 Service 1개까지만 미친다.
- **규칙 위반 시(수치 예)**: Controller 3개가 규칙을 어기고 Repository를 직접 호출한다고 하면, 같은 스키마 변경이 발생했을 때 수정해야 할 파일이 Service 1개가 아니라 Controller 3개 + Service 1개 = 4개로 늘어난다. 계층이 많아질수록(예: 5계층) 위반 1건이 유발하는 수정 범위는 계층 수만큼 배가된다.

### MVC — 통신 경로와 책임 분리
- 구조: 사용자가 View에 입력하면 Controller가 요청을 받아 Model을 갱신·조회하고, 그 결과를 다시 View에 반영한다. **View는 Model을 직접 수정하지 않고 반드시 Controller를 거친다.**
- 프론트엔드(View: React/Vue)와 백엔드(Model+Controller)를 물리적으로 분리하는 현대 웹 구조의 근간이 이 3분할이다.

### Pipe-Filter — 단계별 독립 가공
- 구조: 필터마다 입력을 받아 변환한 뒤 다음 파이프로 넘긴다. 필터는 서로의 내부를 모른 채 입출력 형식만 맞으면 된다.
- 예: `cat file.txt | grep "error" | wc -l`은 파일 읽기 → 패턴 필터링 → 개수 세기의 3단계 필터가 파이프로 연결된 것이다. 필터 하나(`grep`)만 다른 명령으로 교체해도 나머지는 그대로 동작한다 — 필터 간 결합이 없다는 뜻이다.
- 단, 필터는 상태를 공유하지 않는 것이 원칙이라 여러 요청에 걸친 문맥(세션 등)을 다루기는 어렵다.

### Event-Driven — 동기 체인 vs 비동기 발행의 지연 시간 비교
- **동기(Sync) 체인**: 주문 100ms → 결제 150ms → 포인트 적립 200ms → 메일 발송 300ms를 순서대로 호출하면 사용자는 응답까지 100+150+200+300 = **750ms**를 기다리고, 메일 서버가 멈추면 전체 요청이 실패(롤백)한다.
- **비동기(Async) 발행**: 주문(100ms)과 결제(150ms)까지만 동기로 처리해 250ms만에 "주문 완료" 응답을 반환하고, "포인트 적립"·"메일 발송"은 이벤트로 큐(Kafka)에 발행한 뒤 별도 구독자가 처리한다. 메일 서버가 멈춰도 주문·결제 성공률에는 영향이 없고, 서버 복구 후 큐에 쌓인 이벤트를 재처리하면 된다.
- 이처럼 발행자와 구독자가 서로의 존재를 몰라도 되는 **느슨한 결합**이 Event-Driven의 본질이며, 장애 격리(Fault Isolation)가 핵심 가치다.

### 판별 원리 — 언제 무엇을 쓰는가
- 화면·로직·데이터처럼 **정적 책임**을 나눌 때는 Layered·MVC를 쓴다.
- 데이터가 여러 단계의 **순차 변환**을 거칠 때(파싱→검증→압축 등)는 Pipe-Filter를 쓴다.
- 서비스 간 **느슨한 결합과 장애 격리**가 필요할 때(대량 트래픽, MSA 서비스 간 통신)는 Event-Driven을 쓴다.

### 비유와 흔한 오해
- **비유**: 정수기 필터(Pipe-Filter)에 쇼핑몰 주문 로직을 태우거나, 영상 처리 파이프라인을 MVC로 짜면 구조가 맞지 않아 코드가 뒤엉킨다. 데이터가 흐르는 방식에 맞춰 뼈대를 골라야 한다.
- **오해**: "Spring Boot를 쓰면 자동으로 Layered 패턴이다" — 사실이 아니다. Controller 안에서 SQL을 직접 짜면 그 순간 계층 규칙이 깨진 것이다. 패턴은 프레임워크가 부여하는 것이 아니라 개발자가 의존 방향 규칙을 지켜야 완성된다.

## 연결 개념
- **마이크로서비스 아키텍처 (MSA, 042)**: 이 패턴들이 단일 프로세스 내부의 관심사 분리라면, MSA는 프로세스 자체를 서비스 단위로 분리하는 상위 아키텍처다.
- **GoF 디자인 패턴**: 아키텍처 패턴이 시스템 전체의 구조(숲)를 다룬다면, 디자인 패턴(싱글톤, 팩토리 등)은 클래스 2~3개 사이의 관계(나무)를 다룬다.

# 📝 【답안용】 시험 답안 템플릿

> 목적: 시험장에서 25분에 그대로 쓰는 답안 양식. 작성방식(추상표현 금지·수치·도식·문제유형 전환)을 엄격히 지킨다.
> 핵심: 이 시험은 정보를 많이 나열하는 시험이 아니라, 문제 신호어에서 출제자 의도를 읽고 핵심 논점을 선별해 쓰는 시험이다.

## 핵심 인사이트 (3줄 요약)

> 1. **본질**: 소프트웨어 시스템의 복잡성을 제어하기 위해, 서브시스템 간의 역할(Role)과 책임(Responsibility), 그리고 데이터 흐름을 규격화한 최적의 아키텍처 설계 템플릿(족보)이다.
> 2. **가치**: 모듈 간의 결합도(Coupling)를 느슨하게(Loose) 풀고 응집도(Cohesion)를 높여, 비즈니스 요구사항 변경 시 시스템 전체로 파급(Ripple)되는 유지보수 비용을 방어한다.
> 3. **판단 포인트**: 정적인 관심사 분리(Layered, MVC)와 동적인 데이터 흐름 제어(Pipe-Filter, Event-Driven) 패턴을 명확히 대조하고, 현대 MSA 토폴로지에서 이벤트 기반 아키텍처가 채택되는 이유를 규명해야 한다.

## 출제 의도 및 답안 포인트

| 출제 의도 | 반드시 짚을 핵심 | 감점 회피 포인트 |
|:---|:---|:---|
| 아키텍처 패턴의 분류와 각 패턴의 동작 메커니즘 | MVC(관심사 분리) / 파이프필터(스트림 처리) / EDA(비동기) | 단순히 3~4개 패턴의 이름만 암기하여 나열하고 적용 도메인(어디에 쓰는지) 누락 |
| Layered 아키텍처의 의존성 규칙과 한계 | 상위 레이어가 하위 레이어만 호출 (건너뛰기 금지) | Layered와 MVC를 완전히 동일한 개념으로 뭉뚱그려 설명하는 기본기 오류 |
| 마이크로서비스(MSA)와 이벤트 기반(EDA) 결합 | 브로커(Kafka) 기반의 비동기 발행/구독(Pub-Sub) 모델 | 클라이언트-서버(동기 통신) 패턴으로 대규모 트래픽을 처리한다고 적는 성능 설계 에러 |

> 요약: 화면을 고쳤더니 DB가 터지는(스파게티) 비극을 막기 위해, 선배 엔지니어들이 멱살을 잡고 강제해 둔 '방화벽'들의 모음집이다.

## Ⅰ. 개요 및 필요성

- 정의: 소프트웨어 설계 시 반복적으로 발생하는 문제(Problem)에 대해, 시스템의 컴포넌트 구조와 그들 간의 상호작용 규칙(Context)을 추상화하여 제시하는 재사용 가능한 아키텍처 해법(Solution)
- 배경: 시스템 규모가 커지며 모놀리식(Monolithic) 스파게티 코드가 양산되고, 특정 프레임워크나 인프라에 비즈니스 로직이 강하게 결합(Tight Coupling)되어 시스템 진화(Evolution) 마비
- 필요성: 모듈 간 통신 방식을 규격화하여 독립적인 병렬 개발을 가능케 하고, 변경 파급 효고(Ripple Effect)를 국소화하여 유지보수성과 확장성(Scalability)을 극대화하기 위함

## Ⅱ. 핵심 아키텍처 패턴의 구조와 제어 흐름 도식

```text
[ 1. MVC (관심사 분리) ]         [ 2. Event-Driven (이벤트/비동기 통신) ]
사용자 -> (요청) -> [ Controller ]    [ 주문 서비스 ] --(Event 발행)--> [ Event Bus (Kafka) ]
                     /      \                                                /        \
          (갱신) /          \ (선택)                       (Event 구독) /          \ (Event 구독)
               /              \                                       /              \
         [ Model ] <--(조회)-- [ View ]                  [ 결제 서비스 ]                [ 배송 서비스 ]
```

| 아키텍처 패턴 | 메커니즘 및 뼈대 (Topology) | 최적 적용 도메인 및 맹점 |
|:---|:---|:---|
| **Layered (계층형)** | 프레젠테이션 -> 비즈니스 -> 영속성(DB). **하향식 단방향 의존성** 강제 | **일반적 웹서버 (Spring Boot)**. 너무 많은 계층을 통과하므로 성능 저하 우려 (Sinkhole Anti-pattern) |
| **MVC** | 모델(Data), 뷰(UI), 컨트롤러(Logic) 3분할. **Controller가 M과 V의 중재자 역할** | **GUI 및 프론트/웹 애플리케이션**. 코드가 방대해지면 Controller가 비대해짐(Fat Controller) |
| **Pipe-Filter (데이터 흐름)**| 컴포넌트(Filter)들이 파이프(Stream)로 연결되어 데이터를 순차적 변환 가공 | **배치 처리, 영상 인코딩, 빅데이터 파이프라인**. 필터 간 상태 공유(Stateful)가 불가능함 |
| **Event-Driven (이벤트 기반)**| 발행자(Publisher)와 구독자(Subscriber)가 서로를 모른 채(Decoupled) 이벤트 버스를 통해 소통 | **MSA(마이크로서비스), 금융 트랜잭션**. 트래픽 폭주 방어에 최적이나 디버깅 추적이 극도로 험난함 |

> 요약: 정수기 필터(Pipe-filter)에 쇼핑몰 로직을 태울 순 없다. 반대로 영상 처리 엔진을 MVC로 짜는 것도 미친 짓이다. 도메인(Domain)의 데이터가 어떻게 흐르는지에 따라 뼈대(패턴)를 골라야 한다.

## Ⅲ. 엔터프라이즈 아키텍처의 진화: MVC에서 EDA(Event-Driven)로

모바일 시대 트래픽 폭주(초당 10만 건)를 맞으며, 동기(Sync) 방식의 MVC와 Layered 패턴은 붕괴했다.

| 붕괴 한계 (동기 통신의 비극) | 아키텍처적 전환 (이벤트 기반 도입) | 시스템적 방어 효과 |
|:---|:---|:---|
| 쇼핑몰 결제 시 "결제->포인트적립->메일발송"을 순서대로(동기) 호출. 메일 서버가 뻗으면 결제 전체가 롤백되고 사용자는 무한 로딩 창을 봄 | **메시지 큐(Message Queue) 도입 (Asynchronous)**. "결제"만 처리하고, "메일발송해라"는 이벤트를 큐(Kafka)에 던지고 사용자에게 즉시 "결제 완료" 응답 반환 | 메일 서버가 하루 종일 죽어있어도 결제는 1초 만에 100% 정상 처리됨(장애 격리). 메일 서버 복구 시 큐에 쌓인 밀린 일을 알아서 재처리 |

> 요약: 현대 백엔드의 핵심은 "내가 할 일만 딱 끝내고, 나머지는 알림창(Event)에 던진 뒤 뒤도 안 돌아보고 퇴근하는 것(Decoupling)"이다. 이 이기적인 구조가 전체 서버의 생존(가용성)을 보장한다.

## Ⅳ. 극복해야 할 시스템적 리스크 및 인프라 튜닝

우아한 아키텍처 패턴도 룰(Rule)을 강제할 컴플라이언스 도구가 없으면 금세 스파게티로 회귀한다.

| 리스크 요인 | 발생 시나리오 및 시스템 붕괴 원인 | 아키텍처 대응 방안 (실무 튜닝) |
|:---|:---|:---|
| **Layered 우회 (Bypass) 폭주** | 주니어 개발자가 바쁘다며 UI(프레젠테이션) 컨트롤러에서 직접 DB(Repository) SQL을 호출해 계층 룰을 파괴하고 보안 취약점 노출 | **ArchUnit 기반 정적 분석 TDD 도입**. CI 파이프라인(Jenkins)에서 `Controller는 무조건 Service만 의존해야 함`이라는 아키텍처 룰을 JUnit 테스트 코드로 강제하여 빌드 차단 |
| **이벤트(Event) 미아 및 추적 상실** | 10개의 서비스가 카프카(Kafka)로 비동기 이벤트를 주고받다 에러가 터졌는데, 어느 서비스의 몇 번째 큐에서 죽었는지 로그 추적이 불가능해 복구 포기 | **분산 추적(Distributed Tracing) 튜닝**: 모든 이벤트 헤더에 고유한 `Trace-ID`를 부여하고, Zipkin이나 Jaeger 인프라를 구축해 이벤트의 여정을 폭포수 시각화 대시보드로 가시성 100% 확보 |

> 요약: 이벤트 기반 아키텍처(EDA)는 평소에는 서버가 절대 안 죽는 마법 같지만, 한 번 오류가 나면 10개의 마이크로서비스를 다 뒤져야 하는 '디버깅 지옥'을 열어버린다. 분산 추적(Trace-ID) 없는 EDA는 자살행위다.

## Ⅴ. 실무 적용 방안 및 결론

**적용 방안 3개:**
1. [CQRS 패턴 튜닝 기반의 대용량 트래픽 처리] 티켓 예매 사이트(쓰기 1 : 읽기 99 비율) 구축 시, 단일 DB의 읽기/쓰기 락(Lock) 병목을 타파하기 위해 상태 변경(Command)은 기존 RDBMS로 처리하고, 조회(Query)는 Redis나 ElasticSearch로 완벽히 찢어 읽기 성능을 100배 스케일아웃(Scale-out)
2. [MVC 뷰(View)의 완전 독립 및 BFF(Backend For Frontend) 도입] 모바일 앱, 태블릿, 웹 등 클라이언트가 다변화됨에 따라 서버사이드 렌더링(JSP) 기반 MVC를 폐기하고, View를 React/Vue.js(SPA)로 완전 격리한 뒤 각 프론트엔드 매체별 맞춤형 API를 조립해 주는 BFF 아키텍처 레이어 삽입
3. [Pipe-Filter 아키텍처 기반 빅데이터 전처리] 초당 1만 건의 IoT 센서 데이터를 RDBMS에 넣기 전, Apache NiFi 또는 Logstash를 배치하여 데이터 파싱(Filter 1) -> 이상치 마스킹(Filter 2) -> 압축(Filter 3) 파이프라인으로 엮어 데이터 웨어하우스(DW) 부하 원천 차단

**결론:**
- 기술사 판단: 아키텍처 패턴은 단기적으로 코딩량을 늘리고 개발자를 귀찮게 만들지만, 장기적으로 소프트웨어의 수명(Lifespan)을 10년으로 연장하는 엔지니어링의 정수다. 특히 현대 IT 토폴로지는 특정 패턴 1개가 아니라 MVC(화면) + Layered(단일 모듈) + Event-Driven(모듈 간 통신)이 복합적으로 엮인 하이브리드 진화를 거치고 있다.
- 향후 방향: 클라우드 네이티브(Cloud-Native) 시대로 넘어오며 시스템의 경계가 서버 단일 머신(Machine)에서 AWS/GCP 인프라 전체로 확장되었다. 이에 따라 코드 레벨의 아키텍처 패턴을 넘어, 서버리스(Serverless)와 API 게이트웨이를 활용한 인프라 레벨의 아키텍처 패턴(Cloud Design Patterns)으로 설계 주도권이 넘어가고 있다.
