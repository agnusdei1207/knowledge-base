# 📖 【암기용】 개념 완전 이해

> 목적: 아키텍처 패턴을 처음 봐도 완벽히 이해하게 만든다. 시험 답안 양식이 아니라, 이해를 위한 친절한 설명이다.

## 한눈에
- **개요**: 반복되는 시스템 구조 문제를 해결하는 검증된 설계 틀
- **왜 필요한가**: 기능이 늘수록 코드보다 구조가 장애·배포·변경 비용을 좌우함. MVC, MSA, 이벤트 기반을 구분해야 요구사항에 맞는 구조를 고를 수 있음.
- **핵심 직관**: 아키텍처 패턴은 집의 평면도와 같아서, 방을 나눈 방식이 생활 동선과 수리 비용을 결정함.

## 깊이 이해
- **배경·문제의식**: 단일 코드베이스는 초기 개발 속도와 배포 단순성에서 유리하지만, 팀·기능·트래픽이 커지면 결합도 증가와 배포 대기열이 발생함.
- **작동 원리**: MVC는 화면·제어·모델을 분리해 UI 변경 영향을 제한함. MSA는 도메인 단위 서비스를 독립 배포함. 이벤트 기반은 생산자와 소비자를 메시지로 느슨하게 연결함.
- **비유**: MVC는 주방·홀·계산대를 나눈 식당, MSA는 전문 매장들의 푸드코트, 이벤트 기반은 주문표를 게시판에 붙이면 담당자가 가져가는 방식임.
- **구체 예시**: 월 주문 1만 건 쇼핑몰은 MVC 모놀리스로 운영 가능하나, 초당 5천 주문과 20개 팀 동시 배포 환경은 MSA+Kafka 이벤트 구조가 배포 대기 시간을 줄임.
- **흔한 오해·주의점**: MSA가 항상 정답은 아님. 서비스 수 10개 미만, 팀 2개 이하, 데이터 모델이 자주 함께 바뀌면 모듈형 모놀리스가 운영 비용을 낮춤.

## 연결 개념
- 마이크로서비스 아키텍처: 서비스 경계와 독립 배포성 판단
- 이벤트 드리븐 아키텍처: 비동기 메시징과 최종 일관성 판단
- 결합도·응집도: 패턴 선택의 구조 품질 기준

# 📝 【답안용】 시험 답안 템플릿

> 목적: 시험장에서 25분에 그대로 쓰는 답안 양식. 작성방식(추상표현 금지·수치·도식·문제유형 전환)을 엄격히 지킨다.
> 핵심: 패턴 명칭 나열이 아니라 요구사항별 결합도·응집도·동기/비동기·운영 복잡도 trade-off를 판단한다.

## 핵심 인사이트 (3줄 요약)

> 1. **본질**: 아키텍처 패턴은 시스템 구성요소와 의존관계를 반복 가능한 구조로 묶어 변경 영향과 운영 비용을 통제하는 설계 해법이다.
> 2. **가치**: MVC는 UI 분리, MSA는 독립 배포, 이벤트 기반은 비동기 확장과 장애 격리를 제공하되 관측성·정합성 비용이 증가함.
> 3. **판단 포인트**: 팀 규모, 배포 빈도, 트래픽 변동, 데이터 일관성 요구를 기준으로 모놀리스·MSA·이벤트 기반을 선택해야 함.

## 출제 의도 및 답안 포인트

| 출제 의도 | 반드시 짚을 핵심 | 감점 회피 포인트 |
|:---|:---|:---|
| 아키텍처 선택 역량 확인 | MVC/MSA/Event-driven의 구조, 결합도, 동기/비동기 비교 | 패턴을 유행어처럼 나열하고 선택 기준 누락 |
| 운영 trade-off 판단 확인 | 독립 배포성, 장애 격리, 데이터 정합성, 관측성 지표 | MSA를 무조건 우위로 단정 |
| 시험 답안 전개력 확인 | 구조도, 흐름도, 비교표, 리스크 대응 연결 | UI 패턴과 분산 시스템 패턴을 같은 층위로 혼합 |

> 요약: 이 문제는 패턴 암기가 아니라 요구사항을 구조 품질 속성으로 바꾸는 판단을 요구한다.

---

## Ⅰ. 개요 및 필요성

아키텍처 패턴은 반복되는 구조 문제의 표준 해법이다. 소프트웨어는 규모가 커질수록 기능 구현보다 변경 영향, 배포 충돌, 장애 전파가 비용을 만든다. 따라서 MVC, MSA, 이벤트 기반을 요구사항과 운영 지표에 맞춰 선택해야 한다.

---

## Ⅱ. 구조 및 구성요소

```text
Architecture Requirement
  / UI 중심 -> MVC -> Model / View / Controller
  / 도메인 독립 배포 -> MSA -> Service / DB per Service / Gateway
  / 비동기 확장 -> Event-driven -> Producer / Broker / Consumer
Quality Attribute -> Coupling / Cohesion / Deployability / Observability
```

| 구성요소 | 역할 | 특이사항 |
|:---|:---|:---|
| MVC | 화면, 제어, 데이터를 분리 | UI 변경 영향 범위 축소 |
| MSA | 도메인별 서비스와 저장소 분리 | 독립 배포와 분산 트랜잭션 trade-off |
| Event-driven | 이벤트 생산자와 소비자 비동기 연결 | 최종 일관성, 중복 처리 대응 필요 |
| 품질 속성 | 결합도·응집도·가용성·변경성 측정 | ATAM, ADR로 의사결정 기록 |

> 요약: 아키텍처 패턴은 구성요소 분리 방식과 의존관계를 통해 변경 영향, 배포 단위, 장애 전파를 통제한다.

---

## Ⅲ. 동작원리 및 흐름도

```text
요구사항 수집 -> 품질 속성 도출 -> 패턴 후보 선정
-> 결합도/응집도 평가 -> 동기/비동기 흐름 설계
-> 운영 지표 검증 -> ADR 기록
```

| 단계 | 처리 내용 | 검증 기준 |
|:---:|:---|:---|
| 1 | 기능·비기능 요구사항 분리 | p95 지연, 배포 주기, 장애 허용 범위 |
| 2 | 도메인·UI·이벤트 흐름 분석 | 변경 빈도, 데이터 소유권, 트랜잭션 범위 |
| 3 | MVC/MSA/Event-driven 후보 비교 | 결합도, 응집도, 팀 소유권 |
| 4 | POC와 운영 지표 측정 | 배포 실패율, MTTR, 메시지 지연 |
| 5 | ADR로 선택 근거 기록 | 대안, 결정, 영향 범위 명시 |

> 요약: 패턴 선택은 요구사항을 품질 속성으로 바꾼 뒤 후보 구조를 지표로 검증하는 절차이다.

---

## Ⅳ. 특징

| 구분 | MVC | MSA | Event-driven |
|:---|:---|:---|:---|
| 결합도 | UI 계층 결합 감소 | 서비스 간 API 결합 관리 | 생산자/소비자 시간 결합 제거 |
| 배포 단위 | 애플리케이션 단위 | 서비스 단위, 일 10회 이상 가능 | 소비자별 독립 배포 가능 |
| 정합성 | 단일 DB 트랜잭션 | Saga, Outbox 필요 | 최종 일관성, 재처리 필요 |
| 운영 비용 | 로그·모니터링 단순 | 분산 추적, SLO 필요 | Broker lag, DLQ 관리 필요 |

> 요약: MVC는 구조 단순성, MSA는 독립 배포성, 이벤트 기반은 비동기 확장을 제공하나 운영 지표 체계가 필요하다.

---

## Ⅴ. 심화 비교 및 적용 판단

| 비교 축 | 기존/대안 | 본 키워드 | 선택 기준 |
|:---|:---|:---|:---|
| 구조 | 계층형 모놀리스 | 패턴 기반 구조 분리 | 팀 3개 이상, 배포 충돌 월 5회 이상 |
| 비용/성능 | 단일 호출·단일 DB | 네트워크 호출, Broker 추가 | p95 200ms 요구면 동기 호출 수 제한 |
| 운영/위험 | 장애 영향 범위 전체 | 장애 격리와 관측성 필요 | MTTR 30분 이하 목표 시 추적 체계 필수 |

> 요약: 패턴 적용은 구조 미학이 아니라 배포 충돌, 장애 범위, 지연 목표를 근거로 선택해야 한다.

| 리스크 | 원인 | 대응 방안 | 확인 지표 |
|:---|:---|:---|:---|
| 과분해 | 도메인 경계 미성숙 | 모듈형 모놀리스 후 분리 | 서비스당 변경 요청 수 |
| 정합성 오류 | 분산 트랜잭션 부재 | Saga, Outbox, idempotency key | 보상 실패율, 중복 처리율 |
| 관측성 공백 | 호출 경로 분산 | OpenTelemetry trace, correlation ID | trace coverage 95% 이상 |

> 요약: 주요 리스크는 과분해와 정합성 오류이며, 서비스 경계와 관측성 지표로 통제한다.

| 점검 항목 | 목표 기준 | 측정 방법 |
|:---|:---|:---|
| 변경 영향 | 변경 1건당 수정 모듈 3개 이하 | Git diff, dependency graph |
| 배포 품질 | 배포 실패율 5% 이하, rollback 10분 이내 | CI/CD 로그 |
| 운영 관측 | p95 지연, error rate, trace coverage | APM, 로그, 분산 추적 |

> 요약: 아키텍처 패턴의 성공 여부는 변경 영향, 배포 실패율, 관측성 커버리지로 검증한다.

---

## Ⅵ. 실무 적용 및 결론

**적용 방안 3개 (필수 - 단계별 또는 항목별):**
1. 요구사항을 ATAM 품질 속성으로 분류하고 p95 지연 200ms, 가용성 99.9%, 배포 주기 일 1회 이상처럼 수치화함.
2. 도메인 경계와 데이터 소유권을 기준으로 MVC, 모듈형 모놀리스, MSA, 이벤트 기반을 후보로 두고 ADR에 선택 근거 기록함.
3. OpenTelemetry, Prometheus, Grafana로 호출 지연·오류율·Broker lag를 수집하고 SLO 위반 시 패턴 재조정함.

**결론 (2줄):**
- 기술사 판단: 팀·배포·트래픽이 작으면 MVC/모듈형 모놀리스, 독립 배포와 장애 격리가 필요하면 MSA/Event-driven을 선택함.
- 향후 방향: 플랫폼 엔지니어링과 관측성 표준화를 결합해 패턴 선택을 코드 구조와 운영 지표로 함께 검증하는 방향임.
