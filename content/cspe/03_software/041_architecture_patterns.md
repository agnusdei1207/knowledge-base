## 미리 알고가기

- MVC는 화면 처리와 비즈니스 로직을 나누는 계층형 패턴임
- MSA는 서비스를 독립 배포 단위로 나누는 분산 아키텍처임
- 이벤트드리븐 아키텍처는 상태 변화를 이벤트로 전달해 비동기 협력을 구성하는 방식임

## Ⅰ. 개요

- **정의/개념**: 소프트웨어 아키텍처 패턴은 반복되는 설계 문제를 일정한 구조와 상호작용 방식으로 푸는 해법이며, MVC, MSA, 이벤트드리븐 구조가 대표 예시임.
- **배경/필요성**: 시스템마다 UI 변경 부담, 서비스 독립 배포 요구, 비동기 통합 요구가 다르므로, 어떤 축을 기준으로 구조를 나눌지 판단할 공통 패턴이 필요함.

## Ⅱ. 특징

- MVC는 표현 계층과 처리 계층을 나눠 화면 변경 부담을 줄임
- MSA는 서비스별 배포와 확장을 가능하게 하지만 운영 복잡도를 키움
- 이벤트드리븐 구조는 생산자와 소비자가 이벤트 계약을 통해 비동기로 통신함
- 하나의 시스템에서도 계층별로 서로 다른 패턴을 함께 사용할 수 있음

## Ⅲ. 종류 및 비교

| 구분 | MVC | MSA | 이벤트드리븐 |
|:---|:---|:---|:---|
| 주된 분리 기준 | 화면, 입력 처리, 비즈니스 로직을 계층으로 나눔 | 비즈니스 기능을 서비스 단위로 나눔 | 상태 변화를 이벤트와 소비자 관계로 나눔 |
| 변경·배포 단위 | Model·View·Controller 책임별 변경 | 서비스별 독립 빌드·배포·확장 | 생산자·소비자를 독립 변경하고 이벤트 계약으로 연결 |
| 주된 한계 | 대규모 분산 문제나 서비스 독립 배포 문제는 직접 해결하지 못함 | 데이터 분산과 네트워크 장애와 운영 자동화 부담이 커짐 | 추적과 재처리와 일관성 관리가 어려워질 수 있음 |
| 대표 환경 | 웹 애플리케이션 프레젠테이션 계층 | 여러 팀이 서비스별 배포를 담당하는 복합 도메인 | 알림·통합 이벤트·비동기 서비스 협력 |

> 요약: 아키텍처 패턴 선택은 유행을 고르는 일이 아니라 어디를 분리해야 변경과 운영 부담이 줄어드는지 정하는 일임.

## Ⅳ. 구성요소 및 구조

| 구성요소 | 설명 |
|:---|:---|
| Presentation Separation | MVC에서는 View, Controller, Model을 나눠 화면 변경이 비즈니스 규칙에 바로 번지지 않게 함 |
| Service Boundary | MSA에서는 기능 경계를 서비스 단위로 나눠 배포와 확장과 장애 격리 단위를 만듦 |
| Event Bus or Broker | 이벤트드리븐 구조에서는 생산자와 소비자 사이를 중개해 직접 결합을 줄임 |
| Contract Interface | 계층, 서비스, 이벤트 간 상호작용 규약을 명확히 해 변경 영향을 통제함 |

## Ⅴ. 원리 및 절차 흐름도

```text
+-------------+     +-------------+     +-------------+     +-------------+
| 요구 특성 분석  | --> | 분리 축 선택   | --> | 계약/경계 정의  | --> | 운영 검증      |
+-------------+     +-------------+     +-------------+     +-------------+
```

1. **요구 특성 분석**: UI 변경 중심인지, 서비스 독립 배포 중심인지, 비동기 통합 중심인지 파악함
2. **분리 축 선택**: 가장 자주 바뀌는 축에 맞춰 적합한 패턴을 고름
3. **계약 및 경계 정의**: 계층 책임, API, 이벤트 규약을 명확히 정함
4. **운영 검증**: 배포 독립성, 추적성, 장애 영향 범위를 실제 운영으로 확인함

## Ⅵ. 실무 적용 및 유의점

1. 웹 포털과 업무 화면 개발에서는 MVC를 적용하되 컨트롤러에 업무 규칙이 몰리면 테스트와 변경이 어려워지므로 계층 책임 규칙을 함께 두고 컨트롤러 복잡도와 단위 테스트 범위로 확인함
2. 대형 플랫폼에서는 MSA와 이벤트드리븐 구조를 함께 쓰더라도 경계와 계약이 약하면 분산 모놀리스로 흐르기 쉬우므로 도메인 경계와 이벤트 스키마 관리 규칙을 함께 운영하고 동시 배포 비율과 계약 호환성 위반 건수로 확인함

## Ⅶ. 결론

아키텍처 패턴은 이름보다 시스템이 가장 자주 변하는 축을 어디서 끊어야 하는지를 기준으로 선택해야 함.
