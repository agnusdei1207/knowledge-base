# 📖 【암기용】 개념 완전 이해

> 목적: 오픈소스 컴플라이언스를 처음 봐도 완벽히 이해하게 만든다. 시험 답안 양식이 아니라, 이해를 위한 친절한 설명이다.

## 한눈에
- **개요**: 오픈소스 컴플라이언스는 **오픈소스 라이선스** 의무와 **취약점(보안) 리스크**를 조직의 **정책·승인 프로세스**로 준수하는 거버넌스 활동이다 — 개별 개발자의 선의가 아니라 조직 차원의 통제 체계를 뜻한다.
- **왜 필요한가**: 개발자가 패키지 하나를 설치하면 그 패키지가 또 의존하는 수십 개의 간접 의존성이 함께 딸려 들어온다. 그 안에 GPL 코드나 알려진 취약점(CVE)이 섞여 있어도 개발자 개인은 대부분 인지하지 못한다.
- **핵심 직관**: 컴플라이언스는 "이 코드를 써도 되는지, 어떻게 고지할지, 위험은 무엇인지"를 릴리스 전에 통과시키는 검문소(gate)다.

## 핵심 용어 정리 (내부에 등장하는 것들)

| 용어 | 의미 | 비유 |
|:---|:---|:---|
| 오픈소스 컴플라이언스 | 라이선스·보안 의무를 조직 정책과 승인 절차로 준수하는 활동 전체 | 통관 절차 전체 |
| SCA (Software Composition Analysis) | 의존성 목록·라이선스·CVE를 자동으로 스캔하는 도구/기법 | 성분표를 자동으로 읽어주는 기계 |
| Transitive Dependency (간접 의존성) | 내가 설치한 패키지가 또 의존하는 패키지 | 친구가 데려온 친구의 친구 |
| License Policy (라이선스 정책) | 허용/검토/금지 3등급으로 라이선스를 분류한 규정 | 신호등(초록/노랑/빨강) |
| Review Board (승인 워크플로) | 법무·보안·개발이 함께 위험 라이선스·취약점 사용을 승인·거부하는 절차 | 대출 심사위원회 |
| Exception (예외 승인) | 정책 위반이지만 특정 조건에서 한시적으로 허용하는 결정 | 유효기간이 있는 특별 통행 허가증 |
| NOTICE / Source Offer | 라이선스가 요구하는 고지문 또는 소스 제공 의무의 이행 산출물 | 제품 뒷면 성분 표시 |
| Release Gate (릴리스 게이트) | 정책 위반 시 배포 파이프라인을 자동으로 막는 체크포인트 | 공항 보안 검색대 |
| SBOM | 컴플라이언스 판단의 입력이 되는 컴포넌트 목록 | 자재 명세서 |

## 깊이 이해

### 왜 "라이선스 표시"만으로는 부족한가 (배경)
- 현대 소프트웨어 제품에서 직접 작성한 코드는 전체의 10~20% 수준에 불과하고 나머지는 오픈소스 의존성인 경우가 흔하다. 문제는 직접 설치한 패키지(direct dependency) 20개가 각자 평균 5~10개의 간접 의존성을 끌고 오면, 실제 포함 컴포넌트 수는 수백 개로 불어난다는 점이다. 개발자가 이를 하나하나 확인하는 것은 현실적으로 불가능하다.

### 3단계 라이선스 등급화의 판별 원리
- 실무에서는 라이선스를 "허용(Permissive: MIT/BSD/Apache-2.0) — 검토(Weak Copyleft: LGPL/MPL) — 금지(Strong Copyleft: GPL/AGPL, 또는 상용 금지 조항)" 3단계로 나눠 자동 판정한다.
- 판별 기준은 배포 방식(내부 사용 vs 외부 배포), 결합 방식(정적/동적 링크, API 호출), 소스공개 요구 여부다. 예: 같은 GPL 라이브러리라도 "사내 배치 작업에서만 실행"이면 허용 등급, "고객에게 배포하는 제품에 포함"이면 금지 등급으로 판정이 달라진다.

### 릴리스 파이프라인에서의 실제 흐름 (수치 예시)
- 신규 패키지 추가 → CI에서 SCA가 자동 스캔 → SPDX 라이선스 식별 → 정책 매칭 순으로 진행된다. 예를 들어 릴리스당 평균 500개 컴포넌트를 스캔한다면, unknown license(식별 불가) 목표는 0건, GPL·AGPL 같은 high-risk 항목은 승인 기록 100%가 있어야 릴리스 게이트를 통과하도록 설계한다.
- critical CVE가 발견되면 배포를 차단하고 7일 이내 조치 SLA(Service Level Agreement)를 적용하는 식으로, 라이선스 심사와 취약점 심사가 같은 파이프라인에서 함께 처리된다.

### 예외(Exception) 관리가 핵심인 이유
- 정책을 100% 기계적으로 적용하면 업무가 마비된다(예: GPL이지만 내부 테스트 도구라 실제 위험이 없는 경우). 그래서 "예외 승인 + 만료일"이 필수다 — 예외는 영구가 아니라 재검토 시점(예: 90일)을 못 박아야, 위험을 임시로만 감수하고 있다는 사실을 잊지 않는다.

### 비유와 흔한 오해
- **비유**: 식품 회사가 원재료 원산지·알레르기 성분·유통기한을 표시하듯, 소프트웨어 회사도 구성요소와 그 의무를 표시해야 한다는 것이 오픈소스 컴플라이언스의 근본 발상이다.
- **오해 1**: 컴플라이언스는 법무팀만의 업무라는 생각은 틀렸다. SCA 스캔은 개발 단계, 승인은 법무·보안, 증적 보관은 릴리스 관리 — 여러 역할이 같은 SBOM과 워크플로를 공유해야 작동한다.
- **오해 2**: "한 번 검토하면 끝"이 아니다. 오늘 안전하다고 판단된 컴포넌트도 내일 새 CVE가 나올 수 있으므로 지속적 재스캔이 필요하다.

## 연결 개념
- 소프트웨어 라이선스 — 컴플라이언스가 준수하려는 개별 의무의 근거
- SBOM — 컴플라이언스 판단에 필요한 컴포넌트 목록의 출처
- SLSA — 빌드·배포 단계의 무결성까지 확장한 상위 공급망 보안 체계

# 📝 【답안용】 시험 답안 템플릿

> 목적: 시험장에서 25분에 그대로 쓰는 답안 양식. 작성방식(추상표현 금지·수치·도식·문제유형 전환)을 엄격히 지킨다.
> 핵심: 오픈소스 컴플라이언스는 라이선스 표기 활동이 아니라 정책, 자동 스캔, 승인, 배포 증적, 예외 관리 체계이다.

## 핵심 인사이트 (3줄 요약)

> 1. **본질**: 오픈소스 컴플라이언스는 OSS 사용에 따른 라이선스·보안·출처·고지 의무를 릴리스 전에 검증하는 통제 체계이다.
> 2. **가치**: 법적 분쟁, 배포 중단, 취약점 미조치, 공급망 공격 영향을 정책과 증적으로 줄인다.
> 3. **판단 포인트**: SCA, SBOM, 승인 workflow, NOTICE, 예외 만료일, 감사 추적이 답안의 필수 축이다.

## 출제 의도 및 답안 포인트

| 출제 의도 | 반드시 짚을 핵심 | 감점 회피 포인트 |
|:---|:---|:---|
| OSS 거버넌스 이해 확인 | 정책, 역할, 도구, 릴리스 게이트 | 라이선스 종류만 나열 |
| 법적·보안 리스크 판단 확인 | GPL/AGPL, CVE, 출처, NOTICE | 취약점 관리와 라이선스 관리를 분리 설명 |
| 실무 프로세스 설계 확인 | SCA, SBOM, 승인, 예외, 증적 보관 | 예외 승인 만료일과 재검토 누락 |

> 요약: 이 문제는 OSS 사용 허용 여부를 개발 pipeline에서 판단하는 운영 체계를 요구한다.

## Ⅰ. 개요 및 필요성

- 개요: OSS 사용 의무 준수 체계
- 배경: 제품에 포함된 라이브러리, 컨테이너 이미지, 코드 스니펫은 라이선스와 취약점을 함께 가져온다.
- 필요성: 릴리스 전 식별, 승인, 고지, 증적 관리로 배포 중단과 감사 실패를 막아야 한다.

---

## Ⅱ. 구조 및 구성요소

```text
OSS Policy -> Developer Request -> SCA Scan
-> SBOM -> Legal/Security Review -> Approval/Exception
-> NOTICE/Source Offer -> Release Gate -> Evidence Store
```

| 구성요소 | 역할 | 특이사항 |
|:---|:---|:---|
| OSS Policy | 허용·검토·금지 라이선스와 취약점 기준 | GPL, AGPL, critical CVE 기준 |
| SCA Tool | 의존성, 라이선스, CVE 자동 식별 | direct/transitive dependency 포함 |
| Review Board | 법무·보안·개발 승인 | 예외 만료일과 재검토 조건 |
| Evidence Store | SBOM, NOTICE, 승인 기록 보관 | 감사 대응 5영업일 목표 |

> 요약: 컴플라이언스 구조는 정책, 자동 식별, 합의 승인, 릴리스 증적 저장소로 구성된다.

---

## Ⅲ. 동작원리 및 흐름도

```text
패키지 추가 -> CI SCA Scan -> License/CVE 분류
-> Policy Match -> 승인 또는 차단
-> NOTICE/SBOM 생성 -> Release Gate 통과
-> 사후 CVE 모니터링
```

| 단계 | 처리 내용 | 검증 기준 |
|:---:|:---|:---|
| 1 | 신규 OSS 요청과 의존성 수집 | 패키지 누락 0건 |
| 2 | 라이선스·CVE 자동 분석 | SPDX 식별 100% |
| 3 | 위험 등급별 승인 처리 | high risk 승인 100% |
| 4 | 릴리스 산출물과 증적 보관 | NOTICE/SBOM 포함 100% |

> 요약: OSS 컴플라이언스는 개발 중 스캔하고 릴리스 전 차단·승인·증적을 완료하는 흐름이다.

> 요약: 주요 리스크는 라이선스, CVE, 증적이며 CI gate와 만료일 기반 예외로 통제한다.

| 점검 항목 | 목표 기준 | 측정 방법 |
|:---|:---|:---|
| 정책 준수 | 금지 라이선스 0건 | SCA policy report |
| 예외 관리 | 예외 만료일 100% 등록 | workflow audit |
| 사후 모니터링 | 신규 critical CVE 24시간 내 알림 | vulnerability feed |

> 요약: 운영 수준은 금지 항목 차단, 예외 만료 관리, 신규 CVE 탐지 시간으로 판단한다.

## Ⅵ. 실무 적용 및 결론

**적용 방안 3개 (필수 — 단계별 또는 항목별):**
1. OSS 정책을 허용, 검토, 금지 3단계로 정의하고 GPL/AGPL/SSPL/상용금지 조항은 릴리스 전 법무 승인 적용
2. SCA를 CI에 연결해 라이선스, CVE, transitive dependency를 검사하고 critical CVE는 7일 SLA로 처리
3. 릴리스마다 CycloneDX 또는 SPDX SBOM, NOTICE, source offer, 승인 기록을 생성해 감사 저장소에 보관

**결론 (2줄):**
- 기술사 판단: OSS 비중 30% 이상 또는 외부 배포 제품은 SCA와 SBOM 기반 컴플라이언스 게이트를 필수 통제로 적용
- 향후 방향: 오픈소스 컴플라이언스는 SLSA, 서명 검증, VEX와 결합되어 공급망 신뢰성 관리로 확장
