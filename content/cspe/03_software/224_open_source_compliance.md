## Ⅰ. 개요
- **정의**: 오픈소스 라이선스 의무를 체계적으로 식별·이행하여 법적 위험을 제거하는 관리 활동임
- **배경/필요성**: 상용 SW의 오픈소스 비율이 70% 이상으로 증가하면서, 의무 미이행 시 소송·배포 중단 위험이 현실화됨
- **비유**: 식자재 원산지 표시 의무처럼, 사용한 오픈소스의 출처와 조건을 투명하게 공개하는 것과 유사함

| 출제 의도 | 반드시 짚을 핵심 | 감점 회피 포인트 |
|:---|:---|:---|
| 컴플라이언스 프로세스 설계 | 정책-식별-검토-이행 흐름 | 라이선스(223 참조)와 컴플라이언스의 관계 구분 |

> 요약: 오픈소스 사용에 따른 법적·기술적 의무를 조직 차원에서 이행하는 체계임

## Ⅱ. 구성요소
```text
+----------+    +----------+    +----------+
|  Policy  |--->| Tool     |--->| Process  |
| (정책)   |    | (도구)    |    | (프로세스)|
+----------+    +----------+    +----------+
                     |
                +----+----+
                | SBOM DB |
                +---------+
```

| 구성요소 | 설명 | 비유 |
|:---|:---|:---|
| 정책(Policy) | 허용/금지 라이선스 목록과 승인 기준을 정의함 | 사내 구매 규정 |
| 도구(Tool) | SCA 도구로 코드 내 오픈소스를 자동 스캔하고 SBOM을 생성함 | 식자재 검수기 |
| 프로세스 | 식별-검토-승인-이행-감사 절차를 수행함 | 품질관리 워크플로 |
| SBOM DB | 프로젝트별 오픈소스 구성 목록을 저장·관리함 | 재고 원장 |

> 요약: 정책·도구·프로세스·SBOM DB 4요소로 컴플라이언스 체계를 구성함

## Ⅲ. 절차
```text
정책수립 --> 스캔/식별 --> 법률검토 --> 의무이행
```
- 1단계: 정책수립 — 조직의 오픈소스 사용 정책과 승인 기준 확정
- 2단계: 스캔/식별 — SCA 도구로 소스·바이너리를 분석하여 오픈소스 컴포넌트 식별
- 3단계: 법률검토 — 식별된 라이선스의 의무 사항과 호환성을 법무팀이 확인
- 4단계: 의무이행 — 고지문 작성, 소스 공개, 라이선스 문서 배포 등 의무 충족

> 요약: 정책수립-스캔-법률검토-의무이행 4단계로 체계적 준수를 달성함

## Ⅳ. 문제점
- 간접 의존성 누락: transitive dependency의 라이선스까지 추적하기 어려움 — 잠재 위반 잔존
- 조직 인식 부족: 개발자가 라이선스 의무를 인지하지 못한 채 컴포넌트를 도입 — 사후 발견 시 수정 비용 급증
- 글로벌 규제 차이: 국가별 오픈소스 관련 법규가 상이 — 다국적 배포 시 준수 복잡도 증가

> 요약: 의존성 누락, 인식 부족, 규제 차이가 컴플라이언스의 3대 장벽임

## Ⅴ. 개선방안
1. 단기: CI 파이프라인에 SCA 게이트를 삽입하여 미식별 의존성 빌드 차단
2. 중기: 오픈소스 교육 프로그램과 내부 포털을 운영하여 개발자 인식 제고
3. 장기: ISO/IEC 5230(OpenChain) 인증 획득으로 글로벌 규제 대응 체계 표준화

> 요약: CI 게이트 → 교육·포털 → OpenChain 인증 순으로 성숙도 향상

## Ⅵ. 전망
- 발전 방향: SW 공급망 보안 규제(EU CRA 등)와 연계되어 컴플라이언스 범위가 보안까지 확대됨
- 기술사적 판단: SBOM 의무화 흐름에서 컴플라이언스는 SW 출하의 전제 조건으로 정착함
- 기술사 제언: 라이선스 관리와 보안 취약점 관리를 통합한 단일 거버넌스 체계 수립을 권고함
