# 📖 【암기용】 개념 완전 이해

> 목적: LLM 기반 서비스 개발과 RAG 구현을 처음 보는 사람도 완벽히 이해하게 만든다. 시험 답안 양식이 아니라, 이해를 위한 친절한 설명이다.

## 한눈에
- **개요**: RAG(Retrieval-Augmented Generation, 검색 증강 생성)는 **LLM 서비스 아키텍처**의 대표 패턴으로, 외부 문서를 검색해 LLM 프롬프트에 결합함으로써 근거 기반 답변을 생성하는 방식이다.
- **왜 필요한가**: LLM은 학습 시점 이후 생긴 사내 문서·업무 규정을 모르고, 모르는 내용도 그럴듯하게 지어내는 환각(Hallucination)을 일으킨다. 관련 문서를 검색해 프롬프트에 붙이면 "아는 척"이 아니라 실제 문서에 근거한 답변을 만들 수 있다.
- **핵심 직관**: LLM에게 기억만 믿고 답하라 하지 않고, 시험 직전에 관련 교재 페이지를 찾아 건네준 뒤 그 페이지를 참고해 답하게 하는 오픈북 시험 방식이다.

## 핵심 용어 정리 (내부에 등장하는 것들)

| 용어 | 의미 | 비유 |
|:---|:---|:---|
| LLM 서비스 아키텍처 | LLM을 실제 업무 서비스에 통합하기 위한 구조 설계 전체 — RAG는 그 중 지식 결합 패턴 | 자동차(LLM) 위에 얹는 내비게이션(RAG) 시스템 |
| 환각(Hallucination) | LLM이 근거 없이 그럴듯한 오답을 사실처럼 생성하는 현상 | 모르는 문제를 자신 있게 틀리게 답하는 학생 |
| Chunking(청크 분할) | 긴 문서를 검색·임베딩 단위(보통 300~800토큰)로 잘게 나누는 것 | 책 한 권을 챕터가 아니라 문단 단위로 잘라 색인하는 것 |
| Embedding(임베딩) | 텍스트를 의미가 가까울수록 가까운 위치에 놓이는 고차원 벡터로 변환하는 것 | 비슷한 뜻의 단어를 지도 위 가까운 좌표에 찍는 것 |
| Vector DB / HNSW | 임베딩 벡터를 저장하고 유사도 기준으로 빠르게 찾는 저장소 / 근사 최근접 탐색을 빠르게 하는 그래프 인덱스 구조 | 도서관에서 책 내용이 아니라 "느낌이 비슷한 책"을 빨리 찾아주는 사서 |
| Retriever / top-k | 질의 임베딩과 가장 가까운 문서 청크를 상위 k개 골라내는 검색기 | 시험에 나올 것 같은 페이지 상위 5개만 뽑아주는 것 |
| Hybrid Search (BM25 + 벡터) | 키워드 매칭(BM25)과 의미 유사도(벡터)를 함께 써서 검색 정확도를 보완하는 방식 | 단어 그대로도 찾고, 비슷한 뜻으로도 찾는 두 가지 검색을 동시에 |
| Rerank | 1차로 뽑힌 후보 문서들을 더 정교한 모델로 다시 순위 매기는 후처리 단계 | 1차 서류 합격자 중 면접으로 다시 순위를 매기는 것 |
| Prompt Augmentation(프롬프트 보강) | 검색된 청크를 시스템/사용자 프롬프트에 컨텍스트로 삽입하는 과정 | 답안지에 참고자료를 붙여 함께 제출하는 것 |
| Faithfulness(충실도) | 생성된 답변이 실제로 검색된 문서 내용에 근거하는 정도를 재는 평가 지표 | 답안이 제시된 교재 내용을 벗어나지 않았는지 채점 |
| recall@k / MRR / nDCG | 검색 품질 지표 — recall@k: 정답 문서가 top-k 안에 있었는가, MRR: 정답이 몇 번째 순위에 나왔는가의 역수 평균, nDCG: 순위별 가중치를 반영한 정렬 품질 | 정답이 상위 몇 번째에 있었는지로 채점하는 방식 |
| Access Filter(ABAC) | 사용자 권한에 따라 검색 대상 문서를 제한하는 필터 | 직급별로 열람 가능한 문서함이 다른 것 |

## 깊이 이해

### 배경 — 왜 파인튜닝이 아니라 검색인가
기업 서비스는 사내 규정, 계약서, 매뉴얼처럼 자주 바뀌는 문서를 답변 근거로 써야 한다. 문서가 바뀔 때마다 모델을 재학습(파인튜닝)하면 GPU 비용과 갱신 시간이 크고, 그 사이에는 낡은 정보로 답한다. 반면 RAG는 문서를 재색인만 하면 되므로, 모델 자체는 그대로 두고 지식만 실시간에 가깝게 갱신할 수 있다.

### 전체 파이프라인을 수치로 따라가기
1. **문서 수집·정제**: Confluence·PDF·DB에서 문서를 모으고 중복을 제거한다.
2. **Chunking**: 문서를 500토큰 청크로, 문맥 단절을 막기 위해 앞뒤 50토큰씩 겹치게(overlap) 분할한다. 청크가 너무 크면(예: 2,000토큰) 질문과 무관한 내용까지 섞여 들어가 답변 정확도가 떨어지고, 너무 작으면(예: 100토큰) 문맥이 끊겨 의미를 잃는다.
3. **Embedding**: 각 청크를 예를 들어 1,536차원 벡터로 변환해 Vector DB(HNSW 인덱스)에 저장한다.
4. **질의 처리**: 사용자 질문도 같은 방식으로 임베딩하고, 코사인 유사도가 가장 높은 top-k(예: 5)개 청크를 검색한다.
5. **Rerank**: 1차로 뽑힌 20개 후보를 정교한 재순위 모델로 다시 정렬해 최종 5개로 좁힌다.
6. **Prompt Augmentation·생성**: 최종 청크를 프롬프트에 넣고 LLM이 답변과 출처 URL을 함께 생성한다.

### 검색 품질을 어떻게 수치로 판정하는가
정답 문서가 실제로 상위 5위 안에 몇 번 들어왔는지가 recall@5다. 예: 골든셋 질문 100개 중 정답 문서가 top-5 안에 90번 있었다면 recall@5 = 90%. MRR은 정답이 3번째 순위에 있었으면 그 질문의 점수가 1/3이고, 이를 전체 질문에 대해 평균한다. recall@5 90%, MRR 0.8 이상을 배포 기준으로 삼는 식이다.

### 환각을 어떻게 통제하는가 — Faithfulness 평가
RAG를 쓴다고 환각이 사라지지 않는다. 검색된 문서와 무관한 내용을 LLM이 섞어 넣을 수 있기 때문이다. 그래서 생성된 답변의 각 문장이 실제로 검색된 청크에서 근거를 찾을 수 있는지를 자동/사람 평가로 측정하는데 이것이 faithfulness다. 예: RAGAS 같은 평가 프레임워크로 100개 답변 중 95개가 근거 문서와 일치하면 faithfulness 95% — 이 수치가 배포 게이트 기준이 된다.

### 판별 원리 — RAG vs 파인튜닝
지식이 자주 바뀌고 출처 제시가 필요한 업무(사내 헬프데스크, 법률·의료 규정 안내)는 RAG가 적합하다. 반대로 특정 말투·형식으로 항상 답하게 하거나(고객 응대 톤 고정), 지식보다 "행동 패턴"을 가르쳐야 하는 경우는 파인튜닝이 더 맞는다. 실무에서는 둘을 함께 쓰기도 한다 — 파인튜닝으로 형식을 고정하고, RAG로 최신 지식을 공급한다.

### 비유와 흔한 오해
- **비유**: 상담원이 모든 규정을 외우는 대신, 검색 시스템에서 관련 조항을 찾아 읽고 그걸 근거로 답변하는 절차와 같다.
- **오해 1**: "RAG를 쓰면 환각이 0이 된다" — 틀렸다. 검색이 실패하거나(관련 문서를 못 찾음) LLM이 검색 결과를 무시하고 지어내면 환각은 여전히 발생한다. faithfulness 평가로 지속 감시해야 한다.
- **오해 2**: 권한 필터를 빼먹으면, RAG가 오히려 사고 원인이 된다. 검색이 문서 접근 권한(ACL)을 무시하면, 일반 사용자 질문에 대해 임원 전용 문서 내용이 검색·노출될 수 있다. 그래서 Access Filter(ABAC)로 사용자 권한에 맞는 문서만 검색 대상에 넣어야 한다.

## 연결 개념
- Vector DB: 임베딩 벡터를 저장하고 유사도로 검색하는 RAG의 핵심 저장소
- Hybrid Search: BM25(키워드)와 벡터 검색을 결합해 검색 recall을 보완하는 기법
- LLMOps: 프롬프트, 평가(RAGAS), 비용, 안전을 운영 단계에서 관리하는 체계

## Ⅰ. 개요 및 필요성

- 개요: RAG는 검색 결합 LLM 서비스 구조다.
- 배경: 사내 문서와 업무 지식은 자주 바뀌므로 모델 재학습만으로 대응하기 어렵다.
- 필요성: 문서 검색 결과를 프롬프트에 결합해 근거 문서 기반 답변과 출처 추적을 제공해야 한다.

---

## Ⅱ. 구조 및 구성요소

```text
Document -> Chunking -> Embedding -> Vector DB
Query -> Retriever -> Prompt Augmentation -> LLM -> Answer with Source
                    / Access Filter
                    / Evaluation
```

| 구성요소 | 역할 | 설계 기준 |
|:---|:---|:---|
| 문서 파이프라인 | 수집, 정제, 청크 분할 | 300~800토큰 청크 |
| 임베딩·벡터 DB | 문서 벡터화와 유사도 검색 | top-k, cosine, HNSW |
| Retriever | 질의와 관련 문서 선택 | hybrid search, rerank |
| Generator | 검색 문서를 근거로 답변 생성 | 출처 표시, 금칙어 필터 |

> 요약: RAG는 문서 인덱싱 경로와 질의 응답 경로를 분리해 검색 결과를 LLM 입력으로 제공한다.

---

## Ⅲ. 동작원리 및 흐름도

```text
문서 수집 -> 청크 분할 -> 임베딩 저장 -> 질문 임베딩 -> top-k 검색 -> 프롬프트 보강 -> 답변 생성 -> 평가
```

| 단계 | 처리 내용 | 검증 기준 |
|:---:|:---|:---|
| 1 | 문서 수집과 청크 분할 | 중복 제거, 권한 태그 |
| 2 | 임베딩 생성과 벡터 인덱스 구축 | 검색 recall@k |
| 3 | 질의 검색과 rerank 수행 | MRR, nDCG |
| 4 | 근거 포함 답변 생성과 평가 | faithfulness, answer relevancy |

> 요약: RAG 품질은 LLM보다 문서 청크, 검색 recall, 근거 일치 평가에 의해 크게 좌우된다.

## Ⅴ. 심화 비교 및 적용 판단

| 구분 | 기존/대안 | RAG 구현 | 선택 기준 |
|:---|:---|:---|:---|
| 구조 | LLM 단독 호출 | 검색+프롬프트 보강 | 사내 문서 기반 답변 |
| 비용/성능 | 프롬프트 짧음 | 검색 지연과 토큰 증가 | p95 3초 목표 |
| 운영/위험 | 근거 부족 | 출처와 권한 필터 | 감사·고객 응답 |

> 요약: 사내 지식과 근거 제시가 필요하면 RAG를 선택하고, 단순 요약·분류는 LLM 단독 호출도 가능하다.

| 리스크 | 원인 | 대응 방안 | 확인 지표 |
|:---|:---|:---|:---|
| 검색 실패 | 청크 품질, 임베딩 부적합 | hybrid search, reranker | recall@5, MRR |
| 권한 위반 | 문서 ACL 미반영 | metadata filter, ABAC | 권한 위반 0건 |
| 환각 답변 | 근거 외 생성 | 출처 필수, answer grounding 평가 | faithfulness 95% |

> 요약: RAG 리스크는 검색 실패, 권한 위반, 환각이며 검색 평가와 권한 필터로 통제한다.

| 점검 항목 | 목표 기준 | 측정 방법 |
|:---|:---|:---|
| 검색 품질 | recall@5 90%, MRR 기준 충족 | 골든셋 평가 |
| 답변 품질 | faithfulness 95%, 출처 포함률 100% | RAGAS, Human Review |
| 서비스 지표 | p95 3초, 요청당 비용 예산 준수 | LLM Gateway, APM |

> 요약: RAG 운영 평가는 검색 품질, 근거 일치, 지연·비용을 함께 측정해야 한다.

## Ⅵ. 실무 적용 및 결론

**적용 방안 3개:**
1. Confluence, PDF, DB 문서를 수집해 300~800토큰 청크로 분할하고 문서 ACL과 출처 URL을 metadata로 저장함
2. OpenSearch BM25와 Vector DB HNSW를 결합한 hybrid search 후 reranker로 top-k 5개 문서를 선별함
3. RAGAS 또는 자체 골든셋으로 recall@5 90%, faithfulness 95%, p95 3초 기준을 배포 게이트로 설정함

**결론 (2줄):**
- 기술사 판단: 지식 갱신과 출처 제시가 필요한 업무는 RAG를 우선 적용하고, 응답 형식 고정이 핵심이면 파인튜닝을 병행함
- 향후 방향: RAG는 multi-hop retrieval, agentic workflow, 권한 기반 검색과 결합해 기업 지식 서비스의 기본 구조로 발전함
