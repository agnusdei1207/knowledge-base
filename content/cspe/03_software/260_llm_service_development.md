## Ⅰ. 개요
- **정의**: LLM을 핵심 추론 엔진으로 활용하는 서비스를 설계·구현·운영하는 개발 체계임
- **배경/필요성**: LLM API 호출만으로는 품질·비용·지연시간 제어가 불가하므로 서비스 아키텍처 설계가 필요함
- **비유**: 엔진(LLM)을 탑재한 자동차를 설계하는 과정처럼 엔진 외 프레임·제어장치까지 함께 구성하는 작업임

| 출제 의도 | 반드시 짚을 핵심 | 감점 회피 포인트 |
|:---|:---|:---|
| LLM 기반 서비스 아키텍처 설계 역량 | RAG·Guardrail·캐싱 레이어 구성 | 단순 API 래핑으로만 설명 시 감점 |

> 요약: LLM을 서비스로 제공하기 위한 아키텍처·품질·비용 제어 체계임

## Ⅱ. 구성요소
```text
Client --> API Gateway --> Guardrail(Input)
                               |
                               v
                    RAG Retriever --> LLM Engine --> Guardrail(Output)
                                                        |
                                                        v
                         Cache Layer <----- Response Formatter --> Client
```

| 구성요소 | 설명 | 비유 |
|:---|:---|:---|
| API Gateway | 인증·Rate Limit·라우팅 처리 | 건물 출입 보안 게이트 |
| Guardrail | 입출력 유해성·민감정보 필터링 | 안전 가드레일 |
| RAG Retriever | 외부 지식 검색으로 컨텍스트 증강(252 참조) | 참고서 검색 엔진 |
| LLM Engine | 핵심 추론 수행(자체 호스팅 또는 API 호출) | 자동차 엔진 |
| Cache Layer | 동일·유사 질의에 대한 응답 캐싱으로 비용·지연 절감 | 자주 묻는 질문 답변집 |

> 요약: Gateway·Guardrail·RAG·LLM·Cache 5개 계층으로 서비스를 구성함

## Ⅲ. 절차
```text
Requirement --> Architecture Design --> Develop + Integrate --> Deploy + Operate
```
- 1단계: 요구사항 정의 — 응답 품질 기준·지연시간 SLA·비용 한도 설정
- 2단계: 아키텍처 설계 — RAG 필요 여부·모델 선택·Guardrail 정책 결정
- 3단계: 개발·통합 — 프롬프트 엔지니어링·벡터 DB 연동·Guardrail 룰 구현
- 4단계: 배포·운영 — LLMOps(252 참조) 기반 모니터링·비용 추적·프롬프트 버전 관리

> 요약: 요구사항 → 설계 → 개발 → 운영의 4단계로 LLM 서비스를 구축함

## Ⅳ. 문제점
- 응답 품질 불안정: 동일 프롬프트에도 응답이 달라져 서비스 일관성 유지가 곤란함
- 비용 예측 불확실: 토큰 소비량이 입력 길이·대화 턴 수에 따라 가변적임
- 보안·규정 위험: 민감 정보 유출·유해 콘텐츠 생성 등 규정 위반 가능성이 존재함

> 요약: 품질 불안정·비용 가변·보안 위험이 LLM 서비스의 3대 과제임

## Ⅴ. 개선방안
1. 단기: Temperature 고정·Few-shot 표준화로 응답 일관성 확보
2. 중기: 토큰 예산 제어·Semantic Cache 도입으로 비용 예측성 향상
3. 장기: 다층 Guardrail(입력·출력·PII 마스킹) 체계화로 보안·규정 준수 내재화

> 요약: 일관성·비용 제어·Guardrail로 서비스 안정성을 단계적으로 확보함

## Ⅵ. 전망
- 발전 방향: Agent 기반 자율 추론 서비스로 LLM 활용 범위가 확대되는 추세임
- 기술사적 판단: LLM 서비스 아키텍처 설계 역량이 SW 기술사의 핵심 평가 영역으로 부상함
- 기술사 제언: 모델 의존도를 낮추는 모듈화 설계로 모델 교체 유연성을 확보해야 함
