# 📖 【암기용】 개념 완전 이해

> 목적: 알파·베타·인수 테스트를 출시 전 검증 단계 차이로 이해하게 만든다. 시험 답안 양식이 아니라, 이해를 위한 설명이다.

## 한눈에
- **개요**: 내부 검증, 제한 사용자 검증, 고객 승인 검증으로 나뉘는 출시 전 테스트
- **왜 필요한가**: 개발팀 테스트만으로 실제 사용자 환경, 사용성, 고객 업무 수용 여부를 모두 확인하기 어렵다. 단계별 테스트는 출시 위험을 점진적으로 줄임.
- **핵심 직관**: 제품을 연구소에서 점검하고, 일부 고객에게 시범 제공한 뒤, 계약 기준으로 최종 승인받는 과정임.

## 깊이 이해
- **배경·문제의식**: 시스템 테스트가 완료되어도 현장 데이터, 사용자 습관, 고객 업무 규칙이 다르면 결함과 불만이 발생함. 알파는 내부 통제 환경, 베타는 실제 사용자 제한 환경, 인수는 고객 승인 기준을 확인함.
- **작동 원리**: 알파 테스트는 개발사 내부 QA와 업무 담당자가 결함을 찾고, 베타 테스트는 제한된 외부 사용자가 실제 환경에서 피드백을 제공함. 인수 테스트는 계약·요구사항 기반 수용 기준을 만족하는지 확인함.
- **비유**: 공연 리허설, 초대 관객 시사회, 정식 개막 전 최종 승인 심사의 차이임.
- **구체 예시**: 모바일 앱은 사내 100명 알파, 지역별 5,000명 베타, 고객 UAT 30개 시나리오 통과 후 정식 출시함.
- **흔한 오해·주의점**: 베타 테스트는 무작위 공개가 아님. 대상자, 기간, 피드백 채널, 개인정보 처리, release criteria를 통제해야 함.

## 연결 개념
- UAT: 사용자가 업무 요구사항 충족 여부를 승인하는 테스트
- Release Criteria: 출시 허용을 판단하는 결함·성능·업무 기준
- Defect Triage: 발견 결함의 심각도와 출시 영향 판단

# 📝 【답안용】 시험 답안 템플릿

> 목적: 시험장에서 25분에 그대로 쓰는 답안 양식. 작성방식(추상표현 금지·수치·도식·문제유형 전환)을 엄격히 지킨다.
> 핵심: 알파·베타·인수 테스트는 테스트 대상, 환경, 승인 주체, release criteria가 다른 출시 검증 단계임.

## 핵심 인사이트 (3줄 요약)

> 1. **본질**: 알파는 내부 통제 검증, 베타는 제한 사용자 실환경 검증, 인수 테스트는 고객 승인 기준 검증임.
> 2. **가치**: 출시 전 결함, 사용성, 업무 수용성을 단계적으로 확인해 운영 반영 리스크를 낮춤.
> 3. **판단 포인트**: 대상자, 환경, 수용 기준, 결함 심각도, go/no-go 기준을 구분해야 함.

## 출제 의도 및 답안 포인트

| 출제 의도 | 반드시 짚을 핵심 | 감점 회피 포인트 |
|:---|:---|:---|
| 테스트 단계 차이 확인 | alpha, beta, acceptance 목적·주체 | 이름만 나열하고 승인 기준 누락 |
| 출시 판단 역량 확인 | release criteria, defect triage | 베타를 홍보 행사로 설명 |
| 고객 수용성 확인 | UAT, 계약 요구사항, sign-off | 시스템 테스트와 인수 테스트 혼동 |

> 요약: 이 문제는 출시 전 검증 단계를 승인 주체와 수용 기준 중심으로 비교해야 한다.

---

## Ⅰ. 개요 및 필요성

알파·베타·인수 테스트는 제품 출시 전 내부, 제한 사용자, 고객 관점에서 수행하는 검증 단계이다. 기능 테스트 통과만으로는 실제 사용 환경과 고객 업무 적합성을 보장할 수 없다. 따라서 단계별 대상과 release criteria를 구분해 출시 판단 근거를 확보한다.

---

## Ⅱ. 구조 및 구성요소

```text
System Test 완료 -> Alpha Test -> Defect Fix
Alpha Pass -> Beta Test -> Feedback/Triage
Beta Pass -> Acceptance Test(UAT) -> Sign-off/Release
```

| 구성요소 | 역할 | 특이사항 |
|:---|:---|:---|
| Alpha Test | 내부 QA·업무 담당자 검증 | 통제 환경, 초기 결함 제거 |
| Beta Test | 제한 외부 사용자 실환경 검증 | telemetry, feedback 채널 |
| Acceptance Test | 고객·발주자 승인 검증 | 계약 요구사항, UAT sign-off |
| Release Criteria | 출시 허용 기준 | P1 0건, P2 5건 이하 |

> 요약: 세 테스트는 시스템 테스트 이후 출시 전 위험을 내부, 외부 사용자, 고객 승인 관점에서 단계적으로 줄인다.

---

## Ⅲ. 동작원리 및 흐름도

```text
출시 후보 빌드 -> Alpha 실행 -> 결함 수정
-> Beta 대상 배포 -> 피드백 수집/분류
-> UAT 실행 -> 승인/보류 판정
```

| 단계 | 처리 내용 | 검증 기준 |
|:---:|:---|:---|
| 1 | release candidate와 테스트 범위 확정 | build freeze, scope 명시 |
| 2 | 내부 알파 테스트 수행 | P1 결함 0건 |
| 3 | 제한 사용자 베타 배포와 telemetry 수집 | crash-free session 99% |
| 4 | 고객 UAT 시나리오 실행 | 승인 시나리오 100% 통과 |
| 5 | go/no-go 회의와 release sign-off | 잔여 위험 승인 기록 |

> 요약: 출시 후보는 알파 결함 제거, 베타 실환경 피드백, 인수 승인 순서로 release criteria를 통과해야 한다.

---

## Ⅳ. 특징

| 구분 | 알파 테스트 | 베타 테스트 | 인수 테스트 |
|:---|:---|:---|:---|
| 수행 주체 | 개발사 QA, 내부 사용자 | 제한 외부 사용자 | 고객, 발주자, 현업 |
| 환경 | 통제된 내부 환경 | 실제 또는 준운영 환경 | 계약·업무 기준 환경 |
| 목적 | 중대 결함 조기 제거 | 사용성·호환성·실환경 검증 | 수용 기준 충족 확인 |
| 판정 기준 | P1 0건 | crash-free 99%, 피드백 triage | UAT 100%, sign-off |

> 요약: 알파는 내부 결함 제거, 베타는 실사용 피드백, 인수는 고객 승인이라는 판정 기준이 다르다.

## Ⅴ. 심화 비교 및 적용 판단

| 비교 축 | 기존/대안 | 본 키워드 | 선택 기준 |
|:---|:---|:---|:---|
| 구조 | 시스템 테스트 후 즉시 출시 | alpha-beta-acceptance 단계화 | 사용자 규모 1만명 이상 서비스 |
| 비용/성능 | 출시 후 결함 대응 | 사전 피드백과 결함 triage | P1 장애 비용이 큰 업무 |
| 운영/위험 | 실제 환경 결함 운영 유출 | 베타 telemetry로 조기 탐지 | 디바이스·브라우저 다양성 큰 경우 |
| 계약/승인 | 내부 품질 판단 | UAT sign-off | 발주·납품 계약 시스템 |

> 요약: 단계별 출시 검증은 사용자 영향과 계약 승인 요구가 클수록 필요성이 커진다.

| 리스크 | 원인 | 대응 방안 | 확인 지표 |
|:---|:---|:---|:---|
| 베타 품질 사고 | 대상자와 기능 범위 과다 | feature flag, cohort 제한 | crash-free 99% |
| 개인정보 노출 | 실제 사용자 데이터 수집 | 동의, masking, retention 정책 | privacy incident 0건 |
| 승인 지연 | UAT 기준 불명확 | acceptance criteria 사전 합의 | UAT pass 100% |
| 피드백 혼선 | 채널 분산 | defect triage board 단일화 | triage SLA 24시간 |

> 요약: 출시 전 검증 리스크는 대상 범위, 개인정보, 수용 기준, 피드백 채널을 통제해야 한다.

| 점검 항목 | 목표 기준 | 측정 방법 |
|:---|:---|:---|
| 결함 상태 | P1 0건, P2 5건 이하 | defect tracker |
| 베타 품질 | crash-free session 99% 이상 | telemetry, analytics |
| 사용자 피드백 | high feedback 24시간 triage | feedback board |
| 인수 승인 | UAT scenario 100% 통과 | sign-off report |

> 요약: release criteria는 결함 심각도, crash-free 비율, 피드백 처리, UAT 승인으로 구성한다.

## Ⅵ. 실무 적용 및 결론

**적용 방안 3개 (필수 — 단계별 또는 항목별):**
1. 알파 단계에서 내부 QA와 현업 대표가 P1 0건, P2 5건 이하 기준으로 release candidate를 검증함.
2. 베타 단계에서 feature flag와 cohort 5% 제한 배포를 적용하고 telemetry, crash report, feedback form을 단일 triage board로 수집함.
3. 인수 단계에서 계약 요구사항별 UAT 시나리오와 증적을 연결하고 고객 sign-off 없이는 운영 전환을 차단함.

**결론 (2줄):**
- 기술사 판단: 대규모 사용자 서비스는 베타를, 납품·계약 시스템은 인수 테스트를 release gate로 두고 알파는 모든 출시 후보에 적용함.
- 향후 방향: 원격 telemetry, feature flag, progressive delivery와 결합해 출시 검증이 지속적 운영 검증으로 확장됨.
