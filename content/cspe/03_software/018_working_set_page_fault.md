## Ⅰ. 개요
- **정의**: 특정 시간 윈도우 내에서 프로세스가 참조하는 페이지 집합
- **배경/필요성**: 프로세스에 적정 프레임을 할당하지 않으면 Thrashing이 발생하므로 실제 사용 페이지 규모를 파악할 기준이 필요함
- **비유**: 요리사가 지금 만들고 있는 요리에 쓰는 재료만 조리대에 올려놓는 것과 유사함

| 출제 의도 | 반드시 짚을 핵심 | 감점 회피 포인트 |
|:---|:---|:---|
| Thrashing 예방 원리 이해 | 윈도우 크기(delta)와 WSS 관계 | 페이지 교체(017 참조)와 연계하여 설명 필요 |

> 요약: 시간 윈도우 기반으로 프로세스 활성 페이지 집합을 정의하여 프레임 할당의 기준을 제공함

## Ⅱ. 구성요소
```text
Time Window (delta)
|<---------------------------->|
| page references: A B A C B D |
|                              |
Working Set = {A, B, C, D}  --> WSS = 4
```

| 구성요소 | 설명 | 비유 |
|:---|:---|:---|
| Window Size (delta) | 워킹셋을 측정하는 시간 윈도우 크기 | 조리대 위 재료 유효 시간 |
| WSS (Working Set Size) | 윈도우 내 고유 참조 페이지 수 | 조리대에 올라간 재료 종류 수 |
| Page Fault Rate | 단위 시간당 페이지 폴트 발생 빈도 | 재료를 창고에서 가져오는 횟수 |
| Frame Allocation | 프로세스에 할당된 물리 프레임 수 | 조리대 크기 |

> 요약: 윈도우 크기, WSS, 폴트율, 프레임 할당이 워킹셋 모델의 핵심 요소임

## Ⅲ. 절차
```text
참조 기록 수집 --> WSS 계산 --> 프레임 할당 조정 --> Thrashing 모니터링
```
- 1단계: 프로세스의 페이지 참조 기록을 시간 윈도우(delta) 단위로 수집
- 2단계: 윈도우 내 고유 페이지 수를 집계하여 WSS 산출
- 3단계: WSS 이상의 프레임을 해당 프로세스에 할당 (부족 시 프로세스 일시 중단)
- 4단계: 페이지 폴트율을 지속 모니터링하여 할당량 동적 조정

> 요약: 참조 수집-WSS 산출-프레임 할당-폴트율 모니터링 4단계로 운영함

## Ⅳ. 문제점
- 윈도우 크기 설정 난이도: delta가 너무 크면 과다 할당, 너무 작으면 WSS 과소 추정 — 적정값 결정 곤란
- 측정 오버헤드: 참조 기록 추적에 인터럽트·타이머 사용 — 런타임 성능 저하
- 동적 변동성: 프로그램 실행 단계별 지역성 변화 — 고정 delta로는 변동 추적 한계

> 요약: 윈도우 크기 결정, 측정 오버헤드, 동적 변동 추적이 주요 문제임

## Ⅴ. 개선방안
1. 단기: Page Fault Frequency(PFF) 기반 적응형 프레임 할당으로 delta 의존도 완화
2. 중기: 참조 비트 샘플링 방식으로 정확도 유지하며 측정 오버헤드 감소
3. 장기: 실행 단계 자동 감지(phase detection) 기반 동적 윈도우 크기 조정

> 요약: PFF 적응 할당, 샘플링 최적화, 단계 감지 순으로 개선 필요

## Ⅵ. 전망
- 발전 방향: 컨테이너·VM 환경에서 워킹셋 기반 메모리 오토스케일링이 확산 중임
- 기술사적 판단: 메모리 자원 효율화가 클라우드 비용에 직결되므로 WSS 추정 정밀도가 중요해질 전망임
- 기술사 제언: 가상화 환경에서 게스트-호스트 간 WSS 정보를 공유하는 협력적 메모리 관리 체계를 구축할 필요
