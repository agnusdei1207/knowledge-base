# 📖 【암기용】 개념 완전 이해

> 목적: 이 개념을 처음 보는 사람도 완벽히 이해하게 만든다. 시험 답안 양식이 아니라, 이해를 위한 친절한 설명이다.

## 한눈에
- **개요**: **페이지 폴트(Page Fault)**는 CPU가 참조한 페이지가 물리 메모리에 없을 때(Valid 비트=0) MMU가 발생시키는 인터럽트이며, **워킹 셋(Working Set)**은 이 폴트를 억제하기 위해 프로세스가 최근 일정 시간(Δ) 동안 실제로 참조한 고유 페이지 집합을 수학적으로 정의해 그만큼의 프레임을 보장하는 모델이다.
- **왜 필요한가**: 페이지 폴트가 나면 디스크 I/O 때문에 접근 시간이 수만 배로 늘어난다. 이 지연을 시스템이 감당할 수 있는 폴트율의 한계를 알아야 하고(EAT 공식), 애초에 폴트를 줄이려면 "이 프로세스가 최소한 몇 개의 프레임을 쥐고 있어야 하는가"를 정량화해야 한다(워킹 셋).
- **핵심 직관**: 폴트 하나의 비용은 RAM 접근 대비 수만~수십만 배로 크므로, 폴트율을 극한까지 낮추는 것이 시스템 성능의 핵심 레버이며, 워킹 셋은 그 레버를 당기는 구체적인 방법이다.

## 핵심 용어 정리 (내부에 등장하는 것들)

| 용어 | 의미 | 비유 |
|:---|:---|:---|
| 페이지 폴트 (Page Fault) | 참조 페이지가 RAM에 없어 발생하는 하드웨어 인터럽트 | 서가에 없는 책을 찾으러 감 |
| Valid/Invalid 비트 | 페이지 테이블 엔트리가 유효한 매핑인지 표시 — 0이면 폴트 트리거 | 재고 있음/없음 표시 |
| Major (Hard) Fault | 디스크에서 실제로 읽어와야 하는 폴트 — 병목의 본체 | 창고까지 가서 물건을 가져옴 |
| Minor (Soft) Fault | 이미 파일 캐시에 있고 페이지 테이블만 갱신하면 되는 폴트 | 옆 서랍에서 바로 꺼냄 |
| EAT (Effective Access Time) | 폴트 확률까지 반영한 평균 메모리 접근 시간 | 실제 체감 대기 시간 |
| 워킹 셋 (Working Set), WS(t, Δ) | 시각 t 기준 최근 Δ 동안 참조된 고유 페이지 집합 | 최근에 자주 꺼내 쓴 물건 세트 |
| 윈도우 크기 (Δ) | 워킹 셋을 계산하는 관찰 구간 길이 — 크기 선택이 정확도를 좌우 | 얼마나 최근까지 되짚어볼지 정하는 기간 |

## 깊이 이해

### 페이지 폴트가 나면 정확히 무슨 일이 일어나는가 (처리 절차)
1. CPU가 가상 주소를 참조 → MMU가 페이지 테이블에서 Valid 비트=0을 확인 → 트랩 발생, 제어권이 커널로 이동한다.
2. 커널이 이 참조가 합법적인지 검사한다(불법 접근이면 Segmentation Fault로 프로세스를 종료한다).
3. 빈 프레임을 확보한다(없으면 페이지 교체 알고리즘이 발동한다 — 017 참조).
4. 디스크에서 해당 페이지를 읽어온다. 이 대기 시간 동안 프로세스는 Blocked 상태로 전환되고, 스케줄러는 다른 프로세스에 CPU를 넘긴다.
5. 읽기가 끝나면 페이지 테이블을 갱신한다(Valid=1, 프레임 번호 기록).
6. 트랩이 걸렸던 명령어를 처음부터 재실행한다.

### EAT 공식으로 폴트율의 파괴력을 계산해보기 (수치)
- RAM 접근 시간을 200ns, 폴트 처리 시간(디스크 I/O)을 8ms(8,000,000ns)라 하면 EAT = (1-p)×200 + p×8,000,000 = 200 + 7,999,800p (p는 폴트율)다.
- p = 0.001(1,000번에 1번 폴트)이면 EAT ≈ 8,200ns — 원래보다 약 41배 느려진다.
- 성능 저하를 10% 이내(EAT < 220ns)로 묶으려면 200 + 7,999,800p < 220 → p < 0.0000025, 즉 40만 번 접근에 폴트가 1번 이하여야 한다.
- 이 계산이 보여주는 것: 폴트율이 조금만 높아져도 시스템 체감 속도가 디스크 속도로 끌려 내려간다. 그래서 폴트를 원천적으로 줄이는 워킹 셋 모델이 필요해진다.

### 워킹 셋을 수식으로 어떻게 정의하는가 (Δ 윈도우, 수치 예)
- WS(t, Δ) = 시각 [t-Δ, t] 구간 동안 참조된 서로 다른 페이지 번호들의 집합이다.
- 예: 참조열 2, 6, 1, 5, 7, 7, 7, 7, 5, 1에서 Δ=10이면 워킹 셋 = {1, 2, 5, 6, 7}, 크기(WSS)=5다. 윈도우가 오른쪽으로 이동해 7, 7, 5, 1, 6, 2, 3, 4, 1, 2를 보면 워킹 셋 = {1, 2, 3, 4, 5, 6, 7}, 크기=7로 늘어난다 — 프로세스가 새로운 국면(Phase)에 진입해 더 많은 페이지를 활발히 쓰고 있다는 뜻이다.
- OS는 모든 프로세스의 WSS 합(ΣWSS)이 물리 프레임 총량 M을 넘지 않는 동안만 새 프로세스를 받아들이고(Admission), ΣWSS > M이 되면 프로세스 하나를 통째로 스왑 아웃한다.

### Δ를 어떻게 잡아야 하는가 (딜레마)
- Δ가 너무 작으면(예: 최근 10번 참조만 봄) 반복문 한 바퀴 전체를 담지 못해 워킹 셋이 과소 추정되고 폴트가 늘어난다.
- Δ가 너무 크면 이미 안 쓰는 과거 페이지까지 워킹 셋에 남아 프레임을 낭비한다.
- 정답은 프로그램의 반복 주기(루프 크기)에 달려 있어 고정할 수 없다. 실무에서는 이 관찰 비용 자체가 부담스러워, 참조 비트를 타이머로 주기적으로 샘플링하는 근사 구현을 쓰거나, 아예 워킹 셋 대신 폴트율만 보는 PFF(018_thrashing_working_set_pff.md 참조)로 대체하는 경우가 많다.

### 흔한 오해
- 워킹 셋은 고정된 목록이 아니라 시간에 따라 계속 이동하는 창이다. 프로세스가 함수 A를 실행하다 함수 B로 넘어가면 워킹 셋도 서서히 새 페이지 집합으로 교체된다.
- Major Fault와 Minor Fault를 뭉뚱그리면 안 된다. Minor Fault(파일 캐시 히트, 페이지 테이블만 갱신)는 사실상 비용이 거의 없고, 시스템을 위협하는 것은 디스크까지 가는 Major Fault다.

> 핵심: 이 시험은 정보를 많이 나열하는 시험이 아니라, 문제 신호어에서 출제자 의도를 읽고 핵심 논점을 선별해 쓰는 시험이다.

## 핵심 인사이트 (3줄 요약)

> 1. **본질**: 페이지 폴트는 가상 메모리 미적재 시 발생하는 필수 인터럽트이며, 워킹 셋은 이 폴트율을 억제하기 위해 보장해야 하는 참조 지역성 기반의 최소 프레임 집합이다.
> 2. **가치**: 스케줄러가 워킹 셋 크기(추정치)의 총합을 물리 램(RAM) 이내로 통제하여, 시스템 마비 현상(스레싱, Thrashing)을 선제적으로 예방(Swap out)한다.
> 3. **판단 포인트**: 페이지 폴트 처리의 막대한 디스크 I/O 오버헤드 구조를 분해하고, 시간에 따라 동적으로 이동하는 워킹 셋 윈도우($\Delta$)의 적정 사이즈 튜닝 한계를 짚어야 한다.

## 출제 의도 및 답안 포인트

| 출제 의도 | 반드시 짚을 핵심 | 감점 회피 포인트 |
|:---|:---|:---|
| 페이지 폴트 처리 메커니즘과 지연(Latency)의 실체 | Valid-Invalid 비트 검사 + 하드디스크 Swap I/O | 폴트를 램(RAM) 접근 지연으로만 착각하는 서술 (디스크 I/O가 본질) |
| 스레싱 방지를 위한 워킹 셋 모델의 제어 철학 | $WS(t, \Delta)$ 공식과 프로세스 강제 Swap-out 룰 | 워킹 셋 크기가 프로그램 내내 고정된다고 적는 정적 사고 (시간에 따라 동적 갱신됨) |

> 요약: 폴트(Fault)는 무지에 대한 벌금(디스크 읽기)이다. 잦은 벌금으로 파산(스레싱)하지 않으려면, 방금 썼던 페이지 집합(워킹 셋)만큼은 무조건 램에 묶어두는 독점권이 필요하다.

## Ⅰ. 개요 및 필요성

- 정의: 페이지 폴트는 CPU가 참조한 논리 주소 페이지가 물리 메모리에 없을 때 발생하는 MMU 인터럽트이며, 워킹 셋은 프로세스가 특정 시간 동안 빈번하게 참조하는 페이지들의 동적 집합
- 배경: 제한된 프레임을 너무 많은 프로세스가 쪼개어 쓰면, 각 프로세스가 본연의 코드를 1사이클 돌리기조차 벅차 잦은 폴트와 문맥 교환 오버헤드만 폭발
- 필요성: 시스템 전체의 CPU 이용률 붕괴(Thrashing)를 막기 위해, 프로세스의 지역성 덩어리(워킹 셋) 크기를 통째로 보장할 수 없다면 아예 실행을 유보(Suspend)하는 강제 통제력 확보 필수

## Ⅱ. 페이지 폴트 (Page Fault) 처리 아키텍처 및 페널티

```text
[ CPU 가상 주소 참조 ] -> [ MMU 장부(Page Table) 확인 ] -> Valid Bit = 0 (🚨 Fault 발생)
                                        | (OS 커널 모드 진입)
                 +----------------------+----------------------+
                 | 1. 문맥 저장 (CPU -> PCB)                    |
                 | 2. 디스크에서 해당 페이지 읽기 명령 (I/O)       | -> 🐢 약 10,000,000 ns (10ms) 대기
                 | 3. 프로세스는 Blocked 상태로 대기 큐 이동       |    (일반 RAM 읽기 대비 10만 배 느림)
                 | 4. 읽기 완료 후 장부 갱신 (Valid=1, 프레임 매핑)|
                 +---------------------------------------------+
                                        | (Ready 큐 복귀)
[ 프로세스 재개 (다시 같은 명령어 재시도) ] -> 🚀 RAM 접근 (100 ns)
```

| 폴트 유형 분류 | 발생 원인 | 성능에 미치는 아키텍처 타격 |
|:---|:---|:---|
| **Major (Hard) Fault** | 진짜 램에 없어서 디스크(스왑)에서 퍼 올려야 함 | 기계식 암(Arm) 또는 플래시 읽기 지연. **치명적 병목 (블로킹)** |
| **Minor (Soft) Fault** | 디스크에서 이미 파일 캐시(Page Cache)로 올라와 있으나 내 장부만 갱신 안 됨 | 램 복사만 하면 되므로 오버헤드 거의 없음 (히트 율 양호) |

> 요약: 폴트가 터지면 CPU는 그 찰나에 100만 번의 덧셈을 할 수 있는 시간을 디스크 헤더가 징징 돌아가는 소리를 들으며 낭비하게 된다.

## Ⅲ. 워킹 셋 모델: 수학적 정의와 메모리 제어(Admission Control)

워킹 셋은 윈도우 크기($\Delta$)라는 타임머신 창문으로 과거를 들여다보는 철학이다.
* 정의 수식: $WS(t, \Delta) = [t-\Delta, t]$ 시간 동안 참조된 고유한 페이지 번호들의 집합

| 스케줄링 제어 룰 | 판단 기준 로직 | 시스템 스레싱(Thrashing) 방어 메커니즘 |
|:---|:---|:---|
| **Admission (승인 및 적재)** | `Σ(모든 프로세스 WS 크기) < 전체 물리 램 크기` | 모든 프로세스에게 그들이 요구하는 밥그릇(WS)을 다 주고도 램이 남음. 쾌적한 가동 지속 |
| **Suspend (강제 스왑 아웃)** | `Σ(모든 프로세스 WS 크기) > 전체 물리 램 크기` | 방 뺄 놈을 하나 고름(Victim 프로세스). 그놈을 **아예 하드디스크로 재우고(Swap Out)**, 걔가 뱉은 프레임을 남은 놈들에게 분배 |

> 요약: "다 같이 조금씩 굶으면 다 같이 죽는다(스레싱). 밥(램)이 모자라면 확실하게 한 놈을 밖으로 쫓아내고 남은 놈들 배부터 채워라." 이것이 워킹 셋의 냉혹한 철학이다.

---

## Ⅳ. 극복해야 할 시스템 리스크 및 튜닝 방안 (Delta의 딜레마)

워킹 셋의 완벽함은 윈도우 사이즈($\Delta$)를 어떻게 잡느냐에 달렸으나, 이는 영원한 딜레마다.

| 윈도우 크기($\Delta$) 한계 | 런타임 결과 및 병목 현상 | 아키텍처 대응 방안 (실무 튜닝 대체재) |
|:---|:---|:---|
| $\Delta$가 너무 작을 때 | 프로세스의 지역성(필수 페이지)을 다 담지 못해 폴트 폭주 | 윈도우 갱신이라는 거대한 하드웨어 오버헤드를 포기하고, OS는 단순히 폴트 발생 '비율'만 측정하는 **PFF (Page Fault Frequency)** 알고리즘을 실무 채택 |
| $\Delta$가 너무 클 때 | 과거에 썼고 이제 안 쓸 쓰레기 페이지까지 껴안아 램 초토화 | JVM 환경에서는 가비지 컬렉터(GC)가 주기적으로 참조 잃은 쓰레기 객체를 비워내 애플리케이션 레벨의 가상 워킹 셋 슬림화 수행 |

> 요약: 매 1나노초마다 메모리를 찌를 때 장부에 타임스탬프를 갱신하는 짓(순수 Working Set)은 오버헤드가 극심해 상용 OS 탑재가 불가능했다. 현업은 비율 통제(PFF)로 꼼수 우회한다.

## Ⅴ. 실무 적용 방안 및 결론

**적용 방안 3개:**
1. [OS 모니터링 및 성능 튜닝] 리눅스 서버 운영 시 `vmstat` 또는 `sar` 명령어를 통해 `pgpgin/pgpgout`(스왑 I/O) 지표가 지속적으로 높게 치솟을 경우 Major Page Fault 폭주로 인한 스레싱으로 간주, 노드 메모리 2배 증설 또는 OOM 스코어 튜닝
2. [Redis 워킹 셋 램핏(RAM-fit) 전략] 인메모리 DB(Redis, Memcached) 아키텍처 설계 시, 전체 빅데이터 수십 TB를 램에 올릴 수 없으므로, 80/20 파레토 법칙에 기반해 20%의 자주 읽히는 핫 데이터(Hot Data) 덩어리를 애플리케이션의 런타임 워킹 셋으로 산정하여 물리 메모리 한도 사이징(Sizing)
3. [GC 스레싱 원천 봉쇄 (JVM 튜닝)] Java 백엔드 애플리케이션 기동 시 워킹 셋(Hot Object)이 힙 메모리에 완전히 안착할 때까지 Minor GC가 폭발하는 콜드 스타트를 막기 위해, `-Xms`(초기)와 `-Xmx`(최대)를 동일하게 부여하여 OS 프레임을 선점 강제화

**결론:**
- 기술사 판단: 페이지 폴트는 가상 메모리가 부리는 거짓말(무한 램)의 필연적 대가(I/O 지연)다. 워킹 셋은 이 대가를 감당하기 위해 프로세스의 '지역성'이라는 성향을 파악하고, 무리한 다중 프로그래밍을 쳐내어 시스템의 안정성을 사수하는 최후의 방어선이다.
- 향후 방향: 최근 클라우드 및 컨테이너(Docker/K8s) 환경에서는 Cgroup 제어를 통해 호스트 OS 레벨의 전역 스레싱 방지보다, 컨테이너별로 램 쿼터(Quota)를 격리하여 자기 밥그릇 안에서만 폴트가 나도록(국부 교체) 가두리 양식(Isolation)을 강화하는 방향으로 진화하고 있다.
