# 📖 【암기용】 개념 완전 이해

## 한눈에
- **개요**: 프로세스가 일정 시간 동안 집중적으로 참조하는 페이지들의 집합인 **워킹 셋(Working Set)**을 메모리에 보장하여, 참조 실패 시 발생하는 **페이지 부재(Page Fault)**와 스레싱을 막는 가상 메모리 최적화 기법.
- **왜 필요한가**: 시험공부할 때 1~3단원 책이 집중적으로 필요한데, 책상이 좁다고 1단원을 치우면 바로 다시 찾게 되어 공부 흐름이 뚝뚝 끊긴다(Page Fault 폭증). 지금 집중적으로 보는 책들(워킹 셋)만큼은 무조건 책상에 올릴 공간을 확보해줘야 한다.
- **핵심 직관**: 
  - **지역성(Locality)**: 사람은 방금 쓴 물건 근처를 또 찾는 습성이 있다.
  - **워킹 셋**: 그 '최근에 쓴 물건들의 묶음'을 의미한다.
  - **페이지 폴트**: 필요한 물건이 책상에 없어서 서랍(디스크)에 다녀오는 수고. 워킹 셋만 보장해주면 이 수고가 획기적으로 준다.

## 핵심 용어 정리

| 용어/표기 | 의미 | 비유·예 |
|:---|:---|:---|
| **지역성 (Locality)** | 실행 중인 프로세스가 특정 시간, 특정 구역의 데이터만 집중 참조하는 현상 (시간/공간 지역성) | "루프(for문)를 도는 동안 같은 코드만 계속 읽는 특성" |
| **워킹 셋 (Working Set, $WS(t, \Delta)$)** | 시점 $t$에서 과거 $\Delta$ 시간 윈도우 동안 참조된 고유한 페이지들의 집합 | "최근 10분 동안 꺼내 본 책들의 목록" |
| **페이지 폴트 (Page Fault)** | CPU가 호출한 가상 메모리 페이지가 물리 메모리 프레임에 적재되어 있지 않은 상태 | "필요한 책이 책상에 없어 디스크(창고)로 다녀와야 함" |
| **워킹 셋 윈도우 ($\Delta$)** | 페이지 참조 기록을 되돌아보는 시간적 간격 | "최근 몇 분 동안의 기록을 유효하게 볼 것인가의 기준치" |

## 깊이 이해
- **배경·문제의식**: 고정 할당 방식(모든 프로세스에 똑같이 프레임 10개씩 분배)은 어떤 프로그램은 메모리가 남아돌고 어떤 프로그램은 부족해 스레싱이 발생한다. 프로세스마다 그때그때 필요한 메모리 양이 다르므로 '동적'으로 할당해야 한다.
- **작동 원리 (워킹 셋 모델)**:
  1. OS는 각 프로세스의 최근 $\Delta$ 시간 동안의 참조 페이지를 추적하여 $WS$ 크기를 계산한다.
  2. 시스템에 남은 여유 프레임이 프로세스들의 전체 $WS$ 합보다 크면, 각 프로세스에 $WS$ 크기만큼 프레임을 할당한다.
  3. 여유가 부족하면 덜 중요한 프로세스 하나를 완전히 디스크로 쫓아내고(Swap-out, Suspend), 남은 프로세스들의 $WS$를 확실히 보장한다.
- **구체 예시**: 윈도우($\Delta$)를 최근 5번의 메모리 참조로 설정. 참조가 `[1, 2, 1, 3, 2]`라면 현재 워킹 셋은 `{1, 2, 3}`이다. 즉 이 프로세스는 최소 프레임 3개를 쥐어줘야 원활히 돌아간다. 윈도우가 넘어가 새 참조 패턴이 들어오면 $WS$ 크기도 유연하게 변한다.
- **흔한 오해·주의점**: 워킹 셋 알고리즘이 완벽해 보이지만, "과거 $\Delta$ 시간 동안 참조한 페이지"를 매 클럭마다 추적하고 계산하는 것은 엄청난 H/W 오버헤드를 유발한다. 따라서 실무에서는 정교한 워킹 셋 모델보다 Page Fault 횟수 자체를 모니터링하는 **PFF (Page Fault Frequency)** 모델을 근사 기법으로 더 많이 쓴다.

## 연결 개념
- (015 프로세스 스레싱 참조) 워킹 셋을 보장하지 못해 시스템이 붕괴되는 현상
- (017 페이지 교체 참조) 워킹 셋 내부가 아닌 페이지를 우선 방출하는 원리

# 📝 【답안용】 시험 답안 템플릿

## 핵심 인사이트 (3줄 요약)

> 1. **본질**: 워킹 셋은 프로세스의 지역성(Locality)을 수치화한 동적 메모리 요구량 모델이며, 페이지 폴트는 이 요구량이 충족되지 않을 때 발생하는 디스크 스왑 병목이다.
> 2. **가치**: 프로세스마다 필요한 최소 프레임 수를 동적으로 할당 보장하여, 스레싱(Thrashing)을 방지하고 다중 프로그래밍 정도(MPD)를 안전하게 최적화한다.
> 3. **판단 포인트**: 순수 워킹 셋 모델은 추적 오버헤드가 크므로, 페이지 부재 빈도를 임계치로 통제하는 PFF(Page Fault Frequency) 방식과 트레이드오프를 고려해 적용해야 한다.

## 출제 의도 및 답안 포인트

| 출제 의도 | 반드시 짚을 핵심 | 감점 회피 포인트 |
|:---|:---|:---|
| 가상 메모리 동적 할당 원리 및 스레싱 통제 모델 이해 | 지역성 기반의 워킹 셋 정의 수식 $WS(t, \Delta)$, 프레임 할당 메커니즘 | 워킹 셋 크기가 고정되어 있다고 서술하는 오류 (동적 변화 명시) |
| 오버헤드를 고려한 실무 적용 기법 판단 | 워킹 셋 추적 오버헤드와 그 대안인 PFF(페이지 부재 빈도) 알고리즘 비교 | Page Fault를 무조건 나쁜 에러로 취급 (정상적인 요구 페이징 메커니즘임) |

> 요약: 지역성 원리에 기반한 워킹 셋의 동적 산출 구조를 제시하고, 그 구현 오버헤드를 극복하기 위한 실용적 대안(PFF)과의 비교 판단을 도출해야 한다.

## Ⅰ. 개요 및 필요성

- 개요: 워킹 셋 모델은 프로세스가 최근 참조한 페이지 집합을 물리 메모리에 동적으로 유지하여 페이지 폴트(Page Fault)를 최소화하는 프레임 할당 정책
- 배경: 프로세스에 고정된 프레임을 할당하면 단계별 메모리 요구량 변화를 반영하지 못해 스레싱(부족) 또는 메모리 낭비(과다) 발생
- 필요성: 시스템 전체의 가용 프레임을 프로세스별 지역성 집합 크기에 맞춰 유연하게 재분배하여 CPU 이용률과 시스템 안정성을 동시 확보 필수

---

## Ⅱ. 구조 및 구성요소

```text
[CPU 메모리 참조] -> [시간 윈도우(\Delta) 내 고유 페이지 추적] -> Working Set 도출
                                                             |
OS 스케줄러 <- [총 가용 프레임 >= $\Sigma WS_{i}$ 검증] <- [할당 프레임 수 동적 조정]
```

| 구성요소 | 역할 | 특이사항 |
|:---|:---|:---|
| 지역성 (Locality) | 워킹 셋 모델의 근본 전제 (시간적/공간적) | 특정 구역의 페이지가 집중적으로 재참조됨 |
| 윈도우 크기 ($\Delta$) | 워킹 셋을 계산하는 과거 참조 이력의 기준 간격 | $\Delta$가 너무 크면 메모리 낭비, 작으면 폴트 폭증 |
| 할당 제어기 (OS) | 시스템 전체 여유 프레임과 모든 프로세스의 총 WS 크기를 비교 통제 | 여유 부족 시 특정 프로세스를 Suspend하여 남은 WS 보장 |

> 요약: 워킹 셋은 시간 윈도우($\Delta$)를 통해 지역성을 수학적 집합으로 도출하고, OS는 이 집합의 합계가 물리 메모리를 초과하지 않도록 통제한다.

---

## Ⅲ. 동작원리 및 흐름도

```text
프로세스 진행 -> 최근 $\Delta$ 시간 동안의 페이지 참조 기록 갱신 -> WS 집합 추출
  / 가용 프레임 > 총 WS 크기 -> 각 프로세스별 WS 집합 100% 메모리 보장 적재 -> Page Fault 최소화
  / 가용 프레임 < 총 WS 크기 -> 우선순위 낮은 프로세스 Swap-out(중단) -> 남은 프로세스 WS 보장 (스레싱 차단)
```

- 1단계 [참조 추적]: OS는 타이머 인터럽트와 참조 비트를 결합하여 시점 $t$ 기준 과거 $\Delta$ 동안의 참조 페이지 식별
- 2단계 [워킹 셋 갱신]: 시간이 지남에 따라 참조 윈도우가 이동하며 WS 집합에서 제외된 페이지는 프레임 회수 대상이 됨
- 3단계 [할당 및 폴트 제어]: 프로세스가 필요한 WS만큼 프레임을 동적 할당하여, 해당 영역 내 연산 시 Page Fault 발생 억제
- 4단계 [과부하 통제]: 메모리가 절대 부족할 경우, 프로세스를 일부 중지시켜 시스템 전체의 스레싱 진입을 물리적으로 차단

> 요약: 프로세스의 상태 전이(Phase Transition)에 따라 워킹 셋 크기는 팽창과 수축을 반복하며, 프레임 할당량도 이에 연동된다.

## Ⅳ. 비교 (Working Set vs PFF)

| 비교 축 | Working Set 알고리즘 | PFF (Page Fault Frequency) 알고리즘 | 선택 기준 |
|:---|:---|:---|:---|
| 제어 기준 | 과거 $\Delta$ 시간 동안 참조된 페이지 자체 추적 | 주기적인 페이지 부재(Fault) 발생 횟수(비율) | 정밀한 지역성 반영 vs 제어 복잡도 |
| 프레임 할당 | WS 크기가 팽창/수축함에 따라 직접 할당 | 폴트율 상한 도달 시 프레임 증가, 하한 시 회수 | 오버헤드와 직관성 |
| 구현 오버헤드 | 모든 참조 기록과 타임스탬프 갱신 필요 (매우 큼) | 부재 발생 시점과 참조 비트만 확인 (매우 낮음) | 현대 OS 실무 적용 가능성 |
| 한계점 | 과거 예측이 미래를 100% 보장 불가, $\Delta$ 설정 난해 | 빈도만 보므로 어떤 페이지가 필요한지는 간접적 대응 | 구현 현실성에 따른 트레이드오프 |

> 요약: 워킹 셋은 완벽한 이론적 최적을 목표로 하나 구현이 무거워, 실제 OS에서는 Page Fault 빈도로 임계치를 통제하는 PFF 기법을 실용적으로 채택한다.

## Ⅴ. 심화 비교 및 적용 판단

**리스크·대응:**
- 참조 패턴의 급변(Phase Transition): 루프를 끝내고 새로운 서브루틴 진입 시 과거의 워킹 셋이 전혀 쓸모없어지고 Page Fault가 일시 폭증 → 워킹 셋 윈도우 $\Delta$를 런타임에 동적으로 조절하는 적응형 윈도우 정책 적용 (지표: 트랜지션 구간의 Fault Rate 스파이크 통제)
- 다중 윈도우 겹침 누수: 여러 프로세스가 동시에 윈도우를 팽창시킬 때 OOM(Out of Memory) 연쇄 발생 → 커널의 메모리 압박 징후 감지 시 예비 풀(Reserve Pool) 선제 확보 및 빠른 프로세스 Suspend 결단

**도입 후 점검 지표:**
- 성능: 전체 시스템의 Page Fault Rate — `sar -B` 지표에서 fault/s 및 majflt/s(디스크 I/O 동반 폴트) 추이
- 품질: 프로세스당 Resident Set Size (RSS) 안정성 — RSS가 워킹 셋 크기에 수렴하여 진동하지 않는지 확인

## Ⅵ. 실무 적용 및 결론

**적용 방안 3개:**
1. 리눅스 Cgroups 메모리 Limit 설정: 클라우드 환경에서는 컨테이너의 메모리 한도를 프로세스의 추정 워킹 셋보다 20~30% 높게 설정(OOM Kill 방지)하여 지역성 보장
2. 대용량 JVM 힙(Heap)과 워킹 셋 동기화: 자바 애플리케이션의 경우 GC(Garbage Collection) 스캔이 전체 메모리를 건드려 워킹 셋을 파괴하지 않도록, ZGC 등 지역성 보존형 최신 GC로 튜닝
3. DB 버퍼 풀 온메모리 락업: 워킹 셋 방출을 막기 위해 핵심 DB 인덱스나 핫 데이터 페이지는 OS 커널 레벨에서 핀(mlock)으로 고정하여 디스크 스왑 대상에서 영구 제외

**결론 (2줄):**
- 기술사 판단: 워킹 셋 모델은 가상 메모리 안정성의 핵심 이론이나, 실무에서는 H/W 추적 오버헤드를 고려하여 PFF 임계치 제어나 애플리케이션(DB) 차원의 버퍼 직접 제어 방식을 병행해야 한다.
- 향후 방향: 빅데이터 및 인메모리 처리 증가로 워킹 셋 크기 자체가 물리 RAM을 초과하는 사례가 늘어, NVMe Caching 및 메모리 티어링(Memory Tiering) 솔루션으로 모델이 진화하고 있다.
