## Ⅰ. 개요
- **정의**: 일정 시간 윈도우 내에서 프로세스가 참조하는 페이지 집합
- **배경/필요성**: 프로세스에 할당할 프레임 수를 결정하여 페이지 폴트율을 제어할 필요가 있음 (016 참조)
- **비유**: 요리사가 현재 조리 중인 레시피에 올려놓은 재료(페이지)들의 집합과 같음

| 출제 의도 | 반드시 짚을 핵심 | 감점 회피 포인트 |
|:---|:---|:---|
| 메모리 할당 정책 이해 | 워킹셋 윈도우(Δ)와 스래싱 관계 | 워킹셋 크기는 고정값이 아닌 동적 변동값임을 명시 |

> 요약: 시간 윈도우 기반 참조 페이지 집합으로 프레임 할당량을 결정하는 모델임

## Ⅱ. 구성요소
```text
Time Window (Delta)
|<--------->|
| P1 P3 P1 P2 P4 P2 P3 |  --> Working Set = {P1,P2,P3,P4}
                              --> Size = 4 frames needed
```

| 구성요소 | 설명 | 비유 |
|:---|:---|:---|
| 워킹셋 윈도우(Δ) | 참조 이력을 추적하는 시간/참조 횟수 구간 | 최근 주문 조회 기간 |
| 워킹셋 크기(WSS) | 윈도우 내 고유 페이지 수 | 조리대 위 재료 가짓수 |
| 페이지 폴트율(PFR) | 단위 시간당 페이지 폴트 발생 빈도 | 재료 부족으로 창고행 횟수 |
| 스래싱 임계점 | WSS 합이 물리 프레임 총량을 초과하는 시점 | 조리대가 넘쳐 재료가 바닥에 떨어지는 시점 |

> 요약: 윈도우·WSS·폴트율·스래싱 임계점이 워킹셋 모델의 핵심 요소임

## Ⅲ. 절차
```text
참조 추적 --> WSS 산출 --> 프레임 할당 --> 스래싱 판별
```
- 1단계: 프로세스의 페이지 참조 문자열을 시간 윈도우 Δ 단위로 기록
- 2단계: 윈도우 내 고유 페이지 수를 집계하여 WSS 산출
- 3단계: WSS만큼 물리 프레임을 할당하고 초과분은 회수
- 4단계: 전체 프로세스 WSS 합이 가용 프레임을 초과하면 스래싱으로 판별하고 부하 조절

> 요약: 참조 추적-WSS 산출-프레임 할당-스래싱 판별 순으로 메모리를 관리함

## Ⅳ. 문제점
- Δ 설정 어려움: 워크로드마다 최적 윈도우가 상이 — 과소 시 폴트 증가, 과대 시 메모리 낭비
- WSS 산출 오버헤드: 매 참조마다 이력 갱신 필요 — 참조 비트 스캔에 CPU 시간 소모
- 스래싱 감지 지연: WSS 합산이 사후적 — 스래싱 진입 후에야 감지되어 대응이 늦음

> 요약: 윈도우 튜닝·산출 오버헤드·감지 지연이 워킹셋 모델의 한계임

## Ⅴ. 개선방안
1. 단기: PFF(Page Fault Frequency) 기법 병행으로 폴트율 기반 Δ를 동적 조정
2. 중기: 참조 비트 샘플링 주기를 적응적으로 변경하여 산출 오버헤드 저감
3. 장기: 부하 제어기(Admission Control) 도입으로 스래싱 임계 도달 전 선제적 프로세스 중단

> 요약: PFF 병행, 적응적 샘플링, 선제적 부하 제어로 워킹셋 한계를 보완함

## Ⅵ. 전망
- 발전 방향: 컨테이너·서버리스 환경에서 워크로드별 메모리 자동 확장/축소에 WSS 활용 확대
- 기술사적 판단: 메모리 과할당 방지와 QoS 보장을 위한 기초 지표로서 중요성 유지
- 기술사 제언: cgroup memory.stat 등 OS 계측 데이터와 WSS 모니터링을 연계 운영 권장
