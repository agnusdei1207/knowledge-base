## Ⅰ. 개요
- 정의: 시스템의 응답 시간, 처리량, 자원 활용도 등을 측정하고 병목을 식별하는 활동
- 배경: 사용자·요청량 증가에 따른 응답 지연, 처리량 한계, 자원 포화 지점을 검증할 필요
- 출제 의도: 성능 테스팅의 3대 유형(Load, Stress, Endurance)의 차이점 이해

## Ⅱ. 구성요소
- 구조도
  [Traffic]
     |   [Load] : 설계 범위 내 부하
     |   [Stress] : 임계치 이상의 과부하 (Break point 찾기)
     |   [Endurance] : 장시간 부하 (Memory Leak 확인)

- 구성요소 표
| 유형 | 설명 | 핵심 측정 |
| :--- | :--- | :--- |
| 부하(Load) | 기대되는 동시 접속 하중에서의 성능 | 응답 시간, TPS |
| 스트레스 | 시스템 장애 발생 시점까지 하중 증가 | 한계점, 회복력 |
| 내구성(Soak) | 장시간 부하 시 안정성 유지 여부 | 메모리 누수, 자원 소진 |
> 요약: 설계 부하·한계 초과 부하·장시간 부하에서 응답 시간·처리량·자원 사용량을 측정함

## Ⅲ. 절차
- 흐름도
  목표 수립 -> 스크립트/환경 구축 -> 테스트 수행 -> 분석/튜닝
- 4단계 설명
1. 목표 수립: 목표 응답 시간, 최대 동시 접속자 수, 가용 자원 임계치 등 정의
2. 환경 구축: 운영 환경과 유사한 독립 테스트 환경 및 데이터, 부하 발생기 준비
3. 테스트 수행: 정의된 시나리오에 따라 단계별로 부하를 가하며 성능 지표 수집
4. 분석/튜닝: APM(Application Performance Management) 등을 활용해 병목 구간 식별 및 개선
> 요약: 목표 지표와 측정값의 차이를 분석하고 병목을 조정한 뒤 동일 시나리오로 재검증함

## Ⅳ. 문제점
- 테스트 환경과 운영 환경의 인프라 격차로 인한 결과 값의 신뢰도 저하
- 단순 TPS 수치에만 집착하여 네트워크 지연, DB Lock 등 근본 병목 원인 간과

## Ⅴ. 개선방안
- 클라우드 환경을 활용한 가변적 인프라 구성으로 운영 환경과의 유사성 확보
- Full Stack 모니터링 및 코드 프로파일링을 통한 정밀한 병목 원인 진단

## Ⅵ. 전망
- CI/CD 파이프라인 내 성능 테스트 자동화(Continuous Performance) 체계 정착
- CSF: 비즈니스 피크 타임을 고려한 현실적인 부하 프로파일링 및 시나리오 수립
