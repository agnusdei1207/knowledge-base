## 미리 알고가기

- 2PL(Two-Phase Locking): 트랜잭션의 잠금 획득 시점과 잠금 해제 시점을 구분하여 성장과 축소 단계로 나눔으로써 직렬 가능성을 보장하는 잠금 프로토콜임
- 성장 단계(Growing Phase): 트랜잭션이 새로운 잠금을 획득할 수만 있고, 이미 획득한 잠금은 절대 해제할 수 없는 단계임
- 축소 단계(Shrinking Phase): 트랜잭션이 잠금을 해제할 수만 있고, 새로운 잠금을 획득하는 것은 절대 불가능한 단계임
- 공유 잠금(Shared Lock, S-Lock): 데이터 조회 시 설정하여 일관성을 지키고, 다른 공유 잠금과는 동시 획득이 가능하나 배타 잠금과는 충돌함
- 배타 잠금(Exclusive Lock, X-Lock): 데이터 수정 시 설정하여 다른 모든 공유/배타 잠금과의 동시 접근을 차단함
- 데드락(Deadlock): 두 개 이상의 트랜잭션이 서로가 선점한 잠금의 해제를 무한히 대기하여 정체되는 교착 상태임

## 작성 근거(검토용)

- 핵심 키워드 선정 이유: 동시성 제어의 이론적 기반이 되는 직렬화 가능성(Serializability) 보증 프로토콜인 2PL의 유형(Basic, Strict, Rigorous)과 동작 원리를 검증하고 데드락 회피 방안을 정립하기 위함
- 절 구성 및 전개 흐름 이유: 개요에서 2PL의 기본 정의와 충돌 직렬성 보장 목적을 규명함. 특징에서 성장/축소 구조적 규칙을 정의하고, 비교표를 통해 Basic과 Strict의 연쇄 롤백 방지 효과를 대조함. 구조 설계에서는 락 매니저와 대기 그래프의 역할을 정형화하며, 절차 흐름에서 잠금 분기를 분석하고 실무 조치를 제시함
- 전수 검수 완료 근거: 제목, frontmatter, 미리 알고가기, 본문, 표 헤더·셀, 요약, 결론의 전체 맞춤법 및 한국어 표현 자연스러움을 검사하고 5회 완독을 통과함

## Ⅰ. 개요

- **정의/개념**: 2PL은 트랜잭션이 잠금을 획득하는 성장 단계와 해제하는 축소 단계의 순서를 엄격히 구분하여 스케줄의 충돌 직렬화 가능성(Conflict Serializability)을 보장하는 잠금 프로토콜임
- **배경/필요성**: 다중 트랜잭션이 데이터에 임의로 잠금을 걸고 해제할 때 발생할 수 있는 데이터 불일치 스케줄을 방지하고, 안전한 처리 순서를 시스템적으로 보장하기 위해 필요함

### 쉽게 이해하기 (학습용)
- 필요한 모든 열쇠를 주머니에 전부 채워 넣을 때까지는 절대 열쇠를 내려놓지 않고(성장), 한 번이라도 열쇠를 내려놓기 시작하면 새 열쇠를 줍지 않는(축소) 규칙임

## Ⅱ. 특징

- 성장 단계와 축소 단계가 교차하지 않도록 단방향 잠금 가시성을 강제함
- 직렬화 가능성은 완벽히 보장되나, 자원에 잠금을 거는 순서에 따라 데드락(교착 상태)을 유발할 우려가 큼
- 배타 잠금의 유지 기간을 커밋 시점까지 연장하여 연쇄 롤백(Cascading Rollback) 문제를 회복 가능한 스케줄로 개선함
- 데이터베이스의 잠금 밀도(Granularity) 설정에 따라 잠금 오버헤드와 동시 처리량 간의 성능 변화가 큼

### 쉽게 이해하기 (학습용)
- 직렬 연산 순서는 깔끔하게 맞춰주지만, 욕심쟁이처럼 열쇠를 다 쥐고 있다 보니 다른 사람이 기다리다 지쳐 데드락(교착)이 발생할 수 있음

## Ⅲ. 종류 및 비교

| 판단 기준 | Basic 2PL | Strict 2PL |
|:---|:---|:---|
| 잠금 해제 시점 | 성장 단계를 지나 축소 단계에 들어가면 임의 자원 즉시 해제 가능 | 트랜잭션이 완전히 커밋 또는 롤백될 때까지 배타 잠금을 유지함 |
| 복구 영향 | 중간에 해제된 값을 타 트랜잭션이 읽을 수 있어 연쇄 롤백 위험 존재 | 완료 시까지 쓰기 잠금을 보유하므로 Dirty Read 및 연쇄 롤백 원천 방지 |
| 주요 한계 | 롤백 발생 시 동시 취소되는 트랜잭션 범위 확산으로 복구 복잡도 상승 | 잠금 유지 시간이 대폭 길어져 트랜잭션 대기 지연 및 병목 발생 |

> 요약: Basic 2PL은 축소 단계에서 잠금을 해제하고, Strict 2PL은 커밋·롤백까지 배타 잠금을 유지함.

### 쉽게 이해하기 (학습용)
- Basic 2PL은 일이 끝나기도 전에 열쇠를 일부 반납해 혼란을 야기할 수 있고, Strict 2PL은 일이 완전히 끝날 때까지 쥐고 있어 안전하지만 속도는 느림

## Ⅳ. 설계 요소 및 구조

```text
+-------------------------------------------------------------+
|                       2PL 잠금 관리 구조                    |
+-------------------------------------------------------------+
        │                               │
        ▼                               ▼
+────────────────────────+      +────────────────────────+
|   1. 락 테이블 / 매니저 |      |   2. 트랜잭션 상태 제어|
|   - 해시 맵 기반 관리  |      |   - 성장 상태 (Locking) |
|   - S-Lock / X-Lock    |      |   - 축소 상태 (Unlocking)|
+────────────────────────+      +────────────────────────+
        │                               │
        +───────────────┬───────────────+
                        ▼
+─────────────────────────────────────────────────────────────+
|                     3. 데드락 감지 및 복구 엔진             |
|   - 대기 그래프 (Wait-For Graph) 주기적 순환 감지           |
|   - 피해자 트랜잭션 선정 (Victim Selection) 및 롤백         |
+-------------------------------------------------------------+
```

| 설계 요소 | 설명 |
|:---|:---|
| 락 매니저 (Lock Manager) | 메모리상에 잠금 테이블을 구축하여 트랜잭션별 자원 획득 현황과 대기열을 추적하는 모듈 |
| 성장 단계 제어기 | 잠금 요청 함수만 수락하고 잠금 해제 요청은 축소 진입 전까지 차단하는 상태 감시 엔진 |
| 대기 그래프 (Wait-For Graph) | 자원을 대기하는 트랜잭션 간의 유향 그래프를 유지하여 순환 구조($Cycle$)를 감지하는 탐지기 |
| 피해자 선정기 (Victim Selector) | 데드락 발견 시 비용 복잡도($O(1)$ 혹은 트랜잭션 가중치)를 고려해 강제 롤백할 트랜잭션을 골라내는 장치 |

> 요약: 잠금 관리자가 성장 단계의 획득과 축소 단계의 해제를 통제하고 순환 대기는 데드락 처리로 해소함.

### 쉽게 이해하기 (학습용)
- 자물쇠 관리자(락 매니저)가 언제 열쇠를 줄지 감시하고, 꼬여서 안 풀리는 관계(데드락)를 그래프로 찾아 강제로 한 명을 끊어버리는 뼈대임

## Ⅴ. 원리 및 절차 흐름도

```text
[트랜잭션 시작] 
      │
      ▼ (성장 단계 진입)
[필요 잠금 획득] ── (S-Lock / X-Lock 획득 수행, 해제는 금지)
      │
      ▼ (잠금 해제 발생 시점)
[축소 단계 진입] ── (기존 락 순차 해제 수행, 신규 획득 금지)
      │
      ▼
[트랜잭션 커밋/롤백] ── (남은 모든 잠금 최종 반환 및 정리)
```

1. **잠금 획득 시작 (성장 단계)**: 트랜잭션이 구동되고, 실행할 쿼리에 맞춰 대상 리소스의 잠금을 순차적으로 요청하여 확보함
2. **성장 제한선 도달**: 더 이상 추가 잠금이 필요 없는 시점(락 포인트, Lock Point)까지 잠금 해제는 철저히 유보됨
3. **잠금 해제 시작 (축소 단계)**: 비즈니스 판단 후 첫 잠금을 푸는 즉시 축소 단계로 전환되며, 이때부터는 새로운 자원에 대한 잠금 획득이 원천 차단됨
4. **스케줄 완료 및 락 해제**: 트랜잭션이 최종 완료(Commit)되거나 이상 시 철회(Rollback)되고 잔존하는 모든 자물쇠가 해제됨

> 요약: 성장 단계에서 잠금을 획득하고 첫 해제 뒤에는 새 잠금을 얻지 않은 채 커밋·롤백으로 종료함.

### 쉽게 이해하기 (학습용)
- 마트에서 물건을 카트에 담기만 하다가(성장), 하나라도 카트에서 빼놓는 순간부터는 쇼핑을 멈추고 계산대로 직행해야 하는 원리임

## Ⅵ. 실무 사례

1. 계좌 이체 DB는 계정 잠금 순서를 표준화하고 데드락 발생 건수·재시도 성공률을 확인함
2. 온라인 거래 DB는 긴 배치를 별도 트랜잭션으로 분리하고 잠금 보유 시간·대기 트랜잭션 비율을 확인함

### 쉽게 이해하기 (학습용)
- 왼쪽 사람이 오른쪽 사람 책을 빌리고, 오른쪽 사람이 왼쪽 사람 책을 빌려 꼬이는 일이 없도록 물건의 정렬 ID 순서대로만 자물쇠를 걸게 제어함

## Ⅶ. 결론

- 2PL은 이론적으로 충돌 직렬성을 완벽하게 보장하지만, 자원 대기 연장으로 인한 동시성 저하와 데드락 리스크를 함께 짊어지는 트레이드오프 관계임
- 그러므로 대규모 웹 애플리케이션에서는 비관적 2PL 잠금 방식을 최소화하고, MVCC나 애플리케이션 수준의 낙관적 버전 검증(Optimistic Lock) 기법을 주류 아키텍처로 채택하는 것이 바람직함

### 쉽게 이해하기 (학습용)
- 완전 무결한 데이터 처리가 최우선일 때 쓰는 정석적인 규칙이지만, 병목을 피하기 위해 요즘은 낙관적 락이나 MVCC를 섞어 쓰는 추세임
