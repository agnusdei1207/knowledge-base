## 미리 알고가기

- 2PL은 잠금을 더 얻는 단계와 잠금을 푸는 단계를 나누는 잠금 규칙임
- 공유 잠금은 읽기용 잠금이고, 배타 잠금은 다른 읽기와 쓰기를 막는 쓰기용 잠금임
- 데드락은 서로 가진 잠금을 기다리느라 트랜잭션이 멈춘 상태를 뜻함

## 작성 근거(검토용)

- 제목·frontmatter·미리 알고가기·본문·표·요약·결론을 5회 전수 검수해 어색한 단어·조사·동사 결합·장황한 명사구를 교정함
- 2PL은 공유·배타 잠금, 성장·축소 단계, Strict 규칙, 데드락 처리를 핵심 축으로 설명함
- 비교표는 Basic·Strict 2PL의 해제 시점·복구 영향·경합 비용·적합 업무를 대비함
- 이체와 온라인 거래 DB는 데드락 건수·잠금 보유 시간으로 검증함

## Ⅰ. 개요

- **정의/개념**: 2PL은 잠금 획득만 하는 성장 단계와 잠금 해제만 하는 축소 단계를 분리해 충돌 직렬 가능성을 보장하는 프로토콜임
- **배경/필요성**: 동시 트랜잭션의 읽기·쓰기 충돌 순서를 직렬 가능하게 만들기 위해 잠금 획득·해제 규칙이 필요함

## Ⅱ. 특징

- 성장·축소 단계 규칙으로 충돌 직렬 가능성을 보장함
- 공유 잠금과 배타 잠금으로 읽기 충돌과 쓰기 충돌을 구분함
- 잠금을 오래 잡는 트랜잭션이 있으면 대기열과 데드락이 늘어날 수 있음
- 직렬 가능성을 보장하지만 공유·배타 잠금 경합은 읽기·쓰기 트랜잭션 대기를 늘릴 수 있음

## Ⅲ. 종류 및 비교

| 판단 기준 | Basic 2PL | Strict 2PL |
|:---|:---|:---|
| 잠금 해제 시점 | 축소 단계에 들어가면 잠금을 풀 수 있음 | 커밋이나 롤백 전까지 배타 잠금을 유지함 |
| 복구 영향 | 축소 단계에서 해제된 값을 다른 트랜잭션이 읽을 수 있음 | 커밋·롤백까지 배타 잠금을 유지해 Dirty Read·연쇄 롤백을 방지함 |
| 한계 | 중간 해제로 복구 해석이 복잡해질 수 있음 | 경합과 대기 시간이 더 늘 수 있음 |
| 대표 환경 | 직렬 가능 스케줄을 위한 일반 잠금 제어 | Dirty Read·연쇄 롤백을 차단해야 하는 거래 처리 |

> 요약: Basic 2PL은 축소 단계에서 잠금을 해제하고, Strict 2PL은 커밋·롤백까지 배타 잠금을 유지함.

## Ⅳ. 구성요소 및 구조

| 구성요소 | 설명 |
|:---|:---|
| 잠금 관리자 | 트랜잭션별 잠금 요청과 대기 상태를 관리함 |
| 성장 단계 | 필요한 잠금을 추가로 얻기만 하며 안전한 실행 순서를 형성함 |
| 축소 단계 | 잠금을 풀기 시작한 뒤에는 새 잠금을 얻지 못하게 막음 |
| 데드락 처리 | 순환 대기를 탐지하거나 시간 초과로 끊어 정체를 해소함 |

> 요약: 잠금 관리자가 성장 단계의 획득과 축소 단계의 해제를 통제하고 순환 대기는 데드락 처리로 해소함.

## Ⅴ. 원리 및 절차 흐름도

1. **잠금 획득 시작**: 읽기와 쓰기 대상에 필요한 공유 잠금과 배타 잠금을 요청함
2. **성장 단계 진행**: 필요한 잠금을 모두 얻을 때까지 잠금을 풀지 않음
3. **잠금 해제 시작**: 첫 잠금 해제 이후에는 다른 잠금을 새로 얻지 않음
4. **커밋 또는 롤백 종료**: 작업 결과를 확정하거나 취소한 뒤 남은 잠금을 정리함

> 요약: 성장 단계에서 잠금을 획득하고 첫 해제 뒤에는 새 잠금을 얻지 않은 채 커밋·롤백으로 종료함.

## Ⅵ. 실무 사례

1. 계좌 이체 DB는 계정 잠금 순서를 표준화하고 데드락 발생 건수·재시도 성공률을 확인함
2. 온라인 거래 DB는 긴 배치를 별도 트랜잭션으로 분리하고 잠금 보유 시간·대기 트랜잭션 비율을 확인함

## Ⅶ. 결론

- 2PL은 성장·축소 단계로 잠금 순서를 통제하고 데드락·대기 비용을 관리함
