## 미리 알고가기

- 2PL은 잠금을 더 얻는 단계와 잠금을 푸는 단계를 나누는 잠금 규칙임
- 공유 잠금은 읽기용 잠금이고, 배타 잠금은 다른 읽기와 쓰기를 막는 쓰기용 잠금임
- 데드락은 서로 가진 잠금을 기다리느라 트랜잭션이 멈춘 상태를 뜻함

## Ⅰ. 개요

- **정의/개념**: 2단계 잠금 프로토콜 2PL은 트랜잭션이 필요한 잠금을 모두 얻기 전에는 잠금을 풀지 않고, 한 번 잠금을 풀기 시작하면 새 잠금을 다시 얻지 못하게 해 직렬 실행과 같은 안전한 결과를 보장하는 동시성 제어 방식임.
- **배경/필요성**: 여러 트랜잭션이 같은 데이터를 동시에 바꾸는 환경에서는 잠금 순서가 흐트러지면 정합성이 깨지므로, 잠금 획득과 해제 규칙을 명확히 고정할 필요가 있음.

## Ⅱ. 특징

- 잠금 규칙이 분명해 직렬 가능성을 설명하기 쉬움
- 공유 잠금과 배타 잠금으로 읽기 충돌과 쓰기 충돌을 구분함
- 잠금을 오래 잡는 트랜잭션이 있으면 대기열과 데드락이 빠르게 늘어날 수 있음
- 강한 정합성에는 유리하지만 읽기 비중이 높은 환경에서는 병목이 커질 수 있음

## Ⅲ. 종류 및 비교

| 판단 기준 | Basic 2PL | Strict 2PL |
|:---|:---|:---|
| 잠금 해제 시점 | 축소 단계에 들어가면 잠금을 풀 수 있음 | 커밋이나 롤백 전까지 배타 잠금을 유지함 |
| 장점 | 잠금 유지 시간이 비교적 짧을 수 있음 | 복구가 단순하고 연쇄 롤백을 막기 쉬움 |
| 한계 | 중간 해제로 복구 해석이 복잡해질 수 있음 | 경합과 대기 시간이 더 늘 수 있음 |
| 적합 환경 | 일반적인 직렬화 제어 | 강한 정합성과 복구 단순성이 중요한 업무 |

## Ⅳ. 구성요소 및 구조

| 구성요소 | 설명 |
|:---|:---|
| 잠금 관리자 | 트랜잭션별 잠금 요청과 대기 상태를 관리함 |
| 성장 단계 | 필요한 잠금을 추가로 얻기만 하며 안전한 실행 순서를 형성함 |
| 축소 단계 | 잠금을 풀기 시작한 뒤에는 새 잠금을 얻지 못하게 막음 |
| 데드락 처리 | 순환 대기를 탐지하거나 시간 초과로 끊어 정체를 해소함 |

## Ⅴ. 원리 및 절차 흐름도

```text
+-------------+     +-------------+     +-------------+     +-------------+
| 잠금 획득 시작  | --> | 성장 단계 진행   | --> | 잠금 해제 시작  | --> | 커밋/롤백 종료  |
+-------------+     +-------------+     +-------------+     +-------------+
```

1. **잠금 획득 시작**: 읽기와 쓰기 대상에 필요한 공유 잠금과 배타 잠금을 요청함
2. **성장 단계 진행**: 필요한 잠금을 모두 얻을 때까지 잠금을 풀지 않음
3. **잠금 해제 시작**: 첫 잠금 해제 이후에는 다른 잠금을 새로 얻지 않음
4. **커밋 또는 롤백 종료**: 작업 결과를 확정하거나 취소한 뒤 남은 잠금을 정리함

## Ⅵ. 실무 적용 및 유의점

1. 계정 이체와 잔액 갱신처럼 순서가 엄격한 업무에는 2PL이 적합하지만 잠금 순서가 흔들리면 데드락이 늘어나므로 접근 순서를 표준화하고 데드락 발생 건수와 재시도 성공률로 확인함.
2. 긴 배치와 짧은 온라인 거래가 함께 있는 환경에서는 긴 트랜잭션이 잠금을 오래 잡지 않게 범위를 줄이거나 MVCC와 분리하고 잠금 보유 시간과 대기 트랜잭션 비율로 확인함.

## Ⅶ. 결론

2PL은 잠금을 강하게 거는 기법이 아니라 잠금 획득과 해제 순서를 통제해 정합성을 지키되 데드락과 대기 비용을 함께 관리하는 방식임.
