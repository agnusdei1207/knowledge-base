# 📖 【암기용】 개념 완전 이해

## 한눈에
- **개요**: 트랜잭션이 데이터에 접근할 때 직렬성(정확성)을 보장하기 위해 락(Lock)을 '획득하는 단계'와 '반납하는 단계'로 명확히 나누어 실행하는 잠금 규약
- **왜 필요한가**: 데이터를 읽고 쓸 때마다 자유롭게 락을 걸었다 풀었다 반복하면, 다른 트랜잭션이 중간에 끼어들어 데이터 일관성이 깨진다(직렬성 실패). 이를 방지하기 위한 강제 룰이다.
- **핵심 직관**: 숨참기 잠수와 같다. "물에 들어가면서 숨을 계속 들이마시기만 하고(확장 단계), 한 번 숨을 내뱉기 시작하면(수축 단계) 다시 들이마실 수 없다."

## 핵심 용어 정리

| 용어/표기 | 의미 | 비유·예 |
|:---|:---|:---|
| 직렬가능성 (Serializability) | 여러 트랜잭션이 동시에 실행되어도, 하나씩 순서대로 실행한 결과와 똑같아지는 성질 | 꼬이지 않는 완벽한 새치기 방지줄 |
| S-Lock (Shared Lock) | 읽기 전용 락. 남이 같이 읽는 건 허용, 수정은 불가 | 도서관 열람실 책 (같이 볼 순 있음) |
| X-Lock (Exclusive Lock) | 쓰기 전용 배타 락. 남이 읽거나 수정하는 것 모두 불가 | 개인 일기장 (나만 보고 쓸 수 있음) |
| 확장 단계 (Growing Phase) | 트랜잭션이 필요한 락을 계속 얻기만 하는 시기 | 숨을 들이마시며 자원을 모으는 시기 |
| 수축 단계 (Shrinking Phase) | 락을 풀기 시작하는 시기. (이때부턴 새 락 획득 불가) | 숨을 내뱉으며 자원을 놓는 시기 |

## 깊이 이해
- **배경·문제의식**: 단순히 데이터 조작 직전에 락을 걸고 직후에 풀면(조기 해제), 다른 트랜잭션이 끼어들어 일관성이 깨진다. 직렬가능성을 수학적으로 완벽히 보장할 규칙이 필요했다.
- **작동 원리 (2단계 규약)**:
  - **제 1단계 (Growing Phase, 확장)**: 트랜잭션은 데이터 접근을 위해 S-Lock이나 X-Lock을 계속 요청해 획득한다. 단, 한 번이라도 락을 해제(Unlock)하면 이 단계는 끝난다.
  - **제 2단계 (Shrinking Phase, 수축)**: 한 번 락을 반납(해제)하기 시작하면, 그 이후로는 새로운 락을 **절대** 다시 요청할 수 없다. 가진 락을 다 풀 때까지 해제만 한다.
- **비유**: 은행 강도(트랜잭션)가 금고 3개를 턴다고 할 때, "금고 3개를 다 열 때까지(확장 단계) 절대 어떤 금고문도 닫지 마! 하나라도 닫기 시작하면(수축 단계) 더 이상 새 금고를 열 수 없어"라고 규칙을 정한 것.
- **흔한 오해·주의점**: "2PL을 쓰면 데드락(교착상태)도 예방되나?" 아니다! 2PL은 직렬가능성(정확성)은 100% 보장하지만, 서로 락을 기다리는 데드락은 발생할 수 있다. 오히려 락을 움켜쥐고 있는 2PL 특성상 데드락 위험이 더 크다.

## 연결 개념
- **교착 상태 (Deadlock)**: 2PL을 엄격하게 적용할 때 발생하는 치명적인 부작용 (009 키워드)
- **MVCC**: 2PL의 락 대기로 인한 성능 저하를 해결하기 위해 등장한 현대적 동시성 제어 (098 키워드)

# 📝 【답안용】 시험 답안 템플릿

## 핵심 인사이트 (3줄 요약)

> 1. **본질**: 2단계 잠금 프로토콜(2PL)은 트랜잭션의 직렬가능성(Serializability)을 보장하기 위해 잠금 획득(확장)과 해제(수축)를 2개의 독립된 페이즈로 분리한 동시성 제어 규약이다.
> 2. **가치**: 이 규칙을 준수하는 모든 트랜잭션 스케줄은 수학적으로 충돌 직렬성(Conflict Serializable)을 보장받아 데이터 무결성이 100% 유지된다.
> 3. **판단 포인트**: 정합성은 완벽하나 상호 대기로 인한 교착상태(Deadlock) 위험과 병행 처리 성능 저하가 필연적이므로, Strict 2PL 적용 및 교착상태 회피 설계가 병행되어야 한다.

## 출제 의도 및 답안 포인트

| 출제 의도 | 반드시 짚을 핵심 | 감점 회피 포인트 |
|:---|:---|:---|
| 2PL의 동작 원리와 상태 전이 이해 | 확장 단계(Growing)와 수축 단계(Shrinking)의 명확한 분리 원칙 | 단순 Lock(S/X) 개념만 설명하고 2단계 분리를 누락 |
| 2PL의 한계와 보완책 적용 역량 | 교착상태(Deadlock) 발생 위험 및 Strict 2PL(엄격한 2PL) 적용 | 2PL이 데드락까지 해결한다고 잘못 서술 |

> 요약: 락을 '획득만 하는 단계'와 '반납만 하는 단계'로 분리하여 직렬성을 확보한다는 원리를 데드락 리스크와 묶어 설명해야 한다.

---

## Ⅰ. 개요 및 필요성

- 개요: 2단계 잠금 프로토콜(2PL, Two-Phase Locking)은 트랜잭션 스케줄의 직렬가능성을 보장하기 위해, 잠금 요청과 잠금 해제를 두 개의 독립된 단계로 엄격히 구분하는 규약임
- 배경: 트랜잭션 수행 중 자유롭게 Lock/Unlock을 반복할 경우 타 트랜잭션 개입으로 비일관성 노출(직렬성 위배) 문제 발생
- 필요성: 다중 트랜잭션 병행 처리 시 복잡한 트랜잭션 스케줄링 검증 없이, 프로토콜 준수만으로 충돌 직렬성(Conflict Serializability)을 보장하기 위해 필수적임

---

## Ⅱ. 구조 및 구성요소 (2PL 상태 전이)

```text
Lock Count
  ^
  |        [ 확장 단계 ]            [ 수축 단계 ]
  |       (Lock 획득 가능)         (Lock 획득 불가)
  |      +------> Lock Point (정점) ---->+
  |     /                                 \
  |    / (Lock 요청/획득)        (Unlock 수행) \
  |   /                                         \
  +-------------------------------------------------> Time
```

| 구분 | 개념 및 원칙 | 발생 연산 |
|:---|:---|:---|
| 확장 단계 (Growing Phase) | 트랜잭션이 새로운 락(S-Lock, X-Lock)을 계속 획득할 수 있는 단계 | Lock(x), 업그레이드(S→X) |
| Lock Point (잠금 정점) | 트랜잭션에 필요한 모든 잠금을 획득한 순간 | 전환점 |
| 수축 단계 (Shrinking Phase) | 한 번 락을 해제하기 시작한 이후로, 새 락 획득이 절대 불가한 단계 | Unlock(x), 다운그레이드(X→S) |

> 요약: 한 번이라도 Unlock 연산이 수행되면 수축 단계로 진입하여 새로운 데이터 접근을 위한 Lock 요청이 원천 차단된다.

---

## Ⅲ. 동작원리 및 흐름도

```text
Tx 시작 -> 데이터 A 읽기 (S-Lock 획득) -> 데이터 B 쓰기 (X-Lock 획득) -> Lock Point 도달
-> Tx 연산 완료 -> 데이터 A 해제 (Unlock) -> 수축 단계 진입 (이후 새 락 불가) -> 데이터 B 해제 (Unlock)
```

- 1단계 [확장 진입]: 트랜잭션 수행에 필요한 데이터 접근 시 공유 락(S) 또는 배타 락(X)을 순차적으로 요청하여 획득
- 2단계 [연산 및 정점]: 모든 락을 획득(Lock Point)하고 안전한 고립 상태에서 핵심 비즈니스(수정/조회) 연산 수행
- 3단계 [수축 전환]: 일부 데이터 조작이 끝나 첫 번째 Unlock을 호출하는 순간 수축 단계로 자동 전환
- 4단계 [해제 및 종료]: 규칙에 따라 잔여 락을 모두 반납하고 커밋. 만약 이 시점에 데이터 C에 접근하려 하면 2PL 위배로 에러 처리됨

> 요약: 락 획득과 해제의 순서를 엄격하게 2분할함으로써 트랜잭션의 논리적 경계를 완벽히 보호한다.

---

## Ⅳ. 특징

- 직렬성 보장: 2PL을 준수하는 모든 트랜잭션 스케줄은 반드시 '직렬가능(Serializable)'함이 수학적으로 증명됨
- 데드락 내재: A가 B를 기다리고 B가 A를 기다리는 교착상태(Deadlock)는 2PL 규칙만으로는 예방 불가능
- 폭포수 롤백(Cascading Rollback) 위험: 수축 단계에서 락을 푼 데이터를 타 트랜잭션이 읽었는데, 원 트랜잭션이 롤백되면 연쇄 롤백 발생 (기본 2PL의 한계)

---

## Ⅴ. 심화 비교 및 적용 판단

| 비교 축 | 기본 2PL (Basic) | 엄격한 2PL (Strict 2PL) | 강건한 2PL (Rigorous 2PL) |
|:---|:---|:---|:---|
| 해제 시점 | 연산 종료 시 점진적 해제 | 쓰기(X-Lock)는 Commit 시 일괄 해제 | 읽기/쓰기 락 모두 Commit 시 해제 |
| 직렬성 보장 | O | O | O |
| 연쇄 롤백 방어 | 취약함 (발생 가능) | 완벽히 방어 (X-Lock 유지) | 완벽히 방어 |
| 동시성 성능 | 높음 (락 조기 반납) | 보통 (대부분의 상용 DB 적용) | 최하 (대기 시간 최장) |

> 요약: 연쇄 롤백의 치명적 위험 때문에 실무 상용 RDBMS는 수축 단계를 지연시켜 트랜잭션 종료(Commit) 시점에 X-Lock을 일괄 해제하는 Strict 2PL을 채택한다.

**리스크·대응 (기본은 불릿):**
- 교착상태(Deadlock) 발생: 트랜잭션 A, B가 확장 단계에서 서로의 락을 상호 대기 → 타임아웃(Timeout) 설정, 대기 그래프 기반 탐지 알고리즘 적용 (지표: Deadlock 감지 횟수)
- 병행성 저하(성능 병목): 락 유지 시간 증가로 TPS 급락 → MVCC 아키텍처 도입으로 읽기 작업의 락(S-Lock) 획득 과정을 면제하여 병목 제거

## Ⅵ. 실무 적용 및 결론

**적용 방안 3개:**
1. 엄격한 2PL(Strict 2PL) 강제: DB 엔진 파라미터 튜닝 시 트랜잭션 롤백에 대비해 커밋 시점까지 배타 락을 유지하도록 구성하여 데이터 무결성 최우선 확보
2. 락 경합 방지 로직 설계: 교착 상태를 예방하기 위해 애플리케이션 내 모든 트랜잭션이 데이터 테이블에 접근하는 순서(예: A테이블 -> B테이블)를 전사적으로 통일되게 설계
3. 인덱스 튜닝을 통한 잠금 최소화: Table Lock 대신 Record Lock이나 넥스트 키 락이 작동하도록 WHERE 절 조건 컬럼에 적절한 인덱스를 생성하여 2PL 락 범위 최소화

**결론 (2줄):**
- 기술사 판단: 2PL은 트랜잭션 무결성을 위한 가장 수학적이고 확실한 프로토콜이지만 데드락과 성능 저하를 동반하므로, 인덱스 튜닝과 트랜잭션 범위 최소화로 락 유지 시간을 극소화해야 한다
- 향후 방향: 최근 대규모 트래픽 처리 시스템은 비관적 락(2PL) 대신 분산 합의 알고리즘(Raft)이나 낙관적 락(Optimistic Concurrency Control) 기반으로 병행 제어 패러다임을 전환하고 있다
