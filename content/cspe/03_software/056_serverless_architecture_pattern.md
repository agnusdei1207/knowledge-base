# 📖 【암기용】 개념 완전 이해

## 한눈에
- **개요**: 서버리스 아키텍처 패턴은 개발자가 서버 인프라(OS, 용량 할당)를 직접 관리하지 않고 핵심 비즈니스 로직(함수)만 배포하며, 이벤트 실행 횟수에 비례하여 비용을 지불하는 클라우드 네이티브 설계 패턴이다.
- **왜 필요한가**: 항상 켜져 있는 서버(EC2, VM)는 트래픽이 없어도 돈이 나간다. 트래픽이 몰릴 때 자동으로 스케일 아웃되고, 트래픽이 없으면 과금이 0원이 되는 진정한 종량제를 구현하기 위해 탄생했다.
- **핵심 직관**: 수도꼭지 렌탈. 물(서버)을 쓰기 위해 뒷단의 펌프나 파이프(인프라)를 관리할 필요가 없다. 수도꼭지를 틀 때(이벤트 발생 시)만 물이 나오고, 튼 만큼만 돈을 낸다. 첫 물을 틀 때 배관에 물이 차느라 약간 미지근한 물이 늦게 나오는 현상이 '콜드 스타트'다.

## 핵심 용어 정리

| 용어/표기 | 의미 | 비유·예 |
|:---|:---|:---|
| FaaS (Function as a Service) | 애플리케이션 로직을 '함수' 단위로 배포하고 이벤트에 의해 실행됨 | AWS Lambda, Google Cloud Functions |
| BaaS (Backend as a Service) | 인증, DB 등 백엔드 기능을 API 형태로 제공받아 서버리스 구현 지원 | Firebase Authentication, DynamoDB |
| 이벤트 트리거 (Event Trigger) | 함수를 실행시키는 방아쇠 (HTTP 요청, 파일 업로드 등) | "이미지가 S3에 올라오면 함수 실행해" |
| 콜드 스타트 (Cold Start) | 오랜만에 함수가 호출될 때 컨테이너를 새로 띄우느라 지연이 발생하는 현상 | 잠자는 자동차 엔진에 시동 걸 때 걸리는 시간 |

## 깊이 이해
- **배경·문제의식**: 클라우드 IaaS(VM)나 CaaS(컨테이너)도 결국 OS 패치, 용량 산정, 오토스케일링 설정을 개발자가 해야 한다(Ops 부담). 비즈니스 로직에만 100% 집중할 수 있는 환경(NoOps)이 요구되었다.
- **작동 원리**: 서버가 아예 없는 것이 아니라, 클라우드 제공자(AWS 등)가 동적으로 서버를 할당하고 회수한다. HTTP 요청이나 큐 메시지 같은 '이벤트'가 발생하면, 클라우드는 컨테이너를 프로비저닝하고(콜드 스타트), 함수 로직을 실행한 뒤, 실행 시간에 비례해 과금하고, 일정 시간 요청이 없으면 자원을 회수한다.
- **구체 예시**: 사용자가 S3 버킷에 이미지를 업로드(이벤트) -> AWS Lambda(FaaS)가 자동으로 깨어나 이미지를 리사이징 -> 결과를 저장하고 Lambda는 종료됨.
- **흔한 오해·주의점**: 무조건 싼 것이 아니다. 24시간 내내 초당 수천 건의 트래픽이 일정한 서비스라면 서버리스 비용이 기존 EC2 서버보다 훨씬 더 비싸진다. 간헐적(Spiky) 트래픽에 최적화되어 있다.

## 연결 개념
- 마이크로서비스 아키텍처 (MSA) — 서버리스(FaaS)는 MSA를 가장 잘게 나눈 극단적인 형태로 나노서비스(Nanoservice)라고도 불림
- 클라우드 네이티브 컴퓨팅 — 서버리스는 컨테이너, MSA, CI/CD와 함께 클라우드 네이티브의 핵심 기둥 중 하나
- 콜드 스타트 (Cold Start) — 서버리스 최대의 성능 병목. 이를 회피하기 위한 Provisioned Concurrency 기술이 발달함

# 📝 【답안용】 시험 답안 템플릿

## 핵심 인사이트 (3줄 요약)

> 1. **본질**: 인프라 관리(서버 프로비저닝, 패치 등)를 클라우드 벤더에 위임하고, 비즈니스 로직을 함수 단위로 배포하여 이벤트에 반응하는 아키텍처이다.
> 2. **가치**: NoOps를 통한 개발 생산성 극대화와 진정한 사용량 기반 종량제(Pay-as-you-go)를 실현하여 초기 인프라 비용을 제로화한다.
> 3. **판단 포인트**: 간헐적 스파이크 트래픽에 최적화되어 있으나, 초기 구동 지연(콜드 스타트)과 클라우드 벤더 종속성(Lock-in) 리스크를 반드시 고려해야 한다.

## 출제 의도 및 답안 포인트

| 출제 의도 | 반드시 짚을 핵심 | 감점 회피 포인트 |
|:---|:---|:---|
| 서버리스의 구조와 동작 원리 이해 | FaaS/BaaS 분류, 이벤트 기반 실행 원리, 자동 확장 | "물리적 서버가 아예 없다"는 잘못된 정의 |
| 성능 및 아키텍처 트레이드오프 파악 | 콜드 스타트 병목, 상태 비저장(Stateless) 제약 | 항상 비용이 저렴하다는 무조건적 긍정 단정 |
| 리스크 통제 및 적용 방안 제시 역량 | 벤더 종속성 해결책(헥사고날), Provisioned Concurrency | 콜드 스타트 해소 방안 누락 |

> 요약: 서버리스는 인프라 관리 제로의 혁신이지만, 상태 비저장 특성과 벤더 락인이라는 아키텍처적 제약을 어떻게 극복할 것인가가 핵심 논점이다.

## Ⅰ. 개요 및 필요성

- 개요: 서버의 프로비저닝과 관리를 클라우드 제공자가 전담하고, 개발자는 함수(FaaS) 중심의 로직만 작성하여 이벤트 주도로 실행되는 클라우드 네이티브 아키텍처임
- 배경: 기존 IaaS/PaaS 환경에서도 OS 패치, 용량 산정, 오토 스케일링 설정 등 인프라 운영(Ops) 부담이 지속적으로 발생
- 필요성: 개발팀이 비즈니스 로직 구현에만 집중할 수 있는 환경(NoOps)과 미사용 시 과금이 0원이 되는 진정한 종량제 요금제 도입 필수

---

## Ⅱ. 구조 및 구성요소

```text
클라이언트 -> [ 이벤트 소스 ] -> [ 컴퓨팅 (FaaS) ] -> [ 백엔드 서비스 (BaaS) ]
            (API Gateway/S3)    (AWS Lambda)       (DynamoDB/Firebase)
```

| 구성요소 | 역할 | 특이사항 |
|:---|:---|:---|
| 이벤트 소스 (Event Source) | 함수 실행을 트리거하는 이벤트 발생기 | HTTP 요청, 파일 업로드, 메시지 큐 등 |
| FaaS (Function as a Service) | 상태 비저장(Stateless) 형태로 실행되는 비즈니스 로직 단위 | 실행 시간(ms) 및 메모리 크기 기반 과금 |
| BaaS (Backend as a Service) | 데이터베이스, 인증, 스토리지 등 서드파티 백엔드 API | 인프라 관리 없이 서비스로 호출 연동 |

> 요약: 서버리스는 FaaS로 로직을 구성하고 BaaS로 상태를 보관하며, 철저히 이벤트에 의해 구동되는 반응형 아키텍처다.

---

## Ⅲ. 동작원리 및 흐름도

```text
이벤트 발생 -> 컨테이너 프로비저닝 (Cold Start) -> 함수 로직 실행 (Warm Start) -> 결과 반환 및 자원 회수
```

- 1단계 [이벤트 발생]: API Gateway로 HTTP 요청이 들어오거나 S3에 파일이 업로드되는 등 트리거 발생
- 2단계 [자원 할당 (콜드 스타트)]: 유휴 상태일 경우 클라우드 벤더가 컨테이너를 띄우고 런타임(Node, Python)을 로드 (지연 발생)
- 3단계 [로직 처리]: 프로비저닝된 환경(Warm 상태)에서 핵심 비즈니스 로직 함수 실행 및 BaaS와 연동하여 데이터 처리
- 4단계 [자원 회수]: 실행이 완료되면 즉시 결과를 반환하고, 일정 시간 요청이 없으면 할당된 컨테이너 파기 (과금 중지)

> 요약: 인프라가 켜져 대기하는 것이 아니라, 이벤트 발생 시점에 동적으로 자원이 깨어나고(콜드 스타트) 즉각 회수된다.

---

## Ⅳ. 특징

- 극단적 오토스케일링: 트래픽 급증(Spike) 시 인프라 설정 없이 클라우드 벤더가 백엔드 리소스를 무제한에 가깝게 자동 수평 확장
- NoOps 기반 TCO 절감: OS 패치, 보안 업데이트, 로드밸런싱 등 운영 인력 비용이 대폭 절감되어 비즈니스 타임투마켓(TTM) 단축
- 상태 비저장(Stateless) 한계: 함수가 종료되면 메모리가 초기화되므로, 세션이나 파일 등 지속적 상태 보관을 위해서는 별도의 외부 스토리지(BaaS) 강제

> 요약: 인력 및 초기 비용을 드라마틱하게 줄여주지만, 상태를 내부 메모리에 보관할 수 없는 아키텍처 제약이 따른다.

## Ⅴ. 심화 비교 및 적용 판단

| 비교 축 | 서버 기반 (CaaS / 컨테이너) | 서버리스 (FaaS) | 선택 기준 |
|:---|:---|:---|:---|
| 프로비저닝 | 인스턴스/파드 항상 대기 (Warm) | 이벤트 시 동적 프로비저닝 (Cold) | 응답 시간의 엄격도 (p99 Latency) |
| 과금 방식 | 할당된 리소스 시간 단위 | 실제 실행 밀리초(ms) 단위 | 트래픽 패턴 (일정함 vs 간헐적 스파이크) |
| 제어권 | OS, 런타임, 네트워크 제어 완전 가능 | 클라우드 벤더의 환경 제약 (시간/용량) | 커스텀 바이너리 및 장시간 실행 필요성 |

> 요약: 예측 가능하고 꾸준히 트래픽이 높은 서비스는 CaaS가 유리하며, 간헐적이고 예측 불가한 배치나 스크립트는 서버리스가 압도적으로 효율적이다.

**리스크·대응:**
- 콜드 스타트 지연: 오랜만에 호출 시 컨테이너 로드 지연(수백 ms ~ 초 단위) 발생 → Provisioned Concurrency(사전 예열) 적용 또는 런타임을 경량화(Java 지양, Go/Node.js 사용) (지표: p95 응답 지연 시간)
- 벤더 락인 (Vendor Lock-in): 특정 클라우드 벤더의 FaaS 규격과 BaaS에 코드가 종속됨 → 헥사고날 아키텍처를 도입하여 비즈니스 로직과 클라우드 SDK 어댑터를 분리 (지표: 타 클라우드 마이그레이션 예상 공수)

## Ⅵ. 실무 적용 및 결론

**적용 방안 3개:**
1. 비동기 백그라운드 워크로드 적용: 이미지 리사이징, 로그 수집/파싱, 주기적 스케줄링 배치 작업 등 지연 시간(콜드 스타트)에 민감하지 않은 작업부터 전환
2. BFF(Backend for Frontend) 패턴 연계: 마이크로서비스 환경에서 모바일, 웹 등 채널별 API 조합 및 데이터 가공을 담당하는 경량 BFF 계층을 FaaS로 구현
3. 서버리스 컨테이너 혼합 운용: AWS Fargate나 Google Cloud Run처럼 콜드 스타트 제약을 완화하고 컨테이너의 유연성을 결합한 서버리스 컨테이너 적극 채택

**결론 (2줄):**
- 기술사 판단: 서버리스는 만병통치약이 아니며, 장시간 실행(15분 이상 제약)이나 초저지연이 필요한 코어 서비스보다는 유휴 시간이 긴 스파이크성 이벤트 처리에 적합함
- 향후 방향: FaaS 중심의 1세대 서버리스에서, 컨테이너 자체를 서버리스로 구동하는 Knative, Cloud Run 등 '서버리스 2.0'으로 생태계가 융합 확장 중임
