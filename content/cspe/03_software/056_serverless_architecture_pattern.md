# 📖 【암기용】 개념 완전 이해

> 목적: 이 개념을 처음 보는 사람도 완벽히 이해하게 만든다. 시험 답안 양식이 아니라, 이해를 위한 친절한 설명이다.

## 한눈에
- **개요**: **서버리스(Serverless)**는 진짜 서버가 없다는 뜻이 아니다. "개발자인 네가 굳이 서버(OS, 메모리, CPU)를 신경 쓰지 않아도 돼(less)"라는 뜻이다. 그냥 순수한 '코드(함수)' 덩어리만 압축해서 클라우드(AWS)에 휙 던져놓으면, 알아서 컴퓨터를 켜고 코드를 실행한 뒤 알아서 꺼버리는 얌체 같은 클라우드 아키텍처다.
- **왜 필요한가**: 과거에는 서버 1대를 24시간 켜놔야 했다. 새벽 3시에 접속자가 0명이어도 전기세(서버비)를 냈다. 블랙프라이데이에 트래픽이 몰리면 수동으로 서버를 10대로 늘려야 했다. 서버리스는 이걸 박살 냈다. 접속자가 올 때만 0.1초 만에 서버를 띄워서 코드를 실행하고 돈(밀리초 단위)을 받고, 끝나면 즉시 서버를 꺼버린다(비용 0원).
- **핵심 직관**: 
  - 일반 서버 (자가용): 기름값, 보험료(고정비) 매달 나감. 주차(관리)도 내가 해야 함.
  - 서버리스 (택시): 내가 이동할 때(이벤트 발생 시)만 돈 내고 탐. 목적지 도착하면 미터기 끄고 내림. 유지보수 신경 제로.

## 깊이 이해
- **배경·문제의식**: 클라우드(IaaS)가 나와서 가상머신(EC2)을 쉽게 빌려 쓰게 되었지만, 여전히 리눅스 OS를 깔고, 보안 패치를 하고, 톰캣(Tomcat)을 올리는 노가다는 개발자 몫이었다. 개발자들은 "아 제발 다 귀찮고, 그냥 내가 짠 이 함수 1개만 실행시켜 주면 안 돼?"라고 절규했다. 그렇게 FaaS(Function as a Service)가 탄생했다.
- **작동 원리 (핵심 2가지 축)**: 서버리스 아키텍처는 보통 이 두 개를 섞어 쓴다.
  1. **FaaS (Function as a Service)**: AWS Lambda. 내 코드(함수)를 올려둔다. 누군가 버튼을 누르면(이벤트 발생) 클라우드가 함수를 100만 번 복제해서 동시에 실행해 준다. 무한대의 오토스케일링이 기본 장착되어 있다.
  2. **BaaS (Backend as a Service)**: Firebase, AWS Cognito. 개발자가 굳이 코딩할 필요 없이 아마존이 만들어둔 '로그인 기능', '푸시 알림 기능' API를 돈 주고 그냥 땡겨 쓰는 것. FaaS 함수가 BaaS를 호출하며 굴러간다.
- **비유**: 
  - 놀이공원 자판기. 손님이 동전을 넣을 때(이벤트)만 불이 켜지고 캔(결과)이 나온다. 24시간 자판기 불을 켜놓는(서버 온) 편의점 알바생은 필요 없다.
- **흔한 오해·주의점**: "서버리스 최고네! 그럼 우리 회사 서버 다 서버리스로 바꾸자!" 절대 안 된다. 서버리스의 가장 큰 약점은 **'콜드 스타트(Cold Start)'**다. 꺼져있던 서버를 켜서 코드를 메모리에 올리고 실행하는 데 최초 1번은 1~2초가 딜레이된다. 주식 매매나 FPS 게임 서버처럼 0.01초가 생명인 곳에 쓰면 회사가 망한다.

## 연결 개념
- **마이크로서비스 (MSA)**: MSA가 서버를 100개로 쪼개는 거라면, 서버리스(FaaS)는 서버를 함수(Function) 단위로 1만 개로 쪼개는 극단적인 쪼개기의 끝판왕(Nano-service)이다.
- **이벤트 기반 아키텍처 (EDA)**: 서버리스는 누군가 찔러주지(이벤트) 않으면 절대 깨어나지 않는 잠자는 숲속의 공주다. (예: S3에 이미지가 올라오면 -> Lambda 함수가 깨어나서 리사이징).

# 📝 【답안용】 시험 답안 템플릿

> 목적: 시험장에서 25분에 그대로 쓰는 답안 양식. 작성방식(추상표현 금지·수치·도식·문제유형 전환)을 엄격히 지킨다.
> 핵심: 이 시험은 정보를 많이 나열하는 시험이 아니라, 문제 신호어에서 출제자 의도를 읽고 핵심 논점을 선별해 쓰는 시험이다.

## 핵심 인사이트 (3줄 요약)

> 1. **본질**: 개발자가 서버 인프라(OS, 런타임, 프로비저닝)에 대한 관리(Provisioning) 책임을 클라우드 벤더(AWS 등)에 100% 위임하고, 오직 핵심 비즈니스 로직(Function) 작성에만 집중하는 클라우드 네이티브 아키텍처 패러다임이다.
> 2. **가치**: 트래픽에 비례한 극단적인 Auto-Scaling(수만 개 병렬)과 미사용 시 과금 제로(Pay-as-you-go)를 달성하며, NoOps(운영 제로) 철학을 실현하여 Time-to-Market을 극대화한다.
> 3. **판단 포인트**: FaaS와 BaaS의 컴포넌트 도식을 명확히 구분하고, 무한한 확장성의 대가로 지불해야 하는 콜드 스타트(Cold Start) 지연 딜레마와 특정 벤더 락인(Vendor Lock-in) 리스크 방어책을 짚어야 한다.

## 출제 의도 및 답안 포인트

| 출제 의도 | 반드시 짚을 핵심 | 감점 회피 포인트 |
|:---|:---|:---|
| 인프라 추상화 단계 이해 (IaaS -> PaaS -> CaaS -> FaaS) | NoOps (서버 관리 제로) 및 트래픽 연동 Pay-as-you-go | "서버가 없는(No Server) 아키텍처"라고 직역하여 물리적 서버 부재로 오답 서술 |
| 서버리스 아키텍처를 구성하는 두 축 매핑 | FaaS(비즈니스 함수, Lambda) + BaaS(관리형 서비스, Firebase) | 단순히 AWS Lambda 하나만 서버리스로 퉁쳐서 백엔드(BaaS) 의존성 생태계 누락 |
| 극단적 추상화가 낳는 시스템 리스크 및 한계 | 콜드 스타트(Cold Start) 레이턴시 및 Vendor Lock-in | 트래픽 폭주 시 무제한 확장되어 모든 시스템에 다 좋다는 무비판적 찬양 |

> 요약: 서버리스는 개발팀을 운영(Ops)의 지옥에서 해방시켰다. 리눅스 보안 패치나 로드밸런서 설정 따위는 AWS가 알아서 한다. 개발자는 그냥 `def run()` 파이썬 함수 하나 던져놓고 롤(게임) 하러 가면 된다.

## Ⅰ. 개요 및 필요성

- 정의: 클라우드 프로바이더(CSP)가 서버 인프라 할당 및 오토스케일링을 동적으로(Dynamically) 완벽히 관리하며, 사용자는 이벤트(Trigger) 구동 시 소비한 리소스만큼만 비용을 지불하는 애플리케이션 설계 모델
- 배경: 기존 IaaS(EC2) 모델은 Idle Time(유휴 시간)에도 24시간 컴퓨팅 비용이 고정 지출되었고, 피크(Peak) 트래픽 대비를 위한 용량 산정(Capacity Planning) 및 인프라 전담 인력 유지 비용 한계 도달
- 필요성: 1초 만에 트래픽이 1만 배 폭증하는 현대 워크로드에서 인간의 개입(Ops) 없이 즉각적인 스케일 아웃을 달성하고, 100ms 단위의 극단적 종량제 요금(Pay-per-use)으로 인프라 TCO를 절감하기 위함

## Ⅱ. 서버리스 아키텍처 도식: 이벤트 기반 FaaS + BaaS 융합

서버리스 시스템은 24시간 깨어있는 좀비(모놀리식)가 아니다. 찔러야(Event) 움직이는 반사 신경 덩어리다.

```text
[ 이벤트 주도(Event-Driven) 서버리스 토폴로지 도식 ]

(1. 사진 업로드 이벤트)        (2. 자동 발동)        (3. 리사이징 코드)      (4. 외부 서비스 의존)
    [ 사용자 앱 ]       ---> [ AWS S3 스토리지 ] ---> [ AWS Lambda (FaaS) ] ---> [ Auth / DB (BaaS) ]
                                   |                   (0.1초 만에 켜짐)         (Firebase / DynamoDB)
                                   |                         |
                           (이벤트 트리거 ⚡)        (동시 1만 장 🚀 1만 개 복제 실행)
```

| 서버리스 컴포넌트 | 아키텍처적(엔지니어링) 제어 메커니즘 | 실무 튜닝 효과 |
|:---|:---|:---|
| **FaaS** <br> (Function as a Service) | 개발자가 작성한 순수 비즈니스 로직(함수)을 보관. 요청(Event)이 들어오면 컨테이너를 띄워 함수를 실행하고 응답 후 즉시 컨테이너 소멸 (Stateless 강제) | EC2나 K8s(Pod)를 상시 띄워두지 않으므로 트래픽 0일 때 비용 0원. 트래픽 폭주 시 인스턴스 무제한 격리 스케일 아웃 |
| **BaaS** <br> (Backend as a Service) | 회원 가입, 푸시 알림, NoSQL DB 등 표준화된 백엔드 기능을 클라우드 벤더가 API 형태로 완전 관리형(Managed) 제공 | 개발자가 '인증 서버'나 'DB 클러스터'를 직접 코딩하거나 설치할 필요 없이 100% 아웃소싱하여 개발 리드타임 소거 |
| **Event Source** <br> (이벤트 트리거) | HTTP API(Gateway), 스토리지 업로드(S3), 메시지 큐(Kafka/SQS), 크론 주기(CloudWatch) 등 FaaS를 깨우는 자극(자명종) | 폴링(Polling, 계속 물어보기) 방식의 스레드 낭비를 없애고, 이벤트 훅(Hook)으로만 동작하는 완벽한 비동기 아키텍처 완성 |

> 요약: 서버리스 세상에서 개발자는 레고 블록 조립공이다. 로그인(BaaS) 블록 가져오고, 결제(BaaS) 블록 가져온 뒤, 그 사이를 이어주는 간단한 본드(FaaS 함수)만 바르면 거대한 백엔드 시스템이 몇 시간 만에 완성된다.

## Ⅲ. 극복해야 할 시스템적 리스크 (콜드 스타트의 저주)

"필요할 때만 켜서 쓴다"는 완벽해 보이는 모델의 치명적 대가(Trade-off)는 '지연(Latency)'이다.

| 리스크 요인 | 발생 시나리오 및 시스템 붕괴 원인 (안티패턴) | 아키텍처 대응 방안 (실무 튜닝) |
|:---|:---|:---|
| **Cold Start (콜드 스타트) 지연 딜레마** | 10분간 아무도 안 써서 함수(컨테이너)가 꺼져있는 상태에서 접속. AWS가 부랴부랴 런타임(Java JVM)을 올리고 코드를 로딩하느라 사용자에게 **최초 1회 3초 이상의 딜레이** 발생 | **Warm Start 튜닝 (Provisioned Concurrency)**: 5분마다 강제로 함수를 찌르는 빈 핑(Ping) 이벤트를 날리거나, AWS 요금을 더 내고 "컨테이너 10개는 절대 끄지 마라"고 고정 할당하여 콜드 스타트 원천 차단 |
| **초 단기 타임아웃 셧다운** | 대규모 빅데이터 정제 배치(Batch) 로직을 Lambda(FaaS)에 올렸는데, 15분(AWS Lambda 최대 실행 제한 시간)이 지나는 순간 프로세스가 강제 킬(Kill) 당해 데이터 유실 파국 | **롱러닝(Long-running) 배치 완전 금지**: 서버리스는 1초 안에 끝나는 짧은 작업 전용이다. 무거운 작업은 AWS Batch나 컨테이너(Fargate, EKS) 등 지속 실행이 가능한 일반 CaaS 인프라로 아키텍처 분리 설계 |

> 요약: Java와 Spring Boot는 서버리스(Lambda) 환경에서 최악의 쓰레기다. JVM 켜고 스프링 로딩하는 데만 5초(콜드 스타트)가 걸리기 때문이다. 서버리스는 파이썬(Python), 노드(Node.js), 고(Go)처럼 0.01초 만에 팍! 켜지는 가벼운 언어들의 독무대다.

## Ⅳ. 종속성 딜레마 방어: Vendor Lock-in 극복 (추상화 진화)

클라우드 벤더(AWS)의 달콤한 서버리스 독을 마시면, 아마존의 노예가 되어 평생 빠져나올 수 없다.

| 리스크 요인 | 인프라 종속성 붕괴 시나리오 | 튜닝 대응 (오픈소스 프레임워크 기반 탈출) |
|:---|:---|:---|
| **벤더 락인 (Vendor Lock-in)** | AWS Lambda API와 DynamoDB에 특화된 코드를 10만 줄 짰는데, AWS 요금이 3배 폭등함. 다른 클라우드(GCP)로 이사 가려 했더니 함수 코드를 전부 다시 짜야 하는 마이그레이션 포기 상태 도달 | **Serverless Framework 호환 계층 도입**: `serverless.yml`이라는 클라우드 중립적 인프라 추상화 설정 파일로 배포를 통제하여, 소스코드 수정 없이 빌드 타겟만 AWS에서 GCP로 변경 가능하도록 IaC(인프라 코드화) 브릿지 구축 |

> 요약: 아마존은 서버리스(Lambda)를 엄청나게 싸게 제공한다. 이유는 한 번 Lambda와 S3 생태계로 로직을 엮어놓으면, 코드가 AWS 환경과 세포 수준으로 결합하여 절대 Azure나 구글 클라우드로 도망칠 수 없기 때문이다.

## Ⅴ. 실무 적용 방안 및 결론

**적용 방안 3개:**
1. [이벤트 기반 백그라운드 미디어 처리 아키텍처] 넷플릭스 등 미디어 서비스에서 원본 영상이 S3에 업로드되는 즉시(S3 Trigger) -> Lambda 3개가 동시에 켜져 1080p, 720p, 480p로 병렬 트랜스코딩 연산을 때린 후 종료하여 서버 유휴 비용을 제로화
2. [API Gateway + Lambda 기반 마이크로서비스 웹 백엔드 구축] 간헐적으로 트래픽이 튀는 티켓 예매 조회 API 구성 시, API Gateway 뒤에 Lambda를 붙여 0명일 땐 인프라 비용 0원을 유지하다가 오후 2시 티켓 오픈 시 1만 개의 Lambda 컨테이너가 1초 만에 스케일 아웃되어 트래픽 댐을 방어
3. [Spring Cloud Function / GraalVM 결합 콜드 스타트 타파] 기존 Java Spring 생태계를 서버리스로 이식할 때 발생하는 극악의 콜드 스타트를 잡기 위해, GraalVM AOT(Ahead-of-Time) 네이티브 이미지 컴파일(Native Image)을 적용하여 기동 시간을 5초에서 50ms로 압축시켜 C언어급 반응 속도 확보

**결론:**
- 기술사 판단: 서버리스(Serverless)는 컴퓨터 공학 역사상 인프라(운영체제)의 존재를 소스코드로부터 가장 완벽하게 지워버린(Decoupling) 마법의 아키텍처다. 그러나 인프라 관리를 안 한다는 것은 그 통제권을 클라우드 벤더(AWS)에게 100% 바친다는 의미다. 콜드 스타트, 15분 타임아웃, 벤더 종속성이라는 치명적 독을 인지하고 비동기/경량 도메인에만 국지적으로 투입하는 날카로운 설계 감각이 요구된다.
- 향후 방향: 최근 시장은 FaaS(Lambda)의 콜드 스타트 제약을 벗어나기 위해, 개발자가 컨테이너(Docker)를 말아 던지면 클라우드가 무제한 스케일링해 주는 AWS Fargate나 Google Cloud Run 같은 'CaaS(Container as a Service) 기반 서버리스'로 주도권이 이동하며 한계를 돌파하고 있다.
