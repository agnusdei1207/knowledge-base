## 미리 알고가기

- 서버리스는 서버가 없다는 뜻이 아니라 실행 인프라 운영 책임을 플랫폼이 더 많이 맡는 모델임
- FaaS는 이벤트가 들어올 때 함수 단위로 코드를 실행하는 서비스 형태임
- 콜드 스타트는 오랫동안 쉬고 있던 함수가 다시 켜질 때 초기 지연이 생기는 현상임

## Ⅰ. 개요

- **정의/개념**: 서버리스 아키텍처 패턴은 기능을 함수나 관리형 서비스 단위로 나누고 실행 인프라와 확장과 일부 운영 책임을 클라우드 플랫폼에 위임해 애플리케이션을 구성하는 방식임.
- **배경/필요성**: 짧고 불규칙한 트래픽이 많은 서비스는 서버를 미리 확보해 두는 방식이 비효율적일 수 있으므로, 이벤트가 발생한 만큼만 실행하고 운영 부담을 줄일 수 있는 구조가 필요함.

## Ⅱ. 특징

- 사용량 기준 과금과 자동 확장으로 초기 운영 부담을 낮춤
- API·메시지·스케줄 이벤트가 함수 실행을 시작하므로 알림·변환·자동화 작업을 이벤트별 함수로 분리함
- 상태 유지와 장시간 실행이 필요한 업무에는 제약이 큼
- 플랫폼 종속성과 관측 한계를 설계 초기에 함께 봐야 함

## Ⅲ. 종류 및 비교

| 구분 | 전통 서버 기반 | 서버리스 패턴 |
|:---|:---|:---|
| 인프라 운영 | 서버 용량과 배포 환경을 팀이 직접 관리함 | 실행 환경과 확장을 플랫폼이 자동으로 관리함 |
| 비용 구조 | 사용량이 적어도 서버를 미리 확보한 비용이 듦 | 실제 호출량과 실행 시간만큼 비용을 내는 경우가 많음 |
| 실행·확장 방식 | 상시 프로세스에서 상태와 장시간 작업을 직접 관리 | 이벤트마다 함수를 시작하고 플랫폼이 인스턴스 수를 조정 |
| 구조상 한계 | 용량 계획과 패치와 확장 운영 부담이 큼 | 콜드 스타트와 실행 시간 제한과 플랫폼 종속이 생길 수 있음 |

> 요약: 서버리스는 서버를 숨기는 기술이 아니라 불규칙한 이벤트 처리와 운영 자동화에 맞춘 실행 모델임.

## Ⅳ. 구성요소 및 구조

| 구성요소 | 설명 |
|:---|:---|
| 함수 실행 계층 | 이벤트를 받아 짧은 작업 단위로 코드를 실행하는 핵심 계층임 |
| 이벤트 입력원 | API 호출과 메시지와 스케줄 같은 입력이 함수 실행을 시작함 |
| 관리형 서비스 | 저장소와 인증과 큐 같은 공통 기능을 관리형 서비스로 받아 운영 부담을 줄임 |
| 관측과 배포 정의 | 로그와 추적과 배포 정의를 함께 관리해 분산된 함수 운영을 통제함 |

## Ⅴ. 원리 및 절차 흐름도

```text
+-------------+     +-------------+     +-------------+     +-------------+
| 이벤트 발생    | --> | 함수 실행      | --> | 관리형 서비스 연동 | --> | 로그/비용 분석 |
+-------------+     +-------------+     +-------------+     +-------------+
```

1. **이벤트 발생**: API, 메시지, 스케줄 같은 신호가 실행을 시작함
2. **함수 실행**: 플랫폼이 필요한 런타임을 준비하고 코드를 수행함
3. **관리형 서비스 연동**: 저장과 인증과 통신을 외부 서비스와 조합함
4. **로그 및 비용 분석**: 실행 지연과 실패와 호출 비용을 추적함

## Ⅵ. 실무 적용 및 유의점

1. 이벤트 기반 알림과 배치 자동화처럼 짧고 불규칙한 업무에는 서버리스가 잘 맞지만 지연 민감 구간에서는 콜드 스타트가 문제이므로 함수 분리와 예열 전략을 함께 두고 콜드 스타트 지연시간과 상위 1% 응답시간으로 확인함
2. 함수 수가 빠르게 늘어나는 조직에서는 권한과 배포 규칙이 흩어지기 쉬우므로 공통 템플릿과 IaC를 함께 운영하고 권한 불일치 건수와 배포 일관성으로 확인함

## Ⅶ. 결론

서버리스 패턴은 불규칙한 이벤트 처리에서 운영 부담을 줄일 가치가 플랫폼 제약과 종속 비용보다 클 때 선택해야 함.
