## 미리 알고가기

- 서버리스는 서버가 없다는 뜻이 아니라 실행 인프라 운영 책임을 플랫폼이 더 많이 맡는 모델임
- FaaS는 이벤트가 들어올 때 함수 단위로 코드를 실행하는 서비스 형태임
- 콜드 스타트는 오랫동안 쉬고 있던 함수가 다시 켜질 때 초기 지연이 생기는 현상임

## 작성 근거(검토용)

- 서버리스는 인프라 책임, 비용 구조, 실행 방식, 플랫폼 제약을 핵심 비교축으로 선정함
- 구성과 절차는 이벤트 발생부터 함수 실행과 관리형 서비스 연동까지의 흐름을 중심으로 제시함
- 실무 판단은 콜드 스타트 지연, 상위 1% 응답시간, 권한 오류 건수로 구체화함

## Ⅰ. 개요

- **정의/개념**: 서버리스 아키텍처는 기능을 함수·관리형 서비스로 구성하고 실행 환경과 확장 책임을 클라우드 플랫폼에 위임하는 방식임
- **배경/필요성**: 짧고 불규칙한 작업에 상시 서버를 확보하는 비용을 줄이고 이벤트 발생량에 따라 실행 자원을 확장할 구조가 필요함

## Ⅱ. 특징

- 사용량 기준 과금과 자동 확장으로 유휴 서버 유지 비용과 용량 관리 작업을 줄임
- API·메시지·스케줄 이벤트가 함수 실행을 시작하므로 알림·변환·자동화 작업을 이벤트별 함수로 분리함
- 상태 유지와 장시간 실행 업무는 함수 실행시간과 로컬 상태 저장 제약을 받음
- 설계 초기에 플랫폼 종속 범위와 분산 함수의 관측 방식을 정해야 함

## Ⅲ. 종류 및 비교

| 판단 기준 | 전통 서버 기반 | 서버리스 패턴 |
|:---|:---|:---|
| 인프라 운영 | 서버 용량과 배포 환경을 팀이 직접 관리함 | 실행 환경과 확장을 플랫폼이 자동으로 관리함 |
| 비용 구조 | 사용량이 적어도 서버를 미리 확보한 비용이 듦 | 실제 호출량과 실행 시간만큼 비용을 내는 경우가 많음 |
| 실행·확장 방식 | 상시 프로세스에서 상태와 장시간 작업을 직접 관리 | 이벤트마다 함수를 시작하고 플랫폼이 인스턴스 수를 조정 |
| 구조상 한계 | 용량 계획과 패치와 확장 운영 부담이 큼 | 콜드 스타트와 실행 시간 제한과 플랫폼 종속이 생길 수 있음 |

> 요약: 상시·장시간 작업은 서버 기반, 짧고 불규칙한 이벤트 처리는 서버리스 패턴이 적합함.

## Ⅳ. 구성요소 및 구조

| 구성요소 | 설명 |
|:---|:---|
| 함수 실행 계층 | 이벤트를 받아 짧은 작업 단위로 코드를 실행하는 핵심 계층임 |
| 이벤트 입력원 | API 호출과 메시지와 스케줄 같은 입력이 함수 실행을 시작함 |
| 관리형 서비스 | 저장소와 인증과 큐 같은 공통 기능을 관리형 서비스로 받아 운영 부담을 줄임 |
| 관측과 배포 정의 | 로그와 추적과 배포 정의를 함께 관리해 분산된 함수 운영을 통제함 |

> 요약: 이벤트 입력원이 함수를 실행하면 함수가 관리형 서비스와 연동하고 실행 정보는 관측 계층에 기록됨.

## Ⅴ. 원리 및 절차 흐름도

```text
+-------------+     +-------------+     +-------------+     +-------------+
| 이벤트 발생    | --> | 함수 실행      | --> | 관리형 서비스 연동 | --> | 로그/비용 분석 |
+-------------+     +-------------+     +-------------+     +-------------+
```

1. **이벤트 발생**: API, 메시지, 스케줄 같은 신호가 실행을 시작함
2. **함수 실행**: 플랫폼이 필요한 런타임을 준비하고 코드를 수행함
3. **관리형 서비스 연동**: 저장과 인증과 통신을 외부 서비스와 조합함
4. **로그 및 비용 분석**: 실행 지연과 실패와 호출 비용을 추적함

> 요약: 이벤트 발생 시 플랫폼이 함수를 실행하고 관리형 서비스 연동 결과와 비용을 기록함.

## Ⅵ. 실무 사례

1. 알림·파일 변환은 이벤트별 함수로 분리하고 콜드 스타트 지연·상위 1% 응답시간을 확인함
2. 서버리스 플랫폼은 IaC로 권한·배포 규칙을 관리하고 권한 오류 건수·배포 성공률을 확인함

## Ⅶ. 결론

서버리스 패턴은 짧고 불규칙한 이벤트 처리에서 운영 부담 절감 효과가 플랫폼 제약보다 클 때 적용함
