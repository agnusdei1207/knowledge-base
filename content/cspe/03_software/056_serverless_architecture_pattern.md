## Ⅰ. 개요
- **정의**: 서버 인프라 관리를 클라우드에 위임하고 함수 단위로 비즈니스 로직을 실행하는 아키텍처
- **배경/필요성**: 서버 프로비저닝·스케일링·패치 등 운영 부담이 개발 속도를 저하시키므로, 인프라 추상화를 통해 로직에 집중할 필요
- **비유**: 전기를 직접 발전하지 않고 콘센트에 꽂기만 하면 쓸 수 있는 유틸리티 모델과 유사함

| 출제 의도 | 반드시 짚을 핵심 | 감점 회피 포인트 |
|:---|:---|:---|
| FaaS·BaaS 구분과 이벤트 기반 실행 모델 이해 | Cold Start, 실행 시간 제한 | 서버가 없다는 뜻이 아님을 명확히 서술 필요 |

> 요약: 서버 관리를 클라우드에 위임하고 이벤트 기반 함수 단위로 실행하는 아키텍처임

## Ⅱ. 구성요소
```text
Event Source --> API Gateway --> FaaS (Function) --> BaaS (DB/Auth/MQ)
 (HTTP/MQ/       (라우팅)       (로직 실행)        (관리형 서비스)
  Schedule)
```

| 구성요소 | 설명 | 비유 |
|:---|:---|:---|
| FaaS | 이벤트에 의해 트리거되는 상태 비저장 함수 실행 환경 | 자판기(동전 투입 시만 작동) |
| BaaS | 인증·DB·스토리지 등 관리형 백엔드 서비스 | 전기·수도 등 공공 인프라 |
| API Gateway | 외부 요청을 함수로 라우팅하는 진입점 | 건물 안내 데스크 |
| Event Source | 함수 실행을 트리거하는 이벤트 발생원 | 센서(감지 시 알림 발송) |

> 요약: Event Source가 트리거하고 FaaS가 실행하며 BaaS가 인프라를 제공하는 구조임

## Ⅲ. 절차
```text
이벤트발생 --> API Gateway라우팅 --> 컨테이너할당/함수실행 --> 결과반환/자원해제
```
- 1단계: HTTP 요청·메시지큐·스케줄 등 이벤트 소스에서 이벤트가 발생함
- 2단계: API Gateway가 이벤트를 분석하여 대상 함수로 라우팅함
- 3단계: 플랫폼이 컨테이너를 할당하고 함수를 실행함(Cold Start 발생 가능)
- 4단계: 실행 결과를 반환하고 유휴 시 컨테이너 자원을 해제함

> 요약: 이벤트 트리거부터 자원 해제까지 온디맨드 방식으로 실행함

## Ⅳ. 문제점
- Cold Start 지연: 유휴 컨테이너 해제 후 재할당 시 수백ms 지연 — 실시간 응답 요구 시 문제
- 벤더 종속: 특정 클라우드 FaaS API에 의존 — 멀티 클라우드 전환 비용 증가
- 디버깅 난이도: 분산된 함수 단위 실행 — 요청 추적과 로그 통합이 어려움

> 요약: Cold Start 지연, 벤더 종속, 디버깅 난이도가 주요 문제임

## Ⅴ. 개선방안
1. 단기: Provisioned Concurrency 설정으로 Cold Start 지연 완화
2. 중기: 서버리스 프레임워크(SAM, Serverless Framework) 활용으로 벤더 추상화 계층 확보
3. 장기: 분산 추적(OpenTelemetry) 도입으로 함수 간 요청 흐름 가시화

> 요약: Provisioned Concurrency, 추상화 프레임워크, 분산 추적으로 개선함

## Ⅵ. 전망
- 발전 방향: WebAssembly 기반 경량 런타임으로 Cold Start 문제 해소 추세임
- 기술사적 판단: 이벤트 기반 소규모 워크로드에 적합하나 대규모 상태 관리엔 한계 존재
- 기술사 제언: MSA(057 참조) 전환 시 서버리스를 부분 적용하는 하이브리드 전략 필요
