# 📖 【암기용】 개념 완전 이해

> 목적: 서버리스 아키텍처 패턴을 처음 보는 사람도 완벽히 이해하게 만든다. 시험 답안 양식이 아니라, 이해를 위한 친절한 설명이다.

## 한눈에
- **개요**: 서버 운영 책임을 클라우드에 위임하고 이벤트 단위로 함수와 관리형 서비스를 조합하는 구조
- **왜 필요한가**: 트래픽이 들쑥날쑥한 업무에서 서버를 상시 운영하면 유휴 비용과 패치 업무가 발생한다. 서버리스는 요청이 있을 때만 실행하고 사용량 기준으로 과금한다.
- **핵심 직관**: 서버를 없애는 것이 아니라, 서버 용량 계획과 OS 운영을 클라우드 사업자 책임으로 이동시키는 방식이다.

## 깊이 이해
- **배경·문제의식**: VM·컨테이너 기반 구조는 인스턴스 크기, 오토스케일링, 패치, 런타임 업그레이드 운영이 필요하다.
- **작동 원리**: API Gateway, Queue, Object Storage 같은 이벤트 소스가 FaaS를 호출하고, 함수는 상태를 외부 DB·Cache·BaaS에 저장한다.
- **비유**: 상시 고용 직원 대신 주문이 들어올 때마다 전문 작업자가 호출되어 정해진 작업을 끝내고 비용을 청구하는 구조와 같다.
- **구체 예시**: 이미지 업로드 시 Object Storage 이벤트가 Lambda를 호출해 썸네일을 만들고, 결과 메타데이터를 DynamoDB에 저장하며, 월 100만 호출 단위로 비용을 산정한다.
- **흔한 오해·주의점**: 서버리스는 운영이 사라지는 구조가 아니다. IAM, 콜드 스타트, 관측성, 비용 폭주, 공급사 종속을 별도로 통제해야 한다.

## 연결 개념
- FaaS·BaaS: 함수 실행과 관리형 백엔드 서비스
- 이벤트 기반 아키텍처: 비동기 트리거와 큐 중심 통합
- 관측성: 분산 함수 호출의 로그·메트릭·트레이스 수집

# 📝 【답안용】 시험 답안 템플릿

> 목적: 시험장에서 25분에 그대로 쓰는 답안 양식. 작성방식(추상표현 금지·수치·도식·문제유형 전환)을 엄격히 지킨다.
> 핵심: 서버리스는 FaaS만이 아니라 이벤트 소스, 관리형 서비스, IAM, 관측성을 포함한 운영 패턴이다.

## 핵심 인사이트 (3줄 요약)

> 1. **본질**: 서버리스 아키텍처는 인프라 운영을 클라우드에 위임하고 이벤트 기반 FaaS·BaaS 조합으로 기능을 실행하는 패턴이다.
> 2. **가치**: 유휴 서버 비용을 줄이고 이벤트 피크에 자동 확장하지만, 콜드 스타트와 공급사 종속을 설계 단계에서 통제해야 한다.
> 3. **판단 포인트**: 짧은 실행 시간, 무상태 처리, 이벤트 기반 흐름, 간헐 트래픽이면 적합하고 장시간 연결·고정 지연 요구에는 부적합하다.

## 출제 의도 및 답안 포인트

| 출제 의도 | 반드시 짚을 핵심 | 감점 회피 포인트 |
|:---|:---|:---|
| 클라우드 네이티브 구조 이해 확인 | FaaS, BaaS, Event Source, Stateless, IAM | 서버가 없다고 표현하고 운영 책임 누락 |
| 운영 리스크 판단 확인 | Cold Start, Vendor Lock-in, Observability, Cost Spike | 비용 절감만 강조 |
| 적용 업무 선별 역량 확인 | 배치, 이미지 처리, API, IoT 이벤트 | 장시간 트랜잭션에 무조건 적용 |
> 요약: 출제자는 서버리스 구성요소와 운영 리스크를 함께 판단하는 능력을 확인한다.

---

## Ⅰ. 개요 및 필요성

서버리스는 이벤트 기반 함수 실행과 관리형 서비스를 조합하는 클라우드 아키텍처이다.
서버 용량 산정, OS 패치, 런타임 운영을 줄이고 호출량 기준 과금으로 간헐 트래픽 비용을 통제한다.
대신 콜드 스타트, 실행 시간 제한, IAM 권한, 분산 추적을 설계에 포함해야 한다.

---

## Ⅱ. 구조 및 구성요소

```text
Client / Event Source -> API Gateway / Queue / Storage Event
Trigger -> Function as a Service
Function -> BaaS / DB / Object Storage / External API
Function -> Log / Metric / Trace
IAM Policy -> Least Privilege Control
```

| 구성요소 | 역할 | 특이사항 |
|:---|:---|:---|
| Event Source | 함수 호출 조건 제공 | HTTP, Queue, Storage, Scheduler |
| FaaS | 짧은 업무 로직 실행 | 실행 시간·메모리 제한 |
| BaaS | 상태 저장·인증·메시징 제공 | DB, Auth, Storage, EventBridge |
| IAM | 함수 권한 통제 | 최소 권한 원칙 필수 |
| Observability | 로그·메트릭·트레이스 수집 | 함수 단위 상관관계 필요 |
> 요약: 서버리스는 이벤트 소스, 함수, 관리형 서비스, IAM, 관측성이 함께 설계되어야 한다.

---

## Ⅲ. 동작원리 및 흐름도

```text
이벤트 발생 -> Trigger 규칙 평가
Trigger -> 함수 컨테이너 할당
함수 실행 -> 외부 상태 저장 / API 호출
성공 / 실패 -> 응답 / 재시도 / DLQ
로그·메트릭·트레이스 -> 모니터링
```

| 단계 | 처리 내용 | 검증 기준 |
|:---:|:---|:---|
| 1 | API, Queue, Storage 이벤트 수신 | 이벤트 스키마 버전 관리 |
| 2 | 런타임 컨테이너 할당 및 콜드 스타트 발생 | p95 cold start 500ms 이하 |
| 3 | 함수가 무상태 로직 실행 | 실행 시간 15분 이하 |
| 4 | DB, Storage, 외부 API 연동 | 타임아웃·재시도 정책 |
| 5 | 실패 이벤트 DLQ 전송 및 추적 | DLQ 적체 0건 목표 |
> 요약: 서버리스 실행은 이벤트 트리거, 함수 할당, 무상태 처리, 실패 재처리, 관측성 수집 순서로 진행된다.

---

## Ⅳ. 특징

| 구분 | VM·컨테이너 상시 운영 | 서버리스 패턴 | 수치·판단 포인트 |
|:---|:---|:---|:---|
| 과금 | 인스턴스 실행 시간 | 호출 수·실행 시간 | 간헐 트래픽 월 100만 호출 |
| 확장 | HPA·ASG 설정 | 이벤트 기반 자동 확장 | 동시 실행 한도 설정 |
| 상태 | 로컬 상태 가능 | 외부 상태 저장 | Stateless 함수 원칙 |
| 지연 | 워밍 상태 지연 예측 가능 | 콜드 스타트 발생 | p95 500ms 기준 검토 |
| 운영 | OS·런타임 관리 필요 | 플랫폼 관리형 | IAM·관측성은 직접 설계 |
> 요약: 서버리스는 간헐 이벤트 처리에 적합하나 콜드 스타트와 권한 통제 지표를 별도로 둬야 한다.

## Ⅴ. 심화 비교 및 적용 판단

| 비교 축 | 컨테이너/Kubernetes | 서버리스 | 선택 기준 |
|:---|:---|:---|:---|
| 실행 시간 | 장시간 프로세스 | 짧은 함수 실행 | 15분 이하 작업 |
| 트래픽 | 지속 부하 | 간헐·피크 이벤트 | 유휴 시간 50% 이상 |
| 제어권 | 런타임·네트워크 세밀 제어 | 플랫폼 제약 수용 | 커널·사이드카 필요 여부 |
| 비용 | 리소스 예약 | 호출량 과금 | 호출당 비용 산정 가능 |
> 요약: 서버리스는 짧고 무상태이며 간헐적인 이벤트 업무에 선택하고, 장시간 연결은 컨테이너가 적합하다.

| 리스크 | 원인 | 대응 방안 | 확인 지표 |
|:---|:---|:---|:---|
| 콜드 스타트 | 런타임 초기화와 VPC 연결 | Provisioned Concurrency, 경량 런타임 | p95 cold start |
| 비용 폭주 | 이벤트 루프·재시도 반복 | Budget Alarm, DLQ, idempotency key | 일 호출 수, 비용 알림 |
| 공급사 종속 | 독자 이벤트·스토리지 API | 추상화 계층, IaC, 표준 런타임 | 이식 대상 API 수 |
| 권한 과다 | 함수별 IAM Wildcard | 최소 권한, Access Analyzer | wildcard 정책 0건 |
> 요약: 서버리스 위험은 콜드 스타트, 비용 폭주, 종속, 권한 과다이며 각각 지표로 통제한다.

| 점검 항목 | 목표 기준 | 측정 방법 |
|:---|:---|:---|
| 지연 | p95 응답 300ms, cold start 500ms 이하 | APM, X-Ray |
| 신뢰성 | DLQ 적체 0건, 재처리 성공률 99.9% | Queue Metric |
| 비용 | 함수별 월 예산 초과 0건 | Cost Explorer, FinOps Tag |
| 보안 | 함수별 최소 권한, Secret Manager 사용 | IAM Analyzer, 감사로그 |
> 요약: 도입 후 지연, DLQ, 비용, IAM 권한을 함수 단위로 추적해야 한다.

## Ⅵ. 실무 적용 및 결론

**적용 방안 3개:**
1. 이미지 변환, 알림 발송, 파일 처리처럼 실행 5분 이하 이벤트 업무를 FaaS로 분리하고 DLQ와 멱등키를 기본 적용한다.
2. API 함수는 Provisioned Concurrency와 캐시를 적용해 p95 cold start 500ms 이하를 목표로 운영한다.
3. IAM 정책은 함수별 최소 권한으로 작성하고 로그, 메트릭, 분산 트레이스를 Correlation ID로 연결한다.

**결론 (2줄):**
- 기술사 판단: 간헐 트래픽·짧은 무상태 작업은 서버리스, 장시간 연결·세밀한 런타임 제어는 컨테이너를 선택함
- 향후 방향: 서버리스는 이벤트 브로커, 워크플로 오케스트레이션, FinOps 관측성과 결합해 운영 자동화 중심으로 확장됨
