## 미리 알고가기

- 서버리스(Serverless): 서버가 존재하지 않는 것이 아니라 실행 인프라의 관리 및 운영 책임을 클라우드 플랫폼이 맡는 모델임
- FaaS(Function as a Service): 이벤트가 발생할 때 등록된 함수 단위로 코드를 실행하고 종료하는 컴퓨팅 서비스임
- BaaS(Backend as a Service): 데이터베이스, 인증 등 백엔드 기능을 직접 구현하지 않고 타사 관리형 API로 제공받는 모델임
- 콜드 스타트(Cold Start): 유휴 상태인 서버리스 함수가 최초 호출 시 컨테이너를 구동하고 런타임을 준비하느라 지연이 발생하는 현상임
- IaC(Infrastructure as Code): 인프라 구성을 수동 작업 대신 구성 정의 파일을 통해 코드로 작성하고 자동화하는 방식임

## 작성 근거(검토용)

- 서버리스의 핵심 아키텍처 구조를 직관적으로 전달하기 위해 인프라 관리 방식, 비용 과금 체계, 실행 특성을 3대 비교축으로 선정함
- 이벤트 트리거부터 함수 실행, 관리형 서비스 연동에 이르는 동적 절차를 텍스트 도식화하여 실무 적용 흐름을 구조화함
- 5회 이상 문장별 완독 검수를 수행하였으며, 어색한 명사구와 장황한 표현을 답안에 적합한 명료한 어휘로 다듬고, Zola 빌드 무오류를 확인 검증함

## Ⅰ. 개요

- **정의/개념**: 서버리스 아키텍처는 개별 기능을 독립된 함수로 개발하고 실행 인프라의 자동 확장 및 운영 관리를 클라우드 서비스 제공자에게 전적으로 위임하는 설계 패턴임
- **배경/필요성**: 트래픽 변동이 크고 불규칙한 분산 시스템 환경에서 고정 인프라 운영 비용을 최적화하고 애플리케이션 핵심 로직 개발에만 집중할 수 있는 구조가 필요함

### 쉽게 이해하기 (학습용)
- 가게를 상시 운영하기 위해 정규직 직원을 고용하는 대신, 손님이 올 때만 단기 대행 아르바이트를 호출하여 일을 처리하고 비용을 지불하는 방식과 유사함

## Ⅱ. 특징

- 사용량 기반 과금 구조를 통해 함수가 실제 호출되어 실행된 시간 및 메모리 점유량만큼만 가변적으로 비용을 지불함
- 플랫폼 자동 확장을 지원하여 호출 트래픽의 급증에 맞춰 실행 컨테이너가 무상태(Stateless) 기반으로 즉시 수평 확장됨
- 이벤트 구동형 아키텍처로서 API 호출, 메시지 큐 유입, 스케줄 타임 등 다양한 이벤트 소스와 유연하게 결합하여 작동함
- 클라우드 공급자에 대한 기술 종속성(Lock-in)이 높고 최대 실행 시간 제한 및 최초 호출 시 초기 지연이 발생할 수 있는 트레이드오프가 존재함

### 쉽게 이해하기 (학습용)
- 손님이 올 때마다 즉시 임시 천막을 쳐서 서비스를 제공하므로 유지비는 적지만, 첫 손님은 천막을 치는 동안 기다려야 하고 긴 시간 체류는 어려운 특성과 같음

## Ⅲ. 종류 및 비교

| 판단 기준 | 전통 서버 기반 | 서버리스 패턴 |
|:---|:---|:---|
| 인프라 관리 | OS 패치, 용량 산정, 네트워크 설정을 직접 수행함 | 인프라 구성, 자동 확장, 실행 환경을 플랫폼이 제공함 |
| 비용 구조 | 트래픽에 무관하게 서버 유지 및 가동에 대한 고정 비용이 발생함 | 실제 함수 호출 횟수와 실행 처리 시간($\text{ms}$) 비례 가변 비용이 발생함 |
| 실행 특성 | 메모리에 상태를 상시 유지하며 장시간 연산 작업 수행에 적합함 | 매 호출마다 새로 기동하는 무상태 환경이며 최대 실행 시간에 제약이 있음 |

> 요약: 상시 서비스 유지가 필요한 장시간 작업은 서버 기반, 트래픽 기복이 심한 이벤트 처리는 서버리스 패턴이 유리함.

### 쉽게 이해하기 (학습용)
- 내 건분을 직접 사서 관리하는 방식과 매시간 사용한 만큼만 지불하고 정해진 규정에 맞게 공유 오피스를 단기로 빌려 쓰는 방식의 비교와 같음

## Ⅳ. 구성요소 및 구조

```text
+-------------------+      +-------------------+      +--------------------+
|   이벤트 입력원    | ---> |   함수 실행 계층   | ---> |  관리형 서비스 연동 |
| (API, Message,..) |      |   (FaaS, Code)    |      | (DB, Storage, Auth)|
+-------------------+      +-------------------+      +--------------------+
                                     │
                                     ▼
                           +-------------------+
                           |  관측 및 분석 계층  |
                           |   (APM, Logging)  |
                           +-------------------+
```

| 설계 요소 | 설명 |
|:---|:---|
| 이벤트 입력원 | API 게이트웨이 호출, 메시지 대기열 유입, 타이머 스케줄 등 함수 실행을 트리거하는 이벤트 소스임 |
| 함수 실행 계층 | 무상태 기반으로 사전에 작성된 단일 책임 코드를 로딩하고 실행을 담당하는 런타임 환경임 |
| 관리형 서비스 | 데이터베이스, 영속성 스토리지, 사용자 인증 등 자체 구축 대신 클라우드에서 제공하는 API 연동 서비스임 |
| 관측 및 분석 계층 | 분산된 함수들의 실행 로그 수집, 에러 모니터링 및 호출당 과금 비용을 실시간 추적하고 시각화하는 도구임 |

> 요약: 이벤트 소스가 함수를 호출하면, 함수 실행 계층이 무상태 코드를 구동하고 백엔드 관리형 서비스와 연동한 뒤 관측 도구에 실행 지표를 기록함.

### 쉽게 이해하기 (학습용)
- 벨(이벤트)을 누르면 주방 이모(함수)가 냉장고(관리형 서비스)에서 재료를 꺼내 요리를 하고, 주문 전표(관측 계층)에 판매 실적을 적는 구조임

## Ⅴ. 원리 및 절차 흐름도

```text
[이벤트 발생] -> [컨테이너 생성/재사용] -> [런타임 준비/코드 로딩] -> [함수 실행 및 연동] -> [과금/로그 기록]
```

1. **이벤트 발생 및 감지**: API 게이트웨이 호출이나 큐에 메시지가 수신되어 플랫폼으로 트리거 신호를 전송함
2. **컨테이너 준비**: 플랫폼이 해당 함수를 처리할 컨테이너를 즉시 기동하거나 기존 활성 컨테이너(Warm State)를 재사용함
3. **코드 로딩 및 실행**: 구동된 컨테이너에 런타임을 준비하고 개발자가 업로드한 함수 코드를 올려 비즈니스 로직을 수행함
4. **외부 서비스 연동**: 필요한 데이터 조회나 알림 발송을 위해 외부 API나 관리형 데이터베이스에 접근하여 처리함
5. **리소스 반환 및 과금**: 실행이 종료되면 컨테이너 자원을 반환하고, 실제 연산 소비 시간과 메모리 할당 크기에 따라 과금을 기록함

> 요약: 트리거 감지 시 컨테이너 준비 및 코드 로딩 단계를 거쳐 함수가 실행되며 완료 후 과금 처리와 함께 자원을 회수함.

### 쉽게 이해하기 (학습용)
- 전화로 배달 주문이 들어오면 대기 중인 배달 오토바이를 배정하고, 내비게이션을 켜서 음식을 배달한 뒤 운행 거리만큼 수수료를 계산하여 정산하는 절차임

## Ⅵ. 실무 사례

- 실무에서는 대용량 미디어 파일 업로드 이벤트 발생 시 즉시 이미지를 썸네일로 크기 변환하는 비동기 이미지 처리 파이프라인에 서버리스 함수를 연동함
- 일정한 시간마다 주기적으로 데이터 수집 및 상태 보고서 배치를 수행하는 백엔드 배치 관리 시스템에 스케줄러 트리거와 함수를 결합해 인프라 유휴 비용을 최소화함

### 쉽게 이해하기 (학습용)
- 유튜브에 동영상이 올라갈 때마다 자동으로 여러 화질의 파일로 변환하여 저장하거나, 새벽에만 작동하는 정산 프로그램을 돌릴 때 사용하는 사례임

## Ⅶ. 결론

- 서버리스 아키텍처 패턴은 개발자가 비즈니스 로직 개발에만 집중하고 클라우드 관리 오버헤드를 낮추어 가용성 확보와 운영 자원의 유연성을 극대화함
- 시스템 설계 시에는 플랫폼 종속성에 따른 락인 위험과 콜드 스타트 지연 제약을 신중히 분석하여, 장시간 워크로드와 구분 배치하는 다중 하이브리드 아키텍처 전략이 필요함

### 쉽게 이해하기 (학습용)
- 일할 때만 대리인을 불러 비용을 낮출 수 있지만 너무 잦은 업무나 긴 시간이 걸리는 일은 오히려 대리 비용이 크고 초기 소통 시간이 걸리므로 성격에 맞춰 상시 고용과 섞어 써야 함
