## Ⅰ. 개요
- 정의: 명령(C)과 조회(Q) 모델을 분리하고(CQRS), 상태 대신 변화 사건을 저장(Event Sourcing)하는 기술.
- 출제 의도: 대규모 분산 환경에서 읽기/쓰기 성능 최적화 및 데이터 이력 관리의 정밀도 향상 전략 평가.

## Ⅱ. 구성요소
- ASCII 구조도
  [ Command ] -> [ Write DB ] -> [ Event Store ] --(Publish)--> [ Event Bus ]
                                                                    |
  [ Query   ] <- [ Read DB  ] <-------------------------------------+ (Subscribe)
- 구성요소 표
| 구성요소 | 설명 | 비유 |
| :--- | :--- | :--- |
| Command Model | 데이터 변경(Create/Update/Delete)을 담당하는 로직 | 입금/출금 전표 |
| Query Model | 데이터 조회(Read)에 최적화된 단순화된 데이터 모델 | 통장 잔액 조회 |
| Event Store | 발생한 모든 이벤트를 순차적으로 저장하는 Append-only DB | 회계 장부 |
> 요약: 쓰기는 엄격하게, 읽기는 빠르게 수행하도록 아키텍처를 이원화함.

## Ⅲ. 절차
- ASCII 흐름도
  [명령 수신] -> [이벤트 저장] -> [비동기 전파] -> [조회 모델 갱신]
- 4단계 설명
1. 사용자의 변경 요청을 받아 비즈니스 유효성 검사 후 이벤트를 생성함.
2. 생성된 이벤트를 변경 불가능한 상태로 Event Store에 영구 기록함.
3. 메시지 브로커를 통해 이벤트를 발행하여 구독 중인 조회 시스템에 전달함.
4. 조회 전용 DB가 이벤트를 반영하여 최신 상태의 읽기 모델로 동기화함.
> 요약: 데이터의 현재 상태가 아닌 '발생한 사실'들의 누적으로 상태를 재구성함.

## Ⅳ. 문제점
- 데이터 일관성: 쓰기와 읽기 모델 간의 비동기 동기화로 인한 일시적 불일치 발생함.
- 시스템 복잡도: 두 개의 모델과 동기화 메커니즘을 유지해야 하므로 구현 비용 급상승함.

## Ⅴ. 개선방안
- 결과적 정합성: 비즈니스적으로 허용 가능한 시간 내에 데이터 일치 보장 정책 수립 필요함.
- 스냅샷 기술: 이벤트가 너무 많을 경우 중간 상태를 저장하여 상태 재구성 속도 향상함.

## Ⅵ. 전망
- 복잡한 도메인 로직을 가진 금융, 이커머스 시스템의 표준 아키텍처로 입지 강화됨.
- 서버리스 이벤트 처리 기술과의 결합을 통해 실시간 데이터 분석 플랫폼 구축 핵심 기술로 부상함.
- 데이터 감사(Audit) 및 규제 준수가 중요한 산업군에서 변경 이력 추적성 확보를 위해 필수 적용됨.
