# 📖 【암기용】 개념 완전 이해

> 목적: 미들웨어 ESB·MOM·Message Broker를 처음 봐도 완전히 이해하게 만든다. 시험 답안 양식이 아니라, 이해를 위한 설명이다.

## 한눈에
- **개요**: **미들웨어**는 서로 다른 애플리케이션을 직접 연결하지 않고 중간에서 이어주는 **통합(Integration) 계층**이며, ESB·MOM·Message Broker는 그 안에서 메시지를 처리하는 방식이 다른 세 가지 구현 유형이다.
- **왜 필요한가**: 시스템끼리 직접 1:1로 연결하면 시스템 수가 늘수록 연결 수가 기하급수적으로 늘고, 한 시스템 장애가 연결된 모든 시스템으로 전파되며, 인터페이스 하나를 바꿀 때마다 영향 분석 범위가 커진다.
- **핵심 직관**: 모든 부서가 서로 직접 전화하지 않고 우편실·교환대·택배 시스템을 통해 문서를 주고받는 구조다 — 발신자는 수신자가 누구인지, 언제 받는지 몰라도 된다.

## 핵심 용어 정리 (내부에 등장하는 것들)

| 용어 | 의미 | 비유 |
|:---|:---|:---|
| 미들웨어 / EAI | 애플리케이션 간 통신을 중재하는 소프트웨어 계층(전체 상위 개념) | 부서 간 우편실 |
| ESB (Enterprise Service Bus) | 중앙 버스에서 메시지 변환·라우팅·오케스트레이션을 수행하는 미들웨어 | 중앙 전화 교환대 |
| MOM (Message Oriented Middleware) | 큐(Queue) 기반으로 메시지를 비동기 전달하는 미들웨어(JMS 표준) | 우편함 — 넣어두면 수신자가 나중에 확인 |
| Message Broker | topic·stream 기반 publish/subscribe로 대량 이벤트를 중개하는 미들웨어 | 구독자가 있는 뉴스 배포 시스템 |
| Queue | 메시지가 순서대로 쌓이고 **하나의 소비자만** 각 메시지를 가져가는 자료구조(1:1, competing consumers) | 은행 번호표 — 한 사람이 뽑으면 다른 사람은 못 뽑음 |
| Topic | 같은 메시지를 **구독한 모두**에게 전달하는 채널(1:N, pub/sub) | 라디오 방송 — 듣는 사람 모두가 같은 방송을 듣는다 |
| Consumer Group | 같은 topic을 구독하는 소비자 묶음으로, 파티션을 나눠 병렬 소비 | 배달 기사 여러 명이 구역을 나눠 배달 |
| ACK (Acknowledgement) | 소비자가 메시지 처리를 완료했다고 브로커에 알리는 신호 | 택배 수령 확인 서명 |
| DLQ (Dead Letter Queue) | 재시도해도 계속 실패한 메시지를 격리해 쌓아두는 별도 큐 | 반송 불가 우편물 보관함 |
| Idempotency(멱등성) | 같은 메시지를 여러 번 처리해도 결과가 한 번 처리한 것과 같아지는 성질 | 같은 결제 요청을 두 번 눌러도 돈은 한 번만 빠짐 |
| 전달 보장 시맨틱 | 메시지가 몇 번 전달되는지에 대한 약속 — at-most-once/at-least-once/exactly-once | 등기우편(추적·재발송) vs 일반우편(분실 가능) |

## 깊이 이해

### 왜 직접 연동이 폭발하는가 — 숫자로 확인
- 시스템 n개를 점대점(Point-to-Point)으로 직접 연결하면 연결 수는 조합 공식 `n(n-1)/2`를 따른다.
- **예시**: 시스템이 5개면 5×4/2=10개 연결, 10개면 10×9/2=45개 연결이 필요하다. 시스템이 2배(5→10) 늘었을 뿐인데 연결은 4.5배(10→45) 늘어난다.
- 미들웨어(허브형)를 두면 각 시스템은 미들웨어 하나와만 연결하면 되므로, 시스템이 몇 개든 연결 수는 딱 n개다. 시스템 10개 기준 45개 → 10개로 줄어드는 것이 미들웨어의 핵심 효익이다.

### ESB vs MOM vs Message Broker — 무엇이 다른가
- 셋 다 "중간에서 메시지를 처리한다"는 공통점이 있지만 무게 중심이 다르다.
- **ESB**: 메시지 자체보다 **변환·라우팅·오케스트레이션 로직**이 중심이다. SOAP/XML을 REST/JSON으로 바꾸거나, 하나의 요청을 여러 백엔드로 순서대로 호출하는 조율(orchestration)을 수행한다. 레거시 시스템이 서로 다른 프로토콜·포맷을 쓸 때 강점이 있다.
- **MOM**: **비동기 전달 보장** 자체가 중심이다. Queue에 메시지를 넣으면 수신자가 당장 온라인이 아니어도 나중에 처리할 수 있다(시간적 결합 해제). 트랜잭션성 메시지(주문 접수 큐 등)에 적합하다.
- **Message Broker**: **대량 이벤트의 발행·구독**이 중심이다. 하나의 이벤트를 여러 구독자가 각자 다른 목적으로 소비한다(재고 차감, 알림 발송, 통계 집계를 각각 독립적으로 수행).

### Queue vs Topic — 소비자 수로 갈린다
- **Queue(1:1, competing consumers)**: 메시지 하나는 소비자 그룹 안에서 딱 한 명만 가져간다. 소비자를 여러 명 붙이면 부하 분산(load balancing)이 된다.
- **Topic(1:N, pub/sub)**: 메시지 하나를 구독한 소비자 **전원**이 각자 받는다. 재고 서비스와 알림 서비스가 같은 주문 이벤트를 동시에 받아 서로 다른 일을 하는 구조가 이것이다.
- **Kafka의 절충**: topic 안에 파티션을 여러 개 두고, 같은 consumer group 안의 소비자들이 파티션을 나눠 갖는다. 예: topic이 6개 파티션이고 consumer group에 소비자가 3명이면, 각 소비자가 파티션 2개씩 맡아 병렬 처리한다(Queue의 부하분산 + Topic의 구독 개념을 동시에 구현).

### 전달 보장 시맨틱을 숫자로 이해하기
- **at-most-once**: 전송 후 확인 없이 끝 — 네트워크 장애 시 메시지가 유실될 수 있다(전송 1회, 성공 여부 불확실).
- **at-least-once**: ACK을 못 받으면 재전송 — 유실은 없지만 같은 메시지가 2번, 3번 도착할 수 있다. 예: 결제 서비스가 ACK 응답을 놓치면 브로커가 3초 후 같은 결제 메시지를 재전송해, 소비자 쪽에 같은 메시지가 2번 도착한다.
- **exactly-once**: at-least-once의 중복 문제를 **idempotency key**(또는 트랜잭션 커밋)로 소비자 쪽에서 걸러내 "정확히 1번 처리된 것처럼" 만든다. 결제 메시지에 주문 ID를 idempotency key로 붙이면, 같은 주문 ID가 2번 와도 이미 처리된 건 무시한다.
- DLQ는 이 재시도가 계속 실패할 때(예: 3회 재시도 후에도 처리 실패)의 최종 격리 지점이다. DLQ에 쌓인 메시지는 자동 삭제되지 않고 별도 원인 분석·수동 재처리 대상이 된다.

### 비유와 흔한 오해
- **비유**: ESB는 중앙 교환대(모든 통화가 한 곳을 거침), MOM은 우편함(비동기·시간차 수신), Message Broker는 구독형 뉴스 배포(1건 발행 → N명 수신)에 가깝다.
- **오해**: ESB가 모든 통합 문제의 정답은 아니다. 하나의 버스에 모든 로직이 몰리면 그 버스 자체가 병목이 되고, 변경할 때마다 중앙 승인을 거쳐야 해 배포가 느려진다. 이벤트가 많고 팀이 독립적으로 배포해야 하는 MSA 환경에서는 중앙 ESB보다 분산된 Message Broker(Kafka 등) 기반 통합이 더 적합한 경우가 많다.

## 연결 개념
- EAI - 기업 애플리케이션 통합(미들웨어가 구현하는 상위 목표)
- Event-Driven Architecture - 이벤트 발행·구독 기반 비동기 구조(Message Broker의 활용 맥락)
- Saga Pattern - 분산 트랜잭션에서 메시징으로 보상 처리를 조율하는 패턴

## Ⅰ. 개요 및 필요성

- 개요: 미들웨어는 애플리케이션 간 통신과 데이터 교환을 중재하는 계층이다.
- 배경: 직접 연동은 인터페이스 수 증가, 장애 전파, 형식 변환 중복을 만든다.
- 필요성: ESB·MOM·Message Broker를 동기성, 신뢰성, 처리량 요구에 맞게 선택해야 한다.

---

## Ⅱ. 구조 및 구성요소

```text
Producer/System A -> Middleware -> Consumer/System B
                  / Routing
                  / Transformation
                  / Queue/Topic
                  / Monitoring/DLQ
```

| 구성요소 | 역할 | 특이사항 |
|:---|:---|:---|
| ESB | 중앙 라우팅·변환·오케스트레이션 | SOAP/REST, canonical model |
| MOM | 큐 기반 비동기 메시지 전달 | JMS, IBM MQ, ActiveMQ |
| Message Broker | topic·stream 기반 pub/sub | Kafka, RabbitMQ, Pulsar |
| DLQ/Monitoring | 실패 메시지 격리·추적 | 재처리와 알림 기준 필요 |

> 요약: 미들웨어는 통신 중재, 변환, 큐·토픽, 실패 격리를 제공하며 유형별 중심 기능이 다르다.

---

## Ⅲ. 동작원리 및 흐름도

```text
메시지 생성 -> 라우팅/변환 -> 큐 또는 토픽 저장 -> 소비자 전달 -> ACK/Retry -> DLQ/모니터링
```

| 단계 | 처리 내용 | 검증 기준 |
|:---:|:---|:---|
| 1 | Producer가 표준 메시지 생성 | schema registry 적용 |
| 2 | Middleware가 라우팅·변환 수행 | 변환 실패율 1% 이하 |
| 3 | Queue/Topic에 메시지 저장 | replication factor 3 |
| 4 | Consumer가 처리 후 ACK·재시도 | DLQ 비율 0.1% 이하 |

> 요약: 동작은 메시지 생성, 변환·라우팅, 저장, 소비, 실패 격리 순서로 신뢰성 있는 통합을 수행한다.

## Ⅳ. 특징

| 구분 | 직접 연동 | ESB·MOM·Broker | 수치·판단 기준 |
|:---|:---|:---|:---|
| 연결 구조 | n:n 직접 호출 | 중간 계층으로 결합도 완화 | 인터페이스 수 30% 이상 감소 |
| 처리 방식 | 동기 호출 중심 | 비동기·버퍼링 가능 | p95 지연·lag 측정 |
| 장애 영향 | 호출자까지 전파 | 큐·DLQ로 격리 | DLQ 0.1% 이하 |
| 한계 | 구조 단순 | 운영 복잡도 증가 | broker cluster 운영 필요 |

> 요약: 미들웨어는 결합도와 장애 전파를 줄이지만, 메시지 중복·순서·운영 지표를 설계해야 한다.

## Ⅴ. 심화 비교 및 적용 판단

| 구분 | 기존/대안 | 본 키워드 | 선택 기준 |
|:---|:---|:---|:---|

| 운영/위험 | 변경 영향 직접 전파 | 스키마·DLQ·재처리 통제 | 중복 처리 허용 여부 |

> 요약: 시스템 수와 비동기 요구가 증가하면 직접 연동보다 미들웨어 기반 통합이 적합하다.

| 리스크 | 원인 | 대응 방안 | 확인 지표 |
|:---|:---|:---|:---|
| 메시지 중복 | 재시도·ACK 실패 | idempotency key, dedup store | 중복 처리 건수 |
| 순서 역전 | 병렬 consumer | partition key, single consumer | out-of-order 비율 |
| 적체 | consumer 처리 지연 | autoscaling, backpressure | consumer lag |

> 요약: 메시징 리스크는 중복, 순서, 적체이며 idempotency와 lag 관리가 필요하다.

| 점검 항목 | 목표 기준 | 측정 방법 |
|:---|:---|:---|
| 처리량 | 목표 TPS 대비 120% 용량 | load test |
| 신뢰성 | DLQ 0.1% 이하 | broker metric |
| 운영 지연 | p95 end-to-end latency 목표 충족 | tracing, lag monitor |

> 요약: 성공 여부는 처리량, DLQ 비율, end-to-end 지연으로 판단한다.

## Ⅵ. 실무 적용 및 결론

**적용 방안 3개 (필수 - 단계별 또는 항목별):**
1. 중앙 변환·오케스트레이션이 필요한 레거시 EAI는 ESB, 서비스 간 비동기 이벤트는 Kafka·RabbitMQ 기반 broker 선택
2. 메시지 schema registry, idempotency key, retry policy, DLQ 재처리 절차를 표준 인터페이스 계약에 포함
3. broker lag, DLQ, p95 latency, throughput을 Prometheus·Grafana로 관측하고 장애 시 circuit breaker와 backpressure 적용

**결론 (2줄):**
- 기술사 판단: 레거시 표준 통합은 ESB, 트랜잭션성 큐는 MOM, 대량 이벤트 스트리밍은 Kafka형 broker를 선택
