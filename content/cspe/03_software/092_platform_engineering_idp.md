# 📖 【암기용】 개념 완전 이해

> 목적: 플랫폼 엔지니어링과 IDP를 개발자 self-service와 운영 거버넌스를 동시에 제공하는 체계로 이해하게 만든다. 시험 답안 양식이 아니라, 이해를 위한 설명이다.

## 한눈에
- **개요**: IDP(Internal Developer Platform, 내부 개발자 플랫폼)는 개발자가 **표준 경로(Golden Path)** 로 서비스 생성·배포·관측을 **셀프서비스**로 수행하는 내부 플랫폼이다.
- **왜 필요한가**: 팀마다 CI/CD·Kubernetes 설정·보안 정책을 각자 만들면 같은 작업이 팀 수만큼 중복되고, 보안·배포 방식이 팀마다 달라 사고 발생 시 원인 파악이 어려워진다.
- **핵심 직관**: 개발자에게는 이미 깔린 도로와 표지판(Golden Path)을 주고, 플랫폼팀은 그 도로의 교통법규와 안전장치(정책·SLO)를 관리하는 방식이다.

## 핵심 용어 정리 (내부에 등장하는 것들)

| 용어 | 의미 | 비유 |
|:---|:---|:---|
| IDP(Internal Developer Platform) | 개발자 셀프서비스와 운영 표준을 함께 제공하는 내부 플랫폼 — 이 개념의 대상 | 상위 키워드 |
| Self-Service(셀프서비스) | 개발자가 티켓·승인 대기 없이 스스로 자원을 만드는 방식 | 상위 키워드 |
| Golden Path(Paved Road, 표준 경로) | 플랫폼팀이 미리 검증해둔 표준 개발·배포 경로 | 이미 깔린 고속도로 |
| Service Catalog(서비스 카탈로그) | 서비스별 소유자·중요도(tier)·SLO·의존성을 등록한 명부 | 회사 조직도 겸 명함첩 |
| Developer Portal(개발자 포털) | 서비스 생성·문서·요청을 처리하는 셀프서비스 창구(예: Backstage) | 관공서 민원포털 |
| SLO(Service Level Objective) | 플랫폼 자체가 지켜야 할 신뢰도 목표치(가용성 등) | 상위 키워드 |
| Scorecard(스코어카드) | 서비스가 보안·배포·문서 표준을 얼마나 지키는지 항목별로 점수화한 카드 | 성적표 |
| Policy as Code | 보안·규정을 코드로 정의해 자동으로 검사·강제하는 방식 | 자동 채점기 |
| Escape Hatch(예외 경로) | 표준 경로를 못 쓰는 특수 상황을 위한 승인 기반 예외 통로 | 비상구 |

## 깊이 이해

### 왜 필요했나 (배경)
- DevOps 확산 초기에는 "팀에 자율권을 주면 알아서 잘한다"는 원칙이 강조됐지만, 팀 수가 늘면서 팀마다 Dockerfile·Helm chart·CI 파이프라인을 처음부터 새로 만드는 중복이 쌓였다. 예: 10개 팀이 각자 컨테이너 배포 설정을 만들면 같은 작업을 10번 반복하면서 보안 스캔 적용 여부·로깅 표준까지 팀마다 달라진다.
- IDP는 이 중복을 플랫폼팀이 한 번 만들어 모두가 재사용하는 "제품"으로 바꾼다. 핵심은 "표준을 강제"하는 게 아니라 "표준을 따르는 게 가장 쉬운 길"로 만드는 것이다.

### 작동 원리 — 요청부터 관측까지
- 개발자가 포털(또는 CLI)에서 "신규 서비스 생성"을 요청하면, 미리 정의된 Golden Path 템플릿이 Git 저장소, Dockerfile, Helm chart, CI 파이프라인, observability 대시보드까지 한 번에 생성한다. 이 전 과정이 약 10분 내에 끝나도록 설계하는 것이 IDP 채택의 실질적인 목표치다.
- 생성된 서비스는 Service Catalog에 소유자(owner)·중요도(tier)·SLO와 함께 등록되고, Scorecard가 정책 준수 여부(보안 스캔 통과, 로깅 표준 적용, owner 지정 등)를 점수로 매긴다. 예: 점검 항목 5개(보안스캔·SLO등록·owner지정·라이선스검사·로깅표준) 중 4개를 충족하면 스코어카드 80점이다.

### Golden Path와 Escape Hatch — 표준과 예외의 균형
- 표준 경로를 강제로만 밀어붙이면 특수한 요구가 있는 팀이 우회로를 몰래 만들어버려 오히려 표준이 무너진다. 그래서 IDP는 표준 경로 외에 Escape Hatch(예외 승인 경로)를 함께 둔다. 예외는 승인 이력이 남고, 예외가 많아지는 팀·항목은 플랫폼팀이 Golden Path 자체를 개선하는 신호로 활용한다.
- 표준 템플릿 채택률(예: 신규 서비스의 80% 이상이 Golden Path로 생성)을 지표로 삼으면, 표준이 실제로 "가장 쉬운 선택"이 되고 있는지 확인할 수 있다.

### Platform SLO — 플랫폼 자체도 신뢰도 목표가 있다
- IDP도 하나의 제품이므로 자체 가용성 목표(Platform SLO)를 가진다. 예: SLO 99.9%는 연간 허용 다운타임이 약 8.76시간(365일 × 24시간 × 0.1%)이라는 뜻이다. 이 기준을 넘기면 플랫폼팀이 사후 분석(postmortem)을 수행한다.
- 플랫폼이 곧 모든 팀의 배포 통로이므로, 플랫폼 장애는 단일 장애점(SPOF)이 된다. 그래서 IDP를 설계할 때는 배포 파이프라인·포털 자체의 이중화·DR(재해복구) 계획도 함께 잡아야 한다.

### 비유와 흔한 오해
- **비유**: 회사 구내식당이 재료 구매·위생·결제를 표준화해두면, 직원들이 매번 자기 주방을 차리지 않고도 끼니를 해결할 수 있는 것과 같다. 다만 식당이 문을 닫으면 다들 굶으므로, 식당(플랫폼)의 안정성 자체가 중요해진다.
- **오해**: IDP를 "쿠버네티스 관리 포털 UI를 만드는 일"로 오해하기 쉽다. 실제로는 개발자 경험(DevEx), 표준 템플릿, 보안·비용 정책, 플랫폼 자체 SLO를 하나의 제품처럼 로드맵을 갖고 운영하는 조직 활동이다. 포털만 만들고 방치하면 개발자들이 다시 각자 방식으로 돌아간다.

## 연결 개념
- GenAI DevOps Automation — IDP의 표준 경로 위에서 실제 배포·운영 자동화가 얹히는 관계
- Golden Path/Service Catalog — IDP를 구성하는 핵심 실행 메커니즘
- DORA 지표 — IDP 도입 효과(리드타임·변경실패율 개선)를 검증하는 공통 척도

# 📝 【답안용】 시험 답안 템플릿

> 목적: 시험장에서 25분에 그대로 쓰는 답안 양식. 작성방식(추상표현 금지·수치·도식·문제유형 전환)을 엄격히 지킨다.
> 핵심: IDP 답안은 포털 설명이 아니라 self-service, paved road, SLO, scorecard, governance를 연결해야 한다.

## 핵심 인사이트 (3줄 요약)

> 1. **본질**: IDP는 개발팀이 표준화된 도구·템플릿·파이프라인·운영 기능을 self-service로 사용하는 내부 개발자 플랫폼이다.
> 2. **가치**: 개발팀의 반복 인프라 작업을 줄이고 플랫폼팀은 보안, 배포, 관측성, 비용 정책을 공통 경로에 내장한다.
> 3. **판단 포인트**: IDP는 도구 모음이 아니라 내부 제품이므로 사용자 여정, SLO, adoption, scorecard로 운영해야 한다.

## 출제 의도 및 답안 포인트

| 출제 의도 | 반드시 짚을 핵심 | 감점 회피 포인트 |
|:---|:---|:---|
| 플랫폼 엔지니어링 이해 확인 | IDP, self-service, golden path, paved road | Kubernetes 포털만으로 설명하지 않음 |
| DevEx·거버넌스 판단 확인 | SLO, scorecard, 정책 내장, 표준 템플릿 | 중앙 통제와 개발자 자율성 균형을 누락하지 않음 |
| 운영 성과 측정 확인 | lead time, adoption, MTTR, compliance | 도구 도입 건수만 성과로 제시하지 않음 |
> 요약: IDP는 개발자가 표준 경로로 배포하고 플랫폼팀이 정책·관측·비용을 내장하는 제품형 운영체계이다.

## Ⅰ. 개요 및 필요성

- 개요: IDP는 내부 개발자 셀프서비스 플랫폼이다.
- 배경: 클라우드, Kubernetes, CI/CD를 팀별로 구현하면 중복 파이프라인과 보안 설정 편차가 발생한다.
- 필요성: Golden Path, Service Catalog, SLO, Scorecard로 신규 서비스 생성 리드타임과 표준 준수율을 측정해야 한다.

---

## Ⅱ. 구조 및 구성요소

```text
Developer Portal/CLI -> Service Catalog -> Golden Path Template
-> CI/CD/IaC/Policy -> Runtime Platform
-> Observability/SLO/Scorecard -> Feedback Loop
```

| 구성요소 | 역할 | 산정 포인트 |
|:---|:---|:---|
| Developer Portal | 서비스 생성·문서·요청 창구 | Backstage 등 포털 |
| Service Catalog | 서비스 소유자·의존성 관리 | owner, tier, SLO |
| Golden Path | 표준 템플릿과 파이프라인 | paved road, 예외 승인 |
| Platform Governance | 정책·보안·비용 통제 | Policy as Code, scorecard |
> 요약: IDP는 포털, 카탈로그, 표준 경로, 정책·관측 계층이 결합된 내부 플랫폼이다.

---

## Ⅲ. 동작원리 및 흐름도

```text
개발자 요청 -> 템플릿 선택 -> 저장소/파이프라인 생성
-> IaC로 런타임 구성 -> 배포 -> 관측성 대시보드 생성
-> scorecard 점검 -> 피드백으로 golden path 개선
```

| 단계 | 처리 내용 | 검증 기준 |
|:---:|:---|:---|
| 1 | 서비스 카탈로그 등록 | owner·tier·SLO 필수 |
| 2 | Golden path 템플릿 적용 | 표준 파이프라인 생성률 |
| 3 | CI/CD와 IaC 실행 | 배포 실패율 15% 이하 |
| 4 | Observability와 SLO 연결 | dashboard·alert 자동 생성 |
| 5 | Scorecard로 준수 점검 | 정책 준수율 95% 이상 |
> 요약: IDP는 서비스 생성부터 배포, 관측, 점검까지 표준 경로를 자동 제공한다.

## Ⅵ. 실무 적용 및 결론

**적용 방안 3개:**
1. 상위 3개 개발자 여정인 신규 서비스 생성, 배포, 장애 확인을 먼저 IDP golden path로 구현함.
2. Service catalog에 owner, tier, dependency, SLO를 필수 필드로 두고 scorecard를 PR·배포 게이트와 연결함.
3. 플랫폼팀은 월간 adoption, lead time, 플랫폼 SLO, 개발자 만족도 점수를 제품 지표로 관리함.

**결론 (2줄):**
- 기술사 판단: 개발팀과 서비스 수가 많고 클라우드 운영 편차가 크면 IDP를 적용하고, 소규모 조직은 핵심 템플릿부터 시작함.
- 향후 방향: IDP는 AI 보조, FinOps, security guardrail, service catalog를 통합하는 개발자 운영 허브로 발전함.
