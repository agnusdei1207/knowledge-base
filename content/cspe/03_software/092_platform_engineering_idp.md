## 핵심 인사이트 (3줄 요약)
- 데브옵스(DevOps) 시대에 개발자가 인프라(K8s, CI/CD, AWS) 설정까지 다 떠안게 되면서 극심한 피로도(Cognitive Load)를 겪자, 이를 해결하기 위해 등장한 개념.
- **내부 개발자 플랫폼 (IDP, Internal Developer Platform)**을 구축하여, 복잡한 인프라 툴체인을 하나의 셀프서비스 포털(Self-service Portal)로 추상화함.
- "You build it, You run it(네가 만든 건 네가 운영해라)"이라는 DevOps의 이상향을 유지하면서도, 개발자가 오직 '비즈니스 로직(코드)' 개발에만 집중할 수 있게 인프라를 '제품화(Platform as a Product)'하는 것이 핵심 철학임.
---
## Ⅰ. 개요 및 필요성
- **개요**: 소프트웨어 개발 팀이 자율적으로 인프라를 프로비저닝하고 배포할 수 있도록, 도구와 프로세스를 통합한 셀프서비스 내부 플랫폼을 설계하고 구축하는 학문(가트너 선정 10대 전략 기술).
- **필요성**: MSA와 K8s가 도입되면서 개발자가 알아야 할 툴(Docker, Helm, Terraform, Datadog 등)이 수십 개로 늘어남. 결과적으로 코딩할 시간은 없고 인프라 설정(Yaml 파일)만 뜯어고치다 퇴근하는 '인지 부하(Cognitive Load)' 폭발 사태가 벌어짐. 인프라 전문가(플랫폼 팀)가 이 복잡성을 숨겨주는 '자판기'를 만들어 줄 필요가 생김.
---
## Ⅱ. 아키텍처 및 핵심 원리
- **IDP (내부 개발자 플랫폼) 구조**:
  1. **Developer Control Plane (개발자 제어면)**: 개발자가 접속하는 웹 포털 (예: Backstage). 버튼 클릭 한 번으로 "Spring Boot + MySQL 환경의 마이크로서비스 뼈대"를 즉시 발급받음.
  2. **Integration & Delivery (통합/배포 계층)**: GitHub Actions, ArgoCD 등이 포털의 명령을 받아 실제 코드를 빌드하고 배포함.
  3. **Infrastructure (인프라 계층)**: AWS, GCP, K8s 클러스터 등 하단의 복잡한 클라우드 자원.
- **플랫폼 엔지니어링의 핵심 철학**:
  - **Platform as a Product**: 플랫폼 팀은 개발자(내부 고객)를 만족시키기 위해 제품 기획하는 PM처럼 행동해야 함.
  - **Golden Path (골든 패스)**: "우리가 세팅해 놓은 이 길(표준 스택)로 가면 가장 빠르고 안전하게 배포할 수 있어"라고 유도하는 표준화된 개발 경로.

```text
[ 플랫폼 엔지니어링 도입 전후 비교 ]

 [ 도입 전: DevOps의 저주 ] 
 개발자 ➡️ "DB 생성법 좀 알려주세요" ➡️ 인프라팀 (티켓 대기 3일)
 개발자 ➡️ "K8s 배포 야믈(yaml) 파일 에러 났어요 ㅠㅠ" (인지 부하 폭발 🤯)

 [ 도입 후: IDP 셀프 서비스 ]
 개발자 ➡️ [ IDP 웹 포털 접속 ] ➡️ "신규 서비스 A (Spring Boot) 생성" 버튼 클릭
                   ⬇️ (플랫폼이 인프라/CI-CD/DB/모니터링 자동 세팅)
            (개발자는 즉시 비즈니스 코드만 짜서 Git Push 하면 끝! 🥳)
```

## Ⅲ. 비교 및 연결
| 구분 | SRE (사이트 신뢰성 엔지니어링) | Platform Engineering (플랫폼 엔지니어링) |
|---|---|---|
| **최우선 목표** | 시스템의 안정성 (가용성, MTTR 단축) | **개발자의 생산성 (인지 부하 감소)** |
| **주요 고객** | 최종 사용자 (시스템이 안 죽게 함) | **내부 개발자 (개발자가 코딩만 하게 함)** |
| **주요 결과물** | SLI/SLO 지표, 장애 복구 자동화 스크립트 | **IDP (내부 개발자 플랫폼 포털)** |
| **역할 비유** | 소방관, 응급구조대 | **고속도로 건설 노동자** |
---
## Ⅳ. 실무 적용 및 기술사 판단
- **DevOps는 죽었는가?**: 플랫폼 엔지니어링이 등장하면서 "DevOps is Dead"라는 자극적 문구가 유행함. 하지만 기술사적 관점에서 플랫폼 엔지니어링은 DevOps를 부정한 것이 아니라, DevOps가 실패한 지점(개발자에게 인프라 책임을 과도하게 떠넘긴 문제)을 해결하여 **"진정한 DevOps를 완성하기 위한 다음 단계(Next Step)"**로 해석해야 함.
- **Backstage의 부상**: Spotify가 오픈소스로 공개한 'Backstage'가 IDP 구축의 글로벌 표준 프레임워크(De facto)로 자리 잡음. 조직에 플랫폼 엔지니어링을 도입하려면 거창하게 처음부터 짜는 것이 아니라, Backstage에 사내 플러그인을 하나씩 붙여나가는 애자일한 접근이 필수적임.
---
## Ⅴ. 기대효과 및 결론
- 신규 개발자가 입사해서 첫 코드를 상용 서버에 배포하기까지 걸리는 시간(Lead Time)을 수 주(Weeks)에서 단 몇 시간(Hours)으로 단축함.
- 개발팀은 '비즈니스 가치 창출'에, 플랫폼 팀은 '시스템 인프라 최적화'에 각자 100% 집중할 수 있게 하는 현대 클라우드 네이티브 조직의 최종 진화 형태임.

### 📌 관련 개념 맵
- MSA / K8s (복잡성 증가) ➡️ DevOps 피로도 ➡️ IDP / 플랫폼 엔지니어링 ➡️ Golden Path (골든 패스)

### 📈 관련 키워드 및 발전 흐름도
- Silo (개발/운영 분리) ➡️ DevOps (개발/운영 통합) ➡️ DevOps 피로도 발생 ➡️ Platform Engineering (IDP 기반 셀프서비스)

### 👶 어린이를 위한 3줄 비유 설명
1. 뷔페에 갔는데 접시도 직접 굽고, 포크도 직접 깎아서 써야 한다면 너무 힘들겠죠? (이게 실패한 데브옵스예요).
2. 플랫폼 엔지니어링은 뷔페에 '자동 접시 자판기(IDP)'를 설치해 주는 거예요.
3. 요리사(개발자)는 자판기에서 접시를 꺼내서 맛있는 요리(코드)를 담는 데만 집중하면 되니까, 식당이 훨씬 빨리 돌아간답니다!
