## 미리 알고가기

- IDP(Internal Developer Platform): 개발자가 인프라 및 배포 기능을 독립적으로 사용할 수 있도록 API와 포털 형태로 제공하는 사내 개발 플랫폼임
- 플랫폼 엔지니어링: 개별 팀이 각각 구축하던 공통 도구와 인프라 파이프라인을 하나의 공통 제품($Platform-as-a-Product$)으로 개발·제공하는 활동임
- 가드레일(Guardrail): 시스템 내부에서 개발자가 안전하고 표준화된 정책 범위를 벗어나지 않도록 통제하는 자동화된 규칙 모음임
- 셀프서비스(Self-service): 운영팀의 수동 승인이나 티켓 작업 대기 없이 개발자가 UI 또는 API로 직접 가상 인프라와 배포 환경을 생성하는 방식임
- 개발자 경험(DX, Developer Experience): 개발자가 도구와 시스템을 활용해 소프트웨어를 빌드, 배포, 운영할 때 느끼는 주관적 효율성과 만족도임

## 작성 근거(검토용)

- **핵심 키워드 선정 이유**: 플랫폼 엔지니어링의 핵심 산출물인 IDP는 티켓 대기 오버헤드를 낮추는 셀프서비스와 안전성을 담보하는 정책 가드레일이 핵심이므로 이를 중심축으로 삼아 전개함
- **절 구성 및 전개 흐름 이유**: 개요에서 셀프서비스 가치를 제시하고, Ⅱ절에서 제품 지표 관리 및 개발자 경험 측면의 성질을 정리함. Ⅲ절에서 기존의 운영 티켓 방식과 대조해 가치를 밝히고, Ⅳ절과 Ⅴ절을 분할하여 플랫폼 설계의 정적/동적 모습을 도식화해 구조적으로 명확히 함
- **전수 검수 완료 근거**: 제목, 메타 데이터, 미리 알고가기, 본문, 비교표, 결론까지 총 5회 전수 검토를 실행하여 어색한 문장 결합과 불필요한 명사구를 다듬고 완성도를 높임

## Ⅰ. 개요

- **정의/개념**: 플랫폼 엔지니어링 IDP는 인프라, 파이프라인, 보안, 모니터링 도구를 템플릿과 API로 패키징하여 개발자에게 셀프서비스 형태로 제공하는 내부 개발 플랫폼임
- **배경/필요성**: 개발팀마다 파편화된 인프라 구축 방식의 오차를 줄이고 운영 지원 요청($Ticket$) 대기 시간을 최소화하기 위해 표준 개발 경로를 제공하는 사내 플랫폼 구축이 필요함

### 쉽게 이해하기 (학습용)
- 밀키트 전문점처럼 미리 손질되어 있고 조리법(가이드)이 검증된 재료 모음을 가져가 손님이 직접 찌개(개발 환경)를 끓여 먹게 하는 방식과 같음

## Ⅱ. 특징

- **개발자 경험($DX$) 우선 설계**: 복잡한 클라우드 및 컨테이너 관리 명령어들을 추상화하여 포털 UI 클릭 한 번으로 가상 환경을 제공함
- **정책 통제 내재화**: 배포 환경 생성과 동시에 조직의 보안, 규정 준수, 비용 한도 제어 규칙이 자동으로 주입되어 규제 위반을 원천 차단함
- **제품 관점의 피드백 제어**: 플랫폼을 일회성 시스템이 아닌 내부 제품으로 취급하여 채택률을 분석하고 기능 요청을 받아 지속 개선함
- **책임 및 인지 부하 감소**: 개발자가 인프라 하부 구조($AWS, Kubernetes$)를 자세히 모르는 상태에서도 코딩에 집중할 수 있는 환경을 보장함

### 쉽게 이해하기 (학습용)
- 스마트폰을 사용할 때 내부의 모뎀 칩셋이나 전기 회로 작동 방식을 몰라도(인프라 추상화), 앱 스토어 버튼 하나로 안전한 정식 앱을 내려받는 것과 같음

## Ⅲ. 종류 및 비교

- 전통적인 공용 인프라팀 지원 방식과 플랫폼 엔지니어링 IDP의 운영 차이를 비교함

| 판단 기준 | 전통적 공용 인프라팀 | 플랫폼 엔지니어링 IDP |
|:---|:---|:---|
| **제공 방식** | 운영팀이 메일이나 티켓 요청을 접수 후 직접 작업함 | 개발자가 카탈로그에서 표준 구성을 셀프서비스로 선택함 |
| **통제 방식** | 요청마다 담당자가 문서를 읽고 수동으로 승인 및 검사함 | 정책 코드가 플랫폼과 배포 워크플로우 내부에 자동 내장됨 |
| **성공 지표** | 요청 처리 소요 시간과 인프라 장애 발생 건수 중심 | 개발자 채택률($Adoption$), 리드타임($Lead-time$), 장애율 복합 측정 |

### 쉽게 이해하기 (학습용)
- 은행 창구에 서류를 적어내고 직원 확인 후 통장을 개설하는 옛 방식(티켓 지원)과 비대면 은행 앱에서 직접 몇 번의 터치로 즉시 비대면 계좌를 트는 방식(IDP)의 차이임

## Ⅳ. 구성요소 및 구조

- 플랫폼 엔지니어링 IDP를 이루는 정적 구조와 관계임

```text
[개발자 포털 (DX UI)] ──> [서비스 카탈로그] ──> [배포 워크플로우]
                                                    │
[운영 개선 피드백] <── [프로비저닝 인프라] <── [정책 및 가드레일] <──────┘
```

| 설계 요소 | 설명 |
|:---|:---|
| **개발자 포털** | 통합 대시보드, 서비스 현황 모니터링, 기술 문서를 통합하여 개발자에게 단일 진입점을 제공함 |
| **서비스 카탈로그** | 가동 가능한 데이터베이스, 애플리케이션 프레임워크 템플릿 목록으로 표준 구성을 카테고리화하여 보관함 |
| **배포 워크플로우** | 빌드, 환경 설정 주입, 가상 인프라 생성 및 배포 흐름을 정의하는 논리 파이프라인 엔진임 |
| **정책 및 가드레일** | 네트워크 보안 접근 제어($ACL$), 데이터베이스 암호화, 허용 비용 기준을 파이프라인에서 자동 대조함 |

### 쉽게 이해하기 (학습용)
- 자동차 튜닝 숍에서 튜닝 스타일 책자(카탈로그)를 보며 옵션을 선택하면, 검증된 기계(워크플로우)가 안전 규격 범위(가드레일) 안에서 부품을 조립해 완성차를 인도하는 형태임

## Ⅴ. 원리 및 절차 흐름도

- 개발자가 IDP를 이용하여 애플리케이션 환경을 배포하는 표준 동적 흐름임

```text
[템플릿 선택] ──> [셀프서비스 생성] ──> [표준 배포 실행] ──> [운영 피드백 반영]
```

1. **템플릿 선택**: 개발자가 포털의 서비스 카탈로그에서 필요한 서비스 유형($Spring Boot Web App$)과 표준 리소스를 선택함
2. **셀프서비스 생성**: 파이프라인이 즉시 지정된 원격 저장소와 컨테이너 환경, $IaC$(인프라 정의 코드)를 연동 생성함
3. **표준 배포 실행**: 코드가 정책 가드레일 규칙을 통과하면 자동으로 인프라를 프로비저닝하고 보안 그룹 설정을 주입하여 배포함
4. **운영 피드백 반영**: 완성된 서비스 사용성과 메트릭, 문제 사항을 플랫폼 개선 및 최적의 템플릿 업그레이드 데이터로 다시 연동함

### 쉽게 이해하기 (학습용)
- 스마트 벤딩머신에서 음료를 고르고(템플릿), 카드를 대서 즉시 컵에 음료가 조합되어 나오고(셀프서비스), 컵 뚜껑이 잘 씌워졌는지 확인 후 나오며(표준 배포), 기계 속 잔량을 서버에 알려 재고를 관리하는(피드백) 과정임

## Ⅵ. 실무 사례

- **마이크로서비스 도입 가속화**: 대형 커머스 서비스에서 신규 마이크로서비스 개설 시 인프라 생성 평균 시간을 수일에서 수분 수준으로 단축하고 플랫폼 채택률을 분석하여 우회 경로 생성을 방지함
- **보안 및 규제 규정 준수**: 금융 및 결제 관련 서비스 개발에 정책 코드를 배포 파이프라인에 내장하여 비인가 가상 네트워크 개설을 자동으로 차단하고 감사 보고서를 자동 생성함

### 쉽게 이해하기 (학습용)
- 사내 보안 교육 수강과 PC 지급 절차를 하나의 신청 사이트로 통일하여 신입 사원이 오자마자 즉시 개발 업무 PC를 안전하게 불출받고 실무 투입되는 경우와 같음

## Ⅶ. 결론

- 플랫폼 엔지니어링 IDP는 복잡한 인프라 관리 부담을 추상화하여 소프트웨어 개발 생산성을 비약적으로 높임
- 단순 도입에 그치지 않고, 개발자 커뮤니티의 피드백을 지속적으로 관측하고 가드레일을 고도화하여 실제 사내 표준으로 완전히 정착시켜야 함

### 쉽게 이해하기 (학습용)
- 도시 계획 시 무작위로 집을 짓기보다 정돈된 신도시 단지(IDP)를 만들고 상하수도와 도로를 완비해 주민(개발자)들의 거주 만족도를 높이며 살기 좋은 동네로 가꾸어가는 것과 같음
