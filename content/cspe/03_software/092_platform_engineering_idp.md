## 미리 알고가기

- IDP는 Internal Developer Platform의 약자로 개발자용 셀프서비스 플랫폼을 뜻함
- 플랫폼 엔지니어링은 공통 인프라와 배포와 관측 기능을 제품처럼 제공하는 접근임
- 목표는 개발자 자율성과 운영 표준을 동시에 높이는 것임

## Ⅰ. 개요

- **정의/개념**: 플랫폼 엔지니어링 IDP는 애플리케이션 팀이 표준화된 배포 경로와 인프라 템플릿과 보안 정책과 관측 기능을 셀프서비스로 이용할 수 있도록 내부 플랫폼을 제품처럼 설계하고 운영하는 접근임
- **배경/필요성**: 마이크로서비스와 클라우드 환경이 확산되면서 각 팀이 인프라와 배포 체계를 개별 구축하면 생산성 편차와 운영 복잡도가 커지므로, 공통 기반을 플랫폼으로 제공할 필요가 있음

## Ⅱ. 특징

- 개발자 경험을 제품 지표로 관리하며 셀프서비스를 제공함
- 표준 배포 경로와 보안 정책을 플랫폼에 내장해 편차를 줄임
- 플랫폼 팀과 제품 팀의 책임 경계를 명확히 해야 효과가 유지됨
- 과도한 중앙집중 설계는 현장 요구를 흡수하지 못해 우회 사용을 부를 수 있음

## Ⅲ. 종류 및 비교

| 판단 기준 | 전통적 공용 인프라팀 | 플랫폼 엔지니어링 IDP |
|:---|:---|:---|
| 제공 방식 | 요청 기반 지원 | 셀프서비스 제품형 제공 |
| 강점 | 중앙 통제 용이 | 개발 속도와 표준화 동시 확보 |
| 한계 | 대기 시간과 병목 발생 | 초기 투자와 제품 운영 역량 필요 |
| 성공 기준 | 운영 안정성 | 개발자 경험과 채택률과 안정성 |

## Ⅳ. 구성요소 및 구조

| 구성요소 | 설명 |
|:---|:---|
| Service Catalog | 표준 서비스와 템플릿을 카탈로그로 제공해 시작 비용을 낮춤 |
| Delivery Workflow | 빌드와 배포와 승인 절차를 내장해 일관된 출시 경로를 제공함 |
| Policy and Guardrail | 보안과 비용과 규정 준수 기준을 기본값으로 강제함 |
| Developer Portal | 문서와 상태와 요청 경로를 통합해 개발자 경험을 높임 |

## Ⅴ. 원리 및 절차 흐름도

```text
+-------------+     +-------------+     +-------------+     +-------------+
| 템플릿 선택    | --> | 셀프서비스 생성  | --> | 표준 배포 실행  | --> | 운영 피드백 수집 |
+-------------+     +-------------+     +-------------+     +-------------+
```

1. **템플릿 선택**: 개발 팀이 카탈로그에서 표준 구성을 고름
2. **셀프서비스 생성**: 저장소와 파이프라인과 인프라를 자동 생성함
3. **표준 배포 실행**: 정책이 내장된 경로로 변경을 배포함
4. **운영 피드백 수집**: 사용성 지표와 장애 지표를 플랫폼 개선에 반영함

## Ⅵ. 문제점 및 해결 방안

1. 문제: 플랫폼이 현장 서비스 패턴을 충분히 반영하지 못하면 개발팀이 우회 경로를 만들며 표준화 효과가 무너질 수 있음
   - 해결방안: product discovery와 template feedback loop를 운영하고 platform adoption rate와 workaround ratio로 검증함
2. 문제: 셀프서비스를 열어도 정책 가드레일이 약하면 속도 향상이 곧 보안과 비용 리스크 증가로 이어질 수 있음
   - 해결방안: policy-as-code를 내장하고 compliant deployment rate와 policy exception count로 검증함
3. 문제: 플랫폼 팀이 운영자 시각에만 머무르면 개발자 경험이 낮아져 사용성이 빠르게 떨어질 수 있음
   - 해결방안: developer journey metric을 관리하고 time-to-first-deploy와 developer satisfaction score로 검증함

## Ⅶ. 적용 사례

- 사내 마이크로서비스 플랫폼에서는 카탈로그 기반 셀프서비스를 제공하고, platform adoption rate와 workaround ratio로 결과를 확인함
- 금융권 공통 배포 플랫폼에서는 정책 코드를 내장하고, compliant deployment rate와 policy exception count로 결과를 확인함
- 대규모 개발 조직에서는 개발자 포털 경험을 측정하고, time-to-first-deploy와 developer satisfaction score로 결과를 확인함

## Ⅷ. 결론

플랫폼 엔지니어링 IDP의 성패는 공통 기능을 많이 모으는 데 있지 않고 개발자 자율성과 운영 표준을 동시에 높이는 제품형 플랫폼으로 운영하는 데 있음.
