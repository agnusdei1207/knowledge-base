## Ⅰ. 개요
- 정의: 고성능 분산 스트리밍 플랫폼인 카프카의 핵심 논리적/물리적 데이터 관리 구조.
- 출제 의도: 대규모 병렬 처리와 데이터 순서 보장을 위한 내부 메커니즘 심화 이해도 평가.

## Ⅱ. 구성요소
- ASCII 구조도
  < Topic >
  [ Partition 0 ] | Msg 0 | Msg 1 | Msg 2 | (Offset)
  [ Partition 1 ] | Msg 0 | Msg 1 | (Offset)
  [ Partition 2 ] | Msg 0 | Msg 1 | Msg 2 | Msg 3 | (Offset)
- 구성요소 표
| 구성요소 | 설명 | 비유 |
| :--- | :--- | :--- |
| 토픽 (Topic) | 메시지를 구분하는 논리적인 분류 단위 | 신문사/카테고리 |
| 파티션 (Partition) | 토픽을 분산 처리하기 위해 나눈 물리적 저장 단위 | 배송 트럭/차선 |
| 오프셋 (Offset) | 파티션 내에서 메시지의 위치를 나타내는 고유 번호 | 페이지 번호 |
> 요약: 파티션을 통해 부하를 분산하고, 오프셋으로 소비 위치를 관리함.

## Ⅲ. 절차
- ASCII 흐름도
  [Write to Leader] -> [Replication to Follower] -> [ISR Update] -> [Commit]
- 4단계 설명
1. 프로듀서가 메시지 키에 따른 해시값으로 파티션을 결정해 리더 노드에 기록함.
2. 팔로워 노드들이 리더로부터 데이터를 복제하여 자신의 로그에 저장함.
3. 복제가 완료된 노드들(ISR: In-Sync Replicas)의 상태를 관리함.
4. 리더는 ISR 내 복제가 완료되면 메시지를 커밋하고 컨슈머에게 노출함.
> 요약: 분산 복제를 통해 고가용성과 데이터 유실 방지를 동시에 달성함.

## Ⅳ. 문제점
- 파티션 과다: 너무 많은 파티션은 리더 선출 지연 및 리소스 낭비 초래함.
- 순서 보장 한계: 토픽 전체의 순서는 보장되지 않으며, 단일 파티션 내에서만 순서 보장됨.

## Ⅴ. 개선방안
- 적정 파티션 설계: 처리량과 노드 수를 고려하여 파티션 개수를 신중히 산정함.
- 메시지 키 활용: 순서가 중요한 데이터는 동일한 키를 부여하여 동일 파티션으로 유도함.

## Ⅵ. 전망
- KRaft 도입으로 Zookeeper 의존성을 제거하여 아키텍처 간소화 및 확장성 개선됨.
- Tiered Storage 기술을 통해 무제한에 가까운 데이터 보관 및 비용 절감 가능해짐.
- 실시간 정형 데이터 처리를 위한 정교한 스키마 레지스트리와의 결합이 필수화됨.
