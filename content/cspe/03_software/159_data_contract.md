## 미리 알고가기

- 데이터 계약은 생산자와 소비자가 데이터의 구조·의미·품질·제공 조건·변경 규칙에 합의한 규약임
- 구문 스키마는 열 이름·타입·필수 여부·형식·키를 정의함
- 의미 정의는 업무 용어·단위·코드·집계 기준과 열의 해석을 설명함
- 호환성 규칙은 열 추가·삭제·타입 변경이 기존 소비자에 미치는 허용 범위를 정함
- 품질 SLO는 완전성·유효성·최신성 같은 데이터 제공 수준과 판정 기준을 정의함
- 계약 검사는 생산자 CI·파이프라인·소비자 읽기 시점에 스키마와 품질 위반을 검출함

## 작성 근거(검토용)

- 데이터 계약은 스키마·의미·품질 SLO·소유권·호환성·검증 위치를 핵심으로 선정함
- 비교표는 API 계약과 데이터 계약의 대상·인터페이스·품질·변경·검증·책임을 같은 기준에서 대비함
- 절차는 변경 제안부터 호환성 검사·생산자 검증·게시·소비자 판정까지 계약 상태 전이를 설명함
- 제목부터 결론까지 모든 문장·표 셀·요약을 5회 전수 검수해 문서 합의와 실행 가능한 검증을 구분함

## Ⅰ. 개요

- **정의/개념**: 데이터 계약은 생산자와 소비자가 데이터의 스키마·의미·품질 SLO·소유자·호환성 규칙을 기계 검증 가능한 형식으로 정의한 인터페이스 규약임
- **배경/필요성**: 생산자 변경이 파이프라인·보고서·모델을 예고 없이 깨뜨리지 않도록 배포 전에 소비자 영향과 제공 품질을 판정할 기준이 필요함

## Ⅱ. 특징

- 스키마의 열·타입·키뿐 아니라 단위·코드·업무 의미와 사용 제한을 함께 정의함
- 소유자·지원 채널·품질 SLO·갱신 주기·지원 중단 절차가 제공 책임을 명시함
- 호환성 정책이 열 삭제·이름 변경·타입 축소처럼 소비자에 영향을 주는 변경을 판정함
- 생산자 CI와 파이프라인 품질 게이트가 계약 위반 데이터의 게시를 제한함
- 계약 버전과 소비자 의존성을 카탈로그·계보에 연결해 변경 승인 범위를 계산함

## Ⅲ. 종류 및 비교

| 판단 기준 | API 계약 | 데이터 계약 |
|:---|:---|:---|
| 계약 대상 | 요청·응답·오류·호출 방식 | 테이블·파일·토픽의 구조·의미·품질 |
| 제공 인터페이스 | 엔드포인트·메서드·메시지 스키마 | 데이터셋 위치·스키마·SLO·접근 정책 |
| 품질 기준 | 응답 코드·지연·가용성 | 완전성·유효성·최신성 |
| 변경 호환성 | 필드·Endpoint·버전 변경 | 열·타입·키·코드·의미·파티션 변경 |
| 검증 위치 | API Gateway·소비자 테스트 | 생산자 CI·파이프라인 게이트·소비자 검사 |
| 책임 범위 | 서비스 소유자와 API 소비자 | 데이터 제품 소유자와 분석·모델 소비자 |

> 요약: 데이터 계약은 데이터의 구조뿐 아니라 의미·품질 SLO·소유권·변경 호환성을 생산자와 소비자 사이에 명시함.

## Ⅳ. 구성요소 및 구조

| 구성요소 | 설명 |
|:---|:---|
| Schema·Key | 열·타입·필수 여부·기본 키·파티션과 직렬화 형식을 정의함 |
| Semantic Definition | 업무 용어·단위·코드·집계 기준과 허용 사용 목적을 설명함 |
| Quality·SLO | 완전성·유효성·최신성 규칙과 목표·측정 구간을 명시함 |
| Ownership·Support | 생산자·소유자·소비자·지원 채널·위반 대응 책임을 배정함 |
| Version·Compatibility | 변경 유형별 호환성·폐기 예고·마이그레이션 기간을 정의함 |
| Validator·Registry | 계약 버전을 저장하고 CI·파이프라인·소비 시점의 위반을 판정함 |

```text
Producer Code -> Contract Validator -> Data Product -> Consumer
                         |
               Registry·Version·SLO
```

> 요약: 계약 Registry와 Validator가 생산자 변경을 스키마·의미·품질·호환성 기준으로 판정해 소비자에게 게시함.

## Ⅴ. 원리 및 절차 흐름도

```text
변경 제안 -> 계약 버전 수정 -> 호환성·품질 검사 -> 계약·데이터 게시 -> 소비자 검증
```

1. **변경 제안**: 생산자가 열·코드·품질 목표의 변경 내용과 영향 소비자를 식별함
2. **계약 수정**: 새 스키마·의미·SLO·적용 시점과 폐기 계획을 버전으로 작성함
3. **사전 검사**: CI가 기존 계약과 호환성을 비교하고 예제·품질 규칙을 실행함
4. **게시**: 승인된 계약 버전을 Registry에 올리고 대응하는 데이터를 게시함
5. **소비 검증**: 소비자가 지원 버전과 품질 결과를 확인하고 위반 시 사용을 제한함

> 요약: 데이터 변경은 계약 버전과 호환성·품질 검사를 먼저 통과한 뒤 데이터와 함께 소비자에게 게시됨.

## Ⅵ. 실무 사례

1. 주문 이벤트는 스키마·금액 단위 계약을 CI에서 검사하고 호환성 실패·품질 위반 건수를 확인함
2. 분석 테이블은 최신성 SLO와 소유자를 등록하고 SLO 위반 시간·미승인 변경 수를 확인함

## Ⅶ. 결론

- 데이터 계약은 스키마·의미·품질 SLO·소유권과 호환성 검사를 배포 경로에서 집행할 수 있어야 함
