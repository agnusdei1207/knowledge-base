# 📖 【암기용】 개념 완전 이해

> 목적: 데이터 계약을 처음 보는 사람도 완벽히 이해하게 만든다. 시험 답안 양식이 아니라, 이해를 위한 친절한 설명이다.

## 한눈에
- **개요**: **인터페이스 계약**(Interface Contract)의 데이터 버전 — 데이터 **생산자**와 **소비자**가 스키마·의미·품질·SLA·변경 절차를 문서와 코드로 합의한 명세
- **왜 필요한가**: 생산 시스템이 통보 없이 컬럼명을 바꾸거나 null을 허용하면, 그 컬럼을 쓰는 대시보드·AI 피처가 조용히 깨진다. 계약은 "이 데이터는 이런 모양·품질·주기로 제공한다"를 미리 약속하고 변경 전 검증을 강제한다.
- **핵심 직관**: REST API가 요청·응답 형식을 문서로 명시하듯, 데이터도 생산자-소비자 사이에 같은 수준의 계약이 필요하다는 발상이다.

## 핵심 용어 정리 (내부에 등장하는 것들)

| 용어 | 의미 | 비유 |
|:---|:---|:---|
| 인터페이스 계약 | 두 시스템이 주고받는 데이터의 형식과 규칙을 미리 합의하는 상위 개념 | API 명세서 |
| Schema (스키마) | 필드명·타입·nullable 여부 등 구조 정의 | 택배 상자의 규격 |
| Semantic (의미 정의) | 필드가 실제로 무엇을 뜻하는지(예: amount가 세전인지 세후인지) | 상품 설명서 |
| Quality Rule (품질 규칙) | not null, 값의 범위, 유일성 같은 검증 조건 | 출고 전 검수 기준표 |
| Freshness (신선도) | 데이터가 얼마나 최신이어야 하는지의 시간 기준 | 유통기한 |
| Ownership | 계약 위반 시 책임지는 담당자 | 납품 계약서의 책임자 서명 |
| Versioning | 계약 변경 이력을 버전으로 관리 | 계약서 개정판 번호 |
| Breaking Change | 하위 호환을 깨는 변경(필드 삭제·타입 변경) | 상자 규격을 바꿔 기존 운송장이 안 맞게 됨 |
| Schema Registry | 스키마 버전을 중앙에서 관리·검증하는 저장소 | 표준 규격 등록소 |
| CI/CD Gate | 배포 전 자동으로 계약 위반을 걸러내는 검증 단계 | 출고 전 검수대 |

## 깊이 이해

### 왜 필요한가 — 느슨한 결합의 함정 (배경)
- 데이터 플랫폼에서 생산자(주문 시스템)와 소비자(BI 대시보드, AI 피처)는 테이블 하나로만 연결되고 서로의 코드를 모른다. 생산자가 `order_id`를 nullable로 바꾸면, 그 필드로 group by 하던 소비자 쿼리 중 몇 개가 깨질지 생산자는 알 방법이 없다 — 계약이 없으면 영향 범위가 장애가 터진 뒤에야 드러난다.

### 계약 명세를 수치로 이해하기 (worked example)
- `orders` 데이터 계약: `order_id not null`, `amount >= 0`, `currency in {KRW, USD}`, `freshness ≤ 15분`, breaking change는 **7일 전** 공지가 명세라고 하자.
- 어느 개발자가 PR에서 `order_id`를 nullable로 바꾸려 하면, CI가 계약 명세와 스키마를 비교해 not null 규칙 위반을 감지하고 **머지를 차단**한다 — 이 자동 검증이 없으면 계약은 문서로만 남고 실제로는 지켜지지 않는다.
- 파이프라인이 새벽 적재 도중 2시간 지연되면 freshness 15분 기준을 위반해 owner에게 알림이 간다 — 지연도 계약 위반으로 다루는 이유다.

### Breaking Change vs Compatible Change 판별 원리
- **호환 변경(Compatible)**: 필드 추가, optional 필드 신설처럼 기존 소비자 쿼리가 그대로 동작하는 변경 → 자동 승인.
- **비호환 변경(Breaking)**: 필드 삭제, 타입 변경(string→int), not null 해제처럼 기존 소비자가 깨지는 변경 → 최소 7일 전 공지와 owner 승인이 필요.
- 판별 기준은 "기존 소비자의 쿼리·코드를 수정 없이 그대로 돌렸을 때 여전히 동작하는가"이다.

### 흔한 오해
- 계약을 문서로 적어두는 것만으로는 작동하지 않는다. 스키마 레지스트리에 등록하고, CI에서 PR마다 검증하고, 파이프라인에서 품질 규칙을 실행하고, 위반 시 Slack·PagerDuty로 알림이 가는 자동화 체인이 있어야 계약이 실효를 가진다.

## 연결 개념
- 데이터 품질 관리 — 계약에 명시된 품질 규칙을 실제로 실행하는 단계
- 데이터 제품 — 계약은 데이터 제품이 제공하는 SLA의 근거 명세
- 데이터 계보 — 계약 변경이 어디까지 영향을 주는지 추적하는 수단

# 📝 【답안용】 시험 답안 템플릿

> 목적: 시험장에서 25분에 그대로 쓰는 답안 양식. 작성방식(추상표현 금지·수치·도식·문제유형 전환)을 엄격히 지킨다.
> 핵심: 데이터 계약 답안은 생산자/소비자 책임, 스키마/품질/SLA 명세, 변경 관리, 자동 검증을 함께 제시해야 한다.

## 핵심 인사이트 (3줄 요약)

> 1. **본질**: 데이터 계약은 producer와 consumer가 데이터 구조, 의미, 품질, freshness, 변경 절차를 합의한 운영 명세임.
> 2. **가치**: breaking change, 품질 오류, 지연을 사전에 탐지해 downstream 장애를 줄임.
> 3. **판단 포인트**: 계약은 문서가 아니라 CI/CD, 스키마 레지스트리, DQ 검사, 알림에 연결되어야 함.

## 출제 의도 및 답안 포인트

| 출제 의도 | 반드시 짚을 핵심 | 감점 회피 포인트 |
|:---|:---|:---|
| 데이터 생산/소비 책임 이해 확인 | producer, consumer, owner, SLA | 품질 규칙과 혼동 |
| 변경 통제 구조 확인 | versioning, breaking change, approval | 스키마 설명만 작성 |
| 자동 검증 판단 확인 | CI, schema registry, DQ rule, alert | 수동 문서로만 서술 |

> 요약: 데이터 계약은 데이터 변경을 API 변경처럼 통제하는 생산자-소비자 합의 체계임.

---

## Ⅰ. 개요 및 필요성

- 개요: 데이터 계약은 데이터 제공 약속 명세임.
- 배경: 생산 시스템 변경은 하위 분석, 보고, AI 피처에 장애를 만든다.
- 필요성: 스키마, 의미, 품질, SLA, 변경 절차를 명시해 downstream 호환성 위반을 사전에 검출한다.

---

## Ⅱ. 구조 및 구성요소

```text
Producer -> Contract Spec -> CI/Schema Check -> Pipeline Validation -> Consumer
                         +-> Version/Approval
                         +-> Alert/Lineage
```

| 구성요소 | 역할 | 특이사항 |
|:---|:---|:---|
| 계약 명세 | schema, semantic, quality, SLA 정의 | YAML, JSON, protobuf |
| 생산자 | 데이터 생성과 변경 책임 | owner, version 관리 |
| 소비자 | 요구 필드와 사용 조건 제시 | report, feature, API |
| 검증 체계 | 스키마와 품질 자동 검사 | CI, DQ, registry |

> 요약: 데이터 계약은 명세, 책임자, 검증 체계, 변경 승인으로 구성됨.

---

## Ⅲ. 동작원리 및 흐름도

```text
요구 정의 -> 계약 작성 -> 배포 전 검증 -> 파이프라인 검사 -> 위반 알림/차단 -> 버전 관리
```

| 단계 | 처리 내용 | 검증 기준 |
|:---:|:---|:---|
| 1 | 소비자 요구 필드와 SLA 정의 | 필수 필드 100% 명시 |
| 2 | 생산자 계약 명세 작성 | owner, version 필수 |
| 3 | 스키마 변경 CI 검사 | breaking change 차단 |
| 4 | 파이프라인 품질/freshness 검사 | freshness 15분 이하 |
| 5 | 위반 알림과 버전 배포 | 공지 7일 이상 |

> 요약: 데이터 계약은 요구 합의부터 배포 전 검증과 운영 중 위반 감지까지 연결됨.

---

## Ⅳ. 특징

| 구분 | 비계약 데이터 공유 | 데이터 계약 | 판단 포인트 |
|:---|:---|:---|:---|
| 책임 | 소비자 사후 대응 | producer/consumer 역할 명시 | owner 100% |
| 변경 | 임의 스키마 변경 | version, approval | breaking change 차단 |
| 품질 | 사용자가 발견 | rule 기반 검사 | null, range, freshness |
| 한계 | 절차 부담 낮음 | 초기 합의 필요 | 계약 범위 선정 |

> 요약: 데이터 계약은 변경 자유도를 줄이는 대신 downstream 장애를 사전에 차단함.

## Ⅴ. 심화 비교 및 적용 판단

| 비교 축 | 기존/대안 | 본 키워드 | 선택 기준 |
|:---|:---|:---|:---|
| 구조 | 암묵적 테이블 공유 | 명시적 계약 명세 | 소비자 3개 이상 |
| 비용/처리 | 사후 수정 | CI와 DQ 자동 검증 | 장애 복구 비용 |
| 운영/위험 | 변경 영향 미인지 | version/approval | 핵심 지표, AI 피처 |

> 요약: 데이터 계약은 하위 소비자가 많고 변경 영향이 큰 데이터셋부터 적용함.

| 리스크 | 원인 | 대응 방안 | 확인 지표 |
|:---|:---|:---|:---|
| 계약 미준수 | 검증 미연계 | CI/DQ 차단, owner 알림 | violation count |
| 과도한 계약 | 모든 테이블 적용 | critical data 우선 | 계약 대상 비율 |
| 변경 지연 | 승인 절차 과다 | compatible change 자동 승인 | lead time |

> 요약: 데이터 계약은 핵심 데이터에 우선 적용하고 자동 검증으로 운영 부담을 낮춰야 함.

| 점검 항목 | 목표 기준 | 측정 방법 |
|:---|:---|:---|
| 준수 | 계약 위반 0건 또는 P1 0건 | CI/DQ report |
| 신선도 | freshness SLA 15분 이하 | pipeline timestamp |
| 변경 | breaking change 사전 공지 7일 | version history |

> 요약: 계약 운영은 위반 건수, freshness, 변경 공지 이력으로 판단함.

## Ⅵ. 실무 적용 및 결론

**적용 방안 3개 (필수 - 단계별 또는 항목별):**
1. 계약 범위 선정: 매출, 주문, 고객, AI 피처 등 소비자 3개 이상 핵심 데이터셋부터 schema, quality, freshness 명세 작성
2. 검증 자동화: PR 단계에서 스키마 호환성 검사, 파이프라인 단계에서 null/range/freshness rule 적용
3. 변경 관리: breaking change는 7일 전 공지, compatible change는 자동 승인, 위반 시 owner Slack/PagerDuty 알림

**결론 (2줄):**
- 기술사 판단: 소비자가 많고 장애 파급이 큰 데이터는 계약 필수, 임시 탐색 데이터는 경량 품질 규칙으로 충분함
- 향후 방향: 데이터 계약은 데이터 제품과 결합되어 SLA 기반 데이터 플랫폼 운영의 표준 인터페이스가 됨
