## 핵심 인사이트 (3줄 요약)
- "A 서버야, B 일 좀 해줘(명령/API)" 방식에서 벗어나, **"나는 방금 [회원가입]을 완료했어(이벤트 발생). 누군지 몰라도 관심 있으면 알아서 가져가~(구독)" 방식으로 시스템을 분리하는 초-디커플링 아키텍처**.
- 중앙에 카프카(Kafka) 같은 이벤트 브로커(확성기)를 두고, 어떤 서비스에서 상태 변화(Event)가 생기면 확성기에 소리치고, 알림 톡 발송 서버나 포인트 적립 서버가 그 소리를 듣고 알아서 동작함.
- 새로운 마이크로서비스(예: 가입 시 쿠폰 발급)를 추가할 때, 기존 코드를 단 한 줄도 건드리지 않고 브로커에 숟가락만 얹으면 되는(Plug & Play) 궁극의 확장성을 제공함.
---
## Ⅰ. 개요 및 필요성
- **개요**: 시스템의 상태 변화나 비즈니스 팩트를 '이벤트(Event)' 형태로 생성(Publish)하고, 이를 관심 있는 다른 서비스들이 수신(Subscribe)하여 비동기적으로 처리하는 소프트웨어 아키텍처 패턴.
- **필요성**: 회원가입 완료 시 `[포인트 적립 API]`, `[가입 축하 메일 API]`, `[쿠폰 발급 API]` 3개를 회원 서버가 직접 찔러야 함. 만약 메일 서버가 죽으면 회원가입 전체가 에러 나고 롤백됨(강한 결합). **"회원 서버는 그냥 가입 처리만 하고 '가입 완료됨!'이라고 허공에 소리치게 하자! 메일을 보내든 쿠폰을 주든 그건 니들이 알아서 듣고 처리해!"**라며 EDA가 도입됨.
---
## Ⅱ. 아키텍처 및 핵심 원리
- **1. 상태 변화 (Event)**:
  - 이벤트는 "이미 일어난 과거의 사실"임. 따라서 이름도 무조건 과거형으로 지음. (예: `UserCreated`, `OrderPlaced`).
  - 특징: 과거의 사실이므로 절대 취소하거나 수정할 수 없음(Immutable).
- **2. Pub/Sub (발행/구독) 모델**:
  - **Publisher (발행자)**: "나 방금 주문 받았음!" 이벤트를 Event Router(브로커)로 던짐. (누가 들을지 관심 없음).
  - **Subscriber (구독자)**: 자기가 듣고 싶은 주제(Topic)만 브로커에 등록해 둠. "주문 들어왔다"는 소리가 들리면 즉시 알림 톡 발송을 시작함.
- **3. 이벤트 브로커 (Event Broker, Apache Kafka 등)**:
  - 모든 이벤트가 모이고 퍼져나가는 거대한 심장이자 로그 파일.
  - 일반 MQ(RabbitMQ)와 달리 카프카는 **데이터를 지우지 않고 보관**하므로, 며칠 뒤에 새로운 구독자가 와서 옛날 이벤트부터 싹 다 다시 읽어갈 수 있음(Replay).

```text
[ 기존 API 호출 (강한 결합) vs 이벤트 기반 아키텍처 (느슨한 결합) 비교 ]

 🔗 [ 기존: API 동기 호출 (의존성 덩어리) ]
 회원 서버 ➡️ (API) ➡️ 메일 서버 (죽으면 가입 실패 💥)
         ➡️ (API) ➡️ 쿠폰 서버 (죽으면 가입 실패 💥)
         ➡️ (나중에 포인트 서버 추가하려면 회원 서버 코드 뜯어고쳐야 함 🤬)

 📢 [ EDA: Pub/Sub 모델 (완벽한 디커플링) ]
 회원 서버 ➡️ "가입 완료(Event)!" ➡️ [ 이벤트 브로커 (Kafka) ] 
 
         (브로커가 알아서 뿌려줌) ➡️ 🎧 [ 메일 서버 (구독 중) ] 알아서 메일 발송
                              ➡️ 🎧 [ 쿠폰 서버 (구독 중) ] 알아서 쿠폰 발송
                              ➡️ 🎧 [ 포인트 서버 (신규 추가!) ] (회원 서버 코드 수정 0줄로 추가 완료! 🎉)
```

## Ⅲ. 비교 및 연결
| 구분 | Command (명령/REST) | Event (이벤트/Pub-Sub) |
|---|---|---|
| **의도** | "B야, 이 행동을 해라!" (미래/명령) | **"나는 이 행동을 끝냈다." (과거/사실보고)** |
| **방향성** | Point-to-Point (1:1 타겟 지정) | **1:N (누가 들을지 모름, 관심 있는 놈이 들음)** |
| **결합도** | 타겟이 죽으면 나도 멈춤 (강한 결합) | **타겟이 죽어도 나는 내 갈 길 감 (느슨한 결합)** |
| **트랜잭션** | 하나의 큰 트랜잭션으로 묶기 쉬움 | **결과적 일관성(Eventual Consistency) 감수해야 함** |
---
## Ⅳ. 실무 적용 및 기술사 판단
- **Eventual Consistency (결과적 일관성) 수용**: EDA를 도입하면 "방금 결제했는데 왜 내 포인트는 아직 안 올라갔지?"라는 고객 클레임이 반드시 들어옴. 이벤트가 카프카를 거쳐 포인트 서버로 가는 데 0.5초의 지연(Delay)이 발생하기 때문. 기술사는 비즈니스 부서에 **"실시간(ACID) 일관성을 포기하는 대신, 절대 시스템이 죽지 않는 확장성을 얻었다"**는 트레이드오프(결과적 일관성)를 반드시 설득하고 설계에 반영해야 함.
- **이벤트 스키마 레지스트리 (Schema Registry) 도입**: 이벤트가 수천 개로 늘어나면, 발행자가 JSON 필드를 `user_id`에서 `userId`로 바꾸는 순간 모든 구독자 서버가 에러를 뿜고 전멸함(스키마 붕괴). 실무에서는 카프카 옆에 반드시 '스키마 레지스트리'를 두어, "이벤트의 데이터 모양(구조)이 바뀌면 중앙에서 먼저 검사하여 거부"하는 데이터 거버넌스 통제 체계를 구축해야 파국을 막을 수 있음.
---
## Ⅴ. 기대효과 및 결론
- 코드를 한 줄도 고치지 않고 새로운 비즈니스 요구사항(새로운 서버 추가)을 무한대로 붙일 수 있는 궁극의 민첩성(Agility)을 제공함.
- 마이크로서비스(MSA)가 수십 개로 쪼개진 클라우드 네이티브 환경에서, 서비스 간의 거미줄 같은 통신 지옥을 깔끔한 중앙 차선으로 정리해 주는 21세기 백엔드 아키텍처의 최종 진화 형태임.

### 👶 어린이를 위한 3줄 비유 설명
1. **기존 방식**은 엄마가 방마다 문 문을 열고 들어가서 "첫째 밥 먹어! 둘째 밥 먹어! 셋째 밥 먹어!"라고 일일이 명령하는 거예요. (엄마가 너무 피곤해요).
2. **이벤트 방식(EDA)**은 엄마가 거실에 서서 확성기로 "밥 다 됐다!!(이벤트)"라고 한 번만 외치는 거예요.
3. 그럼 배고픈 애들(구독자)은 알아서 뛰어나오고, 배 안 고픈 애들은 그냥 무시해요. 나중에 넷째가 태어나도 엄마는 똑같이 소리만 지르면 되니까 엄청 편하답니다!
