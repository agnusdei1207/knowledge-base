# 📖 【암기용】 개념 완전 이해

## 한눈에
- **개요**: 시스템의 상태 변경(이벤트)을 감지하고, 이 이벤트를 비동기적으로 발행(Publish)하여 구독(Subscribe)하는 서비스들이 각자 반응하도록 설계된 분산 아키텍처
- **왜 필요한가**: A 서비스가 B, C, D 서비스를 직접 호출(REST API)하면 강결합이 발생해 새로운 E 서비스가 추가될 때마다 A의 코드를 수정해야 한다. 이를 막기 위해 "나(A)는 모르겠고, 내 상태가 변했으니 알아서들 해라"라고 외치기 위해 필요하다.
- **핵심 직관**: 라디오 방송국(생산자)은 전파(이벤트)만 뿌릴 뿐, 그 전파를 차에서 듣는지 집에서 듣는지(구독자)는 전혀 신경 쓰지 않는 방송(Broadcasting) 방식이다.

## 핵심 용어 정리

| 용어/표기 | 의미 | 비유·예 |
|:---|:---|:---|
| Event (이벤트) | 과거에 이미 발생한 '의미 있는 상태의 변경' | "주문이 완료됨 (OrderCreated)" |
| Event Publisher | 이벤트를 생성하고 브로커로 발행하는 서비스 | 라디오 방송국 (주문 마이크로서비스) |
| Event Subscriber | 특정 이벤트를 구독하여 비즈니스 로직을 실행하는 서비스 | 라디오 청취자 (결제, 배송 마이크로서비스) |
| Event Broker | 이벤트를 중개하고 저장·라우팅하는 인프라 | 방송 전파탑 (Kafka, EventBridge) |

## 깊이 이해
- **배경·문제의식**: MSA에서 서비스 개수가 100개가 넘어가면, API 동기 호출 방식(Request-Response)은 통신의 사슬(Chain)을 만든다. 한 서버가 느려지면 사슬 전체가 멈추고(장애 전파), 코드는 스파게티처럼 얽힌다. 이를 해결하기 위해 호출(Command) 중심에서 반응(Reaction) 중심으로 패러다임을 바꾼 것이다.
- **작동 원리**: 사용자가 상품을 구매하면 주문 서비스는 `OrderCreated` 이벤트를 Kafka 같은 브로커에 던진다(Publish). 주문 서비스는 즉시 사용자에게 "주문 성공"을 응답한다. 한편, 결제 서비스, 알림 서비스, 재고 서비스는 브로커를 쳐다보고 있다가(Subscribe) 해당 이벤트가 들어오면 비동기적으로 각자의 로직(결제 승인, 카톡 발송, 재고 차감)을 수행한다.
- **비유**: 동기 호출은 상사가 부하직원 3명에게 일일이 전화해서 지시하고 끝날 때까지 기다리는 것이고, 이벤트 기반은 사내 게시판에 "A 프로젝트 승인됨"이라고 공지하면 관련 부서들이 알아서 자기 일을 시작하는 것이다.
- **구체 예시**: 회원가입 시(UserRegistered 이벤트) 웰컴 이메일, 쿠폰 지급, 통계 서버 업데이트가 필요한데, 신규 마케팅 서비스(SMS 발송)가 추가되어도 회원가입 서버의 코드는 단 1줄도 수정할 필요가 없다. (완벽한 확장성)
- **흔한 오해·주의점**: "이벤트 기반은 무조건 좋다"는 착각이다. 로직의 흐름이 중앙에 보이지 않고 여러 서비스로 파편화되므로, 전체 프로세스(예: 주문부터 배송까지)가 어디까지 진행되었는지 추적(Traceability)하기가 극도로 어려워지는 치명적 단점이 있다.

## 연결 개념
- **Apache Kafka**: EDA 구현을 위한 사실상의 표준 이벤트 스트리밍 브로커
- **Event Sourcing**: DB의 현재 상태만 저장하지 않고, 발생한 모든 이벤트를 장부처럼 순차 저장하는 패턴
- **Saga Pattern**: EDA 환경에서 여러 서비스에 걸친 분산 트랜잭션을 롤백(보상 트랜잭션)하기 위한 패턴

# 📝 【답안용】 시험 답안 템플릿

## 핵심 인사이트 (3줄 요약)

> 1. **본질**: 시스템의 상태 변경을 '이벤트'로 정의하고, 이를 비동기적인 발행-구독(Pub/Sub) 모델로 전달하여 마이크로서비스 간 통신을 수행하는 아키텍처 패턴이다.
> 2. **가치**: 서비스 간의 시간적·공간적 강결합을 제거하여, 생산자 수정 없이 새로운 구독자를 무한히 추가할 수 있는 궁극의 확장성과 장애 격리를 제공한다.
> 3. **판단 포인트**: 흐름의 파편화로 인한 디버깅 복잡도(Spaghetti Architecture 리스크)와 결과적 일관성(Eventual Consistency)에 따른 데이터 지연을 허용할 수 있는 도메인에만 제한적으로 도입해야 한다.

## 출제 의도 및 답안 포인트

| 출제 의도 | 반드시 짚을 핵심 | 감점 회피 포인트 |
|:---|:---|:---|
| MSA 통신 방식 패러다임 전환 이해 | Request/Response vs Pub/Sub, 공간적/시간적 분리 | 이벤트(과거형)와 커맨드(명령형)를 혼용하여 서술 |
| EDA의 아키텍처 토폴로지 구성 파악 | Mediator 토폴로지(중앙통제) vs Broker 토폴로지(분산) | 단순 브로커 인프라 설명으로 치부 (설계 패턴 누락) |
| 단점 및 트레이드오프 대응 방안 | 분산 추적(Distributed Tracing), 최종 일관성, 보상 트랜잭션 | 확장성 등 장점만 찬양하고 트랜잭션 깨짐 문제 무시 |

> 요약: 결합도를 낮추는 아키텍처적 이점을 설명하되, 분산 트랜잭션의 결과적 일관성 유지와 전체 흐름 모니터링 한계를 어떻게 극복할 것인지 설계 관점에서 제시해야 한다.

## Ⅰ. 개요 및 필요성

- 개요: 시스템의 유의미한 상태 변화(Event)를 생성하여 이벤트 브로커에 발행하고, 관심 있는 다수의 서비스가 이를 비동기 구독하여 처리하는 분산 아키텍처
- 배경: 동기식 API 기반 MSA 환경에서 서비스 간 호출 사슬이 길어짐에 따라 장애 파급력(Cascading Failure) 및 결합도 증가
- 필요성: 생산자와 소비자를 완벽히 분리(Decoupling)하여 신규 서비스 추가 시 코드 변경을 없애고(OCP 원칙 준수), 트래픽 피크 시 비동기 버퍼링 필요

---

## Ⅱ. 구조 및 구성요소 (Broker Topology 기준)

```text
[서비스 A (생산자)] -> (상태 변경 이벤트 Publish) -> [Event Broker (Kafka 등)] -> (비동기 Subscribe) -> [서비스 B (결제)]
 (주문 완료)                                                                   |-> (비동기 Subscribe) -> [서비스 C (배송)]
```

| 구성요소 | 역할 | 특이사항 |
|:---|:---|:---|
| Event Generator | 비즈니스 로직 수행 후 상태 변경(예: `OrderCreated`) 이벤트 발행 | 수신자가 누군지 알지 못함 |
| Event Channel/Broker | 이벤트를 라우팅하고 필요 시 영속성(Persistence)을 보장 | 메시지 큐(RabbitMQ) 또는 스트리밍(Kafka) |
| Event Processor | 채널을 구독하여 이벤트 수신 시 자체 비즈니스 로직 실행 (반응) | 이벤트 중복 수신 대비 멱등성 보장 필수 |

> 요약: 생산자는 중앙 브로커에 이벤트를 던질 뿐이며, 다수의 소비자는 이를 비동기적으로 가져가 독립적인 비즈니스 로직을 수행한다.

---

## Ⅲ. 동작원리 및 흐름도

```text
상태 변경 -> DB 트랜잭션 및 이벤트 발행(Outbox) -> 브로커 영속화 -> 다중 소비자 구독 -> 최종 일관성 달성
```

- 1단계 [상태 변경 및 로컬 트랜잭션]: 생산자 서비스 내부에서 로컬 DB 상태를 변경하고, 성공 시 이벤트를 생성
- 2단계 [이벤트 발행(Publish)]: 생성된 이벤트를 트랜잭셔널 아웃박스(Transactional Outbox) 패턴 등을 통해 Broker로 원자적 전송
- 3단계 [분산 라우팅 및 적재]: 브로커는 Topic/Exchange 룰에 따라 이벤트를 분류하고 디스크/메모리에 영속화
- 4단계 [이벤트 소비 및 반응(React)]: 해당 Topic을 구독 중인 각 서비스들이 비동기로 이벤트를 읽어와 자신의 상태를 업데이트(최종 일관성 확보)

> 요약: 발행과 소비의 과정이 철저히 비동기로 이루어지며, 즉각적인 데이터 일치가 아닌 일정 시간 후 일치하는 '최종 일관성(Eventual Consistency)'을 지향한다.

## Ⅳ. 특징
- 공간적·시간적 분리(Decoupling): 통신 타겟의 IP나 포트를 몰라도 되며(공간 분리), 수신 서버가 다운된 상태에서도 이벤트를 발행할 수 있음(시간 분리)
- 무한한 확장성(Plug & Play): 이벤트 구독자(Consumer) 코드를 브로커에 연결만 하면 되므로, 기존 운영 중인 시스템의 중단 없이 실시간 분석 모듈 등을 추가 가능
- 역학적 복잡도 증가(Pinball Effect): 이벤트가 연쇄적으로 발생할 경우, 비즈니스 흐름이 파편화되어 에러 발생 시 전체 비즈니스 컨텍스트 추적이 극도로 어려움

> 요약: 최고의 확장성과 탄력성을 제공하지만, 전체 시스템 동작을 한눈에 파악하기 힘든 디버깅 난이도 상승을 초래한다.

## Ⅴ. 심화 비교 및 적용 판단 (EDA 토폴로지 설계 패턴)

| 비교 축 | Mediator Topology (중앙통제형) | Broker Topology (분산형) | 선택 기준 |
|:---|:---|:---|:---|
| 통제 주체 | 중앙의 이벤트 오케스트레이터(Mediator) 존재 | 중앙 통제 없이 체인 형태로 이벤트 전달 | 복잡한 트랜잭션 워크플로우 통제 필요성 |
| 워크플로우 추적 | 중앙 노드에서 전체 단계 파악 및 에러 제어 용이 | 추적 어려움, 각 노드가 독자적 판단 | 에러 복구(보상 트랜잭션)의 중요도 |
| 성능 및 결합도 | 병목(SPOF) 발생 가능성, 결합도 다소 증가 | 브로커의 높은 확장성, 최저 결합도 | 대규모 트래픽 및 완벽한 분리 우선 시 |

> 요약: 프로세스 제어와 트랜잭션 롤백이 중요한 주문/결제는 Mediator를, 단순 상태 전파나 로그 처리는 Broker 패턴을 적용한다.

**리스크·대응 (기본은 불릿):**
- 분산 데이터 정합성 파괴: 결제는 실패했는데 배송 이벤트가 이미 트리거되는 불일치 발생 → Saga 패턴(Choreography/Orchestration)을 통한 비동기 보상 이벤트(결제 취소) 발행으로 최종 롤백 구현
- 비즈니스 가시성 상실(Blackbox): 주문 하나가 실패했을 때 어느 마이크로서비스에서 이벤트가 끊겼는지 파악 불가 → OpenTelemetry 기반 Correlation ID를 모든 이벤트 헤더에 주입하여 Zipkin/Jaeger로 분산 추적(Distributed Tracing) 구현
- 중복 이벤트 처리: 네트워크 재시도로 인해 동일 이벤트가 여러 번 수신 → 소비자 측 DB에 '처리 완료된 이벤트 ID' 테이블을 두어 중복을 무시하는 멱등성(Idempotency) 로직 필수화

**도입 후 점검 지표 (기본은 불릿):**
- 성능/운영: 이벤트 End-to-End 지연시간(최종 일관성 도달 시간), 브로커 초당 메시지 처리량(Throughput)
- 품질/장애: 보상 트랜잭션(Saga 롤백) 발생 비율, 이벤트 중복 수신 방어(멱등성) 성공률 100%

## Ⅵ. 실무 적용 및 결론

**적용 방안 3개:**
1. CQRS(명령/조회 책임 분리) 아키텍처 융합: 쓰기(Command) 모델은 이벤트 소싱으로 상태 변경 이벤트를 Kafka에 쌓고, 이를 구독하는 읽기(Query) 전용 DB(ElasticSearch 등)를 비동기로 동기화하여 대규모 조회 트래픽 처리
2. Transactional Outbox + CDC 연동: RDBMS 트랜잭션과 이벤트 발행 간의 원자성(Atomicity) 보장을 위해 DB에 이벤트를 저장하고, Debezium 같은 CDC(Change Data Capture) 툴을 이용해 로그를 파싱하여 브로커로 안정적 전송
3. Event Registry(Schema Registry) 운영: 이벤트 페이로드 구조(JSON)가 변경될 때 구독자가 크래시되는 것을 막기 위해, Avro/Protobuf 스키마를 중앙 레지스트리에서 버전 관리하여 하위 호환성 강제 통제

**결론 (2줄):**
- 기술사 판단: EDA는 넷플릭스나 우버 같은 대규모 MSA 환경에서 필수불가결한 은탄환처럼 보이나, 결과적 일관성과 디버깅 복잡도를 감당할 성숙도(Observability Инфра)가 없는 조직에게는 재앙(Spaghetti)이 될 수 있다.
- 향후 방향: 단순 비동기 통신을 넘어, 실시간으로 유입되는 무수한 이벤트를 결합·분석하여 인사이트를 도출하는 복합 이벤트 처리(CEP, Complex Event Processing) 플랫폼으로 진화할 것이다.
