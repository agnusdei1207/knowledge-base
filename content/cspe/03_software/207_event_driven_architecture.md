## Ⅰ. 개요
- **정의**: 상태 변화를 이벤트로 발행하고 관심 있는 소비자가 비동기로 반응하는 소프트웨어 아키텍처 스타일
- **배경/필요성**: 동기 요청-응답 모델의 강결합이 서비스 확장·장애 격리를 제약하므로 비동기 이벤트 기반 탈결합 필요
- **비유**: 방송국(Publisher)이 뉴스를 송출하면 각 가정(Subscriber)이 원하는 채널만 시청하는 구조

| 출제 의도 | 반드시 짚을 핵심 | 감점 회피 포인트 |
|:---|:---|:---|
| 비동기 탈결합 아키텍처 설계 | Event Notification vs Event Sourcing 구분 | 최종 일관성(Eventual Consistency) 전제 명시 |

> 요약: 이벤트 발행·구독으로 서비스 간 결합을 제거하고 비동기 반응형 처리를 구현하는 아키텍처임

## Ⅱ. 구성요소
```text
Event Producer --event--> [Event Channel] --event--> Event Consumer
                              |
                    +---------+---------+
                    |         |         |
                 Broker   Event Store  Router
```

| 구성요소 | 설명 | 비유 |
|:---|:---|:---|
| Event Producer | 상태 변화를 감지하여 이벤트를 발행하는 서비스 | 방송국 |
| Event Channel | 이벤트를 라우팅·전달하는 메시지 인프라(206 참조) | 전파 송출탑 |
| Event Consumer | 이벤트를 수신하여 후속 처리를 수행하는 서비스 | 시청 가정 |

> 요약: Producer가 Channel을 통해 이벤트를 발행하고 Consumer가 비동기로 반응함

## Ⅲ. 절차
```text
상태 변화 감지 --> 이벤트 발행 --> 라우팅/전달 --> 소비자 처리
```
- 1단계: 도메인 서비스에서 상태 변화(주문 생성 등) 감지
- 2단계: 변화 내용을 표준 이벤트 포맷으로 직렬화하여 Channel에 발행
- 3단계: Broker/Router가 토픽·필터 기반으로 관심 소비자에게 이벤트 라우팅
- 4단계: Consumer가 이벤트 수신 후 독립적으로 후속 비즈니스 로직 실행

> 요약: 상태 변화 감지부터 이벤트 발행, 라우팅, 소비자 처리까지 4단계로 동작함

## Ⅳ. 문제점
- 이벤트 순서 보장: 분산 환경에서 발행 순서와 소비 순서 불일치 — 데이터 정합성 훼손
- 디버깅 난이도: 비동기 다단계 이벤트 체인으로 인해 장애 원인 추적 곤란
- 최종 일관성 지연: 이벤트 전파 지연 시 서비스 간 데이터 불일치 창(window) 발생

> 요약: 순서 보장, 디버깅 난이도, 일관성 지연이 주요 문제임

## Ⅴ. 개선방안
1. 단기: 파티션 키 기반 순서 보장·시퀀스 번호 부여로 이벤트 순서 제어
2. 중기: 분산 추적(Distributed Tracing)·Correlation ID 도입으로 이벤트 체인 가시화
3. 장기: Saga 패턴·보상 트랜잭션 도입으로 최종 일관성 실패 시 자동 복구 체계 구축

> 요약: 순서 제어, 분산 추적, Saga 패턴으로 단계적 개선함

## Ⅵ. 전망
- 발전 방향: Event Mesh·CloudEvents 표준화로 멀티 클라우드 이벤트 상호운용성 확대
- 기술사적 판단: CQRS·Event Sourcing과 결합 시 감사 추적·시간 여행 쿼리 구현 가능
- 기술사 제언: 분산 일관성(208 참조) 트레이드오프를 전제로 아키텍처 결정 필요
