# 📖 【암기용】 개념 완전 이해

> 목적: 이벤트 기반 아키텍처를 처음 봐도 완전히 이해하게 만든다. 시험 답안 양식이 아니라, 이해를 위한 설명이다.

## 한눈에
- **개요**: 이벤트 기반 아키텍처(EDA)는 서비스가 상태 변화를 이벤트로 발행하고, 여러 소비자가 이를 구독해 각자 비동기로 반응하는 **발행-구독(Publish-Subscribe) 아키텍처**다.
- **왜 필요한가**: 주문 완료 하나에 결제, 재고, 알림, 분석처럼 후속 처리가 여럿 붙으면, 이를 전부 동기 API 호출 체인으로 엮은 MSA는 결국 하나의 거대한 시스템처럼 결합돼버린다(분산 모놀리스). EDA는 발행자가 소비자를 몰라도 되게 만들어 이 결합을 끊는다.
- **핵심 직관**: 방송국이 뉴스를 송출하면, 그 뉴스를 듣는 각 부서(회계, 문자 발송, 통계)가 방송국에 등록하지 않고도 알아서 반응하는 구조다. 방송국은 누가 듣는지 몰라도 되고, 새 청취자가 늘어도 방송국 코드를 바꿀 필요가 없다.

## 핵심 용어 정리 (내부에 등장하는 것들)

| 용어 | 의미 | 비유 |
|:---|:---|:---|
| 발행-구독 (Publish-Subscribe) | 발행자가 이벤트를 내보내면 등록된 여러 구독자가 각자 받아 처리하는 통신 모델 | 방송 송출과 각 가정의 수신 |
| Domain Event | "무슨 일이 일어났다"는 과거형 사실을 담은 이벤트(예: OrderCreated) | 뉴스 속보 한 건 |
| Event Producer | 상태 변화가 생겼을 때 이벤트를 만들어 내보내는 서비스 | 방송국 |
| Broker / Event Stream | 이벤트를 저장하고 구독자에게 전달하는 인프라(Kafka, RabbitMQ 등) | 전파를 실어 나르는 송신탑 |
| Consumer / Subscriber | 이벤트를 구독해 자기 업무를 수행하는 서비스 | 뉴스를 듣는 각 부서 |
| Schema Registry | 이벤트 데이터 형식을 등록·검증해 소비자가 깨지지 않게 관리하는 저장소 | 방송 자막 표준 규격 관리소 |
| Outbox Pattern | DB 트랜잭션과 이벤트 발행을 한 묶음으로 처리해 발행 유실을 막는 기법 | 계약서 서명과 발송을 같은 봉투에 담음 |
| 최종 일관성 (Eventual Consistency) | 지금 당장은 서비스마다 데이터가 다를 수 있지만, 시간이 지나면 모두 같아지는 일관성 모델 | 뉴스가 지역마다 조금 늦게 도착해도 결국 다 같은 내용을 앎 |
| Saga Pattern | 여러 서비스에 걸친 트랜잭션을 이벤트 체인과 보상 이벤트로 처리하는 기법 | 잘못되면 이전 단계를 하나씩 되돌리는 절차 |
| CQRS | 명령(쓰기)과 조회(읽기) 모델을 분리하는 패턴, EDA와 자주 결합 | 접수 창구와 안내 창구를 분리 |
| Choreography vs Orchestration | 각자 이벤트에 반응해 흐름을 만드는 방식(안무) vs 중앙 지휘자가 순서를 지정하는 방식(지휘) | 즉흥 군무 vs 지휘자가 있는 오케스트라 |

## 깊이 이해

### 왜 필요했나 — 동기 호출 체인이 만드는 문제
- MSA에서 주문 서비스가 결제·재고·알림 서비스를 각각 동기 API로 순서대로 호출한다고 하면, 셋 중 하나(예: 알림 서비스)가 느려지거나 죽으면 주문 서비스의 응답도 함께 느려지거나 실패한다. 이러면 서비스를 나눈 의미(독립 장애·독립 배포)가 사라지고, 사실상 하나의 큰 시스템처럼 묶인 분산 모놀리스가 된다.
- EDA는 주문 서비스가 `OrderCreated` 이벤트 하나만 발행하고 끝내게 한다. 결제·재고·알림·분석은 각자 이 이벤트를 구독해서 자기 속도로, 자기 실패를 자기가 감당하며 처리한다. 발행자는 몇 개의 소비자가 붙어있는지, 그들이 살아있는지조차 몰라도 된다.

### Outbox Pattern으로 발행 유실을 막는 원리 — 구체 예로
- 문제: 주문을 DB에 저장(commit)한 직후 이벤트를 브로커로 보내려는 순간 서버가 죽으면, DB에는 주문이 저장됐는데 이벤트는 발행되지 않은 상태(불일치)가 생긴다.
- 해법: 주문을 저장하는 같은 트랜잭션 안에서 발행할 이벤트를 outbox 테이블에도 함께 저장한다. 이 두 INSERT는 하나의 DB 트랜잭션이므로 둘 다 성공하거나 둘 다 실패한다. 이후 별도의 relay 프로세스가 outbox 테이블을 주기적으로 읽어 브로커로 발행하고, 성공하면 표시한다.
- 예: `OrderCreated` 이벤트 1건이 발행되면 결제 예약, 재고 차감, 알림 발송, 분석 적재 4개의 서로 다른 소비자가 각자 독립적으로 이 이벤트를 소비해 처리한다 — 주문 서비스 코드는 이 4개 소비자의 존재를 전혀 몰라도 된다.

### 최종 일관성을 수치로 이해하기 — 언제 허용되는가
- 주문이 생성된 순간 재고가 즉시 차감되지 않고, 이벤트가 전파되어 재고 서비스가 처리하기까지 예를 들어 200ms~수 초의 지연이 생길 수 있다. 이 지연 동안에는 주문은 됐는데 재고 화면엔 아직 안 줄어든 짧은 불일치 구간이 존재한다.
- 이 지연이 문제가 되는지는 업무 성격에 달려있다. 결제 승인처럼 그 자리에서 결과를 사용자에게 보여줘야 하는 업무는 동기 처리를 유지하고, 알림 발송·통계 집계처럼 몇 초~몇 분 늦어도 되는 후속 업무만 EDA로 분리하는 것이 일반적 판단 기준이다.

### 판별 원리 — 언제 EDA를 쓰는가
- 신호 1: 한 사건 뒤에 후속 처리가 3개 이상으로 늘어나 동기 호출 체인이 길어지고 있다.
- 신호 2: 새 소비자(예: 새로운 분석 시스템)를 추가할 때마다 발행자 코드를 계속 고쳐야 한다 — 이는 결합도가 너무 높다는 신호다.
- 신호 3: 즉시 일관성이 필요 없고, 수 초~수 분의 지연을 사용자·업무가 수용할 수 있다.
- 반대로 지금 당장 결과가 맞아야 하는 트랜잭션(예: 결제 승인 자체)은 EDA로 옮기면 안 된다 — 최종 일관성이 오히려 버그로 보인다.

### 비유와 흔한 오해
- **비유**: 은행 입금 알림이 뜨면 회계 시스템, 문자 발송 시스템, 포인트 적립 시스템이 각자 알아서 반응한다. 은행 창구(발행자)는 이 세 시스템이 몇 개인지, 어떻게 동작하는지 몰라도 된다.
- **오해**: "이벤트 기반으로 바꾸면 트랜잭션이 필요 없어진다"는 생각. 실제로는 트랜잭션의 범위가 하나의 DB에서 여러 서비스에 걸친 Saga(보상 트랜잭션)로 바뀔 뿐이다. 이벤트 정의(스키마), outbox, 멱등성, 최종적으로는 일관되지만 그 사이 잠깐 안 맞는 UX 설계를 소홀히 하면 데이터 불일치가 그대로 장애로 이어진다.

## 연결 개념
- Message Queue·Kafka — 이벤트를 실제로 저장·전달하는 인프라 계층
- Saga Pattern — EDA로 분산된 트랜잭션을 보상 이벤트로 완결 짓는 기법
- CQRS — 이벤트로 갱신되는 조회 전용 모델을 명령 모델과 분리하는 패턴

# 📝 【답안용】 시험 답안 템플릿

> 목적: 시험장에서 25분에 그대로 쓰는 답안 양식. 수치·표준명·비교축으로 작성한다.
> 핵심: EDA는 비동기 메시징 도입이 아니라 이벤트 의미, 전달 보장, 일관성 모델을 함께 설계하는 아키텍처이다.

## 핵심 인사이트 (3줄 요약)

> 1. **본질**: EDA는 도메인 상태 변화를 이벤트로 발행하고 구독자가 비동기로 처리하는 구조이다.
> 2. **가치**: 서비스 결합도와 장애 전파를 줄이고, 신규 소비자를 발행자 수정 없이 추가한다.
> 3. **판단 포인트**: 이벤트 스키마, outbox, 순서, 중복, eventual consistency, 관측성을 설계해야 한다.

## 출제 의도 및 답안 포인트

| 출제 의도 | 반드시 짚을 핵심 | 감점 회피 포인트 |
|:---|:---|:---|
| 분산 아키텍처 설계 확인 | Event producer, broker, consumer, schema registry | 단순 메시지 큐 사용으로 축소 |
| 일관성 판단 확인 | eventual consistency, Saga, outbox | ACID 전체 보장으로 오해 |
| 운영 리스크 확인 | 중복, 순서, 재처리, poison event | 이벤트 추적·보상 처리 누락 |

> 요약: 이 문제는 이벤트 전달 기술보다 도메인 이벤트와 일관성 통제 설계를 요구한다.

## Ⅰ. 개요 및 필요성

- 개요: 이벤트 발행·구독 분산 아키텍처
- 배경: MSA의 동기 호출 체인은 장애 전파와 배포 결합을 만든다.
- 필요성: event broker, schema registry, DLQ, trace 기준으로 서비스 결합도와 비동기 확장을 관리한다.

---

## Ⅱ. 구조 및 구성요소

```text
Domain Service -> Event Producer -> Broker/Stream -> Consumer A/B/C
                              +-> Schema Registry / DLQ / Trace
```

| 구성요소 | 역할 | 특이사항 |
|:---|:---|:---|
| Domain Event | 상태 변화의 사실 표현 | `OrderCreated`, `PaymentApproved` |
| Producer | 트랜잭션 후 이벤트 발행 | outbox pattern 권장 |
| Broker/Stream | 이벤트 저장·전달 | Kafka, RabbitMQ, Pulsar |
| Consumer | 이벤트 수신 후 후속 처리 | 멱등성과 재처리 필요 |

> 요약: EDA는 도메인 이벤트, 발행자, 전달 인프라, 소비자, 스키마·관측 통제로 구성된다.

---

## Ⅲ. 동작원리 및 흐름도

```text
업무 트랜잭션 -> Outbox 저장 -> Event Publish -> Consumer 처리 -> Projection 갱신 -> Trace 수집
```

| 단계 | 처리 내용 | 검증 기준 |
|:---:|:---|:---|
| 1 | 도메인 트랜잭션과 outbox 레코드 저장 | DB commit atomicity |
| 2 | relay가 event broker로 발행 | publish failure 재시도 |
| 3 | 소비자가 이벤트 처리 및 ACK | idempotency key 확인 |
| 4 | 조회 모델·후속 업무 갱신 | consumer lag, consistency delay 측정 |

> 요약: EDA는 트랜잭션과 이벤트 발행을 outbox로 묶고, 소비자 지연과 보상 처리를 관측한다.

## Ⅳ. 특징

| 구분 | 동기 호출 아키텍처 | 이벤트 기반 아키텍처 | 판단 포인트 |
|:---|:---|:---|:---|
| 결합 | 호출 대상·순서 고정 | 구독자 독립 추가 | 소비자 3개 이상이면 EDA 검토 |
| 일관성 | 요청 내 즉시 일관성 | 최종 일관성 | 지연 허용 1초~수분 여부 |
| 장애 | 하위 장애가 상위 응답에 영향 | 큐·스트림에 적재 후 재처리 | DLQ와 replay 필수 |
| 추적 | 단일 trace 상대 단순 | 비동기 trace 연결 필요 | correlation id 100% 전파 |

> 요약: EDA는 결합도를 낮추지만 최종 일관성과 비동기 관측성 설계가 필수이다.

## Ⅴ. 심화 비교 및 적용 판단

| 구분 | 기존/대안 | 본 키워드 | 선택 기준 |
|:---|:---|:---|:---|
| 구조 | Request/Response 체인 | Publish/Subscribe | 후속 처리 3개 이상, 독립 배포 필요 |
| 비용/성능 | 호출 지연 누적 | 비동기 지연 분산 | API p95 300ms 이하, consistency delay 허용 |
| 운영/위험 | 장애 즉시 노출 | lag·DLQ·replay 운영 | 운영팀이 event trace를 볼 수 있어야 함 |

> 요약: EDA는 즉시 응답보다 후속 처리 분리와 독립 확장이 더 큰 시스템에 적합하다.

| 리스크 | 원인 | 대응 방안 | 확인 지표 |
|:---|:---|:---|:---|
| 이벤트 유실 | 트랜잭션 후 발행 실패 | transactional outbox | outbox pending 0건 |
| 중복 처리 | 재전달·consumer restart | idempotency, dedup store | duplicate side effect 0건 |
| 스키마 파손 | 이벤트 필드 삭제·타입 변경 | schema registry, compatibility check | incompatible schema 0건 |

> 요약: EDA 리스크는 유실, 중복, 스키마 파손이며 outbox와 schema registry로 통제한다.

| 점검 항목 | 목표 기준 | 측정 방법 |
|:---|:---|:---|
| 전달 | event publish success 99.9% 이상 | broker metric |
| 지연 | consumer lag 업무 SLA 이하 | stream offset, queue depth |
| 추적 | correlation id 전파 100% | distributed tracing |

> 요약: EDA 성공 여부는 이벤트 전달률, 소비 지연, trace 연결률로 판단한다.

## Ⅵ. 실무 적용 및 결론

**적용 방안 3개 (필수):**
1. 도메인 이벤트는 past tense 명명, version 필드, schema registry compatibility rule로 표준화함.
2. Transactional outbox와 relay를 적용해 DB commit과 이벤트 발행 사이 유실 구간을 제거함.
3. Consumer 멱등성, DLQ, replay runbook, correlation id 전파를 운영 표준으로 정의함.

**결론 (2줄):**
- 기술사 판단: 즉시 일관성이 필수인 결제 승인 자체는 동기 처리, 승인 후 알림·분석·정산은 EDA로 분리함.
- 향후 방향: EDA는 CQRS, event sourcing, data mesh와 결합해 실시간 운영 데이터 플랫폼으로 확장됨.
