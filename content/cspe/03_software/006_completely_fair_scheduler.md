# 📖 【암기용】 개념 완전 이해

## 한눈에
- **정의**: 리눅스 커널 2.6.23부터 도입된 표준 스케줄러로, 프로세스들에게 CPU 시간을 **'절대적으로 공평하게'** 나눠주는 것을 목표로 함.
- **핵심 직관**: 뷔페에서 음식을 담는 규칙. 모두가 똑같은 양의 음식을 먹어야 함. 많이 먹은 사람은 다음 차례에 뒤로 가고, 적게 먹은 사람을 제일 앞으로 불러서 음식을 주어 결국 모두가 먹은 양을 똑같이 맞춤.
- **핵심 지표 (vruntime)**: 프로세스가 실제 CPU를 사용한 시간을 가중치(Nice값)로 계산한 **'가상 실행 시간'**. CFS는 이 vruntime이 가장 작은 프로세스를 다음에 실행함.

## 깊이 이해
- **왜 도입되었나? ($O(1)$의 한계)**: 이전의 $O(1)$ 스케줄러는 복잡한 수식과 휴리스틱(I/O 바운드 판별 등)을 썼으나, 특정 상황에서 인터랙티브 앱의 응답성이 떨어지는 문제가 있었음. CFS는 복잡한 판단 대신 '공정성'이라는 단순한 원칙으로 회귀함.
- **Red-Black Tree**: 수백 개의 프로세스 중 vruntime이 가장 작은 놈을 빨리 찾기 위해 사용함. (가장 왼쪽 리프 노드만 꺼내면 됨. 탐색 복잡도 $O(\log N)$)
- **Nice값의 마법**: 우선순위가 높은(Nice값이 낮은) 프로세스는 vruntime이 천천히 올라가게 계산함. 똑같이 1초를 일해도 우선순위가 높으면 '0.5초만 일한 걸로 쳐줄게'라고 하여 CPU를 더 자주 잡게 함.
- **Granularity**: 너무 자주 스위칭하면 오버헤드가 크므로, 한 번 잡으면 최소한 이만큼은 써라 하는 '최소 실행 단위'를 둠.

## 연결 개념
- **MLFQ (005)**: 큐를 여러 개 쓰는 방식. CFS는 큐 대신 하나의 트리와 vruntime으로 관리함.
- **Red-Black Tree**: CFS의 성능을 지탱하는 자료구조.
- **Context Switching (002)**: CFS가 프로세스를 교체할 때 발생하는 물리적 작업.

# 📝 【답안용】 시험 답안 템플릿

## 핵심 인사이트 (3줄 요약)
> 1. **본질**: 하드웨어가 이상적인 멀티태스킹(모두에게 공평하게 CPU 분배)을 지원한다고 가정하고, 이를 소프트웨어적으로 모방한 **공정성 기반 스케줄링**임.
> 2. **기술적 핵심**: **vruntime(Virtual Runtime)**을 지표로 사용하며, 효율적인 탐색을 위해 **Red-Black Tree** 자료구조를 활용하여 $O(\log N)$의 스케줄링 성능을 보장함.
> 3. **가치**: 휴리스틱에 의존하던 기존 방식에서 탈피하여, 수학적 공정성을 통해 I/O Bound와 CPU Bound 프로세스 간의 균형 잡힌 응답성을 확보함.

## Ⅰ. 리눅스 표준의 선택, CFS(Completely Fair Scheduler)의 개요
- **정의**: 특정 프로세스가 CPU를 독점하지 못하도록 실행 시간을 가중치에 따라 공평하게 배분하는 리눅스 커널의 기본 스케줄링 알고리즘.
- **철학**: "시스템에 N개의 프로세스가 있다면, 각각에게 1/N의 처리 능력을 할당한다."

## Ⅱ. CFS의 핵심 메커니즘: vruntime과 Red-Black Tree

### 1. vruntime (Virtual Runtime)
- **개념**: 프로세스가 실행된 물리적 시간에 Nice 값에 따른 가중치를 적용한 가상 시간.
- **계산식**: $vruntime = \text{Actual Runtime} \times \frac{\text{Weight}_{0}}{\text{Weight}_{i}}$
    - 우선순위가 높을수록(Weight가 클수록) vruntime 증가 속도가 느려져 CPU 점유 기회가 많아짐.

### 2. 자료구조: Red-Black Tree (Self-Balancing BST)
- **구조**: 모든 실행 가능한 프로세스를 vruntime 기준으로 정렬하여 트리에 삽입.
- **동작**: 
    - **Selection**: 트리의 가장 왼쪽 노드(Smallest vruntime)를 선택 ($O(1)$ 또는 $O(\log N)$).
    - **Insertion**: 실행 완료된 프로세스를 갱신된 vruntime으로 트리 재삽입 ($O(\log N)$).

## Ⅲ. CFS의 주요 기술 요소 및 동작 흐름

### 1. 주요 기술 요소
| 요소 | 상세 설명 | 기술적 가치 |
|:---:|:---|:---|
| **Nice Value** | -20 ~ 19 사이의 값 | 가중치(Weight) 결정의 근거 |
| **Target Latency** | 모든 프로세스가 최소 한 번씩 실행되어야 하는 주기 | 응답성 보장 |
| **Minimum Granularity** | 프로세스가 선점되기 전 보장받는 최소 실행 시간 | 문맥 전환 오버헤드 방지 |
| **Load Weight** | 각 우선순위 단계별로 정의된 고정 가중치 | Nice값 간 10% 성능 차이 유지 |

### 2. 동작 흐름
1. **Tick 발생**: 현재 실행 중인 프로세스의 vruntime 업데이트.
2. **비교**: 현재 프로세스의 vruntime과 트리의 가장 왼쪽 노드 vruntime 비교.
3. **선점(Preemption)**: 현재 프로세스의 vruntime이 더 크고 차이가 일정 기준 이상이면 CPU 반납 및 트리 재삽입.
4. **교체**: 새로운 최저 vruntime 프로세스 실행.

## Ⅳ. CFS vs $O(1)$ 스케줄러 비교

| 비교 항목 | $O(1)$ Scheduler | CFS (Completely Fair) |
|:---:|:---|:---|
| **자료구조** | Priority Arrays (Active/Expired) | **Red-Black Tree** |
| **알고리즘** | 우선순위 기반, 복잡한 휴리스틱 | **공정성 기반 (vruntime)** |
| **I/O 대응** | 상호작용성 판별 수식 존재 | vruntime 미증가로 자동 우대 |
| **복잡도** | $O(1)$ | $O(\log N)$ |
| **주요 특징** | 성능은 좋으나 공정성 결여 | 구조적 단순함과 예측 가능한 공정성 |

## Ⅴ. CFS의 한계 및 보완 (심화)

- **Scalability**: 프로세스 수가 수만 개로 늘어나면 $O(\log N)$의 트리 탐색 비용도 무시할 수 없음.
- **Multicore 효율**: 각 코어마다 런큐(Run-queue)를 두어 락 경합을 줄여야 하며, 코어 간 부하 불균형 시 로드 밸런싱이 추가로 필요함.
- **Group Scheduling**: 사용자별, 컨테이너별로 CPU 할당량을 제한하기 위한 계층적(Cgroups) 확장 지원.

## Ⅵ. 기술사 관점의 결론 및 제언
- CFS는 **'복잡한 로직보다 단순하고 공정한 원칙'**이 더 좋은 성능을 낼 수 있음을 증명한 사례임.
- **실무 제언**: 특정 애플리케이션의 성능이 낮을 때 무조건 Nice값을 올리기보다는, `sched_latency_ns`나 `sched_min_granularity_ns` 같은 커널 파라미터를 튜닝하여 워크로드 성격(Throughput 지향 vs Latency 지향)에 맞추는 전략이 필요함.
