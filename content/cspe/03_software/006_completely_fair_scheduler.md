## Ⅰ. 개요
- **정의**: 가상 실행 시간(vruntime) 기반으로 CPU 시간을 공정 분배하는 리눅스 프로세스 스케줄러
- **배경/필요성**: 우선순위 고정 방식의 기아(starvation) 문제를 해소하는 공정 스케줄링이 필요함
- **비유**: 먹은 양이 가장 적은 사람에게 다음 한 입을 주는 뷔페 규칙임

| 출제 의도 | 반드시 짚을 핵심 | 감점 회피 포인트 |
|:---|:---|:---|
| 리눅스 스케줄링 원리 이해 | `vruntime` 최소 태스크 선택 | 레드블랙 트리 O(log n) 삽입·삭제 명시 |

> 요약: `vruntime`이 가장 작은 태스크를 선택하여 CPU 시간을 균등 분배하는 스케줄러임

## Ⅱ. 구성요소
```text
Task Pool --> Red-Black Tree (key: vruntime) --> Pick Leftmost --> Dispatch
                  |                                   |
              Insert/Update                      vruntime += delta
```

| 구성요소 | 설명 | 비유 |
|:---|:---|:---|
| `vruntime` | 가중치 보정된 누적 실행 시간 | 뷔페에서 먹은 총량 |
| Red-Black Tree | `vruntime` 순서로 태스크를 정렬하는 균형 이진 트리 | 정렬된 대기줄 |
| `nice` 값 | 태스크 가중치 — 낮을수록 `vruntime` 증가 속도가 느림 | 접시 크기(작으면 천천히 참) |
| Timeslice | `sched_latency` / 태스크 수로 산출한 실행 할당 시간 | 1회 식사 시간 |

> 요약: 레드블랙 트리에서 `vruntime` 최소 태스크를 O(1)로 선택하여 공정성을 보장함

## Ⅲ. 절차
```text
태스크 생성 --> vruntime 초기화 --> RB트리 삽입 --> 최소 vruntime 선택/실행
                                       ^                    |
                                       +--- vruntime 갱신 --+
```
- 1단계: 신규 태스크 생성 시 현재 큐의 최소 `vruntime`으로 초기화
- 2단계: 레드블랙 트리에 `vruntime`을 키로 삽입(O(log n))
- 3단계: 트리의 최좌측 노드(최소 `vruntime`)를 선택하여 CPU에 디스패치
- 4단계: 실행 종료 후 `vruntime += 실행시간 * (기본가중치 / nice가중치)` 갱신 후 재삽입

> 요약: 삽입-선택-실행-갱신 순환으로 CPU 시간을 지속적으로 균등 분배함

## Ⅳ. 문제점
- 캐시 친화성 저하: 잦은 태스크 전환 — 컨텍스트 스위칭으로 캐시 미스율 증가
- 실시간 응답 부적합: 공정성 우선 설계 — 경성 실시간 데드라인 보장 불가
- 다코어 부하 불균형: 코어별 독립 RB트리 운영 — 코어 간 태스크 편중 발생 가능

> 요약: 캐시 효율, 실시간성, 다코어 균형에서 한계가 존재함

## Ⅴ. 개선방안
1. 단기: 스케줄 도메인 내 주기적 로드밸런싱으로 캐시 친화성과 균형을 동시 추구
2. 중기: RT 스케줄링 클래스(SCHED_FIFO/RR)와 계층 분리로 실시간 태스크 별도 처리
3. 장기: EEVDF(Earliest Eligible Virtual Deadline First) 등 차세대 공정 스케줄러로 전환

> 요약: 로드밸런싱, RT 클래스 분리, 차세대 스케줄러 전환으로 한계를 극복함

## Ⅵ. 전망
- 발전 방향: 리눅스 커널에서 EEVDF 스케줄러가 CFS를 점진 대체하는 추세임
- 기술사적 판단: CFS의 `vruntime` 공정성 원리는 차세대 스케줄러에도 핵심 개념으로 계승됨
- 기술사 제언: 워크로드 특성(배치/대화형/실시간)에 따른 스케줄링 정책 선택 기준 수립이 필요
