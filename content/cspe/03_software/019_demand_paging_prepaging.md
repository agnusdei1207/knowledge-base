# 📖 【암기용】 개념 완전 이해

## 한눈에
- **개요**: 요구 페이징(Demand Paging)은 프로세스가 실제 참조할 때만 페이지를 디스크에서 메모리로 가져오는 **반입(Fetch) 정책**이고, 프리페이징(Prepaging)은 폴트 발생 시 인접 페이지까지 예측해 한꺼번에 적재하는 반입 정책임.
- **왜 필요한가**: 프로그램 전체를 메모리에 올리면 공간이 낭비되고, 1장씩만 올리면(순수 요구 페이징) 초기 폴트가 집중 발생(Cold Start)해 디스크 탐색 비용이 폭증함. 두 정책의 트레이드오프를 이해해야 최적의 반입 전략을 구성할 수 있음.
- **핵심 직관**: 요구 페이징은 "필요한 재료만 그때그때 사는 알뜰형", 프리페이징은 "어차피 마트 간 김에 몰아서 사는 대량구매형" — 공간 지역성이 높으면 대량구매가 이득이고, 무작위 접근이면 그때그때가 유리함.

## 핵심 용어 정리 (내부에 등장하는 것들)

| 용어/표기 | 의미 | 비유·예 |
|:---|:---|:---|
| 반입 정책 (Fetch Policy, 상위 키워드) | 페이지를 언제·얼마나 메모리로 가져올지 결정하는 정책 | 장보기 시점·수량 규칙 |
| 요구 페이징 (Demand Paging) | CPU가 참조하는 시점(Page Fault 발생)에 해당 페이지 1장만 적재 | 필요한 재료만 즉시 구매 |
| 순수 요구 페이징 (Pure Demand Paging) | 프로세스 시작 시 페이지를 전혀 미리 올리지 않는 극단형 | 빈손으로 주방에 서는 것 |
| 프리페이징 (Prepaging) | 폴트 시 인접 페이지나 워킹셋을 예측해 한꺼번에 적재 | 한 번 갈 때 묶음 구매 |
| 공간 지역성 (Spatial Locality) | 방금 참조한 주소 근처를 곧 참조할 경향 | 마트 한 코너를 보면 옆 코너도 봄 |
| Readahead | 리눅스 커널이 순차 읽기 패턴 감지 시 미리 읽기 창을 점진적으로 확대하는 프리페이징 구현 | 자동 추천 장바구니 |
| Direct I/O | 애플리케이션이 OS의 Page Cache(프리페이징)를 우회해 디스크를 직접 제어 | 직원 없이 직접 골라 담기 |

## 깊이 이해
- **배경·문제의식**: 가상 메모리 시스템(016 참조)에서 페이지 폴트는 디스크 I/O를 수반해 수 ms의 지연을 유발함. 디스크는 탐색 시간(Seek Time, HDD 기준 5~10ms)이 전송 시간(0.1ms/4KB)보다 수십 배 크므로, 요청 횟수를 줄이는 것이 I/O 비용 절감의 핵심임. 이 문제에서 "언제, 얼마나 가져올 것인가"라는 반입 정책 설계가 등장함.
- **작동 원리**:
  - 요구 페이징: CPU가 주소 참조 -> MMU가 유효 비트 확인 -> Invalid이면 Page Fault 인터럽트 -> OS가 디스크에서 해당 페이지 1장을 프레임에 적재 -> 페이지 테이블 갱신 -> 명령어 재실행.
  - 프리페이징: 위 과정에서 페이지 1장이 아닌 인접 블록(예: 32KB = 8페이지)을 한 번의 디스크 탐색으로 일괄 적재. 리눅스의 Readahead는 순차 패턴 감지 시 창 크기를 128KB->256KB->...로 점진 확대함.
- **비유**: HDD의 디스크 암(Arm)이 원하는 위치까지 이동하는 것은 크레인이 컨테이너를 찾아가는 것과 유사함. 1개씩 가져오면 크레인이 매번 이동하지만, 인접 4개를 한 번에 가져오면 이동은 1회로 줄어듦.
- **구체 예시**: `int arr[10000]` 순차 순회 시 순수 요구 페이징은 4KB 페이지당 1024개 정수를 담으므로 약 10회 폴트 발생. 프리페이징(8페이지 단위)이면 2회 폴트로 감소. 반면 B-Tree 인덱스 탐색처럼 랜덤 접근이면 프리페이징한 인접 페이지 7장이 미참조되어 프레임만 낭비됨.
- **흔한 오해·주의점**: (1) 두 정책은 양자택일이 아님 — 현대 OS는 상황별로 혼합(Hybrid) 운용함. (2) NVMe SSD는 탐색 시간이 HDD의 1/100이라 프리페이징의 이득이 감소하지만, 요청 횟수 자체를 줄이는 효과는 여전함. (3) RDBMS는 OS의 프리페이징이 자체 버퍼 풀과 이중 캐싱을 유발하므로 Direct I/O(`O_DIRECT`)로 우회함.

## 연결 개념
- (018 워킹셋·페이지 폴트) 프리페이징이 통째로 적재하는 대상인 워킹셋(WS(t,Δ))의 정의
- (017 페이지 교체 알고리즘) 프리페이징으로 적재된 페이지도 프레임 부족 시 교체 대상이 됨
- (016 가상 메모리) 페이지 폴트가 발생하는 전제 구조

# 📝 【답안용】 시험 답안 템플릿

## 핵심 인사이트 (3줄 요약)

> 1. **본질**: 가상 메모리에서 페이지 폴트 비용을 제어하기 위해, 참조 시점에만 1장을 적재(요구 페이징)할지 인접 페이지까지 예측 적재(프리페이징)할지를 결정하는 I/O 반입(Fetch) 정책임.
> 2. **가치**: 요구 페이징은 메모리 낭비를 원천 차단하고, 프리페이징은 디스크 탐색 횟수를 줄여 순차 접근 처리량을 수 배 향상시킴.
> 3. **판단 포인트**: 워크로드의 접근 패턴(순차 vs 랜덤)에 따라 두 정책의 혼합 비율을 동적으로 조절하는 하이브리드 설계가 핵심임.

## 출제 의도 및 답안 포인트

| 출제 의도 | 반드시 짚을 핵심 | 감점 회피 포인트 |
|:---|:---|:---|
| 반입 정책별 장단점과 트레이드오프 이해 | 요구 페이징(초기 지연, 공간 절약) vs 프리페이징(I/O 최적화, 예측 실패 낭비) | 하나가 절대 우월하다는 이분법적 서술 |
| 프리페이징의 작동 근거와 한계 | 공간 지역성(Spatial Locality) 기반 예측, Readahead 구현 | 예측 실패 시 캐시 오염 리스크 누락 |

> 요약: 요구 페이징(메모리 절약)과 프리페이징(I/O 절감)의 트레이드오프를 공간 지역성 관점에서 분석하고 하이브리드 전략을 도출해야 함.

---

## Ⅰ. 개요 및 필요성

- 개요: 가상 메모리 시스템에서 페이지를 언제·얼마나 적재할지 결정하는 반입(Fetch) 정책임
- 배경: 프로그램 전체 적재는 메모리 낭비, 1장씩 요구 페이징은 디스크 탐색 비용(HDD 5~10ms/회) 폭증
- 필요성: 디스크 I/O 횟수를 최소화하면서 메모리 사용 효율을 극대화하기 위해 접근 패턴 기반 적응형 반입 전략이 필수임

---

## Ⅱ. 구조 및 구성요소

```text
CPU 참조 -> MMU: 유효 비트 확인
  -> Hit: 물리 프레임에서 즉시 읽기 (폴트 없음)
  -> Miss(Page Fault):
     / 요구 페이징: 해당 페이지 1장만 디스크에서 적재
     / 프리페이징: 해당 페이지 + 인접 N장을 블록 단위로 일괄 적재
       -> 페이지 테이블 갱신 -> 명령어 재실행
```

| 구성요소 | 역할 | 비고 |
|:---|:---|:---|
| Page Fault Handler | 폴트 감지 후 디스크 I/O 요청 발행 | 인터럽트 기반 |
| Readahead 엔진 | 순차 패턴 감지 시 미리 읽기 창 크기를 점진 확대 | 리눅스 VFS 계층 |
| Page Cache | 디스크에서 읽은 페이지를 메모리에 캐싱 | 프리페이징 결과 저장 |
| Direct I/O 인터페이스 | 앱이 Page Cache를 우회해 디스크 직접 접근 | O_DIRECT 플래그 |

> 요약: Page Fault Handler가 반입을 트리거하고, Readahead가 프리페이징 범위를 결정하며, Direct I/O로 불필요한 프리페이징을 차단함.

---

## Ⅲ. 동작원리 및 흐름도

```text
프로세스 시작(메모리 비어 있음) -> 첫 참조 -> Page Fault 발생
  -> OS: 접근 패턴 판별
    / 순차 패턴: Readahead 창 확대(128KB -> 256KB -> ...) -> 블록 단위 프리페이징
    / 랜덤 패턴: 해당 페이지 1장만 요구 페이징
  -> 프레임 할당 -> 페이지 테이블 갱신 -> 명령어 재실행
```

1. 폴트 발생: CPU 참조 시 유효 비트 Invalid이면 Fault Trap 발생
2. 패턴 감지: 커널이 최근 폴트 주소의 연속성을 검사해 순차/랜덤 패턴 판별
3. 반입 결정: 순차면 Readahead 창만큼 프리페이징, 랜덤이면 1장만 요구 페이징
4. 적재 완료: 프레임에 페이지 배치 후 페이지 테이블 갱신, 프로세스 재개

> 요약: OS가 접근 패턴을 실시간 감지해 요구 페이징과 프리페이징의 비율을 동적으로 조절함.

---

## Ⅳ. 특징

- 메모리 효율: 요구 페이징은 참조된 페이지만 적재하므로 메모리 낭비가 0이며, 프리페이징은 예측 실패 시 미참조 페이지가 프레임을 점유함
- I/O 효율: 프리페이징은 한 번의 탐색으로 연속 블록을 전송해 디스크 탐색 횟수를 1/N로 감소시킴
- 예측 의존성: 프리페이징 효과는 공간 지역성에 비례하며, 랜덤 접근 워크로드에서는 캐시 오염(불필요한 페이지가 필요한 페이지를 축출)을 유발함
- 하이브리드 운용: 현대 OS는 프로세스 초기에는 요구 페이징, 순차 패턴 감지 시 프리페이징, 프로세스 재개 시 워킹셋 프리페이징으로 상황별 전환함

> 요약: 두 정책은 메모리 절약과 I/O 절감의 트레이드오프이며, 접근 패턴에 따라 동적 혼합이 최적임.

---

## Ⅴ. 심화 비교 및 적용 판단

| 구분 | 요구 페이징 | 프리페이징 | 선택 기준 |
|:---|:---|:---|:---|
| 트리거 | Page Fault 발생 시점 | Fault + 인접 예측 또는 프로세스 재개 | 접근 패턴 |
| 메모리 사용 | 참조 페이지만 점유 (낭비 0) | 예측 실패 시 미참조 페이지 점유 | 메모리 여유도 |
| I/O 비용 | 폴트당 탐색 1회 (HDD 5~10ms) | 탐색 1회로 N장 전송 | 디스크 특성(HDD vs SSD) |
| 적합 워크로드 | 랜덤 접근(인덱스 탐색, OLTP) | 순차 접근(스트리밍, 배열 순회) | 공간 지역성 강도 |

> 요약: 랜덤 접근은 요구 페이징, 순차 접근은 프리페이징이 유리하며, NVMe SSD 환경에서는 프리페이징 이득이 감소하므로 Readahead 크기를 보수적으로 설정함.

**리스크·대응:**
- 프리페이징 캐시 오염: 랜덤 접근 시 미참조 페이지가 워킹셋 페이지를 축출 -> Direct I/O(O_DIRECT)로 OS 프리페이징 우회 (지표: Page Cache Hit Rate)
- 순수 요구 페이징 Cold Start: 프로세스 시작·재개 시 폴트 연쇄 -> 워킹셋 기반 프리페이징으로 핫 페이지 일괄 적재 (지표: Major Fault 횟수)

**도입 후 점검 지표:**
- 성능: Major Page Fault Rate — `sar -B` pgmajfault, 목표: 워크로드별 임계 이하 유지
- 운영: Readahead Hit Rate — 프리페이징된 페이지의 실제 참조 비율, 50% 미만이면 창 크기 축소 필요

## Ⅵ. 실무 적용 및 결론

**적용 방안 3개:**
1. Linux Readahead 튜닝: 파일 서버(NFS/Samba) 대용량 파일 전송 시 `blockdev --setra 4096`(2MB)으로 미리 읽기 창을 확대해 디스크 탐색을 최소화함
2. DB Direct I/O 설정: PostgreSQL·Oracle의 shared_buffers에 자체 LRU 교체를 적용하고, `O_DIRECT` 기반으로 OS Page Cache 의존성을 제거해 이중 캐싱(Double Buffering) 방지함
3. 컨테이너 워킹셋 프리페이징: 쿠버네티스 Pod 재시작 시 이전 워킹셋(RSS 기준)을 ZRAM에 압축 보존 후 복귀 시 일괄 복원해 Cold Start 지연을 최소화함

**결론:**
- 기술사 판단: 요구 페이징과 프리페이징은 상극이 아닌 보완 관계이며, 접근 패턴(순차 vs 랜덤)과 저장 매체(HDD vs SSD)에 따라 동적 비율 조절이 필수임
- 향후 방향: NVMe/CXL 메모리 계층에서는 탐색 비용이 극소화되어 프리페이징보다 `madvise` 시스템 콜 기반의 애플리케이션 힌트형 반입이 강조되는 추세임
