# 📖 【암기용】 개념 완전 이해

## 한눈에
- **개요**: 쿠버네티스에서 데이터베이스처럼 '상태(State)'와 '순서'가 중요한 애플리케이션을 안정적으로 배포하고 관리하기 위한 워크로드 컨트롤러이다.
- **왜 필요한가**: 일반적인 ReplicaSet(Deployment)은 파드를 무작위 이름으로 동시에 띄우고 지운다. DB 클러스터(Master-Slave)는 1번이 마스터, 2번이 슬레이브라는 순서와 고정된 식별자가 필요한데, Deployment로는 이를 구현할 수 없다.
- **핵심 직관**: Deployment가 이름 없는 알바생들(누가 죽든 새 알바생을 투입)이라면, StatefulSet은 번호표를 달고 자기 전용 책상(디스크)을 가진 정규직(1번이 죽으면 똑같은 1번 이름과 1번 책상을 가진 정규직이 다시 옴)이다.

## 핵심 용어 정리

| 용어/표기 | 의미 | 비유·예 |
|:---|:---|:---|
| StatefulSet | 상태를 가지는 파드의 순차적 배포/관리를 담당하는 컨트롤러 | "고유 번호표를 가진 정규직 관리자" |
| 헤드리스 서비스 (Headless Service) | ClusterIP가 None으로 설정되어 파드 각각의 고정된 도메인(DNS)을 만들어주는 서비스 | "정규직 각자의 직통 전화번호 부여" |
| VolumeClaimTemplates | 파드가 생성될 때마다 파드 전용 PVC를 자동으로 찍어내는 템플릿 | "정규직 한 명당 전용 캐비닛(디스크) 자동 지급" |
| 순서 보장 (Ordered, Graceful) | 파드가 0번부터 순차적으로 생성되고, 역순으로 삭제되는 특성 | "0번 마스터 세팅 후 1번 슬레이브 투입" |

## 깊이 이해
- **배경·문제의식**: K8s 초기에는 무상태(Stateless) 웹 서버만 띄우기 좋았다. 하지만 Redis 클러스터나 MySQL 복제본을 K8s에 올리려니, 파드가 죽었다 뜰 때마다 IP와 디스크가 바뀌어 DB 동기화가 다 깨졌다. 상태 보존을 위한 강력한 식별자와 전용 스토리지 맵핑 기능이 필요했다.
- **작동 원리**: StatefulSet은 파드 이름에 0부터 시작하는 인덱스를 붙인다(`web-0, web-1`). 그리고 `VolumeClaimTemplates`를 통해 `web-0` 전용 디스크를 만들어 붙인다. `web-0`이 죽어서 새로 스케줄링되더라도 이름은 무조건 `web-0`으로 고정되고, 원래 쓰던 `web-0`의 디스크를 다시 찾아가 마운트한다.
- **비유**: 좌석 번호 지정제다. 1번 타자가 아파서 교체되어도 새로 온 선수는 반드시 1번 타석에 서고, 1번 타자 전용 배트(스토리지)를 그대로 물려받아 사용한다.
- **구체 예시**: MongoDB 리플리카셋 배포 시 `mongo-0`이 Primary가 되고 `mongo-1`, `mongo-2`가 Secondary가 된다. Headless Service 덕분에 `mongo-0.mongo-svc`라는 고정 도메인이 생겨 통신이 보장된다.
- **흔한 오해·주의점**: StatefulSet을 삭제한다고 해서 파드들이 쓰던 디스크(PVC)까지 같이 삭제되지는 않는다. 데이터 안전을 위해 디스크는 의도적으로 남겨두므로, 완전 삭제 시 수동으로 PVC를 지워야 한다.

## 연결 개념
- Deployment — 상태가 없는(Stateless) 파드를 무작위로 복제하는 가장 일반적인 컨트롤러
- PersistentVolumeClaim (PVC) — 파드가 사용할 스토리지 요청서, StatefulSet에서는 템플릿으로 자동 생성됨
- Operator Pattern — StatefulSet보다 한 차원 높게, DB 특유의 백업/복구 로직까지 K8s 컨트롤러에 심는 패턴

# 📝 【답안용】 시험 답안 템플릿

## 핵심 인사이트 (3줄 요약)

> 1. **본질**: StatefulSet은 파드의 고정된 식별자(네트워크 DNS, 인덱스)와 전용 스토리지(PVC) 맵핑을 보장하는 쿠버네티스 컨트롤러이다.
> 2. **가치**: 파드의 생성/삭제 순서를 엄격히 제어하고, 파드가 재시작되어도 기존 데이터를 그대로 물려받아 DB 클러스터링 구성이 가능해진다.
> 3. **판단 포인트**: 웹 프론트는 Deployment를 사용하되, 인덱스 고정과 영속성이 필수적인 RDBMS, NoSQL, Kafka 브로커 등은 StatefulSet과 Headless Service를 결합해 아키텍처를 설계해야 한다.

## 출제 의도 및 답안 포인트

| 출제 의도 | 반드시 짚을 핵심 | 감점 회피 포인트 |
|:---|:---|:---|
| 상태 보존(Stateful) 애플리케이션의 컨테이너화 요건 이해 | 고유한 네트워크 식별자(Headless Service), 전용 스토리지(VolumeClaimTemplates), 순차적 배포 | Deployment와 차이를 명확히 비교하지 않고 단순 파드 생성 컨트롤러로 서술 |

> 요약: 변동성이 큰 K8s 환경에서 식별자와 데이터를 영속적으로 유지하는 메커니즘을 Deployment와의 비교를 통해 명확히 제시해야 한다.

## Ⅰ. 개요 및 필요성

- 개요: 상태 보존이 필요한 애플리케이션(DB 등)을 위해 파드의 순서, 고유 식별자, 전용 스토리지를 보장하는 오케스트레이션 워크로드 컨트롤러
- 배경: 무상태(Stateless) 중심의 Deployment 컨트롤러는 파드의 무작위 생성과 공용 스토리지 매핑으로 인해 Master-Slave 구조의 DB 클러스터 링 구성 불가
- 필요성: 파드가 죽고 재시작하더라도 동일한 DNS 이름과 기존에 쓰던 물리적 데이터(디스크)를 정확히 다시 찾아 연결(Re-binding)하기 위함

---

## Ⅱ. 구조 및 구성요소

```text
StatefulSet Controller
   |-> (순서 제어: 0 -> 1 -> 2)
   |-> Pod 0 (web-0) <---> PVC (data-web-0) <---> PV (EBS)
   |-> Pod 1 (web-1) <---> PVC (data-web-1) <---> PV (EBS)
Headless Service -> web-0.nginx.default.svc.cluster.local (고정 DNS 부여)
```

| 구성요소 | 역할 | 특이사항 |
|:---|:---|:---|
| StatefulSet 리소스 | 파드의 순차 생성/삭제/롤링업데이트 제어 명세 | `podManagementPolicy: OrderedReady` 보장 |
| 헤드리스 서비스 (Headless Svc) | `clusterIP: None`으로 설정되어 개별 파드의 고정 DNS 도메인 쿼리 지원 | 파드 간 P2P 통신 및 클러스터링 필수 요소 |
| VolumeClaimTemplates | 파드 복제본 수만큼 파드 이름이 접미사로 붙은 고유 PVC를 자동 생성 | 수동 PVC 생성 불필요 |

> 요약: StatefulSet은 헤드리스 서비스로 네트워크 식별자를 고정하고, 볼륨 템플릿으로 각 파드에 1:1 전용 데이터 공간을 영구 할당한다.

---

## Ⅲ. 동작원리 및 흐름도

```text
StatefulSet 생성 -> Pod 0 기동/PVC 바인딩 -> Pod 0 Ready -> Pod 1 기동 -> (장애 시) 동일 이름으로 재기동
```

- 1단계 [순차적 프로비저닝]: StatefulSet이 인덱스 0번 파드(`web-0`)와 매칭되는 PVC를 생성하고 노드에 스케줄링 시작
- 2단계 [상태 점검 및 다음 진행]: `web-0` 파드의 Readiness Probe가 통과되어 완전 구동(Ready) 상태가 되어야만 비로소 인덱스 1번(`web-1`) 생성 착수
- 3단계 [네트워크 고정]: 생성된 파드들은 Headless Service를 통해 `web-0.svc-name` 형식의 고정된 DNS 레코드를 획득하여 클러스터링 조인 수행
- 4단계 [장애 복구 및 영속성]: `web-0` 파드가 노드 장애로 죽으면, K8s는 다른 노드에 똑같은 이름(`web-0`)으로 파드를 재현하고 원래 쓰던 PVC(`data-web-0`)를 다시 연결

> 요약: 생성과 삭제가 철저히 인덱스 순서에 따라(Ordered) 진행되며, 재해 복구 시에도 파드의 이름과 디스크가 강결합되어 상태를 유지한다.

## Ⅳ. 심화 비교 및 적용 판단

| 비교 축 | Deployment | StatefulSet | 선택 기준 |
|:---|:---|:---|:---|
| 상태 유무 | Stateless (무상태) | Stateful (상태 보존) | 데이터 영속성 요구 여부 |
| 파드 식별자 | 무작위 해시 (`web-7b9c...`) | 고정 인덱스 (`web-0, web-1`) | 고정 네트워크 DNS 필요성 |
| 스토리지 매핑 | 모든 파드가 동일 PVC 공유 또는 임시 | 파드당 1:1 고유 PVC 할당 보장 | 개별 파드의 전용 디스크 여부 |
| 배포 순서 | 병렬 생성 및 삭제 (빠름) | 0번부터 순차적 생성 및 역순 삭제 | Master-Slave 초기화 순서 강제 여부 |

> 요약: 무상태 웹 프론트나 API 서버는 Deployment로 신속히 확장하고, 데이터 복제와 순서가 중요한 DB, 카프카 등은 StatefulSet을 채택한다.

**리스크·대응:**
- 스플릿 브레인(Split Brain): 노드 네트워크 단절 시, 기존 파드가 살아있는데 새 노드에 동일 이름의 파드가 떠서 데이터 오염 발생 위험 → StatefulSet은 노드 단절 시 Kubelet의 확실한 파드 삭제(강제 차단) 확인 전까지 대체 파드를 생성하지 않는 보수적 방어 체계 유지 (지표: 파드 중복 실행 건수 0건)
- 불완전한 삭제 리스크: StatefulSet 삭제 시 파드만 지워지고 디스크(PVC)는 남아 클라우드 비용 누수 발생 → 의도된 안전 장치이나, 완전 철거 시 수동으로 PVC를 식별하여 삭제(Delete)하는 운영 프로세스 강제화 (지표: 미사용 고립 볼륨 0건)

## Ⅴ. 실무 적용 및 결론

**적용 방안 3개:**
1. RDBMS 리플리카 구성: MySQL 배포 시 StatefulSet을 적용해 0번은 Master로, 1~N번은 Read-only Slave로 고정 구성하고 Headless Service로 데이터 동기화 채널 구축
2. 메시지 브로커 분산 환경: Kafka 및 ZooKeeper 클러스터 구성 시 노드 번호 기반 식별이 필수적이므로 StatefulSet으로 1:1 디스크 매핑 보장
3. Operator 패턴 고도화: 단순 StatefulSet만으로는 복잡한 DB 백업이나 Fail-over 로직 처리에 한계가 있으므로, 특정 DB 맞춤형 커스텀 컨트롤러인 K8s Operator(예: Percona Operator)로 진화 적용

**결론 (2줄):**
- 기술사 판단: 컨테이너는 원래 일회성이지만 StatefulSet은 파드에 영속적 정체성(식별자+데이터)을 부여하여, 모놀리식 DB 인프라를 클라우드 네이티브 환경으로 끌어들인 핵심 리소스이다.
- 향후 방향: StatefulSet은 쿠버네티스의 기본 프리미티브 역할을 넘어, 특정 애플리케이션의 복잡한 운영 노하우를 코드로 캡슐화한 Operator 패턴 아키텍처로 흡수/통합될 것이다.
