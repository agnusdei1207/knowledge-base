## Ⅰ. 개요
- **정의**: 검증 범위를 함수-모듈 간 연동-시스템 전체로 확장하는 3계층 테스트 분류 체계
- **배경/필요성**: 단일 수준 테스트만으로는 계층 간 인터페이스 결함을 검출할 수 없음
- **비유**: 부품 검사(단위) → 조립 검사(통합) → 완성차 시승(E2E)

| 출제 의도 | 반드시 짚을 핵심 | 감점 회피 포인트 |
|:---|:---|:---|
| 3수준 차이와 테스트 피라미드 비율 | 범위·속도·비용 간 트레이드오프 | 각 수준의 의존성 처리 방식(Mock/Stub/실환경) 구분 |

> 요약: 함수-연동-전체 3계층으로 결함 검출 범위를 계층화하는 체계임

## Ⅱ. 구성요소
```text
        /   E2E Test    \    <-- 실 환경, 느림, 소량
       /  Integration    \   <-- 모듈 간 연동, 중간
      /   Unit Test       \  <-- 함수 단위, 빠름, 대량
     +--------------------+
```

| 구성요소 | 설명 | 비유 |
|:---|:---|:---|
| Unit Test | 단일 함수·클래스를 Mock/Stub으로 격리해 검증 | 부품 단품 검사 |
| Integration Test | 모듈 간 인터페이스·DB·API 연동을 검증 | 조립 후 결합 검사 |
| E2E Test | 사용자 시나리오 기반으로 전체 시스템을 실 환경에서 검증 | 완성차 시승 |

> 요약: 격리 범위가 넓어질수록 현실성이 높아지고 실행 비용도 증가함

## Ⅲ. 절차
```text
Unit 작성 --> Integration 작성 --> E2E 작성 --> CI 파이프라인 배치
```
- 1단계: Unit 작성—핵심 로직 함수에 대해 입력-출력 쌍을 검증하는 테스트 작성
- 2단계: Integration 작성—DB·외부 API 등 실 의존성을 연결해 모듈 간 계약 검증
- 3단계: E2E 작성—사용자 시나리오(로그인→주문→결제)를 브라우저·API 수준에서 자동화
- 4단계: CI 파이프라인 배치—Unit → Integration → E2E 순서로 실행해 빠른 피드백 확보

> 요약: Unit-Integration-E2E-CI 배치 순으로 테스트를 구축·운영함

## Ⅳ. 문제점
- Unit 과신: 단위 커버리지가 높아도 모듈 간 계약 불일치는 검출 불가함
- Integration 환경 불안정: 외부 시스템 장애 시 테스트가 비결정적(flaky)으로 실패함
- E2E 유지 비용: UI 변경마다 선택자(selector)가 깨져 스크립트 수정 공수가 큼

> 요약: 수준 간 사각지대, 비결정적 실패, UI 의존 유지 비용이 과제임

## Ⅴ. 개선방안
1. 단기: Contract Test 도입으로 모듈 간 인터페이스 불일치를 Unit 수준에서 검출
2. 중기: 테스트 컨테이너(Testcontainers)로 외부 의존성을 격리해 비결정성 감소
3. 장기: Page Object 패턴·데이터 속성 기반 선택자로 E2E 스크립트 변경 내성 확보

> 요약: Contract Test-테스트 컨테이너-선택자 안정화 순으로 개선함

## Ⅵ. 전망
- 발전 방향: AI 기반 테스트 자동 생성으로 3계층 커버리지 균형을 자동 최적화
- 기술사적 판단: 테스트 피라미드 비율 준수가 CI/CD 파이프라인 성능의 핵심 지표임
- 기술사 제언: 테스트 전략(084)과 연계해 수준별 커버리지 목표를 명시할 필요
