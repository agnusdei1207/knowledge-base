## Ⅰ. 개요
- **정의**: 단위 시간당 API 호출 횟수를 제한하여 서버 자원을 보호하는 트래픽 제어 기법
- **배경/필요성**: 무제한 API 호출은 서버 과부하·비용 폭증·서비스 장애를 유발하므로 사전 차단이 필요함
- **비유**: 놀이공원 입장 인원을 시간대별로 제한하여 안전과 서비스 품질을 유지하는 것과 유사함

| 출제 의도 | 반드시 짚을 핵심 | 감점 회피 포인트 |
|:---|:---|:---|
| API 보호·트래픽 제어 설계 | 알고리즘별 특성 비교 | 429 응답 코드·Retry-After 헤더 언급 |

> 요약: 단위 시간당 호출 횟수를 제한하여 API 서버를 과부하로부터 보호하는 기법임

## Ⅱ. 구성요소
```text
Client --> [Rate Limiter] --> API Server
               |
        Counter / Bucket
        (Redis / In-Memory)
```

| 구성요소 | 설명 | 비유 |
|:---|:---|:---|
| Rate Limiter | 요청 빈도를 측정·제한하는 게이트웨이 컴포넌트 | 놀이공원 입장 게이트 |
| Counter/Bucket | 호출 횟수·토큰 잔량을 추적하는 저장소 | 입장권 잔여 수량 카운터 |
| Policy | 사용자·IP·API 키별 제한 규칙을 정의하는 정책 | 티켓 등급별 입장 규칙 |
| 429 Response | 한도 초과 시 반환하는 HTTP 상태 코드 | 매진 안내 표지판 |

> 요약: Rate Limiter-Counter-Policy-429 Response 구조로 트래픽을 제어함

## Ⅲ. 절차
```text
요청 수신 --> 식별/분류 --> 한도 검사 --> 허용/거부
     |            |            |            |
     v            v            v            v
  API 호출    키/IP 추출   카운터 비교   200 or 429
```
- 1단계: Rate Limiter가 클라이언트 요청을 수신함
- 2단계: API 키·IP·사용자 ID 등으로 요청자를 식별·분류함
- 3단계: 해당 식별자의 카운터를 정책 한도와 비교함
- 4단계: 한도 이내이면 요청을 통과시키고, 초과 시 429 + `Retry-After`를 반환함

> 요약: 수신-식별-검사-허용/거부 4단계로 호출 빈도를 제어함

## Ⅳ. 문제점
- 분산 환경 동기화: 다중 서버에서 카운터 정합성을 유지하기 어려움
- 버스트 트래픽 대응: 고정 윈도우 방식은 윈도우 경계에서 순간 2배 트래픽을 허용함
- 정책 세분화 한계: 단순 글로벌 제한은 사용자 등급별 차등 제어에 부적합함

> 요약: 분산 동기화·버스트·정책 세분화가 주요 과제임

## Ⅴ. 개선방안
1. 단기: Redis 기반 중앙 카운터로 분산 환경 정합성 확보
2. 중기: Sliding Window·Token Bucket 알고리즘으로 버스트 트래픽 평활화
3. 장기: 사용자 등급·API 엔드포인트별 다계층 정책 엔진 구축

> 요약: 중앙 카운터-평활 알고리즘-다계층 정책 순으로 개선함

## Ⅵ. 전망
- 발전 방향: API Gateway·서비스 메시에 내장형 Rate Limiting이 표준화 중임
- 기술사적 판단: API 경제 확산과 함께 과금·SLA 연계형 제어의 중요성이 증가함
- 기술사 제언: Rate Limiting과 Circuit Breaker·Throttling을 통합한 복합 방어 전략을 수립할 필요
