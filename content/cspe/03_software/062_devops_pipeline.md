# 📖 【암기용】 개념 완전 이해

## 한눈에
- **개요**: 소프트웨어의 코딩부터 빌드, 테스트, 릴리스, 배포, 운영까지의 전 과정을 자동화한 작업 흐름
- **왜 필요한가**: 개발(Dev)과 운영(Ops)이 단절되면 코드를 넘길 때마다 병목이 생기고 책임이 모호해진다. 이를 자동화된 파이프라인으로 연결하여 신속하고 안정적인 배포를 달성해야 한다.
- **핵심 직관**: "컨베이어 벨트". 개발자가 코드를 올리면, 벨트가 알아서 조립(빌드)하고 검수(테스트)해서 매장(운영 환경)에 진열(배포)한다.

## 핵심 용어 정리

| 용어/표기 | 의미 | 비유·예 |
|:---|:---|:---|
| 지속적 통합 (CI) | 코드 변경 사항을 수시로 병합하고 자동 빌드·테스트 | 매일 퇴근 전 레고 블록 조립해보기 |
| 지속적 배포 (CD) | 테스트를 통과한 코드를 프로덕션 환경에 자동 릴리스/배포 | 조립 완료된 레고를 즉시 진열대에 올리기 |
| CAMS 모델 | Culture, Automation, Measurement, Sharing (DevOps 4요소) | 협업을 위한 4가지 핵심 가치 |

## 깊이 이해
- **배경·문제의식**: 전통적 환경에서는 개발팀이 몇 달간 만든 코드를 운영팀에 "던져주고" 배포를 요구했다. 운영팀은 안정성이 깨질까 두려워 배포를 꺼리고, 이는 타임투마켓(Time-to-Market) 지연으로 이어졌다.
- **작동 원리**: 소스코드 관리(Git)를 시작으로, 코드가 푸시되면 Jenkins나 GitHub Actions 같은 파이프라인 엔진이 트리거된다. 엔진은 코드를 컴파일하고 유닛 테스트를 돌린다(CI). 통과하면 컨테이너 이미지를 만들고 저장소에 올린 뒤, 운영 서버에 새 버전을 반영한다(CD). 이 모든 과정이 인간 개입 없이 자동으로 흐른다.
- **비유**: 자동차 공장의 조립 라인. 부품(코드)이 들어오면 용접, 도색, 안전 검사(테스트)가 자동으로 차례차례 진행되어 최종 자동차(서비스)가 나온다.
- **구체 예시**: 개발자가 버그 수정 코드를 `main` 브랜치에 푸시 -> Jenkins가 즉시 코드를 받아 JUnit 테스트 실행 -> 성공 시 Docker 이미지 빌드 후 넥서스에 푸시 -> K8s 클러스터에 Rolling Update 배포. (소요 시간 10분)
- **흔한 오해·주의점**: "DevOps 파이프라인 = Jenkins 구축"으로 착각한다. 도구(툴체인)는 수단일 뿐, 핵심은 Dev와 Ops 간의 장벽을 허물고 작은 단위로 빈번하게 배포하는 문화적 변화(Culture)다.

## 연결 개념
- CI/CD (Continuous Integration / Continuous Deployment): 파이프라인의 핵심 기술 실체
- 컨테이너 및 쿠버네티스: 파이프라인을 통한 멱등성 있는 배포를 가능케 하는 인프라 기술
- DevSecOps: 파이프라인 각 단계에 보안 스캔을 내재화한 확장 개념

# 📝 【답안용】 시험 답안 템플릿

## 핵심 인사이트 (3줄 요약)

> 1. **본질**: DevOps 파이프라인은 소프트웨어 생명주기(SDLC)의 계획, 코드, 빌드, 테스트, 배포, 운영 전 단계를 자동화된 툴체인으로 엮은 연속적인 작업 흐름이다.
> 2. **가치**: 수동 개입을 최소화하여 배포 리드 타임을 단축시키고(Time-to-Market), 잦은 소규모 배포로 장애 발생 시 리스크(Blast Radius)를 줄인다.
> 3. **판단 포인트**: 단순히 CI/CD 도구를 나열하는 데 그치지 않고, 형상관리부터 모니터링까지 이어지는 전체 순환 구조(Feedback Loop)와 문화적 융합을 제시해야 한다.

## 출제 의도 및 답안 포인트

| 출제 의도 | 반드시 짚을 핵심 | 감점 회피 포인트 |
|:---|:---|:---|
| 소프트웨어 딜리버리 자동화 이해 | CI/CD 요소, 파이프라인 단계(Plan-Code-Build-Test-Release-Deploy-Operate) | 특정 툴(Jenkins 등) 사용법 서술 |
| 개발과 운영의 사일로 해결 방안 | CAMS 모델, 피드백 루프(Feedback Loop) 통합 | 기술적 요소만 강조하고 문화 누락 |
| 현대 SDLC 적용 역량 | 컨테이너 기반 멱등성, 자동화된 테스트 범위 | 수동 테스트 중심 아키텍처 제시 |

> 요약: 도구적 결합(CI/CD)을 넘어 개발과 운영의 책임을 통합하는 문화적·프로세스적 순환 구조임을 명확히 한다.

## Ⅰ. 개요 및 필요성

- 개요: 애플리케이션 변경 사항이 발생할 때부터 운영 환경에 반영될 때까지의 전 과정을 자동화한 통합 워크플로우
- 배경: 기존 사일로(Silo) 환경에서는 개발(속도 중시)과 운영(안정성 중시)의 목표 충돌로 인해 배포 지연 및 장애 빈발
- 필요성: 고품질 소프트웨어의 신속한 시장 출시(Time-to-Market 단축), 수동 작업 오류 제거, 잦은 배포를 통한 리스크 분산

---

## Ⅱ. 구조 및 구성요소

```text
[Plan] -> [Code] -> [Build] -> [Test] -> [Release] -> [Deploy] -> [Operate] -> [Monitor]
  ^                                                                                |
  +------------------------------- 피드백 루프 ---------------------------------------+
```

| 구성요소 | 주요 도구 예시 | 역할 |
|:---|:---|:---|
| 소스코드 및 형상관리 | Git, GitHub | 소스코드 버전 관리 및 변경 추적 (SSOT) |
| CI (지속적 통합) | Jenkins, GitHub Actions | 자동화된 컴파일, 패키징, 단위 테스트 |
| CD (지속적 배포) | ArgoCD, Spinnaker | 아티팩트를 대상 운영 환경에 안전하게 배포 |
| 모니터링 및 피드백 | Prometheus, Grafana | 운영 지표 수집 및 개발 단계로의 피드백 제공 |

> 요약: 코드 커밋부터 모니터링까지 선형적 흐름과 지속적 개선을 위한 피드백 루프가 툴체인으로 연결된다.

---

## Ⅲ. 동작원리 및 흐름도

```text
Commit 트리거 -> 소스 Checkout -> 빌드 및 단위 테스트 -> 이미지 생성 -> 프로비저닝 및 배포
```

- 1단계 [코드 통합 및 트리거]: 개발자가 코드를 메인 브랜치에 푸시하면 Webhook을 통해 CI 서버가 작동 시작
- 2단계 [빌드 및 정적 분석]: 소스코드를 컴파일하고, SonarQube 등을 통해 정적 코드 품질을 자동 검사
- 3단계 [테스트 및 아티팩트 생성]: 단위·통합 테스트를 수행하고, 성공 시 배포 가능한 불변 아티팩트(예: Docker Image) 생성 및 레지스트리 등록
- 4단계 [인프라 프로비저닝 및 배포]: IaC 도구로 인프라를 구성하고, 무중단 배포(Blue-Green 등) 기법으로 운영 환경 반영

> 요약: 커밋 즉시 트리거된 파이프라인이 코드 품질을 검증한 후 불변 아티팩트를 만들어 운영에 안전하게 배포한다.

---

## Ⅳ. 특징
- [불변 인프라(Immutable)]: 한 번 생성된 배포 아티팩트는 변경되지 않으며, 문제 시 새 버전을 빌드해 대체
- [파이프라인 코드화(Pipeline as Code)]: 파이프라인 자체를 Jenkinsfile 등의 코드로 관리하여 버전 관리 및 재사용성 확보
- [자동화된 피드백]: 빌드나 테스트 실패 시 즉각 알림을 발송해 결함이 뒷단으로 넘어가는 것을 차단(Shift-Left 효과)
- [단일 진실 공급원]: 형상 관리 시스템이 소스뿐 아니라 인프라 및 배포 파이프라인의 기준점 역할 수행

> 요약: 파이프라인 코드화와 불변성을 기반으로 수동 오류를 차단하고 일관된 배포를 보장한다.

## Ⅴ. 심화 비교 및 적용 판단

| 비교 축 | 전통적 배포 파이프라인 | DevOps 파이프라인 | 선택 기준 |
|:---|:---|:---|:---|
| 배포 주기 | 수 주 ~ 수 개월 단위 빅뱅 배포 | 일/시간 단위 소규모 빈번 배포 | 비즈니스 민첩성 요구 수준 |
| 품질 보증 | 수동 QA 및 인프라 구성 | 자동화된 테스트 및 정적 분석 | 결함 조기 발견 역량 |
| 협업 구조 | Dev와 Ops의 분리 (사일로) | 다기능 팀(Cross-functional) 통합 | 조직 문화 및 책임 공유 여부 |

> 요약: 빈번한 소규모 배포로 민첩성을 확보하되, 이를 뒷받침할 촘촘한 자동화 테스트와 조직 문화 개편이 전제되어야 한다.

**리스크·대응:**
- [테스트 커버리지 부족]: 자동화 속도만 빠르고 결함이 라이브로 직행 → 파이프라인 내 게이트웨이(Quality Gate) 설정 의무화 (지표: 결함 유출률)
- [플러그인/의존성 지옥]: CI 도구의 플러그인 업데이트로 파이프라인 붕괴 → 컨테이너 기반 격리 파이프라인(예: Tekton, GitHub Actions) 전환 (지표: 빌드 실패율)

**도입 후 점검 지표:**
- DORA 메트릭: 배포 빈도(Deployment Frequency), 변경 리드 타임(Lead Time for Changes) — 파이프라인 통계
- 안정성 지표: 변경 실패율(Change Failure Rate), 서비스 복구 시간(MTTR) — 모니터링 시스템

## Ⅵ. 실무 적용 및 결론

**적용 방안 3개:**
1. Pipeline as Code 도입: 파이프라인 구성을 수동 클릭이 아닌 `Jenkinsfile`이나 `yaml`로 정의하여 프로젝트 코드와 함께 형상 관리
2. 파이프라인 병렬화 및 캐싱: 빌드 속도 개선을 위해 의존성 다운로드 캐싱을 적용하고, 독립적인 테스트들을 병렬 스테이지로 구성하여 빌드 시간 50% 단축
3. 점진적 무중단 배포: CD 단계에 카나리(Canary) 배포 전략을 연동하여, 신규 버전을 5% 사용자에게 먼저 노출해 안정성 검증 후 전체 확대

**결론 (2줄):**
- 기술사 판단: DevOps 파이프라인의 성공 여부는 화려한 툴체인 구축이 아니라, 수동 개입 구간(Manual Approval)을 얼마나 안전하게 자동화 게이트로 대체하느냐에 달렸다.
- 향후 방향: 보안이 내재화된 DevSecOps를 거쳐, 플랫폼 엔지니어링(Platform Engineering)을 통한 개발자 셀프서비스(Self-Service) 파이프라인으로 진화해야 한다.
