## 미리 알고가기

- DevOps는 개발과 운영의 협업과 자동화를 통해 전달 속도와 안정성을 함께 높이려는 방식임
- 파이프라인은 계획에서 운영까지 흐름을 도구와 절차로 연결한 전달 경로임
- 공동 소유는 개발팀이 배포 후 운영 결과까지 책임지는 방식임

## Ⅰ. 개요

- **정의/개념**: DevOps 파이프라인은 코드 작성과 빌드와 테스트와 배포와 운영 모니터링과 피드백까지를 하나의 연속 흐름으로 연결해 개발과 운영 협업을 자동화하는 전달 체계임.
- **배경/필요성**: 개발 완료와 운영 인수인계가 분리된 조직에서는 배포 지연과 책임 공백이 커지므로, 전체 전달 흐름을 하나의 구조로 묶어 관리할 필요가 있음.

## Ⅱ. 특징

- 개발부터 운영까지 피드백 주기를 짧게 만듦
- 자동화와 운영 지표를 통해 병목을 드러냄
- 조직 협업 문화가 약하면 도구만 늘고 성과는 제한될 수 있음
- 배포 이후의 장애와 성능 결과를 다시 개발 흐름으로 되돌릴 수 있음

## Ⅲ. 종류 및 비교

| 구분 | 개발-운영 분리 방식 | DevOps 파이프라인 |
|:---|:---|:---|
| 책임 흐름 | 단계별 인계 중심으로 책임이 끊기기 쉬움 | 서비스 단위 공동 소유로 흐름이 이어짐 |
| 구조상 장점 | 역할 구분이 단순하고 초기 운영 방식 유지가 쉬움 | 배포 속도와 피드백 속도를 함께 높이기 좋음 |
| 구조상 한계 | 인수인계 지연과 책임 공백이 반복되기 쉬움 | 협업 문화와 자동화 체계를 함께 바꿔야 함 |
| 적합한 환경 | 저빈도 변경과 고정 절차 중심 조직에 맞음 | 제품 개선이 빠른 서비스 조직에 맞음 |

> 요약: DevOps 파이프라인은 배포 도구 모음이 아니라 개발과 운영 책임을 하나의 흐름으로 묶는 구조임.

## Ⅳ. 구성요소 및 구조

| 구성요소 | 설명 |
|:---|:---|
| 계획과 개발 흐름 | 요구와 작업을 코드 변경으로 연결해 우선순위와 개발 흐름을 정렬함 |
| 빌드와 검증 흐름 | 산출물 생성과 품질 검증과 배포 준비를 자동화함 |
| 운영과 모니터링 흐름 | 로그와 메트릭과 장애를 수집해 전달 결과를 관찰함 |
| 피드백 순환 | 운영 결과를 다시 개선 작업으로 돌려 지속 학습을 만듦 |

## Ⅴ. 원리 및 절차 흐름도

```text
+-------------+     +-------------+     +-------------+     +-------------+
| 계획/개발      | --> | 빌드/검증      | --> | 배포/운영      | --> | 피드백/개선    |
+-------------+     +-------------+     +-------------+     +-------------+
```

1. **계획 및 개발**: 요구를 작업 항목과 코드 변경으로 연결함
2. **빌드 및 검증**: 자동 빌드와 테스트와 품질 검사를 수행함
3. **배포 및 운영**: 운영 환경 배포와 모니터링을 진행함
4. **피드백 및 개선**: 장애와 성능과 사용자 반응을 다음 작업에 반영함

## Ⅵ. 실무 적용 및 유의점

1. SaaS 제품팀에서는 DevOps 파이프라인이 배포 속도를 높이지만 개발과 운영 책임이 여전히 분리돼 있으면 효과가 약하므로 서비스 공동 소유 모델을 함께 두고 인수인계 지연 시간과 배포 빈도로 확인함
2. 운영 지표가 개발 백로그로 돌아오지 않는 조직에서는 파이프라인이 단순 배포 통로로 남기 쉬우므로 장애와 성능 정보를 작업 시스템과 연결하고 피드백 반영 시간과 반복 결함 비율로 확인함

## Ⅶ. 결론

DevOps 파이프라인은 개발과 운영을 한 팀의 연속 책임으로 묶어 전달과 개선을 동시에 빠르게 만드는 구조임.
