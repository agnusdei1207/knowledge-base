# 📖 【암기용】 개념 완전 이해

> 목적: ISO/IEC 25010을 처음 봐도 소프트웨어 품질을 기능·성능·보안·유지보수 등 8개 특성으로 평가하는 모델로 이해하게 만든다. 시험 답안 양식이 아니라, 이해를 위한 설명이다.

## 한눈에
- **개요**: ISO/IEC 25010은 소프트웨어 **품질 특성(Quality Characteristics)**을 8개 축으로 정의한 국제 표준이며, 실무에서는 이 8개 축을 **측정 가능한 지표(Metric)와 인수 기준(Acceptance Criteria)**으로 변환해야 비로소 요구사항·테스트·릴리스 판단에 쓸 수 있다.
- **왜 필요한가**: "품질이 좋다"는 말은 검증할 수 없다. 같은 특성이라도 사람마다 기준이 달라 인수 단계에서 분쟁이 생긴다. 각 특성을 p95 응답시간, 가용성 퍼센트, 결함 밀도 같은 수치로 바꿔야 발주자와 개발자가 같은 잣대로 "통과/미통과"를 판정할 수 있다.
- **핵심 직관**: 건강검진이 "건강하다"는 말 대신 혈압 수치, 혈당 수치, 심전도 파형을 재서 정상 범위와 비교하듯, 소프트웨어 품질도 각 특성을 수치로 재서 목표값과 비교한다.

## 핵심 용어 정리 (내부에 등장하는 것들)

| 용어 | 의미 | 비유 |
|:---|:---|:---|
| 품질 특성 (Quality Characteristic) | ISO 25010이 정의한 8개 품질 축 — 측정의 대상이 되는 상위 개념 | 건강검진의 검사 항목 분류(순환기, 대사, 신경계) |
| 지표 (Metric) | 품질 특성을 실제로 잴 수 있는 숫자로 표현한 것 | 혈압계로 잰 "120/80" 수치 |
| 인수 기준 (Acceptance Criteria) | 어느 지표값 이상/이하면 통과로 인정할지 미리 합의한 목표선 | 건강검진에서 "정상 범위"로 정해둔 구간 |
| p95 응답시간 | 전체 요청 중 95%가 이 시간 안에 처리됨을 뜻하는 성능 지표 | 반 학생 중 95%가 이 시간 안에 도착한 기준선 |
| 가용성 (Availability) | 전체 운영 시간 중 정상 동작한 시간의 비율 | 한 해 동안 문을 연 날의 비율 |
| MTTR (Mean Time To Repair) | 장애 발생 후 복구까지 걸리는 평균 시간 | 고장 난 뒤 다시 고쳐 쓰기까지 걸리는 평균 시간 |
| CVE (Common Vulnerabilities and Exposures) | 공개적으로 등록·식별된 보안 취약점 항목 | 리콜 대상으로 등록된 결함 목록 번호 |
| 순환 복잡도 (Cyclomatic Complexity) | 코드 내 분기 경로의 수를 세어 코드 이해·수정 난이도를 나타내는 지표 | 길이 갈라지는 갈림길의 개수 |
| Gap 분석 | 측정값과 목표값의 차이를 찾아 무엇이 부족한지 확인하는 절차 | 목표 체중과 현재 체중의 차이를 확인하는 것 |
| Quality Gate | 지표가 목표를 만족해야만 다음 단계(빌드·배포)로 넘어가게 막는 관문 | 기준 미달이면 통과시키지 않는 검문소 |

## 깊이 이해

### 8개 특성을 왜 곧바로 쓸 수 없는가
"성능 효율성이 좋다"는 표현만으로는 테스트 담당자가 무엇을 확인해야 할지 알 수 없다. 성능 효율성이라는 특성 아래에는 시간 동작(응답 속도), 자원 활용(CPU·메모리 사용량), 용량(동시 처리 한도) 같은 세부 특성이 있고, 각 세부 특성마다 실제로 잴 수 있는 지표를 정해야 한다. 예를 들어 시간 동작은 "API 응답시간 p95 300ms 이하"로, 자원 활용은 "동시 사용자 1,000명에서 CPU 사용률 70% 이하"로 구체화해야 테스트 스크립트로 확인할 수 있다.

### 특성별 지표화 — 구체 수치 예시
- **성능 효율성**: 온라인 쇼핑몰 검색 API의 p95 응답시간을 300ms 이하로 설정한다. 부하 테스트 도구로 초당 500건 요청을 발생시켜 이 기준을 만족하는지 측정한다.
- **신뢰성**: 월 가용성 99.9%를 목표로 잡으면, 한 달(약 43,200분) 중 허용 다운타임은 약 43분이다. 99.99%로 올리면 허용 다운타임은 약 4.3분으로 줄어 인프라 이중화 비용이 크게 늘어난다.
- **보안성**: 배포 전 SAST·DAST·SCA 스캔에서 Critical·High 등급 CVE가 0건이어야 배포를 허용하는 식으로 기준을 잡는다.
- **유지보수성**: 정적 분석 도구(SonarQube 등)로 측정한 순환 복잡도를 함수당 15 이하, 코드 중복률을 5% 이하로 관리한다.

### Gap 분석 절차 — 측정에서 개선까지
1. 업무 성격에 따라 우선순위가 높은 품질 특성을 선정한다. 금융 서비스라면 보안성·신뢰성, 커머스 서비스라면 성능 효율성·가용성이 우선순위가 높다.
2. 선정한 특성마다 목표 지표값을 정한다(p95 300ms, 가용성 99.9% 등).
3. 부하 테스트, 정적 분석, 운영 로그(APM)로 실제 값을 측정한다.
4. 목표값과 측정값의 차이(Gap)를 계산한다. 예를 들어 목표 p95 300ms인데 실측이 420ms라면 40%의 gap이 발생한 것이다.
5. Gap이 있는 항목은 배포를 보류하거나, 다음 스프린트의 개선 백로그로 등록한다.

### 흔한 오해 — 특성 나열은 인수 기준이 아니다
"기능 적합성, 성능 효율성 등 8개 특성을 고려해 개발했다"고만 쓰면 계약서·감리 문서로서 아무 힘이 없다. 실제 인수 기준서에는 "요구사항 추적률 100%, Critical 결함 0건, p95 응답시간 300ms 이하, High 등급 취약점 0건"처럼 통과/미통과를 기계적으로 판정할 수 있는 숫자가 있어야 한다. ISO/IEC 25010은 이 숫자를 뽑아내기 위한 분류 체계이지, 그 자체로 테스트 케이스 목록은 아니다.

## 연결 개념
- ISO/IEC 25000 SQuaRE — 품질 요구·평가 표준군, 25010은 그중 품질 모델을 정의하는 파트
- NFR(비기능 요구사항) — 25010의 특성을 요구사항 문서의 형태로 표현한 것
- Quality Gate — 측정된 지표가 인수 기준을 만족해야 빌드·릴리스를 통과시키는 자동화 관문

# 📝 【답안용】 시험 답안 템플릿

> 목적: 시험장에서 25분에 그대로 쓰는 답안 양식. 작성방식(추상표현 금지·수치·도식·문제유형 전환)을 엄격히 지킨다.
> 핵심: ISO/IEC 25010은 품질을 추상 평가가 아니라 8개 특성과 지표로 분해해 요구사항·테스트·인수 기준을 연결하는 표준 모델이다.

## 핵심 인사이트 (3줄 요약)
> 1. **본질**: ISO/IEC 25010은 소프트웨어 제품 품질과 사용 품질을 평가하기 위한 SQuaRE 계열 품질 모델이다.
> 2. **가치**: 기능 적합성, 성능 효율성, 호환성, 사용성, 신뢰성, 보안성, 유지보수성, 이식성을 지표로 변환해 품질 게이트를 설계함.
> 3. **판단 포인트**: 품질 특성 나열보다 업무 중요도에 맞춘 가중치, 측정 방법, acceptance criteria 설정이 핵심임.

## 출제 의도 및 답안 포인트
| 출제 의도 | 반드시 짚을 핵심 | 감점 회피 포인트 |
|:---|:---|:---|
| 품질 표준 이해 확인 | ISO/IEC 25010, 제품 품질 8특성, 사용 품질 | ISO 9126과 혼동하거나 특성 누락 |
| 비기능 요구 전환 역량 확인 | p95, availability, vulnerability, maintainability 지표 | 품질을 추상 표현으로 작성 |
| 평가·인수 기준 판단 확인 | 품질 게이트, 가중치, 측정 도구 | 표준 설명만 쓰고 적용 방안 누락 |

> 요약: 이 문제는 품질 특성을 실제 측정 가능한 요구사항과 검증 기준으로 바꾸는 능력을 요구한다.

## Ⅰ. 개요 및 필요성

- 개요: SW 품질 모델 표준
- 배경: 소프트웨어 품질은 기능 구현 여부만으로 판단할 수 없고 응답시간, 장애 복구, 보안, 변경 용이성 같은 비기능 요구를 포함한다.
- 필요성: ISO/IEC 25010의 8개 품질특성으로 발주, 개발, 테스트, 감리 단계의 요구사항과 인수 조건을 같은 기준으로 관리한다.

## Ⅱ. 구조 및 구성요소

```text
Quality Requirement -> ISO/IEC 25010 Quality Model
  -> Product Quality 8 Characteristics
  -> Metrics / Acceptance Criteria
  -> Test / Review / Release Gate
```

| 구성요소 | 역할 | 특이사항 |
|:---|:---|:---|
| Functional Suitability | 기능 완전성·정확성 평가 | 요구사항 추적률, 결함률 |
| Performance Efficiency | 시간·자원·용량 평가 | p95, TPS, CPU, memory |
| Compatibility/Portability | 공존·상호운용·이식 평가 | API 호환, OS·DB 전환 |
| Reliability/Security | 장애 지속·복구·보안 통제 평가 | availability, MTTR, CVE |
| Maintainability/Usability | 변경·분석·테스트·사용 용이성 평가 | complexity, SUS, task success |

> 요약: ISO/IEC 25010은 품질 요구를 8개 특성과 측정 지표로 분해해 테스트와 릴리스 기준으로 연결한다.

```text
Stakeholder Need -> Quality Attribute Select
  -> Metric Define -> Target Set
  -> Test / Measurement -> Gap Analyze
```

| 단계 | 처리 내용 | 검증 기준 |
|:---:|:---|:---|
| 1 | 업무 특성에 맞는 품질 특성 선정 | 금융: 보안·신뢰성, 커머스: 성능·가용성 |
| 2 | 특성별 측정 지표와 목표값 설정 | p95 300ms, availability 99.9% |

| 5 | 릴리스 승인 또는 개선 계획 수립 | release gate pass, backlog 생성 |

> 요약: 품질 평가는 특성 선택, 지표 설정, 측정, gap 분석, 릴리스 판단 순서로 수행된다.

> 요약: 품질 모델 적용 리스크는 측정 지표, 가중치, 자동 수집, 인수 기준 합의로 통제한다.

| 점검 항목 | 목표 기준 | 측정 방법 |
|:---|:---|:---|

| 유지보수성 | complexity 15 이하, duplication 5% 이하 | 정적 분석 |

> 요약: ISO/IEC 25010의 성과는 품질 특성을 업무별 수치 목표와 측정 도구로 연결했는지로 판단한다.

## Ⅵ. 실무 적용 및 결론

**적용 방안 3개 (필수 — 단계별 또는 항목별):**
1. 요구사항 단계에서 8개 품질 특성을 업무 위험에 따라 상·중·하로 분류하고 상위 특성에 p95, availability, CVE 기준을 부여함.
2. CI/CD에 단위 테스트, 부하 테스트, SAST·DAST, 정적 분석을 연결해 품질 게이트를 자동화함.
3. 인수 기준서에 기능 추적률 100%, critical defect 0건, p95 300ms, high 취약점 0건 등 측정 가능한 조건을 명시함.

**결론 (2줄):**
- 기술사 판단: 공공·금융·대형 SI처럼 인수와 감리가 필요한 프로젝트는 ISO/IEC 25010 기반 품질 모델을 적용하고, 소규모 서비스는 핵심 품질 특성 중심으로 축소 적용함.
- 향후 방향: 품질 평가는 SLO, DORA, DevSecOps, Observability 지표와 결합해 운영 중 지속 측정 체계로 전환됨.
