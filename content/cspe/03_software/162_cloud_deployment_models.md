# 📖 【암기용】 개념 완전 이해

## 한눈에
- **개요**: 클라우드 인프라가 어디에 위치하고, 누가 소유하며, 누구에게 서비스되는지를 정의하는 배포 방식(퍼블릭, 프라이빗, 하이브리드, 멀티)이다.
- **왜 필요한가**: 모든 데이터를 외부에 맡길 수는 없고(보안 규제), 모든 서버를 직접 구축하기엔 비용이 크다. 데이터 중요도와 비용 효율성을 저울질해 적합한 인프라 소유/운영 형태를 선택해야 한다.
- **핵심 직관**: 퍼블릭은 공공 임대 주택(저렴, 관리 편리, 공유), 프라이빗은 자가 주택(비싸고 관리 필요, 독립적), 하이브리드는 자가 주택에 살면서 필요할 때 호텔을 빌려 쓰는 방식이다.

## 핵심 용어 정리

| 용어/표기 | 의미 | 비유·예 |
|:---|:---|:---|
| 퍼블릭 클라우드 (Public) | CSP가 자원을 여러 고객에게 공유 형태로 인터넷을 통해 제공 | "공공 임대 주택, 대중교통" (AWS, Azure) |
| 프라이빗 클라우드 (Private) | 단일 기업만을 위해 전용으로 구축·운영되는 클라우드 | "자가 주택, 개인 자가용" (OpenStack 구축 환경) |
| 하이브리드 클라우드 (Hybrid) | 프라이빗 클라우드와 퍼블릭 클라우드를 결합하여 연동하는 환경 | "평소엔 자가용, 사람 많을 땐 대절 버스 이용" |
| 멀티 클라우드 (Multi) | 2개 이상의 서로 다른 퍼블릭 클라우드(예: AWS + GCP)를 함께 사용 | "용도에 따라 여러 렌터카 회사 동시에 이용" |

## 깊이 이해
- **배경·문제의식**: 퍼블릭 클라우드의 저렴함과 확장성을 누리고 싶지만, 금융/의료 등 민감한 데이터는 규제상 외부에 둘 수 없어 통제권(프라이빗)과의 조화가 필요해짐.
- **작동 원리**: 퍼블릭은 인터넷망(공중망)을 통해 CSP의 거대 데이터센터 자원을 Multi-Tenant(다중 테넌트) 방식으로 쪼개 쓴다. 프라이빗은 기업 내부망(보안 구역)에 Single-Tenant 환경을 구축한다. 이 둘을 전용선(VPN, Direct Connect)으로 묶어 오케스트레이션하면 하이브리드가 된다.
- **비유**: 보안이 중요한 회사 핵심 문서는 자체 금고(프라이빗)에 보관하고, 대고객 홍보 웹사이트는 외부 호스팅(퍼블릭)에 올려 트래픽을 감당하는 식.
- **구체 예시**: 은행이 계좌 원장 시스템은 사내 프라이빗 클라우드에 두고, 모바일 뱅킹 앱의 대규모 이벤트 트래픽 처리는 퍼블릭 클라우드로 분산 처리(Cloud Bursting)하여 하이브리드를 구성.
- **흔한 오해·주의점**: 멀티 클라우드와 하이브리드 클라우드는 다르다. 하이브리드는 퍼블릭+프라이빗의 결합이고, 멀티는 퍼블릭+퍼블릭(또는 다수 환경)의 결합으로 종속성 회피가 주 목적이다.

## 연결 개념
- 하이브리드 클라우드(Hybrid Cloud) — 배포 모델의 실무적 진화 형태
- 멀티 클라우드 전략(Multi Cloud Strategy) — 특정 CSP 벤더 종속성(Lock-in) 회피
- 쿠버네티스(Kubernetes) — 여러 배포 모델 간 워크로드 이동성을 보장하는 핵심 기술

# 📝 【답안용】 시험 답안 템플릿

## 핵심 인사이트 (3줄 요약)

> 1. **본질**: 클라우드 배포 모델은 인프라의 소유권, 위치, 테넌트(Tenant) 구성 방식에 따라 퍼블릭, 프라이빗, 하이브리드, 커뮤니티(멀티)로 구분된다.
> 2. **가치**: 보안 규제 준수(프라이빗)와 탄력적 리소스 확장(퍼블릭)이라는 상충되는 요구사항을 워크로드 특성에 맞게 분리하여 최적화할 수 있다.
> 3. **판단 포인트**: 도입 시 데이터 민감도, 초기 구축 비용, 특정 CSP 종속성(Lock-in) 위험을 종합적으로 평가하여 단일 모델 또는 하이브리드/멀티 모델을 결정해야 한다.

## 출제 의도 및 답안 포인트

| 출제 의도 | 반드시 짚을 핵심 | 감점 회피 포인트 |
|:---|:---|:---|
| 각 배포 모델의 개념과 차이 파악 | 인프라 소유권, 테넌트 공유 여부, 보안 통제 수준 | 단순 정의 나열에 그침 |
| 비즈니스 목적에 맞는 배포 전략 수립 | 하이브리드(보안+확장) 및 멀티 클라우드(종속성 회피) 선택 기준 | 멀티와 하이브리드의 개념 혼용 |
| 하이브리드/멀티 환경의 운영 리스크 인지 | 복잡성 증가, 데이터 통합 어려움, 단일 가시성 확보 필요 | 장점만 나열하고 복잡성 리스크 누락 |

> 요약: 워크로드의 보안 민감도와 자원 수요 패턴에 따라 퍼블릭과 프라이빗의 장점을 결합하는 하이브리드/멀티 전략과 그에 따른 통합 운영 방안을 제시해야 한다.

## Ⅰ. 개요 및 필요성

- 개요: 클라우드 배포 모델은 서비스 대상과 자원의 소유/운영 주체에 따라 퍼블릭, 프라이빗, 하이브리드 등으로 구분되는 인프라 아키텍처 전략
- 배경: 퍼블릭 클라우드는 확장이 쉽지만 보안/규제 문제가 있고, 프라이빗 클라우드는 보안성은 높으나 구축 비용과 유연성 한계가 존재
- 필요성: 데이터 보안 컴플라이언스를 준수하면서도 대규모 트래픽 변동에 유연하게 대응하기 위해, 모델 간 장점을 취합하는 전략적 선택 필요

---

## Ⅱ. 구조 및 구성요소

```text
[ Private Cloud ] <--- VPN / Direct Connect ---> [ Public Cloud ]
- Single Tenant                                 - Multi Tenant
- High Security / On-Premise                    - High Scalability / Off-Premise
- Core Data / Legacy                            - Web Front / Burst Traffic
        \                                            /
         +-------> [ Hybrid / Multi Cloud Management ]
```

| 구성요소 | 역할 | 특이사항 |
|:---|:---|:---|
| 퍼블릭 클라우드 (Public) | 외부 CSP가 인프라를 구축하고 다수 사용자(Multi-Tenant)에게 서비스 | 자원 탄력성 극대화, 종량제 (예: AWS, Azure) |
| 프라이빗 클라우드 (Private) | 단일 기업(Single-Tenant)이 전용으로 방화벽 내부에 인프라 구축·운영 | 보안 통제 및 규제 준수 용이 (예: OpenStack, VMware) |
| 하이브리드 클라우드 (Hybrid) | 프라이빗과 퍼블릭을 전용 네트워크로 연동하여 워크로드 분산 | 핵심 자산은 프라이빗, 트래픽 폭주 시 퍼블릭 활용 |
| 커뮤니티 클라우드 (Community) | 공동의 목적(규제, 보안)을 가진 여러 조직이 인프라를 공유 | 공공기관, 특정 산업군(금융) 전용 클라우드 |

> 요약: 배포 모델은 테넌트 공유 수준과 인프라 소유 방식에 따라 나뉘며, 현대 아키텍처는 이를 결합하는 하이브리드 및 멀티 클라우드로 진화하고 있다.

---

## Ⅲ. 동작원리 및 흐름도

```text
워크로드 분석 -> 민감도/트래픽 평가 -> 배포 모델 분배
-> [Core: Private 배치] / [Front: Public 배치] -> 전용선 연동 및 통합 모니터링
```

- 1단계 [워크로드 분석]: 데이터 민감도, 규제 요건, 트래픽 변동성, SLA 요구사항 식별
- 2단계 [배포 모델 분배]: 보안이 중요한 DB/코어는 Private, 트래픽 유동성이 큰 웹/채널은 Public 할당
- 3단계 [네트워크 연동]: IPSec VPN, 전용선(Direct Connect)을 통해 이종 클라우드 간 안전한 통신 확보
- 4단계 [통합 운영]: 통합 관리 플랫폼(CMP)을 통해 복수 환경의 리소스 프로비저닝 및 모니터링 일원화

> 요약: 애플리케이션 특성을 분석하여 적재적소에 배포 모델을 매핑하고, 안전한 네트워크 연동과 CMP를 통한 통합 관리를 수행한다.

---

## Ⅳ. 특징

- 비용 구조의 차이: 퍼블릭은 OPEX(운영비) 중심, 프라이빗은 CAPEX(자본비) 중심의 재무 구조를 가짐
- 보안 및 통제: 프라이빗은 물리적 레벨의 강력한 통제력을 제공하며, 퍼블릭은 논리적 격리(VPC)를 통한 보안 제공
- 확장성(Scalability): 퍼블릭은 무한에 가까운 자원 확장이 가능하나, 프라이빗은 보유한 하드웨어 용량 한계 내에서만 확장 가능
- 상호 운용성 과제: 하이브리드/멀티 환경 구성 시 이종 플랫폼 간의 데이터 정합성 유지 및 API 호환성 확보가 필수적임

## Ⅴ. 심화 비교 및 적용 판단

| 비교 축 | 퍼블릭 클라우드 | 프라이빗 클라우드 | 하이브리드 클라우드 |
|:---|:---|:---|:---|
| 자원 공유 | Multi-Tenant (다중) | Single-Tenant (단일) | 혼합 (자원 동적 분배) |
| 보안 및 통제력 | CSP 의존 (논리적 통제) | 기업 직접 통제 (물리적) | 워크로드별 선택적 적용 |
| 도입 비용 구조 | Pay-as-you-go (OPEX) | 초기 구축 비용 큼 (CAPEX) | 인프라 투자 + 구독료 혼합 |
| 주요 적용 대상 | 스타트업, 비핵심 업무 | 금융/공공 핵심 DB | 엔터프라이즈 통합 워크로드 |

> 요약: 신속한 서비스 출시는 퍼블릭, 보안 규제 컴플라이언스는 프라이빗, 이 둘의 균형과 Cloud Bursting이 필요하면 하이브리드를 선택한다.

**리스크·대응:**
- 사일로(Silo)화 및 운영 복잡성: 여러 환경이 분리되어 관리 포인트 증가 → CMP(Cloud Management Platform) 및 IaC 툴(Terraform) 도입으로 프로비저닝 일원화 (지표: 인프라 배포 리드타임)
- 벤더 종속성(Vendor Lock-in): 단일 퍼블릭 CSP의 기술에 깊게 결합됨 → 쿠버네티스(K8s) 컨테이너 기반 아키텍처로 이식성(Portability) 확보 (지표: CSP 마이그레이션 테스트 성공률)

**도입 후 점검 지표:**
- 통합 가시성: 하이브리드 환경 간 네트워크 지연(Latency) 10ms 이하 유지 — 네트워크 모니터링
- 보안 컴플라이언스: 프라이빗-퍼블릭 간 데이터 전송 시 End-to-End 암호화 적용 비율 100% — 보안 취약점 진단

## Ⅵ. 실무 적용 및 결론

**적용 방안 3개:**
1. 클라우드 버스팅(Cloud Bursting): 평소에는 온프레미스(Private)에서 워크로드를 처리하고, 이벤트 트래픽 폭주 시 퍼블릭 자원을 동적으로 할당받아 처리
2. 재해 복구(DR) 연동: 메인 센터는 프라이빗 클라우드로 운영하고, 원격지 DR 센터는 퍼블릭 클라우드를 활용해 낮은 RPO/RTO와 비용 절감 동시 달성
3. 컨테이너 기반 이식성 확보: 애플리케이션을 Docker/Kubernetes 기반으로 패키징하여, Private과 Public 간 제약 없는 워크로드 이동(Migration) 실현

**결론 (2줄):**
- 기술사 판단: 단일 배포 모델만으로는 현대 엔터프라이즈의 복잡한 요구사항을 맞출 수 없으므로, 데이터 중요도와 비용 효율성에 기반한 하이브리드/멀티 클라우드 채택이 필수적이다.
- 향후 방향: 배포 환경의 차이를 사용자(개발자)로부터 완전히 추상화하는 클라우드 네이티브 플랫폼(예: Anthos, Azure Arc)을 통한 단일 제어 평면(Control Plane) 관리가 주류가 될 것이다.
