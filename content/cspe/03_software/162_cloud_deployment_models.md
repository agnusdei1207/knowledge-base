# 📖 【암기용】 개념 완전 이해

> 목적: 클라우드 배포 모델을 처음 봐도 완벽히 이해하게 만든다. 시험 답안 양식이 아니라, 이해를 위한 친절한 설명이다.

## 한눈에
- **개요**: 클라우드 자원을 어디에 두고 누구와 공유하는지 정하는 배치 방식
- **왜 필요한가**: 같은 SaaS·PaaS·IaaS라도 공용 리전, 전용 센터, 내부 센터, 여러 사업자 조합에 따라 규제와 운영 방식이 달라진다.
- **핵심 직관**: 서비스 모델이 "무엇을 빌리는가"라면 배포 모델은 "어디에 놓고 누구와 쓰는가"를 정한다.

## 깊이 이해
- **배경·문제의식**: 모든 업무를 퍼블릭 클라우드로 옮기면 민첩성은 확보되지만 데이터 주권, 지연시간, 레거시 연계 문제가 생긴다. 반대로 프라이빗만 쓰면 탄력 용량과 글로벌 리전 활용에 제약이 있다.
- **작동 원리**: 퍼블릭은 CSP 공유 인프라를 사용하고, 프라이빗은 조직 전용 환경을 구축한다. 하이브리드는 온프레미스와 퍼블릭을 연결하고, 멀티 클라우드는 두 개 이상 CSP를 목적별로 병행한다.
- **비유**: 퍼블릭은 공유 오피스, 프라이빗은 전용 사옥, 하이브리드는 본사와 공유 오피스 연결, 멀티는 여러 지역의 다른 공유 오피스 계약이다.
- **구체 예시**: 핵심 DB는 프라이빗에 두고 웹 프론트는 퍼블릭에 배치, 재해복구는 다른 CSP 리전에 구성하면 하이브리드와 멀티 클라우드가 결합된다.
- **흔한 오해·주의점**: 멀티 클라우드는 자동으로 장애 대응이 되는 구조가 아니다. DNS, 데이터 복제, IAM, 네트워크 라우팅을 설계하지 않으면 단일 CSP 장애와 같은 영향이 남는다.

## 연결 개념
- 클라우드 서비스 모델 - 배포 모델 위에서 IaaS·PaaS·SaaS를 선택
- 하이브리드 클라우드 - 온프레미스와 퍼블릭 연결 모델
- 멀티 클라우드 전략 - 여러 CSP를 목적별로 병행하는 운영 전략

> 핵심: 퍼블릭·프라이빗·하이브리드·멀티를 장소 기준으로만 쓰지 말고 규제, 지연시간, 가용성, 비용, 운영 역량 기준으로 선택한다.

## 핵심 인사이트 (3줄 요약)

> 1. **본질**: 클라우드 배포 모델은 클라우드 자원의 소유·공유·위치·연결 방식을 구분하는 아키텍처 선택 기준이다.
> 2. **가치**: 업무 특성에 따라 공용 리전, 전용 환경, 온프레미스 연계, 다중 CSP를 조합해 규제와 운영 목표를 맞춘다.
> 3. **판단 포인트**: 데이터 민감도, 지연시간, DR 목표, 벤더 종속 위험, 운영 인력 수준이 모델 선택의 기준이다.

## Ⅰ. 개요 및 필요성

클라우드 배포 모델은 클라우드 자원의 위치와 공유 방식을 정하는 구조이다. 기업은 민감 데이터, 레거시 연계, 글로벌 서비스, 재해복구 요구를 동시에 만족해야 한다. 따라서 배포 모델은 기술 선택이 아니라 규제·비용·운영 책임을 반영한 아키텍처 결정이다.

---

## Ⅱ. 구조 및 구성요소

```text
Workload Requirement -> Public Cloud / Private Cloud
                     -> Hybrid 연결
                     -> Multi Cloud 분산
                     +-> IAM/Network/Observability 통합
```

| 구성요소 | 역할 | 특이사항 |
|:---|:---|:---|
| Public Cloud | CSP 공용 리전의 자원 사용 | 탄력 용량, 글로벌 리전 |
| Private Cloud | 조직 전용 인프라 제공 | 규제·망분리·전용 통제 |
| Hybrid Cloud | 온프레미스와 퍼블릭 연계 | VPN, Direct Connect, 전용 회선 |
| Multi Cloud | 두 개 이상 CSP 병행 | 종속 완화, 운영 복잡도 증가 |

> 요약: 배포 모델은 공용·전용·연계·다중 CSP 조합이며, 통합 IAM과 네트워크 설계가 전제다.

---

## Ⅲ. 동작원리 및 흐름도

```text
업무 분류 -> 데이터 민감도/지연시간 평가 -> 배포 모델 선택
-> 네트워크/IAM/로그 통합 -> 배포 -> SLA/RTO/RPO 점검
```

| 단계 | 처리 내용 | 검증 기준 |
|:---:|:---|:---|
| 1 | 업무와 데이터 등급 분류 | 개인정보, 금융, 내부 등급 |
| 2 | 배포 후보 모델 비교 | 리전, 전용성, 지연시간, 비용 |
| 3 | 연결·보안 설계 | VPN, 전용 회선, IAM federation |
| 4 | 운영 지표 검증 | SLA 99.9%, RTO/RPO, 로그 수집률 |

> 요약: 배포 모델은 업무 분류, 위치 결정, 연결 통제, 운영 지표 검증 순서로 확정한다.

## Ⅳ. 특징

| 구분 | 기존 단일 데이터센터 | 클라우드 배포 모델 | 수치·판단 포인트 |
|:---|:---|:---|:---|
| 용량 | 구매 용량 고정 | 퍼블릭 리전 탄력 용량 | 피크 대비 30% 버퍼 축소 |
| 규제 | 내부 통제로 대응 | 프라이빗·소버린 리전 선택 | 데이터 위치 요구 충족 |
| 장애 대응 | 단일 DR 센터 중심 | 다중 AZ·다중 리전·다중 CSP | RTO 1시간, RPO 15분 목표 |
| 운영 | 단일 도구 | CSP별 도구와 통합 관측성 | 로그 수집률 95% 이상 |

> 요약: 배포 모델 선택은 용량 탄력성, 데이터 위치, DR 목표, 운영 통합 수준의 균형이다.

## Ⅴ. 심화 비교 및 적용 판단

| 비교 축 | 퍼블릭/프라이빗 | 하이브리드 | 멀티 |
|:---|:---|:---|:---|
| 선택 조건 | 단일 환경으로 요구 충족 | 레거시·민감 데이터와 퍼블릭 연계 | 벤더 종속 완화, CSP별 서비스 활용 |
| 비용 구조 | 단일 과금 또는 전용 투자 | 회선·동기화 비용 추가 | 중복 운영·교육 비용 추가 |
| 운영 위험 | 단일 장애 도메인 | 연결 장애와 데이터 정합성 | 정책 불일치와 관측성 분산 |

> 요약: 하이브리드는 연결 품질, 멀티는 운영 표준화 역량이 선택 조건이다.

| 리스크 | 원인 | 대응 방안 | 확인 지표 |
|:---|:---|:---|:---|
| 지연시간 증가 | 온프레미스와 리전 거리 | 전용 회선, 캐시, 지역 리전 선택 | p95 지연 100ms 이하 |
| 정책 불일치 | CSP별 IAM·네트워크 정책 차이 | 정책 코드화, 표준 태그, landing zone | 정책 위반 0건 |
| 비용 중복 | 다중 회선, 중복 라이선스 | FinOps 예산, 리소스 통합 점검 | 월 예산 편차 10% 이하 |

> 요약: 배포 모델 리스크는 네트워크 지연, 정책 편차, 중복 비용이며 표준화와 지표로 통제한다.

| 점검 항목 | 목표 기준 | 측정 방법 |
|:---|:---|:---|
| 가용성 | SLA 99.9% 이상, RTO/RPO 충족 | 장애 훈련, DR 리포트 |
| 네트워크 | p95 지연 100ms 이하, 패킷 손실 0.1% 이하 | APM, synthetic test |
| 거버넌스 | 태그·IAM·로그 적용률 95% 이상 | CSPM, SIEM, Billing Export |

> 요약: 배포 모델의 유효성은 가용성, 네트워크 품질, 거버넌스 적용률로 판정한다.

## Ⅵ. 실무 적용 및 결론

**적용 방안 3개 (필수 - 단계별 또는 항목별):**
1. 업무 배치 원칙 수립: 민감 DB는 프라이빗, 대외 채널은 퍼블릭, 레거시 연계는 하이브리드, DR은 다중 리전으로 분리
2. 공통 통제 구축: IAM federation, 표준 태그, 중앙 로그, KMS 정책을 배포 모델과 무관하게 적용
3. 운영 검증: DR 훈련 반기 1회, p95 지연 100ms 이하, 태그 적용률 95% 이상을 배포 승인 조건으로 설정

**결론 (2줄):**
- 기술사 판단: 규제와 지연시간이 지배하면 프라이빗/하이브리드, 종속 완화와 서비스 선택 폭이 목표면 멀티를 선택함
- 향후 방향: 배포 모델은 소버린 클라우드, 엣지, 쿠버네티스 기반 공통 제어면과 결합해 운영 표준화가 과제로 확대됨
