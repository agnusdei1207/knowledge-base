# 📖 【암기용】 개념 완전 이해

> 목적: 클라우드 배포 모델을 처음 봐도 완벽히 이해하게 만든다. 시험 답안 양식이 아니라, 이해를 위한 친절한 설명이다.

## 한눈에
- **개요**: **클라우드 아키텍처**에서 자원을 물리적으로 어디에 두고 누구와 공유하는지를 정하는 **배포 모델**(Deployment Model) — 퍼블릭·프라이빗·하이브리드·멀티 클라우드
- **왜 필요한가**: 같은 IaaS·PaaS·SaaS라도 공용 리전에 둘지, 전용 센터에 둘지, 온프레미스와 연결할지, 여러 사업자를 조합할지에 따라 규제 준수·지연시간·장애 범위가 완전히 달라진다.
- **핵심 직관**: 서비스 모델(161)이 "무엇을 빌리는가"를 정한다면, 배포 모델은 "그것을 어디에 놓고 누구와 함께 쓰는가"를 정한다.

## 핵심 용어 정리 (내부에 등장하는 것들)

| 용어 | 의미 | 비유 |
|:---|:---|:---|
| 클라우드 아키텍처 | 클라우드 자원을 어떻게 조달·배치·연결할지 설계하는 상위 개념 | 회사의 부동산 전략 전체 |
| 클라우드 배포 모델 | 그중 자원을 물리적으로 어디에 두고 누구와 공유할지 정하는 배치 방식 | 사무 공간을 공유오피스로 할지 전용 사옥으로 할지 |
| Public Cloud | CSP가 여러 고객과 함께 쓰는 공용 리전 자원 | 공유 오피스 |
| Private Cloud | 한 조직 전용으로 구축된 인프라 | 전용 사옥 |
| Hybrid Cloud | 온프레미스와 퍼블릭을 네트워크로 연결해 함께 운용 | 본사와 공유오피스 지점을 전용선으로 연결 |
| Multi-Cloud | 2개 이상의 CSP를 목적별로 병행 사용 | 여러 지역에 각각 다른 공유오피스 계약 |
| 데이터 주권 (Data Sovereignty) | 특정 국가·지역 법에 따라 데이터가 물리적으로 그 지역에 있어야 하는 요건 | 국내법상 원본 문서는 국내 보관 의무 |
| RTO / RPO | 재해 발생 시 복구 목표 시간 / 복구 목표 시점(허용 가능한 데이터 손실 범위) | "정전 후 몇 시간 내 복구" / "몇 분치 데이터까지는 잃어도 됨" |
| Direct Connect / VPN | 온프레미스와 클라우드를 잇는 전용회선 / 암호화 터널 | 전용 도로 / 임시로 뚫은 지하 통로 |

## 깊이 이해

### 서비스 모델과 배포 모델을 헷갈리지 않기
- 161의 IaaS/PaaS/SaaS는 "빌리는 대상의 층위"이고, 여기 배포 모델은 "그 층위를 어디에 배치하는가"다. 예를 들어 "프라이빗 클라우드에 PaaS를 구축"하는 것도 가능하다 — 두 축은 독립적으로 조합된다.

### 왜 필요한가 — 퍼블릭 올인과 프라이빗 올인의 함정 (배경)
- 모든 업무를 퍼블릭으로 옮기면 배포 민첩성은 오르지만, 데이터 주권(예: 금융 데이터는 국내 보관 의무)이나 온프레미스 레거시 연계, 리전 간 지연시간 문제가 남는다. 반대로 프라이빗만 쓰면 트래픽 급증 시 탄력적으로 서버를 늘리기 어렵고 글로벌 리전을 활용할 수 없다. 그래서 실무는 대개 두 방식을 조합한다.

### 하이브리드·멀티를 수치로 조합하기 (worked example)
- 핵심 주문 DB는 데이터 주권 요건 때문에 **프라이빗**에 두고, 웹 프론트는 트래픽 변동이 크므로 **퍼블릭**(주 리전)에 배치하고, 재해복구는 **다른 CSP의 리전**에 구성한다고 하자.
- 프라이빗-퍼블릭 연결에는 Direct Connect로 **p95 지연 100ms 이하**를 목표하고, DR 사이트는 **RTO 1시간, RPO 15분**(최대 15분치 데이터만 유실 허용)을 기준으로 삼는다. 이것이 하이브리드(온프레미스+퍼블릭)와 멀티(2개 CSP)가 한 아키텍처에 동시에 나타나는 예다.

### 판별 원리 — 어떤 배포 모델을 선택하나
- **데이터 민감도**가 높고 규제가 엄격하면 → 프라이빗(또는 소버린 리전). **탄력적 확장**과 글로벌 서비스가 목표면 → 퍼블릭. **레거시와 신규 시스템 공존**이 필요하면 → 하이브리드. **벤더 종속 회피**와 CSP별 강점 활용이 목표면 → 멀티.

### 흔한 오해
- 멀티 클라우드를 쓰면 한 CSP가 장애 나도 다른 CSP가 자동으로 받아준다고 착각하기 쉽다. 실제로는 DNS 페일오버, 데이터 실시간 복제, IAM 연동(federation), 네트워크 라우팅을 별도로 설계하지 않으면, 두 CSP를 쓰더라도 실질적으로는 단일 CSP 장애와 같은 영향을 받는다 — 설계가 없으면 비용만 두 배로 드는 구조다.

## 연결 개념
- 클라우드 서비스 모델 — 배포 모델 위에서 IaaS·PaaS·SaaS를 선택하는 별개의 축(161)
- 하이브리드 클라우드 — 온프레미스-퍼블릭 연결의 세부 구현
- 멀티 클라우드 전략 — 여러 CSP를 목적별로 병행하는 운영 전략

## Ⅰ. 개요 및 필요성

- 개요: 클라우드 배포 모델은 자원 위치와 공유 방식 구조임.
- 배경: 기업은 민감 데이터, 레거시 연계, 글로벌 서비스, 재해복구 요구를 동시에 만족해야 한다.
- 필요성: 규제, 비용, 운영 책임 기준으로 Public, Private, Hybrid, Community 모델을 선택한다.

## Ⅱ. 구조 및 구성요소

```text
Workload Requirement -> Public Cloud / Private Cloud
                     -> Hybrid 연결
                     -> Multi Cloud 분산
                     +-> IAM/Network/Observability 통합
```

| 구성요소 | 역할 | 특이사항 |
|:---|:---|:---|
| Public Cloud | CSP 공용 리전의 자원 사용 | 탄력 용량, 글로벌 리전 |
| Private Cloud | 조직 전용 인프라 제공 | 규제·망분리·전용 통제 |
| Hybrid Cloud | 온프레미스와 퍼블릭 연계 | VPN, Direct Connect, 전용 회선 |
| Multi Cloud | 두 개 이상 CSP 병행 | 종속 완화, 운영 복잡도 증가 |

> 요약: 배포 모델은 공용·전용·연계·다중 CSP 조합이며, 통합 IAM과 네트워크 설계가 전제다.

## Ⅲ. 동작원리 및 흐름도

```text
업무 분류 -> 데이터 민감도/지연시간 평가 -> 배포 모델 선택
-> 네트워크/IAM/로그 통합 -> 배포 -> SLA/RTO/RPO 점검
```

| 단계 | 처리 내용 | 검증 기준 |
|:---:|:---|:---|
| 1 | 업무와 데이터 등급 분류 | 개인정보, 금융, 내부 등급 |
| 2 | 배포 후보 모델 비교 | 리전, 전용성, 지연시간, 비용 |
| 3 | 연결·보안 설계 | VPN, 전용 회선, IAM federation |
| 4 | 운영 지표 검증 | SLA 99.9%, RTO/RPO, 로그 수집률 |

> 요약: 배포 모델은 업무 분류, 위치 결정, 연결 통제, 운영 지표 검증 순서로 확정한다.

| 운영 위험 | 단일 장애 도메인 | 연결 장애와 데이터 정합성 | 정책 불일치와 관측성 분산 |

> 요약: 하이브리드는 연결 품질, 멀티는 운영 표준화 역량이 선택 조건이다.

| 비용 중복 | 다중 회선, 중복 라이선스 | FinOps 예산, 리소스 통합 점검 | 월 예산 편차 10% 이하 |

> 요약: 배포 모델 리스크는 네트워크 지연, 정책 편차, 중복 비용이며 표준화와 지표로 통제한다.

|:---|:---|:---|
| 가용성 | SLA 99.9% 이상, RTO/RPO 충족 | 장애 훈련, DR 리포트 |
| 네트워크 | p95 지연 100ms 이하, 패킷 손실 0.1% 이하 | APM, synthetic test |
| 거버넌스 | 태그·IAM·로그 적용률 95% 이상 | CSPM, SIEM, Billing Export |

> 요약: 배포 모델의 유효성은 가용성, 네트워크 품질, 거버넌스 적용률로 판정한다.

## Ⅵ. 실무 적용 및 결론

**적용 방안 3개 (필수 - 단계별 또는 항목별):**
1. 업무 배치 원칙 수립: 민감 DB는 프라이빗, 대외 채널은 퍼블릭, 레거시 연계는 하이브리드, DR은 다중 리전으로 분리
2. 공통 통제 구축: IAM federation, 표준 태그, 중앙 로그, KMS 정책을 배포 모델과 무관하게 적용
3. 운영 검증: DR 훈련 반기 1회, p95 지연 100ms 이하, 태그 적용률 95% 이상을 배포 승인 조건으로 설정

**결론 (2줄):**
- 기술사 판단: 규제와 지연시간이 지배하면 프라이빗/하이브리드, 종속 완화와 서비스 선택 폭이 목표면 멀티를 선택함
- 향후 방향: 배포 모델은 소버린 클라우드, 엣지, 쿠버네티스 기반 공통 제어면과 결합해 운영 표준화가 과제로 확대됨
