# 📖 【암기용】 개념 완전 이해

## 한눈에
- **개요**: 데이터를 2차원 표(Table/Relation) 형태로 표현하고, 데이터 간의 관계를 기본키(PK)와 외래키(FK)로 연결하는 데이터베이스 모델
- **왜 필요한가**: 데이터를 단순히 파일에 나열하면 중복이 생기고 일관성이 깨진다. 데이터를 수학적 집합(Relation)과 무결성 규칙(제약조건)으로 강력하게 통제하기 위해 탄생했다.
- **핵심 직관**: 엑셀 시트(표) 여러 장을 펴놓고, "회원 시트의 학번"과 "성적 시트의 학번"을 고리로 연결해(Join) 데이터를 정확하게 관리하는 것.

## 핵심 용어 정리

| 용어/표기 | 의미 | 비유·예 |
|:---|:---|:---|
| 릴레이션 (Relation) | 데이터를 행(Row)과 열(Column)로 구성한 2차원 테이블 | 엑셀 시트 1장 |
| 튜플 (Tuple) | 릴레이션의 하나의 행 (레코드) | 학생 1명의 전체 정보 줄 |
| 속성 (Attribute) | 릴레이션의 열 (컬럼/필드) | '이름', '학번' 같은 헤더 |
| 차수 (Degree) | 속성의 총 개수 (열의 수) | 엑셀 열이 5개면 차수 5 |
| 카디널리티 (Cardinality) | 튜플의 총 개수 (행의 수) | 학생이 100명이면 카디널리티 100 |

## 깊이 이해
- **배경·문제의식**: 과거 계층형/망형 DB는 구조가 너무 복잡해 데이터 접근 경로를 프로그래머가 일일이 알아야 했다. 1970년 E.F. Codd가 "수학적 집합론"에 기반해 데이터를 표 형태로 추상화하고, SQL이라는 언어로 선언적 조회를 제안함.
- **키(Key)의 원리**: 데이터를 유일하게 식별하고 테이블을 연결하는 고리.
  - **슈퍼키**: 유일성은 만족 (예: 학번+이름)
  - **후보키**: 유일성 + 최소성 만족 (예: 학번, 주민번호)
  - **기본키(PK)**: 후보키 중 선택된 짱. (NULL 불가)
  - **외래키(FK)**: 다른 테이블의 기본키를 참조. (테이블 간의 연결 고리)
- **제약조건 (무결성)**: 데이터에 쓰레기값이 안 들어가게 막는 거름망.
  - **개체 무결성**: 기본키는 NULL이나 중복값을 가질 수 없다. (학번 없는 학생은 존재할 수 없음)
  - **참조 무결성**: 외래키는 참조하는 테이블의 기본키에 존재하는 값만 가져야 한다. (없는 학과 코드를 학생이 가질 수 없음)
- **흔한 오해·주의점**: "RDBMS는 무조건 느리다?" 아니다. 조인이 많아지면 스케일아웃(서버 분산)이 어려워 빅데이터 처리에 불리할 뿐, 트랜잭션의 정확성(ACID)과 복잡한 조건 조회에는 여전히 최강자이다.

## 연결 개념
- **정규화 (Normalization)**: 릴레이션의 중복을 없애고 쪼개는 과정 (100 키워드)
- **트랜잭션 ACID**: RDBMS가 신뢰성을 보장하는 핵심 메커니즘 (095 키워드)

# 📝 【답안용】 시험 답안 템플릿

## 핵심 인사이트 (3줄 요약)

> 1. **본질**: 관계형 데이터베이스(RDB)는 2차원 릴레이션(Relation)을 기반으로 데이터를 표현하고 키(Key)를 통해 개체 간의 관계를 맺는 수학적 데이터 모델이다.
> 2. **가치**: 개체 무결성, 참조 무결성 등 엄격한 제약조건을 통해 데이터의 정합성과 일관성을 무결하게 유지한다.
> 3. **판단 포인트**: 데이터의 강한 정합성과 복잡한 조인이 필요할 때는 RDBMS를, 유연한 스키마와 대규모 수평 확장이 필요할 때는 NoSQL을 선택해야 한다.

## 출제 의도 및 답안 포인트

| 출제 의도 | 반드시 짚을 핵심 | 감점 회피 포인트 |
|:---|:---|:---|
| 관계형 데이터 모델의 수학적/논리적 구조 이해 | 릴레이션, 튜플, 속성, 차수, 카디널리티 용어 | 용어(개념)와 물리적 구현(테이블/로우)의 혼동 |
| 데이터 무결성을 보장하는 핵심 메커니즘 설명 | 기본키(PK), 외래키(FK), 무결성 제약조건(개체/참조) | 키의 종류(후보, 기본, 외래) 누락 |

> 요약: RDB 모델은 릴레이션 구조와 무결성을 보장하는 키(Key) 및 제약조건 메커니즘이 핵심이다.

---

## Ⅰ. 개요 및 필요성

- 개요: 관계형 데이터베이스(RDB)는 집합론과 술어 논리에 기반하여 데이터를 2차원 테이블(릴레이션) 형태로 추상화한 데이터 모델임
- 배경: 파일 시스템과 계층형/망형 데이터베이스의 종속성과 중복성, 복잡한 접근 경로 문제를 해결하기 위해 등장 (E.F. Codd)
- 필요성: 엔터프라이즈 환경에서 데이터의 논리적/물리적 독립성을 보장하고, 엄격한 무결성 규칙을 통해 데이터 정합성을 유지하기 위해 필수적임

---

## Ⅱ. 구조 및 구성요소

```text
Database
  -> Relation (Table)
       -> Attribute (열/차수), Tuple (행/카디널리티), Domain (값의 범위)
  -> Key (슈퍼/후보/기본/외래키)
  -> Integrity Constraint (개체/참조/도메인 무결성)
```

| 구성요소 | 역할 | 물리적 대응 |
|:---|:---|:---|
| Relation (릴레이션) | 데이터 개체와 관계를 표현하는 2차원 구조 | Table (테이블) |
| Tuple (튜플) | 릴레이션에 속한 데이터의 단일 인스턴스 | Row, Record (행) |
| Attribute (속성) | 릴레이션의 특징을 나타내는 성질 | Column, Field (열) |
| Domain (도메인) | 하나의 속성이 가질 수 있는 원자값들의 집합 | Data Type, 제약 (예: 성별 M/F) |

> 요약: 논리적 모델인 릴레이션은 속성(열)과 튜플(행)로 구성되며, 물리적 테이블 구조로 매핑된다.

---

## Ⅲ. 키(Key)와 무결성 제약조건

```text
Relation A (기본키 PK 정의) -> [참조 무결성 검증] <- Relation B (외래키 FK 정의)
       | (개체 무결성: NULL 불가, 중복 불가)
```

- 1단계 [키(Key) 체계]: 
  - 후보키(유일성+최소성 만족) 중 데이터 식별을 위한 **기본키(Primary Key)** 선정
  - 다른 릴레이션을 참조하기 위한 **외래키(Foreign Key)** 설정
- 2단계 [개체 무결성]: 기본키를 구성하는 어떤 속성도 NULL 값이나 중복값을 가질 수 없음 보장
- 3단계 [참조 무결성]: 외래키 값은 참조하는 릴레이션의 기본키 값과 일치하거나 NULL이어야 함 보장 (고아 레코드 방지)
- 4단계 [도메인 무결성]: 속성값이 정의된 도메인(타입, 범위)에 속한 원자값이어야 함 보장

> 요약: RDB는 기본키로 개체 무결성을, 외래키로 참조 무결성을 통제하여 데이터의 쓰레기값 유입을 원천 차단한다.

---

## Ⅳ. 특징

- 정합성 강제: 엄격한 스키마(Schema)와 무결성 제약조건을 통해 데이터 불일치 및 이상(Anomaly) 방지
- 독립성 보장: 뷰(View)를 통한 논리적 독립성, 저장 구조 변경에 따른 물리적 독립성 제공
- 비절차적 질의: SQL을 사용하여 '어떻게(How)'가 아닌 '무엇을(What)' 조회할지 선언적으로 접근
- 스케일업(Scale-Up) 한계: 스키마와 조인 제약으로 인해 서버를 수평 분산(Sharding)하기 까다로워 대용량 분산 확장에 제약 존재

## Ⅴ. 심화 비교 및 적용 판단

| 비교 축 | RDBMS (관계형) | NoSQL (비관계형) | 선택 기준 |
|:---|:---|:---|:---|
| 데이터 구조 | 정형 스키마, 2차원 테이블 | 비정형/반정형 (Document, Key-Value) | 데이터 유연성 |
| 정합성 | 강력한 ACID, 무결성 제약 | 최종 일관성 (Eventual Consistency), BASE | 트랜잭션 신뢰도 |
| 확장성 | 스케일업(Scale-Up) 중심 | 스케일아웃(Scale-Out) 중심 수평 확장 | 데이터 볼륨/분산 |

> 요약: 금융/결제 등 엄격한 정합성이 필요하면 RDBMS를, 로그/SNS 등 대규모 수평 확장이 필요하면 NoSQL을 선택한다.

**리스크·대응 (기본은 불릿):**
- 조인(Join) 성능 저하: 다수 테이블 조인 시 카테시안 곱으로 인한 성능 폭락 → 적절한 인덱스 설계 및 필요한 경우 반정규화(Denormalization) 수행
- 스키마 변경 경직성: 운영 중 컬럼 추가/삭제 시 서비스 락(Lock) 발생 리스크 → Online DDL 도구 사용 및 배포 파이프라인 자동화

---

## Ⅵ. 실무 적용 및 결론

**적용 방안 3개:**
1. 논리 모델링 설계: ERD 작성 시 정규화 원칙(3NF 이상)을 준수하여 중복 데이터 배제 및 무결성 확보
2. 제약조건 DB 위임: 비즈니스 로직(Application)단에서만 검증하지 않고, DB 스키마 레벨에 PK, FK, Unique, Check 제약을 강력하게 설정
3. 성능 최적화: 자주 조인되는 속성이나 조건절에 쓰이는 속성에 B-Tree / 복합 인덱스를 구성하여 I/O 성능 향상

**결론 (2줄):**
- 기술사 판단: 최근 NoSQL이나 NewSQL이 부상하고 있으나, 데이터의 정합성과 트랜잭션 신뢰성이 코어 비즈니스를 결정하는 환경에서는 여전히 RDBMS가 절대적 기준이다
- 향후 방향: RDBMS의 확장성 한계를 극복하기 위해 분산 아키텍처를 수용하는 NewSQL(Spanner, CockroachDB) 형태로 발전하고 있다
