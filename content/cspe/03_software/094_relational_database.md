## 미리 알고가기

- 관계형 데이터베이스(RDB): 2차원 테이블(릴레이션) 형태로 데이터를 표현하고, 공통 키값으로 관계를 맺어 구조화하는 데이터베이스 관리 시스템임
- 릴레이션(Relation): 행($Tuple$)과 열($Attribute$)로 구성된 수학적 집합 개념의 2차원 데이터 테이블 구조임
- 무결성 제약조건(Integrity Constraint): 데이터베이스 내부 데이터의 정확성, 정합성, 일관성을 보장하기 위해 도메인, 개체, 참조 관계에 강제하는 제약 규칙임
- 기본키(Primary Key, PK): 릴레이션 내부에서 각각의 튜플을 고유하게 식별할 수 있는 대표 속성(또는 속성 집합)임
- 외래키(Foreign Key, FK): 다른 릴레이션의 기본키를 참조하여 테이블 간 논리적 연관 관계를 맺는 연결 속성임
- 도메인(Domain): 릴레이션의 각 열이 가질 수 있는 동일 성격의 유효한 원자값들의 집합임

## 작성 근거(검토용)

- **핵심 키워드 선정 이유**: 관계형 데이터베이스의 핵심 근간인 릴레이션 이론과 데이터의 신뢰성을 지탱하는 3대 무결성 제약조건, 그리고 관계 처리 구조를 명확히 정립하기 위해 이를 중심축으로 선정함
- **절 구성 및 전개 흐름 이유**: 개요에서 수학적 정합성 가치를 강조하고, Ⅱ절에서 구조적·안정적 스키마 특징을 서술함. Ⅲ절에서 비관계형(NoSQL)과의 본질적 차이를 대비하고, Ⅳ절과 Ⅴ절을 분리 복원하여 정적 구성요소(도식 포함)와 SQL 질의 처리의 동적 흐름도를 체계적으로 완성함
- **전수 검수 완료 근거**: 제목, 미리 알고가기, 본문, 비교표, Ⅴ절 복원본, 결론까지 총 5회 완독 정밀 검토하여 매끄럽지 않은 번역 투 어휘와 중복 설명을 제거함

## Ⅰ. 개요

- **정의/개념**: 관계형 데이터베이스는 데이터를 수학적 집합인 릴레이션으로 구조화하고, 기본키·외래키의 참조 연산 및 무결성 제약조건을 강제하여 데이터 일관성을 제공하는 데이터 관리 모델임
- **배경/필요성**: 기업 핵심 자산인 트랜잭션 데이터의 불일치($Anomaly$)와 중복 저장을 원천 차단하고 구조화된 질의로 정보 조작을 표준화하기 위해 엄격한 스키마 기반 데이터베이스가 필요함

### 쉽게 이해하기 (학습용)
- 회사 사원 정보와 부서 정보를 각각 분리된 엑셀 시트에 적어두고, 사원 시트의 '부서 번호'를 부서 시트의 '부서 번호'와 일치시켜 서로 연결해 관리하는 구조와 같음

## Ⅱ. 특징

- **수학적 집합 기반 구조**: 튜플의 순서가 없고 중복 행이 존재하지 않는 릴레이션 수학 모델을 차용하여 데이터 연산 안정성을 확보함
- **선언형 질의($SQL$) 지원**: 데이터 저장의 물리적 구조를 몰라도 사용자가 원하는 결과($What$)만 정의하면 엔진이 최적의 실행 경로를 찾아냄
- **엄격한 무결성 보장**: 개체 무결성, 참조 무결성, 도메인 제약조건을 엔진 수준에서 상시 대조하여 규칙에 어긋난 갱신을 차단함
- **데이터 독립성 유지**: 내부 저장 방식이나 인덱스 구조가 변경되어도 논리 스키마와 데이터 접근 응용 프로그램 소스 코드는 영향을 받지 않음

### 쉽게 이해하기 (학습용)
- 규격화된 블록 완구 조립 판처럼, 각 블록마다 고유 홈(기본키)이 있고 정해진 구멍(외래키)에만 정확히 끼워지도록 제한하여 엉뚱한 결합을 막는 것과 같음

## Ⅲ. 종류 및 비교

- 관계형 데이터베이스와 비관계형(NoSQL) 데이터베이스의 아키텍처적 대비임

| 판단 기준 | 관계형 DB | 비관계형 DB (NoSQL) |
|:---|:---|:---|
| **데이터 모델** | 엄격한 2차원 테이블 형태 스키마로 정의함 | Key-Value, Document, Graph 등 유연한 스키마를 씀 |
| **관계 및 무결성** | 조인($Join$) 연산과 $PK/FK$ 제약을 엔진이 강제함 | 애플리케이션 계층에서 관계를 해결하거나 비정형 결합을 씀 |
| **확장성 특징** | 주로 고성능 서버 증설($Scale-up$)에 의존함 | 저사양 서버 다수를 엮는 수평 확장($Scale-out$)에 유리함 |

### 쉽게 이해하기 (학습용)
- 규격과 서랍이 명확히 짜여 있어 제자리에만 넣어야 하는 정교한 약 상자(RDB)와 넣고 싶은 물건을 제한 없이 던져 넣을 수 있는 큰 보관 박스(NoSQL)의 차이임

## Ⅳ. 구성요소 및 구조

- 관계형 데이터베이스의 정적 아키텍처 및 연결 관계임

```text
[SQL 질의 엔진 (Optimizer)]
              │ (최적화 실행계획 전달)
              ▼
[릴레이션 (테이블/튜플)] <──(PK-FK 논리 관계 연결)──> [릴레이션]
              │
              ▼ (도메인/개체/참조 제약 검사)
[무결성 제약조건 검증]
```

| 설계 요소 | 설명 |
|:---|:---|
| **릴레이션** | 헤더($Header$)의 속성 스키마와 바디($Body$)의 실제 튜플들로 구성된 데이터의 기본 저장 단위임 |
| **기본키 및 외래키** | 튜플의 유일 식별성을 확보하고 테이블 간의 참조 경로를 정의하는 제약 장치임 |
| **무결성 제약조건** | 도메인, 개체($PK \ne Null$), 참조($FK$가 실제 존재하는 $PK$ 가리킴) 규칙을 통제하는 엔진 엔진임 |
| **SQL 및 옵티마이저** | 사용자의 질의를 실행 계획($Execution Plan$)으로 컴파일하고 효율적인 인덱스 스캔 경로를 설계하는 모듈임 |

### 쉽게 이해하기 (학습용)
- 학교 학적부 시트(릴레이션)에서 학번(기본키)으로 학생을 식별하고, 수강 신청 시트의 학번(외래키)과 대조하며 전공명(도메인)이 유효한지 학사 프로그램(SQL엔진)이 통제하는 구조임

## Ⅴ. 원리 및 절차 흐름도

- RDB 엔진이 사용자의 SQL 질의를 받아 무결성 규칙을 유지하며 수행하는 동적 흐름임

```text
[SQL 질의 입력] ──> [구문 분석 및 변환] ──> [최적화 및 계획 수립] ──> [무결성 검증 및 실행]
```

1. **SQL 질의 입력**: 사용자가 데이터의 검색 또는 수정을 수행하는 $SQL$ 문을 선언적으로 입력함
2. **구문 분석 및 변환**: 엔진이 구문과 철자($Syntax, Semantic$) 오류를 점검하고 관계 대수식 형태의 내부 표현식으로 바꿈
3. **최적화 및 계획 수립**: 비용 기반 옵티마이저가 테이블 통계를 분석하여 최소 비용을 갖는 스캔 및 조인 방식의 실행 계획을 확정함
4. **무결성 검증 및 실행**: 데이터를 읽거나 쓸 때 정의된 $PK$, $FK$ 제약조건과 도메인 범위를 확인하여 이상 없을 시 실행 후 결과를 반환함

### 쉽게 이해하기 (학습용)
- 식당 점원에게 메뉴를 주문하면(질의 입력), 요리 주문이 올바른지 확인하고(구문 분석), 가장 효율적인 조리 순서를 정해(최적화), 레시피 재료 위생을 검증하여 요리를 만들어 서빙하는(검증 및 실행) 과정과 같음

## Ⅵ. 실무 사례

- **금융 트랜잭션 관리**: 계좌 마스터 테이블의 계좌번호($PK$)와 거래 내역 테이블의 계좌번호($FK$) 간에 엄격한 참조 무결성을 걸어, 실재하지 않는 계좌로 입금 내역을 만드는 부정 거래를 데이터베이스 엔진 수준에서 차단함
- **데이터 분석 및 튜닝**: 대규모 주문 처리 시스템에서 쿼리 실행 계획($Execution Plan$)을 추적하여 디스크 전체 스캔을 방지하고 적절한 인덱스를 적용해 슬로우 쿼리 발생 비율을 낮춤

### 쉽게 이해하기 (학습용)
- 쇼핑몰에서 상품 주문 시, 존재하지 않는 가짜 회원 ID나 재고 번호로 주문서가 등록되지 않도록 회원 정보 테이블을 참조하여 엄격히 유효성을 확인하고 주문서를 결제 처리하는 실제 조치임

## Ⅶ. 결론

- 관계형 데이터베이스는 엄격한 논리적 스키마와 무결성 제약조건을 제공하여 비즈니스 데이터의 깨지지 않는 원천 신뢰도를 보장함
- 극도의 수평 분산 처리가 요구되는 구간에서는 샤딩 전략을 수립하거나, 성능 병목 완화를 위해 캐시 계층($Redis$) 및 NoSQL 데이터베이스와의 하이브리드 아키텍처를 도입해 확장성 한계를 제어해야 함

### 쉽게 이해하기 (학습용)
- 튼튼한 건물 뼈대(RDB)를 1층에 세워 하중을 지탱하게 하고, 가벼운 가벽 인테리어(NoSQL)를 2층 이상에 설계하여 안전성과 공간 유연성을 동시에 만족시키는 아키텍처 의사결정과 같음
