## 핵심 인사이트 (3줄 요약)
- 1970년 에드거 F. 커드(E.F. Codd)가 창안한 데이터 모델로, 데이터를 2차원의 표(Table, Relation) 형태로 저장하고 수학적 집합론에 기반하여 데이터를 다루는 시스템(RDBMS).
- 데이터의 일관성과 무결성을 지키기 위해 고정된 구조(Schema)를 가지며, 기본키(PK)와 외래키(FK)를 통해 테이블 간의 **'관계(Relationship)'**를 맺어 데이터 중복을 최소화(정규화)함.
- NoSQL의 등장에도 불구하고, 금융/결제 등 절대 틀려서는 안 되는 강력한 정합성(ACID)이 필요한 도메인에서는 영원히 대체 불가능한 소프트웨어 아키텍처의 심장임.

## Ⅰ. 개요 및 필요성
- **개요**: 행(Row/Tuple)과 열(Column/Attribute)로 구성된 테이블(Relation)에 데이터를 저장하고, SQL을 통해 조작하는 데이터베이스 관리 시스템 (Oracle, MySQL, PostgreSQL).
- **필요성**: 과거의 계층형/망형 데이터베이스는 데이터 구조가 포인터(링크)로 단단히 묶여 있어, 응용 프로그램이 데이터 구조에 종속되었음. 데이터의 물리적 저장 방식과 논리적 구조를 분리(데이터 독립성)하여, 인간이 이해하기 쉬운 직관적인 표 형태로 데이터를 다룰 수학적 모델이 필요했음.
---
## Ⅱ. 아키텍처 및 핵심 원리
- **RDB의 핵심 구성 요소**:
  1. **릴레이션 (Relation)**: 데이터를 담는 2차원 테이블 (수학의 집합).
  2. **튜플 (Tuple / Row)**: 릴레이션을 구성하는 각 행 (객체의 인스턴스/데이터 한 건).
  3. **속성 (Attribute / Column)**: 데이터의 성질을 나타내는 열 (데이터의 필드).
  4. **도메인 (Domain)**: 하나의 속성이 가질 수 있는 원자값(더 이상 쪼갤 수 없는 값)들의 집합 (예: '성별' 도메인은 {남, 여}).
- **무결성 제약조건 (Integrity Constraints)**:
  - **개체 무결성 (Entity Integrity)**: 기본키(PK)는 절대 NULL이 될 수 없으며, 중복될 수 없음.
  - **참조 무결성 (Referential Integrity)**: 외래키(FK) 값은 참조하는 부모 테이블의 기본키에 반드시 존재해야 함 (고아 레코드 방지).

```text
[ 관계형 데이터베이스의 논리적 구조 (PK-FK 관계) ]

 [ 부서 테이블 (Department) ]            [ 사원 테이블 (Employee) ]
 +---------+-----------+               +---------+--------+------------+
 | 부서코드(PK)| 부서명     |               | 사번(PK) | 이름   | 부서코드(FK) |
 +---------+-----------+               +---------+--------+------------+
 |   D01   | 개발팀     | <====(참조)==== |  1001   | 김철수  |    D01     |
 |   D02   | 영업팀     |               |  1002   | 이영희  |    D02     |
 +---------+-----------+               +---------+--------+------------+
  (부서코드 D03이 없는데, 사원 테이블에 부서코드 D03을 넣으려고 하면 ➡️ 참조 무결성 에러 발생!)
```

## Ⅲ. 비교 및 연결
| 구분 | RDB (관계형 DB) | NoSQL (비관계형 DB) |
|---|---|---|
| **데이터 구조** | 스키마(Schema)가 고정된 테이블 | 스키마가 없는(유연한) JSON/문서 |
| **데이터 무결성** | 매우 강함 (ACID 보장) | 비교적 약함 (Eventual Consistency) |
| **확장성 (Scaling)**| Scale-Up (수직 확장) 유리 | **Scale-Out (수평 확장, 분산)** 유리 |
| **적합한 워크로드** | 금융 시스템, ERP, 복잡한 조인(JOIN) | 실시간 로그 수집, SNS, 대용량 비정형 데이터 |
---
## Ⅳ. 실무 적용 및 기술사 판단
- **조인(JOIN)의 양날의 검**: RDB의 가장 강력한 무기는 정규화된 테이블을 묶어내는 JOIN임. 하지만 트래픽이 폭주하는 MSA 환경에서 5~6개의 테이블을 무거운 JOIN으로 엮어내면 DB의 CPU가 버티지 못함. 실무 아키텍처에서는 조인을 최소화하기 위해 '의도적인 역정규화(Denormalization)'를 수행하거나, 읽기 전용 복제본(Read Replica)을 두어 부하를 분산하는 설계가 필수적임.
- **ORM(객체-관계 매핑)의 임피던스 불일치**: Java(객체)와 RDB(테이블)는 태생적 패러다임이 달라 필연적인 충돌(Impedance Mismatch)이 발생함. JPA나 Hibernate 같은 ORM 도구가 이 간극을 메워주지만, N+1 문제 같은 치명적 성능 저하를 유발하므로 개발자는 반드시 하단의 SQL이 어떻게 생성되는지 원리를 꿰뚫고 있어야 함.

## Ⅴ. 기대효과 및 결론
- "데이터는 한 번만 기록되어야 한다(정규화)"는 철학을 통해, 50년 동안 전 세계 비즈니스 데이터의 정합성과 신뢰성을 굳건히 지켜온 IT 산업의 척추임.
- 클라우드 네이티브 시대에 RDB는 수평 확장(Scale-out)이 어렵다는 비판을 받았으나, 최근 Aurora, Spanner 등 '분산형 RDBMS(NewSQL)'의 등장으로 클라우드 환경에서도 영원한 생명력을 이어가고 있음.
