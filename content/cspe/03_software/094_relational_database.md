# 📖 【암기용】 개념 완전 이해

> 목적: 관계형 데이터베이스를 처음 보는 사람도 릴레이션·튜플·속성·키·제약조건의 관계를 이해하게 만든다. 시험 답안 양식이 아니라, 이해를 위한 설명이다.

## 한눈에
- **개요**: 데이터를 표처럼 저장하고 수학적 관계 연산으로 다루는 데이터 모델
- **왜 필요한가**: 파일 단위 저장은 중복·불일치·검색 로직 분산을 만든다. RDB는 스키마와 제약조건으로 데이터 의미를 한곳에 고정한다.
- **핵심 직관**: 표는 데이터 저장 공간이고, 키와 제약조건은 "이 표가 현실 세계를 어긋나지 않게 표현하는 규칙"이다.

## 깊이 이해
- **배경·문제의식**: 업무 데이터는 고객, 주문, 상품처럼 서로 연결된다. 프로그램마다 파일 구조를 직접 해석하면 변경 비용과 데이터 불일치가 커진다.
- **작동 원리**: 릴레이션은 행(Tuple)과 열(Attribute)로 구성된다. 기본키는 행을 식별하고, 외래키는 릴레이션 간 참조를 만든다. SQL은 SELECT·INSERT·UPDATE·DELETE로 데이터를 조작하고, DBMS는 무결성 제약을 검사한다.
- **비유**: 도서관 대출대장에 회원번호와 도서번호를 적는 것과 같다. 번호 체계가 없으면 동명이인과 같은 제목 도서를 구분하지 못한다.
- **구체 예시**: 주문 테이블은 `order_id` 기본키, `customer_id` 외래키, `amount >= 0` CHECK 제약, `email` UNIQUE 제약으로 중복·음수 금액·고객 미존재를 차단한다.
- **흔한 오해·주의점**: RDB는 단순 표 저장소가 아니다. 릴레이션 모델, 키, 정규화, 트랜잭션, SQL 최적화가 함께 동작해야 업무 정합성을 유지한다.

## 연결 개념
- 트랜잭션 ACID - 여러 SQL을 하나의 업무 단위로 묶는 원칙
- 데이터베이스 정규화 - 함수 종속 기반 중복 제거 기법
- SQL 실행계획 - 관계 대수 연산을 비용 기반으로 수행하는 절차

# 📝 【답안용】 시험 답안 템플릿

> 목적: 시험장에서 25분에 그대로 쓰는 답안 양식. 수치·표준·도식·문제유형 전환을 반영한다.
> 핵심: RDB 답안은 표 구조 설명이 아니라, 관계 모델이 무결성·질의·동시성·복구를 어떻게 보장하는지 연결해야 한다.

## 핵심 인사이트 (3줄 요약)

> 1. **본질**: 관계형 데이터베이스는 릴레이션, 튜플, 속성, 키, 제약조건으로 데이터를 논리적으로 표현하는 모델이다.
> 2. **가치**: SQL 표준, ACID 트랜잭션, 무결성 제약으로 중복·불일치·동시 수정 오류를 통제한다.
> 3. **판단 포인트**: 업무 정합성은 스키마 설계, 키 선택, 참조무결성, 인덱스, 트랜잭션 범위의 조합으로 판단한다.

## 출제 의도 및 답안 포인트

| 출제 의도 | 반드시 짚을 핵심 | 감점 회피 포인트 |
|:---|:---|:---|
| 관계 모델 기본 이해 확인 | Relation, Tuple, Attribute, Domain, Key, Constraint | 표 저장 방식만 설명하고 관계 대수·무결성 누락 |
| 데이터 정합성 설계 역량 확인 | 기본키·외래키·UNIQUE·CHECK·NOT NULL | 인덱스와 제약조건을 같은 개념으로 혼동 |
| 실무 적용 판단 확인 | OLTP, SQL, 트랜잭션, 정규화, 반정규화 기준 | NoSQL 대비 기준 없이 RDB 우위 단정 |
> 요약: RDB 문제는 데이터 구조보다 무결성 규칙과 업무 정합성 보장 방식을 묻는다.

## Ⅰ. 개요 및 필요성

RDB는 관계 모델 기반 데이터 관리 체계이다. 업무 데이터는 고객·주문·상품처럼 연결되며, 중복 저장 시 변경 불일치가 발생한다. RDB는 스키마, 키, 제약조건, SQL, 트랜잭션으로 데이터 의미와 조작 규칙을 DBMS에 집중시킨다.

---

## Ⅱ. 구조 및 구성요소

```text
Business Entity -> Relation Schema -> Table Storage
  / Key Constraint -> Tuple Identification
  / Referential Constraint -> Relation Link
SQL -> Optimizer -> Execution Engine -> Result Set
```

| 구성요소 | 역할 | 판단 포인트 |
|:---|:---|:---|
| 릴레이션 | 동일 속성 집합을 가진 튜플 집합 | 수학적 집합 기반, 중복 튜플 배제 |
| 튜플·속성 | 행과 열로 데이터 값 표현 | 속성 Domain과 NULL 허용 여부 명시 |
| 키 | 후보키·기본키·외래키로 식별·참조 | 기본키 불변성, 외래키 삭제 정책 |
| 제약조건 | 데이터 입력·수정 규칙 검증 | NOT NULL, UNIQUE, CHECK, FK |
| SQL | DDL·DML·DCL·TCL 제공 | SQL:2016, 벤더 확장 구분 |
> 요약: RDB 구조는 릴레이션에 데이터를 담고 키와 제약조건으로 업무 규칙을 DBMS 레벨에서 검증하는 방식이다.

---

## Ⅲ. 동작원리 및 흐름도

```text
요구사항 식별 -> ER 모델링 -> 릴레이션 스키마 변환
-> 키·제약조건 부여 -> SQL 실행 -> 무결성 검사
-> 트랜잭션 Commit / Rollback -> 결과 반환
```

| 단계 | 처리 내용 | 검증 기준 |
|:---:|:---|:---|
| 1 | 업무 엔티티와 관계 식별 | 엔티티명, 식별자, 카디널리티 |
| 2 | 릴레이션 스키마 설계 | 1NF 이상, 기본키 후보 1개 이상 |
| 3 | 제약조건과 인덱스 배치 | FK 위반 0건, 주요 조회 p95 목표 |
| 4 | SQL 실행과 트랜잭션 처리 | ACID, Commit 로그, Rollback 가능 |
| 5 | 통계 기반 실행계획 선택 | Full Scan 비율, 인덱스 선택도 |
> 요약: RDB는 설계 단계의 스키마를 실행 단계의 SQL·무결성 검사·트랜잭션 처리로 일관되게 적용한다.

## Ⅳ. 특징

| 구분 | 기존 파일 처리 | 관계형 데이터베이스 | 정량·판단 기준 |
|:---|:---|:---|:---|
| 데이터 구조 | 프로그램별 파일 포맷 | 릴레이션 스키마 | 테이블·컬럼·Domain 명시 |
| 정합성 | 애플리케이션 코드 검사 | PK/FK/CHECK/UNIQUE | 제약 위반 SQLSTATE 기록 |
| 질의 | 파일 순차 탐색 | SQL·관계 대수·옵티마이저 | 인덱스 선택도 5% 이하 우선 |
| 변경 영향 | 파일 파서 동시 수정 | DDL 변경과 마이그레이션 | 스키마 버전·Rollback 계획 |
> 요약: RDB는 데이터 의미와 제약을 저장소 계층에 배치해 프로그램별 검사 누락을 줄인다.

## Ⅴ. 심화 비교 및 적용 판단

| 비교 축 | 기존/대안 | 본 키워드 | 선택 기준 |
|:---|:---|:---|:---|
| 모델 | Key-Value·Document | Relation·Schema·SQL | 다중 테이블 Join과 강한 정합성 요구 |
| 비용/성능 | 스키마 자유도 | 정규화와 인덱스 관리 | 쓰기 TPS, Join 비용, 스토리지 중복률 |
| 운영/위험 | 애플리케이션 무결성 | DB 제약조건과 트랜잭션 | FK 위반 0건, 장애복구 RPO 15분 |
> 요약: 강한 정합성과 복잡 질의가 우선이면 RDB, 유연한 문서 구조와 수평 분산이 우선이면 대안 모델을 검토한다.

| 리스크 | 원인 | 대응 방안 | 확인 지표 |
|:---|:---|:---|:---|
| 스키마 경직 | 업무 변경 대비 DDL 영향 | Expand-Contract 마이그레이션 | 배포 실패율, Lock 대기 시간 |
| Join 병목 | 과도한 정규화와 인덱스 누락 | 실행계획 리뷰, 복합 인덱스 | p95 지연, Buffer Hit Ratio |
| 참조 무결성 오류 | FK 미설계 또는 삭제 정책 부재 | FK, ON DELETE 정책, 테스트 데이터 | FK violation 0건 |
> 요약: RDB 리스크는 스키마 변경, Join 비용, 참조 무결성으로 나뉘며 설계·인덱스·마이그레이션으로 통제한다.

| 점검 항목 | 목표 기준 | 측정 방법 |
|:---|:---|:---|
| 무결성 | PK 중복 0건, FK 위반 0건 | 제약조건 검사, 데이터 품질 SQL |
| 질의 처리 | 주요 API p95 200ms 이하 | APM, EXPLAIN ANALYZE |
| 복구 | WAL 기반 RPO 15분, RTO 30분 | 백업 복구 리허설 |
> 요약: RDB 도입 효과는 무결성 위반, 질의 지연, 복구 지표로 검증한다.

## Ⅵ. 실무 적용 및 결론

**적용 방안 3개:**
1. 스키마 설계: 후보키 도출 후 기본키·외래키·UNIQUE·CHECK를 DDL에 반영하고 FK 위반 0건 기준으로 검증함
2. 질의 설계: 상위 20개 SQL에 대해 EXPLAIN ANALYZE를 수행하고 p95 200ms 초과 쿼리에 복합 인덱스·쿼리 재작성 적용함
3. 운영 설계: WAL 아카이빙, PITR, 일 1회 백업 복구 리허설로 RPO 15분·RTO 30분 달성 여부 확인함

**결론 (2줄):**
- 기술사 판단: 강한 정합성·복잡 Join·표준 SQL이 필요하면 RDB, 유연 스키마·초대규모 단순 조회가 우선이면 NoSQL 병행을 선택함
- 향후 방향: HTAP, 분산 SQL, 클라우드 관리형 DB로 OLTP 정합성과 분석 접근성을 함께 설계하는 방향임
