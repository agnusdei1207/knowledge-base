# 📖 【암기용】 개념 완전 이해

> 목적: 관계형 데이터베이스를 처음 보는 사람도 릴레이션·튜플·속성·키·제약조건의 관계를 이해하게 만든다. 시험 답안 양식이 아니라, 이해를 위한 설명이다.

## 한눈에
- **개요**: 관계형 데이터베이스(RDB)는 **관계 모델(Relational Model)**을 기반으로 데이터를 **릴레이션(테이블)**로 표현하고 **SQL**로 조작하는 **DBMS**다.
- **왜 필요한가**: 파일 단위 저장은 프로그램마다 구조를 직접 해석해야 해서 중복·불일치·검색 로직 분산을 만든다. RDB는 스키마와 제약조건을 DBMS 한곳에 고정해 데이터 의미를 통일한다.
- **핵심 직관**: 릴레이션(표)은 데이터를 담는 그릇이고, 키와 제약조건은 "이 그릇이 현실 세계의 규칙과 어긋나지 않게 만드는 검문소"다.

## 핵심 용어 정리 (내부에 등장하는 것들)

| 용어 | 의미 | 비유 |
|:---|:---|:---|
| 관계 모델 (Relational Model) | 데이터를 집합론적 관계(릴레이션)로 표현하는 데이터 모델 — RDB의 **상위 개념**, 1970년 Codd가 제안 | 표 형태로 데이터를 다루는 수학적 규칙 |
| DBMS (Database Management System) | 데이터 저장·조회·무결성·동시성·복구를 관리하는 소프트웨어 — RDB의 **상위 개념** | 도서관 전체를 운영하는 관리 시스템 |
| 릴레이션 (Relation) | 동일한 속성 집합을 가진 튜플들의 **집합** — 흔히 "테이블" | 표 한 장 |
| 튜플 (Tuple) | 릴레이션의 한 행 — 하나의 개체 인스턴스 | 표의 한 줄 (예: 학생 한 명) |
| 속성 (Attribute) | 릴레이션의 한 열 — 튜플이 갖는 값의 종류 | 표의 한 칸 제목 (예: 이름, 나이) |
| 도메인 (Domain) | 속성이 가질 수 있는 값의 범위 | "나이" 칸에는 정수만, 문자는 안 됨 |
| 슈퍼키 (Super Key) | 튜플을 유일하게 식별하는 속성(들)의 집합, 불필요한 속성 포함 가능 | "학번+이름"처럼 과하게 큰 식별표 |
| 후보키 (Candidate Key) | 슈퍼키 중 더 줄일 수 없는 최소 식별자 | "학번" 하나만으로 충분한 식별표 |
| 기본키 (Primary Key) | 후보키 중 대표로 선택해 실제 식별에 쓰는 키 | 주민등록번호처럼 공식 대표 번호 |
| 외래키 (Foreign Key) | 다른 릴레이션의 기본키를 참조해 두 표를 연결하는 속성 | 주문서에 적힌 "고객번호" — 고객 표를 가리킴 |
| 참조무결성 (Referential Integrity) | 외래키 값이 반드시 참조 대상 릴레이션에 실제로 존재해야 한다는 규칙 | 존재하지 않는 고객번호로 주문 못 함 |
| CHECK / NOT NULL / UNIQUE | 값의 범위·존재·중복을 강제하는 제약조건 | 입력 폼의 필수 항목·중복 검사 |
| SQL | DDL(정의)·DML(조작)·DCL(권한)·TCL(트랜잭션 제어)을 포괄하는 관계형 DB 표준 질의어 | 표를 다루는 공용 명령어 |
| 정규화 (Normalization) | 함수 종속 관계를 분석해 중복을 제거하는 스키마 설계 절차 | 중복 기재를 줄이도록 서식을 재배치 |

## 깊이 이해

### 왜 등장했나 (배경)
- 1970년 이전에는 계층형·네트워크형 DB가 주류였는데, 이들은 데이터 접근 경로가 프로그램 코드에 고정되어 스키마를 바꾸면 프로그램도 함께 고쳐야 했다. E. F. Codd는 1970년 논문에서 데이터를 "관계(집합)"로만 표현하고, 접근은 관계 대수(집합 연산)로 하자는 관계 모델을 제안했다 — 이것이 RDB의 이론적 뿌리다.
- 파일 기반 처리에서는 고객·주문·상품처럼 서로 연결된 데이터를 프로그램마다 직접 파싱해야 해서, 구조가 바뀌면 관련된 모든 프로그램을 수정해야 했다. RDB는 이 구조 해석 책임을 DBMS 한곳으로 모았다.

### 릴레이션의 수학적 성질 — 왜 "그냥 표"가 아닌가
- 릴레이션은 집합이므로 두 가지 성질을 갖는다: ① 튜플 중복이 없다(같은 행이 두 번 존재할 수 없다) ② 튜플 사이에 순서가 없다(정렬은 조회 시 별도 지정). 이 때문에 릴레이션은 유일하게 식별 가능한 키가 반드시 있어야 한다 — 그래야 "중복 없음"을 보장할 수 있다.

### 키 구조를 구체 예로 이해하기
- 학생 릴레이션에 (학번, 주민등록번호, 이름, 학과) 속성이 있다고 하자. 학번과 주민등록번호는 각각 단독으로 학생을 유일하게 식별하므로 둘 다 **후보키**다. 이름은 동명이인이 있을 수 있어 후보키가 될 수 없다.
- 두 후보키 중 시스템 내부용으로 짧고 변하지 않는 학번을 **기본키**로 선택한다. 이때 슈퍼키는 후보키에 임의의 속성을 더 붙인 것도 포함하므로 "학번+이름"도 슈퍼키지만 이름이 불필요하므로 후보키는 아니다. 즉 슈퍼키 ⊇ 후보키 ⊇ 기본키(1개 선택) 관계다.

### 제약조건을 구체 수치로 이해하기
- 주문(order) 테이블: `order_id`를 기본키로 두어 같은 주문번호가 두 번 들어오지 못하게 막고, `customer_id`를 외래키로 두어 존재하지 않는 고객번호(예: customer_id=99999인데 고객 테이블에 없음)로는 주문이 생성되지 않게 막는다. `amount >= 0` CHECK 제약은 -500원 같은 음수 결제 금액 입력을 DB 단에서 차단하고, `email` UNIQUE 제약은 같은 이메일로 회원 가입이 두 번 되는 것을 막는다.
- 이 네 가지 제약이 없으면 애플리케이션 코드가 매번 "고객이 존재하는가", "금액이 0 이상인가"를 검사해야 하고, 코드 경로 하나라도 빠뜨리면 잘못된 데이터가 쌓인다. DBMS가 제약을 검사하면 어떤 경로로 데이터가 들어오든 규칙이 100% 적용된다.

### 정규화 감 잡기 — 중복 제거 워크드 예제
- 정규화 전: 주문 테이블에 (주문번호, 고객번호, 고객이름, 고객주소, 상품번호, 상품명, 수량)을 한 테이블에 다 넣으면, 같은 고객이 10번 주문할 때 고객이름·주소가 10번 중복 저장된다. 고객이 이사하면 10개 행을 전부 갱신해야 하고, 하나라도 빠뜨리면 데이터가 어긋난다(갱신 이상).
- 정규화 후: 고객 테이블(고객번호, 이름, 주소)과 주문 테이블(주문번호, 고객번호 FK, 상품번호, 수량)로 분리하면 고객 정보는 1곳에만 있고, 주문 테이블은 고객번호만 참조한다. 고객이 이사하면 고객 테이블 1행만 갱신하면 된다.

### SQL 실행의 이면 — 관계 대수와 옵티마이저
- `SELECT name FROM customer WHERE city='Seoul'`은 내부적으로 관계 대수의 선택(Selection, σ)과 투영(Projection, π) 연산으로 변환된다. 옵티마이저는 인덱스 존재 여부, 테이블 통계(행 수, 값 분포)를 보고 Full Scan과 Index Scan 중 비용이 적은 실행계획을 고른다. 예를 들어 city='Seoul' 조건에 맞는 행이 전체의 5% 이하이면 인덱스 스캔이, 50% 이상이면 오히려 Full Scan이 더 빠를 수 있다.

### 비유와 흔한 오해
- **비유**: 도서관 대출대장에 회원번호와 도서번호를 적는 것과 같다. 이름만 적으면 동명이인, 같은 제목의 다른 판본을 구분하지 못하므로 고유 번호(키) 체계가 필요하다.
- **오해**: RDB는 단순히 "표에 데이터를 저장하는 것"이 아니다. 릴레이션 모델(집합 성질), 키(식별·참조), 정규화(중복 제거), 트랜잭션(변경 정합성), SQL 옵티마이저(실행 비용)가 함께 동작해야 업무 정합성과 성능을 동시에 유지한다.

## 연결 개념
- 트랜잭션 ACID: 여러 SQL을 하나의 업무 단위로 묶어 정합성을 보장하는 원칙
- 데이터베이스 정규화: 함수 종속 분석 기반으로 중복을 제거하는 설계 절차
- SQL 실행계획: 관계 대수 연산을 비용 기반으로 최적화해 수행하는 절차

# 📝 【답안용】 시험 답안 템플릿

> 목적: 시험장에서 25분에 그대로 쓰는 답안 양식. 수치·표준·도식·문제유형 전환을 반영한다.
> 핵심: RDB 답안은 표 구조 설명이 아니라, 관계 모델이 무결성·질의·동시성·복구를 어떻게 보장하는지 연결해야 한다.

## 핵심 인사이트 (3줄 요약)

> 1. **본질**: 관계형 데이터베이스는 릴레이션, 튜플, 속성, 키, 제약조건으로 데이터를 논리적으로 표현하는 모델이다.
> 2. **가치**: SQL 표준, ACID 트랜잭션, 무결성 제약으로 중복·불일치·동시 수정 오류를 통제한다.
> 3. **판단 포인트**: 업무 정합성은 스키마 설계, 키 선택, 참조무결성, 인덱스, 트랜잭션 범위의 조합으로 판단한다.

## 출제 의도 및 답안 포인트

| 출제 의도 | 반드시 짚을 핵심 | 감점 회피 포인트 |
|:---|:---|:---|
| 관계 모델 기본 이해 확인 | Relation, Tuple, Attribute, Domain, Key, Constraint | 표 저장 방식만 설명하고 관계 대수·무결성 누락 |
| 데이터 정합성 설계 역량 확인 | 기본키·외래키·UNIQUE·CHECK·NOT NULL | 인덱스와 제약조건을 같은 개념으로 혼동 |
| 실무 적용 판단 확인 | OLTP, SQL, 트랜잭션, 정규화, 반정규화 기준 | NoSQL 대비 기준 없이 RDB 우위 단정 |
> 요약: RDB 문제는 데이터 구조보다 무결성 규칙과 업무 정합성 보장 방식을 묻는다.

## Ⅰ. 개요 및 필요성

- 개요: RDB는 관계 모델 기반 데이터 관리 체계이다.
- 배경: 고객, 주문, 상품 데이터가 파일·테이블별로 중복 저장되면 변경 불일치와 조회 로직 분산이 발생한다.
- 필요성: 스키마, PK/FK, CHECK, SQL, ACID 트랜잭션으로 데이터 의미와 조작 규칙을 DBMS에 집중시켜야 한다.

---

## Ⅱ. 구조 및 구성요소

```text
Business Entity -> Relation Schema -> Table Storage
  / Key Constraint -> Tuple Identification
  / Referential Constraint -> Relation Link
SQL -> Optimizer -> Execution Engine -> Result Set
```

| 구성요소 | 역할 | 판단 포인트 |
|:---|:---|:---|
| 릴레이션 | 동일 속성 집합을 가진 튜플 집합 | 수학적 집합 기반, 중복 튜플 배제 |
| 튜플·속성 | 행과 열로 데이터 값 표현 | 속성 Domain과 NULL 허용 여부 명시 |
| 키 | 후보키·기본키·외래키로 식별·참조 | 기본키 불변성, 외래키 삭제 정책 |
| 제약조건 | 데이터 입력·수정 규칙 검증 | NOT NULL, UNIQUE, CHECK, FK |
| SQL | DDL·DML·DCL·TCL 제공 | SQL:2016, 벤더 확장 구분 |
> 요약: RDB 구조는 릴레이션에 데이터를 담고 키와 제약조건으로 업무 규칙을 DBMS 레벨에서 검증하는 방식이다.

## Ⅲ. 동작원리 및 흐름도

```text
요구사항 식별 -> ER 모델링 -> 릴레이션 스키마 변환
-> 키·제약조건 부여 -> SQL 실행 -> 무결성 검사
-> 트랜잭션 Commit / Rollback -> 결과 반환
```

| 단계 | 처리 내용 | 검증 기준 |
|:---:|:---|:---|
| 1 | 업무 엔티티와 관계 식별 | 엔티티명, 식별자, 카디널리티 |
| 2 | 릴레이션 스키마 설계 | 1NF 이상, 기본키 후보 1개 이상 |
| 3 | 제약조건과 인덱스 배치 | FK 위반 0건, 주요 조회 p95 목표 |
| 4 | SQL 실행과 트랜잭션 처리 | ACID, Commit 로그, Rollback 가능 |
| 5 | 통계 기반 실행계획 선택 | Full Scan 비율, 인덱스 선택도 |
> 요약: RDB는 설계 단계의 스키마를 실행 단계의 SQL·무결성 검사·트랜잭션 처리로 일관되게 적용한다.

## Ⅳ. 특징

| 구분 | 기존 파일 처리 | 관계형 데이터베이스 | 정량·판단 기준 |
|:---|:---|:---|:---|
| 데이터 구조 | 프로그램별 파일 포맷 | 릴레이션 스키마 | 테이블·컬럼·Domain 명시 |
| 정합성 | 애플리케이션 코드 검사 | PK/FK/CHECK/UNIQUE | 제약 위반 SQLSTATE 기록 |
| 질의 | 파일 순차 탐색 | SQL·관계 대수·옵티마이저 | 인덱스 선택도 5% 이하 우선 |
| 변경 영향 | 파일 파서 동시 수정 | DDL 변경과 마이그레이션 | 스키마 버전·Rollback 계획 |
> 요약: RDB는 데이터 의미와 제약을 저장소 계층에 배치해 프로그램별 검사 누락을 줄인다.

## Ⅴ. 심화 비교 및 적용 판단

| 비교 축 | 기존/대안 | 본 키워드 | 선택 기준 |
|:---|:---|:---|:---|
| 모델 | Key-Value·Document | Relation·Schema·SQL | 다중 테이블 Join과 강한 정합성 요구 |
| 비용/성능 | 스키마 자유도 | 정규화와 인덱스 관리 | 쓰기 TPS, Join 비용, 스토리지 중복률 |
| 운영/위험 | 애플리케이션 무결성 | DB 제약조건과 트랜잭션 | FK 위반 0건, 장애복구 RPO 15분 |
> 요약: 강한 정합성과 복잡 질의가 우선이면 RDB, 유연한 문서 구조와 수평 분산이 우선이면 대안 모델을 검토한다.

| 리스크 | 원인 | 대응 방안 | 확인 지표 |
|:---|:---|:---|:---|
| 스키마 경직 | 업무 변경 대비 DDL 영향 | Expand-Contract 마이그레이션 | 배포 실패율, Lock 대기 시간 |
| Join 병목 | 과도한 정규화와 인덱스 누락 | 실행계획 리뷰, 복합 인덱스 | p95 지연, Buffer Hit Ratio |
| 참조 무결성 오류 | FK 미설계 또는 삭제 정책 부재 | FK, ON DELETE 정책, 테스트 데이터 | FK violation 0건 |
> 요약: RDB 리스크는 스키마 변경, Join 비용, 참조 무결성으로 나뉘며 설계·인덱스·마이그레이션으로 통제한다.

| 점검 항목 | 목표 기준 | 측정 방법 |
|:---|:---|:---|
| 무결성 | PK 중복 0건, FK 위반 0건 | 제약조건 검사, 데이터 품질 SQL |
| 질의 처리 | 주요 API p95 200ms 이하 | APM, EXPLAIN ANALYZE |
| 복구 | WAL 기반 RPO 15분, RTO 30분 | 백업 복구 리허설 |
> 요약: RDB 도입 효과는 무결성 위반, 질의 지연, 복구 지표로 검증한다.

## Ⅵ. 실무 적용 및 결론

**적용 방안 3개:**
1. 스키마 설계: 후보키 도출 후 기본키·외래키·UNIQUE·CHECK를 DDL에 반영하고 FK 위반 0건 기준으로 검증함
2. 질의 설계: 상위 20개 SQL에 대해 EXPLAIN ANALYZE를 수행하고 p95 200ms 초과 쿼리에 복합 인덱스·쿼리 재작성 적용함
3. 운영 설계: WAL 아카이빙, PITR, 일 1회 백업 복구 리허설로 RPO 15분·RTO 30분 달성 여부 확인함

**결론 (2줄):**
- 기술사 판단: 강한 정합성·복잡 Join·표준 SQL이 필요하면 RDB, 유연 스키마·초대규모 단순 조회가 우선이면 NoSQL 병행을 선택함
- 향후 방향: HTAP, 분산 SQL, 클라우드 관리형 DB로 OLTP 정합성과 분석 접근성을 함께 설계하는 방향임
