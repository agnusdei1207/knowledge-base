## 핵심 인사이트 (3줄 요약)
- "클라우드(AWS)를 쓰면 보안은 아마존이 다 알아서 해주는 거 아냐?"라는 경영진의 치명적인 착각을 깨부수는, **클라우드 제공자(CSP)와 고객 간의 보안 책임 한계를 명확히 그어놓은 계약서이자 대원칙**.
- **AWS의 책임 (클라우드 '의' 보안)**: 데이터센터 건물에 도둑이 들거나, 네트워크 케이블이 끊어지거나, 하드웨어 디스크가 고장 나는 물리적 인프라의 철통 방어를 책임짐.
- **고객의 책임 (클라우드 '내에서의' 보안)**: 방화벽 포트 80번을 열어두거나, DB 비밀번호를 `1234`로 설정하거나, 직원 PC가 해킹당해 데이터가 털리는 것은 100% 고객의 과실이며 아마존은 보상하지 않음.

## Ⅰ. 개요 및 필요성
- **개요**: 클라우드 컴퓨팅 환경에서 발생할 수 있는 장애나 보안 사고에 대해, 서비스 제공자(AWS, Azure)와 사용자(기업)가 어디까지 책임을 져야 하는지(Responsibility)를 분담해 놓은 프레임워크.
- **필요성**: 클라우드 초창기, 기업이 AWS S3에 기밀문서를 올려놨는데, 담당자가 권한 설정을 실수해서(Public Open) 전 세계에 기밀이 유출됨. 기업은 "아마존 해킹당했다! 보상해라!"라고 소송을 걸었음. 아마존은 "우리가 제공한 인프라는 완벽했습니다. 당신들이 대문을 활짝 열어놓고 나간 건데 왜 우리 탓을 합니까?"라며 선을 그음. 이 모호한 책임 소재를 법적으로 정리하기 위해 탄생함.
---
## Ⅱ. 아키텍처 및 핵심 원리
- **1. 클라우드 제공자의 책임 (Security OF the Cloud)**:
  - 무장 경비원이 데이터센터 문을 지키는 물리적 보안.
  - 전력 공급, 냉각, 네트워크 케이블 유지보수.
  - 가상화 소프트웨어(Hypervisor) 패치 및 하드웨어 결함 방지.
  - "우리가 만든 바닥(인프라)이 무너지는 일은 절대 없게 하겠다."
- **2. 고객의 책임 (Security IN the Cloud)**:
  - 클라우드 위에서 돌아가는 O/S 윈도우 보안 패치 (IaaS의 경우).
  - 네트워크 방화벽(Security Group) 규칙 설정. (예: 22번 SSH 포트 함부로 안 열기).
  - 데이터 암호화, 직원 로그인 비밀번호 복잡도, 데이터 백업 주기 설정.
  - "당신이 빌린 방 안에 쓰레기를 버리거나, 창문을 열어둬서 도둑이 드는 건 당신 책임이다."
- **3. 서비스 모델에 따른 책임의 변화 (IaaS ➡️ PaaS ➡️ SaaS)**:
  - **IaaS**: 고객 책임이 가장 큼. (운영체제 패치까지 고객이 다 해야 함).
  - **PaaS**: 제공자 책임이 늘어남. (OS 패치는 AWS가 해줌. 코드는 고객 책임).
  - **SaaS**: 제공자 책임이 극대화됨. (고객은 그냥 계정 비밀번호 관리만 잘하면 됨).

```text
[ 공동 책임 모델의 아파트 렌트 비유 ]

 🏢 [ AWS (건물주 / 관리사무소) 의 책임 ]
 - 1층 현관문 비밀번호 유지, 경비원 배치, 엘리베이터 고장 수리, 수도관 터짐 방지.
 - 만약 아파트가 지진에 무너지면 건물주가 물어냄! (인프라 보안).

 🔑 [ 기업 (세입자) 의 책임 ]
 - 내 집(101호) 도어락 비밀번호 관리, 창문 닫고 외출하기, 귀중품 금고에 넣기.
 - 만약 내가 101호 문을 활짝 열어두고 나가서 도둑이 노트북을 훔쳐 가면? 
 ➡️ "건물주(AWS) 잘못 없음! 문 열어놓은 세입자(고객) 100% 과실!" (데이터 및 접근 제어 보안).
```

## Ⅲ. 비교 및 연결
| 책임 영역 | IaaS (EC2) 환경 | PaaS (RDS, Beanstalk) 환경 | SaaS (Slack, Gmail) 환경 |
|---|---|---|---|
| **애플리케이션 코드/데이터**| **고객 책임** | **고객 책임** | **고객 책임 (데이터만)** |
| **운영체제 (OS 패치 등)** | **고객 책임 (직접 패치)** | 제공자 책임 (자동화) | 제공자 책임 |
| **네트워크 / 방화벽 설정**| **고객 책임** | 공동 책임 | 제공자 책임 |
| **물리적 인프라 (서버 기계)**| 제공자 책임 (AWS) | 제공자 책임 (AWS) | 제공자 책임 (AWS) |

## Ⅳ. 실무 적용 및 기술사 판단
- **CSPM (Cloud Security Posture Management) 솔루션 도입**: 클라우드 보안 사고의 99%는 해커의 고도의 공격이 아니라, 관리자의 '설정 오류(Misconfiguration)'에서 발생함 (예: S3 버킷 퍼블릭 오픈, 방화벽 Any Open). 기술사는 사람이 눈으로 이런 실수를 막는 것은 불가능하므로, Prisma Cloud 나 AWS Security Hub 같은 **CSPM 솔루션**을 의무적으로 도입해야 함. 이는 클라우드 환경의 잘못된 설정을 실시간으로 탐지하고 규정에 맞게 자동 수정하여 고객의 책임 영역을 방어하는 핵심 방패임.
- **제로 트러스트 (Zero Trust) 아키텍처 연계**: 클라우드 환경에서는 "내부망에 들어왔으니 안전하다"는 성벽 모델이 통하지 않음. 고객 책임의 핵심은 권한 관리(IAM)에 있으므로, 기술사는 "그 누구도 믿지 않고, 모든 요청(API, 로그인)마다 최소 권한(Least Privilege) 원칙으로 지속 검증한다"는 제로 트러스트 사상을 아키텍처 근간에 심어야 함.
---
## Ⅴ. 기대효과 및 결론
- 클라우드 벤더와 고객이 각자 가장 잘할 수 있는 영역에 집중하게 하여, 기존 온프레미스(직접 구축) 시대보다 훨씬 더 강력하고 효율적인 보안 생태계를 구축함.
- "클라우드로 가면 보안이 뚫린다"는 것은 구시대적 편견이며, 공동 책임 모델을 완벽히 이해하고 '우리 몫의 보안(접근 통제, 암호화)'만 철저히 한다면 지구상에서 클라우드보다 안전한 데이터센터는 존재하지 않음.

### 👶 어린이를 위한 3줄 비유 설명
1. 내가 은행(클라우드)에 개인 금고를 빌렸어요.
2. 은행(AWS)은 무장 경찰을 세워두고, 지진이 나도 건물이 무너지지 않게 튼튼하게 지어줄 책임이 있어요 (클라우드의 보안).
3. 하지만 내가 금고 번호를 '0000'으로 해놓거나, 열쇠를 길거리에 버리고 와서 도둑맞는 건 전적으로 내 책임이에요 (클라우드 안에서의 보안).
