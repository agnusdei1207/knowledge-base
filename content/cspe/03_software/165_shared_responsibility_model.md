# 📖 【암기용】 개념 완전 이해

> 목적: 클라우드 공유 책임 모델을 처음 봐도 완벽히 이해하게 만든다. 시험 답안 양식이 아니라, 이해를 위한 친절한 설명이다.

## 한눈에
- **개요**: 클라우드 보안과 운영에서 CSP와 고객이 각각 맡는 책임을 구분하는 모델
- **왜 필요한가**: 클라우드를 쓰면 물리 보안과 일부 운영은 CSP가 맡지만, 데이터·계정·설정 오류는 여전히 고객 책임으로 남는다.
- **핵심 직관**: 건물 보안은 임대인이 맡아도 사무실 문단속, 직원 출입증, 문서 보관은 입주사가 맡는 구조다.

## 깊이 이해
- **배경·문제의식**: 클라우드 사고 상당수는 CSP 인프라 장애보다 고객의 공개 버킷, 과도한 IAM 권한, 암호화 미적용, 로그 미수집에서 발생한다. 책임 경계를 모르면 장애와 사고 시 대응 주체가 불명확해진다.
- **작동 원리**: CSP는 클라우드 "의" 보안, 즉 물리 시설, 하드웨어, 가상화 계층, 관리형 서비스 기반을 책임진다. 고객은 클라우드 "내" 보안, 즉 데이터, 계정, 네트워크 설정, 애플리케이션, 로그를 책임진다.
- **비유**: 은행 금고 시설은 은행이 관리하지만, 금고 안에 무엇을 넣고 누가 열람할지는 고객이 정한다.
- **구체 예시**: S3 버킷의 내구성은 CSP가 책임지지만, 버킷 공개 차단, KMS 암호화, 객체 권한, 접근 로그는 고객이 설정해야 한다.
- **흔한 오해·주의점**: 관리형 DB를 쓰면 DB 엔진 패치는 CSP 책임이 될 수 있지만, DB 사용자 권한, SQL 권한, 데이터 마스킹, 백업 보존 정책은 고객 통제 항목이다.

## 연결 개념
- 클라우드 서비스 모델 - IaaS·PaaS·SaaS별 책임 경계가 달라짐
- 클라우드 보안 형상 관리 CSPM - 고객 책임 영역 점검
- IAM - 고객 책임 영역에서 가장 빈번한 사고 지점

# 📝 【답안용】 시험 답안 템플릿

> 목적: 시험장에서 25분에 그대로 쓰는 답안 양식. 작성방식(추상표현 금지·수치·도식·문제유형 전환)을 엄격히 지킨다.
> 핵심: 공유 책임 모델은 보안 원칙 설명이 아니라 서비스 모델별 통제 주체, 감사 증적, 사고 대응 경계를 명확히 하는 답안으로 작성한다.

## 핵심 인사이트 (3줄 요약)

> 1. **본질**: 공유 책임 모델은 클라우드 보안·운영 책임을 CSP와 고객 사이에 계층별로 분리한 통제 모델이다.
> 2. **가치**: 책임 공백을 줄이고 IAM, 데이터 암호화, 네트워크 설정, 로그 보존 같은 고객 통제 항목을 명확히 한다.
> 3. **판단 포인트**: IaaS에서 SaaS로 갈수록 CSP 책임은 늘지만 데이터·계정·접근권한 책임은 고객에게 남는다.

## 출제 의도 및 답안 포인트

| 출제 의도 | 반드시 짚을 핵심 | 감점 회피 포인트 |
|:---|:---|:---|
| 클라우드 보안 책임 경계 확인 | CSP 책임, 고객 책임, 서비스 모델별 변화 | "CSP가 모두 책임"으로 오해 |
| 사고 예방 통제 확인 | IAM 최소권한, KMS, 네트워크 제한, 감사 로그 | 추상 보안 효과만 서술 |
| 감사·운영 대응 역량 확인 | RACI, 통제 매핑, 증적, SLA와 계약 | 책임 매트릭스와 지표 누락 |

> 요약: 이 문제는 클라우드 보안 사고의 책임 주체와 고객 통제 항목을 구체화하는 능력을 요구한다.

---

## Ⅰ. 개요 및 필요성

- 개요: 공유 책임 모델은 CSP와 고객의 보안·운영 책임 분리 모델임.
- 배경: 클라우드 도입 후에도 데이터, 계정, 권한, 네트워크 설정, 애플리케이션 보안은 고객 책임으로 남는다.
- 필요성: 책임 경계를 문서화해 사고 대응, 감사, 계약 관리의 누락 영역을 식별한다.

---

## Ⅱ. 구조 및 구성요소

```text
CSP Responsibility -> Facility -> Hardware -> Virtualization -> Managed Service Base
Customer Responsibility -> Data -> IAM -> Network Config -> Application -> Logging
Service Model -> IaaS / PaaS / SaaS 책임 범위 조정
```

| 구성요소 | 역할 | 특이사항 |
|:---|:---|:---|
| CSP 책임 | 물리 시설, 전원, 하드웨어, 가상화 계층 | SLA, 인증서, 리전 가용성 |
| 고객 책임 | 데이터, 계정, 권한, 네트워크, 앱 보안 | IAM, KMS, 보안 그룹, 로그 |
| 공동 책임 | 백업, 패치, 모니터링, 사고 대응 | 서비스 모델별 주체 변경 |

> 요약: CSP는 기반 환경을, 고객은 데이터와 접근 통제를 책임지며 일부 항목은 서비스 모델에 따라 공동 책임이 된다.

---

## Ⅲ. 동작원리 및 흐름도

```text
서비스 모델 식별 -> 책임 항목 분해 -> RACI 매핑
-> 통제 적용 -> 증적 수집 -> 감사/사고 대응
```

| 단계 | 처리 내용 | 검증 기준 |
|:---:|:---|:---|
| 1 | IaaS·PaaS·SaaS 모델 식별 | 서비스 카탈로그와 계약서 |
| 2 | 책임 항목 분해 | 데이터, IAM, 패치, 백업, 로그 |
| 3 | 고객 통제 적용 | MFA 100%, KMS 암호화, SG 최소 개방 |
| 4 | 증적과 사고 절차 관리 | 감사 로그 1년 보존, RACI 승인 |

> 요약: 공유 책임은 서비스 식별, 책임 매핑, 통제 적용, 증적 관리 순서로 운영된다.

---

## Ⅳ. 특징

| 구분 | 온프레미스 책임 | 공유 책임 모델 | 수치·판단 포인트 |
|:---|:---|:---|:---|
| 인프라 | 고객 전담 | CSP가 시설·하드웨어·가상화 담당 | SLA 99.9% 이상 |
| 보안 설정 | 고객 전담 | 고객이 IAM·네트워크·데이터 통제 | MFA 100%, 공개 리소스 0개 |
| 패치 | 고객 전담 | IaaS는 고객, PaaS/SaaS는 일부 CSP | 패치 SLA 30일 이내 |
| 감사 | 내부 증적 중심 | CSP 인증 + 고객 설정 증적 결합 | 로그 보존 1년 이상 |

> 요약: 공유 책임 모델은 인프라 책임을 CSP로 이전하지만 데이터와 접근 통제 책임은 고객에게 유지된다.

## Ⅴ. 심화 비교 및 적용 판단

| 비교 축 | IaaS | PaaS | SaaS |
|:---|:---|:---|:---|
| 고객 책임 | OS, 미들웨어, 앱, 데이터 | 코드, 설정, 데이터, 계정 | 데이터, 계정, 권한, 계약 |
| CSP 책임 | 물리, 하드웨어, 가상화 | 런타임, DB 엔진 일부 | 애플리케이션 운영 대부분 |
| 선택 기준 | 세부 통제 필요 | 개발 속도와 운영 축소 | 표준 업무와 사용자 관리 |

> 요약: 서비스 모델별 책임 차이를 표로 제시해야 공유 책임 모델 답안의 채점 포인트가 드러난다.

| 리스크 | 원인 | 대응 방안 | 확인 지표 |
|:---|:---|:---|:---|
| 공개 리소스 | 버킷, 보안 그룹 설정 오류 | CSPM, 정책 코드, 승인 워크플로 | 공개 버킷 0개 |
| 과도한 권한 | IAM 역할 누적 | 최소권한, JIT 접근, 정기 리뷰 | 관리자 권한 계정 5개 이하 |
| 증적 부족 | 로그 미수집, 보존 정책 부재 | CloudTrail, SIEM, WORM 저장 | 로그 수집률 95% 이상 |

> 요약: 고객 책임 영역의 사고는 설정 오류와 권한 남용에서 발생하므로 자동 점검과 증적 보존이 필요하다.

| 점검 항목 | 목표 기준 | 측정 방법 |
|:---|:---|:---|
| IAM | MFA 100%, 휴면 계정 0개 | IAM Access Analyzer, 계정 리뷰 |
| 데이터 보호 | KMS 암호화 100%, 민감 데이터 태깅 | CSPM, DLP 스캔 |
| 감사 | 감사 로그 1년 이상, 변경 이력 추적 | SIEM, 로그 보존 정책 |

> 요약: 공유 책임 모델의 도입 결과는 IAM, 데이터 보호, 감사 증적의 적용률로 검증한다.

---

## Ⅵ. 실무 적용 및 결론

**적용 방안 3개 (필수 - 단계별 또는 항목별):**
1. 책임 매트릭스 작성: IaaS·PaaS·SaaS별 CSP/고객/RACI를 정의하고 계약서와 보안 기준서에 반영
2. 고객 책임 통제 자동화: CSPM, IaC policy, MFA, KMS, 중앙 로그를 기본 landing zone에 포함
3. 감사와 사고 대응 연계: 로그 1년 보존, 공개 리소스 0개, 관리자 권한 리뷰 월 1회를 지표로 운영

**결론 (2줄):**
- 기술사 판단: 클라우드 보안 사고 책임은 서비스 모델별 책임 경계를 기준으로 판단하며, 데이터와 IAM은 고객 통제 항목으로 관리함
- 향후 방향: 공유 책임 모델은 CSPM, CNAPP, policy as code와 결합해 지속 점검 체계로 전환됨

### 🔀 문제 유형별 목차 전환 (이 키워드 출제 시)

| 유형 | 문제 신호어 | Ⅲ 강조 | Ⅳ 강조 |
|:---|:---|:---|:---|
| 포괄형 | "공유 책임 모델을 설명하시오" | 책임 매핑 흐름과 서비스 모델별 변화 | 온프레미스 대비 책임 변화 |
| 요구사항 명시형 | "보안 방안을 제시하시오", "감사 대응을 설계하시오" | RACI, 통제 적용, 증적 수집 절차 | IAM·KMS·로그·CSPM 점검 기준 |

> 요약: 설명형은 책임 경계, 보안형은 고객 책임 통제와 증적 지표 중심으로 전환한다.
