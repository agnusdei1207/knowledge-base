## 미리 알고가기

- 작업 큐: 실행 요청을 워커 스레드가 가져갈 때까지 보관하는 대기열임
- 워커 스레드: 작업 큐에서 요청을 꺼내 실행하고 다시 대기하는 재사용 실행 단위임
- 포화 정책: 큐와 워커가 모두 사용 중일 때 새 작업을 거절·대기·호출자 실행으로 처리하는 규칙임
- 코어·최대 풀 크기: 상시 유지하는 최소 워커 수와 부하 증가 시 늘릴 수 있는 최대 워커 수의 상한임

## 작성 근거(검토용)

- 스레드 풀은 생성 비용 절감보다 작업 큐·워커 재사용·풀 크기·포화 정책으로 설명함
- 요청별 생성과 풀 재사용을 생성·재사용 방식, 동시 실행 상한, 과부하 처리라는 3개 판단축으로 비교함
- API 서버와 배치 실행기를 분리해 큐 대기시간과 활성 워커 수를 직접 검증함

## Ⅰ. 개요
- **정의/개념**: 스레드 풀은 생성한 워커 스레드를 재사용하고 작업 큐와 포화 정책으로 동시 실행 수를 제한하는 스케줄링 구조임
- **배경/필요성**: 요청마다 발생하는 스레드 생성·제거 비용과 동시 실행 자원 상한을 통제하기 위해 워커 재사용 구조가 필요함

## Ⅱ. 특징

- 작업은 큐에서 대기하고 유휴 워커가 준비된 순서대로 가져감
- 워커는 작업 완료 후 종료하지 않고 풀로 돌아가 재사용됨
- 풀 크기가 작으면 큐 대기가, 크면 스택 메모리와 문맥 전환이 증가함
- 큐 용량과 포화 정책은 과부하 시 요청 지연·거절 동작을 결정함

## Ⅲ. 종류 및 비교

| 판단 기준 | 요청별 스레드 생성 | 스레드 풀 |
|:---|:---|:---|
| 생성·재사용 방식 | 요청마다 생성·종료, 생성 비용 반복 | 워커를 미리 생성해 재사용 |
| 동시 실행 상한 | 요청 수에 따라 증가, OS 스케줄러가 대기 | 풀 크기로 제한, 작업 큐에서 대기 |
| 과부하 처리 | 스레드·메모리 무제한 증가 | 큐 용량 초과 시 포화 정책 적용 |

> 요약: 요청별 생성은 요청 수만큼 스레드를 만들고, 스레드 풀은 작업을 큐에 두고 정해진 워커를 재사용함.

## Ⅳ. 구성요소 및 구조
```
[ Client ] -> [ Task Queue ] -> [ Thread Pool ]
                 (FIFO)        | T1 | T2 | T3 |
                               | T4 | T5 | T6 |
```
| 구성요소 | 설명 | 관리 기준 |
| :--- | :--- | :--- |
| 작업 큐 | 실행 대기 중인 Task들을 저장하는 버퍼 | 큐 길이와 대기 시간 |
| 워커 스레드 | 풀 내에서 루프를 돌며 작업을 꺼내 실행하는 스레드 | 활성·유휴 스레드 수 |
| 풀 관리자 | 스레드 개수를 동적으로 조절하고 상태를 감시하는 로직 | 코어·최대 풀 크기 |
> 요약: 작업 큐와 유휴 스레드 집합을 결합하여 동시성을 제어함.

## Ⅴ. 원리 및 절차 흐름도
```
[Request] -> [Queue Submit] -> [Worker Pick] -> [Execute] -> [Idle Return]
```
1. **작업 제출**: 애플리케이션이 실행할 작업을 풀에 전달함
2. **큐·포화 판정**: 유휴 워커가 없으면 큐에 넣고 용량을 넘으면 포화 정책을 적용함
3. **워커 실행**: 유휴 워커가 큐에서 작업을 꺼내 실행함
4. **워커 복귀**: 작업 완료 후 워커가 풀로 돌아가 다음 작업을 기다림
> 요약: 대기 중인 워커를 재사용해 스레드 생성 비용을 줄이며, 큐 대기 시간은 풀 크기와 작업 도착률에 따라 달라짐.

## Ⅵ. 실무 사례

1. API 서버는 CPU·I/O 비율에 맞춰 풀 크기를 설정하고 작업 큐 대기시간과 활성 워커 수를 확인함
2. 배치 실행기는 큐 용량과 거절 정책을 설정하고 거절률과 p99 작업 대기시간을 확인함

## Ⅶ. 결론

- 스레드 풀은 작업 도착률·실행시간·CPU 및 I/O 대기 비율로 워커 수와 큐·포화 정책을 정함
