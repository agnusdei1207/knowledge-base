# 📖 【암기용】 개념 완전 이해

## 한눈에
- **개요**: 실시간 스케줄링(Real-Time Scheduling)은 각 작업이 **정해진 데드라인(마감 시각) 안에 반드시 끝나도록** CPU를 배정하는 스케줄링으로, "얼마나 빨리"가 아니라 "제때(정시성)"를 최우선 목표로 삼는다.
- **왜 필요한가**: 일반 스케줄링(004 참조)은 평균 응답 시간·처리량을 최적화하지만, 에어백 전개·심박 조율기·모터 제어처럼 데드라인을 한 번만 놓쳐도 사고가 나는 시스템에서는 "평균"이 아니라 "최악의 경우에도 마감 보장"이라는 예측 가능성이 필요하다.
- **핵심 직관**: 방송국 편성표와 같다. 매 시각 어떤 프로그램이 몇 분 안에 반드시 나가야 하는지가 정해져 있고, 인기(우선순위)가 아니라 **주기가 짧은 것(RM)** 또는 **마감이 임박한 것(EDF)**을 먼저 내보내야 전체 편성이 펑크 없이 돌아간다.

## 핵심 용어 정리 (내부에 등장하는 것들)

아래 답안용에 나오는 주기·데드라인·이용률 관련 표기를 비유와 함께 먼저 세운다. 맨 위가 이 주제의 상위 핵심 키워드다.

| 용어/표기 | 의미 | 비유·예 |
|:---|:---|:---|
| 실시간 스케줄링 (상위 키워드) | 데드라인 준수를 목표로 CPU를 배정하는 정책 | 마감 시각이 박힌 방송 편성 |
| 주기 태스크 (Periodic Task) | 일정 간격 Tᵢ마다 반복 실행되는 작업 | 매 20ms마다 도는 센서 읽기 |
| 주기 Tᵢ (Period) | 같은 태스크가 다시 시작되는 시간 간격 | "20ms마다 한 번" 할 때 그 20ms |
| 실행 시간 Cᵢ (Computation Time) | 한 번 수행에 필요한 최악 CPU 점유 시간(WCET) | 센서 읽기 1회에 드는 5ms |
| 데드라인 Dᵢ (Deadline) | 그 인스턴스가 반드시 끝나야 하는 마감(보통 Dᵢ=Tᵢ) | 다음 주기 시작 전까지 |
| 이용률 Uᵢ (Utilization) | 태스크가 CPU를 점유하는 비율 = Cᵢ/Tᵢ | 5ms/20ms = 0.25, CPU의 25% 차지 |
| 경성 실시간 (Hard Real-Time) | 데드라인 1회 위반이 곧 시스템 실패 | 에어백·항공 제어 |
| 연성 실시간 (Soft Real-Time) | 가끔 놓쳐도 품질만 저하, 치명적이지 않음 | 영상 스트리밍 프레임 |
| RM (Rate Monotonic) | 주기가 짧을수록 높은 고정 우선순위 부여 | 자주 오는 손님을 늘 먼저 응대 |
| EDF (Earliest Deadline First) | 마감이 가장 임박한 작업에 동적 우선순위 부여 | 마감 임박 원고를 먼저 처리 |
| 고정 우선순위 (Static Priority) | 실행 전 정해져 런타임에 안 바뀜 | 사전에 못 박은 좌석 등급 |
| 동적 우선순위 (Dynamic Priority) | 매 시점 남은 마감에 따라 바뀜 | 그때그때 급한 순으로 재배치 |
| 이용률 한계 (Utilization Bound) | 스케줄 가능 보장을 위한 CPU 총이용률 상한 | 편성표가 안 터지는 최대 방송 밀도 |
| 우선순위 역전 (Priority Inversion) | 저순위가 쥔 락 때문에 고순위가 밀리는 현상 | 급한 사람이 느린 사람 뒤에 묶임 |

## 깊이 이해
- **배경·문제의식**: 범용 스케줄러(FCFS·RR·CFS)는 "언젠가 공평하게" 실행을 보장할 뿐 "몇 ms 안에"를 보장하지 못한다. 자동차·항공·의료처럼 물리 세계와 맞물린 제어에서는 결과가 늦으면 틀린 것과 같다. 그래서 도착 순서·공평성이 아니라 **주기와 마감**을 1급 정보로 삼아, 시스템을 켜기 전에 "모든 데드라인이 항상 지켜지는가"를 수학적으로 검증(스케줄 가능성 분석)하는 이론이 필요해졌다.
- **작동 원리(어떻게+왜)**:
  - RM은 주기 Tᵢ가 짧은 태스크에 높은 우선순위를 **고정** 부여한다. 자주 마감이 오는 작업일수록 여유가 없으므로 먼저 줘야 한다는 직관을 정적으로 못 박은 것이다. 검증은 Liu & Layland 이용률 한계 `ΣCᵢ/Tᵢ ≤ n(2^(1/n)−1)`로 하며, n→∞에서 이 한계는 약 0.693(ln2)으로 수렴한다. 즉 RM은 CPU를 약 69%까지만 채우면 안전이 보장된다.
  - EDF는 매 시점 **남은 데드라인이 가장 가까운** 작업을 고른다. 우선순위가 런타임에 바뀌는 동적 방식이며, 단일 프로세서에서 `ΣCᵢ/Tᵢ ≤ 1`이면(즉 CPU 100%까지) 스케줄 가능한 최적 알고리즘이다.
- **비유**: RM은 "정기 배송 트럭" 편성이다. 배송 주기가 짧은 노선에 늘 우선권을 고정한다. EDF는 "택배 기사"가 손에 든 물건 중 마감이 가장 임박한 것을 매번 다시 골라 배달하는 방식이다. 고정 방식은 관리가 단순하고, 동적 방식은 CPU를 꽉 채워 쓴다.
- **구체 예시**: 태스크 A(C=1ms, T=4ms, U=0.25), B(C=2ms, T=5ms, U=0.4), C(C=1ms, T=10ms, U=0.1). 총 U=0.75. RM 이용률 한계는 n=3일 때 3(2^(1/3)−1)≈0.780. 0.75 ≤ 0.780이므로 RM으로 스케줄 가능. 만약 총 U가 0.85였다면 RM 한계는 넘지만 EDF 한계(1.0)는 안 넘으므로 EDF로는 여전히 가능하다 — CPU 활용도에서 EDF가 유리함을 보여준다.
- **흔한 오해·주의점**: (1) "실시간 = 빠름"이 아니라 "정시성(예측 가능)"이다. 평균은 느려도 데드라인을 늘 지키면 실시간이다. (2) RM 이용률 한계(69%)는 **충분조건**일 뿐이다. 이를 초과해도 정확한 응답시간 분석(RTA)으로 스케줄 가능할 수 있어, 한계 미달만으로 "불가"로 단정하면 안 된다. (3) EDF가 이론상 우월해도, 과부하(U>1) 시 도미노처럼 연쇄 데드라인 실패가 나 예측성이 급락하는 반면 RM은 저순위부터 순차 실패해 열화가 완만하다.

## 연결 개념
- 프로세스 스케줄링 개요(004 참조) — 선점·우선순위·지표 등 일반 배경은 여기에 위임
- 우선순위 역전·우선순위 상속(012 참조) — 실시간에서 데드라인을 깨는 대표 원인과 대응 프로토콜
- 멀티프로세서 스케줄링(030 참조) — 멀티코어에서 실시간 보장이 어려워지는 이유(분할·전역 방식)

# 📝 【답안용】 시험 답안 템플릿

## 핵심 인사이트 (3줄 요약)

> 1. **본질**: 실시간 스케줄링은 주기·데드라인·이용률을 1급 정보로 삼아 최악의 경우에도 마감을 보장하는 예측 가능성 중심의 CPU 배정 정책임.
> 2. **가치**: RM(고정 우선순위)과 EDF(동적 우선순위)는 시스템 가동 전 이용률 한계로 스케줄 가능성을 사전 검증해 제어·안전 시스템의 정시성을 확보함.
> 3. **판단 포인트**: 검증 단순성·열화 안정성이면 RM, CPU 활용 극대화면 EDF이며, 우선순위 역전 통제가 데드라인 보장의 전제임.

| 출제 의도 | 반드시 짚을 핵심 | 감점 회피 포인트 |

| RM·EDF 원리와 스케줄 가능성 검증 | 이용률 한계식(RM 약 0.693, EDF 1.0) | 이용률 한계 판정식 누락 |
| 두 기법의 트레이드오프 판단 | 고정 vs 동적, 과부하 시 열화 양상 | 우선순위 역전 대응 누락 |

> 요약: RM·EDF의 우선순위 부여 규칙과 이용률 한계에 의한 사전 검증, 과부하 열화·우선순위 역전 통제를 함께 제시함.

## Ⅰ. 개요 및 필요성

- 개요: 태스크의 데드라인 준수를 최우선으로 CPU를 배정하는 예측 가능형 스케줄링임
- 배경: 범용 스케줄러는 평균 성능만 최적화해 최악의 경우 마감 시각을 보장하지 못함
- 필요성: 자동차·항공·의료 제어처럼 데드라인 위반이 곧 사고인 시스템은 가동 전 정시성의 수학적 검증이 필수임

## Ⅱ. 구조 및 구성요소

선형 구조도 (태스크 파라미터가 스케줄러로 흐르는 경로):

    태스크 집합 {(Cᵢ, Tᵢ, Dᵢ)} -> 스케줄 가능성 분석(이용률 한계)
      -> 통과 시 우선순위 규칙 설정 (RM: 주기순 고정 / EDF: 마감순 동적)
      -> 런타임 선점 스케줄러가 매 시점 최상위 태스크 실행

| 구성요소 | 역할 | 특이사항 |
|:---|:---|:---|
| 주기 태스크 (Cᵢ,Tᵢ,Dᵢ) | 반복 실행 작업의 시간 파라미터 | Cᵢ는 WCET(최악 실행시간) 기준 |
| 스케줄 가능성 분석 | 가동 전 모든 데드라인 충족 여부 검증 | 이용률 한계·응답시간 분석(RTA) |
| 우선순위 할당 규칙 | RM(고정)·EDF(동적) 중 선택 | RM은 오프라인, EDF는 온라인 결정 |
| 선점형 실행 엔진 | 상위 우선순위 도착 시 즉시 교체 | 선점 지연·문맥 전환 오버헤드 존재 |

> 요약: 시간 파라미터를 먼저 검증하고, RM·EDF 규칙으로 우선순위를 정한 뒤 선점 실행 엔진이 마감 임박·주기 짧은 태스크를 우선 실행함.

## Ⅲ. 동작원리 및 흐름도

선형 흐름도:

    태스크 도착 -> 스케줄러가 우선순위 판정
      -> [RM] 주기 Tᵢ 짧을수록 상위 (실행 전 고정)
      -> [EDF] 남은 데드라인 가까울수록 상위 (매 시점 갱신)
      -> 최상위 태스크 실행 -> 상위 인스턴스 도착 시 선점 -> 데드라인 내 완료

- 1단계 [파라미터 선언]: 각 태스크가 실행시간 Cᵢ·주기 Tᵢ·데드라인 Dᵢ를 사전 등록함
- 2단계 [사전 검증]: 스케줄러가 총이용률 ΣCᵢ/Tᵢ를 RM 한계(n(2^(1/n)−1)) 또는 EDF 한계(1.0)와 비교해 가능성 판정함
- 3단계 [우선순위 부여]: RM은 주기 기준 고정 우선순위를, EDF는 매 시점 최임박 마감 기준 동적 우선순위를 부여함
- 4단계 [선점 실행]: 실행 중 더 급한 인스턴스가 도착하면 CPU를 선점하고, 각 인스턴스를 데드라인 전 완료시킴

> 요약: 태스크가 시간 파라미터를 신고하고, 사전 이용률 검증을 통과하면 RM·EDF 규칙에 따라 선점 실행으로 데드라인을 보장함.

## Ⅳ. 특징

- 정시성 우선: 평균 응답이 아닌 최악의 경우 데드라인 보장을 목표로 하여 예측 가능성을 확보함
- 사전 검증 가능: 이용률 한계식으로 가동 전 스케줄 가능성을 수학적으로 판정함
- RM 고정 우선순위: 주기 기준으로 오프라인 결정되어 구현이 단순하고 런타임 오버헤드가 낮음
- EDF 동적 우선순위: CPU를 100%까지 활용하는 단일 프로세서 최적이나, 매 시점 마감 재계산 비용이 발생함
- 과부하 열화 차이: 과부하 시 RM은 저순위부터 완만히 실패, EDF는 연쇄 실패로 예측성이 급락함

## Ⅴ. 심화 비교 및 적용 판단

RM과 EDF를 우선순위 방식·검증·활용도·과부하 축으로 종합 대조함.

| 구분 | RM (Rate Monotonic) | EDF (Earliest Deadline First) |
|:---|:---|:---|
| 우선순위 | 주기 기준 고정(정적) | 남은 데드라인 기준 동적 |
| 이용률 한계 | n(2^(1/n)−1), n→∞ 시 약 0.693 | 1.0 (단일 프로세서 최적) |
| 구현·오버헤드 | 단순·낮음(오프라인 결정) | 복잡·높음(매 시점 재계산) |
| 과부하 시 거동 | 저순위부터 순차 실패(완만) | 연쇄 데드라인 실패(급락) |

> 요약: 안정적 열화·단순 구현이 중요한 경성 안전 시스템은 RM, CPU 자원 활용 극대화가 목표면 EDF를 채택함.

**리스크·대응:**
- 우선순위 역전 — 저순위가 쥔 공유 락에 고순위가 막혀 데드라인 위반 — 우선순위 상속·상한(PIP·PCP) 프로토콜 적용(012 참조)
- WCET 과소 산정 — 실측보다 낮게 잡아 런타임에 데드라인 초과 — 캐시·파이프라인 고려한 정적 분석·측정 병행으로 여유(마진) 확보
- 과부하 연쇄 실패 — 일시 부하로 EDF가 도미노 붕괴 — 어드미션 컨트롤·과부하 시 저중요 태스크 강등(Mixed-Criticality)

**점검 지표:**
- 성능: 총이용률(ΣCᵢ/Tᵢ), 데드라인 미스율(Deadline Miss Ratio)
- 운영: 최악 응답시간(WCRT), 선점 지연(Preemption Latency)

## Ⅵ. 실무 적용 및 결론

**적용 방안:**
1. RTOS 우선순위 설계: FreeRTOS·VxWorks에서 주기 짧은 제어 태스크에 RM 기반 고정 우선순위를 부여하고 총이용률을 69% 이하로 관리함
2. 우선순위 역전 차단: 공유 자원 접근에 우선순위 상속 뮤텍스(PIP)를 적용해 고순위 태스크의 마감 보장을 확보함
3. 혼합 중요도 운영: 안전 필수(ASIL) 태스크는 경성 RM으로, 편의 기능은 연성으로 분리해 과부하 시 저중요 태스크를 먼저 강등함

**결론:**
- 기술사 판단: 검증 단순성·열화 안정성이 관건인 경성 실시간은 RM을, CPU 활용 극대화가 목표인 연성·부하 밀집 환경은 EDF를 택하되 우선순위 역전 통제를 전제함
- 향후 방향: 멀티코어 확산으로 분할(Partitioned)·전역(Global) EDF와 캐시 간섭을 고려한 혼합 중요도 스케줄링(MCS)이 핵심 과제로 부상함
