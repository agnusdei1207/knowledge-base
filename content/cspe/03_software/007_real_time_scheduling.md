# 📖 【암기용】 개념 완전 이해

## 한눈에
- **개요**: 작업의 논리적 정확성뿐만 아니라 시간적 정확성(Deadlines)을 반드시 엄수해야 하는 시스템의 스케줄링 기법
- **왜 필요한가**: 범용 스케줄러(CFS 등)는 "평균적으로 공평하고 빠른" 것이 목표지만, 항공기 제어나 의료기기는 1초 늦으면 치명적 사고로 직결되므로 "기한 준수"가 유일한 목표여야 한다.
- **핵심 직관**: 공장 컨베이어 벨트나 폭탄 해체와 같다. 폭탄 타이머가 1초 남은 것을 최우선으로 자르지(EDF), 평등하게 번갈아 자르지(RR) 않는다.

## 핵심 용어 정리

| 용어/표기 | 의미 | 비유·예 |
|:---|:---|:---|
| 데드라인 (Deadline) | 작업을 반드시 완료해야 하는 기한 | 폭탄 타이머 종료 시점 |
| 주기 (Period) | 작업이 반복적으로 발생하는 간격 | 1초마다 센서 값 갱신 |
| RM (Rate Monotonic) | 정적 우선순위 스케줄링. 주기가 짧을수록 우선순위가 높음 | 자주 울리는 알람일수록 빨리 끄기 |
| EDF (Earliest Deadline First)| 동적 우선순위 스케줄링. 데드라인이 가장 임박한 작업 우선 | 급한 불(타이머) 먼저 끄기 |
| Hard Real-time | 데드라인 어기면 시스템 실패/치명적 결과 | 에어백 터뜨리기, 미사일 요격 |
| Soft Real-time | 데드라인 어기면 가치 하락이나 시스템 지속 가능 | 동영상 스트리밍 프레임 드랍 |

## 깊이 이해
- **배경·문제의식**: 시분할(Round Robin) 방식은 퀀텀을 나누어 모두에게 CPU를 배분한다. 하지만 실시간 시스템에서는 평균 응답 시간이 중요한 게 아니라, 특정 프로세스가 "무조건 정해진 시간 내에" 끝나야 한다.
- **작동 원리 (RM vs EDF)**:
  - **RM (Rate Monotonic)**: 실행 전에 "이 작업은 주기가 10ms니까 우선순위 1등, 저건 50ms니까 2등"이라고 고정(정적)해버린다. 구현이 쉽고 예측 가능하지만 CPU 활용률 한계가 있다(약 69%).
  - **EDF**: 실행 중에 매번 "지금 당장 기한이 제일 급한 게 누구지?"(동적)를 계산해 우선순위를 계속 바꾼다. 이론상 CPU를 100% 활용할 수 있지만 구현이 복잡하고 과부하 시 도미노 실패 위험이 있다.
- **비유**: 숙제가 여러 개 있을 때, 매일 해야 하는 숙제를 무조건 먼저 하는 것이 RM. 내일 검사받는 숙제를 먼저 하는 것이 EDF.
- **흔한 오해·주의점**: "실시간(Real-time) = 초고속(Fast)"이 아니다. 실시간은 "예측 가능성(Predictability)"을 의미한다. 1초 뒤에 결과를 내기로 했으면, 0.1초 만에 내도 안 되고 정확히 기한 내에 내는 보장이 핵심이다.

## 연결 개념
- 스케줄링 (004 참조) — 범용 스케줄링과의 목표 차이
- 교착상태 (009 참조) — 실시간 환경에서의 우선순위 역전 문제
- CFS (006 참조) — 리눅스의 SCHED_FIFO/SCHED_RR과의 관계

# 📝 【답안용】 시험 답안 템플릿

## 핵심 인사이트 (3줄 요약)

> 1. **본질**: 실시간 스케줄링은 연산 결과의 논리적 정확성뿐 아니라 응답의 시간적 정확성(데드라인 준수)을 보장하는 운영체제 핵심 제어 기법이다.
> 2. **가치**: 주기/비주기적 태스크 환경에서 스케줄링 가능성(Schedulability)을 수학적으로 증명하여 시스템 붕괴를 사전 차단한다.
> 3. **판단 포인트**: 안정성·예측성을 중시하면 정적 방식인 RM을, CPU 활용률 극대화가 필요하면 동적 방식인 EDF를 선택한다.

## 출제 의도 및 답안 포인트

| 출제 의도 | 반드시 짚을 핵심 | 감점 회피 포인트 |
|:---|:---|:---|
| 실시간 시스템의 목표 특성 이해 | Hard vs Soft 구분, 데드라인 준수율 100% | 빠른 처리(Fast)와 실시간(Real-time) 혼동 |
| 정적/동적 실시간 스케줄링 알고리즘 비교 | RM(주기 기반 정적) vs EDF(마감일 기반 동적) | 알고리즘 작동 원리 생략 후 장단점만 서술 |
| 스케줄링 한계 극복 방안 | 스케줄링 가능성 테스트(Utilization Bound), 우선순위 역전 방지 | 우선순위 역전(Priority Inversion) 누락 |

> 요약: 범용 OS와 달리 실시간 스케줄링은 CPU 자원의 "수학적 사전 검증"을 통해 데드라인 엄수를 담보하는 것이 핵심이다.

---

## Ⅰ. 개요 및 필요성

- 개요: 시스템에 주어진 다수의 태스크들이 각각의 정해진 시간 제약(Deadline) 내에 실행을 완료하도록 CPU를 할당하는 정책
- 배경: 범용 스케줄러(CFS, RR 등)는 공평성과 처리량에 집중하여 특정 프로세스의 최악의 응답 시간(Worst-case execution time)을 보장하지 못함
- 필요성: 자율주행, 우주·항공, 의료기기 등 기한 초과가 치명적 장애로 직결되는 환경(Hard Real-time)에서 결정론적(Deterministic) 실행 보장 필수

---

## Ⅱ. 구조 및 구성요소

```text
태스크 모델링 (C: 실행시간, P: 주기/데드라인)
   -> 스케줄링 가능성 테스트 (Utilization U = Σ(C_i/P_i) ≤ 임계치)
      |-- [Pass] -> RM / EDF 스케줄러 투입 -> 성공 보장
      |-- [Fail] -> 태스크 거부 (Admission Control)
```

| 구성요소 | 역할 | 특이사항 |
|:---|:---|:---|
| 실행 시간 (C, Execution Time) | 해당 태스크를 처리하는 데 필요한 총 CPU 연산 시간 | Worst-case 기준 산정 |
| 주기 (P, Period) | 태스크가 반복적으로 시스템에 유입되는 간격 | 주기 = 데드라인 가정 |
| RM (Rate Monotonic) | 주기가 짧은 태스크에 고정된 높은 우선순위 부여 | 정적 우선순위 알고리즘 |
| EDF (Earliest Deadline First)| 현재 시점에서 데드라인이 가장 가까운 태스크 우선 | 동적 우선순위 알고리즘 |

> 요약: 실시간 시스템은 실행 전 태스크들의 CPU 점유율(U)을 계산해 데드라인 준수 가능성을 사전에 검증한다.

---

## Ⅲ. 동작원리 및 흐름도

```text
새 태스크 도달 -> [분기: RM vs EDF 정책 확인]
  -> [RM] 사전 정의된 고정 우선순위 검사 (주기 기준)
  -> [EDF] 현재 런큐 내 태스크들의 잔여 데드라인 동적 계산
  -> 우선순위 재산정 -> [선점] 실행 중인 태스크보다 높으면 뺏음
```

- 1단계 [태스크 진입]: 주기적(Periodic) 또는 비주기적 이벤트에 의해 태스크가 Ready 큐에 도달
- 2단계 [우선순위 판정]: RM은 미리 정해진 `1/주기` 비율로 순위를 매기고, EDF는 현재 시점 기준 `절대 마감일`을 계산하여 비교
- 3단계 [CPU 선점]: 우선순위가 더 높은 태스크가 나타나면 즉시 문맥 전환을 수행하여 CPU를 선점(Preemption)
- 4단계 [실행 및 종료]: 태스크 완료 시 원래 선점 당했던 차순위 태스크로 신속히 복귀

> 요약: 실시간 스케줄링은 철저한 선점형 기반으로 동작하며, 누가 1순위인지 평가하는 기준(주기 vs 마감일)이 알고리즘을 가른다.

---

## Ⅳ. 특징

- RM 한계 (CPU 활용률): 태스크가 늘어날수록 보장 가능한 임계 CPU 활용률이 약 69.3%로 수렴하여 자원 낭비가 존재함
- EDF 장점 (활용률 100%): 동적 우선순위 조정을 통해 이론적으로 CPU를 100% 꽉 채워서 스케줄링 가능
- EDF 한계 (도미노 현상): 과부하(Overload) 발생 시 우선순위가 계속 역전되며 모든 태스크가 데드라인을 놓치는 연쇄 실패 위험성

> 요약: 이론적 효율성은 EDF가 앞서나, 오버헤드가 적고 실패 시 예측이 가능한 RM이 산업계에서는 더 널리 쓰인다.

---

## Ⅴ. 심화 비교 및 적용 판단

| 비교 축 | Rate Monotonic (RM) | Earliest Deadline First (EDF) | 선택 기준 |
|:---|:---|:---|:---|
| 우선순위 할당 | 정적 (고정됨) | 동적 (매 순간 변함) | 구현 복잡성 수용 범위 |
| 스케줄링 임계치 | 약 69.3% (n→∞) | 100% (이론적 최대치) | 하드웨어 자원 여유도 |
| 과부하 시 동작 | 저우선순위만 실패 (예측 가능) | 모두 실패 가능 (도미노 효과) | 장애 허용(Fault Tolerance) 기준 |

> 요약: 안정성과 예측 가능성이 치명적으로 중요하면 RM을, CPU 활용률 극대화가 필수적이면 EDF를 채택한다.

**리스크·대응 (기본은 불릿):**
- 우선순위 역전(Priority Inversion): 저우선순위 태스크가 락(Lock)을 쥐고 있어 고우선순위가 대기하는 현상 → 우선순위 상속(Priority Inheritance) 또는 우선순위 올림(Priority Ceiling) 프로토콜 적용 (지표: 최대 블로킹 시간 제한)
- 컨텍스트 스위치 오버헤드: 동적 계산(EDF) 시 스위칭 오버헤드로 인한 데드라인 초과 → 태스크 실행 시간(C) 산정 시 스위칭 오버헤드 최악치 포함하여 보수적(Worst-case) 설계

**도입 후 점검 지표 (기본은 불릿):**
- 성능/효율: Deadline Miss Ratio (Hard 실시간은 0% 필수)
- 품질/운영: WCET(Worst-Case Execution Time) 초과 발생 건수

---

## Ⅵ. 실무 적용 및 결론

**적용 방안 3개 (필수 — 단계별 또는 항목별):**
1. 하드웨어 타이머 최적화: 범용 타이머 틱(Tick) 대신 고정밀 타이머(HPET)를 사용하여 마이크로초(us) 단위 선점 해상도 확보
2. 혼합 임계치(Mixed-Criticality) 스케줄링: Hard Real-time 태스크와 Soft Real-time 태스크를 분리해, 과부하 시 Soft 태스크를 즉시 드랍하여 Hard 시스템 보호
3. 리눅스 환경 구성: PREEMPT_RT 패치를 적용하고, 실시간 태스크를 `SCHED_FIFO` 클래스(우선순위 99)로 고정하여 커널 선점성 극대화

**결론 (2줄):**
- 기술사 판단: 실시간 시스템 설계의 본질은 가장 빠른 CPU를 고르는 것이 아니라 최악의 상황(Worst-case)을 수학적으로 제어해 예측성을 100% 달성하는 것이다.
- 향후 방향: 멀티코어 환경 확산에 따라 단일 코어 기반의 RM/EDF 한계를 극복하기 위한 파티셔닝(Partitioned) 및 글로벌(Global) 실시간 스케줄링 기법으로 진화 중이다.
