# 📖 【암기용】 개념 완전 이해

## 한눈에
- **정의**: 작업의 처리 결과가 정확해야 할 뿐만 아니라, 정해진 시간(**Deadline**) 내에 결과가 나와야 하는 시스템을 위한 스케줄링.
- **핵심 직관**: 에어백 제어 시스템. 사고가 나면 0.1초 안에 에어백이 터져야 함. 1초 뒤에 터지는 에어백은 아무리 완벽하게 터져도 '실패'임.
- **분류**:
    - **Hard Real-time**: 데드라인을 어기면 시스템 전체가 파멸 (예: 비행기 제어, 원자로).
    - **Soft Real-time**: 데드라인을 좀 어겨도 품질만 저하 (예: 동영상 스트리밍, 온라인 게임).

## 깊이 이해
- **결정론적 수행 (Deterministic)**: 실시간 시스템은 '운 좋으면 빠르고 운 나쁘면 느린' 것이 아니라, '최악의 상황에서도 반드시 이 시간 안에 끝남'을 보장해야 함.
- **Rate Monotonic (RM)**: 정적 우선순위 방식. **주기가 짧을수록** (자주 발생할수록) 높은 우선순위를 줌. 구현이 단순하지만 CPU 이용률이 약 69%($n(2^{1/n}-1)$)를 넘으면 데드라인 보장이 안 될 수 있음.
- **Earliest Deadline First (EDF)**: 동적 우선순위 방식. **데드라인이 가장 임박한** 놈에게 우선순위를 줌. 이론적으로 CPU 이용률을 100%까지 쓸 수 있지만 구현이 복잡함.
- **우선순위 역전 (Priority Inversion)**: 낮은 우선순위 애가 락(Lock)을 잡고 있어서, 높은 애가 못 실행되는 치명적인 문제. (화성 탐사선 패스파인더의 사고 원인)

## 연결 개념
- **우선순위 역전 해결 (011 연계)**: Priority Inheritance (상속) 또는 Priority Ceiling (최고조).
- **인터럽트 (002)**: 실시간성을 보장하려면 커널의 인터럽트 지연(Latency)이 극도로 낮아야 함.
- **임베디드 OS (RTOS)**: 실시간 스케줄링을 최우선으로 설계된 OS.

# 📝 【답안용】 시험 답안 템플릿

## 핵심 인사이트 (3줄 요약)
> 1. **본질**: 시간 제약 조건(Deadline)의 충족 여부가 시스템의 성패를 결정짓는 **결정론적(Deterministic) 성능 보장** 스케줄링임.
> 2. **기술적 핵심**: 주기에 기반한 정적 스케줄링(**RM**)과 데드라인에 기반한 동적 스케줄링(**EDF**)의 트레이드오프를 이해하고 최악 실행 시간(WCET)을 분석해야 함.
> 3. **장애 대응**: 실시간성 확보의 최대 장애물인 **우선순위 역전** 현상을 방지하기 위해 우선순위 상속(Inheritance) 등의 프로토콜 적용이 필수적임.

## Ⅰ. 시간의 정확성이 곧 품질, 실시간 스케줄링 개요
- **정의**: 프로세스의 실행 완료 시점이 미리 정의된 시간적 제약(Deadline) 내에 있음을 보장하는 알고리즘.
- **주요 특징**: 예측 가능성(Predictability), 높은 응답성, 마감시간 준수 엄격성.

## Ⅱ. 실시간 스케줄링의 양대 산맥: RM vs EDF

### 1. RM (Rate Monotonic) - 정적(Static) 방식
- **원리**: 각 작업의 발생 주기(Period)가 짧을수록 높은 우선순위 부여.
- **장점**: 구현이 간단, 오버헤드 적음.
- **단점**: CPU 이용률 상한선 존재 ($U = \sum \frac{C_i}{T_i} \le n(2^{1/n}-1)$, $n \to \infty$ 일 때 약 0.69).

### 2. EDF (Earliest Deadline First) - 동적(Dynamic) 방식
- **원리**: 현재 시점에서 마감시간(Deadline)이 가장 가까운 작업에 최고 우선순위 부여.
- **장점**: CPU 이용률을 이론상 100%까지 활용 가능.
- **단점**: 마감시간이 계속 변하므로 관리 오버헤드 발생, 과부하 시 연쇄적 데드라인 실패 위험.

## Ⅲ. RM과 EDF 기술적 상세 비교

| 구분 | Rate Monotonic (RM) | Earliest Deadline First (EDF) |
|:---:|:---|:---|
| **우선순위 부여** | 실행 전 결정 (정적) | 실행 중 결정 (동적) |
| **판단 기준** | 주기의 역수 (Frequency) | 마감 시간 (Deadline) |
| **CPU 이용률 상한** | 약 69% (안전성 중심) | 100% (효율성 중심) |
| **구현 복잡도** | 낮음 (범용 OS 가능) | 높음 (RTOS 특화) |
| **적합 환경** | 주기적 작업 위주 시스템 | 주기/비주기 혼재 시스템 |

## Ⅳ. 실시간 시스템의 치명적 결함: 우선순위 역전 (Priority Inversion)

### 1. 현상 (ASCII Diagram)
```text
High (H)   : ───── (Wait Lock L) ────────────────── (Execute) ──▶
Medium (M) :              └────── (Preempt M) ─────┘
Low (L)    : ── (Hold Lock L) ──┘
```
- 낮은 순위(L)가 공유 자원 락을 쥔 채, 중간 순위(M)에게 CPU를 뺏겨, 높은 순위(H)가 영원히 대기하는 현상.

### 2. 해결 방안
- **Priority Inheritance (우선순위 상속)**: H가 대기 중이면 L의 우선순위를 임시로 H만큼 높여서 빨리 끝내게 함.
- **Priority Ceiling (우선순위 최고조)**: 공유 자원에 최고 우선순위를 설정하여 아예 중간 순위가 선점 못 하게 함.

## Ⅴ. 실시간 성능 평가의 핵심 지표
- **WCET (Worst Case Execution Time)**: 최악의 실행 시간 분석. 실시간 보장의 기준.
- **Jitter**: 응답 시간의 변동성. 낮을수록 안정적.
- **Interrupt Latency**: 인터럽트 발생 후 서비스 루틴 시작까지의 지연 시간.
- **Context Switch Time**: 문맥 전환에 걸리는 시간. RTOS에서는 이 시간을 최소화함.

## Ⅵ. 기술사 관점의 결론 및 제언
- 실시간 스케줄링은 **'빠른 것(Fast)'이 아니라 '제시간(On-time)'**에 수행되는 것이 핵심임.
- **설계 제언**: 자율주행, 로봇 제어 등 미션 크리티컬 시스템에서는 범용 Linux 대신 **Preempt-RT 패치**가 적용된 커널이나 **FreeRTOS, QNX** 같은 전용 RTOS를 사용하여 비결정론적 요소를 제거해야 함.
