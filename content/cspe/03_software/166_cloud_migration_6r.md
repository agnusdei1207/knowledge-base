# 📖 【암기용】 개념 완전 이해

> 목적: 클라우드 마이그레이션 6R을 처음 봐도 완벽히 이해하게 만든다. 시험 답안 양식이 아니라, 이해를 위한 친절한 설명이다.

## 한눈에
- **개요**: 클라우드 마이그레이션 6R은 **클라우드 마이그레이션**(기존 시스템의 클라우드 이전) 전략을 업무별로 고르는 **6가지 이전 방식 분류 체계**다.
- **왜 필요한가**: 모든 시스템을 하나의 방식(예: 그대로 옮기기)으로 이전하면 어떤 업무는 비용이 과다해지고 어떤 업무는 일정이 지나치게 길어진다.
- **핵심 직관**: 이사할 때 짐마다 그대로 포장, 부품만 교체, 새로 구매, 버리기, 보관하기가 다르듯, 시스템도 업무 특성에 따라 이전 방식이 다르다.

## 핵심 용어 정리 (내부에 등장하는 것들)

| 용어 | 의미 | 비유 |
|:---|:---|:---|
| 클라우드 마이그레이션 | 온프레미스·레거시 시스템을 클라우드 환경으로 옮기는 전체 활동 — 6R은 그 안의 세부 전략 분류 | 이사 전체 프로젝트 |
| Rehost (Lift & Shift) | 구조 변경 없이 그대로 VM을 옮기는 방식 | 가구 그대로 트럭에 실어 옮기기 |
| Replatform (Lift & Reshape) | 핵심 구조는 유지하되 일부를 관리형 서비스로 바꾸는 방식(예: 자체 DB→관리형 DB) | 다리만 새 다리로 교체 |
| Repurchase | 기존 시스템을 버리고 SaaS 등 상용 제품으로 대체하는 방식 | 낡은 가구 버리고 새 가구 구매 |
| Refactor (Re-architect) | 클라우드 네이티브 구조(MSA 등)로 근본적으로 다시 설계하는 방식 | 맞춤 가구 제작 |
| Retire | 더 이상 쓰지 않는 시스템을 폐기하는 방식 | 안 쓰는 짐 버리기 |
| Retain | 규제·기술적 제약으로 지금은 옮기지 않고 그대로 두는 방식 | 당장 옮기지 않고 창고에 보관 |
| CMDB | 시스템·자산과 그 의존관계를 기록한 자산 목록 DB | 이삿짐 목록표 |
| Migration Wave | 여러 애플리케이션을 의존성·위험도로 묶어 순차 이전하는 단위 | 이사를 한 번에 안 하고 방 단위로 나눠 하기 |
| 컷오버(Cutover) | 실제 운영 트래픽을 신규(클라우드) 환경으로 전환하는 순간 | 이사 완료 후 새 주소로 우편물 전환 |
| Dual Run | 이전 전 신·구 시스템을 잠시 동시에 운영해 결과를 비교 검증하는 방식 | 이사 후에도 잠시 옛집 전화를 유지해 비교 |

## 깊이 이해

### 6R을 어떻게 판별하나 — 판단 기준을 순서로
- 판별 질문 순서: ① 이 업무가 아직 필요한가? (아니오 → Retire) ② 규제·기술 제약으로 지금 옮길 수 없는가? (예 → Retain) ③ 시중에 대체 가능한 SaaS가 있는가? (예 → Repurchase) ④ 구조를 바꿀 시간·예산이 있고 기술부채 해소가 목표인가? (예 → Refactor) ⑤ 관리형 전환만으로 이득이 큰가? (예 → Replatform) ⑥ 그 외 단순 이전은 Rehost로 판단한다.
- 워크드 예(자산 100개 포트폴리오): 사용 빈도 낮은 배치 시스템 15개는 Retire, 규제상 국내 폐쇄망 유지가 필요한 금융 DB 10개는 Retain, 표준 그룹웨어·CRM 20개는 Repurchase(SaaS 전환), 확장성이 중요한 핵심 주문 시스템 10개는 Refactor(MSA), 자체 Oracle DB 20개는 Replatform(관리형 DB로), 나머지 단순 VM 25개는 Rehost로 분류하는 식이다.

### 왜 순위가 아니라 선택지인가 — 비용·일정 트레이드오프
- Rehost는 이전 기간이 짧고(시스템당 수 주) 초기 비용이 낮지만, 구조를 바꾸지 않아 클라우드의 오토스케일링·서버리스 이점을 못 살려 운영비가 오히려 20~30% 늘어날 수 있다(over-provisioning).
- Refactor는 MSA·서버리스로 재설계해 장기 운영비와 확장성이 개선되지만, 초기 개발 기간이 6개월~1년 이상 걸리고 실패 리스크(품질 저하, 일정 지연)가 크다.
- 그래서 일정이 급한 핵심 업무에 무조건 Refactor를 쓰면 리스크가 크고, 여유 있고 기술부채가 큰 업무를 Rehost만 하면 클라우드 전환의 이점(비용 최적화)을 놓친다 — 업무 중요도·일정·예산을 함께 봐야 한다.

### 컷오버 검증 — RTO/RPO로 보는 전환 리스크
- 워크드 예: 주문 시스템을 Refactor로 전환한 뒤 실제 트래픽을 옮기는 컷오버 시, DNS 전환에 걸리는 시간(TTL 설정에 따라 수 분~1시간)과 데이터 마이그레이션 완료 시점 사이에 신규 주문이 유실될 수 있다. 이를 막기 위해 Dual Run(신·구 시스템 동시 운영, 결과 비교) 후 트래픽을 점진 전환(예: 10%→50%→100%)하고, 문제 시 즉시 롤백하는 절차를 사전에 리허설한다. 목표 기준으로 RTO 1시간, 데이터 유실 허용 RPO 15분 이하를 세운다.

## 연결 개념
- 하이브리드 클라우드 — Retain과 Rehost가 공존하는 이전 중간 상태
- FinOps — Rehost 이후 비용 우측정과 예약 구매 판단
- 마이크로서비스 아키텍처 — Refactor의 대표 목표 구조

## Ⅰ. 개요 및 필요성

- 개요: 클라우드 마이그레이션 6R은 애플리케이션별 이전 전략 프레임임.
- 배경: 기업 시스템은 업무 중요도, 기술부채, 데이터 민감도, 라이선스 제약이 다르다.
- 필요성: Rehost, Replatform, Refactor 등 6R 기준으로 애플리케이션 포트폴리오 전환 방식을 결정한다.

---

## Ⅱ. 구조 및 구성요소

```text
Application Portfolio -> Assessment -> 6R Decision
                      -> Migration Wave -> Test/Cutover/Rollback
                      +-> Cost/Security/Operation Control
```

| 구성요소 | 역할 | 특이사항 |
|:---|:---|:---|
| Assessment | 애플리케이션, 의존성, 데이터, 비용 평가 | CMDB, APM, 인터뷰 |
| 6R 결정 | 업무별 이전 전략 선택 | Rehost, Replatform, Repurchase, Refactor, Retire, Retain |
| Migration Wave | 이전 묶음과 일정 수립 | 의존성·위험도 기반 그룹화 |
| 검증·전환 | 테스트, 컷오버, 롤백 | RTO/RPO, 데이터 검증 |

> 요약: 6R은 애플리케이션 평가 결과를 이전 전략과 웨이브 실행으로 연결하는 구조다.

## Ⅲ. 동작원리 및 흐름도

```text
자산 식별 -> 의존성/비용/위험 평가 -> 6R 배정
-> 웨이브 계획 -> 마이그레이션 실행 -> 테스트/컷오버 -> 운영 안정화
```

| 단계 | 처리 내용 | 검증 기준 |
|:---:|:---|:---|
| 1 | 자산과 의존성 수집 | CMDB 정확도 95% 이상 |
| 2 | 6R 전략 배정 | 업무 중요도, 변경 난이도, 비용 |
| 3 | 이전과 데이터 동기화 | RPO 15분 이하, 검증 SQL |
| 4 | 컷오버와 롤백 | RTO 1시간, 롤백 절차 승인 |

> 요약: 마이그레이션은 자산 평가, 6R 배정, 웨이브 실행, 컷오버 검증 순서로 진행된다.

## Ⅴ. 심화 비교 및 적용 판단

| 비교 축 | Rehost/Replatform | Repurchase/Refactor | Retire/Retain |
|:---|:---|:---|:---|
| 적용 조건 | 단기 이전, 구조 변경 최소화 | 기능 대체 또는 구조 개선 필요 | 미사용, 규제, 이전 보류 |
| 비용/성능 | 이전 비용 낮음, 운영비 최적화 필요 | 초기 비용 높음, 장기 기술부채 감소 | 유지 비용과 보안 패치 검토 |
| 운영/위험 | 클라우드 비용 증가 가능 | 일정 지연과 품질 리스크 | 보류 시스템 연계 유지 필요 |

> 요약: 6R 선택은 단기 일정과 장기 기술부채 사이의 균형으로 판단한다.

| 리스크 | 원인 | 대응 방안 | 확인 지표 |
|:---|:---|:---|:---|
| 의존성 누락 | 인터페이스·배치 식별 부족 | APM, 트래픽 분석, CMDB 정합 | 미식별 연계 0건 |
| 비용 초과 | Rehost 후 과다 자원 | rightsizing, 예약 인스턴스, 스케줄링 | 월 비용 10% 이내 |
| 컷오버 실패 | 데이터 정합성·DNS 전환 오류 | 리허설, dual run, 롤백 절차 | 컷오버 성공률 95% 이상 |

> 요약: 마이그레이션 리스크는 의존성, 비용, 컷오버에서 발생하며 사전 리허설과 비용 통제로 관리한다.

| 점검 항목 | 목표 기준 | 측정 방법 |
|:---|:---|:---|
| 자산 평가 | 포트폴리오 분류 100%, CMDB 정확도 95% | discovery, 인터뷰 |
| 전환 품질 | RTO 1시간, RPO 15분, 장애 0건 | 컷오버 리포트 |
| 비용 | 월 비용 편차 10% 이하, 예약 적용률 60% 이상 | Billing Export, FinOps |

> 요약: 6R 성공 여부는 분류 완성도, 전환 품질, 비용 예측 정확도로 판정한다.

## Ⅵ. 실무 적용 및 결론

**적용 방안 3개 (필수 - 단계별 또는 항목별):**
1. 포트폴리오 평가: CMDB, APM, 인터뷰로 애플리케이션 100%를 6R로 분류하고 의존성 맵 작성
2. 웨이브 실행: 저위험 Rehost부터 시작해 Replatform, Refactor 순서로 이전하고 웨이브당 롤백 runbook 승인
3. 운영 최적화: 이전 후 30일 내 rightsizing, 예약 구매, 백업 정책, 보안 기준선 점검 수행

**결론 (2줄):**
- 기술사 판단: 일정이 지배하면 Rehost/Replatform, 기술부채 해소가 목적이면 Refactor, 표준 업무는 Repurchase를 선택함
- 향후 방향: 6R은 자동 discovery, migration factory, IaC 기반 반복 전환 체계로 고도화됨
