## 미리 알고가기

- Rehost는 애플리케이션 구조를 유지한 채 실행 인프라를 클라우드로 옮김
- Replatform은 구조 변경을 제한하고 DB·런타임 등 일부 플랫폼을 관리형 서비스로 바꿈
- Repurchase는 기존 제품을 다른 상용 제품이나 SaaS로 대체함
- Refactor는 애플리케이션 구조와 코드를 클라우드 네이티브 방식으로 재설계함
- Retain은 규제·의존성·투자 시점 때문에 기존 환경에 유지함
- Retire는 업무 가치가 없거나 중복된 애플리케이션을 종료함
- 7R 체계는 6R에 가상화 환경을 그대로 옮기는 Relocate를 별도 전략으로 추가함
- 이전 웨이브는 의존성과 변경 시간대를 기준으로 함께 전환할 애플리케이션을 묶은 단위임

## 작성 근거(검토용)

- 6R은 이전 기법 나열이 아니라 업무 가치·변경 범위·의존성에 따른 포트폴리오 판정 기준으로 설명함
- 여섯 전략의 조치·적합 조건·변경 범위·주요 위험을 한 표에서 구분하고 이전 절차로 연결함
- 제목부터 결론까지 5회 전수 검수하여 전략 간 경계와 사례의 단일 판단 맥락을 확인함

## Ⅰ. 개요

- **정의/개념**: 6R은 업무 가치·기술 의존성·변경 범위로 이전·대체·유지·종료 방식을 분류하는 클라우드 전환 체계임
- **배경/필요성**: 애플리케이션마다 이전 목적과 변경 위험이 다르므로 포트폴리오별 전환 방식을 정할 기준이 필요함

## Ⅱ. 특징

- 애플리케이션 단위로 업무 가치와 기술 상태를 평가한 뒤 하나의 주 전략을 지정함
- Rehost에서 Refactor로 갈수록 코드·데이터·운영 방식의 변경 범위가 늘어남
- Retain·Retire도 이전 제외가 아니라 비용·규제·의존성을 반영한 포트폴리오 결정임
- 전략 결과를 의존성 순서와 결합해 이전 웨이브·검증·롤백 범위를 정함

## Ⅲ. 전략별 비교

| 전략 | 핵심 조치 | 적합 조건 | 변경 범위 | 주요 위험 |
|:---|:---|:---|:---|:---|
| Rehost | VM·서버 구성을 유사한 클라우드 인프라로 이전 | 데이터센터 종료 일정 준수가 우선 | 인프라 중심 | 기존 운영 문제와 비용 구조가 유지 |
| Replatform | DB·런타임 등 일부 계층을 관리형 서비스로 전환 | 제한된 변경으로 운영 부담 감소 필요 | 플랫폼 설정과 연동 | 호환성·성능 특성 차이 발생 |
| Repurchase | 기존 제품을 SaaS·상용 제품으로 교체 | 표준 기능으로 기존 업무를 대체할 수 있음 | 제품·데이터·업무 절차 | 기능 차이와 데이터 전환 오류 발생 |
| Refactor | 구조·코드·배포를 클라우드 네이티브로 재설계 | 확장·배포·복구 구조 개선이 목적 | 애플리케이션 전반 | 기간·비용·회귀 결함 증가 |
| Retain | 기존 환경에서 운영하고 재검토 시점을 지정 | 규제·장비·선행 의존성 때문에 이전할 수 없음 | 없음 | 노후화 비용과 기술 부채 지속 |
| Retire | 데이터 보존 후 서비스와 인프라를 종료 | 업무 가치가 없거나 기능이 중복 | 제거 | 숨은 사용자·연동 누락 발생 |

> 요약: 6R은 변경 범위·적합 조건·주요 위험으로 이전·대체·유지·종료 방식을 판정함.

## Ⅳ. 구성요소 및 구조

| 구성요소 | 역할 |
|:---|:---|
| 애플리케이션 목록 | 소유자·사용자·기술 스택·운영 비용을 식별함 |
| 의존성 지도 | 호출·데이터·인증·배치·장비 연결을 파악함 |
| 평가 기준 | 업무 가치·규제·변경 난이도·운영 위험을 점수화함 |
| 6R 결정 기록 | 선택 전략과 제외 전략의 사유를 애플리케이션별로 남김 |
| 이전 웨이브 | 의존성과 공통 플랫폼을 기준으로 전환 순서를 묶음 |
| 검증·롤백 계획 | 데이터 정합성·기능·성능·복귀 조건을 정의함 |

```text
애플리케이션 목록 -> 의존성 분석 -> 6R 판정 -> 이전 웨이브 -> 전환·검증
```

> 요약: 자산과 의존성 분석 결과가 6R 판정과 이전 순서의 입력이 됨.

## Ⅴ. 원리 및 절차 흐름도

```text
자산 식별 -> 가치·의존성 평가 -> 6R 결정 -> 웨이브 실행 -> 검증·종료
```

1. **자산 식별**: 애플리케이션·서버·데이터·소유자와 사용 현황을 연결함
2. **가치·의존성 평가**: 업무 중요도와 규제·장비·연동 제약을 확인함
3. **6R 결정**: 변경 범위와 기대 가치를 대조해 주 전략과 재검토 조건을 정함
4. **웨이브 실행**: 선행 시스템과 공통 플랫폼부터 전환하고 데이터·트래픽을 이동함
5. **검증·종료**: 기능·정합성·성능을 확인한 뒤 원본 시스템을 종료하거나 롤백함

> 요약: 업무 가치와 의존성으로 6R을 정하고 선행 관계에 따라 전환·검증함.

## Ⅵ. 실무 사례

1. 사내 웹 시스템은 Replatform으로 관리형 DB를 적용하고 전환 중단 시간·오류 건수를 확인함
2. 중복 그룹웨어는 Repurchase로 SaaS에 통합하고 데이터 누락 건수·사용자 전환율을 확인함

## Ⅶ. 결론

- 6R은 애플리케이션별 업무 가치와 변경 위험을 대조해 이전·대체·유지·종료 전략을 선택해야 함
