## Ⅰ. 개요
- **정의**: 고급 언어 소스 코드를 기계어로 변환하는 번역기의 내부 처리 단계 구조
- **배경/필요성**: 번역 과정을 단계별로 분리해야 각 단계를 독립적으로 최적화·확장할 수 있음
- **비유**: 외국어 문서를 번역할 때 단어 분리 → 문법 파악 → 의미 해석 → 번역문 작성 순서와 유사함

| 출제 의도 | 반드시 짚을 핵심 | 감점 회피 포인트 |
|:---|:---|:---|
| 컴파일러 단계별 역할 구분 | 전단부(분석)와 후단부(합성) 분리 | 각 단계의 입출력 산출물을 명확히 구분 |

> 요약: 소스 코드를 단계별로 분석·합성하여 기계어로 변환하는 번역기 구조임

## Ⅱ. 구성요소
```text
Source Code
    |
    v
[Front-End: 분석]
  Lexical -> Syntax -> Semantic
    |
    v
[Middle: 최적화]
  IR Optimization
    |
    v
[Back-End: 합성]
  Code Generation -> Target Code
```

| 구성요소 | 설명 | 비유 |
|:---|:---|:---|
| Lexical Analyzer | 소스를 토큰 단위로 분리(178 참조) | 문장에서 단어 분리 |
| Syntax Analyzer | 토큰 열의 문법 구조를 파스 트리로 구성(179 참조) | 단어의 문법 관계 파악 |
| Semantic Analyzer | 타입 검사·스코프 검증 등 의미 적합성 판단(180 참조) | 문맥상 의미 확인 |
| IR Optimizer | 중간 표현(IR)에서 불필요한 연산 제거·루프 최적화 수행 | 번역문 다듬기 |
| Code Generator | 최적화된 IR을 대상 기계어·어셈블리로 변환 | 최종 번역문 출력 |
| Symbol Table | 식별자 이름·타입·스코프 정보를 전 단계에서 공유하는 자료구조 | 용어 사전 |

> 요약: 전단부(분석 3단계)·중간부(최적화)·후단부(코드 생성)로 구성된 파이프라인 구조임

## Ⅲ. 절차
```text
Source -> Tokens -> Parse Tree -> Annotated Tree -> IR -> Optimized IR -> Target Code
```
- 1단계: 어휘 분석기가 소스 코드를 토큰 열로 분리함
- 2단계: 구문 분석기가 토큰 열을 문법 규칙에 따라 파스 트리로 구성함
- 3단계: 의미 분석기가 타입·스코프를 검증하고 IR을 생성한 뒤 최적화를 수행함
- 4단계: 코드 생성기가 최적화된 IR을 대상 아키텍처의 기계어로 변환함

> 요약: 토큰화 → 파싱 → 의미 검증·최적화 → 코드 생성의 순차 파이프라인으로 동작함

## Ⅳ. 문제점
- 단계 간 의존성: 전단부 오류가 후속 단계로 전파되어 오류 메시지 정확도가 저하됨
- 최적화 비용: 고급 최적화 적용 시 컴파일 시간이 증가하여 개발 생산성이 저하됨
- 다중 타겟 지원 부담: 아키텍처별 코드 생성기를 별도 구현해야 하므로 유지보수 비용이 증가함

> 요약: 오류 전파·최적화 시간·다중 타겟 유지보수가 주요 과제임

## Ⅴ. 개선방안
1. 단기: 단계별 오류 복구(Error Recovery) 전략으로 오류 전파 범위 축소
2. 중기: 최적화 수준 옵션(`-O0`~`-O3`) 분리로 개발·배포 단계별 컴파일 시간 조절
3. 장기: 공통 IR(LLVM IR 등) 기반 프론트-백엔드 분리로 다중 타겟 재사용성 확보

> 요약: 오류 복구·최적화 수준 분리·공통 IR 기반 설계로 단계적 개선이 필요함

## Ⅵ. 전망
- 발전 방향: LLVM 등 모듈형 컴파일러 인프라가 언어·플랫폼 독립 번역 표준으로 확산 중임
- 기술사적 판단: JIT 컴파일·AOT 컴파일 혼합 방식이 런타임 성능 최적화의 핵심 기술로 부상함
- 기술사 제언: 컴파일러 단계 이해를 기반으로 DSL 설계·정적 분석 도구 활용 역량 확보가 필요함
