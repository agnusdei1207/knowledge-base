# 📖 【암기용】 개념 완전 이해

> 목적: CRDT를 처음 봐도 완벽히 이해하게 만든다. 시험 답안 양식이 아니라, 이해를 위한 친절한 설명이다.

## 한눈에
- **개요**: CRDT(Conflict-free Replicated Data Type)는 **최종 일관성**을 수학적으로 보장하는 **분산 자료구조**로, 여러 노드가 동시에 갱신해도 병합 순서·횟수와 무관하게 항상 같은 결과로 수렴한다.
- **왜 필요한가**: 모바일 오프라인 편집, 다중 리전 협업, 엣지 저장소는 중앙 잠금만으로는 지연시간과 가용성 요구를 맞추기 어렵다. CRDT는 로컬 쓰기를 즉시 허용하고, 나중에 수학적으로 정해진 병합 규칙으로 수렴시킨다.
- **핵심 직관**: 각 노드가 따로 적은 장부를 나중에 합쳐도, 합치는 순서와 횟수에 관계없이 언제나 같은 최종 장부가 되는 구조다.

## 핵심 용어 정리 (내부에 등장하는 것들)

| 용어 | 의미 | 비유 |
|:---|:---|:---|
| 최종 일관성 (Eventual Consistency) | CRDT가 달성하려는 상위 목표 — 복제본이 결국 같은 상태로 수렴 | CRDT는 이를 수학적으로 보장하는 구체적 방법 |
| 교환법칙 (Commutativity) | 연산 순서를 바꿔도 결과가 같음 (a+b = b+a) | 합치는 순서를 안 가림 |
| 결합법칙 (Associativity) | 묶는 방식을 바꿔도 결과가 같음 ((a+b)+c = a+(b+c)) | 몇 개씩 나눠 합쳐도 결과는 동일 |
| 멱등성 (Idempotence) | 같은 연산을 여러 번 적용해도 결과가 변하지 않음 (a∪a=a) | 같은 스탬프를 두 번 찍어도 한 번 찍은 것과 동일 |
| 상태 기반 CRDT (CvRDT) | 노드의 전체 상태를 통째로 전파해 join(합집합 등) 연산으로 병합 | 장부 전체를 복사해서 합치기 |
| 연산 기반 CRDT (CmRDT) | 상태가 아니라 add/remove 같은 연산만 전파 | 변경 내역만 전달 |
| G-Counter | 증가만 가능한 카운터. 노드별 카운트를 따로 유지하다 합산 | 노드별 집계함을 다 더함 |
| PN-Counter | 증가·감소 모두 가능한 카운터. 내부적으로 증가용 P와 감소용 N, 두 G-Counter의 차로 계산 | 입금함과 출금함을 따로 두고 차감 |
| OR-Set (Observed-Remove Set) | 추가·삭제가 가능한 집합. 원소마다 고유 태그를 붙여 삭제 충돌을 방지 | 스탬프마다 고유번호를 매겨 중복·삭제를 구분 |
| LWW-Register | 타임스탬프가 가장 늦은 값을 채택하는 단일 값 저장소 | 최신 수정시각 값을 채택 |
| Tombstone | 삭제된 원소를 완전히 지우지 않고 "삭제됨" 표식으로 남기는 메타데이터 | 지운 자국을 남겨 나중에 대조 |

## 깊이 이해

### 수학적 조건이 왜 "충돌 없음"을 보장하나
- 병합 함수가 교환법칙·결합법칙·멱등성을 모두 만족하면, 노드가 메시지를 어떤 순서로 받든, 몇 번 중복해서 받든 최종 결과는 항상 같다 — 이것이 CRDT의 핵심 정리다. 예를 들어 집합의 합집합(∪) 연산은 세 조건을 모두 만족한다: {A}∪{B} = {B}∪{A}(교환), ({A}∪{B})∪{C} = {A}∪({B}∪{C})(결합), {A}∪{A} = {A}(멱등). 그래서 OR-Set 같은 CRDT는 합집합을 병합 규칙으로 쓴다.

### 워크드 예제 1: G-Counter로 조회수 합산하기
- 노드 3개(서울, 도쿄, 버지니아)가 각자 조회 이벤트를 센다. 서울=5, 도쿄=3, 버지니아=7로 각 노드가 자기 카운트만 증가시킨다(다른 노드 값은 절대 건드리지 않는다). 병합은 노드별 값을 벡터로 유지하다 합산한다: 5+3+7=15. 어느 순서로 병합하든, 몇 번을 재병합하든 항상 15가 나온다 — 노드별로 완전히 분리된 카운터의 합이라는 구조 자체가 교환·결합·멱등을 자동으로 만족시키기 때문이다.

### 워크드 예제 2: OR-Set으로 장바구니 병합하기
- 3개 리전 장바구니: 서울이 상품 A를 추가(태그 a1), 도쿄가 상품 B를 추가(태그 b1), 버지니아는 오프라인 상태였다가 나중에 동기화한다. 병합 시 각 원소를 태그 단위로 합치므로 {A(a1), B(b1)}로 수렴한다. 만약 버지니아가 오프라인 중 A를 삭제했다면, 삭제는 "태그 a1을 tombstone 처리"로 기록되어 있어 나중에 동기화해도 정확히 a1만 사라진다 — 혹시 그 사이 다른 노드가 A를 새로 추가했다면(다른 태그 a2) 그 원소는 살아남는다. "같은 값이지만 다른 삭제 이력"을 태그로 구분해 삭제 충돌을 막는 원리다.

### 상태 기반 vs 연산 기반의 차이
- 상태 기반(CvRDT)은 노드의 전체 상태를 통째로 보내 join 연산으로 병합한다 — 구현은 단순하지만 상태가 커지면 전송 비용이 크다. 연산 기반(CmRDT)은 "add(A)", "remove(B)" 같은 연산만 전파한다 — 트래픽은 작지만 연산이 정확히 한 번은 도달해야 한다는 전제가 더 엄격히 요구된다(중복 도달 시 멱등성으로, 순서 뒤바뀜 시 교환법칙으로 방어).

### 판별원리: CRDT가 못 푸는 문제
- CRDT는 자료구조 병합 자체의 충돌은 수학적으로 없앤다. 하지만 "재고 1개를 두 사용자가 동시에 산다"처럼 업무 규칙(불변식)을 위반하면 안 되는 경우는 CRDT로 풀 수 없다 — 병합 결과는 항상 나오지만 그 결과가 "재고 -1개"처럼 비즈니스적으로 불가능한 상태일 수 있기 때문이다. 이런 경우는 escrow(한도를 미리 노드별로 배분), reservation(예약 잠금), 단일 리더 트랜잭션 같은 별도 통제가 필요하다.

### 비유
- 여러 지점이 각자 스탬프 카드에 도장을 찍고, 본사가 나중에 전 지점 카드를 모아 합칠 때 "같은 도장은 한 번만 세고, 모든 지점의 도장을 다 합산"하는 방식이다. 어느 지점 카드를 먼저 보든, 두 번 보든 최종 합계는 같다.

## 연결 개념
- 최종 일관성(Eventual Consistency) — CRDT가 수학적으로 달성하는 수렴 목표
- CAP 정리 — 분할 허용(AP) 시 가용성과 일관성 선택 배경
- 벡터 클록(Vector Clock) — 갱신 인과관계를 추적하는 수단, CRDT 메타데이터에 활용

# 📝 【답안용】 시험 답안 템플릿

> 목적: 시험장에서 25분에 그대로 쓰는 답안 양식. 작성방식(추상표현 금지·수치·도식·문제유형 전환)을 엄격히 지킨다.
> 핵심: CRDT 답안은 자료구조 명칭 나열이 아니라, 병합 법칙과 적용 제한을 함께 써야 득점 가능함.

## 핵심 인사이트 (3줄 요약)

> 1. **본질**: CRDT는 교환·결합·멱등 병합으로 다중 복제본의 동시 갱신을 자동 수렴시키는 분산 자료구조임.
> 2. **가치**: 리전 간 RTT 100ms 이상 환경에서도 로컬 쓰기 허용, 오프라인 편집, 협업 편집 충돌 감소에 유효함.
> 3. **판단 포인트**: 카운터·집합·레지스터에는 적합하나, 재고·계좌처럼 불변 제약이 있는 업무는 별도 직렬화 통제가 필요함.

## 출제 의도 및 답안 포인트

| 출제 의도 | 반드시 짚을 핵심 | 감점 회피 포인트 |
|:---|:---|:---|
| 분산 일관성 설계 이해 확인 | 교환법칙, 결합법칙, 멱등성, 최종 수렴 | "충돌이 없다"를 모든 업무 제약 해결로 단정하지 않음 |
| CAP/PACELC 관점 판단 확인 | AP 지향, 로컬 쓰기, 비동기 복제 | 강한 일관성 DB 대체재로 일반화하지 않음 |
| 실무 적용 범위 확인 | OR-Set, PN-Counter, LWW-Register 선택 기준 | 삭제 충돌, tombstone 증가, 메타데이터 비용 누락 방지 |

> 요약: CRDT 문제는 병합 수학 조건과 업무 제약 분리 여부를 함께 판단하는 문제임.

## Ⅰ. 개요 및 필요성

- 개요: CRDT는 충돌 없이 수렴하는 복제 자료구조이다.
- 배경: 다중 리전·오프라인·엣지 환경은 네트워크 분할과 지연을 전제로 하므로 중앙 잠금 기반 쓰기만으로 사용자 지연 목표를 맞추기 어렵다.
- 필요성: 로컬 갱신과 비동기 병합으로 복제본을 같은 상태로 수렴시켜 협업 편집, 장바구니, 엣지 캐시의 충돌 처리를 단순화한다.

---

## Ⅱ. 구조 및 구성요소

```text
Client Update -> Local Replica -> CRDT State/Op -> Anti-Entropy Sync -> Merge -> Converged State
                                      +-> Version Metadata / Tombstone
```

| 구성요소 | 역할 | 특이사항 |
|:---|:---|:---|
| 로컬 복제본 | 네트워크 왕복 없이 쓰기 수락 | 오프라인 쓰기 허용 |
| 병합 함수 | 복제본 상태를 결정적 결과로 합성 | 교환·결합·멱등 필요 |
| 메타데이터 | 인과관계·삭제 정보 추적 | vector clock, dot, tombstone |
| 동기화 계층 | 상태 또는 연산 전파 | anti-entropy, gossip |

> 요약: CRDT는 로컬 쓰기, 메타데이터, 결정적 병합 함수, 비동기 동기화가 결합된 구조임.

## Ⅲ. 동작원리 및 흐름도

```text
Local Write -> Metadata Attach -> State/Op Replicate -> Merge Rule Apply -> Same Result Check
```

| 단계 | 처리 내용 | 검증 기준 |
|:---:|:---|:---|
| 1 | 노드별 로컬 갱신 수행 | write latency 리전 내부 p95 기준 |
| 2 | 버전·노드 ID·삭제 표식 부여 | 중복 연산 멱등 처리 |
| 3 | 상태 또는 연산을 다른 노드로 전파 | gossip lag, replication queue |
| 4 | join·union·max 등 병합 규칙 적용 | 합치는 순서 변경 시 동일 결과 |
| 5 | 모든 복제본 상태 비교 | divergence count 0 |

> 요약: CRDT는 로컬 갱신을 먼저 허용하고, 결정적 병합 법칙으로 복제본 차이를 0으로 수렴시킴.

## Ⅴ. 심화 비교 및 적용 판단

| 비교 축 | 기존/대안 | 본 키워드 | 선택 기준 |
|:---|:---|:---|:---|
| 일관성 | 2PC, 단일 리더 | AP 지향 최종 수렴 | 오프라인·협업 쓰기 비중 30% 이상 |
| 데이터 모델 | 일반 행·문서 | Counter, Set, Register | 병합 규칙을 수학적으로 정의 가능 |
| 운영/위험 | 충돌 핸들러 | 자동 병합+메타데이터 | tombstone 보존 기간·압축 정책 |

> 요약: CRDT는 병합 가능한 자료형과 사용자 지연 목표가 명확할 때 선택한다.

| 리스크 | 원인 | 대응 방안 | 확인 지표 |
|:---|:---|:---|:---|
| 불변 제약 위반 | 동시 재고 차감 | escrow, reservation, 단일 리더 경로 | oversell count 0 |
| 저장량 증가 | tombstone·버전 벡터 누적 | compaction, causal stability 확인 | metadata bytes per object |
| 수렴 지연 | 복제 지연·노드 장애 | anti-entropy 주기 1~5초, 재전송 큐 | convergence lag p95 |

> 요약: CRDT 리스크는 업무 불변식, 메타데이터, 수렴 지연을 분리해 통제한다.

| 점검 항목 | 목표 기준 | 측정 방법 |
|:---|:---|:---|
| 수렴성 | divergence count 0 | 복제본 해시 비교 |
| 지연 | local write p95 50ms 이하 | 클라이언트 APM |
| 복제 | convergence lag p95 5초 이하 | gossip lag 메트릭 |

> 요약: CRDT 적용 효과는 로컬 쓰기 지연과 복제본 수렴 지표로 판단한다.

## Ⅵ. 실무 적용 및 결론

**적용 방안 3개 (필수 — 단계별 또는 항목별):**
1. 협업 문서·장바구니는 OR-Set, 카운터는 PN-Counter, 최신값 표시만 필요한 항목은 LWW-Register로 자료형을 제한함.
2. tombstone 보존 기간 7~30일, compaction 배치, causal stability 기준을 운영 정책으로 고정함.
3. 재고·결제·한도 초과 업무는 CRDT 경로에서 제외하고 2PL·MVCC·단일 리더 트랜잭션으로 분리함.

**결론 (2줄):**
- 기술사 판단: 오프라인·다중 리전 쓰기면 CRDT를 선택하고, 금액·재고 불변식이면 강한 일관성 경로를 선택함.
- 향후 방향: 엣지 컴퓨팅과 협업 SaaS 확대에 따라 CRDT와 정책 기반 제약 검증의 결합이 요구됨.
