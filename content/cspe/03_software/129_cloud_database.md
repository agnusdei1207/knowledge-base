# 📖 【암기용】 개념 완전 이해

## 한눈에
- **개요**: 클라우드 환경에서 제공되는 데이터베이스 서비스(DBaaS)로, 인프라 관리 부담 없이 즉시 생성하고 확장할 수 있다. 대표적으로 AWS의 RDS, Aurora, DynamoDB가 있다.
- **왜 필요한가**: 과거에는 서버 랙을 사고, OS를 깔고, 오라클을 설치하고 백업 스크립트까지 직접 짜야 했다. 이제는 클릭 몇 번으로 최적화된 DB를 띄우고 장애 시 자동 복구까지 클라우드 벤더가 알아서 해주는 서비스가 필요해졌다.
- **핵심 직관**: 
  - **RDS**: 남이 대신 관리해 주는 "표준 아파트" (기존 MySQL/PostgreSQL 100% 호환, 관리만 대행)
  - **Aurora**: 클라우드에 맞게 뼈대부터 재설계한 "최첨단 고급 아파트" (저장소와 컴퓨팅 분리, 압도적 성능)
  - **DynamoDB**: 필요할 때마다 무한히 늘어나는 "모듈형 창고" (완전 관리형 NoSQL, 빠른 속도와 무한 확장)

## 핵심 용어 정리

| 용어/표기 | 의미 | 비유·예 |
|:---|:---|:---|
| RDS | Relational Database Service, 관리형 RDBMS | 기사님이 관리해 주는 렌터카 (엔진은 일반차) |
| Aurora | AWS가 클라우드 네이티브로 재설계한 고성능 RDBMS | 테슬라 (전기차 전용 뼈대로 처음부터 다시 만듦) |
| DynamoDB | AWS의 완전 관리형 서버리스 NoSQL (Key-Value) | 끝없이 확장 가능한 무인 창고 |
| DBaaS | Database as a Service, 클라우드 DB 서비스 모델 | DB를 '소유'하는 게 아니라 '구독'하는 것 |

## 깊이 이해
- **배경·문제의식**: 온프레미스 DB는 하드웨어 장애 대비, 스케일업(CPU/RAM 증설), 정기 백업 등 운영 유지보수(Toil)에 엄청난 인건비가 든다. 클라우드가 대세가 되면서 DB도 SaaS처럼 편하게 쓰고 싶어졌다.
- **작동 원리**: 
  - **RDS**: 기존 MySQL 같은 상용/오픈소스 DB 엔진을 AWS EC2(가상머신) 위에 올리고, 백업/패치 자동화 래퍼(Wrapper)를 씌운 것이다. 구조적 한계는 기존 DB와 같다.
  - **Aurora**: 쿼리 연산(컴퓨팅)과 데이터 저장(스토리지)을 분리했다. 스토리지는 3개 가용영역(AZ)에 6벌씩 분산 복제되어 디스크 I/O 병목을 해결, 기존 MySQL보다 5배 빠르다.
  - **DynamoDB**: 서버(인스턴스) 개념조차 없는 서버리스(Serverless)다. 파티션 키로 데이터를 무한 분산시켜 어떤 규모의 트래픽이 와도 10ms 이하 응답을 보장한다(아마존 닷컴 장바구니에 쓰임).
- **흔한 오해·주의점**: "Aurora는 MySQL과 완전히 다른 DB다?" 뼈대(스토리지)는 완전히 갈아엎었지만, 겉모습(SQL 파서)은 MySQL/PostgreSQL과 100% 호환되게 만들었다. 기존 코드를 수정 없이 그대로 쓸 수 있다. DynamoDB는 RDBMS가 아니므로 조인이 불가능하다.

## 연결 개념
- Cloud Native Architecture — 클라우드 환경에 최적화된 설계 (Aurora)
- Serverless — 인프라 프로비저닝이 필요 없는 개념 (DynamoDB)
- 컴퓨팅과 스토리지 분리 — 최신 클라우드 DB의 공통된 진화 방향

# 📝 【답안용】 시험 답안 템플릿

## 핵심 인사이트 (3줄 요약)

> 1. **본질**: 하드웨어 프로비저닝, 패치, 백업 등 관리형 오버헤드를 추상화한 DBaaS(Database as a Service) 라인업이다.
> 2. **가치**: 기존 호환성을 중시하는 RDS, 클라우드 네이티브 스토리지 최적화로 성능을 극대화한 Aurora, 서버리스 기반 무한 확장의 DynamoDB로 워크로드 요구를 충족한다.
> 3. **판단 포인트**: 트랜잭션 보장, 스토리지-컴퓨팅 분리 여부, 스키마리스 확장성 등 비즈니스 특성에 맞춘 클라우드 DB 선택(Polyglot Persistence) 기준을 제시해야 한다.

## 출제 의도 및 답안 포인트

| 출제 의도 | 반드시 짚을 핵심 | 감점 회피 포인트 |
|:---|:---|:---|
| 클라우드 DB 발전 단계 및 아키텍처 특성 이해 | RDS(호환/관리형), Aurora(컴퓨팅-스토리지 분리), DynamoDB(서버리스 NoSQL) | 세 서비스의 차이를 단순히 '비용'으로만 뭉뚱그려 설명 |

> 요약: 단순 관리 대행(RDS)에서 스토리지 분리(Aurora), 그리고 완전한 서버리스(DynamoDB)로 이어지는 클라우드 데이터베이스의 진화와 아키텍처 차이를 명확히 비교한다.

---

## Ⅰ. 개요 및 필요성

- 개요: 클라우드 서비스 제공자(CSP)가 데이터베이스 설치, 백업, HA 구성, 패치 등을 자동화하여 제공하는 관리형 서비스(DBaaS)
- 배경: 온프레미스 환경에서 DB 이중화 및 백업 구성에 과도한 인프라 인력이 소모되고, 트래픽 급증 시 유연한 확장이 불가함
- 필요성: 비즈니스 민첩성 향상을 위한 즉각적인 프로비저닝, 클라우드 규모의 수평/수직 확장성, 그리고 사용한 만큼만 지불하는 탄력적 아키텍처 필요

---

## Ⅱ. 구조 및 구성요소 (Aurora 기준 발전 아키텍처)

```text
[ 기존 RDS 아키텍처 ]                [ 클라우드 네이티브 Aurora 아키텍처 ]
Application                       Application
    |                                 |
[ Compute + Storage (일체형) ]       [ Compute (쿼리, 캐시, 트랜잭션) ]  <-- (Stateless)
    | (동기 복제 병목)                    | (Log만 비동기 전송)
[ Standby DB ]                    [ Distributed Storage Volume ] <-- (3개 AZ, 6벌 복제)
```

| 구성요소 | 역할 | 특이사항 |
|:---|:---|:---|
| 컴퓨팅(Compute) 노드 | SQL 파싱, 트랜잭션 처리, 캐싱 수행 | 쿼리 엔진은 기존 MySQL/PgSQL 호환 |
| 분산 스토리지 볼륨 | 데이터의 물리적 저장 및 자체 복구 수행 | 컴퓨팅 노드와 독립적으로 자동 확장 (최대 128TB) |
| Log-Structured Storage | 변경 로그(Redo Log)만 스토리지로 전송 | 네트워크 I/O 병목 획기적 감소 (RDS 대비) |

> 요약: 기존 RDS는 컴퓨팅과 스토리지가 결합되어 복제 오버헤드가 크지만, Aurora는 이를 분리하여 성능과 가용성을 극대화했다.

---

## Ⅲ. 동작원리 및 흐름도 (Aurora 기반 쓰기/복제 원리)

```text
쓰기 쿼리 발생 -> Redo Log 생성 -> 분산 스토리지 6개 노드로 비동기 전송 -> Quorum 합의 응답
```

- 1단계 [쿼리 수신]: 마스터(Primary) 컴퓨팅 노드가 UPDATE 쿼리를 받아 데이터 페이지 대신 Redo Log(변경분)만 생성
- 2단계 [스토리지 전송]: 네트워크를 통해 3개의 가용 영역(AZ)에 흩어진 6개의 스토리지 노드로 Redo Log를 병렬 전송
- 3단계 [Quorum 합의]: 6개의 스토리지 노드 중 4개(쓰기 쿼럼, Vw=4)가 디스크/메모리에 로그를 기록하고 ACK 응답 시 쓰기 완료로 판단
- 4단계 [비동기 병합]: 스토리지 노드 내부에서 백그라운드로 Redo Log를 병합하여 데이터 블록을 생성하고 지속적 백업(S3) 수행

> 요약: 스토리지 단으로 '변경 로그'만 보내고, 분산된 노드들이 자체적으로 데이터를 조립하게 하여 컴퓨팅 노드의 부하를 덜어낸다.

---

## Ⅳ. 주요 서비스 특징 비교

- RDS (Relational Database Service): 기존 RDBMS(Oracle, MySQL 등)를 클라우드 VM에 올려 관리(백업, 이중화)를 자동화한 표준 서비스. 기존 환경과 동일한 아키텍처
- Aurora: 스토리지와 컴퓨팅을 분리한 클라우드 네이티브 RDBMS. MySQL 대비 5배 성능, 밀리초 단위 복제 지연, 3개 AZ 6벌 복제를 통한 압도적 내결함성(Fault Tolerance)
- DynamoDB: Key-Value 기반 완전 관리형 NoSQL. 인스턴스(서버) 개념이 없는 서버리스 아키텍처로, 요청량(RCU/WCU) 설정 시 무한한 수평 확장을 통해 한 자릿수 밀리초 응답 보장

> 요약: 레거시 마이그레이션은 RDS, 초고성능 엔터프라이즈 RDB는 Aurora, 예측 불가의 대규모 비정형 트래픽은 DynamoDB가 담당한다.

## Ⅴ. 심화 비교 및 적용 판단

| 비교 축 | RDS | Aurora | DynamoDB |
|:---|:---|:---|:---|
| 아키텍처 사상 | 전통적 모놀리식 RDB | 클라우드 네이티브 RDB | 서버리스 NoSQL |
| 확장성 (Scale) | Scale-up 중심 (수직) | Scale-up + 읽기 복제본 15대 | 무한 Scale-out (수평) |
| 데이터 정합성 | 강한 정합성 (ACID) | 강한 정합성 (ACID) | 최종 일관성 (강한 정합성 옵션 지원) |
| 도입 적합성 | 기존 온프레미스의 단순 마이그레이션(Lift & Shift) | 대규모 금융, 이커머스 등 고성능 트랜잭션 필수 워크로드 | 게임 리더보드, 장바구니 등 초고속 키-값 조회 |

> 요약: 관계형 스키마와 조인이 필요하면 Aurora를 최우선 고려하고, 조인 없이 폭발적 확장이 필요하면 DynamoDB를 선택한다.

**리스크·대응 (기본은 불릿):**
- 벤더 락인(Vendor Lock-in): Aurora와 DynamoDB는 AWS 전용 기술로 타 클라우드(GCP, Azure) 이전 시 재설계 비용 발생 → 핵심 로직은 ORM으로 추상화하고 데이터 엑세스 계층(Repository) 격리
- DynamoDB 파티션 핫스팟: 특정 파티션 키(예: 특정 유저)에 트래픽이 몰려 쓰기 병목 발생(Throttling) → 카디널리티가 높은 해시 키 설계 및 Write Sharding 기법 적용

## Ⅵ. 실무 적용 및 결론

**적용 방안 3개:**
1. MSA 기반 Polyglot Persistence: 주문/결제 마이크로서비스는 트랜잭션 무결성을 위해 Aurora MySQL을 사용하고, 유저 세션 관리와 상품 리뷰 서비스는 DynamoDB를 조합하여 사용
2. 글로벌 무중단 서비스 아키텍처: Aurora Global Database를 구성하여 리전 간 1초 미만 복제 지연을 유지하고, 재해 복구(DR) 시 RTO를 1분 이내로 단축
3. Serverless 이벤트 구동 처리: IoT 기기에서 쏟아지는 스트리밍 데이터를 API Gateway → AWS Lambda → DynamoDB 파이프라인으로 구축하여 인프라 유휴 비용 0원 달성

**결론 (2줄):**
- 기술사 판단: 클라우드 DB 선택은 단순한 비용 문제가 아니라 아키텍처의 패러다임 전환이다. 관계형 모델의 ACID가 필수라면 Aurora를, 극단적 스케일아웃이 필요하다면 DynamoDB를 선택해야 한다.
- 향후 방향: 최근 클라우드 DB는 AI 트렌드에 맞춰 벡터 검색(Vector Search)을 내장하고, 트래픽에 따라 DB 인스턴스 크기가 스스로 조절되는 Aurora Serverless v2 형태로 지능화되고 있다.
