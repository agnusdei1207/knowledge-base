## 미리 알고가기

- 관리형 데이터베이스는 백업, 패치, 장애 복구 같은 운영 작업을 서비스 사업자가 대신 맡는 방식임
- RDS는 익숙한 관계형 데이터베이스를 관리형으로 쓰는 서비스임
- Aurora는 관계형 호환성을 유지하면서 저장 구조를 분산화한 서비스임
- DynamoDB는 키값형과 문서형에 가까운 완전 관리형 NoSQL 서비스임

## Ⅰ. 개요

- **정의/개념**: 클라우드 DB는 데이터베이스 엔진만 빌려 쓰는 것이 아니라 배포, 백업, 복구, 확장 같은 운영 기능까지 서비스 형태로 제공하는 데이터베이스 운영 방식임
- **배경/필요성**: 서비스 출시 속도는 빨라지고 운영 인력은 제한되므로 데이터베이스를 직접 설치하고 장애를 복구하는 부담을 줄일 관리형 방식이 필요해짐

## Ⅱ. 특징

- 백업, 패치, 모니터링 같은 운영 작업을 크게 줄일 수 있음
- 서비스마다 데이터 모델과 확장 방식이 달라 선택 기준이 뚜렷해야 함
- 자동 확장과 고가용성을 쉽게 얻을 수 있지만 비용 구조를 함께 봐야 함
- 관리형이라도 일관성 모델과 장애 전환 특성은 직접 이해해야 함

## Ⅲ. 종류 및 비교

| 판단 기준 | RDS | Aurora | DynamoDB |
|:---|:---|:---|:---|
| 데이터 모델 | 관계형 | 관계형 | 키값형·문서형 |
| 강점 | 익숙한 운영 방식 | 읽기 확장과 고가용성 | 큰 트래픽에도 자동 확장 |
| 주의점 | 대규모 확장은 한계가 있음 | 기능과 비용 구조를 잘 이해해야 함 | 조인과 복잡한 조건 검색은 약함 |
| 잘 맞는 업무 | 일반 업무 시스템 | 고가용성 관계형 서비스 | API, 세션, 대규모 단건 조회 |

## Ⅳ. 구성요소 및 구조

| 구성요소 | 설명 |
|:---|:---|
| 제어 계층 | 배포, 백업, 패치, 모니터링을 자동화함 |
| 저장과 복제 구조 | 각 서비스의 성능과 장애 복구 특성을 결정함 |
| 확장 정책 | 읽기 복제, 자동 조정, 파티션 방식이 처리량 한계를 좌우함 |
| 접근 모델 | SQL 중심인지 키 기반 접근 중심인지가 응용 구조를 바꿈 |

```text
+-----------+      +-----------+      +-----------+
| 응용 서비스 | ---> | 클라우드 DB | ---> | 백업/복제/모니터링 |
+-----------+      +-----------+      +-----------+
```

## Ⅴ. 원리 및 절차 흐름도

```text
+-------------+     +-------------+     +-------------+     +-------------+
| 업무 요구 파악   | --> | 서비스 유형 선택 | --> | 확장과 복제 설계 | --> | 비용과 성능 점검 |
+-------------+     +-------------+     +-------------+     +-------------+
```

1. **업무 요구 파악**: SQL 사용량, 처리량, 정합성 요구를 확인함
2. **서비스 유형 선택**: RDS, Aurora, DynamoDB 중 맞는 구조를 고름
3. **확장과 복제 설계**: 읽기 확장, 장애 복구, 백업 구조를 정함
4. **비용과 성능 점검**: 예상 트래픽에서 응답 시간과 비용을 함께 확인함

## Ⅵ. 실무 적용 및 유의점

1. 조인과 트랜잭션이 많은 업무는 관계형 계열인 RDS나 Aurora가 맞으므로 기능이 부족한 저장소로 무리하게 옮기지 말고 질의 재작성 건수와 평균 응답 시간으로 선택이 맞는지 확인함
2. 트래픽 변동이 큰 API나 세션 저장은 DynamoDB가 유리할 수 있지만 파티션 키가 한쪽으로 몰리면 성능과 비용이 함께 흔들리므로 쏠림 비율과 요청당 비용으로 운영 상태를 계속 점검함

## Ⅶ. 결론

클라우드 DB의 핵심은 관리형이라는 말만 보는 데 있지 않고 데이터 모델, 확장 방식, 비용 구조를 업무 요구와 정확히 맞추는 데 있음.
