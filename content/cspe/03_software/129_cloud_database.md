## 미리 알고가기

- 관리형 데이터베이스는 프로비저닝·패치·백업·장애 조치 같은 운영 기능을 공급자 제어 계층이 수행하는 서비스임
- 이 문서의 RDS는 MySQL·PostgreSQL·Oracle·SQL Server 등 일반 RDS 관계형 엔진을 뜻하며 Aurora도 RDS에서 관리되는 별도 엔진 계열임
- Aurora는 MySQL·PostgreSQL 호환 관계형 엔진과 여러 가용 영역에 걸친 클러스터 볼륨을 사용함
- DynamoDB는 파티션 키와 선택적 정렬 키로 항목을 분산하는 키-값·문서형 관리형 NoSQL 서비스임
- Multi-AZ는 장애 조치, 읽기 복제본은 읽기 확장을 주목적으로 하므로 RDS 구성에 따라 역할을 구분해야 함

## 작성 근거(검토용)

- RDS·Aurora·DynamoDB는 데이터 모델·확장 방식·적합 조건을 핵심 축으로 비교함
- Ⅴ절은 업무 요구를 데이터 모델·질의·트랜잭션·확장·장애 목표로 분해해 서비스를 선택하는 절차를 제시함
- 실무 사례는 관계형 주문 DB와 키 기반 API에서 커밋·장애 조치 지연과 파티션 부하 편차로 검증함

## Ⅰ. 개요

- **정의/개념**: 클라우드 DB는 데이터베이스 엔진과 프로비저닝·패치·백업·복제·장애 조치·용량 제어를 API 기반 관리형 서비스로 제공하는 운영 모델임
- **배경/필요성**: 데이터 모델·트랜잭션·확장 요구는 유지하면서 설치·패치·백업·장애 복구의 운영 부담을 줄이기 위해 관리형 데이터베이스가 필요함

### 쉽게 이해하기 (학습용)
- 데이터베이스 설치·패치·백업·장애 조치를 클라우드가 맡고 사용자는 모델과 용량을 선택함

## Ⅱ. 특징

- 공급자가 제어 계층을 운영하지만 사용자는 스키마·키·인덱스·일관성·백업 보존·장애 조치 정책을 결정함
- 관계형 인스턴스, 분리된 관계형 클러스터 저장소, 관리형 키 파티션은 확장·복구 단위가 서로 다름
- 읽기 복제본·다중 가용 영역·파티션 용량 구성에 따라 읽기 확장·장애 조치·부하 분산 방식이 달라짐
- 관리형 서비스도 복제 지연·장애 조치 시간·핫 파티션·요청당 용량 비용을 응용 요구와 함께 검증해야 함

### 쉽게 이해하기 (학습용)
- 관리 부담은 줄지만 서비스별 질의·확장 단위와 비용·종속성이 다름

## Ⅲ. 종류 및 비교

| 판단 기준 | RDS | Aurora | DynamoDB |
|:---|:---|:---|:---|
| 데이터 모델 | 엔진별 관계형 테이블 | MySQL·PostgreSQL 호환 관계형 테이블 | 키-값·문서형 항목 |
| 확장 방식 | 인스턴스 증설·읽기 복제본·스토리지 조정 | 읽기 인스턴스 추가와 클러스터 스토리지 확장 | 온디맨드·프로비저닝 용량과 파티션 분산 |
| 적합 조건 | 엔진 호환성과 일반 관계형 운영이 우선 | 관계형 호환성과 읽기 확장·장애 조치가 함께 필요 | 키 기반 접근·파티션 확장·관리형 처리량이 우선 |

> 요약: RDS·Aurora는 SQL 관계형 모델을 유지하고, DynamoDB는 키 기반 파티션·용량 모델로 확장함.

### 쉽게 이해하기 (학습용)
- RDS는 관리형 관계형, Aurora는 클러스터 관계형, DynamoDB는 키 기반 분산 저장소임

## Ⅳ. 설계 요소 및 구조

| 구성요소 | 설명 |
|:---|:---|
| 관리 제어 계층 | 프로비저닝·패치·백업·모니터링·장애 조치를 API로 수행함 |
| 접속 엔드포인트 | RDS 인스턴스, Aurora 클러스터, DynamoDB 리전 API로 요청을 수신함 |
| 질의·키 처리 계층 | SQL 실행 계획 또는 파티션·정렬 키로 처리 대상을 결정함 |
| 컴퓨팅·파티션 계층 | DB 인스턴스·Aurora 인스턴스·DynamoDB 파티션이 연산을 수행함 |
| 저장·복제 계층 | 인스턴스 스토리지·클러스터 볼륨·관리형 복제 파티션이 데이터를 보존함 |

```text
+-----------+      +-----------+      +-----------+
| 응용 서비스 | ---> | 접속·질의 계층 | ---> | 컴퓨팅·저장·복제 |
+-----------+      +-----------+      +-----------+
                         |
                  관리 제어 계층
```

> 요약: 관리 제어 계층은 공통 운영을 맡고 각 서비스의 접속·질의·컴퓨팅·저장 구조가 처리와 장애 조치 단위를 결정함.

### 쉽게 이해하기 (학습용)
- 관리 화면은 같아도 실제 요청은 인스턴스·클러스터·파티션으로 서로 다르게 흐름

## Ⅴ. 원리 및 절차 흐름도

```text
[업무 요구 분류] -> [관계형·키 기반 모델 선택] -> [확장·장애 목표 매핑]
        -> [RDS·Aurora·DynamoDB 선정] -> [성능·복구·비용 검증]
```

1. 조인·트랜잭션·키 조회와 데이터 크기·부하 분포를 식별함
2. 엔진 호환성, 읽기 확장, 파티션 기반 처리량의 우선순위를 정함
3. RPO·RTO·다중 가용 영역·리전 요구와 용량 과금 모델을 매핑함
4. 커밋 지연·장애 조치 시간·파티션 편차·월 비용으로 선택을 검증함

> 요약: 데이터 모델과 질의·트랜잭션·확장·복구 목표를 서비스 구조에 매핑해 선택함.

### 쉽게 이해하기 (학습용)
- 장부 종류와 손님 수, 비상 복구 시간과 요금을 비교해 맞는 관리형 창고를 고름

## Ⅵ. 실무 사례

1. 주문 관계형 DB는 Aurora 읽기 인스턴스와 장애 조치 우선순위를 적용하고 p99 커밋 지연·장애 조치 시간을 확인함
2. 세션 API는 DynamoDB 파티션 키를 분산하고 최대 파티션 요청 점유율·제한 요청률을 확인함

### 쉽게 이해하기 (학습용)
- 일반 주문은 RDS, 읽기 확장 관계형은 Aurora, 키 기반 대규모 API는 DynamoDB를 검토함

## Ⅶ. 결론

- 클라우드 DB는 데이터 모델·질의 경로·트랜잭션·확장 단위·장애 조치와 용량 비용을 기준으로 선택해야 함
- 관리형이라는 이유로 운영 책임이 사라지지 않으므로 백업 복구·용량 한도·비용·서비스 종속성을 지속 검증해야 함

### 쉽게 이해하기 (학습용)
- 창고 관리를 맡겨도 물건 배치와 복구 시험, 사용 요금은 사용자가 계속 책임져야 함
