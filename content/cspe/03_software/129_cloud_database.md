# 📖 【암기용】 개념 완전 이해

> 목적: 클라우드 DB 비교를 처음 봐도 완벽히 이해하게 만든다. 시험 답안 양식이 아니라, 이해를 위한 친절한 설명이다.

## 한눈에
- **개요**: 설치·패치·백업·장애조치 같은 운영 작업을 클라우드 사업자가 대신 수행하는 **관리형 데이터베이스 서비스**(Managed DBaaS)이며, RDS·Aurora·DynamoDB는 그 대표 제품이다.
- **왜 필요한가**: 직접 DB를 설치하면 OS 패치, 야간 백업, 장애 시 failover까지 운영자가 모두 책임져야 한다. 관리형 DB는 이 반복 작업을 서비스로 위임하지만, 제품마다 데이터 모델·확장 방식·비용 구조가 달라 업무 특성에 맞는 선택 기준이 필요하다.
- **핵심 직관**: 직접 주방을 차릴지, 표준 인테리어 식당을 빌릴지, 좌석 수가 자동으로 늘어나는 무인 급식 시스템을 쓸지를 업무 메뉴(쿼리 패턴)에 맞춰 고르는 문제다.

## 핵심 용어 정리 (내부에 등장하는 것들)

| 용어 | 의미 | 비유 |
|:---|:---|:---|
| 관리형 DB(Managed DBaaS) | 설치·패치·백업·모니터링을 클라우드가 대행하는 운영 모델 | 인테리어·시설관리를 대행업체가 맡는 임대 매장 |
| 공유 책임 모델(Shared Responsibility Model) | 인프라 운영은 클라우드, 스키마·쿼리·접근권한 설계는 사용자 책임으로 나누는 경계선 | 건물 관리는 임대인, 매장 진열은 세입자 책임 |
| RDS | 기존 MySQL·PostgreSQL 등 RDB 엔진을 관리형으로 제공 — EC2+EBS 기반 | 익숙한 사무실을 관리업체가 돌봐줌 |
| Aurora | 컴퓨트와 스토리지를 분리한 AWS 클라우드 네이티브 RDB | 클라우드용으로 아예 새로 설계된 사무실 |
| DynamoDB | 파티션 키 기반 서버리스 key-value/document NoSQL | 좌석 수가 자동으로 늘어나는 무인 접수대 |
| Multi-AZ | 다른 가용영역(AZ)에 동기 복제본을 둬 장애 시 자동 전환하는 구성 | 본점이 문 닫으면 즉시 분점으로 전환 |
| 파티션 키(Partition Key) | DynamoDB가 데이터를 여러 물리 파티션에 분산하는 해시 기준 컬럼 | 우편번호로 소포를 지역 창고에 나눠 보관 |
| RTO/RPO | 장애 후 복구까지 걸리는 시간(RTO)과 데이터 손실 허용 범위(RPO) | RTO=병원 도착 시간, RPO=마지막 백업 이후 유실 허용치 |

## 깊이 이해

### 왜 관리형 DB가 필요했나 (배경)
- 직접 DB를 운영하면 OS 패치, DB 마이너 버전 업그레이드, 매일 새벽 백업 스크립트, 장애 시 failover 절차를 전부 운영자가 만들고 당직으로 대응해야 한다. 2009년 AWS가 출시한 RDS는 이 반복 작업을 표준 서비스로 만들어, 사용자는 인스턴스 크기와 백업 주기만 설정하면 되게 했다. 이후 Aurora(2014)·DynamoDB(2012)처럼 클라우드 환경에 맞춰 아예 새로 설계된 DB 서비스가 이어졌다.

### RDS와 Aurora의 구조 차이 — 수치로 이해
- RDS는 EC2 위에 표준 엔진을 얹고 EBS 볼륨에 저장한다. 복제(read replica)는 스토리지 블록을 통째로 동기화하는 방식이라, replica를 늘릴수록 지연(lag)과 스토리지 비용이 replica 수에 비례해 늘어난다.
- Aurora는 컴퓨트 노드와 스토리지 계층을 분리하고, 스토리지는 3개 AZ에 걸쳐 자동으로 6개 복사본을 유지한다(쓰기는 6개 중 4개 응답으로 커밋, 읽기는 6개 중 3개 응답으로 확정 — 쿼럼 방식). 그 결과 read replica를 최대 15개까지 붙여도 각 replica가 스토리지를 따로 복제하지 않고 같은 로그 스트림을 공유해, RDS보다 낮은 복제 지연으로 확장할 수 있다.

### DynamoDB가 확장하는 방식 — 파티션 키 수치 예
- DynamoDB는 파티션 키 값을 해시해서 물리 파티션에 데이터를 흩뿌린다. 예: 초당 10,000건 쓰기가 들어오는 장바구니 서비스에서 파티션 키를 "국가코드"(값이 5개뿐)로 잡으면, 파티션 하나가 감당할 수 있는 처리량 한도(파티션당 쓰기 용량 약 1,000 WCU)를 넘어서 특정 파티션에 요청이 쏠리는 hot partition이 발생하고 나머지 요청은 throttling된다. 파티션 키를 `user_id`처럼 값의 종류(카디널리티)가 매우 높은 컬럼으로 바꾸면 같은 10,000건이 수천 개 파티션에 고르게 분산돼 한도에 걸리지 않는다.

### 세 서비스의 선택 기준 — 구체 예시
- 기존 MySQL 업무를 SQL 수정 없이 그대로 옮기려면 RDS(엔진 호환 우선)를 쓴다.
- 같은 관계형 데이터인데 읽기 트래픽이 피크 시 평시 대비 10배까지 튀는 주문 조회 서비스는 Aurora의 read replica 확장성이 유리하다.
- 세션·장바구니·이벤트 상태처럼 단순 key 조회가 초당 수만 건 발생하고 스키마 변경이 드물면 DynamoDB를 쓴다.

### 흔한 오해
- 관리형 DB라고 운영 책임이 사라지는 게 아니다. 인덱스 설계, 파티션 키 설계, 쿼리 튜닝, 비용 급증 알람, 백업 복구 리허설은 여전히 사용자(개발팀) 책임이다 — 인프라 운영과 데이터 설계 책임을 나눠 지는 이 경계를 공유 책임 모델이라 부른다.

## 연결 개념
- Database as a Service(DBaaS) — 관리형 DB의 상위 운영 모델
- RDBMS vs NoSQL — DynamoDB 선택 시 근거가 되는 데이터 모델 판단 기준
- Multi-AZ, Quorum Replication — RDS·Aurora가 가용성을 확보하는 메커니즘

## Ⅰ. 개요 및 필요성

- 개요: 클라우드 DB는 관리형 데이터베이스 서비스이다.
- 배경: 기업은 DB 패치·백업·장애조치·용량 증설 부담을 줄이면서 서비스 요구에 맞는 데이터 모델을 선택해야 한다.
- 필요성: RDS, Aurora, DynamoDB의 호환성·확장·비용 구조를 기준으로 워크로드별 DB를 선택한다.

---

## Ⅱ. 구조 및 구성요소

```text
Application -> Cloud DB Endpoint
  / RDS -> Managed Relational Engine -> Multi-AZ/Backup
  / Aurora -> Compute Node -> Distributed Storage -> Replica
  / DynamoDB -> Partition Key -> Partition -> Global Table
```

| 구성요소 | 역할 | 특이사항 |
|:---|:---|:---|
| RDS | MySQL, PostgreSQL 등 관리형 RDB | 기존 SQL·엔진 호환 |
| Aurora | 분산 스토리지 기반 관계형 DB | read replica, storage 분리 |
| DynamoDB | 서버리스 key-value/document DB | partition key, capacity mode |
| 운영 계층 | 백업, 모니터링, 장애조치 | SLA·비용·권한 관리 |

> 요약: 클라우드 DB는 RDB 호환형, 클라우드 네이티브 RDB, 서버리스 NoSQL로 나뉨.

## Ⅵ. 실무 적용 및 결론

**적용 방안 3개 (필수 — 단계별 또는 항목별):**
1. 기존 SQL·조인 중심 업무는 RDS 우선, 읽기 확장과 분산 스토리지 이점이 필요하면 Aurora를 검토함.
2. 단순 키 조회·세션·장바구니·이벤트 상태는 DynamoDB partition key와 capacity mode를 설계함.
3. 마이그레이션은 CDC, dual run, rollback plan, RTO/RPO 검증을 포함해 최소 1회 이상 리허설함.

**결론 (2줄):**
- 기술사 판단: 호환성은 RDS, 관계형 확장은 Aurora, 키 기반 대규모 요청은 DynamoDB를 선택함.
- 향후 방향: 클라우드 DB는 서버리스, 글로벌 복제, 자동 튜닝과 결합되어 운영 자동화 범위를 넓힘.
