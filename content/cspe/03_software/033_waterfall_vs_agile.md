# 📖 【암기용】 개념 완전 이해

> 목적: 폭포수와 애자일의 차이를 처음 봐도 요구사항·납기·품질 관점으로 이해하게 만든다. 시험 답안 양식이 아니라, 이해를 위한 친절한 설명이다.

## 한눈에
- **개요**: 폭포수는 단계 순차 진행, 애자일은 짧은 반복으로 제품을 진화시키는 개발 방식
- **왜 필요한가**: 모든 프로젝트에 같은 방법론을 적용하면 변경 비용과 품질 리스크가 커진다. 요구사항 안정성, 규제, 팀 규모, 릴리스 빈도에 맞춰 선택해야 한다.
- **핵심 직관**: 폭포수는 건축 설계처럼 시작 전 확정이 핵심이고, 애자일은 제품 실험처럼 사용자 피드백을 반복 반영한다.

## 깊이 이해
- **배경·문제의식**: 폭포수는 분석-설계-구현-테스트가 단계별로 진행되어 계약·감사에 맞지만, 변경이 늦게 발생하면 재작업 비용이 커진다. 애자일은 1~4주 반복으로 작동 제품을 만들지만 범위·우선순위 관리가 약하면 납기 예측이 흔들린다.
- **작동 원리**: 폭포수는 stage gate 승인으로 다음 단계 진입을 통제한다. 애자일은 backlog, sprint, review, retrospective를 반복해 요구사항을 조정한다. 둘의 차이는 문서 유무가 아니라 변경을 언제, 어떤 비용으로 받아들이는가이다.
- **비유**: 폭포수는 도면 승인 후 교량을 짓는 방식이고, 애자일은 앱 기능을 2주마다 출시해 사용 데이터를 보고 고치는 방식이다.
- **구체 예시**: 공공 금융 정산 시스템은 감사 산출물과 승인 단계가 필요해 V-Model 적합도가 높고, 모바일 추천 기능은 A/B 테스트와 주간 배포가 필요해 애자일 적합도가 높음.
- **흔한 오해·주의점**: 애자일은 문서를 만들지 않는 방식이 아니다. user story, acceptance criteria, definition of done, burndown chart가 있어야 통제 가능함.

## 연결 개념
- Stage Gate: 폭포수 모델의 단계 승인 통제 방식
- Scrum: 애자일 구현 프레임워크
- Change Cost Curve: 요구사항 변경 시점에 따른 비용 증가 곡선

# 📝 【답안용】 시험 답안 템플릿

> 목적: 시험장에서 25분에 그대로 쓰는 답안 양식. 작성방식(추상표현 금지·수치·도식·문제유형 전환)을 엄격히 지킨다.
> 핵심: 폭포수와 애자일 비교는 선호 논쟁이 아니라 요구사항 안정성, 규제 감사, 릴리스 빈도, 변경 비용의 선택 문제이다.

## 핵심 인사이트 (3줄 요약)

> 1. **본질**: Waterfall은 순차 단계 승인 모델, Agile은 반복 피드백 기반 점진 개발 모델이다.
> 2. **가치**: Waterfall은 기준선·감사 추적성, Agile은 변화 대응·고객 피드백 반영에 초점을 둔다.
> 3. **판단 포인트**: 요구사항 고정·규제 산출물은 Waterfall/V-Model, 시장 반응·잦은 릴리스는 Agile/Scrum을 선택한다.

## 출제 의도 및 답안 포인트

| 출제 의도 | 반드시 짚을 핵심 | 감점 회피 포인트 |
|:---|:---|:---|
| 방법론 차이와 선택 기준 확인 | 단계 순차, iteration, stage gate, backlog, change cost | Waterfall을 낡은 방식, Agile을 만능으로 단정 |
| 프로젝트 특성별 적용 판단 확인 | 요구사항 안정성, 규제, 팀 성숙도, 릴리스 빈도 | 문서 유무만 비교 |
| 품질·납기 trade-off 이해 확인 | 승인 기준, velocity, defect leakage, 변경 실패율 | 테스트와 품질 게이트 누락 |

> 요약: 이 문제는 두 방법론의 장단점보다 조건별 선택 기준과 혼합 적용 방안을 요구한다.

---

## Ⅰ. 개요 및 필요성

Waterfall과 Agile은 변경 통제 방식이 다른 개발 모델이다.
Waterfall은 요구사항을 초기에 고정하고 단계별 승인으로 품질을 통제한다.
Agile은 짧은 반복과 고객 피드백으로 변경을 흡수하므로, 프로젝트 특성별 선택 기준이 필요함.

---

## Ⅱ. 구조 및 구성요소

```text
Waterfall: Requirement -> Design -> Implementation -> Test -> Deploy
Agile: Product Backlog -> Sprint Planning -> Build/Test -> Review -> Retrospective
Selection Control -> Requirement Stability / Compliance / Release Frequency
```

| 구성요소 | Waterfall | Agile |
|:---|:---|:---|
| 요구사항 | SRS 기준선, CCB 변경 승인 | Product backlog 지속 정제 |
| 일정 통제 | WBS, milestone, stage gate | sprint, velocity, release burndown |
| 품질 통제 | 단계별 산출물 검토, V-Model | DoD, 자동 테스트, sprint review |
| 고객 참여 | 주요 단계 승인 시 참여 | sprint review마다 피드백 |

> 요약: Waterfall은 기준선과 승인, Agile은 backlog와 반복 피드백으로 프로젝트를 통제한다.

---

## Ⅲ. 동작원리 및 흐름도

```text
프로젝트 조건 분석 -> 요구사항 변동성 판단 -> 규제·감사 요구 확인
-> Waterfall / Agile / Hybrid 선택 -> 품질 게이트 설정 -> 지표 측정
```

| 단계 | 처리 내용 | 검증 기준 |
|:---:|:---|:---|
| 1 | 요구사항 안정성 평가 | 월 변경률 5% 이하 여부 |
| 2 | 규제·계약 산출물 확인 | SRS, 설계서, 시험성적서 필요 여부 |
| 3 | 반복 개발 단위 설정 | sprint 1~4주, release cadence |
| 4 | 품질 게이트 운영 | 결함 유출률 2% 이하, DoD 준수 |
| 5 | 납기·변경 지표 측정 | velocity 변동률, 변경 승인 리드타임 |

> 요약: 방법론 선택은 요구사항 변동성과 규제 산출물 수준을 먼저 평가한 뒤 품질 지표로 보정한다.

---

## Ⅳ. 특징

| 구분 | Waterfall | Agile | 수치·판단 포인트 |
|:---|:---|:---|:---|
| 변경 수용 | 기준선 이후 CCB 승인 | backlog 우선순위 조정 | 월 변경률 10% 이상이면 Agile 적합 |
| 납기 예측 | 초기 일정 기준선 | velocity 기반 예측 | velocity 변동률 20% 이하 관리 |
| 품질 확보 | 산출물 검토와 테스트 단계 | 자동 테스트와 지속 피드백 | 자동 회귀 테스트 70% 이상 |
| 규제 대응 | 감사 추적성 확보 | 산출물 경량화 시 보완 필요 | ISO/IEC/IEEE 12207, CMMI |

> 요약: Waterfall은 감사·계약 통제, Agile은 변화 반영과 릴리스 흐름에서 판단 가치가 갈린다.

---

## Ⅴ. 심화 비교 및 적용 판단

| 비교 축 | Waterfall 적용 | Agile 적용 | 선택 기준 |
|:---|:---|:---|:---|
| 요구사항 | 초기 확정 가능 | 탐색·변경 빈번 | 요구사항 월 변경률 5% 기준 |
| 조직·계약 | 고정 범위·고정 납기 | 제품팀·가변 범위 | 계약상 산출물 의무 여부 |
| 운영 | 대형 릴리스 | 소규모 빈번 릴리스 | 배포 빈도 주 1회 이상이면 Agile |

> 요약: 요구사항 안정성, 계약 구조, 배포 빈도가 Waterfall과 Agile 선택의 핵심 축이다.

| 리스크 | 원인 | 대응 방안 | 확인 지표 |
|:---|:---|:---|:---|
| Waterfall 재작업 | 후반 변경 발견 | prototype, 요구사항 review 강화 | 변경 요청 리드타임 |
| Agile 범위 확산 | backlog 우선순위 미통제 | PO 권한, MoSCoW, sprint goal | sprint scope change 10% 이하 |
| Hybrid 혼선 | 승인 단계와 sprint 충돌 | release gate와 sprint cadence 분리 | gate 승인 지연 건수 |

> 요약: 두 모델의 리스크는 변경 발생 시점과 승인 체계 충돌에서 발생하므로 지표 기반으로 조정해야 한다.

| 점검 항목 | 목표 기준 | 측정 방법 |
|:---|:---|:---|
| 납기 | milestone 준수율 90% 이상 또는 sprint predictability 80% 이상 | 일정 baseline, velocity |
| 품질 | 결함 유출률 2% 이하 | defect leakage, UAT defect |
| 변경 | 변경 승인 리드타임 2일 이내 또는 backlog aging 30일 이하 | CCB log, Jira aging |

> 요약: 방법론 성과는 납기, 품질, 변경 리드타임을 동일 기준으로 비교해야 한다.

## Ⅵ. 실무 적용 및 결론

**적용 방안 3개 (필수 - 단계별 또는 항목별):**
1. 공공·금융·의료 프로젝트는 Waterfall/V-Model에 SRS, RTM, 시험성적서, CCB를 배치해 감사 추적성 확보
2. 디지털 제품 개발은 Scrum 2주 sprint, product backlog, automated regression test로 피드백 주기 단축
3. 대규모 조직은 Hybrid로 계약 산출물은 stage gate, 구현은 sprint 단위로 운영하고 release gate에서 통합 검증

**결론 (2줄):**
- 기술사 판단: 요구사항 안정·규제 산출물이 우선이면 Waterfall, 탐색·시장 반응이 우선이면 Agile을 선택함
- 향후 방향: Waterfall과 Agile은 DevOps, SAFe, Value Stream 지표와 결합되어 조직 규모별 혼합 운영으로 진화함
