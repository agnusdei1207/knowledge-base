# 📖 【암기용】 개념 완전 이해

> 목적: TTA 소프트웨어 품질 평가 시험을 처음 봐도 완벽히 이해하게 만든다. 시험 답안 양식이 아니라, 이해를 위한 친절한 설명이다.

## 한눈에
- **개요**: **TTA SW 품질 평가 시험**은 한국정보통신기술협회(TTA)가 **ISO/IEC 25010 품질모델**(SQuaRE 시리즈)을 기준으로 SW 제품을 제3자 입장에서 **검증(Verification)·확인(Validation)**하고 성적서·인증서를 발급하는 활동이다.
- **왜 필요한가**: 개발사가 스스로 "우리 제품은 품질이 좋다"고 주장해도 객관적 증거가 없으면 공공 조달·기업 납품에서 신뢰받기 어렵다. 제3자 시험은 개발사의 이해관계에서 독립된 기관이 동일한 기준으로 측정한 증거를 제공한다.
- **핵심 직관**: 자동차가 공인 시험장에서 제동·충돌·배출 기준을 통과해야 판매되듯, SW도 실제 실행 제품을 표준 품질특성 기준으로 시험해 통과 증거를 남기는 것이다.

## 핵심 용어 정리 (내부에 등장하는 것들)

| 표기/용어 | 의미 | 비유 |
|:---|:---|:---|
| ISO/IEC 25010 | SW 품질 요구사항 및 평가 모델(SQuaRE) — 이 시험이 근거로 삼는 **품질 기준 표준** | 요리 경연의 심사 항목표(맛·플레이팅·위생...) |
| 8대 품질특성 | 기능적합성·성능효율성·호환성·사용성·신뢰성·보안성·유지보수성·이식성 — 25010이 정의한 병렬 평가축(아래 "깊이 이해"에서 상술) | 심사 항목표의 세부 항목들 |
| ISO/IEC 25023 | 각 품질특성을 "어떻게 수치로 측정할지" 정의한 측정 표준 — 25010의 짝 | 심사 항목을 실제 점수로 매기는 채점 기준표 |
| TTA | 한국정보통신기술협회 — 이 시험의 시행·인증 기관 | 공인 시험장 운영기관 |
| GS 인증(Good Software) | TTA가 발급하는 SW 품질 인증마크. 공공 조달 시 가점 등 실질 혜택이 있음 | 공인 시험 합격증 |
| 시험케이스(TC) | 품질특성별로 "무엇을 어떻게 확인할지" 구체화한 시험 절차 | 시험 문제지의 개별 문항 |
| 결함등급 | Blocking(시험 진행 자체가 불가) > Critical(핵심기능 불가) > Major(주요기능 오류) > Minor(경미) 순 심각도 | 화재 등급(대형/중형/소형)처럼 대응 우선순위를 정하는 척도 |
| 회귀시험(Regression Test) | 결함을 고친 뒤 "고치면서 다른 데를 망가뜨리지 않았는가"를 재확인하는 시험 | 수술 부위를 고친 뒤 다른 장기가 멀쩡한지 재검진 |
| 시험성적서/인증서 | 시험 결과, 대상 제품명·버전, 시험 범위를 명시한 공식 증빙 문서 | 시험 합격증 + 성적표 |

## 깊이 이해

### 왜 "제3자" 시험이어야 하나
- 개발사 자체 QA는 이해관계가 걸려 있어 "합격시키고 싶은 유인"이 존재한다. 제3자 시험기관은 개발사로부터 독립적이므로, 같은 기준을 다른 제품에도 동일하게 적용한다는 신뢰가 생긴다. 이것이 공공 조달에서 자체 QA 결과서가 아니라 TTA 성적서를 요구하는 이유다.

### ISO/IEC 25010의 8대 품질특성 — 무엇을 재는가
- **기능적합성**: 명시된 기능을 얼마나 완전·정확·적절하게 구현했는가. 예: 요구사항 120개 중 118개 정상 동작 → 기능 충족률 98.3%.
- **성능효율성**: 응답시간·자원사용량·처리량이 기준 내인가. 예: 동시접속 500명에서 평균 응답 2초 이내.
- **호환성**: 다른 시스템·환경과 공존·연동 가능한가. 예: Chrome/Edge/Firefox 3개 브라우저에서 동일 기능 동작.
- **사용성**: 사용자가 이해·학습·조작하기 쉬운가. 예: 신규 사용자가 안내 없이 핵심 기능 3개를 5분 내 완료.
- **신뢰성**: 장애 없이 지속 운영되는가(성숙성·가용성·장애허용성·회복성). 예: 24시간 부하시험에서 장애 0건.
- **보안성**: 기밀성·무결성·인증·부인방지가 보장되는가. 예: 권한 없는 계정으로 관리자 URL 접근 시 100% 차단.
- **유지보수성**: 결함 수정·기능 추가가 용이한가. 예: 모듈화 구조, 코드 중복률 기준 이하.
- **이식성**: 다른 환경으로 이식이 쉬운가(적응성·설치성·대체성). 예: 설치 스크립트로 30분 내 신규 서버 구축.
- 판별 원리: 시험 설계자는 이 8개 특성 중 "이 제품·이 문제에서 중요한 특성이 무엇인가"를 먼저 판단하고, 그 특성에 시험케이스를 집중 배치한다. 내부 업무용 도구는 이식성보다 사용성·신뢰성에, 대외 서비스형 제품은 보안성·성능효율성에 무게를 둔다.

### 시험 절차를 수치로 이해하기
- 접수 시 제품설명서·사용자문서·실행 SW를 받는다. 이후 요구사항추적표(RTM)로 "요구사항 120개 → 시험케이스 120개 이상"을 매핑해 추적률 100%를 확보한다.
- 시험 수행 중 결함이 나오면 등급을 매긴다. 예: Blocking 1건, Critical 3건이 나오면 재현·보완을 요구하고, 개발사가 수정하면 회귀시험으로 "이 3건이 사라졌는가 + 주변 기능이 안 깨졌는가"를 재확인한다.
- 최종적으로 Blocking·Critical 0건이 확인되면 시험성적서를 발급한다. 성적서에는 제품명, **정확한 버전**, 시험 범위(어떤 품질특성을 시험했는지)가 명시된다 — 이 버전이 실제 배포 버전과 다르면 인증의 의미가 없어진다.

### GS 인증과의 관계
- TTA 품질 시험의 결과물 중 하나가 GS 인증이다. 즉 "TTA 시험 ⊃ GS 인증" 관계로, TTA는 품질 시험 전반을 수행하는 기관이고 GS 인증은 그 시험을 통과한 제품에 부여하는 마크다. GS 인증은 공공기관 소프트웨어 사업의 우수제품 지정, 조달 심사 가점 등에 활용된다.

### 비유와 흔한 오해
- **비유**: 자동차 제조사가 신차를 출시하기 전 공인 시험장에서 제동거리·충돌안전성·배출가스를 검사받는 것과 같다. 제조사 자체 시험 데이터만으로는 판매 인가가 나지 않는다.
- **오해 1**: TTA 인증 = 보안 인증이 아니다. 보안성은 8대 특성 중 하나일 뿐이며, 전문 보안 인증(예: 취약점 진단, ISMS)과는 별개다.
- **오해 2**: 인증받은 제품이라고 영구히 안전한 게 아니다. 인증은 **특정 버전**에 대한 것이라, 이후 기능이 추가되거나 버전이 바뀌면 재시험이 필요하다.

## 연결 개념
- ISO/IEC 25010 (이 시험의 근거 품질모델 — 위 표에서 다룬 세부 개념)
- GS 인증 (TTA 시험 결과물 중 하나인 품질 인증 마크)
- 소프트웨어 테스트 (테스트케이스 설계·결함관리·회귀시험 등 이 시험이 사용하는 실행 기법)

# 📝 【답안용】 시험 답안 템플릿

> 목적: 시험장에서 25분에 그대로 쓰는 답안 양식. 작성방식(추상표현 금지·수치·도식·문제유형 전환)을 엄격히 지킨다.
> 핵심: TTA 시험은 인증 명칭보다 품질특성, 시험절차, 결함 보완, 성적서 활용, 적용 한계를 함께 써야 한다.

## 핵심 인사이트 (3줄 요약)

> 1. **본질**: TTA SW 품질 평가 시험은 실행 SW와 문서를 제3자 기준으로 시험해 품질 적합성을 확인하는 절차이다.
> 2. **가치**: 공공 조달, 제품 신뢰 증빙, 결함 개선, 사용자 문서 품질을 객관 시험 결과로 제시한다.
> 3. **판단 포인트**: ISO/IEC 25010 품질특성, 시험환경, 결함 조치율, 재시험, 인증 범위·버전을 명확히 구분한다.

## 출제 의도 및 답안 포인트

| 출제 의도 | 반드시 짚을 핵심 | 감점 회피 포인트 |
|:---|:---|:---|
| SW 품질평가 이해 확인 | 품질특성, 시험케이스, 결함관리, 인증서 | 단순 "공인 인증"으로만 설명 |
| 제3자 시험 절차 확인 | 접수, 시험설계, 수행, 보완, 재시험, 발급 | 시험환경과 제품 버전 누락 |
| 실무 적용 판단 확인 | 조달, 품질 개선, 사용자 문서 검증 | 보안·성능 전체 보증으로 과장 |

> 요약: 이 문제는 TTA 시험의 절차와 품질특성별 증거를 제품 출시·조달 판단에 연결하는 답안을 요구한다.

## Ⅰ. 개요 및 필요성

- 개요: 제3자 SW 품질검증
- 배경: SW 제품은 기능 구현뿐 아니라 설치성, 사용성, 호환성, 신뢰성, 문서 품질을 증명해야 한다.
- 필요성: TTA 시험·인증 결과로 납품, 개선 조치, 품질 증적을 제시해야 한다.

---

## Ⅱ. 구조 및 구성요소

```text
제품/문서 접수 -> 품질모델 기준 설정 -> 시험설계
-> 시험수행 -> 결함보고 -> 보완/재시험
-> 성적서/인증서 -> 조달/납품 활용
```

| 구성요소 | 역할 | 특이사항 |
|:---|:---|:---|
| 품질모델 | 평가 기준 정의 | ISO/IEC 25010, 25023 참조 |
| 시험환경 | 실제 운영과 유사한 조건 구성 | OS, DB, Browser, Network 명시 |
| 결함관리 | 결함 등급·재현·조치 추적 | blocking defect 0건 목표 |
| 성적서/인증서 | 평가 결과와 범위 증빙 | 제품명, 버전, 시험 범위 명시 |

> 요약: 품질 평가는 기준, 환경, 결함관리, 결과 증빙이 함께 있어야 활용 가능하다.

## Ⅲ. 동작원리 및 흐름도

```text
신청 -> 제품설명서 검토 -> 시험항목 도출
-> 테스트케이스 실행 -> 결함 등록
-> 보완 확인 -> 회귀시험 -> 결과 발급
```

| 단계 | 처리 내용 | 검증 기준 |
|:---:|:---|:---|
| 1 | 제품설명서·사용자 문서 검토 | 필수 기능 추적률 100% |
| 2 | 기능·신뢰·사용·호환 시험 설계 | 품질특성별 TC 작성 |
| 3 | 시험 실행과 결함 등급화 | critical/blocking 0건 |
| 4 | 보완 후 회귀시험과 결과 발급 | 재발 결함 0건 |

> 요약: TTA 시험은 문서 기반 요구를 테스트케이스로 바꾸고 결함 보완을 확인한 뒤 결과를 발급한다.

## Ⅴ. 심화 비교 및 적용 판단

| 구분 | 기존/대안 | TTA SW Quality Test | 선택 기준 |
|:---|:---|:---|:---|
| 구조 | 내부 QA 결과 | 제3자 시험·성적서 | 공공 조달·외부 납품 제품 |
| 비용/성능 | 즉시 릴리스 | 시험 접수·보완 일정 | 출시 일정 4주 이상 여유 |
| 운영/위험 | 객관성 부족 | 범위 제한·버전 불일치 | 인증 범위 명확화 |

> 요약: 외부 신뢰 증빙이 필요한 제품은 TTA 시험을 선택하되 일정과 인증 범위를 사전에 반영해야 한다.

| 리스크 | 원인 | 대응 방안 | 확인 지표 |
|:---|:---|:---|:---|
| 인증 범위 오해 | 버전·모듈 변경 | 인증 대상과 배포 버전 매핑 | 버전 불일치 0건 |
| 시험 지연 | 결함 보완 반복 | 사전 자체 TC와 결함 triage | 재시험 횟수 1회 이하 |
| 품질특성 누락 | 기능 시험 편중 | ISO/IEC 25010 특성 매핑 | 품질특성 커버리지 100% |

> 요약: 주요 리스크는 범위 오해, 일정 지연, 품질특성 누락이며 사전 매핑과 결함관리로 줄인다.

| 점검 항목 | 목표 기준 | 측정 방법 |
|:---|:---|:---|
| 시험 준비 | 요구사항-TC 추적률 100% | RTM 검토 |
| 결함 품질 | critical/blocking 0건 | defect report |
| 인증 활용 | 성적서·인증서·버전 일치 100% | release checklist |

> 요약: 시험 성과는 추적률, 치명 결함 0건, 인증 버전 일치율로 판단한다.

## Ⅵ. 실무 적용 및 결론

**적용 방안 3개 (필수 — 단계별 또는 항목별):**
1. 시험 신청 전 ISO/IEC 25010 품질특성별 자체 테스트케이스를 만들고 요구사항 추적률 100%를 확보
2. 제품설명서, 사용자취급설명서, 설치 매뉴얼, 릴리스 노트를 시험 대상 버전과 동일하게 freeze
3. 결함 등급별 SLA를 critical 2영업일, major 5영업일로 정하고 보완 후 회귀시험 증적을 릴리스 저장소에 보관

**결론 (2줄):**
- 기술사 판단: 공공 조달·외부 납품 SW는 TTA 품질 시험을 품질 증거로 활용하되 인증 범위와 실제 배포 버전 일치가 선결 조건
- 향후 방향: 품질 평가는 CI 테스트, 정적분석, 보안점검, 사용성 평가와 결합된 릴리스 품질 게이트로 확장
