# 📖 【암기용】 개념 완전 이해

> 목적: 이 개념을 처음 보는 사람도 완벽히 이해하게 만든다. 시험 답안 양식이 아니라, 이해를 위한 친절한 설명이다.

## 한눈에
- **개요**: **디스크 스케줄링**은 운영체제 커널의 **I/O 관리** 기법 중 하나로, 여러 디스크 접근 요청이 쌓인 큐(Queue)를 재정렬하여 헤더(Head)의 **탐색 시간(Seek Time)**을 최소화하는 알고리즘이다.
- **왜 필요한가**: 하드디스크(HDD)는 물리적으로 팔(Actuator Arm)을 움직여 원하는 트랙을 찾는 기계 장치라, 요청이 들어온 순서대로 무작정 처리하면 헤더가 디스크 안쪽과 바깥쪽을 반복해서 오가며 시간을 낭비한다. 이 이동 경로를 똑똑하게 짜는 것이 디스크 스케줄링이다.
- **핵심 직관**: 여러 층에서 호출 버튼이 눌린 엘리베이터를 생각하면 된다. 누른 순서대로(1층→10층→2층) 움직이면 비효율적이지만, 방향을 정해 한쪽으로 쓸고 지나가면(엘리베이터 알고리즘) 훨씬 효율적이다.

## 핵심 용어 정리 (내부에 등장하는 것들)

| 용어 | 의미 | 비유 |
|:---|:---|:---|
| I/O 관리 | 커널이 저장장치·네트워크 등 입출력 장치를 다루는 총괄 영역 — 디스크 스케줄링이 속한 상위 분야 | 공장의 물류 관리 전체 |
| 디스크 접근 시간 | 탐색 시간 + 회전 지연 + 전송 시간의 합 | 택배가 도착하기까지 걸리는 총 시간 |
| 탐색 시간 (Seek Time) | 헤더가 목표 트랙(실린더)까지 이동하는 시간 — 접근 시간의 가장 큰 병목 | 엘리베이터가 원하는 층까지 이동하는 시간 |
| 회전 지연 (Rotational Latency) | 플래터가 돌아 원하는 섹터가 헤더 밑에 오기까지 기다리는 시간 | 회전문이 내가 탈 위치까지 돌아오길 기다리는 시간 |
| 전송 시간 (Transfer Time) | 헤더가 자리를 잡은 뒤 실제로 데이터를 읽어 옮기는 시간 | 문이 열려 짐을 싣는 시간 |
| FCFS (First Come First Serve) | 요청이 도착한 순서 그대로 처리 | 번호표 없이 새치기 없는 줄서기 |
| SSTF (Shortest Seek Time First) | 현재 헤더 위치에서 가장 가까운 요청부터 처리 | 가까운 손님부터 서빙하는 종업원 |
| SCAN | 한쪽 끝까지 쭉 이동하며 처리하고, 끝에 닿으면 방향을 바꿔 반대로 이동 | 엘리베이터가 꼭대기까지 올라갔다 내려오는 운행 |
| C-SCAN (Circular SCAN) | 한 방향으로만 처리하고, 끝에 닿으면 처리 없이 반대쪽 끝으로 돌아와 같은 방향으로 다시 처리 | 편도 순환 버스 노선 |
| 기아 (Starvation) | 특정 요청이 계속 뒤로 밀려 무한정 대기하는 현상 | 인기 없는 정류장에 버스가 영영 안 옴 |
| 버퍼 캐시 | 커널이 RAM 일부를 떼어 디스크에서 읽은 블록을 임시 저장해두는 공간 | 자주 찾는 서류를 책상 위에 미리 꺼내둠 |
| DMA (Direct Memory Access) | CPU를 거치지 않고 디스크와 메모리 사이를 직접 오가는 전용 하드웨어 | CPU를 대신해 짐을 나르는 운반 로봇 |

## 깊이 이해

### 디스크 접근 시간의 구조 — 왜 탐색 시간이 병목인가 (수치로 확인)
7200RPM 하드디스크를 기준으로 계산해보면 구조가 보인다. 1분에 7200번 도니까 1초에 120번, 한 바퀴 도는 데 걸리는 시간은 1000ms÷120 ≈ 8.33ms다. 회전 지연은 평균적으로 반 바퀴를 기다리는 것이므로 약 4.17ms. 여기에 평균 탐색 시간은 트랙 간 이동 거리에 따라 다르지만 통상 8~9ms 수준이다. 반면 4KB 한 블록을 옮기는 전송 시간은 초당 150MB 전송 기준으로 4096바이트÷157,286,400바이트 ≈ 0.026ms에 불과하다. 즉 탐색 시간(약 9ms)과 회전 지연(약 4ms)을 합친 약 13ms가 접근 시간 대부분을 차지하고, 전송 시간은 그 0.2%도 안 된다. 그래서 디스크 스케줄링은 오직 탐색 시간을 줄이는 데 집중한다.

### 4개 알고리즘을 같은 예제로 비교하기 (수치 워크드 예제)
헤더가 53번 트랙에 있고, 요청 큐가 `98, 183, 37, 122, 14, 124, 65, 67` 순서로 들어왔다고 하자.
- **FCFS**: 온 순서 그대로 53→98→183→37→122→14→124→65→67로 움직이면 총 이동 거리는 45+85+146+85+108+110+59+2 = **640**이다. 디스크 양 끝을 세 번이나 왕복해 낭비가 심하다.
- **SSTF**: 매번 가장 가까운 트랙을 골라 53→65→67→37→14→98→122→124→183으로 움직이면 총 이동 거리는 **236**으로, FCFS의 약 37%(63% 절감)에 그친다. 다만 처음부터 계속 53 근처 요청만 들어오면 183번 요청은 영원히 밀릴 수 있다(기아).
- **SCAN**: 방향을 정해(여기선 아래쪽 먼저) 53→37→14→0(끝점에서 방향 전환)→65→67→98→122→124→183으로 움직이면 총 이동 거리는 **236**으로 SSTF와 비슷하지만, 방향성이 있어 특정 요청이 무한정 밀리지 않는다.
- **C-SCAN**: 한 방향(위쪽)으로만 처리하고 끝(199)에 닿으면 처리 없이 0으로 순간 복귀한 뒤 다시 위로 처리한다. 53→65→67→…→183→199→0→14→37로 움직이면 총 이동 거리는 **382**로 SSTF·SCAN보다 62% 더 길다. 대신 어떤 트랙이든 헤더를 만나는 주기가 균일해 응답 시간 편차가 가장 작다 — 즉 **이동 거리를 더 쓰는 대신 공평성을 산다.**

### 판별 원리 — 언제 무엇을 쓰나
- 다중 사용자가 몰리는 서버에서 특정 사용자의 요청이 영원히 밀리면 안 되므로, 실무에서는 SSTF보다 SCAN 계열(리눅스의 `cfq`, `deadline` 스케줄러)을 기본값으로 쓴다.
- SSD(낸드 플래시)는 기계식 헤더가 없어 어느 주소를 찾든 접근 속도가 동일하다(탐색 시간 ≈ 0). 이 경우 SCAN처럼 순서를 계산하는 것 자체가 CPU 낭비이므로, 리눅스는 SSD를 인식하면 스케줄러를 `NOOP`(=FCFS와 동일하게 그대로 흘려보냄)이나 `none`, `kyber`, `mq-deadline`으로 바꾼다.

### 흔한 오해
- "회전 지연이 접근 시간의 가장 큰 병목이다"는 틀렸다. 위 수치에서 보듯 탐색 시간(약 9ms)이 회전 지연(약 4ms)보다 크다.
- "SSD 시대에도 SCAN 최적화가 여전히 중요하다"도 틀렸다. SSD는 탐색 시간이라는 개념 자체가 사실상 사라지므로 SCAN의 존재 이유가 없어진다.

## 연결 개념
- **버퍼 캐시**: 애초에 디스크까지 가지 않도록 RAM에서 요청을 걸러내는 앞단 방어선 — 스케줄링이 발동할 일 자체를 줄인다.
- **DMA**: 스케줄링으로 헤더 이동을 줄인 뒤, 실제 데이터 이동은 CPU 대신 전담 하드웨어가 처리해 CPU 부담을 없앤다.
- **NVMe / blk-mq**: SSD·NVMe 시대에 디스크 스케줄링 큐 자체를 CPU 코어 수만큼 병렬화한 후속 기술(Ⅳ 참고).

# 📝 【답안용】 시험 답안 템플릿

> 목적: 시험장에서 25분에 그대로 쓰는 답안 양식. 작성방식(추상표현 금지·수치·도식·문제유형 전환)을 엄격히 지킨다.
> 핵심: 이 시험은 정보를 많이 나열하는 시험이 아니라, 문제 신호어에서 출제자 의도를 읽고 핵심 논점을 선별해 쓰는 시험이다.

## 핵심 인사이트 (3줄 요약)

> 1. **본질**: 커널의 I/O 서브시스템이 다수의 블록(Block) 디스크 접근 요청 큐를 재정렬하여, 기계식 헤더의 물리적 탐색 시간(Seek Time)을 극적으로 최소화하는 OS 스케줄링 알고리즘이다.
> 2. **가치**: CPU(나노초)와 디스크(밀리초) 간의 100만 배 속도 갭을 버퍼링과 엘리베이터 알고리즘(SCAN 계열)으로 완충하여, I/O 병목으로 인한 전체 시스템 처리량(Throughput) 저하를 방어한다.
> 3. **판단 포인트**: 탐색 거리 최소화(SSTF)와 기아 현상(Starvation) 간의 트레이드오프를 도식화하고, 기계식 부품(Actuator)이 없는 현대 SSD 플래시 환경에서는 스케줄링 무용론(NOOP/None)이 적용됨을 반드시 짚어내야 한다.

## 출제 의도 및 답안 포인트

| 출제 의도 | 반드시 짚을 핵심 | 감점 회피 포인트 |
|:---|:---|:---|
| 기계식 디스크의 I/O 접근 시간 분해와 병목 도출 | `접근 시간 = 탐색(Seek) + 회전(Latency) + 전송(Transfer)` | 회전 지연 시간(플래터 도는 시간)이 가장 느리다고 적는 착각 (탐색 시간이 압도적 병목임) |
| 스케줄링 알고리즘의 동선(Path)과 공평성 트레이드오프 | SSTF(가장 짧음/기아 발생) vs C-SCAN(응답 시간 편차 최소화) | SCAN을 엘리베이터에 비유하지 못하고 큐 정렬로만 추상적으로 서술 |
| 최신 스토리지 환경(SSD)으로의 패러다임 전환 | SSD는 Seek Time이 0이므로 NOOP(FCFS) 스케줄러로 전환 | NVMe 시대에도 SCAN 최적화가 중요하다고 우기는 구시대적 맹점 |

> 요약: 바늘이 이리저리 튀는 기계식 HDD 시절에는 SCAN 스케줄링이 구원자였지만, 낸드 플래시(SSD) 시대가 오면서 OS 커널은 20년 된 이 훌륭한 큐 정렬 로직을 스스로 휴지통에 던져 넣었다.

## Ⅰ. 개요 및 필요성

- 정의: 다중 프로그래밍 환경에서 쏟아지는 I/O 요청을 큐(Queue)에 버퍼링한 뒤, 실린더(Cylinder)를 이동하는 헤더의 동선을 재배치하여 평균 탐색 시간을 단축하는 커널 모듈 기법
- 배경: 기계식 스토리지(HDD)의 탐색 시간 지연(Seek Time Latency)은 수십 밀리초(ms)에 달해 CPU 연산 성능을 깎아먹는 폰 노이만 아키텍처의 최대 병목 구간으로 작용
- 필요성: 단순 FCFS 처리 시 발생하는 헤더의 횡단(Sweep) 낭비를 막고, 특정 실린더 요청이 무한 대기하는 기아(Starvation) 현상 없이 균일한 응답 시간(Variance)을 보장하기 위함

## Ⅱ. 디스크 스케줄링 알고리즘 (FCFS, SSTF, SCAN, C-SCAN) 

헤더 시작 위치: `53` / 요청 큐: `98, 183, 37, 122, 14, 124, 65, 67`

```text
[ SSTF (Shortest Seek Time First) ] - 거리 우선
53 -> 65 -> 67 -> 37 -> 14 -> 98 -> 122 -> 124 -> 183 (총 이동 236)
🚨 한계: 50 근처 요청만 계속 들어오면, 183번 요청은 평생 굶어 죽음 (Starvation).

[ SCAN (엘리베이터) & C-SCAN ] - 방향성 우선
(SCAN)   53 -> 37 -> 14 -> 0(끝점) -> 65 -> 67 -> 98 -> 122 -> 124 -> 183
(C-SCAN) 53 -> 65 -> 67 ... -> 183 -> 199(끝점) ==> 0(빛의 속도 귀환) -> 14 -> 37
✅ C-SCAN 가치: 양끝 실린더나 중간 실린더나 동일한 밀도로 서비스받아 응답시간 편차가 제로(0)에 수렴.
```

| 스케줄링 알고리즘 | 헤더 이동 철학 (결정 룰) | 치명적 맹점 및 한계 |
|:---|:---|:---|
| **FCFS** | 큐에 도착한 시간적 순서 그대로 무지성 이동 | 디스크 양끝을 횡단하는 핑퐁 현상 폭주 |
| **SSTF** | 현재 헤더 위치에서 탐색 거리가 가장 짧은 놈 우선 | 양극단(디스크 외곽) 실린더의 완벽한 기아 상태 |
| **SCAN** | 한쪽 방향 끝까지 전진 후 역방향으로 스윕(Sweep) | 양끝 트랙은 헤더를 만나는 주기가 2배 길어 불공평함 |
| **C-SCAN** | 끝에 닿으면 서브 안 하고 반대 끝으로 회귀 후 단방향 전진 | 응답 편차는 완벽하나, 빈 깡통으로 돌아가는 복귀 오버헤드 |

> 요약: 철저하게 물리적인 기계 쇳덩이(바늘)를 어떻게 굴려야 기름(시간)을 아낄 수 있는지에 대한 극도로 로우레벨(Low-level)적인 고찰이다.

## Ⅲ. 현대 운영체제의 I/O 스택과 하드웨어 추상화(DMA)

디스크 스케줄링 혼자서는 I/O 병목을 다 풀 수 없다. OS는 램(RAM)과 전담 칩셋을 동원한다.

| 현대 커널 I/O 인프라 | 동작 원리 메커니즘 | CPU 병목 해소(Off-loading) 가치 |
|:---|:---|:---|
| **버퍼 캐시 (Buffer Cache)** | 커널이 물리 RAM의 절반을 강제 징발해, 디스크에서 읽은 블록을 램에 임시 캐싱 | Hit 시 디스크 접근 자체를 0(Zero)으로 소거하여 100만 배 속도 부스팅 (스케줄링 발동 억제) |
| **DMA (Direct Memory Access)** | 디스크 컨트롤러와 램 사이에 CPU를 거치지 않는 직통 고속도로 하드웨어 회로 신설 | 과거엔 1바이트마다 CPU가 인터럽트를 받아 운반(PIO)하여 CPU가 뻗었으나, DMA 도입 후 CPU 연산과 I/O 완벽 분리 병렬화 |
| **I/O 스케줄러 (Block Layer)** | 커널의 블록 디바이스 계층에서 인접한 작은 I/O 요청 덩어리들을 큰 블록 하나로 `Merge(병합)` | 디스크 헤더가 2번 내려찍을 것을 1번으로 압축하는 선제적 튜닝 |

> 요약: 최고로 훌륭한 디스크 스케줄링은 "아예 디스크로 가지 않게 램(버퍼 캐시)에서 쳐내는 것"이고, 어쩔 수 없이 갈 거면 "CPU 대신 노예(DMA)를 시켜서 다녀오게 하는 것"이다.

## Ⅳ. 패러다임의 붕괴: SSD 환경에서의 스케줄링 무용론

낸드 플래시 메모리(SSD) 시대의 도래로 기계식 바늘(Actuator)이 증발하면서 기존의 모든 철학이 휴지통에 들어갔다.

| 리스크 요인 | HDD 기반 스케줄러(SCAN) 적용 시 발생 시나리오 | 차세대 커널 대응 방안 (SSD 튜닝) |
|:---|:---|:---|
| 소프트웨어적 헛수고(Overhead) | SSD는 1번 블록이나 100번 블록이나 전기적 접근 속도가 똑같음(탐색 시간 0). 커널이 SCAN 하겠다고 CPU를 써서 큐(Queue)를 무거운 알고리즘으로 줄 세우면 램과 CPU 사이클만 낭비 | 리눅스 커널 스케줄러를 엘리베이터(`cfq`)에서 **`NOOP` (또는 `None`)**으로 변경. 큐 정렬 연산을 0으로 만들고 FIFO로 냅다 하드웨어에 던지는 것이 가장 빠름 |
| NVMe 멀티 큐 병목 폭발 | NVMe(PCIe)는 초당 100만 번(1M IOPS)의 I/O를 날리는데, 구형 단일 큐(Single-queue) 스케줄러는 Lock 경합 때문에 소프트웨어 큐 자체가 뻗어버림 | **Multi-Queue Block I/O (blk-mq)** 도입. CPU 코어 개수만큼 하드웨어 큐를 다중화(Mapping)하고 Lock-free 설계로 수백만 IOPS 병목 완전 제거 |

> 요약: 스토리지 하드웨어가 너무 빨라지자, 이를 똑똑하게 조율하려던 OS 커널 스케줄러 계층 자체가 가장 거대한 속도 저해물(Bottleneck)로 전락하는 아이러니가 연출되었다.

## Ⅴ. 실무 적용 방안 및 결론

**적용 방안 3개:**
1. [Linux I/O 스케줄러 튜닝 (SSD)] 데이터베이스 서버 배포 시, 하드웨어가 엔터프라이즈 NVMe SSD일 경우 `/sys/block/sda/queue/scheduler` 값을 조회하여 구형 `cfq`나 `deadline`으로 잡혀있다면 즉시 `none` 또는 `mq-deadline`으로 강제 튜닝해 CPU 스케줄링 오버헤드 원천 소거
2. [멀티미디어 스트리밍 서버 Deadline 보장] 대용량 기계식 HDD 어레이(RAID)를 쓰는 VOD 서버 환경에서는, C-SCAN의 공평성을 차용한 `deadline` 스케줄러를 적용하여 특정 클라이언트 영상 패킷의 읽기(Read) 응답 지연(Starvation)을 막고 QoS(Quality of Service) 보장
3. [EBS 볼륨 블록 병합(Merge) 최적화] AWS EC2 프로비저닝 시, 애플리케이션 로그를 4KB씩 1초에 1,000번 쓰면 커널 I/O 스케줄러가 이를 병합(Merge)하지 못해 EBS IOPS 과금 폭탄을 맞으므로, 앱 레벨에서 버퍼(Logback)를 키워 1MB 단위로 플러시(Flush) 하도록 백프레셔(Backpressure) 통제

**결론:**
- 기술사 판단: 디스크 스케줄링은 "하드웨어의 느린 물리적 제약(바늘 이동)을 소프트웨어의 수학적 논리(엘리베이터)로 메운다"는 운영체제 아키텍처의 찬란한 유산이다. SSTF와 SCAN은 자원 최적화라는 시스템 공학의 본질을 완벽히 투영한다.
- 향후 방향: 모터 기반 디스크 폼팩터가 사실상 종말을 고하고 비휘발성 메모리(NVMe/SCM) 생태계로 진입함에 따라, 차세대 I/O 서브시스템은 커널 스케줄링 큐를 완전히 우회하여 애플리케이션이 스토리지 H/W를 직접 때리는 SPDK(Storage Performance Development Kit)나 커널 바이패스(Kernel Bypass) 아키텍처로 도약하고 있다.
