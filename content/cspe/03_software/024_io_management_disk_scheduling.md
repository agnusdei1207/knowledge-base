# 📖 【암기용】 개념 완전 이해

## 한눈에
- **개요**: I/O 관리는 CPU(나노초)와 I/O 장치(밀리초) 간 극심한 속도 차이를 완충하는 운영체제 기능이며, **디스크 스케줄링**은 HDD의 물리적 헤드 이동 거리를 최소화하도록 I/O 요청 순서를 재배열하는 알고리즘임.
- **왜 필요한가**: I/O 요청을 도착 순서대로 처리하면 디스크 헤드가 양끝을 왕복하며 탐색 시간(Seek Time)을 낭비해 전체 시스템 처리량이 급락함. 헤드 이동 경로를 최적화해 처리량과 응답 시간의 균형을 확보해야 함.
- **핵심 직관**: 엘리베이터가 1층→10층→2층→9층 순서로 버튼이 눌렸다고 그대로 가지 않고, 올라가는 길에 2→9→10층을 처리하고 내려가며 1층을 처리하는 것(SCAN 알고리즘)과 같은 원리임.

## 핵심 용어 정리 (내부에 등장하는 것들)

| 용어/표기 | 의미 | 비유·예 |
|:---|:---|:---|
| 디스크 스케줄링 (상위 키워드) | I/O 큐의 요청을 헤드 이동 최소화 순서로 재배열하는 알고리즘 | 배달 경로 최적화 |
| 탐색 시간 (Seek Time) | 디스크 헤드가 원하는 트랙(실린더)으로 이동하는 물리적 시간 (HDD 기준 3~10ms) | 레코드판 바늘을 옮기는 시간 |
| 회전 지연 (Rotational Latency) | 트랙 내 원하는 섹터가 헤드 아래로 회전해 올 때까지의 대기 시간 (7200RPM 기준 평균 4.2ms) | 원하는 곡 시작점이 올 때까지 대기 |
| FCFS | First Come First Served — 도착 순서대로 처리 (공평하지만 비효율) | 줄 선 순서대로 |
| SSTF | Shortest Seek Time First — 현재 헤드에서 가장 가까운 요청 우선 (기아 발생) | 가장 가까운 배달지 우선 |
| SCAN | 엘리베이터 알고리즘 — 한 방향 끝까지 진행하며 처리, 역방향 전환 (기아 해결) | 엘리베이터 운행 |
| C-SCAN | Circular SCAN — 한 방향만 처리, 끝에서 처음으로 빠르게 회귀 (응답 편차 최소) | 순환 버스 노선 |
| NOOP/mq-deadline | SSD용 스케줄러 — 탐색 시간이 없으므로 단순 FIFO 또는 마감 기한 기반 | 택배 접수 순서대로 |

## 깊이 이해
- **배경·문제의식**: HDD는 기계식 액추에이터 암(Arm)으로 헤드를 이동시키므로 탐색 시간이 디스크 접근 시간의 대부분(60~70%)을 차지함. 무작위 I/O를 순서대로 처리하면 헤드가 디스크 양끝을 왕복하며 시간을 낭비함. 디스크 스케줄링은 이 탐색 시간을 최소화하기 위해 요청 순서를 재배열함.
- **작동 원리(알고리즘별)**:
  - **FCFS**: 큐에 도착한 순서대로 처리. 구현이 단순하지만 헤드 이동 거리가 최적화되지 않음.
  - **SSTF**: 현재 헤드 위치에서 가장 가까운 트랙의 요청을 먼저 처리. 처리량은 높지만 외곽 트랙 요청이 무한 대기하는 기아(Starvation) 발생.
  - **SCAN**: 헤드가 한 방향으로 끝까지 이동하며 경로상의 모든 요청을 처리한 후 역방향으로 전환. 기아를 해결하되, 중앙 트랙이 양끝보다 서비스 빈도가 높음.
  - **C-SCAN**: 한 방향으로만 서비스하고 끝에 도달하면 반대 끝으로 빠르게 회귀(서비스 없이). 응답 시간 편차를 최소화해 멀티테넌트 환경에 적합함.
- **비유**: FCFS는 택시가 콜 순서대로 이동, SSTF는 가장 가까운 승객만 우선 태움(먼 승객 무시), SCAN은 시내버스가 한 방향 노선을 끝까지 운행, C-SCAN은 순환 버스가 회차점에서 다시 출발.
- **구체 예시**: 큐에 트랙 98, 183, 37, 122, 14, 124, 65, 67이 있고 현재 헤드 위치가 53일 때, FCFS 총 이동거리 = 640, SSTF = 236, SCAN = 236(방향 고려 시 변동), C-SCAN ≈ 382.
- **흔한 오해·주의점**: (1) SSD는 물리적 헤드가 없으므로 SCAN 등 탐색 최적화 알고리즘이 불필요하고 오히려 CPU 오버헤드만 발생함 → NOOP·mq-deadline 스케줄러로 전환. (2) 리눅스 커널 5.0+에서는 블록 멀티큐(blk-mq) 기반으로 전환되어 기존 단일 큐 CFQ가 제거됨.

## 연결 개념
- (022 파일 시스템) 파일 시스템이 발행한 블록 I/O를 디스크 스케줄러가 최적화
- DMA(Direct Memory Access) — I/O 데이터 전송 시 CPU 개입을 최소화하는 H/W 기법
- 인터럽트·폴링 — I/O 완료 통지 방식

# 📝 【답안용】 시험 답안 템플릿

## 핵심 인사이트 (3줄 요약)

> 1. **본질**: CPU(ns)와 I/O 장치(ms) 간 속도 차이를 완충하기 위해 HDD 헤드 이동 거리를 최소화하는 순서 최적화 알고리즘임.
> 2. **가치**: I/O 처리량(Throughput) 향상과 특정 요청의 기아(Starvation) 방지를 통해 응답 시간 형평성을 보장함.
> 3. **판단 포인트**: HDD 환경은 SCAN/C-SCAN으로 헤드 이동을 통제하고, SSD 환경은 NOOP·mq-deadline으로 전환하는 매체 특성 기반 아키텍처 판단이 핵심임.

## 출제 의도 및 답안 포인트

| 출제 의도 | 반드시 짚을 핵심 | 감점 회피 포인트 |
|:---|:---|:---|
| 디스크 I/O 병목 원인과 스케줄링 기법 진화 | Seek Time, SSTF 기아, SCAN 방향성, C-SCAN 형평성 | SSD 특성 간과하고 HDD 스케줄링만 서술 |
| 매체 특성에 맞는 스케줄러 선택 기준 | HDD(SCAN/C-SCAN) vs SSD(NOOP/mq-deadline) | 최신 블록 멀티큐(blk-mq) 아키텍처 누락 |

> 요약: FCFS->SSTF(기아)->SCAN(방향성)->C-SCAN(형평성)의 진화 축을 대조하고, SSD 전환에 따른 스케줄러 변경 판단을 제시해야 함.

---

## Ⅰ. 개요 및 필요성

- 개요: 디스크 접근 시간의 대부분을 차지하는 탐색 시간(Seek Time)을 최소화하기 위해 I/O 큐의 처리 순서를 재배열하는 기법임
- 배경: HDD의 기계식 헤드 이동에 의한 탐색 시간(3~10ms)이 시스템 전체의 I/O 병목을 유발함
- 필요성: 처리량 극대화, 기아 방지, 응답 시간 편차 최소화를 동시에 달성하기 위해 스케줄링 알고리즘 적용이 필수임

---

## Ⅱ. 구조 및 구성요소

```text
애플리케이션 -> I/O 요청 큐 -> OS I/O 스케줄러(SCAN/C-SCAN 등)
                                    |
                                    +-> 요청 순서 재배열
                                    |
                               디바이스 드라이버 -> I/O 컨트롤러 -> 디스크(HDD/SSD)
                                                      |
                                                      +-> DMA 전송 -> 버퍼 캐시
```

| 구성요소 | 역할 | 비고 |
|:---|:---|:---|
| I/O 요청 큐 | 프로세스의 블록 읽기·쓰기 요청을 대기시킴 | 트랙·섹터 정보 포함 |
| I/O 스케줄러 | 큐의 요청을 알고리즘 기반으로 재정렬 | Linux: CFQ(단일큐, 제거), mq-deadline(멀티큐) |
| I/O 컨트롤러 | 스케줄러 지시 순서대로 디바이스에 전기 제어 신호 전달 | DMA 방식으로 CPU 개입 최소화 |

> 요약: 스케줄러가 I/O 큐의 요청을 탐색 최적 순서로 재정렬해 컨트롤러에 전달하고, DMA가 CPU 개입 없이 데이터를 전송함.

---

## Ⅲ. 동작원리 및 흐름도

```text
I/O 요청 발생 -> 큐 삽입 -> 스케줄러: 현재 헤드 위치+방향 기준 최적 순서 계산
  -> 헤드 이동(Seek) -> 회전 대기(Rotational Latency) -> 데이터 전송
    -> I/O 완료 인터럽트 -> CPU에 통지
```

1. 큐 삽입: `read()`/`write()` 시스템 콜에 의해 목표 트랙 번호가 큐에 등록됨
2. 스케줄링 평가: 현재 헤드 위치와 진행 방향을 기준으로 큐 내 모든 요청의 거리를 계산함
3. 순서 확정·이동: 선택된 알고리즘(SCAN 등)에 따라 진행 방향상 가장 가까운 트랙으로 헤드를 이동함
4. 전송 완료: 데이터를 DMA로 버퍼 캐시에 전송 완료 후 CPU에 인터럽트로 통지함

> 요약: 현재 위치와 방향을 기준으로 최적 다음 목적지를 실시간 계산해 기계적 헤드 이동을 통제함.

---

## Ⅳ. 특징

- FCFS 한계: 구현 단순하지만 디스크 양끝 왕복 시 응답 시간이 기하급수적으로 증가함
- SSTF 기아: 처리량은 높으나 현재 헤드에서 먼 외곽 트랙 요청이 무한 대기에 빠짐
- SCAN 방향성: 엘리베이터처럼 한 방향 끝까지 진행하며 처리해 기아를 해결하되, 중앙 트랙이 양끝보다 서비스 빈도가 높음
- C-SCAN 형평성: 단방향 스윕 후 즉시 회귀해 모든 트랙의 응답 시간 편차를 최소화함
- SSD 무관성: SSD는 탐색 시간이 0이므로 SCAN 등이 불필요하고 NOOP·mq-deadline이 적합함

---

## Ⅴ. 심화 비교 및 적용 판단

| 구분 | FCFS | SSTF | SCAN | C-SCAN | 선택 기준 |
|:---|:---|:---|:---|:---|:---|
| 기준 | 도착 순서 | 현재 최단 거리 | 방향 내 최단 | 단방향 최단+회귀 | 공평성 요구 |
| 기아 | 없음 | 발생(외곽) | 없음 | 없음 | 워크로드 분포 |
| 처리량 | 낮음 | 높음 | 중~높음 | 중간 | 성능 요구 |
| 응답 편차 | 큼 | 매우 큼 | 큼(중앙 유리) | 작음(균등) | SLA 요구 |

> 요약: 최고 처리량이면 SSTF(기아 허용 시), 응답 균등성이면 C-SCAN, SSD면 NOOP·mq-deadline을 선택함.

**리스크·대응:**
- SSD 오적용: 탐색 시간이 없는 SSD에 SCAN 적용 시 CPU 오버헤드만 발생 -> NOOP 또는 mq-deadline 전환 (지표: I/O 큐 대기 시간)
- I/O 독점: 대량 백업 작업이 실시간 I/O를 차단 -> cgroups-v2 blkio로 프로세스별 I/O 대역폭 제한 (지표: I/O 응답 지연 p99)

**도입 후 점검 지표:**
- 성능: 평균 I/O 대기 시간(await) — iostat 측정, HDD 목표 20ms 이하
- 운영: I/O 기아 발생 빈도 — 특정 프로세스 I/O 지연 SLA 초과율

---

## Ⅵ. 실무 적용 및 결론

**적용 방안 3개:**
1. HDD DW 서버: 대용량 순차 I/O가 많은 데이터 웨어하우스에 C-SCAN 기반 Deadline 스케줄러를 적용해 일관된 응답 시간을 확보함
2. NVMe SSD 서버: Linux I/O 스케줄러를 블록 멀티큐(blk-mq) 기반 `mq-deadline` 또는 `kyber`로 설정해 SSD의 병렬 I/O를 극대화함
3. 멀티테넌트 클라우드: cgroups-v2 blkio로 컨테이너·VM별 I/O 대역폭 가중치·제한을 부여해 Noisy Neighbor 현상을 차단함

**결론:**
- 기술사 판단: 현대 시스템 I/O 병목 해결은 저장 매체의 물리 특성(HDD 탐색 시간 vs SSD 병렬 처리)을 식별하고 스케줄러를 매칭하는 것이 핵심이며, 단일 알고리즘 맹신은 오히려 역효과를 초래함
- 향후 방향: 하드웨어 기반 고정 스케줄링에서 eBPF·io_uring을 활용해 애플리케이션 워크로드 특성을 동적으로 인지하는 지능형 I/O 스케줄링으로 진화 중임
