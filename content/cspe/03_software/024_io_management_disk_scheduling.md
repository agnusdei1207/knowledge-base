## 미리 알고가기

- I/O 관리는 운영체제가 장치 요청을 큐잉하고 배분하고 완료 처리하는 기능임
- 디스크 스케줄링은 저장장치 요청 순서를 조정해 지연과 처리량을 개선하는 정책임
- HDD와 SSD는 병목 특성이 달라 같은 스케줄링이 항상 유효하지 않음

## Ⅰ. 개요

- **정의/개념**: I/O 관리와 디스크 스케줄링은 운영체제가 프로세스의 입출력 요청을 큐에 모아 장치 특성에 맞게 배치하고 순서를 조정해 처리량과 응답성과 공정성을 관리하는 기능임
- **배경/필요성**: 저장장치와 네트워크 장치는 CPU보다 지연 변동이 크고 경쟁이 심하므로, 요청을 무작정 도착 순서로 처리하면 장치 효율과 서비스 응답성이 크게 떨어질 수 있음

## Ⅱ. 특징

- 장치 큐 관리와 우선순위와 배치 정책이 성능을 크게 좌우함
- HDD는 탐색 거리 최적화가 중요하고 SSD는 병렬 큐 활용과 tail latency 제어가 중요함
- I/O 관리는 장치 효율뿐 아니라 응답 시간 공정성까지 고려해야 함
- 멀티큐와 비동기 I/O 구조가 현대 스토리지 성능의 핵심 기반이 됨

## Ⅲ. 종류 및 비교

| 판단 기준 | FCFS | SCAN or C-SCAN | Deadline or MQ 계열 |
|:---|:---|:---|:---|
| 핵심 기준 | 도착 순서 | 헤드 이동 방향 최적화 | 응답 시간과 병렬 큐 균형 |
| 장점 | 단순성과 공정성 | HDD 탐색 거리 절감 | 현대 장치에서 지연 제어 우수 |
| 한계 | 장치 효율 낮을 수 있음 | SSD에는 효과 제한적 | 구현과 튜닝 복잡도 큼 |
| 적합 환경 | 단순 기준선 | HDD 중심 | SSD와 고부하 서버 |

## Ⅳ. 구성요소 및 구조

| 구성요소 | 설명 |
|:---|:---|
| I/O Request Queue | 프로세스 요청이 모이는 대기열로 스케줄링 정책이 직접 적용되는 핵심 위치임 |
| Scheduler | 요청 순서를 재배열해 장치 효율과 응답성 목표를 동시에 맞추려 함 |
| Device Driver | 커널 스케줄링 결과를 장치 명령으로 변환해 실제 하드웨어와 연결함 |
| Completion Path | 완료 인터럽트와 상위 프로세스 깨우기를 처리해 체감 응답성을 결정함 |

## Ⅴ. 원리 및 절차 흐름도

```text
+-------------+     +-------------+     +-------------+     +-------------+
| 요청 수집      | --> | 큐 정렬/우선화 | --> | 장치 제출      | --> | 완료 처리      |
+-------------+     +-------------+     +-------------+     +-------------+
```

1. **요청 수집**: 프로세스와 파일 시스템이 읽기나 쓰기 요청을 생성함
2. **큐 정렬 및 우선화**: 스케줄러가 장치 특성과 정책에 따라 요청 순서를 조정함
3. **장치 제출**: 드라이버가 장치 큐에 요청을 내려 실제 I/O를 실행함
4. **완료 처리**: 완료 인터럽트를 받아 프로세스에 결과를 전달함

## Ⅵ. 문제점 및 해결 방안

1. 문제: HDD와 SSD에 동일한 정책을 적용하면 한쪽에서는 탐색 비용을, 다른 쪽에서는 병렬성을 제대로 활용하지 못할 수 있음
   - 해결방안: 장치 특성별 스케줄러를 분리 적용하고 device wait time과 queue depth efficiency로 검증함
2. 문제: 처리량 위주로 큐를 길게 유지하면 일부 요청의 tail latency가 크게 악화될 수 있음
   - 해결방안: deadline 계열 정책과 latency budget을 적용하고 p99 I/O latency와 starvation count로 검증함
3. 문제: 멀티큐 환경에서 CPU와 장치 큐 매핑이 어긋나면 lock 경쟁과 캐시 이동이 늘 수 있음
   - 해결방안: CPU affinity와 multi-queue tuning을 적용하고 queue lock contention과 IOPS scaling efficiency로 검증함

## Ⅶ. 적용 사례

- HDD 기반 백업 서버에서는 SCAN 계열 정책을 사용하고, average seek distance와 throughput으로 결과를 확인함
- NVMe 서버에서는 멀티큐 스케줄링을 조정하고, p99 I/O latency와 IOPS scaling efficiency로 결과를 확인함
- 혼합 워크로드 스토리지에서는 deadline 계열 정책을 적용하고, starvation count와 device wait time로 결과를 확인함

## Ⅷ. 결론

I/O 관리의 핵심은 요청을 많이 받는 것이 아니라 장치 특성에 맞게 큐를 제어해 처리량과 tail latency를 함께 관리하는 데 있음.
