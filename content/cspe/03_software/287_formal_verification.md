## Ⅰ. 개요
- **정의**: 수학적 모델과 논리적 증명으로 시스템이 명세를 만족함을 보장하는 검증 기법
- **배경/필요성**: 테스트는 결함 부재를 증명할 수 없으므로 수학적 보증 수단이 필요함
- **비유**: 모든 경우의 수를 수학 공식으로 증명하는 것과 유사함 (샘플 확인이 아닌 완전 증명)

| 출제 의도 | 반드시 짚을 핵심 | 감점 회피 포인트 |
|:---|:---|:---|
| 테스트와 정형 검증 차이 | 정리 증명·모델 체킹(288) 구분 | 상태 폭발 문제 반드시 언급 |

> 요약: 수학적 증명으로 시스템 정확성을 보장하는 무결성 검증 기법임

## Ⅱ. 구성요소
```text
Formal Spec --> Model/Proof --> Verification Engine --> Result
                                       |
                               +-------+-------+
                               |               |
                        Theorem Proving   Model Checking(288)
```

| 구성요소 | 설명 | 비유 |
|:---|:---|:---|
| 정형 명세 | 시스템 속성을 수학적 논리(시제 논리·Z 표기법 등)로 기술 | 정밀 설계 도면 |
| 정리 증명 | 공리·추론 규칙으로 속성 성립을 연역적으로 증명 | 수학 정리 증명 과정 |
| 모델 체킹 | 유한 상태 공간 전수 탐색으로 속성 위반 여부 자동 확인(288 참조) | 모든 경우의 수 전수 조사 |
| 반례 생성 | 속성 위반 시 구체적 반례 경로 자동 출력 | 오류 재현 시나리오 제공 |

> 요약: 정형 명세→정리 증명/모델 체킹→결과·반례의 수학적 검증 체계임

## Ⅲ. 절차
```text
명세 작성 --> 모델 구축 --> 검증 실행 --> 결과 해석
```
- 1단계: 검증 대상 속성을 시제 논리(LTL·CTL) 등 정형 언어로 명세
- 2단계: 시스템을 오토마타·전이 시스템 등 수학적 모델로 추상화
- 3단계: 정리 증명기 또는 모델 체커로 속성 만족 여부 자동 검증
- 4단계: 성립 증명 또는 반례 경로 분석 후 설계 수정·재검증

> 요약: 명세→모델→검증→해석으로 시스템 정확성을 수학적으로 보증함

## Ⅳ. 문제점
- 상태 폭발: 시스템 규모 증가 시 탐색 상태 수 지수 급증 — 모델 체킹 적용 한계
- 높은 전문성 요구: 정형 명세·증명 작성에 수리 논리 전문 역량 필요 — 도입 장벽
- 추상화 간극: 모델과 실제 구현 간 차이 발생 가능 — 검증 결과 신뢰성 저하

> 요약: 상태 폭발·전문성 장벽·추상화 간극이 주요 한계임

## Ⅴ. 개선방안
1. 단기: 추상화·대칭 축소 기법으로 상태 공간 규모 감축
2. 중기: 자동 명세 생성 도구·검증 프레임워크로 전문성 진입 장벽 완화
3. 장기: 코드 수준 정형 검증(Proof-Carrying Code)으로 모델-구현 간극 제거

> 요약: 상태 축소·도구 자동화·코드 수준 검증으로 적용성 확대 필요

## Ⅵ. 전망
- 발전 방향: SMT 솔버 발전으로 산업 규모 시스템에 대한 자동 검증 확대
- 기술사적 판단: 안전 필수 시스템(286) 인증에서 정형 검증 요구 수준 강화 추세임
- 기술사 제언: 정형 검증과 테스트를 상호 보완하는 계층적 V&V 전략 수립 필요
