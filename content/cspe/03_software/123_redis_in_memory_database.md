## 미리 알고가기

- 인메모리 DB는 데이터를 주기억장치에 두고 빠르게 읽고 쓰는 DB 계열임
- TTL은 키의 만료 시간을 뜻하며 캐시와 세션 관리에서 자주 씀
- Redis는 문자열뿐 아니라 리스트와 해시와 셋과 스트림 같은 자료형을 함께 지원함

## Ⅰ. 개요

- **정의/개념**: Redis는 메모리에 키-값 데이터를 저장해 매우 빠른 응답을 제공하고 다양한 자료형과 만료 정책과 복제 기능을 함께 지원하는 인메모리 데이터베이스임
- **배경/필요성**: 세션과 캐시와 실시간 랭킹처럼 짧은 지연과 높은 처리량이 중요한 업무는 디스크 중심 DB만으로는 병목이 생기기 쉬워 인메모리 DB가 필요해짐

## Ⅱ. 특징

- 모든 연산을 메모리 중심으로 처리해 응답 속도가 빠름
- 문자열과 해시와 셋과 스트림 등 자료형이 풍부해 활용 범위가 넓음
- TTL과 Pub/Sub와 Lua 스크립트로 캐시와 큐와 실시간 처리에 유리함
- 메모리 비용이 높고 영속성 정책을 잘못 잡으면 장애 시 데이터 손실 범위가 커질 수 있음

## Ⅲ. 종류 및 비교

| 판단 기준 | Redis | Memcached |
|:---|:---|:---|
| 자료형 | 문자열, 해시, 셋, 스트림 등 다양함 | 단순 키-값 중심임 |
| 영속성 | RDB, AOF 같은 저장 옵션이 있음 | 기본적으로 캐시 용도에 가까움 |
| 활용 범위 | 캐시, 세션, 큐, 분산락, 랭킹 | 단순 캐시 |
| 주의점 | 메모리 관리와 운영 기능이 더 복잡함 | 기능은 단순하지만 활용 폭이 좁음 |

## Ⅳ. 구성요소 및 구조

| 구성요소 | 설명 |
|:---|:---|
| Key Space | 키 단위로 데이터를 저장하고 자료형별 명령을 적용함 |
| Data Types | 문자열, 해시, 리스트, 셋, 정렬된 셋, 스트림을 제공함 |
| Expiration | TTL로 자동 만료를 처리해 캐시 수명을 제어함 |
| Persistence | RDB 스냅샷과 AOF 로그로 재시작 후 복구 범위를 정함 |
| Replication / Sentinel / Cluster | 복제와 장애 조치와 샤딩 확장을 맡음 |

```text
클라이언트 -> Key Space -> Data Type 처리
                    |
           TTL / Persistence / Replication
```

## Ⅴ. 원리 및 절차 흐름도

```text
키 설계 -> 메모리 저장 -> TTL/자료형 연산 -> 복제/저장 -> 만료 또는 갱신
```

1. **키 설계**: 서비스 목적에 맞는 키 규칙과 자료형을 정함
2. **메모리 저장**: 데이터를 메모리에 적재해 빠르게 접근함
3. **자료형 연산**: 자료형별 명령으로 조회와 갱신을 처리함
4. **복제와 저장**: 필요 시 복제와 AOF 또는 RDB를 적용함
5. **만료와 갱신**: TTL이나 삭제 정책으로 수명을 관리함

## Ⅵ. 실무 적용 및 유의점

1. 세션 저장과 조회 캐시는 Redis가 잘 맞지만 키 만료 정책이 엉키면 원본 DB 부하가 한꺼번에 튀므로 TTL 분산과 요청 합치기를 함께 설계하고 캐시 적중률과 동시 만료 건수와 원본 DB 급증 비율로 확인함
2. 분산락과 큐처럼 상태 제어에 Redis를 쓸 때는 메모리만 빠르다고 믿지 말고 영속성과 복제 구조를 함께 점검하고 락 충돌 건수와 대기 시간과 장애 후 복구 범위로 확인함

## Ⅶ. 결론

- Redis는 빠른 응답과 풍부한 자료형이 강점이지만 TTL과 영속성과 장애 조치 구조를 함께 설계해야 캐시를 넘어 운영 핵심 계층으로 안정적으로 쓸 수 있음
