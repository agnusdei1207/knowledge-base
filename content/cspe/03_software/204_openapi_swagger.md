## Ⅰ. 개요
- **정의**: REST API의 엔드포인트·요청·응답·인증 구조를 기계 가독형 YAML/JSON으로 기술하는 표준 명세
- **배경/필요성**: API 제공자·소비자 간 구두·문서 기반 소통의 불일치를 구조화된 계약으로 해소 필요
- **비유**: 건축 설계도처럼 API의 입구·출구·구조를 사전에 합의하는 청사진

| 출제 의도 | 반드시 짚을 핵심 | 감점 회피 포인트 |
|:---|:---|:---|
| API 계약 기반 개발 이해 | OAS 3.x 구조, Design-First vs Code-First | Swagger는 도구명, OpenAPI는 명세 표준명 구분 |

> 요약: REST API 구조를 기계 가독형 명세로 정의하여 제공자·소비자 간 계약을 표준화함

## Ⅱ. 구성요소
```text
OpenAPI Spec (YAML/JSON)
    |
    +--- paths: 엔드포인트 정의
    +--- schemas: 데이터 모델
    +--- securitySchemes: 인증 방식
    |
    v
Swagger UI / Codegen / Validator
```

| 구성요소 | 설명 | 비유 |
|:---|:---|:---|
| paths | HTTP 메서드별 엔드포인트·파라미터·응답 정의 | 건물 출입구 목록 |
| schemas | 요청·응답 데이터 구조를 JSON Schema로 정의 | 방 평면도 |
| Swagger UI | 명세를 대화형 웹 문서로 렌더링하는 도구 | 모델하우스 |

> 요약: paths·schemas로 API 계약을 정의하고 Swagger UI로 시각화·테스트함

## Ⅲ. 절차
```text
명세 작성 --> 검증 --> 코드/문서 생성 --> 런타임 검증
```
- 1단계: Design-First 방식으로 OpenAPI 명세(YAML/JSON) 작성
- 2단계: Spectral 등 린터로 명세 문법·스타일 규칙 자동 검증
- 3단계: Codegen으로 서버 스텁·클라이언트 SDK·API 문서 자동 생성
- 4단계: 런타임에 요청·응답이 명세와 일치하는지 미들웨어로 검증

> 요약: 명세 작성, 검증, 코드 생성, 런타임 검증 4단계로 계약 기반 개발 수행함

## Ⅳ. 문제점
- 명세-코드 불일치: 수동 관리 시 코드 변경이 명세에 미반영 — API 소비자 혼란 발생
- 대규모 명세 관리: 수백 개 엔드포인트 단일 파일 시 가독성·유지보수성 저하
- 표현력 한계: 복잡한 비즈니스 규칙·조건부 필드를 JSON Schema만으로 표현 곤란

> 요약: 명세-코드 불일치, 대규모 관리 난이도, 표현력 한계가 주요 문제임

## Ⅴ. 개선방안
1. 단기: CI 파이프라인에 명세-코드 동기화 검증 단계 추가로 불일치 조기 탐지
2. 중기: `$ref` 기반 명세 분할·재사용 구조 도입으로 대규모 명세 모듈화
3. 장기: 확장 속성(`x-`)·Overlay 활용으로 비즈니스 규칙 표현력 확대

> 요약: CI 동기화 검증, 명세 모듈화, 확장 속성 활용으로 단계적 개선함

## Ⅵ. 전망
- 발전 방향: OAS 3.1의 JSON Schema 완전 호환으로 생태계 도구 통합 가속화
- 기술사적 판단: API-First 전략의 기반 기술로 조직 간 협업 효율 결정 요소임
- 기술사 제언: API 버저닝 전략(205 참조)과 연계한 명세 거버넌스 체계 수립 권장
