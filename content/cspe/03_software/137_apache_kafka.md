# 📖 【암기용】 개념 완전 이해

## 한눈에
- **개요**: 분산 환경에서 발생하는 대규모 실시간 데이터(이벤트)를 안전하게 모으고 여러 곳에 분배해주는 고성능 분산 이벤트 스트리밍 플랫폼이다.
- **왜 필요한가**: 마이크로서비스 간에 데이터를 직접(API로) 주고받으면 한쪽이 죽었을 때 통신이 막히고, 서비스가 늘어날수록 연결선(스파게티 네트워크)이 폭증해 관리가 불가능하다. 
- **핵심 직관**: 가운데 거대하고 튼튼한 "중앙 우체국(메시지 버퍼)"을 두고, 보내는 놈은 던져놓고 잊고(비동기), 받는 놈은 자기 속도에 맞춰 알아서 가져가게(Pull) 만든다.

## 핵심 용어 정리 (내부에 등장하는 것들)

| 용어/표기 | 의미 | 비유·예 |
|:---|:---|:---|
| Producer / Consumer | 데이터를 생산해서 보내는 앱 / 데이터를 꺼내서 소비하는 앱 | "편지를 보내는 발신자 / 우체통에서 꺼내가는 수신자" |
| Topic | 데이터를 구분하는 주제 (RDBMS의 테이블과 비슷) | "주제별 분류 우체통 (예: 결제 내역 토픽)" |
| Partition (파티션) | 토픽 하나를 여러 개로 쪼개어 분산 저장하는 물리적 단위 | "우체통 크기를 늘리기 위해 나란히 둔 여러 박스" |
| Offset (오프셋) | 파티션 안에서 각 메시지가 가지는 고유한 순서 번호 | "책에 매겨진 페이지 번호 (읽은 위치 기억)" |
| Consumer Group | 파티션을 나눠서 병렬로 처리하는 소비자들의 모임 | "우체통을 같이 비우는 우체부 한 팀" |

## 깊이 이해
- **배경·문제의식**: 링크드인은 시스템 간 로그 연동이 너무 복잡했다. 기존 메시지 큐(RabbitMQ 등)는 큐가 데이터를 보관하다 소비되면 삭제하는 구조라 대규모 빅데이터 로그(초당 수백만 건)를 감당하지 못했다. 데이터를 삭제하지 않고 파일에 순차적으로 기록(Append-only)하면서 확장 가능한 새로운 시스템이 필요했다.
- **작동 원리**: 카프카는 데이터를 RAM이 아닌 '디스크 파일' 맨 끝에 순서대로 쌓기만 한다(Sequential I/O). 디스크라도 순차 기록은 매우 빠르다. 브로커(Broker, 서버)는 데이터를 여러 파티션으로 쪼개 클러스터에 분산·복제한다. Consumer는 브로커가 데이터를 밀어주는(Push) 대신, 자기가 처리할 수 있는 속도로 오프셋 위치를 기억하며 당겨간다(Pull 방식).
- **비유**: 회전초밥집(Kafka). 요리사(Producer)는 초밥을 레일(Topic)에 계속 올려놓는다. 손님(Consumer)은 자기 식사 속도에 맞춰 초밥을 집어먹는다. 요리사는 손님이 얼마나 먹는지 신경 쓰지 않고 초밥을 올리는 데만 집중하며, 손님 A가 연어를 먹었다고 손님 B가 못 먹는 게 아니라 각자 자기 자리(Consumer Group)에서 알아서 복사해 간다.
- **구체 예시**: MSA 쇼핑몰. 결제 서비스가 '결제 완료'를 카프카 토픽에 던진다. 배송 서비스, 포인트 적립 서비스, 알림 서비스(서로 다른 Consumer Group)가 이 토픽을 구독해 각자 자기 일만 비동기로 처리한다. 배송 서버가 잠시 다운돼도 데이터는 카프카에 쌓여 있어 복구 후 이어서 처리하면 된다.
- **흔한 오해·주의점**: 하나의 파티션 안에서는 데이터 순서가 보장되지만, 1개 토픽이 여러 파티션으로 쪼개진 경우 토픽 전체의 순서는 보장되지 않는다. 따라서 사용자 ID 등 순서가 중요한 데이터는 같은 파티션에 들어가도록 파티셔닝 키(Partition Key)를 지정해야 한다.

# 📝 【답안용】 시험 답안 템플릿

## 핵심 인사이트 (3줄 요약)

> 1. **본질**: 카프카는 디스크 순차 I/O와 파티셔닝(Partitioning) 분산 구조를 활용하여 초당 수백만 건의 이벤트를 처리하는 분산 메시지 브로커다.
> 2. **가치**: 송·수신 시스템의 강력한 디커플링(비동기 분리)을 달성하여 장애 격리를 실현하고, 데이터를 영속 저장해 빅데이터 파이프라인의 핵심 버퍼 역할을 실현한다.
> 3. **판단 포인트**: 메시지 소비 시 지우지 않고 다중 컨슈머가 구독 가능한 특징은 Pub/Sub 아키텍처에 완벽히 부합하나, 파티션 순서 보장 한계와 브로커 관리 복잡도가 수반된다.

## 출제 의도 및 답안 포인트

| 출제 의도 | 반드시 짚을 핵심 | 감점 회피 포인트 |
|:---|:---|:---|
| 대용량 스트리밍 플랫폼의 성능/확장성 원리 | 순차 I/O, Page Cache, Partition, Pull 방식 | 기존 큐(AMQP 등)처럼 Push 방식이라 단정 |
| MSA 환경에서의 역할과 아키텍처 | 비동기 통신(Decoupling), 이벤트 드리븐 기반 | 기능 나열에 그침 (장애 격리 효과 누락) |
| 순서 보장 및 장애 허용성 통제 역량 | Partition Key 전략, ISR 복제, Consumer Group 오프셋 | 파티션이 많아도 전체 순서가 보장된다는 오답 |

> 요약: 카프카가 단순한 큐를 넘어, 디스크 기반의 영속성과 파티션을 통한 선형 확장이 가능한 '이벤트 스트리밍 플랫폼'임을 증명해야 한다.

## Ⅰ. 개요 및 필요성

- 개요: Pub-Sub 모델을 기반으로 대규모 실시간 데이터 피드를 고성능·저지연으로 처리하는 분산 이벤트 스트리밍 플랫폼
- 배경: 서비스 규모 증가(MSA, 로그 수집 등)로 점대점(Point-to-Point) 연결 복잡도가 폭증하고 동기 통신의 장애 전파 위험 대두
- 필요성: 시스템 간 결합도를 낮추고 데이터 유실 없이 이벤트를 버퍼링·재처리할 수 있는 확장 가능한 중앙 집중형 허브 필요

---

## Ⅱ. 구조 및 구성요소

```text
Producer -> [Kafka Cluster / Broker 1..N] -> Consumer Group A
                 |-> Topic X                 |-> Consumer 1, 2
                 |  +-> Partition 0, 1, 2    -> Consumer Group B
                 |-> Zookeeper/KRaft(메타)
```

| 구성요소 | 역할 | 특이사항 |
|:---|:---|:---|
| Broker & Cluster | 이벤트 데이터를 파일로 로컬 디스크에 저장 및 분산 노드 구성 | 스케일 아웃이 용이함 |
| Topic & Partition | 데이터를 주제별(Topic)로 물리적 단위(Partition)로 분산 | 파티션 수가 병렬 처리 처리량(Throughput) 결정 |
| Consumer Group | 1개 이상의 Consumer 묶음, 파티션 데이터를 1:1 점유 분산 처리 | 다른 그룹 간에는 서로 영향 없이 독립적 오프셋 소비 |
| Zookeeper / KRaft | 클러스터 메타데이터, 브로커 생존 및 파티션 리더 선출 관리 | 최신 버전은 Zookeeper 걷어내고 KRaft 모드 전환 중 |

> 요약: 프로듀서는 토픽에 기록하고, 카프카 브로커는 이를 파티션 분산 저장하며, 컨슈머 그룹이 당겨(Pull) 처리하는 구조다.

---

## Ⅲ. 동작원리 및 흐름도

```text
메시지 발행 -> 파티션 라우팅 -> 디스크 순차 기록 (OS Page Cache 활용) -> Consumer Pull 요청 -> 오프셋 갱신
```

- 1단계 [발행 및 라우팅]: Producer가 메시지(Key, Value) 전송 시 Key의 해시값에 따라 특정 Partition 리더 브로커로 라우팅
- 2단계 [영속 저장 및 복제]: 리더 브로커는 OS Page Cache에 기록 후 디스크 끝에 Append-only로 추가하며, 팔로워들에게 ISR(In-Sync Replica) 복제
- 3단계 [소비 및 Pull]: Consumer가 자기 속도에 맞춰 브로커에 Fetch 요청(Pull 방식)을 보내어 메시지를 가져옴 (네트워크 과부하 방지)
- 4단계 [오프셋 커밋]: 처리가 끝난 Consumer는 내부 토픽(`__consumer_offsets`)에 자기가 읽은 위치(Offset)를 커밋해 중단 시점 기억

> 요약: RAM이 아닌 디스크 순차 쓰기와 OS 캐시를 활용해 속도를 내며, Pull 방식을 통해 컨슈머 부하를 통제한다.

---

## Ⅳ. 특징
- [디커플링 및 스파이크 완화]: 송신자/수신자 속도 차이(Traffic Spike)를 버퍼링으로 흡수하고 한쪽 장애가 타 서비스로 전파되지 않음
- [고성능 영속성]: 디스크 접근 횟수를 줄이는 Zero-Copy 및 순차 쓰기 최적화로 초당 수백만 건 처리
- [순서 보장 제약]: 토픽 전체의 순서는 보장할 수 없으며, 단일 파티션 내에서만 입력 순서가 보장됨

> 요약: 확장성과 장애 격리가 탁월하지만 완벽한 순서 보장을 위해서는 키 기반 파티션 라우팅 설계라는 트레이드오프가 따른다.

## Ⅴ. 심화 비교 및 적용 판단

| 비교 축 | 기존/대안 (RabbitMQ) | 본 키워드 (Apache Kafka) | 선택 기준 |
|:---|:---|:---|:---|
| 데이터 영속성 | 메시지 소비 시 큐에서 즉시 삭제 | 보관 주기(Retention) 동안 영구 보존 | 다수 앱의 동일 데이터 재사용/재처리 여부 |
| 소비 방식 | Smart Broker / Dumb Consumer (Push) | Dumb Broker / Smart Consumer (Pull) | 메시지 라우팅 복잡성 vs 고성능 처리량 |
| 아키텍처 적합성 | 복잡한 라우팅, 소규모 트랜잭션 | 대규모 실시간 로그 파이프라인, MSA 이벤트 | 데이터 볼륨 규모 및 이벤트 소싱 적용 여부 |

> 요약: 정교하고 작은 메시지 분배는 RabbitMQ가, 방대한 비동기 데이터 댐 역할은 카프카가 적합하다.

**리스크·대응 (기본은 불릿):**
- [메시지 유실 및 중복]: 네트워크 지연 시 최소 한 번(At-least-once) 전송으로 중복 소비 발생 → 멱등성 프로듀서(`enable.idempotence=true`) 옵션 및 트랜잭션 API 적용으로 Exactly-Once 달성 (지표: 중복 레코드 카운트)
- [순서 엉킴(Out of order)]: 다중 파티션 환경에서 연관 데이터 비순차 처리 → 특정 회원 ID 등 연관성을 묶는 Partition Key를 부여해 동일 파티션 배정 강제

**도입 후 점검 지표 (기본은 불릿):**
- 성능/효율: Consumer Lag(생산과 소비의 오프셋 차이) 임계치 미만 유지 — Prometheus/Grafana Lag 모니터링
- 품질/운영: ISR(동기화 복제본) 수축 현상 발생 0건 — 브로커 URP(Under Replicated Partitions) 지표 추적

## Ⅵ. 실무 적용 및 결론

**적용 방안 3개:**
1. MSA 이벤트 드리븐 도입: API 동기 호출(REST)의 결합도를 끊고, 카프카 중심의 비동기 메시징 아키텍처인 Choreography Saga 패턴 구현
2. 스트림 파이프라인 확장: 카프카 커넥트(Kafka Connect)를 통한 DB CDC(Change Data Capture) 연동과 KSQL을 이용한 경량 실시간 분석 구축
3. 파티션 및 복제 설계: 서비스 SLA에 따라 토픽 생성 시 Replication Factor=3, min.insync.replicas=2 원칙을 적용해 브로커 장애 내성 확보

**결론 (2줄):**
- 기술사 판단: 카프카는 MSA 환경에서 데이터의 신경망 역할을 수행하며, 시스템 장애와 복잡도를 격리하는 가장 확실한 인프라 투자이다.
- 향후 방향: Zookeeper의 관리 오버헤드를 완전히 제거한 KRaft 체제로 전환되고 있으며, 서버리스 기반 매니지드 서비스(Confluent Cloud 등) 도입이 확대될 것이다.
