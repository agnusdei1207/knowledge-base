## 핵심 인사이트 (3줄 요약)
- N개의 송신자(Producer)와 M개의 수신자(Consumer)가 거미줄처럼 얽혀 통신하던 MSA의 지옥을, **단 하나의 거대한 우체국(고속도로)으로 통일해 버린 분산 이벤트 스트리밍 플랫폼의 제왕**.
- 기존 메시지 큐(RabbitMQ 등)가 메시지를 읽으면 지워버리는 '휘발성 메모리' 방식이었다면, Kafka는 모든 데이터를 하드 디스크에 순차적으로 기록(Append-only Log)하여 수일~수년 치 데이터를 영구 보존함.
- 디스크를 쓰면서도 메모리보다 빠른 이유는 O/S 레벨의 **페이지 캐시(Page Cache)와 제로 카피(Zero-Copy)** 기술을 극한으로 활용했기 때문이며, 빅데이터 파이프라인의 핵심 심장(Single Source of Truth)으로 군림함.

## Ⅰ. 개요 및 필요성
- **개요**: 링크드인(LinkedIn)에서 개발한 오픈소스 분산 스트리밍 플랫폼. 초당 수백만 건의 이벤트를 발행, 구독, 저장, 처리하는 Pub/Sub 기반의 메시지 큐.
- **필요성**: 링크드인 내부에 100개의 서비스(DB, 검색엔진, 캐시 등)가 서로 데이터를 주고받으려니 연결선이 10,000개가 넘는 스파게티 네트워크가 됨. A서버가 죽으면 데이터가 영원히 유실되는 참사가 벌어짐. "모든 부서는 그냥 중앙의 거대한 버퍼(Buffer) 통에 데이터를 던지고, 각자 알아서 퍼가게 하자!"는 발상에서 탄생함.

## Ⅱ. 아키텍처 및 핵심 원리
- **1. 핵심 구성 요소**:
  - `Producer`: 이벤트를 만들어 카프카에 던지는 놈 (예: 결제 완료 서버).
  - `Topic`: 데이터가 쌓이는 폴더(카테고리). (예: '결제내역' 토픽).
  - `Partition`: 1개의 Topic을 여러 개로 쪼갠 파일. (분산 처리의 핵심 단위).
  - `Consumer`: 파티션에 빨대를 꽂고 데이터를 가져가서 처리하는 놈 (예: 알림 발송 서버).
- **2. 컨슈머 그룹 (Consumer Group)과 오프셋 (Offset)**:
  - 데이터는 읽혀도 절대 지워지지 않음. 대신, 각 Consumer가 "나는 152번(Offset) 줄까지 읽었어"라고 책갈피만 기록해 둠. 
  - 서버가 죽었다 살아나면, 153번부터 다시 읽기 시작하므로 데이터 유실이 제로(0)에 수렴함.
- **3. 제로 카피 (Zero-Copy) 성능 최적화**:
  - 보통 디스크에서 네트워크로 데이터를 쏠 때 CPU가 메모리로 2번 퍼 나름. Kafka는 커널 단에서 디스크의 데이터를 랜카드로 직접 쏴버림(Zero-Copy). 디스크 기반임에도 초당 수백만 건 처리가 가능한 이유임.

```text
[ 스파게티 아키텍처 vs Kafka 중심 아키텍처 ]

 🍝 [ 도입 전: N x M 스파게티 연결 ]
 [결제 서버] ➡️ (결제완료 API) ➡️ [DB]
 [결제 서버] ➡️ (알림 API) ➡️ [알림 서버] (알림 서버 죽으면 데이터 증발!)
 
 🛣️ [ 도입 후: Pub/Sub 고속도로 ]
 [결제 서버] ➡️ (결제완료 메시지 1건 던짐) ➡️ 🐘 [ Kafka '결제 토픽' ]
 
 🐘 [ Kafka ] ➡️ (내 템포에 맞춰서 가져감) ➡️ [DB]
 🐘 [ Kafka ] ➡️ (알림 서버가 죽어있음! 하지만 디스크에 3일간 저장됨) ➡️ (다음날 살아난 알림 서버가 밀린 거 다 퍼감! 데이터 유실 Zero!)
```

## Ⅲ. 비교 및 연결
| 구분 | RabbitMQ / ActiveMQ | Apache Kafka |
|---|---|---|
| **메시지 보관 철학** | Smart Broker / Dumb Consumer | **Dumb Broker / Smart Consumer** |
| **메시지 삭제** | Consumer가 읽고 ACK(확인)하면 삭제 | **읽어도 안 지움. 설정된 보관주기(예: 7일) 후 자동 삭제** |
| **처리 성능 (초당)** | 수만 건 (메모리 큐 중심) | **수백만 건 (디스크 순차 I/O 중심)** |
| **주 사용 목적** | 앱 간의 단순 비동기 통신 (이메일 발송 등) | **거대 MSA 통신, 실시간 로그 수집, 빅데이터 파이프라인** |

## Ⅳ. 실무 적용 및 기술사 판단
- **이벤트 소싱(Event Sourcing)의 근간**: 현대 MSA 아키텍처에서 DB의 최종 상태만 저장하는 것이 아니라, "장바구니 담음 ➡️ 취소함 ➡️ 결제함" 같은 **모든 상태 변경 이벤트를 Kafka에 영구 보존(Retention=Forever)**하는 패턴이 대유행임. 만약 주문 DB가 박살 나도, Kafka에 저장된 이벤트를 0번부터 다시 재생(Replay)하면 DB를 100% 원상 복구할 수 있는 무결성 아키텍처를 그릴 수 있음 (카파 아키텍처와 연결).
- **파티션(Partition) 튜닝과 순서 보장**: 토픽의 데이터를 병렬로 빨리 처리하려면 파티션 개수를 늘려야 함. 하지만 주의할 점은, **순서는 오직 '1개의 파티션 내에서만' 보장**된다는 것임. "A유저의 결제 ➡️ 취소" 이벤트가 각각 다른 파티션에 들어가면 컨슈머가 '취소'를 먼저 읽는 재앙이 발생함. 기술사는 반드시 A유저의 아이디를 파티션 키(Key)로 지정하여, 특정 유저의 이벤트는 항상 같은 파티션에 꽂히도록 설계해야 함.

## Ⅴ. 기대효과 및 결론
- "데이터를 잃어버리지 않고, 병목 없이 무한대로 파이프라인을 뚫어준다"는 철학으로 넷플릭스, 우버, 카카오 등 글로벌 IT 기업의 신경망 역할을 하는 절대적인 표준 인프라임.
- 단순한 메시지 큐를 넘어, 데이터를 저장하고, SQL로 스트림을 분석(ksqlDB)하는 거대한 '실시간 데이터베이스(Real-time Data Fabric)' 생태계로 진화하고 있음.
