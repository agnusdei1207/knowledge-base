## 미리 알고가기

- 토픽(Topic)은 이벤트를 분류하는 논리 단위이며 여러 파티션으로 분할됨
- 파티션(Partition)은 이벤트를 오프셋 순서로 추가하는 복제 로그이자 병렬 처리 단위임
- 오프셋(Offset)은 파티션 안에서 이벤트 위치를 식별하는 증가 번호임
- 소비자 그룹(Consumer Group)은 파티션을 그룹 내 소비자에게 나눠 병렬로 읽음
- ISR(In-Sync Replica)은 리더 로그를 따라잡아 리더 후보로 유지되는 복제본 집합임
- 멱등성 프로듀서는 재시도 과정의 중복 기록을 억제하고 트랜잭션 프로듀서는 레코드와 소비 오프셋을 원자적으로 커밋함

## 작성 근거(검토용)

- Kafka는 파티션 로그·오프셋·소비자 그룹·복제·재처리를 핵심 판단축으로 선정함
- 비교표는 전통 작업 큐와 저장·소비 구조·처리 범위·재처리를 같은 기준에서 대비함
- 구조와 절차는 프로듀서 기록부터 복제 확인, 소비와 오프셋 커밋까지 실제 데이터 흐름으로 연결함
- 제목부터 결론까지 모든 문장·표 셀·요약을 5회 전수 검수해 동작과 보장 범위를 구분함

## Ⅰ. 개요

- **정의/개념**: Kafka는 이벤트를 파티션 로그에 영속 저장하고 소비자 그룹이 오프셋으로 구독·재처리하는 분산 스트리밍 플랫폼임
- **배경/필요성**: 응용 간 이벤트 전달과 이력 재처리를 분리하고 처리량을 파티션 단위로 확장하기 위해 영속 로그 기반 중개 구조가 필요함

### 쉽게 이해하기 (학습용)
- 이벤트를 지우지 않고 번호가 붙은 분산 일지에 보존해 여러 독자가 각자 읽는 플랫폼임

## Ⅱ. 특징

- 같은 키의 이벤트는 같은 파티션에 기록해 파티션 안의 오프셋 순서를 유지함
- 소비자 그룹은 파티션을 소비자에게 배정하고 그룹별 커밋 오프셋으로 처리 위치를 관리함
- 파티션 리더가 쓰기를 받고 팔로워가 로그를 복제하며 장애 시 ISR에서 새 리더를 선출함
- 보존 기간·용량 정책으로 이벤트를 유지하고 로그 압축은 키별 최신 값을 보존함
- 멱등성 프로듀서는 내부 재시도의 중복 기록을 억제하고 트랜잭션 프로듀서는 읽기-변환-쓰기 결과를 원자적으로 커밋함

### 쉽게 이해하기 (학습용)
- 병렬성과 재처리는 좋지만 파티션 안에서만 순서가 보장되고 편중·재배정을 관리해야 함

## Ⅲ. 종류 및 비교

| 판단 기준 | 전통 작업 큐 | Apache Kafka |
|:---|:---|:---|
| 저장·소비 구조 | 소비 완료 메시지를 큐 정책에 따라 제거하고 브로커가 전달 상태를 관리 | 이벤트를 파티션 로그에 보존하고 소비자 그룹이 오프셋을 커밋 |
| 처리 범위 | 큐·소비자 구성에 따라 전달 순서를 정하고 경쟁 소비자 수로 작업 분산 | 같은 파티션 안에서 오프셋 순서를 유지하고 파티션을 그룹 내 소비자에게 배정 |
| 재처리 | 이미 확인한 메시지의 재전달 범위가 제한됨 | 오프셋을 되돌려 보존 이벤트를 다시 처리 |

> 요약: Kafka는 이벤트를 파티션 로그에 보존하고 소비자 그룹별 오프셋으로 병렬 소비와 재처리를 지원함.

### 쉽게 이해하기 (학습용)
- 작업 큐는 소비 후 작업 전달에, Kafka는 보존 일지와 여러 독자 재생에 초점을 둠

## Ⅳ. 설계 요소 및 구조

| 구성요소 | 설명 |
|:---|:---|
| Producer | 키와 값을 직렬화하고 대상 토픽·파티션으로 이벤트를 전송함 |
| Topic·Partition | 이벤트를 오프셋 순서의 분산 로그로 저장하고 병렬 처리 범위를 나눔 |
| Broker·Replica | 파티션 리더가 요청을 처리하고 팔로워가 로그를 복제함 |
| Consumer Group | 파티션을 소비자에게 배정하고 그룹별 처리 위치를 유지함 |
| Group Coordinator | 소비자 등록·재배정과 커밋 오프셋 저장을 조정함 |
| Controller | 브로커·파티션 메타데이터와 리더 선출을 관리함 |

```text
Producer -> Partition Leader -> Follower Replica
                    |
                    v
           Consumer Group -> Offset Commit
```

> 요약: 프로듀서는 파티션 리더에 기록하고 브로커는 복제하며 소비자 그룹은 배정된 파티션과 오프셋을 관리함.

### 쉽게 이해하기 (학습용)
- 작성자, 번호가 붙은 일지, 사본 서버와 독자 그룹·책갈피 관리자로 구성됨

## Ⅴ. 원리 및 절차 흐름도

```text
키 기반 파티션 선택 -> 리더 로그 추가 -> 복제·응답 -> 소비자 Fetch -> 오프셋 커밋
```

1. **파티션 선택**: 프로듀서가 키 해시나 지정 정책으로 이벤트의 파티션을 정함
2. **로그 추가**: 파티션 리더가 이벤트를 다음 오프셋에 추가함
3. **복제·응답**: 설정한 확인 조건에 따라 팔로워 복제 상태를 확인하고 프로듀서에 응답함
4. **이벤트 소비**: 그룹 내 소비자가 배정된 파티션에서 오프셋 이후 이벤트를 가져옴
5. **위치 커밋**: 처리 완료 위치를 그룹 오프셋으로 저장해 재시작 지점을 정함

> 요약: Kafka는 키로 파티션을 정해 로그를 복제하고 소비자가 처리한 위치를 그룹 오프셋으로 커밋함.

### 쉽게 이해하기 (학습용)
- 키로 일지를 고르고 사본 확인 뒤 기록하며 독자는 처리한 번호를 저장함

## Ⅵ. 실무 사례

1. 응용 로그 수집은 서비스 이름을 파티션 키로 사용하고 프로듀서 요청 지연·소비자 지연량을 확인함
2. DB 변경 이벤트는 테이블 키 순서를 유지하고 ISR 수·소비 오프셋 지연량을 확인함

### 쉽게 이해하기 (학습용)
- 주문 이벤트에 적용하고 파티션 편중·소비 지연·재배정 중단 시간을 확인함

## Ⅶ. 결론

- Kafka는 이벤트 순서 범위·보존 기간·파티션 수·복제 조건과 소비자 재처리 요구를 기준으로 설계해야 함
- 브로커 처리량만 보지 말고 소비 지연·불완전 복제 파티션·재배정과 스키마 호환성을 운영 지표로 관리해야 함

### 쉽게 이해하기 (학습용)
- 일지가 빨리 쌓여도 독자가 뒤처지거나 사본과 문서 양식이 깨지면 안정적인 플랫폼이 아님
