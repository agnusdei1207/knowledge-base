# 📖 【암기용】 개념 완전 이해

> 목적: TOGAF를 처음 보는 사람도 완벽히 이해하게 만든다. 시험 답안 양식이 아니라, 이해를 위한 친절한 설명이다.

## 한눈에
- **개요**: TOGAF는 **EA(전사적 아키텍처, Enterprise Architecture)**를 수립·운용하기 위한 오픈그룹(The Open Group) 표준 **아키텍처 프레임워크**이며, 그 핵심 절차가 반복적 개발 방법론인 **ADM(Architecture Development Method)**이다.
- **왜 필요한가**: EA는 업무·데이터·응용·기술을 동시에 다루는 방대한 작업이다. 정해진 절차 없이 조직마다 다르게 접근하면 산출물 형태가 제각각이고 의사결정 근거가 남지 않는다. TOGAF는 이 절차와 산출물을 반복 가능한 표준으로 제공한다.
- **핵심 직관**: TOGAF는 건축 설계 매뉴얼이고, ADM은 그 매뉴얼이 정한 "설계→시공→준공→변경관리" 순서다.

## 핵심 용어 정리 (내부에 등장하는 것들)

| 용어 | 의미 | 비유 |
|:---|:---|:---|
| EA | 조직의 업무·데이터·응용·기술을 통합해 그린 청사진 — TOGAF가 만들려는 **대상** | 도시 종합계획도 |
| TOGAF | EA를 만드는 절차·산출물·거버넌스를 표준화한 프레임워크 | 설계 매뉴얼 |
| ADM | TOGAF의 심장 — 원형으로 반복되는 개발 절차(Preliminary+A~H, 총 9단계) | 레시피의 조리 순서 |
| Preliminary | ADM 착수 전 아키텍처 원칙·조직·거버넌스 체계를 준비하는 단계 | 요리 전 주방 세팅 |
| Phase A: Architecture Vision | 사업 범위, 이해관계자, 목표 아키텍처의 큰 그림 정의 | 설계 컨셉 확정 |
| Phase B: Business Architecture | 업무 프로세스·조직·역할 설계 | 평면도 |
| Phase C: Information Systems Architecture | 데이터 아키텍처 + 응용 아키텍처 설계 | 배관·전기 도면 |
| Phase D: Technology Architecture | 인프라·플랫폼·네트워크 기술 설계 | 골조·자재 명세 |
| Phase E: Opportunities & Solutions | 현행-목표 Gap을 분석해 이행 프로젝트 단위(Work Package)로 묶음 | 공사를 공정 패키지로 나누기 |
| Phase F: Migration Planning | 이행 프로젝트의 순서·일정·비용 계획 수립 | 공사 일정표 작성 |
| Phase G: Implementation Governance | 실제 구현 프로젝트가 목표 아키텍처를 지키는지 심의 | 준공 감리 |
| Phase H: Architecture Change Management | 운영 중 발생하는 변경 요청을 관리 | 준공 후 리모델링 절차 |
| Requirements Management | ADM 원의 중심에서 전 단계 요구사항을 저장·추적하는 상시 활동 | 프로젝트 내내 참조하는 계약서 원본 |
| Architecture Repository | 산출물·표준·빌딩블록을 축적하는 저장소 | 도면 보관함 |
| Content Metamodel | 산출물 간 관계(무엇이 무엇을 참조하는지)를 정의하는 구조 | 도면 양식 표준 |
| Tailoring | 조직 규모·성숙도에 맞게 ADM 산출물 범위를 줄이거나 늘리는 조정 | 표준 설계도를 현장 사정에 맞게 축약 |

## 깊이 이해

### ADM은 왜 원형(Cycle)으로 그리는가
- ADM 문서의 대표 도식은 9개 단계(Preliminary, A~H)를 원형으로 배치하고 그 중심에 Requirements Management를 둔다. 원형인 이유는 H단계(변경관리)에서 끝나는 게 아니라, 변경 요청이 다시 Preliminary나 Vision으로 돌아가 다음 반복(iteration)을 시작하기 때문이다 — 폭포수가 아니라 순환 개발이다.
- Requirements Management가 중심에 있는 이유: 8개 단계 모두가 요구사항을 만들거나 소비하므로, 중심에서 상시 추적하지 않으면 뒷단계에서 앞단계 요구를 잊어버린다.

### 워크드 예제 — 18개월 클라우드 전환 EA
- Preliminary(1개월): 아키텍처 원칙 12개, 거버넌스 조직(Architecture Board 5인) 확정.
- Phase A(1개월): 전환 대상 시스템 40개 중 우선순위 상위 15개를 범위로 확정.
- Phase B/C/D(각 2개월, 총 6개월): 업무 프로세스 30개, 데이터 주제영역 12개, 응용 40개, 클라우드 인프라 표준을 설계.
- Phase E/F(2개월): Gap 분석 결과 이행 프로젝트 8개, 마이그레이션 웨이브 3차(1차 5개·2차 6개·3차 4개 시스템)로 계획.
- Phase G(잔여 기간 상시): 매 스프린트마다 준수 심의를 열어 목표 아키텍처 이탈 항목을 점검.
- 이처럼 ADM 단계는 실제 사업에서 개월 수·시스템 수·프로젝트 개수로 구체화되어야 산출물이 나온다.

### Tailoring — 표준을 그대로 쓰지 않는 이유
- TOGAF 표준 콘텐츠 메타모델은 카탈로그·매트릭스·다이어그램 등 수십 종의 산출물을 정의한다. 그러나 중소 규모 사업에서 이를 전부 만들면 설계보다 문서 작성에 시간을 다 쓴다.
- 그래서 Tailoring 단계에서 "필수 10종 + 선택 10종"처럼 산출물을 골라 쓴다. 단일 부서 시스템 전환이면 Business Architecture의 조직도·역량 매트릭스는 생략하고 데이터·응용·기술 산출물만 남기는 식이다.

### 판별 원리 — 언제 TOGAF ADM을 쓰는가
- 전사 범위(여러 업무·시스템을 아우름) + 다년(1년 이상) 전환계획 + 거버넌스 필요 → ADM 풀사이클 적용.
- 단일 시스템 설계, 단기 프로젝트 → ADM 전체를 쓰기보다 필요한 단계(예: C, D)만 경량화해 참고한다.

### 비유와 흔한 오해
- **비유**: 대규모 리모델링에서 설계 기준(Preliminary)→공간 설계(B)→배관·전기(C)→골조(D)→공정 패키지(E)→일정(F)→감리(G)→준공 후 변경(H) 순서를 밟는 것과 같다.
- **오해 1**: TOGAF는 ADM 단계명 암기가 아니다. 단계마다 무엇을 "산출"하고 다음 단계에 무엇을 "넘기는지"가 핵심이다.
- **오해 2**: TOGAF 산출물을 그대로 베끼면 오히려 실패한다. Tailoring 없이 표준을 그대로 적용하면 문서 과다로 이어진다.

## 연결 개념
- EA — TOGAF가 만들어내는 대상(상위 개념)
- BDAT(Business·Data·Application·Technology) — ADM Phase B~D가 다루는 4대 아키텍처 도메인
- Architecture Governance — Phase G·H가 담당하는 준수·변경 통제 체계

# 📝 【답안용】 시험 답안 템플릿

> 목적: 시험장에서 25분에 그대로 쓰는 답안 양식. 작성방식(추상표현 금지·수치·도식·문제유형 전환)을 엄격히 지킨다.
> 핵심: TOGAF 답안은 ADM 단계, 산출물, 거버넌스, 조직 맞춤 적용을 함께 제시해야 한다.

## 핵심 인사이트 (3줄 요약)

> 1. **본질**: TOGAF는 EA 수립을 ADM 중심의 반복 절차, 산출물, 거버넌스로 표준화한 프레임워크이다.
> 2. **가치**: 업무·정보시스템·기술 아키텍처와 전환계획을 단계별로 연결해 아키텍처 의사결정 누락을 줄인다.
> 3. **판단 포인트**: ADM 단계 암기보다 조직 맞춤 테일러링, 이해관계자 관리, 준수 심의 운영이 답안의 차별점이다.

## 출제 의도 및 답안 포인트

| 출제 의도 | 반드시 짚을 핵심 | 감점 회피 포인트 |

| 실무 적용 역량 확인 | Tailoring, Repository, Compliance Review | 모든 산출물을 동일 깊이로 작성한다고 단정 |

> 요약: TOGAF 문제는 ADM 흐름을 기준으로 산출물과 거버넌스를 연결해야 한다.

## Ⅰ. 개요 및 필요성

- 개요: EA 수립·운영 프레임워크
- 배경: EA는 조직 범위가 넓어 절차와 산출물 기준이 없으면 설계 누락과 이해관계자 충돌이 발생한다.
- 필요성: ADM 반복 사이클과 거버넌스로 현행, 목표, 전환계획을 관리해야 한다.

---

## Ⅱ. 구조 및 구성요소

```text
Preliminary -> Architecture Vision -> BA -> IS Architecture -> TA -> Opportunities/Solutions -> Migration -> Governance -> Change
                 +-> Requirements Management가 전 단계 요구사항 통제
```

| 구성요소 | 역할 | 산출물 |
|:---|:---|:---|
| ADM | 아키텍처 개발 단계와 반복 절차 제공 | 단계별 아키텍처 산출물 |
| Requirements Management | 전 단계 요구사항 추적·변경 통제 | 요구사항 저장소, 변경 이력 |
| Architecture Content | 산출물, 빌딩블록, 참조모형 구조화 | 카탈로그, 매트릭스, 다이어그램 |
| Architecture Governance | 준수 심의와 예외 승인 운영 | 심의 기록, 준수 평가 |

> 요약: TOGAF는 ADM 절차를 중심으로 요구사항, 산출물, 거버넌스를 하나의 EA 운영 체계로 묶는다.

## Ⅲ. 동작원리 및 흐름도

```text
준비/원칙 -> 비전/범위 -> 업무 설계 -> 데이터/응용 설계 -> 기술 설계 -> 이행계획 -> 준수 점검 -> 변경관리
```

| 단계 | 처리 내용 | 검증 기준 |
|:---:|:---|:---|
| 1 | Preliminary와 Vision에서 범위·원칙·이해관계자 정의 | 아키텍처 원칙 승인, 범위 합의 |
| 2 | BA, Data, Application, Technology Architecture 작성 | 현행·목표·Gap 산출물 |
| 3 | Opportunities, Solutions, Migration Planning 수행 | 전환 웨이브, 비용, 위험 |
| 4 | Implementation Governance와 Change Management 운영 | 준수 심의, 예외 승인, 변경 이력 |

> 요약: TOGAF는 목표 구조를 만든 뒤 전환 웨이브와 구현 준수 점검까지 이어지는 반복 사이클로 동작한다.

> 요약: TOGAF는 대규모 EA에서 절차 표준화와 운영 통제가 필요할 때 적용 가치가 크다.

> 요약: TOGAF 적용 리스크는 과도한 산출물과 거버넌스 미운영이며 맞춤 범위와 준수 심의로 통제한다.

| 점검 항목 | 목표 기준 | 측정 방법 |
|:---|:---|:---|
| 요구 추적성 | 요구사항별 ADM 산출물 연결 100% | Requirements Repository 점검 |
| 산출물 품질 | 현행·목표·Gap 누락 0건 | Architecture Review Board 검토 |
| 준수 운영 | 구현 프로젝트 준수 검토 100% | Compliance Review 기록 |

> 요약: TOGAF 성과는 ADM 수행 여부가 아니라 요구 추적성, 산출물 품질, 준수 심의 기록으로 확인한다.

## Ⅵ. 실무 적용 및 결론

**적용 방안 3개:**
1. 조직 규모에 맞춰 ADM 산출물을 필수 10종, 선택 10종으로 분류하고 Tailoring Matrix에 근거를 기록함
2. Architecture Board를 구성해 Vision 승인, 목표 아키텍처 승인, 구현 준수 검토를 3회 이상 수행함
3. EA Repository에 원칙, 표준, 빌딩블록, 변경 이력을 등록하고 프로젝트 착수·종료 시점에 갱신함

**결론 (2줄):**
- 기술사 판단: 전사 EA와 다년 전환계획이면 TOGAF ADM을 적용하고, 단일 시스템 설계는 경량 아키텍처 프로세스로 축소함
- 향후 방향: TOGAF는 클라우드, 데이터, AI 거버넌스 산출물을 포함하도록 조직별 메타모델을 확장해야 함
