## Ⅰ. 개요
- **정의**: 빈번히 접근하는 데이터를 고속 저장소에 임시 보관하여 응답 지연을 줄이는 기법
- **배경/필요성**: 매 요청마다 원본 저장소를 조회하면 지연 시간 증가와 원본 부하 과중이 발생함
- **비유**: 자주 보는 책을 서재가 아닌 책상 위에 꺼내두는 것

| 출제 의도 | 반드시 짚을 핵심 | 감점 회피 포인트 |
|:---|:---|:---|
| 캐시 패턴별 정합성-성능 트레이드오프 | Cache-Aside, Write-Through, Write-Behind 차이 | 캐시 무효화(Invalidation) 문제를 반드시 언급할 것 |

> 요약: 응답 속도와 원본 부하를 동시에 개선하는 데이터 접근 최적화 기법임

## Ⅱ. 구성요소
```text
Client --> App Server --Cache Hit?--> Cache(Redis 등)
                       |                    |
                     Miss              Return Data
                       |
                       v
                    Database --Load--> Cache
```

| 구성요소 | 설명 | 비유 |
|:---|:---|:---|
| Cache Store | 데이터 사본을 저장하는 고속 인메모리 저장소 | 책상 위 메모 |
| Cache Policy | TTL, LRU, LFU 등 데이터 보관·퇴거 기준 | 메모 정리 규칙 |
| Invalidation | 원본 변경 시 캐시를 무효화하여 정합성을 유지하는 메커니즘 | 오래된 메모 폐기 |

> 요약: 고속 저장소에 정책 기반으로 데이터를 캐싱하고 무효화하는 구조임

## Ⅲ. 절차
```text
Request --> Cache Lookup --> Hit/Miss --> Response
```
- 1단계: Cache Lookup — 요청 키로 캐시 저장소 조회
- 2단계: Hit 처리 — 캐시에 데이터 존재 시 즉시 반환
- 3단계: Miss 처리 — 캐시 부재 시 원본 DB 조회 후 결과를 캐시에 적재
- 4단계: Invalidation — 데이터 변경 이벤트 발생 시 해당 캐시 항목 삭제 또는 갱신

> 요약: 조회-히트/미스-적재-무효화의 4단계 사이클로 운영됨

## Ⅳ. 문제점
- 캐시 스탬피드: 대량 키가 동시 만료되면 원본 DB에 순간 부하가 집중됨
- 정합성 불일치: Write-Behind 패턴에서 캐시와 DB 간 데이터 차이가 발생함
- 메모리 한계: 캐시 용량 초과 시 빈번한 퇴거로 히트율이 급락함

> 요약: 스탬피드, 정합성 불일치, 용량 한계가 주요 과제임

## Ⅴ. 개선방안
1. 단기: 만료 시간에 랜덤 지터(jitter) 추가로 동시 만료 분산
2. 중기: 이벤트 기반 무효화(CDC 등) 도입으로 캐시-DB 정합성 확보
3. 장기: 계층형 캐시(L1 로컬 + L2 분산) 아키텍처로 용량과 히트율 동시 확보

> 요약: 지터, 이벤트 무효화, 계층 캐시 순으로 안정성을 강화함

## Ⅵ. 전망
- 발전 방향: 서버리스 엣지 캐시와 AI 기반 프리페치가 확대되는 추세
- 기술사적 판단: 읽기 비율이 높은 워크로드에서 캐싱은 가장 비용 효율적 최적화 수단임
- 기술사 제언: 데이터 특성별 캐시 패턴 선택 가이드라인을 아키텍처 표준에 포함할 필요
