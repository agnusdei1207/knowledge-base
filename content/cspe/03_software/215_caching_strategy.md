## 핵심 인사이트 (3줄 요약)
- 느려터진 디스크(DB)에서 매번 데이터를 퍼오는 대신, **자주 찾는 데이터를 빛처럼 빠른 컴퓨터 메모리(RAM)에 잠시 올려두고 바로바로 꺼내 주는 성능 치트키**.
- 데이터를 읽을 때는 일단 캐시부터 찔러보고 없으면 DB로 가는 **Look-aside** 전략, 데이터를 쓸 때는 캐시에 먼저 쓰고 나중에 DB로 몰아서 붓는 **Write-behind** 전략 등 '어떻게 저장하고 꺼낼 것인가'가 핵심임.
- 캐시는 용량이 작기 때문에 "어떤 놈을 지울 것인가(Eviction)"가 중요한데, 실무에서는 가장 오랫동안 안 쓴 데이터를 지우는 **LRU(Least Recently Used)** 알고리즘이 절대 표준임.

## Ⅰ. 개요 및 필요성
- **개요**: 애플리케이션의 성능과 응답 속도를 향상시키기 위해, 데이터 접근이 빠른 임시 저장소(Cache)에 복사본을 저장해 두고 재사용하는 기법.
- **필요성**: 네이버 메인 뉴스는 1초에 10만 명이 봄. 10만 번 모두 오라클 DB(하드디스크)에 접속해서 Select 쿼리를 날리면 DB가 녹아내림. **"아니, 뉴스는 한 시간 동안 내용이 똑같잖아? 1번째 손님이 왔을 때 DB에서 캐와서 RAM에 올려두고, 나머지 99,999명한테는 RAM에 있는 복사본을 0.001초 만에 던져주자!"**
---
## Ⅱ. 아키텍처 및 핵심 원리
- **1. 읽기 전략 (Read Strategy)**:
  - **Look-aside (Lazy Loading)**: 가장 흔한 패턴. 
    1. 앱이 캐시를 찔러봄(Cache Hit). ➡️ 있으면 즉시 반환(끝).
    2. 캐시에 없으면(Cache Miss) ➡️ DB에서 읽어옴 ➡️ 캐시에 밀어 넣음 ➡️ 반환.
  - 장점: 캐시 서버가 죽어도 DB로 가면 되니까 서비스가 안 죽음. (대신 일시적으로 느려짐).
- **2. 쓰기 전략 (Write Strategy)**:
  - **Write-through**: 앱이 캐시에 먼저 쓰고, 캐시가 즉시 DB에도 씀. (데이터 불일치가 없지만, 두 번 써야 해서 쓰기가 느림).
  - **Write-behind (Write-back)**: 앱이 캐시에만 씀 (쓰기 속도 광속). 캐시는 그걸 모아뒀다가 5분에 한 번씩 DB에 쏟아부음(배치). (유튜브 좋아요 수에 쓰임. 중간에 캐시가 죽으면 데이터가 날아가는 위험 있음).
- **3. 캐시 축출 알고리즘 (Eviction Policy)**:
  - 메모리는 16GB밖에 안 됨. 꽉 차면? 
  - **LRU (Least Recently Used)**: 가장 오랫동안 아무도 안 찾아본 데이터를 버림. (실무 99% 사용).
  - **LFU (Least Frequently Used)**: 가장 조회수(빈도)가 적은 데이터를 버림.

```text
[ Look-aside 캐싱 패턴의 데이터 흐름 (가장 대중적) ]

 👤 고객 "아이유 검색!" 
   ⬇️
 🧠 [ Redis 캐시 서버 ] ---(있어?)---> ❌ Cache Miss! (아직 안 찾아봄)
   ⬇️
 🗄️ [ MySQL 원본 DB ] ---(조회)---> 📄 아이유 데이터 발견 (1초 소요 🐢)
   ⬇️
 🧠 [ Redis 캐시 서버 ] ---(저장)---> 📄 메모리에 아이유 데이터 복사! (TTL: 10분)
   ⬇️
 👤 고객 "아이유 데이터 도착!" (1.1초 소요)

 👥 1초 뒤, 다른 고객 10,000명 "아이유 검색!"
   ⬇️
 🧠 [ Redis 캐시 서버 ] ---(있어?)---> ✅ Cache Hit! (있지롱!) ➡️ 즉시 반환 (0.01초 소요 🚀)
   * 💡 DB는 건드리지도 않음. DB 평화로움.
```

## Ⅲ. 비교 및 연결
| 구분 | Memcached (멤캐시드) | Redis (레디스) |
|---|---|---|
| **데이터 구조** | 단순한 Key-Value (문자열만 가능) | **List, Hash, Set, Sorted Set 등 다양한 자료구조 지원** |
| **속도** | 엄청나게 빠름 | 엄청나게 빠름 (싱글 스레드) |
| **영속성(Persistence)**| 서버 꺼지면 데이터 다 날아감 (순수 메모리) | **AOF, RDB로 디스크에 백업 가능 (재부팅해도 안 날아감)** |
| **현재 실무 위상** | 구형 시스템에 가끔 남아있음 | **현대 클라우드 인프라의 글로벌 표준 캐시/세션 스토리지** |

## Ⅳ. 실무 적용 및 기술사 판단
- **Cache Stampede (캐시 쇄도) 현상 방어**: 실무에서 가장 자주 터지는 장애. 10분짜리 유효기간(TTL)을 가진 네이버 메인 뉴스 캐시가 딱 10분째 되는 순간 만료(Expire)되어 지워짐. 바로 그 0.1초 찰나에 1만 명의 유저가 동시에 접속함 ➡️ 1만 명 모두 Cache Miss가 남 ➡️ 1만 명이 동시에 DB에 쿼리를 때림 ➡️ DB 즉사. 기술사는 이를 막기 위해 **캐시에 값이 없을 때 1명만 DB에 다녀오게 Lock(Mutex)을 걸거나, TTL이 다 되기 전에 백그라운드 봇이 캐시를 미리 갱신해 두는(Pre-fetching)** 방어 아키텍처를 반드시 설계해야 함.
- **분산 세션 스토어로서의 Redis**: K8s 환경에서 파드가 수시로 죽고 살아나는 탓에, 서버 메모리에 로그인 정보(세션)를 들고 있으면 유저가 툭툭 튕김. 따라서 실무에서는 모든 백엔드 서버의 세션 정보를 서버 내부(Local)가 아니라, **외부에 띄워둔 Redis 서버(Global Cache) 한 곳으로 집중**시켜 무상태(Stateless) 아키텍처를 구현하는 것이 표준임.

## Ⅴ. 기대효과 및 결론
- 디스크 I/O라는 물리적인 속도 한계를 메모리 I/O로 우회하여, 서버나 DB 장비를 추가로 사지 않고도 시스템 성능을 100배 이상 끌어올릴 수 있는 가성비 최고의 마법.
- 트래픽이 예측 불가능하게 폭증하는 B2C 서비스(선착순 이벤트, 티켓팅, 뉴스)에서 DB가 찢어지는 것을 온몸으로 막아주는 가장 강력하고 든든한 방패임.

### 👶 어린이를 위한 3줄 비유 설명
1. 수학 문제를 풀 때마다(DB 조회), 두꺼운 백과사전(하드디스크)을 꺼내서 찾는 건 너무 오래 걸려요.
2. **캐시(Cache)**는 방금 찾았던 정답을 내 앞의 '작은 연습장(메모리)'에 잠시 적어두는 거예요.
3. 다음번에 똑같은 문제가 나오면 백과사전을 안 찾고 연습장만 쓱 보고(Cache Hit) 1초 만에 대답할 수 있어서 엄청 똑똑하고 빨라진답니다!
