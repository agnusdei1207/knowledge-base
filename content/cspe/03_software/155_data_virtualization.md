## Ⅰ. 개요
- **정의**: 이기종 데이터 소스를 물리적 이동 없이 논리적 뷰로 통합 제공하는 기술
- **배경/필요성**: ETL로 데이터를 복제하면 지연·중복·저장 비용이 발생하므로 실시간 논리 통합이 필요함
- **비유**: 여러 서점의 재고를 한 화면에서 검색하되 책을 한곳에 모으지 않는 것과 같음

| 출제 의도 | 반드시 짚을 핵심 | 감점 회피 포인트 |
|:---|:---|:---|
| 데이터 통합 방식 비교 | 물리 통합(ETL) vs 논리 통합(가상화) | 캐싱과 물리 복제 차이 구분 |

> 요약: 데이터를 이동하지 않고 논리 계층에서 통합 접근을 제공하는 기술임

## Ⅱ. 구성요소
```text
[소스 A] --+
[소스 B] --+--> [가상화 엔진] --> [통합 논리 뷰] --> [소비자]
[소스 C] --+         |
                [커넥터/어댑터]
                     |
                [쿼리 캐시]
```

| 구성요소 | 설명 | 비유 |
|:---|:---|:---|
| 가상화 엔진 | 분산 쿼리를 최적화·실행하는 핵심 처리기 | 통합 검색 엔진 |
| 커넥터/어댑터 | 이기종 소스별 프로토콜을 추상화하는 모듈 | 멀티탭 어댑터 |
| 통합 논리 뷰 | 여러 소스를 하나의 스키마로 노출하는 가상 테이블 | 통합 메뉴판 |
| 쿼리 캐시 | 반복 쿼리 결과를 임시 저장하여 응답 속도를 높이는 계층 | 즐겨찾기 목록 |

> 요약: 커넥터로 소스를 연결하고 가상화 엔진이 논리 뷰를 실시간 생성하는 구조임

## Ⅲ. 절차
```text
소스 등록 --> 스키마 매핑 --> 쿼리 연합 --> 결과 통합 반환
```
- 1단계: 소스 등록 — 커넥터를 통해 이기종 데이터 소스를 연결함
- 2단계: 스키마 매핑 — 소스별 스키마를 통합 논리 모델에 매핑함
- 3단계: 쿼리 연합 — 사용자 쿼리를 소스별 하위 쿼리로 분해·최적화함
- 4단계: 결과 통합 반환 — 각 소스 결과를 조인·집계하여 단일 결과로 반환함

> 요약: 소스등록-매핑-쿼리분해-결과통합의 4단계로 논리적 데이터 통합을 수행함

## Ⅳ. 문제점
- 성능 저하: 대량 조인 시 네트워크 I/O 병목 — 물리 통합 대비 응답 지연
- 소스 장애 전파: 특정 소스 불가용 시 전체 쿼리 실패 — 가용성 저하
- 보안 복잡성: 소스별 접근 통제 정책 상이 — 통합 뷰에서 권한 관리 복잡

> 요약: 성능 병목, 장애 전파, 보안 복잡성이 주요 제약 요인임

## Ⅴ. 개선방안
1. 단기: 쿼리 캐시·매터리얼라이즈드 뷰 활용으로 빈번 쿼리 응답 속도 개선
2. 중기: 서킷 브레이커 패턴 적용으로 소스 장애 시 부분 결과 반환
3. 장기: 통합 접근 통제 계층(ABAC) 도입으로 소스별 보안 정책 일원화

> 요약: 캐싱, 장애 격리, 통합 접근 통제로 단계적 개선이 필요함

## Ⅵ. 전망
- 발전 방향: 데이터 패브릭 아키텍처의 핵심 기술로 가상화 역할 확대
- 기술사적 판단: 클라우드 멀티소스 환경에서 논리 통합 수요 지속 증가 전망
- 기술사 제언: ETL과 가상화를 워크로드 특성에 따라 하이브리드로 적용할 필요
