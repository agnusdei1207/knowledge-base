## Ⅰ. 개요
- **정의**: 소스 데이터를 변환(Transform)하는 시점이 적재 전(ETL)인지 후(ELT)인지에 따른 데이터 통합 방식 분류임
- **배경/필요성**: 클라우드 DW의 컴퓨팅 자원이 충분해지며, 적재 후 변환이 가능한 ELT 패턴의 실용성이 높아짐
- **비유**: ETL은 식재료를 손질해서 냉장고에 넣는 것, ELT는 일단 냉장고에 넣고 요리할 때 손질하는 것

| 출제 의도 | 반드시 짚을 핵심 | 감점 회피 포인트 |
|:---|:---|:---|
| 두 방식의 구조적 차이와 선택 기준 | Transform 시점 차이와 DW 의존도 | ETL·ELT 각각의 장단을 균형 있게 서술 |

> 요약: 변환 시점 차이가 아키텍처·비용·유연성을 결정하는 핵심 기준임

## Ⅱ. 구성요소
```text
[Source] --> [Extract] --> [Transform] --> [Load] --> [DW]   : ETL
[Source] --> [Extract] ---------------------> [Load] --> [Transform in DW] : ELT
```

| 구성요소 | 설명 | 비유 |
|:---|:---|:---|
| Extract | 소스 시스템에서 원시 데이터를 추출하는 단계 | 창고에서 물건 꺼내기 |
| Transform | 정제·매핑·집계 등 비즈니스 규칙 적용 단계 | 식재료 손질 |
| Load | 대상 저장소에 데이터를 적재하는 단계 | 냉장고에 보관 |

> 요약: Extract-Transform-Load 세 단계의 순서 배치가 ETL과 ELT를 구분함

## Ⅲ. 절차
```text
요건정의 --> 소스매핑 --> 파이프라인구현 --> 검증/운영
```
- 1단계: 요건정의 — 소스·타겟 스키마, 변환 규칙, SLA 정의
- 2단계: 소스매핑 — 소스 컬럼과 타겟 컬럼 간 매핑 테이블 작성
- 3단계: 파이프라인구현 — ETL 도구 또는 DW 내 SQL 기반 ELT 스크립트 개발
- 4단계: 검증/운영 — 데이터 정합성 검증 후 스케줄링 및 모니터링 적용

> 요약: 요건-매핑-구현-검증 순서로 파이프라인을 구축함

## Ⅳ. 문제점
- ETL 변환 병목: 중간 스테이징 서버의 자원 한계 — 대용량 처리 시 지연 발생
- ELT 거버넌스 약화: 원시 데이터가 DW에 먼저 적재됨 — 민감 정보 노출 위험 증가
- 스키마 변경 대응 부담: 소스 스키마 변경 시 매핑 재작성 필요 — 유지보수 비용 증가

> 요약: 성능 병목, 보안 노출, 스키마 변경 대응이 주요 과제임

## Ⅴ. 개선방안
1. 단기: 파이프라인 병렬화 및 증분 처리(CDC) 도입으로 ETL 처리 시간 단축
2. 중기: DW 적재 전 마스킹·토큰화 레이어 추가로 ELT 환경의 민감 정보 보호
3. 장기: 스키마 레지스트리 기반 자동 매핑 갱신 체계 구축으로 유지보수 비용 절감

> 요약: 병렬화·보안 레이어·스키마 자동화로 각 문제를 단계적으로 해소함

## Ⅵ. 전망
- 발전 방향: 클라우드 네이티브 DW 확산으로 ELT가 기본 패턴으로 자리잡는 추세임
- 기술사적 판단: ETL과 ELT는 배타적 선택이 아닌, 데이터 민감도·볼륨에 따른 혼합 적용이 현실적임
- 기술사 제언: 변환 시점보다 데이터 품질 검증 시점 설계에 더 큰 비중을 둘 필요
