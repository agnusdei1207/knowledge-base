## Ⅰ. 개요
- **정의**: 시스템 성능을 정량 측정하기 위한 표준화된 평가 지표 체계임
- **배경/필요성**: 주관적 판단으로는 병목 원인 특정 불가하므로 객관적 수치 기반 평가 필요
- **비유**: 건강검진 시 혈압·혈당·심박수 등 수치로 상태를 판단하는 것과 동일함

| 출제 의도 | 반드시 짚을 핵심 | 감점 회피 포인트 |
|:---|:---|:---|
| 핵심 지표 간 관계와 측정 방법 | TPS·응답시간·자원사용률 3요소 연계 | 지표 간 상관관계 설명 누락 주의 |

> 요약: TPS·응답시간·자원사용률 등 정량 지표로 시스템 성능을 객관 평가하는 체계임

## Ⅱ. 구성요소
```text
Performance Metrics
  +-- Throughput (TPS, RPS)
  +-- Response Time (평균, 95th percentile)
  +-- Resource Utilization (CPU, Memory, I/O)
  +-- Error Rate (오류 비율)
  +-- Concurrent Users (동시 사용자 수)
```

| 구성요소 | 설명 | 비유 |
|:---|:---|:---|
| 처리량(TPS) | 단위 시간당 완료 트랜잭션 수 | 톨게이트 시간당 통과 차량 수 |
| 응답시간 | 요청 발생~응답 수신까지 소요 시간 | 주문 후 음식 도착까지 대기시간 |
| 자원사용률 | CPU·메모리·디스크 I/O 점유 비율 | 도로 차선 점유율 |
| 오류율 | 전체 요청 대비 실패 요청 비율 | 불량품 발생률 |

> 요약: 처리량·응답시간·자원사용률·오류율의 상호 연계로 성능 상태를 진단함

## Ⅲ. 절차
```text
목표 설정 -> 시나리오 설계 -> 부하 실행/측정 -> 결과 분석/보고
```
- 1단계: SLA 기반 목표 TPS·응답시간·오류율 한계값 설정
- 2단계: 사용자 행위 모델링 및 부하 시나리오(Think Time 포함) 설계
- 3단계: 부하 도구(JMeter, nGrinder 등)로 점진 부하 인가 및 지표 수집
- 4단계: 병목 구간 식별, 기준 대비 편차 분석 후 개선 권고 보고서 작성

> 요약: 목표 설정부터 결과 분석까지 4단계로 성능 지표를 체계적으로 측정함

## Ⅳ. 문제점
- 지표 편중: TPS만 측정하고 응답시간 분포 무시 — 95th percentile 지연 미탐지
- 환경 괴리: 테스트 환경과 운영 환경 차이 — 측정값의 운영 대표성 부족
- 기준선 부재: 과거 성능 데이터 미축적 — 성능 변화 추세 판단 불가

> 요약: 지표 편중·환경 괴리·기준선 부재가 성능 측정 신뢰도를 저하시킴

## Ⅴ. 개선방안
1. 단기: 평균값 외 P95·P99 백분위 응답시간 동시 측정 의무화
2. 중기: 컨테이너 기반 운영 동일 환경 구성으로 테스트-운영 간 환경 격차 해소
3. 장기: CI/CD 파이프라인 내 성능 회귀 테스트 자동화로 기준선 지속 갱신

> 요약: 백분위 측정 → 환경 일치 → 자동화 회귀 테스트로 측정 신뢰도를 확보함

## Ⅵ. 전망
- 발전 방향: AI 기반 이상 탐지로 성능 지표 자동 분석 및 예측 강화
- 기술사적 판단: 성능 지표의 정량적 관리가 SLA 준수와 서비스 안정성의 전제 조건임
- 기술사 제언: 개발 초기부터 성능 예산(Performance Budget) 할당 후 지표 기반 검증 필요
