# 📖 【암기용】 개념 완전 이해

> 목적: 성능 테스트 지표를 단순 용어가 아니라, 지표들이 수식으로 서로 어떻게 얽히는지까지 이해하게 만든다. 시험 답안 양식이 아니라, 이해를 위한 설명이다.

## 한눈에
- **개요**: **성능 테스트 지표**는 시스템의 처리 능력을 **처리량(TPS)**·**지연시간(Response Time)**·**동시성(Concurrent Users)**·**오류율**·**자원 사용률**의 다섯 축으로 나눠 정량 측정하는 기준이다.
- **왜 필요한가**: "사용자 1만 명 지원"이라는 말은 동시 접속자 수인지, 초당 요청 수인지, 피크 10분간의 순간 수치인지에 따라 전혀 다른 시스템 용량을 뜻한다. 다섯 지표를 분리해야 이 모호함을 없애고 병목과 검수 결과를 정확히 해석할 수 있다.
- **핵심 직관**: 도로 평가에서 차량 수, 평균 속도, 정체 길이, 사고율을 따로 보는 것처럼, 애플리케이션도 처리량·지연·동시성·오류를 분리해서 봐야 어디가 문제인지 짚어낼 수 있다.

## 핵심 용어 정리 (내부에 등장하는 것들)

| 용어 | 의미 | 비유 |
|:---|:---|:---|
| TPS(Transactions Per Second) | 서버가 초당 완료 처리한 트랜잭션 수 — 성공 요청 기준 | 식당이 한 시간에 처리한 주문 수 |
| 응답시간(Response Time) | 요청 시작부터 응답 완료까지 걸린 시간, p50/p95/p99 백분위수로 표현 | 주문 후 음식이 나오기까지 대기 시간 |
| 동시 사용자(Concurrent Users) | 같은 시점에 활동 중인 사용자 수 | 식당에 동시에 앉아 있는 손님 수 |
| Think Time | 사용자가 응답을 받은 뒤 다음 요청을 보내기까지 대기하는 시간 | 음식을 받고 먹는 동안(주문을 안 넣는 시간) |
| 오류율 | 실패 요청 비율(HTTP 5xx, timeout, assertion fail 포함) | 주문 누락·오배송 비율 |
| 자원 사용률 | CPU, 메모리, DB wait, GC pause 등 서버 내부 소모 지표 | 주방의 화구 점유율, 조리 대기열 |

## 깊이 이해

### TPS와 동시 사용자는 왜 다른가 — Little's Law로 수치 이해하기
- 대기행렬 이론의 **Little's Law**: 동시 사용자 수(L) = 도착률(TPS, λ) × 평균 체류시간(W, 응답시간+think time). 이 공식이 "동시 사용자 수 ≠ TPS"의 수학적 근거다.
- 예: TPS 100(초당 100건 도착)이고, 사용자가 응답 대기 2초 + think time 8초로 시스템에 총 10초 머문다면, 동시 사용자 수 = 100 × 10 = **1,000명**이다.
- 반대로 "동시 사용자 5,000명"이 주어졌다고 하자. Think time 8초, 응답시간 0.5초라면 평균 체류시간은 8.5초이므로, TPS = 5,000 ÷ 8.5 ≈ **588 TPS**다. 만약 think time을 3초로 짧게 설정했다면 체류시간 3.5초, TPS = 5,000 ÷ 3.5 ≈ 1,429로 크게 달라진다.
- 즉 같은 "동시 사용자 5,000명"이라도 think time 가정에 따라 실제로 걸리는 부하(TPS)가 2배 넘게 차이난다 — 부하 시나리오를 설계할 때 think time을 명시해야 하는 이유다.

### percentile이 평균보다 중요한 이유 — 수치로 확인
- 100개 요청 중 95개는 100ms에 끝나고 5개는 GC pause나 DB Lock 대기로 3,000ms가 걸렸다고 하자. 평균은 (95×100 + 5×3,000) ÷ 100 = 245ms로, 마치 전체적으로 준수한 성능처럼 보인다.
- 하지만 p95는 100ms, p99는 3,000ms 근처다. 평균만 보고했다면 사용자 5%가 실제로 겪는 3초 지연을 완전히 놓친다 — SLA는 항상 p95/p99로 정의해야 이런 이상치를 감춰지지 않게 한다.

### 오류율을 셀 때 무엇을 실패로 볼 것인가
- HTTP 5xx는 물론, 타임아웃(응답은 안 왔지만 서버 로그엔 에러가 없는 경우), assertion fail(HTTP 200을 받았지만 응답 본문의 값이 기대와 다른 경우, 예: 결제는 성공했다는데 금액이 0으로 찍힘)까지 오류로 포함해야 실제 실패율을 놓치지 않는다.

### 병목을 지표로 구분하는 판별 원리
- CPU 사용률이 90% 이상으로 지속되면 CPU-bound(연산 자체가 병목). CPU는 낮은데(예: 40%) 응답이 느리면 DB Lock 대기·네트워크 RTT 같은 I/O-bound 병목을 의심한다. 응답시간이 간헐적으로 튀는 패턴이면 GC pause(Stop-the-World)를 의심하고 GC 로그의 pause time을 확인한다.
- 예: p95는 300ms인데 p99.9만 5,000ms로 튀는 경우, 이는 평상시 힙이 부족해 대형 GC가 드물게 발생하는 패턴과 일치한다 — 힙 크기 조정이나 GC 알고리즘 변경으로 접근한다.

### 비유와 흔한 오해
- **비유**: 식당의 실력을 보려면 한 시간 주문 수(TPS), 주문 후 음식 대기 시간(응답시간), 동시에 앉은 손님 수(동시 사용자), 주문 누락률(오류율)을 같이 봐야 한다. 손님이 많다고(동시 사용자↑) 회전율(TPS)이 항상 높은 것은 아니다 — 손님이 오래 앉아 있으면(think time↑) 같은 손님 수로도 회전율은 떨어진다.
- **오해**: 동시 사용자 5,000명이 TPS 5,000을 뜻하지 않는다. Little's Law가 보여주듯 TPS는 동시 사용자 수를 체류시간으로 나눈 값이며, think time을 얼마로 가정하느냐에 따라 같은 동시 사용자 수도 전혀 다른 TPS로 이어진다.

## 연결 개념
- Little's Law (동시 사용자·TPS·응답시간을 잇는 대기행렬 이론적 근거)
- 313 부하·스트레스·소크 테스트 (이 지표들을 정상·한계·장시간 조건별로 적용, 후행)
- APM (테스트 중 Trace, DB Query, GC, 자원 병목 관측 도구)

# 📝 【답안용】 시험 답안 템플릿

> 목적: 성능 지표를 정의하고, 지표 간 관계와 해석 기준을 시험 답안에 바로 전개한다.
> 핵심: TPS·응답시간·동시 사용자는 같은 의미가 아니며, 워크로드와 측정 구간을 함께 제시해야 한다.

## 핵심 인사이트 (3줄 요약)

> 1. **본질**: 성능 테스트 지표는 처리량(TPS), 지연시간, 동시성, 오류율, 자원 사용률을 정량 측정하는 기준이다.
> 2. **가치**: 평균값 대신 p95/p99, 피크 구간, 오류율을 함께 제시해 사용자 체감 지연과 시스템 한계를 판정한다.
> 3. **판단 포인트**: 목표 TPS만 달성해도 p95 지연 또는 오류율 기준을 넘으면 성능 통과로 볼 수 없다.

## 출제 의도 및 답안 포인트

| 출제 의도 | 반드시 짚을 핵심 | 감점 회피 포인트 |
|:---|:---|:---|
| 지표 정의 정확성 확인 | TPS, response time, concurrent user 차이 | 동시 사용자와 TPS 동일시 |
| 성능 시험 해석 역량 확인 | 평균·p95·p99, 오류율, 자원 사용률 | 평균 응답시간만 제시 |
| 병목 진단 판단 확인 | CPU, DB, Lock, GC, Network 지표 연결 | 툴 이름만 나열 |

> 요약: 이 문제는 지표 정의보다 지표 간 관계와 병목 해석을 요구한다.

## Ⅰ. 개요 및 필요성

- 개요: 처리 능력의 판정 지표
- 배경: TPS, 응답시간, 동시 사용자는 각각 처리량·지연·부하 규모를 나타내므로 단일 지표로 용량을 판단할 수 없음
- 필요성: TPS, p95 응답시간, 오류율, CPU·메모리 사용률을 함께 측정해 인수 기준과 증설 기준을 산정해야 함

---

## Ⅱ. 구조 및 구성요소

```text
워크로드 모델 -> 가상 사용자 -> 요청 발생 -> 서버 처리 -> 지표 수집
                 / TPS / 응답시간 / 동시 사용자 / 오류율 / 자원 사용률
```

| 구성요소 | 역할 | 특이사항 |
|:---|:---|:---|
| TPS | 초당 완료 트랜잭션 수 | 성공 요청 기준, 업무별 가중치 필요 |
| 응답시간 | 요청 시작부터 응답 완료까지 지연 | 평균보다 p95/p99 사용 |
| 동시 사용자 | 같은 시점에 활동 중인 사용자 수 | think time과 세션 유지 시간 반영 |
| 오류율 | 실패 요청 비율 | HTTP 5xx, timeout, assertion fail 포함 |

> 요약: 성능 지표는 처리량·지연·동시성·실패율을 함께 봐야 부하 조건을 해석할 수 있다.

## Ⅲ. 동작원리 및 흐름도

```text
시나리오 정의 -> 부하 주입 -> 응답 측정 -> 자원 관측 -> 기준 판정
```

| 단계 | 처리 내용 | 검증 기준 |
|:---:|:---|:---|
| 1 | 업무별 시나리오와 데이터 건수 정의 | 조회 70%, 등록 20%, 배치 10% |
| 2 | 가상 사용자와 ramp-up 설정 | 0 -> 5,000명, 30분 증가 |
| 3 | 요청별 TPS·지연·오류율 측정 | TPS 1,000, p95 500ms |
| 4 | 서버·DB·네트워크 자원 수집 | CPU 70% 이하, DB wait 20ms 이하 |
| 5 | 목표 대비 통과·미달 판정 | 리포트, 병목 근거, 재시험 조건 |

> 요약: 성능 시험은 워크로드 정의부터 지표 수집과 병목 근거까지 연결되어야 판정 가능하다.

## Ⅴ. 심화 비교 및 적용 판단

> 요약: 성능 지표는 일회성 시험값보다 기준선과 회귀 탐지에 연결될 때 운영 가치가 생긴다.

| 리스크 | 원인 | 대응 방안 | 확인 지표 |
|:---|:---|:---|:---|

> 요약: 성능 시험 리스크는 운영 로그 기반 워크로드와 관측 지표 확대로 줄인다.

| 점검 항목 | 목표 기준 | 측정 방법 |
|:---|:---|:---|
| 처리량 | 목표 업무 TPS 1,000 이상 | JMeter, k6, Gatling |
| 지연 | 주요 API p95 500ms 이하 | APM percentile, test report |
| 자원/오류 | 오류율 0.1% 이하, CPU 70% 이하 | Prometheus, system metrics |

> 요약: 성능 통과는 처리량·지연·오류·자원 기준을 동시에 만족하는 경우로 한정한다.

## Ⅵ. 실무 적용 및 결론

**적용 방안 3개:**
1. 운영 로그에서 상위 20개 API를 추출하고 조회·등록·배치 비율로 JMeter/k6 시나리오 작성
2. 목표값을 TPS 1,000, p95 500ms, 오류율 0.1%, CPU 70% 이하처럼 동시 판정 조건으로 명시
3. 테스트 중 APM Trace, DB wait event, GC pause, 네트워크 RTT를 수집해 병목별 조치 이력 관리

**결론 (2줄):**
- 기술사 판단: TPS 목표를 먼저 보고, p95 지연과 오류율이 기준을 넘으면 용량 증설보다 병목 제거를 우선한다
- 향후 방향: 성능 지표는 배포 파이프라인의 성능 회귀 테스트와 SLO 대시보드로 연결된다
