# 📖 【암기용】 개념 완전 이해

> 목적: 성능 테스트 지표를 단순 용어가 아니라 부하 조건과 검수 기준으로 이해하게 만든다.

## 한눈에
- **개요**: 시스템 처리 능력을 TPS, 응답시간, 동시 사용자, 오류율, 자원 사용률로 측정하는 기준
- **왜 필요한가**: "사용자 1만 명 지원"은 동시 접속인지, 초당 요청인지, 피크 10분인지가 다르다. 지표를 분리해야 병목과 검수 결과를 해석할 수 있다.
- **핵심 직관**: 도로 평가에서 차량 수, 평균 속도, 정체 길이, 사고율을 따로 보는 것처럼 애플리케이션도 처리량·지연·동시성·오류를 분리해 본다.

## 깊이 이해
- **배경·문제의식**: 성능 목표를 평균 응답시간만으로 쓰면 p95 지연, 짧은 피크, 오류 재시도, DB Lock 병목이 가려진다. 시험 결과는 워크로드, 데이터 건수, 네트워크 조건까지 함께 읽어야 한다.
- **작동 원리**: 가상 사용자를 늘리며 요청을 발생시키고, 서버가 완료한 초당 트랜잭션 수(TPS), 요청 시작부터 응답 완료까지 시간, 동시 세션 수, HTTP 5xx·타임아웃 비율을 수집한다.
- **비유**: 식당의 실력을 보려면 한 시간 주문 수, 주문 후 음식 대기 시간, 동시에 앉은 손님 수, 주문 누락률을 같이 봐야 한다.
- **구체 예시**: 목표가 TPS 1,000, p95 500ms, 동시 사용자 5,000명, 오류율 0.1% 이하라면 네 조건을 같은 테스트 구간에서 동시에 충족해야 통과다.
- **흔한 오해·주의점**: 동시 사용자 5,000명이 TPS 5,000을 뜻하지 않는다. 사용자는 생각 시간(think time)을 가지며, TPS는 요청 빈도와 처리 완료 수로 계산된다.

## 연결 개념
- 부하 테스트 - 목표 TPS에서 기준 충족 여부 확인
- 스트레스 테스트 - 한계점과 병목 지점 확인
- APM - 테스트 중 Trace, DB Query, 자원 병목 관측

# 📝 【답안용】 시험 답안 템플릿

> 목적: 성능 지표를 정의하고, 지표 간 관계와 해석 기준을 시험 답안에 바로 전개한다.
> 핵심: TPS·응답시간·동시 사용자는 같은 의미가 아니며, 워크로드와 측정 구간을 함께 제시해야 한다.

## 핵심 인사이트 (3줄 요약)

> 1. **본질**: 성능 테스트 지표는 처리량(TPS), 지연시간, 동시성, 오류율, 자원 사용률을 정량 측정하는 기준이다.
> 2. **가치**: 평균값 대신 p95/p99, 피크 구간, 오류율을 함께 제시해 사용자 체감 지연과 시스템 한계를 판정한다.
> 3. **판단 포인트**: 목표 TPS만 달성해도 p95 지연 또는 오류율 기준을 넘으면 성능 통과로 볼 수 없다.

## 출제 의도 및 답안 포인트

| 출제 의도 | 반드시 짚을 핵심 | 감점 회피 포인트 |
|:---|:---|:---|
| 지표 정의 정확성 확인 | TPS, response time, concurrent user 차이 | 동시 사용자와 TPS 동일시 |
| 성능 시험 해석 역량 확인 | 평균·p95·p99, 오류율, 자원 사용률 | 평균 응답시간만 제시 |
| 병목 진단 판단 확인 | CPU, DB, Lock, GC, Network 지표 연결 | 툴 이름만 나열 |

> 요약: 이 문제는 지표 정의보다 지표 간 관계와 병목 해석을 요구한다.

---

## Ⅰ. 개요 및 필요성

성능 테스트 지표는 처리 능력의 판정 기준이다. TPS는 처리량, 응답시간은 지연, 동시 사용자는 부하 규모를 나타낸다. 세 지표를 오류율·자원 사용률과 함께 측정해야 인수 기준과 용량 산정이 가능하다.

---

## Ⅱ. 구조 및 구성요소

```text
워크로드 모델 -> 가상 사용자 -> 요청 발생 -> 서버 처리 -> 지표 수집
                 / TPS / 응답시간 / 동시 사용자 / 오류율 / 자원 사용률
```

| 구성요소 | 역할 | 특이사항 |
|:---|:---|:---|
| TPS | 초당 완료 트랜잭션 수 | 성공 요청 기준, 업무별 가중치 필요 |
| 응답시간 | 요청 시작부터 응답 완료까지 지연 | 평균보다 p95/p99 사용 |
| 동시 사용자 | 같은 시점에 활동 중인 사용자 수 | think time과 세션 유지 시간 반영 |
| 오류율 | 실패 요청 비율 | HTTP 5xx, timeout, assertion fail 포함 |

> 요약: 성능 지표는 처리량·지연·동시성·실패율을 함께 봐야 부하 조건을 해석할 수 있다.

---

## Ⅲ. 동작원리 및 흐름도

```text
시나리오 정의 -> 부하 주입 -> 응답 측정 -> 자원 관측 -> 기준 판정
```

| 단계 | 처리 내용 | 검증 기준 |
|:---:|:---|:---|
| 1 | 업무별 시나리오와 데이터 건수 정의 | 조회 70%, 등록 20%, 배치 10% |
| 2 | 가상 사용자와 ramp-up 설정 | 0 -> 5,000명, 30분 증가 |
| 3 | 요청별 TPS·지연·오류율 측정 | TPS 1,000, p95 500ms |
| 4 | 서버·DB·네트워크 자원 수집 | CPU 70% 이하, DB wait 20ms 이하 |
| 5 | 목표 대비 통과·미달 판정 | 리포트, 병목 근거, 재시험 조건 |

> 요약: 성능 시험은 워크로드 정의부터 지표 수집과 병목 근거까지 연결되어야 판정 가능하다.

---

## Ⅳ. 특징

| 구분 | 단일 지표 접근 | 복합 지표 접근 | 수치 컬럼 |
|:---|:---|:---|:---|
| 처리량 | TPS만 측정 | TPS와 오류율 동시 측정 | TPS 1,000, 오류율 0.1% |
| 지연 | 평균 응답시간 | p95/p99 응답시간 | p95 500ms, p99 1s |
| 동시성 | 접속자 수 집계 | 활성 사용자와 think time 반영 | 동시 사용자 5,000명 |

> 요약: 검수 기준은 TPS, p95 지연, 오류율이 같은 구간에서 동시에 충족되는지로 판단한다.

## Ⅴ. 심화 비교 및 적용 판단

| 비교 축 | 기존/대안 | 본 키워드 | 선택 기준 |
|:---|:---|:---|:---|
| 측정 방식 | 평균 응답시간 | p95/p99 percentile | 사용자 체감 지연 확인 |
| 비용/성능 | 최대 서버 투입 | 병목 기반 용량 산정 | CPU, DB wait, GC time |
| 운영/위험 | 시험 1회 리포트 | CI 성능 기준선 관리 | 릴리스별 회귀 탐지 |

> 요약: 성능 지표는 일회성 시험값보다 기준선과 회귀 탐지에 연결될 때 운영 가치가 생긴다.

| 리스크 | 원인 | 대응 방안 | 확인 지표 |
|:---|:---|:---|:---|
| 결과 왜곡 | 캐시 예열·데이터 부족 | cold/warm 구간 분리 | 캐시 hit ratio |
| 과소 부하 | think time 미반영 | 운영 로그 기반 모델링 | request per user |
| 병목 미식별 | 서버 지표만 수집 | APM, DB AWR, flame graph | DB wait, GC pause |

> 요약: 성능 시험 리스크는 운영 로그 기반 워크로드와 관측 지표 확대로 줄인다.

| 점검 항목 | 목표 기준 | 측정 방법 |
|:---|:---|:---|
| 처리량 | 목표 업무 TPS 1,000 이상 | JMeter, k6, Gatling |
| 지연 | 주요 API p95 500ms 이하 | APM percentile, test report |
| 자원/오류 | 오류율 0.1% 이하, CPU 70% 이하 | Prometheus, system metrics |

> 요약: 성능 통과는 처리량·지연·오류·자원 기준을 동시에 만족하는 경우로 한정한다.

## Ⅵ. 실무 적용 및 결론

**적용 방안 3개:**
1. 운영 로그에서 상위 20개 API를 추출하고 조회·등록·배치 비율로 JMeter/k6 시나리오 작성
2. 목표값을 TPS 1,000, p95 500ms, 오류율 0.1%, CPU 70% 이하처럼 동시 판정 조건으로 명시
3. 테스트 중 APM Trace, DB wait event, GC pause, 네트워크 RTT를 수집해 병목별 조치 이력 관리

**결론 (2줄):**
- 기술사 판단: TPS 목표를 먼저 보고, p95 지연과 오류율이 기준을 넘으면 용량 증설보다 병목 제거를 우선한다
- 향후 방향: 성능 지표는 배포 파이프라인의 성능 회귀 테스트와 SLO 대시보드로 연결된다
