## 핵심 인사이트 (3줄 요약)
- "서버 엄청 좋은 거 샀으니까 우리 시스템 빠르겠죠?" ➡️ 감으로 찍지 말고, 시스템이 얼마나 많은 일을 얼마나 빨리 쳐내는지 **3가지 황금 지표(동시 사용자, TPS, 응답 시간)**로 성적표를 매겨야 함.
- 핵심 공식은 리틀의 법칙(Little's Law). **`동시 사용자 = TPS × (응답 시간 + Think Time)`**. 이 톱니바퀴 공식 하나로 "1만 명이 접속할 때 3초 안에 응답하려면 서버가 초당 몇 건(TPS)을 처리해야 하는가?"를 수학적으로 도출함.
- 단순히 수치가 높은 게 중요한 게 아님. 부하를 계속 올리다가 TPS가 더 이상 안 오르고 그래프가 꺾이는 **'포화점(Saturation Point)'**을 찾아내고, 그 원인이 DB인지 CPU인지 병목을 박살 내는 것이 성능 테스트의 진짜 목적임.

## Ⅰ. 개요 및 필요성
- **개요**: 시스템의 처리 용량과 속도를 정량적으로 평가하기 위해 측정하는 핵심 성능 지표(Metrics). 부하 테스트(Load Test) 시 병목 구간 식별과 용량 산정(Capacity Planning)의 절대적 기준.
- **필요성**: 수능 성적 발표 날, 서버가 뻗었음. 사장님이 "얼마나 트래픽이 몰렸길래 터졌어? 서버 몇 대 더 사면 돼?"라고 화를 냄. 개발자가 "어... 사람이 엄청 많이 와서 느렸습니다"라고 답하면 짤림. **"아니, '초당 5,000건(TPS)이 들어왔는데 우리 서버 처리량이 2,000건이라 터졌으니, 서버를 3배 늘려야 합니다'라고 수학적이고 과학적인 지표로 대답할 순 없어?"**

## Ⅱ. 핵심 아키텍처 및 3대 지표 원리 (리틀의 법칙)
수학자 John Little이 마트 계산대 줄 서는 것을 보고 만든 법칙이 서버에도 똑같이 적용됨.

### 1. 동시 사용자 (Concurrent Users)
- **정의**: 현재 시스템에 로그인해서 화면을 보고 있거나 버튼을 누르고 있는 '활성 상태의 유저 수'.
- **주의점**: 누적 회원 수(100만 명)와 헷갈리면 안 됨. 지금 이 1초의 찰나에 서버와 연결되어 있는 진짜 사람 수임.

### 2. 응답 시간 (Response Time)
- **정의**: 유저가 "검색" 버튼을 누른 순간부터, 화면에 결과가 뜰 때까지 걸린 전체 시간 (네트워크 왕복 + 서버 처리 + DB 조회).
- **목표**: 보통 1~3초 이내. 3초가 넘어가면 유저가 짜증 나서 앱을 끔.

### 3. TPS (Transactions Per Second, 초당 처리 건수)
- **정의**: 서버가 1초 동안 완벽하게 끝마친 '업무(트랜잭션)'의 개수. **성능 평가의 꽃이자 전투력 수치.**
- **리틀의 법칙 공식 적용**:
  - `적정 TPS = (동시 사용자 수) / (응답 시간 + 사용자가 다음 버튼을 누를 때까지 멍때리는 시간[Think Time])`
  - 예: 동시 사용자 10,000명, 목표 응답 시간 1초, 유저가 글 읽는 시간 9초. ➡️ `TPS = 10,000 / (1 + 9) = 1,000`. 
  - 즉, 우리 서버는 무조건 **1,000 TPS** 전투력을 가져야 1만 명을 버팀!

```text
[ 병목(Bottleneck) 그래프와 포화점 ]

 📈 유저가 늘어날수록 (부하 증가):
 1) 초기: 유저 증가 ➡️ TPS 쑥쑥 오름 ➡️ 응답 시간 1초 유지 (아주 평온).
 2) **포화점 (Saturation / 변곡점)**: 서버 CPU가 100%를 찍음. 
 3) 헬게이트: 유저 계속 증가 ➡️ TPS는 더 이상 안 오르고 멈춤 ➡️ 응답 시간은 1초 ➡️ 5초 ➡️ 30초로 미친 듯이 수직 상승! ➡️ 타임아웃 장애 터짐! 💥
```

## Ⅲ. 오해와 진실
| 오해 | 진실 |
|---|---|
| "응답 시간이 평균 1초니까 우리 서버 성능 엄청 좋은 거 아님?" | **평균(Average)의 함정.** 평균이 1초여도, 99명은 0.1초 만에 받고 1명이 90초 걸려서 평균 1초가 나왔을 수 있음. 그 1명은 쌍욕을 함. 현대 성능 지표에서는 평균을 버리고 **99퍼센타일(P99) 지표**를 씀. "하위 1%의 가장 불운한 유저도 2초 안에는 응답을 받았다"는 것을 증명해야 진정한 성능임. |
| "무조건 TPS 높게 나오게 테스트 쏴주세요!" | 테스트 툴(JMeter)에서 Think Time(유저가 생각하는 3~5초의 대기 시간)을 0초로 설정하고 쏘면 봇(Bot)들의 공격임. 실제 인간의 패턴(Think Time)을 반영해야 서버가 세션을 유지하며 버티는 진짜 '동시 사용자 버퍼' 능력을 알 수 있음. |

## Ⅳ. 실무 적용 및 기술사 판단
- **용량 산정(Capacity Planning)의 근거**: 기술사는 차세대 시스템 서버 스펙을 잡을 때, `Peak Time 동시 접속자 수`를 마케팅팀으로부터 받아 리틀의 법칙으로 `목표 TPS`를 역산출해야 함. 이 목표 TPS를 Jmeter로 쏴서 **포화점(Saturation Point)을 찾고, 그 포화점의 원인이 DB 커넥션 풀 부족인지, CPU 부족인지 APM 툴(Scouter)로 찍어내 병목을 제거하는 튜닝(Tuning)**을 주도해야 함.
- **SRE (Error Budget) 메트릭 연동**: 이 지표들은 테스트 환경에서만 쓰는 게 아님. 기술사는 운영 환경(Prometheus/Grafana)에 RED 메트릭(Rate=TPS, Errors, Duration=응답시간) 대시보드를 구축하고, P99 응답 시간이 3초를 넘기면 즉시 Auto-scaling(서버 증설)이 발동되도록 아키텍처를 자동화해야 함.

## Ⅴ. 기대효과 및 결론
- "빠르다, 느리다"라는 주관적이고 감정적인 대화를 숫자가 지배하는 공학적 논의(Throughput, Latency)로 끌어올림.
- 블랙프라이데이, 수강신청 등 예측 불가능한 트래픽 쓰나미가 몰려오기 전에, 우리 시스템의 방어력(한계치)을 수치로 정확히 알고 선제적으로 인프라를 증설할 수 있게 해주는 필수 계기판임.

### 👶 어린이를 위한 3줄 비유 설명
1. **동시 사용자**는 마트에서 쇼핑카트를 끌고 돌아다니는 '손님의 수'예요.
2. **응답 시간**은 손님이 계산대에 줄을 서서 물건을 다 찍고 나갈 때까지 걸린 '기다린 시간'이에요.
3. **TPS**는 계산원 아주머니가 바코드를 '1초에 띡! 띡! 몇 개나 찍어내는지'의 속도예요! 손님이 100명(동시 사용자)이나 몰렸는데 아주머니의 바코드 속도(TPS)가 느리면, 기다리는 시간(응답 시간)이 엄청 길어져서 손님들이 화를 내겠죠?

### 🔀 문제 유형별 목차 전환 (이 키워드 출제 시)
- **개념/공식형 (Ⅱ·Ⅲ 강조)**: 3대 지표의 명확한 정의. 리틀의 법칙(N = λT)에 기반한 동시 접속자 수, TPS, 응답 시간, Think Time 간의 상관관계 공식 및 수치 예시 도식화. 부하 증가에 따른 포화점(Saturation Point/변곡점) 그래프 표현.
- **성능 튜닝/용량 산정형 (Ⅳ·Ⅴ 강조)**: 클라우드 차세대 시스템 구축 시 목표 TPS 산출을 통한 Capacity Planning 프로세스. 부하 테스트 툴(JMeter, nGrinder)과 APM(Scouter)을 결합한 병목 구간(DB 락, Thread Pool 고갈) 식별 및 성능 최적화(Tuning) 전략.
