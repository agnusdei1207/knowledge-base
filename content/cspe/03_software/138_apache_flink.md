## 미리 알고가기

- 이벤트 시간(Event Time)은 이벤트가 발생한 시각이며 처리 서버의 현재 시각과 구분됨
- 워터마크(Watermark)는 이벤트 시간이 특정 시점까지 진행됐음을 알리는 표식임
- Keyed State는 같은 키의 이벤트가 공유하는 연산 상태이며 키별로 분할 저장됨
- 체크포인트는 소스 위치와 연산자 상태를 일관된 시점으로 저장하는 자동 복구 스냅샷임
- 세이브포인트는 배포·업그레이드·병렬도 변경을 위해 운영자가 생성하는 상태 스냅샷임
- 역압력(Backpressure)은 하위 연산자의 처리 지연이 상위 연산자의 전송 속도를 제한하는 상태임

## 작성 근거(검토용)

- Flink는 이벤트 시간·상태 연산·워터마크·체크포인트·역압력을 핵심 판단축으로 선정함
- 비교표는 Spark Structured Streaming과 실행 단위·시간 처리·상태·복구·지연·적합 업무를 대비함
- 절차는 이벤트 시간 부여부터 키 분할, 상태 갱신, 체크포인트와 결과 커밋까지 실제 상태 변화를 설명함
- 제목부터 결론까지 모든 문장·표 셀·요약을 5회 전수 검수해 상태 보장과 싱크 보장 조건을 분리함

## Ⅰ. 개요

- **정의/개념**: Flink는 연속 데이터플로에서 이벤트 시간·키별 상태·체크포인트로 스트림 연산을 수행하는 분산 처리 엔진임
- **배경/필요성**: 순서가 뒤바뀐 이벤트의 시간 기준 집계와 장애 후 상태 복구를 지속 처리하기 위해 이벤트 시간과 일관된 상태 관리가 필요함

## Ⅱ. 특징

- 레코드를 연속 처리하며 키 분할과 연산자 체인으로 병렬 데이터플로를 실행함
- 이벤트 시간과 워터마크로 순서가 뒤바뀐 이벤트의 윈도 종료 시점을 판단함
- Keyed State와 Operator State를 상태 백엔드에 두고 연산자가 상태를 직접 관리함
- 체크포인트 장벽이 소스 위치와 분산 연산자 상태를 일관된 스냅샷으로 묶음
- 하위 연산자 처리량이 부족하면 역압력을 상위 연산자로 전파해 버퍼 증가를 제한함

## Ⅲ. 종류 및 비교

| 판단 기준 | Spark Structured Streaming | Apache Flink |
|:---|:---|:---|
| 기본 실행 단위 | 입력을 증분 마이크로배치로 처리 | 이벤트를 연속 데이터플로로 처리 |
| 이벤트 시간 | 워터마크와 트리거로 마이크로배치 결과 갱신 | 워터마크와 타이머로 연산자 상태 갱신 |
| 상태 배치 | 상태 저장소를 질의 계획과 배치 실행에 연결 | Keyed State를 연산자 병렬 인스턴스에 분할 |
| 장애 복구 | 체크포인트와 입력 로그로 질의 상태 복구 | 장벽 스냅샷과 재생 가능한 소스로 상태 복구 |
| 지연 특성 | 배치 트리거 간격이 결과 갱신 주기에 반영 | 레코드 도착 후 연산자 체인을 연속 통과 |
| 적합 업무 | SQL 중심 배치·스트림 통합 처리 | 이벤트 시간·타이머·대형 상태 기반 처리 |

> 요약: Flink는 연속 데이터플로에서 이벤트 시간과 키별 상태를 처리하고 체크포인트로 완료된 지점을 복구함.

## Ⅳ. 구성요소 및 구조

| 구성요소 | 설명 |
|:---|:---|
| Client | 응용 코드를 Job Graph로 변환해 JobManager에 제출함 |
| JobManager | Task를 스케줄링하고 체크포인트·장애 복구를 조정함 |
| TaskManager·Slot | 연산자 Subtask를 실행하고 데이터 스트림을 교환함 |
| Source·Watermark | 이벤트와 발생 시각을 읽고 이벤트 시간 진행 정보를 생성함 |
| Operator·State Backend | 키별 변환·윈도 연산과 상태의 작업 사본을 관리함 |
| Checkpoint Storage | 상태 스냅샷을 영속 저장해 장애 후 복구 지점을 제공함 |
| Sink | 연산 결과를 트랜잭션 또는 멱등 방식으로 외부 시스템에 반영함 |

```text
Source·Watermark -> Keyed Operator·State -> Window·Timer -> Sink
                          |
                          v
                 Checkpoint Storage
```

> 요약: JobManager가 Task를 조정하고 TaskManager의 연산자는 워터마크·키별 상태·체크포인트로 결과를 계산함.

## Ⅴ. 원리 및 절차 흐름도

```text
시간 부여·워터마크 -> 키 분할 -> 상태·윈도 갱신 -> 장벽 스냅샷 -> 결과 커밋
```

1. **시간 부여**: Source가 이벤트 발생 시각을 추출하고 워터마크를 데이터플로에 전달함
2. **키 분할**: `keyBy`가 같은 키의 이벤트를 동일한 병렬 연산자로 보냄
3. **상태 갱신**: 연산자가 이벤트별 상태를 갱신하고 워터마크에 따라 윈도·타이머를 실행함
4. **스냅샷 저장**: 체크포인트 장벽이 통과하면 소스 위치와 연산자 상태를 영속 저장함
5. **결과 커밋**: 완료된 체크포인트와 연계해 트랜잭션 또는 멱등 싱크에 결과를 반영함

> 요약: Flink는 이벤트를 키별 상태에 반영하고 체크포인트가 완료되면 복구 가능한 상태와 싱크 결과를 확정함.

## Ⅵ. 실무 사례

1. 이상 거래 탐지는 계정별 상태·이벤트 시간 타이머를 적용하고 처리 지연·역압력 시간을 확인함
2. CDC 집계는 체크포인트와 트랜잭션 싱크를 적용하고 상태 크기·체크포인트 시간을 확인함

## Ⅶ. 결론

- Flink는 이벤트 시간 정확성·상태 크기·처리 지연·복구 보장과 싱크 커밋 방식을 기준으로 적용해야 함
