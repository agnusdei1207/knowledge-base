## 핵심 인사이트 (3줄 요약)
- Spark Streaming이 데이터를 0.5초씩 모아서 처리하는 '가짜 실시간(Micro-batch)' 방식의 한계에 부딪혔을 때, **1건의 데이터가 들어올 때마다 즉시 처리하는 '진짜 실시간(Native Streaming)'**의 정점을 찍은 분산 스트림 처리 엔진.
- 네트워크 지연 때문에 이벤트가 늦게 도착해도 꼬이지 않게 시간의 기준점을 잡아주는 **'워터마크(Watermark)'**와, 내부 메모리 상태를 완벽하게 디스크로 스냅샷 뜨는 **'체크포인트(Checkpoint)'** 기술이 압도적임.
- Uber, Netflix, 넷마블 등 0.001초의 지연(이상 거래 탐지, 실시간 게임 랭킹)도 허용하지 않으면서, 서버가 죽어도 데이터가 100% 1번만 처리됨(Exactly-once)을 보장해야 하는 극상위 티어 기업들의 표준 엔진임.
---
## Ⅰ. 개요 및 필요성
- **개요**: "모든 데이터는 무한히 흐르는 스트림이다"라는 철학 아래, 제한 없는 데이터 스트림(Unbounded)과 제한된 데이터 셋(Bounded, 배치)을 하나의 엔진으로 처리하는 상태 기반(Stateful) 프레임워크.
- **필요성**: Spark Streaming으로 실시간 처리를 했지만, 마이크로 배치의 한계 때문에 최소 지연 시간이 수백 밀리초에 달했음. 또한, 사용자가 밤 11시 59분에 핸드폰으로 결제했는데 산속이라 인터넷이 끊겨서 새벽 1시에 서버로 데이터가 도착했을 때, 이 결제액을 '어제' 매출로 잡아야 할지 '오늘' 매출로 잡아야 할지 통계가 다 꼬여버림(Event Time vs Processing Time). 이를 완벽히 해결할 차세대 엔진이 절실했음.
---
## Ⅱ. 아키텍처 및 핵심 원리
- **1. Native Streaming (이벤트 단위 처리)**:
  - 데이터가 뭉텅이로 모일 때까지 기다리지 않음. 이벤트 1개가 들어오면 1개 파이프라인을 통과하며 1밀리초(ms) 단위로 즉시 처리됨.
- **2. 워터마크(Watermark)와 시간의 통제**:
  - **이벤트 시간(Event Time)**: 데이터가 실제 폰에서 발생한 시간 (밤 11:59).
  - **처리 시간(Processing Time)**: 서버에 도착한 시간 (새벽 1:00).
  - Flink는 '워터마크'라는 기준선을 뒤로 졸졸 흘려보냄. "워터마크 11:59분이 지나갔으니, 이제 11시 대의 통계를 마감하고 화면에 보여줘라! 늦게 도착한 지각생 데이터는 특별한 방(Side Output)으로 빼라!"라고 지시하여 통계의 완벽한 정확성을 보장함.
- **3. 체크포인트 (Checkpointing)와 상태(State) 저장**:
  - "최근 1시간 평균 온도"를 구하려면 지난 59분간의 온도를 메모리(상태, State)에 들고 있어야 함.
  - Flink는 이 메모리 상태를 수 밀리초 단위로 분산 스토리지(S3, HDFS)에 비동기로 사진을 찰칵(스냅샷) 찍어둠. 서버가 죽어도 스냅샷을 불러와서 정확히 이어서 계산함 (Exactly-once 보장).

```text
[ Spark(Micro-batch)와 Flink(Native Stream)의 처리 방식 차이 ]

 📦 [ Spark Streaming (마이크로 배치) ]
 1초 동안 기다림 ➡️ "물방울(데이터) 100개 모였네? 한 컵(Batch) 원샷!" ➡️ 처리 (최소 1초 지연)
 
 💧 [ Apache Flink (네이티브 스트림) ]
 "물방울 하나 떨어지네? 바로 꿀꺽!" ➡️ "하나 더 떨어지네? 바로 꿀꺽!" ➡️ (지연 시간 0.001초!)
 
 🌊 [ Flink의 워터마크(지각생 처리) ]
 (10시 데이터) ➡️ (10시 5분 데이터) ➡️ 🚩 [10시 5분 워터마크 발송: "이제 10시 5분 이전 데이터 통계 마감해!"] ➡️ (뒤늦게 도착한 10시 3분 데이터) ➡️ "너는 지각이야! 마감됐으니 따로 모아둘게!" (통계 정확도 100% 보장)
```

## Ⅲ. 비교 및 연결
| 구분 | Apache Spark | Apache Flink |
|---|---|---|
| **처리 철학** | "스트리밍은 아주 잘게 쪼갠 배치(Batch)다" | **"배치(Batch)는 유한하게 끝이 있는 스트림일 뿐이다"** |
| **스트림 처리 방식**| Micro-batch (가짜 실시간) | **Native Streaming (진짜 실시간)** |
| **지연 시간 (Latency)**| 수백 밀리초 ~ 수 초 | **수 밀리초 (압도적 빠름)** |
| **주요 사용 사례** | 거대 데이터 배치 전처리, SQL 분석 | **이상 거래 탐지(FDS), 실시간 가격 책정(Uber), 카파 아키텍처** |
---
## Ⅳ. 실무 적용 및 기술사 판단
- **Kappa 아키텍처의 완성 (배치와 스트림의 통합)**: 과거 람다 아키텍처 시절, 개발자들은 하둡(배치)과 스톰(스트림) 두 가지 코드를 짜야 했음. Flink는 "스트리밍 코드 1개만 짜면, 평소엔 실시간 처리하고, 옛날 데이터는 Flink Batch 모드로 돌리면 된다!"는 꿈의 카파(Kappa) 아키텍처를 산업계에서 실제로 구현 가능하게 만든 주인공임.
- **상태 크기(State Size) 관리의 고통**: Flink 메모리(State)에 "최근 1주일 치 고객 클릭 정보"를 전부 쥐고 실시간 조인을 하려고 하면 메모리가 폭발함. 아키텍트는 내부 상태를 RocksDB로 빼서 디스크 기반으로 관리하도록 튜닝하고, Checkpoint 주기를 최적화하여 넷플릭스처럼 장애 복구 시에도 1원의 오차 없이 100% 재처리(Exactly-once)가 되도록 설계해야 함.
---
## Ⅴ. 기대효과 및 결론
- 데이터가 태어나는 그 찰나의 순간에 가치를 뽑아내는 '스트림 컴퓨팅'의 최종 진화형으로, 빅데이터 업계의 무게 중심을 배치(Spark)에서 실시간 스트림(Flink)으로 완전히 옮겨버렸음.
- 비즈니스의 대응 속도를 '내일 아침(배치)'에서 '지금 당장(실시간)'으로 바꾸어, 금융 사기를 즉각 차단하고 추천 알고리즘을 0.1초마다 갱신하는 리얼타임 비즈니스를 가능하게 한 IT 인프라의 마스터피스.
