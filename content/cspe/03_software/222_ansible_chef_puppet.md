## Ⅰ. 개요
- **정의**: 서버 구성 상태를 코드로 정의하고 자동 적용하는 구성관리(CM) 도구임
- **배경/필요성**: 서버 수가 수십~수천 대로 증가하면서 수작업 설정은 환경 편차와 장애 재현 불능을 초래함
- **비유**: 모든 교실에 같은 시간표(코드)를 배포하여 동일한 수업 환경을 보장하는 것과 유사함

| 출제 의도 | 반드시 짚을 핵심 | 감점 회피 포인트 |
|:---|:---|:---|
| CM 도구 간 아키텍처 차이 비교 | Agent 유무, Push/Pull 방식 구분 | IaC(221 참조)와 CM의 역할 차이 명시 필요 |

> 요약: 다수 서버의 구성 상태를 코드로 일관되게 유지하는 자동화 도구임

## Ⅱ. 구성요소
```text
+----------+    Push/Pull    +---------+
| Control  | -------------> | Managed |
| Node     |    SSH/Agent   | Node(s) |
+----------+                +---------+
      |
+-----+------+
| Playbook / |
| Recipe /   |
| Manifest   |
+------------+
```

| 구성요소 | 설명 | 비유 |
|:---|:---|:---|
| 제어 노드 | 구성 코드를 해석하고 대상 서버에 전달함 | 본사 관리팀 |
| 관리 대상 노드 | 구성이 적용되는 서버 집합임 | 각 지점 매장 |
| 구성 코드 | Playbook(YAML), Recipe(Ruby), Manifest(DSL)로 상태를 선언함 | 표준 운영 매뉴얼 |
| 통신 계층 | SSH(Ansible) 또는 Agent(Chef/Puppet)로 명령을 전달함 | 배송 수단 |

> 요약: 제어 노드가 구성 코드를 통신 계층으로 관리 대상에 적용하는 구조임

## Ⅲ. 절차
```text
정의 --> 검증 --> 적용 --> 수렴
```
- 1단계: 정의 — 원하는 서버 상태를 YAML/Ruby/DSL로 작성
- 2단계: 검증 — Dry-run(--check, why-run)으로 변경 영향을 사전 확인
- 3단계: 적용 — Push 또는 Pull 방식으로 대상 서버에 구성 반영
- 4단계: 수렴 — 주기적 실행으로 드리프트 발생 시 원래 상태로 자동 복원

> 요약: 정의-검증-적용-수렴 4단계로 멱등성 기반 상태 수렴을 달성함

## Ⅳ. 문제점
- 에이전트 관리 부담: Chef/Puppet은 각 노드에 Agent 설치·업데이트 필요 — 대규모 환경에서 운영 오버헤드 증가
- 학습 곡선: 도구별 DSL이 달라 팀 전환 시 재학습 비용 발생 — 조직 표준화 저해
- 컨테이너 환경 부적합: 불변 인프라(Immutable Infra) 패턴에서는 CM 적용 대상 자체가 소멸 — 역할 축소

> 요약: Agent 운영, 이질적 DSL, 컨테이너 전환이 주요 과제임

## Ⅴ. 개선방안
1. 단기: Agentless 방식(Ansible) 우선 도입으로 운영 부담 최소화
2. 중기: 도구 통합 또는 단일 표준 선정으로 DSL 파편화 해소
3. 장기: 컨테이너/K8s 환경에서는 이미지 빌드 파이프라인으로 CM 역할 전환

> 요약: Agentless 채택 → DSL 표준화 → 이미지 기반 불변 인프라 전환 순으로 대응

## Ⅵ. 전망
- 발전 방향: 컨테이너 중심 환경에서 CM은 베이스 이미지 구성 단계로 역할이 수렴함
- 기술사적 판단: VM 기반 레거시가 존재하는 한 CM 도구의 수요는 지속됨
- 기술사 제언: 인프라 유형(VM vs 컨테이너)에 따라 CM과 이미지 빌드를 병행 적용할 것을 권고함
