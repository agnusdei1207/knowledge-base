# 📖 【암기용】 개념 완전 이해

> 목적: 모델 모니터링과 드리프트 감지를 처음 보는 사람도 완벽히 이해하게 만든다. 시험 답안 양식이 아니라, 이해를 위한 친절한 설명이다.

## 한눈에
- **개요**: 모델 모니터링은 운영 중인 모델의 **입력·예측·정답 분포 변화(드리프트)**를 감시해 **모델 성능 저하(모델 부패, Model Decay)**를 조기에 탐지하는 활동이다.
- **왜 필요한가**: 정답(라벨)은 대출 부도 여부처럼 수개월 뒤에나 확정되는 경우가 많아, 라벨을 기다리면 이미 늦다. 그래서 라벨 없이도 조기 경보를 줄 수 있는 입력·예측 분포 변화부터 감시해야 한다.
- **핵심 직관**: 모델을 한 번 배포하고 끝내는 것이 아니라, 기계가 먹는 데이터와 내는 답이 변하는지 계속 건강검진을 하는 것이다.

## 핵심 용어 정리 (내부에 등장하는 것들)

| 용어 | 의미 | 비유 |
|:---|:---|:---|
| 모델 부패 (Model Decay, 상위 개념) | 시간이 지나며 운영 데이터가 학습 때와 달라져 모델 성능이 점점 떨어지는 현상 — 모니터링이 막으려는 대상 | 유통기한 지난 지도 |
| Data Drift | 입력 피처의 분포가 학습 시점과 달라지는 것 | 손님 연령대가 달라짐 |
| Concept Drift | 입력과 정답 사이의 관계 자체가 바뀌는 것 | 같은 증상인데 다른 병명 |
| Prediction Drift | 모델이 내놓는 예측값(확률) 분포가 변하는 것 | 판정 결과 비율이 변함 |
| PSI(Population Stability Index) | 두 시점의 분포 차이를 하나의 숫자로 요약하는 지표 | 체중 변화율 |
| KS 검정(Kolmogorov-Smirnov) | 두 분포가 통계적으로 같은지 검정하는 방법 | 두 그래프를 겹쳐 최대 차이를 재는 것 |
| Label(정답) 지연 | 실제 정답이 예측 시점보다 한참 뒤에 확정되는 것 | 시험 채점 결과가 몇 달 뒤에 나옴 |

## 깊이 이해

### 왜 배포 후에도 감시해야 하나 — 라벨 지연 문제
분류 모델의 진짜 성능(F1, AUC)을 알려면 정답(라벨)이 필요하다. 그런데 신용평가 모델의 "부도 여부"는 대출 실행 후 수개월~1년 뒤에나 확정된다. 그 사이 모델이 나쁜 예측을 계속 내놓아도 아무도 모른다. 그래서 라벨을 기다리지 않고도 낼 수 있는 신호, 즉 입력 피처 분포(Data Drift)와 예측값 분포(Prediction Drift)를 먼저 감시한다.

### PSI로 드리프트를 수치화하는 법 — 워크드 예제
PSI는 기준 시점(학습 데이터)과 비교 시점(운영 데이터)의 구간별 비율 차이를 합산한다. 공식: PSI = Σ (비교비율 − 기준비율) × ln(비교비율 / 기준비율). 예: `income` 피처를 구간으로 나눴을 때 학습 시점에는 저소득 구간이 20%였는데 운영 시점에는 35%로 늘었다면, 이 구간에서만 (0.35−0.20) × ln(0.35/0.20) ≈ 0.15 × 0.56 ≈ 0.084가 나온다. 모든 구간을 합산해 전체 PSI가 0.25를 넘으면 "심각한 드리프트"로 판정해 재학습 후보에 올린다. 판정 기준(경험칙): PSI < 0.1 안정, 0.1~0.25 경미(관찰), 0.25 초과 심각(조치 필요).

### Data Drift와 Concept Drift 구분 — 대응이 다르다
Data Drift는 입력 분포만 변하고 입력-정답 관계는 그대로인 경우다(예: 겨울이라 난방기기 구매 문의가 늘어남 — 피처 분포는 변했지만 "문의 패턴과 구매 여부"의 관계는 동일). 이때는 재학습만으로 충분할 수 있다. 반면 Concept Drift는 관계 자체가 바뀐 것이다(예: 팬데믹 이후 "재택근무 신청"과 "생산성" 사이의 관계가 이전과 달라짐). 이 경우 재학습뿐 아니라 피처 설계 자체를 재검토해야 한다. 두 드리프트를 구분하지 않고 무조건 재학습만 반복하면 근본 원인(피처 설계 오류)을 놓친다.

### 오탐(False Alert)을 줄이는 판별 원리
계절성(매년 12월 쇼핑 급증)이나 이벤트(프로모션)로 인한 일시적 분포 변화를 드리프트로 오판하면 불필요한 재학습이 반복된다. 그래서 기준 window를 계절성에 맞춰 분리하고(작년 12월 vs 올해 12월), 표본 수가 너무 작을 때(예: 신규 트래픽 100건 미만)는 통계적 유의성이 없으므로 경보를 보류하는 최소 표본 수 규칙을 둔다.

### 대응 절차 — 경보가 곧 재학습은 아니다
드리프트 경보가 뜨면 곧바로 재학습하지 않고 ① 데이터 파이프라인 오류(예: 특정 소스가 결측치로 채워짐) ② 업무 정책 변경(예: 승인 기준 자체가 바뀜) ③ 실제 라벨 기반 성능 저하를 순서대로 확인한다. 라벨 지표(F1이 5%p 이상 하락)까지 확인된 경우에만 재학습을 확정한다.

## 연결 개념
- 모델 부패(상위 개념)
- 피처 스토어(253) — Feature Monitor가 감시하는 피처 값의 출처
- 카나리 모델 배포(257) — 신규 모델 배포 단계에서도 같은 지표(p95, 오류율)로 감시

# 📝 【답안용】 시험 답안 템플릿

> 목적: 시험장에서 25분에 그대로 쓰는 답안 양식. 작성방식(추상표현 금지·수치·도식·문제유형 전환)을 엄격히 지킨다.
> 핵심: 모델 모니터링 답안은 서비스 지표와 모델 지표를 분리하고, 드리프트 감지 후 재학습 판단까지 연결해야 한다.

## 핵심 인사이트 (3줄 요약)

> 1. **본질**: 모델 모니터링은 운영 중 입력·예측·정답·시스템 지표를 수집해 모델 부패와 장애를 탐지하는 활동이다.
> 2. **가치**: 라벨 지연 환경에서도 PSI, KS, 예측 분포 변화로 품질 저하 가능성을 조기 발견한다.
> 3. **판단 포인트**: 드리프트 경보를 재학습으로 바로 연결하지 말고 데이터 오류, 정책 변경, 라벨 지표를 함께 검증해야 한다.

## 출제 의도 및 답안 포인트

| 출제 의도 | 반드시 짚을 핵심 | 감점 회피 포인트 |
|:---|:---|:---|
| 모델 운영 감시 이해 | data drift, concept drift, prediction drift | 서버 모니터링만 설명 |

> 요약: 이 문제는 모델 품질 감시와 서비스 관측성을 분리해 재학습 판단까지 연결하는 역량을 본다.

## Ⅰ. 개요 및 필요성

- 개요: 모델 모니터링은 운영 모델 품질 감시 체계다.
- 배경: 배포 후 데이터 분포, 사용자 행동, 업무 정책이 변하면 예측 품질이 목표 기준 아래로 내려갈 수 있다.
- 필요성: 드리프트 지표와 라벨 기반 평가로 재학습·롤백 시점을 판단해야 한다.

---

## Ⅱ. 구조 및 구성요소

```text
Serving Log -> Feature Monitor -> Prediction Monitor -> Label Monitor -> Alert -> Root Cause -> Retraining
                         / System Metrics
                         / Drift Report
```

| 구성요소 | 역할 | 지표 예시 |
|:---|:---|:---|
| Feature Monitor | 입력 피처 분포 변화 감시 | PSI, KS, null rate |
| Prediction Monitor | 예측값과 확률 분포 감시 | approval rate, score shift |
| Label Monitor | 실제 정답 도착 후 품질 측정 | F1, AUC, RMSE |
| System Monitor | 서빙 지연과 오류 감시 | p95, 5xx, timeout |

> 요약: 모델 모니터링은 피처, 예측, 라벨, 시스템 지표를 분리해 원인을 좁힌다.

---

## Ⅲ. 동작원리 및 흐름도

```text
로그 수집 -> 기준 분포와 비교 -> 임계값 평가 -> 경보 생성 -> 원인 분석 -> 재학습/롤백 결정
```

| 단계 | 처리 내용 | 검증 기준 |
|:---:|:---|:---|
| 1 | 학습 기준 분포와 운영 로그 수집 | 기준 window 고정 |
| 2 | 피처와 예측 분포 비교 | PSI 0.2, KS p-value |
| 3 | 라벨 도착 후 품질 지표 산출 | F1 5%p 하락 |
| 4 | 원인 분석 후 조치 선택 | 재학습, 롤백, 데이터 수정 |

> 요약: 드리프트 감지는 기준 분포와 운영 분포를 비교하고 라벨 품질로 재학습 여부를 확정한다.

## Ⅴ. 심화 비교 및 적용 판단

| 구분 | 기존/대안 | 모델 모니터링 | 선택 기준 |
|:---|:---|:---|:---|
| 구조 | 배포 후 지표 확인 없음 | 온라인 로그와 기준 분포 비교 | 운영 의사결정 모델 |
| 비용/성능 | 저장 비용 낮음 | 로그 저장과 통계 계산 필요 | 라벨 지연 1일 이상 |
| 운영/위험 | 품질 저하 사후 발견 | 조기 경보와 재학습 절차 | 고객 영향 큰 모델 |

> 요약: 운영 결과가 업무 판단에 영향을 주면 모델 모니터링을 적용하고, 단순 배치 분석은 정기 평가로 시작한다.

| 리스크 | 원인 | 대응 방안 | 확인 지표 |
|:---|:---|:---|:---|
| 오탐 경보 | 계절성, 이벤트, 표본 수 부족 | 기준 window 분리, 최소 표본 수 | false alert rate |
| 라벨 지연 | 정답 도착이 늦음 | proxy metric, delayed label join | label latency |
| 개인정보 노출 | 추론 로그 원문 저장 | 마스킹, 샘플링, 접근통제 | PII 검출 0건 |

> 요약: 모니터링 리스크는 오탐, 라벨 지연, 로그 민감정보이며 기준 window와 마스킹으로 통제한다.

| 점검 항목 | 목표 기준 | 측정 방법 |
|:---|:---|:---|
| 드리프트 | PSI 0.2 미만 유지 | Evidently, WhyLabs |
| 모델 품질 | F1 하락 5%p 이내 | 라벨 조인 평가 |
| 서비스 지표 | p95 100ms, 오류율 0.1% 이하 | APM, 서빙 로그 |

> 요약: 모델 모니터링은 드리프트, 라벨 품질, 서비스 지표가 모두 기준 안에 있는지 확인한다.

## Ⅵ. 실무 적용 및 결론

**적용 방안 3개:**
1. 서빙 로그에 feature vector, prediction, model version, request id를 남기고 PII는 SHA-256 해시 또는 마스킹 처리함
2. Evidently 또는 WhyLabs로 PSI 0.2 이상, F1 5%p 하락, p95 100ms 초과 알림을 구성함
3. 경보 발생 시 데이터 수집 오류, 정책 변경, 라벨 품질을 점검한 뒤 재학습 또는 롤백을 실행함

**결론 (2줄):**
- 기술사 판단: 라벨이 지연되는 운영 모델은 드리프트 지표로 조기 경보를 만들고, 라벨 지표로 재학습을 확정함
- 향후 방향: 모델 모니터링은 피처 스토어, 모델 레지스트리, 자동 재학습과 연결되어 폐루프 MLOps로 발전함
