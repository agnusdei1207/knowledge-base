# 📖 【암기용】 개념 완전 이해

> 목적: REST API 보안을 처음 봐도 인증·인가·채널 보호의 차이를 이해하게 만든다. 시험 답안 양식이 아니라, 이해를 위한 설명이다.

## 한눈에
- **개요**: REST API 보안은 **무상태(Stateless)** 요청마다 호출 주체를 **인증(Authentication)**하고 권한을 **인가(Authorization)**하며 전송 구간을 암호화하는 통제 체계다.
- **왜 필요한가**: REST는 매 요청이 독립적이라 서버가 이전 요청을 기억하지 못한다. 그래서 세션 쿠키 하나로 때우던 방식과 달리, 모바일·SPA·파트너·내부 서비스가 같은 엔드포인트를 호출할 때마다 "누구인지·무엇을 할 수 있는지"를 매번 새로 증명해야 하며, 이 증명이 뚫리면 즉시 데이터 노출로 이어진다.
- **핵심 직관**: API Key는 출입증 번호(신분 대조 없이 카드 번호만 확인), OAuth는 역할이 적힌 임시 허가증(위임된 권한만 확인), mTLS는 양쪽이 서로 신분증을 맞대고 확인하는 전용 통로다.

## 핵심 용어 정리 (내부에 등장하는 것들)

| 용어 | 의미 | 비유 |
|:---|:---|:---|
| 인증(Authentication) | 호출자가 누구/무엇인지 확인 | 카드 리더기가 카드 번호를 읽음 |
| 인가(Authorization) | 인증된 주체가 무엇을 할 수 있는지 결정 | 카드로 열 수 있는 문이 정해져 있음 |
| 무상태(Stateless) | 서버가 이전 요청 상태를 기억하지 않는 REST의 원칙 — 매 요청에 인증 정보를 다시 실어야 함 | 매번 새로 신분증을 보여줘야 하는 창구 |
| API Key | 애플리케이션(사용자 아님)을 식별하는 고정 문자열 — 호출량 제어 기준 | 출입증에 새겨진 카드 번호 |
| OAuth 2.0 | 사용자가 자신의 권한 일부를 제3자 앱에 위임하는 프레임워크 | "이 앱에게만 내 사진첩 읽기를 허락합니다" 동의서 |
| Authorization Code Grant | OAuth 2.0에서 사용자 동의를 거쳐 인증 서버가 코드를 발급하고, 그 코드를 다시 토큰으로 교환하는 절차 | 방문 신청서를 접수처에 냈다가 정식 출입증으로 바꿔 받는 절차 |
| PKCE (Proof Key for Code Exchange) | Authorization Code를 가로채도 토큰으로 못 바꾸게 막는 추가 검증(code_verifier/code_challenge 쌍) | 접수증을 훔쳐도, 접수 당시 준 비밀 번호를 모르면 출입증으로 못 바꿈 |
| Access Token | 인가된 권한 범위 내에서 API를 호출할 수 있는 짧은 수명의 토큰 | 임시 방문증(유효시간 짧음) |
| Refresh Token | Access Token이 만료되면 재발급받는 데 쓰는 장기 토큰 | 방문증 재발급 신청서 |
| Scope | 토큰이 허용하는 권한 범위(예: `order:read`) | 출입 가능 구역 표시 |
| mTLS (mutual TLS) | TLS 핸드셰이크에서 서버뿐 아니라 클라이언트도 인증서로 신원을 증명하는 방식 | 양쪽이 서로 신분증을 맞대고 확인 |
| Rate Limiting | 단위 시간당 허용 요청 수를 제한하는 통제 | 회전문 초당 통과 인원 제한 |
| HMAC 서명 | 공유 비밀키로 요청 내용의 해시를 생성해 위변조를 검증하는 방식 | 봉투에 찍는 밀랍 인장 |

## 깊이 이해

### 인증 수단별 "무엇을 증명하는가"의 차이
- API Key는 **애플리케이션 식별**만 한다. 사용자가 누구인지는 전혀 모른다 — 그래서 "API Key가 있으니 인증됐다"는 말은 반은 틀렸다. 사용자 신원과 권한까지 필요하면 OAuth가 있어야 한다.
- OAuth 2.0/OIDC는 **위임된 사용자 권한**을 Access Token에 담는다. 토큰 안의 scope가 "이 앱이 사용자를 대신해 무엇을 할 수 있는지"를 정의한다.
- mTLS는 **통신 채널 양쪽의 신원**을 증명한다. 인증서가 곧 신원이므로, 서버 간 고신뢰 호출(내부 서비스, 파트너 서버)에서 "이 연결 자체가 승인된 상대와만 맺어졌는가"를 보장한다.

### PKCE를 실제 값으로 이해하기
- 절차: 클라이언트가 임의의 랜덤 문자열 `code_verifier`(예: `dBjftJeZ4CVP-mB92K27uhbUJU1p1r_wW1gFWFOEjXk`, 43~128자)를 만들고, 이를 SHA-256 해시한 뒤 Base64URL 인코딩해 `code_challenge`를 계산한다.
- 인증 요청 시에는 `code_challenge`만 서버에 보낸다(원본 `code_verifier`는 클라이언트에만 보관). 서버는 Authorization Code와 함께 이 `code_challenge`를 저장해둔다.
- 토큰 교환 시 클라이언트가 원본 `code_verifier`를 제출하면, 서버가 같은 해시 연산을 다시 수행해 저장해둔 `code_challenge`와 일치하는지 검증한다.
- **왜 필요한가**: Authorization Code는 리다이렉트 URL을 통해 전달되므로 모바일 앱·SPA 환경에서 악성 앱이 가로챌 위험이 있다. code만 훔쳐도 `code_verifier`(클라이언트만 아는 값)가 없으면 토큰으로 교환할 수 없어, 탈취된 code가 무력화된다.

### mTLS 핸드셰이크를 단계로 이해하기
- 일반 TLS는 서버만 인증서를 제시하지만, mTLS는 클라이언트도 인증서를 제시한다. 순서: ① ClientHello(클라이언트가 지원 암호 스위트 제시) ② ServerHello + 서버 인증서 ③ **CertificateRequest**(서버가 클라이언트에게 인증서를 요구 — 일반 TLS와 다른 지점) ④ 클라이언트가 자신의 인증서 제출 ⑤ 클라이언트가 개인키로 서명해 소유 증명 ⑥ 서버가 클라이언트 인증서의 CN/SAN, 유효기간, CRL/OCSP(폐기 여부)를 검증 ⑦ 세션 키 협상 완료.
- 이 중 ③~⑥이 mTLS를 일반 TLS와 구분 짓는 핵심이다 — 서버가 "이 클라이언트가 우리가 발급한 인증서를 가진 신뢰된 상대"임을 연결 수립 시점에 확인한다.

### 만료 시간과 호출량을 숫자로 감 잡기
- Access Token 만료 5~15분: 10분(600초)으로 잡으면, 토큰이 탈취돼도 공격자가 악용할 수 있는 창(window)은 최대 600초로 제한된다. 만료를 1시간으로 늘리면 탈취 시 악용 가능 시간이 6배로 늘어난다.
- Rate Limiting 1,000 RPM(분당 요청): 초당으로 환산하면 1000/60 ≈ 초당 16.7건이다. 이 한도를 넘는 호출은 429(Too Many Requests)로 거부해, 무차별 대입이나 스크래핑성 트래픽이 정상 트래픽을 밀어내는 것을 막는다.
- 인증서 유효기간 397일 이하: TLS 서버 인증서 표준 상한이며, 만료 30일 전 알림을 걸어야 갱신 누락으로 인한 서비스 중단(만료된 인증서로 핸드셰이크 자체가 실패)을 막을 수 있다.

### 비유와 흔한 오해
- **비유**: 건물 출입에서 카드 번호는 API Key(누구 회사 카드인지만 앎), 임시 방문증은 OAuth 토큰(발급 시 정한 구역만 출입 가능), 신분증 대조와 전용 통로는 mTLS(양쪽 다 신원 확인)에 해당한다.
- **오해 1**: "TLS만 쓰면 API 보안이 끝난다"는 틀렸다. TLS는 전송 구간 도청만 막을 뿐, 호출 주체가 정당한지·권한이 맞는지는 별도로 인증·인가 계층이 검증해야 한다.
- **오해 2**: API Key를 사용자 인증으로 착각하면 안 된다. API Key가 유출되면 "그 앱인 척"까지만 가능해 보이지만, 애초에 사용자 구분이 없으므로 유출 즉시 해당 앱 권한 전체가 노출된 것과 같다.

## 연결 개념
- API Gateway: 인증·인가·Rate Limit을 중앙에서 집행하는 정책 실행 지점
- OAuth 2.0/OIDC: 위임 권한과 사용자 인증 정보를 분리하는 상위 프레임워크
- Zero Trust: 네트워크 위치보다 주체·기기·권한을 매 요청 검증하는 상위 보안 모델

# 📝 【답안용】 시험 답안 템플릿

> 목적: 시험장에서 25분에 그대로 쓰는 답안 양식. API 보안은 인증 수단 나열이 아니라 호출 주체, 권한 범위, 전송 채널, 감사 추적을 연결해 답안을 구성한다.

## 핵심 인사이트 (3줄 요약)

> 1. **본질**: REST API 보안은 API Key, OAuth 2.0/OIDC, mTLS, Rate Limit, 감사 로그로 호출 주체와 권한을 매 요청 검증하는 통제 구조이다.
> 2. **가치**: 무상태 API에서 키 유출, 토큰 탈취, 권한 초과 호출, 중간자 공격을 인증·인가·암호화·탐지 계층으로 분리 통제한다.
> 3. **판단 포인트**: 외부 파트너는 API Key+mTLS, 사용자 위임은 OAuth/OIDC, 내부 서비스 간 호출은 mTLS+JWT audience 검증 조합을 선택한다.

## 출제 의도 및 답안 포인트

| 출제 의도 | 반드시 짚을 핵심 | 감점 회피 포인트 |
|:---|:---|:---|
| REST API 공격면 이해 확인 | 인증, 인가, 전송 보호, Rate Limit, 감사 로그 | API Key를 사용자 인증으로 단정 |
| OAuth·mTLS 적용 판단 확인 | Token 만료, Scope, Audience, Client Certificate 검증 | TLS만 쓰면 API 보안이 끝난다고 서술 |
| 운영 통제 역량 확인 | 키 회전, 토큰 폐기, 429 제어, SIEM 연계 | 비밀값 저장소와 로그 마스킹 누락 |

> 요약: REST API 보안 답안은 수단별 역할을 분리하고, 요청 단위 검증과 운영 지표를 함께 제시해야 한다.

## Ⅰ. 개요 및 필요성

- 개요: API 호출의 신원·권한·채널 통제
- 배경: 공개 API, 모바일 앱, MSA 내부 호출은 HTTP 기반으로 노출되어 인증 실패가 데이터 유출로 이어짐
- 필요성: 무상태 요청마다 OAuth 2.0/OIDC, TLS, Rate Limit로 주체·권한·호출량을 검증해야 함

---

## Ⅱ. 구조 및 구성요소

```text
Client -> API Gateway -> Auth Server -> Resource Server -> Audit Log
  / API Key 검증
  / OAuth Token 검증
  / mTLS Client Cert 검증
```

| 구성요소 | 역할 | 특이사항 |
|:---|:---|:---|
| API Key | 앱·파트너 식별, Rate Limit 기준 | 사용자 권한 증명 아님, 90일 회전 |
| OAuth/OIDC | 사용자 위임 권한, Scope·Audience 검증 | Access Token 5~15분 만료 |
| mTLS | 서버·클라이언트 상호 인증 | 인증서 CN/SAN, 지문, CRL/OCSP 확인 |
| API Gateway | 인증 전처리, WAF, 429 제어 | 정책 일관성·로그 수집 지점 |

> 요약: API Key는 식별, OAuth는 권한 위임, mTLS는 채널 신뢰를 담당하며 Gateway가 정책 집행 지점이다.

---

## Ⅲ. 동작원리 및 흐름도

```text
Request 수신 -> TLS/mTLS 검증 -> Key/Token 검증 -> Scope 판단 -> Service 호출 -> Log 저장
```

| 단계 | 처리 내용 | 검증 기준 |
|:---:|:---|:---|
| 1 | TLS 또는 mTLS 핸드셰이크 | TLS 1.2 이상, 인증서 만료·폐기 확인 |
| 2 | API Key 또는 JWT 파싱 | 서명, issuer, audience, exp 검증 |
| 3 | 인가 정책 평가 | HTTP Method, URL, scope 매핑 |
| 4 | 호출량·위협 제어 | 429, IP reputation, WAF rule |
| 5 | 감사 로그 저장 | Trace ID, subject, status, latency 기록 |

> 요약: 요청은 채널 검증, 신원 확인, 권한 평가, 호출량 통제, 감사 기록 순서로 처리된다.

## Ⅴ. 심화 비교 및 적용 판단

| 구분 | 기존/대안 | 본 키워드 | 선택 기준 |
|:---|:---|:---|:---|
| 외부 연동 | API Key 단독 | API Key+mTLS | 파트너 서버 고정, B2B 계약 |
| 사용자 위임 | ID/PW 전달 | OAuth 2.0 Authorization Code+PKCE | 모바일·SPA 사용자 권한 위임 |
| 내부 호출 | 네트워크 ACL | mTLS+JWT audience | Zero Trust, 서비스 메시 |

> 요약: API 보안 수단은 하나를 고르는 문제가 아니라 호출 주체와 위임 여부에 따라 조합하는 문제이다.

| 리스크 | 원인 | 대응 방안 | 확인 지표 |
|:---|:---|:---|:---|
| 키 유출 | 소스 저장소·로그 노출 | Secret Manager, 키 회전, 로그 마스킹 | 노출 키 0건, 회전 준수율 100% |
| 토큰 탈취 | XSS, 저장소 평문 보관 | PKCE, HttpOnly, 짧은 exp, refresh 회전 | 재사용 탐지 건수 |
| 권한 초과 | Scope 설계 누락 | Endpoint-scope 매핑표, ABAC | 403 비율, 정책 테스트 통과율 |

> 요약: 핵심 리스크는 비밀값 노출과 과권한이며, 회전·마스킹·정책 테스트로 통제한다.

| 점검 항목 | 목표 기준 | 측정 방법 |
|:---|:---|:---|
| 인증 실패 | 401/403 원인별 추적 | Gateway 로그, SIEM |
| 호출량 제어 | 429 정책, 초당 요청 한도 | Rate Limit 대시보드 |
| 암호화·인증서 | TLS 1.2 이상, 만료 30일 전 알림 | 인증서 스캐너, OCSP 로그 |

> 요약: 도입 후에는 인증 실패 원인, 호출량, 인증서 상태를 운영 지표로 관리한다.

## Ⅵ. 실무 적용 및 결론

**적용 방안 3개 (필수):**
1. 외부 공개 API는 API Gateway에서 API Key, JWT 서명, Rate Limit 1,000 RPM, WAF OWASP CRS를 일괄 적용함.
2. 사용자 위임 API는 OAuth 2.0 Authorization Code+PKCE, Access Token 10분, Refresh Token 회전, scope 최소화를 적용함.
3. 파트너·내부 서비스 API는 mTLS, 인증서 자동 갱신, SPIFFE ID 또는 SAN 매핑, 감사 로그 1년 보관을 적용함.

**결론 (2줄):**
- 기술사 판단: 단순 식별이면 API Key, 사용자 위임이면 OAuth/OIDC, 서버 간 고신뢰 호출이면 mTLS를 조합함.
- 향후 방향: API 보안은 Gateway 중심에서 서비스 메시, Zero Trust, 정책 코드화(OPA) 기반으로 확장됨.
