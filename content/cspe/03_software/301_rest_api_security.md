## 핵심 인사이트 (3줄 요약)
- 클라이언트가 서버의 REST API를 호출할 때 "나쁜 놈이 막 찔러보는 건 아닐까? 도청당하지는 않을까?"를 막기 위해, 용도와 깐깐함의 정도에 따라 **3단계의 방패(보안 체계)**를 둘러치는 설계 기법.
- **API Key**가 동네 헬스장 바코드(가장 단순, 털리기 쉬움)라면, **OAuth 2.0**은 호텔 키 카드(권한을 세밀하게 통제하고 시간 지나면 만료됨)이고, **mTLS**는 청와대 신원 확인(너도 신분증 까고 나도 신분증 까는 극강의 양방향 인증)임.
- 금융/오픈뱅킹 시대에 이 3가지는 하나만 고르는 게 아니라, 상황에 맞게 섞어 쓰는(Defense in Depth) 클라우드 아키텍처의 필수 무기임.

## Ⅰ. 개요 및 필요성
- **개요**: 분산된 RESTful 웹 서비스 환경에서 자원을 보호하고 무결성, 기밀성, 가용성을 보장하기 위해 클라이언트와 서버 간의 인증(Authentication), 인가(Authorization), 암호화를 구현하는 기술.
- **필요성**: 은행에서 잔액을 조회하는 `/api/balance`를 열어둠. 1) 아무나 와서 호출하면 돈 털림 (인증 필요). 2) 로그인했더라도 A가 B의 계좌를 볼 수 있으면 안 됨 (권한 인가 필요). 3) 통신하는 중간에 와이파이 공유기에서 해커가 데이터를 가로채면 털림 (암호화 필요). **"REST API는 태생적으로 뻥 뚫린(Stateless) 문인데, 누가 어떻게 이 문을 열게 할지 규격화된 자물쇠 3형제 없어?"**
---
## Ⅱ. 3대 API 자물쇠 (핵심 아키텍처)

### 1. API Key (단순 식별 번호)
- **방식**: 클라이언트에게 발급된 난수 문자열(`x-api-key: d8f3...`)을 HTTP 헤더에 담아 보냄.
- **특징**: "너 네이버 날씨 앱 맞지?" 정도의 단순 신원 확인용.
- **한계**: 암호화되지 않고 평문으로 날아가므로 탈취에 극히 취약함. 개인정보가 없는 공공 데이터(날씨, 지도 API) 호출 등에만 제한적으로 씀.

### 2. OAuth 2.0 (권한 위임 및 인가)
- **방식**: 비밀번호를 직접 주지 않고, 권한을 증명하는 '접근 토큰(Access Token - 주로 JWT)'을 주고받음.
- **특징**: 사용자가 서드파티 앱(예: 구글 로그인)에 "내 프로필만 읽을 수 있게 허락해 줘"라고 세밀한 '권한(Scope)'을 쪼개서 허락할 수 있음. 토큰은 수명이 짧아 탈취당해도 타격이 적음. B2C 서비스 API 보안의 제왕.

### 3. mTLS (Mutual TLS, 상호 인증) - 끝판왕
- **방식**: 일반적인 HTTPS(TLS)는 브라우저만 서버를 의심해서 서버의 인증서를 검사함(단방향). **mTLS**는 서버도 클라이언트를 못 믿어서, "너도 네 인증서 내놔봐!"라며 **클라이언트와 서버가 서로(양방향) 신분증을 까고 확인**한 뒤에만 통신을 시작함.
- **특징**: 기계 대 기계(M2M) 통신이나, 마이크로서비스 간(K8s) 통신의 절대 규격. 해커가 토큰을 훔쳤더라도, 해커 PC에는 '합법적인 인증서'가 없으므로 API 호출 자체가 거부됨 (Zero Trust 완성).

```text
[ 상황별 최적의 API 자물쇠 선택 가이드 ]

 🌤️ [ 공공 데이터 (날씨, 지도) ]
 ➡️ **API Key**. 털려도 날씨 정보 좀 빼가는 것뿐. 트래픽 과금(Rate Limit) 용도로만 씀.

 👤 [ 유저 데이터 (구글 로그인, 인스타그램 앱) ]
 ➡️ **OAuth 2.0 (JWT 토큰)**. 유저의 권한을 세밀하게 제어하고 모바일 환경에 최적화됨.

 🏦 [ 금융권 / 내부 MSA 통신 (계좌 송금 봇 ➡️ DB 서버) ]
 ➡️ **mTLS**. 토큰이고 나발이고, 해커가 와이파이 중간에서 패킷 자체를 못 건드리게 물리적 암호화 터널부터 뚫어버림.
```

## Ⅲ. 오해와 진실
| 오해 | 진실 |
|---|---|
| "우린 OAuth 2.0 토큰으로 암호화하니까 털릴 일 없죠!" | **OAuth 토큰은 암호화가 아님.** 토큰 자체는 Base64로 인코딩된 평문임. 중간에 탈취당하면 해커가 그대로 API를 찔러서 악용할 수 있음. 따라서 **반드시 HTTPS(TLS) 보안 채널 위에서만** 토큰을 날려야 안전함. |
| "mTLS는 완벽하니까 다 mTLS로 도배하자!" | 브라우저를 쓰는 일반 유저 수백만 명에게 인증서를 깔라고 할 수는 없음. mTLS는 유저-서버 구간(B2C)이 아니라, 우리 회사 내부 서버-서버 구간(Backend-to-Backend) 통신을 보호할 때 사용하는 것이 정석임. |
---
## Ⅳ. 실무 적용 및 기술사 판단
- **Service Mesh를 통한 mTLS 자동화**: 수백 개의 마이크로서비스(MSA)가 통신할 때 개발자가 일일이 mTLS 인증서를 갱신하고 코딩하는 것은 지옥임. 기술사는 K8s 환경에 **Istio 같은 서비스 메시(Service Mesh)**를 도입하여, 소스 코드 수정 없이 사이드카(Sidecar) 프록시 간에 자동으로 인증서를 발급·갱신하고 100% mTLS 통신을 강제하는 '투명한 네트워크 보안'을 설계해야 함.
- **API Gateway 기반의 다층 보안 설계**: 외부에 노출되는 엔드포인트는 **API Gateway**가 1차 관문이 되어야 함. 기술사는 이 게이트웨이에서 단순 DDos를 막고, API Key의 초당 호출 제한(Rate Limiting)을 체크하며, OIDC(OAuth) 토큰의 유효성을 1차 검증(Offloading)하여, 통과한 깨끗한 트래픽만 내부 망으로 흘려보내는 방파제 아키텍처를 구축해야 함.
---
## Ⅴ. 기대효과 및 결론
- "열려있는 창문"과 같은 REST API를, 비즈니스 성격과 데이터 민감도에 맞춰 적절한 무게의 철조망(Key ➡️ OAuth ➡️ mTLS)으로 감싸 안전한 API 경제(API Economy) 생태계를 구축함.
- 아무도 믿지 않고 모든 통신을 검증한다는 클라우드 네이티브의 **'제로 트러스트(Zero Trust)' 철학을 코드가 아닌 인프라 레벨에서 기술적으로 실현**하는 코어 메커니즘임.

### 📈 관련 키워드 및 발전 흐름도
- 옛날 Basic Auth (비밀번호를 통째로 보냄, 최악) ➡️ 개발자 편의를 위한 단순 식별자 **API Key** 도입 ➡️ 비밀번호를 서드파티에 넘기지 않기 위해 **OAuth 2.0** 표준 제정 ➡️ REST API가 MSA 환경의 내부 통신까지 장악함 ➡️ 내부 통신도 해커가 훔쳐볼 수 있다는 공포에, 기계 간 양방향 신분 검증인 **mTLS**와 Service Mesh가 클라우드 보안의 표준으로 등극 (현재)

### 👶 어린이를 위한 3줄 비유 설명
1. **API Key**는 놀이공원 '입장권'이에요. 잃어버리면 남이 주워서 쓸 수 있지만, 놀이기구 타는 데는 편해요.
2. **OAuth 2.0**은 손목에 차는 '자유이용권 팔찌'예요. 나에게만 딱 맞는 권한(예: 롤러코스터만 탑승 가능)이 적혀있고, 하루가 지나면 종이가 찢어져서 버려져요.
3. **mTLS**는 '비밀 기지'에 들어갈 때, 경비원도 내 얼굴을 확인하고 **나도 경비원 명찰을 확인**하는 진짜 깐깐한 쌍방향 비밀 요원 검사랍니다!

### 🔀 문제 유형별 목차 전환 (이 키워드 출제 시)
- **개념/비교형 (Ⅱ·Ⅲ 강조)**: 3가지 보안 기술의 인증 주체 및 강도 비교. API Key(식별, 통계용), OAuth 2.0(권한 위임, B2C 인가), mTLS(인증서 기반 양방향 암호화 통신, M2M)의 작동 메커니즘 도식화.
- **MSA 보안/아키텍처형 (Ⅳ·Ⅴ 강조)**: 제로 트러스트(Zero Trust) 관점에서의 방어 심도(Defense in Depth) 설계. 외곽망(North-South)은 API Gateway의 OAuth 통제, 내부망(East-West)은 Service Mesh(Istio)를 통한 무중단 mTLS 적용 전략 제시.
