## Ⅰ. 개요
- **정의**: REST API의 인증·인가·전송 보호를 통해 무단 접근과 데이터 유출을 방지하는 보안 체계임
- **배경/필요성**: API가 시스템 간 통신의 표준이 되면서 공격 표면이 확대되어 체계적 보안이 필요함
- **비유**: API 보안은 건물의 출입증(인증) + 층별 권한 카드(인가) + CCTV(모니터링)와 같음

| 출제 의도 | 반드시 짚을 핵심 | 감점 회피 포인트 |
|:---|:---|:---|
| API 보안 위협과 대응 체계 이해 | 인증·인가·전송 암호화 3요소 | OAuth와 API Key 차이 혼동 주의 |

> 요약: REST API 보안은 인증·인가·전송 보호의 3계층으로 무단 접근을 차단하는 체계임

## Ⅱ. 구성요소
```text
Client --> [API Gateway] --> [Auth Server] --> [Resource Server]
              |                   |                  |
         Rate Limit          Token 발급         접근 제어
         TLS 종단            Scope 관리         입력 검증
```

| 구성요소 | 설명 | 비유 |
|:---|:---|:---|
| 인증(Authentication) | OAuth 2.0, JWT 등으로 요청자 신원을 확인함 | 건물 출입증 확인 |
| 인가(Authorization) | Scope·Role 기반으로 자원 접근 권한을 통제함 | 층별 출입 카드 |
| 전송 보호(TLS) | HTTPS를 통해 전송 구간 데이터를 암호화함 | 밀봉 봉투로 전달 |
| Rate Limiting | 단위 시간당 요청 수를 제한하여 남용을 방지함 | 1인 1매 구매 제한 |
| 입력 검증 | 요청 파라미터의 형식·범위를 검증하여 인젝션을 차단함 | 소지품 검사 |

> 요약: 인증·인가·전송 보호·속도 제한·입력 검증의 5개 구성요소가 다층 방어를 형성함

## Ⅲ. 절차
```text
요청 수신 --> TLS 복호화 --> 토큰 검증 --> 권한 확인 --> 입력 검증 --> 자원 응답
```
- 1단계: TLS를 통해 암호화된 요청을 수신하고 복호화함
- 2단계: JWT/OAuth 토큰의 유효성·만료 여부를 검증함
- 3단계: 토큰 내 Scope·Role과 요청 자원의 접근 권한을 대조함
- 4단계: 요청 파라미터 검증 후 자원을 처리하고 응답함

> 요약: TLS 복호화 → 토큰 검증 → 권한 확인 → 입력 검증의 순차 파이프라인으로 동작함

## Ⅳ. 문제점
- 토큰 탈취: Stateless JWT는 만료 전 폐기가 불가하여 탈취 시 악용 가능함
- 과도한 노출: 응답에 불필요한 필드가 포함되어 민감 데이터가 유출될 수 있음
- 속도 제한 우회: 분산 IP를 활용한 공격 시 단순 Rate Limiting이 무력화됨

> 요약: 토큰 관리·데이터 노출·우회 공격이 REST API 보안의 주요 취약점임

## Ⅴ. 개선방안
1. 단기: 토큰 블랙리스트와 짧은 만료 시간(15분 이내) 적용으로 탈취 피해를 최소화함
2. 중기: 응답 필드 필터링(GraphQL Projection 등)으로 최소 데이터만 노출함
3. 장기: AI 기반 이상 행위 탐지로 분산 공격 패턴을 실시간 식별·차단함

> 요약: 토큰 수명 단축 → 응답 최소화 → AI 이상탐지 순으로 보안 성숙도를 높임

## Ⅵ. 전망
- 발전 방향: Zero Trust 모델과 결합하여 모든 요청을 매번 검증하는 방향으로 전환됨
- 기술사적 판단: API 보안은 서비스 메시·게이트웨이와 통합되어 인프라 수준에서 처리될 전망임
- 기술사 제언: OWASP API Top 10 기반 위협 모델링을 설계 단계부터 적용할 것을 권고함
