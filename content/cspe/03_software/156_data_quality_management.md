# 📖 【암기용】 개념 완전 이해

> 목적: 데이터 품질 관리를 처음 보는 사람도 완벽히 이해하게 만든다. 시험 답안 양식이 아니라, 이해를 위한 친절한 설명이다.

## 한눈에
- **개요**: 데이터 품질 관리는 **데이터 관리(Data Management)** 활동 중, 데이터가 업무 목적에 맞는지를 **완전성(Completeness)·정확성(Accuracy)·일관성(Consistency)** 같은 품질 차원으로 정의하고 규칙 기반으로 검증·통제하는 것이다.
- **왜 필요한가**: 결측, 오입력, 중복, 코드 불일치가 누적되면 보고서 숫자, AI 학습 데이터, 운영 의사결정이 조용히 틀어진다. 문제가 드러날 땐 이미 여러 단계 후 시스템까지 오염된 뒤다.
- **핵심 직관**: 공장 품질검사처럼 데이터도 출하(적재) 전에 불량률, 검사 기준, 책임자를 정해야 한다.

## 핵심 용어 정리 (내부에 등장하는 것들)

| 용어 | 의미 | 비유 |
|:---|:---|:---|
| 완전성(Completeness) | 있어야 할 값이 실제로 채워져 있는가 | 서류에 빈칸이 없는가 |
| 정확성(Accuracy) | 값이 실제 세계와 일치하는가(형식·범위 포함) | 서류 내용이 사실과 맞는가 |
| 일관성(Consistency) | 같은 대상이 여러 시스템에서 같은 값·정의로 존재하는가 | 여러 부서 서류의 숫자가 서로 맞는가 |
| null rate(결측률) | 필수 컬럼 중 값이 비어 있는 비율 | 미기재 항목 비율 |
| duplicate rate(중복률) | 동일 대상이 두 번 이상 기록된 비율 | 같은 서류가 두 부 접수된 비율 |
| reconciliation gap(정합성 차이) | 원천과 목적지(예: ERP와 DW)의 합계 값 차이 | 두 장부의 잔액 차이 |
| reject / quarantine | 오류 레코드를 아예 버림(reject) vs 격리 보관 후 재처리(quarantine) | 불량품 폐기 vs 검사 대기 창고 이동 |
| P1/P2/P3(심각도) | 오류의 업무 영향 크기에 따른 등급(P1=즉시 차단 필요) | 응급실 중증도 분류 |
| Great Expectations / Deequ | 품질 규칙을 코드로 정의하고 자동 검사하는 대표 오픈소스 도구 | 자동 검사 장비 |

## 깊이 이해

### 세 가지 품질 차원을 실제 예로 구분하기
같은 "주문 데이터 오류"도 원인에 따라 차원이 다르다.
- **완전성 위반**: `order_id`가 비어 있는 레코드 — 주문 자체를 식별할 수 없다.
- **정확성 위반**: 주문금액이 -5,000원처럼 물리적으로 불가능한 값 — 값은 있지만 틀렸다.
- **일관성 위반**: ERP에는 오늘 매출 1억 원, DW 집계는 9,800만 원 — 같은 사실이 시스템마다 다르게 기록됐다.
- (참고로 완전성·정확성·일관성 외에 적시성·유일성·유효성 같은 차원도 있지만, 이 문서는 세 차원에 집중한다.)

### 임계값을 수치로 정하기 — 구체 예시
"품질이 좋다"는 감상이 아니라 숫자로 정의해야 검사·차단이 가능하다. 주문 100만 건 기준으로 예를 들면:
- 완전성 기준 null rate 0.5% 이하 → 100만 건 중 최대 5,000건까지만 결측 허용, 5,001건째부터 규칙 위반.
- 정확성 기준 오류율 0.5% 이하 → 범위·형식 위반(음수 금액 등)이 최대 5,000건.
- 일관성 기준 reconciliation gap 0.1% 이하 → ERP 매출이 10억 원이면 DW 집계와의 차이가 최대 100만 원까지만 허용, 초과하면 원인 조사(RCA) 대상.
- 이 임계값이 없으면 "오류가 있다/없다"만 알 뿐, 언제 적재를 막고 언제 그냥 지켜볼지 판단할 기준이 없다.

### 파이프라인에서 어떻게 작동하나 (작동 원리)
품질 규칙을 코드로 정의(Great Expectations, Deequ 등)해 파이프라인 실행 단계(적재 전/후)에 끼워 넣는다. 검사를 통과 못한 레코드는 심각도에 따라 처리한다: **P1(예: PII 컬럼 완전 결측)**은 적재 자체를 차단(reject), **P2**는 격리 저장소로 보내고(quarantine) owner에게 알림 후 재처리, **P3**는 경고만 남기고 통과시킨다. 이렇게 등급을 나누는 이유는, 모든 오류를 무조건 차단하면 정상 데이터까지 멈춰 업무가 마비되기 때문이다.

### 판별 원리 — 언제 막고 언제 경고만 하나
데이터가 결제·규제 보고·고객 접점처럼 잘못되면 즉시 손실로 이어지는 영역이면 reject(차단형)을 쓰고, 탐색적 분석용 데이터처럼 다소 부정확해도 업무에 즉시 영향이 없는 영역이면 warning(경고형)으로 시작해 점진적으로 강화한다.

### 비유
식당 재료 검수와 같다. 재료가 빠졌는지(완전성), 유통기한이 맞는지(정확성), 주문서 수량과 실제 입고 수량이 일치하는지(일관성)를 확인하지 않으면 요리(분석 결과)를 신뢰할 수 없다.

### 흔한 오해
품질 관리는 문제가 생긴 뒤 SQL로 고치는 사후 정제가 아니다. 사후 정제는 같은 오류가 다음 배치에서 또 발생하는 것을 막지 못한다. 데이터 계약(producer-consumer 합의), 파이프라인 내장 검사, 자동 차단, owner 알림까지 이어져야 재발을 줄일 수 있다.

## 연결 개념
- 데이터 계약 — producer와 consumer 간 품질 기준 합의
- ETL/ELT 파이프라인 — 품질 규칙이 실제로 실행되는 지점
- 데이터 거버넌스 — 품질 owner 지정과 개선 책임 부여

## Ⅰ. 개요 및 필요성

- 개요: 데이터 품질 관리는 데이터 오류 통제 체계임.
- 배경: 결측, 오입력, 중복, 코드 불일치는 분석 결과와 업무 처리를 왜곡한다.
- 필요성: 완전성, 정확성, 일관성 규칙 기반 검증으로 데이터 사용 전 오류를 식별하고 개선 절차를 실행한다.

---

## Ⅱ. 구조 및 구성요소

```text
Data Source -> Quality Rule -> Validation Engine -> Quarantine/Load -> Alert/Dashboard
                              +-> Owner Remediation
```

| 구성요소 | 역할 | 특이사항 |
|:---|:---|:---|
| 품질 규칙 | 필수값, 범위, 참조무결성, 중복 기준 정의 | Great Expectations, Deequ |
| 검증 엔진 | 배치/스트림 데이터 검사 | CI, Airflow, Spark 연계 |
| 격리 저장소 | 실패 레코드 보관과 재처리 | reject/quarantine 구분 |
| 알림/대시보드 | owner 통보와 품질 추세 관리 | SLA, SLO 기반 |

> 요약: 품질 관리는 규칙, 검증, 격리, 알림이 파이프라인에 내장되어야 작동함.

---

## Ⅲ. 동작원리 및 흐름도

```text
규칙 정의 -> 데이터 검사 -> 오류 분류 -> 차단/경고/격리 -> 원인 수정 -> 재검증
```

| 단계 | 처리 내용 | 검증 기준 |
|:---:|:---|:---|
| 1 | 품질 차원과 규칙 정의 | 핵심 컬럼 rule coverage 95% |
| 2 | 적재 전/후 데이터 검사 | 검사 실행률 100% |
| 3 | 오류 심각도 분류 | P1/P2/P3 기준 |
| 4 | 차단, 격리, 경고 처리 | P1 데이터 적재 0건 |
| 5 | owner 수정과 재검증 | 재발률 5% 이하 |

> 요약: 품질 관리는 규칙 실행 후 오류를 등급별로 처리하고 재발률을 관리하는 반복 절차임.

## Ⅵ. 실무 적용 및 결론

**적용 방안 3개 (필수 - 단계별 또는 항목별):**
1. 규칙 설정: 핵심 테이블 50개와 핵심 컬럼에 null, range, enum, referential rule을 정의하고 coverage 95% 이상 확보
2. 파이프라인 내장: Airflow/dbt/Spark 단계에 Great Expectations 또는 Deequ 검사를 넣고 P1 오류는 적재 차단
3. 개선 운영: 오류 레코드는 quarantine에 보관하고 owner 알림, RCA, 재검증을 통해 재발률 5% 이하 관리

**결론 (2줄):**
- 기술사 판단: 규제 보고, 결제, 고객 접점 데이터는 차단형 품질 검사를 적용하고 탐색 분석 데이터는 경고형으로 시작함
- 향후 방향: 데이터 계약과 observability가 결합되어 품질 오류를 배포 전 단계에서 차단하는 구조로 확장됨
