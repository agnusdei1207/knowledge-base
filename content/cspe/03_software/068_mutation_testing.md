## 핵심 인사이트 (3줄 요약)
- 내가 짠 '테스트 코드'가 진짜로 버그를 잡아낼 능력이 있는지, **테스트 코드 자체의 품질(결함 검출력)을 검증**하는 테스트 기법.
- 원본 소스 코드의 연산자(`+`를 `-`로, `==`를 `!=`로)를 일부러 조작한 '돌연변이(Mutant)' 코드를 수십 개 생성한 뒤, 기존 테스트 코드가 이를 에러로 감지하여 실패(Kill)하는지 확인함.
- 높은 '테스트 커버리지(Coverage)' 수치 뒤에 숨겨진 '검증(Assert) 없는 껍데기 테스트'를 완벽하게 색출해내는 가장 진보된 품질 검증 기법임.
---
## Ⅰ. 개요 및 필요성
- **개요**: 의도적으로 프로그램에 오류를 주입하여, 기존의 테스트 케이스 집합이 그 오류를 얼마나 잘 검출하는지(Mutation Score) 측정하는 기법.
- **필요성**: CI/CD 파이프라인에서 "커버리지 80% 이상 통과"라는 룰을 만들자, 개발자들이 메서드를 그냥 실행만 시키고 결과값 검증(`assertEquals`)을 빼먹는 꼼수를 부림. 커버리지는 100%인데 실제 버그는 하나도 못 잡는 허수(Illusion)를 깨부술 강력한 도구가 필요했음.
---
## Ⅱ. 아키텍처 및 핵심 원리
- **동작 원리 (4단계)**:
  1. **Mutant Generation (돌연변이 생성)**: 원본 코드의 조건문이나 연산자를 미세하게 바꿈 (예: `if (a > b)` ➡️ `if (a >= b)`).
  2. **Test Execution (테스트 실행)**: 조작된 돌연변이 코드를 대상으로 기존 테스트 스위트를 쫙 돌림.
  3. **Mutant Killed (사살 성공)**: 테스트가 실패(Red)하면 ➡️ 테스트 코드가 훌륭하게 버그를 잡아낸 것임 (좋은 상태).
  4. **Mutant Survived (생존/사살 실패)**: 코드가 조작되었는데도 테스트가 성공(Green)하면 ➡️ 테스트 코드에 검증(Assert) 로직이 빠져있다는 뜻임 (경고 발생).
- **돌연변이 점수 (Mutation Score)**: 
  - `(Killed Mutants / Total Mutants) * 100`. 이 점수가 높을수록 테스트 케이스의 신뢰도가 높음.

```text
[ Mutation Testing 동작 도식 ]

 [ 원본 코드: return a + b; ]
        ⬇️ (돌연변이 연산자 주입 도구 - PIT, Stryker)
 [ 돌연변이 1: return a - b; ]  ➡️  [ 기존 Test Case 실행 ] 
                                          ⬇️
                   +---------------------------------------------+
                   | 🔴 Test가 실패함! (버그를 발견함)               |
                   | ➡️ 돌연변이 사살(Killed) = "테스트 코드 훌륭함!"   |
                   +---------------------------------------------+
                   | 🟢 Test가 통과함! (코드를 망쳤는데 왜 통과해?)     |
                   | ➡️ 돌연변이 생존(Survived) = "테스트 코드 엉터리!" |
                   +---------------------------------------------+
```

## Ⅲ. 비교 및 연결
| 구분 | 코드 커버리지 (Code Coverage) | 돌연변이 테스트 (Mutation Testing) |
|---|---|---|
| **측정 목적** | 테스트 코드가 **어디까지 실행했나?** (양적 지표) | 테스트 코드가 **버그를 잡을 수 있나?** (질적 지표) |
| **속이는 방법**| `assert`를 아예 안 쓰고 메서드만 호출하면 통과됨 | 절대 속일 수 없음 (코드를 망가뜨리기 때문) |
| **실행 시간** | 빠름 (단순 1회 실행) | **매우 느림** (돌연변이 수십 개를 각각 컴파일하고 실행) |
| **도구** | JaCoCo, Cobertura, SonarQube | PIT (Java), Stryker (JS/C#), mutmut (Python) |
---
## Ⅳ. 실무 적용 및 기술사 판단
- **컴퓨팅 파워의 장벽 (Performance Issue)**: 소스 코드가 큰 프로젝트에서 돌연변이 테스트를 돌리면, 경우의 수가 수만 개로 늘어나 테스트에만 수십 시간이 걸림. 따라서 CI 파이프라인(매 커밋마다)에 넣는 것은 불가능에 가까우며, 주말 야간 빌드(Nightly Build)에만 돌리거나, 최근 수정된 코드(Incremental)에만 제한적으로 돌리는 것이 실무적 정석임.
- **테스트 품질의 최종 보스**: 화이트박스 테스트, 경곗값 분석, TDD를 모두 완벽히 수행했다면 돌연변이 점수는 자연스럽게 90%를 넘김. 기술사는 커버리지 지표에 안주하는 조직에게 "진짜 안전한가?"라는 화두를 던질 때 이 기법을 도입해야 함.

## Ⅴ. 기대효과 및 결론
- "누가 감시자를 감시하는가?(Who tests the tests?)"라는 소프트웨어 공학의 오랜 난제에 대해 가장 기계적이고 확실한 해답을 제공함.
- 연산 비용이 비싸다는 단점에도 불구하고, 결코 타협할 수 없는 금융/항공/의료 등 미션 크리티컬(Mission Critical) 도메인에서는 필수적인 품질 검증 무기로 자리 잡고 있음.

### 👶 어린이를 위한 3줄 비유 설명
1. 경찰관(테스트 코드)이 도둑(버그)을 잘 잡는지 훈련시키려고 해요.
2. 그래서 일부러 가짜 도둑(돌연변이 코드)을 은행에 몰래 들여보내 봅니다.
3. 경찰관이 가짜 도둑을 잡아서 감옥에 넣으면(Killed) 훌륭한 경찰관이지만, 도둑이 지나가는데도 멀뚱멀뚱 쳐다만 보고 통과시켜 주면(Survived) 엉터리 경찰관인 걸 알 수 있죠!
