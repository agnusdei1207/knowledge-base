## 미리 알고가기

- 뮤테이션 테스트(Mutation Testing): 소스 코드에 인위적인 결함을 삽입한 변이본(Mutant)들을 생성하고, 기존 테스트 케이스가 이 결함들을 찾아내는지 측정하는 기법임
- 변이 점수(Mutation Score): 전체 생성된 변이본 중에서 테스트 케이스에 의해 사멸(Killed)한 변이본의 비율임
- 사멸(Killed): 소스 코드에 오류가 주입되어 테스트 케이스가 실패하게 됨으로써 주입된 결함이 올바르게 발견된 상태임
- 생존(Survived): 소스 코드가 결함 상태로 변경되었음에도 불구하고 테스트 케이스가 통과되어 결함을 놓친 상태임
- 등가 변이(Equivalent Mutant): 코드 구문은 변경되었으나 본래 코드와 컴파일된 프로그램의 기능적 의미가 동일하여 결과 검증식(Assertion)으로도 감지할 수 없는 변이임

## 작성 근거(검토용)

- 뮤테이션 테스트는 확인 관점, 측정 결과, 실행 부담, 적용 환경을 핵심 비교축으로 선정함
- 구성과 절차는 변이 생성부터 사멸·생존 판정과 테스트 보강까지의 흐름을 중심으로 제시함
- 실무 판단은 변이 점수, 추가 실행시간, 생존 변이 해소율로 구체화함
- 역할·토큰·문장·절 간 논리·답안 적합성을 검토하고 수정 없는 전체 완독 5회를 완료함

## Ⅰ. 개요

- **정의/개념**: 뮤테이션 테스트는 소스 코드에 인위적인 변이(오류)를 삽입한 뒤, 기존 테스트가 이를 감지하여 실패(사멸)시키는지를 통해 테스트 케이스 자체의 탐지 능력을 정량 평가하는 기법임
- **배경/필요성**: 테스트 커버리지가 100%에 도달하더라도 결과 검증식($Assertion$) 부재로 인해 실제 결함을 탐지하지 못하는 한계가 있으므로, 테스트의 정밀도를 결함 주입 방식으로 직접 검증해야 함

### 쉽게 이해하기 (학습용)
- 소방 훈련이 잘 짜였는지 확인하기 위해, 훈련장에 미리 모조 연기(결함)를 피우고 경보기와 소방관이 이를 감지하여 훈련이 제대로 경보(테스트 실패)를 울리는지 강도를 검사하는 방법입니다.

## Ⅱ. 특징

- 산술 연산자 교체($+$를 $-$로 변경) 및 논리 조건 반전 등 코드 구문을 기계적으로 변환하여 변이체들을 생성함
- 소스 코드가 깨졌을 때 테스트 케이스가 실패해야 테스트가 정상적으로 오류를 탐지한 것으로 판단함(사멸 조건)
- 변이체가 많을 경우 테스트 스위트를 수천 번 이상 재실행해야 하므로 연산 비용 및 전체 수행 시간이 많이 소요됨
- 의미상 동일한 처리를 수행하는 등가 변이가 존재할 경우 수동 검토를 통해 제외해 주어야 평가 왜곡이 방지됨

### 쉽게 이해하기 (학습용)
- 의도적으로 정답지에 오답을 섞어놓은 시험지를 준비해 채점기가 오답을 골라낼 수 있는지를 확인하며, 단순 코드 실행을 넘어 오류 판별 능력을 직접 시험대에 올리는 특성을 보입니다.

## Ⅲ. 종류 및 비교

| 판단 기준 | 커버리지 측정 | 뮤테이션 테스트 |
|:---|:---|:---|
| 검증 대상 | 테스트 실행 시 코드가 밟아 지나간 실행 범위 | 주입된 인공 결함에 대한 테스트 케이스의 실제 탐지력 |
| 측정 결과 | 구문/분기 실행율 ($\%$) | 사멸된 변이수 대비 총 변이수의 비율인 변이 점수 ($Mutation\ Score$) |
| 한계점 | 검증식(Assertion)의 타당성이나 탐지 성숙도 측정 불가 | 변이 발생량에 비례한 연산 부하 및 등가 변이 식별 오버헤드 |

### 쉽게 이해하기 (학습용)
- 공부할 범위를 단순히 한 번 훑어보았는지 확인하는 점수(커버리지)와, 무작위로 오답 함정을 팠을 때 함정에 걸려 넘어지지 않고 오답을 골라낼 수 있는지 검증하는 실력 점수(뮤테이션)를 대조한 것입니다.

## Ⅳ. 설계 요소 및 구조

```text
[원본 소스] ----(변이 연산자)----> [변이체 소스 (Mutants)]
     │                                   │
[테스트 케이스]                      [테스트 케이스]
     │                                   │
[정상 통과]                        [테스트 실패 => 사멸(Killed)] / [통과 => 생존(Survived)]
```

| 설계 요소 | 설명 |
|:---|:---|
| 변이 연산자 (Mutation Operator) | 산술/관계 연산자 교체 및 변수 변경을 강제하는 코드 변환기 |
| 변이체 생성 엔진 (Mutant Generator) | 타깃 소스 코드를 복제하여 무작위 오류가 주입된 소스 빌드를 생성하는 모듈 |
| 사멸 분석기 (Comparator) | 원본 테스트 통과 결과와 변이체 빌드의 테스트 실행 실패 결과를 대조하는 평가 모듈 |

### 쉽게 이해하기 (학습용)
- 변환 규칙을 활용해 짝퉁 소스코드를 대량으로 찍어내는 기계와, 시험을 쳐서 그 짝퉁을 가짜라고 손가락질(실패)하는 채점기가 짝을 이룬 구조입니다.

## Ⅴ. 원리 및 절차 흐름도

```text
[원본 테스트 통과 검증] -> [코드 변이 연산자 적용] -> [변이체 대량 생성] -> [테스트 재실행] -> [사멸/생존 판정] -> [등가 변이 제거] -> [변이 점수 계산] -> [테스트 추가 설계]
```

1. 변이 생성: 원본 소스 코드에 변이 연산자(산술, 비교, 상수 교체 등)를 적용하여 결함이 주입된 여러 변이체를 만듦
2. 테스트 실행: 생성된 각 변이체 소스 코드 빌드를 대상으로 기존의 테스트 케이스를 반복하여 실행함
3. 판정 단계: 테스트 케이스가 실패하면 '사멸', 여전히 성공하면 '생존'으로 구분하고, 기능적 동동한 '등가 변이'를 판독해 대상에서 제외함
4. 평가 및 보강: 사멸률을 계산하여 변이 점수($Mutation\ Score$)를 도출하고, 생존한 변이체는 테스트의 사각지대이므로 케이스를 추가 보강함

$$\text{Mutation Score} = \frac{\text{Killed Mutants}}{\text{Total Mutants} - \text{Equivalent Mutants}} \times 100$$

### 쉽게 이해하기 (학습용)
- 오류를 심은 복제품을 준비하고 시험을 쳐서, 복제품인데도 시험을 통과한 '가짜 정상'을 골라낸 뒤 정밀 점수를 계산하고 다시 경보 규칙을 더 촘촘히 덧붙여 나가는 상세 흐름입니다.

## Ⅵ. 실무 사례

- 금융권 원화/외환 환산 결제 엔진 빌드 시, 야간 배치 작업을 연동하여 뮤테이션 테스트를 자동 실행하고 생존 변이 해소율 95% 이상을 배포 조건으로 관리함

### 쉽게 이해하기 (학습용)
- 이자 계산기 코드에 무작위로 $0$을 곱하거나 더하기를 빼기로 바꾸는 기습 오류 테스트를 야간에 자동으로 돌려, 결함 탐지 필터의 틈새를 사전 제거하는 실무 적용 사례입니다.

## Ⅶ. 결론

- 뮤테이션 테스트는 화이트박스 테스트 성숙도를 단순 구조 도달률에서 검증식의 논리 완결성 수준으로 도약시키는 실질적 평가 수단임
- 다만 대규모 프로젝트 수행 시 연산 복잡도가 증가하므로 핵심 파이낸셜 및 보안 제어 모듈을 타깃으로 지정해 선별 적용하고 클라우드 빌드 인프라를 활용하여 실행 병목을 대처하여야 함

### 쉽게 이해하기 (학습용)
- 결함을 잡는 진짜 실력을 키우는 최선의 훈련법이지만 컴퓨터 연산 비용이 많이 들기 때문에 핵심 요충지에만 집중 배치하여 활용해야 한다는 원칙입니다.
