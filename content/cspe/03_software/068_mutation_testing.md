# 📖 【암기용】 개념 완전 이해

## 한눈에
- **개요**: 원본 소스코드에 의도적인 오류(돌연변이)를 주입한 뒤, 기존 테스트 코드들이 이 오류를 잡아내는지(Kill) 확인하는 기법
- **왜 필요한가**: 테스트 커버리지가 100%라도, 그 테스트 케이스 자체가 엉터리(Assert 구문 누락 등)라면 버그를 못 잡는다. "테스트 코드를 테스트"하기 위해 필요하다.
- **핵심 직관**: 보안 검색대에 일부러 가짜 폭탄(돌연변이)을 넣은 가방을 통과시켜 본다. 검색대(테스트 코드)가 경보를 울리면(Kill) 정상, 무사통과하면(Survive) 검색대 교체 필요!

## 핵심 용어 정리

| 용어/표기 | 의미 | 비유·예 |
|:---|:---|:---|
| 돌연변이 (Mutant) | 원본 코드를 살짝 변형하여 버그를 의도적으로 만든 코드 | 덧셈 `+` 기호를 뺄셈 `-` 로 바꾼 코드 |
| Killed (사멸) | 돌연변이 코드를 테스트 코드가 돌려서 실패(Red)로 잡아냄 | 가짜 폭탄을 제대로 적발함 (테스트 양호) |
| Survived (생존) | 돌연변이 코드인데도 테스트 코드가 통과(Green)해버림 | 가짜 폭탄이 무사통과함 (테스트 부실) |
| Mutation Score | 생성된 전체 돌연변이 중 Killed 된 비율 (100%가 목표) | 보안 검색대 적발률 |

## 깊이 이해
- **배경·문제의식**: 구문 커버리지(Statement Coverage) 달성에 집착하면, 개발자들은 단순히 코드를 "실행"만 하고 결과를 꼼꼼히 검증하지 않는(Assert 없는) 테스트 코드를 양산하는 착시 현상이 발생한다. 커버리지 지표의 신뢰성 붕괴.
- **작동 원리**: 도구(PIT, Stryker 등)가 소스코드를 분석하여 산술 연산자(`+` -> `-`), 논리 연산자(`>` -> `>=`), 리턴값(`return true` -> `return false`) 등을 기계적으로 바꾼 수백 개의 뮤턴트를 만든다. 각 뮤턴트에 대해 기존 단위 테스트를 실행한다. 하나라도 테스트가 실패하면(Fail) 해당 뮤턴트는 "죽은(Killed)" 것으로 간주하여 성공적이다.
- **비유**: 예방접종. 약해진 바이러스(뮤턴트)를 주입했을 때, 우리 몸의 면역 체계(테스트 스위트)가 이를 찾아내 죽여야만 진짜 질병에 강하다고 확신할 수 있다.
- **구체 예시**: `if (age >= 18)` 코드를 뮤테이션 도구가 `if (age > 18)`로 바꾼다. 이때 18살을 테스트하는 케이스가 없었다면, 이 돌연변이 코드는 테스트를 통과(Survive)해버린다. 개발자는 아차! 하고 18살 경계값 테스트 케이스를 추가한다.
- **흔한 오해·주의점**: "돌연변이가 생존(Survive)했다면 무조건 나쁜 건가?" 대부분 테스트 부실이지만, 가끔 코드를 바꿔도 논리적으로 동일한 결과를 내는 "동등 돌연변이(Equivalent Mutant)"가 발생한다. 이는 도구가 죽일 수 없으므로 사람의 분석이 필요하다.

## 연결 개념
- 테스트 커버리지: 뮤테이션 테스트가 보완하려는 대상(실행 여부만 측정하는 한계)
- 단위 테스트 / TDD: 뮤테이션 테스트는 촘촘한 단위 테스트 위에서만 의미가 있음
- 결함 주입 (Fault Injection): 더 큰 아키텍처 관점에서 고의로 장애를 내는 카오스 엔지니어링과 맥락 상통

# 📝 【답안용】 시험 답안 템플릿

## 핵심 인사이트 (3줄 요약)

> 1. **본질**: 뮤테이션 테스트는 원본 소스코드에 의도적인 문법적 오류(Mutant)를 주입하여, 기존 테스트 스위트(Test Suite)의 결함 검출 능력을 평가하는 화이트박스 테스트 기법이다.
> 2. **가치**: 코드 커버리지(실행률) 100%의 함정(Assertion 누락 등)을 돌파하여 테스트 케이스 자체의 실질적 견고성(Rigor)을 수학적 점수(Mutation Score)로 증명한다.
> 3. **판단 포인트**: 뮤턴트 생성-실행-상태(Killed/Survived) 판정으로 이어지는 메커니즘과, 수행 비용(컴퓨팅 파워) 폭발을 해결하기 위한 실무적 최적화 전략을 제시해야 한다.

## 출제 의도 및 답안 포인트

| 출제 의도 | 반드시 짚을 핵심 | 감점 회피 포인트 |
|:---|:---|:---|
| 기존 테스트 커버리지의 한계 인식 | 코드 실행(Coverage) ≠ 검증(Assertion), 테스트 품질의 맹점 | 뮤테이션 테스트를 단순히 버그 찾는 기법으로 서술 |
| 뮤테이션 테스트 동작 원리 | 뮤턴트 주입, Killed/Survived 판정, Mutation Score 공식 | 상태 판정(Kill/Survive)의 주체(테스트 코드) 혼동 |
| 트레이드오프 및 한계 극복 | 엄청난 실행 비용(수천 번 컴파일/실행), Equivalent Mutant 판단 | 도입의 장점만 나열하고 성능 이슈 누락 |

> 요약: 뮤테이션 테스트는 '제품'을 테스트하는 것이 아니라 '테스트 코드'를 테스트하는 메타 검증(Meta-Verification) 기법임을 명확히 한다.

## Ⅰ. 개요 및 필요성

- 개요: 소스코드에 의미적 변형(돌연변이)을 가한 후, 기존 단위 테스트가 이 오류를 적발하여 실패하는지 여부를 측정해 테스트 케이스의 품질을 평가하는 기법
- 배경: 라인 커버리지/분기 커버리지만으로는 검증 로직(Assert)이 누락되었거나 부실한 테스트 케이스(허수 테스트)를 걸러낼 수 없음
- 필요성: 테스트 케이스 품질의 정량적 평가, 경곗값 및 논리 오류 누락 방지, 안전 필수(Safety-Critical) 시스템의 극단적 신뢰성 확보

---

## Ⅱ. 구조 및 구성요소

```text
[원본 코드] --(돌연변이 연산자)--> [뮤턴트 1] [뮤턴트 2] [뮤턴트 3]
                                     |          |          |
                              [테스트 스위트 (Unit Tests) 일괄 실행]
                                     |          |          |
                              (Fail) 적발   (Pass) 통과   (Fail) 적발
                                     v          v          v
                                  [Killed]  [Survived]  [Killed]
```

| 구성요소 | 역할 | 특이사항 |
|:---|:---|:---|
| 원본 소스코드 & TC | 분석의 대상이 되는 프로덕션 코드와 그 단위 테스트 | 100% Pass하는 상태가 전제됨 |
| 돌연변이 연산자 | 코드의 문법을 기계적으로 변형하는 규칙 집합 | 산술, 관계, 논리, 반환값 변경 |
| 뮤턴트 상태 판정 | 테스트가 실패하면 Killed(우수), 성공해버리면 Survived(부실) | Survived 발생 시 TC 보강 필요 |
| 동등 돌연변이 | 문법은 바뀌었으나 원본과 완벽히 동일한 동작을 하는 뮤턴트 | 도구로 판별 불가(무조건 Survive) |

> 요약: 원본 코드에 수백 개의 결함을 주입하고, 테스트 코드가 이 결함들을 얼마나 많이 사멸(Kill)시켰는지 방어율을 측정한다.

---

## Ⅲ. 동작원리 및 흐름도

```text
초기 단위 테스트 100% Pass -> 뮤턴트 자동 생성 -> 뮤턴트별 테스트 실행 -> Mutation Score 산출 -> 테스트 리팩터링
```

- 1단계 [초기 검증]: 원본 소스코드에 대해 작성된 테스트 스위트가 모두 초록색(Pass)인지 확인
- 2단계 [오류 주입]: 뮤테이션 프레임워크(PIT, Stryker 등)가 연산자 조작 규칙에 따라 수백 개의 변형된 돌연변이 버전 생성
- 3단계 [검증 능력 테스트]: 각 돌연변이 코드마다 전체 단위 테스트를 실행하여, 붉은색(Fail)이 뜨면 적발(Killed)로 기록
- 4단계 [지표 산출 및 개선]: `(Killed 수 / 총 유효 뮤턴트 수) × 100`으로 Score를 계산하고, 살아남은 뮤턴트를 잡기 위해 부족한 테스트 케이스를 보강

> 요약: 뮤턴트 생존(Survive)은 해당 코드 영역에 대한 엣지 케이스(경곗값)나 검증(Assertion) 로직이 빠져 있음을 경고하는 강력한 신호다.

---

## Ⅳ. 특징
- [메타 테스팅(Meta-Testing)]: 프로덕션 로직의 결함을 찾는 것이 주 목적이 아니라, '결함을 찾는 능력'을 향상시키는 것이 목적
- [비용의 기하급수성]: 뮤턴트가 1,000개라면 컴파일과 전체 테스트 스위트 실행을 1,000번 반복해야 하므로 엄청난 컴퓨팅 파워 소모
- [경곗값 누락 색출 탁월]: 개발자가 `>=` 를 `>`로 잘못 인지하여 테스트를 짰을 때, 뮤테이션 도구가 이를 반대로 바꿔 치명적인 Off-by-one 에러 누락을 귀신같이 잡아냄
- [거짓 음성(Equivalent Mutant)]: 컴파일 최적화나 동어 반복적 코드로 인해, 실제로는 동일한 논리인데 무한정 Survive하는 뮤턴트가 발생해 수동 분석 비용 초래

> 요약: 커버리지 착시 현상을 부수는 가장 강력한 무기이나, 실행 비용(성능) 이슈로 전략적 접근이 필요하다.

## Ⅴ. 심화 비교 및 적용 판단

| 비교 축 | 구조적 코드 커버리지 (Statement/Branch) | 뮤테이션 테스트 (Mutation Score) | 선택 기준 |
|:---|:---|:---|:---|
| 측정 대상 | 대상 코드가 "실행(Executed)" 되었는가? | 실행 결과가 올바르게 "검증(Asserted)" 되었는가? | 품질 통제의 깊이 |
| 달성 비용 | 한 번의 테스트 실행으로 즉시 측정 가능 (저비용) | N개의 뮤턴트마다 테스트 재실행 (초고비용) | CI/CD 파이프라인 여유 자원 |
| 지표의 신뢰성 | Assertion이 없어도 100% 달성 가능한 맹점 존재 | 테스트 로직 자체가 부실하면 Score 하락 (높은 신뢰도) | 안전 필수 도메인 여부 |

> 요약: 코드 커버리지가 테스팅의 양(Quantity)을 측정한다면, 뮤테이션 스코어는 테스팅의 질(Quality)을 측정한다.

**리스크·대응:**
- [CI 파이프라인 병목]: 모든 커밋마다 수만 번의 테스트 재실행으로 CI 시간 10배 증가 → 변경된 클래스(Incremental Analysis) 주변의 테스트와 뮤턴트만 한정적으로 실행하는 최적화 적용 (지표: 뮤테이션 분석 빌드 타임)
- [동등 돌연변이 분석 피로도]: 절대 죽일 수 없는 Equivalent Mutant로 인해 100% Score 달성 불가 및 개발자 피로 누적 → 목표 Score를 80~90% 수준으로 조정하고, 도구 레벨에서 정적 분석을 통해 동등 뮤턴트 사전 필터링

---

## Ⅵ. 실무 적용 및 결론

**적용 방안 3개:**
1. 점진적(Incremental) 분석 파이프라인: 야간 빌드(Nightly Batch) 시에만 전체 프로젝트 뮤테이션을 수행하고, 일간 PR 커밋에는 변경된 파일에만 PIT(Java), Stryker(JS) 플러그인을 가동
2. 핵심 도메인 타겟팅: 결제 릴레이, 인증 토큰 발급 등 비즈니스 코어(Core) 모듈에만 뮤테이션 점수 85% 이상을 강제하여 제한된 컴퓨팅 자원 효율화
3. 리뷰 도구 결합: SonarQube 등 코드 품질 대시보드와 연동하여, Survived 돌연변이 위치를 리뷰어에게 직접 시각화하여 테스트 케이스 누락을 방지

**결론 (2줄):**
- 기술사 판단: 뮤테이션 테스트는 코드 커버리지의 신뢰성 함정을 극복하는 최종 방어선이나, 무거운 실행 비용을 통제할 점진적/선택적 전략 없이는 조직에 정착할 수 없다.
- 향후 방향: 최근 AI/LLM을 활용해 동등 돌연변이(Equivalent Mutant)를 자동 식별하거나, 살아남은 뮤턴트를 죽일 수 있는 테스트 코드를 역으로 자동 생성하는 지능화 연구가 활발히 적용되고 있다.
