# 📖 【암기용】 개념 완전 이해

> 목적: ATAM을 처음 봐도 아키텍처가 품질속성을 어떻게 만족하거나 충돌시키는지 검토하는 방법으로 이해하게 만든다. 시험 답안 양식이 아니라, 이해를 위한 설명이다.
> 이 파일은 ATAM의 **전체 절차와 산출물 구조**(유틸리티 트리로 우선순위를 매기고 민감점·트레이드오프를 구분하는 방법론 관점)에 집중한다. 클라우드 네이티브 환경의 트레이드오프 지점을 깊이 파고드는 관점은 079_atam_architecture_tradeoff.md에서 다룬다.

## 한눈에
- **개요**: ATAM(Architecture Tradeoff Analysis Method)은 소프트웨어 아키텍처가 여러 **품질속성**(성능·가용성·보안·변경성 등)을 얼마나 충족하는지 **시나리오** 기반으로 검토하는 **아키텍처 평가 방법론**임 — CMU SEI가 1998년 개발함
- **왜 필요한가**: 아키텍처는 코딩을 시작하기 전 단계에서 확정되지만, 한번 굳어지면 구현 이후 고치는 비용이 설계 단계에서 고치는 비용의 약 10~100배로 커짐(보엠의 결함 비용 곡선). 그래서 코드를 짜기 전에 "이 설계로 정말 원하는 품질을 만족하는가"를 미리 검증해야 함
- **핵심 직관**: 여러 이해관계자를 모아놓고 "이 설계안은 성능은 좋지만 보안이 약하다"처럼 품질 간 저울질(트레이드오프)을 표로 꺼내놓고 합의하는 회의라고 보면 됨

## 핵심 용어 정리 (내부에 등장하는 것들)

| 용어 | 의미 | 비유 |
|:---|:---|:---|
| 아키텍처 평가 방법론 | 코드를 짜기 전, 설계도(아키텍처) 단계에서 품질 충족 여부를 검증하는 절차 — ATAM이 속하는 **상위 개념** | 집을 짓기 전 설계도만 보고 구조 안전성을 점검하는 것 |
| 품질속성(Quality Attribute) | 성능·가용성·보안·변경성처럼 시스템이 갖춰야 할 비기능 특성 — ATAM이 저울질하는 **대상** | 자동차의 속도·연비·안전성 |
| Business Driver | 평가의 배경이 되는 사업 목표·제약(매출, 규제, 일정) | "이번 블랙프라이데이 매출을 지켜야 한다"는 경영진 목표 |
| Quality Attribute Scenario | 품질 요구를 자극(stimulus)·환경(environment)·응답(response)·측정값(response measure)으로 구체화한 문장 | "10만 명이 동시 접속하면(자극) 결제가 2초 안에 끝나야 한다(측정값)"처럼 숫자로 못 박은 요구사항 |
| Utility Tree | 막연한 품질 요구를 품질속성 → 세부속성 → 시나리오로 가지 치듯 분해하고, 각 시나리오에 중요도(importance)·구현난이도(difficulty)를 매겨 우선순위를 정하는 구조 | 막연한 "빠르게 해주세요"를 "성능 → 응답속도 → 결제 2초 이내"로 구체화한 나뭇가지 |
| 민감점(Sensitivity Point) | 하나의 아키텍처 결정이 **한 개**의 품질속성을 크게 좌우하는 지점 | DB 쿼리 타임아웃을 3초로 잡으면 가용성이 크게 달라짐 — 가용성 하나만 좌우 |
| 트레이드오프점(Tradeoff Point) | 하나의 아키텍처 결정이 **두 개 이상**의 품질속성에 서로 반대 방향으로 영향을 주는 지점(민감점들의 교집합) | 캐시를 도입하면 응답속도(성능)는 좋아지지만 원본 데이터와의 정합성(정확성)은 나빠짐 |
| 리스크(Risk) / 비리스크(Non-Risk) | 현재 아키텍처가 시나리오의 목표치를 못 채울 것으로 예상되면 리스크, 채울 것으로 확인되면 비리스크 | 목표 응답속도 2초인데 실측 5초 예상 → 리스크. 실측 1.5초 예상 → 비리스크 |
| 리스크 테마(Risk Theme) | 여러 개별 리스크에서 반복되는 공통 원인을 묶은 것 — 후속 개선 과제로 연결됨 | "모든 지연 리스크의 원인이 동기 호출 구조"처럼 공통 패턴 추출 |

## 깊이 이해

### 왜 구현 전에 평가해야 하나 (배경)
- 아키텍처는 시스템의 뼈대여서, 구현이 다 끝난 뒤 "성능은 좋은데 보안이 약하다"는 걸 발견하면 데이터 흐름·모듈 경계 자체를 뜯어고쳐야 한다. 설계 단계에서 발견하면 문서 한 장을 수정하면 되지만, 구현·테스트가 끝난 뒤 발견하면 코드·테스트·배포를 전부 다시 해야 하므로 비용이 10~100배로 뛴다는 것이 소프트웨어 공학의 오래된 경험칙(보엠의 결함 비용 곡선)이다. ATAM은 이 비용 폭증을 막기 위해 "설계도만 보고 미리 검증"하는 절차다.

### 유틸리티 트리로 우선순위를 매기는 법 — 수치로 이해
- 모든 시나리오를 똑같이 다룰 수는 없으므로, 각 시나리오에 중요도(High/Medium/Low)와 구현 난이도(High/Medium/Low)를 매겨 2×2로 분류한다.
- 예: 결제 시스템에서 나온 6개 시나리오 중 "블랙프라이데이 10만 동접 시 결제 2초 이내"는 중요도 High·난이도 High(가장 먼저 심층 분석), "관리자 로그 포맷 변경"은 중요도 Low·난이도 Low(뒤로 미룸)로 분류하면, 워크숍 시간을 중요도·난이도가 모두 높은 시나리오에 집중할 수 있다.

### 민감점과 트레이드오프점을 수치로 구분하기
- 판별 원리는 "이 설계 결정을 바꾸면 몇 개의 품질속성이 움직이는가"이다.
- 민감점 예: "DB 쿼리 타임아웃을 3초로 설정" — 이 값을 1초로 낮추면 가용성(빠른 실패·재시도)만 크게 바뀌고 다른 품질에는 영향이 적다. 품질속성 1개만 좌우하므로 민감점이다.
- 트레이드오프점 예: "조회 결과를 60초 캐시" — 캐시를 도입하면 응답속도가 200ms에서 20ms로 90% 개선(성능 향상)되지만, 원본 DB 값이 바뀌어도 최대 60초 동안 캐시에는 예전 값이 남아 데이터 정합성이 떨어진다. 성능(+)과 정합성(-)이 **동시에, 반대 방향으로** 움직이므로 트레이드오프점이다.

### 리스크·비리스크를 판정하는 법 — 수치로 이해
- 시나리오의 목표 측정값과 아키텍처의 예상 성능을 비교해서 판정한다.
- 예: 장애 복구 시나리오의 목표가 "RTO(복구 목표 시간) 5분 이내"인데, 현재 설계(단일 DB, 수동 페일오버)의 예상 복구 시간이 8분이면 **리스크**로 기록한다. 이중화 DB와 자동 페일오버를 도입해 예상 복구 시간을 3분으로 줄이면 같은 시나리오가 **비리스크**로 바뀐다.

### ATAM 절차 흐름
- 크게 ① 이해관계자(아키텍트·개발·운영·보안·사업)를 모아 비즈니스 동인을 확인하고, ② 품질속성 시나리오를 수집해 유틸리티 트리로 우선순위를 매기고, ③ 우선순위 높은 시나리오마다 아키텍처가 어떤 접근법(tactic)으로 대응하는지 분석해 민감점·트레이드오프점을 찾고, ④ 목표 미달 항목을 리스크로, 충족 항목을 비리스크로 기록하고, ⑤ 반복되는 리스크를 리스크 테마로 묶어 개선 과제(action item)로 넘기는 순서로 진행한다.

### 비유와 흔한 오해
- **비유**: 건축 설계도 심사와 같다. 내진 성능을 높이려고 벽을 두껍게 하면 공간(평수)이 줄고 공사비가 오른다. 이 저울질을 시공 전에 설계도만 보고 검토하는 것이 ATAM이다.
- **오해**: ATAM을 하면 모든 품질을 만족하는 완벽한 설계가 나온다고 착각하기 쉽다. 실제로는 "무엇을 얻기 위해 무엇을 포기했는가"를 드러내고 이해관계자의 합의를 받는 것이 목적이지, 결함 없는 최적 설계를 자동으로 찾아주는 도구가 아니다. 또한 실제 부하를 걸어보는 성능 테스트도 아니다 — 어디까지나 설계도와 시나리오를 놓고 하는 정성적·구조적 분석이다.

## 연결 개념
- Quality Attribute Scenario — 품질 요구를 자극·환경·응답·측정값으로 표현하는 ATAM의 기본 입력 단위
- Utility Tree — 품질속성 우선순위 구조
- 079_atam_architecture_tradeoff.md — 같은 ATAM을 트레이드오프점 중심, 클라우드 네이티브 환경 관점에서 심화
- CBAM — ATAM이 찾은 리스크·트레이드오프에 비용·편익을 더해 개선 전략을 선택(080에서 상세)

# 📝 【답안용】 시험 답안 템플릿

> 목적: 시험장에서 25분에 그대로 쓰는 답안 양식. 작성방식(추상표현 금지·수치·도식·문제유형 전환)을 엄격히 지킨다.
> 핵심: ATAM은 아키텍처를 설명하는 기법이 아니라 품질속성 시나리오 기반으로 민감점, 트레이드오프, 리스크를 도출하는 평가 방법이다.

## 핵심 인사이트 (3줄 요약)
> 1. **본질**: ATAM은 Architecture Tradeoff Analysis Method로, 아키텍처 의사결정과 품질속성 간의 민감점·트레이드오프·리스크를 분석한다.
> 2. **가치**: 성능, 가용성, 보안, 변경성 요구를 시나리오와 utility tree로 구조화해 구현 전 아키텍처 위험을 식별함.
> 3. **판단 포인트**: 품질속성 간 충돌을 tradeoff point로 드러내고, 아키텍처 리스크를 의사결정 기록과 개선 과제로 연결해야 함.

## 출제 의도 및 답안 포인트

| 출제 의도 | 반드시 짚을 핵심 | 감점 회피 포인트 |
|:---|:---|:---|
| 아키텍처 평가 방법 이해 확인 | utility tree, quality attribute scenario, sensitivity point | 디자인 리뷰 일반론으로 작성 |
| 품질속성 트레이드오프 판단 확인 | tradeoff point, risk, non-risk, risk theme | 성능만 평가하고 보안·변경성 누락 |
| 실무 적용 절차 확인 | stakeholder workshop, scenario prioritization, action item | 도구명 나열 또는 테스트 활동으로 오해 |

> 요약: 이 문제는 아키텍처 구조와 품질속성 충돌을 시나리오 기반으로 분석하는 답안을 요구한다.

## Ⅰ. 개요 및 필요성

- 개요: 아키텍처 품질속성 평가
- 배경: 아키텍처 결정은 성능, 가용성, 보안, 유지보수성에 장기 영향을 주며 품질속성 간 트레이드오프와 설계 리스크를 만든다.
- 필요성: ATAM은 이해관계자 시나리오, utility tree, sensitivity point, tradeoff point로 구현 전 리스크와 변경 비용 발생 지점을 식별한다.

---

## Ⅱ. 구조 및 구성요소

```text
Business Driver -> Quality Attribute Scenario -> Utility Tree
  -> Architecture Approach -> Sensitivity Point
  -> Tradeoff Point -> Risk / Non-Risk -> Risk Theme
```

| 구성요소 | 역할 | 특이사항 |
|:---|:---|:---|
| Business Driver | 평가 배경과 우선순위 제공 | 매출, 규제, SLA, 일정 |
| Quality Attribute Scenario | 품질 요구를 측정 가능하게 표현 | stimulus, environment, response |
| Utility Tree | 품질속성 우선순위 구조화 | importance와 difficulty 평가 |
| Sensitivity/Tradeoff Point | 결정이 품질에 미치는 영향 식별 | 캐시, 복제, 동기화 구조 |
| Risk Theme | 반복 리스크를 묶어 개선 과제화 | action item과 owner 필요 |

> 요약: ATAM 구조는 비즈니스 동인, 품질속성 시나리오, utility tree, 아키텍처 결정 분석, 리스크 테마로 구성된다.

---

## Ⅲ. 동작원리 및 흐름도

```text
ATAM Planning -> Stakeholder Workshop
  -> Scenario Elicitation -> Utility Tree Prioritization
  -> Architecture Analysis -> Risk Theme
  -> Mitigation Plan
```

| 단계 | 처리 내용 | 검증 기준 |
|:---:|:---|:---|
| 1 | 평가 범위와 이해관계자 선정 | architect, dev, ops, security 포함 |
| 2 | 품질속성 시나리오 수집 | 측정값 포함, 예: p95 300ms |
| 3 | utility tree로 중요도·난이도 평가 | high/high 시나리오 우선 |
| 4 | 아키텍처 접근법과 민감점 분석 | tactic, pattern, dependency 확인 |
| 5 | 리스크·비리스크·트레이드오프 기록 | action item, owner, due date |

> 요약: ATAM은 워크숍에서 품질 시나리오를 우선순위화하고 아키텍처 선택 리스크와 트레이드오프를 도출한다.

|:---|:---|:---|:---|
| 구조 | 체크리스트 리뷰 | 시나리오 기반 분석 | 품질속성 충돌이 큰 시스템 |
| 비용/성능 | 성능 테스트는 구현 후 | ATAM은 설계 전 위험 도출 | 변경 비용이 큰 초기 설계 |
| 운영/위험 | 장애 후 아키텍처 수정 | 리스크 사전 식별 | SLA·규제 시스템 |
| 후속 | 분석 결과만 남음 | CBAM과 연계 가능 | 비용-편익 선택 필요 시 |

> 요약: ATAM은 구현 전 아키텍처 품질 리스크를 찾아야 하는 대형·고위험 시스템에 적합하다.

| 리스크 | 원인 | 대응 방안 | 확인 지표 |
|:---|:---|:---|:---|
| 시나리오 부실 | 측정값 없는 요구 | stimulus-response-measure 템플릿 사용 | 측정값 포함률 100% |
| 이해관계자 누락 | 운영·보안 관점 미포함 | stakeholder map 작성 | 핵심 역할 참여율 |
| 분석 형식화 | 리스크 후속 조치 없음 | action item, owner, due date 등록 | 조치 완료율 |
| 트레이드오프 미인식 | 단일 품질속성 집중 | utility tree와 tactic mapping | tradeoff point 수 |

> 요약: ATAM 리스크는 측정 가능한 시나리오, 이해관계자 참여, 후속 조치, 트레이드오프 기록으로 통제한다.

| 점검 항목 | 목표 기준 | 측정 방법 |
|:---|:---|:---|
| 시나리오 품질 | high priority 시나리오 20~30개 | workshop 산출물 |
| 리스크 식별 | risk와 tradeoff point 전수 기록 | ATAM report |
| 후속 실행 | action item 완료율 90% 이상 | Jira, ADR |
| 품질 검증 | RTO, p95, 오류율 목표 충족 | 테스트·운영 지표 |

> 요약: ATAM 성과는 시나리오 품질, 리스크 기록, 후속 실행률, 품질 목표 검증으로 판단한다.

## Ⅵ. 실무 적용 및 결론

**적용 방안 3개 (필수 — 단계별 또는 항목별):**
1. 아키텍처 검토 전 비즈니스 driver와 품질속성 시나리오를 수집하고 RTO 5분, p95 300ms, high CVE 0건처럼 측정값을 포함함.
2. utility tree에서 중요도와 구현 난이도가 모두 높은 시나리오를 우선 분석하고 tactic, pattern, dependency별 sensitivity point를 기록함.
3. tradeoff point와 risk theme을 ADR·Jira에 연결해 owner, due date, 검증 테스트를 지정하고 설계 변경 여부를 추적함.

**결론 (2줄):**
- 기술사 판단: 품질속성 간 충돌과 변경 비용이 큰 핵심 시스템은 ATAM으로 설계 전 리스크를 도출하고, 단순 CRUD 시스템은 체크리스트 리뷰로 충분함.
- 향후 방향: ATAM은 CBAM, ADR, Architecture Fitness Function, Observability 지표와 결합해 지속적 아키텍처 평가로 발전함.
