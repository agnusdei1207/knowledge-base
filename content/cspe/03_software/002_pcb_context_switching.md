# 📖 【암기용】 개념 완전 이해

> 목적: 이 개념을 처음 보는 사람도 완벽히 이해하게 만든다. 시험 답안 양식이 아니라, 이해를 위한 친절한 설명이다.

## 한눈에
- **개요**: **PCB(Process Control Block)**는 운영체제가 각 프로세스의 실행 상태를 기록해두는 **커널 자료구조**이고, **컨텍스트 스위칭(Context Switching)**은 CPU를 다른 프로세스로 넘길 때 현재 프로세스의 상태를 PCB에 저장하고 다음 프로세스의 상태를 PCB에서 복원하는 작업이다.
- **왜 필요한가**: CPU는 1개인데 실행 대기 중인 프로그램은 여러 개다. 이를 초 단위보다 훨씬 짧은 간격으로 번갈아 실행(시분할)해야 사람 눈에는 동시에 도는 것처럼 보인다. 교대할 때 "어디까지 실행했는지"를 저장해두지 않으면 나중에 이어서 실행할 수 없다 — 그 저장 창고가 PCB다.
- **핵심 직관**: 책을 읽다가(프로세스 A 실행) 심부름을 하러 가야 한다(인터럽트 발생). 읽던 페이지에 책갈피(PCB A 기록)를 꽂고 책을 덮는다. 돌아와서 다른 책(프로세스 B)을 펼치는데, 저번에 꽂아둔 책갈피(PCB B) 위치부터 이어서 읽는다. 이 "책갈피를 꽂고 책을 바꿔 드는" 전체 과정이 컨텍스트 스위칭이다.

## 핵심 용어 정리 (내부에 등장하는 것들)

| 용어 | 의미 | 비유 |
|:---|:---|:---|
| PCB(Process Control Block) | 프로세스 하나의 실행 상태 전부를 담은 커널 메모리 상의 자료구조 | 환자 차트 한 장 |
| 컨텍스트(Context) | "지금 어디까지, 어떤 값으로 실행 중이었나"를 나타내는 실행 문맥(PC+레지스터+상태 전체) | 책 읽던 위치 + 밑줄 친 내용 |
| PC(Program Counter) | 다음에 실행할 명령어의 메모리 주소를 가리키는 레지스터 | 책갈피가 꽂힌 페이지 번호 |
| 레지스터(Register) 상태 | CPU 내부의 임시 계산값(누산기·인덱스·스택 포인터 등) | 계산 중이던 메모 |
| 프로세스 상태(State) | New·Ready·Running·Blocked·Terminated 중 현재 상태 값 | 환자의 현재 상태(대기/진료중/퇴원) |
| 페이지 테이블 포인터(메모리 맵) | 이 프로세스의 가상 주소를 물리 주소로 바꾸는 매핑표의 시작 주소 | 이 환자 전용 병실 배치도 |
| 컨텍스트 스위칭(Context Switching) | 실행 중인 프로세스의 컨텍스트를 PCB에 저장하고, 다음 프로세스의 컨텍스트를 PCB에서 복원해 CPU에 얹는 작업 | 책갈피 꽂고 책 바꿔 들기 |
| 인터럽트(Interrupt) | 컨텍스트 스위칭을 유발하는 신호(타이머 만료, I/O 완료 등) | 심부름을 시키는 부름 |
| TLB(Translation Lookaside Buffer) | 가상-물리 주소 변환 결과를 캐싱해두는 소형 캐시 | 자주 찾는 주소 단축번호 목록 |
| 오버헤드(Overhead) | 컨텍스트 스위칭 동안 CPU가 사용자 연산을 전혀 못 하고 순수하게 낭비되는 시간 | 책 바꿔 드는 동안 독서를 못 하는 시간 |
| 타임 퀀텀(Time Quantum) | 프로세스 하나가 강제로 스위칭되기 전까지 허용된 CPU 점유 시간 | 한 사람당 발언 제한 시간 |

## 깊이 이해

### 왜 PCB가 필요했나 (배경)
- 시분할 운영체제(Time Sharing)는 "CPU를 나 혼자 독점하는 것처럼 보이게 하는 환상"을 만들어야 한다. 이를 위해 아주 짧은 간격으로 프로세스를 바꿔가며 실행해야 하는데, 바꿀 때마다 "직전에 어디까지, 어떤 값으로 계산하고 있었는지"를 완전히 잃어버리면 프로그램이 처음부터 다시 실행되는 것과 같아진다. 그래서 프로세스별로 이 정보를 담아두는 자료구조(PCB)가 필요했고, 이는 커널 메모리 영역에 프로세스 생성과 동시에 만들어진다.

### PCB의 구조와 저장 위치
- PCB는 사용자 프로그램이 직접 건드릴 수 없는 커널 공간(Kernel Space)의 메모리에 있다. 사용자 프로그램이 PCB를 마음대로 고칠 수 있다면 다른 프로세스인 척 위장하거나 우선순위를 조작할 수 있기 때문이다.
- 핵심 필드는 PC(다음 실행 위치), 레지스터 상태, 프로세스 상태, 페이지 테이블 포인터, 그리고 스케줄링에 쓰이는 우선순위·PID 등이다. 이 중 PC가 가장 중요한데, PC가 없으면 CPU가 "이 프로세스는 어느 명령어부터 이어서 실행해야 하는지" 전혀 알 수 없기 때문이다.

### 컨텍스트 스위칭이 실제로 일어나는 순서 — 수치로 이해
1. 타이머 인터럽트가 발생한다(예: 10ms마다 1회, 이 10ms가 타임 퀀텀이다).
2. 커널이 개입해 현재 프로세스 A의 PC·레지스터 값을 PCB_A에 기록한다.
3. A의 상태를 Running → Ready로 바꾸고 Ready 큐에 넣는다.
4. 스케줄러가 다음에 실행할 프로세스 B를 고른다.
5. PCB_B에서 PC·레지스터 값을 꺼내 CPU에 그대로 얹는다.
6. B의 페이지 테이블로 바뀌면서 TLB(주소 변환 캐시)가 무효화되어 다시 채워져야 한다.
7. CPU는 PCB_B의 PC가 가리키는 명령어부터 B의 실행을 재개한다.
- **구체 예시**: A가 `3 + 5`를 계산하다가 스위칭당했다고 하자. 레지스터에 있던 `3`과 `5`가 PCB_A에 저장된다. B가 CPU를 차지해 같은 레지스터에 자신의 값을 채워 쓴다. 다시 A 차례가 오면 PCB_A에서 `3`과 `5`를 복원해 CPU 레지스터에 넣고, 끊겼던 덧셈을 그대로 이어간다.

### 오버헤드를 수치로 보기 — 왜 타임 퀀텀 크기가 중요한가
- 컨텍스트 스위칭 자체는 실제 리눅스 환경에서 대략 수 마이크로초(μs) 단위로 걸린다(레지스터 저장/복원 자체는 빠르고, TLB·캐시가 식으면서 발생하는 간접 비용이 더 크다).
- 타임 퀀텀을 1ms로 아주 짧게 잡으면, 스위칭 비용이 5μs라 해도 1,000μs 중 5μs, 즉 약 0.5%가 낭비다. 그런데 퀀텀을 0.01ms(10μs)로 지나치게 줄이면 스위칭 비용 5μs가 실행 시간 10μs의 50%를 잡아먹어 CPU가 일은 안 하고 책갈피만 꽂았다 뺐다 하는 **스레싱(Thrashing)**이 발생한다. 반대로 퀀텀을 100ms로 늘리면 스위칭 비용 비중은 0.005%로 줄지만, 프로세스 하나가 100ms 동안 독점해 마우스 클릭 같은 즉각 반응이 느려진다. 그래서 실무 스케줄러는 보통 10ms~100ms 사이에서 타임 퀀텀을 정한다.

### 비유와 흔한 오해
- **비유**: 병원 회진. 의사(CPU)가 1번 환자(프로세스 A)의 차트(PCB_A)를 보고 진료한 뒤 차트에 오늘 소견을 적어두고, 2번 환자 침대로 가서 2번 차트(PCB_B)를 펼쳐 지난 소견부터 이어 진료한다. 차트가 없으면 의사는 매번 환자가 누구인지, 어디까지 치료했는지부터 새로 물어야 한다.
- **오해**: 컨텍스트 스위칭 중에도 CPU가 뭔가 유용한 일을 한다고 착각하기 쉽다. 아니다 — 스위칭하는 동안 CPU는 사용자 프로그램 연산을 단 1건도 처리하지 못하는 **100% 순수 오버헤드**다. 그래서 스위칭 자체는 자주 일어날수록 무조건 나쁘고, 다만 응답성을 위해 어쩔 수 없이 감수하는 비용이다.

## 연결 개념
- **인터럽트(Interrupt)**: 컨텍스트 스위칭을 유발하는 방아쇠다. 타이머 인터럽트(할당 시간 만료)나 I/O 인터럽트(디스크 읽기 완료)가 터져야 커널이 개입해 교대를 지시한다.
- **프로세스 생명주기(003)**: 컨텍스트 스위칭은 상태 전이(Running→Ready, Running→Blocked)가 실제로 일어나는 메커니즘이다. PCB의 상태 필드가 바로 이 전이를 기록한다.
- **스레드(001)**: 프로세스 전체를 바꾸는 컨텍스트 스위칭은 페이지 테이블(메모리 맵)이 통째로 바뀌어 TLB를 모두 비워야 해서 무겁다. 반면 같은 프로세스 안 스레드끼리 교체(TCB 교환)는 주소 공간이 그대로라 TLB·캐시를 유지한 채 훨씬 가볍게 끝난다.
- **프로세스 스케줄링(004)**: "다음에 실행할 프로세스를 무엇으로 고를지" 정하는 정책이 스케줄링이고, 컨텍스트 스위칭은 그 선택을 실제로 CPU에 적용하는 집행 단계다.

# 📝 【답안용】 시험 답안 템플릿

> 목적: 시험장에서 25분에 그대로 쓰는 답안 양식. 작성방식(추상표현 금지·수치·도식·문제유형 전환)을 엄격히 지킨다.
> 핵심: 이 시험은 정보를 많이 나열하는 시험이 아니라, 문제 신호어에서 출제자 의도를 읽고 핵심 논점을 선별해 쓰는 시험이다.

## 핵심 인사이트 (3줄 요약)

> 1. **본질**: PCB는 운영체제가 프로세스 상태(문맥)를 관리하기 위한 커널 자료구조이며, 컨텍스트 스위칭은 CPU 점유권을 다른 프로세스로 넘길 때 이 PCB를 저장하고 복원하는 일련의 메커니즘이다.
> 2. **가치**: 시분할 다중 프로그래밍(Time-Sharing) 환경을 구현하여 사용자에게 여러 프로그램이 동시에 실행되는 듯한 병행성(Concurrency)을 제공한다.
> 3. **판단 포인트**: 컨텍스트 스위칭은 순수 오버헤드(Overhead)이므로, 캐시 플러시(TLB) 패널티를 줄이기 위한 스레드 기반 스위칭과의 비용(Cost) 차이를 도식으로 대조해야 한다.

## 출제 의도 및 답안 포인트

| 출제 의도 | 반드시 짚을 핵심 | 감점 회피 포인트 |
|:---|:---|:---|
| 시분할 OS의 핵심 제어 구조 이해 | PCB의 핵심 구성 요소(PC, 레지스터, 포인터) | PCB가 사용자 공간이 아닌 '커널 공간(RAM)'에 적재됨을 누락하는 오류 |
| 스위칭 오버헤드의 실체와 최적화 방안 | 레지스터 저장/복원 + TLB/캐시 Flush 지연 시간 | 문맥 교환 동안 CPU가 유용한 작업을 수행한다고 착각하는 서술 |

> 요약: 스위칭은 멀티태스킹을 위한 필수 불가결한 멈춤(Pause)이다. 이 멈춤 시간을 얼마나 찰나로 깎아내느냐가 커널 엔지니어링의 핵심이다.

## Ⅰ. 개요 및 필요성

- 정의: PCB(Process Control Block)는 프로세스의 메타데이터(상태, 레지스터 등)를 저장하는 커널 자료구조이며, 컨텍스트 스위칭은 CPU가 현재 문맥을 PCB에 저장하고 새 문맥을 적재하는 교환 과정
- 배경: CPU 자원은 단일(Single)인 반면 실행 대기 중인 프로세스는 다수이므로, 공평한 자원 할당과 병행성(Concurrency) 보장을 위한 시분할 교대 메커니즘 필수
- 필요성: 인터럽트나 시스템 콜 발생 시 이전 작업의 연속성(어디까지 실행했는지)을 완벽히 보장하여 상태 유실 없이 작업을 재개하기 위함

## Ⅱ. PCB 구성요소 및 컨텍스트 스위칭 흐름도

```text
[ 프로세스 A 실행 중 ] -> 🚨 타이머 인터럽트 발생 (할당 시간 만료)

1. [ 상태 저장 ] : CPU 내부의 PC, 레지스터 값들을 -> [ PCB_A ] 에 기록 (커널 RAM)
2. [ 상태 전이 ] : 프로세스 A의 상태를 Running -> Ready 로 변경
3. [ 스케줄러 ] : 다음 실행할 프로세스 B를 큐(Queue)에서 선택
4. [ 상태 복원 ] : [ PCB_B ] 의 데이터를 읽어와 -> CPU 레지스터와 PC 덮어쓰기
5. [ 캐시 플러시 ]: 프로세스 B의 메모리 맵(MMU) 갱신 및 TLB(주소 변환 캐시) 초기화 

[ 프로세스 B 실행 재개 ] (PCB_B의 PC가 가리키는 코드 라인부터)
```

| PCB 주요 구성요소 | 역할 및 저장 내용 | 시스템 제어 영향 |
|:---|:---|:---|
| **프로그램 카운터 (PC)** | 이 프로세스가 중단된 지점(다음 실행할 명령어 주소) | 복원 시 가장 핵심이 되는 실행 지표 |
| **레지스터 세트 (Registers)** | Accumulator, Index, Stack Pointer 등 임시 계산값 | 연산의 연속성 보장 |
| **메모리 맵 포인터** | 해당 프로세스의 페이지 테이블(Page Table) 시작 주소 | 가상 주소 공간 분리 및 보안 보장 |
| **프로세스 상태 (State)** | New, Ready, Running, Blocked(대기), Terminated | 스케줄러 큐(Queue) 이동의 판단 근거 |

> 요약: 인터럽트가 터지면 커널이 난입해 A의 머릿속(레지스터)을 사진 찍어 차트(PCB)에 박제하고, B의 차트를 꺼내 CPU 머리에 덮어씌우는 릴레이 바통 터치다.

## Ⅲ. 프로세스 스위칭 vs 스레드 스위칭 (오버헤드 심화 대조)

컨텍스트 스위칭은 CPU가 사용자 연산을 1비트도 하지 않는 100% 버려지는 낭비(Overhead)다.

| 구분 | 프로세스 컨텍스트 스위칭 (Heavy-weight) | 스레드 컨텍스트 스위칭 (Light-weight) |
|:---|:---|:---|
| 자원 공유 | 서로 다른 가상 주소 공간을 가짐 (격리) | 동일한 주소 공간(Code/Data/Heap)을 완벽히 공유 |
| 교체 대상 장부 | **PCB (Process Control Block)** 전체 교체 | **TCB (Thread Control Block)** (스택과 레지스터만) 교체 |
| **TLB 및 캐시 붕괴** | 페이지 테이블 포인터가 통째로 바뀌므로, 기존 MMU의 **TLB(주소 캐시)를 전부 Flush(백지화)** 해야 함. 이후 콜드 스타트(Cold Miss) 극심 | 동일 프로세스 내부 이동이므로 **TLB와 L1/L2 캐시를 그대로 유지(Warm)**. 스위칭 지연이 압도적으로 낮음 |

> 요약: 스레드 교환은 그냥 작업복만 갈아입는 거지만, 프로세스 교환은 공장 건물 자체를 옮기는 것이라 머릿속(TLB)을 다 비워야 하는 치명상을 동반한다.

## Ⅳ. 극복해야 할 시스템 병목 및 통제 방안

| 리스크 요인 | 발생 시나리오 | 아키텍처 대응 방안 (운영체제 튜닝) |
|:---|:---|:---|
| 스위칭 스레싱 (Thrashing) | 스케줄러의 타임 퀀텀(Time Quantum, 할당 시간)을 너무 짧게 (예: 1ms) 설정 시, CPU가 연산보다 PCB 저장/복원에 시간을 다 써버려 전체 처리량 붕괴 | 라운드 로빈(RR) 스케줄링 시 타임 퀀텀을 스위칭 오버헤드 시간의 10배 이상(보통 10ms~100ms)으로 설정하여 스위칭 비용을 10% 미만으로 희석 |
| 캐시 오염 (Cache Pollution) 방어 | 멀티 코어 환경에서 프로세스를 1번 코어에서 빼서 2번 코어로 보내면(Migration), 2번 코어의 캐시는 텅 비어있어 속도 폭락 | **CPU 선호도(Affinity) 할당**: 특정 프로세스를 무조건 1번 코어에서만 스위칭되도록(Pinning) 묶어두어 L2/L3 캐시 재사용(Warm Cache) 극대화 |

> 요약: 스위칭을 너무 자주 하면 CPU가 짐 싸고 풀다가 하루가 다 간다. 스위칭 주기(Quantum)를 수학적으로 튜닝하고, 가급적 살던 코어(Affinity)에 계속 살게 하는 것이 정답이다.

## Ⅴ. 실무 적용 방안 및 결론

**적용 방안 3개:**
1. [Nginx의 비동기 이벤트 루프] Apache처럼 1요청 1프로세스(스레드)를 띄우면 1만 커넥션 시 C10K 스위칭 오버헤드로 서버가 뻗으므로, Nginx는 단일 스레드 안에서 `epoll`로 이벤트를 받아 PCB 스위칭 자체를 박멸하는 락 프리(Lock-free) 아키텍처 채택
2. [가상 스레드(Project Loom) 도입] Java 백엔드 시스템에서 I/O 블로킹 대기 시 OS 커널의 PCB 스위칭 비용을 내지 않기 위해, 사용자 공간(JVM) 내에서 힙(Heap)만 복사하며 초경량으로 교체하는 가상 스레드(Virtual Thread) 전환 설계
3. [인터럽트 코어 분산 (IRQ Affinity)] 고성능 네트워크 서버(10Gbps+) 운영 시, 쏟아지는 패킷 인터럽트로 코어 0번만 계속 스위칭 당하는 병목을 막기 위해, `smp_affinity`를 설정하여 NIC 인터럽트를 여러 코어로 분산(RSS/RPS)하여 스위칭 부하 분할

**결론:**
- 기술사 판단: 컨텍스트 스위칭은 시분할 OS라는 마술을 완성하기 위해 필연적으로 지불해야 하는 입장료다. 이 입장료(오버헤드)를 최소화하려는 투쟁의 역사가 바로 멀티 스레드, CPU 선호도(Affinity), 그리고 최근의 비동기 이벤트 루프와 가상 스레드의 탄생을 견인했다.
- 향후 방향: 하드웨어 진화 측면에서는 CPU 내부에 레지스터 세트(Register Window)를 통째로 여러 벌 물리적으로 탑재하여(예: SPARC 아키텍처, SMT/하이퍼스레딩), 램(PCB)에 저장할 필요 없이 단 1사이클 만에 물리적 스위치를 전환해버리는 'Zero-Cost Context Switch' 칩셋 기술로 진화 중이다.
