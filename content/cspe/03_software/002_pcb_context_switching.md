# 📖 【암기용】 개념 완전 이해

## 한눈에
- **PCB (Process Control Block)**: OS가 프로세스를 관리하기 위해 필요한 상태 정보를 담은 **'운전면허증/신분증'** 같은 자료구조.
- **컨텍스트 스위칭 (Context Switching)**: CPU가 다른 프로세스로 실행을 넘길 때, 현재 상태를 PCB에 저장하고 새로운 프로세스의 상태를 복구하는 **'인수인계'** 과정.
- **핵심 직관**: 여러 명의 고객을 응대하는 은행원이 상담을 멈추고 다음 고객으로 넘어갈 때, 이전 고객과의 상담 내용을 서류(PCB)에 적어두고 다음 서류를 꺼내는 행위.

## 깊이 이해
- **왜 저장하는가?**: CPU는 한 번에 하나의 프로세스만 실행 가능함. 시분할(Time Sharing) 시스템에서 실행 중이던 작업을 나중에 **정확히 멈춘 지점부터 재개**하려면 레지스터 상태, PC(Program Counter), 스택 포인터 등을 어딘가에 박제해둬야 함.
- **PCB의 저장 장소**: 일반 메모리가 아닌 커널 영역(Kernel Stack 등)의 보호된 공간에 위치함.
- **오버헤드 (The Cost)**: 컨텍스트 스위칭은 순수 관리 작업이므로 실제 계산 업무를 수행하지 않음. 이때 발생하는 시간 낭비를 오버헤드라 하며, 잦은 스위칭은 시스템 성능을 갉아먹는 '스레싱(Thrashing)'의 원인이 됨.
- **하드웨어의 도움**: 최근 CPU는 컨텍스트 스위칭 속도를 높이기 위해 레지스터 세트를 여러 개 두거나(Register Windowing), 하드웨어 스레드를 지원함.

## 연결 개념
- **프로세스 vs 스레드 (001)**: TCB(Thread Control Block)는 PCB보다 가벼운 서류임.
- **프로세스 상태 (003)**: Running -> Ready/Blocked로 바뀔 때 스위칭이 일어남.
- **인터럽트 (Interrupt)**: 컨텍스트 스위칭을 유발하는 가장 대표적인 트리거.

# 📝 【답안용】 시험 답안 템플릿

## 핵심 인사이트 (3줄 요약)
> 1. **본질**: PCB는 커널 내 프로세스 정보 저장소이며, 컨텍스트 스위칭은 이를 이용한 CPU 실행 권한의 원자적(Atomic) 교체 과정임.
> 2. **기술적 핵심**: 스위칭 시 발생하는 **TLB Flush와 캐시 미스**가 시스템 성능의 주된 병목이며, 이를 최소화하는 것이 OS 스케줄링의 목표임.
> 3. **진화**: 인터럽트 기반의 비자발적 스위칭에서, 최근에는 Virtual Thread 등을 활용한 협력적(Cooperative) 경량 스위칭으로 발전 중임.

## Ⅰ. 멀티태스킹의 핵심 기제, PCB와 컨텍스트 스위칭의 정의
- **PCB (Process Control Block)**: OS 커널이 각 프로세스를 제어하기 위해 유지하는 상태 정보 및 자원 관리용 데이터 구조체.
- **컨텍스트 스위칭 (Context Switching)**: CPU 점유권을 반납하는 프로세스의 문맥(State)을 PCB에 저장하고, 다음 실행할 프로세스의 문맥을 복원하는 제어권 전환 과정.

## Ⅱ. PCB의 내부 구조 및 주요 구성 요소

### 1. PCB 논리적 구조
```text
┌──────────────────────────────────────────┐
│              Process State               │ (Ready, Running, Blocked 등)
├──────────────────────────────────────────┤
│           Process ID (PID)               │ (고유 식별자)
├──────────────────────────────────────────┤
│        Program Counter (PC)              │ (다음 실행할 명령어 주소)
├──────────────────────────────────────────┤
│             Registers                    │ (CPU 레지스터 값 보존)
├──────────────────────────────────────────┤
│        Memory Management Info            │ (Page Table, Base/Limit Register)
├──────────────────────────────────────────┤
│          I/O Status & Files              │ (열린 파일 리스트, I/O 장치 정보)
├──────────────────────────────────────────┤
│         CPU Scheduling Info              │ (우선순위, 할당 시간)
└──────────────────────────────────────────┘
```

### 2. 주요 필드 상세 기술
| 필드명 | 기술적 역할 | 중요성 |
|:---:|:---|:---|
| **PID** | 프로세스 고유 식별 번호 | 프로세스 간 구분 및 관리의 기본 |
| **PC** | 다음에 실행될 명령의 메모리 주소 | 실행 중단 지점 복구의 핵심 |
| **CPU Registers** | ACC, Index, Stack Pointer 등 | 연산 도중의 데이터 보존 |
| **State** | 현재 프로세스의 생애주기 상태 | 스케줄링 결정의 근거 |

## Ⅲ. 컨텍스트 스위칭의 메커니즘과 동작 흐름

### 1. 전환 프로세스 (P1 -> P2 전환 예시)
1.  **Trigger**: 인터럽트(Interrupt) 또는 시스템 콜(System Call) 발생.
2.  **Save State**: P1의 PC, 레지스터 등을 PCB1에 저장 (Kernel Stack 활용).
3.  **Scheduling**: 스케줄러가 다음에 실행할 프로세스 P2 선택.
4.  **Restore State**: PCB2에서 P2의 상태 정보를 CPU 레지스터로 로드.
5.  **Resume**: P2의 PC가 가리키는 지점부터 실행 재개.

### 2. 하드웨어 관점의 비용 (Overhead)
- **Direct Cost**: 저장/복원 명령어 실행 시간.
- **Indirect Cost (Crucial)**: 
    - **TLB Flush**: 가상 주소 변환 캐시 초기화로 인한 메모리 접근 지연.
    - **Cache Pollution**: L1/L2 캐시에 로드된 이전 프로세스 데이터가 무효화되어 캐시 미스 급증.

## Ⅳ. 컨텍스트 스위칭 발생 사유 및 오버헤드 최소화 방안

- **발생 사유**:
    - **Multitasking**: 할당된 Time Quantum 만료 (Preemption).
    - **Interrupt**: I/O 완료, 타이머 만료 등 하드웨어 신호.
    - **System Call**: 프로세스가 OS에 자원 요청 후 대기(Blocked).

- **최소화 방안 (기술사 제언)**:
    - **스레드 활용**: 주소 공간을 공유하여 TLB Flush를 방지 (001 연계).
    - **적정 Time Quantum**: 너무 작으면 스위칭 빈발, 너무 크면 응답성 저하 (Tuning).
    - **Affinity**: CPU 친화도 설정을 통해 캐시 활용도 극대화.

## Ⅴ. 심화 비교: 프로세스 vs 스레드 문맥 전환

| 구분 | 프로세스 스위칭 | 스레드 스위칭 |
|:---:|:---|:---|
| **가상 메모리** | 페이지 테이블 교체 (비쌈) | 공유 (교체 불필요) |
| **TLB/Cache** | 전체 Flush / Cold Cache 발생 | 유지 / Warm Cache 가능 |
| **수행 속도** | 느림 | 매우 빠름 |

## Ⅵ. 실무적 시사점 및 결론
- **결론**: 컨텍스트 스위칭은 멀티태스킹 구현을 위한 '필요악(Necessary Evil)'이며, 고성능 시스템 설계를 위해서는 이 오버헤드를 제어하는 능력이 필수적임.
- **최신 경향**: 클라우드 네이티브 환경에서는 수많은 마이크로서비스 간 스위칭 부하를 줄이기 위해 **eBPF** 기반의 관측 기술이나 **Kernel-bypass (DPDK)** 기술을 도입하여 문맥 전환 없이 유저 영역에서 고속 패킷 처리를 수행하기도 함.
