# 📖 【암기용】 개념 완전 이해

## 한눈에
- **개요**: CPU가 실행 중인 프로세스를 바꾸기 위해 기존 상태(PCB)를 저장하고 새 상태를 적재하는 과정
- **왜 필요한가**: CPU는 1개인데 여러 프로그램이 동시에 도는 것처럼 보여야 하므로(다중 프로그래밍), 상태를 빠르게 교체하는 메커니즘이 필수적이다.
- **핵심 직관**: 공부(A과목)하다가 전화(인터럽트)가 오면, 책갈피를 꽂고(PCB 저장) 전화를 받은 뒤 다시 책갈피 꽂은 곳부터 공부(복구)하는 것과 같다.

## 핵심 용어 정리

| 용어/표기 | 의미 | 비유·예 |
|:---|:---|:---|
| PCB (Process Control Block) | 운영체제가 프로세스 상태를 기록해두는 자료구조 | 작업자의 진행 상황을 적은 수첩 |
| 컨텍스트 스위칭 (Context Switching) | CPU 레지스터 상태를 PCB에 저장/복원하는 작업 | 교대 근무자의 인수인계 |
| 디스패처 (Dispatcher) | 스케줄러가 선택한 프로세스에게 실제 CPU를 넘겨주는 모듈 | 교대 신호를 주고 작업자를 교체하는 반장 |

## 깊이 이해
- **배경·문제의식**: 시분할 시스템에서는 CPU 할당 시간이 끝나면 다른 프로세스에게 CPU를 넘겨야 한다. 이때 이전 작업이 어디까지 진행됐는지 레지스터 값, PC(Program Counter) 등을 저장해두지 않으면 이어서 실행할 수 없다.
- **작동 원리**: 프로세스 P0 실행 중 인터럽트(Timer 등) 발생 → OS 진입 → P0의 상태를 PCB0에 저장 → 스케줄러가 P1 선택 → PCB1에서 상태 복원 → P1 실행. 이 일련의 과정 동안 CPU는 실제 유용한 사용자 작업을 하지 못하므로 오버헤드가 발생한다.
- **비유**: CPU는 요리사 1명이다. 요리 2개(P0, P1)를 동시에 하려면, P0을 젓다가(실행) 냄비를 내려놓고 어디까지 했는지 적어두고(PCB 저장), P1 냄비를 올리고 레시피를 다시 확인(PCB 복구)해야 한다.
- **구체 예시**: 타이머 인터럽트가 10ms마다 발생하면 초당 100번 스위칭이 일어난다. 만약 스위칭에 100μs가 걸리면, 1초 중 10ms(1%)가 스위칭 오버헤드로 날아간다.
- **흔한 오해·주의점**: 컨텍스트 스위칭 시간은 CPU 입장에서 100% 오버헤드다. 따라서 멀티태스킹을 늘릴수록(스레드 수를 무한정 늘릴수록) 이 오버헤드가 커져서 어느 순간부터 시스템 전체 성능이 오히려 급락(스레싱)하게 된다.

## 연결 개념
- 프로세스 vs 스레드 (001 참조) — 스레드 간 전환은 PCB가 아닌 TCB 교체로 더 가벼움
- 스케줄링 (004 참조) — 누구를 교체할지 결정하는 알고리즘
- 프로세스 스레싱 (015 참조) — 잦은 스위칭으로 인한 성능 저하

# 📝 【답안용】 시험 답안 템플릿

## 핵심 인사이트 (3줄 요약)

> 1. **본질**: PCB는 프로세스 상태 정보를 담는 운영체제 자료구조이며, 컨텍스트 스위칭은 CPU가 프로세스를 교체할 때 PCB를 저장하고 적재하는 일련의 과정이다.
> 2. **가치**: 시분할 다중 프로그래밍(Multi-programming)과 멀티태스킹을 가능하게 하는 핵심 메커니즘이다.
> 3. **판단 포인트**: 컨텍스트 스위칭은 순수 오버헤드이므로, 시스템 설계 시 스레드 풀, 비동기 I/O 등을 통해 이 스위칭 횟수와 지연을 통제해야 한다.

## 출제 의도 및 답안 포인트

| 출제 의도 | 반드시 짚을 핵심 | 감점 회피 포인트 |
|:---|:---|:---|
| 운영체제의 프로세스 상태 관리 및 전환 메커니즘 이해 | PCB 주요 항목(PC, Register, State), 디스패처 역할 | PCB 항목만 나열하고 스위칭 흐름 누락 |
| 멀티태스킹 오버헤드 및 시스템 병목 판단 | 스위칭 오버헤드(Cache, TLB Flush), 스레싱(Thrashing) 위험 | 스위칭을 유용한 작업으로 서술 |
| 성능 최적화 방안 제시 | 스레드 풀 적용, 비동기 논블로킹 전환 | 단순 "성능이 좋다"는 추상 표현 |

> 요약: 컨텍스트 스위칭의 필수 불가결함과 오버헤드를 인지하고, 이를 최소화하기 위한 아키텍처적 대응을 제시한다.

---

## Ⅰ. 개요 및 필요성

- 개요: 다중 프로그래밍 환경에서 CPU가 현재 프로세스 상태를 PCB에 저장하고 다음 프로세스 상태를 적재하는 전환 과정
- 배경: CPU 하나로 여러 프로세스를 동시 실행하는 시분할 시스템(Time Sharing System)에서 공평한 CPU 할당 메커니즘 필요
- 필요성: 인터럽트 발생이나 I/O 대기 시 CPU 유휴 시간을 줄이고 활용도를 극대화하기 위해 상태 복구 체계(PCB) 필수

---

## Ⅱ. 구조 및 구성요소

```text
OS 커널 영역 (Kernel Space)
  |-- PCB_A: [ PID=1, State=Ready, PC=0x10, Registers=..., Mem Info=... ]
  |-- PCB_B: [ PID=2, State=Running, PC=0x20, Registers=..., Mem Info=... ]
```

| 구성요소 | 역할 | 특이사항 |
|:---|:---|:---|
| 프로세스 식별자 (PID) | 프로세스 고유 번호 식별 | - |
| 프로세스 상태 (State) | 생성, 준비, 실행, 대기, 종료 상태 기록 | 스케줄러가 참조 |
| 프로그램 카운터 (PC) | 다음 실행할 명령어의 주소 저장 | 복원 시 가장 중요 |
| 레지스터 (Registers) | 누산기, 인덱스 레지스터 등 CPU 상태값 | 연산 연속성 보장 |
| 메모리 관리 정보 | Base/Limit 레지스터, 페이지 테이블 포인터 | 메모리 보호 및 주소 변환 |

> 요약: PCB는 프로세스의 식별, 상태, 실행 위치, 메모리 정보를 담아 스위칭 시 끊김 없는 복원을 보장한다.

---

## Ⅲ. 동작원리 및 흐름도

```text
프로세스 P0 실행 -> 인터럽트/시스템콜 발생 -> OS 개입 (P0 정지)
  -> P0 상태를 PCB0에 저장 -> 스케줄러가 P1 선택 (디스패처 호출)
  -> PCB1에서 P1 상태 복원 -> 프로세스 P1 실행 시작
```

- 1단계 [실행 중단 및 진입]: 타이머 인터럽트나 I/O 요청 등으로 프로세스 P0의 사용자 모드 실행 중단 및 커널 모드 전환
- 2단계 [상태 저장]: P0의 현재 PC 및 레지스터 값을 커널 내 PCB0에 저장
- 3단계 [대상 선정 및 적재]: 스케줄러가 준비 큐에서 P1을 선택하고, 디스패처가 PCB1의 값을 CPU 레지스터와 PC로 적재
- 4단계 [실행 재개]: 모드 전환 후 P1이 이전 중단점부터 실행 재개

> 요약: 기존 상태 저장 -> 스케줄러의 다음 대상 선정 -> 새 상태 적재의 과정을 거치며, 이 구간은 순수 커널 오버헤드 영역이다.

---

## Ⅳ. 특징

- 순수 오버헤드(Overhead): 컨텍스트 스위칭 시간 동안 CPU는 사용자 애플리케이션의 유용한 작업을 수행하지 못함
- 캐시 오염(Cache Pollution) 유발: 프로세스 교체 시 기존 L1/L2 캐시 및 TLB 데이터가 무효화(Flush)되어 초기 성능 저하 유발
- 아키텍처 의존성: 레지스터 수, 메모리 관리 복잡도 등 하드웨어 아키텍처에 따라 스위칭 소요 시간이 다름

> 요약: 잦은 스위칭은 캐시 초기화와 메모리 병목을 유발하여 시스템 전체의 유효 처리량(Throughput)을 하락시킨다.

---

## Ⅴ. 심화 비교 및 적용 판단

| 비교 축 | 프로세스 컨텍스트 스위칭 | 스레드 컨텍스트 스위칭 | 선택 기준 |
|:---|:---|:---|:---|
| 전환 대상 | PCB 전체 (주소 공간 포함) | TCB (스택, PC 등 일부) | - |
| 메모리 비용 | TLB 및 캐시 Flush 발생 (비용 고) | 메모리 공간 유지 (비용 저) | 지연 민감도에 따른 구조 선택 |
| 활용 환경 | 독립성이 요구되는 멀티프로세스 | 응답성이 요구되는 고성능 서버 | 장애 격리(프로세스) vs 성능(스레드) |

> 요약: 컨텍스트 스위칭 최적화를 위해서는 프로세스 전환을 스레드 전환으로 대체하거나 전환 빈도 자체를 줄여야 한다.

**리스크·대응 (기본은 불릿):**
- 캐시 스래싱(Cache Thrashing): 잦은 스위칭으로 캐시 미스율 급증 → CPU 친화도(Affinity) 설정으로 프로세스를 특정 코어에 고정 (지표: L1 Cache Hit Rate)
- 프로세스 스레싱(Thrashing): 다중 프로그래밍 정도가 너무 높아 스위칭 시간 > 실행 시간 역전 → 동시 실행 프로세스 수(Multi-programming degree) 조절 (지표: CPU User Time vs System Time 비율)

**도입 후 점검 지표 (기본은 불릿):**
- 성능/효율: 초당 컨텍스트 스위칭 횟수(cs per sec), 디스패치 지연 시간
- 품질/운영: CPU 커널 모드 점유율(sys %), 사용자 모드 점유율(user %)

## Ⅵ. 실무 적용 및 결론

**적용 방안 3개 (필수 — 단계별 또는 항목별):**
1. 스레드 풀(Thread Pool) 운영: 대규모 웹 트래픽 처리 시, 무한정 프로세스/스레드 생성 대신 고정된 풀을 운용해 스위칭 폭증 방지
2. 비동기 I/O 및 이벤트 루프: I/O 대기(Block)에 따른 스위칭을 없애기 위해 epoll, kqueue 기반 비동기 Non-Blocking I/O 아키텍처 적용
3. NUMA 및 코어 친화도 최적화: `taskset` 등의 도구로 특정 프로세스를 동일 코어에 묶어두어 스위칭 시 캐시 활용도 극대화

**결론 (2줄):**
- 기술사 판단: 컨텍스트 스위칭은 멀티태스킹의 필수 악이므로, 개발/운영자는 `vmstat` 등을 통해 'cs' 지표를 모니터링하고 시스템 과부하를 선제 판단해야 한다.
- 향후 방향: 최근 OS는 User-level 스레드(가상 스레드, 코루틴)를 지원하여, 커널 개입 없는 극저지연 컨텍스트 스위칭으로 진화하고 있다.
