# 📖 【암기용】 개념 완전 이해

## 한눈에
- **개요**: PCB(Process Control Block)는 프로세스의 실행 상태를 담는 **커널 자료구조**이고, 컨텍스트 스위칭은 CPU가 실행 대상을 바꿀 때 현재 상태를 PCB에 **저장**하고 다음 상태를 **복원**하는 과정이다.
- **왜 필요한가**: CPU는 1개인데 여러 프로세스가 동시에 도는 것처럼 보이려면(다중 프로그래밍), 중단된 지점을 완벽히 기억했다가 되살리는 상태 저장·복원 메커니즘이 있어야 한다.
- **핵심 직관**: 공부(A과목)하다 전화(인터럽트)가 오면, 책갈피를 꽂고(PCB 저장) 전화를 받은 뒤 그 책갈피부터 다시 이어 읽는 것(복원)과 같다.

## 핵심 용어 정리 (내부에 등장하는 것들)

프로세스·주소 공간·TCB 개념은 001에서 세웠으므로, 여기서는 "상태를 어디에 어떻게 담고 바꾸는가"의 용어를 정리한다.

| 용어/표기 | 의미 | 비유·예 |
|:---|:---|:---|
| 문맥(Context) | 프로세스 재개에 필요한 상태 전부 = PC·레지스터·메모리 정보 (상위 키워드) | 하던 일을 이어가는 데 필요한 모든 메모 |
| PCB (Process Control Block) | 프로세스별 문맥을 저장하는 커널 자료구조 | 프로세스 관리 대장 |
| PID (Process ID) | 프로세스 고유 식별 번호 | 대장의 일련번호 |
| 프로그램 카운터 (PC) | 다음에 실행할 명령어의 주소 | 책갈피(몇 페이지까지 읽었나) |
| 레지스터 (Registers) | 연산 중간값을 담은 CPU 내부 저장소 | 계산 중인 암산 값 |
| 컨텍스트 스위칭 (Context Switching) | 실행 프로세스 A의 문맥을 저장하고 B의 문맥을 복원하는 작업 | 교대 근무 인수인계 |
| 인터럽트 (Interrupt) | 실행을 중단시키는 하드웨어·소프트웨어 신호 | 갑자기 걸려온 전화 |
| 모드 전환 (Mode Switch) | 유저 모드 ↔ 커널 모드 특권 수준 변경 | 일반 창구 → 관리자실 출입 |
| 디스패처 (Dispatcher) | 스케줄러가 고른 프로세스에 실제로 CPU를 넘기는 모듈 | 교대 신호를 주는 반장 |
| 스케줄러 (Scheduler) | 다음에 실행할 프로세스를 고르는 정책 모듈 (상세는 004) | "다음 근무자 누구" 결정자 |
| TLB (Translation Lookaside Buffer) | 가상→물리 주소 변환을 캐싱하는 하드웨어 | 자주 쓰는 주소 단축 메모 |
| 캐시 오염 (Cache Pollution) | 프로세스 교체로 캐시·TLB 내용이 무효화되는 현상 | 교대하며 책상 위 자료가 뒤섞임 |
| 오버헤드 (Overhead) | 유용한 작업이 아닌 관리에 소모되는 비용 | 인수인계에 쓰는 순수 낭비 시간 |

## 깊이 이해
- **배경·문제의식**: 시분할 시스템은 타임 슬라이스가 끝나거나 I/O 대기가 생기면 CPU를 다른 프로세스에 넘긴다. 이때 중단된 프로세스가 "어디까지, 무슨 값으로" 실행했는지(PC·레지스터)를 저장해두지 않으면 재개가 불가능하다. 그 상태 보관소가 PCB다.
- **작동 원리(어떻게+왜)**: P0 실행 중 인터럽트 발생 → 모드 전환으로 커널 진입 → P0 문맥을 PCB0에 저장 → 스케줄러가 P1 선택 → 디스패처가 PCB1의 값을 CPU 레지스터·PC로 복원 → P1 재개. 이 구간 동안 CPU는 사용자 작업을 전혀 못 하므로 **순수 오버헤드**다. 스레드 전환은 001의 TCB만 교체하고 주소 공간이 유지돼 더 싸다.
- **비유**: CPU는 요리사 1명이다. 요리 2개를 번갈아 하려면 한 냄비를 내려놓고 어디까지 했는지 적어두고(PCB 저장) 다른 냄비를 올려 레시피를 다시 확인(PCB 복원)해야 한다. 이 왔다갔다 자체는 요리가 아니라 낭비다.
- **구체 예시**: 타이머 인터럽트가 10ms마다 발생하면 초당 100회 전환이 일어난다. 전환 1회가 실제로는 캐시·TLB 재적재까지 포함해 수 µs가 들며, `vmstat`의 `cs` 열로 초당 전환 수를, `sys%`로 커널 소모 비율을 관측한다.
- **흔한 오해·주의점**: 컨텍스트 스위칭 시간은 CPU 관점 100% 낭비다. 그래서 스레드를 무한정 늘리면 어느 지점부터 전환 오버헤드가 실행 시간을 압도해 처리량이 급락한다(스레싱, 015). "많은 병렬 = 빠름"이 아니라, 코어 수와 워크로드 특성에 맞춘 적정 동시성이 핵심이다.

## 연결 개념
- 프로세스 vs 스레드 (001 참조) — 스레드 전환은 PCB가 아닌 TCB 교체로 더 경량
- 프로세스 스케줄링 (004 참조) — 전환 시 누구를 고를지 결정하는 정책
- 프로세스 스레싱 (015 참조) — 잦은 전환이 유발하는 성능 급락

# 📝 【답안용】 시험 답안 템플릿

## 핵심 인사이트 (3줄 요약)

> 1. **본질**: PCB는 프로세스 문맥을 담는 커널 자료구조, 컨텍스트 스위칭은 그 문맥을 저장·복원해 실행 대상을 교체하는 과정임.
> 2. **가치**: 시분할 다중 프로그래밍과 멀티태스킹을 성립시키는 핵심 메커니즘임.
> 3. **판단 포인트**: 전환은 순수 오버헤드이므로 스레드 풀·비동기 I/O·코어 친화도로 전환 횟수와 지연을 통제해야 함.

## 출제 의도 및 답안 포인트

| 출제 의도 | 반드시 짚을 핵심 | 감점 회피 포인트 |
|:---|:---|:---|
| 프로세스 상태 관리·전환 메커니즘 이해 | PCB 주요 항목(PC·레지스터·상태), 디스패처 역할 | PCB 항목 나열만 하고 전환 흐름 누락 |
| 멀티태스킹 오버헤드·병목 판단 | TLB·캐시 플러시, 스레싱 위험 | 전환을 유용한 작업으로 오해 서술 |
| 성능 최적화 방안 제시 | 스레드 풀, 비동기 논블로킹, 코어 친화도 | 추상적 "성능 향상" 단정 |

> 요약: 전환의 필수성과 순수 오버헤드성을 함께 인지하고, 전환 최소화를 위한 아키텍처적 대응을 제시함.

## Ⅰ. 개요 및 필요성

- 개요: 다중 프로그래밍에서 CPU가 현재 프로세스 문맥을 PCB에 저장하고 다음 프로세스 문맥을 복원하는 전환 과정임
- 배경: CPU 1개로 여러 프로세스를 번갈아 실행하는 시분할 시스템에서, 중단점을 완벽히 복구할 상태 보관 체계가 요구됨
- 필요성: 인터럽트·I/O 대기 시 CPU 유휴를 줄여 활용도를 높이려면 PCB 기반 저장·복원이 필수임

---

## Ⅱ. 구조 및 구성요소

```text
커널 공간(PCB 테이블)
  -> PCB_A [ PID / State=Ready / PC / Registers / Mem정보 ]
  -> PCB_B [ PID / State=Running / PC / Registers / Mem정보 ]
```

| 구성요소 | 역할 | 특이사항 |
|:---|:---|:---|
| PID | 프로세스 고유 식별 | 자원·권한 매핑 기준 |
| 프로세스 상태 | Ready·Running·Blocked 등 기록(상세는 003) | 스케줄러가 참조 |
| 프로그램 카운터(PC) | 다음 실행 명령어 주소 | 복원 시 재개 지점 |
| 레지스터 집합 | 누산기·인덱스 등 CPU 상태값 | 연산 연속성 보장 |
| 메모리 관리 정보 | Base/Limit·페이지 테이블 포인터 | 주소 변환·메모리 보호 |

> 요약: PCB는 식별·상태·재개 지점·메모리 정보를 담아 전환 후 끊김 없는 복원을 보장함.

---

## Ⅲ. 동작원리 및 흐름도

```text
P0 실행(유저 모드) -> 인터럽트/시스템콜 -> 커널 진입(모드 전환, P0 정지)
  -> P0 문맥을 PCB0에 저장 -> 스케줄러 P1 선택 -> 디스패처가 PCB1 복원
  -> 모드 복귀 -> P1 중단점부터 재개
```

- 1단계 [중단·진입]: 타이머 인터럽트나 I/O 요청으로 P0 실행을 멈추고 모드 전환으로 커널에 진입함
- 2단계 [상태 저장]: P0의 PC·레지스터 값을 커널 내 PCB0에 저장함
- 3단계 [선정·복원]: 스케줄러가 준비 큐에서 P1을 고르고 디스패처가 PCB1 값을 CPU에 적재함
- 4단계 [재개]: 유저 모드로 복귀해 P1이 이전 중단점부터 실행을 이어감

> 요약: 저장 → 선정 → 복원의 세 구간을 거치며, 이 전 구간은 사용자 작업이 정지된 순수 커널 오버헤드 영역임.

---

## Ⅳ. 특징

- 순수 오버헤드: 전환 구간 동안 CPU는 사용자 애플리케이션의 유용한 작업을 수행하지 못함
- 캐시·TLB 무효화: 프로세스 교체 시 L1/L2 캐시와 TLB 내용이 무효화돼 재적재 전까지 지연이 가중됨
- 아키텍처 의존성: 레지스터 수·메모리 관리 복잡도 등 하드웨어에 따라 전환 소요 시간이 달라짐
- 스레드 대비 고비용: 프로세스 전환은 주소 공간 교체를 동반해, TCB만 바꾸는 스레드 전환보다 무거움

## Ⅴ. 심화 비교 및 적용 판단

| 구분 | 프로세스 컨텍스트 스위칭 | 스레드 컨텍스트 스위칭 | 선택 기준 |
|:---|:---|:---|:---|
| 교체 대상 | PCB 전체(주소 공간 포함) | TCB(스택·PC·레지스터) | 지연 민감도 |
| 메모리 비용 | TLB·캐시 플러시 발생(고) | 주소 공간 유지(저) | 전환 빈도 |
| 적합 환경 | 격리가 필요한 멀티프로세스 | 응답성이 필요한 고성능 서버 | 격리 vs 성능 |

> 요약: 전환 최적화는 프로세스 전환을 스레드 전환으로 대체하거나 전환 빈도 자체를 줄이는 두 방향으로 접근함.

**리스크·대응 (불릿):**
- 캐시 스래싱: 잦은 전환으로 캐시 미스 급증 → 코어 친화도(Affinity)로 프로세스를 특정 코어에 고정 (지표: L1 Cache Hit Rate)
- 프로세스 스레싱: 다중 프로그래밍 정도 과다로 전환 시간이 실행 시간을 역전 → 동시 실행 수 조절 (지표: sys% vs user% 비율)

**점검 지표 (불릿):**
- 성능: 초당 컨텍스트 스위칭 수(`cs`), 디스패치 지연
- 운영: 커널 모드 점유율(sys%), 유저 모드 점유율(user%)

---

## Ⅵ. 실무 적용 및 결론

**적용 방안 3개:**
1. 스레드 풀 운영: 대규모 트래픽에서 무제한 생성 대신 고정 풀로 전환 폭증을 방지함
2. 비동기 논블로킹 I/O: epoll·kqueue 기반으로 I/O 대기에 따른 전환 자체를 제거함
3. 코어 친화도·NUMA 최적화: `taskset` 등으로 프로세스를 동일 코어에 묶어 전환 시 캐시 재사용률을 높임

**결론 (2줄):**
- 기술사 판단: 컨텍스트 스위칭은 멀티태스킹의 필수 비용이므로, `vmstat`의 `cs`·`sys%`를 모니터링해 과부하를 선제 진단함
- 향후 방향: 유저 레벨 스레드(가상 스레드·코루틴)로 커널 개입 없는 극저지연 전환으로 진화 중임
