## Ⅰ. 개요
- **정의**: 생성 후 상태 변경이 불가한 객체와, 부수 효과 없는 순수 함수 중심의 프로그래밍 패러다임
- **배경/필요성**: 동시성 환경에서 공유 가변 상태가 경쟁 조건의 근본 원인이므로 상태 불변을 보장할 필요
- **비유**: 원본 문서를 수정 금지로 잠그고, 변경이 필요하면 사본을 만들어 쓰는 방식과 유사함

| 출제 의도 | 반드시 짚을 핵심 | 감점 회피 포인트 |
|:---|:---|:---|
| 불변성·순수 함수 원리와 장점 | Thread-Safe 연계(274 참조), 방어적 복사 vs 불변 설계 | 불변 = 메모리 낭비라는 오해 경계, 구조적 공유 언급 |

> 요약: 상태 변경을 원천 차단하여 동시성 안전과 예측 가능성을 확보하는 설계 원칙임

## Ⅱ. 구성요소
```text
Immutable Object
  +-- final fields
  +-- no setter
  +-- defensive copy (입력)
  +-- structural sharing (변환 시)

Functional Programming
  +-- Pure Function (no side effect)
  +-- Higher-Order Function
  +-- Referential Transparency
```

| 구성요소 | 설명 | 비유 |
|:---|:---|:---|
| Pure Function | 동일 입력에 동일 출력을 반환하며 외부 상태를 변경하지 않는 함수 | 같은 재료를 넣으면 같은 요리가 나오는 레시피 |
| Structural Sharing | 변경 시 전체 복사 대신 변경 부분만 새로 생성하고 나머지는 공유 | 책 개정판에서 수정 페이지만 교체하는 방식 |
| Higher-Order Function | 함수를 인자로 받거나 반환하는 함수(`map`, `filter`, `reduce`) | 다른 도구를 조합해 쓰는 만능 공구함 |
| Referential Transparency | 표현식을 그 결과값으로 치환해도 프로그램 동작이 변하지 않는 성질 | 수학 공식에서 변수를 값으로 대입해도 등식이 유지됨 |

> 요약: 순수 함수·구조적 공유·참조 투명성이 불변 패러다임의 핵심 요소임

## Ⅲ. 절차
```text
가변 상태 식별 -> 불변 설계 적용 -> 함수 합성 -> 부수효과 격리
```
- 1단계: 기존 코드에서 가변 필드·setter·공유 컬렉션을 식별
- 2단계: 필드를 `final`로 선언하고 setter를 제거, 변경 시 새 객체 반환으로 전환
- 3단계: `map`·`filter`·`reduce` 등 고차 함수로 데이터 변환 파이프라인 구성
- 4단계: I/O·DB 접근 등 부수 효과를 경계 계층에 격리하여 핵심 로직의 순수성 유지

> 요약: 가변 상태 제거 → 불변 전환 → 함수 합성 → 부수효과 격리 순서로 적용함

## Ⅳ. 문제점
- 객체 생성 비용: 변경마다 새 객체를 생성하므로 GC 부담이 증가함(272 참조)
- 학습 장벽: 명령형 사고에 익숙한 개발자에게 함수형 패러다임 전환 비용이 높음
- 기존 코드 호환: 가변 API를 사용하는 프레임워크·라이브러리와 통합 시 래핑 비용 발생

> 요약: 객체 생성 오버헤드, 학습 비용, 가변 API 호환이 주요 문제임

## Ⅴ. 개선방안
1. 단기: 구조적 공유 자료구조(Persistent Collection) 적용으로 복사 비용 억제
2. 중기: 점진적 전환 전략(핵심 도메인부터 불변화)으로 학습 부담 분산
3. 장기: 불변 우선 API 설계 표준을 수립하여 프레임워크 수준에서 호환성 확보

> 요약: 구조적 공유, 점진적 전환, 불변 우선 API 표준으로 각 문제에 대응함

## Ⅵ. 전망
- 발전 방향: Kotlin·Swift·Rust 등 현대 언어가 불변 기본값·값 타입을 표준 채택하는 추세
- 기술사적 판단: 리액티브·이벤트 소싱 아키텍처에서 불변 이벤트 로그가 핵심 설계 요소임
- 기술사 제언: 동시성 안전 확보를 위해 공유 가변 상태 제거를 아키텍처 원칙으로 채택할 필요
