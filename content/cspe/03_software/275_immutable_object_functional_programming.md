# 📖 【암기용】 개념 완전 이해

> 목적: 이 개념을 처음 보는 사람도 완벽히 이해하게 만든다. 시험 답안 양식이 아니라, 이해를 위한 친절한 설명이다.

## 한눈에
- **개요**: 불변 객체(Immutable Object)와 함수형 프로그래밍(Functional Programming)은 **상태**(State) 변경과 **부작용**(Side Effect)을 코드에서 최대한 제거해 프로그램의 예측 가능성을 높이는 설계 방식이다.
- **왜 필요한가**: 여러 스레드나 분산 노드가 같은 상태를 공유하며 바꾸면 274에서 본 race condition, 재현이 안 되는 결함, 조합 폭발하는 테스트 케이스가 생긴다. 애초에 "바뀌는 상태"를 없애면 이 문제들이 설계로 사라진다.
- **핵심 직관**: 문서 원본을 그 자리에서 고치는 대신, 고칠 때마다 새 버전 사본을 만들어 남기면 누가 언제 무엇을 바꿨는지 추적하기 쉽고, 누군가 예전 사본을 읽는 중이어도 절대 망가지지 않는다.

## 핵심 용어 정리 (내부에 등장하는 것들)

| 용어 | 의미 | 비유 |
|:---|:---|:---|
| 상태(State) | 시간에 따라 값이 바뀔 수 있는 데이터 — 이 문서 전체가 다루는 상위 주제 | 계속 고쳐 쓰는 메모장 |
| 부작용(Side Effect) | 함수가 자기 반환값 외에 외부 상태(전역 변수, DB, 파일, 화면)를 바꾸는 동작 | 계산만 부탁했는데 남의 서랍까지 뒤지는 것 |
| 불변 객체(Immutable Object) | 생성 시점에 값이 고정되어 이후 절대 바뀌지 않는 객체 | 한 번 인쇄되면 다시 못 고치는 영수증 |
| 순수 함수(Pure Function) | 같은 입력을 넣으면 항상 같은 출력이 나오고 외부에 아무 부작용도 남기지 않는 함수 | 자판기 — 같은 버튼을 누르면 항상 같은 음료가 나오고 다른 건 안 건드림 |
| 참조 투명성(Referential Transparency) | 함수 호출 부분을 그 결과값으로 통째로 바꿔 써도 프로그램 동작이 똑같이 유지되는 성질(순수 함수의 결과) | "3+4"를 어디서든 "7"로 바꿔 써도 아무 문제 없음 |
| 구조 공유(Structural Sharing) | 값을 변경할 때 바뀌는 부분만 새로 만들고, 바뀌지 않는 나머지는 원본과 그대로 공유하는 기법 | 책 한 페이지만 새로 인쇄하고 나머지 페이지는 원본 그대로 재사용 |
| Persistent Data Structure | 구조 공유로 구현되어, 변경 후에도 이전 버전을 그대로 유지하는 불변 컬렉션(Clojure vector, Scala List 등) | 개정판을 내도 이전 판이 도서관에 그대로 남아있는 책 |
| 고차 함수(map/filter/reduce) | 함수를 인자로 받거나 반환하는 함수 — 반복문 대신 값 변환 파이프라인을 구성 | "이 작업을 각 항목에 적용해줘"라고 작업 자체를 건네주는 것 |
| Escape Analysis | JIT 컴파일러가 "이 객체가 힙 밖(다른 스레드·리턴값)으로 안 나간다"고 판단되면 스택에 할당해 GC 부담을 줄이는 최적화 | 굳이 창고(힙)에 안 넣고 손(스택)에 들고 있다가 바로 버림 |

## 깊이 이해

### 불변이 왜 스레드 안전을 "설계로" 만드는가
- 274에서 본 race condition은 결국 "누군가 쓰는 동안 누군가 읽거나 쓴다"는 상황에서만 생긴다. 불변 객체는 생성된 이후 쓰기 자체가 존재하지 않으므로, 몇 개의 스레드가 동시에 읽든 경쟁이 원천적으로 발생할 수 없다 — 락을 걸 필요조차 없는 lock-free by construction 상태다.
- 예: Java `String`은 불변이라 여러 스레드가 같은 문자열 참조를 동시에 공유해도 내부 char 배열을 아무도 고치지 않으므로 안전하다. 반대로 `StringBuilder`는 가변이라 공유 시 반드시 동기화가 필요하다.

### 구조 공유가 복사 비용을 얼마나 줄이는가 — 수치로 확인
- 만약 원소 100만 개짜리 리스트를 "변경할 때마다 전체 복사"한다면 매번 $O(N)$=100만 번의 복사가 필요해 비현실적이다.
- Persistent vector(예: Clojure vector, 분기수 32의 트리 구조)는 원소 하나를 바꿀 때 트리를 뿌리부터 그 원소가 있는 리프까지만 새로 만들고 나머지 가지는 원본과 공유한다. 100만 개 원소면 트리 깊이는 log₃₂(1,000,000) ≈ 4단계에 불과해, 매번 4개 안팎의 새 노드만 만들면 된다 — 전체 복사(100만) 대비 약 25만 배 적은 작업량이다.

### 순수 함수가 테스트를 얼마나 쉽게 만드는가
- 순수 함수 `add(a, b) = a + b`는 DB나 시계, 네트워크를 참조하지 않으므로 입력값만으로 결과가 완전히 결정된다. 이 성질 덕분에 "임의의 a, b에 대해 add(a, b) == add(b, a)"처럼 규칙(불변식) 자체를 property-based test로 자동 검증할 수 있다.
- 반대로 현재 시각이나 전역 변수를 읽는 함수는 매번 다른 결과가 나올 수 있어(비결정적) mock이나 fixture 없이는 재현 가능한 테스트를 짤 수 없다.

### GC 압력과의 트레이드오프 — 수치로 확인
- 불변 스타일은 상태를 바꿀 때마다 새 객체를 만든다. 예: 초당 10,000건 요청을 처리하며 요청당 불변 객체 5개(각 200바이트)를 새로 만들면 초당 약 10MB가 새로 할당된다. young generation이 256MB라면 대략 25초마다 minor GC가 한 번씩 도는 셈이다.
- escape analysis가 "이 객체가 메서드 밖으로 안 나간다"고 판단하면 힙 대신 스택에 할당해버려 이 GC 압력 자체를 없앨 수 있다 — 그래서 불변 스타일이 반드시 느린 것은 아니다.

### 비유
- 회의록 원본을 그 자리에서 고치지 않고 매번 새 버전 사본(v1, v2, v3...)을 남기면, 누가 언제 무엇을 바꿨는지 이력이 그대로 남고, 누군가 v1을 읽는 도중에 누가 내용을 바꿔서 망가뜨릴 위험도 없다.

### 흔한 오해·주의점
- "불변 객체는 무조건 메모리를 많이 쓴다"는 틀렸다 — 구조 공유를 쓰면 변경 부분만 새로 만들 뿐이라 전체 복사보다 오히려 적게 쓰는 경우가 많다.
- "모든 객체를 불변으로 만들면 좋다"도 틀렸다 — 필드가 아주 많은 대용량 엔티티를 매번 통째로 새로 만들면 오히려 비효율적이다. 이럴 땐 aggregate 경계 안에서 제한적으로 가변을 허용하는 절충이 실무적이다.

## 연결 개념
- 스레드 안전(274) — 불변은 공유 변경 상태 자체를 없애 락 없이 스레드 안전을 얻는 접근
- 순수 함수·참조 투명성 — 입력과 출력이 결정적이라 테스트와 병렬화가 쉬워지는 근거
- 이벤트 소싱(Event Sourcing) — 현재 상태를 직접 바꾸는 대신 "무엇이 바뀌었는지"를 이벤트 로그로 보존하는, 불변 사고를 상태 저장 방식 전체로 확장한 패턴

## Ⅰ. 개요 및 필요성

- 개요: 불변 객체·함수형 프로그래밍은 상태 변경을 제한하는 설계 방식이다.
- 배경: 동시성, 테스트, 롤백, 이벤트 처리에서 변경 가능한 공유 상태가 결함 원인이 된다.
- 필요성: 값 중심 모델, 순수 함수, 부작용 격리로 공유 상태 변경 범위를 코드 수준에서 제한해야 한다.

---

## Ⅱ. 구조 및 구성요소

```text
Input Value -> Pure Function -> New Value
  / Immutable Object -> Structural Sharing -> Safe Sharing
  / Side Effect Boundary -> DB/IO/Network
```

| 구성요소 | 역할 | 특이사항 |
|:---|:---|:---|
| Immutable Object | 생성 후 상태 고정 | final, readonly, record |
| Pure Function | 같은 입력에 같은 출력 | 테스트·병렬화 용이 |
| Structural Sharing | 변경 부분만 새 노드 생성 | persistent collection |
| Effect Boundary | IO·DB 변경 격리 | transaction, adapter layer |

> 요약: 함수형 구조는 값 변환 경로와 부작용 경계를 분리해 상태 변경 지점을 줄인다.

---

## Ⅲ. 동작원리 및 흐름도

```text
요청 입력 -> 값 객체 생성 -> 순수 함수 조합
  -> 새 상태 산출 -> 부작용 경계에서 저장/전송
  -> 로그/이벤트로 변경 추적
```

| 단계 | 처리 내용 | 검증 기준 |
|:---:|:---|:---|
| 1 | 입력을 값 객체로 변환 | validation pass |
| 2 | 순수 함수로 도메인 계산 | deterministic test |
| 3 | 새 객체 또는 이벤트 생성 | original object unchanged |
| 4 | DB·메시지 등 부작용 수행 | transaction boundary |

> 요약: 계산은 순수 함수로 격리하고 외부 변경은 경계 계층에 모아 재현성과 추적성을 확보한다.

| 구분 | 가변 객체 중심 | 불변·함수형 중심 | 정량·기술 포인트 |

|:---|:---|:---|

| 자원 | allocation rate 기준 대비 20% 이내 증가 | profiler, GC log |

> 요약: 성공 여부는 공유 변경 상태 감소, 순수 함수 테스트, 할당량 증가폭으로 판단한다.

## Ⅵ. 실무 적용 및 결론

**적용 방안 3개 (필수 — 단계별 또는 항목별):**
1. 금액, 기간, 식별자 같은 도메인 값은 Java record, Kotlin data class, C# record로 불변 값 객체화함.
2. 병렬 계산은 mutable shared list 대신 stream map/filter/reduce와 immutable collection으로 구성함.
3. 외부 변경은 repository, message producer, transaction boundary에 모아 순수 계산과 IO를 분리함.

**결론 (2줄):**
- 기술사 판단: 도메인 값과 병렬 계산은 불변성을 기본으로 두고, 대용량 엔티티 변경은 aggregate 경계에서 제한적으로 허용.
- 향후 방향: 함수형 패턴은 reactive stream, event sourcing, CQRS와 결합해 상태 변경을 추적 가능한 값 흐름으로 전환함.
