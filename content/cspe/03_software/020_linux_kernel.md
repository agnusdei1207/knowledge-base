## Ⅰ. 개요
- 정의: 하드웨어와 사용자 프로세스 사이의 중재자인 리눅스 커널의 구조와 가동 절차
- 배경: 오픈소스 기반의 안정적이고 유연한 시스템 운영 환경 구축을 위한 이해 필수
- 출제 의도: 전반적인 시스템 초기화 흐름과 커널의 주요 서브시스템 역할 파악

## Ⅱ. 구성요소
```
[ User Space ]  Shell, Apps, Libraries
--------------------------------------
[ Kernel Space ] System Call Interface
 +-----------+ +-----------+ +-----------+
 | Process M | | Memory M  | | File Sys  |
 +-----------+ +-----------+ +-----------+
 | Network S | | Device Dr | | Interrupt |
 +-----------+ +-----------+ +-----------+
--------------------------------------
[ Hardware ] CPU, RAM, Disk, NIC
```
| 구성요소 | 설명 | 비유 |
| :--- | :--- | :--- |
| 서브시스템 | 프로세스, 메모리, 파일, 네트워크 관리 모듈 | 정부 부처 |
| LKM | 실행 중 동적으로 로드/언로드 가능한 커널 모듈 | 플러그인 |
| Systemd | 커널 부팅 후 가장 먼저 실행되는 사용자 공간 서비스 | 총무부 |
> 요약: 계층형 구조를 통해 하드웨어 추상화 및 자원 관리를 수행함.

## Ⅲ. 절차
```
[BIOS/UEFI] -> [Bootloader] -> [Kernel Load] -> [Init/Systemd]
```
1. 전원 인가 후 BIOS/UEFI가 하드웨어 점검(POST) 및 부트로더(GRUB) 실행
2. 부트로더가 커널 이미지(vmlinuz)와 초기 램 디스크(initrd)를 메모리에 적재
3. 커널이 하드웨어 드라이버 초기화 및 루트 파일 시스템 마운트 수행
4. PID 1번인 init(systemd) 프로세스를 생성하여 사용자 환경 및 서비스 가동
> 요약: 하드웨어 체크부터 사용자 서비스 실행까지 단계별 제어권이 이양됨.

## Ⅳ. 문제점
- 원인: 커널 소스 비대화 및 복잡도 증가로 인해 디버깅 및 유지보수 난이도 상승
- 원인: 부팅 과정에서 많은 서비스 동시 실행 시 부팅 시간(Boot time) 지연 발생

## Ⅴ. 개선방안
- (단기) 불필요한 커널 모듈 제거 및 시스템 서비스 최적화(Disable/Mask) 수행
- (중기) 커널 패치 자동화 및 라이브 패칭(Live Patching) 기술로 중단 없는 업데이트
- (장기) 마이크로 서비스 아키텍처 철학을 담은 경량화된 컨테이너 전용 OS 커널 도입

## Ⅵ. 전망
- eBPF 기술을 통해 커널 수정 없이도 고성능 네트워킹 및 모니터링이 가능해지는 추세임
- 보안 강화를 위해 커널 주소 공간 무작위화(KASLR) 및 하드웨어 기반 격리 기술(TEE) 융합 가속화
