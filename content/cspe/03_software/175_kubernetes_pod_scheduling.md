## 미리 알고가기

- 미배치 Pod는 `.spec.nodeName`이 정해지지 않아 스케줄링 큐에서 노드 선택을 기다림
- 자원 요청값은 스케줄러가 노드의 할당 가능 CPU·메모리와 비교하는 예약 기준임
- Filter는 자원·정책·볼륨 조건을 충족하지 못한 노드를 후보에서 제외함
- Score는 Filter를 통과한 노드를 선호 규칙으로 순위화함
- Taint는 노드가 거부하는 조건이고 Toleration은 Pod가 해당 조건을 허용한다는 선언임
- Affinity·Topology Spread는 Pod의 공동 배치·분산 배치 선호와 필수 조건을 표현함
- QueueSort는 처리할 Pod 순서를 정하고 Filter·Score는 후보 노드와 순위를 계산함
- Reserve·Permit·Bind는 선택 노드의 자원을 예약·허가한 뒤 Pod와 노드를 연결함

## 작성 근거(검토용)

- 스케줄링은 자원 평균 분배보다 필수 조건으로 후보를 거른 뒤 선호 조건으로 순위를 정하는 과정이 핵심임
- Filter와 Score를 목적·입력·노드 영향·산출·실패 상태·적용 기준으로 비교함
- 제목부터 결론까지 5회 전수 검수하여 필수 조건과 선호 조건의 동작을 혼용하지 않도록 교정함

## Ⅰ. 개요

- **정의/개념**: Pod 스케줄링은 미배치 Pod의 자원·정책 제약을 충족하는 노드를 찾고 후보를 점수화해 하나의 노드에 바인딩하는 과정임
- **배경/필요성**: 제한된 노드 자원에 워크로드의 필수·선호 배치 조건을 반영하기 위해 필터링·점수화 기준이 필요함

## Ⅱ. 특징

- 스케줄러는 실제 사용량이 아니라 Pod 자원 요청값과 노드 할당 가능량을 비교함
- 필수 affinity·허용하지 않은 taint·볼륨 토폴로지는 Filter에서 노드를 제외함
- 선호 affinity·분산·이미지 지역성 규칙은 후보 노드의 Score에 반영됨
- 실행 가능한 노드가 없으면 Pod는 Pending 상태로 남고 조건 변화나 선점 후 다시 시도함

## Ⅲ. Filter와 Score 비교

| 판단 기준 | Filter | Score |
|:---|:---|:---|
| 목적 | 실행 불가능한 노드를 후보에서 제외 | 실행 가능한 노드의 선호 순위를 계산 |
| 입력 조건 | 자원 부족·필수 affinity·taint·볼륨 제약 | 자원 균형·선호 affinity·토폴로지 분산 |
| 노드 영향 | 조건 하나라도 실패하면 후보에서 제거 | 플러그인 점수를 합산해 순위에 반영 |
| 산출물 | 실행 가능한 노드 집합 | 후보별 정규화 점수와 최상위 노드 |
| 조건 미충족 | 후보가 없으면 Pod가 미배치 상태로 대기 | 다른 후보가 있으면 낮은 순위로 배치 가능 |
| 적용 기준 | 반드시 지켜야 할 실행·정책 조건 | 실행 가능 노드 중 배치 위치를 고를 선호 조건 |

> 요약: Filter는 실행 가능성을 판정하고 Score는 실행 가능한 후보의 우선순위를 정함.

## Ⅳ. 구성요소 및 구조

| 구성요소 | 역할 |
|:---|:---|
| 스케줄링 큐 | 우선순위와 재시도 상태로 미배치 Pod를 정렬함 |
| 클러스터 상태 캐시 | 노드 자원·Pod·볼륨·정책 정보를 스케줄러에 제공함 |
| Filter 플러그인 | 자원·포트·taint·affinity·볼륨 조건을 검사함 |
| Score 플러그인 | 자원 배치·지역성·분산 선호를 점수화함 |
| Reserve·Permit | 바인딩 전 자원을 임시 예약하고 승인 조건을 확인함 |
| Bind 플러그인 | 선택 노드를 Pod의 `.spec.nodeName`에 기록함 |

```text
미배치 Pod -> 스케줄링 큐 -> Filter -> Score -> Reserve·Permit -> Bind
                                   |
                             후보 없음 -> 재대기·선점
```

> 요약: 큐의 Pod는 실행 가능 후보와 순위를 거쳐 노드에 바인딩되며 후보가 없으면 다시 대기함.

## Ⅴ. 스케줄링 절차

```text
Pod 선택 -> 상태 조회 -> 노드 Filter -> 후보 Score -> 예약·허가 -> API 바인딩
```

1. **Pod 선택**: QueueSort 규칙이 스케줄링할 미배치 Pod를 선택함
2. **상태 조회**: Pod 요청과 노드 자원·정책·볼륨 상태를 스냅샷으로 읽음
3. **노드 Filter**: 필수 조건을 통과한 실행 가능 노드 집합을 만듦
4. **후보 Score**: 활성 플러그인 점수를 합산해 최상위 노드를 선택함
5. **예약·허가**: 바인딩 전 자원을 예약하고 Permit·PreBind 조건을 확인함
6. **API 바인딩**: 선택 노드를 기록하고 kubelet이 Pod 실행을 시작함

> 요약: 필수 조건을 통과한 노드만 점수화하며 바인딩 결과가 kubelet 실행의 입력이 됨.

## Ⅵ. 실무 사례

1. GPU 추론 Pod는 taint·toleration과 필수 affinity를 적용해 미배치 시간·배치 실패 건수를 확인함
2. API 복제본은 토폴로지 분산을 적용하고 영역별 Pod 편차·재배치 시간을 확인함

## Ⅶ. 결론

- Pod 스케줄링은 필수 실행 조건을 Filter에, 배치 선호를 Score에 분리해 설계해야 함
