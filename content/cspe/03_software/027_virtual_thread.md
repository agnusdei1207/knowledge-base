# 📖 【암기용】 개념 완전 이해

## 한눈에
- **개요**: OS가 관리하는 무거운 플랫폼 스레드 대신, JVM이 직접 관리하여 수백만 개를 동시에 생성할 수 있는 초경량 사용자 스레드 기술이다. (Java 21 공식 도입)
- **왜 필요한가**: 기존 자바 서버는 I/O 대기(DB 조회, API 통신) 동안 스레드가 블로킹되어 아까운 스레드를 낭비했다. 이를 피하려고 코드가 복잡한 비동기(Reactive) 방식을 썼는데, 가상 스레드는 동기식으로 짜면서도 비동기 성능을 내게 해준다.
- **핵심 직관**: 플랫폼 스레드가 비싼 '정규직 직원'이라면, 가상 스레드는 일당을 받는 '아르바이트생'이다. 일을 하다가 대기 상태가 되면 정규직은 자리를 비워주고 다른 아르바이트생이 그 자리에 앉아 일을 계속한다.

## 핵심 용어 정리

| 용어/표기 | 의미 | 비유·예 |
|:---|:---|:---|
| 플랫폼 스레드 (Platform Thread) | OS 커널 스레드와 1:1로 매핑되는 무거운 전통적 스레드 | 비싼 고정석을 차지하는 정규직 직원 |
| 캐리어 스레드 (Carrier Thread) | 가상 스레드를 할당받아 실제 CPU에서 실행해주는 플랫폼 스레드 | 아르바이트생(가상 스레드)이 일할 수 있는 실제 책상 |
| Continuation (연속성) | 스레드의 실행 상태(Call Stack)를 저장하고 복원할 수 있는 저수준 제어 흐름 단위 | 일하던 문서(스택)를 서랍에 넣었다가 다시 꺼내는 기능 |

## 깊이 이해
- **배경·문제의식**: 자바의 전통적 스레드는 1개당 1MB의 메모리를 먹고 컨텍스트 스위칭 비용이 커서 수천 개 이상 만들 수 없었다. 웹 요청 1개당 스레드 1개를 쓰는 Thread-per-request 모델은 I/O 블로킹 시 시스템 스루풋이 급감했다. Reactive(WebFlux)는 성능은 좋으나 디버깅이 지옥이었다.
- **작동 원리**: 
  - 수백만 개의 가상 스레드를 만든다. 
  - 가상 스레드가 실행되려면 소수의 캐리어 스레드(플랫폼 스레드)에 마운트(Mount)되어야 한다.
  - 네트워크 I/O 등을 만나서 블로킹을 호출하면, JVM이 이를 가로채어 가상 스레드의 스택(상태)을 힙(Heap) 메모리로 언마운트(Unmount)하고, 빈 캐리어 스레드에 다른 가상 스레드를 올려 실행한다.
- **비유**: 식당에 요리사(캐리어 스레드)는 10명뿐인데, 주문(가상 스레드)은 1만 개다. 요리사는 고기가 익는 동안(I/O 블로킹) 멍때리지 않고 고기 굽는 판을 잠시 치워두고(언마운트) 다른 주문의 야채를 썬다.
- **구체 예시**: Java 21의 `Executors.newVirtualThreadPerTaskExecutor()`
- **흔한 오해·주의점**: 가상 스레드는 I/O 바운드 작업에 특화되어 있다. CPU를 쉬지 않고 쓰는 CPU 바운드 작업(예: 암호화 계산)을 가상 스레드로 돌려봤자 어차피 캐리어 스레드를 계속 점유하므로 성능 향상이 전혀 없다. 오히려 오버헤드만 커진다.

## 연결 개념
- 컨텍스트 스위칭, 비동기 I/O, 리액티브 프로그래밍, Go 언어의 Goroutine

# 📝 【답안용】 시험 답안 템플릿

## 핵심 인사이트 (3줄 요약)

> 1. **본질**: OS 커널의 컨텍스트 스위칭 비용을 우회하기 위해, JVM 레벨에서 힙 메모리를 활용해 스레드 상태를 저장/복원(Continuation)하는 초경량 사용자 스레드.
> 2. **가치**: 코드의 가독성(동기식 직관성)을 유지하면서도 수백만 개의 동시 연결 처리가 가능해 리액티브(비동기) 프로그래밍의 복잡성을 해결함.
> 3. **판단 포인트**: I/O 바운드 중심의 마이크로서비스 및 API 게이트웨이에 최적화되어 있으나, CPU 바운드 및 `synchronized` 블록(Pinning 현상)에서는 오히려 성능이 저하된다.

## 출제 의도 및 답안 포인트

| 출제 의도 | 반드시 짚을 핵심 | 감점 회피 포인트 |
|:---|:---|:---|
| 기존 동시성 모델의 한계와 가상 스레드의 해결 원리 | 플랫폼 스레드와의 1:N 매핑(Carrier Thread), Continuation, 언마운트 메커니즘 | "가상 스레드가 무조건 빠르다"는 오답 지양 (CPU 바운드 한계 명시) |

> 요약: 스레드 생성 비용과 컨텍스트 스위칭 오버헤드를 JVM 내부의 Mount/Unmount 메커니즘으로 회피하는 구조를 설명한다.

## Ⅰ. 개요 및 필요성

- 개요: Java 플랫폼(Project Loom)에서 도입된, OS 커널 대신 JVM이 직접 스케줄링하고 관리하는 경량(Lightweight) 스레드 구현체.
- 배경: 전통적인 Thread-per-request 모델은 네트워크/DB 대기 시 플랫폼 스레드가 블로킹되어 막대한 자원 낭비(C10K 문제) 유발.
- 필요성: 비동기(Reactive) 프로그래밍의 극심한 학습 곡선과 콜백 지옥(Callback Hell)을 극복하고, 동기식 코드 작성으로 비동기의 스루풋을 달성하기 위해 필요함.

---

## Ⅱ. 구조 및 구성요소

```text
[사용자 공간 (JVM)]
가상 스레드 A, B, C (Heap 메모리에 수백만 개 생성 가능)
      |   (Continuation 기반 Mount / Unmount)
캐리어 스레드 1, 2 (ForkJoinPool)
------------------------------------------------------
[커널 공간 (OS)]
OS 커널 스레드 1, 2 (캐리어 스레드와 1:1 매핑)
```

| 구성요소 | 역할 | 특이사항 |
|:---|:---|:---|
| 가상 스레드 (Virtual Thread) | 개발자가 생성하는 작업 단위로, 힙(Heap) 메모리에 스택 프레임을 저장 | 생성 비용 및 메모리 점유율 극소(수 KB) |
| 캐리어 스레드 (Carrier Thread) | 가상 스레드를 싣고 실제 CPU 코어에서 실행시키는 플랫폼 스레드 | 기본적으로 시스템 코어 수만큼 생성됨 |
| Continuation | 스레드의 실행을 일시 중단(yield)하고 나중에 재개할 수 있는 제어 흐름 메커니즘 | JVM 내부 깊숙이 구현된 코어 기술 |

> 요약: 다수의 가상 스레드를 소수의 캐리어 스레드에 동적으로 매핑(M:N)하여, OS 개입 없는 사용자 레벨 스케줄링을 구현한다.

---

## Ⅲ. 동작원리 및 흐름도

```text
작업 할당 -> [가상 스레드 Mount] -> I/O 블로킹 발생 -> [가상 스레드 Unmount] -> 다른 가상 스레드 실행
```

- 1단계 [작업 할당 및 실행]: JVM이 가상 스레드를 캐리어 스레드에 마운트(Mount)하여 실행을 시작함 (스택 프레임을 복사).
- 2단계 [I/O 차단 및 Unmount]: 가상 스레드가 네트워크 소켓 등 블로킹 I/O를 호출하면, JVM이 이를 감지하고 가상 스레드의 상태를 힙으로 이동(Unmount)함.
- 3단계 [캐리어 스레드 재할당]: 비워진 캐리어 스레드는 대기 중인 다른 가상 스레드를 새로 마운트하여 CPU 연산을 쉼 없이 지속함.
- 4단계 [I/O 완료 및 재개]: 2단계의 I/O 응답이 오면, 해당 가상 스레드를 다시 가용한 캐리어 스레드에 마운트하여 작업을 이어서 수행함.

> 요약: I/O 대기 시 OS 스레드를 블로킹시키는 대신, 스택 정보만 힙에 덜어내고 다른 작업을 수행함으로써 컨텍스트 스위칭 비용을 제거한다.

## Ⅳ. 특징

- 동기식 코드의 직관성 유지: `CompletableFuture`나 RxJava 없이 기존의 직관적인 동기식(Imperative) 흐름제어 코드를 그대로 사용할 수 있음.
- 극단적인 동시성 확장: 스레드 생성 비용이 거의 0에 가까워, 요청마다 스레드를 할당하고 파기하는 Thread-per-request 모델을 수백만 규모로 지원.
- 스레드 풀 불필요: 너무 가벼워서 풀링(Pooling)할 필요가 없으며, 작업이 끝남과 동시에 GC(Garbage Collector)의 수거 대상이 됨.
- Pinning 현상 (단점/한계): `synchronized` 블록 안에서 I/O 대기를 할 경우, 캐리어 스레드에서 Unmount되지 못하고 함께 묶이는(Pin) 현상이 발생해 성능이 저하됨.

> 요약: 높은 스루풋과 코드 가독성을 동시에 잡았으나, 락(Lock) 메커니즘과 CPU 바운드 작업에서는 구조적 한계가 존재한다.

## Ⅴ. 심화 비교 및 적용 판단

| 비교 축 | Thread-per-request (전통 방식) | Reactive (WebFlux) | Virtual Thread (Loom) |
|:---|:---|:---|:---|
| 제어 흐름 / 가독성 | 직관적 (동기식) | 매우 복잡 (비동기 체인) | 직관적 (동기식) |
| 메모리 / 컨텍스트 비용 | 큼 (OS 스레드 1MB + 전환) | 작음 (이벤트 루프) | 매우 작음 (Heap 수 KB + Unmount) |
| 디버깅 / 예외 추적 | 쉬움 (스택 트레이스 명확) | 매우 어려움 (콜백 스택 끊김) | 쉬움 (스택 트레이스 완벽 보존) |

> 요약: 리액티브 프로그래밍의 난해함을 극복하기 위한 궁극적인 패러다임 시프트로, I/O 바운드 애플리케이션의 새로운 표준이 되고 있다.

**도입 시 리스크 및 대응 지표:**
- Thread Pinning: 레거시 JDBC 드라이버 내장 `synchronized` 사용 시 발생 → `ReentrantLock` 기반의 최신 드라이버로 마이그레이션 (지표: JFR - Virtual Thread Pinned 이벤트 빈도)
- 과도한 동시 접속 폭주: 가상 스레드가 무제한 생성되어 백엔드 DB 커넥션 풀을 고갈시킴 → 세마포어(Semaphore)를 활용한 동시성 제한율 제어 (지표: DB Connection Timeout 횟수)

## Ⅵ. 실무 적용 및 결론

**적용 방안 3개:**
1. MSA 기반 API 게이트웨이 전환: 다수의 외부 API를 애그리게이션(Aggregation)하며 I/O 대기가 긴 BFF(Backend For Frontend) 서버를 Spring Boot 3.2+ 와 가상 스레드로 전환.
2. 기존 Tomcat 튜닝: 대규모 블로킹 트래픽 환경에서 레거시 MVC 애플리케이션의 톰캣(Tomcat) 스레드 풀을 가상 스레드 기반(`Executor`)으로 교체하여 처리량 10배 이상 증대.
3. 데이터 파이프라인 수집기: 초당 수만 건의 외부 REST API 스크래핑 크롤러 개발 시, 고비용 리액티브 라이브러리 대신 순수 자바 HTTP 클라이언트와 가상 스레드를 결합.

**결론 (2줄):**
- 기술사 판단: 가상 스레드는 I/O 병목을 애플리케이션 코드가 아닌 JVM 스케줄러 계층에서 해결하는 혁신으로, 리액티브의 복잡성을 완전히 대체할 아키텍처임.
- 향후 방향: Java 생태계의 모든 라이브러리(JDBC, 캐시 등)가 락 구조를 개편하고 있으며, 구조적 동시성(Structured Concurrency)과 결합하여 무결성까지 갖춘 표준으로 자리 잡을 것임.
