# 📖 【암기용】 개념 완전 이해

> 목적: UML 다이어그램을 처음 보는 사람도 정적·동적 관점과 사용 목적을 구분해 이해하게 만든다. 시험 답안 양식이 아니라, 이해를 위한 친절한 설명이다.

## 한눈에
- **개요**: UML은 소프트웨어 구조와 행위를 표준 기호로 표현하는 모델링 언어
- **왜 필요한가**: 요구사항, 설계, 구현 담당자가 같은 시스템을 서로 다르게 이해하면 결함이 생긴다. UML은 관점별 다이어그램으로 구조, 상호작용, 배치, 상태 변화를 공유한다.
- **핵심 직관**: 건축 도면이 평면도, 전기 배선도, 배관도를 나누듯 소프트웨어도 구조도와 동작도를 나눠 그린다.

## 깊이 이해
- **배경·문제의식**: 복잡한 시스템은 코드만 보면 업무 흐름, 객체 관계, 메시지 순서, 배포 구조를 빠르게 파악하기 어렵다. UML은 Use Case, Class, Sequence, Activity, State, Component, Deployment 등 표준 다이어그램으로 관점을 분리한다.
- **작동 원리**: 정적 관점은 클래스, 컴포넌트, 배포처럼 변하지 않는 구조를 표현한다. 동적 관점은 시퀀스, 활동, 상태처럼 시간에 따른 행위를 표현한다. 요구사항 분석에는 Use Case, 상세 설계에는 Class/Sequence, 운영 배치에는 Deployment가 적합하다.
- **비유**: 영화 제작에서 등장인물 관계도, 장면 순서표, 촬영장 배치도가 각각 다른 목적을 가지는 것과 같다.
- **구체 예시**: 결제 기능 설계 시 Use Case로 사용자 목표를 잡고, Sequence로 주문-결제-승인 메시지 순서를 검증하며, Deployment로 WAS, DB, PG 연동 서버 배치를 표현함.
- **흔한 오해·주의점**: UML을 많이 그릴수록 설계 품질이 올라가는 것은 아니다. 변경 가능성이 큰 화면까지 과도하게 모델링하면 문서 갱신 비용이 코드 변경 속도를 따라가지 못한다.

## 연결 개념
- Use Case Diagram: 사용자 목표와 시스템 경계를 표현
- Sequence Diagram: 객체 간 메시지 순서를 시간축으로 표현
- Class Diagram: 객체 구조와 관계를 표현

# 📝 【답안용】 시험 답안 템플릿

> 목적: 시험장에서 25분에 그대로 쓰는 답안 양식. 작성방식(추상표현 금지·수치·도식·문제유형 전환)을 엄격히 지킨다.
> 핵심: UML 답안은 다이어그램 종류 나열이 아니라 요구사항, 설계, 구현, 배포 단계에서 어떤 관점을 선택할지 판단해야 한다.

## 핵심 인사이트 (3줄 요약)

> 1. **본질**: UML은 시스템의 정적 구조와 동적 행위를 표준 다이어그램으로 표현하는 모델링 언어이다.
> 2. **가치**: 이해관계자 간 설계 합의를 만들고 요구사항-설계-구현 추적성을 높인다.
> 3. **판단 포인트**: Use Case, Class, Sequence, Activity, State, Component, Deployment를 목적별로 선택하고 과도한 모델링을 방지해야 한다.

## 출제 의도 및 답안 포인트

| 출제 의도 | 반드시 짚을 핵심 | 감점 회피 포인트 |
|:---|:---|:---|
| UML 유형 분류 이해 확인 | 구조 다이어그램, 행위 다이어그램, 상호작용 다이어그램 | 다이어그램 명칭만 나열 |
| 단계별 활용 판단 확인 | 요구분석, 상세설계, 테스트, 배포 설계 | 모든 상황에 Class Diagram만 제시 |
| 모델링 리스크 인식 확인 | 문서-코드 불일치, 과도한 모델링, 추적성 | UML을 산출물 작성 자체로 오해 |

> 요약: UML 문제는 정적·동적 관점별 다이어그램 선택과 모델-코드 일치 관리가 핵심이다.

## Ⅰ. 개요 및 필요성

- 개요: 표준 소프트웨어 모델링 언어
- 배경: 복잡한 시스템은 요구사항, 객체 구조, 메시지 흐름, 배포 구성을 코드만으로 공유하기 어려워 분석·설계 간 해석 차이가 발생함.
- 필요성: Use Case, Class, Sequence, Deployment diagram으로 요구-설계-테스트 추적성과 인터페이스 검토 기준을 확보해야 함.

---

## Ⅱ. 구조 및 구성요소

```text
Requirement View -> Use Case / Activity
Design View -> Class / Sequence / State
Implementation View -> Component
Deployment View -> Deployment
```

| 구성요소 | 역할 | 활용 단계 |
|:---|:---|:---|
| Use Case Diagram | 사용자 목표와 시스템 경계 표현 | 요구사항 분석 |
| Class/Component Diagram | 구조, 책임, 인터페이스 표현 | 분석·설계·구현 |
| Sequence/Activity Diagram | 메시지 순서와 업무 흐름 표현 | 상세 설계·검증 |
| State/Deployment Diagram | 상태 전이와 물리 배치 표현 | 상태 설계·운영 배치 |

> 요약: UML은 요구, 구조, 행위, 배포 관점을 나누어 필요한 다이어그램만 선택해 사용한다.

---

## Ⅲ. 동작원리 및 흐름도

```text
요구사항 식별 -> 관점 선택 -> 다이어그램 작성 -> 이해관계자 검토
-> 설계 보완 -> 코드·테스트 연결 -> 변경 시 모델 갱신
```

| 단계 | 처리 내용 | 검증 기준 |
|:---:|:---|:---|
| 1 | 모델링 목적과 범위 결정 | 시스템 경계, 대상 use case |
| 2 | 정적·동적 관점 선택 | 구조/행위/배포 구분 |
| 3 | UML 다이어그램 작성 | 표준 표기 준수, 모호 관계 제거 |
| 4 | 설계 리뷰와 요구사항 추적 | 요구 ID-모델 요소 매핑 |
| 5 | 구현·테스트 변경 시 모델 갱신 | 모델-코드 불일치 0건 목표 |

> 요약: UML은 목적 선택, 다이어그램 작성, 리뷰, 추적성, 갱신 관리까지 수행되어야 설계 자산이 된다.

## Ⅳ. 특징

| 구분 | 비표준 문서 | UML 적용 | 수치·판단 포인트 |
|:---|:---|:---|:---|
| 의사소통 | 담당자별 표현 상이 | 표준 기호와 관점 분리 | 리뷰 결함 건수 감소 추세 |
| 설계 검증 | 코드 이후 발견 | sequence/state로 흐름 사전 검증 | 요구-모델 매핑 100% |
| 유지보수 | 문서 갱신 누락 | 변경 영향 분석 지원 | 모델 갱신 리드타임 2일 이내 |
| 비용 | 작성 부담 낮음 | 과도 모델링 비용 발생 | 핵심 use case 중심 선별 |

> 요약: UML은 표준화된 설계 소통 도구이나, 모델 갱신 비용과 활용 범위를 함께 통제해야 한다.

## Ⅴ. 심화 비교 및 적용 판단

| 비교 축 | 문서 중심 설계 | UML 모델링 | 선택 기준 |
|:---|:---|:---|:---|
| 표현력 | 자연어·표 중심 | 구조·행위 시각화 | 메시지 순서·상태 전이 복잡 시 UML |
| 추적성 | 문서 간 수동 연결 | 요구-모델-테스트 매핑 | 규제·대형 프로젝트 적용 |
| 유지 비용 | 작성은 낮음 | 갱신 관리 필요 | 변경 빈도 높은 화면은 경량화 |

> 요약: UML은 복잡한 구조·행위 검증에는 적합하지만 변경 빈도와 갱신 비용을 기준으로 범위를 제한해야 한다.

| 리스크 | 원인 | 대응 방안 | 확인 지표 |
|:---|:---|:---|:---|
| 과도한 모델링 | 모든 기능 상세 다이어그램화 | 핵심 use case와 아키텍처 중심 선별 | 모델 작성 시간 비율 10% 이하 |
| 모델-코드 불일치 | 변경 시 갱신 누락 | review checklist, architecture decision record | 불일치 결함 0건 |
| 표기 오해 | UML 기호 숙련도 부족 | 표기 가이드, 예제 저장소 | 리뷰 재작업 건수 |

> 요약: UML 리스크는 작성 범위, 갱신 체계, 표기 표준을 명확히 해야 줄일 수 있다.

| 점검 항목 | 목표 기준 | 측정 방법 |
|:---|:---|:---|
| 추적성 | 요구-모델-테스트 매핑 100% | RTM, modeling tool |
| 모델 품질 | 리뷰 결함 건수 감소 추세 | architecture review log |
| 유지관리 | 모델 갱신 리드타임 2일 이내 | 변경 요청-모델 commit 비교 |

> 요약: UML 활용 성과는 추적성, 리뷰 결함, 갱신 리드타임으로 검증한다.

## Ⅵ. 실무 적용 및 결론

**적용 방안 3개 (필수 - 단계별 또는 항목별):**
1. 요구사항 단계는 Use Case와 Activity, 상세 설계는 Class와 Sequence, 운영 배치는 Component와 Deployment로 관점별 산출물 지정
2. 핵심 업무 20%와 장애 영향이 큰 use case를 우선 모델링하고, CRUD 화면은 표준 템플릿으로 경량화
3. 요구 ID, UML 요소, 테스트 케이스를 RTM으로 연결하고 설계 리뷰 때 모델-코드 불일치 0건을 확인

**결론 (2줄):**
- 기술사 판단: 복잡한 업무 흐름·상태 전이·배포 구조가 있으면 UML을 적용하고, 변경 빈도 높은 단순 화면은 경량 문서로 대체함
- 향후 방향: UML은 MDD, SysML, C4 model, architecture decision record와 결합되어 코드와 아키텍처 문서의 추적성을 보완함
