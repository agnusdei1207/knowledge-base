## 미리 알고가기

- UML은 소프트웨어 구조와 행위를 표준 기호로 표현하는 모델링 언어임
- 정적 구조도와 동적 행위도가 대표 구분임
- 다이어그램 수를 많이 그리는 것보다 목적에 맞는 선택이 중요함

## Ⅰ. 개요

- **정의/개념**: UML 다이어그램은 소프트웨어 시스템의 구조와 행위와 상호작용을 표준화된 시각 모델로 표현해 이해관계자 간 의사소통과 설계 검토를 돕는 모델링 도구임
- **배경/필요성**: 복잡한 시스템은 텍스트 명세만으로 구조와 동작을 공유하기 어려우므로, 설계 의도와 관계를 빠르게 파악할 수 있는 공통 표기 체계가 필요함

## Ⅱ. 특징

- 구조와 행위를 나눠 서로 다른 관점에서 시스템을 설명함
- 개발자와 기획자와 아키텍트 간 의사소통 비용을 줄임
- 목적 없이 남발하면 문서 유지 비용만 커지고 실효성이 떨어짐
- 실제 코드와 모델 간 정합성이 유지될 때 가치가 높아짐

## Ⅲ. 종류 및 비교

| 판단 기준 | 구조 다이어그램 | 행위 다이어그램 |
|:---|:---|:---|
| 초점 | 클래스, 컴포넌트, 배치 관계 | 시나리오, 상태, 흐름 |
| 대표 예 | Class, Component, Deployment | Sequence, Activity, State |
| 활용 시점 | 아키텍처와 설계 구조 설명 | 동작 절차와 상호작용 설명 |
| 주의점 | 과도한 상세화 위험 | 현실 흐름과 불일치 위험 |

## Ⅳ. 구성요소 및 구조

| 구성요소 | 설명 |
|:---|:---|
| Class Diagram | 객체와 속성과 관계를 표현해 도메인 구조와 책임 분배를 보여줌 |
| Sequence Diagram | 시간 순서에 따른 메시지 교환을 보여줘 API 호출과 협력 관계를 설명함 |
| Activity Diagram | 업무나 처리 절차 흐름을 보여줘 조건 분기와 병렬 흐름을 정리함 |
| Component and Deployment Diagram | 컴포넌트 의존성과 실행 배치를 표현해 실제 시스템 구성을 이해하게 함 |

## Ⅴ. 원리 및 절차 흐름도

```text
+-------------+     +-------------+     +-------------+     +-------------+
| 모델 목적 정의  | --> | 다이어그램 선택 | --> | 핵심 요소 표현 | --> | 리뷰/정합 관리 |
+-------------+     +-------------+     +-------------+     +-------------+
```

1. **모델 목적 정의**: 구조 설명인지 동작 설명인지 목표를 정함
2. **다이어그램 선택**: 목적에 맞는 UML 유형을 고름
3. **핵심 요소 표현**: 과도한 세부보다 필요한 관계와 흐름만 모델링함
4. **리뷰 및 정합 관리**: 실제 구현과 맞는지 확인하며 유지함

## Ⅵ. 문제점 및 해결 방안

1. 문제: 목적 없이 다양한 UML을 모두 그리면 문서 유지 비용만 늘고 설계 가치가 떨어질 수 있음
   - 해결방안: 의사결정 목적별 최소 다이어그램 세트를 정하고 documentation overhead와 usage frequency로 검증함
2. 문제: 구현이 바뀌어도 다이어그램을 갱신하지 않으면 모델이 오히려 잘못된 지식을 퍼뜨릴 수 있음
   - 해결방안: 설계 변경 시 갱신 책임을 명확히 하고 model drift count와 review freshness로 검증함
3. 문제: 표준 기호 이해가 약하면 같은 그림도 이해관계자마다 해석이 달라질 수 있음
   - 해결방안: 표기 규칙 템플릿을 제공하고 notation error rate와 review clarification count로 검증함

## Ⅶ. 적용 사례

- 도메인 설계 리뷰에서는 class diagram을 사용하고, review clarification count와 model drift count로 결과를 확인함
- API 협력 구조 설명에서는 sequence diagram을 사용하고, notation error rate와 integration defect count로 결과를 확인함
- 운영 아키텍처 문서화에서는 component와 deployment diagram을 사용하고, usage frequency와 review freshness로 결과를 확인함

## Ⅷ. 결론

UML의 가치는 그림 수가 아니라 어떤 구조나 동작을 빠르게 합의해야 하는지에 맞춰 필요한 모델만 정확히 유지하는 데 있음.
