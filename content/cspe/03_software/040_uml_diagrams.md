## 미리 알고가기

- UML은 소프트웨어 구조와 동작을 표준 기호로 표현하는 모델링 언어임
- 구조 다이어그램은 정적 관계를, 행위 다이어그램은 시간 흐름과 상호작용을 설명함
- Model drift는 설계 문서와 실제 구현이 어긋나는 상태를 뜻함

## 작성 근거(검토용)

- 구조·행위 다이어그램을 표현 대상·시간·대표 유형·검토 질문·변경 계기·활용으로 비교함
- 유형 분류가 중심이므로 임의의 모델 작성 업무 순서를 Ⅴ절로 두지 않음
- 아키텍처 리뷰와 API 협력 설계를 분리해 문서·구현 불일치와 연동 결함을 검증함

## Ⅰ. 개요

- **정의/개념**: UML 다이어그램은 소프트웨어의 정적 구조·동적 행위·객체 상호작용을 표준 기호로 표현하는 모델링 도구임
- **배경/필요성**: 설계 참여자가 구조와 시간 순서·상태 변화를 같은 표기로 검토하기 위해 공통 모델링 언어가 필요함

## Ⅱ. 특징

- 구조 관점과 행위 관점을 나눠 서로 다른 질문에 답할 수 있게 함
- 개발자·기획자·아키텍트가 같은 기호와 관계를 기준으로 설계를 검토함
- 검토 질문과 연결되지 않은 다이어그램은 갱신 대상만 늘리고 설계 판단 근거를 제공하지 못함
- 구현 변경 시 관련 다이어그램을 갱신해야 모델의 구조·행위가 실제 코드와 일치함

## Ⅲ. 종류 및 비교

| 구분 | 구조 다이어그램 | 행위 다이어그램 |
|:---|:---|:---|
| 표현 대상 | 클래스, 컴포넌트, 배치처럼 정적인 관계를 표현함 | 시나리오, 상태 변화, 처리 흐름처럼 시간에 따라 달라지는 동작을 표현함 |
| 대표 예시 | Class, Component, Deployment Diagram이 대표적임 | Sequence, Activity, State Diagram이 대표적임 |
| 주된 활용 | 아키텍처와 설계 구조를 설명할 때 유용함 | API 호출 순서와 업무 절차를 설명할 때 유용함 |
| 주의할 점 | 세부를 지나치게 넣으면 구조가 오히려 흐려질 수 있음 | 실제 동작과 다르게 그리면 잘못된 운영 지식을 퍼뜨릴 수 있음 |
| 시간 표현 | 특정 시점의 구성 | 메시지 순서·상태 전이·활동 흐름 |
| 변경 계기 | 클래스·컴포넌트·배치 변경 | 시나리오·프로토콜·상태 로직 변경 |

> 요약: 구조 다이어그램은 정적 관계를, 행위 다이어그램은 메시지 순서·상태 전이·처리 흐름을 표현함.

## Ⅳ. 구성요소 및 구조

| 구성요소 | 설명 |
|:---|:---|
| 클래스 다이어그램 | 클래스의 속성·책임·연관·상속 관계를 표현함 |
| 시퀀스 다이어그램 | 객체·컴포넌트 사이의 시간순 메시지 교환을 표현함 |
| 액티비티 다이어그램 | 조건 분기·병렬 흐름·처리 순서를 표현함 |
| 컴포넌트·배치 다이어그램 | 컴포넌트 의존성과 노드별 실행 배치를 표현함 |

> 요약: 클래스·컴포넌트·배치는 정적 관계를, 시퀀스·액티비티는 메시지와 처리 순서를 표현함.

## Ⅵ. 실무 사례

1. 아키텍처 리뷰는 컴포넌트·배치 다이어그램을 갱신하고 문서·구현 불일치 수를 확인함
2. API 설계는 시퀀스 다이어그램으로 호출·예외 순서를 검토하고 연동 결함 수를 확인함

## Ⅶ. 결론

- UML은 검토 대상이 정적 구조인지 시간순 행위인지에 따라 다이어그램 유형을 선택함
