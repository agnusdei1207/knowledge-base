# 📖 【암기용】 개념 완전 이해

> 목적: 이 개념을 처음 보는 사람도 완벽히 이해하게 만든다. 시험 답안 양식이 아니라, 이해를 위한 친절한 설명이다.

## 한눈에
- **개요**: **UML(Unified Modeling Language)**은 **객체지향(Object-Oriented)** 소프트웨어의 구조와 동작을 표준화된 기호로 시각화하는 **모델링 언어**다. 글로만 수백 장을 쓰면 사람마다 다르게 이해하지만, 도면 기호(다이어그램)를 국제 표준으로 통일(Unified)해 같은 그림을 같은 의미로 읽게 한다.
- **왜 필요한가**: 말과 글만으로 소프트웨어 구조를 설명하면 사람마다 다르게 이해해서 설계 오류가 코딩 단계까지 넘어간다. UML은 클래스·관계·메시지 흐름을 표준 기호로 통일해, 코딩을 시작하기 전에 설계 오류를 시각적으로 미리 잡아낸다.
- **핵심 직관**: **정적(구조) 다이어그램**은 시간이 멈춘 사진처럼 "무엇이 무엇과 연결되어 있는가"를 보여주고(예: 클래스 다이어그램), **동적(행위) 다이어그램**은 동영상처럼 "시간 순서대로 무슨 일이 일어나는가"를 보여준다(예: 시퀀스 다이어그램).

## 핵심 용어 정리 (내부에 등장하는 것들)

| 용어 | 의미 | 비유 |
|:---|:---|:---|
| 객체지향(Object-Oriented) | 데이터(속성)와 동작(메서드)을 하나의 객체로 묶어 설계하는 프로그래밍 패러다임 — UML이 시각화하는 대상 | 상위 개념 |
| UML(Unified Modeling Language) | 객체지향 소프트웨어의 구조와 동작을 표준 기호로 시각화하는 모델링 언어 | 건축 도면의 표준 기호 체계 |
| 구조(정적) 다이어그램 | 시간이 멈춘 한 시점의 구성 요소와 관계를 보여주는 다이어그램군 | 사진 한 장 |
| 행위(동적) 다이어그램 | 시간 흐름에 따른 메시지·상태 변화를 보여주는 다이어그램군 | 동영상 |
| 클래스 다이어그램(Class Diagram) | 클래스의 속성·메서드와 클래스 간 관계를 표현하는 대표 구조 다이어그램 | 건물의 뼈대 도면 |
| 유스케이스 다이어그램(Usecase Diagram) | 액터(사용자)와 시스템이 제공하는 기능의 관계를 표현하는 대표 행위 다이어그램 | 이용 안내판 |
| 시퀀스 다이어그램(Sequence Diagram) | 객체 간 메시지 호출 순서를 시간 축(생명선)을 따라 표현하는 다이어그램 | 대화 스크립트 |
| 생명선(Lifeline) | 시퀀스 다이어그램에서 한 객체의 존재 기간을 나타내는 수직선 | 각 배우의 등장 구간 |
| 상태 다이어그램(State Machine Diagram) | 한 객체가 생애주기 동안 거치는 상태와 전이를 표현하는 다이어그램 | 신호등의 색 변화 |
| 일반화(Generalization) | 상속 관계 — 빈 삼각형 화살표로 표시 | 부모-자식 유전 |
| 실체화(Realization) | 인터페이스 구현 관계 — 점선과 빈 삼각형 화살표로 표시 | 계약서 이행 |
| 합성(Composition) | 전체가 사라지면 부분도 함께 사라지는 강한 전체-부분 관계 — 꽉 찬 마름모로 표시 | 자동차와 엔진 |
| 집합(Aggregation) | 전체가 사라져도 부분은 독립적으로 남는 약한 전체-부분 관계 — 빈 마름모로 표시 | 팀과 팀원 |
| 다중성(Multiplicity) | 관계에 참여하는 객체의 개수 범위(예: 1, 0..1, 1..*, 0..*) | 고객 한 명이 여러 주문을 가질 수 있음을 나타내는 숫자 |

## 깊이 이해

### 정적 vs 동적을 가르는 판별 원리
- "시간을 멈추고 봐도 설명이 되는가?"가 판별 기준이다. 클래스, 객체, 컴포넌트, 배포 다이어그램은 특정 시점의 구조를 보여주므로 정적(구조) 다이어그램이다. 반대로 "시간 순서가 없으면 의미가 없는가?"에 해당하면 동적(행위) 다이어그램이다 — 유스케이스, 시퀀스, 상태, 액티비티 다이어그램은 시간에 따른 흐름·전이·메시지 순서를 표현하므로 여기 속한다.

### 클래스 다이어그램의 관계 기호 — 합성과 집합을 예로 구분하기
- 합성(Composition, 꽉 찬 마름모): `자동차 1 ◆── 1 엔진`. 자동차 객체가 삭제되면 엔진 객체도 함께 메모리에서 사라진다. 자동차 클래스 내부에서 `new Engine()`으로 엔진을 직접 생성하고 소유하는 코드 구조가 이에 해당한다.
- 집합(Aggregation, 빈 마름모): `팀 1 ◇── 0..* 선수`. 팀 객체가 삭제되어도 선수 객체는 독립적으로 존재할 수 있다(다른 팀으로 이적 가능). 선수 객체를 외부에서 생성해 팀 객체에 참조로 전달(주입)하는 코드 구조가 이에 해당한다.
- 판별 원리: "부모 객체가 사라질 때 자식 객체의 생명주기도 함께 끝나는가?"로 가른다. 끝나면 합성, 자식이 독립적으로 살아남으면 집합이다.
- 다중성(Multiplicity) 표기: `주문 1 ── 1..* 주문항목`은 주문 하나가 최소 1개 이상의 주문항목을 가진다는 뜻이다. `0..1`은 있어도 되고 없어도 됨(선택)을, `*`(=0..*)는 개수 제한 없음을 뜻한다.

### 시퀀스 다이어그램을 예로 읽는 법
- 예: 로그인 요청이라면 ① 클라이언트 생명선이 서버 생명선으로 `login(id, pw)` 메시지 화살표를 보낸다 → ② 서버 생명선이 DB 생명선으로 `SELECT * FROM user WHERE id=?` 메시지를 보낸다 → ③ DB가 결과를 반환(점선 화살표)하면 → ④ 서버가 클라이언트에 `200 OK` 또는 `401 Unauthorized`를 반환한다.
- 조건 분기가 필요하면 `alt`(alternative) 프레임으로 성공/실패 두 경로를 사각 박스 안에 나눠 그린다. 이 표기 덕분에 API 호출 순서와 실패 시나리오를 코드를 보지 않고도 파악할 수 있다.

### 왜 14종이나 필요한가 — 다각도 뷰 관점
- 시스템 하나를 한 장의 그림으로 완전히 설명할 수 없다. 건물도 평면도·배관도·전기도가 따로 있듯, 소프트웨어도 "무엇으로 구성되는가(클래스)", "누가 무엇을 할 수 있는가(유스케이스)", "메시지가 어떤 순서로 오가는가(시퀀스)", "물리적으로 어디서 도는가(배포)"를 각각 다른 다이어그램으로 나눠 본다.
- 실무에서는 14종 전부를 그리지 않고, 프로젝트 성격에 맞는 3~4종(보통 클래스·시퀀스·유스케이스)만 선택해 사용한다.

### 비유
- 정적 다이어그램(클래스, 배포)은 인체의 골격도에 해당한다 — 시간이 지나도 뼈의 배치 자체는 안 변한다. 동적 다이어그램(시퀀스, 상태)은 혈액 순환도에 해당한다 — 심장이 뛰는 순서(시간)가 있어야 의미가 생긴다.

## 연결 개념
- **디자인 패턴(Design Patterns)**: 싱글톤·팩토리 등 재사용 가능한 설계 해법은 클래스 다이어그램의 관계 기호로 표현되어 카탈로그화되어 있다.
- **요구사항 분석**: 유스케이스 다이어그램은 요구사항 도출·명세 단계의 산출물을 시각화한 것이다.
- **역공학(Reverse Engineering)**: 소스 코드로부터 클래스 다이어그램을 자동 생성하는 도구(PlantUML 등)를 이용하면 문서와 코드의 불일치(Out of Sync) 문제를 완화할 수 있다.

# 📝 【답안용】 시험 답안 템플릿

> 목적: 시험장에서 25분에 그대로 쓰는 답안 양식. 작성방식(추상표현 금지·수치·도식·문제유형 전환)을 엄격히 지킨다.
> 핵심: 이 시험은 정보를 많이 나열하는 시험이 아니라, 문제 신호어에서 출제자 의도를 읽고 핵심 논점을 선별해 쓰는 시험이다.

## 핵심 인사이트 (3줄 요약)

> 1. **본질**: 복잡한 객체 지향(Object-Oriented) 소프트웨어 시스템의 아키텍처와 비즈니스 로직을, 이해관계자 간 시각적(Visual)으로 합의하고 문서화하기 위한 OMG 공인 국제 표준 모델링 언어다.
> 2. **가치**: 모호한 텍스트 기반 요구사항을 정형화된 기호(도면)로 치환하여 설계 결함을 조기에 발견하고, 정적(구조) 뷰와 동적(행위) 뷰의 다각도 교차 검증을 통해 시스템 붕괴를 방어한다.
> 3. **판단 포인트**: 14종의 다이어그램을 정적(Static)/동적(Dynamic)으로 완벽히 분류 매핑하고, 실무에서 가장 핵심이 되는 클래스(Class) 간의 관계(상속, 집합 등) 기호와 시퀀스(Sequence)의 생명선(Lifeline) 메커니즘을 도식화해야 한다.

## 출제 의도 및 답안 포인트

| 출제 의도 | 반드시 짚을 핵심 | 감점 회피 포인트 |
|:---|:---|:---|
| UML 2.0 표준의 양대 아키텍처 뷰(View) 분류 역량 | 구조(정적) 다이어그램 vs 행위(동적) 다이어그램 맵핑 | 유스케이스나 시퀀스를 정적 다이어그램으로 잘못 분류하는 치명적 오류 |
| 클래스 다이어그램 등 핵심 도면의 기호 및 관계 해석 | 일반화(상속 ◁-), 연관(실선), 집합(◇)과 합성(◆) 대조 | 상속(Generalization)과 실체화(Realization)의 점선/실선 기호를 혼동 |
| SDLC 전 주기에서 UML 모델이 변환되는 흐름 | 요구사항(유스케이스) -> 설계(클래스/시퀀스) -> 구현(코드) | UML을 기획자가 화면 그리는 와이어프레임(UI/UX) 도구로 착각하는 맹점 |

> 요약: 건축가가 도면 없이 건물 콘크리트부터 붓지 않듯, 소프트웨어 엔지니어도 UML 클래스 다이어그램(뼈대)과 시퀀스 다이어그램(데이터 흐름) 없이 IDE(코딩)를 열어서는 안 된다.

## Ⅰ. 개요 및 필요성

- 정의: 객체 지향 소프트웨어 시스템의 산출물을 명세(Specify), 시각화(Visualize), 구축(Construct), 문서화(Document)하기 위해 OMG(Object Management Group)에서 표준화한 14종의 모델링 언어
- 배경: 1990년대 객체 지향 패러다임 부상과 함께 Booch, Rumbaugh(OMT), Jacobson(OOSE) 등 파편화된 표기법 난립으로 개발자 간 의사소통 비용 및 학습 곡선(Learning Curve) 폭증
- 필요성: 시스템의 구조(클래스 관계)와 행위(메시지 통신)를 다차원 뷰(4+1 View)로 시각적 설계하여, 코딩(구현) 전 아키텍처 무결성을 검증하고 벤더 종속성 없는 명세서(Specification)를 확보하기 위함

## Ⅱ. UML 2.0 핵심 다이어그램 맵핑 (정적 vs 동적)

객체는 상태를 유지하는 '데이터(구조)'와 메시지를 주고받는 '행동(행위)'으로 이루어지므로, 다이어그램도 이를 완벽히 이등분한다.

```text
[ UML 2.0 다이어그램 분류 체계 (핵심 5대장 🌟) ]

1. 구조 다이어그램 (Structural / 정적 뷰) : 시간의 흐름 무시, 스냅샷 (명사/구조)
   ├─ 🌟 클래스 (Class)       : 속성과 오퍼레이션, 상속/관계 표현 (가장 중요)
   ├─ 객체 (Object)         : 특정 시점의 클래스 인스턴스 값 표현
   ├─ 컴포넌트 (Component)  : DLL, JAR 등 물리적 모듈 패키징 의존성 (API 인터페이스)
   └─ 배포 (Deployment)     : AWS 서버, 물리 DB 등 하드웨어 노드 매핑

2. 행위 다이어그램 (Behavioral / 동적 뷰) : 시간에 따른 로직 흐름 (동사/행동)
   ├─ 🌟 유스케이스 (Usecase) : 사용자(Actor) 관점의 시스템 제공 기능 (요구사항)
   ├─ 🌟 시퀀스 (Sequence)    : 객체 간 API/메시지 호출 순서를 생명선(Lifeline)으로 표현
   ├─ 🌟 상태 (State Machine) : 하나의 객체가 라이프사이클 동안 갖는 상태 전이(Transition)
   └─ 🌟 액티비티 (Activity)  : 업무 흐름(Flow)과 제어 분기(Fork/Join) 모델링
```

| 다이어그램 | 아키텍처적(엔지니어링) 역할과 타겟 독자 |
|:---|:---|
| **유스케이스** (Usecase) | **기획자/고객 타겟.** "시스템이 뭘 할 수 있나?" 요구사항을 도출하는 뼈대 (Includes/Extends 활용) |
| **클래스** (Class) | **백엔드 개발자 타겟.** "어떤 엔티티(DB)와 서비스가 엮여 있나?" 객체 지향 구조의 100% 설계도 |
| **시퀀스** (Sequence) | **통합 연동 개발자 타겟.** "프론트가 호출 시 백엔드가 외부 API를 찌르는 타이밍" (동기/비동기 화살표) |

> 요약: 고객 앞에서는 유스케이스(동그라미)를 그리고, DB 설계자 앞에서는 클래스 다이어그램(네모)을 그리고, 프론트/백엔드 API 연동 회의에서는 시퀀스 다이어그램(생명선)을 긋는 것이 소프트웨어 공학의 국룰이다.

---

## Ⅲ. 아키텍처 설계를 결정짓는 클래스(Class) 다이어그램의 관계(Relationship)

클래스 하나는 아무 의미가 없다. 진짜 설계는 "객체와 객체가 어떻게 의존(Dependency)하는가"를 긋는 화살표에 있다.

| 화살표 기호 | 관계(Relationship) 명칭 | 물리적 구현 및 아키텍처적 의미 (Java 기준) |
|:---:|:---|:---|
| ◁─ (빈 삼각형) | **일반화 (Generalization)** | `extends` (상속). 부모와 자식 간의 강력한 결합 (IS-A 관계) |
| ◁- - (점선 삼각형) | **실체화 (Realization)** | `implements` (인터페이스). 약속(오퍼레이션)을 실제로 코딩 구현함 |
| ◆─ (꽉 찬 마름모) | **합성 (Composition)** | '전체-부분' 관계. 부모(Car)가 죽으면 자식(Engine)도 메모리에서 삭제됨 (생명주기 일치) |
| ◇─ (빈 마름모) | **집합 (Aggregation)** | '전체-부분' 관계이나, 부모(Team)가 죽어도 자식(Player)은 살아남음 (생명주기 독립) |

> 요약: 합성과 집합을 헷갈리면 큰일 난다. 회사(부모)가 망했을 때 회사 법인차량(자식)은 꽉 찬 마름모(합성)라 같이 날아가지만, 직원(자식)은 빈 마름모(집합)라 해고될 뿐 다른 회사로 이직(생존)할 수 있다.

---

## Ⅳ. 극복해야 할 시스템적 리스크 및 역공학(Reverse Engineering) 튜닝

방대한 UML 문서는 프로젝트의 속도를 갉아먹는 폭포수(Waterfall)의 적폐로 전락할 위험이 매우 높다.

| 리스크 요인 | 발생 시나리오 및 프로젝트 붕괴 원인 | 아키텍처 대응 방안 (실무 튜닝) |
|:---|:---|:---|
| **문서와 코드의 괴리 (Out of Sync)** | 초기 설계 시 완벽한 클래스 다이어그램을 그렸으나, 개발 중 코드를 수정하고 다이어그램을 업데이트하지 않아 3개월 뒤 쓸모없는 쓰레기 문서(Dead Document)로 전락 | **역공학(Reverse Engineering) 툴체인 튜닝**: IntelliJ 기반 플러그인(PlantUML 등)을 CI/CD와 연동하여, Java 소스 코드가 푸시되면 자동으로 최신 클래스 다이어그램을 생성(Code-to-UML)하도록 파이프라인 무인화 |
| 모델링 병목 현상 (Analysis Paralysis) | 완벽한 도면을 그리겠다며 14종 다이어그램을 Visio로 정교하게 그리느라 한 달을 낭비하여 타임투마켓(Time-to-Market) 붕괴 초래 | **애자일 모델링(Agile Modeling)** 철학 이식. "문서를 위한 모델링"을 금지하고, 화이트보드에 스케치 후 사진만 찍고 지우는 버림형(Throw-away) 소통 도구로 한정 |

> 요약: 그림 그리는 데 시간을 쏟지 마라. UML은 코딩을 하기 위해 잠시 거쳐가는 '지도'일 뿐이다. 지도를 너무 정성스럽게 그리느라 출발(코딩)조차 못하는 것이 가장 멍청한 짓이다.

## Ⅴ. 실무 적용 방안 및 결론

**적용 방안 3개:**
1. [PlantUML 기반 순방향/역방향 자동화(Docs as Code)] 카카오/네이버 등 플랫폼 연동 API 가이드 작성 시, 그림 파일(PNG) 캡처본을 첨부하는 구시대적 방식을 폐기하고 마크다운(Markdown) 문서 내에 PlantUML 텍스트 스크립트를 삽입해 렌더링되도록 처리하여 형상(Git) 변경 추적성 확보
2. [마이크로서비스(MSA) 시퀀스 다이어그램 기반 Saga 설계] 3개의 MSA(주문, 결제, 재고) 모듈 간 분산 트랜잭션 장애 발생 시 롤백(보상 트랜잭션) 방안을 수립하기 위해, 시퀀스 다이어그램의 `Alt`(조건 분기) 기호를 통해 결제 실패 시 재고 원복(Restore) API가 트리거되는 비동기 라이프라인(Lifeline) 사전 시각화 설계
3. [상태 다이어그램 기반 비즈니스 로직 테스트 커버리지 100%] '쇼핑몰 환불' 처리 비즈니스 로직 TDD 구현 시, 머릿속으로 예외(Edge) 케이스를 상상하지 않고 상태 머신(State Machine) 다이어그램의 상태 전이 화살표(Transition) 화살표 갯수만큼 JUnit 단위 테스트 메서드(메소드)를 1:1 강제 매핑(Test Case 도출)

**결론:**
- 기술사 판단: UML은 소프트웨어 엔지니어링이 획득한 '바벨탑의 극복'이다. 개발 언어(Java, Python)나 프레임워크가 무엇이든, UML이라는 시각적 기호 언어를 통해 설계자와 개발자는 아키텍처의 구조(정적)와 흐름(동적)을 오해 없이(Unambiguous) 합의할 수 있다.
- 향후 방향: 최근 모델 주도 아키텍처(MDA)와 AI(LLM) 코딩 에이전트의 발전으로, UML 다이어그램을 그리면 비즈니스 로직(Spring Boot 엔티티 및 컨트롤러 코드)이 100% 뼈대로 자동 제네레이션(Generation)되는 형태로, 설계와 구현 간의 갭(Gap)이 제로(0)에 수렴하는 시대로 진화 중이다.
