## 미리 알고가기

- UML은 소프트웨어 구조와 동작을 표준 기호로 표현하는 모델링 언어임
- 구조 다이어그램은 정적 관계를, 행위 다이어그램은 시간 흐름과 상호작용을 설명함
- Model drift는 설계 문서와 실제 구현이 어긋나는 상태를 뜻함

## Ⅰ. 개요

- **정의/개념**: UML 다이어그램은 소프트웨어 시스템의 구조와 행위와 상호작용을 표준 표기법으로 표현해 설계 의사소통과 검토를 돕는 모델링 도구임.
- **배경/필요성**: 복잡한 시스템은 텍스트만으로 구조와 흐름을 공유하기 어려우므로, 이해관계자가 같은 그림을 보고 설계 의도와 관계를 빠르게 파악할 수 있는 공통 표기 체계가 필요함.

## Ⅱ. 특징

- 구조 관점과 행위 관점을 나눠 서로 다른 질문에 답할 수 있게 함
- 개발자, 기획자, 아키텍트 사이의 의사소통 비용을 줄임
- 목적 없이 많이 그리면 유지 비용만 늘고 실제 설계 판단에는 도움이 약해짐
- 구현 변경 시 관련 다이어그램을 갱신해야 모델의 구조·행위가 실제 코드와 일치함

## Ⅲ. 종류 및 비교

| 구분 | 구조 다이어그램 | 행위 다이어그램 |
|:---|:---|:---|
| 표현 대상 | 클래스, 컴포넌트, 배치처럼 정적인 관계를 표현함 | 시나리오, 상태 변화, 처리 흐름처럼 시간에 따라 달라지는 동작을 표현함 |
| 대표 예시 | Class, Component, Deployment Diagram이 대표적임 | Sequence, Activity, State Diagram이 대표적임 |
| 주된 활용 | 아키텍처와 설계 구조를 설명할 때 유용함 | API 호출 순서와 업무 절차를 설명할 때 유용함 |
| 주의할 점 | 세부를 지나치게 넣으면 구조가 오히려 흐려질 수 있음 | 실제 동작과 다르게 그리면 잘못된 운영 지식을 퍼뜨릴 수 있음 |

> 요약: UML은 그림 수를 늘리는 도구가 아니라 설계에서 무엇을 합의해야 하는지에 맞춰 관점을 골라 쓰는 도구임.

## Ⅳ. 구성요소 및 구조

| 구성요소 | 설명 |
|:---|:---|
| Class Diagram | 객체의 속성, 책임, 관계를 표현해 도메인 구조와 책임 분배를 보여줌 |
| Sequence Diagram | 시간 순서에 따른 메시지 교환을 표현해 협력 흐름과 호출 순서를 설명함 |
| Activity Diagram | 조건 분기와 병렬 흐름을 포함한 처리 절차를 정리함 |
| Component and Deployment Diagram | 컴포넌트 의존성과 실행 배치를 표현해 실제 시스템 구성을 이해하게 함 |

## Ⅴ. 원리 및 절차 흐름도

```text
+-------------+     +-------------+     +-------------+     +-------------+
| 모델 목적 정의  | --> | 다이어그램 선택 | --> | 핵심 요소 표현 | --> | 리뷰/정합 관리 |
+-------------+     +-------------+     +-------------+     +-------------+
```

1. **모델 목적 정의**: 구조를 설명할지, 동작을 설명할지 먼저 정함
2. **다이어그램 선택**: 목적에 맞는 UML 유형만 고름
3. **요소 표현**: 검토할 구조·상호작용·상태 전이에 필요한 관계와 흐름을 표현함
4. **리뷰 및 정합 관리**: 구현과 맞는지 확인하며 갱신 책임을 유지함

## Ⅵ. 실무 적용 및 유의점

1. 아키텍처 리뷰에서는 클래스 다이어그램과 컴포넌트 다이어그램처럼 의사결정에 직접 필요한 모델만 유지하되 문서가 구현보다 늦게 바뀌지 않도록 변경 시 갱신 책임을 묶어 관리하고 문서-구현 불일치 건수와 최근 갱신 시점으로 확인함
2. API 협력 설계에서는 시퀀스 다이어그램으로 호출 순서를 설명하되 표기 규칙이 팀마다 다르면 해석이 갈리므로 공통 템플릿을 운영하고 표기 오류율과 연동 결함 건수로 확인함

## Ⅶ. 결론

UML은 검토 목적에 맞는 구조·행위·상호작용을 표준 표기법으로 표현해 설계 관계와 구현 정합성을 확인하는 도구임.
