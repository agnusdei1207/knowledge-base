# 📖 【암기용】 개념 완전 이해

## 한눈에
- **개요**: 관계형 데이터베이스의 뼈대를 이루는 핵심 룰로, 행의 고유성 보장(개체)과 테이블 간 올바른 연결 보장(참조)을 의미한다.
- **왜 필요한가**: 유령 데이터(식별 불가)나 고아 데이터(부모 없음) 생성을 막아 DB 신뢰성을 유지하기 위해 필요하다.
- **핵심 직관**: **개체 무결성**은 "모든 국민은 고유한 주민번호가 있다", **참조 무결성**은 "출생신고 부모란에는 실존하는 주민번호만 쓸 수 있다"이다.

## 핵심 용어 정리

| 용어/표기 | 의미 | 비유·예 |
|:---|:---|:---|
| 기본키 (Primary Key, PK) | 테이블 내 각 튜플을 유일하게 식별하는 속성 | 학번, 사번, 주민번호 |
| 외래키 (Foreign Key, FK) | 다른 테이블 기본키를 참조하여 관계를 맺는 속성 | 학생의 '소속 학과 코드' |
| NULL 값 | 알 수 없음(Unknown)을 의미하는 특수 상태 | 미부여 신입생 학번 |
| 고아 레코드 (Orphan) | 부모 데이터가 삭제되어 허공을 가리키는 자식 데이터 | 폐지된 학과 코드를 가진 학생 |

## 깊이 이해
- **배경·문제의식**: RDB는 테이블을 쪼개고 조인으로 연결한다. 행을 식별할 수 없거나 연결 고리가 끊어지면 릴레이션 전체가 붕괴된다.
- **작동 원리**: 개체 무결성은 PK가 NULL일 수 없고 중복될 수 없게 강제한다. 참조 무결성은 FK 값이 참조 테이블 PK에 존재해야 함을 강제한다(FK는 NULL 허용 가능).
- **비유**: 모든 호텔 방은 번호가 있어야 하며(개체), 예약 명부의 방 번호는 실제 존재하는 방이어야 한다(참조).
- **구체 예시**: 사원 테이블에서 사번이 NULL인 사원은 등록할 수 없고, 없는 부서코드를 배정할 수 없다.
- **흔한 오해·주의점**: 참조 무결성에서 "외래키는 절대 NULL일 수 없다"고 오해하나, 비즈니스 요건에 따라 FK는 NULL 허용이 가능하다(예: 부서 배정 전 사원).

## 연결 개념
- **데이터베이스 정규화 (Normalization)**: 테이블을 분리하여 PK/FK 구조를 만드는 과정.
- **조인 (Join)**: 참조 무결성이 보장된 FK-PK 쌍으로 테이블을 연결하는 연산.

# 📝 【답안용】 시험 답안 템플릿

## 핵심 인사이트 (3줄 요약)

> 1. **본질**: 관계형 데이터 모델에서 튜플의 식별성(기본키)과 릴레이션 간 연관성(외래키)을 보장하는 규약
> 2. **가치**: 미식별 데이터나 고아 데이터 발생을 차단하여 조인(Join) 연산의 정확성을 담보
> 3. **판단 포인트**: 참조 무결성 위배 상황 시 대응 옵션(CASCADE, RESTRICT 등) 명시

## 출제 의도 및 답안 포인트

| 출제 의도 | 반드시 짚을 핵심 | 감점 회피 포인트 |
|:---|:---|:---|
| DB의 근본적인 두 제약 조건 이해 및 실무 적용 능력 평가 | 개체 무결성(PK Not Null+Unique)과 참조 무결성(FK 유효성) 정의 | 참조 무결성 위배 대응 전략 누락 |

> 요약: 개체 식별을 위한 PK 규칙과 테이블 간 조인 정합성을 위한 FK 규칙으로 모델을 지탱한다.

---

## Ⅰ. 개요 및 필요성

- 개요: RDB에서 튜플의 유일성(개체 무결성)과 릴레이션 간 논리적 연결의 정합성(참조 무결성)을 보장하는 규약
- 배경: 정규화 구조에서 삽입, 삭제, 갱신 시 조인 고리가 단절되는 데이터 불일치 빈발
- 필요성: 시스템 내 유령 데이터 및 고아 데이터 원천 차단하여 정보 신뢰성과 조인 결과 보장

---

## Ⅱ. 구조 및 구성요소

```text
[개체 무결성] (내부 식별)                    [참조 무결성] (외부 연관)
사원(Employee) 튜플                          부서(Department) 튜플
+------+------+------+                       +--------+--------+
| 사번 | 이름 | 부서 | ----(FK 참조)------> | 부서ID | 부서명 |
+------+------+------+                       +--------+--------+
  PK(Not Null, Unique)                         PK(기준 데이터 존재)
```

| 구분 | 적용 대상 | 제약 조건 내용 | 구현 수단 |
|:---|:---|:---|:---|
| 개체 무결성 | 기본키 (PK) | 어떠한 속성도 NULL 허용 안 됨, 중복 값 불가 | `PRIMARY KEY` 제약 (Unique Index) |
| 참조 무결성 | 외래키 (FK) | 부모 PK 값이거나 NULL이어야 함 | `FOREIGN KEY` 제약 및 참조 룰(ON DELETE 등) |

> 요약: 개체 무결성은 테이블 내부 행 식별을 책임지고, 참조 무결성은 테이블 외부와의 연결을 책임진다.

---

## Ⅲ. 동작원리 및 흐름도

```text
DML 발생 -> 무결성 검증 엔진 -> PK 중복/NULL 체크(개체) -> 참조 테이블 스캔(참조) -> 조치(Commit/Rollback/Cascade)
```

- 1단계 개체 검증(삽입): `INSERT` 시 PK NULL 여부 확인, 유니크 인덱스로 기존 중복 충돌 검사
- 2단계 참조 검증(자식 삽입): 새 FK 입력 시, 부모 테이블 PK 인덱스를 룩업해 실제 값 존재 확인
- 3단계 참조 검증(부모 삭제): 부모 테이블 PK 삭제 시, 자식 테이블에 참조 레코드가 있는지 검사
- 4단계 제약조건 액션: 부모 삭제 시 자식 참조 발견되면 정의된 규칙(RESTRICT, CASCADE 등) 처리

> 요약: 인덱스 기반 룩업을 거치며 부모/자식 의존성에 따라 연쇄 조치를 트리거한다.

---

## Ⅳ. 특징
- 근본적 방어막: 애플리케이션 로직 오류와 상관없이 DB 엔진 최하단에서 데이터 오염 방지
- 상호 의존성: 참조 무결성은 반드시 대상 테이블의 개체 무결성(PK)이 확립되어야 성립 가능
- 연산 부하: 데이터 삽입/삭제 시 연관 인덱스를 교차 조회하므로 트랜잭션 TPS 저하 유발
- 외래키 NULL 허용: 개체 무결성과 달리 참조 무결성은 비즈니스 로직에 따라 비참조 상태(NULL) 허용 가능

> 요약: 무결성을 완벽히 지키지만 강한 결합도를 생성하여 대규모 DML 수행 시 성능 제약이 된다.

---

## Ⅴ. 심화 비교 및 적용 판단

| 대응 옵션 (부모 삭제 시) | 동작 방식 | 선택 기준 / 적용 시나리오 |
|:---|:---|:---|
| RESTRICT | 자식에 참조 튜플이 있으면 삭제 즉시 거부(Rollback) | 재무 데이터 등 삭제 시 심각한 불일치 예상 시 |
| CASCADE | 참조하는 자식 튜플도 함께 자동으로 삭제/수정 | 게시글 삭제 시 댓글 연쇄 삭제 등 강한 종속 시 |
| SET NULL | 부모 삭제 시, 참조하던 자식 FK 값을 NULL로 변경 | 부서 폐지 시 사원의 소속 부서를 미정으로 둘 때 |
| SET DEFAULT | 사전에 정의된 기본값(Default)으로 FK 값 변경 | 탈퇴 회원 글 소유자를 '알수없음' 계정으로 돌릴 때 |

> 요약: 비즈니스 룰에 따라 4가지 참조 무결성 대응 액션 중 최적 방식을 설계해야 한다.

**리스크·대응:**
- 성능 저하: 대규모 배치 작업 시 FK 검사 병목 → 일괄 적재 시 `SET FOREIGN_KEY_CHECKS = 0` 지연 (지표: 배치 소요시간)
- MSA 환경 제약: 마이크로서비스 간 물리적 FK 불가 → API 조합, 보상 트랜잭션(Saga) 기반 최종 일관성 확보 (지표: 데이터 정합성 성공률)

---

## Ⅵ. 실무 적용 및 결론

**적용 방안 3개:**
1. 대리키(Surrogate Key) 활용: 주민번호 등 복합/의미 속성 대신 인공키(Auto Increment)를 PK로 삼아 갱신 비용 최소화
2. 논리적 삭제(Soft Delete) 도입: 참조 무결성 에러를 피하기 위해 `is_deleted = 'Y'` 컬럼을 사용해 물리적 삭제 회피
3. 인덱스 자동화 검토: 조인 성능 향상을 위해 FK 컬럼에 명시적 Non-Clustered 인덱스 생성

**결론:**
- 기술사 판단: 개체/참조 무결성은 RDBMS 존재 이유이므로 단일 DB 내에서는 반드시 물리적 스키마로 강제해야 시스템 부채를 예방할 수 있다.
- 향후 방향: 최근 NoSQL 및 MSA 전환 기조에서는 DB 엔진 수준의 강결합 제약을 풀고, 애플리케이션 레벨의 유연한 무결성 검증으로 전환 중이다.
