# 📖 【암기용】 개념 완전 이해

> 목적: 개체 무결성과 참조 무결성을 처음 보는 사람도 PK와 FK가 어떤 오류를 막는지 이해하게 만든다. 시험 답안 양식이 아니라, 이해를 위한 설명이다.

## 한눈에
- **개요**: 개체 무결성과 참조 무결성은 **무결성 제약 조건**(103) 중 각각 "행을 유일하게 식별할 수 있는가"와 "테이블 간 관계가 실제 존재하는 행을 가리키는가"를 담당하는 두 축이다.
- **왜 필요한가**: 주문 행이 고객을 가리키는데 그 고객 행이 없으면 청구·배송·CS 처리가 중간에서 끊긴다. 개체 무결성은 중복·결측 식별자를, 참조 무결성은 고아 레코드(orphan row)를 차단한다.
- **핵심 직관**: 주민등록번호가 비어 있거나 중복이면 사람을 구분할 수 없고(개체 무결성 위반), 서류에 존재하지 않는 보호자 이름을 적으면 가족관계가 성립하지 않는다(참조 무결성 위반).

## 핵심 용어 정리 (내부에 등장하는 것들)

| 용어 | 의미 | 비유 |
|:---|:---|:---|
| 무결성 제약 조건 (상위 개념) | DBMS가 강제하는 데이터 품질 규칙 전체 — 개체·참조는 그중 두 축 | 창고 출고 검사대 규칙 전체 |
| 개체 무결성 (Entity) | 기본키는 NULL 불가 + 중복 불가 | 주민등록번호 빈칸·중복 불가 |
| 참조 무결성 (Referential) | 외래키 값은 부모 테이블에 실제 존재해야 함 | 존재하지 않는 보호자 기입 금지 |
| 후보키 (Candidate Key) | 유일성·최소성을 만족해 PK가 될 자격이 있는 속성(들) | 학번도, 주민번호도 각각 학생을 유일 식별 가능 |
| 기본키 (Primary Key) | 후보키 중 실제로 선택되어 행 식별에 쓰이는 키 | 여러 후보 중 대표로 뽑힌 학번 |
| 대체키 (Alternate Key) | PK로 선택되지 않은 나머지 후보키 — 보통 UNIQUE로 구현 | PK로 안 뽑힌 주민번호를 UNIQUE로 관리 |
| 외래키 (Foreign Key) | 다른 테이블의 PK/UNIQUE를 참조하는 컬럼 | 주문서의 "고객번호" 칸 |
| 고아 레코드 (Orphan Row) | FK가 가리키는 부모 행이 존재하지 않는 자식 행 | 보호자가 없는 것으로 등록된 아이 |
| CASCADE | 부모 변경(삭제/수정)을 자식 행에 그대로 전파 | 부모 회사 폐업 시 소속 직원기록도 함께 폐기 |
| RESTRICT / NO ACTION | 자식 행이 있으면 부모 변경 자체를 차단 | 자녀가 있으면 부모 등록을 말소할 수 없음 |
| SET NULL | 부모가 사라지면 자식의 FK만 NULL로 비움 | 보호자가 사라져도 아이 기록은 남고 보호자 칸만 공란 |

## 깊이 이해

### 개체 무결성 판별: PK의 두 조건이 왜 둘 다 필요한가
- PK는 NOT NULL과 UNIQUE를 동시에 만족해야 한다. 학생 10,000명 테이블에서 학번이 NULL인 행이 하나라도 있으면 "그 학번의 학생"이라는 질의 자체가 성립하지 않는다. 학번이 중복되면 `WHERE 학번=12345`가 1건이 아니라 2건 이상을 반환해 성적 처리 같은 단건 업데이트가 엉뚱한 행까지 건드릴 수 있다. 둘 중 하나만 지켜도 "행을 유일하게 가리킨다"는 목적이 깨진다.

### 참조 무결성 판별: FK 값이 부모에 실제로 있는가
- `orders` 100만 건 중 `customer_id = 99999`인 행이 있는데 `customers` 테이블에 99999가 없으면 이 행은 고아 레코드다. 이런 행은 `orders LEFT JOIN customers ON ... WHERE customers.customer_id IS NULL` 같은 안티조인(anti-join)으로 찾아낼 수 있다. FK 제약이 걸려 있으면 애초에 이런 insert 자체가 DB 단에서 거부되어 이 검사가 항상 0건이 되도록 강제된다.

### CASCADE·RESTRICT·SET NULL, 언제 무엇을 쓰나
- 고객 1명을 삭제하는데 그 고객의 주문이 1,200건 있다고 하자.
  - **CASCADE**: 주문 1,200건도 함께 삭제된다. 회계·감사 이력이 함께 사라지므로 원장성 데이터에는 위험하다.
  - **RESTRICT(NO ACTION)**: 주문이 남아있는 한 고객 삭제 자체가 거부된다. 먼저 주문을 정리해야만 고객을 지울 수 있어 실수로 인한 대량 삭제를 막는다.
  - **SET NULL**: 주문 1,200건은 그대로 남고 `customer_id`만 NULL이 된다. 탈퇴 회원의 과거 매출 통계는 유지하되 개인 식별 연결만 끊고 싶을 때(익명화) 적합하다.
- 실무 기준: 원장·정산 데이터는 RESTRICT를 기본으로, "부모 없이 자식이 존재할 이유가 없는" 종속 관계(예: 주문-주문상세)만 CASCADE를 허용한다.

### 후보키·대체키가 왜 필요한가
- 학생 테이블에서 학번과 주민등록번호는 둘 다 각 학생을 유일하게 식별할 수 있으므로 둘 다 후보키다. 이 중 하나(보통 학번)를 PK로 선택하면, 선택받지 못한 주민등록번호는 대체키가 되고 실제 구현은 UNIQUE 제약으로 한다. PK 하나만으로는 "주민번호 중복 가입"까지는 못 막으므로 대체키 개념이 필요하다.

## 연결 개념
- 무결성 제약 조건 (103) — 상위 개념, 개체·참조 무결성은 그중 두 축
- 후보키·대체키 — PK를 선정하기 이전 단계의 키 분류
- 정규화 — FK 관계가 성립할 수 있는 테이블 구조를 만드는 전제 작업

## 핵심 인사이트 (3줄 요약)

> 1. **본질**: 개체 무결성은 PK의 NOT NULL·UNIQUE, 참조 무결성은 FK의 부모 존재성과 삭제·수정 정책을 보장한다.
> 2. **가치**: 중복 식별자, NULL 키, 고아 레코드, 잘못된 삭제 전파를 차단해 원장 데이터 품질을 유지한다.
> 3. **판단 포인트**: cascade, restrict, set null, soft delete 중 업무 보존 기준과 감사 요구에 맞는 정책을 선택해야 한다.

> 요약: 이 문제는 행 식별성과 관계 일관성을 업무 삭제 정책과 운영 지표로 설명하는 답안을 요구한다.

## Ⅰ. 개요 및 필요성

- 개요: 개체·참조 무결성은 PK/FK 관계 규칙이다.
- 배경: 행 식별자가 비어 있거나 자식 행이 없는 부모를 참조하면 조회 누락, 집계 오류, 삭제 손실이 발생한다.
- 필요성: PK의 NOT NULL·UNIQUE와 FK의 cascade, restrict, set null 정책으로 고아 레코드와 삭제 전파를 통제해야 한다.

---

## Ⅱ. 구조 및 구성요소

```text
부모 테이블 PK/UK -> 자식 테이블 FK -> DML 제약 검사 -> 삭제/수정 정책 적용
                   / cascade
                   / restrict
                   / set null
```

| 구성요소 | 역할 | 특이사항 |
|:---|:---|:---|
| Primary Key | 행을 유일하게 식별 | NOT NULL, UNIQUE 동시 만족 |
| Foreign Key | 부모 행 존재성 검사 | 부모 PK 또는 UNIQUE 참조 |
| Cascade | 부모 변경을 자식에 전파 | 주문상세처럼 생명주기 종속 시 적용 |
| Restrict/No Action | 자식 존재 시 부모 삭제 차단 | 원장·감사 데이터 보존 시 적용 |
| Set Null | 부모 제거 시 FK를 NULL 처리 | 선택 관계와 익명화 요구에 사용 |

> 요약: 개체 무결성은 PK로 행을 식별하고, 참조 무결성은 FK와 삭제 정책으로 관계의 존재성을 유지한다.

---

## Ⅲ. 동작원리 및 흐름도

```text
DML 요청 -> PK NOT NULL/UNIQUE 검사 -> FK 부모 존재 검사 -> 정책 적용 -> Commit/Rollback
```

| 단계 | 처리 내용 | 검증 기준 |
|:---:|:---|:---|
| 1 | INSERT 시 PK NULL·중복 여부 확인 | PK violation 0건 |
| 2 | INSERT/UPDATE 시 FK 부모 행 조회 | orphan row 0건 |
| 3 | DELETE/UPDATE 부모키 요청 수신 | 자식 행 존재 여부 확인 |
| 4 | cascade, restrict, set null 정책 실행 | 업무 보존 규칙 충족 |
| 5 | 트랜잭션 commit 또는 rollback | 감사 로그와 row count 일치 |

> 요약: DBMS는 키 검사와 관계 검사 후 업무 정책에 맞게 자식 행 처리 방식을 결정한다.

## Ⅳ. 특징

| 구분 | 개체 무결성 | 참조 무결성 | 판단 포인트 |
|:---|:---|:---|:---|
| 대상 | 단일 테이블 행 식별 | 테이블 간 관계 | PK와 FK의 책임 구분 |
| 제약 | PK NOT NULL, UNIQUE | FK 존재성, 삭제 정책 | 부모·자식 생명주기 분석 |
| 위반 사례 | NULL 고객ID, 중복 주문ID | 없는 고객을 참조한 주문 | orphan count 0건 |
| 운영 영향 | 인덱스 기반 중복 검사 | FK 검사와 잠금 발생 | 참조 컬럼 인덱스 필요 |

> 요약: 개체 무결성은 행 자체의 식별성, 참조 무결성은 행 사이 관계의 존재성을 보장한다.

## Ⅴ. 심화 비교 및 적용 판단

| 구분 | 기존/대안 | 본 키워드 | 선택 기준 |
|:---|:---|:---|:---|
| 구조 | 애플리케이션 관계 검증 | DB PK/FK 제약 | 다중 서비스·배치 갱신 경로 |
| 비용/성능 | DML 검사 비용 없음 | FK lookup, lock 발생 | 참조 컬럼 인덱스와 TPS 측정 |
| 운영/위험 | 고아 레코드 가능 | 제약 위반으로 저장 차단 | 원장·정산·감사 데이터 우선 적용 |

> 요약: 핵심 업무 관계는 PK/FK로 DB에서 강제하고, 대량 적재 구간은 임시 비활성보다 staging 검증을 우선한다.

| 리스크 | 원인 | 대응 방안 | 확인 지표 |
|:---|:---|:---|:---|
| 고아 레코드 | FK 미설정 또는 검증 우회 | FK 추가, anti-join 정기 점검 | orphan row 0건 |
| 삭제 전파 사고 | cascade 범위 과다 | restrict 기본, cascade 목록 승인 | cascade delete row count |
| 잠금 대기 | 자식 FK 인덱스 누락 | FK 컬럼 인덱스 생성 | lock wait 1초 이하 |

> 요약: 참조 무결성 운영의 핵심 리스크는 고아 레코드와 삭제 전파이며, 정책 승인과 지표 감시가 필요하다.

| 점검 항목 | 목표 기준 | 측정 방법 |
|:---|:---|:---|
| 식별성 | PK NULL 0건, 중복 0건 | catalog, duplicate query |
| 관계성 | orphan row 0건 | left anti join 검사 |
| 삭제 정책 | cascade 영향 row 사전 산정 | dry-run count, audit log |

> 요약: PK 중복, FK 고아, 삭제 영향 행 수를 배포 전후로 측정해 무결성 통제를 검증한다.

## Ⅵ. 실무 적용 및 결론

**적용 방안 3개 (필수 — 단계별 또는 항목별):**
1. 모든 원장 테이블에 surrogate key 또는 natural key 기준 PK를 두고, 업무 식별자는 UNIQUE로 추가해 중복 가입·중복 주문을 차단함
2. FK 삭제 정책은 기본 restrict로 두고, 생명주기 종속 관계만 cascade를 허용하며 배포 전 dry-run row count를 승인함
3. FK 컬럼 인덱스와 orphan 검사를 운영 점검표에 포함해 lock wait 1초 이하, orphan 0건을 유지함

**결론 (2줄):**
- 기술사 판단: 정산·계약·주문 원장은 PK/FK 필수, 로그·임시 적재 테이블은 staging 검증 후 본 테이블 반영 방식 선택
- 향후 방향: 마이크로서비스 환경에서도 데이터 계약과 참조 검증 배치를 결합해 관계 품질을 유지해야 함
