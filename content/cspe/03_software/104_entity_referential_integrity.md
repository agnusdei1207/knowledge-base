# 📖 【암기용】 개념 완전 이해

> 목적: 개체 무결성과 참조 무결성을 처음 보는 사람도 PK와 FK가 어떤 오류를 막는지 이해하게 만든다. 시험 답안 양식이 아니라, 이해를 위한 설명이다.

## 한눈에
- **개요**: 기본키로 행을 식별하고 외래키로 관계의 존재성을 보장하는 규칙
- **왜 필요한가**: 주문 행이 고객을 가리키는데 고객 행이 없으면 청구, 배송, CS 처리가 끊긴다. PK와 FK는 중복 식별자와 고아 레코드를 차단한다.
- **핵심 직관**: 주민등록번호가 비어 있거나 중복이면 사람을 구분할 수 없고, 존재하지 않는 보호자를 적으면 가족 관계가 깨지는 것과 같다.

## 깊이 이해
- **배경·문제의식**: 관계형 DB에서 각 행은 식별 가능해야 하고, 테이블 간 관계는 실제 존재하는 행을 참조해야 한다. 이를 지키지 않으면 조회 결과 누락, 집계 오류, 삭제 손실이 발생한다.
- **작동 원리**: 개체 무결성은 PK가 NOT NULL과 UNIQUE를 만족하게 한다. 참조 무결성은 FK 값이 부모 테이블의 PK 또는 UNIQUE 값에 존재하게 하고, 부모 삭제·수정 시 cascade, restrict, set null 정책을 적용한다.
- **비유**: 회사 사원번호가 비어 있으면 급여 지급 대상을 찾을 수 없고, 팀 코드가 없는 부서를 가리키면 조직도가 끊긴다.
- **구체 예시**: `orders.customer_id` FK가 `customers.customer_id`를 참조하면 없는 고객 주문은 저장되지 않는다. 고객 삭제 시 주문 보존이 필요하면 restrict, 탈퇴 이력 분리가 필요하면 set null 또는 soft delete를 선택한다.
- **흔한 오해·주의점**: FK를 성능 때문에 무조건 빼면 데이터 품질 검증 책임이 애플리케이션과 배치로 흩어진다. 핵심 원장 관계는 DB 제약으로 통제해야 한다.

## 연결 개념
- Primary Key — 행 식별자와 개체 무결성의 기준
- Foreign Key — 부모·자식 관계와 참조 무결성의 기준
- Cascade Policy — 부모 변경 시 자식 처리 정책

# 📝 【답안용】 시험 답안 템플릿

> 목적: 시험장에서 25분에 그대로 쓰는 답안 양식. 작성방식(추상표현 금지·수치·도식·문제유형 전환)을 엄격히 지킨다.
> 핵심: 개체·참조 무결성은 PK/FK 문법이 아니라 식별 가능성과 관계 일관성을 보장하는 데이터 모델 통제이다.

## 핵심 인사이트 (3줄 요약)

> 1. **본질**: 개체 무결성은 PK의 NOT NULL·UNIQUE, 참조 무결성은 FK의 부모 존재성과 삭제·수정 정책을 보장한다.
> 2. **가치**: 중복 식별자, NULL 키, 고아 레코드, 잘못된 삭제 전파를 차단해 원장 데이터 품질을 유지한다.
> 3. **판단 포인트**: cascade, restrict, set null, soft delete 중 업무 보존 기준과 감사 요구에 맞는 정책을 선택해야 한다.

## 출제 의도 및 답안 포인트

| 출제 의도 | 반드시 짚을 핵심 | 감점 회피 포인트 |
|:---|:---|:---|
| PK/FK 기반 무결성 이해 확인 | 개체 무결성, 참조 무결성, orphan prevention | PK와 FK 문법만 나열 |
| 삭제·수정 정책 판단 확인 | cascade, restrict, set null, no action | cascade를 모든 관계에 적용 |
| 실무 운영 리스크 인식 확인 | FK 인덱스, lock wait, soft delete, 감사 이력 | 성능 이유로 FK 제거만 주장 |

> 요약: 이 문제는 행 식별성과 관계 일관성을 업무 삭제 정책과 운영 지표로 설명하는 답안을 요구한다.

---

## Ⅰ. 개요 및 필요성

- 개요: 개체·참조 무결성은 PK/FK 관계 규칙이다.
- 배경: 행 식별자가 비어 있거나 자식 행이 없는 부모를 참조하면 조회 누락, 집계 오류, 삭제 손실이 발생한다.
- 필요성: PK의 NOT NULL·UNIQUE와 FK의 cascade, restrict, set null 정책으로 고아 레코드와 삭제 전파를 통제해야 한다.

---

## Ⅱ. 구조 및 구성요소

```text
부모 테이블 PK/UK -> 자식 테이블 FK -> DML 제약 검사 -> 삭제/수정 정책 적용
                   / cascade
                   / restrict
                   / set null
```

| 구성요소 | 역할 | 특이사항 |
|:---|:---|:---|
| Primary Key | 행을 유일하게 식별 | NOT NULL, UNIQUE 동시 만족 |
| Foreign Key | 부모 행 존재성 검사 | 부모 PK 또는 UNIQUE 참조 |
| Cascade | 부모 변경을 자식에 전파 | 주문상세처럼 생명주기 종속 시 적용 |
| Restrict/No Action | 자식 존재 시 부모 삭제 차단 | 원장·감사 데이터 보존 시 적용 |
| Set Null | 부모 제거 시 FK를 NULL 처리 | 선택 관계와 익명화 요구에 사용 |

> 요약: 개체 무결성은 PK로 행을 식별하고, 참조 무결성은 FK와 삭제 정책으로 관계의 존재성을 유지한다.

---

## Ⅲ. 동작원리 및 흐름도

```text
DML 요청 -> PK NOT NULL/UNIQUE 검사 -> FK 부모 존재 검사 -> 정책 적용 -> Commit/Rollback
```

| 단계 | 처리 내용 | 검증 기준 |
|:---:|:---|:---|
| 1 | INSERT 시 PK NULL·중복 여부 확인 | PK violation 0건 |
| 2 | INSERT/UPDATE 시 FK 부모 행 조회 | orphan row 0건 |
| 3 | DELETE/UPDATE 부모키 요청 수신 | 자식 행 존재 여부 확인 |
| 4 | cascade, restrict, set null 정책 실행 | 업무 보존 규칙 충족 |
| 5 | 트랜잭션 commit 또는 rollback | 감사 로그와 row count 일치 |

> 요약: DBMS는 키 검사와 관계 검사 후 업무 정책에 맞게 자식 행 처리 방식을 결정한다.

---

## Ⅳ. 특징

| 구분 | 개체 무결성 | 참조 무결성 | 판단 포인트 |
|:---|:---|:---|:---|
| 대상 | 단일 테이블 행 식별 | 테이블 간 관계 | PK와 FK의 책임 구분 |
| 제약 | PK NOT NULL, UNIQUE | FK 존재성, 삭제 정책 | 부모·자식 생명주기 분석 |
| 위반 사례 | NULL 고객ID, 중복 주문ID | 없는 고객을 참조한 주문 | orphan count 0건 |
| 운영 영향 | 인덱스 기반 중복 검사 | FK 검사와 잠금 발생 | 참조 컬럼 인덱스 필요 |

> 요약: 개체 무결성은 행 자체의 식별성, 참조 무결성은 행 사이 관계의 존재성을 보장한다.

---

## Ⅴ. 심화 비교 및 적용 판단

| 비교 축 | 기존/대안 | 본 키워드 | 선택 기준 |
|:---|:---|:---|:---|
| 구조 | 애플리케이션 관계 검증 | DB PK/FK 제약 | 다중 서비스·배치 갱신 경로 |
| 비용/성능 | DML 검사 비용 없음 | FK lookup, lock 발생 | 참조 컬럼 인덱스와 TPS 측정 |
| 운영/위험 | 고아 레코드 가능 | 제약 위반으로 저장 차단 | 원장·정산·감사 데이터 우선 적용 |

> 요약: 핵심 업무 관계는 PK/FK로 DB에서 강제하고, 대량 적재 구간은 임시 비활성보다 staging 검증을 우선한다.

| 리스크 | 원인 | 대응 방안 | 확인 지표 |
|:---|:---|:---|:---|
| 고아 레코드 | FK 미설정 또는 검증 우회 | FK 추가, anti-join 정기 점검 | orphan row 0건 |
| 삭제 전파 사고 | cascade 범위 과다 | restrict 기본, cascade 목록 승인 | cascade delete row count |
| 잠금 대기 | 자식 FK 인덱스 누락 | FK 컬럼 인덱스 생성 | lock wait 1초 이하 |

> 요약: 참조 무결성 운영의 핵심 리스크는 고아 레코드와 삭제 전파이며, 정책 승인과 지표 감시가 필요하다.

| 점검 항목 | 목표 기준 | 측정 방법 |
|:---|:---|:---|
| 식별성 | PK NULL 0건, 중복 0건 | catalog, duplicate query |
| 관계성 | orphan row 0건 | left anti join 검사 |
| 삭제 정책 | cascade 영향 row 사전 산정 | dry-run count, audit log |

> 요약: PK 중복, FK 고아, 삭제 영향 행 수를 배포 전후로 측정해 무결성 통제를 검증한다.

---

## Ⅵ. 실무 적용 및 결론

**적용 방안 3개 (필수 — 단계별 또는 항목별):**
1. 모든 원장 테이블에 surrogate key 또는 natural key 기준 PK를 두고, 업무 식별자는 UNIQUE로 추가해 중복 가입·중복 주문을 차단함
2. FK 삭제 정책은 기본 restrict로 두고, 생명주기 종속 관계만 cascade를 허용하며 배포 전 dry-run row count를 승인함
3. FK 컬럼 인덱스와 orphan 검사를 운영 점검표에 포함해 lock wait 1초 이하, orphan 0건을 유지함

**결론 (2줄):**
- 기술사 판단: 정산·계약·주문 원장은 PK/FK 필수, 로그·임시 적재 테이블은 staging 검증 후 본 테이블 반영 방식 선택
- 향후 방향: 마이크로서비스 환경에서도 데이터 계약과 참조 검증 배치를 결합해 관계 품질을 유지해야 함
