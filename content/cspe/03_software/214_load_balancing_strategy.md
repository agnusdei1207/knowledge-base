## Ⅰ. 개요
- **정의**: 다수 서버에 클라이언트 요청을 분산하여 부하를 균등화하는 기술
- **배경/필요성**: 단일 서버는 트래픽 증가 시 처리 한계에 도달하므로 수평 확장과 함께 요청 분배 메커니즘이 필요함
- **비유**: 은행 창구 안내원이 고객을 빈 창구로 배분하는 역할

| 출제 의도 | 반드시 짚을 핵심 | 감점 회피 포인트 |
|:---|:---|:---|
| L4/L7 구분과 알고리즘별 특성 비교 | 계층별 분산 기준 차이 | 세션 유지(Sticky)와 무상태 분산의 트레이드오프 명시 |

> 요약: 수평 확장 환경에서 가용성과 처리량을 확보하는 핵심 기술임

## Ⅱ. 구성요소
```text
Client --> Load Balancer --> Server 1
                         --> Server 2
                         --> Server 3
                              |
                        Health Check
```

| 구성요소 | 설명 | 비유 |
|:---|:---|:---|
| Load Balancer | 요청을 수신하여 알고리즘에 따라 백엔드 서버로 전달하는 분배기 | 창구 안내원 |
| 분산 알고리즘 | Round Robin, Least Connection, Weighted 등 분배 기준 | 배분 규칙표 |
| Health Check | 백엔드 서버 상태를 주기적으로 확인하여 비정상 노드를 제외함 | 창구 가용 확인 |

> 요약: 분배기가 알고리즘과 헬스체크를 기반으로 요청을 분산하는 구조임

## Ⅲ. 절차
```text
Request --> LB 수신 --> 알고리즘 적용 --> 서버 전달
```
- 1단계: Request 수신 — 클라이언트 요청이 LB의 VIP(Virtual IP)로 도달
- 2단계: 서버 선택 — 설정된 알고리즘(RR, Least Conn 등)에 따라 대상 서버 결정
- 3단계: 요청 전달 — L4는 TCP 패킷 포워딩, L7은 HTTP 헤더 기반 라우팅으로 전달
- 4단계: 응답 반환 — 서버 응답을 클라이언트에 전달하고 연결 통계를 갱신

> 요약: VIP 수신-알고리즘 선택-전달-응답의 4단계로 부하를 분산함

## Ⅳ. 문제점
- LB 단일 장애점: LB 자체 장애 시 전체 서비스가 중단됨
- 세션 편중: Sticky Session 사용 시 특정 서버에 부하가 집중됨
- 헬스체크 지연: 체크 주기 사이에 장애 서버로 요청이 전달될 수 있음

> 요약: LB 가용성, 세션 편중, 헬스체크 간극이 주요 과제임

## Ⅴ. 개선방안
1. 단기: Active-Standby 또는 VRRP 기반 LB 이중화로 단일 장애점 제거
2. 중기: 외부 세션 저장소(Redis 등) 분리로 Sticky 의존도 해소
3. 장기: Passive Health Check(실시간 오류율 기반)로 장애 감지 지연 최소화

> 요약: 이중화, 세션 외부화, 실시간 감지 순으로 안정성을 강화함

## Ⅵ. 전망
- 발전 방향: 서비스 메시 Sidecar 프록시가 L7 LB를 내재화하는 추세
- 기술사적 판단: 글로벌 서버 로드밸런싱(GSLB)과 결합한 멀티리전 분산이 확대됨
- 기술사 제언: 트래픽 패턴 분석 기반 적응형 알고리즘 도입 검토가 필요
