## 핵심 인사이트 (3줄 요약)
- 한 대의 서버에 트래픽이 몰려 뻗어버리는 것을 막기 위해, **사용자의 수많은 요청을 뒤에 있는 여러 대의 서버로 공평하게(또는 영리하게) 분배해 주는 교통경찰(부하 분산) 기술**.
- 단순히 IP 주소만 보고 기계적으로 분배하는 무식하고 빠른 **L4 스위치**와, HTTP 패킷 내용(주소, 헤더)까지 까보고 "아, 이놈은 결제 요청이네? 결제 서버로 가라!"라고 분배해 주는 똑똑한 **L7 로드밸런서(Ingress/ALB)**로 나뉨.
- 분배 알고리즘은 라운드 로빈(순서대로 돌리기)이 기본이지만, 각 서버의 체력(CPU)이나 현재 응답 속도를 모니터링하여 가벼운 쪽에 트래픽을 더 밀어주는 '동적 알고리즘(Least Connection 등)'으로 진화하고 있음.

## Ⅰ. 개요 및 필요성
- **개요**: 컴퓨터 네트워크 기술의 일종으로, 둘 혹은 그 이상의 중앙처리장치 혹은 저장장치와 같은 컴퓨터 자원들에게 작업을 나누어 주는 인프라 컴포넌트.
- **필요성**: 수강신청 날 1만 명이 접속함. 서버 1대로는 어림없어서 똑같은 서버를 10대(스케일 아웃) 복사해 뒀음. 근데 사용자들이 앞문(IP)으로 막 밀고 들어올 때, 누가 어디로 가야 할지 안내를 안 해주면 1번 서버에만 9천 명이 몰려서 터지고 2~10번 서버는 팽팽 놂. **"가장 앞에 서서 사용자 트래픽을 10대의 서버에 골고루, 1000명씩 예쁘게 나눠서 뿌려주는 똑똑한 신호등이 필요하다!"**
---
## Ⅱ. 아키텍처 및 핵심 원리
- **1. L4 로드밸런싱 (전송 계층 - 무식하고 엄청 빠름)**:
  - 택배 박스(패킷)의 '겉면(IP 주소와 포트 번호)'만 보고 분배함. 안에 무슨 내용(데이터)이 들었는지는 관심 없음.
  - 패킷을 뜯어보지 않기 때문에 속도가 광속임. 트래픽이 어마어마한 시스템의 최전방 방어선으로 쓰임 (예: AWS NLB).
- **2. L7 로드밸런싱 (응용 계층 - 똑똑하고 살짝 느림)**:
  - 택배 박스를 칼로 뜯어서 '내용물(HTTP 헤더, URL, 쿠키)'까지 싹 다 확인한 후 분배함.
  - "어? URL이 `/video`네? 너는 동영상 전용 고성능 서버로 가라!" 같은 정밀한 분기가 가능함 (예: AWS ALB, K8s Ingress, Nginx).
- **3. Health Check (사망 확인 기능)**:
  - 로드밸런서의 핵심 임무. 1번 서버가 뻗었는데 계속 거기로 트래픽을 보내면 대참사가 남.
  - 5초마다 서버들에게 "살아있니?" 찔러보고, 대답이 없으면 분배 리스트에서 즉시 빼버림.

```text
[ L4 vs L7 로드밸런서 분배 아키텍처 비교 ]

 🌐 [ 사용자 트래픽 1,000명 ] 
          ⬇️
 🛑 [ L4 로드밸런서 (IP/Port만 봄) ] -> "다 모르겠고 500명씩 나눠 들어가!"
      ↙️            ↘️
[ L7 ALB ]       [ L7 ALB ]
      ⬇️ 패킷 분해 ⬇️
 "너는 URL이 /image 네? 이미지 서버로!" ➡️ 🖼️ 이미지 서버 (파드)
 "너는 URL이 /login 이네? 회원 서버로!" ➡️ 👤 회원 서버 (파드)
 "너는 VIP 쿠키가 있네? 고속 서버로!"   ➡️ 🚀 VIP 전용 서버 (파드)
```

## Ⅲ. 비교 및 연결 (주요 분배 알고리즘)
| 알고리즘 종류 | 작동 방식 (규칙) | 장점 | 단점 / 한계 |
|---|---|---|---|
| **Round Robin (라운드 로빈)** | 1번, 2번, 3번 서버 순서대로 1개씩 던짐 | 가장 단순하고 공평함 | 서버들의 스펙(체력)이 다르면, 약한 서버가 퍼짐 |
| **Weighted (가중치) RR** | 좋은 서버엔 3개, 구린 서버엔 1개 던짐 | 서버 성능 차이 극복 | 설정값을 사람이 일일이 지정해 줘야 함 |
| **Least Connection** | 지금 '현재 일거리(연결 수)'가 가장 적은 서버에게 던짐 | 트래픽이 가장 효율적으로 동적 분산됨 | 세션 길이를 계산해야 하므로 연산 오버헤드 존재 |
| **IP Hash (해시 기반)** | 고객 IP를 암호화해서 항상 똑같은 서버로만 보냄 | **장바구니(세션)가 끊기지 않음** | 특정 지역(회사 IP)에서 폭주하면 그 서버만 죽음 |
---
## Ⅳ. 실무 적용 및 기술사 판단
- **Sticky Session (세션 고정)의 양날의 검**: 초보 아키텍트는 로그인 정보(세션)를 메모리에 저장해 놓고, 로드밸런서에서 `Sticky Session(IP Hash)`을 켜서 한 유저가 계속 1번 서버만 타게 만듦. 기술사는 이를 **스케일 아웃의 적(Anti-pattern)**으로 규정해야 함. 1번 서버가 죽으면 그 유저의 로그인이 풀려버림. 올바른 클라우드 네이티브 아키텍처는 로드밸런서의 Sticky 옵션을 꺼버리고(무작위 분배), 세션 데이터는 **외부 Redis 같은 분산 캐시 스토어로 완전히 분리(Stateless Server)**해야 완벽한 서버 확장이 가능해짐.
- **Client-side Load Balancing (클라이언트 주도 분산)**: MSA 환경에서는 중앙의 로드밸런서(Nginx) 장비 하나가 죽으면 회사 전체가 멈추는 SPOF(단일 장애점)가 됨. 최근 트렌드는 **gRPC나 Istio(Service Mesh)**를 활용하여, 중앙의 무거운 장비를 없애고 각각의 클라이언트(파드) 내부 프록시가 직접 남은 서버들의 리스트를 들고 알아서 트래픽을 분배하는 분산형 로드밸런싱 아키텍처로 진화하고 있음.
---
## Ⅴ. 기대효과 및 결론
- "트래픽이 늘어나면 서버(컴퓨터)를 껐다 켜서 램을 업그레이드(Scale-up)해야 한다"는 과거의 한계를 부수고, 컴퓨터 대수만 계속 무한대로 늘리면(Scale-out) 되는 마법을 현실화함.
- 수만 대의 서버를 마치 하나의 거대한 슈퍼컴퓨터처럼 작동하게 묶어주는, 현대 인터넷 서비스와 클라우드 아키텍처의 가장 위대한 문지기임.
