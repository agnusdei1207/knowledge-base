# 📖 【암기용】 개념 완전 이해

## 한눈에
- **개요**: 네트워크 트래픽이나 클라이언트 요청을 여러 대의 서버로 적절히 분산시키는 기법
- **왜 필요한가**: 한 대의 서버로는 대규모 트래픽(수만 TPS)을 감당할 수 없으며, 서버 한 대가 죽더라도 서비스가 중단되지 않게(고가용성) 하려면 여러 서버가 일을 나눠야 한다.
- **핵심 직관**: 마트의 계산대 점원들. 손님이 몰리면 점장을(로드 밸런서) 세워 줄이 짧은 계산대나 손이 빠른 점원에게 손님을 배분해주는 것.

## 핵심 용어 정리

| 용어/표기 | 의미 | 비유·예 |
|:---|:---|:---|
| L4 로드밸런싱 | 전송 계층(IP, Port) 수준에서 트래픽 분산 | 주소만 보고 패킷 전달 |
| L7 로드밸런싱 | 응용 계층(HTTP 헤더, 쿠키, URL) 데이터를 분석하여 세밀하게 분산 | 편지 내용을 읽고 담당 부서로 전달 |
| Health Check | 뒷단 서버가 살아있는지 주기적으로 확인 | "계산원 잘 깨어있나 콕콕 찔러봄" |
| Session Affinity (Sticky Session) | 동일한 클라이언트의 요청은 동일한 서버로 지속 전달 | "내 상담 이력 아는 점원에게 계속 감" |

## 깊이 이해
- **배경·문제의식**: Scale-Up(서버 성능 향상)은 물리적 한계와 고비용 문제가 있다. Scale-Out(서버 대수 증가)으로 가야 하는데, 여러 서버로 트래픽을 어떻게 '공평하고 효율적으로' 분배할지가 숙제다.
- **작동 원리**:
  - 클라이언트가 로드밸런서의 VIP(Virtual IP)로 요청을 보낸다.
  - 로드밸런서에 설정된 **분산 알고리즘**(Round Robin, Least Connection 등)에 따라 타겟 서버를 픽(pick)한다.
  - 타겟 서버로 요청을 전달(NAT, DSR 등)하고, 죽은 서버는 Health Check로 감지하여 분산 대상에서 제외한다.
- **비유**: 톨게이트 요금소 배분. 무조건 번갈아가며 배분(Round Robin), 차가 제일 적은 톨게이트로 배분(Least Connection).
- **구체 예시**: Nginx를 L7 로드밸런서로 구성하면 `/api/user`는 User 서버 그룹으로, `/api/order`는 Order 서버 그룹으로 분산하는 'URL 기반 라우팅'이 가능하다.
- **흔한 오해·주의점**: Round Robin이 항상 공평한 것은 아니다. 요청마다 처리 시간이 다르면, 어느 한 서버에만 무거운 요청이 쌓여 다운될 수 있다. 이럴 땐 Least Connection이나 응답 시간 기반 알고리즘이 필요하다.

## 연결 개념
- 고가용성 설계 — Active-Active
- 마이크로서비스 아키텍처 MSA
- 서비스 디스커버리

# 📝 【답안용】 시험 답안 템플릿

## 핵심 인사이트 (3줄 요약)

> 1. **본질**: 분산 시스템 환경에서 가용 자원 간 트래픽을 최적으로 분배하여 응답 시간을 최소화하고 병목을 방지하는 네트워크/소프트웨어 기술이다.
> 2. **가치**: 단일 서버의 물리적 한계를 스케일 아웃(Scale-Out)으로 극복하고, 단일 장애점(SPOF) 제거 및 고가용성(HA) 아키텍처를 구현하는 필수 인프라 요건이다.
> 3. **판단 포인트**: 트래픽의 특성(정적/동적), 세션 유지 필요성, 요구되는 분산 레이어(L4/L7)에 맞춰 정적/동적 분산 알고리즘을 선택해야 한다.

## 출제 의도 및 답안 포인트

| 출제 의도 | 반드시 짚을 핵심 | 감점 회피 포인트 |
|:---|:---|:---|
| 트래픽 제어 및 확장성 확보 역량 확인 | 분산 알고리즘 유형(정적/동적), L4 vs L7 계층 차이 | 하드웨어 장비(L4 스위치) 중심의 편협한 서술 |
| 최적의 분산 설계 트레이드오프 판별 | Session Affinity 리스크, Health Check 메커니즘 | 세션 클러스터링 부재 상황에서 단순 라운드로빈 맹신 |

> 요약: 로드 밸런서는 단순한 트래픽 분배기를 넘어 L4/L7 계층별 특성과 동적 스케줄링 알고리즘이 결합된 가용성 통제 지점임을 제시해야 한다.

---

## Ⅰ. 개요 및 필요성

- 개요: 클라이언트의 네트워크 요청을 다수의 서버 인스턴스에 논리적 규칙(알고리즘)에 따라 분산하여 처리하는 트래픽 제어 전략
- 배경: 트래픽 급증 시 단일 서버(Scale-Up) 방식은 물리적/비용적 한계가 존재하며, 특정 노드 장애 시 전체 서비스 중단 위험 발생
- 필요성: 시스템 가용성(99.99%) 확보, 응답 속도 최적화, 무중단 확장(Scale-Out) 지원

---

## Ⅱ. 구조 및 구성요소

```text
클라이언트 -> VIP(Virtual IP) -> 로드밸런서 (알고리즘 + Health Check)
                                 |            |             |
                             서버 노드 1  서버 노드 2   서버 노드 3
```

| 구성요소 | 역할 | 특이사항 |
|:---|:---|:---|
| VIP (Virtual IP) | 클라이언트에게 노출되는 단일 진입점 IP | 로드밸런서 자체 이중화(VRRP 등) 필수 |
| 스케줄링 알고리즘 | 백엔드 서버를 선택하는 트래픽 분산 로직 | 정적(RR) / 동적(Least Connection) |
| Health Check | 백엔드 노드의 서비스 정상 여부 주기적 모니터링 | 실패 시 가용 풀에서 즉시 격리(Eviction) |
| NAT / DSR | 패킷의 IP 주소를 변환하거나 서버가 클라이언트에게 직접 응답 | DSR(Direct Server Return)로 병목 해소 |

> 요약: 단일 진입점(VIP)을 제공하고, 상태 검증(Health Check)과 분산 알고리즘을 결합하여 백엔드 서버 풀을 효율적으로 운영한다.

---

## Ⅲ. 동작원리 및 흐름도

```text
요청 수신 -> 정책 및 계층(L4/L7) 확인 -> 노드 상태 확인 -> 알고리즘 기반 노드 선택 -> 요청 전달
```

- 1단계 [요청 진입]: 클라이언트 패킷이 VIP를 통해 로드밸런서에 도착
- 2단계 [계층 검사]: L4(IP/Port) 또는 L7(HTTP 헤더/URI) 패킷 분석 및 분산 정책 적용
- 3단계 [대상 픽업]: 설정된 분산 알고리즘(예: 라운드 로빈, 최소 연결)으로 활성 서버 선택
- 4단계 [전달·응답]: NAT 변환 또는 DSR 방식으로 서버에 요청 전달, 서버 처리 후 반환
- 5단계 [상태 갱신]: 백그라운드 헬스체크로 장애 감지 시 픽업 풀에서 제외

> 요약: 로드밸런싱은 패킷 분석을 통한 대상 선정과 상태 감시를 통한 우회 라우팅의 반복 메커니즘이다.

---

## Ⅳ. 특징
- 가용성 보장: 장애 노드를 자동으로 풀에서 제외하여 전체 서비스에 대한 사용자 체감 장애 방지
- 계층적 인텔리전스 (L7): URI, 쿠키, 헤더 기반의 정밀 라우팅이 가능하여 API 게이트웨이 및 마이크로서비스 라우팅에 적합
- 세션 유지 종속성: 로드밸런서 수준에서 Sticky Session 적용 시 특정 서버 부하 집중 및 서버 다운 시 세션 유실 한계

> 요약: 트래픽 분산 효과가 탁월하나, 세션 상태(Stateful) 처리 방식에 따라 특정 노드에 부하가 고착될 수 있다.

## Ⅴ. 심화 비교 및 적용 판단

| 비교 축 | 라운드 로빈 (Round Robin) | 최소 연결 (Least Connection) | 해시 기반 (IP/URL Hash) | 선택 기준 |
|:---|:---|:---|:---|:---|
| 분산 기준 | 순차적 할당 | 현재 활성 세션/연결 수 | IP 또는 데이터 해시값 | 분산 대상 |
| 특징 | 서버 스펙과 처리 시간이 균일할 때 | 요청 처리 시간이 들쭉날쭉할 때 | 특정 세션을 한 서버로 고정할 때 | 트래픽 패턴 |
| 발생 리스크 | 무거운 요청 집중 시 지연(Tail Latency) 발생 | 상태 모니터링에 따른 부하 발생 | 해시 키 편중 시 핫스팟 현상 | 장애 포인트 |

> 요약: 동종 정적 컨텐츠는 라운드 로빈이, 복잡한 비즈니스 로직은 최소 연결이, 세션 유지가 필수라면 해시 기반이 유리하다.

| 비교 축 | L4 로드밸런싱 | L7 로드밸런싱 | 선택 기준 |
|:---|:---|:---|:---|
| 기준 데이터 | Transport Layer (IP, Port, TCP/UDP) | Application Layer (HTTP Header, URI, Cookie) | 분석 대상 계층 |
| 장점 | 패킷 조작 최소화로 속도 및 처리량 극대화 | 페이로드 분석을 통한 콘텐츠 기반 정밀 라우팅 | 속도 vs 정밀도 |
| 실무 적용 | DB 클러스터링, 대규모 단순 트래픽 인입점 | MSA API Gateway, 웹 애플리케이션 분산 | 비즈니스 라우팅 필요 여부 |

**리스크·대응 (기본은 불릿):**
- Sticky Session 부하 불균형: 상태 유지 서버 집중으로 과부하 → 세션 클러스터링(Redis) 외부화 및 무상태(Stateless) 아키텍처 전환 (지표: 노드 간 CPU 사용률 편차)
- 로드밸런서 SPOF: 단일 장비 장애 시 전체 서비스 마비 → Active-Standby (Keepalived/VRRP) 이중화 구축 (지표: VIP 절체 시간)

## Ⅵ. 실무 적용 및 결론

**적용 방안 3개:**
1. Global Server Load Balancing (GSLB) 적용: 다중 리전/AZ에 걸쳐 DNS 기반으로 트래픽을 분산하여 재해 복구(DR) 및 근거리 응답 지연 최적화 구현
2. 클라우드 네이티브 스케일아웃 결합: AWS ALB(Application Load Balancer)와 Auto-Scaling Group을 연동하여 트래픽 임계치에 따른 노드 증감 자동화
3. DSR(Direct Server Return) 모드 구성: 아웃바운드 트래픽 병목을 해소하기 위해 클라이언트 응답 시 로드밸런서를 거치지 않고 서버가 직접 전송하도록 네트워크 튜닝

**결론:**
- 기술사 판단: 애플리케이션이 Stateless하게 설계되지 않으면 아무리 정교한 동적 로드밸런싱 알고리즘을 써도 부하 불균형을 막을 수 없다.
- 향후 방향: 최근 쿠버네티스 환경에서는 중앙 집중형 L4/L7 장비를 넘어, Envoy 프록시 기반의 서비스 메시(Service Mesh)가 클라이언트 사이드 로드밸런싱을 전담하는 방향으로 진화 중이다.
