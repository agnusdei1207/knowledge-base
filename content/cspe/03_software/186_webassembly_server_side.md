# 📖 【암기용】 개념 완전 이해

## 한눈에
- **개요**: 웹 브라우저에서 빠른 실행을 위해 만들어진 WebAssembly(WASM) 바이너리 포맷을 브라우저 밖인 서버(백엔드) 환경에서 실행하는 기술이다.
- **왜 필요한가**: 컨테이너(Docker)는 무겁고 시작(Cold Start)이 느리다. 서버리스나 엣지 컴퓨팅에서는 밀리초 단위로 켜지고 커널 수준으로 안전하게 격리되는 초경량 런타임이 필요한데, WASM이 이 요구를 완벽히 충족한다.
- **핵심 직관**: 언어에 상관없이 "WASM이라는 공용 기계어"로 번역해두면, 매우 가볍고 빠르며 철저히 격리된 투명 상자(샌드박스) 안에서 서버든 엣지든 어디서나 실행할 수 있다.

## 핵심 용어 정리

| 용어/표기 | 의미 | 비유·예 |
|:---|:---|:---|
| WebAssembly (WASM) | 다양한 언어(C, Rust, Go 등)를 컴파일해 브라우저/서버에서 네이티브 속도로 실행하는 이진 포맷 | 소프트웨어계의 공용어 |
| 샌드박스 격리 | 메모리를 선형(Linear)으로만 접근하게 하여 호스트 OS 자원 탈취를 원천 차단하는 실행 환경 | 밖으로 못 나오는 투명 방패 |
| Wasmtime / WasmEdge | 브라우저 밖에서 WASM을 실행시켜 주는 백엔드 전용 런타임 엔진 | WASM용 자바 가상머신(JVM) |

## 깊이 이해
- **배경·문제의식**: 기존 서버리스(FaaS)에서 람다(Lambda) 함수를 띄우려면 리눅스 컨테이너를 구동해야 해서 1초 이상의 콜드 스타트 지연이 발생했다. 이는 실시간 반응이 필수인 엣지 컴퓨팅이나 마이크로서비스 확장에 큰 병목이 되었다.
- **작동 원리**: 개발자가 Rust나 C++로 코드를 짠 뒤 WASM으로 컴파일(Build)한다. 서버사이드 런타임(Wasmtime)은 이 바이너리를 읽고 JIT(Just-In-Time) 컴파일하여 호스트 CPU에서 실행한다. 이때 WASM은 기본적으로 외부 시스템(파일, 네트워크)에 접근할 권한이 일절 없으며, 명시적으로 허용된 권한(Capability)만 사용할 수 있다.
- **비유**: 컨테이너가 '풀옵션 캠핑카'라면, WASM은 '초경량 1인용 텐트'다. 캠핑카는 시동 걸고 주차하기 무겁지만, 텐트는 1초 만에 펼칠 수 있고 어디든 던져놓을 수 있다.
- **구체 예시**: Cloudflare Workers나 Fastly 같은 엣지 컴퓨팅 서비스는 수백만 개의 테넌트 함수를 실행해야 한다. 도커로 띄우면 메모리가 거덜나지만, WASM을 쓰면 5밀리초(ms) 만에 함수를 구동하고 메모리는 불과 수십 KB만 사용하여 완벽한 다중 테넌시를 구현한다.
- **흔한 오해·주의점**: "WASM이 도커를 완전히 대체한다"는 것은 오해다. 기존 복잡한 레거시 웹 앱을 통째로 WASM으로 돌리긴 어렵다(WASI 표준 등이 성숙하는 중). 오히려 플러그인 생태계나 초경량 서버리스 함수 등 도커가 무거워서 못 쓰던 영역을 보완한다.

## 연결 개념
- **WASI (WebAssembly System Interface)**: WASM이 브라우저 밖 서버 환경에서 파일, 네트워크 등 OS 자원에 안전하게 접근하기 위한 표준 인터페이스 (187번 키워드 참조)
- **서버리스 / 엣지 컴퓨팅**: 극도로 짧은 지연과 경량화가 요구되는 WASM의 최대 활용처
- **JIT 컴파일**: 실행 시점에 바이트코드를 네이티브 기계어로 변환해 성능을 끌어올리는 기술

# 📝 【답안용】 시험 답안 템플릿

## 핵심 인사이트 (3줄 요약)

> 1. **본질**: WASM 서버사이드는 웹을 위해 고안된 휴대성 높고 안전한 이진 명령어 포맷을 클라우드 및 엣지 백엔드 런타임으로 확장한 기술이다.
> 2. **가치**: 기존 컨테이너(수백 ms) 대비 밀리초(< 5ms) 수준의 극단적 콜드 스타트 단축과 네이티브에 준하는 성능, 샌드박스 격리 보안을 동시에 제공한다.
> 3. **판단 포인트**: 다중 테넌트 서버리스 인프라 최적화에 탁월하나, 언어 지원 제약과 쓰레딩·네트워크 등 시스템 인터페이스 표준(WASI) 성숙도를 고려해야 한다.

## 출제 의도 및 답안 포인트

| 출제 의도 | 반드시 짚을 핵심 | 감점 회피 포인트 |
|:---|:---|:---|
| 기존 컨테이너(Docker)와의 아키텍처 차이 분석 | OS 의존성 제거, 극단적 경량화, 콜드 스타트 단축 | 단순히 "가상머신 종류"로 오해한 서술 |
| WASM의 보안 메커니즘 원리 이해 | 메모리 샌드박스(Linear Memory), Capability 기반 권한 통제 | 커널 네임스페이스 기반의 도커 격리와 혼동 |
| 엔터프라이즈 백엔드 실무 적용 분야 식별 | 엣지 컴퓨팅, 서버리스 함수, 동적 플러그인 확장 | 브라우저 프론트엔드 기술로만 국한하는 설명 |

> 요약: 리눅스 커널 자원에 의존하는 컨테이너의 한계를 극복하는 경량 샌드박스 구조를 제시하고, 서버리스 콜드 스타트 병목 해결의 핵심임을 논해야 한다.

## Ⅰ. 개요 및 필요성

- 개요: WASM 서버사이드는 특정 플랫폼에 종속되지 않는 안전하고 빠른 바이너리 코드 포맷을 브라우저 외곽의 백엔드 런타임에서 실행하는 아키텍처임
- 배경: 서버리스 및 엣지 컴퓨팅 확산 시 리눅스 컨테이너(Docker)의 무거운 OS 스택 초기화로 인한 콜드 스타트 지연과 메모리 오버헤드 한계 직면
- 필요성: 다양한 프로그래밍 언어로 작성된 코드를 네이티브에 가까운 속도로 즉각 실행하면서, 호스트 환경과 완벽히 격리하는 초경량 런타임 필요

---

## Ⅱ. 구조 및 구성요소

```text
[개발 언어: Rust, Go, C++] -> 컴파일러(LLVM) -> [WASM 바이너리 (.wasm)]
                                                      |
[Host OS] -> [WASM Runtime (Wasmtime, WasmEdge)] -> JIT/AOT 변환 -> CPU 네이티브 실행
```

| 구성요소 | 역할 | 특이사항 |
|:---|:---|:---|
| WASM 바이너리 | 다국어(Polyglot) 소스가 컴파일된 스택 머신 기반의 저수준 이진 포맷 | OS/CPU 아키텍처 독립적 |
| WASM 런타임 | 호스트 환경에서 WASM 모듈을 격리 실행하는 엔진 (예: Wasmtime) | V8, JVM과 유사한 역할 |
| JIT/AOT 컴파일러 | 실행 전 또는 실행 중 WASM 코드를 기계어로 변환하여 고속 연산 보장 | 네이티브 대비 80~90% 성능 |
| WASI (System Interface) | 파일 시스템, 소켓 등 호스트 OS 자원 접근을 추상화한 안전한 인터페이스 | 샌드박스의 창구 역할 |

> 요약: 언어 독립적 바이너리를 생성하여, 백엔드 전용 런타임이 이를 JIT 컴파일로 고속 실행 및 보안 샌드박싱하는 구조이다.

---

## Ⅲ. 동작원리 및 흐름도

```text
다국어 컴파일 -> 바이너리 배포 -> 선형 메모리 샌드박스 할당 -> JIT 변환/실행 -> 호스트 권한 통제
```

- 1단계 [소스 컴파일]: Rust, C++ 등으로 작성된 비즈니스 로직을 LLVM 기반 컴파일러를 통해 .wasm 파일로 빌드
- 2단계 [격리 환경 할당]: 서버 런타임이 모듈 실행 시 연속된 1차원 배열 형태의 선형 메모리(Linear Memory)만 제한적으로 할당
- 3단계 [보안 변환]: 런타임이 호스트 밖으로 메모리 참조가 불가능한지 검증 후, 타겟 CPU 네이티브 명령어로 JIT 변환
- 4단계 [제한적 자원 접근]: 연산 실행 중 외부 자원(파일, 네트워크) 접근 시 권한 기반(Capability-based) 시스템인 WASI를 거쳐 안전하게 접근

> 요약: 선형 메모리 격리와 명시적 권한 부여(Capability)를 통해 호스트 시스템 접근을 원천 차단하는 제로 트러스트 실행 환경을 보장한다.

---

## Ⅳ. 특징
- [극단적 경량화]: OS 커널 부팅이나 복잡한 런타임 초기화가 없어 시작 시간(Cold Start)이 컨테이너 대비 10~100배 빠른 밀리초(ms) 단위 달성
- [플랫폼 이식성(Portability)]: ARM, x86 등 하드웨어 아키텍처나 리눅스, 윈도우 등 OS 종류와 무관하게 동일 바이너리로 실행(Write Once, Run Anywhere)
- [다국어 지원(Polyglot)]: C/C++, Rust, Go, Python 등 다양한 언어를 단일 WASM 규격으로 빌드하여 언어 장벽 해소
- [시스템 접근 제약]: 네트워크 소켓, 스레딩 모델 등 운영체제 밀착 기능이 아직 표준화(WASI) 과도기에 있어 레거시 앱의 직접 마이그레이션이 어려움

> 요약: 콜드 스타트 제거와 강력한 격리 보안으로 서버리스에 최적화되어 있으나, 기존 OS 기능 추상화 표준의 성숙도가 현재의 제약 조건이다.

## Ⅴ. 심화 비교 및 적용 판단

| 비교 축 | Docker Container | WASM Server-side | 선택 기준 |
|:---|:---|:---|:---|
| 실행 기반 | 호스트 OS 커널(Namespace, Cgroup) | 런타임 내 소프트웨어 샌드박스 | 격리 의존성 계층 |
| 이미지 크기 | 수십~수백 MB (OS 런타임 포함) | 수십 KB ~ 수 MB (순수 바이너리) | 배포 및 스케일링 민첩성 |
| 구동 시간 | 500ms ~ 수 초 (네트워크 병목 시 더 김) | 1ms ~ 10ms (콜드스타트 극복) | 응답성(Latency) 민감도 |

> 요약: 기존 레거시 앱 호스팅과 복잡한 스택 운영에는 도커가 유리하며, 마이크로서비스 확장과 엣지 서버리스 함수에는 WASM이 압도적이다.

**리스크·대응 (기본은 불릿):**
- [멀티스레딩/네트워크 제약]: WASI 표준화 지연으로 복잡한 비동기 I/O 애플리케이션 포팅 불가 → 컴포넌트 모델(Component Model) 도입 및 WasmEdge 등 특화 런타임 확장에 의존 (지표: 표준 커버리지율)
- [디버깅 도구 부재]: 크래시 발생 시 네이티브 바이너리 수준의 디버깅 난해 → DWARF 디버그 정보 내장 컴파일 및 WASM 전용 프로파일러 체계 구축 (지표: 버그 원인 분석 시간 MTTR)

**도입 후 점검 지표 (기본은 불릿):**
- 성능 개선: FaaS 함수 호출 시 콜드 스타트 지연 시간(p99) 10ms 이하 방어 — APM 호출 트레이스
- 비용 효율: 다중 테넌트 구동 시 노드당 메모리 점유율 기존 대비 80% 감소 — 컨테이너 관측 메트릭

## Ⅵ. 실무 적용 및 결론

**적용 방안 3개 (필수 — 단계별 또는 항목별):**
1. [초저지연 엣지 런타임 구축]: CDN 혹은 엣지 노드에 Wasmtime 기반 환경을 배포하여, 사용자 요청의 실시간 데이터 필터링/라우팅을 5ms 이내 처리
2. [서버리스 함수 경량화 전환]: 트래픽 변동이 심한 AWS Lambda 등 FaaS 워크로드를 WASM 모듈로 전환 배포하여 인프라 비용 절감 및 반응 속도 극대화
3. [확장 플러그인 아키텍처 적용]: API Gateway(Envoy 등)의 요청 변환 로직이나 데이터베이스(Proxy)의 UDF를 WASM 플러그인으로 동적 적재하여 재시작 없이 룰 갱신

**결론 (2줄):**
- 기술사 판단: WASM은 도커를 대체하는 것이 아니라, 도커가 무거워서 진입하지 못한 극초단기 실행(서버리스)과 임베디드 엣지 시장의 공백을 메우는 핵심 기술임
- 향후 방향: WASI와 Component Model 표준이 완성되면 마이크로서비스 간 레고 블록처럼 결합하는 "포스트 컨테이너" 시대를 주도할 것임
