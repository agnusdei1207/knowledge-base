# 📖 【암기용】 개념 완전 이해

> 목적: Green Software SCI를 처음 봐도 완전히 이해하게 만든다. 시험 답안 양식이 아니라, 이해를 위한 친절한 설명이다.

## 한눈에
- **개요**: SCI(Software Carbon Intensity)는 Green Software Foundation이 정의한 **소프트웨어 탄소 배출량** 지표로, 시스템 전체가 아니라 **기능 단위 하나(예: API 요청 1건)당** 배출되는 탄소량을 gCO2e(이산화탄소 환산 그램)로 계산하는 공식이다.
- **왜 필요한가**: 기존 APM(애플리케이션 성능 모니터링)은 지연시간·CPU·오류율은 측정하지만 탄소 배출량은 보이지 않는다. 클라우드 사용량이 늘수록 전력 소비와 그 전력이 어디서 왔는지(탄소 집약도)가 서비스 운영의 책임 범위에 들어오면서, 비교 가능한 숫자로 만들 지표가 필요해졌다.
- **핵심 직관**: 자동차 연비가 "1리터로 몇 km 가는가"라면, SCI는 "요청 1건을 처리하는 데 탄소가 몇 그램 나오는가"이다 — 전체 배출량이 아니라 업무 하나를 처리하는 데 드는 "단가"를 계산한다.

## 핵심 용어 정리 (내부에 등장하는 것들)

| 용어 | 의미 | 비유 |
|:---|:---|:---|
| 소프트웨어 탄소 배출량 | 소프트웨어 실행이 유발하는 이산화탄소 환산량 (SCI가 측정하려는 대상, 상위 개념) | 소프트웨어의 "탄소 발자국" |
| Energy(E) | 워크로드 실행에 소비된 전력량(CPU·메모리·스토리지·네트워크 합산, 단위 kWh) | 전기요금 고지서의 사용량 |
| Carbon Intensity(I) | 전력 1kWh를 만들 때 배출되는 탄소량(단위 gCO2e/kWh, 지역·시간대마다 다름) | 같은 전기라도 "발전소 종류"에 따라 다른 탄소값 |
| Embodied Carbon(M) | 서버 등 하드웨어를 제조·폐기할 때 배출된 탄소를 사용 기간에 배분한 값 | 자동차를 "만들 때" 이미 발생한 탄소를 주행거리로 나눈 몫 |
| Functional Unit(R) | 배출량을 나눌 기준 단위(API 요청 1건, 배치 1회, 사용자 1명 등) | "1인분"처럼 비교의 기준이 되는 단위 |
| gCO2e | 이산화탄소 환산 그램 — 여러 온실가스를 CO2 기준으로 환산한 단위 | 서로 다른 통화를 달러로 환산해 비교하는 것 |
| Green Software Foundation | SCI 공식을 표준화해 발표한 리눅스 재단 산하 비영리 기구 | SCI의 "표준을 정하는 기관" |

## 깊이 이해

### 공식이 만들어진 배경
- 클라우드 사업자들이 탄소 배출을 줄이겠다고 선언은 하지만, "얼마나" 줄었는지 비교할 공통 단위가 없으면 검증이 불가능하다. Green Software Foundation은 `SCI = ((E × I) + M) / R` 공식을 표준화해, 서로 다른 회사·서비스도 같은 방식으로 탄소 효율을 비교할 수 있게 했다.
- 공식의 구조: 이번 실행에서 쓴 전력(E)을 그 지역 전력의 탄소 집약도(I)로 곱해 실제 배출량을 구하고, 여기에 하드웨어를 만들 때 이미 배출된 몫(M)을 더한 뒤, 처리한 업무량(R)으로 나눠 1건당 단가로 만든다.

### 계산을 숫자로 따라가기 (워크드 예제)
- 어떤 API 서버가 1시간에 전력 2kWh를 쓰고(E=2), 그 서버가 있는 리전의 탄소 집약도가 400gCO2e/kWh이며(I=400), 그 1시간 동안 서버 하드웨어에 배분된 내재 탄소가 50gCO2e이고(M=50), 같은 시간에 100,000건의 요청을 처리했다면(R=100,000):
  - E × I = 2 × 400 = 800 gCO2e (전력 사용으로 인한 배출)
  - (E × I) + M = 800 + 50 = 850 gCO2e (총 배출량)
  - SCI = 850 / 100,000 = 0.0085 gCO2e/request
- 이제 코드 최적화로 전력 사용량이 2kWh에서 1.5kWh로 줄었다고 하자(E=1.5, 나머지 조건 동일): E×I = 1.5×400 = 600, +M(50) = 650, SCI = 650/100,000 = 0.0065 gCO2e/request. 850과 비교해 약 23.5% 개선된 것을 숫자로 확인할 수 있다.

### R을 고정해야 하는 이유 (판별 원리)
- 만약 같은 기간에 요청 수가 100,000건에서 150,000건으로 늘었다면, E와 I가 그대로여도 SCI = 850/150,000 ≈ 0.0057 gCO2e/request로 더 "좋아 보인다". 하지만 이는 코드가 효율적으로 바뀐 게 아니라 분모(R)가 커져서 생긴 착시다.
- 그래서 SCI를 릴리스 간 비교할 때는 R의 정의(무엇을 1건으로 셀지)를 먼저 고정하고, 이후 R이 바뀌면 "개선"이 아니라 "지표 정의 변경"으로 별도 표시해야 한다. SCI 도입 문서가 항상 "측정 경계"를 먼저 문서화하라고 강조하는 이유다.

### 비유와 흔한 오해
- **비유**: SCI는 "회사 전체의 탄소 배출 총량(ESG 보고서)"이 아니라 "요리 한 그릇을 만드는 데 드는 가스량"처럼 업무 단위 하나의 효율을 재는 것이다.
- **흔한 오해**: SCI가 낮다고 회사 전체 탄소 배출이 적은 것은 아니다. 사용자가 폭증하면 건당 SCI는 낮아도 총 배출량(SCI × 총 요청 수)은 오히려 늘 수 있다. SCI는 "효율" 지표이지 "총량" 지표가 아니다.

## 연결 개념
- Carbon-Aware Software — SCI로 측정한 효율을 실행 시점·지역 조정으로 개선하는 실행 기법
- FinOps — 비용 태깅과 자원 사용량 측정 인프라를 SCI 계측과 공유
- Observability — 전력·CPU·요청량 데이터를 SCI 계산에 공급하는 계측 체계

# 📝 【답안용】 시험 답안 템플릿

> 목적: 시험장에서 25분에 그대로 쓰는 답안 양식. 작성방식(추상표현 금지·수치·도식·문제유형 전환)을 엄격히 지킨다.
> 핵심: SCI 문제는 친환경 선언이 아니라 단위 기능당 gCO2e를 계산하고 개선 대상을 고르는 지표 설계 문제로 답한다.

## 핵심 인사이트 (3줄 요약)

> 1. **본질**: Green Software SCI는 `((Energy * Carbon Intensity) + Embodied Carbon) / Functional Unit`으로 소프트웨어 탄소 배출량을 정규화한 지표이다.
> 2. **가치**: API 요청, 배치 1건, 사용자 1명 등 기능 단위별 gCO2e를 산출해 코드·인프라·지역 변경 효과를 비교한다.
> 3. **판단 포인트**: R 정의, 측정 경계, 지역별 탄소 집약도, 내재 탄소 배분 방식이 일관되어야 시계열 비교가 가능하다.

## 출제 의도 및 답안 포인트

| 출제 의도 | 반드시 짚을 핵심 | 감점 회피 포인트 |
|:---|:---|:---|
| 지속가능 SW 지표 설계 역량 확인 | SCI 공식, E/I/M/R 의미, gCO2e 단위 | 친환경 문구만 쓰고 계산식 누락 |
| 클라우드 운영 판단 확인 | 리전, 워크로드 시간대, 자원 우측정 연결 | 전력 절감과 비용 절감을 동일시 |

> 요약: SCI 답안은 탄소 배출량을 기능 단위로 나누고, 코드·인프라·운영 변경의 정량 효과를 검증하는 구조로 작성한다.

## Ⅰ. 개요 및 필요성

- 개요: SCI는 기능 단위 탄소 배출량 지표이다.
- 배경: 클라우드·AI 워크로드 증가로 전력 사용량과 지역별 탄소 집약도가 서비스 품질 지표와 함께 관리 대상이 되었다.
- 필요성: 지연시간, 비용, gCO2e/request를 함께 측정해 설계 대안의 탄소 영향을 판단해야 한다.

---

## Ⅱ. 구조 및 구성요소

```text
Workload -> Energy Metering -> Carbon Intensity -> Embodied Carbon
         -> Functional Unit -> SCI(gCO2e/unit) -> Improvement Backlog
```

| 구성요소 | 역할 | 특이사항 |
|:---|:---|:---|
| Energy(E) | CPU·메모리·스토리지·네트워크 전력 사용량 산정 | kWh, CPU time 기반 추정 |
| Carbon Intensity(I) | 지역·시간별 전력 탄소 계수 반영 | gCO2e/kWh, 리전별 차이 |
| Embodied Carbon(M) | 서버 제조·폐기 배출량 배분 | 장비 수명 3~5년 배분 |
| Functional Unit(R) | 요청·거래·학습 1회 등 기준 단위 | 변경 금지, 비교 기준 |

> 요약: SCI는 전력, 탄소 계수, 하드웨어 배출량을 기능 단위로 정규화해 서비스별 개선 대상을 드러낸다.

---

## Ⅲ. 동작원리 및 흐름도

```text
기능 단위 정의 -> 사용량 계측 -> 탄소 계수 매핑
-> SCI 계산 -> 기준선 비교 -> 개선 항목 반영
```

| 단계 | 처리 내용 | 검증 기준 |
|:---:|:---|:---|
| 1 | API 요청 1건, 배치 1건 등 R 고정 | 산정 기간 내 동일 R 유지 |
| 2 | CPU time, kWh, 스토리지 GB-hour 수집 | APM·클라우드 메트릭 누락률 1% 이하 |
| 3 | 리전별 gCO2e/kWh와 M 배분값 결합 | 계수 출처·시간대 기록 |
| 4 | SCI 산출 후 릴리스별 비교 | gCO2e/unit, p95, 비용 동시 점검 |

> 요약: SCI는 기능 단위 고정 후 사용량과 탄소 계수를 결합하고 릴리스 단위로 기준선 대비 변화를 추적한다.

| 구분 | 기존 운영 지표 | SCI 지표 | 수치 판단 |

| 활용 | 장애·용량 관리 | 배포·리전·스케줄 의사결정 | 릴리스별 SCI 기준선 비교 |

> 요약: SCI는 기존 SRE 지표를 대체하지 않고 탄소 배출량을 같은 의사결정 테이블에 추가한다.

## Ⅴ. 심화 비교 및 적용 판단

| 구분 | 기존/대안 | 본 키워드 | 선택 기준 |
|:---|:---|:---|:---|
| 측정 | CPU·비용 중심 | gCO2e/unit 중심 | ESG 보고와 서비스 개선을 함께 요구할 때 |
| 구조 | 전체 배출량 합산 | 기능 단위 정규화 | 사용자 수 증가 영향을 분리해야 할 때 |
| 운영 | 월별 비용 리뷰 | 릴리스별 SCI 회귀 점검 | CI/CD 품질 게이트에 탄소 기준 포함 |

> 요약: 기능 단위별 비교가 필요한 서비스는 총량 지표보다 SCI가 릴리스 영향 분석에 적합하다.

| 리스크 | 원인 | 대응 방안 | 확인 지표 |
|:---|:---|:---|:---|
| 비교 왜곡 | R 정의 변경 | API·사용자·거래 기준 문서화 | R 변경 이력 100% 기록 |
| 계수 오류 | 탄소 집약도 출처 혼재 | 리전별 계수 버전 관리 | gCO2e/kWh 출처 태그 |
| 성능 회귀 | 탄소만 보고 자원 축소 | p95·오류율·SCI 동시 게이트 | p95 200ms, 오류율 0.1% 이하 |

> 요약: SCI 도입 리스크는 지표 정의 오류와 품질 회귀이므로 R·계수·SLO를 함께 통제한다.

| 점검 항목 | 목표 기준 | 측정 방법 |
|:---|:---|:---|
| 탄소 | SCI 기준선 대비 10% 감소 | 배포 전후 gCO2e/unit 비교 |
| 서비스 품질 | p95 200ms, 오류율 0.1% 이하 | APM, synthetic test |
| 운영 | 월 1회 리전·스케줄 검토 | FinOps 태그, carbon dashboard |

> 요약: 도입 성과는 SCI 감소만이 아니라 p95와 오류율을 유지하는 조건에서 판단한다.

## Ⅵ. 실무 적용 및 결론

**적용 방안 3개 (필수 — 단계별 또는 항목별):**
1. 기능 단위를 API 요청·배치 작업·모델 추론 1회로 고정하고 `gCO2e/unit` 대시보드 구성
2. CI/CD에 SCI 회귀 기준 10%, p95 200ms, 오류율 0.1% 게이트를 함께 적용
3. 리전별 탄소 계수와 스팟·예약 인스턴스 정보를 결합해 배치 실행 시간을 조정

**결론 (2줄):**
- 기술사 판단: 규제 보고와 서비스 개선이 함께 요구되면 SCI를 SLO·FinOps 지표와 결합하고, 단순 홍보 목적이면 총량 배출 보고와 구분한다
- 향후 방향: AI 추론·배치 워크로드는 Carbon-Aware Scheduling과 SCI를 결합해 gCO2e/token 또는 gCO2e/job 단위로 관리한다
