# 📖 【암기용】 개념 완전 이해

> 목적: Green Software SCI를 처음 봐도 완전히 이해하게 만든다. 시험 답안 양식이 아니라, 이해를 위한 친절한 설명이다.

## 한눈에
- **개요**: SCI는 소프트웨어 실행 단위당 탄소 배출량을 수치화하는 지표
- **왜 필요한가**: 클라우드 사용량이 늘면 전력, 탄소 집약도, 하드웨어 배출량까지 서비스 책임 범위에 들어온다. SCI는 배포 단위별 개선 대상을 숫자로 드러낸다.
- **핵심 직관**: 같은 요청 1,000건을 처리할 때 전력과 탄소가 적게 드는 코드·인프라·지역을 선택하는 계산식이다.

## 깊이 이해
- **배경·문제의식**: 기존 APM은 지연시간·CPU·오류율을 보지만 탄소 배출량은 보이지 않는다. Green Software Foundation은 `SCI = ((E * I) + M) / R`로 에너지(E), 탄소 집약도(I), 내재 탄소(M), 기능 단위(R)를 연결한다.
- **작동 원리**: 먼저 기능 단위(R)를 API 요청, 학습 1회, 사용자 1명 등으로 정한다. 이후 전력 사용량, 지역별 gCO2e/kWh, 서버 제조 배출량 배분값을 모아 단위당 gCO2e를 산출한다.
- **비유**: 자동차 연비가 km/L라면 SCI는 요청 1건당 gCO2e이다. 빠른 차가 아니라 같은 업무를 더 낮은 gCO2e로 처리하는 차를 고르는 기준이다.
- **구체 예시**: 1시간 2kWh, 지역 탄소 집약도 400gCO2e/kWh, 내재 탄소 50g, 처리 요청 100,000건이면 SCI는 0.0085gCO2e/request이다.
- **흔한 오해·주의점**: SCI는 기업 전체 ESG 점수가 아니다. 서비스 기능 단위별 소프트웨어 탄소 지표이며, R 정의가 바뀌면 비교가 무효가 된다.

## 연결 개념
- Carbon-Aware Software — 시간·지역별 탄소 집약도에 맞춰 실행 시점 조정
- FinOps — 비용 태깅과 자원 사용량 측정 체계 공유
- Observability — 전력·CPU·요청량·지역 정보를 지표 파이프라인에 수집

# 📝 【답안용】 시험 답안 템플릿

> 목적: 시험장에서 25분에 그대로 쓰는 답안 양식. 작성방식(추상표현 금지·수치·도식·문제유형 전환)을 엄격히 지킨다.
> 핵심: SCI 문제는 친환경 선언이 아니라 단위 기능당 gCO2e를 계산하고 개선 대상을 고르는 지표 설계 문제로 답한다.

## 핵심 인사이트 (3줄 요약)

> 1. **본질**: Green Software SCI는 `((Energy * Carbon Intensity) + Embodied Carbon) / Functional Unit`으로 소프트웨어 탄소 배출량을 정규화한 지표이다.
> 2. **가치**: API 요청, 배치 1건, 사용자 1명 등 기능 단위별 gCO2e를 산출해 코드·인프라·지역 변경 효과를 비교한다.
> 3. **판단 포인트**: R 정의, 측정 경계, 지역별 탄소 집약도, 내재 탄소 배분 방식이 일관되어야 시계열 비교가 가능하다.

## 출제 의도 및 답안 포인트

| 출제 의도 | 반드시 짚을 핵심 | 감점 회피 포인트 |
|:---|:---|:---|
| 지속가능 SW 지표 설계 역량 확인 | SCI 공식, E/I/M/R 의미, gCO2e 단위 | 친환경 문구만 쓰고 계산식 누락 |
| 클라우드 운영 판단 확인 | 리전, 워크로드 시간대, 자원 우측정 연결 | 전력 절감과 비용 절감을 동일시 |
| 지표 검증 역량 확인 | 기능 단위 고정, 측정 경계, 대시보드 | R 변경 후 전후 비교하는 오류 |

> 요약: SCI 답안은 탄소 배출량을 기능 단위로 나누고, 코드·인프라·운영 변경의 정량 효과를 검증하는 구조로 작성한다.

## Ⅰ. 개요 및 필요성

- 개요: SCI는 기능 단위 탄소 배출량 지표이다.
- 배경: 클라우드·AI 워크로드 증가로 전력 사용량과 지역별 탄소 집약도가 서비스 품질 지표와 함께 관리 대상이 되었다.
- 필요성: 지연시간, 비용, gCO2e/request를 함께 측정해 설계 대안의 탄소 영향을 판단해야 한다.

---

## Ⅱ. 구조 및 구성요소

```text
Workload -> Energy Metering -> Carbon Intensity -> Embodied Carbon
         -> Functional Unit -> SCI(gCO2e/unit) -> Improvement Backlog
```

| 구성요소 | 역할 | 특이사항 |
|:---|:---|:---|
| Energy(E) | CPU·메모리·스토리지·네트워크 전력 사용량 산정 | kWh, CPU time 기반 추정 |
| Carbon Intensity(I) | 지역·시간별 전력 탄소 계수 반영 | gCO2e/kWh, 리전별 차이 |
| Embodied Carbon(M) | 서버 제조·폐기 배출량 배분 | 장비 수명 3~5년 배분 |
| Functional Unit(R) | 요청·거래·학습 1회 등 기준 단위 | 변경 금지, 비교 기준 |

> 요약: SCI는 전력, 탄소 계수, 하드웨어 배출량을 기능 단위로 정규화해 서비스별 개선 대상을 드러낸다.

---

## Ⅲ. 동작원리 및 흐름도

```text
기능 단위 정의 -> 사용량 계측 -> 탄소 계수 매핑
-> SCI 계산 -> 기준선 비교 -> 개선 항목 반영
```

| 단계 | 처리 내용 | 검증 기준 |
|:---:|:---|:---|
| 1 | API 요청 1건, 배치 1건 등 R 고정 | 산정 기간 내 동일 R 유지 |
| 2 | CPU time, kWh, 스토리지 GB-hour 수집 | APM·클라우드 메트릭 누락률 1% 이하 |
| 3 | 리전별 gCO2e/kWh와 M 배분값 결합 | 계수 출처·시간대 기록 |
| 4 | SCI 산출 후 릴리스별 비교 | gCO2e/unit, p95, 비용 동시 점검 |

> 요약: SCI는 기능 단위 고정 후 사용량과 탄소 계수를 결합하고 릴리스 단위로 기준선 대비 변화를 추적한다.

---

## Ⅳ. 특징

| 구분 | 기존 운영 지표 | SCI 지표 | 수치 판단 |
|:---|:---|:---|:---|
| 초점 | p95, TPS, 오류율 | gCO2e/request, gCO2e/job | 탄소 10% 감소와 p95 200ms 준수 동시 확인 |
| 경계 | 애플리케이션 런타임 | 런타임+인프라+내재 탄소 | 리전·장비 수명 반영 |
| 활용 | 장애·용량 관리 | 배포·리전·스케줄 의사결정 | 릴리스별 SCI 기준선 비교 |

> 요약: SCI는 기존 SRE 지표를 대체하지 않고 탄소 배출량을 같은 의사결정 테이블에 추가한다.

## Ⅴ. 심화 비교 및 적용 판단

| 비교 축 | 기존/대안 | 본 키워드 | 선택 기준 |
|:---|:---|:---|:---|
| 측정 | CPU·비용 중심 | gCO2e/unit 중심 | ESG 보고와 서비스 개선을 함께 요구할 때 |
| 구조 | 전체 배출량 합산 | 기능 단위 정규화 | 사용자 수 증가 영향을 분리해야 할 때 |
| 운영 | 월별 비용 리뷰 | 릴리스별 SCI 회귀 점검 | CI/CD 품질 게이트에 탄소 기준 포함 |

> 요약: 기능 단위별 비교가 필요한 서비스는 총량 지표보다 SCI가 릴리스 영향 분석에 적합하다.

| 리스크 | 원인 | 대응 방안 | 확인 지표 |
|:---|:---|:---|:---|
| 비교 왜곡 | R 정의 변경 | API·사용자·거래 기준 문서화 | R 변경 이력 100% 기록 |
| 계수 오류 | 탄소 집약도 출처 혼재 | 리전별 계수 버전 관리 | gCO2e/kWh 출처 태그 |
| 성능 회귀 | 탄소만 보고 자원 축소 | p95·오류율·SCI 동시 게이트 | p95 200ms, 오류율 0.1% 이하 |

> 요약: SCI 도입 리스크는 지표 정의 오류와 품질 회귀이므로 R·계수·SLO를 함께 통제한다.

| 점검 항목 | 목표 기준 | 측정 방법 |
|:---|:---|:---|
| 탄소 | SCI 기준선 대비 10% 감소 | 배포 전후 gCO2e/unit 비교 |
| 서비스 품질 | p95 200ms, 오류율 0.1% 이하 | APM, synthetic test |
| 운영 | 월 1회 리전·스케줄 검토 | FinOps 태그, carbon dashboard |

> 요약: 도입 성과는 SCI 감소만이 아니라 p95와 오류율을 유지하는 조건에서 판단한다.

## Ⅵ. 실무 적용 및 결론

**적용 방안 3개 (필수 — 단계별 또는 항목별):**
1. 기능 단위를 API 요청·배치 작업·모델 추론 1회로 고정하고 `gCO2e/unit` 대시보드 구성
2. CI/CD에 SCI 회귀 기준 10%, p95 200ms, 오류율 0.1% 게이트를 함께 적용
3. 리전별 탄소 계수와 스팟·예약 인스턴스 정보를 결합해 배치 실행 시간을 조정

**결론 (2줄):**
- 기술사 판단: 규제 보고와 서비스 개선이 함께 요구되면 SCI를 SLO·FinOps 지표와 결합하고, 단순 홍보 목적이면 총량 배출 보고와 구분한다
- 향후 방향: AI 추론·배치 워크로드는 Carbon-Aware Scheduling과 SCI를 결합해 gCO2e/token 또는 gCO2e/job 단위로 관리한다
