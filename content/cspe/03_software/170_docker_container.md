# 📖 【암기용】 개념 완전 이해

> 목적: Docker 컨테이너를 처음 봐도 완벽히 이해하게 만든다. 시험 답안 양식이 아니라, 이해를 위한 친절한 설명이다.

## 한눈에
- **개요**: **OS-레벨 가상화(OS-level Virtualization)**의 대표 구현체로, 애플리케이션과 실행 의존성을 이미지로 묶어 호스트 커널 위에서 격리 실행하는 **경량 컨테이너 가상화** 기술이다.
- **왜 필요한가**: 개발 환경에서는 동작하던 프로그램이 운영 서버에서는 라이브러리 버전·OS 설정 차이로 실패하는 문제("내 컴퓨터에선 됐는데")가 반복된다. 실행 환경 자체를 통째로 옮길 방법이 필요했다.
- **핵심 직관**: 컨테이너는 애플리케이션을 실행에 필요한 파일과 함께 밀봉 포장해, 어느 서버에서 열어도 같은 내용물이 나오게 한다.

## 핵심 용어 정리 (내부에 등장하는 것들)

| 용어 | 의미 | 비유 |
|:---|:---|:---|
| OS-레벨 가상화 | 하드웨어가 아니라 OS 커널 단계에서 프로세스를 격리하는 가상화 방식 — 컨테이너의 상위 개념 | 한 건물 안에서 사무실만 나누기 |
| 이미지(Image) | 애플리케이션 코드·의존성·설정을 담은 읽기 전용 템플릿 | 요리 레시피와 재료 세트 |
| 레이어(Layer) | Dockerfile 명령 하나가 만드는 읽기 전용 이미지 조각, 캐시·재사용 단위 | 옷을 겹쳐 입듯 이미지를 쌓음 |
| 컨테이너(Container) | 이미지를 실행해 만든, 쓰기 가능한 레이어가 얹힌 격리 프로세스 | 레시피대로 실제 요리를 시작한 상태 |
| Dockerfile | 이미지를 어떻게 만들지 정의하는 빌드 스크립트 | 레시피 문서 |
| namespace | 프로세스·네트워크·마운트 등을 커널 단위로 격리하는 기능 | 사무실 문을 잠가 서로 안 보이게 함 |
| cgroup(Control Group) | 프로세스가 쓸 수 있는 CPU·메모리 사용량을 제한하는 커널 기능 | 사무실별 전기·수도 사용 한도 계약 |
| OverlayFS(Union File System) | 여러 읽기 전용 레이어와 쓰기 레이어를 하나로 합쳐 보여주는 파일시스템 | 여러 장의 투명 필름을 겹쳐서 하나의 그림처럼 봄 |
| 레지스트리(Registry) | 이미지를 저장·배포하는 저장소(Docker Hub, ECR 등) | 레시피 공유 도서관 |
| OCI(Open Container Initiative) | 이미지 형식·실행 방식을 업계 공통 규격으로 정한 표준 | 만국 공통 도량형 |

## 깊이 이해

### 컨테이너 기술은 어디서 왔나 (배경)
- 프로세스 격리는 Docker가 처음 만든 개념이 아니다. 1979년 UNIX의 `chroot`가 파일시스템 루트를 바꿔 격리를 흉내 냈고, 2000년 FreeBSD Jail, 2006년 구글이 리눅스 커널에 기여한 cgroups, 2008년 이를 묶은 LXC(Linux Container)가 이미 존재했다.
- Docker(2013)의 혁신은 새로운 격리 기술이 아니라 **사용성**이었다 — namespace·cgroup 같은 저수준 커널 기능을 Dockerfile이라는 선언적 빌드 파일, 계층형 이미지, Docker Hub라는 공유 레지스트리로 묶어 "누구나 쉽게" 컨테이너를 만들고 배포하게 했다. 이후 2015년 Docker가 실행 엔진(runc)과 이미지 규격을 OCI로 기부하며 업계 표준이 됐다.

### namespace — 프로세스를 격리하는 6가지 경계
- **PID namespace**: 컨테이너 안에서는 자신이 PID 1이며, 호스트나 다른 컨테이너의 프로세스가 보이지 않는다.
- **NET namespace**: 독립된 네트워크 인터페이스·IP·라우팅 테이블을 가지며, `veth` 가상 케이블 쌍으로 호스트와 연결된다.
- **MNT namespace**: 독립된 파일시스템 마운트 지점을 가져 컨테이너 안에서 본 `/`가 호스트의 `/`와 다르다.
- **UTS namespace**: 독립된 hostname을 가진다.
- **IPC namespace**: 세마포어·메시지 큐 같은 프로세스 간 통신 자원을 격리한다.
- **USER namespace**: 컨테이너 내부의 root(UID 0)를 호스트의 비특권 UID로 매핑한다 — 이것이 rootless 컨테이너의 기반이다.

### cgroup — 자원 제한을 수치로 이해
- cgroup은 "얼마나 볼 수 있는가"(namespace)가 아니라 "얼마나 쓸 수 있는가"를 제한한다. 예: `memory.max=512M`로 설정한 컨테이너가 600MB를 요구하면 커널의 OOM Killer가 해당 프로세스를 강제 종료한다(OOMKilled).
- CPU는 절대량이 아니라 상대 비율로도 배분한다. 두 컨테이너의 `cpu.shares`가 각각 512와 1024라면, CPU 경합 시 1:2 비율로 시간을 나눠 받는다 — 여유가 있으면 둘 다 100% 다 쓸 수 있지만, 부족해지면 비율이 강제된다.

### 이미지 레이어와 Copy-on-Write — 수치로 이해
- Dockerfile의 각 명령(`RUN`, `COPY` 등)이 레이어 하나를 만들고, 레이어는 읽기 전용으로 캐시된다. 컨테이너를 실행하면 그 위에 얇은 쓰기 가능 레이어(container layer) 하나가 얹힌다. OverlayFS는 `lowerdir`(읽기 전용 이미지 레이어들), `upperdir`(컨테이너 쓰기 레이어), `merged`(합쳐서 보여주는 최종 뷰)로 구성된다.
- 파일을 수정하면 원본 레이어를 고치지 않고 **Copy-on-Write**로 `upperdir`에 복사한 뒤 그 사본을 고친다. 예: 1GB 이미지 안의 설정파일 하나(10KB)만 바꿔도 `upperdir`에는 10KB만 추가되고 나머지 1GB는 그대로 공유된다.
- 그래서 같은 이미지로 컨테이너 100개를 띄워도 디스크에는 이미지 실 데이터가 1벌만 있고, 컨테이너별 변경분만 각각 얇게 쌓인다 — `python:3.12-slim`(약 150MB) 기반 이미지로 100개 컨테이너를 띄워도 디스크 사용량은 150MB + (컨테이너별 변경분 합)에 가깝지, 150MB×100이 아니다.

### 비유와 흔한 오해
- **비유**: 컨테이너는 같은 건물(호스트 커널)을 쓰는 여러 사무실이 각자 문(namespace)을 잠그고 전기·수도 사용량(cgroup)을 계약서대로 제한받는 것과 같다. 건물 전체를 새로 짓는 VM과 달리 사무실 인테리어만 새로 하면 되니 준비(부팅)가 빠르다.
- **오해**: 컨테이너는 VM처럼 완전히 독립된 커널을 갖지 않는다. 호스트 커널을 공유하므로 커널 취약점 하나가 컨테이너 탈출(escape)로 이어질 수 있다 — 그래서 rootless 실행, 이미지 취약점 스캔, 최소 권한(non-root), seccomp/AppArmor 같은 추가 통제가 반드시 필요하다.

## Ⅰ. 개요 및 필요성

- 개요: Docker 컨테이너는 실행 환경을 이미지로 패키징하는 기술임.
- 배경: 개발·운영 환경 차이, 배포 반복성, 자원 사용량 문제가 애플리케이션 릴리스를 지연시킨다.
- 필요성: 컨테이너 이미지를 CI/CD와 Kubernetes의 공통 배포 단위로 사용해 환경 차이를 통제한다.

---

## Ⅱ. 구조 및 구성요소

```text
Dockerfile -> Image Layer -> Registry -> Container Runtime
                                      -> Namespace / cgroup
                                      -> Network / Volume / Log
```

| 구성요소 | 역할 | 특이사항 |
|:---|:---|:---|
| Dockerfile | 이미지 빌드 절차 정의 | base image, RUN, COPY, CMD |
| Image/Layer | 애플리케이션과 의존성 패키징 | 읽기 전용 레이어, 캐시 |
| Registry | 이미지 저장·배포 | private registry, 서명 |
| Runtime | 컨테이너 실행 | namespace, cgroup, OCI runtime |

> 요약: Docker는 Dockerfile로 이미지를 만들고 레지스트리에 저장한 뒤 런타임에서 격리 프로세스로 실행한다.

---

## Ⅲ. 동작원리 및 흐름도

```text
소스 코드 -> Dockerfile 빌드 -> 이미지 스캔 -> Registry push
-> 컨테이너 실행 -> 로그/메트릭 수집 -> 재배포/롤백
```

| 단계 | 처리 내용 | 검증 기준 |
|:---:|:---|:---|
| 1 | Dockerfile 작성과 이미지 빌드 | 이미지 크기 500MB 이하 권장 |
| 2 | 이미지 취약점 스캔 | Critical CVE 0건 |
| 3 | 컨테이너 실행과 리소스 제한 | CPU/memory limit 설정 |
| 4 | 배포와 운영 관측 | 로그 수집률 95%, 헬스체크 |

> 요약: Docker 운영은 빌드, 스캔, 실행, 관측, 재배포의 반복 흐름으로 관리한다.

## Ⅳ. 특징

| 구분 | VM | Docker 컨테이너 | 수치·판단 포인트 |
|:---|:---|:---|:---|
| 가상화 단위 | OS 전체 | 프로세스와 파일시스템 | 이미지 수백 MB 수준 |

> 요약: 컨테이너는 VM보다 배포 단위가 작고 시작 시간이 짧지만 커널 공유에 따른 보안 통제가 필요하다.

## Ⅴ. 심화 비교 및 적용 판단

| 구분 | VM | Docker 컨테이너 | 선택 기준 |
|:---|:---|:---|:---|
| 구조 | Guest OS 포함 | 호스트 커널 공유 | 강한 격리 vs 배포 반복성 |
| 비용/성능 | 자원 오버헤드 큼 | 밀도 높은 배치 가능 | CPU·메모리 limit와 노드 밀도 |
| 운영/위험 | 패치 단위 큼 | 이미지 취약점·secret 노출 | 이미지 스캔과 런타임 정책 |

> 요약: 강한 격리와 OS 다양성은 VM, 이미지 단위 배포와 수평 확장은 컨테이너가 적합하다.

| 리스크 | 원인 | 대응 방안 | 확인 지표 |
|:---|:---|:---|:---|
| 이미지 취약점 | 오래된 base image, 패키지 CVE | Trivy/Grype 스캔, 정기 rebuild | Critical CVE 0건 |
| 권한 상승 | root 실행, privileged 모드 | rootless, non-root user, seccomp | privileged 컨테이너 0개 |
| 자원 경합 | limit 미설정, 로그 폭증 | CPU/memory limit, log rotation | OOMKilled 0건 |

> 요약: 컨테이너 리스크는 이미지, 권한, 자원 제한에서 발생하며 스캔과 런타임 정책으로 통제한다.

| 점검 항목 | 목표 기준 | 측정 방법 |
|:---|:---|:---|
| 이미지 품질 | 500MB 이하, Critical CVE 0건 | Registry scan, SBOM |
| 보안 | non-root 100%, secret 이미지 포함 0건 | admission control, policy |
| 운영 | 헬스체크 100%, 로그 수집률 95% | Kubernetes probe, 로그 시스템 |

> 요약: Docker 도입 효과는 이미지 품질, 보안 정책 준수, 운영 관측성으로 판정한다.

## Ⅵ. 실무 적용 및 결론

**적용 방안 3개 (필수 - 단계별 또는 항목별):**
1. 이미지 표준화: multi-stage build, slim base image, SBOM, 이미지 서명으로 500MB 이하와 Critical CVE 0건 유지
2. 런타임 보안: non-root user, read-only filesystem, seccomp, resource limit, secret 외부 주입 적용
3. 배포 운영: Registry digest 고정, health check, 로그 수집률 95%, 롤백 가능한 CI/CD 파이프라인 구성

**결론 (2줄):**
- 기술사 판단: 이미지 단위 배포와 수평 확장이 필요한 애플리케이션은 Docker 컨테이너를 선택하고, 강한 OS 격리 요구는 VM을 병행함
- 향후 방향: Docker 컨테이너는 OCI 표준, Kubernetes, SBOM, supply chain security와 결합해 운영 단위가 정교화됨
