# 📖 【암기용】 개념 완전 이해

## 한눈에
- **개요**: Docker는 애플리케이션과 그 실행 환경(의존성)을 하나로 묶어, 호스트 OS 커널을 공유하면서 격리된 공간에서 실행하는 경량 가상화 기술이다.
- **왜 필요한가**: 개발 환경에서는 잘 돌아가던 코드가 운영 서버에서는 OS 설정이나 라이브러리 버전 차이로 오류가 나는 "환경 불일치" 문제를 원천 차단하기 위해 필요하다.
- **핵심 직관**: 물류 산업을 혁신한 규격화된 '컨테이너 박스'처럼, 소프트웨어를 환경에 구애받지 않고 어디서든 똑같이 실행할 수 있게 포장한 규격화 상자다.

## 핵심 용어 정리

| 용어/표기 | 의미 | 비유·예 |
|:---|:---|:---|
| 컨테이너 (Container) | 호스트 OS 커널을 공유하며 논리적으로 격리 실행되는 애플리케이션 프로세스 | 내용물이 담겨 배에 실린 화물 컨테이너 |
| 이미지 (Image) | 컨테이너를 실행하기 위해 필요한 소스, 라이브러리, 설정의 읽기 전용 템플릿 | 붕어빵을 똑같이 찍어내는 틀 |
| Dockerfile | 이미지를 생성하기 위해 작성하는 명령어 스크립트 파일 | 재료와 조리 순서가 적힌 요리 레시피 |
| Docker 데몬 (dockerd) | 컨테이너를 생성, 실행, 배포하는 백그라운드 관리 프로세스 | 항만에서 컨테이너를 옮기는 크레인 시스템 |

## 깊이 이해
- **배경·문제의식**: 기존 하이퍼바이저 기반 가상머신(VM)은 완전히 분리된 Guest OS를 부팅해야 하므로 무겁고 느리며 자원 낭비가 심했다. 마이크로서비스 아키텍처(MSA)처럼 작고 수많은 서비스를 빠르게 배포해야 하는 환경에서는 이 오버헤드를 감당할 수 없었다.
- **작동 원리**: 리눅스 커널의 핵심 기능인 **cgroups**(CPU, 메모리 등 물리적 자원 할당량 제한)와 **namespace**(PID, 네트워크 등 논리적 시스템 뷰 격리)를 활용한다. Guest OS를 설치하지 않고 호스트 OS 커널을 그대로 공유하면서, 프로세스 관점에서만 완벽히 격리된 환경을 만들어낸다.
- **비유**: VM이 '큰 땅(호스트) 위에 수도와 전기를 따로 깐 독립된 개별 주택(Guest OS)'을 여러 채 짓는 것이라면, Docker 컨테이너는 '큰 아파트(호스트 커널) 하나를 지어 방(Namespace)만 쪼개고, 중앙에서 관리하는 수도·전기(cgroups)를 효율적으로 나눠 쓰는 것'이다.
- **구체 예시**: 1GB가 넘는 Ubuntu VM 이미지와 달리, Alpine Linux 기반 컨테이너 이미지는 약 5MB에 불과하다. 부팅 속도 역시 VM은 수 분(minutes)이 걸리지만, 컨테이너는 프로세스 하나를 띄우는 것과 같아 수 밀리초(ms) 단위로 완료된다.
- **흔한 오해·주의점**: "컨테이너는 VM보다 보안이 더 뛰어나다"는 오해다. 호스트 커널을 모든 컨테이너가 공유하기 때문에, 커널 취약점이 뚫리면(컨테이너 이스케이프) 전체 호스트와 다른 컨테이너까지 한 번에 위험해진다. 보안 격리 수준은 하드웨어 단에서 분리된 VM이 훨씬 강력하다.

## 연결 개념
- 하이퍼바이저 가상화 (Type 1, Type 2) — 컨테이너와 대비되는 전통적 가상화
- 쿠버네티스 (Kubernetes) — 여러 대의 도커 호스트와 컨테이너를 자동 배치하고 관리하는 오케스트레이션 도구
- 마이크로서비스 아키텍처 (MSA) — 컨테이너가 활약하는 최적의 아키텍처

# 📝 【답안용】 시험 답안 템플릿

## 핵심 인사이트 (3줄 요약)

> 1. **본질**: 호스트 OS 커널을 공유하고, Namespace로 프로세스 뷰를 격리하며, cgroups로 자원을 통제하는 OS 레벨의 경량 가상화 기술이다.
> 2. **가치**: 인프라를 코드로 관리(Dockerfile)하여 불변 인프라(Immutable Infrastructure)를 실현하고, ms 단위의 기동 속도와 고밀도 집적도를 제공한다.
> 3. **판단 포인트**: VM 대비 압도적인 확장성을 가지나 커널 공유로 인한 보안 리스크(컨테이너 이스케이프)가 존재하므로, 강력한 격리가 필요할 경우 gVisor 등 샌드박스 기술 혼용을 고려해야 한다.

## 출제 의도 및 답안 포인트

| 출제 의도 | 반드시 짚을 핵심 | 감점 회피 포인트 |
|:---|:---|:---|
| 하이퍼바이저 가상화와의 구조적 차별성 파악 | cgroups, namespace, Guest OS 제거, 호스트 커널 공유 | 단순히 "성능이 좋다, 빠르다" 식의 빈 추상 서술 |
| 컨테이너 생명주기와 핵심 메커니즘 이해 | Dockerfile, Image, Container 동작 흐름 및 R/W 레이어 결합 | 이미지(템플릿)와 컨테이너(런타임) 개념 혼용 |
| 실무 도입 시의 보안 리스크와 통제 방안 | 커널 공유 취약점 (컨테이너 이스케이프), Seccomp, Rootless | 무조건적인 컨테이너 도입 및 VM 대체 단정 |

> 요약: VM 대비 높은 집적도와 이식성(Build Once, Run Anywhere)을 달성하는 원리와, 이에 수반되는 보안 트레이드오프를 명확히 제시해야 한다.

## Ⅰ. 개요 및 필요성

- 개요: 리눅스 커널의 Namespace와 cgroups를 활용해 애플리케이션과 의존성을 하나로 패키징하고 호스트 OS 커널 위에서 격리 실행하는 경량 가상화 기술
- 배경: 기존 하이퍼바이저 기반 VM은 무거운 Guest OS 부팅 오버헤드로 인해 MSA 환경의 잦은 배포와 빠른 확장에 부적합함
- 필요성: 개발-운영 간 환경 불일치 오류를 제거하고, ms 단위 기동과 하드웨어 자원 집적도 극대화를 위해 필요

---

## Ⅱ. 구조 및 구성요소

```text
Client (CLI) -> Docker Daemon (dockerd) -> containerd -> runc -> Container (격리 실행)
                   | (Push / Pull)
             Registry (Docker Hub 등)
```

| 구성요소 | 역할 | 특이사항 |
|:---|:---|:---|
| Namespace | 컨테이너별 PID, IPC, Network 등 독립된 시스템 뷰 제공 | OS 레벨의 논리적 격리 |
| cgroups | CPU, Memory, I/O 등 물리적 하드웨어 자원 할당 및 사용량 제한 | 특정 컨테이너의 자원 독점 방지 |
| Docker Daemon | 이미지 빌드, 컨테이너 생성 및 생명주기(런타임) 중앙 제어 | 백그라운드 서비스 로직 처리 |
| Registry | 빌드된 읽기 전용 이미지(Template)를 저장하고 분배 | 퍼블릭(Hub) 또는 프라이빗 구축 |

> 요약: 리눅스 커널의 격리 기능(Namespace, cgroups)을 기반으로, 데몬이 레지스트리와 연동해 이미지 기반 컨테이너 생명주기를 통제한다.

---

## Ⅲ. 동작원리 및 흐름도

```text
Dockerfile 작성 -> [docker build] -> Image 생성 -> [docker run] -> Container 실행
      (코드)                               (템플릿)                           (프로세스)
```

- 1단계 빌드 (Build): Dockerfile의 인스트럭션 단위로 읽기 전용 레이어(Layer)를 차곡차곡 쌓아 불변의 이미지 생성
- 2단계 공유 (Push/Pull): 생성된 이미지를 Registry에 업로드하거나, 배포 대상 호스트에서 이미지를 다운로드
- 3단계 실행 (Run): 읽기 전용 이미지 레이어 최상단에 읽기/쓰기(R/W) 레이어를 결합해 독립된 컨테이너 프로세스로 기동
- 4단계 통제 (Control): 호스트 커널의 cgroups를 통해 자원 상한을 걸고, Namespace로 타 프로세스와 격리하여 운영

> 요약: 코드를 다중 레이어 이미지로 빌드하여 배포하고, 런타임에 R/W 레이어를 얹어 격리된 프로세스로 빠르게 기동한다.

---

## Ⅳ. 특징

- 경량성·고성능: Guest OS 부팅 과정이 생략되어 수 ms 내 컨테이너 기동 완료 및 메모리 오버헤드 최소화
- 높은 집적도: 동일한 호스트 하드웨어 기준 VM 대비 수 배~수십 배 이상의 컨테이너 동시 구동
- 불변성과 이식성: 한 번 빌드된 이미지는 수정되지 않으므로(Immutable) "Build Once, Run Anywhere" 일관성 실현
- 보안 취약성: 단일 호스트 내 커널을 공유하므로, 커널 레벨 취약점 발생 시 전체 컨테이너와 호스트가 위협에 노출됨

> 요약: VM 대비 압도적인 기동 성능과 집적도를 제공하지만, 호스트 커널을 공유한다는 구조적 보안 한계를 지닌다.

## Ⅴ. 심화 비교 및 적용 판단

| 비교 축 | 하이퍼바이저 (VM) | Docker 컨테이너 | 선택 기준 |
|:---|:---|:---|:---|
| 구조 및 격리 | HW 레벨 가상화 (Guest OS 포함) | OS 레벨 가상화 (호스트 커널 공유) | 애플리케이션의 격리 요건 |
| 성능 및 용량 | 수 분대 기동, GB 단위 템플릿 | ms 단위 기동, MB 단위 템플릿 | 빠른 확장성(Scale-out) 요건 |
| 주 활용 분야 | 레거시 모놀리식, 강력한 보안 격리 | 마이크로서비스(MSA), CI/CD | 시스템 아키텍처 특성 |

> 요약: 빠른 스케일링과 고밀도 집적도가 필요한 MSA에는 컨테이너를, OS 독립성과 강력한 하드웨어 격리가 필요한 환경에는 VM을 선택한다.

**리스크·대응:**
- 컨테이너 이스케이프: 호스트 커널 취약점 악용으로 탈옥 → AppArmor/Seccomp 적용, Rootless 모드 구동 (지표: 취약점 스캔 통과율 100%)
- 이미지 내 악성코드: 출처 불명 베이스 이미지 사용 → 신뢰할 수 있는 프라이빗 레지스트리 구축, Trivy 이미지 취약점 스캔 (지표: High 이상 CVE 검출 0건)

**도입 후 점검 지표:**
- 성능/효율: 컨테이너 기동 속도 1초 이내 달성 — APM 및 Docker events 모니터링 분석
- 품질/운영: 호스트 CPU/Memory 할당 대비 초과 사용 0건 — cAdvisor 연동을 통한 cgroups 메트릭 검증

## Ⅵ. 실무 적용 및 결론

**적용 방안 3개:**
1. 이미지 경량화 적용: Alpine Linux 등 경량 베이스 이미지 사용 및 멀티 스테이지 빌드(Multi-stage Build)로 최종 배포 용량 최소화
2. 파이프라인 내 보안 내재화(DevSecOps): CI/CD 과정에서 Trivy, Clair 등을 연동하여 컨테이너 이미지 빌드 시점 취약점 자동 차단
3. 샌드박스 혼용: 멀티 테넌트 환경 등 강력한 격리가 필요한 워크로드는 커널을 분리하는 gVisor나 Kata Container 혼합 적용

**결론 (2줄):**
- 기술사 판단: 애플리케이션의 라이프사이클이 짧고 잦은 배포가 필수적인 MSA 환경에서는, 불변 인프라 기반의 Docker 컨테이너 도입이 필수적이다.
- 향후 방향: 단일 도커 호스트 관리 한계를 극복하기 위해 Kubernetes 환경 전환이 주류가 되며, 최근에는 보안과 이식성을 극대화한 WASM(WebAssembly) 기반 런타임과 결합하여 진화 중이다.
