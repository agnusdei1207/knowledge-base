## 핵심 인사이트 (3줄 요약)
- 람다(Lambda) 아키텍처에서 코드를 2번 짜야 했던 '유지보수 지옥'을 해결하기 위해, **배치(Batch) 레이어를 아예 폭파시켜 버리고 오직 스트리밍(Streaming) 레이어 하나로 모든 데이터 처리를 통일**한 혁신적 아키텍처.
- "과거의 거대한 배치 데이터도, 결국은 '아주 오래전에 발생한 실시간 이벤트들의 연속'일 뿐이다"라는 철학적 전환을 통해, Kafka 같은 거대한 메시지 큐에 모든 데이터를 밀어 넣고 스트림 엔진(Flink) 하나로 과거와 현재를 모두 처리함.
- 개발자는 1개의 코드(스트림 로직)만 짜면 되므로 인건비와 서버 비용이 획기적으로 줄지만, Kafka 클러스터에 수년 치 데이터를 보관해야 하므로 메모리와 디스크 인프라 비용이 폭발하는 Trade-off를 가짐.

## Ⅰ. 개요 및 필요성
- **개요**: 링크드인(LinkedIn)의 제이 크렙스(Jay Kreps)가 제안한 데이터 아키텍처로, 람다 아키텍처의 배치 레이어를 제거하고 스트림 처리 엔진 단일 프레임워크로 실시간과 과거 데이터(배치)를 모두 처리하는 구조.
- **필요성**: 람다 아키텍처를 도입한 개발자들은 퇴사 직전이었음. '결제액 계산' 로직을 Hadoop(배치용)과 Storm(실시간용) 두 가지 언어로 짜야 했고, 두 엔진의 결과값이 1원이라도 다르면 밤새워 디버깅해야 했음. "왜 똑같은 로직을 두 번 짜야 하나? 짱 쎈 스트림 엔진 하나로 과거 데이터까지 한 방에 처리하면 안 되나?"라는 분노가 시스템을 진화시켰음.
---
## Ⅱ. 아키텍처 및 핵심 원리
- **1. 모든 것은 스트림이다 (Everything is a Stream)**:
  - 배치 처리란 "쌓아둔 데이터를 한 번에 읽는 것"임.
  - 카파 아키텍처의 철학: "과거에 쌓인 10년 치 데이터(배치)도, 10년 전부터 1초마다 들어왔던 스트림 이벤트를 아주 빠른 배속(Fast-forward)으로 재생(Replay)하는 것과 완벽히 동일하다!"
- **2. 거대한 불변의 로그 저장소 (Apache Kafka)**:
  - 카파 아키텍처가 성립하려면, 과거 수년 치의 데이터(이벤트)를 지우지 않고 무한대로 순서대로 보관할 수 있는 엄청난 파이프라인이 필요함. 
  - 이를 Apache Kafka가 담당하며, 데이터의 원본(Single Source of Truth) 역할까지 수행함.
- **3. 단일 스트림 처리 엔진 (Single Stream Processor)**:
  - Apache Flink나 Kafka Streams 같은 1개의 엔진이, 평소에는 실시간으로 들어오는 1건의 데이터를 처리함.
  - 만약 코드가 바뀌어서 과거 데이터를 재계산(Reprocessing)해야 하면? Kafka에게 "1년 전 첫 번째 줄부터 지금(실시간)까지 다시 다 쏴줘!"라고 요청해서 1개의 코드로 쭉 다시 계산함.

```text
[ 람다(Lambda)와 카파(Kappa)의 진화 과정 ]

 🌿 [ 람다 아키텍처 ]
 데이터 ➡️ [ Hadoop (과거 1년 치 계산) 코드 A ] ➡️ 뷰 머지 ➡️ 화면
        ↘️ [ Spark (오늘 방금 계산) 코드 B ] ↗️
 🚨 "개발자: 아악! A코드랑 B코드랑 결과가 달라! 유지보수 최악!"

 ⚡ [ 카파 아키텍처 ]
 데이터 ➡️ [ 🐘 거대 Kafka (원본 전체 보관) ] ➡️ [ Flink (단일 엔진, 코드 1개!) ] ➡️ 화면
 🚀 "개발자: 휴~ 이제 스트리밍 코드 1개만 짜면, 평소엔 실시간 처리하고, 오류 나면 Kafka에서 옛날 데이터 다시 불러와서 똑같은 코드로 재계산하면 끝!"
```

## Ⅲ. 비교 및 연결
| 구분 | 람다 아키텍처 (Lambda) | 카파 아키텍처 (Kappa) |
|---|---|---|
| **처리 레이어** | Batch Layer + Speed Layer (2개) | **Speed Layer 단일화 (1개)** |
| **코드 베이스** | 2개의 엔진, 2개의 분리된 코드 | **1개의 스트리밍 엔진, 1개의 코드** |
| **원본 데이터 저장소**| HDFS, Amazon S3 (오브젝트 스토리지) | **Apache Kafka (분산 메시지 큐)** |
| **재처리 (Reprocessing)**| 배치 레이어에서 HDFS 데이터를 재계산 | **Kafka의 오프셋(Offset)을 0으로 되감아 다시 스트리밍 재생** |

## Ⅳ. 실무 적용 및 기술사 판단
- **카파 아키텍처의 한계와 스토리지 비용 폭발**: 실무 아키텍트가 카파를 도입할 때 가장 경계해야 할 것은 Kafka의 스토리지 비용임. Kafka는 메모리와 고속 디스크를 쓰는 비싼 인프라인데, 이곳에 10년 치 원본 로그 페타바이트(PB)를 무한정 쌓아두는 것은 돈 낭비임. 그래서 실무에서는 결국 카파의 이상을 약간 포기하고, 오래된 데이터는 저렴한 S3로 빼는 '계층화(Tiered Storage)' 전략을 반드시 섞어서 써야 함.
- **스트리밍 엔진의 고도화 (Apache Flink)**: 카파 아키텍처가 실제로 구동되려면, 스트리밍 엔진이 이벤트가 늦게 도착했을 때 시간 순서를 맞춰주는 워터마크(Watermark) 처리와 정확히 한 번(Exactly-once) 처리 보장을 완벽하게 해내야 함. 이 조건에 가장 부합하는 Apache Flink가 카파 아키텍처의 표준 엔진으로 우뚝 서게 됨.

## Ⅴ. 기대효과 및 결론
- "배치(Batch)는 스트리밍(Streaming)의 특수한(일정 기간 끊어 읽는) 하위 집합일 뿐이다"라는 컴퓨터 공학의 새로운 패러다임을 증명하며 데이터 파이프라인의 복잡도를 극적으로 낮춤.
- 카카오, 넷플릭스, 우버 등 거대한 로그를 실시간으로 다루는 테크 기업들의 백엔드 아키텍처를 단일화시켜 개발 생산성을 폭발적으로 끌어올린 현대 데이터 엔지니어링의 표준 모델임.

### 👶 어린이를 위한 3줄 비유 설명
1. 람다(Lambda) 아키텍처는 과거를 기록하는 '일기장'과 지금 방금 일을 적는 '포스트잇'을 따로 쓰고 나중에 합치는 방식이라 너무 번거로웠어요.
2. **카파(Kappa) 아키텍처**는 두루마리 휴지처럼 끝이 없는 '엄청 긴 영수증(Kafka)' 하나만 쓰는 거예요!
3. 평소에는 끝부분에 지금 들어오는 돈을 실시간으로 적고, 옛날 1년 치 계산을 다시 하고 싶으면 영수증을 맨 앞부터 아주 빠른 배속(스트리밍)으로 다시 쭈르륵 훑어버리면 되는 천재적인 방법이랍니다!
