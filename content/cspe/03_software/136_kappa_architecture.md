## 미리 알고가기

- 카파 아키텍처는 과거·최신 이벤트를 하나의 스트림 처리 코드로 계산하는 데이터 처리 구조임
- 이벤트 로그는 재처리에 필요한 원본·순서·오프셋과 보존 기간을 제공해야 함
- 과거 결과는 별도 배치 코드가 아니라 보존 이벤트를 새 스트림 작업에 재생해 다시 생성함
- 체크포인트는 실행 상태를 복구하고 이벤트 재생은 계산 규칙 변경에 따른 전체 상태 재구성을 지원함
- 물질화 뷰는 스트림 연산 결과를 저장해 응용 조회에 제공하는 데이터 구조임
- 새 처리 버전이 최신 오프셋을 따라잡으면 물질화 뷰를 전환해 기존 결과를 교체함

## 작성 근거(검토용)

- 카파 아키텍처는 단일 스트림 코드, 재생 가능한 로그, 상태 복구, 뷰 재구성과 전환을 핵심 축으로 설명함
- 비교표는 Lambda와 처리 경로·과거 재계산·운영 부담을 대비함
- 실무 사례는 서비스 이벤트 집계와 뷰 재구성을 처리 지연·재생 시간·결과 차이로 검증함
- 제목부터 결론까지 모든 문장·표 셀·요약을 5회 전수 검수해 실시간 처리와 재생 처리의 관계를 확인함

## Ⅰ. 개요

- **정의/개념**: 카파 아키텍처는 재생 가능한 이벤트 로그를 단일 스트림 처리 작업으로 계산하고 과거 결과도 로그 재생으로 재구성하는 데이터 처리 구조임
- **배경/필요성**: 배치·실시간 계층의 코드 불일치와 운영 경로 중복을 줄이기 위해 단일 스트림 처리 모델이 필요함

## Ⅱ. 특징

- 과거·최신 이벤트가 동일한 스트림 처리 코드와 상태 전이 규칙을 거침
- 파티션·오프셋·보존 기간이 이벤트 순서와 재생 가능 범위를 결정함
- 체크포인트에서 상태를 복구하고 필요하면 이전 오프셋부터 이벤트를 다시 적용함
- 계산 규칙 변경 시 새 처리 버전이 로그를 재생해 별도 물질화 뷰를 만든 뒤 조회 대상을 전환함
- 배치 코드 중복은 줄지만 장기 로그 보존·고속 재생·대용량 상태 관리 능력이 필요함

## Ⅲ. 종류 및 비교

| 판단 기준 | Lambda Architecture | Kappa Architecture |
|:---|:---|:---|
| 처리 경로 | 배치 계층과 속도 계층을 병행해 결과를 결합 | 하나의 스트림 경로가 과거·최신 이벤트를 처리해 단일 뷰 제공 |
| 과거 재계산 | 불변 원본 전체에서 배치 뷰 재생성 | 보존 이벤트를 스트림에 다시 재생 |
| 운영 부담 | 두 계산 로직과 결과 정합성 관리 | 로그 보존·재생 처리량·상태 관리 |

> 요약: Kappa는 과거·최신 이벤트를 한 스트림 코드로 처리하고 계산 변경 시 로그 재생으로 뷰를 재구성함.

## Ⅳ. 구성요소 및 구조

| 구성요소 | 설명 |
|:---|:---|
| 이벤트 생산자 | 업무 변경을 순서가 있는 이벤트로 생성함 |
| 재생 가능 로그 | 이벤트를 파티션·오프셋과 함께 보존하고 소비자에게 전달함 |
| 스트림 처리 작업 | 이벤트를 같은 계산 규칙으로 변환·집계함 |
| 상태 저장소·체크포인트 | 집계 상태와 처리 위치를 저장해 실패 시 복구함 |
| 물질화 뷰·조회 API | 스트림 결과를 저장하고 응용 조회에 제공함 |

```text
재생 가능 로그 --실시간 입력·로그 재생--> 스트림 처리 -> 상태 저장소 -> 물질화 뷰
```

> 요약: 재생 가능 로그가 실시간 입력과 과거 재처리의 공통 원본이며 스트림 작업이 물질화 뷰를 갱신함.

## Ⅴ. 원리 및 절차 흐름도

```text
이벤트 기록 -> 실시간 처리 -> 체크포인트 -> 새 버전 로그 재생 -> 최신 추격 -> 뷰 전환
```

1. **이벤트 기록**: 생산자가 이벤트를 파티션에 추가하고 로그가 오프셋을 부여함
2. **실시간 처리**: 스트림 작업이 새 이벤트를 읽어 상태와 물질화 뷰를 갱신함
3. **체크포인트**: 처리 위치와 연산 상태를 저장해 장애 시 일관된 지점에서 복구함
4. **새 버전 재생**: 계산 규칙 변경 시 새 작업이 보존 로그를 이전 오프셋부터 처리함
5. **최신 추격·전환**: 새 작업이 최신 이벤트를 따라잡으면 조회 대상을 새 물질화 뷰로 전환함

> 요약: 정상 처리와 과거 재계산이 같은 로그·스트림 코드를 사용하며 새 뷰가 최신 상태에 도달하면 교체됨.

## Ⅵ. 실무 사례

1. 서비스 이벤트는 Kafka 로그와 Flink 상태 연산으로 집계하고 p99 처리 지연·재시작 시간을 확인함
2. 집계 규칙 변경은 새 작업이 보존 로그를 재생하고 재처리 완료 시간·뷰 결과 불일치 건수를 확인함

## Ⅶ. 결론

- 카파 아키텍처는 로그 보존 기간·재생 처리량·상태 관리 규모와 배치·실시간 계산 통합 요구를 기준으로 적용해야 함
