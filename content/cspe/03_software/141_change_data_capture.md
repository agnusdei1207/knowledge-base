# 📖 【암기용】 개념 완전 이해

> 목적: CDC를 처음 보는 사람도 완벽히 이해하게 만든다. 시험 답안 양식이 아니라, 이해를 위한 친절한 설명이다.

## 한눈에
- **개요**: CDC는 원천 DB의 INSERT·UPDATE·DELETE 변경분만 식별해 다른 시스템으로 전달하는 데이터 동기화 기법임
- **왜 필요한가**: 전체 테이블을 매번 복사하면 배치 시간이 길어지고 원천 DB 부하가 증가함. 변경분만 읽으면 DW·레이크·검색엔진에 준실시간 반영 가능함.
- **핵심 직관**: 장부 전체를 매일 다시 쓰지 않고, 오늘 바뀐 거래 내역만 별도 전표로 보내는 방식임.

## 깊이 이해
- **배경·문제의식**: 야간 ETL은 T+1 분석에는 충분하지만 주문·재고·위험탐지처럼 분 단위 반영이 필요한 업무에는 지연이 큼. CDC는 DB 로그나 트리거를 이용해 변경 이벤트를 추출함.
- **작동 원리**: 로그 기반 CDC는 MySQL binlog, PostgreSQL WAL, Oracle redo log를 읽어 커밋 순서대로 이벤트를 만들고 Kafka, Debezium, Flink, Sink Connector로 전달함.
- **비유**: 신문 전체를 다시 인쇄하는 대신 정오 이후 추가 기사만 속보로 발행하는 방식임.
- **구체 예시**: 주문 테이블 10억 건 중 1일 변경 200만 건이면 전체 스캔 대비 읽기 대상이 0.2%로 줄고, Kafka 파티션 12개로 분산 전송 가능함.
- **흔한 오해·주의점**: CDC는 복제와 동일하지 않음. 스키마 변경, 삭제 이벤트, 순서 보장, 재처리 정책을 설계하지 않으면 분석 테이블 불일치가 발생함.

## 연결 개념
- 이벤트 스트리밍: CDC 이벤트를 Kafka 토픽으로 전달하는 통로
- 데이터 웨어하우스: CDC 변경분을 차원·팩트 테이블에 적재하는 분석 저장소
- 데이터 레이크하우스: CDC를 Parquet 테이블의 upsert·merge로 반영하는 구조

# 📝 【답안용】 시험 답안 템플릿

> 목적: 시험장에서 25분에 그대로 쓰는 답안 양식. 작성방식(추상표현 금지·수치·도식·문제유형 전환)을 엄격히 지킨다.
> 핵심: CDC는 도구명이 아니라 변경 식별, 순서 보장, 장애 재처리, 대상 반영 방식을 함께 설계하는 데이터 동기화 패턴이다.

## 핵심 인사이트 (3줄 요약)

> 1. **본질**: CDC는 원천 DB 변경 로그를 이벤트화해 전체 복사 없이 대상 저장소에 반영하는 기법이다.
> 2. **가치**: 배치 주기 24시간을 분 단위로 낮추고, 전체 스캔 I/O를 변경 행 비율만큼 축소한다.
> 3. **판단 포인트**: 로그 기반·트리거 기반·타임스탬프 기반 중 원천 DB 부하, 순서 보장, 삭제 처리 요구에 맞춰 선택한다.

## 출제 의도 및 답안 포인트

| 출제 의도 | 반드시 짚을 핵심 | 감점 회피 포인트 |
|:---|:---|:---|
| 실시간 데이터 연계 구조 판단 | binlog/WAL/redo log, offset, Kafka, idempotent sink | ETL과 CDC 차이를 단순 주기 차이로만 설명 |
| 정합성 통제 역량 확인 | 커밋 순서, exactly-once 유사 처리, 재처리, 스키마 진화 | 중복 이벤트와 삭제 이벤트 처리 누락 |
| 운영 리스크 인식 | 로그 보관기간, connector lag, dead letter queue | 원천 DB 부하와 권한 범위 미기재 |

> 요약: CDC 답안은 변경 추출 방식보다 순서·중복·장애 재처리 기준을 제시해야 채점 포인트를 충족한다.

## Ⅰ. 개요 및 필요성

CDC는 DB 변경분을 이벤트로 캡처하는 동기화 기법이다. 전체 테이블 재적재는 대용량 환경에서 I/O와 배치 윈도우를 증가시킨다. CDC는 변경 로그 기반으로 DW, 레이크, 검색 색인에 분 단위 반영을 제공해 운영계와 분석계 간 시차를 줄인다.

---

## Ⅱ. 구조 및 구성요소

```text
Source DB -> Change Log -> CDC Connector -> Event Broker -> Sink Connector -> Target Store
                      +-> Schema Registry
                      +-> Monitoring / DLQ
```

| 구성요소 | 역할 | 특이사항 |
|:---|:---|:---|
| Change Log | 커밋된 변경 순서 기록 | binlog, WAL, redo log |
| CDC Connector | 로그 위치와 변경 이벤트 추출 | Debezium, GoldenGate, DMS |
| Event Broker | 이벤트 버퍼링과 파티션 분산 | Kafka offset, retention |
| Sink Connector | 대상 저장소에 insert/update/delete 반영 | idempotent key, merge |

> 요약: CDC 구조는 원천 로그를 이벤트 브로커로 옮긴 뒤 대상별 반영 규칙으로 정합성을 맞추는 파이프라인이다.

---

## Ⅲ. 동작원리 및 흐름도

```text
트랜잭션 커밋 -> 로그 기록 -> offset 읽기 -> 이벤트 변환
-> 토픽 발행 -> 대상 merge/delete -> lag / error 측정
```

| 단계 | 처리 내용 | 검증 기준 |
|:---:|:---|:---|
| 1 | 원천 DB 트랜잭션 커밋 후 로그 생성 | commit timestamp, LSN/binlog position |
| 2 | CDC 커넥터가 offset 기준 변경분 읽기 | lag 60초 이하, offset checkpoint |
| 3 | key, before/after, op code로 이벤트 구성 | insert/update/delete 구분 |
| 4 | 대상 테이블에 merge 또는 delete 반영 | 중복 처리 0건, PK 충돌 검출 |

> 요약: CDC는 로그 위치를 기준으로 변경 이벤트를 읽고, 대상 저장소에서 키 기반 멱등 반영으로 정합성을 통제한다.

---

## Ⅳ. 특징

| 구분 | 기존 배치 ETL | CDC | 수치·판단 포인트 |
|:---|:---|:---|:---|
| 처리 단위 | 전체 또는 파티션 단위 재적재 | 변경 행 단위 이벤트 | 변경률 1%면 읽기 대상 99% 감소 |
| 지연 | 일·시간 단위 | 초·분 단위 | connector lag 60초 이하 목표 |
| 삭제 처리 | 누락 가능 | delete 이벤트 명시 | tombstone, soft delete 구분 |
| 운영 부담 | 배치 실패 시 재실행 단순 | offset, 스키마, DLQ 관리 필요 | 로그 보관기간 24~72시간 확보 |

> 요약: CDC는 데이터 반영 지연을 줄이지만 offset, 삭제, 스키마 변경 통제가 필수인 운영형 데이터 통합 방식이다.

## Ⅴ. 심화 비교 및 적용 판단

| 비교 축 | 기존/대안 | CDC | 선택 기준 |
|:---|:---|:---|:---|
| 구조 | 야간 ETL, API polling | 로그 기반 이벤트 추출 | 변경 반영 목표 5분 이하 |
| 비용/성능 | 전체 스캔 I/O 증가 | 변경률만큼 읽기 감소 | 일 변경률 10% 이하일 때 우선 검토 |
| 운영/위험 | 재실행 단순 | offset 손실, 로그 만료 | 로그 보관기간과 재처리 절차 확보 |

> 요약: CDC는 준실시간성과 변경률이 낮은 대용량 테이블에서 적합하며, 로그 보존과 재처리 체계가 선택 전제다.

| 리스크 | 원인 | 대응 방안 | 확인 지표 |
|:---|:---|:---|:---|
| 이벤트 중복 | 커넥터 재시작, offset 재처리 | PK 기반 upsert, idempotent sink | 중복 반영 0건 |
| 데이터 누락 | 로그 만료, 권한 부족 | retention 72시간, 권한 점검 | LSN 연속성, gap count |
| 스키마 불일치 | 컬럼 추가·타입 변경 | Schema Registry, 호환성 검사 | schema error rate 0.1% 이하 |

> 요약: CDC 리스크는 중복보다 누락이 치명적이며, offset 연속성과 스키마 호환성 지표로 관리한다.

| 점검 항목 | 목표 기준 | 측정 방법 |
|:---|:---|:---|
| 지연 | end-to-end lag 60초 이하 | Kafka lag, sink latency |
| 정합성 | 원천·대상 row count 오차 0.01% 이하 | checksum, reconciliation job |
| 복구 | 장애 후 재처리 RTO 30분 이하 | checkpoint 복원 테스트 |

> 요약: CDC 운영 성공 여부는 지연, 정합성, 복구 시간을 동시에 측정해야 판단 가능하다.

## Ⅵ. 실무 적용 및 결론

**적용 방안 3개 (필수 — 단계별 또는 항목별):**
1. MySQL binlog/PostgreSQL WAL 기반 Debezium 커넥터를 적용하고 Kafka retention 72시간, 파티션 12개 기준으로 lag 60초 이하 유지
2. 대상 DW·레이크 테이블은 PK 기반 MERGE, delete tombstone, 재처리용 DLQ를 설계해 중복·삭제 이벤트 처리
3. 스키마 변경은 Schema Registry backward compatibility와 일 1회 reconciliation job으로 원천·대상 row count 검증

**결론 (2줄):**
- 기술사 판단: 변경 반영 목표가 5분 이하이고 원천 DB 로그 접근이 가능하면 CDC, 일 단위 분석이면 배치 ETL 선택
- 향후 방향: CDC는 레이크하우스의 MERGE, 스트리밍 처리, 이벤트 기반 MSA와 결합해 운영·분석 데이터 경계를 줄이는 방향으로 발전
