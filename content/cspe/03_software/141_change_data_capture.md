## 핵심 인사이트 (3줄 요약)
- 낡은 운영 DB(MySQL, Oracle)의 데이터 변경 사항(INSERT/UPDATE/DELETE)을, DB 서버에 부하를 주지 않고 **숨겨진 트랜잭션 로그(Binlog)를 몰래 훔쳐보며 0.1초 만에 실시간으로 뽑아내는 궁극의 데이터 동기화 마법**.
- 과거에는 밤마다 배치를 돌려 1,000만 건 테이블을 전부 다 긁어오느라(Full Scan) 서버가 뻗었지만, CDC는 "변경된 3건"의 로그만 빨대로 쪽 빨아먹고 Kafka에 던져주어 부하를 0(Zero)에 가깝게 만듦.
- MSA 환경에서 찢어진 DB 간의 데이터 동기화, 이기종 DB(MySQL ➡️ ElasticSearch) 마이그레이션, 실시간 데이터 웨어하우스 구축 등 현대 클라우드 데이터 파이프라인의 **가장 중요한 '첫 번째 수도꼭지'** 역할을 함.

## Ⅰ. 개요 및 필요성
- **개요**: 데이터베이스에서 발생한 데이터의 변경(Change) 이벤트를 실시간 포착(Capture)하여, 다른 시스템이나 데이터 웨어하우스로 비동기 전송하는 기술 패턴.
- **필요성**: 쇼핑몰에서 고객이 상품을 사면 운영 DB(MySQL)에 저장됨. 동시에 이 내역이 검색 엔진(ElasticSearch)과 추천 AI(Hadoop)에도 들어가야 함. 개발자가 애플리케이션 코드에 "1. MySQL 저장 ➡️ 2. 검색엔진 전송 ➡️ 3. 추천서버 전송"을 다 짜면 로직이 스파게티가 되고 속도가 느려짐. 앱 코드는 건드리지 않고, **DB 밑단에서 데이터가 변한 사실만 조용히 낚아채서 뿌려주는 인프라**가 절실했음.
---
## Ⅱ. 아키텍처 및 핵심 원리
- **1. 쿼리 기반 CDC (구식/Polling 방식)**:
  - 앱에서 1분마다 `SELECT * FROM 테이블 WHERE 업데이트_시간 > 방금 전;` 쿼리를 때림.
  - 치명적 단점: 1분마다 DB에 부하를 주며, 그 1분 사이에 레코드가 2번(A ➡️ B ➡️ C) 바뀌거나 삭제(Delete)되면 중간 과정을 절대 잡아낼 수 없음.
- **2. 로그 기반 CDC (Log-based CDC, 현대의 표준)**:
  - DBMS는 원래 복구를 위해 모든 변경 내역을 숨겨진 파일(MySQL의 Binlog, Oracle의 Redo Log)에 초 단위로 기록함.
  - **Debezium(디비지움)** 같은 CDC 도구가 DB 엔진인 척 위장하여 이 로그 파일에 빨대를 꽂음. 
  - DB의 CPU나 메모리에는 전혀 부하를 주지 않으며, DELETE나 2번 변경된 과정(A➡️B➡️C)까지 트랜잭션 단위로 100% 훔쳐(Capture)냄.
- **3. 이벤트 스트리밍 파이프라인**:
  - 뽑아낸 `{"op": "u", "before": "A", "after": "B"}` 형태의 JSON 이벤트를 곧바로 Apache Kafka로 쏨. 이로써 전사적 실시간 스트리밍의 수도꼭지가 완성됨.

```text
[ MSA 환경에서의 로그 기반 CDC(Debezium + Kafka) 동작 원리 ]

 📱 [ 고객: 회원 탈퇴 버튼 클릭! ] ➡️ (스프링 백엔드 코드는 MySQL에서 삭제만 하고 끝남, 엄청 빠름!)

 💾 [ 회원 DB (MySQL) ] ➡️ 내부 Binlog 파일에 몰래 적힘: "[DELETE] ID:1 철수"
 
 🕵️ [ Debezium (CDC 도구) ] ➡️ "오호, Binlog에 삭제 이벤트 떴다! 0.1초 만에 캐치!"
        ⬇️ (JSON으로 변환해서 쏨)
 🐘 [ Apache Kafka ] ➡️ "회원 변경 토픽에 이벤트 등록 완료!"
        ↙️                 ↘️
 🔍 [ 검색 엔진 ]        📊 [ 통계 서버 ]
 "철수 검색 삭제!"      "오늘 탈퇴자 1명 추가!" 
 (앱 코드 수정 없이, DB 부하 없이 완벽하게 전사 시스템 실시간 동기화 완료!)
```

## Ⅲ. 비교 및 연결
| 구분 | 배치(Batch) 추출 (ETL) | 쿼리 기반 CDC (Polling) | 로그 기반 CDC (Log-based) |
|---|---|---|---|
| **동기화 지연** | 하루 1번 (24시간 지연) | 1~5분마다 (부하 심함) | **0.1초 실시간 (실시간 동기화)** |
| **운영 DB 부하** | 풀 스캔 시 서버 뻗을 위험 큼 | 쿼리를 계속 날려야 해서 부하 큼 | **로그 파일만 읽으므로 부하 0 (Zero)** |
| **변경 중간 과정**| 알 수 없음 (최종 결과만) | 알 수 없음 (가운데 덮어씌워짐) | **A ➡️ B ➡️ C 변한 족보 100% 다 잡음** |
| **삭제(Delete)** | 삭제된 사실을 감지 못 함 | 감지 불가능 (행이 사라져 버리므로) | **DELETE 이벤트도 100% 캡처함** |

## Ⅳ. 실무 적용 및 기술사 판단
- **아웃박스 패턴(Outbox Pattern)과의 결합**: MSA에서 A서비스가 자기 DB를 업데이트하고, B서비스에 이벤트를 날리다 에러가 나면 데이터 정합성이 깨짐(이중 쓰기 문제). 실무 아키텍트는 이를 막기 위해, A서비스가 자기 DB 안의 'Outbox 테이블'에 이벤트 내역만 `INSERT`(단일 트랜잭션 보장) 해두고, **CDC가 이 Outbox 테이블의 Binlog를 캐치해서 Kafka로 쏘도록 설계**함. 넷플릭스 등 글로벌 기업이 분산 트랜잭션을 회피하는 가장 우아하고 표준적인 패턴임.
- **초기 스냅샷(Snapshot)의 고통**: CDC 도구(Debezium)를 처음 붙일 때, 방금 변한 로그는 잘 잡지만 기존에 쌓여있던 1,000만 건의 옛날 데이터는 알지 못함. 결국 맨 처음 1번은 1,000만 건을 무식하게 풀 스캔(Initial Snapshot) 해야 하는데, 이 과정에서 DB에 엄청난 락(Lock)이 걸려 서비스가 뻗을 수 있음. 기술사는 반드시 서비스 트래픽이 가장 적은 새벽에 스냅샷을 돌리거나 워터마크 기반으로 쪼개서 스냅샷을 뜨는 전략을 세워야 함.

## Ⅴ. 기대효과 및 결론
- "데이터를 옮기는 작업이 메인 데이터베이스를 괴롭혀서는 안 된다"는 아키텍처의 황금률을 완성하며, 레거시 RDB에 갇혀있던 데이터를 실시간 이벤트의 강물(Stream)로 해방시킨 최고의 혁신 기술.
- 모든 시스템이 느슨하게 결합(Decoupling)되어야 하는 현대 클라우드 MSA 환경에서, 이기종 데이터베이스 간의 동기화 병목을 뚫어버린 '비동기 파이프라인의 심장'임.

### 👶 어린이를 위한 3줄 비유 설명
1. 선생님(운영 DB)이 칠판에 필기할 때마다, 반장이 그걸 똑같이 베껴 쓰려면(배치/쿼리) 선생님이 글 쓰는 걸 방해하거나 계속 물어봐야 해서 너무 시끄러웠어요.
2. **CDC(변경 데이터 캡처)**는 선생님 칠판 밑에 '비밀 복사기(로그 훔쳐보기)'를 달아놓은 거예요!
3. 선생님은 평소처럼 조용히 글씨만 쓰고 칠판을 지우기도 하지만, 비밀 복사기가 0.1초 만에 바뀐 내용만 쓱 복사해서 반장(다른 시스템)에게 전달해주니까 교실이 아주 조용하고 평화롭답니다!
