## 미리 알고가기

- CDC(Change Data Capture)는 DB의 삽입·수정·삭제를 변경 이벤트로 추출하는 기법임
- 변경 로그는 DB가 복구·복제를 위해 기록하는 트랜잭션 이력임
- 초기 스냅샷은 기존 전체 데이터를 읽어 변경 스트림의 시작 기준을 만드는 과정임
- 변경 위치는 LSN·SCN·binlog 위치처럼 소스 로그의 재시작 지점을 식별함
- 변경 이벤트는 연산 종류·테이블·키를 담고 설정에 따라 변경 전·후 값과 트랜잭션 메타데이터를 포함함
- 스키마 이력은 변경 로그 해석에 필요한 테이블 구조 변화를 보존함

## 작성 근거(검토용)

- CDC는 변경 탐지 방식·삭제 포착·소스 부하를 핵심 판단축으로 선정함
- 비교표는 로그 기반·트리거 기반·쿼리 기반 CDC를 변경 탐지·삭제 포착·소스 부하 기준에서 대비함
- 절차는 초기 스냅샷과 로그 위치 연결, 이벤트 발행과 위치 저장까지 실제 전환 흐름을 설명함
- 제목부터 결론까지 모든 문장·표 셀·요약을 5회 전수 검수해 용어와 보장 범위를 교정함

## Ⅰ. 개요

- **정의/개념**: CDC는 운영 DB의 삽입·수정·삭제를 변경 로그·트리거·쿼리로 탐지해 변경 이벤트로 전달하는 데이터 연계 기법임
- **배경/필요성**: 운영 DB의 전체 재조회와 배치 복사를 줄이고 변경분을 분석·검색·캐시에 반영하기 위해 변경 위치 기반 추출 구조가 필요함

### 쉽게 이해하기 (학습용)
- 원본 장부를 매번 통째로 복사하지 않고 새로 바뀐 줄만 찾아 다른 시스템에 전달하는 기술임

## Ⅱ. 특징

- 변경 이벤트만 전달해 전체 테이블 복사보다 전송량과 소스 조회 부하를 줄임
- 로그 기반 CDC는 DB 트랜잭션 로그에서 커밋된 변경과 로그 위치를 읽음
- 초기 스냅샷 종료 지점과 변경 로그 시작 지점을 연결해 누락·중복 범위를 통제함
- 기본 키와 연산 종류는 소비자가 삽입·수정·삭제를 멱등 반영하는 기준이 됨
- 스키마 변경과 로그 보존 기간이 커넥터의 이벤트 해석 범위와 장애 복구 가능 범위를 결정함

### 쉽게 이해하기 (학습용)
- 변경 순서와 삭제까지 놓치지 않으면서 재시작할 정확한 위치를 저장해야 함

## Ⅲ. 종류 및 비교

| 판단 기준 | 로그 기반 CDC | 트리거 기반 CDC | 쿼리 기반 CDC |
|:---|:---|:---|:---|
| 변경 탐지 | 트랜잭션 로그를 순차 판독하고 마지막 로그 위치부터 재시작 | 테이블 트리거가 변경 테이블에 기록하고 처리 위치부터 재시작 | 갱신 시각·증가 키 조건으로 재조회하고 마지막 조회 시각·키부터 재조회 |
| 삭제 포착 | 삭제 로그에서 키·이전 값 추출 | 삭제 트리거가 키를 별도 기록 | 삭제 표식이 없으면 탐지하기 어려움 |
| 소스 부하 | 업무 쿼리와 분리된 로그 읽기 부하 | 원본 쓰기에 트리거 실행 부하 추가 | 반복 스캔과 색인 조회 부하 추가 |

> 요약: 로그 기반 CDC는 트랜잭션 로그 위치로 변경과 삭제를 탐지해 재시작 지점을 확보하고 트리거·쿼리 방식은 소스 부하 제약에 따라 선택함.

### 쉽게 이해하기 (학습용)
- 로그 방식은 정확하고 부하가 낮으며 트리거·쿼리 방식은 접근 제약에 따라 선택함

## Ⅳ. 설계 요소 및 구조

| 구성요소 | 설명 |
|:---|:---|
| Source DB·Change Log | 업무 트랜잭션과 삽입·수정·삭제 로그를 생성함 |
| 스냅샷 판독기 | 기존 테이블을 읽고 변경 스트림 시작 기준을 설정함 |
| CDC Connector | 변경 로그를 해석해 공통 변경 이벤트로 변환함 |
| Offset·Schema History | 마지막 처리 위치와 로그 해석에 필요한 스키마 변화를 저장함 |
| Event Broker | 테이블·키별 변경 이벤트를 보존하고 소비자와 생산자를 분리함 |
| Sink Connector | 분석 테이블·검색 색인·캐시에 변경을 멱등 반영함 |

```text
Source DB -> Change Log -> CDC Connector -> Event Broker -> Sink
     |                          |
Snapshot                 Offset·Schema History
```

> 요약: 스냅샷과 변경 로그를 커넥터가 연결하고 처리 위치·스키마 이력으로 재시작 가능한 이벤트를 생성함.

### 쉽게 이해하기 (학습용)
- 원본 로그, 최초 복사기, 변경 해석기, 처리 책갈피와 이벤트 전달 통로로 구성됨

## Ⅴ. 원리 및 절차 흐름도

```text
로그 위치 확보 -> 초기 스냅샷 -> 변경 로그 판독 -> 이벤트 발행 -> 위치 저장
```

1. **위치 확보**: 커넥터가 스냅샷과 이어질 변경 로그의 기준 위치를 기록함
2. **초기 적재**: 기존 행을 일관된 스냅샷으로 읽어 생성 이벤트로 전달함
3. **변경 판독**: 기준 위치 이후의 커밋 로그에서 삽입·수정·삭제와 스키마 변화를 해석함
4. **이벤트 발행**: 테이블·키·연산·변경 값을 포함한 이벤트를 브로커에 기록함
5. **복구점 저장**: 전달이 확정된 로그 위치를 저장해 장애 후 재시작 지점으로 사용함

> 요약: CDC는 스냅샷 기준 위치 이후의 로그를 이벤트로 변환하고 확정 위치를 저장해 연속 처리함.

### 쉽게 이해하기 (학습용)
- 최초 복사 시점과 로그 위치를 연결하고 이후 변경을 순서대로 보내며 위치를 갱신함

## Ⅵ. 실무 사례

1. 상품 검색 색인은 로그 기반 CDC로 변경분을 반영하고 소스 로그 지연량·색인 반영 지연을 확인함
2. 분석 테이블 적재는 변경 키로 멱등 병합하고 재처리 중복 건수·누락 건수를 확인함

### 쉽게 이해하기 (학습용)
- 분석 테이블·검색 색인 동기화에서 지연·중복·삭제 누락·재시작 시간을 확인함

## Ⅶ. 결론

- CDC는 DB 로그 접근성·변경 순서·삭제 포착·복구 위치와 싱크 멱등성 요구를 기준으로 설계해야 함
- 초기 스냅샷과 로그 전환 경계·스키마 변경·로그 보존 만료를 장애 시험과 대사 지표로 검증해야 함

### 쉽게 이해하기 (학습용)
- 첫 복사와 변경 일지 사이에 빠진 줄이 없고 양식 변경 뒤에도 이어 읽는지 시험해야 함
