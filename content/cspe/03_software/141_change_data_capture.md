# 📖 【암기용】 개념 완전 이해

## 한눈에
- **개요**: 데이터베이스에서 발생한 변경 사항(Insert, Update, Delete)을 실시간으로 감지하여 외부 시스템으로 전달하는 기술이다.
- **왜 필요한가**: 원본 DB에 부하를 주지 않고도 데이터 변경 내역을 실시간으로 데이터 웨어하우스나 검색 엔진 등에 동기화해야 하기 때문이다. 배치 추출 방식은 지연 시간이 길고 부하가 크다.
- **핵심 직관**: 데이터베이스가 쓰는 '일기장(트랜잭션 로그)'을 옆에서 몰래 훔쳐보고, 새 내용이 적힐 때마다 다른 시스템에 그대로 전달하는 파이프라인이다.

## 핵심 용어 정리

| 용어/표기 | 의미 | 비유·예 |
|:---|:---|:---|
| 변경 데이터 캡처 (CDC) | DB 변경 사항 감지 및 실시간 전송 기술 | 일기장 감시자 |
| 트랜잭션 로그 (Transaction Log) | DB 내 모든 변경 내역이 순서대로 기록된 파일 (예: MySQL binlog, Oracle Redo log) | DB의 일기장 |
| 소스 시스템 (Source) | 데이터가 처음 변경되는 원본 DB | 원본 일기장 |
| 타겟 시스템 (Target) | 변경 사항을 전달받아 반영하는 시스템 (예: DW, Kafka) | 복사본 일기장 |

## 깊이 이해
- **배경·문제의식**: 기존 데이터 동기화는 주기적인 배치(Batch) 작업으로 전체 데이터를 비교(Diff)하거나 쿼리로 폴링(Polling)했다. 이 방식은 DB 자원을 많이 소모하고 실시간성이 떨어졌다.
- **작동 원리**: 대부분의 현대적 CDC는 로그 기반(Log-based)으로 동작한다. 원본 DB는 복구를 위해 반드시 트랜잭션 로그를 남긴다. CDC 도구(예: Debezium)는 이 로그 파일을 직접 읽어 변경된 내용(Insert, Update, Delete)만 이벤트로 변환하여 메시지 큐(예: Kafka)로 전송한다.
- **비유**: 주기적 쿼리 방식이 매시간 방에 들어가 "바뀐 거 있나요?" 하고 묻는 거라면, 로그 기반 CDC는 방 문에 CCTV를 달아두고 누군가 들어갈 때마다 즉시 알림을 받는 것이다.
- **구체 예시**: MySQL에 고객 정보가 Update되면 binlog에 기록된다. Debezium은 이 binlog를 읽어 JSON 형태의 이벤트(`{"before": {"name": "Old"}, "after": {"name": "New"}}`)를 만들어 Kafka 토픽에 발행한다.
- **흔한 오해·주의점**: 쿼리 기반 CDC(Timestamp 컬럼 기준 추출)도 CDC의 일종이지만, 원본 DB 부하와 Delete 감지 불가 문제로 인해 현재는 주로 로그 기반 CDC를 의미하는 용어로 쓰인다.

## 연결 개념
- Apache Kafka — CDC 이벤트를 안정적으로 전달하고 버퍼링하는 메시징 플랫폼
- 데이터 웨어하우스 (Data Warehouse) — CDC를 통해 실시간으로 데이터를 적재하는 타겟 시스템
- CQRS 패턴 — 상태 변경과 조회를 분리할 때, 상태 변경 이벤트를 조회 모델로 동기화하는 데 CDC 활용

# 📝 【답안용】 시험 답안 템플릿

## 핵심 인사이트 (3줄 요약)

> 1. **본질**: 데이터베이스의 데이터 변경 이벤트(Insert, Update, Delete)를 실시간으로 식별하고 캡처하여 타겟 시스템에 전달하는 데이터 통합 기술이다.
> 2. **가치**: 소스 시스템의 부하를 최소화하면서 데이터 웨어하우스, 데이터 레이크, 마이크로서비스 간의 근실시간(Near Real-time) 데이터 동기화를 보장한다.
> 3. **판단 포인트**: 트리거 방식과 타임스탬프 방식의 한계를 극복하기 위해, 실무에서는 트랜잭션 로그 기반(Log-based) CDC와 이벤트 스트리밍 플랫폼(Kafka)을 결합하여 구성한다.

## 출제 의도 및 답안 포인트

| 출제 의도 | 반드시 짚을 핵심 | 감점 회피 포인트 |
|:---|:---|:---|
| 실시간 데이터 통합 아키텍처 설계 역량 확인 | 로그 기반 CDC, Debezium, Kafka, 원본 부하 최소화 | CDC 방식 비교 누락, 구체적 기술명(Debezium 등) 누락 |

> 요약: 데이터 동기화의 지연 시간과 DB 부하 문제를 해결하기 위한 로그 기반 실시간 데이터 통합 아키텍처 설계력을 요구한다.

## Ⅰ. 개요 및 필요성

- 개요: CDC는 소스 데이터베이스의 데이터 변경 이벤트(Insert, Update, Delete)를 실시간으로 식별·추출하여 타겟 시스템으로 전달하는 기술이다.
- 배경: 기존 배치 기반 ETL 방식은 데이터 추출 주기로 인한 지연(Latency)이 발생하고, 대량 데이터 스캔 시 원본 DB 성능 저하를 야기함
- 필요성: 마이크로서비스 데이터 동기화, 실시간 분석 환경 구축을 위해 원본 부하 없는 근실시간(Near Real-time) 데이터 통합 아키텍처 필수

---

## Ⅱ. 구조 및 구성요소

```text
Source DB -> Transaction Log -> CDC Connector -> Event Broker -> Sink Connector -> Target System
(MySQL)      (binlog)           (Debezium)       (Kafka)         (Kafka Connect)   (DW / Data Lake)
```

| 구성요소 | 역할 | 특이사항 |
|:---|:---|:---|
| Transaction Log | DB 내 모든 데이터 변경 내역을 순서대로 기록 | Redo log, binlog, WAL 등 |
| CDC Connector | 트랜잭션 로그를 읽어 데이터 변경 이벤트를 캡처 및 변환 | Debezium, Oracle GoldenGate |
| Event Broker | 캡처된 변경 이벤트를 수집·버퍼링하여 타겟으로 비동기 전달 | Apache Kafka 활용 |
| Target System | 변경 이벤트를 최종 적재하여 분석 및 조회 서비스 제공 | Snowflake, ElasticSearch 등 |

> 요약: CDC는 트랜잭션 로그를 캡처하는 커넥터와 이벤트를 중계하는 브로커를 통해 원본과 타겟을 디커플링한다.

---

## Ⅲ. 동작원리 및 흐름도

```text
데이터 변경 발생 -> 트랜잭션 로그 기록 -> 로그 스니핑 및 이벤트 변환 -> 이벤트 전송 및 적재
```

- 1단계 [변경 발생 및 기록]: Source DB에서 트랜잭션 커밋 시 변경 내역이 트랜잭션 로그(WAL)에 순차 기록됨
- 2단계 [로그 스니핑]: CDC Connector가 주기적인 DB 폴링 없이 트랜잭션 로그 파일을 직접 읽어들임
- 3단계 [이벤트 변환]: 캡처된 로그 레코드를 표준 이벤트 포맷(예: JSON, Avro)으로 변환하고 Broker 토픽에 발행
- 4단계 [전송 및 적재]: Sink Connector가 Broker를 구독하여 Target System의 스키마에 맞게 데이터를 반영함

> 요약: 원본 DB 메모리나 디스크에 직접 쿼리하지 않고, 트랜잭션 로그 파일만 비동기로 스니핑하여 부하를 격리한다.

---

## Ⅳ. 특징
- 실시간성 보장: 배치(Batch) 방식과 달리 데이터 변경 즉시 이벤트가 발생하여 밀리초(ms) 단위 지연 시간 확보
- 부하 최소화: 로그 기반 CDC는 원본 DB 엔진에 직접 쿼리를 수행하지 않아 서비스 쿼리 성능에 영향 없음
- 데이터 무결성: 순서가 보장된 트랜잭션 로그를 활용하므로 변경 순서 및 삭제(Delete) 이벤트까지 정확히 캡처
- 유연한 확장성: 이벤트 브로커(Kafka)를 통해 1:N 구조의 데이터 파이프라인 구성 및 다양한 타겟 시스템 동시 적재

> 요약: 로그 기반 CDC는 실시간성, 부하 최소화, 무결성을 모두 만족하여 현대 데이터 파이프라인의 표준으로 자리 잡았다.

## Ⅴ. 심화 비교 및 적용 판단

| 비교 축 | Time/Date Column 방식 | Trigger 방식 | Log-based 방식 (CDC) | 선택 기준 |
|:---|:---|:---|:---|:---|
| 작동 원리 | 갱신 일시 컬럼 조건 쿼리 추출 | 변경 시 트리거 구동 후 별도 테이블 적재 | DB 트랜잭션 로그 직접 스니핑 | 실시간성 및 부하 요건 |
| 원본 부하 | 쿼리 스캔으로 인한 부하 높음 | 트랜잭션 오버헤드로 부하 매우 높음 | 로그만 읽으므로 부하 매우 낮음 | 시스템 성능 영향도 |
| 삭제 감지 | Hard Delete 감지 불가 | 감지 가능하나 부하 가중 | 완벽 감지 가능 | 데이터 무결성 요건 |

> 요약: 타임스탬프나 트리거 방식은 부하와 삭제 감지 한계가 있으므로, 성능과 무결성이 중요한 환경에서는 Log-based CDC를 선택한다.

**리스크·대응 (기본 불릿):**
- 스키마 변경 불일치: 소스 DB 스키마 변경 시 CDC 변환 오류 발생 → Schema Registry 연동 및 스키마 진화(Evolution) 정책 적용 (지표: 파이프라인 오류 건수)
- 이벤트 순서 보장 실패: 비동기 전송 중 이벤트 순서 역전 → Kafka 파티션 키를 Primary Key로 지정하여 순서 보장 (지표: 순서 불일치 발생 수)
- 트랜잭션 로그 삭제: DB가 로그를 지우기 전 CDC가 캡처 실패 → 보관 주기(Retention) 연장 및 모니터링 알람 설정 (지표: 로그 소실 경고 수)

**도입 후 점검 지표 (기본 불릿):**
- 성능/효율: End-to-End 지연 시간 p95 5초 이하 — Kafka Consumer Lag 모니터링
- 품질/운영: 원본과 타겟 간 데이터 불일치율 0% — 주기적인 데이터 정합성 검증 스크립트 실행

## Ⅵ. 실무 적용 및 결론

**적용 방안 3개:**
1. 마이크로서비스 간 데이터 동기화: MSA 환경에서 Strangler Fig 패턴 적용 시, 구형 모놀리식 DB와 신규 마이크로서비스 DB 간 상태 동기화에 Debezium 활용
2. 실시간 데이터 웨어하우스 적재: RDBMS의 운영 데이터를 Snowflake, BigQuery 등 클라우드 DW로 실시간 복제하여 최신 분석 환경 제공
3. 캐시 및 검색 인덱스 무효화: DB 변경 시 CDC를 통해 Redis 캐시를 무효화(Invalidation)하거나 Elasticsearch 인덱스를 실시간 업데이트

**결론:**
- 기술사 판단: 서비스 DB 부하 요건이 엄격하고 실시간성이 요구되는 경우, 타임스탬프 기반 폴링을 배제하고 반드시 Log-based CDC 구조로 설계해야 한다.
- 향후 방향: 최근에는 CDC 솔루션들이 클라우드 네이티브 서비스(예: AWS DMS, Confluent) 형태로 발전하여 관리 편의성과 확장성을 높이고 있다.
