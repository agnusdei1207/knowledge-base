# 📖 【암기용】 개념 완전 이해

> 목적: CDC를 처음 보는 사람도 완벽히 이해하게 만든다. 시험 답안 양식이 아니라, 이해를 위한 친절한 설명이다.

## 한눈에
- **개요**: CDC(Change Data Capture)는 **데이터 동기화**(Data Synchronization) 기법 중 하나로, 원천 DB 테이블 전체를 복사하지 않고 커밋된 변경 로그(INSERT·UPDATE·DELETE)만 이벤트로 뽑아 다른 시스템에 반영한다.
- **왜 필요한가**: 매일 전체 테이블을 다시 복사하는 방식(풀 스캔 배치)은 테이블이 커질수록 배치 시간과 원천 DB 부하가 함께 늘어난다. 변경분만 읽으면 읽어야 할 데이터량이 변경률만큼 줄고, 분 단위로 대상 시스템에 반영할 수 있다.
- **핵심 직관**: 회계 장부 전체를 매일 새로 옮겨 적지 않고, 오늘 발생한 거래만 별도 전표로 옆 부서에 보내는 방식이다 — 전표(변경 이벤트)만 보면 오늘 무엇이 바뀌었는지 알 수 있다.

## 핵심 용어 정리 (내부에 등장하는 것들)

| 용어 | 의미 | 비유 |
|:---|:---|:---|
| 데이터 동기화 | 서로 다른 저장소의 데이터를 같은 상태로 맞추는 것 — CDC가 속하는 상위 분류 | 여러 시계를 같은 시각으로 맞추는 것 |
| 변경 로그(Change Log) | DB가 트랜잭션 커밋 순서대로 기록하는 로그 — binlog(MySQL), WAL(PostgreSQL), redo log(Oracle) | 은행의 거래 원장 |
| LSN·오프셋 | 로그 안에서 특정 위치를 가리키는 번호 — 어디까지 읽었는지 추적 | 책의 페이지 번호 |
| CDC 커넥터 | 변경 로그를 읽어 이벤트로 변환하는 소프트웨어(Debezium, GoldenGate, DMS) | 원장을 읽어 전표로 옮겨 적는 사무원 |
| op 코드(before/after) | 이벤트가 insert·update·delete 중 무엇인지, 변경 전·후 값이 무엇인지 담은 필드 | 전표의 "입금·출금·정정" 구분란 |
| 톰스톤(Tombstone) | delete 이벤트를 나타내는 특수 레코드(값이 null) | "이 계좌 폐쇄"라는 도장 |
| 멱등 반영(Idempotent Sink) | 같은 이벤트가 중복 도착해도 대상 테이블 결과가 한 번 반영한 것과 같도록 하는 방식(예: PK 기반 MERGE) | 같은 정정 전표가 두 번 와도 최종 잔액은 한 번만 바뀌는 것 |
| 로그 기반 CDC | DB 내부 트랜잭션 로그를 읽는 방식 — 원천 DB 부하가 적고 delete까지 잡힘 | 원장을 옆에서 몰래 읽어가는 방식 |
| 트리거 기반 CDC | 테이블에 트리거를 달아 변경 시 별도 테이블에 기록하는 방식 — 원천 DB 쓰기 부하 추가 | 거래 때마다 사본을 즉시 한 부 더 쓰는 방식 |
| 타임스탬프 폴링 | updated_at 컬럼을 주기적으로 조회해 변경분을 찾는 방식 — delete 이벤트 포착 불가 | 몇 분마다 장부를 훑어보며 바뀐 줄만 찾는 방식 |

## 깊이 이해

### 세 가지 CDC 방식의 판별 기준
- 로그 기반: MySQL binlog, PostgreSQL WAL, Oracle redo log를 읽는다. 원천 DB에 추가 쿼리 부하를 주지 않고 delete까지 정확히 잡으며 커밋 순서를 그대로 보존한다. 대신 DB 종류별로 로그 포맷이 달라 커넥터(Debezium 등)가 필요하고, 로그 보관 기간이 짧으면(예: binlog 24시간) 커넥터가 오래 멈췄을 때 유실 위험이 있다.
- 트리거 기반: 테이블에 AFTER INSERT·UPDATE·DELETE 트리거를 달아 변경분을 별도 테이블에 적재한다. 구현이 단순하지만 트랜잭션마다 트리거 실행 비용이 추가되어 원천 DB 쓰기 성능이 떨어진다.
- 타임스탬프 폴링: updated_at 컬럼을 주기적으로(예: 1분마다) `WHERE updated_at > 마지막 조회 시각`으로 조회한다. 구현이 가장 쉽지만 물리 delete는 updated_at이 없어 포착할 수 없고(soft delete 컬럼을 따로 둬야 함), 폴링 주기만큼 지연이 생긴다.
- 판별 원리: 원천 DB 부하 민감도가 높고 delete·순서 보장이 필요하면 로그 기반, 원천 DB가 로그 접근이 어려운 구형 시스템이면 트리거 기반, 지연에 관대하고 구현 단순성이 우선이면 타임스탬프 폴링을 선택한다.

### 변경률로 I/O 절감을 수치로 확인하기
- 주문 테이블이 10억 건이고 하루 변경(신규+수정) 건수가 200만 건이면 변경률은 200만÷10억=0.2%다. 전체 스캔 배치는 10억 건을 매번 읽어야 하지만 CDC는 200만 건만 읽으면 되므로 읽기 대상이 99.8% 줄어든다.
- 이 200만 건을 Kafka 파티션 12개로 나누면 파티션당 약 16.7만 건이 되어 병렬로 분산 처리할 수 있고, 커넥터 랙(lag)을 60초 이하로 유지하기 쉬워진다.

### 로그 기반 CDC의 실제 동작 순서 — 워크드 예제
1. 애플리케이션이 `UPDATE orders SET status='SHIPPED' WHERE order_id=1001`을 커밋한다. MySQL은 이 변경을 binlog에 순서대로 기록한다.
2. Debezium 커넥터가 마지막으로 읽은 offset(예: binlog position 48213) 이후를 계속 tailing한다. 새 레코드를 발견하면 before={status: 'PAID'}, after={status: 'SHIPPED'}, op='u'(update)로 이벤트를 구성한다.
3. 이 이벤트를 Kafka 토픽(예: `orders.public.orders`)에 order_id를 파티션 키로 발행한다 — 같은 order_id의 변경은 항상 같은 파티션에 들어가 순서가 보장된다.
4. 대상 DW의 sink connector가 이 이벤트를 읽어 `MERGE INTO dw_orders USING (order_id=1001) WHEN MATCHED THEN UPDATE SET status='SHIPPED'`처럼 PK 기반으로 반영한다. 같은 이벤트가 재시도로 두 번 와도 MERGE는 결과적으로 한 번 반영한 것과 동일하다(멱등).
5. delete는 톰스톤 이벤트(op='d', after=null)로 와서 대상 테이블에서 해당 PK 행을 삭제하거나 soft delete 플래그를 세운다.

### 흔한 오해 — CDC ≠ 단순 복제
- CDC를 단순 DB 복제와 같다고 오해하기 쉽지만, 복제는 원천과 대상이 같은 스키마·엔진임을 전제하는 경우가 많은 반면 CDC는 이벤트를 Kafka 같은 브로커에 태워 스키마가 다른 여러 대상(DW, 검색엔진, 캐시)에 동시에 분산할 수 있다.
- 스키마가 바뀌면(컬럼 추가·타입 변경) 이미 발행 중인 이벤트의 포맷이 바뀌므로, Schema Registry로 호환성을 사전 검증하지 않으면 다운스트림 컨슈머가 파싱에 실패한다.
- 로그 보관 기간을 넘겨 커넥터가 오래 멈추면(예: 72시간 이상 장애) 그 사이 로그가 삭제되어 변경 이벤트를 영영 복구할 수 없다 — 이 경우 원천 테이블을 다시 풀 스냅샷해야 한다.

## 연결 개념
- 이벤트 스트리밍(Kafka) — CDC 이벤트를 전달하는 브로커 통로
- 데이터 웨어하우스(142) — CDC 변경분을 차원·팩트 테이블에 MERGE로 적재하는 대상
- 실시간 스트리밍 플랫폼(140) — CDC를 소스로 삼는 상위 아키텍처
- Exactly-Once Semantics(139) — CDC의 멱등 반영이 지향하는 정합성 목표

# 📝 【답안용】 시험 답안 템플릿

> 목적: 시험장에서 25분에 그대로 쓰는 답안 양식. 작성방식(추상표현 금지·수치·도식·문제유형 전환)을 엄격히 지킨다.
> 핵심: CDC는 도구명이 아니라 변경 식별, 순서 보장, 장애 재처리, 대상 반영 방식을 함께 설계하는 데이터 동기화 패턴이다.

## 핵심 인사이트 (3줄 요약)

> 1. **본질**: CDC는 원천 DB 변경 로그를 이벤트화해 전체 복사 없이 대상 저장소에 반영하는 기법이다.
> 2. **가치**: 배치 주기 24시간을 분 단위로 낮추고, 전체 스캔 I/O를 변경 행 비율만큼 축소한다.
> 3. **판단 포인트**: 로그 기반·트리거 기반·타임스탬프 기반 중 원천 DB 부하, 순서 보장, 삭제 처리 요구에 맞춰 선택한다.

## 출제 의도 및 답안 포인트

| 출제 의도 | 반드시 짚을 핵심 | 감점 회피 포인트 |

| 정합성 통제 역량 확인 | 커밋 순서, exactly-once 유사 처리, 재처리, 스키마 진화 | 중복 이벤트와 삭제 이벤트 처리 누락 |
| 운영 리스크 인식 | 로그 보관기간, connector lag, dead letter queue | 원천 DB 부하와 권한 범위 미기재 |

> 요약: CDC 답안은 변경 추출 방식보다 순서·중복·장애 재처리 기준을 제시해야 채점 포인트를 충족한다.

## Ⅰ. 개요 및 필요성

- 개요: CDC는 DB 변경분을 이벤트로 캡처하는 동기화 기법이다.
- 배경: 전체 테이블 재적재는 대용량 환경에서 I/O와 배치 윈도우를 증가시킨다.
- 필요성: 변경 로그 기반으로 DW, 레이크, 검색 색인에 분 단위 반영을 제공해 운영계와 분석계 간 시차를 줄인다.

---

## Ⅱ. 구조 및 구성요소

```text
Source DB -> Change Log -> CDC Connector -> Event Broker -> Sink Connector -> Target Store
                      +-> Schema Registry
                      +-> Monitoring / DLQ
```

| 구성요소 | 역할 | 특이사항 |
|:---|:---|:---|
| Change Log | 커밋된 변경 순서 기록 | binlog, WAL, redo log |
| CDC Connector | 로그 위치와 변경 이벤트 추출 | Debezium, GoldenGate, DMS |
| Event Broker | 이벤트 버퍼링과 파티션 분산 | Kafka offset, retention |
| Sink Connector | 대상 저장소에 insert/update/delete 반영 | idempotent key, merge |

> 요약: CDC 구조는 원천 로그를 이벤트 브로커로 옮긴 뒤 대상별 반영 규칙으로 정합성을 맞추는 파이프라인이다.

---

## Ⅲ. 동작원리 및 흐름도

```text
트랜잭션 커밋 -> 로그 기록 -> offset 읽기 -> 이벤트 변환
-> 토픽 발행 -> 대상 merge/delete -> lag / error 측정
```

| 단계 | 처리 내용 | 검증 기준 |
|:---:|:---|:---|
| 1 | 원천 DB 트랜잭션 커밋 후 로그 생성 | commit timestamp, LSN/binlog position |
| 2 | CDC 커넥터가 offset 기준 변경분 읽기 | lag 60초 이하, offset checkpoint |
| 3 | key, before/after, op code로 이벤트 구성 | insert/update/delete 구분 |
| 4 | 대상 테이블에 merge 또는 delete 반영 | 중복 처리 0건, PK 충돌 검출 |

> 요약: CDC는 로그 위치를 기준으로 변경 이벤트를 읽고, 대상 저장소에서 키 기반 멱등 반영으로 정합성을 통제한다.

## Ⅳ. 특징

| 구분 | 기존 배치 ETL | CDC | 수치·판단 포인트 |
|:---|:---|:---|:---|
| 처리 단위 | 전체 또는 파티션 단위 재적재 | 변경 행 단위 이벤트 | 변경률 1%면 읽기 대상 99% 감소 |
| 지연 | 일·시간 단위 | 초·분 단위 | connector lag 60초 이하 목표 |
| 삭제 처리 | 누락 가능 | delete 이벤트 명시 | tombstone, soft delete 구분 |
| 운영 부담 | 배치 실패 시 재실행 단순 | offset, 스키마, DLQ 관리 필요 | 로그 보관기간 24~72시간 확보 |

> 요약: CDC는 데이터 반영 지연을 줄이지만 offset, 삭제, 스키마 변경 통제가 필수인 운영형 데이터 통합 방식이다.

## Ⅴ. 심화 비교 및 적용 판단

| 비교 축 | 기존/대안 | CDC | 선택 기준 |
|:---|:---|:---|:---|
| 구조 | 야간 ETL, API polling | 로그 기반 이벤트 추출 | 변경 반영 목표 5분 이하 |
| 비용/성능 | 전체 스캔 I/O 증가 | 변경률만큼 읽기 감소 | 일 변경률 10% 이하일 때 우선 검토 |
| 운영/위험 | 재실행 단순 | offset 손실, 로그 만료 | 로그 보관기간과 재처리 절차 확보 |

> 요약: CDC는 준실시간성과 변경률이 낮은 대용량 테이블에서 적합하며, 로그 보존과 재처리 체계가 선택 전제다.

| 리스크 | 원인 | 대응 방안 | 확인 지표 |
|:---|:---|:---|:---|
| 이벤트 중복 | 커넥터 재시작, offset 재처리 | PK 기반 upsert, idempotent sink | 중복 반영 0건 |
| 데이터 누락 | 로그 만료, 권한 부족 | retention 72시간, 권한 점검 | LSN 연속성, gap count |
| 스키마 불일치 | 컬럼 추가·타입 변경 | Schema Registry, 호환성 검사 | schema error rate 0.1% 이하 |

> 요약: CDC 리스크는 중복보다 누락이 치명적이며, offset 연속성과 스키마 호환성 지표로 관리한다.

| 점검 항목 | 목표 기준 | 측정 방법 |
|:---|:---|:---|
| 지연 | end-to-end lag 60초 이하 | Kafka lag, sink latency |
| 정합성 | 원천·대상 row count 오차 0.01% 이하 | checksum, reconciliation job |
| 복구 | 장애 후 재처리 RTO 30분 이하 | checkpoint 복원 테스트 |

> 요약: CDC 운영 성공 여부는 지연, 정합성, 복구 시간을 동시에 측정해야 판단 가능하다.

## Ⅵ. 실무 적용 및 결론

**적용 방안 3개 (필수 — 단계별 또는 항목별):**
1. MySQL binlog/PostgreSQL WAL 기반 Debezium 커넥터를 적용하고 Kafka retention 72시간, 파티션 12개 기준으로 lag 60초 이하 유지
2. 대상 DW·레이크 테이블은 PK 기반 MERGE, delete tombstone, 재처리용 DLQ를 설계해 중복·삭제 이벤트 처리
3. 스키마 변경은 Schema Registry backward compatibility와 일 1회 reconciliation job으로 원천·대상 row count 검증

**결론 (2줄):**
- 기술사 판단: 변경 반영 목표가 5분 이하이고 원천 DB 로그 접근이 가능하면 CDC, 일 단위 분석이면 배치 ETL 선택
- 향후 방향: CDC는 레이크하우스의 MERGE, 스트리밍 처리, 이벤트 기반 MSA와 결합해 운영·분석 데이터 경계를 줄이는 방향으로 발전
