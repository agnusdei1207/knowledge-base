## 미리 알고가기

- HPA는 관측 메트릭과 목표값을 비교해 Deployment 같은 워크로드의 Pod 복제본 수를 조정함
- VPA는 실제 자원 사용량을 분석해 Pod의 CPU·메모리 요청값과 제한값을 추천하거나 갱신함
- 자원 요청값은 스케줄러가 노드 배치 가능성을 판단하고 HPA가 CPU 사용률을 계산할 때 사용함
- HPA는 현재 부하가 목표 수준보다 높으면 필요한 처리 용량만큼 복제본을 늘리고 낮으면 줄이는 방식으로 동작함
- VPA 갱신 방식에 따라 Pod 재생성이나 인플레이스 자원 조정이 발생할 수 있음
- HPA와 VPA가 같은 CPU·메모리 신호를 동시에 바꾸면 제어 루프가 서로 영향을 줄 수 있음
- OOM(Out of Memory)은 컨테이너가 메모리 한계를 넘어 프로세스가 종료되는 상태임

## 작성 근거(검토용)

- HPA와 VPA는 메트릭 이름보다 조정 대상이 복제본인지 자원 요청값인지가 핵심이므로 이를 중심에 둠
- 조정 기준·실행 영향·적합 조건의 정확히 3개 축으로 비교하고 각 제어 흐름으로 연결함
- 제목부터 결론까지 5회 전수 검수하여 수평·수직 조정의 대상과 결과를 구분함

## Ⅰ. 개요

- **정의/개념**: HPA·VPA는 워크로드 메트릭을 목표값과 비교해 Pod 수나 CPU·메모리 요청값을 자동 조정하는 쿠버네티스 제어기임
- **배경/필요성**: 부하 변화에 맞춰 처리 용량과 자원 예약량을 조정하기 위해 메트릭·목표값·조정 범위가 필요함

### 쉽게 이해하기 (학습용)
- HPA는 일꾼 수를, VPA는 일꾼 한 명에게 줄 장비 크기를 조정하는 제어 방식임

## Ⅱ. 특징

- HPA는 주기적 제어 루프에서 메트릭별 필요 복제본을 계산하고 가장 큰 값을 선택함
- VPA는 사용 이력과 OOM 이벤트를 분석해 자원 요청값을 추천하거나 워크로드에 반영함
- 두 방식 모두 최소·최대 범위와 조정 속도를 제한해 반복 증감과 자원 고갈을 통제함
- Pod 확장만으로 노드 용량이 생기지 않으므로 스케줄 가능한 노드 자원을 함께 확인해야 함

### 쉽게 이해하기 (학습용)
- Pod 수나 크기를 늘려도 실제 노드에 빈 자원이 없으면 확장이 완료되지 않음

## Ⅲ. 종류 및 비교

| 판단 기준 | HPA | VPA |
|:---|:---|:---|
| 조정 기준 | 현재 부하와 목표 수준으로 Pod 복제본 수를 조정 | 사용 이력·OOM·정책 범위로 CPU·메모리 요청값을 조정 |
| 실행 영향 | 새 Pod가 준비될 때까지 확장 용량이 반영되지 않음 | 갱신 방식에 따라 Pod 재생성이 발생할 수 있음 |
| 적합 조건 | 병렬 처리 가능한 무상태·분산 워크로드 | 복제 수보다 Pod당 자원 크기 산정이 필요한 워크로드 |

> 요약: HPA는 복제본 수를, VPA는 Pod당 자원 요청값을 조정함.

### 쉽게 이해하기 (학습용)
- 같은 부하 문제라도 처리 인스턴스를 늘릴지 인스턴스 크기를 바꿀지에 따라 선택이 달라짐

## Ⅳ. 구성요소 및 구조

| 구성요소 | 역할 |
|:---|:---|
| 메트릭 수집 계층 | Pod·애플리케이션의 현재 사용량과 사용자 정의 지표를 제공함 |
| HPA 객체·제어기 | 목표값과 현재값으로 필요 복제본 수를 계산함 |
| VPA 객체·추천기 | 사용 이력과 정책 범위로 자원 요청 추천값을 계산함 |
| VPA 갱신기·승인 제어기 | 갱신 대상 Pod를 정하고 새 Pod에 요청값을 적용함 |
| 워크로드 제어기 | Deployment·StatefulSet의 복제본과 Pod 템플릿을 관리함 |
| 스케줄러·노드 | 조정된 Pod 수와 요청값을 수용할 노드를 선택함 |

```text
메트릭 -> HPA -> scale -> 워크로드 제어기 -> Pod 수
사용 이력 -> VPA -> 자원 요청값 -> 승인 제어기 -> 스케줄러
```

> 요약: HPA는 scale을 갱신하고 VPA는 스케줄링 전 Pod 자원 요청값을 갱신함.

### 쉽게 이해하기 (학습용)
- 메트릭 수집 뒤 HPA는 개수 정보를, VPA는 자원 설정을 바꾸고 스케줄러가 실제 배치를 수행함

## Ⅴ. 제어 흐름

```text
HPA: 메트릭 수집 -> 목표값 비교 -> 필요 복제본 계산 -> scale 갱신 -> 새 메트릭 확인
VPA: 사용 이력 수집 -> 추천값 계산 -> 갱신 대상 판정 -> 요청값 적용 -> 사용량 재평가
```

1. **HPA 흐름**: 메트릭별 복제본 수를 계산하고 상한·하한·조정 정책을 적용함
2. **HPA 반영**: scale 하위 자원을 갱신하고 새 Pod의 준비 상태를 다음 주기에 확인함
3. **VPA 흐름**: 사용 분포와 OOM 신호로 최소·최대 범위 안의 추천값을 계산함
4. **VPA 반영**: 갱신 모드에 따라 추천만 제공하거나 Pod 자원 설정을 변경함

> 요약: 두 제어기는 관측값을 목표 범위와 비교하지만 서로 다른 워크로드 속성을 갱신함.

### 쉽게 이해하기 (학습용)
- 관측하고 판단하고 조정한 뒤 새 상태를 다시 보는 같은 순환을 서로 다른 대상에 적용함

## Ⅵ. 실무 사례

1. 무상태 API는 요청률 기반 HPA를 적용하고 목표값 편차·스케일 완료시간을 확인함
2. JVM Pod는 VPA 추천 모드로 크기를 산정하고 권고값 편차·OOM 건수를 확인함

### 쉽게 이해하기 (학습용)
- 요청량이 변하는 API는 HPA, Pod 크기가 불명확한 JVM은 VPA 추천으로 시작할 수 있음

## Ⅶ. 결론

- 오토 스케일링은 조정 대상이 복제본 수인지 Pod 자원 요청값인지에 따라 HPA·VPA를 선택해야 함

### 쉽게 이해하기 (학습용)
- 자동 확장이라는 이름보다 무엇을 바꾸며 실제 노드가 그 변화를 수용할 수 있는지가 중요함
