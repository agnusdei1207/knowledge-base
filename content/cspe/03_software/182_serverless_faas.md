# 📖 【암기용】 개념 완전 이해

## 한눈에
- **개요**: 클라우드 제공자가 서버의 인프라 할당과 확장을 동적으로 관리하여, 개발자는 코드 작성에만 집중할 수 있는 클라우드 실행 모델이다.
- **왜 필요한가**: 트래픽 예측이 어려운 서비스에서 서버를 항상 켜두면 유휴 리소스 낭비가 심하다. 호출될 때만 실행하고 사용한 시간(ms)만큼만 비용을 지불하여 효율성을 극대화한다.
- **핵심 직관**: 수도꼭지를 틀었을 때만 물(컴퓨팅 파워)이 나오고 쓴 만큼만 수도 요금을 내는 방식이다. 배관(서버) 관리는 수도 공사(CSP)가 전담한다.

## 핵심 용어 정리

| 용어/표기 | 의미 | 비유·예 |
|:---|:---|:---|
| FaaS (Function as a Service) | 애플리케이션을 함수 단위로 쪼개어 배포하고 실행하는 서버리스의 핵심 모델 | 자판기의 개별 버튼 |
| Cold Start | 함수가 처음 호출될 때 컨테이너를 구동하고 런타임을 초기화하느라 발생하는 지연 시간 | 차가운 엔진 예열 시간 |
| Scale to Zero | 트래픽이 없을 때 인스턴스 수를 0으로 줄여 비용을 청구하지 않는 메커니즘 | 손님 없을 때 가게 불 끄기 |

## 깊이 이해
- **배경·문제의식**: 기존 IaaS나 CaaS 환경에서는 개발팀이 운영체제 패치, 오토스케일링 정책, 서버 프로비저닝을 직접 관리해야 했다. 이는 비즈니스 로직 개발에 집중해야 할 시간을 인프라 관리에 빼앗기는 원인이 되었다.
- **작동 원리**: 이벤트(HTTP 요청, DB 변경, 메시지 큐 등)가 발생하면 클라우드 플랫폼이 즉각적으로 격리된 실행 환경(MicroVM 또는 컨테이너)을 생성하여 함수 실행을 처리한다. 실행이 완료되면 인스턴스를 회수하거나 잠시 유지(Warm)한다.
- **비유**: 필요할 때만 호출해서 일회성으로 업무를 처리하고 바로 퇴근하는 초단기 프리랜서를 고용하는 것과 같다. 자리가 필요 없고, 일한 초 단위로만 임금을 지불한다.
- **구체 예시**: AWS Lambda를 통해 썸네일 생성 함수를 배포하면, S3에 이미지가 업로드(이벤트)될 때만 함수가 실행되어 썸네일을 만들고 종료된다. 100만 번 호출에 단돈 몇 달러 수준으로 처리된다.
- **흔한 오해·주의점**: 서버리스라고 서버가 없는 것이 아니라 "서버 관리가 없는" 것이다. 또한 항상 저렴한 것은 아니다. 24시간 내내 일정한 고부하 트래픽이 발생한다면 차라리 고정 인스턴스(VM/컨테이너)를 띄워두는 것이 비용면에서 훨씬 유리하다.

## 연결 개념
- **이벤트 기반 아키텍처(EDA)**: 특정 이벤트 발생 시 컴포넌트 간 비동기적으로 메시지를 주고받는 구조
- **AWS Lambda / Knative**: 대표적인 퍼블릭 FaaS와 쿠버네티스 환경의 오픈소스 서버리스 플랫폼
- **콜드 스타트 완화 기법**: Provisioned Concurrency, AWS SnapStart 등 초기화 지연 극복 기술

# 📝 【답안용】 시험 답안 템플릿

## 핵심 인사이트 (3줄 요약)

> 1. **본질**: 서버리스 컴퓨팅은 CSP가 인프라 관리를 전담하고, 이벤트를 트리거로 함수 단위 코드를 실행하는(FaaS) 추상화 모델이다.
> 2. **가치**: 0에서 무한대(Zero-to-N) 스케일링과 밀리초 단위 과금을 통해 예측 불가능한 워크로드의 비용과 운영 효율을 극대화한다.
> 3. **판단 포인트**: 콜드 스타트로 인한 지연(Latency), 벤더 종속성(Lock-in), 무상태성(Stateless) 강제라는 트레이드오프를 고려해 워크로드를 선별해야 한다.

## 출제 의도 및 답안 포인트

| 출제 의도 | 반드시 짚을 핵심 | 감점 회피 포인트 |
|:---|:---|:---|
| 클라우드 진화 모델과 서버리스 아키텍처 원리 이해 | FaaS 구조, Event-Driven, Scale to Zero | "서버가 존재하지 않음" 식의 사실 오류 |
| 서버리스 도입의 기술적 트레이드오프 파악 | 콜드 스타트 지연, 무상태성 한계, 벤더 종속성 | 무조건 성능이 좋고 비용이 저렴하다는 단정 |
| 엔터프라이즈 환경 적용을 위한 한계 극복 방안 | Provisioned Concurrency, 헥사고날 아키텍처 | 단순 장점 나열에 그쳐 실무 해결책 누락 |

> 요약: 서버리스의 민첩성/비용 효율성을 설명하되, 콜드 스타트 지연과 상태 관리 제약 등 성능 리스크를 통제하는 아키텍처 방안을 제시해야 한다.

## Ⅰ. 개요 및 필요성

- 개요: 서버리스 컴퓨팅은 인프라 프로비저닝 없이 코드를 이벤트 기반으로 실행하고 쓴 만큼 과금하는 클라우드 실행 모델임
- 배경: 서비스 규모 변동이 심한 환경에서 유휴 서버 유지 비용 증가 및 인프라 운영 복잡도 심화
- 필요성: 개발자는 비즈니스 로직에만 집중(NoOps)하고, 트래픽 폭증 시 즉각적인 Auto-Scaling을 통해 서비스 가용성을 보장해야 함

---

## Ⅱ. 구조 및 구성요소

```text
Event Source -> Event Router/Bus -> FaaS 런타임 -> Backend Services
(HTTP, DB 등)       (트리거)         (코드 실행)      (상태 저장)
```

| 구성요소 | 역할 | 특이사항 |
|:---|:---|:---|
| Event Source | 함수 호출을 트리거하는 외부 자극 발생 | S3 업로드, Kafka 메시지, API Gateway |
| Event Router | 이벤트를 캡처하여 매핑된 함수로 라우팅 | 비동기 호출 시 재시도 처리 로직 포함 |
| FaaS Runtime | 개발자가 작성한 비즈니스 로직 코드 실행 | Node.js, Python, Java 등 격리 컨테이너 실행 |
| Backend/State | 함수의 무상태성 보완을 위한 데이터 영속화 | DynamoDB, S3, ElastiCache 활용 |

> 요약: 상태가 없는(Stateless) 함수(FaaS)가 외부 이벤트를 받아 실행되고, 결과는 외부 백엔드 스토리지에 영속화하는 구조를 갖는다.

---

## Ⅲ. 동작원리 및 흐름도

```text
이벤트 발생 -> 인스턴스 확인 -> (없으면) 콜드 스타트(환경 구성) -> 함수 실행 -> 결과 반환 및 유휴 대기
```

- 1단계 [이벤트 감지]: API Gateway나 메시지 큐 등에서 트리거 조건이 충족되어 함수 호출 요청 발생
- 2단계 [인스턴스 할당]: Warm 컨테이너가 있으면 재사용, 없으면 새 컨테이너 생성 및 런타임 초기화(Cold Start)
- 3단계 [코드 실행]: 전달된 이벤트 페이로드를 입력으로 비즈니스 로직 실행 및 상태 외부 저장
- 4단계 [자원 회수]: 실행 종료 후 밀리초 단위 요금 산정 및 일정 시간(예: 15분) 미호출 시 인스턴스 파기(Scale-to-Zero)

> 요약: 트래픽에 반응하여 컨테이너를 동적 할당하고, 유휴 상태 시 즉각 회수하여 리소스 점유와 비용 발생을 차단한다.

---

## Ⅳ. 특징
- [Zero-to-N 확장]: 트래픽 급증 시 CSP 인프라 풀을 활용해 밀리초 단위로 수만 개 인스턴스 병렬 확장 가능
- [마이크로 과금]: 실행 시간(ms)과 메모리 할당량 비례 과금으로 유휴 리소스 비용 제로화 구현
- [무상태성 강제]: 인스턴스가 휘발성이므로 인메모리 세션 유지가 불가하여 상태 관리는 외부 DB에 의존해야 함
- [벤더 종속성]: AWS Lambda, Azure Functions 등 특정 벤더의 이벤트 트리거 구조와 SDK에 강하게 결합됨

> 요약: 운영 효율과 확장성이 극대화되나, 벤더 종속성과 애플리케이션 구조 제한(무상태성)이라는 설계 한계가 동반된다.

## Ⅴ. 심화 비교 및 적용 판단

| 비교 축 | IaaS/VM | CaaS (Kubernetes) | FaaS (Serverless) | 선택 기준 |
|:---|:---|:---|:---|:---|
| 스케일링 단위 | 서버/VM 단위 (수 분) | Pod 단위 (수 초) | 함수 단위 (밀리초) | 트래픽 변동폭 및 반응 속도 |
| 운영 복잡도 | OS 구성, 패치 (높음) | 노드/클러스터 관리 (중간) | 인프라 관리 불필요 (낮음) | 인프라 전담 조직 유무 |
| 상태 관리 | Stateful 유연 | Stateful/Stateless 혼용 | Stateless 강제 | 트랜잭션 연속성 요구도 |

> 요약: 지속적인 고부하 서비스는 CaaS가 유리하며, 간헐적 트래픽 및 이벤트 기반 비동기 처리는 FaaS가 압도적으로 효율적이다.

**리스크·대응 (기본은 불릿):**
- [Cold Start 지연]: 초기화 오버헤드로 인한 p95 지연 증가 → 사전 프로비저닝(Provisioned Concurrency) 및 JVM SnapStart 활용 (지표: 함수 구동 초기화 지연 시간)
- [벤더 종속성(Lock-in)]: 특정 클라우드 서비스 강한 결합 → 헥사고날 아키텍처로 비즈니스 로직 분리, Knative 기반 자체 구축 (지표: 클라우드 종속 코드 비율)

**도입 후 점검 지표 (기본은 불릿):**
- 성능/안정성: 콜드 스타트 발생 비율 5% 미만 유지 — APM 연동 지연 트레이싱
- 비용/효율: 기존 IaaS 대비 유휴 리소스 절감율 40% 이상 달성 — FinOps 대시보드 분석

## Ⅵ. 실무 적용 및 결론

**적용 방안 3개 (필수 — 단계별 또는 항목별):**
1. [배치 워크로드 전환]: 주기적인 로그 압축, 썸네일 생성 등 비동기 백그라운드 작업을 FaaS로 우선 전환하여 비용 절감
2. [API 성능 최적화]: 사용자 요청을 처리하는 동기식 API는 콜드 스타트 방지 정책(Provisioned)을 적용하여 p99 200ms 응답성 보장
3. [벤더 중립성 확보]: 오픈소스 기반 서버리스 프레임워크(Serverless Framework, Knative)를 도입하여 멀티 클라우드 이식성 확보

**결론 (2줄):**
- 기술사 판단: 서버리스는 만능이 아니며, 예측 가능한 고부하 워크로드에는 부적합하므로 이벤트 주도 비동기 처리에 선별 적용해야 함
- 향후 방향: WASM(WebAssembly)을 런타임으로 채택하여 콜드 스타트를 마이크로초 단위로 줄이는 초경량 서버리스 엣지 환경으로 발전 중임
