# 📖 【암기용】 개념 완전 이해

> 목적: 서버리스 컴퓨팅과 FaaS를 처음 보는 사람도 완벽히 이해하게 만든다. 시험 답안 양식이 아니라, 이해를 위한 친절한 설명이다.

## 한눈에
- **개요**: Serverless FaaS(Function as a Service)는 서버 프로비저닝·용량 산정·패치를 클라우드가 대신하고, 개발자는 **이벤트에 반응하는 함수 단위 코드**만 배포하는 **이벤트 기반 실행 모델**이다.
- **왜 필요한가**: 요청이 불규칙하거나 짧고 간헐적인 업무(이미지 처리, 웹훅, 배치 알림)를 VM·컨테이너로 상시 운영하면 유휴 시간에도 비용이 들고 용량을 미리 추정해야 한다. FaaS는 호출된 순간에만 자원을 쓰고 그만큼만 과금한다.
- **핵심 직관**: 주방 전체를 월세로 빌리는 대신, 주문이 들어올 때만 조리대와 요리사를 초 단위로 빌리는 구조다.

## 핵심 용어 정리 (내부에 등장하는 것들)

| 용어 | 의미 | 비유 |
|:---|:---|:---|
| 이벤트 기반 실행(Event-driven Execution) | 특정 이벤트가 발생해야 코드가 실행되는 모델 — FaaS가 속하는 상위 실행 패러다임 | 벨이 울려야 움직이는 당직 근무 |
| FaaS(Function as a Service) | 함수 단위 코드를 이벤트 트리거로 실행하는 서버리스의 핵심 축 | 초단위로 부르는 임시 요리사 |
| BaaS(Backend as a Service) | 인증·DB·스토리지 같은 백엔드 기능 자체를 관리형 서비스로 제공(FaaS와 함께 서버리스를 구성하는 다른 축) | 완제품 부품을 그대로 가져다 쓰는 것 |
| 콜드 스타트(Cold Start) | 일정 시간 호출이 없어 인스턴스가 회수된 뒤, 첫 호출이 새 런타임을 초기화하는 데 걸리는 추가 지연 | 문 닫은 가게를 다시 여는 데 걸리는 시간 |
| 웜 스타트(Warm Start) | 이미 초기화된 인스턴스가 재사용되어 초기화 지연 없이 바로 실행되는 경우 | 이미 불 켜진 가게에 들어가는 것 |
| 동시성(Concurrency)/Throttling | 특정 시점에 동시에 실행 중인 함수 인스턴스 수 한도와, 이를 넘으면 요청을 지연·거부하는 것 | 매장 동시 입장 인원 제한 |
| GB-second | 함수가 사용한 메모리(GB)와 실행 시간(초)을 곱한 과금 단위 | 대여한 조리대 크기 × 사용 시간 |
| 상태 외부화(Externalized State) | 함수 인스턴스가 재활용·소멸될 수 있어 로컬 메모리 대신 DB·캐시·오브젝트 스토리지에 상태를 저장하는 원칙 | 개인 사물함 대신 공용 창고에 물건 보관 |
| 벤더 종속(Vendor Lock-in) | 특정 CSP의 이벤트 포맷·IAM·SDK에 강하게 결합되어 다른 클라우드로 이전이 어려워지는 문제 | 한 업체 전용 부품으로만 조립된 기계 |

## 깊이 이해

### VM/컨테이너와 무엇이 다른가 (배경)
- VM은 OS 전체를, 컨테이너(K8s Deployment)는 애플리케이션 프로세스를 사용자가 계속 띄워둔다 — 트래픽이 0이어도 최소 replica는 상시 실행되어 비용이 발생한다.
- FaaS는 "이벤트가 없으면 실행 인스턴스가 아예 없다"를 기본 전제로 한다. 이벤트가 오면 그제서야 플랫폼이 샌드박스(예: AWS Lambda는 Firecracker microVM)를 할당해 코드를 실행하고, 실행이 끝나면 일정 시간 뒤 인스턴스를 회수한다.

### 요청 하나의 생애주기를 수치로 이해
- 이미지 업로드 이벤트(S3 PutObject) 발생 -> Event Source가 함수 트리거 -> 콜드 스타트라면 512MB 메모리의 함수 런타임을 초기화(수백ms~1~2초, 언어·패키지 크기에 따라 다름) -> 코드 실행(예: 썸네일 생성 3초) -> 결과를 S3에 저장 -> 로그/메트릭 기록.
- 과금 예: 512MB(=0.5GB) 함수가 3초 걸렸다면 0.5GB × 3s = 1.5 GB-second 소비. 100만 번 호출에 매번 평균 1.5 GB-second라면 총 150만 GB-second에 호출 100만 건에 대한 고정 요청 과금이 더해진다 — "쓴 만큼만" 과금되는 구조를 수치로 확인할 수 있다.

### 콜드 스타트가 왜 생기고 어떻게 줄이는가
- 일정 시간(대략 5~15분, 플랫폼·설정에 따라 다름) 호출이 없으면 플랫폼은 idle 인스턴스를 회수해 자원을 재활용한다. 다음 호출이 오면 런타임 초기화(컨테이너 기동, 언어 런타임 로딩, 코드 로딩)부터 다시 해야 하는데 이 추가 지연이 콜드 스타트다.
- JVM 기반 함수는 초기화가 수 초까지 걸릴 수 있고, Node.js/Python 같은 경량 런타임은 수백ms 수준으로 상대적으로 짧다. 운영 목표는 흔히 "cold start p95 500ms 이하"처럼 잡는다.
- 완화 방법: provisioned concurrency(항상 웜 상태로 인스턴스를 미리 띄워둠, 대신 상시 비용 발생), 경량 런타임 선택, 패키지 크기 최소화, VPC 연결 최소화(VPC ENI 초기화도 콜드 스타트를 늘리는 요인).

### 동시성 한도와 DB 연결 폭증을 수치로 이해
- 함수는 요청이 몰리면 순간적으로 수백~수천 개 인스턴스가 동시에 실행될 수 있다. 각 인스턴스가 DB에 직접 커넥션을 맺으면, 동시 실행 500개 = DB 커넥션 500개 요구 -> 관리형 DB의 기본 max_connections(수백 개 수준)를 순식간에 초과해 DB 자체가 응답 불가에 빠질 수 있다.
- 그래서 커넥션 풀러(RDS Proxy 등)를 앞에 두어 "함수 동시성 수"와 "실제 DB 커넥션 수"를 분리한다 — 다수의 짧은 함수 커넥션 요청을 소수의 실제 DB 커넥션으로 풀링해 재사용한다.
- concurrency quota(계정/함수별 동시 실행 상한, 예: 계정 기본 1,000)를 넘는 요청은 throttling(오류 반환)되거나 큐에 쌓인다 — 이 한도를 모니터링하지 않으면 트래픽 급증 시 요청이 조용히 실패한다.

### stateless 원칙과 상태 외부화
- 함수 인스턴스는 언제든 재활용·소멸될 수 있어, 로컬 메모리나 디스크에 저장한 상태는 다음 호출에서 그대로 있으리라 보장할 수 없다(웜 재사용 시 우연히 남아있을 순 있지만 설계로 의존하면 안 된다).
- 그래서 세션, 파일, 캐시는 반드시 외부 저장소(관리형 DB, Redis, Object Storage 등)에 둔다 — "함수는 계산만, 상태는 바깥"이 FaaS 아키텍처의 원칙이다.

### 비유와 흔한 오해
- **비유**: 상주 요리사(VM/컨테이너)를 24시간 고용하는 대신, 주문벨이 울릴 때마다 대기 중인 요리사를 호출해 그 요리 하나만 시키고 보내는 구조다 — 인건비는 실제 요리 시간만큼만 나가지만, 처음 호출된 요리사가 앞치마를 두르는 준비 시간(콜드 스타트)이 있고, 한 번에 너무 많은 주문이 몰리면 대기줄(throttling)이 생긴다.
- **오해 1**: "서버리스는 서버가 없다" — 틀렸다. 서버는 여전히 존재하고 실행되지만, 그 운영 책임(패치, 용량, 오토스케일)이 사용자에서 CSP로 이동했을 뿐이다.
- **오해 2**: "서버리스는 항상 더 싸다" — 틀렸다. 상시 고부하(idle이 거의 없는) 워크로드는 오히려 VM/컨테이너 상시 실행이 GB-second 누적 과금보다 저렴할 수 있다. FaaS는 "유휴 시간 비중이 큰 변동성 워크로드"에서 이득이 크다.

## 연결 개념
- 이벤트 기반 아키텍처 - Queue, Pub/Sub, Object Event로 함수를 호출하는 트리거 계층
- 오토스케일링 - concurrency와 throttling으로 함수 동시 실행을 제어하는 메커니즘
- 마이크로서비스 - 기능 단위로 쪼개 배포하고 API·이벤트로 조합하는 상위 설계 사상

## 핵심 인사이트 (3줄 요약)

> 1. **본질**: Serverless FaaS는 이벤트 발생 시 함수 단위 코드를 실행하고 인프라 프로비저닝, 패치, 확장을 플랫폼이 담당하는 모델임.
> 2. **가치**: 호출 수와 실행 시간 기반 과금, 자동 확장, 운영 자동화로 변동성 큰 워크로드의 자원 우측정 문제를 줄임.
> 3. **판단 포인트**: 콜드 스타트 p95, 동시 실행 한도, 실행 시간 제한, 상태 외부화, 관측성, 벤더 종속을 기준으로 적용해야 함.

## Ⅰ. 개요 및 필요성

- 개요: 이벤트 기반 함수 실행 모델
- 배경: 인프라 운영 책임을 플랫폼에 맡기고 개발자는 함수 코드, 트리거, 권한, 관측 지표를 지정한다.
- 필요성: 요청 변동이 크고 짧은 작업에서 초 단위 과금과 자동 확장으로 서버 상시 운영 부담을 줄인다.

---

## Ⅱ. 구조 및 구성요소

```text
Client/Event Source -> API Gateway/Queue/Object Event -> Function Runtime -> Managed Service
  / State: DB/Cache/Object Storage
  / Control: IAM/Quota/Observability
```

| 구성요소 | 역할 | 특이사항 |
|:---|:---|:---|
| Event Source | 함수 호출 트리거 제공 | HTTP, Queue, S3, Cron |
| Function Runtime | 코드 실행 샌드박스 | Node.js, Python, Java |
| Managed State | 상태 저장과 외부 연계 | DynamoDB, RDS Proxy, Redis |
| Control Plane | 권한, 동시성, 로그 관리 | IAM, quota, CloudWatch |

> 요약: FaaS는 이벤트, 함수 런타임, 외부 상태, 통제 계층으로 구성되어 stateless 실행을 전제로 동작함.

---

## Ⅲ. 동작원리 및 흐름도

```text
이벤트 발생 -> 트리거 매핑 -> 함수 인스턴스 할당 -> 코드 실행 -> 외부 상태 저장 -> 로그/메트릭 수집
  / cold start -> runtime 초기화
  / concurrency 초과 -> throttling 또는 queue 적재
```

| 단계 | 처리 내용 | 검증 기준 |
|:---:|:---|:---|
| 1 | API, Queue, Object 이벤트 수신 | trigger error 0건 |
| 2 | 런타임 컨테이너 할당 | cold start p95 측정 |
| 3 | 함수 코드 실행과 외부 API 호출 | timeout 0.1% 이하 |
| 4 | DB, Cache, Object Storage에 상태 저장 | connection pool 제한 |
| 5 | 로그, metric, trace 수집 | error rate, duration, throttle |

> 요약: FaaS는 이벤트 수신부터 상태 외부화와 관측까지 짧은 실행 주기를 반복함.

## Ⅳ. 특징

| 구분 | VM/Container 상시 실행 | Serverless FaaS | 수치/판단 포인트 |
|:---|:---|:---|:---|
| 과금 | 인스턴스 시간 | 호출 수, GB-second | idle 비용 0원에 근접 |
| 확장 | HPA, ASG 설정 | 동시 실행 자동 조정 | concurrency quota |
| 지연 | warm process | cold start 존재 | p95 cold start 500ms 이하 목표 |
| 상태 | 로컬 메모리 가능 | 외부 저장소 필요 | stateless 함수 원칙 |

> 요약: FaaS는 변동 요청과 짧은 작업에 맞지만 지연, 상태, 동시성 한도를 설계해야 함.

## Ⅴ. 심화 비교 및 적용 판단

| 비교 축 | 기존/대안 | 본 키워드 | 선택 기준 |
|:---|:---|:---|:---|

| 비용/처리 | 상시 인스턴스 | 호출 기반 과금 | idle 60% 이상 업무 |
| 운영/위험 | 런타임 직접 관리 | CSP 관리형 런타임 | 패치 책임 전환 필요 |

> 요약: 실행 시간이 짧고 요청 변동이 큰 이벤트 업무는 FaaS, 장시간 연결과 예측 처리량 업무는 컨테이너를 선택함.

| 리스크 | 원인 | 대응 방안 | 확인 지표 |
|:---|:---|:---|:---|

| 벤더 종속 | CSP event, IAM, SDK 의존 | OpenFaaS, Knative, hexagonal 구조 | 이식 함수 비율 |

> 요약: FaaS 리스크는 지연, 상태, 종속성을 지표와 구조 분리로 통제함.
