# 📖 【암기용】 개념 완전 이해

> 목적: SPOF 제거를 처음 봐도 완전히 이해하게 만든다. 시험 답안 양식이 아니라, 이해를 위한 친절한 설명이다.

## 한눈에
- **개요**: 하나의 구성요소 장애가 전체 서비스 중단으로 이어지는 지점을 제거하는 설계
- **왜 필요한가**: 서버를 여러 대 두어도 단일 DB, 단일 DNS, 단일 인증 서버가 남아 있으면 장애는 계속 전체 장애로 번진다.
- **핵심 직관**: 체인의 가장 약한 고리 하나가 끊기면 전체가 끊기므로, 각 고리에 우회 경로를 만드는 작업이다.

## 깊이 이해
- **배경·문제의식**: 장애 분석에서 "웹 서버 3대" 같은 숫자만 보면 이중화가 된 것처럼 보인다. 그러나 로드밸런서, NAT, DB primary, 메시지 브로커, 배포 서버가 하나라면 여전히 SPOF이다.
- **작동 원리**: 의존성 맵을 작성하고 단일 인스턴스, 단일 AZ, 단일 계정, 단일 운영자 절차를 찾아 이중화·분산·자동 전환·권한 분리를 적용한다.
- **비유**: 건물 출입문이 하나뿐이면 내부 방이 여러 개여도 화재 시 대피가 막힌다. SPOF 제거는 출입문과 비상계단을 동시에 설계하는 일이다.
- **구체 예시**: API 서버 4대 뒤에 단일 Redis를 둔 경우 Redis 장애 시 로그인 세션 전체 장애가 발생한다. Redis Sentinel 또는 managed cluster로 자동 승격을 구성한다.
- **흔한 오해·주의점**: 모든 것을 복제하면 끝나는 문제가 아니다. 복제된 요소를 제어하는 DNS, quorum, 인증서, 운영 권한도 SPOF가 될 수 있다.

## 연결 개념
- High Availability — SPOF 제거 후 가용성 목표 달성
- Auto Failover — 대체 경로로 자동 전환
- Dependency Mapping — 장애 전파 경로 식별

# 📝 【답안용】 시험 답안 템플릿

> 목적: 시험장에서 25분에 그대로 쓰는 답안 양식. 작성방식(추상표현 금지·수치·도식·문제유형 전환)을 엄격히 지킨다.
> 핵심: SPOF 답안은 구성요소 목록이 아니라 의존성 맵에서 단일 장애점을 찾아 제거 우선순위를 제시해야 한다.

## 핵심 인사이트 (3줄 요약)

> 1. **본질**: SPOF는 특정 구성요소 1개 장애가 서비스 전체 장애로 전파되는 단일 의존 지점이다.
> 2. **가치**: 웹, DB, 네트워크, 인증, 운영 절차의 단일 의존성을 제거해 장애 영향 범위를 축소한다.
> 3. **판단 포인트**: 이중화 여부보다 자동 전환, 데이터 정합성, 장애 격리, 정기 검증까지 포함해야 한다.

## 출제 의도 및 답안 포인트

| 출제 의도 | 반드시 짚을 핵심 | 감점 회피 포인트 |
|:---|:---|:---|
| 가용성 병목 식별 확인 | 단일 노드, 단일 AZ, 단일 계정, 단일 절차 | 서버 이중화만 언급 |
| 제거 방안 설계 확인 | 다중화, quorum, failover, backup path | 복제 후 전환 검증 누락 |
| 운영 검증 확인 | dependency map, chaos test, SLO | 장애 전파 경로 미분석 |

> 요약: SPOF 제거는 의존성 맵 기반으로 단일 실패 지점을 찾아 대체 경로와 전환 검증을 설계하는 문제이다.

---

## Ⅰ. 개요 및 필요성

- 개요: SPOF는 단일 장애가 전체 중단을 유발하는 지점이다.
- 배경: 클라우드 시스템은 웹 서버 외에도 DNS, DB, 메시지 브로커, 인증, 배포 파이프라인에서 SPOF가 발생한다.
- 필요성: 장애 전파 경로와 RTO 기준을 근거로 이중화·분산·대체 경로 적용 우선순위를 정해야 한다.

---

## Ⅱ. 구조 및 구성요소

```text
Service Map -> SPOF Identification -> Redundancy Design
            -> Failover Path -> Chaos Test -> Residual Risk
```

| 구성요소 | 역할 | 특이사항 |
|:---|:---|:---|
| Dependency Map | 서비스·DB·네트워크 의존성 시각화 | 호출·데이터·운영 경로 포함 |
| SPOF Catalog | 단일 인스턴스와 단일 절차 목록화 | LB, DNS, DB, IAM |
| Redundancy Design | 다중 AZ·클러스터·대체 경로 설계 | quorum, fencing 필요 |
| Verification | 장애 주입과 전환 결과 측정 | chaos test, RTO |

> 요약: SPOF 제거는 식별, 다중화, 전환 경로, 검증의 순서로 수행된다.

---

## Ⅲ. 동작원리 및 흐름도

```text
자산 식별 -> 의존성 분석 -> 단일 지점 판정
-> 제거 방식 선택 -> 장애 주입 -> 잔여 위험 등록
```

| 단계 | 처리 내용 | 검증 기준 |
|:---:|:---|:---|
| 1 | 서비스 호출·DB·네트워크·운영 경로 수집 | 주요 서비스 100% 맵핑 |
| 2 | 단일 인스턴스·단일 AZ·단일 권한 식별 | SPOF 목록 승인 |
| 3 | 이중화·클러스터·대체 절차 적용 | failover 60초 이하 |
| 4 | 장애 주입으로 실제 영향 확인 | 오류율 0.1% 이하 |

> 요약: SPOF 제거는 문서 점검이 아니라 장애 주입으로 단일 실패가 전체 장애로 번지지 않음을 확인한다.

## Ⅳ. 특징

| 구분 | SPOF 존재 구조 | SPOF 제거 구조 | 수치 판단 |
|:---|:---|:---|:---|
| 장애 영향 | 전체 서비스 중단 | 장애 도메인 내 격리 | blast radius 1개 AZ 이하 |
| 전환 | 수동 복구 | 자동 failover | RTO 60초 이하 |
| 검증 | 구성도 확인 | chaos test 반복 | 분기 1회 이상 |

> 요약: SPOF 제거 구조는 장애 범위를 제한하고 자동 전환과 주기적 실험으로 검증한다.

## Ⅴ. 심화 비교 및 적용 판단

| 비교 축 | 기존/대안 | 본 키워드 | 선택 기준 |
|:---|:---|:---|:---|
| 애플리케이션 | 단일 서버 | 다중 인스턴스 + LB | 무상태 전환 가능 시 |
| 데이터 | 단일 DB | replica + 자동 승격 | RTO/RPO 요구가 있을 때 |
| 운영 | 단일 담당자·수동 절차 | runbook + 권한 분산 | 야간·휴일 장애 대응 필요 시 |

> 요약: 기술 요소뿐 아니라 운영 권한과 절차도 SPOF 제거 대상에 포함해야 한다.

| 리스크 | 원인 | 대응 방안 | 확인 지표 |
|:---|:---|:---|:---|
| 숨은 SPOF | 인증·DNS·배포 경로 누락 | dependency map 정기 갱신 | 미등록 의존성 0건 |
| Split-brain | 이중화 제어 실패 | quorum, fencing | dual primary 0건 |
| 비용 증가 | 모든 계층 일괄 다중화 | BIA 기반 우선순위 | Tier-1 100% 제거 |

> 요약: SPOF 제거는 모든 계층 일괄 복제가 아니라 업무 영향도 기준으로 우선순위를 둔다.

| 점검 항목 | 목표 기준 | 측정 방법 |
|:---|:---|:---|
| 식별 | Tier-1 의존성 100% 등록 | CMDB, architecture review |
| 전환 | failover 60초 이하 | chaos test |
| 영향 범위 | 장애 도메인 1개 AZ 이하 | incident postmortem |

> 요약: 식별률, 전환 시간, 영향 범위가 SPOF 제거의 핵심 검증 지표이다.

## Ⅵ. 실무 적용 및 결론

**적용 방안 3개 (필수 — 단계별 또는 항목별):**
1. Tier-1 서비스의 LB, DNS, DB, IAM, 메시지 브로커, 배포 파이프라인 의존성 맵을 100% 작성
2. 단일 AZ·단일 primary·단일 계정 지점에 다중 AZ, quorum, break-glass 계정을 적용
3. 분기별 chaos test로 LB, DB primary, Redis 장애를 주입하고 RTO 60초 이하를 검증

**결론 (2줄):**
- 기술사 판단: SPOF 제거는 서버 수 증가가 아니라 단일 의존성 제거와 전환 검증까지 포함해야 완료된다
- 향후 방향: platform engineering은 golden path에 다중 AZ, managed failover, 정책 검사를 내장해 SPOF 생성을 사전에 차단한다
