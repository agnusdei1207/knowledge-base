# 📖 【암기용】 개념 완전 이해

> 목적: SPOF 제거를 처음 봐도 완전히 이해하게 만든다. 시험 답안 양식이 아니라, 이해를 위한 친절한 설명이다.

## 한눈에
- **개요**: SPOF(Single Point of Failure, 단일 장애점)는 **가용성(Availability)** 설계에서 하나의 구성요소 장애가 전체 서비스 중단으로 곧장 이어지는 지점을 뜻하며, 이를 찾아 없애는 것이 **이중화(Redundancy)** 설계의 목표다.
- **왜 필요한가**: 웹 서버를 여러 대로 늘려도, 그 뒤의 로드밸런서·DB·DNS·인증 서버가 하나뿐이면 그 하나가 여전히 전체 장애의 원인이 된다. 이중화된 부분만 보고 "가용성이 확보됐다"고 착각하면 실제 장애 때 배신당한다.
- **핵심 직관**: 사슬은 가장 약한 고리 하나가 끊기면 전체가 끊긴다. SPOF 제거는 사슬의 모든 고리를 점검해 약한 고리마다 우회 경로(병렬 고리)를 추가하는 작업이다.

## 핵심 용어 정리 (내부에 등장하는 것들)

| 용어 | 의미 | 비유 |
|:---|:---|:---|
| 가용성(Availability) | 시스템이 정상 동작하는 시간의 비율 — SPOF가 갉아먹는 대상 | 자판기 정상 작동 비율 |
| 이중화(Redundancy) | 동일 기능을 하는 구성요소를 병렬로 여러 개 두는 것 — SPOF 제거의 기본 수단 | 비상계단을 하나 더 만드는 것 |
| 의존성 맵(Dependency Map) | 서비스가 어떤 구성요소에 의존하는지 시각화한 지도 — SPOF를 찾는 출발점 | 건물의 전기·수도 배관도 |
| Blast Radius(장애 반경) | 하나의 장애가 실제로 영향을 미치는 범위 — SPOF가 클수록 반경이 넓음 | 폭발이 미치는 반경 |
| Quorum/Fencing | 이중화된 구성요소가 동시에 주(Primary) 역할을 하지 못하게 막는 통제(245에서 상세) | 동시에 두 사람이 운전대를 잡지 못하게 하는 잠금장치 |
| Chaos Test(장애 주입) | 실제로 구성요소를 강제로 죽여서 대체 경로가 작동하는지 검증하는 실험 | 소방 훈련(실제로 대피시켜 봄) |
| CMDB | 자산·구성요소의 목록과 관계를 관리하는 데이터베이스 — 의존성 맵의 데이터 원천 | 건물 설비 대장 |

## 깊이 이해

### 왜 "서버 여러 대"만으로는 부족한가 (배경)
장애 분석 회의에서 "웹 서버가 3대입니다"라는 말만 들으면 이중화가 된 것처럼 들린다. 그러나 그 3대 앞의 로드밸런서가 1대, 그 뒤의 DB가 1대(primary), DNS가 1개 레코드, 메시지 브로커가 클러스터가 아니라 1개 노드, 배포를 실행하는 CI 서버가 1대라면, 이 중 어느 하나만 죽어도 웹 서버 3대는 무의미해진다. SPOF는 "보이는 계층"이 아니라 "의존성 그래프 전체"에서 찾아야 한다.

### 이중화가 가용성을 어떻게 바꾸는가 — 직렬·병렬 수치 계산
구성요소 하나의 가용성이 99.9%(월 다운타임 약 43분)라고 하자.
- **직렬 연결(SPOF 존재)**: 웹 서버 → LB → DB → 인증서버가 모두 순서대로 의존하면, 전체 가용성은 각 구간 가용성의 **곱**이다. 5개 구성요소가 직렬이면 0.999⁵ ≈ **99.5%**로, 개별 요소보다 전체 가용성이 떨어진다. 의존 사슬이 길어질수록(SPOF가 많을수록) 전체 가용성은 낮아진다.
- **병렬 이중화(SPOF 제거)**: 동일 기능을 하는 노드 2대를 병렬(둘 중 하나만 살아있어도 서비스 가능)로 두면, 전체가 죽는 경우는 두 노드가 "동시에" 죽는 경우이므로 미가용률(0.1% = 0.001)끼리 곱해진다. 전체 가용성 = 1 - (1-0.999)×(1-0.999) = 1 - 0.001×0.001 = **99.9999%**. 99.9%짜리 부품 2개를 병렬로 두면 가용성이 소수점 4자리가 올라가는 극적인 개선이 나온다.
- 이 계산이 SPOF 제거의 수학적 근거다 — 직렬은 약점을 누적시키고, 병렬(이중화)은 약점을 지수적으로 줄인다.

### SPOF를 찾고 없애는 절차
1. 의존성 맵을 그려 서비스 호출 경로, 데이터 경로, 운영(배포·인증) 경로를 모두 포함한다.
2. 각 노드가 단일 인스턴스·단일 AZ·단일 계정·단일 담당자 절차인지 점검해 SPOF 목록(SPOF Catalog)을 만든다.
3. 이중화(다중 AZ, 클러스터), quorum/fencing(245 참고), 대체 경로(백업 DNS, 보조 인증 경로)를 적용한다.
4. 실제로 해당 구성요소를 죽여보는 Chaos Test로 대체 경로가 진짜 작동하는지 검증한다 — 문서상 이중화와 실제 작동은 다를 수 있다.

### 흔히 놓치는 "숨은 SPOF" — 구체 예시
API 서버 4대를 Active-Active로 이중화해도, 그 뒤에서 로그인 세션을 저장하는 Redis가 1대뿐이면 Redis가 죽는 순간 API 서버 4대가 살아있어도 로그인 세션 전체가 사라져 서비스 전체 장애가 난다. 이 경우 Redis Sentinel(자동 승격 구성) 또는 관리형 클러스터로 Redis 자체를 이중화해야 진짜 SPOF가 제거된다. 마찬가지로, 이중화된 DB를 가리키는 DNS 레코드가 1개뿐이거나, 배포 파이프라인에 접근 가능한 운영자가 1명뿐이면(휴가·연락두절 시 배포 불가) 그것도 SPOF다.

### 비유
출입문이 하나뿐인 건물은 내부에 방이 아무리 많아도 화재가 나면 대피가 그 문 하나에 몰려 병목이 생긴다. SPOF 제거는 출입문 개수(이중화)뿐 아니라 비상계단(대체 경로), 대피 안내판(자동 전환 로직)까지 함께 설계하는 일이다.

### 흔한 오해·주의점
모든 계층을 무조건 다 복제하면 끝나는 문제가 아니다. 이중화 자체를 제어하는 DNS, quorum, 인증서 발급 권한, 운영자 계정이 여전히 하나뿐이면 그것이 새로운 SPOF가 된다. 또한 이중화는 비용이 들므로, BIA로 업무 영향도가 큰 Tier-1부터 우선 제거하는 것이 합리적이며 모든 시스템에 동일한 이중화 수준을 강제할 필요는 없다.

## 연결 개념
- High Availability — SPOF 제거 이후 실제 가용성 목표를 달성하는 설계(245)
- Auto Failover — 이중화된 대체 경로로 자동 전환하는 메커니즘(247)
- Disaster Recovery RTO/RPO — SPOF 제거 우선순위를 정하는 근거가 되는 복구 목표(244)

# 📝 【답안용】 시험 답안 템플릿

> 목적: 시험장에서 25분에 그대로 쓰는 답안 양식. 작성방식(추상표현 금지·수치·도식·문제유형 전환)을 엄격히 지킨다.
> 핵심: SPOF 답안은 구성요소 목록이 아니라 의존성 맵에서 단일 장애점을 찾아 제거 우선순위를 제시해야 한다.

## 핵심 인사이트 (3줄 요약)

> 1. **본질**: SPOF는 특정 구성요소 1개 장애가 서비스 전체 장애로 전파되는 단일 의존 지점이다.
> 2. **가치**: 웹, DB, 네트워크, 인증, 운영 절차의 단일 의존성을 제거해 장애 영향 범위를 축소한다.
> 3. **판단 포인트**: 이중화 여부보다 자동 전환, 데이터 정합성, 장애 격리, 정기 검증까지 포함해야 한다.

| 제거 방안 설계 확인 | 다중화, quorum, failover, backup path | 복제 후 전환 검증 누락 |

## Ⅰ. 개요 및 필요성

- 개요: SPOF는 단일 장애가 전체 중단을 유발하는 지점이다.
- 배경: 클라우드 시스템은 웹 서버 외에도 DNS, DB, 메시지 브로커, 인증, 배포 파이프라인에서 SPOF가 발생한다.
- 필요성: 장애 전파 경로와 RTO 기준을 근거로 이중화·분산·대체 경로 적용 우선순위를 정해야 한다.

---

## Ⅱ. 구조 및 구성요소

```text
Service Map -> SPOF Identification -> Redundancy Design
            -> Failover Path -> Chaos Test -> Residual Risk
```

| 구성요소 | 역할 | 특이사항 |
|:---|:---|:---|
| Dependency Map | 서비스·DB·네트워크 의존성 시각화 | 호출·데이터·운영 경로 포함 |
| SPOF Catalog | 단일 인스턴스와 단일 절차 목록화 | LB, DNS, DB, IAM |
| Redundancy Design | 다중 AZ·클러스터·대체 경로 설계 | quorum, fencing 필요 |
| Verification | 장애 주입과 전환 결과 측정 | chaos test, RTO |

> 요약: SPOF 제거는 식별, 다중화, 전환 경로, 검증의 순서로 수행된다.

---

## Ⅲ. 동작원리 및 흐름도

```text
자산 식별 -> 의존성 분석 -> 단일 지점 판정
-> 제거 방식 선택 -> 장애 주입 -> 잔여 위험 등록
```

| 단계 | 처리 내용 | 검증 기준 |
|:---:|:---|:---|
| 1 | 서비스 호출·DB·네트워크·운영 경로 수집 | 주요 서비스 100% 맵핑 |
| 2 | 단일 인스턴스·단일 AZ·단일 권한 식별 | SPOF 목록 승인 |
| 3 | 이중화·클러스터·대체 절차 적용 | failover 60초 이하 |
| 4 | 장애 주입으로 실제 영향 확인 | 오류율 0.1% 이하 |

> 요약: SPOF 제거는 문서 점검이 아니라 장애 주입으로 단일 실패가 전체 장애로 번지지 않음을 확인한다.

| 구분 | 기존/대안 | 본 키워드 | 선택 기준 |
|:---|:---|:---|:---|

> 요약: 기술 요소뿐 아니라 운영 권한과 절차도 SPOF 제거 대상에 포함해야 한다.

| 리스크 | 원인 | 대응 방안 | 확인 지표 |
|:---|:---|:---|:---|
| 숨은 SPOF | 인증·DNS·배포 경로 누락 | dependency map 정기 갱신 | 미등록 의존성 0건 |
| Split-brain | 이중화 제어 실패 | quorum, fencing | dual primary 0건 |
| 비용 증가 | 모든 계층 일괄 다중화 | BIA 기반 우선순위 | Tier-1 100% 제거 |

> 요약: SPOF 제거는 모든 계층 일괄 복제가 아니라 업무 영향도 기준으로 우선순위를 둔다.

| 점검 항목 | 목표 기준 | 측정 방법 |
|:---|:---|:---|
| 식별 | Tier-1 의존성 100% 등록 | CMDB, architecture review |
| 전환 | failover 60초 이하 | chaos test |
| 영향 범위 | 장애 도메인 1개 AZ 이하 | incident postmortem |

> 요약: 식별률, 전환 시간, 영향 범위가 SPOF 제거의 핵심 검증 지표이다.

## Ⅵ. 실무 적용 및 결론

**적용 방안 3개 (필수 — 단계별 또는 항목별):**
1. Tier-1 서비스의 LB, DNS, DB, IAM, 메시지 브로커, 배포 파이프라인 의존성 맵을 100% 작성
2. 단일 AZ·단일 primary·단일 계정 지점에 다중 AZ, quorum, break-glass 계정을 적용
3. 분기별 chaos test로 LB, DB primary, Redis 장애를 주입하고 RTO 60초 이하를 검증

**결론 (2줄):**
- 기술사 판단: SPOF 제거는 서버 수 증가가 아니라 단일 의존성 제거와 전환 검증까지 포함해야 완료된다
- 향후 방향: platform engineering은 golden path에 다중 AZ, managed failover, 정책 검사를 내장해 SPOF 생성을 사전에 차단한다
