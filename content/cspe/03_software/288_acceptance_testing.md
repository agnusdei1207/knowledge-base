## Ⅰ. 개요
- 정의: 시스템을 인도하기 전, 계약상의 요구사항이 충족되었는지 사용자가 최종 확인하는 과정
- 배경: 개발자와 사용자 간의 요구사항 해석 차이를 해소하고 잔금 지급 등 행정적 근거 마련
- 출제 의도: 인수 테스팅의 종류(Alpha, Beta 등) 및 합격 판정 기준 이해

## Ⅱ. 구성요소
- 구조도
  [System Test] -> [Acceptance Test] -> [Go/No-Go Decision] -> [Release]
                      |-- Alpha Test (Dev Site)
                      |-- Beta Test (User Site)

- 구성요소 표
| 유형 | 장소 | 참여자 |
| :--- | :--- | :--- |
| 알파 테스트 | 개발자 조직 내부 | 선택된 사용자 + 개발자 |
| 베타 테스트 | 실제 사용 환경 | 다수의 불특정 사용자 |
| 규정 인수 테스트 | 고객 현장 | 정부/감독 기관 (법규 준수) |
> 요약: 계약 요구사항·업무 시나리오·성능 임계치와 시험 결과를 비교하여 인수 여부를 판정함

## Ⅲ. 절차
- 흐름도
  인수 기준 확정 -> 시나리오 준비 -> 테스트 수행 -> 인수 승인/거부
- 4단계 설명
1. 인수 기준 확정: 계약 시 합의된 기능 범위 및 성능 임계치 재확인
2. 시나리오 준비: 업무 흐름(End-to-End) 중심의 사용자 수락 테스트 케이스 작성
3. 테스트 수행: 사용자가 주도적으로 테스트를 수행하며 결과 및 결함 기록
4. 인수 승인: 중대한 결함이 없고 기준을 충족할 경우 인수 서명 및 운영 전환 결정
> 요약: 사용자가 End-to-End 시나리오를 수행하고 결함 등급과 합격 기준에 따라 승인·보완·거부를 결정함

## Ⅳ. 문제점
- 개발 단계에서 누락된 요구사항이 인수 단계에서 뒤늦게 발견되어 분쟁 발생
- 인수 테스트 기간 부족으로 인해 부실한 검증이 이루어져 오픈 초기 장애 속출

## Ⅴ. 개선방안
- 요구사항 추적 매트릭스(RTM)를 통해 설계-개발-인수 단계의 일관성 상시 점검
- 개발 중반부터 인수 시나리오를 선제적으로 공유하여 최종 검증 준비성 강화

## Ⅵ. 전망
- 사용자 환경의 다양화(OS, 기기 등)에 따른 자동화된 원격 베타 테스트 플랫폼 확산
- CSF: 정량적 통과 기준 외에 운영 조직의 인수 준비성(Readiness) 평가 병행
