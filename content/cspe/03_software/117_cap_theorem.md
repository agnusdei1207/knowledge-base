# 📖 【암기용】 개념 완전 이해

## 한눈에
- **개요**: 분산 데이터베이스 시스템은 '일관성(C)', '가용성(A)', '파티션 감내성(P)'이라는 3가지 속성 중 최대 2가지만 완벽히 만족할 수 있다는 컴퓨터 공학의 기본 정리
- **왜 필요한가**: 수십 대의 서버로 구성된 글로벌 서비스에서 완벽하게 똑같은 데이터를(C) 1초도 안 멈추고(A) 네트워크가 끊겨도(P) 서비스하겠다는 요구가 물리적으로 불가능함을 증명하기 위해 등장했다.
- **핵심 직관**: 양손에 짐을 가득 든 상태(C, A)에서 누군가 문을 열어달라고(P) 하면, 하나(C 또는 A)를 바닥에 내려놔야만 문을 열 수 있는 것과 같다.

## 핵심 용어 정리

| 용어/표기 | 의미 | 비유·예 |
|:---|:---|:---|
| Consistency (일관성) | 모든 사용자가 어떤 노드에 접속하든 똑같은 최신 데이터를 봄 | 서울 지점과 부산 지점의 통장 잔고가 항상 일치 |
| Availability (가용성) | 시스템의 일부 노드에 장애가 나도, 살아있는 노드는 정상 응답함 | 서울 지점이 정전돼도 부산 지점에서 출금 가능 |
| Partition Tolerance (파티션 감내) | 노드 간 네트워크 통신이 단절(Partition)되어도 시스템이 계속 동작함 | 서울-부산 통신선이 끊겨도 각 지점은 영업 계속 |

## 깊이 이해
- **배경·문제의식**: Eric Brewer 교수가 2000년에 제안. 단일 DB(RDBMS) 시절에는 C와 A만 신경 쓰면 됐다(CA 시스템). 하지만 클라우드 분산 환경에서는 네트워크 단절이나 지연(Partition)이 '반드시' 일어나는 상수가 되었다.
- **작동 원리 (네트워크 단절 시 딜레마)**:
  - 서울(Node 1)과 부산(Node 2) 간 네트워크가 끊어졌다 (P 발생).
  - 이때 부산 고객이 "잔고 1만 원 출금"을 요청한다.
  - **선택 1 (CP - 일관성 유지)**: 서울과 동기화를 못 하므로 잔고 오류를 막기 위해 부산 지점의 "출금 거절(에러 응답)"을 한다. (A 포기)
  - **선택 2 (AP - 가용성 유지)**: 일단 부산 지점이 가진 옛날 잔고 기록으로라도 "출금 승인"을 해준다. 나중에 네트워크가 복구되면 잔고를 맞춘다. (C 포기)
- **비유**: 회의록(데이터)을 공유하는 두 비서(분산 노드)가 있다. 둘의 무전기(네트워크)가 고장 났을 때(P), 상무님이 결정 사항을 물어본다면?
  - CP: "다른 비서와 연락이 안 되어 확실치 않으니 대답을 보류하겠습니다." (에러/대기)
  - AP: "연락은 끊겼지만, 제가 아는 선(옛날 정보)에서 일단 말씀드리겠습니다." (오래된 데이터 응답)
- **흔한 오해·주의점**: CAP 정리는 "평소에 2개만 선택해야 한다"가 아니다. 네트워크 단절(P)이라는 **장애 상황이 발생했을 때만** C와 A 중 하나를 희생해야 한다는 뜻이다. 평상시(P가 없을 때)는 C와 A를 모두 제공할 수 있다.

## 연결 개념
- PACELC 정리: CAP 정리는 P(장애) 상황만 설명하므로, 평상시(E)의 지연 시간(L)과 일관성(C)의 트레이드오프까지 설명하기 위해 확장된 최신 이론
- Eventual Consistency (최종 일관성): AP를 선택한 시스템이 결국엔 C(일관성)를 맞추겠다는 타협안

# 📝 【답안용】 시험 답안 템플릿

## 핵심 인사이트 (3줄 요약)

> 1. **본질**: CAP 정리는 분산 시스템 설계 시 일관성(Consistency), 가용성(Availability), 파티션 감내성(Partition Tolerance)의 3요소 중 최대 2개만 선택 가능하다는 한계 원리다.
> 2. **가치**: 대규모 클라우드/분산 아키텍처에서 물리적인 네트워크 단절(P)을 상수로 인정하고, 비즈니스 도메인에 맞춰 C(정합성)와 A(응답성) 중 하나를 포기하는 기준을 제공한다.
> 3. **판단 포인트**: 현실의 분산 시스템은 P를 포기할 수 없으므로(네트워크 장애는 필연), 금융/결제는 CP 아키텍처로, SNS/카탈로그는 AP 아키텍처로 설계하는 이분법적 결단이 요구된다.

## 출제 의도 및 답안 포인트

| 출제 의도 | 반드시 짚을 핵심 | 감점 회피 포인트 |
|:---|:---|:---|
| 분산 시스템 한계의 원리적 이해 | 3요소(C, A, P)의 정확한 정의 및 상호 배타성 증명 | P를 단순한 서버 장애로 설명 (P는 네트워크 단절임) |
| 아키텍처 트레이드오프 판단 역량 | 분산 환경에서 P는 필수불가결하므로 CP vs AP 선택 | CA 시스템이 클라우드 분산 환경에 존재한다고 단정 |
| 도메인별 NoSQL 선택 기준 | CP(MongoDB, HBase)와 AP(Cassandra, Dynamo) 사례 | CAP를 평상시에도 2개만 선택한다고 오해함 |

> 요약: 분산 시스템에서 네트워크 단절(P)은 피할 수 없는 물리적 현실이므로, 아키텍트는 서비스 특성에 따라 강한 일관성(CP)과 지속적 응답(AP) 중 하나를 선택하는 트레이드오프를 수용해야 함을 논증한다.

## Ⅰ. 개요 및 필요성

- 개요: 분산 데이터 시스템에서 일관성, 가용성, 파티션 감내성의 세 가지 속성 중 최대 두 가지만 동시에 만족할 수 있다는 증명 이론
- 배경: Scale-up 기반의 RDBMS(CA 특성)가 한계에 달해 수백 대의 노드로 이루어진 Scale-out 분산 환경이 주류로 부상
- 필요성: 네트워크 지연 및 단절(Split-Brain) 상황에서 시스템의 동작(응답 거부 vs 과거 데이터 응답)을 비즈니스 요구에 맞게 통제하고 설계할 이론적 근거 필요

## Ⅱ. 구조 및 구성요소

```text
       [ Consistency (일관성) ]
             /        \
           /            \
  (CA: RDBMS)          (CP: MongoDB/HBase)
         /                \
       /                    \
[ Availability ]----------[ Partition Tolerance ]
   (가용성)        (AP: Cassandra)       (파티션 감내)
```

| 구성요소 | 역할 | 특이사항 |
|:---|:---|:---|
| Consistency (C) | 모든 읽기 요청이 가장 최근의 쓰기 결과를 받거나 에러를 반환함 | 강한 일관성 보장, 트랜잭션 도메인 필수 |
| Availability (A) | 실패하지 않은 모든 노드는 최신 데이터 여부와 무관하게 정상 응답함 | 무중단 서비스 지향, 24/7 서비스 필수 |
| Partition Tolerance (P) | 노드 간 네트워크 메시지 유실 및 단절에도 시스템 전체는 동작함 | 분산/클라우드 환경에서 포기할 수 없는 기본 전제 |

> 요약: 이론상 세 꼭지점의 조합이 존재하나, 현실의 물리 네트워크는 반드시 단절(P) 가능성을 내포하므로 실질적인 선택지는 CP와 AP로 귀결된다.

---

## Ⅲ. 동작원리 및 흐름도

```text
클라이언트 요청 -> 네트워크 단절(P) 감지 -> 정책에 따른 분기 (CP vs AP)
                +-> CP 시스템: 동기화 실패 -> 에러 반환(Timeout) -> 일관성 방어
                +-> AP 시스템: 동기화 실패 -> 로컬 데이터로 응답 -> 가용성 방어
```

- 1단계 [상황 발생]: 클러스터 내 노드 A와 B 사이의 네트워크 스위치 장애로 통신이 단절(Partition)됨
- 2단계 [요청 인입]: 사용자가 노드 B에 데이터를 업데이트(Write)하거나 조회(Read)를 요청
- 3단계 [CP 선택 흐름]: 정합성이 우선인 시스템은 노드 A와의 동기화 확인이 불가하므로 업데이트를 블록(Block)하거나 에러를 반환
- 4단계 [AP 선택 흐름]: 응답성이 우선인 시스템은 노드 A와의 단절을 무시하고 B 노드 단독으로 쓰기를 허용하거나 이전 데이터를 응답

> 요약: 장애(P) 발생 시, 일관성을 위해 응답을 포기할지(CP), 잘못된 데이터라도 응답을 유지할지(AP) 시스템 설정이 개입한다.

---

## Ⅳ. 특징

- 상호 배타성: 분산된 두 노드 간 통신이 불가능한 상태에서 둘 다 업데이트를 받으면 일관성(C)이 깨지고, 한쪽을 막으면 가용성(A)이 깨지는 구조적 모순
- 선택의 스펙트럼: 완벽한 C와 A의 이분법이 아닌, NoSQL 제품마다 리드/라이트 쿼럼(Quorum) 조정을 통해 C와 A의 강도를 동적으로 튜닝 가능
- PACELC로의 진화: CAP가 '네트워크 단절 시'의 극단적 상황만 다룬다는 한계로 인해, '평상시'의 레이턴시(L) 트레이드오프를 추가한 이론으로 발전

---

## Ⅴ. 심화 비교 및 적용 판단

| 비교 축 | CP 시스템 (Consistency + Partition) | AP 시스템 (Availability + Partition) | 적용 기준 |
|:---|:---|:---|:---|
| 장애 시 동작 | 타 노드와의 쿼럼(과반수) 미달 시 쓰기 거부 | 네트워크 단절 시에도 자체 로컬 데이터로 읽기/쓰기 허용 | 데이터 오류의 치명성 수준 |
| 데이터 정합성 | 항상 최신 데이터 보장 (Strong Consistency) | 한시적 불일치 발생 (Eventual Consistency) | 트랜잭션 vs 대규모 트래픽 |
| 대표적 DB | MongoDB (Primary 노드 선출 시 블로킹), HBase | Cassandra, DynamoDB, Couchbase | 구축할 마이크로서비스 도메인 성격 |

> 요약: 결제, 재고, 인증 도메인은 오류 응답(CP)을 감수하고서라도 정합성을 지켜야 하며, SNS 피드나 로그 수집은 옛날 글이 보이더라도 무조건 응답(AP)해야 한다.

**리스크·대응:**
- CP 시스템의 프로모션 딜레이: MongoDB 등에서 마스터 노드 장애 시 새 마스터 선출까지 수 초~수십 초간 Write 전면 중단(A 저하) → 빠른 헬스체크 및 투표(Election) 타임아웃 튜닝
- AP 시스템의 Split-Brain 충돌: 통신 단절 복구 후 양쪽 노드의 쓰기 데이터 충돌 발생 → 타임스탬프(LWW)나 벡터 시계(Vector Clock)를 활용한 자동 병합 아키텍처 구현
- 정합성 한계: AP 기반에서 결제 시 초과 출금 리스크 → 금융 도메인은 2PC나 Saga 패턴을 활용하여 애플리케이션 레벨에서 최종 일관성을 강제 보정

## Ⅵ. 실무 적용 및 결론

**적용 방안 3개:**
1. 도메인 주도 DB 매핑 (Polyglot): 이커머스에서 장바구니/추천은 AP 기반 Cassandra를 적용하여 장바구니 담기 실패율을 0%로 만들고, 결제 트랜잭션은 CP 기반 HBase 또는 RDBMS를 적용
2. Quorum 기반 튜닝: Cassandra와 같은 튜너블(Tunable) NoSQL에서 `W(Write) + R(Read) > N(Replication Factor)` 공식을 적용해 평상시에는 강한 일관성을 흉내 내도록 설정 변경
3. 회로 차단기(Circuit Breaker) 연계: CP 시스템에서 타임아웃 발생 시, 단순 에러 노출 대신 회로 차단기를 통해 큐(Kafka)에 요청을 적재하고 비동기 보상(Compensation)을 수행하는 구조 설계

**결론 (2줄):**
- 기술사 판단: 클라우드 환경에서 네트워크 장애(P)는 필연이므로, 아키텍트는 "모든 것을 완벽히 제공하겠다"는 환상을 버리고 비즈니스 중요도에 따라 C와 A 중 희생할 타깃을 명확히 정의해야 한다.
- 향후 방향: 최근 분산 시스템은 CAP의 이분법을 넘어, Spanner(Google)처럼 TrueTime API 기반 원자적 시계를 도입하여 글로벌 P 상황에서도 C와 A를 극대화하는 NewSQL 방향으로 발전하고 있다.
