## Ⅰ. 개요
- 정의: 아키텍처 설계 내용을 이해관계자들에게 효과적으로 전달하고 합의를 도출하는 활동임
- 배경: 아키텍처에 대한 오해로 인한 오구현 방지 및 기술적 비전의 공유 필요성 대두
- 출제 의도: 이해관계자별 맞춤형 뷰 제공 및 설득력 있는 의사소통 전략 역량 평가

## Ⅱ. 구성요소
- ASCII 구조도
  [Architect] <---(Feedback)---> [Stakeholders]
       |                            |
       +-----(Language/Visual)------+
- 구성요소 표
| 구성요소 | 설명 | 비유 |
| :--- | :--- | :--- |
| 관점(Viewpoint) | 특정 이해관계자의 관심사에 맞는 시각적 표현 | 청사진 뷰 |
| 공통 언어 | 모호함을 제거한 기술적 합의 용어(Ubiquitous) | 표준어 |
| 시각화 도구 | 복잡한 구조를 쉽게 설명하기 위한 다이어그램 | 조감도 |
> 요약: 대상에 맞는 언어와 뷰를 선택하여 기술적 의사결정을 공유하고 피드백을 받음

## Ⅲ. 절차
- ASCII 흐름도
  Stakeholder ID -> Message Tailoring -> Delivery -> Feedback
- 4단계 설명
1. Stakeholder ID: 고객, 개발자, 운영자 등 커뮤니케이션 대상 식별함
2. Message Tailoring: 대상의 전문성 수준에 맞춰 기술적 깊이 조절함
3. Delivery: 워크숍, 프리젠테이션, 위키 등 적절한 매체로 전파함
4. Feedback: 제안된 아키텍처에 대한 우려 사항 수렴 및 설계 수정함
> 요약: 대상을 파악하여 맞춤형 정보를 전달하고 피드백을 통해 합의를 형성함

## Ⅳ. 문제점
- 아키텍트가 결정만 전달하고 구현 피드백을 받지 않으면 설계와 개발 제약이 불일치할 수 있음

## Ⅴ. 개선방안
- 개발·운영 담당자가 설계 워크숍과 기술 검증에 참여하고 결정·우려·후속 조치를 함께 기록함

## Ⅵ. 전망
- 가상 현실(VR) 기반 아키텍처 시각화 및 협업 플랫폼 도입 확대 전망
- CSF: 기술적 전문성뿐만 아니라 갈등 조정(Conflict Resolution) 능력이 아키텍트의 핵심임
