## 핵심 인사이트 (3줄 요약)
- 사람이 AWS 콘솔 화면에서 마우스를 딸깍거리며 서버를 만드는 대신, **"서버 1대, 디스크 100GB, 방화벽 80포트 오픈"이라고 코드로 적어서 실행하면 인프라가 자동으로 붕어빵처럼 찍혀 나오는 마법**.
- 인프라를 '자바 소스 코드'처럼 Git으로 버전 관리(형상 관리)할 수 있게 되어, "어제 누가 서버 설정 건드렸어?" 같은 끔찍한 미스터리를 완벽하게 해결함.
- "내가 원하는 최종 상태(Desired State)"만 선언하면 알아서 똑같이 맞춰주는 **선언형(Declarative)** 모델(Terraform 등)이 대세이며, 현대 클라우드 네이티브/DevOps 철학을 현실로 만든 절대적인 기반 기술임.

## Ⅰ. 개요 및 필요성
- **개요**: 수동 프로세스 및 GUI 환경 대신 기계가 읽을 수 있는 정의 파일(코드)을 통해 컴퓨터 데이터 센터 및 클라우드 인프라 자원을 관리하고 프로비저닝하는 프로세스.
- **필요성**: 개발 서버를 AWS에서 마우스 클릭으로 3시간 걸려 세팅함. 기획팀이 "이제 상용 서버 똑같이 만들어주세요!"라고 함. 담당자가 퇴사해서 어떻게 세팅했는지 아무도 모름. 마우스로 찍다 보니 방화벽 하나 빼먹어서 서버 털림. **"아니, 인프라 세팅 과정을 엑셀(문서)에 적지 말고, 아예 컴퓨터가 알아듣는 코드로 짜서 실행 버튼 하나로 수백 번 똑같이 찍어낼 수 있게 만들자!"**
---
## Ⅱ. 아키텍처 및 핵심 원리
- **1. 선언형(Declarative) vs 명령형(Imperative)**:
  - **명령형(Bash, Python)**: "1. AWS 로그인해라 ➡️ 2. 서버 만들어라 ➡️ 3. 디스크 붙여라". (서버가 이미 있으면 에러 남. 멱등성 보장 안 됨).
  - **선언형(Terraform 등 대세)**: "나는 '서버 1대, 디스크 1개'가 있는 **상태를 원해!**". (알아서 현재 상태를 검사하고, 부족하면 만들고, 넘치면 지워서 완벽히 상태를 일치시킴. 100번 실행해도 결과는 똑같음=멱등성 보장).
- **2. 코드 버전 관리 (GitOps의 시발점)**:
  - 인프라 코드를 `git commit` 함.
  - "앗! 실수로 DB 서버를 지웠네!" ➡️ `git revert`로 과거 코드로 되돌리고 다시 실행하면 DB 서버가 1분 만에 짠! 하고 다시 살아남. (인프라의 타임머신화).
- **3. Immutable Infrastructure (불변 인프라)와의 결합**:
  - IaC로 찍어낸 서버는 운영 중에 사람이 수동으로 들어가서 만지면 안 됨(수동으로 만지면 코드와 실제 인프라 간의 **설정 표류(Drift)**가 발생함). 바꿀 게 있으면 코드를 고쳐서 다시 덮어씌우는 것이 철칙임.

```text
[ 수동 인프라 구축 vs IaC 기반 인프라 구축 비교 ]

 🐭 [ ClickOps (수동 클릭 - 휴먼 에러의 온상) ]
 엔지니어: (AWS 화면) "EC2 생성 클릭... 아 방화벽 뭐였지? (클릭) 아 깜빡했다..."
 결과: 개발 서버와 상용 서버의 설정이 달라서, 어제까지 되던 게 상용에선 안 단. 💥

 💻 [ IaC (Infrastructure as Code - 무한 복제) ]
 1. 엔지니어: `main.tf` 파일에 "서버 1대, 80포트 오픈" 작성 ➡️ GitHub에 Push.
 2. Terraform: "설계도 접수! AWS에 똑같이 만들어줄게." (10초 컷)
 3. (1년 뒤) "일본 지사 상용 서버 만들어줘!" 
 4. 엔지니어: "일본 리전으로 변수만 바꿔서 `terraform apply` 실행!" (10초 컷 완료 🚀)
```

## Ⅲ. 비교 및 연결
| 구분 | 프로비저닝 도구 (Provisioning) | 구성 관리 도구 (Configuration Mgmt) |
|---|---|---|
| **핵심 역할** | **인프라 자체(하드웨어, 네트워크)를 뼈대부터 만듦** | **만들어진 뼈대 안에 들어가서 S/W(OS, 앱)를 깜** |
| **작동 방식** | 불변 인프라 지향 (서버를 통째로 찍어내고 부숨) | 가변 인프라 지향 (서버 안에서 이것저것 고침) |
| **방식** | 주로 선언형 (Declarative) | 명령형/선언형 혼합 |
| **대표 도구** | **Terraform, AWS CloudFormation** | **Ansible, Chef, Puppet** |

## Ⅳ. 실무 적용 및 기술사 판단
- **상태 파일 (State File)의 중앙 관리 보안**: 테라폼(Terraform)을 쓸 때 가장 위험한 것은 `terraform.tfstate`라는 상태 파일임. 이 파일 안에는 서버의 현재 상태와 **DB 비밀번호 같은 초민감 정보(Secrets)**가 평문으로 들어있을 수 있음. 초보자들이 이걸 GitHub에 퍼블릭으로 올렸다가 회사가 털림. 기술사는 IaC 아키텍처를 설계할 때 반드시 **상태 파일을 AWS S3(암호화)에 저장하고 DynamoDB로 Lock을 거는 원격 백엔드(Remote Backend)** 구성을 표준으로 강제해야 함.
- **GitOps의 실현**: 코드를 Git에 올리고, 사람이 `terraform apply`를 치는 것도 구시대적임. 최신 실무에서는 **GitOps** 아키텍처를 도입하여, 엔지니어가 `main` 브랜치에 코드를 머지(Merge)하는 순간 CI/CD 파이프라인(ArgoCD, GitHub Actions)이 낚아채서 자동으로 인프라를 프로비저닝하게 만들어 '사람의 터치'를 0%로 만들어야 함.
---
## Ⅴ. 기대효과 및 결론
- "내 컴퓨터에서는 되는데 서버에서는 안 된다"는 영원한 핑계를, '개발부터 상용까지 100% 동일한 인프라 복제'를 통해 완벽하게 박살 냄.
- 재난 발생 시(데이터 센터 화재), 클릭 한 번으로 지구 반대편 클라우드에 1시간 전과 완벽히 똑같은 인프라 수천 대를 부활시킬 수 있는 궁극의 재해 복구(DR) 능력을 부여함.
