# 📖 【암기용】 개념 완전 이해

## 한눈에
- **개요**: 마우스 클릭이나 수동 명령어로 서버를 세팅하는 대신, 인프라의 모든 구성을 소스 코드로 작성하고 자동화된 도구로 배포하는 방식
- **왜 필요한가**: 클라우드 서버 수백 대를 마우스 클릭(콘솔)으로 만들면 실수하기 쉽고, 어제 만든 테스트 서버와 똑같은 서버를 오늘 다시 만들 방법이 없기 때문
- **핵심 직관**: 건물을 지을 때 벽돌을 하나하나 말로 지시하는 대신, 완벽한 '건축 설계도(코드)'를 넘기면 로봇 머신(IaC 도구)이 설계도대로 정확히 건물을 지어주는 것.

## 핵심 용어 정리

| 용어/표기 | 의미 | 비유·예 |
|:---|:---|:---|
| 프로비저닝 (Provisioning) | 인프라 자원(네트워크, 서버, DB 등)을 준비하고 생성하는 과정 | 빈 땅에 도로 깔고 건물 뼈대 세우기 |
| 선언형 (Declarative) | "무엇을(What)" 원하는지 최종 상태만 정의하면 도구가 알아서 맞춤 | "에어컨 24도로 맞춰줘" (Terraform, Kubernetes) |
| 명령형 (Imperative) | "어떻게(How)" 해야 하는지 단계별 스크립트 작성 | "전원 켜고, 모드 냉방 맞추고, 온도 내려" (Ansible, Bash) |
| 멱등성 (Idempotency) | 코드를 1번 실행하나 100번 실행하나 결과 상태가 똑같음 | 에어컨 24도 버튼 100번 눌러도 24도 |

## 깊이 이해
- **배경·문제의식**: 예전에는 서버 관리자가 매뉴얼 문서(Word, Wiki)를 보며 GUI 콘솔에서 버튼을 눌렀다. 이는 인수인계가 어렵고 휴먼 에러를 낳으며 '재현 불가능(Not reproducible)'하다.
- **작동 원리**:
  1. 개발자가 `.tf` 나 `.yaml` 파일로 "AWS VPC 1개, EC2 2대, S3 1개 필요해"라고 코드를 짠다.
  2. 코드를 Git에 올린다 (버전 관리, 리뷰 가능).
  3. Terraform 등의 도구가 코드를 읽고 클라우드 API를 호출해 인프라를 똑같이 구성한다.
- **비유**: 인프라 문서화가 죽은 위키 문서에서 살아 숨쉬는 코드로 진화.
- **구체 예시**: HashiCorp Terraform(프로비저닝), Ansible(형상 관리/설정). 테라폼 코드 한 줄 추가하고 `terraform apply` 치면 클라우드에 서버 한 대가 즉시 올라간다.
- **흔한 오해·주의점**: IaC를 그냥 "스크립트 짜는 것"으로 오해하면 안 된다. 일반 스크립트(Bash)는 다시 실행하면 서버가 하나 더 생기거나 에러가 나지만, IaC 도구는 현재 상태(State)를 인지하고 '멱등성'을 보장하여 바뀐 부분만 수정(diff)한다는 점이 핵심이다.

## 연결 개념
- 불변 인프라 (Immutable Infrastructure)
- GitOps
- 클라우드 네이티브

# 📝 【답안용】 시험 답안 템플릿

## 핵심 인사이트 (3줄 요약)

> 1. **본질**: 하드웨어 및 클라우드 인프라의 프로비저닝과 설정을 수동 GUI가 아닌 기계가 읽을 수 있는 선언적 코드로 정의하고 관리하는 기술 프랙티스다.
> 2. **가치**: 인프라 구축의 속도와 재현성을 보장하고, 인프라 코드 자체를 Git으로 버전 관리하여 변경 추적, 리뷰, 롤백이 가능한 인프라 형상 관리를 실현한다.
> 3. **판단 포인트**: 프로비저닝에 특화된 선언형 도구(Terraform)와 서버 내부 설정에 특화된 절차형/구성관리 도구(Ansible)를 목적에 맞게 분리 결합해야 한다.

## 출제 의도 및 답안 포인트

| 출제 의도 | 반드시 짚을 핵심 | 감점 회피 포인트 |
|:---|:---|:---|
| 클라우드 인프라 자동화 및 DevOps 역량 이해 | 코드로 관리(Version Control), 멱등성(Idempotency), 선언형 모델 | IaC를 단순 자동화 쉘 스크립트로 묘사 |
| IaC 아키텍처 생태계 및 도구 트레이드오프 파악 | 프로비저닝 도구(Terraform) vs 구성 관리 도구(Ansible) 역할 비교 | 불변 인프라 원칙과 IaC 적용의 연결점 누락 |

> 요약: 인프라가 소프트웨어 개발 주기에 통합되었음을 명시하고, 멱등성과 선언적 설계가 가져오는 운영 패러다임의 변화를 서술해야 한다.

## Ⅰ. 개요 및 필요성

- 개요: 수동 프로세스 대신 스크립트 및 선언형 코드를 사용하여 데이터센터 컴퓨터 시스템, 클라우드 자원을 프로비저닝하고 관리하는 접근 방식
- 배경: 클라우드 인스턴스가 기하급수적으로 늘어나며 수작업 콘솔 기반 설정은 휴먼 에러 유발 및 재해 복구 시 재현 불가능성 노출
- 필요성: 인프라 배포의 반복 가능성(재현성) 확보, 멱등성 기반 상태 일치, 인프라 변경 이력의 버전 통제(Version Control)

---

## Ⅱ. 구조 및 구성요소

```text
개발자 -> IaC 코드(선언형) 작성 -> Git (버전 관리/리뷰) -> CI/CD 파이프라인 연동
                                                    |
                                         IaC 엔진 (Terraform/Ansible) -> [상태 파일 비교]
                                                    | (API 호출)
                                   클라우드 프로바이더 (AWS, GCP, Azure 등)
```

| 구성요소 | 역할 | 특이사항 |
|:---|:---|:---|
| IaC 템플릿 코드 | 인프라의 최종 형상(Desired State)을 기술한 소스 파일 | HCL(Terraform), YAML/JSON 문법 |
| Source Control (Git) | 인프라 코드의 변경 이력 추적 및 협업(리뷰) 기반 제공 | GitOps 진화의 핵심 기반 |
| State File (상태 파일) | 이전에 배포된 실제 인프라의 현재 상태 매핑 정보 기록 | 현재 상태와 코드의 Diff 계산 원천 |
| Provisioning Engine | 코드를 파싱하여 클라우드 벤더 API로 변환 후 멱등성 적용 실행 | Terraform Provider 플러그인 생태계 |

> 요약: 사람이 코드를 짜서 버전 관리에 올리면, 엔진이 상태 파일을 대조하여 클라우드 API로 변경분만 동기화한다.

---

## Ⅲ. 동작원리 및 흐름도

```text
인프라 코드 수정 커밋 -> 상태(State) 비교(Plan) -> 델타(Diff) 도출 -> 프로비저닝 실행(Apply) -> 인프라 형상 일치
```

- 1단계 [코드화 및 검토]: 개발자가 HCL 코드로 변경 사항 작성 후 PR(Pull Request) 리뷰 진행
- 2단계 [계획 수립(Plan)]: IaC 엔진이 현재 배포된 인프라 상태 파일(State)과 코드를 대조하여 변경분(추가/삭제/수정) 계산
- 3단계 [실행(Apply) 및 멱등성 확인]: 계산된 변경분만 벤더 API를 통해 프로비저닝 (중복 실행 시에도 결과 동일)
- 4단계 [상태 동기화]: 완료 후 실제 인프라 상태를 State 파일에 업데이트하여 차기 기준점으로 삼음

> 요약: 스크립트처럼 무조건 순차 실행하는 것이 아니라, 목표 상태와 현재 상태의 차이(Diff)를 계산해 필요한 조치만 수행한다.

---

## Ⅳ. 특징
- 멱등성(Idempotency): 수십 번 스크립트를 재실행해도 서버가 무한 증식하지 않고, 코드로 선언한 정확한 개수와 상태만 100% 보장 유지
- 재사용 및 템플릿화: 잘 짜인 VPC, 네트워크 코드를 모듈(Module)화하여 개발/QA/운영 환경에 변수만 교체해 즉시 복제(Spin-up) 가능
- 인프라 가시성 및 문서화: 코드가 곧 최신 상태의 인프라 명세서(Living Documentation)로 기능하여 숨겨진 섀도우 IT 및 설정 누락 원천 차단

> 요약: 인프라가 논리적 소프트웨어 파일로 전환되면서 복제성, 투명성, 멱등성이라는 강력한 무기를 얻는다.

## Ⅴ. 심화 비교 및 적용 판단

| 비교 축 | 선언형 (Declarative) 프로비저닝 | 명령형 (Imperative) 구성 관리 | 선택 기준 |
|:---|:---|:---|:---|
| 핵심 개념 | "무엇(What)을 원하는지 명시" | "어떻게(How) 할지 절차 명시" | 수행하려는 인프라 단계 |
| 주요 용도 | 서버 생성, 네트워크, 인프라 뼈대 구축 | 띄워진 서버 내부 OS 설정, 앱 배포 패치 | 타겟 자원 (인프라 외곽 vs OS 내부) |
| 대표 도구 | Terraform, AWS CloudFormation | Ansible, Chef, Puppet | 멱등성 통제 방식 |
| 상태 관리 | 상태 파일(State) 의존성 강함 | 상대적으로 상태 의존성 낮음 | 관리 복잡도 수용 여부 |

> 요약: 최적의 조합은 Terraform(선언형)으로 클라우드 인프라 골조를 세우고, Ansible(명령형/절차형)로 내부 소프트웨어를 구성하는 하이브리드 방식이다.

**리스크·대응 (기본은 불릿):**
- 수동 변경 충돌(Drift): 급하다고 클라우드 콘솔 창에서 마우스로 리소스를 직접 수정 시 IaC 코드와 불일치 발생 → 콘솔 권한 강등 및 주기적 상태 Drift 탐지/강제 리셋 정책(Reconcile) 적용 (지표: 인프라 Drift 탐지 건수)
- 상태 파일(State File) 오염: 다수 개발자 동시 작업 시 상태 파일 충돌 및 민감 정보 노출 → S3 원격 저장 및 DynamoDB Lock(잠금 매커니즘) 구성, 암호화 적용 (지표: State Lock 충돌 발생률)

## Ⅵ. 실무 적용 및 결론

**적용 방안 3개:**
1. GitOps 아키텍처 연동: IaC 코드를 Git에 올리는 순간 CI/CD 파이프라인(ArgoCD, GitHub Actions)이 트리거되어 인프라 배포를 100% 자동화, 휴먼 터치 차단
2. 보안 규칙 정적 분석 통합 (Shift-Left): 코드가 배포되기 전 `tfsec`, `Checkov` 같은 SAST 도구를 파이프라인에 넣어 방화벽이나 S3 퍼블릭 권한 누수 취약점 사전 차단
3. 벤더 종속성(Lock-in) 방어: AWS CloudFormation 대신 멀티 클라우드(AWS, GCP, Azure) API를 모두 지원하는 Terraform을 표준 프로비저닝 도구로 채택하여 클라우드 유연성 확보

**결론:**
- 기술사 판단: IaC는 클라우드 네이티브의 기본 전제조건이며, '서버 생성 스크립트 작성' 수준을 넘어 애플리케이션처럼 인프라 코드를 테스트하고 리뷰하는 문화가 필수다.
- 향후 방향: 최근에는 HCL/YAML 같은 정적 설정 언어를 넘어, TypeScript나 Python 같은 범용 프로그래밍 언어로 인프라 논리를 더 복잡하게 짤 수 있는 Pulumi, AWS CDK 형태(Infra as Software)로 발전하고 있다.
