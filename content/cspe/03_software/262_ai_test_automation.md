# 📖 【암기용】 개념 완전 이해

> 목적: AI 기반 테스트 자동화를 처음 봐도 이해하게 만든다. 시험 답안 양식이 아니라, 이해를 위한 설명이다.

## 한눈에
- **개요**: AI로 테스트 케이스 생성, 우선순위화, 실행 분석, 결함 예측을 자동화하는 방식
- **왜 필요한가**: 릴리스 주기가 짧아지면 사람이 모든 회귀 테스트를 설계·선별하기 어렵다. AI는 변경 코드, 로그, 과거 결함을 보고 위험 높은 테스트부터 실행한다.
- **핵심 직관**: 전체 시험지를 매번 푸는 대신, 최근 틀린 단원과 바뀐 단원 중심으로 시험 범위를 고르는 방식이다.

## 깊이 이해
- **배경·문제의식**: MSA, 모바일, SaaS는 배포가 하루 여러 번 발생한다. 수동 테스트와 고정 회귀팩은 실행 시간이 길고, 변경 영향 없는 테스트까지 반복한다.
- **작동 원리**: 요구사항·코드 변경·커버리지·결함 이력을 입력으로 테스트를 생성하고, 위험 점수로 실행 순서를 정한다. 실행 후 실패 로그를 묶어 원인을 추천하고 결함 티켓을 만든다.
- **비유**: 병원 triage처럼 모든 환자를 같은 순서로 보지 않고, 증상과 위험도를 기준으로 검사 순서를 정한다.
- **구체 예시**: 결제 모듈 12개 파일 변경 시 결제 API, 쿠폰, 환불 E2E를 우선 실행하고, 검색 UI 테스트는 뒤로 미룬다. 실패율 30% 이상 테스트는 flaky 후보로 분리한다.
- **흔한 오해·주의점**: AI가 테스트를 대신하더라도 기대 결과, 품질 기준, 릴리스 승인 책임은 테스트 리더와 개발 조직에 남는다.

## 연결 개념
- CI/CD - 커밋·PR·배포 파이프라인에 테스트 자동화 배치
- TDD/BDD - 요구사항을 테스트 표현으로 바꾸는 기반
- Flaky Test 관리 - 실패 원인 분류와 신뢰도 관리

# 📝 【답안용】 시험 답안 템플릿

> 목적: 시험장에서 25분에 그대로 쓰는 답안 양식. 작성방식(추상표현 금지·수치·도식·문제유형 전환)을 엄격히 지킨다.
> 핵심: AI 테스트 자동화는 테스트 생성 도구가 아니라 위험 기반 품질 게이트로 설명해야 한다.

## 핵심 인사이트 (3줄 요약)

> 1. **본질**: AI 기반 테스트 자동화는 요구사항·코드 변경·결함 이력을 학습해 테스트 생성, 선별, 실행, 실패 분석을 자동화하는 품질 체계이다.
> 2. **가치**: 회귀 테스트 시간을 120분에서 30분으로 줄이는 것이 목표가 아니라, 변경 영향 영역 결함을 릴리스 전 탐지하는 것이 목표이다.
> 3. **판단 포인트**: 커버리지, 결함 검출률, flaky 비율, MTTR, false positive 비율로 도입 효과를 판단한다.

## 출제 의도 및 답안 포인트

| 출제 의도 | 반드시 짚을 핵심 | 감점 회피 포인트 |
|:---|:---|:---|
| SW 품질 자동화 이해 확인 | 테스트 생성, 우선순위화, 실패 분석, 결함 예측 | AI 도구명만 나열 |
| CI/CD 적용 설계 확인 | PR 테스트, 야간 회귀, 릴리스 게이트 | 단위 테스트와 E2E 테스트 구분 누락 |
| 품질 지표 판단 확인 | 커버리지, 결함 검출률, flaky, false positive | 실행 시간 단축만 강조 |

> 요약: 이 문제는 테스트 자동 생성보다 위험 기반 품질 통제 구조와 측정 지표를 요구한다.

---

## Ⅰ. 개요 및 필요성

- 개요: AI 기반 테스트 자동화는 AI로 테스트 설계·실행·분석을 지원하는 기술이다.
- 배경: 배포 주기 단축, 회귀 범위 확대, 테스트 데이터 복잡도 증가로 수동 선별 방식은 릴리스 속도를 따라가기 어렵다.
- 필요성: 변경 영향 기반 테스트와 결함 예측을 결합해 제한된 테스트 시간 안에서 품질 위험을 선별해야 한다.

---

## Ⅱ. 구조 및 구성요소

```text
Requirement/Code/Defect History -> AI Test Model -> Test Generation
                                -> Prioritization -> CI Execution -> Defect Analysis
```

| 구성요소 | 역할 | 특이사항 |
|:---|:---|:---|
| 입력 데이터 | 요구사항, 코드 diff, 커버리지, 결함 이력 수집 | 데이터 품질이 추천 품질을 좌우 |
| 테스트 생성기 | 단위·API·E2E 테스트 후보 생성 | 기대 결과와 경계값 검증 필요 |
| 우선순위 엔진 | 위험 점수 기반 실행 순서 결정 | 변경 영향, 결함 빈도, 업무 영향 반영 |
| 분석·리포팅 | 실패 로그 군집화, 원인 후보 제시 | flaky 테스트 분리 필요 |

> 요약: AI 테스트 자동화는 데이터 입력, 테스트 생성, 위험 기반 선별, 실패 분석으로 구성된다.

---

## Ⅲ. 동작원리 및 흐름도

```text
변경 감지 -> 영향 범위 분석 -> 테스트 후보 생성 -> 위험 점수 산정
-> CI 실행 -> 실패 군집화 -> 결함 티켓/릴리스 판단
```

| 단계 | 처리 내용 | 검증 기준 |
|:---:|:---|:---|
| 1 | 코드 diff와 요구사항 연결 | 요구사항-테스트 추적률 90% 이상 |
| 2 | 테스트 후보 생성 | 경계값, 예외, 권한 케이스 포함 |
| 3 | 위험 기반 실행 | 결함 빈도 상위 20% 모듈 우선 |
| 4 | 결과 분석 | flaky 비율 5% 이하, false positive 추적 |

> 요약: 변경 영향 분석으로 테스트 범위를 줄이고, 실패 분석으로 릴리스 판단 근거를 만든다.

---

## Ⅳ. 특징

| 구분 | 기존 테스트 자동화 | AI 기반 테스트 자동화 | 판단 포인트 |
|:---|:---|:---|:---|
| 테스트 설계 | 사람이 케이스 작성 | 요구사항·코드 기반 후보 생성 | 생성 테스트 승인율 |
| 실행 전략 | 전체 회귀팩 반복 | 위험 점수 기반 선별 | 회귀 시간, 결함 검출률 |
| 실패 분석 | 로그 수동 확인 | 유사 실패 군집화 | MTTR, 중복 티켓 감소 |
| 한계 | 자동화 범위 고정 | 모델 추천 오류 가능 | false positive/negative 관리 |

> 요약: AI 기반 방식은 테스트를 많이 실행하는 방식이 아니라 위험 높은 영역을 먼저 검증하는 방식이다.

## Ⅴ. 심화 비교 및 적용 판단

| 비교 축 | 기존/대안 | 본 키워드 | 선택 기준 |
|:---|:---|:---|:---|
| 구조 | 스크립트 기반 자동화 | AI 추천+CI 게이트 | 릴리스 빈도 주 1회 이상 |
| 비용/성능 | 전체 회귀 120분 | 위험 기반 30분 목표 | 결함 검출률 90% 이상 유지 |
| 운영/위험 | 테스트 노후화 | 생성 테스트 검토 필요 | flaky 5% 이하 관리 |

> 요약: 배포 빈도와 테스트 시간이 충돌할 때 AI 기반 선별과 실패 분석을 적용한다.

| 리스크 | 원인 | 대응 방안 | 확인 지표 |
|:---|:---|:---|:---|
| 누락 결함 | 영향 분석 오류 | 코드 소유자 리뷰, mutation test | escaped defect 건수 |
| flaky 증가 | 비결정적 테스트 데이터 | 격리 DB, 시간 의존 제거 | flaky rate 5% 이하 |
| 과잉 차단 | false positive | 신뢰도 점수, 수동 승인 경로 | false positive 10% 이하 |

> 요약: AI 테스트의 위험은 누락, flaky, 과잉 차단이며 품질 지표로 지속 조정해야 한다.

| 점검 항목 | 목표 기준 | 측정 방법 |
|:---|:---|:---|
| 커버리지 | 핵심 도메인 branch 80% 이상 | JaCoCo, Istanbul |
| 결함 검출 | 릴리스 전 결함 검출률 90% 이상 | 결함 관리 시스템 |
| 실행 시간 | PR 게이트 15분 이하 | CI 실행 로그 |

> 요약: 도입 효과는 커버리지, 결함 검출률, PR 게이트 시간으로 판정한다.

## Ⅵ. 실무 적용 및 결론

**적용 방안 3개 (필수 - 단계별 또는 항목별):**
1. PR 단계: 코드 diff 기반 단위·API 테스트를 15분 이내 실행하고 실패 시 병합 차단
2. 야간 단계: AI 생성 E2E와 전체 회귀를 실행해 결함 빈도 상위 모듈 리스크 점수 갱신
3. 운영 단계: 장애·고객 문의를 테스트 케이스로 환류하고 escaped defect를 월 단위 추적

**결론 (2줄):**
- 기술사 판단: 배포 빈도가 낮고 도메인이 단순하면 기존 자동화, 다중 서비스·일 배포 환경이면 AI 기반 위험 선별을 채택함
- 향후 방향: AI 테스트 자동화는 요구사항 추적, 코드 분석, 운영 장애 데이터를 연결한 품질 게이트로 발전함
