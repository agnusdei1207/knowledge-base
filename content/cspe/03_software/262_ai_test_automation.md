# 📖 【암기용】 개념 완전 이해

> 목적: AI 기반 테스트 자동화를 처음 봐도 이해하게 만든다. 시험 답안 양식이 아니라, 이해를 위한 설명이다.

## 한눈에
- **개요**: AI 기반 테스트 자동화는 **위험 기반 테스트(Risk-Based Testing)**를 AI로 확장한 것으로, 요구사항·코드 변경·결함 이력을 학습해 테스트 생성·우선순위화·실행·실패 분석을 자동화하는 품질 보증 기법이다.
- **왜 필요한가**: 릴리스 주기가 하루 여러 번으로 짧아지면 사람이 모든 회귀 테스트를 매번 설계·선별하기 어렵다. AI는 변경된 코드, 과거 결함 이력, 실행 로그를 근거로 위험이 큰 영역의 테스트부터 실행 순서를 정해준다.
- **핵심 직관**: 전체 시험 범위를 매번 다 푸는 대신, 최근 틀린 단원과 새로 바뀐 단원 중심으로 시험 범위를 추려서 공부하는 것과 같다.

## 핵심 용어 정리 (내부에 등장하는 것들)

| 용어 | 의미 | 비유 |
|:---|:---|:---|
| 위험 기반 테스트(Risk-Based Testing) | 모든 테스트를 균등하게 실행하지 않고, 결함 발생 가능성과 업무 영향도가 큰 영역을 우선 검증하는 전략 | 전수 검사 대신 불량률 높은 라인부터 집중 검사하는 것 |
| 회귀 테스트(Regression Test) | 코드가 변경된 뒤 기존 기능이 여전히 정상 동작하는지 재확인하는 테스트 묶음 | 리모델링 후 기존 배관·전기가 멀쩡한지 다시 점검하는 것 |
| 위험 점수(Risk Score) | 변경 크기, 과거 결함 빈도, 업무(매출) 영향도를 가중합해 테스트 우선순위를 매기는 지표 | 환자 분류표(triage score) |
| Flaky Test | 코드 변경 없이 같은 테스트를 반복 실행해도 성공/실패가 들쭉날쭉한 비결정적 테스트 | 같은 문제를 풀 때마다 답이 오락가락하는 불안정한 채점자 |
| False Positive / False Negative | 정상인데 실패로 잘못 보고(양성 오탐) / 결함이 있는데 통과로 잘못 보고(음성 누락) | 화재경보기가 헛울림(오탐)하거나, 실제 화재에도 안 울리는 것(누락) |
| Escaped Defect | 테스트 단계를 통과해 실제 운영(릴리스)까지 새어나간 결함 | 검수를 통과하고 나서야 발견되는 하자 |
| MTTR (Mean Time To Repair/Resolve) | 결함이 발견된 후 수정 완료까지 걸리는 평균 시간 | 고장 신고 후 수리가 끝나기까지 걸리는 평균 시간 |
| Mutation Test(변이 테스트) | 코드에 일부러 작은 결함(변이)을 주입해, 기존 테스트가 그 결함을 잡아내는지로 테스트 자체의 품질을 검증하는 기법 | 가짜 화재를 일부러 내서 화재경보기가 제대로 울리는지 점검하는 것 |
| Branch Coverage | 코드의 조건 분기(if/else 등)가 테스트로 얼마나 실행됐는지의 비율 | 갈림길이 있는 미로에서 몇 갈래 길을 실제로 다 가봤는지 |

## 깊이 이해

### 배경 — 왜 전체 회귀팩을 매번 돌릴 수 없는가
MSA·모바일·SaaS 환경은 하루에도 여러 번 배포한다. 전체 회귀팩을 매번 처음부터 끝까지 실행하면 시간이 오래 걸리고(예: 120분), 그중 상당수는 이번 변경과 아무 관련 없는 영역까지 반복 검증하는 낭비다. 배포 속도와 테스트 커버리지가 충돌하는 지점에서, "이번 변경이 영향을 줄 만한 영역"만 골라 먼저 검증하려는 필요가 생긴다.

### 위험 점수는 어떻게 계산되는가 — 워크드 예시
위험 점수는 보통 세 요소의 가중합으로 계산한다: ① 변경 크기(변경된 파일 수·라인 수), ② 해당 모듈의 최근 결함 빈도(최근 3개월 결함 건수), ③ 업무 영향도(매출·트래픽 기여도). 예를 들어 결제 모듈이 최근 3개월간 결함 8건으로 검색 UI 모듈(결함 1건)보다 8배 많고, 매출 기여도가 3배 높다면, 결제 모듈에 연결된 테스트가 검색 UI 테스트보다 훨씬 높은 위험 점수를 받아 먼저 실행된다. 실제 사례: 결제 모듈 12개 파일이 변경되면 결제 API·쿠폰·환불 E2E 테스트를 최우선으로 실행하고, 이번 변경과 무관한 검색 UI 테스트는 야간 배치로 미룬다.

### 회귀 시간이 줄어드는 원리 — 수치로 보기
전체 회귀 120분 중, diff 분석으로 이번 변경과 무관한 테스트를 제외하면 실행해야 할 테스트가 크게 줄어든다. 예: 전체 테스트 2,000개 중 이번 변경이 실제로 영향을 주는 모듈에 걸린 테스트가 450개(약 22%)라면, 그 부분만 우선 실행해 PR 게이트를 15분 안에 끝내고, 나머지 전체 회귀는 야간에 별도로 돌려 결함 검출률을 보완한다. "빠르게, 그러나 놓치지 않게"를 위해 PR 단계(속도)와 야간 단계(전수)를 분리하는 것이 핵심이다.

### Flaky Test는 어떻게 판별하는가
같은 커밋을 여러 번(예: 10회) 반복 실행했을 때 성공/실패가 왔다 갔다 하면 비결정적이라는 뜻이다. 예: 어떤 테스트가 10회 중 3회 실패했다면 실패율 30%이고, 이는 코드 결함이 아니라 테스트 자체의 불안정성(시간 의존, 공유 DB 상태, 네트워크 타이밍)일 가능성이 크다. 실패율이 임계치(예: 30%) 이상이면 flaky 후보로 분리해 별도 격리 DB나 시간 의존성 제거로 원인을 고친 뒤에야 신뢰 가능한 게이트로 되돌린다. flaky를 방치하면 "테스트 실패=결함"이라는 신뢰가 깨져 사람들이 실패를 무시하게 되는 것이 더 큰 위험이다.

### 판별 원리 — False Positive와 False Negative의 트레이드오프
위험 기반 선별은 두 가지 실수를 할 수 있다. 위험도를 과대평가해 실제로는 안전한 변경까지 계속 차단하면 false positive가 늘어 개발 속도가 떨어지고, 반대로 위험도를 과소평가해 실제 결함이 있는 변경을 통과시키면 escaped defect(false negative)가 늘어 운영 장애로 이어진다. 그래서 이 둘을 각각 지표로 추적한다 — false positive는 "차단됐지만 나중에 문제없었던 비율"로, escaped defect는 "릴리스 이후 발견된 결함 수"로 측정하며, mutation test로 테스트 스위트 자체가 결함을 실제로 잡아낼 능력이 있는지도 주기적으로 검증한다.

### 비유와 흔한 오해
- **비유**: 병원 triage처럼 모든 환자를 같은 순서로 보지 않고, 증상과 위험도를 기준으로 검사 순서를 정하는 것과 같다.
- **오해**: "AI가 테스트를 대신하니 테스트 리더가 필요 없다" — 틀렸다. AI는 후보 생성과 우선순위 제안까지만 하고, 기대 결과의 타당성, 품질 기준, 최종 릴리스 승인의 책임은 여전히 테스트 리더와 개발 조직에 남는다. AI가 생성한 테스트도 사람이 승인율을 관리해야 신뢰할 수 있다.

## 연결 개념
- CI/CD: 커밋·PR·배포 파이프라인 각 단계에 위험 기반 테스트를 배치하는 실행 환경
- TDD/BDD: 요구사항을 테스트로 표현하는 기반 방법론 — AI 생성 테스트도 이 표현 형식을 따른다
- Flaky Test 관리: 실패 원인을 결함/비결정성으로 분류하고 테스트 신뢰도를 유지하는 운영 활동

# 📝 【답안용】 시험 답안 템플릿

> 목적: 시험장에서 25분에 그대로 쓰는 답안 양식. 작성방식(추상표현 금지·수치·도식·문제유형 전환)을 엄격히 지킨다.
> 핵심: AI 테스트 자동화는 테스트 생성 도구가 아니라 위험 기반 품질 게이트로 설명해야 한다.

## 핵심 인사이트 (3줄 요약)

> 1. **본질**: AI 기반 테스트 자동화는 요구사항·코드 변경·결함 이력을 학습해 테스트 생성, 선별, 실행, 실패 분석을 자동화하는 품질 체계이다.
> 2. **가치**: 회귀 테스트 시간을 120분에서 30분으로 줄이는 것이 목표가 아니라, 변경 영향 영역 결함을 릴리스 전 탐지하는 것이 목표이다.
> 3. **판단 포인트**: 커버리지, 결함 검출률, flaky 비율, MTTR, false positive 비율로 도입 효과를 판단한다.

## 출제 의도 및 답안 포인트

| 출제 의도 | 반드시 짚을 핵심 | 감점 회피 포인트 |
|:---|:---|:---|
| SW 품질 자동화 이해 확인 | 테스트 생성, 우선순위화, 실패 분석, 결함 예측 | AI 도구명만 나열 |
| CI/CD 적용 설계 확인 | PR 테스트, 야간 회귀, 릴리스 게이트 | 단위 테스트와 E2E 테스트 구분 누락 |
| 품질 지표 판단 확인 | 커버리지, 결함 검출률, flaky, false positive | 실행 시간 단축만 강조 |

> 요약: 이 문제는 테스트 자동 생성보다 위험 기반 품질 통제 구조와 측정 지표를 요구한다.

## Ⅰ. 개요 및 필요성

- 개요: AI 기반 테스트 자동화는 AI로 테스트 설계·실행·분석을 지원하는 기술이다.
- 배경: 배포 주기 단축, 회귀 범위 확대, 테스트 데이터 복잡도 증가로 수동 선별 방식은 릴리스 속도를 따라가기 어렵다.
- 필요성: 변경 영향 기반 테스트와 결함 예측을 결합해 제한된 테스트 시간 안에서 품질 위험을 선별해야 한다.

---

## Ⅱ. 구조 및 구성요소

```text
Requirement/Code/Defect History -> AI Test Model -> Test Generation
                                -> Prioritization -> CI Execution -> Defect Analysis
```

| 구성요소 | 역할 | 특이사항 |
|:---|:---|:---|
| 입력 데이터 | 요구사항, 코드 diff, 커버리지, 결함 이력 수집 | 데이터 품질이 추천 품질을 좌우 |
| 테스트 생성기 | 단위·API·E2E 테스트 후보 생성 | 기대 결과와 경계값 검증 필요 |
| 우선순위 엔진 | 위험 점수 기반 실행 순서 결정 | 변경 영향, 결함 빈도, 업무 영향 반영 |
| 분석·리포팅 | 실패 로그 군집화, 원인 후보 제시 | flaky 테스트 분리 필요 |

> 요약: AI 테스트 자동화는 데이터 입력, 테스트 생성, 위험 기반 선별, 실패 분석으로 구성된다.

---

## Ⅲ. 동작원리 및 흐름도

```text
변경 감지 -> 영향 범위 분석 -> 테스트 후보 생성 -> 위험 점수 산정
-> CI 실행 -> 실패 군집화 -> 결함 티켓/릴리스 판단
```

| 단계 | 처리 내용 | 검증 기준 |
|:---:|:---|:---|
| 1 | 코드 diff와 요구사항 연결 | 요구사항-테스트 추적률 90% 이상 |
| 2 | 테스트 후보 생성 | 경계값, 예외, 권한 케이스 포함 |
| 3 | 위험 기반 실행 | 결함 빈도 상위 20% 모듈 우선 |
| 4 | 결과 분석 | flaky 비율 5% 이하, false positive 추적 |

> 요약: 변경 영향 분석으로 테스트 범위를 줄이고, 실패 분석으로 릴리스 판단 근거를 만든다.

## Ⅳ. 특징

| 구분 | 기존 테스트 자동화 | AI 기반 테스트 자동화 | 판단 포인트 |
|:---|:---|:---|:---|
| 테스트 설계 | 사람이 케이스 작성 | 요구사항·코드 기반 후보 생성 | 생성 테스트 승인율 |
| 실행 전략 | 전체 회귀팩 반복 | 위험 점수 기반 선별 | 회귀 시간, 결함 검출률 |
| 실패 분석 | 로그 수동 확인 | 유사 실패 군집화 | MTTR, 중복 티켓 감소 |
| 한계 | 자동화 범위 고정 | 모델 추천 오류 가능 | false positive/negative 관리 |

> 요약: AI 기반 방식은 테스트를 많이 실행하는 방식이 아니라 위험 높은 영역을 먼저 검증하는 방식이다.

## Ⅴ. 심화 비교 및 적용 판단

| 구분 | 기존/대안 | 본 키워드 | 선택 기준 |
|:---|:---|:---|:---|
| 구조 | 스크립트 기반 자동화 | AI 추천+CI 게이트 | 릴리스 빈도 주 1회 이상 |
| 비용/성능 | 전체 회귀 120분 | 위험 기반 30분 목표 | 결함 검출률 90% 이상 유지 |
| 운영/위험 | 테스트 노후화 | 생성 테스트 검토 필요 | flaky 5% 이하 관리 |

> 요약: 배포 빈도와 테스트 시간이 충돌할 때 AI 기반 선별과 실패 분석을 적용한다.

| 리스크 | 원인 | 대응 방안 | 확인 지표 |
|:---|:---|:---|:---|
| 누락 결함 | 영향 분석 오류 | 코드 소유자 리뷰, mutation test | escaped defect 건수 |
| flaky 증가 | 비결정적 테스트 데이터 | 격리 DB, 시간 의존 제거 | flaky rate 5% 이하 |
| 과잉 차단 | false positive | 신뢰도 점수, 수동 승인 경로 | false positive 10% 이하 |

> 요약: AI 테스트의 위험은 누락, flaky, 과잉 차단이며 품질 지표로 지속 조정해야 한다.

| 점검 항목 | 목표 기준 | 측정 방법 |
|:---|:---|:---|
| 커버리지 | 핵심 도메인 branch 80% 이상 | JaCoCo, Istanbul |
| 결함 검출 | 릴리스 전 결함 검출률 90% 이상 | 결함 관리 시스템 |
| 실행 시간 | PR 게이트 15분 이하 | CI 실행 로그 |

> 요약: 도입 효과는 커버리지, 결함 검출률, PR 게이트 시간으로 판정한다.

## Ⅵ. 실무 적용 및 결론

**적용 방안 3개 (필수 - 단계별 또는 항목별):**
1. PR 단계: 코드 diff 기반 단위·API 테스트를 15분 이내 실행하고 실패 시 병합 차단
2. 야간 단계: AI 생성 E2E와 전체 회귀를 실행해 결함 빈도 상위 모듈 리스크 점수 갱신
3. 운영 단계: 장애·고객 문의를 테스트 케이스로 환류하고 escaped defect를 월 단위 추적

**결론 (2줄):**
- 기술사 판단: 배포 빈도가 낮고 도메인이 단순하면 기존 자동화, 다중 서비스·일 배포 환경이면 AI 기반 위험 선별을 채택함
- 향후 방향: AI 테스트 자동화는 요구사항 추적, 코드 분석, 운영 장애 데이터를 연결한 품질 게이트로 발전함
