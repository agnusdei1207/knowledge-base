# 📖 【암기용】 개념 완전 이해

## 한눈에
- **개요**: 데이터가 여러 서버(노드)에 복제되어 있을 때, 클라이언트가 데이터를 읽고 쓸 때 얼마나 "정확하고 동일한(최신) 데이터"를 보장받을 수 있는지를 정의한 룰(계약)
- **왜 필요한가**: 모든 노드를 실시간 동기화(강한 일관성)하면 시스템이 너무 느려진다. 반대로 동기화를 늦추면(약한 일관성) 낡은 데이터를 읽게 된다. 성능(지연시간)과 데이터 정확성 사이의 타협점을 정하기 위해 필요하다.
- **핵심 직관**: 은행 계좌 잔고는 0.1초라도 틀리면 안 되므로 무조건 '강한 일관성'을 써야 하고, 인스타그램 좋아요 숫자는 방금 누른 게 남한테 1초 뒤에 보여도 상관없으므로 '최종 일관성'을 쓰는 식이다.

## 핵심 용어 정리

| 용어/표기 | 의미 | 비유·예 |
|:---|:---|:---|
| Strong Consistency (강한 일관성) | 쓰기가 완료된 직후 어떤 노드에서 읽어도 반드시 최신 값을 반환 | 통장 잔고 갱신 (전 지점 동기화 대기) |
| Eventual Consistency (최종 일관성) | 시간이 지나면(언젠가는) 모든 노드가 동일한 최신 상태에 도달함을 보장 | SNS 피드, DNS 전파 (당장은 옛날값 보일 수 있음) |
| Causal Consistency (인과적 일관성) | 인과 관계가 있는 작업 순서는 모든 노드에서 동일하게 보장 | 댓글(원인)과 대댓글(결과)의 순서 |
| CAP 정리 (CAP Theorem) | 일관성(C), 가용성(A), 분할 내성(P) 중 최대 2개만 선택 가능함 | 완벽한 삼각형을 만들 수 없다는 법칙 |

## 깊이 이해
- **배경·문제의식**: 단일 DB 시대에는 트랜잭션(ACID)만 있으면 데이터가 완벽했다. 하지만 클라우드 시대에 전 세계에 서버를 분산 복제(Replication)하면서 문제가 생겼다. 미국 서버에 "비밀번호 변경"을 저장했는데, 한국 서버로 동기화되기 전(0.5초)에 한국 서버에 로그인을 시도하면 옛날 비밀번호를 읽게 되는 데이터 불일치(Stale Data)가 발생한다.
- **작동 원리**: 
  - **강한 일관성**: 클라이언트가 값을 쓰면, 리더 노드는 모든 팔로워 노드에 데이터를 복제하고(완료 응답을 모두 받은 후) 클라이언트에 "성공"을 반환한다. (매우 느리나 정확함)
  - **최종 일관성**: 리더 노드가 자기 디스크에만 쓰고 즉시 클라이언트에 "성공"을 반환한 뒤, 뒤에서 비동기로 팔로워들에게 데이터를 흩뿌린다. (매우 빠르나 일시적 불일치 발생)
- **비유**: 
  - 강한 일관성: 반장(리더)이 공지사항을 반 전체 30명에게 일일이 확인 서명을 받은 뒤에야 조회를 끝낸다.
  - 최종 일관성: 반장이 칠판에 공지를 적어두고 종례를 끝낸다. 애들이 집에 가다보면 '언젠가는' 소문이 다 퍼지겠지 하는 방식이다.
- **구체 예시**: 분산 데이터베이스인 Cassandra는 클라이언트가 직접 'Consistency Level'을 지정할 수 있다. 쓰기/읽기 시 몇 대의 노드에서 확인을 받을지(예: QUORUM, ALL, ONE) 설정하여 강한/약한 일관성을 조율한다.
- **흔한 오해·주의점**: "최종 일관성은 데이터가 유실된다는 뜻이다"는 오해다. 유실(Data Loss)이 아니라, 데이터 복제 지연(Replication Lag) 때문에 일시적으로 낡은(Stale) 버전을 읽을 수 있다는 뜻이지 언젠가는 반드시 최신 상태로 수렴한다.

## 연결 개념
- **CAP 정리 & PACELC 정리**: 분산 시스템에서 네트워크 단절(P) 시 일관성(C)과 가용성(A)의 트레이드오프를 수식화한 이론
- **분산 합의 (Consensus)**: 다수의 노드가 장애 속에서도 강한 일관성을 유지하기 위해 하나의 값에 동의하는 알고리즘 (Raft, Paxos)
- **Quorum (쿼럼)**: 데이터 읽기/쓰기 시 정족수(과반수 등)를 만족해야 성공으로 인정하여 일관성을 조율하는 기법

# 📝 【답안용】 시험 답안 템플릿

## 핵심 인사이트 (3줄 요약)

> 1. **본질**: 분산 저장소에서 데이터 복제 지연(Replication Lag) 발생 시, 클라이언트의 읽기/쓰기 작업에 대해 데이터의 정확도와 동기화 시점을 보장하는 규약이다.
> 2. **가치**: 비즈니스 도메인의 특성에 맞춰 엄격한 데이터 정합성(금융)과 초고속 응답성/가용성(SNS, 캐시) 사이의 아키텍처적 타협점(Trade-off)을 제공한다.
> 3. **판단 포인트**: 단일 일관성 모델을 강요하지 않고, CAP 정리와 PACELC 정리에 따라 마이크로서비스별 또는 트랜잭션별로 강한 일관성과 최종 일관성을 혼합(Polyglot) 구성해야 한다.

## 출제 의도 및 답안 포인트

| 출제 의도 | 반드시 짚을 핵심 | 감점 회피 포인트 |
|:---|:---|:---|
| 분산 환경에서 일관성이 깨지는 원리 | 데이터 복제 지연, 네트워크 파티션, 비동기 통신 | 단일 DB의 트랜잭션(ACID) 고립성 문제로 오답 기재 |
| 연속적인 일관성 모델 스펙트럼 인지 | Strong, Causal, Read-your-writes, Eventual | 강한 일관성 vs 최종 일관성 2분법으로만 극단적 서술 |
| 실무 데이터베이스 설정 방안 | Quorum 조율 (W + R > N), 튜너블(Tunable) 일관성 | 이론만 나열하고 실제 DB 시스템의 적용 방법 누락 |

> 요약: 이론적 분류(Strong vs Eventual)를 넘어, 클라이언트 중심의 세분화된 일관성 모델과 실제 분산 DB에서의 정족수(Quorum) 기반 조율 기법을 제시해야 한다.

## Ⅰ. 개요 및 필요성

- 개요: 다수의 노드에 데이터가 복제된 분산 시스템에서 읽기/쓰기 연산이 수행될 때 반환되는 데이터의 최신성과 정확성 보장 수준
- 배경: 클라우드 스케일아웃으로 인한 노드 간 복제 시간 지연(Latency) 및 네트워크 단절(Partition) 환경 일상화
- 필요성: 성능(가용성)과 데이터 정합성 사이의 트레이드오프를 비즈니스 요구사항에 맞춰 최적화하고 명확한 데이터 반환 계약(Contract) 수립

---

## Ⅱ. 일관성 스펙트럼 (Data-Centric Consistency)

```text
[성능/가용성 최대화]  <--------------------------------------------------> [데이터 정확성 최대화]
  Eventual             Causal            Sequential              Linearizable (Strong)
 (최종 일관성)       (인과적 일관성)      (순차적 일관성)          (선형성/강한 일관성)
  비동기 복제           원인-결과 순서 보장    모든 노드 동일 순서 관측    전역 클록 기반 즉시 갱신
```

| 일관성 모델 | 특징 | 적합한 도메인 |
|:---|:---|:---|
| Linearizable (강한 일관성) | 쓰기 성공 즉시 모든 노드에서 최신 데이터 읽기 보장 | 계좌 이체, 결제 시스템, 메타데이터 제어 |
| Sequential Consistency | 전역 시간은 무시하되, 모든 노드가 동일한 업데이트 순서를 관측 | 협업 편집 도구, 채팅 순서 |
| Causal Consistency | 인과 관계가 있는 데이터 연산의 순서를 보장 (논리적 시계 활용) | 소셜 미디어 댓글과 대댓글 |
| Eventual Consistency | 즉각적 보장은 없으나 장애가 없다면 최종적으로 동일 상태 수렴 | SNS 피드, 조회수, 상품 리뷰 |

> 요약: 강한 일관성은 결제 도메인에, 최종 일관성은 고가용성이 필요한 조회성 도메인에 적용하며, 스펙트럼 상의 다양한 중간 단계가 존재한다.

---

## Ⅲ. 일관성 조율 메커니즘 (Quorum 원리 흐름도)

```text
총 노드(N=3), 쓰기 정족수(W=2), 읽기 정족수(R=2) 설정 시 -> W + R (4) > N (3) 이면 강한 일관성 도출 가능
```

- 1단계 [설정]: 대상 복제본 수(N), 쓰기 성공으로 간주할 노드 수(W), 읽을 때 확인할 노드 수(R) 설정
- 2단계 [Write 발생]: 클라이언트가 데이터를 쓰면 W개의 복제본 노드로부터 성공(Ack) 응답을 받을 때까지 대기
- 3단계 [비동기 전파]: W개에 속하지 않은 나머지(N-W) 노드에는 백그라운드에서 비동기 복제 수행
- 4단계 [Read 발생]: R개의 노드에서 데이터를 읽어 타임스탬프가 가장 최신인 버전(버전 벡터)을 클라이언트에 반환

> 요약: $W + R > N$ 공식을 충족하도록 튜닝하면, 비동기 복제 환경(Cassandra 등)에서도 항상 최신 데이터를 읽어내는 튜너블(Tunable) 강한 일관성을 달성할 수 있다.

## Ⅳ. 특징
- CAP 정리의 현실적 제약: 분할 내성(P)이 필수인 분산망에서 강한 일관성(C)을 택하면 일부 노드 장애 시 전체 쓰기를 막아야 하므로 가용성(A)이 희생됨
- 클라이언트 중심 모델(Client-Centric): "내가 쓴 데이터는 내가 즉시 볼 수 있다(Read-your-writes)", "세션 내 단조 읽기(Monotonic Reads)" 등 사용자 경험 중심의 변형 모델 발달
- 지연시간(Latency)과의 필연적 반비례: 락(Lock)을 걸고 다수 노드의 합의를 기다릴수록 p99 응답 속도는 기하급수적으로 저하됨 (PACELC 정리)

> 요약: 완벽한 동기화는 물리적 지연과 가용성 저하를 동반하므로, 현대 아키텍처는 대부분 사용자 경험을 해치지 않는 선의 최종 일관성을 선호한다.

## Ⅴ. 심화 비교 및 적용 판단

| 비교 축 | 강한 일관성 (CP 패턴) | 최종 일관성 (AP 패턴) | 선택 기준 |
|:---|:---|:---|:---|
| 동기화 방식 | 동기식(Synchronous) 복제, 합의 알고리즘(Raft) | 비동기식(Asynchronous) 복제 | 노드 간 네트워크 지연(Latency) 허용 여부 |
| 노드 장애 시 | 합의 불가 시 쓰기 거부 (가용성 저하) | 일단 로컬에 쓰고 나중에 복구 (고가용성) | 데이터 유실/오염 리스크 vs 다운타임 비용 |
| 적용 아키텍처 | 관계형 분산 DB, Zookeeper, etcd | 분산 NoSQL(Cassandra), 메시지 큐 기반 EDA | 단일 진실 공급원(SSOT) 필요성 |

> 요약: 메타데이터 관리나 계좌 거래는 CP 시스템을 구축하여 일관성을 강제하고, 대규모 트래픽 흡수나 로그 수집은 AP 시스템을 구성한다.

**리스크·대응 (기본은 불릿):**
- Eventual Consistency 환경의 동시 업데이트 충돌: 두 클라이언트가 각기 다른 노드에서 동시 수정 시 데이터 정합성 파괴 → Vector Clock(버전 벡터) 또는 CRDT(Conflict-free Replicated Data Type) 구조를 적용하여 자동 병합
- Read-your-writes 실패: 방금 작성한 글이 새로고침 시 안 보이는 UX 결함 → Sticky Session 적용 또는 클라이언트 토큰 기반으로 최신화된 읽기 복제본(Read Replica)으로 강제 라우팅
- Split Brain 현상: 네트워크 단절 시 양쪽 파티션이 모두 리더로 승격하여 데이터 분기 발생 → 과반수(Majority) 정족수 룰(Raft 알고리즘 등)을 강제하여 소수 파티션의 쓰기를 중단시킴

**도입 후 점검 지표 (기본은 불릿):**
- 성능/효율: 읽기/쓰기 지연시간(Latency), 노드 간 복제 지연 시간(Replication Lag, 목표 < 100ms)
- 품질/운영: 동시성 충돌 발생 건수, 쿼럼(Quorum) 미달 시 실패(Timeout) 비율

## Ⅵ. 실무 적용 및 결론

**적용 방안 3개:**
1. Tunable Consistency 아키텍처 설계: Cassandra나 Cosmos DB 적용 시, 계정 설정 등 중요 트랜잭션은 `Consistency=STRONG(Quorum)`으로 읽고, 로그/피드는 `EVENTUAL(One)`로 읽도록 애플리케이션 레벨 분기
2. Saga 패턴 기반 최종 일관성 달성: MSA 간 분산 트랜잭션 시 2PC(Two-Phase Commit) 대신, 비동기 이벤트 발행(Kafka)과 보상 트랜잭션을 통해 시스템 전체의 결과적 정합성 보장
3. CRDT 기반 충돌 없는 동기화: 동시 편집 문서(구글 닥스)나 분산 카트 도메인에서 네트워크 파티션 중의 오프라인 쓰기를 허용하고, 복구 시 CRDT 알고리즘(Redis Enterprise 등)으로 수학적으로 완벽히 병합

**결론 (2줄):**
- 기술사 판단: 클라우드 스케일에서는 물리적 한계로 인해 강한 일관성을 고집하는 것은 불가능하며, 비즈니스 도메인을 잘게 쪼개어 필수 영역에만 강한 일관성을 국소적으로 적용하는 하이브리드 설계가 필수다.
- 향후 방향: 최근 구글 Spanner(TrueTime 활용)나 CockroachDB 같은 NewSQL의 등장으로, 분산 환경에서도 락오버헤드를 최소화하며 강한 일관성을 제공하는 기술적 돌파구가 마련되고 있다.
