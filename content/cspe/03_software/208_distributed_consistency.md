## Ⅰ. 개요
- **정의**: 분산 노드 간 데이터 복제 시 읽기·쓰기 결과가 일관된 상태를 보장하는 정도를 나타내는 속성
- **배경/필요성**: 분산 환경에서 가용성·파티션 허용과 일관성 간 트레이드오프(CAP) 설계 판단 필요
- **비유**: 여러 지점 은행에서 동시 출금 시 잔고가 모든 지점에서 동일하게 보이는지의 문제

| 출제 의도 | 반드시 짚을 핵심 | 감점 회피 포인트 |
|:---|:---|:---|
| CAP·일관성 모델 이해 | Strong vs Eventual Consistency 구분 | CAP에서 P는 항상 전제, 실제 선택은 C vs A임을 명시 |

> 요약: 분산 노드 간 데이터 일관성 보장 수준을 정의하고 트레이드오프를 설계하는 속성임

## Ⅱ. 구성요소
```text
Client --write--> Node A --replicate--> Node B
Client --read---> Node B (일관성 수준에 따라 결과 상이)

Strong:   write 완료 후 모든 노드 동일 값 보장
Eventual: write 후 일정 시간 경과 후 수렴
```

| 구성요소 | 설명 | 비유 |
|:---|:---|:---|
| Strong Consistency | 쓰기 완료 후 모든 읽기가 최신 값 반환 보장 | 실시간 전광판 |
| Eventual Consistency | 일정 시간 후 모든 복제본이 최신 값으로 수렴 | 우편 배달 |
| Causal Consistency | 인과 관계가 있는 연산 간 순서만 보장 | 대화 맥락 유지 |

> 요약: Strong·Eventual·Causal 등 일관성 수준별로 지연·가용성 트레이드오프가 상이함

## Ⅲ. 절차
```text
쓰기 요청 --> 복제 전파 --> 정족수 확인 --> 읽기 일관성 판정
```
- 1단계: 클라이언트가 리더/코디네이터 노드에 쓰기 요청 전송
- 2단계: 리더가 팔로워 노드들에게 복제 데이터 전파
- 3단계: 설정된 정족수(Quorum: W+R > N) 충족 여부 확인 후 쓰기 ACK 반환
- 4단계: 읽기 시 정족수 조건에 따라 최신 값 반환 여부 판정

> 요약: 쓰기, 복제 전파, 정족수 확인, 읽기 판정 4단계로 일관성 수준 결정함

## Ⅳ. 문제점
- 지연 증가: Strong Consistency 적용 시 모든 복제 완료 대기 — 쓰기 지연 증가
- 가용성 저하: 네트워크 파티션 발생 시 일관성 우선 정책은 요청 거부 — 서비스 중단
- 충돌 해소: Eventual Consistency에서 동시 쓰기 충돌 시 자동 병합 로직 복잡

> 요약: 지연 증가, 가용성 저하, 충돌 해소 복잡성이 주요 문제임

## Ⅴ. 개선방안
1. 단기: 읽기/쓰기 정족수 튜닝(W=1, R=N 등)으로 용도별 지연·일관성 균형 조정
2. 중기: 서비스별 일관성 수준 차등 적용(결제=Strong, 추천=Eventual)으로 가용성 확보
3. 장기: CRDT·벡터 클럭 기반 자동 충돌 해소 알고리즘 도입

> 요약: 정족수 튜닝, 차등 일관성, CRDT 도입으로 단계적 개선함

## Ⅵ. 전망
- 발전 방향: NewSQL(CockroachDB 등)이 분산 환경에서도 Strong Consistency 제공 시도 중
- 기술사적 판단: CAP 이후 PACELC 모델로 정상 상태 지연-일관성 트레이드오프까지 확장 분석 필요
- 기술사 제언: 분산 합의 알고리즘(209 참조)과 연계하여 일관성 보장 메커니즘 이해 필수
