# 📖 【암기용】 개념 완전 이해

> 목적: FinOps를 처음 봐도 완벽히 이해하게 만든다. 시험 답안 양식이 아니라, 이해를 위한 친절한 설명이다.

## 한눈에
- **개요**: FinOps는 **클라우드 비용 관리**를 기술팀·재무팀·사업팀이 함께 운영하는 **거버넌스 체계**(Financial Operations의 줄임말)다.
- **왜 필요한가**: 온프레미스는 구매 승인 시점에 비용이 통제되지만, 클라우드는 개발자가 콘솔 클릭 몇 번으로 자원을 즉시 만들 수 있어 비용 통제 시점이 "구매 전"에서 "사용 중"으로 옮겨간다.
- **핵심 직관**: 전기요금처럼 쓴 만큼 청구되지만, 어느 부서가 어떤 장비를 왜 켰는지까지 태그로 추적해 책임을 지우는 체계다.

## 핵심 용어 정리 (내부에 등장하는 것들)

| 용어 | 의미 | 비유 |
|:---|:---|:---|
| 클라우드 비용 관리 | 클라우드 사용량과 비용을 추적·통제하는 활동 전반 — FinOps는 이를 조직적으로 운영하는 방법론 | 가계부 관리 전체 |
| FinOps(Financial Operations) | 기술·재무·사업이 공동으로 비용을 가시화·최적화·운영하는 클라우드 비용 거버넌스 방법론 | 부서별 법인카드 내역을 공동 관리하는 체계 |
| Inform / Optimize / Operate | FinOps의 3단계 — 비용을 보이게 하고(Inform), 낭비를 줄이고(Optimize), 반복 운영한다(Operate) | 지출 파악 → 절약 실행 → 매달 예산 재점검 |
| 태그(Tag) | 리소스에 붙이는 라벨(부서·프로젝트·환경 등)로 비용을 누구 것인지 분류하는 메타데이터 | 영수증에 부서명을 적어 분류 |
| Rightsizing | 실제 사용량(CPU·메모리)에 맞춰 인스턴스 사양을 낮추거나 올리는 작업 | 안 쓰는 큰 방 대신 딱 맞는 방으로 이사 |
| 예약 인스턴스(Reserved Instance) | 1~3년 사용을 약정하고 할인받는 구매 방식 | 통신사 약정 요금제 |
| 스팟 인스턴스(Spot Instance) | CSP의 유휴 자원을 저렴하게 빌리되 언제든 회수될 수 있는 구매 방식 | 초특가지만 취소될 수 있는 항공권 |
| Showback / Chargeback | 부서별 비용을 보여주기만 함(Showback) vs 실제로 부서 예산에서 차감함(Chargeback) | 카드값 명세서만 보여주기 vs 실제로 정산해서 걷기 |
| 단위 경제성(Unit Economics) | 거래 1건·사용자 1명당 비용처럼 정규화한 비용 지표 | 총 식비가 아니라 "한 끼당 얼마"로 보는 것 |

## 깊이 이해

### Inform-Optimize-Operate를 수치로 이해
- Inform(가시화): 계정·프로젝트·소유자·환경 태그를 표준화해 비용을 분류한다. 목표 태그 커버리지는 실무에서 보통 95% 이상 — 태그 없는 리소스가 5%를 넘으면 그만큼 "누구 것인지 알 수 없는 비용"이 쌓인다는 뜻이다.
- Optimize(최적화): CPU 사용률 20% 이하로 오래 유지되는 인스턴스를 한 단계 축소(rightsizing)하거나, 24시간 켜진 개발용 VM을 업무시간(예: 평일 09~19시, 하루 10시간)에만 가동되도록 스케줄링하면 해당 자원 비용을 약 58%(24시간 중 10시간만 가동) 절감할 수 있다.
- Operate(운영): 월간 리뷰에서 예산 편차 10% 이하를 목표로 잡고, 초과 시 자동 알림이 발송되도록 예산 알림을 설정해 매달 반복한다.

### 예약/스팟 구매로 보는 비용 절감 폭
- 워크드 예: 온디맨드(사용한 만큼 정가 지불) 대비 1년 예약 인스턴스는 보통 30~40%, 3년 예약은 50~60% 할인된다. 가동률이 100%에 가까운 상시 운영 DB는 예약으로 전환하는 것이 유리하다.
- 스팟 인스턴스는 온디맨드 대비 60~90% 저렴하지만 CSP가 언제든 회수(interruption)할 수 있다. 그래서 배치 작업처럼 중단돼도 재시도 가능한 워크로드(예: 야간 데이터 처리)에만 적용하고, 체크포인트·재처리 큐로 중단에 대비한다.

### 단위 경제성 — 총액이 아니라 "1건당 비용"으로 판단하는 이유
- 워크드 예: 이번 달 클라우드 비용이 지난달보다 20% 늘었다고 무조건 나쁜 신호는 아니다. 같은 기간 거래량이 30% 늘었다면 거래 1건당 비용(cost per transaction)은 오히려 (1.2÷1.3 ≈ 0.92배로) 약 8% 감소한 것이므로, 서비스가 더 효율적으로 운영되고 있다는 뜻이다. FinOps는 이 단위 비용 지표로 "비용이 늘었다=나쁘다"는 단순 판단을 피한다.

### 흔한 오해
- "FinOps는 비용을 무조건 줄이는 활동"이라는 오해가 흔하다. 실제로는 SLO(서비스 목표 수준, 예: p95 지연 100ms 이하)를 유지하는 조건에서 비용 대비 가치를 최적화하는 것이 목적이며, 과도한 rightsizing으로 성능이 떨어지면 이는 FinOps의 실패 사례로 본다.

## 연결 개념
- 예약 인스턴스·스팟 인스턴스 — FinOps의 구매 최적화 수단
- 오토 스케일링 — 사용량 기반 자원 조정 수단
- 클라우드 서비스 모델 — IaaS·PaaS·SaaS별 비용 구조 차이

> 핵심: FinOps는 비용 절감 구호가 아니라 비용 가시화, 책임 배부, 사용량 최적화, 단위 경제성 지표를 운영하는 체계다.

> 2. **가치**: 태그, 예산, 사용량 지표를 통해 자원 낭비를 줄이고 서비스 가치 대비 비용을 판단한다.
> 3. **판단 포인트**: 태그 커버리지, rightsizing, 예약/스팟 적용률, 단위 거래당 비용이 핵심 지표다.

## Ⅰ. 개요 및 필요성

- 개요: FinOps는 클라우드 비용 가시화와 운영 거버넌스임.
- 배경: 클라우드는 사용량 기반 과금으로 인해 개발·운영 활동이 곧 비용 발생으로 연결된다.
- 필요성: 태그, 예산, 단가, 사용량 데이터를 기준으로 기술, 재무, 사업 조직의 비용 의사결정을 정렬한다.

---

## Ⅱ. 구조 및 구성요소

```text
Cloud Usage -> Billing Export -> Tag/Account Allocation
            -> Inform -> Optimize -> Operate
            +-> Engineering / Finance / Business Owner
```

| 구성요소 | 역할 | 특이사항 |
|:---|:---|:---|
| 비용 가시화 | 계정, 태그, 서비스별 비용 분류 | 태그 커버리지 95% 이상 |
| 최적화 실행 | rightsizing, 예약, 스팟, 스케줄링 | CPU, 메모리, 사용 패턴 분석 |
| 운영 거버넌스 | 예산, 알림, 비용 배부, 정례 회의 | showback, chargeback |
| 단위 경제성 | 거래·사용자·요청당 비용 분석 | Cost per transaction |

> 요약: FinOps는 비용 데이터를 태그로 분류하고 최적화 실행과 조직 운영으로 연결하는 체계다.

---

## Ⅲ. 동작원리 및 흐름도

```text
사용량 수집 -> 태그/계정별 비용 배부 -> 낭비 식별
-> rightsizing/예약/스팟 적용 -> 예산 알림 -> 월간 리뷰
```

| 단계 | 처리 내용 | 검증 기준 |
|:---:|:---|:---|
| 1 | 비용 데이터 수집 | Billing Export 일 단위 수집 |
| 2 | 태그와 계정으로 배부 | 태그 커버리지 95% 이상 |
| 3 | 최적화 후보 식별 | CPU 20% 이하, 미사용 디스크 |
| 4 | 실행과 재측정 | 월 예산 편차 10% 이하 |

> 요약: FinOps는 비용을 보이게 한 뒤 최적화하고, 예산 편차를 반복 측정하는 운영 루프다.

## Ⅳ. 특징

| 구분 | 전통 IT 비용관리 | FinOps | 수치·판단 포인트 |
|:---|:---|:---|:---|
| 비용 시점 | 구매 승인 시 통제 | 사용 중 실시간 통제 | 일 단위 비용 리포트 |
| 책임 | 재무 중심 | 엔지니어링·재무·사업 공동 | 서비스별 owner 100% 지정 |
| 최적화 | 장비 표준화 | rightsizing, 예약, 스팟, 스케줄 | 월 비용 10~30% 절감 사례 |
| 지표 | 총 IT 예산 | 단위 거래당 비용, 예산 편차 | cost per order, cost per user |

> 요약: FinOps는 총액 관리에서 사용량과 단위 경제성 중심의 반복 운영으로 전환한다.

## Ⅴ. 심화 비교 및 적용 판단

| 구분 | 비용 절감 프로젝트 | FinOps | 선택 기준 |
|:---|:---|:---|:---|
| 구조 | 일회성 비용 삭감 | 상시 비용 운영 체계 | 클라우드 월 비용 변동성 |
| 비용/성능 | 자원 축소 중심 | SLO 유지 조건에서 우측정 | p95 지연·오류율 유지 |
| 운영/위험 | 재무 주도 | 엔지니어링 실행 책임 | owner와 태그 기준 존재 |

> 요약: FinOps는 비용을 줄이는 활동이 아니라 서비스 SLO와 비용을 함께 조정하는 운영 체계다.

| 리스크 | 원인 | 대응 방안 | 확인 지표 |
|:---|:---|:---|:---|
| 태그 누락 | 생성 시 정책 부재 | IaC 태그 강제, 미태그 차단 | 태그 커버리지 95% 이상 |
| 성능 저하 | 과도한 rightsizing | SLO 기반 변경 승인 | p95 지연 100ms 이하 유지 |
| 스팟 중단 | 인터럽션 발생 | checkpoint, queue, fallback | 작업 재시도 성공률 99% |

> 요약: FinOps 리스크는 태그 누락, 과도한 축소, 스팟 중단이며 정책과 SLO 지표로 통제한다.

| 점검 항목 | 목표 기준 | 측정 방법 |
|:---|:---|:---|
| 가시화 | 태그 커버리지 95%, owner 100% 지정 | Billing Export, CMDB |
| 최적화 | 미사용 리소스 월 1회 제거, 예약 적용률 60% | 비용 분석 리포트 |
| 단위 경제성 | 거래당 비용 월 5% 이하 변동 | APM, 매출·사용량 데이터 |

> 요약: FinOps 성과는 비용 총액보다 태그, 최적화 실행률, 단위 비용 변동률로 판단한다.

## Ⅵ. 실무 적용 및 결론

**적용 방안 3개 (필수 - 단계별 또는 항목별):**
1. Inform: 계정·프로젝트·owner·환경 태그를 표준화하고 태그 커버리지 95% 이상을 배포 조건으로 설정
2. Optimize: CPU 20% 이하 인스턴스 rightsizing, 개발 환경 야간 정지, 1년 상시 사용량 예약 구매 적용
3. Operate: 월간 FinOps 회의에서 예산 편차 10% 이하, 단위 거래당 비용, SLO 지표를 함께 검토

**결론 (2줄):**
- 기술사 판단: 클라우드 비용은 총액이 아니라 서비스 가치 대비 단위 비용과 SLO 유지 여부로 판단함
- 향후 방향: FinOps는 GreenOps, 자동 rightsizing, 정책 기반 예산 차단과 결합해 실시간 비용 제어로 발전함

|:---|:---|:---|:---|

| 요구사항 명시형 | "비용 최적화 방안을 제시하시오" | 태그, rightsizing, 예약/스팟 실행 절차 | SLO와 단위 비용 선택 기준 |

> 요약: 설명형은 운영 체계, 방안형은 측정 지표와 실행 수단 중심으로 전환한다.
