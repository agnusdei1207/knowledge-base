## 핵심 인사이트 (3줄 요약)
- 벤더사(Datadog, Dynatrace 등)마다 달랐던 관측성 데이터(로그, 메트릭, 트레이스)의 수집 규칙과 형식을, **하나의 언어로 완벽하게 통일해 버린 글로벌 오픈소스 표준(CNCF 프로젝트)**.
- 예전에는 A사 모니터링 툴을 쓰려면 코드 전체에 A사 전용 라이브러리를 도배해야 했음(벤더 락인). 이제는 **OTel 표준 라이브러리**만 코드에 심어두면, 데이터를 Datadog으로 쏠지 Prometheus로 쏠지 설정 파일 한 줄만 바꿔서 마음대로 결정할 수 있음.
- "데이터를 모으는 것(수집)"은 OpenTelemetry가 공통으로 담당하고, "데이터를 보여주는 것(분석/대시보드)"은 각 회사 입맛에 맞는 백엔드 툴이 경쟁하는 건강한 생태계를 완성함.

## Ⅰ. 개요 및 필요성
- **개요**: 클라우드 네이티브 소프트웨어의 관측성 데이터(Traces, Metrics, Logs)를 계측(Instrument), 생성, 수집 및 내보내기 위한 프레임워크이자 통합 도구 세트.
- **필요성**: 회사가 Jaeger(트레이싱), Prometheus(메트릭), ELK(로그)를 섞어 쓰고 있었음. 개발자는 코드 안에 이 3가지 툴의 추적용 라이브러리를 덕지덕지 발라야 했음. 그러다 CTO가 "내년부터 Datadog으로 툴 바꾼다!"라고 선언함. 개발팀은 수백 개 앱의 소스 코드를 뒤져서 옛날 라이브러리를 빼고 Datadog 라이브러리로 다시 갈아 끼우는 대공사를 하느라 밤을 새움. **"아니, 어떤 모니터링 툴을 쓰든 앱 코드는 절대 안 건드리게 중간에서 데이터를 싹 모아서 번역해 주는 범용 어댑터(표준) 하나 만들면 안 돼?"**라며 OTel이 등장함.
---
## Ⅱ. 아키텍처 및 핵심 원리
- **1. 계측 (Instrumentation - 라이브러리)**:
  - 개발자는 Java나 Python 앱에 특정 벤더(Datadog 등) 라이브러리가 아니라 **OTel SDK** 하나만 설치함.
  - OTel 라이브러리가 앱 내부에서 도는 함수의 실행 시간, SQL 쿼리 내역 등을 '표준 포맷'으로 떠먹기 좋게 포장해 냄. (심지어 Auto-Instrumentation으로 코드 한 줄 안 짜도 Java 에이전트가 알아서 데이터를 다 캐냄).
- **2. 수집기 (OTel Collector)**:
  - OTel의 심장이자 데이터 댐. 파드 옆이나 노드에 깔려 있음.
  - 앱들이 쏟아내는 수많은 OTel 데이터를 중간에서 싹 다 빨아들임(Receiver).
  - 주민등록번호 같은 민감 정보는 중간에서 지우거나 묶어서 가공함(Processor).
- **3. 내보내기 (Exporter)**:
  - 댐에 모인 표준 데이터를 원하는 백엔드 툴의 입맛에 맞게 쏴줌.
  - "이 데이터는 AWS X-Ray로 쏴! 아, 백업으로 Prometheus에도 쏴!" ➡️ 엑스포터 설정만 추가하면 코드를 안 고치고도 여러 모니터링 툴에 데이터를 동시 분배할 수 있음.

```text
[ 벤더 종속(과거) vs OpenTelemetry(현재) 데이터 흐름 비교 ]

 ⛓️ [ 과거: 벤더 종속 (Vendor Lock-in) 끔찍한 스파게티 ]
 앱 코드 ➡️ (Datadog 라이브러리) ➡️ Datadog 서버
 앱 코드 ➡️ (Prometheus 라이브러리) ➡️ Prometheus 서버
 * 툴 바꿀 때마다 소스 코드를 다 뜯어고쳐야 함! 😱

 🌐 [ 현재: OpenTelemetry 표준 통합 (플러그 앤 플레이) ]
 앱 코드 ➡️ (오직 OTel 라이브러리 1개!) 
        ⬇️ (표준 OTLP 통신)
 [ OTel Collector (만능 수집기/분배기) ]
        ⬇️ 분배 ⬇️ (Exporter)
 [Jaeger]  [Prometheus]  [Datadog]  [New Relic]
 * 툴을 바꾸고 싶으면? Collector의 목적지 주소만 바꾸면 됨! 코드는 건드릴 필요 제로! 😎
```

## Ⅲ. 비교 및 연결
| 기능/도구 | 관측성 3대 기둥 | 기존 분절화된 도구들 | OpenTelemetry (대통합) |
|---|---|---|---|
| **트레이싱 (Traces)**| 요청 경로 추적 | OpenTracing (Jaeger), OpenCensus | **➡️ OTel Traces로 완전 통합됨** |
| **메트릭 (Metrics)** | CPU, 에러율 숫자 | Prometheus, StatsD | **➡️ OTel Metrics로 표준화** |
| **로그 (Logs)** | 텍스트 기록 | Fluentd, Logstash | **➡️ OTel Logs 규격 통합 중** |
| **결과** | - | 툴마다 계측 방법이 다 다름 | **단 하나의 OTel 에이전트로 3개 다 수집!** |

## Ⅳ. 실무 적용 및 기술사 판단
- **Auto-Instrumentation (자동 계측) 전략**: 실무 환경에 수천 개의 자바(Spring Boot) 레거시 앱이 있을 때, 개발자들에게 "OTel SDK 넣어서 코드 다시 빌드하세요"라고 하면 1년이 걸림. 기술사는 **K8s OTel Operator를 도입**하여, 파드가 뜰 때 자동으로 Java Agent(바이트코드 주입)를 딱 밀어 넣는 무설정(Zero-Code) 자동 계측 방식을 채택해야 단 며칠 만에 사내 전체 시스템의 통신 지도를 그려낼 수 있음.
- **OTel Collector 게이트웨이 아키텍처**: 모든 파드에 OTel 수집기를 띄워서 외부(Datadog)로 쏘면 아웃바운드 트래픽 관리도 안 되고 클라우드 API 호출 비용이 폭발함. 실무에서는 각 파드는 노드에 있는 OTel Collector(DaemonSet)로 데이터를 넘기고, 이 노드 수집기들이 다시 **중앙 OTel Gateway(대형 댐)**로 데이터를 모은 다음 한 번에 압축해서 외부 벤더로 쏘는 2-Tier 수집 아키텍처를 설계해야 함.
---
## Ⅴ. 기대효과 및 결론
- 모니터링 도구 회사들이 자신들의 툴을 쓰게 하려고 만들었던 '데이터 수집 장벽(독점 라이브러리)'을 무너뜨리고, 관측성 데이터의 주권을 기업과 개발자에게 되찾아준 민주화 운동.
- 데이터 생성(OTel)과 분석(벤더)을 완벽하게 디커플링(Decoupling)하여, 쿠버네티스(K8s)에 버금가는 클라우드 네이티브 시대의 두 번째로 위대하고 거대한 오픈소스 표준 인프라로 군림함.
