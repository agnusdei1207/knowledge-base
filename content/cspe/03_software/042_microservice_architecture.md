## 미리 알고가기

- MSA는 시스템을 작은 독립 서비스 집합으로 나누는 구조임
- 각 서비스는 독립 배포와 독립 확장을 목표로 함
- 분리 이점보다 운영 복잡도와 데이터 일관성 비용을 같이 봐야 함

## Ⅰ. 개요

- **정의/개념**: 마이크로서비스 아키텍처는 비즈니스 기능을 작은 독립 서비스로 분리하고 각 서비스를 개별 개발과 배포와 확장이 가능하도록 구성하는 분산 소프트웨어 아키텍처임
- **배경/필요성**: 대형 모놀리식 시스템은 배포 충돌과 기술 스택 경직성과 장애 영향 범위가 커지므로, 빠른 기능 변경과 팀 자율성을 높이기 위한 서비스 단위 분리가 필요해짐

## Ⅱ. 특징

- 서비스별 배포 독립성과 기술 선택 자율성이 높음
- 팀 구조를 서비스 경계와 맞출 수 있어 조직 확장에 유리함
- 네트워크 호출과 데이터 분산으로 운영 복잡도와 장애 지점이 늘어남
- 경계를 잘못 자르면 분산 모놀리스로 변질되기 쉬움

## Ⅲ. 종류 및 비교

| 판단 기준 | 모놀리식 | MSA |
|:---|:---|:---|
| 배포 단위 | 전체 애플리케이션 | 서비스별 독립 단위 |
| 확장 방식 | 전체 스케일 아웃 | 필요한 서비스만 확장 |
| 장점 | 단순한 운영과 트랜잭션 | 팀 자율성과 변경 속도 |
| 한계 | 배포 충돌과 확장 비효율 | 복잡한 운영과 분산 데이터 문제 |

## Ⅳ. 구성요소 및 구조

| 구성요소 | 설명 |
|:---|:---|
| Service Boundary | 도메인 기능별 경계를 나눠 독립 배포와 소유권 단위를 만듦 |
| API Contract | 서비스 간 통신 규약을 정의해 분산 환경에서도 변경 영향을 통제함 |
| Data Ownership | 서비스별 데이터 소유를 분리해 자율성을 높이지만 일관성 설계를 요구함 |
| Observability and Ops Layer | 로깅과 트레이싱과 배포 자동화가 운영 복잡도를 감당하는 기반이 됨 |

## Ⅴ. 원리 및 절차 흐름도

```text
+-------------+     +-------------+     +-------------+     +-------------+
| 도메인 분리      | --> | 서비스 설계    | --> | 계약/데이터 정의 | --> | 독립 배포/운영 |
+-------------+     +-------------+     +-------------+     +-------------+
```

1. **도메인 분리**: 비즈니스 기능과 팀 책임을 기준으로 경계를 정함
2. **서비스 설계**: 각 서비스의 API와 책임과 데이터 범위를 설계함
3. **계약 및 데이터 정의**: 동기 호출과 이벤트와 저장소 소유권을 정함
4. **독립 배포 및 운영**: 서비스별로 배포와 확장과 모니터링을 수행함

## Ⅵ. 문제점 및 해결 방안

1. 문제: 서비스 경계가 약하면 동기 호출이 과도해져 분산 모놀리스로 변질될 수 있음
   - 해결방안: bounded context 기준 경계를 재설계하고 interservice dependency density와 deployment coupling rate로 검증함
2. 문제: 서비스별 데이터 분리로 인해 트랜잭션과 정합성 관리가 복잡해질 수 있음
   - 해결방안: eventual consistency와 saga를 적용하고 consistency incident count와 compensation success rate로 검증함
3. 문제: 서비스 수가 늘수록 배포와 관측과 장애 분석 비용이 급격히 증가할 수 있음
   - 해결방안: 플랫폼 자동화와 tracing을 강화하고 MTTR와 operational overhead per service로 검증함

## Ⅶ. 적용 사례

- 전자상거래 주문 플랫폼에서는 서비스별 배포를 운영하고 확인 지표는 deployment coupling rate와 MTTR임
- 금융 API 플랫폼에서는 데이터 소유를 분리하고 확인 지표는 consistency incident count와 compensation success rate임
- 대규모 SaaS 조직에서는 공통 플랫폼 자동화를 구축하고 확인 지표는 operational overhead per service와 interservice dependency density임

## Ⅷ. 결론

MSA의 성공은 서비스를 많이 쪼개는 데 있지 않고 경계와 데이터 소유와 운영 자동화를 함께 설계해 독립성이 실제로 작동하게 만드는 데 있음.
