## 미리 알고가기

- MSA는 비즈니스 기능을 작은 서비스 단위로 나누는 분산 아키텍처임
- Bounded context는 같은 용어와 규칙이 유효한 도메인 경계임
- Eventual consistency는 여러 저장소가 즉시 같지 않아도 일정 시간 안에 맞춰지는 상태임

## Ⅰ. 개요

- **정의/개념**: 마이크로서비스 아키텍처는 비즈니스 기능을 독립 서비스로 분리하고 각 서비스를 개별 개발, 배포, 확장이 가능하도록 구성하는 분산 소프트웨어 구조임.
- **배경/필요성**: 대형 모놀리식 시스템은 배포 충돌, 기술 스택 경직, 장애 확산 범위가 커지기 쉬우므로, 변경 속도와 팀 자율성을 높일 수 있는 서비스 단위 분리가 필요함.

## Ⅱ. 특징

- 서비스별 독립 배포와 선택적 확장이 가능함
- 서비스별 소유 팀이 코드·데이터·배포·운영 책임을 함께 담당함
- 네트워크 호출과 데이터 분산이 늘어 운영 복잡도와 장애 지점도 늘어남
- 경계를 잘못 자르면 서비스만 많고 결합은 강한 분산 모놀리스가 되기 쉬움

## Ⅲ. 종류 및 비교

| 구분 | 모놀리식 | MSA |
|:---|:---|:---|
| 배포 단위 | 애플리케이션 전체를 한 번에 배포함 | 서비스별로 필요한 부분만 따로 배포함 |
| 확장 방식 | 전체 시스템을 함께 늘리는 경우가 많음 | 부하가 집중되는 서비스만 선택적으로 늘릴 수 있음 |
| 소유·배포 방식 | 하나의 릴리스 단위와 공통 운영 책임 | 서비스별 소유 팀과 독립 배포 파이프라인 |
| 운영 한계 | 작은 변경도 전체 릴리스와 충돌하기 쉬움 | 분산 데이터와 관측과 장애 분석 비용이 커짐 |

> 요약: MSA는 코드를 잘게 나누는 방식이 아니라 배포와 소유권을 서비스 경계에 맞추는 방식임.

## Ⅳ. 구성요소 및 구조

| 구성요소 | 설명 |
|:---|:---|
| Service Boundary | 도메인 기능별 경계를 나눠 독립 배포와 책임 소유 단위를 만듦 |
| API Contract | 서비스 간 호출 규약을 정의해 분산 환경에서도 변경 영향을 통제함 |
| Data Ownership | 서비스별 데이터 소유를 분리해 자율성을 높이되 정합성 설계를 요구함 |
| Observability and Ops Layer | 로깅, 트레이싱, 배포 자동화가 늘어난 운영 복잡도를 감당하는 기반이 됨 |

## Ⅴ. 원리 및 절차 흐름도

```text
+-------------+     +-------------+     +-------------+     +-------------+
| 도메인 분리      | --> | 서비스 설계    | --> | 계약/데이터 정의 | --> | 독립 배포/운영 |
+-------------+     +-------------+     +-------------+     +-------------+
```

1. **도메인 분리**: 비즈니스 기능과 팀 책임을 기준으로 경계를 정함
2. **서비스 설계**: 각 서비스의 책임, API, 데이터 범위를 설계함
3. **계약 및 데이터 정의**: 동기 호출과 이벤트와 저장소 소유권을 정함
4. **독립 배포 및 운영**: 서비스별 배포와 확장과 관측 체계를 운영함

## Ⅵ. 실무 적용 및 유의점

1. 전자상거래나 SaaS 플랫폼처럼 기능 변화가 빠른 환경에서는 MSA가 유리하지만 서비스 경계가 약하면 호출이 뒤엉키므로 바운디드 컨텍스트 기준으로 재설계하고 서비스 간 호출 수와 동시 배포 비율로 확인함
2. 금융·정산 시스템처럼 데이터 정합성이 중요한 환경에서는 서비스별 저장소를 분리하되 분산 트랜잭션을 억지로 숨기지 말고 사가와 보상 절차를 운영하며 정합성 사고 건수와 보상 처리 성공률로 확인함

## Ⅶ. 결론

MSA는 bounded context를 기준으로 서비스와 데이터 소유권을 나누고 독립 배포·관측·장애 대응 체계를 함께 운영해야 함.
