# 📖 【암기용】 개념 완전 이해

## 한눈에
- **개요**: **마이크로서비스 아키텍처(MSA)**는 단일 애플리케이션을 비즈니스 도메인 단위의 작고 독립적인 서비스들로 나누어 구성하는 아키텍처 접근법이다.
- **왜 필요한가**: 거대한 모놀리식(Monolithic) 시스템은 코드 한 줄만 고쳐도 전체를 다시 빌드·배포해야 하고, 특정 기능에 트래픽이 몰려도 전체 시스템을 스케일아웃해야 하는 비효율이 발생한다.
- **핵심 직관**: 거대한 종합 쇼핑몰을 여러 개의 독립된 전문 매장(정육점, 채소가게, 빵집)으로 나누는 것. 각 매장은 알아서 재고를 관리하고 직원을 뽑으며 독립적으로 운영된다.

## 핵심 용어 정리

| 용어/표기 | 의미 | 비유·예 |
|:---|:---|:---|
| 모놀리식 (Monolith) | 모든 기능이 하나의 코드베이스와 통짜 DB로 구성된 구조 | 모든 부서가 한 사무실을 쓰는 회사 |
| 폴리글랏 (Polyglot) | 각 서비스 목적에 맞춰 다양한 언어와 DB를 혼용하는 특성 | 부서별로 가장 편한 언어와 도구를 사용 |
| API 게이트웨이 | 클라이언트 요청을 받아 각 마이크로서비스로 라우팅하는 단일 진입점 | 회사 로비의 안내 데스크 |
| 서비스 메시 (Service Mesh) | 서비스 간 통신, 보안, 모니터링을 인프라 계층에서 처리하는 망 | 건물 내 부서 간 전용 통신망 |

## 깊이 이해
- **배경·문제의식**: 클라우드 시대에 민첩성(Agility)이 중요해지면서, 코드가 방대해질수록 빌드/배포 시간(수십 분~시간 단위)이 길어지고 장애가 전체 시스템으로 전파되는 모놀리식의 한계가 극명해졌다.
- **작동 원리**: 각 서비스는 자신만의 독립적인 데이터베이스(DB per Service)를 가지며, 서비스 간 통신은 REST API나 비동기 메시징(Kafka 등)을 통해 이루어진다. 장애가 발생해도 해당 서비스에만 국한(장애 격리)되며, 개별 배포가 가능하다.
- **비유**: 레고 블록 조립. 각 블록(서비스)은 독립적으로 만들어지고 교체될 수 있으며, 전체 시스템은 이 블록들의 조합으로 돌아간다.
- **구체 예시**: 넷플릭스는 결제, 추천, 스트리밍 등을 독립적인 서비스로 쪼개어, 추천 서비스가 죽더라도 결제와 스트리밍은 정상 작동하도록 설계했다.
- **흔한 오해·주의점**: "MSA를 하면 무조건 빨라지고 좋다"는 오해다. 오히려 서비스 간 네트워크 호출(RPC) 비용이 증가하고, 분산 트랜잭션 관리와 로깅·추적이 매우 복잡해져 운영 난이도가 급증한다.

## 연결 개념
- 도메인 주도 설계 (DDD) — MSA를 적절한 크기로 나누는 논리적 분해 기법
- API Gateway & Service Mesh — MSA 통신 및 관리 인프라
- 분산 트랜잭션 (Saga Pattern) — 쪼개진 DB들 간의 데이터 정합성 유지 기법

# 📝 【답안용】 시험 답안 템플릿

## 핵심 인사이트 (3줄 요약)

> 1. **본질**: MSA는 비즈니스 도메인 중심으로 애플리케이션을 분할하여 독립적인 배포와 확장을 가능하게 하는 분산 소프트웨어 아키텍처이다.
> 2. **가치**: 모놀리식 시스템의 배포 병목과 확장 한계를 극복하여 배포 빈도를 높이고 서비스 가용성과 조직 민첩성을 극대화한다.
> 3. **판단 포인트**: 기술적 장점 이면에 숨겨진 네트워크 지연, 분산 데이터 정합성 문제, 관측성 부족 리스크를 극복할 인프라(DevOps, Service Mesh) 성숙도가 도입의 전제 조건이다.

## 출제 의도 및 답안 포인트

| 출제 의도 | 반드시 짚을 핵심 | 감점 회피 포인트 |
|:---|:---|:---|
| MSA의 개념적 특징과 모놀리식 한계 비교 | 독립 배포, DB 분리, 폴리글랏 프로그래밍, 장애 격리 | 물리적 분리(컨테이너)만 강조하고 논리적 도메인 분리(DDD) 누락 |
| 분산 아키텍처의 리스크 및 해결 방안 제시 | 분산 트랜잭션(Saga), 통신 지연(Async), 관측성(Tracing) | 단순 인프라 구축으로 모든 문제가 해결된다는 식의 서술 |

> 요약: 단순한 개념 설명을 넘어, 도입 시 발생하는 분산 환경의 트레이드오프와 구체적인 아키텍처적 극복 방안을 제시해야 한다.

## Ⅰ. 개요 및 필요성

- 개요: 애플리케이션을 비즈니스 기능(도메인) 단위로 분해하여 독립적으로 개발·배포·확장 가능한 작은 서비스들의 조합으로 구축하는 아키텍처
- 배경: 모놀리식 구조의 결합도 심화로 인한 배포 지연, 부분 확장의 어려움, 작은 오류가 전체 시스템 장애로 이어지는 문제 부각
- 필요성: 클라우드 네이티브 환경에서 시장 변화에 즉각 대응하는 민첩성(배포 소요시간 10분 이내)과 무중단 서비스 제공을 위해 필수적

---

## Ⅱ. 구조 및 구성요소

```text
Client -> API Gateway -> Service A (Auth) -> DB A
                         |
                         +-> Service B (Order) -> DB B
                         |
                         +-> Service C (Pay) -> DB C
                         |
                         +-> Message Broker (Async Event)
```

| 구성요소 | 역할 | 특이사항 |
|:---|:---|:---|
| API Gateway | 클라이언트 요청 단일 진입점, 라우팅, 인증/인가 | 병목 방지를 위한 이중화 필수 |
| Microservice | 특정 비즈니스 도메인 기능 수행 및 독립 배포 | Bounded Context 단위 분리 (DDD) |
| DB per Service | 서비스별 독립적 데이터베이스 소유 및 관리 | 폴리글랏 퍼시스턴스 허용 |
| Service Mesh | 서비스 간 통신 제어, 트래픽 관리, 보안 | Istio, Envoy 패턴 등 적용 |

> 요약: MSA는 API 게이트웨이로 요청을 분배하고, 각 마이크로서비스가 독립된 DB를 가지며 메시지 브로커 등으로 협력하는 구조다.

---

## Ⅲ. 동작원리 및 흐름도

```text
클라이언트 요청 -> API Gateway 인증/라우팅 -> 해당 마이크로서비스 호출
-> 연관 서비스 간 이벤트 발행/구독 (Saga) -> 개별 DB 커밋 -> 응답 반환
```

- 1단계 [진입 라우팅]: API Gateway가 클라이언트 요청을 수신하여 인증 후 적절한 서비스(예: 주문)로 라우팅
- 2단계 [독립 처리]: 주문 서비스가 자체 DB(DB B)에 데이터를 기록하고, 결제 요청 이벤트를 비동기로 발행
- 3단계 [분산 트랜잭션 협력]: 결제 서비스가 이벤트를 구독하여 처리하며, 성공/실패에 따라 보상 트랜잭션(Saga) 실행
- 4단계 [결과 응답]: 동기적 결과는 API Gateway를 통해 클라이언트에 즉시 응답 반환

> 요약: 서비스 호출은 동기(REST/gRPC)와 비동기(Message Queue)를 혼용하며, 분산 트랜잭션은 보상 트랜잭션 방식으로 처리된다.

---

## Ⅳ. 특징
- 독립 배포 및 확장: 특정 서비스(예: 이벤트 기간 결제 서비스)만 HPA를 통해 수평 스케일아웃 가능
- 장애 격리(Fault Isolation): 하나의 서비스 지연 및 장애가 시스템 전체로 전파되지 않도록 서킷 브레이커 패턴으로 차단
- 폴리글랏 기술 적용: 데이터 특성에 따라 RDBMS, NoSQL, In-Memory DB 등을 서비스별로 최적화하여 선택 가능

> 요약: MSA는 독립 배포와 장애 격리라는 강력한 이점을 제공하지만, 복잡한 분산 시스템 제어라는 과제를 안겨준다.

---

## Ⅴ. 심화 비교 및 적용 판단

| 비교 축 | 모놀리식 (Monolithic) | 마이크로서비스 (MSA) | 선택 기준 |
|:---|:---|:---|:---|
| 배포·확장 | 전체 통합 빌드/배포, 통째로 확장 | 서비스 단위 개별 배포, 수평 확장 | 서비스 규모 및 트래픽 변동성 |
| 데이터 관리 | 단일 DB, 트랜잭션 완벽 보장 | DB per Service, 분산 트랜잭션 필요 | 데이터 정합성 최우선 vs 독립성 최우선 |
| 운영 복잡도 | 로컬 호출, 디버깅 용이 | 네트워크 홉 증가, 추적 분산 통제 | 개발/운영 자동화 인프라 성숙도 |

> 요약: 초기 개발 속도와 데이터 정합성이 중요하면 모놀리식을, 대규모 트래픽 분산과 조직의 민첩성이 필수적이면 MSA를 선택한다.

**리스크·대응:**
- 분산 트랜잭션 실패: 단일 DB의 ACID 보장 불가 → Saga 패턴(보상 트랜잭션)과 Eventual Consistency 도입 (지표: 트랜잭션 성공률)
- 장애 추적 어려움: 다수 서비스 간 호출 흐름 파악 곤란 → 분산 추적 시스템(Jaeger, Zipkin) 및 중앙 집중형 로깅(ELK) 적용
- 성능 지연(Latency): 서비스 간 RPC 호출 폭증 → gRPC 전환 및 API Gateway를 이용한 Backend for Frontend(BFF) 패턴 적용

**도입 후 점검 지표:**
- 개발 민첩성: 배포 빈도 주 10회 이상, 리드 타임 1일 이내 — DORA 메트릭스 측정
- 서비스 가용성: 장애 전파율 0%, 핵심 서비스 가용성 99.99% — SLO/SLI 기반 모니터링

---

## Ⅵ. 실무 적용 및 결론

**적용 방안 3개:**
1. 아키텍처 분해: 도메인 주도 설계(DDD)의 Bounded Context를 기준으로 서비스를 식별하고, Strangler Fig 패턴을 통해 점진적으로 분리 분해
2. 인프라 자동화: CI/CD 파이프라인 구축 및 Kubernetes 기반 컨테이너 오케스트레이션 적용으로 독립 배포 자동화 구현
3. 통신 및 보안 제어: Service Mesh(Istio 등)를 도입하여 코드 수정 없이 서비스 간 상호 인증(mTLS), 트래픽 라우팅, 서킷 브레이커 적용

**결론 (2줄):**
- 기술사 판단: MSA는 기술의 문제가 아니라 조직 구조(콘웨이의 법칙)와 성숙도의 문제이므로, 충분한 DevOps 역량 확보 후 점진적으로 전환해야 한다.
- 향후 방향: MSA의 분산 복잡도를 줄이기 위해 인프라 제어를 위임하는 Service Mesh와 서버리스 아키텍처로의 발전이 가속화될 것이다.
