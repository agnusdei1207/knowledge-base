## Ⅰ. 개요
- **정의**: 비즈니스 기능 단위로 독립 배포·확장 가능한 서비스를 조합하는 아키텍처
- **배경/필요성**: 모놀리식 구조에서 변경 영향 범위가 전체로 전파되어 배포 주기와 확장성에 한계가 발생함
- **비유**: 푸드코트에서 각 매장이 독립적으로 메뉴·인원·영업시간을 운영하는 구조

| 출제 의도 | 반드시 짚을 핵심 | 감점 회피 포인트 |
|:---|:---|:---|
| 모놀리식 대비 장단점 분석 | 서비스 경계 설정과 데이터 분리 | SOA와의 차이점을 명확히 구분 |

> 요약: 서비스 단위 독립성을 통해 배포·확장의 유연성을 확보하는 분산 아키텍처임

## Ⅱ. 구성요소
```text
Client --> API Gateway --> Service A (DB-A)
                      |-> Service B (DB-B)
                      |-> Service C (DB-C)
                           |
                      Message Broker
```

| 구성요소 | 설명 | 비유 |
|:---|:---|:---|
| API Gateway | 클라이언트 요청을 적절한 서비스로 라우팅하고 인증·로깅을 처리함 | 호텔 프론트 데스크 |
| 서비스 인스턴스 | 단일 비즈니스 기능을 수행하며 자체 DB를 소유함 | 독립 매장 |
| Message Broker | 서비스 간 비동기 통신을 중개하여 결합도를 낮춤 | 우체국 |

> 요약: API Gateway·독립 서비스·메시지 브로커가 핵심 구성이며 서비스별 DB 분리가 원칙임

## Ⅲ. 절차
```text
도메인 분석 --> 서비스 경계 정의 --> 개별 구현/배포 --> 운영/모니터링
```
- 1단계: 도메인 모델을 분석하여 Bounded Context를 식별함
- 2단계: 서비스 경계를 정의하고 API 계약과 데이터 소유권을 확정함
- 3단계: 서비스별 독립 CI/CD 파이프라인을 구축하여 개별 빌드·배포함
- 4단계: 분산 추적·중앙 로깅·헬스체크를 통해 서비스 상태를 관제함

> 요약: 도메인 분석에서 서비스 경계 정의·독립 배포·분산 관제까지의 순환 과정임

## Ⅳ. 문제점
- 분산 트랜잭션: DB 분리로 ACID 보장 불가 — 서비스 간 데이터 정합성 유지가 곤란함
- 운영 복잡도: 서비스 수 증가에 비례하여 배포·모니터링·장애 추적 부담이 급증함
- 네트워크 지연: 서비스 간 원격 호출 증가 — 응답 시간 누적과 부분 장애 전파 위험이 존재함

> 요약: 분산 트랜잭션·운영 복잡도·네트워크 지연이 MSA 전환의 핵심 과제임

## Ⅴ. 개선방안
1. 단기: Saga 패턴(048 참조)을 적용하여 분산 트랜잭션의 정합성을 보완함
2. 중기: Service Mesh(046 참조)와 관측가능성 플랫폼을 도입하여 운영 복잡도를 통제함
3. 장기: 비동기 이벤트 기반 통신(047 참조)으로 전환하여 동기 호출 의존을 축소함

> 요약: Saga·Service Mesh·이벤트 기반 전환으로 MSA 고유 과제를 단계적으로 해결함

## Ⅵ. 전망
- 발전 방향: 서버리스·컨테이너 오케스트레이션과 결합하여 서비스 단위 자동 스케일링이 보편화됨
- 기술사적 판단: MSA 도입 여부보다 적정 서비스 크기와 분해 시점의 판단이 성패를 좌우함
- 기술사 제언: 모놀리식에서 점진적 분해(Strangler Fig) 전략으로 전환 리스크를 최소화할 필요
