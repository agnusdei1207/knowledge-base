# 📖 【암기용】 개념 완전 이해

> 목적: 이 개념을 처음 보는 사람도 완벽히 이해하게 만든다. 시험 답안 양식이 아니라, 이해를 위한 친절한 설명이다.

## 한눈에
- **개요**: **MSA(마이크로서비스 아키텍처)**는 하나의 거대한 통짜 프로그램(모놀리식)을, 기능별(예: 결제, 배송, 장바구니)로 쪼개서 각각 **독립된 미니 서버(서비스)**들로 찢어놓는 현대 소프트웨어 설계의 궁극기다.
- **왜 필요한가**: 쿠팡 앱이 통짜(모놀리식)로 되어있다고 치자. 크리스마스에 사람들이 '장바구니' 기능만 미친 듯이 누르면 앱 전체가 죽는다(단일 장애점). 또한 개발자가 '장바구니' 코드 한 줄 고치고 배포하려면, 멀쩡한 '결제' 서버까지 몽땅 내렸다가 올려야 하는 끔찍한 병목이 터진다.
- **핵심 직관**: 
  - **모놀리식(Monolithic)**: 식당에 주방장(서버) 1명이 국밥, 돈까스, 피자 다 만듦. 돈까스 기계 고장 나면 식당 문 닫음. 국밥 주문 밀리면 돈까스 손님도 하루 종일 기다려야 함.
  - **MSA**: 식당을 찢어서 푸드코트로 만듦. 국밥집, 돈까스집, 피자집(마이크로서비스)이 따로 있고 직원도 주방도 따로 쓴다. 국밥집에 불이 나도 피자집은 정상 영업한다.

## 깊이 이해
- **배경·문제의식**: 스마트폰 시대가 열리며 넷플릭스, 아마존 같은 기업은 하루에 수백 번씩 새로운 기능을 찔러 넣고 업데이트해야 했다. 하지만 1,000명의 개발자가 통짜 소스코드 하나를 건드리니 빌드(배포)에만 하루가 꼬박 걸렸다. 그래서 넷플릭스가 가장 먼저 "서버를 기능별로 수백 개로 갈기갈기 찢자!"며 클라우드 환경에 MSA를 퍼뜨렸다.
- **작동 원리 (MSA의 4대 본질)**:
  1. **독립적 배포 가능 (Independently Deployable)**: 장바구니 팀은 결제 팀 허락 없이 하루에 10번 독자적으로 배포할 수 있다.
  2. **독립적 DB (Database per Service)**: (가장 중요) 장바구니 서버는 장바구니 DB만, 결제 서버는 결제 DB만 가진다. 남의 DB를 몰래 훔쳐보는 건 절대 금지. 무조건 API(통신)로만 물어봐야 한다.
  3. **폴리글랏 (Polyglot Programming/Persistence)**: 언어 통일 불필요. 결제팀은 Java+Oracle로 묵직하게 짜고, 통계팀은 Python+MongoDB로 가볍게 짜도 상관없다.
  4. **장애 격리 (Fault Isolation)**: 배송 서버가 죽어도 결제 서버는 정상 작동한다. 고객은 배송 조회만 안 될 뿐 결제는 할 수 있다.
- **비유**: 
  - 모놀리식 = 초거대 여객선 1척. 빵꾸 나면 1,000명이 다 같이 가라앉음.
  - MSA = 소형 구명보트 100척의 함대. 보트 1대 빵꾸 나도 99대는 정상 항해함.
- **흔한 오해·주의점**: "MSA를 쓰면 무조건 빨라지나요?" 절대 아니다! 모놀리식은 함수끼리 호출하니까 0.0001초면 되는데, MSA는 미니 서버끼리 HTTP(네트워크) 통신을 해야 해서 **속도는 무조건 더 느려진다(네트워크 지연 폭발)**. MSA는 속도를 희생해서 '유연성(배포 속도)'과 '생존력(장애 격리)'을 사는 엄청나게 비싼 거래다.

## 연결 개념
- **도메인 주도 설계 (DDD)**: 거대한 서버를 "어떻게(어떤 기준으로) 쪼갤 것인가?"의 기준이 되는 철학 (예: 결제 도메인, 배송 도메인).
- **API 게이트웨이 (API Gateway)**: 서버를 100개로 찢어놓으면 고객(프론트엔드)이 주소를 다 외워야 하니까, 앞에서 요청을 받아서 교통정리 해주는 단일 출입구.

# 📝 【답안용】 시험 답안 템플릿

> 목적: 시험장에서 25분에 그대로 쓰는 답안 양식. 작성방식(추상표현 금지·수치·도식·문제유형 전환)을 엄격히 지킨다.
> 핵심: 이 시험은 정보를 많이 나열하는 시험이 아니라, 문제 신호어에서 출제자 의도를 읽고 핵심 논점을 선별해 쓰는 시험이다.

## 핵심 인사이트 (3줄 요약)

> 1. **본질**: 단일 프로세스로 구동되던 모놀리식(Monolithic) 애플리케이션을 비즈니스 도메인(기능) 단위로 잘게 쪼개어, 각기 독립적으로 배포 및 확장 가능한 서비스들의 네트워크 집합체로 구성하는 아키텍처다.
> 2. **가치**: 특정 서비스의 장애가 전체로 전파되지 않게 격리(Fault Tolerance)하고, 트래픽이 몰리는 서비스만 골라서 스케일 아웃(Scale-out)할 수 있어 클라우드 네이티브 환경의 자원 효율성과 타임투마켓(Time-to-Market)을 극대화한다.
> 3. **판단 포인트**: 모놀리식과의 물리적 구조 차이(단일 DB vs DB-per-Service)를 짚고, MSA의 치명적 리스크인 분산 트랜잭션 붕괴(데이터 정합성) 문제를 어떻게 보완할 것인가(Saga, Event-Driven)를 설계적으로 방어해야 한다.

## 출제 의도 및 답안 포인트

| 출제 의도 | 반드시 짚을 핵심 | 감점 회피 포인트 |
|:---|:---|:---|
| MSA의 아키텍처적 본질 및 쪼개기(Decoupling) 철학 이해 | 독립적 배포, Database-per-Service, 도메인 분리 | 서버만 쪼개고 DB는 예전처럼 1개 통짜로 공유한다고 적는 최악의 설계 오류 |
| 클라우드 환경과의 시너지 (왜 MSA를 하는가) | 부분적 스케일 아웃(Auto-scaling) 리소스 최적화 효율 | MSA가 모놀리식보다 응답 속도(Latency)가 빨라진다는 거짓 성능 찬양 |
| 분산 시스템이 낳는 치명적 안티패턴(단점)과 대응 기법 | API 지연, 분산 트랜잭션(ACID) 붕괴 -> Saga / CQRS | 장점만 나열하고 분산 아키텍처의 네트워크 복잡성 리스크를 덮어두는 행위 |

> 요약: 서버를 잘게 쪼개면 개발팀은 행복해지지만, 인프라 운영팀과 네트워크는 지옥불에 빠진다. MSA는 이 지옥불을 돈(AWS 클라우드)과 인프라 자동화(DevOps)로 버텨내며 억지로 비즈니스 속도를 뽑아내는 거대 기업용 엔지니어링이다.

## Ⅰ. 개요 및 필요성

- 정의: 애플리케이션을 느슨하게 결합된(Loosely coupled), 독립적으로 배포 가능한(Independently deployable) 다수의 작은 서비스들의 조합으로 설계하는 아키텍처 패턴
- 배경: 비즈니스 요구사항과 트래픽이 폭증하면서 1,000만 줄짜리 모놀리식 코드 베이스의 빌드/배포 시간이 하루 이상 소요되고, 단순한 버그 1개가 서버 전체의 셧다운(SPOF)을 초래하는 한계 도달
- 필요성: 각 비즈니스(도메인) 도메인별로 최적의 언어와 DB를 선택(Polyglot)하고, 부하가 집중되는 모듈만 타겟팅하여 Auto-Scaling 하기 위한 독립적 확장성 확보를 위함

## Ⅱ. MSA vs 모놀리식(Monolithic) 아키텍처 구조 대조 도식

```text
[ 1. 모놀리식 아키텍처 (통짜) ]             [ 2. 마이크로서비스 아키텍처 (MSA) ]
                                          
        [ 프론트엔드 (UI) ]                      [ 프론트엔드 (UI) ]
              |                                          |
+-------------V--------------+               +-----------V-----------+ (API Gateway)
| (한 덩어리 프로세스: WAR/JAR)|               |                       |
|  [주문]  [결제]  [배송]     |         +----V----+      +----V----+      +----V----+
+-------------+--------------+         | 주문 Svc |<---->| 결제 Svc |<---->| 배송 Svc |
              |                        +----+----+  API  +----+----+  API  +----+----+
      [ 거대 단일 통합 DB ]                  |                 |                 |
(테이블끼리 무한 JOIN 쿼리 가능)            [주문 DB]          [결제 DB]          [배송 DB]
                                      (절대 남의 DB 훔쳐보기 금지. 무조건 API 통신 강제)
```

| 비교 축 (Trade-off) | 모놀리식 (Monolithic) | MSA (Microservice Architecture) |
|:---|:---|:---|
| **트래픽 확장성 (Scale-out)** | **비효율적**: 주문만 터져도 결제/배송 코드가 포함된 무거운 서버 전체를 복제해야 함 | **최적화**: 트래픽이 몰리는 '주문 서버'의 인스턴스 갯수만 10배로 즉각 폭증(Scaling) |
| **개발 및 배포 독립성** | 1줄만 수정해도 전체 서버를 컴파일/빌드하고 재기동(Downtime) 해야 함 | 팀별로 서로 눈치 보지 않고 하루 100번 배포 가능 (Time-to-Market 극대화) |
| **내부 통신 오버헤드** | **제로(0)**: 메모리 내부 함수 호출(Call)이라 빛의 속도 | **지옥(Hell)**: 모든 통신이 HTTP/네트워크 구간을 타므로 Latency(지연) 수십 배 폭발 |
| **데이터 정합성 (ACID)** | 단일 DB의 강력한 Transaction 단위 롤백으로 무결성 보장 쉬움 | DB가 찢어져 있어 결제 취소 시 배송 취소 연동 등 분산 트랜잭션 붕괴 리스크 폭발 |

> 요약: MSA를 도입하는 건 100명짜리 대가족이 아파트 100채로 뿔뿔이 흩어져 독립하는 것이다. 사생활(배포 독립성)은 보장되지만, 밥 한 끼 같이 먹으려면 버스(네트워크 API)를 타야 하고 가계부(DB) 맞추기가 미친 듯이 어려워진다.

## Ⅲ. MSA를 완성하는 핵심 생태계(Ecosystem) 컴포넌트 4대장

서버를 100개로 찢으면 서로 통신망이 박살 난다. 이를 수습하기 위한 외부 방어 기제가 반드시 세팅되어야 한다.

| 핵심 컴포넌트 맵핑 | 아키텍처적 방어 및 통제 역할 | 실무 오픈소스 솔루션 |
|:---|:---|:---|
| **API Gateway** | 100개의 서비스 IP를 숨기고, 외부 클라이언트에 단일 출입구(Single Entry Point) 제공. 여기서 인증(Token) 및 라우팅 전담 | Spring Cloud Gateway, AWS API Gateway |
| **Service Registry** | 동적으로 IP가 변하는 수백 개의 컨테이너 인스턴스들의 전화번호부 역할. 서버가 켜지면 IP를 등록하고, 죽으면 명부에서 삭제 | Eureka, Consul, ZooKeeper |
| **Circuit Breaker** | A 서비스가 뻗었을 때, A를 호출하던 B, C 서비스까지 연쇄 타임아웃으로 다 같이 죽는 대참사를 막기 위해 퓨즈(회로)를 강제로 끊어 격리 | Resilience4j, Istio(Service Mesh) |
| **Distributed Tracing**| 사용자 요청 하나가 10개의 서버를 핑퐁 칠 때, 어디서 에러가 났는지 로그에 공통 꼬리표(Trace-ID)를 달아 시각적 추적 확보 | Zipkin, Jaeger, Datadog |

> 요약: 서버만 10개 쪼개놓고 MSA를 했다고 주장하면 3일 안에 서버 10개가 도미노처럼 뻗는다. 게이트웨이와 서킷 브레이커라는 '보호막' 인프라를 깔지 않은 MSA는 자살 행위다.

## Ⅳ. 극복해야 할 시스템적 리스크 (데이터 분산의 덫)

MSA의 가장 끔찍한 부작용은 'Database-per-Service(DB 찢기)' 원칙이 가져오는 트랜잭션 마비다.

| 리스크 요인 | 발생 시나리오 및 시스템 붕괴 원인 | 아키텍처 대응 방안 (실무 패턴 튜닝) |
|:---|:---|:---|
| **분산 트랜잭션 롤백 불가** | 주문 DB(Insert) -> 결제 DB(Insert)는 성공했는데, 배송 DB가 죽었음. 모놀리식은 단일 DB라 `Rollback` 1줄이면 끝이지만, MSA는 남의 DB를 롤백시킬 권한이 없어 데이터 오염 방치 | **Saga (사가) 패턴 + EDA 적용**: Kafka(이벤트 버스)를 통해 통신하고, 에러 시 이전 서비스들에 "아까 한 거 취소해라"라는 보상 트랜잭션(Compensating Transaction) 이벤트를 비동기로 역발송 |
| **복합 조회(Join) 성능 폭망** | 마이페이지에서 '주문내역 + 결제금액 + 배송상태'를 보여주려면 3개의 DB를 Join 해야 하는데, 물리적으로 DB가 찢어져 있어 프론트엔드가 API 3번을 찔러야 함 (로딩 10초) | **CQRS (명령/조회 책임 분리)**: 각 서비스에서 데이터가 바뀔 때마다 변경 내역(Event)을 쏘면, 이를 취합하여 오로지 '조회 전용(Read-only)'의 거대 NoSQL 뷰(View) DB에 미리 구워(미리 Join) 렌더링 최적화 |

> 요약: 옛날 DBA들은 DB가 찢어지는 걸 극혐했다. SQL `JOIN` 한 방이면 끝날 일을 API 3번을 호출하며 조립해야 하니까. 이 태생적 비효율을 해결하려면 결국 이벤트(Kafka)와 비동기 큐를 미친 듯이 깔아서 아키텍처를 뒤덮는 수밖에 없다.

## Ⅴ. 실무 적용 방안 및 결론

**적용 방안 3개:**
1. [Strangler Fig(스트랭글러 피그) 패턴 기반 MSA 점진적 전환] 10년 된 거대 레거시 금융 원장을 일시에 MSA로 엎는 빅뱅(Big Bang)은 자살행위이므로, API Gateway를 앞단에 세우고 비교적 안전한 '알림 서비스'나 '통계' 모듈부터 하나씩 새로운 클라우드 MSA로 빼내어 구형 서버를 서서히 말라 죽게 고사(Strangler)시키는 마이그레이션 적용
2. [DDD(도메인 주도 설계) 기반 Bounded Context 경계 획정] 서비스 크기를 무작정 작게(Micro) 쪼개어 API 통신 비용이 폭발하는 안티패턴을 막기 위해, 이벤트 스토밍(Event Storming) 워크숍을 통해 비즈니스 응집도가 강한 '결제' 도메인과 '배송' 도메인의 경계(Bounded Context)를 긋고 이 단위로 DB를 분할
3. [Service Mesh(서비스 메시) 기반 인프라 로직 분리] MSA 갯수가 100개를 넘어가면서 각 서비스 소스코드에 인증, 로깅, 재시도 로직을 일일이 심는 비용을 없애기 위해, 쿠버네티스 환경에 Istio를 도입하여 비즈니스 컨테이너(App) 옆에 프록시 컨테이너(Envoy)를 붙여 통신 룰을 사이드카(Sidecar) 패턴으로 인프라 계층에 전가

**결론:**
- 기술사 판단: MSA는 코딩 기술이 아니라 조직 공학(Organizational Engineering)이다. 넷플릭스는 "팀이 독립적으로 달리게 하려면 서버와 DB도 독립시켜야 한다"는 콘웨이의 법칙(Conway's Law)을 증명했다. 단, 넷플릭스급 인프라와 CI/CD 성숙도가 없는 기업이 껍데기만 MSA를 따라 하면 분산 시스템의 지옥에 갇히게 된다.
- 향후 방향: MSA의 네트워크 복잡성이 극에 달하자, 최근에는 인프라 프로비저닝조차 개발자가 신경 쓰지 않는 서버리스(Serverless, AWS Lambda) 아키텍처로 넘어가거나, 역으로 MSA를 다시 묶어 잘 모듈화된 모놀리식(Modular Monolithic)으로 회귀하는 실용주의적 펜듈럼 현상도 실리콘밸리에서 관찰되고 있다.
