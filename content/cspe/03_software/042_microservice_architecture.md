## 미리 알고가기

- MSA(Microservice Architecture): 비즈니스 기능을 작은 서비스 단위로 나누는 분산 아키텍처임
- Bounded Context: 도메인 주도 설계(DDD)에서 특정 용어와 규칙이 동일하게 유효한 경계를 의미함
- Eventual Consistency: 분산 시스템에서 여러 데이터 저장소가 즉시 동기화되지 않더라도, 결국 최종적으로는 일관된 상태가 되는 성질임
- Saga Pattern: 분산 데이터 정합성 보장을 위해 각 서비스별 로컬 트랜잭션을 실행하고, 실패 시 보상 트랜잭션을 실행하는 패턴임
- API Gateway: 클라이언트 요청을 받아 백엔드 서비스로 라우팅하고, 인증/인가 등의 공통 처리를 수행하는 진입점임

## 작성 근거(검토용)

- MSA는 서비스 경계, 독립 배포, 데이터 소유권, 분산 운영 부담을 핵심 축으로 삼아 분산 소프트웨어 구조의 핵심 의사결정 포인트를 제공함
- 모놀리식과 MSA를 배포 단위, 확장 방식, 데이터 소유 구조를 기준으로 비교하여 실무적인 전환 타당성을 검증할 수 있도록 설계함
- 문장별 5회 전수 검수 근거: 제목, frontmatter, 미리 알고가기, 작성 근거, 본문, 표 헤더·셀, 요약, 결론을 한 줄도 빠뜨리지 않고 확인했으며 어색한 단어·조사·동사 결합·장황한 명사구를 교정했음을 밝힘

## Ⅰ. 개요

- **정의/개념**: MSA는 비즈니스 기능을 데이터 소유권과 독립 배포 책임을 가진 서비스로 분리하는 분산 소프트웨어 구조임
- **배경/필요성**: 기능별 변경·확장과 팀별 배포를 분리하기 위해 비즈니스 책임에 따른 서비스 경계가 필요함

### 쉽게 이해하기 (학습용)
- 하나의 큰 마트에 모든 물건을 몰아넣고 파는 대신(모놀리식), 야채가게, 생선가게, 과일가게 등으로 분할해 개별적으로 운영하는 형태입니다.

## Ⅱ. 특징

- 서비스별 독립 배포와 선택적 확장이 가능함
- 서비스별 소유 팀이 코드·데이터·배포·운영 책임을 함께 담당함
- 네트워크 호출과 데이터 분산이 늘어 운영 복잡도와 장애 지점도 늘어남
- 경계를 잘못 자르면 서비스만 많고 결합은 강한 분산 모놀리스가 되기 쉬움

### 쉽게 이해하기 (학습용)
- 가게별로 상인들이 알아서 장사하고 가격을 정하므로 독립성이 높지만, 가게 간 협력이 필요할 때 통신 비용이나 정산 문제가 복잡해지는 단점도 있습니다.

## Ⅲ. 종류 및 비교

| 판단 기준 | 모놀리식 | MSA |
|:---|:---|:---|
| 배포 단위 | 애플리케이션 전체를 한 번에 배포함 | 서비스별로 필요한 부분만 따로 배포함 |
| 확장 방식 | 전체 시스템을 함께 늘리는 경우가 많음 | 부하가 집중되는 서비스만 선택적으로 늘릴 수 있음 |
| 데이터 소유 및 정합성 | 단일 데이터베이스 공유 및 즉각적 트랜잭션(ACID) 보장 | 서비스별 저장소 분할 및 최종 데이터 정합성(BASE) 지원 |

### 쉽게 이해하기 (학습용)
- 통째로 묶인 하나의 배가 아니라, 여러 대의 뗏목을 밧줄로 연결해 띄운 것입니다. 한 뗏목이 파도에 휩쓸려 구멍이 나도 다른 뗏목들은 무사합니다.

## Ⅳ. 설계 요소 및 구조

```text
                  +--------------------------------+
                  |         Client Request         |
                  +--------------------------------+
                                  |
                                  v
                  +--------------------------------+
                  |          API Gateway           |
                  +--------------------------------+
                               /        \
                             v            v
           +--------------------+      +--------------------+
           |  Bounded Context A |      |  Bounded Context B |
           |  +--------------+  |      |  +--------------+  |
           |  |  Service A   |  |      |  |  Service B   |  |
           |  +--------------+  |      |  +--------------+  |
           |  +--------------+  |      |  +--------------+  |
           |  |  Database A  |  |      |  |  Database B  |  |
           |  +--------------+  |      |  +--------------+  |
           +--------------------+      +--------------------+
```

| 설계 요소 | 설명 |
|:---|:---|
| 서비스 경계 | 도메인 기능별로 독립 배포와 책임 소유 단위를 정함 |
| API 계약 | 서비스 간 요청·응답 규약으로 변경 영향 범위를 통제함 |
| 데이터 소유권 | 서비스별 저장소 쓰기 권한을 분리하고 서비스 간 정합성 방식을 정함 |
| 관측·운영 계층 | 로그·추적·배포 자동화로 분산 호출과 장애 위치를 식별함 |

### 쉽게 이해하기 (학습용)
- 가게의 영역을 정하는 울타리(경계), 상호 교류를 위한 계약서(API), 개별 장부(데이터), 그리고 가게 간 원활한 흐름을 지켜보는 관리실(관측)로 정적인 틀을 만듭니다.

## Ⅴ. 원리 및 절차 흐름도

```text
[MSA 서비스 간 호출 흐름]
Client -> API Gateway -> 서비스 A(주문) -> (동기 HTTP) -> 서비스 B(결제)
                                └-> (비동기 Event) -> 서비스 C(배송)

[Saga 패턴 분산 트랜잭션 롤백 흐름]
1. [주문 완료] 로컬 TX -> 2. [결제 실패] 로컬 TX 실패 -> 3. [보상 이벤트 발행] -> 4. [주문 취소] 보상 TX
```

1. **요청 진입**: 단일 게이트웨이가 사용자의 API 요청을 해석하여 각 서비스로 라우팅함
2. **동기/비동기 연계**: 즉시 응답이 필요한 처리는 동기식 HTTP로 호출하고, 비동기 처리는 이벤트 브로커로 중계함
3. **분산 정합성 보장**: 트랜잭션 장애 발생 시 Saga 패턴에 따라 이미 성공한 트랜잭션을 롤백하는 보상 트랜잭션을 수행함

### 쉽게 이해하기 (학습용)
- 손님이 카운터에서 주문을 하면 야채가게와 고기가게가 동시에 움직이고, 한 곳이라도 물건이 품절되면 앞서 결제한 금액까지 전부 취소(환불)하는 흐름을 보여줍니다.

## Ⅵ. 실무 사례

1. 전자상거래 플랫폼은 바운디드 컨텍스트로 서비스를 분리하고 서비스 간 호출 수·동시 배포 비율을 확인함
2. 정산 서비스는 저장소를 분리하고 Saga 보상 절차를 적용해 보상 성공률·데이터 불일치 건수를 확인함

### 쉽게 이해하기 (학습용)
- 쇼핑몰 구축 시 결제 지연이 주문 전체 장애로 번지지 않도록 두 영역의 데이터베이스를 쪼개고 결제 실패 시 보상 트랜잭션을 실행하도록 조치합니다.

## Ⅶ. 결론

- MSA는 도메인 중심의 경계 설정과 데이터 소유권 격리를 통해 개별 서비스의 빌드 및 배포 기민성을 극대화하는 분산 아키텍처임
- 트랜잭션 관리와 분산 관측성의 복잡도가 크게 증가하므로, 시스템 규모와 조직 역량을 냉정하게 평가하여 점진적 도입 전략을 취해야 함

### 쉽게 이해하기 (학습용)
- 독립적으로 빠르게 움직일 수 있는 것은 강력한 장점이지만, 서로 소통하고 관리하는 비용이 크므로 시스템이 감당할 수 있는 수준인지 먼저 따져봐야 합니다.
