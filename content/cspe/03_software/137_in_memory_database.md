## Ⅰ. 개요
- **정의**: 데이터를 디스크가 아닌 메인 메모리에 저장하여 마이크로초 수준 응답을 제공하는 DB
- **배경/필요성**: 실시간 처리·캐싱·세션 관리 등 극저지연 요구사항에 디스크 I/O가 병목이 됨
- **비유**: 서류를 캐비닛에서 매번 꺼내지 않고 책상 위에 펼쳐 놓고 작업하는 것과 유사함

| 출제 의도 | 반드시 짚을 핵심 | 감점 회피 포인트 |
|:---|:---|:---|
| 메모리 기반 처리의 장단점 | 영속성 보장 방법(AOF, 스냅샷)과 메모리 관리 | 캐시와 인메모리 DB의 역할 차이 구분 필요 |

> 요약: 메모리 상주 데이터로 극저지연 읽기·쓰기를 달성하는 DB임

## Ⅱ. 구성요소
```text
Client --> Memory Engine --+--> Data in RAM
                           +--> Persistence (AOF / Snapshot)
                           +--> Eviction Policy
```

| 구성요소 | 설명 | 비유 |
|:---|:---|:---|
| Memory Engine | 해시·스킵리스트 등 메모리 최적화 자료구조로 데이터 관리 | 책상 위 정리함 |
| Persistence Layer | AOF 로그·RDB 스냅샷으로 디스크에 영속성 보장 | 퇴근 전 서류 백업 |
| Eviction Policy | 메모리 초과 시 LRU·LFU 등 정책으로 데이터 제거 | 책상 공간 부족 시 정리 |
| Replication | 메모리 데이터를 Replica 노드에 복제하여 가용성 확보 | 동료 책상에 사본 비치 |

> 요약: 메모리 엔진·영속성·제거 정책·복제로 고속·안정적 데이터 관리를 수행함

## Ⅲ. 절차
```text
요청 수신 --> 메모리 자료구조 연산 --> 영속성 기록 --> 응답 반환
```
- 1단계: 클라이언트 요청을 수신하여 명령 파싱
- 2단계: 해시 테이블 등 메모리 자료구조에서 읽기·쓰기 연산 수행
- 3단계: 설정된 영속성 정책(AOF 매 쓰기/주기 스냅샷)에 따라 디스크 기록
- 4단계: 연산 결과를 클라이언트에 응답 반환

> 요약: 메모리 연산 후 영속성을 비동기 기록하여 저지연 응답을 제공함

## Ⅳ. 문제점
- 메모리 용량 제한: 데이터 규모가 물리 메모리를 초과하면 서비스 불가함
- 재시작 시 복구 시간: 대용량 데이터 복원 시 AOF 재생·스냅샷 로드에 시간 소요됨
- 비용 효율성: DRAM 단가가 SSD 대비 높아 대규모 데이터 저장 시 비용 부담 큼

> 요약: 용량 제한, 복구 시간, 비용 효율성이 주요 과제임

## Ⅴ. 개선방안
1. 단기: 메모리 제한 → 핫 데이터만 메모리에 유지하고 콜드 데이터는 디스크 티어링
2. 중기: 복구 시간 → 포크리스 스냅샷·증분 AOF로 복구 시간 단축
3. 장기: 비용 효율 → Persistent Memory(PMEM) 도입으로 용량·비용 균형 확보

> 요약: 티어링, 증분 복구, PMEM 도입으로 인메모리 DB 과제를 단계적 해소함

## Ⅵ. 전망
- 발전 방향: CXL 메모리 풀링 기술과 결합하여 메모리 확장 한계가 완화되는 추세임
- 기술사적 판단: 실시간 처리 수요 증가로 인메모리 아키텍처 설계 역량 중요성이 지속됨
- 기술사 제언: 데이터 특성별 메모리-디스크 티어링 전략을 수립할 것을 제언함
