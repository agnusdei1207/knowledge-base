# 📖 【암기용】 개념 완전 이해

## 한눈에
- **개요**: 데이터를 행(Row)과 열(Column)이 아닌, 유연한 JSON 형태의 문서(Document)로 저장하는 대표적인 NoSQL 데이터베이스이다.
- **왜 필요한가**: 스키마가 고정된 관계형 DB는 구조가 자주 바뀌는 웹 로그나 다양한 형태의 사용자 프로필을 저장할 때마다 테이블을 수정(ALTER)해야 하는 번거로움과 조인(Join)으로 인한 성능 저하가 발생한다.
- **핵심 직관**: 폴더 안에 각기 다른 형태의 서류철(JSON)을 그냥 던져 넣는 방식이다. 서류마다 양식이 달라도 상관없고, 관련된 정보(주문 내역, 배송지)를 서류 한 장에 모두 담아 조인 없이 한 번에 꺼내본다.

## 핵심 용어 정리

| 용어/표기 | 의미 | 비유·예 |
|:---|:---|:---|
| Document | 데이터를 저장하는 최소 단위 (JSON/BSON 형식) | 서류철 한 장 |
| Collection | Document들의 논리적 집합 (RDB의 Table에 해당) | 같은 성격의 서류를 모은 폴더 |
| BSON | Binary JSON, 문서를 이진 형태로 압축하여 저장 | 내용을 압축 코드로 변환해 얇게 만든 서류 |
| Replica Set | 고가용성을 위한 마스터-슬레이브 복제 그룹 | 원본 서류와 복사본을 가진 비서진 |

## 깊이 이해
- **배경·문제의식**: 웹 서비스와 모바일 앱이 발달하면서 비정형·반정형 데이터가 폭발적으로 증가했다. RDBMS는 정규화로 인해 데이터가 여러 테이블에 쪼개져 있어 읽기 시 복잡한 조인이 필요했고, 확장을 위한 수평 분할(Sharding)이 어려웠다.
- **작동 원리**: MongoDB는 관련된 데이터를 하나의 문서(BSON)에 내포(Embedding)하여 저장한다. 읽을 때는 조인 없이 문서 하나만 읽으면 되므로 디스크 I/O가 줄고 속도가 빠르다. 쓰기 확장성은 샤딩(Sharding)을 통해 여러 서버로 데이터를 분산시키고, 안정성은 3대 이상의 노드로 구성된 복제 셋(Replica Set)의 자동 페일오버로 보장한다.
- **비유**: RDBMS가 자동차 부품을 문짝 창고, 바퀴 창고에 따로 보관했다가 주문 시 조립(Join)해서 내보낸다면, MongoDB는 완성된 자동차 자체를 하나의 박스(Document)에 담아 보관하다가 통째로 내보낸다.
- **구체 예시**: 사용자 프로필 저장 시, 사용자 테이블, 연락처 테이블, 취미 테이블을 나눌 필요 없이 `{ "이름": "김철수", "연락처": ["010-111-222", "02-123-456"], "취미": ["독서", "영화"] }` 처럼 배열과 중첩 객체를 사용해 한 문서에 모두 저장한다.
- **흔한 오해·주의점**: "MongoDB는 트랜잭션을 지원하지 않는다"는 과거의 이야기다. v4.0부터 다중 문서 ACID 트랜잭션을 지원한다. 그러나 RDBMS처럼 무분별하게 정규화하고 조인을 남발하면 MongoDB의 장점이 사라지므로, 가급적 하나의 문서에 데이터를 임베딩하는 모델링이 필수적이다.

## 연결 개념
- NoSQL — RDBMS의 대안, 비정형 데이터 처리
- JSON / BSON — 데이터 표현 및 저장 포맷
- Sharding / Replication — 분산 데이터베이스의 핵심 구조

# 📝 【답안용】 시험 답안 템플릿

## 핵심 인사이트 (3줄 요약)

> 1. **본질**: BSON(Binary JSON) 포맷을 사용하여 스키마리스(Schemaless) 구조로 데이터를 저장하는 문서 지향(Document-oriented) 분산 NoSQL 데이터베이스이다.
> 2. **가치**: 데이터 모델의 유연성을 제공하고, 자체적인 Auto-Sharding과 Replica Set을 통해 대규모 수평 확장성과 고가용성을 내장한다.
> 3. **판단 포인트**: 정규화 중심의 RDBMS와 달리, 조인을 최소화하는 내포(Embedding) 중심의 데이터 모델링 전환과 분산 아키텍처 이해가 핵심이다.

## 출제 의도 및 답안 포인트

| 출제 의도 | 반드시 짚을 핵심 | 감점 회피 포인트 |
|:---|:---|:---|
| Document DB의 특징과 아키텍처 이해 확인 | BSON, Replica Set, Auto-Sharding, Embedding | 단순 JSON 저장소로 설명 (분산 아키텍처 누락) |

> 요약: 스키마리스의 유연함뿐 아니라, 샤딩과 복제 셋을 통한 엔터프라이즈급 분산 처리 아키텍처를 제시하는 것이 중요하다.

---

## Ⅰ. 개요 및 필요성

- 개요: JSON 형태의 동적 스키마(BSON)를 사용하여 복잡한 계층 구조 데이터를 하나의 문서(Document)에 내포하여 저장하는 NoSQL DB
- 배경: 웹·모바일 환경의 비정형 데이터 폭증으로 RDBMS의 엄격한 스키마 변경 및 조인 오버헤드가 성능 병목으로 작용
- 필요성: 조인 없는 빠른 읽기 성능, 수평적 확장(Sharding) 지원, 유연한 데이터 모델링이 가능한 대용량 저장소 필요

---

## Ⅱ. 구조 및 구성요소

```text
Application -> mongos (Router) -> Config Servers (Metadata)
                               |
                               +-> Shard 0 (Replica Set: Pri/Sec/Sec)
                               +-> Shard 1 (Replica Set: Pri/Sec/Sec)
```

| 구성요소 | 역할 | 특이사항 |
|:---|:---|:---|
| mongos | 클라이언트 요청을 적절한 샤드로 라우팅 | 애플리케이션 투명성 제공 |
| Config Server | 샤드 키 및 데이터 청크의 위치 메타데이터 저장 | 3대 이상의 복제 셋으로 구성 |
| Shard (Replica Set) | 실제 데이터를 분산 저장하는 노드 그룹 | 1 Primary, N Secondary 자동 페일오버 |

> 요약: 라우터, 메타데이터 서버, 분산 데이터 노드로 역할을 분리하여 투명한 수평 확장과 고가용성을 제공한다.

---

## Ⅲ. 동작원리 및 흐름도

```text
Query 입력 -> 라우팅 판단 -> 분산 쿼리 실행 -> 결과 병합 -> 반환
```

- 1단계 [라우팅 판단]: mongos가 쿼리를 수신하고 Config Server의 메타데이터 참조하여 타겟 샤드 확인
- 2단계 [분산 쿼리 실행]: 대상 Shard의 Primary 노드로 읽기/쓰기 연산 전달 (단일 샤드 또는 스캐터-개더)
- 3단계 [노드 내 복제]: 쓰기 연산 시 Primary에서 Oplog(Operation Log)를 기록하고 Secondary로 비동기 복제
- 4단계 [결과 병합·반환]: 분산 조회 시 mongos가 각 샤드의 결과를 병합(Merge/Sort)하여 클라이언트에 응답

> 요약: mongos를 통한 투명한 샤딩 라우팅과 Oplog 기반의 Replica Set 복제를 통해 확장성과 안정성을 동시 구현한다.

---

## Ⅳ. 특징

- 스키마리스 모델링: 테이블 ALTER 없이 자유로운 필드 추가·삭제 및 배열/서브도큐먼트 형태 내포(Embedding) 지원
- Auto-Sharding: 데이터 청크 크기가 임계치를 넘으면 밸런서(Balancer)가 자동으로 샤드 간 데이터 재분배 수행
- ACID 트랜잭션 지원: v4.0부터 단일 문서를 넘어 다중 문서(Multi-document) 분산 트랜잭션 보장

> 요약: 유연한 모델링과 자동화된 분산 처리를 제공하며, 최신 버전에서는 엔터프라이즈 수준의 정합성까지 지원한다.

---

## Ⅴ. 심화 비교 및 적용 판단

| 비교 축 | RDBMS (MySQL, Oracle) | MongoDB | 선택 기준 |
|:---|:---|:---|:---|
| 데이터 모델 | 정규화 기반 2차원 테이블 | 역정규화·내포 기반 계층형 문서 | 데이터 스키마 변동성 및 조인 빈도 |
| 확장성 | 수직 확장(Scale-up) 위주 | 기본 수평 확장(Scale-out) 지원 | 데이터 증가량 및 쓰기 부하 분산 필요성 |
| 트랜잭션 | 강한 정합성, 광범위 복합 트랜잭션 | 다중 문서 트랜잭션 지원(오버헤드 큼) | 금융 결제 등 복합 정합성 우선 여부 |

> 요약: 구조가 자주 변하고 읽기/쓰기 확장이 중요한 도메인에는 MongoDB를, 조인과 강한 정합성이 중심이면 RDBMS를 선택한다.

**리스크·대응 (기본은 불릿):**
- 샤드 키 설계 실패: 특정 샤드로 부하가 몰리는 핫스팟 현상 발생 → 카디널리티가 높고 쓰기가 고르게 분산되는 해시 기반 샤드 키 선정 (지표: 샤드 간 CPU/I/O 편차)
- 디스크 공간 낭비: BSON 필드명 중복 저장 및 파편화 오버헤드 → 짧은 필드명 사용 및 WiredTiger 엔진 압축 활성화 (지표: 스토리지 압축률)

**도입 후 점검 지표 (기본은 불릿):**
- 성능/효율: 샤드 밸런싱 소요 시간 및 쿼리 응답시간 p95 지표 — APM 모니터링
- 품질/운영: Replica Set 지연(Replication Lag) 2초 이내 유지 — Oplog 지연 시간 관측

## Ⅵ. 실무 적용 및 결론

**적용 방안 3개:**
1. 콘텐츠 관리 및 프로필: 사용자 프로필, 상품 카탈로그 등 속성이 다양하고 구조가 가변적인 데이터를 단일 문서로 모델링하여 조인 제거
2. 대용량 로그 및 이벤트 수집: 시계열 이벤트, IoT 센서 데이터를 수평 확장 가능한 샤드 클러스터에 적재하여 쓰기 병목 해소
3. 하이브리드 아키텍처 구성: 결제/정산은 RDBMS로 처리하고, 고속 조회용 뷰(View)나 상품 상세 정보는 MongoDB로 CQRS 분리

**결론 (2줄):**
- 기술사 판단: MongoDB는 모델링의 유연성과 수평 확장의 이점이 크나, 잘못된 샤드 키 설계나 RDBMS식 조인 남용 시 성능이 급감하므로 워크로드 특성 분석이 선행되어야 한다.
- 향후 방향: 클라우드 네이티브 환경에 맞춰 DBaaS(Atlas) 도입이 가속화되며, 벡터 검색(Vector Search) 기능이 통합되어 RAG 등 AI 백엔드 저장소로 진화 중이다.
