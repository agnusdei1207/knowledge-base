## 핵심 인사이트 (3줄 요약)
- 데이터를 표(Table) 대신 **JSON(BSON) 형태의 문서(Document)로 통째로 저장하는 전 세계 1위의 Document 기반 NoSQL 데이터베이스**.
- 스키마가 없어서(Schema-less) 개발자가 필드를 맘대로 추가/삭제할 수 있는 엄청난 유연성을 제공하며, 복잡한 JOIN 없이 하나의 문서 안에 배열(Array)과 하위 객체를 욱여넣어(Denormalization) 조회 성능을 극대화함.
- 수평 확장(Sharding)과 고가용성(Replica Set)이 기본 내장되어 클라우드 친화적이나, 데이터 중복이 심하고 설계(모델링)를 잘못하면 앱(App) 단에서 데이터 정합성 지옥이 열리는 양날의 검임.

## Ⅰ. 개요 및 필요성
- **개요**: C++로 작성된 오픈소스 비관계형(NoSQL) 데이터베이스로, 데이터를 BSON(Binary JSON) 형식으로 유연하게 저장하고 쿼리하는 시스템.
- **필요성**: 스타트업이나 애자일 환경에서 "어제는 회원 정보에 '전화번호'만 있었는데 오늘은 '인스타그램 주소'와 '좋아하는 영화 3개(배열)'를 추가해야 해!"라는 요구가 매일 빗발침. RDBMS는 그때마다 `ALTER TABLE`을 치고 정규화를 해야 해서 릴리즈가 느려짐. 개발자가 던지는 JSON 객체를 그 모양 그대로 저장해 주는 '개발자 친화적'인 DB가 필요했음.
---
## Ⅱ. 아키텍처 및 핵심 원리
- **MongoDB의 데이터 계층 구조**:
  - `Database` ➡️ `Collection` (RDB의 Table) ➡️ `Document` (RDB의 Row, JSON 형태).
- **핵심 철학: 비정규화 (Denormalization)**:
  - RDB에서는 '게시글'과 '댓글'을 두 테이블로 쪼개고 JOIN함.
  - MongoDB에서는 '게시글' Document 안에 '댓글'을 `Array` 형태로 임베딩(Embedding)해버림. 디스크에 데이터가 연속으로 붙어있으므로 한 방에 긁어오는(Select) 속도가 경이로움.
- **클러스터(Cluster) 아키텍처**:
  - **Replica Set**: 무조건 1개의 Primary(쓰기)와 N개의 Secondary(읽기) 노드를 한 세트로 묶어 장애 복구(Fail-over)를 자동화함.
  - **Sharding**: 데이터가 100GB를 넘어가면 `mongos`(라우터)가 여러 `Shard` 서버로 데이터를 쪼개서 분산 저장함.

```text
[ 데이터 모델링 비교: RDB vs MongoDB ]

 🏢 [ RDB (정규화) - 조인 필수 ]
 [유저 테이블]: ID(1), 이름(철수)
 [주소 테이블]: ID(1), 유저ID(1), 도시(서울) 
 [주소 테이블]: ID(2), 유저ID(1), 도시(부산) ➡️ "철수 정보 다 가져오려면 JOIN 해야 함"

 🍃 [ MongoDB (문서형) - 임베딩 ]
 {
   "_id": 1,
   "이름": "철수",
   "주소": [                ⬅️ (배열로 그냥 집어넣음!)
      {"도시": "서울"}, 
      {"도시": "부산"}
   ]
 } ➡️ "ID 1번 문서 1개만 읽으면 끝! 속도 미침!"
```

## Ⅲ. 비교 및 연결
| 구분 | RDBMS (MySQL) | MongoDB |
|---|---|---|
| **저장 단위** | Table, Row, Column | **Collection, Document, Field** |
| **스키마** | 엄격함 (Schema-rigid) | **자유로움 (Schema-less / Flexible)** |
| **조회 방식** | JOIN 연산 중심 | **내장된(Embedded) 배열 조회 중심** |
| **적합한 서비스**| 송금, 재무, 철저한 트랜잭션 | **쇼핑몰 카탈로그, 게임 유저 정보, 블로그** |
---
## Ⅳ. 실무 적용 및 기술사 판단
- **임베딩(Embedding) vs 레퍼런스(Reference)의 딜레마**: MongoDB를 쓸 때 모든 데이터를 1개의 문서에 쑤셔 넣으면 안 됨. BSON 문서 하나의 최대 크기는 16MB로 제한됨. 예를 들어 '유명 유튜버의 게시글' 문서 안에 '댓글' 100만 개를 배열로 박아 넣으면 문서가 터져버림. 실무 아키텍트는 "자주 같이 읽히고, 개수가 제한적인가?(임베딩)" 아니면 "무한히 늘어나는가?(레퍼런스)"를 분석하여 하이브리드 모델링을 해야 함.
- **트랜잭션의 진화**: 과거 MongoDB는 단일 문서(Document) 레벨의 ACID만 보장했으나, 금융권 등 엔터프라이즈의 요구가 빗발치자 4.0 버전부터 '다중 문서 분산 트랜잭션'을 지원하기 시작함. 하지만 분산 트랜잭션을 남발하면 성능이 RDBMS보다 더 나빠지므로 꼭 필요할 때만 써야 함.

## Ⅴ. 기대효과 및 결론
- "객체 지향 코드(JSON) ➡️ 관계형 DB(Table) ➡️ 객체 지향 코드" 사이의 변환(ORM 패러다임 불일치)을 박살 내고, 프론트-백엔드-DB가 모두 JSON으로 소통하는 MEAN/MERN 스택의 대통합을 이뤄냄.
- 비즈니스 요구사항이 빛의 속도로 변하는 현대 애자일(Agile) 스타트업 생태계에서 가장 사랑받는(Developer Favorite) 개발 생산성 최고의 데이터베이스임.

### 👶 어린이를 위한 3줄 비유 설명
1. 기존 DB(RDB)는 레고 로봇을 보관할 때 "머리통 칸", "팔 칸", "다리 칸"에 무조건 분해해서 넣어야 했어요.
2. **MongoDB**는 "커다란 비닐봉지(Document)"예요! 로봇을 분해할 필요 없이 조립된 채로 봉지에 쑥 넣어서 보관하죠.
3. 나중에 로봇을 꺼내서 놀 때 조립(JOIN)할 필요가 없으니까 엄청나게 빠르고, 스티커나 장신구를 마음대로 더 붙여서 넣어도 봉지가 다 늘어나며 받아준답니다!
