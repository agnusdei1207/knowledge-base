# 📖 【암기용】 개념 완전 이해

## 한눈에
- **개요**: SQL 쿼리를 처리하기 위해 DBMS 옵티마이저가 짜낸 가장 효율적인 데이터 탐색 경로(Execution Plan)를 도출하는 과정이다.
- **왜 필요한가**: SQL은 "무엇을" 찾을지만 지시하므로 수많은 탐색 경로 중 최적의 길을 찾아 디스크 I/O를 최소화하기 위해 필요하다.
- **핵심 직관**: 자동차 내비게이션이다. 목적지(SQL)를 입력하면 내비(옵티마이저)가 교통 통계 정보를 분석해 가장 빠른 경로(실행 계획)를 짠다.

## 핵심 용어 정리

| 용어/표기 | 의미 | 비유·예 |
|:---|:---|:---|
| 옵티마이저 (Optimizer) | DBMS 내에서 최적 실행 경로를 결정하는 핵심 두뇌 | 똑똑한 경로 계산 내비게이션 |
| 비용 기반 최적화 (CBO) | 데이터 분포(통계) 기반으로 I/O 비용을 수학적으로 산출해 선택 | 실시간 교통량 반영 경로 선택 |
| 규칙 기반 최적화 (RBO) | 인덱스 유무 등 사전에 정해진 규칙(우선순위)에 따르는 구형 방식 | 무조건 고속도로만 선호하는 옛날 내비 |
| 통계 정보 (Statistics) | 테이블 행 수, 컬럼 분포도 등을 요약한 메타데이터 | 내비게이션의 도로별 평균 속도 데이터 |

## 깊이 이해
- **배경·문제의식**: 똑같은 결과의 쿼리라도 조인 순서나 인덱스 유무에 따라 응답시간이 0.1초와 1시간으로 갈린다. 인간이 수백만 건의 경로를 다 계산할 수 없으므로 DBMS에 자체 지능이 필요했다.
- **작동 원리**: 파서가 쿼리를 분석하면 옵티마이저는 시스템 카탈로그의 통계 정보를 바탕으로 여러 경로의 디스크 I/O 예상 비용(Cost)을 시뮬레이션하고 가장 싼 경로를 채택해 실행 엔진에 넘긴다.
- **비유**: 주방장(옵티마이저)이 면부터 삶을지 고기부터 볶을지 재료 현황(통계 정보)을 보고 작업 순서(실행 계획)를 짜는 것과 같다.
- **구체 예시**: `EXPLAIN` 쿼리를 치면 "1. A테이블 Index Scan -> 2. B테이블 Full Scan -> 3. Hash Join" 처럼 옵티마이저가 짠 내부 단계가 트리로 나온다.
- **흔한 오해·주의점**: 옵티마이저는 완벽하지 않다. 통계 정보가 낡았거나 쿼리가 너무 복잡하면 바보 같은 판단을 한다. 이때 개발자가 '힌트(Hint)'로 교정해 주는 작업이 쿼리 튜닝이다.

## 연결 개념
- **인덱스 구조**: 옵티마이저가 비용 계산 시 우선 고려하는 탐색 수단.
- **조인 알고 조인 알고리즘**: 옵티마이저가 통계에 따라 Hash, NLJ 중 결정하는 테이블 매칭 방식.

# 📝 【답안용】 시험 답안 템플릿

## 핵심 인사이트 (3줄 요약)

> 1. **본질**: 비절차적 언어인 SQL 요구사항을 물리적인 데이터 디스크 I/O 최적 경로로 변환하는 지능적 엔진의 판단 과정
> 2. **가치**: 데이터 분포를 반영한 비용(Cost) 시뮬레이션을 통해 동일 결과 쿼리의 응답 속도를 수백 배 이상 가속
> 3. **판단 포인트**: 통계 정보에 의존하는 CBO 메커니즘 이해 및 통계 정보 노후화 시 힌트(Hint) 적용 등 튜닝 방안 제시

## 출제 의도 및 답안 포인트

| 출제 의도 | 반드시 짚을 핵심 | 감점 회피 포인트 |
|:---|:---|:---|
| SQL 처리 아키텍처 및 튜닝 원천 메커니즘 이해 | 비용 기반 옵티마이저(CBO) 중심 통계 정보 역할 및 산출 로직 | 구버전인 규칙 기반(RBO)에 편향된 서술 지양 |

> 요약: 통계 정보를 기반으로 최소 디스크 I/O 비용을 산출하여 쿼리 실행의 물리적 파이프라인을 결정한다.

---

## Ⅰ. 개요 및 필요성

- 개요: 사용자의 SQL 요구사항을 처리하기 위해 DBMS 내부 옵티마이저가 가장 효율적인 테이블 접근 경로 및 조인 순서를 결정하는 과정
- 배경: 비절차적 언어 특성 상 접근 경로 명시가 없으므로 최적 경로를 스스로 탐색하는 지능적 엔진 필수
- 필요성: 부적절한 실행 계획은 풀 스캔 등 막대한 디스크 I/O 병목을 초래하므로 시스템 장애 예방을 위한 최적화 기제 필요

---

## Ⅱ. 구조 및 구성요소

```text
[SQL 쿼리 입력] -> 파서(Parser) -> [옵티마이저(Optimizer)] -> 실행 계획 도출 -> [실행 엔진]
                                      ↑(비용 견적 기준)
                               [시스템 딕셔너리 (통계/인덱스)]
```

| 구성요소 | 역할 | 특이사항 |
|:---|:---|:---|
| 쿼리 파서 | SQL 문법 검증 및 논리적 파싱 트리 생성 | 에러 조기 반환 |
| 변환기 (Transformer) | 뷰 병합, 서브쿼리 해소 등 효율적 내부 쿼리 재작성 | 휴리스틱(Heuristic) 기반 |
| 비용 산정기 (Estimator) | 통계 기반으로 수립된 다수 경로의 I/O 비용 수학적 산출 | CBO의 핵심 두뇌 역할 |
| 통계 정보 (Statistics) | 테이블 로우 수, 컬럼 분포도(카디널리티), 인덱스 상태 등 데이터 메타 정보 | 주기적 갱신 필수 |

> 요약: 변환기가 논리적 최적화를 수행하고 비용 산정기가 통계 기반 물리적 견적을 내어 최적 경로를 채택한다.

---

## Ⅲ. 동작원리 및 흐름도

```text
SQL 파싱 -> 쿼리 변환 -> 다수 대안 플랜 탐색 -> 예상 비용(Cost) 산출 -> 최적 플랜 채택(캐싱) -> 엔진 실행
```

- 1단계 구문 분석: SQL의 Syntax 오류 체크 및 파싱 트리 분해
- 2단계 쿼리 재작성: 조인 변환 등 옵티마이저 처리에 용이한 형태로 논리적 재작성
- 3단계 비용 산출(CBO): 가능한 조인 순서(A->B) 및 접근 수단(인덱스 유무) 조합 팩토리얼 도출 후 수학적 I/O 비용 예측
- 4단계 실행 및 캐싱: 최저 비용(Cost)의 플랜(Plan)을 채택하고 동일 쿼리 반복 실행을 위해 메모리(Plan Cache)에 캐싱

> 요약: 여러 후보 경로를 만들고 통계 기반 시뮬레이션 비용 척도로 최저 비용 경로를 확정한다.

---

## Ⅳ. 특징
- 비용 최적화(CBO) 표준: 현대 RDBMS는 정해진 규칙 룰(RBO)을 버리고 철저히 통계 데이터 기반 비용(Cost) 산정 방식을 사용
- 플랜 캐시 의존도: 캐싱된 플랜을 재사용하나 변수 값 분포에 따라 비효율적 플랜이 캐싱되는 스니핑(Sniffing) 부작용 가능
- 통계 정보 민감성: 데이터는 수백만 건인데 통계 정보가 미갱신 시 풀 스캔 등 최악의 판단(가비지 인 가비지 아웃) 도출
- 힌트(Hint) 우선순위: 개발자가 SQL에 힌트를 명시할 경우 옵티마이저 자체 판단을 무시하고 강제 경로 실행 지원

> 요약: 강력한 비용 산정 모델이지만 입력값(통계 정보) 품질에 전적으로 의존하는 민감성을 가진다.

---

## Ⅴ. 심화 비교 및 적용 판단

| 비교 축 | 규칙 기반 최적화 (RBO) | 비용 기반 최적화 (CBO) | 선택 기준 |
|:---|:---|:---|:---|
| 의사결정 기준 | 사전 정의 우선순위 (인덱스 > 조인 등) | 테이블 통계, I/O 비용 수학 산출 | 현대 DBMS는 CBO 표준 |
| 지능형 적응 | 낮음 (정해진 룰만 맹신) | 매우 높음 (분포도 따라 플랜 변경) | 데이터 변동성 대응력 |
| 유지보수 | 불필요 | 정기적 통계 갱신(`ANALYZE`) 필수 | DBA 운영 노력 여부 |

> 요약: 룰 기반(RBO)은 과거 유물이며 현재는 통계 기반 CBO가 주류이나 데이터 통계 관리 책임이 따른다.

**리스크·대응:**
- 통계 노후화로 인한 장애: 대형 배치 직후 통계가 안 맞아 잘못된 인덱스를 타서 시스템 지연 → DML 후 즉시 통계 정보 수집 스케줄링 가동 (지표: 옵티마이저 플랜 변경률)
- 바인드 변수 스니핑: 첫 실행 좁은 범위 플랜이 캐싱되어 다음 대량 범위 쿼리를 망침 → 플랜 캐시 초기화 등 바인드 피킹 파라미터 조정 (지표: 캐싱 히트 응답속도)

**도입 후 점검 지표:**
- 성능/효율: `EXPLAIN` 결과 I/O 블록 수(Cost) — 튜닝 쿼리의 Cost 대폭 감소 확인
- 품질/운영: 플랜 캐시 적중률(Hit Ratio) 확보 — 하드 파싱 억제를 통한 CPU 부하 방어

## Ⅵ. 실무 적용 및 결론

**적용 방안 3개:**
1. 악성 쿼리 강제 힌트 튜닝: 옵티마이저가 한계로 비효율 경로 선택 시 소스코드에 `/*+ USE_HASH(a b) */` 힌트를 기입해 실행계획 수동 고정
2. 주말 자동 통계 갱신 스케줄링: 부하가 적은 주말 새벽 시간대를 활용해 전사 주요 테이블 통계(`GATHER_STATS`) 최신화 배치를 자동화
3. 슬로우 쿼리 플랜 모니터링 체계: APM을 통해 3초 초과 쿼리를 즉시 수집하고 풀 스캔 플랜 여부를 튜닝 담당자에게 경고 알람 전송

**결론:**
- 기술사 판단: 옵티마이저의 올바른 작동은 데이터베이스 성능의 근간이므로 튜닝 엔지니어는 통계 정보를 건강하게 관리하고 필요시 힌트로 개입하는 관제 능력이 필수다.
- 향후 방향: 최근 AI/ML을 접목한 자율주행 데이터베이스(Autonomous DB)가 등장하며 쿼리 패턴을 스스로 학습해 힌트 없이 실행 계획을 교정하는 AI 옵티마이저가 진화하고 있다.
