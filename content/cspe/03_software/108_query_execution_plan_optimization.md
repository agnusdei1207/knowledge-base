## 미리 알고가기

- 실행 계획은 DBMS가 SQL을 실제로 수행하는 접근 경로와 연산 순서를 뜻함
- 옵티마이저는 통계와 비용 추정을 기반으로 계획을 선택함
- 느린 쿼리는 SQL 문장 자체보다 계획 선택 오류에서 자주 발생함

## Ⅰ. 개요

- **정의/개념**: 실행 계획과 쿼리 최적화는 SQL을 어떤 인덱스로 접근하고 어떤 조인 순서와 연산자를 사용할지 비용 기반으로 선택해 응답 시간과 자원 사용량을 최소화하는 데이터베이스 성능 제어 활동임
- **배경/필요성**: 같은 SQL도 통계 정보와 조건 선택도와 조인 순서에 따라 성능 차이가 크게 나므로, 실제 계획을 읽고 교정하는 능력이 필요함

## Ⅱ. 특징

- 옵티마이저는 통계와 비용 모델을 활용해 후보 계획 중 하나를 고름
- 조인 순서와 접근 경로와 정렬 유무가 전체 비용을 좌우함
- SQL 수정 없이도 인덱스와 통계 조정만으로 성능이 크게 바뀔 수 있음
- 잘못된 힌트 남용은 일시적 개선 뒤 장기적으로 더 큰 계획 고착을 낳을 수 있음

## Ⅲ. 종류 및 비교

| 판단 기준 | 규칙 기반 튜닝 | 비용 기반 계획 최적화 |
|:---|:---|:---|
| 판단 방식 | 경험 규칙 중심 | 통계와 비용 추정 중심 |
| 장점 | 빠른 초기 대응 | 다양한 조건에서 합리적 선택 |
| 한계 | 환경 변화 대응 약함 | 통계 오류에 취약 |
| 운영 포인트 | 쿼리 리라이트 중심 | 통계·인덱스·계획 검증 병행 |

## Ⅳ. 구성요소 및 구조

| 구성요소 | 설명 |
|:---|:---|
| Optimizer Statistics | 데이터 분포와 선택도를 제공해 비용 추정 정확도를 좌우함 |
| Access Path | full scan과 index scan과 lookup 경로가 I/O 비용을 결정함 |
| Join Order and Operator | 조인 순서와 NLJ와 Hash Join과 Merge Join 선택이 성능을 좌우함 |
| Plan Review Loop | 실제 실행 결과와 추정치를 비교해 계획 오류를 교정함 |

## Ⅴ. 원리 및 절차 흐름도

```text
+-------------+     +-------------+     +-------------+     +-------------+
| 느린 쿼리 식별  | --> | 계획/통계 분석  | --> | SQL·인덱스 교정 | --> | 재실행 검증     |
+-------------+     +-------------+     +-------------+     +-------------+
```

1. **느린 쿼리 식별**: 병목 SQL과 자원 사용량을 수집함
2. **계획과 통계 분석**: 선택된 접근 경로와 추정 오류를 확인함
3. **SQL과 인덱스 교정**: 쿼리 구조와 인덱스와 통계를 조정함
4. **재실행 검증**: 성능 개선과 부작용을 측정함

## Ⅵ. 문제점 및 해결 방안

1. 문제: 실제 실행 시간만 보고 계획 추정 오류를 확인하지 않으면 같은 병목이 데이터 분포 변화 때 반복될 수 있음
   - 해결방안: estimated vs actual gap을 분석하고 cardinality error ratio와 plan regression count로 검증함
2. 문제: 특정 환경에서만 맞는 힌트를 고정하면 데이터 증가 후 오히려 더 나쁜 계획이 강제될 수 있음
   - 해결방안: hint usage를 최소화하고 adaptive review를 수행하며 hint dependency ratio와 post-growth latency로 검증함
3. 문제: 인덱스 추가만 반복하면 개별 쿼리는 빨라져도 전체 쓰기 성능과 운영 복잡도가 악화될 수 있음
   - 해결방안: global index budget을 운영하고 index maintenance cost와 workload latency balance로 검증함

## Ⅶ. 적용 사례

- 대형 전자상거래 DB에서는 계획 추정 오차를 분석하고 확인 지표는 cardinality error ratio와 plan regression count임
- 배치와 OLTP가 공존하는 환경에서는 힌트 의존을 줄이고 확인 지표는 hint dependency ratio와 post-growth latency임
- 플랫폼 DBA 조직에서는 인덱스 예산을 관리하고 확인 지표는 index maintenance cost와 workload latency balance임

## Ⅷ. 결론

쿼리 최적화의 핵심은 SQL 문장을 감으로 고치는 데 있지 않고 실제 실행 계획과 비용 모델이 왜 그렇게 선택됐는지 설명하는 데 있음.
