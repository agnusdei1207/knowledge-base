# 📖 【암기용】 개념 완전 이해

> 목적: VEX를 처음 봐도 완벽히 이해하게 만든다. 시험 답안 양식이 아니라, 이해를 위한 친절한 설명이다.

## 한눈에
- **개요**: VEX(Vulnerability Exploitability eXchange, 취약점 악용 가능성 교환)는 제품에 포함된 컴포넌트의 **취약점**이 그 제품에서 실제로 **악용 가능한지**(exploitability) 상태와 근거를 공급자가 공식적으로 알리는 문서다.
- **왜 필요한가**: SBOM만으로 CVE를 기계적으로 매칭하면 오탐(false positive)이 쏟아진다. 예를 들어 제품 100개 중 log4j-core를 포함한 제품이 30개라도, 실제로 취약한 코드 경로(JndiLookup 호출)를 쓰는 제품은 그중 5개뿐일 수 있다 — 나머지 25개에 대해 "괜찮다"는 근거를 공식 문서로 답하지 않으면 고객 문의와 긴급 패치 요청이 반복된다.
- **핵심 직관**: SBOM이 "무엇이 들어있나"에 답한다면, VEX는 "그게 우리 제품에서 실제로 위험한가"에 답한다 — 재고 목록과 리콜 통지의 차이와 같다.

## 핵심 용어 정리 (내부에 등장하는 것들)

| 용어 | 의미 | 비유 |
|:---|:---|:---|
| SBOM | VEX가 상태를 부여하는 대상(컴포넌트 목록)의 출처 | 재고 목록 |
| Exploitability (악용 가능성) | 취약점이 실제 공격에 쓰일 수 있는지 여부 — VEX가 판정하는 대상 | 총이 있어도 총알이 없으면 쏠 수 없음 |
| Status: affected | 실제로 영향받음, 조치 필요 | "리콜 대상 맞음" |
| Status: not_affected | 컴포넌트는 있지만 실제 영향 없음 | "부품은 있지만 해당 결함 없음" |
| Status: fixed | 이미 패치 적용됨 | "리콜 수리 완료" |
| Status: under_investigation | 아직 조사 중 | "조사 중, 잠정 보류" |
| Justification (근거 코드) | not_affected를 뒷받침하는 표준화된 이유(코드 미포함·실행경로 미도달·설정 비활성 등) | 리콜 사유서의 근거 조항 |
| Reachability Analysis (도달 가능성 분석) | 취약 코드가 실제 실행 경로에서 호출되는지 정적·동적으로 분석하는 기법 | 부품이 차량의 실제 구동계에 연결됐는지 확인 |
| CSAF | OASIS 표준, VEX를 포함하는 보안 권고 교환 형식 | 정부 공인 리콜 통지 양식 |
| OpenVEX / CycloneDX VEX | 경량·확장형 VEX 구현 형식 | 리콜 통지의 다른 양식들 |

## 깊이 이해

### VEX가 풀려는 문제 — 오탐의 규모를 수치로 보기
- SBOM과 CVE 데이터베이스를 기계적으로 매칭하면 "포함되어 있다=위험하다"로 취급된다. 그러나 Log4Shell 사례에서 log4j-core를 포함한 제품이라도, 애플리케이션 코드가 사용자 입력을 로그 메시지에 그대로 넣지 않거나 JndiLookup 클래스가 코드 경로상 호출되지 않으면 실제 악용은 불가능하다. 한 조직에 제품 100개, 컴포넌트당 평균 CVE 매칭 20건이라면 단순 매칭만으로는 2,000건의 "잠재 위험"이 뜨지만, VEX로 걸러내면 실제 조치가 필요한 건수가 수십 건 수준으로 줄어드는 식이다.

### not_affected 판정의 4가지 표준 근거(Justification)
- OpenVEX/CSAF가 정한 대표 근거는 다음과 같다: ① code_not_present(취약 코드 자체가 빌드에서 제거됨) ② vulnerable_code_not_in_execute_path(코드는 있지만 실행 경로상 호출 안 됨) ③ vulnerable_code_cannot_be_controlled_by_adversary(공격자가 입력을 제어할 수 없는 위치) ④ inline_mitigations_already_exist(설정 등으로 이미 완화됨).
- 예: log4j-core 2.14.1을 포함하지만 `-Dlog4j2.formatMsgNoLookups=true` 설정으로 JNDI lookup 기능을 런타임에 비활성화했다면 근거는 ④(inline mitigation), JndiLookup.class 자체를 jar에서 삭제했다면 근거는 ①(code_not_present)이다 — 근거 코드에 따라 재검증 방법도 달라진다.

### 상태는 고정이 아니라 갱신되는 값이다
- under_investigation은 임시 상태이며 SLA(예: critical CVE 발견 후 24시간 내 1차 상태 발행, 이후 조사 완료 시 affected/not_affected로 확정)로 관리해야 한다. 패치가 배포되면 affected였던 상태도 fixed로 갱신해야 하므로, VEX는 한 번 발행하고 끝나는 문서가 아니라 버전 이력을 갖는 살아있는 문서다.

### 비유와 흔한 오해
- **비유**: 자동차 부품 리콜에서 "이 결함 부품이 목록에 있다"(SBOM)와 "내 차 모델에는 그 부품이 실제로 장착되지 않았다"(VEX, not_affected)는 다른 이야기다. VEX는 후자를 공식 문서로 답한다.
- **오해 1**: VEX는 취약점을 숨기는 문서가 아니다 — not_affected 판정에는 반드시 근거(justification)와 검증 증적이 있어야 하며, 근거 없는 not_affected는 컴플라이언스 위반으로 취급된다.
- **오해 2**: VEX가 있다고 패치가 필요 없어지는 게 아니다 — affected 판정이면 여전히 SLA에 따라 조치해야 하고, VEX는 조치 우선순위를 정확히 하는 도구일 뿐이다.

## 연결 개념
- SBOM — VEX가 상태를 부여하는 대상 컴포넌트 목록의 출처
- CVE/CVSS/EPSS — 취약점 식별과 심각도·악용 확률 지표, VEX의 판단 입력값
- SLSA — 빌드 출처 보증으로 공급망의 또 다른 축(변조 방지)을 담당

# 📝 【답안용】 시험 답안 템플릿

> 목적: 시험장에서 25분에 그대로 쓰는 답안 양식. 작성방식(추상표현 금지·수치·도식·문제유형 전환)을 엄격히 지킨다.
> 핵심: VEX는 SBOM 오탐을 줄이는 취약점 상태 통지이며, 상태값·근거·서명·갱신 절차가 답안의 핵심이다.

## 핵심 인사이트 (3줄 요약)

> 1. **본질**: VEX는 제품별 취약점 영향 상태와 판단 근거를 기계 판독 형식으로 교환하는 보안 문서이다.
> 2. **가치**: SBOM-CVE 매칭 오탐을 줄이고 고객·공급자 간 조치 우선순위와 예외 근거를 일치시킨다.
> 3. **판단 포인트**: affected, not_affected, fixed, under_investigation 상태와 근거 품질, 서명, 갱신 SLA가 평가 기준이다.

## 출제 의도 및 답안 포인트

| 출제 의도 | 반드시 짚을 핵심 | 감점 회피 포인트 |
|:---|:---|:---|
| SBOM 한계 이해 확인 | 구성요소 존재와 악용 가능성 차이 | SBOM과 VEX를 동일 문서로 설명 |
| 취약점 운영 판단 확인 | 상태값, 근거, CVE, 제품 버전 | not_affected 근거 없이 오탐 제거로 표현 |
| 공급망 소통 체계 확인 | CSAF, CycloneDX VEX, OpenVEX, 서명 | 고객 제공·갱신 절차 누락 |

> 요약: 이 문제는 취약점이 "존재"하는지보다 제품에서 "영향"이 있는지를 판단하는 체계를 묻는다.

## Ⅰ. 개요 및 필요성

- 개요: 취약점 영향 상태 교환 문서
- 배경: SBOM 컴포넌트가 CVE와 매칭되어도 제품 코드 경로와 설정에 따라 영향이 다르다.
- 필요성: affected 여부와 근거를 제공해 패치, 예외, 모니터링 우선순위를 정해야 한다.

---

## Ⅱ. 구조 및 구성요소

```text
SBOM Component -> CVE Match -> Product Impact Analysis
-> VEX Status -> Justification -> Signature
-> Customer/SOC Consumption -> Remediation Tracking
```

| 구성요소 | 역할 | 특이사항 |
|:---|:---|:---|
| Product/Version | 영향 판단 대상 | 제품명, 버전, artifact digest |
| Vulnerability | CVE, CVSS, advisory 정보 | CVE ID 필수 |
| Status | affected, not_affected, fixed, under_investigation | 상태별 조치 의미 상이 |
| Justification | 영향 없음 또는 조치 근거 | code_not_present, vulnerable_code_not_in_execute_path |

> 요약: VEX는 제품, 취약점, 상태, 근거를 묶어 취약점 대응 판단을 기계 판독 가능하게 만든다.

---

## Ⅲ. 동작원리 및 흐름도

```text
CVE 수신 -> SBOM 매칭 -> 코드 경로/설정 분석
-> 영향 상태 결정 -> VEX 생성/서명
-> 고객 전달 -> 상태 갱신/패치 추적
```

| 단계 | 처리 내용 | 검증 기준 |
|:---:|:---|:---|
| 1 | CVE와 SBOM 컴포넌트 매칭 | purl/CPE 매칭률 100% |
| 2 | 실행 경로와 설정 영향 분석 | 근거 기록 100% |
| 3 | VEX 상태와 조치 기한 결정 | critical affected SLA 7일 |
| 4 | 문서 서명과 배포 | signature 검증 100% |

> 요약: VEX는 취약점 매칭 후 실제 영향 분석과 상태 통지를 통해 조치 우선순위를 만든다.

## Ⅳ. 특징

| 구분 | SBOM만 사용 | VEX 연계 | 판단 수치 |
|:---|:---|:---|:---|
| 판단 범위 | 컴포넌트 존재 | 제품 영향 상태 | not_affected 근거 100% |
| 운영 효과 | CVE 오탐 다수 | 우선순위 선별 | false positive 50% 이상 감소 목표 |
| 고객 소통 | 수동 질의 응답 | 표준 문서 제공 | 고객 응답 2영업일 이하 |
| 한계 | 영향 판단 부재 | 근거 품질 의존 | 근거 없는 상태 0건 |

> 요약: VEX는 SBOM의 구성요소 목록을 제품 영향 판단과 조치 상태로 확장한다.

## Ⅴ. 심화 비교 및 적용 판단

| 구분 | 기존/대안 | VEX | 선택 기준 |
|:---|:---|:---|:---|
| 구조 | CVE별 수동 안내 | 상태값과 근거의 표준 교환 | SBOM 제공 제품 또는 B2B 납품 |
| 비용/성능 | 모든 CVE 패치 요구 | 영향 기반 우선순위 | 고객 질의 응답 2일 이하 |
| 운영/위험 | 오탐·과소조치 | 근거 부실·상태 갱신 지연 | critical CVE 24시간 내 1차 상태 |

> 요약: VEX는 SBOM을 제공하는 제품에서 취약점 영향 여부를 고객과 동일 기준으로 맞추기 위해 필요하다.

| 리스크 | 원인 | 대응 방안 | 확인 지표 |
|:---|:---|:---|:---|
| 과소 판단 | 실행 경로 분석 오류 | 보안팀 리뷰, 테스트 증적 | not_affected 재분류 0건 |
| 갱신 지연 | under_investigation 방치 | SLA와 만료일 설정 | 상태 미갱신 0건 |
| 신뢰성 부족 | 문서 위변조 | 서명, provenance 연결 | signature 검증 100% |

> 요약: VEX 리스크는 판단 오류, 갱신 지연, 문서 신뢰성이며 리뷰·SLA·서명으로 통제한다.

| 점검 항목 | 목표 기준 | 측정 방법 |
|:---|:---|:---|
| 상태 커버리지 | critical/high CVE VEX 100% | VEX repository |
| 처리 시간 | critical CVE 24시간 내 1차 상태 | vulnerability workflow |
| 근거 품질 | justification 누락 0건 | security review checklist |

> 요약: 운영 수준은 VEX 커버리지, 초기 상태 산출 시간, 근거 누락률로 평가한다.

## Ⅵ. 실무 적용 및 결론

**적용 방안 3개 (필수 — 단계별 또는 항목별):**
1. SBOM 저장소와 CVE feed를 연결하고 critical/high 매칭 시 24시간 내 affected 또는 under_investigation 상태를 생성
2. not_affected 판단은 코드 미포함, 실행 경로 미도달, 설정 비활성, 완화 적용 중 하나의 근거와 테스트 증적을 첨부
3. CSAF, CycloneDX VEX, OpenVEX 중 고객 요구 형식을 선택하고 cosign 서명과 버전별 변경 이력을 보관

**결론 (2줄):**
- 기술사 판단: SBOM 제공 조직은 VEX 없이는 CVE 오탐과 고객 질의를 처리하기 어렵기 때문에 취약점 운영 workflow에 포함
- 향후 방향: VEX는 EPSS, runtime reachability, SLSA provenance와 결합되어 영향 기반 취약점 우선순위 체계로 확장

### 🔀 문제 유형별 목차 전환 (이 키워드 출제 시)

| 유형 | 문제 신호어 | Ⅲ 강조 | Ⅳ 강조 |
|:---|:---|:---|:---|
| 포괄형 | "VEX를 설명하시오" | CVE 매칭, 영향 분석, 상태 발행 흐름 | SBOM 대비 특징 |
| 요구사항 명시형 | "취약점 대응 체계를 설계하시오" | 상태값, 근거, SLA, 서명 절차 | 오탐·과소 판단·갱신 지연 대응 |

> 요약: 설명형은 SBOM과의 차이, 설계형은 상태 판단 근거와 SLA 중심으로 전환한다.
