## Ⅰ. 개요
- **정의**: 특정 제품이 알려진 취약점(CVE)에 실제로 영향을 받는지 여부를 명시하는 보안 문서임
- **배경/필요성**: SBOM(225 참조)만으로는 취약점의 실제 영향도를 판단할 수 없어 오탐 기반 과잉 대응이 발생함
- **비유**: 리콜 공지에 "해당 부품이 포함되어 있으나 해당 결함 조건에 해당하지 않음"을 명시하는 것과 유사함

| 출제 의도 | 반드시 짚을 핵심 | 감점 회피 포인트 |
|:---|:---|:---|
| SBOM과 VEX의 관계 이해 | 4가지 상태값 구분 | VEX는 SBOM의 보완재이지 대체재가 아님을 명시 |

> 요약: SBOM 기반 취약점 목록에 실제 영향 여부를 덧붙여 대응 우선순위를 결정하는 문서임

## Ⅱ. 구성요소
```text
+-------+     +---------+
| SBOM  |---->|   VEX   |
+-------+     +----+----+
                   |
        +----------+----------+
        |          |          |
   +---------+ +-------+ +--------+
   | Product | | Vuln  | | Status |
   |  Info   | | (CVE) | | 판정   |
   +---------+ +-------+ +--------+
```

| 구성요소 | 설명 | 비유 |
|:---|:---|:---|
| 제품 정보 | VEX가 적용되는 대상 제품·버전을 식별함 | 리콜 대상 차종 |
| 취약점(CVE) | 평가 대상인 알려진 취약점 식별자를 명시함 | 결함 번호 |
| 상태(Status) | Not Affected, Affected, Fixed, Under Investigation 4가지로 판정함 | 리콜 판정 결과 |
| 근거(Justification) | Not Affected 판정의 기술적 이유를 기술함 | 비해당 사유서 |

> 요약: 제품·취약점·상태·근거 4요소로 영향도를 기계 판독 가능하게 전달함

## Ⅲ. 절차
```text
취약점 수신 --> 영향 분석 --> 상태 판정 --> VEX 발행
```
- 1단계: 취약점 수신 — CVE 피드 또는 SBOM 기반 스캔 결과에서 취약점 목록 확보
- 2단계: 영향 분석 — 해당 컴포넌트의 호출 경로·구성 조건을 분석하여 실제 영향 여부 판단
- 3단계: 상태 판정 — 분석 결과를 4가지 상태값 중 하나로 분류
- 4단계: VEX 발행 — OpenVEX 또는 CSAF 형식으로 문서를 생성하여 소비자에게 배포

> 요약: 수신-분석-판정-발행 4단계로 취약점 영향도를 공식 전달함

## Ⅳ. 문제점
- 수작업 분석 부담: 영향 분석이 개발자 수동 판단에 의존 — 대량 CVE 발생 시 병목
- 표준 미성숙: OpenVEX, CSAF VEX 등 형식이 혼재 — 소비자 측 파싱 복잡도 증가
- 갱신 주기 불명확: 취약점 상태 변경 시 VEX 재발행 기준이 미정립 — 정보 노후화

> 요약: 수작업 병목, 표준 혼재, 갱신 기준 부재가 VEX 확산의 장벽임

## Ⅴ. 개선방안
1. 단기: 도달 가능성 분석(Reachability Analysis) 도구로 영향 분석 자동화
2. 중기: OpenVEX 표준 단일화 추진으로 형식 호환성 확보
3. 장기: SBOM-VEX 연동 파이프라인 구축으로 CVE 발표 시 자동 재발행 체계 수립

> 요약: 자동 분석 → 표준 단일화 → 자동 재발행 순으로 VEX 운영 성숙도 향상

## Ⅵ. 전망
- 발전 방향: SBOM+VEX 결합이 SW 공급망 투명성의 표준 패키지로 자리잡음
- 기술사적 판단: VEX는 취약점 관리의 오탐 감소와 대응 효율화에 핵심 역할을 수행함
- 기술사 제언: SBOM 도입과 동시에 VEX 발행 체계를 설계할 것을 권고함
