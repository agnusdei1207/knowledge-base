## 핵심 인사이트 (3줄 요약)
- 테이블 크기가 수억 건(수십 GB)을 넘어가면 인덱스(B-Tree) 트리 자체가 너무 커져서 검색과 쓰기 속도가 처참하게 느려짐. 이를 막기 위해 **하나의 거대한 논리적 테이블을 여러 개의 물리적 공간(파티션)으로 찢어 저장하는 최적화 기법**.
- 개발자나 사용자는 하나의 테이블(예: `주문테이블`)에 쿼리를 날리지만, DB 엔진이 알아서 `2023년_파티션`, `2024년_파티션` 등으로 쪼개진 디스크로 찾아가 데이터를 긁어옴(투명성 보장).
- 데이터의 성격에 따라 **수직 분할(컬럼 쪼개기)**과 **수평 분할(로우 쪼개기 - Range, Hash, List)**로 나뉘며, 디스크 I/O 분산과 오래된 데이터의 통째 삭제(Drop Partition)에 압도적인 이점을 제공함.

## Ⅰ. 개요 및 필요성
- **개요**: Very Large DB (VLDB) 환경에서 관리 용이성, 성능 향상, 가용성 확보를 위해 테이블이나 인덱스를 더 작고 관리하기 쉬운 조각(Partition)으로 나누는 작업.
- **필요성**: 로그성 데이터(주문, 결제 이력)가 10년 치가 쌓여 10억 건이 됨. 여기서 '어제 발생한 결제 내역'을 찾기 위해 10억 건짜리 인덱스를 스캔하는 것은 자원 낭비임. 또한 5년 지난 데이터를 삭제(DELETE)하려면 DB에 심각한 락(Lock)과 롤백 세그먼트 부하가 걸리므로, 덩어리째 날려버릴 수 있는 구조적 꼼수가 필요했음.
---
## Ⅱ. 아키텍처 및 핵심 원리
- **파티셔닝의 2가지 방향**:
  1. **수직 파티셔닝 (Vertical Partitioning)**:
     - 뚱뚱한 테이블의 컬럼(Column)을 쪼갬.
     - 자주 조회하는 컬럼(이름, 나이)과 잘 안 읽는 무거운 컬럼(프로필 사진 BLOB, 자기소개 텍스트)을 물리적으로 분리하여, 캐시 히트율(메모리 효율)을 극대화함. 정규화와 원리가 유사함.
  2. **수평 파티셔닝 (Horizontal Partitioning)**:
     - 긴 테이블의 행(Row)을 특정 기준(Partition Key)으로 쪼갬. 실무에서 말하는 파티셔닝의 90%는 이것임.
- **수평 파티셔닝의 기법 4가지**:
  - **Range (범위)**: 가장 많이 쓰임. 날짜/숫자 범위 기준 (예: 1월 파티션, 2월 파티션).
  - **List (목록)**: 특정 그룹 기준 (예: '서울' 파티션, '부산' 파티션).
  - **Hash (해시)**: 파티션 키에 해시 함수를 먹여 N개의 파티션에 균등하게 분산시킴 (특정 달에만 트래픽이 쏠리는 것을 막기 위함).
  - **Composite (복합)**: Range로 연도별 쪼개고, 그 안에서 다시 Hash로 쪼개는 이중 분할.

```text
[ Range 파티셔닝의 동작 원리와 Pruning(가지치기) 효과 ]

 [ 논리적 뷰 (사용자 시점) ]
 ➡️ SELECT * FROM 매출 WHERE 주문일자 = '2024-05-15';

 [ 물리적 저장소 (DB 엔진 시점) ]
 +------------------+   +------------------+   +------------------+
 | p_2024_04 파티션  |   | p_2024_05 파티션  |   | p_2024_06 파티션  |
 | (4월 데이터)      |   | (5월 데이터)      |   | (6월 데이터)      |
 +------------------+   +------------------+   +------------------+
          ❌                      ✅ ⬅️ 엔진이 4월, 6월은 쳐다보지도 않고
                                        5월 파티션 디스크만 빠르게 스캔함 (Pruning)
```

## Ⅲ. 비교 및 연결
| 구분 | 파티셔닝 (Partitioning) | 샤딩 (Sharding) |
|---|---|---|
| **물리적 위치** | **하나의 DB 서버** 내에서 디스크 공간만 분할 | **서로 다른 DB 서버(인스턴스)**로 아예 쪼개서 분산 |
| **목적** | 디스크 I/O 최적화 및 관리(보관 주기) 편의성 | CPU/메모리 부하 분산, 클라우드 스케일아웃(확장) |
| **애플리케이션 영향**| 투명함. (코드에서 `SELECT`만 날리면 엔진이 알아서 함) | 코드가 샤드 키(Shard Key)를 알고 서버를 라우팅해야 함 |
| **복잡도** | 상대적으로 낮음 (DBMS 자체 지원 기능) | 매우 높음 (글로벌 트랜잭션, 데이터 리밸런싱 문제) |

## Ⅳ. 실무 적용 및 기술사 판단
- **Drop Partition의 마법 (데이터 아카이빙)**: 수억 건의 로그 테이블에서 3년이 지난 과거 데이터를 `DELETE` 쿼리로 지우면 DB가 뻗음(Undo Log 폭발). Range 파티셔닝이 되어 있다면 `ALTER TABLE 매출 DROP PARTITION p_2021` 명령어 한 줄로 수천만 건의 데이터를 0.1초 만에 흔적도 없이 삭제(디스크 회수)할 수 있음. 이것이 실무에서 파티셔닝을 적용하는 가장 큰 이유임.
- **파티션 키(Partition Key) 선정의 함정**: WHERE 절에 파티션 키(예: 주문일자)가 포함되지 않은 쿼리를 날리면, DB는 10년 치 파티션을 다 뒤져야 하는 재앙(Partition Full Scan)이 발생함. 기술사는 반드시 비즈니스의 메인 쿼리 패턴을 분석하여, 파티션 프루닝(Pruning, 필요 없는 파티션을 건너뛰는 기술)이 무조건 작동하도록 쿼리 표준과 인덱스 전략(Global vs Local Index)을 설계해야 함.
---
## Ⅴ. 기대효과 및 결론
- RDBMS가 클라우드 NoSQL로 넘어가기 전, 단일 몬스터 서버 내에서 테라바이트(TB) 급의 초거대 데이터를 다룰 수 있게 해주는 가장 현실적이고 우아한 DBA의 검(Sword)임.
- "분할하여 정복하라(Divide and Conquer)." 데이터가 무한히 쌓이는 현대 비즈니스 환경에서, 생명주기(Data Life Cycle) 관리와 검색 성능 두 마리 토끼를 동시에 잡는 필수 아키텍처임.

### 👶 어린이를 위한 3줄 비유 설명
1. 10년 치 일기가 두꺼운 공책 한 권에 다 적혀있으면, 작년 5월 5일 일기를 찾을 때 공책을 계속 넘겨야 해서 팔이 아파요.
2. **파티셔닝**은 일기장을 아예 월별로 찢어서 서랍에 12개의 얇은 수첩으로 나누어 놓는 거예요. 겉보기엔 하나의 일기장 같지만요!
3. 그럼 "5월 일기"를 찾을 때 5월 수첩만 쏙 꺼내서 보면 되고(검색 속도 짱!), 작년 일기를 버릴 때도 수첩 하나만 쓰레기통에 툭 던지면 끝나니까 아주 편하답니다!
