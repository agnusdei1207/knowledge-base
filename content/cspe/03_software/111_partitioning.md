# 📖 【암기용】 개념 완전 이해

> 목적: 파티셔닝을 처음 보는 사람도 완전히 이해하게 만든다. 시험 답안 양식이 아니라, 이해를 위한 설명이다.

## 한눈에
- **개요**: 파티셔닝(Partitioning)은 하나의 논리 테이블을 물리적으로 여러 조각(파티션)으로 나누는 **수평 분할** 기법이며, 같은 DB 인스턴스 내부에서 이루어진다는 점이 핵심 정체성이다.
- **왜 필요한가**: 테이블이 수십억 행으로 커지면 전체 스캔, 인덱스 재구성, 백업에 걸리는 시간이 함께 커진다. 조회·삭제·백업이 항상 테이블 전체가 아니라 일부(최근 한 달, 특정 테넌트)에 집중된다면, 그 일부만 물리적으로 분리해두는 편이 훨씬 싸다.
- **핵심 직관**: 창고에 모든 물건을 한 곳에 쌓지 않고 월별·지역별 구역으로 나눠, 찾을 구역 하나만 열어보는 방식이다.

## 핵심 용어 정리 (내부에 등장하는 것들)

| 용어 | 의미 | 비유 |
|:---|:---|:---|
| 파티셔닝(Partitioning) | 논리적으로 하나인 테이블을 물리적으로 여러 조각으로 나누는 것 — 이 개념 자체 | 창고를 구역별로 나누기 |
| 파티션 키(Partition Key) | 어느 파티션에 행이 들어갈지 정하는 기준 컬럼(날짜·지역·ID 등) | 물건을 어느 구역에 둘지 정하는 분류 기준 |
| Range Partition(범위 파티션) | 연속된 값 구간(날짜·금액 범위)으로 나누는 방식 | 월별로 구역 나누기 |
| Hash Partition(해시 파티션) | 키에 해시 함수를 적용한 값으로 균등하게 나누는 방식 | 물건 번호를 해시로 섞어 여러 칸에 고르게 배분 |
| List Partition(리스트 파티션) | 명시적으로 지정한 값 집합(지역 코드·상태 값)으로 나누는 방식 | "서울/부산/대구" 식으로 정해진 목록에 따라 구역 배정 |
| 파티션 프루닝(Partition Pruning) | 쿼리의 조건절을 보고 옵티마이저가 관련 없는 파티션은 아예 건드리지 않고 건너뛰는 최적화 | 찾는 물건이 3월 것임을 알면 3월 구역만 열어봄 |
| 로컬 인덱스(Local Index) | 파티션마다 독립적으로 갖는 인덱스 — 해당 파티션 데이터만 색인 | 구역마다 따로 있는 색인 카드함 |
| 글로벌 인덱스(Global Index) | 모든 파티션을 아우르는 하나의 인덱스 — 전역 유일성 검증 등에 필요 | 창고 전체를 아우르는 통합 색인 카드함 |
| 핫 파티션(Hot Partition)·Skew | 특정 기간·키에 쓰기·조회가 몰려 그 파티션만 과부하되는 현상 | 최신 물건이 들어오는 구역 하나만 계속 붐빔 |

## 깊이 이해

### 왜 필요한가 — 숫자로 보는 단일 테이블의 한계
- OLTP 주문 테이블이 매일 100만 건씩 쌓여 3년 뒤 약 10억 행이 됐다고 하자. 이 상태에서 인덱스 하나를 재구성(REBUILD)하려면 10억 행 전체를 다시 정렬해야 하고, 백업도 매번 전체를 떠야 한다. 반면 이 테이블을 월별로 나눠 36개 파티션(파티션당 약 2,800만 행)으로 관리하면, 최근 파티션 하나만 자주 갱신·백업하면 되고 나머지는 거의 손대지 않는다.

### 파티션 프루닝의 동작 — 조건이 곧 접근 범위를 줄인다
- `WHERE order_date BETWEEN '2026-06-01' AND '2026-06-30'` 조건이 있고 테이블이 월별 Range Partition으로 나뉘어 있으면, 옵티마이저는 36개 파티션 중 2026년 6월 파티션 딱 1개만 스캔 대상으로 남긴다(파티션 프루닝). 접근 대상이 36개 중 1개, 즉 약 2.8%로 줄어든다.
- 반대로 파티션 키 조건이 SQL에 없거나(`WHERE customer_id = 100`처럼 파티션 키가 아닌 컬럼만 조건에 있음), 조건절에 함수가 씌워져 있으면(`WHERE YEAR(order_date) = 2026`) 옵티마이저가 프루닝 판단을 못 해 36개 파티션을 전부 스캔하는 최악의 경우로 되돌아간다.

### 세 파티션 방식을 언제 쓰는가 — 판별 원리
- **Range**: 조회 조건이 날짜·금액처럼 연속 구간으로 자주 걸리고, 오래된 구간을 통째로 삭제(보관 만료)해야 할 때. 삭제는 `DELETE`로 수백만 건을 지우는 대신, 파티션 자체를 `DROP PARTITION`으로 제거하면 로그 기록 없이 수초 내에 끝난다.
- **Hash**: 특정 값에 쓰기가 몰리는 것(예: 최신 날짜에만 쓰기 집중)을 피하고 여러 파티션에 균등하게 분산하고 싶을 때. 다만 해시는 순서를 보존하지 않아 범위 조회에는 프루닝 효과가 없다.
- **List**: 값의 종류가 적고 명시적으로 정해져 있을 때(지역 코드 5개, 상태 값 3개 등).

### 로컬 인덱스 vs 글로벌 인덱스 — 유지보수 비용의 차이
- 로컬 인덱스는 파티션 하나에만 걸려 있으므로, 오래된 파티션을 `DROP`해도 그 파티션의 로컬 인덱스만 함께 사라진다 — 유지보수가 파티션 단위로 끝난다.
- 글로벌 인덱스는 모든 파티션을 아우르므로, 파티션 하나를 `DROP`해도 전체 글로벌 인덱스를 다시 손봐야 할 수 있다. 예를 들어 전역 유일 제약(unique key)을 파티션 키가 아닌 다른 컬럼에 걸어야 한다면 글로벌 인덱스가 불가피하지만, 그만큼 파티션 교체 비용이 커진다.

### 핫 파티션 — 균등해 보이는데 왜 몰리나
- Range Partition에서는 항상 "가장 최근" 파티션에 신규 쓰기가 집중된다. 예를 들어 일 1억 건 로그를 월별 파티션으로 나눠도, 이번 달 파티션 하나가 쓰기의 100%를 받는다. 이를 완화하려면 `날짜 + 해시`처럼 두 키를 복합해 같은 날짜 안에서도 여러 서브 파티션으로 쓰기를 흩뿌린다.

### 파티셔닝과 샤딩의 경계 — 흔한 오해
- 파티셔닝은 **같은 DB 인스턴스, 같은 서버** 내부에서 저장 단위만 나누는 것이다. CPU·메모리·디스크 IOPS 한계는 여전히 그 한 대의 서버에 남아 있다. "파티션을 늘리면 서버가 여러 대로 늘어난 것처럼 처리량이 는다"는 것은 오해다 — 여러 물리 노드로 데이터를 흩어 처리량 자체를 늘리는 것은 파티셔닝이 아니라 샤딩(112)의 역할이다.

## 연결 개념
- 샤딩(112) — 파티션 개념을 여러 물리 노드로 확장한 것, 단일 서버 한계에 도달했을 때 다음 단계
- 파티션 프루닝 — 조건절 기반 접근 범위 축소, 이 개념의 핵심 성능 이득
- 로컬/글로벌 인덱스 — 파티션 단위 유지보수 비용을 좌우하는 설계 선택

## Ⅰ. 개요 및 필요성

- 개요: 파티셔닝은 테이블 물리 분할 기법이다.
- 배경: 데이터 증가로 전체 스캔, 인덱스 재구성, 백업 시간이 증가하면 단일 테이블 운영 비용이 커진다.
- 필요성: Range, Hash, List Partition과 partition pruning으로 접근 범위와 보관 주기별 삭제·압축·백업 단위를 분리해야 한다.

---

## Ⅱ. 구조 및 구성요소

```text
Application SQL -> Partitioned Table
  / Range Partition: 날짜·금액 구간
  / Hash Partition: 해시 버킷
  / List Partition: 지역·상태 코드
Optimizer -> Partition Pruning -> Local/Global Index -> Storage Segment
```

| 구성요소 | 역할 | 특이사항 |
|:---|:---|:---|
| 파티션 키 | 분할 기준 컬럼 | 날짜·tenant_id·region 등 조회 조건과 일치 필요 |
| 범위 파티션 | 연속 구간 분리 | 월별 보관, sliding window에 적합 |
| 해시 파티션 | 해시값으로 균등 분배 | 범위 조회보다 균등 쓰기 분산에 적합 |
| 리스트 파티션 | 명시 값 집합 분리 | 지역·상태 코드처럼 값 종류가 제한된 경우 적합 |
| 인덱스 전략 | 로컬/글로벌 인덱스 선택 | 로컬은 유지보수 단순, 글로벌은 전체 유일성 검증에 사용 |

> 요약: 파티셔닝 구조는 키, 분할 방식, 프루닝, 인덱스 전략이 결합되어 조회 범위와 운영 비용을 결정한다.

## Ⅲ. 동작원리 및 흐름도

```text
SQL 조건 입력 -> 파티션 키 조건 추출
  / 키 조건 있음 -> 대상 파티션 목록 산정 -> local index scan
  / 키 조건 없음 -> 전체 파티션 scan -> 비용 증가
결과 병합 -> 실행 계획·통계 갱신
```

| 단계 | 처리 내용 | 검증 기준 |
|:---:|:---|:---|
| 1 | SQL 파싱 후 `where order_date` 등 파티션 키 조건 확인 | 실행 계획에 partition pruning 표시 |
| 2 | 파티션 메타데이터에서 대상 파티션 목록 산정 | 접근 파티션 수 1~3개 수준 |
| 3 | 로컬 또는 글로벌 인덱스로 데이터 접근 | index range scan, bitmap scan 여부 |
| 4 | 파티션별 결과 병합 및 정렬 | merge sort 메모리 사용량 |
| 5 | 통계 갱신과 파티션 교체 수행 | analyze 주기, attach/drop 소요시간 |

> 요약: 파티션 키 조건이 실행 계획에 반영될 때 접근 파티션 수가 줄고, 키 조건 누락 시 전체 파티션 스캔으로 전환된다.

## Ⅳ. 특징

| 구분 | 기존 단일 테이블 | 파티셔닝 적용 | 수치·판단 기준 |
|:---|:---|:---|:---|
| 조회 범위 | 전체 테이블 후보 | 조건에 맞는 파티션만 접근 | 월별 36개 중 1개 접근 |
| 삭제 | 대량 `DELETE`와 로그 증가 | `DROP/TRUNCATE PARTITION` | 보관 만료 삭제 수초~수분 |
| 인덱스 | 하나의 대형 인덱스 | 로컬/글로벌 인덱스 선택 | 재구성 범위 파티션 단위 |
| 쓰기 분산 | 특정 최신 구간 집중 | 해시·복합 키로 분산 | 핫 파티션 write 비율 40% 이하 |
| 한계 | 구조 단순 | 파티션 수·통계 관리 필요 | 수천 개 이상이면 계획 비용 증가 |

> 요약: 파티셔닝은 조회·삭제·인덱스 유지 범위를 줄이지만, 키 설계와 파티션 수 관리가 부실하면 계획 비용과 skew가 증가한다.

## Ⅴ. 심화 비교 및 적용 판단

| 구분 | 기존/대안 | 본 키워드 | 선택 기준 |
|:---|:---|:---|:---|
| 구조 | 단일 테이블 | 논리 테이블 + 물리 파티션 | 테이블 1억 행 이상, 기간 조건 빈번 |
| 분산 범위 | 단일 스토리지 | 동일 DB 내부 분할 | 서버 CPU 한계 전까지 적용 |
| 조회 | 전체 인덱스 후보 | partition pruning | 파티션 키가 주요 조건절에 포함 |
| 운영 | 대량 삭제·백업 | 파티션 단위 교체 | 보관주기 월/분기 단위 |
| 확장 대안 | 샤딩 | 파티셔닝 선적용 | 단일 노드 IO 포화 전 단계 |

> 요약: 단일 DB 내 데이터 관리 문제는 파티셔닝으로 먼저 줄이고, 노드 한계가 명확할 때 샤딩을 검토한다.

| 리스크 | 원인 | 대응 방안 | 확인 지표 |
|:---|:---|:---|:---|
| 핫 파티션 | 최신 날짜에 쓰기 집중 | 날짜+해시 복합 파티션 | 상위 파티션 write 비율 |
| 프루닝 실패 | 조건절 함수 가공, 키 누락 | 원본 키 조건 유지, generated column | explain 대상 파티션 수 |
| 글로벌 인덱스 비용 | 파티션 drop 시 전체 인덱스 갱신 | 로컬 인덱스 우선, 유일키 재설계 | index maintenance time |
| 파티션 폭증 | 일 단위 장기 보관 | 월 단위 병합, 보관 정책 자동화 | 파티션 개수 1,000개 이하 |

> 요약: 핵심 리스크는 핫 파티션과 프루닝 실패이며, 실행 계획과 파티션별 부하 분포로 통제한다.

| 점검 항목 | 목표 기준 | 측정 방법 |
|:---|:---|:---|
| 프루닝 | 주요 쿼리 접근 파티션 5% 이하 | `EXPLAIN`, DBMS 실행 계획 |
| 쿼리 지연 | p95 조회 지연 100ms 이하 | APM, slow query log |
| 운영 작업 | 월 파티션 삭제 5분 이내 | maintenance job log |

> 요약: 파티셔닝 효과는 접근 파티션 수, p95 지연, 유지보수 시간, 저장공간 감소율로 판단한다.

## Ⅵ. 실무 적용 및 결론

**적용 방안 3개 (필수 - 단계별 또는 항목별):**
1. 키 설계: 주문·로그는 `created_at` range + `tenant_id` hash 복합 파티션으로 월별 보관과 쓰기 분산을 동시에 반영함
2. 인덱스 설계: 파티션 키를 선두 컬럼에 두고 로컬 인덱스를 기본값으로 채택, 전역 유일성은 별도 sequence 또는 UUID로 처리함
3. 운영 자동화: 13개월 보관 정책을 `CREATE/ATTACH/DROP PARTITION` 배치로 구현하고 `EXPLAIN` 기반 프루닝 회귀 테스트를 배포 전 수행함

**결론 (2줄):**
- 기술사 판단: 조회 조건이 기간·테넌트 중심이면 파티셔닝, 단일 노드 CPU·IO가 70% 이상 지속되면 샤딩 검토가 타당함
- 향후 방향: HTAP·클라우드 DB에서는 자동 파티션 추천, tiered storage, workload 통계 기반 재배치가 결합되는 방향임

### 🔀 문제 유형별 목차 전환 (이 키워드 출제 시)

| 유형 | 문제 신호어 | Ⅲ 강조 | Ⅳ 강조 |
|:---|:---|:---|:---|
| 포괄형 | "파티셔닝을 설명하시오", "기술하시오" | range/hash/list 원리와 pruning 흐름 | 단일 테이블 대비 조회·운영 차이 |
| 요구사항 명시형 | "설계하시오", "비교하시오", "운영 방안을 제시하시오" | 업무 조건별 키 선택과 인덱스 전략 | 핫 파티션, 글로벌 인덱스, 유지보수 대응 |
