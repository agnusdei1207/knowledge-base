# 📖 【암기용】 개념 완전 이해

## 한눈에
- **개요**: 대용량 테이블을 작은 논리적 단위(파티션)로 나누어 분산 저장·관리하는 데이터베이스 기법
- **왜 필요한가**: 수십억 건의 데이터가 쌓인 단일 테이블은 인덱스 트리가 거대해져 검색이 느려지고, 오래된 데이터를 지우는 배치 작업에 엄청난 락(Lock)과 리소스가 소모된다.
- **핵심 직관**: 백과사전을 가나다순으로 권별로 쪼개놓으면, '가'로 시작하는 단어를 찾을 때 '가' 권만 뒤지면 되고, 나중에 '가' 권만 따로 버리거나 교체하기도 쉽다.

## 핵심 용어 정리

| 용어/표기 | 의미 | 비유·예 |
|:---|:---|:---|
| 수평 파티셔닝 | 행(Row)을 기준으로 테이블을 분할 | 백과사전을 ㄱ~ㅎ 권으로 나눔 |
| 수직 파티셔닝 | 열(Column)을 기준으로 테이블을 분할 | 이름·전화번호부와 이름·주소부로 나눔 |
| 파티션 키 | 데이터를 나눌 기준이 되는 컬럼 | '가입일자'나 '고객ID' |
| 파티션 프루닝 (Pruning) | 쿼리 시 불필요한 파티션을 검색 대상에서 제외 | 2026년 조회 시 2025년 파티션 무시 |

## 깊이 이해
- **배경·문제의식**: VLDB(Very Large Database) 환경에서 테이블 크기가 커지면 인덱스의 깊이(Depth)가 깊어져 B-Tree 탐색 성능이 저하된다. 특정 기간의 데이터를 일괄 삭제(Purge)할 때 대량의 DELETE가 발생하여 트랜잭션 로그가 꽉 차고 성능 병목이 발생한다.
- **작동 원리**: 데이터베이스 내부적으로는 여러 개의 물리적 테이블로 쪼개지만, 애플리케이션(사용자) 입장에서는 하나의 논리적 테이블로 접근한다. 파티션 키에 따라 DBMS가 알아서 데이터를 적절한 파티션에 라우팅한다.
- **비유**: 회사 서류철을 연도별로 캐비닛에 보관(Range)하고, 5년 지난 캐비닛은 통째로 창고로 보낸다(Drop Partition). 캐비닛 안에서는 부서별로 폴더(List)를 나눈다.
- **구체 예시**: 로그 데이터를 `CREATE TABLE ... PARTITION BY RANGE (log_date)`로 생성하면, 매달 새로운 파티션을 추가하고 오래된 파티션을 `DROP PARTITION`으로 1초 만에 날릴 수 있다.
- **흔한 오해·주의점**: 파티셔닝은 성능을 무조건 향상시키지 않는다. 파티션 키를 조건에 포함하지 않는 쿼리는 모든 파티션을 다 뒤져야 하는 오버헤드(Partition Scan)가 발생해 단일 테이블보다 느려질 수 있다.

## 연결 개념
- 샤딩 (Sharding): 파티셔닝이 한 DB 내의 물리적 분할이라면, 샤딩은 물리적으로 다른 DB 서버로 쪼개는 수평 분할 기법
- 인덱스 분할 (Local/Global Index): 파티션 테이블에 인덱스를 생성할 때 파티션별로 종속시킬지 전체를 아우를지 결정하는 구조

# 📝 【답안용】 시험 답안 템플릿

## 핵심 인사이트 (3줄 요약)

> 1. **본질**: 파티셔닝은 초대용량 테이블(VLDB)을 파티션 키를 기준으로 다수의 물리적 세그먼트로 분할해 성능과 관리성을 높이는 기법이다.
> 2. **가치**: 불필요한 영역을 배제하는 파티션 프루닝(Pruning)으로 I/O를 최소화하고, Drop 파티션을 통해 삭제 트랜잭션 부하를 제거한다.
> 3. **판단 포인트**: 데이터 특성에 맞는 분할 방식(Range·Hash·List)을 선택하고, 파티션 인덱스(Local/Global) 전략을 병행해야 병목을 방지한다.

## 출제 의도 및 답안 포인트

| 출제 의도 | 반드시 짚을 핵심 | 감점 회피 포인트 |
|:---|:---|:---|
| VLDB 관리 및 튜닝 기법 이해 | Range·Hash·List 기법 비교, 파티션 프루닝 명시 | 파티셔닝과 샤딩(서버 간 분할) 혼동 |
| 파티션 인덱스 설계 역량 확인 | Local 인덱스와 Global 인덱스의 구조적 차이 비교 | 파티셔닝이 무조건 빠르다는 단정 |
| 데이터 생명주기 운영 역량 | 대용량 이력 데이터의 Drop Partition을 통한 Purge 효율화 | 범위 파티셔닝 시 MAXVALUE 설정 누락 |

> 요약: 단일 서버 내에서의 분할 기법인 파티셔닝 유형과 인덱스 전략, 그리고 이를 통한 VLDB 성능 및 관리 효율화 방안을 제시해야 한다.

---

## Ⅰ. 개요 및 필요성

- 개요: VLDB의 큰 테이블과 인덱스를 관리 가능한 작은 물리적 단위(파티션)로 분할하는 데이터베이스 관리 기법
- 배경: 단일 테이블이 기가/테라바이트 단위로 커지면 인덱스 깊이 증가로 탐색 비용이 급증하고 Lock 경합이 심화됨
- 필요성: 파티션 프루닝을 통한 디스크 I/O 90% 이상 절감 및 파티션 단위 DDL 작업을 통한 운영 중단 최소화 필요

---

## Ⅱ. 구조 및 구성요소

```text
Application Query -> DBMS Optimizer (Partition Pruning 적용) -> Partitioned Table
                                                                  |
                                                                  +-> Partition A (2026-01)
                                                                  +-> Partition B (2026-02)
                                                                  +-> Partition C (2026-03)
```

| 구성요소 | 역할 | 특이사항 |
|:---|:---|:---|
| 파티션 키 (Partition Key) | 데이터를 물리적으로 나눌 기준 컬럼 | 변동이 적고 고르게 분포된 컬럼 권장(날짜 등) |
| 로컬 인덱스 (Local Index) | 개별 파티션과 1:1로 종속되어 생성되는 인덱스 | 파티션 DDL 수행 시 타 파티션 영향 없음 |
| 글로벌 인덱스 (Global Index) | 전체 파티션을 통합하여 단일 구조로 생성되는 인덱스 | 특정 파티션 Drop 시 전체 인덱스 무효화 위험 |

> 요약: 논리적으로는 단일 테이블로 보이나, 물리적으로는 파티션 키 기준의 개별 세그먼트로 나뉘며 인덱스 종속성에 따라 로컬과 글로벌로 구분된다.

---

## Ⅲ. 동작원리 및 흐름도

```text
SQL Request -> Partition Pruning (조건 분석) -> Target Partition 접근
-> Local/Global Index 탐색 -> Data Fetch -> Result Return
```

- 1단계 [쿼리 최적화]: Optimizer가 WHERE 절의 파티션 키 조건을 분석하여 접근할 파티션 목록 도출
- 2단계 [파티션 프루닝]: 불필요한 물리적 파티션을 디스크 I/O 스캔 대상에서 완전히 배제
- 3단계 [인덱스 스캔]: 선택된 파티션의 인덱스(Local 등)를 통해 데이터 블록의 ROWID 식별
- 4단계 [데이터 추출]: 도출된 ROWID로 디스크 블록에 접근하여 결과를 Fetch 후 사용자 반환

> 요약: Optimizer가 쿼리 조건을 분석해 스캔 범위를 특정 파티션으로 한정(Pruning)함으로써 불필요한 Full Scan 부하를 방지한다.

---

## Ⅳ. 특징

- 관리 편의성: 보관 주기가 지난 이력 데이터를 `DELETE` 대신 `DROP PARTITION`으로 처리해 트랜잭션 로그 부하 99% 절감
- 성능 향상: 데이터 스캔 범위를 물리적으로 한정하여 응답 속도를 보장하고 단일 인덱스 트리의 비대화 방지
- 가용성 증대: 파티션 단위의 독립적 백업·복구가 가능하며, 특정 파티션 손상이 전체 테이블 장애로 직결되지 않음

---

## Ⅴ. 심화 비교 및 적용 판단

| 비교 축 | 범위 (Range) | 해시 (Hash) | 리스트 (List) |
|:---|:---|:---|:---|
| 분할 기준 | 연속된 값 (날짜, 숫자 구간) | 해시 함수를 통한 연산 값 | 사전에 정의된 특정 값의 목록 |
| 장점 | 이력 데이터(시계열) 보관·관리에 최적 | 데이터가 균등 분배되어 I/O 병목 방지 | 지역, 부서 등 명확한 불연속 값 분류 시 유리 |
| 단점 | 특정 최신 기간에 트래픽이 몰릴 수 있음 | 특정 범위(Range) 검색 시 프루닝 미동작 | 새로운 값 등장 시 파티션 수동 추가 필요 |

> 요약: 시계열 이력 데이터는 Range 파티션을 기본으로 하고, PK 조회가 많고 쏠림이 우려되면 Hash 파티션을 선택한다.

**리스크·대응:**
- 전체 파티션 스캔: 파티션 키 누락 쿼리 실행 시 Full Scan 부하 → 애플리케이션 쿼리 가이드라인에 파티션 키 포함 강제
- 인덱스 무효화 장애: 파티션 DDL 후 Global 인덱스 상태 변경(Unusable) → DDL 수행 시 `UPDATE GLOBAL INDEXES` 옵션 병행
- 특정 파티션 Hotspot: 트래픽 쏠림 현상 → Range 파티션 하위에 Hash 서브 파티션을 두는 복합 파티셔닝(Composite) 도입

---

## Ⅵ. 실무 적용 및 결론

**적용 방안 3개:**
1. 시계열 데이터 파티셔닝: 대용량 로그 테이블(1TB 이상) 대상 Range 파티셔닝 적용 및 월단위 파티션 자동 생성 잡(Job) 스케줄링
2. 파티션 인덱스 최적화: 관리 독립성을 위해 Local Index를 원칙으로 하고, PK 등 글로벌 유일성 보장이 필수인 경우만 Global Index 제한적 사용
3. 데이터 아카이빙(Purge) 자동화: 보관 주기(Retention)를 초과한 파티션은 야간 배치 시간에 DDL(`DROP PARTITION`)을 통해 I/O 부하 없이 폐기

**결론 (2줄):**
- 기술사 판단: 파티셔닝은 단순한 테이블 분할이 아니라 I/O 제어와 아카이빙 효율성을 높이는 설계이므로 쿼리 패턴과 일치해야 한다.
- 향후 방향: 단일 DB의 스케일업 한계를 극복하기 위해, 점진적으로 분산 DB 환경의 수평 분할(Sharding)로 확장을 고려해야 한다.
