## Ⅰ. 개요
- **정의**: 포트와 어댑터를 통해 도메인 로직을 외부 기술 요소로부터 격리하는 아키텍처 스타일
- **배경/필요성**: UI·DB·외부 API 변경이 핵심 비즈니스 로직에 전파되면 유지보수 비용이 급증하므로, 의존 방향을 역전시켜 격리할 필요
- **비유**: 가전제품의 콘센트(포트)와 어댑터처럼, 규격만 맞으면 내부 기기를 바꾸지 않고 외부 전원을 교체할 수 있는 구조

| 출제 의도 | 반드시 짚을 핵심 | 감점 회피 포인트 |
|:---|:---|:---|
| 포트/어댑터 개념과 의존성 역전 이해 | Inbound/Outbound 포트 구분 | 단순 계층형 아키텍처와의 차이를 명확히 서술 필요 |

> 요약: 포트-어댑터 패턴으로 도메인을 외부 기술로부터 격리하는 아키텍처임

## Ⅱ. 구성요소
```text
  Driving Side          Core Domain         Driven Side
  (Inbound)                                  (Outbound)
+-----------+      +----------------+      +-----------+
| Web UI    |---->| Inbound Port   |      | Outbound  |
| REST API  |     |   Domain Logic |----->| Port      |---> DB
| CLI       |     |                |      |           |---> MQ
+-----------+      +----------------+      +-----------+
  Adapter              Application           Adapter
```

| 구성요소 | 설명 | 비유 |
|:---|:---|:---|
| Inbound Port | 외부 요청을 수신하는 도메인 인터페이스 | 건물 현관문 역할 |
| Outbound Port | 도메인이 외부 자원에 접근하기 위한 인터페이스 | 건물 후문(물류 반입구) 역할 |
| Adapter | 포트 인터페이스를 구현하여 실제 기술을 연결하는 구현체 | 변환 플러그 역할 |
| Domain Core | 비즈니스 규칙만 포함하며 외부 의존 없는 순수 로직 영역 | 기기 본체 역할 |

> 요약: Inbound/Outbound 포트와 어댑터가 도메인 코어를 감싸는 구조임

## Ⅲ. 절차
```text
외부요청 --> Inbound Adapter --> Inbound Port --> Domain --> Outbound Port --> Outbound Adapter
```
- 1단계: 외부 요청(HTTP, CLI 등)이 Inbound Adapter로 진입함
- 2단계: Adapter가 요청을 도메인 모델로 변환하여 Inbound Port를 호출함
- 3단계: Domain Core가 비즈니스 로직을 실행하고 Outbound Port를 통해 외부 자원 접근함
- 4단계: Outbound Adapter가 DB·메시지큐 등 실제 인프라와 통신하여 결과를 반환함

> 요약: 요청은 Inbound에서 Domain을 거쳐 Outbound로 단방향 흐름을 따름

## Ⅳ. 문제점
- 구현 복잡도: 포트·어댑터 인터페이스 수가 증가 — 소규모 서비스에서 과잉 설계가 됨
- 팀 학습 비용: 의존성 역전 원칙 숙지 필요 — 경험 부족 시 계층 간 의존 방향 오류 발생
- 테스트 이중화: 포트별 Mock 작성 필요 — 테스트 코드 유지보수 부담 증가

> 요약: 인터페이스 증가, 학습 비용, 테스트 이중화가 주요 문제임

## Ⅴ. 개선방안
1. 단기: 소규모 서비스는 Inbound/Outbound 각 1포트로 시작하여 점진 확장
2. 중기: 아키텍처 의사결정 기록(ADR)과 코드 리뷰로 의존 방향 준수 검증
3. 장기: 포트별 Contract Test 자동화로 Mock 유지보수 부담 경감

> 요약: 점진 도입, ADR 기반 검증, Contract Test 자동화로 개선함

## Ⅵ. 전망
- 발전 방향: 클린 아키텍처·양파 아키텍처와 융합하여 DDD 기반 설계 표준으로 확산 중임
- 기술사적 판단: MSA 환경에서 서비스 간 경계 설계의 기본 패턴으로 자리잡고 있음
- 기술사 제언: DDD의 바운디드 컨텍스트(054 참조)와 함께 적용 시 효과 극대화 가능
