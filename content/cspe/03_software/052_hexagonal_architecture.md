## 핵심 인사이트 (3줄 요약)
- 앨리스터 코오번(Alistair Cockburn)이 제안한 아키텍처로, **'포트와 어댑터(Ports and Adapters)'** 패턴으로도 불림.
- 애플리케이션의 핵심 비즈니스 로직(도메인)을 중앙에 두고, 외부의 UI, DB, 외부 시스템 등은 모두 '어댑터'를 통해 '포트'로 연결되도록 탈착식(Pluggable)으로 설계함.
- 인프라(외부 기술)의 변경이 도메인 로직에 영향을 주지 않도록 완벽히 격리하며, UI나 DB 없이도 도메인 로직만 독립적으로 단위 테스트가 가능해짐.

## Ⅰ. 개요 및 필요성
- **개요**: 비즈니스 로직과 외부 인프라스트럭처(DB, 웹 프레임워크) 간의 의존성을 분리하기 위한 대칭적 아키텍처 패턴.
- **필요성**: 기존의 전통적인 계층형(Layered) 아키텍처는 도메인 로직이 데이터베이스(Repository) 계층에 강하게 의존(DB-Driven Design)하는 문제가 있었음. 이로 인해 DB 기술을 바꾸거나 테스트를 할 때마다 핵심 로직이 깨지는 것을 막기 위해, 의존성의 방향을 역전(DIP)시킬 구조가 필요했음.
---
## Ⅱ. 아키텍처 및 핵심 원리
- **도메인 헥사곤 (Core)**: 
  - 정육각형의 가장 안쪽에 위치하며, 외부 기술(Spring, MySQL 등)을 전혀 모르는 순수한 비즈니스 로직만 존재.
- **포트 (Ports)**: 
  - 도메인 코어와 외부가 소통하기 위한 인터페이스(Interface).
  - **Inbound Port (Driving)**: 외부(UI/Web)에서 도메인으로 들어오는 요청을 정의 (예: `UseCase` 인터페이스).
  - **Outbound Port (Driven)**: 도메인이 외부(DB/API)로 나가는 요청을 정의 (예: `Repository` 인터페이스).
- **어댑터 (Adapters)**: 
  - 포트에 맞춰진 실제 기술 구현체. (예: WebController 어댑터, MySQL DB 어댑터).

```text
[ 헥사고날 아키텍처 (Ports and Adapters) 도식 ]

 (Driving Side / 주도하는 쪽)              (Driven Side / 수동적인 쪽)
 
 [ Web UI ]                                         [ MySQL DB ]
     ⬇️ (호출)                                            ⬆️ (접근)
 [ Web Adapter (Controller) ]                  [ DB Adapter (JPA) ]
          \                                       /
---------(Inbound Port)-----------------(Outbound Port)---------
|             \                               /                |
|              \                             /                 |
|            [ 비즈니스 도메인 로직 (순수 객체) ]                   |
|                                                              |
----------------------------------------------------------------
* 화살표는 의존성의 방향을 의미하며, 모두 헥사곤(내부)을 향해야 함 (DIP)
```
---
## Ⅲ. 비교 및 연결
| 구분 | Layered Architecture (계층형) | Hexagonal Architecture (헥사고날) |
|---|---|---|
| **의존성의 방향** | Web ➡️ Domain ➡️ DB | Web ➡️ Domain ⬅️ DB |
| **설계의 중심** | 데이터베이스 중심 (Data Model) | 도메인 중심 (Domain Model) |
| **테스트 용이성** | DB가 없으면 비즈니스 로직 테스트 어려움 | DB 어댑터 대신 Mock 객체를 꽂아 즉시 테스트 가능 |
| **복잡도** | 비교적 낮음 (빠른 개발) | 인터페이스(포트)와 어댑터를 일일이 매핑하므로 높음 |
---
## Ⅳ. 실무 적용 및 기술사 판단
- **클린 아키텍처와의 융합**: 헥사고날 아키텍처는 클린 아키텍처(Clean Architecture)와 철학(의존성 역전, 관심사 분리)이 완전히 동일하며, 마이크로서비스(MSA) 설계 시 각 서비스의 내부 구조를 잡는 가장 표준적인 패턴(De facto)으로 쓰임.
- **오버엔지니어링 경계**: 단순한 CRUD(게시판 등) 시스템에 헥사고날을 적용하면 포트와 매퍼(Mapper) 코드만 수백 줄이 나오는 보일러플레이트 지옥에 빠짐. 핵심 비즈니스 로직이 복잡하고 오래 유지보수해야 하는 '핵심 도메인(Core Domain)'에만 선별적으로 도입하는 것이 아키텍트의 지혜임.
---
## Ⅴ. 기대효과 및 결론
- "웹은 세부사항이다, DB도 세부사항이다"라는 철학을 실현하여, 언제든 기술 스택(예: REST API ➡️ gRPC, MySQL ➡️ MongoDB)을 도메인 로직 수정 없이 갈아끼울 수 있는 극강의 유연성을 확보함.
- 도메인 주도 설계(DDD)를 실제 코드로 구현할 때 가장 궁합이 잘 맞는 아키텍처로, 복잡한 엔터프라이즈 환경에서 기술 부채를 방어하는 훌륭한 방패가 됨.

### 👶 어린이를 위한 3줄 비유 설명
1. 컴퓨터 본체를 보면 마우스 꽂는 구멍(포트)과 모니터 꽂는 구멍(포트)이 따로 있죠?
2. 헥사고날 아키텍처는 프로그램의 핵심 '두뇌'를 가운데 두고, 밖에는 이 구멍(포트)들만 뚫어놓는 거예요.
3. 그러면 낡은 유선 마우스를 최신 무선 마우스(어댑터)로 바꿔 끼워도, 컴퓨터의 두뇌는 아무 수정 없이 똑같이 잘 작동한답니다!
