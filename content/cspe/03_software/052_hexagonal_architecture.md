# 📖 【암기용】 개념 완전 이해

> 목적: 헥사고날 아키텍처를 처음 보는 사람도 완벽히 이해하게 만든다. 시험 답안 양식이 아니라, 이해를 위한 친절한 설명이다.

## 한눈에
- **개요**: 도메인 코어를 외부 UI, DB, 메시징, API로부터 분리하는 포트·어댑터 구조
- **왜 필요한가**: 업무 규칙이 프레임워크와 DB 코드에 섞이면 DB 교체, API 추가, 테스트 자동화가 어려워진다. 헥사고날은 도메인 규칙을 가운데 두고 외부 기술을 어댑터로 밀어낸다.
- **핵심 직관**: 업무 규칙은 전기 콘센트의 기기처럼 포트 규격만 알며, 실제 플러그 모양은 어댑터가 맞춘다.

## 깊이 이해
- **배경·문제의식**: 계층형 아키텍처는 Presentation -> Service -> Repository 흐름이 명확하지만, 도메인이 DB와 웹 프레임워크에 의존하기 쉽다.
- **작동 원리**: 도메인 내부는 유스케이스와 엔티티로 구성하고, 외부 요청은 인바운드 어댑터가 포트를 호출하며, 외부 저장소·메시징은 아웃바운드 포트를 통해 접근한다.
- **비유**: 노트북 본체가 USB-C 규격만 제공하고 HDMI, LAN, SD카드는 허브가 변환하는 구조와 같다.
- **구체 예시**: 주문 생성 유스케이스는 `OrderRepositoryPort`만 호출한다. 운영 DB는 JPA Adapter, 테스트는 InMemory Adapter를 붙여 동일 테스트를 100ms 이내로 실행한다.
- **흔한 오해·주의점**: 폴더명을 `port`, `adapter`로 나누는 것만으로 달성되지 않는다. 의존 방향이 도메인 안쪽을 향해야 한다.

## 연결 개념
- Clean Architecture: 의존성 규칙을 더 넓은 계층 구조로 일반화
- DDD: 도메인 모델을 코어에 두는 설계 기반
- 테스트 대역: 외부 시스템을 어댑터로 교체하는 검증 방식

# 📝 【답안용】 시험 답안 템플릿

> 목적: 시험장에서 25분에 그대로 쓰는 답안 양식. 작성방식(추상표현 금지·수치·도식·문제유형 전환)을 엄격히 지킨다.
> 핵심: 포트·어댑터 용어 나열이 아니라, 도메인 격리와 의존 방향을 구조도로 증명한다.

## 핵심 인사이트 (3줄 요약)

> 1. **본질**: 헥사고날 아키텍처는 도메인 코어를 중심에 두고 외부 기술을 인바운드·아웃바운드 어댑터로 연결하는 구조이다.
> 2. **가치**: DB, UI, 메시지 브로커 교체 시 도메인 코드 수정 0건을 목표로 하며, 유스케이스 단위 테스트를 외부 I/O 없이 실행한다.
> 3. **판단 포인트**: 포트는 도메인이 필요로 하는 계약이고, 어댑터는 외부 기술을 그 계약에 맞추는 구현임을 구분해야 한다.

## 출제 의도 및 답안 포인트

| 출제 의도 | 반드시 짚을 핵심 | 감점 회피 포인트 |
|:---|:---|:---|
| 아키텍처 의존성 통제 역량 확인 | Domain, Inbound Port, Outbound Port, Adapter, Dependency Rule | 계층형 구조와 동일하게 설명 |
| 테스트 가능성 판단 확인 | InMemory Adapter, Mock, Contract Test, 외부 I/O 제거 | 테스트가 쉽다는 추상 표현만 작성 |
| Clean Architecture 관계 확인 | Hexagonal은 포트·어댑터 중심, Clean은 원형 계층 중심 | 용어만 바꾸고 차이 누락 |
> 요약: 이 문제는 포트·어댑터 구조로 도메인 격리와 테스트 전략을 설명하는지를 확인한다.

## Ⅰ. 개요 및 필요성

- 개요: 도메인 중심 포트·어댑터 구조
- 배경: 웹, DB, 메시징 프레임워크가 업무 규칙에 침투하면 기술 교체와 단위 테스트가 외부 인프라에 의존하고 변경 범위가 확대됨.
- 필요성: Port, Adapter, Domain Service로 의존성 방향을 내부로 고정해 외부 변경을 어댑터 수정으로 제한하고 테스트 double 적용 범위를 확보해야 함.

---

## Ⅱ. 구조 및 구성요소

```text
Inbound Adapter -> Inbound Port -> Use Case -> Domain Model
Domain Model -> Outbound Port -> Outbound Adapter -> DB / API / Message
Test Driver -> Inbound Port
InMemory Adapter -> Outbound Port
Dependency Direction -> Domain Core
```

| 구성요소 | 역할 | 특이사항 |
|:---|:---|:---|
| Domain Model | 업무 규칙과 상태 전이 보유 | 프레임워크 어노테이션 최소화 |
| Inbound Port | 외부가 유스케이스를 호출하는 계약 | Command, Query 인터페이스 |
| Outbound Port | 도메인이 외부 자원을 요구하는 계약 | Repository, Gateway 인터페이스 |
| Adapter | REST, JPA, Kafka 등 기술 변환 | 포트 구현체, 교체 가능 단위 |
> 요약: 구조의 중심은 도메인 코어이며, 모든 외부 기술은 포트 계약을 통해 어댑터로 연결된다.

---

## Ⅲ. 동작원리 및 흐름도

```text
HTTP 요청 -> Controller Adapter
Controller Adapter -> Inbound Port 호출
Use Case -> Domain Rule 실행
Use Case -> Outbound Port 호출
JPA / Kafka Adapter -> 외부 시스템 처리
결과 -> Response Adapter -> Client
```

| 단계 | 처리 내용 | 검증 기준 |
|:---:|:---|:---|
| 1 | 인바운드 어댑터가 HTTP, CLI, 메시지를 명령 객체로 변환 | DTO와 Domain 객체 분리 |
| 2 | 인바운드 포트가 유스케이스 진입점 제공 | 포트 메서드가 업무 행위로 명명 |
| 3 | 유스케이스가 도메인 규칙 실행 | DB 접근 없이 순수 규칙 테스트 |
| 4 | 아웃바운드 포트가 저장소·외부 API 요구 표현 | 구현체 의존 0건 |
| 5 | 어댑터가 JPA, REST, Kafka 호출 수행 | Contract Test 통과 |
> 요약: 요청은 어댑터에서 포트로 들어오고, 도메인은 포트만 호출하며, 실제 기술 처리는 어댑터가 담당한다.

---

## Ⅳ. 특징

| 구분 | 계층형 구조 | 헥사고날 구조 | 수치·판단 포인트 |
|:---|:---|:---|:---|
| 의존 방향 | Service가 Repository 구현에 의존 | Domain이 Port에 의존 | 도메인 외부 import 0건 |
| 테스트 | DB·웹 컨테이너 필요 | InMemory Adapter로 유스케이스 테스트 | 단위 테스트 100ms 이하 |
| 기술 교체 | 서비스 코드 수정 동반 | 어댑터 교체 중심 | DB 변경 시 도메인 수정 0건 |
| 복잡도 | 소규모 CRUD에 단순 | 포트·어댑터 파일 증가 | 유스케이스 10개 이상일 때 적합 |
| 관계 | Layered Architecture | Clean Architecture 구현 변형 | 의존성 규칙 공통 |
> 요약: 헥사고날은 도메인 격리와 테스트 자동화에 유리하지만, 소규모 CRUD에서는 파일 수 증가를 검토해야 한다.

## Ⅴ. 심화 비교 및 적용 판단

| 비교 축 | 계층형·Clean | 헥사고날 | 선택 기준 |
|:---|:---|:---|:---|
| 중심 개념 | 계층, 유스케이스 원 | 포트와 어댑터 | 외부 연동 3종 이상이면 헥사고날 |
| 도메인 복잡도 | CRUD 중심 가능 | 규칙·상태 전이 중심 | 도메인 규칙 20개 이상 |
| 테스트 전략 | 통합 테스트 비중 | 포트 단위 대역 테스트 | CI 단위 테스트 5분 이하 |
| 운영 변경 | DB·브로커 변경 영향 존재 | 어댑터 교체로 제한 | 공급사 API 교체 빈도 |
> 요약: 외부 연동과 도메인 규칙이 함께 늘어나는 시스템에서 헥사고날 선택 가치가 커진다.

| 리스크 | 원인 | 대응 방안 | 확인 지표 |
|:---|:---|:---|:---|
| 포트 남발 | CRUD마다 인터페이스 생성 | 유스케이스 기준 포트 설계 | 포트당 구현체 수 |
| 빈약한 도메인 | 규칙이 Service에 잔류 | Entity, Value Object로 규칙 이동 | 도메인 테스트 수 |
| 어댑터 누수 | JPA Entity가 도메인으로 침투 | Mapper, DTO 분리 | 외부 패키지 import 0건 |
| 테스트 공백 | Mock만 사용하고 계약 불일치 | Contract Test와 Testcontainers | 계약 테스트 통과율 |
> 요약: 포트 남발과 기술 누수는 의존성 검사와 계약 테스트로 통제한다.

| 점검 항목 | 목표 기준 | 측정 방법 |
|:---|:---|:---|
| 의존성 | domain 패키지 외부 프레임워크 import 0건 | ArchUnit |
| 테스트 | 유스케이스 단위 테스트 80% 이상 | JaCoCo, mutation test |
| 교체성 | 저장소 어댑터 2종 이상 검증 | InMemory, JPA 테스트 |
| 배포 영향 | 어댑터 변경 시 도메인 diff 0건 | Git diff 분석 |
> 요약: 성공 여부는 의존성 방향, 유스케이스 테스트, 어댑터 교체 범위로 판단한다.

## Ⅵ. 실무 적용 및 결론

**적용 방안 3개:**
1. 주문, 결제, 정산 유스케이스별 Inbound Port를 만들고 Controller는 Command DTO 변환만 수행하도록 제한한다.
2. Repository, PaymentGateway, EventPublisher를 Outbound Port로 두고 JPA, REST, Kafka Adapter를 구현체로 분리한다.
3. ArchUnit으로 domain 패키지의 Spring, JPA import 0건을 검사하고 PR마다 5분 내 단위 테스트를 실행한다.

**결론 (2줄):**
- 기술사 판단: 외부 연동 3종 이상이고 도메인 규칙 변경이 월 2회 이상이면 헥사고날 적용, 단순 CRUD는 계층형 구조가 타당함
- 향후 방향: DDD, Clean Architecture, Testcontainers 기반 계약 테스트와 결합해 도메인 중심 배포 구조로 발전함
