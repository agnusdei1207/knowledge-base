## 미리 알고가기

- 포트는 도메인이 외부에 제공하거나 외부 기술에 요구하는 호출 계약임
- 어댑터는 웹·DB·메시징 기술을 포트 계약에 맞춰 연결하는 구현체임
- 의존 방향은 바깥 기술이 안쪽 도메인에 맞추는 쪽으로 유지해야 함

## 작성 근거(검토용)

- 헥사고날 아키텍처는 의존 방향, 테스트·교체 경계, 구조 부담을 핵심 비교축으로 선정함
- 구조와 절차는 입력 어댑터부터 도메인과 출력 어댑터로 이어지는 호출 흐름을 중심으로 제시함
- 실무 판단은 의존 방향 위반 건수, 외부 연동 교체 시간, 포트의 외부 기술 타입 노출 건수로 구체화함

## Ⅰ. 개요

- **정의/개념**: 헥사고날 아키텍처는 도메인과 외부 기술의 연결을 포트·어댑터로 분리해 의존 방향을 도메인 안쪽으로 유지하는 구조임
- **배경/필요성**: 도메인 로직이 DB·API·메시징 구현에 의존하면 테스트와 기술 교체 범위가 커지므로 외부 연동 경계가 필요함

## Ⅱ. 특징

- 도메인 규칙이 포트 인터페이스에 의존하고 DB·API·메시징 구현은 어댑터에 배치됨
- DB와 API와 메시지 브로커 교체 시 영향 범위를 줄일 수 있음
- 업무 규칙과 외부 연동이 적은 CRUD 서비스에서는 포트·어댑터 계층 수가 늘어남
- 포트 설계가 구현 세부를 그대로 노출하면 추상화만 늘어날 수 있음

## Ⅲ. 종류 및 비교

| 판단 기준 | 계층형 구조 | 헥사고날 아키텍처 |
|:---|:---|:---|
| 의존 방향 | 상위 계층이 하위 기술 계층에 직접 의존하기 쉬움 | 외부 기술이 도메인 포트에 맞춰 안쪽으로 의존함 |
| 테스트·교체 경계 | 도메인 테스트가 DB·프레임워크 구성에 의존 | 포트의 대역 구현으로 외부 연동을 교체·격리 |
| 구조상 한계 | 도메인과 인프라 결합이 누적되기 쉬움 | 초기 포트 설계와 구조 정리가 더 필요함 |
| 적합한 환경 | 단일 DB·API를 사용하는 CRUD 서비스 | 여러 외부 기술을 교체하며 도메인 규칙을 유지하는 시스템 |

> 요약: 단일 DB·API의 CRUD는 계층형 구조, 외부 기술 교체가 반복되면 헥사고날 아키텍처가 적합함.

## Ⅳ. 구성요소 및 구조

| 구성요소 | 설명 |
|:---|:---|
| 도메인 핵심 | 비즈니스 규칙을 담고 외부 기술에 의존하지 않음 |
| 입력·출력 포트 | 도메인이 제공하거나 요구하는 호출 계약을 정의함 |
| 입력·출력 어댑터 | 웹·DB·메시징 기술을 포트 계약에 맞춰 연결함 |
| 의존 경계 | 외부 어댑터가 도메인 포트에 의존하도록 방향을 제한함 |

> 요약: 도메인이 포트를 정의하고 외부 기술은 어댑터로 포트 계약을 구현함.

## Ⅴ. 원리 및 절차 흐름도

```text
+-------------+     +-------------+     +-------------+     +-------------+
| 외부 요청      | --> | 입력 어댑터·포트 | --> | 도메인 규칙 실행 | --> | 출력 포트·어댑터 |
+-------------+     +-------------+     +-------------+     +-------------+
```

1. **외부 요청**: 사용자나 외부 시스템이 API·메시지로 요청함
2. **입력 어댑터·포트**: 어댑터가 요청을 입력 포트 형식으로 변환함
3. **도메인 규칙 실행**: 도메인이 비즈니스 규칙을 처리하고 출력 포트를 호출함
4. **출력 포트·어댑터**: 출력 어댑터가 DB·외부 API·메시지 브로커와 통신함

> 요약: 요청은 입력 어댑터와 포트를 거쳐 도메인에서 처리되고 출력 포트와 어댑터로 외부 기술에 전달됨.

## Ⅵ. 실무 사례

1. 결제 연동 모듈은 외부 PG를 출력 어댑터로 분리하고 연동 교체 시간·회귀 결함률을 확인함
2. 도메인 플랫폼은 아키텍처 테스트를 적용하고 의존 방향 위반·외부 기술 타입 노출 건수를 확인함

## Ⅶ. 결론

헥사고날 아키텍처는 포트·어댑터로 외부 기술 변경이 도메인 규칙에 전파되는 범위를 줄임
