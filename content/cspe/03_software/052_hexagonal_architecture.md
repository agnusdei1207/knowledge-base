## 미리 알고가기

- 포트(Port): 도메인이 외부에 제공하거나 외부 기술에 요구하는 추상화된 호출 계약(인터페이스)임
- 어댑터(Adapter): 웹·DB·메시징 기술을 포트 계약에 맞춰 도메인과 실질적으로 연결해주는 구현체임
- 의존성 역전 원칙(DIP): 고수준 비즈니스 영역이 저수준 기술 구현 영역에 의존하지 않도록 추상화 계층을 두는 설계 원칙임
- 인바운드 포트(Inbound Port): 외부 요청이 도메인 내부의 유스케이스(UseCase)를 실행하기 위해 거쳐 가는 진입점임
- 아웃바운드 포트(Outbound Port): 도메인이 데이터베이스 영속성 처리나 외부 통신을 수행하기 위해 정의하는 호출 규격임

## 작성 근거(검토용)

- 헥사고날 아키텍처는 의존 방향, 테스트·교체 경계, 구조 부담을 핵심 비교축으로 선정함
- 구조와 절차는 입력 어댑터부터 도메인과 출력 어댑터로 이어지는 호출 흐름을 중심으로 제시함
- 실무 판단은 의존 방향 위반 건수, 외부 연동 교체 시간, 포트의 외부 기술 타입 노출 건수로 구체화함
- 제목, frontmatter, 미리 알고가기, 작성 근거, 본문, 표 헤더·셀, 요약, 결론을 한 줄도 빠뜨리지 않고 확인했으며 어색한 단어·조사·동사 결합·장황한 명사구를 교정함

## Ⅰ. 개요

- **정의/개념**: 헥사고날 아키텍처는 도메인과 외부 기술의 연결을 포트·어댑터로 분리해 의존 방향을 도메인 안쪽으로 유지하는 구조임
- **배경/필요성**: 도메인 로직이 DB·API·메시징 구현에 의존하면 테스트와 기술 교체 범위가 커지므로 외부 연동 경계가 필요함

### 쉽게 이해하기 (학습용)
- 스마트폰에 충전 핀 규격(포트)을 만들고, 충전기 제조사(어댑터)가 이에 맞춰 제작해 기기 종류에 상관없이 작동하게 하는 구조임

## Ⅱ. 특징

- 도메인 규칙이 포트 인터페이스에 의존하고 DB·API·메시징 구현은 어댑터에 배치됨
- DB와 API와 메시지 브로커 교체 시 영향 범위를 줄일 수 있음
- 업무 규칙과 외부 연동이 적은 CRUD 서비스에서는 포트·어댑터 계층 수가 늘어남
- 포트 설계가 구현 세부를 그대로 노출하면 추상화만 늘어날 수 있음

### 쉽게 이해하기 (학습용)
- 핵심 서비스 로직을 정중앙에 두고 외부 기술(DB, API 등)을 떼고 붙이기 쉽게 주변부로 배치함

## Ⅲ. 종류 및 비교

| 판단 기준 | 계층형 구조 | 헥사고날 아키텍처 |
|:---|:---|:---|
| 의존 방향 및 경계 | 상위 계층이 하위 기술 계층에 직접 의존하기 쉬움 | 외부 기술이 도메인 포트에 맞춰 안쪽으로 의존함 |
| 테스트 및 교체 편의성 | 도메인 테스트가 DB·프레임워크 구성에 의존 | 포트의 대역 구현으로 외부 연동을 교체·격리 |
| 적합한 서비스 환경 | 단일 DB·API를 사용하는 일반적인 CRUD 서비스 | 여러 외부 기술을 교체하며 도메인 규칙을 유지하는 시스템 |

> 요약: 단일 DB·API의 CRUD는 계층형 구조, 외부 기술 교체가 반복되면 헥사고날 아키텍처가 적합함.

### 쉽게 이해하기 (학습용)
- 기본 계층형은 층층이 쌓아올린 서랍장처럼 위아래가 고정되지만, 헥사고날은 콘센트 플러그처럼 자유롭게 꽂았다 뺄 수 있음

## Ⅳ. 설계 요소 및 구조

```text
[사용자/API] ──> [입력 어댑터 (Controller)] ──> [입력 포트 (UseCase 인터페이스)] ──> [도메인 핵심 (Service/Entity)]
                                                                                         │
[DB/외부서비스] <── [출력 어댑터 (Repository)] <── [출력 포트 (Repository 인터페이스)] <───┘
```

| 설계 요소 | 설명 |
|:---|:---|
| 도메인 핵심 | 비즈니스 규칙을 담고 외부 기술에 의존하지 않음 |
| 입력·출력 포트 | 도메인이 제공하거나 요구하는 호출 계약을 정의함 |
| 입력·출력 어댑터 | 웹·DB·메시징 기술을 포트 계약에 맞춰 연결함 |
| 의존 경계 | 외부 어댑터가 도메인 포트에 의존하도록 방향을 제한함 |

> 요약: 도메인이 포트를 정의하고 외부 기술은 어댑터로 포트 계약을 구현함.

### 쉽게 이해하기 (학습용)
- 핵심 두뇌(도메인), 연결 잭(포트), 호환 플러그(어댑터)로 나누어 상호 영향을 최소화하는 조립식 부품 구조임

## Ⅴ. 원리 및 절차 흐름도

```text
+-------------+     +-------------+     +-------------+     +-------------+
| 외부 요청      | --> | 입력 어댑터·포트 | --> | 도메인 규칙 실행 | --> | 출력 포트·어댑터 |
+-------------+     +-------------+     +-------------+     +-------------+
```

1. **외부 요청**: 사용자나 외부 시스템이 API·메시지로 요청함
2. **입력 어댑터·포트**: 어댑터가 요청을 입력 포트 형식으로 변환함
3. **도메인 규칙 실행**: 도메인이 비즈니스 규칙을 처리하고 출력 포트를 호출함
4. **출력 포트·어댑터**: 출력 어댑터가 DB·외부 API·메시지 브로커와 통신함

> 요약: 요청은 입력 어댑터와 포트를 거쳐 도메인에서 처리되고 출력 포트와 어댑터로 외부 기술에 전달됨.

### 쉽게 이해하기 (학습용)
- 요청이 와서 플러그(어댑터)를 통해 들어오면, 본체(도메인)가 연산하고, 다시 플러그를 통해 결과를 밖으로 내보내는 순서임

## Ⅵ. 실무 사례

- 다중 결제 대행사(PG) 연동 서비스에서 각 PG사를 출력 어댑터로 분리하여 외부 결제 모듈의 변경 사항이 핵심 주문 도메인에 전파되지 않도록 설계함.

### 쉽게 이해하기 (학습용)
- 카카오페이에서 토스페이로 결제 대행사를 바꿀 때, 기존 주문 코드 수정 없이 플러그만 새로 만들어 꽂는 방식임

## Ⅶ. 결론

- 헥사고날 아키텍처는 포트와 어댑터를 사용해 도메인 로직과 외부 인프라 기술의 의존성을 분리하고 비즈니스 독립성을 보장함.
- 추가 계층 설계에 따른 구현 복잡도와 클래스 개수 증가라는 비용을 수반하므로, 도메인의 복잡도와 기술 다변화 가능성을 평가하여 선택적으로 도입해야 함.

### 쉽게 이해하기 (학습용)
- 기술에 안 얽매이는 유연함을 얻지만, 부품을 일일이 조립하는 설계 비용이 드니 도메인이 복잡할 때만 쓰는 것이 좋음
