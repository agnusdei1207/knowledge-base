# 📖 【암기용】 개념 완전 이해

## 한눈에
- **개요**: 헥사고날 아키텍처는 비즈니스 로직을 외부 기술(DB, 웹 프레임워크)과 철저히 격리하여 포트와 어댑터로만 통신하게 하는 아키텍처 패턴이다.
- **왜 필요한가**: 계층형 아키텍처에서는 도메인 로직이 데이터베이스(JPA 등)나 인프라에 의존하게 되어 기술 변경 시 도메인 코드를 다 고쳐야 하는 문제가 발생한다.
- **핵심 직관**: 전원 플러그와 어댑터와 같다. 220V 포트(인터페이스)만 맞춰두면 청소기든 TV든 꽂아 쓸 수 있고, 다른 환경에 가면 어댑터(구현체)만 바꾸면 본체(도메인 로직)는 뜯어고칠 필요가 없다.

## 핵심 용어 정리

| 용어/표기 | 의미 | 비유·예 |
|:---|:---|:---|
| 내부 육각형 (Domain) | 순수한 비즈니스 로직과 도메인 모델 | 애플리케이션의 본질적인 심장부 |
| 포트 (Port) | 내부와 외부가 통신하기 위한 규격(인터페이스) | 콘센트 구멍 (명세서) |
| 어댑터 (Adapter) | 포트 규격에 맞춰 외부 시스템을 연결하는 구현체 | 110V를 220V로 바꿔주는 돼지코 |
| 인바운드 (Inbound) | 외부에서 내부 도메인으로 들어오는 흐름 | 사용자 요청을 받는 REST API 컨트롤러 |
| 아웃바운드 (Outbound) | 내부 도메인에서 외부 시스템을 호출하는 흐름 | 도메인이 데이터를 저장하기 위해 호출하는 DB 리포지토리 |

## 깊이 이해
- **배경·문제의식**: 전통적인 3계층(웹-도메인-DB) 구조는 도메인 로직이 영속성(DB) 계층에 강하게 결합(Coupling)되는 한계가 있다. 인프라가 바뀌면 도메인도 깨진다. 이를 막기 위해 Alistair Cockburn이 고안했다.
- **작동 원리**: 의존성 역전 원칙(DIP)을 극대화한다. 도메인 로직이 외부 DB를 호출할 때 직접 의존하지 않고, 내부에서 정의한 '아웃바운드 포트(인터페이스)'를 호출한다. 외부 DB는 이 포트를 구현한 '아웃바운드 어댑터'로 연결되므로, 의존성 화살표가 모두 중앙 도메인을 향하게 된다.
- **구체 예시**: `OrderService`(도메인)는 `OrderRepository` 인터페이스(포트)만 안다. 실제 데이터는 MySQL에 저장되든 MongoDB에 저장되든, 각각을 구현한 어댑터 클래스만 갈아끼우면 된다.
- **흔한 오해·주의점**: 이름이 육각형이라고 반드시 6개의 면이 있는 것은 아니다. 포트의 개수가 다양할 수 있음을 상징적으로 표현한 도형일 뿐, '포트 앤 어댑터 아키텍처'가 더 정확한 본질이다.

## 연결 개념
- 의존성 역전 원칙 (DIP) — 헥사고날 아키텍처의 논리적 기반
- 클린 아키텍처 (Clean Architecture) — 유사한 목적(도메인 보호)을 가진 Robert C. Martin의 아키텍처
- 마이크로서비스 아키텍처 (MSA) — 각 마이크로서비스 내부를 헥사고날로 구현하여 자율성을 높임

# 📝 【답안용】 시험 답안 템플릿

## 핵심 인사이트 (3줄 요약)

> 1. **본질**: 비즈니스 로직을 중앙에 두고 포트와 어댑터를 통해 외부 인프라 및 UI와 통신함으로써 외부 의존성을 완벽히 격리하는 아키텍처 패턴이다.
> 2. **가치**: 인프라 기술 변경이나 UI 프레임워크 교체 시 도메인 로직의 수정을 막아 유지보수성과 독립적 테스트 용이성을 극대화한다.
> 3. **판단 포인트**: 도메인 보호라는 강력한 장점 이면에는 포트와 어댑터 인터페이스 증가로 인한 구조적 복잡도 상승이 따르므로, 비즈니스 로직이 충분히 복잡한 경우에 한해 적용해야 한다.

## 출제 의도 및 답안 포인트

| 출제 의도 | 반드시 짚을 핵심 | 감점 회피 포인트 |
|:---|:---|:---|
| 의존성 격리 구조 파악 역량 | 인바운드/아웃바운드 포트 및 어댑터, DIP(의존성 역전) | 단순히 '육각형 모양'에 치중한 기하학적 설명 단정 |
| 레거시 계층형 구조 한계 개선 방안 제시 | 영속성 계층 결합 문제 해결, 도메인 중심 설계 | 도메인이 외부에 의존하는 잘못된 화살표 방향 기재 |
| 구조적 한계와 트레이드오프 판단 | 인터페이스 보일러플레이트 코드 증가, 매핑 오버헤드 | 모든 시스템에 헥사고날이 최선이라는 맹목적 긍정 |

> 요약: 헥사고날 아키텍처는 의존성 방향을 모두 내부 도메인으로 향하게 하여 인프라 변경 파급을 차단하는 구조 설계 능력을 요구한다.

## Ⅰ. 개요 및 필요성

- 개요: 애플리케이션의 핵심 비즈니스 로직을 외부 기술 요소로부터 분리하기 위해 포트(Port)와 어댑터(Adapter)를 도입한 도메인 중심 아키텍처임
- 배경: 전통적 3계층 아키텍처는 비즈니스 로직이 데이터베이스(영속성 계층)에 강하게 의존하여 인프라 변경 시 코어 로직이 오염되는 한계 노출
- 필요성: 클라우드 네이티브 및 MSA 환경에서 외부 인터페이스(REST, gRPC, MQ)가 다양화됨에 따라 비즈니스 로직의 독립성 및 모의 객체(Mocking) 기반 단위 테스트 격리 필수

---

## Ⅱ. 구조 및 구성요소

```text
외부 통신 -> 인바운드 어댑터 -> 인바운드 포트 -> 내부 도메인 로직 -> 아웃바운드 포트 -> 아웃바운드 어댑터 -> 외부 시스템
              (웹/CLI 등)    (인터페이스)                         (인터페이스)     (DB/외부 API)
```

| 구성요소 | 역할 | 특이사항 |
|:---|:---|:---|
| 내부 도메인 (Domain) | 외부 의존성 없이 순수 비즈니스 룰과 상태 관리 수행 | 모든 의존성 화살표의 최종 도착지 |
| 인바운드 포트 (Inbound Port) | 외부에서 도메인 기능을 사용하기 위한 진입 명세 제공 | 도메인이 구현하고 인바운드 어댑터가 호출 |
| 아웃바운드 포트 (Outbound Port) | 도메인이 외부 자원을 사용하기 위한 명세 정의 | 도메인이 호출하고 아웃바운드 어댑터가 구현 (DIP) |
| 어댑터 (Adapter) | 포트 명세에 맞춰 외부 프로토콜 및 인프라 기술 변환 | REST Controller, Spring Data JPA 등 구체적 구현 |

> 요약: 도메인 로직은 오직 포트(인터페이스)에만 의존하며, 구체적인 기술은 어댑터 형태로 철저히 격리된다.

---

## Ⅲ. 동작원리 및 흐름도

```text
HTTP/메시지 수신 -> 포트 스펙 변환 -> 코어 비즈니스 처리 -> 외부 인프라 인터페이스 호출 -> 쿼리/연동 실행
```

- 1단계 [요청 수신 및 변환]: 인바운드 어댑터가 외부 HTTP 요청을 수신하여 도메인에서 이해할 수 있는 Command 객체로 매핑
- 2단계 [포트 진입]: 변환된 객체를 인바운드 포트(Usecase)를 통해 내부 도메인 로직으로 전달
- 3단계 [로직 처리 및 외부 호출]: 도메인 로직 처리 중 영속화가 필요하면 직접 DB를 호출하지 않고 아웃바운드 포트 호출
- 4단계 [어댑터 실행]: 아웃바운드 어댑터가 포트 인터페이스를 구현하여 실제 RDBMS 쿼리 또는 외부 API를 실행 후 반환

> 요약: 외부 연동은 반드시 어댑터의 변환 과정과 포트라는 추상화 계층을 거쳐 도메인에 도달하거나 빠져나간다.

---

## Ⅳ. 특징

- 의존성 역전(DIP) 극대화: 아웃바운드 포트를 통해 저수준 모듈(DB 어댑터)이 고수준 모듈(도메인)에 의존하게 하여 결합도 최소화
- 플러그인 기반 확장성: 비즈니스 로직 수정 없이 새로운 UI(CLI 등)나 데이터 저장소(MongoDB 등) 어댑터를 손쉽게 추가 가능
- 테스트 격리성 제고: 외부 인프라 연동 없이 아웃바운드 포트를 Mock 객체로 대체하여 밀리초 단위의 독립적인 단위 테스트(Unit Test) 가능

> 요약: 비즈니스 로직의 완벽한 순수성을 보장하지만, 객체 간 변환(매핑) 로직이 다수 발생하여 초기 구현 코드가 증가한다.

---

## Ⅴ. 심화 비교 및 적용 판단

| 비교 축 | 계층형 아키텍처 (Layered) | 헥사고날 아키텍처 (Hexagonal) | 선택 기준 |
|:---|:---|:---|:---|
| 의존성 방향 | 웹 -> 도메인 -> 영속성 (단방향 하향) | 어댑터 -> 도메인 (모두 중앙 지향) | 인프라 변경에 대한 내성 확보 여부 |
| 코어 로직 오염 | DB 테이블 구조에 도메인 모델이 종속 가능성 | 도메인 모델이 인프라와 완벽히 분리 | 비즈니스 로직의 복잡도 및 수명 |
| 구현 복잡도 | 인터페이스 없이 직관적 구현 가능 | 포트 인터페이스 및 양방향 모델 매핑 필수 | 팀의 설계 역량 및 프로젝트 규모 |

> 요약: 헥사고날 아키텍처는 단순 CRUD 중심의 앱에서는 오버엔지니어링이나, 복잡한 핵심 도메인을 가진 시스템에서는 필수적이다.

**리스크·대응:**
- 모델 매핑 오버헤드: 도메인 모델과 영속성 모델 간 변환 코드 폭증 → 복잡도가 낮은 서브도메인은 매핑을 생략하는 완화된(Relaxed) 아키텍처 혼용 (지표: 매핑 클래스 수 비율)
- 과도한 포트 분리: 불필요하게 촘촘한 인터페이스 설계로 유지보수 저하 → 하나의 유스케이스 당 하나의 인바운드 포트 원칙 적용 (지표: 인터페이스 당 메서드 수)

## Ⅵ. 실무 적용 및 결론

**적용 방안 3개:**
1. MSA 기반 서비스 분할 시 도입: 개별 마이크로서비스 내부에 헥사고날 아키텍처를 적용하여 타 서비스 연동을 아웃바운드 어댑터로 격리
2. 패키지 의존성 통제: 프로젝트 패키지 구조를 `domain`, `adapter.in`, `adapter.out`으로 강제하여 개발자의 의도치 않은 의존성 침범을 컴파일 타임에 차단
3. 점진적 마이그레이션: 레거시 모놀리식 시스템에서 가장 변경이 잦은 핵심 도메인부터 스트랭글러 패턴과 결합하여 헥사고날 구조로 분리 적용

**결론 (2줄):**
- 기술사 판단: 헥사고날 아키텍처는 인프라 종속성을 끊어내는 강력한 무기지만, 팀의 숙련도와 초기 보일러플레이트 비용을 감당할 수 있을 때 핵심 도메인 위주로 도입해야 함
- 향후 방향: 최근 클린 아키텍처 및 어니언 아키텍처와 결합하여, 도메인 주도 설계(DDD)의 전략적 설계를 구현하는 전술적 템플릿으로 표준화되고 있음
