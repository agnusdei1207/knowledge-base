# 📖 【암기용】 개념 완전 이해

> 목적: 이 개념을 처음 보는 사람도 완벽히 이해하게 만든다. 시험 답안 양식이 아니라, 이해를 위한 친절한 설명이다.

## 한눈에
- **개요**: **헥사고날(육각형) 아키텍처**는 소프트웨어를 짤 때 가장 소중한 **'핵심 비즈니스 로직(도메인)'을 시스템의 정중앙에 완벽히 고립**시켜 보호하고, 외부의 지저분한 것들(웹 화면, DB, 외부 API)은 **포트(구멍)와 어댑터(돼지코 변환기)**를 통해 바깥쪽에서 꽂아 넣게 만드는 설계 방식이다. (포트 앤 어댑터 아키텍처라고도 불린다).
- **왜 필요한가**: 기존의 '계층형 아키텍처(Controller -> Service -> DB)'는 가장 아래에 DB가 있어서, 비즈니스 로직(Service)이 DB(데이터베이스 기술)에 완전히 종속되는 비극을 낳았다. DB를 Oracle에서 MongoDB로 바꾸면 비즈니스 로직 코드까지 다 뜯어고쳐야 했다. 헥사고날은 이 종속성을 뒤집어(역전), 비즈니스 로직이 왕이 되고 DB나 웹이 신하가 되게 만든다.
- **핵심 직관**: 
  - 정중앙(핵심): "주문 시 10% 할인"이라는 순수 비즈니스 로직 (프레임워크, DB 코드 단 1줄도 섞이면 안 됨).
  - 포트(Port): 노트북의 USB 구멍 (인터페이스 규격).
  - 어댑터(Adapter): 마우스, 키보드, 모니터 케이블 (웹 컨트롤러, DB 저장소 구현체).

## 깊이 이해
- **배경·문제의식**: 코드를 짜다 보면 "게시글 작성 로직" 안에 Spring 프레임워크의 `@Transactional` 어노테이션이나 JPA(DB) 코드가 곰팡이처럼 피어난다. 10년 뒤 Spring이나 JPA가 망해서 다른 기술로 바꾸려면, 회사 시스템을 아예 처음부터 다시 짜야 한다(벤더 락인). 
- **작동 원리 (안쪽과 바깥쪽)**:
  1. **육각형 안쪽 (순수 도메인 코어)**: 오로지 순수한 Java(순수 언어)로만 비즈니스 규칙을 짠다. 밖으로 통하는 인터페이스(Port)만 뚫어놓는다. 이 안쪽 코드는 DB가 Oracle이든 MySQL이든, 프론트가 웹이든 모바일이든 전혀 알지 못한다.
  2. **육각형 바깥쪽 (어댑터들)**:
     - **인바운드(Inbound, 왼쪽)**: 사용자가 앱을 누르면 들어오는 곳. (웹 컨트롤러, API 라우터 어댑터). 
     - **아웃바운드(Outbound, 오른쪽)**: 핵심 로직이 다 끝나고 결과를 밖으로 내보내는 곳. (DB Repository, 카프카 메시지 발행기 어댑터).
  3. **의존성의 방향 (가장 중요)**: 화살표는 **무조건 바깥쪽에서 안쪽(도메인)으로만** 향해야 한다! 안쪽(도메인)이 바깥쪽(DB)을 의존(호출)하면 절대 안 된다. DIP(의존성 역전 원칙)를 통해 이를 차단한다.
- **비유**: 
  - 최신형 모니터(순수 도메인 로직). 이 모니터 안에는 HDMI 잭, C타입 잭(포트)만 뚫려 있다.
  - 여기에 플스5를 꽂든, 맥북을 꽂든, 닌텐도를 꽂든(어댑터), 모니터 본체 내부의 패널 기판(비즈니스 로직)은 1mm도 고칠 필요가 없다. 
- **흔한 오해·주의점**: "왜 하필 원도 아니고 네모도 아니고 육각형인가요?" 특별한 이유는 없다. 그냥 바깥에서 꽂아 들어올 수 있는 포트(구멍)가 4면(네모)보다는 많다는 걸 시각적으로 보여주기 위해 알리스테어 코오번이 대충 육각형(Hexagon)으로 그렸을 뿐이다. (다각형이면 다 됨).

## 연결 개념
- **클린 아키텍처 (Clean Architecture)**: 밥 아저씨(로버트 C. 마틴)가 주창한 궁극의 아키텍처. 헥사고날(포트/어댑터) 아키텍처나 양파(Onion) 아키텍처 모두 클린 아키텍처의 철학(의존성은 안쪽 코어를 향해야 한다)을 구현하는 구체적인 쌍둥이 방식들이다.
- **DDD (도메인 주도 설계)**: 헥사고날 아키텍처는 DDD를 구현할 때 찰떡궁합이다. DDD의 "비즈니스 도메인을 가장 중요하게 뭉쳐둬라"라는 철학을 코드로 짜려면 헥사고날의 '안쪽 육각형' 구조가 절대적으로 필요하다.

# 📝 【답안용】 시험 답안 템플릿

> 목적: 시험장에서 25분에 그대로 쓰는 답안 양식. 작성방식(추상표현 금지·수치·도식·문제유형 전환)을 엄격히 지킨다.
> 핵심: 이 시험은 정보를 많이 나열하는 시험이 아니라, 문제 신호어에서 출제자 의도를 읽고 핵심 논점을 선별해 쓰는 시험이다.

## 핵심 인사이트 (3줄 요약)

> 1. **본질**: 애플리케이션의 핵심 비즈니스 로직(도메인)을 정중앙에 고립시키고, 외부 요소(UI, DB, 외부 API)를 인터페이스(Port)와 구현체(Adapter)로 분리하여 꽂아 넣는 아키텍처 패턴이다.
> 2. **가치**: 기존 계층형(Layered) 아키텍처가 유발하는 '데이터베이스 주도 설계(DB 종속성)'를 타파하고, 특정 프레임워크나 외부 기술 인프라의 변경이 순수 비즈니스 로직에 영향을 주지 못하게 완벽히 차단(Decoupling)한다.
> 3. **판단 포인트**: 의존성의 화살표가 무조건 바깥쪽(인프라)에서 안쪽(도메인 코어)으로만 향해야 한다는 클린 아키텍처의 대원칙을 도식화하고, DIP(의존성 역전 원칙)가 어떻게 아웃바운드 포트를 제어하는지 맵핑해야 한다.

## 출제 의도 및 답안 포인트

| 출제 의도 | 반드시 짚을 핵심 | 감점 회피 포인트 |
|:---|:---|:---|
| 기존 Layered(계층형) 아키텍처의 치명적 한계(DB 종속성) 지적 | Service가 Repository(DB)에 의존하는 하향식 결합도 | Layered 패턴을 여전히 최고라고 칭송하거나 문제의식을 도출하지 않음 |
| 헥사고날 아키텍처의 컴포넌트 메커니즘 (포트와 어댑터) | Inbound/Outbound Port(인터페이스)와 Adapter(구현체) 분리 | 왜 육각형인지 도형의 의미에 집착하여 원리를 놓침 (포트의 다면성을 의미할 뿐임) |
| 객체 지향 5원칙(SOLID)과의 엔지니어링적 결합도 | **DIP (의존성 역전)**를 통한 아웃바운드 의존성 화살표 역전 | DIP(의존성 역전) 언급 없이 단순히 인터페이스만 쓴다고 얕게 서술 |

> 요약: 10년 뒤에 회사가 Spring 프레임워크를 버리고 Node.js로 갈아타기로 결정했다. 이때 헥사고날로 짠 코드는 '바깥쪽 껍데기(어댑터)'만 Node.js로 다시 짜면, 안쪽의 수십만 줄짜리 비즈니스 로직은 단 한 글자도 수정 없이 복붙(재사용)이 가능하다.

## Ⅰ. 개요 및 필요성

- 정의: 알리스테어 코오번(Alistair Cockburn)이 제안한 모델로, 애플리케이션 코어를 캡슐화하고 외부와의 통신을 Port(인터페이스)와 Adapter(구현 모듈)로 추상화하는 포트 앤 어댑터(Ports and Adapters) 아키텍처
- 배경: 전통적 3계층(Presentation-Business-Data) 구조에서는 비즈니스 로직이 하위의 영속성(DB) 계층에 강하게 결합(Tightly coupled)되어, DB 벤더나 테이블 구조가 바뀌면 비즈니스 로직이 파괴되는 역전 현상 발생
- 필요성: 순수 비즈니스 로직(Domain)을 특정 프레임워크(Spring)나 인프라스트럭처(Oracle, Kafka) 기술 부채로부터 완벽히 격리(Isolation)하여, MSA 환경에서의 이식성(Portability)과 단위 테스트(Unit Test) 용이성을 확보하기 위함

## Ⅱ. 헥사고날 (Port & Adapter) 아키텍처 핵심 제어 도식

핵심은 "모든 화살표(의존성)는 무조건 안쪽(Core)을 향해 찌른다"는 것이다.

```text
[ 헥사고날 아키텍처 의존성 화살표 (Inward Dependency) 도식 ]

(외부 사용자/시스템)                                                         (외부 인프라/DB)
      |                                                                         ^
      V                                                                         |
[ Inbound Adapter ]                                                    [ Outbound Adapter ]
(웹 Controller, REST API)                                              (JPA Repository, Kafka 발송)
      | (호출)                                                                  ^ (구현)
      V                                                                         |
========================= < 육각형 경계 (Hexagon) > =========================================
   [ Inbound Port ]                                                   [ Outbound Port ] 
  (비즈니스 유스케이스 인터페이스) <---(의존)--- [ 순수 도메인 코어 ] ---(의존)---> (DB 조회를 위한 인터페이스)
      ^ (구현)                                  (POJO 비즈니스 로직) 
      |                                (프레임워크, DB 관련 어노테이션 절대 금지) 
   [ Application Service ]
=============================================================================================
```

| 컴포넌트 맵핑 | 아키텍처적(엔지니어링) 제어 메커니즘 | 실무 방어 효과 |
|:---|:---|:---|
| **Domain Core** <br> (안쪽 육각형) | 순수 Java(POJO)로만 작성된 도메인 엔티티와 비즈니스 룰 덩어리. 밖으로 나가는 화살표가 전혀 없는 **무의존성 성역** | JPA `@Entity` 떡칠이나 Spring `@Transactional` 어노테이션 침투 원천 차단 (순수성 방어) |
| **Port** <br> (포트 / 인터페이스) | 안쪽(코어)과 바깥쪽(어댑터)이 대화하기 위한 규격서(Interface). `Inbound`는 "나한테 명령하려면 이 규격 맞춰", `Outbound`는 "DB 조회가 필요하니 누가 이 규격대로 가져와" | USB C타입 규격과 같음. 이 규격만 맞추면 바깥에서 무슨 기술(Web, CLI, Test)이 꽂히든 상관 안 함 |
| **Adapter** <br> (어댑터 / 구현체) | 포트 규격에 맞춰 실제 외부 기술과 결합하는 모듈. `Inbound`는 HTTP JSON을 포트에 맞게 번역, `Outbound`는 포트의 요청을 SQL 쿼리로 번역 | 외부 DB가 Oracle에서 MongoDB로 통째로 갈려도, `Outbound Adapter` 클래스 딱 1개만 교체하면 완료 (OCP 완벽 달성) |

> 요약: 헥사고날의 핵심은 'DIP(의존성 역전)'를 쓴 오른쪽(아웃바운드)이다. 비즈니스 로직(안쪽)이 DB 저장소(바깥쪽)를 직접 부르는 게 아니라, 안쪽에서 "저장해 주는 인터페이스(Port)"만 딸랑 던져놓으면, 바깥쪽(DB Adapter)이 그 인터페이스를 억지로 상속받아(역전) 구현체를 밀어 넣어 바치는 구조다.

## Ⅲ. 극복해야 할 시스템적 리스크 (오버엔지니어링의 덫)

안전장치를 너무 많이 달면 무거워서 날지 못한다. 헥사고날의 패착은 끔찍한 코드 량(보일러플레이트) 폭발이다.

| 리스크 요인 | 발생 시나리오 및 시스템 붕괴 원인 | 아키텍처 대응 방안 (실무 튜닝) |
|:---|:---|:---|
| **보일러플레이트 코드 폭증** <br> (클래스 폭발) | 단순 게시판(CRUD) 하나 만드는데, `Controller -> InPort -> Service -> OutPort -> Adapter -> Entity` 6개의 클래스 파일과 DTO 맵퍼가 강제되어 개발 속도 마비 | CQRS 기반 타협 튜닝: 복잡한 비즈니스 로직이 없는 **단순 조회(Read-only Query) 기능은 과감히 헥사고날 룰을 깨고 Controller에서 즉시 DB Query 모델을 직접 호출**하는 바이패스(Bypass) 허용 (실용주의 도입) |
| **DTO 객체 변환 오버헤드** | 계층(어댑터-포트-도메인)을 넘어갈 때마다 데이터를 캡슐화하기 위해 DTO(Web DTO -> Command DTO -> Domain Entity)로 계속 값을 복사(Mapping)하다가 CPU 및 메모리 할당 병목 폭발 | MapStruct 같은 고성능 객체 매핑 라이브러리를 바이트코드 컴파일 타임에 강제화하고, 포트 바운더리를 넘어설 때 불변 객체(Immutable)를 사용하여 복사 비용(Deep Copy) 방어 |

> 요약: 헥사고날은 개발자들의 인건비(노가다 시간)를 태워 미래의 확장성(안전)을 사는 극단적 보험이다. 변경이 거의 없는 단순 서비스에 이 짓을 하면, 코드의 바다에 빠져 질식사한다.

## Ⅳ. MSA와 도메인 주도 설계(DDD)와의 아키텍처 융합

헥사고날은 단독으로 쓰기보단 MSA 환경에서 마이크로서비스 1개의 뼈대로 들어갈 때 진가를 발휘한다.

| 진화 아키텍처 연계 | 물리적 융합 메커니즘 | 해결되는 비즈니스/운영 한계 |
|:---|:---|:---|
| **DDD (도메인 주도 설계)** <br> 전술적 패턴 융합 | DDD의 `Aggregate Root`와 `Entity`가 헥사고날의 '안쪽 코어'에 정확히 안착. DDD의 `Domain Service`가 Inbound Port를 구현하며 순수 도메인 로직 격리 완성 | 기획자의 '비즈니스 룰'과 개발자의 'Java 코드'가 1:1로 100% 일치되어, 기획 변경 시 코드를 수정할 위치를 1초 만에 식별 (Traceability) |
| **테스트 주도 개발 (TDD)** <br> 유닛 테스트 100% | 바깥쪽 인프라(DB, 웹)를 떼어내고, 빈 구멍(Port)에 Mockito(가짜 객체)를 꽂아 넣어 코어 비즈니스 로직만 빛의 속도로 테스트 가능 | DB가 구축되지 않았거나 외부 API 통신이 단절된 상황에서도, 백엔드 비즈니스 룰 검증 CI/CD 파이프라인(Jenkins) 0.1초 컷 패스 |

> 요약: 헥사고날을 짜면 개발 중에 "우리 DB 아직 세팅 안 됐는데요?"라는 핑계가 통하지 않는다. DB 포트(구멍)에 가짜(Mock) 어댑터를 임시로 꽂아놓고 비즈니스 로직(할인율 계산 등)을 완벽하게 다 짜서 테스트까지 마칠 수 있기 때문이다.

## Ⅴ. 실무 적용 방안 및 결론

**적용 방안 3개:**
1. [결제 도메인(Payment) 코어 로직의 완벽 격리 보호] 쇼핑몰 내 가장 복잡도가 높은 '결제 MSA' 구축 시, `PaymentProcessor` 코어에 Spring Web 플러그인(`HttpServletRequest`)과 JPA 플러그인 침투를 원천 차단하고, 순수 Java 로직으로만 20종의 쿠폰/포인트 할인 룰을 연산하도록 헥사고날로 완전 고립(Isolation)
2. [이벤트 기반(EDA) 아웃바운드 어댑터 플러그인 확장] MSA 간 통신 룰이 RabbitMQ에서 Apache Kafka로 교체되는 인프라 대공사 발생 시, 코어 로직은 전혀 건드리지 않고 오직 `EventPublishOutboundPort`를 구현하는 `KafkaAdapter` 클래스 단 1개만 갈아 끼워(Plug-in) 무중단 인프라 마이그레이션 달성
3. [멀티 디바이스 인바운드 뷰(View) 확장] 동일한 '주문 접수' 코어 로직(Port)을 두고, Inbound 쪽 껍데기만 3개(`WebAdapter`, `MobileAppAdapter`, `KafkaConsumerAdapter`)로 찍어내어, 하나의 비즈니스 코어가 웹 요청, 앱 API 요청, 비동기 메시지 요청을 모두 동시 지원하는 다형성(Polymorphism) 아키텍처 완성

**결론:**
- 기술사 판단: 헥사고날 아키텍처는 기술(프레임워크, DB)이라는 꼬리가 도메인(비즈니스)이라는 몸통을 흔들던(Tail wags dog) 레거시 시대의 기형적 종속성을 파괴한 클린 아키텍처의 실전 도면이다. 초기 폴더 구조와 인터페이스 파일이 비대해지는 초기 비용(Trade-off)을 감수하고서라도, 5년 이상 생존해야 하는 핵심 MSA 서버 코어에는 타협 없이 강제해야 할 엔지니어링 표준이다.
- 향후 방향: 최근 실무에서는 헥사고날의 보일러플레이트 극단성을 완화하기 위해, 명령(Command) 처리에는 엄격한 헥사고날과 DDD를 적용하여 무결성을 방어하고, 조회(Query)에는 포트 앤 어댑터를 무시하고 MyBatis나 JPA Projections로 직접 화면을 렌더링하는 CQRS(명령/조회 분리) 융합 아키텍처가 대세로 자리 잡았다.
