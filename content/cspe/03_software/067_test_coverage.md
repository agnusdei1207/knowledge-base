# 📖 【암기용】 개념 완전 이해

## 한눈에
- **개요**: 작성된 소스코드가 테스트 과정에서 얼마나 실행되었는지를 정량적으로 나타내는 측정 지표
- **왜 필요한가**: "테스트 다 했어요!"라는 개발자의 말을 숫자로 검증하기 위해. 커버리지가 낮으면 안 돌아간(숨겨진) 코드가 많아 버그가 터질 확률이 높다.
- **핵심 직관**: 손전등(테스트)으로 어두운 방(코드)을 비출 때, 방의 구석구석을 얼마나 밝혔는가를 나타내는 퍼센트. 100%면 어두운 곳이 없다는 뜻.

## 핵심 용어 정리

| 용어/표기 | 의미 | 비유·예 |
|:---|:---|:---|
| 구문 커버리지 (Statement) | 전체 문장(라인) 중 몇 줄이 실행되었는가 | 미로의 모든 방을 밟았는가? |
| 결정 커버리지 (Decision, 분기) | if/while 등의 참(T)과 거짓(F) 분기를 모두 탔는가 | 교차로에서 좌/우회전 다 해봤는가? |
| 조건 커버리지 (Condition) | 전체 조건식이 아닌, 개별 조건식이 참/거짓을 다 가졌는가 | A>0 (T/F), B>0 (T/F) 각각 만족 여부 |
| MC/DC | 조건/결정 커버리지의 약점을 극복한 항공/자동차 수준의 엄격한 기법 | "내 결정이 전체 결과를 바꿀 수 있나?" |

## 깊이 이해
- **배경·문제의식**: 코드가 복잡해지면 수많은 if-else 분기가 생긴다. 단순 구문 커버리지 100%를 달성했다고 해도, `if` 조건이 거짓일 때 발생하는 에러(숨은 분기 오류)를 놓칠 수 있다. 따라서 커버리지의 "강도(Rigor)"를 단계별로 높여야 한다.
- **작동 원리**: 코드를 예로 들면 `if (A > 0 and B > 0)`이 있다. 
  - **구문**: 내부 코드를 실행시키기 위해 둘 다 True인 케이스 1개만 돌리면 달성.
  - **결정(분기)**: if 전체 결과가 True, False가 되도록 2개 케이스를 돌리면 달성.
  - **조건**: A가 T/F, B가 T/F를 갖도록 돌리되, 전체 if 결과는 무관.
  - **조건/결정(C/DC)**: 개별 조건과 전체 결정이 모두 T/F를 갖게 복합 테스트.
  - **MC/DC**: 독립적으로 영향을 미치는 최소한의 조합만 추출해 폭발적인 케이스 수를 줄이면서 100% 안전성을 증명.
- **흔한 오해·주의점**: "커버리지 100% = 결함 0%"? 절대 아니다! 커버리지는 '코드가 실행됨'을 보장할 뿐, '기능이 올바름'을 보장하지 않는다. 즉, 오타나 잘못된 수식이 실행되었어도 100%로 잡힌다. 명세 기반(블랙박스) 테스트가 병행되어야 한다.

## 연결 개념
- 화이트박스 테스트: 테스트 커버리지를 측정하는 근간이 되는 기법
- 정적 분석기 (SonarQube): 빌드 파이프라인에서 커버리지를 자동 측정하는 도구
- ISO 26262 (기능 안전 표준): 자동차 도메인에서 ASIL 등급에 따라 MC/DC를 법적으로 강제함

# 📝 【답안용】 시험 답안 템플릿

## 핵심 인사이트 (3줄 요약)

> 1. **본질**: 테스트 커버리지는 소프트웨어 소스코드가 테스트 스위트에 의해 얼마나 실행되었는지를 구조적으로 측정하는 화이트박스 정량 지표다.
> 2. **가치**: 수행되지 않은 코드(Dead code)나 테스트 누락 구간을 식별하고, 목표 커버리지(예: 80%)를 빌드 게이트웨이로 설정하여 품질을 통제한다.
> 3. **판단 포인트**: 구문 < 분기 < 조건/결정 < 다중조건 순으로 강도가 높아지며, 특히 안전 필수 도메인(Safety-critical)에서 요구되는 MC/DC의 독립적 영향 평가 원리를 정확히 대비해야 한다.

## 출제 의도 및 답안 포인트

| 출제 의도 | 반드시 짚을 핵심 | 감점 회피 포인트 |
|:---|:---|:---|
| 커버리지 레벨의 차이 구분 | 구문, 결정(분기), 조건, 조건/결정, 다중조건 정의 | 결정(분기)과 조건을 혼동 |
| MC/DC (Modified Condition / Decision) 이해 | 개별 조건의 독립적 영향, TC 개수 최적화 (N+1) | MC/DC 원리를 다중조건으로 잘못 서술 |
| 실무 적용 및 품질 통제 방안 | CI/CD 파이프라인 내 SonarQube 등 연동, 게이트웨이 제어 | 단순히 이론 나열에 그침 |

> 요약: 각 커버리지가 해결하지 못하는 맹점을 다음 단계의 커버리지가 어떻게 보완하는지(특히 분기 vs 조건) 논리적으로 보여주어야 한다.

## Ⅰ. 개요 및 필요성

- 개요: 테스트 대상의 전체 논리 구조(구문, 분기, 조건) 대비 실제 테스트가 수행된 비율을 측정하는 정량적 품질 지표
- 배경: 테스터의 직관에 의존한 테스트는 숨겨진 분기나 복잡한 논리 조합을 놓쳐 운영 단계 장애로 직결됨
- 필요성: 테스트 완전성(Completeness)의 객관적 증명, 미수행 코드(Dead Code) 색출, 안전 필수 시스템(자동차, 항공)의 국제 표준 준수

---

## Ⅱ. 구조 및 구성요소

```text
[코드 덩어리] -> if (A && B) { ... }
                 |
  1단계 강도: 구문 커버리지 (Statement) - 코드 블록 진입 여부
  2단계 강도: 결정 커버리지 (Decision) - if 전체의 T/F 결과
  3단계 강도: 조건 커버리지 (Condition) - A와 B 각각의 T/F 결과
  4단계 강도: MC/DC 커버리지 - A/B가 전체 결과에 미치는 독립적 영향 평가
```

| 커버리지 유형 | 측정 기준 | 한계점 |
|:---|:---|:---|
| 구문 (Statement) | 소스코드 내 전체 문장이 실행된 비율 | 거짓(False) 조건이나 생략된 분기 오류 미발견 |
| 결정/분기 (Decision/Branch) | 전체 결정식(조건문)이 참(T)/거짓(F)을 모두 갖는 비율 | 개별 조건식의 논리 오류(AND/OR 혼동) 미발견 |
| 조건 (Condition) | 전체 식과 무관하게, 개별 조건식이 각각 T/F를 갖는 비율 | 전체 결정식이 참/거짓을 다 가지지 않을 수 있음 |
| 조건/결정 (C/DC) | 개별 조건식 T/F와 전체 결정식 T/F를 모두 충족하는 비율 | 특정 개별 조건이 결과에 영향을 주지 못하고 묻힐 수 있음 |

> 요약: 구문 커버리지가 가장 약하고 조건/결정 커버리지 이상으로 갈수록 테스트 강도와 비용이 기하급수적으로 증가한다.

---

## Ⅲ. 심화 동작원리 (MC/DC)

**MC/DC (Modified Condition / Decision Coverage)**
- 원리: "다른 모든 개별 조건은 고정된 상태에서, 단일 조건의 변화가 전체 결정 결과에 독립적으로 영향을 미침"을 증명
- 목적: 다중 조건 커버리지(2^N)의 폭발적 테스트 케이스 증가 문제를 (N+1)개로 획기적으로 축소하면서 100% 안전성 보장

```text
조건식: Z = A and B  (N=2, TC는 N+1=3개 필요)
1) A=T, B=T -> Z=T
2) A=F, B=T -> Z=F (A가 Z에 독립적 영향을 미침: 1번과 비교)
3) A=T, B=F -> Z=F (B가 Z에 독립적 영향을 미침: 1번과 비교)
```

- 활용처: DO-178C(항공기), ISO 26262(자동차 ASIL-D) 등 최고 수준의 안전 표준에서 법적으로 강제

> 요약: MC/DC는 조건과 결정 커버리지를 모두 만족하면서도, 조합 폭발 문제를 우회하는 가장 효율적인 고강도 기법이다.

---

## Ⅳ. 특징
- [비례성 오류]: 커버리지가 높다고 품질이 선형적으로 높은 것은 아님 (잘못된 수식을 계산하는 코드는 실행되어도 100%로 집계됨)
- [한계 수확 체감]: 커버리지를 80%에서 100%로 끌어올리는 비용은 0%에서 80%를 만드는 비용보다 훨씬 크며, 가성비가 떨어짐
- [안전 표준 강제성]: 도메인별 생명과 직결된 시스템은 임의의 목표가 아닌 국제 표준이 정한 커버리지율(예: 100% MC/DC)을 필수 충족해야 함
- [자동화 용이성]: 소스코드 구조 기반이므로 JaCoCo, Cobertura 등의 정적/동적 도구를 통해 100% 측정 자동화가 가능함

> 요약: 정량적 통제에는 탁월하나, '기능의 올바름'을 입증하는 블랙박스 테스트와 병행해야 진정한 품질을 보장한다.

---

## Ⅴ. 심화 비교 및 적용 판단

| 비교 축 | 분기 커버리지 (Branch) | 조건 커버리지 (Condition) | 선택 기준 |
|:---|:---|:---|:---|
| 포커스 | 전체 조건문의 결과(T/F) | 개별 조건문의 결과(T/F) | 검증 대상의 복잡도 |
| 상호 보완성 | 개별 조건 무시 | 전체 결정 무시 | 두 기법 단독 사용 불가 (C/DC 필요) |
| 도입 도메인 | 일반적인 엔터프라이즈 앱 | 높은 논리 복잡도를 가진 시스템 | 리스크 수준 및 투입 비용 |

> 요약: 분기 커버리지는 개별 조건의 오류를 덮어버리고, 조건 커버리지는 분기를 타지 못하는 약점이 있어 C/DC나 MC/DC로 결합해야 한다.

**리스크·대응:**
- [맹목적 100% 추구]: 방어적 코드(예외처리) 강제 수행을 위한 억지 TC 작성으로 개발 기간 지연 → 80% 수준에서 Quality Gate를 설정하고, 비즈니스 핵심 로직만 100% 타겟팅 (지표: 커버리지 대비 장애 발생률 비교)
- [품질 착시 현상]: Assertion(결과 검증) 없는 무의미한 테스트 케이스로 커버리지 퍼센트만 뻥튀기 → 뮤테이션 테스트(Mutation Testing)를 도입하여 테스트 케이스 자체의 견고성 교차 검증 (지표: 뮤테이션 스코어)

---

## Ⅵ. 실무 적용 및 결론

**적용 방안 3개:**
1. CI/CD 파이프라인 Quality Gate 연동: Jenkins에서 PR(Pull Request) 병합 시, 신규 추가된 코드의 라인 커버리지가 80% 미만일 경우 Merge를 자동 차단(Reject) 설정
2. ASIL-D 수준 MC/DC 적용: 자율주행, 의료기기 등 크리티컬 모듈에 대해서는 단위 테스트 도구(VectorCAST 등)를 활용하여 100% MC/DC를 강제 달성하고 리포팅
3. 커버리지 뱃지(Badge) 시각화: GitLab, GitHub 저장소 메인 화면에 현재 빌드의 커버리지 퍼센트를 뱃지로 노출하여 개발 조직 내 품질 경쟁 및 심리적 기준 상향

**결론 (2줄):**
- 기술사 판단: 커버리지는 결함을 찾는 은탄환이 아니며, 코드의 유지보수 안전망을 구축하고 최소한의 실행을 강제하는 '가드레일'로 활용해야 한다.
- 향후 방향: 단순 구문/분기 커버리지 달성을 넘어, 돌연변이 코드를 주입하여 테스트 스위트의 품질 자체를 검증하는 뮤테이션 테스트(Mutation Test)로 진화해야 한다.
