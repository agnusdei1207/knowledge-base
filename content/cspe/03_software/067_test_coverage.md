## 핵심 인사이트 (3줄 요약)
- 소프트웨어의 전체 소스 코드 중, 자동화된 테스트 코드(TC)에 의해 **실제로 실행(검증)된 코드의 비율**을 나타내는 정량적 품질 지표.
- 구문(Statement), 결정(Decision/Branch), 조건(Condition) 등 코드를 얼마나 촘촘하게 훑었느냐에 따라 커버리지의 강도가 다름.
- 커버리지가 높다고 버그가 없는 것은 아니지만, 커버리지가 낮으면 언제 시스템이 무너질지 모르는 시한폭탄(레거시)을 안고 있는 것과 같음.

## Ⅰ. 개요 및 필요성
- **개요**: 테스트 케이스가 소스 코드의 구조적 요소(제어 흐름)를 얼마나 실행했는지 측정하는 화이트박스 테스트 지표.
- **필요성**: 개발자가 "테스트 다 짰어요!"라고 말할 때, 그것이 정말로 모든 예외 상황(if/else)을 다 커버했는지 객관적으로 증명할 수단이 필요했음. 소나큐브(SonarQube)나 JaCoCo 같은 정적 분석 도구를 통해 CI/CD 파이프라인에서 품질 게이트(Quality Gate) 역할을 수행함.
---
## Ⅱ. 아키텍처 및 핵심 원리
- **구문 커버리지 (Statement Coverage)**:
  - 소스 코드의 모든 '실행 가능한 문장(Line)'이 최소 1번 실행되었는가? (가장 약한 기준).
- **결정 커버리지 (Decision / Branch Coverage)**:
  - `if`나 `while` 같은 제어문(분기)이 **참(True)과 거짓(False)** 결과를 최소 1번씩 가졌는가? (실무적 표준).
- **조건 커버리지 (Condition Coverage)**:
  - 제어문 내부의 **개별 조건식**들이 각각 참과 거짓을 가졌는가?
- **조건/결정 커버리지 (Condition/Decision Coverage)**:
  - 개별 조건식의 T/F와 전체 결과의 T/F를 모두 만족하는가?
- **MC/DC (Modified Condition/Decision Coverage)**:
  - 다른 조건에 영향을 주지 않고, 오직 특정 개별 조건 하나만으로 전체 결과가 바뀌는 독립적 영향을 100% 테스트함 (항공/의료 등 인명 직결(Safety-Critical) 소프트웨어의 국제 표준 DO-178B 기준).

```text
[ 커버리지 유형별 강도와 포함 관계 ]

 (가장 약함)                                                (가장 강함)
 구문(Statement) ⊂ 결정(Decision) ⊂ 조건/결정(C/D) ⊂ MC/DC ⊂ 다중 조건(Multiple)
 
 * 예: if (A && B) { ... }
   - 구문: 안쪽 블록이 1번만 실행되면 통과 (A=T, B=T)
   - 결정: 블록 실행 1번, 건너뛰기 1번 (A=T, B=T / A=F, B=F)
   - MC/DC: A가 결과를 바꾸는 경우, B가 결과를 바꾸는 경우를 엄밀히 증명
```

## Ⅲ. 비교 및 연결
| 구분 | 구문 커버리지 (Line/Statement) | 분기/결정 커버리지 (Branch/Decision) | MC/DC |
|---|---|---|---|
| **측정 대상** | 코드의 줄(Line) 단위 | If, Switch 문의 True/False 방향 | 개별 조건의 독립적 영향도 |
| **달성 난이도** | 쉬움 | 보통 (실무 권장) | 매우 어려움 (TC 개수 최적화) |
| **은닉 버그 발견**| `else` 문이 비어있으면 에러 못 잡음 | `else`로 빠지는 흐름까지 완벽히 잡음 | 복잡한 복합 논리식의 논리 오류 탐지 |
| **주 적용처** | 일반적인 웹 애플리케이션 | 엔터프라이즈 서버 시스템 | 항공기, 자율주행, 의료기기 SW |

## Ⅳ. 실무 적용 및 기술사 판단
- **커버리지 100%의 환상과 역효과**: 커버리지를 100%로 강제하면, 개발자들은 단순히 커버리지 수치만 채우기 위해 `assert`(검증)가 없는 의미 없는 테스트 코드(껍데기 TC)를 양산함. 실무에서는 전체 80% 달성을 목표로 하되, 핵심 도메인 로직은 95% 이상, DTO나 단순 UI 코드는 제외하는 유연한 임계치(Threshold) 설정이 필수임.
- **돌연변이 테스트(Mutation Testing)의 보완**: 커버리지는 "코드가 실행되었는가"만 볼 뿐, "테스트가 버그를 진짜 잡아내는가"는 보장하지 못함. 이를 해결하기 위해 일부러 원본 코드에 버그(돌연변이)를 주입해 놓고 기존 테스트가 이를 찾아내서 실패(Kill)하는지 검증하는 기법이 대두되고 있음.
---
## Ⅴ. 기대효과 및 결론
- 테스트 커버리지는 시스템의 "기술 부채(Technical Debt)"를 시각화하여, 코드를 안심하고 리팩토링할 수 있는 안전망의 두께를 알려줌.
- "측정할 수 없는 것은 관리할 수 없다"는 명언처럼, 커버리지는 지속적 통합(CI) 환경에서 나쁜 코드가 프로덕션으로 배포되는 것을 막는 가장 강력하고 기계적인 수문장임.

### 👶 어린이를 위한 3줄 비유 설명
1. 롤러코스터 레일(소스 코드)을 새로 만들었어요. 이 레일이 안전한지 보려면 빈 수레(테스트)를 굴려봐야겠죠?
2. 테스트 커버리지는 수레가 레일의 '모든 길(분기점)'을 구석구석 다 한 번씩 지나갔는지 퍼센트(%)로 점수를 매겨주는 거예요.
3. 점수가 100점이면 모든 길을 한 번씩 가봤다는 뜻이라 안심할 수 있지만, 30점이면 나머지 70% 길은 수레가 가다가 낭떠러지로 떨어질지 아무도 모른다는 무서운 뜻이랍니다!
