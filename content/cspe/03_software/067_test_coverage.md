# 📖 【암기용】 개념 완전 이해

> 목적: 이 개념을 처음 보는 사람도 완벽히 이해하게 만든다. 시험 답안 양식이 아니라, 이해를 위한 친절한 설명이다.

## 한눈에
- **개요**: **테스트 커버리지**는 화이트박스 테스트에서 작성한 테스트 케이스가 대상 소스코드의 구문·분기·조건·경로 등 논리적 제어 구조를 얼마나 실행했는지를 백분율(%)로 측정하는 지표다. 코드의 몇 %가 "테스트에 의해 실제로 밟혔는가"를 재는 것이지, 실행 결과가 맞는지(assertion) 자체를 보장하지는 않는다.
- **왜 필요한가**: "테스트를 다 짰다"는 개발자의 주관적 주장은 신뢰하기 어렵다. 같은 정상 흐름만 반복해서 테스트하고 예외 처리 코드는 한 번도 실행하지 않을 수 있기 때문이다. 커버리지는 이런 사각지대를 숫자로 드러내, CI/CD 파이프라인이 기계적으로 배포를 막을 수 있는 객관적 기준을 제공한다.
- **핵심 직관**: 코드를 갈림길이 있는 미로라고 하면, 구문 커버리지는 "바닥을 한 번씩 밟았는가", 분기 커버리지는 "갈림길 양쪽을 다 가봤는가", 경로 커버리지는 "입구부터 출구까지 가능한 모든 경우의 수를 다 가봤는가"를 묻는다. 뒤로 갈수록 요구 강도가 세진다.

## 핵심 용어 정리
| 용어 | 의미 | 비유 |
|:---|:---|:---|
| 테스트 커버리지 | 테스트가 소스코드의 논리 구조를 실행한 비율 | 밟은 면적의 비율 |
| 구문 커버리지 (Statement) | 실행 가능한 코드 줄 중 최소 1번 실행된 줄의 비율 | 바닥 블록을 한 번씩 밟기 |
| 분기 커버리지 (Branch/Decision) | `if`문 전체 결과가 참(T)·거짓(F) 각각 한 번씩 나온 비율 | 갈림길 양쪽 다 가보기 |
| 조건 커버리지 (Condition) | `if`문 안의 개별 조건 각각이 참·거짓을 모두 가진 비율 | 각 신호등을 개별로 점검 |
| 조건/분기 커버리지 (C/D) | 분기 기준과 조건 기준을 모두 만족하는 결합 지표 | 전체와 부분을 동시에 확인 |
| MC/DC (변형 조건/분기) | 다른 조건은 고정한 채 조건 1개만 바꿨을 때 전체 결과가 그 조건에 의해 바뀌는지 확인하는 지표 | 나머지는 고정하고 변수 1개씩 실험 |
| 경로 커버리지 (Path) | 시작부터 끝까지 가능한 모든 실행 흐름 조합을 실행한 비율 | 미로의 모든 경로 답파 |
| 계측 (Instrumentation) | 커버리지 측정 도구가 코드에 실행 여부를 기록하는 카운터를 삽입하는 과정 | 통과 지점마다 도장 찍기 |
| Quality Gate | 커버리지 등 품질 지표가 기준 미달이면 빌드·배포를 차단하는 CI 관문 | 기준 미달 시 통과 불가 |

## 깊이 이해

### 배경 — 테스트 개수(양)가 아니라 실행 범위(질)를 재는 이유
"테스트를 100개 작성했다"는 개수는 그 테스트들이 코드의 어느 부분을 실행하는지 말해주지 않는다. 같은 정상 흐름(Happy Path)만 100번 반복해서 테스트해도, 예외 처리(`catch`) 블록은 단 한 번도 실행되지 않은 채 남아있을 수 있다. 이런 미실행 코드가 운영 환경에서 처음 실행되면 결함이 그대로 노출된다. 그래서 "테스트가 코드의 몇 %를 실제로 지나갔는가"를 재는 정량 지표가 필요해졌다.

### 5개 커버리지 유형을 하나의 코드로 비교하기
`if (a > 0 && b > 0) { ... }`라는 조건문 하나를 기준으로 비교한다.
1. **구문 커버리지**: 이 블록 안으로 최소 1번만 들어가면(예: a=1, b=1) 블록 내부 문장은 100% 채워진다. 조건이 거짓이 되는 경우(예외 흐름)는 전혀 검증하지 않아도 100%가 나올 수 있다는 게 약점이다.
2. **분기 커버리지**: 전체 조건식이 참(T)이 되는 케이스 1개(a=1, b=1)와 거짓(F)이 되는 케이스 1개(a=-1, b=1)를 넣으면 100%가 된다. 다만 `a`와 `b` 개별 값의 조합은 따지지 않는다.
3. **조건 커버리지**: `a>0`이 T/F 한 번씩, `b>0`이 T/F 한 번씩 나오면 만족한다. 그런데 (a=1,b=1)과 (a=-1,b=-1) 두 케이스만으로도 개별 조건 T/F는 모두 채워지지만, 전체 결과는 계속 T, F로만 나오고 조합 오류(A는 맞는데 B가 틀려서 전체가 F가 되는 경우)를 놓칠 수 있다.
4. **조건/분기 커버리지**: 3번(개별 조건 T/F)과 2번(전체 T/F)을 모두 만족해야 하므로 케이스 수가 늘어난다.
5. **MC/DC**: `b`를 고정(예: b=1)한 채 `a`만 1에서 -1로 바꿨을 때 전체 결과가 T에서 F로 바뀌는 것을 확인하고, 다음으로 `a`를 고정한 채 `b`만 바꿔 같은 것을 확인한다. 즉 조건이 N개면 최소 N+1개의 케이스로 각 조건의 "독립적 영향력"을 증명한다. 조건이 2개(N=2)면 MC/DC는 3개 케이스로 충분하지만, 모든 조합을 다 따지는 다중 조건 커버리지는 2²=4개, 조건이 5개면 다중 조건은 2⁵=32개가 필요한 반면 MC/DC는 N+1=6개로 끝난다. 이 차이 때문에 MC/DC는 항공·의료기기 소프트웨어 표준(DO-178C)에서 요구하는 실용적 절충안으로 채택되어 있다.

### 경로 커버리지가 현실적으로 100% 불가능한 이유
독립된 `if`문 3개가 순서대로 있으면 가능한 경로는 2×2×2=8가지다. 조건이 5개면 2⁵=32가지로 늘어난다. 여기에 반복문(`for`)이 하나만 섞여도 반복 횟수만큼 경로가 곱해지므로, 반복 횟수가 입력에 따라 달라지는 일반적인 코드에서는 가능한 경로 수가 사실상 무한대로 발산한다. 그래서 경로 커버리지는 이상적인 상한선으로만 취급되고, 실무에서는 매카브(McCabe)의 순환 복잡도를 기준으로 최소한의 독립 경로만 추려 테스트하는 절충안을 쓴다.

### CI/CD와 결합해 숫자로 배포를 막는 원리
JaCoCo 같은 도구는 컴파일된 코드에 실행 여부를 기록하는 카운터를 심어(계측, Instrumentation) 실제 실행된 구문·분기 수를 수집한다. 이 결과를 SonarQube 같은 정적 분석 서버로 보내, 예를 들어 "분기 커버리지 80% 미만이면 빌드 실패"라는 Quality Gate 규칙을 걸어두면, 개발자가 코드를 커밋할 때마다 자동으로 기준 미달 시 배포가 차단된다. 실무에서는 구문 80% + 분기 70% 전후를 일반적인 기준선으로 삼고, 그 이상(조건/분기, MC/DC)은 결함 발생 시 인명·안전에 직결되는 미션 크리티컬 소프트웨어에 한정해 요구하는 경우가 많다.

### 비유
동네 골목길 순찰에 비유하면, 구문 커버리지는 큰길을 한 번씩 걸어본 것이고, 분기 커버리지는 갈림길에서 왼쪽·오른쪽을 각각 한 번씩 가본 것이며, 경로 커버리지는 그 동네에서 가능한 모든 이동 경로(오른쪽 돌고 직진, 왼쪽 돌고 후진 등)를 하나도 빠짐없이 걸어보는 것이다. 골목이 몇 개만 늘어나도 경로의 수는 순식간에 감당할 수 없이 불어난다.

## 연결 개념
- 066 화이트박스 테스트 — 테스트 커버리지는 화이트박스 테스트의 충분성을 재는 정량 지표
- 064 소프트웨어 테스트 — 주로 단위 테스트 단계에서 커버리지 목표(예: 80%)를 관리
- 뮤테이션 테스트 — 커버리지가 채워졌어도 assertion 품질이 낮을 수 있다는 맹점을 보완하는 2차 지표(066에서 상세)

# 📝 【답안용】 시험 답안 템플릿

> 목적: 시험장에서 25분에 그대로 쓰는 답안 양식. 작성방식(추상표현 금지·수치·도식·문제유형 전환)을 엄격히 지킨다.
> 핵심: 이 시험은 정보를 많이 나열하는 시험이 아니라, 문제 신호어에서 출제자 의도를 읽고 핵심 논점을 선별해 쓰는 시험이다.

## 핵심 인사이트 (3줄 요약)

> 1. **본질**: 화이트박스 테스트(구조 기반 검사)를 수행할 때, 작성된 테스트 케이스(TC) 세트가 대상 소스코드의 로직(제어 흐름)을 얼마나 빈틈없이 실행(Exercise)했는지를 정량적으로 백분율(%)로 측정한 품질 지표다.
> 2. **가치**: 감각(Heuristic)에 의존하는 개발자의 테스트 작성을 기계적인 정량적 수치로 가시화(Visibility)하여 사각지대(Dead Code)를 색출하고, CI/CD 퀄리티 게이트(Quality Gate)의 객관적 차단 기준으로 활용된다.
> 3. **판단 포인트**: 구문 -> 분기 -> 조건 -> 다중 조건 -> 경로 커버리지로 이어지는 포괄성(Subsumption) 계층 관계를 도식화하고, 미션 크리티컬(항공/국방) 환경에서 강제되는 극강의 커버리지인 MC/DC의 독립적 영향 원리를 명확히 규명해야 한다.

## 출제 의도 및 답안 포인트

| 출제 의도 | 반드시 짚을 핵심 | 감점 회피 포인트 |
|:---|:---|:---|
| 화이트박스 테스트의 정량적 측정(Metric) 지표 차이 규명 | **구문(Line) < 분기(Decision) < 조건(Condition)의 계층 수준** | 구문 커버리지 100%가 분기 커버리지 100%를 보장한다고 적는 치명적 오개념 |
| 다중 조건(AND/OR) 처리의 한계점과 최고 수준 척도 (MC/DC) | **MC/DC (Modified Condition/Decision)**의 독립적 영향 평가 원리 | MC/DC라는 단어만 던지고, "타 조건을 고정하고 개별 조건의 독립적 영향을 본다"는 원리를 누락 |
| 실무 DevSecOps / CI 파이프라인과의 아키텍처 융합 | **JaCoCo, SonarQube** 연동 빌드 블로킹(Blocking) 통제망 | 테스트 커버리지가 단순히 문서(보고용)로만 쓰인다고 적는 수동적 뷰 |

> 요약: 개발자가 "구문(Line) 커버리지 100% 찍었습니다!"라고 자랑하는 건 사기다. 코드의 모든 줄을 밟았을지는 몰라도, 엣지 케이스(`if`가 거짓일 때 건너뛰는 상황)는 1개도 검사 안 했을 확률이 높다. 최소한 **분기(Branch) 커버리지**를 들이밀어야 진짜 검사다.

## Ⅰ. 개요 및 필요성

- 정의: 구조 기반(화이트박스) 테스트의 충분성을 평가하는 지표로, 전체 소스코드의 구문, 분기, 조건, 경로 등의 논리적 제어 구조 중 테스트 케이스에 의해 실행된(Covered) 부분의 비율(%)
- 배경: 테스터의 주관적 경험에 의존한 블랙박스 테스트만으로는 소스코드 내부에 은닉된 예외 처리부(`catch`)나 악성 코드(백도어)가 한 번도 실행되지 않고 실서버로 유출되는(Defect Leakage) 맹점 노출
- 필요성: 테스트 케이스의 누락(Hole)을 기계적 알고리즘으로 식별하여 QA 커버리지 척도(Metric)를 객관화하고, 100% 무결성이 요구되는(DO-178C 등 국방/항공) 소프트웨어의 강제 인증 규격을 만족하기 위함

## Ⅱ. 화이트박스 커버리지 진화(Subsumption) 계층 도식

오른쪽으로 갈수록 테스트 짜기가 지옥같이 빡세지며(TC 개수 폭발), 커버리지의 강도가 세진다. (포괄 관계).

```text
[ 커버리지 강도(Strength) 포괄 계층 도식 ]
(약함)                                                                              (강함 / 무한대)
구문 (Statement) ⊂ 분기 (Decision) ⊂ 조건/분기 (C/D) ⊂ MC/DC ⊂ 다중 조건 (Multiple) ⊂ 경로 (Path)
```

| 커버리지 유형 | 검증 메커니즘 (코드 관점: `if (A && B)`) | TC 산출 조건 및 실무 적용 한계 |
|:---|:---|:---|
| **1. 구문 (Statement)** | 모든 **실행 가능한 코드 라인(문장)**을 최소 1번 밟음 | `if`문이 True일 때만 실행해도 전체 코드를 밟을 수 있어 False 상황 누락 (최하위 수준) |
| **2. 분기 (Decision)** <br> *(결정 커버리지)* | 전체 `if(결정)`문 덩어리가 최소 한 번 **참(T)과 거짓(F)** 결괏값을 가짐 | `A`와 `B`의 조합은 무시하고 최종 전체 덩어리의 T/F만 챙기므로 개별 조건 결함 누락 (일반 SW 표준) |
| **3. 조건 (Condition)** | 전체 덩어리는 무시하고, 개별 조건 `A`가 T/F, `B`가 T/F 한 번씩 가짐 | 개별 조건은 다 돌았는데, 묘하게 조합되어 전체 덩어리가 계속 T만 반환하는 논리 폭탄 발생 |
| **4. 조건/분기 (C/D)** | **분기(전체) + 조건(개별) 짬짜면**. 전체 덩어리 T/F, 개별 `A, B` T/F 모두 만족 강제 | TC 설계 개수가 너무 많아지고 조건 간섭(Masking)을 100% 잡아내지 못하는 한계 |

> 요약: 실무(일반적인 웹 백엔드)에서는 `구문 80% + 분기 70%` 정도만 맞춰도 CI/CD 파이프라인에서 훌륭한 수준으로 쳐준다. 그 위로 넘어가면 배보다 배꼽(테스트 짜는 비용)이 수백 배 더 커져서 스타트업은 파산한다.

---

## Ⅲ. 엔터프라이즈 극강 커버리지 척도: MC/DC 와 경로 커버리지

비행기가 추락(Bug)하면 사람이 수백 명 죽는다(Mission Critical). 이런 곳에선 위쪽의 허접한 커버리지로는 어림도 없다.

| 궁극의 커버리지 | 물리적(논리적) 통제 메커니즘 | 해결되는 비즈니스/품질 한계 |
|:---|:---|:---|
| **MC/DC** <br> (변형 조건 / 분기) | 다른 모든 조건은 T/F로 꽉 고정해 놓고(마스킹 방지), 오직 1개 타겟 조건(A)의 T/F만 스위칭했을 때, **전체 분기 결과가 A에 의해 종속적으로 100% 독립적 영향을 받아 바뀌는지** 테스트 조합 | 조건이 $N$개일 때 다중 조건 커버리지는 $2^N$개의 무한대 TC가 나오지만, MC/DC는 딱 $N+1$개의 TC만으로 $2^N$과 동일한 결함 검출력을 확보하는 가성비 최강 논리 튜닝 (항공 DO-178C 표준) |
| **경로 커버리지** <br> (Path Coverage) | 순서도(Control Flow Graph)에서 시작부터 끝까지 이어지는 **모든 논리적 조합 100% 패스 밟기** | `for` 반복문(Loop)이 1,000번 돌면 테스트 경로가 무한대(Infinity)로 발산하여 **현실 세계에서 달성 100% 불가능** (매카브의 순환 복잡도 기반 기초 경로 한정 활용) |

> 요약: 자율주행 자동차 브레이크 코드를 분기 커버리지로 통과시켰다간 당장 감옥에 간다. MC/DC 기법은 "브레이크 센서 A, B, C 중에 B 센서 하나만 고장 났을 때 전체 시스템이 어떻게 반응하는지 독립적으로 발라내어 증명"하는 수술용 메스다.

## Ⅳ. CI/CD 파이프라인 아키텍처 연동 융합 (Quality Gate)

개발자가 로컬 PC에서 커버리지 높다고 찍은 스크린샷은 쓰레기다. 무조건 서버 파이프라인 봇(Bot)이 측정해서 차단해야 한다.

| 아키텍처 융합 | 물리적 제어 파이프라인 (엔지니어링 튜닝) |
|:---|:---|
| **JaCoCo 기반** <br> 바이트코드 인젝션 | 개발자가 커밋(Push) 시 Jenkins 파이프라인에서 Java 바이트코드(`.class`) 사이사이에 카운터(Counter) 코드를 쑤셔 넣어(Instrumentation), **실제 실행된 구문과 분기 라인 수를 JVM 런타임에 실시간 획득** |
| **SonarQube 연동** <br> 빌드 블로킹 (차단) | JaCoCo가 뽑은 리포트(예: 구문 72%, 분기 65%)를 SonarQube 정적 분석 서버에 쏨. 관리자가 설정한 `Quality Gate (분기 최저선 80%)` 미달 시, Jenkins 빌드 즉각 `Failed(실패)` 처리 및 **Merge 원천 봉쇄** |

> 요약: 테스트 커버리지는 '목표(Goal)'가 아니라 '안전망(Safety Net)'이다. 100% 커버리지가 무조건 버그 0개를 보장하지 않는다. (블랙박스 기획 누락은 못 잡으니까). 하지만 30% 커버리지는 100% 버그 폭탄임을 보장한다.

## Ⅴ. 실무 적용 방안 및 결론

**적용 방안 3개:**
1. [SonarQube Quality Gate 기반 점진적 커버리지 강제화 튜닝] 초기 레거시 프로젝트(커버리지 10%)에 다짜고짜 80% 커버리지를 강제하면 팀 전체 빌드가 셧다운되므로, `New Code Coverage (신규 작성 코드)`에만 80% 허들을 엄격히 적용(Ratchet 기법)하여 기존 레거시는 놔두고 새로 짜는 코드부터 방어하는 연착륙 통제망 구축
2. [단위 테스트 중심의 롬복(Lombok)/DTO 제외 튜닝 패치] 커버리지를 계산할 때 아무 로직도 없는 `Getter/Setter`나 DTO 클래스까지 분모(전체 코드 수)에 들어가면 커버리지가 강제로 폭락함. JaCoCo 설정(`pom.xml`)에 `Excludes` 태그를 삽입하여 무의미한 보일러플레이트 코드를 계산에서 도려내어 순수 비즈니스 로직(Core)에만 집중 타격
3. [미션 크리티컬 모듈 대상 MC/DC 자동 도출 도구 결합] 의료 SW나 결제(정산) 코어 모듈 테스트 시, 테스터가 머리로 조합하기 불가능한 MC/DC 조합 세트를 `VectorCAST`나 `Reactis` 같은 상용/오픈소스 정형 분석(Formal Analysis) 봇에 위임. 알고리즘이 뱉어준 최소 조합(N+1개) TC만 선별 타격하여 리소스 최적화

**결론:**
- 기술사 판단: 테스트 커버리지 척도는 코드 내부를 현미경으로 쪼개어 분석하는 구조(White-box) 테스트의 정량적 신뢰 자본(Trust Capital)이다. 아무리 화려한 CI/CD 파이프라인 자동 배포망을 짰더라도, 그 안을 흐르는 코드의 분기(Branch) 커버리지가 80% 미만이라면 그것은 '버그 자동 배포 기계'로 전락한다. 커버리지는 소프트웨어의 건강을 증명하는 유일한 혈압 수치다.
- 향후 방향: 최근 현업 개발자들은 커버리지 80% 허들을 넘기 위해 아무 의미 없이 값만 넣고 `assert`를 안 하는 깡통 테스트(Cheat)를 양산하는 안티패턴에 빠졌다. 이를 막기 위해 컴파일된 코드를 기계가 강제로 돌연변이(고장)내서 테스트 코드가 그걸 잡아내는지 죽음의 레이스를 펼치는 **'뮤테이션 테스트(Mutation Testing)'** 패러다임으로 커버리지 품질의 2차 방어선이 구축되고 있다.
