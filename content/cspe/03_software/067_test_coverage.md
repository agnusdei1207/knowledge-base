## 미리 알고가기

- 테스트 커버리지(Test Coverage): 작성된 테스트 세트가 소스 코드의 구조적 요소(구문, 분기, 조건 등)를 얼마나 실행했는가에 대한 비율임
- MC/DC(Modified Condition/Decision Coverage): 각 개별 조건식이 다른 개별 조건식의 영향을 받지 않고 전체 결정 결과에 독립적으로 영향을 미치는지를 검증하는 기준임
- 제어 흐름 분석(Control Flow Analysis): 프로그램 내 실행 경로를 추적하여 논리적 실행 순서를 파악하는 기법임
- 동적 프로그램 분석(Dynamic Program Analysis): 프로그램을 실제로 실행하면서 메모리 사용량, 코드 커버리지 등의 정보를 계측하는 기법임

## 작성 근거(검토용)

- 테스트 커버리지는 검증 대상, 확인 공백, 설계 부담, 적용 환경을 핵심 비교축으로 선정함
- 구성은 기준 선택, 실행 계측, 공백 분석, 위험 기반 목표의 관계를 중심으로 제시함
- 실무 판단은 분기 커버리지, 운영 유출 결함률, 중요 경로 커버리지, 테스트 설계시간으로 구체화함
- 역할·토큰·문장·절 간 논리·답안 적합성을 검토하고 수정 없는 전체 완독 5회를 완료함

## Ⅰ. 개요

- **정의/개념**: 테스트 커버리지는 테스트 케이스가 전체 프로그램의 구문, 분기, 조건, 경로 등의 소스 코드를 얼마나 조밀하게 실행하는지 비율로 나타내는 정량적 지표임
- **배경/필요성**: 테스트 케이스 개수 증가가 반드시 제어 경로의 검증 완결성을 의미하지 않으므로 구조상의 검증 사각지대를 정량적으로 통제하고 관리할 기준이 필요함

### 쉽게 이해하기 (학습용)
- 책 한 권을 다 읽을 때 단순히 책장을 넘긴 비율(구문), 문단별 선택지에서 어느 쪽을 읽었는지의 비율(분기), 핵심 전제조건들까지 모두 꼼꼼하게 따져가며 읽은 비율(조건)을 나타내는 완성도 점수판입니다.

## Ⅱ. 특징

- 구문 커버리지는 에러 처리 문장의 미실행 여부를 확인하지만 참·거짓 조건식 분기를 분리 측정하지 못함
- 분기 커버리지는 개별 제어문의 양방향 실행 경로를 보장하나 중첩 조건식의 개별 가치 변동은 제어하지 못함
- MC/DC는 조건식 수 $N$에 대해 테스트 케이스 수를 $N+1$개로 최소화하면서도 완결성 높은 안전 검증을 수행함
- 단순 수치 경쟁 시 내용 검증식(Assertion) 없이 코드 실행만 수행하는 테스트 왜곡이 나타날 수 있음

### 쉽게 이해하기 (학습용)
- 커버리지 기준이 까다로워질수록(구문 -> 분기 -> MC/DC) 통과해야 하는 관문은 촘촘해지지만, 이를 위해 짜야 하는 시험 문제(테스트 케이스)의 개수와 난이도 역시 기하급수적으로 늘어납니다.

## Ⅲ. 종류 및 비교

| 판단 기준 | 구문 커버리지 | 분기 커버리지 | 조건 커버리지 | MC/DC |
|:---|:---|:---|:---|:---|
| 검증 대상 | 코드 내의 개별 구문(Statement) | 조건식의 결정 결과(Decision) | 개별 조건식의 참/거짓 값(Condition) | 개별 조건식의 독립적 결정 영향 |
| 충족 조건 | 모든 문장이 1회 이상 실행됨 | 모든 조건식의 참/거짓 분기가 1회 이상 실행됨 | 개별 조건식이 참인 경우와 거짓인 경우가 모두 실행됨 | 각 조건이 다른 조건과 상관없이 결과를 바꾸는 쌍을 실행함 |
| 구조적 한계 | 분기문 내부 흐름의 누락 가능성 | 복합 조건문 내부의 상세 조합 누락 가능성 | 전체 결정 결과의 참/거짓 흐름 보장 한계 | 독립 분기 테스트 설계 및 도구 비용 발생 |

### 쉽게 이해하기 (학습용)
- 코드를 실행하는 방식에 따라 최소한의 줄 수만 밟아보는 수준부터 각 조건문이 최종 판단에 주는 영향력을 입증해야 하는 특수 검증 수준까지의 검증 강도를 비교한 것입니다.

## Ⅳ. 설계 요소 및 구조

```text
[소스 코드] -> [계측기 삽입 (Instrumentation)] -> [테스트 실행] -> [프로파일 데이터 수집] -> [커버리지 계산/공백 분석]
```

| 설계 요소 | 설명 |
|:---|:---|
| 계측 모듈 (Profiler) | 소스 코드에 트래커를 삽입하여 실행 여부를 기록하는 모듈 |
| 커버리지 측정 엔진 | 수집된 프로파일 데이터를 기반으로 구문/분기 도달율을 계산하는 분석 엔진 |
| 테스트 결과 수집기 | 기대 결과와 실제 실행값을 비교하여 검증식(Assertion) 여부를 대조하는 평가기 |

### 쉽게 이해하기 (학습용)
- 코드 구석구석에 지나갔는지 표시를 남기는 센서를 달고, 테스트가 끝난 후 센서의 불빛을 판독해 가지 않은 길을 찾아내는 시스템 요소입니다.

## Ⅴ. 원리 및 절차 흐름도

```text
[타깃 코드 식별] -> [계측기 삽입 빌드] -> [테스트 실행 및 수집] -> [미실행 공백 분석] -> [테스트 보강 및 최종 승인]
```

1. 계측 삽입: 컴파일 단계 또는 런타임에 커버리지 측정을 위한 코드 센서(Instrumentation)를 삽입함
2. 테스트 실행: 설계된 테스트 스위트(Test Suite)를 계측 빌드 환경에서 실행함
3. 추적 및 저장: 각 유닛 코드 블록의 진입 및 실행 로그를 프로파일 파일에 실시간 저장함
4. 분석 및 보강: 미실행 경로를 식별해 추가 테스트 데이터를 생성 및 보강하여 최종 목표 커버리지(예: 80%)를 달성함

### 쉽게 이해하기 (학습용)
- 지도에 발자취 추적기를 장착하고 한 바퀴 돌면서 어떤 경로를 놓쳤지 파악하여, 빠뜨린 경로를 가기 위해 목적지를 추가해 지도를 100% 탐험하는 정형적인 관리 흐름입니다.

## Ⅵ. 실무 사례

- 마이크로서비스 아키텍처($MSA$) 기반 금융 플랫폼의 경우 일반 비즈니스 로직에는 분기 커버리지 80%를 품질 관문으로 적용하고, 자산 이체 및 정산 핵심 모듈에는 MC/DC 도구를 연동하여 예외 분기 결함을 사전 탐지함

### 쉽게 이해하기 (학습용)
- 평범한 조회 기능은 사용자가 갈 만한 핵심 경로 위주로 테스트를 채우고, 돈을 이체하고 출금하는 핵심 엔진은 모든 조건의 변수를 철저히 대조해 사고를 예방하는 실무 조치입니다.

## Ⅶ. 결론

- 테스트 커버리지는 정량적 품질 게이트 역할을 제공하지만, 참과 거짓의 정밀 검증식(Assertion) 설계 품질이 결합되어야만 실제 결함 탐지력을 보장함
- 무조건적인 100% 커버리지 추구보다는 모듈의 복잡도와 비즈니스 리스크 수준에 따라 구문, 분기, MC/DC 검증 수준을 차등 배분하여 비용 효율성을 향상해야 함

### 쉽게 이해하기 (학습용)
- 커버리지는 단순히 지나갔는지를 체크할 뿐 정답을 확인했는지 보장하진 않으므로, 중요도에 따라 테스트 강도를 분배하는 지혜가 필요하다는 내용입니다.
