## Ⅰ. 개요
- **정의**: 애플리케이션 외부 통신을 전담하는 프록시 컨테이너를 두어 연결 관리를 캡슐화하는 패턴임
- **배경/필요성**: 재시도·서킷브레이커·TLS 등 외부 통신 로직이 비즈니스 코드에 침투하면 복잡도가 높아짐
- **비유**: 외국 대사(Ambassador)가 본국을 대신하여 외교 통신을 전담하는 것과 같음

| 출제 의도 | 반드시 짚을 핵심 | 감점 회피 포인트 |
|:---|:---|:---|
| 외부 통신 관심사 분리 방법 | Sidecar와의 차이(방향성: 내부 vs 외부) | Ambassador는 아웃바운드 전용임을 명시 |

> 요약: 외부 서비스 통신의 재시도·보안·모니터링을 별도 프록시로 캡슐화하는 패턴임

## Ⅱ. 구성요소
```text
+-- Pod -------------------------+
|                                |
| [App] --localhost--> [Ambassador Proxy] ---> External Service
|                         |
|                    재시도/TLS/로깅
+--------------------------------+
```

| 구성요소 | 설명 | 비유 |
|:---|:---|:---|
| App Container | 비즈니스 로직만 수행하고 외부 통신은 localhost로 위임함 | 본국 정부 |
| Ambassador Proxy | 재시도·서킷브레이커·TLS 종단 등 외부 연결을 전담함 | 외교 대사 |
| External Service | App이 접근해야 하는 외부 API·DB·메시지 브로커 등임 | 외국 정부 |

> 요약: App이 localhost로 요청하면 Ambassador가 외부 통신의 복잡성을 처리함

## Ⅲ. 절차
```text
외부 통신 식별 --> Proxy 설정 --> Pod 내 배치 --> 모니터링 연동
```
- 1단계: 애플리케이션의 외부 서비스 호출 지점과 통신 요구사항을 식별함
- 2단계: 재시도 정책·서킷브레이커·TLS 인증서 등을 Ambassador Proxy에 설정함
- 3단계: App과 동일 Pod에 Ambassador를 배치하고 localhost 포트로 연결함
- 4단계: Proxy의 요청 로그·지연 메트릭을 모니터링 시스템에 연동함

> 요약: 통신 식별 → Proxy 설정 → Pod 배치 → 모니터링 연동의 4단계로 적용함

## Ⅳ. 문제점
- 지연 추가: 모든 외부 호출이 Proxy를 경유하여 왕복 지연이 발생함
- 단일 장애점: Ambassador 장애 시 해당 Pod의 외부 통신이 전면 중단됨
- 설정 복잡도: 외부 서비스별 재시도·타임아웃 정책을 개별 관리해야 함

> 요약: 지연·단일 장애점·설정 관리가 Ambassador 패턴의 주요 트레이드오프임

## Ⅴ. 개선방안
1. 단기: 커넥션 풀링과 HTTP/2 멀티플렉싱으로 Proxy 경유 지연을 최소화함
2. 중기: Ambassador의 Health Check와 자동 재시작을 구성하여 장애 복구 시간을 단축함
3. 장기: 서비스 메시 Control Plane에서 정책을 중앙 관리하여 설정 복잡도를 해소함

> 요약: 커넥션 최적화 → 자동 복구 → 중앙 정책 관리로 단계적 개선함

## Ⅵ. 전망
- 발전 방향: 서비스 메시의 Egress Gateway로 Ambassador 역할이 통합되는 추세임
- 기술사적 판단: 레거시 시스템의 외부 통신 현대화 시 유효한 중간 단계 패턴임
- 기술사 제언: Sidecar(304 참조)와 역할을 혼동하지 않도록 인바운드/아웃바운드 경계를 설계 시 명확히 구분할 것을 권고함
