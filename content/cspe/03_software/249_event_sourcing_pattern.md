# 📖 【암기용】 개념 완전 이해

> 목적: 이벤트 소싱 패턴을 처음 봐도 완전히 이해하게 만든다. 시험 답안 양식이 아니라, 이해를 위한 친절한 설명이다.

## 한눈에
- **개요**: 이벤트 소싱(Event Sourcing)은 **애플리케이션의 현재 상태를 직접 저장하지 않고, 상태를 변화시킨 모든 도메인 이벤트를 시간 순서대로 append-only로 저장**한 뒤, 필요할 때 이벤트를 처음부터 재생(replay)해 현재 상태를 계산하는 상태 저장 패턴이다.
- **왜 필요한가**: 일반 CRUD의 UPDATE는 이전 값을 덮어써서 "왜, 어떤 순서로 상태가 바뀌었는지"가 사라진다. 이벤트 소싱은 이 변경 이력 자체를 원본(source of truth)으로 보존해 감사·재처리·시점 복원을 가능하게 한다.
- **핵심 직관**: 계좌의 최종 잔액 한 줄만 저장하는 대신, 입금·출금 거래 내역을 모두 남겨 그 내역을 합산해 잔액을 계산하는 은행 거래 원장 방식이다.

## 핵심 용어 정리 (내부에 등장하는 것들)

| 용어 | 의미 | 비유 |
|:---|:---|:---|
| CRUD 상태 저장 (비교 대상) | 현재 상태만 테이블 row로 덮어쓰는 일반적 저장 방식 | 화이트보드에 최종 값만 적고 이전 값은 지움 |
| Command | 상태를 바꿔달라는 요청(아직 확정된 사실 아님) | "입금해주세요"라는 요청 |
| Domain Event | Command가 검증을 통과해 실제로 발생한 사실(과거형) | "입금되었음"이라는 확정된 사실 |
| Aggregate | 이벤트를 적용받는 도메인 단위(예: 주문, 계좌) | 하나의 통장 |
| Event Store | 이벤트를 순서대로 append만 하는 저장소 | 거래 내역이 적힌 원장 |
| Stream / Sequence | 하나의 Aggregate에 속한 이벤트 묶음과 그 순번 | 한 통장의 거래번호 1, 2, 3… |
| Projection | 이벤트를 읽어 조회하기 쉬운 읽기 모델로 변환하는 과정 | 거래내역을 합산해 "현재 잔액" 표를 만듦 |
| Snapshot | 특정 시점까지의 상태를 미리 계산해 저장 — 재생 시간 단축용 | 매달 1일 잔액을 별도로 적어둠 |
| Optimistic Locking | Aggregate 버전으로 동시 수정 충돌을 감지하는 기법 | 통장 페이지 번호로 "누가 먼저 썼는지" 확인 |

## 깊이 이해

### CRUD의 한계와 이벤트 소싱의 등장 배경
- 계좌 잔액을 `UPDATE account SET balance = 900`으로 저장하면, 직전 값이 1000이었는지 800이었는지, 어떤 거래로 900이 됐는지는 사라진다. 장애가 나면 "정상 상태로 복구"는 되어도 "무슨 일이 있었는지"는 재구성할 수 없다.
- 이벤트 소싱은 `Deposited(1000)`, `Withdrawn(100)`처럼 일어난 사실을 이벤트로 append하고, 현재 잔액이 필요하면 이 이벤트들을 순서대로 재생해 `0 + 1000 - 100 = 900`으로 계산한다. 잔액은 언제든 다시 만들 수 있는 산출물일 뿐, 이벤트가 원본이다.

### 작동 원리 — Command에서 Projection까지
1. Command(`WithdrawMoney(100)`)가 들어오면 Aggregate가 잔액이 충분한지 등 도메인 규칙을 검증한다.
2. 검증을 통과하면 `MoneyWithdrawn` 이벤트를 생성해 Event Store에 append한다. 이 시점부터 이 이벤트는 취소·수정이 불가능한 사실이 된다.
3. 별도의 Projection 프로세스가 새 이벤트를 읽어 조회용 읽기 모델(예: "현재 잔액" 테이블)을 갱신한다. 이 갱신은 비동기이므로 이벤트 저장 시점과 조회 모델 반영 시점 사이에 지연(eventual consistency)이 생긴다.

### Snapshot이 필요한 이유 — 수치로 보기
- 어떤 계좌 Aggregate에 이벤트가 100만 건 쌓였다면, 매번 잔액을 계산하기 위해 100만 건을 처음부터 재생하는 것은 비현실적이다.
- 그래서 1만 건마다 스냅샷(그 시점까지의 계산된 상태)을 저장해두고, 다음 조회 시에는 "가장 가까운 스냅샷 + 그 이후 이벤트만" 재생한다. 예를 들어 100만 번째 이벤트 시점의 상태가 필요하면 99만 건 스냅샷 + 이후 1만 건만 재생하면 되므로, 재생 시간을 200ms 이하로 유지할 수 있다.

### 동시 수정 충돌 — Optimistic Locking
- 두 개의 Command가 같은 Aggregate(같은 계좌)에 동시에 들어오면, 둘 다 "현재 버전 5"를 보고 이벤트를 append하려 할 수 있다. 이때 Aggregate 버전 번호를 함께 저장해, 두 번째 append 시도가 "버전이 5가 아니라 이미 6이 됐다"는 것을 감지하면 충돌로 거부하고 재시도시킨다.

### 비유와 흔한 오해
- **비유**: 회계의 분개 장부와 같다. 최종 잔액표(재무제표)는 매번 다시 만들 수 있는 산출물이고, 진짜 원본은 모든 거래를 기록한 분개장이다.
- **오해 1**: 이벤트 소싱은 메시지 큐(Kafka 등)와 다르다. 메시지 큐는 통과하는 파이프일 뿐이고, 이벤트 소싱의 Event Store는 그 자체가 **영구 저장되는 상태의 원본**이다.
- **오해 2**: 모든 도메인에 적합한 게 아니다. 단순 CRUD 게시판에 이벤트 소싱을 쓰면 재생·버전 관리 복잡도만 늘어난다. 감사 추적이나 "과거 특정 시점 상태"가 업무적으로 의미 있는 도메인(주문, 결제, 재고)에 적합하다.

## 연결 개념
- CQRS — 이벤트 소싱의 쓰기 모델(Event Store)과 읽기 모델(Projection)을 구조적으로 분리하는 패턴
- Outbox Pattern — 이벤트를 다른 서비스로 발행할 때 DB 트랜잭션과 발행을 묶는 방법
- Saga Pattern — 여러 Aggregate·서비스에 걸친 이벤트 기반 장기 트랜잭션 조정
- Optimistic Locking — Aggregate 버전으로 동시 수정을 감지하는 동시성 제어 기법

## Ⅰ. 개요 및 필요성

- 개요: 이벤트 소싱은 상태 변경 이벤트를 원본으로 저장하는 패턴이다.
- 배경: 현재 상태만 저장하는 CRUD는 감사 추적, 과거 상태 재구성, 이벤트 재처리에 한계가 있다.
- 필요성: 도메인 이력 보존 가치와 저장소·프로젝션·정합성 관리 비용을 비교해 적용 범위를 판단해야 한다.

---

## Ⅱ. 구조 및 구성요소

```text
Command -> Aggregate -> Domain Event -> Event Store
        -> Projection -> Read Model -> Query
```

| 구성요소 | 역할 | 특이사항 |
|:---|:---|:---|
| Command | 상태 변경 요청 | 검증 후 이벤트 생성 |
| Aggregate | 도메인 규칙과 버전 관리 | optimistic locking |
| Event Store | append-only 이벤트 저장소 | stream id, sequence |
| Projection | 읽기 모델 생성 | eventual consistency |

> 요약: 쓰기 경로는 이벤트를 저장하고 읽기 경로는 projection이 만든 모델을 조회한다.

---

## Ⅲ. 동작원리 및 흐름도

```text
명령 수신 -> 기존 이벤트 재생 -> 규칙 검증
-> 새 이벤트 append -> projection 갱신 -> 조회 모델 제공
```

| 단계 | 처리 내용 | 검증 기준 |
|:---:|:---|:---|
| 1 | aggregate stream 이벤트 로드 | sequence 누락 0건 |
| 2 | 이벤트 재생으로 현재 상태 계산 | snapshot 기준 재생 시간 200ms 이하 |
| 3 | 명령 검증 후 새 이벤트 append | optimistic lock conflict 처리 |
| 4 | projection이 read model 갱신 | projection lag 5초 이하 |

> 요약: 이벤트 소싱은 이벤트 재생으로 상태를 만들고 새 이벤트를 추가한 뒤 읽기 모델을 갱신한다.

## Ⅳ. 특징

| 구분 | CRUD 상태 저장 | Event Sourcing | 수치 판단 |
|:---|:---|:---|:---|
| 원본 | 현재 row | 변경 이벤트 로그 | append-only, sequence |
| 감사 | 별도 audit table | 이벤트 자체가 감사 기록 | 100% 변경 이력 |
| 조회 | 즉시 현재 상태 | projection 기반 조회 | lag 5초 이하 목표 |

> 요약: 이벤트 소싱은 감사와 재처리에 강하지만 projection 지연과 이벤트 버전 관리가 필요하다.

## Ⅴ. 심화 비교 및 적용 판단

| 비교 축 | 기존/대안 | 본 키워드 | 선택 기준 |
|:---|:---|:---|:---|
| 도메인 | 단순 CRUD | 이벤트 원장 | 감사·시점 복원이 핵심일 때 |
| 읽기 | 동일 DB 조회 | CQRS read model | 조회 패턴이 쓰기 모델과 다를 때 |
| 운영 | 스키마 변경 단순 | 이벤트 버전·upcaster 필요 | 장기 보존 이벤트가 있을 때 |

> 요약: 감사와 재처리 가치가 운영 복잡도보다 큰 도메인에 이벤트 소싱을 적용한다.

| 리스크 | 원인 | 대응 방안 | 확인 지표 |
|:---|:---|:---|:---|
| 재생 지연 | 이벤트 수 증가 | snapshot, stream partition | 재생 시간 200ms 이하 |
| 스키마 호환 | 이벤트 필드 변경 | versioning, upcaster | replay 실패 0건 |
| 정합성 지연 | projection 비동기 처리 | lag monitor, retry | projection lag 5초 이하 |

> 요약: 이벤트 소싱 운영 리스크는 재생 시간, 스키마 호환, projection 지연으로 관리한다.

| 점검 항목 | 목표 기준 | 측정 방법 |
|:---|:---|:---|
| 이벤트 저장 | sequence 누락 0건 | event store consistency check |
| 조회 지연 | projection lag 5초 이하 | consumer lag metric |
| 복원 | replay 성공률 100% | staging replay test |

> 요약: 이벤트 원장의 신뢰성과 projection 지연이 이벤트 소싱 성공 기준이다.

## Ⅵ. 실무 적용 및 결론

**적용 방안 3개 (필수 — 단계별 또는 항목별):**
1. 주문·결제처럼 감사와 보상 처리가 필요한 aggregate에만 이벤트 소싱을 적용하고 단순 마스터 데이터는 CRUD 유지
2. event store에 stream id, sequence, event version을 저장하고 10,000건 단위 snapshot으로 재생 시간을 200ms 이하로 관리
3. projection lag 5초 이하 모니터링과 replay test를 CI에 포함해 읽기 모델 복구 가능성을 검증

**결론 (2줄):**
- 기술사 판단: 이벤트 이력 자체가 업무 가치인 도메인에는 적합하나 단순 CRUD 업무에는 복잡도 대비 이득이 작다
- 향후 방향: CQRS, Outbox, Kafka 기반 로그 처리와 결합해 감사 가능하고 재처리 가능한 이벤트 중심 아키텍처로 확장된다
