# 📖 【암기용】 개념 완전 이해

## 한눈에
- **개요**: **이벤트 소싱(Event Sourcing) 패턴**은 데이터베이스에 현재 상태(최종 결괏값)만 저장하는 기존 방식과 달리, 데이터가 변경된 **모든 이력(이벤트)을 순서대로 저장**하고, 이를 재생(Replay)하여 현재 상태를 만들어내는 아키텍처 패턴이다.
- **왜 필요한가**: 모놀리식 DB에서 "현재 잔고 5만 원"만 저장하면, 어제 10만 원을 잃어버렸는지 5만 원을 벌었는지(문맥과 이력)를 알 수 없다. 마이크로서비스(MSA)에서 데이터 분산 환경의 정합성을 추적하고 복구하려면 "어떤 일들이 발생했는지"를 기록하는 원장이 필요하다.
- **핵심 직관**: 은행 통장(계좌 원장)을 떠올려라. 은행 DB는 내 통장 "현재 잔고 100만 원"이라는 숫자 하나만 저장하지 않는다. '+50만 원 입금', '-20만 원 출금' 같은 모든 **거래 내역(Event)**을 기록해 둔다. 잔고는 이 내역들을 처음부터 끝까지 더한 결과일 뿐이다.

## 핵심 용어 정리

| 용어/표기 | 의미 | 비유·예 |
|:---|:---|:---|
| 이벤트 스토어 (Event Store) | 모든 상태 변경 이벤트를 순차적으로 저장하는 추가 전용(Append-only) DB | 블랙박스 테이프, 은행 원장 장부 |
| 이벤트 (Event) | 도메인에서 이미 일어난 중요한 사실 (과거형 명명) | "OrderCreated", "ItemShipped" |
| 스냅샷 (Snapshot) | 이벤트를 1번부터 만 번까지 다 재생하기 느리므로, 중간에 한 번씩 미리 계산해둔 현재 상태 | "2026년 7월 1일 자정 기준 잔고: 50만 원" 메모 |
| 재생 (Replay) | 과거 이벤트들을 순서대로 쭉 다시 읽어 상태를 재조립하는 과정 | 체스 게임 기보를 보며 처음부터 말판을 다시 세팅하기 |

## 깊이 이해
- **배경·문제의식**: 기존 CRUD 방식 RDBMS 모델은 데이터(Row)를 덮어쓰기(UPDATE, DELETE) 하므로, 상태 변경의 히스토리와 의도가 삭제된다. 이는 복잡한 비즈니스 로직 분석이나 분산 시스템 장애 시 데이터 복원, 감사(Audit) 추적을 매우 어렵게 만든다.
- **작동 원리**:
  1. 클라이언트가 "장바구니 담기" 요청(Command)을 보낸다.
  2. 시스템은 장바구니 테이블을 `UPDATE`하지 않고, `ItemAddedToCart`라는 이벤트를 **이벤트 스토어에 추가(Insert)만** 한다. 데이터 덮어쓰기나 삭제는 절대 없다 (Append-Only).
  3. 장바구니 화면을 띄워야 할 때(조회), 이벤트 스토어에서 이 유저의 이벤트를 쫙 긁어와서 순서대로 계산(재생)해 현재 상태를 도출한다.
- **비유**: 수정테이프가 없는 볼펜으로 공책 필기하기. 잘못 적어도 지우지 않고 밑줄 긋고 "취소됨"이라고 적은 뒤 옆에 새로 쓴다. 결과적으로 펜 자국(이벤트)을 다 읽어보면 어떤 사고 흐름으로 정답에 도달했는지 100% 추적할 수 있다.
- **구체 예시**: 블록체인. 블록체인은 특정 계좌의 잔액을 갱신하는 것이 아니라, 코인이 이동한 모든 트랜잭션 블록(이벤트)을 꼬리에 꼬리를 무는 체인으로 추가만 한다.
- **흔한 오해·주의점**: 모든 이벤트를 덧붙이기만 하면 조회가 매우 느려진다(조회할 때마다 재생해야 하므로). 그래서 **CQRS(명령과 조회의 책임 분리)** 패턴과 거의 항상 한 세트로 묶여 다닌다. 이벤트는 명령 쪽에 쌓고, 조회용 DB(Read Model)에는 재생 결과를 따로 캐싱(Update)해둔다.

## 연결 개념
- 마이크로서비스 아키텍처 MSA (데이터 분산 처리에 핵심)
- CQRS (이벤트 소싱의 짝꿍 패턴 - 조회를 빠르게)
- Saga 패턴 — 분산 트랜잭션 (이벤트 기반 보상 트랜잭션 활용)

# 📝 【답안용】 시험 답안 템플릿

## 핵심 인사이트 (3줄 요약)

> 1. **본질**: 이벤트 소싱 패턴은 애플리케이션의 현재 상태를 DB에 덮어쓰지 않고, 상태를 변화시키는 모든 이력(이벤트)을 순차적으로 기록(Append-Only)하여 최종 상태를 도출하는 분산 데이터 아키텍처이다.
> 2. **가치**: 데이터의 변조가 불가능하고 이력 추적이 완벽히 보장되어(Audit Log 내재화), 마이크로서비스 환경에서 비동기 트랜잭션의 정합성 복원과 시스템 스케일아웃에 강력한 기반을 제공한다.
> 3. **판단 포인트**: 데이터 덮어쓰기 충돌이 없다는 장점이 크나, 조회 속도 저하(Replay 부하)를 유발하므로 필수적으로 CQRS 패턴 도입 및 스냅샷 캐싱 전략과 결합하여 약점을 극복해야 한다.

## 출제 의도 및 답안 포인트

| 출제 의도 | 반드시 짚을 핵심 | 감점 회피 포인트 |
|:---|:---|:---|
| 기존 CRUD 모델의 한계 인식 및 대안 제시 | 데이터 상태 업데이트(UPDATE) vs 이벤트 추가(Append-only) 패러다임 비교 | 이벤트 소싱을 단순한 애플리케이션 로깅(System Log) 수준으로 오해 서술 |
| 조회 성능 저하 리스크의 구조적 해결 역량 | CQRS 패턴 적용도, 스냅샷(Snapshot) 처리 기반 Replay 오버헤드 완화 | CQRS와의 연관성을 빼놓고 장점만 나열 (성능 병목 외면) |

> 요약: 상태 저장이 아닌 "변화 이력 누적"이라는 사상 전환을 명시하고, 필연적인 조회 성능 한계를 CQRS 설계도로 돌파하는 구조를 그려야 한다.

## Ⅰ. 개요 및 필요성

- 개요: 이벤트 소싱(Event Sourcing)은 데이터를 갱신(UPDATE)하는 대신, 애플리케이션 상태를 변경하는 일련의 도메인 이벤트를 시간 순서대로 이벤트 스토어에 추가 저장하는 패턴임
- 배경: MSA로 도메인이 쪼개지면서 분산 트랜잭션의 무결성 추적이 2PC(Two-Phase Commit)로는 한계에 다다름 (Lock 유발)
- 필요성: 시스템 장애 발생 시 과거 특정 시점으로의 롤백 및 감사(Audit) 추적이 필수적인 금융/커머스 도메인에 대한 신뢰성 아키텍처가 요구됨

---

## Ⅱ. 구조 및 구성요소

```text
[CQRS와 결합된 이벤트 소싱 아키텍처]
Command (쓰기 요청) -> [Command Model] -> Event Store (이벤트 Append) 
                                                  |
(Replay / Async Publish)                          v
Query (조회 요청) <--- [Query Read Model] <--- Event Bus (이벤트 전파) 
```

| 구성요소 | 역할 | 특이사항 |
|:---|:---|:---|
| Event Store | 도메인 이벤트가 불변(Immutable) 상태로 누적 저장되는 전용 DB | RDBMS 대신 Kafka, EventStoreDB 주로 활용 |
| Command Model | 비즈니스 검증 수행 후 신규 이벤트를 생성하여 Event Store에 발행 | 오직 생성(Insert) 명령만 수행 |
| Snapshot (스냅샷) | 거대해진 이벤트 이력을 매번 재생(Replay)하는 비용을 줄이기 위해 주기적 상태 저장 | 복구 시간 및 조회 성능 극대화 인프라 |
| Replay (재생) | 장애 발생 등 필요시 이벤트를 순차 재생하여 뷰 모델 상태 재구성 | 임의의 과거 특정 시점으로 Time Travel 복구 가능 |

> 요약: 쓰기 단에서는 덮어쓰기 없는 이벤트 스토어를 구성하고, 읽기 단에서는 이벤트를 수신하여 빠른 조회 뷰(Read Model)를 동기화한다.

---

## Ⅲ. 동작원리 및 흐름도

```text
클라이언트 요청 -> 비즈니스 검증 -> 이벤트 스토어 Append -> 브로커 전파 -> Read 뷰 업데이트
```

- 1단계 [의도 발생]: 클라이언트가 주문 취소 요청(`CancelOrderCommand`)을 시스템으로 발송함
- 2단계 [이벤트 저장]: 시스템은 기존 주문 상태를 업데이트하지 않고 `OrderCancelled` 이벤트를 생성하여 이벤트 스토어에 추가(Append-only)함
- 3단계 [전파 및 투영]: 저장된 이벤트가 Kafka 등의 메시지 버스를 통해 타 도메인이나 Read 전용 DB 모델(Projection)로 비동기 전파됨
- 4단계 [상태 재조립]: 클라이언트가 조회를 요청하면 Read Model 데이터를 반환하거나, 복구가 필요 시 이벤트 스토어를 Replay하여 메모리 객체 상태를 복원함

> 요약: 상태 변경은 오직 새로운 이벤트 레코드의 추가로만 일어나며, 이 추가된 이벤트가 읽기 뷰나 타 서비스의 트리거 역할을 동시 수행한다.

## Ⅳ. 특징

- 완벽한 감사(Audit) 트레일 보장: 데이터의 상태뿐 아니라 "왜" 그 상태가 되었는지 의도를 나타내는 이력이 모두 남으므로 법적 분쟁 및 추적에 압도적 강점
- 쓰기 성능 극대화(Lock-Free): DB 레벨의 동시성 락(Lock)이나 트랜잭션 경합을 유발하는 UPDATE/DELETE 연산 없이, 순차적 INSERT 연산만 존재하므로 쓰기 속도가 매우 빠름
- 비동기 최종 일관성 수용: 쓰기 모델(Event Store)과 읽기 모델(Read View) 사이의 동기화 지연(Delay) 발생에 따른 최종 일관성(Eventual Consistency) 모델 허용

> 요약: 쓰기 동시성 경합 해소와 완벽한 데이터 추적이 보장되는 대신, 일시적인 데이터 불일치(최종 일관성)를 사용자 경험(UX)으로 감내해야 한다.

## Ⅴ. 심화 비교 및 적용 판단

| 비교 축 | 전통적 상태 저장 (State-oriented / CRUD) | 이벤트 소싱 패턴 (Event-oriented) | 선택 기준 |
|:---|:---|:---|:---|
| 데이터 구조 | 현재 상태(최종 결괏값)의 단일 Row 유지 | 과거부터 누적된 이벤트 스트림 시퀀스 | 이력 추적 및 롤백 중요도 |
| 트랜잭션 성격 | 분산 환경에서 2PC 강한 일관성 필요 (락 발생) | Saga 패턴 결합한 최종 일관성 (비동기) | 비즈니스 성능 vs 정합성 즉각성 |
| 장애 디버깅 | 현재 에러 상태만 보이며 과거 유추 불가 | 이벤트를 재생하며 사고 유발 지점 완벽 탐지 | 운영 인프라 난이도 한계점 |

> 요약: 복잡한 락 관리가 불필요하고 감사 로깅이 필수인 MSA 기반 전자상거래(주문/결제) 등 핵심 도메인에는 이벤트 소싱을 적용하고, 단순 마스터 코드 관리에는 CRUD를 유지해야 한다.

**리스크·대응:**
- 재조립 부하(Replay Overhead): 1년 치 이벤트를 매번 처음부터 재생하면 메모리 오버헤드 및 응답 지연 파국 초래 → N번(예: 100회) 이벤트마다 스냅샷(Snapshot)을 생성하고 스냅샷 이후 이벤트만 재생 
- 시스템 마이그레이션(Schema Evolution): 도메인 정책이 바뀌어 이벤트의 JSON 구조(스키마)가 과거와 달라지면 과거 이벤트를 최신 코드가 재생하지 못하는 예외 발생 → Upcaster 패턴 적용 (과거 페이로드를 현재 스키마 폼으로 동적 매핑)

## Ⅵ. 실무 적용 및 결론

**적용 방안 3개:**
1. **CQRS 패턴과의 듀얼 아키텍처 필수 구성**: 명령 처리(Write)는 도메인 중심의 RDBMS나 NoSQL 이벤트 스토어로 처리하고, 읽기(Read)는 빠른 집계를 위해 Elasticsearch나 Redis로 투영(Projection)하는 물리적 데이터베이스 분리 설계
2. **Saga 보상 트랜잭션 기반 에러 복구 체계 연동**: 여러 MSA 컴포넌트에 걸쳐 이벤트가 전파되다 실패할 경우, 이전 이벤트를 상쇄하는 역방향 '보상 이벤트(예: 환불 승인)'를 다시 이벤트 스토어에 발행하여 롤백 구현
3. **타임 머신 디버깅 및 머신러닝 피처 분석 도구화**: 장애 시각의 버그 원인 분석을 위해 특정 시간대의 스냅샷까지만 시스템을 리플레이하여 디버깅하거나, 누적된 순차적 사용자 이력 데이터를 통째로 AI 학습 파이프라인(Data Lake)의 행동 분석 피처로 직송 처리

**결론:**
- 기술사 판단: 이벤트 소싱은 단순 게시판 등 로직이 얕은 시스템에는 복잡성 폭탄(Over-engineering)이 되나, 분산 환경의 비동기 연쇄 작용이 심한 Core 도메인 결제망에서는 데이터 무결성을 위한 최선의 선택임
- 향후 방향: 최근 Kafka 중심의 이벤트 스트리밍 플랫폼 도입이 표준화되면서, 이벤트 소싱 설계의 인프라 정합적 제약이 낮아지고 데이터 메시(Data Mesh) 사상과 융합되어 전사 데이터 흐름 뼈대로 발전 중임
