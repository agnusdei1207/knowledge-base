# 📖 【암기용】 개념 완전 이해

> 목적: 이벤트 소싱 패턴을 처음 봐도 완전히 이해하게 만든다. 시험 답안 양식이 아니라, 이해를 위한 친절한 설명이다.

## 한눈에
- **개요**: 현재 상태를 직접 저장하지 않고 상태 변경 이벤트를 순서대로 저장하는 패턴
- **왜 필요한가**: 주문 상태만 저장하면 왜 그렇게 되었는지 추적하기 어렵다. 이벤트 소싱은 `주문생성`, `결제승인`, `배송시작` 같은 사건을 원장처럼 남긴다.
- **핵심 직관**: 계좌 잔액만 저장하지 않고 입금·출금 거래 내역을 모두 보관해 잔액을 계산하는 방식이다.

## 깊이 이해
- **배경·문제의식**: 일반 CRUD는 현재 상태 조회가 단순하지만 감사, 재처리, 시간 여행 조회가 약하다. 이벤트 소싱은 append-only event store를 기준으로 상태를 재구성하므로 변경 이력이 사라지지 않는다.
- **작동 원리**: 명령(Command)이 들어오면 도메인 규칙을 검증하고 이벤트를 생성한다. 이벤트는 event store에 append되고, projection이 읽기 모델을 갱신한다.
- **비유**: 회계 장부의 분개와 같다. 최종 잔액보다 모든 거래 기록이 원본이며, 필요하면 특정 날짜의 잔액도 다시 계산할 수 있다.
- **구체 예시**: 주문 aggregate는 `OrderCreated`, `PaymentCaptured`, `OrderShipped` 이벤트를 순서대로 적용해 현재 상태를 만든다. 100만 이벤트마다 snapshot을 두어 재구성 시간을 줄인다.
- **흔한 오해·주의점**: 모든 시스템에 맞는 저장 방식이 아니다. 단순 CRUD에는 과도하며, 이벤트 버전 관리와 projection 지연을 감당해야 한다.

## 연결 개념
- CQRS — 쓰기 모델과 읽기 모델 분리
- Outbox Pattern — 이벤트 발행과 DB 트랜잭션 연결
- Saga Pattern — 여러 서비스의 장기 트랜잭션 조정

## 핵심 인사이트 (3줄 요약)

> 1. **본질**: Event Sourcing은 현재 상태 대신 도메인 이벤트를 append-only로 저장하고 상태를 이벤트 재생으로 계산하는 패턴이다.
> 2. **가치**: 감사 추적, 재처리, 시점 복원, 이벤트 기반 통합에 강하며 CQRS와 함께 읽기 모델을 분리한다.
> 3. **판단 포인트**: 이벤트 스키마 버전, projection 지연, snapshot, 중복 처리, GDPR 삭제 요구를 설계해야 한다.

## Ⅰ. 개요 및 필요성

이벤트 소싱은 상태 변경 이벤트를 원본 데이터로 저장하는 패턴이다. 현재 상태만 저장하는 CRUD는 감사 추적과 재처리에 한계가 있다. 기술사는 도메인 이력 보존 가치와 운영 복잡도를 비교해 적용 범위를 판단해야 한다.

---

## Ⅱ. 구조 및 구성요소

```text
Command -> Aggregate -> Domain Event -> Event Store
        -> Projection -> Read Model -> Query
```

| 구성요소 | 역할 | 특이사항 |
|:---|:---|:---|
| Command | 상태 변경 요청 | 검증 후 이벤트 생성 |
| Aggregate | 도메인 규칙과 버전 관리 | optimistic locking |
| Event Store | append-only 이벤트 저장소 | stream id, sequence |
| Projection | 읽기 모델 생성 | eventual consistency |

> 요약: 쓰기 경로는 이벤트를 저장하고 읽기 경로는 projection이 만든 모델을 조회한다.

---

## Ⅲ. 동작원리 및 흐름도

```text
명령 수신 -> 기존 이벤트 재생 -> 규칙 검증
-> 새 이벤트 append -> projection 갱신 -> 조회 모델 제공
```

| 단계 | 처리 내용 | 검증 기준 |
|:---:|:---|:---|
| 1 | aggregate stream 이벤트 로드 | sequence 누락 0건 |
| 2 | 이벤트 재생으로 현재 상태 계산 | snapshot 기준 재생 시간 200ms 이하 |
| 3 | 명령 검증 후 새 이벤트 append | optimistic lock conflict 처리 |
| 4 | projection이 read model 갱신 | projection lag 5초 이하 |

> 요약: 이벤트 소싱은 이벤트 재생으로 상태를 만들고 새 이벤트를 추가한 뒤 읽기 모델을 갱신한다.

---

## Ⅳ. 특징

| 구분 | CRUD 상태 저장 | Event Sourcing | 수치 판단 |
|:---|:---|:---|:---|
| 원본 | 현재 row | 변경 이벤트 로그 | append-only, sequence |
| 감사 | 별도 audit table | 이벤트 자체가 감사 기록 | 100% 변경 이력 |
| 조회 | 즉시 현재 상태 | projection 기반 조회 | lag 5초 이하 목표 |

> 요약: 이벤트 소싱은 감사와 재처리에 강하지만 projection 지연과 이벤트 버전 관리가 필요하다.

---

## Ⅴ. 심화 비교 및 적용 판단

| 비교 축 | 기존/대안 | 본 키워드 | 선택 기준 |
|:---|:---|:---|:---|
| 도메인 | 단순 CRUD | 이벤트 원장 | 감사·시점 복원이 핵심일 때 |
| 읽기 | 동일 DB 조회 | CQRS read model | 조회 패턴이 쓰기 모델과 다를 때 |
| 운영 | 스키마 변경 단순 | 이벤트 버전·upcaster 필요 | 장기 보존 이벤트가 있을 때 |

> 요약: 감사와 재처리 가치가 운영 복잡도보다 큰 도메인에 이벤트 소싱을 적용한다.

| 리스크 | 원인 | 대응 방안 | 확인 지표 |
|:---|:---|:---|:---|
| 재생 지연 | 이벤트 수 증가 | snapshot, stream partition | 재생 시간 200ms 이하 |
| 스키마 호환 | 이벤트 필드 변경 | versioning, upcaster | replay 실패 0건 |
| 정합성 지연 | projection 비동기 처리 | lag monitor, retry | projection lag 5초 이하 |

> 요약: 이벤트 소싱 운영 리스크는 재생 시간, 스키마 호환, projection 지연으로 관리한다.

| 점검 항목 | 목표 기준 | 측정 방법 |
|:---|:---|:---|
| 이벤트 저장 | sequence 누락 0건 | event store consistency check |
| 조회 지연 | projection lag 5초 이하 | consumer lag metric |
| 복원 | replay 성공률 100% | staging replay test |

> 요약: 이벤트 원장의 신뢰성과 projection 지연이 이벤트 소싱 성공 기준이다.

## Ⅵ. 실무 적용 및 결론

**적용 방안 3개 (필수 — 단계별 또는 항목별):**
1. 주문·결제처럼 감사와 보상 처리가 필요한 aggregate에만 이벤트 소싱을 적용하고 단순 마스터 데이터는 CRUD 유지
2. event store에 stream id, sequence, event version을 저장하고 10,000건 단위 snapshot으로 재생 시간을 200ms 이하로 관리
3. projection lag 5초 이하 모니터링과 replay test를 CI에 포함해 읽기 모델 복구 가능성을 검증

**결론 (2줄):**
- 기술사 판단: 이벤트 이력 자체가 업무 가치인 도메인에는 적합하나 단순 CRUD 업무에는 복잡도 대비 이득이 작다
- 향후 방향: CQRS, Outbox, Kafka 기반 로그 처리와 결합해 감사 가능하고 재처리 가능한 이벤트 중심 아키텍처로 확장된다
