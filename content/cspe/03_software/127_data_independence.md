# 📖 【암기용】 개념 완전 이해

> 목적: 데이터 독립성을 처음 봐도 완벽히 이해하게 만든다. 시험 답안 양식이 아니라, 이해를 위한 친절한 설명이다.

## 한눈에
- **개요**: 데이터 구조 변경이 응용 프로그램에 미치는 영향을 줄이는 DBMS 특성
- **왜 필요한가**: 인덱스 추가, 저장 파일 변경, 테이블 분해가 있을 때 애플리케이션을 매번 수정하면 운영 비용과 장애 위험이 커진다. 데이터 독립성은 스키마 계층을 분리해 변경 영향을 흡수한다.
- **핵심 직관**: 건물 내부 배관을 바꿔도 수도꼭지 사용법은 그대로 두는 설계임

## 깊이 이해
- **배경·문제의식**: 파일 처리 방식은 레코드 저장 위치와 프로그램 로직이 강하게 결합된다. DBMS는 외부·개념·내부 스키마를 분리하여 사용자가 보는 구조와 실제 저장 구조를 독립시킨다.
- **작동 원리**: 논리적 데이터 독립성은 개념 스키마 변경이 외부 스키마에 미치는 영향을 줄이고, 물리적 데이터 독립성은 내부 저장 구조 변경이 개념 스키마에 미치는 영향을 줄인다.
- **비유**: 식당 메뉴판은 유지하면서 주방 동선과 냉장고 위치를 바꾸거나, 메뉴 분류를 바꿔도 손님 주문 방식은 유지하는 구조임
- **구체 예시**: 고객 테이블에 `grade` 컬럼을 추가해도 기존 주문 조회 화면은 view로 동일 컬럼만 제공하면 수정 없이 동작함. 인덱스를 B+Tree에서 해시로 바꿔도 SQL은 유지됨.
- **흔한 오해·주의점**: 데이터 독립성은 변경 영향 감소이지 변경 영향 0을 보장하지 않는다. 컬럼 삭제, 의미 변경, 제약조건 변경은 API·쿼리·보고서 영향 분석이 필요하다.

## 연결 개념
- 3단계 스키마 - 외부·개념·내부 분리 구조
- View - 논리적 데이터 독립성 구현 수단
- 인덱스·파일 조직 - 물리적 데이터 독립성 대상

# 📝 【답안용】 시험 답안 템플릿

> 목적: 시험장에서 25분에 그대로 쓰는 답안 양식. 작성방식(추상표현 금지·수치·도식·문제유형 전환)을 엄격히 지킨다.
> 핵심: 데이터 독립성 답안은 논리/물리 구분과 3단계 스키마 매핑을 함께 써야 함.

## 핵심 인사이트 (3줄 요약)

> 1. **본질**: 데이터 독립성은 스키마 계층 분리로 데이터 구조 변경과 응용 프로그램 변경을 분리하는 DBMS 특성임.
> 2. **가치**: 테이블 구조·인덱스·저장 방식 변경 시 애플리케이션 수정 범위와 장애 가능성을 줄임.
> 3. **판단 포인트**: 논리적 독립성은 외부-개념 매핑, 물리적 독립성은 개념-내부 매핑으로 설명해야 함.

## 출제 의도 및 답안 포인트

| 출제 의도 | 반드시 짚을 핵심 | 감점 회피 포인트 |
|:---|:---|:---|
| DBMS 3단계 구조 이해 확인 | 외부·개념·내부 스키마와 매핑 | 데이터 무결성과 혼동하지 않음 |
| 논리/물리 구분 확인 | 컬럼·테이블 변경 vs 인덱스·파일 변경 | 두 독립성의 예시를 바꿔 쓰지 않음 |
| 실무 변경관리 판단 확인 | view, API, migration, 영향 분석 | 무중단 변경을 자동 보장한다고 쓰지 않음 |

> 요약: 데이터 독립성 문제는 스키마 계층별 변경 영향 차이를 정확히 구분하는 문제임.

---

## Ⅰ. 개요 및 필요성

- 개요: 데이터 독립성은 구조 변경과 응용 변경 분리 원칙이다.
- 배경: DB 시스템은 업무 변화에 따라 테이블·인덱스·저장 구조를 계속 바꾼다.
- 필요성: 스키마 계층 분리로 저장 구조 변경이 프로그램 수정과 장애로 전파되는 범위를 줄인다.

---

## Ⅱ. 구조 및 구성요소

```text
User View -> External Schema -> Conceptual Schema -> Internal Schema -> Storage
                 +-> External/Conceptual Mapping
                                      +-> Conceptual/Internal Mapping
```

| 구성요소 | 역할 | 특이사항 |
|:---|:---|:---|
| 외부 스키마 | 사용자·프로그램별 뷰 | view, API projection |
| 개념 스키마 | 전체 논리 데이터 구조 | entity, relationship, constraint |
| 내부 스키마 | 물리 저장 구조 | index, page, partition |
| 매핑 | 계층 간 변환 | 변경 영향 흡수 지점 |

> 요약: 데이터 독립성은 외부-개념-내부 스키마와 매핑 계층으로 변경 영향을 차단함.

---

## Ⅲ. 동작원리 및 흐름도

```text
Change Request -> Schema Layer Identify -> Mapping Adjust -> Program Impact Check -> Deploy
```

| 단계 | 처리 내용 | 검증 기준 |
|:---:|:---|:---|
| 1 | 변경 대상이 논리/물리 중 어디인지 분류 | schema diff |
| 2 | 외부·개념·내부 매핑 영향 분석 | dependent view count |
| 3 | view, synonym, migration으로 호환성 유지 | backward compatibility test |
| 4 | 인덱스·파티션 등 물리 구조 변경 | explain plan, lock time |
| 5 | 응용 영향과 데이터 품질 확인 | regression test pass |

> 요약: 데이터 독립성은 변경 계층을 먼저 식별하고 매핑 조정으로 프로그램 영향 범위를 줄이는 방식으로 동작함.

## Ⅳ. 특징

| 구분 | 논리적 데이터 독립성 | 물리적 데이터 독립성 | 판단 포인트 |
|:---|:---|:---|:---|
| 변경 대상 | 테이블, 컬럼, 관계 | 인덱스, 파일, 파티션 | 스키마 계층 분류 |
| 보호 대상 | 외부 뷰·응용 SQL | 개념 스키마·SQL 의미 | 매핑 유지 가능성 |
| 구현 수단 | view, API versioning | optimizer, storage engine | 테스트와 실행계획 검증 |

> 요약: 논리적 독립성은 사용자가 보는 구조, 물리적 독립성은 저장 방식 변경 영향을 제어함.

## Ⅴ. 심화 비교 및 적용 판단

| 비교 축 | 기존/대안 | 본 키워드 | 선택 기준 |
|:---|:---|:---|:---|
| 구조 | 파일 처리 결합 | DBMS 스키마 분리 | 프로그램-저장 구조 결합도 |
| 비용/성능 | 변경 때 프로그램 수정 | 매핑·뷰로 영향 흡수 | 변경 건당 수정 모듈 수 |
| 운영/위험 | 직접 테이블 변경 | 호환 뷰와 단계 배포 | rollback 가능성 |

> 요약: 데이터 독립성은 변경 빈도가 높고 응용 수가 많은 DB에서 변경 리스크를 낮추는 기준임.

| 리스크 | 원인 | 대응 방안 | 확인 지표 |
|:---|:---|:---|:---|
| 의미 변경 누락 | 컬럼 의미 재정의 | data contract, API version | contract test pass |
| 뷰 복잡도 증가 | 호환 계층 누적 | deprecation 일정, view 정리 | view dependency depth |
| 실행계획 변동 | 인덱스·파티션 변경 | plan baseline, 통계 갱신 | p95 query latency |

> 요약: 데이터 독립성 적용 시 의미 호환성, 뷰 누적, 실행계획 변동을 통제해야 함.

| 점검 항목 | 목표 기준 | 측정 방법 |
|:---|:---|:---|
| 변경 영향 | 수정 모듈 20% 이하 | impact analysis |
| 호환성 | 기존 API 테스트 100% 통과 | regression suite |
| 성능 | 주요 SQL p95 10% 이내 변동 | APM, explain diff |

> 요약: 데이터 독립성은 변경 영향 범위, 호환성 테스트, 실행계획 변화로 검증함.

---

## Ⅵ. 실무 적용 및 결론

**적용 방안 3개 (필수 — 단계별 또는 항목별):**
1. 외부 스키마는 view·API projection으로 고정하고, 내부 테이블 변경은 expand-contract migration으로 단계 배포함.
2. 인덱스·파티션 변경은 shadow index, plan baseline, lock timeout 5초 이하 기준으로 적용함.
3. 컬럼 삭제·의미 변경은 data contract와 deprecation 기간 30~90일을 두고 소비자 영향 분석을 수행함.

**결론 (2줄):**
- 기술사 판단: 응용 수가 많고 변경 빈도가 높을수록 데이터 독립성 설계가 DB 변경관리의 전제임.
- 향후 방향: 데이터 계약, 스키마 레지스트리, 자동 영향 분석이 논리적 데이터 독립성의 실무 수단으로 확대됨.
