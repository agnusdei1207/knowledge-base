## 미리 알고가기

- 물리적 독립성은 저장 방식이 바뀌어도 상위 논리 구조가 덜 흔들리게 하는 성질임
- 논리적 독립성은 테이블 구조가 바뀌어도 사용자 화면과 프로그램이 덜 흔들리게 하는 성질임
- 스키마는 데이터 구조를 정의한 설계도라고 보면 됨

## Ⅰ. 개요

- **정의/개념**: 데이터 독립성은 저장 구조나 논리 구조가 바뀌어도 사용자 화면과 응용 프로그램이 가능한 한 덜 영향을 받도록 계층을 나눠 설계하는 원리임
- **배경/필요성**: 데이터베이스는 성능 튜닝과 업무 변화 때문에 구조가 계속 바뀌므로 변경이 곧바로 프로그램 수정으로 번지지 않게 막을 장치가 필요함

## Ⅱ. 특징

- 변경 영향을 아래 계층에서 흡수하려는 구조적 원리임
- 물리적 독립성은 비교적 구현하기 쉽고 실무 효과가 큼
- 논리적 독립성은 더 어렵지만 서비스 변경 비용을 크게 줄임
- 독립성이 약하면 작은 튜닝도 여러 프로그램 수정으로 이어짐

## Ⅲ. 종류 및 비교

| 판단 기준 | 물리적 독립성 | 논리적 독립성 |
|:---|:---|:---|
| 바뀌는 대상 | 파일 구조, 인덱스, 저장 경로 | 테이블, 속성, 관계 구조 |
| 보호하려는 대상 | 개념 스키마와 질의 로직 | 외부 화면과 응용 프로그램 |
| 대표 예 | 인덱스 추가, 파일 재배치 | 컬럼 추가, 테이블 분리 |
| 구현 난도 | 상대적으로 낮음 | 상대적으로 높음 |

## Ⅳ. 구성요소 및 구조

| 구성요소 | 설명 |
|:---|:---|
| 외부 스키마 | 사용자와 프로그램이 보는 데이터 모습임 |
| 개념 스키마 | 조직 전체의 논리 구조를 정의함 |
| 내부 스키마 | 실제 저장 구조와 접근 경로를 다룸 |
| 매핑 규칙 | 계층 사이를 이어 변경 영향을 흡수함 |

```text
+-----------+      +-----------+      +-----------+
| 외부 스키마 | <--> | 개념 스키마 | <--> | 내부 스키마 |
+-----------+      +-----------+      +-----------+
```

## Ⅴ. 원리 및 절차 흐름도

```text
+-------------+     +-------------+     +-------------+     +-------------+
| 구조 변경 요구   | --> | 어느 계층 변화인지 판단 | --> | 매핑 조정      | --> | 상위 영향 확인  |
+-------------+     +-------------+     +-------------+     +-------------+
```

1. **구조 변경 요구**: 성능 튜닝이나 업무 변경이 발생함
2. **어느 계층 변화인지 판단**: 저장 방식 변화인지 논리 구조 변화인지 구분함
3. **매핑 조정**: 위 계층에 영향이 덜 가도록 연결을 손봄
4. **상위 영향 확인**: 화면과 프로그램 수정 범위를 점검함

## Ⅵ. 실무 적용 및 유의점

1. 인덱스 추가나 저장 재배치 같은 성능 튜닝은 응용 프로그램이 물리 구조에 직접 기대지 않게 해야 하므로 SQL 수정 건수와 응답 시간 변화를 함께 보며 물리적 독립성을 확인함
2. 스키마 진화가 잦은 서비스는 뷰와 데이터 계약을 같이 운영해 논리 변경을 흡수하고 화면 오류 건수와 배포 뒤 수정 범위로 논리적 독립성 수준을 점검함

## Ⅶ. 결론

데이터 독립성의 핵심은 구조 변경을 없애는 데 있지 않고 변경이 생겨도 영향 범위를 아래 계층에서 최대한 막아 내는 데 있음.
