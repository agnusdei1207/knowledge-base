# 📖 【암기용】 개념 완전 이해

## 한눈에
- **개요**: 데이터베이스 시스템에서 하위 레벨의 데이터 구조가 변경되더라도 상위 레벨의 응용 프로그램이나 사용자에게 영향을 주지 않는 성질이다.
- **왜 필요한가**: 과거에는 파일 시스템을 썼기 때문에, 파일에 필드 하나를 추가하거나 저장 위치를 바꾸면 그 파일을 읽는 모든 프로그램을 수정하고 재컴파일해야 했다. 이런 '유지보수 지옥'을 벗어나기 위해 데이터와 프로그램을 분리해야 했다.
- **핵심 직관**: 텔레비전(응용 프로그램)과 방송국(물리적 데이터)의 관계다. 방송국이 카메라를 바꾸거나 송신탑 위치를 옮겨도, 우리는 텔레비전 채널만 맞추면 똑같이 방송을 볼 수 있다. 중간에 표준 주파수(매핑)가 독립성을 보장하기 때문이다.

## 핵심 용어 정리

| 용어/표기 | 의미 | 비유·예 |
|:---|:---|:---|
| 논리적 데이터 독립성 | 논리적 구조(개념 스키마)가 변해도 응용 프로그램(외부 스키마)은 안 변함 | "부서" 테이블이 쪼개져도 원래 보던 "사원 정보" 뷰(View)는 그대로 |
| 물리적 데이터 독립성 | 물리적 저장 장치/구조가 변해도 논리적 구조(개념 스키마)는 안 변함 | 하드디스크를 SSD로 바꾸고 인덱스를 추가해도 SQL문은 안 바뀜 |
| 스키마 (Schema) | 데이터베이스의 뼈대(구조, 제약조건 등)를 정의한 것 | 건물의 설계도 |
| 매핑 (Mapping) | 서로 다른 스키마 간의 연결 고리 (사상) | 엘리베이터 층수 버튼(외부)과 실제 도르래 위치(물리)의 연결 |

## 깊이 이해
- **배경·문제의식**: 데이터 종속성(Data Dependency)은 최악의 비효율을 낳는다. 데이터를 다루는 규칙이 프로그램 코드 안에 하드코딩되어 있으면, 비즈니스 요건 변화나 성능 개선을 위해 DB를 손댈 때마다 시스템 전체가 마비된다.
- **작동 원리**: 데이터베이스 관리 시스템(DBMS)이 3단계 스키마(외부, 개념, 내부)라는 계층 구조를 도입하고, 각 계층 사이에 '매핑(사상)'을 둔다. 만약 물리적 저장 위치가 바뀌면 '개념-내부 매핑' 규칙만 수정하면 된다. 응용 프로그램은 '외부 스키마'만 바라보므로 아래쪽에서 무슨 일이 일어났는지 알 필요가 없다.
- **비유**: 식당에서 손님(응용 프로그램)은 메뉴판(외부 스키마)만 보고 주문한다. 주방장(DBMS)이 요리 레시피(개념 스키마)를 바꾸든, 식재료 보관 냉장고 위치(물리적 구조)를 바꾸든 손님은 똑같이 김치찌개를 먹는다.
- **구체 예시**: 
  - (물리적 독립성): DB 튜닝을 위해 A 테이블에 새로운 B-Tree 인덱스를 생성했다. 하지만 개발자가 작성한 `SELECT * FROM A` 코드는 전혀 수정할 필요가 없다.
  - (논리적 독립성): A 테이블을 A1과 A2로 분리했다. DB 관리자는 A1과 A2를 조인한 뷰(View)를 A라는 이름으로 만들어 두면, 기존 프로그램들은 여전히 A를 바라보며 정상 동작한다.
- **흔한 오해·주의점**: 논리적 독립성을 100% 보장하기란 현실적으로 어렵다. 테이블이 아예 삭제되거나 필수 컬럼이 사라지면 응용 프로그램도 영향을 받을 수밖에 없다. 반면 물리적 독립성은 인덱스, 파티셔닝 등을 통해 DBMS가 거의 완벽하게 보장한다.

## 연결 개념
- 3단계 스키마 (Three-Level Schema) — 데이터 독립성을 구현하는 구체적인 아키텍처
- 뷰 (View) — 논리적 데이터 독립성을 제공하는 대표적 수단
- 데이터 모델링 — 비즈니스 로직과 물리적 구현의 분리

# 📝 【답안용】 시험 답안 템플릿

## 핵심 인사이트 (3줄 요약)

> 1. **본질**: DBMS가 제공하는 핵심 가치로, 하위 스키마의 구조적 변경이 상위 스키마나 응용 프로그램에 영향을 미치지 않도록 차단하는 속성이다.
> 2. **가치**: 데이터 종속성을 제거하여 유지보수 비용을 획기적으로 낮추고, 응용 프로그램 중단 없는 데이터베이스 성능 튜닝 및 확장을 가능하게 한다.
> 3. **판단 포인트**: 이를 구현하는 아키텍처가 ANSI/SPARC 3단계 스키마이며, 외부/개념 사상(논리적 독립성)과 개념/내부 사상(물리적 독립성)의 원리를 정확히 구분해야 한다.

## 출제 의도 및 답안 포인트

| 출제 의도 | 반드시 짚을 핵심 | 감점 회피 포인트 |
|:---|:---|:---|
| 데이터베이스의 기본 원리 및 종속성 해결 역량 확인 | 논리적 독립성, 물리적 독립성, 3단계 스키마, 매핑(사상), 뷰(View) | 독립성 종류(논리/물리)의 개념 혼동 기술 |

> 요약: 데이터 독립성은 DBMS의 존재 이유이며, 3단계 스키마 아키텍처를 통한 계층 간 매핑(Mapping)으로 논리적/물리적 독립성이 달성됨을 명확히 제시한다.

---

## Ⅰ. 개요 및 필요성

- 개요: 하위 레벨의 데이터베이스 구조나 저장 방식이 변경되더라도 상위 응용 프로그램이나 사용자 뷰를 수정할 필요가 없는 DBMS의 특성
- 배경: 과거 파일 시스템(File System)은 데이터와 프로그램이 강하게 결합(Coupling)되어 있어, 데이터 구조 변경 시 프로그램 재컴파일이 필수적이었음
- 필요성: 잦은 비즈니스 요건 변화(논리적 구조 변경) 및 성능 최적화(물리적 구조 변경) 시 시스템 중단 및 소스 코드 수정 비용 최소화 필요

---

## Ⅱ. 구조 및 구성요소 (데이터 독립성 계층)

```text
응용 프로그램 / 사용자
        |  (논리적 데이터 독립성 보장 구역)
        V
[ 외부 스키마 (External Schema) ]
        |  <- 외부/개념 사상 (Mapping)
[ 개념 스키마 (Conceptual Schema) ]
        |  <- 개념/내부 사상 (Mapping)
        V
[ 내부 스키마 (Internal Schema) ]
  (물리적 데이터 독립성 보장 구역)
```

| 구성요소 | 역할 | 특이사항 |
|:---|:---|:---|
| 논리적 독립성 | 논리적 구조(개념 스키마) 변경 시 응용 프로그램 보호 | 뷰(View)를 통해 주로 구현됨 |
| 물리적 독립성 | 물리적 저장 장치/구조 변경 시 논리적 구조(개념 스키마) 보호 | 인덱스, 파티셔닝, 스토리지 변경 시 적용 |
| 사상 (Mapping) | 각 스키마 계층 간의 대응 관계를 정의하는 규칙 | 독립성 보장의 실질적 메커니즘 |

> 요약: 스키마를 3단계로 분리하고 그 사이에 사상(매핑) 규칙을 두어 변경의 여파를 위로 올라가지 못하게 차단한다.

---

## Ⅲ. 동작원리 및 흐름도

```text
물리적/논리적 변경 발생 -> 사상(Mapping) 규칙 갱신 -> 상위 계층 투명성 유지
```

- 1단계 [변경 요구 발생]: DB 관리자(DBA)가 성능 향상을 위해 테이블을 분할하거나 새로운 인덱스를 추가
- 2단계 [내부 구조 변경]: 개념 스키마(논리 구조)나 내부 스키마(물리 구조) 상의 정의(DDL)를 실제로 수정
- 3단계 [사상 규칙 갱신]: DBMS 내부에서 '개념/내부 사상' 또는 '외부/개념 사상' 매핑 정보를 변경된 구조에 맞게 업데이트
- 4단계 [투명성 유지]: 상위의 응용 프로그램은 기존에 호출하던 뷰(View)나 쿼리를 그대로 사용하며 변경을 인지하지 못함

> 요약: 구조 변경 시 상위 스키마를 건드리지 않고 중간의 연결 고리(매핑)만 업데이트하여 독립성을 유지한다.

---

## Ⅳ. 특징

- 투명성(Transparency) 제공: 개발자는 물리적인 디스크 트랙/섹터 단위나 파일 형식을 모르더라도 SQL 쿼리만으로 데이터 접근 가능
- 독립성의 비대칭성: 저장 매체 변경(물리적 독립성)은 응용 프로그램에 전혀 영향을 주지 않지만, 테이블 통합/분리(논리적 독립성)는 제약조건에 따라 100% 보장이 어려움 (응용 수정이 일부 필요할 수 있음)
- DBA의 유연성 확보: 시스템 가동 중에도 인덱스 생성, 데이터 마이그레이션 등을 자유롭게 수행할 수 있는 운영 유연성 제공

> 요약: 물리적 레벨에서는 완벽한 투명성을 제공하지만, 논리적 레벨에서는 비즈니스 로직에 따라 일부 종속성이 남을 수 있다.

## Ⅴ. 심화 비교 및 적용 판단

| 비교 축 | 논리적 데이터 독립성 | 물리적 데이터 독립성 | 선택/구분 기준 |
|:---|:---|:---|:---|
| 변경 대상 | 개념 스키마 (테이블 구조, 속성 추가/삭제) | 내부 스키마 (인덱스, 파티션, 해싱, 저장 장치) | 변경이 발생하는 스키마 계층 |
| 보호 대상 | 외부 스키마 (응용 프로그램, 사용자 뷰) | 개념 스키마 (논리적 데이터 모델) | 어떤 스키마 계층이 영향을 받지 않는가 |
| 구현 수단 | View(뷰), Synonym(동의어) 활용 | DBMS의 내장 스토리지 엔진 및 매핑 기능 | 실무에서 적용하는 기법 |

> 요약: 데이터 모델(엔티티)의 진화는 논리적 독립성으로 방어하고, 인프라나 성능 최적화는 물리적 독립성으로 방어한다.

**리스크·대응 (기본은 불릿):**
- 매핑 오버헤드: 다단계 매핑을 거치면서 쿼리 해석 및 변환 비용 증가로 성능 저하 → 뷰 병합(View Merging) 및 쿼리 옵티마이저 최적화 (지표: 파싱/컴파일 소요 시간)
- 뷰를 통한 갱신 한계: 여러 테이블이 조인된 복잡한 뷰를 통해 데이터를 삽입(INSERT)/수정(UPDATE) 시 원본 추적 불가 → 논리적 독립성 유지를 위해 INSTEAD OF 트리거 등 우회 방안 적용

## Ⅵ. 실무 적용 및 결론

**적용 방안 3개:**
1. MSA 기반 데이터 분리(논리적 독립성): 레거시 모놀리식 DB를 MSA로 쪼갤 때, 기존 API나 모듈이 깨지지 않도록 데이터베이스 뷰(View)를 활용해 점진적 마이그레이션(Strangler Fig 패턴) 수행
2. 무중단 성능 최적화(물리적 독립성): 서비스 트래픽 급증 시 응용 프로그램 코드 배포 없이, DBA가 백그라운드에서 테이블 파티셔닝(Partitioning) 및 인덱스 리빌딩 수행
3. ORM 프레임워크 활용: JPA, Hibernate 등 ORM을 사용하여 개발 코드(객체 지향)와 DBMS 구조(관계형) 간의 패러다임 불일치 및 종속성을 프레임워크 레벨에서 차단

**결론 (2줄):**
- 기술사 판단: 데이터 독립성은 IT 시스템 생명주기 비용을 결정하는 핵심 원칙이므로, 설계 초기 단계부터 뷰(View) 계층과 ORM을 적극 도입하여 결합도를 낮춰야 한다.
- 향후 방향: 클라우드 네이티브 환경에서는 스토리지와 컴퓨팅이 분리되고 폴리글랏(Polyglot) 데이터베이스가 도입되면서, 물리적 독립성은 클라우드 벤더가 완전히 추상화하는 방향으로 발전하고 있다.
