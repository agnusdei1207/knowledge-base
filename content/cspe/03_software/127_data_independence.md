# 📖 【암기용】 개념 완전 이해

> 목적: 데이터 독립성을 처음 봐도 완벽히 이해하게 만든다. 시험 답안 양식이 아니라, 이해를 위한 친절한 설명이다.

## 한눈에
- **개요**: 데이터 독립성은 DBMS를 외부·개념·내부 3단계로 분리해 데이터 구조 변경이 응용 프로그램에 미치는 영향을 줄이는 **3단계 스키마(ANSI/SPARC 아키텍처)** 의 핵심 목표다.
- **왜 필요한가**: 인덱스 추가, 저장 파일 변경, 테이블 컬럼 추가가 있을 때마다 애플리케이션 코드를 매번 고쳐야 한다면 운영 비용과 장애 위험이 계속 커진다. 데이터 독립성은 "구조가 바뀌는 지점"과 "그 구조를 쓰는 프로그램" 사이에 매핑 계층을 두어 변경의 파급을 그 계층에서 흡수한다.
- **핵심 직관**: 건물 내부 배관(내부 구조)을 바꿔도 수도꼭지 사용법(사용자 인터페이스)은 그대로 두는 설계와 같다.

## 핵심 용어 정리
| 용어 | 의미 | 비유 |
|:---|:---|:---|
| 3단계 스키마(ANSI/SPARC 아키텍처) | DBMS를 외부-개념-내부 3계층으로 나눠 데이터 독립성을 구현하는 표준 구조 — 이 개념 전체가 속하는 상위 틀 | 건물의 사용자층·설계도층·배관층 분리 |
| 외부 스키마(External Schema) | 사용자·응용 프로그램마다 필요한 부분만 보여주는 개별 뷰 | 손님마다 다르게 주는 개인 메뉴판 |
| 개념 스키마(Conceptual Schema) | 조직 전체가 공유하는 논리적 데이터 구조(전체 개체·관계·제약조건) | 식당 전체 재고 목록 |
| 내부 스키마(Internal Schema) | 실제 저장 방식(파일 구조, 인덱스, 페이지)을 정의한 물리적 구조 | 창고의 실제 진열 방식 |
| 스키마(Schema) vs 인스턴스(Instance) | 스키마=구조 정의(설계도), 인스턴스=특정 시점의 실제 데이터 값 | 설계도 vs 실제로 지어진 건물 |
| 외부/개념 매핑 | 외부 스키마와 개념 스키마를 연결하는 대응 규칙 — 논리적 데이터 독립성이 이 매핑에서 보장됨 | 개인 메뉴판과 전체 재고의 대응표 |
| 개념/내부 매핑 | 개념 스키마와 내부 스키마를 연결하는 대응 규칙 — 물리적 데이터 독립성이 이 매핑에서 보장됨 | 전체 재고와 실제 창고 위치의 대응표 |
| 논리적 데이터 독립성 | 개념 스키마가 바뀌어도 외부 스키마(응용 프로그램)는 영향받지 않는 성질 | 재고 목록 항목이 늘어도 손님 메뉴판은 그대로 |
| 물리적 데이터 독립성 | 내부 스키마(저장 방식)가 바뀌어도 개념 스키마는 영향받지 않는 성질 | 창고 진열을 바꿔도 재고 목록 숫자는 그대로 |
| View(뷰) | 외부 스키마를 구현하는 대표적 수단 — 저장된 질의로 만든 가상 테이블 | 미리 짜인 요약표 |

## 깊이 이해

### 배경 — 파일 처리 시스템의 문제 (구체 예)
- DBMS 이전의 파일 처리 시스템에서는 프로그램이 레코드의 물리적 위치(byte offset)에 직접 의존했다. 예를 들어 "고객 이름은 파일에서 120바이트 지점부터 20바이트"라고 프로그램에 하드코딩돼 있으면, 중간에 필드 하나만 추가돼도 이후 모든 필드의 오프셋이 밀려 그 파일을 읽는 모든 프로그램을 다시 고치고 재컴파일해야 했다.
- DBMS는 이 "프로그램이 저장 위치를 직접 아는" 강한 결합을 스키마 계층으로 끊어낸다 — 이것이 데이터 독립성이 풀려는 문제의 원점이다.

### 3단계 매핑이 실제로 동작하는 방식 (워크드 예제)
- 개념 스키마: `고객(고객ID, 이름, 등급, 가입일)` 테이블이 정의돼 있다.
- 외부 스키마 A(주문 화면 뷰): `CREATE VIEW 주문화면 AS SELECT 고객ID, 이름 FROM 고객` — `등급` 컬럼은 아예 보여주지 않는다.
- **논리적 변경과 그 흡수**: 이후 고객 테이블에 `연락처` 컬럼을 새로 추가해도, 외부 스키마 A의 `SELECT` 목록에는 `연락처`가 없으므로 주문 화면 프로그램은 코드 수정 없이 그대로 동작한다. 이것이 논리적 데이터 독립성이 실제로 작동하는 방식이다.
- **물리적 변경과 그 흡수**: 고객 테이블의 인덱스를 B+Tree에서 해시 인덱스로 바꿔도, `SELECT * FROM 고객 WHERE 고객ID=1001`이라는 SQL의 의미와 결과는 동일하다 — 옵티마이저가 내부적으로 접근 경로(인덱스 탐색 방식)만 바꾸기 때문이다. 이것이 물리적 데이터 독립성이다.

### 논리적 독립성이 물리적 독립성보다 구현이 더 어려운 이유
- 물리적 변경(인덱스 종류, 파일 조직, 파티션 분할)은 SQL의 **의미**를 바꾸지 않고 접근 경로만 바꾸므로, 옵티마이저 선에서 자동으로 흡수된다.
- 논리적 변경(컬럼 추가·삭제, 테이블 분해·병합)은 응용이 실제로 사용하는 데이터의 **구조와 의미**를 바꿀 수 있어, view나 API 버전 관리처럼 사람이 설계한 매핑 계층이 있어야만 영향을 막을 수 있다. 그래서 실무에서는 "컬럼 추가"는 대체로 안전하지만, "컬럼 삭제·의미 변경"은 항상 영향 분석이 필요하다는 비대칭이 생긴다.

### 독립성이 보장하지 못하는 것 (경계 조건)
- 데이터 독립성은 변경의 "영향 범위 축소"이지 "영향 0 보장"이 아니다. 예: 고객 테이블에서 `등급` 컬럼을 삭제하면, 그 컬럼을 참조하던 외부 스키마 뷰 자체가 깨진다 — 논리적 독립성으로도 이런 삭제·의미 변경까지는 못 막는다.
- 그래서 컬럼 삭제·제약조건 변경 같은 파괴적 변경은 `expand-contract` 방식(새 구조를 먼저 추가해 병행 운영한 뒤, 소비자 전환을 확인하고 나서 옛 구조를 제거)의 단계적 마이그레이션과 영향 분석이 반드시 필요하다.

### 비유 정리
- 식당 메뉴판(외부 스키마)은 그대로 두고 주방 동선이나 냉장고 위치(내부 스키마)를 바꾸는 것이 물리적 독립성이고, 재고 분류 체계(개념 스키마)를 바꿔도 손님이 받는 메뉴판 구성(외부 스키마)은 그대로 유지하는 것이 논리적 독립성이다. 다만 메뉴 자체(컬럼)를 없애면 그 메뉴를 시키던 손님 화면은 어차피 깨진다 — 이것이 독립성의 한계다.

## 연결 개념
- 3단계 스키마(ANSI/SPARC) — 데이터 독립성이 실현되는 상위 아키텍처.
- View — 논리적 데이터 독립성을 구현하는 대표 수단.
- 인덱스·파일 조직 — 물리적 데이터 독립성이 흡수하는 변경 대상.

# 📝 【답안용】 시험 답안 템플릿

> 목적: 시험장에서 25분에 그대로 쓰는 답안 양식. 작성방식(추상표현 금지·수치·도식·문제유형 전환)을 엄격히 지킨다.
> 핵심: 데이터 독립성 답안은 논리/물리 구분과 3단계 스키마 매핑을 함께 써야 함.

## 핵심 인사이트 (3줄 요약)

> 1. **본질**: 데이터 독립성은 스키마 계층 분리로 데이터 구조 변경과 응용 프로그램 변경을 분리하는 DBMS 특성임.
> 2. **가치**: 테이블 구조·인덱스·저장 방식 변경 시 애플리케이션 수정 범위와 장애 가능성을 줄임.
> 3. **판단 포인트**: 논리적 독립성은 외부-개념 매핑, 물리적 독립성은 개념-내부 매핑으로 설명해야 함.

## 출제 의도 및 답안 포인트

| 출제 의도 | 반드시 짚을 핵심 | 감점 회피 포인트 |
|:---|:---|:---|
| DBMS 3단계 구조 이해 확인 | 외부·개념·내부 스키마와 매핑 | 데이터 무결성과 혼동하지 않음 |
| 논리/물리 구분 확인 | 컬럼·테이블 변경 vs 인덱스·파일 변경 | 두 독립성의 예시를 바꿔 쓰지 않음 |
| 실무 변경관리 판단 확인 | view, API, migration, 영향 분석 | 무중단 변경을 자동 보장한다고 쓰지 않음 |

> 요약: 데이터 독립성 문제는 스키마 계층별 변경 영향 차이를 정확히 구분하는 문제임.

## Ⅰ. 개요 및 필요성

- 개요: 데이터 독립성은 구조 변경과 응용 변경 분리 원칙이다.
- 배경: DB 시스템은 업무 변화에 따라 테이블·인덱스·저장 구조를 계속 바꾼다.
- 필요성: 스키마 계층 분리로 저장 구조 변경이 프로그램 수정과 장애로 전파되는 범위를 줄인다.

---

## Ⅱ. 구조 및 구성요소

```text
User View -> External Schema -> Conceptual Schema -> Internal Schema -> Storage
                 +-> External/Conceptual Mapping
                                      +-> Conceptual/Internal Mapping
```

| 구성요소 | 역할 | 특이사항 |
|:---|:---|:---|
| 외부 스키마 | 사용자·프로그램별 뷰 | view, API projection |
| 개념 스키마 | 전체 논리 데이터 구조 | entity, relationship, constraint |
| 내부 스키마 | 물리 저장 구조 | index, page, partition |
| 매핑 | 계층 간 변환 | 변경 영향 흡수 지점 |

> 요약: 데이터 독립성은 외부-개념-내부 스키마와 매핑 계층으로 변경 영향을 차단함.

## Ⅲ. 동작원리 및 흐름도

```text
Change Request -> Schema Layer Identify -> Mapping Adjust -> Program Impact Check -> Deploy
```

| 단계 | 처리 내용 | 검증 기준 |
|:---:|:---|:---|
| 1 | 변경 대상이 논리/물리 중 어디인지 분류 | schema diff |
| 2 | 외부·개념·내부 매핑 영향 분석 | dependent view count |
| 3 | view, synonym, migration으로 호환성 유지 | backward compatibility test |
| 4 | 인덱스·파티션 등 물리 구조 변경 | explain plan, lock time |
| 5 | 응용 영향과 데이터 품질 확인 | regression test pass |

> 요약: 데이터 독립성은 변경 계층을 먼저 식별하고 매핑 조정으로 프로그램 영향 범위를 줄이는 방식으로 동작함.

## Ⅳ. 특징

| 구분 | 논리적 데이터 독립성 | 물리적 데이터 독립성 | 판단 포인트 |
|:---|:---|:---|:---|
| 변경 대상 | 테이블, 컬럼, 관계 | 인덱스, 파일, 파티션 | 스키마 계층 분류 |
| 보호 대상 | 외부 뷰·응용 SQL | 개념 스키마·SQL 의미 | 매핑 유지 가능성 |
| 구현 수단 | view, API versioning | optimizer, storage engine | 테스트와 실행계획 검증 |

> 요약: 논리적 독립성은 사용자가 보는 구조, 물리적 독립성은 저장 방식 변경 영향을 제어함.

## Ⅴ. 심화 비교 및 적용 판단

| 구분 | 기존/대안 | 본 키워드 | 선택 기준 |
|:---|:---|:---|:---|
| 구조 | 파일 처리 결합 | DBMS 스키마 분리 | 프로그램-저장 구조 결합도 |
| 비용/성능 | 변경 때 프로그램 수정 | 매핑·뷰로 영향 흡수 | 변경 건당 수정 모듈 수 |
| 운영/위험 | 직접 테이블 변경 | 호환 뷰와 단계 배포 | rollback 가능성 |

> 요약: 데이터 독립성은 변경 빈도가 높고 응용 수가 많은 DB에서 변경 리스크를 낮추는 기준임.

| 리스크 | 원인 | 대응 방안 | 확인 지표 |
|:---|:---|:---|:---|
| 의미 변경 누락 | 컬럼 의미 재정의 | data contract, API version | contract test pass |
| 뷰 복잡도 증가 | 호환 계층 누적 | deprecation 일정, view 정리 | view dependency depth |
| 실행계획 변동 | 인덱스·파티션 변경 | plan baseline, 통계 갱신 | p95 query latency |

> 요약: 데이터 독립성 적용 시 의미 호환성, 뷰 누적, 실행계획 변동을 통제해야 함.

| 점검 항목 | 목표 기준 | 측정 방법 |
|:---|:---|:---|
| 변경 영향 | 수정 모듈 20% 이하 | impact analysis |
| 호환성 | 기존 API 테스트 100% 통과 | regression suite |
| 성능 | 주요 SQL p95 10% 이내 변동 | APM, explain diff |

> 요약: 데이터 독립성은 변경 영향 범위, 호환성 테스트, 실행계획 변화로 검증함.

## Ⅵ. 실무 적용 및 결론

**적용 방안 3개 (필수 — 단계별 또는 항목별):**
1. 외부 스키마는 view·API projection으로 고정하고, 내부 테이블 변경은 expand-contract migration으로 단계 배포함.
2. 인덱스·파티션 변경은 shadow index, plan baseline, lock timeout 5초 이하 기준으로 적용함.
3. 컬럼 삭제·의미 변경은 data contract와 deprecation 기간 30~90일을 두고 소비자 영향 분석을 수행함.

**결론 (2줄):**
- 기술사 판단: 응용 수가 많고 변경 빈도가 높을수록 데이터 독립성 설계가 DB 변경관리의 전제임.
