## Ⅰ. 개요
- **정의**: 분산 시스템에서 일관성(C), 가용성(A), 분할 내성(P) 세 속성을 동시에 만족할 수 없다는 정리
- **배경/필요성**: 네트워크 분할은 분산 환경에서 불가피하므로, 분할 발생 시 C와 A 중 하나를 선택해야 하는 트레이드오프 인식이 필요함
- **비유**: 세 개의 공을 동시에 저글링할 수 있지만, 하나가 빠지면(분할) 나머지 둘 중 하나만 잡을 수 있는 것과 유사함

| 출제 의도 | 반드시 짚을 핵심 | 감점 회피 포인트 |
|:---|:---|:---|
| 분산 DB 설계 트레이드오프 이해 | P는 선택이 아닌 전제, C vs A 선택 | "3개 중 2개 선택" 단순화 지양 |

> 요약: 네트워크 분할(P) 전제 하에 일관성(C)과 가용성(A) 간 트레이드오프를 명시한 정리임

## Ⅱ. 구성요소
```text
         C (Consistency)
        / \
       /   \
      /     \
     A ------P (Partition Tolerance)
  (Availability)

  P 발생 시: CP 또는 AP 선택
```

| 구성요소 | 설명 | 비유 |
|:---|:---|:---|
| Consistency | 모든 노드가 동일 시점에 같은 데이터를 반환하는 속성 | 모든 지점 동일 재고 표시 |
| Availability | 장애 없는 노드는 항상 응답을 반환하는 속성 | 어느 창구든 응대 가능 |
| Partition Tolerance | 네트워크 분할 상황에서도 시스템이 동작을 계속하는 속성 | 전화선 끊겨도 영업 지속 |

> 요약: C, A, P 세 속성 중 P를 전제로 C-A 트레이드오프를 결정함

## Ⅲ. 절차
```text
시스템 요구 분석 --> P 전제 확인 --> C/A 우선순위 결정 --> DB 유형 선택
```
- 1단계: 서비스 요구사항에서 데이터 정합성과 응답 보장 중 우선순위를 식별함
- 2단계: 분산 환경에서 네트워크 분할(P)은 불가피한 전제임을 확인함
- 3단계: CP 선택 시 분할 중 일부 요청 거부, AP 선택 시 분할 중 불일치 허용을 결정함
- 4단계: CP 시스템(HBase, MongoDB 등) 또는 AP 시스템(Cassandra, DynamoDB 등)을 선택함

> 요약: P 전제 하에 서비스 요구에 맞는 C/A 우선순위로 분산 DB를 선택함

## Ⅳ. 문제점
- 이분법적 단순화: 실제 시스템은 C-A를 연속 스펙트럼으로 조절하나 CAP은 이를 표현하지 못함
- 정상 상태 미반영: 분할 미발생 시 지연(Latency)과 일관성 간 트레이드오프를 설명하지 못함(PACELC 128 참조)
- 설계 지침 부족: "CP 또는 AP"라는 분류만으로는 구체적 구현 수준 가이드를 제공하지 못함

> 요약: 이분법 단순화, 정상 상태 미반영, 구체적 설계 지침 부족이 한계임

## Ⅴ. 개선방안
1. 단기: 일관성 수준을 Quorum 기반으로 세분화(Strong, Eventual, Read-your-writes 등)
2. 중기: PACELC(128 참조) 모델로 정상 상태의 Latency-Consistency 트레이드오프까지 확장
3. 장기: 서비스 도메인별 일관성 SLA를 정의하고 Tunable Consistency 정책 적용

> 요약: 일관성 세분화, PACELC 확장, Tunable Consistency로 CAP 한계를 보완함

## Ⅵ. 전망
- 발전 방향: CAP을 기반으로 PACELC, Jepsen 테스트 등 분산 시스템 검증 체계 고도화
- 기술사적 판단: 분산 DB 설계의 출발점으로 개념 이해는 필수이나 실무에서는 확장 모델 병용 필요
- 기술사 제언: CAP 분류에 머무르지 않고 구체적 일관성 수준과 장애 시나리오를 설계에 반영할 필요
