# 📖 【암기용】 개념 완전 이해

## 한눈에
- **개요**: 플랫폼 엔지니어링에서 플랫폼 팀이 정의해 놓은 "최적의 표준 개발 경로 및 도구 세트"
- **왜 필요한가**: 개발자가 수많은 도구(AWS, K8s, GitHub Actions 등) 중에서 뭘 고를지 고민하는 시간(결정 피로)을 없애고, 보안·로깅 등 회사 표준을 자동으로 맞추기 위함이다.
- **핵심 직관**: 숲을 지날 때 이것저것 길을 개척하려면 힘들고 위험하지만, 관리자가 잘 닦아놓은 포장도로(Golden Path)를 따라가면 빠르고 안전하게 목적지에 도달하는 것.

## 핵심 용어 정리

| 용어/표기 | 의미 | 비유·예 |
|:---|:---|:---|
| 골든 패스 (Golden Path) | 회사가 권장하고 100% 지원하는 개발 템플릿 경로 | 잘 포장된 고속도로 |
| 포장된 길 (Paved Road) | 골든 패스와 동일한 의미로 혼용됨 (Netflix 등에서 사용) | 닦아놓은 길 |
| 섀도우 IT (Shadow IT) | 권장 경로를 벗어나 개발자 임의로 도입한 비표준 기술 | 샛길로 빠지기 |

## 깊이 이해
- **배경·문제의식**: 개발자 자율성을 강조했더니, A팀은 AWS/EKS/Jenkins, B팀은 GCP/GKE/ArgoCD 등 사내 기술 스택이 파편화되었다. 이로 인해 부서 이동 시 적응이 힘들고, 전사적 보안 패치 적용이 불가능해짐.
- **작동 원리**: 
  - 플랫폼 팀은 사내 표준(예: Java Spring + K8s 배포 + Datadog 모니터링)을 템플릿화함.
  - 개발자가 IDP 포털에서 골든 패스를 선택하면, 보안 규칙과 사내 표준이 내장된 뼈대 코드가 즉시 생성됨.
  - **중요**: 골든 패스는 '강제'가 아니라 '권장'이다. 이 길로 가면 100% 플랫폼 팀의 지원(자동화, 문제 해결)을 받지만, 굳이 다른 길(비표준)을 간다면 본인이 모든 책임과 수고를 감수해야 한다.
- **비유**: 고속도로(골든 패스)를 타면 톨게이트비 없이 시속 100km로 달릴 수 있다. 국도(비표준)로 가도 안 말리지만, 고장나면 본인이 알아서 고쳐야 한다. 결국 다들 고속도로를 탄다.
- **구체 예시**: 신규 프로젝트 생성 시 "Spring Boot 백엔드 서비스 (표준)" 골든 패스를 클릭하면, GitHub Repo 생성, CI/CD 파이프라인 구성, Vault 시크릿 연동, K8s 매니페스트 생성이 5분 안에 완료된다.
- **흔한 오해·주의점**: 강압적인 탑다운(Top-down) 정책으로 "이것만 써!"라고 강제하는 것이 아니다. "이걸 쓰면 너무 편해서 안 쓸 이유가 없게" 만드는 **넛지(Nudge)** 전략이다.

## 연결 개념
- **플랫폼 엔지니어링 (IDP)**: 골든 패스를 제공하는 그릇이자 포털
- **인지 부하 (Cognitive Load)**: 골든 패스를 통해 해결하고자 하는 핵심 문제

# 📝 【답안용】 시험 답안 템플릿

## 핵심 인사이트 (3줄 요약)

> 1. **본질**: 골든 패스(Golden Path)는 내부 개발자 플랫폼(IDP)에서 생산성과 품질을 보장하기 위해 사전 정의된 표준화된 개발 템플릿 및 가이드 경로이다.
> 2. **가치**: 인프라 파편화와 결정 피로를 방지하고, 보안·로깅 등 전사 표준을 내장하여 안전하고 빠른 서비스 출시(Time-to-Market)를 지원한다.
> 3. **판단 포인트**: 골든 패스는 강력한 강제(Enforcement)가 아니라, 이 경로를 선택할 때 가장 쉽고 편하도록 설계된 넛지(Nudge) 기반의 자발적 표준화 전략이어야 한다.

## 출제 의도 및 답안 포인트

| 출제 의도 | 반드시 짚을 핵심 | 감점 회피 포인트 |
|:---|:---|:---|
| IDP 내에서 골든 패스의 역할 이해 | 인지 부하 감소, 기본 내장(Default-in)된 보안/로깅 | 골든 패스를 단순 사내 규정 문서로 설명 |
| 골든 패스 적용의 철학 | 강제가 아닌 권장(포장도로), 이탈 허용 유연성 | 강제적 기술 통제로 단정 |

> 요약: 골든 패스는 개발자의 자율성을 존중하면서도, 압도적인 편의성을 제공하여 자발적 사내 표준화를 유도하는 핵심 기제이다.

---

## Ⅰ. 개요 및 필요성

- 개요: 골든 패스(Golden Path, 또는 Paved Road)는 플랫폼 엔지니어링 환경에서 개발자가 빠르고 안전하게 개발할 수 있도록 사전에 구성된 권장 기술 스택 및 파이프라인 경로임
- 배경: 자율성에 기반한 DevOps 확산이 기술 파편화(Fragmentation)와 유지보수 비용 급증을 초래함
- 필요성: 보안 설정, 규정 준수, 모니터링 연동 등 비기능적 요구사항을 템플릿에 기본 내장(Built-in)하여 개발자 인지 부하 경감 및 전사 표준화 달성 필요

---

## Ⅱ. 구조 및 구성요소

```text
Developer Request -> IDP Portal -> Golden Path Template Selection
                                        | (Built-in Standards)
                            +-------------------------------+
                            | - Repo & CI/CD Pipeline       |
                            | - Security & RBAC             |
                            | - Observability (Log/Metric)  |
                            +-------------------------------+
                                        | Provisioning
                             Ready-to-Code Environment
```

| 구성요소 | 역할 | 특이사항 |
|:---|:---|:---|
| 템플릿(Scaffolding) 카탈로그 | 뼈대 코드(Boilerplate) 및 환경 설정 사전 정의 | Spring, Node.js 등 주력 스택별 |
| Built-in Security (보안 내장) | SAST, DAST, 컨테이너 스캔 파이프라인 기본 탑재 | Shift-Left 자동 실현 |
| Built-in Observability | 로깅, 트레이싱(OpenTelemetry), APM 에이전트 기본 연동 | 가시성 표준화 |
| 자동 프로비저닝 엔진 | 선택한 템플릿을 실제 인프라(IaC) 코드로 변환 배포 | Terraform, Crossplane |

> 요약: 골든 패스는 애플리케이션 뼈대와 보안·관측성 파이프라인을 템플릿에 하나로 묶어 즉시 실행 가능한 환경을 제공한다.

---

## Ⅲ. 동작원리 및 흐름도

```text
골든 패스 카탈로그 조회 -> 템플릿 파라미터 입력 -> 인프라/파이프라인 생성 -> 서비스 개발
```

- 1단계 [카탈로그 조회]: 개발자가 IDP(예: Backstage)에서 신규 서비스를 위한 'Spring Boot 마이크로서비스 골든 패스' 검색
- 2단계 [파라미터 입력]: 서비스명, DB 종류(예: Redis 추가 유무), 배포 클러스터 등 기본 설정 입력
- 3단계 [자동 프로비저닝]: 플랫폼이 GitHub Repo 생성, GitHub Actions 템플릿 복사, K8s Manifest 작성 자동화
- 4단계 [개발 전환]: 개발자는 인프라 고민 없이 즉시 비즈니스 로직 작성 및 커밋 시작

> 요약: 카탈로그 선택과 최소 입력만으로 사내 표준 인프라가 배포되어 Day 0 환경 세팅 시간이 수 주에서 수 분으로 단축된다.

---

## Ⅳ. 특징

- 생산성 가속(Day 0 셋업): 환경 구축에 소요되는 리드 타임을 극적으로 단축시켜 온보딩 및 신규 서비스 런칭 가속화
- 넛지(Nudge) 기반 표준화: 강압적 통제가 아닌, 너무 편해서 쓸 수밖에 없는 경험을 제공하여 비표준 섀도우 IT 자발적 축소
- Shift-Left 보안 자동화: 보안 정책(권한 통제, 취약점 스캔)이 템플릿에 내장되어 개발 초기부터 보안 내재화(Security by Default)

---

## Ⅴ. 심화 비교 및 적용 판단

| 비교 축 | 자율 선택형 (DIY 스택) | 골든 패스 (Paved Road) | 선택 기준 |
|:---|:---|:---|:---|
| 기술 선택 | 팀별 완전 자율 (다양성 높음) | 사내 검증된 권장 스택 제공 | 도메인 특수성 유무 |
| 유지보수 주체 | 개별 제품 개발팀 (인지 부하↑) | 플랫폼 엔지니어링 팀 지원 보장 | 운영 리소스 |
| 보안·컴플라이언스 | 팀별로 규정 준수 직접 구현 | 템플릿 내장으로 자동 준수 | 규제 민감도 |

> 요약: 특수한 목적이 없는 대다수 범용 서비스는 플랫폼 팀의 지원을 받는 골든 패스를 선택하는 것이 경제적이다.

**리스크·대응 (기본은 불릿):**
- 골든 패스 고착화(Innovation 억제): 새로운 신기술(예: 신규 언어) 도입을 막아 혁신 저해 → 이탈을 허용하되, 비표준 스택의 책임은 개발팀에 부여 (유연성 확보)
- 템플릿 노후화: 골든 패스 템플릿이 구버전 라이브러리에 머물러 보안 취약점 발생 → 플랫폼 팀 내 전담 인력 배정 및 정기적인 템플릿 버전업 프로세스 확립 (지표: 최신 템플릿 반영률)
- 과도한 추상화: 디버깅 시 블랙박스화 발생 → 골든 패스 생성물(IaC 코드 등)을 개발팀 저장소에 투명하게 노출하여 수정 가능하게 허용

---

## Ⅵ. 실무 적용 및 결론

**적용 방안 3개:**
1. 핵심 스택 선별: 전사 프로젝트의 80%를 커버할 수 있는 핵심 기술 스택(예: Java/Spring + React)을 골든 패스 v1.0으로 우선 정의
2. 템플릿 엔진 도입: 뼈대 코드를 자동화하기 위해 소프트웨어 템플릿 툴(Backstage Software Templates) 도입
3. 커뮤니티 기반 진화: 개발팀의 비표준 스택 중 성공 사례가 많아지면 이를 플랫폼 팀이 리뷰 후 신규 골든 패스로 승격시킴

**결론 (2줄):**
- 기술사 판단: 골든 패스는 단순한 코드 템플릿이 아니라 조직의 거버넌스, 보안, 베스트 프랙티스를 기술적으로 강제력 없이 내재화하는 훌륭한 추상화 전략이다
- 향후 방향: 정적인 템플릿을 넘어, 환경 변화와 보안 권고안을 지속적으로 기존 골든 패스 생성물에 자동 동기화(Drift Management)하는 방향으로 발전해야 한다
