# 📖 【암기용】 개념 완전 이해

## 한눈에
- **개요**: 시스템에 올라간 다중 프로그래밍 정도(프로세스 수)가 과도하여, CPU가 실제 연산을 하는 시간보다 페이지 교체(Page Fault) 처리로 디스크 I/O를 기다리는 시간이 더 많아져 시스템 성능이 급격히 붕괴하는 현상.
- **왜 필요한가**: 가상 메모리 시스템에서는 메모리(RAM)보다 더 큰 프로그램을 실행할 수 있지만, 물리 메모리 한계치를 넘으면 끊임없이 디스크와 메모리 간 스왑(Swap)이 일어나 시스템 전체가 멈춘 듯한 상태가 된다. 이를 예방하고 적정 동시 실행 수준을 유지해야 한다.
- **핵심 직관**: 좁은 책상에 20과목의 전공 서적을 올려놓고 공부하는 상황. A과목을 보려니 공간이 없어 B과목을 바닥에 내리고 A를 올린다. 다음 순간 B가 필요해 A를 내리고 B를 올린다. 결국 '책을 올리고 내리는 작업(디스크 I/O)'만 하느라 실제 '공부(CPU 연산)'는 1분도 못하는 상태다.

## 핵심 용어 정리

| 용어/표기 | 의미 | 비유·예 |
|:---|:---|:---|
| **스레싱 (Thrashing)** | 실제 CPU 사용률보다 페이지 교체로 인한 I/O 대기 시간이 압도적으로 커진 상태 | "일은 안 하고 책상 정리만 계속하는 상태" |
| **다중 프로그래밍 정도 (MPD, Degree of Multiprogramming)** | 메모리에 동시에 적재되어 실행 중인 프로세스의 개수 | "책상 위에 펼쳐둔 책의 개수" |
| **페이지 부재 (Page Fault)** | CPU가 접근하려는 페이지가 물리 메모리에 없어 디스크(Swap)에서 가져와야 하는 현상 | "필요한 책이 책상에 없어 서고에 다녀오는 상황" |
| **지역성 (Locality)** | 프로세스가 특정 시간, 특정 영역의 메모리만 집중적으로 참조하는 특성 | "공부할 때 현재 단원 주변만 집중적으로 보는 것" |

## 깊이 이해
- **배경·문제의식**: OS는 CPU 이용률이 떨어지면 "일할 프로세스가 부족하구나!" 판단하고 MPD를 더 높인다(새 프로세스 추가). 하지만 CPU 이용률이 떨어진 진짜 이유가 '메모리 부족으로 인한 잦은 페이지 교체 대기'라면, 새 프로세스의 추가는 메모리 부족을 악화시켜 페이지 부재율을 기하급수적으로 폭증시킨다. 악순환의 고리다.
- **작동 원리**:
  1. 메모리에 프로세스가 많아짐 $ightarrow$ 프로세스당 할당받는 물리 프레임 수 감소.
  2. 프레임 수가 프로세스 실행에 필요한 최소 '워킹 셋(Working Set)'보다 적어짐 $ightarrow$ 잦은 페이지 부재 발생.
  3. 디스크 I/O 대기(Sleep) 증가 $ightarrow$ CPU 이용률 하락.
  4. OS 스케줄러 오판: "CPU가 노네? 프로세스 더 투입!" $ightarrow$ 스레싱 진입 및 시스템 마비.
- **구체 예시**: 물리 메모리가 4GB인데, 각각 2GB 메모리를 активно 쓰는 크롬 브라우저 3개를 띄웠다고 가정하자. 윈도우는 부족한 메모리를 하드 디스크(Pagefile)로 빼내고 다시 올리는 작업(Page in/out)을 반복하며 하드 디스크 사용률이 100%를 찍고 마우스 커서마저 끊기는 스레싱 상태가 된다.
- **흔한 오해·주의점**: 스레싱은 단순한 메모리 누수(Memory Leak)와 다르다. 메모리 누수는 공간이 좀먹어가는 '원인' 중 하나일 뿐, 스레싱 자체는 디스크 I/O 병목으로 인해 CPU가 일을 못하는 '현상'을 지칭한다.

# 📝 【답안용】 시험 답안 템플릿

## 핵심 인사이트 (3줄 요약)

> 1. **본질**: 스레싱은 프로세스에 할당된 물리 메모리가 부족하여, CPU 연산보다 페이지 교체(Page Fault)를 위한 디스크 I/O 오버헤드가 더 커지는 성능 붕괴 현상이다.
> 2. **가치**: 스레싱 제어는 다중 프로그래밍 정도(MPD)를 최적치로 유지하여 시스템의 처리량(Throughput)과 CPU 이용률을 동시에 극대화하는 가상 메모리 관리의 핵심이다.
> 3. **판단 포인트**: OS의 MPD 제어 오판 메커니즘을 끊기 위해 지역성(Locality) 기반의 워킹 셋(Working Set) 모델이나 페이지 부재 빈도(PFF) 기반 프레임 할당 정책을 적용해야 한다.

## 출제 의도 및 답안 포인트

| 출제 의도 | 반드시 짚을 핵심 | 감점 회피 포인트 |
|:---|:---|:---|
| 가상 메모리 성능 저하 메커니즘과 OS 스케줄링 간의 악순환 파악 | CPU 이용률 하락 $ightarrow$ MPD 증가 $ightarrow$ Page Fault 폭증의 악순환 구조 | 단순 메모리 부족 문제로만 치부하여 악순환 구조 누락 |
| 스레싱 해결 기법과 프레임 할당 전략 제시 역량 | 지역성(Locality), 워킹 셋(Working Set), 페이지 부재 빈도(PFF) 조절 | 스레싱 발생 시 단순히 'RAM 증설' 등 H/W적 대응만 나열 |

> 요약: 스레싱은 OS 스케줄러의 오판으로 발생하는 악순환 구조이므로, 지역성 원리에 기반한 동적 프레임 할당(워킹 셋, PFF) 기법으로 대응해야 함을 논리적으로 서술해야 한다.

## Ⅰ. 개요 및 필요성

- 개요: 스레싱은 다중 프로그래밍 환경에서 과도한 프로세스 적재로 인하여, CPU 실행 시간보다 페이지 교체 작업(I/O) 시간이 압도적으로 커지는 시스템 성능 저하 현상
- 배경: 가상 메모리 시스템은 프로세스당 최소 필요한 물리 프레임(Working Set)을 보장하지 못할 경우 잦은 페이지 부재(Page Fault)를 유발
- 필요성: 시스템 마비(Hang)를 방지하고 CPU 이용률을 임계점 내에서 최적화하기 위해, 다중 프로그래밍 정도(MPD)를 동적으로 제어하는 메커니즘 필수

---

## Ⅱ. 구조 및 구성요소

```text
[OS 스케줄러] -> 프로세스 투입 (MPD 증가) -> 각 프로세스별 가용 물리 프레임 감소
                                                  |
[성능 붕괴] <- CPU 이용률 곤두박질 <- 디스크 I/O 대기 폭증 <- [페이지 부재(Page Fault) 연쇄 발생]
```

| 구성요소 | 역할 및 상태 | 특이사항 (스레싱 시) |
|:---|:---|:---|
| 다중 프로그래밍 정도 (MPD) | 메모리에 적재된 활성 프로세스 수 | 과도한 증가로 인해 프로세스당 할당 프레임이 임계치 미만으로 하락 |
| OS 스케줄러 | CPU 이용률을 모니터링하여 MPD 조절 | I/O 대기로 CPU 이용률이 떨어지자 이를 유휴 상태로 오판하여 MPD 추가 증가 |
| Page Fault 처리기 | 디스크 스왑 영역에서 필요한 페이지 로드 | 잦은 Swap In/Out 교차로 인해 디스크 I/O 대역폭 포화 상태 진입 |

> 요약: 스레싱은 할당 프레임 부족 $ightarrow$ 디스크 I/O 증가 $ightarrow$ CPU 이용률 하락 $ightarrow$ 스케줄러의 오판(MPD 추가 증가)이라는 악순환 구조로 발생한다.

---

## Ⅲ. 동작원리 및 흐름도

```text
물리 메모리 한계 도달 -> 프로세스 투입(MPD 증가) -> 프로세스별 프레임 부족
  -> 잦은 페이지 교체(Page Fault) -> 디스크 I/O 대기 큐 적체 -> CPU Idle 증가
  -> 스케줄러 오판(새 프로세스 투입) -> 악순환 반복 및 시스템 성능 붕괴
```

- 1단계 [프레임 부족]: 다수 프로세스 실행으로 개별 프로세스에 할당된 물리 프레임 수가 프로세스의 지역성 범위보다 작아짐
- 2단계 [빈번한 부재]: 참조하는 페이지가 계속 메모리에 없어 극심한 Page Fault 비율(Fault Rate) 발생
- 3단계 [디스크 대기]: 페이지 교체를 위해 느린 디스크(Swap 공간) 접근 시간이 발생하며 프로세스들이 Blocked 상태 전이
- 4단계 [악순환 진입]: CPU 이용률 하락을 감지한 롱텀 스케줄러가 MPD를 더 높여 프레임 부족을 가속, 시스템 전체 멈춤 현상 초래

> 요약: 스레싱의 핵심은 지역성 원리를 위배할 정도로 적은 메모리가 할당되었을 때 일어나는 연쇄적인 I/O 병목에 있다.

---

## Ⅳ. 특징
- 비선형적 성능 붕괴: MPD가 증가함에 따라 CPU 이용률이 비례하여 오르다가, 특정 임계점(스레싱 포인트)을 넘는 순간 수직 낙하함
- 지역성(Locality) 위배 반작용: 프로그램의 시간/공간적 지역성 집합을 물리 메모리가 수용하지 못할 때 발생하는 H/W-S/W 불일치
- H/W 리소스 불균형: CPU는 휴면 상태이고 디스크 I/O(스왑) 사용률만 100%에 달하는 비정상적 리소스 병목 패턴

> 요약: 스레싱 현상은 단순 메모리 부족을 넘어 OS 스케줄러의 보상 기전이 오히려 성능을 파괴하는 악순환의 딜레마다.

---

## Ⅴ. 심화 비교 및 적용 판단

| 비교 축 | 워킹 셋 (Working Set) | PFF (Page Fault Frequency) | 선택 기준 |
|:---|:---|:---|:---|
| 접근 개념 | 시간적 지역성에 기반하여 과거 일정 참조 윈도우 내의 페이지 집합 유지 | 페이지 부재율 자체를 모니터링하여 프레임 직접 가감 | 모니터링 대상(참조 기록 vs 부재율) |
| 프레임 할당 | 워킹 셋 집합 크기만큼 동적으로 할당 보장 | 상한/하한 임계치를 설정하여 프레임 동적 할당 | 구현 복잡도와 오버헤드 수준 |
| 장점 | 지역성을 직접 반영하여 MPD 최적 조절 | 구현 방식이 상대적으로 단순하고 직관적 제어 | OS의 메모리 관리 오버헤드 수용 여부 |

> 요약: 두 알고리즘 모두 각 프로세스에 필요한 최소 적정 프레임을 동적으로 할당하여 스레싱의 근본 원인인 프레임 부족을 방지하는 동적 할당(Dynamic Allocation) 정책이다.

**리스크·대응:**
- 참조 패턴의 급변: 국소적 반복 구간을 벗어나 새로운 모듈로 진입할 때(Phase Transition) 워킹 셋 예측이 빗나감 → 워킹 셋 윈도우 크기($\Delta$)를 너무 크지도 작지도 않게 적응형으로 튜닝
- OOM (Out of Memory) 연쇄 킬: 메모리 확보를 위해 커널이 중요 프로세스까지 강제 종료 → OOM Killer 점수를 조정하고 Swap 공간을 SSD 등 고속 I/O 매체로 구성 (지표: Swap I/O 대기 시간)

**도입 후 점검 지표:**
- 성능/효율: CPU 이용률(Utilization)과 디스크 스왑 대역폭(I/O Wait) 동시 측정 — 텔레메트리 모니터링
- 품질/운영: 프로세스별 페이지 부재율(Page Fault Rate) — PFF의 상한/하한 임계치 이내 통제

## Ⅵ. 실무 적용 및 결론

**적용 방안 3개:**
1. 적응형 PFF 임계치 통제: 리눅스 커널 등에서 상한치 이상의 부재율을 보이는 프로세스에 추가 프레임을 할당하고, 하한치 이하일 경우 프레임을 회수하여 MPD 동적 최적화
2. 구역 할당(Local Allocation) 정책 강제: 페이지 교체 범위를 해당 프로세스 내부로 제한(Local Replacement)하여, 한 프로세스의 메모리 과소비가 다른 프로세스의 스레싱으로 전파되지 않도록 장애 격리
3. 인프라 기반 스왑(Swap) 최적화: 가상 메모리 스왑 영역을 고성능 NVMe SSD로 배치하고, 메모리 압축(ZRAM 등)을 활성화하여 디스크 I/O에 의한 병목 지연 최소화

**결론 (2줄):**
- 기술사 판단: 스레싱은 OS의 MPD 제어 오판에서 비롯되므로, 하드웨어 증설(RAM 확장) 이전에 워킹 셋 및 PFF 기반의 동적 프레임 할당 정책으로 지역성을 보장하는 소프트웨어적 통제가 선행되어야 한다.
- 향후 방향: 클라우드 컨테이너 환경(Kubernetes)에서는 cgroups의 메모리 리밋(OOM)으로 통제하므로, 파드(Pod) 단위의 지역성 프로파일링과 분산 메모리(Memcached 등) 오프로딩 아키텍처로 스레싱 붕괴를 예방해야 한다.
