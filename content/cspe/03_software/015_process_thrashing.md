## Ⅰ. 개요
- **정의**: 페이지 폴트가 과다 발생하여 프로세스가 실제 작업보다 페이지 교체에 더 많은 시간을 소비하는 현상
- **배경/필요성**: 다중프로그래밍 정도가 과도하면 프레임 부족으로 페이지 폴트율이 급증하여 CPU 이용률이 급락함
- **비유**: 책상이 좁아서 책을 꺼내고 넣기만 반복하며 공부를 못 하는 상황과 같음

| 출제 의도 | 반드시 짚을 핵심 | 감점 회피 포인트 |
|:---|:---|:---|
| 스레싱 발생 원인과 해소 기법 | 다중프로그래밍 정도와 CPU 이용률의 관계 | 스레싱과 단순 페이지 폴트를 구분할 것 |

> 요약: 프레임 부족으로 페이지 교체가 과다 발생하여 CPU 이용률이 급락하는 현상임

## Ⅱ. 구성요소
```text
                 CPU Utilization
                      ^
                      |    /--\
                      |   /    \
                      |  /      \--- Thrashing
                      | /
                      +-------------------> Degree of Multiprogramming
```

| 구성요소 | 설명 | 비유 |
|:---|:---|:---|
| 다중프로그래밍 정도 | 메모리에 동시 적재된 프로세스 수 | 책상 위 동시에 펼친 책 수 |
| 페이지 폴트율 | 요청한 페이지가 메모리에 없는 비율 | 필요한 책이 책꽂이에 있어 꺼내야 하는 빈도 |
| Working Set | 특정 시점에 프로세스가 활발히 참조하는 페이지 집합 (018 참조) | 현재 공부에 필요한 책 묶음 |

> 요약: 프로세스 수, 페이지 폴트율, 워킹 셋의 상호작용으로 스레싱 발생 여부가 결정됨

## Ⅲ. 절차
```text
프로세스 증가 -> 프레임 부족 -> 페이지 폴트 급증 -> CPU 이용률 급락
```
- 1단계: OS가 CPU 이용률을 높이기 위해 다중프로그래밍 정도를 증가시킴
- 2단계: 프로세스당 할당 프레임이 워킹 셋보다 작아져 프레임 부족 상태에 진입함
- 3단계: 페이지 폴트가 급증하여 대부분의 시간을 디스크 I/O 대기에 소비함
- 4단계: CPU 이용률이 급락하고 OS가 다시 프로세스를 추가하여 악순환이 심화됨

> 요약: 프로세스 과적재 -> 프레임 부족 -> 폴트 급증 -> CPU 급락의 악순환 구조임

## Ⅳ. 문제점
- CPU 이용률 급락: 스레싱 발생 시 CPU 이용률이 수 퍼센트 수준으로 하락하여 처리량이 사실상 정지함
- 악순환 구조: OS의 자동 프로세스 추가 정책이 스레싱을 더 악화시키는 양성 피드백 루프를 형성함
- 탐지 지연: 페이지 폴트율 증가와 CPU 이용률 하락 간 시간차로 조기 탐지가 어려움

> 요약: CPU 급락, 악순환, 탐지 지연이 스레싱의 핵심 문제임

## Ⅴ. 개선방안
1. 단기: 워킹 셋 모델 기반으로 프로세스당 최소 프레임 수를 보장하여 폴트율을 제어함
2. 중기: PFF(Page Fault Frequency) 알고리즘으로 폴트율 상·하한을 모니터링하고 프레임을 동적 재할당함
3. 장기: 부하 제어(Load Control)를 통해 다중프로그래밍 정도 상한을 동적으로 조정하여 악순환을 차단함

> 요약: 워킹 셋 보장, PFF 기반 동적 할당, 부하 제어로 스레싱을 방지·해소할 수 있음

## Ⅵ. 전망
- 발전 방향: SSD 기반 스왑과 대용량 메모리 확대로 스레싱 임계점이 상승하는 추세임
- 기술사적 판단: 컨테이너 환경에서 메모리 cgroup 제한과 스레싱의 관계가 새로운 이슈로 부상 중임
- 기술사 제언: 메모리 오버커밋 정책 수립 시 워킹 셋 크기 추정을 기반으로 안전 마진을 설정할 필요
