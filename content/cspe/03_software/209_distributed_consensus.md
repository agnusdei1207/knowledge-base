# 📖 【암기용】 개념 완전 이해

## 한눈에
- **개요**: 분산된 여러 대의 서버(노드) 중 일부에 장애나 네트워크 단절이 발생하더라도, 전체 시스템이 '하나의 일관된 상태(값)'에 동의하도록 만드는 알고리즘
- **왜 필요한가**: 5대의 서버가 있을 때 2대가 죽거나 네트워크가 끊겨 두 그룹으로 나뉘면(Split-brain), 각자 다른 값을 참이라고 우기는 심각한 데이터 오염이 발생하기 때문이다.
- **핵심 직관**: 5명의 의사결정 위원회에서 2명이 결석해도, 남은 3명(과반수)이 투표로 리더를 뽑고 리더의 결정에 모두 따르게 하여 '단일한 목소리'를 유지하는 다수결 시스템이다.

## 핵심 용어 정리

| 용어/표기 | 의미 | 비유·예 |
|:---|:---|:---|
| Consensus (합의) | 다수의 노드가 장애 상황에서도 하나의 단일한 상태값에 동의하는 과정 | 5명이 동시에 만장일치(또는 과반수)로 의견을 정함 |
| Split-Brain (스플릿 브레인) | 네트워크 단절로 클러스터가 두 개로 쪼개져 서로 리더라고 주장하는 뇌사 상태 | 하나의 나라에 왕이 2명 생겨 각자 명령을 내림 |
| Quorum (정족수, 과반수) | 합의를 이루기 위해 필요한 최소 노드 수 (통상 $N/2 + 1$) | 의결 정족수 (5명 중 3명 찬성 필요) |
| Replicated Log (복제 로그) | 모든 노드가 동일한 순서로 저장해야 하는 상태 변경 기록 | 순서대로 적힌 회의록 |

## 깊이 이해
- **배경·문제의식**: 분산 데이터베이스나 쿠버네티스(etcd) 같은 핵심 인프라에서는 메타데이터(예: "현재 마스터 DB는 A서버다")의 완벽한 일관성이 필요하다. 하지만 네트워크 지연, 패킷 유실, 서버 다운이 일상인 환경에서 어떻게 노드들이 완벽히 같은 상태를 유지할 수 있을까? 이를 수학적으로 푼 것이 Paxos이고, 이를 엔지니어가 구현하기 쉽게 만든 것이 Raft다.
- **작동 원리 (Raft 기준)**: 
  - **리더 선출 (Leader Election)**: 모든 노드는 '팔로워'로 시작한다. 리더의 심장박동(Heartbeat)이 안 오면 누군가 '후보자(Candidate)'가 되어 투표를 요청한다. 과반수(Quorum) 표를 얻으면 '리더'가 된다.
  - **로그 복제 (Log Replication)**: 클라이언트의 쓰기 요청은 오직 리더만 받는다. 리더는 임시 로그를 팔로워들에게 뿌리고, 팔로워 과반수가 "잘 받았다(Ack)"고 하면 그제서야 로그를 확정(Commit)하고 클라이언트에 성공을 반환한다.
- **비유**: 반장 선거를 해서 과반수 득표로 반장(리더)을 뽑는다. 선생님(클라이언트)의 지시사항은 무조건 반장만 받고, 반장이 과반수의 학생(팔로워)에게 지시를 전파해 확인을 받아야만 "선생님, 반 전체에 전달 완료했습니다"라고 보고하는 체계다.
- **구체 예시**: 5대의 etcd 클러스터에서 2대가 랜선이 뽑혀 죽더라도, 남은 3대(과반수 3 만족)는 계속 리더를 유지/선출하며 시스템이 정상 작동(가용성 보장)한다. 하지만 3대가 죽어 2대만 남으면 과반수 미달로 쓰기를 거부하여 데이터 오염을 막는다.
- **흔한 오해·주의점**: "노드가 많을수록 무조건 가용성과 성능이 좋다"는 오해다. 노드가 5대에서 100대로 늘어나면 과반수(51대)의 Ack를 받아야 하므로 합의 성능(쓰기 속도)은 끔찍하게 느려진다. 그래서 합의 클러스터는 통상 3, 5, 7대 등 홀수 소규모로만 운영한다.

## 연결 개념
- **CAP 정리**: 합의 알고리즘은 네트워크 파티션(P) 시 무조건 일관성(C)을 지키고 가용성(A)을 희생(쓰기 거부)하는 완벽한 CP 시스템이다.
- **etcd / ZooKeeper**: Raft(etcd)와 ZAB/Paxos(ZooKeeper) 합의 알고리즘을 내부적으로 사용하는 대표적인 분산 코디네이터 소프트웨어
- **비잔틴 장애 허용 (BFT)**: 단순 노드 다운(Raft/Paxos)을 넘어, 노드가 해킹되어 '거짓말'을 하는 상황까지 합의하는 알고리즘 (블록체인)

# 📝 【답안용】 시험 답안 템플릿

## 핵심 인사이트 (3줄 요약)

> 1. **본질**: 비동기 분산 네트워크 환경에서 일부 노드의 장애(Crash Fault)나 단절 시에도 전체 시스템이 단일한 상태(Replicated State)를 유지하도록 보장하는 프로토콜이다.
> 2. **가치**: 스플릿 브레인(Split-Brain)으로 인한 데이터 오염을 방지하고, 단일 리더 기반의 복제 로그 관리를 통해 분산 인프라의 핵심 메타데이터 저장소(etcd, Zookeeper)의 신뢰성을 담보한다.
> 3. **판단 포인트**: 수학적 완결성의 Paxos보다 이해와 구현이 쉬운 리더 기반의 Raft가 현대 클라우드 네이티브 아키텍처의 표준으로 자리 잡았음을 인지해야 한다.

## 출제 의도 및 답안 포인트

| 출제 의도 | 반드시 짚을 핵심 | 감점 회피 포인트 |
|:---|:---|:---|
| 분산 합의가 필요한 장애 상황 인식 | Split-Brain, 네트워크 파티션, Quorum (과반수) | 일반적인 DB 복제(Master-Slave)와 합의 알고리즘 혼동 |
| Raft 알고리즘의 동작 메커니즘 이해 | 리더 선출(Leader Election), 로그 복제(Log Replication) | 리더와 팔로워의 역할을 명시하지 않고 모호하게 서술 |
| 합의 알고리즘 간의 차이와 한계 파악 | Paxos(복잡, Peer) vs Raft(단순, Leader), BFT 비교 | 성능이 매우 좋다고 서술 (과반수 대기로 인해 쓰기 성능은 저하됨) |

> 요약: 스플릿 브레인을 방어하는 정족수(Quorum)의 원리를 핵심으로, 학술적 Paxos와 실용적 Raft의 차이점 및 구체적 동작(리더 선출/로그 복제)을 서술해야 한다.

## Ⅰ. 개요 및 필요성

- 개요: 노드 장애나 메시지 유실/지연이 발생하는 비동기 네트워크 분산 환경에서 다수의 노드가 단일한 상태값에 동의(Consensus)하는 알고리즘
- 배경: 분산 시스템의 규모 확장으로 특정 노드 장애는 상시 발생하며, 단순 Master-Slave 복제 시 마스터 다운 및 Split-brain으로 데이터 무결성 파괴 위험
- 필요성: 과반수(Quorum) 원리를 적용하여 $F$개의 장애를 견디기 위해 $2F+1$개의 노드를 구성, 클러스터의 완벽한 강한 일관성(Strong Consistency) 유지 인프라 필요

---

## Ⅱ. 분산 합의 메커니즘 구조 (Raft 중심)

```text
[클라이언트] -> (Write 요청) -> [Leader 노드 (임기: Term)] -> (Log 전송) -> [Follower 노드 1, 2, 3]
                                   | (과반수 Ack 수신 시 Commit)                 | (수신 및 Ack 반환)
                                   +<--------------------------------------------+
```

| 구성요소 (상태) | 역할 | 특이사항 |
|:---|:---|:---|
| Leader (리더) | 클라이언트의 모든 쓰기 요청 독점 처리 및 로그 복제 통제 | 한 임기(Term)에 오직 1대만 존재 |
| Follower (팔로워) | 리더의 로그 복제 명령을 수동적으로 수신 및 로컬 저장 | 리더의 Heartbeat 대기 (타임아웃 시 후보로 전환) |
| Candidate (후보자) | 리더 장애 감지 시 새로운 리더가 되기 위해 투표(Vote) 요청 | 과반수(Quorum) 득표 시 리더 승격 |

> 요약: Raft는 상태 공간을 3가지(리더, 팔로워, 후보자)로 명확히 분리하여 모든 통제권을 리더에게 집중함으로써 합의 로직을 극도로 단순화했다.

---

## Ⅲ. 동작원리 및 흐름도 (Raft 알고리즘)

```text
리더 장애 감지 -> 후보자 투표 요청 -> 과반수 득표(리더 선출) -> 클라이언트 쓰기 -> 과반수 로그 복제 -> 확정(Commit)
```

- 1단계 [Leader Election (리더 선출)]: Follower가 일정 시간(Random Timeout) 리더의 Heartbeat를 못 받으면 Candidate로 전환하여 자신에게 1표를 행사 후 타 노드에 투표(RequestVote) 요청
- 2단계 [과반수 득표 및 승격]: 클러스터 노드의 과반수($N/2+1$) 이상 찬성 표를 얻은 Candidate가 새로운 임기(Term)의 Leader로 승격
- 3단계 [Log Replication (로그 복제)]: 클라이언트의 쓰기 요청을 받은 Leader는 이를 Uncommitted 로그로 생성하고 Follower들에게 전송(AppendEntries)
- 4단계 [Commit 및 응답]: Follower 과반수가 디스크 기록 후 Ack를 반환하면, Leader는 로그를 Commit(상태 기계에 적용)하고 클라이언트에 성공 응답 전송

> 요약: 타임아웃 기반의 선거로 리더를 뽑고, 리더는 과반수의 팔로워에게 로그를 강제 동기화하는 Two-Phase Commit 유사 방식으로 합의를 이룬다.

## Ⅳ. 특징
- 스플릿 브레인 원천 차단: 네트워크가 단절되어 5대 노드가 [3대]와 [2대]로 쪼개질 경우, [2대] 파티션은 과반수 득표가 불가능하여 리더를 선출하지 못하고 쓰기를 거부(가용성 포기, 일관성 수호)
- 복제 상태 기계(Replicated State Machine): 동일한 초기 상태에서 동일한 순서의 확정된(Committed) 로그 명령어를 실행하면, 모든 노드는 수학적으로 완벽히 동일한 최종 상태에 도달함 보장
- BFT(비잔틴 장애) 방어 불가: 노드가 악의적으로 변조된 데이터(거짓말)를 보내는 상황은 가정하지 않는 Crash-Fault Tolerant(CFT) 알고리즘임

> 요약: 네트워크 단절 시 일부 노드의 가용성을 희생하더라도 데이터의 강한 일관성을 절대적으로 사수하는 CP(CAP 정리) 시스템의 뼈대다.

## Ⅴ. 심화 비교 및 적용 판단

| 비교 축 | Paxos (팩소스) | Raft (래프트) | 선택 기준 |
|:---|:---|:---|:---|
| 아키텍처 사상 | Peer-to-Peer 분산 구조 | Leader 중심 중앙 통제 구조 | 구현 용이성과 유지보수성 |
| 이해 및 구현 난이도 | 수학적 증명 중심, 매우 난해함 | 엔지니어링 관점의 설계, 명관함 | 클라우드 네이티브 생태계 (Raft 압승) |
| 쓰기(Write) 위임 | 모든 노드가 Proposer 역할 가능 | 오직 Leader만 Write 권한 가짐 | 동시성 제어 복잡도 회피 |
| 대표적 구현체 | Google Spanner, Apache ZooKeeper(ZAB) | etcd (Kubernetes), Consul, TiKV | 현대 오픈소스 표준 채택 |

> 요약: 이론적 시초인 Paxos에서 발전하여, 실무 구현과 가독성을 극대화한 Raft가 현대 클러스터링 미들웨어의 절대적 표준으로 자리잡았다.

**리스크·대응 (기본은 불릿):**
- 클러스터 규모 확장에 따른 쓰기 지연: 노드가 9대, 11대로 커질수록 과반수 Ack 대기 시간 급증 → 합의 클러스터 노드는 홀수로 3~5대까지만 소규모 배치하고, 읽기 전용(Learner/Observer) 노드를 분리 증설
- 동시다발적 선거(Vote Split) 교착 상태: 여러 Follower가 동시에 Timeout되어 표가 분산됨 → Election Timeout을 150~300ms 사이의 완전 무작위(Randomized) 값으로 설정하여 충돌 원천 회피
- 악의적 노드의 비잔틴 결함(Byzantine Fault): 해킹된 노드가 위조된 표나 로그 전송 → 퍼블릭 환경에서는 PBFT(Practical Byzantine Fault Tolerance) 등 블록체인 합의 알고리즘으로 전환 설계

**도입 후 점검 지표 (기본은 불릿):**
- 안정성/장애: Leader 선거 발생 빈도(네트워크 불안정 지표), Quorum 구성 실패(No Leader) 지속 시간
- 성능/효율: 로그 AppendEntries 지연시간(p99 Latency), 디스크 fsync(강제 동기화) 소요 시간

## Ⅵ. 실무 적용 및 결론

**적용 방안 3개:**
1. Kubernetes 제어 평면(Control Plane) 구성: k8s의 모든 클러스터 상태(Pod 정보, Config)를 단일 진실 공급원(SSOT)인 etcd(Raft 기반) 3대 또는 5대 클러스터에 저장하여 마스터 노드 장애 시 완벽한 복구 보장
2. 분산 데이터베이스 메타데이터 관리: MongoDB의 Replica Set이나 Kafka의 KRaft 모드(Zookeeper 제거)에 Raft를 내장시켜, 컨트롤러 선출 및 토픽 메타데이터의 Split-brain 없는 정합성 통제
3. 서비스 디스커버리 분산 락(Distributed Lock) 제공: 마이크로서비스 환경에서 동시성 제어가 필요한 크리티컬 자원에 접근 시, Consul(Raft)을 활용한 Session/Lock API를 호출하여 안전한 상호배제(Mutex) 획득

**결론 (2줄):**
- 기술사 판단: 클라우드 네이티브 아키텍처에서 노드 장애는 예외가 아닌 상수이므로, 인프라의 두뇌 역할을 하는 서비스(etcd, 분산DB 메타데이터)에 분산 합의 알고리즘 적용은 절대적 필수 요건이다.
- 향후 방향: Zookeeper 같은 별도의 코디네이터 서버를 두는 아키텍처에서 벗어나, Kafka의 KRaft처럼 애플리케이션 자체가 Raft 프로토콜을 내재화(Embedded)하여 인프라 복잡성을 줄이는 방향으로 진화 중이다.
