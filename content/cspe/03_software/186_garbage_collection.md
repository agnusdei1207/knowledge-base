## Ⅰ. 개요
- **정의**: 프로그램이 더 이상 참조하지 않는 힙 메모리 객체를 자동으로 탐지·회수하는 메모리 관리 기법
- **배경/필요성**: 수동 해제 시 메모리 누수(187 참조)·이중 해제 등 오류가 빈번하므로 자동 회수 메커니즘이 필요함
- **비유**: 도서관에서 반납 기한이 지난 책을 사서가 자동으로 수거해 서가에 복원하는 것과 유사함

| 출제 의도 | 반드시 짚을 핵심 | 감점 회피 포인트 |
|:---|:---|:---|
| GC 알고리즘 종류와 동작 원리 | Mark-Sweep, Generational, Concurrent GC 구분 | STW(Stop-The-World) 발생과 지연 시간 영향 명시 |

> 요약: 도달 불가 객체를 자동 탐지·회수하여 메모리 안전성을 확보하는 런타임 메커니즘임

## Ⅱ. 구성요소
```text
Root Set (Stack, Static, Register)
         |
         v
   +------------+
   | Mark Phase  |--- Reachable? --> Live
   +------------+
         |
         v
   +------------+
   | Sweep Phase |--- Unreachable --> Free
   +------------+
         |
         v
   +------------+
   | Compact     |--- Defragment Heap
   +------------+
```

| 구성요소 | 설명 | 비유 |
|:---|:---|:---|
| 루트 집합 | 스택 변수·정적 필드·레지스터 등 GC 탐색의 시작점 | 도서관 대출 장부 |
| 마킹 | 루트에서 참조 그래프를 순회하며 도달 가능 객체에 표시 | 대출 장부에 있는 책에 스티커 부착 |
| 스위핑/압축 | 표시 없는 객체 해제 후 단편화 해소를 위해 생존 객체 이동 | 스티커 없는 책 수거 후 서가 정리 |

> 요약: 루트-마킹-스위핑/압축 과정으로 미참조 객체를 자동 회수함

## Ⅲ. 절차
```text
할당 요청 --> 힙 공간 부족? --> STW 진입 --> Mark --> Sweep/Compact --> STW 해제
```
- 1단계: 객체 할당 요청 시 힙 잔여 공간을 확인하고 부족하면 GC 트리거
- 2단계: 애플리케이션 스레드를 일시 정지(STW)하고 루트 집합에서 마킹 시작
- 3단계: 도달 불가 객체를 해제(Sweep)하고, 필요 시 생존 객체를 연속 배치(Compact)
- 4단계: STW를 해제하고 애플리케이션 스레드를 재개, 확보된 공간에 후속 할당 수행

> 요약: 트리거-정지-마킹/스위핑-재개의 사이클로 힙 메모리를 회수함

## Ⅳ. 문제점
- STW 지연: 마킹·압축 동안 모든 스레드가 정지하여 응답 지연 발생 — 실시간 시스템에 부적합
- 처리량 감소: GC 사이클이 CPU 자원을 소비하여 애플리케이션 가용 처리량 감소
- 메모리 풋프린트: 세대별 GC의 복수 영역 유지 및 카드 테이블 등 부가 구조로 메모리 오버헤드 발생

> 요약: 지연·처리량·메모리 오버헤드가 GC의 주요 과제임

## Ⅴ. 개선방안
1. 단기: G1/ZGC 등 저지연 수집기 적용으로 STW 시간을 밀리초 이하로 단축
2. 중기: Concurrent Marking 병행으로 애플리케이션 스레드와 GC 스레드 동시 실행하여 처리량 확보
3. 장기: Region 기반 할당과 세대 간 참조 최소화 설계로 부가 메모리 구조 축소

> 요약: 저지연 수집기·병행 마킹·리전 설계로 GC 오버헤드를 체계적으로 감소시킴

## Ⅵ. 전망
- 발전 방향: ZGC·Shenandoah 등 10ms 이하 STW 수집기가 프로덕션 표준으로 자리 잡는 추세
- 기술사적 판단: 대용량 힙(수백 GB) 환경에서 GC 확장성이 핵심 평가 기준이 됨
- 기술사 제언: 워크로드 특성(지연 민감/처리량 우선)에 따라 GC 알고리즘을 선택하는 가이드라인 수립이 필요함
