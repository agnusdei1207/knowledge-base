# 📖 【암기용】 개념 완전 이해

> 목적: 클라우드 네이티브 보안 4C를 처음 보는 사람도 어느 계층에서 어떤 통제를 해야 하는지 이해하게 만든다. 시험 답안 양식이 아니라, 이해를 위한 설명이다.

## 한눈에
- **개요**: 4C는 Cloud, Cluster, Container, Code 네 계층으로 클라우드 네이티브 보안을 나누는 모델이다.
- **왜 필요한가**: 컨테이너 보안은 이미지 스캔만으로 끝나지 않고 IAM, 네트워크, 런타임, 애플리케이션 코드까지 연결된다.
- **핵심 직관**: 건물 보안이 도시, 단지, 방, 사용자 행동을 모두 보듯 클라우드 보안도 계층별 통제가 필요하다.

## 깊이 이해
- **배경·문제의식**: Kubernetes 기반 서비스는 클라우드 권한, 클러스터 설정, 이미지 취약점, 코드 결함이 연결되어 공격 경로를 만든다.
- **작동 원리**: Cloud 계층에서 IAM과 네트워크를 통제하고, Cluster에서 RBAC와 NetworkPolicy를 적용한다. Container에서는 이미지·런타임을 점검하고, Code에서는 SAST·SCA·Secrets 점검을 수행한다.
- **비유**: 성 안으로 들어오는 길(Cloud), 성문과 경비(Cluster), 방 잠금(Container), 방 안의 금고 사용법(Code)을 따로 관리하는 구조이다.
- **구체 예시**: 공개 S3 버킷, Kubernetes cluster-admin 권한, root 컨테이너, 하드코딩된 API Key가 함께 존재하면 단일 취약점보다 침해 범위가 커진다.
- **흔한 오해·주의점**: 4C는 보안 제품 분류가 아니다. 설계·배포·런타임 각 단계에서 누락 계층이 없는지 점검하는 체크 프레임이다.

## 연결 개념
- Kubernetes 보안: RBAC, NetworkPolicy, Pod Security Admission
- CNAPP: 4C 계층을 통합 점검하는 플랫폼
- DevSecOps: 코드·이미지·IaC 보안을 CI/CD에 내장

# 📝 【답안용】 시험 답안 템플릿

> 목적: 4C를 계층별 통제와 점검 지표로 작성하는 답안 양식이다.
> 핵심: 출제자는 컨테이너 이미지 스캔만이 아니라 Cloud부터 Code까지 공격면을 연결해 통제하는지 확인한다.

## 핵심 인사이트 (3줄 요약)

> 1. **본질**: 클라우드 네이티브 보안 4C는 Cloud, Cluster, Container, Code 계층별 공격면과 보안 통제를 분리하는 모델이다.
> 2. **가치**: IAM, RBAC, 이미지 취약점, Secrets, 런타임 이상행위를 계층별로 점검해 공급망부터 실행 환경까지 관리한다.
> 3. **판단 포인트**: 한 계층만 점검하면 우회 경로가 남으므로 CI/CD와 런타임 통제를 함께 배치해야 한다.

## 출제 의도 및 답안 포인트

| 출제 의도 | 반드시 짚을 핵심 | 감점 회피 포인트 |
|:---|:---|:---|
| 클라우드 네이티브 공격면 분류 확인 | Cloud, Cluster, Container, Code 4계층 | 컨테이너 보안만 서술 |
| 계층별 통제 설계 역량 확인 | IAM, RBAC, NetworkPolicy, 이미지 스캔, SAST | 제품명 나열 후 구조 누락 |
| DevSecOps 연계 확인 | CI/CD 품질 게이트, 런타임 탐지 | 배포 전 검사와 운영 탐지 분리 누락 |

> 요약: 4C 답안은 계층 분류와 각 계층의 예방·탐지·대응 통제를 함께 제시해야 한다.

---

## Ⅰ. 개요 및 필요성

4C는 클라우드 네이티브 보안 계층 모델이다. Kubernetes 서비스는 코드 결함, 이미지 취약점, 클러스터 권한, 클라우드 IAM이 하나의 공격 경로로 연결된다. 4C는 계층별 통제를 배치해 공급망과 런타임 위험을 줄인다.

---

## Ⅱ. 구조 및 구성요소

```text
Cloud -> Cluster -> Container -> Code
  +-> IAM/VPC   +-> RBAC/Policy   +-> Image/Runtime   +-> SAST/SCA/Secrets
```

| 구성요소 | 역할 | 특이사항 |
|:---|:---|:---|
| Cloud | 계정, IAM, 네트워크, 관리형 서비스 통제 | 최소권한, KMS, VPC |
| Cluster | Kubernetes 제어면과 정책 통제 | RBAC, NetworkPolicy, Admission |
| Container | 이미지와 런타임 통제 | CVE 스캔, root 금지, seccomp |
| Code | 애플리케이션과 의존성 통제 | SAST, SCA, Secrets 탐지 |

> 요약: 4C는 클라우드 인프라부터 소스코드까지 공격면을 네 계층으로 나눠 누락 통제를 찾는 모델이다.

---

## Ⅲ. 동작원리 및 흐름도

```text
코드 작성 -> SAST/SCA/Secrets 검사 -> 이미지 빌드/서명
-> Admission 정책 검증 -> 런타임 탐지 -> 클라우드 로그 감사
```

| 단계 | 처리 내용 | 검증 기준 |
|:---:|:---|:---|
| 1 | Code 계층 보안 검사 | Critical CVE 0건, Secret 0건 |
| 2 | Container 이미지 검증 | 서명 검증, root 실행 금지 |
| 3 | Cluster 정책 적용 | RBAC 최소권한, PSA restricted |
| 4 | Cloud 권한 점검 | IAM 과권한 0건, KMS 적용 |
| 5 | 런타임 탐지와 대응 | Falco rule, 감사 로그 보존 |

> 요약: 4C는 개발 단계 검사에서 배포 승인, 런타임 탐지, 클라우드 감사까지 이어지는 흐름으로 적용한다.

---

## Ⅳ. 특징

| 구분 | 단일 컨테이너 보안 | 4C 모델 | 판단 포인트 |
|:---|:---|:---|:---|
| 범위 | 이미지·런타임 중심 | Cloud부터 Code까지 | 공격 경로 전체 |
| 적용 시점 | 배포 전후 일부 | 개발, 배포, 운영 전 과정 | CI/CD 품질 게이트 |
| 통제 방식 | CVE 스캔 | IAM/RBAC/Policy/SAST 결합 | 계층별 소유자 |
| 한계 | 계층 누락 가능 | 운영 책임 분산 필요 | RACI 정의 |

> 요약: 4C는 컨테이너 보안을 클라우드 권한, 클러스터 정책, 코드 공급망까지 확장해 보는 계층 모델이다.

## Ⅴ. 심화 비교 및 적용 판단

| 비교 축 | 기존/대안 | 본 키워드 | 선택 기준 |
|:---|:---|:---|:---|
| 구조 | 이미지 스캔 중심 | 4계층 통제 | Kubernetes 운영 시 |
| 비용/성능 | 사후 취약점 조치 | CI/CD 게이트로 사전 차단 | Critical CVE 반복 시 |
| 운영/위험 | 보안팀 단독 점검 | 개발·플랫폼·보안 공동 책임 | 계층별 소유자 필요 |

> 요약: 4C는 클라우드 네이티브 운영 조직에서 책임 경계를 나누고 계층별 통제를 배치할 때 적합하다.

| 리스크 | 원인 | 대응 방안 | 확인 지표 |
|:---|:---|:---|:---|
| 과권한 | IAM·RBAC 기본값 사용 | 최소권한, Just-in-Time 접근 | 과권한 정책 0건 |
| 공급망 침해 | 이미지·의존성 검증 누락 | SBOM, 서명, SCA | Critical CVE 0건 |
| 런타임 우회 | 배포 전 검사만 수행 | eBPF/Falco 탐지, NetworkPolicy | 런타임 위반 건수 |

> 요약: 4C 리스크는 권한, 공급망, 런타임 우회에서 발생하므로 예방과 탐지를 함께 둬야 한다.

| 점검 항목 | 목표 기준 | 측정 방법 |
|:---|:---|:---|
| Cloud | 공개 리소스 0건, MFA 100% | CSPM, IAM Analyzer |
| Cluster/Container | PSA restricted 100%, root 컨테이너 0건 | Admission 로그, kube-bench |
| Code | Secret 0건, Critical CVE 0건 | SAST, SCA, SBOM |

> 요약: 4C 도입 후 계층별 정책 준수율과 Critical 취약점 잔여 건수로 통제 수준을 판단한다.

## Ⅵ. 실무 적용 및 결론

**적용 방안 3개:**
1. Cloud 계층은 IAM 최소권한, KMS 암호화, 공개 버킷 0건 정책을 CSPM으로 점검하고 월 1회 권한 리뷰를 수행함
2. Cluster/Container 계층은 RBAC, NetworkPolicy, Pod Security Admission restricted, 이미지 서명 검증을 Admission 단계에서 차단함
3. Code 계층은 SAST, SCA, Secret 스캔, SBOM 생성을 CI/CD 필수 게이트로 두고 Critical CVE 0건 기준을 적용함

**결론 (2줄):**
- 기술사 판단: Kubernetes 기반 서비스는 4C 모델로 계층별 통제를 배치하고, 단일 VM 중심 서비스는 Cloud·Code 계층 중심으로 적용 범위를 줄임
- 향후 방향: CNAPP, SBOM, SLSA, eBPF 런타임 탐지를 결합해 공급망부터 실행 환경까지 통합 점검 체계로 확장함
