# 📖 【암기용】 개념 완전 이해

## 한눈에
- **개요**: 클라우드 네이티브 환경을 방어하기 위해 인프라부터 애플리케이션 코드까지 4개 계층을 감싸는 심층 방어(Defense in Depth) 보안 프레임워크
- **왜 필요한가**: 쿠버네티스 같은 환경은 구성이 매우 복잡하고 동적이라, 예전처럼 방화벽 하나(단일 경계)로는 뚫리면 내부가 초토화되기 때문
- **핵심 직관**: 러시아 인형(마트료시카)처럼 바깥부터 안쪽까지 겹겹이 자물쇠를 채운다. 가장 바깥의 클라우드(Cloud), 그 안의 쿠버네티스(Cluster), 그 안의 컨테이너(Container), 제일 안쪽의 코드(Code) 계층을 방어한다.

## 핵심 용어 정리

| 용어/표기 | 의미 | 비유·예 |
|:---|:---|:---|
| Cloud (클라우드) | 기초가 되는 인프라 보안 | "성의 외벽과 해자 (AWS IAM 설정)" |
| Cluster (클러스터) | 쿠버네티스 시스템 자체의 보안 | "성문 경비와 통행증 (K8s RBAC)" |
| Container (컨테이너) | 실행되는 컨테이너 이미지 환경 보안 | "병사들의 갑옷 상태 검사 (취약점 스캔)" |
| Code (코드) | 개발한 애플리케이션 소스 레벨의 보안 | "병사가 가진 무기의 결함 확인 (SAST/DAST)" |

## 깊이 이해
- **배경·문제의식**: 기존 온프레미스 보안은 네트워크 경계선만 잘 막는 방화벽 중심(Perimeter Security)이었다. 하지만 마이크로서비스는 서로 수많은 API를 주고받고 수시로 생성·삭제되므로, 해커가 경계를 한 번 뚫거나 내부에서 감염되면 횡적 이동(Lateral Movement)으로 순식간에 확산된다.
- **작동 원리**: 4C 모델은 하나의 뚫림이 전체 붕괴로 이어지지 않게 각 계층별로 독립적인 통제 수단을 적용한다. Cloud는 IAM과 네트워크 격리, Cluster는 API 서버 접근 통제(RBAC)와 네트워크 정책(NetworkPolicy), Container는 이미지 취약점 스캔과 실행 권한 축소, Code는 정적/동적 코드 분석을 담당한다.
- **비유**: 4단계 철통 보안 건물. 1단계 정문 게이트(Cloud), 2단계 층별 출입증 통제(Cluster), 3단계 개별 사무실 도어락(Container), 4단계 금고 자체의 비밀번호(Code).
- **구체 예시**: 개발자가 실수로 컨테이너를 루트(Root) 권한으로 띄웠을 때, 클러스터 계층의 정책(Pod Security Admission)이 작동하여 실행 자체를 거부함으로써 컨테이너 탈출(Container Breakout) 공격을 사전에 차단한다.
- **흔한 오해·주의점**: 4개 중 1개만 잘하면 되는 것이 아니다. 각 계층은 서로 보완적이며, 가장 안쪽 코드 계층의 취약점은 바깥 계층에서 완벽히 방어할 수 없으므로(예: 애플리케이션 내부 SQL 인젝션) 모든 계층이 조화롭게 적용되어야 한다.

## 연결 개념
- DevSecOps — 4C 모델을 개발-운영 파이프라인에 구현하는 철학
- Kubernetes Security — Cluster 계층 방어의 핵심 대상
- CNAPP (Cloud Native Application Protection Platform) — 4C를 통합적으로 관리하는 보안 도구

# 📝 【답안용】 시험 답안 템플릿

## 핵심 인사이트 (3줄 요약)

> 1. **본질**: 클라우드 네이티브 보안 4C는 Cloud, Cluster, Container, Code 4단계 계층으로 구성된 심층 방어(Defense in Depth) 아키텍처 모델임
> 2. **가치**: 단일 경계 방어의 한계를 극복하고, 내부 횡적 이동(Lateral Movement)을 차단하여 클라우드 환경의 취약점 파급력을 최소화함
> 3. **판단 포인트**: 클러스터 및 컨테이너 단의 정책 자동화(OPA 등)와 코드 단의 시프트 레프트(Shift-Left) 보안 체계 구축이 성패를 가름

## 출제 의도 및 답안 포인트

| 출제 의도 | 반드시 짚을 핵심 | 감점 회피 포인트 |
|:---|:---|:---|
| 클라우드 환경의 다계층 방어 전략 및 요소기술 이해 | 4C 각각의 계층별 통제 기법, RBAC, 이미지 스캔 | 4C 이름만 나열하고 구체적 방어 기술 누락 |

> 요약: 4C 모델은 인프라 바깥부터 소스 코드 안쪽까지 겹겹이 보호하는 클라우드 특화 심층 방어 체계임

---

## Ⅰ. 개요 및 필요성

- 개요: 클라우드 네이티브 환경을 Cloud, Cluster, Container, Code의 4개 계층으로 나누어 방어하는 심층 보안 프레임워크임
- 배경: 마이크로서비스 확산으로 시스템 복잡도가 증가하고 경계 기반 방어망(Perimeter-based) 무력화
- 필요성: 각 계층의 독립적 통제로 단일 지점 실패 시에도 전체 시스템 탈취를 막는 단계적 차단 메커니즘 절실

---

## Ⅱ. 구조 및 구성요소

```text
[Defense in Depth 방어 구조]
Cloud 방어 -> Cluster 제어
                 |
                 +-> Container 격리 -> Code 검증
```

| 구성요소 | 방어 영역 | 주요 보안 기술 |
|:---|:---|:---|
| Cloud | 클라우드 인프라 제공자 (CSP) | IAM, VPC, 시큐리티 그룹, 암호화 키 관리 |
| Cluster | 쿠버네티스 노드 및 API 서버 | RBAC, NetworkPolicy, Audit 로깅, TLS 통신 |
| Container | 실행되는 이미지 및 런타임 | 이미지 취약점 스캔, Non-Root 실행, Seccomp |
| Code | 애플리케이션 소스 코드 | SAST, DAST, SCA(오픈소스 취약점 점검) |

> 요약: 바깥 인프라부터 안쪽 소스 코드까지 4단계 계층별로 특화된 보안 통제 기술을 적용함

---

## Ⅲ. 동작원리 및 흐름도

```text
코드 커밋 검증 -> 컨테이너 이미지 스캔 -> 클러스터 배포 통제 -> 클라우드 접근 제어
```

- 1단계 [Code 방어]: 개발자가 코드를 커밋할 때 CI 파이프라인에서 정적 분석(SAST)으로 취약점 사전 차단
- 2단계 [Container 방어]: 빌드된 컨테이너 이미지를 레지스트리에서 스캔하여 CVE 취약점 유무 검증
- 3단계 [Cluster 방어]: 쿠버네티스 Admission Controller가 비인가 권한(Root) 컨테이너의 클러스터 배포 런타임 차단
- 4단계 [Cloud 방어]: 배포된 서비스는 클라우드 IAM과 시큐리티 그룹을 통해 외부 네트워크 접근을 최소 권한으로 격리

> 요약: 개발부터 배포, 운영에 이르는 파이프라인 전체 과정에서 4개 계층의 보안 검증이 순차적으로 개입함

---

## Ⅳ. 특징
- 시프트 레프트(Shift-Left): Code와 Container 계층의 통제를 개발 단계로 전진 배치하여 조기 결함 발견 및 수정 비용 절감
- 심층 방어(Defense in Depth): 한 계층이 뚫리더라도 다음 계층이 공격의 진행을 늦추고 차단하여 폭발 반경(Blast Radius) 통제
- 코드로서의 정책(PaC): OPA(Open Policy Agent) 등을 활용해 클러스터 및 컨테이너 보안 정책을 코드로 관리하고 자동화 검증

---

## Ⅴ. 심화 비교 및 적용 판단

| 방어 체계 | 경계 기반 보안 (전통적) | 4C 심층 보안 (클라우드 네이티브) | 선택 기준 |
|:---|:---|:---|:---|
| 방어 초점 | 외부에서 내부로의 침입 차단 (남북 트래픽) | 내부 횡적 이동 차단 포함 (동서 트래픽) | 아키텍처 환경 |
| 통제 지점 | 방화벽, IPS 등 단일 관문 집중 | 인프라, K8s API, 이미지, 코드 전방위 | 방어망 복잡도 감수 |
| 신뢰 모델 | 내부망은 기본적으로 신뢰 | 내부망도 신뢰하지 않음 (제로 트러스트) | 보안 정책 기조 |

> 요약: 4C 모델은 내부를 신뢰하지 않는 제로 트러스트 관점으로 동서 트래픽 횡적 이동 차단에 최적화됨

**리스크·대응 (기본은 불릿):**
- 보안 도구 파편화: 4개 계층별 개별 솔루션 도입으로 관제 사각지대 발생 → 통합 클라우드 보안 플랫폼(CNAPP) 기반 단일 가시성 확보 (지표: 통합 대시보드 경보 누락 건수)
- 통제 과도에 따른 배포 지연: 과도한 검증으로 애자일 속도 저하 → CI/CD 파이프라인 내 정책 자동화(PaC) 연동으로 사람 개입 최소화 (지표: 파이프라인 보안 스캔 소요 시간)

**도입 후 점검 지표 (기본은 불릿):**
- 취약점 식별: Container 및 Code 계층에서 탐지된 High/Critical 취약점 조치율 100% 달성 — 스캐너 대시보드 검증
- 권한 최소화: Cluster 내 Root 권한으로 실행되는 Pod 비율 0% 유지 — K8s Audit 로그 분석

---

## Ⅵ. 실무 적용 및 결론

**적용 방안 3개:**
1. Code/Container 시프트 레프트: IDE 플러그인 및 CI 도구에 Trivy, SonarQube를 연동하여 개발 단계에서 이미지 및 코드 취약점 자동 차단
2. Cluster 동적 제어: OPA Gatekeeper를 클러스터에 배포하여 Non-root 실행, 특정 레지스트리 전용 이미지 사용 등 배포 정책 강제화
3. 런타임 위협 탐지: Falco와 같은 런타임 보안 도구를 적용하여 컨테이너 내 비정상 쉘(Shell) 실행이나 파일 변조 발생 시 즉각 경보 발송

**결론 (2줄):**
- 기술사 판단: 클라우드 네이티브 보안은 특정 솔루션 하나로 해결될 수 없으며, 4개 계층 모두에 걸쳐 정책을 코드화하고 파이프라인에 내재화하는 체계 혁신이 필수임
- 향후 방향: 4C 모델을 확장하여 애플리케이션 보안과 인프라 보안을 하나로 융합하여 보호하는 CNAPP(Cloud Native Application Protection Platform)으로 발전
