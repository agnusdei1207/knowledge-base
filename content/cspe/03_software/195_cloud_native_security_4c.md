## 미리 알고가기

- 4C는 Cloud·Cluster·Container·Code 계층으로 클라우드 네이티브 보안 범위를 나누는 모델임
- 외부 계층의 통제가 약하면 내부 계층이 제공할 수 있는 보호 범위도 제한됨
- Cloud는 계정·네트워크·키·물리 인프라와 공급자 책임 경계를 포함함
- Cluster는 API 서버·etcd·노드·RBAC·네트워크 정책 같은 오케스트레이터 통제를 포함함
- Container는 이미지·런타임·권한·파일시스템·리소스 제한을 포함함
- Code는 소스·의존성·비밀정보·입력 검증·애플리케이션 권한을 포함함
- Admission 제어는 API 요청을 저장하기 전에 정책과 허용 조건을 검사함
- seccomp는 컨테이너 프로세스가 호출할 수 있는 Linux 시스템 호출을 제한함

## 작성 근거(검토용)

- 4C는 Cloud에서 Code로 이어지는 계층 의존성과 계층별 보호 대상·통제를 핵심 축으로 설명함
- 분류표는 각 계층의 보호 대상·대표 통제·검증 증적을 같은 수준에서 제시함
- 클러스터 기준선과 배포 파이프라인에서 여러 계층의 통제 연결을 검증함

## Ⅰ. 개요

- **정의/개념**: 클라우드 네이티브 보안 4C는 Cloud·Cluster·Container·Code의 중첩 계층별 자산과 통제를 구분해 심층 방어를 설계하는 모델임
- **배경/필요성**: 코드 통제만으로 계정 탈취·클러스터 오설정·컨테이너 권한 상승을 통제할 수 없어 계층별 책임과 방어가 필요함

## Ⅱ. 특징

- Cloud에서 Code로 갈수록 기반 인프라에서 애플리케이션 로직으로 보호 대상이 좁아짐
- 각 내부 계층은 외부 계층의 신원·네트워크·키·실행 경계를 전제로 동작함
- 공급자·플랫폼·개발·보안 팀의 책임을 계층별 통제와 증적으로 연결함
- 예방 통제와 함께 런타임 탐지·감사 로그·취약점 검증을 각 계층에 배치함

## Ⅲ. 종류 및 비교

| 4C 계층 | 보호 대상 | 대표 통제 | 검증 증적 |
|:---|:---|:---|:---|
| Cloud | 계정·가상 네트워크·키·호스트 인프라 | IAM·네트워크 분리·키 관리·감사 로그 | 관리자 권한·공개 자원·키 사용 이력 |
| Cluster | API 서버·etcd·노드·워크로드 제어면 | RBAC·Admission·네트워크 정책·etcd 암호화 | 권한 바인딩·정책 거부·감사 이벤트 |
| Container | 이미지·런타임·프로세스·파일시스템 | 이미지 서명·비루트 실행·seccomp·자원 제한 | 서명 검증·취약점·권한 위반·런타임 이벤트 |
| Code | 소스·의존성·비밀정보·입력·업무 권한 | 코드 분석·의존성 검사·비밀 스캔·입력 검증 | 결함·취약 패키지·비밀 노출·인가 테스트 |

> 요약: 4C는 Cloud 계층부터 Code 계층까지 보호 대상과 통제·증적을 연결함.

## Ⅳ. 구성요소 및 구조

```text
+--------------------------------------------------+
| Cloud: 계정·네트워크·키·호스트 인프라            |
|  +--------------------------------------------+  |
|  | Cluster: API·etcd·노드·정책               |  |
|  |  +--------------------------------------+  |  |
|  |  | Container: 이미지·런타임·프로세스    |  |  |
|  |  |  +--------------------------------+  |  |  |
|  |  |  | Code: 소스·의존성·입력·인가    |  |  |  |
|  |  |  +--------------------------------+  |  |  |
|  |  +--------------------------------------+  |  |
|  +--------------------------------------------+  |
+--------------------------------------------------+
```

| 연결 지점 | 설명 |
|:---|:---|
| 신원 연계 | Cloud IAM·Cluster 서비스 계정·애플리케이션 권한을 최소 범위로 연결함 |
| 공급망 연계 | Code 의존성·Container 이미지·Cluster Admission 검증을 배포 조건으로 연결함 |
| 런타임 연계 | Container 행위와 Cluster·Cloud 감사 이벤트를 같은 워크로드로 연결함 |
| 책임 연계 | 공급자·플랫폼·개발 팀의 통제 소유자와 예외 승인자를 지정함 |

> 요약: 외부 계층의 신원·공급망·런타임 통제가 내부 계층까지 끊기지 않아야 심층 방어가 성립함.

## Ⅵ. 실무 사례

1. Kubernetes 플랫폼은 Cloud IAM·RBAC·비루트 실행을 연계하고 정책 위반·특권 Pod 수를 확인함
2. 배포 파이프라인은 코드 검사·이미지 서명·Admission을 연결하고 차단된 배포·잔여 취약점 수를 확인함

## Ⅶ. 결론

- 클라우드 네이티브 보안은 4C 계층별 책임·통제·증적을 연결하고 외부 계층부터 검증해야 함
