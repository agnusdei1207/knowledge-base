## Ⅰ. 개요
- **정의**: 외부 동작을 변경하지 않고 코드의 내부 구조를 개선하는 체계적 변환 기법
- **배경/필요성**: 기능 추가가 반복되면 코드 복잡도가 증가하여 변경 비용이 누적되므로 구조 개선이 필요함
- **비유**: 방 배치를 바꿔 동선을 개선하되 방의 용도(기능)는 그대로 유지하는 것과 유사함

| 출제 의도 | 반드시 짚을 핵심 | 감점 회피 포인트 |
|:---|:---|:---|
| 코드 스멜 식별·리팩토링 기법 적용 | 동작 보존 원칙, 테스트 선행 | 리팩토링 ≠ 리라이트, 기술 부채(279 참조)와 연계 설명 |

> 요약: 동작을 보존하면서 내부 구조를 개선하여 변경 비용을 낮추는 기법임

## Ⅱ. 구성요소
```text
Code Smell 식별
  +-- Long Method
  +-- Large Class
  +-- Duplicated Code
        |
        v
Refactoring Catalog
  +-- Extract Method
  +-- Move Method
  +-- Replace Conditional with Polymorphism
```

| 구성요소 | 설명 | 비유 |
|:---|:---|:---|
| Code Smell | 설계 문제를 암시하는 코드의 구조적 징후 | 냄새 — 직접적 결함은 아니지만 문제 징후 |
| Extract Method | 긴 메서드에서 의미 단위를 별도 메서드로 분리 | 긴 문단을 소제목별로 나누는 편집 |
| Replace Conditional | 조건 분기를 다형성·전략 패턴으로 대체하여 확장성 확보 | 매뉴얼 스위치를 자동 분배기로 교체 |
| Inline/Move | 불필요한 간접 계층을 제거하거나 책임에 맞는 클래스로 이동 | 빈 전달 창구를 없애고 담당자에게 직접 연결 |

> 요약: 코드 스멜을 식별하고 카탈로그 기법을 적용하여 구조를 개선함

## Ⅲ. 절차
```text
테스트 확보 -> 스멜 식별 -> 기법 적용 -> 회귀 검증
```
- 1단계: 리팩토링 대상 코드에 대한 자동화 테스트를 충분히 확보
- 2단계: 정적 분석 도구·코드 리뷰로 코드 스멜을 식별하고 우선순위 결정
- 3단계: 한 번에 하나의 리팩토링 기법을 적용하고 커밋 단위를 소규모로 유지
- 4단계: 매 적용 후 전체 테스트 스위트를 실행하여 동작 보존을 검증

> 요약: 테스트 확보 → 스멜 식별 → 소규모 적용 → 회귀 검증 순서로 반복함

## Ⅳ. 문제점
- 테스트 부재: 레거시 코드에 테스트가 없으면 동작 보존 검증이 불가함
- 범위 확산: 연쇄적 의존성으로 한 곳의 변경이 예상 외 영역으로 파급됨
- 일정 압박: 기능 개발 일정에 밀려 리팩토링 시간 확보가 어려움

> 요약: 테스트 부재, 변경 파급, 일정 압박이 주요 문제임

## Ⅴ. 개선방안
1. 단기: 특성화 테스트(Characterization Test)를 작성하여 레거시 동작을 캡처
2. 중기: 의존성 분석 도구로 변경 영향 범위를 사전 파악하여 파급 제어
3. 장기: 스프린트별 기술 부채 버짓(279 참조)을 할당하여 리팩토링 시간 제도화

> 요약: 특성화 테스트, 영향 분석, 기술 부채 버짓으로 각 문제에 대응함

## Ⅵ. 전망
- 발전 방향: AI 기반 코드 스멜 자동 탐지·리팩토링 제안 도구 확산
- 기술사적 판단: 지속적 리팩토링이 소프트웨어 장기 유지보수 비용을 결정하는 핵심 활동임
- 기술사 제언: 리팩토링을 기능 개발과 동등한 백로그 항목으로 관리하는 프로세스를 수립할 필요
