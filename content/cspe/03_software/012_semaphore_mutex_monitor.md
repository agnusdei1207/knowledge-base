# 📖 【암기용】 개념 완전 이해

## 한눈에
- **개요**: 병행 프로세스(또는 스레드) 환경에서 공유 자원에 대한 동시 접근을 제어하여 데이터 정합성을 보장하는 임계 구역 상호 배제(Mutual Exclusion) 동기화 기법.
- **왜 필요한가**: 여러 스레드가 동시에 은행 계좌 잔고를 수정하면, 값이 덮어써져 정합성이 깨지는 경쟁 상태(Race Condition)가 발생한다. 이를 막기 위해 자원에 "자물쇠"를 채우는 메커니즘이 필요하다.
- **핵심 직관**: 
  - **뮤텍스**: 화장실 열쇠가 1개뿐. 열쇠를 가진 사람만 들어가고, 나오면서 다음 사람에게 열쇠를 준다.
  - **세마포어**: 식당의 빈자리 개수(N개). 자리가 있으면 카운트를 깎고 들어가고, 자리가 없으면 줄 서서 기다린다. 나올 때 카운트를 늘린다.
  - **모니터**: 객체 지향 언어에서 자물쇠와 자원을 아예 한 방에 몰아넣고, 방에 들어가는 입구 자체를 언어 차원에서 통제하는 "자동문".

## 핵심 용어 정리

| 용어/표기 | 의미 | 비유·예 |
|:---|:---|:---|
| **임계 구역 (Critical Section)** | 공유 자원(변수, 파일 등)에 접근하여 수정하는 코드 영역 | "한 번에 한 명만 들어가야 하는 화장실 내부" |
| **P 연산 (Wait, Down)** | 자원을 획득하려는 시도. 자원이 없으면 대기(Sleep) 상태로 전환 | "빈자리 확인 후 없으면 번호표 뽑고 대기" |
| **V 연산 (Signal, Up)** | 자원 사용을 마치고 반납하며 대기 중인 프로세스를 깨움 | "식사 끝내고 나오면서 대기자 호출" |
| **경쟁 상태 (Race Condition)** | 두 개 이상의 프로세스가 공유 데이터에 동시 접근하여 결과가 훼손되는 상태 | "두 명이 동시에 하나의 문서를 수정하여 덮어쓰기 발생" |

## 깊이 이해
- **배경·문제의식**: 하드웨어적인 인터럽트 비활성화나 Test-And-Set 명령어만으로는 복잡한 소프트웨어의 동기화를 제어하기 어렵고(Busy Waiting 발생), 프로그래머의 실수(자물쇠를 안 풀고 나옴 등)로 인해 교착상태가 빈번히 발생했다.
- **작동 원리**:
  - **세마포어(Semaphore)**: 정수형 변수 $S$와 대기 큐를 갖는다. `wait(S)`는 $S$를 1 감소시키고 음수면 큐에서 블로킹 대기한다. `signal(S)`는 $S$를 1 증가시키고 음수거나 0이면 큐에서 하나를 깨워 Ready 상태로 만든다.
  - **뮤텍스(Mutex)**: 이진 세마포어(0 또는 1)와 유사하지만, 가장 큰 차이는 **Lock을 건 스레드만이 Unlock을 할 수 있다**는 소유권(Ownership)의 유무다.
  - **모니터(Monitor)**: 자바의 `synchronized` 키워드처럼, 데이터와 그 데이터를 조작하는 프로시저(함수)를 하나의 모듈로 캡슐화하고, 한 번에 하나의 프로세스만 내부 프로시저를 실행할 수 있도록 컴파일러가 자동 보장한다. 프로그래머가 명시적으로 P/V 연산을 호출할 필요가 없어 안전하다.
- **구체 예시**: Java에서 `Vector`나 `Hashtable`은 내부 메서드에 `synchronized`가 걸려 있는 모니터 기반 객체로, 스레드 안전(Thread-Safe)을 보장한다. 반면 C언어의 `pthread_mutex_lock()`은 수동으로 뮤텍스를 제어한다.
- **흔한 오해·주의점**: 이진 세마포어와 뮤텍스를 완전히 같다고 오해하는 경우가 많다. 이진 세마포어는 A 스레드가 0으로 만들고, B 스레드가 1로 올리는 것(Signal)이 가능하지만, 뮤텍스는 A 스레드가 잠갔으면 반드시 A 스레드가 풀어야 한다.

## 연결 개념
- (014 임계 구역·상호 배제 참조) 동기화의 3원칙(상호배제, 진행, 한계대기)
- (009 교착상태 참조) 잘못된 동기화 제어가 유발하는 교착상태
- 우선순위 역전(Priority Inversion) - 뮤텍스 점유로 인해 발생하는 성능 문제

# 📝 【답안용】 시험 답안 템플릿

## 핵심 인사이트 (3줄 요약)

> 1. **본질**: 세마포어, 뮤텍스, 모니터는 병행 처리 환경에서 공유 데이터의 무결성을 보장하기 위해 상호 배제(Mutual Exclusion)를 달성하는 OS 및 언어 수준의 동기화 기법이다.
> 2. **가치**: Busy Waiting으로 인한 CPU 자원 낭비를 Sleep-Wakeup 메커니즘으로 해결하고, 경쟁 상태를 방지하여 시스템의 신뢰성을 보장한다.
> 3. **판단 포인트**: 세 기법은 소유권(Ownership)의 유무와 프로그래머의 개입 수준(명시적 호출 vs 언어 차원 캡슐화)에서 차이가 나며, 시스템 복잡도와 개발 안전성 측면에서 트레이드오프를 갖는다.

## Ⅰ. 개요 및 필요성

- 개요: 세마포어·뮤텍스·모니터는 다중 프로세스/스레드 환경에서 임계 구역에 대한 배타적 접근을 제어하여 데이터 무결성을 보장하는 동기화 메커니즘
- 배경: 공유 자원 동시 접근 시 발생하는 경쟁 상태(Race Condition)를 막기 위한 H/W 명령어(Test-And-Set)는 Busy Waiting으로 CPU 낭비 초래
- 필요성: CPU 사이클 낭비를 막는 Sleep-Wakeup 구조를 제공하고, 개발 복잡도를 낮추어 교착상태(Deadlock) 등 치명적 오류를 방지하기 위해 필수적

---

## Ⅱ. 구조 및 구성요소

```text
프로세스 A (P 연산 호출) -> [Lock 확인: 사용 중] -> Wait Queue 블로킹 (Sleep)
                                                        |
프로세스 B (임계 구역 완료) -> V 연산 호출 -> [Lock 반환] -> Wait Queue 프로세스 Wakeup -> Ready Queue
```

| 기법 | 핵심 구성요소 | 역할 및 특이사항 |
|:---|:---|:---|
| 세마포어 (Semaphore) | 정수 변수 $S$, 대기 큐 | P(Wait)/V(Signal) 연산으로 정수 카운트를 증감, 소유권 개념 없음 |
| 뮤텍스 (Mutex) | Lock 상태(0/1), Owner 정보 | 이진 상태를 가지며, **반드시 Lock을 획득한 스레드만 Unlock 가능** |
| 모니터 (Monitor) | 캡슐화된 데이터·메서드, Condition 변수 | 컴파일러가 임계 구역 진입 통제를 자동 처리하여 프로그래머 오류 차단 |

> 요약: 세마포어는 자원의 가용 개수를 정수로 관리하며, 뮤텍스는 1:1 소유권을 강제하고, 모니터는 객체 캡슐화를 통해 안전성을 극대화한다.

---

## Ⅲ. 동작원리 및 흐름도

```text
임계 구역 진입 요청 -> Lock/카운트 가용성 검사
  / 가용 시: Lock 획득/카운트 차감 -> 임계 구역 실행 -> Lock 반환/카운트 증가 -> 대기자 Wakeup
  / 불가 시: 자신의 상태를 Blocked로 변경 -> 대기 큐 진입 (Context Switching)
```

- 1단계 [진입 요청 및 검사]: 임계 구역 진입 전 `P(S)` 또는 `lock()`을 호출하여 자원 가용 여부 확인
- 2단계 [가용성 판단 및 블로킹]: 가용(S>0) 시 S를 차감하고 진입, 불가(S≤0) 시 프로세스의 PCB를 Wait Queue에 넣고 CPU 반환(Sleep)
- 3단계 [임계 구역 실행]: 배타적 권한을 가지고 공유 데이터 읽기/쓰기 작업 수행
- 4단계 [반환 및 Wakeup]: 작업 완료 후 `V(S)` 또는 `unlock()` 호출 시 자원을 반납하고, Wait Queue의 프로세스를 Ready 상태로 전환

> 요약: 자원이 가용하지 않으면 루프를 돌며 대기(Busy Waiting)하는 대신, OS 큐에서 Sleep 상태로 전환하여 CPU 활용도를 높인다.

---

## Ⅳ. 특징
- 오버헤드: 상태 전이(Running → Blocked → Ready)에 따른 컨텍스트 스위칭 오버헤드 발생 (짧은 대기에는 비효율적)
- 의존성 체인: 자원 획득 대기로 인해 여러 스레드 간의 락(Lock) 체인이 형성되며, 이는 교착상태의 잠재적 원인
- 소유권 제어(뮤텍스): 뮤텍스는 Lock 소유자를 추적하므로, 우선순위 상속(Priority Inheritance) 같은 데드락 방지 프로토콜 구현 가능

> 요약: 효율적인 상호 배제를 달성하나, 잘못 사용 시 교착상태나 우선순위 역전 등의 심각한 성능 지연을 유발할 수 있다.

## Ⅴ. 심화 비교 및 적용 판단

| 비교 축 | 세마포어 (Semaphore) | 뮤텍스 (Mutex) | 모니터 (Monitor) | 선택 기준 |
|:---|:---|:---|:---|:---|
| 자원 한도 | N개 (Counting 가능) | 1개 (Binary 고정) | 1개 (구조체 캡슐화) | 동시 접근 가능 자원의 수량 |
| 소유권(Ownership) | 없음 (A가 P, B가 V 가능) | **있음** (A가 Lock, A가 Unlock) | 있음 (언어 차원 보장) | 동기화 오류 방지의 강도 |
| 적용 수준 | OS / 커널 레벨 기능 | OS / 애플리케이션 라이브러리 | 프로그래밍 언어 (Java, C#) | 개발 언어의 지원 여부 및 성능 요구 |

> 요약: 다중 인스턴스 자원은 세마포어, 엄격한 1:1 보호는 뮤텍스, 개발 복잡도를 낮추어 안전성을 높일 때는 모니터를 선택한다.

**리스크·대응:**
- 우선순위 역전(Priority Inversion): 하위 스레드가 Lock을 쥐어 상위 스레드가 대기하는 상태에서 중위 스레드가 선점 시 무한 지연 발생 → 하위 스레드 우선순위를 상위 스레드만큼 일시 상향하는 **우선순위 상속(Priority Inheritance Protocol)** 적용 (지표: 상위 스레드 응답 지연 시간)
- 교착상태(Deadlock): 복수의 Lock을 교차 점유하여 무한 대기 → Lock 획득 순서를 계층화하여 환형 대기 차단, Timeout 설정

**도입 후 점검 지표:**
- 성능/효율: Lock 대기 시간율(Wait Time Ratio) 및 컨텍스트 스위칭 발생 빈도 측정 (APM 프로파일링)
- 품질/운영: Thread Dump 분석을 통한 Deadlock 탐지 여부 (발생 0건 목표)

## Ⅵ. 실무 적용 및 결론

**적용 방안 3개:**
1. 데이터베이스 커넥션 풀 통제: Counting 세마포어를 활용하여 풀(Pool) 내의 커넥션 개수(N개)만큼만 스레드 접근을 허용하고 이후 요청은 큐잉 처리
2. 실시간 시스템 데드락 방지: RTOS(Real-Time OS) 환경에서는 뮤텍스를 사용하되, 반드시 PCP(Priority Ceiling Protocol)를 적용하여 우선순위 역전 리스크 차단
3. 애플리케이션 상태 안전성 확보: 자바 등 OOP 환경의 비즈니스 로직에서는 명시적 Lock() 호출 대신, `synchronized` 구문을 통한 모니터 패턴을 우선 적용하여 개발자 실수로 인한 Unlock 누락 방지

**결론 (2줄):**
- 기술사 판단: 뮤텍스와 세마포어는 소유권에 근본적 차이가 있으므로, 단일 객체 보호 시에는 뮤텍스를 사용하고 소유자를 추적해 우선순위 상속을 보장해야 한다.
- 향후 방향: 멀티코어 환경이 대중화됨에 따라 Lock 기반 동기화의 컨텍스트 스위칭 비용이 성능 병목이 되고 있으므로, Lock-Free 자료구조나 STM(Software Transactional Memory)으로 발전해야 한다.
