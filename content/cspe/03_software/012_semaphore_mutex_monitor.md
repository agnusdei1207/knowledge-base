# 📖 【암기용】 개념 완전 이해

## 한눈에
- **동기화 (Synchronization)**: 여러 프로세스/스레드가 공유 자원에 동시 접근할 때 데이터의 일관성을 유지하는 기술.
- **뮤텍스 (Mutex)**: 락(Lock)을 가진 자만이 자원을 쓸 수 있는 **'상호 배제'** 도구. (Key가 1개인 화장실)
- **세마포어 (Semaphore)**: 가용한 자원의 개수를 나타내는 카운터를 가진 **'신호기'**. (자리가 N개인 주차장)
- **모니터 (Monitor)**: 세마포어의 복잡함을 해결하기 위해 프로그래밍 언어 차원에서 제공하는 **'고수준 동기화 객체'**. (자동으로 문이 잠기는 안전한 방)

## 깊이 이해
- **뮤텍스 vs 바이너리 세마포어**:
    - 뮤텍스는 **소유권(Ownership)**이 있음. 락을 건 놈만 풀 수 있음.
    - 세마포어는 소유권이 없음. A가 기다리고(Wait), B가 신호를 보낼(Signal) 수 있음.
- **P/V 연산 (by Dijkstra)**:
    - **P (Proberen, Test/Wait)**: 자원을 사용하기 전 값을 감소시킴. 0보다 작으면 대기.
    - **V (Verhogen, Increment/Signal)**: 사용 후 값을 증가시킴. 대기 중인 놈을 깨움.
- **모니터의 위력**: 세마포어는 `P()`와 `V()`를 직접 호출해야 해서 실수(예: 둘 다 P를 하거나 V를 빼먹음)하면 데드락이 걸림. 모니터는 메서드에 `synchronized`만 붙이면 알아서 관리해줌. (Java의 핵심 동기화 기법)
- **Condition Variable**: 모니터 안에서 특정 조건을 기다릴 때 쓰는 대기실. `wait()`, `notify()`로 관리.

## 연결 개념
- **Critical Section (014)**: 동기화 도구들이 보호하려는 실제 코드 영역.
- **Spinlock vs Mutex (013)**: 기다릴 때 잠잘 것인가(Mutex), 계속 확인할 것인가(Spinlock).
- **Deadlock (009)**: 동기화 도구를 잘못 썼을 때 발생하는 최악의 상황.

# 📝 【답안용】 시험 답안 템플릿

## 핵심 인사이트 (3줄 요약)
> 1. **본질**: 공유 자원 접근에 따른 **Race Condition**을 방지하고 데이터의 **원자성(Atomicity)**과 일관성을 보장하기 위한 메커니즘임.
> 2. **기술적 핵심**: 뮤텍스는 '소유권' 기반의 상호 배제, 세마포어는 '카운트' 기반의 자원 관리, 모니터는 '추상화'를 통한 프로그래밍 편의성을 제공함.
> 3. **판단**: 낮은 레벨의 제어와 가벼운 성능이 필요하면 뮤텍스/세마포어를, 개발 생산성과 안정성이 중요하면 모니터를 선택함.

## Ⅰ. 병행 제어의 3대장, 동기화 도구의 개요
- **정의**: 다중 스레드 환경에서 공유 자원에 대한 동시 접근을 제어하여 임계 구역(Critical Section) 문제를 해결하는 기술적 수단.
- **목적**: 상호 배제(Mutual Exclusion) 보장, 진행(Progress) 보장, 한정 대기(Bounded Waiting) 보장.

## Ⅱ. 뮤텍스, 세마포어, 모니터 비교 분석

### 1. 기술적 특성 비교표
| 구분 | 뮤텍스 (Mutex) | 세마포어 (Semaphore) | 모니터 (Monitor) |
|:---:|:---|:---|:---|
| **정의** | Binary 공유 자원 관리 | 정수형(N) 카운터 기반 신호 | ADT 기반 고수준 동기화 |
| **핵심 기제** | Lock / Unlock | P(Wait) / V(Signal) | Entry Queue / Condition Variable |
| **소유권** | 있음 (Owner 존재) | 없음 (누구나 해제 가능) | 자동 관리 (언어 레벨) |
| **적용 범위** | 스레드 간 상호 배제 | 프로세스/스레드 간 동기화 | 객체 지향 프로그래밍 (Java 등) |
| **복잡도** | 낮음 | 중간 (실수 가능성 높음) | 낮음 (캡슐화) |

### 2. 세마포어 P/V 연산 메커니즘 (Pseudo Code)
```c
P(S) {
    while (S <= 0) ; // 대기 (Busy-wait or Block)
    S--;
}

V(S) {
    S++;
    // 대기 중인 프로세스 하나를 깨움
}
```

## Ⅲ. 모니터(Monitor)의 구조와 동작 원리

### 1. 모니터 내부 구조
- **Shared Data**: 외부 접근이 차단된 보호 자원.
- **Operations**: 자원에 접근하는 유일한 통로 (메서드).
- **Entry Queue**: 모니터 진입을 위해 대기하는 큐 (한 번에 하나만 진입).
- **Condition Variables**: 특정 조건 충족 시까지 대기하는 큐 (`wait()`, `signal()`).

### 2. 모니터의 장점
- **캡슐화**: 데이터와 동기화 로직을 하나로 묶어 코드 가독성 향상.
- **안전성**: 세마포어의 고질적 문제인 `P/V` 호출 누락 등을 컴파일러 수준에서 방지.

## Ⅳ. 동기화 도구 선택 기준 및 실무 고려사항

1. **상호 배제만 필요한 경우**: 가장 가벼운 **뮤텍스** 권장.
2. **자원 개수가 여러 개인 경우**: **Counting Semaphore** 필수.
3. **Producer-Consumer 문제**: **세마포어**나 **모니터**를 통해 빈 버퍼와 채워진 버퍼를 신호로 관리.
4. **데드락 방지**: 락 획득 순서 강제, `tryLock` 등을 이용한 타임아웃 적용.

## Ⅴ. 기술적 심화: 하드웨어적 동기화 원리
- **CAS (Compare-And-Swap)**: 메모리 값과 기대값을 비교하여 같을 때만 새 값으로 교체하는 원자적 명령. 뮤텍스나 Lock-free 자료구조의 근간.
- **TSL (Test-and-Set Lock)**: 특정 메모리 영역을 읽고 동시에 1로 세팅하는 원자적 하드웨어 명령어.

## Ⅵ. 기술사 관점의 결론 및 제언
- 동기화 도구의 오용은 **데드락**이나 **우선순위 역전** 같은 치명적 결함을 야기함.
- **실무 제언**: 가급적이면 락의 범위를 최소화하고, 최신 프로그래밍 언어에서 제공하는 **Concurrent Collection**이나 **불변 객체(Immutable Object)** 패턴을 활용하여 '락 없는 동기화'를 지향하는 것이 시스템 확장성(Scalability) 측면에서 유리함.
