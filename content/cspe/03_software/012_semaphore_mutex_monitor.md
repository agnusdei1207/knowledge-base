## Ⅰ. 개요
- **정의**: 공유 자원에 대한 동시 접근을 제어하는 세 가지 동기화 기법
- **배경/필요성**: 다중 프로세스/스레드 환경에서 경쟁 조건을 방지하려면 상호 배제를 보장하는 동기화 메커니즘이 필요함
- **비유**: 화장실 열쇠(뮤텍스), 주차장 카운터(세마포어), 안내 데스크(모니터)에 비유할 수 있음

| 출제 의도 | 반드시 짚을 핵심 | 감점 회피 포인트 |
|:---|:---|:---|
| 세 기법의 차이와 적용 상황 구분 | 소유권 유무, 카운터 범위, 캡슐화 수준 | 세마포어와 뮤텍스를 동일시하지 않을 것 |

> 요약: 상호 배제와 동기화를 구현하는 세 기법의 메커니즘 차이를 이해하는 것이 핵심임

## Ⅱ. 구성요소
```text
Semaphore          Mutex             Monitor
+-----------+    +-----------+    +-----------+
| counter S |    | owner     |    | procedure |
| wait()    |    | lock()    |    | condition |
| signal()  |    | unlock()  |    | wait/signal|
+-----------+    +-----------+    +-----------+
```

| 구성요소 | 설명 | 비유 |
|:---|:---|:---|
| Semaphore | 정수 카운터 기반으로 N개 자원의 동시 접근을 제어하는 기법 | 주차장 빈자리 카운터 |
| Mutex | 소유권 개념이 있어 잠근 스레드만 해제 가능한 이진 잠금 | 열쇠를 가진 사람만 여는 문 |
| Monitor | 공유 데이터와 접근 절차를 하나의 모듈로 캡슐화한 고수준 동기화 구조 | 접수처에서 순서대로 안내 |

> 요약: 카운터 기반(세마포어), 소유권 기반(뮤텍스), 캡슐화 기반(모니터)으로 구분됨

## Ⅲ. 절차
```text
Thread 요청 -> 동기화 객체 획득 시도 -> 임계 구역 진입 -> 작업 완료 후 해제
```
- 1단계: 스레드가 공유 자원 접근을 위해 동기화 객체에 획득 요청을 보냄
- 2단계: 세마포어는 카운터 감소, 뮤텍스는 소유권 확인, 모니터는 진입 큐에서 대기함
- 3단계: 획득 성공 시 임계 구역에 진입하여 공유 자원을 사용함
- 4단계: 작업 완료 후 동기화 객체를 해제하고 대기 중인 스레드에 신호를 전달함

> 요약: 획득-진입-사용-해제의 4단계로 임계 구역 접근을 직렬화하는 절차임

## Ⅳ. 문제점
- 세마포어 오용: `wait()`/`signal()` 순서를 잘못 사용하면 교착 또는 상호 배제 위반이 발생함
- 뮤텍스 우선순위 역전: 저우선순위 스레드가 잠금을 보유한 상태에서 고우선순위 스레드가 차단됨
- 모니터 이식성 한계: 언어 수준 지원이 필요하여 지원하지 않는 환경에서는 사용이 불가함

> 요약: 오용 위험, 우선순위 역전, 언어 종속성이 주요 한계임

## Ⅴ. 개선방안
1. 단기: 세마포어 사용 시 RAII 패턴을 적용하여 해제 누락을 구조적으로 방지함
2. 중기: 우선순위 상속(Priority Inheritance) 프로토콜을 뮤텍스에 적용하여 역전을 해소함
3. 장기: 언어 독립적 동기화 추상 계층(예: lock-free 자료구조)을 도입하여 이식성을 확보함

> 요약: RAII 패턴, 우선순위 상속, lock-free 구조로 각 한계를 해소할 수 있음

## Ⅵ. 전망
- 발전 방향: lock-free, wait-free 알고리즘으로 잠금 기반 동기화의 병목을 제거하는 추세임
- 기술사적 판단: 하드웨어 CAS 명령어 지원 확대로 소프트웨어 동기화 기법의 패러다임이 전환 중임
- 기술사 제언: 시스템 특성에 따라 잠금 기반과 비잠금 기반 기법을 혼합 적용하는 설계가 필요함
