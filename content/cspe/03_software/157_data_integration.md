## Ⅰ. 개요
- **정의**: 이기종 데이터 소스를 하나의 일관된 뷰로 결합하여 활용 가능하게 하는 프로세스
- **배경/필요성**: 시스템 간 데이터 사일로가 분석·운영의 병목이 되므로 통합된 데이터 접근이 필요함
- **비유**: 여러 지류를 하나의 본류로 합류시키는 것과 같음

| 출제 의도 | 반드시 짚을 핵심 | 감점 회피 포인트 |
|:---|:---|:---|
| 통합 방식 비교 능력 | ETL/ELT, 가상화(155 참조), CDC(156 참조) 방식 구분 | 물리 통합과 논리 통합의 적용 시나리오 구분 |

> 요약: 분산된 데이터를 일관된 형태로 결합하여 분석·운영에 활용하는 프로세스임

## Ⅱ. 구성요소
```text
[소스 A] --+                              +-- [DW/데이터 레이크]
[소스 B] --+--> [통합 파이프라인] ------->+
[소스 C] --+        |                     +-- [분석/리포트]
               [변환 엔진]
                    |
              [오케스트레이터]
```

| 구성요소 | 설명 | 비유 |
|:---|:---|:---|
| 통합 파이프라인 | 추출-변환-적재 흐름을 실행하는 처리 체인 | 조립 라인 |
| 변환 엔진 | 스키마 매핑·정제·집계를 수행하는 모듈 | 원자재 가공기 |
| 오케스트레이터 | 파이프라인 실행 순서·의존성을 관리하는 스케줄러 | 공정 관리자 |
| 커넥터 | 소스·타겟 시스템별 접속을 추상화하는 어댑터 | 규격 변환 플러그 |

> 요약: 커넥터-변환엔진-오케스트레이터로 파이프라인을 구성·실행하는 구조임

## Ⅲ. 절차
```text
추출(Extract) --> 변환(Transform) --> 적재(Load) --> 검증
```
- 1단계: 추출 — 소스 시스템에서 전체 또는 변경분 데이터를 읽어옴
- 2단계: 변환 — 스키마 매핑·데이터 정제·비즈니스 규칙 적용을 수행함
- 3단계: 적재 — 변환된 데이터를 타겟 저장소에 기록함
- 4단계: 검증 — 건수 일치·무결성 체크로 적재 결과를 확인함

> 요약: 추출-변환-적재-검증의 4단계로 데이터를 통합함

## Ⅳ. 문제점
- 배치 지연: 대량 데이터 배치 처리 시 최신 데이터 반영 지연 — 분석 적시성 저하
- 스키마 불일치: 소스 간 데이터 모델 상이 — 매핑 복잡도 증가 및 오류 유발
- 파이프라인 장애: 단일 단계 실패 시 후속 단계 연쇄 중단 — 복구 시간 증가

> 요약: 배치 지연, 스키마 불일치, 파이프라인 장애가 주요 문제임

## Ⅴ. 개선방안
1. 단기: CDC(156 참조) 도입으로 변경분 실시간 통합하여 지연 해소
2. 중기: 스키마 레지스트리 기반 자동 매핑으로 불일치 대응 자동화
3. 장기: 재시도·체크포인트 기반 장애 복구 자동화 아키텍처 구축

> 요약: 실시간 통합, 스키마 자동화, 장애 복구 자동화로 개선이 필요함

## Ⅵ. 전망
- 발전 방향: 데이터 패브릭 내 물리·논리 통합의 하이브리드 방식 확산
- 기술사적 판단: ELT 패턴이 클라우드 DW 환경에서 ETL 대비 채택률 증가 추세
- 기술사 제언: 통합 전략 수립 시 워크로드 특성별로 ETL·ELT·가상화를 구분 적용할 필요
