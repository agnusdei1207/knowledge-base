# 📖 【암기용】 개념 완전 이해

> 목적: ETL/ELT 파이프라인을 처음 보는 사람도 완벽히 이해하게 만든다. 시험 답안 양식이 아니라, 이해를 위한 친절한 설명이다.

## 한눈에
- **개요**: ETL/ELT는 **데이터 파이프라인**에서 원천 데이터를 목적지로 옮기는 두 가지 처리 순서로, **변환(Transform)**을 적재 전에 하느냐(ETL) 후에 하느냐(ELT)로 나뉜다.
- **왜 필요한가**: 운영 DB의 원천 데이터는 형식이 제각각이고 정제되지 않아, 분석·리포트·AI 학습에 그대로 쓸 수 없다. 형식 변환, 정제, 집계, 품질 검사를 거쳐야 신뢰할 수 있는 데이터가 된다.
- **핵심 직관**: ETL은 주방에서 손질한 뒤 창고에 넣고, ELT는 재료를 창고에 먼저 넣은 뒤 창고 안에서 손질하는 방식이다.

## 핵심 용어 정리 (내부에 등장하는 것들)

| 용어 | 의미 | 비유 |
|:---|:---|:---|
| 데이터 파이프라인 | 데이터가 원천에서 목적지까지 자동으로 흐르도록 연결한 처리 흐름 전체 — ETL/ELT는 그 하위 처리 방식 | 공장의 생산 라인 |
| Extract(추출) | 원천 시스템에서 데이터를 읽어오는 단계 | 창고에서 원자재 반입 |
| Transform(변환) | 정제·조인·집계·표준화 등 데이터 형태를 바꾸는 단계 | 원자재 가공 |
| Load(적재) | 변환된(또는 원본) 데이터를 목적지 저장소에 쓰는 단계 | 완제품 입고 |
| CDC(Change Data Capture) | 원천의 변경분(추가·수정·삭제)만 실시간에 가깝게 감지해 가져오는 기법 | 통장의 입출금 내역만 확인 |
| full / incremental extract | 매번 전체를 다 가져오는 방식 vs 변경분만 가져오는 방식 | 전체 재고조사 vs 오늘 입출고만 확인 |
| raw / staging / mart (bronze/silver/gold) | 원본 그대로(raw) → 정제 중간(staging) → 분석용 최종(mart) 3단계 저장 영역 | 원자재 창고 → 반제품 창고 → 완제품 매장 |
| idempotent load(멱등 적재) | 같은 작업을 여러 번 실행해도 결과가 중복되지 않고 항상 같은 상태가 되는 적재 방식 | 같은 서류를 여러 번 제출해도 접수는 한 번만 처리 |
| watermark | 어디까지 처리했는지 표시해두는 기준점(주로 시간·ID) | 책갈피 |
| partition pruning | 쿼리 시 필요한 파티션(예: 특정 날짜)만 읽어 스캔량을 줄이는 최적화 | 서랍 전체를 안 뒤지고 필요한 서랍만 엶 |

## 깊이 이해

### 왜 ETL이 먼저였고 ELT가 나중에 나왔나 (배경)
전통적인 온프레미스 DW는 저장 공간과 연산 자원이 비싸고 한정적이었다. 그래서 지저분한 원본을 그대로 넣기보다, 별도의 변환 서버에서 미리 정제·요약한 뒤 필요한 결과만 DW에 적재하는 ETL이 주류였다. 클라우드 DW와 레이크하우스는 저장(스토리지)과 연산(컴퓨트)을 분리해 저장 비용이 훨씬 저렴해졌고, DW/Lake 자체의 연산 성능도 커졌다. 그래서 "일단 원본을 다 저장해두고, 필요할 때 DW/Lake 안에서 SQL·dbt·Spark로 변환"하는 ELT가 가능해지고 널리 퍼졌다.

### 처리 위치가 왜 중요한가 — 구체 예시
일 1억 건씩 쌓이는 로그를 예로 들면: ELT 방식에서는 우선 S3 같은 객체 스토리지의 raw 영역에 원본을 그대로 적재한다. 이후 Spark/dbt가 그 raw 데이터를 읽어 bronze(원본에 가까운 정제)→silver(표준화·조인)→gold(집계·마트) 순서로 DW/Lake 내부에서 단계적으로 변환한다. 고객 마트는 매일 T+1(다음날) 06:00까지 만들어지는 것을 SLA로 정한다. ETL 방식이었다면, 이 변환을 별도의 전용 변환 서버에서 먼저 끝낸 뒤에야 DW에 적재하므로, 변환 서버가 병목이 되면 전체 파이프라인이 지연된다.

### CDC와 watermark — 왜, 어떻게 증분만 가져오나
원천 테이블 전체를 매번 다시 읽는 full extract는 데이터가 커질수록 시간과 부하가 기하급수적으로 늘어난다. CDC는 원천 DB의 트랜잭션 로그(binlog 등)를 읽어 "무엇이 바뀌었는지"만 뽑아낸다. 이때 "어디까지 이미 처리했는지"를 watermark(예: 마지막으로 처리한 트랜잭션 시각이나 ID)로 기록해두고, 다음 실행은 그 watermark 이후 것만 가져온다. CDC lag(원천 변경 발생 시점과 파이프라인이 반영하는 시점의 차이)를 5분 이하로 두는 식으로 SLA를 정한다.

### idempotent load가 왜 필요한가
파이프라인은 네트워크 오류나 재시도로 같은 배치가 두 번 실행될 수 있다. 단순 INSERT(추가)만 하면 재실행 시 같은 레코드가 중복 저장된다. idempotent load는 "이 키가 이미 있으면 덮어쓰고, 없으면 추가"하는 merge/upsert 방식을 써서, 같은 작업을 몇 번을 재실행해도 최종 결과가 항상 동일하게 만든다. 이 성질이 없으면 실패 후 재시도 자체가 위험해진다.

### 판별 원리 — ETL과 ELT 중 무엇을 고르나
개인정보처럼 적재 전에 반드시 마스킹해야 하는 데이터, 원천 시스템 부하를 최소화해야 하는 경우는 변환을 먼저 끝내고 결과만 적재하는 ETL이 맞다. 반대로 원본을 보존해 나중에 다른 방식으로 재처리(backfill)하거나 ad-hoc 분석이 잦은 경우, 그리고 클라우드 DW의 연산력을 활용하고 싶은 경우는 ELT가 유리하다. 실무에서는 두 방식을 함께 쓰기도 한다(민감 컬럼만 적재 전 마스킹하는 ETL 처리 + 나머지는 ELT).

### 비유
이사할 때 짐을 미리 종류별로 분류해서 트럭에 싣는 방식이 ETL이고, 일단 모든 짐을 새 집(창고)에 옮겨놓은 뒤 창고 안에서 천천히 정리하는 방식이 ELT다. 짐이 적으면 미리 분류하는 게 낫지만, 짐이 아주 많고 새 집 공간이 넉넉하면 일단 옮겨놓고 정리하는 편이 이사(적재) 자체를 빨리 끝낼 수 있다.

### 흔한 오해
ELT가 항상 우월한 방식은 아니다. 개인정보 마스킹이 적재 전에 반드시 필요한 경우, 원천 시스템에 부하를 주면 안 되는 경우, 네트워크 전송 비용이 큰 경우, 변환 결과의 재현성을 엄격히 통제해야 하는 경우는 여전히 ETL이 더 적합하다.

## 연결 개념
- 데이터 파이프라인 오케스트레이션 — 작업 순서와 실패 재시도 관리
- 데이터 품질 관리 — 변환 전후 검증 규칙이 실행되는 지점
- 레이크하우스 — ELT의 변환이 실제로 실행되는 기반 플랫폼

# 📝 【답안용】 시험 답안 템플릿

> 목적: 시험장에서 25분에 그대로 쓰는 답안 양식. 작성방식(추상표현 금지·수치·도식·문제유형 전환)을 엄격히 지킨다.
> 핵심: ETL/ELT 답안은 순서 차이뿐 아니라 처리 위치, 원본 보존, 비용, 품질 검증, 개인정보 처리 기준을 비교해야 한다.

## 핵심 인사이트 (3줄 요약)

> 1. **본질**: ETL은 적재 전 변환, ELT는 적재 후 변환하는 데이터 파이프라인 처리 방식임.
> 2. **가치**: 원천 데이터를 분석 모델에 맞게 정제, 표준화, 집계하고 SLA와 품질 지표로 관리함.
> 3. **판단 포인트**: 데이터 민감도, 원천 부하, 변환 복잡도, 클라우드 DW 처리 비용을 기준으로 ETL/ELT를 선택함.

## 출제 의도 및 답안 포인트

| 출제 의도 | 반드시 짚을 핵심 | 감점 회피 포인트 |
|:---|:---|:---|
| ETL/ELT 차이 이해 확인 | Extract, Transform, Load 순서와 처리 위치 | 순서만 쓰고 선택 기준 누락 |
| 데이터 플랫폼 설계 판단 확인 | raw/staging/mart, 품질 검사, 재처리 | 단순 배치 작업으로 축소 |
| 운영 위험 확인 | 중복 적재, 지연, 스키마 변경, PII | SLA와 DQ 지표 누락 |

> 요약: ETL/ELT 문제는 처리 순서보다 어떤 조건에서 어떤 방식을 선택하는지가 채점 포인트임.

## Ⅰ. 개요 및 필요성

- 개요: ETL/ELT는 분석 데이터 처리 파이프라인 방식임.
- 배경: 운영 데이터는 분석 목적에 맞게 추출, 정제, 적재, 집계되어야 한다.
- 필요성: 데이터 품질 규칙, 재처리 절차, SLA, 비용 기준으로 분석 데이터 생성 과정을 통제한다.

---

## Ⅱ. 구조 및 구성요소

```text
Source -> Extract -> Transform -> Load -> DW/Mart
Source -> Extract -> Load Raw -> Transform in DW/Lake -> Mart
```

| 구성요소 | 역할 | 특이사항 |
|:---|:---|:---|
| 추출 | DB, API, 파일, CDC에서 데이터 확보 | full/incremental/CDC |
| 변환 | 정제, 조인, 집계, 표준화 | SQL, Spark, dbt |
| 적재 | raw, staging, mart 저장 | partition, merge, upsert |
| 검증 | 건수, 합계, null, 중복 검사 | DQ rule, reconciliation |

> 요약: ETL/ELT는 추출, 변환, 적재, 검증의 순서와 실행 위치가 다른 파이프라인 구조임.

---

## Ⅲ. 동작원리 및 흐름도

```text
원천 변경 감지 -> 증분 추출 -> 원본 보관 -> 변환/품질 검사 -> 마트 적재 -> SLA 확인
```

| 단계 | 처리 내용 | 검증 기준 |
|:---:|:---|:---|
| 1 | 원천 변경 감지와 추출 | CDC lag 5분 이하 |
| 2 | raw 영역 적재 또는 변환 엔진 전달 | 중복 적재 0건 |
| 3 | 정제, 조인, 집계 수행 | null, range, referential rule |
| 4 | mart 적재와 파티션 갱신 | T+1 06:00 SLA |
| 5 | 건수/합계 대사와 로그 기록 | reconciliation gap 0.1% 이하 |

> 요약: 파이프라인은 변경 감지, 적재, 변환, 검증, SLA 확인의 순서로 운영됨.

---

## Ⅳ. 특징

| 구분 | ETL | ELT | 판단 포인트 |
|:---|:---|:---|:---|
| 처리 위치 | 전용 변환 서버 | DW/Lake 내부 | 클라우드 DW 자원 |
| 원본 보존 | 변환 결과 중심 | raw 데이터 보존 | 재처리 필요성 |
| 민감정보 | 적재 전 마스킹 가능 | raw 접근 통제 필요 | PII 등급 |
| 한계 | 변환 서버 병목 | 쿼리 비용 증가 | 작업별 비용 태깅 |

> 요약: ETL은 적재 전 통제, ELT는 raw 보존과 재처리에 유리하므로 데이터 민감도와 비용 기준으로 선택함.

## Ⅴ. 심화 비교 및 적용 판단

| 구분 | 기존/대안 | 본 키워드 | 선택 기준 |
|:---|:---|:---|:---|
| 구조 | 수동 SQL 배치 | 관리형 ETL/ELT | SLA 1일 1회 이상 |
| 비용/처리 | 고정 서버 | DW/Lake 연산 과금 | 스캔 비용, 파티션 설계 |
| 운영/위험 | 실패 후 수동 복구 | 재시도, backfill, DQ | 실패율 1% 이하 |

> 요약: ETL/ELT는 데이터 양보다 SLA, 재처리, 비용 통제 요구가 있을 때 설계 대상이 됨.

| 리스크 | 원인 | 대응 방안 | 확인 지표 |
|:---|:---|:---|:---|
| 지연 | 원천 부하, 대용량 조인 | 증분 처리, 파티션, pushdown | SLA miss 1% 이하 |
| 중복/누락 | watermark 오류 | idempotent load, checkpoint | duplicate 0건 |
| 비용 초과 | 전체 스캔 변환 | partition pruning, incremental model | query cost/job |

> 요약: 파이프라인 리스크는 지연, 중복/누락, 비용 초과이며 증분 처리와 멱등 적재로 통제함.

| 점검 항목 | 목표 기준 | 측정 방법 |
|:---|:---|:---|
| SLA | T+1 06:00 또는 CDC lag 5분 이하 | scheduler log |
| 품질 | reconciliation gap 0.1% 이하 | DQ report |
| 비용 | job별 스캔량 예산 이내 | warehouse billing tag |

> 요약: 운영 판단은 SLA, 품질 대사, job별 비용을 함께 확인해야 함.

## Ⅵ. 실무 적용 및 결론

**적용 방안 3개 (필수 - 단계별 또는 항목별):**
1. 처리 방식 선택: PII 적재 전 마스킹 필요 시 ETL, raw 재처리와 ad-hoc 분석 필요 시 ELT 선택
2. 증분 설계: CDC watermark, idempotent merge, partition key를 적용해 중복 0건과 backfill 가능 구조 확보
3. 검증 내장: row count, checksum, null/range rule, reconciliation gap 0.1% 기준을 Airflow/dbt 단계에 적용

**결론 (2줄):**
- 기술사 판단: 보안 통제가 먼저면 ETL, 클라우드 DW와 원본 재처리가 먼저면 ELT가 적합함
- 향후 방향: 배치 ETL/ELT는 스트리밍 CDC, 데이터 계약, 자동 품질 검증과 결합됨
