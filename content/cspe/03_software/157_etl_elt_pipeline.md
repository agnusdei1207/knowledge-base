## 핵심 인사이트 (3줄 요약)
- 밖에서 데이터를 예쁘게 가공한 뒤에 창고(DW)에 넣던 전통적인 **ETL(추출-변환-적재)** 방식이, 클라우드 시대가 열리며 일단 창고(Lake)에 다 때려 박고 창고 안에서 강력한 엔진으로 가공하는 **ELT(추출-적재-변환)**로 완전히 역전됨.
- 변환(Transform)을 밖에서 하느냐 안에서 하느냐의 작은 차이 같지만, 이는 '스토리지 비용 폭락'과 '클라우드 컴퓨팅 파워의 무한 확장성'이 만들어낸 빅데이터 아키텍처의 거대한 패러다임 시프트임.
- 현재는 dbt(data build tool) 같은 도구가 ELT의 'T'를 SQL만으로 완벽하게 제어하게 해주면서, ELT가 현대 데이터 스택(Modern Data Stack)의 확고한 글로벌 표준으로 자리 잡음.

## Ⅰ. 개요 및 필요성
- **개요**: 다양한 소스(운영 DB, 로그 등)에서 데이터를 추출(Extract)하여, 분석하기 좋은 형태로 변환(Transform)하고, 타겟 저장소에 적재(Load)하는 데이터 통합 파이프라인.
- **필요성**: 과거에는 데이터 웨어하우스(Oracle 등)의 디스크와 CPU가 100억 원이 넘을 만큼 너무 비쌌음. 그래서 비싼 DW 안에서 지저분한 변환 작업 하면 서버가 뻗으므로, 밖에서 값싼 별도의 중간 서버(ETL 툴)를 두고 깎고 다듬은 뒤에 "예쁜 데이터만 DW에 넣어주자"는 생존 전략에서 ETL이 탄생함.
---
## Ⅱ. 아키텍처 및 핵심 원리
- **1. ETL (Extract ➡️ Transform ➡️ Load)**:
  - **흐름**: 소스 DB ➡️ [별도의 ETL 변환 서버 (여기서 조인/필터링)] ➡️ 타겟 DW
  - **특징**: 데이터를 밖에서 가공하므로 타겟 DW의 부하가 적음. 하지만 변환 서버의 성능 한계가 전체 파이프라인의 병목이 되고, 원본 데이터(Raw)를 버리기 때문에 나중에 AI 학습용으로 쓸 원본이 안 남음.
- **2. ELT (Extract ➡️ Load ➡️ Transform)**:
  - **흐름**: 소스 DB ➡️ [타겟 데이터 레이크/DW (일단 원본 다 쏟아부음!)] ➡️ [DW 내부 엔진으로 가공]
  - **특징**: S3나 Snowflake 같이 스토리지는 거의 공짜고 CPU는 무한대로 늘어나는 클라우드의 장점을 100% 활용. 밖에서 가공 안 하고 그대로 복사해오니 수집 속도가 빛의 속도임. 원본이 100% 보존되므로 나중에 구조를 바꾸기 쉬움.
- **3. 현대 데이터 스택의 T (Transform) 혁명 (dbt)**:
  - ELT에서 'T'를 수행하려면 데이터베이스 안에서 복잡한 프로시저나 파이썬을 짜야 했음. 
  - **dbt(data build tool)**가 등장하면서, 일반 분석가도 `SELECT` SQL문만 짜면 알아서 의존성을 파악하고 타겟 DW 안에서 변환 작업을 자동화해 주며 ELT의 천하통일을 이룸.

```text
[ ETL과 ELT의 작업 방식 비교 ]

 ✂️ [ ETL (과거: 비싼 창고) ]
 1. 밭에서 감자를 캡니다 (Extract).
 2. 밖에서 싱크대(ETL 서버)를 하나 사서 흙을 다 씻고 껍질을 깝니다 (Transform). ➡️ [가장 오래 걸림]
 3. 비싼 냉장고(DW)에는 깨끗한 감자만 넣습니다 (Load).
 * 단점: 흙 묻은 원본 감자는 버렸기 때문에 나중에 흙이 필요해도 못 찾음.

 📦 [ ELT (현재: 클라우드 무한 창고) ]
 1. 밭에서 감자를 캡니다 (Extract).
 2. 엄청나게 넓고 싼 창고(S3/Snowflake)에 흙 묻은 감자를 덤프트럭으로 일단 다 때려 박습니다 (Load). ➡️ [초고속]
 3. 나중에 요리할 때, 창고 안에 있는 엄청나게 쎈 세척기(Spark/SQL 엔진)를 켜서 1초 만에 씻습니다 (Transform).
 * 장점: 원본 감자가 그대로 남아있어서 언제든 다른 요리 가능!
```

## Ⅲ. 비교 및 연결
| 구분 | ETL (Extract-Transform-Load) | ELT (Extract-Load-Transform) |
|---|---|---|
| **데이터 변환 위치**| 타겟 DB로 들어가기 전 (중간 서버) | **타겟 DB에 들어간 후 (내부 컴퓨팅)** |
| **원본 데이터 보존**| ❌ (변환 과정에서 원본 버려짐) | **⭕ (Data Lake에 원본 그대로 보존)** |
| **적합한 아키텍처** | 전통적 On-premise DW (비싼 스토리지) | **Cloud Data Lake / Lakehouse (싼 스토리지)** |
| **유연성 (수정)** | 파이프라인 앞단부터 다시 다 뜯어고쳐야 함 | **원본이 레이크에 있으므로 쿼리만 바꾸면 됨** |

## Ⅳ. 실무 적용 및 기술사 판단
- **Zero-ETL의 도래**: 최근 AWS 실무에서는 아예 Extract조차 없애버리는 'Zero-ETL'이 화두임. Amazon Aurora(운영 DB)에 데이터가 꽂히면, AWS 내부망을 통해 1초 만에 Amazon Redshift(DW)로 자동 복제됨. 기술사는 더 이상 Kafka나 Debezium으로 무거운 추출 파이프라인을 짤 필요 없이, 벤더(AWS)가 제공하는 Zero-ETL 통합 기능을 적극 활용하여 파이프라인 구축 비용을 극단적으로 낮춰야 함.
- **스트리밍 ETL (Streaming ETL)**: 기존 ELT가 매일 자정에 한 번 도는 배치(Batch) 위주였다면, 요즘엔 Flink를 이용해 "데이터가 흘러가는 파이프라인 공중에서 1초 만에 즉시 변환(Transform)"해 버리는 Streaming ETL 아키텍처를 사기 탐지(FDS)나 추천 시스템에 필수적으로 결합해야 함.

## Ⅴ. 기대효과 및 결론
- 데이터 엔지니어링의 병목을 '데이터 추출'에서 '분석 쿼리 작성(SQL)'으로 옮겨놓아, 비개발자(분석가)도 데이터 파이프라인을 직접 통제할 수 있는 시대를 염.
- 컴퓨팅과 스토리지를 완벽하게 분리한 클라우드 철학을 파이프라인에 그대로 이식하여, 무한대의 데이터(Data Lake)를 자유자재로 가공할 수 있는 현대 빅데이터 생태계의 대동맥임.

### 📌 관련 개념 맵
- Data Warehouse ➡️ ETL ➡️ 클라우드 (스토리지/컴퓨팅 분리) ➡️ Data Lakehouse ➡️ ELT 전환 ➡️ dbt (Transform)

### 📈 관련 키워드 및 발전 흐름도
- Informatica, DataStage 등 무거운 상용 ETL 시대 ➡️ S3, Snowflake 등장으로 스토리지 비용 폭락 ➡️ ELT(Extract-Load-Transform) 아키텍처로 패러다임 역전 ➡️ dbt의 등장 ➡️ Fivetran/Airbyte(추출) + dbt(변환)의 모던 데이터 스택 완성 ➡️ Zero-ETL 트렌드

### 👶 어린이를 위한 3줄 비유 설명
1. **ETL**은 마트에서 산 물건들을 집 밖에서 포장지를 다 뜯고, 빈 통에 예쁘게 담은 뒤에야 냉장고에 넣는 거예요. 밖에서 너무 오래 걸려요.
2. **ELT**는 클라우드 시대의 방법이에요. 마트에서 사 온 봉지째로 일단 엄청나게 큰 냉장고(데이터 레이크)에 다 쑤셔 넣어요!
3. 그리고 나중에 요리할 때 냉장고 안에서 포장지를 뜯고 요리하는 거예요. 짐 정리 속도가 엄청나게 빠르고, 나중에 반품(원본 데이터 확인)하기도 좋답니다!
