# 📖 【암기용】 개념 완전 이해

> 목적: 이 개념을 처음 보는 사람도 완벽히 이해하게 만든다. 시험 답안 양식이 아니라, 이해를 위한 친절한 설명이다.

## 한눈에
- **개요**: **CI/CD**는 개발자가 짠 코드를 사용자 스마트폰(운영 서버)까지 배달해 주는 **'초고속 자동 컨베이어 벨트'**다. 개발자가 코드 작성을 끝내고(Commit) "업로드!" 버튼만 누르면, 기계가 알아서 에러 검사(Test)하고, 압축(Build)해서, 라이브 서버에 밀어 넣는(Deploy) 과정을 사람이 1도 개입 안 하고 무인(자동)으로 끝낸다.
- **왜 필요한가**: 옛날에는 개발자가 코드를 다 짜면, 금요일 밤에 퇴근 안 하고 모여서 수동으로 서버에 파일을 복사해 넣었다. 그러다 오타 하나 나서 서버 터지면 주말 내내 서버실에서 울면서 복구했다(빅뱅 배포). 이걸 기계가 대신 매일매일 조금씩(자동으로) 올리게 해서 멘붕을 막는 거다.
- **핵심 직관**: 
  - **CI (지속적 통합)**: 코드 검사소. 여러 명이 짠 코드를 매일매일 한 바구니에 합쳐보고(Merge), "에러 안 나나?" 자동 테스트를 돌려본다. (버그 조기 발견).
  - **CD (지속적 배포/제공)**: 물류 센터. 검사를 무사히 통과한 코드를 포장(Docker Image)해서, 클라우드 운영 서버로 냅다 쏴버리는(Deploy) 로봇.

## 깊이 이해
- **배경·문제의식**: 기획팀이 "이 버튼 색깔 빨리 좀 빨간색으로 바꿔줘"라고 했는데, 개발팀이 "이번 달 릴리즈(배포)는 끝났고 한 달 뒤에나 나갑니다"라고 하면 회사는 망한다. 모바일 시대에는 경쟁사가 하루에 10번씩 기능을 찍어내기 때문이다. **Time-to-Market(시장 출시 속도)**을 극단적으로 줄이려면 인간이 수동으로 배포하는 시간을 기계(DevOps)로 삭제해야 했다.
- **작동 원리 (파이프라인 5단계 흐름)**:
  1. **Commit (코드 저장)**: 개발자가 깃허브(Git)에 코드를 올림.
  2. **Build (조립)**: 젠킨스(Jenkins)나 GitHub Actions 봇(Bot)이 그걸 낚아채서 압축파일(Jar)로 만듦. (여기서 문법 틀렸으면 빌드 터지면서 빨간불 삐용삐용 들어옴).
  3. **Test (검사)**: 미리 짜둔 자동화 테스트 코드(JUnit) 1,000개가 미친 듯이 돌아가서 버그가 있는지 검사함.
  4. **Package (포장)**: 에러가 없으면 이 코드를 도커(Docker) 컨테이너로 예쁘게 포장함.
  5. **Deploy (배달)**: 포장된 상자를 AWS 서버에 냅다 꽂아 넣고 서버를 새로 고침 시킴.
- **비유**: 
  - 수제 자동차 공방(과거) vs 현대 포드 컨베이어 벨트(CI/CD). 나사 하나 조이고(Commit), 기계가 불량 체크하고(Test), 엔진 조립하고(Build), 매장에 전시한다(Deploy). 인간은 코딩만 하면 컨베이어 벨트가 알아서 상품으로 내보낸다.
- **구체 예시**: 넷플릭스, 아마존 개발자들은 하루에 수천 번씩 라이브 서버에 코드를 배포한다. 
- **흔한 오해·주의점**: "CD가 도구 이름인가요?" 아니다. Jenkins, GitLab CI, GitHub Actions 같은 건 '도구'고, CI/CD는 그 도구들을 이어 붙여서 만든 **'파이프라인(개념)'**이다. 

## 연결 개념
- **DevOps (데브옵스)**: "개발(Dev)과 운영(Ops)을 합쳐버리자!"는 철학. 옛날엔 개발자가 코드 짜서 던지면 운영팀이 손으로 배포했다. DevOps는 그딴 거 없이 개발자가 코드 짜면 CI/CD 벨트가 알아서 운영 서버에 올려버리게 만드는 문화를 뜻한다.
- **무중단 배포 (Zero-downtime Deployment)**: 서버를 안 끄고 배포하는 마법(블루-그린, 카나리 배포). CD가 자동으로 배포할 때 사용자가 에러를 보지 않게 쓱 바꿔치기해 준다.

# 📝 【답안용】 시험 답안 템플릿

> 목적: 시험장에서 25분에 그대로 쓰는 답안 양식. 작성방식(추상표현 금지·수치·도식·문제유형 전환)을 엄격히 지킨다.
> 핵심: 이 시험은 정보를 많이 나열하는 시험이 아니라, 문제 신호어에서 출제자 의도를 읽고 핵심 논점을 선별해 쓰는 시험이다.

## 핵심 인사이트 (3줄 요약)

> 1. **본질**: 소스코드의 병합(Merge)부터 빌드, 테스트, 운영 서버 릴리즈에 이르는 소프트웨어 배포의 전 생명주기(SDLC)를 사람의 개입 없이 100% 기계가 수행하는(No-touch) 파이프라인 자동화 아키텍처다.
> 2. **가치**: 버그 발견 시점을 '운영 단계'에서 '빌드 단계'로 극단적으로 앞당겨(Shift-Left) 디버깅 비용을 소거하고, 하루 수십 번의 무중단 배포를 통해 애자일(Agile) 비즈니스의 극한 타임투마켓(Time-to-Market)을 달성한다.
> 3. **판단 포인트**: CI(빌드/테스트 자동화)와 CD(배포/릴리즈 자동화)의 개념적 구간을 분리 도식화하고, 이 무인 컨베이어 벨트를 완성하기 위한 '자동화 테스트 코드(TDD/Unit Test)의 커버리지'가 선결 조건임을 반드시 규명해야 한다.

## 출제 의도 및 답안 포인트

| 출제 의도 | 반드시 짚을 핵심 | 감점 회피 포인트 |
|:---|:---|:---|
| 수동 릴리즈(Big-bang)의 한계와 CI/CD 도입 목적 차이 | Time-to-Market 단축 및 버그 조기 식별 (Shift-Left) | 단순히 "Jenkins 툴을 쓰는 기술" 정도로 얕게 묘사하고 프로세스 관점 이탈 |
| 파이프라인의 물리적 구간(Phase) 및 자동화 흐름 매핑 | Code -> Build -> Test (CI) -> Release -> Deploy (CD) | CI 구간과 CD 구간의 목적 차이를 분리하지 못하고 뭉뚱그려 서술 |
| CI/CD 성공을 담보하는 필수 인프라 요건 방어 | **자동화된 단위 테스트(Test Automation) 없이는 불가** | 테스트 코드 없이 빌드만 기계가 대신해 준다고 오해하는 치명적 맹점 |

> 요약: 자동화 테스트(Test) 코드가 없는 CI/CD는 브레이크 없는 페라리다. 개발자가 똥(에러 코드)을 푸시했는데 젠킨스가 그걸 광속으로 라이브 서버에 퍼다 날라버리면, 회사가 5분 만에 파산하게 된다.

## Ⅰ. 개요 및 필요성

- 정의: **CI(Continuous Integration, 지속적 통합)**는 개발자들의 코드를 공유 레포지토리에 빈번히 병합하여 빌드/테스트를 자동화하는 것이며, **CD(Continuous Delivery/Deployment, 지속적 배포)**는 검증된 코드를 운영 환경까지 무인(Zero-touch)으로 릴리즈하는 데브옵스 핵심 파이프라인
- 배경: 과거 월 1회 진행되는 수동(Manual) 정기 배포는 수많은 브랜치 코드가 한 번에 엉켜(Merge Hell) 치명적 롤백 불가 사태를 낳았고, 배포를 위한 운영팀 야간작업(Human Error) 리스크 극대화
- 필요성: 사람이 손으로 FTP를 올려 배포하는 휴먼 에러를 0%로 소거하고, 비즈니스 신규 피처(Feature)를 고객에게 전달하는 리드 타임(Lead Time)을 수 주(Weeks)에서 수십 분(Minutes)으로 단축하기 위함

## Ⅱ. CI/CD 파이프라인 토폴로지: 흐름 제어 및 도식

코드가 깃허브에 들어오는 순간부터 라이브 서버에 박힐 때까지의 자동화 컨베이어 벨트.

```text
[ CI (지속적 통합 구간: 버그 조기 차단) ]           [ CD (지속적 배포 구간: 릴리즈 자동화) ]

(개발자)        (트리거)
 👨‍💻 --(Push)--> [ Git ] --(Webhook)--> [ Jenkins / GitHub Actions (자동화 서버 데몬) ]
                                            |
                  +-------------------------+-------------------------+
                  V                         V                         V
          [ 1. Build ]               [ 2. Test ]             [ 3. Package & Deploy ]
        (Maven/Gradle)            (JUnit, SonarQube)         (Docker Image Build)
        (소스코드 컴파일)           (단위/통합 테스트 1000개)         (AWS EKS 서버로 Push 🚀)
                  |                         |                         |
         (실패 시 Slack 알림 🚨)    (커버리지 80% 미만 시 차단 🚨)    (무중단 블루그린 배포 적용 ✅)
```

| 구간 (Phase) | 아키텍처적(엔지니어링) 통제 메커니즘 | 실무 품질 방어 효과 (Shift-Left) |
|:---|:---|:---|
| **CI (통합)** <br> : Build / Test | 개발자가 하루에 5번 코드를 섞는다(Commit). 서버(Jenkins)가 이를 낚아채 코드를 컴파일하고, 즉시 단위 테스트(Unit Test)를 수백 개 돌려 정합성을 검증 | **버그 조기 색출 (Shift-Left)**. 운영 서버 가기 전에 문법 오류나 로직 충돌을 파이프라인 단에서 터뜨려버림 (개발자 멱살 즉시 잡음) |
| **CD (배포)** <br> : Release | 테스트를 통과한 결점 없는 코드를 도커(Docker) 컨테이너 이미지로 구워내고 레지스트리(ECR)에 밀어 넣음(Push) | 테스트 서버(Staging)든 운영 서버(Prod)든 사람이 개입하지 않고 버튼 1릭으로 동일한(Immutable) 이미지가 불변 배포됨 |
| **CD (전개)** <br> : Deploy | Kubernetes나 AWS ECS에 훅(Hook)을 찔러넣어, 기존 살아있는 구형 서버를 내리고 신형 서버를 갈아 끼움 (무중단) | 서비스 중단(Downtime) 없이 매일 10번이라도 사용자 모르게 앱 기능 업데이트 완료 |

> 요약: CI/CD의 진짜 무서움은 "배포 속도"가 아니라 "강제력"에 있다. 주니어 개발자가 테스트 코드를 안 짰거나, 코드 품질(SonarQube) 점수가 낮으면 파이프라인 기계가 뱉어내 버린다. 기계가 꼰대 시니어 역할을 대신해 주는 것이다.

## Ⅲ. 극복해야 할 시스템적 리스크 (테스트 부재와 병목)

컨베이어 벨트는 튼튼한데, 벨트 위에 올라가는 부품(코드) 검사기가 망가지면 불량품이 빛의 속도로 양산된다.

| 리스크 요인 | 발생 시나리오 및 시스템 붕괴 원인 (안티패턴) | 아키텍처 대응 방안 (실무 튜닝) |
|:---|:---|:---|
| **테스트 없는 허구의 CI** <br> (Garbage In, Garbage Out) | 단위 테스트(Unit Test)를 1개도 안 짰는데 CI 파이프라인(Jenkins)만 화려하게 구축. 문법 오류만 없으면 무조건 '성공(Green)'을 띄워 치명적 논리 버그가 라이브 서버로 자동 배포됨 | **테스트 커버리지(Coverage) 임계치 강제 락인**: CI 파이프라인 설정(JaCoCo 등)에 `Coverage Minimum: 80%`를 박아넣어, 소스코드의 80% 이상을 테스트 코드가 감싸지 않으면 무조건 빌드 자체를 **Failed(실패)**로 터뜨려 배포 원천 차단 |
| **파이프라인 병목 지연** | 프로젝트가 커지면서 테스트 코드가 10,000개가 됨. 코드를 1줄 고쳤는데 CI 빌드 파이프라인 통과에 40분이 걸려 개발자들이 퇴근을 못 하고 병목(Bottleneck) 폭발 | **테스트 병렬화 및 캐싱(Caching) 튜닝**: 의존성 패키지(Node `node_modules`, Java `.m2`)를 캐시 처리하여 다운로드 시간을 증발시키고, 통합 테스트 모듈을 5개의 워커(Worker) 인스턴스로 찢어서 비동기 병렬(Parallel) 실행하여 파이프라인 속도 5분 이내 사수 |

> 요약: 자동 배포(CD)보다 천 배 더 중요한 게 자동 검사(CI Test)다. 테스트 자동화 인프라를 못 갖춘 스타트업은 절대 CD(자동 배포)를 켜선 안 된다. 인간이 수동으로 눈(QA)으로 검사하고 배포 버튼을 눌러야 한다.

## Ⅳ. 엔터프라이즈 데브옵스 진화: DevSecOps 융합망

코드만 빨리 배포하다 보면 해커가 심어놓은 백도어 코드까지 광속으로 배포된다.

| 진화 아키텍처 | 물리적 융합 메커니즘 (파이프라인 삽입) | 해결되는 보안 한계 |
|:---|:---|:---|
| **DevSecOps** <br> (보안 내재화) | 배포 완료 후 보안팀이 해킹 테스트를 하던 사후 검사(과거)를 버리고, **CI/CD 파이프라인 벨트 한가운데에 '보안 스캐너(SCA, DAST)' 로봇을 강제 배치** | 개발자가 암호(DB 비번)를 하드코딩하거나 구형 취약점(Log4j) 라이브러리를 임포트하면, **CI 빌드 로봇이 이를 적발해 빨간불을 켜고 파이프라인을 멈춰(블로킹) 배포 자체를 물리적으로 원천 방어** |

> 요약: 이제 보안팀은 엑셀로 체크리스트를 만들지 않는다. 대신 Jenkins 파이프라인 스크립트 안에 해킹 툴을 욱여넣는다. 기계(코드)를 이기려면 기계(보안봇)로 막아야 한다.

## Ⅴ. 실무 적용 방안 및 결론

**적용 방안 3개:**
1. [GitHub Actions 기반 클라우드 네이티브 서버리스 파이프라인] 기존의 무거운 설치형 Jenkins 서버(EC2) 유지보수 비용을 소거하기 위해, GitHub 레포지토리 내 `.github/workflows/` YAML 파일만으로 빌드/테스트/ECR 푸시까지 전 과정을 실행하는 GitHub Actions 서버리스 환경으로 마이그레이션(Zero-Ops 달성)
2. [SonarQube(소나큐브) 결합 코드 스멜(Code Smell) 자동 차단] CI 파이프라인의 `Test` 구간 직후에 정적 분석 툴(SonarQube)을 연동시켜, 중복 코드, 순환 참조, 보안 취약점 점수가 B등급 미만으로 떨어질 경우 퀄리티 게이트(Quality Gate)를 닫아(Block) 개발자의 메인 브랜치 병합을 물리적으로 통제
3. [ArgoCD / Spinnaker 기반 쿠버네티스(k8s) 배포 자동화] MSA 환경에서 수십 개의 컨테이너가 쏟아질 때 스크립트(bash) 배포의 한계를 극복하기 위해, Git에 저장된 인프라 상태(Manifest)와 실제 k8s 실서버 상태를 실시간 동기화(Sync)하는 ArgoCD(GitOps)를 CD 꼬리단에 부착하여 선언적 릴리즈 통제망 구축

**결론:**
- 기술사 판단: CI/CD 파이프라인은 단순히 쉘 스크립트를 이어 붙인 자동화 툴(Tool)이 아니다. "에러는 발생하기 마련이니(Fail Fast), 인간의 손을 치우고 기계가 하루 10번씩 멱살을 잡고(테스트) 고쳐 배포하게 만들자"는 데브옵스(DevOps)의 사상이 물리적인 컨베이어 벨트로 육화(Incarnation)된 핵심 인프라다.
- 향후 방향: 최근 클라우드 환경에서는 서버형 배포(Jenkins Push) 방식의 보안 취약점을 극복하기 위해, 배포 타겟 서버(Kubernetes) 내부의 에이전트가 Git의 형상(YAML)을 직접 긁어가서 자기 자신을 동기화(Pull) 시키는 **GitOps(깃옵스) 패러다임**으로 CD 아키텍처의 패권이 완벽히 이동하고 있다.
