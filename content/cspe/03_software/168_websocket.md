## Ⅰ. 개요
- **정의**: HTTP 핸드셰이크 후 TCP 위에 전이중 양방향 지속 연결을 수립하는 통신 프로토콜
- **배경/필요성**: HTTP의 요청-응답 반이중 구조로는 실시간 양방향 데이터 전송이 비효율적임
- **비유**: 전화 통화처럼 한 번 연결하면 양쪽이 자유롭게 말할 수 있는 것과 유사함

| 출제 의도 | 반드시 짚을 핵심 | 감점 회피 포인트 |
|:---|:---|:---|
| 실시간 통신 프로토콜 이해 | 전이중·지속 연결·낮은 오버헤드 | HTTP Polling·SSE와의 차이 구분 |

> 요약: TCP 기반 전이중 지속 연결로 양방향 실시간 통신을 수행하는 프로토콜임

## Ⅱ. 구성요소
```text
Client <--Full Duplex--> [WebSocket Server]
   |                          |
HTTP Upgrade              Frame Protocol
(Handshake)              (Text/Binary)
```

| 구성요소 | 설명 | 비유 |
|:---|:---|:---|
| Handshake | HTTP Upgrade 헤더로 WS 프로토콜 전환을 합의함 | 전화 연결 수립 |
| Frame | 텍스트·바이너리 데이터를 감싸는 경량 전송 단위 | 대화 한 마디 |
| Connection | 핸드셰이크 후 유지되는 전이중 TCP 연결 | 통화 유지 상태 |
| Close Frame | 연결 종료 의사를 전달하는 제어 프레임 | 전화 끊기 신호 |

> 요약: Handshake-Frame-Connection-Close 구조로 양방향 지속 통신을 수행함

## Ⅲ. 절차
```text
HTTP Upgrade --> WS 연결 수립 --> 양방향 메시지 교환 --> Close 종료
      |               |                 |                  |
      v               v                 v                  v
  101 Switching    TCP 지속 연결     Frame 송수신       정상 종료
```
- 1단계: 클라이언트가 HTTP Upgrade 요청을 보내고 서버가 101 응답을 반환함
- 2단계: 프로토콜이 WS로 전환되어 전이중 TCP 연결이 수립됨
- 3단계: 양쪽이 Frame 단위로 텍스트·바이너리 메시지를 자유롭게 송수신함
- 4단계: 한쪽이 Close Frame을 전송하면 상대방이 확인 후 연결을 종료함

> 요약: Upgrade-연결수립-양방향교환-종료 4단계로 실시간 통신을 수행함

## Ⅳ. 문제점
- 연결 유지 비용: 대량 동시 접속 시 서버 메모리·파일 디스크립터가 소진될 수 있음
- 로드밸런싱 제약: 지속 연결이므로 HTTP 수준 라우팅·분배가 어려움
- 재연결 미지원: 프로토콜 자체에 자동 재연결 메커니즘이 없음

> 요약: 연결 자원 소모·로드밸런싱·재연결 미지원이 주요 한계임

## Ⅴ. 개선방안
1. 단기: 연결 풀링 + Heartbeat Ping/Pong으로 유휴 연결을 정리하여 자원 절약
2. 중기: Sticky Session 또는 L4 로드밸런서로 지속 연결 분배 문제 해소
3. 장기: 클라이언트 측 자동 재연결 + 지수 백오프 라이브러리 표준화

> 요약: 연결 관리-L4 분배-자동 재연결 순으로 개선함

## Ⅵ. 전망
- 발전 방향: 채팅·게임·IoT 등 실시간 양방향 통신의 사실상 표준으로 정착됨
- 기술사적 판단: SSE(단방향)와 용도별 분담 구조가 형성됨
- 기술사 제언: 대규모 동시 접속 시 서버 아키텍처(이벤트 루프·비동기 I/O) 설계 역량이 필요함
