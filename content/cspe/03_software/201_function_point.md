## Ⅰ. 개요
- 사용자 관점에서 소프트웨어의 기능을 정량적으로 측정하는 비용 산정 방식임
- 구현 기술이나 언어에 독립적으로, 요구사항을 기반으로 규모를 산출함
| 구분 | 내용 | 비유 |
| --- | --- | --- |
| 출제의도 | FP 구성요소(데이터/트랜잭션), 간이법 vs 정법, 소프트웨어 사업 대가 | 건물의 방 개수와 용도 기준 공사비 |

## Ⅱ. 구성요소
- 데이터 기능(내부/외부 파일)과 트랜잭션 기능(입력/출력/조회)으로 구분됨
[데이터: ILF, EIF] + [트랜잭션: EI, EO, EQ] = [기능 점수]
- 구성요소 표
| 구성요소 | 설명 | 비유 |
| --- | --- | --- |
| 내부 논리 파일(ILF) | 애플리케이션 내부에서 유지되는 데이터 그룹 | 내 집 안의 금고 |
| 외부 인터페이스 파일(EIF) | 타 시스템에서 참조만 하는 데이터 그룹 | 이웃집 도서관 |
| 외부 입력/출력/조회 | 데이터 등록(EI), 파생 정보 출력(EO), 단순 검색(EQ) | 창구의 입금/통계/잔액조회 |
> 요약: 5가지 핵심 기능의 복잡도(RET, DET, FTR 등)에 따라 점수를 부여함

## Ⅲ. 절차
- ISO 표준(IFPUG) 기반의 산정 프로세스임
[측정 유형 결정] -> [범위 획정] -> [미조정 점수 산출] -> [보정 및 최종 점수]
- 4단계 설명
1) 기능 식별: 분석 설계서를 기반으로 데이터 및 트랜잭션 기능을 도출함
2) 복잡도 산정: 각 기능별 데이터 요소(DET) 등 수치에 따라 난이도 결정함
3) 미조정 FP(UFP): 식별된 기능별 가중치 합계를 통해 기초 규모 도출함
4) 보정 계수 적용: 규모, 연계, 성능 등 특성별 가중치를 곱해 최종 점수 확정함
> 요약: 비즈니스 가치 중심의 정량화된 소프트웨어 자산 가치를 측정함

## Ⅳ. 문제점
- 산정 과정이 복잡하고 전문가의 주관에 따라 결과 편차가 발생함 (원인: 분석 난이도)
- 소규모 수정이나 비기능적 요구사항(보안, 성능) 반영에 한계가 있음 (원인: 기능 위주 측정)

## Ⅴ. 개선방안
- (단기) 초기 단계에서는 기능 유형별 평균 복잡도를 사용하는 '간이법' 적용함
- (중기) SW 사업 대가 산정 가이드에 따른 보정 계수(애플리케이션 유형 등) 정밀화함
- (장기) 설계 모델(UML 등)로부터 기능을 자동 추출하는 자동 FP 산정 도구 도입함

## Ⅵ. 전망
- 클라우드 네이티브 환경의 복잡한 API 연계를 반영한 신규 FP 표준 논의가 가속화될 것임
- AI 기반 사업 대가 산정 검증 시스템이 공공 사업의 투명성을 높이는 핵심 CSF가 될 것임
