# 📖 【암기용】 개념 완전 이해

## 한눈에
- **개요**: 기아(Starvation)는 우선순위 경쟁에서 계속 밀린 특정 프로세스가 **필요한 자원(CPU·락)을 무한히 못 받는** 상태이고, 에이징(Aging)은 **대기 시간이 길수록 우선순위를 점점 올려** 이를 해소하는 기법이다.
- **왜 필요한가**: 우선순위 기반 스케줄링(004·005 참조)은 응답성·중요도를 살리지만, 낮은 우선순위 작업이 상위 작업에 영원히 밀릴 수 있다. 시스템은 멈추지 않아 겉보기엔 정상인데 특정 작업만 방치되므로, 공평성을 보장할 별도 장치가 필요하다.
- **핵심 직관**: 응급실에서 중증 환자가 계속 실려 오면 경증 환자는 순번이 밀려 하루 종일 못 들어간다(기아). 이를 막으려 "대기 시간이 길어지면 우선순위를 올려준다"는 규칙을 두는 것이 에이징이다.

## 핵심 용어 정리 (내부에 등장하는 것들)

아래 답안용에 나오는 기아 원인·에이징 표기와 관련 개념을 비유와 함께 먼저 세운다. 맨 위가 이 주제의 상위 핵심 키워드다.

| 용어/표기 | 의미 | 비유·예 |
|:---|:---|:---|
| 기아 (상위 키워드, Starvation) | 우선순위에 밀려 특정 프로세스가 자원을 영영 못 받음 | 새치기에 계속 밀려 못 들어가는 경증 환자 |
| 에이징 (Aging) | 대기 시간에 비례해 우선순위를 점진 상향 | 오래 기다린 환자의 순번을 올려줌 |
| 우선순위 (Priority) | 스케줄러가 자원을 줄 순서를 정하는 값 | 진료 급한 정도(중증도) |
| 무한 봉쇄 (Indefinite Blocking) | 기아의 다른 이름, 무기한 대기 상태 | 언제 부를지 기약 없는 대기 |
| 우선순위 역전 (Priority Inversion) | 저순위가 쥔 락 때문에 고순위가 대기하는 현상 | 경증 환자가 쥔 장비를 중증이 못 씀 |
| 우선순위 상속 (Priority Inheritance) | 락 점유 저순위에 고순위의 우선순위를 임시 부여 | 장비 쥔 환자에게 급한 순번을 잠시 넘김 |
| 교착상태 (Deadlock) | 상호 자원 대기로 관련 모두가 정지 (009 참조) | 서로 안 비키는 두 차 |
| 공평성 (Fairness) | 모든 작업이 유한 시간 내 자원을 받도록 보장 | 아무도 무한정 방치하지 않는 원칙 |
| vruntime (가상 실행시간) | CFS가 적게 실행된 작업을 우선하는 공평성 지표 (006 참조) | 지금까지 가장 적게 먹은 사람 먼저 |

## 깊이 이해
- **배경·문제의식**: 스케줄링(004 참조)에서 SJF·우선순위·MLFQ 같은 **우선순위가 개입하는 선점형** 방식은 짧거나 중요한 작업을 앞세워 성능을 높인다. 그러나 상위 작업이 끊임없이 도착하면 하위 작업은 자기 차례가 영영 오지 않는다. FCFS·RR은 늦더라도 순번이 반드시 오므로 구조적으로 기아가 없다는 점이 대비된다.
- **작동 원리(어떻게+왜)**: 에이징은 각 프로세스의 우선순위를 고정하지 않고, **Ready 큐에서 기다린 시간에 비례해 우선순위를 주기적으로 가산**한다. 예컨대 "5초 대기마다 우선순위 1단계 상향"을 두면, 아무리 낮은 작업도 시간이 지나면 결국 최상위에 도달해 CPU를 받는다. 이로써 성능 지향 우선순위 정책에 유한 대기 보장을 덧입힌다. 리눅스 CFS(006 참조)는 명시적 에이징 대신 vruntime이 작은 작업을 우선하는 구조로 기아를 원천적으로 억제한다.
- **비유**: 놀이공원 대기줄에서 VIP가 계속 새치기하면 일반 손님은 못 탄다. "1시간 기다릴 때마다 우대권 등급을 올려준다"는 규칙을 두면, 일반 손님도 언젠가 VIP급이 되어 탑승한다. 이 규칙이 에이징이다.
- **구체 예시**: 우선순위 0(최저)~127(최고) 시스템에서 우선순위 5인 배치 작업이 우선순위 60~100대 대화형 작업에 계속 밀려 대기한다고 하자. 에이징으로 "10초당 +10"을 적용하면 이 배치 작업은 약 100초 후 우선순위 100대에 진입해 CPU를 확보한다. 방치되던 작업에 완료 상한선이 생긴다.
- **흔한 오해·주의점**: (1) **기아 ≠ 교착**이다. 교착(009 참조)은 관련 프로세스가 *모두* 상호 대기로 정지하지만, 기아는 시스템은 돌아가는데 *특정 하나*만 밀린다. (2) 기아는 CPU뿐 아니라 락·I/O·네트워크 대역 등 모든 경쟁 자원에서 발생한다. (3) 우선순위 역전은 기아의 특수 사례로, 락을 쥔 저순위 때문에 고순위가 대기하는 것이며 해법은 에이징이 아니라 **우선순위 상속**이다.

## 연결 개념
- 프로세스 스케줄링(004 참조) — 기아를 유발하는 우선순위·SJF·MLFQ 정책의 배경
- CFS(006 참조) — vruntime 기반으로 명시적 에이징 없이 공평성을 보장하는 리눅스 표준
- 교착상태(009 참조) — 기아와 구별되는 또 다른 무한 대기(상호 정지)

# 📝 【답안용】 시험 답안 템플릿

## 핵심 인사이트 (3줄 요약)

> 1. **본질**: 기아는 우선순위 경쟁에 밀린 특정 프로세스가 자원을 무한 대기하는 상태이고, 에이징은 대기 시간에 비례해 우선순위를 올려 이를 해소함.
> 2. **가치**: 성능 지향 우선순위 정책(SJF·MLFQ)에 유한 대기 보장을 덧입혀 공평성과 성능을 양립시킴.
> 3. **판단 포인트**: 기아는 교착과 달리 시스템은 정상 동작하므로 탐지가 어렵고, 우선순위 역전은 상속으로 별도 대응해야 함.

## 출제 의도 및 답안 포인트

| 출제 의도 | 반드시 짚을 핵심 | 감점 회피 포인트 |
|:---|:---|:---|
| 기아 발생 원인 이해 | 우선순위 개입 선점형(SJF·MLFQ)에서 발생 | 기아와 교착 개념 혼동 |
| 에이징 해소 원리 | 대기 시간 비례 우선순위 상향 | 에이징 상향 기준(대기 시간) 누락 |
| 관련 현상 구분 | 우선순위 역전은 상속으로 별도 대응 | 역전 해법을 에이징으로 단정 |

> 요약: 기아의 원인을 우선순위 정책으로 특정하고, 에이징(대기 시간 상향)과 역전 대응(상속)을 구분해 제시함.

## Ⅰ. 개요 및 필요성

- 개요: 기아는 우선순위에 밀려 특정 프로세스가 자원을 무한 대기하는 상태임
- 배경: 우선순위·SJF·MLFQ 등 성능 지향 정책(004 참조)은 하위 작업의 영구 대기를 유발할 수 있음
- 필요성: 시스템은 정상 동작해 방치가 드러나지 않으므로 유한 대기를 강제할 공평성 장치가 필요함

## Ⅱ. 구조 및 구성요소

선형 구조도 (기아 발생과 에이징 해소 경로):

    상위 작업 연속 도착 -> 하위 작업 Ready 큐에 무한 적체(기아)
      -> 에이징 적용: 대기 시간 누적 -> 우선순위 주기적 가산
      -> 우선순위 임계 도달 -> 스케줄러 선택 -> CPU 확보(해소)

| 구성요소 | 역할 | 특이사항 |
|:---|:---|:---|
| 우선순위 값 | 스케줄러의 선택 기준 | 고정 시 하위 작업 기아 유발 |
| 대기 시간 | 에이징의 상향 근거 | Ready 큐 체류 시간 누적 |
| 에이징 계수 | 단위 대기당 우선순위 증가폭 | 과대 시 우선순위 정책 무력화 |
| 스케줄러 | 우선순위 반영해 CPU 배정 | 에이징 갱신 주기와 연동 |

> 요약: 고정 우선순위가 기아의 원인이며, 대기 시간을 우선순위에 반영하는 에이징이 핵심 해소 장치임.

## Ⅲ. 동작원리 및 흐름도

선형 흐름도 (에이징 동작):

    Ready 큐 진입 -> 우선순위로 선택 경쟁
      -> [선택 실패] 대기 시간 누적 -> 주기적 우선순위 += 에이징 계수
      -> [임계 도달] 최상위 근접 -> 스케줄러가 선택 -> 실행 후 우선순위 원복

- 1단계 [기아 발생]: 스케줄러가 상위 우선순위 작업만 반복 선택해 하위 작업이 Ready 큐에 적체됨
- 2단계 [대기 측정]: 커널이 각 프로세스의 Ready 큐 체류 시간을 누적 측정함
- 3단계 [우선순위 상향]: 에이징이 대기 시간에 비례해 해당 프로세스의 우선순위를 주기적으로 가산함
- 4단계 [해소]: 상향된 우선순위가 임계에 도달하면 스케줄러가 선택해 CPU를 배정하고 우선순위를 원복함

> 요약: 대기 시간을 우선순위로 환산해 방치된 작업을 결국 최상위로 끌어올려 유한 시간 내 실행을 보장함.

## Ⅳ. 특징

- 은닉성: 교착과 달리 시스템은 정상 작동해 특정 작업 방치가 겉으로 드러나지 않음
- 정책 의존성: 우선순위가 개입하는 선점형(SJF·MLFQ)에서 발생하고 FCFS·RR은 구조적 무기아
- 에이징의 양면성: 공평성을 얻는 대신 우선순위 정책의 변별력을 일부 희석함
- 자원 보편성: CPU뿐 아니라 락·I/O·네트워크 등 모든 경쟁 자원에서 발생함
- 역전과의 구별: 우선순위 역전은 락 점유가 원인이며 에이징이 아닌 상속으로 대응함

## Ⅴ. 심화 비교 및 적용 판단

무한 대기 현상인 기아와 교착상태를 발생 범위·해소 방식 축으로 대조함(교착 상세는 009 참조).

| 구분 | 기아 (Starvation) | 교착상태 (Deadlock) |
|:---|:---|:---|
| 대상 범위 | 특정 프로세스 하나가 밀림 | 관련 프로세스 모두 상호 정지 |
| 시스템 상태 | 전체는 정상 진행 | 관련 부분 전체 정지 |
| 근본 원인 | 우선순위 경쟁 지속 | 코프만 4조건 동시 성립 |
| 해소 방식 | 에이징(우선순위 상향) | 예방·회피·탐지·복구 |
| 자기 해소 | 부하 감소 시 자연 해소 가능 | 외부 개입 없이 불가능 |

> 요약: 기아는 단일 작업의 상대적 지연으로 에이징이 해법이고, 교착은 상호 정지로 4대 전략이 필요함.

**리스크·대응:**
- 우선순위 역전 — 락 쥔 저순위가 고순위를 막아 고순위가 대기 — 우선순위 상속(Priority Inheritance) 프로토콜 적용
- 에이징 계수 과대 — 상향폭이 커 우선순위 정책이 무력화 — 대기 임계·증가폭을 워크로드에 맞춰 튜닝
- 락 기아 — 특정 스레드가 뮤텍스를 계속 놓쳐 무한 대기 — 공정(fair) 락·FIFO 큐 락으로 순번 보장

**점검 지표:**
- 성능: 하위 우선순위 작업 최대 대기 시간(p99), Run Queue 최장 체류 시간
- 운영: 기아 의심 작업 수, 우선순위 역전 발생 빈도

## Ⅵ. 실무 적용 및 결론

**적용 방안:**
1. 스케줄러 에이징 파라미터 설정: 우선순위 스케줄러에 대기 시간당 우선순위 가산(예: 10초당 +10)을 두어 배치 작업 완료 상한 보장
2. 실시간 시스템 우선순위 상속: RTOS 뮤텍스에 Priority Inheritance/Ceiling 프로토콜을 적용해 우선순위 역전 차단
3. 공정 락 도입: 다중 스레드 경쟁 구간에 FIFO 순서를 보장하는 fair lock을 써 특정 스레드의 락 기아 방지

**결론:**
- 기술사 판단: 응답성·중요도가 핵심이면 우선순위 정책에 에이징을 병행하고, 순수 공평성이 목표면 CFS·RR처럼 구조적 무기아 방식을 택함
- 향후 방향: 멀티코어·컨테이너 혼합 워크로드 확산으로, vruntime 기반 CFS와 cgroup 자원 배분처럼 명시적 에이징 없이 공평성을 내재화한 스케줄링이 표준으로 자리 잡음
