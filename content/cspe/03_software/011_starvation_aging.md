# 📖 【암기용】 개념 완전 이해

> 목적: 이 개념을 처음 보는 사람도 완벽히 이해하게 만든다. 시험 답안 양식이 아니라, 이해를 위한 친절한 설명이다.

## 한눈에
- **개요**: **기아(Starvation)**는 우선순위가 낮은 프로세스가 자기보다 급한 프로세스들에 밀려 평생 CPU나 자원을 할당받지 못하고 굶어 죽는 현상이다. **에이징(Aging, 노화)**은 이 불쌍한 프로세스가 굶은 시간에 비례하여 우선순위를 강제로 높여주어 결국에는 구제해 주는 해결책이다.
- **왜 필요한가**: 가장 효율적인 스케줄러(SJF 등)일수록 "짧고 급한 일 먼저"라는 극단적 규칙을 쓴다. 이때 길고 덜 중요한 프로세스는 영원히 뒤로 밀리는 치명적 부작용이 생기는데, 시스템이 특정 작업을 영구 방치하는 것을 막기 위한 안전장치가 필요하다.
- **핵심 직관**: 병원 응급실에 '무릎 까진 환자(우선순위 최하)'가 왔다. 그런데 계속 '심정지 환자(우선순위 최상)'가 실려 온다. 원칙대로면 무릎 까진 환자는 평생 진료를 못 받는다(기아). 이때 간호사가 "이분 3일째 기다렸어요, 오늘은 무조건 진료 보게 해주세요"라고 순번을 앞으로 당겨주는 것(에이징)이다.

## 깊이 이해
- **배경·문제의식**: 기아 상태는 데드락(Deadlock)과 달리 시스템 전체가 멈추지는 않는다. CPU는 심정지 환자들을 열심히 치료하며 엄청 바쁘게 잘 돌고 있다. 다만 특정 프로세스 하나만 소외되어 영구 대기(Indefinite Blocking) 상태에 빠지는 논리적 오류다.
- **작동 원리 (에이징 기법)**: 
  - 커널은 각 프로세스 PCB에 `대기 시간`과 `현재 우선순위`를 기록한다.
  - 프로세스가 큐(Queue)에 머무는 시간이 길어질수록, 타이머 인터럽트가 발생할 때마다 해당 프로세스의 우선순위 숫자를 인위적으로 한 단계씩 높여준다. (Priority = Base Priority + Wait Time)
  - 결국 꼴찌였던 녀석도 시간이 지나면 1등 우선순위에 도달하게 되어, 무조건 한 번은 CPU를 차지(Dispatch)하게 된다.
- **비유**: 놀이공원에서 줄 서기. VIP 패스(우선순위 높음)를 산 사람들이 계속 오면 일반 줄(우선순위 낮음)은 꼼짝도 안 한다(기아). 그래서 "일반 줄에서 1시간 이상 기다린 사람은 강제로 VIP 줄 맨 앞으로 보내준다(에이징)"는 규칙을 만드는 것이다.
- **구체 예시**: MLFQ(멀티레벨 피드백 큐)에서 하위 큐(Q3)로 쫓겨난 동영상 인코딩 프로세스는 상위 큐(Q1)에 마우스 클릭 같은 대화형 프로세스가 계속 들어오면 영원히 멈춘다. 이를 막기 위해 OS는 1초마다 시스템 내의 모든 프로세스를 Q1으로 강제 승급(Priority Boost)시켜준다.
- **흔한 오해·주의점**: 에이징은 원래 우선순위를 "무시"하는 것이 아니다. 시간에 비례해 일시적으로 "보정"하는 것이다. 그래서 에이징으로 CPU를 한 번 할당받아 작업을 수행하고 나면, 다시 원래의 낮은 우선순위(Base Priority)로 원복시켜 줘야 한다.

## 연결 개념
- **데드락(Deadlock) vs 기아(Starvation)**: 데드락은 서로가 서로의 열쇠를 쥐고 있어 시스템 자체가 '물리적으로 정지'한 것이고, 기아는 시스템은 잘 돌아가지만 자원 분배 정책의 불평등 때문에 특정 작업만 '논리적으로 배제'된 것이다.
- **다익스트라의 식사하는 철학자 문제**: 철학자 5명이 젓가락을 집을 때, 양보(Yield) 규칙을 너무 예의 바르게 짜면 아무도 밥을 못 먹고 굶어 죽는 기아나 라이브락(Livelock)에 빠진다.

# 📝 【답안용】 시험 답안 템플릿

> 목적: 시험장에서 25분에 그대로 쓰는 답안 양식. 작성방식(추상표현 금지·수치·도식·문제유형 전환)을 엄격히 지킨다.
> 핵심: 이 시험은 정보를 많이 나열하는 시험이 아니라, 문제 신호어에서 출제자 의도를 읽고 핵심 논점을 선별해 쓰는 시험이다.

## 핵심 인사이트 (3줄 요약)

> 1. **본질**: 기아(Starvation)는 우선순위 스케줄링의 고질적인 불평등으로 인한 영구 대기 현상이며, 에이징(Aging)은 대기 시간에 비례해 우선순위를 강제 보정하는 구제 메커니즘이다.
> 2. **가치**: 특정 프로세스의 극단적 지연을 막아 시스템의 공정성(Fairness)과 유한 대기(Bounded Waiting) 요건을 수학적으로 보장한다.
> 3. **판단 포인트**: 기아와 데드락의 차이점을 명확히 대조하고, 현대 범용 OS(Linux MLFQ/CFS)가 에이징 철학을 어떻게 아키텍처에 녹여냈는지(Boost, vruntime) 증명해야 한다.

## 출제 의도 및 답안 포인트

| 출제 의도 | 반드시 짚을 핵심 | 감점 회피 포인트 |
|:---|:---|:---|

| 운영체제 차원의 에이징 적용 기법 | 대기 시간(Wait Time)에 비례한 인위적 가중치 상승 | 에이징 후 우선순위 원복(Reset) 과정을 누락하는 실수 |

## Ⅰ. 개요 및 필요성

- 정의: 기아(Starvation)는 하위 우선순위 프로세스가 상위 태스크의 지속적 유입으로 자원(CPU 등)을 무한 대기하는 현상이며, 에이징(Aging)은 이 대기 시간에 비례해 우선순위를 상향시키는 해결책
- 배경: 가장 직관적이고 효율적인 스케줄러인 SJF(Shortest Job First) 등은 작업 처리량을 극대화하지만, 길이가 긴 프로세스를 영구적으로 큐에 방치하는 치명적 부작용 유발
- 필요성: 시스템이 임의의 사용자 작업을 무기한 거부하는 것을 막고, 크리티컬 시스템의 상한 응답 시간(유한 대기, Bounded Waiting)을 보장하기 위함

## Ⅱ. 기아(Starvation) 발생 메커니즘과 에이징(Aging) 구조도

```text
[ 기아 상태 발생 (우선순위 스케줄링) ]
+-----------------------------------+
| 유입: P_High(우선순위 10), P_Mid(5)  |
| 대기: P_Low(우선순위 1)             |
+-----------------------------------+
스케줄러는 계속 P_High와 P_Mid만 꺼내감 -> P_Low는 무한 대기(기아)

[ 에이징 알고리즘 동작 (우선순위 보정) ]
P_Low의 동적 우선순위(Dynamic Priority) = 기본(Base: 1) + 대기 시간(Wait Time * α)
1. 10초 대기 -> 동적 우선순위 3으로 상승
2. 50초 대기 -> 동적 우선순위 11로 상승 (P_High 역전!)
3. P_Low CPU 획득 후 실행 (기아 탈출)
4. 실행 완료 후 동적 우선순위를 다시 Base(1)로 롤백
```

| 구분 | 파라미터 계산식 예시 | 운영체제 처리 역할 |
|:---|:---|:---|
| 발생 원인 | $P_{new} > P_{waiting}$ 이 무한 반복됨 | 철저한 우선순위 기반 스케줄링의 부작용 |
| 에이징 팩터 | $P = P_{base} + (T_{wait} \times \alpha)$ | 틱(Tick)마다 대기 큐 스캔 및 가중치 업데이트 |
| 원복 로직 | $P = P_{base}$ | CPU 획득 후 특혜 소멸을 통한 밸런스 유지 |

> 요약: 노화(Aging)는 공정성을 위한 윤리적 장치가 아니라, 시스템 큐가 처리 불가능한 쓰레기 작업들로 꽉 차서 정지하는 것을 막는 실용적 쓰레기 수거(Garbage Collection)다.

## Ⅲ. 교착상태(Deadlock) vs 기아(Starvation) 심화 비교

기아는 시스템 전체의 마비가 아니라는 점에서 데드락과 궤를 달리한다.

| 비교 축 | 교착상태 (Deadlock) | 기아 (Starvation) |
|:---|:---|:---|
| 정의 | 자원 획득 고리(Cycle) 형성으로 인한 상호 영구 정지 | 정책(우선순위)에 의한 일방적 무한 대기 |
| CPU 상태 | 얽힌 프로세스들은 Sleep 되어 CPU 이용률 **0% (유휴)** | 상위 프로세스 처리로 인해 CPU 이용률 **100% (매우 바쁨)** |
| 4대 발생 조건 | 상호배제, 점유대기, 비선점, 순환대기 동시 만족 시 | 스케줄러가 에이징 로직 없이 우선순위/SJF 채택 시 |
| 커널 해결책 | 발생 회피(은행원) 또는 탐지 후 희생자(Victim) Kill | 발생 전 에이징(Aging)을 통한 우선순위 부스트 |

> 요약: 데드락이 두 차가 골목에서 마주 쳐 도로 전체가 멈춘 '사고'라면, 기아는 갓길에 세운 똥차가 벤츠들에 양보하느라 평생 대로로 진입하지 못하는 '불평등'이다.

## Ⅳ. 현대 범용 OS의 에이징(Aging) 철학 계승 아키텍처

현대 운영체제는 매 틱(Tick)마다 모든 프로세스 우선순위를 수동으로 1씩 더하는 $O(N)$의 계산 오버헤드를 버리고, 아키텍처 수준에서 에이징 철학을 변형해 구현했다.

| 운영체제/알고리즘 | 에이징 적용 메커니즘 (구현체) | 성능 오버헤드 방어 전략 |
|:---|:---|:---|
| Unix/Linux MLFQ | **Periodic Priority Boost**: 하위 큐(Q3)에 박혀있는 태스크들을 1초 등 특정 주기마다 한꺼번에 최상위 큐(Q1)로 일괄 승격시킴 | 매번 계산하지 않고 주기적으로 집단 멱살(Boost)을 잡아끌어올림 |
| Linux CFS | **vruntime 누적 정렬**: 우선순위(nice)가 낮아도, 오래 기다리면 가상 실행 시간(vruntime) 자체가 상대적으로 매우 작아짐 | Red-Black Tree의 가장 왼쪽으로 자연스럽게 위치하게 되어 자동 구제(O(1) 추출) |
| Windows NT | **Dynamic Priority Boost**: I/O 완료 응답이 떨어지면, 백그라운드 스레드의 우선순위를 일시적으로 점프시켜 즉시 화면 렌더링에 관여하게 함 | I/O 이벤트를 트리거로 삼아 데스크톱 반응성 극대화 |

> 요약: 에이징은 단순한 이론이 아니라, MLFQ의 부스트(Boost)나 CFS의 장부(vruntime) 설계 사상의 핵심 근간으로 자리 잡아 현대 커널을 지탱하고 있다.

## Ⅴ. 실무 적용 방안 및 결론

**적용 방안 3개:**
1. [RDBMS 트랜잭션 기아 방어] 데이터베이스 락(Lock) 매니저 구현 시, 읽기 락(Shared Lock)이 무한정 쏟아져 들어올 때 쓰기 락(Exclusive Lock)이 기아에 빠지는 것을 막기 위해, 대기 큐에 쓰기 요청이 진입하면 신규 읽기 요청을 차단(Write-Preferring)하는 논리적 에이징 룰 적용
2. [스레드 풀 작업 기아 방지] Java 멀티스레딩 환경에서 `PriorityBlockingQueue`를 사용할 때, 단순히 우선순위 값만 넣지 않고 `(우선순위 * 가중치) + (System.currentTimeMillis() - EnqueueTime)`를 계산하는 커스텀 Comparator를 주입하여 큐 체류 시간에 비례한 자동 순위 상향 아키텍처 구현
3. [로드밸런서 가중치 라우팅] L7 로드밸런서(HAProxy 등)에서 트래픽을 백엔드 노드에 분배할 때, 성능이 떨어지는 저사양 노드(Low Priority)가 트래픽을 아예 못 받아 캐시가 콜드(Cold) 상태가 되는 것을 막기 위해 서서히 가중치를 높이는 백오프/에이징 폴링 스크립트 결합

**결론:**
- 기술사 판단: 이론적으로 가장 완벽한 SJF나 절대 우선순위 스케줄러가 상용화되지 못하는 이유는 극단적 불평등(기아)을 유발하기 때문이다. 엔지니어링은 언제나 '평균 성능의 극대화'와 '최악 응답 시간(기아) 방어'라는 두 마리 토끼를 에이징과 같은 트레이드오프 파라미터로 조율하는 과정이다.
- 향후 방향: 최근 클라우드 자원 할당기(Kubernetes Scheduler)에서는 노드의 자원이 꽉 차 중요도가 낮은 파드(Pod)가 계속 스케줄링을 받지 못하는 기아를 막기 위해, 파드 생성 시도 횟수를 누적 추적하여 점진적으로 선점(Preemption) 권한을 강화하는 기능이 적용되고 있다.
