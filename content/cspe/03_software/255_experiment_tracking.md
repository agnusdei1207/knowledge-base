# 📖 【암기용】 개념 완전 이해

> 목적: 실험 추적을 처음 보는 사람도 완벽히 이해하게 만든다. 시험 답안 양식이 아니라, 이해를 위한 친절한 설명이다.

## 한눈에
- **개요**: 실험 추적은 ML 학습의 **재현성(Reproducibility)**을 확보하기 위해 코드·데이터·파라미터·지표·산출물을 **Run** 단위로 기록하는 활동이다.
- **왜 필요한가**: 하이퍼파라미터를 바꿔가며 수십~수백 번 학습을 반복하다 보면 "어떤 설정이 어떤 결과를 냈는지"를 잊기 쉽다. 기록이 없으면 가장 점수가 좋았던 모델조차 재현하거나 배포할 수 없다.
- **핵심 직관**: 연구노트와 실험실 장비 로그를 디지털로 통합해, 어떤 실험(Run)이 왜 더 좋았는지 근거를 남기고 비교하는 장치다.

## 핵심 용어 정리 (내부에 등장하는 것들)

| 용어 | 의미 | 비유 |
|:---|:---|:---|
| 재현성 (상위 개념) | 같은 입력·설정으로 다시 실행해도 같은 결과가 나오는 성질 — 실험 추적이 확보하려는 목표 | 같은 레시피면 같은 맛 |
| Run | 학습을 한 번 실행한 단위, 고유 ID가 부여됨 | 실험 1회차 기록카드 |
| Parameter(하이퍼파라미터) | 학습 전에 사람이 정하는 설정값(learning_rate, batch_size 등) | 오븐 온도·시간 설정 |
| Metric(지표) | 학습 중/후 측정되는 결과 수치(AUC, RMSE 등) | 완성된 요리의 맛 평가 점수 |
| Artifact | 산출물 파일(모델 가중치, 그래프, 환경파일) | 완성품과 포장 상자 |
| Tracking Server | Run들의 파라미터·지표·아티팩트를 저장·조회하는 서버 | 실험 기록 보관소 |
| 코드 SHA / 데이터 버전 | 어떤 코드 커밋, 어떤 데이터 스냅샷으로 학습했는지 식별하는 값 | 레시피판 번호·재료 로트번호 |

## 깊이 이해

### 왜 필요한가 — "제일 좋았던 그 모델"을 잃어버리는 문제
하이퍼파라미터 탐색을 할 때 learning_rate 3가지(0.1, 0.01, 0.001), batch_size 3가지(32, 64, 128)를 조합하면 9번의 Run이 생긴다. 기록 없이 진행하면 "AUC 0.812가 나온 조합이 정확히 무엇이었는지"를 재현할 수 없다. 실험 추적은 이 9개 Run 각각에 ID를 부여하고 `learning_rate=0.001, batch_size=64 → AUC=0.812`처럼 파라미터-지표 쌍을 자동 기록해, 대시보드에서 정렬·비교할 수 있게 한다.

### 재현에 필요한 4요소 — 지표만으로는 부족한 이유
지표(AUC 0.812)만 기록하면 "얼마나 좋았는지"는 알아도 "어떻게 다시 만드는지"는 모른다. 재현하려면 ① 코드(어떤 커밋 a1b2c3), ② 데이터(어떤 버전·해시), ③ 환경(라이브러리 버전이 담긴 conda.yaml), ④ 랜덤 시드까지 함께 있어야 한다. 이 중 하나라도 빠지면 같은 파라미터로 재실행해도 결과가 미세하게 흔들린다(예: 라이브러리 버전 차이만으로 AUC가 0.812에서 0.807로 변동).

### 작동 원리 — autolog로 기록 누락을 줄이는 법
수동으로 `log_param()`, `log_metric()`을 코드마다 호출하면 담당자가 빠뜨리기 쉽다. MLflow의 `autolog()`처럼 학습 프레임워크 훅에 자동으로 걸어 파라미터·지표·모델을 자동 기록하면 필수 필드 누락률을 낮춘다. 목표 예: 필수 태그(코드 SHA, 데이터 해시, 시드) 누락률 0%.

### 레지스트리로의 연결
비교 대시보드에서 여러 Run 중 목표 지표(예: baseline AUC 0.78 대비 +0.03 이상)를 만족하는 Run을 골라, 그 Run의 Artifact를 모델 레지스트리(254)에 등록하면서 실험 단계에서 운영 배포 단계로 넘어간다.

## 연결 개념
- 재현성(상위 개념)
- 모델 레지스트리(254) — 선택된 Run의 Artifact가 등록·승격되는 다음 단계
- 하이퍼파라미터 튜닝 — 실험 추적이 기록한 Run들을 탐색 알고리즘이 활용

# 📝 【답안용】 시험 답안 템플릿

> 목적: 시험장에서 25분에 그대로 쓰는 답안 양식. 작성방식(추상표현 금지·수치·도식·문제유형 전환)을 엄격히 지킨다.
> 핵심: 실험 추적 답안은 파라미터·지표 저장을 넘어 재현성, 후보 비교, 레지스트리 승격 기준까지 포함해야 한다.

## 핵심 인사이트 (3줄 요약)

> 1. **본질**: 실험 추적은 ML 학습 실행의 입력, 설정, 결과, 산출물을 Run 단위로 기록하는 재현성 관리 기법이다.
> 2. **가치**: 모델 후보 비교와 원인 분석을 가능하게 하며 배포 대상 모델의 근거 지표를 보존한다.
> 3. **판단 포인트**: metric만 저장하지 말고 데이터 버전, 코드 SHA, 환경, artifact를 함께 기록해야 한다.

## 출제 의도 및 답안 포인트

| 출제 의도 | 반드시 짚을 핵심 | 감점 회피 포인트 |
|:---|:---|:---|
| ML 실험 관리 이해 | Run, parameter, metric, artifact | 시각화 도구 소개로 축소 |
| 재현성 판단 확인 | 데이터 버전, 코드 SHA, 환경 정보 | 정확도 최고값만 비교 |
| MLOps 연계 확인 | 모델 후보 선택, 레지스트리 등록 | 배포 승인 기준 누락 |

> 요약: 실험 추적은 모델 선택의 근거와 재현 가능성을 확보하는 MLOps 시작점이다.

---

## Ⅰ. 개요 및 필요성

- 개요: 실험 추적은 ML 학습 실행 기록 관리다.
- 배경: 모델 결과는 데이터, 코드, 파라미터, 실행 환경에 따라 달라진다.
- 필요성: Run 단위로 지표·파라미터·artifact를 기록해 후보 비교와 재현 가능한 배포 근거를 확보해야 한다.

---

## Ⅱ. 구조 및 구성요소

```text
Training Code -> Run ID -> Parameters/Metrics -> Artifacts -> Tracking Server -> Dashboard -> Registry
                          / Data Version
                          / Environment
```

| 구성요소 | 역할 | 도구 예시 |
|:---|:---|:---|
| Run 관리 | 실험 실행 식별자와 실행 시간 기록 | MLflow Run, W&B Run |
| Parameter·Metric | 하이퍼파라미터와 결과 지표 저장 | lr, batch, AUC, RMSE |
| Artifact 저장 | 모델 파일, 그래프, 환경 파일 보관 | S3, MinIO, W&B Artifacts |
| 비교 대시보드 | 후보 모델 검색과 시각 비교 | MLflow UI, W&B Sweep |

> 요약: 실험 추적은 실행 ID를 중심으로 입력 설정과 결과 산출물을 연결한다.

---

## Ⅲ. 동작원리 및 흐름도

```text
실험 계획 -> Run 시작 -> 파라미터 기록 -> 학습 실행 -> 지표/산출물 저장 -> 후보 비교 -> 레지스트리 등록
```

| 단계 | 처리 내용 | 검증 기준 |
|:---:|:---|:---|
| 1 | 실험 목적과 평가 지표 정의 | baseline, target metric |
| 2 | 학습 실행과 파라미터 기록 | 랜덤 시드, 코드 SHA |
| 3 | metric과 artifact 저장 | AUC, RMSE, confusion matrix |
| 4 | 후보 비교 후 모델 승격 | 기준 지표와 재현 실행 |

> 요약: 실험 추적은 실험 설계부터 후보 승격까지 지표와 산출물을 누락 없이 연결한다.

## Ⅴ. 심화 비교 및 적용 판단

| 비교 축 | 기존/대안 | 실험 추적 | 선택 기준 |
|:---|:---|:---|:---|
| 구조 | 엑셀·문서 기록 | Tracking Server와 Artifact Store | 실험 20회 이상 반복 |
| 비용/성능 | 초기 구성 없음 | 저장소와 서버 운영 필요 | 협업 인원 3명 이상 |
| 운영/위험 | 재현 실패 가능 | Run 기반 재현 | 배포 모델 감사 필요 |

> 요약: 반복 실험과 협업이 있는 ML 프로젝트는 실험 추적 도구를 적용하고, 단일 분석은 경량 로깅으로 시작한다.

| 리스크 | 원인 | 대응 방안 | 확인 지표 |
|:---|:---|:---|:---|
| 기록 누락 | 수동 log 호출 의존 | autolog, 필수 필드 검사 | 필수 태그 누락률 |
| 지표 비교 오류 | 데이터셋 버전 차이 | DVC, dataset hash 기록 | 데이터 버전 일치율 |
| 저장소 비용 증가 | artifact 무제한 보관 | 보존 정책, 압축, lifecycle | 월 저장량 증가율 |

> 요약: 실험 추적 리스크는 기록 누락, 데이터 버전 차이, 저장소 비용이며 자동 기록과 보존 정책으로 통제한다.

| 점검 항목 | 목표 기준 | 측정 방법 |
|:---|:---|:---|
| 재현성 | 선택 모델 재실행 지표 편차 1% 이내 | 재학습 검증 |
| 기록 완전성 | 필수 파라미터·metric 100% | Tracking validation |
| 후보 비교 | baseline 대비 목표 지표 충족 | 대시보드 리포트 |

> 요약: 실험 추적 성과는 재현성, 기록 완전성, 후보 비교 가능성으로 판단한다.

## Ⅵ. 실무 적용 및 결론

**적용 방안 3개:**
1. MLflow 또는 W&B에 Run ID, 코드 SHA, 데이터 해시, 랜덤 시드, 환경 파일을 필수 태그로 기록함
2. AUC, F1, RMSE, p95 추론 지연을 metric으로 남기고 baseline 대비 개선 폭을 대시보드에서 비교함
3. 선택 모델의 artifact를 모델 레지스트리에 등록하고 Staging 승격 전 재현 실행을 1회 수행함

**결론 (2줄):**
- 기술사 판단: 반복 실험과 배포 후보 비교가 있으면 실험 추적을 필수 적용하고, 탐색 분석은 최소 Run 기록부터 적용함
- 향후 방향: 실험 추적은 모델 레지스트리, AutoML, 비용 추적과 결합해 ML 개발 의사결정 기반으로 발전함
