## Ⅰ. 개요
- **정의**: 클라이언트가 필요한 데이터의 구조와 필드를 명시적으로 요청하는 API 쿼리 언어
- **배경/필요성**: REST API(166 참조)의 Over-fetching·Under-fetching 문제를 해결할 유연한 데이터 요청 방식이 필요함
- **비유**: 뷔페에서 원하는 반찬만 골라 담는 것과 유사함 (정해진 세트 메뉴가 아닌 선택식)

| 출제 의도 | 반드시 짚을 핵심 | 감점 회피 포인트 |
|:---|:---|:---|
| API 설계 방식 비교 | 단일 엔드포인트 + 스키마 기반 쿼리 | REST와의 차이를 Over/Under-fetching 관점으로 설명 |

> 요약: 스키마 기반 단일 엔드포인트로 클라이언트 주도 데이터 조회를 수행하는 쿼리 언어임

## Ⅱ. 구성요소
```text
Client --Query/Mutation--> [GraphQL Server] --Resolver--> Data Sources
                                |
                             Schema
```

| 구성요소 | 설명 | 비유 |
|:---|:---|:---|
| Schema | 타입·필드·관계를 정의하는 API 계약서 | 메뉴판 |
| Query | 데이터를 읽기 요청하는 연산 | 주문서 |
| Mutation | 데이터를 생성·수정·삭제하는 연산 | 주문 변경 요청 |
| Resolver | 각 필드의 데이터를 실제로 조회·반환하는 함수 | 주방에서 요리를 만드는 셰프 |

> 요약: Schema-Query/Mutation-Resolver 구조로 유연한 데이터 요청을 처리함

## Ⅲ. 절차
```text
쿼리 작성 --> 스키마 검증 --> Resolver 실행 --> 응답 반환
    |              |              |              |
    v              v              v              v
 필드 선택     타입 일치 검사   데이터 조회    요청 구조 동일 응답
```
- 1단계: 클라이언트가 필요한 필드만 지정하여 쿼리를 작성함
- 2단계: 서버가 스키마와 대조하여 쿼리의 타입·필드 유효성을 검증함
- 3단계: 검증 통과 시 각 필드에 매핑된 Resolver가 데이터를 조회함
- 4단계: 요청한 구조와 동일한 JSON 형태로 응답을 반환함

> 요약: 작성-검증-해석-반환 4단계로 클라이언트 맞춤 응답을 생성함

## Ⅳ. 문제점
- N+1 쿼리: 중첩 필드 Resolver가 개별 호출되어 DB 쿼리가 급증할 수 있음
- 캐싱 어려움: 단일 엔드포인트·가변 쿼리로 HTTP 캐시 활용이 제한됨
- 복잡 쿼리 공격: 악의적 깊은 중첩 쿼리로 서버 자원이 고갈될 수 있음

> 요약: N+1 쿼리·캐싱 제한·악성 쿼리가 주요 과제임

## Ⅴ. 개선방안
1. 단기: DataLoader 패턴으로 N+1 문제를 배치 처리하여 해소
2. 중기: 쿼리 해시 기반 Persisted Query로 캐싱 효율 확보
3. 장기: 쿼리 깊이·복잡도 제한 + Cost Analysis로 악성 쿼리 차단

> 요약: DataLoader-Persisted Query-Cost 제한 순으로 개선함

## Ⅵ. 전망
- 발전 방향: Federation 구조로 MSA 환경의 통합 API Gateway 역할이 확대됨
- 기술사적 판단: BFF(Backend For Frontend) 패턴과 결합하여 프론트엔드 주도 개발에 적합함
- 기술사 제언: REST(166 참조)와 상호 보완적으로 적용하되 보안·성능 거버넌스를 수립할 필요
