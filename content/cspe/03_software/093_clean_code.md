## Ⅰ. 개요
- **정의**: 가독성과 변경 용이성을 갖춘, 의도가 명확히 드러나는 코드 작성 원칙임
- **배경/필요성**: 코드는 작성보다 읽히는 횟수가 압도적으로 많으므로 읽는 비용을 최소화하는 작성 규율이 필요함
- **비유**: 정리된 서재처럼 누구든 원하는 책을 빠르게 찾을 수 있는 코드 구조임

| 출제 의도 | 반드시 짚을 핵심 | 감점 회피 포인트 |
|:---|:---|:---|
| 클린 코드 원칙과 실천법 | 명명, 함수 크기, 주석 최소화 등 구체 원칙 | 추상적 구호가 아닌 측정 가능한 기준 제시 |

> 요약: 읽기 비용을 줄이고 변경을 용이하게 하는 코드 작성 규율임

## Ⅱ. 구성요소
```text
[클린 코드 원칙 구조]
  명명 규칙(Naming) -------> 의도를 드러내는 이름
        |
        v
  함수 설계(Function) -----> 단일 책임, 소규모 함수
        |
        v
  포맷팅(Formatting) ------> 일관된 들여쓰기와 배치
        |
        v
  오류 처리(Error Handling) > 예외 기반 흐름 분리
```

| 구성요소 | 설명 | 비유 |
|:---|:---|:---|
| 명명 규칙 | 변수/함수/클래스명이 역할을 즉시 전달하도록 작성함 | 도로 표지판 |
| 함수 설계 | 한 함수가 한 가지 일만 수행하며 20줄 이내로 유지함 | 단일 공구 |
| 포맷팅 | 팀 전체가 동일한 코드 배치 규칙을 따름 | 통일된 서식 |
| 오류 처리 | 정상 흐름과 예외 흐름을 분리하여 가독성을 확보함 | 비상구 분리 |

> 요약: 명명-함수-포맷-오류처리 4원칙으로 가독성을 확보함

## Ⅲ. 절차
```text
규칙 정의 --> 작성 적용 --> 코드 리뷰 --> 지표 모니터링
```
- 1단계: 규칙 정의 — 팀 코딩 표준을 문서화하고 린터 규칙으로 자동화함
- 2단계: 작성 적용 — 개발자가 작성 시점에 원칙을 준수하며 코딩함
- 3단계: 코드 리뷰 — 동료 리뷰에서 원칙 위반을 식별하고 피드백함
- 4단계: 지표 모니터링 — 순환 복잡도, 함수 길이 등을 CI에서 추적함

> 요약: 규칙 수립-적용-리뷰-모니터링 순환으로 코드 품질을 유지함

## Ⅳ. 문제점
- 주관성: 깨끗함의 기준이 개인마다 달라 리뷰 시 불필요한 논쟁이 발생함
- 초기 비용: 원칙 준수가 단기 개발 속도를 낮추는 것으로 인식됨 — 일정 압박 시 생략
- 과잉 적용: 지나친 분리로 클래스/함수 수가 폭증하면 탐색 비용이 증가함

> 요약: 주관성, 초기 비용 인식, 과잉 분리가 클린 코드 정착의 장벽임

## Ⅴ. 개선방안
1. 단기: 정량 기준(함수 20줄, 순환 복잡도 10 이하 등)을 린터로 자동 강제함
2. 중기: 리팩터링(092 참조)과 병행하여 코드 정리를 개발 루틴에 내재화함
3. 장기: 코드 품질 지표와 결함률 상관관계를 분석하여 적정 수준의 기준을 최적화함

> 요약: 정량 기준 자동화-루틴화-최적화 순서로 클린 코드를 정착시킴

## Ⅵ. 전망
- 발전 방향: AI 코드 어시스턴트가 작성 시점에 클린 코드 원칙 위반을 즉시 제안하는 추세임
- 기술사적 판단: 클린 코드는 기술 부채(091 참조) 예방의 1차 방어선으로 위치함
- 기술사 제언: 코딩 표준을 조직 자산으로 관리하고 온보딩 과정에 포함할 필요
