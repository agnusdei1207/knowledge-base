# 📖 【암기용】 개념 완전 이해

> 목적: 시계열 데이터베이스를 처음 봐도 완벽히 이해하게 만든다. 시험 답안 양식이 아니라, 이해를 위한 친절한 설명이다.

## 한눈에
- **개요**: 시계열 데이터베이스(TSDB)는 **시간(timestamp)을 1차 축**으로 삼아 시간순으로 계속 쌓이는 측정 데이터를 저장·압축·집계하는 데 특화된 데이터베이스다.
- **왜 필요한가**: 서버 CPU, IoT 센서, 주가, 로그 메트릭은 끊임없이 append되고 조회는 대부분 "최근 5분·1시간·30일" 같은 시간 범위 집계다. 일반 RDB에 행 단위로 그대로 쌓으면 쓰기량·인덱스 크기·보관 비용이 감당 안 되는 속도로 커진다.
- **핵심 직관**: 병원 체온표처럼 모든 기록에 시각 도장을 찍어 순서대로 적고, 오래된 기록은 날짜별로 요약해 저해상도로 줄여 보관하는 구조다.

## 핵심 용어 정리
| 용어 | 의미 | 비유 |
|:---|:---|:---|
| 시계열 데이터(Time Series Data) | 시간 순서대로 발생하는 측정값의 연속 — TSDB가 저장·조회에 특화하는 상위 대상 | 시간 도장이 찍힌 기록들 |
| Timestamp | 데이터가 발생한 시각 — 시계열 데이터의 필수 축 | 기록에 찍힌 시각 도장 |
| Metric(측정 지표) | 무엇을 측정했는지의 이름(예: `cpu_usage`) | 온도계의 이름표 |
| Tag/Label(태그) | 측정을 구분하는 차원 값(예: `host=server01`, `region=seoul`) | 서류 분류 라벨 |
| Field/Value | 실제로 측정된 수치값 | 온도계가 가리키는 숫자 |
| Cardinality(카디널리티) | 고유한 태그 조합(하나의 series)의 총 개수 | 라벨 조합의 가짓수 |
| Time Partition | 시간 구간별로 나눈 저장 단위(예: 1일 단위 파티션) | 날짜별 서랍 |
| Downsampling(다운샘플링) | 오래된 원본 데이터를 더 낮은 해상도(예: 1분→1시간 평균)로 요약해 용량을 줄이는 과정 | 사진을 저해상도로 축소 보관 |
| Rollup | 다운샘플링으로 만든 요약 집계 데이터(예: 시간별 평균·최대) | 요약본 |
| Retention Policy(보존 정책) | 데이터를 얼마나 보관하고 언제 삭제·축소할지 정하는 규칙 | 서류 보관 연한 |
| 압축(Delta/XOR Encoding) | 연속된 timestamp·value의 "차이"만 저장해 용량을 줄이는 기법 | 매번 전체 주소 대신 "어제와 다른 부분만" 적기 |

## 깊이 이해

### 왜 일반 RDB로는 부족한가 (수치로 이해)
- 서버 5,000대가 10초마다 CPU·메모리·디스크 등 20개 메트릭을 보낸다고 하면, 초당 포인트 수는 `5,000 × 20 ÷ 10 = 10,000 points/sec`이고, 하루로 환산하면 `10,000 × 86,400 = 864,000,000` 포인트가 쌓인다.
- 이 양을 RDB에 행 단위로 그대로 넣으면 매 삽입마다 B-Tree 인덱스를 갱신해야 해 쓰기가 갈수록 느려지고, 인덱스 자체도 거대해진다. TSDB는 애초에 이 정도 쓰기량을 전제로 append 전용 구조와 압축을 설계한다.

### Cardinality 폭발 — 판별 원리를 수치로 이해
- series 수는 대략 "각 태그의 고유값 개수를 모두 곱한 값"이다. 예: `host`(100개) × `region`(5개) × `metric`(20개) = 10,000 series라면 정상 범주다.
- 여기에 `user_id`처럼 고유값이 100만 개인 태그를 하나 추가하면, series 수는 `10,000 × 1,000,000 = 100억` 규모로 폭증한다. TSDB는 series마다 별도의 인덱스 엔트리(태그 조합→저장 위치 매핑)를 유지하므로, series가 폭증하면 이 인덱스 자체가 메모리를 다 먹어 시스템이 멎는다 — 이것이 "cardinality bomb"의 원리이며, 그래서 사용자 ID·요청 ID처럼 고유값이 무한히 늘어나는 값은 태그가 아니라 value(필드)로 저장해야 한다.

### 압축 원리 — Delta/XOR Encoding
- timestamp는 대개 일정한 간격(예: 10초)으로 들어오므로, "직전 값과의 차이(delta)"만 저장하면 대부분 같은 값(0)이 반복돼 매우 잘 압축된다.
- value(수치)도 직전 값과 비트 단위로 XOR을 취하면 변화가 적은 구간에서는 앞·뒤 비트가 대부분 같아 0이 많이 나온다. 이런 기법을 결합하면 포인트당 원래 16바이트(timestamp 8바이트+value 8바이트) 수준이던 저장 용량을 1~2바이트 수준으로, 즉 10배 이상 압축할 수 있다.

### Retention·Downsampling 워크드 예제 (수치로 이해)
- 정책 예: 원본(10초 해상도)은 7일 보존, 1분 rollup은 90일 보존, 1시간 rollup은 1년 보존.
- 원본 7일 용량: `864,000,000 points/day × 7 = 6,048,000,000` 포인트.
- 1분 rollup 90일 용량: 10초 데이터를 1분(6개) 단위로 압축하면 초당 포인트가 `10,000 ÷ 6 ≈ 1,667`로 줄어 하루 약 `144,000,000` 포인트, 90일이면 약 `12,960,000,000`이지만 원본보다 포인트당 크기가 훨씬 작고 조회 시 스캔량이 원본 대비 6분의 1로 줄어든다.
- 이렇게 최근 데이터는 고해상도로, 오래된 데이터는 저해상도로 유지하는 것이 저장 비용과 조회 속도를 동시에 잡는 핵심 전략이다.

### 비유 정리
- 병원 체온표가 매 시각 측정값을 순서대로 적고, 오래된 기록은 일별 평균과 이상 구간만 남기듯, TSDB는 최근 데이터는 원본 그대로, 오래된 데이터는 요약(rollup)으로 갈아치운다.

### 흔한 오해
- 시계열 DB는 로그 원문을 전부 저장하는 범용 로그 저장소가 아니다. 자유 텍스트 검색이나 임의 조건 검색이 중심이면 검색엔진·로그 저장소가 더 적합하고, TSDB는 "시간 범위 + 태그 조건"으로 좁혀지는 수치 집계 조회에 최적화돼 있다.

## 연결 개념
- 관측성(Observability) — metrics·logs·traces 중 TSDB는 metrics를 저장하는 축을 담당한다.
- LSM-Tree — append 중심 쓰기 구조라는 점에서 Cassandra(124)의 저장 엔진과 원리가 유사하다.
- 데이터 보존 정책 — retention·downsampling·compaction이 저장 비용과 조회 성능의 트레이드오프를 결정한다.

## Ⅰ. 개요 및 필요성

- 개요: 시계열 DB는 시간순 측정값 저장소이다.
- 배경: 관측성·IoT·금융 데이터는 지속 발생하고 최근 시간 범위 조회와 집계가 집중된다.
- 필요성: 시간 파티션, 압축, 보존 정책으로 대량 쓰기와 장기 저장 비용을 제어한다.

---

## Ⅱ. 구조 및 구성요소

```text
Agent/Sensor -> Ingestion -> Time Partition -> Compressed Block -> Query Engine
                 +-> Tag Index
                 +-> Retention/Downsampling
```

| 구성요소 | 역할 | 특이사항 |
|:---|:---|:---|
| Data Point | timestamp, tag, value 저장 | append 중심 입력 |
| Tag Index | host, region, service 필터링 | cardinality 관리 필요 |
| Time Partition | 시간 구간별 저장 단위 | 최근 구간 조회 최적화 |
| Retention | 보존·삭제·다운샘플 정책 | 7일 원본, 1년 집계 예시 |

> 요약: 시계열 DB는 시간 파티션과 태그 인덱스를 중심으로 수집·저장·집계가 구성됨.

## Ⅲ. 동작원리 및 흐름도

```text
Metric Collect -> Timestamp Normalize -> Tag Index Update -> Block Write -> Range Query -> Aggregate
```

| 단계 | 처리 내용 | 검증 기준 |
|:---:|:---|:---|
| 1 | 에이전트·센서가 측정값 전송 | ingestion rate points/sec |
| 2 | timestamp 정규화와 태그 검증 | clock skew, tag whitelist |
| 3 | 시간 파티션에 append 저장 | write latency p95 |
| 4 | 압축·compaction·retention 적용 | compression ratio |
| 5 | 시간 범위와 태그 조건으로 집계 | query latency p95 |

> 요약: 시계열 DB는 수집값을 시간 파티션에 append하고, 조회 시 시간 범위와 태그로 집계함.

## Ⅴ. 심화 비교 및 적용 판단

| 구분 | 기존/대안 | 본 키워드 | 선택 기준 |
|:---|:---|:---|:---|

> 요약: 시계열 DB 선택은 포인트 수, 시간 범위 쿼리, 보존 정책으로 결정한다.

| 리스크 | 원인 | 대응 방안 | 확인 지표 |
|:---|:---|:---|:---|

| 저장 비용 증가 | 원본 장기 보존 | downsampling, retention 30/365일 | GB/day, compression ratio |
| 지연 조회 | 넓은 범위 고해상도 쿼리 | rollup table, query limit | query p95, scanned blocks |

> 요약: 시계열 DB 리스크는 태그 수, 보존 기간, 조회 범위를 기준으로 통제함.

| 점검 항목 | 목표 기준 | 측정 방법 |
|:---|:---|:---|
| 수집 | ingest rate 목표 대비 120% 여유 | ingestion metric |
| 저장 | compression ratio 5:1 이상 | storage report |
| 조회 | 최근 1시간 p95 1초 이하 | query log |

> 요약: 시계열 DB는 수집 여유율, 압축률, 시간 범위 조회 지연으로 평가함.

## Ⅵ. 실무 적용 및 결론

**적용 방안 3개 (필수 — 단계별 또는 항목별):**
1. metric name, tag whitelist, label cardinality 한도를 사전에 정의해 사용자 ID·요청 ID 태그화를 차단함.
2. 원본 7~30일, 1분 rollup 90일, 1시간 rollup 1년 같은 retention/downsampling 정책을 적용함.
3. 대시보드는 최근 1시간·24시간 쿼리에 맞춰 사전 집계하고, 장기 분석은 데이터 레이크로 이관함.

**결론 (2줄):**
- 기술사 판단: 시간 범위 집계와 지속 수집이 핵심이면 시계열 DB, 임의 조건 검색이 핵심이면 검색/분석 DB를 선택함.
- 향후 방향: 관측성 플랫폼은 metrics·logs·traces를 연계해 SLO와 장애 원인 분석을 자동화하는 방향으로 발전함.
