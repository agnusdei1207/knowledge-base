## Ⅰ. 개요
- **정의**: 프로그램 실행 중(런타임)에 바이트코드를 네이티브 기계어로 변환하여 실행 성능을 높이는 컴파일러
- **배경/필요성**: 인터프리터의 반복 해석 오버헤드(183 참조)를 제거하면서도 플랫폼 독립성을 유지하기 위해 런타임 컴파일이 필요함
- **비유**: 자주 가는 길을 처음엔 지도 보며 가다가, 익숙해지면 지도 없이 최단 경로로 달리는 것과 유사함

| 출제 의도 | 반드시 짚을 핵심 | 감점 회피 포인트 |
|:---|:---|:---|
| JIT 동작 원리와 AOT(185 참조) 대비 차이 | 핫스팟 탐지·프로파일 기반 최적화·코드 캐시 | 워밍업 지연(Warm-up Latency) 존재 명시 |

> 요약: 런타임 프로파일 정보를 활용해 핫 코드를 네이티브로 변환하는 동적 컴파일 기법임

## Ⅱ. 구성요소
```text
Bytecode Input
      |
      v
+-----------------+
| Profiler        |---> Hotspot Detection
+-----------------+
      |
      v
+-----------------+
| JIT Compiler    |---> Native Code
+-----------------+
      |
      v
+-----------------+
| Code Cache      |---> Reuse
+-----------------+
```

| 구성요소 | 설명 | 비유 |
|:---|:---|:---|
| 프로파일러 | 메서드 호출 횟수·분기 빈도를 추적하여 핫스팟 식별 | 교통량 측정 카메라 |
| JIT 컴파일러 | 핫스팟 바이트코드를 네이티브 코드로 변환, 인라이닝·루프 언롤링 적용 | 자주 쓰는 문서를 암기 |
| 코드 캐시 | 컴파일된 네이티브 코드를 메모리에 저장하여 재호출 시 재사용 | 암기한 내용을 노트에 정리 |

> 요약: 프로파일링-컴파일-캐싱의 순환으로 실행 중 점진적 성능 향상을 달성함

## Ⅲ. 절차
```text
바이트코드 실행 --> 프로파일 수집 --> 임계치 도달 --> 네이티브 컴파일 --> 캐시 저장/실행
```
- 1단계: VM이 바이트코드를 인터프리터로 실행하며 프로파일 데이터 수집
- 2단계: 메서드 호출 카운터가 임계치에 도달하면 해당 메서드를 핫스팟으로 판정
- 3단계: JIT 컴파일러가 프로파일 정보(타입 피드백·분기 확률)를 활용해 최적화된 네이티브 코드 생성
- 4단계: 생성된 네이티브 코드를 코드 캐시에 저장하고, 이후 호출 시 네이티브 코드로 분기

> 요약: 인터프리트-프로파일-컴파일-캐시의 4단계로 점진적 최적화를 수행함

## Ⅳ. 문제점
- 워밍업 지연: 초기 인터프리트 구간에서 응답 시간이 느림 — 서버리스·단기 프로세스에 불리
- 메모리 오버헤드: 코드 캐시·프로파일 데이터가 추가 메모리를 소비함 — 메모리 제약 환경에서 부담
- 탈최적화 비용: 타입 가정 위반 시 컴파일된 코드를 폐기하고 인터프리터로 회귀함 — 간헐적 성능 저하

> 요약: 워밍업·메모리·탈최적화가 JIT의 주요 한계임

## Ⅴ. 개선방안
1. 단기: 계층형 컴파일(C1/C2) 도입으로 빠른 초기 컴파일과 점진적 고성능 컴파일 병행
2. 중기: 프로파일 데이터 사전 수집(PGO) 및 AOT 캐시(185 참조)로 워밍업 구간 단축
3. 장기: GraalVM(190 참조) 등 다중 언어 JIT 프레임워크로 메모리 공유 및 크로스 언어 인라이닝 구현

> 요약: 계층 컴파일·PGO·다중 언어 프레임워크로 JIT 한계를 보완함

## Ⅵ. 전망
- 발전 방향: 프로파일 기반 최적화와 AOT 사전 컴파일의 경계가 점차 모호해지는 추세
- 기술사적 판단: 클라우드 네이티브 환경에서 시작 시간 단축 요구로 JIT+AOT 혼합 모델 확산
- 기술사 제언: 워크로드 수명 주기에 따라 JIT/AOT 비율을 동적으로 조절하는 적응형 런타임 전략 수립이 필요함
