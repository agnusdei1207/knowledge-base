# 📖 【암기용】 개념 완전 이해

## 한눈에
- **개요**: 분산 시스템 간에 데이터를 주고받는 두 가지 대표적인 웹 서비스 아키텍처 스타일
- **왜 필요한가**: 시스템 간 통합(EAI, B2B)이 늘어나면서, 엄격한 규칙으로 통신할 것인지(SOAP), 가볍고 직관적으로 통신할 것인지(REST) 설계 방향을 결정해야 하기 때문
- **핵심 직관**: SOAP는 복잡한 서류 봉투에 도장을 꽉꽉 찍어 보내는 '등기 우편(규격 철저)'이고, REST는 내용을 쉽게 알아볼 수 있는 '엽서(가볍고 유연함)'다.

## 핵심 용어 정리

| 용어/표기 | 의미 | 비유·예 |
|:---|:---|:---|
| SOAP (Simple Object Access Protocol) | XML 기반의 복잡하고 엄격한 프로토콜 | "격식을 차린 공식 공문서" |
| REST (Representational State Transfer) | HTTP 자원 중심의 아키텍처 스타일 | "주소와 동작이 명확한 메모지" |
| WSDL (Web Services Description Language) | SOAP에서 서비스 인터페이스를 설명하는 XML 문서 | "이 기계의 상세 사용 설명서" |

## 깊이 이해
- **배경·문제의식**: 2000년대 초반, 서로 다른 언어와 플랫폼이 통신하기 위해 SOAP라는 강력하고 무거운 표준을 만들었다. 하지만 모바일 시대가 열리고 빠르고 가벼운 통신이 필요해지면서, 사람들은 복잡한 XML 껍데기(Envelope)를 벗어 던지고 HTTP 본연의 기능(메서드와 URI)을 활용하는 REST를 선호하게 되었다.
- **작동 원리**: **SOAP**는 HTTP를 단순히 통신 채널(터널)로만 쓴다. 헤더와 바디가 엄격히 정의된 XML 덩어리(Envelope)를 POST로만 주고받으며 자체적인 보안(WS-Security)과 트랜잭션 표준을 갖는다. 반면 **REST**는 HTTP 자체를 적극 활용한다. 자원을 URI(`/users/1`)로 정의하고, 행위를 HTTP 메서드(GET, POST, PUT, DELETE)로 매핑하며, 포맷은 주로 가벼운 JSON을 쓴다.
- **비유**: SOAP로 은행 송금을 하려면 10장짜리 계약서(XML)를 정확한 양식에 맞춰 전송해야 처리된다. REST로 조회하려면 은행 창구(URI)에 가서 "조회(GET)해주세요"라고 말하면 메모장(JSON)에 잔액을 적어주는 식이다.
- **구체 예시**: 기상청 날씨 조회. SOAP는 껍데기 태그(`<soapenv:Envelope>`) 안에 복잡한 요청을 말아 보내고 XML로 받는다. REST는 `GET /weather/seoul`을 보내면 `{ "temp": 24 }`라는 JSON을 즉각 받는다.
- **흔한 오해·주의점**: "SOAP는 구식이고 REST가 무조건 정답이다"는 틀린 말이다. 금융 결제나 항공 예약처럼 메시지의 무결성 보장, 분산 트랜잭션, 엔터프라이즈급 보안(WS-Security)이 필요할 때는 여전히 SOAP의 엄격함이 요구된다.

## 연결 개념
- HTTP 메서드 — REST 행위의 근간
- XML vs JSON — 두 구조가 주로 사용하는 데이터 포맷의 차이
- 마이크로서비스 아키텍처(MSA) — REST가 대세로 자리 잡은 배경

# 📝 【답안용】 시험 답안 템플릿

## 핵심 인사이트 (3줄 요약)

> 1. **본질**: SOAP는 엄격한 표준과 규격을 갖춘 '프로토콜'이며, REST는 HTTP 인프라를 본연의 목적대로 활용하는 '아키텍처 스타일'임
> 2. **가치**: SOAP는 강력한 보안과 트랜잭션 무결성을 제공하고, REST는 가벼운 메시징과 유연성으로 모바일 및 MSA 환경에 최적화됨
> 3. **판단 포인트**: 데이터 포맷의 유연성, 성능 요건, 트랜잭션의 복잡성을 기준으로 비즈니스 특성(금융 vs 모바일 서비스)에 맞게 취사 선택해야 함

## 출제 의도 및 답안 포인트

| 출제 의도 | 반드시 짚을 핵심 | 감점 회피 포인트 |
|:---|:---|:---|
| 웹 서비스 연계 기술의 특징 비교 및 적합성 판단 역량 | 프로토콜(SOAP) vs 스타일(REST), 데이터 포맷, 보안(WS-Security vs TLS/OAuth) | REST를 프로토콜이라고 단정하는 오류 |

> 요약: 두 기술은 경쟁 관계라기보다 트랜잭션 강건성(SOAP)과 아키텍처 유연성(REST)의 트레이드오프를 갖는 대안임

---

## Ⅰ. 개요 및 필요성

- 개요: 서로 다른 분산 시스템 간에 네트워크를 통해 기능과 데이터를 교환하기 위해 사용하는 웹 서비스 연계 기술 표준임
- 배경: 이기종 시스템 통합 요구(SOAP 등장)와 경량화된 모바일/MSA 환경의 확산(REST 대두)
- 필요성: 서비스 연계 시 페이로드 크기, 개발 생산성, 트랜잭션 신뢰성 요구 수준을 고려한 최적의 인터페이스 설계 방식 선택 절실

---

## Ⅱ. 구조 및 구성요소

```text
[SOAP 구조] HTTP 터널링 -> XML Envelope (Header + Body) -> 엄격한 검증
[REST 구조] HTTP Method -> URI (자원 식별) -> JSON 페이로드 -> 경량화 처리
```

| 구성요소 | SOAP의 특성 | REST의 특성 |
|:---|:---|:---|
| 자원 표현 | 오직 XML (Envelope, Header, Body 구조) | JSON, XML, Plain Text 등 다양 |
| 서비스 정의 | WSDL (XML 기반 엄격한 스펙 문서) | OpenAPI (Swagger), WADL, 유연함 |
| 전송 프로토콜 | HTTP, SMTP, TCP 등 다중 프로토콜 지원 | 오직 HTTP 웹 표준에 의존 |

> 요약: SOAP는 메시지 자체에 엄격한 구조(Envelope)를 강제하고, REST는 HTTP와 URI 자원 중심으로 가볍게 통신함

---

## Ⅲ. 동작원리 및 흐름도

```text
[클라이언트] -> (SOAP: POST/XML) / (REST: GET·POST/JSON) -> [네트워크] -> [서버 처리 및 응답]
```

- 1단계 [요청 조립]: SOAP는 클라이언트가 WSDL을 참조해 XML 봉투를 생성, REST는 URI와 HTTP 메서드만으로 단순 조립
- 2단계 [요청 전송]: SOAP는 대부분 HTTP POST로 전송, REST는 리소스의 CRUD에 맞춰 GET/POST/PUT/DELETE 전송
- 3단계 [서버 검증]: SOAP는 WS-Security 및 봉투 규격에 따른 엄격한 파싱, REST는 헤더와 라우팅 기반의 유연한 파싱
- 4단계 [응답 반환]: SOAP는 정형화된 XML 오류 코드(Fault) 또는 결과 반환, REST는 HTTP 상태 코드(200, 404 등)로 결과 직관적 반환

> 요약: SOAP는 캡슐화된 메시지 규격을 뜯어서 처리하며, REST는 HTTP 표준 동작 자체에 의존하여 응답함

---

## Ⅳ. 특징
- 유연성 측면: REST는 JSON 포맷을 사용하여 프론트엔드(JavaScript)와 완벽히 호환되며 파싱 오버헤드가 적어 MSA에 적합
- 보안 및 신뢰성: SOAP는 WS-Security, WS-ReliableMessaging 등 자체 표준으로 엔터프라이즈 수준의 종단간 무결성 보장
- 캐싱 능력: REST는 HTTP GET을 사용하므로 인프라(CDN, 웹서버) 수준의 캐싱이 기본 지원되지만, SOAP는 모든 요청이 POST라 기본 캐싱이 불가

---

## Ⅴ. 심화 비교 및 적용 판단

| 비교 축 | SOAP | REST | 선택 기준 |
|:---|:---|:---|:---|
| 설계 철학 | 행위 중심 (Operation-centric) | 자원 중심 (Resource-centric) | 도메인 모델 복잡도 |
| 상태 관리 | Stateful 작업 지원 용이 | 무상태성 (Stateless) 강제 | 서버의 세션 유지 필요성 |
| 보안 통제 | WS-Security 내장 (메시지 암호화) | TLS, OAuth 등 전송망 의존 | 종단간 보안 요구 수준 |
| 적용 분야 | B2B 결제, 금융, 레거시 통합 | 모바일 앱, Open API, MSA 연동 | 트랜잭션 신뢰성 vs 성능 |

> 요약: 강력한 트랜잭션과 보안이 필요하면 SOAP를, 빠른 개발과 가벼운 데이터 전송이 필요하면 REST를 선택함

**리스크·대응 (기본은 불릿):**
- SOAP 성능 병목: XML 파싱으로 인한 오버헤드 발생 → Payload 크기 최적화 및 MTOM(바이너리 첨부) 표준 활용 (지표: API 응답 지연 시간)
- REST 트랜잭션 한계: 분산 환경에서 ACID 보장 취약 → Saga 패턴 연계 및 보상 트랜잭션(Compensating Transaction) 설계로 일관성 확보 (지표: 데이터 불일치 건수)

**도입 후 점검 지표 (기본은 불릿):**
- 대역폭 효율: JSON 도입(REST) 후 기존 XML(SOAP) 대비 API 페이로드 크기 감소율 — 네트워크 트래픽 분석
- 개발 리드타임: API 명세(Swagger 등) 공유 후 클라이언트 개발팀의 연동 완료까지 소요되는 시간 단축률 — 애자일 스프린트 리포트

## Ⅵ. 실무 적용 및 결론

**적용 방안 3개:**
1. 아키텍처 혼용 (Bi-modal): 금융사의 경우 코어뱅킹 간 통신은 SOAP를 유지하고, 모바일 앱 클라이언트와의 통신은 API Gateway를 거쳐 REST로 변환(Mediation)
2. REST 설계 표준화: URI에 동사 금지, 명사 복수형 사용, HTTP 상태 코드의 정확한 반환 등 성숙도 모델(Richardson Maturity Model) 기반의 API 표준 가이드라인 수립
3. REST 보안 강화: SOAP의 WS-Security 부재를 보완하기 위해 API Gateway에서 OAuth 2.0 인가와 JWT 토큰 기반 인증, mTLS를 전면 적용

**결론 (2줄):**
- 기술사 판단: 최근 신규 구축의 90% 이상이 REST(또는 gRPC/GraphQL)를 채택하고 있으나, 기존에 투자된 레거시 통합망(ESB)을 무리하게 들어낼 필요는 없음
- 향후 방향: REST의 오버헤드마저 부담되는 마이크로서비스 내부 통신 환경에서는 바이너리 프로토콜인 gRPC가 SOAP와 REST의 대안으로 부상 중임
