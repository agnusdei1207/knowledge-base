# 📖 【암기용】 개념 완전 이해

> 목적: SOAP와 REST를 처음 보는 사람도 프로토콜 중심 방식과 리소스 중심 아키텍처 스타일의 차이를 이해하게 만든다. 시험 답안 양식이 아니라, 이해를 위한 설명이다.

## 한눈에
- **개요**: SOAP는 XML 메시지 기반 프로토콜이고, REST는 HTTP 리소스와 메서드를 활용하는 아키텍처 스타일이다.
- **왜 필요한가**: API 설계에서 보안·트랜잭션·계약 엄격성이 필요한지, 웹·모바일 연동과 캐시가 필요한지에 따라 선택이 달라진다.
- **핵심 직관**: SOAP는 규격이 촘촘한 공문서 교환, REST는 URL과 HTTP 동사로 자원을 다루는 웹 방식이다.

## 깊이 이해
- **배경·문제의식**: 기업 시스템은 이기종 연동과 계약 안정성이 필요했고 SOAP는 WSDL, WS-Security, WS-ReliableMessaging을 제공했다. 웹 API 확산 후 REST는 단순한 HTTP 활용과 JSON 기반 경량 연동으로 널리 쓰였다.
- **작동 원리**: SOAP는 Envelope, Header, Body로 XML 메시지를 만들고 WSDL로 서비스 계약을 정의한다. REST는 URI로 자원을 식별하고 GET, POST, PUT, PATCH, DELETE로 상태를 전송한다.
- **비유**: SOAP는 양식이 정해진 등기우편이고, REST는 표준 주소와 동작 규칙으로 처리하는 웹 요청이다.
- **구체 예시**: 금융기관 간 정산처럼 메시지 무결성, 서명, 재전송 보장이 필요한 업무는 SOAP가 남아 있고, 모바일 상품 조회 API는 REST+JSON이 일반적이다.
- **흔한 오해·주의점**: REST는 단순히 JSON을 쓰는 API가 아니다. 리소스 식별, 무상태성, 표준 메서드, 캐시 가능성 같은 제약을 만족해야 한다.

## 연결 개념
- RESTful API 설계 원칙: REST의 구체 설계 기준
- WSDL/WS-Security: SOAP의 계약과 보안 확장
- gRPC/GraphQL: REST 이후 API 대안

# 📝 【답안용】 시험 답안 템플릿

> 목적: SOAP와 REST를 정의 나열이 아니라 계약, 보안, 성능, 운영 관점의 선택 기준으로 비교한다.
> 핵심: 출제자는 "REST가 더 최신"이라는 단정이 아니라 업무 요구사항별 API 방식 선택 판단을 본다.

## 핵심 인사이트 (3줄 요약)

> 1. **본질**: SOAP는 XML 기반 메시징 프로토콜, REST는 HTTP 리소스 중심 아키텍처 스타일이다.
> 2. **가치**: SOAP는 엄격한 계약·보안 확장이 필요한 B2B 연동에, REST는 웹·모바일·마이크로서비스 API에 적합하다.
> 3. **판단 포인트**: 트랜잭션 신뢰성, 메시지 보안, 캐시, 개발 생산성, 클라이언트 다양성을 기준으로 선택해야 한다.

## 출제 의도 및 답안 포인트

| 출제 의도 | 반드시 짚을 핵심 | 감점 회피 포인트 |
|:---|:---|:---|
| API 연동 방식 비교 역량 확인 | SOAP 프로토콜 vs REST 스타일 | SOAP=구식, REST=최신으로 단정 |
| 보안·계약 요구 판단 확인 | WSDL, WS-Security, HTTP 메서드, JSON | JSON 여부만 비교 |
| 업무별 선택 기준 확인 | 금융 B2B, 모바일 API, MSA | 적용 사례와 제약 누락 |

> 요약: SOAP vs REST 답안은 기능 차이보다 업무 요구사항에 따른 선택 기준을 제시해야 한다.

---

## Ⅰ. 개요 및 필요성

SOAP와 REST는 시스템 간 API 연동 방식이다. 기업 시스템은 보안, 계약, 트랜잭션, 성능, 개발 편의 조건이 업무별로 다르다. 두 방식을 비교해 B2B 연동, 웹 API, MSA 환경에 맞는 인터페이스를 선택해야 한다.

---

## Ⅱ. 구조 및 구성요소

```text
SOAP Client -> XML Envelope -> SOAP Service -> WSDL Contract
REST Client -> URI Resource -> HTTP Method -> JSON/XML Response
```

| 구성요소 | SOAP | REST |
|:---|:---|:---|
| 메시지 구조 | XML Envelope, Header, Body | HTTP URI, Header, Body |
| 계약 | WSDL 기반 엄격 계약 | OpenAPI 등 선택 적용 |
| 보안 | WS-Security, XML Signature | TLS, OAuth2, JWT |
| 전송 | HTTP, SMTP 등 | HTTP 중심 |

> 요약: SOAP는 메시지 프로토콜과 계약 규격이 중심이고, REST는 HTTP 리소스와 메서드가 중심이다.

---

## Ⅲ. 동작원리 및 흐름도

```text
요구사항 식별 -> 계약 엄격성/보안/캐시 필요 판단
-> SOAP 또는 REST 선택 -> 스키마/API 문서 정의 -> 테스트/운영
```

| 단계 | 처리 내용 | 검증 기준 |
|:---:|:---|:---|
| 1 | 업무 연동 요구 분석 | B2B, 모바일, 내부 MSA |
| 2 | 계약·보안 수준 판단 | WSDL, WS-Security, OAuth2 |
| 3 | 메시지 형식 결정 | XML, JSON, MTOM |
| 4 | 오류 처리 설계 | SOAP Fault, HTTP Status |
| 5 | 운영 검증 | p95 지연, 실패율, 호환성 |

> 요약: API 방식은 기술 선호가 아니라 계약 엄격성, 보안 확장, 클라이언트 특성에 따라 결정한다.

---

## Ⅳ. 특징

| 구분 | SOAP | REST | 판단 포인트 |
|:---|:---|:---|:---|
| 표준성 | WS-* 확장 풍부 | HTTP 표준 활용 | 보안·신뢰 메시징 요구 |
| 데이터 형식 | XML 중심 | JSON/XML 등 | 모바일 대역폭 |
| 상태 | 상태 유지 가능 | 무상태성 권장 | 수평 확장 |
| 캐시 | 별도 설계 | HTTP Cache 활용 | 조회 API 비율 |
| 오류 | SOAP Fault | HTTP Status Code | 클라이언트 처리 일관성 |

> 요약: SOAP는 계약과 보안 확장, REST는 HTTP 생태계와 클라이언트 호환성에서 선택 근거가 갈린다.

---

## Ⅴ. 심화 비교 및 적용 판단

| 비교 축 | 기존/대안 | 본 키워드 | 선택 기준 |
|:---|:---|:---|:---|
| 구조 | SOAP | REST | 웹·모바일·MSA 조회 API |
| 비용/성능 | XML 파싱 비용 | JSON과 HTTP 캐시 | p95 지연·대역폭 제약 |
| 운영/위험 | 엄격 계약과 복잡도 | 느슨한 계약과 버전 관리 | API 변경 빈도 |

> 요약: 금융 B2B·정산은 SOAP, 공개 웹 API와 내부 MSA는 REST를 우선 검토하되 계약 요구가 기준이다.

| 리스크 | 원인 | 대응 방안 | 확인 지표 |
|:---|:---|:---|:---|
| SOAP 복잡도 | WS-* 설정 과다 | 표준 프로파일과 계약 테스트 | 상호운용 테스트 통과율 |
| REST 오남용 | RPC식 URI 설계 | 리소스 중심 URI와 HTTP 메서드 | 4xx/5xx 오류율 |
| 버전 충돌 | 클라이언트 변경 관리 미흡 | OpenAPI, 버전 정책, Deprecation | 호환성 테스트 통과율 |

> 요약: SOAP는 상호운용 복잡도, REST는 리소스 설계와 버전 관리 실패가 주된 리스크이다.

| 점검 항목 | 목표 기준 | 측정 방법 |
|:---|:---|:---|
| 성능 | p95 지연 300ms, 오류율 0.1% 이하 | APM, Gateway 로그 |
| 계약 | 스키마 호환성 100% | WSDL/OpenAPI 테스트 |
| 보안 | TLS 1.2 이상, OAuth2 또는 WS-Security 적용 | 보안 스캔, 인증 로그 |

> 요약: API 선택 후에는 지연시간, 계약 호환성, 인증·암호화 적용 여부를 함께 점검한다.

---

## Ⅵ. 실무 적용 및 결론

**적용 방안 3개:**
1. 금융 정산·기관 B2B처럼 서명, 암호화, 엄격 계약이 필요한 업무는 SOAP+WSDL+WS-Security를 적용함
2. 모바일·웹·MSA API는 REST+JSON+OpenAPI+OAuth2를 적용하고 GET 조회 API에는 Cache-Control과 ETag를 설계함
3. 전환 프로젝트는 SOAP Adapter 또는 API Gateway를 두고 계약 테스트, 성능 테스트, 보안 테스트를 배포 전 자동화함

**결론 (2줄):**
- 기술사 판단: SOAP와 REST 선택은 신구 기술 문제가 아니라 계약 엄격성, 보안 확장, 클라이언트 생태계 기준으로 결정함
- 향후 방향: REST는 OpenAPI·API Gateway 중심으로, 고성능 내부 통신은 gRPC, 복합 조회는 GraphQL과 병행 검토함
