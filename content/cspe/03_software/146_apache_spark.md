## Ⅰ. 개요
- **정의**: 인메모리 기반 분산 데이터 처리 엔진으로, 배치·스트림·ML·그래프 워크로드를 통합 API로 처리하는 프레임워크임
- **배경/필요성**: MapReduce의 디스크 I/O 병목을 해소하고, 다양한 분석 워크로드를 단일 엔진에서 수행할 필요가 있음
- **비유**: 여러 요리(배치·스트림·ML)를 하나의 주방(엔진)에서 동시에 조리하는 만능 주방임

| 출제 의도 | 반드시 짚을 핵심 | 감점 회피 포인트 |
|:---|:---|:---|
| 분산 처리 엔진 아키텍처 이해 | RDD/DataFrame, DAG 실행, 인메모리 캐싱 | Hadoop MapReduce와 대체 관계가 아닌 보완 관계로 서술 |

> 요약: 인메모리 DAG 실행으로 디스크 I/O를 줄여 MapReduce 대비 처리 속도를 높인 엔진임

## Ⅱ. 구성요소
```text
[Driver] --> [Cluster Manager] --> [Executor] --> [Task]
                                       |
                                   [RDD/DataFrame]
                                       |
                                   [DAG Scheduler]
```

| 구성요소 | 설명 | 비유 |
|:---|:---|:---|
| Driver | 사용자 프로그램을 실행하고 DAG를 생성·관리하는 마스터 프로세스 | 주방장 |
| Executor | Worker 노드에서 태스크를 병렬 실행하고 데이터를 캐싱하는 프로세스 | 조리사 |
| DAG Scheduler | 변환 연산의 의존관계를 DAG로 구성하고 스테이지를 분할하는 스케줄러 | 조리 순서표 |
| RDD/DataFrame | 분산 데이터 추상화로, 불변·지연 평가(Lazy Evaluation) 특성을 가짐 | 식재료 목록 |

> 요약: Driver-Executor-DAG-데이터 추상화가 Spark의 분산 처리 골격을 구성함

## Ⅲ. 절차
```text
잡제출 --> DAG생성 --> 스테이지분할 --> 태스크실행
```
- 1단계: 잡제출 — 사용자 코드를 Driver가 수신하여 논리 실행 계획 수립
- 2단계: DAG생성 — 변환 연산 간 의존관계를 방향성 비순환 그래프로 구성
- 3단계: 스테이지분할 — 셔플 경계 기준으로 DAG를 스테이지로 나누고 태스크 할당
- 4단계: 태스크실행 — Executor가 파티션 단위로 태스크를 병렬 수행 후 결과 반환

> 요약: 잡-DAG-스테이지-태스크 순서로 분산 처리가 수행됨

## Ⅳ. 문제점
- 셔플 비용: 조인·집계 시 네트워크를 통한 데이터 재분배 발생 — 지연 및 디스크 I/O 증가
- 메모리 부족(OOM): 대규모 데이터셋 캐싱 시 Executor 메모리 초과 — 태스크 실패
- 소규모 파일 문제: 다수의 작은 파일 입력 시 태스크 수 폭증 — 스케줄링 오버헤드 증가

> 요약: 셔플·메모리·소규모 파일이 Spark 성능 저하의 주요 원인임

## Ⅴ. 개선방안
1. 단기: `repartition`·`broadcast join` 활용 및 AQE(Adaptive Query Execution) 활성화로 셔플 최적화
2. 중기: 오프힙 메모리 관리, 스필(Spill) 임계값 조정으로 OOM 발생 빈도 감소
3. 장기: 소규모 파일 병합(Compaction) 자동화 및 Delta Lake 등 테이블 포맷 도입으로 입력 최적화

> 요약: AQE·메모리 튜닝·파일 병합으로 성능 병목을 단계적으로 해소함

## Ⅵ. 전망
- 발전 방향: Spark Connect를 통한 클라이언트-서버 분리, GPU 가속, Photon 엔진 등 처리 효율 강화 추세임
- 기술사적 판단: Spark는 배치-스트림 통합 엔진으로서 데이터 플랫폼의 핵심 처리 계층 지위를 유지 중임
- 기술사 제언: 워크로드 특성(배치/스트림/ML)에 따라 Spark와 Flink의 적합성을 비교 검토할 필요
