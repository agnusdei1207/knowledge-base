## Ⅰ. 개요
- 정의: OS의 핵심 기능을 구성하는 구조적 설계 방식(Monolithic, Micro, Hybrid)
- 배경: 시스템의 성능, 안정성, 확장성 간의 트레이드오프를 최적화하기 위해 발전
- 출제 의도: 아키텍처별 구성 방식의 차이와 그에 따른 장단점 분석 능력 검증

## Ⅱ. 구성요소
```
[ Monolithic ]        [ Micro Kernel ]        [ Hybrid ]
+------------+        +--------------+        +------------+
| App | App  |        | App  | App   |        | App | App  |
+------------+        +--------------+        +------------+
|   Kernel   |        | User Service |        | Non-Core FS|
| (FS, Net,  |        +--------------+        +------------+
|  Drivers)  |        | Micro Kernel |        | Kernel Core|
+------------+        +--------------+        +------------+
```
| 구성요소 | 설명 | 비유 |
| :--- | :--- | :--- |
| 모놀리식 | 모든 OS 서비스를 커널 공간에 통합 (Linux) | 올인원 가전 |
| 마이크로 | 최소 기능만 커널에 두고 나머지는 사용자 공간 (Mach) | 조립식 가구 |
| 하이브리드 | 성능과 구조적 유연성을 절충 (Windows, macOS) | 세미 빌트인 |
> 요약: 모놀리식은 속도 지향, 마이크로는 안정성 및 모듈화 지향임.

## Ⅲ. 절차
```
[App Request] -> [System Call] -> [Kernel Mode Execution] (Monolithic)
[App Request] -> [IPC Message] -> [Kernel] -> [User Service] (Micro)
```
1. 애플리케이션의 자원 요청 시 시스템 호출 또는 IPC 메시지 발생
2. 모놀리식은 커널 내부 함수 호출로 즉각 처리하여 모드 전환 오버헤드 최소화
3. 마이크로는 커널을 거쳐 사용자 공간의 서버(FS, Driver 등)로 메시지 전달 및 응답
4. 하이브리드는 핵심 보안은 커널에, 일부 서비스는 모듈화하여 동적 로드/실행
> 요약: 통신 방식(함수 호출 vs IPC)에 따라 실행 경로가 결정됨.

## Ⅳ. 문제점
- 원인: 모놀리식은 특정 모듈 오류가 전체 시스템 크래시(Crash)로 이어질 위험이 큼
- 원인: 마이크로는 잦은 IPC와 모드 전환으로 인해 성능 저하가 뚜렷함

## Ⅴ. 개선방안
- (단기) 모놀리식 커널에 동적 적재 모듈(LKM) 기술을 적용하여 유연성 확보
- (중기) 마이크로 커널의 IPC 성능 개선을 위한 하드웨어 가속 및 제로 카피 기술 도입
- (장기) 러스트(Rust)와 같은 메모리 안전 언어로 커널을 재작성하여 안정성 근본적 해결

## Ⅵ. 전망
- 보안이 강조되는 임베디드 및 자동차 OS(QNX 등) 분야에서 마이크로 커널 채택 증가
- 성능과 격리를 동시에 만족하기 위한 라이브러리 OS(Unikernel) 형태의 특화 커널 발전 가속화
