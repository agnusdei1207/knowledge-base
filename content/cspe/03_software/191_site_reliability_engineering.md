# 📖 【암기용】 개념 완전 이해

> 목적: SRE를 처음 보는 사람도 서비스 운영과 소프트웨어 공학이 어떻게 결합되는지 이해하게 만든다. 시험 답안 양식이 아니라, 이해를 위한 설명이다.

## 한눈에
- **개요**: **SRE(Site Reliability Engineering)**는 서비스 신뢰성을 사람의 수작업이 아니라 **SLO(목표)·오류 예산·자동화**라는 소프트웨어 공학 방법으로 관리하는 운영 체계다.
- **왜 필요한가**: 장애 대응을 담당자의 경험과 야간 호출에만 의존하면 대응 시간(MTTR)과 재발률이 사람마다 달라지고 개선되지 않는다. SRE는 운영을 수치화·자동화된 엔지니어링 문제로 바꾼다.
- **핵심 직관**: 불이 날 때마다 사람이 뛰어가 끄는 대신, 스프링클러(자동화)와 화재 경보 기준(SLO)을 미리 설계해두는 것과 같다.

## 핵심 용어 정리

| 용어 | 의미 | 비유 |
|:---|:---|:---|
| SRE(Site Reliability Engineering) | 신뢰성을 공학적으로 관리하는 체계 — 이 개념의 정체성 | 소방을 사람 대응에서 자동 소화 설비로 전환 |
| SLI(Service Level Indicator) | 실제로 측정한 지표값(192에서 상세) | 체온계가 읽은 숫자 |
| SLO(Service Level Objective) | SLI가 만족해야 할 내부 목표 수치 | 정상 체온 범위 목표 |
| Error Budget(오류 예산) | SLO에서 허용되는 실패량(100%-SLO) | 다이어트에서 허용된 하루 칼로리 여유분 |
| Burn Rate | 오류 예산을 얼마나 빠르게 소진하는지의 속도 | 기름 게이지가 줄어드는 속도 |
| Toil | 반복적·수동적이고 자동화 가능한데 사람이 계속 하는 운영 작업 | 매번 손으로 물을 긷는 노동(자동 펌프로 대체 가능) |
| Postmortem(포스트모템) | 장애 후 원인·조치·재발방지를 남기는 비난 없는(blameless) 회고 | 사고 후 블랙박스 분석 보고서 |
| On-call / Runbook | 당번 대응 체계 / 정해진 대응 절차서 | 당직표와 매뉴얼 |
| Canary 배포 | 신규 버전을 소수 트래픽에만 먼저 노출하는 점진 배포 | 새 음식을 카나리아에게 먼저 먹여보는 것 |

## 깊이 이해

### 배경 — DevOps 다음 단계로서의 SRE
- 2003년 Google이 처음 SRE 역할을 만들었다. DevOps가 "개발과 운영의 경계를 허문다"는 문화적 원칙이라면, SRE는 그 원칙을 "오류 예산 정책", "SLO 계약", "Toil 상한"처럼 구체적 수치와 프로세스로 구현한 실행 방법론이다.
- 핵심 전제는 "운영 업무도 소프트웨어 문제다"라는 것이다. 반복되는 수동 대응(Toil)은 사람이 아니라 코드가 처리해야 한다고 본다.

### 오류 예산 — 수치로 이해
- 월 SLO 99.9%는 100%-99.9%=0.1%의 실패를 허용한다는 뜻이다. 30일(43,200분) 기준으로 0.1%는 43.2분이다. 즉 한 달에 43.2분까지는 장애가 나도 SLO 위반이 아니다.
- SLO를 99.99%로 올리면 예산은 4.32분으로 10분의 1이 된다. "나인(9)"을 하나 더 붙일 때마다 허용 장애 시간은 약 10배씩 줄어든다 — 이게 신뢰성을 올릴수록 비용과 난이도가 기하급수적으로 커지는 이유다.
- 이 예산은 **배포 허가증**으로 쓰인다. 이번 달 예산을 이미 다 썼다면(예: 장애로 50분을 이미 소진), 남은 기간은 신규 기능 배포보다 안정화 작업을 우선한다 — 배포 속도(개발팀 요구)와 안정성(운영 요구)을 사람의 협상이 아니라 숫자로 자동 조정하는 장치다.

### Burn Rate 알림 — "빠르게 vs 천천히" 소진을 구분
- 오류 예산이 43.2분 있어도, 1시간 만에 다 쓰는 것과 30일에 걸쳐 천천히 쓰는 것은 대응 긴급도가 다르다. Burn rate는 "예산을 정상 속도의 몇 배로 소진 중인가"를 나타낸다.
- 예: burn rate 14.4x는 이 속도가 유지되면 예산이 30일/14.4 ≈ 2.08일 만에 소진된다는 뜻 — 즉시 대응(page)이 필요하다. burn rate 2x는 30일/2=15일 만에 소진되는 속도로, 좀 더 여유 있게(티켓으로) 대응한다.
- 이렇게 소진 속도별로 알림 등급을 나누면, 순간적 스파이크에는 즉시 대응하고 완만한 저하에는 계획적으로 대응할 수 있다 — 무조건 "임계치 초과 = 즉시 알림"보다 알림 피로가 줄어든다.

### Toil 판별 원리 — 이건 자동화 대상인가
- Google SRE가 제시하는 Toil의 특징: 수동(manual)·반복적(repetitive)·자동화 가능(automatable)·장기적 가치가 없음(no enduring value)·서비스 규모에 비례해 증가(scales with growth)하는 작업이 이에 해당한다.
- 예: 매번 사람이 SSH로 접속해 로그를 지우는 작업은 Toil(자동 로그 로테이션으로 대체 가능)이지만, 새로운 장애 유형을 조사해 원인을 찾는 작업은 매번 다르므로 Toil이 아니다.
- SRE 조직은 Toil 비율을 예컨대 월 근무시간의 50% 이하로 상한을 두고, 넘으면 신규 기능 개발보다 자동화를 우선한다.

### 비유와 흔한 오해
- **비유**: 건물 관리자가 고장 날 때마다 사람이 뛰어가 엘리베이터를 고치는 대신, 센서로 이상 진동을 미리 감지하고 정비 일정을 자동 배정하는 시스템을 만드는 것이 SRE다.
- **오해**: SRE는 "장애 대응 당번 조직"의 새 이름이 아니다. SLO·오류 예산·Toil 상한·포스트모템 같은 구체적 정책이 없으면 기존 운영팀 명패만 바꾼 것에 불과하다.

## 연결 개념
- SLO·SLA·SLI — SRE가 다루는 목표·계약·측정값의 구분(192에서 상세)
- Cloud Native Observability — SLI를 측정하기 위한 메트릭·로그·트레이스 기반(188에서 상세)
- Distributed Tracing — SLO 위반 요청의 원인을 span 단위로 분석하는 도구(190에서 상세)

# 📝 【답안용】 시험 답안 템플릿

> 목적: 시험장에서 25분에 그대로 쓰는 답안 양식. SRE는 개념 소개가 아니라 SLO 기반 운영 통제와 자동화 판단으로 답안을 구성한다.
> 핵심: 출제자가 묻는 것은 운영 조직 명칭이 아니라 서비스 신뢰성을 수치·프로세스·자동화로 통제하는 역량이다.

## 핵심 인사이트 (3줄 요약)

> 1. **본질**: SRE는 운영 문제를 소프트웨어 공학으로 해결해 SLO, 오류 예산, 자동화, 포스트모템으로 신뢰성을 관리하는 체계이다.
> 2. **가치**: 장애 대응 MTTR, 알람 소음률, 수동 Toil 비율을 수치화해 배포 속도와 가용성 간 균형을 맞춘다.
> 3. **판단 포인트**: SLO가 없으면 자동화 도구 나열에 머물므로 사용자 영향 지표와 오류 예산 정책을 먼저 제시해야 한다.

## 출제 의도 및 답안 포인트

| 출제 의도 | 반드시 짚을 핵심 | 감점 회피 포인트 |
|:---|:---|:---|
| DevOps 이후 운영 신뢰성 통제 역량 확인 | SLI/SLO, Error Budget, Toil, 포스트모템 | 모니터링 도구명만 나열하고 SLO 정책 누락 |
| 장애 대응과 배포 속도 균형 판단 확인 | 오류 예산 소진 시 배포 동결, MTTR 기준 | SLA와 SLO를 혼용 |
| 자동화 적용 범위 판단 확인 | 반복 작업 자동화, Runbook, 점진 배포 | 모든 장애를 AI 탐지로 해결한다고 단정 |

> 요약: SRE 답안은 지표 목표와 오류 예산을 중심으로 운영·배포·장애 대응을 연결해야 한다.

## Ⅰ. 개요 및 필요성

- 개요: 신뢰성 목표 기반 운영 체계
- 배경: 클라우드·MSA 환경은 배포 빈도와 장애 전파 경로가 증가하므로 운영 경험만으로 MTTR과 재발률을 통제하기 어렵다.
- 필요성: SLO, 오류 예산, 자동화, 포스트모템으로 배포 허용 기준과 장애 재발 방지 기준을 관리한다.

---

## Ⅱ. 구조 및 구성요소

```text
User Journey -> SLI 수집 -> SLO 설정 -> Error Budget 산정
                       +-> Alert/Runbook -> Incident Response -> Postmortem
```

| 구성요소 | 역할 | 특이사항 |
|:---|:---|:---|
| SLI/SLO | 사용자 영향 지표와 목표 수치 정의 | 가용성 99.9%, p95 지연 300ms 등 |
| Error Budget | 허용 실패량을 배포 정책에 연결 | 월 43.2분 기준, 소진 시 변경 제한 |
| Toil 자동화 | 반복 운영 작업 제거 | 수동 작업 50% 이하 목표 |
| Incident/Postmortem | 장애 대응과 재발 방지 | 비난 없는 원인 분석, 조치 기한 |

> 요약: SRE 구조는 사용자 지표에서 시작해 오류 예산, 알림, 대응, 재발 방지로 닫힌 루프를 만든다.

---

## Ⅲ. 동작원리 및 흐름도

```text
서비스 정의 -> SLI 측정 -> SLO/알림 기준 설정 -> 오류 예산 계산
-> 배포 허용 판단 -> 장애 대응 -> 포스트모템 -> 자동화 백로그 반영
```

| 단계 | 처리 내용 | 검증 기준 |
|:---:|:---|:---|
| 1 | 사용자 여정별 SLI 선택 | 요청 성공률, p95 지연, 오류율 |
| 2 | SLO와 알림 임계치 설정 | 99.9%, burn rate 2x/14x |
| 3 | 배포와 오류 예산 연동 | 예산 0% 도달 시 릴리스 중단 |
| 4 | 장애 처리와 사후 분석 | MTTA 5분, MTTR 30분 |
| 5 | 자동화 과제 등록 | Toil 비율 월 50% 이하 |

> 요약: SRE는 측정, 목표, 예산, 대응, 개선을 반복해 신뢰성을 운영 프로세스가 아닌 공학 대상으로 다룬다.

| 운영/위험 | 장애 후 복구 | 오류 예산 기반 사전 통제 | 월 장애 허용시간 산정 가능 시 |

> 요약: SRE는 장애가 비즈니스 지표에 영향을 주고 배포 빈도가 주 1회 이상인 서비스에서 적용 효과가 드러난다.

| SLO 왜곡 | 내부 지표만 사용 | 고객 여정별 SLI 설정 | SLO 위반과 CS 티켓 상관 |
| 자동화 부채 | Runbook 미정비 | 월 Toil 리뷰와 자동화 백로그 | 수동 처리 시간 월 50% 이하 |

> 요약: SRE 리스크는 지표 선택 오류와 알림 과다에서 발생하므로 사용자 영향 기준으로 통제해야 한다.

| 점검 항목 | 목표 기준 | 측정 방법 |
|:---|:---|:---|
| 신뢰성 | 월 SLO 99.9%, 오류 예산 43.2분 | APM, Synthetic Monitoring |
| 대응 | MTTA 5분, MTTR 30분 | Incident 로그, PagerDuty |
| 운영 자동화 | Toil 50% 이하, 재발 장애 0건 | 작업 티켓, Postmortem 추적 |

> 요약: SRE 성과는 SLO 준수율, 장애 대응 시간, Toil 비율로 측정한다.

## Ⅵ. 실무 적용 및 결론

**적용 방안 3개:**
1. 핵심 서비스 3개부터 SLI를 요청 성공률, p95 지연, 오류율로 정의하고 월 99.9% SLO와 burn rate 알림을 설정함
2. 오류 예산 25% 이하 도달 시 신규 릴리스 승인 절차를 SRE 리뷰로 전환하고 Canary 5%, 25%, 100% 단계 배포를 적용함
3. 장애 포스트모템을 48시간 이내 작성하고 재발 방지 항목을 자동화 백로그와 연결해 Toil 월 50% 이하를 목표로 운영함

**결론 (2줄):**
- 기술사 판단: 배포 빈도와 장애 영향이 모두 큰 서비스는 SRE를 적용하고, 내부 배치성 시스템은 SLO 범위를 제한해 적용함
- 향후 방향: AIOps 상관분석과 플랫폼 엔지니어링을 결합해 알림 정비, 자동 복구, 정책 기반 배포 통제로 확장함
