## 미리 알고가기

- Saga는 여러 서비스에 걸친 업무 흐름을 로컬 트랜잭션 연쇄로 처리하는 패턴임
- 보상 트랜잭션은 실패 시 이전 단계 효과를 업무적으로 되돌리는 처리임
- Orchestration은 중앙 조정자가 흐름을 제어하고 choreography는 이벤트로 각 서비스가 반응하는 방식임

## Ⅰ. 개요

- **정의/개념**: Saga 패턴은 여러 서비스에 걸친 하나의 비즈니스 흐름을 각 서비스의 로컬 트랜잭션과 보상 트랜잭션으로 나눠 처리하는 분산 트랜잭션 패턴임.
- **배경/필요성**: MSA 환경에서는 2단계 커밋 같은 강한 분산 트랜잭션이 성능과 가용성과 결합도 측면에서 부담이 크므로, 저장소가 즉시 같아지지 않더라도 업무 흐름을 이어 갈 수 있는 대안적 정합성 처리 방식이 필요함.

## Ⅱ. 특징

- 각 서비스가 독립 저장소를 유지하면서도 하나의 업무 흐름을 이어갈 수 있음
- 실패 복구를 보상 로직으로 처리하므로 가용성은 높지만 설계 난도도 커짐
- Orchestration은 흐름 가시성이 높고 choreography는 중앙 결합이 낮음
- 보상이 어려운 작업이 많으면 적용 범위가 제한됨

## Ⅲ. 종류 및 비교

| 구분 | Orchestration | Choreography |
|:---|:---|:---|
| 제어 방식 | 중앙 오케스트레이터가 단계 순서와 실패 처리를 직접 제어함 | 이벤트를 받은 각 서비스가 다음 동작을 자율적으로 수행함 |
| 얻는 장점 | 흐름 추적과 장애 지점 파악이 비교적 쉬움 | 중앙 조정자 의존이 줄고 서비스 자율성이 높음 |
| 주된 한계 | 오케스트레이터 자체가 관리 포인트와 장애 지점이 될 수 있음 | 이벤트가 많아질수록 전체 흐름을 이해하고 디버깅하기 어려워짐 |
| 적합한 환경 | 단계 순서와 예외 처리가 복잡한 업무 흐름에 맞음 | 느슨한 이벤트 협력과 단순 단계 연쇄에 맞음 |

> 요약: Saga는 분산 트랜잭션을 숨기는 기술이 아니라 강한 일관성 대신 보상과 추적을 감당하는 설계 방식임.

## Ⅳ. 구성요소 및 구조

| 구성요소 | 설명 |
|:---|:---|
| Local Transaction | 각 서비스 안에서 원자적으로 수행되는 최소 작업 단위임 |
| Compensation Action | 실패 시 이전 효과를 업무적으로 되돌려 정합성을 회복하는 수단임 |
| Saga Coordinator or Event Flow | 중앙 조정자나 이벤트 흐름이 전체 진행 순서를 이어 줌 |
| State Tracking | 현재 단계와 실패 위치를 추적해 재시도와 보상을 정확히 실행하게 함 |

## Ⅴ. 원리 및 절차 흐름도

```text
+-------------+     +-------------+     +-------------+     +-------------+
| 단계 실행      | --> | 다음 단계 전달 | --> | 실패 감지      | --> | 보상 수행      |
+-------------+     +-------------+     +-------------+     +-------------+
```

1. **단계 실행**: 첫 서비스가 로컬 트랜잭션을 수행함
2. **다음 단계 전달**: 중앙 조정자나 이벤트로 다음 서비스에 흐름을 넘김
3. **실패 감지**: 어느 단계에서 실패했는지 상태를 확인함
4. **보상 수행**: 이미 끝난 단계들을 규칙에 따라 되돌림

## Ⅵ. 실무 적용 및 유의점

1. 주문·결제·재고처럼 여러 서비스가 함께 움직이는 업무에서는 사가가 유효하지만 보상 트랜잭션이 실제 상태를 완전히 원복하지 못하면 사고가 남으므로 보상 가능성을 먼저 검토하고 보상 처리 성공률과 잔여 정합성 오류 건수로 확인함
2. 이벤트 기반 사가를 운영하는 환경에서는 중복 이벤트와 재처리로 흐름이 꼬이기 쉬우므로 상관관계 ID와 멱등 처리 저장을 함께 적용하고 추적 누락 건수와 중복 실행 비율로 확인함

## Ⅶ. 결론

Saga 패턴은 분산 환경에서 강한 락 대신 보상과 추적 체계로 업무 정합성을 관리하는 방식임.
