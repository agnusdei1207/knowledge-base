# 📖 【암기용】 개념 완전 이해

## 한눈에
- **개요**: **Saga(사가) 패턴**은 마이크로서비스 환경에서 여러 서비스에 걸친 분산 트랜잭션을 처리하기 위해, 각 서비스의 로컬 트랜잭션을 연속적으로 실행하고 실패 시 보상 트랜잭션(Rollback)을 수행하는 패턴이다.
- **왜 필요한가**: 모놀리식에서는 단일 DB의 트랜잭션(ACID)으로 '전부 성공 아니면 전부 취소'가 보장된다. 하지만 DB가 쪼개진 MSA에서는 하나의 트랜잭션으로 묶을 수 없어 데이터 정합성이 깨질 위험이 크다.
- **핵심 직관**: 온라인 환불 과정과 같다. 결제 취소(1단계) -> 포인트 회수(2단계) 중 포인트 회수에 실패하면, 이미 취소된 결제를 다시 원상 복구(보상 트랜잭션)하는 방식이다.

## 핵심 용어 정리

| 용어/표기 | 의미 | 비유·예 |
|:---|:---|:---|
| 로컬 트랜잭션 | 단일 마이크로서비스가 자신의 DB에서 수행하는 개별 트랜잭션 | 내 부서의 장부 기록 |
| 보상 트랜잭션 (Compensating Transaction) | 앞선 로컬 트랜잭션의 결과를 되돌리기 위해 실행하는 '취소용' 로컬 트랜잭션 | 결제 취소에 대한 '결제 재승인' |
| 코레오그래피 사가 (Choreography) | 중앙 통제 없이 각 서비스가 이벤트를 주고받으며 자율적으로 흐름을 제어 | 안무가의 지시 없이 각자 춤추는 댄서들 |
| 오케스트레이션 사가 (Orchestration) | 중앙 관리자(Orchestrator)가 각 서비스에 트랜잭션 수행과 취소를 지시 | 지휘자가 있는 오케스트라 교향악단 |

## 깊이 이해
- **배경·문제의식**: 기존 분산 환경에서는 2PC(Two-Phase Commit)라는 양단계 커밋 프로토콜을 썼다. 하지만 2PC는 모든 DB가 준비(Lock)될 때까지 기다려야 하므로 성능이 극악이고, NoSQL 등에서는 아예 지원하지 않는 한계가 컸다. 이를 대체하기 위한 비동기 기반의 트랜잭션 모델이 필요했다.
- **작동 원리**: 전체 트랜잭션을 `T1 -> T2 -> T3`와 같은 로컬 트랜잭션 체인으로 쪼갠다. T1 성공 후 T2를 실행하다 실패하면, 2PC처럼 일시 정지 후 롤백하는 것이 아니라, 이미 커밋된 T1을 논리적으로 취소하기 위한 **C1(보상 트랜잭션)**을 실행한다.
- **비유**: 숙소(A)와 항공편(B)을 예약하는 패키지 여행. 숙소 예약 성공 후 항공편이 매진되어 실패하면, 이미 결제된 숙소 예약을 환불(보상 트랜잭션)하는 것이 사가 패턴이다.
- **구체 예시**: e-커머스 주문. `주문 생성(주문 서비스)` -> `재고 차감(재고 서비스)` -> `결제 승인(결제 서비스)`. 만약 결제가 잔액 부족으로 실패하면, 재고 서비스에 "재고 원복 이벤트"를 보내고, 주문 서비스에 "주문 취소 이벤트"를 보내서 전체 상태의 정합성을 맞춘다.
- **흔한 오해·주의점**: "보상 트랜잭션은 자동 롤백 기능이다"라는 오해. DB가 알아서 해주는 트랜잭션 롤백과 달리, 보상 트랜잭션은 개발자가 "어떻게 취소할 것인지" 로직(예: -100원 했으면 +100원 하기)을 직접 코드로 구현해야 한다.

## 연결 개념
- 마이크로서비스 아키텍처 (MSA) — 사가 패턴이 적용되는 분산 데이터 환경
- 2PC (Two-Phase Commit) — 사가 패턴이 대체한 동기식 강결합 분산 트랜잭션
- 아웃박스 패턴 (Outbox Pattern) — 사가 패턴 구현 시 DB 커밋과 이벤트 발행의 원자성을 보장하는 패턴

# 📝 【답안용】 시험 답안 템플릿

## 핵심 인사이트 (3줄 요약)

> 1. **본질**: 사가(Saga) 패턴은 MSA 분산 데이터 환경에서 일련의 로컬 트랜잭션과 실패 시 보상 트랜잭션(Compensating Transaction)을 결합하여 데이터 정합성을 유지하는 패턴이다.
> 2. **가치**: 성능 저하와 Lock이 심한 2PC(Two-Phase Commit)를 대체하여, 높은 가용성과 비동기 확장성을 제공하면서 최종 일관성(Eventual Consistency)을 달성한다.
> 3. **판단 포인트**: 서비스 수와 결합도에 따라 이벤트 기반의 코레오그래피(Choreography) 방식과 중앙 통제형 오케스트레이션(Orchestration) 방식 중 적합한 토폴로지를 선택해야 한다.

## 출제 의도 및 답안 포인트

| 출제 의도 | 반드시 짚을 핵심 | 감점 회피 포인트 |
|:---|:---|:---|
| MSA 분산 트랜잭션 한계 극복 역량 | 2PC의 한계(Locking), 보상 트랜잭션, Eventual Consistency | 사가 패턴이 ACID의 '격리성(Isolation)'을 보장한다는 오답 |
| 구현 패턴 간의 트레이드오프 이해 | 코레오그래피 vs 오케스트레이션 비교 | 단순히 "MSA 트랜잭션은 사가로 한다" 수준의 얕은 서술 |

> 요약: 사가 패턴은 완벽한 ACID 트랜잭션을 포기하는 대신, 보상 로직을 통한 궁극적 일관성을 선택하여 분산 시스템의 가용성을 확보한다.

## Ⅰ. 개요 및 필요성

- 개요: 마이크로서비스 간에 걸쳐 있는 비즈니스 트랜잭션을 처리하기 위해, 순차적인 로컬 트랜잭션 실행과 실패 시 보상 트랜잭션으로 데이터를 복구하는 분산 트랜잭션 패턴
- 배경: DB per Service 구조에서는 단일 DB 트랜잭션(ACID) 적용 불가 및 동기식 2PC의 심각한 락(Lock) 점유와 병목 발생
- 필요성: 시스템 가용성을 해치지 않으면서(Lock-Free), 서비스 간 데이터 불일치(Inconsistency)를 해소할 비동기 기반의 최종 일관성(Eventual Consistency) 메커니즘 필요

---

## Ⅱ. 구조 및 구성요소

```text
[서비스 A (로컬 트랜잭션 T1)] -> 이벤트 -> [서비스 B (로컬 트랜잭션 T2)]
                                          | (실패 시 보상 이벤트 발생)
[서비스 A (보상 트랜잭션 C1)] <- 이벤트 <-+
```

| 구성요소 | 역할 | 특이사항 |
|:---|:---|:---|
| 로컬 트랜잭션 (T) | 각 마이크로서비스 내부 DB에서 실행되는 개별 ACID 트랜잭션 | 각 트랜잭션 완료 시 이벤트 발행 |
| 보상 트랜잭션 (C) | 이전 단계에서 실행된 로컬 트랜잭션 결과를 논리적으로 취소/원복 | 멱등성(Idempotency) 보장 필수 |
| 코레오그래피 패턴 | 중앙 통제 없이 서비스 간 이벤트(Pub/Sub) 구독으로 흐름 제어 | 서비스 2~4개 규모의 단순 흐름에 적합 |
| 오케스트레이션 패턴 | 중앙 컨트롤러(Orchestrator)가 실행/취소 명령을 서비스에 직접 하달 | 복잡도 높은 결제/주문 시스템에 적합 |

> 요약: 전체 트랜잭션은 로컬 트랜잭션의 연속이며, 장애 발생 시 역순으로 보상 트랜잭션을 실행하여 원상 복구한다.

---

## Ⅲ. 동작원리 및 흐름도

```text
(T1) 주문 생성 성공 -> (T2) 재고 차감 성공 -> (T3) 결제 승인 실패
-> (C2) 재고 원복 실행 -> (C1) 주문 취소 상태 변경 -> 사가 종료 (최종 일관성 확보)
```

- 1단계 [정상 진행]: 주문 서비스가 내부 DB에 주문을 기록(T1)하고 '주문 생성됨' 이벤트를 브로커에 발행
- 2단계 [연계 처리]: 재고 서비스가 이벤트를 수신하여 재고 차감(T2)을 완료하고 '재고 차감됨' 이벤트를 발행
- 3단계 [장애 발생]: 결제 서비스가 '재고 차감됨'을 받아 결제(T3)를 시도했으나 잔액 부족으로 실패하여 '결제 실패' 이벤트(또는 실패 응답) 발생
- 4단계 [보상 처리]: 결제 실패를 인지한 시스템이 역순으로 재고 서비스에 원복(C2), 주문 서비스에 상태 변경(C1)을 실행하여 전체 상태를 롤백(보상)

> 요약: 사가는 중간에 트랜잭션이 실패하더라도 이미 커밋된 이전 단계의 데이터를 되돌리는 명시적 보상 연산을 통해 정합성을 맞춘다.

---

## Ⅳ. 특징
- 가용성 극대화 (Lock-Free): 2PC와 달리 타 서비스의 처리를 기다리며 DB 락을 쥐고 있지 않으므로 대규모 동시성 처리에 유리
- 격리성(Isolation) 부재: T1 성공 후 T2 실패 사이에 다른 클라이언트가 T1의 결과(예: 임시 생성된 주문)를 조회할 수 있는 읽기 일관성 위반 문제 발생
- 개발 복잡도 증가: 단순한 롤백(`ROLLBACK`)이 불가하므로 개발자가 모든 스텝마다 취소(보상) 로직을 일일이 구현하고 테스트해야 함

> 요약: 사가 패턴은 강력한 가용성을 얻는 대가로, ACID 특성 중 I(격리성)를 상실하므로 이를 비즈니스 로직으로 방어해야 한다.

## Ⅴ. 심화 비교 및 적용 판단

| 비교 축 | 2PC (Two-Phase Commit) | Saga 패턴 | 선택 기준 |
|:---|:---|:---|:---|
| 데이터 일관성 | 강한 일관성 (Strong Consistency) | 최종 일관성 (Eventual Consistency) | 실시간 정합성 요구 수준 |
| 병행성 및 성능 | Lock 점유로 성능 저하 심각 | 비동기 기반으로 높은 성능량 처리 | 트래픽 규모 (대용량 여부) |
| 트랜잭션 제어 | DB 엔진 단에서 자동 롤백 지원 | 애플리케이션 레벨의 보상 로직 구현 | NoSQL 등 폴리글랏 환경 여부 |

> 요약: 단일 RDBMS 클러스터 내의 결제 모듈 등은 2PC가 안전하나, MSA 간의 대규모 통신은 반드시 Saga 패턴을 선택해야 한다.

**리스크·대응:**
- 보상 트랜잭션(취소 로직) 자체의 실패 리스크: 보상 로직 중 서버가 죽으면 영구적 불일치 발생 → 보상 연산의 재시도(Retry) 의무화 및 중복 실행 방지를 위한 멱등성(Idempotency Key) 구현
- 격리성 부재 리스크: 아직 사가가 완료되지 않은 데이터를 다른 곳에서 참조 → Semantic Lock(주문 상태를 'PENDING'으로 두어 외부 노출 통제) 적용
- 이벤트 유실: 로컬 DB 커밋 후 메시지 브로커 전송 전 서버 다운 시 트랜잭션 단절 → 아웃박스 패턴(Outbox Pattern) 적용으로 발행 보장

**도입 후 점검 지표:**
- 분산 트랜잭션 성공률: 전체 사가 워크플로우의 정상 완료율 99.9% 이상 유지 — 분산 추적(Jaeger) 통계
- 보상 트랜잭션 소요 시간: 장애 감지 후 보상 트랜잭션이 완료되기까지의 지연(Recovery Time) p95 기준 2초 이내 달성

## Ⅵ. 실무 적용 및 결론

**적용 방안 3개:**
1. 아키텍처 선택: 참여 서비스가 3개 이하인 경우 메시지 기반의 코레오그래피(Choreography)로 결합도를 낮추고, 4개 이상이거나 결제처럼 상태 관리가 복잡한 경우 오케스트레이터(Camunda, AWS Step Functions)를 도입
2. 트랜잭션 멱등성 확보: 네트워크 재시도에 의해 보상 트랜잭션이 중복 호출되더라도 데이터가 훼손되지 않도록, 이벤트 ID 기반의 멱등성(Idempotency) 체크 테이블 구현
3. 아웃박스 패턴 적용: DB의 'Outbox 테이블'에 이벤트를 먼저 저장하고 배치나 CDC(Debezium)를 통해 메시지를 발행하여 원자적(Atomic) 이벤트 발행 체계 구축

**결론 (2줄):**
- 기술사 판단: MSA 환경에서 분산 트랜잭션은 완벽한 기술적 롤백이 불가능하므로, 사가 패턴을 통한 비즈니스 레벨의 보상 체계 구축이 유일한 현실적 대안이다.
- 향후 방향: 사가 패턴의 복잡성을 줄이기 위해 프레임워크(Seata, Eventuate Tram)의 도입이 확대되고 있으며, 서버리스 기반의 오케스트레이션 서비스 통합이 가속화되고 있다.
