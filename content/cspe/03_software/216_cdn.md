## 미리 알고가기

- CDN은 Origin의 콘텐츠를 Edge Cache에 복제하고 Client 요청을 선택된 Edge에서 처리하는 분산 전달 계층임
- Cache Key는 URI와 Method를 기본으로 하며 Query·Header·Cookie를 포함할 때 Hit 분할과 사용자 데이터 혼합을 검토해야 함
- `Cache-Control`·`Expires`는 Freshness, ETag·Last-Modified는 Stale 응답의 재검증 조건을 표현함
- Pull CDN은 첫 요청에서 Origin을 조회하고 Push CDN은 배포 전에 콘텐츠를 Edge·중간 저장소에 업로드함
- Signed URL·Cookie, Origin 접근 제한, TLS·WAF를 적용해 비공개 콘텐츠와 Origin 우회를 통제함

## 작성 근거(검토용)

- CDN은 요청 라우팅, Cache Key, Freshness·재검증, Origin Shield, 무효화, 접근 통제를 핵심 축으로 설명함
- 비교표는 Pull·Push의 배포 시점·첫 요청·원본 부하·변경 반영·저장·적합 조건을 대비함
- 웹 정적 자산과 모델 파일 배포는 Hit Ratio·Origin 전송량·p95 다운로드 시간으로 검증함

## Ⅰ. 개요

- **정의/개념**: CDN은 DNS·Anycast 등으로 Client를 Edge에 연결하고 Cache Policy에 따라 Origin 응답을 저장·재사용·재검증해 콘텐츠를 분산 전달하는 시스템임
- **배경/필요성**: 다수 Client의 동일 파일·응답 요청을 Origin마다 반복 처리하지 않고 Edge에서 재사용하며 Origin 장애·트래픽 급증·접근 통제를 전달 계층에서 완화해야 함

## Ⅱ. 특징

- Request Router가 Client·Edge 상태와 정책으로 Edge Location을 선택하고 Edge가 Cache Key를 계산함
- Fresh 응답은 Origin 호출 없이 재사용하고 Stale 응답은 ETag·If-None-Match 등으로 변경 여부를 재검증함
- Regional Cache·Origin Shield가 여러 Edge의 Miss를 합쳐 Origin Connection·Request 수를 제한함
- 콘텐츠 Hash가 포함된 URL은 장기 `immutable` Cache를 사용하고 변경 가능한 URL은 TTL·재검증·무효화를 적용함
- Query·Cookie·Authorization을 Cache Key에 포함·제외할 때 Variant 수와 사용자별 응답 격리를 함께 확인함
- Range Request·압축·이미지 변환은 Origin·Edge 지원 범위와 Cache Variant 규칙을 일치시킴

## Ⅲ. 종류 및 비교

| 판단 기준 | Pull CDN | Push CDN |
|:---|:---|:---|
| Edge 배치 시점 | Client Miss가 발생할 때 Origin에서 가져옴 | 배포 작업이 콘텐츠를 사전에 업로드함 |
| 첫 요청 경로 | Edge Miss 후 Origin·Shield 왕복 | 업로드 완료 Edge에서 Cache Hit 가능 |
| Origin 요청 | Edge별 최초 Miss·재검증 발생 | 배포 업로드·동기화 요청 발생 |
| 변경 반영 | TTL·재검증·무효화로 갱신 | 새 객체 업로드·버전 교체·삭제로 갱신 |
| Edge 저장 범위 | 실제 요청된 객체부터 저장 | 배포 대상으로 선택한 객체를 저장 |
| 적합 조건 | 요청 분포를 미리 알기 어려운 웹 자산 | 릴리스 시점·대상 파일이 정해진 배포 자산 |

> 요약: Pull은 요청 Miss에서 Origin 콘텐츠를 채우고 Push는 릴리스 전에 지정 콘텐츠를 Edge 저장소에 배포함.

## Ⅳ. 구성요소 및 구조

| 구성요소 | 설명 |
|:---|:---|
| DNS·Anycast·Request Router | Client 요청을 정책상 사용할 Edge Location으로 연결함 |
| Edge Cache·Cache Key | URI·Query·Header·Cookie 조합으로 저장·재사용할 Variant를 구분함 |
| Cache Policy·Validator | TTL·Freshness·ETag·Last-Modified·Stale 허용 범위를 적용함 |
| Regional Cache·Origin Shield | 여러 Edge Miss를 병합하고 Origin 요청 경로를 집중함 |
| Origin·Origin Access Control | 원본 파일·API를 제공하고 CDN 경로만 Origin에 접근하게 함 |
| Invalidation·Signed Access·WAF | 객체 갱신·비공개 접근·요청 공격 필터를 관리함 |

```text
Client -> DNS|Anycast -> Edge Cache -> Regional Cache|Shield -> Origin
                         Hit Return      Miss·Revalidate
```

> 요약: Router가 Edge를 선택하고 Edge·Shield Cache가 Key·Freshness를 확인한 뒤 필요한 Miss·재검증만 Origin으로 전달함.

## Ⅴ. 원리 및 절차 흐름도

```text
Edge 선택 -> Cache Key 계산 -> Freshness 확인 -> Hit 반환 | Miss·재검증 -> 저장·반환
```

1. **Edge 선택**: DNS·Anycast와 Routing Policy가 요청을 Edge Location으로 연결함
2. **Key 계산**: URI와 허용된 Query·Header·Cookie로 Cache Variant를 찾음
3. **Freshness 확인**: Age·TTL·Cache-Control을 평가해 재사용·재검증·Miss를 결정함
4. **Origin 조회**: Shield·Origin에 조건부 또는 전체 요청을 보내 응답·304 결과를 받음
5. **저장·반환**: Cache 가능 응답과 Validator를 저장하고 Client에 Age·Cache 상태와 함께 전달함

> 요약: CDN은 Edge의 Cache Key·Freshness·Validator를 기준으로 Hit를 반환하고 Miss·Stale만 Origin 경로로 전달함.

## Ⅵ. 실무 사례

1. 웹 정적 자산은 콘텐츠 Hash URL과 장기 Cache를 적용하고 Edge 캐시 적중률·Origin 전송량을 확인함
2. 모델 파일 배포는 Signed URL·Range Request를 적용하고 p95 다운로드 시간·Origin 전송량을 확인함

## Ⅶ. 결론

- CDN은 Cache Key·Freshness·재검증·무효화·Origin 보호·비공개 접근을 콘텐츠 변경 주기와 함께 설계해야 함
