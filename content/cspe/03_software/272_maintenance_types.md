## Ⅰ. 개요
- 정의: 시스템 인도 후 오류 수정, 환경 변화 대응, 성능 향상을 위해 수행하는 활동
- 배경: 운영 중 결함·환경·요구사항·코드 구조 변화에 따라 변경 요청이 누적되므로 유형별 관리 필요
- 출제 의도: 유지보수 4대 유형(교정, 적응, 완전, 예방)의 특징 및 구분 능력 평가

## Ⅱ. 구성요소
- 구조도
  [Maintenance]
  +-- [교정(Corrective)]: 결함 제거
  +-- [적응(Adaptive)]: 환경 변화(OS, DB 등) 대응
  +-- [완전(Perfective)]: 기능 개선 및 성능 향상
  +-- [예방(Preventive)]: 미래 장애 대비 리팩토링

- 구성요소 표
| 유형 | 설명 | 비유 |
| :--- | :--- | :--- |
| 교정 | 사용 중 발견된 버그 수정 | 고장 난 전구 교체 |
| 적응 | 외부 인터페이스나 규제 변화 반영 | 이사 후 가전 재배치 |
| 완전 | 사용자 요구에 따른 신기능 추가 | 베란다 확장 공사 |
> 요약: 결함 수정, 환경 적응, 기능 개선, 미래 결함 예방 목적에 따라 유지보수 활동을 구분함

## Ⅲ. 절차
- 흐름도
  변경 요청 접수 -> 영향도 분석 -> 변경 승인/수정 -> 회귀 테스트/배포
- 4단계 설명
1. 변경 요청 접수: 사용자나 운영자로부터 오류 보고 또는 개선 제안 수집
2. 영향도 분석: 변경 시 관련 모듈 및 데이터베이스에 미치는 파급 효과 평가
3. 변경 승인/수정: 형상 통제 위원회(CCB) 승인 후 소스 코드 및 문서 수정
4. 회귀 테스트: 수정 사항이 기존 기능에 부작용을 일으키지 않는지 최종 검증
> 요약: 변경 영향도를 분석하고 승인·수정·회귀 테스트를 거쳐 기존 기능의 이상 여부를 검증함

## Ⅳ. 문제점
- 잦은 패치와 땜질식 수동 수정으로 인한 코드 스파게티화 및 복잡도 증대
- 초기 설계 문서와 소스 코드 간의 불일치로 인한 유지보수 분석 난이도 상승

## Ⅴ. 개선방안
- 지속적 리팩토링(예방 유지보수)과 테스트 자동화(회귀 테스트) 환경 구축
- 레거시 코드의 기술 부채(Technical Debt) 시각화 및 주기적 상환 계획 수립

## Ⅵ. 전망
- 인공지능 기반의 코드 영향도 자동 분석 및 자가 수정(Self-repairing) 기술 발전
- CSF: 운영(Ops) 데이터가 개발(Dev)로 환류되는 밀접한 협업 체계(DevOps) 강화
