## 미리 알고가기

- API 게이트웨이(API Gateway): 외부 클라이언트의 모든 요청을 받아 적절한 백엔드 마이크로서비스로 전달하는 단일 진입점임
- Rate Limiting: 시스템 보호를 위해 단위 시간당 클라이언트의 요청 횟수를 제한하는 제어 메커니즘임
- API Aggregation: 클라이언트가 여러 번 호출해야 하는 데이터를 게이트웨이 수준에서 단일 호출로 묶어 반환하는 기법임
- 인증 및 인가(Authentication & Authorization): 클라이언트의 신원을 확인하고 특정 API 자원에 대한 접근 권한을 검증하는 보안 조치임
- P95 지연 시간(Latency): 전체 요청 중 가장 느린 5%를 제외한 95%의 요청이 완료되는 데 걸린 시간으로 성능을 평가하는 지표임

## 작성 근거(검토용)

- API 게이트웨이는 외부 진입점, 공통 정책, 서비스 라우팅, 응답 조합을 핵심 축으로 삼아 통제 구조의 편의성을 강조함
- 직접 호출과 게이트웨이 사용 방식을 진입 경로, 공통 정책 적용, 응답 처리 및 장애 여파를 기준으로 비교하여 구축 실익을 검증함
- 문장별 5회 전수 검수 근거: 제목, frontmatter, 미리 알고가기, 작성 근거, 본문, 표 헤더·셀, 요약, 결론을 한 줄도 빠뜨리지 않고 확인했으며 어색한 단어·조사·동사 결합·장황한 명사구를 교정했음을 밝힘

## Ⅰ. 개요

- **정의/개념**: API 게이트웨이는 외부 요청의 인증·사용량 제한·라우팅·응답 조합을 수행하는 단일 진입 계층임
- **배경/필요성**: 클라이언트별 인증·버전·오류 처리를 중복 구현하지 않도록 외부 진입 정책을 통합할 계층이 필요함

### 쉽게 이해하기 (학습용)
- 대기업 로비의 안내 데스크와 같습니다. 외부 방문객은 각 사무실을 직접 찾아갈 필요 없이, 안내 데스크에서 신분증을 확인받고 지정된 사무실로 안내받습니다.

## Ⅱ. 특징

- 클라이언트와 내부 서비스 사이 결합을 줄이고 진입 정책을 한곳에서 관리함
- 인증, rate limiting, 로깅, 버전 관리 같은 공통 기능을 중앙화할 수 있음
- 응답 조합과 형식 변환으로 채널별 API 계약을 제공함
- 비즈니스 로직이 누적되면 게이트웨이 처리량과 변경 범위가 함께 커짐

### 쉽게 이해하기 (학습용)
- 출입 보안과 방문 기록 작성을 한곳에서 해결할 수 있어 편리하지만, 안내 데스크에 사람이 너무 많이 몰리면 로비 전체가 마비될 위험이 있습니다.

## Ⅲ. 종류 및 비교

| 판단 기준 | 직접 서비스 호출 | API 게이트웨이 사용 |
|:---|:---|:---|
| 진입 경로 및 제어 | 클라이언트가 서비스별 경로와 인증 방식을 관리함 | 단일 엔드포인트에 공통 진입 규칙을 적용함 |
| 공통 정책 적용 | 서비스별로 같은 보안 및 통제 기능을 중복 구현하기 쉬움 | 인증과 사용량 제어를 중앙에서 일관되게 적용함 |
| 응답 처리 및 장애 여파 | 클라이언트가 다중 호출 및 가공하되 특정 서비스 장애에 대응 | 게이트웨이가 응답을 가공·병합하나 게이트웨이 장애 시 전면 마비 |

### 쉽게 이해하기 (학습용)
- 개별 사무실을 방문객이 일일이 찾아가는 방식은 비효율적이고 복잡하지만, 로비 안내소(게이트웨이)를 거치면 단 한 번의 확인으로 복잡한 이동 절차가 간소화됩니다.

## Ⅳ. 설계 요소 및 구조

```text
Client (Web / Mobile)
        |
        v
+-----------------------------------------------------------+
|                        API Gateway                        |
|  +---------------------+         +---------------------+  |
|  |     Filter Chain    |         |    Routing Layer    |  |
|  |  - Authentication   | ------> |  - Service Path     |  |
|  |  - Rate Limiting    |         |  - Version Control  |  |
|  +---------------------+         +---------------------+  |
|                                             |             |
|  +---------------------+                    |             |
|  |  Aggregator/Metrics | <------------------+             |
|  +---------------------+                                  |
+-----------------------------------------------------------+
        |                        |                        |
        v                        v                        v
+---------------+        +---------------+        +---------------+
|   Service A   |        |   Service B   |        |   Service C   |
+---------------+        +---------------+        +---------------+
```

| 설계 요소 | 설명 |
|:---|:---|
| 라우팅 계층 | 요청 경로·버전에 따라 대상 서비스를 결정함 |
| 인증·정책 필터 | 인증·인가·사용량 제한을 외부 요청에 공통 적용함 |
| 응답 조합·변환 | 여러 서비스 응답을 조합하고 채널별 형식으로 변환함 |
| 관측 지점 | 로그·추적·메트릭을 수집해 API 요청과 장애 경로를 식별함 |

### 쉽게 이해하기 (학습용)
- 길 안내판(라우팅), 출입 카드 검사기(필터), 여러 물건을 한 상자에 담아주는 포장대(조합), 방문객 현황판(관측)이 모인 종합 인프라입니다.

## Ⅴ. 원리 및 절차 흐름도

```text
  [1. 요청 수신]               [2. 인증 및 정책]              [3. 서비스 라우팅]              [4. 응답 조합 및 반환]
+-----------------+        +--------------------+        +-------------------+        +---------------------+
|  외부 API 요청   | -----> |  Token (JWT) 검증  | -----> |  내부 서비스 라우팅| -----> |  응답 데이터 포맷팅 |
|  엔드포인트 매칭 |        |  Rate Limit 체크   |        |  (HTTP/gRPC 호출) |        |  클라이언트에 반환  |
+-----------------+        +--------------------+        +-------------------+        +---------------------+
```

1. **요청 수신**: 외부 클라이언트가 발송한 API 요청을 게이트웨이의 단일 도메인 엔드포인트에서 대표 수신함
2. **인증 및 정책 적용**: 등록된 필터를 통해 JWT 토큰 등의 신원을 검증하고, 요청 IP/키 별로 할당된 사용량 제한(Rate Limit)을 적용함
3. **서비스 라우팅**: 내부 서비스 디스커버리 등과 연계하여 대상 마이크로서비스로 요청을 포워딩하거나 동시 호출함
4. **응답 조합 및 반환**: 다수의 백엔드 응답 데이터를 클라이언트 맞춤형 포맷으로 통합하고 로깅을 수행한 뒤 최종 반환함

### 쉽게 이해하기 (학습용)
- 방문객이 도착하면(수신), 신원을 조회하고(인증), 방문 도장을 찍어 적절한 층으로 연결한 뒤(라우팅), 돌아오는 길에 필요한 서류를 챙겨서 내보내는(반환) 절차입니다.

## Ⅵ. 실무 사례

1. B2B API 플랫폼은 인증·사용량 제한·오류 계약을 게이트웨이에 적용하고 p95 지연·오류 계약 일치율을 확인함
2. 게이트웨이 클러스터는 다중 인스턴스와 자동 확장을 적용하고 장애 전환 시간·5xx 응답률을 확인함

### 쉽게 이해하기 (학습용)
- 모바일 쇼핑몰 앱에서 API Gateway를 거쳐 인증 토큰 검증과 Rate Limiting을 일괄 처리하고, 마이페이지 구성 시 주문, 쿠폰, 장바구니 데이터를 게이트웨이가 묶어서 반환하도록 조치합니다.

## Ⅶ. 결론

- API 게이트웨이는 분산 시스템의 복잡도를 은폐하고 공통 횡단 관심을 일원화하는 관문 인프라임
- 게이트웨이가 비대해지지 않도록 비즈니스 로직 적용을 엄격히 통제하고 단일 장애점(SPOF) 대응을 위한 고가용성 설계를 병행해야 함

### 쉽게 이해하기 (학습용)
- 모든 손님을 입구에서 한 번에 확인하고 정리해주는 것은 매우 효율적이지만, 입구 자체가 무너지면 가게 전체가 문을 닫아야 하므로 비상 통로(이중화)를 마련해두는 것이 핵심입니다.
