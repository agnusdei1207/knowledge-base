# 📖 【암기용】 개념 완전 이해

> 목적: 이 개념을 처음 보는 사람도 완벽히 이해하게 만든다. 시험 답안 양식이 아니라, 이해를 위한 친절한 설명이다.

## 한눈에
- **개요**: MSA 환경에서 백엔드 서버가 100개로 쪼개지면, 프론트엔드(모바일 앱, 웹)가 "어떤 데이터를 받으려면 어느 서버로 가야 하지?"라며 100개의 주소(IP)를 다 외워야 하는 대혼란이 터진다. 이를 막기 위해 클라이언트와 백엔드 서버들 사이에 딱 하나 세워둔 **'단일 출입구(문지기)'**가 API 게이트웨이다.
- **왜 필요한가**: 1. 주소 숨기기(라우팅). 프론트가 게이트웨이한테 "결제해줘!"라고 던지면, 게이트웨이가 알아서 결제 서버(IP: 10.0.0.1)로 넘겨준다. 2. 공통 업무 짬처리(Cross-Cutting). 100개의 서버마다 로그인(인증), 로그 남기기 로직을 다 짜넣으면 미친 짓이다. 문지기(게이트웨이)가 앞에서 1번만 검사하고 뒷문으로 통과시킨다.
- **핵심 직관**: 
  - 코엑스 몰(MSA)에 입구(Gateway)가 딱 1개뿐이다. 손님이 들어올 때 입구 경비원이 "신분증(토큰) 확인(인증)"하고, "초당 10명 이상 못 들어감(속도 제한)" 통제한 뒤, "나이키 매장은 3층입니다(라우팅)" 하고 길을 안내해 주는 것이다.

## 깊이 이해
- **배경·문제의식**: 모놀리식 시절에는 앱이 통신할 주소(IP)가 딱 1개였다. MSA로 넘어오면서 서버 IP가 수백 개가 되고, 서버가 죽었다 켜질 때마다 IP가 계속 바뀌었다(동적 오토스케일링). 클라이언트가 이 IP를 다 추적하는 건 불가능했기에, '프록시(Proxy)' 역할을 해줄 중간 거점이 절대적으로 필요해졌다.
- **작동 원리 (핵심 4대 기능)**:
  1. **라우팅 (Routing)**: URL 주소를 보고 알맞은 뒷단 마이크로서비스로 요청을 쏴준다. (`/order` -> 주문 서버, `/pay` -> 결제 서버)
  2. **인증 및 인가 (Auth)**: 게이트웨이 앞단에서 JWT(토큰)를 까보고 정상 유저인지 확인한다. (백엔드 서버 100개는 인증 로직 짤 필요 없이 비즈니스 로직만 짜면 됨).
  3. **속도 제한 (Rate Limiting) 및 보안**: 해커가 1초에 1만 번 새로고침(DDoS)을 누르면, 백엔드 서버까지 가기도 전에 게이트웨이 선에서 컷(Cut) 해버린다.
  4. **프로토콜 변환 및 조립**: 클라이언트는 1번 요청했는데, 게이트웨이가 주문 서버와 배송 서버를 둘 다 찔러서 데이터 2개를 모아(조립) 클라이언트에게 1개의 JSON으로 내려준다.
- **비유**: 
  - **라우터 비유**: 호텔 프론트 데스크. 손님이 "수건 주세요"하면 하우스키핑 부서로 전화를 돌려주고, "밥 주세요"하면 룸서비스 부서로 연결해 준다.
- **구체 예시**: 넷플릭스(Zuul), 스프링 진영(Spring Cloud Gateway), 아마존(AWS API Gateway), 카카오(Kong) 등이 실무에서 쓰는 대표적인 게이트웨이 솔루션이다.
- **흔한 오해·주의점**: "게이트웨이 1개가 모든 트래픽을 다 받으면 죽지 않나요?" 맞다. **단일 장애점(SPOF, Single Point of Failure)**이 될 수 있다. 그래서 실무에서는 게이트웨이 자체도 2~3개씩 이중화(Scale-out)해 두고, 그 앞단에 L4(로드밸런서)를 두어 절대 죽지 않게 철통 방어를 친다.

## 연결 개념
- **BFF (Backend For Frontend)**: API 게이트웨이의 변종. 게이트웨이를 1개만 두지 않고, 모바일용 게이트웨이, PC 웹용 게이트웨이, 스마트TV용 게이트웨이를 따로 찢어서 "프론트엔드 맞춤형"으로 입구를 여러 개 만드는 패턴.
- **서비스 레지스트리 (Service Registry, Eureka)**: 뒷단에 있는 수백 개 서버들의 '전화번호부'. 게이트웨이는 라우팅을 할 때 이 전화번호부를 보고 "아 결제 서버 IP가 오늘 10.0.0.5로 바뀌었네" 하고 찾아간다.

# 📝 【답안용】 시험 답안 템플릿

> 목적: 시험장에서 25분에 그대로 쓰는 답안 양식. 작성방식(추상표현 금지·수치·도식·문제유형 전환)을 엄격히 지킨다.
> 핵심: 이 시험은 정보를 많이 나열하는 시험이 아니라, 문제 신호어에서 출제자 의도를 읽고 핵심 논점을 선별해 쓰는 시험이다.

## 핵심 인사이트 (3줄 요약)

> 1. **본질**: MSA 환경에서 동적으로 변하는 다수의 마이크로서비스 엔드포인트(IP)를 클라이언트로부터 캡슐화(은닉)하고, 시스템의 단일 진입점(Single Entry Point)을 제공하는 리버스 프록시 컴포넌트다.
> 2. **가치**: 클라이언트와 백엔드 간의 직접 통신(Direct Client-to-Microservice)이 낳는 거미줄 같은 결합도를 타파하고, 인증/로깅/Rate Limiting 등 공통 횡단 관심사(Cross-Cutting Concerns)를 일괄 처리하여 백엔드의 비즈니스 집중도를 높인다.
> 3. **판단 포인트**: 동적 라우팅(Service Registry 연동)과 API 조합(Aggregator) 메커니즘을 도식화하고, 중앙 집중으로 인한 SPOF(단일 장애점) 리스크를 이중화 아키텍처나 BFF(맞춤형 게이트웨이)로 방어하는 전략을 짚어야 한다.

## 출제 의도 및 답안 포인트

| 출제 의도 | 반드시 짚을 핵심 | 감점 회피 포인트 |
|:---|:---|:---|
| MSA 네트워크 복잡성 타파를 위한 캡슐화 설계 | 단일 진입점(Facade) 및 동적 라우팅(Discovery) 맵핑 | 단순히 L4 로드밸런서와 동일한 것으로 얕게 치부(게이트웨이는 L7(어플리케이션) 레벨 로직 처리 수행) |
| 공통 관심사(횡단 로직)의 중앙집중화에 따른 효율성 | 인증(JWT Token 검증), Rate Limiting, 로깅 일괄 오프로드 | 개별 마이크로서비스마다 인증 로직을 심어야 한다고 적는 안티패턴 에러 |
| 아키텍처적 리스크 인지 및 차세대 게이트웨이 진화 | SPOF 병목 우려 -> Scale-out 및 BFF(매체별 분리) 대응 | 트래픽 폭주 시 병목 리스크(Single Point of Failure)를 누락하고 장점만 찬양 |

> 요약: 서버를 100개로 쪼개면 해커가 뚫고 들어올 구멍(문)도 100개가 된다. 백엔드 서버들의 외부 문을 싹 다 걸어 잠그고(내부망 격리), 튼튼한 정문(Gateway) 딱 1개만 열어서 수문장을 세우는 것이 엔터프라이즈 보안의 기본이다.

## Ⅰ. 개요 및 필요성

- 정의: 클라이언트와 마이크로서비스 그룹 사이에 위치하여, 클라이언트의 요청을 받아 적절한 백엔드 서비스로 동적 라우팅(Routing)하고 응답을 반환하는 L7 계층의 핵심 인프라 컴포넌트
- 배경: MSA로 분할 시 클라이언트가 수십 개의 동적 IP를 하드코딩으로 추적해야 하는 불가능에 직면하고, 다수의 API 호출로 인한 네트워크 지연(Latency)과 모바일 배터리 소모 폭증
- 필요성: 클라이언트와 내부 아키텍처를 디커플링(Decoupling)하여 내부 서비스 변경 시 클라이언트 영향을 제로(0)화하고, 보안(SSL, 인증) 및 트래픽 제어(Rate Limit) 정책을 일원화하기 위함

## Ⅱ. API Gateway 아키텍처 구조 및 핵심 방어 메커니즘

문지기는 요청을 그냥 넘겨주지 않는다. 신분증을 검사하고, 여러 심부름을 합쳐서 한 번에 가져다준다.

```text
[ API Gateway 토폴로지 통제 도식 ]

(Mobile / Web) ---( 단 1번의 통합 API 호출 `GET /dashboard` )--->
      |
+-----|-------------------------------------------------------+
|  [ API Gateway (Spring Cloud Gateway, Kong, AWS API GW) ]   |
|   1. 인증(Auth) : 헤더의 JWT 토큰 검증(인가 여부)               |
|   2. Rate Limit : 초당 1000건 초과 시 HTTP 429 에러 컷팅        |
|   3. Aggregation : 프론트가 요청한 데이터 조립을 위해 3곳 찌름  |
|   4. Routing : 서비스 레지스트리(전화번호부) 조회 후 분배       |
+-----|-----------------|-----------------|-------------------+
      | (A 찌름)        | (B 찌름)        | (C 찌름)
 [ 사용자 Svc ]     [ 주문 Svc ]      [ 배송 Svc ]
```

| 핵심 기능 (역할) | 아키텍처적(엔지니어링) 효과 |
|:---|:---|
| **동적 라우팅 (Routing)** | Eureka(Service Registry)와 통신하여, Auto-scaling으로 1초마다 바뀌는 백엔드 인스턴스의 IP/Port를 동적으로 추적하여 분배 |
| **인증/인가 (Offloading)** | 100개의 마이크로서비스 소스코드에서 토큰 파싱 로직을 싹 지워버려(횡단 관심사 제거), 개발자들이 오직 비즈니스 로직에만 몰입 가능 |
| **페이로드 조립 (Aggregation)**| 프론트엔드가 백엔드를 3번 찌르면 모바일 배터리가 녹음. 게이트웨이가 대신 3번 찌른 뒤 JSON을 한 덩어리로 합쳐(조립) 프론트에 1번만 리턴 |
| **Rate Limiting & 서킷 브레이커**| 악의적 DDoS 트래픽이나 비정상 호출을 게이트웨이 단에서 차단하여 백엔드 서버 과부하 보호 (Throttling) |

> 요약: 게이트웨이가 없다면 모든 개발팀이 각자의 서버 소스코드에 JWT 토큰 파서 라이브러리를 임포트(Import)하고, 시큐리티 컨피그를 세팅해야 한다. 게이트웨이는 이 '귀찮은 잡일(오프로딩)'을 전담해 주는 고마운 짬통이다.

## Ⅲ. 극복해야 할 시스템적 리스크 (단일 장애점 딜레마)

모든 트래픽이 문지기(Gateway) 한 명에게 몰리면, 이 문지기가 쓰러지는 순간 성 안이 멀쩡해도 코엑스는 마비된다.

| 리스크 요인 | 발생 시나리오 및 시스템 붕괴 원인 | 아키텍처 대응 방안 (실무 튜닝) |
|:---|:---|:---|
| **SPOF (단일 장애점) 셧다운** | 블랙프라이데이에 트래픽이 10배 폭주. 백엔드 서버(결제)들은 100대로 오토스케일링 되었으나, 정작 입구인 API Gateway 1대가 메모리 초과(OOM)로 죽어버려 사이트 100% 마비 | **게이트웨이 클러스터링(Scale-out) 및 L4 로드밸런서 배치**: API Gateway 자체를 상태가 없는(Stateless) 구조로 설계하여 인스턴스를 다중화하고, 그 앞단에 AWS ALB(L4/L7)나 Route53(DNS)을 두어 트래픽 분산 트리를 완벽히 구축 |
| **거대 게이트웨이의 병목화** | 게이트웨이가 API 조립(Aggregation)과 데이터 포맷 변환(XML->JSON) 같은 무거운 비즈니스 연산까지 수행하다가 CPU가 터져 응답 지연(Latency) 폭발 | 게이트웨이에는 **절대 비즈니스 로직(무거운 연산)을 넣지 않는 순수 더미(Dummy) 라우터 원칙** 고수. 필요하다면 논블로킹(Non-blocking) I/O 엔진(Netty 등) 기반 솔루션을 사용하여 스레드 병목 원천 차단 |

> 요약: 게이트웨이는 철저하게 가벼워야(Thin) 한다. 여기서 복잡한 데이터 변환을 하거나 외부 DB를 찌르는(조회) 코딩을 하는 순간, 넷플릭스도 못 고치는 '게이트웨이 모놀리식 지옥'이 시작된다.

## Ⅳ. 매체 다변화 대응을 위한 진화 아키텍처: BFF 패턴

모바일 화면과 60인치 스마트 TV 화면은 필요한 데이터 양이 다르다. 게이트웨이 1개로 이걸 다 맞출 수 없다.

| 진화 아키텍처 | 물리적 구성 메커니즘 | 해결되는 프론트/백엔드 충돌 한계 |
|:---|:---|:---|
| **BFF** <br> (Backend For Frontend) | 거대한 API Gateway 1개를 버리고, **매체별(웹용, 모바일용, TV용)로 쪼개진 여러 개의 전용 미니 게이트웨이**를 프론트엔드 팀이 직접 소유하고 맞춤형(Tailored) API를 조립 제공 | 모바일 팀이 "데이터 3개만 내려주세요"라고 백엔드(공용 게이트웨이) 팀에 사정하다 거절당하는 사일로(Silo) 파괴. 프론트엔드 팀이 자신의 BFF(Node.js 등)를 직접 만져서 원하는 데이터만 필터링/가공 |

> 요약: 정문(Gateway) 1개로 감당이 안 되면, 아예 모바일 전용 출입구, 데스크톱 전용 출입구, 스마트시계 전용 출입구(BFF)를 여러 개 뚫어주는 것이 맞다.

## Ⅴ. 실무 적용 방안 및 결론

**적용 방안 3개:**
1. [Spring Cloud Gateway 기반 비동기/논블로킹 환경 구축] 대규모 Java 진영 MSA 환경에서, 과거 스레드 병목(Thread per Request)을 유발하던 Netflix Zuul 1.x를 폐기하고, Spring WebFlux(Netty) 기반의 Spring Cloud Gateway로 마이그레이션하여 적은 스레드로 동시 접속 10만 건 이상의 트래픽 비동기 수용(Throuput 극대화)
2. [Kong(NGINX) / AWS API Gateway 기반 인프라 위임 관리] 백엔드 로직이 다언어(Polyglot)로 쪼개져 있거나 서버리스(Lambda) 환경일 경우, Java에 종속적인 프레임워크를 버리고 NGINX 기반의 Kong Gateway나 완전 관리형(Managed) AWS API Gateway를 배치하여 인프라 팀(SRE)이 라우팅 룰을 중앙 통제
3. [Token 기반 Edge Security (경계 보안) 중앙화] 백엔드 마이크로서비스들을 모두 프라이빗(Private) 서브넷에 숨기고 인터넷 통신을 차단(보안 강화)한 뒤, 퍼블릭(Public) 서브넷에 위치한 API 게이트웨이에서만 외부 클라이언트의 OAuth 2.0 / JWT 토큰을 까서 검증하는 Zero Trust 토폴로지 구축

**결론:**
- 기술사 판단: API 게이트웨이는 MSA라는 흩어진 '구슬'들을 꿰어 클라이언트에게 예쁜 목걸이로 포장해 주는 실(Thread)과 같다. 이 강력한 파사드(Facade)가 없다면 마이크로서비스는 서로의 존재를 찾지 못해 표류하고, 클라이언트는 100개의 주소를 외우다 지쳐 떨어져 나가는 재앙을 맞는다.
- 향후 방향: 최근 클라우드 환경에서는 게이트웨이의 라우팅과 트래픽 제어(Rate Limit) 역할을 쿠버네티스(k8s)의 Ingress Controller(예: NGINX Ingress, Traefik)나 나아가 서비스 메시(Service Mesh, Istio)의 Gateway(프록시)로 인프라 레이어 밑단으로 흡수(Shift-down) 시키는 아키텍처적 일원화 현상이 뚜렷하게 나타나고 있다.
