# 📖 【암기용】 개념 완전 이해

## 한눈에
- **개요**: 클라이언트와 수많은 마이크로서비스들 사이에서 모든 요청을 받아주는 단일 진입점(Single Point of Entry) 서버다.
- **왜 필요한가**: MSA 환경에서는 서비스가 수십 개로 쪼개져 있다. 클라이언트가 각 서비스의 주소를 모두 알아내 직접 통신하면 결합도가 너무 높아지고 인증·보안 관리가 불가능해진다.
- **핵심 직관**: 놀이공원의 '정문 매표소'와 같다. 모든 관람객(클라이언트)은 반드시 정문을 통과하며 표 검사(인증)를 받고, 안내 지도(라우팅)를 통해 각 놀이기구(서비스)로 이동한다.

## 핵심 용어 정리

| 용어/표기 | 의미 | 비유·예 |
|:---|:---|:---|
| 라우팅 (Routing) | 요청을 적절한 목적지 서비스로 연결해주는 작업 | 매표소의 길 안내 |
| 인증/인가 (Auth) | 요청자의 신원 확인 및 권한 검증 | 입장권 검사 |
| 로드 밸런싱 (Load Balancing) | 트래픽을 여러 서버로 고르게 분산 | 입장객 줄 나누기 |

## 깊이 이해
- **배경·문제의식**: 모놀리식 아키텍처에서는 엔드포인트가 하나였으나, MSA로 전환되면서 서비스가 잘게 나뉘었다. 클라이언트가 이 수많은 주소를 직접 관리하면 통신 복잡도가 극증하고, 각 서비스마다 인증 코드를 중복 구현해야 하는 한계가 발생했다.
- **작동 원리**: 클라이언트는 오직 API Gateway의 주소만 바라본다. 요청이 들어오면 API Gateway가 동적 라우팅 테이블(Service Discovery와 연동)을 참조해 적합한 백엔드 마이크로서비스로 요청을 넘겨준다. 백엔드의 응답을 받으면 다시 클라이언트에게 전달한다.
- **비유**: 대형 병원의 '종합 안내 데스크'. 환자는 내과, 외과, 방사선과 등 각 부서에 직접 전화를 걸지 않고 안내 데스크에 접수한다. 데스크에서 신원을 확인하고 적절한 과로 안내한다.
- **구체 예시**: 앱에서 "내 프로필 조회" 요청 시, API Gateway(예: Spring Cloud Gateway)가 JWT 토큰을 검증한 뒤, 정상 토큰이면 '회원 마이크로서비스'로 요청을 라우팅한다.
- **흔한 오해·주의점**: "게이트웨이에 비즈니스 로직(예: 회원 등급 계산)을 넣어도 된다."는 엄청난 오해다. 비즈니스 로직이 들어가는 순간 게이트웨이는 무거운 모놀리스가 되어 병목을 유발한다. 인증, 로깅 등 순수 공통 관심사(Cross-cutting concerns)만 처리해야 한다.

## 연결 개념
- 마이크로서비스 아키텍처 (MSA) — 게이트웨이가 필수적으로 도입되는 환경
- 서비스 디스커버리 (Service Discovery) — 백엔드 서비스의 동적 IP 위치를 게이트웨이에 알려주는 레지스트리
- BFF (Backend for Frontend) — 프론트엔드 유형별로 맞춤형 진입점을 제공하는 확장 패턴

# 📝 【답안용】 시험 답안 템플릿

## 핵심 인사이트 (3줄 요약)

> 1. **본질**: 클라이언트와 다수의 백엔드 마이크로서비스 사이에서 단일 진입점(Single Point of Entry)을 제공하는 리버스 프록시 서버다.
> 2. **가치**: 클라이언트와 내부 서비스 간 통신 결합도를 낮추고 인증, 율속(Rate Limiting), 로깅 등 공통 관심사를 중앙에서 통제하여 운영 효율을 극대화한다.
> 3. **판단 포인트**: 모든 트래픽이 집중되는 단일 장애점(SPOF)이 될 수 있으므로 Active-Active 이중화 설계와 비동기 논블로킹(Non-blocking) I/O 기반 성능 확보가 필수적이다.

## 출제 의도 및 답안 포인트

| 출제 의도 | 반드시 짚을 핵심 | 감점 회피 포인트 |
|:---|:---|:---|
| MSA 통신 복잡도 해결 원리 확인 | 단일 진입점 캡슐화, 동적 라우팅, 공통 관심사 분리(Cross-cutting) | 비즈니스 로직 포함 등 안티패턴을 장점처럼 서술 |
| 대용량 트래픽 처리 아키텍처 판단 | SPOF 회피(고가용성), 율속(Rate Limiting), 비동기 I/O 적용 | 구체적 제품명(Zuul, Kong)만 나열하고 원리 누락 |

> 요약: 내부 통신 복잡도를 캡슐화로 숨기고 공통 기능을 중앙화하는 구조적 이점과, 트래픽 집중에 따른 SPOF 해결책을 연결해야 한다.

---

## Ⅰ. 개요 및 필요성

- 개요: MSA 환경에서 외부 클라이언트의 모든 요청을 받아 적절한 서비스로 라우팅하고 공통 처리를 수행하는 단일 진입점 서버
- 배경: 분산 환경에서 클라이언트가 각 서비스 엔드포인트를 직접 호출할 경우, 보안 취약성 및 엔드포인트 관리 복잡도 급증
- 필요성: 클라이언트와 백엔드 간 통신 결합도 완화 및 인증·인가·로깅 등 공통 기능의 중앙화 처리로 개별 서비스 개발 중복 제거

---

## Ⅱ. 구조 및 구성요소

```text
클라이언트 -> [ 단일 진입점 수신 ] -> [ 공통 필터 체인 ] -> [ 동적 라우팅 ] -> 개별 마이크로서비스
                                      |                 |
                                      +-> 인증 / 율속   +-> 서비스 디스커버리 조회
```

| 구성요소 | 역할 | 특이사항 |
|:---|:---|:---|
| 라우터 (Router) | URI 패스나 헤더 기반으로 목적지 서비스 매핑 | 동적 라우팅 지원 |
| 필터 (Filter) | 요청/응답 과정에서 인증, 로깅, 헤더 변환 수행 | Pre/Post 필터 분리 |
| 서비스 디스커버리 | 백엔드 서비스의 동적 IP/Port 인스턴스 정보 조회 | Eureka, Consul 연동 |
| 로드 밸런서 | 동일 서비스의 여러 인스턴스 중 하나로 트래픽 분산 | 라운드 로빈 등 적용 |

> 요약: API Gateway는 단일 진입점으로 요청을 수신하여 필터 체인으로 보안 및 공통 로직을 처리한 후, 동적 라우터와 로드 밸런서를 통해 백엔드로 전달한다.

---

## Ⅲ. 동작원리 및 흐름도

```text
요청 수신 -> 공통 기능 필터링 -> 목적지 해석 및 로드밸런싱 -> 서비스 호출 및 응답 반환
```

- 1단계 [클라이언트 요청 수신]: 단일 엔드포인트(URL)를 통해 클라이언트의 외부 REST API 요청을 일괄 접수
- 2단계 [공통 기능 필터링]: Pre-filter를 통해 JWT 토큰 검증, 율속(Rate Limiting), IP 차단 등 인바운드 제어 로직 수행
- 3단계 [목적지 해석 및 분산]: 서비스 레지스트리를 조회하여 타겟 마이크로서비스의 실제 IP를 확정하고 로드 밸런싱 수행
- 4단계 [서비스 호출 및 응답]: 타겟 서비스로 요청을 프록시하고, 수신된 응답을 Post-filter로 가공(헤더 추가 등)하여 클라이언트에 반환

> 요약: 클라이언트 요청은 인바운드 접수, 인증 및 공통 필터링, 동적 라우팅 주소 확정을 거쳐 서비스로 전달되고 역순으로 응답된다.

---

## Ⅳ. 특징
- 단일 진입점 캡슐화: 내부 서비스 구조를 완벽히 숨겨 클라이언트 복잡도를 낮추고 백엔드 구조 변경(리팩토링)의 자유도 보장
- 공통 관심사 분리: 인증, SSL 터미네이션, 로깅 등을 게이트웨이로 이관하여 개별 서비스는 순수 비즈니스 로직에만 집중
- 프로토콜 변환: 외부 클라이언트의 HTTP/REST 요청을 내부의 gRPC, AMQP 등 고성능 이기종 프로토콜로 동적 변환
- 성능 병목 위험: 시스템의 모든 트래픽이 집중되므로 게이트웨이 장애 시 시스템 전체 장애(SPOF)로 직결되는 태생적 한계 존재

> 요약: 내부 복잡성을 감추고 공통 기능을 중앙화하는 강력한 캡슐화 이점을 제공하나, 트래픽 집중에 따른 SPOF 위험을 동반한다.

---

## Ⅴ. 심화 비교 및 적용 판단

| 비교 축 | API Gateway | BFF (Backend for Frontend) | 선택 기준 |
|:---|:---|:---|:---|
| 구조 | 시스템 전체 단일 진입점 (1개) | 클라이언트 유형별 진입점 (N개) | 클라이언트 디바이스 다양성 |
| 비용/성능 | 공통 관심사 중앙화로 로직 중복 제거 | 특정 UI 맞춤형 데이터 조합으로 응답 최적화 | 맞춤형 데이터 집계 필요성 |
| 운영/위험 | 트래픽 과집중으로 SPOF 위험 존재 | 서비스 파편화 및 운영 관리 포인트 증가 | 개발 조직 규모 및 팀 자율성 |

> 요약: 모든 트래픽을 범용적으로 통제할 때는 API Gateway를, 모바일/웹 등 프론트엔드 맞춤형 최적화가 필수적일 때는 BFF 패턴을 선택한다.

**리스크·대응 (기본은 불릿):**
- SPOF 발생 및 전체 장애: 모든 트래픽 집중 → Active-Active 이중화 클러스터 구성 및 오토 스케일링 적용 (지표: 가용성 99.99%)
- 백엔드 지연으로 스레드 고갈: 동기 블로킹 호출 시 대기 누적 → 비동기 논블로킹(Netty 등) 스택 및 서킷 브레이커 연동 (지표: 인스턴스 스레드 점유율)
- 게이트웨이 비대화: 비즈니스 로직 혼재 → 필터에는 보안/로깅 등 순수 공통 로직만 허용하는 아키텍처 정책 강제 (지표: 필터 코드 복잡도)

**도입 후 점검 지표 (기본은 불릿):**
- 성능/효율: 평균 처리 지연 시간(Latency) 50ms 이하 — APM(애플리케이션 성능 관리) 도구로 P99 지표 측정
- 품질/운영: 비정상 라우팅 오류율 0.01% 미만 — 4xx, 5xx 에러 비율 통합 로그 모니터링

## Ⅵ. 실무 적용 및 결론

**적용 방안 3개:**
1. 전역 보안 제어 (Global Security): OAuth 2.0 및 JWT 기반의 글로벌 인증 필터를 적용하여 백엔드의 인증 구현 부담 제거 및 중앙 통제
2. 트래픽 제어 및 과부하 방지: 토큰 버킷(Token Bucket) 알고리즘 기반의 율속(Rate Limiting)을 설정하여 초당 요청 수(TPS) 제한으로 인프라 보호
3. 무중단 마이그레이션: 스트랭글러 패턴(Strangler Fig Pattern)을 적용하여 구형 모놀리식과 신규 MSA로 트래픽을 선별 라우팅하며 무중단 전환 수행

**결론 (2줄):**
- 기술사 판단: 클라이언트 통합 제어가 우선이면 API Gateway를, 프론트엔드별 성능 최적화가 필수면 BFF 패턴과 결합하는 하이브리드 전략을 채택한다.
- 향후 방향: 단순 라우팅 및 필터링을 넘어, GraphQL 연동 및 AI 기반 이상 트래픽 탐지 기능을 결합한 차세대 API Management 플랫폼으로 진화하고 있다.
