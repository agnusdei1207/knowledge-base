## Ⅰ. 개요
- **정의**: 클라이언트와 백엔드 서비스 사이에서 단일 진입점 역할을 수행하는 역방향 프록시
- **배경/필요성**: MSA(042 참조)에서 서비스 수가 증가하면 클라이언트가 개별 서비스 주소를 관리하기 곤란함
- **비유**: 호텔 프론트 데스크처럼 모든 투숙객 요청을 접수하여 적절한 부서로 전달하는 창구

| 출제 의도 | 반드시 짚을 핵심 | 감점 회피 포인트 |
|:---|:---|:---|
| MSA 인프라 구성 이해 | 라우팅·인증·속도제한 기능 | API Gateway와 Load Balancer 혼동 금지 |

> 요약: MSA 환경에서 요청 라우팅·인증·정책 적용을 단일 진입점에서 처리하는 인프라 컴포넌트임

## Ⅱ. 구성요소
```text
Client ---> [API Gateway] --+--> Service A
                            +--> Service B
                            +--> Service C
             |
     +-------+-------+
     | Route | Auth  |
     | Rate  | Log   |
     | Cache | Trans |
     +-------+-------+
```

| 구성요소 | 설명 | 비유 |
|:---|:---|:---|
| 라우팅 엔진 | URL 패턴·헤더 기반으로 요청을 대상 서비스에 전달함 | 우편 분류기 |
| 인증/인가 필터 | JWT·OAuth 토큰을 검증하여 미인증 요청을 차단함 | 출입 보안 게이트 |
| 속도 제한(Rate Limit) | 단위 시간당 요청 수를 제한하여 백엔드 과부하를 방지함 | 고속도로 진입 신호등 |

> 요약: 라우팅·인증·속도 제한이 핵심 기능이며 횡단 관심사를 서비스 외부에서 처리함

## Ⅲ. 절차
```text
요청 수신 --> 인증/인가 --> 라우팅/변환 --> 응답 집계
```
- 1단계: 클라이언트 요청을 수신하고 TLS 종단·프로토콜 변환을 수행함
- 2단계: 토큰 검증·권한 확인·속도 제한 정책을 적용함
- 3단계: 요청 경로에 따라 대상 서비스로 라우팅하고 필요 시 페이로드를 변환함
- 4단계: 복수 서비스 응답을 집계(Aggregation)하여 클라이언트에 단일 응답을 반환함

> 요약: 수신 → 인증 → 라우팅 → 응답 집계의 파이프라인으로 요청을 처리함

## Ⅳ. 문제점
- 단일 장애점: 게이트웨이 장애 시 전체 서비스 접근 불가 — 가용성 리스크가 집중됨
- 성능 병목: 모든 트래픽이 게이트웨이를 경유 — 처리량 한계가 전체 시스템 병목이 됨
- 설정 복잡도: 서비스별 라우팅·정책 규칙 증가 — 설정 오류로 인한 장애 가능성이 높아짐

> 요약: 단일 장애점·성능 병목·설정 복잡도가 API Gateway 운영의 핵심 리스크임

## Ⅴ. 개선방안
1. 단기: Active-Standby 이중화 및 헬스체크를 적용하여 단일 장애점을 제거함
2. 중기: 수평 확장(Auto Scaling)과 캐싱을 도입하여 트래픽 병목을 해소함
3. 장기: GitOps 기반 설정 관리와 카나리 배포를 적용하여 설정 변경 리스크를 통제함

> 요약: 이중화·수평 확장·GitOps 기반 설정 관리로 게이트웨이 리스크를 단계적으로 완화함

## Ⅵ. 전망
- 발전 방향: BFF(Backend For Frontend) 패턴과 결합하여 클라이언트 유형별 맞춤 게이트웨이가 확산됨
- 기술사적 판단: 게이트웨이 로직 비대화를 경계하고 횡단 관심사에 한정하는 것이 핵심임
- 기술사 제언: Service Mesh(046 참조)와 역할을 분담하여 남북(N-S) 트래픽에 집중할 필요
