## 미리 알고가기

- API 게이트웨이는 외부 요청을 내부 서비스로 전달하는 단일 진입 계층임
- Rate limiting은 일정 시간 동안 허용할 요청 수를 제한하는 제어 방식임
- Aggregation은 여러 서비스 응답을 하나로 묶어 클라이언트에 반환하는 처리임

## 작성 근거(검토용)

- API 게이트웨이는 외부 진입점, 공통 정책, 서비스 라우팅, 응답 조합을 핵심 축으로 설명함
- 직접 호출과 게이트웨이는 클라이언트 부담, 정책 위치, 요청 경로, 장애 범위로 비교함
- 실무 판단은 게이트웨이 p95 지연, 오류 계약 일치율, 장애 전환 시간, 5xx 응답률로 구체화함

## Ⅰ. 개요

- **정의/개념**: API 게이트웨이는 외부 요청의 인증·사용량 제한·라우팅·응답 조합을 수행하는 단일 진입 계층임
- **배경/필요성**: 클라이언트별 인증·버전·오류 처리를 중복 구현하지 않도록 외부 진입 정책을 통합할 계층이 필요함

## Ⅱ. 특징

- 클라이언트와 내부 서비스 사이 결합을 줄이고 진입 정책을 한곳에서 관리함
- 인증, rate limiting, 로깅, 버전 관리 같은 공통 기능을 중앙화할 수 있음
- 응답 조합과 형식 변환으로 채널별 API 계약을 제공함
- 비즈니스 로직이 누적되면 게이트웨이 처리량과 변경 범위가 함께 커짐

## Ⅲ. 종류 및 비교

| 판단 기준 | 직접 서비스 호출 | API 게이트웨이 사용 |
|:---|:---|:---|
| 진입 경로 | 클라이언트가 서비스별 경로와 인증 방식을 관리함 | 단일 엔드포인트에 공통 진입 규칙을 적용함 |
| 공통 정책 처리 | 서비스별로 같은 기능을 중복 구현하기 쉬움 | 인증과 사용량 제어를 중앙에서 일관되게 적용함 |
| 응답 처리 | 클라이언트가 서비스별 응답을 변환·조합함 | 게이트웨이가 여러 응답을 채널별 형식으로 변환·조합함 |
| 구조상 한계 | 서비스 변경이 클라이언트 수정으로 전파될 수 있음 | 게이트웨이 장애나 비대화가 전체 진입점에 영향을 줌 |

> 요약: 직접 호출은 클라이언트가 서비스별 규칙을 처리하고, 게이트웨이는 공통 진입 정책을 통합함.

## Ⅳ. 구성요소 및 구조

| 구성요소 | 설명 |
|:---|:---|
| 라우팅 계층 | 요청 경로·버전에 따라 대상 서비스를 결정함 |
| 인증·정책 필터 | 인증·인가·사용량 제한을 외부 요청에 공통 적용함 |
| 응답 조합·변환 | 여러 서비스 응답을 조합하고 채널별 형식으로 변환함 |
| 관측 지점 | 로그·추적·메트릭을 수집해 API 요청과 장애 경로를 식별함 |

> 요약: 인증·정책 필터가 요청을 검증하고 라우팅 계층이 서비스를 선택한 뒤 응답 조합·관측을 수행함.

## Ⅴ. 원리 및 절차 흐름도

```text
+-------------+     +-------------+     +-------------+     +-------------+
| 요청 수신      | --> | 인증·정책 적용 | --> | 서비스 라우팅  | --> | 응답 반환      |
+-------------+     +-------------+     +-------------+     +-------------+
```

1. **요청 수신**: 클라이언트 요청을 단일 진입점에서 받음
2. **인증 및 정책 적용**: 토큰 검증과 권한과 사용량 제한을 수행함
3. **서비스 라우팅**: 대상 서비스로 요청을 전달하거나 여러 응답을 조합함
4. **응답 반환**: 변환과 로깅을 마친 뒤 결과를 반환함

> 요약: 게이트웨이는 요청 인증과 사용량 정책을 적용한 뒤 대상 서비스로 라우팅하고 응답을 변환함.

## Ⅵ. 실무 사례

1. B2B API 플랫폼은 인증·사용량 제한·오류 계약을 게이트웨이에 적용하고 p95 지연·오류 계약 일치율을 확인함
2. 게이트웨이 클러스터는 다중 인스턴스와 자동 확장을 적용하고 장애 전환 시간·5xx 응답률을 확인함

## Ⅶ. 결론

API 게이트웨이는 인증·사용량 제한·라우팅·응답 조합을 담당하고 비즈니스 로직은 서비스에 배치함
