## 미리 알고가기

- API 게이트웨이는 외부 요청을 내부 서비스로 전달하는 단일 진입 계층임
- Rate limiting은 일정 시간 동안 허용할 요청 수를 제한하는 제어 방식임
- Aggregation은 여러 서비스 응답을 하나로 묶어 클라이언트에 반환하는 처리임

## Ⅰ. 개요

- **정의/개념**: API 게이트웨이는 클라이언트 요청을 받아 인증, 정책 적용, 라우팅, 응답 조합을 수행한 뒤 내부 서비스로 전달하는 API 진입 제어 계층임.
- **배경/필요성**: 마이크로서비스 환경에서는 클라이언트가 여러 서비스와 직접 통신하면 인증, 버전, 오류 처리, 호출 경로 관리가 복잡해지므로 이를 앞단에서 통합할 계층이 필요함.

## Ⅱ. 특징

- 클라이언트와 내부 서비스 사이 결합을 줄이고 진입 정책을 한곳에서 관리함
- 인증, rate limiting, 로깅, 버전 관리 같은 공통 기능을 중앙화할 수 있음
- 응답 조합과 형식 변환으로 채널별 API를 다듬기 좋음
- 비즈니스 로직을 과도하게 넣으면 게이트웨이 자체가 병목이 될 수 있음

## Ⅲ. 종류 및 비교

| 구분 | 직접 서비스 호출 | API 게이트웨이 사용 |
|:---|:---|:---|
| 클라이언트 부담 | 서비스마다 인증과 경로와 오류 처리를 직접 알아야 함 | 단일 엔드포인트 기준으로 공통 규칙을 적용받음 |
| 공통 정책 처리 | 서비스별로 같은 기능을 중복 구현하기 쉬움 | 인증과 사용량 제어를 중앙에서 일관되게 적용함 |
| 구조상 장점 | 중간 계층이 없어 경로가 단순함 | 진입 복잡도를 줄이고 채널별 API 조합이 쉬움 |
| 구조상 한계 | 서비스 변경이 클라이언트 수정으로 바로 번질 수 있음 | 게이트웨이 장애나 비대화가 전체 진입점 문제로 이어질 수 있음 |

> 요약: API 게이트웨이는 엔드포인트를 하나로 만드는 도구가 아니라 외부 진입 정책과 복잡도를 통제하는 계층임.

## Ⅳ. 구성요소 및 구조

| 구성요소 | 설명 |
|:---|:---|
| Routing Layer | 요청 경로와 버전에 따라 대상 서비스를 결정해 진입 제어의 중심 역할을 함 |
| Auth and Policy Filter | 인증, 권한, rate limiting을 공통 적용해 보안과 사용량 통제를 일관되게 유지함 |
| Aggregation or Transformation | 여러 서비스 응답을 조합하거나 형식을 바꿔 채널별 요구에 맞춤 |
| Observability Hook | 로그와 추적과 메트릭을 수집해 API 사용량과 장애 원인을 드러냄 |

## Ⅴ. 원리 및 절차 흐름도

```text
+-------------+     +-------------+     +-------------+     +-------------+
| 요청 수신      | --> | 인증/정책 적용 | --> | 서비스 라우팅  | --> | 응답 반환      |
+-------------+     +-------------+     +-------------+     +-------------+
```

1. **요청 수신**: 클라이언트 요청을 단일 진입점에서 받음
2. **인증 및 정책 적용**: 토큰 검증과 권한과 사용량 제한을 수행함
3. **서비스 라우팅**: 대상 서비스로 요청을 전달하거나 여러 응답을 조합함
4. **응답 반환**: 변환과 로깅을 마친 뒤 결과를 반환함

## Ⅵ. 실무 적용 및 유의점

1. 모바일 백엔드나 B2B API 플랫폼에서는 게이트웨이로 인증과 정책을 묶어 처리하되 응답 조합과 예외 처리가 과도하게 쌓이면 병목이 되므로 표준 오류 계약과 기능 범위 기준을 함께 두고 게이트웨이 지연시간과 오류 응답 형식 일치율로 확인함
2. 다수 서비스가 하나의 진입점을 공유하는 환경에서는 게이트웨이 장애가 전체 접근 장애로 번질 수 있으므로 이중화와 자동 확장과 단계적 기능 축소를 적용하고 게이트웨이 가용률과 장애 전환 성공률로 확인함

## Ⅶ. 결론

API 게이트웨이는 공통 진입 정책을 모으는 데 효과적이지만 비즈니스 로직을 떠안지 않도록 경계를 분명히 해야 함.
