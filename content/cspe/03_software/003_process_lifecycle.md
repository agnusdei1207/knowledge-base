# 📖 【암기용】 개념 완전 이해

> 목적: 이 개념을 처음 보는 사람도 완벽히 이해하게 만든다. 시험 답안 양식이 아니라, 이해를 위한 친절한 설명이다.

## 한눈에
- **개요**: **프로세스 생명주기(Process Lifecycle)**는 프로세스가 생성되어 실행되고 소멸하기까지 거치는 **상태 전이(State Transition)**의 흐름이다. 프로그램이 메모리에 적재되어 태어나고(생성), CPU를 기다리다(Ready) 실행되며(Running), 중간에 입출력을 기다리고(Blocked), 마지막에 자원을 반납하고 사라진다(종료).
- **왜 필요한가**: CPU는 1개인데 동시에 존재하는 프로세스는 수십~수백 개다. OS가 각 프로세스를 방치하면 누가 CPU를 쓸 차례인지, 누가 입출력을 기다리는 중이라 지금 실행해봐야 소용없는지 구분할 수 없다. 그래서 OS는 각 프로세스의 상태를 명시적으로 관리하고, "지금 당장 CPU를 줄 수 있는 프로세스(Ready)"와 "CPU를 줘도 못 쓰는 프로세스(Blocked)"를 서로 다른 큐로 철저히 분리해 관리한다.
- **핵심 직관**: 놀이공원 롤러코스터(CPU) 이용 절차와 같다. 표를 끊고 들어와(생성) 대기 줄에 서고(Ready) 롤러코스터에 탄다(Running=CPU 점유). 타는 도중 화장실(I/O)이 급해지면 줄에서 벗어나 휴게소로 간다(Blocked). 볼일을 마치면 곧장 롤러코스터로 돌아가는 게 아니라, 다시 대기 줄(Ready)의 맨 뒤에 서야 한다.

## 핵심 용어 정리 (내부에 등장하는 것들)

| 용어 | 의미 | 비유 |
|:---|:---|:---|
| 상태 전이(State Transition) | 프로세스가 실행 중 겪는 상태 변화 전체와 그 규칙 | 신호등이 바뀌는 규칙 |
| New(생성) | PCB가 막 만들어지고 메모리 적재를 기다리는 상태 | 매표소에서 표를 끊는 중 |
| Ready(준비) | CPU만 배정받으면 즉시 실행할 수 있는 상태. Ready Queue에서 대기 | 놀이기구 대기 줄 |
| Running(실행) | 현재 CPU를 점유해 명령어를 실행 중인 상태 | 롤러코스터 탑승 중 |
| Blocked/Waiting(대기) | I/O 등 외부 이벤트를 기다리느라 CPU를 줘도 실행할 수 없는 상태. Wait Queue에서 대기 | 화장실(휴게소)에 감 |
| Terminated(종료) | 실행이 끝나 자원을 OS에 반납한 상태 | 놀이공원 퇴장 |
| Ready Queue | Ready 상태 프로세스들이 CPU 배정을 기다리며 늘어선 줄 | 놀이기구 대기 줄 그 자체 |
| Wait(I/O) Queue | Blocked 상태 프로세스들이 특정 I/O 장치별로 대기하는 줄 | 화장실 앞 줄 |
| Dispatch | 스케줄러가 Ready 큐에서 프로세스를 골라 CPU에 배정하는 동작(Ready→Running) | 대기 줄에서 불러 태워줌 |
| Timeout(선점) | 할당 시간이 다 돼 강제로 CPU를 뺏는 동작(Running→Ready) | 탑승 시간 종료로 강제 하차 |
| Wakeup | I/O가 끝나 Blocked였던 프로세스를 Ready로 옮기는 동작(Blocked→Ready) | 화장실 다녀와 다시 대기 줄로 |
| Suspend(스왑아웃) | 메모리 부족 시 프로세스 전체를 디스크로 밀어내는 것 | 대기 줄 사람을 임시로 건물 밖으로 내보냄 |
| 좀비 프로세스 | Terminated 됐지만 부모가 `wait()`를 안 불러 PCB가 안 치워진 프로세스 | 퇴장했는데 명단에서 안 지워진 손님 |

## 깊이 이해

### 왜 상태를 나눠 관리해야 하나 (배경)
- CPU 연산 1사이클은 나노초(약 0.3ns, 3GHz 기준) 단위지만, 디스크 I/O 응답은 보통 수 밀리초(ms), 네트워크 응답은 수십~수백 ms 걸린다. 이는 CPU 속도보다 자릿수로 수백만 배 이상 느리다.
- 만약 OS가 상태를 구분하지 않고 모든 프로세스를 순서대로만 실행한다면, I/O를 기다리는 프로세스 차례가 왔을 때 CPU는 응답이 올 때까지 수 ms 동안 아무 일도 못 하고 멈춰 있어야 한다. 이 몇 ms는 CPU 입장에서는 수백만 사이클을 그냥 날리는 것과 같다.
- 그래서 I/O를 기다리는 프로세스는 즉시 Blocked로 분리해 Ready 큐에서 빼버리고, 그사이 CPU가 실행 가능한(Ready) 다른 프로세스에게 넘어가도록 설계한 것이 상태 전이 모델이다.

### 5대 상태와 전이 트리거 — 순서로 이해
1. **New**: 프로그램이 디스크에서 메모리로 적재되며 PCB가 생성된다.
2. **New → Ready**: 메모리 적재가 끝나면(Admitted) Ready 큐에 들어간다.
3. **Ready → Running(Dispatch)**: 스케줄러가 골라 CPU를 배정한다.
4. **Running → Ready(Timeout)**: 타이머 인터럽트로 할당 시간이 끝나 강제로 밀려난다(선점).
5. **Running → Blocked(Block)**: 프로세스가 스스로 I/O를 요청해 CPU를 자발적으로 반납한다.
6. **Blocked → Ready(Wakeup)**: I/O 완료 인터럽트가 오면 Ready 큐로 옮겨진다 — **Running으로 직행하지 않는다.**
7. **Running → Terminated(Exit)**: 실행이 끝나 자원을 반납한다.
- **구체 예시**: 화면에 `Hello`를 출력하는 코드 한 줄이 실행되면, 모니터에 실제로 글자가 찍히기까지는 CPU 입장에서 상대적으로 긴 시간(수 ms)이 걸린다. 이 순간 프로세스는 Running에서 Blocked(출력 I/O 대기)로 전이되고, OS는 그 틈에 다른 Ready 프로세스에게 CPU를 넘긴다. 출력이 끝났다는 인터럽트가 오면 그 프로세스는 Ready로 옮겨지고, 스케줄러 차례가 다시 왔을 때에야 Running으로 돌아간다.

### 왜 Blocked에서 Running으로 직행하지 않는가 — 판별 원리
- I/O가 끝난 프로세스를 곧장 Running으로 보내버리면, 마침 그 순간 실행 중이던 다른 프로세스를 매번 강제로 끊어야 하고, I/O를 자주 쓰는 프로세스가 항상 새치기하는 불공평이 생긴다.
- 그래서 원칙은 "I/O가 끝났다 = 이제 다시 실행 후보가 됐다"일 뿐, "지금 당장 실행한다"가 아니다. Wakeup은 반드시 Blocked → Ready이며, 그다음 Ready → Running은 스케줄러(004)가 다른 Ready 프로세스들과 공정하게 비교한 뒤에 결정한다.

### 메모리가 부족할 때 — Suspend(스왑) 확장 상태
- 5대 상태만으로 부족한 경우가 있다. 메모리(RAM)에 여유 공간이 없을 때, OS는 당장 실행 가능성이 낮은 프로세스(주로 Blocked 상태)를 통째로 디스크로 밀어낸다. 이를 **Suspended Blocked**라 한다.
- 이 상태에서 I/O가 끝나도 메모리에 빈자리가 없으면 곧바로 Ready로 못 돌아가고, "메모리만 확보되면 바로 뛸 수 있다"는 뜻의 **Suspended Ready**로 전환된다. 메모리에 빈 프레임이 생기면(Swap-in) 그제야 진짜 Ready 큐로 복귀한다.
- 이렇게 5개 기본 상태에 Suspended Blocked·Suspended Ready 2개를 더한 것을 7-상태 모델이라 부른다.

### 비유와 흔한 오해
- **비유**: 식당 주방에서 요리사(프로세스)들이 도마(CPU) 하나를 나눠 쓴다. 요리사 A가 도마에서 양파를 썰다가(Running) 오븐에 빵을 구워야 하면 도마를 비우고 오븐 앞(Blocked)에 가서 기다린다. 그사이 대기하던 요리사 B(Ready)가 도마로 와서 고기를 썬다. 오븐이 다 구워지면 A는 곧바로 도마로 오는 게 아니라 다시 도마 대기 줄(Ready) 맨 뒤에 선다.
- **오해**: Blocked에서 I/O가 끝나면 곧바로 Running이 된다고 착각하기 쉽다. 실제로는 반드시 Ready를 거친다. 또한 "좀비 프로세스"는 실행 중인 프로세스가 아니라 이미 Terminated 됐는데 부모가 `wait()`로 종료 코드를 거둬가지 않아 PCB(프로세스 테이블 엔트리)만 남아있는 상태다. 이런 좀비가 수만 개 쌓이면 커널의 유한한 프로세스 테이블(PID 슬롯)을 잠식할 수 있다.

## 연결 개념
- **인터럽트(Interrupt, 002)**: 상태 전이를 유발하는 방아쇠다. 타이머 인터럽트는 Running→Ready를, I/O 인터럽트는 Blocked→Ready를 일으킨다.
- **PCB·컨텍스트 스위칭(002)**: 상태 전이가 일어날 때마다 PCB의 상태(State) 필드가 갱신되고, Running↔Ready·Running↔Blocked 전이는 실제로 컨텍스트 스위칭을 동반한다.
- **프로세스 스케줄링(004)**: Ready 큐에 여러 프로세스가 쌓였을 때 "다음 Dispatch 대상을 누구로 할지" 정하는 정책이 스케줄링이다.
- **가상 메모리·스와핑**: Suspend 상태는 가상 메모리 관리와 맞닿아 있다 — 물리 메모리가 부족할 때 프로세스를 디스크로 내보내는 것은 페이지 교체 정책과 같은 문제의식(메모리 과다 사용, 스레싱 방지)에서 출발한다.

# 📝 【답안용】 시험 답안 템플릿

> 목적: 시험장에서 25분에 그대로 쓰는 답안 양식. 작성방식(추상표현 금지·수치·도식·문제유형 전환)을 엄격히 지킨다.
> 핵심: 이 시험은 정보를 많이 나열하는 시험이 아니라, 문제 신호어에서 출제자 의도를 읽고 핵심 논점을 선별해 쓰는 시험이다.

## 핵심 인사이트 (3줄 요약)

> 1. **본질**: 다중 프로그래밍 환경에서 프로세스가 메모리에 적재되어 소멸하기까지 겪는 PCB 상태 변화(State Transition) 메커니즘이다.
> 2. **가치**: CPU 점유(Running), 할당 대기(Ready), I/O 이벤트 대기(Blocked)를 철저히 큐(Queue) 단위로 분리하여 CPU 유휴 시간을 0%로 수렴시킨다.
> 3. **판단 포인트**: 시분할 스케줄링을 위한 `Timer Interrupt (Run -> Ready)`와 비동기 자원 요청을 위한 `I/O Wait (Run -> Blocked)`의 분기점을 정확히 도식화해야 한다.

## 출제 의도 및 답안 포인트

| 출제 의도 | 반드시 짚을 핵심 | 감점 회피 포인트 |
|:---|:---|:---|
| CPU 이용률 극대화를 위한 상태 전이 메커니즘 | Ready 큐와 Blocked(Wait) 큐의 엄격한 분리 통제 | Blocked에서 I/O 완료 시 Running으로 직행한다고 긋는 치명적 오개념 |
| 인터럽트에 의한 선점/비선점 흐름 통제 | 타이머(할당 시간 만료) / 시스템 콜(I/O 요청) 방아쇠 | 상태 전이가 OS의 자발적 제어인지 HW 인터럽트인지 헷갈려 서술 |

> 요약: 준비(Ready)와 대기(Blocked)는 완전히 다른 차원의 대기다. 준비는 CPU만 오매불망 기다리는 것이고, 대기는 다른 볼일(I/O)을 보느라 CPU를 거들떠보지도 않는 상태다.

## Ⅰ. 개요 및 필요성

- 정의: 프로세스의 생성(New)부터 준비(Ready), 실행(Running), 대기(Blocked), 종료(Terminated)에 이르는 OS 커널의 PCB 상태 추적 및 스케줄링 생명주기
- 배경: 단일 CPU 환경에서 다수의 프로세스가 자원을 경합할 때, 입출력(I/O) 장치의 속도가 CPU보다 수백만 배 느려 CPU 병목 현상(Idle) 심화
- 필요성: CPU가 필요한 프로세스 그룹(Ready)과 디스크 응답을 기다리는 그룹(Blocked)을 논리적으로 격리하여, 스케줄러가 탐색 오버헤드 없이 즉시 다음 실행 타겟을 골라내기 위함

## Ⅱ. 프로세스 5대 상태 전이 (State Transition) 도식

```text
       [ New (생성) ]
             | (Admitted: 메모리 적재)
             v
       [ Ready (준비) ] <----------------+ (I/O 완료 / Event Occurs)
         |   ^                           |
Dispatch |   | Timeout (할당시간 만료)   |
         v   |                           |
     [ Running (실행) ] ----------------> [ Blocked / Wait (대기) ]
         |              (I/O 요청 / Event Wait)
    Exit |
         v
  [ Terminated (종료) ]
```

| 핵심 상태 전이(Transition) | 유발 트리거 (Trigger) | 커널 내부 동작 (큐 조작) |
|:---|:---|:---|
| **Dispatch** (Ready -> Run) | OS 스케줄러 알고리즘 선택 | Ready 큐에서 PCB 추출 후 CPU 레지스터 및 PC 복원 |
| **Timeout** (Run -> Ready) | 타이머 인터럽트 발생 | 선점(Preemption) 처리. 문맥 저장 후 Ready 큐 맨 뒤로 삽입 |
| **Block** (Run -> Blocked) | I/O 시스템 콜 호출 | CPU를 자발적 양보(Yield). I/O 디바이스별 대기 큐로 편입 |
| **Wakeup** (Blocked -> Ready) | I/O 컨트롤러 인터럽트 | I/O 대기 큐에서 꺼내어 **반드시 Ready 큐로 이동시킴** |

> 요약: 실행(Run)에서 밀려나는 길은 두 가지다. 내 밥그릇(시간)을 다 비워서 강제로 쫓겨나거나(Timeout), 반찬(I/O)이 더 필요해서 스스로 주방에 가거나(Block) 둘 중 하나다.

## Ⅲ. 고급 상태 전이 확장: Suspend (스왑 아웃) 메커니즘

메모리(RAM) 용량이 한계에 달했을 때, 커널은 프로세스를 통째로 하드디스크(Swap)로 쫓아내는 지연(Suspend) 상태 2가지를 추가로 가동한다.

| 7-State 모델 확장 상태 | 쫓겨난 위치 및 사유 | 상태 복귀 조건 |
|:---|:---|:---|
| **Suspended Blocked** | I/O 대기(Blocked) 중인데 램이 부족하여 **디스크로 스왑 아웃(Swap-out)** 당함 | I/O가 완료되면 메모리로 당장 못 오고 'Suspended Ready'로 신분 전환 |
| **Suspended Ready** | 당장 뛸 준비(Ready)가 되었는데 메모리 자리가 없어 **디스크에서 억울하게 대기** | 메모리에 여유 프레임이 생기면 스왑 인(Swap-in) 되어 Ready 큐로 복귀 |

> 요약: Blocked 상태로 램에 누워 자는 놈들은 메모리 낭비다. OS는 램이 부족해지면 자고 있는 놈들부터 멱살을 잡아 하드디스크(Suspend)로 던져버려 성능 스레싱을 방어한다.

## Ⅳ. 현대 시스템의 프로세스 제어 리스크와 튜닝 방안

스레드가 수천 개씩 뜨는 서버 환경에서는 Block/Wakeup 오버헤드 자체가 커다란 병목이 된다.

| 리스크 요인 | 아키텍처 한계점 | 극복을 위한 현대 아키텍처 패턴 |
|:---|:---|:---|
| I/O 블로킹 동기화 병목 | 웹 서버(Apache 등)에서 DB 쿼리나 파일 읽기(I/O)를 할 때마다 스레드가 Blocked 상태로 전이되어 수만 개의 대기 큐 팽창 유발 | **Non-blocking 이벤트 루프**: Nginx나 Node.js는 단일 스레드(Running)에서 `epoll`/`kqueue`를 써서 Block 당하지 않고 I/O 이벤트를 뒤로 미뤄버림 (상태 전이 박멸) |
| 좀비 프로세스 낭비 | 자식 프로세스가 Terminated 되었으나 부모가 `wait()`를 호출하지 않아 리눅스 커널의 프로세스 테이블(PID)을 무한 점유 | **고아 처리 및 Init(1번) 위임**: 커널은 부모 잃은 자식들을 PID 1번(`systemd`)에 입양시켜 강제로 장부(PCB)를 수거(Reap)하는 가비지 컬렉션 수행 |

> 요약: 성능을 쥐어짜 내는 현대 백엔드는 "최대한 Blocked 큐로 쫓겨나지 않고 Running 상태에서 모든 걸 버티는(Non-blocking I/O)" 기이한 락 프리(Lock-free) 철학으로 진화했다.

## Ⅴ. 실무 적용 방안 및 결론

**적용 방안 3개:**
1. [Nginx C10K 병목 돌파] 1만 개의 커넥션 요청이 들어올 때, 프로세스를 생성(New)하고 I/O 대기(Blocked)시키는 고전적 상태 전이를 피하기 위해 워커(Worker) 프로세스 수를 CPU 코어 수와 동일하게 맞추고 이벤트 주도(Event-driven) 비동기 처리로 상태 퀀텀 스위치 차단
2. [리눅스 `top` 및 `ps` 모니터링 대응] 서버 부하 폭증 시 상태 표시 플래그(`R`: Running, `D`: Uninterruptible Sleep, `Z`: Zombie)를 분석. 디스크 I/O 병목 시 커널 락을 쥔 `D` 상태가 큐를 점령하므로 스토리지 IOPS 업그레이드 조치 수행
3. [Android App 생명주기 관리] 모바일 램(RAM) 부족 시, 안드로이드 LMK(Low Memory Killer)가 백그라운드의 Blocked/Suspended 앱들을 강제 Terminate 하므로, 개발자는 `onSaveInstanceState` 콜백을 통해 UI 상태를 미리 영속화하여 좀비 재구동 시 사용자 경험 방어

**결론:**
- 기술사 판단: 프로세스 상태 전이는 단순히 상태값을 바꾸는 코드가 아니라, 한정된 자원(CPU, RAM, I/O)을 극단적으로 착취하기 위해 OS 커널이 빚어낸 거대한 톱니바퀴다. 이 톱니바퀴의 맞물림(전이) 타이밍을 완벽히 이해해야만 비동기(Async) 프로그래밍의 본질을 꿰뚫을 수 있다.
- 향후 방향: 최근 클라우드 네이티브 환경에서는 무거운 프로세스 단위의 생명주기를 다루는 것을 넘어, 수십 밀리초 만에 생성(New)되고 폭파(Terminated)되는 AWS Lambda 같은 '서버리스(Serverless)' 콜드 스타트 최적화 기술로 패러다임의 축이 이동하고 있다.
