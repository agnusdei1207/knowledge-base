# 📖 【암기용】 개념 완전 이해

> 목적: 이상 현상을 처음 보는 사람도 중복 데이터가 왜 삽입·삭제·갱신 문제를 만드는지 이해하게 만든다. 시험 답안 양식이 아니라, 이해를 위한 설명이다.

## 한눈에
- **개요**: 이상현상(Anomaly)은 **정규화**되지 않은 릴레이션에서 서로 다른 성격의 사실이 한 테이블에 섞여, **함수 종속**이 잘못 배치된 채로 삽입·삭제·갱신할 때 데이터 모순이나 손실이 발생하는 현상이다.
- **왜 필요한가**: 사원과 부서 정보를 한 테이블에 함께 두면, 부서 정보만 단독으로 등록·삭제할 수 없고, 부서 정보를 바꿀 때 그 부서 소속 사원 수만큼 반복 수정해야 한다. 이상현상은 정규화가 왜 필요한지를 구체적 실패 사례로 보여준다.
- **핵심 직관**: 같은 전화번호를 수첩 10곳에 적어두면, 번호가 바뀌었을 때 한 곳만 고치고 나머지 9곳을 놓치는 순간 어느 게 맞는 번호인지 알 수 없어지는 상황이다.

## 핵심 용어 정리

| 용어 | 의미 | 비유 |
|:---|:---|:---|
| 정규화(Normalization) | 이상현상을 제거하기 위해 릴레이션을 분해하는 절차(100 참고) | 뒤섞인 서류를 주제별 서랍에 나눠 정리 |
| 함수 종속(Functional Dependency) | 한 속성 값이 다른 속성 값을 하나로 결정하는 관계. 이상현상은 이 관계가 잘못 배치돼서 생김 | "부서코드를 알면 부서장이 하나로 정해진다" |
| 중복(Redundancy) | 같은 사실이 여러 행에 반복 저장된 상태. 이상현상의 직접 원인 | 같은 번호를 수첩 여러 곳에 적음 |
| 후보키(Candidate Key) | 각 행을 유일하게 식별하는 최소 속성 집합. 이상현상 판단의 기준점이 됨 | 그 표를 대표하는 열쇠 |
| 삽입 이상(Insertion Anomaly) | 관련 없는 다른 속성 값이 없어서(또는 NOT NULL 제약 때문에) 넣고 싶은 사실을 못 넣는 상태 | 방이 비어 있어도 투숙객 이름이 없으면 방을 등록할 수 없음 |
| 삭제 이상(Deletion Anomaly) | 한 행을 지웠더니 그 행에 얹혀 있던, 지우면 안 되는 다른 사실까지 함께 사라지는 상태 | 마지막 손님이 체크아웃하면 호텔 자체 정보도 지워짐 |
| 갱신 이상(Update Anomaly) | 같은 사실이 여러 행에 중복돼 있어, 일부 행만 고치면 나머지와 모순이 생기는 상태 | 주소록 10곳 중 3곳만 새 주소로 고쳐 6곳은 옛 주소로 남음 |

## 깊이 이해

### 이상현상이 생기는 구조 — 함수 종속의 잘못된 배치
`사원(사번, 사원명, 부서코드, 부서명, 부서장명)` 테이블을 생각하자. 기본키는 사번이다. 그런데 `부서코드 → 부서명, 부서장명`이라는 함수 종속이 사원 테이블 안에 그대로 들어 있다 — 즉 부서 정보가 부서 자체가 아니라 "그 부서에 속한 사원 행"에 얹혀 저장된다. 이것이 이상현상의 근본 원인이다. 부서 정보의 생명주기(부서는 사원과 별개로 생기고 없어짐)가 사원 행의 생명주기에 종속돼버리기 때문이다.

### 삽입 이상 — 수치로 보는 실패 사례
신설 부서 "AI전략팀"(부서코드=90, 부서장="김OO")이 아직 배정된 사원이 없다고 하자. 사번이 기본키이고 NOT NULL이므로, 사원이 0명인 상태로는 이 행 자체를 만들 수 없다. 결국 부서가 실제로 존재하는데도 DB에는 "AI전략팀이 있다"는 사실을 기록할 방법이 없다. 부서 배정이 끝날 때까지 조직도 관리 업무가 지연되는 실무 문제로 이어진다.

### 삭제 이상 — 수치로 보는 손실 사례
"글로벌전략팀"(부서코드=77) 소속 사원이 1명뿐인 상황에서 그 사원이 퇴사해 행을 DELETE하면, 그 행이 "글로벌전략팀"이라는 사실을 담고 있던 유일한 행이었으므로 부서명·부서장 정보까지 함께 사라진다. 사원 1명의 퇴사 처리가 부서 자체의 기록 손실로 번지는 것이다.

### 갱신 이상 — 수치로 보는 모순 사례
"영업1팀"(부서코드=10) 소속 사원이 300명이라면, 부서장이 교체될 때 이 부서코드를 가진 300개 행을 모두 UPDATE해야 한다. 만약 배치 작업 오류로 299개 행만 갱신되고 1개 행이 누락되면, 같은 부서코드=10에 대해 어떤 행은 새 부서장, 어떤 행은 옛 부서장을 가리키는 모순이 생긴다. 이 경우 "영업1팀의 부서장이 누구인가"라는 질문에 DB가 두 가지 답을 내놓게 된다.

### 세 이상현상의 공통점과 해결 방향
세 현상 모두 "부서에 관한 사실이 사원 행에 중복 저장된다"는 같은 원인에서 나온다. 해결책은 부서 정보를 별도 테이블로 분리하는 것이다: `사원(사번, 사원명, 부서코드)`와 `부서(부서코드, 부서명, 부서장명)`로 나누면, 부서는 사원 없이도 등록·삭제할 수 있고(삽입·삭제 이상 해소), 부서장 교체는 `부서` 테이블 1행만 고치면 된다(갱신 이상 해소). 이것이 곧 정규화(2NF/3NF)가 하는 일이다.

### 이상현상과 반정규화를 혼동하면 안 되는 이유
이상현상은 "의도치 않은 설계 결함"이고, 반정규화(101)는 "성능을 위해 의도적으로, 검증 절차를 두고 도입하는 통제된 중복"이다. 반정규화된 `order_summary` 같은 테이블도 원본과의 동기화가 깨지면 갱신 이상과 똑같은 증상(불일치)을 보일 수 있지만, 차이는 원본 정규화 모델이 별도로 존재하고 checksum·CDC 같은 검증 장치가 있다는 점이다.

## 연결 개념
- 함수 종속(100) — 이상현상의 근본 원인이 되는 관계
- 정규화(100) — 1NF~BCNF 분해로 이상현상을 제거하는 절차
- 반정규화(101) — 의도적·통제된 중복으로, 무통제 중복인 이상현상과 구분해야 하는 개념

# 📝 【답안용】 시험 답안 템플릿

> 목적: 시험장에서 25분에 그대로 쓰는 답안 양식. 작성방식(추상표현 금지·수치·도식·문제유형 전환)을 엄격히 지킨다.

> 2. **가치**: 이상 현상을 식별하면 1NF~BCNF 정규화로 무결성 위반과 유지보수 비용을 줄일 수 있다.
> 3. **판단 포인트**: 삽입·삭제·갱신 사례를 함수 종속, 후보키, 정규형 위반으로 연결해야 한다.

## Ⅰ. 개요 및 필요성

- 개요: 이상 현상은 변경 시 데이터 모순이다.
- 배경: 한 테이블에 여러 주제의 사실을 섞으면 삽입 제약, 삭제 손실, 갱신 불일치가 발생한다.
- 필요성: 함수 종속, 후보키, 1NF~BCNF 정규화로 삽입·삭제·갱신 이상을 제거해야 한다.

## Ⅱ. 구조 및 구성요소

```text
비정규 테이블 -> 중복 속성 -> 함수 종속 혼재 -> 삽입/삭제/갱신 이상
               / 부분 종속
               / 이행 종속
               / 후보키 아닌 결정자
```

| 구성요소 | 역할 | 특이사항 |
|:---|:---|:---|
| 비정규 테이블 | 여러 엔터티 사실을 한 행에 저장 | 학생·과목·교수 정보 혼재 |
| 함수 종속 | 특정 속성이 다른 속성을 결정 | 과목코드 -> 과목명 |
| 중복 속성 | 같은 사실이 여러 행에 반복 | 교수명, 부서명, 상품명 반복 |
| 이상 현상 | 변경 시 모순·손실 발생 | 삽입, 삭제, 갱신 3종 |
| 정규화 처방 | 종속 관계 기준 테이블 분해 | 2NF, 3NF, BCNF 적용 |

> 요약: 이상 현상은 중복 속성과 잘못 배치된 함수 종속이 결합해 변경 작업에서 모순을 만드는 구조이다.

## Ⅲ. 동작원리 및 흐름도

```text
속성 목록 수집 -> 후보키 식별 -> 함수 종속 분석 -> 이상 유형 판정 -> 정규형 분해
```

| 단계 | 처리 내용 | 검증 기준 |
|:---:|:---|:---|
| 1 | 테이블의 후보키와 비키 속성 식별 | 후보키 1개 이상 도출 |
| 2 | 부분 종속·이행 종속 분석 | 2NF, 3NF 위반 여부 |
| 3 | 삽입·삭제·갱신 시나리오 작성 | 변경 1건당 영향 행 수 산정 |
| 4 | 엔터티별 테이블 분해 | 무손실 조인, 종속성 보존 |
| 5 | PK, FK, UNIQUE 제약 부여 | 중복률 0%, orphan 0건 |

> 요약: 이상 현상 분석은 후보키와 함수 종속을 먼저 찾고, 변경 시나리오로 검증한 뒤 정규화로 제거한다.

| 점검 항목 | 목표 기준 | 측정 방법 |
|:---|:---|:---|

> 요약: 이상 현상 제거 효과는 중복률, 제약 위반, 변경 영향 행 수로 검증한다.

## Ⅵ. 실무 적용 및 결론

**적용 방안 3개 (필수 — 단계별 또는 항목별):**
1. 테이블별 후보키와 함수 종속을 도출하고 부분 종속은 2NF, 이행 종속은 3NF, 후보키 아닌 결정자는 BCNF 검토 대상으로 분류함
2. 마이그레이션 전후 row count, checksum, orphan count를 비교해 무손실 분해와 참조 무결성을 검증함
3. 정규화 후 조회 지연이 p95 300ms를 초과하면 인덱스, View, 제한적 반정규화를 순차 적용함

**결론 (2줄):**
- 기술사 판단: 기준 데이터·원장 데이터는 이상 현상 제거를 우선하고, 조회 전용 화면은 검증 가능한 복제본으로 분리함
- 향후 방향: 데이터 품질 도구와 CDC 기반 검증을 결합해 정규화 모델과 분석 모델을 분리 운영해야 함
