## 미리 알고가기

- 이상 현상은 비정상적인 테이블 구조 때문에 데이터 조작 시 정보 손실이나 중복 수정이 생기는 문제임
- 삽입 이상과 삭제 이상과 갱신 이상은 중복 설계에서 주로 발생함
- 정규화와 제약조건이 대표적인 예방 수단임

## Ⅰ. 개요

- **정의/개념**: 삽입·삭제·갱신 이상은 한 테이블에 서로 다른 의미의 데이터가 과도하게 결합되어 있을 때 새로운 사실을 넣지 못하거나 불필요한 삭제로 정보가 사라지거나 동일 사실을 여러 곳에서 반복 수정해야 하는 구조적 데이터 조작 문제임
- **배경/필요성**: 데이터베이스 문제의 상당수는 쿼리보다 스키마 구조에서 시작되므로, 이상 현상을 이해해야 설계 단계에서 무결성 비용을 줄일 수 있음

## Ⅱ. 특징

- 삽입 이상은 일부 값이 없어도 저장해야 할 사실을 넣지 못하는 현상임
- 삭제 이상은 한 행 삭제가 의도하지 않은 다른 사실까지 제거하는 현상임
- 갱신 이상은 같은 사실을 여러 행에서 반복 수정해야 하는 현상임
- 모두 데이터 중복과 부적절한 속성 결합에서 비롯됨

## Ⅲ. 종류 및 비교

| 판단 기준 | 삽입 이상 | 삭제 이상 | 갱신 이상 |
|:---|:---|:---|:---|
| 대표 원인 | 과도한 속성 결합 | 한 행에 다중 의미 저장 | 중복 데이터 반복 저장 |
| 영향 | 새 사실 저장 불가 | 정보 손실 | 불일치 데이터 발생 |
| 예방 방향 | 테이블 분해 | 관계 분리 | 중복 제거와 키 정비 |
| 확인 신호 | NULL 남용 | 삭제 후 참조 손실 | 동일 값 다중 수정 |

## Ⅳ. 구성요소 및 구조

| 구성요소 | 설명 |
|:---|:---|
| Mixed Entity Table | 여러 개체 의미가 한 테이블에 섞여 이상 현상을 유발함 |
| Redundant Attribute | 같은 사실을 반복 저장해 갱신 부담을 높임 |
| Dependency Violation | 함수 종속 위반이 구조 문제를 설명하는 근거가 됨 |
| Normalized Redesign | 개체와 관계를 분리해 조작 이상을 줄이는 재설계 방향을 제공함 |

## Ⅴ. 원리 및 절차 흐름도

```text
+-------------+     +-------------+     +-------------+     +-------------+
| 현재 스키마 분석 | --> | 이상 유형 식별  | --> | 종속성 재정의   | --> | 테이블 재구성   |
+-------------+     +-------------+     +-------------+     +-------------+
```

1. **현재 스키마 분석**: 속성과 키와 중복 구조를 점검함
2. **이상 유형 식별**: 삽입과 삭제와 갱신 문제를 확인함
3. **종속성 재정의**: 개체별 종속 관계를 다시 정리함
4. **테이블 재구성**: 정규화 기반으로 구조를 분리함

## Ⅵ. 문제점 및 해결 방안

1. 문제: 이상 현상을 데이터 입력 실수로만 보면 구조적 원인이 방치되어 동일 문제가 반복될 수 있음
   - 해결방안: schema review에서 anomaly pattern을 점검하고 anomaly recurrence rate와 redundant attribute count로 검증함
2. 문제: 운영 중 발생한 이상 현상을 임시 쿼리로만 봉합하면 테이블 복잡도와 수정 비용이 계속 커질 수 있음
   - 해결방안: normalization backlog를 관리하고 structural fix lead time과 workaround query count로 검증함
3. 문제: 재설계 후 애플리케이션 매핑을 함께 정리하지 않으면 구조는 좋아져도 기능 오류가 발생할 수 있음
   - 해결방안: schema-app contract test를 수행하고 mapping regression count와 deployment defect rate로 검증함

## Ⅶ. 적용 사례

- 레거시 업무 DB 개선에서는 이상 패턴 점검을 수행하고, anomaly recurrence rate와 redundant attribute count로 결과를 확인함
- 운영 장애 대응팀에서는 구조 개선 백로그를 관리하고, structural fix lead time와 workaround query count로 결과를 확인함
- 스키마 개편 프로젝트에서는 계약 테스트를 운영하고, mapping regression count와 deployment defect rate로 결과를 확인함

## Ⅷ. 결론

삽입·삭제·갱신 이상은 쿼리 기술 부족이 아니라 데이터 의미를 잘못 섞은 설계의 결과이므로 구조 개선으로 해결해야 함.
