# 📖 【암기용】 개념 완전 이해

> 목적: 이 개념을 처음 보는 사람도 완벽히 이해하게 만든다. 시험 답안 양식이 아니라, 이해를 위한 친절한 설명이다.

## 한눈에
- **개요**: 12 팩터 앱은 클라우드 환경에서도 코드 수정 없이 이식·확장·복구가 가능한 애플리케이션을 만들기 위해 지켜야 할 **12가지 설계 원칙**이다. Heroku 엔지니어들이 여러 SaaS 앱을 운영하며 반복적으로 실패한 패턴을 정리해 2011년 공개했다.
- **왜 필요한가**: 개발자 노트북에서는 잘 돌던 코드가 운영 서버에서 터지는 이유는 대개 DB 접속 정보 같은 환경별 값이 코드 안에 하드코딩돼 있거나, 서버 메모리에 상태(세션 등)를 저장해 두었기 때문이다. 12 팩터 원칙은 이런 코드-환경 결합을 제거해, 서버가 언제 죽고 언제 복제돼도 동일하게 동작하게 만든다.
- **핵심 직관**: 코드는 환경과 완전히 분리되어야 하고(설정을 코드 밖으로), 서버 자신은 아무 상태도 기억하지 않아야 하며(무상태), 서버는 언제든 즉시 죽었다가 다시 뜰 수 있어야 한다(폐기 용이성).

## 핵심 용어 정리 (내부에 등장하는 것들)

| 용어 | 의미 | 비유 |
|:---|:---|:---|
| 이식성 (Portability) | 코드 수정 없이 서로 다른 실행 환경(로컬·운영·클라우드 벤더)에서 동일하게 동작하는 성질 — 12 팩터가 궁극적으로 추구하는 상위 목표 | 어느 콘센트에 꽂아도 작동하는 만능 어댑터 |
| Config(설정) | DB 접속 정보, API 키처럼 환경마다 달라지는 값 | 여행지마다 바뀌는 전압·플러그 규격 |
| 백킹 서비스 (Backing Service) | 앱이 네트워크로 접속해 쓰는 외부 자원(DB, 메시지 큐, 캐시 등) | 앱 입장에서는 그냥 URL로 연결하는 외부 부품 |
| 무상태 프로세스 (Stateless Process) | 서버 자신의 메모리나 디스크에 요청 간 상태를 저장하지 않는 성질 | 매번 손님을 처음 보는 것처럼 응대하는 직원 |
| 포트 바인딩 (Port Binding) | 앱이 별도 웹 서버 없이 스스로 포트를 열어 서비스를 노출하는 방식 | 건물 관리인 없이 스스로 문을 여는 매장 |
| 폐기 용이성 (Disposability) | 프로세스가 빠르게 시작되고, 종료 신호를 받으면 하던 일을 정리하고 즉시 꺼지는 성질 | 언제 뽑아도 데이터가 안전한 USB 안전 제거 |
| Dev/Prod Parity | 개발·스테이징·운영 환경을 최대한 동일하게 유지하는 원칙 | 리허설 무대와 실제 공연 무대를 똑같이 꾸미는 것 |
| SIGTERM | 프로세스에 "정상적으로 종료해 달라"고 보내는 신호 | 화재 대피 시 안내방송으로 미리 알리는 것(강제 정전과 다름) |

## 깊이 이해

### 배경 — 상태를 서버 안에 두면 생기는 일
클라우드는 컨테이너를 초 단위로 띄우고 죽인다(Scale-out/in). 그런데 옛날 방식의 서버가 로그인 세션을 자신의 로컬 메모리에 저장해 두면, 그 서버가 재시작되거나 다른 서버로 요청이 라우팅되는 순간 세션 정보가 사라져 사용자가 로그아웃된다. 12 팩터는 이런 상태 보존형(Stateful) 설계를 애초에 금지하는 원칙들의 묶음이다.

### 설정(Config) 분리 — 구체 예
DB 비밀번호를 코드(`application.yml`)에 직접 적어 두면, 운영 환경에 배포할 때마다 코드를 고쳐 다시 빌드해야 하고 소스가 유출되면 비밀번호도 함께 유출된다. 대신 코드는 `DB_PASSWORD`라는 환경 변수 이름만 참조하게 하고, 실제 값은 배포 시점에 운영 환경의 OS 환경 변수나 쿠버네티스 Secret으로 주입한다. 같은 코드(같은 빌드 산출물)를 개발 환경에서는 A값으로, 운영 환경에서는 B값으로 실행할 수 있다.

### 무상태 프로세스 — 수치로 보는 확장성
서버 1대에 세션을 메모리로 저장하면, 트래픽이 늘어 서버를 2대로 늘리는(Scale-out) 순간 사용자가 1번 서버와 2번 서버 중 어디로 배정되느냐에 따라 로그인 상태가 달라진다. 세션을 외부 Redis(백킹 서비스)로 옮기면 서버가 몇 대든(1대든 100대든) 모두 같은 Redis를 참조하므로 어느 서버가 요청을 받아도 동일한 결과를 낸다. 이 성질이 있어야 트래픽 증가에 따라 서버 대수를 늘리는 수평 확장이 가능하다.

### 폐기 용이성 — Graceful Shutdown 수치 예
컨테이너를 내릴 때 강제로 즉시 죽이면(Hard Kill), 처리 중이던 결제 트랜잭션이 중간에 끊길 수 있다. 대신 SIGTERM 신호를 보내고 예를 들어 30초의 유예 시간을 주면, 프로세스는 그 30초 동안 새 요청은 받지 않되(신규 트래픽 차단) 이미 받은 요청은 마무리하고 DB 커넥션을 정리한 뒤 스스로 종료한다. 30초가 지나도 안 끝나면 그때 강제 종료(SIGKILL)한다 — 이 유예 구간이 없으면 오토스케일링으로 서버가 자주 교체될 때마다 진행 중이던 요청이 유실된다.

### Dev/Prod Parity — 왜 로컬과 운영을 맞춰야 하나
개발자가 로컬에서는 가벼운 인메모리 DB로 테스트하고 운영에서는 별도 RDBMS를 쓰면, 로컬에서는 안 나던 SQL 문법 오류가 운영 배포 직후에만 발생할 수 있다. Docker로 로컬 개발 환경도 운영과 동일한 DB 이미지를 띄워 사용하면, "내 컴퓨터에서는 됐는데" 문제 자체가 성립하지 않는다.

## 연결 개념
- 백킹 서비스: 무상태 프로세스가 상태를 위임하는 대상 — 앱은 이 자원이 로컬에 있는지 클라우드에 있는지 신경 쓰지 않고 URL로만 연결한다.
- 서비스 메시(046): 12 팩터가 앱 설계 차원에서 강제하던 것(설정 분리, 장애 격리 일부)을, 서비스 메시는 인프라 계층에서 한 번 더 대신 처리해 준다.
- CI/CD 파이프라인: 12 팩터 중 빌드·릴리즈·실행 단계 분리를 자동화하는 실무 도구.

# 📝 【답안용】 시험 답안 템플릿

> 목적: 시험장에서 25분에 그대로 쓰는 답안 양식. 작성방식(추상표현 금지·수치·도식·문제유형 전환)을 엄격히 지킨다.
> 핵심: 이 시험은 정보를 많이 나열하는 시험이 아니라, 문제 신호어에서 출제자 의도를 읽고 핵심 논점을 선별해 쓰는 시험이다.

## 핵심 인사이트 (3줄 요약)

> 1. **본질**: Heroku가 제안한 SaaS(Software as a Service) 애플리케이션 개발의 12가지 원칙으로, 코드와 인프라 환경을 완벽히 분리(Decoupling)하여 클라우드 환경에 최적화된 앱을 구축하는 선언문이다.
> 2. **가치**: 설정(Config) 하드코딩 제거와 무상태(Stateless) 프로세스를 강제함으로써, 개발-스테이징-운영 환경 간의 불일치(Inconsistency)를 없애고 자유로운 Auto-Scaling(수평 확장)을 가능케 한다.
> 3. **판단 포인트**: 12개 항목을 나열하는 암기 대회가 아니다. 12 팩터가 왜 클라우드 네이티브(컨테이너, CI/CD, 무상태 확장)의 이론적 근간이 되는지 그 연결 고리(엔지니어링 사상)를 규명해야 한다.

## 출제 의도 및 답안 포인트

| 출제 의도 | 반드시 짚을 핵심 | 감점 회피 포인트 |
|:---|:---|:---|
| 클라우드(K8s)에서 살아남기 위한 소프트웨어의 체질 요건 | 무상태(Stateless) 프로세스 및 외부 백킹 서비스 의존 | 클라우드 인프라(AWS) 기능 설명으로 빠져 앱 설계 관점을 이탈하는 맹점 |
| 형상 관리와 환경 변수의 완벽한 분리(Decoupling) 사상 | 하나의 Codebase, 설정(Config)은 코드 밖(OS)으로 추출 | 설정 파일(properties)을 Git에 같이 올려 커밋한다고 적는 보안/설계 에러 |
| 민첩성(Agility) 향상을 위한 빌드/릴리즈/런 격리 | CI/CD 파이프라인 맵핑 및 빠른 폐기(Disposability) | 컨테이너가 죽어도 데이터가 서버 내부에 저장되어야 한다고 적는 과거 패러다임 |

> 요약: 서버는 일회용 종이컵이다. 물(트래픽)을 담고 버리면 그만이다. 서버 안(메모리, 로컬 디스크)에 소중한 보석(상태 데이터, 설정값)을 숨겨두면 쓰레기통에 같이 버려지는 대참사가 일어난다.

## Ⅰ. 개요 및 필요성

- 정의: 이식성(Portability), 탄력성(Resilience), 확장성(Scalability)을 극대화하기 위해 클라우드 네이티브(Cloud-Native) 애플리케이션이 준수해야 할 12가지 아키텍처 및 배포 설계 원칙
- 배경: 과거 물리 서버(On-premise) 시대의 종속적이고 상태 보존(Stateful)적인 코드 베이스를 클라우드나 컨테이너(Docker) 환경에 그대로 올릴 시 수평 확장 불가 및 배포 시 장애 폭발 도달
- 필요성: 어떠한 클라우드 벤더(AWS, GCP, Azure) 환경에서도 소스코드의 수정 0줄(Zero)로 즉각 실행 및 스케일 아웃이 가능한 100% 독립적 마이크로서비스(MSA)를 구축하기 위함

## Ⅱ. 12 팩터 앱의 핵심 원칙 4가지와 클라우드 매핑 도식

12개를 관통하는 하나의 철학은 **"앱을 언제든지 죽이고 다시 살려도 1초 전과 똑같이 돌아가게 만들어라"**는 것이다.

```text
[ 12 Factor 원리: 클라우드 파이프라인 맵핑 ]

[ 1. 팩터 I (코드) ] : 오직 1개의 Git 레포지토리 (개발/운영 브랜치만 다름)
         |
         V
[ 2. 팩터 V (빌드/릴리즈/런) ] : Jenkins CI/CD를 통한 패키징 (JAR/Docker Image)
         | (여기서 절대로 하드코딩된 패스워드를 넣지 않음!)
         V
==============[ 쿠버네티스(클라우드) 운영 서버 환경 진입 ]==============
         |
[ 3. 팩터 III (설정) ] : "너 운영 환경이네? DB 비번은 이거야" -> OS 환경변수(Env)로 즉석 주입!
         |
[ 4. 팩터 VI (무상태) & 팩터 IX (폐기성) ] : 
  (컨테이너 10대로 복제/확장. 데이터는 무조건 외부 [팩터 IV 백킹 서비스(Redis)]에 밀어 넣음)
  (서버 죽어? 1초 만에 깔끔하게 종료하고 새 컨테이너 띄움)
```

| 핵심 팩터 (Factor) | 레거시(과거) 방식의 치명적 리스크 | 12 팩터 기반 아키텍처 대응 방안 (튜닝) |
|:---|:---|:---|
| **III. 설정 (Config)** | `db_pwd="admin"` 코드를 박아놔서 소스가 털리면 다 털림. 운영 서버 갈 땐 소스코드를 고쳐서 다시 컴파일해야 함 | 환경 변수(Environment Variable)나 Config Server(Spring Cloud Config)를 통해 **코드 밖에서 설정값을 주사기처럼 주입** |
| **IV. 백킹 서비스** | DB 연결이 로컬 호스트(localhost) IP에 강하게 결합되어 있어, DB 서버가 바뀌면 앱을 뜯어고쳐야 함 | DB, SMTP 메일, 외부 API 모두를 'URL'로 취급. 언제든 URL만 바꾸면 A서버에서 B서버로 1초 만에 스위칭 |
| **VI. 무상태 프로세스**| 사용자 로그인 세션(Session)을 Tomcat 서버 1번 메모리에 저장함. L4가 사용자를 Tomcat 2번으로 던지면 로그인이 풀려버림 | **무상태(Stateless)**: 서버 메모리는 연산만 할 뿐 아무것도 기억하지 않음. 세션은 외부 Redis(백킹 서비스)에 모조리 위임 |
| **IX. 빠른 시작과 우아한 종료 (Disposability)**| 죽이라고 명령(Kill)해도 스레드가 꼬여 서버가 안 죽음. 켜는 데 스프링 로딩만 1분 걸려 트래픽 폭주 시 Auto-scaling 타임아웃 붕괴 | **SIGTERM(종료 시그널)** 수신 시, 받던 요청까지만 딱 끝내고 DB 커넥션을 반납한 뒤 즉시 프로세스 클린 종료(Graceful Shutdown) |

> 요약: 무상태(Stateless)를 지키지 않은 서버는 "아 1번 서버 껐다 켜면 회원들 장바구니 다 날아가는데 어쩌지?" 라며 벌벌 떨어야 한다. 무상태를 지킨 12 팩터 앱은 "서버 죽었어? 응 버리고 새거 틀어"라는 쿨한 운영(DevOps)을 가능하게 한다.

## Ⅲ. 극복해야 할 시스템적 리스크 (로컬/운영 불일치)

개발자 자리에서는 잘 되던 코드가 운영 서버에서 터지는 비극. 12 팩터는 이를 '환경 비대칭'으로 규정한다.

| 리스크 요인 | 발생 시나리오 및 시스템 붕괴 원인 | 아키텍처 대응 방안 (X 팩터 적용) |
|:---|:---|:---|
| **Dev/Prod 불일치 파국** | 개발자는 로컬 노트북에서 가벼운 H2 DB로 테스트하고, 운영은 무거운 Oracle을 씀. 운영에 배포하자마자 SQL 방언(Dialect) 불일치로 시스템 마비 | **팩터 X (Dev/Prod Parity)**: 개발, 스테이징, 운영 환경을 **100% 일치(동일한 Docker 이미지)**시킬 것. 로컬에서도 무조건 운영과 같은 DB(컨테이너)를 띄워놓고 코딩 강제 |
| **로그(Logs) 증발 현상** | 서버 로컬 폴더(`/var/log/`)에 에러 로그를 텍스트 파일로 쌓음. 오토스케일링(Auto-scaling)된 컨테이너가 축소(Scale-in)되며 죽을 때 로그 파일도 함께 영원히 허공으로 증발 | **팩터 XI (로그를 이벤트 스트림으로 취급)**: 서버는 절대 로그 파일에 쓰지 말고, 모조리 `stdout(표준 출력)`으로 뱉어라. 그럼 바깥에 있는 Fluentd 같은 로그 수집 데몬이 낚아채서 중앙 ELK(Elasticsearch)에 영구 보관함 |

> 요약: 개발 환경과 운영 환경이 다르다는 건 소프트웨어 공학에서 가장 멍청한 변명이다. 12 팩터는 도커(Docker)라는 완벽한 밀폐 용기를 통해 개발자의 노트북과 아마존 서버의 환경을 단 1비트의 오차도 없이 100% 동일하게 락인(Lock-in) 시켜버렸다.

## Ⅳ. MSA와 클라우드 네이티브 생태계와의 결합(Beyond 12 Factor)

10년 전 Heroku가 만든 12 팩터로는 2026년의 쿠버네티스/MSA 보안을 다 막을 수 없어 3가지 팩터가 더 진화했다.

| 클라우드 진화 (Beyond 12) | 물리적 구현 메커니즘 | 해결되는 보안/운영 한계 |
|:---|:---|:---|
| **API 우선 (API First)** | 코딩부터 하지 말고, Swagger/OpenAPI 등 API 명세서(계약)부터 먼저 짜고 합의한 뒤 각자(MSA) 독립 개발 진입 | 통신이 100%를 차지하는 MSA 환경에서, 뒷단이 다 짜질 때까지 프론트엔드가 놀고 있는 블로킹(Blocking) 병목 타파 |
| **보안(Telemetry & Security)** | 인프라 밖에서 IP 방화벽으로 막는 시대 종말. 앱 내부 코딩 단계에서부터 역할(RBAC) 검증 및 JWT 인증을 코어 로직으로 내재화 | Zero Trust 네트워크 환경에서 언제 어디서든 컨테이너가 해킹(탈취)당해도 내부 비즈니스 데이터 무결성 철통 사수 |

> 요약: 12 팩터가 기본 체력을 훈련하는 '피지컬 트레이닝'이라면, Beyond 12(API, 보안, 원격 측정)는 쿠버네티스(k8s)라는 링 위에서 펀치를 주고받기 위한 '전술 훈련'이다.

## Ⅴ. 실무 적용 방안 및 결론

**적용 방안 3개:**
1. [Kubernetes ConfigMap 및 Secret 연동 (Factor 3: 설정)] 클라우드 이관 프로젝트 시, 기존 Spring `application.yml`에 박혀있던 DB 접속 정보를 싹 지우고, 쿠버네티스의 `ConfigMap`과 `Secret` 객체를 생성하여 Pod(컨테이너)가 기동될 때 OS 환경 변수로 실시간 주입받도록 아키텍처 완전 분리
2. [Redis 기반 Session Clustering (Factor 6: 무상태)] L4 스위치의 Sticky Session(세션 유지) 방식이 특정 컨테이너에 트래픽을 몰빵시키는 병목을 막기 위해, 서버 안의 세션 데이터를 완전 폐기하고 외부 Redis(백킹 서비스)에 JWT 토큰 및 장바구니 세션을 몰아넣어(Off-loading) 트래픽 라운드 로빈(Round-robin) 완벽 분산 처리
3. [Spring Boot Actuator 기반 Graceful Shutdown (Factor 9: 폐기성)] EKS(AWS 쿠버네티스) 오토스케일링 환경에서, 죽어가는 노드가 처리 중이던 결제 트랜잭션이 끊기는 현상을 막기 위해 `server.shutdown=graceful` 설정을 켜서 SIGTERM 수신 후 30초간 신규 트래픽은 막고 기존 처리 큐를 비운 뒤 우아하게 프로세스를 종료하도록 튜닝

**결론:**
- 기술사 판단: 12 팩터 앱은 "클라우드(AWS)만 쓰면 무조건 스케일 아웃(Scale-out)이 될 줄 알았던" 무지한 레거시 개발자들에게 날린 강력한 일침이다. 코드를 컨테이너에 담는다고 클라우드 네이티브가 되는 것이 아니다. 내 서버가 1초 뒤에 사라져도 데이터가 보존되는 무상태(Stateless) 철학을 소스코드 깊숙이 체화해야만 진정한 엘리트 조직으로 도약할 수 있다.
- 향후 방향: 현재 12 팩터 사상은 Kubernetes 프레임워크와 Istio(Service Mesh) 인프라로 완전히 흡수되었다. 개발자가 12가지 팩터를 일일이 코딩하지 않아도 플랫폼(PaaS)이 암묵적으로 설정(Config) 주입과 무상태 라우팅을 강제해 주는 진정한 플랫폼 엔지니어링(Platform Engineering) 시대로 안착했다.
