# 📖 【암기용】 개념 완전 이해

## 한눈에
- **개요**: **12 팩터 앱(12-Factor App)**은 클라우드 네이티브 환경(SaaS)에서 확장성 있고 배포하기 쉬운 애플리케이션을 만들기 위해 지켜야 할 12가지의 아키텍처 및 개발 방법론이다.
- **왜 필요한가**: 과거에는 개발자가 자기 노트북 환경에 맞춰 서버를 세팅했다(서버에 직접 접속해서 설정 파일 수정 등). 하지만 클라우드 환경에서는 서버가 수시로 생기고 사라지므로, 환경에 종속적인 앱은 클라우드에 올릴 수가 없다.
- **핵심 직관**: 텐트(애플리케이션)를 칠 때 땅바닥에 시멘트를 부어 고정(환경 종속)하는 것이 아니라, 언제든 접어서 다른 캠핑장(클라우드)으로 쉽게 옮길 수 있도록 설계하는 규칙 12가지.

## 핵심 용어 정리

| 용어/표기 | 의미 | 비유·예 |
|:---|:---|:---|
| 코드베이스 (Codebase) | 버전 관리되는 하나의 코드 저장소 | 깃허브(GitHub)의 단일 레포지토리 |
| 백킹 서비스 (Backing Service) | 애플리케이션이 실행될 때 네트워크를 통해 이용하는 모든 외부 서비스 | DB, 메시지 큐, 캐시 서버 |
| 무상태 (Stateless) | 애플리케이션이 이전 사용자의 상태나 데이터를 메모리에 기억하지 않는 성질 | 은행 창구 직원이 매번 신분증을 새로 요구함 |
| 동시성 (Concurrency) | 다수의 요청을 처리하기 위해 프로세스 수를 늘려 수평 확장하는 것 | 손님이 많아지면 알바생을 더 고용함 |

## 깊이 이해
- **배경·문제의식**: Heroku(클라우드 PaaS 업체) 엔지니어들이 수백만 개의 앱을 호스팅하면서 "어떤 앱은 클라우드에서 잘 돌고, 어떤 앱은 맨날 죽고 확장이 안 된다"는 패턴을 발견했다. 잘 도는 앱들의 공통된 특징을 모아 정리한 것이 12-Factor다.
- **작동 원리**: 
  - **설정과 코드 분리(Config)**: DB 비밀번호 등을 코드에 하드코딩하지 않고 환경 변수(ENV)로 주입한다.
  - **무상태 프로세스(Stateless)**: 세션 등 상태 데이터는 로컬 메모리가 아닌 Redis 같은 외부 백킹 서비스에 저장하여, 컨테이너가 죽거나 스케일아웃 되어도 문제가 없게 한다.
  - **로그를 이벤트 스트림으로(Logs)**: 앱은 로그 파일 경로를 관리하지 않고 표준 출력(stdout)으로만 뱉으며, 수집기(Fluentd)가 알아서 가져간다.
- **비유**: 넷플릭스 영화. 스마트폰, TV, 노트북(환경) 어디서든 재생되지만, 영화 본편(코드)은 절대 바뀌지 않고, 오직 화질이나 자막(환경 변수)만 플랫폼에 맞춰 주입된다.
- **구체 예시**: 개발 환경과 운영 환경을 최대한 똑같이 유지한다(Dev/prod parity). "내 PC에선 잘 되는데 서버에선 안 돼"라는 변명을 원천 차단하기 위해, 로컬도 Docker 기반으로 운영과 동일한 인프라를 쓴다.
- **흔한 오해·주의점**: "12 팩터는 특정 언어나 프레임워크 기술이다"라는 오해. 12 팩터는 철학이자 방법론이므로 자바, 파이썬, Go 등 어떤 언어로 만들든 동일하게 지켜야 하는 아키텍처 원칙이다.

## 연결 개념
- 클라우드 네이티브 (Cloud Native) — 12-Factor를 준수하여 만든 애플리케이션의 지향점
- MSA (Microservice Architecture) — 마이크로서비스 하나하나는 12-Factor를 만족해야 함
- 컨테이너 / 도커 (Docker) — 12-Factor를 가장 완벽하게 기술적으로 구현해 주는 도구

# 📝 【답안용】 시험 답안 템플릿

## 핵심 인사이트 (3줄 요약)

> 1. **본질**: 12 팩터 앱은 클라우드(PaaS, SaaS) 환경에 최적화된 높은 이식성, 확장성, 회복 탄력성을 갖춘 애플리케이션을 구축하기 위한 12가지 아키텍처 방법론이다.
> 2. **가치**: 코드와 환경 설정을 엄격히 분리하고 무상태(Stateless) 프로세스를 지향하여, 클라우드 환경에서 서버 다운과 무한 수평 확장(Scale-out)에 투명하게 대응할 수 있다.
> 3. **판단 포인트**: MSA와 클라우드 전환 시 레거시 앱이 클라우드 네이티브로 동작할 수 있는지 검증하는 체크리스트이자, 아키텍처 리팩토링의 핵심 기준이 된다.

## 출제 의도 및 답안 포인트

| 출제 의도 | 반드시 짚을 핵심 | 감점 회피 포인트 |
|:---|:---|:---|
| 클라우드 네이티브 애플리케이션 설계 역량 | 설정과 코드 분리(ENV), 무상태성, 백킹 서비스 | 12가지 항목을 단순히 나열만 하고 적용 효과 누락 |
| 레거시 마이그레이션(클라우드 전환) 시 고려사항 | 환경 일치(Dev/Prod Parity), 로그 스트림, 수평 확장 | 특정 벤더(AWS 등) 종속적인 기술 설명으로 치우침 |

> 요약: 12-Factor는 "내 PC에선 잘 도는데 서버에선 안 돈다"는 문제를 뿌리 뽑고, 언제든 스케일아웃이 가능한 클라우드 레디(Cloud-Ready) 상태를 만드는 원칙이다.

## Ⅰ. 개요 및 필요성

- 개요: 서비스로서의 소프트웨어(SaaS) 개발에 적합한, 높은 이식성(Portability)과 확장성을 제공하는 12가지 선언적(Declarative) 아키텍처 구축 원칙
- 배경: 기존 온프레미스 기반의 환경 종속적 설계, 코드 내 하드코딩된 설정, 상태 의존적(Stateful) 프로세스로 인해 클라우드의 동적 확장 지원 불가
- 필요성: 클라우드 네이티브 및 MSA로의 진화 과정에서 새로운 개발자가 프로젝트에 참여하는 시간과 비용을 최소화하고 민첩한 배포 환경(CI/CD) 구축 필수

---

## Ⅱ. 구조 및 구성요소 (12 팩터 분류)

```text
[ 코드/배포 관리 ] -> [ 환경 및 인프라 통합 ] -> [ 프로세스 및 동시성 제어 ]
```

| 범주 | 핵심 팩터 (Factor) | 설계 원칙 |
|:---|:---|:---|
| 코드 및 배포 | 1. Codebase, 3. Config, 5. Build/Release/Run | 하나의 저장소 유지, 환경 설정(ENV)의 철저한 분리 및 독립적 빌드 단계 분리 |
| 아키텍처/인프라 | 2. Dependencies, 4. Backing Services, 6. Processes | 명시적 의존성 선언, 외부 서비스를 리소스로 취급, 무상태(Stateless) 프로세스 실행 |
| 확장 및 통제 | 8. Concurrency, 9. Disposability, 10. Dev/Prod Parity | 프로세스 모델 수평 확장, 빠른 시작/종료(안전한 폐기), 개발/운영 환경 최대한 일치 |
| 텔레메트리/운영 | 7. Port Binding, 11. Logs, 12. Admin Processes | 포트 바인딩 통한 서비스 노출, 로그를 이벤트 스트림으로 취급, 일회성 관리 프로세스 분리 |

> 요약: 12 팩터는 코드 관리부터 인프라 통합, 프로세스 제어, 운영 편의성까지 클라우드 네이티브 시스템이 갖춰야 할 전체 생명주기를 커버한다.

---

## Ⅲ. 동작원리 및 흐름도 (12 팩터 적용 라이프사이클)

```text
(1/2) Git 저장소 및 의존성 격리 -> (3) 환경변수(ENV) 주입 -> (5) Build/Release 분리
-> (6/8) 무상태 프로세스 스케일아웃 -> (9) Graceful Shutdown -> (11) stdout 로그 수집
```

- 1단계 [코드 격리]: 단일 코드베이스(Factor 1)에서 의존성을 명시적으로 선언(Factor 2)하여 어디서든 동일하게 빌드되도록 구성
- 2단계 [빌드와 릴리스 분리]: 빌드된 실행 파일에 각 배포 환경(Dev/Prod)에 맞는 환경변수(Factor 3)를 결합하여 고유한 릴리스 버전 생성(Factor 5)
- 3단계 [실행 및 스케일아웃]: 백킹 서비스(Factor 4)에 상태를 위임하고, 앱은 무상태(Factor 6)로 실행되어 부하에 따라 프로세스를 동시성(Factor 8) 기반 수평 확장
- 4단계 [폐기 및 모니터링]: 클라우드 오케스트레이터가 필요시 프로세스를 즉시 폐기(Factor 9)하며, 이 과정의 모든 로그는 표준 출력으로 스트리밍(Factor 11)하여 중앙 관리

> 요약: 코드는 불변(Immutable) 상태로 유지되며, 환경과 백킹 서비스를 외부에서 주입받아 수많은 무상태 프로세스로 동시 실행 및 통제된다.

---

## Ⅳ. 특징
- 극단적인 이식성 (Portability): 운영체제나 서버 사양 등 기저 시스템 환경에 종속되지 않아, AWS에서 GCP로의 이전이나 로컬 컨테이너 실행이 자유로움
- 민첩성 및 스케일링 (Agility & Scaling): 상태(State)가 없으므로 로드밸런서 뒤에서 언제든지 프로세스를 늘리고 줄이는 동적 탄력성(Elasticity) 극대화
- 환경 일치성 보장 (Parity): 개발, 스테이징, 운영 환경의 차이를 최소화(Factor 10)하여 릴리스 시 발생하는 예측 불가능한 장애(사이드 이펙트)를 원천 차단

> 요약: 12 팩터를 준수한 애플리케이션은 인프라의 변화나 확장에 흔들리지 않는 견고한 클라우드 친화성을 지닌다.

## Ⅴ. 심화 비교 및 적용 판단

| 비교 축 | 레거시 온프레미스 앱 | 12-Factor 앱 | 선택 기준 |
|:---|:---|:---|:---|
| 상태 관리 (State) | 로컬 파일/메모리에 세션 저장 | DB/Redis 등 백킹 서비스에 위임 (무상태) | 클라우드 Scale-out 필수 여부 |
| 환경 설정 (Config) | 코드 내부 또는 특정 properties 파일 | OS 환경 변수 (Environment Variables) | 보안 유지 및 환경 이식성 |
| 로그 처리 (Log) | 특정 경로의 로그 파일로 순환 저장 | 표준 출력(stdout) 스트림으로 방출 | 중앙 집중형 관측성 시스템 유무 |

> 요약: 고정된 서버 자원을 사용하는 기존 시스템은 레거시 방식으로도 동작하나, 쿠버네티스와 같은 동적 컨테이너 환경에서는 12-Factor 적용이 필수다.

**리스크·대응:**
- 무상태 전환에 따른 통신 지연: 로컬 메모리를 쓰지 않고 원격 백킹 서비스(Redis 등) 호출 시 네트워크 레이턴시 증가 → 백킹 서비스의 인메모리 캐싱 최적화 및 VPC 내부 초고속망 배치
- 외부 설정 의존도 심화: 환경 변수(ENV) 설정 누락 시 프로세스 기동 즉시 크래시(Crash) 발생 → 시작 시 필수 환경변수 존재 여부를 검증하는 Fail-Fast 로직 적용

**도입 후 점검 지표:**
- 배포 민첩성: 코드 커밋 후 운영 배포까지 걸리는 시간(Lead Time) 10분 이내 단축 — CI/CD 파이프라인 지표
- 프로세스 회복력: 프로세스 강제 종료 시 Graceful Shutdown 성공률 100% 및 재생성 시간 3초 이내 방어

## Ⅵ. 실무 적용 및 결론

**적용 방안 3개:**
1. 레거시 마이그레이션 전략 (Factor 3, 4, 6): 모놀리식 앱을 클라우드로 올리기 전, 가장 먼저 하드코딩된 DB 접속 정보를 ENV로 빼고(Config), 로컬 세션을 Redis(Backing Service)로 넘겨 무상태(Stateless)화 적용
2. CI/CD 및 컨테이너 통합 (Factor 1, 5, 10): 단일 Git 저장소(Codebase)에서 Docker 이미지 빌드를 트리거하고, 쿠버네티스의 ConfigMap/Secret을 결합하여 릴리스(Release)하는 파이프라인 구축
3. 클라우드 로깅 아키텍처 (Factor 11): 애플리케이션은 오직 `stdout`과 `stderr`로 로그를 남기고, DaemonSet으로 배포된 Fluent-bit나 Logstash가 이를 수집해 ELK로 보내도록 인프라 분리

**결론 (2줄):**
- 기술사 판단: 12-Factor 앱은 단순한 기술 스택이 아니라 클라우드 네이티브 생태계(Docker, K8s, CI/CD)와 가장 완벽하게 호환되기 위한 필수 아키텍처 철학이다.
- 향후 방향: 최근에는 12 팩터에 보안(Security), 텔레메트리, API 우선 설계 등을 추가 확장한 '15-Factor App(또는 Beyond the 12-Factor)' 개념으로 클라우드 네이티브 표준이 진화하고 있다.
