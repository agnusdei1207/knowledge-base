## 핵심 인사이트 (3줄 요약)
- 과거엔 "일반 유저는 관리자 페이지 못 들어가!"라는 규칙(인가, Authorization)을 개발자가 자바나 파이썬 코드(`if user != admin`) 안에 하드코딩했음. 코드를 바꾸려면 서버를 다시 배포해야 함.
- **OPA(Open Policy Agent)**는 이 모든 정책(규칙)을 프로그램에서 뜯어내서, 중앙의 독립된 **'경찰관 서버(정책 엔진)'**로 분리하는 기술임. `Rego`라는 전용 언어로 규칙을 적어두면, OPA가 모든 접근 요청을 심사해 줌.
- "코드형 정책(Policy as Code)"의 글로벌 표준. 쿠버네티스에서 "root 권한 컨테이너 띄우지 마!", API 게이트웨이에서 "밤 10시 이후엔 결제 API 호출 금지!" 같은 모든 종류의 규정을 **단 하나의 OPA로 통합 통제**할 수 있음.

## Ⅰ. 개요 및 필요성
- **개요**: 클라우드 네이티브 환경(MSA, Kubernetes, API Gateway, CI/CD 등) 전반에 걸쳐 통합된 컨텍스트 기반 정책 결정을 제공하는 범용 오픈소스 정책 엔진(Policy Engine).
- **필요성**: 회사에 규칙이 생김. "금요일 퇴근 후엔 서버 배포 금지". 이 규칙을 Jenkins에도 코딩해 넣고, Kubernetes 설정에도 넣고, 사내망 API에도 일일이 코딩함. 정책이 바뀌면 3군데 코드를 다 고쳐야 함. **"아니, 회사의 모든 규칙(결재 로직, 권한)을 하나의 중앙 문서로 적어두고, 각 시스템은 중앙 문서한테 '이거 해도 돼?'라고 물어보게만 만들면 안 돼?"**
---
## Ⅱ. 핵심 아키텍처 및 동작 원리 (Decoupling Policy)
OPA의 철학은 **정책(Policy)과 실행(Enforcement)을 완벽히 분리**하는 것.

- **1. Policy (정책 - Rego 언어)**:
  - 정책을 `Rego`라는 선언적 언어로 텍스트 파일로 작성함. (예: `allow = true { input.method == "GET" }`).
- **2. Data (참조 데이터)**:
  - 정책 판단에 필요한 데이터 (예: "홍길동은 관리자다"라는 JSON 데이터 리스트).
- **3. Input (요청 질의)**:
  - 쿠버네티스나 API 서버가 OPA에게 질문을 던짐. (예: `JSON: { "user": "홍길동", "action": "delete" }`).
- **4. Output (판단 결과)**:
  - OPA가 Policy와 Data를 바탕으로 계산해서 대답함. (`JSON: { "allow": false }`). 실행 시스템은 그 대답대로만 행동함.

```text
[ 하드코딩 방식 vs OPA 분리 방식 ]

 🚫 [ 과거: 강결합 (하드코딩) ]
 - 결제 서버 코드: `if (user.role == 'admin') { allow(); }`
 - 단점: 룰이 "어드민이거나 VIP 등급"으로 바뀌면 개발자가 결제 서버 코드를 뜯어고치고 전체 서버를 다시 배포해야 함.

 ✅ [ OPA: 정책의 분리 (Policy as Code) ]
 - 결제 서버: "OPA 경찰관님, A 유저가 결제 버튼 눌렀는데 통과시킬까요?" (Input 던짐)
 - OPA 엔진: (자신의 Rego 법전을 뒤져봄) "음, 룰에 어긋나. 거부(Deny)해!" (Output 리턴)
 - 결제 서버: "네 알겠습니다. 거부!" (서버 코드는 1줄도 안 바뀜).
```

## Ⅲ. 오해와 진실
| 오해 | 진실 |
|---|---|
| "OPA는 아이디/비번 확인하는 로그인(Authentication) 서버인가요?" | **절대 아님.** 로그인은 Keycloak 같은 IdP가 하는 것. OPA는 "이 사람이 누군지 이미 증명된 상태"에서, **"이 사람이 지금 이 행동을 해도 되는가?(Authorization, 인가)"**만을 판단하는 재판관 역할임. |
| "모든 API 요청마다 외부 OPA 서버를 찌르면 네트워크 지연(Latency) 때문에 짱 느리겠네?" | **아님.** 실무에서 OPA는 중앙 서버 1대 파놓고 쓰는 게 아님. 마이크로서비스 컨테이너 바로 옆에 **사이드카(Sidecar)** 패턴으로 딱 붙여서 띄움. 로컬 호스트 통신이므로 1ms(0.001초) 만에 판결이 끝남. |

## Ⅳ. 실무 적용 및 기술사 판단
- **Kubernetes 어드미션 컨트롤 (Admission Control) 통합**: 개발자가 K8s에 `root` 권한으로 실행되는 위험한 파드(Pod)를 띄우려고 `kubectl apply`를 날림. 기술사는 **OPA Gatekeeper**를 K8s Admission Webhook에 연동하여, 이 위험한 요청이 K8s DB(etcd)에 저장되기도 전에 OPA가 낚아채서 "보안 규정 위반! 배포 거부!"를 때리도록 자동화된 통제 아키텍처를 구축해야 함.
- **GitOps 기반의 형상 관리 (Policy as Code)**: OPA 정책(`Rego` 파일)은 단순한 텍스트 코드임. 기술사는 이 정책 파일들을 Git 저장소에 올리고, 정책이 수정될 때마다 개발자가 PR(Pull Request) 리뷰를 거치게 하며 자동화된 단위 테스트를 수행하는 **GitOps 파이프라인**을 통해, 기업의 인가 거버넌스를 완벽하게 추적하고 통제해야 함.
---
## Ⅴ. 기대효과 및 결론
- 클라우드 네이티브의 수많은 인프라(K8s, Terraform, API)마다 찢어져 있던 보안 및 권한 설정 방식을 `Rego`라는 단 하나의 언어와 표준으로 대통합해 냄.
- 비즈니스 로직과 권한 검사 로직을 분리함으로써, 개발자는 비즈니스에만 집중하고 보안팀/운영팀은 서버 배포 없이 자유롭게 정책(룰)을 업데이트할 수 있는 '진정한 정책 주도 아키텍처'를 실현함.

### 📈 관련 키워드 및 발전 흐름도
- 역할 기반 접근 제어(RBAC)와 코드 내 하드코딩 유행 ➡️ MSA의 확산으로 50개 서버의 권한 로직이 파편화됨 ➡️ 정책(Policy)만 분리해서 중앙에서 관리하자는 사상 대두 ➡️ 2016년 Styra사에서 OPA 오픈소스 발표 ➡️ 클라우드 네이티브 컴퓨팅 재단(CNCF)의 최상위 졸업(Graduated) 프로젝트로 승격하며, K8s와 MSA 인가/정책 분야의 글로벌 표준으로 자리 잡음 (현재)

### 👶 어린이를 위한 3줄 비유 설명
1. 옛날엔 놀이공원의 놀이기구 50개마다 직원이 서서 키가 120cm 넘는지 일일이 자로 재보고 태워줬어요. 기준이 130cm로 바뀌면 50명한테 다 알려줘야 했죠.
2. **OPA**는 놀이공원의 **'유일한 법전(규칙책)'**이에요! 이제 놀이기구 기계들은 사람을 태우기 전에, OPA 법전에게 "키 125cm인데 태울까요?" 하고 무전기(API)로 물어보기만 해요.
3. 법전이 "아니, 오늘부터 130cm니까 거절해!"라고 대답해 주면 바로 컷! 규칙이 바뀌어도 이 법전 딱 한 권만 수정하면 온 동네 놀이기구 규칙이 한방에 바뀌는 마법이랍니다!

### 🔀 문제 유형별 목차 전환 (이 키워드 출제 시)
- **개념/도구 설명형 (Ⅱ·Ⅲ 강조)**: Policy(Rego), Data, Input, Output의 분리 구조(Decoupling)와 JSON 기반 통신 원리. 사이드카(Sidecar) 아키텍처를 통한 낮은 응답 시간(Low Latency) 달성 원리.
