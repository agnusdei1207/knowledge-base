# 📖 【암기용】 개념 완전 이해

## 한눈에
- **개요**: 소프트웨어 개발 수명 주기(SDLC) 초기부터 끝까지 보안을 융합하여, "보안이 내재화된 자동화된 배포"를 실현하는 방법론
- **왜 필요한가**: DevOps의 속도로 코드를 배포하는데, 마지막 배포 직전에만 보안팀이 수동 점검하면 병목이 생기고(출시 지연) 수정 비용이 급증한다.
- **핵심 직관**: 보안 검사를 출시 전 "문지기" 역할에서, 코딩부터 배포까지 매 단계마다 촘촘히 쳐놓은 "안전망"으로 바꾸는 것.

## 핵심 용어 정리

| 용어/표기 | 의미 | 비유·예 |
|:---|:---|:---|
| Shift-Left | 보안 검사와 품질 검증을 SDLC의 가능한 가장 이른(왼쪽) 단계로 당김 | 병이 커지기 전 조기 건강검진 |
| SAST (정적 분석) | 실행하지 않고 소스코드 자체의 보안 취약점 분석 | 건축 도면의 구조적 결함 검사 |
| DAST (동적 분석) | 실행 중인 애플리케이션을 외부에서 해킹하듯 테스트 | 지어진 건물에 모의 침입 시도 |
| SCA (소프트웨어 구성 분석) | 오픈소스 라이브러리의 알려진 취약점(CVE) 스캔 | 식자재 원산지 및 유통기한 검사 |

## 깊이 이해
- **배경·문제의식**: 클라우드와 DevOps 도입으로 하루에 수십 번씩 배포하는 환경이 되었다. 하지만 보안은 여전히 폭포수(Waterfall) 모델처럼 마지막에 몰아서 하거나 방화벽 등 경계 보안에만 의존했다. 결과적으로 배포 병목 현상이 발생하고, Log4j 사태처럼 오픈소스 취약점에 무방비로 노출되었다.
- **작동 원리**: 개발자가 IDE에서 코드를 짤 때 플러그인이 취약점을 경고(Shift-Left). 코드를 커밋하면 파이프라인이 SAST와 SCA(오픈소스 취약점)를 자동 수행한다. 빌드된 컨테이너 이미지는 레지스트리에서 스캔되고, 테스트 환경에 배포되면 DAST가 작동한다. 이 모든 과정이 파이프라인 코드로 자동화되어 개발자에게 즉각 피드백된다.
- **비유**: 자동차 제조 공정에서 맨 마지막에 충돌 테스트를 하는 것이 아니라, 부품 설계 시점(SAST), 조립 단계(SCA), 엔진 시동 시점(DAST)마다 센서를 달아 결함을 실시간으로 걸러내는 공장.
- **구체 예시**: 개발자가 평문 암호가 포함된 코드를 푸시함 -> Jenkins 파이프라인 내 SonarQube(SAST)가 이를 감지 -> 빌드를 즉시 실패(Fail)시키고 개발자 슬랙으로 알림 발송 -> 개발자가 수정 전까지 배포 불가.
- **흔한 오해·주의점**: "보안 도구를 몇 개 사서 파이프라인에 넣으면 DevSecOps 완성?" 아니다. 도구에서 발생한 수많은 오탐(False Positive)으로 파이프라인이 멈추면 개발자들이 보안을 우회하려 한다. 개발자 친화적인 알림과 보안팀과의 협업 문화가 필수다.

## 연결 개념
- DevOps 파이프라인: DevSecOps가 얹혀지는 기초 인프라
- 소프트웨어 공급망 보안 (SBOM, SLSA): SCA와 연계하여 서드파티 의존성 취약점을 방어하는 핵심 요소
- 정책 기반 제어 (Policy as Code): OPA 등을 활용해 보안 정책을 코드로 관리

# 📝 【답안용】 시험 답안 템플릿

## 핵심 인사이트 (3줄 요약)

> 1. **본질**: DevSecOps는 SDLC 전 과정(계획-코드-빌드-배포-운영)에 걸쳐 보안 활동을 내재화하고 자동화하는 문화 및 기술 체계다.
> 2. **가치**: Shift-Left 접근법을 통해 취약점 조기 발견으로 수정 비용을 절감하고, 보안 병목 없는 신속하고 안전한 배포(Secure by Default)를 달성한다.
> 3. **판단 포인트**: 단계별 적용되는 구체적 보안 기술(SAST/DAST/SCA)과 개발·보안·운영 간의 책임 공유(Shared Responsibility) 문화를 통합적으로 제시해야 한다.

## 출제 의도 및 답안 포인트

| 출제 의도 | 반드시 짚을 핵심 | 감점 회피 포인트 |
|:---|:---|:---|
| Shift-Left 개념의 이해 | 보안 점검의 전진 배치, 조기 결함 발견 비용 절감 효과 | 보안을 개발 후반부 작업으로 분리 서술 |
| 단계별 보안 점검 기술 매핑 | IDE(Lint), CI(SAST/SCA), CD(DAST/이미지 스캔), Ops(CSPM) | 툴 이름만 나열하고 파이프라인 단계 누락 |
| 현대 공급망 위협 대응 | 오픈소스 취약점 관리, SBOM, 컨테이너 보안 | 네트워크/방화벽 중심의 레거시 보안 제시 |

> 요약: 개발 파이프라인의 각 단계에 어떤 보안 요소가 자동화되어 삽입되는지 명확한 매핑을 보여야 한다.

## Ⅰ. 개요 및 필요성

- 개요: DevOps의 민첩성을 유지하면서 애플리케이션 보안, 인프라 보안, 규정 준수를 파이프라인 전반에 자동화하여 통합하는 방법론
- 배경: 클라우드 네이티브 환경 진화와 일 십~백 회 배포 환경에서 기존의 사후 수동 보안 점검 방식은 심각한 병목 초래
- 필요성: 조기 취약점 발견(Shift-Left)을 통한 수정 비용 최소화, 소프트웨어 공급망 공격(Supply Chain Attack) 선제 대응, 보안 규정 자동 준수

---

## Ⅱ. 구조 및 구성요소

```text
[Plan/Code] -----> [Build/Test] -----> [Release/Deploy] -----> [Operate/Monitor]
    |                  |                      |                       |
 Threat Modeling    SAST / SCA          Container Scan           CSPM / CWPP
 IDE Security       DAST / IAST         Policy as Code           WAF / RASP
```

| 구성요소 | 역할 | 적용 도구/기술 예 |
|:---|:---|:---|
| Code (개발) | 코드 작성 시점의 취약점 사전 차단 | IDE 플러그인(Linting), 시크릿 탐지 |
| Build (빌드) | 소스코드 구조 분석 및 의존성 취약점 점검 | SAST(정적), SCA(오픈소스/SBOM) |
| Test (테스트) | 런타임 환경에서 공격 시뮬레이션 | DAST(동적), IAST(대화형) |
| Deploy/Ops (운영) | 배포 이미지 무결성 검증 및 인프라 보안 | 컨테이너 이미지 스캔, OPA(정책), RASP |

> 요약: 각 파이프라인 단계마다 성격이 다른 자동화된 보안 도구가 배치되어 다심도 방어(Defense in Depth)를 구현한다.

---

## Ⅲ. 동작원리 및 흐름도

```text
코드 Push -> SAST/SCA 스캔 -> 취약점 판단 -> (Fail) 개발자 피드백
                             -> (Pass) 이미지 빌드 -> 이미지 스캔 -> 배포
```

- 1단계 [코드 기반 점검 (Shift-Left)]: 개발자가 커밋 시 파이프라인이 SAST로 소스코드 패턴 분석 및 SCA로 오픈소스 CVE 스캔 수행
- 2단계 [자동화된 게이트웨이 (Quality Gate)]: 발견된 취약점의 심각도(Critical/High)가 정책 기준을 초과하면 빌드를 즉시 중단(Break 단절)
- 3단계 [동적 환경 검증]: 컨테이너 기반 격리 환경에 배포 후, DAST 도구가 SQL 인젝션, XSS 등 런타임 취약점 자동 모의 해킹
- 4단계 [안전한 배포 및 지속 모니터링]: 서명된 안전한 아티팩트만 운영 클러스터에 배포하고, 런타임 보안 도구(RASP)로 제로데이 공격 방어

> 요약: 코드부터 런타임까지 모든 단계에 Security Gate가 존재하며, 통과하지 못하면 다음 단계로 넘어가지 못한다.

---

## Ⅳ. 특징
- [Shift-Left 보안]: 결함을 배포 후가 아닌 개발 단계에서 발견하여, 수정 비용을 최대 100배 이상 절감
- [Security as Code]: 인프라뿐만 아니라 보안 정책 설정, 규정 준수 검사까지 코드로 정의(Policy as Code)하여 자동화
- [책임 공유 (Shared Responsibility)]: 보안은 보안팀만의 몫이 아니라, 개발자·운영자·보안팀 모두가 책임을 분담하는 문화
- [투명한 가시성]: 보안 스캔 결과가 개발자의 익숙한 도구(IDE, Jira, Slack)로 즉각 피드백되어 조치 유도

> 요약: 보안 검사를 사람의 개입 없이 코드로 자동화하고, 그 책임을 개발 프로세스 전반으로 분산시킨다.

## Ⅴ. 심화 비교 및 적용 판단

| 비교 축 | 레거시 보안 (Waterfall) | DevSecOps | 선택 기준 |
|:---|:---|:---|:---|
| 개입 시점 | 테스트 완료 후 배포 직전 | SDLC 전 단계 (Shift-Left) | 배포 주기 및 속도 목표 |
| 점검 방식 | 보안 전문가의 수동/반자동 점검 | 파이프라인 내 코드 기반 자동 점검 | 데브옵스 인프라 성숙도 |
| 장애 대응 | 사후 패치 및 방화벽 차단 중심 | 컨테이너 재빌드/배포 및 근본 원인 제거 | 클라우드 네이티브(불변 인프라) 환경 여부 |

> 요약: CI/CD가 구축된 민첩한 환경에서는 기존 경계 보안이 아닌 파이프라인 내재화된 DevSecOps가 필수다.

**리스크·대응:**
- [스캔 오탐(False Positive) 폭발]: 너무 많은 보안 알람으로 개발자가 알람을 무시하는 현상 → 치명도(Critical/High) 위주로 게이트웨이 설정, 예외 처리 프로세스 간소화 (지표: 오탐율 및 티켓 무시 비율)
- [빌드 시간 지연]: DAST 등 무거운 보안 검사로 파이프라인 실행 지연 → SAST/SCA는 매 커밋마다, 무거운 DAST는 야간 배치(Nightly Build)로 분리 (지표: 파이프라인 총 소요 시간)

**도입 후 점검 지표:**
- 취약점 평균 수정 시간(MTTR for Vulnerabilities): 발견부터 패치까지 걸린 시간 — 취약점 관리 대시보드
- 배포 전 취약점 발견 비율: 전체 결함 중 운영 배포 전에 식별·조치된 비율 — Shift-Left 성공 척도

## Ⅵ. 실무 적용 및 결론

**적용 방안 3개:**
1. 의존성 취약점(SCA) 조기 통제: Nexus나 Artifactory에 패키지 프록시를 구성하고, 사전에 인가된/스캔된 안전한 오픈소스 라이브러리만 다운로드 가능토록 통제
2. 민감 정보(Secret) 노출 방지: Git-secrets 또는 Trivy를 CI 초기 단계에 연동하여 소스코드에 하드코딩된 API Key, 패스워드 커밋을 원천 차단
3. Policy as Code 도입: OPA(Open Policy Agent)를 쿠버네티스 Admission Controller에 연동하여, `root` 권한 컨테이너 등 보안 정책에 어긋나는 배포를 런타임 직전에 차단

**결론 (2줄):**
- 기술사 판단: DevSecOps는 보안 툴의 도입 개수가 아니라, 파이프라인 속도를 저해하지 않으면서 핵심 취약점을 차단하는 Quality Gate의 튜닝이 성패를 가른다.
- 향후 방향: 최근 소프트웨어 공급망 공격 방어가 핵심 과제로 떠오르며, DevSecOps 체계에서 SBOM(소프트웨어 자재명세서) 생성 및 검증 파이프라인이 필수 표준으로 자리잡을 것이다.
