## 미리 알고가기

- DevSecOps는 보안을 개발과 배포 흐름 안에 통합하는 방식임
- SAST는 코드를 실행하지 않고 소스 수준에서 취약 패턴을 찾는 정적 분석임
- SCA는 오픈소스 의존성과 알려진 취약점을 점검하는 분석임

## 작성 근거(검토용)

- DevSecOps는 검사 시점, 결함 처리 경로, 운영 부담, 적용 환경을 핵심 비교축으로 선정함
- 구성과 절차는 코드·의존성 검사부터 정책 판정과 운영 피드백까지의 흐름을 중심으로 제시함
- 실무 판단은 오탐률, 우회 배포율, 취약점 수정 시간, 반복 취약점 수로 구체화함

## Ⅰ. 개요

- **정의/개념**: DevSecOps는 개발·배포 흐름에 보안 검사·정책 집행·취약점 대응을 통합하는 소프트웨어 전달 방식임
- **배경/필요성**: 출시 직전 보안 점검은 취약점 수정 범위와 릴리스 지연을 키우므로 개발 초기부터 자동 보안 통제가 필요함

## Ⅱ. 특징

- 보안 검사를 개발 초반과 파이프라인 단계에 분산 배치함
- 정책 위반을 자동 차단해 배포 기준을 일관되게 유지함
- 오탐률과 검사시간이 팀 기준을 넘으면 파이프라인 우회와 예외 요청이 늘어남
- 취약점 위험도별 수정 기한과 처리 담당자를 지정해야 함

## Ⅲ. 종류 및 비교

| 판단 기준 | 후행 보안 점검 | DevSecOps |
|:---|:---|:---|
| 검사 시점 | 개발 후반이나 배포 직전에 집중됨 | 개발부터 운영까지 흐름 전체에 분산됨 |
| 결함 처리 | 배포 전 보안 점검에서 결함 발견·수정 | commit·build·배포 단계별 검사와 위험도 기반 차단 |
| 구조상 한계 | 늦게 발견돼 수정 범위와 비용이 커짐 | 정책과 도구와 운영 책임을 함께 설계해야 함 |
| 대표 환경 | 배포 전 별도 보안 승인을 수행하는 조직 | 변경마다 SAST·SCA·비밀 탐지·정책 검사를 실행하는 조직 |

> 요약: 배포 전 집중 검사는 후행 보안 점검, 개발부터 운영까지 단계별 검사는 DevSecOps 방식임.

## Ⅳ. 구성요소 및 구조

| 구성요소 | 설명 |
|:---|:---|
| 보안 검사 단계 | SAST와 SCA와 비밀 정보 탐지가 코드와 의존성 위험을 조기에 드러냄 |
| 정책 코드화 | 배포 허용 기준과 승인된 예외를 코드로 정의해 자동 집행함 |
| 취약점 분류 | 모든 경고를 같은 수준으로 다루지 않고 위험도와 노출 범위에 따라 우선순위를 정함 |
| 운영 피드백 | 운영 중 발견된 보안 사건을 다시 개발 흐름으로 돌려 반복 취약점을 줄임 |

> 요약: 단계별 보안 검사가 취약점을 찾고 정책 코드가 배포 여부를 판정하며 운영 결과를 규칙에 반영함.

## Ⅴ. 원리 및 절차 흐름도

```text
+-------------+     +-------------+     +-------------+     +-------------+
| 코드/의존성 검사 | --> | 정책 판정      | --> | 배포/운영 모니터링 | --> | 취약점 개선    |
+-------------+     +-------------+     +-------------+     +-------------+
```

1. **코드와 의존성 검사**: 정적 분석과 라이브러리 검사를 수행함
2. **정책 판정**: 위험도와 정책 기준에 따라 통과 여부를 결정함
3. **배포 및 운영 모니터링**: 배포 후 런타임 보안 신호를 관찰함
4. **취약점 개선**: 결과를 수정 작업과 기준 보강으로 연결함

> 요약: 코드·의존성 검사 결과를 정책으로 판정하고 운영 보안 사건을 다음 개발·검사 기준에 반영함.

## Ⅵ. 실무 사례

1. 금융 서비스는 SAST·SCA 규칙을 위험도별로 적용하고 오탐률·우회 배포율을 확인함
2. 오픈소스 플랫폼은 취약점 수정 기한을 운영하고 수정 시간·반복 취약점 수를 확인함

## Ⅶ. 결론

DevSecOps는 전달 단계별로 보안 결함을 탐지하고 위험도·노출 범위에 따라 수정·차단하는 운영 방식임
