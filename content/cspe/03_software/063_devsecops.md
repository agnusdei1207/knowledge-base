# 📖 【암기용】 개념 완전 이해

> 목적: 이 개념을 처음 보는 사람도 완벽히 이해하게 만든다. 시험 답안 양식이 아니라, 이해를 위한 친절한 설명이다.

## 한눈에
- **개요**: **DevSecOps**는 쾌속 질주하는 데브옵스(DevOps) 파이프라인(개발-운영) 한가운데에 **'보안(Security)'을 강제로 욱여넣어 하나로 합친 사상**이다. "배포 속도는 유지하면서, 보안 검사도 사람 대신 기계(파이프라인)가 0.1초 만에 다 해버리자!"는 궁극의 자동화 철학이다.
- **왜 필요한가**: 데브옵스 시대가 오면서 개발자들은 하루에 10번씩 코드를 배포(CI/CD)했다. 그런데 옛날 방식의 보안팀(보안 꼰대들)이 배포 직전에 나타나서 "엑셀 체크리스트 작성해 와. 취약점 검사하게 배포 1주일 연기해!"라고 막아섰다. 결국 속도(Agile)와 보안(Security)이 정면충돌했고, 이를 타파하기 위해 보안팀의 엑셀을 버리고 '파이프라인 보안 로봇(코드)'으로 대체한 것이다.
- **핵심 직관**: 
  - **시프트 레프트 (Shift-Left)**: ⭐️(가장 중요) 파이프라인의 맨 끝(오른쪽=운영/배포)에서 하던 보안 검사를 맨 앞(왼쪽=코딩/빌드)으로 당겨온다. 코드를 짜자마자(왼쪽) 보안 로봇이 즉시 해킹 테스트를 때려서 빠꾸먹인다.

## 깊이 이해
- **배경·문제의식**: 개발자들은 깃허브에서 남이 짜놓은 소스(오픈소스)를 무단 복제(Ctrl+C, V)해다 쓴다. (Log4j 사태). 그 안에 해커가 심어놓은 백도어나 비밀번호 하드코딩이 섞여 있어도 CI/CD 파이프라인은 그냥 눈 감고 통과시켰다. (Garbage in, Garbage out). 고속도로(CI/CD)에 톨게이트(보안)가 없으니 범죄자(해킹 코드)가 빛의 속도로 실서버까지 뚫고 들어갔다.
- **작동 원리 (파이프라인 단계별 보안 로봇 침투)**:
  1. **IDE (코딩 중)**: 개발자가 VScode에서 `password = "1234"`라고 치는 순간, 플러그인이 빨간줄을 긋고 욕함.
  2. **Git (커밋 중)**: 비번이 적힌 코드를 강제로 Push 하면, Git 훅(Hook)이 발동해서 업로드 자체를 거부함 (Pre-commit hook).
  3. **Build (SAST)**: 젠킨스가 코드를 컴파일할 때, 정적 분석 봇(SonarQube)이 코드 전체를 스캔해서 SQL 인젝션 취약점이 있으면 빌드를 터뜨림(Block).
  4. **Package (SCA/DAST)**: 도커 컨테이너를 구웠을 때, 안에 구형 오픈소스(Log4j)가 있으면 컨테이너 폐기(SCA). 살아있는 서버를 띄워놓고 가짜 해킹 공격(DAST)을 때려봄.
- **비유**: 
  - 과거: 공항 출국장(운영). 짐(코드)을 다 부치고 비행기 타기 직전에 폭발물 검사해서 걸리면 집으로 쫓겨남 (시간/비용 극심).
  - DevSecOps: 집에서 가방 싸기(왼쪽/코딩). 짐을 쌀 때부터 가방 자체가 폭발물을 넣으면 안 잠기게 설계됨(시프트 레프트).
- **흔한 오해·주의점**: "그럼 보안팀은 할 일이 없어지나요?" 아니다. 보안팀은 엑셀을 버리고, CI/CD 파이프라인(젠킨스)에 심어놓을 '보안 봇(Bot)의 정책 코드'를 짜는 파이프라인 설계자로 직무가 180도 바뀐다. (Security as Code).

## 연결 개념
- **SCA / SAST / DAST**: DevSecOps를 완성하는 3대 보안 스캐너 무기. (SCA=남이 짠 오픈소스 검사, SAST=내가 짠 코드 문법 검사, DAST=실제 동작 중인 서버 모의 해킹).
- **IaC (인프라 코드화)**: 인프라도 코드로 짜는 시대(Terraform)가 왔다. 인프라 코드를 실행하기도 전에 봇이 읽어보고 "방화벽 포트 다 열려있는데? 반려!"라고 막아버리는 것도 DevSecOps다.

# 📝 【답안용】 시험 답안 템플릿

> 목적: 시험장에서 25분에 그대로 쓰는 답안 양식. 작성방식(추상표현 금지·수치·도식·문제유형 전환)을 엄격히 지킨다.
> 핵심: 이 시험은 정보를 많이 나열하는 시험이 아니라, 문제 신호어에서 출제자 의도를 읽고 핵심 논점을 선별해 쓰는 시험이다.

## 핵심 인사이트 (3줄 요약)

> 1. **본질**: 애플리케이션 개발(Dev)과 운영(Ops) 파이프라인의 모든 생명주기(SDLC)에 걸쳐 보안(Security) 검증을 통합 및 자동화하는(Security as Code) 조직 문화이자 엔지니어링 실천론이다.
> 2. **가치**: 배포 직전(오른쪽)에 수행하던 무거운 보안 검사를 개발 극초기(왼쪽)로 끌어오는 '시프트 레프트(Shift-Left)' 사상을 통해, 배포 속도(Agility)의 저하 없이 취약점 수정 비용을 1/100로 극단적 압축한다.
> 3. **판단 포인트**: 단순히 보안 툴(도구)의 나열에 그치지 말고, CI/CD 파이프라인의 각 구획(Code -> Build -> Test -> Deploy)마다 SAST, SCA, DAST 등 어떤 보안 로봇이 매핑되어 파이프라인을 차단(Block)하는지 도식화해야 한다.

## 출제 의도 및 답안 포인트

| 출제 의도 | 반드시 짚을 핵심 | 감점 회피 포인트 |
|:---|:---|:---|
| 기존 사후 보안(Perimeter Security) 검열의 병목 한계 지적 | 배포 속도와 보안의 충돌 및 시프트 레프트(Shift-Left) 사상 | 애자일과 보안이 왜 충돌했는지 근본적 배경(Time to market) 누락 |
| CI/CD 파이프라인 단계별 보안 통제 도구 매핑 | Code(IDE) -> Build(SAST/SCA) -> Test(DAST) 도식 | SAST(화이트박스)와 DAST(블랙박스)의 스캐닝 원리 차이 혼동 서술 |
| 보안 통제의 자동화 패러다임 (Security as Code) | 파이프라인 내 퀄리티 게이트(Quality Gate) 자동 차단 메커니즘 | 사람이 보안 툴을 수동으로 돌린다고 적는 레거시 시각 맹점 |

> 요약: 데브옵스(DevOps)가 브레이크 없이 시속 300km로 달리는 페라리를 만들었다면, 데브섹옵스(DevSecOps)는 그 페라리가 벽에 부딪히기 1초 전에 기계가 강제로 핸들을 꺾어버리는 첨단 자율주행 방어 시스템(파이프라인)이다.

## Ⅰ. 개요 및 필요성

- 정의: 소프트웨어 개발 및 배포 전 주기(SDLC)에 보안 테스트, 취약점 스캐닝, 규정 준수 검사를 CI/CD 파이프라인 툴체인(Toolchain) 안에 코드로 내재화(Built-in)하는 방법론
- 배경: 기존 워터폴(Waterfall) 시대의 '배포 직전 보안 검열(Pen-test)' 방식은 일 10회 배포하는 애자일 환경에서 극심한 병목을 유발했고, 오픈소스 무단 도용(Log4j) 공격을 방어 불능 상태로 만듦
- 필요성: 보안 결함을 프로덕션(운영) 도달 전에 파이프라인 단에서 차단(Fail-Fast)하여 결함 수정 비용(Cost of Defect)을 최소화하는 **'시프트 레프트(Shift-Left)'**를 달성하기 위함

## Ⅱ. 시프트 레프트(Shift-Left) 파이프라인 보안 융합 도식

과거엔 운영(오른쪽)에서 터지던 보안 폭탄을, 이제는 젠킨스(왼쪽)가 대신 맞고 장렬히 전사(Build Failed)한다.

```text
[ DevSecOps CI/CD 파이프라인: 단계별 자동화 스캐닝 블로킹(Blocking) 도식 ]

(좌측: Shift-Left 👈)                                                  (우측: 운영/모니터링)
  [ 1. Code / Commit ]  ---> [ 2. Build (CI) ]  ---> [ 3. Test/Deploy ]  ---> [ 4. Operate (Ops) ]
         |                          |                        |                       |
[ IDE Linter 🚨 ]          [ SAST / SCA 🚨 ]          [ DAST / IAST 🚨 ]       [ RASP / SIEM 🚨 ]
(비번 하드코딩 즉시 차단)    (코드 문법 분석 및       (실제 컨테이너 띄워놓고    (실서버 동작 중 메모리 변조
 Git Pre-commit Hook      오픈소스 취약점 스캔.       모의 해킹/SQL 인젝션    및 비정상 행위 실시간 차단)
                          점수 미달 시 빌드 킬)       공격. 뚫리면 배포 중단)
```

| 파이프라인 구간 | 핵심 보안 스캐닝 기법 (엔지니어링 메커니즘) | 방어 및 차단(Block) 효과 |
|:---|:---|:---|
| **Build 구간** <br> (화이트박스) | **SAST (정적 애플리케이션 보안 테스트)**: 소스코드(Text)를 컴파일(Build)할 때 실행하지 않고 문법 자체의 취약점(버퍼 오버플로 등)을 스캔 <br> **SCA (소프트웨어 구성 분석)**: Maven/npm의 서드파티 오픈소스(Log4j) 버전 라이선스 취약점 대조 | 런타임(Runtime) 환경 세팅 전 극초기에 XSS 등 태생적 버그 원천 봉쇄. **Jenkins 퀄리티 게이트 연동 시 즉시 빌드 실패(Red) 처리** |
| **Test 구간** <br> (블랙박스) | **DAST (동적 애플리케이션 보안 테스트)**: 코드를 모름. Staging 서버에 앱을 띄워두고 외부 해커처럼 무작위 XSS, 인젝션 페이로드를 쏴서 방어막 검증 | 정적 분석(SAST)이 잡지 못하는 프레임워크 설정 오류나 실제 인증(Auth) 우회 홀(Hole) 색출 |
| **Operate 구간** <br> (런타임 방어) | **RASP (런타임 애플리케이션 자가 방어)**: 서버(JVM 등) 메모리 안쪽에 기생하며 동작. 외부 WAF(방화벽)를 뚫고 들어온 공격이 앱 내부 메모리를 변조하려 할 때 즉각 세션 킬(Kill) | 외부 네트워크 단이 아닌, 가장 깊숙한 애플리케이션 심장부(Kernel/Runtime)에서의 제로데이 공격 방어 |

> 요약: 주니어 개발자가 Git에 덜컥 DB 비밀번호를 푸시(Push)했다. 옛날엔 보안팀이 다음 달 정기 점검 때 발견하고 사유서를 썼다. DevSecOps 환경에서는 엔터 치자마자 1초 만에 `Git Hook` 봇이 욕을 하며 업로드를 튕겨낸다. 이것이 자동화의 힘이다.

## Ⅲ. 극복해야 할 시스템적 리스크 (오탐지와 파이프라인 병목)

파이프라인에 검문소(보안 스캐너)를 너무 많이 설치하면, 고속도로(CI/CD)가 마비되어 데브옵스 자체가 붕괴한다.

| 리스크 요인 | 발생 시나리오 및 시스템 붕괴 원인 (안티패턴) | 아키텍처 대응 방안 (실무 튜닝) |
|:---|:---|:---|
| **과도한 오탐(False Positive) 병목** | SAST 툴이 무려 10,000개의 '위험 의심' 경고를 띄우며 파이프라인 빌드를 전부 멈춰 세움(Block). 99%가 가짜(오탐)였고 개발자들은 툴을 꺼버림(Bypass) | **Critical Only 강제 및 허용(Exception) 목록 관리**: 도입 초기에는 `Block` 임계치를 최상위(Critical) 레벨 5개에만 적용하여 파이프라인 마비를 막고, 지속적 튜닝으로 신뢰도를 높이는 유연한 퀄리티 게이트(Quality Gate) 조율 |
| **보안 병목으로 인한 CI 지연** | DAST(동적 스캔)는 실서버를 띄우고 해킹을 시도하므로 무려 3시간이 소요됨. 10분 만에 배포를 끝내야 하는 애자일 파이프라인과 시간(Time)의 정면충돌 폭발 | **Out-of-Band (비동기 병렬) 스캐닝 튜닝**: 가벼운 SAST/SCA(1분 컷)는 In-band(파이프라인 직결 블로킹)로 메인에 걸고, 무거운 DAST는 별도의 야간(Nightly) 배치 파이프라인으로 찢어서(Out-of-band) 비동기 실행 |

> 요약: 보안 검사를 한다고 배포가 10분에서 3시간으로 늘어나면, 그건 DevSecOps가 아니라 끔찍한 레거시의 부활일 뿐이다. 핵심은 "개발 속도를 1분 1초도 늦추지 않는 보안 자동화"다.

## Ⅳ. 클라우드 인프라 확장: IaC(인프라 코드화) 통제 융합

개발자의 소스코드뿐만 아니라, AWS 서버를 띄우는 테라폼(Terraform) 코드도 보안 검열 대상이다.

| 융합 패러다임 | 물리적 파이프라인 제어 메커니즘 | 해결되는 인프라 운영 한계 |
|:---|:---|:---|
| **Security as Code** <br> (보안의 코드화) | **인프라 설정 보안(IaC Scanning)**: Terraform이나 K8s YAML 파일에 `ssh_port = 22 open(0.0.0.0/0)` 같은 치명적 멍청한 설정이 있는지 배포 전에 `Checkov`, `tfsec` 봇이 텍스트로 스캔하여 사살 | 과거 해커들이 클라우드 방화벽(SG) 열린 틈을 타 서버 전체를 털어먹던 리스크를, 클라우드 자원을 **생성하기도 전(코드 상태)에 원천 차단하는 마법** 완성 |

> 요약: 클라우드 시대 해킹의 99%는 해커가 천재라서가 아니라, 개발자가 S3 스토리지를 '전체 공개(Public)'로 열어두는 멍청한 실수(Misconfiguration) 때문에 일어난다. DevSecOps는 인간의 이 멍청함을 기계가 대신 스캔하게 만드는 최강의 방패다.

## Ⅴ. 실무 적용 방안 및 결론

**적용 방안 3개:**
1. [SonarQube(SAST) + Dependency-Check(SCA) CI 블로킹 통합] Jenkins 빌드 파이프라인의 핵심 `Test Stage`에 정적 코드 분석 툴을 강제 결합하여, JVN(Java) 코드 컨벤션 위반 및 CVE 취약점이 랭크된 낡은 외부 라이브러리 검출 시 즉각 젠킨스 빌드 상태를 `Failed`로 꺾어버려 실서버 배포 100% 원천 차단
2. [Secret Management(볼트)를 통한 인증 정보 하드코딩 타파] 소스코드나 설정(YAML) 파일 내부에 API 토큰, DB 패스워드를 박아넣어 Git에 털리는 사고를 막기 위해, HashiCorp Vault와 K8s External Secrets를 연동. 코드는 `${DB_PASS}` 변수만 가지고 있고 런타임에 메모리에서만 Vault를 찔러 패스워드를 1회성 주입받는 철통 아키텍처
3. [Trivy 컨테이너 이미지 취약점 스캐닝 및 OPA (정책 강제화)] 도커(Docker) 빌드가 끝난 컨테이너 이미지를 AWS ECR(저장소)로 푸시하기 직전에 Trivy 스캐너가 컨테이너 OS 내부 취약점(CVE)을 스캔하고, OPA(Open Policy Agent)가 "취약점 점수 90점 이상 컨테이너는 절대 K8s 클러스터 내 구동 불가"라는 선언적 룰을 실시간 집행

**결론:**
- 기술사 판단: DevSecOps는 개발, 운영, 보안이라는 세 개의 거대한 사일로(Silo)를 자동화된 파이프라인(Code)이라는 용광로에 녹여낸 아키텍처의 완전체다. '시프트 레프트(Shift-Left)' 철학을 통해 보안 통제권을 보안팀의 엑셀에서 기계(파이프라인)의 영역으로 이관함으로써, 보안과 배포 속도는 상충한다는 수십 년의 소프트웨어 공학 딜레마를 완벽히 종식시킨다.
- 향후 방향: 최근 대규모 MSA/클라우드 환경에서는 단순히 코드 스캐닝을 넘어, GitOps(선언적 배포) 환경 자체를 무결점으로 방어하기 위한 서플라이 체인(Supply Chain) 보안 강화와 SBOM(소프트웨어 자재명세서) 추출 자동화가 파이프라인의 필수 규제 요건(Compliance)으로 자리 잡고 있다.
