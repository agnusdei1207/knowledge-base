## 미리 알고가기

- DevSecOps는 보안을 개발과 배포 흐름 안에 통합하는 방식임
- SAST는 코드를 실행하지 않고 소스 수준에서 취약 패턴을 찾는 정적 분석임
- SCA는 오픈소스 의존성과 알려진 취약점을 점검하는 분석임

## Ⅰ. 개요

- **정의/개념**: DevSecOps는 개발과 운영 자동화 흐름에 보안 점검과 정책 집행과 취약점 대응을 내장해 보안을 별도 후행 단계가 아니라 지속 전달 과정의 일부로 만드는 실천 체계임.
- **배경/필요성**: 배포 속도가 빨라질수록 출시 직전이나 운영 단계에서만 보안을 점검하면 취약점 수정 비용이 커지고 릴리스 지연이 생기므로, 초기부터 자동화된 보안 통제가 필요함.

## Ⅱ. 특징

- 보안 검사를 개발 초반과 파이프라인 단계에 분산 배치함
- 정책 위반을 자동 차단해 배포 기준을 일관되게 유지함
- 경고가 많고 느린 검사만 늘면 개발자가 우회하려는 유인이 커짐
- 도구 수보다 우선순위 기준과 처리 책임 모델이 더 중요함

## Ⅲ. 종류 및 비교

| 구분 | 후행 보안 점검 | DevSecOps |
|:---|:---|:---|
| 검사 시점 | 개발 후반이나 배포 직전에 집중됨 | 개발부터 운영까지 흐름 전체에 분산됨 |
| 구조상 장점 | 초기 도입이 단순하고 기존 절차를 유지하기 쉬움 | 수정 비용과 릴리스 지연을 줄이기 좋음 |
| 구조상 한계 | 늦게 발견돼 수정 범위와 비용이 커짐 | 정책과 도구와 운영 책임을 함께 설계해야 함 |
| 적합한 환경 | 저빈도 배포와 느린 릴리스 조직에 맞음 | 빠른 배포와 잦은 변경이 있는 조직에 맞음 |

> 요약: DevSecOps의 핵심은 보안 도구를 더 넣는 데 있지 않고 보안 결함을 더 이르게 더 자주 처리하게 만드는 데 있음.

## Ⅳ. 구성요소 및 구조

| 구성요소 | 설명 |
|:---|:---|
| 보안 검사 단계 | SAST와 SCA와 비밀 정보 탐지가 코드와 의존성 위험을 조기에 드러냄 |
| 정책 코드화 | 배포 허용 기준을 코드로 정의해 예외 없는 자동 집행을 가능하게 함 |
| 취약점 분류 | 모든 경고를 같은 수준으로 다루지 않고 위험도와 노출 범위에 따라 우선순위를 정함 |
| 운영 피드백 | 운영 중 발견된 보안 사건을 다시 개발 흐름으로 돌려 반복 취약점을 줄임 |

## Ⅴ. 원리 및 절차 흐름도

```text
+-------------+     +-------------+     +-------------+     +-------------+
| 코드/의존성 검사 | --> | 정책 판정      | --> | 배포/운영 모니터링 | --> | 취약점 개선    |
+-------------+     +-------------+     +-------------+     +-------------+
```

1. **코드와 의존성 검사**: 정적 분석과 라이브러리 검사를 수행함
2. **정책 판정**: 위험도와 정책 기준에 따라 통과 여부를 결정함
3. **배포 및 운영 모니터링**: 배포 후 런타임 보안 신호를 관찰함
4. **취약점 개선**: 결과를 수정 작업과 기준 보강으로 연결함

## Ⅵ. 실무 적용 및 유의점

1. 금융과 공공 서비스처럼 보안 기준이 엄격한 조직에서는 DevSecOps가 필수지만 경고가 너무 많으면 개발자가 우회하므로 규칙 튜닝과 위험도 분류를 함께 운영하고 오탐 비율과 우회 배포 비율로 확인함
2. 오픈소스 의존성이 많은 플랫폼에서는 스캔 결과를 발견만 하고 쌓아 두면 효과가 없으므로 취약점 수정 기한과 운영 보안 사건 연계를 함께 두고 취약점 수정 리드타임과 반복 취약점 건수로 확인함

## Ⅶ. 결론

DevSecOps는 빠른 배포 흐름을 늦추지 않으면서 보안 결함을 초기에 통제하려는 조직에서 가장 실효성이 큰 방식임.
