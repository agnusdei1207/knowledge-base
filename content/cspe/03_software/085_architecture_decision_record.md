## 핵심 인사이트 (3줄 요약)
- **ADR(Architecture Decision Record)**: 소프트웨어 프로젝트를 진행하며 내린 중요한 아키텍처적 의사결정(예: "왜 MySQL 대신 MongoDB를 선택했는가?")의 **맥락(Context)과 이유**를 짧은 마크다운 문서로 기록하는 실천법.
- 설계는 코드로 남지만, 그 설계를 선택하기 위해 포기해야 했던 '트레이드오프(Trade-off)'와 당시의 상황은 코드로 남지 않아 미래의 유지보수자에게 '기술 부채'로 돌아옴.
- "이전 개발자들 바보 아냐? 왜 이렇게 짰지?"라는 비난을 막고, 아키텍처의 진화 과정을 역사책처럼 추적할 수 있게 해주는 경량화된 문서화 기법임.

## Ⅰ. 개요 및 필요성
- **개요**: 프로젝트의 생명주기 동안 소프트웨어 아키텍처에 중대한 영향을 미친 결정 사항들을 기록한 짧은 텍스트(Markdown) 파일.
- **필요성**: 애자일 환경에서는 "작동하는 소프트웨어가 포괄적인 문서보다 중요하다"고 하여 문서를 안 쓰는 경향이 생김. 하지만 2년 뒤 새로 입사한 시니어가 "이 부분은 RDB가 맞는데 왜 NoSQL을 썼지?" 하고 다 뜯어고치려다 당시의 제약사항(트래픽 폭주로 인한 임시 조치)에 걸려 시스템이 박살 나는 현상이 발생함. '결정의 이유'를 기록할 가벼운 도구가 필요해짐.
---
## Ⅱ. 아키텍처 및 핵심 원리
- **ADR 문서의 핵심 구성 요소 (Michael Nygard 템플릿)**:
  1. **Title (제목)**: 결정 사항을 명확히 요약 (예: ADR-005: 검색 엔진으로 ElasticSearch 채택).
  2. **Status (상태)**: 제안됨(Proposed), 승인됨(Accepted), 거절됨(Rejected), 폐기됨(Superseded).
  3. **Context (맥락)**: 이 결정을 내려야만 했던 당시의 기술적/비즈니스적 배경 (예: "기존 DB 쿼리로는 1초 내 검색이 불가능해짐").
  4. **Decision (결정)**: 채택한 구체적인 기술이나 패턴 (예: "ElasticSearch 클러스터를 구축한다").
  5. **Consequences (결과/영향)**: 이 결정으로 인해 좋아지는 점(Positive)과 감수해야 할 나쁜 점(Negative/Trade-off) (예: "검색은 빨라지나 인프라 관리 비용이 매월 100만 원 증가함").

```text
[ ADR 생명주기와 코드 저장소 통합 ]

 [ 신규 기술 도입 토론 ] ➡️ [ ADR 마크다운 파일 작성 ] ➡️ [ Git PR (Pull Request) 리뷰 ]
 (개발팀 회의)                (docs/adr/001-use-redis.md)   (팀원들의 승인 / Accepted)
                                                                 ⬇️ (1년 뒤)
 [ 아키텍처 변경 필요 ]  ⬅️ [ 과거 ADR 문서 읽기 ] ⬅️ [ 새로운 상태로 변경: Superseded ]
 (Redis를 Kafka로 교체)     (아, 그 당시엔 이런 이유였군!)   (docs/adr/002-use-kafka.md 작성)
```

## Ⅲ. 비교 및 연결
| 구분 | 전통적 아키텍처 설계서 (SAD) | 아키텍처 결정 기록 (ADR) |
|---|---|---|
| **문서 형태** | 수백 페이지의 Word, PPT (무거움) | 1~2페이지의 마크다운(Markdown) 파일 |
| **저장 위치** | 사내 위키(Confluence)나 문서 저장소 | **소스코드 저장소(Git)에 코드와 함께 저장** |
| **업데이트 빈도**| 배포 시 한 번 작성되고 방치됨 (죽은 문서) | 매 결정마다 지속해서 쌓임 (살아있는 문서) |
| **포커스** | 시스템 구조 전체의 '결과물' 묘사 | 단일 결정의 '배경과 트레이드오프' 묘사 |

## Ⅳ. 실무 적용 및 기술사 판단
- **Git 중심의 문서화 (Docs-as-Code)**: ADR의 가장 큰 강점은 Git 저장소의 `docs/adr/` 디렉토리에 소스코드와 함께 존재한다는 것임. 코드가 수정될 때 문서(ADR)도 함께 PR을 올려 리뷰받게 되므로, 문서와 코드의 버전이 100% 일치하게 되어 문서의 부패(Rotten)를 방지함.
- **감정의 배제**: ADR의 Context 란에 "CTO가 무조건 쓰라고 지시해서 어쩔 수 없이 씀"이라고 적으면 안 됨. "조직의 기술 스택 통일화 전략에 맞춤"과 같이 객관적이고 기술적인 언어로 승화시켜 기록하는 것이 프로페셔널한 아키텍트의 자세임.
---
## Ⅴ. 기대효과 및 결론
- "코드만으로는 절대 알 수 없는 설계자의 의도(Why)"를 타임캡슐처럼 보존하여, 팀의 온보딩(Onboarding) 속도를 높이고 잘못된 아키텍처 번복을 막아줌.
- 거창한 아키텍처 문서화에 질려버린 현대 애자일/MSA 조직에서 채택할 수 있는 가장 가성비 높고 실용적인 문서화 표준(De facto)임.

### 👶 어린이를 위한 3줄 비유 설명
1. 아빠가 갑자기 작은 차를 팔고 커다란 캠핑카를 샀어요. 10년 뒤에 내가 보면 "왜 저렇게 기름 많이 먹는 차를 샀지?" 궁금하겠죠.
2. ADR은 아빠가 차 트렁크에 쪽지를 남겨두는 거예요. "그때 너희들이 캠핑을 너무 가고 싶어 해서, 기름값(단점)을 감수하고 샀단다!"
3. 이 쪽지를 읽으면 "아하, 아빠가 바보여서 산 게 아니라 다 깊은 이유가 있었구나!" 하고 완벽하게 이해할 수 있답니다!
