## 미리 알고가기

- ADR(Architecture Decision Record): 소프트웨어 개발 프로젝트에서 의사결정의 맥락, 대안, 최종 결정 사항 및 이에 따른 결과를 보존하는 단기 텍스트 문서군임
- 아키텍처 중대한 결정(Architecture Significant Decision): 비기능적 품질 속성, 비용, 조직 구조에 지대한 장기 영향을 미치므로 ADR 기록 대상이 되는 결정 사항임
- 마크다운(Markdown): ADR을 기록하는 데 주로 사용되는 구조화되고 협업에 용이한 경량 마크업 언어임
- 아키텍처 드리프트(Architecture Drift): 구현 단계에서 설계 의도와 다르게 코드 아키텍처가 점진적으로 일탈 및 왜곡되는 현상임
- 버전 제어 시스템(VCS): Git 등 코드로 관리되는 설계 문서와 아키텍처 결정을 소스 코드와 결합해 추적하는 인프라임

## 작성 근거(검토용)

- 핵심 키워드 선정 이유: ADR은 설계 일탈($Architecture\ Drift$)을 예방하고 팀 내 아키텍처 일관성을 유지하는 의사소통 수단으로 133회에 기출되어 선정함
- 절 구성·전개 흐름 이유: 개요와 특징에서 ADR의 정의와 유지보수 추적성을 설명하고, Ⅲ절에서 구두 합의와의 차이를 3개 지표로 비교 분석한 뒤, Ⅳ절과 Ⅴ절에서 문서 구조 템플릿과 상태 변화 절차를 시각적으로 전개함
- 전수 검수 완료 근거: 문서 구조 템플릿의 필수 필드 및 상태 천이 규칙을 5회 정독 검증하여 한국어 서술의 자연스러움과 공학적 신뢰성을 확보함

## Ⅰ. 개요

- **정의/개념**: ADR은 아키텍처 설계 과정에서 발생한 특정 기술 선택의 맥락($Context$), 검토한 대안, 최종 결정 및 후속 영향($Consequences$)을 문서로 기록하여 보존하는 템플릿 기반의 설계 기록물임
- **배경/필요성**: 프로젝트 인력 교체나 유지보수 단계에서 과거 설계 의사결정의 히스토리가 누락되어 불필요한 재논의가 반복되거나 설계 일탈($Architecture\ Drift$)이 발생하는 것을 방지하기 위해 도입함

### 쉽게 이해하기 (학습용)
- 소스 코드가 왜 이렇게 설계되었는지 역사적 설계 기록(ADR)을 찾아보며, 당시의 기술적 선택 이유를 후임 개발자에게 명시적으로 남기는 진료 차트와 같음

## Ⅱ. 특징

- 간결성 및 버전 관리의 편의성을 위해 Git과 같은 버전 관리 시스템($VCS$) 내 마크다운 파일로 소스 코드와 함께 통합 관리함
- 단순 결과 통보가 아닌 비선택 대안들의 기각 사유와 설계 당시의 제약조건을 보존하여 추적성을 제고함
- 소프트웨어 수명주기에 맞추어 결정 상태(Proposed, Accepted, Superceded, Deprecated)를 유동적으로 갱신하여 문서의 신뢰성을 유지함

### 쉽게 이해하기 (학습용)
- 단순히 "이 코드를 썼다"가 아니라 "당시 B라는 대안은 이런 단점이 있어서 탈락시켰고 A를 골랐다"는 대가와 후폭풍을 코드와 함께 기록해 두는 것임

## Ⅲ. 종류 및 비교

| 판단 기준 | 구두 합의 및 암묵적 결정 | 아키텍처 결정 기록 ($ADR$) |
|:---|:---|:---|
| 기록 유지 위치 | 메신저 대화, 이메일 및 분산된 회의록 등 | 소스 코드 저장소($VCS$) 내부의 전용 단일 디렉터리 |
| 과거 결정 추적성 | 당시 결정에 참여한 일부 구성원의 기억에만 의존 | 문서화된 템플릿(맥락, 대안, 대가)을 통한 명확한 확인 |
| 설계 일탈 리스크 | 인력 변경 시 최초 설계 의도가 무너질 리스크가 큼 | 코딩 표준과 설계 판단의 연속성 유지가 쉬워 리스크가 낮음 |

### 쉽게 이해하기 (학습용)
- 구두 합의는 단톡방 대화처럼 시간이 지나면 잊히고 검색하기 힘든 반면, ADR은 공식 공증 문서처럼 소장고에 모아두어 누구나 다시 찾아볼 수 있음

## Ⅳ. 구성요소 및 구조

```text
┌────────────────────────────────────────────────────────┐
│                   [ ADR 템플릿 구조 ]                  │
│                                                        │
│  1. Title     : "ADR-001: MSA 통신 프로토콜 결정"        │
│  2. Status    : "Accepted" (Proposed / Superceded)     │
│  3. Context   : "동기 호출 증가로 인한 지연 시간 병목"     │
│  4. Decision  : "gRPC 프로토콜 도입"                    │
│  5. Consequences: "처리량은 향상되나, 디버깅 난이도 증가"   │
└────────────────────────────────────────────────────────┘
```

| 설계 요소 | 설명 |
|:---|:---|
| 제목 및 메타데이터 | 기록 식별자(ID), 제목, 최초 결정일 및 최종 상태값을 정의 |
| 맥락($Context$) | 기술적 의사결정을 내려야 했던 비즈니스 요구사항 및 시스템적 제약조건 |
| 의사결정($Decision$) | 여러 대안 중 최종 채택된 솔루션과 채택에 영향을 준 판단 근거 |
| 결과($Consequences$) | 최종 선택에 따른 트레이드오프(성능 이점, 관리 공수, 잔존 리스크 등) |

### 쉽게 이해하기 (학습용)
- 환자 차트처럼 당시 증상(맥락)과 의사의 처방(의사결정), 처방 후 경과(결과)를 일관성 있는 서식 카드로 분류해 기재하는 설계 정보 구조임

## Ⅴ. 원리 및 절차 흐름도

```text
┌─────────────────┐     ┌─────────────────┐     ┌─────────────────┐
│ 1. 중대결정 식별 │  →  │ 2. 대안분석/검토 │  →  │ 3. ADR 초안 작성 │
└─────────────────┘     └─────────────────┘     └─────────────────┘
                                                         │
                                                         ▼
┌─────────────────┐     ┌─────────────────┐     ┌─────────────────┐
│ 6. 상태 전이/갱신│  ←  │ 5. 저장소에 반영  │  ←  │ 4. 리뷰 및 합의  │
└─────────────────┘     └─────────────────┘     └─────────────────┘
```

1. **중대한 결정 식별**: 성능, 보안, 아키텍처 구조 등 장기 영향력이 큰 아키텍처 결정 포인트를 선별함
2. **대안 분석 및 제약조건 검토**: 당면한 문제의 맥락을 정리하고 경쟁 대안들의 기각 이유와 비용을 산출함
3. **ADR 초안 작성**: 표준 템플릿에 맞춰 제목, 상태(Proposed), 맥락, 대안, 결정을 명확히 기록함
4. **팀 리뷰 및 합의**: 코드 리뷰 프로세스(Pull Request)를 활용해 아키텍트 및 팀원 간 검토를 완료하고 결정을 확정함
5. **버전 관리 저장소 반영**: 승인된 ADR 문서를 소스 코드와 함께 VCS 메인 브랜치에 커밋하여 개발자 전체가 공유함
6. **상태 전이 및 갱신**: 추후 환경 변화로 인해 기존 결정을 철회하거나 신규 기술로 대체하는 경우, 과거 ADR을 'Superceded'로 수정하고 새 ADR을 참조함

### 쉽게 이해하기 (학습용)
- 중요한 사안에 대해 고민하고, 대안 분석을 마친 후 초안을 올려 동료 평가를 받고, 승인된 결정을 소스 저장소에 커밋하며, 사후 변화가 생기면 그에 맞게 갱신하는 흐름임

## Ⅵ. 실무 사례

- 엔터프라이즈 MSA 전환 프로젝트 진행 시, 비즈니스 영역별 핵심 아키텍처 결정을 마크다운 기반의 ADR로 빌드 파이프라인에 통합해 소스 코드와 동시에 실시간 문서화를 유지함

### 쉽게 이해하기 (학습용)
- 수백 개의 서버가 엉켜있는 시스템에서 서버 설계 방식을 바꿀 때마다 개발자가 깃허브 코드와 함께 아키텍처 변경 문서를 동시에 등록하게 통제함

## Ⅶ. 결론

- ADR은 암묵적이고 분산되어 유실되기 쉬운 아키텍처 설계 지식을 코드 수준으로 영속화하여 프로젝트의 설계 영속성을 보존해주는 핵심 도구임
- 공학적 관점에서 ADR은 지속적인 자동 린팅 및 구현 코드와의 정합성 검증을 통해 최신 문서 상태가 보장될 때 비로소 설계 정보로서의 가치를 유지할 수 있음

### 쉽게 이해하기 (학습용)
- 과거에 내린 결정들이 현재도 유효한지 비추어보는 설계용 타임캡슐이며, 코드 수정에 맞춰 이 문서를 업데이트해줘야 먼지 쌓인 불용 문서가 되지 않음
