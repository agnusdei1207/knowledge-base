# 📖 【암기용】 개념 완전 이해

> 목적: ADR을 아키텍처 의사결정을 기록·추적하는 경량 문서 형식으로 완전히 이해하게 만든다. 시험 답안 양식이 아니라, 이해를 위한 설명이다.

## 한눈에
- **개요**: ADR(Architecture Decision Record)은 시스템의 **아키텍처 의사결정**을 배경(Context)·선택(Decision)·상태(Status)·결과(Consequence)와 함께 짧게 남기는 **경량 결정 기록 문서**다.
- **왜 필요한가**: 시간이 지나면 "왜 Kafka를 골랐는지, 왜 MSA로 갔는지"에 대한 기억이 팀원 교체와 함께 사라지고, 같은 논쟁이 반복되거나 근거 없이 뒤집힌다. ADR은 그 판단 근거를 코드처럼 저장소에 버전관리한다.
- **핵심 직관**: 회의록이 "무슨 얘기를 했나"를 남긴다면, ADR은 건축 인허가 서류처럼 "왜 이 구조로 짓기로 했고, 나중에 바뀌면 무엇을 근거로 바뀌었는지"를 남긴다.

## 핵심 용어 정리 (내부에 등장하는 것들)

| 용어 | 의미 | 비유 |
|:---|:---|:---|
| ADR | 의사결정 하나를 기록하는 경량 문서 형식(이 개념의 상위 키워드) | 판례 하나를 기록한 판결문 |
| Context | 이 결정이 필요했던 문제·제약·배경 | 사건의 경위 |
| Decision | 실제로 선택한 안(과 배제한 대안) | 판결 주문 |
| Status | 결정의 생명주기 상태(Proposed·Accepted·Deprecated·Superseded) | 판결의 확정·파기 여부 |
| Consequence | 이 결정으로 생기는 긍정적/부정적 영향 | 판결의 후속 효과 |
| Superseded | 새 ADR이 이전 ADR을 대체함(이전 문서는 지우지 않고 링크로 연결) | 판례 변경(이전 판례는 남기고 새 판례로 갱신) |
| ASD(Architecturally Significant Decision) | ADR로 남길 가치가 있는, 되돌리기 어렵고 영향이 큰 결정 | 대법원까지 갈 만한 중대 사건만 판례로 남김 |

## 깊이 이해

### 왜 ADR이 필요했나 (배경)
- 2011년 Michael Nygard가 제안한 형식이다. 그전까지 아키텍처 결정은 대형 설계문서(SAD, Software Architecture Document)에 담겼는데, 이런 문서는 너무 무거워 갱신이 안 되고 결국 현실과 어긋난 "죽은 문서"가 되는 문제가 있었다. ADR은 "결정 하나 = 문서 하나"로 쪼개, 가볍게 쓰고 저장소에 코드와 함께 버전관리하도록 설계됐다.

### 어떤 결정을 ADR로 남기나 — 판별 원리
- 모든 결정을 다 기록하지 않는다. 기준은 "되돌리기 어렵고(reversal cost가 높고) 시스템 전반에 영향을 주는가"다. 예를 들어 "메시지 브로커를 Kafka로 할지 RabbitMQ로 할지"는 나중에 바꾸려면 데이터 파이프라인 전체를 다시 설계해야 하므로 ADR감이지만, "변수명 컨벤션"은 되돌리기 쉬우므로 ADR로 남기지 않는다.

### 템플릿 구조와 워크드 예제
- 표준 구조는 번호+제목, Status, Context, Decision, Consequences(선택적으로 Alternatives Considered)다.
- 예: "ADR-012: 메시지 브로커로 Kafka 채택. **Context**: 초당 10만 건 이벤트를 순서 보장하며 처리해야 하는데 기존 RabbitMQ는 파티션 기반 순서 보장이 약함. **Decision**: Kafka를 채택한다(대안이었던 RabbitMQ, Pulsar는 배제). **Status**: Accepted(2026-03-01). **Consequence**: p99 지연 200ms 목표는 달성 가능하나 Kafka 클러스터 운영 인력 2명이 추가로 필요하고, 팀의 러닝커브가 발생한다."

### Status 생명주기와 불변성 원칙
- 상태 흐름: Proposed(제안) → Accepted(승인) → (필요 시) Deprecated(더 이상 권장하지 않음) 또는 Superseded by ADR-0XX(다른 결정으로 대체됨).
- 핵심 원칙은 **불변성**이다. 한번 Accepted된 ADR의 본문은 사후에 고쳐 쓰지 않는다. 결정이 바뀌면 기존 ADR을 수정하는 대신 새 ADR을 작성해 Superseded 관계로 링크한다. 법원이 과거 판결문을 지우지 않고 새 판례로 갱신하는 것과 같은 이유다 — 나중에 "왜 그때는 그렇게 결정했는가"를 추적할 수 있어야 하기 때문이다.

### 흔한 오해와 주의점
- ADR은 장문 설계서를 대체하는 것이 아니라, 설계서 안에서도 "왜 이렇게 했는가"에 해당하는 결정 부분만 따로 경량화한 것이다. 나머지 상세 설계는 여전히 별도 문서나 코드로 관리한다.
- ADR을 써놓고 상태를 갱신하지 않으면(Deprecated 처리 누락) 오히려 "이미 안 쓰는 기술을 여전히 쓰는 것처럼" 오해를 유발하는 문서 부채가 된다. 결정 기록만큼 상태 관리가 중요하다.

## 연결 개념
- Architecture Governance — ADR을 리뷰·승인하는 절차와 표준 준수를 관리하는 상위 체계
- RFC/Design Doc — ADR보다 더 상세하고 무거운 설계 논의 문서(ADR은 그 결론만 경량 기록)
- Traceability — 요구사항-ADR-코드-운영지표를 연결해 결정의 실제 효과를 검증

# 📝 【답안용】 시험 답안 템플릿

> 목적: 시험장에서 25분에 그대로 쓰는 답안 양식. 작성방식(추상표현 금지·수치·도식·문제유형 전환)을 엄격히 지킨다.
> 핵심: ADR 답안은 문서 형식보다 의사결정 추적성, 상태관리, 거버넌스, 변경 영향 분석을 써야 한다.

## 핵심 인사이트 (3줄 요약)

> 1. **본질**: ADR은 아키텍처 결정 관련 Context, Decision, Status, Consequence를 기록해 설계 판단 추적성을 확보하는 경량 문서이다.
> 2. **가치**: 신규 팀원 온보딩, 기술부채 관리, 감사 대응, 변경 영향 분석에서 "왜 이 선택을 했는가"를 재현한다.
> 3. **판단 포인트**: Accepted, Deprecated, Superseded 상태를 관리하고 요구사항·코드·운영 지표와 연결해야 문서 부채가 되지 않는다.

## 출제 의도 및 답안 포인트

| 출제 의도 | 반드시 짚을 핵심 | 감점 회피 포인트 |
|:---|:---|:---|
| 아키텍처 거버넌스 이해 확인 | context, decision, status, consequence | 단순 회의록이나 설계서로 설명하지 않음 |
| 추적성·변경관리 판단 확인 | 요구사항-ADR-코드-운영 지표 연결 | 결정 이후 상태 변경을 누락하지 않음 |
| 실무 적용 역량 확인 | ADR 템플릿, 리뷰 절차, 저장소 관리 | 문서 작성량만 늘리는 방식으로 제시하지 않음 |
> 요약: ADR은 의사결정 이유와 결과를 남겨 아키텍처 변경 비용과 반복 논쟁을 줄이는 거버넌스 장치이다.

## Ⅰ. 개요 및 필요성

- 개요: 아키텍처 결정 기록 문서
- 배경: 대규모 시스템은 기술 선택 이유가 사라지면 같은 논쟁, 무근거 변경, 표준 이탈이 반복되고 신규 구성원이 맥락을 복원하기 어렵다.
- 필요성: ADR은 context, decision, consequence를 짧게 남겨 팀 교체, 감사, 장애 분석, 기술부채 관리 시 판단 근거를 제공한다.

---

## Ⅱ. 구조 및 구성요소

```text
Architecture Issue -> Context/Constraints -> Options
-> Decision -> Status -> Consequence
-> Requirement/Code/Metric Trace -> Governance Review
```

| 구성요소 | 역할 | 산정 포인트 |
|:---|:---|:---|
| Context | 문제·제약·요구사항 설명 | 성능, 비용, 보안, 조직 역량 |
| Decision | 선택안과 배제안 기록 | 대안 2개 이상 비교 |
| Status | 결정 생명주기 관리 | Proposed, Accepted, Deprecated |
| Consequence | 영향과 후속 조치 | 운영비, 장애영향, Lock-in |
> 요약: ADR은 배경, 선택, 상태, 결과를 한 단위로 묶어 의사결정 추적성을 만든다.

---

## Ⅲ. 동작원리 및 흐름도

```text
이슈 등록 -> 대안 비교 -> ADR 초안 작성
-> 아키텍처 리뷰 -> 상태 승인 -> 구현 연결
-> 운영 지표 검증 -> 폐기/대체 ADR 작성
```

| 단계 | 처리 내용 | 검증 기준 |
|:---:|:---|:---|
| 1 | 아키텍처 이슈와 제약 식별 | 요구사항 ID 연결 |
| 2 | 대안 비교와 결정 작성 | 비용·성능·위험 축 3개 이상 |
| 3 | 리뷰와 상태 승인 | 승인자, 일자, 상태 기록 |
| 4 | 코드·IaC·운영 지표 연결 | 링크 누락 0건 |
| 5 | 변경 시 대체 ADR 작성 | Superseded 관계 명시 |
> 요약: ADR은 작성, 승인, 구현 연결, 운영 검증, 대체 기록까지 생명주기로 관리한다.

## Ⅳ. 특징

| 구분 | 일반 회의록 | ADR | 수치·판단 기준 |
|:---|:---|:---|:---|
| 목적 | 논의 내용 보관 | 의사결정 근거 추적 | 결정 단위 1건 1문서 |
| 형식 | 자유 서술 | Context·Decision·Status·Consequence | 1~2쪽 이내 |
| 생명주기 | 작성 후 방치 | Accepted·Deprecated·Superseded | 상태 누락 0건 |
| 검증 | 참석자 기억 | 코드·지표 링크 | 추적 링크 100% |
> 요약: ADR은 짧은 기록을 상태관리와 추적성에 연결할 때 아키텍처 거버넌스 도구가 된다.

## Ⅴ. 심화 비교 및 적용 판단

| 구분 | 기존/대안 | 본 키워드 | 선택 기준 |
|:---|:---|:---|:---|
| 구조 | 대형 설계서 | 경량 결정 기록 | 변경 빈도 높은 제품팀 |
| 비용/규모 | 문서 작성 공수 큼 | 결정당 30~60분 작성 | 월 5건 이상 기술 결정 |
| 운영/위험 | 구두 합의 의존 | 상태와 결과 추적 | 팀 교체·감사·장애 분석 |
| 품질 | 표준 이탈 발견 지연 | 리뷰와 링크 기반 통제 | 아키텍처 원칙 준수율 |
> 요약: ADR은 장문 설계서보다 결정 단위 추적이 필요한 애자일·DevOps 조직에 적합하다.

| 리스크 | 원인 | 대응 방안 | 확인 지표 |
|:---|:---|:---|:---|
| 문서 부채 | 작성 후 미갱신 | 상태 리뷰 분기 1회 | Deprecated 누락 0건 |
| 형식 남용 | 사소한 결정까지 기록 | 영향도 기준 3점 이상만 ADR | ADR 반려율 |
| 추적성 단절 | 코드·요구사항 링크 없음 | PR 템플릿에 ADR 링크 필수 | 링크 누락 0건 |
| 거버넌스 지연 | 승인 절차 과다 | 리스크 등급별 리뷰 SLA | 승인 리드타임 3일 이하 |
> 요약: ADR 운영 리스크는 작성량보다 상태 갱신, 링크, 리뷰 SLA 관리로 통제한다.

| 점검 항목 | 목표 기준 | 측정 방법 |
|:---|:---|:---|
| 추적성 | ADR-PR-요구사항 링크 100% | 저장소 링크 검사 |
| 상태관리 | 상태 누락 0건 | ADR 인벤토리 |
| 리뷰 속도 | 승인 리드타임 3영업일 이하 | 리뷰 로그 |
| 효과 검증 | 결정별 운영 지표 1개 이상 | SLO·비용·장애 지표 |
> 요약: ADR 성과는 문서 수가 아니라 추적 링크, 상태 최신성, 리뷰 리드타임, 운영 지표 연결로 판단한다.

## Ⅵ. 실무 적용 및 결론

**적용 방안 3개:**
1. ADR 템플릿을 Context, Options, Decision, Status, Consequence, Links 6항목으로 표준화하고 저장소에 버전관리함.
2. PR 템플릿에 "관련 ADR" 항목을 추가하고 영향도 3점 이상 변경은 아키텍처 리뷰를 필수화함.
3. 분기별 ADR 인벤토리를 점검해 Deprecated·Superseded 상태와 운영 지표 링크를 갱신함.

**결론 (2줄):**
- 기술사 판단: 의사결정 반복과 기술부채가 큰 조직이면 ADR을 적용하고, 승인 병목은 리스크 등급별 리뷰 SLA로 통제함.
- 향후 방향: ADR은 IDP, Scorecard, SLO와 연결되어 아키텍처 거버넌스 자동화 데이터로 발전함.
