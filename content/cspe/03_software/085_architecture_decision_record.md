# 📖 【암기용】 개념 완전 이해

> 목적: ADR을 아키텍처 의사결정 추적성과 거버넌스 도구로 이해하게 만든다. 시험 답안 양식이 아니라, 이해를 위한 설명이다.

## 한눈에
- **개요**: ADR은 아키텍처 의사결정 배경, 선택, 상태, 결과를 짧게 남기는 기록
- **왜 필요한가**: 시스템은 시간이 지나면 왜 Kafka, PostgreSQL, MSA를 선택했는지 기억이 사라지고 같은 논쟁이 반복된다.
- **핵심 직관**: 회의록이 아니라 건축 허가서처럼 나중에 설계 책임과 변경 근거를 확인하는 문서임.

## 깊이 이해
- **배경·문제의식**: 아키텍처 결정은 성능, 비용, 보안, 조직 역량에 영향을 주지만 구두 합의로 끝나면 변경 시 근거가 사라짐.
- **작동 원리**: Context로 문제와 제약을 쓰고, Decision으로 선택안을 명시하며, Status와 Consequence로 승인 상태와 영향을 추적함.
- **비유**: 의사가 처방 이유와 부작용을 차트에 남겨 다음 진료자가 같은 맥락에서 판단하게 하는 것과 같음.
- **구체 예시**: "ADR-012: 메시징은 Kafka 선택, 상태 Accepted, 결과 p99 200ms 목표와 운영인력 2명 필요"처럼 기록함.
- **흔한 오해·주의점**: ADR은 장문 설계서가 아니라 변경 가능한 의사결정 단위이며, 폐기·대체 상태를 남겨야 지식 부채를 줄임.

## 연결 개념
- Architecture Governance: 결정 승인과 표준 준수 통제
- Traceability: 요구사항·설계·코드·운영 지표 연결
- Golden Path: 표준 선택지를 ADR과 함께 제공

# 📝 【답안용】 시험 답안 템플릿

> 목적: 시험장에서 25분에 그대로 쓰는 답안 양식. 작성방식(추상표현 금지·수치·도식·문제유형 전환)을 엄격히 지킨다.
> 핵심: ADR 답안은 문서 형식보다 의사결정 추적성, 상태관리, 거버넌스, 변경 영향 분석을 써야 한다.

## 핵심 인사이트 (3줄 요약)

> 1. **본질**: ADR은 아키텍처 결정 관련 Context, Decision, Status, Consequence를 기록해 설계 판단 추적성을 확보하는 경량 문서이다.
> 2. **가치**: 신규 팀원 온보딩, 기술부채 관리, 감사 대응, 변경 영향 분석에서 "왜 이 선택을 했는가"를 재현한다.
> 3. **판단 포인트**: Accepted, Deprecated, Superseded 상태를 관리하고 요구사항·코드·운영 지표와 연결해야 문서 부채가 되지 않는다.

## 출제 의도 및 답안 포인트

| 출제 의도 | 반드시 짚을 핵심 | 감점 회피 포인트 |
|:---|:---|:---|
| 아키텍처 거버넌스 이해 확인 | context, decision, status, consequence | 단순 회의록이나 설계서로 설명하지 않음 |
| 추적성·변경관리 판단 확인 | 요구사항-ADR-코드-운영 지표 연결 | 결정 이후 상태 변경을 누락하지 않음 |
| 실무 적용 역량 확인 | ADR 템플릿, 리뷰 절차, 저장소 관리 | 문서 작성량만 늘리는 방식으로 제시하지 않음 |
> 요약: ADR은 의사결정 이유와 결과를 남겨 아키텍처 변경 비용과 반복 논쟁을 줄이는 거버넌스 장치이다.

---

## Ⅰ. 개요 및 필요성

ADR은 아키텍처 의사결정 기록 문서이다.
대규모 시스템은 기술 선택 이유가 사라지면 같은 논쟁, 무근거 변경, 표준 이탈이 반복된다.
ADR은 결정 배경과 결과를 짧게 남겨 팀 교체, 감사, 장애 분석, 기술부채 관리 시 판단 근거를 제공한다.

---

## Ⅱ. 구조 및 구성요소

```text
Architecture Issue -> Context/Constraints -> Options
-> Decision -> Status -> Consequence
-> Requirement/Code/Metric Trace -> Governance Review
```

| 구성요소 | 역할 | 산정 포인트 |
|:---|:---|:---|
| Context | 문제·제약·요구사항 설명 | 성능, 비용, 보안, 조직 역량 |
| Decision | 선택안과 배제안 기록 | 대안 2개 이상 비교 |
| Status | 결정 생명주기 관리 | Proposed, Accepted, Deprecated |
| Consequence | 영향과 후속 조치 | 운영비, 장애영향, Lock-in |
> 요약: ADR은 배경, 선택, 상태, 결과를 한 단위로 묶어 의사결정 추적성을 만든다.

---

## Ⅲ. 동작원리 및 흐름도

```text
이슈 등록 -> 대안 비교 -> ADR 초안 작성
-> 아키텍처 리뷰 -> 상태 승인 -> 구현 연결
-> 운영 지표 검증 -> 폐기/대체 ADR 작성
```

| 단계 | 처리 내용 | 검증 기준 |
|:---:|:---|:---|
| 1 | 아키텍처 이슈와 제약 식별 | 요구사항 ID 연결 |
| 2 | 대안 비교와 결정 작성 | 비용·성능·위험 축 3개 이상 |
| 3 | 리뷰와 상태 승인 | 승인자, 일자, 상태 기록 |
| 4 | 코드·IaC·운영 지표 연결 | 링크 누락 0건 |
| 5 | 변경 시 대체 ADR 작성 | Superseded 관계 명시 |
> 요약: ADR은 작성, 승인, 구현 연결, 운영 검증, 대체 기록까지 생명주기로 관리한다.

---

## Ⅳ. 특징

| 구분 | 일반 회의록 | ADR | 수치·판단 기준 |
|:---|:---|:---|:---|
| 목적 | 논의 내용 보관 | 의사결정 근거 추적 | 결정 단위 1건 1문서 |
| 형식 | 자유 서술 | Context·Decision·Status·Consequence | 1~2쪽 이내 |
| 생명주기 | 작성 후 방치 | Accepted·Deprecated·Superseded | 상태 누락 0건 |
| 검증 | 참석자 기억 | 코드·지표 링크 | 추적 링크 100% |
> 요약: ADR은 짧은 기록을 상태관리와 추적성에 연결할 때 아키텍처 거버넌스 도구가 된다.

## Ⅴ. 심화 비교 및 적용 판단

| 비교 축 | 기존/대안 | 본 키워드 | 선택 기준 |
|:---|:---|:---|:---|
| 구조 | 대형 설계서 | 경량 결정 기록 | 변경 빈도 높은 제품팀 |
| 비용/규모 | 문서 작성 공수 큼 | 결정당 30~60분 작성 | 월 5건 이상 기술 결정 |
| 운영/위험 | 구두 합의 의존 | 상태와 결과 추적 | 팀 교체·감사·장애 분석 |
| 품질 | 표준 이탈 발견 지연 | 리뷰와 링크 기반 통제 | 아키텍처 원칙 준수율 |
> 요약: ADR은 장문 설계서보다 결정 단위 추적이 필요한 애자일·DevOps 조직에 적합하다.

| 리스크 | 원인 | 대응 방안 | 확인 지표 |
|:---|:---|:---|:---|
| 문서 부채 | 작성 후 미갱신 | 상태 리뷰 분기 1회 | Deprecated 누락 0건 |
| 형식 남용 | 사소한 결정까지 기록 | 영향도 기준 3점 이상만 ADR | ADR 반려율 |
| 추적성 단절 | 코드·요구사항 링크 없음 | PR 템플릿에 ADR 링크 필수 | 링크 누락 0건 |
| 거버넌스 지연 | 승인 절차 과다 | 리스크 등급별 리뷰 SLA | 승인 리드타임 3일 이하 |
> 요약: ADR 운영 리스크는 작성량보다 상태 갱신, 링크, 리뷰 SLA 관리로 통제한다.

| 점검 항목 | 목표 기준 | 측정 방법 |
|:---|:---|:---|
| 추적성 | ADR-PR-요구사항 링크 100% | 저장소 링크 검사 |
| 상태관리 | 상태 누락 0건 | ADR 인벤토리 |
| 리뷰 속도 | 승인 리드타임 3영업일 이하 | 리뷰 로그 |
| 효과 검증 | 결정별 운영 지표 1개 이상 | SLO·비용·장애 지표 |
> 요약: ADR 성과는 문서 수가 아니라 추적 링크, 상태 최신성, 리뷰 리드타임, 운영 지표 연결로 판단한다.

---

## Ⅵ. 실무 적용 및 결론

**적용 방안 3개:**
1. ADR 템플릿을 Context, Options, Decision, Status, Consequence, Links 6항목으로 표준화하고 저장소에 버전관리함.
2. PR 템플릿에 "관련 ADR" 항목을 추가하고 영향도 3점 이상 변경은 아키텍처 리뷰를 필수화함.
3. 분기별 ADR 인벤토리를 점검해 Deprecated·Superseded 상태와 운영 지표 링크를 갱신함.

**결론 (2줄):**
- 기술사 판단: 의사결정 반복과 기술부채가 큰 조직이면 ADR을 적용하고, 승인 병목은 리스크 등급별 리뷰 SLA로 통제함.
- 향후 방향: ADR은 IDP, Scorecard, SLO와 연결되어 아키텍처 거버넌스 자동화 데이터로 발전함.
