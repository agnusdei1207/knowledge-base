# 📖 【암기용】 개념 완전 이해

## 한눈에
- **개요**: 프로젝트 진행 중 내린 중요한 소프트웨어 아키텍처 의사결정의 배경, 맥락, 결과를 짧고 표준화된 포맷으로 기록하는 문서
- **왜 필요한가**: 수개월 뒤 "왜 우리가 MySQL 대신 MongoDB를 썼더라?" 혹은 "왜 굳이 Kafka를 붙였지?"라는 질문에 아무도 대답하지 못하는 '맥락 소실'을 막기 위해 등장했다.
- **핵심 직관**: 코드에 남기는 주석이 'How(어떻게 구현했나)'라면, ADR은 아키텍트가 쓴 'Why(왜 이 기술을 선택했나)'의 일기장이다.

## 핵심 용어 정리

| 용어/표기 | 의미 | 비유·예 |
|:---|:---|:---|
| Context (맥락) | 의사결정을 내려야만 했던 당시의 비즈니스적/기술적 상황과 제약조건 | "블랙프라이데이 때 동시접속자가 10배 늘어 DB가 뻗음" |
| Decision (결정) | 논의 끝에 최종적으로 채택한 기술 스택, 디자인 패턴 또는 정책 | "관계형 DB 대신 분산 처리가 쉬운 NoSQL 도입 결정" |
| Consequences (결과) | 그 결정으로 인해 얻게 된 장점(Good)과 짊어져야 할 단점/기술부채(Bad) | "확장성은 좋아졌으나 트랜잭션 복잡도는 우리가 안고 감" |
| Immutable (불변성) | 한번 확정된 ADR 문서는 수정하지 않고, 변경 시 새 ADR로 덮어쓰는 속성 | 법원의 판결문 (뒤집을 땐 새 판결문을 냄) |

## 깊이 이해
- **배경·문제의식**: 애자일 환경에서는 무거운 아키텍처 명세서(UML 수십 장)를 유지보수하기 힘들다. 하지만 문서가 없으면 담당자 퇴사 시 기술 도입의 역사와 타협(Trade-off)의 이유가 증발해, 후임자가 과거의 실수를 반복하거나 멀쩡한 구조를 갈아엎는 비용이 발생한다.
- **작동 원리**: 가벼운 마크다운(Markdown) 파일 형태로 작성되며 소스코드 저장소(Git)에 함께 관리된다. 새로운 기술 스택 도입, 모노리스의 분리, 라이선스 정책 변경 등 중대한 구조적 결정이 있을 때마다 `[Title, Status, Context, Decision, Consequences]` 5가지 항목을 1~2페이지 분량으로 남긴다.
- **비유**: 회의록이 "누가 무슨 말을 했나"라면, ADR은 "그래서 결론이 뭐고, 우리가 포기한 것은 무엇인가"를 요약한 '결전의 증서'다.
- **구체 예시**: `ADR-005.md: 검색 엔진 변경`. 맥락: RDB LIKE 검색이 너무 느림. 결정: ElasticSearch 도입. 결과: 검색 속도 10배 향상(장점), 검색 노드 인프라 유지보수 비용 월 50만 원 추가 발생(단점).
- **흔한 오해·주의점**: 모든 사소한 코드 레벨의 결정(변수명 규칙 등)을 ADR로 적지 않는다. 오직 시스템 구조, 보안, 성능에 지대한 영향을 미치는 '아키텍처 수준'의 결정만 기록한다.

## 연결 개념
- 소프트웨어 아키텍처 평가 (ATAM/CBAM) — ADR에 기록될 대안 선택의 논리적 근거가 되는 평가 기법
- 기술부채 (Technical Debt) — ADR의 'Consequences' 항목에 명시적으로 기록되고 관리되어야 할 부채

# 📝 【답안용】 시험 답안 템플릿

## 핵심 인사이트 (3줄 요약)

> 1. **본질**: 애자일 환경에서 구조적 의사결정의 맥락(Context)과 타협안(Trade-off)을 경량화된 마크다운 형식으로 형상 관리하는 기술 자산화 도구다.
> 2. **가치**: 인력 변동 시 발생하는 '아키텍처 기억 상실증'을 방지하고, 의사결정의 합리성을 검증하여 기술부채의 맹목적 누적을 차단한다.
> 3. **판단 포인트**: 작성 자체가 목적이 되면 안 되며, Git 레포지토리와 결합해 코드 리뷰 시점에 검토되고 지속적 참조가 이루어지는 문화 정착이 필수적이다.

## 출제 의도 및 답안 포인트

| 출제 의도 | 반드시 짚을 핵심 | 감점 회피 포인트 |
|:---|:---|:---|
| 애자일/MSA 환경의 아키텍처 문서화 패러다임 이해 | 무거운 정적 명세서 → 경량(Markdown), 코드와 함께(Git) 관리되는 동적 기록 전환 | 전통적 EA나 ISP 수준의 무거운 문서 관리로 기술 |
| ADR의 핵심 구성요소 인지 | Nygard 템플릿 5요소 (Title, Status, Context, Decision, Consequences) | 단순 회의록이나 버그 리포트 구성요소 나열 |

> 요약: ADR은 무거운 아키텍처 명세서를 대체하여, 결정의 맥락과 트레이드오프(결과)를 Git 기반으로 가볍게 이력 관리하는 문서 체계다.

---

## Ⅰ. 개요 및 필요성

- 개요: 시스템 아키텍처와 관련된 중요 의사결정 사항(배경, 대안, 채택 사유, 결과)을 구조화하여 기록하는 경량 기술 문서임
- 배경: 애자일/DevOps 확산으로 설계 문서가 최신화되지 않고 버려지며, 담당자 교체 시 기술 스택 선정의 근거(Why)가 소실되는 문제 발생함
- 필요성: 아키텍처 변경의 역사적 맥락 보존, 신규 인력의 온보딩 비용 최소화, 명시적 트레이드오프 인식을 통한 기술부채 통제력 확보 필요함

---

## Ⅱ. 구조 및 구성요소

```text
비즈니스 요구/기술 제약 발생 -> [ADR 템플릿 작성] -> Git 레포지토리 커밋 -> 리뷰 및 확정(상태 변경)
                                |
                   (Context -> Decision -> Consequences)
```

| 구성요소 (Nygard 포맷) | 역할 및 내용 | 특이사항 |
|:---|:---|:---|
| Title / Status | 결정 사항 제목 및 현재 상태 (Proposed, Accepted, Deprecated, Superseded) | 고유 번호 부여 (예: ADR-001) |
| Context (맥락) | 의사결정을 촉발한 기술적/비즈니스적 배경 및 당면한 문제점 | "무엇이 이 결정을 강제했는가?" |
| Decision (결정 사항) | 고려한 대안들 중 최종적으로 선택한 아키텍처/기술적 해법 | 구체적이고 단호한 문장 사용 |
| Consequences (결과) | 선택으로 인해 얻은 이득(Positive)과 안게 된 제약/기술부채(Negative) | 장점과 단점(Trade-off) 객관적 명시 |

> 요약: ADR은 고유 번호와 상태를 가지며, 문제 발생 배경(Context), 최종 결정(Decision), 그리고 그 결정이 낳은 명암(Consequences)으로 구성된다.

---

## Ⅲ. 동작원리 및 흐름도

```text
이슈 발생 -> 대안 검토 -> ADR 초안 작성(Proposed) -> 팀 리뷰/합의 -> 확정(Accepted) -> 후속 변경 시 대체(Superseded)
```

- 1단계 [의사결정 트리거]: 프레임워크 변경, MSA 분리, 신규 DB 도입 등 아키텍처에 중대한 영향을 미치는 이슈 발생
- 2단계 [ADR 초안 작성]: 마크다운(Markdown) 포맷으로 소스코드 레포지토리의 `/docs/adr` 디렉토리에 초안(Proposed)을 작성 후 PR 생성
- 3단계 [리뷰 및 상태 확정]: 이해관계자 및 아키텍트 간 코드 리뷰(PR)를 통해 맥락과 결과를 검토 후 Accepted 상태로 머지(Merge)함
- 4단계 [이력 관리]: 문서 내용은 불변(Immutable)으로 유지하며, 훗날 기술 변경 시 기존 문서를 수정하지 않고 새 ADR을 작성해 기존 문서를 Superseded 처리함

> 요약: ADR은 코드와 동일하게 Git PR을 통해 제안되고 리뷰되며, 한 번 승인된 문서는 수정하지 않고 새 문서를 통해 폐기(대체) 상태로 이력 관리된다.

---

## Ⅳ. 특징

- 경량화 및 접근성: 워드나 PDF가 아닌 Plain Text/Markdown 형태이므로 개발자가 IDE 내에서 코딩 중 즉시 열람 및 작성 가능함
- 불변성(Immutability) 유지: 역사적 사료와 같으므로 과거의 바보 같은 결정이라도 삭제/수정하지 않으며, 당시 상황(Context)을 이해하는 용도로 보존함
- 분산 아키텍처 친화적: MSA 환경에서 각 마이크로서비스 저장소마다 독립적인 ADR 폴더를 두어 도메인별 자율적 의사결정을 기록하기 용이함
- 코드와의 동기화: 설계 문서가 별도 위키(Wiki)나 폴더에 방치되어 코드(실제 시스템)와 괴리되는 현상(문서의 부패)을 방지함

## Ⅴ. 심화 비교 및 적용 판단

| 비교 축 | 전통적 아키텍처 명세서 (SAD) | ADR (Architecture Decision Record) | 선택 기준 |
|:---|:---|:---|:---|
| 목적 | 시스템의 종합적 청사진(How) 제공 | 결정의 맥락과 사유(Why) 기록 | 현재 상태파악(SAD) vs 변경의 역사(ADR) |
| 작성/수정 비용 | 높음 (다이어그램, 잦은 형상 파편화) | 매우 낮음 (텍스트 중심, 불변성) | 애자일 스프린트 속도 확보 여부 |
| 관리 위치 | 중앙 문서 관리 시스템 (ECM, Wiki) | 소스코드 형상관리(Git) 내부 저장 | 개발자의 동선과 일치하는가 |

**리스크·대응:**
- [작성 기준 모호성]: 변수명 변경 등 사소한 것까지 ADR을 남겨 피로도 증가 → "기술부채를 발생시키거나 성능/보안에 영향이 있는 경우"로 작성 임계치 명문화
- [단점(Negative) 누락]: 작성자가 자신의 결정을 합리화하려 장점만 기록 → PR 리뷰 시 ATAM 등 트레이드오프 평가 기법을 적용해 보안/성능 측면의 페널티 강제 기입 요구
- [검색 및 가시성 부족]: 파일이 늘어나며 전체 결정 흐름 파악 곤란 → adr-tools 같은 CLI 자동화 도구 도입으로 목차(Index) 자동 생성 및 상태 변이 다이어그램 연동

**도입 후 점검 지표:**
- 작성 밀도: 스프린트당 구조 변경 건 대비 ADR 작성률 90% 이상
- 온보딩 효율성: 신규 개발자의 시스템 구조 파악 리딩 타임 감소율 (설문 및 온보딩 기간 측정)

## Ⅵ. 실무 적용 및 결론

**적용 방안 3개:**
1. GitOps 파이프라인 연동: GitHub/GitLab PR 시 `/docs/adr` 변경 사항이 감지되면 리뷰어 자동 할당 및 슬랙(Slack) 알림을 쏘는 CI/CD 플러그인 구성
2. 기술부채 백로그 연동: ADR의 'Consequences' 항목에 명시된 기술적 약점이나 향후 개선 과제를 즉시 Jira 티켓(Tech Debt Epic)으로 생성하여 잊히지 않게 관리
3. 자동화 도구 기반 템플릿 통일: `adr-tools` CLI(`adr new "Use Redis"`)를 표준 환경에 배포하여 팀 간 포맷 파편화를 방지하고 번호 매기기를 자동화함

**결론 (2줄):**
- 기술사 판단: ADR은 애자일의 약점인 '문서화 부족'을 개발자 친화적으로 메우는 최적의 도구이며, 이는 단순한 서식 작성이 아닌 트레이드오프를 인정하는 성숙한 엔지니어링 문화다.
- 향후 방향: ADR 텍스트 파일들을 LLM(대규모 언어 모델)에 벡터 임베딩(RAG)하여, 신규 개발자가 "이전에 NoSQL 도입 검토한 적 있어?"라고 물으면 챗봇이 즉시 맥락을 찾아주는 AI 아키텍처 비서 형태로 진화할 것이다.
