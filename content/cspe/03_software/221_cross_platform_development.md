## Ⅰ. 개요
- 하나의 코드베이스(One Source)로 iOS와 Android 앱을 동시에 개발하는 방식임
- 네이티브에 근접한 성능과 개발 생산성을 동시에 잡으려는 현대적 모바일 전략임
| 구분 | 내용 | 비유 |
| --- | --- | --- |
| 출제의도 | Flutter(Skia) vs React Native(Bridge), 선언적 UI, 핫 리로드 | 양손잡이용 도구 |

## Ⅱ. 구성요소
- 렌더링 방식 및 브릿지 유무에 따라 Flutter와 React Native로 대변됨
[Flutter: 자체 엔진(Skia) 직접 렌더링]
[React Native: JS Bridge를 통한 네이티브 위젯 호출]
- 구성요소 표
| 구성요소 | 설명 | 비유 |
| --- | --- | --- |
| Flutter | Dart 언어 사용, UI를 직접 그려 일관된 디자인 유지 (Skia 엔진) | 캔버스에 직접 그리는 화가 |
| React Native | JS/React 사용, 네이티브 구성 요소를 매핑하여 성능 확보 | 부품을 주문해서 조립하는 기사 |
| 핫 리로드 | 코드 수정 시 앱 재실행 없이 즉각 결과 확인 (생산성 핵심) | 실시간 미리보기 |
> 요약: 플랫폼별 UI 차이를 최소화하고 개발 속도를 네이티브 대비 2배 이상 향상함

## Ⅲ. 절차
- 단일 코드 기반의 멀티 플랫폼 배포 절차임
[프레임워크 선정] -> [UI/로직 구현] -> [플랫폼 채널 연동] -> [빌드 및 배포]
- 4단계 설명
1) 기술 스택 확정: 개발팀 역량(JS vs Dart)과 디자인 요구에 맞춰 도구 선정함
2) UI 컴포넌트 설계: 양쪽 OS에서 공통으로 보일 선언적 UI 구조를 코딩함
3) 네이티브 모듈 연동: 푸시, 카메라 등 OS 특화 기능은 플랫폼 채널로 연결함
4) 바이너리 빌드: 각 OS에 맞는 패키지(APK, IPA)를 자동화 도구로 생성함
> 요약: 코드 중복을 제거하고 운영 관리 포인트를 단일화함

## Ⅳ. 문제점
- 네이티브 최신 API 반영이 프레임워크 업데이트 속도에 의존적임 (원인: 서드파티 종속)
- 특정 복잡한 그래픽 처리나 하드웨어 제어 시 네이티브보다 성능이 저하됨 (원인: 렌더링 계층)

## Ⅴ. 개선방안
- (단기) 성능 병목 구간은 네이티브 코드를 직접 작성하여 브릿지로 호출함
- (중기) 코드 푸시(Code Push) 기술을 적용하여 스토어 심사 없이 앱 업데이트 수행함
- (장기) 웹과 데스크탑까지 확장 가능한 멀티 플랫폼 에코시스템 구축함

## Ⅵ. 전망
- 기업용 앱 개발의 80% 이상이 크로스 플랫폼 기반으로 전환될 것임
- 향후 AI가 디자인 시안을 보고 Flutter/RN 코드를 자동 생성하는 기술이 필수 CSF가 될 것임
