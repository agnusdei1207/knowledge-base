# 📖 【암기용】 개념 완전 이해

## 한눈에
- **개요**: 소프트웨어 기능점수(FP)를 산정할 때, 요구사항의 상세화 수준에 따라 복잡도를 적용하는 방식(간이법 vs 정통법)
- **왜 필요한가**: 프로젝트 극초기(기획 단계)에는 화면 입력 항목수(DET)나 DB 테이블 컬럼을 정확히 알 수 없어 정밀한 측정이 불가능하다. 이때 예산을 대략이라도 잡기 위해 간이법이 필요하다.
- **핵심 직관**: 집을 지을 때 설계도가 나오기 전에는 "30평 아파트 평균 평당 단가(간이법)"로 예산을 잡고, 상세 설계도가 나오면 "거실 벽지 종류, 타일 개수(정통법)"를 직접 세서 견적을 확정하는 것과 같다.

## 핵심 용어 정리

| 용어/표기 | 의미 | 비유·예 |
|:---|:---|:---|
| 정통법 (Detailed FP) | 데이터 요소(DET), 레코드 요소(RET) 개수를 직접 세어 Low/Avg/High 복잡도를 정확히 판정하는 방식 | 실시설계 도면을 보고 자재 개수를 하나씩 직접 세는 견적 |
| 간이법 (Estimated FP) | 기능 개수만 식별하고, 과거 수많은 프로젝트 통계로 산출된 '평균 복잡도 가중치'를 일괄 곱하는 방식 | 평당 평균 건축비로 대략적인 예산을 산출하는 방식 |
| DET (Data Element Type) | 사용자가 인식할 수 있는 고유한 데이터 필드(속성) | 회원가입 화면의 '이름', '아이디', '비밀번호' 입력 칸 하나하나 |
| RET (Record Element Type) | 하나의 데이터 기능(ILF/EIF) 내에 포함된 서브 데이터 그룹 | '주문' 테이블에 딸린 '주문 상세(품목)' 그룹 |

## 깊이 이해
- **배경·문제의식**: 기능점수(FP)는 객관적이지만, 측정을 위해선 입력 화면의 필드 수(DET)와 DB 테이블 구조(RET, FTR)가 모두 도출되어야 한다. 하지만 예산 확보는 기획 단계에서 해야 하므로, 이 모순을 해결할 통계 기반의 간이 산정법이 공공기관 예산 편성 지침에 도입되었다.
- **작동 원리**: **정통법**은 요구사항 정의 및 설계가 완료되어 모든 DET/RET를 식별할 수 있을 때 IFPUG의 복잡도 매트릭스(Low/Avg/High)를 적용해 산정한다. **간이법**은 기획/발주 단계에서 기능(예: 회원가입, 상품조회) 목록만 식별한 뒤, 국가 통계로 정해진 평균 가중치(예: EI는 4.0점, ILF는 7.5점 등)를 곱해 미조정 기능점수(UFP)를 구한다.
- **비유**: 여행 경비를 짤 때, 간이법은 "일본 3박 4일이면 보통 하루 20만 원 잡아(평균 가중치)"이고, 정통법은 "교통비 500엔, 라멘 1000엔 영수증 다 더하기"다.
- **구체 예시**: 회원가입 기능(EI) 1개 산정 시, 정통법은 입력 항목(DET) 2개면 Low(3점), 16개면 High(6점)로 계산한다. 간이법은 항목 수를 모르므로 무조건 평균인 4.0점을 부여한다.
- **흔한 오해·주의점**: 간이법은 기능점수의 공식 국제 표준(IFPUG) 방식이 아니라, 국내 SW 사업 대가산정 가이드(한국소프트웨어산업협회)에서 예산 편성을 위해 활용하는 실무적 변형이다.

## 연결 개념
- SW 기능점수 FP 측정 (Function Point) — 두 방식의 근간이 되는 규모 산정 원리
- 소프트웨어 대가산정 (SW Cost Estimation) — 간이법으로 예산을 편성하고 정통법으로 대가를 정산하는 체계

# 📝 【답안용】 시험 답안 템플릿

## 핵심 인사이트 (3줄 요약)

> 1. **본질**: SW 사업 단계별 정보 가용성에 맞춰 FP 산정 방식을 단순화(간이법)하거나 정밀화(정통법)한 실무 적용 기법이다.
> 2. **가치**: 사업 초기 기획 단계의 모호한 요구사항에서도 평균 복잡도 가중치를 이용해 신속하게 기준 예산을 편성할 수 있게 해준다.
> 3. **판단 포인트**: 간이법은 평균 통계에 의존하므로 실제 구축 시 시스템 고유의 복잡성을 반영하지 못해 오차가 발생하며, 설계 완료 후 반드시 정통법으로 정산·보정해야 한다.

## 출제 의도 및 답안 포인트

| 출제 의도 | 반드시 짚을 핵심 | 감점 회피 포인트 |
|:---|:---|:---|
| 산정 시점에 따른 방법론 선택 역량 | 기획 단계(간이법)와 설계 단계(정통법)의 적용 시점 구분 | 두 기법의 적용 단계를 혼동하여 기술 |
| 복잡도 산출 방식의 차이점 이해 | 정통법(DET/RET 직접 식별 매트릭스) vs 간이법(평균 복잡도 가중치) | 간이법에 IFPUG 복잡도 매트릭스를 적용한다고 단정 |

> 요약: 간이법은 기획 단계에서 기능별 평균 복잡도를 곱해 산정하고, 정통법은 설계 이후 DET/RET를 직접 식별해 정확한 복잡도를 산정한다.

## Ⅰ. 개요 및 필요성

- 개요: SW 기능점수 산정 시 요구사항의 구체화 수준에 따라 복잡도를 통계적 평균(간이법) 또는 실측 매트릭스(정통법)로 구하는 규모 산정 기법임
- 배경: 프로젝트 예산은 기획 단계에서 확보해야 하나, 해당 시점에는 상세 설계(DET, RET 등)가 없어 IFPUG 표준 방식 적용이 불가능함
- 필요성: 발주 시점의 신속한 예산 편성과 구현 완료 시점의 정확한 대가 지급을 분리하여 SW 사업비 관리의 현실성과 정확성을 동시에 확보함

---

## Ⅱ. 구조 및 구성요소

```text
요구사항 명세 수준 -> [기획/발주 단계: 모호] -> 간이법 (평균 가중치 기반 신속 산정) -> 예산 확보
                 |
                 -> [상세 설계 단계: 명확] -> 정통법 (DET/RET 기반 정밀 산정) -> 대가 확정
```

| 구성요소 | 정통법 (Detailed FP) | 간이법 (Estimated FP) |
|:---|:---|:---|
| 데이터 요소 식별 | DET, RET, FTR 등 세부 속성 100% 식별 | 세부 속성 식별 생략, 기능(단위 프로세스)만 식별 |
| 복잡도 판정 | IFPUG 복잡도 매트릭스 (Low/Avg/High) 적용 | 국내 과거 프로젝트 통계 기반 평균 가중치 적용 |
| 적용 단계 | 상세 설계 완료 시점 ~ 구현 종료 시점 | 정보화 전략 계획(ISP), 예산 편성 및 발주 단계 |

> 요약: 정통법은 설계 기반 실측 복잡도를 사용해 대가를 확정하며, 간이법은 기능 도출 후 평균 가중치를 적용해 초기 예산을 편성한다.

---

## Ⅲ. 동작원리 및 흐름도

```text
[요구사항 분석] -> 기능 유형 식별(ILF/EI 등) -> 정통법/간이법 선택 -> 복잡도 적용 -> 미조정 점수(UFP) 산출
```

- 1단계 [기능 식별]: 사용자 관점에서 제공되는 데이터(ILF, EIF) 및 트랜잭션(EI, EO, EQ) 기능을 도출함
- 2단계 [복잡도 기준 적용]: 정통법은 DET/RET 개수를 세어 L/A/H 판정, 간이법은 기능 유형별 고정 평균치(예: EI=4.0) 일괄 적용함
- 3단계 [미조정 점수 총합]: 식별된 기능 수 × (실측 복잡도 점수 OR 평균 가중치 점수)를 합산하여 UFP 도출함
- 4단계 [보정 계수 적용]: 14가지 일반 시스템 특성 및 공공 가이드 보정 계수(규모, 언어 등)를 반영해 최종 대가 산정함

> 요약: 두 방법 모두 기능(ILF, EI 등)을 식별하는 1단계는 같으나, 2단계에서 복잡도(가중치)를 결정하는 방식에만 차이가 존재함.

---

## Ⅳ. 특징

- 신속성 vs 정확성 트레이드오프: 간이법은 상세 속성(DET) 파악이 불필요해 단기간 산정 가능하나 정확도가 떨어지며, 정통법은 정확하나 분석 공수가 큼
- 통계적 유의성 확보(간이법): 한국소프트웨어산업협회(KOSA)에서 매년 누적된 사업 데이터를 바탕으로 평균 복잡도를 현행화하여 오차율을 줄임
- 국내 공공사업 표준 절차화: 예산 편성 시 간이법 의무 적용 후, 사업 종료 시 정통법 실사 결과를 바탕으로 과업 변경 및 정산 수행함
- 요구사항 변경 추적 제약: 간이법은 세부 필드 기준선이 없어, 프로젝트 중 필드 몇 개가 추가/삭제되는 수준의 변경은 점수에 반영하기 어려움

## Ⅴ. 심화 비교 및 적용 판단

| 비교 축 | 간이법 (Estimated) | 정통법 (Detailed) | 선택 기준 |
|:---|:---|:---|:---|
| 시간/공수 | 매우 적음 (기능 도출만 필요) | 매우 높음 (상세 화면/DB 설계 필수) | 프로젝트 잔여 일정 및 인력 여력 |
| 오차율 수준 | 중간 (통계적 평균치와의 괴리) | 낮음 (실제 스펙과 1:1 매핑) | 요구사항 변동성이 큰 애자일 환경(간이법 유리) |
| 산정 근거 | KOSA SW 대가산정 가이드 | IFPUG 국제 표준 매뉴얼 | 대외 감리 및 글로벌 계약 시 국제 표준 여부 |

**리스크·대응:**
- [간이법 과다/과소 계상]: 실제 업무 난이도가 평균을 크게 벗어날 시 예산 왜곡 → 복잡도가 극단적인 도메인(핵심 코어 뱅킹 등)은 간이법 적용 전 전문가 직관 보정 결합
- [정산 시점 갈등]: 간이법 예산과 정통법 실측 규모 간 20% 이상 차이 발생 시 비용 분쟁 → 계약서에 과업 변경 심의위원회(정산) 근거 및 허용 오차범위 명시
- [기능 쪼개기 꼼수]: 간이법 산정 시 점수를 높이려 1개 기능을 여러 개로 억지 분리 → 업무 프로세스 흐름도(BPM) 기반의 단위 프로세스 식별 기준(End-to-End) 엄격 적용

**도입 후 점검 지표:**
- 산정 공수: 간이법 산정 시 투입 공수 3 M/D 이하 — 신속성 검증
- 예산 정합성: 기획(간이법) 규모 대비 완료(정통법) 규모 편차 15% 이내 — KOSA 가이드라인 참조

## Ⅵ. 실무 적용 및 결론

**적용 방안 3개:**
1. 공공 하이브리드 산정: ISP 단계에서 간이법으로 사업 예산을 신청하고, 제안요청서(RFP) 작성 시점 또는 분석·설계 완료 후 정통법으로 재산정해 과업을 확정함
2. MSA 도메인별 분리 적용: 코어 서비스는 정확도 확보를 위해 정통법을 적용하고, 단순 CRUD 위주의 어드민/백오피스 서비스는 간이법으로 신속히 산정함
3. 애자일 스프린트 혼합: 요구사항이 수시로 변하는 백로그 1차 추정은 간이법으로 속도전(T-Shirt Sizing 연계)을 펼치고, 완료된 스프린트 실적 정산은 정통법으로 증빙함

**결론 (2줄):**
- 기술사 판단: 간이법과 정통법은 대립하는 개념이 아니라 프로젝트 생명주기(기획→설계)에 따라 상호 보완적으로 전환(Shift)해 써야 하는 실무 도구다.
- 향후 방향: 과거 프로젝트 실적 데이터를 머신러닝에 학습시켜 도메인별(금융, 공공 등) 특화 평균 가중치를 자동 추천하는 지능형 간이 산정 모델로 발전해야 한다.
