# 📖 【암기용】 개념 완전 이해

> 목적: EA를 처음 보는 사람도 완벽히 이해하게 만든다. 시험 답안 양식이 아니라, 이해를 위한 친절한 설명이다.

## 한눈에
- **개요**: EA는 조직의 업무, 데이터, 응용, 기술 구조를 한 체계로 관리하는 청사진이다.
- **왜 필요한가**: 시스템이 부서별로 늘어나면 같은 데이터가 여러 곳에 생기고 인터페이스가 복잡해진다. EA는 전체 구조를 보여주고 변경이 미치는 범위를 통제한다.
- **핵심 직관**: EA는 도시 전체의 도로·건물·전기·상하수도 지도를 관리하는 도시계획도와 같다.

## 깊이 이해
- **배경·문제의식**: 정보시스템은 업무 변화에 따라 계속 추가된다. 관리 기준이 없으면 중복 기능, 데이터 불일치, 기술 표준 불일치가 누적된다.
- **작동 원리**: 현행 아키텍처와 목표 아키텍처를 업무, 데이터, 응용, 기술 관점으로 정의한다. 변경 요구가 들어오면 참조모형, 표준, 원칙, 전환계획에 맞는지 검토한다.
- **비유**: 새 건물을 지을 때 도시계획과 건축 기준을 확인하는 것처럼, 새 시스템도 EA 원칙과 표준을 확인한 뒤 구축한다.
- **구체 예시**: 고객 데이터가 CRM, 콜센터, 모바일 앱에 흩어져 있으면 EA는 마스터 데이터, API 표준, 통합 인증, 기술 표준을 지정해 중복을 줄인다.
- **흔한 오해·주의점**: EA는 문서 보관소가 아니다. 변경 심의, 표준 준수, 투자 검토에 사용되지 않으면 아키텍처 관리 기능이 사라진다.

## 연결 개념
- ISP: EA가 따를 중장기 정보화 과제와 로드맵 제공
- TOGAF: EA를 수립하고 운영하는 대표 프레임워크
- TRM·DRM: 공공 부문 기술·데이터 참조 기준

# 📝 【답안용】 시험 답안 템플릿

> 목적: 시험장에서 25분에 그대로 쓰는 답안 양식. 작성방식(추상표현 금지·수치·도식·문제유형 전환)을 엄격히 지킨다.
> 핵심: EA 답안은 정의보다 아키텍처 관점, 거버넌스, 변경 통제, 투자 중복 방지 구조를 함께 써야 한다.

## 핵심 인사이트 (3줄 요약)

> 1. **본질**: EA는 업무·데이터·응용·기술 아키텍처를 통합 관리해 조직 목표와 IT 자산을 정렬하는 구조 관리 체계이다.
> 2. **가치**: 중복 시스템, 데이터 불일치, 표준 미준수, 변경 영향 누락을 아키텍처 원칙과 참조모형으로 통제한다.
> 3. **판단 포인트**: EA 성패는 산출물 작성이 아니라 아키텍처 심의, 표준 준수율, 변경 영향 분석의 운영 여부로 결정된다.

## 출제 의도 및 답안 포인트

| 출제 의도 | 반드시 짚을 핵심 | 감점 회피 포인트 |
|:---|:---|:---|
| EA 관점 구조 이해 확인 | BA, DA, AA, TA와 현행·목표·전환계획 | 업무·기술 목록만 나열 |
| 아키텍처 거버넌스 판단 확인 | 원칙, 표준, 참조모형, 심의, 변경관리 | 문서 작성 프로젝트로만 설명 |
| ISP·TOGAF와 관계 확인 | ISP는 계획, EA는 구조, TOGAF는 방법론 | 세 개념을 혼용 |

> 요약: EA 문제는 전체 구조와 변경 통제 체계를 함께 제시해야 채점 포인트가 선명해진다.

## Ⅰ. 개요 및 필요성

EA는 조직 전체 정보자원을 구조적으로 관리하는 아키텍처 체계이다. 복수 시스템이 독립 구축되면 기능 중복, 데이터 불일치, 인터페이스 폭증이 발생한다. EA는 현행과 목표 구조를 정의하고 변경 시 표준과 원칙을 적용해 IT 투자 방향을 통제한다.

---

## Ⅱ. 구조 및 구성요소

```text
전략/업무 목표 -> BA -> DA -> AA -> TA -> 전환계획
                  +-> 원칙/표준/참조모형/거버넌스
```

| 구성요소 | 역할 | 산출물 |
|:---|:---|:---|
| BA 업무 아키텍처 | 업무 기능, 조직, 프로세스 정의 | 업무 기능 분해도, 프로세스 맵 |
| DA 데이터 아키텍처 | 데이터 주제영역, 표준, 흐름 정의 | 데이터 모델, 표준 용어, 소유자 |
| AA 응용 아키텍처 | 시스템 기능, 서비스, 인터페이스 정의 | 응용 목록, 인터페이스 맵 |
| TA 기술 아키텍처 | 플랫폼, 네트워크, 보안, 기술 표준 정의 | 기술 표준, 참조모형, 구성도 |

> 요약: EA는 업무에서 기술까지 4개 관점을 연결하고 원칙·표준·거버넌스로 변경을 통제한다.

---

## Ⅲ. 동작원리 및 흐름도

```text
전략 확인 -> 현행 아키텍처 수집 -> 목표 아키텍처 정의 -> Gap 분석 -> 전환계획 수립 -> 심의/준수 점검
```

| 단계 | 처리 내용 | 검증 기준 |
|:---:|:---|:---|
| 1 | 전략과 업무 요구를 아키텍처 원칙으로 변환 | 원칙-목표 매핑 |
| 2 | 현행 업무·데이터·응용·기술 자산 목록화 | 자산 누락률, 인터페이스 목록 |
| 3 | 목표 구조와 표준 기술 정의 | 표준 준수 기준, 참조모형 적합성 |
| 4 | 변경 요구 심의와 전환계획 관리 | 심의 통과율, 예외 승인 건수 |

> 요약: EA는 현행 구조를 기준선으로 만들고 목표 구조와의 차이를 전환계획 및 심의 절차로 관리한다.

## Ⅳ. 특징

| 구분 | 단위 시스템 관리 | EA | 판단 포인트 |
|:---|:---|:---|:---|
| 관리 범위 | 시스템별 기능·일정 | 전사 업무·데이터·응용·기술 | 조직 전체 영향 분석 |
| 통제 방식 | 프로젝트 PM 중심 | 아키텍처 원칙·표준·심의 | 예외 승인 절차 |
| 성과 지표 | 구축 완료 여부 | 중복 제거, 표준 준수, 인터페이스 감소 | 준수율 90% 이상 목표 |

> 요약: EA는 개별 프로젝트 관리가 아니라 전사 구조 기준으로 투자와 변경을 통제하는 체계이다.

## Ⅴ. 심화 비교 및 적용 판단

| 비교 축 | 기존/대안 | EA | 선택 기준 |
|:---|:---|:---|:---|
| 구조 | 시스템 목록 관리 | BA·DA·AA·TA 통합 구조 | 시스템 10개 이상, 인터페이스 복잡도 증가 |
| 비용/성과 | 사업별 예산 판단 | 중복 기능, 공통 플랫폼, 표준 재사용 | 중복 기능 제거율, 운영비 절감액 |
| 운영/위험 | 변경 영향 수작업 검토 | 아키텍처 심의·준수 점검 | 법규·보안·표준 예외 관리 필요 시 |

> 요약: EA는 시스템 수와 변경 영향이 커질수록 투자 타당성과 운영 통제 기준을 제공한다.

| 리스크 | 원인 | 대응 방안 | 확인 지표 |
|:---|:---|:---|:---|
| 문서화 고립 | 심의·예산 절차와 미연계 | 투자심사 체크리스트에 EA 항목 반영 | 심의 적용률 100% |
| 현행 불일치 | 자산 변경 후 EA 저장소 미갱신 | CMDB, 배포 승인과 연계 | 갱신 지연 30일 이하 |
| 과도한 표준 | 업무 특수성 미반영 | 예외 승인과 만료일 관리 | 예외 재검토율 100% |

> 요약: EA 운영 리스크는 산출물 미갱신과 거버넌스 미연계이며 심의·CMDB·예외관리로 통제한다.

| 점검 항목 | 목표 기준 | 측정 방법 |
|:---|:---|:---|
| 표준 준수 | 신규 사업 표준 준수율 90% 이상 | 아키텍처 심의 결과 |
| 중복 통제 | 동일 기능 중복 구축 0건 | 기능 카탈로그 비교 |
| 변경 영향 | 주요 변경 영향 분석 100% 수행 | 변경관리 티켓 검토 |

> 요약: EA 도입 효과는 표준 준수율, 중복 구축 건수, 변경 영향 분석 수행률로 판단한다.

## Ⅵ. 실무 적용 및 결론

**적용 방안 3개:**
1. BA·DA·AA·TA 기준 자산 카탈로그를 만들고 시스템, 데이터, 인터페이스 소유자를 1개 부서로 지정함
2. 신규 사업 투자심사에 EA 적합성 항목을 추가하고 표준 미준수는 예외 승인·만료일·대체 계획을 기록함
3. EA 저장소를 CMDB, API 카탈로그, 데이터 표준관리 도구와 연결해 월 1회 기준선 차이를 점검함

**결론 (2줄):**
- 기술사 판단: 조직 규모와 시스템 의존성이 크면 EA를 의무 심의 체계로 운영하고, 단일 부서 시스템은 경량 아키텍처 검토로 적용함
- 향후 방향: EA는 클라우드, 데이터 플랫폼, AI 서비스까지 포함하는 지속 운영형 아키텍처 거버넌스로 확장되어야 함
