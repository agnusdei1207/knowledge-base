# 📖 【암기용】 개념 완전 이해

> 목적: EA를 처음 보는 사람도 완벽히 이해하게 만든다. 시험 답안 양식이 아니라, 이해를 위한 친절한 설명이다.

## 한눈에
- **개요**: **EA**(전사적 아키텍처, Enterprise Architecture)는 조직의 **업무(BA)·데이터(DA)·응용(AA)·기술(TA)** 구조를 하나의 체계로 통합 관리하는 청사진이자 **아키텍처 거버넌스** 체계다. 시스템 하나하나를 따로 보지 않고, 조직 전체 IT 자산의 구조와 그 변화를 통제한다.
- **왜 필요한가**: 시스템이 부서별로 계속 늘어나면 같은 고객 데이터가 여러 곳에 중복 저장되고, 시스템끼리 인터페이스가 기하급수적으로 늘어나 하나만 바꿔도 어디까지 영향이 가는지 아무도 모르게 된다. EA는 전체 구조를 하나의 지도로 만들어 변경 영향을 미리 파악하게 한다.
- **핵심 직관**: EA는 도시 전체의 도로·건물·전기·상하수도를 그린 도시계획도와 같다. 개별 건물(시스템) 인허가를 낼 때마다 이 지도와 맞는지 확인하는 것이 EA 거버넌스다.

## 핵심 용어 정리 (내부에 등장하는 것들)

| 표기/용어 | 의미 | 비유 |
|:---|:---|:---|
| BA (Business Architecture, 업무 아키텍처) | 업무 기능·조직·프로세스를 정의한 관점 | 도시의 "어떤 활동이 어디서 일어나는가"(주거·상업·공업지구 구분) |
| DA (Data Architecture, 데이터 아키텍처) | 데이터 주제영역·표준·흐름·소유자를 정의한 관점 | 상하수도망 — 물(데이터)이 어디서 어디로 흐르는가 |
| AA (Application Architecture, 응용 아키텍처) | 시스템 기능·서비스·인터페이스를 정의한 관점 | 건물들(개별 시스템) |
| TA (Technical Architecture, 기술 아키텍처) | 플랫폼·네트워크·보안·기술표준을 정의한 관점 | 전기·통신망 같은 기반 인프라 |
| TOGAF | EA를 수립·운영하는 대표적 방법론/프레임워크. ADM(Architecture Development Method)이라는 단계별 절차(예비단계 + A~H 총 9단계)를 제공 | 도시계획을 세우는 표준 절차 매뉴얼 |
| TRM (Technical Reference Model) | 기술 표준·구성요소를 정의한 참조모형 — "어떤 기술을 써야 하는가"의 공통 기준 | 전선 규격·통신 프로토콜 표준 |
| DRM (Data Reference Model) | 데이터 분류·표준 용어를 정의한 참조모형 — "데이터를 어떻게 정의하고 부를 것인가"의 공통 기준 | 도로명 주소 체계 같은 공통 표기 규칙 |
| 현행/목표 아키텍처(As-Is/To-Be) | 현재 구조와 미래 지향 구조 | 현재 도시 지도 / 개발계획 반영 지도 |
| 전환계획(Transition Plan) | As-Is에서 To-Be로 이동하는 단계별 실행 계획 | 재개발 단계별 공정표 |
| 아키텍처 거버넌스 | 신규 사업이 EA 원칙·표준에 맞는지 심의하고 예외를 관리하는 의사결정 체계 | 건축 인허가 심의위원회 |

## 깊이 이해

### EA가 왜 "4개 관점"으로 쪼개져 있나
- 조직의 IT를 한 번에 통째로 관리하기는 불가능하므로, TOGAF는 "무엇을 하는가(BA) → 그 일에 어떤 데이터가 필요한가(DA) → 그 데이터를 어떤 시스템이 다루는가(AA) → 그 시스템이 어떤 기술 위에서 도는가(TA)"의 4계층으로 나눠 위에서 아래로 설계한다.
- 이 순서가 중요하다. 기술(TA)부터 정하고 업무(BA)를 나중에 맞추면 "기술은 좋은데 업무에 안 맞는" 시스템이 나온다. 반드시 업무 요구가 먼저고, 데이터·응용·기술은 그 업무를 지원하는 수단으로 뒤따른다.

### 중복 데이터 문제를 EA가 어떻게 잡는가 — 구체 예시
- 고객 데이터가 CRM·콜센터 시스템·모바일 앱 3곳에 각각 저장돼 있다고 하자. 고객이 전화로 주소를 바꾸면 콜센터 DB만 갱신되고 CRM·앱은 옛 주소로 남는다.
- DA(데이터 아키텍처) 관점에서 "고객"을 마스터 데이터로 지정하고, AA(응용 아키텍처) 관점에서 API 표준을 만들어 3개 시스템이 모두 이 마스터 데이터를 참조하게 하면, 주소 변경이 한 곳에서 3곳 모두에 즉시 반영된다. 이렇게 관점을 나눠 원인(데이터 소유권 분산)과 해법(마스터 데이터 지정)을 짝짓는 것이 EA의 실제 작동 방식이다.

### 참조모형(TRM/DRM)과 거버넌스의 역할 — 판별 원리
- 참조모형은 "표준 그 자체"이고, 거버넌스는 "그 표준을 지키는지 확인하는 절차"다. 신규 시스템을 만들 때 TA 참조모형(예: 인증은 반드시 SSO 사용)에 맞지 않으면 아키텍처 심의에서 반려되거나, 불가피한 사유가 있으면 예외 승인(만료일 포함)을 받는다.
- 판별 기준: "이 변경이 EA 심의를 통과했는가, 아니면 프로젝트 팀이 독자적으로 결정했는가"로 거버넌스가 실제로 작동하는지 확인할 수 있다. 심의 없이 진행된 시스템이 많을수록 EA는 문서로만 존재하고 실효성이 없다는 뜻이다.

### EA가 "문서 보관소"로 전락하는 실패 패턴
- EA를 처음 도입할 때 현행 아키텍처를 조사해 두꺼운 문서를 만드는 데까지는 잘 되지만, 이후 신규 사업 심의·투자 검토와 연결되지 않으면 그 문서는 만들어진 순간부터 낡기 시작한다.
- 판별 원리: EA 저장소(자산 목록)가 실제 배포·변경관리(CMDB)와 연동돼 있는가, 신규 투자심사 체크리스트에 EA 적합성 항목이 들어있는가로 EA가 살아있는 체계인지 죽은 문서인지 구분한다.

### 비유
- 새 건물(시스템)을 지을 때 도시계획과 건축기준(EA 원칙·참조모형)을 먼저 확인해야 하는 것과 같다. 기준을 무시하고 지으면 나중에 상하수도(데이터)가 안 맞거나 도로(인터페이스)가 막힌다.

## 연결 개념

- TOGAF (EA를 수립·운영하는 대표 방법론 — 위 표에서 다룬 세부 개념)

# 📝 【답안용】 시험 답안 템플릿

> 목적: 시험장에서 25분에 그대로 쓰는 답안 양식. 작성방식(추상표현 금지·수치·도식·문제유형 전환)을 엄격히 지킨다.
> 핵심: EA 답안은 정의보다 아키텍처 관점, 거버넌스, 변경 통제, 투자 중복 방지 구조를 함께 써야 한다.

## 핵심 인사이트 (3줄 요약)

> 1. **본질**: EA는 업무·데이터·응용·기술 아키텍처를 통합 관리해 조직 목표와 IT 자산을 정렬하는 구조 관리 체계이다.
> 2. **가치**: 중복 시스템, 데이터 불일치, 표준 미준수, 변경 영향 누락을 아키텍처 원칙과 참조모형으로 통제한다.
> 3. **판단 포인트**: EA 성패는 산출물 작성이 아니라 아키텍처 심의, 표준 준수율, 변경 영향 분석의 운영 여부로 결정된다.

## 출제 의도 및 답안 포인트

| 출제 의도 | 반드시 짚을 핵심 | 감점 회피 포인트 |
|:---|:---|:---|
| EA 관점 구조 이해 확인 | BA, DA, AA, TA와 현행·목표·전환계획 | 업무·기술 목록만 나열 |
| 아키텍처 거버넌스 판단 확인 | 원칙, 표준, 참조모형, 심의, 변경관리 | 문서 작성 프로젝트로만 설명 |
| ISP·TOGAF와 관계 확인 | ISP는 계획, EA는 구조, TOGAF는 방법론 | 세 개념을 혼용 |

> 요약: EA 문제는 전체 구조와 변경 통제 체계를 함께 제시해야 채점 포인트가 선명해진다.

## Ⅰ. 개요 및 필요성

- 개요: 전사 정보자원 관리 체계
- 배경: 복수 시스템이 독립 구축되면 기능 중복, 데이터 불일치, 인터페이스 폭증이 발생한다.
- 필요성: 현행·목표 구조와 표준 원칙으로 IT 투자와 변경 방향을 통제해야 한다.

---

## Ⅱ. 구조 및 구성요소

```text
전략/업무 목표 -> BA -> DA -> AA -> TA -> 전환계획
                  +-> 원칙/표준/참조모형/거버넌스
```

| 구성요소 | 역할 | 산출물 |
|:---|:---|:---|
| BA 업무 아키텍처 | 업무 기능, 조직, 프로세스 정의 | 업무 기능 분해도, 프로세스 맵 |
| DA 데이터 아키텍처 | 데이터 주제영역, 표준, 흐름 정의 | 데이터 모델, 표준 용어, 소유자 |
| AA 응용 아키텍처 | 시스템 기능, 서비스, 인터페이스 정의 | 응용 목록, 인터페이스 맵 |
| TA 기술 아키텍처 | 플랫폼, 네트워크, 보안, 기술 표준 정의 | 기술 표준, 참조모형, 구성도 |

> 요약: EA는 업무에서 기술까지 4개 관점을 연결하고 원칙·표준·거버넌스로 변경을 통제한다.

---

## Ⅲ. 동작원리 및 흐름도

```text
전략 확인 -> 현행 아키텍처 수집 -> 목표 아키텍처 정의 -> Gap 분석 -> 전환계획 수립 -> 심의/준수 점검
```

| 단계 | 처리 내용 | 검증 기준 |
|:---:|:---|:---|
| 1 | 전략과 업무 요구를 아키텍처 원칙으로 변환 | 원칙-목표 매핑 |
| 2 | 현행 업무·데이터·응용·기술 자산 목록화 | 자산 누락률, 인터페이스 목록 |
| 3 | 목표 구조와 표준 기술 정의 | 표준 준수 기준, 참조모형 적합성 |
| 4 | 변경 요구 심의와 전환계획 관리 | 심의 통과율, 예외 승인 건수 |

> 요약: EA는 현행 구조를 기준선으로 만들고 목표 구조와의 차이를 전환계획 및 심의 절차로 관리한다.

> 요약: EA 도입 효과는 표준 준수율, 중복 구축 건수, 변경 영향 분석 수행률로 판단한다.

## Ⅵ. 실무 적용 및 결론

**적용 방안 3개:**
1. BA·DA·AA·TA 기준 자산 카탈로그를 만들고 시스템, 데이터, 인터페이스 소유자를 1개 부서로 지정함
2. 신규 사업 투자심사에 EA 적합성 항목을 추가하고 표준 미준수는 예외 승인·만료일·대체 계획을 기록함
3. EA 저장소를 CMDB, API 카탈로그, 데이터 표준관리 도구와 연결해 월 1회 기준선 차이를 점검함

**결론 (2줄):**
- 기술사 판단: 조직 규모와 시스템 의존성이 크면 EA를 의무 심의 체계로 운영하고, 단일 부서 시스템은 경량 아키텍처 검토로 적용함
- 향후 방향: EA는 클라우드, 데이터 플랫폼, AI 서비스까지 포함하는 지속 운영형 아키텍처 거버넌스로 확장되어야 함
