## 핵심 인사이트 (3줄 요약)
- 하둡(MapReduce)이 1단계 계산마다 결과를 하드 디스크에 저장하느라 엄청나게 느렸던 병목을, **전체 연산 과정을 컴퓨터의 램(RAM, 인메모리) 위에서 처리하여 속도를 무려 100배(100x) 이상 끌어올린 빅데이터 분석의 황제**.
- 디스크에 쓰지 않고도 메모리 장애를 견디기 위해, 데이터가 어떻게 만들어졌는지 그 족보(Lineage)를 기억해 두었다가 실패 시 재연산하는 **RDD(탄력적 분산 데이터셋)**라는 기적의 자료구조를 발명함.
- 단순히 배치(Batch) 분석뿐만 아니라, 스트리밍(Spark Streaming), 머신러닝(MLlib), SQL, 그래프 분석 등 5가지 툴을 하나의 엔진으로 통합해 낸 현대 데이터 파이프라인의 글로벌 표준임.

## Ⅰ. 개요 및 필요성
- **개요**: 버클리 AMPLab에서 개발한 오픈소스 클러스터 컴퓨팅 프레임워크로, 인메모리(In-Memory) 연산을 통해 대용량 데이터를 초고속으로 분석하는 통합 분산 엔진.
- **필요성**: 하둡(Hadoop)으로 빅데이터를 다룰 수 있게 된 건 좋았지만, 딥러닝이나 반복 알고리즘(For Loop 100번)을 돌릴 때마다 매번 디스크를 긁어오니 며칠씩 걸렸음. "메모리(RAM) 값이 똥값이 된 시대인데, 그냥 중간 결과물을 디스크에 안 쓰고 메모리에 다 띄워놓고 쾅쾅쾅 연산하면 안 되나?"라는 발상에서 탄생함.
---
## Ⅱ. 아키텍처 및 핵심 원리
- **1. RDD (Resilient Distributed Dataset)**:
  - 스파크의 심장이자 읽기 전용(Immutable) 분산 메모리 객체.
  - RDD는 중간 데이터를 디스크나 다른 노드에 복사해 두지 않음. 대신, "A데이터에서 B를 더하고 C를 곱해서 만들어짐"이라는 **족보(Lineage, 방향성 비순환 그래프 DAG)**만 기억함. 
  - 만약 메모리 연산 중 서버 1대가 뻗어서 데이터가 날아가면? 족보(Lineage)를 보고 처음부터 다시 계산해서 복구함(Resilient, 탄력성).
- **2. Lazy Evaluation (지연 연산의 마법)**:
  - 개발자가 `map()`(필터링), `join()` 등의 변환 명령을 100번 내려도 스파크는 절대 즉시 계산하지 않고 계획표(DAG)만 짬.
  - 마지막에 `count()`나 `save()` 같은 **액션(Action)** 명령이 떨어지는 순간, 엔진(Catalyst)이 100번의 명령을 최적화(SQL의 옵티마이저처럼)해서 한 방에 메모리에서 날려버림.
- **3. 인메모리 컴퓨팅 (In-Memory Computing)**:
  - MapReduce: `[디스크 Read] ➡️ [연산] ➡️ [디스크 Write]` 의 무한 반복.
  - Spark: `[디스크 Read] ➡️ [메모리 연산 ➡️ 메모리 연산 ➡️ 메모리 연산] ➡️ [디스크 Write]`. (디스크 I/O가 획기적으로 사라짐).

```text
[ Hadoop MapReduce와 Spark의 100번 반복 연산(ML학습) 속도 차이 ]

 🐌 [ Hadoop (디스크 기반) ]
 1회차: 메모리 계산 ➡️ 디스크에 저장 (1분 소요)
 2회차: 디스크에서 읽기 ➡️ 메모리 계산 ➡️ 디스크에 저장 (1분 소요)
 ... 100회차 반복 ➡️ (총 100분 소요!)

 ⚡ [ Spark (인메모리 기반) ]
 1회차: 메모리 계산 ➡️ (결과를 램에 그대로 둠, 0초 소요)
 2회차: 램에서 바로 계산 ➡️ (램에 둠)
 ... 100회차 ➡️ 마지막에만 디스크에 저장 ➡️ (총 1분 소요! 100배 빠름!)
```

## Ⅲ. 비교 및 연결
| 구분 | Apache Hadoop (MapReduce) | Apache Spark |
|---|---|---|
| **연산 아키텍처** | 하드 디스크 I/O 의존 | **RAM(인메모리) 최적화 연산** |
| **장애 복구 방식** | 디스크에 중복 저장된 데이터를 다시 읽음 | **RDD Lineage(족보)를 바탕으로 재계산** |
| **반복(Iterative) 연산**| 극도로 느림 (머신러닝 불가능 수준) | **극도로 빠름 (ML 최적화)** |
| **역할 포지션** | 저렴한 대용량 영구 저장소 (HDFS)로 퇴역 | **빅데이터 분석 및 연산 엔진의 1인자** |

## Ⅳ. 실무 적용 및 기술사 판단
- **DataFrame과 Catalyst Optimizer**: 초기에는 개발자들이 날것의 RDD로 코딩했으나, 스파크 2.0부터는 RDB의 테이블처럼 스키마(컬럼명)를 갖춘 **DataFrame**과 **Spark SQL**이 대세가 됨. 기술사는 "스파크 짤 때 RDD 쓰지 마라. DataFrame으로 짜면 밑단에 있는 텅스텐(Tungsten) 물리 엔진과 카탈리스트(Catalyst) 논리 최적화기가 코드를 C++ 수준으로 기계어로 번역해서 실행하므로 무조건 더 빠르다"는 원칙을 실무에 적용해야 함.
- **스트리밍 아키텍처의 한계 (Micro-batch)**: 스파크 스트리밍은 사실 진짜 실시간(0.001초)이 아님. 들어오는 물줄기를 0.5초 단위의 아주 작은 양동이(Micro-batch)에 담아서 배치 처리를 매우 빨리 하는 눈속임임. 진정한 밀리초 단위의 이벤트 처리가 필요한 금융권 사기 탐지 시스템 등에서는 스파크 대신 **Apache Flink**를 도입하는 아키텍처 의사결정이 필요함.

## Ⅴ. 기대효과 및 결론
- 하드 디스크의 느려 터진 족쇄를 풀고 빅데이터 처리의 무대를 메모리(RAM)로 끌어올림으로써, 대규모 데이터셋에 대한 인공지능(AI)과 머신러닝 학습을 산업계에서 실현할 수 있게 한 일등 공신.
- "데이터를 저장하는 곳(S3, HDFS)"과 "데이터를 연산하는 곳(Spark)"을 완벽히 분리(Decoupling)한 클라우드 데이터 레이크(Data Lake) 아키텍처를 완성시킨 가장 위대한 소프트웨어 중 하나임.

### 👶 어린이를 위한 3줄 비유 설명
1. **하둡**은 요리할 때 냉장고(디스크)에서 당근을 꺼내서 자르고, 다시 냉장고에 넣고. 양파를 꺼내서 자르고, 또 넣고 하는 아주 답답한 요리사예요.
2. **스파크**는 넓은 '도마(메모리)'를 가져와서, 냉장고에서 재료를 한 번에 싹 꺼내놓고 도마 위에서 당근, 양파를 미친 듯이 다다다닥(인메모리) 한 번에 썰어버리는 천재 요리사예요!
3. 만약 도마가 엎어져서 재료가 쏟아져도, '레시피(RDD 족보)'를 완벽히 외우고 있어서 다시 냉장고에서 꺼내 순식간에 복구해 낸답니다!
