# 📖 【암기용】 개념 완전 이해

> 목적: UNIX 커널·쉘·파일시스템 3요소를 처음 봐도 완벽히 이해하게 만든다. 시험 답안 양식이 아니라, 이해를 위한 친절한 설명이다.

## 한눈에
- **개요**: UNIX는 커널, 쉘, 파일시스템을 중심으로 자원 관리와 사용자 명령 실행을 구성한 운영체제이다
- **왜 필요한가**: 사용자는 명령을 입력하고, 프로그램은 프로세스로 실행되며, 데이터와 장치는 파일처럼 접근된다. 세 요소가 맞물려 다중 사용자·다중 작업 환경을 만든다.
- **핵심 직관**: 커널은 엔진, 쉘은 운전대, 파일시스템은 도로와 주소 체계에 해당한다.

## 깊이 이해
- **배경·문제의식**: UNIX는 작은 도구를 조합하는 철학과 다중 사용자 환경을 기반으로 설계됐다. 복잡한 기능을 거대한 프로그램 하나에 넣지 않고, 프로세스·파일·파이프를 연결해 문제를 해결한다.
- **작동 원리**: 사용자가 쉘에 명령을 입력하면 쉘은 fork로 자식 프로세스를 만들고 exec로 프로그램을 적재한다. 프로그램은 open/read/write 같은 system call로 커널에 요청하고, 커널은 파일 권한과 장치 접근을 검사한다.
- **비유**: 쉘은 접수 창구, 커널은 내부 처리 부서, 파일시스템은 문서 보관실이다. 사용자는 창구에 요청하고 내부 부서는 권한을 확인한 뒤 문서를 읽거나 쓴다.
- **구체 예시**: `cat access.log | grep 500 | wc -l`은 세 프로세스를 파이프로 연결한다. 각 프로세스는 표준입출력 파일 디스크립터 0, 1, 2를 사용한다.
- **흔한 오해·주의점**: 쉘은 커널이 아니다. 쉘은 사용자 공간 프로그램이며, 권한 검사와 프로세스 스케줄링은 커널이 수행한다.

## 연결 개념
- system call — 사용자 공간과 커널 공간의 진입점
- pipe/redirection — 작은 프로그램을 연결하는 UNIX 조합 방식
- permission — user/group/other와 rwx 접근통제

## Ⅰ. 개요 및 필요성

UNIX는 커널, 쉘, 파일시스템으로 구성된 운영체제이다. 커널은 CPU·메모리·파일·장치를 관리하고, 쉘은 사용자 명령을 해석하며, 파일시스템은 데이터와 장치를 파일 인터페이스로 제공한다. 이 구조는 다중 사용자, 프로세스 조합, 권한 분리를 가능하게 한다.

---

## Ⅱ. 구조 및 구성요소

```text
User -> Shell -> fork / exec -> Process
  -> System Call -> Kernel -> File System / Device / Network
  -> Permission Check -> File Descriptor -> read / write
```

| 구성요소 | 역할 | 특이사항 |
|:---|:---|:---|
| Kernel | CPU·메모리·프로세스·파일·장치 관리 | kernel mode에서 실행 |
| Shell | 명령 해석, 변수, 파이프, 리다이렉션 처리 | sh, bash, zsh |
| File System | 파일·디렉터리·장치를 계층 구조로 제공 | everything is file |
| Process | 실행 중인 프로그램 단위 | PID, PPID, signal |
| Permission | 사용자·그룹·기타 권한 통제 | rwx, UID/GID, umask |

> 요약: UNIX는 쉘이 사용자 명령을 프로세스로 만들고 커널이 system call과 권한 검사를 통해 파일·장치를 제어한다.

---

## Ⅲ. 동작원리 및 흐름도

```text
명령 입력 -> 쉘 파싱 -> fork -> exec -> system call
  -> 권한 검사 -> 파일 / 장치 접근 -> 종료 상태 반환
```

| 단계 | 처리 내용 | 검증 기준 |
|:---:|:---|:---|
| 1 | 쉘이 명령어, 옵션, 파이프, 리다이렉션 파싱 | syntax error 여부 |
| 2 | fork로 자식 프로세스 생성 | PID 생성, parent-child 관계 |
| 3 | exec로 실행 파일을 프로세스 이미지에 적재 | PATH, execute bit |
| 4 | open/read/write로 커널에 파일 I/O 요청 | file descriptor, errno |
| 5 | wait와 exit status로 종료 결과 회수 | exit code 0/비0 |

> 요약: UNIX 명령 실행은 쉘 파싱, fork/exec, system call, 권한 검사, 종료 상태 회수 순서로 진행된다.

## Ⅳ. 특징

| 구분 | 기존/대안 | 본 기술 | 수치·판단 포인트 |
|:---|:---|:---|:---|
| 추상화 | 장치별 API | everything is file | FD 0/1/2 표준입출력 |
| 실행 모델 | 단일 프로그램 중심 | fork/exec와 pipe 조합 | 프로세스 단위 격리 |
| 권한 | 단순 소유자 접근 | user/group/other rwx | chmod 755, umask 022 |
| 운영 | GUI 중심 조작 | 쉘 스크립트 자동화 | cron, pipe, exit code |

> 요약: UNIX의 특징은 파일 추상화, 프로세스 조합, 권한 모델이며 쉘은 이를 자동화하는 사용자 공간 계층이다.

| 비교 축 | 기존/대안 | 본 키워드 | 선택 기준 |

| 운영/위험 | 관리자 직접 실행 | 권한·소유자·스크립트 통제 | sudo 감사, least privilege |

> 요약: UNIX 방식은 작은 도구 조합에 적합하나 반복 실행량이 큰 경우 프로세스 생성 비용과 권한 통제를 점검한다.

| 리스크 | 원인 | 대응 방안 | 확인 지표 |
|:---|:---|:---|:---|

> 요약: UNIX 운영 리스크는 권한, 스크립트 실패, 자원 고갈이며 감사와 limit 설정으로 통제한다.

| 점검 항목 | 목표 기준 | 측정 방법 |
|:---|:---|:---|
| 성능/자원 | fork rate, load average 기준치 유지 | top, pidstat |
| 품질/자동화 | 배치 exit code 0 비율 99% 이상 | cron log, systemd journal |
| 운영/보안 | sudo 감사로그 180일, world-writable 0건 | auditd, find, sudo log |

> 요약: UNIX 운영 품질은 프로세스 자원, 배치 성공률, 권한 감사 지표로 판단한다.

## Ⅵ. 실무 적용 및 결론

**적용 방안 3개 (필수 — 단계별 또는 항목별):**
1. 운영 스크립트는 `set -euo pipefail`, exit code 점검, 로그 파일 회전 기준 30일을 적용한다.
2. 파일 권한은 umask 027, 서비스 계정 분리, sudoers 명령 단위 허용으로 최소 권한을 적용한다.
3. 프로세스·파일 디스크립터는 systemd `LimitNOFILE`, cgroup, ulimit로 제한하고 open fd를 모니터링한다.

**결론 (2줄):**
- 기술사 판단: UNIX는 커널·쉘·파일시스템 분리와 everything is file 원칙을 통해 자동화와 다중 사용자 운영에 적합한 구조이다.
- 향후 방향: 컨테이너와 클라우드 운영에서도 UNIX 프로세스·파일·권한 모델은 런타임 격리와 자동화의 기본 전제로 유지된다.
