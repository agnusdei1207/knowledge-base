## Ⅰ. 개요
- **정의**: Protocol Buffers 기반 IDL로 서비스를 정의하고 HTTP/2 위에서 바이너리 RPC를 수행하는 프레임워크
- **배경/필요성**: REST(166 참조)의 텍스트 직렬화·HTTP/1.1 한계를 넘어 저지연·고처리량 서비스 간 통신이 필요함
- **비유**: 표준 양식(Proto)을 미리 합의한 뒤 압축 택배(바이너리)로 주고받는 것과 유사함

| 출제 의도 | 반드시 짚을 핵심 | 감점 회피 포인트 |
|:---|:---|:---|
| 서비스 간 고성능 통신 방식 | HTTP/2 멀티플렉싱 + Protobuf 직렬화 | REST·GraphQL과의 비교 관점 포함 |

> 요약: Protobuf IDL + HTTP/2 기반으로 고성능 바이너리 RPC를 수행하는 프레임워크임

## Ⅱ. 구성요소
```text
Client Stub --HTTP/2--> [gRPC Server] --Protobuf--> Service Impl
                |
         Channel / Interceptor
```

| 구성요소 | 설명 | 비유 |
|:---|:---|:---|
| Proto 파일 | 서비스·메시지를 정의하는 IDL 계약서 | 표준 주문 양식 |
| Stub | Proto에서 자동 생성된 클라이언트 측 프록시 | 대리 주문 접수원 |
| Channel | 서버와의 연결을 관리하는 전송 계층 | 전용 배송 경로 |
| Interceptor | 요청·응답에 인증·로깅 등 횡단 관심사를 삽입하는 미들웨어 | 택배 검수 게이트 |

> 요약: Proto-Stub-Channel-Interceptor 구조로 타입 안전 RPC를 수행함

## Ⅲ. 절차
```text
Proto 정의 --> 코드 생성 --> Stub 호출 --> 서버 처리/응답
     |             |             |              |
     v             v             v              v
  IDL 작성    protoc 컴파일   바이너리 직렬화   역직렬화+로직
```
- 1단계: `.proto` 파일에 서비스 메서드와 메시지 타입을 정의함
- 2단계: `protoc` 컴파일러가 클라이언트 Stub·서버 스켈레톤 코드를 자동 생성함
- 3단계: 클라이언트가 Stub을 통해 메시지를 Protobuf 바이너리로 직렬화하여 호출함
- 4단계: 서버가 역직렬화 후 비즈니스 로직을 수행하고 응답을 반환함

> 요약: 정의-생성-호출-처리 4단계로 타입 안전한 원격 호출을 수행함

## Ⅳ. 문제점
- 브라우저 직접 호출 제한: HTTP/2 바이너리 프레이밍을 브라우저가 직접 다루기 어려움
- 디버깅 난이도: 바이너리 페이로드로 텍스트 기반 도구(curl 등)로 확인이 곤란함
- 스키마 변경 관리: Proto 필드 번호 충돌 시 하위 호환성이 깨질 수 있음

> 요약: 브라우저 제한·디버깅 난이도·스키마 호환이 주요 과제임

## Ⅴ. 개선방안
1. 단기: gRPC-Web 프록시 도입으로 브라우저 호출 지원
2. 중기: gRPC 전용 디버깅 도구(grpcurl·Postman gRPC)로 가시성 확보
3. 장기: Proto 필드 번호 거버넌스 + Buf 등 린트 도구로 스키마 호환성 관리

> 요약: gRPC-Web-디버깅 도구-스키마 거버넌스 순으로 개선함

## Ⅵ. 전망
- 발전 방향: 서비스 메시(Istio 등)와 결합하여 MSA 내부 통신 표준으로 확산 중임
- 기술사적 판단: 내부 서비스 간 통신은 gRPC, 외부 공개 API는 REST로 역할 분담이 정착됨
- 기술사 제언: 스트리밍 RPC(Bidirectional)를 활용한 실시간 통신 설계 역량을 확보할 필요
