## Ⅰ. 개요
- 정의: 소프트웨어 개발부터 운영 배포까지의 전 과정을 자동화된 일련의 단계로 구성한 체계.
- 출제 의도: 파이프라인의 각 단계별 기술적 역할과 품질 보증을 위한 자동화 도구 활용 능력 평가.

## Ⅱ. 구성요소
- ASCII 구조도
  [ Source ] -> [ Build ] -> [ Test ] -> [ Staging ] -> [ Prod ]
  (Git)         (Maven)      (JUnit)     (EKS-Dev)      (EKS-Real)
- 구성요소 표
| 구성요소 | 설명 | 비유 |
| :--- | :--- | :--- |
| Artifact | 빌드 결과물(Jar, Docker Image 등)로 배포의 기본 단위 | 완제품 박스 |
| Pipeline Tool | 각 단계를 연결하고 제어하는 엔진(Jenkins, GitHub Actions) | 공정 컨트롤러 |
| 품질 게이트 | 특정 기준(테스트 통과율 등) 미달 시 다음 단계 차단 | 불량 검출기 |
> 요약: 코드가 살아있는 서비스로 변환되는 자동화된 흐름의 통로임.

## Ⅲ. 절차
- ASCII 흐름도
  [Event Trigger] -> [Env Provision] -> [Execution] -> [Notification]
- 4단계 설명
1. PR 생성이나 특정 브랜치 푸시 이벤트를 감지하여 파이프라인 기동함.
2. 격리된 환경(Container 등)을 동적으로 생성하여 클린 빌드 준비함.
3. 정의된 스크립트에 따라 빌드, 스캔, 테스트, 아티팩트 업로드 수행함.
4. 성공/실패 여부를 슬랙 등 협업 도구로 실시간 통보하여 대응 유도함.
> 요약: 수동 개입 없는 'Zero-touch' 배포 환경을 지향함.

## Ⅳ. 문제점
- 파이프라인 취약점: 파이프라인 설정 파일(YAML) 변조를 통한 악성 코드 주입 위험함.
- 환경 불일치: 테스트 환경과 실제 운영 환경의 미세한 차이로 인해 '배포 사고' 발생함.

## Ⅴ. 개선방안
- Pipeline as Code: 파이프라인 구성을 코드화하고 상호 리뷰를 통해 무단 변경 방지함.
- 컨테이너 기반 검증: 운영 환경과 동일한 이미지를 테스트 단계에서 사용하여 일관성 확보함.

## Ⅵ. 전망
- GitOps 아키텍처(ArgoCD 등)와 결합하여 'Push' 방식이 아닌 'Pull' 방식 배포로 전환됨.
- AI 코파일럿이 파이프라인 에러를 분석하고 수정 가이드를 제시하는 자동 복구 기술 도입됨.
- 공급망 보안 강화를 위해 생성된 모든 아티팩트에 서명을 부여하는 SLSA 프레임워크 적용 확산됨.
