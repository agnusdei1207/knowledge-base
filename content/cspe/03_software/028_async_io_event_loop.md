## 미리 알고가기

- 비동기 I/O는 요청 등록 후 호출자에게 제어를 반환하고 완료 이벤트로 결과를 전달함
- 이벤트 루프는 준비된 이벤트를 순차적으로 처리하는 실행 구조임
- 이벤트 루프는 준비된 I/O만 처리하고 CPU 연산은 워커 풀로 분리함

## 작성 근거(검토용)

- 동기식과 비동기식 I/O를 스레드·대기·완료·흐름 제어·제약·적용 업무로 비교함
- 요청 등록·준비 이벤트 감지·콜백 실행·후속 등록을 실제 제어권 전이로 유지함
- API 게이트웨이와 실시간 입력을 분리해 이벤트 루프 지연과 큐 깊이를 검증함

## Ⅰ. 개요

- **정의/개념**: 비동기 I/O는 요청 후 호출 흐름을 반환하고 완료 이벤트로 후속 처리를 실행하며, 이벤트 루프는 준비된 이벤트를 순차 디스패치하는 서버 실행 모델임
- **배경/필요성**: 연결별 스레드 방식은 연결 수만큼 스레드 스택과 스케줄링 자원을 사용하므로, 연결과 실행 자원을 분리하는 비동기 구조가 필요함

## Ⅱ. 특징

- 연결 수와 실행 스레드 수를 분리해 I/O 대기 중인 연결이 스레드를 점유하지 않게 함
- backpressure·콜백 순서·오류 전파 규칙이 없으면 처리 경로와 실패 위치를 추적하기 어려움
- CPU 집약 작업은 워커 풀로 분리해 이벤트 루프 점유시간을 제한함
- 이벤트 루프의 장기 실행 작업은 뒤에 대기하는 이벤트의 처리시간을 늘림

## Ⅲ. 종류 및 비교

| 판단 기준 | 동기식 I/O | 비동기 I/O 이벤트 루프 |
|:---|:---|:---|
| 스레드 사용 | 연결 수 비례 증가 | 적은 스레드 유지 가능 |
| 코드 흐름 | 직선적 | 콜백 또는 future 중심 |
| 실행 흐름 | 호출 스택에서 요청 완료까지 대기 | 완료 이벤트가 callback·future 후속 작업 실행 |
| 주의점 | 자원 비용 큼 | 복잡도와 backpressure 설계 필요 |
| 흐름 제어 | 스레드·연결 한도 | 큐 상한·backpressure |
| 대표 적용 사례 | 낮은 동시성·순차 처리 | API 게이트웨이·메시지 서버 |

> 요약: 동기식 I/O는 호출 스레드가 완료를 기다리고, 비동기 I/O는 요청 후 제어권을 반환하고 완료 이벤트로 후속 작업을 실행함.

## Ⅳ. 구성요소 및 구조

| 구성요소 | 설명 |
|:---|:---|
| 이벤트 루프 | 준비 이벤트를 큐에서 꺼내 콜백을 순차 실행함 |
| 비차단 I/O API | 준비되지 않은 읽기·쓰기에서 대기 상태를 반환함 |
| 콜백·Future 체인 | 완료 결과를 후속 연산과 오류 처리에 연결함 |
| 워커 풀 | CPU 연산·차단 호출을 이벤트 루프 밖에서 실행함 |

> 요약: 비차단 API가 요청을 등록하고 이벤트 루프가 준비 이벤트를 콜백·Future에 전달함.

## Ⅴ. 원리 및 절차 흐름도

```text
+-------------+     +-------------+     +-------------+     +-------------+
| 요청 등록      | --> | 이벤트 감시    | --> | 준비 이벤트 처리 | --> | 완료 통지      |
+-------------+     +-------------+     +-------------+     +-------------+
```

1. **요청 등록**: 소켓·파일 I/O를 비차단 방식으로 등록하고 제어권을 반환함
2. **준비 이벤트 감시**: selector·poller가 읽기·쓰기 가능 이벤트를 수집함
3. **콜백 실행**: 이벤트 루프가 준비된 요청의 콜백·Future 후속 작업을 실행함
4. **후속 등록**: 완료 결과를 전달하고 추가 I/O가 있으면 다시 등록함

## Ⅵ. 실무 사례

1. API 게이트웨이는 CPU 연산을 워커 풀로 분리하고 이벤트 루프 지연과 p99 요청 지연을 확인함
2. 실시간 입력 서버는 큐 상한과 backpressure를 적용하고 큐 깊이와 입력 거절률을 확인함

## Ⅶ. 결론

- 비동기 I/O는 연결 수·I/O 대기 비율·CPU 작업 분리·큐 상한을 기준으로 이벤트 루프를 설계함
