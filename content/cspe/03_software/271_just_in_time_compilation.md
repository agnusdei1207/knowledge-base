## Ⅰ. 개요
- **정의**: 실행 시점에 바이트코드를 네이티브 코드로 변환하는 동적 컴파일 기법
- **배경/필요성**: 인터프리터의 반복 해석 오버헤드를 제거하면서 AOT 컴파일의 이식성 제약을 회피할 필요
- **비유**: 외국어 문서를 매번 통역하던 것을 자주 쓰는 문단만 미리 번역해 두는 것과 유사함

| 출제 의도 | 반드시 짚을 핵심 | 감점 회피 포인트 |
|:---|:---|:---|
| 동적 컴파일 원리 이해 | 핫스팟 탐지 → 컴파일 → 캐시 흐름 | AOT와 혼동 금지, 프로파일 기반 최적화 언급 필요 |

> 요약: 실행 빈도 높은 코드를 런타임에 네이티브로 변환하여 해석 오버헤드를 제거하는 기법임

## Ⅱ. 구성요소
```text
Source -> [Bytecode] -> Interpreter
                            |
                      Profiler(Hot Spot)
                            |
                      JIT Compiler
                            |
                      [Native Code Cache]
```

| 구성요소 | 설명 | 비유 |
|:---|:---|:---|
| Profiler | 메서드 호출 빈도·루프 반복 횟수를 측정하여 핫스팟 식별 | 자주 가는 길목을 기록하는 교통 조사원 |
| JIT Compiler | 핫스팟 바이트코드를 네이티브 명령어로 변환 | 자주 쓰는 문단을 모국어로 번역하는 번역가 |
| Code Cache | 컴파일된 네이티브 코드를 메모리에 보관하여 재사용 | 번역 완료 문서를 꽂아 두는 파일 캐비닛 |
| Deoptimizer | 가정 위반 시 인터프리터 모드로 복귀 | 오역 발견 시 원문으로 되돌리는 교정 담당 |

> 요약: 프로파일러가 핫스팟을 탐지하면 JIT 컴파일러가 네이티브로 변환하고 코드 캐시에 보관함

## Ⅲ. 절차
```text
바이트코드 실행 -> 프로파일링 -> 핫스팟 판별 -> 네이티브 컴파일/캐시
```
- 1단계: 인터프리터가 바이트코드를 순차 실행하며 프로파일 데이터 수집
- 2단계: 호출 카운터가 임계값 초과 시 해당 메서드를 핫스팟으로 표시
- 3단계: JIT 컴파일러가 인라이닝·루프 언롤링 등 최적화 적용 후 네이티브 코드 생성
- 4단계: 생성된 네이티브 코드를 코드 캐시에 저장하고 이후 호출 시 캐시에서 실행

> 요약: 프로파일 → 핫스팟 식별 → 최적화 컴파일 → 캐시 재사용 순서로 동작함

## Ⅳ. 문제점
- 워밍업 지연: 초기 실행 시 프로파일·컴파일 비용이 발생하여 응답 시간이 증가함
- 메모리 소비: 코드 캐시가 힙 외 메모리를 점유하여 제한된 환경에서 OOM 위험 존재
- 탈최적화 비용: 가정 위반 시 네이티브→인터프리터 전환 과정에서 성능 급락 발생

> 요약: 워밍업 지연, 캐시 메모리 소비, 탈최적화 비용이 주요 문제임

## Ⅴ. 개선방안
1. 단기: AOT 사전 컴파일(GraalVM Native Image)로 워밍업 제거
2. 중기: 계층형 컴파일(C1/C2) 적용으로 코드 캐시 크기 최적화
3. 장기: 프로파일 기반 적응형 탈최적화 정책으로 전환 비용 최소화

> 요약: AOT 병행, 계층형 컴파일, 적응형 탈최적화로 각 문제에 대응함

## Ⅵ. 전망
- 발전 방향: GraalVM·Project Leyden 등 AOT+JIT 하이브리드 모델로 수렴 추세
- 기술사적 판단: 클라우드 네이티브 환경에서 콜드스타트 최소화가 핵심 과제임
- 기술사 제언: 서버리스·컨테이너 환경별 JIT/AOT 전략을 분리 설계할 필요
