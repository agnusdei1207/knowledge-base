# 📖 【암기용】 개념 완전 이해

> 목적: JIT 컴파일을 VM 실행 중 수집한 정보를 이용해 핫 코드를 네이티브 코드로 바꾸는 기술로 이해하게 만든다.

## 한눈에
- **개요**: JIT(Just-In-Time) 컴파일은 **바이트코드 VM**이 프로그램을 실행하면서 자주 실행되는 코드 구간(핫스팟)을 실시간으로 찾아내 **네이티브 코드**로 즉석 변환하는 런타임 최적화 기법이다.
- **왜 필요한가**: 바이트코드 VM은 한 번 컴파일해 어디서나 실행 가능한 이식성을 주지만, 매번 명령을 해석하는 비용이 든다. JIT은 이식성은 유지하면서 실제로 많이 도는 부분만 네이티브 코드로 바꿔 해석 비용을 없앤다.
- **핵심 직관**: 처음 몇 번은 통역사가 그때그때 옮기다가, 같은 문장이 반복되면 아예 번역문을 만들어 그다음부터는 번역문을 읽기만 하는 방식이다.

## 핵심 용어 정리 표 (내부에 등장하는 것들)

| 용어 | 의미 | 비유 |
|:---|:---|:---|
| JIT (Just-In-Time) 컴파일 | 실행 중 핫 코드를 네이티브 코드로 변환하는 기법 (상위 개념) | 반복되는 대사를 즉석에서 대본화 |
| 바이트코드 VM | 바이트코드를 해석·실행하는 소프트웨어 실행 환경 | 어디서든 같은 대본을 읽는 통역 부스 |
| 인터프리터 | JIT 이전 단계에서 바이트코드를 한 줄씩 해석 실행 | 매번 즉석 통역 |
| 프로파일러(Profiler) | 메서드 호출 횟수·분기·타입 정보를 실행 중 수집 | 누가 어떤 말을 몇 번 하는지 기록하는 속기사 |
| 핫스팟(Hotspot) | 호출·반복 횟수가 임계값을 넘어 컴파일 대상이 된 코드 구간 | 자주 반복돼서 외워버린 대사 |
| Tiered Compilation (C1/C2) | 빠른 저수준 컴파일(C1)과 느리지만 강력한 최적화(C2)를 단계적으로 적용 | 초벌 번역 후 정교한 재번역 |
| 코드 캐시(Code Cache) | JIT이 생성한 네이티브 코드를 저장해 재사용하는 메모리 영역 | 한 번 만든 번역문을 보관하는 서랍 |
| Deoptimization (역최적화) | 최적화의 전제(가정)가 깨졌을 때 네이티브 코드를 버리고 인터프리터로 되돌아가는 과정 | 번역문이 상황과 안 맞아 다시 통역으로 전환 |
| Warm-up | 프로그램 시작 후 JIT이 핫스팟을 충분히 컴파일해 정상 성능에 도달하기까지의 구간 | 통역사가 워밍업하는 초반 시간 |
| AOT (Ahead-Of-Time) | 실행 전, 배포 시점에 미리 네이티브 코드를 만들어 두는 방식 | 아예 사전 번역해서 배포 |

## 깊이 이해

### 배경 — 이식성과 속도의 trade-off
- Java 같은 언어는 "한 번 작성해 어디서나 실행"을 목표로 바이트코드+VM 구조를 택했다. 문제는 인터프리터가 바이트코드를 한 줄씩 해석하는 비용이 네이티브 코드 실행보다 수십~수백 배 느릴 수 있다는 점이다(270 참조).
- JIT은 "실행 시간의 대부분을 차지하는 건 전체 코드의 일부(핫 코드)뿐"이라는 관찰에서 이 문제를 풀어낸다 — 전체를 미리 컴파일하지 않고, 실제로 많이 실행되는 부분만 실행 중에 골라 컴파일한다.

### 핫스팟을 찾는 원리 — 카운터와 임계값
- 인터프리터는 메서드가 호출될 때마다, 그리고 루프가 한 바퀴 돌 때마다(백엣지, backedge) 카운터를 증가시킨다. 예를 들어 HotSpot JVM은 메서드 호출 카운터가 특정 임계값(가벼운 C1 단계는 약 1,500회, 완전 최적화 C2 단계는 약 10,000회 수준을 예로 든다)을 넘으면 그 메서드를 컴파일 큐에 올린다.
- 임계값 이하로만 호출되는 코드(초기화 코드처럼 한 번만 도는 부분)는 끝까지 인터프리터로만 실행된다 — 컴파일 비용을 들일 가치가 없기 때문이다.

### Tiered Compilation — 단계적으로 최적화하는 이유
- 처음부터 최고 수준 최적화(C2)를 하면 컴파일 자체에 시간이 오래 걸려 오히려 초반 성능이 나빠진다. 그래서 HotSpot은 먼저 C1으로 빠르게(가벼운 최적화만) 컴파일해 인터프리터보다 즉시 빠르게 만들고, 호출 횟수가 더 쌓이면 C2가 프로파일 정보(실제 관측된 타입, 분기 확률)를 활용해 인라이닝·이스케이프 분석 같은 고급 최적화를 적용한 코드로 다시 교체한다. "빠르게 대충 → 느리지만 정교하게"의 2단계 접근이다.

### Deoptimization을 구체 예로 이해하기
- JIT은 실행 중 관측한 타입 정보를 믿고 최적화한다. 예를 들어 `process(obj)`가 지금까지 항상 `Cat` 타입만 받았다면, C2는 "obj는 Cat이다"라고 가정하고 가상 호출을 생략한 채 Cat의 메서드를 직접 호출하는 코드를 만든다(인라인 캐싱).
- 이후 `Dog` 객체가 들어오면 이 가정이 깨진다. JVM은 방금 만든 네이티브 코드를 즉시 버리고 그 지점부터 인터프리터로 되돌아가(deoptimization) 정확성을 지킨 뒤, 필요하면 새 프로파일로 재컴파일한다. deopt가 자주 발생하면(예: deopt rate 1%를 넘으면) 컴파일-폐기가 반복돼 오히려 성능이 떨어진다.

### Warm-up을 수치로 이해하기
- 프로그램을 막 시작한 시점에는 모든 코드가 인터프리터로만 돈다. 카운터가 쌓여 C1, C2로 승격되기까지 수백 ms~수 초가 걸리므로, 이 구간의 응답 지연은 정상 운영 때보다 눈에 띄게 느리다(예: cold start 시 첫 요청들이 1~10초 걸릴 수 있음).
- 그래서 실제 서비스에서는 배포 직후 실트래픽을 바로 받지 않고, pre-warm 트래픽을 흘려 JIT이 핫스팟을 미리 컴파일하게 한 뒤 라우팅을 여는 운영 기법을 쓴다.

### 비유와 AOT와의 차이
- 콜센터 상담원이 처음 몇 번은 매뉴얼을 찾아가며 즉석으로 답하다가, 같은 질문이 반복되면 정형 답변 스크립트를 만들어 다음부터는 그걸 그대로 읽는 것이 JIT이다.
- 반대로 AOT는 상담을 시작하기도 전에 예상 질문 전체에 대한 스크립트를 미리 다 만들어 놓는 방식이다 — 시작은 빠르지만(warm-up이 없음), 실제 실행 중 관측한 정보를 반영해 최적화하지는 못한다. 그래서 장시간 도는 서버는 JIT이, 실행 즉시 끝나는 CLI·서버리스 함수는 AOT(GraalVM Native Image 등)가 유리하다.

## 연결 개념
- 바이트코드 VM — JIT이 최적화 대상으로 삼는 중간 실행 표현 (270 참조)
- 프로파일 기반 최적화 — 실제 실행에서 관측된 타입·분기 정보를 최적화에 활용하는 원리
- AOT 컴파일 — 배포 전 네이티브 코드를 생성해 warm-up을 없애는 대안 방식

# 📝 【답안용】 시험 답안 템플릿

> 목적: JIT을 단순 컴파일 방식이 아니라 프로파일 수집, 핫스팟 탐지, 코드 캐시, deoptimization까지 포함한 런타임 최적화로 답안화한다.

## 핵심 인사이트 (3줄 요약)

> 1. **본질**: JIT 컴파일은 VM 실행 중 핫스팟 코드를 네이티브 코드로 변환하여 해석 비용을 줄이는 기법이다.
> 2. **가치**: 플랫폼 이식성은 바이트코드가, 실행 경로 최적화는 런타임 프로파일이 담당한다.
> 3. **판단 포인트**: warm-up, code cache, GC, deoptimization 지표를 함께 봐야 서버 운영 적합성을 판단할 수 있다.

## 출제 의도 및 답안 포인트

| 출제 의도 | 반드시 짚을 핵심 | 감점 회피 포인트 |
|:---|:---|:---|
| VM 최적화 구조 이해 확인 | 인터프리터, profiler, compiler, code cache | "실행 중 컴파일" 한 줄로 종료 |
| 서버 운영 판단 확인 | warm-up time, p95 latency, code cache pressure | 평균 지연만 제시하고 초기 지연 누락 |
| AOT와 비교 역량 확인 | JIT의 동적 최적화 vs AOT의 예측 가능한 시작 시간 | JIT과 AOT를 우열 관계로 단정 |

> 요약: JIT 문제는 핫스팟 탐지부터 운영 지표까지 연결해야 채점 포인트를 확보한다.

## Ⅰ. 개요 및 필요성

- 개요: JIT 컴파일은 실행 중 바이트코드를 네이티브 코드로 바꾸는 기술이다.
- 배경: VM 기반 언어는 이식성을 확보하지만 해석 비용이 발생해 반복 실행 구간에서 CPU 사용률과 지연이 커진다.
- 필요성: 실행 빈도가 높은 hot path만 네이티브 코드로 변환해 런타임 최적화 비용을 통제해야 한다.

---

## Ⅱ. 구조 및 구성요소

```text
Bytecode -> Interpreter -> Profiler -> Hotspot Detector
  -> JIT Compiler -> Code Cache -> Native Execution
  -> Deoptimization -> Interpreter
```

| 구성요소 | 역할 | 특이사항 |
|:---|:---|:---|
| Interpreter | 바이트코드 초기 실행 | warm-up 구간 담당 |
| Profiler | 호출 횟수, 타입, 분기 빈도 수집 | tiered compilation 입력 |
| JIT Compiler | IR 최적화 후 네이티브 코드 생성 | inlining, escape analysis |
| Code Cache | 생성 코드 저장·재사용 | 용량 부족 시 컴파일 제한 |

> 요약: JIT은 해석, 프로파일링, 컴파일, 코드 캐시, 역최적화가 순환하는 런타임 파이프라인이다.

---

## Ⅲ. 동작원리 및 흐름도

```text
프로그램 시작 -> 바이트코드 해석 -> 호출 카운터 증가
  -> 임계값 초과 -> 네이티브 코드 생성 -> 코드 캐시 실행
  -> 가정 실패 -> deoptimization -> 재해석
```

| 단계 | 처리 내용 | 검증 기준 |
|:---:|:---|:---|
| 1 | 바이트코드 로딩 및 인터프리터 실행 | class loading time |
| 2 | 메서드 호출·루프 반복 프로파일 수집 | invocation/backedge counter |
| 3 | hot method 컴파일 및 인라이닝 | compilation count, tier level |
| 4 | 코드 캐시 실행 및 가정 검증 | deopt count, code cache usage |

> 요약: JIT은 실행 빈도 기반으로 컴파일 대상을 좁히고, 가정이 깨지면 역최적화로 실행 정확성을 보존한다.

## Ⅳ. 특징

| 구분 | 인터프리터 | JIT | 정량·기술 포인트 |
|:---|:---|:---|:---|
| 시작 시간 | 즉시 실행 | 컴파일 전 warm-up 필요 | cold start 1~10초 가능 |
| 최적화 정보 | 정적 정보 제한 | 실제 타입·분기 정보 활용 | profile guided optimization |
| 메모리 | 코드 캐시 없음 | 코드 캐시·메타데이터 사용 | code cache 128~512MB |
| 운영 영향 | 예측 가능 | 컴파일 스파이크 발생 가능 | p95/p99 latency 관측 |

> 요약: JIT은 장시간 실행 서버에서 유리한 구조이나 cold start와 코드 캐시를 운영 지표로 관리해야 한다.

## Ⅴ. 심화 비교 및 적용 판단

| 비교 축 | 기존/대안 | 본 키워드 | 선택 기준 |
|:---|:---|:---|:---|
| AOT | 배포 전 네이티브 생성 | 실행 중 네이티브 생성 | cold start 500ms 이하 필요 시 AOT |
| 인터프리터 | 해석 비용 지속 | 핫스팟만 컴파일 | 반복 실행 비율 70% 이상인 서버 |
| 컨테이너 | 시작 시간 민감 | warm-up 필요 | readiness probe와 pre-warm 적용 |

> 요약: JIT은 반복 호출이 많은 장수 프로세스에 적합하고, 짧은 실행 함수는 AOT 또는 인터프리터가 선택 기준이다.

| 리스크 | 원인 | 대응 방안 | 확인 지표 |
|:---|:---|:---|:---|
| cold start 지연 | 초기 해석·컴파일 비용 | CDS, pre-warm, AOT 검토 | startup time, readiness time |
| 지연 스파이크 | JIT 컴파일 CPU 점유 | tiered level 조정, compilation thread 제한 | p99 latency, CPU steal |
| 코드 캐시 고갈 | 동적 생성 코드 증가 | code cache sizing, class unloading | code cache used percent |

> 요약: JIT 운영 리스크는 시작 시간, 지연 스파이크, 코드 캐시 고갈로 구분해 대응한다.

| 점검 항목 | 목표 기준 | 측정 방법 |
|:---|:---|:---|
| warm-up | 배포 후 3분 내 p95 목표 도달 | load test, APM |
| 컴파일 상태 | deopt rate 1% 이하 | JVM JFR, perf event |
| 메모리 | code cache 사용률 80% 이하 | runtime metric, alert |

> 요약: JIT 적용 성공은 warm-up 시간, deoptimization 비율, 코드 캐시 사용률로 판단한다.

## Ⅵ. 실무 적용 및 결론

**적용 방안 3개 (필수 — 단계별 또는 항목별):**
1. JVM 서비스는 JFR로 compilation time, deopt count, code cache 사용률을 수집하고 배포 전 부하 테스트에 반영함.
2. Kubernetes 배포는 startup probe와 readiness probe를 분리하고, pre-warm 트래픽으로 p95 지연 목표 도달 후 라우팅함.
3. 서버리스·CLI는 GraalVM Native Image, ReadyToRun, AOT를 검토해 cold start 500ms 이하 요구를 충족함.

**결론 (2줄):**
- 기술사 판단: 반복 실행 서버는 JIT, 짧은 수명 워크로드는 AOT 또는 인터프리터 중심으로 선택.
- 향후 방향: tiered JIT, profile guided AOT, CRaC 같은 체크포인트 복원 기술이 결합되는 방향임.
