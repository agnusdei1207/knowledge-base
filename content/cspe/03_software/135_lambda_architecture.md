# 📖 【암기용】 개념 완전 이해

## 한눈에
- **개요**: 빅데이터를 정확한 대용량 배치(Batch) 레이어와 빠른 실시간 스피드(Speed) 레이어로 동시에 나누어 처리하고, 결과를 서빙(Serving) 레이어에서 합쳐 보여주는 데이터 파이프라인 아키텍처다.
- **왜 필요한가**: 수집된 데이터를 전부 분석하려면 배치 처리를 해야 하는데 시간이 오래 걸리고, 스트리밍으로 빨리빨리 처리하면 정확도가 떨어진다. 정확도와 실시간성 두 마리 토끼를 다 잡고 싶었다.
- **핵심 직관**: "어제까지의 완벽한 과거 장부(배치)" + "오늘 아침부터 지금 이 순간까지의 임시 장부(스피드)"를 더해서 사용자에게 실시간 현재 상태(서빙)를 보여준다.

## 핵심 용어 정리 (내부에 등장하는 것들)

| 용어/표기 | 의미 | 비유·예 |
|:---|:---|:---|
| Batch Layer (배치) | 모든 원본 데이터를 보관하고 정확한 전체 재계산을 주기적으로 수행 | "밤마다 마감하는 철저한 일일 정산 장부" |
| Speed Layer (스피드) | 배치 연산이 도는 동안의 최신 데이터를 실시간 처리 (최근 데이터만 다룸) | "실시간으로 적는 가계부 (임시 메모)" |
| Serving Layer (서빙) | 배치 레이어 뷰와 스피드 레이어 뷰를 병합해 사용자 질의에 응답 | "어제 장부 + 오늘 임시 메모를 더해 보여주는 점원" |
| 마스터 데이터 세트 | 수정 불가(Immutable), 추가만 가능(Append-only)한 원본 데이터 | "한 번 쓰면 지울 수 없는 로그 창고" |

## 깊이 이해
- **배경·문제의식**: 하둡 기반의 맵리듀스는 정확하지만 결과를 보려면 몇 시간이 걸렸다(High Latency). 실시간 대응이 안 되어 스트리밍 기술(Storm 등)을 붙이려 하니, 분산 환경 특성상 데이터가 유실되거나 중복 처리되어 결과가 100% 안 맞았다(Low Accuracy). 둘 다 포기할 수 없어 네이선 마츠(Nathan Marz)가 제안한 것이 두 경로를 쪼개는 람다 아키텍처다.
- **작동 원리**: 데이터가 들어오면 양쪽으로 보낸다. 
  1. 스피드 레이어는 수 초 내로 빨리 처리해 실시간 뷰를 만든다(부정확할 수 있음). 
  2. 배치 레이어는 거대한 원본 데이터를 하루 1번 돌려 정확한 배치 뷰를 만든다. 
  3. 클라이언트가 쿼리를 던지면 서빙 레이어가 `Batch View + Speed View`를 엮어서 완벽한 현재 상태를 리턴한다.
  4. 배치 연산이 완료되어 어제 데이터가 확정되면, 스피드 레이어에 있던 어제치 임시 뷰는 폐기한다.
- **비유**: 대형 은행 잔고 표시. 어제 자정까지 완벽하게 정산된 잔고(배치)에, 오늘 아침부터 스마트폰으로 이체하고 카드로 긁은 승인 내역(스피드)을 합산해야 고객이 보는 현재 잔고(서빙)가 된다. 자정이 지나면 오늘 내역은 다시 완벽 정산 장부에 들어간다.
- **구체 예시**: 카프카(Kafka)로 들어온 로그를 스파크 배치(Spark)가 HDFS에 매일 야간에 굽고, 스톰(Storm)이 1분 단위로 실시간 계산을 한다. 뷰어는 카산드라(Cassandra)에서 둘을 엮어서 본다.
- **흔한 오해·주의점**: 아이디어는 좋지만, 똑같은 로직(예: 합산, 필터링)을 배치용(Spark) 코드와 스트리밍용(Storm) 코드 두 세트로 각각 개발하고 관리해야 하는 '이중 코드 관리' 부담이 최악의 단점이다. 유지보수가 너무 어려워 카파(Kappa) 아키텍처로 넘어가게 된 원인이 된다.

# 📝 【답안용】 시험 답안 템플릿

## 핵심 인사이트 (3줄 요약)

> 1. **본질**: 람다 아키텍처는 대용량 배치 처리의 높은 정확성과 스트림 처리의 실시간성을 결합하기 위해 데이터 경로를 2개로 나눈 이중 파이프라인 설계다.
> 2. **가치**: 불변(Immutable)의 마스터 데이터를 유지하면서 결함 허용성이 강한 배치 뷰와 저지연 스피드 뷰를 병합해 신뢰성 있는 실시간 서비스를 가능하게 했다.
> 3. **판단 포인트**: 배치용/스트림용 코드를 이중으로 유지보수해야 하는 구조적 한계가 존재하므로, 최신 실무에서는 단일 엔진 통합(카파 아키텍처)과 비교하여 선택해야 한다.

## 출제 의도 및 답안 포인트

| 출제 의도 | 반드시 짚을 핵심 | 감점 회피 포인트 |
|:---|:---|:---|
| 빅데이터 파이프라인의 이중 구조 설계 사상 파악 | Batch, Speed, Serving 3계층 역할 명시 | 람다를 최신 완전무결한 기술로 포장 (한계 명시 필요) |
| 정확성과 실시간성의 트레이드오프 해결 원리 | 불변 마스터 데이터, 실시간 뷰의 주기적 폐기·보정 | Serving 계층의 병합(Merge) 역할 누락 |
| 아키텍처 운영 한계 및 발전 방향 제시 역량 | 동일 로직 이중 구현 유지보수 부담, 카파 아키텍처 전환 | 단일 엔진 서술 금지 (이중 엔진이 람다의 특징) |

> 요약: 정확도와 속도를 위해 두 계층을 분리한 아이디어의 우수성과 그로 인한 이중 코드 관리의 구조적 부채를 함께 짚어야 한다.

## Ⅰ. 개요 및 필요성

- 개요: 빅데이터를 배치(Batch), 스피드(Speed), 서빙(Serving) 레이어로 나누어 처리함으로써 정확성과 실시간성을 동시 만족하는 아키텍처
- 배경: 기존 하둡 배치는 응답 지연(High Latency)이 길고, 초기 스트리밍 시스템은 데이터 유실·중복으로 정확성(Accuracy)이 부족
- 필요성: 장애나 코드 버그 발생 시에도 원본 데이터를 재계산하여 완벽히 복구 가능하면서 실시간 질의응답이 가능한 시스템 요구

---

## Ⅱ. 구조 및 구성요소

```text
Incoming Data -> [Batch Layer: Master Data 보관 & 전체 연산] -> Batch View
      |                                                             |
      +--------> [Speed Layer: 최근 데이터 실시간 연산]      -> Real-time View -> [Serving Layer 병합] -> Query
```

| 구성요소 | 역할 | 특이사항 |
|:---|:---|:---|
| Batch Layer | 불변의 마스터 원본 저장 및 주기적/정확한 대용량 재계산 | Hadoop HDFS, Spark 등 대규모 연산 엔진 적용 |
| Speed Layer | 배치 처리 주기의 틈새를 메우는 최신 데이터 저지연 연산 | 정확도보다 속도 우선, 정산 시 데이터 폐기 |
| Serving Layer | 생성된 Batch View와 Real-time View를 병합해 사용자 질의 응답 | 빠른 조회를 위한 NoSQL (HBase, Cassandra) |

> 요약: 데이터가 입력되면 배치와 스피드 양 갈래로 복제되어, 한쪽은 무겁고 완벽하게, 한쪽은 빠르고 임시로 처리된다.

---

## Ⅲ. 동작원리 및 흐름도

```text
데이터 인입 -> Kafka(분배) -> 1) HDFS 누적 적재 -> 일 단위 Batch 실행 -> 정산 View 생성
                            -> 2) Spark Streaming 연산 -> 초 단위 실시간 View 생성
                               -> Client 요청 시 두 View 결과 Merge 및 반환
```

- 1단계 [분배 및 보관]: 카프카 같은 메시지 브로커가 이벤트를 불변(Append-only) 속성으로 Batch와 Speed 경로로 분배
- 2단계 [배치 정산]: Batch Layer가 모인 데이터를 주 단위/일 단위로 Full-scan 재계산하여 정확도 100%의 인덱스 생성
- 3단계 [실시간 보완]: Speed Layer는 최근 배치 이후에 유입된 데이터만 점진적(Incremental)으로 즉시 연산해 임시 뷰 유지
- 4단계 [서빙 및 보정]: Serving 계층은 요청 시 두 뷰를 합산하며, 새 배치가 완료되면 구식 스피드 뷰를 폐기·교체

> 요약: 완벽한 과거 데이터(배치)에 지연된 최신 데이터(스피드)를 얹어 보여주고, 배치가 끝나면 스피드를 초기화하는 방식이다.

---

## Ⅳ. 특징
- [결함 허용성(Fault Tolerance)]: 스피드 레이어 장애나 부정확한 결과 발생 시 배치 레이어의 원본 데이터로 언제든 재복구 가능
- [실시간 응답성]: 배치 마감을 기다릴 필요 없이 스피드 레이어 뷰를 통해 수 초 내의 최신 상태 실시간 서빙
- [유지보수 오버헤드]: 하나의 비즈니스 로직을 배치용(예: Spark)과 스트리밍용(예: Storm) 2가지 분산 프레임워크 언어로 이중 작성·관리해야 함

> 요약: 무결성과 속도를 맞교환하지 않고 둘 다 쟁취한 대신, 아키텍처 복잡성과 개발 비용이라는 기술 부채를 떠안았다.

---

## Ⅴ. 심화 비교 및 적용 판단

| 비교 축 | 본 키워드 (Lambda) | 대안 (Kappa) | 선택 기준 |
|:---|:---|:---|:---|
| 처리 경로 | 2-Track (Batch + Speed) | 1-Track (Speed 단일) | 이중 코드 유지보수 여력 |
| 데이터 저장 | HDFS 같은 파일 스토리지 위주 | Kafka 등 스트리밍 버퍼 위주 | 마스터 데이터의 영구 보존 방식 |
| 시스템 복잡도 | 높음 (다기종 프레임워크 혼재) | 낮음 (단일 프레임워크 통일) | 아키텍처 설계 단순화 요구 |

> 요약: 람다는 과도기적 완성형 설계였으며, 최근 스트림 기술 발전으로 인해 복잡도를 낮춘 카파(Kappa)로 무게 중심이 이동했다.

**리스크·대응 (기본은 불릿):**
- [이중 코드 관리 부담]: 비즈니스 로직 수정 시 배치와 스피드 코드 양쪽을 동기화해야 하는 휴먼 에러 증가 → Spark 같은 통합 엔진을 배치/스트림 양쪽에 사용하여 코드베이스 단일화 유도
- [서빙 레이어 병합 부하]: 뷰를 병합하는 로직 탓에 쿼리 응답(Read) 지연 발생 → 사전에 NoSQL 카운터 컬럼이나 인메모리(Redis)에서 원자적 증감 처리 수행 (지표: API 응답 지연 시간)

**도입 후 점검 지표 (기본은 불릿):**
- 성능/효율: 최신 데이터 반영부터 서빙 뷰 노출까지의 End-to-End 지연 시간 5초 이내 — 파이프라인 트레이싱
- 품질/운영: 배치 뷰와 스피드 뷰 간의 데이터 집계 오차율 0% 수렴(일 단위 정산 후) — 데이터 정합성 검증 배치 실행

## Ⅵ. 실무 적용 및 결론

**적용 방안 3개:**
1. 프레임워크 통일화: 람다 구조를 유지하되 Batch와 Speed 처리 엔진을 Spark API로 통일하여 이중 코드 작성 부담 완화
2. 데이터 복구 정책: 인프라 장애나 로직 오류 시 마스터 데이터를 재실행(Re-compute)하여 전체 뷰를 복원하는 장애 복구 플레이북 마련
3. 뷰 격리 및 GC(가비지 컬렉션): 서빙 레이어 내 임시 스피드 뷰를 독립된 테이블/키스페이스로 분리하고 만료된 데이터 자동 삭제(TTL) 설정

**결론 (2줄):**
- 기술사 판단: 람다 아키텍처는 데이터 파이프라인의 불변성과 무결성 개념을 확립했으나, 다기종 엔진 유지보수의 복잡도가 높아 기술 부채로 전락할 위험이 있다.
- 향후 방향: Flink, Spark Structured Streaming 같이 스트림 처리가 배치 처리 수준의 정합성을 보장(Exactly-Once)하게 되면서 카파(Kappa) 아키텍처로 대체되고 있다.
