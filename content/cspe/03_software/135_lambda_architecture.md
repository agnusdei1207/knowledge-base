## 핵심 인사이트 (3줄 요약)
- 빅데이터 시스템에서 "대규모 과거 데이터를 완벽하게 집계하는 **배치(Batch) 레이어**"와 "지금 막 들어오는 데이터를 0.1초 만에 보여주는 **스피드(Speed) 레이어**"를 두 갈래(λ)로 병렬 운영하는 아키텍처 설계 패턴.
- 배치가 도는 데 12시간이 걸리는 동안 '오늘 하루 동안의 최신 데이터'를 볼 수 없는 치명적인 정보 공백(Blind Spot)을 메우기 위해, 스피드 레이어(실시간 스트리밍)가 땜빵을 쳐주는 것이 핵심 원리임.
- 완벽한 데이터 뷰를 제공하지만, 똑같은 분석 로직을 배치용(Hadoop)과 실시간용(Storm/Spark) 코드로 **두 번씩 짜고 두 개의 시스템을 관리해야 하는 '코드/운영 중복의 지옥'**이라는 치명적 단점이 있음.

## Ⅰ. 개요 및 필요성
- **개요**: 네이선 마츠(Nathan Marz)가 제안한 데이터 처리 아키텍처로, 데이터를 배치 레이어, 스피드 레이어, 서빙 레이어로 분리하여 처리 및 쿼리하는 구조.
- **필요성**: 기업은 10년 치 판매 통계(배치 분석, 정확도 100%)도 보고 싶고, 동시에 방금 전 1분 동안 터진 블랙프라이데이 최신 트래픽(실시간 분석, 속도 우선)도 보고 싶어 함. 하지만 하둡(Hadoop)은 어제 데이터까지만 계산되어 있고 오늘은 아직 계산이 안 끝남. "정확한 옛날 데이터 + 방금 들어온 실시간 데이터"를 합쳐서 100% 완벽한 현재 뷰를 볼 방법이 절실했음.
---
## Ⅱ. 아키텍처 및 핵심 원리
- **람다 아키텍처의 3대 레이어 (핵심 구조)**:
  1. **배치 레이어 (Batch Layer)**:
     - 원본 데이터(Immutable Master Data)를 전체 저장(HDFS, S3).
     - 매일 밤마다 엄청난 컴퓨팅(Spark, Hadoop)을 돌려 과거부터 어제까지의 완벽하고 정확한 통계 데이터(Batch View)를 만들어 냄.
  2. **스피드 레이어 (Speed Layer)**:
     - 어젯밤 배치 작업이 끝난 이후부터 '지금 당장'까지 들어오는 실시간 데이터만 잽싸게(근사치로) 계산함 (Kafka + Spark Streaming).
     - 데이터가 유실되거나 꼬일 수 있지만(정확도 낮음), 응답 속도(Latency)가 생명임 (Real-time View).
  3. **서빙 레이어 (Serving Layer)**:
     - 사용자가 화면에서 쿼리를 날리면, 서빙 레이어가 **[배치 뷰(어제까지의 완벽한 통계) + 실시간 뷰(오늘 갓 들어온 통계)]**를 즉시 `MERGE` 해서 최종적으로 가장 최신화된 화면을 보여줌.

```text
[ 람다 아키텍처의 동작 흐름 (갈래길: λ 모양) ]

 (이벤트 발생: 앱 클릭 로그) 
       ⬇️ (데이터가 두 갈래로 찢어짐!)
 
 🔄 [ 길 1: 배치 레이어 (Hadoop) ] ➡️ (어제까지 1억 건 로그 통계 완벽 계산 중... 10시간 소요) ➡️ [ 배치 뷰 ]
 
 ⚡ [ 길 2: 스피드 레이어 (Spark Streaming) ] ➡️ (방금 클릭한 5건 즉시 계산! 1초 소요) ➡️ [ 실시간 뷰 ]
 
       ⬇️ (클라이언트 화면 호출 시)
 
 🤝 [ 서빙 레이어 ] : "어제까지의 완벽한 1억 건 통계 + 방금 터진 5건 = 1억 5건!" 
 ➡️ (고객에게 완벽한 실시간 통계 제공)
 * 중요: 내일 밤에 배치 레이어가 오늘 5건까지 포함해서 완벽히 재계산하면, 스피드 레이어의 5건 통계는 폐기(삭제)됨!
```

## Ⅲ. 비교 및 연결
| 구분 | 전통적 배치 처리 (DW) | 람다(Lambda) 아키텍처 | 카파(Kappa) 아키텍처 |
|---|---|---|---|
| **처리 지연(Latency)**| 수 시간 ~ 1일 (최신 데이터 맹점) | **실시간 (Batch + Speed 결합)** | 실시간 (Speed 단일 엔진) |
| **코드베이스/유지보수**| 단일 엔진으로 쉬움 | **엔진이 2개(Hadoop, Streaming)라 코드를 두 번 짜야 하는 유지보수 지옥** | 단일 스트리밍 엔진으로 통일 |
| **데이터 정확성** | 100% (완벽함) | **배치가 덮어쓰기 전까지는 실시간 레이어의 약간의 오차 존재** | 이벤트 순서 꼬이면 복구 어려움 |

## Ⅳ. 실무 적용 및 기술사 판단
- **마스터 데이터 불변성 (Immutable Data)**: 람다 아키텍처를 설계하는 기술사가 반드시 지켜야 할 원칙은 "들어온 원시(Raw) 데이터는 절대 Update하거나 Delete 하지 않고, 100% HDFS나 S3에 차곡차곡 Append-only로 쌓아둔다"는 것임. 그래야 나중에 스피드 레이어에서 버그가 터져서 실시간 통계가 쓰레기 값이 되어도, 밤에 도는 배치 레이어가 원본 데이터를 밀고 다시 계산해서 모든 오류를 깨끗하게 자정(Self-healing)할 수 있기 때문임.
- **운영 지옥과 TCO 상승의 함정**: 람다 아키텍처는 개념적으로는 아름답지만, 실제 기업(우아한형제들, 카카오 등)이 도입해 보니 백엔드 개발자들이 "평균 매출 계산" 로직을 배치용(Spark SQL)으로 한 번 짜고, 실시간용(Spark Streaming)으로 또 한 번 짜야 하는 끔찍한 고통(로직 불일치 버그)을 겪음. 결국 이 고통을 해결하기 위해 엔진을 1개로 합치는 카파(Kappa) 아키텍처로 진화하게 됨.
---
## Ⅴ. 기대효과 및 결론
- "방대한 데이터를 정확하게 처리해야 한다(Hadoop)"는 요구와 "최신 트렌드를 1초 만에 모니터링해야 한다(Streaming)"는 상충하는 두 비즈니스 요구사항을 거대한 시스템의 이원화를 통해 무식하지만 확실하게 풀어낸 빅데이터 설계의 바이블.
- 비록 운영 복잡도 때문에 트렌드에서 내려오고 있지만, **'배치 뷰와 실시간 뷰의 결합을 통한 정보 공백 최소화'**라는 철학은 데이터 엔지니어링 역사에 영원히 남을 이정표임.

### 👶 어린이를 위한 3줄 비유 설명
1. **배치 레이어**는 꼼꼼한 회계사예요. 어제까지 번 돈을 10원짜리 하나까지 100% 완벽하게 계산해 주는데, 너무 오래 걸려요.
2. **스피드 레이어**는 눈치 빠른 알바생이에요. 오늘 아침부터 번 돈을 대충 훑어보고 "사장님, 오늘 한 10만 원쯤 벌었어요!"라고 1초 만에 알려주죠.
3. **서빙 레이어(람다 아키텍처)**는 사장님이에요! 회계사가 계산한 어제까지 돈(100만 원)에 알바생이 방금 알려준 오늘 돈(10만 원)을 더해서 "내 전 재산은 110만 원이구나!"라고 똑똑하게 파악한답니다!
