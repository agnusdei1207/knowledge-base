## 미리 알고가기

- 배치 계층은 전체 데이터를 기준으로 정확한 결과를 다시 계산하는 계층임
- 속도 계층은 최신 이벤트를 빠르게 반영하는 실시간 계층임
- 서빙 계층은 배치 결과와 실시간 결과를 합쳐 사용자에게 제공하는 계층임

## Ⅰ. 개요

- **정의/개념**: 람다 아키텍처는 대용량 데이터 처리에서 정확한 배치 계산과 빠른 실시간 반영을 동시에 만족시키기 위해 배치 계층과 속도 계층과 서빙 계층을 함께 두는 데이터 처리 구조임
- **배경/필요성**: 배치 처리만으로는 최신 반영이 느리고 실시간 처리만으로는 전체 재계산과 정합성 유지가 어려워 두 요구를 함께 맞추는 구조가 필요해짐

## Ⅱ. 특징

- 과거 전체 데이터는 배치 계층에서 정확하게 다시 계산함
- 최신 이벤트는 속도 계층에서 증분 계산해 배치 재계산 전 임시 결과에 반영함
- 두 계층 결과를 서빙 계층이 합쳐 사용자에게 제공함
- 같은 로직을 배치와 실시간에 이중 구현하기 쉬워 운영 복잡도가 커질 수 있음

## Ⅲ. 종류 및 비교

| 판단 기준 | 람다 아키텍처 | 카파 아키텍처 |
|:---|:---|:---|
| 처리 계층 | 배치와 실시간을 분리함 | 스트림 중심으로 단순화함 |
| 코드·결과 경로 | batch와 speed 로직을 각각 구현하고 serving에서 병합 | 단일 stream 처리 로직으로 과거·신규 이벤트 갱신 |
| 운영 부담 | 이중 파이프라인 관리가 필요함 | 스트림 엔진 의존이 큼 |
| 대표 환경 | 원본 전체 재계산과 최신 증분 결과가 모두 필요한 분석 | event replay와 stream 상태로 재계산 가능한 처리 |

## Ⅳ. 구성요소 및 구조

| 구성요소 | 설명 |
|:---|:---|
| Batch Layer | 전체 데이터를 보관하고 정확한 결과를 재계산함 |
| Speed Layer | 최신 이벤트를 빠르게 반영해 지연을 줄임 |
| Serving Layer | 두 결과를 병합해 조회용 모델을 제공함 |
| Message / Storage | 이벤트 수집과 원본 데이터 보관을 담당함 |
| Query Interface | 사용자나 서비스가 결과를 읽는 진입점임 |

```text
원본 데이터 -> Batch Layer -> Serving Layer
          \-> Speed Layer ---^
```

## Ⅴ. 원리 및 절차 흐름도

```text
이벤트 수집 -> 실시간 반영 -> 주기적 전체 재계산 -> 결과 병합 -> 조회 제공
```

1. **이벤트 수집**: 원본 이벤트를 저장소와 메시지 경로로 받음
2. **실시간 반영**: 속도 계층이 최신 데이터를 즉시 계산함
3. **전체 재계산**: 배치 계층이 전체 데이터를 기준으로 정확한 결과를 만듦
4. **결과 병합**: 서빙 계층이 두 결과를 합쳐 제공함
5. **조회 제공**: 사용자와 서비스가 최신 결과를 읽음

## Ⅵ. 실무 적용 및 유의점

1. 대시보드와 실시간 지표는 람다 구조가 유용하지만 배치와 실시간 로직이 어긋나면 값이 달라지므로 공통 계산 규칙을 맞추고 계층 간 결과 차이와 재계산 반영 지연과 운영 오류 건수로 확인함
2. 스트림 엔진 성숙도가 높지 않은 조직은 람다가 현실적일 수 있지만 파이프라인이 둘로 늘어나는 부담이 크므로 유지 인력과 장애 대응 시간과 이중 파이프라인 장애 건수로 확인함

## Ⅶ. 결론

- 람다 아키텍처는 정확성과 최신성을 함께 잡는 구조이지만 이중 구현 부담을 감당할 수 있는지 먼저 따져야 함
