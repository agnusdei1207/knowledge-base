## 핵심 인사이트 (3줄 요약)
- 낡고 느린 리눅스의 `iptables`를 버리고, **혁신적인 eBPF 기술을 기반으로 만든 차세대 쿠버네티스 CNI(네트워크 플러그인)의 제왕**.
- 패킷이 노드에 도착하자마자 커널 밑바닥에서 eBPF 코드가 빛의 속도로 라우팅과 방화벽을 처리해 버려서, K8s 클러스터의 네트워크 속도와 CPU 효율을 극한으로 끌어올림.
- 단순한 통신 연결(CNI)을 넘어, 파드 옆에 무거운 프록시(Envoy)를 붙이지 않고도 암호화와 L7 라우팅을 수행하는 **사이드카리스 서비스 메시(Sidecarless Service Mesh)**의 시대를 연 주인공임.

## Ⅰ. 개요 및 필요성
- **개요**: eBPF 기술을 기반으로 클라우드 네이티브 환경(K8s)의 네트워크 연결, 보안, 관측성을 제공하는 오픈소스 소프트웨어. (현재 CNCF 졸업 프로젝트).
- **필요성**: 기존 쿠버네티스의 통신은 `iptables`라는 리눅스의 구형 방화벽 기술에 의존했음. 파드가 1만 개면 규칙이 10만 줄이 넘어가서 CPU가 뻗어버림. **"앱 컨테이너가 아무리 가벼워도 네트워크가 병목이면 무슨 소용인가? 가장 밑바닥인 커널 단에서 트래픽을 빛의 속도로 찢어줄 새로운 네트워크 아키텍처가 필요하다!"**라는 니즈가 터지며 대세로 등극함.
---
## Ⅱ. 아키텍처 및 핵심 원리
- **1. eBPF 기반의 패킷 가로채기 (Bypassing Netfilter)**:
  - 기존 네트워크는 랜카드 ➡️ `iptables` (규칙 10만 개 검색) ➡️ IP 라우팅 ➡️ 파드 도착이라는 긴 여정을 거침.
  - Cilium은 랜카드에 패킷이 닿는 순간(XDP 단계) eBPF 프로그램이 낚아채서, 해시맵을 딱 한 번(O(1)) 조회한 뒤 곧바로 타겟 파드에 꽂아버림. 엄청난 속도 향상.
- **2. 쿠버네티스 메타데이터 인지 (Identity-based Security)**:
  - `iptables`는 IP 주소(예: `10.0.0.5`)로만 방화벽을 침. 파드가 죽고 IP가 바뀌면 룰 업데이트하느라 클러스터가 렉이 걸림.
  - Cilium은 파드의 라벨(`role=frontend`)에 고유 ID를 부여함. IP가 수백 번 바뀌어도 "프론트엔드 아이디는 백엔드 아이디만 찌를 수 있다"는 보안 정책이 흔들림 없이 빛의 속도로 적용됨.
- **3. 허블 (Hubble) - 초정밀 관측성**:
  - Cilium 위에 얹혀서 돌아가는 모니터링 툴.
  - eBPF가 커널을 꿰뚫어 보고 있으므로, 어떤 파드가 어떤 파드에게 DNS 쿼리를 날렸고 TCP 연결이 몇 초 걸렸는지, 앱 코드를 한 줄도 수정하지 않고 지도(Service Map)로 그려냄.

```text
[ 기존 Calico(iptables) vs 차세대 Cilium(eBPF) 아키텍처 비교 ]

 🐢 [ 기존 CNI (Calico / kube-proxy) ]
 파드 A ➡️ (Host OS 진입) ➡️ iptables (10만 줄 룰 검사: "통과? 차단? 어디로?") ➡️ 파드 B
 ❗ 문제점: 룰이 많아질수록 O(N)으로 느려짐. CPU 자원 엄청 먹음.

 🚀 [ 차세대 CNI (Cilium) ]
 파드 A ➡️ (Host 커널 진입 즉시 eBPF 훅 발동!) ➡️ 해시맵 조회 (O(1) 속도) ➡️ 파드 B
 ❗ 장점: 룰이 100만 개여도 속도 저하 없음. kube-proxy를 아예 삭제해 버림(Kube-proxy Replacement).
```

## Ⅲ. 비교 및 연결
| 기능 | 기존 Service Mesh (Istio) | Cilium 기반 Service Mesh |
|---|---|---|
| **아키텍처** | 모든 파드 옆에 **사이드카 프록시(Envoy)** 1개씩 주입 | 사이드카 없이 **노드(서버) 커널의 eBPF**에서 한 번에 통제 |
| **자원 소모 (Overhead)**| 파드 1,000개면 프록시 1,000개 띄워야 함 (메모리 낭비) | **메모리 절감 극대화 (커널 레벨 처리)** |
| **통신 홉 (Hop)** | 파드 ➡️ 사이드카 ➡️ 사이드카 ➡️ 파드 (복잡함) | 파드 ➡️ (커널 eBPF) ➡️ 파드 (단순, 초고속) |
| **최신 동향** | 여전히 L7의 복잡한 통제에 강점 | **사이드카리스(Sidecar-less) 트렌드의 선두주자** |
---
## Ⅳ. 실무 적용 및 기술사 판단
- **Kube-proxy 완전 대체 (Kube-proxy Replacement)**: 실무에서 클러스터가 커지면 쿠버네티스의 기본 네트워킹 컴포넌트인 `kube-proxy`가 병목의 원흉이 됨. 기술사는 쿠버네티스를 구축할 때 아예 처음부터 `kube-proxy`를 끄고(Disable), 그 역할을 Cilium의 eBPF가 10배 빠른 속도로 전담하게 만드는 아키텍처를 적용해야 대규모 트래픽을 견딜 수 있음.
- **L7 네트워크 정책의 선언적 통제**: 기존 CNI(Calico)는 "포트 80번 허용" 같은 L4 수준의 방화벽만 칠 수 있었음. Cilium은 eBPF를 활용해 HTTP 헤더나 URL 경로까지 까볼 수 있음. "개발팀 파드는 `/public` URL만 GET 방식으로 찌를 수 있다"는 정교한 L7 마이크로 세그멘테이션을 NetworkPolicy YAML 파일 한 장으로 사내망에 강제할 수 있는 강력한 무기임.
---
## Ⅴ. 기대효과 및 결론
- 클라우드 네이티브 네트워크의 고질병이었던 속도 저하와 리소스 낭비를 '커널 프로그래밍(eBPF)'이라는 발상의 전환으로 완벽하게 치료함.
- CNI(통신) ➡️ L7 방화벽(보안) ➡️ 허블(관측성) ➡️ 사이드카 없는 서비스 메시까지 한방에 해결해 주는 통합 네트워크 OS로 자리 잡으며, AWS와 구글(GKE)의 기본 CNI 엔진으로 채택되는 등 K8s 네트워크의 천하를 통일하고 있음.
