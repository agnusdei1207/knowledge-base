## Ⅰ. 개요
- **정의**: 소프트웨어를 기획부터 폐기까지 체계적으로 관리하는 생명주기 프레임워크
- **배경/필요성**: 개발 과정의 산출물·일정·품질을 예측 가능하게 통제할 표준 절차가 필요함
- **비유**: 건물 신축 시 설계-시공-준공-유지보수의 단계를 정해놓는 것과 유사함

| 출제 의도 | 반드시 짚을 핵심 | 감점 회피 포인트 |
|:---|:---|:---|
| 생명주기 단계별 역할과 산출물 이해 | 각 단계의 입력-활동-산출물 | 특정 모델(폭포수 등)과 SDLC 자체를 혼동 금지 |

> 요약: 소프트웨어 개발 전 과정을 단계별로 정의하고 관리하는 표준 프레임워크임

## Ⅱ. 구성요소
```text
요구분석 -> 설계 -> 구현 -> 테스트 -> 배포 -> 운영/유지보수
```

| 구성요소 | 설명 | 비유 |
|:---|:---|:---|
| 요구분석 | 이해관계자 요구를 수집·정제하여 명세서로 작성함 | 건축주 요구사항 청취 |
| 설계 | 아키텍처·인터페이스·DB 구조를 결정함 | 설계도면 작성 |
| 구현 | 설계를 코드로 변환하고 단위 테스트를 수행함 | 실제 시공 |
| 테스트 | 통합·시스템·인수 테스트로 결함을 검출함 | 준공 검사 |
| 배포 | 운영 환경에 릴리스하고 사용자 교육을 수행함 | 입주 및 인수인계 |
| 운영/유지보수 | 장애 대응, 기능 개선, 패치를 지속 수행함 | 건물 관리 및 보수 |

> 요약: 요구분석부터 유지보수까지 6개 핵심 활동으로 구성됨

## Ⅲ. 절차
```text
요구분석 -> 설계 -> 구현 -> 테스트 -> 배포/운영
```
- 1단계: 이해관계자 인터뷰와 문서 분석으로 요구사항을 도출하고 SRS를 작성함
- 2단계: SRS 기반으로 아키텍처 설계서와 상세 설계서를 작성함
- 3단계: 코딩 표준에 따라 구현하고 코드 리뷰·단위 테스트를 수행함
- 4단계: 통합-시스템-인수 테스트 후 결함을 수정하고 릴리스를 승인함

> 요약: SRS 작성 → 설계 → 구현/리뷰 → 테스트/릴리스 순으로 진행함

## Ⅳ. 문제점
- 요구사항 변동: 후반부 변경 시 재작업 비용이 기하급수로 증가함
- 단계 간 단절: 산출물 중심 인수인계 시 암묵지가 유실됨
- 측정 부재: 진척률을 정량 측정하지 않으면 일정 지연을 조기에 감지하지 못함

> 요약: 요구변동 비용, 암묵지 유실, 진척 측정 부재가 주요 문제임

## Ⅴ. 개선방안
1. 단기: 변경통제위원회(CCB)를 운영하여 요구변동의 영향을 사전 평가함
2. 중기: 단계 간 겹침(오버랩) 허용과 지속적 피드백 루프로 암묵지 유실을 방지함
3. 장기: EVM·번다운 차트 등 정량 지표를 도입하여 진척을 실시간 추적함

> 요약: CCB 운영, 피드백 루프, 정량 지표 도입으로 개선 가능함

## Ⅵ. 전망
- 발전 방향: DevOps·CI/CD와 결합하여 단계 경계가 연속적 흐름으로 전환되는 추세임
- 기술사적 판단: 모델에 관계없이 SDLC의 6대 활동 자체는 변하지 않는 기본 원리임
- 기술사 제언: 프로젝트 특성에 맞는 SDLC 모델 선정 기준을 수립하는 것이 필요함
