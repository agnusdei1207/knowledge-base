# 📖 【암기용】 개념 완전 이해

> 목적: SDLC를 처음 보는 사람도 완전한 흐름과 그 안에 등장하는 모든 용어를 이해하게 만든다. 시험 답안 양식이 아니라, 이해를 위한 친절한 설명이다.

## 한눈에
- **개요**: SDLC(Software Development Lifecycle)는 소프트웨어를 기획부터 폐기까지 통제하는 **생명주기 프로세스 모델**이며, 요구사항·설계·구현·테스트·배포·유지보수 각 단계에 산출물과 **품질 게이트**를 두어 결함과 비용을 통제하는 **소프트웨어 공학 관리 체계**다.
- **왜 필요한가**: 결함을 늦게 발견할수록 수정 비용이 기하급수로 커진다. 배리 뵘(Barry Boehm)이 제시한 상대 비용 배율에 따르면 요구사항 단계에서 잡는 결함의 수정 비용을 1이라 할 때, 설계 단계는 약 5배, 구현 단계는 약 10배, 테스트 단계는 약 20배, 이미 운영 중인 시스템에서는 약 100배로 뛴다. SDLC는 이 비용 곡선을 초기 단계로 끌어당기기 위한 절차다.
- **핵심 직관**: 집을 지을 때 설계도-인허가-기초공사-골조-마감-준공검사 순서를 건너뛸 수 없듯, 소프트웨어도 각 단계 산출물이 다음 단계 입력이 되고 검증(게이트)을 통과해야만 다음 단계로 넘어간다.

## 핵심 용어 정리 (내부에 등장하는 것들)

| 용어 | 의미 | 비유 |
|:---|:---|:---|
| SDLC | 기획~유지보수 전 과정을 단계·산출물·게이트로 정의한 상위 프레임 | 이 표 전체가 속한 큰 우산 |
| 품질 게이트(Quality Gate) | 한 단계 산출물이 기준을 만족해야 다음 단계 진행을 허용하는 승인 지점 | 공항 보안검색대 — 통과해야 다음 구역 입장 |
| 요구사항 기준선(Baseline) | 승인 후 임의로 못 바꾸게 고정한 요구사항 버전 | 계약서 서명본 |
| V-Model | 개발 단계(좌변)와 테스트 단계(우변)를 1:1로 대응시켜 추적성을 만드는 모델 | 알파벳 V자로 접은 개발-검증 짝짓기 |
| RTM(요구사항 추적표) | 요구사항 ID-설계-코드-테스트 케이스를 한 행으로 연결한 표 | 택배 송장 번호로 전 배송단계를 추적하는 것 |
| CCB(변경통제위원회) | 기준선 확정 후 들어오는 변경 요청을 심사·승인하는 조직 | 설계 변경 신청을 심사하는 인허가 위원회 |
| DevOps | 배포 이후 운영 데이터를 다시 계획 단계로 되먹임하는 개발-운영 통합 문화 | 운행 후 정비 기록을 다음 설계에 반영하는 피드백 루프 |
| ALM(Application Lifecycle Management) | 요구사항·코드·빌드·테스트·릴리스를 도구로 연결해 SDLC를 자동 추적하는 관리 체계 | RTM을 손으로 안 적고 도구가 자동으로 이어주는 버전 |

## 깊이 이해

### 왜 단계를 쪼개는가 — 비용 곡선으로 이해
- 소프트웨어는 눈에 안 보이는 산출물이라 결함이 어디서 생겼는지 늦게 발견하기 쉽다. 위의 1:5:10:20:100 비용 배율이 SDLC가 존재하는 이유다. 요구사항 단계에서 "이 필드는 필수인가 선택인가"를 확정하는 비용은 1이지만, 이미 배포된 시스템에서 같은 문제를 고치려면 코드 수정·재테스트·재배포·데이터 마이그레이션이 겹쳐 100배가 든다.
- 그래서 SDLC는 각 단계 끝에 품질 게이트를 두어 문제를 최대한 이른 단계에서 걸러낸다.

### 7단계 흐름과 각 단계가 만드는 산출물
- **기획(Planning)**: 범위·일정·예산을 정한다. 산출물은 WBS(작업분해구조), 일정 기준선.
- **분석(Analysis)**: 기능·비기능 요구사항을 식별한다. 산출물은 SRS(요구사항명세서), 요구사항 ID(예: `REQ-PAY-012`).
- **설계(Design)**: 구조·데이터·인터페이스를 정한다. 산출물은 아키텍처 문서, API 명세.
- **구현(Implementation)**: 코드를 작성한다. 산출물은 소스 코드, 코드 리뷰 기록.
- **테스트(Test)**: 단위-통합-시스템-인수 테스트로 결함을 찾는다. 산출물은 테스트 케이스(예: `TC-PAY-045`), 결함 리포트.
- **배포(Deploy)**: 운영 환경에 반영한다. 산출물은 릴리스 노트(예: `v2.3.1`), 롤백 계획.
- **유지보수(Maintenance)**: 운영 중 결함 수정·개선을 반영하고 다음 기획으로 피드백한다.
- 이 7단계는 폭포수든 애자일이든 공통으로 존재한다. 차이는 이 단계를 한 번에 순차로 도는지(폭포수), 짧은 주기로 반복하는지(애자일)일 뿐이다.

### V-Model로 추적성을 만드는 원리 — 예로 확인
- V자의 왼쪽 내림변은 요구사항→설계→상세설계→구현으로 내려가고, 오른쪽 오름변은 구현→단위테스트→통합테스트→시스템테스트→인수테스트로 올라간다. 왼쪽 각 단계는 오른쪽의 같은 높이 테스트 단계와 짝을 이룬다 — 요구사항은 인수테스트와, 아키텍처 설계는 시스템테스트와, 상세설계는 통합테스트와 대응한다.
- 예: `REQ-PAY-012`(결제 승인 요구사항)를 설계 시 결제 모듈 인터페이스에 반영하고, 이 인터페이스를 검증하는 `TC-PAY-045`를 미리 정의해 두면, 결제 승인 로직이 바뀔 때 이 요구사항과 연결된 테스트 케이스가 몇 개인지 RTM에서 즉시 확인할 수 있다. "RTM 매핑률 100%"란 모든 요구사항 행에 최소 1개의 테스트 케이스가 연결되어 있다는 뜻이다.

### 언제 어떤 모델을 쓰는가 — 판별 원리
- 요구사항 변경 빈도, 규제 강도, 실패 시 손실 규모 3가지로 판별한다.
- 항공 관제, 금융 정산처럼 요구사항이 법·물리 제약으로 고정되고 오류 허용치가 0에 가까우면 V-Model/폭포수로 기준선을 먼저 굳힌다.
- 커머스 UI처럼 요구사항이 사용자 반응에 따라 매주 바뀌고 실패해도 되돌릴 수 있으면 짧은 반복 주기로 SDLC 7단계를 계속 도는 애자일/DevOps를 쓴다.
- 실무에서는 인프라·보안처럼 바꾸기 어려운 뼈대는 폭포수로 먼저 고정하고, 세부 기능은 애자일로 도는 하이브리드도 흔하다.

### 흔한 오해
- SDLC는 폭포수의 다른 이름이 아니다. "기획-분석-설계-구현-테스트-배포-유지보수"라는 7단계 뼈대 자체는 모델과 무관한 공통 골격이고, 폭포수·V-Model·반복형·애자일·DevOps는 이 뼈대를 도는 순서와 주기만 다르게 정한 것이다.

## 연결 개념
- V-Model: SDLC 7단계 중 설계와 테스트를 1:1로 대응시켜 추적성을 만드는 세부 모델
- 폭포수 vs 애자일(033): SDLC 7단계를 한 번에 순차로 도는지, 짧은 주기로 반복하는지의 실행 전략 비교
- DevOps: 배포·운영 피드백을 SDLC 계획 단계로 되돌리는 운영 통합 모델

# 📝 【답안용】 시험 답안 템플릿

> 목적: 시험장에서 25분에 그대로 쓰는 답안 양식. 작성방식(추상표현 금지·수치·도식·문제유형 전환)을 엄격히 지킨다.
> 핵심: SDLC는 단계 암기가 아니라 요구사항 변동, 품질 게이트, 납기 리스크를 추적성으로 통제하는 관리 프레임이다.

## 핵심 인사이트 (3줄 요약)

> 1. **본질**: SDLC는 소프트웨어 기획부터 유지보수까지 단계·산출물·검증 기준을 연결하는 생명주기 통제 체계이다.
> 2. **가치**: 요구사항-설계-코드-테스트-릴리스 추적성으로 변경 영향 분석 시간을 단축하고 결함 유출률을 낮춘다.
> 3. **판단 포인트**: 요구사항 안정성, 규제 감사, 릴리스 빈도에 따라 Waterfall, V-Model, Iterative, DevOps 적용 범위를 조정해야 한다.

## 출제 의도 및 답안 포인트

| 출제 의도 | 반드시 짚을 핵심 | 감점 회피 포인트 |
|:---|:---|:---|
| 개발 프로세스 전 단계 이해 확인 | planning, analysis, design, implementation, test, deploy, maintenance | 단계 이름만 나열하고 산출물·검증 기준 누락 |
| 품질 게이트와 추적성 판단 확인 | V-Model, RTM, 승인 기준, 결함 유출률 | 문서화와 개발 속도를 단순 대립으로 설명 |
| DevOps 전환 관점 확인 | CI/CD, 운영 피드백, 릴리스 자동화, MTTR | SDLC를 폭포수와 동일시 |

> 요약: SDLC 문제는 단계 순서보다 변경·품질·운영 피드백을 어떤 지표로 통제하는지 묻는다.

## Ⅰ. 개요 및 필요성

- 개요: 소프트웨어 생명주기 통제 체계
- 배경: 요구사항 누락은 설계·구현·테스트 단계로 갈수록 재작업 범위를 키우고, 산출물 기준이 없으면 승인 지연과 범위 변경이 반복됨.
- 필요성: 요구사항 명세서, 설계서, 테스트 케이스, RTM으로 단계별 승인 기준과 결함밀도, 일정 편차, 변경 요청 건수를 추적해야 함.

---

## Ⅱ. 구조 및 구성요소

```text
Business Goal -> Planning -> Analysis -> Design -> Implementation
              -> Test -> Deploy -> Maintenance -> Feedback
              +-> Quality Gate / Traceability / Change Control
```

| 구성요소 | 역할 | 산출물·지표 |
|:---|:---|:---|
| Planning | 범위·일정·예산 기준 수립 | WBS, 일정 기준선, 리스크 등록부 |
| Analysis | 기능·비기능 요구사항 식별 | SRS, 요구사항 ID, 수용 기준 |
| Design | 구조·데이터·인터페이스 설계 | Architecture, UML, API 명세 |
| Test/Deploy | 결함 검증과 운영 반영 | Test Report, Release Note, rollback plan |

> 요약: SDLC는 단계별 산출물을 품질 게이트로 승인하고, 요구사항 ID로 변경 영향 범위를 추적한다.

---

## Ⅲ. 동작원리 및 흐름도

```text
요구 식별 -> 요구사항 기준선 -> 설계 분해 -> 구현 커밋
-> 테스트 검증 -> 릴리스 승인 -> 운영 모니터링 -> 변경 요청 환류
```

| 단계 | 처리 내용 | 검증 기준 |
|:---:|:---|:---|
| 1 | 사업 목표와 범위 확정 | 승인된 charter, 범위 변경률 |
| 2 | 요구사항 분석 및 기준선 설정 | SRS 승인, RTM 100% 매핑 |
| 3 | 설계·구현·코드 리뷰 수행 | 코드 리뷰 커버리지 90% 이상 |
| 4 | 단위·통합·인수 테스트 실행 | 치명 결함 0건, 테스트 통과율 95% 이상 |
| 5 | 배포 후 운영 피드백 반영 | MTTR, 변경 실패율, 고객 이슈 건수 |

> 요약: SDLC는 요구사항 기준선을 테스트·릴리스까지 연결하고 운영 피드백을 다음 계획에 반영하는 순환 구조이다.

## Ⅳ. 특징

| 구분 | 전통적 임기응변 개발 | SDLC 적용 | 수치·판단 포인트 |
|:---|:---|:---|:---|
| 요구사항 | 구두 요청 중심 | SRS, user story, acceptance criteria | RTM 매핑률 100% |
| 품질 통제 | 마지막 테스트 집중 | 단계별 review, V-Model test 대응 | 결함 유출률 2% 이하 |
| 변경 관리 | 담당자 기억 의존 | CCB, baseline, impact analysis | 변경 승인 리드타임 2일 이내 |
| 운영 연계 | 배포 후 분리 | DevOps feedback, incident postmortem | MTTR 30분 이하 |

> 요약: SDLC의 효과는 문서량이 아니라 추적성, 게이트 승인, 운영 피드백 지표로 판단한다.

## Ⅴ. 심화 비교 및 적용 판단

| 구분 | Waterfall/V-Model | Iterative/Agile/DevOps | 선택 기준 |
|:---|:---|:---|:---|
| 요구사항 | 초기 기준선 고정 | backlog 기반 반복 정제 | 규제·계약 요구가 명확하면 V-Model |
| 릴리스 | 단계 종료 후 일괄 배포 | sprint 또는 CI/CD 단위 배포 | 월 1회 이상 릴리스면 DevOps |
| 품질 | 문서 검토와 테스트 단계 분리 | 자동 테스트와 피드백 결합 | 회귀 테스트 자동화율 70% 이상 필요 |

> 요약: 요구사항 안정성과 릴리스 빈도가 SDLC 모델 선택의 1차 기준이다.

| 리스크 | 원인 | 대응 방안 | 확인 지표 |
|:---|:---|:---|:---|
| 요구사항 누락 | 이해관계자 식별 부족 | workshop, prototype, acceptance criteria | 요구사항 변경률 10% 이하 |
| 게이트 형식화 | 승인 기준 부재 | checklist, peer review, CCB 운영 | review defect density |
| 배포 장애 | 운영 이관 지연 | blue-green, canary, rollback 자동화 | 변경 실패율 15% 이하 |

> 요약: SDLC 리스크는 기준선, 검토 기준, 배포 복구 절차를 지표로 묶어야 통제된다.

| 점검 항목 | 목표 기준 | 측정 방법 |
|:---|:---|:---|
| 추적성 | 요구사항-테스트 매핑 100% | RTM, ALM dashboard |
| 품질 | 결함 유출률 2% 이하 | defect leakage, RCA |
| 운영 | MTTR 30분 이하, 배포 성공률 95% 이상 | APM, incident log |

> 요약: SDLC 성숙도는 문서 존재가 아니라 추적성·결함·운영 복구 지표로 검증한다.
