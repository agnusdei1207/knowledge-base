# 📖 【암기용】 개념 완전 이해

> 목적: 재현 가능 빌드를 처음 보는 사람도 개념과 내부 용어를 완전히 이해하게 만든다. 시험 답안 양식이 아니라, 이해를 위한 친절한 설명이다.

## 한눈에
- **개요**: 재현 가능 빌드는 **결정적 빌드(Deterministic Build)** 기법으로, 같은 소스·같은 빌드 조건이면 언제 누가 빌드해도 **byte 단위로 동일한 산출물**이 나오게 만들어 **소스와 바이너리의 일치성**을 제3자가 검증할 수 있게 하는 소프트웨어 공급망 무결성 기법이다.
- **왜 필요한가**: 소스 저장소가 완전히 정상이어도 빌드 서버가 침해되면, 소스에는 없는 코드가 컴파일 과정에서 산출물에 삽입될 수 있다. 이를 잡으려면 "이 바이너리가 정말 이 소스에서 나왔다"를 독립적으로 재현해 확인해야 한다.
- **핵심 직관**: 같은 레시피와 같은 재료로 다른 사람이 다시 만들어도 정확히 같은 바코드가 찍힌 제품이 나오는 표준화된 생산 공정과 같다.

## 핵심 용어 정리 (내부에 등장하는 것들)

| 용어 | 의미 | 비유 |
|:---|:---|:---|
| 소프트웨어 공급망 무결성 | 소스부터 배포까지 변조되지 않았음을 보증하는 상위 개념 | 재현 가능 빌드가 속한 큰 범주 |
| 결정적 빌드(Deterministic Build) | 같은 입력이면 항상 같은 출력을 내는 빌드 성질 | 같은 함수에 같은 인자를 넣으면 같은 리턴값 |
| Hermetic Build(밀폐 빌드) | 네트워크·시스템 시계 등 외부 가변 상태를 빌드 도중 차단 | 외부와 단절된 클린룸에서 조립 |
| 비결정성 요소(Non-determinism) | 같은 소스인데도 결과를 다르게 만드는 요인 — 타임스탬프, 파일 경로, 정렬 순서, 난수, locale, 병렬 처리 순서 | 같은 요리인데 매번 플레이팅이 달라지는 원인들 |
| SOURCE_DATE_EPOCH | 빌드 시각 대신 소스 커밋 시각(UNIX epoch 초)을 파일 타임스탬프로 강제 고정하는 환경변수 | "지금 시각" 대신 "제작 연도"만 도장에 찍기 |
| 독립 빌더(Independent Rebuilder) | 원 빌드팀과 무관한 제3자가 같은 소스로 다시 빌드해 해시를 비교하는 검증자 | 원본 없이도 같은 도면으로 복제품을 만들어 대조하는 감정사 |
| Hash 비교 | 두 산출물의 SHA-256을 비교해 1비트도 다르지 않은지 확인 | 지문 완전 일치 여부 확인 |

## 깊이 이해

### 왜 "컨테이너로 빌드하면 재현된다"는 착각이 생기나
- Docker 컨테이너는 OS·라이브러리 버전은 고정해 주지만, 그 자체로 재현성을 보장하지 않는다. 컨테이너 안에서도 빌드 시각이 파일에 기록되거나(`.class`, `.jar`의 timestamp 헤더), `apt-get install`이 그날 저장소의 최신 버전을 받아오거나, 파일 시스템 디렉터리 순회 순서가 실행마다 달라질 수 있다.
- 그래서 컨테이너(환경 고정) + 아래 비결정성 제거(내용 고정) 둘 다 필요하다.

### 비결정성의 대표 원인과 제거법 — 구체 사례로 이해
- **타임스탬프**: gzip·zip·JAR 포맷은 기본적으로 압축 시각을 헤더에 기록한다. 오늘 빌드하면 헤더에 `2026-07-01 10:32:05`가, 내일 다시 빌드하면 `2026-07-02 09:11:40`이 찍혀 파일 내용이 100% 동일해도 해시가 달라진다.
  - 해결: `SOURCE_DATE_EPOCH=1735689600`(예: 2025-01-01 00:00:00 UTC)처럼 **소스의 마지막 커밋 시각**을 고정값으로 주입해, 언제 빌드하든 이 값을 쓰게 강제한다.
- **파일 경로**: `/home/ci-runner-7/build/...`처럼 빌드 서버의 절대경로가 디버그 심볼이나 에러 메시지 문자열에 박히면, 빌드 머신이 바뀔 때마다 해시가 달라진다.
  - 해결: `-fdebug-prefix-map=/home/ci-runner-7=/build`처럼 경로를 가상의 고정 경로로 치환(path remap)한다.
- **파일 순서·정렬**: tar나 zip으로 여러 파일을 묶을 때, OS의 디렉터리 조회 순서가 실행마다 달라지면 아카이브 내부 파일 순서가 바뀌어 해시가 달라진다.
  - 해결: `tar --sort=name --mtime`처럼 이름순 정렬과 고정 시각을 강제한다.
- **의존성 버전 변동**: `pip install requests`처럼 버전을 명시하지 않으면 오늘과 내일 설치되는 버전이 달라질 수 있다.
  - 해결: lock file(`package-lock.json`, `poetry.lock` 등)로 정확한 버전을 고정하고, base image는 태그가 아닌 digest로 고정한다.

### 검증 절차 — 수치로 보는 흐름
1. 개발자 A가 커밋 SHA `a1b2c3d`로 빌드해 산출물 해시 `sha256:111...`을 얻는다.
2. 독립 빌더 B(다른 조직·다른 인프라)가 같은 커밋 SHA `a1b2c3d`를 받아, 같은 lock file·같은 컴파일러 버전·같은 SOURCE_DATE_EPOCH로 다시 빌드한다.
3. B가 얻은 해시가 `sha256:111...`과 **정확히 일치**하면 재현 성공 — "이 바이너리는 소스 그대로에서 나왔고, A의 빌드 서버가 뭔가를 몰래 추가하지 않았다"가 증명된다.
4. 일치하지 않으면 어느 단계(타임스탬프/경로/의존성/컴파일러)에서 차이가 났는지 역추적한다. Debian reproducible-builds 프로젝트는 이런 방식으로 수만 개 패키지 중 대다수를 재현 가능 상태로 만들었다.

### 비유와 흔한 오해
- **비유**: 시험 답안지를 채점할 때 이름과 필체를 가리고 답만 비교해야 공정하듯, 빌드도 "언제·어디서·누가 만들었나"라는 잡음(타임스탬프·경로)을 지우고 "결과물 내용"만 비교해야 한다.
- **오해**: "재현 가능 빌드 = 빌드가 항상 성공한다"가 아니다. 재현성은 성공 여부가 아니라 **결과물의 바이트 동일성**을 의미한다. 빌드는 매번 성공해도 해시가 다르면 재현 실패다.
- **293 아티팩트 서명과의 관계**: 재현 가능 빌드는 "이 바이너리가 이 소스와 일치한다"를 증명하고, 서명은 "이 바이너리(digest)를 신뢰된 주체가 승인했다"를 증명한다. 재현성 검증 뒤 서명하면 소스-바이너리 일치와 배포 주체 신뢰를 모두 확보한다.

## 연결 개념
- Hermetic Build — 재현 가능 빌드를 만들기 위한 환경 격리 전제조건
- SLSA — 빌드 출처(provenance)와 재현성을 포함하는 무결성 보증 체계, 상위 프레임워크
- Artifact Signing(293) — 재현 검증이 끝난 산출물의 digest에 서명해 배포 신뢰를 완성하는 다음 단계

# 📝 【답안용】 시험 답안 템플릿

> 목적: 시험장에서 25분에 그대로 쓰는 답안 양식. 동일 산출물 조건과 검증 절차를 구체 기준으로 답한다.

## 핵심 인사이트 (3줄 요약)

> 1. **본질**: 재현 가능 빌드는 동일 소스·의존성·환경에서 동일 byte 산출물을 생성해 소스와 바이너리의 일치를 검증하는 기법이다.
> 2. **가치**: 빌드 서버 침해, 의존성 변조, 비결정적 컴파일 결과를 해시 비교로 탐지한다.
> 3. **판단 포인트**: timestamp, path, dependency, locale, network access를 통제해야 재현성 검증이 성립한다.

## 출제 의도 및 답안 포인트

| 출제 의도 | 반드시 짚을 핵심 | 감점 회피 포인트 |
|:---|:---|:---|
| 공급망 신뢰 검증 이해 확인 | deterministic build, hermetic build, hash compare | 단순 CI 재실행으로 설명 |
| 빌드 비결정성 원인 파악 | timestamp, path, random seed, dependency version | 컨테이너 사용만으로 해결된다고 단정 |
| 운영 적용 판단 확인 | 독립 빌더, provenance, artifact signing | 해시 비교 후 배포 정책 누락 |

> 요약: 이 문제는 빌드 자동화가 아니라 소스와 산출물의 검증 가능한 일치성을 묻는다.

## Ⅰ. 개요 및 필요성

- 개요: 재현 가능 빌드는 같은 입력에서 byte 동일 산출물을 만드는 통제이다.
- 배경: 소스 저장소가 정상이어도 빌드 서버나 의존성 저장소가 변조되면 악성 바이너리가 생성될 수 있다.
- 필요성: 빌드 입력을 고정하고 독립 환경에서 hash를 비교해 공급망 변조 여부를 확인해야 한다.

---

## Ⅱ. 구조 및 구성요소

```text
Source Commit -> Pinned Dependency -> Hermetic Build Env -> Artifact -> Hash Compare -> Signing
                                / Timestamp/Path Control
                                / Provenance Record
```

| 구성요소 | 역할 | 특이사항 |
|:---|:---|:---|
| 고정 입력 | 소스·의존성·도구 버전 고정 | lock file, base image digest |
| 결정적 빌드 환경 | 외부 상태와 네트워크 차단 | Bazel, Nix, Guix |
| 비결정성 제거 | 시간·경로·정렬·난수 통제 | SOURCE_DATE_EPOCH |
| 검증자 | 독립 빌드 후 hash 비교 | SHA-256 digest 일치 |

> 요약: 재현 가능 빌드는 고정 입력, 결정적 환경, 비결정성 제거, 독립 검증자로 산출물 신뢰를 만든다.

## Ⅲ. 동작원리 및 흐름도

```text
소스 선택 -> 의존성 고정 -> 환경 격리 -> 결정적 빌드 -> 산출물 해시 -> 독립 빌드 해시 비교
```

| 단계 | 처리 내용 | 검증 기준 |
|:---:|:---|:---|
| 1 | 소스 commit SHA와 lock file 확정 | 입력 버전 100% 기록 |
| 2 | 빌드 도구·base image digest 고정 | mutable tag 사용 0건 |
| 3 | timestamp·locale·path 제거 | SOURCE_DATE_EPOCH 적용 |
| 4 | 독립 빌더가 산출물 hash 비교 | SHA-256 동일 여부 |

> 요약: 동작은 입력 고정, 환경 격리, 결정적 빌드, 해시 비교 순서로 소스와 바이너리 일치를 확인한다.

## Ⅵ. 실무 적용 및 결론

**적용 방안 3개 (필수 - 단계별 또는 항목별):**
1. base image는 tag 대신 digest로 고정하고 npm·Maven·pip lock 파일을 CI 필수 입력으로 지정
2. Bazel·Nix·Guix 또는 hermetic container build로 네트워크 접근을 차단하고 `SOURCE_DATE_EPOCH` 적용
3. 독립 빌더 2곳에서 SHA-256 해시를 비교한 뒤 Cosign 서명과 SLSA provenance를 함께 배포

**결론 (2줄):**
- 기술사 판단: 공개 배포·금융·공공 산출물은 재현 가능 빌드, 내부 실험 서비스는 lock file과 서명부터 단계 적용
- 향후 방향: SLSA L3 이상 provenance와 재현성 검증을 결합해 빌드 서버 신뢰 의존도를 낮추는 방향 필요
