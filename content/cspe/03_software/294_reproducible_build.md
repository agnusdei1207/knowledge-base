# 📖 【암기용】 개념 완전 이해

> 목적: 재현 가능 빌드를 처음 봐도 완전히 이해하게 만든다. 시험 답안 양식이 아니라, 이해를 위한 설명이다.

## 한눈에
- **개요**: 같은 소스와 같은 빌드 조건에서 byte 단위로 동일한 산출물이 나오도록 만드는 빌드 방식
- **왜 필요한가**: 빌드 서버가 침해되면 소스에는 없는 악성 코드가 산출물에 삽입될 수 있어, 제3자가 같은 결과를 검증할 수 있어야 한다.
- **핵심 직관**: 같은 레시피와 같은 재료로 누가 만들어도 같은 바코드의 제품이 나오는 생산 공정이다.

## 깊이 이해
- **배경·문제의식**: 컴파일 시간, 파일 경로, 정렬 순서, 난수, 로케일이 산출물에 섞이면 같은 소스도 다른 해시를 가진다. 이 차이는 공급망 검증을 어렵게 만든다.
- **작동 원리**: 빌드 환경을 고정하고 timestamp, path, locale, dependency version을 통제한다. 독립 빌더가 산출물 해시를 비교해 소스와 바이너리의 일치를 검증한다.
- **비유**: 시험 답안지를 채점할 때 이름과 필체를 지우고 답만 비교해야 공정한 것처럼, 빌드도 시간·경로 같은 잡음을 제거해야 한다.
- **구체 예시**: Debian reproducible builds는 `SOURCE_DATE_EPOCH`로 timestamp를 고정하고 패키지 해시를 비교해 빌드 재현성을 확인한다.
- **흔한 오해·주의점**: Docker 이미지를 쓰면 자동으로 재현되는 것은 아니다. base image digest, 패키지 저장소 상태, 파일 생성 순서까지 고정해야 한다.

## 연결 개념
- Hermetic Build - 네트워크와 외부 상태를 차단한 빌드
- SLSA - 빌드 출처와 무결성 보증 체계
- Artifact Signing - 재현된 산출물의 digest 서명

# 📝 【답안용】 시험 답안 템플릿

> 목적: 시험장에서 25분에 그대로 쓰는 답안 양식. 동일 산출물 조건과 검증 절차를 구체 기준으로 답한다.

## 핵심 인사이트 (3줄 요약)

> 1. **본질**: 재현 가능 빌드는 동일 소스·의존성·환경에서 동일 byte 산출물을 생성해 소스와 바이너리의 일치를 검증하는 기법이다.
> 2. **가치**: 빌드 서버 침해, 의존성 변조, 비결정적 컴파일 결과를 해시 비교로 탐지한다.
> 3. **판단 포인트**: timestamp, path, dependency, locale, network access를 통제해야 재현성 검증이 성립한다.

## 출제 의도 및 답안 포인트

| 출제 의도 | 반드시 짚을 핵심 | 감점 회피 포인트 |
|:---|:---|:---|
| 공급망 신뢰 검증 이해 확인 | deterministic build, hermetic build, hash compare | 단순 CI 재실행으로 설명 |
| 빌드 비결정성 원인 파악 | timestamp, path, random seed, dependency version | 컨테이너 사용만으로 해결된다고 단정 |
| 운영 적용 판단 확인 | 독립 빌더, provenance, artifact signing | 해시 비교 후 배포 정책 누락 |

> 요약: 이 문제는 빌드 자동화가 아니라 소스와 산출물의 검증 가능한 일치성을 묻는다.

---

## Ⅰ. 개요 및 필요성

재현 가능 빌드는 같은 입력에서 byte 동일 산출물을 만드는 빌드 통제이다. 소스 저장소가 정상이어도 빌드 서버나 의존성 저장소가 변조되면 악성 바이너리가 생성될 수 있다. 따라서 빌드 입력을 고정하고 독립 환경에서 hash를 비교해야 한다.

---

## Ⅱ. 구조 및 구성요소

```text
Source Commit -> Pinned Dependency -> Hermetic Build Env -> Artifact -> Hash Compare -> Signing
                                / Timestamp/Path Control
                                / Provenance Record
```

| 구성요소 | 역할 | 특이사항 |
|:---|:---|:---|
| 고정 입력 | 소스·의존성·도구 버전 고정 | lock file, base image digest |
| 결정적 빌드 환경 | 외부 상태와 네트워크 차단 | Bazel, Nix, Guix |
| 비결정성 제거 | 시간·경로·정렬·난수 통제 | SOURCE_DATE_EPOCH |
| 검증자 | 독립 빌드 후 hash 비교 | SHA-256 digest 일치 |

> 요약: 재현 가능 빌드는 고정 입력, 결정적 환경, 비결정성 제거, 독립 검증자로 산출물 신뢰를 만든다.

---

## Ⅲ. 동작원리 및 흐름도

```text
소스 선택 -> 의존성 고정 -> 환경 격리 -> 결정적 빌드 -> 산출물 해시 -> 독립 빌드 해시 비교
```

| 단계 | 처리 내용 | 검증 기준 |
|:---:|:---|:---|
| 1 | 소스 commit SHA와 lock file 확정 | 입력 버전 100% 기록 |
| 2 | 빌드 도구·base image digest 고정 | mutable tag 사용 0건 |
| 3 | timestamp·locale·path 제거 | SOURCE_DATE_EPOCH 적용 |
| 4 | 독립 빌더가 산출물 hash 비교 | SHA-256 동일 여부 |

> 요약: 동작은 입력 고정, 환경 격리, 결정적 빌드, 해시 비교 순서로 소스와 바이너리 일치를 확인한다.

## Ⅳ. 특징

| 구분 | 일반 빌드 | 재현 가능 빌드 | 수치·판단 기준 |
|:---|:---|:---|:---|
| 입력 | 외부 저장소 상태 의존 | lock·digest로 고정 | 의존성 고정률 100% |
| 환경 | 빌더별 차이 존재 | hermetic 환경 | 네트워크 접근 0회 |
| 검증 | CI 성공 여부 | hash 동일성 | SHA-256 byte 동일 |
| 한계 | 설정 부담 낮음 | 비결정성 제거 비용 | 재현 실패 원인 추적 필요 |

> 요약: 재현 가능 빌드는 CI 성공을 넘어 byte 동일성을 검증하지만, 빌드 입력과 환경 통제가 선행되어야 한다.

## Ⅴ. 심화 비교 및 적용 판단

| 비교 축 | 기존/대안 | 본 키워드 | 선택 기준 |
|:---|:---|:---|:---|
| 구조 | 일반 CI 빌드 | hermetic + deterministic build | 배포 산출물 무결성 요구 |
| 비용/성능 | 설정 단순 | 캐시·고정 저장소 운영 | 빌드 시간 증가 20% 이하 |
| 운영/위험 | 빌더 신뢰 | 독립 검증 | 고위험 패키지·공개 배포 |

> 요약: 외부 배포 소프트웨어와 규제 대상 산출물은 일반 CI보다 재현 가능 빌드와 독립 검증이 적합하다.

| 리스크 | 원인 | 대응 방안 | 확인 지표 |
|:---|:---|:---|:---|
| 해시 불일치 | timestamp·path 포함 | SOURCE_DATE_EPOCH, path remap | 재현 실패율 |
| 의존성 변동 | latest tag, floating version | lock file, artifact cache | mutable dependency 0건 |
| 빌드 지연 | hermetic cache 미흡 | remote cache, incremental build | p95 build time |

> 요약: 재현 실패는 비결정 입력에서 발생하므로 timestamp·path·의존성 고정을 점검해야 한다.

| 점검 항목 | 목표 기준 | 측정 방법 |
|:---|:---|:---|
| 재현성 | release artifact hash 일치 100% | 독립 빌더 hash 비교 |
| 입력 고정 | lock·digest 누락 0건 | CI policy scan |
| 출처 증명 | provenance 생성 100% | SLSA attestation 검토 |

> 요약: 성공 여부는 hash 일치율, 입력 고정률, provenance 생성률로 판단한다.

## Ⅵ. 실무 적용 및 결론

**적용 방안 3개 (필수 - 단계별 또는 항목별):**
1. base image는 tag 대신 digest로 고정하고 npm·Maven·pip lock 파일을 CI 필수 입력으로 지정
2. Bazel·Nix·Guix 또는 hermetic container build로 네트워크 접근을 차단하고 `SOURCE_DATE_EPOCH` 적용
3. 독립 빌더 2곳에서 SHA-256 해시를 비교한 뒤 Cosign 서명과 SLSA provenance를 함께 배포

**결론 (2줄):**
- 기술사 판단: 공개 배포·금융·공공 산출물은 재현 가능 빌드, 내부 실험 서비스는 lock file과 서명부터 단계 적용
- 향후 방향: SLSA L3 이상 provenance와 재현성 검증을 결합해 빌드 서버 신뢰 의존도를 낮추는 방향 필요
