# 📖 【암기용】 개념 완전 이해

## 한눈에
- **개요**: 시스템 간에 데이터를 직접 주고받지 않고, 중간에 '우체통' 역할을 하는 큐(Queue)를 두어 비동기적으로 메시지를 전달하는 미들웨어
- **왜 필요한가**: 주문 시스템이 결제 시스템을 직접 호출하면(동기 통신), 결제 서버가 죽었을 때 주문 서버도 같이 뻗어버리는 장애 전파(Cascading Failure)가 발생하기 때문이다.
- **핵심 직관**: 식당에서 손님이 요리사에게 직접 주문을 외치는 대신, 주문서(메시지)를 레일(큐)에 올려두면 요리사가 자기 속도에 맞춰 꺼내가는 방식이다.

## 핵심 용어 정리

| 용어/표기 | 의미 | 비유·예 |
|:---|:---|:---|
| Producer (생산자) | 큐에 메시지를 발행(Publish/Send)하는 주체 | 주문을 접수하는 점원 |
| Consumer (소비자) | 큐에서 메시지를 읽어와(Subscribe/Receive) 처리하는 주체 | 요리를 만드는 셰프 |
| Broker (브로커) | 메시지 큐 서버 자체 (RabbitMQ, ActiveMQ 등) | 메시지 보관 우체국 |
| AMQP (Advanced Message Queuing Protocol) | 메시지 큐 시스템 간 통신을 위한 개방형 표준 프로토콜 | 국제 우편 규격 |

## 깊이 이해
- **배경·문제의식**: 마이크로서비스 아키텍처(MSA)에서는 서비스 간 의존성이 매우 높다. 동기식 HTTP(REST API)로만 통신하면, 트래픽 폭주 시 병목이 발생하고 어느 한 서버의 장애가 전체 시스템 마비로 이어진다. 이를 해결하기 위해 두 시스템을 느슨하게 결합(Loose Coupling)할 미들웨어가 필요했다.
- **작동 원리**: Producer가 데이터(메시지)를 Broker에 전송하면, Broker는 이를 큐에 안전하게 저장(영속화)한다. Consumer는 자신이 처리할 수 있는 속도로 큐에서 메시지를 가져와 비즈니스 로직을 수행하고, 완료 후 Ack(확인 응답)를 보내 브로커가 메시지를 삭제하게 한다. 만약 Consumer 서버가 다운되어도 메시지는 큐에 남아있으므로, 복구 후 다시 처리가 가능하다.
- **비유**: 수도꼭지(Producer)에서 물이 콸콸 쏟아질 때 바로 하수구(Consumer)로 버리면 넘치지만, 중간에 큰 물탱크(메시지 큐)를 두면 하수구가 소화할 수 있는 만큼만 물을 흘려보낼 수 있다. (이를 단기 부하 평탄화, Peak Load Leveling이라 함)
- **구체 예시**: 배달앱에서 사용자가 "주문하기"를 누르면, 즉시 DB에 주문완료를 띄우고(빠른 응답), 백그라운드에서는 "주문발생" 메시지를 RabbitMQ에 넣는다. 그러면 결제서버, 알림톡 서버가 이를 가져가 순차적으로 처리한다.
- **흔한 오해·주의점**: "메시지 큐(RabbitMQ)와 이벤트 스트리밍(Kafka)은 같은 것이다"는 오해다. 메시지 큐는 Consumer가 읽어가면 큐에서 메시지가 '삭제'되는 Task 중심 통신이고, Kafka는 읽어가도 디스크에 보존되어 여러 Consumer가 언제든 재시작해 읽을 수 있는 Event 로그 기반이라는 근본적 차이가 있다.

## 연결 개념
- **Event-Driven Architecture**: 메시지 큐를 기반으로 서비스들이 이벤트를 발행/구독하며 동작하는 아키텍처
- **Apache Kafka**: 단순 메시지 전달을 넘어 대용량 이벤트 스트리밍 및 보존에 특화된 분산 플랫폼
- **Saga Pattern**: MSA 환경에서 메시지 큐를 활용해 분산 트랜잭션의 정합성을 보장하는 설계 패턴

# 📝 【답안용】 시험 답안 템플릿

## 핵심 인사이트 (3줄 요약)

> 1. **본질**: 분산 시스템 간 비동기 메시지 전달을 중개하여 서비스 간 결합도를 낮추는 MOM(Message Oriented Middleware)이다.
> 2. **가치**: 트래픽 스파이크 발생 시 요청을 버퍼링하여 장애를 방어하고(Peak Leveling), 시스템 간 장애 격리(Fault Isolation)를 보장한다.
> 3. **판단 포인트**: 메시지 전달 신뢰성 보장을 위해 QoS(Exactly-Once 등)와 DLQ(Dead Letter Queue) 설계가 필수적이며, 단순 작업 분배(RabbitMQ)와 대용량 로그 스트리밍(Kafka)을 구분하여 도입해야 한다.

## 출제 의도 및 답안 포인트

| 출제 의도 | 반드시 짚을 핵심 | 감점 회피 포인트 |
|:---|:---|:---|
| 도입 목적 및 아키텍처 개선 효과 | 느슨한 결합(Decoupling), 비동기성, 부하 평탄화 | "통신 속도가 빨라진다"는 오답 (동기보다 지연됨) |
| 메시지 유실 방지 신뢰성 보장 원리 | 영속성(Persistence), Ack 메커니즘, DLQ | 데이터 유실(Data Loss) 통제 메커니즘 누락 |
| Kafka 등 다른 브로커와의 비교 선택 | 메시지 삭제(MQ) vs 이벤트 보존(Kafka) | RabbitMQ와 Kafka를 동의어로 취급하는 서술 |

> 요약: 서비스 간 의존성을 끊어내고 가용성을 높이는 미들웨어로서의 역할을 명시하고, 메시지 전달 신뢰성(QoS) 보장 방안을 핵심으로 다루어야 한다.

## Ⅰ. 개요 및 필요성

- 개요: 생산자(Producer)와 소비자(Consumer) 사이에서 비동기적으로 메시지를 저장하고 라우팅하는 미들웨어 시스템(예: RabbitMQ, ActiveMQ)
- 배경: MSA 및 클라우드 환경에서 HTTP 기반 동기 통신의 강결합(Tight-Coupling)으로 인한 연쇄 장애(Cascading Failure) 한계 대두
- 필요성: 시스템 간 통신을 비동기로 분리하여 단일 장애점(SPOF)을 제거하고, 순간적인 대규모 트래픽 쇄도(Spike)에 대한 버퍼링 필요

---

## Ⅱ. 구조 및 구성요소

```text
[Producer 앱] -> (메시지 발행) -> [Message Broker] -> (라우팅 룰) -> [Queue] -> (소비) -> [Consumer 앱]
                                      |                                   | (Ack 반환 시)
                                      +-----------------------------------+ (메시지 삭제)
```

| 구성요소 | 역할 | 특이사항 |
|:---|:---|:---|
| Producer / Consumer | 메시지를 발행(Publish)하고 소비(Consume)하는 주체 | 서로의 IP나 상태를 알 필요 없음 |
| Exchange / Topic | 발행된 메시지를 어떤 Queue로 보낼지 결정하는 라우팅 허브 | Direct, Fanout, Topic 라우팅 방식 지원 |
| Queue | 메시지가 순차적으로 저장되는 메모리/디스크 버퍼 공간 | Consumer가 읽으면 기본적으로 삭제됨 (Pop) |

> 요약: 생산자는 브로커의 Exchange로 메시지를 넘기고, 브로커는 라우팅 룰에 따라 큐에 분배하여 소비자에게 비동기 전달한다.

---

## Ⅲ. 동작원리 및 흐름도 (RabbitMQ 기준)

```text
1. 메시지 생산/발행 -> 2. 브로커 수신 및 라우팅 -> 3. 큐 적재 및 영속화 -> 4. 소비자 인계 및 Ack 처리
```

- 1단계 [발행 및 라우팅]: Producer가 메시지와 라우팅 키를 Exchange로 전송하면, 바인딩(Binding) 규칙에 매칭되는 Queue로 라우팅
- 2단계 [영속화 (Persistence)]: Broker 다운 시 데이터 유실 방지를 위해 수신된 메시지를 메모리에서 디스크(Storage)로 동기화(fsync)
- 3단계 [소비자 인계 (Push/Pull)]: 유휴 상태의 Consumer에게 메시지를 Push 하거나 Consumer가 Pull 방식으로 메시지 획득
- 4단계 [Ack 기반 메시지 삭제]: Consumer가 비즈니스 로직을 완료하고 명시적 확인 응답(Ack)을 보내면 큐에서 메시지를 영구 삭제

> 요약: 데이터 유실 방지를 위해 큐에 메시지를 영속화하며, 처리 완료 응답(Ack)을 받아야만 큐에서 안전하게 제거한다.

---

## Ⅳ. 특징
- 비동기성 및 느슨한 결합: 송신자와 수신자의 라이프사이클이 완벽히 분리되어, 수신자가 장애 상태여도 송신자는 정상 서비스 가능
- 피크 부하 평탄화 (Peak Leveling): 초당 1만 건의 주문이 발생해도 큐에 쌓아두고, DB는 초당 1백 건씩 자신의 처리 능력 한도 내에서 안전하게 반영
- 라우팅 유연성: 하나의 메시지를 Fanout 방식으로 여러 큐에 복제 전달하여 결제, 알림, 재고 등 다수 MSA 서비스 동시 트리거 가능

> 요약: 시스템 간 시간적·공간적 결합을 끊어내어 극단적인 트래픽 쇄도에서도 서버 셧다운을 방어하는 완충재 역할을 한다.

## Ⅴ. 심화 비교 및 적용 판단 (메시지 전달 보장 수준 / QoS)

| 보장 수준(QoS) | 원리 및 특징 | 적용 도메인 |
|:---|:---|:---|
| At-Most-Once (최대 1번) | 메시지 발송 후 Ack 대기 안함 (유실 가능, 속도 최상) | 센서 로그 수집, 단순 클릭 트래킹 |
| At-Least-Once (최소 1번) | Ack 수신 실패 시 재전송 (중복 수신 가능, 멱등성 필수) | 결제 트리거, 주문 시스템 (가장 범용적) |
| Exactly-Once (정확히 1번) | 트랜잭션 매니저를 통해 중복 및 유실 원천 차단 (속도 최하) | 금융 계좌 이체, 블록체인 거래 |

> 요약: 금융/결제 도메인에서는 반드시 'At-Least-Once' 이상을 적용하고, Consumer 측에 멱등성(Idempotency) 로직을 필수로 구현해야 한다.

**리스크·대응 (기본은 불릿):**
- 메시지 무한 루프(Poison Message): 특정 메시지 처리 시 로직 에러로 Ack 미발생 시 무한 재시도 → Max-Retry 설정(예: 3회) 후 실패 시 DLQ(Dead Letter Queue)로 격리 및 알람
- 큐 메모리 고갈(Backpressure): Consumer 장애로 큐에 메시지가 수십만 건 누적되어 브로커 셧다운 → TTL(Time to Live) 설정 및 Auto-Scaling을 통한 Consumer 인스턴스 긴급 증설
- 분산 트랜잭션 실패: DB 저장(로컬 트랜잭션)은 성공했는데 브로커 발송은 실패하는 불일치 → Transactional Outbox 패턴을 적용하여 RDBMS에 이벤트 선 기록 후 릴레이 발송

**도입 후 점검 지표 (기본은 불릿):**
- 성능/운영: 큐 대기 메시지 수(Queue Depth), 메시지 종단 간 지연시간(End-to-End Latency, 목표 p95 < 500ms)
- 품질/장애: DLQ로 라우팅된 메시지 비율(목표 0.01% 이하), Consumer 재시작 시 중복 메시지(멱등성) 처리 성공률

## Ⅵ. 실무 적용 및 결론

**적용 방안 3개:**
1. Transactional Outbox 패턴 구축: 주문 DB 업데이트와 메시지 발행의 원자성을 보장하기 위해, 동일 DB 내 'Outbox 테이블'에 메시지를 저장한 후 백그라운드 워커(CDC 등)가 비동기로 브로커에 전송
2. 마이크로서비스 간 비동기 보상 트랜잭션(Saga): 재고 차감 후 결제가 실패한 경우, "결제 취소" 보상 이벤트 메시지를 큐에 발행하여 재고 서비스가 이를 구독해 롤백 처리
3. DLQ 모니터링 자동화 체계: RabbitMQ/SQS의 Dead Letter Queue에 들어온 메시지를 EventBridge 등으로 캡처하여 Slack 알람을 발송하고 관리자 재처리 UI 연동

**결론 (2줄):**
- 기술사 판단: 클라우드 네이티브 MSA 환경에서 메시지 큐는 장애 전파를 막는 최후의 보루이나, 도입 시 아키텍처 복잡도와 디버깅 비용이 기하급수적으로 상승하므로 동기 통신과의 Trade-off를 엄격히 산정해야 한다.
- 향후 방향: 단순 메시지 전달(RabbitMQ 등)을 넘어 이벤트를 영구 보존하고 스트림 데이터를 실시간 분석하는 Event Streaming Platform(Kafka 등)으로 역할이 진화 및 통합되고 있다.
