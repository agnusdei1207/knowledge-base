# 📖 【암기용】 개념 완전 이해

> 목적: 아티팩트 서명·검증을 처음 보는 사람도 개념과 내부 용어를 완전히 이해하게 만든다. 시험 답안 양식이 아니라, 이해를 위한 친절한 설명이다.

## 한눈에
- **개요**: 아티팩트 서명·검증은 **소프트웨어 공급망 보안(Software Supply Chain Security)**의 핵심 통제로, 빌드 산출물(이미지·패키지)에 **전자서명**을 붙여 **무결성**(변조 여부)과 **출처**(누가 만들었는가)를 암호학적으로 증명하는 절차다.
- **왜 필요한가**: 소스 코드 리뷰를 통과해도, 그 이후 빌드 서버·레지스트리·전송 구간 중 어느 한 곳이 변조되면 악성 코드가 섞인 산출물이 정상처럼 배포될 수 있다. 서명은 "이 바이트가 신뢰된 파이프라인에서 나온 그대로"임을 검증 가능하게 만든다.
- **핵심 직관**: 택배 상자를 봉인하고 발송자 신원 확인서를 동봉한 뒤, 수령 시 봉인 훼손 여부와 발송자를 대조하는 것과 같다. 봉인이 뜯겼거나 발송자가 다르면 수령을 거부한다.

## 핵심 용어 정리 (내부에 등장하는 것들)

| 용어 | 의미 | 비유 |
|:---|:---|:---|
| 소프트웨어 공급망 보안 | 소스→빌드→배포→실행 전 구간의 변조를 막는 상위 개념 | 택배가 공장에서 문 앞까지 오는 전체 경로 보안 |
| 무결성(Integrity) | 산출물이 만들어진 뒤 바뀌지 않았음을 보장 | 봉인이 뜯기지 않음 |
| 출처(Provenance) | 누가, 어떤 소스로, 어떻게 빌드했는지에 대한 증명 | 발송자 확인서 |
| Digest | 산출물 바이트 전체를 SHA-256으로 압축한 고정 길이 지문(256비트=64자리 16진수) | 지문 대조 |
| 서명(Signature) | 개인키로 digest에 만든 값. 공개키로 검증하면 "이 개인키 소유자가 이 digest를 승인했다"가 증명됨 | 위조 불가능한 인감증명 |
| Keyless 서명(Sigstore/Fulcio) | 장기 개인키를 저장하지 않고, OIDC 로그인으로 10분 안팎의 단기 인증서를 발급받아 그 순간만 서명 | 매번 새로 발급하는 1회용 출입증 |
| Transparency Log(Rekor) | 모든 서명 이벤트를 위·변조 불가능하게(append-only, Merkle Tree) 기록하는 공개 장부 | 공증 사무소의 공개 등기부 |
| Admission Controller | Kubernetes에서 배포 요청이 오면 정책을 검사해 실행을 허용/차단하는 검문소 | 공항 출입국 심사대 |
| SLSA Provenance | 어떤 커밋을, 어떤 빌더가, 어떤 단계로 만들었는지 기록한 메타데이터(attestation) | 제조 이력 증명서 |

## 깊이 이해

### 검증이 실제로 확인하는 4가지 — 순서대로 이해하기
서명 검증은 막연히 "서명이 있다/없다"를 보는 게 아니라, 아래 네 가지를 순서대로 확인해야 비로소 신뢰할 수 있다.
1. **무결성 확인**: 지금 받은 산출물의 바이트로 SHA-256을 다시 계산한 값(D')이 서명에 찍힌 digest(D)와 같은가? 한 비트라도 다르면 완전히 다른 해시가 나오므로(눈사태 효과), 같다는 것은 "받은 그대로다"를 뜻한다.
2. **서명 유효성 확인**: 서명(S)이 실제로 그 인증서의 개인키로 D에 대해 만들어졌는가를 공개키로 검증한다. 개인키 없이는 유효한 S를 위조할 수 없다(2^256 경우의 수를 대입하는 것은 현실적으로 불가능).
3. **신원(identity) 확인**: 서명에 쓰인 인증서가 신뢰된 CA(Fulcio) 체인에 속하고, 그 인증서의 OIDC identity가 "우리 CI 파이프라인"과 일치하는가? 예: `signer=https://github.com/org/repo/.github/workflows/build.yml@refs/heads/main`이 승인된 signer 목록에 있는가.
4. **투명성 로그 확인**: Rekor에 이 서명 이벤트의 inclusion proof(Merkle Tree 경로)가 존재하는가? 없으면 아무도 모르게 조용히 서명한 것이므로 사후 감사가 불가능해 신뢰하지 않는다.
- 넷 중 하나라도 실패하면 admission controller는 배포를 차단한다.

### 왜 "태그"가 아니라 "digest"를 서명해야 하나 — 구체 시나리오
- `myapp:latest`, `myapp:v1.2`같은 **태그(tag)는 가변(mutable)**하다. 오늘 `myapp:v1.2`가 `sha256:aaa...`를 가리켜도, 내일 누군가 같은 태그로 다시 push하면 `sha256:bbb...`로 바뀔 수 있다.
- "태그 v1.2가 서명됐다"고만 검증하면, digest가 바뀐 뒤에도 계속 통과한다 — 태그 자체는 서명 시점의 내용을 고정하지 못하기 때문이다.
- 그래서 실제로는 `registry/app@sha256:3a1b2c4d5e6f7890...`처럼 **digest를 서명 대상이자 배포 참조 값**으로 고정한다(digest pinning). digest는 내용이 1비트라도 바뀌면 완전히 다른 값이 되므로, 위조 시점을 봉쇄한다.

### Keyless 서명이 등장한 이유 — 전통 PKI의 약점
- 전통적인 GPG/PKI 서명은 개발자가 개인키를 로컬이나 CI 시크릿에 장기 보관해야 한다. 키가 유출되면(예: CI 시크릿 노출 사고) 공격자가 영구히 그 팀 이름으로 서명할 수 있다.
- Sigstore의 keyless 서명은 매 서명마다 OIDC(예: GitHub Actions 워크플로 신원)로 로그인해 Fulcio CA로부터 **10분 남짓 유효한 단기 인증서**를 발급받고, 그 인증서로 서명한 뒤 버린다. 유출돼도 10분이 지나면 무용지물이라 장기 키 유출 리스크가 사라진다.
- 대신 "그 순간에 실제로 서명했다"는 증거가 사라지지 않도록 Rekor transparency log에 서명 시점·신원을 영구 기록해 사후 추적을 보장한다.

### 비유와 흔한 오해
- **비유**: 계약서에 도장만 찍는 것이 아니라, 계약서 해시와 서명자 신원을 공증 사무소 등기부(Rekor)에 남겨 나중에 "이 계약서가 그때 그 사람이 서명한 것과 같은가"를 누구나 재검증할 수 있게 하는 것과 같다.
- **오해 1**: "이미지에 서명이 있으니 안전하다" — 서명은 "누가 만들었는지"만 증명하지, "그 코드가 안전한지"는 증명하지 않는다. 악성 코드도 정당한 CI 파이프라인을 거치면 정상 서명된다. 그래서 서명은 SBOM·취약점 스캔과 함께 써야 한다.
- **오해 2**: "signer 신원만 확인하면 충분하다" — signer가 승인된 CI라도, digest가 다른(변조된) 이미지에 대한 서명이면 무의미하다. 반드시 digest-서명-신원 3개를 함께 대조해야 한다.

## 연결 개념
- SLSA(294 재현 가능 빌드와 연결) — 빌드 출처와 무결성 보증 수준을 단계별(L1~L4)로 정의, 서명은 그 증거를 담는 그릇
- SBOM — 서명 대상 산출물 안에 어떤 구성요소가 들었는지 목록화, 서명은 "이 SBOM이 이 산출물의 것"을 보증
- Admission Control(Kubernetes) — 런타임 배포 직전 정책 검증 지점, 서명 검증이 실제로 실행되는 위치

# 📝 【답안용】 시험 답안 템플릿

> 목적: 시험장에서 25분에 그대로 쓰는 답안 양식. 서명 알고리즘 나열보다 출처 증명, 무결성, 배포 차단 기준을 중심으로 답한다.

## 핵심 인사이트 (3줄 요약)

> 1. **본질**: 아티팩트 서명·검증은 빌드 산출물의 작성 주체와 변경 여부를 암호학적으로 확인하는 공급망 보증 절차이다.
> 2. **가치**: digest, certificate identity, transparency log를 결합해 서명 없는 이미지와 변조 이미지를 배포 전 차단한다.
> 3. **판단 포인트**: 태그가 아니라 digest를 기준으로 서명하고, CI 신원과 런타임 admission 정책을 연결해야 한다.

## 출제 의도 및 답안 포인트

| 출제 의도 | 반드시 짚을 핵심 | 감점 회피 포인트 |
|:---|:---|:---|
| 소프트웨어 공급망 무결성 이해 확인 | digest, 서명, 인증서, 투명성 로그, 검증 정책 | GPG 명령만 설명하고 배포 차단 누락 |
| CI/CD 보안 설계 확인 | 빌드 후 서명, 레지스트리 저장, admission 검증 | 개발자 로컬 서명만 제시 |
| 운영 통제 기준 확인 | keyless, key rotation, signer allowlist | 태그 기준 검증으로 설명 |

> 요약: 이 문제는 산출물 신뢰를 코드 리뷰가 아니라 암호학적 출처 증명과 런타임 정책으로 보장하는지 묻는다.

## Ⅰ. 개요 및 필요성

- 개요: 아티팩트 서명·검증은 산출물 무결성과 출처 확인 통제이다.
- 배경: 컨테이너 이미지와 패키지가 레지스트리를 거쳐 배포되므로 변조 산출물을 배포 전에 차단해야 한다.
- 필요성: Sigstore·Cosign·SLSA 기반으로 CI 신원, digest, 투명성 로그를 연결해야 한다.

---

## Ⅱ. 구조 및 구성요소

```text
Source Commit -> CI Build -> Artifact Digest -> Signing -> Registry
                                           / Transparency Log
Runtime Admission -> Signature Verify -> Policy Decision -> Deploy/Reject
```

| 구성요소 | 역할 | 특이사항 |
|:---|:---|:---|
| Digest | 산출물 변경 여부 식별 | SHA-256 기반 이미지 digest |
| Signer | digest에 전자서명 생성 | Cosign, GPG, Sigstore keyless |
| Transparency Log | 서명 이력 공개 장부 | Rekor로 서명 위조 탐지 |
| Policy Verifier | 배포 전 검증·차단 | Kyverno, OPA Gatekeeper |

> 요약: 구조는 digest 산출, 서명, 투명성 기록, admission 검증으로 공급망 무결성을 통제한다.

---

## Ⅲ. 동작원리 및 흐름도

```text
빌드 완료 -> digest 계산 -> CI 신원으로 서명 -> 레지스트리 저장 -> 배포 요청 -> 서명 검증 -> 실행 허용/차단
```

| 단계 | 처리 내용 | 검증 기준 |
|:---:|:---|:---|
| 1 | CI가 소스 커밋으로 아티팩트 빌드 | provenance에 commit SHA 포함 |
| 2 | 산출물 digest 계산 후 서명 | SHA-256 digest 기준 |
| 3 | 인증서·서명·로그 기록 저장 | Rekor inclusion proof 확인 |
| 4 | 런타임 admission에서 정책 평가 | signer allowlist 일치 |

> 요약: 동작은 빌드 시 서명하고 실행 시 검증하며, signer identity와 digest 일치 여부가 배포 허용 기준이다.

## Ⅳ. 특징

| 구분 | 무서명 배포 | 아티팩트 서명·검증 | 수치·판단 기준 |
|:---|:---|:---|:---|

|:---|:---|:---|:---|

> 요약: 컨테이너와 자동 배포 환경은 digest 기반 서명과 admission 검증을 기본 통제로 둬야 한다.

| 리스크 | 원인 | 대응 방안 | 확인 지표 |
|:---|:---|:---|:---|
| 키 유출 | 장기 개인키 보관 | keyless OIDC, HSM/KMS | signer 비정상 사용 건수 |
| 정책 우회 | 예외 namespace 허용 | exception approval, audit | unsigned deploy 0건 |
| 태그 변조 | mutable tag 사용 | digest pinning | digest 미고정 배포 건수 |

> 요약: 키 유출, 정책 우회, 태그 변조는 keyless, 예외 감사, digest pinning으로 통제한다.

| 점검 항목 | 목표 기준 | 측정 방법 |
|:---|:---|:---|
| 서명 적용 | 릴리스 아티팩트 100% 서명 | registry scan |
| 검증 차단 | unsigned artifact 배포 0건 | admission audit |
| 출처 추적 | provenance commit 매핑 100% | SLSA attestation 조회 |

> 요약: 운영 성숙도는 서명 적용률, 배포 차단률, provenance 추적률로 판단한다.

## Ⅵ. 실무 적용 및 결론

**적용 방안 3개 (필수 - 단계별 또는 항목별):**
1. GitHub Actions OIDC와 Cosign keyless로 컨테이너 digest를 서명하고 Rekor transparency log에 기록
2. Kubernetes에 Kyverno·OPA 정책을 적용해 signer allowlist와 digest pinning 미충족 이미지를 차단
3. SLSA provenance와 SBOM을 함께 attestation으로 저장해 릴리스별 소스 커밋·빌드 환경·의존성 추적

**결론 (2줄):**
- 기술사 판단: 자동 배포와 다중 레지스트리 환경은 태그 신뢰를 폐기하고 digest 서명·admission 검증을 필수 통제로 선택
- 향후 방향: SLSA, Sigstore, SBOM attestation 결합으로 빌드 출처부터 런타임 실행까지 연속 보증 필요

### 🔀 문제 유형별 목차 전환 (이 키워드 출제 시)
