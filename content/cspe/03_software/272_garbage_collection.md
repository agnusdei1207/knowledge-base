## Ⅰ. 개요
- **정의**: 프로그램이 할당한 힙 메모리 중 참조가 없는 객체를 자동으로 회수하는 메커니즘
- **배경/필요성**: 수동 메모리 해제는 누수·이중 해제 오류를 유발하므로 자동 회수 체계가 필요함
- **비유**: 퇴근 후 빈 사무실의 불을 자동으로 꺼주는 건물 관리 시스템과 유사함

| 출제 의도 | 반드시 짚을 핵심 | 감점 회피 포인트 |
|:---|:---|:---|
| GC 알고리즘 비교·STW 영향 | 세대별 수집, Mark-Sweep-Compact 흐름 | STW 최소화 전략(ZGC 등) 언급 필요 |

> 요약: 참조 없는 힙 객체를 자동 식별·회수하여 메모리 누수를 방지하는 런타임 기능임

## Ⅱ. 구성요소
```text
Heap
  +-- Young Gen --+-- Eden
  |               +-- Survivor 0/1
  +-- Old Gen
  +-- Metaspace

GC Roots --> Mark --> Sweep --> Compact
```

| 구성요소 | 설명 | 비유 |
|:---|:---|:---|
| GC Roots | 스택 변수·정적 필드 등 도달 가능성 판별의 시작점 | 건물 출입구에서 사용 중인 방을 추적하는 기준점 |
| Young Generation | 신규 객체가 할당되는 영역, Minor GC 대상 | 신입 직원 임시 좌석 구역 |
| Old Generation | 장수 객체가 승격되는 영역, Major GC 대상 | 정규직 고정 좌석 구역 |
| STW(Stop-The-World) | GC 수행 중 애플리케이션 스레드를 일시 정지하는 구간 | 청소를 위해 잠시 업무를 멈추는 시간 |

> 요약: GC Roots에서 도달 불가 객체를 식별하고 세대별로 나눠 회수함

## Ⅲ. 절차
```text
객체 할당(Eden) -> Minor GC -> 승격(Old) -> Major GC/Full GC
```
- 1단계: 새 객체를 Eden 영역에 할당하고 Eden이 가득 차면 Minor GC 트리거
- 2단계: GC Roots부터 참조 그래프를 탐색하여 도달 불가 객체를 Mark
- 3단계: Mark되지 않은 객체를 Sweep하고, 생존 객체를 Survivor/Old로 이동
- 4단계: Old 영역 임계 도달 시 Major GC를 수행하여 Compact 후 단편화 해소

> 요약: Eden 할당 → Mark → Sweep → Compact/승격 순서로 반복 수행함

## Ⅳ. 문제점
- STW 지연: Full GC 시 수백 ms~수 초의 일시 정지가 발생하여 실시간 응답성 저하
- 메모리 단편화: Sweep 후 비연속 빈 공간이 남아 대형 객체 할당 실패 가능
- 튜닝 복잡도: 힙 크기·세대 비율·GC 알고리즘 선택 등 조합 파라미터가 과다함

> 요약: STW 지연, 단편화, 튜닝 복잡도가 주요 문제임

## Ⅴ. 개선방안
1. 단기: ZGC·Shenandoah 등 동시 수집기 적용으로 STW를 1 ms 이하로 억제
2. 중기: Region 기반 할당(G1GC)으로 단편화를 회피하고 증분 Compact 수행
3. 장기: 자동 튜닝 에이전트(Adaptive GC Policy) 도입으로 파라미터 자동 조정

> 요약: 동시 수집기, Region 기반 할당, 자동 튜닝으로 각 문제에 대응함

## Ⅵ. 전망
- 발전 방향: 1 ms 미만 Pause를 목표로 하는 저지연 GC가 표준화 추세
- 기술사적 판단: 컨테이너 메모리 제약 환경에서 GC 튜닝의 중요도가 증가함
- 기술사 제언: 워크로드 특성(배치/실시간)별 GC 알고리즘 선정 가이드를 수립할 필요
