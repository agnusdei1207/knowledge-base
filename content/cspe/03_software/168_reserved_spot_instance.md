# 📖 【암기용】 개념 완전 이해

> 목적: 예약 인스턴스와 스팟 인스턴스를 처음 봐도 완벽히 이해하게 만든다. 시험 답안 양식이 아니라, 이해를 위한 친절한 설명이다.

## 한눈에
- **개요**: **컴퓨팅 과금 모델(Pricing Model)** 중에서 사용 패턴을 미리 약정하거나 유휴 자원을 활용해 단가를 낮추는 **구매 옵션**이다 — 상시 사용은 예약 인스턴스, 중단을 허용하는 사용은 스팟 인스턴스로 할인받는다.
- **왜 필요한가**: 온디맨드 단일 단가만 쓰면 두 가지 낭비가 생긴다. 24시간 상시로 켜두는 서버는 계속 정가를 내고, CSP 입장에서는 특정 시점에 안 팔린 유휴 서버가 그대로 논다. 이 둘을 서로 다른 가격으로 매칭하는 것이 예약·스팟이다.
- **핵심 직관**: 예약은 헬스장 연간 회원권(매달 덜 가도 이미 낸 돈, 회당 단가는 훨씬 낮음)이고, 스팟은 항공사 스탠바이 티켓(정가의 일부만 내지만 좌석이 필요해지면 먼저 내려야 함)이다.

## 핵심 용어 정리 (내부에 등장하는 것들)

| 용어 | 의미 | 비유 |
|:---|:---|:---|
| 컴퓨팅 과금 모델 | 클라우드 VM 비용을 산정하는 방식 전체 — 예약·스팟이 속한 상위 개념 | 통신사 요금제 종류 |
| 온디맨드(On-Demand) | 약정 없이 초 단위로 정가를 지불 | 편의점 정가 구매 |
| 예약 인스턴스(Reserved Instance, RI) | 1년 또는 3년 동안 특정 인스턴스 사용을 약정하고 최대 약 72% 할인받음 | 헬스장 연간 회원권 |
| Savings Plan | 특정 인스턴스가 아니라 시간당 지출액($/hr)을 약정해 유연하게 적용 | 정액 구독제(기기 안 써도 요금 고정) |
| 스팟 인스턴스(Spot Instance) | CSP가 안 팔고 놀리는 유휴 용량을 경매가로 최대 약 90% 할인 구매 | 스탠바이 항공권 |
| 스팟 가격(Spot Price) | 해당 시점 수요·공급에 따라 실시간으로 바뀌는 시장가 | 성수기·비수기로 바뀌는 특가 |
| 중단 통지(Interruption Notice) | CSP가 용량을 회수하며 주는 사전 경고(AWS 기준 종료 2분 전 알림) | "곧 좌석 필요하니 내려주세요" 방송 |
| 선결제 옵션(Upfront) | All/Partial/No Upfront로 결제 시점을 나눔 — 선결제가 많을수록 할인율이 커짐 | 선불 요금제일수록 기본료가 낮음 |

## 깊이 이해

### 왜 이런 가격 체계가 생겼나 (배경)
- 온디맨드는 "쓴 만큼만 낸다"는 클라우드의 첫 번째 약속이지만, 상시로 켜두는 워크로드(24시간 운영 DB, 항상 떠 있는 API 서버)에는 오히려 불리하다. 매초 정가를 내는 것과 다르지 않기 때문이다.
- 반대로 CSP는 전 세계에 대규모 서버를 미리 사서 대기시키는데, 이 중 상당수는 특정 시점에 아무도 빌리지 않은 유휴 상태다. 이 유휴 용량을 그냥 놀리느니 싸게라도 파는 것이 CSP에도 이득이다.
- 그래서 "미리 오래 쓰겠다고 약속하면 싸게"(예약)와 "남는 걸 싸게 줄 테니 필요하면 언제든 회수하겠다"(스팟)라는 서로 반대 방향의 할인 모델이 함께 나왔다.

### 예약 인스턴스 작동 원리 — 수치로 이해
- AWS 기준 m5.large 온디맨드가 시간당 약 $0.096일 때, 1년 약정 All Upfront RI는 시간당 환산 약 $0.060 수준으로 약 38% 할인되고, 3년 약정 All Upfront는 약 $0.030~0.035 수준까지 내려가 약 60~72% 할인된다. **약정 기간이 길고 선결제 비율이 클수록 할인율이 커지는 구조**다.
- 결제 옵션은 세 가지다. All Upfront(전액 선결제, 할인율 최대), Partial Upfront(일부 선결제), No Upfront(월별 분납, 할인율 최소). 실제 서버를 켜지 않아도 약정한 만큼 요금이 청구되므로, **사용률이 낮으면 오히려 손해**다 — 예를 들어 1년 RI를 샀는데 실제 가동률이 50%라면, 안 쓴 절반도 요금이 나가 총비용이 온디맨드보다 비쌀 수 있다.
- Standard RI는 인스턴스 패밀리를 바꿀 수 없지만 할인율이 가장 크고, Convertible RI는 약정 기간 중 다른 인스턴스 타입으로 교환할 수 있는 대신 할인율이 조금 낮다.

### 스팟 인스턴스 작동 원리 — 수치로 이해
- 스팟 가격은 고정가가 아니라 해당 인스턴스 타입·AZ의 수요·공급에 따라 시시각각 바뀌는 시장가다. 온디맨드 대비 최대 약 90%까지 할인되지만, 특정 시점에 다른 사용자의 온디맨드 수요가 늘면 CSP가 그 용량을 회수해간다.
- 회수될 때는 무통보가 아니라 AWS 기준 **종료 2분 전**에 인터럽션 통지(CloudWatch 이벤트)가 온다. 이 2분 안에 상태 저장(체크포인트)이나 다른 노드로 작업을 옮기는 로직이 필요하다.
- 예: 딥러닝 모델 학습을 스팟 인스턴스로 돌리면 시간당 비용이 온디맨드의 1/10 수준까지 낮아지지만, 학습 도중 회수되면 그때까지의 진행 상황을 잃을 수 있다. 그래서 매 N 스텝마다 체크포인트를 저장해 재시작 시 이어받도록 설계한다.
- Capacity-Optimized 할당 전략은 여러 인스턴스 타입과 여러 AZ에 걸쳐 스팟 요청을 분산시켜, 특정 풀 하나가 회수되어도 전체 작업이 멈추지 않게 한다 — 계란을 한 바구니에 담지 않는 원리다.

### 언제 무엇을 쓰나 — 판별 원리
- 판별 기준은 **사용 예측성**과 **중단 허용도** 두 축이다. ① 24시간 상시 켜져 있고 예측 가능한 워크로드(DB, 코어 API) → 예약. ② 언제 죽어도 재시도하면 되는 무상태·배치 워크로드(이미지 변환, CI 빌드, ML 학습) → 스팟. ③ 사용 패턴이 불확실하거나 스팟 회수 시 즉시 대체가 필요한 fallback → 온디맨드.
- 실무에서는 세 가지를 섞는다. 기준 부하(baseline)는 예약으로 깔고, 변동·피크 부하는 스팟이나 온디맨드로 얹는 방식이 표준이다.

### 비유와 흔한 오해
- **비유**: 예약은 자주 안 가도 돈이 나가지만 방문당 단가는 저렴한 헬스장 연회원권이고, 스팟은 평소엔 저렴하지만 좌석이 필요해지면 취소당할 수 있는 스탠바이 항공권이다.
- **오해 1**: 예약은 무조건 저렴하다 — 사실이 아니다. 약정한 용량을 다 못 쓰면(사용률 저조) 오히려 온디맨드보다 총비용이 커질 수 있다.
- **오해 2**: 스팟은 아무 워크로드에나 써도 된다 — 상태를 잃으면 안 되는 DB, 세션 서버, 중단이 곧 장애로 이어지는 서비스에는 부적합하다. 무상태·재시도 가능·체크포인트 가능한 작업에만 적용한다.

## 연결 개념

- 오토 스케일링 - 스팟과 온디맨드를 혼합해 확장하는 실행 단위
- 클라우드 마이그레이션 6R - 이전 후 실측 사용 패턴을 보고 구매 옵션을 재산정

# 📝 【답안용】 시험 답안 템플릿

> 목적: 시험장에서 25분에 그대로 쓰는 답안 양식. 작성방식(추상표현 금지·수치·도식·문제유형 전환)을 엄격히 지킨다.
> 핵심: 예약·스팟은 할인 수단이 아니라 워크로드 중단 허용도와 사용 예측성을 기준으로 구매 옵션을 배정하는 비용 전략이다.

## 핵심 인사이트 (3줄 요약)

> 1. **본질**: 예약 인스턴스는 장기 사용 약정 할인, 스팟 인스턴스는 유휴 용량 기반 변동 할인 구매 방식이다.
> 2. **가치**: 상시 워크로드는 예약으로 단가를 낮추고, 중단 허용 배치 작업은 스팟으로 컴퓨팅 비용을 절감한다.
> 3. **판단 포인트**: 사용률, 중단 허용도, 상태 저장 여부, 재시도 구조, 약정 기간을 기준으로 선택한다.

## 출제 의도 및 답안 포인트

| 출제 의도 | 반드시 짚을 핵심 | 감점 회피 포인트 |
|:---|:---|:---|
| 클라우드 구매 옵션 이해 확인 | 온디맨드, 예약, 스팟의 과금·가용성 차이 | 할인율만 쓰고 중단 리스크 누락 |
| 비용 최적화 판단 확인 | 상시 사용량과 변동 사용량 분리 | DB에 스팟 적용 같은 부적절 사례 |
| 운영 설계 역량 확인 | 스팟 중단 대응, fallback, checkpoint | 재시도·혼합 풀 설계 누락 |

> 요약: 이 문제는 비용 옵션을 워크로드 특성과 장애 허용도에 맞춰 배정하는 판단을 요구한다.

## Ⅰ. 개요 및 필요성

- 개요: 예약·스팟 인스턴스는 사용 패턴별 구매 옵션임.
- 배경: 온디맨드는 사전 약정이 없지만 장기 상시 사용 시 단가 부담이 커진다.
- 필요성: 예측 가능한 사용량은 예약, 중단 가능한 배치 작업은 스팟으로 분리해 컴퓨팅 단가를 관리한다.

---

## Ⅱ. 구조 및 구성요소

```text
Workload Profile -> Baseline Capacity -> Reserved Instance
                 -> Burstable/Batch Capacity -> Spot Instance
                 -> Fallback -> On-Demand Instance
```

| 구성요소 | 역할 | 특이사항 |
|:---|:---|:---|
| 예약 인스턴스 | 1년/3년 약정 기반 상시 용량 구매 | 사용률 70% 이상일 때 검토 |
| 스팟 인스턴스 | 유휴 용량 할인 사용 | 중단 통지와 회수 가능 |
| 온디맨드 | 즉시 사용, 약정 없음 | 기준 단가, fallback 용도 |
| 혼합 풀 | 예약·스팟·온디맨드 조합 | Auto Scaling, capacity-optimized |

> 요약: 기준 용량은 예약, 변동·배치 용량은 스팟, 예외 용량은 온디맨드로 구성한다.

---

## Ⅲ. 동작원리 및 흐름도

```text
사용 패턴 분석 -> 기준 사용량 산정 -> 예약 구매
-> 변동 작업 분리 -> 스팟 풀 구성 -> 중단 시 재시도/온디맨드 전환
```

| 단계 | 처리 내용 | 검증 기준 |
|:---:|:---|:---|
| 1 | 30~90일 사용량 분석 | 평균, p95, 야간 사용률 |
| 2 | 예약 구매량 산정 | 예약 사용률 80% 이상 목표 |
| 3 | 스팟 적용 대상 분리 | 무상태, 재시도 가능, 체크포인트 |
| 4 | 중단 대응 검증 | 재시도 성공률 99%, 작업 손실 0건 |

> 요약: 구매 옵션은 사용량 분석 후 기준 용량과 중단 허용 용량을 분리해 적용한다.

## Ⅳ. 특징

| 구분 | 온디맨드 | 예약·스팟 | 수치·판단 포인트 |
|:---|:---|:---|:---|
| 비용 | 표준 단가 | 예약 1/3년 약정, 스팟 할인 | 사용률 80% 이상 예약 검토 |
| 가용성 | 회수 없음 | 스팟은 중단 가능 | 중단 통지 대응 필요 |
| 적용 대상 | 예측 불가·단기 사용 | 상시 사용·배치 작업 | DB는 예약, 배치는 스팟 |
| 운영 | 구매 관리 단순 | 약정·풀·fallback 관리 | 월 예약 미사용률 10% 이하 |

> 요약: 예약은 예측 가능한 기준 용량, 스팟은 중단 허용 작업에 적용해야 비용과 운영 리스크가 균형을 이룬다.

## Ⅴ. 심화 비교 및 적용 판단

| 비교 축 | 예약 인스턴스 | 스팟 인스턴스 | 선택 기준 |
|:---|:---|:---|:---|
| 구조 | 장기 약정 할인 | 유휴 용량 변동 할인 | 사용 예측성 vs 중단 허용도 |
| 비용/성능 | 사용률 낮으면 낭비 | 중단 대비 로직 필요 | 예약 80% 이상, 스팟 재시도 가능 |
| 운영/위험 | 약정 변경 제약 | 회수와 용량 부족 | 약정 기간과 fallback 설계 |

> 요약: 예약은 사용률, 스팟은 중단 복구 가능성이 선택 기준이다.

| 리스크 | 원인 | 대응 방안 | 확인 지표 |
|:---|:---|:---|:---|
| 예약 낭비 | 과도한 약정 구매 | 단계 구매, 월별 사용률 리뷰 | 미사용률 10% 이하 |
| 스팟 중단 | CSP 용량 회수 | checkpoint, queue, 온디맨드 fallback | 작업 실패율 1% 이하 |
| 용량 부족 | 단일 인스턴스 타입 의존 | mixed instance policy, 다중 AZ | capacity error 0건 |

> 요약: 구매 옵션 리스크는 과도한 약정과 스팟 회수이며 사용률과 실패율로 통제한다.

| 점검 항목 | 목표 기준 | 측정 방법 |
|:---|:---|:---|
| 비용 | 월 비용 편차 10% 이하, 예약 적용률 60% | Billing Export |
| 예약 활용 | 사용률 80% 이상, 미사용률 10% 이하 | RI/SP utilization report |
| 스팟 복구 | 재시도 성공률 99%, 처리 지연 SLA 충족 | 작업 큐, 배치 로그 |

> 요약: 예약·스팟 적용 성과는 비용, 약정 사용률, 중단 복구율로 판단한다.

## Ⅵ. 실무 적용 및 결론

**적용 방안 3개 (필수 - 단계별 또는 항목별):**
1. 사용량 분석: 90일 사용량을 기준으로 24시간 기준 용량과 피크 용량을 분리하고 예약 구매량을 70~80% 범위로 산정
2. 스팟 설계: 배치·CI·ML 학습 워커에 checkpoint, queue, retry, 온디맨드 fallback을 적용
3. 월간 조정: 예약 사용률 80% 이상, 스팟 실패율 1% 이하, 예산 편차 10% 이하를 FinOps 회의에서 점검

**결론 (2줄):**
- 기술사 판단: 상시·상태 저장 워크로드는 예약, 무상태·재시도 가능 워크로드는 스팟, 불확실 수요는 온디맨드를 선택함
- 향후 방향: 구매 옵션은 오토 스케일링, 스케줄링, 자동 rightsizing과 결합해 정책 기반으로 운용됨
