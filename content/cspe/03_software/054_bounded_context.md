# 📖 【암기용】 개념 완전 이해

> 목적: 이 개념을 처음 보는 사람도 완벽히 이해하게 만든다. 시험 답안 양식이 아니라, 이해를 위한 친절한 설명이다.

## 한눈에
- **개요**: **바운디드 컨텍스트**는 도메인 주도 설계(DDD)의 **전략적 설계**에서 하나의 **도메인 모델과 유비쿼터스 언어가 일관되게 유효한 경계**를 의미하며, 이 경계 밖에서는 같은 용어라도 다른 의미로 모델링된다.
- **왜 필요한가**: 조직 전체가 "상품"이라는 테이블 하나를 공유하면, 주문팀(가격·재고가 필요)과 배송팀(무게·부피가 필요)이 같은 테이블에 서로 다른 목적의 컬럼을 계속 추가하며 충돌한다. 바운디드 컨텍스트는 "상품"을 팀별로 별도 모델로 쪼개, 각 팀이 자기 컨텍스트 안에서만 자유롭게 모델을 바꾸게 한다.
- **핵심 직관**: 같은 단어라도 경계를 넘으면 다른 뜻이다. "회원"이라는 단어는 로그인 컨텍스트에서는 ID·비밀번호를 가진 인증 주체이고, 배송 컨텍스트에서는 주소를 가진 수령인이다 — 하나의 통합 모델로 억지로 합치지 않는다.

## 핵심 용어 정리 (내부에 등장하는 것들)

| 용어 | 의미 | 비유 |
|:---|:---|:---|
| 유비쿼터스 언어 | 컨텍스트 안에서 기획자·개발자가 동일한 뜻으로 쓰는 용어 | 그 동네에서만 통하는 방언 |
| 컨텍스트 매핑 (Context Mapping) | 서로 다른 바운디드 컨텍스트가 통신하는 방식을 정의하는 상위 설계 | 국가 간 외교 협정 |
| ACL (Anti-Corruption Layer, 부패 방지 계층) | 외부 모델이 내 컨텍스트에 그대로 들어오지 않도록 변환하는 계층 | 통역사를 거쳐 정보를 받음 |
| OHS (Open Host Service) | 여러 외부 컨텍스트가 쓸 수 있도록 표준 API를 공개하는 방식 | 만인에게 동일한 규격의 창구를 여는 것 |
| Shared Kernel (공유 커널) | 두 컨텍스트가 어쩔 수 없이 공유하는 최소 공통 모듈 | 두 부서가 함께 쓰는 공용 회의실 |
| 이벤트 스토밍 (Event Storming) | 도메인 이벤트를 나열해 컨텍스트 경계를 찾아내는 워크숍 기법 | 업무 흐름을 포스트잇으로 시간순 나열하기 |

## 깊이 이해

### 배경 — 전사 통합 모델이 실패하는 이유
- 과거 ERP류 시스템은 회사 전체가 공유하는 단 하나의 데이터 모델을 추구했다. 그러나 부서마다 같은 단어("고객", "상품")에 요구하는 속성이 다르다. 통합 모델은 모든 부서의 요구를 다 반영하려다 한 엔티티에 컬럼이 수십 개씩 붙는 거대 객체(God Object)가 되고, 결국 어느 부서도 마음대로 바꾸지 못하는 병목이 된다.

### 경계를 나누는 판별 원리 — 유비쿼터스 언어가 바뀌는 지점
- 판별 원리: 같은 용어를 두고 두 팀이 서로 다른 정의를 말하기 시작하는 지점이 컨텍스트 경계다. "재고"를 물류팀은 "창고에 실제로 쌓인 물리적 수량"으로, 판매팀은 "지금 주문 가능한 수량(예약분 제외)"으로 다르게 정의한다면 이 지점에서 재고 모델을 물류 컨텍스트와 판매 컨텍스트로 분리해야 한다.

### 구체 예시 — 하나의 개념이 3개로 쪼개지는 경우
- 배달 앱의 "회원"은 3개 컨텍스트로 분리될 수 있다. ① 인증 컨텍스트: 아이디·비밀번호·로그인 이력만 다루는 `AuthUser`. ② 배달 컨텍스트: 위도·경도 배송지 정보를 다루는 `Recipient`. ③ 정산 컨텍스트: 계좌번호·정산 이력을 다루는 `Payee`. 세 클래스는 물리적으로 다른 서버·DB에 저장되며, 정합성이 필요할 때는 회원 ID로만 서로를 참조한다(직접 JOIN 불가).
- 판별 원리(효율 vs 명확성): 이 방식은 회원 ID 등 일부 데이터가 여러 DB에 중복 저장되는 비효율을 감수한다. DDD는 저장 공간의 중복 비용보다, 한 팀이 다른 팀 코드·DB 구조를 신경 쓰지 않고 독립적으로 배포할 수 있는 이익이 더 크다고 본다.

### 컨텍스트 매핑 — 경계를 나눈 뒤 통신 규약
- ACL: 우리가 외부 시스템에 종속적인 입장(을)일 때 쓴다. 예: 외부 PG사의 결제 응답 JSON 구조가 지저분하면, 우리 컨텍스트 경계 바로 안쪽에 변환 클래스(예: `PgResponseTranslator`)를 두어 외부 구조를 우리 도메인 언어(`PaymentResult`)로 변환한 뒤에만 내부 로직에 전달한다. 외부 구조가 바뀌어도 이 변환 클래스 1개만 고치면 된다.
- OHS: 우리가 여러 소비자에게 데이터를 제공하는 입장(갑)일 때 쓴다. 예: 사내 10개 팀이 상품 정보를 요청한다면, 각 팀 요구에 맞춰 API를 10개 만드는 대신 표준 REST API 1개를 공개하고 모든 팀이 그 규격에 맞춰 호출하게 한다.
- Shared Kernel: 두 컨텍스트가 도저히 나눌 수 없는 공통 로직(예: 통화 환산 규칙)이 있으면 공용 라이브러리로 분리해 공유한다. 단, 이 공유 코드를 고칠 때는 두 팀이 함께 합의해야 하므로 의존이 완전히 사라지지는 않는다 — 최후의 타협책이다.

### 컨텍스트 경계 찾는 법 — 이벤트 스토밍
- 기획·개발자가 모여 업무에서 일어나는 사건을 과거분사형(예: "주문됨", "결제됨", "배송시작됨")으로 시간순 나열한다. 이벤트들이 서로 강하게 뭉쳐 하나의 흐름을 이루는 구간과, 책임 주체가 바뀌는 지점(예: "결제됨" 다음 "배송시작됨"으로 넘어가며 담당 팀이 바뀜)을 찾아 그 절취선을 컨텍스트 경계로 확정한다.

### 흔한 오해
- "같은 데이터를 여러 컨텍스트가 중복 저장하면 비효율 아닌가"라는 지적은 맞지만, 이는 의도된 트레이드오프다. 중복 저장 비용보다 한 팀의 변경이 다른 팀 코드를 깨뜨리는 결합 비용이 실무에서 훨씬 크다고 보기 때문에 DDD는 물리적 분리를 우선한다.
- 바운디드 컨텍스트와 마이크로서비스(MSA)는 같은 개념이 아니다. 컨텍스트는 논리적/모델 경계이고 MSA는 배포 단위다. 다만 실무에서는 컨텍스트 1개를 MSA 1개로 매핑하는 것이 가장 자연스러운 출발점으로 쓰인다.

## 연결 개념
- 도메인 주도 설계(DDD) 전술적 설계 — 한 바운디드 컨텍스트 내부를 Entity·Aggregate로 모델링 (053)
- 마이크로서비스 아키텍처(MSA) — 컨텍스트 경계를 물리적 서비스 단위로 구현하는 실무 매핑
- 이벤트 기반 아키텍처(Event-Driven Architecture) — 컨텍스트 간 결합 없이 통신하는 방법(도메인 이벤트, Saga)

# 📝 【답안용】 시험 답안 템플릿

> 목적: 시험장에서 25분에 그대로 쓰는 답안 양식. 작성방식(추상표현 금지·수치·도식·문제유형 전환)을 엄격히 지킨다.
> 핵심: 이 시험은 정보를 많이 나열하는 시험이 아니라, 문제 신호어에서 출제자 의도를 읽고 핵심 논점을 선별해 쓰는 시험이다.

## 핵심 인사이트 (3줄 요약)

> 1. **본질**: 도메인 주도 설계(DDD)의 전략적 설계(Strategic Design) 핵심으로, 특정한 도메인 모델과 유비쿼터스 언어가 완벽하게 일관성을 유지하며 유효한 '논리적/물리적 의미의 경계(Boundary)'다.
> 2. **가치**: 전사적 단일 모델(Global Model)이 유발하는 강결합과 모델 오염을 타파하고, 마이크로서비스(MSA)를 분할할 때 기능이나 데이터가 아닌 '비즈니스 응집도' 중심의 가장 이상적인 식별 기준(1 Context = 1 MSA)을 제공한다.
> 3. **판단 포인트**: 동일한 개념(엔티티)이 컨텍스트에 따라 다르게 모델링되는 다형적 분리 도식을 그리고, 분리된 컨텍스트 간의 통합을 위한 컨텍스트 매핑(ACL, OHS 등 외교 협정) 아키텍처를 규명해야 한다.

## 출제 의도 및 답안 포인트

| 출제 의도 | 반드시 짚을 핵심 | 감점 회피 포인트 |
|:---|:---|:---|
| MSA 서버 분할의 절대적 기준점 식별 | Bounded Context 기반의 마이크로서비스 및 DB 분할 | 무작정 테이블이나 코드 라인 수 기준으로 MSA를 쪼갠다고 서술하는 기획 에러 |
| 거대 통합 모델(Monolith)의 한계와 모델 독립성 | 동일한 '상품'도 주문/배송 컨텍스트별로 쪼개져야 함을 설명 | 찢어진 컨텍스트들이 하나의 거대 DB 테이블을 공유한다고 적는 최악의 오답 |
| 시스템 간 통합(Integration) 방어 기제 맵핑 | 컨텍스트 매핑 (ACL, Shared Kernel, OHS) 패턴 | 어떻게 찢어지는지만 쓰고, 찢어진 애들끼리 어떻게 통신하는지(매핑) 누락 |

> 요약: "우리 회사 통합 DB 하나 만들자!"는 건 IT 역사상 최악의 거짓말이다. 마케팅팀의 언어와 물류팀의 언어는 섞일 수 없다. 각자의 언어가 통하는 울타리(Context)를 치고 서로 불가침 조약을 맺게 하는 것이 DDD 전략적 설계의 정수다.

## Ⅰ. 개요 및 필요성

- 정의: 특정한 도메인 모델(비즈니스 룰, 객체)이 적용되는 유효한 경계를 의미하며, 기획자와 개발자가 합의한 유비쿼터스 언어(Ubiquitous Language)가 오직 한 가지 의미로만 통용되는 캡슐화된 아키텍처 단위
- 배경: 과거 전사 통합 데이터 모델링(ERP) 방식은 상이한 부서 간의 요구사항 충돌을 야기했고, 이를 무리하게 수용하느라 엔티티(Entity)에 수십 개의 컬럼이 달라붙는 거대괴물(God Object) 붕괴 도달
- 필요성: 시스템을 고응집(High Cohesion) 덩어리로 찢어 각 팀의 개발 자율성과 독립적 배포(MSA)를 보장하고, 컨텍스트 간 결합도를 끊어내어 파급 효과(Ripple Effect)를 차단하기 위함

## Ⅱ. 바운디드 컨텍스트의 물리적 분리(Decoupling) 도식

동일한 현실의 개념(상품)도, 어떤 안경(Context)을 끼고 보느냐에 따라 설계(Code)가 완전히 달라져야 한다.

```text
[ 모놀리식 통합 모델의 비극 ] 
          +--( 멱살 )-- [상품 (Item)] --( 멱살 )--+
       주문 팀      (가격, 재고, 무게, 부피, 태그)      배송 팀
        (수정)              🚨 100컬럼 🚨             (수정 시 연쇄 붕괴)


[ Bounded Context 기반 물리적/논리적 분할 도식 (DDD) ] 
======================================================================
[ 컨텍스트 A: 주문 도메인 (Order MSA) ]    [ 컨텍스트 B: 배송 도메인 (Delivery MSA) ]
- 🗣️ 언어: 가격, 재고, 프로모션             - 🗣️ 언어: 체적, 중량, 파손주의
- 📦 객체: Order.Item 클래스               - 📦 객체: Delivery.Item 클래스
- 💾 DB : 주문 DB (Oracle)                - 💾 DB : 배송 DB (MongoDB)
                |                                  |
                +--------( 비동기 이벤트 전파 )-------+
======================================================================
```

| 설계 제어 메커니즘 | 아키텍처적(엔지니어링) 극복 가치 | MSA 전환 파급력 |
|:---|:---|:---|
| **유비쿼터스 언어의 국소화** | '사용자'라는 단어는 로그인 컨텍스트에서는 AuthUser로, 결제 컨텍스트에서는 Payer로 국소화되어 의미의 꼬임(모호성) 원천 차단 | 기획서의 단어와 Java 소스코드의 변수명이 100% 일치하여 추적성(Traceability) 극대화 |
| **모델의 자율성 (Autonomy)** | 다른 컨텍스트의 눈치를 보지 않고, 내 울타리 안의 `Item` 클래스에 컬럼을 맘대로 추가/삭제/변경 가능 | 특정 MSA 수정 시 타 MSA팀과 API 회의를 할 필요가 없어지는 극강의 개발 속도(Time-to-market) 향상 |
| **DB-per-Service 사상** | 컨텍스트 1개가 1개의 트랜잭션 경계가 되며, 다른 컨텍스트의 데이터가 필요하면 절대 SQL Join 불가. API나 카프카(Kafka)로 복제(조회) 강제 | 클라우드 환경에서 트래픽이 몰리는 특정 컨텍스트(서버+DB)만 타겟팅하여 수평 확장(Scale-out) 완벽 지원 |

> 요약: DDD는 무식할 정도로 물리적 격리를 사랑한다. 코드가 좀 중복(Duplication)되더라도, 다른 팀 코드와 엮여서 옴짝달싹 못하는 끔찍한 결합(Coupling)보다는 중복이 100배 낫다는 철학이다.

## Ⅲ. 시스템 통합 방어망: 컨텍스트 매핑 (Context Mapping) 패턴

울타리를 쳤으니 서로 남이 되었다. 하지만 일은 같이해야 한다. 남의 똥이 내 울타리로 넘어오지 않게 막는 '외교 협정'이 필요하다.

| 매핑(외교) 패턴 | 발생 시나리오 및 통신 권력 구조 | 아키텍처 방어 기제 (튜닝) |
|:---|:---|:---|
| **ACL** <br> (Anti-Corruption Layer) | **우리가 '을'일 때**. 외부 PG(결제) 시스템 모델이 너무 구려서 그대로 우리 시스템에 가져오면 우리 코드까지 구려지고 종속됨 (부패 전파) | 우리 컨텍스트 경계 바로 안쪽에 **파사드/어댑터(변환기) 클래스를 하나 세움**. 외부의 더러운 JSON 데이터를 우리만의 '유비쿼터스 언어' 객체로 100% 번역(Mapping)하여 내부 수용 |
| **OHS** <br> (Open Host Service) | **우리가 '갑'일 때**. 외부에서 우리 데이터(상품 목록)를 달라고 조르는 팀이 10개나 됨. 일일이 맞춰주기 귀찮고 시스템 부하 우려 | 외부 팀들 입맛에 맞추지 않고, **우리가 정의한 범용적인 표준(REST API) 규격 프로토콜**을 딱 하나 선언함. "데이터 가져가려면 무조건 이 규격(Host)에 니들이 맞춰서 호출해"라고 통보 |
| **Shared Kernel** <br> (공유 커널) | 두 개의 컨텍스트가 너무 밀접하게 연관되어 있어 도저히 찢을 수 없는 공통 모듈(예: 공통 화폐 연산 로직) 존재 | **타협안(Anti-pattern 경계)**. 어쩔 수 없이 공통 라이브러리(JAR)로 빼서 양쪽이 공유함. 단, 이 공통 코드를 고칠 때는 두 팀이 무조건 함께 모여 합의 후 수정(CI 동기화) 강제 |

> 요약: 내 서비스가 외부 API를 호출해서 받아온 DTO 객체를 내 비즈니스 로직(Service) 깊숙이 그대로 던져 넣는다면, 당신의 시스템은 이미 외부 시스템에 의해 부패(Corruption)한 것이다. 문지기(ACL)를 세워서 우리 언어로 통역부터 해라.

## Ⅳ. MSA 분할 딜레마: 컨텍스트 식별 워크숍 (이벤트 스토밍)

개발자 혼자 책상에 앉아서 테이블 개수로 컨텍스트를 쪼개면 무조건 망한다. 비즈니스 행동(이벤트)을 기준으로 찢어야 한다.

| 분할 기법 | 프로세스 메커니즘 | 추출 산출물 |
|:---|:---|:---|
| **이벤트 스토밍** <br> (Event Storming) | 기획/디자인/개발자가 모여, 비즈니스 흐름을 오렌지색 포스트잇(과거분사 이벤트: "결제됨", "배송됨")으로 벽에 시간순으로 도배 | 발생한 이벤트(Event)와 커맨드(Command)들이 강하게 뭉치는 군집(응집도)을 시각적으로 식별하여 펜으로 원형 **바운디드 컨텍스트 울타리 획정 확정** |

> 요약: "어떻게 쪼개야 하나요?"의 정답은 코드에 있지 않다. 업무 프로세스(이벤트)를 따라가다 보면 자연스럽게 책임이 바뀌는 지점(주문 완료 -> 결제 시작)이 나오는데, 그곳이 바로 컨텍스트를 잘라야 할 완벽한 절취선이다.

## Ⅴ. 실무 적용 방안 및 결론

**적용 방안 3개:**
1. [Strangler(스트랭글러) 패턴 기반 점진적 레거시 뜯어내기] 20년 된 통합 모놀리식 통짜 서버를 쪼갤 때, 이벤트 스토밍을 통해 '쿠폰' 바운디드 컨텍스트를 1차로 식별하고, API Gateway 앞단 라우팅을 조작하여 기존 모놀리식의 쿠폰 트래픽만 신규 MSA 컨텍스트(Spring Boot)로 스위칭(Bypass)하여 1차 안전 분할 마이그레이션
2. [Kafka 기반 도메인 이벤트(Domain Event) 발행-구독 통합] 분할된 '주문' 컨텍스트와 '정산' 컨텍스트 간의 강결합(동기 HTTP 호출)을 끊기 위해, 주문 컨텍스트가 완료 시 내부 상태를 수정함과 동시에 `OrderCompletedEvent`를 카프카 토픽에 던지면(Publish), 정산 컨텍스트가 이를 비동기 구독(Subscribe)하여 자기 DB를 업데이트하는 결과적 일관성 구축
3. [부패 방지 계층(ACL)을 통한 외부 솔루션 벤더 락인 방어] 외부 SaaS(Salesforce CRM) 연동 시, 해당 벤더의 복잡한 SDK나 API 응답 모델 구조를 우리 쪽 `Customer` 도메인 내부에 침투시키지 않기 위해, `SalesforceTranslatorAdapter` 계층을 삽입하여 외부 종속성을 인프라스트럭처 레벨(어댑터)에서 100% 방어 튜닝

**결론:**
- 기술사 판단: 바운디드 컨텍스트는 단순한 소프트웨어 모듈화 기법이 아니다. "소프트웨어의 구조는 그 소프트웨어를 만드는 조직의 통신 구조를 따라간다(Conway's Law)"는 철학을 아키텍처에 강제 주입하는 조직 공학(Organizational Engineering)이다. 컨텍스트가 명확히 분리된 조직만이 타 팀의 족쇄(동기화 결합)에서 벗어나 하루 10번 배포하는 민첩성(Agility)을 쟁취할 수 있다.
- 향후 방향: 최근 클라우드 환경에서는 단순히 컨텍스트를 마이크로서비스(MSA)로 1:1 매핑하는 것을 넘어, 서버리스(AWS Lambda) 함수 단위로 컨텍스트의 내부 기능(커맨드)을 더욱 잘게 쪼개어 이벤트 훅(Event Hook)으로 연결하는 극단적인 디커플링(Decoupling) 아키텍처로 엔터프라이즈 설계 표준이 이동하고 있다.
