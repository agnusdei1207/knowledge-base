## 미리 알고가기

- Bounded context는 특정 모델과 용어와 규칙이 일관되게 적용되는 경계임
- 같은 단어도 컨텍스트가 다르면 업무 의미가 달라질 수 있음
- Context map은 컨텍스트 간 관계와 번역 방식을 정리한 그림임

## Ⅰ. 개요

- **정의/개념**: 바운디드 컨텍스트는 특정 도메인 모델과 용어와 규칙이 일관되게 적용되는 범위를 뜻하며, 복잡한 시스템을 여러 의미 영역으로 나눠 모델 충돌과 과도한 결합을 줄이는 DDD 핵심 개념임.
- **배경/필요성**: 대형 시스템에서는 주문, 결제, 정산처럼 같은 단어도 부서와 업무에 따라 의미가 달라지므로, 하나의 통합 모델로 모든 것을 설명하면 충돌과 복잡도가 커짐.

## Ⅱ. 특징

- 컨텍스트마다 모델과 용어를 독립적으로 최적화할 수 있음
- 서비스 경계와 팀 소유권을 정하는 기준점이 됨
- 경계가 모호하면 같은 데이터가 서로 다른 의미로 섞이기 쉬움
- 경계 간 통합 규약을 별도로 설계해야 함

## Ⅲ. 종류 및 비교

| 구분 | 단일 통합 모델 | 바운디드 컨텍스트 분리 |
|:---|:---|:---|
| 용어 관리 | 모든 영역에 하나의 의미를 강제로 적용함 | 영역별 의미를 유지하되 경계에서 번역함 |
| 구조상 장점 | 표면적으로는 문서와 구조가 단순해 보임 | 실제 업무 차이를 반영해 모델 충돌을 줄일 수 있음 |
| 구조상 한계 | 의미 충돌이 누적되면 거대 모델과 변경 충돌이 커짐 | 경계 간 API, 이벤트, 번역 규약을 따로 설계해야 함 |
| 적합한 환경 | 도메인이 단순하고 의미 차이가 크지 않은 시스템에 맞음 | 조직과 업무가 복합적인 대형 시스템에 맞음 |

> 요약: 바운디드 컨텍스트는 서비스를 잘게 나누는 기법이 아니라 서로 다른 의미 체계를 억지로 하나로 묶지 않게 하는 경계임.

## Ⅳ. 구성요소 및 구조

| 구성요소 | 설명 |
|:---|:---|
| Context Boundary | 모델과 규칙이 유효한 범위를 정해 의미 충돌을 통제함 |
| Ubiquitous Language | 같은 컨텍스트 안에서는 용어를 통일하고 다른 컨텍스트와는 구분함 |
| Context Map | 컨텍스트 간 관계와 통합 방식을 드러내 의존 구조를 보이게 함 |
| Ownership Alignment | 컨텍스트와 팀 책임이 맞아야 경계가 실제 운영에서 유지됨 |

## Ⅴ. 원리 및 절차 흐름도

```text
+-------------+     +-------------+     +-------------+     +-------------+
| 의미 충돌 탐색  | --> | 경계 정의      | --> | 관계 맵핑      | --> | 통합 규약 운영 |
+-------------+     +-------------+     +-------------+     +-------------+
```

1. **의미 충돌 탐색**: 같은 용어가 다른 뜻으로 쓰이는 영역을 찾음
2. **경계 정의**: 독립 모델이 필요한 범위를 bounded context로 나눔
3. **관계 맵핑**: 컨텍스트 간 upstream과 downstream 관계를 정함
4. **통합 규약 운영**: 번역과 이벤트와 API 규약으로 경계 간 연결을 관리함

## Ⅵ. 실무 적용 및 유의점

1. 전자상거래나 정산 플랫폼에서는 주문과 회계의 의미 체계가 다르므로 컨텍스트를 분리하되 경계가 문서에만 남지 않도록 컨텍스트 맵과 팀 소유권을 함께 운영하고 용어 충돌 건수와 중복 변경 비율로 확인함
2. 서비스 재편 프로젝트에서는 컨텍스트를 지나치게 잘게 나누면 통합 비용이 급증하므로 자율성과 통합 부담을 함께 보고 컨텍스트 분할 수준과 통합 운영 비용으로 확인함

## Ⅶ. 결론

바운디드 컨텍스트는 다른 의미를 가진 모델을 억지로 하나로 합치지 않게 해 장기 변경 비용을 줄이는 경계 설계임.
