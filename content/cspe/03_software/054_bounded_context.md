## Ⅰ. 개요
- **정의**: 특정 도메인 모델이 일관된 의미를 유지하는 명시적 경계 영역
- **배경/필요성**: 하나의 용어가 부서·기능마다 다른 의미로 사용되면 모델 충돌이 발생하므로, 경계를 명시해 모델 일관성을 보장할 필요
- **비유**: 같은 "계좌"라는 단어가 은행과 게임에서 다른 의미를 갖듯, 맥락별 경계를 설정하는 것과 유사함

| 출제 의도 | 반드시 짚을 핵심 | 감점 회피 포인트 |
|:---|:---|:---|
| DDD 전략 설계의 핵심 단위 이해 | 컨텍스트 맵 관계 유형 | 단순 모듈 분리가 아닌 모델 경계임을 명확히 서술 필요 |

> 요약: 도메인 모델의 의미 일관성을 유지하는 논리적 경계 단위임

## Ⅱ. 구성요소
```text
+--- Context Map ---+
|                    |
| [주문 BC] --ACL-- [결제 BC]
|     |                 |
|  Shared Kernel    OHS/PL
|     |                 |
| [재고 BC] ------  [배송 BC]
+--------------------+
```

| 구성요소 | 설명 | 비유 |
|:---|:---|:---|
| 바운디드 컨텍스트 | 유비쿼터스 언어가 통용되는 모델 경계 영역 | 국가 영토(국경 안에서 법 통용) |
| 컨텍스트 맵 | BC 간 관계와 통합 방식을 시각화한 전체 지도 | 국가 간 외교 관계도 |
| ACL(Anti-Corruption Layer) | 외부 모델 오염을 차단하는 변환 계층 | 입국 심사대 |
| Shared Kernel | 두 BC가 공유하는 최소한의 공통 모델 | 양국 공용 화폐 |

> 요약: 컨텍스트 맵 위에 ACL·Shared Kernel 등 관계 유형으로 BC 간 통합을 정의함

## Ⅲ. 절차
```text
도메인용어수집 --> 동음이의어식별 --> BC경계획정 --> 컨텍스트맵작성
```
- 1단계: 도메인 전문가와 함께 주요 용어와 개념을 수집함
- 2단계: 동일 용어가 다른 의미로 사용되는 지점(동음이의어)을 식별함
- 3단계: 의미 충돌 지점을 기준으로 BC 경계를 획정함
- 4단계: BC 간 관계 유형(ACL, OHS, Shared Kernel 등)을 정의하고 컨텍스트 맵을 작성함

> 요약: 용어 수집에서 컨텍스트 맵 작성까지 4단계로 경계를 확정함

## Ⅳ. 문제점
- 경계 과다 분할: BC를 지나치게 세분화 — 컨텍스트 간 통신 오버헤드 증가
- 경계 모호: 도메인 이해 부족으로 BC 경계가 불명확 — 모델 오염이 경계를 넘어 전파됨
- 맵 관리 부재: 컨텍스트 맵 미갱신 — 실제 통합 구조와 문서 간 괴리 발생

> 요약: 과다 분할, 경계 모호, 맵 미관리가 주요 문제임

## Ⅴ. 개선방안
1. 단기: 이벤트 스토밍(055 참조)으로 BC 경계를 팀 합의 기반으로 도출하여 과다 분할 방지
2. 중기: ACL 도입을 의무화하여 경계 모호 시에도 모델 오염 차단
3. 장기: 컨텍스트 맵을 코드 의존성 분석 도구와 연동해 자동 갱신 체계 구축

> 요약: 이벤트 스토밍 기반 합의, ACL 의무화, 자동 갱신으로 개선함

## Ⅵ. 전망
- 발전 방향: MSA 서비스 분리 기준으로 BC가 사실상 표준 단위로 활용되고 있음
- 기술사적 판단: 서비스 경계 = BC 경계로 매핑하는 역량이 아키텍트의 핵심 역량임
- 기술사 제언: DDD(053 참조) 전략 설계와 함께 조직 구조(역콘웨이 법칙)까지 고려 필요
