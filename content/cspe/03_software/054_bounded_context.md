# 📖 【암기용】 개념 완전 이해

> 목적: 바운디드 컨텍스트를 처음 보는 사람도 완벽히 이해하게 만든다. 시험 답안 양식이 아니라, 이해를 위한 친절한 설명이다.

## 한눈에
- **개요**: 하나의 도메인 모델과 용어가 일관된 의미를 갖는 경계
- **왜 필요한가**: 같은 "고객", "상품", "주문"이라도 영업, 결제, 배송에서 의미와 규칙이 다르다. 경계를 나누지 않으면 하나의 거대 모델이 모든 예외를 품어 변경 비용이 증가한다.
- **핵심 직관**: 같은 단어라도 문맥이 달라지면 뜻이 달라지므로, 모델도 문맥별로 따로 살아야 한다.

## 깊이 이해
- **배경·문제의식**: 전사 공통 모델을 만들려는 시도는 속성 폭증, null 필드 증가, 팀 간 배포 대기를 만든다.
- **작동 원리**: 컨텍스트 내부에서는 유비쿼터스 언어를 엄격히 유지하고, 컨텍스트 간 관계는 Context Map으로 Upstream, Downstream, Shared Kernel, Anti-Corruption Layer로 표현한다.
- **비유**: "계좌"라는 단어가 은행 창구, 회계, 보안 감사에서 다른 속성을 갖듯, 컨텍스트마다 필요한 모델만 유지한다.
- **구체 예시**: 커머스에서 Catalog의 Product는 노출명과 카테고리가 중심이고, Inventory의 Product는 SKU와 재고 수량이 중심이며, Pricing의 Product는 가격 정책과 쿠폰 적용이 중심이다.
- **흔한 오해·주의점**: 바운디드 컨텍스트는 무조건 별도 서비스가 아니다. 하나의 모놀리식 안에서도 모듈 경계로 둘 수 있다.

## 연결 개념
- Context Map: 컨텍스트 간 관계와 의존 방향 표현
- Anti-Corruption Layer: 외부 모델 오염 방지 계층
- MSA: 컨텍스트가 서비스 분해 후보가 됨

# 📝 【답안용】 시험 답안 템플릿

> 목적: 시험장에서 25분에 그대로 쓰는 답안 양식. 작성방식(추상표현 금지·수치·도식·문제유형 전환)을 엄격히 지킨다.
> 핵심: 바운디드 컨텍스트는 서비스 이름이 아니라 모델 의미와 팀 책임이 일치하는 경계이다.

## 핵심 인사이트 (3줄 요약)

> 1. **본질**: 바운디드 컨텍스트는 특정 도메인 모델과 유비쿼터스 언어가 일관되게 통용되는 의미 경계이다.
> 2. **가치**: 모델 충돌을 분리해 팀별 개발·배포 독립성을 확보하고, 컨텍스트 간 통합을 명시적 계약으로 관리한다.
> 3. **판단 포인트**: 컨텍스트 경계는 데이터 테이블이 아니라 용어 의미, 업무 규칙, 팀 책임, 배포 단위로 판단한다.

## 출제 의도 및 답안 포인트

| 출제 의도 | 반드시 짚을 핵심 | 감점 회피 포인트 |
|:---|:---|:---|
| DDD 전략 설계 이해 확인 | 모델 경계, Ubiquitous Language, Context Map | 서비스 분리와 동일시 |
| MSA 분해 기준 판단 확인 | 팀 경계, 배포 경계, 데이터 소유권 | 테이블 수 기준 분해 |
| 통합 리스크 대응 확인 | Shared Kernel, ACL, Published Language | 컨텍스트 간 호출 리스크 누락 |
> 요약: 출제자는 모델 의미 경계를 찾고 컨텍스트 간 통합 방식을 설계하는 능력을 본다.

---

## Ⅰ. 개요 및 필요성

바운디드 컨텍스트는 모델 의미가 일관된 도메인 경계이다.
같은 용어를 전사 공통 모델로 강제하면 속성 충돌과 팀 간 변경 대기가 발생한다.
컨텍스트를 나누면 모델 자율성과 통합 계약을 분리해 변경 영향 범위를 통제할 수 있다.

---

## Ⅱ. 구조 및 구성요소

```text
Domain -> Subdomain 식별
Subdomain -> Bounded Context -> Ubiquitous Language
Bounded Context A -> Context Map -> Bounded Context B
관계 유형 -> Shared Kernel / Customer-Supplier / ACL
팀 / 데이터 / 배포 -> Context 경계 정렬
```

| 구성요소 | 역할 | 특이사항 |
|:---|:---|:---|
| Ubiquitous Language | 컨텍스트 내부 공통 용어 | 문서·코드·테스트명 일치 |
| Context Boundary | 모델 의미와 규칙의 적용 범위 | 패키지, 서비스, DB 경계 후보 |
| Context Map | 컨텍스트 간 관계 표현 | Upstream, Downstream 방향 명시 |
| Anti-Corruption Layer | 외부 모델 변환·격리 | DTO, Mapper, Adapter 활용 |
| Shared Kernel | 일부 모델 공동 사용 | 변경 승인 절차 필요 |
> 요약: 바운디드 컨텍스트는 내부 언어 일관성과 외부 관계 명시를 동시에 요구한다.

---

## Ⅲ. 동작원리 및 흐름도

```text
업무 용어 수집 -> 의미 충돌 탐지
의미 충돌 -> Context 후보 분리
Context 후보 -> 팀 / 데이터 / 배포 경계 검증
Context Map -> 관계 유형 선택
통합 구현 -> ACL / Event / API 계약 적용
```

| 단계 | 처리 내용 | 검증 기준 |
|:---:|:---|:---|
| 1 | Event Storming으로 Command, Event, Policy 수집 | 업무 이벤트 30개 이상 도출 |
| 2 | 동일 용어의 속성·규칙 차이 식별 | 용어 충돌 목록 작성 |
| 3 | 컨텍스트 후보를 팀·데이터 경계와 대조 | 소유 팀 1개, 소유 DB 명시 |
| 4 | Context Map 관계 유형 결정 | Upstream, Downstream 표시 |
| 5 | API, Event, ACL로 통합 구현 | 계약 테스트 100% 통과 |
> 요약: 경계는 용어 충돌에서 출발하고, 팀·데이터·배포 경계로 검증한 뒤 Context Map으로 통합한다.

## Ⅳ. 특징

| 구분 | 전사 공통 모델 | 바운디드 컨텍스트 | 수치·판단 포인트 |
|:---|:---|:---|:---|
| 모델 | 하나의 통합 모델 | 컨텍스트별 모델 | 용어 충돌 2건 이상이면 분리 검토 |
| 데이터 | 공유 테이블 | Context별 소유 데이터 | 공유 테이블 0개 목표 |
| 팀 | 공통 모델 승인 대기 | 팀별 모델 책임 | PR 승인 팀 1개 |
| 통합 | 직접 참조·JOIN | API, Event, ACL | 계약 테스트 통과율 100% |
| 리스크 | 모델 비대화 | 컨텍스트 과분할 | 서비스 간 호출 p95 100ms 이하 |
> 요약: 바운디드 컨텍스트는 모델 충돌을 줄이지만, 과분할 시 호출 비용과 운영 복잡도가 증가한다.

## Ⅴ. 심화 비교 및 적용 판단

| 비교 축 | 모듈 경계 | 바운디드 컨텍스트 | 선택 기준 |
|:---|:---|:---|:---|
| 기준 | 기술 계층, 패키지 | 업무 의미, 언어, 규칙 | 용어 의미 차이가 우선 |
| 배포 | 단일 배포 가능 | 서비스 분리 후보 | 배포 빈도 차이 2배 이상 |
| 데이터 | 공통 DB 가능 | 데이터 소유권 분리 | 테이블 공유 변경 충돌 발생 |
| 팀 | 기술 역할별 팀 | 도메인 팀 | 팀 3개 이상 협업 |
> 요약: 컨텍스트는 기술 모듈보다 업무 의미와 팀 책임을 기준으로 잡아야 한다.

| 리스크 | 원인 | 대응 방안 | 확인 지표 |
|:---|:---|:---|:---|
| 과분할 | 작은 용어 차이를 서비스로 분리 | 모듈 우선, 서비스 분리 보류 | 서비스 간 호출 수 |
| 공유 커널 충돌 | Shared Kernel 변경 합의 지연 | 버전 관리, 승인자 지정 | 공동 모델 변경 리드타임 |
| 모델 오염 | Upstream 모델 직접 사용 | ACL, DTO 변환 | 외부 모델 import 0건 |
| 데이터 정합성 | 컨텍스트별 DB 분리 | Saga, Outbox, 보상 처리 | 이벤트 지연 p95 1초 이하 |
> 요약: 통합 리스크는 ACL과 이벤트 기반 정합성 통제로 관리한다.

| 점검 항목 | 목표 기준 | 측정 방법 |
|:---|:---|:---|
| 언어 일관성 | 컨텍스트 내부 용어 충돌 0건 | 용어 사전 리뷰 |
| 데이터 소유권 | 공유 테이블 0개 | DB 스키마 점검 |
| 배포 독립성 | 타 컨텍스트 승인 없는 배포 90% 이상 | 배포 이력 |
| 계약 품질 | API·Event 계약 테스트 100% | Pact, Schema Registry |
> 요약: 경계 품질은 용어 일관성, 데이터 소유권, 배포 독립성, 계약 테스트로 측정한다.

## Ⅵ. 실무 적용 및 결론

**적용 방안 3개:**
1. 주문, 결제, 배송 등 도메인 이벤트를 기준으로 용어 사전을 만들고 의미 충돌이 있는 용어를 컨텍스트 후보로 분리한다.
2. Context Map에 Upstream, Downstream, Shared Kernel, ACL 관계를 표시하고 호출 방향과 데이터 소유자를 명시한다.
3. 컨텍스트 간 통합은 REST 계약 테스트, 이벤트 스키마 버전, ACL Mapper로 검증하여 외부 모델 침투를 차단한다.

**결론 (2줄):**
- 기술사 판단: 용어 충돌과 데이터 소유권 충돌이 있으면 바운디드 컨텍스트 분리, 단순 패키지 문제면 모듈 경계로 충분함
- 향후 방향: 바운디드 컨텍스트는 Team Topologies와 결합해 팀 API, 배포 단위, 플랫폼 경계 설계 기준으로 확장됨
