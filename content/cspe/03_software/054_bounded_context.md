## 핵심 인사이트 (3줄 요약)
- 도메인 주도 설계(DDD)의 전략적 패턴 중 하나로, 특정 도메인 모델과 유비쿼터스 언어가 의미를 잃지 않고 완벽하게 적용되는 **'논리적/물리적 경계'**.
- 같은 '사용자(User)'라는 단어라도 결제팀(신용카드 정보)과 배송팀(집 주소)에서는 의미와 구조가 완전히 다르므로, 이들을 억지로 하나의 거대한 DB에 통합하지 않고 경계를 나누어 분리함.
- 이 바운디드 컨텍스트의 경계가 곧 마이크로서비스(MSA)를 나누는 가장 이상적인 크기(Size)와 기준선이 됨.

## Ⅰ. 개요 및 필요성
- **개요**: 하나의 거대한 시스템(도메인) 내에서, 서로 다른 비즈니스 규칙과 용어의 의미가 섞이지 않도록 보호하는 캡슐화된 경계.
- **필요성**: 과거 전사적 아키텍처(EA) 시절에는 "전사의 모든 데이터를 하나의 거대한 ERD로 통일하자"는 헛된 꿈(One Big Model)을 꿨음. 하지만 부서마다 단어의 의미가 달라 항상 충돌(Conflict)과 병목이 발생했음. 비즈니스 현실은 모순 투성이이므로, 모델을 분리하여 각각의 문맥(Context) 안에서만 일관성을 유지할 경계가 필요했음.
---
## Ⅱ. 아키텍처 및 핵심 원리
- **단일 모델의 함정 회피**: 
  - (예) '상품(Product)'이라는 클래스에 `가격`, `무게`, `할인율`, `창고위치` 등 전사의 모든 속성을 다 때려 넣으면(God Object), 누군가 수정할 때마다 전체 시스템이 깨짐.
- **컨텍스트 매핑 (Context Mapping)**:
  - 분리된 바운디드 컨텍스트끼리는 필연적으로 통신이 필요함. 이들 간의 협력/통합 관계를 정의한 지도(Map).
  - **Shared Kernel**: 두 컨텍스트가 모델의 일부를 공유함 (수정 시 합의 필요).
  - **Anti-Corruption Layer (부패 방지 계층)**: 외부 타 시스템의 낡은 모델이 우리 컨텍스트 내부로 오염되는 것을 막기 위해 데이터를 번역(Translate)하는 어댑터 레이어.

```text
[ 바운디드 컨텍스트 분리 및 컨텍스트 매핑 ]

 +-----------------------+               +-----------------------+
 | [ 주문 컨텍스트 (BC) ]   |   (API 통신)  | [ 배송 컨텍스트 (BC) ]   |
 |                       | ============▶ |                       |
 |  Product (상품)       | (Translation) |  Product (상품)       |
 |  - id, name, price    |               |  - id, weight, addr   |
 |  (결제/매출 중심)       |               |  (물류/부피 중심)       |
 +-----------------------+               +-----------------------+
  * 각각 별도의 팀, 별도의 DB(Polyglot Persistence)를 가짐 ➡️ MSA의 탄생
```

## Ⅲ. 비교 및 연결
| 구분 | 전사 통합 모델 (Enterprise Data Model) | 바운디드 컨텍스트 (Bounded Context) |
|---|---|---|
| **모델의 개수** | 회사 전체를 아우르는 단 1개의 거대 모델 | 문맥별로 독립된 수십 개의 작은 모델 |
| **언어의 모호성** | 극도로 높음 (부서별로 타협하며 속성 추가) | 완벽히 제거됨 (해당 문맥 내에서만 유효) |
| **데이터베이스** | 거대한 단일 Oracle DB | 각 컨텍스트마다 별도의 독립된 DB |
| **팀의 자율성** | 의존성이 너무 강해 배포 시 전사 합의 필요 | 타 팀 눈치 안 보고 독립적 배포 가능 (애자일) |
---
## Ⅳ. 실무 적용 및 기술사 판단
- **MSA 분해의 안티패턴 방어**: MSA를 도입할 때 "테이블 1개당 서비스 1개"처럼 무조건 작게 쪼개는 것은 최악의 분산 모놀리스(Distributed Monolith)를 낳음. 바운디드 컨텍스트는 "하나의 비즈니스 목적을 달성하는 응집된 기능의 집합"이므로, 트랜잭션이 잦은 엔티티들은 하나의 경계 안에 두어 네트워크 지연을 막아야 함.
- **콘웨이의 법칙 (Conway's Law)**: "시스템의 구조는 그 조직의 소통 구조를 닮는다". 바운디드 컨텍스트를 잘 나눴더라도 조직(팀)이 프론트/백엔드/DBA로 나뉘어 있으면 실패함. 하나의 바운디드 컨텍스트를 하나의 목적 조직(Cross-functional Team)이 온전히 소유(Ownership)해야 함.
---
## Ⅴ. 기대효과 및 결론
- "전체를 통일하려는 환상"을 버리고, "문맥에 맞는 작고 확실한 일관성"을 유지함으로써 거대한 시스템의 유지보수를 가능케 함.
- 도메인 주도 설계(DDD)의 가장 위대한 전략적 성과이며, 성공적인 마이크로서비스 아키텍처로 가는 첫 번째이자 가장 중요한 관문임.

### 👶 어린이를 위한 3줄 비유 설명
1. 학교에서 '마우스'라는 단어를 쓰면, 동물반 친구들은 '찍찍 우는 쥐'를 생각하고 컴퓨터반 친구들은 '컴퓨터 마우스'를 생각하죠?
2. 바운디드 컨텍스트는 "동물반 교실"과 "컴퓨터반 교실"처럼 벽(경계)을 세워주는 거예요.
3. 이 벽 안에서는 자기가 생각하는 '마우스' 이야기를 마음껏 해도, 다른 반 친구들과 절대 싸우거나 헷갈릴 일이 없답니다!
