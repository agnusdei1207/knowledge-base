# 📖 【암기용】 개념 완전 이해

## 한눈에
- **개요**: 바운디드 컨텍스트는 특정한 도메인 모델과 유비쿼터스 언어가 일관되게 적용되는 논리적 경계이다.
- **왜 필요한가**: 하나의 거대한 시스템 안에서 '상품'이라는 단어는 배송팀과 결제팀에게 전혀 다른 의미를 가진다. 이를 억지로 하나의 테이블이나 클래스로 통합하면 누더기가 된다. 모델의 의미가 변질되지 않도록 명확한 경계(울타리)를 쳐야 한다.
- **핵심 직관**: 국가 간의 국경선과 같다. 각 나라(컨텍스트)마다 통용되는 법과 언어(도메인 모델)가 명확히 분리되어 있으며, 국경을 넘을 때는 통역사(매핑 계층)가 필요하다.

## 핵심 용어 정리

| 용어/표기 | 의미 | 비유·예 |
|:---|:---|:---|
| 컨텍스트 맵 (Context Map) | 바운디드 컨텍스트 간의 관계와 통신 방식을 정의한 지도 | 국가 간의 외교 및 무역 협정 지도 |
| 안티 코럽션 레이어 (ACL) | 다른 컨텍스트의 모델이 내 모델을 오염시키지 못하도록 번역해주는 부패 방지 계층 | 통역사 또는 번역기 |
| 서브도메인 (Subdomain) | 현실 세계의 비즈니스 문제 공간 (Problem Space) | 현실의 실제 지형과 산맥 |
| 바운디드 컨텍스트 | 소프트웨어로 구현된 해결 공간 (Solution Space) | 현실 지형 위에 그어진 행정 구역 (국경) |

## 깊이 이해
- **배경·문제의식**: (053 도메인 주도 설계 참조) 엔터프라이즈 시스템에서는 동일한 객체라도 문맥에 따라 속성과 행위가 다르게 정의되어야 한다. 하지만 과거 데이터 중심 설계에서는 무조건 '통합 모델(전사 단일 스키마)'을 추구했고, 결과적으로 어느 팀도 마음대로 수정할 수 없는 거대한 결합 덩어리가 만들어졌다.
- **작동 원리**: DDD의 전략적 설계의 핵심이다. '주문 컨텍스트'와 '배송 컨텍스트'를 나눈다. 주문 안에서의 '주문 아이템'은 가격과 수량이 중요하고, 배송 안에서의 '주문 아이템'은 무게와 배송지 주소가 중요하다. 이 둘을 별도의 모델로 분리하고, 두 컨텍스트가 통신할 때만 ACL(부패 방지 계층)이나 OHS(오픈 호스트 서비스)를 통해 데이터를 변환(매핑)한다.
- **흔한 오해·주의점**: 바운디드 컨텍스트와 모듈(패키지)을 혼동하면 안 된다. 모듈은 코드의 조직화 방법일 뿐이지만, 바운디드 컨텍스트는 '언어와 모델의 의미적 일관성'이 보장되는 경계다. 가장 이상적으로는 1개의 바운디드 컨텍스트가 1개의 마이크로서비스(MSA)로 물리적 분리된다.

## 연결 개념
- 마이크로서비스 아키텍처 (MSA) — 바운디드 컨텍스트는 마이크로서비스를 나누는 가장 이상적인 크기와 기준점
- 도메인 주도 설계 (DDD) — 바운디드 컨텍스트를 도출하는 전체적인 전략적 설계 방법론
- 안티 코럽션 레이어 (ACL) — 레거시 시스템이나 타 컨텍스트와의 결합도를 낮추는 핵심 매핑 기법

# 📝 【답안용】 시험 답안 템플릿

## 핵심 인사이트 (3줄 요약)

> 1. **본질**: 도메인 주도 설계(DDD)에서 유비쿼터스 언어와 도메인 모델이 일관되게 유지되는 논리적, 의미적 경계이다.
> 2. **가치**: 모델 간의 불필요한 통합을 방지하여 결합도를 낮추며, MSA 환경에서 마이크로서비스를 식별하고 분할하는 가장 강력한 기준을 제공한다.
> 3. **판단 포인트**: 컨텍스트 간 통신 시 모델 오염을 막기 위해 ACL(부패 방지 계층) 등 컨텍스트 맵 패턴을 적용해야 하며, 이는 매핑 오버헤드와 트레이드오프 관계에 있다.

## 출제 의도 및 답안 포인트

| 출제 의도 | 반드시 짚을 핵심 | 감점 회피 포인트 |
|:---|:---|:---|
| 도메인 일관성 유지 범위 파악 역량 | 유비쿼터스 언어 유지 범위, 해결 공간(Solution Space) | 컨텍스트를 단순히 자바 패키지로 축소 설명 |
| MSA 서비스 분할 기준 제시 역량 | 컨텍스트 단위 서비스 분할, 마이크로서비스 1:1 매핑 | 테이블 쪼개기 중심의 데이터베이스 분할로 오답 기재 |
| 컨텍스트 간 연동 패턴 적용 역량 | 컨텍스트 맵, 안티 코럽션 레이어(ACL) 통제 메커니즘 | 두 컨텍스트가 모델을 무조건 공유해야 한다는 단정 |

> 요약: 단일 통합 모델의 한계를 극복하고, 모델의 일관성을 유지하는 독립된 경계 설정과 컨텍스트 간 의존성 통제 방안을 제시해야 한다.

## Ⅰ. 개요 및 필요성

- 개요: 도메인 모델과 유비쿼터스 언어가 일관되게 적용되고 유지되는 시스템의 논리적이고 의미론적인 경계임
- 배경: 전사적 단일 모델(Enterprise Data Model) 추구 시, 서로 다른 부서의 요구사항 충돌로 인해 모델이 비대해지고 유지보수가 불가능해지는 현상 발생
- 필요성: 문맥에 따라 달라지는 객체의 의미를 격리하여 높은 응집도를 확보하고, MSA 전환 시 독립적 배포가 가능한 서비스 분할 기준 제시 필수

---

## Ⅱ. 구조 및 구성요소

```text
[ 컨텍스트 A (주문) ] -> 매핑/변환 (ACL) -> [ 컨텍스트 B (배송) ]
  - 고유 도메인 모델 A    (컨텍스트 맵)        - 고유 도메인 모델 B
  - 유비쿼터스 언어 A                          - 유비쿼터스 언어 B
```

| 구성요소 | 역할 | 특이사항 |
|:---|:---|:---|
| 도메인 모델 (Domain Model) | 해당 문맥 안에서만 유효한 비즈니스 룰과 데이터 캡슐화 | 타 컨텍스트 모델과 분리(독립) |
| 컨텍스트 맵 (Context Map) | 분리된 컨텍스트 간의 상호작용 방식과 의존성 관계 정의 | ACL, OHS, Conformist 등 패턴 존재 |
| 안티 코럽션 레이어 (ACL) | 타 컨텍스트의 변경이 내부 모델을 오염시키지 않도록 번역(매핑) 수행 | 부패 방지 계층, 어댑터 형태로 구현 |

> 요약: 각 컨텍스트는 고유한 언어와 모델을 가지며, 외부와의 통신은 철저히 컨텍스트 맵을 통한 번역 계층을 거친다.

---

## Ⅲ. 동작원리 및 흐름도

```text
문제 공간 분석 -> 유비쿼터스 언어 도출 -> 모델 충돌 지점 식별 -> 경계 분리 -> 매핑 룰 정의
```

- 1단계 [문제 공간 분석]: 이벤트 스토밍을 통해 도메인 이벤트를 나열하고 비즈니스 흐름(서브도메인) 파악
- 2단계 [언어 및 충돌 식별]: 동일한 객체(예: '상품')가 부서나 업무에 따라 다른 속성(가격 vs 무게)을 가짐을 식별
- 3단계 [경계 획정]: 의미적 충돌이 발생하는 지점을 기준으로 바운디드 컨텍스트를 분리하여 해결 공간 정의
- 4단계 [매핑(Context Map) 설정]: 분리된 컨텍스트 간 데이터 교환 시 ACL을 적용하여 상호 의존성 및 모델 오염 차단

> 요약: 비즈니스 의미의 충돌 지점을 식별하여 경계를 긋고, 격리된 모델 간의 통신은 변환 계층으로 안전하게 연결한다.

---

## Ⅳ. 특징

- 마이크로서비스 식별 기준: 1개의 바운디드 컨텍스트를 1개의 마이크로서비스로 매핑하여 서비스의 크기와 책임을 명확히 규정
- 개발팀의 자율성 보장: 경계 내부의 모델은 해당 팀이 완전히 소유하므로, 타 팀의 간섭 없이 독립적인 기술 스택 및 구조 변경 가능
- 통합 복잡도 전가: 모델 통합을 포기하는 대신 컨텍스트 간 매핑 및 분산 트랜잭션(Saga 패턴 등) 처리 복잡도 증가

> 요약: 모델의 자율성과 독립적 배포성을 극대화하지만, 컨텍스트 간 통신 오버헤드와 분산 시스템 복잡도가 트레이드오프된다.

---

## Ⅴ. 심화 비교 및 적용 판단

| 비교 축 | 서브도메인 (Subdomain) | 바운디드 컨텍스트 (Bounded Context) | 선택 기준 |
|:---|:---|:---|:---|
| 영역 관점 | 문제 공간 (Problem Space) | 해결 공간 (Solution Space) | 현실 비즈니스 vs 소프트웨어 구현 |
| 획정 주체 | 현실 비즈니스 구조에 의해 이미 존재 | 설계자와 개발자가 의도적으로 획정 | 모델 경계의 논리적 분리 여부 |
| 이상적 관계 | 1 (서브도메인) | 1 (바운디드 컨텍스트) | 최적의 응집도를 위한 1:1 매핑 지향 |

> 요약: 서브도메인이 현실의 비즈니스 문제라면, 바운디드 컨텍스트는 이를 소프트웨어로 어떻게 쪼개어 구현할 것인가의 해결책이다.

**리스크·대응:**
- 무분별한 모델 동기화: 컨텍스트 A의 변경이 B를 망가뜨리는 강결합 발생 → ACL(부패 방지 계층)을 도입하여 DTO 변환 강제 적용 (지표: API 변경 파급 횟수)
- 분산 트랜잭션 롤백 실패: 여러 컨텍스트에 걸친 쓰기 실패 시 데이터 불일치 → 보상 트랜잭션 기반의 Saga 패턴 또는 최종 일관성(Eventual Consistency) 적용 (지표: 비즈니스 트랜잭션 정합성 비율)

## Ⅵ. 실무 적용 및 결론

**적용 방안 3개:**
1. 레거시 마이그레이션 적용: 스트랭글러(Strangler) 패턴 적용 시, 가장 결합도가 낮고 독립적인 바운디드 컨텍스트부터 MSA로 순차적 추출
2. 컨텍스트 간 비동기 통신: 시스템 간 강결합을 끊기 위해 REST API 대신 Apache Kafka 등 메시지 큐를 활용한 도메인 이벤트 기반 비동기 연동 적용
3. ACL을 통한 레거시 격리: 신규 MSA 서비스가 구형 레거시 DB나 API를 호출할 때 안티 코럽션 레이어를 두어 레거시 모델 침투를 원천 차단

**결론 (2줄):**
- 기술사 판단: 바운디드 컨텍스트는 물리적 패키징 이전에 논리적 의미를 보호하는 방벽이므로, 서비스 크기를 물리적 코드 라인 수가 아닌 비즈니스 응집도를 기준으로 획정해야 함
- 향후 방향: MSA가 고도화되면서 바운디드 컨텍스트 간의 복잡한 통신을 돕기 위해 서비스 메시(Service Mesh) 및 이벤트 드리븐 아키텍처(EDA)와의 결합이 필수가 되고 있음
