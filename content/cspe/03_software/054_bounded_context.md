## 미리 알고가기

- bounded context는 특정 모델과 용어가 유효한 경계임
- 같은 단어도 컨텍스트가 다르면 의미가 달라질 수 있음
- 서비스 경계와 팀 책임을 정할 때 중요한 기준이 됨

## Ⅰ. 개요

- **정의/개념**: 바운디드 컨텍스트는 특정 도메인 모델과 용어와 규칙이 일관되게 적용되는 경계를 뜻하며, 시스템을 여러 의미 영역으로 나눠 모델 충돌과 과도한 결합을 줄이는 DDD 핵심 개념임
- **배경/필요성**: 대형 시스템에서는 주문과 결제와 정산처럼 같은 용어도 부서와 업무에 따라 의미가 달라지므로, 하나의 통합 모델로 모든 것을 설명하려 하면 충돌과 복잡도가 커짐

## Ⅱ. 특징

- 컨텍스트마다 모델과 용어를 독립적으로 최적화할 수 있음
- 서비스 분리와 팀 소유권 설계의 기준점이 됨
- 경계가 모호하면 동일 데이터 의미 충돌이 발생함
- 경계 간 통합 규약이 따로 필요함

## Ⅲ. 종류 및 비교

| 판단 기준 | 단일 통합 모델 | 바운디드 컨텍스트 분리 |
|:---|:---|:---|
| 용어 관리 | 하나의 의미로 강제 | 영역별 의미 유지 가능 |
| 장점 | 표면상 단순 | 실제 도메인 복잡도 반영 |
| 한계 | 의미 충돌과 거대 모델 | 경계 간 통합 설계 필요 |
| 적합 환경 | 단순 도메인 | 복합 조직과 대형 시스템 |

## Ⅳ. 구성요소 및 구조

| 구성요소 | 설명 |
|:---|:---|
| Context Boundary | 모델과 규칙이 유효한 범위를 정해 충돌을 통제하는 기본 경계임 |
| Ubiquitous Language | 같은 컨텍스트 안에서는 용어를 통일하고 다른 컨텍스트와는 구분함 |
| Context Map | 컨텍스트 간 관계와 통합 방식을 드러내 의존 구조를 가시화함 |
| Ownership Alignment | 컨텍스트와 팀 책임이 맞아야 경계가 실제 운영에서 유지됨 |

## Ⅴ. 원리 및 절차 흐름도

```text
+-------------+     +-------------+     +-------------+     +-------------+
| 의미 충돌 탐색  | --> | 경계 정의      | --> | 관계 맵핑      | --> | 통합 규약 운영 |
+-------------+     +-------------+     +-------------+     +-------------+
```

1. **의미 충돌 탐색**: 같은 용어가 다른 뜻으로 쓰이는 영역을 찾음
2. **경계 정의**: 독립 모델이 필요한 범위를 bounded context로 나눔
3. **관계 맵핑**: 컨텍스트 간 upstream과 downstream 관계를 정함
4. **통합 규약 운영**: 번역과 이벤트와 API 규약으로 경계 간 연결을 관리함

## Ⅵ. 문제점 및 해결 방안

1. 문제: bounded context 경계가 약하면 같은 데이터 의미가 서비스마다 섞여 변경 충돌이 자주 생길 수 있음
   - 해결방안: context map과 ownership을 명확히 하고 terminology conflict count와 change overlap ratio로 검증함
2. 문제: 컨텍스트를 지나치게 잘게 나누면 통합 비용과 운영 복잡도가 급증할 수 있음
   - 해결방안: 비즈니스 자율성과 통합 비용을 함께 보고 context granularity score와 integration overhead로 검증함
3. 문제: 팀 구조가 경계와 맞지 않으면 문서상의 컨텍스트가 실제 코드에서 무너질 수 있음
   - 해결방안: 팀 책임 재정렬과 아키텍처 리뷰를 운영하고 ownership clarity score와 dependency violation count로 검증함

## Ⅶ. 적용 사례

- 전자상거래 플랫폼에서는 주문과 정산을 다른 컨텍스트로 분리하고, terminology conflict count와 change overlap ratio로 결과를 확인함
- 대형 조직 아키텍처 리뷰에서는 context map을 운영하고, integration overhead와 ownership clarity score로 결과를 확인함
- 서비스 재편 프로젝트에서는 경계와 팀 책임을 동시에 조정하고, context granularity score와 dependency violation count로 결과를 확인함

## Ⅷ. 결론

바운디드 컨텍스트의 가치는 서비스를 많이 나누는 데 있지 않고 서로 다른 의미 체계를 억지로 하나로 묶지 않게 하는 경계 설계에 있음.
