## 미리 알고가기

- 바운디드 컨텍스트(Bounded Context): 특정 도메인 모델, 용어, 그리고 규칙이 일관되게 적용되는 비즈니스적 경계임
- 콘텍스트 맵(Context Map): 여러 바운디드 컨텍스트 사이의 연동 관계와 데이터 번역 방식을 시각화한 구조도임
- 충돌 방지 계층(Anticorruption Layer, ACL): 외부 시스템의 데이터 모델 구조가 내부 도메인 모델을 오염시키지 않도록 변환해 주는 통신 계층임
- 오픈 호스트 서비스(Open Host Service, OHS): 여러 컨텍스트가 하위 호환성을 유지하며 접근할 수 있게 제공하는 개방형 프로토콜 및 API 세트임
- 공유 커널(Shared Kernel): 두 바운디드 컨텍스트가 도메인 모델의 일부분을 공유하여 공동으로 사용하는 물리적 영역임

## 작성 근거(검토용)

- 바운디드 컨텍스트는 용어 의미, 모델 변경 범위, 경계 통합 부담을 핵심 비교축으로 선정함
- 구성은 모델 경계, 공통 언어, 컨텍스트 관계, 팀 소유권을 중심으로 제시함
- 실무 판단은 용어 충돌 건수, 경계 간 중복 변경률, 통합 계약 위반 건수로 구체화함
- 제목, frontmatter, 미리 알고가기, 작성 근거, 본문, 표 헤더·셀, 요약, 결론을 한 줄도 빠뜨리지 않고 확인했으며 어색한 단어·조사·동사 결합·장황한 명사구를 교정함

## Ⅰ. 개요

- **정의/개념**: 바운디드 컨텍스트는 특정 도메인 모델·용어·규칙이 일관되게 적용되는 범위를 정하는 DDD의 모델 경계임
- **배경/필요성**: 같은 용어가 업무 영역마다 다른 의미를 가지면 단일 모델에서 충돌하므로 의미 체계별 경계가 필요함

### 쉽게 이해하기 (학습용)
- '책임자'라는 단어가 군대에서는 분대장, 회사에서는 팀장을 뜻하듯, 서로 헷갈리지 않게 부서(경계)를 나누어 용어를 쓰는 것임

## Ⅱ. 특징

- 컨텍스트마다 같은 용어의 의미와 모델 규칙을 독립 정의하고 경계에서 변환함
- 서비스 경계와 팀 소유권을 정하는 기준점이 됨
- 모델 소유자와 경계 계약이 없으면 같은 데이터에 서로 다른 업무 의미가 섞임
- 경계 간 통합 규약을 별도로 설계해야 함

### 쉽게 이해하기 (학습용)
- 영역별로 사전을 따로 두고 일을 처리하며, 경계를 명확히 해서 서로의 영역을 간섭하지 않도록 방어막을 친 구조임

## Ⅲ. 종류 및 비교

| 판단 기준 | 단일 통합 모델 | 바운디드 컨텍스트 분리 |
|:---|:---|:---|
| 도메인 용어 관리 방식 | 모든 영역에 하나의 의미를 강제로 적용함 | 영역별 의미를 유지하되 경계에서 번역함 |
| 모델 변경 영향도 | 공통 모델 변경이 여러 업무 영역에 전파 | 컨텍스트 내부 모델을 변경하고 경계 계약에서 변환 |
| 시스템 구조 및 통합 비용 | 의미 충돌 누적으로 인한 거대 모델 변경 병목 발생 | 경계 간 API, 이벤트, 번역 규약 설계에 따른 비용 필요 |

> 요약: 용어와 규칙이 공통이면 단일 모델, 업무별 의미가 다르면 바운디드 컨텍스트로 분리함.

### 쉽게 이해하기 (학습용)
- 회사 전체가 하나의 사전만 쓰면 소통이 꼬이지만(단일), 부서별 사전을 따로 두고 통역사(번역기)를 두면 업무 효율이 올라가는 방식임

## Ⅳ. 설계 요소 및 구조

```text
[주문 컨텍스트 (Order)] ──(Context Map)──> [결제 컨텍스트 (Payment)]
  - 용어: 상품 (주문 대상)                    - 용어: 상품 (결제 대상 금액)
  - 소유팀: 주문 개발팀                        - 소유팀: 결제 개발팀
```

| 설계 요소 | 설명 |
|:---|:---|
| 컨텍스트 경계 | 모델·용어·규칙이 유효한 범위를 정함 |
| 공통 언어 | 같은 컨텍스트 안의 용어 의미를 통일함 |
| 컨텍스트 맵 | 컨텍스트 간 의존 관계와 번역 방식을 표현함 |
| 팀 소유권 | 컨텍스트별 변경·운영 책임을 담당 팀에 배치함 |

> 요약: 컨텍스트 경계 안에서는 공통 언어를 사용하고 경계 사이는 컨텍스트 맵의 계약으로 연결함.

### 쉽게 이해하기 (학습용)
- 독립된 섬(컨텍스트)들이 있고, 섬 안에서는 같은 언어를 쓰며, 섬끼리는 다리(컨텍스트 맵)와 통역을 통해 연결되는 모양새임

## Ⅴ. 원리 및 절차 흐름도

```text
[1. 비즈니스 도메인 분석] ──> [2. 컨텍스트 영역 획정] ──> [3. 연동 계약 설계] ──> [4. 인터페이스 구현]
```

- **1. 비즈니스 도메인 분석**: 현업 부서들과의 워크숍을 통해 각 업무 영역별로 사용되는 도메인 용어의 의미적 차이를 분석함
- **2. 컨텍스트 영역 획정**: 용어의 혼선이 없는 범위를 기준으로 바운디드 컨텍스트의 경계를 긋고 모델을 고립시킴
- **3. 연동 계약 설계**: 상호 통신이 필요한 컨텍스트 간에 업스트림(Upstream)과 다운스트림(Downstream) 관계를 명시해 계약을 정의함
- **4. 인터페이스 구현**: 외부 모델과의 격리를 위한 충돌 방지 계층(ACL)이나 대외용 오픈 호스트 서비스(OHS)를 설계하고 연동을 처리함

### 쉽게 이해하기 (학습용)
- 용어를 분류하고, 영역의 경계를 긋고, 각 영역을 잇는 통신 계약(통역 방식)을 맺은 뒤 시스템을 구현하는 흐름임

## Ⅵ. 실무 사례

- 쇼핑몰 구축 프로젝트에서 동일한 상품(Product) 단어가 갖는 비즈니스 맥락의 다변화를 해결하기 위해 주문 컨텍스트와 전시 컨텍스트를 바운디드 컨텍스트로 격리하고, 상호 연동은 이벤트 발행 방식으로 조치함.

### 쉽게 이해하기 (학습용)
- 쇼핑몰에서 '상품'이 주문 부서에서는 '택배 보낼 물건', 회계 부서에서는 '세금 매길 금액'으로 다르게 쓰여 부서별 코드로 떼어놓은 것임

## Ⅶ. 결론

- 바운디드 컨텍스트는 하나의 거대한 모델이 가진 인지 과부하를 해소하고, 경계 단위의 독립적 배포와 확장 체계를 제공함.
- 무분별한 경계 획정은 네트워크 지연과 분산 트랜잭션 등 오버헤드를 유발하므로, 성능과 통신 모델의 복잡도를 감안하여 적절한 경계 크기(Granularity)를 유지해야 함.

### 쉽게 이해하기 (학습용)
- 프로그램이 커져도 꼬이지 않게 관리할 수 있지만, 너무 잘게 쪼개면 부서 간 대화(API 호출) 비용이 늘어나므로 알맞게 조절해야 함
