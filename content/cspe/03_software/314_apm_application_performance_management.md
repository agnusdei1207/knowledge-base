## Ⅰ. 개요
- **정의**: 애플리케이션의 성능을 실시간 모니터링·분석·최적화하는 관리 체계임
- **배경/필요성**: MSA·클라우드 환경에서 서비스 간 호출 복잡도 증가로 성능 병목 추적 수단 필요
- **비유**: 병원 환자 모니터가 심박·혈압·산소포화도를 실시간 표시하듯, 애플리케이션 건강 상태를 감시함

| 출제 의도 | 반드시 짚을 핵심 | 감점 회피 포인트 |
|:---|:---|:---|
| APM 구성 요소와 모니터링 범위 | 트랜잭션 추적·메트릭·로그 3요소 | 인프라 모니터링과의 차이 명확화 |

> 요약: 애플리케이션 계층의 트랜잭션·메트릭·로그를 실시간 수집·분석하는 성능 관리 체계임

## Ⅱ. 구성요소
```text
APM Platform
  +-- Agent (애플리케이션 내 데이터 수집)
  +-- Collector (데이터 수신/집계)
  +-- Storage (시계열 DB 저장)
  +-- Dashboard (시각화/알림)
```

| 구성요소 | 설명 | 비유 |
|:---|:---|:---|
| Agent | 바이트코드 계측으로 트랜잭션·메트릭 자동 수집 | 차량 블랙박스 센서 |
| Collector | 다수 에이전트 데이터를 수신·정규화·집계 | 관제센터 데이터 수신기 |
| Storage | 시계열 DB에 메트릭·트레이스 저장 및 쿼리 지원 | 진료 기록 보관소 |
| Dashboard | 실시간 토폴로지 맵·알림 임계치 기반 시각화 | 관제 모니터 화면 |

> 요약: Agent-Collector-Storage-Dashboard 파이프라인으로 성능 데이터를 수집·분석·시각화함

## Ⅲ. 절차
```text
에이전트 설치 -> 데이터 수집/전송 -> 분석/상관관계 도출 -> 알림/최적화
```
- 1단계: 대상 애플리케이션에 에이전트 설치(바이트코드 계측 또는 SDK 삽입)
- 2단계: 트랜잭션 트레이스·메트릭·로그를 Collector로 실시간 전송
- 3단계: 분산 트레이싱 기반 서비스 간 호출 상관관계 분석 및 병목 식별
- 4단계: 임계치 초과 시 알림 발송, 근본 원인 기반 튜닝 수행

> 요약: 에이전트 계측부터 알림·튜닝까지 4단계 순환으로 성능을 지속 관리함

## Ⅳ. 문제점
- 계측 오버헤드: 에이전트 삽입으로 응답시간 1~3% 증가 — 고성능 시스템에서 부담
- 데이터 폭증: MSA 환경 다량 트레이스 발생 — 저장 비용 및 분석 지연 증가
- 알림 피로: 임계치 오탐 빈발 — 운영자 알림 무시로 실제 장애 대응 지연

> 요약: 계측 오버헤드·데이터 폭증·알림 피로가 APM 운영 실효성을 저해함

## Ⅴ. 개선방안
1. 단기: 샘플링 비율 조절(Adaptive Sampling)로 계측 오버헤드 최소화
2. 중기: 트레이스 데이터 Tail-Based Sampling 적용으로 이상 트랜잭션만 선별 저장
3. 장기: AIOps 기반 동적 임계치 설정으로 오탐률 감소 및 근본 원인 자동 추론

> 요약: 샘플링 최적화 → 선별 저장 → AIOps 연계로 APM 실효성을 제고함

## Ⅵ. 전망
- 발전 방향: OpenTelemetry 표준 기반 벤더 중립 관측가능성(Observability) 통합 확산
- 기술사적 판단: APM은 MSA·서버리스 환경에서 운영 가시성 확보의 핵심 인프라임
- 기술사 제언: 메트릭·트레이스·로그 3신호 통합 관측 체계 구축 선행 필요
