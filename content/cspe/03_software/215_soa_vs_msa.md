## Ⅰ. 개요
- 서비스를 비즈니스 단위로 분리하여 유연성과 재사용성을 높이는 아키텍처임
- 중앙 집중형 통합(SOA)에서 분산형 독립 배포(MSA)로 진화하는 추세임
| 구분 | 내용 | 비유 |
| --- | --- | --- |
| 출제의도 | SOA(ESB 중심) vs MSA(API Gateway 중심), 데이터 분산, 결합도 | 백화점(통합 관리) vs 전통시장(독립 상점) |

## Ⅱ. 구성요소
- SOA는 중앙 서비스 버스, MSA는 서비스 간 직접 통신 또는 게이트웨이 활용함
[SOA: App <-> ESB <-> App]
[MSA: App -> Gateway -> Microservices]
- 구성요소 표
| 구성요소 | 설명 | 비유 |
| --- | --- | --- |
| ESB (SOA) | 서비스 간 메시지 변환 및 라우팅을 담당하는 거대한 중앙 고속도로 | 터미널 환승 센터 |
| Microservice (MSA) | 작고 독립적으로 배포 가능한 단위 서비스 (Polyglot 지원) | 푸드트럭 각각의 주방 |
| API Gateway | MSA의 진입점으로 인증, 라우팅, 부하 분산을 수행하는 단일 창구 | 아파트 보안 데스크 |
> 요약: SOA는 재사용과 전사적 통합, MSA는 독립적 확장과 빠른 배포에 강점임

## Ⅲ. 절차
- 아키텍처 전환 및 서비스 구현 전략임
[서비스 식별] -> [바운디드 컨텍스트 설정] -> [독립 배포] -> [오케스트레이션]
- 4단계 설명
1) 도메인 분할: DDD(Domain Driven Design)를 통해 서비스 경계를 확정함
2) 데이터베이스 분리: MSA의 경우 서비스별 전용 DB(Database per Service) 할당함
3) 통신 설계: 동기(REST/gRPC) 및 비동기(Kafka/RabbitMQ) 방식 혼합 사용함
4) 운영 자동화: CI/CD 파이프라인 및 컨테이너 오케스트레이션(K8s) 적용함
> 요약: 중앙 제어의 복잡성을 줄이고 분산 서비스의 자율성을 극대화함

## Ⅳ. 문제점
- MSA는 분산 트랜잭션 관리와 데이터 일관성 유지가 매우 어려움 (원인: DB 분산)
- 서비스 간 호출 네트워크 증가로 인한 지연 시간 및 복잡도 급증함 (원인: 통신 오버헤드)

## Ⅴ. 개선방안
- (단기) Saga 패턴 또는 TCC(Try-Confirm-Cancel)를 통한 분산 데이터 정합성 관리함
- (중기) 서비스 메쉬(Istio 등) 도입으로 통신 가시성 및 보안 통제 강화함
- (장기) 비즈니스 중요도에 따라 모놀리식과 마이크로서비스를 혼합한 모듈러 모놀리스 검토함

## Ⅵ. 전망
- 향후 아키텍처는 무조건적인 MSA 지향보다는 '적정 규모(Right-sized)' 서비스 설계로 회귀할 것임
- 서버리스와 MSA가 결합된 지능형 서버리스 아키텍처가 차세대 표준이 될 것임
