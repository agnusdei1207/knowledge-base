# 📖 【암기용】 개념 완전 이해

> 목적: 운영 프로파일 기반 테스트를 처음 봐도 왜 "모든 기능을 똑같이 테스트하는 것"이 실제로는 불균등한 결과를 낳는지 수치로 이해하게 만든다. 시험 답안 양식이 아니라, 이해를 위한 설명이다.

## 한눈에
- **개요**: **운영 프로파일 기반 테스트**는 실제 운영 환경에서 수집한 사용 시나리오와 그 발생 확률(**운영 프로파일**)을 근거로 테스트 케이스와 부하 배분의 우선순위를 정하는 **신뢰도(Reliability)** 중심 테스트 기법이다.
- **왜 필요한가**: 기능이 10개면 테스트도 10개에 균등히 배분하는 것이 공정해 보이지만, 실제 사용자는 그 10개 기능을 균등하게 쓰지 않는다. 사용자가 자주 지나가는 경로에 작은 결함이 있으면 장애 건수가 크게 늘고, 거의 안 쓰는 경로의 결함은 실제로는 사용자에게 거의 노출되지 않는다.
- **핵심 직관**: 시험 범위 전체를 균등하게 공부하는 것이 아니라, 실제 기출 빈도에 맞춰 공부 시간을 배분하는 것과 같다. 자주 나오는 유형에 결함(실수)이 남아 있으면 시험(운영)에서 훨씬 자주 틀리기 때문이다.

## 핵심 용어 정리 (내부에 등장하는 것들)

| 용어 | 의미 | 비유 |
|:---|:---|:---|
| 신뢰도(Software Reliability) | 정해진 조건에서 시스템이 결함 없이 동작할 확률 — 이 테스트가 궁극적으로 높이려는 **대상** | 제품의 무결점 비율(불량률의 반대) |
| 운영 프로파일(Operational Profile) | 사용 시나리오별 발생 확률을 정리한 분포표 | 여론조사 응답 비율표 |
| 시나리오 마이닝 | 로그·APM·비즈니스 이벤트에서 사용자 행동 패턴과 빈도를 추출하는 작업 | 마트 CCTV로 동선을 분석해 매대 배치를 정하는 것 |
| 위험 가중치(Risk Weight) | 발생 확률 × 업무 영향도로 계산한, 빈도만으로는 못 잡는 보정값 | 보험료 산정(발생확률 × 손해액) |
| MTBF(평균 고장 간격) | 고장과 고장 사이 평균 정상 동작 시간 | 부품 평균 수명 |
| Escaped Defect Rate | 테스트를 통과하고 출시된 뒤 운영에서 발견된 결함 비율 | 검수를 통과했지만 매장에서 발견된 불량품 비율 |

## 깊이 이해

### 왜 이 기법이 등장했나 (배경)
- 1990년대 벨연구소의 John Musa가 제안한 **Software Reliability Engineering**(약칭 SRE, 소프트웨어 신뢰성 공학)의 핵심 기법이다. 기능 명세 기반 테스트("이 버튼이 명세대로 동작하는가")는 기능의 존재를 확인할 뿐, "출시 후 사용자가 결함을 마주칠 확률"은 답하지 못한다는 문제의식에서 출발했다.
- 주의: 이 약칭 SRE는 구글이 정립한 **Site Reliability Engineering**(191번 파일, 운영 신뢰성 공학)과 이름이 같지만 완전히 다른 개념이다. 전자는 1990년대 테스트 설계 기법, 후자는 2000년대 이후 운영 조직 체계다.

### 균등 테스트가 놓치는 것 — 노출 건수를 수치로 비교하기
- 쇼핑몰의 월간 트랜잭션이 100만 건이고, 상품조회 70%·장바구니 20%·결제 10%로 구성된다고 하자. 균등 테스트 방식이라면 3개 모듈에 테스트 케이스를 각각 33%씩 배분한다.
- 그런데 세 모듈에 결함 밀도가 동일하게(1,000건당 1건 결함) 남아 있다고 가정하면, 실제 운영에서 사용자가 그 결함을 마주치는 횟수는 조회 700건, 장바구니 200건, 결제 100건으로 **7배 차이**가 난다. 결함 밀도가 같아도 사용자 노출 횟수는 사용 빈도에 비례해 커지기 때문이다.
- 따라서 테스트 케이스 배분도 노출 확률에 비례해야 한다: 테스트 예산 1,000건이면 조회 700건·장바구니 200건·결제 100건으로 배분하는 것이, 각 모듈이 실제로 유발할 장애 건수를 균형 있게 줄이는 방법이다.

### 위험 가중치로 보정하기 — 빈도만으로는 부족한 이유
- 위 계산대로만 하면 결제(10%)는 테스트 자원을 가장 적게 받는다. 하지만 결제 결함 1건의 업무 영향도(금전 손실, 법적 책임)가 조회 결함보다 훨씬 크다.
- 그래서 실제 배분 비중은 "발생확률 × 업무영향도"로 정규화한다. 예를 들어 조회의 영향도 점수를 1, 결제의 영향도 점수를 5로 두면, 위험 가중치는 조회 70×1=70, 결제 10×5=50이 되어 결제가 처음 계산(10%)보다 훨씬 큰 비중(약 42%)을 받게 조정된다. 이것이 "저빈도 고위험 케이스는 별도로 필수화한다"는 원칙의 계산적 근거다.

### 비유와 흔한 오해
- **비유**: 지하철 안전 점검에서 하루 10명이 쓰는 비상구와 10만 명이 쓰는 환승 통로를 같은 횟수로 점검하지 않는 것과 같다. 통로가 넓어서가 아니라, 결함(고장) 하나가 영향을 미치는 사람 수가 다르기 때문이다.
- **오해**: 사용 빈도가 낮은 기능을 테스트에서 버려도 된다는 뜻이 아니다. 법규·보안·결제처럼 발생은 드물어도 영향도가 큰 경로는 위험 가중치로 별도 보정해 필수 케이스로 지정해야 한다 — 빈도만 보면 이런 경로가 테스트에서 사라지는 것이 이 기법의 가장 흔한 오용이다.

## 연결 개념
- Software Reliability Engineering(John Musa, 1990년대) — 이 기법이 속한 상위 방법론
- 191 Site Reliability Engineering — 이름은 같은 약칭(SRE)이지만 다른 개념(운영 조직 체계), 혼동 주의
- 312 성능 테스트 지표 — 운영 프로파일을 부하 테스트의 트랜잭션 비율로 반영할 때 연결(후행)

# 📝 【답안용】 시험 답안 템플릿

> 목적: 시험장에서 25분에 그대로 쓰는 답안 양식. 운영 프로파일 기반 테스트는 실제 사용 빈도와 업무 영향도를 반영한 테스트 우선순위로 답한다.

## 핵심 인사이트 (3줄 요약)

> 1. **본질**: 운영 프로파일 기반 테스트는 실제 운영 시나리오와 발생 확률을 모델링해 테스트 케이스·부하·신뢰도 검증 비중을 배분하는 기법이다.
> 2. **가치**: 사용자에게 많이 노출되는 경로의 결함 발견 확률을 높여 운영 장애 건수와 오류 예산 소모를 줄인다.
> 3. **판단 포인트**: 빈도만 보지 말고 결제·보안·규제 기능처럼 영향도가 큰 경로에는 위험 가중치를 추가한다.

## 출제 의도 및 답안 포인트

| 출제 의도 | 반드시 짚을 핵심 | 감점 회피 포인트 |
|:---|:---|:---|
| 테스트 우선순위 설계 확인 | 운영 시나리오, 사용 확률, 위험 가중치 | 기능 목록을 균등 테스트한다고 서술 |
| 신뢰도 평가 이해 확인 | 사용 빈도 기반 결함 발견, reliability estimate | 단순 커버리지와 동일시 |
| 운영 데이터 활용 확인 | 로그, APM, 이벤트, SLO | 운영 데이터 품질과 갱신 주기 누락 |

> 요약: 이 문제는 실제 사용 확률과 영향도를 반영해 테스트 자원을 배분하는 능력을 요구한다.

## Ⅰ. 개요 및 필요성

- 개요: 실제 사용 빈도 기반 테스트 설계
- 배경: 기능 수 기준 균등 테스트는 사용자 영향이 큰 경로를 충분히 검증하지 못함
- 필요성: 운영 로그, 이벤트, 트랜잭션 비율로 시나리오 확률을 산정해 테스트 비중과 결함 우선순위를 조정해야 함

## Ⅱ. 구조 및 구성요소

```text
Operation Log -> Scenario Mining -> Probability Model -> Test Design -> Execution -> Reliability Report
  / Risk Weight
  / SLO
  / Feedback
```

| 구성요소 | 역할 | 특이사항 |
|:---|:---|:---|
| 운영 데이터 | 실제 사용자 행동 수집 | 로그, APM, clickstream |
| 운영 프로파일 | 시나리오별 발생 확률 모델 | 조회 70%, 장바구니 20%, 결제 10% |
| 테스트 설계 | 확률·위험 기반 케이스 배분 | 경계값·오류 경로 포함 |
| 신뢰도 리포트 | 결함률·MTBF·SLO 영향 분석 | 릴리스 승인 근거 |

> 요약: 운영 데이터에서 확률 모델을 만들고 테스트 설계와 신뢰도 보고서로 연결한다.

## Ⅲ. 동작원리 및 흐름도

```text
로그 수집 -> 시나리오 분류 -> 발생 확률 산정 -> 위험 가중치 적용 -> 테스트 실행 -> 프로파일 갱신
```

| 단계 | 처리 내용 | 검증 기준 |
|:---:|:---|:---|
| 1 | 운영 로그·이벤트 수집 | 표본 기간 2~4주 |
| 2 | 사용자 시나리오 분류 | 상위 20개 경로 80% 커버 |
| 3 | 발생 확률·위험 가중치 산정 | 빈도×업무 영향도 |
| 4 | 테스트 케이스·부하 배분 | 프로파일 오차 5%p 이하 |
| 5 | 결함·신뢰도 분석 후 갱신 | 결함 밀도, MTBF, SLO |

> 요약: 운영 프로파일은 로그 기반 확률 산정, 위험 보정, 테스트 실행, 갱신의 반복 절차로 운영된다.

> 요약: 표본 왜곡, 저빈도 고위험 누락, 로그 품질 문제를 보정해야 테스트 우선순위가 타당하다.

> 요약: 적용 성과는 경로 커버리지, 운영 결함률, 트랜잭션 분포 재현성으로 측정한다.

## Ⅵ. 실무 적용 및 결론

**적용 방안 3개 (필수):**
1. 최근 4주 APM·이벤트 로그에서 상위 사용자 경로를 추출하고 발생 확률과 업무 영향도를 곱해 테스트 우선순위를 산정함.
2. 부하 테스트는 실제 transaction mix를 반영해 조회 70%, 장바구니 20%, 결제 10%처럼 구성하고 오차 5%p 이하를 목표로 함.
3. 결제·인증·개인정보 기능은 사용 빈도와 무관하게 고위험 필수 케이스로 지정하고 릴리스 게이트에 포함함.

**결론 (2줄):**
- 기술사 판단: 사용자 행동 로그가 확보되고 운영 신뢰도가 목표인 서비스는 운영 프로파일 기반 테스트, 초기 개발 단계는 위험 기반 테스트를 병행함.
- 향후 방향: 운영 프로파일은 SLO, AIOps 이상 탐지, 자동 테스트 케이스 생성과 결합해 지속 테스트 체계로 확장됨.
