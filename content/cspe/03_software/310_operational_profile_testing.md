## 핵심 인사이트 (3줄 요약)
- 100가지 기능이 있는 소프트웨어를 납품할 때, 개발팀은 100가지 기능에 1/100씩 균등하게 시간을 쪼개서 테스트를 함. 그리고 오픈 첫날, 사람들이 90% 확률로 클릭하는 '로그인' 버튼에서 서버가 터짐. (삽질).
- **운영 프로파일(Operational Profile)**은 **"실제 사용자가 이 시스템을 쓸 때, 어떤 기능을 얼마나 자주 쓸까?"에 대한 통계 확률 지도**임. (예: 상품 검색 70%, 장바구니 20%, 회원탈퇴 1%).
- 이 확률 지도를 바탕으로, 사용빈도가 압도적으로 높은 기능(검색)에 테스트 자원과 시간의 90%를 몰빵하여, **가장 자주 일어나는 장애를 우선적으로 막아내는 극강의 가성비 테스트 전략**임.

## Ⅰ. 개요 및 필요성
- **개요**: 시스템의 실제 운영 환경에서 각 기능이 사용될 확률(발생 빈도)을 정량적으로 모델링하고, 확률이 높은 기능에 테스트 케이스와 자원을 집중 할당하는 신뢰성(Reliability) 기반 테스트 기법.
- **필요성**: 테스트 시간은 1주일밖에 안 남았음. 기능은 1,000개임. 무작위로 테스트하면 정작 제일 중요한 메인 화면은 1번만 테스트하고, 1년에 한 번 쓸까 말까 한 '비밀번호 5번 틀렸을 때 이메일 인증' 기능을 10번 테스트하는 뻘짓을 하게 됨. **"아니, 무식하게 N분의 1로 테스트하지 말고, 실제 고객이 매일같이 누르는 버튼부터 확률적으로 가중치를 둬서 집중 테스트해야 하는 거 아냐?"**

## Ⅱ. 핵심 아키텍처 및 동작 원리 (프로파일 도출 5단계)
Musa(무사)가 제안한 운영 프로파일 도출 절차.

- **1. 고객(Customer) 프로파일**:
  - 누가 이 시스템을 쓰는가? (예: 일반 구매자 90%, 상점 주인 9%, 시스템 관리자 1%).
- **2. 사용자(User) 프로파일**:
  - 구매자는 보통 어떤 성향인가? (예: 모바일 접속자 80%, PC 접속자 20%).
- **3. 시스템 모드(System Mode) 프로파일**:
  - 어느 시간대에 트래픽이 몰리는가? (예: 평시 모드 80%, 블랙프라이데이 폭주 모드 20%).
- **4. 기능(Functional) 프로파일**:
  - 어떤 기능을 가장 많이 쓰는가? (예: 상품 조회 60%, 장바구니 담기 30%, 환불 10%).
- **5. 운영(Operational) 프로파일 (최종)**:
  - 위 확률을 다 곱해서 최종 표를 만듦.
  - `A 작업 (모바일 구매자의 평시 상품 조회) = 발생 확률 43% ➡️ 전체 테스트 케이스의 43% 할당!`
  - `B 작업 (PC 관리자의 폭주 시 서버 리부팅) = 발생 확률 0.01% ➡️ 테스트 케이스 1개만 할당.`

```text
[ 전통적 테스트 vs 운영 프로파일 기반 테스트 ]

 🎲 [ 전통적 균등 테스트 (Coverage 중심) ]
 기능 1부터 100까지 각각 10시간씩 똑같이 테스트함.
 결과: 1년에 한 번 쓰는 기능의 버그는 완벽히 잡았으나, 매일 100만 명이 쓰는 메인 페이지 성능 테스트는 부족해서 오픈 당일 서버 뻗음.

 📊 [ 운영 프로파일 테스트 (Risk & Usage 중심) ]
 통계를 돌려보니 '로그인'과 '결제'가 전체 사용의 90%를 차지함.
 결과: 테스트 기간 100일 중 90일을 두 기능에 몰빵. 오픈 당일 치명적 장애 확률 0%에 수렴!
```

## Ⅲ. 오해와 진실
| 오해 | 진실 |
|---|---|
| "확률이 낮은 기능은 아예 테스트를 안 해도 된다는 건가요?" | **아님.** 확률이 낮아도, 한 번 실패했을 때 회사가 망할 정도의 치명적 피해(예: 관리자의 DB 초기화 버튼)를 주는 기능이라면 **위험도(Risk)**를 가중치로 곱해서 테스트 케이스를 강제로 늘려야 함. 운영 프로파일은 '빈도'를 따지지만, 궁극적으로는 빈도 * 치명도를 고려한 '리스크 기반 테스트'와 융합되어야 함. |
| "오픈 전인 새 시스템은 사용자 통계 데이터가 없는데 어떻게 확률을 구함?" | 이전 레거시 시스템의 로그, 경쟁사 데이터, 기획자의 델파이 기법(전문가 합의), 알파/베타 테스트의 로그를 영혼까지 끌어모아 추정(Estimation)해야 함. 데이터가 쌓이면 릴리스마다 프로파일을 업데이트함. |

## Ⅳ. 실무 적용 및 기술사 판단
- **클라우드 네이티브/MSA 성능 테스트 기준선 수립**: 기술사는 Jmeter나 nGrinder로 부하 테스트(Load Test)를 수행할 때, "그냥 API 10개를 100 TPS로 똑같이 쏘세요"라고 지시하면 아마추어임. 반드시 **운영 프로파일에 따라 "조회 API 80 TPS, 주문 API 15 TPS, 결제 API 5 TPS" 비율로 섞어서 쏘도록 시나리오를 설계**해야만 실제 라이브와 유사한 병목(Bottleneck)을 찾을 수 있음.
- **SRE 지표(SLI/SLO)와의 연계**: 운영 프로파일의 상위 10% 핵심 사용자 여정(Critical User Journey)을 추출하여, 이를 사이트 신뢰성 공학(SRE)의 주요 SLI(서비스 수준 지표)로 맵핑하고, 이 구간의 가용성만큼은 99.99%를 사수하는 모니터링/경보 체계를 최우선으로 구축해야 함.

## Ⅴ. 기대효과 및 결론
- 한정된 예산과 턱없이 부족한 테스트 시간 속에서, 고객이 피부로 느끼는 체감 신뢰도(Perceived Reliability)를 극대화하는 가장 공학적인 자원 분배법임.
- "모든 코드를 다 100% 커버하겠다"는 비현실적 강박에서 벗어나, 데이터와 통계 확률을 무기로 "가장 중요한 전장부터 지켜낸다"는 실용주의 테스트 전략의 정수임.

### 👶 어린이를 위한 3줄 비유 설명
1. 내가 만든 게임에 방패, 칼, 활, 마법 지팡이 4개의 무기가 있어요. 버그를 잡을 시간이 10시간밖에 없어요.
2. 예전엔 4개 무기를 똑같이 2.5시간씩 검사했어요. 근데 알고 보니 유저의 90%는 '칼'만 쓰고 지팡이는 아무도 안 써요. (시간 낭비!)
3. **운영 프로파일 테스트**는 유저가 가장 많이 쓰는 '칼'에 9시간을 몰빵해서 검사하는 거예요. 그래서 유저들이 "와, 이 게임 버그 하나도 없네!"라고 느끼게 만드는 똑똑한 시간 활용법이랍니다!

### 🔀 문제 유형별 목차 전환 (이 키워드 출제 시)
- **개념/프로세스형 (Ⅱ·Ⅲ 강조)**: John Musa의 운영 프로파일 도출 5단계(고객 ➡️ 사용자 ➡️ 시스템 모드 ➡️ 기능 ➡️ 운영 프로파일) 상세 서술. 균등 테스트 대비 체감 신뢰성 향상 메커니즘 도식화.
- **성능/SRE 실무형 (Ⅳ·Ⅴ 강조)**: 대규모 트래픽 부하 테스트(Load Test) 수행 시 운영 프로파일을 활용한 시나리오 및 Workload Mix 비율 산정 방법. SRE의 Critical User Journey 식별 및 리스크 기반 테스트(Risk-based Testing)와의 융합을 통한 한정된 자원 배분 전략.
