## 핵심 인사이트 (3줄 요약)
- 24시간 365일 무중단 서비스를 제공하기 위해, 새 버전의 코드를 배포할 때 사용자가 서버의 다운타임(Downtime)을 전혀 느끼지 못하게 라우팅을 조작하는 전략.
- **블루-그린(Blue-Green)**: 구 버전(Blue)과 똑같은 규모의 신 버전(Green)을 띄워놓고, 로드밸런서의 스위치를 1초 만에 딸깍 전환하는 '안전하고 빠른 롤백'의 대명사.
- **카나리(Canary)**: 새 버전을 소수(예: 5%)의 실 트래픽에만 먼저 노출시켜 에러율을 간 본 뒤, 점진적으로 100%까지 늘려가는 '리스크 최소화' 전략.

## Ⅰ. 개요 및 필요성
- **개요**: 클라우드와 K8s 환경에서 애플리케이션의 가용성을 100% 유지하면서 새 버전(v2)으로 교체하는 릴리즈 기법.
- **필요성**: 과거의 '빅뱅 배포'는 주말 새벽에 점검 공지를 띄우고 서버를 껐다 켜야 했음. 만약 버그가 터지면 아침까지 롤백하느라 개발자들이 밤을 새웠음. 넷플릭스처럼 하루에 천 번 배포하는 시대에는 서버를 내리지 않고 배포와 롤백을 수행할 아키텍처가 필수적임.
---
## Ⅱ. 아키텍처 및 핵심 원리
- **블루-그린 배포**:
  - Blue(v1)가 서비스 중일 때, 별도의 인프라에 Green(v2)을 완벽히 세팅함.
  - QA가 내부적으로 Green을 테스트한 후, 로드밸런서(Router)가 트래픽을 Green으로 한 번에(100%) 돌림.
  - 문제가 생기면 로드밸런서만 다시 Blue로 돌리면 1초 만에 롤백됨.
- **카나리 배포**:
  - 광부들이 유독가스를 감지하기 위해 카나리아 새를 데려간 것에서 유래.
  - 기존 v1 서버 95대, 신규 v2 서버 5대를 두고 로드밸런싱함.
  - 모니터링 시스템(Prometheus)이 v2의 에러율, 응답시간을 분석함. 이상이 없으면 v2의 비중을 20% ➡️ 50% ➡️ 100%로 점차 올림.

```text
[ 로드밸런서를 통한 무중단 배포 라우팅 ]

 [ 1. Blue-Green 배포 ]                 [ 2. Canary 배포 ]
 
       (User Traffic 100%)                   (User Traffic 100%)
              ⬇️                                     ⬇️
       [ Load Balancer ]                      [ Load Balancer ]
            /   (전환!) \                       (95%) /   \ (5%만)
           /           \                           /     \
  [ Blue (v1) ]   [ Green (v2) ]           [ v1 서버들 ]  [ v2 서버 ]
    (대기 상태)      (새 라이브)               (메인 팜)     (위험 탐지용)
```

## Ⅲ. 비교 및 연결
| 구분 | 롤링 배포 (Rolling Update) | 블루-그린 배포 (Blue-Green) | 카나리 배포 (Canary) |
|---|---|---|---|
| **배포 방식** | v1 인스턴스를 하나씩 v2로 교체 | v2를 100% 띄우고 라우팅 한방 전환 | v2 트래픽을 5%부터 점진적 증가 |
| **인프라 비용** | 추가 인프라 거의 필요 없음 | 인스턴스가 정확히 2배(200%) 필요 | 소폭 증가 (버전 혼재) |
| **롤백 속도** | 느림 (다시 하나씩 이전 버전 띄움) | **가장 빠름 (로드밸런서 롤백 1초)** | 비교적 빠름 |
| **데이터베이스**| 구/신 버전이 DB를 동시에 공유(스키마 호환성 필수) | 동일 (스키마 마이그레이션이 가장 큰 난관) | 동일 |
---
## Ⅳ. 실무 적용 및 기술사 판단
- **DB 스키마 마이그레이션의 지옥**: 무중단 배포의 가장 큰 적은 '소스코드'가 아니라 '데이터베이스 스키마 변경'임. v1과 v2가 동시에 도는 순간(롤링, 카나리) 양쪽 모두 호환되는 DB 스키마를 유지해야 함. 따라서 테이블 컬럼을 삭제/변경할 때는 `(1) 새 컬럼 추가 배포 ➡️ (2) 양쪽 쓰기 배포 ➡️ (3) 구 컬럼 삭제 배포`라는 3단계 확장을 거쳐야 장애를 막을 수 있음 (Expand and Contract 패턴).
- **Service Mesh의 활용**: Istio 같은 서비스 메시를 활용하면 K8s 기본 기능(Pod 개수 비율 기반)의 한계를 넘어, HTTP 헤더(`User-Agent: iPhone`)나 정확한 % 기반으로 초정밀 카나리 트래픽 라우팅이 가능해짐.
---
## Ⅴ. 기대효과 및 결론
- 배포가 비즈니스 중단을 의미하던 시대는 끝났음. 사용자는 언제 앱이 업데이트되었는지도 모른 채 항상 최신 기능을 즐기게 됨.
- 장애 발생 시 원인 분석보다 '빠른 원상 복구(MTTR 단축)'를 우선시하는 클라우드 네이티브의 핵심 생존 전략임.

### 👶 어린이를 위한 3줄 비유 설명
1. 롤링 배포는 징검다리 돌을 하나씩 새 걸로 바꾸는 거예요. 건너는 사람은 조금 불편할 수 있죠.
2. 블루-그린 배포는 옛날 다리(Blue) 옆에 튼튼한 새 다리(Green)를 완벽하게 지어놓고, 어느 날 아침 표지판만 새 다리 쪽으로 휙 돌려버리는 거예요!
3. 카나리 배포는 새 다리를 지은 뒤, 겁 없는 어른들 5명만 먼저 건너보게 해서 다리가 안 무너지는지 간을 본 다음에 모두를 건너게 하는 거랍니다!
