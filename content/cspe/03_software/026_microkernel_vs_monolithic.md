# 📖 【암기용】 개념 완전 이해

> 목적: 마이크로커널과 모놀리식 커널을 처음 봐도 완벽히 이해하게 만든다. 시험 답안 양식이 아니라, 이해를 위한 친절한 설명이다.

## 한눈에
- **개요**: OS 핵심 기능을 커널 내부에 둘지 사용자 공간 서버로 분리할지에 대한 커널 구조 비교
- **왜 필요한가**: 커널 안에서 드라이버가 오류를 내면 전체 시스템 장애로 번질 수 있다. 반대로 기능을 밖으로 빼면 IPC 비용과 설계 복잡도가 생긴다.
- **핵심 직관**: 모놀리식은 모든 부서가 한 건물 안에서 직접 협업하고, 마이크로커널은 핵심 본부만 남기고 각 부서를 별도 건물로 분리한 구조이다.

## 깊이 이해
- **배경·문제의식**: 전통 OS는 파일시스템, 네트워크, 드라이버를 커널 내부에 넣어 호출 비용을 줄였다. 그러나 드라이버 결함이 커널 패닉으로 이어져 고신뢰 시스템에서는 격리 요구가 커졌다.
- **작동 원리**: 모놀리식 커널은 프로세스 관리, 메모리, 파일시스템, 네트워크, 드라이버를 kernel mode에서 실행한다. 마이크로커널은 스케줄링, 주소공간, IPC 같은 최소 기능만 커널에 두고 파일시스템과 드라이버는 user mode 서버로 실행한다.
- **비유**: 모놀리식은 종합병원 한 층에 모든 진료과가 붙어 있어 이동이 짧다. 마이크로커널은 진료과를 별도 건물로 나눠 한 곳 장애가 전체 폐쇄로 번지는 것을 막는다.
- **구체 예시**: Linux는 모놀리식 커널에 모듈 로딩을 결합하고, Mach 계열은 마이크로커널 연구 기반을 제공했으며, QNX는 차량·산업 제어처럼 고신뢰 환경에서 사용된다.
- **흔한 오해·주의점**: 모놀리식이 무조건 낡은 구조는 아니다. Linux는 모듈, namespace, cgroup, eBPF로 확장성과 격리 일부를 보완한다.

## 연결 개념
- IPC — 마이크로커널에서 서버 간 메시지 전달 비용의 중심
- 드라이버 격리 — 결함 전파 범위를 줄이는 설계 목표
- Linux kernel module — 모놀리식 커널의 확장 구조

# 📝 【답안용】 시험 답안 템플릿

> 목적: 시험장에서 25분에 그대로 쓰는 답안 양식. 작성방식(추상표현 금지·수치·도식·문제유형 전환)을 엄격히 지킨다.
> 핵심: 커널 구조 비교는 "크다/작다"가 아니라 IPC 비용, 드라이버 격리, 장애 전파, 운영 생태계를 기준으로 작성한다.

## 핵심 인사이트 (3줄 요약)

> 1. **본질**: 마이크로커널과 모놀리식 커널은 OS 서비스를 커널 공간에 통합할지 사용자 공간 서버로 분리할지에 대한 구조 차이이다.
> 2. **가치**: 모놀리식은 직접 호출로 지연을 줄이고, 마이크로커널은 드라이버·파일시스템 장애 격리를 제공한다.
> 3. **판단 포인트**: IPC 비용, context switch, driver isolation, 실시간성, 생태계 지원을 조건별로 평가해야 한다.

## 출제 의도 및 답안 포인트

| 출제 의도 | 반드시 짚을 핵심 | 감점 회피 포인트 |
|:---|:---|:---|
| OS 구조 비교 역량 확인 | kernel mode 범위, user mode server, IPC | 마이크로커널을 단순 경량 커널로만 설명 |
| 신뢰성·성능 트레이드오프 확인 | 드라이버 격리 vs IPC overhead | Linux/Mach/QNX 사례 누락 |
| 적용 판단 확인 | 서버, 임베디드, 안전 필수 시스템 선택 기준 | 특정 구조를 절대 우위로 단정 |

> 요약: 이 문제는 커널 내부 배치와 격리 수준을 성능·신뢰성·생태계 관점에서 비교하는 판단형 문제이다.

---

## Ⅰ. 개요 및 필요성

- 개요: 커널 구조는 OS 서비스 배치 방식이다.
- 배경: 모놀리식 커널은 파일시스템·네트워크·드라이버를 커널 내부에 두고, 마이크로커널은 IPC와 스케줄링 등 최소 기능만 커널에 둔다.
- 필요성: 고처리량 서버와 고신뢰 임베디드는 syscall latency, IPC 비용, driver fault isolation 기준으로 커널 구조를 선택해야 한다.

---

## Ⅱ. 구조 및 구성요소

```text
Monolithic: App -> System Call -> Kernel Services / Drivers -> Hardware
Microkernel: App -> IPC -> User Server -> IPC -> Microkernel -> Hardware
  / Core: scheduling, memory, IPC
  / Server: file, network, driver
```

| 구성요소 | 역할 | 특이사항 |
|:---|:---|:---|
| Monolithic Kernel | OS 서비스와 드라이버를 kernel mode에 통합 | Linux, traditional UNIX |
| Microkernel | 스케줄링·주소공간·IPC 최소 기능 제공 | Mach, QNX, L4 계열 |
| User Server | 파일시스템·네트워크·드라이버 서비스 수행 | 장애 격리 가능 |
| IPC | 프로세스 간 메시지 전달 | context switch와 copy 비용 |
| Driver Isolation | 드라이버 결함 격리 | 재시작·복구 설계 가능 |

> 요약: 모놀리식은 커널 내부 직접 호출, 마이크로커널은 IPC 기반 사용자 공간 서버 분리가 구조상 차이이다.

---

## Ⅲ. 동작원리 및 흐름도

```text
App 요청 -> System Call / IPC 진입 -> 커널 또는 서버 처리
  -> 드라이버 접근 -> 결과 반환 -> 장애 시 격리 / 전파 판단
```

| 단계 | 처리 내용 | 검증 기준 |
|:---:|:---|:---|
| 1 | 애플리케이션이 파일·네트워크 요청 발생 | syscall count |
| 2 | 모놀리식은 커널 내부 서비스 직접 호출 | context switch 1회 수준 |
| 3 | 마이크로커널은 IPC로 사용자 서버 호출 | IPC latency, switch count |
| 4 | 드라이버 오류 발생 시 격리 범위 결정 | kernel panic 여부 |
| 5 | 서비스 재시작 또는 커널 복구 수행 | MTTR, fault containment |

> 요약: 두 구조의 차이는 요청 처리 중 커널 내부 직접 호출을 쓰는지, IPC로 분리 서버를 호출하는지에 있다.

---

## Ⅳ. 특징

| 구분 | 기존/대안 | 본 기술 | 수치·판단 포인트 |
|:---|:---|:---|:---|
| 모놀리식 | Linux, UNIX | 커널 내부 통합 | syscall 지연·드라이버 성숙도 |
| 마이크로커널 | QNX, Mach, L4 | 최소 커널+서버 | IPC latency, fault isolation |
| 신뢰성 | 결함 시 전체 영향 가능 | 서버 재시작 설계 가능 | MTTR 1분 이하 목표 |
| 성능 | 직접 함수 호출 | IPC·context switch 추가 | p99 syscall latency |

> 요약: 모놀리식은 호출 경로가 짧고 생태계가 넓으며, 마이크로커널은 결함 격리와 안전 필수 시스템에 강점이 있다.

## Ⅴ. 심화 비교 및 적용 판단

| 비교 축 | 기존/대안 | 본 키워드 | 선택 기준 |
|:---|:---|:---|:---|
| 구조 | 단일 커널 통합 | 최소 커널+서버 분리 | 장애 격리 요구와 IPC 허용 지연 |
| 비용/성능 | 직접 호출, 캐시 locality | IPC, context switch | p99 latency 1ms 이하 워크로드 |
| 운영/위험 | 드라이버 결함 전파 | 서버 재시작 가능 | 안전 인증, 장치 드라이버 품질 |

> 요약: 범용 서버는 모놀리식, 안전 필수·임베디드 제어는 마이크로커널을 우선 검토한다.

| 리스크 | 원인 | 대응 방안 | 확인 지표 |
|:---|:---|:---|:---|
| 커널 패닉 | 드라이버 결함이 kernel mode 실행 | 드라이버 검증, 모듈 서명, 격리 | panic 월 0건 |
| IPC 지연 | 서버 분리와 context switch | zero-copy IPC, L4 계열 최적화 | IPC p99 100us 이하 |
| 생태계 부족 | 드라이버·패키지 제한 | 장치 호환성 목록, PoC | 지원 장치 100% 확인 |

> 요약: 구조 선택 리스크는 결함 전파, IPC 지연, 생태계 부족이며 검증 지표로 사전 판단한다.

| 점검 항목 | 목표 기준 | 측정 방법 |
|:---|:---|:---|
| 성능/지연 | syscall p99 1ms 이하, IPC p99 100us 이하 | lmbench, perf |
| 신뢰성 | 드라이버 장애 격리율 100% | fault injection |
| 운영/보안 | 커널 모듈 서명 100%, CVE 패치 7일 | SBOM, 취약점 스캔 |

> 요약: 커널 구조의 적합성은 지연, 장애 격리, 드라이버·패치 운영 지표로 판단한다.

## Ⅵ. 실무 적용 및 결론

**적용 방안 3개 (필수 — 단계별 또는 항목별):**
1. 범용 서버는 Linux 모놀리식 커널을 선택하고 LTS 커널, 모듈 서명, eBPF 관측으로 운영 위험을 통제한다.
2. 차량·산업 제어는 QNX 같은 마이크로커널을 검토하고 드라이버 fault injection으로 격리율 100%를 검증한다.
3. 구조 선택 전 syscall p99, IPC p99, 드라이버 지원 목록, 안전 인증 요구사항을 PoC 체크리스트로 측정한다.

**결론 (2줄):**
- 기술사 판단: 처리량·드라이버 생태계가 조건이면 모놀리식, 장애 격리·안전 인증이 조건이면 마이크로커널을 선택한다.
- 향후 방향: 범용 OS는 모듈 격리와 eBPF sandbox를 결합하고, 안전 필수 영역은 마이크로커널 기반 분리 구조를 확대한다.
