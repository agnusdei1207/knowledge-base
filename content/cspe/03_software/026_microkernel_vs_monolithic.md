# 📖 【암기용】 개념 완전 이해

## 한눈에
- **개요**: 운영체제 핵심부(커널)의 설계 아키텍처로, 모든 OS 서비스를 커널 공간에 집적하는 **모놀리식 커널**과, 최소 핵심 기능(스케줄링·메모리·IPC)만 남기고 나머지를 사용자 공간으로 분리하는 **마이크로커널**의 설계 철학 차이임.
- **왜 필요한가**: 모놀리식 커널은 드라이버 버그 하나로 전체 시스템이 패닉(SPOF)에 빠지는 문제가 있고, 마이크로커널은 IPC 오버헤드로 성능이 저하되는 문제가 있음. 워크로드 특성(고성능 vs 고신뢰)에 따라 적합한 커널 아키텍처를 선택해야 함.
- **핵심 직관**: 모놀리식은 모든 부서가 한 사무실에 모인 종합상사(빠르지만 한 부서 화재 시 전체 위험), 마이크로커널은 핵심 연락망(IPC)만 남기고 외주를 준 지주회사(안전하지만 소통 비용 발생)임.

## 핵심 용어 정리 (내부에 등장하는 것들)

| 용어/표기 | 의미 | 비유·예 |
|:---|:---|:---|
| 모놀리식 커널 (상위 키워드) | 프로세스·메모리·파일시스템·드라이버가 하나의 커널 공간에서 실행 | 대기업 내 전부서 |
| 마이크로커널 (상위 키워드) | 스케줄링·메모리·IPC만 커널에 남기고 나머지를 사용자 공간 프로세스로 분리 | 지주회사(외주 관리) |
| IPC (Inter-Process Communication) | 사용자 공간의 서비스 프로세스 간 데이터를 주고받는 메시지 패싱 메커니즘 | 외주 업체 간 사내 메신저 |
| 하이브리드 커널 | 모놀리식 성능 + 마이크로커널 사상의 절충 — Windows NT, macOS(XNU) | 핵심만 사내, 일부 외주 |
| LKM (Loadable Kernel Module) | Linux에서 런타임에 커널 모듈을 동적 탈부착하는 메커니즘 | 재건축 없이 인테리어만 변경 |
| 결함 격리 (Fault Isolation) | 한 서비스의 크래시가 전체 시스템에 전파되지 않도록 분리 | 방화벽으로 화재 확산 차단 |

## 깊이 이해
- **배경·문제의식**: 025에서 다룬 UNIX의 커널은 모놀리식 설계였음. 기능이 추가될수록 커널 코드가 수백만 줄로 비대해지고, 그래픽 카드 드라이버의 작은 오류로도 전체 커널 패닉(블루스크린)이 발생함. 1990년대 Mach 커널을 기반으로 "커널을 쪼개자"는 마이크로커널 사상이 대두됨(리누스 토발즈 vs 앤드류 타넨바움 논쟁).
- **작동 원리 비교(파일 읽기 요청 시)**:
  - **모놀리식**: 시스템 콜 -> 커널 내부에서 VFS -> 파일시스템 -> 드라이버를 함수 호출(Function Call)로 연쇄 처리. 모드 전환 1회(사용자->커널)만 발생해 빠르지만, 드라이버 버그가 커널 전체를 오염시킴.
  - **마이크로커널**: 시스템 콜 -> 커널 IPC -> 사용자 공간 파일서버 -> 커널 IPC -> 사용자 공간 디스크 드라이버. 모드 전환이 4~6회 발생해 느리지만, 드라이버가 죽어도 해당 프로세스만 재시작하면 됨(결함 격리).
- **비유**: 모놀리식은 한 냄비에 모든 재료를 넣은 부대찌개(빠르고 진하지만 하나 상하면 전체 폐기), 마이크로커널은 재료를 따로 담은 구절판(안전하고 깔끔하지만 먹을 때 손이 많이 감).
- **구체 예시**: 모놀리식 — Linux(커널 코드 3,000만 줄+), FreeBSD. 마이크로커널 — QNX(차량·항공), seL4(형식 검증), Minix, L4. 하이브리드 — Windows NT, macOS(XNU = Mach + BSD).
- **흔한 오해·주의점**: (1) "마이크로커널이 대세"는 오류 — 범용 서버·클라우드는 Linux(모놀리식)가 압도적이며, 마이크로커널은 실시간·안전 필수(자동차·항공·의료) 영역에서 강점을 가짐. (2) Linux의 LKM은 모놀리식의 유연성을 보완하지만, 모듈이 커널 공간에서 실행되므로 결함 격리는 제공하지 않음. (3) eBPF는 모놀리식 커널 내부에서 샌드박스된 코드를 실행하는 혁신으로, 마이크로커널의 안전성을 모놀리식에 부분 도입하는 효과가 있음.

## 연결 개념
- (025 UNIX 커널·쉘·파일시스템) 모놀리식 설계의 원형인 UNIX 커널 구조
- (004 프로세스 스케줄링·컨텍스트 스위칭) 마이크로커널의 IPC가 유발하는 잦은 모드 전환 비용
- SOA/MSA — 소프트웨어 아키텍처의 모놀리식 vs 마이크로서비스와 동일한 설계 철학 대비

# 📝 【답안용】 시험 답안 템플릿

## 핵심 인사이트 (3줄 요약)

> 1. **본질**: 커널 공간에 포함되는 OS 서비스의 범위를 정의하는 커널 아키텍처 설계 패러다임임.
> 2. **가치**: 모놀리식은 커널 내 함수 호출로 최고 성능을, 마이크로커널은 서비스의 사용자 공간 격리로 최고 안정성·확장성을 제공함.
> 3. **판단 포인트**: 범용 고성능 서버는 모놀리식(Linux), 무중단·실시간 임베디드(자율주행·항공)는 마이크로커널(QNX·seL4), 데스크톱은 하이브리드(Windows·macOS)를 선택함.

## 출제 의도 및 답안 포인트

| 출제 의도 | 반드시 짚을 핵심 | 감점 회피 포인트 |
|:---|:---|:---|
| 성능과 안정성의 트레이드오프 이해 | 함수 호출(성능) vs IPC 메시지(안정성), 모드 전환 횟수 차이 | "마이크로커널이 대세"식 잘못된 단정 |
| 워크로드별 적정 커널 아키텍처 선택 | 서버(모놀리식)·임베디드(마이크로)·데스크톱(하이브리드) 매핑 | 하이브리드 커널·LKM·eBPF 등 절충 기법 누락 |

> 요약: 서비스 모듈의 위치(커널 vs 사용자 공간)에 따른 IPC 횟수와 모드 전환 오버헤드를 대조하고, 워크로드별 선택 기준을 제시해야 함.

---

## Ⅰ. 개요 및 필요성

- 개요: OS 서비스를 커널 공간에 집적(모놀리식)할지, 사용자 공간으로 분리(마이크로)할지를 결정하는 커널 설계 아키텍처임
- 배경: 모놀리식 커널의 코드 비대화(Linux 3,000만 줄+)로 드라이버 버그 1건이 전체 패닉을 유발하는 SPOF 리스크 증가
- 필요성: 워크로드 특성(고성능 서버 vs 고신뢰 임베디드)에 따라 성능 최적화와 결함 격리 사이의 아키텍처적 선택이 필수임

---

## Ⅱ. 구조 및 구성요소

```text
[모놀리식 커널]                          [마이크로커널]
사용자 공간: 앱                          사용자 공간: 앱 / 파일서버 / 디바이스서버
--- 시스템 콜 ---                        --- IPC 메시지 ---
커널 공간: 스케줄러/메모리/FS/드라이버     커널 공간: 스케줄러 / 메모리 / IPC 관리기
--- H/W ---                              --- H/W ---
```

| 구성요소 | 모놀리식 커널 | 마이크로커널 |
|:---|:---|:---|
| 모듈 위치 | 파일시스템·드라이버 전부 커널 공간 상주 | 파일서버·드라이버가 사용자 공간 프로세스 |
| 통신 방식 | 커널 내 직접 함수 호출(Function Call) | 프로세스 간 메시지 패싱(IPC) |
| 결함 영향도 | 드라이버 크래시 = 전체 커널 패닉 | 해당 서비스 프로세스만 재시작(격리) |
| 모드 전환 | 시스템 콜 시 1회 | IPC마다 4~6회(사용자<->커널 왕복) |

> 요약: 모놀리식은 단일 커널 공간에서 함수 호출로 빠르게 처리하고, 마이크로커널은 서비스를 분리해 IPC로 통신하며 결함을 격리함.

---

## Ⅲ. 동작원리 및 흐름도

```text
[모놀리식] 앱 -> 시스템콜 -> (커널 內: VFS -> FS -> 드라이버) -> H/W -> 결과 반환
[마이크로] 앱 -> IPC -> 커널(중계) -> 파일서버(User) -> IPC -> 커널(중계) -> 드라이버(User) -> H/W
```

1. 시스템 콜: 앱이 파일 읽기를 요청해 커널 모드에 진입함
2. 서비스 간 통신: 모놀리식은 커널 내 함수 연쇄 호출(1회 전환), 마이크로는 IPC 중계로 4~6회 모드 전환 발생
3. H/W 제어: 디스크 컨트롤러에 I/O 명령을 전달해 데이터를 읽음
4. 결과 반환: 역순으로 데이터를 전달하며 애플리케이션으로 반환함

> 요약: 마이크로커널은 서비스 간 협력을 위해 사용자-커널 모드를 반복 전환하므로 모드 전환 오버헤드가 모놀리식 대비 수 배 발생함.

---

## Ⅳ. 특징

- 극대 성능(모놀리식): 커널 내 함수 호출로 IPC·모드 전환 오버헤드 없이 I/O 처리량이 최고 수준임
- 동적 모듈(모놀리식 보완): LKM으로 런타임에 드라이버를 탈부착 가능하지만, 커널 공간 실행이므로 결함 격리는 불가함
- 결함 격리(마이크로): 드라이버 크래시 시 해당 프로세스만 재시작해 전체 OS 무중단 운영이 가능함
- 이식성(마이크로): H/W 종속 커널 코드가 극소량이어서 새 CPU 아키텍처 포팅이 용이함

---

## Ⅴ. 심화 비교 및 적용 판단

| 구분 | 모놀리식(Linux) | 마이크로(QNX·L4) | 하이브리드(Windows·macOS) | 선택 기준 |
|:---|:---|:---|:---|:---|
| 성능 | 최고(함수 호출) | 낮음(IPC 병목) | 높음(절충) | I/O 처리량 요구 |
| 안정성 | 낮음(버그=패닉) | 최고(결함 격리) | 중간 | 무중단 운영 요구 |
| 확장성 | LKM 동적 로딩 | 서버 프로세스 추가 용이 | 두 방식 절충 | 기능 추가 빈도 |
| 적용 영역 | 클라우드·서버 | 자동차·항공·의료 | 데스크톱 | 도메인 특성 |

> 요약: 고성능 범용 서버는 모놀리식(Linux), 안전 필수 실시간은 마이크로(QNX·seL4), 데스크톱은 하이브리드(Windows·macOS)를 선택함.

**리스크·대응:**
- 마이크로커널 IPC 병목: 잦은 메시지 패싱으로 지연 발생 -> 공유 메모리 기반 IPC 최적화, L4 계열의 고속 IPC 설계 적용 (지표: IPC Latency μs)
- 모놀리식 공격 면적: 커널 코드 비대화로 CVE 취약점 증가 -> eBPF 기반 샌드박스 확장으로 커널 소스 수정 없이 기능 추가, 커널 모듈 최소화 (지표: CVE 발견 건수)

**도입 후 점검 지표:**
- 성능: I/O 처리량(Throughput) — 모놀리식 기준 마이크로커널 대비 처리량 감소율
- 안정성: 커널 패닉 발생 빈도 — 모놀리식은 MTBF, 마이크로는 서비스 재시작 횟수

---

## Ⅵ. 실무 적용 및 결론

**적용 방안 3개:**
1. 클라우드 서버(모놀리식): 높은 I/O 처리량과 네트워크 대역폭이 필수인 웹·DB 서버에 Linux 커널을 채택하고, LKM으로 드라이버를 관리함
2. 자율주행 차량(마이크로): 인포테인먼트 크래시 시에도 브레이크 제어가 정상 동작해야 하는 안전 필수 환경에 QNX·seL4(형식 검증 완료) 적용
3. eBPF 기반 하이브리드: 모놀리식 Linux 커널에 eBPF(Cilium 등)를 적용해 커널 소스 수정 없이 네트워크·보안 로직을 샌드박스에서 안전하게 실행함

**결론:**
- 기술사 판단: 커널 아키텍처 선택은 S/W 공학의 모놀리식 vs MSA 논쟁과 동일하며, 성능(응집도)과 안정성(결합도 완화)을 도메인 요건에 맞춰 판단해야 함
- 향후 방향: eBPF·Unikernel 등으로 모놀리식의 성능을 유지하면서 마이크로커널의 안전성을 부분 도입하는 유연한 하이브리드 모델로 수렴 중임
