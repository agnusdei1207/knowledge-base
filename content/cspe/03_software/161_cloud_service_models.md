# 📖 【암기용】 개념 완전 이해

> 목적: 클라우드 서비스 모델을 처음 봐도 완벽히 이해하게 만든다. 시험 답안 양식이 아니라, 이해를 위한 친절한 설명이다.

## 한눈에
- **개요**: 클라우드에서 어디까지 사업자가 맡고 어디부터 사용자가 맡는지 나누는 계층 모델
- **왜 필요한가**: 기업은 서버 구매, OS 설치, 미들웨어 운영, 애플리케이션 개발 중 어떤 범위까지 직접 통제할지 결정해야 한다.
- **핵심 직관**: IaaS는 빈 사무실 임대, PaaS는 책상과 네트워크가 깔린 사무실, SaaS는 바로 쓰는 업무 서비스에 가깝다.

## 깊이 이해
- **배경·문제의식**: 온프레미스는 하드웨어부터 애플리케이션까지 전부 기업 책임이다. 클라우드는 책임 일부를 사업자에게 이전해 초기 투자와 운영 범위를 줄이지만, 통제권도 함께 이동한다.
- **작동 원리**: IaaS는 VM·스토리지·네트워크를 제공하고 OS 이상은 사용자가 운영한다. PaaS는 런타임·DB·배포 환경까지 제공하고 사용자는 코드와 데이터에 집중한다. SaaS는 완성된 애플리케이션을 계정·권한·데이터 중심으로 사용한다.
- **비유**: IaaS는 주방만 빌리는 형태, PaaS는 조리도구와 재료 보관까지 갖춘 주방, SaaS는 식당에서 메뉴를 주문하는 형태다.
- **구체 예시**: 쇼핑몰 구축 시 IaaS는 EC2+RDS+Nginx 직접 운영, PaaS는 App Engine/Cloud Run 배포, SaaS는 Shopify처럼 주문·결제·재고 기능을 서비스로 사용한다.
- **흔한 오해·주의점**: SaaS라고 모든 책임이 사라지지 않는다. 계정 권한, 데이터 분류, 감사 로그 보존, 계약 종료 시 데이터 반출은 고객 책임이다.

## 연결 개념
- 공유 책임 모델 - 서비스 모델별 보안·운영 책임 경계
- 클라우드 배포 모델 - 퍼블릭·프라이빗·하이브리드와 결합되는 선택 축
- FinOps - IaaS·PaaS·SaaS별 비용 가시화와 사용량 통제

# 📝 【답안용】 시험 답안 템플릿

> 목적: 시험장에서 25분에 그대로 쓰는 답안 양식. 작성방식(추상표현 금지·수치·도식·문제유형 전환)을 엄격히 지킨다.
> 핵심: IaaS·PaaS·SaaS 명칭 나열이 아니라 책임 경계, 통제 수준, 비용 구조, 보안 범위를 비교해 문제 요구에 맞는 모델을 선택한다.

## 핵심 인사이트 (3줄 요약)

> 1. **본질**: 클라우드 서비스 모델은 인프라, 플랫폼, 애플리케이션 운영 책임을 사업자와 고객 사이에 나누는 계층 구분이다.
> 2. **가치**: 자본지출을 사용량 과금으로 바꾸고, OS·런타임·애플리케이션 중 내부 역량을 집중할 계층을 선택하게 한다.
> 3. **판단 포인트**: 통제권이 필요한 워크로드는 IaaS, 개발 생산성은 PaaS, 업무 기능 표준화는 SaaS가 적합하다.

## 출제 의도 및 답안 포인트

| 출제 의도 | 반드시 짚을 핵심 | 감점 회피 포인트 |
|:---|:---|:---|
| 서비스 모델별 책임 경계 확인 | IaaS, PaaS, SaaS의 관리 범위와 고객 책임 비교 | "클라우드 종류"만 나열하고 보안 책임 누락 |
| 도입 모델 선택 역량 확인 | 통제권, 개발 속도, 표준 업무, 비용 구조 비교 | 모든 업무를 SaaS로 단정 |
| 운영·보안 통제 연결 확인 | IAM, 데이터 암호화, 패치, 감사 로그 책임 분리 | 공유 책임 모델과의 연결 누락 |

> 요약: 이 문제는 서비스 모델별 책임 경계와 업무 조건에 따른 선택 기준을 요구한다.

---

## Ⅰ. 개요 및 필요성

클라우드 서비스 모델은 고객과 사업자의 운영 책임을 나누는 계층 모델이다. 인프라 구매 없이 VM·런타임·애플리케이션을 사용량 기반으로 조달한다. 기업은 규제, 개발 역량, 운영 인력, 비용 예측성을 기준으로 IaaS·PaaS·SaaS를 선택해야 한다.

---

## Ⅱ. 구조 및 구성요소

```text
Business Requirement -> SaaS 업무 기능
Business Requirement -> PaaS 런타임/DB/배포
Business Requirement -> IaaS VM/Storage/Network
                       +-> IAM/Logging/Billing 공통 통제
```

| 구성요소 | 역할 | 고객 책임 |
|:---|:---|:---|
| IaaS | 가상 서버, 스토리지, 네트워크 제공 | OS 패치, 미들웨어, 애플리케이션, 데이터 |
| PaaS | 런타임, DB, 배포 플랫폼 제공 | 코드, 설정, 데이터, 접근권한 |
| SaaS | 완성 애플리케이션 제공 | 계정, 권한, 데이터 분류, 계약 관리 |

> 요약: IaaS에서 SaaS로 갈수록 사업자 책임은 늘고 고객 통제 범위는 애플리케이션·데이터 중심으로 축소된다.

---

## Ⅲ. 동작원리 및 흐름도

```text
요구사항 식별 -> 통제권/규제/개발역량 평가 -> 서비스 모델 선택
-> IAM/네트워크/데이터 보호 설계 -> 배포/사용 -> 비용/로그 점검
```

| 단계 | 처리 내용 | 검증 기준 |
|:---:|:---|:---|
| 1 | 업무 요구와 규제 조건 분류 | 개인정보, 금융, 로그 보존 기준 |
| 2 | 책임 경계와 운영 인력 산정 | OS·DB·앱 운영 담당 지정 |
| 3 | IaaS·PaaS·SaaS 선택 | 통제권, 출시 일정, 표준 기능 적합도 |
| 4 | 운영·보안 통제 적용 | IAM, KMS, 감사 로그, 비용 태그 |

> 요약: 서비스 모델 선택은 기능 조달이 아니라 책임 경계와 통제 지표를 먼저 정하는 절차다.

---

## Ⅳ. 특징

| 구분 | 기존 온프레미스 | 클라우드 서비스 모델 | 수치·판단 포인트 |
|:---|:---|:---|:---|
| 비용 | 장비 선구매, 3~5년 감가상각 | 사용량 과금, 월별 비용 배부 | 태그 커버리지 95% 이상 |
| 운영 | 전 계층 내부 운영 | IaaS/PaaS/SaaS별 책임 분리 | 패치 책임 계층 명시 |
| 통제 | 물리 장비와 네트워크 직접 통제 | API 기반 통제, 계약 기반 SLA | SLA 99.9% 이상 여부 확인 |
| 도입 속도 | 구매·설치 수주 소요 | SaaS 계정 생성, PaaS 배포 자동화 | 배포 리드타임 시간 단위 |

> 요약: 클라우드 서비스 모델은 통제권을 일부 이전하는 대신 비용 배부, 배포 자동화, 책임 경계 명확화를 제공한다.

## Ⅴ. 심화 비교 및 적용 판단

| 비교 축 | IaaS | PaaS | SaaS |
|:---|:---|:---|:---|
| 선택 조건 | 레거시 이전, OS 제어 필요 | 신규 개발, 표준 런타임 | CRM, 협업, 회계 등 표준 업무 |
| 비용 구조 | VM·디스크·트래픽 과금 | 요청·인스턴스·DB 과금 | 사용자 수·기능 등급 과금 |
| 운영 책임 | OS부터 앱까지 고객 | 코드와 데이터 중심 | 계정·권한·데이터 중심 |

> 요약: 선택 기준은 기능보다 통제권, 내부 운영 역량, 표준화 가능성이다.

| 리스크 | 원인 | 대응 방안 | 확인 지표 |
|:---|:---|:---|:---|
| 책임 공백 | 모델별 담당 미정의 | RACI, shared responsibility matrix 작성 | 미지정 통제 항목 0개 |
| 비용 초과 | 리소스 방치, SaaS 휴면 계정 | 태그 정책, 예산 알림, 계정 정리 | 월 예산 편차 10% 이하 |
| 벤더 종속 | 전용 API·데이터 형식 의존 | 표준 API, 데이터 반출 절차, 계약 종료 조항 | 반출 리허설 연 1회 |

> 요약: 서비스 모델 도입 리스크는 책임 공백, 비용 가시성 부족, 데이터 반출 제약에서 발생한다.

| 점검 항목 | 목표 기준 | 측정 방법 |
|:---|:---|:---|
| 운영 | 패치·백업·장애 담당 100% 지정 | RACI 표, 운영 매뉴얼 |
| 보안 | IAM MFA 100%, KMS 암호화 적용 | CSPM, 감사 로그 |
| 비용 | 태그 커버리지 95%, 미사용 리소스 월 1회 제거 | FinOps 리포트, Billing Export |

> 요약: 성공 여부는 서비스 사용량이 아니라 책임 지정률, 보안 통제율, 비용 태그율로 판단한다.

## Ⅵ. 실무 적용 및 결론

**적용 방안 3개 (필수 - 단계별 또는 항목별):**
1. 워크로드 분류: 레거시·규제 시스템은 IaaS, 신규 API는 PaaS, 표준 업무는 SaaS로 분류하고 예외 승인 절차 운영
2. 책임 경계 문서화: 계층별 패치, 백업, 암호화, 로그 보존 책임을 RACI와 보안 기준선으로 등록
3. 운영 지표 연계: SLA 99.9%, 월 예산 편차 10% 이하, MFA 적용률 100%를 서비스 모델별 대시보드로 점검

**결론 (2줄):**
- 기술사 판단: 통제권과 규제가 크면 IaaS/PaaS, 표준 업무와 사용자 생산성이 목적이면 SaaS를 선택함
- 향후 방향: 서비스 모델은 컨테이너 PaaS, 서버리스, 산업별 SaaS와 결합해 책임 경계가 더 세분화됨
