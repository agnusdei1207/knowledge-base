# 📖 【암기용】 개념 완전 이해

## 한눈에
- **개요**: 클라우드 컴퓨팅에서 자원(인프라, 플랫폼, 소프트웨어)을 제공하는 3가지 기본 형태이다.
- **왜 필요한가**: 기업이 IT 자원을 직접 소유하고 관리하는 온프레미스(On-Premise) 방식은 초기 투자 비용이 크고 확장성이 떨어진다. 필요한 만큼 빌려 쓰는 모델이 필요하다.
- **핵심 직관**: 피자를 먹을 때, 재료부터 도구까지 다 사서 집에서 만드는 것(온프레미스), 냉동 피자를 사서 데워 먹는 것(IaaS), 피자 배달을 시켜 먹는 것(PaaS), 식당에 가서 먹는 것(SaaS)의 차이와 같다.

## 핵심 용어 정리

| 용어/표기 | 의미 | 비유·예 |
|:---|:---|:---|
| 온프레미스 (On-Premise) | 모든 IT 인프라를 기업이 직접 구축·관리 | "재료부터 도구까지 다 사서 집에서 피자 만들기" |
| IaaS (Infrastructure) | 서버, 스토리지, 네트워크 자원만 제공 | "냉동 피자를 사서 집 오븐으로 데워 먹기" (AWS EC2) |
| PaaS (Platform) | 인프라 위에 런타임, 미들웨어 등 개발 환경까지 제공 | "피자 배달 시켜 먹기" (AWS Elastic Beanstalk) |
| SaaS (Software) | 인프라, 플랫폼, 애플리케이션까지 모두 완성된 서비스로 제공 | "피자 식당에 가서 완성된 피자 먹기" (Google Workspace) |

## 깊이 이해
- **배경·문제의식**: 물리적 서버 구매와 관리에 많은 시간과 비용이 소모되며, 트래픽 변화에 유연하게 대처하지 못하는 기존 환경의 한계.
- **작동 원리**: 클라우드 사업자(CSP)가 가상화 기술을 이용해 물리적 자원을 논리적으로 분할하고, 고객은 필요한 만큼만 자원(IaaS), 플랫폼(PaaS), 소프트웨어(SaaS)를 구독 형태로 사용한다. 고객의 관리 영역은 IaaS -> PaaS -> SaaS로 갈수록 줄어든다.
- **비유**: IaaS는 빈 땅과 수도·전기를 빌려주는 것, PaaS는 빈 사무실(가구 포함)을 빌려주는 것, SaaS는 완비된 공유 오피스를 빌려주는 것.
- **구체 예시**: 스타트업이 초기 서버 인프라를 AWS EC2(IaaS)로 구축하고, 데이터베이스는 Amazon RDS(PaaS)를 사용하며, 사내 메일 및 협업은 Microsoft 365(SaaS)를 도입하여 초기 인프라 구축 비용(CAPEX)을 운영 비용(OPEX)으로 전환함.
- **흔한 오해·주의점**: "SaaS를 쓰면 보안 책임이 전부 클라우드 사업자에게 있다"는 오해. 데이터 자체와 접근 권한 관리는 여전히 고객의 책임이다(공유 책임 모델).

## 연결 개념
- 가상화(Virtualization) — 클라우드를 가능하게 하는 핵심 기술
- 공유 책임 모델(Shared Responsibility Model) — 서비스 모델별 보안 책임 소재
- 서버리스 컴퓨팅(Serverless) — PaaS를 넘어선 더 추상화된 실행 환경

# 📝 【답안용】 시험 답안 템플릿

## 핵심 인사이트 (3줄 요약)

> 1. **본질**: 클라우드 서비스 모델(IaaS, PaaS, SaaS)은 IT 자원의 소유권을 클라우드 사업자에게 넘기고, 사용자가 관리하는 계층의 깊이에 따라 구분되는 구독형 서비스 제공 방식이다.
> 2. **가치**: 초기 자본 지출(CAPEX)을 운영 지출(OPEX)로 전환하고, 비즈니스 요구에 따른 탄력적인 확장성(Elasticity)을 제공한다.
> 3. **판단 포인트**: 도입 시 자원 통제력(IaaS)과 관리 효율성(SaaS) 간의 트레이드오프를 고려하고, 공유 책임 모델에 기반한 보안 및 규제 준수를 판단해야 한다.

## 출제 의도 및 답안 포인트

| 출제 의도 | 반드시 짚을 핵심 | 감점 회피 포인트 |
|:---|:---|:---|
| 클라우드 서비스 계층의 이해 확인 | IaaS, PaaS, SaaS의 관리 영역 구분, 책임 공유 모델 | 각 모델의 정의만 나열함 |
| 비즈니스 환경에 맞는 모델 선택 역량 | 통제력과 관리 편의성의 트레이드오프, CAPEX/OPEX 전환 | 보안 책임을 사업자에게 전가함 |
| 최신 클라우드 진화 방향 인지 | Serverless(FaaS), XaaS로의 서비스 확장 | IaaS에만 국한된 설명 |

> 요약: 각 서비스 모델의 관리 영역 구분을 명확히 하고, 비즈니스 요구사항에 따른 적절한 모델 선택 기준과 보안 책임 분배를 서술해야 한다.

---

## Ⅰ. 개요 및 필요성

- 개요: 클라우드 서비스 모델은 제공되는 IT 자원의 추상화 수준과 사용자의 관리 통제 영역에 따라 IaaS, PaaS, SaaS로 구분되는 자원 제공 방식
- 배경: 기존 온프레미스 환경의 높은 초기 구축 비용(CAPEX), 리소스 유휴화, 트래픽 급증 시 확장 한계 노출
- 필요성: 관리 오버헤드를 줄이고 비즈니스 핵심 역량에 집중하기 위해, 자원 통제력과 관리 편의성을 교환하는 유연한 아키텍처 선택 필요

---

## Ⅱ. 구조 및 구성요소

```text
User -> [ SaaS: Application, Data ] -> End User
User -> [ PaaS: Runtime, Middleware, OS ] -> Developer
User -> [ IaaS: Virtualization, Server, Storage, Network ] -> SysAdmin
         |
         +-> Cloud Service Provider (CSP) Managed Area
```

| 구성요소 | 역할 | 특이사항 |
|:---|:---|:---|
| IaaS (Infrastructure) | 가상화된 컴퓨팅, 스토리지, 네트워크 자원 제공 | OS 및 미들웨어 관리 책임은 고객에게 있음 (예: AWS EC2) |
| PaaS (Platform) | 애플리케이션 개발·실행을 위한 플랫폼(OS, 런타임) 제공 | 개발자는 코드와 데이터 관리에 집중 (예: AWS Elastic Beanstalk) |
| SaaS (Software) | 소프트웨어와 애플리케이션을 완성된 서비스 형태로 제공 | 고객은 데이터와 접근 통제만 관리 (예: Microsoft 365, Salesforce) |

> 요약: IaaS에서 SaaS로 올라갈수록 클라우드 사업자의 관리 영역이 넓어지며, 고객의 통제력은 줄어들지만 운영 편의성은 증대된다.

---

## Ⅲ. 동작원리 및 흐름도

```text
요구사항 분석 -> 통제력/편의성 판단 -> 서비스 모델 선택
-> [IaaS: OS/App 구성] / [PaaS: Code 배포] / [SaaS: Account 설정] -> 서비스 운영
```

- 1단계 [요구사항 분석]: 비즈니스 목적, 보안 규제, 필요 자원 및 기존 시스템 호환성 분석
- 2단계 [서비스 모델 선택]: 통제력(IaaS), 개발 생산성(PaaS), 즉시 도입(SaaS) 중 우선순위 기반 모델 선정
- 3단계 [자원 프로비저닝 및 구성]: IaaS는 인프라 구성, PaaS는 앱 배포, SaaS는 계정 및 권한 설정 수행
- 4단계 [운영 및 최적화]: SLA 모니터링, 오토스케일링 설정, FinOps 기반 비용 최적화 적용

> 요약: 서비스 모델 선택은 비즈니스 요구에 따른 통제력과 편의성의 교환 과정이며, 선택된 모델에 따라 배포 및 운영 방식이 달라진다.

---

## Ⅳ. 특징

- 유연성 및 확장성: 스케일업(Scale-up) 및 스케일아웃(Scale-out)을 통해 트래픽 변화에 즉각적인 대응 가능 (Elasticity)
- 비용 효율성: 초기 투자(CAPEX) 없이 사용한 만큼만 지불하는 Pay-as-you-go 과금 체계(OPEX) 적용
- 관리 영역의 트레이드오프: IaaS는 높은 커스터마이징을 제공하나 운영 부담이 크고, SaaS는 즉시 도입이 가능하나 벤더 종속성(Lock-in) 발생 우려
- 책임 공유 모델: IaaS는 인프라 보안만 CSP 책임, SaaS는 데이터/계정 외 대부분을 CSP가 책임지는 등 보안 책임이 분산됨

---

## Ⅴ. 심화 비교 및 적용 판단

| 비교 축 | IaaS | PaaS | SaaS |
|:---|:---|:---|:---|
| 주요 사용자 | 시스템 관리자 (SysAdmin) | 앱 개발자 (Developer) | 최종 사용자 (End User) |
| 고객 관리 영역 | OS, 미들웨어, 런타임, 앱, 데이터 | 앱, 데이터 | 데이터, 접근 권한 |
| 통제력 vs 편의성 | 통제력 최고 / 편의성 최저 | 통제력 중간 / 편의성 중간 | 통제력 최저 / 편의성 최고 |
| 과금 기준 | 인스턴스 시간, 스토리지 크기 | API 호출, 런타임 리소스 | 사용자 수, 기능 라이선스 |

> 요약: IaaS는 인프라 통제가 필요한 레거시 마이그레이션에, PaaS는 신규 앱 개발에, SaaS는 범용 소프트웨어 도입에 적합하다.

**리스크·대응:**
- 벤더 종속성(Lock-in): 특정 CSP 플랫폼 종속 → 컨테이너(Docker/K8s) 도입으로 멀티 클라우드 이식성 확보 (지표: 마이그레이션 소요 시간)
- 보안 책임 오인: 모든 보안을 CSP에 의존 → CSP 공유 책임 모델 기반 고객 책임 영역(데이터, 계정) 보안 강화 (지표: 보안 설정 오류 수)

**도입 후 점검 지표:**
- 리소스 효율: 예약 인스턴스 커버리지, 유휴 리소스 비율 — FinOps 도구 활용 모니터링
- 가용성: 서비스 SLA 달성률(예: 99.9%) — CSP 제공 대시보드 및 APM 측정

---

## Ⅵ. 실무 적용 및 결론

**적용 방안 3개:**
1. 레거시 시스템 마이그레이션: 기존 온프레미스 시스템을 리호스팅(Lift & Shift) 방식으로 AWS EC2(IaaS)로 전환하여 인프라 유연성 확보
2. 클라우드 네이티브 개발: 개발 생산성 극대화를 위해 AWS Elastic Beanstalk(PaaS) 또는 Serverless(FaaS) 환경에 마이크로서비스 배포
3. 범용 업무 시스템 도입: 그룹웨어, CRM 등 비핵심 도메인은 SaaS 솔루션(Salesforce, Microsoft 365)을 도입하여 운영 비용(TCO) 최소화

**결론 (2줄):**
- 기술사 판단: 클라우드 서비스 모델은 통제력과 관리 편의성의 트레이드오프이므로, 워크로드의 특성(보안, 성능, 레거시 의존성)에 따라 최적의 모델을 하이브리드로 구성해야 한다.
- 향후 방향: PaaS의 추상화가 고도화되어 인프라 관리가 완전히 사라지는 서버리스(Serverless, FaaS) 아키텍처 및 산업 특화 클라우드(Industry Cloud)로 발전 중이다.
