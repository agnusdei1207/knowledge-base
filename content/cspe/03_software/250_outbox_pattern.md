# 📖 【암기용】 개념 완전 이해

## 한눈에
- **개요**: 분산 시스템 환경에서 데이터베이스 갱신과 이벤트 메시지 발행을 하나의 트랜잭션으로 묶어 원자성을 보장하는 패턴
- **왜 필요한가**: RDB에 데이터를 저장하는 트랜잭션과 Kafka 같은 외부 메시지 브로커에 이벤트를 발행하는 작업은 서로 다른 시스템이므로 2PC(Two-Phase Commit) 없이 묶을 수 없다. 중간에 네트워크 오류가 나면 데이터는 저장됐는데 이벤트는 발행되지 않는 데이터 불일치가 발생하므로 이를 막기 위해 필요하다.
- **핵심 직관**: 편지를 보낼 때, 편지를 쓰고 봉투에 넣어 내 집 앞 '우체통(Outbox)'에 넣는 것까지를 하나의 작업으로 묶고, 우체부(Message Relay)가 우체통에 있는 편지만 나중에 가져가게 하는 방식.

## 핵심 용어 정리

| 용어/표기 | 의미 | 비유·예 |
|:---|:---|:---|
| MSA (마이크로서비스) | 독립적으로 배포 가능한 작은 서비스 단위 | 각자 주방이 있는 푸드코트 식당 |
| Event-Driven Architecture | 상태 변화를 이벤트로 발행하고 구독하는 아키텍처 | 방송국(발행자)과 라디오(구독자) |
| Transactional Outbox | 비즈니스 데이터와 이벤트를 동일 DB 트랜잭션으로 임시 저장하는 패턴 | 편지 쓰기와 우체통 넣기를 동시에 묶음 |
| Message Relay | Outbox 테이블을 읽어 메시지 브로커로 전송하는 프로세스 | 우체통에서 편지를 수거하는 우체부 |
| CDC (Change Data Capture) | DB의 트랜잭션 로그를 읽어 변경 사항을 추출하는 기술 | 식당 장부를 몰래 보고 바뀐 내역만 빼옴 |

## 깊이 이해
- **배경·문제의식**: 주문 생성(DB) 후 주문 완료 이벤트(Kafka) 발행 시, DB는 커밋 성공했는데 Kafka 발행 중 네트워크 오류가 나면 데이터 불일치가 발생한다. 반대로 분산 트랜잭션(2PC)으로 두 시스템을 묶으면 성능과 가용성이 크게 저하된다.
- **작동 원리**: 1) 서비스가 비즈니스 엔티티(예: Order) 갱신과 Outbox 엔티티(예: Event) 삽입을 동일한 로컬 DB 트랜잭션으로 묶어 실행한다. 2) 커밋 완료 시 데이터와 이벤트가 무조건 함께 저장된다. 3) 별도의 Message Relay(Polling 또는 CDC 방식)가 Outbox 테이블을 지속적으로 읽어 메시지 브로커에 전송한다. 4) 전송 확인(Ack)을 받으면 Outbox에서 이벤트를 삭제하거나 상태를 업데이트한다.
- **비유**: 집 안에서 편지를 쓰고 바로 앞마당 우체통에 넣는 것까지는 내가 100% 보장(로컬 트랜잭션)한다. 우체국(Kafka)으로 가져가는 건 우체부(Relay)가 주기적으로 와서 대신 해준다. 우체국이 문을 닫아도 편지는 우체통에 안전하게 남아 있으니 유실되지 않는다.
- **구체 예시**: 주문 서비스가 MySQL의 `Orders` 테이블에 INSERT하고, 동시에 `Outbox` 테이블에 'OrderCreated' 이벤트를 INSERT한다. 백그라운드의 Debezium(CDC 도구)이 MySQL의 binlog(트랜잭션 로그)를 읽어 Kafka에 메시지를 비동기로 전송한다.
- **흔한 오해·주의점**: Outbox 패턴이 "정확히 한 번(Exactly-once)" 처리를 보장한다고 생각하기 쉽다. 실제로는 Message Relay가 발행 후 Ack를 받기 전 죽고 재시도하면 "적어도 한 번(At-least-once)" 발행되므로 중복될 수 있다. 따라서 수신 측(Consumer)에서 멱등성(Idempotency) 방어 설계가 필수적이다.

## 연결 개념
- 멱등성 설계(Idempotency) — 수신자가 중복 메시지를 받아도 결과가 같도록 보장
- CDC (Change Data Capture) — DB 트랜잭션 로그 기반 이벤트 캡처
- Saga 패턴 — 분산 트랜잭션 환경에서 보상 트랜잭션 기반 일관성 유지 패턴
- Inbox 패턴 — 수신 측에서 중복 처리를 방지하기 위해 처리된 이벤트 ID를 기록하는 패턴

# 📝 【답안용】 시험 답안 템플릿

## 핵심 인사이트 (3줄 요약)

> 1. **본질**: 분산 환경에서 비즈니스 데이터 갱신과 이벤트 메시지 발행을 단일 로컬 트랜잭션으로 묶어 데이터 일관성을 보장하는 통합 패턴이다.
> 2. **가치**: 2PC(Two-Phase Commit)의 성능 저하와 결합도 증가를 피하면서, 메시지 유실 없는 At-least-once(적어도 한 번) 전송을 보장한다.
> 3. **판단 포인트**: 트래픽 규모와 지연 민감도에 따라 Polling 방식과 CDC 방식 중 적합한 Message Relay 아키텍처를 선택하고 멱등성을 확보해야 한다.

## 출제 의도 및 답안 포인트

| 출제 의도 | 반드시 짚을 핵심 | 감점 회피 포인트 |
|:---|:---|:---|
| 분산 트랜잭션 환경의 데이터 일관성 해결 역량 확인 | 로컬 트랜잭션 원자성, Message Relay, At-least-once, 최종 일관성 | 2PC와 Outbox의 차이점 누락 |
| 아키텍처 트레이드오프 판단 및 설계 역량 | Polling vs CDC 비교축, 수신자 측 멱등성 확보 방안 | 멱등성 설계의 중요성을 단정적으로 누락 |

> 요약: 마이크로서비스에서 외부 메시지 브로커와의 분산 트랜잭션 없이 데이터 정합성을 지키는 구조적 통제 방안을 묻는 문제다.

---

## Ⅰ. 개요 및 필요성

- 개요: 마이크로서비스 환경에서 비즈니스 테이블 갱신과 발행할 이벤트를 동일한 DB의 트랜잭션(Outbox 테이블)으로 묶어 저장하는 데이터 일관성 보장 패턴
- 배경: RDB와 메시지 브로커(Kafka 등) 간 분산 트랜잭션 적용 시 성능 병목 및 단일 장애점(SPOF) 발생 한계 존재
- 필요성: 시스템 가용성과 응답 속도를 유지하면서 메시지 유실(Loss)을 원천 방지하는 At-least-once 전송 구조 필수

---

## Ⅱ. 구조 및 구성요소

```text
서비스 요청 -> 비즈니스 서비스 -> (RDB 로컬 트랜잭션) -> 비즈니스 테이블 / Outbox 테이블
                                                     |
                                                     +-> Message Relay -> 메시지 브로커
```

| 구성요소 | 역할 | 특이사항 |
|:---|:---|:---|
| 비즈니스 테이블 | 도메인 상태 변경 데이터 저장 | Orders, Payments 등 주요 엔티티 |
| Outbox 테이블 | 발행할 이벤트 메시지를 임시 저장 | 비즈니스 데이터와 동일 DB 트랜잭션 공유 |
| Message Relay | Outbox 데이터를 읽어 브로커로 비동기 전송 | Polling Publisher 또는 CDC 기술 사용 |
| 메시지 브로커 | 캡처된 이벤트를 구독자에게 비동기 전달 | Kafka, RabbitMQ 등 메시지 큐 시스템 |

> 요약: 비즈니스 테이블과 Outbox 테이블을 로컬 트랜잭션으로 묶고, 독립적인 Message Relay가 브로커 전송을 책임지는 구조다.

---

## Ⅲ. 동작원리 및 흐름도

```text
이벤트 발생 -> DB 트랜잭션 커밋(비즈니스+Outbox) -> Relay 캡처 -> 브로커 발행 -> Outbox 갱신/삭제
```

- 1단계 [DB 동시 저장]: 서비스가 비즈니스 엔티티 처리와 이벤트 데이터를 동일 RDB 트랜잭션으로 묶어 Insert
- 2단계 [이벤트 캡처]: Message Relay가 Polling 쿼리 또는 CDC(Binlog)를 통해 Outbox 테이블의 신규 이벤트를 식별
- 3단계 [브로커 발행]: 식별된 이벤트를 Kafka 등 메시지 브로커로 비동기 Publish 수행
- 4단계 [상태 동기화]: 브로커의 Ack 수신 후 Outbox 테이블의 해당 이벤트를 삭제하거나 처리 완료(Published) 상태로 갱신

> 요약: 로컬 트랜잭션으로 메시지 저장을 100% 보장한 후, 비동기 릴레이를 통해 브로커로 이벤트를 안전하게 전달한다.

---

## Ⅳ. 특징
- 일관성 보장: 2PC 없이 로컬 DB 트랜잭션만으로 비즈니스 데이터와 이벤트 발행 간의 최종 일관성(Eventual Consistency) 확보
- 가용성 확보: 메시지 브로커 장애 시에도 서비스 로직은 DB 갱신 후 정상 응답 가능하여 시스템 간 장애 격리 달성
- At-least-once 전달: Relay 재시도 과정에서 메시지가 중복 발행될 수 있으므로 수신 측의 멱등성(Idempotency) 방어 설계 필수

> 요약: 브로커 장애로부터 서비스를 격리하여 가용성을 높이나, 중복 전달 가능성에 따른 수신측 멱등성 보완이 요구된다.

---

## Ⅴ. 심화 비교 및 적용 판단

| 분산 아키텍처 관점 | Polling Publisher | Transaction Log Tailing (CDC) | 선택 기준 |
|:---|:---|:---|:---|
| 구조 | DB 쿼리(SELECT) 주기적 실행 기반 추출 | DB 트랜잭션 로그(Binlog, WAL) 스트림 구독 | DB 부하 허용량 및 실시간성 요구 수준 |
| 비용/성능 | 구현 단순, DB 지속적 쿼리 부하 발생 가능 | 구현 복잡(Debezium 등 도입), DB 부하 최소화 | 대용량 트래픽 및 이벤트 발생 빈도 |
| 운영/위험 | Polling 주기에 따른 지연 발생, 인덱스 필요 | DB 벤더 종속적 구조, 인프라 운영 복잡도 증가 | 실시간 이벤트 전송 지연 1초 미만 요구 여부 |

> 요약: 소규모 시스템은 구현이 단순한 Polling을, 대규모 실시간 시스템은 DB 부하가 적고 지연이 짧은 CDC 방식을 선택한다.

**리스크·대응:**
- 중복 메시지 처리: Relay 전송 후 Ack 수신 전 실패 시 중복 발행 발생 → 수신 측 멱등성 처리(Idempotency Key 활용) 및 이벤트 중복 제거 필터링 적용 (지표: 중복 처리율)
- Outbox 테이블 비대화: 처리 완료 이벤트 데이터 누적으로 인한 DB 용량 및 성능 저하 → 스케줄러 기반 정기적 삭제(Purge/Archiving) 파이프라인 수행 (지표: 테이블 사이즈 및 쿼리 지연 시간)

**도입 후 점검 지표:**
- 성능/효율: 이벤트 전송 지연(End-to-End Latency) p95 500ms 이하 — APM 분산 추적(Trace ID) 기반 체인 모니터링
- 품질/운영: 이벤트 발행 실패율 0.1% 이하 — Message Relay 오류 로그 수집 및 데드 레터 큐(DLQ) 통합 모니터링

---

## Ⅵ. 실무 적용 및 결론

**적용 방안 3개:**
1. 도메인 이벤트 식별 및 표준화: Aggregate Root 변경에 따른 발생 이벤트를 식별하고, Outbox 테이블 스키마(UUID, Payload, Type, Status)를 전사 표준으로 수립
2. 비동기 릴레이 파이프라인 구축: 시스템 트래픽과 확장을 고려하여 Kafka Connect 및 Debezium(CDC) 도구를 결합한 안정적이고 부하가 적은 Message Relay 구성
3. 수신자 멱등성 통제 보장: Consumer 애플리케이션 내에 처리된 이벤트 ID를 DB에 기록하는 Inbox 패턴 또는 Redis 기반 멱등성 검증 캐시를 적용하여 중복 실행 방지

**결론 (2줄):**
- 기술사 판단: Outbox 패턴은 RDB 기반 마이크로서비스에서 데이터 정합성을 지키는 핵심 기법이나, 인프라 복잡도가 증가하므로 트래픽 규모에 맞는 Relay 방식(Polling vs CDC) 선택과 멱등성 통제가 성공을 좌우한다.
- 향후 방향: 단순 비동기 이벤트 발행을 넘어 CQRS(명령과 조회 책임 분리) 아키텍처의 데이터 동기화 파이프라인으로 결합하여, 쓰기와 읽기 성능 최적화를 동시에 달성하는 방향으로 진화해야 한다.
