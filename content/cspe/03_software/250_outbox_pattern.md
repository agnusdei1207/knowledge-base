## Ⅰ. 개요
- **정의**: DB 트랜잭션과 메시지 발행을 원자적으로 처리하기 위해 Outbox 테이블을 활용하는 패턴임
- **배경/필요성**: DB 저장과 메시지 브로커 발행이 별도 트랜잭션이면 둘 중 하나만 실패하여 데이터 불일치가 발생하므로 원자적 보장이 필요함
- **비유**: 편지를 쓰는 동시에 발송 대장에 기록하고, 우체부가 대장을 보고 수거하는 방식과 같음

| 출제 의도 | 반드시 짚을 핵심 | 감점 회피 포인트 |
|:---|:---|:---|
| 분산 트랜잭션 없이 일관성 보장 | Outbox 테이블 + CDC/Polling | 2PC와의 차이를 설명할 것 |

> 요약: DB 트랜잭션 내에 이벤트를 저장하고 별도 프로세스로 발행하여 원자성을 보장하는 패턴임

## Ⅱ. 구성요소
```text
[Service]
    |
    v
[DB Transaction]
    |--- Business Table (INSERT/UPDATE)
    |--- Outbox Table   (INSERT event)
    |
    v
[Relay / CDC]
    |
    v
[Message Broker]
```

| 구성요소 | 설명 | 비유 |
|:---|:---|:---|
| Outbox Table | 발행할 이벤트를 DB 트랜잭션 내에 저장하는 전용 테이블임 | 발송 대장 |
| Relay (Publisher) | Outbox 테이블의 미발행 이벤트를 읽어 브로커로 전송하는 프로세스임 | 우체부 |
| CDC Connector | DB 변경 로그(WAL)를 감시하여 Outbox 이벤트를 캡처하는 방식임 | 자동 감시 카메라 |
| Message Broker | 발행된 이벤트를 소비자에게 전달하는 비동기 메시징 인프라임 | 우체국 |

> 요약: Outbox 테이블, Relay/CDC, Message Broker로 원자적 이벤트 발행을 구현함

## Ⅲ. 절차
```text
비즈니스 처리 + Outbox 저장 --> Relay/CDC 감지 --> 브로커 발행 --> 소비자 처리
```
- 1단계: 비즈니스 로직과 Outbox 테이블 INSERT를 동일 DB 트랜잭션으로 실행
- 2단계: Relay(Polling) 또는 CDC가 Outbox 테이블의 미발행 레코드를 감지
- 3단계: 감지된 이벤트를 Message Broker(Kafka, RabbitMQ 등)에 발행
- 4단계: 소비자가 이벤트를 수신하여 처리(멱등성(248 참조) 적용 권장)

> 요약: 동일 트랜잭션 저장 → 감지 → 발행 → 소비 순으로 처리함

## Ⅳ. 문제점
- Outbox 테이블 비대화: 이벤트 누적으로 테이블 크기가 증가하여 DB 성능이 저하됨
- At-Least-Once 중복: Relay 재시도 시 동일 이벤트가 중복 발행될 수 있음
- Polling 지연: Polling 방식은 주기 간격만큼 이벤트 발행이 지연됨

> 요약: 테이블 비대화, 중복 발행, 발행 지연이 주요 과제임

## Ⅴ. 개선방안
1. 단기: 발행 완료 이벤트를 주기적으로 아카이브·삭제하여 Outbox 테이블 크기 관리
2. 중기: 소비자 측 멱등성(248 참조) 적용으로 중복 발행의 부작용 제거
3. 장기: CDC(Debezium 등) 기반 실시간 변경 캡처로 Polling 지연 제거

> 요약: 테이블 관리, 소비자 멱등성, CDC 전환을 통해 Outbox 패턴을 최적화함

## Ⅵ. 전망
- 발전 방향: MSA 환경에서 Saga 패턴의 이벤트 발행 보장 수단으로 표준 채택이 확대될 전망임
- 기술사적 판단: Event Sourcing(249 참조)과 결합하여 이벤트 저장·발행을 통합하는 것이 바람직함
- 기술사 제언: CDC 기반 Outbox를 인프라 표준으로 정립하여 서비스 간 데이터 일관성을 체계적으로 보장하는 것이 필요함
