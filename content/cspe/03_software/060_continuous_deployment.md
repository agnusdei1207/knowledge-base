## 핵심 인사이트 (3줄 요약)
- CI(지속적 통합)를 통해 검증된 소프트웨어를 실제 서비스 환경(Production)까지 빠르고 안전하게 배포하는 자동화 체계.
- **Continuous Delivery(제공)**는 릴리즈 승인 버튼을 사람이 누르는 반면, **Continuous Deployment(배포)**는 사람의 개입 없이 프로덕션까지 직행하는 극단적 자동화임.
- 최근에는 단순히 코드를 배포(Deploy)하는 것을 넘어, 비즈니스 가치를 사용자에게 노출(Release)하는 과정을 분리 통제하는 '점진적 딜리버리(Progressive Delivery)'로 진화하고 있음.

## Ⅰ. 개요 및 필요성
- **개요**: 빌드, 테스트, 패키징된 애플리케이션 아티팩트를 대상 환경에 배포하는 릴리즈 공학 프로세스.
- **필요성**: 개발이 아무리 빨라도 운영팀이 보안 감사와 수동 배포 스크립트를 핑계로 2주에 한 번씩만 배포한다면 비즈니스 속도는 느려짐. 개발과 운영의 벽(Silo)을 허물고(DevOps), 코드가 작성되면 즉시 고객의 피드백을 받을 수 있는 고속도로가 필요했음.
---
## Ⅱ. 아키텍처 및 핵심 원리
- **CD 파이프라인의 핵심 단계**:
  1. **Provisioning**: 인프라가 코드로 준비됨 (Terraform 등).
  2. **Deployment**: 아티팩트를 서버/컨테이너에 복사하고 실행.
  3. **Verification (Post-deployment Test)**: 배포 직후 헬스 체크 및 스모크 테스트(Smoke Test) 실행.
  4. **Rollback (원상복구)**: 에러율이 임계치를 넘으면 1분 이내에 자동으로 이전 버전으로 되돌림.
- **Deploy와 Release의 분리 (Decoupling)**:
  - **Deploy**: 코드를 서버에 올리는 기술적 행위.
  - **Release**: 새 기능을 사용자에게 보여주는 비즈니스 행위 (피처 플래그 등을 활용해 배포는 하되 노출은 나중에 함).

```text
[ Delivery vs Deployment 의 경계 차이 ]

 (CI 파이프라인)          (CD: Continuous Delivery)      (CD: Continuous Deployment)
 [ 단위 테스트 ]            [ Staging 자동 배포 ]            [ Staging 자동 배포 ]
       ⬇️                         ⬇️                             ⬇️
 [ 이미지 빌드 ]          👤 (수동 승인 / Manual Gate)    (자동 통합 테스트 통과)
       ⬇️                         ⬇️                             ⬇️
 [ 레지스트리 ]           🚀 [ Production 수동 릴리즈]   🚀 [ Production 100% 자동 배포 ]
```

## Ⅲ. 비교 및 연결
| 구분 | 릴리즈 방식 | 리스크 관리 기법 | 대상 |
|---|---|---|---|
| **빅뱅 배포 (Big Bang)** | 특정 일시에 전체 시스템을 한 번에 업데이트 | 다운타임 발생, 실패 시 롤백 매우 고통스러움 | 과거 온프레미스 |
| **블루-그린 (Blue-Green)**| 새 환경(Green)을 통째로 띄우고 라우터만 전환 | 순식간에 배포/롤백 가능, 인프라 비용 2배 | 클라우드 VM/K8s |
| **카나리 (Canary)** | 5%의 트래픽만 새 버전에 흘려보내 모니터링 | 비즈니스 영향 최소화, 에러 시 즉각 롤백 | 대규모 트래픽 서비스 |
| **점진적 딜리버리** | 피처 플래그(Feature Flag)를 통한 제어 | 코드는 이미 배포됨, UI에서 버튼만 켜고 끔 | 현대 SaaS 표준 |

## Ⅳ. 실무 적용 및 기술사 판단
- **Delivery vs Deployment의 실무적 타협**: 넷플릭스나 아마존이 아닌 이상, 금융권이나 일반적인 엔터프라이즈 환경에서 100% 무인 'Continuous Deployment'를 도입하는 것은 비즈니스 컴플라이언스(결재 프로세스) 위반임. 따라서 실무에서는 프로덕션 직전까지 완벽히 자동화하되, 최종 배포 버튼은 릴리즈 매니저(RM)나 PO가 누르는 'Continuous Delivery'가 표준(De facto)으로 통용됨.
- **롤백 역량(Rollback Capability)이 곧 배포 역량**: "배포를 잘한다"는 것은 실패하지 않는 것이 아니라, **"실패했을 때 얼마나 빨리, 사용자 모르게 원상 복구할 수 있는가(MTTR 단축)"**에 달려 있음. CD 파이프라인 설계 시 자동 롤백 스크립트는 배포 스크립트보다 더 중요하게 다뤄져야 함.
---
## Ⅴ. 기대효과 및 결론
- 지속적 배포 체계는 비즈니스 가설(A/B 테스트 등)을 하루에도 수십 번 검증할 수 있는 강력한 무기가 되며, 경쟁사보다 압도적으로 빠른 시장 적응력을 제공함.
- 개발팀에게 배포는 더 이상 주말 새벽에 하는 '두려운 행사'가 아니라, 일과 중 커피를 마시며 버튼 클릭 한 번으로 수행하는 '일상'으로 탈바꿈함.

### 👶 어린이를 위한 3줄 비유 설명
1. 장난감 공장에서 로봇을 만들 때, 포장까지 끝난 로봇(CI 완료)을 트럭에 실어 가게에 배달하는 과정이 'CD'예요.
2. 딜리버리(Delivery)는 트럭 기사님이 가게 문 앞에서 사장님(사람)의 허락을 받고 물건을 내려놓는 방식이고요,
3. 디플로이먼트(Deployment)는 로봇이 공장에서 만들어지자마자 자율주행 드론을 타고 손님 집 안으로 곧바로 슝~ 날아가는 초고속 마법 배달이랍니다!
