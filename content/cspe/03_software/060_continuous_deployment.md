# 📖 【암기용】 개념 완전 이해

## 한눈에
- **개요**: 지속적 배포(Continuous Deployment)는 코드가 커밋되고 자동화 테스트(CI)를 통과하면, 인간의 수동 승인 개입 없이 운영 환경(Production)까지 완전 자동으로 릴리스하는 극단적 자동화 프랙티스이다.
- **왜 필요한가**: 자동화된 파이프라인을 만들어도 마지막 운영 서버 배포 버튼을 "팀장이 내일 아침에 누를게"라고 미루면 결국 배포가 지연된다. 이 마지막 병목(인간의 결재)마저 기계에 맡겨 타임투마켓을 극대화한다.
- **핵심 직관**: 자율주행 배달 로봇. 공장에서 물건이 완성되면, 사람이 일일이 배달 출발 버튼을 누르지 않아도 로봇이 알아서 고객 집 앞(운영 서버)까지 안전하게 가져다 놓는 완전 무인 시스템.

## 핵심 용어 정리

| 용어/표기 | 의미 | 비유·예 |
|:---|:---|:---|
| 지속적 제공 (Continuous Delivery) | 테스트를 통과한 코드를 '배포 가능한 상태'로 대기시키며, 마지막 배포는 수동 승인 | "배송 준비 완료, 발송 버튼 눌러주세요" |
| 지속적 배포 (Continuous Deployment) | 테스트 통과 즉시 운영 서버로 '자동 배포'까지 실행 (인간 개입 제로) | "배송 준비 완료되자마자 자동 발송 출발" |
| 다크 론칭 (Dark Launching) | 코드는 배포되었으나 사용자에게는 숨겨놓고 내부에서만 테스트하는 기법 | 오픈 전 가오픈 상태 |
| 피처 플래그 (Feature Flag) | 코드 배포 후에도 특정 기능의 켜고 끄기를 런타임에 제어할 수 있는 스위치 기술 | 기능 전원 스위치 |

## 깊이 이해
- **배경·문제의식**: (059 CI/CD 파이프라인 참조) CI 파이프라인이 아무리 빨라도, 운영 배포를 위해 승인 위원회(CAB)를 거치고 심야에 작업하는 문화가 남으면 진정한 애자일이 아니다. 하루에 수천 번 배포하는 넷플릭스, 아마존처럼 속도를 높이려면 인간의 검증을 기계의 100% 자동화 테스트로 대체해야 했다.
- **작동 원리**: 지속적 제공(Delivery)과 경로가 같으나 마지막 1단계만 다르다. 코드 푸시 -> CI 빌드 -> 100% 자동화 단위/인수 테스트 통과 -> (승인 대기 없이 바로) -> 블루/그린 등 무중단 배포 실행. 
- **안전장치**: 인간이 안 보는 대신 시스템이 더 촘촘히 감시한다. 배포 직후 에러 로그율이 1%만 튀어도 스크립트가 스스로 5초 만에 이전 버전으로 롤백한다(자동 롤백).
- **흔한 오해·주의점**: Continuous Delivery(제공)와 Continuous Deployment(배포)의 약자가 둘 다 CD라서 자주 혼용되지만, "운영 서버 배포 시 수동 승인이 있는가(Delivery) 없는가(Deployment)"라는 결정적 차이가 있다. 금융권 등 규제가 엄격한 곳은 Deployment가 불가능하다.

## 연결 개념
- 무중단 배포 (Blue-Green, Canary) — 자동 배포 과정에서 사용자 접속이 끊기지 않게 하는 필수 전제 조건
- 피처 플래그 (Feature Flag) — 코드는 자동 배포하되 비즈니스 릴리스 타이밍은 마케팅 팀이 결정할 수 있게 코드와 릴리스를 분리하는 기술
- 마이크로서비스 아키텍처 (MSA) — 덩치가 작아 자동 배포의 부담이 적은 MSA 구조가 지속적 배포에 가장 적합

# 📝 【답안용】 시험 답안 템플릿

## 핵심 인사이트 (3줄 요약)

> 1. **본질**: 파이프라인의 자동화 테스트(CI)를 통과한 코드를 인간의 개입(수동 승인) 없이 운영 환경(Production)까지 즉시 릴리스하는 완전 자동화 프랙티스이다.
> 2. **가치**: 배포 대기 시간 및 승인 병목을 제로화하여 피드백 루프를 최단으로 압축하고, 하루 수십 번의 소규모 배포를 통해 버그 추적 및 롤백을 용이하게 한다.
> 3. **판단 포인트**: 완전 자동화의 전제 조건은 완벽에 가까운 자동화 테스트 커버리지와 배포 직후 이상 감지 시 즉각적인 자동 롤백 체계가 갖춰져야 한다는 점이다.

## 출제 의도 및 답안 포인트

| 출제 의도 | 반드시 짚을 핵심 | 감점 회피 포인트 |
|:---|:---|:---|
| CD 파이프라인의 개념적 분별력 확인 | 지속적 제공(Delivery)과 지속적 배포(Deployment)의 수동 개입 유무 차이 | 둘을 동일한 개념으로 혼용하여 기재 |
| 극단적 자동화에 따른 리스크 통제 방안 | 무중단 배포(블루그린, 카나리), 자동 롤백, 피처 플래그 결합 | 인간의 검증을 대체할 자동화된 안전망 서술 누락 |
| 실무 환경 제약 및 적용 판단 기준 제시 | 규제/컴플라이언스 준수 조직(금융/의료) 적용 불가성 | 모든 서비스에 무조건 도입해야 한다는 맹목적 단정 |

> 요약: 기계에 최종 배포 권한을 위임하기 위해 어떤 기술적 안전망(테스트, 롤백, 무중단)을 구축해야 하는가에 집중해야 한다.

## Ⅰ. 개요 및 필요성

- 개요: 소스 코드 병합 후 빌드 및 자동화 테스트를 통과한 결과물을 수동 승인 게이트 없이 운영 환경까지 즉각적으로 자동 릴리스하는 파이프라인 아키텍처임
- 배경: 비즈니스 속도 경쟁 심화로, 기능 개발이 완료되었음에도 정기 릴리스 일정이나 수동 결재를 기다리며 가치 창출이 지연되는 병목 발생
- 필요성: 코드 변경분(Delta)을 가장 작을 때 자주 배포함으로써 장애 발생 시 원인 추적을 단순화하고, 타임투마켓(TTM)을 극대화하기 위한 완전 자동화 필수

---

## Ⅱ. 구조 및 구성요소

```text
[ Git Commit ] -> [ CI Build / 자동화 테스트 ] -> [ Staging 인수 테스트 ] -> (수동 개입 없음) -> [ 운영 서버 무중단 배포 ]
 (코드 작성)           (단위/통합 단위)               (E2E/부하 테스트)         자동 패스         (카나리 / 자동 롤백)
```

| 구성요소 관점 | Continuous Delivery (지속적 제공) | Continuous Deployment (지속적 배포) |
|:---|:---|:---|
| 파이프라인 종착지 | 배포 가능한 상태(Artifact)로 대기 (Staging) | 운영(Production) 서버까지 도달 |
| 승인 방식 (Gate) | 배포 담당자 또는 비즈니스 책임자의 수동 승인 대기 | 테스트 통과 시 조건 없는 완전 자동 승인 |
| 적합한 환경 | 금융, 의료 등 규제와 컴플라이언스가 엄격한 도메인 | SaaS 기반 웹 서비스, 스타트업 (장애 감내성 높음) |

> 요약: 양자의 차이는 파이프라인 마지막 구간의 문지기를 "인간(Delivery)이 하느냐, 시스템 통과 결과(Deployment)가 하느냐"에 있다.

---

## Ⅲ. 동작원리 및 흐름도

```text
코드 병합 -> 빌드 및 100% 테스트 자동 수행 -> (패스) -> 운영 카나리 배포 -> 모니터링 분석 -> 100% 트래픽 전환
```

- 1단계 [코드 기반 품질 검증]: 코드 푸시 직후 단위 테스트, 통합 테스트, 정적 분석을 통해 빌드 무결성을 기계적으로 검증
- 2단계 [인수 테스트 자동화]: 스테이징 환경에 배포 후 Selenium 등을 통한 E2E(End-to-End) 테스트와 부하 테스트 스크립트 자동 실행
- 3단계 [조건부 무인 릴리스]: 위 모든 테스트를 에러율 0%로 통과하면, 승인 절차 없이 즉시 운영 환경의 일부 노드(Canary)에 배포 실행
- 4단계 [지표 기반 자동 롤백]: 배포 후 5분간 500 에러 증가율 및 지연(Latency) 지표를 자동 모니터링하고, 이상 징후 감지 시 이전 버전으로 즉시 자동 롤백

> 요약: 인간의 육안 검증을 완벽하게 대체하기 위해, 철저한 테스트 자동화와 운영 메트릭 기반의 기계적 롤백이 맞물려 동작한다.

## Ⅳ. 특징

- 배포 리스크의 파편화: 거대한 릴리스를 분기에 1번 배포(고위험)하는 대신, 하루 수십 번의 극소규모 배포(저위험)로 전환하여 버그 범위 축소
- 비즈니스 민첩성 극대화: A/B 테스트와 고객 피드백 루프가 즉각적으로 가동되어, 가설 검증과 서비스 피벗(Pivot)을 초고속으로 수행 가능
- 엄격한 전제 조건: 테스트 커버리지가 낮거나 테스트 코드가 취약한 상태에서 지속적 배포를 가동하면 운영 환경 대규모 장애를 양산하는 역효과 초래

> 요약: 소프트웨어 딜리버리의 궁극적 지향점이나, 이를 안전하게 운영하려면 최고 수준의 테스트 엔지니어링 역량이 뒷받침되어야 한다.

## Ⅴ. 심화 비교 및 적용 판단

| 비교 축 | 수동 배포 기반 | 지속적 배포 (Continuous Deployment) | 선택 기준 |
|:---|:---|:---|:---|
| 배포 빈도 | 월 1회 ~ 주 1회 (정기 릴리스) | 일 수십 회 ~ 수백 회 (온디맨드) | 시장의 기능 출시 속도 요구 |
| 장애 식별 | 변경된 코드가 너무 많아 원인 파악 지연 | 방금 커밋한 몇 줄의 코드로 원인 한정 | 장애 복구 시간 (MTTR) 목표치 |
| 롤백 (Rollback) | 절차가 복잡하여 롤포워드(핫픽스) 선호 | 배포 즉시 자동 롤백 메커니즘 가동 | 인프라 자동화 시스템 성숙도 |

> 요약: 비즈니스 가치가 높은 신생 IT 기업일수록 지속적 배포를 추구하나, 인명 및 금융과 직결된 시스템은 지속적 제공(Delivery) 수준에 멈춰야 한다.

**리스크·대응:**
- 운영 장애 필터링 실패: 비정상 코드가 테스트를 우회하여 운영에 자동 배포됨 → 운영 트래픽의 1~5%만 신버전에 할당하여 검증하는 카나리(Canary) 배포 전략 적용으로 장애 영향도 5% 내 통제 (지표: 카나리 검증 성공률)
- 비즈니스 오픈 타이밍 불일치: 코드는 자동 배포되나 마케팅 발표 시점은 다음 주일 경우 기능 노출 사고 발생 → 피처 플래그(Feature Flag)를 적용하여 코드는 배포하되 기능 활성화 스위치는 Off 상태로 격리 (지표: 배포(Deployment)와 릴리스(Release)의 물리적 분리 달성)

## Ⅵ. 실무 적용 및 결론

**적용 방안 3개:**
1. 테스트 커버리지 품질 게이트 강제: SonarQube 등 코드 품질 도구를 연동하여 단위 테스트 커버리지 80% 미만 시 파이프라인 배포를 원천 차단(Fail Fast)
2. GitOps 기반 선언적 배포 도입: 쿠버네티스 환경에서 ArgoCD를 활용해, 원격 저장소의 설정값(Manifest) 변경 시 클러스터가 변경된 상태를 자동으로 Pull하여 운영에 띄우는 완전 자동화 구현
3. 다크 론칭(Dark Launching) 훈련: 사용자에게 UI를 감춘 상태로 백엔드 코드만 지속 배포하여 운영 환경 데이터 흐름을 검증한 뒤, 안정화 시 UI를 오픈하는 기법 적용

**결론 (2줄):**
- 기술사 판단: 지속적 배포는 기술 도입만으로 이루어지지 않으며, 배포 실패를 비난하지 않고 즉각 복구하는 롤백 메커니즘을 신뢰하는 데브옵스(DevOps) 문화가 정착되어야 완성됨
- 향후 방향: 최근 넷플릭스 등 선도 기업은 AI 기반 지표 분석(AIOps)을 지속적 배포 파이프라인에 결합하여 카나리 분석과 롤백 여부를 지능적으로 판단하는 수준으로 고도화 중임
