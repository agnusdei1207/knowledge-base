## 미리 알고가기

- 지속적 배포는 자동 검증을 통과한 변경을 사람 승인 없이 운영에 반영하는 방식임
- 지속적 전달은 배포 가능한 상태까지 자동화하지만 마지막 운영 반영은 사람이 승인할 수 있음
- 자동 롤백과 피처 플래그와 운영 관측이 함께 있어야 안정적으로 운영할 수 있음

## Ⅰ. 개요

- **정의/개념**: 지속적 배포는 코드 변경이 자동 검증과 품질 게이트를 통과하면 별도 수동 승인 없이 운영 환경까지 자동으로 배포되도록 하는 전달 방식임.
- **배경/필요성**: 변경을 짧은 주기로 운영에 반영하려면 병합 이후 검증·점진 배포·이상 탐지·롤백을 반복 가능한 자동 절차로 구성해야 함.

## Ⅱ. 특징

- 배포 대기 시간을 줄여 작은 변경을 자주 운영에 반영함
- 변경 단위가 작아질수록 장애 원인을 빠르게 좁힐 수 있음
- 검증 체계가 약하면 결함도 더 빨리 운영으로 퍼질 수 있음
- 점진 배포와 자동 복구가 함께 설계돼야 실효성이 생김

## Ⅲ. 종류 및 비교

| 구분 | 지속적 전달 | 지속적 배포 |
|:---|:---|:---|
| 운영 반영 방식 | 자동 검증 후 사람이 운영 배포를 승인함 | 자동 검증 후 바로 운영에 반영함 |
| 승인·반영 경로 | 자동 검증 후 수동 승인 대기 | 자동 검증 통과 후 점진 배포 시작 |
| 구조상 한계 | 승인 대기 시간이 남아 병목이 될 수 있음 | 테스트와 관측 신뢰도가 낮으면 장애 전파 속도가 빨라짐 |
| 대표 환경 | 운영 반영 전 승인 증적이 필요한 조직 | 자동 시험·관측·롤백 기준을 운영하는 온라인 서비스 |

> 요약: 지속적 배포는 배포를 자동으로 많이 하는 기술이 아니라 검증과 복구를 자동화해 운영 반영을 일상화하는 방식임.

## Ⅳ. 구성요소 및 구조

| 구성요소 | 설명 |
|:---|:---|
| 자동 테스트 체계 | 운영 승인을 대신할 만큼 신뢰할 수 있는 자동 검증 장치임 |
| 배포 정책 | 어떤 변경을 자동 배포할지 위험 기준을 정해 통제함 |
| 점진 배포 | 카나리나 블루-그린으로 위험 범위를 줄이며 운영에 반영함 |
| 빠른 롤백 체계 | 이상 징후가 보이면 즉시 이전 버전으로 되돌리는 복구 경로임 |

## Ⅴ. 원리 및 절차 흐름도

```text
+-------------+     +-------------+     +-------------+     +-------------+
| 변경 병합      | --> | 자동 검증      | --> | 점진 배포      | --> | 관측/자동 롤백 |
+-------------+     +-------------+     +-------------+     +-------------+
```

1. **변경 병합**: 기준 브랜치 변경이 자동 배포 흐름을 시작함
2. **자동 검증**: 테스트와 보안과 품질 게이트를 통과함
3. **점진 배포**: 운영에 자동 반영하되 트래픽을 단계적으로 확대함
4. **관측 및 자동 롤백**: 이상 징후가 보이면 즉시 배포를 중단하고 복구함

## Ⅵ. 실무 적용 및 유의점

1. SaaS 제품팀에서는 지속적 배포가 큰 이점을 주지만 테스트 신뢰도가 낮으면 결함도 바로 운영에 퍼지므로 자동 회귀 검증과 점진 배포를 함께 두고 변경 실패율과 롤백 시간으로 확인함
2. 고위험 기능이 섞인 서비스에서는 모든 변경을 같은 방식으로 자동 배포하지 말고 위험 기준과 피처 플래그를 함께 운영하며 자동 배포 비율과 고위험 장애 비율로 확인함

## Ⅶ. 결론

지속적 배포는 자동 검증과 점진 배포와 빠른 복구가 한 세트로 작동할 때만 성립하는 운영 모델임.
