## 미리 알고가기

- 지속적 배포는 자동 검증을 통과한 변경을 사람 승인 없이 운영에 반영하는 방식임
- 지속적 전달은 배포 가능한 상태까지 자동화하지만 마지막 운영 반영은 사람이 승인할 수 있음
- 자동 롤백과 피처 플래그와 운영 관측이 함께 있어야 안정적으로 운영할 수 있음

## 작성 근거(검토용)

- 지속적 배포는 운영 반영 방식, 승인 경로, 장애 전파 위험, 적용 환경을 핵심 비교축으로 선정함
- 구성과 절차는 변경 병합부터 자동 검증·점진 배포·자동 롤백까지의 흐름을 중심으로 제시함
- 실무 판단은 변경 실패율, 롤백 시간, 단계별 오류율, 자동 차단 시간으로 구체화함

## Ⅰ. 개요

- **정의/개념**: 지속적 배포는 코드 변경이 자동 검증을 통과하면 수동 승인 없이 운영 환경에 반영하는 전달 방식임
- **배경/필요성**: 변경을 짧은 주기로 운영에 반영하려면 검증·점진 배포·이상 탐지·롤백을 자동화할 필요가 있음

## Ⅱ. 특징

- 배포 대기 시간을 줄여 작은 변경을 자주 운영에 반영함
- 변경 단위가 작으면 장애 원인 후보가 해당 변경 범위로 줄어듦
- 자동 검증이 결함을 놓치면 해당 변경이 운영 환경에 반영됨
- 점진 배포와 자동 복구가 없으면 장애 노출 범위와 복구 시간을 제한하기 어려움

## Ⅲ. 종류 및 비교

| 판단 기준 | 지속적 전달 | 지속적 배포 |
|:---|:---|:---|
| 운영 반영 방식 | 자동 검증 후 사람이 운영 배포를 승인함 | 자동 검증 후 운영에 반영함 |
| 위험 제어 | 운영 반영 전에 사람이 위험을 검토함 | 점진 배포와 자동 롤백으로 노출 범위를 제어함 |
| 구조상 한계 | 승인 대기 시간이 남아 병목이 될 수 있음 | 테스트와 관측 신뢰도가 낮으면 장애 전파 속도가 빨라짐 |
| 대표 환경 | 운영 반영 전 승인 증적이 필요한 조직 | 자동 테스트·관측·롤백 기준을 운영하는 온라인 서비스 |

> 요약: 운영 반영에 수동 승인이 필요하면 지속적 전달, 자동 검증 후 운영에 반영하면 지속적 배포임.

## Ⅳ. 구성요소 및 구조

| 구성요소 | 설명 |
|:---|:---|
| 자동 테스트 체계 | 운영 승인을 대신할 만큼 신뢰할 수 있는 자동 검증 장치임 |
| 배포 정책 | 어떤 변경을 자동 배포할지 위험 기준을 정해 통제함 |
| 점진 배포 | 카나리나 블루-그린으로 위험 범위를 줄이며 운영에 반영함 |
| 자동 롤백 체계 | 이상 지표가 중단 기준을 넘으면 이전 버전으로 되돌리는 복구 경로임 |

> 요약: 자동 테스트와 배포 정책으로 변경을 선별하고 점진 배포 중 이상 징후를 감지하면 롤백함.

## Ⅴ. 원리 및 절차 흐름도

```text
+-------------+     +-------------+     +-------------+     +-------------+
| 변경 병합      | --> | 자동 검증      | --> | 점진 배포      | --> | 관측/자동 롤백 |
+-------------+     +-------------+     +-------------+     +-------------+
```

1. **변경 병합**: 기준 브랜치 변경이 자동 배포 흐름을 시작함
2. **자동 검증**: 테스트와 보안과 품질 게이트를 통과함
3. **점진 배포**: 운영에 자동 반영하되 트래픽을 단계적으로 확대함
4. **관측 및 자동 롤백**: 이상 지표가 중단 기준을 넘으면 배포를 중단하고 복구함

> 요약: 변경은 자동 검증 후 점진적으로 운영에 반영되고 이상 징후가 발생하면 이전 버전으로 복구됨.

## Ⅵ. 실무 사례

1. SaaS 제품팀은 자동 회귀 테스트와 점진 배포를 적용하고 변경 실패율·롤백 시간을 확인함
2. 고위험 기능은 피처 플래그로 노출을 통제하고 단계별 오류율·자동 차단 시간을 확인함

## Ⅶ. 결론

지속적 배포는 자동 검증·점진 배포·자동 복구를 결합해 변경을 운영에 반영하는 전달 모델임
