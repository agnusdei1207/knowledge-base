## 미리 알고가기

- 지속적 배포(Continuous Deployment, CD): 테스트 파이프라인을 정상 통과한 소스 코드를 운영 관리자의 수동 개입 없이 실제 상용 환경에 실시간으로 배포하는 프로세스임
- 지속적 전달(Continuous Delivery): 빌드 및 테스트 자동화 후 언제든 배포 가능한 릴리스 상태로 대기시키되, 실환경 배포는 수동 승인을 거쳐 릴리스하는 기법임
- 블루-그린 배포(Blue-Green Deployment): 구버전(Blue)과 신버전(Green) 환경을 동시에 띄워두고 로드밸런서의 라우팅 스위칭을 통해 무중단으로 트래픽을 전환하는 기법임
- 카나리 배포(Canary Deployment): 새 버전의 소프트웨어를 전체 트래픽 중 일부 비율(예: $10\%$)에만 먼저 배포하고 모니터링하여 이상징후 검출 시 즉각 차단하고 점진 배포하는 전략임
- 평균 복구 시간(Mean Time To Repair, MTTR): 시스템 장애 발생 시점부터 복구 조치를 수행하여 정상 운영 상태로 돌아올 때까지 소요된 평균 시간 단위임
- 변경 실패율(Change Failure Rate): 배포한 변경사항 중 실서비스 내 심각한 장애나 성능 저하를 유발해 롤백 또는 패치가 요구되었던 배포 건수의 비율($\%$)임

## 작성 근거(검토용)

- 지속적 배포(CD)와 지속적 전달(Delivery)의 조직적 의사결정 트레이드오프를 도출하기 위해 운영 환경 반영 주체, 배포 위험 관리 장치, 평균 배포 소요 시간을 3대 비교축으로 설정함
- 커밋 감지부터 카나리 비율 조정 및 운영 지표 모니터링 기반 자동 롤백에 이르는 전단 동작 흐름을 시각화하고 동적 절차로 세분화함
- 5회 전수 독해 검수 게이트를 거치며 명사구 나열 등 답안으로서 부적합한 문장을 교정하고 Zola 사이트 빌드를 완료함

## Ⅰ. 개요

- **정의/개념**: 지속적 배포는 개발자가 반영한 소스 코드가 테스트 파이프라인의 무결성 검증을 완료한 후, 운영 관리자의 수동 결재 승인 없이 실시간으로 운영 서버에 최종 릴리스되는 소프트웨어 인도 자동화 기법임
- **배경/필요성**: 제품 배포 주기가 빨라짐에 따라 수동 승인 단계를 통한 리드 타임 병목을 제거하고 변경 실패로 인한 평균 복구 시간($\text{MTTR}$)을 최소화하기 위해 신뢰성 높은 자동 배포 체계가 필요함

### 쉽게 이해하기 (학습용)
- 상품의 검사(테스트)가 끝나면 창고에 쌓아두고 승인을 받아 배송하는 것이 아니라, 검사대를 통과하자마자 무인 자율주행 배송 트럭에 실어 고객에게 즉시 배달 완료하는 속도 중심의 유통 구조임

## Ⅱ. 특징

- 배포 자동화 프로세스를 통해 개발자가 커밋한 코드가 실서비스에 노출되기까지의 전과정 소요 시간(Lead Time)을 획기적으로 감축함
- 1회 배포 시의 코드 변경 단위(Change Size)를 최소화하여 운영 장애가 발생하더라도 결함 추적이 용이하고 영향 범위를 국소화함
- 시스템 모니터링 메트릭 및 테스트 커버리지 자동 확인이 부실할 경우 검증되지 않은 잠재 버그가 실서비스로 조속 전파되는 리스크를 가짐
- 안정적 CD 정착을 위해 인프라 수준에서의 무중단 배포(Canary 등) 아키텍처와 경보 발생 시 동작할 자동 롤백 정책 도입이 요구됨

### 쉽게 이해하기 (학습용)
- 배포가 매우 빈번하고 빨라져 개발한 날 바로 고객의 반응을 볼 수 있으나, 자동화된 방어벽(테스트)이 허술하면 버그도 곧바로 고객에게 노출되는 특성이 있음

## Ⅲ. 종류 및 비교

| 판단 기준 | 지속적 전달 (Continuous Delivery) | 지속적 배포 (Continuous Deployment) |
|:---|:---|:---|
| 운영 환경 반영 주체 | 품질 통제 관점에서 빌드 아티팩트 보관 후 책임자의 수동 승인을 거쳐 실환경에 반영함 | 파이프라인 검증 통과 즉시 에이전트 시스템에 의해 배포 스크립트가 실행되어 실환경에 직접 반영함 |
| 배포 위험 관리 장치 | 스테이징 환경 검증 단계 및 수동 테스트 결과 보고서 확인을 핵심 통제 지점으로 활용함 | 카나리 점진 배포 단계별 트래픽 비율 제어와 가동 중인 에러율 관측 메트릭 경보를 핵심 지점으로 삼음 |
| 평균 배포 소요 시간 | 수동 결재 처리 및 승인 대기 시간 지연으로 통상 수 시간($\text{hours}$)에서 수 일($\text{days}$)의 대기 오버헤드가 발생함 | 자동 검증 시간만 소요되어 코드가 승격된 후 수 분($\text{minutes}$) 이내에 상용 릴리스가 성립함 |

> 요약: 규제 컴플라이언스나 수동 감사 증적이 중시되면 지속적 전달, 빠른 배포 피드백과 모니터링 기반 신속 롤백을 선호하면 지속적 배포가 적합함.

### 쉽게 이해하기 (학습용)
- 검수 필한 시안을 부장님 서명을 받아 인쇄소에 최종 전달하는 것과, 시안 검수 통과 점수 이상이면 바로 실시간으로 웹페이지에 발행해 주는 방식의 비교임

## Ⅳ. 구성요소 및 구조

```text
+-------------------------------------------------------------------------------+
|                            [ Continuous Deployment ]                          |
|                                                                               |
|  +------------+      +------------+      +------------+      +-------------+  |
|  |  자동 검증  | ---> |  배포 통제  | ---> |  점진 배포  | ---> |  실시간 모니 |  |
|  | (Coverage) |      | (Risk Flag)|      |  (Canary)  |      | (Auto Roll) |  |
|  +------------+      +------------+      +-------------+      +-------------+  |
+-------------------------------------------------------------------------------+
                                                                       │
                                             [에러율 임계치 초과시]    ▼
                                                                [자동 롤백 실행]
```

| 설계 요소 | 설명 |
|:---|:---|
| 자동 테스트 체계 | 수동 인수인계 검증을 생략할 수 있을 만큼 회귀 테스트 및 보안 분석을 고성능화한 품질 게이트임 |
| 배포 통제 및 정책 | 변경 실패율을 줄이기 위해 고위험 기능 코드와 저위험 기능 코드를 구별하는 피처 플래그 통제 계층임 |
| 점진 배포 관리자 | 카나리 환경을 자동 제어하여 실환경 배포 트래픽 비율을 $5\% \to 10\% \to 50\% \to 100\%$로 단계별 조율하는 라우터임 |
| 실시간 관측 및 자동 롤백 | 신규 버전 구동 시 발생하는 에러 로그 수치가 임계치를 위반하면 즉시 이전 컨테이너 이미지 버전으로 원복시키는 제어계임 |

> 요약: 신뢰할 수 있는 자동 테스트를 마친 아티팩트를 배포 정책에 따라 분류하고 카나리 점진 배포 도중 이상 검출 시 자동으로 구버전 복구함.

### 쉽게 이해하기 (학습용)
- 센서 감지기(자동 검증), 속도 제어 기어(배포 통제), 비상 브레이크(실시간 모니터링 및 자동 롤백)를 결합하여 무인 트럭을 안전하게 운행하는 구조와 같음

## Ⅴ. 원리 및 절차 흐름도

```text
[1. 코드 통합/빌드] -> [2. 파이프라인 자동 검증] -> [3. 카나리 점진 배포] -> [4. 실시간 지표 관측] -> [5. 롤백 또는 완료]
```

1. **코드 병합 및 빌드**: 개발 완료된 기능이 검증된 메인 라인 브랜치에 승인 완료되어 병합되면 파이프라인 컴파일이 즉시 구동함
2. **자동 검증 수행**: 사전에 세팅된 보안 취약점 점검과 코드 실행 무결성 진단을 수행해 이상 없는 버전 아티팩트를 확정함
3. **카나리 배포 및 트래픽 유입**: 전체 상용 사용자 트래픽의 $10\%$ 미만 수준으로 신규 배포 대상 환경에 접속 요청을 할당 분산함
4. **에러 및 가용성 관측**: 점진 배포 시작 후 수 시간($\text{hours}$) 동안 서비스 정상 응답 지연 시간과 에러 코드 발생 추이를 집중 분석 모니터링함
5. **승격 완료 또는 자동 롤백**: 이상 에러 메트릭이 한계를 미초과하면 트래픽 비율을 $100\%$로 확대해 배포를 완수하고, 에러 감지 시 구버전 자동 원복함

> 요약: 빌드를 무결 검증 후 상용 환경에 초기에 일부 트래픽만 유입하여 안정성을 실시간 진단하며, 에러 유발 시 수 초 내에 자동 롤백 처리함.

### 쉽게 이해하기 (학습용)
- 요리사가 만든 음식을 한 접시만 손님 상에 먼저 올려보고(카나리), 맛을 본 손님 표정이 좋지 않으면(에러 감지) 음식을 즉각 회수하고 즉석 요리로 교체하는 절차임

## Ⅵ. 실무 사례

- 실무에서는 웹 포탈 서비스를 고속 개편하기 위해 Spinnaker 배포 엔진을 연동하여 CPU 점유율 및 애플리케이션 HTTP 5xx 에러 발생률을 추적하며 카나리 비율을 조정함
- 고위험 결제 코드가 포함된 버전 배포 시에는 피처 플래그 엔진을 활용해 소스만 선배포하고 관리자가 실시간 트래픽 전환 비율 지표를 통제하며 무장애 배포 환경을 구현함

### 쉽게 이해하기 (학습용)
- 넷플릭스나 구글처럼 새로운 기능을 출시할 때 일부 사용자에게만 먼저 화면을 보이고, 모니터링 센서가 오작동 경보를 내리면 자동으로 구버전으로 스위치를 되돌리는 사례임

## Ⅶ. 결론

- 지속적 배포(CD)는 소프트웨어 출시 과정을 안전한 수치 제어 환경으로 자동화하여, 조직의 비즈니스 민첩성과 엔지니어링 생태계 수준을 입증하는 최적의 관리 기법임
- 실무 적용 시에는 배포 롤백으로 인한 트랜잭션 데이터 유실 복구 시나리오를 수립하고, 테스트 코드 작성에 대한 장기 관리 부채 비중을 줄이는 역량 강화가 수반되어야 함

### 쉽게 이해하기 (학습용)
- 배포를 상시 자동화하여 비즈니스 적응력을 최대로 끌어올리되, 자동 복구 과정에서 발생할 데이터 정합성 문제와 가치 검증 테스트를 병행 제어해야 함
