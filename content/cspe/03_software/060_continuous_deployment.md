# 📖 【암기용】 개념 완전 이해

> 목적: 이 개념을 처음 보는 사람도 완벽히 이해하게 만든다. 시험 답안 양식이 아니라, 이해를 위한 친절한 설명이다.

## 한눈에
- **개요**: **지속적 배포(Continuous Deployment)**는 테스트(CI)를 통과한 코드를 사람의 승인 절차 없이 자동으로 운영(Production) 서버까지 릴리즈하는 **배포 자동화 방식**이며, 마지막에 사람의 승인이 남아있는 **지속적 제공(Continuous Delivery)**과 구분된다.
- **왜 필요한가**: CI로 빌드·테스트를 자동화해도, 마지막 "실서버에 올릴지"를 사람이 결재하면 그 대기 시간이 파이프라인 전체의 병목이 된다. 이 마지막 인간 판단을 자동화된 테스트에 대한 신뢰로 대체하면 배포 빈도를 하루 수십~수천 회로 늘릴 수 있다.
- **핵심 직관**: Delivery는 "배송 트럭에 짐을 다 실어놓고 사람이 출발 버튼을 누르는 것", Deployment는 "짐이 다 실리는 순간 트럭이 스스로 출발하는 것"이다. 차이는 딱 하나, 마지막 방아쇠를 사람이 당기느냐 기계가 당기느냐다.

## 핵심 용어 정리 (내부에 등장하는 것들)

| 용어 | 의미 | 비유 |
|:---|:---|:---|
| 지속적 배포/제공 | Continuous Deployment/Delivery — 이 개념 전체를 가리키는 상위 키워드 | 배송 자동화 등급 두 단계 |
| Continuous Delivery(지속적 제공) | 릴리즈 가능한 상태까지 자동으로 준비하되, 실서버 반영은 사람이 승인 | 진열 직전까지 포장된 상품, 점장이 진열 버튼을 누름 |
| Continuous Deployment(지속적 배포) | 테스트 통과를 곧 승인으로 간주해 사람 개입 없이 실서버까지 자동 반영 | 공장에서 나온 제품이 바로 매대로 직행 |
| Feature Flag(피처 플래그) | 코드는 배포해 두고 노출 여부를 스위치로 켜고 끄는 장치 — 배포와 노출을 분리 | 리모컨으로 조명을 켰다 껐다 하는 것 |
| Canary(카나리) 배포 | 신규 버전을 트래픽 일부(예: 1~10%)에만 먼저 흘려 반응을 본 뒤 점진 확대 | 광산에서 유독가스를 먼저 감지하던 카나리아 새 |
| Blue-Green 배포 | 기존(Blue)과 동일한 신규(Green) 서버군을 통째로 띄우고 트래픽을 한 번에 스위칭 | 예비 무대를 뒤에 세워두고 커튼만 바꾸는 것 |
| Dark Launching | 미완성 기능을 실서버에 배포는 하되 화면에는 노출하지 않고 내부에서만 검증 | 신메뉴를 주방에서만 몰래 시험 조리 |
| Rollback | 배포한 버전에 문제가 생기면 직전 정상 버전으로 되돌리는 것 | 되감기 버튼 |

## 깊이 이해

### Delivery와 Deployment, 파이프라인 상 정확히 어디가 다른가
- 두 방식 모두 Commit → CI(빌드·테스트) 통과까지는 동일하다. 차이는 그다음 한 단계, "운영 서버 반영"을 누가 트리거하느냐뿐이다. Delivery는 사람이 배포 버튼을 클릭해야 다음 단계가 실행되고, Deployment는 테스트 통과 이벤트 자체가 곧바로 배포를 트리거한다.
- 그래서 Deployment를 하려면 "테스트 스위트가 곧 사람의 판단을 대체할 만큼 신뢰할 수 있는가"가 전제 조건이다. 예를 들어 테스트 5,000개를 갖췄어도 실질적으로 핵심 로직을 검증하는 비율(커버리지)이 낮은 조직이 Deployment를 켜면, 사람이 걸러줬을 결함이 그대로 운영 서버까지 직행한다.

### 카나리 배포를 수치로 이해하기
- 신규 버전을 서버 100대 중 1대(트래픽 1%)에만 배포했다고 하자. 5분간 모니터링해서 5xx 에러율이 기존 대비 임계치(예: 0.5%p) 이상 튀지 않으면 10% → 50% → 100%로 단계적으로 확대한다. 반대로 1%에서 에러율이 튀면 그 1%만 잘라내고(트래픽 회수) 나머지 99%는 무사하므로, 장애 영향 범위(Blast Radius)가 전체 대비 1%로 제한된다.
- Blue-Green은 이와 달리 신규 서버군 전체가 이미 떠 있는 상태에서 로드밸런서 트래픽을 0%에서 100%로 한 번에 넘긴다. 문제가 생기면 스위치를 원래대로 되돌리기만 하면 되므로 롤백이 초 단위로 끝나지만, 잘못된 버전이면 스위칭 순간 트래픽 100%가 즉시 영향을 받는다 — 카나리와 달리 "일부만 먼저 검증"하는 완충 단계가 없다.

### Feature Flag로 배포와 노출을 분리하는 이유
- Deployment는 "코드가 실서버에 올라가는 것"과 "사용자가 그 기능을 보는 것"을 같은 사건으로 취급하지 않는다. 미완성 결제 기능 코드를 실서버에 올려도(배포) 플래그를 꺼두면(`if(FLAG_ON)`) 사용자 화면에는 나타나지 않는다. 이렇게 하면 배포 자체는 매일 여러 번 자동으로 진행하면서, 실제 기능 공개 시점은 별도로 통제할 수 있다.

### 흔한 오해
- "Deployment가 Delivery보다 무조건 상위 기술이다" — 아니다. 금융권처럼 법적 승인이 강제되는 도메인은 Delivery까지만 하고 마지막 승인은 사람이 남겨두는 것이 정답인 경우가 많다.
- "자동 배포는 검증 없이 올리는 것이다" — 아니다. 오히려 사람이 빠지는 만큼 테스트 커버리지, Feature Flag, Canary 같은 안전장치를 더 두껍게 쌓아야 한다.

# 📝 【답안용】 시험 답안 템플릿

> 목적: 시험장에서 25분에 그대로 쓰는 답안 양식. 작성방식(추상표현 금지·수치·도식·문제유형 전환)을 엄격히 지킨다.
> 핵심: 이 시험은 정보를 많이 나열하는 시험이 아니라, 문제 신호어에서 출제자 의도를 읽고 핵심 논점을 선별해 쓰는 시험이다.

## 핵심 인사이트 (3줄 요약)

> 1. **본질**: CI(지속적 통합)를 통과한 릴리즈 가능 코드를 프로덕션(운영) 환경까지 배포하는 전 과정에서 인간의 수동 승인(Manual Approval) 절차를 100% 제거한 제로 터치(Zero-touch) 배포 자동화 아키텍처다.
> 2. **가치**: 코드가 커밋(Commit)되는 즉시 수 분(Minutes) 내에 사용자 화면에 도달하게 하여 타임투마켓(Time-to-Market)을 극한으로 단축시키고, 피드백 루프(Feedback Loop)를 극대화한다.
> 3. **판단 포인트**: Continuous Delivery(수동 릴리즈 승인 대기)와 Continuous Deployment(자동 릴리즈)의 명확한 차이점을 도식으로 대조하고, 인간의 통제를 제거한 만큼의 리스크를 커버하기 위한 '피처 플래그(Feature Flag)'와 '카나리(Canary)' 기법을 맵핑해야 한다.

## 출제 의도 및 답안 포인트

| 출제 의도 | 반드시 짚을 핵심 | 감점 회피 포인트 |
|:---|:---|:---|
| CD(Continuous Delivery vs Deployment) 개념 혼동 판별 | **수동 승인(Manual Approval) 개입 여부**의 차이 | 둘 다 배포 자동화라고 뭉뚱그려서 기술 (가장 흔한 치명적 오답) |
| 무인(Zero-touch) 자동 배포의 기술적 전제 조건 (Prerequisites) | 극한의 테스트 커버리지 및 자동 롤백 인프라 필수 | 코드만 자동으로 실서버에 복사해 주는 스크립트 도구 정도로 얕게 기술 |
| 프로덕션 직결(Direct to Prod)에 따른 장애 방어 기제 | 릴리즈(배포)와 노출(Exposure)을 분리하는 피처 플래그 | 배포되면 무조건 사용자에게 보여진다고 가정하는 레거시 시각 |

> 요약: Delivery(제공)가 "장전된 총"을 책상 위에 올려두는 것이라면, Deployment(배포)는 기계가 인간을 대신해 방아쇠(Trigger)까지 당겨버리는 것이다. 방아쇠를 당기려면 조준경(Test Code)이 100% 완벽해야 한다.

## Ⅰ. 개요 및 필요성

- 정의: 테스트(CI)를 통과한 코드를 일체의 인적 개입(수동 승인, 결재) 없이 프로덕션(Production) 라이브 서버까지 자동으로 파이프라인을 타고 릴리즈하는 궁극의 데브옵스 프랙티스
- 배경: CI(통합) 자동화로 빌드 속도는 빨라졌으나, 최종 배포 권한을 가진 운영자(Ops)의 수동 QA 승인 대기 시간 병목으로 인해 애자일 릴리즈 파이프라인의 속도(Agility)가 반감
- 필요성: 사람의 두려움에 기인한 배포 지연과 휴먼 에러(FTP 덮어쓰기 등)를 기계적 테스트 신뢰성으로 대체하여, 넷플릭스 등 글로벌 빅테크 수준의 1일 수천 회 배포(Deploy) 파이프라인을 쟁취하기 위함

## Ⅱ. Continuous Delivery vs Deployment 아키텍처 대조 도식

단어 한 글자 차이지만, 인간이 버튼을 누르느냐(수동) 마느냐(자동)라는 철학적 차이다.

```text
[ 1. Continuous Delivery (지속적 제공) - 🛑 인간 병목 구간 존재 ] 
(개발자)               (테스트/빌드)                  (Staging 배포)              [ 실서버 배포 ]
 Commit ---> [ CI 파이프라인 (Test 통과) ✅ ] ---> [ 패키징/대기장 📦 ] --( 🧑 수동 클릭 대기 )-- 👉 [ Production 서버 ]
                                                                      (운영팀 퇴근 전까지 대기)


[ 2. Continuous Deployment (지속적 배포) - 🚀 100% No-touch ]
(개발자)               (테스트/빌드)                  (승인 절차 삭제)              [ 실서버 배포 ]
 Commit ---> [ CI 파이프라인 (Test 통과) ✅ ] ------------( Zero-Touch Bypass ⚡ )-----------> 👉 [ Production 서버 ]
             (테스트 통과를 = 인간 결재와 동급으로 취급)
```

| 비교 축 (차이점) | Continuous Delivery (제공) | Continuous Deployment (배포) |
|:---|:---|:---|
| **최종 릴리즈 주체** | **인간 (Human Decision)**. 기계가 릴리즈 준비를 끝내놓고 사람의 클릭(승인)을 기다림 | **기계 (Automation)**. 테스트 스위트(Test Suite)가 통과(Green)하면 묻지도 않고 쏴버림 |
| **적용 도메인 한계** | 금융권, 헬스케어 등 절대적 규제(Compliance)나 심사역의 눈(QA)이 법적으로 강제되는 보수적 환경 | SaaS, 웹, 스트리밍 서비스 등 장애 발생 시 1분 내로 즉각적 롤백(Rollback) 대처가 가능한 환경 |
| **비즈니스 리스크** | 배포 지연으로 인한 경쟁력 약화 및 빅뱅 릴리즈로 인한 폭탄(버그 덩어리) 누적 리스크 | 1개의 잘못된 코드 병합(Commit)이 5분 만에 전 세계 사용자 화면을 박살 낼 수 있는 리스크 |

> 요약: Continuous Delivery는 "버튼을 누르면 바로 나갈 수 있게 장전만 해둘게"다. Deployment는 "테스트 통과했어? 그럼 내가 방아쇠(배포) 당긴다"다. 대부분의 회사가 Deployment를 못 하는 이유는 기계(도구)가 없어서가 아니라, 자기들이 짠 테스트 코드(검증력)를 스스로 믿지 못하기 때문이다.

## Ⅲ. 극복해야 할 시스템적 리스크 (Deployment의 조건)

인간의 통제를 없앴다면, 그에 상응하는 기계적 족쇄(안전장치)를 2배로 채워야 한다.

| 리스크 요인 | 발생 시나리오 및 시스템 붕괴 원인 (안티패턴) | 아키텍처 대응 방안 (실무 튜닝) |
|:---|:---|:---|
| **미검증 기능의 프로덕션 직접 노출** | 기획자가 아직 승인 안 한(미완성) A/B 테스트용 신규 디자인 코드를 개발자가 병합(Merge)해 버렸고, 파이프라인이 이를 실서버로 자동 배포하여 사용자 화면이 깨짐 | **배포(Deployment)와 노출(Exposure)의 분리 (Feature Flag)**: 미완성 코드라도 일단 서버에 무인 배포(Deploy)하되, `if(FLAG_ON)` 조건(피처 플래그)으로 감싸두어 특정 사내 IP 사용자에게만 노출되도록 통제(Dark Launching) |
| **장애 전파 속도의 극대화** | 치명적인 메모리 릭(Leak)을 유발하는 코드가 자동 배포되었는데, 사람이 눈치채기도 전에 전 세계 트래픽 100%가 신규 코드를 타면서 시스템 전체가 1분 만에 블랙아웃 다운됨 | **카나리(Canary) 릴리즈 롤아웃 통제**: 기계가 배포할 때 트래픽의 1%만 신규 서버로 흘림(카나리). 5분간 500에러(Error) 증가율과 CPU 수치를 모니터링 데몬이 판독한 뒤, 정상일 때만 10% -> 100%로 가속(Auto-promotion) |

> 요약: Continuous Deployment 환경에서는 "잘못된 코드가 라이브 서버에 올라가는 것" 자체를 막을 방법이 없다. 따라서 철학을 바꾼다. "잘못 올라가도 고객이 눈치채지 못하게(Feature Flag), 눈치채더라도 1%만 죽고 즉시 복구(Canary)되도록 아키텍처를 방어하라."

## Ⅳ. 무중단 무인 배포 구현 아키텍처 융합 (Blue-Green / Canary)

스크립트 배포 시대는 끝났다. 로드밸런서(LB)와 컨테이너(K8s)가 트래픽을 스위칭하는 것이 현대적 무인 배포다.

| 무인 배포 메커니즘 | 물리적 트래픽 스위칭 방식 | 롤백(Rollback) 방어 전략 |
|:---|:---|:---|
| **Blue-Green** <br> (블루-그린 배포) | 기존 서버군(Blue) 100대와 똑같은 신규 서버군(Green) 100대를 띄워놓고 배포 완료. **공유기(LB)의 포트 트래픽을 한 방에 0% -> 100%로 스위칭(Bypass)** | Green 서버에서 치명적 에러 발생 시, 스위치를 다시 Blue로 꺾기만 하면 **1초 만에 100% 롤백(Rollback)** |
| **Canary** <br> (카나리 배포) | 탄광의 카나리아 새처럼, 기존 서버군 90대는 두고 신규 서버(Canary) 10대만 배포함. **트래픽의 10%만 신규 서버로 흘려보내서 반응형 점진 검사** | 모니터링 시스템(Prometheus)이 Canary 서버의 5xx 에러 임계치 도달을 감지하면, 즉각적으로 트래픽을 회수(Abort)하여 **전체 장애 확산 차단** |

> 요약: CI/CD 파이프라인의 종착역은 결국 "사용자가 시스템 업데이트 사실을 1도 눈치채지 못하게(Zero-downtime)" 서버를 갈아 끼우는 마술 쇼다.

## Ⅴ. 실무 적용 방안 및 결론

**적용 방안 3개:**
1. [다크 런칭(Dark Launching) 기반 실데이터(Prod) 사전 검증] 미완성 결제 모듈 코드를 Continuous Deployment로 라이브 서버에 밀어 넣은 뒤, 백그라운드 스레드(Feature Flag=Dark)로만 구동시켜 실제 고객의 트래픽(결제 데이터)을 섀도잉(Shadowing) 복사하여 로직의 정합성을 수면 아래에서 안전하게 검증
2. [Spinnaker 연동 카나리(Canary) 점수 기반 자동 승격(Auto-promotion)] 무인 배포 파이프라인 끝단에 Spinnaker와 Datadog을 연결하여, 신규 서버(Canary) 배포 후 10분간의 CPU/Memory/Error Metric을 점수화(Kayenta)하고, 95점 이상일 경우에만 남은 90% 트래픽으로 롤아웃을 기계가 스스로 진행
3. [빠른 복구(Mean Time To Recovery, MTTR) 중심의 Fail-forward] Continuous Deployment 환경에서는 배포를 멈추고 롤백(Rollback)하는 시간보다, 개발자가 버그를 1분 만에 고쳐서 다시(Forward) 자동 파이프라인에 던져 배포(Fix)하는 것이 더 빠르므로, 롤백 스크립트 구축 대신 CI 병렬 최적화를 통한 극한의 쾌속 전진 전략 구사

**결론:**
- 기술사 판단: Continuous Deployment는 단순한 '툴(Tool)의 도입'이 아니라 조직 문화의 정점이다. 개발자가 짠 코드가 사람의 결재 없이 라이브 서버에 꽂힌다는 것은, 모든 개발자가 자동화된 테스트 코드를 완벽하게 짜고 코드 리뷰를 치열하게 수행하는 극한의 엔지니어링 책임감(Ownership)이 완성되었음을 의미한다. 이것이 없는 조직에게 Deployment 자동화는 자살 버튼(Suicide Switch)일 뿐이다.
- 향후 방향: 최근 클라우드 네이티브 진영에서는 코드를 배포하는 것을 넘어, 인프라스트럭처 설정(K8s YAML)조차 Git 커밋과 동시에 실서버 프로비저닝으로 동기화(Sync)시키는 **GitOps(깃옵스)** 패러다임으로 진화하며, 진정한 의미의 'Everything as Code' 선언적 자동 배포 시대를 열어젖히고 있다.
