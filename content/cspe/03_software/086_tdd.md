## Ⅰ. 개요
- **정의**: 실패하는 테스트를 먼저 작성하고, 통과시킨 뒤 리팩터링하는 테스트 선행 개발 기법
- **배경/필요성**: 구현 후 테스트 작성 시 테스트가 누락되거나 구현에 종속되는 문제가 발생함
- **비유**: 시험 문제를 먼저 만들고, 문제를 풀 수 있는 교재를 그에 맞춰 집필하는 것

| 출제 의도 | 반드시 짚을 핵심 | 감점 회피 포인트 |
|:---|:---|:---|
| Red-Green-Refactor 사이클 이해 | 테스트가 설계를 주도하는 원리 | BDD(087)와의 관계·차이를 구분할 것 |

> 요약: 테스트 선행 작성으로 설계 품질과 회귀 안전망을 동시에 확보하는 기법임

## Ⅱ. 구성요소
```text
Red (실패 테스트 작성)
 |
 v
Green (최소 코드로 통과)
 |
 v
Refactor (중복 제거·구조 개선)
 |
 +---> 다음 기능으로 반복
```

| 구성요소 | 설명 | 비유 |
|:---|:---|:---|
| Red | 아직 구현이 없어 실패하는 테스트를 작성하는 단계 | 빈 답안지에 채점 기준 작성 |
| Green | 테스트를 통과시키기 위한 최소한의 코드를 구현하는 단계 | 채점 기준에 맞춰 답 작성 |
| Refactor | 중복 제거·네이밍 개선 등 코드 구조를 정리하는 단계 | 답안 퇴고 |

> 요약: Red-Green-Refactor 3단계를 반복해 점진적으로 기능을 구현함

## Ⅲ. 절차
```text
Red --> Green --> Refactor --> (반복)
```
- 1단계: Red—구현할 기능의 기대 동작을 테스트 코드로 표현하고 실패를 확인
- 2단계: Green—테스트를 통과시키는 가장 단순한 코드를 작성
- 3단계: Refactor—모든 테스트가 통과하는 상태를 유지하며 코드 구조를 개선
- 4단계: 반복—다음 기능 요구사항에 대해 1단계부터 재수행

> 요약: 실패 확인-통과-정리-반복의 짧은 사이클로 개발을 진행함

## Ⅳ. 문제점
- 초기 속도 저하: 테스트 선행 작성으로 단기 개발 속도가 감소함
- 설계 고착: 테스트가 내부 구현에 결합되면 리팩터링 시 테스트 대량 수정이 발생함
- 비기능 요구 검증 한계: 성능·보안 등 비기능 속성은 단위 테스트로 검증이 곤란함

> 요약: 초기 속도 저하, 구현 결합, 비기능 검증 한계가 주요 과제임

## Ⅴ. 개선방안
1. 단기: 행위(Behavior) 기반 테스트 작성으로 내부 구현 결합도를 낮춤
2. 중기: 팀 내 페어 프로그래밍·코드 리뷰(089)와 병행해 TDD 숙련도를 향상
3. 장기: 성능·보안 테스트를 CI 파이프라인에 별도 단계로 통합해 비기능 검증을 보완

> 요약: 행위 기반 테스트-팀 숙련-비기능 파이프라인 순으로 한계를 보완함

## Ⅵ. 전망
- 발전 방향: AI 코드 생성 도구가 Red 단계 테스트를 자동 제안하는 방향으로 진화
- 기술사적 판단: TDD는 BDD(087)·ATDD와 결합해 요구사항-테스트-구현 추적성을 강화하는 추세임
- 기술사 제언: TDD 도입 시 팀 역량·프로젝트 복잡도를 고려한 점진적 적용 로드맵이 필요
