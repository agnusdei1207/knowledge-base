## 핵심 인사이트 (3줄 요약)
- 기업 내 뿔뿔이 흩어진 수십 개의 데이터베이스(인사, 재무, 영업 등)에서 데이터를 긁어모아, **분석하기 딱 좋게(Star Schema) 예쁘게 정제하고 가공하여 보관하는 거대한 중앙 데이터 창고**.
- 저장할 때 반드시 규격(스키마)에 맞춰 변환(ETL)해야 하므로 데이터의 품질과 신뢰성이 100% 보장되지만, 텍스트나 비디오 같은 비정형 데이터는 버려야 하고 구축 비용이 천문학적으로 비쌈.
- 90년대부터 BI(Business Intelligence) 통계 리포트를 뽑아내는 대기업의 핵심 인프라였으며, 현재는 AWS Redshift, Snowflake 같은 클라우드 DW로 진화하여 명맥을 잇고 있음.

## Ⅰ. 개요 및 필요성
- **개요**: 의사결정 지원을 위해 기업 전체의 데이터를 통합, 정제하여 주제 중심(Subject-oriented), 통합적(Integrated), 시계열적(Time-variant), 비휘발성(Non-volatile)으로 구축한 데이터 저장소.
- **필요성**: 사장님이 "올해 강남역 매장의 20대 여성 매출 총합이 얼마야?"라고 물음. 개발자가 영업 DB(MySQL)에 무거운 통계 쿼리를 때리니 10분 동안 서버가 멈춰서 전국 결제가 중단되는 대참사가 터짐. "운영 DB(OLTP)는 냅두고, 통계만 전문으로 뽑는 거대한 분석 전용 DB(OLAP)를 따로 만들자!"는 요구에서 탄생함.
---
## Ⅱ. 아키텍처 및 핵심 원리
- **1. ETL (Extract, Transform, Load)**:
  - 데이터 웨어하우스의 심장. 
  - 추출(Extract): 매일 자정, 여러 운영 DB에서 오늘 발생한 데이터를 긁어옴.
  - 변환(Transform): 남/여, M/F로 제각각인 코드를 '성별' 하나로 통일하고, 찌그러진 데이터를 예쁘게 정제함.
  - 적재(Load): DW의 테이블 규격(스키마)에 딱 맞게 끼워 넣음. (Schema-on-Write).
- **2. 다차원 모델링 (Star Schema & Snowflake Schema)**:
  - DW는 RDB의 '정규화(테이블 쪼개기)'를 혐오함. (조인이 많아지면 통계 낼 때 느려짐).
  - 대신, 정가운데에 거대한 **사실(Fact) 테이블**(예: 매출 금액)을 두고, 주변에 **차원(Dimension) 테이블**(예: 시간, 지점, 고객)을 별 모양(Star)으로 배치하여 비정규화된 상태로 쿼리 속도를 극대화함.
- **3. 데이터 마트 (Data Mart)**:
  - DW는 전사 데이터가 다 모여 있어서 너무 무거움. 
  - 인사팀, 영업팀 등 '각 부서가 볼 것만 조그맣게 떼어내서 만든 소형 DW'를 데이터 마트라고 부름.

```text
[ 운영 DB(OLTP)와 데이터 웨어하우스(OLAP)의 차이 ]

 🛒 [ 운영 DB (OLTP) ] ➡️ "빠른 저장 우선!"
 - 1초에 1,000명이 장바구니에 물건을 담음 (INSERT/UPDATE 떡칠).
 - 정규화가 잘 되어 있어서 데이터 중복이 없음.
 - 통계 쿼리(SUM, JOIN) 날리면 서버 뻗음.

 🏢 [ 데이터 웨어하우스 (OLAP) ] ➡️ "빠른 통계 우선!"
 - 어제까지의 데이터가 다 예쁘게 가공되어 정리되어 있음 (읽기 전용).
 - 통계를 빨리 내기 위해 일부러 데이터를 뚱뚱하게 뭉쳐놓음 (비정규화/Star Schema).
 - "최근 10년간 서울 지역 30대 매출 총합"을 5초 만에 뱉어냄!
```

## Ⅲ. 비교 및 연결
| 구분 | 운영 데이터베이스 (OLTP) | 데이터 웨어하우스 (DW / OLAP) | 데이터 레이크 (Data Lake) |
|---|---|---|---|
| **주요 목적** | 실시간 트랜잭션 (결제, 예약) 처리 | **비즈니스 통계 (BI), 의사결정 지원** | AI 학습, 비정형 데이터 발굴 |
| **데이터 형태** | 정형 데이터 (관계형 테이블) | **고도로 정제된 정형 데이터** | 정형, 비정형, 반정형 모두 섞임 |
| **스키마 적용** | 저장할 때 (Schema-on-Write) | **저장할 때 (Schema-on-Write)** | 읽을 때 (Schema-on-Read) |
| **사용자** | 일반 고객, 앱 서버 | **경영진, 데이터 애널리스트** | 데이터 사이언티스트 |

## Ⅳ. 실무 적용 및 기술사 판단
- **Snowflake와 클라우드 DW의 혁명**: 과거 온프레미스 DW(오라클 엑사데이터, 테라데이타)는 깡통 장비 하나에 수십억 원이었고, CPU를 늘리려면 디스크도 같이 사야 했음. 현대 아키텍트는 스토리지(S3)와 컴퓨팅(CPU)을 완벽히 분리하여 데이터 보관료는 거의 공짜로 내고, 통계 쿼리를 칠 때만 CPU를 켜서 쓴 만큼만 돈을 내는 Snowflake, Google BigQuery 같은 클라우드 네이티브 DW로 전사 아키텍처를 마이그레이션 해야 함.
- **컬럼나(Columnar) 스토리지의 필수 도입**: DW는 `SELECT 나이 FROM 고객;` 처럼 특정 컬럼 전체의 평균이나 합을 구하는 일이 99%임. 따라서 Row(가로) 단위로 저장하는 일반 DB 대신, Column(세로) 단위로 데이터를 저장하여 디스크 I/O를 10배 이상 줄이고 압축률을 극대화하는 Parquet 형식이나 컬럼나 DB 기술을 반드시 적용해야 함.

## Ⅴ. 기대효과 및 결론
- "데이터는 쌓아두기만 하면 쓰레기지만, 정제해서 모아두면 금광이 된다"는 사실을 기업 경영에 각인시킨 20세기 최고의 데이터 아키텍처.
- 비록 텍스트나 비디오 등 4차 산업혁명의 비정형 데이터를 담지 못해 '데이터 레이크'에게 왕좌의 일부를 내주었으나, 재무제표나 매출 통계처럼 "1원이라도 틀리면 안 되는 100% 신뢰 가능한 정형 데이터"의 보관소로서는 영원히 대체 불가능한 영역임.
