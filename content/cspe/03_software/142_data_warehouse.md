# 📖 【암기용】 개념 완전 이해

## 한눈에
- **개요**: 기업의 다양한 원천 시스템에서 발생한 데이터를 정제하고 통합하여 주제 중심으로 저장한 대규모 분석용 데이터베이스다.
- **왜 필요한가**: 운영 DB(OLTP)에서 직접 복잡한 분석 쿼리를 돌리면 서비스가 멈출 수 있다. 분석 전용으로 구조화된 거대한 데이터 창고가 필요하다.
- **핵심 직관**: 백화점의 각 매장(운영 DB)에서 팔린 물건의 영수증을 매일 밤 하나의 큰 장부(DW)에 정해진 양식으로 깔끔하게 옮겨 적어놓고, 경영진이 "작년 대비 20대 여성 매출 추이"를 빠르게 검색할 수 있게 만든 것이다.

## 핵심 용어 정리

| 용어/표기 | 의미 | 비유·예 |
|:---|:---|:---|
| 데이터 웨어하우스 (DW) | 주제 중심적, 통합적, 시계열적, 비휘발적 분석 DB | 경영진을 위한 요약 장부 |
| OLTP (Online Transaction Processing) | 트랜잭션 처리에 최적화된 운영 시스템 DB | 매장의 포스(POS) 기기 |
| OLAP (Online Analytical Processing) | 복잡한 분석 쿼리에 최적화된 DW 접근 방식 | 장부를 다차원으로 분석하는 도구 |
| ETL (Extract, Transform, Load) | 데이터를 추출, 정제, 적재하는 파이프라인 | 장부에 옮겨 적기 전 양식 맞추기 |
| 데이터 마트 (Data Mart) | 특정 부서나 목적에 맞게 DW의 일부를 떼어낸 소규모 DW | 마케팅 부서 전용 요약 장부 |

## 깊이 이해
- **배경·문제의식**: 서비스 운영 DB(OLTP)는 '한 건의 데이터를 얼마나 빨리 넣고 빼는가(정규화)'가 핵심이다. 반면 분석은 '수백만 건의 데이터를 어떻게 빨리 집계하는가'가 핵심이다. 둘을 한 곳에서 하면 충돌한다.
- **작동 원리**: 다양한 소스(CRM, ERP, 웹 로그)의 데이터를 ETL 도구를 통해 가져온다. 이때 데이터의 일관성을 맞추고(예: M/F, 남/여 -> M/F로 통일), 다차원 분석에 유리한 스키마(예: Star Schema)로 변환하여 적재한다. 이후 BI(Business Intelligence) 도구가 OLAP 쿼리를 날려 시각화한다.
- **특성 (Inmon의 4대 특성)**:
  1. 주제 중심적(Subject-Oriented): '고객', '매출' 등 주제별로 구성
  2. 통합적(Integrated): 데이터 포맷과 코드 체계를 하나로 통일
  3. 시계열적(Time-Variant): 데이터 변경 시 덮어쓰지 않고 시간 흐름에 따라 스냅샷 유지
  4. 비휘발적(Non-Volatile): 적재 후에는 읽기 전용으로 활용되며 데이터 갱신/삭제 없음
- **구체 예시**: AWS Redshift, Google BigQuery, Snowflake가 대표적인 클라우드 기반 데이터 웨어하우스다.
- **흔한 오해·주의점**: 데이터 웨어하우스는 '정형화된 관계형 데이터(RDB)'만 다룬다. 사진, 텍스트, 비정형 로그까지 다 때려 넣는 '데이터 레이크'와는 목적과 구조가 완전히 다르다.

## 연결 개념
- 데이터 레이크 (Data Lake) — 정형/비정형 불문 원시 데이터를 그대로 저장하는 저장소
- 다차원 모델링 (Star Schema, Snowflake Schema) — DW의 핵심 스키마 설계 기법
- 클라우드 데이터 웨어하우스 (CDW) — 스토리지와 컴퓨팅을 분리한 현대적 DW

# 📝 【답안용】 시험 답안 템플릿

## 핵심 인사이트 (3줄 요약)

> 1. **본질**: 의사결정 지원을 위해 기업 내 다양한 이기종 데이터 소스에서 데이터를 추출·정제하여 통합한 주제 중심적, 시계열적, 비휘발적 분석 데이터베이스다.
> 2. **가치**: 운영 시스템(OLTP)과 분석 시스템(OLAP)을 물리적으로 분리하여 운영 DB의 성능 저하를 막고, 전사적 단일 진실 공급원(SSOT)을 제공한다.
> 3. **판단 포인트**: 전통적 온프레미스 DW는 확장성의 한계가 있으므로, 클라우드 환경에서는 스토리지와 컴퓨팅을 분리한 Cloud Native DW(Snowflake, BigQuery)로 전환하는 것이 핵심이다.

## 출제 의도 및 답안 포인트

| 출제 의도 | 반드시 짚을 핵심 | 감점 회피 포인트 |
|:---|:---|:---|
| 데이터 분석 아키텍처 이해 역량 확인 | Inmon 4대 특성, OLTP vs OLAP 분리, ETL 파이프라인 | 데이터 레이크와의 개념 혼동, 구체적인 4대 특성 누락 |

> 요약: 운영계와의 분리 목적을 명확히 하고, 정형 데이터 기반 다차원 분석을 위한 아키텍처와 특성을 정확히 서술할 것을 요구한다.

## Ⅰ. 개요 및 필요성

- 개요: 데이터 웨어하우스(DW)는 기업의 의사결정 지원을 위해 다수의 원천 시스템으로부터 추출·정제·통합된 전사적 분석용 데이터베이스 시스템이다.
- 배경: 서비스 운영 중심의 OLTP 시스템에서 복잡한 집계 및 분석 쿼리를 수행할 경우, 트랜잭션 처리 성능이 심각하게 저하됨
- 필요성: 운영 시스템 성능 보호 및 데이터 사일로(Silo) 해소를 통한 전사 단일 진실 공급원(SSOT, Single Source of Truth) 확보 필수

---

## Ⅱ. 구조 및 구성요소

```text
Data Sources -> ETL Pipeline -> Data Warehouse -> Data Mart -> BI/Analytics
(OLTP, ERP)    (정제/변환)      (통합 데이터)    (부서별 요약)  (OLAP 쿼리)
                 |                   |
                 +-> 메타데이터 관리 +-> 데이터 품질 관리
```

| 구성요소 | 역할 | 특이사항 |
|:---|:---|:---|
| Data Sources | 분석 대상이 되는 원천 운영 데이터 | RDBMS, CRM, ERP 등 정형 데이터 위주 |
| ETL Pipeline | 데이터를 추출(Extract), 변환(Transform), 적재(Load) | 정합성 확보 및 포맷 통일 수행 |
| Enterprise DW | 전사 통합 데이터를 다차원 모델(Star Schema 등)로 저장 | 주제 중심, 비휘발성 특징 유지 |
| Data Mart | 특정 부서(마케팅, 재무 등) 목적에 맞게 요약된 소규모 DW | 빠른 접근 및 특정 분석 쿼리 최적화 |

> 요약: DW 아키텍처는 ETL을 통해 정제된 데이터를 중앙에 저장하고, 부서별 데이터 마트로 분배하여 BI 툴로 분석하는 계층적 구조를 가진다.

---

## Ⅲ. 동작원리 및 흐름도

```text
원천 데이터 추출 -> 데이터 클렌징 및 변환 -> 전사 통합 적재 -> 다차원 큐브 생성 -> 쿼리 및 시각화
```

- 1단계 [추출]: 스케줄러 기반 배치 작업이나 CDC를 통해 이기종 원천 DB에서 데이터를 추출
- 2단계 [정제·변환]: 누락 데이터 처리, 코드 체계 통일, 타입 변환 등 데이터 클렌징 및 스키마 매핑 수행
- 3단계 [적재]: 변환 완료된 데이터를 DW의 팩트(Fact) 및 디멘전(Dimension) 테이블 구조에 맞게 Insert
- 4단계 [분석]: 적재된 데이터를 기반으로 OLAP 연산(Roll-up, Drill-down) 수행 및 BI 대시보드 시각화

> 요약: 철저하게 스키마 온 라이트(Schema-on-Write) 방식으로, 적재하기 전에 데이터를 완벽히 정제하고 구조화하여 빠른 조회 성능을 보장한다.

---

## Ⅳ. 특징 (Inmon의 4대 특성)
- 주제 중심적(Subject-Oriented): 업무(애플리케이션) 중심이 아닌 고객, 상품, 매출 등 주요 분석 주제별로 데이터 재구성
- 통합적(Integrated): 이기종 소스의 다양한 데이터 포맷, 단위, 인코딩 방식을 일관된 전사 표준 체계로 단일화
- 시계열적(Time-Variant): 데이터의 현재 상태뿐만 아니라 과거 이력까지 스냅샷 형태로 보존하여 시계열 분석 지원
- 비휘발적(Non-Volatile): 일상적인 갱신(Update)이나 삭제(Delete) 트랜잭션 없이 조회(Read-only) 위주로 접근

> 요약: DW는 운영 데이터의 변형을 막고 과거부터 현재까지의 스냅샷을 통일된 규격으로 제공하여 일관된 집계 분석을 가능하게 한다.

## Ⅴ. 심화 비교 및 적용 판단

| 비교 축 | OLTP (운영 시스템) | OLAP / DW (분석 시스템) | 선택 기준 |
|:---|:---|:---|:---|
| 설계 목적 | 현재 데이터의 빠른 트랜잭션 처리 | 대용량 과거 데이터의 복잡한 집계 분석 | 업무 성격 (운영 vs 분석) |
| 데이터 모델 | 정규화(3NF 이상) 모델링 | 반정규화(다차원, Star Schema) 모델링 | 조회 성능 및 중복 허용 범위 |
| 작업 특징 | 단건 쿼리 다수 발생, 읽기/쓰기 비율 유사 | 대량 데이터 스캔 위주, 읽기 중심 | I/O 패턴 및 인덱스 전략 |

> 요약: OLTP는 쓰기 정합성을 위한 정규화에 집중하고, DW는 대규모 읽기 성능을 위한 반정규화 다차원 모델링에 집중한다.

**리스크·대응 (기본 불릿):**
- ETL 병목 현상: 데이터 양 증가로 야간 배치 윈도우 내 ETL 완료 실패 → ELT 아키텍처로 전환 및 클라우드 DW의 병렬 처리 활용 (지표: 배치 완료 지연 횟수)
- 컴퓨팅 한계: 온프레미스 장비의 확장성 한계로 리소스 부족 → 스토리지와 컴퓨팅이 분리되는 Cloud DW(Snowflake 등) 도입 (지표: CPU 사용률 90% 이상 시간)
- 데이터 품질 저하: 쓰레기 데이터 유입 시 분석 신뢰도 하락 → 추출 단계에서 Data Quality Rule(null 검사 등) 강제 적용 (지표: 데이터 정합성 오류율)

**도입 후 점검 지표 (기본 불릿):**
- 성능/효율: 대용량 집계 쿼리 실행 시간 p95 10초 이하 — BI 도구 및 쿼리 플랜 분석
- 품질/운영: 원본 데이터 발생 후 DW 적재까지의 지연 시간 목표 달성 — ETL 파이프라인 모니터링

## Ⅵ. 실무 적용 및 결론

**적용 방안 3개:**
1. 엔터프라이즈 통합 분석 환경: 사내 CRM, ERP, HR 데이터를 클라우드 DW(BigQuery, Redshift)로 통합하여 전사 실적 대시보드 구축
2. Star Schema 기반 데이터 모델링 설계: '매출액' 중심의 Fact 테이블과 '시간, 지점, 상품' 중심의 Dimension 테이블을 구축하여 조인 비용 최소화
3. ELT 아키텍처로의 진화: DW 컴퓨팅 자원을 활용해 우선 원시 데이터를 DW에 적재(Load)한 후, DW 내부에서 SQL을 통해 변환(Transform)하는 dbt 도구 연동

**결론:**
- 기술사 판단: 기업의 정형 데이터 분석은 반드시 OLTP와 분리된 DW 환경에서 수행되어야 하며, 데이터 확장에 대비해 초기부터 클라우드 네이티브 DW(스토리지-컴퓨트 분리) 아키텍처를 채택해야 한다.
- 향후 방향: 정형 데이터 중심의 DW 한계를 극복하기 위해, 비정형 데이터까지 수용하는 데이터 레이크하우스(Data Lakehouse) 아키텍처로 진화하고 있다.
