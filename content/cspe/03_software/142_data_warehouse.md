# 📖 【암기용】 개념 완전 이해

> 목적: 데이터 웨어하우스를 처음 보는 사람도 완벽히 이해하게 만든다. 시험 답안 양식이 아니라, 이해를 위한 친절한 설명이다.

## 한눈에
- **개요**: 데이터 웨어하우스(DW)는 의사결정 분석을 위한 **OLAP**(Online Analytical Processing) 중심의 **주제 지향 통합 데이터 저장소**다 — 거래를 빠르게 처리하는 OLTP DB와 반대로, 여러 원천의 데이터를 하나의 기준으로 통합·정제·이력화해 집계·분석 질의에 최적화한다.
- **왜 필요한가**: 운영 DB(OLTP)는 각자 자기 업무(주문 처리, 재고 관리)에 맞춰 정규화되어 있어, 부서마다 "매출"을 다르게 계산하거나 여러 테이블을 조인하는 무거운 집계 질의가 운영 DB 성능을 위협한다. DW는 이런 집계·분석 부하를 운영 DB에서 분리하고 공통 지표 기준을 제공한다.
- **핵심 직관**: 각 지점(원천 시스템)의 개별 장부를 본사 회계 기준(공통 차원·팩트 모델)으로 다시 정리해, 월별 손익표(집계 리포트)를 만드는 중앙 창고와 같다.

## 핵심 용어 정리 (내부에 등장하는 것들)

| 용어 | 의미 | 비유 |
|:---|:---|:---|
| OLAP(온라인 분석 처리) | 다차원으로 집계·드릴다운하는 분석 질의 방식 — DW가 속하는 상위 목적 | 여러 각도로 잘라보는 분석 보고서 |
| OLTP(온라인 거래 처리) | 짧은 트랜잭션을 빠르게 처리하는 운영계 방식 — DW와 대비되는 원천 | 매장 계산대 시스템 |
| 팩트 테이블(Fact Table) | 측정값(매출액, 수량 등 숫자)을 담는 중심 테이블 | 영수증 한 줄 한 줄 |
| 차원 테이블(Dimension Table) | 팩트를 설명하는 속성(고객, 상품, 날짜)을 담는 테이블 | 영수증에 적힌 "누가, 무엇을, 언제" |
| 스타 스키마(Star Schema) | 팩트 테이블 하나를 여러 차원 테이블이 직접 둘러싼 단순 구조 | 태양(팩트) 주위를 도는 행성(차원)들 |
| 스노우플레이크 스키마 | 차원 테이블을 다시 정규화해 세분화한 구조 | 행성 주위에 위성까지 딸린 구조 |
| ETL/ELT | 원천 데이터를 추출(Extract)·정제(Transform)·적재(Load)하는 절차, 순서만 다름 | 원자재를 가공해 창고에 넣는 공정 |
| SCD(Slowly Changing Dimension) | 차원 값이 시간에 따라 바뀔 때 이력을 관리하는 기법(Type 2 = 새 행 추가로 이력 보존) | 주소 변경 시 옛 주소도 남기는 주민등록 이력 |
| 서로게이트 키(Surrogate Key) | 원천의 업무 키 대신 DW 내부에서 새로 발급하는 인공 키 — 이력 관리에 사용 | 같은 사람도 이사 때마다 새 등록번호를 받는 것 |
| 데이터 마트(Data Mart) | DW의 부서·업무별 하위 집합 | 창고에서 부서별로 필요한 만큼 덜어낸 매대 |

## 깊이 이해

### 왜 팩트·차원으로 나누나 — 정규화 모델의 한계
- OLTP는 중복을 없애려고 3NF(제3정규형)로 잘게 쪼갠다. 예: 주문·주문상품·상품·고객 테이블이 각각 분리되어 있어, "지난달 지역별·상품군별 매출"을 구하려면 여러 테이블을 조인해야 한다.
- DW는 반대로 분석 질의 속도를 위해 의도적으로 비정규화한다. 팩트 테이블(`fact_sales`)에는 매출액·수량 같은 숫자만 두고, 조인 대상이 되는 속성은 차원 테이블(`dim_date`, `dim_product`, `dim_customer`)의 서로게이트 키로 연결한다. 이렇게 하면 집계 질의가 팩트 테이블과 소수의 차원 테이블만 조인하면 되어 훨씬 빨라진다.

### 수치로 보는 스타 스키마 효과
- 일 매출 5,000만 건이 담긴 주문 원장을 그대로 두고 "이번 달, 서울 지역, 전자제품 카테고리 매출 합계"를 구하려면 원장 전체(월 15억 건)를 스캔해야 할 수 있다.
- `fact_sales`(주문 건별 금액 + 날짜키·상품키·지역키)와 `dim_date`, `dim_product` 등으로 분리하고 날짜·지역·카테고리 컬럼에 파티션·인덱스를 걸어두면, 같은 집계를 수초~수십 초 내에 처리할 수 있다 — 조인 대상 차원 테이블이 팩트 테이블보다 훨씬 작기 때문이다(예: dim_product 10만 행 vs fact_sales 15억 행).

### SCD Type 2로 이력을 관리하는 법 — 워크드 예제
- 고객의 거주 지역이 "서울"에서 "부산"으로 바뀌었다고 하자. 단순히 UPDATE로 덮어쓰면(SCD Type 1) 과거 서울에 살 때 발생한 매출도 지금 조회하면 "부산 매출"로 잘못 집계된다.
- SCD Type 2는 기존 행을 유지한 채 새 행을 추가한다: `dim_customer`에 (customer_id=501, region=서울, valid_from=2024-01-01, valid_to=2026-03-14, is_current=N)과 (customer_id=501, region=부산, valid_from=2026-03-15, valid_to=9999-12-31, is_current=Y) 두 행이 공존한다. 서로게이트 키(customer_key=8801, 8802)가 각 행을 구분하고, 팩트 테이블은 거래 시점에 유효했던 customer_key를 참조한다.
- 이렇게 하면 "2024년 매출 지역별 집계"를 다시 돌려도 당시 유효했던 지역(서울) 기준으로 정확히 집계된다.

### ETL과 ELT의 차이 — 언제 무엇을 쓰나
- ETL: 원천에서 데이터를 뽑아(Extract) 별도 처리 서버에서 정제·변환(Transform)한 뒤 DW에 적재(Load)한다. 변환 로직이 DW 밖에 있어 DW 자원을 아끼지만 변환 서버가 별도 인프라로 필요하다.
- ELT: 원천 데이터를 먼저 그대로 적재(Load)하고, DW·레이크의 강력한 연산 자원으로 변환(Transform)을 나중에 수행한다. 클라우드 DW(Snowflake, BigQuery 등)의 확장 가능한 컴퓨팅을 활용할 때 ELT가 흔히 선택된다.

### 비유와 흔한 오해
- **비유**: 매장 영수증(OLTP 트랜잭션 기록)은 개별 거래 증빙일 뿐이고, DW는 그 영수증들을 상품별·지역별·기간별로 다시 묶어 "이번 분기 어느 지역에서 어떤 상품이 잘 팔렸는가"를 보여주는 경영 리포트 보관소다.
- **흔한 오해**: "DW는 그냥 큰 DB"라는 생각은 틀렸다. 핵심은 저장 용량이 아니라 (1) 주제 중심 모델(팩트·차원), (2) 여러 원천 간 공통 지표 정의, (3) 이력 관리(SCD), (4) 데이터 품질 규칙 — 이 네 가지가 있어야 "분석에 믿고 쓸 수 있는" 저장소가 된다. 하나라도 빠지면 부서마다 숫자가 다른 "지표 불일치" 문제가 재발한다.

## 연결 개념
- ETL/ELT — 운영계 데이터를 DW의 팩트·차원 모델로 변환하는 절차
- OLAP — 차원별 집계·드릴다운 분석 방식, DW가 지향하는 목적
- 데이터 마트 — DW의 부서·업무별 하위 집합
- Change Data Capture(141) — DW에 변경분을 준실시간으로 적재하는 소스 기법

# 📝 【답안용】 시험 답안 템플릿

> 목적: 시험장에서 25분에 그대로 쓰는 답안 양식. 작성방식(추상표현 금지·수치·도식·문제유형 전환)을 엄격히 지킨다.
> 핵심: DW 답안은 저장소 설명이 아니라 OLTP와 분리한 분석 모델, 품질, 이력, 거버넌스 판단을 제시해야 한다.

## 핵심 인사이트 (3줄 요약)

> 1. **본질**: 데이터 웨어하우스는 분석 의사결정을 위해 통합·정제·이력화한 주제 중심 데이터 저장소이다.
> 2. **가치**: OLTP 부하를 분리하고, 부서별 KPI를 공통 차원·팩트 기준으로 산출한다.
> 3. **판단 포인트**: 스타 스키마, ETL/ELT, SCD, 데이터 품질 규칙을 업무 지표와 연결해야 한다.

## 출제 의도 및 답안 포인트

| 출제 의도 | 반드시 짚을 핵심 | 감점 회피 포인트 |
|:---|:---|:---|
| OLTP와 OLAP 분리 이해 확인 | 주제 중심, 통합, 시계열, 비휘발성 특성 | 대용량 DB로만 설명 |
| 분석 모델링 역량 확인 | 팩트·차원, 스타 스키마, 집계 테이블 | 정규화 모델만 제시 |
| 품질·거버넌스 판단 확인 | MDM, SCD Type 2, 품질 규칙, lineage | KPI 정의와 이력 관리 누락 |

> 요약: DW 문제는 저장 기술보다 분석 기준 통합과 차원 모델 설계 역량을 평가한다.

## Ⅰ. 개요 및 필요성

- 개요: 데이터 웨어하우스는 분석용 통합 데이터 저장소이다.
- 배경: 운영 DB는 거래 처리와 정합성에 초점을 두므로 복잡한 집계와 장기 이력 분석에 부하가 발생한다.
- 필요성: ETL/ELT, 차원 모델, 품질 규칙으로 기업 공통 KPI를 일관된 기준으로 제공한다.

---

## Ⅱ. 구조 및 구성요소

```text
Source System -> Staging -> ETL / ELT -> Enterprise DW -> Data Mart -> BI / OLAP
                          +-> Metadata / Lineage
                          +-> Data Quality Rule
```

| 구성요소 | 역할 | 특이사항 |
|:---|:---|:---|
| Staging Area | 원천 데이터 임시 적재 | 원천 포맷 보존, 재처리 기준 |
| Enterprise DW | 통합 팩트·차원 저장 | 스타 스키마, SCD |
| Data Mart | 부서·업무별 분석 제공 | 영업·재무·고객 마트 |
| Metadata | 용어·계보·품질 관리 | lineage, catalog |

> 요약: DW는 원천에서 분석 서비스까지 적재, 정제, 통합, 제공 계층을 분리해 KPI 기준을 관리한다.

---

## Ⅲ. 동작원리 및 흐름도

```text
원천 추출 -> 정제 / 표준화 -> 차원키 매핑 -> 팩트 적재
-> 집계 생성 -> BI 조회 -> 품질 / 계보 점검
```

| 단계 | 처리 내용 | 검증 기준 |
|:---:|:---|:---|
| 1 | 원천 DB, 파일, API에서 데이터 추출 | 추출 건수, 배치 성공률 |
| 2 | 표준 코드, 중복, 결측 정제 | 품질 오류율 0.1% 이하 |
| 3 | 차원키 생성과 SCD 이력 반영 | surrogate key, 유효기간 |
| 4 | 팩트·집계 테이블 적재 후 BI 제공 | 집계 오차 0.01% 이하 |

> 요약: DW는 원천 데이터를 공통 코드와 차원키로 통합한 뒤 팩트·집계 테이블로 분석 질의를 제공한다.

| 운영/위험 | 원천별 지표 정의 분산 | 메타데이터·품질 규칙 중앙 관리 | 감사·재무 지표 추적 필요 |

| 적재 지연 | 배치 윈도우 초과 | 증분 적재, 파티션, CDC | SLA 준수율 99% |
| 이력 오류 | SCD 설계 누락 | Type 2 유효기간, surrogate key | 이력 중복·공백 0건 |

> 요약: DW 운영 리스크는 지표 불일치와 이력 오류이며, 용어집과 SCD 검증으로 통제한다.

| 점검 항목 | 목표 기준 | 측정 방법 |
|:---|:---|:---|
| 적재 | 배치 성공률 99%, 지연 30분 이하 | scheduler log, APM |
| 품질 | 결측·중복 오류율 0.1% 이하 | DQ rule, reconciliation |
| 분석 | 주요 대시보드 p95 10초 이하 | BI query log |

> 요약: DW 효과는 적재 SLA, 품질 오류율, BI 응답시간으로 수치화한다.

## Ⅵ. 실무 적용 및 결론

**적용 방안 3개 (필수 — 단계별 또는 항목별):**
1. 매출·고객·상품 공통 차원을 정의하고 `fact_sales`, `dim_customer`, `dim_product` 스타 스키마로 3~7년 이력 보관
2. ETL/ELT 배치에 품질 규칙 20개 이상과 reconciliation job을 적용해 집계 오차 0.01% 이하 검증
3. BI semantic layer와 데이터 카탈로그를 연결해 KPI 정의, lineage, 접근권한을 월 1회 점검

**결론 (2줄):**
