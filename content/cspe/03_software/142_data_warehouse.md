# 📖 【암기용】 개념 완전 이해

> 목적: 데이터 웨어하우스를 처음 보는 사람도 완벽히 이해하게 만든다. 시험 답안 양식이 아니라, 이해를 위한 친절한 설명이다.

## 한눈에
- **개요**: 데이터 웨어하우스는 의사결정 분석을 위해 주제 중심으로 통합·정제·이력화한 데이터 저장소임
- **왜 필요한가**: 운영 DB는 주문 처리에 맞춰져 있어 부서별 지표가 서로 다를 수 있음. DW는 매출, 고객, 재고 같은 공통 지표를 하나의 기준으로 제공함.
- **핵심 직관**: 각 지점 장부를 본사 회계 기준으로 정리해 월별 손익표로 만드는 중앙 분석 창고임.

## 깊이 이해
- **배경·문제의식**: OLTP DB는 현재 거래 처리에 적합하지만 장기간 이력 분석, 복잡한 조인, 다부서 통합 지표에는 부하와 모델 불일치 문제가 있음.
- **작동 원리**: 원천 시스템에서 데이터를 추출해 ETL/ELT로 정제하고, 스타 스키마 또는 스노우플레이크 스키마의 팩트·차원 테이블에 적재함.
- **비유**: 매장 영수증은 거래 기록이고, DW는 상품·지역·기간별로 다시 묶은 경영 리포트 보관소임.
- **구체 예시**: 일 매출 5천만 건을 주문 원장에 두지 않고 `fact_sales`와 `dim_date`, `dim_product`로 분리하면 월별 매출 집계를 수초~수십초 범위로 처리 가능함.
- **흔한 오해·주의점**: DW는 단순 대용량 DB가 아님. 핵심은 주제 중심 모델, 데이터 품질, 공통 지표 정의, 이력 관리임.

## 연결 개념
- ETL/ELT: 운영계 데이터를 DW 모델로 변환하는 절차
- OLAP: 차원별 집계·드릴다운 분석 방식
- 데이터 마트: 부서별 분석 목적에 맞춘 DW 하위 집합

# 📝 【답안용】 시험 답안 템플릿

> 목적: 시험장에서 25분에 그대로 쓰는 답안 양식. 작성방식(추상표현 금지·수치·도식·문제유형 전환)을 엄격히 지킨다.
> 핵심: DW 답안은 저장소 설명이 아니라 OLTP와 분리한 분석 모델, 품질, 이력, 거버넌스 판단을 제시해야 한다.

## 핵심 인사이트 (3줄 요약)

> 1. **본질**: 데이터 웨어하우스는 분석 의사결정을 위해 통합·정제·이력화한 주제 중심 데이터 저장소이다.
> 2. **가치**: OLTP 부하를 분리하고, 부서별 KPI를 공통 차원·팩트 기준으로 산출한다.
> 3. **판단 포인트**: 스타 스키마, ETL/ELT, SCD, 데이터 품질 규칙을 업무 지표와 연결해야 한다.

## 출제 의도 및 답안 포인트

| 출제 의도 | 반드시 짚을 핵심 | 감점 회피 포인트 |
|:---|:---|:---|
| OLTP와 OLAP 분리 이해 확인 | 주제 중심, 통합, 시계열, 비휘발성 특성 | 대용량 DB로만 설명 |
| 분석 모델링 역량 확인 | 팩트·차원, 스타 스키마, 집계 테이블 | 정규화 모델만 제시 |
| 품질·거버넌스 판단 확인 | MDM, SCD Type 2, 품질 규칙, lineage | KPI 정의와 이력 관리 누락 |

> 요약: DW 문제는 저장 기술보다 분석 기준 통합과 차원 모델 설계 역량을 평가한다.

---

## Ⅰ. 개요 및 필요성

데이터 웨어하우스는 분석용 통합 데이터 저장소이다. 운영 DB는 거래 처리와 정합성에 초점을 두므로 복잡한 집계와 장기 이력 분석에 부하가 발생한다. DW는 ETL/ELT, 차원 모델, 품질 규칙으로 기업 공통 KPI를 일관되게 제공한다.

---

## Ⅱ. 구조 및 구성요소

```text
Source System -> Staging -> ETL / ELT -> Enterprise DW -> Data Mart -> BI / OLAP
                          +-> Metadata / Lineage
                          +-> Data Quality Rule
```

| 구성요소 | 역할 | 특이사항 |
|:---|:---|:---|
| Staging Area | 원천 데이터 임시 적재 | 원천 포맷 보존, 재처리 기준 |
| Enterprise DW | 통합 팩트·차원 저장 | 스타 스키마, SCD |
| Data Mart | 부서·업무별 분석 제공 | 영업·재무·고객 마트 |
| Metadata | 용어·계보·품질 관리 | lineage, catalog |

> 요약: DW는 원천에서 분석 서비스까지 적재, 정제, 통합, 제공 계층을 분리해 KPI 기준을 관리한다.

---

## Ⅲ. 동작원리 및 흐름도

```text
원천 추출 -> 정제 / 표준화 -> 차원키 매핑 -> 팩트 적재
-> 집계 생성 -> BI 조회 -> 품질 / 계보 점검
```

| 단계 | 처리 내용 | 검증 기준 |
|:---:|:---|:---|
| 1 | 원천 DB, 파일, API에서 데이터 추출 | 추출 건수, 배치 성공률 |
| 2 | 표준 코드, 중복, 결측 정제 | 품질 오류율 0.1% 이하 |
| 3 | 차원키 생성과 SCD 이력 반영 | surrogate key, 유효기간 |
| 4 | 팩트·집계 테이블 적재 후 BI 제공 | 집계 오차 0.01% 이하 |

> 요약: DW는 원천 데이터를 공통 코드와 차원키로 통합한 뒤 팩트·집계 테이블로 분석 질의를 제공한다.

---

## Ⅳ. 특징

| 구분 | OLTP | 데이터 웨어하우스 | 수치·판단 포인트 |
|:---|:---|:---|:---|
| 목적 | 거래 처리 | 분석·의사결정 | TPS vs 집계 응답시간 |
| 모델 | 3NF 정규화 | 스타·스노우플레이크 | fact/dimension 분리 |
| 데이터 | 현재 상태 중심 | 장기 이력 | 3~7년 보관 정책 |
| 갱신 | 빈번한 insert/update | 배치·마이크로배치 적재 | T+1, T+0.5 SLA |

> 요약: DW는 OLTP와 목적·모델·갱신 방식이 다르며, 이력 분석과 공통 지표 산출에 초점을 둔다.

## Ⅴ. 심화 비교 및 적용 판단

| 비교 축 | 기존/대안 | 데이터 웨어하우스 | 선택 기준 |
|:---|:---|:---|:---|
| 구조 | 운영 DB 직접 조회 | 분석 전용 계층 분리 | 월말 리포트가 OLTP에 10% 이상 부하 유발 |
| 비용/성능 | 부서별 엑셀·마트 난립 | 공통 모델과 집계 테이블 | KPI 불일치 3건 이상 반복 |
| 운영/위험 | 원천별 지표 정의 분산 | 메타데이터·품질 규칙 중앙 관리 | 감사·재무 지표 추적 필요 |

> 요약: DW는 공통 지표와 장기 이력 분석 요구가 있을 때 선택하며, 단순 원시 데이터 보관은 데이터 레이크가 적합하다.

| 리스크 | 원인 | 대응 방안 | 확인 지표 |
|:---|:---|:---|:---|
| KPI 불일치 | 부서별 계산식 차이 | 비즈니스 용어집, semantic layer | KPI 정의 승인율 100% |
| 적재 지연 | 배치 윈도우 초과 | 증분 적재, 파티션, CDC | SLA 준수율 99% |
| 이력 오류 | SCD 설계 누락 | Type 2 유효기간, surrogate key | 이력 중복·공백 0건 |

> 요약: DW 운영 리스크는 지표 불일치와 이력 오류이며, 용어집과 SCD 검증으로 통제한다.

| 점검 항목 | 목표 기준 | 측정 방법 |
|:---|:---|:---|
| 적재 | 배치 성공률 99%, 지연 30분 이하 | scheduler log, APM |
| 품질 | 결측·중복 오류율 0.1% 이하 | DQ rule, reconciliation |
| 분석 | 주요 대시보드 p95 10초 이하 | BI query log |

> 요약: DW 효과는 적재 SLA, 품질 오류율, BI 응답시간으로 수치화한다.

## Ⅵ. 실무 적용 및 결론

**적용 방안 3개 (필수 — 단계별 또는 항목별):**
1. 매출·고객·상품 공통 차원을 정의하고 `fact_sales`, `dim_customer`, `dim_product` 스타 스키마로 3~7년 이력 보관
2. ETL/ELT 배치에 품질 규칙 20개 이상과 reconciliation job을 적용해 집계 오차 0.01% 이하 검증
3. BI semantic layer와 데이터 카탈로그를 연결해 KPI 정의, lineage, 접근권한을 월 1회 점검

**결론 (2줄):**
- 기술사 판단: 정형 KPI와 감사 가능한 이력이 필요하면 DW, 원시 데이터 탐색·ML 피처 저장이 목적이면 데이터 레이크 병행
- 향후 방향: 클라우드 DW는 레이크하우스·오픈 테이블 포맷과 결합해 정형 분석과 원시 데이터 처리 경계를 축소
