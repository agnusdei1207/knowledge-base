# 📖 【암기용】 개념 완전 이해

> 목적: 이 개념을 처음 보는 사람도 완벽히 이해하게 만든다. 시험 답안 양식이 아니라, 이해를 위한 친절한 설명이다. 이 파일은 SAST를 **분석 원리와 파이프라인 아키텍처** 관점에서 다룬다(용어 정의·CWE 분류·PR 게이트 운영 지표 관점은 075_static_application_security_testing.md 참고).

## 한눈에
- **개요**: **SAST(정적 애플리케이션 보안 테스트)**는 프로그램을 **실행하지 않고** 소스코드·바이트코드를 분석해 보안 취약점을 찾는 **화이트박스** 테스트 기법이다.
- **왜 필요한가**: 취약점을 운영 환경에 배포한 뒤 발견하면 이미 사고 위험에 노출된 상태에서 고쳐야 해 수정 비용과 위험이 크다. 코드를 작성하는 시점(커밋·빌드·PR)에 미리 잡아내면 훨씬 저렴하게 막을 수 있다 — 이를 "시프트 레프트(Shift-Left)"라 한다.
- **핵심 직관**: 실행하지 않고 "글"만 읽고 판단한다는 점에서 맞춤법 검사기에 가깝다. 문법과 흐름은 볼 수 있지만, 실제로 실행했을 때만 드러나는 문제(런타임 설정, 인증 우회 등)는 볼 수 없다.

## 핵심 용어 정리
| 용어 | 의미 | 비유 |
|:---|:---|:---|
| SAST | 실행하지 않고 소스코드를 분석해 취약점을 찾는 화이트박스 테스트 | 도면만 보고 하는 건물 감리 |
| 화이트박스 테스트 | 내부 구조(코드)를 열어보고 하는 테스트 | 뚜껑을 열고 보는 검사 |
| DAST | 프로그램을 실행시켜 외부에서 공격해보는 블랙박스 테스트 | 완공된 건물에 실제로 불을 놓아보는 시험 |
| Shift-Left | 보안 검증 시점을 개발 초기(왼쪽)로 앞당기는 원칙 | 늦게 걸릴 병을 조기 검진 |
| AST (추상 구문 트리) | 소스코드를 문법 구조에 따라 나무 모양으로 분해한 표현 | 문장을 주어·동사·목적어로 분해 |
| Taint Analysis (오염 데이터 추적) | 외부에서 들어온 값이 검증 없이 위험한 곳까지 도달하는지 추적하는 분석 | 오염수가 정수 필터를 거치는지 추적 |
| Source / Sink / Sanitizer | 오염원(입력) / 위험한 도착 지점(DB 쿼리 등) / 이를 걸러주는 소독 필터 | 상수원 / 수도꼭지 / 정수 필터 |
| False Positive (오탐) | 실제로는 안전한데 위험하다고 잘못 경고하는 것 | 양치기 소년의 가짜 경보 |
| SCA (Software Composition Analysis) | 내가 짠 코드가 아니라 가져다 쓴 오픈소스 라이브러리의 알려진 취약점(CVE)을 찾는 도구 | 부품 제조사 리콜 확인 |
| IAST | 프로그램을 실제로 실행하면서 내부 코드 흐름까지 함께 추적하는 하이브리드 방식 | 운전하면서 동시에 엔진 내부를 들여다봄 |

## 깊이 이해

### 동작 원리를 단계별로 — 구체 예제
- 1단계: 파서가 소스코드를 AST(추상 구문 트리)로 분해해 변수·함수 호출 간의 관계를 구조화한다.
- 2단계: 규칙 기반 패턴 매칭으로 위험한 텍스트를 찾는다. 예: 코드에 `password="1234"`처럼 비밀번호가 그대로 박혀 있는지(하드코딩) 정규식으로 검사한다.
- 3단계: Taint Analysis로 데이터 흐름을 추적한다. 예를 들어 `String id = request.getParameter("id");`로 들어온 값(source)이 소독 함수(sanitizer)를 거치지 않고 `"SELECT * FROM users WHERE id=" + id`처럼 SQL 문자열에 그대로 이어붙여져 실행부(sink)에 도달하면 SQL 인젝션(CWE-89)으로 표시한다. 반대로 `PreparedStatement`로 파라미터를 바인딩했다면 sanitizer를 거친 것으로 보고 안전 판정한다.

### 수치로 보는 효과 — 결함 비용 곡선
- 결함을 코딩 단계에서 고치는 비용을 1이라 하면, 테스트 단계에서 고치면 약 10배, 운영 배포 후 고치면 약 100배로 커진다는 것이 업계에서 흔히 인용되는 결함 비용 곡선(Cost of Defect Curve)이다. SAST는 결함을 코딩~빌드 단계(비용 1~10배 구간)에 붙잡아 두는 역할을 한다.

### 오탐 문제와 튜닝 원리
- SAST는 실행 문맥을 모르기 때문에 안전한 코드도 위험하다고 표시하는 경우가 많다. 예를 들어 사내에서 자체 제작한 검증 함수 `XSSFilter.sanitize()`를 SAST 엔진이 sanitizer로 인식하지 못하면, 이 필터를 거친 데이터도 여전히 위험하다고 오탐을 낸다.
- 대응 원리는 처음부터 모든 규칙을 켜지 않는 것이다. 치명적(Critical) 등급 규칙 몇 개만 켜서 신뢰를 쌓은 뒤, 사내 필터 함수를 "정상 소독기(Valid Sanitizer)"로 SAST 엔진에 등록해 오탐률을 점진적으로 낮춘다. 경고가 한 번에 수천 건 뜨면 개발자가 알람 자체를 꺼버리는 역효과가 나기 때문이다.

### SAST가 잡을 수 있는 것과 없는 것 (판별 원리)
- 코드에 명시적으로 쓰여 있는 결함(하드코딩된 비밀번호, 검증 없는 입력 처리, 닫지 않은 자원, 죽은 코드)은 SAST가 잡는다.
- 반면 실행해봐야만 드러나는 결함(서버 설정 오류, 세션 관리, 다중 요청 경쟁 조건, 인증 우회 같은 비즈니스 로직 결함)은 소스코드만 봐서는 알 수 없어 SAST로 잡을 수 없다. 이런 부분은 DAST(실행 후 외부 공격 재현)나 수동 점검으로 보완한다.
- 마찬가지로 내가 직접 짠 코드가 아니라 가져다 쓴 오픈소스 라이브러리 내부의 알려진 취약점은 SAST가 아니라 SCA(라이브러리 버전과 CVE 데이터베이스 대조)가 담당한다. SAST(정적)와 DAST(동적) 두 장점을 합쳐, 실행 중에 내부 코드 흐름까지 함께 추적하는 방식이 IAST다.

## 연결 개념
- DevSecOps — SAST를 CI/CD 파이프라인에 내재화하는 운영 철학
- DAST — 실행 후 외부에서 공격을 재현하는 상호 보완 테스트
- SCA — 오픈소스 라이브러리의 알려진 취약점(CVE)을 찾는 상호 보완 도구
- 075_static_application_security_testing — 같은 SAST를 CWE 분류·PR 게이트·SLA 같은 운영 지표 관점에서 다룸

# 📝 【답안용】 시험 답안 템플릿

> 목적: 시험장에서 25분에 그대로 쓰는 답안 양식. 작성방식(추상표현 금지·수치·도식·문제유형 전환)을 엄격히 지킨다.
> 핵심: 이 시험은 정보를 많이 나열하는 시험이 아니라, 문제 신호어에서 출제자 의도를 읽고 핵심 논점을 선별해 쓰는 시험이다.

## 핵심 인사이트 (3줄 요약)

> 1. **본질**: 애플리케이션을 실행(Runtime)하지 않고, 소스코드(Source Code)나 바이트코드의 제어/데이터 흐름(Control/Data Flow)을 정적(Static)으로 파싱하여 보안 취약점과 코딩 컨벤션 위반을 색출하는 화이트박스 검증 기법이다.
> 2. **가치**: CI/CD 파이프라인의 극초기 단계(Build/Commit)에 퀄리티 게이트(Quality Gate)로 결합되어 **'시프트 레프트(Shift-Left)'**를 달성하며, 취약점 조기 식별을 통해 결함 수정 비용(Cost of Defect)을 1/100 수준으로 압축한다.
> 3. **판단 포인트**: AST(추상 구문 트리) 변환을 통한 텍스트 분석 원리와 데이터 오염 추적(Taint Analysis) 메커니즘을 도식화하고, 실행 환경(Runtime)의 문맥을 알 수 없어 발생하는 **막대한 오탐(False Positive)의 한계와 튜닝 방안**을 필수적으로 제시해야 한다.

## 출제 의도 및 답안 포인트

| 출제 의도 | 반드시 짚을 핵심 | 감점 회피 포인트 |
|:---|:---|:---|
| 시프트 레프트(Shift-Left) 사상 관점에서의 SAST 위치 매핑 | 개발 주기의 **극초기(IDE, Commit, Build)** 방어막 | DAST(동적 테스트)와 섞어서 런타임에 쓴다고 적는 치명적 오류 |
| 정적 분석의 핵심 엔지니어링 메커니즘 도출 | AST(Abstract Syntax Tree) 파싱 및 데이터 오염(Taint) 분석 | 단순히 텍스트(문자열) 검색기(`grep`) 수준으로 격하하여 서술 |
| SAST 도입 시 실패하는 현업 리스크 원인과 튜닝망 | 과도한 **오탐(False Positive)**으로 인한 파이프라인 마비 | 단점 없이 100% 버그를 잡는 만능 보안 툴로 과장 |

> 요약: SAST는 "건물을 올리기 전에 도면(코드)만 보고 철근이 빠졌는지 잡아내는 감리"다. 건물을 부술 필요가 없어서 싸고 빠르지만, 도면(코드)만 보다 보니 도면엔 없지만 실제 땅(런타임 메모리)에서 터지는 싱크홀(환경 버그)은 절대로 잡을 수 없다.

## Ⅰ. 개요 및 필요성

- 정의: 소프트웨어 개발 생명주기(SDLC) 초기 단계에서 프로그램을 실행하지 않은 상태로 소스코드의 구조, 구문, 데이터 흐름을 분석하여 OWASP Top 10(XSS, 인젝션 등) 취약점을 식별하는 화이트박스(White-box) 보안 테스팅 기법
- 배경: 애플리케이션 보안 테스트를 릴리즈 직전(운영 환경)에 수행하는 사후 대처 방식은 버그의 근원지(Root Cause) 추적을 어렵게 하고 배포 일정을 치명적으로 지연(Bottleneck) 시킴
- 필요성: 개발자의 IDE(에디터)나 CI 빌드 과정에 정적 스캐너를 밀착 결합(Built-in)하여 비밀번호 하드코딩이나 널 포인터(NPE) 결함을 코드 작성 1초 만에 즉각 차단(Block)하는 **보안 시프트 레프트(Shift-Left)**를 완수하기 위함

## Ⅱ. SAST 정적 분석 아키텍처 및 오염 추적(Taint) 도식

단순한 텍스트 찾기가 아니다. 사용자 입력이 DB까지 도달하는 강(Flow)의 흐름을 쫓아가는 추적망이다.

```text
[ SAST 분석 파이프라인: Taint Analysis (오염 데이터 추적 메커니즘) ]

 1. Source (오염원 유입)      2. AST 파싱 및 데이터 플로우 추적          3. Sink (치명적 실행부 타격)
+-------------------+      +---------------------------------+      +---------------------------+
| String id =       |      | 🤖 SAST 분석 엔진 (실행 안 함)   |      | executeQuery(           |
|  request.get("id")| ---> | - 변수 id의 흐름(Flow) 추적      | ---> |  "SELECT * WHERE id="   |
| (사용자 해킹 입력)   |      | - 소독(Sanitize) 필터가 거쳤는가? |      |   + id );               |
+-------------------+      |   -> "필터 없이 통과했군! 🚨"    |      +---------------------------+
                           +---------------------------------+       (SQL 인젝션 100% 확정)
                                           |
                              🛑 [ 빌드 실패 (Build Failed) ] 및 결함 라인(Line 35) 즉시 리포트
```

| 분석 엔지니어링 메커니즘 | 물리적 통제 방식 (코드 해부) | 탐지하는 취약점(Vulnerability) 유형 |
|:---|:---|:---|
| **AST (추상 구문 트리) 변환** | 소스코드를 문법 구조(Tree)로 분해. 단순 문자열이 아닌 노드(Node) 간의 종속성을 파악 | 불필요한 데드 코드(Dead Code), 닫지 않은 메모리 자원(Memory Leak), 스레드 데드락(Deadlock) 논리 결함 |
| **데이터 흐름 분석** <br> (Data Flow / Taint) | 사용자의 외부 입력값(오염원: Source)이 내부 로직을 거쳐 최종 목적지(Sink: DB 쿼리)에 도달할 때까지 보안 검증(Validation)을 거치는지 텍스트 추적 | **SQL 인젝션(Injection), XSS(크로스 사이트 스크립팅)** 등 외부 악성 페이로드 주입 공격 |
| **패턴 매칭 (Lexical)** | 정규표현식(Regex)을 돌려 위험한 키워드 텍스트 긁어내기 | AWS Access Key 노출, 비밀번호 **하드코딩(Hard-coding)** |

> 요약: SAST의 최고 장점은 "버그가 정확히 `login.java` 35번째 줄에 있다"고 손가락으로 콕 집어준다는 것이다. DAST는 그냥 밖에서 해킹하고 "에러 나는데요?" 하고 던져버리지만, SAST는 소스코드를 보고 있으므로 완벽한 내비게이션(Pinpoint)이 가능하다.

## Ⅲ. 극복해야 할 시스템적 리스크 (오탐 폭발과 파이프라인 마비)

너무 똑똑해서 문제다. "이것도 위험할 것 같은데?"라며 가짜 알람을 1만 개 띄우면 양치기 소년이 된다.

| 리스크 요인 | 발생 시나리오 및 시스템 붕괴 원인 (안티패턴) | 아키텍처 대응 방안 (실무 최적화 튜닝) |
|:---|:---|:---|
| **가짜 경보(False Positive)의 늪** | SAST 봇이 코드를 훑더니 "위험 의심 취약점 5,000개" 경보를 띄우며 Jenkins 빌드를 멈춰(Block)버림. 확인해 보니 99%가 안전한 내부망 코드인데 문맥(Runtime Context)을 몰라서 뱉은 뻥카. 개발자들 분노 폭발 | **룰셋 튜닝 및 인가된 예외(Exception) 처리**: 도입 초기부터 모든 룰을 켜지 않음. OWASP Top 10 기준의 극도로 치명적인(Critical) 룰 5개만 켜서 신뢰도를 확보한 뒤, 회사 프레임워크(Spring)에 맞춰 **화이트리스트(Whitelist) 튜닝을 점진적으로 확대** |
| **타사 오픈소스(3rd Party) 분석 한계** | 내가 짠 코드(SAST)는 깨끗한데, 내가 가져다 쓴 외부 라이브러리(`Log4j.jar`) 속에 숨겨진 취약점은 소스코드가 없거나 스캔 범위를 벗어나 방어망 붕괴 | **SCA (Software Composition Analysis) 결합**: SAST는 내가 짠 코드(Custom Code)만 잡고, 외부 오픈소스 취약점(CVE)은 SCA 봇(Dependency-Check)이 잡도록 **투트랙(Two-track) 스캐닝 방호벽 구축** |

> 요약: SAST를 도입하고 망하는 회사의 99%는 '옵션(Rule) 타협'을 안 했기 때문이다. 경고가 1,000개 뜨면 개발자는 툴을 꺼버린다. 처음엔 10개만 띄워야 한다. "오탐이 없는 10개의 확실한 버그"부터 잡는 것이 안착의 핵심이다.

## Ⅳ. DevSecOps 기반 SAST 통합 퀄리티 게이트 (Quality Gate)

정적 분석은 사람이 돌리는 게 아니다. 파이프라인(기계)이 개발자의 멱살을 잡고 코드를 뱉어내야 한다.

| DevSecOps 파이프라인 | 융합 통제 메커니즘 (차단 기술) | 해결되는 애자일 보안 속도 한계 |
|:---|:---|:---|
| **IDE Linter 플러그인** <br> (0차 방어선) | 개발자가 `VScode`나 `IntelliJ`에서 비밀번호 하드코딩 치는 순간(저장도 하기 전), SonarLint 봇이 빨간 밑줄을 긋고 코딩 자체를 저지 | Git 커밋 전 로컬 PC에서 즉시 교정하여, CI 빌드 서버 낭비(시간 지연) 0초 컷 압살 |
| **SonarQube 기반** <br> (1차 빌드 차단막) | 젠킨스 파이프라인의 `Test` 단계 직후 SAST 스캔 실행. 분석 결과 Critical(심각) 취약점이 1개라도 발견되면, 젠킨스 빌드 상태를 **빨간불(Failed)로 꺾어버리고 PR(Pull Request) Merge 버튼을 100% 비활성화(Lock)** | 사후 보안 심사(보안팀 엑셀 체크)의 며칠짜리 병목을 기계적 블로킹으로 완벽히 치환(Security as Code) |

> 요약: 보안팀이 결재 서류에 도장 찍어주는 시대는 끝났다. 소나큐브(SonarQube) 퀄리티 게이트 룰셋이 곧 보안팀이다. 기계가 통과(Pass)를 외치면 밤 11시라도 그냥 무인 배포(CD)되는 것이 클라우드 네이티브의 룰이다.

## Ⅴ. 실무 적용 방안 및 결론

**적용 방안 3개:**
1. [SonarQube + Fortify 듀얼 정적 분석 및 PR 데코레이팅] GitHub PR(Pull Request) 생성 시 GitHub Actions가 즉각 SAST 엔진을 띄움. 분석 결과(취약점 3건)를 PR의 댓글(Comment) 라인에 봇(Bot)이 자동으로 달아주어(Decorating), 개발자가 화면을 벗어나지 않고 Git UI 안에서 즉각 소스 수정 후 재커밋하는 몰입도(Flow) 확보
2. [Taint Analysis(데이터 오염 추적) 특화 룰셋 사내 최적화 튜닝] 금융권 B2C 앱 백엔드에서 사용자 입력값이 사내 고유의 커스텀 보안 필터(XSSFilter.java)를 거치는 경우, 범용 SAST 툴은 이를 '안전 처리'로 인지하지 못하고 오탐(False Positive)을 뿜음. 이를 제어하기 위해 사내 필터 함수를 SAST 엔진에 `Valid Sanitizer(정상 소독기)`로 강제 매핑(AST 커스텀 룰셋 주입)하여 오탐률 90% 소거
3. [IAST (Interactive AST) 하이브리드 아키텍처 진화 적용] SAST(정적)의 '높은 오탐률'과 DAST(동적)의 '소스코드 위치 추적 불가' 단점을 융합 타파. 앱 내부에 에이전트(Agent)를 심고 QA팀이 화면(블랙박스)을 누르며 동작(DAST)시킬 때, 메모리 내부의 소스코드 실행 흐름을 에이전트가 역추적(SAST)하여 **오탐률 제로(Zero)의 핀포인트 취약점 타격 획득**

**결론:**
- 기술사 판단: 정적 분석(SAST)은 현대 DevSecOps 톱니바퀴의 가장 첫 번째 축이다. 소프트웨어가 실행(Runtime)이라는 옷을 입기 전, 가장 순수한 뼈대(Code) 상태에서 구조적 골다공증을 색출해 내는 백색상자(White-box) 감리관이다. 비록 실행 문맥 부재로 인한 오탐(False Positive)이라는 태생적 짐을 안고 있으나, 취약점을 소스코드 라인(Line Number) 단위로 지적하여 수정 비용을 1/100로 낮추는 시프트 레프트(Shift-Left)의 압도적 경제성은 그 어떤 런타임 보안 툴로도 대체 불가능하다.
- 향후 방향: 최근 보안 시장에서는 방대한 SAST 오탐 로그를 인간 보안 담당자가 걸러내는 병목을 부수기 위해, 거대 언어 모델(LLM)과 머신러닝이 수만 건의 스캔 결과를 선별 학습하여 "이 취약점은 실제 악용 불가능한 가짜(False)입니다"라고 자동 분류해 주거나, 나아가 취약한 코드를 자동 리팩터링(Auto-remediation) 패치로 변환해 주는 AI-Augmented SAST 시대로 급진하고 있다.
