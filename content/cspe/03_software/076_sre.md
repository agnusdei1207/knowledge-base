## Ⅰ. 개요
- **정의**: 소프트웨어 엔지니어링 기법으로 시스템 신뢰성을 정량적으로 관리하는 운영 방법론임
- **배경/필요성**: 수작업 운영은 규모 확장 시 인력 비례 증가를 초래하므로 자동화 기반 신뢰성 관리가 필요함
- **비유**: 병원에서 환자 활력 징후를 수치화하고 기준 이탈 시 자동 알림하는 체계와 유사함

| 출제 의도 | 반드시 짚을 핵심 | 감점 회피 포인트 |
|:---|:---|:---|
| SLI/SLO/SLA 계층과 에러 버짓 개념 | SLI→SLO→SLA 관계, Error Budget, Toil 제거 | DevOps(074 참조)와 혼동하지 말 것(SRE는 정량 신뢰성 초점) |

> 요약: SRE는 SLI/SLO 기반 정량적 신뢰성 관리와 Toil 자동화를 핵심으로 하는 운영 방법론임

## Ⅱ. 구성요소
```text
+----------+     +----------+     +----------+
|   SLI    | --> |   SLO    | --> |   SLA    |
| (지표)   |     | (목표)   |     | (계약)   |
+----------+     +----------+     +----------+
      |                |
      v                v
  Monitoring     Error Budget
```

| 구성요소 | 설명 | 비유 |
|:---|:---|:---|
| SLI | 요청 지연·가용률 등 서비스 품질을 측정하는 정량 지표 | 체온·혈압 수치 |
| SLO | SLI의 목표값(예: 99.9% 가용률)을 정의한 내부 목표 | 정상 체온 범위 |
| Error Budget | 100% - SLO로 산출한 허용 장애 예산 | 연차 휴가 잔여일수 |
| Toil | 자동화 가능하나 수작업으로 반복되는 운영 작업 | 매일 수동 우편 분류 |

> 요약: SLI/SLO/Error Budget으로 신뢰성을 정량화하고 Toil을 자동화 대상으로 관리함

## Ⅲ. 절차
```text
SLI 정의 --> SLO 설정 --> Error Budget 산출 --> Toil 제거 자동화
     |            |              |                    |
   메트릭 수집  목표값 합의   예산 소진율 추적    운영 코드화
```
- 1단계: 서비스 핵심 사용자 경험에서 SLI(지연 P99, 가용률 등)를 정의함
- 2단계: 이해관계자와 SLO 목표값을 합의하고 알림 임계치를 설정함
- 3단계: Error Budget 소진율을 추적하여 소진 시 기능 릴리스를 중단하고 안정화에 집중함
- 4단계: Toil 비율을 측정하여 50% 이상이면 자동화 프로젝트를 우선 수행함

> 요약: SLI 정의→SLO 합의→예산 추적→Toil 자동화 4단계로 신뢰성을 체계 관리함

## Ⅳ. 문제점
- SLO 설정 난이도: 초기 데이터 부족 시 목표값이 과도하거나 느슨하게 설정됨
- Error Budget 갈등: 개발팀 릴리스 욕구와 운영팀 안정성 간 이해충돌 발생함
- Toil 은폐: 수작업이 관행화되면 Toil로 인식되지 않아 자동화 대상에서 누락됨

> 요약: SLO 설정, 예산 갈등, Toil 은폐가 주요 문제임

## Ⅴ. 개선방안
1. 단기: 2~4주 관측 데이터 기반으로 SLO 초기값을 설정하고 분기별 재조정함
2. 중기: Error Budget Policy 문서화로 예산 소진 시 행동 규칙을 사전 합의함
3. 장기: Toil 측정 자동화 도구 도입으로 수작업 비율을 주기적으로 가시화함

> 요약: 데이터 기반 SLO, 예산 정책 합의, Toil 가시화로 개선 가능함

## Ⅵ. 전망
- 발전 방향: AIOps와 결합하여 SLO 위반 예측·자동 대응으로 사전적 신뢰성 관리 전환 중임
- 기술사적 판단: DevOps(074 참조)와 비교 출제 빈도가 높으므로 정량 관리 차별점 강조 필요함
- 기술사 제언: 관측 가능성(077 참조)과 연계한 SLI 수집 자동화 아키텍처 설계를 권고함
