## Ⅰ. 개요
- **정의**: RBAC은 역할 기반, ABAC은 속성 기반으로 자원 접근 권한을 제어하는 인가 모델
- **배경/필요성**: 사용자 수 증가 시 개인별 권한 관리가 비현실적이므로 체계적 인가 모델이 필요함
- **비유**: RBAC은 부서별 출입 카드, ABAC은 시간·장소·직급 등 조건을 조합한 스마트 출입 시스템임

| 출제 의도 | 반드시 짚을 핵심 | 감점 회피 포인트 |
|:---|:---|:---|
| 두 인가 모델의 구조적 차이 비교 | 역할 할당 vs 속성 조합 정책 평가 | RBAC은 정적, ABAC은 동적 인가라는 단순 이분법 회피 |

> 요약: 역할 할당(RBAC)과 속성 조합(ABAC)으로 접근 권한을 체계적으로 제어하는 인가 모델임

## Ⅱ. 구성요소
```text
[RBAC]                          [ABAC]
User -> Role -> Permission      Subject Attr -+
                                Object Attr  -+-> Policy Engine -> Allow/Deny
                                Environ Attr -+
```

| 구성요소 | 설명 | 비유 |
|:---|:---|:---|
| Role (RBAC) | 사용자에게 할당되는 직무 역할 단위 | 부서 출입 카드 |
| Permission (RBAC) | 역할에 연결된 자원별 조작 권한 | 카드에 매핑된 출입 구역 |
| Subject Attribute (ABAC) | 요청자의 속성(직급, 부서, 인증 수준) | 출입자 신원 정보 |
| Object Attribute (ABAC) | 대상 자원의 속성(분류, 민감도 등급) | 구역 보안 등급 |
| Policy Engine (ABAC) | 속성 조합을 정책 규칙으로 평가하여 인가 결정 | 스마트 출입 판단 장치 |

> 요약: RBAC은 역할-권한 매핑, ABAC은 속성-정책 평가로 인가를 수행하는 구조임

## Ⅲ. 절차
```text
[RBAC] User -> 역할 확인 -> 역할별 권한 조회 -> 접근 허용/거부
[ABAC] User -> 속성 수집 -> 정책 엔진 평가 -> 접근 허용/거부
```
- 1단계: 사용자의 접근 요청이 인가 시스템에 도달함
- 2단계: RBAC은 사용자의 역할을, ABAC은 주체·객체·환경 속성을 수집함
- 3단계: RBAC은 역할-권한 테이블을, ABAC은 정책 엔진의 규칙을 기준으로 평가함
- 4단계: 평가 결과에 따라 접근을 허용하거나 거부함

> 요약: 역할 조회 또는 속성 수집 후 정책 평가를 거쳐 접근을 결정하는 흐름임

## Ⅳ. 문제점
- RBAC 역할 폭발: 세분화된 권한 요구 시 역할 수가 기하급수적으로 증가함
- ABAC 정책 복잡성: 속성·조건 조합이 많아지면 정책 충돌과 관리 난이도가 급증함
- 모델 혼용 시 일관성 저하: RBAC·ABAC 병행 운영 시 인가 판단 기준이 분산됨

> 요약: 역할 폭발·정책 복잡성·혼용 시 일관성 저하가 주요 과제임

## Ⅴ. 개선방안
1. 단기: 역할 계층화(Role Hierarchy)와 상속 구조 적용으로 역할 수 억제
2. 중기: 정책 시뮬레이션·충돌 탐지 도구 도입으로 ABAC 정책 검증 자동화
3. 장기: RBAC+ABAC 통합 모델(Policy-Based RBAC) 적용으로 일관된 인가 프레임워크 구축

> 요약: 역할 계층화·정책 검증 자동화·통합 모델로 단계적 고도화가 필요함

## Ⅵ. 전망
- 발전 방향: 클라우드 환경에서 ABAC 기반 세밀 인가와 RBAC 편의성의 결합이 확산 중임
- 기술사적 판단: 제로트러스트 아키텍처에서 속성 기반 동적 인가가 핵심 요소로 자리잡음
- 기술사 제언: 조직 규모와 정책 복잡도에 따라 RBAC·ABAC 적용 범위를 구분하는 설계 필요함
