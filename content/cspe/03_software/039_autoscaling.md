## Ⅰ. 개요
- 정의: 워크로드 부하에 따라 컨테이너 수량(HPA) 또는 리소스 할당량(VPA)을 자동으로 조절하는 기술.
- 출제 의도: 리소스 효율성 극대화 및 서비스 가용성 확보를 위한 동적 확장 메커니즘 이해도 측정.

## Ⅱ. 구성요소
- ASCII 구조도
  [ Metrics Server ] ----> [ HPA Controller ] ----> [ Deployment (Scale Out) ]
  (CPU/Mem Usage)  |
                   +----> [ VPA Controller ] ----> [ Pod (Scale Up) ]
- 구성요소 표
| 구성요소 | 설명 | 비유 |
| :--- | :--- | :--- |
| HPA | 부하 증가 시 Pod의 개수를 늘리는 수평 확장 | 계산대 직원 증원 |
| VPA | 부하 정도에 따라 Pod에 할당된 CPU/MEM 크기 변경 | 직원 업무 숙련도 향상 |
| CA (Cluster Autoscaler) | 리소스 부족 시 노드(VM) 자체를 증설하는 기술 | 매장 공간 확장 |
> 요약: HPA는 양적 확장(Scale-out), VPA는 질적 확장(Scale-up)에 해당함.

## Ⅲ. 절차
- ASCII 흐름도
  [지표 수집] -> [임계치 비교] -> [확장 결정] -> [리소스 갱신]
- 4단계 설명
1. Metrics Server를 통해 Pod의 실시간 자원 사용량을 지속 모니터링함.
2. 설정된 타겟 임계치(예: CPU 70%)와 현재 사용량을 비교함.
3. 부족하다고 판단될 경우 HPA는 Replica 개수를 수정함.
4. 변경된 명세에 따라 신규 Pod가 기동되거나 기존 Pod 리소스가 재설정됨.
> 요약: 관찰 -> 판단 -> 조정의 피드백 루프를 통한 자동 대응 체계임.

## Ⅳ. 문제점
- 상충 발생: HPA와 VPA를 동일 지표(CPU/MEM)에 동시 적용 시 제어 충돌로 시스템 불안정해짐.
- 딜레이 현상: 지표 수집 및 Pod 기동에 시간이 소요되어 급격한 트래픽 유입에 초기 대응 늦음.

## Ⅴ. 개선방안
- 적용 분리: HPA는 비즈니스 지표 기반, VPA는 보조적 자원 최적화 용도로 분리 운영 필요함.
- KEDA 도입: 이벤트 기반 오토스케일링(KEDA)을 통해 외부 큐(Kafka, RabbitMQ) 연동 및 즉각 대응함.

## Ⅵ. 전망
- 머신러닝 기반 예측형 오토스케일링(Predictive Scaling)을 통해 트래픽 유입 전 선제적 확장 가능해짐.
- 인프라 비용 최적화(FinOps) 관점에서 유휴 자원을 회수하는 스케일 다운 기술 고도화될 것임.
- 서버리스 플랫폼과의 통합으로 스케일 제로(0) 상태에서 요청 시 즉시 확장되는 아키텍처 확산됨.
