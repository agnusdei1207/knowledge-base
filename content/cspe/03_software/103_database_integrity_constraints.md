## 미리 알고가기

- 무결성 제약조건은 데이터베이스가 허용할 데이터 상태를 규정하는 규칙임
- 도메인 무결성과 개체 무결성과 참조 무결성이 핵심 축임
- 제약조건은 애플리케이션 로직보다 데이터 저장소 수준에서 강제되는 것이 중요함

## Ⅰ. 개요

- **정의/개념**: 데이터베이스 무결성 제약 조건은 값의 범위와 키의 유일성과 테이블 간 참조 관계 같은 데이터 규칙을 데이터베이스 자체에 명시해 잘못된 상태 저장을 사전에 차단하는 통제 장치임
- **배경/필요성**: 애플리케이션마다 동일 규칙을 따로 구현하면 누락과 불일치가 발생하므로, 저장소 수준에서 공통 규칙을 강제할 필요가 있음

## Ⅱ. 특징

- 데이터 입력 순간에 오류 상태를 차단해 사후 정합 비용을 줄임
- 여러 애플리케이션이 같은 DB를 써도 공통 규칙을 일관되게 적용함
- 제약조건이 약하면 중복과 고아 데이터가 누적되기 쉬움
- 과도하거나 부적절한 제약은 배치 적재와 변경 작업의 유연성을 떨어뜨릴 수 있음

## Ⅲ. 종류 및 비교

| 판단 기준 | 도메인 무결성 | 개체 무결성 | 참조 무결성 |
|:---|:---|:---|:---|
| 통제 대상 | 값의 범위와 형식 | 기본키 유일성과 NULL 금지 | 외래키 관계 일관성 |
| 대표 수단 | CHECK, 타입, DEFAULT | PRIMARY KEY | FOREIGN KEY |
| 방지 문제 | 잘못된 값 입력 | 중복·식별 실패 | 고아 참조와 관계 불일치 |
| 적용 시점 | 컬럼 설계 | 테이블 설계 | 관계 설계 |

## Ⅳ. 구성요소 및 구조

| 구성요소 | 설명 |
|:---|:---|
| Domain Constraint | 값의 범위와 형식과 기본값 규칙을 통해 컬럼 수준 품질을 보장함 |
| Entity Constraint | 기본키와 후보키로 개체 식별의 유일성을 유지함 |
| Referential Constraint | 외래키 관계를 강제해 테이블 간 연결이 깨지지 않게 함 |
| Enforcement Policy | 저장 시점 검증과 예외 처리 방식을 정해 운영 통제를 일관화함 |

## Ⅴ. 원리 및 절차 흐름도

```text
+-------------+     +-------------+     +-------------+     +-------------+
| 규칙 정의      | --> | 스키마 반영     | --> | 저장 시 검증    | --> | 예외/보정 처리  |
+-------------+     +-------------+     +-------------+     +-------------+
```

1. **규칙 정의**: 업무 규칙을 값과 키와 관계 기준으로 정리함
2. **스키마 반영**: 제약조건을 DDL에 반영함
3. **저장 시 검증**: INSERT와 UPDATE 시 위반 여부를 검사함
4. **예외와 보정 처리**: 위반 데이터 적재를 차단하거나 보정 절차로 넘김

## Ⅵ. 문제점 및 해결 방안

1. 문제: 업무 규칙을 애플리케이션에만 두고 DB 제약을 비워두면 채널별 입력 편차로 무결성 오류가 누적될 수 있음
   - 해결방안: critical rule을 DB 제약으로 승격하고 integrity violation count와 channel inconsistency rate로 검증함
2. 문제: 운영 배치와 마이그레이션에서 제약 적용 순서가 잘못되면 대량 실패와 복구 지연이 발생할 수 있음
   - 해결방안: staged constraint rollout을 적용하고 migration failure rate와 backfill success rate로 검증함
3. 문제: 제약조건 변경 이력이 불명확하면 규칙 해석 충돌로 개발과 운영 간 분쟁이 커질 수 있음
   - 해결방안: schema governance와 change rationale 기록을 운영하고 constraint change traceability와 review lead time으로 검증함

## Ⅶ. 적용 사례

- 멀티채널 업무 시스템에서는 핵심 규칙을 DB에 강제하고, integrity violation count와 channel inconsistency rate로 결과를 확인함
- 대규모 데이터 마이그레이션에서는 단계적 제약 적용을 수행하고, migration failure rate와 backfill success rate로 결과를 확인함
- 데이터 거버넌스 조직에서는 변경 이력을 관리하고, constraint change traceability와 review lead time로 결과를 확인함

## Ⅷ. 결론

무결성 제약조건은 저장 오류를 나중에 고치는 비용보다 저장 전에 막는 비용이 훨씬 작다는 원칙을 실무 구조로 구현하는 장치임.
