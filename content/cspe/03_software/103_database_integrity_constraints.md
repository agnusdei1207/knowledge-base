# 📖 【암기용】 개념 완전 이해

> 목적: 무결성 제약 조건을 처음 보는 사람도 DB가 데이터 품질을 어떻게 자동으로 지키는지 이해하게 만든다. 시험 답안 양식이 아니라, 이해를 위한 설명이다.

## 한눈에
- **개요**: DB에 저장되는 값이 업무 규칙과 관계 규칙을 위반하지 않도록 막는 조건
- **왜 필요한가**: 애플리케이션 코드만으로 검증하면 배치, API, 관리자 SQL 등 우회 경로에서 오류 데이터가 들어갈 수 있다. DB 제약은 모든 경로에 동일한 규칙을 적용한다.
- **핵심 직관**: 창고 입구의 자동 검사대처럼 잘못된 상품코드, 중복 주문번호, 없는 고객번호를 저장 전에 차단한다.

## 깊이 이해
- **배경·문제의식**: 관계형 DB는 데이터 공유가 목적이므로 여러 프로그램이 같은 테이블을 갱신한다. 검증 책임이 각 프로그램에 흩어지면 규칙 누락과 불일치가 발생한다.
- **작동 원리**: DOMAIN은 값 범위, KEY는 유일성, ENTITY는 기본키 NULL 금지, REFERENTIAL은 외래키 존재성, CHECK는 업무 조건, UNIQUE는 중복 금지를 DB 엔진이 DML 실행 시 검사한다.
- **비유**: 항공권 예약에서 좌석번호 형식, 예약번호 중복, 존재하지 않는 항공편 참조를 매번 직원이 기억하지 않고 시스템 검표기가 자동 차단하는 구조이다.
- **구체 예시**: `orders.customer_id`에 FK를 두면 없는 고객 주문 insert가 실패한다. `amount > 0` CHECK를 두면 음수 주문금액이 API 오류나 수기 SQL로 들어오는 것을 막는다.
- **흔한 오해·주의점**: 제약 조건은 애플리케이션 검증의 대체물이 아니다. 사용자 메시지는 애플리케이션에서 처리하고, 최종 방어선은 DB 제약으로 둔다.

## 연결 개념
- 트랜잭션 — 제약 검사를 원자성·일관성과 함께 보장
- 정규화 — 제약 조건을 설계할 엔터티 구조를 제공
- 참조 무결성 — FK 기반 관계 품질 통제

# 📝 【답안용】 시험 답안 템플릿

> 목적: 시험장에서 25분에 그대로 쓰는 답안 양식. 작성방식(추상표현 금지·수치·도식·문제유형 전환)을 엄격히 지킨다.
> 핵심: 무결성 제약은 DB 문법 항목이 아니라 트랜잭션 경계에서 데이터 품질을 강제하는 통제 장치이다.

## 핵심 인사이트 (3줄 요약)

> 1. **본질**: 무결성 제약 조건은 도메인, 키, 개체, 참조, CHECK, UNIQUE 규칙을 DBMS가 DML 시점에 강제하는 데이터 품질 장치이다.
> 2. **가치**: 모든 입력 경로에서 중복, NULL, 범위 오류, 고아 레코드, 업무 규칙 위반을 차단한다.
> 3. **판단 포인트**: 애플리케이션 검증, DB 제약, 트랜잭션 격리, 예외 처리의 책임을 분리해야 한다.

## 출제 의도 및 답안 포인트

| 출제 의도 | 반드시 짚을 핵심 | 감점 회피 포인트 |
|:---|:---|:---|
| 관계형 DB 무결성 체계 이해 확인 | domain, key, entity, referential, check, unique | PK와 UNIQUE 차이 누락 |
| 트랜잭션 기반 강제 방식 확인 | DML 실행, commit, deferrable constraint | 화면 입력 검증만으로 설명 |
| 실무 데이터 품질 통제 확인 | 제약 위반 로그, 배치 검증, 예외 처리 | 제약 조건의 성능·운영 영향 누락 |

> 요약: 이 문제는 제약 종류 암기가 아니라 업무 규칙을 DB 레벨에서 일관되게 강제하는 설계력을 묻는다.

---

## Ⅰ. 개요 및 필요성

무결성 제약 조건은 DB 데이터가 정해진 규칙을 만족하도록 강제하는 장치이다. 여러 애플리케이션과 배치가 같은 데이터를 갱신하면 코드 검증만으로는 누락이 발생한다. DB 제약은 저장 시점에 공통 규칙을 적용해 데이터 품질을 유지한다.

---

## Ⅱ. 구조 및 구성요소

```text
DML 요청 -> DBMS 제약 검사 -> 트랜잭션 처리 -> Commit/Rollback
           / Domain
           / Key and Entity
           / Referential
           / Check and Unique
```

| 구성요소 | 역할 | 특이사항 |
|:---|:---|:---|
| Domain Constraint | 컬럼 타입·범위·형식 제한 | `age between 0 and 150` |
| Key Constraint | 튜플 식별과 유일성 보장 | PRIMARY KEY, UNIQUE |
| Entity Integrity | 기본키 NULL과 중복 금지 | PK는 NOT NULL+UNIQUE |
| Referential Integrity | FK가 참조 대상 PK/UK에 존재 | cascade, restrict, set null |
| Check Constraint | 업무 조건을 행 단위로 강제 | `amount > 0`, `status in ('PAID','CANCEL')` |

> 요약: 무결성 제약은 값 범위, 식별자, 관계, 업무 조건을 DBMS가 저장 시점에 검사하는 계층 구조이다.

---

## Ⅲ. 동작원리 및 흐름도

```text
SQL 실행 -> 타입/도메인 검사 -> 키/유일성 검사 -> FK/CHECK 검사 -> Commit 또는 오류 반환
```

| 단계 | 처리 내용 | 검증 기준 |
|:---:|:---|:---|
| 1 | INSERT/UPDATE/DELETE 요청 수신 | SQL 문법·권한 통과 |
| 2 | Domain, NOT NULL, CHECK 검사 | 범위·형식 위반 0건 |
| 3 | PK, UNIQUE 인덱스로 중복 검사 | duplicate key 오류 차단 |
| 4 | FK로 부모 존재성과 삭제 정책 검사 | orphan row 0건 |
| 5 | 트랜잭션 commit 또는 rollback | ACID 일관성 유지 |

> 요약: DBMS는 DML 처리 중 타입, 키, 관계, 업무 조건을 순차 검사하고 위반 시 트랜잭션을 실패 처리한다.

---

## Ⅳ. 특징

| 구분 | 애플리케이션 검증 | DB 무결성 제약 | 판단 포인트 |
|:---|:---|:---|:---|
| 적용 범위 | 특정 서비스 코드 | 모든 SQL 경로 | 배치·관리자 SQL 포함 여부 |
| 오류 차단 시점 | 요청 처리 전 | 저장 직전·commit 전 | 최종 방어선 필요 |
| 표현력 | 복잡한 업무 흐름 가능 | 행·관계 중심 규칙 | cross-row 규칙은 trigger 검토 |
| 비용 | 코드 중복 가능 | 인덱스·FK 검사 비용 | TPS, lock wait 측정 |

> 요약: 애플리케이션은 사용자 경험과 복합 규칙, DB 제약은 최종 데이터 품질 통제를 담당한다.

## Ⅴ. 심화 비교 및 적용 판단

| 비교 축 | 기존/대안 | 본 키워드 | 선택 기준 |
|:---|:---|:---|:---|
| 구조 | 코드 검증 중심 | DB 제약+코드 검증 병행 | 데이터 공유 경로가 2개 이상 |
| 비용/성능 | 저장 전 오류 안내 | 저장 시 인덱스·FK 검사 | 쓰기 TPS와 데이터 품질 비용 비교 |
| 운영/위험 | 규칙 누락 가능 | 마이그레이션 충돌 가능 | 기존 위반 데이터 정제 필요 |

> 요약: 다중 입력 경로와 장기 보존 데이터에는 DB 제약을 기준 통제로 두고, 코드 검증을 보조로 둔다.

| 리스크 | 원인 | 대응 방안 | 확인 지표 |
|:---|:---|:---|:---|
| 배포 실패 | 기존 데이터가 신규 제약 위반 | 사전 profiling, online validation | violation count 0건 |
| 쓰기 지연 | FK·UNIQUE 검사 인덱스 누락 | 참조 컬럼 인덱스 생성 | write p95 100ms 이하 |
| 예외 처리 누락 | DB 오류 코드 미매핑 | SQLSTATE별 메시지 매핑 | constraint error 재시도율 |

> 요약: 제약 도입은 기존 데이터 정제, 인덱스 보완, 오류 코드 처리를 함께 수행해야 운영 장애를 줄인다.

| 점검 항목 | 목표 기준 | 측정 방법 |
|:---|:---|:---|
| 데이터 품질 | constraint violation 0건 | DB catalog, validation query |
| 참조 관계 | orphan row 0건 | anti-join 검사 |
| 성능 영향 | lock wait 1초 이하, deadlock 0건 | DB wait event, deadlock log |

> 요약: 무결성 제약 운영은 위반 건수, 고아 레코드, 락 대기 시간을 함께 측정한다.

## Ⅵ. 실무 적용 및 결론

**적용 방안 3개 (필수 — 단계별 또는 항목별):**
1. 핵심 원장 테이블에 PK, FK, UNIQUE, CHECK를 우선 적용하고 FK 참조 컬럼에는 인덱스를 생성해 lock wait 1초 이하를 목표로 함
2. 신규 제약 추가 전 profiling query로 위반 데이터를 0건까지 정제하고, online validation 또는 maintenance window를 선택함
3. 애플리케이션은 SQLSTATE 23505, 23503 등 제약 위반 코드를 업무 메시지로 매핑하고 감사 로그에 request id를 남김

**결론 (2줄):**
- 기술사 판단: 장기 보존·공유 데이터는 DB 제약 필수, 임시·로그성 데이터는 비용 대비 선별 적용함
- 향후 방향: 데이터 계약, schema registry, CDC 검증과 DB 제약을 결합해 서비스 간 데이터 품질을 통제해야 함
