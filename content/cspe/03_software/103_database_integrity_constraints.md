## 핵심 인사이트 (3줄 요약)
- 데이터베이스에 저장된 데이터가 현실 세계의 비즈니스 규칙과 100% 일치하도록, **'쓰레기 데이터(Garbage)'가 들어오는 것을 DBMS 엔진 차원에서 원천 차단하는 방어선**.
- 개체 무결성(PK는 Null/중복 불가), 참조 무결성(FK는 부모에 존재해야 함), 도메인 무결성(지정된 타입/범위만 허용)이 3대 핵심 기둥임.
- 애플리케이션(Java, Python) 코드에서 if문으로 데이터를 검사하는 것은 버그나 우회로(Direct DB Access)에 뚫릴 수 있으므로, 최종적이고 절대적인 데이터 보호는 반드시 DB의 무결성 제약조건(Constraint)으로 설정해야 함.

## Ⅰ. 개요 및 필요성
- **개요**: 데이터의 정확성(Accuracy), 일관성(Consistency), 유효성(Validity)을 유지하기 위해 데이터베이스 스키마에 정의하는 룰(Rule).
- **필요성**: 은행 시스템에서 계좌 잔액이 -5만 원이 되거나, 나이가 300살인 고객이 가입되거나, 존재하지 않는 부서 코드로 직원이 배정되면 비즈니스가 붕괴함. 응용 프로그램의 버그나 악의적인 SQL 주입 공격으로부터 데이터를 방어할 최후의 방패가 필요했음.
---
## Ⅱ. 아키텍처 및 핵심 원리
- **데이터베이스 4대 무결성**:
  1. **개체 무결성 (Entity Integrity)**:
     - 릴레이션(테이블)의 기본키(PK)를 구성하는 어떤 속성도 **NULL이 될 수 없고, 중복될 수 없다**. (각 행을 유일하게 식별해야 하므로).
  2. **참조 무결성 (Referential Integrity)**:
     - 외래키(FK) 값은 반드시 참조하는 부모 테이블의 기본키(PK) 값으로 존재해야 하거나, 아예 NULL이어야 함. (고아 레코드 방지).
  3. **도메인 무결성 (Domain Integrity)**:
     - 특정 컬럼에 들어가는 값은 지정된 데이터 타입, 길이, 범위를 만족해야 함. (예: 성별은 'M', 'F'만 허용 ➡️ `CHECK` 제약조건).
  4. **사용자 정의 무결성 (User-defined Integrity)**:
     - "모든 직원의 연봉은 3천만 원 이상이어야 한다" 같은 특정 비즈니스 룰을 트리거(Trigger)나 프로시저로 강제함.

```text
[ 무결성 제약조건 위반 방어 메커니즘 ]

 👦 해커(또는 버그 난 앱) ➡️ INSERT INTO 사원 (사번, 이름, 부서, 나이) 
                          VALUES (NULL, '해커', 999, -5);

 🛡️ [ DBMS 제약조건 엔진 방어선 ]
 1단계 방어 ➡️ 사번이 NULL이네? ❌ (개체 무결성 위반: PK는 NULL 불가)
 2단계 방어 ➡️ 부서 999번은 부서 테이블에 없네? ❌ (참조 무결성 위반: FK 제약)
 3단계 방어 ➡️ 나이가 -5살? ❌ (도메인 무결성 위반: CHECK(나이 > 0) 위반)
 
 💥 결과: DBMS가 쿼리 실행을 강제 거부(Rollback)하고 에러(Exception) 반환!
```

## Ⅲ. 비교 및 연결
| 방어 주체 | 애플리케이션 검증 (Java Validation) | 데이터베이스 제약조건 (DB Constraint) |
|---|---|---|
| **실행 위치** | WAS (웹/앱 서버) | DBMS 엔진 (데이터 저장 직전) |
| **장점** | 사용자에게 친절한 에러 메시지(UI) 제공, DB 부하 적음 | 버그/우회 접근을 포함한 **100% 완벽한 데이터 보호** |
| **단점** | 개발자가 if문 빼먹으면 데이터 오염됨 | 제약이 너무 많으면 DB 삽입 속도(성능)가 저하됨 |
| **결론** | UX(사용자 경험)를 위한 1차 검문소 | **데이터 정합성을 위한 최후의 보루 (동시 적용 필수)** |

## Ⅳ. 실무 적용 및 기술사 판단
- **외래키(FK) 제약조건의 실무적 회피**: 교과서적으로는 참조 무결성(FK)을 걸어야 완벽하지만, 대용량 트래픽이 몰리는 실무(MSA 환경, Sharding)에서는 FK 제약을 물리적으로 걸지 않는 경우가 많음. FK를 걸면 데이터를 삭제/수정할 때마다 부모-자식 간에 락(Lock)이 전파되어 심각한 데드락(Deadlock)과 성능 저하가 발생하기 때문임. 대신, FK 논리적 관계는 남겨두고 데이터 정합성은 애플리케이션 코드(배치 스케줄러 등)에서 사후 검증(Eventual Consistency)으로 맞추는 기법이 널리 쓰임.
- **소프트 삭제 (Soft Delete)**: 참조 무결성을 깨지 않기 위해 레코드를 실제로 `DELETE` 하지 않고, `is_deleted = 'Y'` 컬럼을 두어 화면에서만 안 보이게 처리(논리적 삭제)하는 패턴이 실무 아키텍처의 기본임.

## Ⅴ. 기대효과 및 결론
- 데이터베이스를 단순한 '엑셀 파일'이 아닌 '지능적인 데이터 관리 시스템'으로 격상시키는 가장 중요한 핵심 기능임.
- "데이터는 애플리케이션보다 오래 살아남는다." 앱은 5년마다 재개발되지만 데이터는 수십 년간 기업의 자산으로 남기 때문에, 데이터 무결성 설계는 시스템 아키텍처에서 절대 타협할 수 없는 제1 원칙임.

### 📌 관련 개념 맵
- RDB ➡️ PK / FK ➡️ 3대 무결성 (개체, 참조, 도메인) ➡️ 트리거 / 제약조건(Constraints)

### 📈 관련 키워드 및 발전 흐름도
- 단순 파일 시스템(오류 방치) ➡️ RDBMS 무결성 제약(DDL) ➡️ 실무 성능 저하 이슈 ➡️ Logical FK 및 MSA Saga 패턴 도입

### 👶 어린이를 위한 3줄 비유 설명
1. 데이터베이스는 귀중한 보물이 모여 있는 성(Castle)이에요. 무결성은 성문을 지키는 '엄격한 문지기'죠.
2. **개체 무결성**: 문지기가 "얼굴 없는 유령(NULL)이나, 똑같이 생긴 복제인간(중복)은 들어올 수 없다!"고 막는 거예요.
3. **참조 무결성**: "부모님(부서 테이블)이 먼저 우리 성에 살고 있어야만, 아이(사원)도 들어올 수 있다!"고 가짜 고아를 쫓아내는 규칙이랍니다.
