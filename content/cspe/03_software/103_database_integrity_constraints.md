# 📖 【암기용】 개념 완전 이해

> 목적: 무결성 제약 조건을 처음 보는 사람도 DB가 데이터 품질을 어떻게 자동으로 지키는지 이해하게 만든다. 시험 답안 양식이 아니라, 이해를 위한 설명이다.

## 한눈에
- **개요**: 무결성 제약 조건은 DB에 저장되는 값이 정확성·일관성이라는 **데이터 무결성**을 유지하도록 DBMS가 DML 실행 시점에 강제하는 규칙이다.
- **왜 필요한가**: 애플리케이션 코드만으로 검증하면 배치, API, 관리자 SQL 등 우회 경로에서 오류 데이터가 들어갈 수 있다. DB 제약은 어떤 경로로 들어오든 동일한 규칙을 적용하는 최종 방어선이다.
- **핵심 직관**: 각 매장(애플리케이션)이 따로 검수하는 대신, 물류창고 출고 직전에 공통 검사대(DB 제약)를 두어 잘못된 상품코드·중복 주문번호·존재하지 않는 고객번호를 한 곳에서 차단한다.

## 핵심 용어 정리 (내부에 등장하는 것들)

| 용어 | 의미 | 비유 |
|:---|:---|:---|
| 데이터 무결성 (상위 개념) | 저장된 데이터가 정확하고 일관됨을 유지하는 성질 — 제약 조건이 지키려는 **목표** | 장부 숫자가 어디서도 어긋나지 않는 상태 |
| 도메인 무결성 (Domain) | 컬럼 값이 정의된 타입·범위·형식 안에 있어야 함 | 나이 칸에 "삼십"이 아니라 정수 30만 허용 |
| 키 무결성 (Key) | 튜플을 유일하게 식별하는 값은 중복될 수 없음 | 같은 학번을 두 학생에게 발급 금지 |
| 개체 무결성 (Entity) | 기본키는 NULL이 될 수 없고 유일해야 함 | 주민등록번호 빈칸·중복 불가 |
| 참조 무결성 (Referential) | 외래키 값은 참조 대상 테이블에 실제 존재해야 함 | 존재하지 않는 보호자 이름을 서류에 못 적음 |
| CHECK 제약 | 값이 업무 조건(범위·형식)을 만족해야 함 | "주문 금액은 항상 0보다 커야 한다"는 검수 규칙 |
| UNIQUE 제약 | 기본키가 아닌 컬럼도 값 중복을 금지 | 이메일 중복 가입 금지 |
| NOT NULL | 값이 반드시 입력돼야 함 | 신청서의 필수 기입란 |

## 깊이 이해

### 왜 애플리케이션 검증만으로는 부족한가
- 하나의 테이블에 웹 서비스, 야간 배치, DBA 수기 SQL 세 경로가 접근한다고 하자. 검증 로직을 웹 서비스에만 넣으면, 배치나 수기 SQL이 `UPDATE orders SET amount = -500`을 실행할 때 이를 막을 장치가 없다.
- `CHECK (amount > 0)`을 컬럼에 걸어두면, 어느 경로에서 이 UPDATE를 실행하든 DB 엔진이 그 즉시 오류를 반환하며 요청 자체를 거부한다. 검증 책임이 여러 프로그램에 흩어지는 문제를 원천적으로 없애는 것이다.

### 6가지 제약을 판별하는 질문
- 각 제약은 서로 다른 질문에 답한다. "값이 올바른 타입·범위인가?" → 도메인. "이 행을 유일하게 구분할 수 있는가?" → 키. "기본키가 비었거나 중복인가?" → 개체. "외래키가 실존하는 부모 행을 가리키는가?" → 참조. "업무 조건(예: 금액>0)을 만족하는가?" → CHECK. "기본키 외 컬럼도 중복이 없는가?" → UNIQUE.

### 구체 수치로 보는 참조 무결성 검사 비용
- `orders` 테이블에 1,000만 건을 insert할 때, `customer_id`에 FK가 걸려 있으면 매 insert마다 `customers` 테이블에서 해당 고객이 존재하는지 확인한다. `customers.customer_id`에 인덱스가 없으면 매번 100만 행을 full scan해야 해 insert 처리량이 급격히 떨어진다. 인덱스가 있으면 B+Tree 탐색(약 O(log n), 100만 행이면 4단 내외)으로 각 insert가 수 ms 이내에 끝난다.

### PK와 UNIQUE는 무엇이 다른가 (자주 헷갈리는 지점)
- PK는 테이블당 1개만 두고 NOT NULL이 자동으로 포함된다. UNIQUE는 한 테이블에 여러 개 둘 수 있고, DBMS에 따라 NULL을 여러 번 허용하기도 한다(예: MySQL·PostgreSQL은 UNIQUE 컬럼에 NULL을 여러 행에서 허용).
- 예: 회원 테이블에서 PK는 시스템이 발급하는 회원ID(대리키), UNIQUE는 이메일(자연키)로 두면, 이메일 중복 가입은 막으면서도 이메일 미입력 회원(NULL)은 저장할 수 있다.

### 흔한 오해
- 제약 조건은 사용자에게 친절한 오류 메시지를 보여주는 장치가 아니다. 사용자 메시지 처리는 애플리케이션의 몫이고, DB 제약은 그 뒤에서 "무슨 일이 있어도 이 규칙만은 깨지지 않는다"를 보장하는 최종 방어선이다.

## 연결 개념
- 개체 무결성·참조 무결성 (하위 세부 규칙 — 104에서 PK/FK 관점으로 상세히 다룸)
- 트랜잭션 — 제약 위반 시 rollback으로 원자성을 함께 보장
- 정규화 — 제약을 걸 엔터티·속성 구조를 먼저 설계하는 선행 작업

# 📝 【답안용】 시험 답안 템플릿

## 핵심 인사이트 (3줄 요약)

> 1. **본질**: 무결성 제약 조건은 도메인, 키, 개체, 참조, CHECK, UNIQUE 규칙을 DBMS가 DML 시점에 강제하는 데이터 품질 장치이다.
> 2. **가치**: 모든 입력 경로에서 중복, NULL, 범위 오류, 고아 레코드, 업무 규칙 위반을 차단한다.
> 3. **판단 포인트**: 애플리케이션 검증, DB 제약, 트랜잭션 격리, 예외 처리의 책임을 분리해야 한다.

## 출제 의도 및 답안 포인트

| 출제 의도 | 반드시 짚을 핵심 | 감점 회피 포인트 |

## Ⅰ. 개요 및 필요성

- 개요: 무결성 제약은 DB 저장 규칙 강제 장치이다.
- 배경: 여러 애플리케이션과 배치가 같은 데이터를 갱신하면 코드 검증만으로는 NULL, 중복, 범위 오류, 고아 레코드를 막기 어렵다.
- 필요성: PK, FK, UNIQUE, CHECK, NOT NULL을 DML 시점에 검사해 모든 입력 경로에 동일한 규칙을 적용해야 한다.

---

## Ⅱ. 구조 및 구성요소

```text
DML 요청 -> DBMS 제약 검사 -> 트랜잭션 처리 -> Commit/Rollback
           / Domain
           / Key and Entity
           / Referential
           / Check and Unique
```

| 구성요소 | 역할 | 특이사항 |
|:---|:---|:---|
| Domain Constraint | 컬럼 타입·범위·형식 제한 | `age between 0 and 150` |
| Key Constraint | 튜플 식별과 유일성 보장 | PRIMARY KEY, UNIQUE |
| Entity Integrity | 기본키 NULL과 중복 금지 | PK는 NOT NULL+UNIQUE |
| Referential Integrity | FK가 참조 대상 PK/UK에 존재 | cascade, restrict, set null |
| Check Constraint | 업무 조건을 행 단위로 강제 | `amount > 0`, `status in ('PAID','CANCEL')` |

> 요약: 무결성 제약은 값 범위, 식별자, 관계, 업무 조건을 DBMS가 저장 시점에 검사하는 계층 구조이다.

---

## Ⅲ. 동작원리 및 흐름도

```text
SQL 실행 -> 타입/도메인 검사 -> 키/유일성 검사 -> FK/CHECK 검사 -> Commit 또는 오류 반환
```

| 단계 | 처리 내용 | 검증 기준 |
|:---:|:---|:---|
| 1 | INSERT/UPDATE/DELETE 요청 수신 | SQL 문법·권한 통과 |
| 2 | Domain, NOT NULL, CHECK 검사 | 범위·형식 위반 0건 |
| 3 | PK, UNIQUE 인덱스로 중복 검사 | duplicate key 오류 차단 |
| 4 | FK로 부모 존재성과 삭제 정책 검사 | orphan row 0건 |
| 5 | 트랜잭션 commit 또는 rollback | ACID 일관성 유지 |

> 요약: DBMS는 DML 처리 중 타입, 키, 관계, 업무 조건을 순차 검사하고 위반 시 트랜잭션을 실패 처리한다.

## Ⅳ. 특징

| 구분 | 애플리케이션 검증 | DB 무결성 제약 | 판단 포인트 |
|:---|:---|:---|:---|
| 적용 범위 | 특정 서비스 코드 | 모든 SQL 경로 | 배치·관리자 SQL 포함 여부 |
| 오류 차단 시점 | 요청 처리 전 | 저장 직전·commit 전 | 최종 방어선 필요 |
| 표현력 | 복잡한 업무 흐름 가능 | 행·관계 중심 규칙 | cross-row 규칙은 trigger 검토 |
| 비용 | 코드 중복 가능 | 인덱스·FK 검사 비용 | TPS, lock wait 측정 |

> 요약: 애플리케이션은 사용자 경험과 복합 규칙, DB 제약은 최종 데이터 품질 통제를 담당한다.

## Ⅴ. 심화 비교 및 적용 판단

| 비교 축 | 기존/대안 | 본 키워드 | 선택 기준 |
|:---|:---|:---|:---|
| 구조 | 코드 검증 중심 | DB 제약+코드 검증 병행 | 데이터 공유 경로가 2개 이상 |
| 비용/성능 | 저장 전 오류 안내 | 저장 시 인덱스·FK 검사 | 쓰기 TPS와 데이터 품질 비용 비교 |
| 운영/위험 | 규칙 누락 가능 | 마이그레이션 충돌 가능 | 기존 위반 데이터 정제 필요 |

> 요약: 다중 입력 경로와 장기 보존 데이터에는 DB 제약을 기준 통제로 두고, 코드 검증을 보조로 둔다.

| 리스크 | 원인 | 대응 방안 | 확인 지표 |
|:---|:---|:---|:---|
| 배포 실패 | 기존 데이터가 신규 제약 위반 | 사전 profiling, online validation | violation count 0건 |
| 쓰기 지연 | FK·UNIQUE 검사 인덱스 누락 | 참조 컬럼 인덱스 생성 | write p95 100ms 이하 |
| 예외 처리 누락 | DB 오류 코드 미매핑 | SQLSTATE별 메시지 매핑 | constraint error 재시도율 |

> 요약: 제약 도입은 기존 데이터 정제, 인덱스 보완, 오류 코드 처리를 함께 수행해야 운영 장애를 줄인다.

| 점검 항목 | 목표 기준 | 측정 방법 |
|:---|:---|:---|
| 데이터 품질 | constraint violation 0건 | DB catalog, validation query |
| 참조 관계 | orphan row 0건 | anti-join 검사 |
| 성능 영향 | lock wait 1초 이하, deadlock 0건 | DB wait event, deadlock log |

> 요약: 무결성 제약 운영은 위반 건수, 고아 레코드, 락 대기 시간을 함께 측정한다.

## Ⅵ. 실무 적용 및 결론

**적용 방안 3개 (필수 — 단계별 또는 항목별):**
1. 핵심 원장 테이블에 PK, FK, UNIQUE, CHECK를 우선 적용하고 FK 참조 컬럼에는 인덱스를 생성해 lock wait 1초 이하를 목표로 함
2. 신규 제약 추가 전 profiling query로 위반 데이터를 0건까지 정제하고, online validation 또는 maintenance window를 선택함
3. 애플리케이션은 SQLSTATE 23505, 23503 등 제약 위반 코드를 업무 메시지로 매핑하고 감사 로그에 request id를 남김

**결론 (2줄):**
- 기술사 판단: 장기 보존·공유 데이터는 DB 제약 필수, 임시·로그성 데이터는 비용 대비 선별 적용함
- 향후 방향: 데이터 계약, schema registry, CDC 검증과 DB 제약을 결합해 서비스 간 데이터 품질을 통제해야 함
