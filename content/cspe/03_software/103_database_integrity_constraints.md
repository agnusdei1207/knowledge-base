# 📖 【암기용】 개념 완전 이해

## 한눈에
- **개요**: 데이터베이스에 저장된 데이터의 정확성과 일관성을 보장하기 위해 DBMS가 강제하는 규칙(Rule)이다.
- **왜 필요한가**: 애플리케이션의 버그나 실수로 인해 데이터베이스에 쓰레기 데이터(결함 데이터)가 들어오는 것을 원천 차단하기 위해 필요하다.
- **핵심 직관**: 아무나 들어오지 못하게 클럽 입구에 세워둔 '안전 요원'과 같다. 신분증(기본키), 나이 제한(도메인), 동행 확인(참조 무결성)을 거쳐야만 들여보낸다.

## 핵심 용어 정리

| 용어/표기 | 의미 | 비유·예 |
|:---|:---|:---|
| 개체 무결성 (Entity) | 모든 행은 기본키를 가지며 NULL이나 중복될 수 없음 | 모든 국민은 고유한 주민등록번호를 가짐 |
| 참조 무결성 (Referential) | 외래키 값은 참조하는 테이블 기본키에 존재하는 값이거나 NULL임 | 없는 부서 코드를 직원에게 배정할 수 없음 |
| 도메인 무결성 (Domain) | 특정 컬럼 값은 정의된 타입, 길이, 범위를 만족해야 함 | 나이에 "스무살"이나 "-5"를 넣을 수 없음 |
| 사용자정의 무결성 | 비즈니스 규칙에 따라 사용자가 별도로 정의한 제약조건 | 대출 금액은 연봉의 2배를 넘을 수 없다 |

## 깊이 이해
- **배경·문제의식**: 파일 시스템 시절에는 데이터 형식을 코드가 책임졌다. 코드가 버그를 내면 데이터 파일이 엉망이 되었다. 데이터베이스 자체가 최후의 방어선을 쳐야 한다는 요구가 생겼다.
- **작동 원리**: DML(INSERT, UPDATE, DELETE)이 실행될 때, DBMS 내부 무결성 검사기가 트랜잭션 커밋 전 스키마에 정의된 제약을 평가한다. 위배 시 연산을 롤백하고 에러를 반환한다.
- **비유**: 엑셀에 데이터를 입력할 때 '데이터 유효성 검사'를 걸어두어 지정 목록에 없는 값을 치면 경고창이 뜨는 기능의 엔터프라이즈 버전.
- **구체 예시**: `CREATE TABLE` 시 `PRIMARY KEY`, `FOREIGN KEY`, `CHECK(age > 0)` 등을 선언하여 규칙을 등록한다.
- **흔한 오해·주의점**: 무결성(Integrity)은 데이터가 '올바른가(정확성)'의 문제이고, 보안(Security)은 '볼 권한이 있는가(기밀성)'의 문제로 서로 다르다.

## 연결 개념
- **ACID 특성**: 트랜잭션의 일관성(Consistency)이 바로 무결성 제약을 만족함을 의미한다.
- **기본키 및 외래키**: 개체 및 참조 무결성을 물리적으로 구현하는 수단.

# 📝 【답안용】 시험 답안 템플릿

## 핵심 인사이트 (3줄 요약)

> 1. **본질**: 데이터베이스의 정확성(Accuracy)과 일관성(Consistency)을 유지하기 위해 DBMS가 강제하는 룰
> 2. **가치**: 애플리케이션 결함으로부터 데이터 오염을 방지하여 기업 데이터 자산의 신뢰성을 보장
> 3. **판단 포인트**: 도메인, 개체, 참조, 사용자 정의 등 4대 무결성의 정의와 구체적 구현 수단을 매핑

## 출제 의도 및 답안 포인트

| 출제 의도 | 반드시 짚을 핵심 | 감점 회피 포인트 |
|:---|:---|:---|
| 관계형 모델의 기본 철학인 정합성 유지 기법 이해 | 4가지 주요 제약조건 종류와 구현 방법(PK, FK 등) | 보안 개념과 혼용하거나 트랜잭션 격리와 헷갈리는 서술 |

> 요약: 무결성은 외부의 잘못된 DML 시도로부터 릴레이션의 상태를 올바르게 지키는 DBMS의 방어 기제다.

---

## Ⅰ. 개요 및 필요성

- 개요: 데이터베이스에 저장된 데이터 값이 현실 세계의 실제 값과 일치하는 정확성과 논리적 일관성을 보장하기 위한 제약 조건
- 배경: 분산 애플리케이션 환경에서 다수 사용자의 병행 접근 및 버그로 인한 비정상 데이터 적재 시도 증가
- 필요성: 애플리케이션 계층 검증을 우회하는 데이터 오염을 차단하고 트랜잭션 일관성(Consistency) 물리적 강제

---

## Ⅱ. 구조 및 구성요소

```text
DML 요청 -> DBMS 무결성 검사기(Data Dictionary 참조) -> 결과
                            |                                
                            +-> 1. 도메인 (타입/범위 검증)   +-> (통과) -> 커밋
                            +-> 2. 개체 (PK NULL/중복 검증)  +-> (위배) -> 롤백 & 에러
                            +-> 3. 참조 (FK 존재 검증)
```

| 무결성 종류 | 대상 제약 | 물리적 구현 기법 |
|:---|:---|:---|
| 도메인 무결성 | 속성(Column) 값의 유효 범위, 타입 제한 | `NOT NULL`, `DEFAULT`, `CHECK` |
| 개체 무결성 | 튜플(Row)의 식별 가능성 보장 | `PRIMARY KEY` (Unique + Not Null 묵시적 강제) |
| 참조 무결성 | 테이블 간의 연관된 튜플 존재 보장 | `FOREIGN KEY` 제약조건 |
| 사용자정의 무결성 | 특정 업무 비즈니스 룰 강제 | 복잡한 `CHECK`, 서브쿼리 포함 `TRIGGER` |

> 요약: 속성 레벨, 행 레벨, 테이블 간, 업무 룰 측면에서 다각도로 검증한다.

---

## Ⅲ. 동작원리 및 흐름도

```text
DML 트랜잭션 시작 -> 사전 제약조건 평가 -> (위배 시 예외) -> 사후 제약조건 평가 -> 커밋/롤백
```

- 1단계 명령 유입: 클라이언트에서 `INSERT`/`UPDATE` 쿼리 DBMS로 전송
- 2단계 사전 검증: 컬럼의 타입 오류나 PK 중복을 DML 실행 직전에 체크
- 3단계 관계 검증: 삽입하려는 레코드의 FK 값이 부모 테이블에 존재하는지 인덱스 룩업 검사
- 4단계 연산 확정: 모든 제약조건을 통과하면 디스크 반영(Commit), 위배 시 취소(Rollback)

> 요약: DML 실행 전후에 조건을 검사하여 무결성 위배 시 연산을 즉각 거부한다.

---

## Ⅳ. 특징
- 선언적 통제: 코드(로직)가 아닌 스키마 정의(`DDL`)를 통해 규칙을 선언하므로 직관적
- 성능 오버헤드: 데이터 갱신 시마다 추가 조회(특히 FK)가 발생하여 Write 속도 저하 유발
- 예외 허용 곤란: 강제력이 높아 데이터 마이그레이션 시 기존 불량 데이터 적재를 방해하는 병목
- 상태의 일관성: 트랜잭션의 ACID 속성 중 'C'를 보장하는 물리적인 핵심 수단

> 요약: 강력한 정합성을 담보하지만, 대용량 트랜잭션 환경에서는 필연적인 오버헤드를 수반한다.

---

## Ⅴ. 심화 비교 및 적용 판단

| 비교 축 | 선언적 무결성 제약 (Constraints) | 절차적 무결성 구현 (App Logic) | 선택 기준 |
|:---|:---|:---|:---|
| 구현 계층 | DBMS 스키마 (DDL) | 백엔드 코드 또는 DB 트리거 | 아키텍처 의존성 |
| 유연성 | 낮음 (단순 비교, 표준 SQL 제약) | 매우 높음 (외부 API 연동 등) | 업무 룰 복잡도 |
| 성능 오버헤드 | 낮음 (엔진 레벨 최적화 적용) | 높음 (네트워크 왕복 및 컨텍스트 스위칭) | 트랜잭션 처리량 |

> 요약: 기본 데이터 무결성(PK, FK)은 DB 제약조건으로, 복잡한 업무 규칙은 애플리케이션 로직으로 분산 구현한다.

**리스크·대응:**
- 대규모 배치 지연: 일괄 `INSERT` 시 인덱스/제약조건 검사로 인한 병목 → 배치 처리 시 비활성화(Disable) 후 적재 완료 시 재활성화 (지표: 배치 소요 시간)
- MSA 참조 무결성 붕괴: DB 분리로 물리적 FK 불가 → API 기반 최종 일관성 및 Saga 패턴 구현 (지표: 보상 트랜잭션 발생률)

**도입 후 점검 지표:**
- 품질/운영: DML 에러율(무결성 위배 거절 건수) 모니터링 — 비정상 접근 시도 탐지
- 성능 효율: DML 응답시간 기준 0.1초 이내 — 복잡한 CHECK/트리거 병목 추적

---

## Ⅵ. 실무 적용 및 결론

**적용 방안 3개:**
1. 제약조건 이름 명명규칙 표준화: 에러 파악을 위해 `테이블명_컬럼명_PK/FK` 형식 강제
2. ON DELETE CASCADE 신중 적용: 자식 레코드 연쇄 삭제에 따른 데이터 유실 방지를 위해 논리적 삭제(Use_YN) 활용
3. 지연(Deferred) 제약조건 활용: 순환 참조 데이터 적재 시 트랜잭션 커밋 시점까지 무결성 검사를 미루는 기법 적용

**결론:**
- 기술사 판단: 무결성 제약조건은 데이터베이스 신뢰성의 최후 보루이므로, 초기 논리 모델링 단계의 제약을 물리 스키마에 타협 없이 반영해야 한다.
- 향후 방향: MSA 환경 확산으로 단일 DB의 무결성 강제가 어려워짐에 따라 이벤트 기반 동기화 아키텍처의 중요성이 부각되고 있다.
