## 미리 알고가기

- 무결성 제약조건은 데이터베이스가 허용할 수 있는 값과 관계를 미리 정해 두는 규칙임
- 도메인 무결성은 값의 범위를, 개체 무결성은 기본키를, 참조 무결성은 외래키 관계를 다룸
- 같은 규칙을 여러 프로그램이 함께 써도 흔들리지 않게 하려면 저장소 수준에서 강제해야 함
- 제약조건은 애플리케이션 검증을 우회한 변경도 저장 시점에 차단하는 최종 통제선임

## 작성 근거(검토용)

- 제목·frontmatter·미리 알고가기·본문·표·요약·결론을 5회 전수 검수해 어색한 단어·조사·동사 결합·장황한 명사구를 교정함
- 무결성 제약조건은 값·키·관계 규칙을 핵심 축으로 설명함
- 비교표는 도메인·개체·참조 무결성의 통제 대상과 방지 대상을 대비함
- 공유 DB와 데이터 이관은 제약 위반 건수·데이터 불일치 건수로 검증함

## Ⅰ. 개요

- **정의/개념**: 데이터베이스 무결성 제약조건은 값의 범위·행의 식별·테이블 관계를 스키마에 명시해 규칙을 위반한 데이터 저장을 거부하는 통제 장치임
- **배경/필요성**: 여러 애플리케이션과 배치가 같은 데이터를 변경해도 공통 규칙을 유지하기 위해 데이터베이스에서 제약조건을 강제해야 함

### 쉽게 이해하기 (학습용)
- 여러 사람이 같은 장부를 써도 잘못된 값과 끊어진 관계가 들어오지 못하게 장부 자체에 규칙을 거는 것임

## Ⅱ. 특징

- INSERT·UPDATE 시 타입·CHECK·키·참조 규칙을 검사해 위반 데이터의 저장을 거부함
- 여러 애플리케이션이 같은 데이터베이스를 써도 같은 규칙을 적용할 수 있음
- 제약조건이 약하면 중복과 고아 데이터와 잘못된 값이 쌓이기 쉬움
- 제약조건을 설계 없이 늘리면 대량 적재와 스키마 변경이 어려워질 수 있음

### 쉽게 이해하기 (학습용)
- 튼튼한 출입 규칙은 오류를 막지만 너무 복잡하면 정상적인 대량 작업도 느려질 수 있음

## Ⅲ. 종류 및 비교

| 판단 기준 | 도메인 무결성 | 개체 무결성 | 참조 무결성 |
|:---|:---|:---|:---|
| 통제 대상 | 값의 범위와 형식과 기본값 | 기본키의 유일성과 NULL 금지 | 부모와 자식 테이블의 연결 관계 |
| 대표 수단 | CHECK와 데이터 타입과 DEFAULT | PRIMARY KEY | FOREIGN KEY와 삭제 정책 |
| 방지 대상 | 형식 오류와 비정상 값 저장 | 중복 행과 식별 불가 상태 | 고아 데이터와 잘못된 참조 |

> 요약: 도메인 무결성은 값, 개체 무결성은 행 식별, 참조 무결성은 테이블 관계를 통제함.

### 쉽게 이해하기 (학습용)
- 값의 모양, 각 행의 이름표, 부모·자식 연결을 지키는 세 가지 규칙임

## Ⅳ. 설계 요소 및 구조

| 구성요소 | 설명 |
|:---|:---|
| 값 제약 규칙 | 컬럼별 허용 범위와 형식과 기본값을 정해 잘못된 값의 저장을 차단함 |
| 키 제약 규칙 | 기본키와 후보키로 각 행이 유일하게 식별되도록 함 |
| 관계 제약 규칙 | 외래키로 부모와 자식의 연결이 깨지지 않게 함 |
| 적용 정책 | 저장과 삭제와 마이그레이션 시 어떤 순서로 검증할지 정함 |

> 요약: 값·키·관계 제약을 스키마에 반영하고 데이터 변경과 이관 과정에서 위반 여부를 검증함.

### 쉽게 이해하기 (학습용)
- 컬럼 값, 행 이름표, 표 사이 연결을 각각 검사하는 세 겹의 안전망임

## Ⅴ. 원리 및 절차 흐름도

```text
[변경 요청] -> [도메인 검사] -> [키 유일성 검사]
      -> [참조 관계 검사] -> [반영 또는 오류 반환]
```

1. **변경 요청 수신**: INSERT·UPDATE·DELETE 대상과 변경 값을 확인함
2. **제약조건 검사**: 변경 대상에 적용되는 데이터 타입·CHECK·키·외래키 규칙을 확인함
3. **수락 또는 거부**: 모든 규칙을 통과하면 반영하고 위반하면 변경을 거부함
4. **오류 반환**: 위반한 제약조건과 대상을 호출자에게 전달함

> 요약: 데이터 변경 요청의 값·키·관계 제약을 검사하고 통과하면 반영하며 위반하면 오류를 반환함.

### 쉽게 이해하기 (학습용)
- 새 자료가 세 검문소를 모두 통과해야 장부에 기록됨

## Ⅵ. 실무 사례

1. 공유 DB는 핵심 업무 규칙을 PK·FK·CHECK로 강제하고 제약 위반·데이터 불일치 건수를 확인함
2. 데이터 이관은 제약조건을 단계적으로 검증하고 이관 거부율·보정 완료율을 확인함

### 쉽게 이해하기 (학습용)
- 운영 장부와 이관 자료를 같은 규칙으로 검사해 잘못된 값이 새 시스템에 들어가지 않게 함

## Ⅶ. 결론

- 무결성 제약조건은 값·키·관계 규칙을 데이터베이스에서 강제해 잘못된 데이터 저장을 차단함
- 업무 규칙·삭제 정책·적재 성능을 함께 검토하고 위반 지표를 지속 관찰해야 함

### 쉽게 이해하기 (학습용)
- 마지막 문지기 역할을 하되 업무가 바뀌면 검사 규칙도 함께 고쳐야 함
