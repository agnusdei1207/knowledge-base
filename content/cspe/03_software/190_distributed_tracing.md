## 미리 알고가기

- Trace는 하나의 요청이 분산 시스템에서 수행한 전체 작업 경로임
- Span은 Trace ID·Span ID를 가지며 자식 Span은 부모 Span ID로 호출 관계를 나타냄
- Trace Context는 `traceparent`와 `tracestate`로 요청 문맥을 서비스 사이에 전달하는 W3C 규격임
- Span Link는 부모·자식 관계가 아닌 메시지·배치 작업의 연관 Span 문맥을 연결함
- 헤드 샘플링은 요청 시작 시 수집 여부를 결정하고 테일 샘플링은 완료된 Trace를 보고 결정함
- 고카디널리티 속성과 민감정보는 저장 비용·노출 범위를 고려해 제한해야 함

## 작성 근거(검토용)

- 분산 추적은 문맥 전파, Span 관계, 호출 시간, 샘플링, 추적 완전성을 핵심 축으로 설명함
- 비교표는 결정 근거·처리 비용·적합 보존의 정확히 3개 축을 대비함
- 절차는 요청에서 Trace 문맥을 생성하고 하위 서비스 Span을 연결해 저장하는 순서를 따름

## Ⅰ. 개요

- **정의/개념**: 분산 추적은 Trace ID와 부모 Span 문맥을 서비스 호출에 전파해 하나의 요청 경로·구간별 지연·오류를 재구성하는 관측 기법임
- **배경/필요성**: 사용자 요청이 여러 서비스·큐·데이터베이스를 거칠 때 지연과 실패가 발생한 구간을 식별하기 위해 요청 단위 문맥이 필요함

### 쉽게 이해하기 (학습용)
- 분산 추적은 한 요청에 같은 Trace ID를 붙여 여러 서비스의 처리 구간을 연결함

## Ⅱ. 특징

- Trace ID가 여러 프로세스·서비스의 Span을 하나의 요청으로 연결함
- 부모·자식 Span과 Link가 동기 호출·비동기 메시지·팬아웃 관계를 표현함
- 시작·종료 시각과 상태·속성·이벤트로 구간별 처리 시간과 오류를 기록함
- 문맥 누락·샘플링 불일치·시계 오차·과도한 속성이 Trace 품질과 비용을 좌우함

### 쉽게 이해하기 (학습용)
- 호출 경계에서 문맥이 끊기면 일부 Span이 있어도 전체 요청 경로를 복원할 수 없음

## Ⅲ. 종류 및 비교

| 판단 기준 | 헤드 샘플링 | 테일 샘플링 |
|:---|:---|:---|
| 결정 근거 | 요청 시작의 확률·경로·초기 속성 | 완료된 Trace의 전체 지연·오류·Span 속성 |
| 처리 비용 | 시작 지점에서 제외해 후속 저장량 감소 | 결정 전 전체 Span을 버퍼링·처리해야 함 |
| 적합 보존 | 수집량을 미리 제한하는 일반 요청 | 저빈도 오류·고지연 Trace 우선 보존 |

> 요약: 헤드 샘플링은 요청 시작 정보로, 테일 샘플링은 완료된 Trace 결과로 보존 여부를 결정함.

### 쉽게 이해하기 (학습용)
- 헤드는 시작할 때 일부를 고르고 테일은 끝까지 본 뒤 중요한 요청을 고름

## Ⅳ. 구성요소 및 구조

| 구성요소 | 설명 |
|:---|:---|
| Trace Context | Trace ID·부모 Span ID·샘플링 정보를 서비스 호출에 전달함 |
| 계측기·Tracer | 작업 시작·종료 시 Span과 속성·이벤트·상태를 생성함 |
| Propagator | HTTP·RPC·메시지 헤더에 문맥을 주입하고 추출함 |
| Collector | Span을 수신·버퍼·샘플링하고 Trace 백엔드로 전송함 |
| Trace 저장·조회 | Span 관계를 조립해 호출 그래프와 구간별 시간을 제공함 |

```text
클라이언트 -> 서비스 A -> 서비스 B -> DB
                 |           |         |
              Span A      Span B    Span DB
                 +------ 같은 Trace ID ------+
```

> 요약: Trace Context가 호출 경계를 지나고 각 작업의 Span이 같은 Trace ID로 연결됨.

### 쉽게 이해하기 (학습용)
- Trace ID·Span ID·부모 관계와 시간 정보가 요청 경로를 재구성함

## Ⅴ. 원리 및 절차 흐름도

```text
Trace 생성 -> Span 시작 -> 문맥 주입 -> 하위 서비스 추출·Span 생성 -> Span 종료 -> 조립·조회
```

1. **Trace 생성**: 진입 서비스가 Trace ID와 루트 Span을 생성함
2. **문맥 주입**: 호출자는 `traceparent`에 Trace ID·현재 Span ID·플래그를 넣음
3. **문맥 추출**: 수신 서비스가 헤더를 검증하고 자식 Span을 생성함
4. **하위 호출 전파**: 서비스가 같은 Trace ID와 새 부모 ID를 다음 호출에 전달함
5. **Span 종료**: 각 계측기가 처리 시간·상태·속성을 기록해 Collector로 전송함
6. **Trace 조립**: 백엔드가 Span 관계를 연결해 요청 경로와 병목을 표시함

> 요약: 서비스가 Trace 문맥을 추출·갱신·전파하면 백엔드가 Span을 하나의 요청 경로로 조립함.

### 쉽게 이해하기 (학습용)
- 각 서비스가 받은 문맥을 이어 보내야 백엔드가 전체 호출 순서를 조립할 수 있음

## Ⅵ. 실무 사례

1. 결제 API는 Trace로 서비스별 Span을 연결하고 p99 종단 지연·오류 Span 비율을 확인함
2. 비동기 주문은 메시지 문맥과 Span Link를 기록하고 Trace 연결률·Span 누락률을 확인함

### 쉽게 이해하기 (학습용)
- 동기 호출은 부모 관계, 비동기 처리는 메시지 문맥과 Link 연결 상태를 확인함

## Ⅶ. 결론

- 분산 추적은 모든 호출 경계에서 문맥을 전파하고 샘플링·속성·민감정보를 통제해야 함

### 쉽게 이해하기 (학습용)
- 추적 품질은 Span 수보다 문맥 연결률과 필요한 오류·지연 요청의 보존 여부로 판단함
