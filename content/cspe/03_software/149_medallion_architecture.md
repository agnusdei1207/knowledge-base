# 📖 【암기용】 개념 완전 이해

## 한눈에
- **개요**: 데이터 레이크하우스 내에서 데이터의 품질과 정제 수준에 따라 데이터를 3단계(Bronze, Silver, Gold) 물리적 계층으로 나누어 관리하는 데이터 설계 패턴이다.
- **왜 필요한가**: 데이터 레이크에 데이터를 무작정 쌓아두면 쓰레기장이 된다(Data Swamp). 원본 데이터를 보존하면서도 단계적으로 쓸모 있는 데이터로 가공해 나가기 위한 표준화된 체계가 필요하다.
- **핵심 직관**: 광산에서 금을 캐는 과정과 같다. 방금 캐낸 흙 묻은 원석(Bronze)을 씻어내어 순수한 금속 덩어리(Silver)로 만들고, 최종적으로 예쁜 금반지(Gold)로 세공하여 진열장에 올리는 것이다.

## 핵심 용어 정리

| 용어/표기 | 의미 | 비유·예 |
|:---|:---|:---|
| 메달리온 아키텍처 | Bronze, Silver, Gold 3계층으로 데이터를 정제하는 아키텍처 패턴 | 원석 -> 세공 -> 보석 파이프라인 |
| Bronze 계층 (Raw) | 원천 시스템의 데이터를 변경 없이 그대로 저장한 구역 | 방금 캔 흙 묻은 원석 |
| Silver 계층 (Cleansed) | Bronze를 필터링, 정제, 스키마 적용하여 만든 통합 구역 | 불순물을 제거한 은괴 |
| Gold 계층 (Curated) | Silver를 비즈니스 목적에 맞게 집계(Aggregation)한 구역 | 매장에 진열된 반지 |
| Multi-hop Pipeline | 한 계층에서 다음 계층으로 넘어가는 일련의 데이터 처리 과정 | 공장의 컨베이어 벨트 |

## 깊이 이해
- **배경·문제의식**: 예전에는 원시 데이터(Raw)와 가공된 데이터가 한 곳에 섞여 있어, 데이터 분석가가 쿼리를 돌렸을 때 이 데이터가 믿을 만한(정제된) 데이터인지 알 수 없었다. 데이터 파이프라인이 꼬이고 디버깅이 불가능해지는 문제가 빈번했다.
- **작동 원리**: 데이터 파이프라인을 3단계 홉(Hop)으로 나눈다.
  1. **Bronze**: JSON, CSV 등 원본 포맷을 그대로 유지하며, 이력(History) 보존 목적으로 쌓는다.
  2. **Silver**: 중복 제거, 널(Null) 처리, 데이터 타입 강제를 수행한다. 전사적인 '단일 진실 공급원(SSOT)' 역할을 한다.
  3. **Gold**: 마케팅 부서, 재무 부서가 바로 BI 대시보드에 띄울 수 있도록 조인(Join)과 집계(Group By)를 마친 데이터다.
- **비유**: 식당 주방에 비유하자면, Bronze는 아침에 시장에서 사온 '흙 묻은 대파와 생닭' 창고, Silver는 '씻고 손질해서 소분해 둔 재료' 냉장고, Gold는 '손님상에 나가기 직전의 닭볶음탕'이다.
- **구체 예시**: 앱 클릭 로그(Bronze) -> 불량 로그 제외 및 유저 ID 매핑된 깔끔한 로그(Silver) -> 일별/국가별 활성 사용자 수 집계 테이블(Gold).
- **흔한 오해·주의점**: 이는 Databricks가 Delta Lake를 설명하며 유행시킨 '논리적 설계 패턴'일 뿐, 특정 소프트웨어나 기능이 아니다. Iceberg나 Hudi를 쓰든, 심지어 RDBMS를 쓰든 개념적으로 적용할 수 있다.

## 연결 개념
- 데이터 레이크하우스 — 메달리온 아키텍처가 구현되는 가장 대표적인 물리적 환경
- 단일 진실 공급원 (SSOT) — Silver 계층이 기업 내에서 수행하는 핵심 역할
- ETL / ELT — 각 계층 간 데이터를 이동시키고 변환하는 파이프라인 기술

# 📝 【답안용】 시험 답안 템플릿

## 핵심 인사이트 (3줄 요약)

> 1. **본질**: 데이터 레이크하우스 환경에서 데이터의 정제 수준과 비즈니스 가치에 따라 데이터를 Bronze, Silver, Gold의 3계층으로 물리적/논리적으로 분리하는 데이터 모델링 패턴이다.
> 2. **가치**: 원시 데이터 보존(Bronze)을 통한 완벽한 재처리(Re-playability) 능력을 확보하고, 계층 간 점진적 정제를 통해 파이프라인의 디버깅과 데이터 거버넌스를 단순화한다.
> 3. **판단 포인트**: 데이터 늪(Data Swamp) 방지를 위한 가장 효과적인 아키텍처이며, 오픈 테이블 포맷(Delta, Iceberg 등)의 Time Travel 기능과 결합할 때 강력한 시너지를 낸다.

## 출제 의도 및 답안 포인트

| 출제 의도 | 반드시 짚을 핵심 | 감점 회피 포인트 |
|:---|:---|:---|
| 데이터 레이크 품질 관리 및 파이프라인 설계 패턴 이해 | Bronze/Silver/Gold 3계층의 정확한 역할, 재처리(Re-playability) | 3계층을 단순히 '수집-저장-분석'으로 추상화하는 오류 (정제/집계의 차이 부각) |

> 요약: 원본 보존을 통한 롤백 편의성과 점진적 데이터 품질 향상(Data Quality)이라는 두 가지 목적을 3계층 구조에 맞춰 설명해야 한다.

---

## Ⅰ. 개요 및 필요성

- 개요: 메달리온 아키텍처(Medallion Architecture)는 데이터의 품질과 가공 수준에 따라 레이크 내의 데이터를 Bronze, Silver, Gold 3개의 계층으로 관리하는 논리적 데이터 설계 패턴이다.
- 배경: 데이터 레이크에 정제되지 않은 데이터와 가공된 데이터가 혼재되어 데이터 신뢰성이 하락하고(Data Swamp), 파이프라인 오류 시 복구가 어려움
- 필요성: 점진적 데이터 정제를 통해 품질(Data Quality)을 보장하고, 원시 데이터 보존을 바탕으로 언제든 파이프라인을 재구성할 수 있는 표준 체계 필수

---

## Ⅱ. 구조 및 구성요소

```text
Data Sources -> [ Bronze Zone ] -> [ Silver Zone ] -> [ Gold Zone ] -> BI / ML
(스트리밍/배치)  (Raw Data 이력)   (정제/필터링/통합)   (비즈니스 집계)   (분석/리포팅)
```

| 구성요소 | 데이터 특성 | 핵심 역할 |
|:---|:---|:---|
| Bronze (Raw) | 원천 시스템의 원형 보존 (Append-only) | 파이프라인 오류 시 재처리(Replay)를 위한 원본 아카이브 |
| Silver (Cleansed) | 필터링, 정제, 스키마 강제, 중복 제거 적용 | 전사적 단일 진실 공급원(SSOT), 탐색적 ML 모델링 대상 |
| Gold (Curated) | 프로젝트/부서별 특정 비즈니스 요건에 맞춰 집계 | BI 대시보드 및 즉각적인 비즈니스 쿼리(OLAP) 제공 |

> 요약: 메달리온 아키텍처는 원시 상태부터 비즈니스 레벨까지 데이터의 가치가 점진적으로 상승(Multi-hop)하는 파이프라인 구조를 정의한다.

---

## Ⅲ. 동작원리 및 흐름도

```text
원시 데이터 인입 -> 원형 보존(Bronze) -> ETL 정제(Silver) -> 비즈니스 집계(Gold)
```

- 1단계 [Bronze 적재]: 원천 소스의 데이터 포맷(JSON, CSV 등)을 그대로 유지한 채 추가(Append) 방식으로 최상위 레이어에 적재
- 2단계 [Silver 정제]: 스케줄링된 잡(Job)이나 스트리밍 엔진이 Bronze를 읽어 Null 처리, 스키마 맵핑, 중복 제거를 수행 후 정형화 포맷(Parquet)으로 저장
- 3단계 [Gold 가공]: 비즈니스 로직(예: 부서별 월매출 집계)을 적용하여 Silver 데이터를 Join 및 Group By 연산하여 요약 테이블 생성
- 4단계 [서비스 제공]: 시각화 도구(BI)나 애플리케이션이 Gold 레이어에 접근하여 최종 결과를 사용자에게 쿼리 응답

> 요약: 복잡한 단일 ETL 프로세스를 여러 개의 단순한 Hop으로 분할하여, 단계별로 명확한 상태를 가지도록 디커플링(Decoupling)한다.

---

## Ⅳ. 특징
- 단순하고 표준화된 모델링: RDBMS의 복잡한 3NF(제3정규형) 모델링 없이도 데이터 웨어하우스 수준의 데이터 구조화 가능
- 완벽한 재현성(Re-playability): 비즈니스 로직이 바뀌거나 파이프라인 버그가 발생해도, 보존된 Bronze 데이터부터 다시 읽어 Silver와 Gold를 언제든 재생산 가능
- 데이터 거버넌스 강화: 계층별로 접근 권한을 분리하여 보안(Security)을 강화(예: Bronze는 엔지니어만, Gold는 분석가만 접근)
- 배치 및 스트리밍 통합 호환성: Delta Lake 등의 오픈 테이블 포맷과 결합 시 람다 아키텍처 없이도 실시간/배치 처리를 동일 파이프라인에서 통합 처리

> 요약: 메달리온 아키텍처는 파이프라인의 디버깅을 쉽게 만들고, 데이터 엔지니어와 데이터 분석가 간의 작업 영역을 명확히 분리한다.

## Ⅴ. 심화 비교 및 적용 판단

| 비교 축 | 기존 Data Warehouse 아키텍처 | Medallion 아키텍처 | 선택 기준 |
|:---|:---|:---|:---|
| 저장 구조 | Staging -> ODS -> EDW -> Data Mart | Bronze -> Silver -> Gold | 아키텍처 패러다임 |
| 데이터 보존 | 주로 변환 후 정형 데이터만 보존 | 비정형 원천 데이터(Bronze) 완벽 보존 | 데이터 재현성 요구 |
| 처리 유연성 | Schema-on-Write 강제로 수용력 낮음 | 각 계층별로 스키마 적용 시점 유연 조정 | 분석 데이터의 다양성 |

> 요약: 데이터 레이크하우스 기반의 빅데이터 플랫폼을 구축할 경우, 레거시 EDW 모델링 대신 메달리온 아키텍처를 표준으로 채택한다.

**리스크·대응 (기본 불릿):**
- 스토리지 비용 증가: 데이터가 3벌로 복제되어 비용 상승 → Bronze 계층의 오래된 데이터를 저렴한 아카이브(Glacier 등) 티어로 전환 (지표: 계층별 스토리지 비용 추이)
- Silver 계층 병목: 전사 데이터가 Silver로 모이면서 병목 발생 → 도메인 단위로 Silver 파이프라인을 물리적/논리적으로 분할 (지표: Silver 파이프라인 지연 시간)
- 파이프라인 오케스트레이션 복잡도: 다중 Hop으로 인한 잡(Job) 의존성 관리 어려움 → Apache Airflow 등 워크플로우 관리 도구 기반의 의존성 제어 (지표: 파이프라인 실패율)

**도입 후 점검 지표 (기본 불릿):**
- 성능/효율: 파이프라인 실패 시 Bronze에서 재생산(Re-play)하여 복구 완료까지 걸리는 시간 (RTO 지표) — 모의 장애 훈련으로 측정
- 품질/운영: Silver 계층 데이터 품질 제약(Not Null 등) 통과율 99% 이상 — 데이터 품질 대시보드

## Ⅵ. 실무 적용 및 결론

**적용 방안 3개:**
1. 스트리밍 실시간 분석 파이프라인: Kafka로 수집된 로그를 Bronze에 Append하고, Spark Structured Streaming으로 Silver를 거쳐 1분 이내에 Gold 실시간 대시보드에 반영
2. 머신러닝 피처 스토어(Feature Store) 구성: 데이터 사이언티스트가 Gold의 집계된 정보에 의존하지 않고, 풍부한 특징이 남아있는 Silver 데이터에 직접 접근해 모델 학습(EDA) 수행
3. 점진적 마이그레이션(Strangler 패턴): 기존 레거시 DW의 Data Mart 계층을 Gold 레이어로 점진적 대체하면서 하단의 Bronze/Silver를 데이터 레이크로 이관

**결론:**
- 기술사 판단: 무질서한 데이터 늪(Data Swamp) 현상을 방지하고 데이터 파이프라인의 회복 탄력성(Resilience)을 확보하기 위해 레이크하우스 구축 시 반드시 메달리온 패턴을 도입해야 한다.
- 향후 방향: 최근에는 이 메달리온 파이프라인 관리를 자동화해주는 툴(Delta Live Tables 등)의 발전으로, 선언적으로 파이프라인을 구축하는 방향으로 진화 중이다.
