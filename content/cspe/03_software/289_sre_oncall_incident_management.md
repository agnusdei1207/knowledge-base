# 📖 【암기용】 개념 완전 이해

> 목적: SRE 온콜 관리·인시던트 대응을 처음 봐도 완벽히 이해하게 만든다. 시험 답안 양식이 아니라, 이해를 위한 친절한 설명이다.

## 한눈에
- **개요**: SRE 온콜·인시던트 관리는 **서비스 수준 목표(SLO)**와 **에러 버짓(Error Budget)**을 기준으로 장애를 감지·호출·대응·복구·회고하는 **인시던트 관리 프로세스(Incident Management Process)**다.
- **왜 필요한가**: 24시간 운영되는 서비스는 반드시 장애가 발생한다. 누가 언제 호출되고, 무엇을 기준으로 심각도를 정하고, 어떤 순서로 복구하며, 재발을 어떻게 막을지가 즉흥 판단이 아니라 정해진 절차로 돌아가야 대응 시간이 예측 가능해진다.
- **핵심 직관**: 관제탑이 항공기 이상 신호를 감지해 정해진 매뉴얼에 따라 관제사를 호출하고, 우선순위를 정해 통제하며, 사고 후 원인을 분석해 절차를 개선하는 것과 같은 구조다.

## 핵심 용어 정리 (내부에 등장하는 것들)

| 용어 | 의미 | 비유 |
|:---|:---|:---|
| SRE(Site Reliability Engineering) | 신뢰성을 소프트웨어 공학 방식으로 관리하는 상위 개념 — 온콜·인시던트 대응이 속한 실천 영역 | 신뢰성을 엔지니어링으로 다루는 조직 |
| SLO(Service Level Objective) | 서비스가 지켜야 할 목표 수치(예: 가용성 99.9%) | 병원의 응급 대응 목표 시간 |
| Error Budget(에러 버짓) | SLO에서 허용된 실패 여유분 — 소진되면 배포를 멈추고 안정화에 집중 | 이번 달 써도 되는 지각 허용 시간 |
| MTTD(Mean Time To Detect) | 장애 발생부터 감지까지 걸리는 시간 | 화재가 나고 경보가 울리기까지 시간 |
| MTTA(Mean Time To Acknowledge) | 경보 발생부터 담당자가 응답하기까지 시간 | 화재경보 후 소방관 출동이 확인되는 시간 |
| MTTR(Mean Time To Restore/Resolve) | 응답부터 서비스 정상화까지 걸리는 시간 | 소방관 도착 후 진화 완료까지 시간 |
| Sev1/Sev2/Sev3(심각도 등급) | 사용자 영향 범위로 나눈 장애 등급 — 등급마다 대응 속도·호출 범위가 다름 | 재난 등급(대형/중형/소형) |
| Escalation Policy(에스컬레이션 정책) | 1차 담당자 미응답 시 상위 담당자로 자동 호출을 넘기는 규칙 | 구조 요청이 무응답이면 다음 소방서로 넘어가는 규칙 |
| Oncall Rotation(온콜 로테이션) | 담당자를 교대로 배정해 항상 누군가는 대응 가능하게 하는 스케줄 | 소방서 당직 교대표 |
| Incident Commander(인시던트 지휘관) | 장애 대응을 지휘하고 역할을 분배하는 단일 책임자 | 현장 지휘관 |
| Runbook(런북) | 특정 장애 유형에 대한 사전 정의된 대응 절차서 | 화재 유형별 진화 매뉴얼 |
| Postmortem(사후 분석) | 장애 원인과 재발 방지책을 정리하는 회고 문서 — blameless(비난 없는) 원칙으로 작성 | 사고 조사 보고서 |
| Alert Fatigue(경보 피로) | 의미 없는 경보가 너무 많아 담당자가 진짜 경보에 둔감해지는 현상 | 오작동 화재경보가 잦아 무시하게 되는 상황 |
| Burn Rate Alert(소진율 경보) | 에러 버짓이 예상보다 빠르게 소진될 때 울리는 경보 | 예산이 예정보다 빨리 바닥나는 것을 알리는 경보 |

## 깊이 이해

### SLO와 Error Budget이 대응의 출발점인 이유 — 수치로 이해
- SLO 99.9% 가용성은 한 달(약 43,200분) 기준으로 43.2분의 다운타임까지는 허용한다는 뜻이다. 이 43.2분이 에러 버짓이다.
- 예: 이번 달 이미 장애로 30분을 소진했다면 남은 버짓은 13.2분뿐이다. 이 상태에서는 신규 배포를 잠정 중단하고 안정화 작업을 우선한다 — SRE가 "언제 배포를 멈출지"를 감(感)이 아니라 숫자로 판단하는 방식이다.
- burn rate alert는 이 소진 속도를 감시한다. 예: 정상 소진 속도라면 43.2분을 30일에 걸쳐 다 쓰지만, 1시간 만에 버짓의 10%(4.3분)를 소진했다면 이 속도로는 10시간 안에 버짓이 바닥난다는 뜻이므로 즉시 경보를 울린다.

### 감지-호출-복구 파이프라인을 시간으로 쪼개기 (MTTD·MTTA·MTTR)
- 워크드 예제: 14:00:00 결제 성공률이 SLO 이하로 떨어짐 → 14:03:00 모니터링이 이상을 감지해 경보 발송(MTTD 3분) → 14:07:00 1차 담당자가 응답(MTTA 4분) → 14:35:00 우회 라우팅으로 정상화(MTTR 28분).
- 총 장애 영향 시간은 MTTD+MTTA+MTTR = 3+4+28 = 35분이다. 세 구간을 나눠 보면 어디에 투자해야 할지 보인다 — 이 예제는 복구(28분)가 가장 크므로 runbook 자동화가 우선순위다. 반대로 MTTD가 크면 모니터링 커버리지 부족, MTTA가 크면 escalation 정책 문제로 원인이 갈린다.

### 심각도(Sev) 분류와 에스컬레이션이 맞물리는 원리
- Sev1(전체 서비스 중단, 매출 직접 영향), Sev2(핵심 기능 일부 저하), Sev3(경미한 영향, 우회 가능)처럼 사용자 영향 범위로 등급을 나눈다. 등급이 곧 호출 범위와 속도를 정한다.
- 예: Sev1은 1차 담당자에게 즉시 호출하고 5분 내 무응답이면 자동으로 2차 담당자, 다시 5분 내 무응답이면 관리자까지 호출한다(escalation policy). Sev3는 1차 담당자에게만 통상 근무시간 내 알림을 보낸다.
- 이렇게 등급별로 에스컬레이션 속도를 다르게 설계해야, 경미한 장애까지 관리자를 깨우는 낭비(alert fatigue의 원인)를 막으면서도 심각한 장애는 놓치지 않는다.

### Incident Commander와 Runbook의 역할 분담
- 장애가 발생하면 여러 사람이 동시에 지시를 내려 오히려 혼란이 생기는 경우가 많다. Incident Commander는 상황 지휘 한 명, 원인 조사 담당, 대외 커뮤니케이션 담당을 명확히 나눠 이를 막는다.
- 예: 결제 서비스 Sev1 발생 시 IC가 선언되면, Ops Lead는 runbook에 따라 트래픽을 백업 시스템으로 전환하고, Comms Lead는 상태 페이지에 진행 상황을 매 10분 갱신하며, IC는 이 둘을 조율하고 최종 의사결정을 내린다.
- runbook은 "결제 게이트웨이 응답 지연 시 → 캐시된 잔액 확인 모드로 전환 → 5분 후에도 미복구면 대체 PG사로 라우팅"처럼 장애 유형별로 미리 정한 절차라서, 처음 겪는 사람도 즉시 따라 할 수 있다.

### Postmortem이 blameless여야 하는 이유
- 원인 분석에서 "누가 실수했는가"를 추궁하면 다음부터 사람들은 문제를 숨기거나 축소 보고한다. blameless postmortem은 "왜 시스템이 이 실수를 막지 못했는가"를 묻는다.
- 예: 배포 중 설정값 오타로 장애가 났다면, 담당자를 질책하는 대신 "왜 CI가 이 오타를 잡지 못했는가"를 5whys로 파고들어 "설정값 검증 테스트 부재"라는 시스템적 원인을 찾고, action item으로 "배포 전 설정값 스키마 검증 추가(담당자 A, 2주 내)"를 부여한다.
- action item에 소유자와 기한이 없으면 회고 문서로만 남고 재발 방지로 이어지지 않는다.

### 비유
- 관제탑은 항공기 이상 신호를 감지하면(MTTD) 정해진 시간 내 관제사가 응답하고(MTTA), 매뉴얼에 따라 우선순위를 정해 유도해 착륙시킨다(MTTR). 사고 후에는 반드시 조사 보고서를 작성해 다음 매뉴얼에 반영한다 — SRE 인시던트 대응도 이와 동일한 구조다.

## 연결 개념
- SLO/Error Budget — 심각도 판단과 배포 중단 결정의 기준이 되는 상위 개념
- Observability(모니터링·경보) — MTTD를 좌우하는 감지 인프라
- 카오스 엔지니어링(290) — 실제 장애 전에 이 대응 절차 자체를 미리 검증하는 실험
- DORA 메트릭(288·038) — Failed Deployment Recovery Time이 MTTR과 같은 개념으로 연결

# 📝 【답안용】 시험 답안 템플릿

> 목적: 시험장에서 25분에 그대로 쓰는 답안 양식. 작성방식(추상표현 금지·수치·도식·문제유형 전환)을 엄격히 지킨다.
> 핵심: 온콜 근무표가 아니라 SLO 기반 감지, escalation, 역할 분담, 복구, postmortem 체계를 제시한다.

## 핵심 인사이트 (3줄 요약)

> 1. **본질**: SRE 온콜·인시던트 대응은 서비스 이상을 SLO 기준으로 감지하고 역할 기반으로 복구·회고하는 운영 프로세스이다.
> 2. **가치**: MTTD, MTTA, MTTR, 재발률을 줄이고 장애 대응을 개인 경험에서 조직 프로세스로 전환한다.
> 3. **판단 포인트**: 알림 품질, escalation policy, incident role, runbook, postmortem action item을 함께 설계해야 한다.

## 출제 의도 및 답안 포인트

| 출제 의도 | 반드시 짚을 핵심 | 감점 회피 포인트 |
|:---|:---|:---|
| SRE 운영 체계 이해 확인 | SLO, alert, oncall, escalation, postmortem | 장애 신고 절차만 나열 |
| 인시던트 대응 설계 판단 확인 | Sev 등급, Incident Commander, runbook | 원인 분석과 재발 방지 누락 |
| 운영 지표 적용 역량 확인 | MTTD, MTTA, MTTR, alert fatigue | 알림을 많이 만들면 된다고 작성 |

> 요약: 이 문제는 장애 대응 체계를 지표와 역할, 회고까지 연결하는 운영 설계 역량을 요구한다.

## Ⅰ. 개요 및 필요성

- 개요: SRE 온콜은 장애 대응 운영 체계이다.
- 배경: 서비스 장애는 사용자 영향 시간과 매출 손실을 만들기 때문에 감지, 호출, 지휘, 복구, 회고 절차가 필요하다.
- 필요성: SLO와 Sev 등급으로 우선순위를 정하고 MTTR 30분 이하 같은 목표로 운영해야 한다.

---

## Ⅱ. 구조 및 구성요소

```text
Monitoring Alert -> Oncall Routing -> Escalation -> Incident Command -> Runbook Recovery -> Postmortem
                         +-> SLO/Sev Classification
                         +-> Status Communication
```

| 구성요소 | 역할 | 특이사항 |
|:---|:---|:---|
| Alert Rule | SLO 위반과 증상 기반 경보 생성 | burn rate alert, synthetic check |
| Oncall Rotation | 1차·2차 담당자 배정 | PagerDuty, Opsgenie |
| Escalation Policy | 미응답·고심각도 시 상위 호출 | MTTA 5분 이하 |
| Incident Role | 지휘, 커뮤니케이션, 작업 담당 분리 | Incident Commander |
| Postmortem | 원인과 재발 방지 항목 관리 | blameless, action owner |

> 요약: SRE 인시던트 체계는 경보부터 회고까지 역할과 지표로 연결된 운영 프로세스이다.

---

## Ⅲ. 동작원리 및 흐름도

```text
SLO 위반 감지 -> 담당자 호출 -> 심각도 선언 -> 역할 배정 -> 복구 실행 -> 회고/재발방지
```

| 단계 | 처리 내용 | 검증 기준 |
|:---:|:---|:---|
| 1 | SLO와 증상 기반 alert 발생 | MTTD 5분 이하 |
| 2 | oncall 담당자 호출과 응답 확인 | MTTA 5분 이하 |
| 3 | Sev 등급과 Incident Commander 지정 | Sev1/Sev2 기준 문서화 |
| 4 | runbook 기반 완화·복구 수행 | MTTR 30분 이하 |
| 5 | postmortem과 action item 추적 | 재발 방지 완료율 95% 이상 |

> 요약: SRE 대응은 감지, 호출, 지휘, 복구, 회고를 시간 지표로 통제한다.

## Ⅳ. 특징

| 구분 | 전통 장애 대응 | SRE 온콜·인시던트 대응 | 수치·기술 포인트 |
|:---|:---|:---|:---|
| 기준 | 담당자 경험 | SLO, error budget | burn rate alert |
| 호출 | 수동 연락 | rotation, escalation | MTTA 5분 이하 |
| 지휘 | 중복 의사결정 | Incident Commander | role-based response |
| 회고 | 원인 문서 일부 | blameless postmortem | action item 완료율 95% |

> 요약: SRE 방식은 장애 대응을 개인 숙련에서 SLO와 역할 기반 운영 체계로 전환한다.

## Ⅴ. 심화 비교 및 적용 판단

| 구분 | 기존/대안 | 본 키워드 | 선택 기준 |
|:---|:---|:---|:---|
| 구조 | 업무시간 대응 중심 | 24x7 oncall과 escalation | SLA 99.9% 이상 서비스 |
| 비용/성능 | 알림 다수 생성 | SLO 기반 alert 압축 | alert fatigue 월 10건 이하 |
| 운영/위험 | 장애 후 수습 | runbook과 postmortem 학습 | MTTR 30분 이하 요구 |

> 요약: 사용자 영향이 큰 서비스는 SLO 기반 alert와 역할 분담형 인시던트 대응이 필요하다.

| 리스크 | 원인 | 대응 방안 | 확인 지표 |
|:---|:---|:---|:---|
| Alert Fatigue | 증상 아닌 원인별 경보 과다 | SLO burn rate alert, deduplication | actionable alert 80% 이상 |
| Escalation 지연 | 담당자 미응답·연락망 누락 | 1차/2차/관리자 escalation | MTTA 5분 이하 |
| 재발 반복 | postmortem action 미완료 | owner, due date, 월간 추적 | 재발률 월 1건 이하 |

> 요약: 온콜 운영의 리스크는 경보 피로, 호출 지연, 재발이며 지표와 소유자로 통제한다.

| 점검 항목 | 목표 기준 | 측정 방법 |
|:---|:---|:---|
| 감지 | MTTD 5분 이하 | monitoring event timestamp |
| 대응 | MTTA 5분 이하, MTTR 30분 이하 | incident timeline |
| 학습 | action item 완료율 95% 이상 | postmortem tracker |

> 요약: SRE 인시던트 체계는 감지, 대응, 학습 지표가 함께 관리될 때 재발을 줄인다.

---

## Ⅵ. 실무 적용 및 결론

**적용 방안 3개:**
1. 서비스별 SLO와 burn rate alert를 정의하고 Sev1/Sev2/Sev3 기준을 사용자 영향과 error budget 소모율로 설정함
2. PagerDuty/Opsgenie로 1차·2차·관리자 escalation을 구성하고 MTTA 5분 이하를 목표로 온콜 훈련을 수행함
3. 주요 장애 유형별 runbook을 작성하고 postmortem action item에 owner와 due date를 부여해 완료율 95% 이상을 관리함

**결론 (2줄):**
- 기술사 판단: SLA 99.9% 이상 서비스는 SLO 기반 alert, 온콜 rotation, incident role, postmortem을 필수 운영 체계로 둠
- 향후 방향: SRE 대응은 AIOps 알림 상관분석, 자동 완화, error budget 기반 릴리스 제어와 결합됨
