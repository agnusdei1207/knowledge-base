# 📖 【암기용】 개념 완전 이해

> 목적: 플랫폼 엔지니어링 셀프서비스를 처음 보는 사람도 개념과 내부 용어를 완전히 이해하게 만든다. 시험 답안 양식이 아니라, 이해를 위한 친절한 설명이다.

## 한눈에
- **개요**: 플랫폼 엔지니어링 셀프서비스는 **내부 개발자 플랫폼(Internal Developer Platform, IDP)**이 제공하는 셀프서비스 프로비저닝 방식으로, 개발팀이 티켓 없이 표준 포털·템플릿으로 인프라·배포·관측성을 직접 신청·생성하게 하는 운영 모델이다.
- **왜 필요한가**: DevOps 전환으로 개발팀이 인프라 운영까지 떠맡게 됐지만, Kubernetes·CI/CD·보안 정책은 모든 개발자가 깊이 알기엔 너무 복잡해졌다(인지 부하 초과). 플랫폼팀이 반복 작업을 표준 상품으로 만들어 제공하지 않으면 팀마다 제각각 우회하다 장애·보안 사고가 난다.
- **핵심 직관**: 손님이 주방에 직접 들어가 요리하게 두지 않고, 검증된 메뉴 버튼을 누르면 표준 레시피대로 요리가 나오는 구조다. 자유도는 메뉴판 안에서만 준다.

## 핵심 용어 정리 (내부에 등장하는 것들)

| 용어 | 의미 | 비유 |
|:---|:---|:---|
| IDP(내부 개발자 플랫폼) | 셀프서비스 인프라·배포·관측성을 상품처럼 제공하는 플랫폼 전체 | 백화점 매장 전체 시스템 |
| Golden Path(Paved Road) | 플랫폼팀이 검증하고 지원을 보장하는 표준 개발·배포 경로 | 포장된 정규 등산로 — 벗어나면 지원 없음 |
| 서비스 카탈로그 | 어떤 서비스가 있고 누가 소유하며 상태가 어떤지 등록하는 명부 | 조직 내 서비스 전화번호부 |
| 템플릿(Scaffolding) | 신청 시 표준 구성(저장소·CI·네임스페이스 등)을 자동 생성하는 틀 | 붕어빵 틀 |
| Policy as Code | 보안·쿼터·네트워크 규칙을 코드로 정의해 자동 검증·차단 | 매장 입장 규칙을 코드로 자동 심사 |
| 인지 부하(Cognitive Load) | 개발자가 본업(비즈니스 로직) 외에 알아야 하는 인프라 지식의 부담 | 요리사가 요리뿐 아니라 전기·배관까지 알아야 하는 부담 |
| DORA 지표 | 배포 빈도·변경 리드타임·변경 실패율·평균 복구시간(MTTR)으로 소프트웨어 딜리버리 성숙도를 재는 4개 지표 | 배송 서비스의 KPI(배송 빈도·소요시간·파손율·복구시간) |

## 깊이 이해

### 왜 지금 이 개념이 필요해졌나 — DevOps의 그림자
- 2010년대 DevOps는 "만든 사람이 운영도 한다(You build it, you run it)"를 확산시켰다. 문제는 인프라 도구가 기하급수로 늘어난 것이다 — Kubernetes, Terraform, Helm, service mesh, observability stack까지 한 팀이 다 배우기엔 도구 수가 너무 많아졌다.
- 결과적으로 개발자는 비즈니스 로직보다 YAML·네트워크 정책과 씨름하는 시간이 늘었다(불필요한 인지 부하). 플랫폼 엔지니어링은 "그 인프라 복잡성을 플랫폼팀이 대신 흡수하고, 개발자에게는 단순한 셀프서비스 인터페이스만 남기자"는 반작용으로 등장했다.

### 셀프서비스가 실제로 줄이는 것 — 수치로 보는 효과
- 기존 티켓 기반: 새 마이크로서비스 하나를 만들려면 (1) 저장소 생성 요청 티켓, (2) CI 파이프라인 설정 요청, (3) Kubernetes 네임스페이스·쿼터 요청, (4) 모니터링 대시보드 요청을 각각 다른 팀에 올려야 했다 — 팀마다 처리에 1~2일씩 걸리면 총 리드타임이 5일 이상이 된다.
- 플랫폼 셀프서비스: 개발자가 포털에서 "Spring Boot API" 템플릿을 선택하면, 미리 정의된 Terraform·Helm 모듈이 저장소·CI·네임스페이스·대시보드를 한 번에 생성한다 — 승인 규칙이 이미 템플릿에 내장돼 있으므로 사람 대기 없이 수 분~1시간 내 완료된다.
- 이 리드타임 단축이 DORA 지표의 "변경 리드타임"을 직접 개선한다. Elite 성과 조직 기준 리드타임은 1시간 이내, 배포 빈도는 하루 여러 번이 목표치다.

### "무제한 자율"이 아니라 "제한된 자율"인 이유
- 셀프서비스라고 해서 개발자가 아무 리소스나 무한정 만들 수 있게 하면, 예산 초과·보안 구멍·규정 위반이 생긴다. 그래서 템플릿과 포털 뒤에는 반드시 **정책(Policy as Code)**이 숨어 있다.
- 예: 템플릿으로 새 네임스페이스를 만들면 자동으로 (1) CPU/메모리 쿼터 상한, (2) 네트워크 정책(다른 팀 네임스페이스 접근 차단), (3) 이미지 서명 검증(293과 연결) 규칙이 함께 적용된다. 개발자는 이 제약을 못 느끼지만, 정책 위반 요청은 포털 단계에서 거부된다.
- 즉 "자유도를 늘리는 것"이 목적이 아니라, "표준 경로 안에서는 승인 없이 빠르게, 표준 밖은 명시적으로 어렵게" 만드는 것이 목적이다.

### 비유와 흔한 오해
- **비유**: 식당 손님에게 주방을 개방하는 대신, 검증된 메뉴 버튼을 누르면 표준 레시피대로 요리가 나오게 하는 것과 같다 — 손님(개발자)의 선택권은 메뉴판(golden path) 안으로 제한되지만, 그 안에서는 즉시 서비스된다.
- **오해 1**: "플랫폼 엔지니어링 = DevOps 도구를 많이 설치하는 것"이 아니다. 도구를 개발자 제품처럼 다듬어 제공하는 **제품 사고(product mindset)**가 핵심이다 — 플랫폼팀은 인프라 운영팀이 아니라 내부 고객(개발자)을 상대하는 제품팀이다.
- **오해 2**: "표준화하면 혁신이 죽는다"가 아니다. 표준 경로 밖의 예외적 요구는 막는 게 아니라, 승인 절차를 명시적으로 두어(approval gate) 특수 사례를 허용하되 감사 가능하게 만든다.

## 연결 개념
- IDP — 이 셀프서비스를 구현하는 플랫폼 실체(296 Backstage가 대표 구현체)
- Golden Path — 셀프서비스가 안내하는 표준 경로 그 자체
- GitOps — 템플릿이 생성한 선언형 설정을 Git 기준으로 실제 배포까지 연결하는 실행 메커니즘

# 📝 【답안용】 시험 답안 템플릿

> 목적: 시험장에서 25분에 그대로 쓰는 답안 양식. 도구 소개보다 개발자 경험과 운영 통제의 균형을 중심으로 답한다.

## 핵심 인사이트 (3줄 요약)

> 1. **본질**: 플랫폼 엔지니어링 셀프서비스는 공통 인프라 기능을 내부 제품으로 제공해 개발팀의 반복 요청을 표준화하는 운영 모델이다.
> 2. **가치**: golden path, 템플릿, 정책 자동화로 lead time, change failure rate, MTTR을 지표로 관리한다.
> 3. **판단 포인트**: 자유도를 높이는 것이 아니라 권한·quota·보안 정책이 내장된 셀프서비스를 설계해야 한다.

## 출제 의도 및 답안 포인트

| 출제 의도 | 반드시 짚을 핵심 | 감점 회피 포인트 |
|:---|:---|:---|
| DevOps 이후 운영 모델 이해 확인 | IDP, golden path, paved road, self-service | Backstage 도구명만 나열 |
| 플랫폼 제품화 판단 확인 | 개발자 경험, 서비스 카탈로그, 템플릿, SLO | 티켓 자동화 수준으로 축소 |
| 통제 기준 확인 | RBAC, quota, policy as code, audit | 무제한 권한 부여로 설명 |

> 요약: 이 문제는 개발 속도보다 표준 경로와 운영 통제를 제품처럼 제공하는 역량을 요구한다.

## Ⅰ. 개요 및 필요성

- 개요: 플랫폼 엔지니어링 셀프서비스는 표준 포털 기반 개발자 지원 방식이다.
- 배경: 클라우드 네이티브 운영은 도구가 많아 개발팀별 인프라·배포·관측성 사용 편차가 발생한다.
- 필요성: golden path와 자동화 템플릿으로 반복 작업을 제공해 리드타임과 장애 대응 지표를 관리해야 한다.

---

## Ⅱ. 구조 및 구성요소

```text
Developer Portal -> Service Catalog -> Template -> GitOps/IaC -> Runtime Platform
                                  / Policy as Code
                                  / Observability/SLO
```

| 구성요소 | 역할 | 특이사항 |
|:---|:---|:---|
| 개발자 포털 | 요청·조회·문서 진입점 | Backstage, Port |
| 서비스 카탈로그 | 서비스 소유자·의존성·상태 관리 | ownership 필수 |
| 템플릿·Golden Path | 표준 저장소·CI/CD·배포 생성 | 승인된 기술 스택 |
| 정책·관측성 | RBAC, quota, SLO, 로그·메트릭 | Policy as Code 연동 |

> 요약: 셀프서비스 구조는 포털, 카탈로그, 템플릿, 정책, 관측성을 결합해 개발자 요청을 표준 경로로 처리한다.

---

## Ⅲ. 동작원리 및 흐름도

```text
요청 선택 -> 템플릿 파라미터 입력 -> 정책 검증 -> Git PR 생성 -> GitOps 배포 -> SLO 관측
```

| 단계 | 처리 내용 | 검증 기준 |
|:---:|:---|:---|
| 1 | 개발자가 포털에서 서비스 유형 선택 | 승인 템플릿 사용률 80% 이상 |
| 2 | IaC·CI/CD·관측성 설정 자동 생성 | 생성 실패율 5% 이하 |
| 3 | RBAC·quota·보안 정책 검증 | policy violation 차단 |
| 4 | GitOps 배포 후 SLO·소유자 등록 | owner 등록률 100% |

> 요약: 동작은 템플릿 선택, 정책 검증, Git 기반 변경, 배포 관측 순서로 개발자 자율과 운영 통제를 연결한다.

## Ⅵ. 실무 적용 및 결론

**적용 방안 3개 (필수 - 단계별 또는 항목별):**
1. 반복 요청 상위 10개를 선정해 서비스 생성, DB 신청, 배포 파이프라인을 Backstage 템플릿으로 제공
2. Terraform·Helm·Argo CD와 OPA 정책을 연결해 quota, image signing, network policy를 자동 검증
3. 서비스 카탈로그에 owner, SLO, dependency, runbook을 필수 등록하고 DORA·NPS 지표를 월 단위 리뷰

**결론 (2줄):**
- 기술사 판단: 서비스 수 30개 이상 조직은 티켓 운영보다 IDP 기반 셀프서비스를 선택하고, 소규모 조직은 golden path 문서와 템플릿부터 시작
- 향후 방향: 플랫폼팀은 인프라 운영팀이 아니라 내부 제품팀으로 전환해 adoption, lead time, failure rate를 지속 관리해야 함
