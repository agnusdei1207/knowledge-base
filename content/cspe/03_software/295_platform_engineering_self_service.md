# 📖 【암기용】 개념 완전 이해

> 목적: 플랫폼 엔지니어링 셀프서비스를 처음 봐도 완전히 이해하게 만든다. 시험 답안 양식이 아니라, 이해를 위한 설명이다.

## 한눈에
- **개요**: 개발팀이 표준 포털과 템플릿으로 인프라·배포·관측성을 직접 신청·생성하게 하는 내부 플랫폼 운영 방식
- **왜 필요한가**: Kubernetes, CI/CD, 보안 정책이 복잡해지면 개발자가 티켓을 기다리거나 팀마다 다른 방식으로 우회한다.
- **핵심 직관**: 식당 주방을 모든 손님에게 열어 주지 않고, 검증된 메뉴 버튼으로 주문하면 표준 레시피대로 음식이 나오는 구조이다.

## 깊이 이해
- **배경·문제의식**: DevOps 전환 후 개발팀이 인프라까지 맡게 되었지만, 모든 팀이 클러스터·네트워크·보안 정책을 깊게 알 수는 없다. 플랫폼팀은 반복 작업을 제품화해야 한다.
- **작동 원리**: 내부 개발자 플랫폼(IDP)이 서비스 카탈로그, golden path, 템플릿, 권한, 정책, 관측성을 제공한다. 개발자는 포털에서 새 서비스를 만들고, Terraform·Helm·GitOps가 표준 구성을 생성한다.
- **비유**: 사내 PC를 직접 조립하지 않고 표준 모델을 포털에서 신청하면 보안 도구와 계정이 설정된 상태로 받는 것과 같다.
- **구체 예시**: 개발자가 "Spring Boot API" 템플릿을 선택하면 Git 저장소, CI 파이프라인, Kubernetes namespace, Grafana dashboard, PagerDuty service가 자동 생성된다.
- **흔한 오해·주의점**: 셀프서비스는 무제한 자율이 아니다. 정책, quota, 승인, 감사가 내장된 제한된 자율이어야 운영 위험을 줄인다.

## 연결 개념
- IDP - 내부 개발자 플랫폼으로 포털·템플릿·카탈로그 제공
- Golden Path - 검증된 표준 개발·배포 경로
- GitOps - 선언형 설정을 Git 기준으로 배포

# 📝 【답안용】 시험 답안 템플릿

> 목적: 시험장에서 25분에 그대로 쓰는 답안 양식. 도구 소개보다 개발자 경험과 운영 통제의 균형을 중심으로 답한다.

## 핵심 인사이트 (3줄 요약)

> 1. **본질**: 플랫폼 엔지니어링 셀프서비스는 공통 인프라 기능을 내부 제품으로 제공해 개발팀의 반복 요청을 표준화하는 운영 모델이다.
> 2. **가치**: golden path, 템플릿, 정책 자동화로 lead time, change failure rate, MTTR을 지표로 관리한다.
> 3. **판단 포인트**: 자유도를 높이는 것이 아니라 권한·quota·보안 정책이 내장된 셀프서비스를 설계해야 한다.

## 출제 의도 및 답안 포인트

| 출제 의도 | 반드시 짚을 핵심 | 감점 회피 포인트 |
|:---|:---|:---|
| DevOps 이후 운영 모델 이해 확인 | IDP, golden path, paved road, self-service | Backstage 도구명만 나열 |
| 플랫폼 제품화 판단 확인 | 개발자 경험, 서비스 카탈로그, 템플릿, SLO | 티켓 자동화 수준으로 축소 |
| 통제 기준 확인 | RBAC, quota, policy as code, audit | 무제한 권한 부여로 설명 |

> 요약: 이 문제는 개발 속도보다 표준 경로와 운영 통제를 제품처럼 제공하는 역량을 요구한다.

---

## Ⅰ. 개요 및 필요성

- 개요: 플랫폼 엔지니어링 셀프서비스는 표준 포털 기반 개발자 지원 방식이다.
- 배경: 클라우드 네이티브 운영은 도구가 많아 개발팀별 인프라·배포·관측성 사용 편차가 발생한다.
- 필요성: golden path와 자동화 템플릿으로 반복 작업을 제공해 리드타임과 장애 대응 지표를 관리해야 한다.

---

## Ⅱ. 구조 및 구성요소

```text
Developer Portal -> Service Catalog -> Template -> GitOps/IaC -> Runtime Platform
                                  / Policy as Code
                                  / Observability/SLO
```

| 구성요소 | 역할 | 특이사항 |
|:---|:---|:---|
| 개발자 포털 | 요청·조회·문서 진입점 | Backstage, Port |
| 서비스 카탈로그 | 서비스 소유자·의존성·상태 관리 | ownership 필수 |
| 템플릿·Golden Path | 표준 저장소·CI/CD·배포 생성 | 승인된 기술 스택 |
| 정책·관측성 | RBAC, quota, SLO, 로그·메트릭 | Policy as Code 연동 |

> 요약: 셀프서비스 구조는 포털, 카탈로그, 템플릿, 정책, 관측성을 결합해 개발자 요청을 표준 경로로 처리한다.

---

## Ⅲ. 동작원리 및 흐름도

```text
요청 선택 -> 템플릿 파라미터 입력 -> 정책 검증 -> Git PR 생성 -> GitOps 배포 -> SLO 관측
```

| 단계 | 처리 내용 | 검증 기준 |
|:---:|:---|:---|
| 1 | 개발자가 포털에서 서비스 유형 선택 | 승인 템플릿 사용률 80% 이상 |
| 2 | IaC·CI/CD·관측성 설정 자동 생성 | 생성 실패율 5% 이하 |
| 3 | RBAC·quota·보안 정책 검증 | policy violation 차단 |
| 4 | GitOps 배포 후 SLO·소유자 등록 | owner 등록률 100% |

> 요약: 동작은 템플릿 선택, 정책 검증, Git 기반 변경, 배포 관측 순서로 개발자 자율과 운영 통제를 연결한다.

## Ⅳ. 특징

| 구분 | 티켓 기반 운영 | 플랫폼 셀프서비스 | 수치·판단 기준 |
|:---|:---|:---|:---|
| 요청 처리 | 운영팀 수동 작업 | 템플릿 자동 생성 | lead time 5일에서 1시간 |
| 표준화 | 팀별 편차 | golden path 적용 | 표준 템플릿 사용률 80% 이상 |
| 통제 | 리뷰자 의존 | policy as code | 위반 배포 0건 |
| 한계 | 병목 발생 | 플랫폼 제품 관리 필요 | 내부 NPS, adoption 측정 |

> 요약: 셀프서비스는 티켓 병목을 줄이지만, 표준 경로 채택률과 정책 차단 지표로 운영해야 한다.

## Ⅵ. 실무 적용 및 결론

**적용 방안 3개 (필수 - 단계별 또는 항목별):**
1. 반복 요청 상위 10개를 선정해 서비스 생성, DB 신청, 배포 파이프라인을 Backstage 템플릿으로 제공
2. Terraform·Helm·Argo CD와 OPA 정책을 연결해 quota, image signing, network policy를 자동 검증
3. 서비스 카탈로그에 owner, SLO, dependency, runbook을 필수 등록하고 DORA·NPS 지표를 월 단위 리뷰

**결론 (2줄):**
- 기술사 판단: 서비스 수 30개 이상 조직은 티켓 운영보다 IDP 기반 셀프서비스를 선택하고, 소규모 조직은 golden path 문서와 템플릿부터 시작
- 향후 방향: 플랫폼팀은 인프라 운영팀이 아니라 내부 제품팀으로 전환해 adoption, lead time, failure rate를 지속 관리해야 함
