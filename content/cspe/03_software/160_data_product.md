# 📖 【암기용】 개념 완전 이해

> 목적: 데이터 제품을 처음 보는 사람도 완벽히 이해하게 만든다. 시험 답안 양식이 아니라, 이해를 위한 친절한 설명이다.

## 한눈에
- **개요**: **데이터 메시**(Data Mesh) 아키텍처의 핵심 산출물 — 특정 소비자의 문제를 풀기 위해 책임자·품질·SLA·인터페이스를 갖춘 **재사용 가능한 데이터 단위**
- **왜 필요한가**: 데이터셋을 파일이나 테이블로만 던져주면 "이 컬럼이 뭘 뜻하는지", "품질은 믿을 만한지", "누가 책임지는지"가 불명확해 소비자가 매번 물어봐야 한다. 데이터 제품은 데이터를 소프트웨어 제품처럼 취급해 신뢰 기준을 만든다.
- **핵심 직관**: 원재료(raw data)를 그냥 주는 게 아니라, 포장·설명서·품질보증·고객지원이 딸린 상품으로 데이터를 제공하는 방식이다.

## 핵심 용어 정리 (내부에 등장하는 것들)

| 용어 | 의미 | 비유 |
|:---|:---|:---|
| 데이터 메시 | 도메인별로 데이터 소유권과 책임을 분산하는 아키텍처 원칙 — 데이터 제품의 상위 개념 | 각 부서가 자기 물류창고를 직접 운영 |
| Discoverable (검색 가능) | 카탈로그에서 이 데이터 제품을 쉽게 찾을 수 있음 | 쇼핑몰의 상품 검색 |
| Addressable (접근 가능) | 고정된 주소(API·SQL endpoint)로 접근 가능 | 상품 고유 URL |
| Trustworthy (신뢰 가능) | 품질 점수·SLA가 공개되어 믿고 쓸 수 있음 | 품질 인증마크 |
| Self-describing (자기 서술) | 스키마·문서·의미가 함께 제공되어 별도 문의 없이 이해 가능 | 상품에 동봉된 설명서 |
| Owner (제품 책임자) | 품질과 변경을 책임지는 도메인 담당자 | 브랜드 매니저 |
| 인터페이스 (SQL/API/Event) | 소비자가 데이터를 실제로 가져오는 방식 | 매장 진열대, 배달 앱 |
| 데이터 계약 | 이 제품의 스키마·품질·SLA를 구체적으로 명시한 문서 | 제품 사양서 |

## 깊이 이해

### 왜 필요한가 — 중앙 데이터팀의 병목 (배경)
- 중앙 데이터팀 소수 인원이 여러 도메인의 요청을 순번대로 처리하면, 신규 데이터셋 하나 받는 데 대기가 길어진다. 데이터 메시는 이 병목을 "각 도메인이 자기 데이터를 제품으로 직접 제공"하는 구조로 바꿔 요청 대기를 없앤다 — 대신 도메인마다 discoverable·trustworthy 등 최소 품질 기준을 지켜야 한다.

### 데이터셋과 데이터 제품의 차이를 수치로 (worked example)
- `Customer 360` 데이터 제품: 고객 ID, 세그먼트, 동의 상태, 최근 구매 이력을 담고 **품질 점수 98점**, **freshness 1시간 이내**, **API·SQL 양쪽 접근 가능**, **owner 연락처(Slack 채널)** 를 카탈로그에 명시한다.
- 같은 데이터를 그냥 `customer_raw`라는 테이블로만 공유하면 위 네 가지(품질 수치, 신선도, 접근 방식, 담당자)가 전부 비어 있어 소비자가 신뢰하고 쓸 수 없다 — 이 차이가 "제품"과 "데이터셋"을 가른다.

### 제품화 대상 판별 원리
- 아무 테이블이나 제품으로 등록하면 카탈로그가 난립한다. 판별 기준은 **소비자 3명 이상**, **월 반복 요청 10건 이상**, **업무 영향도 P1/P2**다. 이 기준에 못 미치면 임시 데이터셋으로 취급하고 경량 품질 규칙만 적용한다.

### 흔한 오해
- "제품"이라는 이름을 붙였다고 저절로 제품이 되지 않는다. owner가 없거나, SLA가 없거나, 변경 시 소비자에게 통보하지 않으면 이름만 데이터 제품이고 실제로는 방치된 테이블과 같다.

## 연결 개념
- 데이터 메시 — 도메인 소유 데이터 제품을 운영하는 상위 아키텍처 원칙
- 데이터 계약 — 제품의 스키마·품질·SLA를 구체화하는 명세
- 데이터 카탈로그 — 제품을 검색하고 접근 신청하는 진입점

# 📝 【답안용】 시험 답안 템플릿

> 목적: 시험장에서 25분에 그대로 쓰는 답안 양식. 작성방식(추상표현 금지·수치·도식·문제유형 전환)을 엄격히 지킨다.
> 핵심: 데이터 제품 답안은 테이블 제공이 아니라 소비자 가치, owner, 계약, 품질, SLA, 접근 인터페이스를 갖춘 운영 단위로 작성해야 한다.

## 핵심 인사이트 (3줄 요약)

> 1. **본질**: 데이터 제품은 특정 소비자 요구를 해결하도록 품질, SLA, 계약, 문서, 접근 인터페이스를 갖춘 데이터 제공 단위임.
> 2. **가치**: 재사용 가능한 데이터 자산을 제품처럼 관리해 검색, 사용, 변경, 장애 대응 책임을 명확히 함.
> 3. **판단 포인트**: 제품화 대상은 소비자 수, 재사용 빈도, 업무 영향, SLA 요구로 선정해야 함.

## 출제 의도 및 답안 포인트

| 출제 의도 | 반드시 짚을 핵심 | 감점 회피 포인트 |
|:---|:---|:---|
| 데이터 제품 개념 확인 | owner, consumer, SLA, contract, interface | 데이터셋/테이블과 동일시 |
| 데이터 메시 적용 판단 확인 | 도메인 책임과 플랫폼 지원 분리 | 중앙 데이터팀만 언급 |
| 운영 지표 설계 확인 | adoption, freshness, quality, incident | 추상적 가치 설명 |

> 요약: 데이터 제품은 소비자 관점의 데이터 서비스이며 책임과 SLA가 채점 포인트임.

## Ⅰ. 개요 및 필요성

- 개요: 데이터 제품은 소비자 중심 데이터 제공 단위임.
- 배경: 데이터셋만 제공하면 의미, 품질, 변경 책임이 불명확하다.
- 필요성: owner, 계약, 품질, SLA, 인터페이스를 포함해 재사용 가능한 데이터 서비스 단위로 관리한다.

---

## Ⅱ. 구조 및 구성요소

```text
Domain Source -> Product Pipeline -> Data Contract/Quality -> Catalog/API/SQL -> Consumer
                              +-> Owner/SLA
                              +-> Observability
```

| 구성요소 | 역할 | 특이사항 |
|:---|:---|:---|
| 도메인 owner | 제품 목표, 책임, 변경 승인 | product owner 지정 |
| 데이터 계약 | 스키마, 의미, 품질, SLA 정의 | version 관리 |
| 제공 인터페이스 | SQL, API, event, feature store | addressable access |
| 관측성 | freshness, 품질, 사용량, 장애 추적 | SLO dashboard |

> 요약: 데이터 제품은 도메인 책임, 계약, 인터페이스, 관측성이 결합된 데이터 서비스 구조임.

---

## Ⅲ. 동작원리 및 흐름도

```text
소비자 요구 식별 -> 제품 범위 정의 -> 계약/품질 구현 -> 카탈로그 등록 -> 사용/관측/개선
```

| 단계 | 처리 내용 | 검증 기준 |
|:---:|:---|:---|
| 1 | 소비자 문제와 사용 시나리오 정의 | 주요 consumer 3개 이상 |
| 2 | 데이터 모델, 계약, SLA 확정 | freshness, 품질 기준 명시 |
| 3 | 파이프라인과 품질 검사 구현 | quality score 95점 이상 |
| 4 | 카탈로그 등록과 접근 권한 제공 | 승인 SLA 2일 이하 |
| 5 | 사용량, 장애, 만족도 개선 | MAU, incident, NPS |

> 요약: 데이터 제품은 소비자 요구에서 시작해 계약과 관측 지표로 운영되는 생애주기를 가짐.

## Ⅳ. 특징

| 구분 | 일반 데이터셋 | 데이터 제품 | 판단 포인트 |
|:---|:---|:---|:---|
| 관점 | 생산자 중심 | 소비자 문제 중심 | 사용자 수, 재사용 |

| 한계 | 제공 부담 낮음 | 제품 운영 비용 필요 | adoption 기준 |

> 요약: 데이터 제품은 소비자 가치와 운영 책임이 있는 데이터셋만 대상으로 삼아야 함.

## Ⅴ. 심화 비교 및 적용 판단

| 구분 | 기존/대안 | 본 키워드 | 선택 기준 |
|:---|:---|:---|:---|
| 구조 | 중앙 마트 제공 | 도메인 데이터 제품 | 도메인 지식 필요 |
| 비용/처리 | 요청별 개발 | 재사용 제품 운영 | 월 반복 요청 10건 이상 |
| 운영/위험 | 품질 책임 분산 | owner/SLO 책임 | 업무 영향도 P1/P2 |

> 요약: 반복 소비와 도메인 책임이 필요한 데이터는 제품화하고 일회성 분석은 임시 데이터셋으로 처리함.

| 리스크 | 원인 | 대응 방안 | 확인 지표 |
|:---|:---|:---|:---|
| 제품 난립 | 기준 없는 등록 | product review board | 활성 제품 비율 |
| 품질 하락 | owner 부재 | SLO와 incident 관리 | quality score 95점 |
| 소비 저조 | 사용 문제 미정의 | consumer interview, adoption KPI | MAU, query count |

> 요약: 데이터 제품 리스크는 난립과 낮은 사용률이므로 등록 기준과 adoption 지표가 필요함.

| 점검 항목 | 목표 기준 | 측정 방법 |
|:---|:---|:---|
| 사용 | 주요 consumer 3개 이상, MAU 증가 | catalog/API 로그 |
| 품질 | quality score 95점 이상 | DQ dashboard |
| 신선도 | freshness SLA 준수 99% | pipeline timestamp |

> 요약: 제품 성공은 사용률, 품질 점수, freshness 준수율로 판단함.

## Ⅵ. 실무 적용 및 결론

**적용 방안 3개 (필수 - 단계별 또는 항목별):**
1. 대상 선정: 소비자 3개 이상, 월 반복 요청 10건 이상, 업무 영향도 P1/P2 데이터셋을 제품 후보로 선정
2. 제품 명세: owner, 소비자, contract, quality score 95점, freshness SLA, SQL/API/event 인터페이스를 카탈로그에 등록
3. 운영 체계: adoption, SLA miss, incident, change lead time을 월간 리뷰하고 미사용 제품은 archive 절차 적용

**결론 (2줄):**
- 기술사 판단: 데이터 제품은 모든 테이블이 아니라 소비자 가치와 반복 사용이 검증된 데이터에 적용해야 함
- 향후 방향: 데이터 메시, 데이터 계약, AI 피처 스토어와 결합되어 도메인 기반 데이터 플랫폼의 기본 단위가 됨
