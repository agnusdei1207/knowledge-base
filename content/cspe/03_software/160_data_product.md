## 핵심 인사이트 (3줄 요약)
- 과거 IT 부서가 가공해서 던져주던 엑셀 파일이나 낡은 DB 테이블을 벗어나, 데이터를 **사용자가 즉시 구매(활용)할 수 있도록 품질, 보안, 설명서가 완벽하게 포장된 '소프트웨어 상품'**으로 취급하는 철학.
- 단순히 "데이터를 제공한다"가 아니라, 앱스토어의 앱처럼 검색 가능하고(Discoverable), 믿을 수 있고(Trustworthy), 주인이 명확하며(Ownership), 스스로 가치를 증명해야 하는 완성된 자산임.
- '데이터 메시(Data Mesh)' 아키텍처를 구성하는 가장 핵심적인 논리적/기술적 단위(Node)이자, 데이터 민주화와 사내 데이터 거래소(Marketplace)를 현실화하는 궁극의 비즈니스 유닛임.
---
## Ⅰ. 개요 및 필요성
- **개요**: 특정 비즈니스 도메인의 요구를 충족시키기 위해 코드, 데이터, 메타데이터, 인프라를 하나의 독립된 패키지로 묶어 내부/외부 사용자에게 가치를 제공하는 독립적인 데이터 자산.
- **필요성**: 데이터 레이크에 `customer_log_2307_final`이라는 테이블이 있음. 분석가가 이걸 쓰려는데 1) 뜻을 모르겠고, 2) 누가 만들었는지 묻고 다녀야 하고, 3) 권한 신청에 2주가 걸림. "우리가 스마트폰 앱 다운받을 때 이런 고생을 하냐? 앱스토어처럼 설명서 딱 있고, 별점 있고, 다운로드(API/SQL) 누르면 즉시 작동하는 완벽한 '상품(Product)' 형태로 데이터를 배포하자!"라는 철학이 등장함.
---
## Ⅱ. 아키텍처 및 핵심 원리 (데이터 프로덕트의 3대 요소)
- **1. 코드 (Code)**:
  - 데이터만 있는 게 아님. 원본 데이터를 정제하고 변환하는 파이프라인 코드(SQL, Spark), 보안 접근 제어 코드, API 서빙 코드가 하나의 상품 안에 다 내장되어 있음.
- **2. 데이터 및 메타데이터 (Data & Metadata)**:
  - 제공되는 실제 데이터(테이블, 파일, 스트림)와, 그 데이터가 무엇인지 설명하는 완벽한 카탈로그(의미, 리니지, 품질 지표)가 반드시 동봉되어야 함.
- **3. 인프라 (Infrastructure)**:
  - 이 상품이 스스로 돌아갈 수 있는 컴퓨팅 자원(컨테이너, 스토리지 권한)을 독자적으로 가짐.
  - 이를 묶어서 **발견 가능하고(Discoverable), 접근 가능하며(Addressable), 신뢰할 수 있고(Trustworthy), 상호 운용 가능한(Interoperable)** 특성(D-A-T-I)을 만족시켜야 함.

```text
[ 일반 데이터 테이블 vs 데이터 프로덕트(상품)의 차이 ]

 🗑️ [ 일반 데이터 테이블 (창고의 원자재) ]
 - 이름: `tbl_usr_pay_raw_01`
 - 특징: 설명서 없음, 업데이트 언제 되는지 아무도 모름, 만든 개발자는 이미 퇴사.
 - 결과: 분석가가 쓰다가 엉터리 통계 내고 징계받음.

 🎁 [ 데이터 프로덕트 (앱스토어의 완성된 상품) ]
 - 이름: [ 💳 2023년 VIP 고객 결제 성향 분석 API ]
 - 오너(Owner): 마케팅팀 김팀장 (문의처 Slack 링크 연결)
 - 설명서: "이 데이터는 매일 오전 9시에 100% 갱신되며, SLA(가동률) 99%를 보장합니다."
 - 접근법: "SQL로 읽으시려면 이 주소(JDBC), REST API로 받으시려면 이 주소를 쓰세요."
 - 결과: 타 부서에서 쇼핑하듯 즉시 장바구니에 담아 바로 마케팅에 활용!
```

## Ⅲ. 비교 및 연결
| 구분 | 데이터 애즈 어 서비스 (DaaS) | 데이터 프로덕트 (Data Product) |
|---|---|---|
| **성격** | 데이터를 API 클라우드 형태로 제공하는 **비즈니스 모델/서비스** | 메타데이터, 코드, 데이터를 하나의 캡슐로 묶은 **아키텍처 단위** |
| **범위** | 주로 외부 고객에게 데이터를 파는 행위 | 사내 도메인 간의 공유와 **Data Mesh의 핵심 노드** |
| **비유** | 식당에서 배달시켜 먹는 **음식 서비스** | 전자레인지에 돌리면 바로 먹을 수 있는 완벽한 **밀키트(상품)** |
| **핵심 요소**| 클라우드 인프라, API 게이트웨이 | **SLA 보장, 소유권(Ownership), 데이터 계약(Contract)** |

## Ⅳ. 실무 적용 및 기술사 판단
- **데이터 프로덕트 오너(DPO)의 도입**: 소프트웨어를 만들 때 기획/책임지는 프로덕트 매니저(PM)가 있듯, 실무에서 데이터 프로덕트가 성공하려면 이 상품의 품질과 영업을 책임질 **Data Product Owner(DPO)** 직책이 필수임. "이 데이터 상품의 오류는 내가 책임지고, 타 부서가 쉽게 쓰게 홍보하겠다"는 비즈니스 마인드를 가진 오너가 없으면 그냥 예쁘게 포장된 쓰레기가 됨.
- **내부 데이터 마켓플레이스 (Data Marketplace) 구축**: 기술사는 전사 직원들이 데이터 프로덕트를 쉽게 사고팔 수 있는 사내 거래소(Marketplace) 플랫폼을 구축해야 함. 여기에는 별점 시스템, 넷플릭스 같은 추천 알고리즘("영업팀이 가장 많이 쓴 데이터 상품입니다"), 자동 권한 승인 워크플로우가 포함되어, 데이터 민주화의 놀이터 역할을 수행해야 함.
---
## Ⅴ. 기대효과 및 결론
- "데이터를 뽑아주세요"라는 수동적인 IT 헬프데스크 문화를 종식시키고, 각 도메인 부서가 스스로의 가치를 증명하기 위해 데이터를 매력적인 상품으로 빚어내는 능동적인 문화를 창조함.
- 탈중앙화된 데이터 메시(Data Mesh) 아키텍처를 현실에서 구동시키는 마이크로서비스의 궁극적 형태이자, 기업이 진정한 의미의 '데이터 주도 기업(Data-Driven Company)'으로 거듭나기 위한 최종 진화 형태임.

### 👶 어린이를 위한 3줄 비유 설명
1. 옛날엔 친구한테 "장난감 좀 빌려줘" 하면, 설명서도 없고 바퀴도 하나 빠진 더러운 장난감 상자를 대충 던져줬어요 (일반 데이터).
2. **데이터 프로덕트**는 마트에서 파는 '완벽한 레고 세트'예요!
3. 포장지에는 멋진 그림(설명서)이 있고, 안에는 부품(데이터)과 조립 도구(코드)가 완벽하게 들어있으며, 망가지면 언제든 환불해 주겠다는 보증서(데이터 계약)까지 들어있는 최고급 상품이랍니다!
