# 📖 【암기용】 개념 완전 이해

> 목적: 이 개념을 처음 보는 사람도 완벽히 이해하게 만든다. 시험 답안 양식이 아니라, 이해를 위한 친절한 설명이다.

## 한눈에
- **개요**: 다중 프로세서 스케줄링은 대칭형 멀티프로세싱(SMP) 환경에서 여러 CPU 코어에 실행 가능한 프로세스를 어떤 큐(Run Queue) 구조로 배치·이동시킬지를 결정하는 CPU 스케줄링의 확장 문제다. 큐를 시스템 전체에 1개 두는 SQMS(Single Queue Multiprocessor Scheduling)와 코어마다 별도로 두는 MQMS(Multi Queue Multiprocessor Scheduling)가 양대 설계다.
- **왜 필요한가**: 단일 코어에서는 "다음에 무엇을 실행할까"만 정하면 됐지만, 코어가 여러 개면 추가로 "어느 코어에서 실행할까"까지 정해야 한다. 이 선택이 코어 간 부하 분산(로드 밸런싱)과 CPU 캐시 재사용률(캐시 친화성)이라는 서로 상충하는 두 목표에 직접 영향을 준다.
- **핵심 직관**: 큐를 하나로 합치면(SQMS) 어떤 코어든 비면 즉시 일감을 가져가 부하는 고르게 분산되지만, 여러 코어가 큐 1개에 동시에 접근하려면 락(Lock)을 걸어야 해서 경합이 커지고 프로세스가 매번 다른 코어에서 실행되어 캐시가 매번 비워진다. 큐를 코어별로 쪼개면(MQMS) 락 경합은 사라지고 캐시 재사용률은 높아지지만, 특정 큐에만 일이 몰리는 부하 불균형이 생긴다.

## 핵심 용어 정리 (내부에 등장하는 것들)

| 용어 | 의미 | 비유 |
|:---|:---|:---|
| SMP(Symmetric Multiprocessing) | 여러 CPU 코어가 동일한 메모리·I/O를 대등하게 공유하는 다중 프로세서 구조 | 동일한 권한을 가진 여러 명의 계산원 |
| Run Queue | 실행 가능(Ready) 상태의 프로세스를 담아두는 스케줄링 대기열 | 번호표 대기열 |
| SQMS | 시스템 전체가 Run Queue 1개를 공유하고, 어느 코어든 이 큐에서 꺼내 실행 | 은행 번호표 기계 1대, 은행원 여러 명 |
| MQMS | 코어(또는 코어 그룹)마다 전용 Run Queue를 둠 | 계산대마다 별도의 줄 |
| 락 경합(Lock Contention) | 여러 코어가 동시에 같은 큐에 접근하려 할 때 상호배제 락을 얻으려고 대기하며 생기는 병목 | 문이 1개뿐인 방에 여러 명이 동시에 들어가려는 상황 |
| 캐시 친화성(Cache Affinity) | 프로세스가 이전에 실행됐던 코어의 L1/L2 캐시에 자신의 데이터가 남아있어 재실행 시 빨리 도는 성질 | 어제 앉았던 자리에 다시 앉으면 서랍 위치를 이미 아는 것 |
| 로드 밸런싱(Load Balancing) | 코어 간 대기 프로세스 수를 고르게 맞추는 것 | 줄 길이를 맞추는 것 |
| Work Stealing | 자신의 큐가 빈 코어가 다른 코어 큐의 끝에서 프로세스를 가져오는 부하 재분배 기법 | 내 일이 끝나면 옆 사람 일더미에서 몇 개를 가져와 돕는 것 |

## 깊이 이해

### 왜 두 목표가 충돌하는가 — 구체 시나리오
코어 4개, 프로세스 A가 방금 코어 0에서 실행되어 L1 캐시(보통 32~64KB)에 A의 작업 데이터가 올라와 있다고 하자. 로드 밸런싱만 최적화하면 다음 실행 시 A를 가장 한가한 코어(예: 코어 2)에 배정할 수 있는데, 그러면 코어 2의 L1 캐시는 비어 있어 A는 코어 캐시보다 훨씬 느린 메인 메모리(DRAM)에서 데이터를 다시 읽어야 한다. 반대로 캐시 친화성만 최적화해 A를 항상 코어 0에만 배정하면, 코어 0에 대기열이 쌓여도 다른 코어는 노는 상황을 그대로 방치하게 된다.

### SQMS의 구조와 한계 — 락 경합
SQMS는 전역 Run Queue 1개를 코어 N개가 공유한다. 코어가 4개 수준이면 큐 접근 시 락 경합이 상대적으로 크지 않지만, 코어가 수십 개인 서버에서는 여러 코어가 동시에 스케줄링 결정을 내리려 하므로 락 대기가 누적되어 스케줄링 자체가 병목이 된다. SQMS는 소규모 SMP(코어 수 개 수준)에서는 구현이 단순하고 로드 밸런싱이 완벽하다는 장점이 있지만, 코어 수가 늘어날수록 확장성(Scalability)이 급격히 나빠진다.

### MQMS의 구조와 Work Stealing 동작
MQMS는 코어마다 Run Queue를 두어 락 경합을 코어별로 분리한다. 프로세스는 생성 시 배정된 큐에 남아 캐시 히트율이 높게 유지된다. 문제는 코어 0의 큐에 프로세스가 쌓이고 코어 1의 큐가 비어 있는 상황이 그대로 방치되면 코어 1이 유휴 상태로 낭비된다는 것이다. Work Stealing은 코어 1이 자신의 큐가 비면 다른 코어의 큐(보통 큐의 꼬리, tail)를 스캔해 프로세스를 몇 개 가져와 실행하는 방식으로 이를 보정한다. 예를 들어 리눅스 CFS(Completely Fair Scheduler)는 `sched_domain` 계층을 두고 일정 주기(스케줄링 틱 단위)마다 코어 간 부하 차이를 검사해, 불균형이 임계치를 넘으면 유휴 상태인 코어가 다른 큐에서 작업을 훔쳐온다.

### 확장 — NUMA와 SMT 환경에서의 추가 고려
코어 수가 수십 개로 늘고 메모리 접근 지연이 코어 위치에 따라 달라지는 NUMA(Non-Uniform Memory Access) 환경에서는, Work Stealing이 먼 NUMA 노드의 큐에서 작업을 가져오면 캐시뿐 아니라 메모리 접근 지연까지 함께 커진다. 그래서 현대 스케줄러는 우선 같은 NUMA 노드 안에서만 훔치도록 제약을 둔다(031 참고). 하이퍼스레딩(SMT)으로 물리 코어 1개가 논리 코어 2개로 보이는 환경에서는, 무거운 연산 2개를 같은 물리 코어의 논리 코어 2개에 배정하면 실행 자원(파이프라인, 연산 유닛)을 두 스레드가 나눠 써서 성능이 떨어지므로, 스케줄러는 완전히 빈 물리 코어를 우선 배정한다.

## 연결 개념
- Run Queue / Ready Queue — 단일 코어 스케줄링에서 확장된 자료구조. 멀티코어에서는 이를 전역으로 둘지 코어별로 둘지가 SQMS·MQMS를 가른다.
- NUMA-aware 스케줄링(031) — MQMS의 Work Stealing이 노드 경계까지 고려하도록 확장된 것.
- 리눅스 CFS(Completely Fair Scheduler) — 코어별 Run Queue와 `sched_domain` 기반 로드 밸런싱을 실제로 구현한 스케줄러.

## Ⅰ. 개요 및 필요성

- 정의: SMP(Symmetric Multiprocessing) 시스템에서 다수의 CPU 코어에 프로세스를 할당하기 위해 큐(Queue)를 설계하고 스케줄링 정책을 결정하는 커널 서브시스템
- 배경: 싱글 코어 시대의 스케줄러를 멀티 코어에 그대로 이식할 경우, 코어 간 L1/L2 캐시 미스(Cache Miss)가 폭발하고 글로벌 락 경합으로 전체 성능이 붕괴
- 필요성: 동기화 락(Lock) 병목을 최소화(확장성 보장)하면서도, 캐시 웜업(Warm-up) 상태를 유지하여 Throughput을 높이고 코어 간 부하를 균등 제어하기 위함

## Ⅱ. 2대 목표의 딜레마와 아키텍처 구조 (SQMS vs MQMS)

```text
[ SQMS (단일 큐) ] -> 로드 밸런싱 완벽, 캐시 깨짐
(CPU 1) <--+-- [ Global Runqueue (Lock 🚨) ] --+--> (CPU 3)
(CPU 2) <--+             P1, P2, P3            +--> (CPU 4)
* 한계: 코어 4개가 큐에 접근할 때마다 뮤텍스 락 걸림. 병목 지옥.

[ MQMS (다중 큐) ] -> 캐시 보존 완벽, 로드 언밸런스 발생
(CPU 1) <--- [ Queue 1 : P1, P2 ] (바쁨 💦)
(CPU 2) <--- [ Queue 2 : (비어있음) ] (놀고 있음 💤)
* 한계: P1은 무조건 CPU 1만 타므로 캐시는 완벽하지만, CPU 2가 노는 기아(Starvation) 발생.
```

| 비교 축 | SQMS (Single Queue MS) | MQMS (Multi Queue MS) |
|:---|:---|:---|
| **큐(Queue) 구조** | 전체 시스템 1개의 Global Queue | CPU 코어 개수만큼의 Local Queue |
| **캐시 친화성 (Affinity)** | **최악** (매번 다른 코어에 할당되어 L1/L2 플러시) | **최고** (태어난 코어에서 평생 실행되어 캐시 히트) |
| **동기화 오버헤드** | **최악** (모든 코어가 1개의 큐를 두고 Lock 경합) | **제로(0)** (자기 큐만 보므로 Lock 불필요) |
| **부하 분산 (Load Balance)** | **완벽** (빈 코어가 즉시 남은 일 가져감) | **불균형** (특정 큐에만 일이 몰릴 수 있음) |

> 요약: 큐 1개(SQMS)는 화장실 한 줄 서기다. 공평하지만 문 열 때마다 병목이다. 큐 여러 개(MQMS)는 각자 줄 서기다. 빠르지만 내 줄이 안 줄어들면 억울해 미친다. 현대 OS는 MQMS를 베이스로 삼는다.

## Ⅲ. MQMS의 치명적 한계 돌파: Work Stealing (작업 탈취)

MQMS에서 "한 놈은 과로사, 한 놈은 꿀빠는" 상황을 해결하는 현대 커널의 표준 메커니즘.

| 로드 밸런싱 기법 | 동작 원리 메커니즘 및 튜닝 포인트 | 아키텍처적 가치 |
|:---|:---|:---|
| **Work Stealing (훔치기)** | 자신의 큐가 텅 비어 노는 코어(CPU 2)가, 큐가 미어터지는 다른 코어(CPU 1)를 스캔하여 꼬리에 있는 프로세스를 훔쳐 옴 | 캐시 친화성을 조금 희생하더라도, 코어 유휴(Idle)를 막아 전체 CPU 활용률 100% 달성 |
| **Migration (마이그레이션)** | OS 커널 데몬이 백그라운드에서 주기적으로 전체 큐 길이를 스캔하여, 밸런스가 무너지면 강제로 프로세스를 이주(Push/Pull) 시킴 | 특정 프로세스의 캐시를 강제로 식히는(Cold) 부작용이 있으므로, 임계치 초과 시에만 매우 보수적으로 동작 |

> 요약: 훔쳐 오기(Work Stealing)는 멀티 코어 운영체제의 예술이다. 평소엔 각자 줄을 서서 캐시 효율을 극대화하다가, 너무 심각하게 불균형해지면 그때만 예외적으로 훔쳐 와서 밸런스를 맞춘다.

## Ⅳ. 최신 하드웨어 구조에 따른 스케줄링 리스크 및 튜닝

SMP를 넘어 코어 수십 개가 메모리를 공유하는 NUMA(Non-Uniform Memory Access) 시대로 진입하며 캐시 친화성 개념이 확장되었다.

| 리스크 요인 | 발생 시나리오 및 성능 붕괴 원인 | 커널 대응 방안 (실무 적용) |
|:---|:---|:---|
| **NUMA 노드 간 마이그레이션 참사** | 코어 64개짜리 서버(NUMA)에서, Work Stealing이 발생해 CPU 1(Node 0)에서 놀던 프로세스를 저 멀리 있는 CPU 32(Node 1)가 훔쳐 감. 프로세스는 자기 메모리를 읽기 위해 CPU 간 QPI 버스를 건너가야 하므로 지연(Latency) 3배 폭발 | **NUMA-Aware 스케줄러 적용**: 훔쳐오기(Stealing)를 하더라도 가급적 같은 NUMA 노드(근처 코어) 안에서만 훔치도록 패널티를 부여하는 리눅스 `sched_domain` 토폴로지 적용 |
| **하이퍼스레딩(SMT) 충돌** | 1개의 물리 코어에 2개의 논리 코어(가상 스레드)가 묶인 하이퍼스레딩 환경에서, 무거운 연산 2개가 같은 물리 코어의 가상 스레드 2개에 동시 할당되어 파이프라인 자원 경합 폭주 | **SMT 인지 스케줄링**: 스케줄러가 코어 간 물리적 쌍을 인지하고, 한 물리 코어에 작업이 있으면 일단 완전히 빈 다른 물리 코어부터 우선 배정 |

> 요약: 이제는 훔치는 것도 머리를 써야 한다. 서울 지사 일이 밀린다고 부산 지사 직원을 데려오면(NUMA 노드 이동) 비행기 값이 더 든다. 바로 옆 팀(동일 L3 캐시 공유) 직원을 데려와야 한다.

## Ⅴ. 실무 적용 방안 및 결론

**적용 방안 3개:**
1. [실시간(RT) 애플리케이션 CPU 격리] 증권사 HTS 주문 처리 틱 서버와 같은 극단적 지연 민감 워크로드 구축 시, 리눅스 부팅 파라미터에 `isolcpus=2,3`을 주어 커널 스케줄러(MQMS)가 해당 코어에 일반 프로세스를 배정하지 못하게 원천 차단하고 `taskset`으로 주문 프로세스만 전용 할당
2. [캐시 웜업(Warm-up) 사수를 위한 핀셋 고정] In-memory DB(Redis) 기동 시 잦은 Work Stealing으로 인한 L1 캐시 플러시 오버헤드를 막기 위해, `numactl --cpubind=0` 명령을 통해 특정 물리 코어와 NUMA 메모리 노드에 프로세스를 강제 고정(Pinning)하여 캐시 히트율 99% 사수
3. [Go 언어 런타임 스케줄러 적용] 쿠버네티스(K8s) 개발 시, Go 언어의 Goroutine 스케줄러가 OS의 MQMS와 Work Stealing 철학을 유저 레벨 런타임에 100% 모방 구현한 P(Processor)-M(Machine)-G(Goroutine) 아키텍처임을 이해하고 락-프리 병렬 프로그래밍 설계에 차용

**결론:**
- 기술사 판단: 다중 프로세서 스케줄링은 "공정성(로드 밸런싱)"과 "기득권(캐시 친화성)"의 철학적 충돌이다. 현대 운영체제는 SQMS의 공평함을 버리고 MQMS의 극단적 성능(Lock-free)을 취하되, Work Stealing이라는 보완재를 통해 이 거대한 모순을 아름답게 봉합했다.
- 향후 방향: 무어의 법칙이 끝나고 암(ARM) 기반의 big.LITTLE 아키텍처(성능 코어 + 효율 코어 혼합)가 데스크톱과 서버(AWS Graviton)를 지배하면서, 이제 스케줄러는 단순히 짐을 나누는 것을 넘어 "이 연산은 배터리를 아끼기 위해 E코어로, 저 연산은 속도를 위해 P코어로" 찢어 보내는 EAS(Energy Aware Scheduling)의 시대로 진화하고 있다.
