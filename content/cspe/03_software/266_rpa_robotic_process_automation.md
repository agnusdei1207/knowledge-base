# 📖 【암기용】 개념 완전 이해

> 목적: RPA를 처음 봐도 이해하게 만든다. 시험 답안 양식이 아니라, 이해를 위한 설명이다.

## 한눈에
- **개요**: RPA(Robotic Process Automation)는 사람이 화면에서 반복 수행하는 **업무 프로세스**를 소프트웨어 **봇(Bot)**이 사람과 동일한 방식으로 대신 조작하게 만드는 자동화 기술이다.
- **왜 필요한가**: 레거시 시스템은 API가 없는 경우가 많고, 담당자는 조회·복사·붙여넣기·엑셀 정리 같은 규칙적인 반복 작업에 시간을 쓴다. RPA는 시스템 내부를 바꾸지 않고 화면(UI) 수준에서 자동화를 얹는다.
- **핵심 직관**: 신입 직원에게 매뉴얼을 주고 같은 화면 조작을 반복시키는 일을, 소프트웨어 봇이 지치지 않고 대신하는 구조다.

## 핵심 용어 정리 (내부에 등장하는 것들)

| 용어 | 의미 | 비유 |
|:---|:---|:---|
| 업무 프로세스 자동화(Process Automation) | 사람이 정해진 규칙에 따라 반복하는 업무 절차를 기계가 대신 수행하게 만드는 것 — RPA가 속한 **상위 개념** | 컨베이어 벨트가 사람 손동작을 대신함 |
| 봇(Bot) | 화면 요소를 인식하고 클릭·입력·복사를 순서대로 실행하는 소프트웨어 에이전트 | 매뉴얼대로 움직이는 신입 직원 |
| 셀렉터(Selector) | 봇이 화면의 어떤 버튼·입력창을 조작할지 식별하는 규칙(좌표, ID, 이미지 등) | 사람이 "저 파란 버튼"을 알아보는 방식 |
| Orchestrator | 여러 봇의 배포, 스케줄, 실행 큐, 상태를 중앙에서 관리하는 관제 시스템 | 콜센터 전체를 관리하는 상황실 |
| Credential Vault | 봇이 로그인에 쓰는 계정·비밀번호를 안전하게 보관하는 금고형 저장소 | 마스터키 보관함 |
| Attended / Unattended Bot | 사람 PC에서 사람과 함께 실행되는 봇 / 서버에서 사람 없이 스스로 실행되는 봇 | 옆에서 돕는 비서 / 야간 무인 당직자 |
| 예외 큐(Exception Queue) | 봇이 처리하지 못한 실패 건을 모아 담당자가 확인하도록 넘기는 대기열 | 자동화 창구에서 처리 못 한 민원을 사람 창구로 넘김 |
| IPA(Intelligent Process Automation) | RPA에 OCR·NLP·AI 판단을 결합해 비정형 데이터까지 처리하도록 확장한 것 | 매뉴얼대로만 하던 직원이 판단력까지 갖춘 것 |

## 깊이 이해

### 왜 필요했나 — API가 없는 환경에서의 현실적 대안
- 시스템 통합의 정석은 API 연계지만, 레거시 시스템은 API를 아예 제공하지 않거나 API 개발에 수개월이 걸린다. 이 경우 사람이 하던 "화면 클릭"을 그대로 흉내 내는 것이 가장 빠른 자동화 경로가 된다.
- RPA 프로젝트는 API 통합보다 구축 기간이 짧다(예: API 통합 프로젝트 3개월 대비 봇 구축 2~6주). 대신 시스템 내부 로직에 접근하지 못하므로 화면이 바뀌면 그대로 영향을 받는다.

### 작동 원리 — 인식부터 예외 처리까지
- 봇은 셀렉터로 화면 요소(로그인 창, 조회 버튼, 표 셀)를 인식한다.
- Credential Vault에서 계정 정보를 받아 로그인하고, 정해진 순서대로 조회·입력·다운로드·업로드를 수행한다.
- Orchestrator가 스케줄에 따라 봇을 실행시키고 실행 상태를 기록한다.
- 처리 중 오류(팝업, 화면 미인식, 데이터 형식 오류)가 나면 예외 큐로 넘기고, 담당자가 사유를 확인해 재처리하거나 개선한다.

### 구체 수치로 보는 적용 대상 판별
- 월 처리 건수 1,000건 이상, 규칙이 명확해 예외율이 10% 이하인 업무가 RPA 적용 후보로 흔히 제시된다. 예외율이 이보다 높으면 봇이 처리 못 하는 건이 너무 많아 사람이 예외 큐만 붙잡고 있게 된다.
- 예: 매일 09시 ERP 매출 파일을 내려받아 엑셀로 검증한 뒤 회계 시스템에 업로드하는 작업이 사람 손으로는 30분 걸리던 것을, 봇이 5분 이내로 처리하고 실패 시에만 담당자에게 티켓을 넘긴다. 성공률 목표는 통상 98% 이상이다.
- UI가 자주 바뀌는 업무(월 1회 넘게 화면 개편)는 셀렉터가 매번 깨지므로 RPA 적용 후보에서 제외하거나 API 전환을 우선 검토한다.

### 판별 원리 — 언제 RPA, 언제 API 통합인가
- 반복성·규칙성이 높고 API가 없으며 단기간에 자동화가 필요하면 RPA가 적합하다.
- 처리량이 아주 크거나(대량 배치), 핵심 거래처럼 안정성이 최우선이거나, 장기적으로 유지할 시스템이면 API 통합이나 BPM 재설계가 낫다 — 화면 기반 자동화는 근본적인 시스템 통합의 대체재가 아니라 과도기적 해법이기 때문이다.

### 비유와 흔한 오해
- **비유**: 엘리베이터 버튼을 사람이 누르던 절차를, 자동 버튼 장치가 정해진 순서대로 대신 누르는 것과 같다. 건물 배선(시스템 내부)은 그대로 두고 조작 방식만 자동화한다.
- **오해**: RPA는 매크로와 다르다. 매크로는 정해진 좌표·순서만 재생하지만, RPA는 Orchestrator를 통한 중앙 관리, 예외 처리, 감사 로그, 권한 통제까지 포함하는 운영 체계다. 계정을 여러 봇이 공유하면 감사 추적이 불가능해지므로 봇 전용 계정과 Credential Vault가 필수다.

## 연결 개념
- BPM - 업무 프로세스 모델링과 개선 (RPA가 자동화하는 프로세스를 설계하는 상위 활동)
- IPA - RPA에 OCR, NLP, AI 의사결정을 결합 (RPA의 확장형)
- API Integration - 장기적으로 화면 자동화를 대체할 연계 방식 (RPA의 대안이자 전환 목표)

# 📝 【답안용】 시험 답안 템플릿

> 목적: 시험장에서 25분에 그대로 쓰는 답안 양식. 작성방식(추상표현 금지·수치·도식·문제유형 전환)을 엄격히 지킨다.
> 핵심: RPA는 단순 자동 클릭이 아니라 대상 업무 선정, 봇 운영, 권한 통제, 예외 처리 기준이 포함된 업무 자동화 체계이다.

## 핵심 인사이트 (3줄 요약)

> 1. **본질**: RPA는 사람의 반복 화면 조작과 규칙 기반 업무를 소프트웨어 봇으로 수행하는 프로세스 자동화 기술이다.
> 2. **가치**: 월 1,000건 이상 반복 업무에서 처리 시간, 오류율, 감사 로그를 수치로 관리할 수 있다.
> 3. **판단 포인트**: 규칙성, 예외율, UI 변경 빈도, 권한 통제, API 전환 가능성을 기준으로 대상 업무를 선별한다.

## Ⅰ. 개요 및 필요성

- 개요: RPA는 반복 업무를 소프트웨어 봇으로 자동화하는 기술이다.
- 배경: 레거시 시스템, API 부재, 엑셀·웹 포털 혼재 환경에서는 화면 기반 자동화가 단기 통합 수단이 될 수 있다.
- 필요성: 대상 업무, 예외 처리, 계정 권한, 실행 로그 기준을 정해 봇 장애와 감사 리스크를 통제해야 한다.

---

## Ⅱ. 구조 및 구성요소

```text
업무 규칙 -> Bot Script -> Orchestrator/Scheduler -> Target System
          -> Credential Vault -> Log/Exception Queue -> Operator Review
```

| 구성요소 | 역할 | 특이사항 |
|:---|:---|:---|
| 봇 스크립트 | 화면 조작, 입력, 조회, 파일 처리 수행 | UI 변경 영향 큼 |
| Orchestrator | 배포, 스케줄, 큐, 실행 상태 관리 | 중앙 운영 필수 |
| Credential Vault | 계정·비밀번호 보관 | 계정 공유 금지 |
| 예외 큐 | 실패 건 분류와 담당자 처리 | SLA와 재처리 기준 필요 |

> 요약: RPA는 봇 실행보다 Orchestrator, 자격증명, 예외 큐가 운영 품질을 좌우한다.

## Ⅲ. 동작원리 및 흐름도

```text
업무 선정 -> 프로세스 기록 -> 봇 개발/테스트 -> 스케줄 실행
-> 결과 검증 -> 예외 큐 등록 -> 로그 감사
```

| 단계 | 처리 내용 | 검증 기준 |
|:---:|:---|:---|
| 1 | 자동화 후보 선정 | 월 처리 1,000건, 예외율 10% 이하 |
| 2 | 봇 개발과 테스트 | 테스트 케이스 30건 이상 |
| 3 | 운영 실행 | 성공률 98% 이상, 재시도 3회 제한 |
| 4 | 예외·감사 | 실패 사유 코드화, 로그 1년 보관 |

> 요약: RPA는 업무 선정부터 예외 처리까지 폐쇄 루프로 운영해야 한다.

## Ⅵ. 실무 적용 및 결론

**적용 방안 3개 (필수 - 단계별 또는 항목별):**
1. 후보 선정: 반복성 높고 예외율 10% 이하이며 월 1,000건 이상 처리되는 업무를 우선 선정
2. 운영 통제: Bot 전용 계정, Credential Vault, Orchestrator 로그, 권한 분리 기준 적용
3. 전환 관리: UI 변경 잦은 업무와 핵심 거래 업무는 API 통합 전환 후보로 등록하고 분기별 재평가

**결론 (2줄):**
- 기술사 판단: 단기 반복 업무는 RPA, 장기 핵심 프로세스는 API·BPM 기반 통합으로 전환함
- 향후 방향: RPA는 OCR, NLP, LLM 기반 예외 분류와 결합해 지능형 프로세스 자동화로 확장됨
