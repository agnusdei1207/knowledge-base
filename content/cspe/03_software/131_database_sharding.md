## Ⅰ. 개요
- **정의**: 하나의 테이블을 키 기준으로 여러 독립 DB 인스턴스에 수평 분할하여 저장하는 기법
- **배경/필요성**: 단일 DB의 저장·처리 용량 한계를 넘는 대규모 데이터 처리 시 수평 확장이 필요함
- **비유**: 도서관 한 곳에 책이 넘치면 지역별 분관을 두어 분산 보관하는 것과 유사함

| 출제 의도 | 반드시 짚을 핵심 | 감점 회피 포인트 |
|:---|:---|:---|
| 수평 분할 전략 설계 능력 | 샤드 키 선정 기준과 리밸런싱 | 파티셔닝과 샤딩의 차이 명확히 구분 필요 |

> 요약: 샤드 키 기반 수평 분할로 DB 수평 확장성을 확보하는 기법임

## Ⅱ. 구성요소
```text
Client --> Router --> | Shard-1 (key: 0~99)  |
                      | Shard-2 (key: 100~199)|
                      | Shard-3 (key: 200~299)|
```

| 구성요소 | 설명 | 비유 |
|:---|:---|:---|
| Shard Key | 데이터 분배 기준이 되는 컬럼 | 도서 분류 번호 |
| Router | 샤드 키로 대상 샤드를 결정하는 라우팅 계층 | 안내 데스크 |
| Shard | 데이터 부분집합을 보관하는 독립 DB 인스턴스 | 지역 분관 |
| Config Server | 샤드 매핑 메타데이터 관리 저장소 | 분관 위치 목록 |

> 요약: 라우터가 샤드 키 기반으로 요청을 적절한 샤드 인스턴스로 분배하는 구조임

## Ⅲ. 절차
```text
샤드 키 선정 --> 분할 전략 결정 --> 데이터 마이그레이션 --> 라우팅 적용
```
- 1단계: 카디널리티·쿼리 패턴 분석하여 샤드 키 선정
- 2단계: 해시/범위/디렉터리 중 분할 전략 결정
- 3단계: 기존 데이터를 샤드별로 마이그레이션 수행
- 4단계: 라우팅 계층 구성 후 애플리케이션에 적용

> 요약: 키 선정부터 라우팅 적용까지 4단계로 샤딩을 구축함

## Ⅳ. 문제점
- 크로스 샤드 조인: 분산된 샤드 간 JOIN 시 네트워크 비용 증가 — 응답 지연 발생함
- 핫스팟 편중: 샤드 키 분포 불균형 시 특정 샤드에 부하 집중 — 확장 효과 감소함
- 리밸런싱 복잡성: 샤드 추가·제거 시 데이터 재분배 과정이 운영 중단 위험을 수반함

> 요약: 조인 제약, 핫스팟, 리밸런싱이 샤딩의 주요 운영 과제임

## Ⅴ. 개선방안
1. 단기: 크로스 샤드 조인 → 비정규화·로컬 복제 테이블로 샤드 내 조인 유도
2. 중기: 핫스팟 편중 → Consistent Hashing 도입으로 균등 분배 보장
3. 장기: 리밸런싱 복잡성 → 자동 리샤딩 기능 내재된 분산 DB(Vitess 등) 도입

> 요약: 비정규화, 해시 개선, 자동 리샤딩으로 샤딩 과제를 단계적 해소함

## Ⅵ. 전망
- 발전 방향: 클라우드 네이티브 DB에서 자동 샤딩이 기본 기능으로 내재화되는 추세임
- 기술사적 판단: 데이터 규모 증가에 따라 샤딩 설계 역량은 아키텍트 핵심 역량임
- 기술사 제언: 샤드 키 선정 시 비즈니스 쿼리 패턴과 데이터 성장률을 함께 고려할 것을 제언함
