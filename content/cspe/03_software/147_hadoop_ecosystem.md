## Ⅰ. 개요
- **정의**: HDFS·MapReduce·YARN을 핵심으로, 대규모 데이터의 분산 저장·처리를 지원하는 오픈소스 프레임워크 집합임
- **배경/필요성**: 단일 서버로 처리 불가능한 페타바이트급 데이터를 범용 하드웨어에서 처리할 수단이 필요함
- **비유**: 여러 창고(노드)에 물건을 나눠 보관하고, 각 창고 직원이 현장에서 검수(로컬 처리)하는 물류 시스템임

| 출제 의도 | 반드시 짚을 핵심 | 감점 회피 포인트 |
|:---|:---|:---|
| 빅데이터 플랫폼 전체 구조 이해 | HDFS·YARN·MapReduce 역할 구분 | Hadoop = MapReduce로 한정하지 않음 |

> 요약: 분산 저장(HDFS)과 자원 관리(YARN) 위에 다양한 처리 엔진이 결합된 생태계임

## Ⅱ. 구성요소
```text
[Hive/Pig/Spark] ---> [YARN] ---> [MapReduce/Tez/Spark Engine]
                                        |
                                     [HDFS]
                                        |
                                  [NameNode + DataNode]
```

| 구성요소 | 설명 | 비유 |
|:---|:---|:---|
| HDFS | 대용량 파일을 블록 단위로 분산 저장하는 파일 시스템 | 분산 창고 |
| YARN | 클러스터 자원(CPU·메모리)을 애플리케이션에 할당하는 자원 관리자 | 물류 센터 배차 담당 |
| MapReduce | Map(분할 처리)과 Reduce(결합)로 데이터를 일괄 처리하는 엔진 | 각 창고 검수 후 본사 집계 |
| Hive | SQL 인터페이스로 HDFS 데이터를 조회하는 데이터 웨어하우스 도구 | 창고 조회 터미널 |

> 요약: HDFS-YARN-처리엔진-SQL 도구가 Hadoop 생태계의 계층 구조를 형성함

## Ⅲ. 절차
```text
클러스터구축 --> 데이터적재 --> 처리/분석 --> 결과활용
```
- 1단계: 클러스터구축 — NameNode·DataNode 배치, YARN 자원 풀 설정
- 2단계: 데이터적재 — Sqoop·Flume·NiFi 등으로 소스 데이터를 HDFS에 수집
- 3단계: 처리/분석 — Hive SQL, Spark Job(146 참조), MapReduce로 변환·집계 수행
- 4단계: 결과활용 — BI 도구 연동, 데이터 마트 생성, ML 피처스토어 적재

> 요약: 구축-적재-처리-활용 순서로 빅데이터 파이프라인을 운영함

## Ⅳ. 문제점
- HDFS 소규모 파일: 다수의 작은 파일이 NameNode 메모리를 과다 점유 — 메타데이터 병목 발생
- MapReduce 디스크 I/O: 매 단계마다 중간 결과를 디스크에 기록 — 반복 연산에서 지연 큼
- 클러스터 운영 부담: 수십~수백 노드의 하드웨어·네트워크·장애 관리에 전문 인력 필요 — 비용 증가

> 요약: 소규모 파일, 디스크 I/O, 운영 복잡도가 Hadoop의 주요 과제임

## Ⅴ. 개선방안
1. 단기: HAR 아카이브·파일 병합 Job 적용으로 소규모 파일 문제 완화
2. 중기: Spark·Tez 등 인메모리 엔진으로 MapReduce 워크로드 전환하여 I/O 절감
3. 장기: 클라우드 기반 관리형 서비스(EMR, Dataproc) 전환 또는 오브젝트 스토리지 분리로 운영 부담 경감

> 요약: 파일 병합·인메모리 전환·클라우드 이관으로 단계적으로 개선함

## Ⅵ. 전망
- 발전 방향: 온프레미스 Hadoop 클러스터는 클라우드 데이터 레이크로 점진 이관되는 추세임
- 기술사적 판단: HDFS의 저장 역할은 오브젝트 스토리지(S3, GCS)로 대체되나, YARN·Hive 등 생태계 도구는 지속 활용됨
- 기술사 제언: 신규 구축 시 Hadoop 자체보다 클라우드 네이티브 레이크하우스 아키텍처 우선 검토 필요
