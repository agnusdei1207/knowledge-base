## 핵심 인사이트 (3줄 요약)
- 디스크가 아닌 **RAM(메모리)에 데이터를 저장하여 0.001초(밀리초) 이하의 경이로운 읽기/쓰기 속도를 자랑하는 전 세계 1위의 인메모리 Key-Value 데이터 저장소**.
- 단순한 String(문자열)뿐만 아니라 List(대기열), Set(교집합), Sorted Set(실시간 랭킹표) 등 **다양한 '자료구조(Data Structure)'를 메모리 위에서 자체 지원**하여 개발자의 로직을 획기적으로 줄여줌.
- 싱글 쓰레드(Single-Thread) 기반이므로 복잡한 명령어나 O(N) 쿼리를 날리면 시스템 전체가 정지하는 재앙이 발생하며, 휘발성 메모리의 특성상 AOF/RDB 백업 전략이 필수적임.
---
## Ⅰ. 개요 및 필요성
- **개요**: Remote Dictionary Server의 약자로, 메모리 기반의 고성능 키-값 저장소이자 데이터 구조 서버.
- **필요성**: RDBMS 앞단에 방파제(캐시)를 세우기 위해 Memcached를 썼지만, 단순한 String만 저장 가능했음. "실시간 게임 랭킹표를 디스크에 안 쓰고 메모리상에서 순서대로 관리할 수 없을까?", "대기열(Queue)을 메모리에서 바로 빼 쓸 순 없을까?"라는 요구사항을 해결하기 위해 다기능 인메모리 스위스 아미 나이프가 필요했음.
---
## Ⅱ. 아키텍처 및 핵심 원리
- **메모리(RAM)의 한계와 지속성(Persistence) 극복**:
  - 메모리는 전원이 나가면 데이터가 증발함. Redis는 이를 막기 위해 2가지 디스크 백업을 지원함.
  1. **RDB (Redis Database Snapshot)**: 특정 시간(예: 1시간마다) 메모리 전체 상태를 사진 찍듯 디스크에 덤프 뜸 (백업용).
  2. **AOF (Append Only File)**: 데이터가 변경되는 모든 명령어(Log)를 디스크 파일에 초 단위로 계속 이어붙임 (복구용).
- **싱글 쓰레드 (Single-Thread) 아키텍처**:
  - 메인 작업(명령어 처리)을 단 1개의 쓰레드로 순차 처리함. (Context Switching 오버헤드가 없고 원자성(Atomic)이 보장되어 동시성 에러가 안 남).
- **강력한 자료구조 컬렉션**:
  - `String`: 단순 텍스트, 숫자 캐싱 (세션 유지).
  - `List`: 양방향 큐(Queue/Stack) 구현 (알림 피드).
  - `Set`: 중복 없는 집합 연산 (오늘 방문한 고유 IP 수).
  - **`Sorted Set (ZSet)`**: Score(점수)에 따라 실시간 자동 정렬 (게임 랭킹, 실시간 검색어 1~10위).

```text
[ Redis 싱글 쓰레드의 위력과 위험성 ]

 ✅ [ 완벽한 원자성 보장 (장점) ]
 수만 명이 동시에 "조회수 1 증가시켜!"(INCR 명령어)라고 요청해도,
 Redis는 1개의 쓰레드(창구 직원)가 1명씩 처리하므로 
 데이터 충돌(Race Condition) 없이 완벽하게 조회수가 올라감!

 🚨 [ O(N) 명령어의 재앙 (단점) ]
 초보 개발자가 전체 키를 보려고 `KEYS *` (1,000만 개 뒤지기)를 날림.
 ➡️ 1명뿐인 창구 직원이 창고를 10초 동안 뒤지러 감.
 ➡️ 뒤에 줄 서 있던 다른 웹서버들의 정상적인 캐시 요청(수만 건)이 전부 타임아웃 남!
 ➡️ (서비스 전체 다운!) ➡️ 실무에서는 절대 금지명령어임.
```

## Ⅲ. 비교 및 연결
| 구분 | Memcached | Redis |
|---|---|---|
| **저장 타입** | 단순 문자열 (String) | **String, List, Set, Hash, Sorted Set 등** |
| **데이터 영속성**| 미지원 (재부팅 시 100% 날아감) | **RDB 스냅샷, AOF 지원 (디스크 저장 가능)** |
| **확장 아키텍처**| 클라이언트 단에서 분산 (Consistent Hash) | **Redis Cluster 자체 지원 (HA, Sharding)** |
| **쓰레드 모델** | 멀티 쓰레드 (CPU 전부 활용) | **싱글 쓰레드 (원자성 강력 보장)** |
---
## Ⅳ. 실무 적용 및 기술사 판단
- **Redis를 활용한 분산 락(Distributed Lock)**: 쿠폰 발급 시스템(선착순 100명) 등 MSA 환경에서 여러 서버가 동시에 재고를 차감할 때 락이 필요함. 이때 디스크 DB에 락을 걸면 느려서 터짐. 실무 아키텍트는 Redis의 싱글 쓰레드 특성과 `SETNX`(없을 때만 세팅해라) 명령어를 활용하여, 메모리상에서 빛의 속도로 락을 잡고 푸는 Redisson(자바 라이브러리) 기반의 분산 락 아키텍처를 설계해야 함.
- **메모리 파편화와 만료(Eviction) 정책**: Redis 메모리가 가득 차면 OOM(Out of Memory)으로 죽어버림. 반드시 `maxmemory` 옵션을 설정하고, 꽉 찼을 때 덜 쓰인 데이터부터 지우는 `volatile-lru` 또는 `allkeys-lru` 퇴출(Eviction) 알고리즘을 튜닝하는 것이 백엔드 엔지니어의 필수 덕목임.
---
## Ⅴ. 기대효과 및 결론
- 단순히 데이터베이스 앞단에서 부하를 막아주는 멍청한 캐시(Cache)를 넘어, 랭킹, 대기열, 실시간 통계 등 애플리케이션의 핵심 로직까지 흡수하는 가장 똑똑한 중간 계층임.
- 디스크 중심의 구시대적 아키텍처를 '인메모리(In-Memory)' 중심의 리얼타임(Real-time) 아키텍처로 진화시킨 현대 클라우드 시스템의 심장 박동기와 같음.

### 👶 어린이를 위한 3줄 비유 설명
1. 기존 DB가 무거운 책을 찾는 '지하 도서관'이라면, **Redis**는 1초 만에 답을 말해주는 '내 머릿속 기억력(메모리)'이에요.
2. 엄청 똑똑해서 그냥 글씨만 외우는 게 아니라, "우리 반 수학 성적 1등부터 10등까지 순서대로 줄 세워(Sorted Set)!" 하면 0.001초 만에 세워줘요!
3. 다만 직원이 한 명(싱글 쓰레드)이라서, 한 번에 1가지 질문만 빠르게 답할 수 있어요. 너무 복잡한 계산을 시키면 뒤에 줄 선 사람들이 다 화를 낸답니다.
