# 📖 【암기용】 개념 완전 이해

## 한눈에
- **개요**: 모든 데이터를 주 메모리(RAM)에 저장하여 마이크로초 단위의 매우 빠른 응답 속도를 제공하는 고성능 키-값(Key-Value) 데이터 저장소이다.
- **왜 필요한가**: 디스크 기반 DB(RDBMS, MongoDB 등)는 아무리 최적화해도 I/O 병목으로 인해 수 밀리초의 지연이 발생한다. 트래픽이 폭주하는 선착순 이벤트나 실시간 순위표 처리 시 DB 과부하를 막고 즉각 반응하기 위한 초고속 캐시가 필요하다.
- **핵심 직관**: 하드디스크 창고에 가서 물건을 찾는 대신, 작업대(RAM) 위에 가장 자주 쓰는 물건들을 올려놓고 눈감고도 바로바로 꺼내 쓰는 것과 같다.

## 핵심 용어 정리

| 용어/표기 | 의미 | 비유·예 |
|:---|:---|:---|
| In-Memory | 데이터를 HDD/SSD가 아닌 휘발성 RAM에 저장 | 책꽂이(디스크) 대신 책상 위(메모리)에 자료 두기 |
| Data Structures | 단순 문자열 외에 리스트, 셋, 해시, 정렬 셋 등 지원 | 텍스트만 저장하는 게 아니라 서랍장을 통째로 제공 |
| RDB (Redis Database) | 스냅샷 방식으로 메모리 상태를 디스크에 저장 (백업용) | 퇴근 전 작업대 위 상태를 사진으로 찰칵 찍어두기 |
| AOF (Append Only File) | 변경 연산을 모두 로그로 기록하여 데이터 유실 방지 | 작업할 때마다 "포스트잇 추가함"이라고 장부에 꼼꼼히 적기 |

## 깊이 이해
- **배경·문제의식**: 웹 서비스 규모가 커지면서 DB 조회 결과를 임시 저장(캐시)하여 DB 부하를 줄이는 Memcached가 널리 쓰였다. 하지만 Memcached는 데이터 타입이 문자열뿐이고, 재부팅 시 데이터가 모두 날아가며, 복잡한 랭킹 시스템 등을 구현하기는 어려웠다.
- **작동 원리**: Redis는 메모리에서 동작하는 단일 스레드(Single Thread) 구조를 채택하여 원자성(Atomicity)을 보장한다(동시 접근에 의한 락 충돌 없음). 또한 Sorted Set, List, Hash 등 다양한 자료구조를 제공하여 개발자가 로직을 짤 필요 없이 Redis 명령어 하나로 랭킹 산정, 대기열 처리를 끝낸다. 메모리 휘발성을 보완하기 위해 비동기로 디스크에 저장(RDB/AOF)하는 영속성 옵션도 지원한다.
- **비유**: Memcached가 포스트잇만 붙일 수 있는 단순 메모판이라면, Redis는 엑셀, 차트, 달력이 다 갖춰진 다기능 화이트보드다.
- **구체 예시**: 게임의 실시간 순위표를 만들 때, RDBMS는 수백만 건을 정렬(`ORDER BY`)하느라 뻗어버리지만, Redis의 Sorted Set에 점수를 넣으면 삽입과 동시에 O(log N)으로 자동 정렬되어 `ZREVRANGE` 명령어로 즉각 상위 100명을 뽑아낸다.
- **흔한 오해·주의점**: "Redis는 싱글 스레드라서 느리다?" 아니다. 메모리 접근 자체가 워낙 빨라 CPU보다 네트워크 I/O가 병목이다. 오히려 싱글 스레드라 컨텍스트 스위칭 비용이 없고 동시성 문제가 없어 1초에 10만 건 이상을 처리한다. 단, `KEYS *`처럼 오래 걸리는 명령어를 치면 그동안 다른 모든 요청이 대기(블로킹)하므로 서비스가 마비될 수 있다.

## 연결 개념
- 캐싱 전략(Cache-Aside, Write-Through) — Redis의 주 사용 패턴
- 메인 메모리 DBMS (MMDBMS) — RAM 기반 저장 기술
- 분산 시스템 — Redis Cluster, Sentinel

# 📝 【답안용】 시험 답안 템플릿

## 핵심 인사이트 (3줄 요약)

> 1. **본질**: 고성능 RAM을 주 저장소로 활용하며, 단순 Key-Value를 넘어 다양한 자료구조(Data Structure)를 지원하는 싱글 스레드 기반 인메모리 데이터 스토어이다.
> 2. **가치**: 디스크 I/O 병목을 제거하여 마이크로초 단위의 지연을 보장하고, 영속성(RDB, AOF)과 클러스터링을 통해 엔터프라이즈급 캐시 및 메시지 브로커로 활용된다.
> 3. **판단 포인트**: 싱글 스레드 아키텍처로 인한 블로킹 리스크를 통제하고, 휘발성 메모리의 한계를 RDB/AOF 백업과 이중화(Sentinel/Cluster) 아키텍처로 극복하는 설계가 핵심이다.

## 출제 의도 및 답안 포인트

| 출제 의도 | 반드시 짚을 핵심 | 감점 회피 포인트 |
|:---|:---|:---|
| 인메모리 DB의 특징 및 구조 한계 극복 역량 확인 | 싱글 스레드, 다양한 자료구조, 영속성(AOF/RDB), 클러스터 이중화 | Memcached와 구분되는 기능 누락, 영속성 아키텍처 누락 |

> 요약: 단순 캐시를 넘어 풍부한 자료구조와 디스크 영속성, 분산 클러스터를 지원하는 다목적 데이터 스토어로서의 아키텍처를 제시한다.

## Ⅰ. 개요 및 필요성

- 개요: 네트워크 기반의 인메모리 데이터 구조 저장소로, 데이터의 고속 읽기/쓰기 및 다양한 애플리케이션 자료구조를 지원하는 NoSQL DB
- 배경: 트래픽 급증 및 마이크로서비스 확산으로 인해 디스크 기반 DB의 I/O 병목 해소와 상태 공유 공간(Session, Cache) 요구 증대
- 필요성: 밀리초 이하의 응답 속도, 복잡한 실시간 랭킹 연산의 오프로딩, 노드 간 세션 클러스터링을 위한 고속 공유 저장소 필요

---

## Ⅱ. 구조 및 구성요소

```text
Application -> Redis Server (In-Memory Data Structures) -> Async Save -> Disk (RDB/AOF)
                    |
                    +-> Sentinel / Cluster (Failover & Sharding)
```

| 구성요소 | 역할 | 특이사항 |
|:---|:---|:---|
| In-Memory Engine | RAM 상에서 데이터 연산 및 서빙 처리 | 싱글 스레드 이벤트 루프 모델 |
| Data Structures | String, List, Set, Hash, Sorted Set 등 지원 | 로직 없이 DB 레벨에서 복잡한 연산 해결 |
| Persistence | RDB(스냅샷) 및 AOF(로그)로 디스크에 영속화 | 휘발성(Volatility) 한계 극복 |
| HA & Cluster | Sentinel(자동 페일오버), Redis Cluster(샤딩) | 고가용성 및 수평 확장 지원 |

> 요약: 초고속 인메모리 엔진을 핵심으로, 자료구조 지원과 백그라운드 영속화, 분산 클러스터링으로 무장한 구조이다.

---

## Ⅲ. 동작원리 및 흐름도

```text
클라이언트 요청 -> 이벤트 루프 큐잉 -> 명령 순차 실행 -> 결과 반환 및 AOF 로깅
```

- 1단계 [요청 큐잉]: 다수의 클라이언트 커넥션에서 발생한 명령을 I/O 멀티플렉싱을 통해 이벤트 루프 큐에 적재
- 2단계 [명령 순차 실행]: 싱글 스레드 워커가 큐의 명령을 하나씩 꺼내어 메모리 상의 자료구조 업데이트 수행 (원자성 보장)
- 3단계 [응답 및 복제]: 처리 결과를 클라이언트에 즉각 반환하고, Primary 노드에서 Replica 노드로 비동기 데이터 복제 수행
- 4단계 [영속화 (선택)]: 백그라운드 프로세스(BGSAVE 등)를 통해 메모리 상태를 RDB 스냅샷이나 AOF 로그 파일로 디스크 플러시

> 요약: 멀티플렉싱으로 요청을 받아 싱글 스레드로 락 없이 고속 처리하며, 백그라운드로 복제와 영속화를 병행한다.

---

## Ⅳ. 특징

- 자료구조 내장: 단순 Key-Value 외에 Sorted Set(랭킹), Geo(위치), HyperLogLog(유일 방문자 수 추정) 등 특화 데이터 타입 지원
- 단일 스레드 모델: 동시 접근에 대한 락(Lock) 오버헤드와 컨텍스트 스위칭이 없어 CPU 캐시 효율이 높고 원자적(Atomic) 연산 보장
- 영속성 옵션: 정기적 백업인 RDB 방식과 모든 쓰기 연산을 기록하는 AOF 방식을 조합하여 성능과 데이터 안정성의 트레이드오프 조절 가능

> 요약: 풍부한 데이터 구조와 싱글 스레드의 원자성을 무기로 실시간 연산에 강력하나, 단일 스레드 병목의 구조적 약점도 지닌다.

## Ⅴ. 심화 비교 및 적용 판단

| 비교 축 | Memcached | Redis | 선택 기준 |
|:---|:---|:---|:---|
| 데이터 타입 | 단순 문자열(String) 한정 | List, Set, Hash, Sorted Set 등 | 캐싱 외에 자료구조 연산 필요성 |
| 스레드 아키텍처 | 멀티 스레드 (멀티 코어 활용) | 싱글 스레드 (락 경합 없음) | 대규모 단순 조회 vs 복합 연산 |
| 데이터 영속성 | 미지원 (재부팅 시 소실) | 지원 (RDB, AOF) | 인메모리 데이터의 복구 필요성 |

> 요약: 단순하고 거대한 캐시만 필요하다면 Memcached를, 영속성과 복잡한 자료구조 처리가 필요하다면 Redis를 선택한다.

**리스크·대응 (기본은 불릿):**
- 싱글 스레드 블로킹: `KEYS *`, `FLUSHALL` 등 O(N) 명령어 실행 시 전체 서비스 마비 → `SCAN` 명령어로 대체 및 위험 명령어 rename 처리 (지표: Slowlog 임계치 초과 건수)
- OOM (Out Of Memory) 및 스왑: 메모리 부족 시 OS 스왑 발생으로 성능 급감 → Maxmemory 설정 및 LRU/LFU 기반 Eviction 정책 적용 (지표: 메모리 사용률 80% 미만 유지)

**도입 후 점검 지표 (기본은 불릿):**
- 성능/효율: 초당 처리량(Operations Per Second) 5만 건 이상 확보 및 Cache Hit Ratio 85% 이상 — INFO 명령어 모니터링
- 품질/운영: 명령 실행 지연(Latency) p99 5ms 이하 유지 — 클라이언트 타임아웃 로그 관측

## Ⅵ. 실무 적용 및 결론

**적용 방안 3개:**
1. 실시간 랭킹보드 구현: RDBMS의 복잡한 정렬 쿼리 대신 Redis의 Sorted Set(ZADD, ZRANGE)을 활용하여 수백만 유저 순위를 1ms 내 산출
2. 세션 스토어 클러스터링: Stateless 마이크로서비스 환경에서 사용자 세션과 토큰(JWT 블랙리스트)을 Redis에 중앙 집중화하여 확장성 확보
3. 분산 락(Distributed Lock) 및 큐: Redlock 알고리즘을 이용한 동시성 제어 및 List/Pub-Sub을 활용한 경량 메시지 큐(작업 대기열) 파이프라인 구축

**결론 (2줄):**
- 기술사 판단: Redis는 단순 캐시를 넘어 아키텍처의 복잡도를 낮추는 다목적 도구이나, 싱글 스레드 특성상 O(N) 명령어 차단과 OOM 방지 모니터링 체계가 필수적이다.
- 향후 방향: 최근 멀티 스레드 I/O 처리(Redis 6.0+)가 도입되어 네트워크 병목을 해소하고 있으며, 벡터 검색 모듈(RediSearch)을 통해 AI 애플리케이션의 고속 컨텍스트 저장소로 활용 폭이 확대되고 있다.
