## 핵심 인사이트 (3줄 요약)
- 과거엔 서버의 보안 구멍(취약점)을 찾기 위해 실제 돌아가는 서버에 해킹 공격을 쏴보는 방식(동적 스캔)을 썼음.
- 현대 클라우드 네이티브 시대에는 개발자가 만든 **도커(Docker) 컨테이너 '이미지(압축파일)' 자체를 엑스레이(X-ray)처럼 쫙 스캔해서, 그 안에 있는 낡은 라이브러리나 해커에게 뚫릴 구멍(CVE)이 있는지 배포 전에 미리 잡아내는 정적 스캔 기술**이 대세가 됨.
- 오픈소스인 **Trivy**는 CI/CD 파이프라인 한가운데 서서, "어? 방금 네가 구운 도커 이미지 안에 해킹 위험 높은 옛날 버전 `log4j` 들어있어! 서버에 올리지 마!" 하고 빨간 불을 켜서 배포를 원천 차단하는 가장 유명하고 가벼운 보안 수문장임.
---
## Ⅰ. 개요 및 필요성
- **개요**: 컨테이너 이미지 내부에 포함된 OS 패키지(Alpine, Ubuntu)나 언어별 종속성(npm, pip, jar)을 분석하여, 알려진 보안 취약점(CVE)과 숨겨진 비밀번호(Secret) 등을 탐지하는 보안 통제 활동.
- **필요성**: 개발자가 구글에서 대충 퍼온 `ubuntu:18.04` 베이스 이미지로 도커 컨테이너를 구워서 K8s 운영 서버에 배포함. 근데 그 우분투 옛날 버전엔 전 세계 해커가 다 아는 치명적 백도어 구멍이 있었음. 회사가 털림. **"아니, 코드가 서버에 올라가서 실행되기 전에, 저 도커 이미지 '껍데기' 속에 폭탄(취약점)이 들어있는지 미리 엑스레이로 검사해 주는 로봇 없어?"** ➡️ Trivy 등의 이미지 스캐너 탄생.
---
## Ⅱ. 핵심 아키텍처 및 동작 원리 (Trivy의 마법)
컨테이너를 실행(Run)시키지 않고 파일 시스템만 뜯어봄 (정적 분석).

- **1. 취약점 DB (Vulnerability Database) 동기화**:
  - Trivy는 매일 NVD(국가 취약점 DB)나 오픈소스 보안 권고문을 다운받아 최신 해커들의 폭탄 리스트(CVE 번호)를 학습해둠.
- **2. 이미지 레이어(Layer) 분해**:
  - 개발자가 `docker build`로 만든 이미지를 한 꺼풀씩 벗겨서 파일 시스템을 분석함.
- **3. 패키지 및 라이브러리 검사**:
  - OS 패키지(예: `apt`로 깐 nginx 버전)와 앱 라이브러리(예: `pom.xml`에 적힌 `log4j 2.14`)를 싹 긁어모아 최신 취약점 DB와 대조함.
- **4. 판정 및 차단**:
  - "이 이미지 안에 치명적(Critical) 폭탄 1개, 중간(Medium) 폭탄 5개 발견!" 리포트를 출력하고, CI 파이프라인을 에러(Exit 1)로 강제 종료시켜 배포를 막음.

```text
[ DevSecOps 파이프라인에서의 Trivy 역할 ]

 🧑‍💻 [ 개발자 ] ➡️ "도커 이미지 빌드 완료!"
   ⬇️
 🤖 [ CI 파이프라인 (Jenkins / GitHub Actions) ]
   1단계: 빌드 성공 🟢
   2단계: **Trivy 스캔 🚨** ➡️ "삑! Log4shell (CVE-2021-44228) 취약점 발견!"
   3단계: 빌드 강제 중지 및 슬랙 알람 발송 (배포 차단) ❌
   ⬇️
 🛡️ [ 서버 안전 ] (위험한 코드가 실제 서버로 절대 넘어가지 못함)
```

## Ⅲ. 오해와 진실
| 오해 | 진실 |
|---|---|
| "우리는 소스 코드 보안 스캔(SonarQube) 돌리니까 도커 이미지 스캔은 안 해도 되죠?" | **큰일 날 소리.** 소스코드 스캔은 개발자가 짠 로직의 허점(SQL 인젝션 등)만 봄. 도커 이미지 안에는 개발자가 짜지 않은 **'리눅스 OS(알파인 등)'와 '환경 설정 파일'**이 통째로 들어있음. OS 레벨의 취약점은 도커 이미지 스캔으로만 잡을 수 있음. |
| "취약점 1개라도 나오면 무조건 배포 차단해야지!" | **현실적으로 불가능함.** 오픈소스 이미지를 스캔하면 무조건 수십~수백 개의 찌꺼기 취약점(Low, Medium)이 나옴. 무조건 다 막으면 1년 내내 배포 못함. **치명적(Critical)이면서 패치 버전이 존재하는 것만** 차단하는 유연한 임계치(Threshold) 설정이 핵심임. |

## Ⅳ. 실무 적용 및 기술사 판단
- **지속적 스캐닝 (Continuous Scanning) 아키텍처**: 빌드할 때 스캔해서 통과(취약점 0개)했던 이미지가, 6개월 뒤 운영 서버에 떠 있는 동안 새로운 취약점(새로운 해킹 기법 발견)이 발표될 수 있음. 기술사는 빌드 파이프라인뿐만 아니라, **이미 배포되어 레지스트리(Harbor)나 쿠버네티스에서 돌고 있는 이미지들도 주 단위로 주기적 재스캔**을 돌려, 어제까진 안전했던 이미지가 오늘 폭탄으로 변한 것을 즉시 감지하는 런타임 스캔 체계를 구축해야 함.
- **시크릿(Secret) 하드코딩 탐지**: Trivy는 해킹 구멍만 찾는 게 아님. 개발자가 실수로 도커 이미지 안에 AWS 접속 키(Secret Key)나 DB 비밀번호를 하드코딩해서 구워버린 것도 정규식으로 찾아냄. 기술사는 **빌드 파이프라인에 시크릿 스캔 기능을 의무화**하여, 자격 증명이 GitHub이나 도커 허브로 유출되는 1차적 휴먼 에러를 원천 차단해야 함.

## Ⅴ. 기대효과 및 결론
- "보안팀이 나중에 엑셀로 취약점 리스트를 던져주는" 느리고 피곤한 후행적 보안 검사를 끝내고, 코드 배포 과정(CI)에 보안 로봇(Trivy)을 심어버리는 진정한 **Shift-Left 보안(DevSecOps)**을 완성함.
- 외부에서 긁어온 수많은 오픈소스 컨테이너 이미지를 기반으로 조립되는 클라우드 네이티브(K8s) 생태계에서, 소프트웨어 공급망(Supply Chain)을 오염시키는 악성 코드와 취약점을 걸러내는 가장 1차적이고 핵심적인 방어막임.

### 👶 어린이를 위한 3줄 비유 설명
1. 외국에서 수입해 온 상자(도커 컨테이너) 안에 맛있는 과자가 들었는지 폭탄이 들었는지 눈으로는 알 수 없어요.
2. **컨테이너 이미지 보안 스캔(Trivy)**은 상자를 트럭(운영 서버)에 싣기 전에, 공항 수하물 검사대처럼 **'초정밀 엑스레이 기계'**를 통과시키는 거예요.
3. 엑스레이로 딱 찍어보고 "앗! 저기 폭탄(취약점) 숨겨져 있다!"라고 삐빅 소리를 내서, 절대로 위험한 상자가 손님에게 배달되지 않게 막아주는 똑똑한 경찰관이랍니다!

### 🔀 문제 유형별 목차 전환 (이 키워드 출제 시)
- **개념/도구 설명형 (Ⅱ·Ⅲ 강조)**: Trivy의 3대 탐지 기능(OS 패키지 취약점 CVE 탐지, 언어별 의존성 취약점 탐지, Secret 하드코딩 탐지). 정적 파일 시스템 분석 및 CVE DB 대조 알고리즘 설명.
- **DevSecOps/전략형 (Ⅳ·Ⅴ 강조)**: 'Shift-Left' 보안 사상을 실현하기 위한 CI/CD 파이프라인 내 스캐너 통합 방안. CI 빌드 차단(Fail-build) 전략과 운영 중인 이미지 지속 스캐닝 전략, SBOM 추출 연계 방안 중심으로 서술.
