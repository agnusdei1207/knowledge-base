# 📖 【암기용】 개념 완전 이해

## 한눈에
- **개요**: 데이터베이스 시스템이 데이터를 처리하고 상태를 유지하는 두 가지 상반된 패러다임. (ACID = 엄격함, BASE = 유연함)
- **왜 필요한가**: 금융 시스템처럼 1원도 틀리면 안 되는 환경(ACID)과 유튜브 좋아요 수처럼 1~2초 늦게 반영되어도 멈추지 않는 게 중요한 환경(BASE)의 아키텍처는 완전히 달라야 하기 때문이다.
- **핵심 직관**: ACID는 "완벽히 굳을 때까지 아무도 못 만지게 하는 깁스(강직성)"이고, BASE는 "시간이 지나면 알아서 모양이 잡히는 메모리폼 베개(유연성)"다.

## 핵심 용어 정리

| 용어/표기 | 의미 | 비유·예 |
|:---|:---|:---|
| ACID | 원자성, 일관성, 고립성, 지속성의 약자. RDBMS의 철학 | "송금: 돈이 빠지고 들어가는 게 100% 동시에 성공해야 함" |
| BASE | Basically Available, Soft state, Eventual consistency의 약자. NoSQL의 철학 | "SNS 피드 글쓰기: 조금 늦게 떠도 무조건 글은 등록돼야 함" |
| Soft State | 데이터의 상태가 외부 입력 없이도 시스템(복제 등)에 의해 변경될 수 있음 | "조회할 때마다 싱크 중이라 데이터가 다르게 보일 수 있음" |
| Eventual Consistency | 지금 당장은 데이터가 일치하지 않더라도, 결국(언젠가는) 일치하게 됨 | "메인 서버에 올린 글이 3초 뒤에 모든 캐시 서버에 똑같이 복사됨" |

## 깊이 이해
- **배경·문제의식**: RDBMS 시대엔 은행 거래처럼 완벽한 정합성(ACID)이 법이었다. 하지만 클라우드 분산 환경에서 ACID를 지키려면 수십 대의 서버에 Lock을 걸어야 해(2PC) 성능이 끔찍하게 느려졌다. 이를 극복하고자 '완벽함'을 버리고 '가용성(안 죽는 것)'을 선택한 BASE 철학이 등장했다.
- **ACID의 한계**: ACID는 단일 서버(Scale-up) 환경에 최적화되어 있다. 여러 서버로 수평 확장(Scale-out)할 경우, 분산 트랜잭션의 락 타임아웃과 오버헤드로 인해 시스템이 마비된다.
- **BASE의 3요소**:
  - **Basically Available (기본적인 가용성)**: 다수 노드에 장애가 나도, 살아있는 노드가 어떻게든 응답한다. (멈추지 않음)
  - **Soft state (유연한 상태)**: 노드 간 동기화가 진행 중일 때는 데이터가 일관되지 않고 변화하는 상태를 허용한다. (엄격한 Lock 없음)
  - **Eventual consistency (최종 일관성)**: 시스템에 일정 시간 변경이 없으면, 백그라운드 동기화를 통해 결국 모든 노드의 데이터가 똑같아진다. (결국엔 맞춤)
- **비유**: 
  - ACID(결혼식): 신랑, 신부, 주례, 하객이 한 시간, 한 장소에 완벽히 모여야만 식이 성립(Commit)된다. 한 명이라도 없으면 취소(Rollback).
  - BASE(동아리 엠티): 각자 알아서 숙소로 출발하고, 도착 시간이 다 달라도(Soft state) 결국 밤이 되면 다 같이 모여 고기를 먹는다(Eventual Consistency).
- **흔한 오해·주의점**: BASE가 "데이터를 잃어버려도 된다"는 뜻이 절대 아니다. 데이터는 보존되지만, '모든 사용자가 동시에 100% 똑같은 값을 보는 것'을 포기하고 분산 시스템의 처리 속도를 올린 것이다.

## 연결 개념
- CAP 정리 / PACELC 정리: BASE는 CAP의 AP(가용성+파티션)를, ACID는 CA 또는 CP를 지향하는 아키텍처 철학의 구현체다.
- Saga 패턴: MSA(마이크로서비스)에서 분산 트랜잭션을 처리할 때, ACID(2PC) 대신 BASE(보상 트랜잭션)를 적용하여 최종 일관성을 맞추는 설계 기법.

# 📝 【답안용】 시험 답안 템플릿

## 핵심 인사이트 (3줄 요약)

> 1. **본질**: ACID와 BASE는 데이터베이스의 트랜잭션을 처리하는 두 가지 대조적 아키텍처 패러다임으로, 각각 강한 일관성(RDBMS)과 유연한 가용성(NoSQL)을 지향한다.
> 2. **가치**: ACID는 데이터의 완벽한 무결성을 보장하여 금융·코어 트랜잭션의 신뢰를 담보하고, BASE는 락(Lock)을 배제하여 글로벌 스케일아웃 환경에서 무중단 초고속 처리를 가능케 한다.
> 3. **판단 포인트**: 클라우드 네이티브/MSA 환경에서는 분산 락 비용 문제로 ACID(2PC) 적용이 불가능에 가까우므로, 비즈니스 허용 오차 내에서 BASE 철학 기반의 최종 일관성(Eventual Consistency) 모델로 전환해야 한다.

## 출제 의도 및 답안 포인트

| 출제 의도 | 반드시 짚을 핵심 | 감점 회피 포인트 |
|:---|:---|:---|
| 데이터베이스 트랜잭션 철학 비교 | ACID(단일/강정합성)와 BASE(분산/고가용성) 속성 매핑 | BASE를 데이터가 유실되는 불안전한 시스템으로 묘사 |
| 클라우드/분산 환경 패러다임 전환 | Scale-up(ACID)에서 Scale-out(BASE)으로의 진화 이유 | ACID만 무조건 우수하다는 전통적 시각 |
| MSA 트랜잭션 처리 연계 역량 | BASE 철학을 구현하는 구체적 패턴 (Saga, Eventual Consistency) | 2PC(2-Phase Commit)로 분산환경을 푼다는 비현실적 대안 |

> 요약: 단일 RDBMS의 강력한 무결성 룰(ACID)이 대규모 분산 환경에서 어떻게 성능 병목을 일으키는지 지적하고, 이를 우회하여 가용성을 극대화한 BASE 철학의 개념과 한계 극복 방안을 대조해야 한다.

## Ⅰ. 개요 및 필요성

- 개요: 데이터베이스 트랜잭션 관리 패러다임으로, 완벽한 정합성을 추구하는 ACID(RDBMS)와 분산 환경의 가용성을 추구하는 BASE(NoSQL) 모델
- 배경: 서비스 규모가 글로벌하게 확장되면서, 단일 노드에서 Lock을 기반으로 동작하는 ACID 모델은 처리량 한계와 병목(Deadlock)에 직면함
- 필요성: 네트워크 지연과 분할(Partition)이 잦은 클라우드 환경에서 노드 간 결합도를 낮추고 시스템 전체의 생존성(가용성)을 높이는 아키텍처 철학 필요

## Ⅱ. 구조 및 구성요소

```text
[ 트랜잭션 철학 스펙트럼 ]
<--- 강한 일관성 (Pessimistic) ----------------------- 유연한 가용성 (Optimistic) --->
      [ ACID (RDBMS) ]                                 [ BASE (NoSQL) ]
- Atomicity (모 아니면 도)                      - Basically Available (어떻게든 응답)
- Consistency (무결성 규칙 준수)                - Soft state (상태 변화 허용)
- Isolation (동시성 Lock 통제)                  - Eventual consistency (백그라운드 동기화)
- Durability (디스크 영구 기록)                 (CAP 정리의 AP 특성 지향)
```

| 구성요소 (BASE) | 역할 | 특이사항 |
|:---|:---|:---|
| Basically Available | 분산 시스템의 다수 노드 장애 시에도 가용성 방어 | 부분 장애 허용, 지속적 응답 보장 |
| Soft State | 외부 요청 없이도 내부 복제/동기화로 데이터 상태가 변경됨 | 엄격한 Lock 기반의 고립성(Isolation) 포기 |
| Eventual Consistency| 쓰기 직후엔 불일치할 수 있으나 결국엔 모든 노드가 일치함 | 백그라운드 가십(Gossip) 프로토콜 등을 통한 동기화 |

> 요약: ACID가 트랜잭션의 결과가 0 또는 1이 되도록 시스템을 멈춰 세운다면, BASE는 0.5의 상태를 허용하되 시스템의 멈춤을 방지한다.

## Ⅲ. 동작원리 및 흐름도

```text
- ACID 흐름: Client -> 락 획득(Lock) -> 노드 기록 -> 무결성 검증 -> 락 해제 -> Commit 응답 (지연↑)
- BASE 흐름: Client -> 분산 노드 즉시 기록 (No Lock) -> Commit 응답 (지연↓) 
               +-> (비동기) 백그라운드 복제 전송 -> (시간 경과) -> 모든 노드 일치
```

- 1단계 [요청 진입]: 클라이언트가 데이터 업데이트(쓰기) 트랜잭션 요청
- 2단계 [처리 및 통제]: ACID는 자원 점유(Pessimistic Lock) 후 완료될 때까지 타 트랜잭션을 대기시키며, BASE는 대기 없이 즉각 로컬에 기록
- 3단계 [응답 반환]: ACID는 완벽한 동기화 후 확정 응답을 내리나, BASE는 일단 1차 쓰기 후 클라이언트에게 선 응답(낙관적 처리)
- 4단계 [사후 수렴]: BASE 시스템은 비동기 복제 큐를 통해 타 노드로 데이터를 전파하며 최종적으로 일관성(Eventual Consistency) 도달

> 요약: 두 패러다임의 가장 큰 차이는 동기화 처리를 위한 자원 점유(Lock) 여부와 응답을 지연시키는 블로킹(Blocking) 여부다.

## Ⅳ. 특징

- 동시성 처리 한계 (ACID): 엄격한 고립성(I)을 맞추기 위해 직렬화(Serializable)에 가깝게 동작하면 처리량(TPS)이 급감하는 스케일업의 한계
- 고성능 분산 처리 (BASE): 데이터를 여러 샤드 노드에 쪼개 놓고 스키마 제약 없이 밀어 넣으므로 대용량 쓰기(Write-heavy) 환경에서 초고속 처리 가능
- 애플리케이션 복잡도 전가 (BASE): DB 레벨에서 무결성을 안 지켜주므로, 개발자가 코드 레벨에서 버전 충돌(Conflict) 해결이나 중복 제거 멱등성을 구현해야 함

## Ⅴ. 심화 비교 및 적용 판단

| 비교 축 | ACID (RDBMS) | BASE (NoSQL, 분산 DB) | 선택 기준 |
|:---|:---|:---|:---|
| 우선 순위 특성 | Consistency (정합성) 최우선 | Availability (가용성) 최우선 | 비즈니스의 데이터 오류 치명성 |
| 트랜잭션 확장 | 단일 노드 최적화 (Scale-up 위주) | 다중 노드 분산 최적화 (Scale-out 위주) | 예상되는 최대 트래픽 규모 |
| 동기화 / Lock | 동기적(Synchronous) / 비관적 락 | 비동기적(Asynchronous) / 낙관적 락 | 응답 속도(Latency) 요구사항 |
| 적용 도메인 | 코어뱅킹 계정계, 주문 결제, 재고 원장 | 장바구니, IoT 센서 로그, SNS 피드, 추천 | MSA 아키텍처의 개별 바운디드 컨텍스트 |

> 요약: 하나의 거대한 시스템 내에서도 돈이 오가는 코어 트랜잭션은 ACID를, 대규모 트래픽이 몰리는 앞단 서비스는 BASE를 채택하는 이원화 설계가 필수다.

**리스크·대응:**
- BASE의 Stale Read (구형 데이터 노출): 동기화 전 사용자가 옛날 데이터를 조회하여 혼란 유발 → Read-Your-Writes 보장을 위해 클라이언트의 세션 동안 캐시에 최신값 유지
- BASE의 Write Conflict (업데이트 충돌): 양쪽 노드에서 동시 수정 시 데이터 정합성 파괴 → Vector Clock(벡터 시계) 또는 LWW(Last Write Wins) 정책으로 충돌 병합 해소
- ACID의 분산 락(Deadlock) 붕괴: 2PC 도입 시 한 노드 장애가 전체 트랜잭션 롤백 유발 → 마이크로서비스 간 ACID 시도를 금지하고 이벤트 기반 비동기 통신으로 전환

## Ⅵ. 실무 적용 및 결론

**적용 방안 3개:**
1. MSA 기반 Saga 패턴 도입: 마이크로서비스 간 분산 트랜잭션을 ACID(2PC)로 묶지 않고, 각자의 로컬 트랜잭션 완료 후 이벤트를 발행하는 BASE 기반의 코레오그래피(Choreography) Saga 적용
2. CQRS를 통한 하이브리드 아키텍처: 커맨드(CUD) 영역은 ACID를 보장하는 RDBMS로 구성하여 정합성을 지키고, 조회(Read) 영역은 이벤트를 비동기로 받아 뷰를 만드는 BASE 기반 NoSQL/캐시로 분리 설계
3. 낙관적 락(Optimistic Lock) + 멱등성 보장 설계: BASE 환경에서 API 재시도로 인한 데이터 중복 생성을 막기 위해, 고유 트랜잭션 ID를 활용한 멱등성(Idempotency) 로직을 애플리케이션 계층에 필수 구현

**결론 (2줄):**
- 기술사 판단: 클라우드 네이티브의 본질은 무한한 확장성(Scale-out)이므로, 아키텍트는 낡은 ACID의 환상을 버리고 비즈니스 허용 한도 내에서 BASE 철학을 수용하는 타협점을 찾아야 한다.
- 향후 방향: 두 진영의 극단적 대립을 넘어, 최근에는 분산 환경에서도 높은 수준의 ACID를 제공하면서 수평 확장이 가능한 Spanner, CockroachDB 등 NewSQL이 새로운 표준으로 부상하고 있다.
