## 미리 알고가기

- ACID는 전부 성공하거나 전부 실패해야 하는 업무 데이터를 안전하게 처리하는 트랜잭션 원칙임
- BASE는 일부 불일치를 잠시 허용해도 서비스가 계속 열려 있어야 하는 분산 처리 방식임
- 최종 일관성은 잠시 값이 달라도 시간이 지나면 결국 같은 상태로 맞춰지는 성질임

## Ⅰ. 개요

- **정의/개념**: ACID는 데이터 정확성과 복구를 강하게 보장하는 트랜잭션 원칙이고, BASE는 가용성과 확장성을 위해 일시적 불일치를 허용하는 분산 데이터 처리 방식임
- **배경/필요성**: 결제와 주문 같은 핵심 거래와 피드와 알림 같은 대규모 분산 조회를 같은 기준으로 처리하면 한쪽은 느려지고 다른 한쪽은 과도하게 복잡해지므로 업무별 구분이 필요함

## Ⅱ. 특징

- ACID는 오류와 동시성 상황에서도 데이터 신뢰성을 우선함
- BASE는 서비스 지속성과 확장성을 우선해 빠른 분산 처리를 얻기 쉬움
- ACID는 잠금과 동기화 비용이 커질 수 있음
- BASE는 사후 보정과 사용자 안내가 함께 설계돼야 함

## Ⅲ. 종류 및 비교

| 판단 기준 | ACID | BASE |
|:---|:---|:---|
| 우선 가치 | 정확한 처리와 복구 | 지속적인 응답과 확장 |
| 데이터 상태 | 즉시 맞는 값을 지향함 | 잠시 다른 값을 허용함 |
| 실패 처리 | rollback과 복구 로그로 트랜잭션 원자성 유지 | 재시도·보상·병합으로 복제본 상태 수렴 |
| 대표 업무 | 원자적 commit이 필요한 결제·주문·재고 | 일시 불일치를 허용하는 피드·알림·추천 |

## Ⅳ. 구성요소 및 구조

| 구성요소 | 설명 |
|:---|:---|
| 처리 단위 | 한 번에 묶어 성공시킬 범위를 정함 |
| 동시성 제어 | 여러 요청이 함께 와도 데이터가 깨지지 않게 함 |
| 실패 복구 | 중간 실패 시 되돌릴지, 나중에 보정할지 정함 |
| 일관성 정책 | 즉시 맞출지, 시간이 지나며 맞출지 정함 |

```text
+-------------+      +-------------+      +-------------+
| 업무 중요도 구분 | ---> | ACID 또는 BASE | ---> | 복구 방식 설계   |
+-------------+      +-------------+      +-------------+
```

## Ⅴ. 원리 및 절차 흐름도

```text
+-------------+     +-------------+     +-------------+     +-------------+
| 데이터 중요도 판단 | --> | 정합성 수준 결정 | --> | 실패 처리 방식 설계 | --> | 운영 결과 확인  |
+-------------+     +-------------+     +-------------+     +-------------+
```

1. **데이터 중요도 판단**: 틀리면 안 되는 데이터인지 먼저 구분함
2. **정합성 수준 결정**: ACID가 필요한지, BASE가 허용되는지 정함
3. **실패 처리 방식 설계**: 즉시 되돌릴지 나중에 맞출지 정함
4. **운영 결과 확인**: 오류 복구 시간과 불일치 지속 시간을 확인함

## Ⅵ. 실무 적용 및 유의점

1. 결제와 재고처럼 값이 틀리면 바로 손실로 이어지는 업무는 ACID로 묶고 잠금 대기 시간과 복구 실패 건수로 트랜잭션 범위가 과하지 않은지 확인함
2. 피드와 알림처럼 잠시 늦어도 되는 데이터는 BASE로 처리하되 보정 흐름과 사용자 안내를 함께 두고 불일치 지속 시간과 재처리 성공률로 운영 상태를 점검함

## Ⅶ. 결론

BASE와 ACID의 비교는 어느 쪽이 더 좋으냐가 아니라 어떤 업무가 어느 수준의 정확성과 응답성을 요구하는지 나누는 문제임.
