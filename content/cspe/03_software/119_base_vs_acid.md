## 핵심 인사이트 (3줄 요약)
- **ACID**는 전통적인 RDBMS의 철학으로, "단 1원이라도 오차가 생기면 롤백한다"는 100% 완벽한 데이터 무결성과 빡빡한 잠금(Lock)을 추구하는 금융 시스템의 기반임.
- **BASE**는 NoSQL과 분산 클라우드의 철학으로, "서버가 잠깐 죽거나 데이터가 약간 틀려도 일단 서비스는 돌아가게 하고, 시간 지나면 알아서 맞게 두자"는 극단적인 속도와 가용성을 추구함.
- 현대의 거대한 마이크로서비스(MSA) 아키텍처에서는 ACID를 버리고 BASE를 수용해야만 트래픽 폭주를 견딜 수 있으며, 양 진영의 타협점(Saga 패턴 등)을 찾는 것이 아키텍트의 몫임.

## Ⅰ. 개요 및 필요성
- **개요**: 데이터베이스 시스템이 트랜잭션을 처리하고 데이터를 유지하는 상반된 두 가지 철학적 모델.
- **필요성**: 40년간 ACID를 신봉해 왔으나, 아마존 블랙프라이데이 때 수백만 명이 몰리자 트랜잭션 Lock 때문에 DB 전체가 뻗어버림. "결제 금액이 틀리면 안 되지만, 장바구니나 찜하기 버튼은 1분 정도 안 보여도(정합성 훼손) 서비스가 다운되는 것보단 낫잖아?"라는 깨달음에서 BASE 모델이 등장함.
---
## Ⅱ. 아키텍처 및 핵심 원리
- **1. ACID (RDBMS의 철학)**:
  - **A (Atomicity, 원자성)**: 성공 아니면 실패 (ALL or NOTHING).
  - **C (Consistency, 일관성)**: 무결성 제약조건을 완벽히 지킴.
  - **I (Isolation, 격리성)**: 다른 트랜잭션이 끼어들지 못하게 철저히 Lock을 걺 (성능 병목의 주범).
  - **D (Durability, 지속성)**: 커밋되면 디스크에 영구 보존.
- **2. BASE (NoSQL 및 MSA의 철학)**:
  - **BA (Basically Available, 기본적 가용성)**: 다수의 노드 중 일부가 죽어도, 시스템은 어떻게든 응답함(에러 대신 옛날 데이터를 보여주는 한이 있어도 멈추지 않음).
  - **S (Soft State, 소프트 상태)**: 외부의 입력(Update)이 없어도, 시스템 스스로 노드 간 동기화를 맞추기 위해 내부 상태가 계속 꿀렁꿀렁 변함. (데이터가 유동적임).
  - **E (Eventual Consistency, 최종 일관성)**: 당장은 A서버와 B서버의 값이 달라도, 기다리면 "언젠가는(Eventually)" 100% 같아진다는 낙관적 철학.

```text
[ 은행 송금(ACID)과 유튜브 댓글(BASE)의 차이 ]

 🏦 [ ACID 적용 - 계좌 이체 ]
 - A계좌에서 1만원 빼고 ➡️ B계좌에 1만원 넣음.
 - 이 0.1초 사이에는 아무도 A와 B 계좌를 볼 수 없음 (Lock 걸림). 
 - 100% 정확하지만 수십만 명이 동시에 송금하면 서버 멈춤.

 🎬 [ BASE 적용 - 유튜브 좋아요 버튼 ]
 - 유튜버가 영상을 올리고 내가 '좋아요'를 누름. 
 - 하지만 한국 서버(10개)와 미국 서버(5개)의 수치가 3분 동안 서로 다름 (Soft State).
 - 3분 뒤 새로고침을 하면 전 세계 서버가 동기화되어 결국 15개로 똑같아짐! (Eventual Consistency).
```

## Ⅲ. 비교 및 연결
| 구분 | ACID | BASE |
|---|---|---|
| **추구하는 가치** | **데이터의 완벽한 무결성과 신뢰성** | **시스템의 극한의 성능과 가용성** |
| **대표 시스템** | Oracle, MySQL, PostgreSQL | Cassandra, DynamoDB, MongoDB |
| **정합성 모델** | 강한 일관성 (Strong Consistency) | 최종 일관성 (Eventual Consistency) |
| **동시성 제어** | 비관적 락(Pessimistic Lock) 위주 | 낙관적 락(Optimistic Lock), 락 프리(Lock-free) |
| **스케일 확장성**| Scale-Up (장비 업그레이드) 유리 | Scale-Out (분산 서버 추가)에 완벽 최적화 |

## Ⅳ. 실무 적용 및 기술사 판단
- **MSA에서의 ACID 포기와 보상 트랜잭션**: 쇼핑몰을 MSA로 쪼개면(주문 DB ➡️ 재고 DB ➡️ 결제 DB), 3개의 DB를 하나의 ACID 트랜잭션으로 묶는 것(2PC)은 성능상 불가능함. 실무 아키텍트는 분산 환경에서 ACID를 포기하고 BASE 사상을 받아들여야 함. 대신, 결제는 성공했는데 재고가 없으면 "결제 취소 메시지(Event)"를 날려 환불 처리하는 **보상 트랜잭션(Saga Pattern)**으로 최종 일관성(E)을 보장하는 것이 현대 백엔드 설계의 핵심임.
- **비즈니스 도메인별 믹스(Mix)**: 하나의 서비스 안에서도 결제/정산 모듈은 무조건 ACID 기반의 RDB(PostgreSQL)로 짜고, 상품 조회/리뷰 모듈은 BASE 기반의 NoSQL(Redis, MongoDB)로 분리하는 Polyglot Persistence 전략이 필수적임.
---
## Ⅴ. 기대효과 및 결론
- "100% 완벽해야 한다"는 개발자들의 강박관념(ACID)을 깨고, 현실 세계의 분산 환경에서는 어느 정도 타협(BASE)을 해야만 글로벌 스케일의 트래픽을 감당할 수 있음을 일깨워 줌.
- BASE는 데이터베이스 기술의 후퇴가 아니라, 클라우드 컴퓨팅과 비동기 메시징(Kafka) 시대를 열어젖힌 가장 실용적이고 위대한 아키텍처 철학임.

### 👶 어린이를 위한 3줄 비유 설명
1. **ACID**는 '깐깐한 수학 선생님'이에요. 1+1=2가 아니면 그 자리에서 바로 시험지를 찢어버리고(롤백) 처음부터 다시 풀게 하죠. 아주 정확해요!
2. **BASE**는 '마음씨 좋은 체육 선생님'이에요. 친구가 달리기하다 넘어지면 당장 기록이 틀려도 "일단 계속 뛰어!(가용성)"라고 응원해 줘요.
3. 꼴찌로 들어왔더라도 "언젠가 도착했으니 다 같이 완주한 거야~(최종 일관성)"라고 넉넉하게 넘어가 주는 방식이랍니다!
