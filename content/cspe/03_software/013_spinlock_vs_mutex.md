## Ⅰ. 개요
- **정의**: 바쁜 대기(Busy Wait)와 블로킹 대기(Sleep) 방식으로 상호 배제를 구현하는 두 잠금 기법
- **배경/필요성**: 임계 구역 보호 시 대기 방식에 따라 CPU 사용률과 응답 지연이 달라지므로 상황별 선택이 필요함
- **비유**: 문 앞에서 계속 노크하며 기다리기(스핀락) vs 대기실에 앉아 호출을 기다리기(뮤텍스)

| 출제 의도 | 반드시 짚을 핵심 | 감점 회피 포인트 |
|:---|:---|:---|
| 두 기법의 동작 원리와 적용 상황 비교 | 컨텍스트 스위칭 비용 vs CPU 낭비 트레이드오프 | 스핀락이 단일 코어에서 비효율적인 이유 명시 |

> 요약: 대기 방식의 차이에 따른 성능 트레이드오프를 이해하고 적용 상황을 구분하는 것이 핵심임

## Ⅱ. 구성요소
```text
Spinlock                    Mutex
+--------+              +--------+
| flag   |              | owner  |
| CAS()  |              | queue  |
| spin   |              | sleep  |
+--------+              +--------+
  |                        |
  v                        v
CPU cycle 소비          Context Switch 발생
```

| 구성요소 | 설명 | 비유 |
|:---|:---|:---|
| Spinlock | 잠금 해제까지 루프를 돌며 CPU를 점유하는 바쁜 대기 잠금 | 문 앞에서 계속 노크 |
| Mutex | 잠금 실패 시 스레드를 대기 큐에 넣고 CPU를 양보하는 블로킹 잠금 | 대기실에서 호출 대기 |
| CAS 명령어 | 원자적 비교-교환으로 잠금 상태를 변경하는 하드웨어 명령 | 동시에 하나만 통과하는 회전문 |

> 요약: 스핀락은 CPU 점유 대기, 뮤텍스는 CPU 양보 대기로 상호 배제를 구현함

## Ⅲ. 절차
```text
잠금 요청 -> CAS 시도 -> 성공: 진입 / 실패: Spin 또는 Sleep -> 해제 후 통지
```
- 1단계: 스레드가 잠금 변수에 대해 CAS 연산으로 획득을 시도함
- 2단계: 스핀락은 획득 실패 시 루프를 돌며 재시도, 뮤텍스는 대기 큐에 진입하여 Sleep함
- 3단계: 잠금 획득 후 임계 구역에서 공유 자원을 사용함
- 4단계: 작업 완료 후 잠금을 해제하고, 뮤텍스는 대기 큐의 스레드를 깨움

> 요약: CAS 기반 획득 시도 후 실패 시 대기 방식이 갈리는 것이 핵심 차이임

## Ⅳ. 문제점
- 스핀락 CPU 낭비: 임계 구역이 긴 경우 대기 스레드가 CPU 사이클을 무의미하게 소비함
- 뮤텍스 전환 오버헤드: 잠금 경합 시마다 컨텍스트 스위칭이 발생하여 짧은 임계 구역에서 비효율적임
- 단일 코어 스핀락 무효: 단일 코어에서는 스핀 중인 스레드가 CPU를 독점하여 잠금 보유 스레드가 실행 불가함

> 요약: CPU 낭비, 전환 오버헤드, 단일 코어 비효율이 각 기법의 한계임

## Ⅴ. 개선방안
1. 단기: 적응형 스핀(Adaptive Spin)을 적용하여 일정 횟수 스핀 후 자동으로 Sleep 전환함
2. 중기: MCS Lock 등 큐 기반 스핀락을 도입하여 캐시라인 경합을 감소시킴
3. 장기: 하드웨어 트랜잭셔널 메모리(HTM)를 활용하여 잠금 없이 원자적 실행을 구현함

> 요약: 적응형 스핀, 큐 기반 스핀락, HTM으로 각 한계를 극복 가능함

## Ⅵ. 전망
- 발전 방향: 멀티코어 확대에 따라 NUMA 인지형 잠금 기법이 중요해지는 추세임
- 기술사적 판단: 커널 수준에서 적응형 뮤텍스가 표준으로 자리잡고 있음
- 기술사 제언: 임계 구역 길이와 코어 수를 기준으로 스핀락/뮤텍스 선택 기준을 정량적으로 수립할 필요
