# 📖 【암기용】 개념 완전 이해

## 한눈에
- **개요**: 스핀락과 뮤텍스는 모두 임계 구역 상호 배제를 보장하는 락이지만, **락을 얻지 못한 스레드가 기다리는 방식이 다르다** — 스핀락은 CPU를 계속 돌리며 락을 반복 검사하는 바쁜 대기(Busy-waiting), 뮤텍스는 스레드를 재우고 CPU를 양보하는 블로킹(Blocking) 방식이다.
- **왜 필요한가**: 락을 얻지 못했을 때 "계속 확인하며 기다릴지, 잠들었다가 깨워질지"의 선택이 성능을 좌우한다. 대기가 아주 짧으면 문맥 교환 비용이 아까워 스핀이 유리하고, 대기가 길면 CPU를 낭비하지 않는 블로킹이 유리하다.
- **핵심 직관**: 화장실 앞에서 기다리는 두 방식이다. 스핀락은 문고리를 계속 흔들며 문 앞에 서서 기다리는 사람(자리를 안 비우니 곧 열리면 바로 들어감), 뮤텍스는 대기표를 뽑고 의자에 앉아 자다가 순서가 오면 깨워지는 사람(오래 걸릴 때 딴 일 가능)이다.

## 핵심 용어 정리 (내부에 등장하는 것들)

아래 답안용에 나오는 락 대기·전환 관련 표기를 비유와 함께 먼저 세운다. 맨 위가 이 주제의 상위 핵심 키워드다.

| 용어/표기 | 의미 | 비유·예 |
|:---|:---|:---|
| 락 대기 방식 (상위 키워드) | 락 획득 실패 시 스레드가 기다리는 전략 | 문 앞에 서 있기 vs 의자에 앉아 자기 |
| 바쁜 대기 (Busy-waiting) | 루프를 돌며 락 상태를 반복 검사, CPU 계속 점유 | 문고리를 계속 흔들며 서 있음 |
| 블로킹 (Blocking) | 스레드를 대기 상태로 재우고 CPU를 양보 | 대기표 뽑고 앉아서 잠듦 |
| 스핀락 (Spinlock) | 바쁜 대기로 락을 얻는 락, 문맥 교환 없음 | 문 앞에서 계속 확인 |
| 뮤텍스 (Mutex) | 블로킹으로 대기, 소유권 있는 락 (012 참조) | 대기표 방식 잠금 |
| 문맥 교환 (Context Switch) | 실행 스레드를 바꾸며 레지스터·PCB 저장·복원 | 사람 교대하며 짐 싸고 풀기 (002 참조) |
| CAS (Compare-And-Swap) | 값 비교 후 같으면 교체하는 원자적 명령, 스핀락 핵심 | "빈칸이면 내 이름 써넣기"를 한 번에 |
| test-and-set | 값을 1로 세팅하며 이전 값 반환하는 원자 명령 | 문패를 뒤집으며 원래 상태 확인 |
| 커널 모드 전환 | 블로킹·깨우기를 위해 커널에 진입하는 비용 | 관리실에 가서 대기 등록 |
| 임계 구역 (Critical Section) | 공유 자원 접근 보호 코드 영역 (014 참조) | 열쇠 필요한 방 내부 |
| 선점 (Preemption) | 스케줄러가 실행 중 스레드를 강제 회수 | 순번 도중 자리 뺏김 |
| 우선순위 역전 (Priority Inversion) | 저순위가 쥔 락을 고순위가 기다림 (011 참조) | 급한 사람이 느린 사람 뒤에 갇힘 |

## 깊이 이해
- **배경·문제의식**: 락은 임계 구역 진입권을 통제하지만, 진입 실패 시 "기다리는 시간"을 어떻게 소비할지는 별개 문제다. 재우면(블로킹) 문맥 교환에 수 μs가 들고, 안 재우면(스핀) 그 시간만큼 CPU가 헛돈다. 어느 쪽이 싼지는 **예상 대기 시간과 문맥 교환 비용의 비교**로 결정된다.
- **작동 원리(어떻게+왜)**:
  - **스핀락**: `while(test-and-set(lock)) ;` 형태로, 원자적 명령(test-and-set·CAS)으로 락 변수를 반복 검사한다. 실패하면 루프를 계속 돌 뿐 스레드를 재우지 않아 **문맥 교환이 없다**. 락이 곧 풀리면 즉시 진입하므로 매우 짧은 임계 구역에서 빠르다. 단, 도는 동안 CPU 코어 하나를 100% 점유한다.
  - **뮤텍스**: 락 획득 실패 시 스레드를 대기 큐에 넣고 **블로킹(sleep)** 시켜 CPU를 다른 스레드에 양보한다. 락 소유자가 unlock하면 커널이 대기 스레드를 깨운다(wake-up). 재우고 깨우는 데 커널 모드 전환·문맥 교환 비용이 들지만, 대기 중 CPU를 낭비하지 않는다.
  - **왜 상황별로 갈리나**: 임계 구역이 문맥 교환 비용(대략 1~10μs)보다 짧게 끝나면, 재웠다 깨우는 비용이 그냥 도는 비용보다 커서 스핀이 이득이다. 반대로 임계 구역이 길거나 코어가 하나면(단일 CPU에서 스핀은 락 소유자가 실행될 기회를 뺏어 무의미) 블로킹이 이득이다.
- **비유**: 편의점 계산대에 점원이 잠깐 자리를 비웠다. 스핀락은 "3초면 오겠지" 하고 계산대 앞에 계속 서서 기다리는 것 — 곧 오면 바로 계산한다. 뮤텍스는 "오래 걸리겠네" 하고 번호표 뽑고 앉아 다른 일 하다 호출되면 오는 것 — 자리(CPU)를 남에게 내준다.
- **구체 예시**: 리눅스 커널은 `spinlock_t`를 인터럽트 핸들러 등 **재우면 안 되는(sleep 불가) 짧은 임계 구역**에 쓴다. 반면 사용자 공간의 `pthread_mutex`는 기본이 블로킹이다. 실무 구현은 대개 **적응형(adaptive) 뮤텍스** — 락 소유자가 다른 코어에서 실행 중이면 잠깐 스핀하다가, 일정 횟수 넘으면 블로킹으로 전환한다(glibc, Java의 `synchronized` 최적화가 이 방식).
- **흔한 오해·주의점**: (1) **스핀락이 항상 빠르지 않다** — 임계 구역이 길거나 스레드 수가 코어 수보다 많으면 스핀은 CPU를 태우기만 한다. (2) **단일 CPU(비선점 커널)에서 스핀락은 위험** — 락 소유자가 선점당해 못 풀면, 스핀하는 쪽이 CPU를 계속 잡아 소유자가 실행조차 못 해 사실상 교착이 된다. (3) 스핀락은 소유권·재귀 획득·조건 대기 같은 고급 기능이 없어 단순 보호용이며, 뮤텍스는 소유권을 갖는다(012 참조).

## 연결 개념
- 세마포어·뮤텍스·모니터(012 참조) — 뮤텍스의 소유권·블로킹 특성의 상위 분류
- 문맥 교환과 PCB(002 참조) — 블로킹 방식이 지불하는 재우기·깨우기 비용의 실체
- 임계 구역·상호 배제(014 참조) — 두 락이 공통으로 보호하는 대상과 진입 조건

# 📝 【답안용】 시험 답안 템플릿

## 핵심 인사이트 (3줄 요약)

> 1. **본질**: 스핀락과 뮤텍스는 같은 상호 배제 목적의 락이나, 대기 방식이 바쁜 대기(CPU 점유)와 블로킹(CPU 양보)으로 갈림.
> 2. **가치**: 대기 시간과 문맥 교환 비용의 대소가 선택을 좌우해, 매우 짧은 임계 구역은 스핀락, 긴 임계 구역은 뮤텍스가 유리함.
> 3. **판단 포인트**: 임계 구역 길이·코어 수·sleep 가능 여부를 기준으로 선택하며, 실무는 둘을 결합한 적응형 락이 표준임.

## 출제 의도 및 답안 포인트

| 출제 의도 | 반드시 짚을 핵심 | 감점 회피 포인트 |
|:---|:---|:---|
| 두 락의 대기 방식 구분 | 바쁜 대기(스핀) vs 블로킹(뮤텍스) | 대기 방식 차이 누락 |
| 성능 트레이드오프 근거 | 문맥 교환 비용 vs CPU 점유 비용 | 스핀락을 무조건 빠르다 단정 |
| 상황별 선택 기준 | 임계 구역 길이·코어 수·sleep 가능성 | 단일 CPU 스핀락 위험성 누락 |

> 요약: 대기 방식(스핀 vs 블로킹) 차이를 문맥 교환 비용 관점으로 설명하고, 임계 구역 길이·코어 수로 선택 기준을 제시함.

## Ⅰ. 개요 및 필요성

- 개요: 락 획득 실패 시 바쁜 대기로 도는 락(스핀락)과 스레드를 재우는 락(뮤텍스)의 대비임
- 배경: 임계 구역 보호는 같으나 대기 시간 소비 방식에 따라 CPU 효율·지연이 크게 달라짐
- 필요성: 문맥 교환 비용과 예상 대기 시간의 대소를 따져 상황에 맞는 락을 선택해야 함

## Ⅱ. 구조 및 구성요소

선형 구조도 (락 획득 실패 시 분기):

    락 획득 시도 (원자 명령 test-and-set / CAS)
      -> 성공: 임계 구역 진입
      -> 실패 / [스핀락] 루프 반복 검사 - CPU 계속 점유, 문맥 교환 없음
      -> 실패 / [뮤텍스] 대기 큐 삽입 후 블로킹 - CPU 양보, 커널이 깨움

| 구성요소 | 역할 | 특이사항 |
|:---|:---|:---|
| 원자 명령 (CAS·test-and-set) | 락 변수 검사·설정을 한 번에 수행 | 두 락의 공통 진입 판정 수단 |
| 스핀 루프 | 락 풀릴 때까지 반복 검사 | 문맥 교환 없음, CPU 점유 |
| 대기 큐 + 블로킹 | 실패 스레드를 재우고 CPU 양보 | 커널 모드 전환·깨우기 비용 |
| 적응형 로직 | 짧게 스핀 후 블로킹 전환 | glibc·JVM 등 실무 표준 |

> 요약: 두 락은 원자 명령으로 진입을 판정하되, 실패 후 스핀 루프(CPU 점유)와 대기 큐 블로킹(CPU 양보)으로 갈라짐.

## Ⅲ. 동작원리 및 흐름도

선형 흐름도 (락 경합 시 처리):

    스레드 A가 락 보유 -> 스레드 B가 락 시도(실패)
      -> [스핀락] B는 while 루프로 락 상태 반복 검사(CPU 점유 유지)
      -> [뮤텍스] B는 대기 큐 진입 후 sleep(CPU를 C에 양보)
    A가 락 해제 -> [스핀락] B의 다음 검사에서 즉시 획득 / [뮤텍스] 커널이 B를 wake-up

- 1단계 [락 시도]: 스레드 B가 원자 명령으로 락 획득을 시도하나, A가 점유 중이라 실패함
- 2단계 [대기 방식 분기]: 스핀락이면 B가 루프를 돌며 CPU를 계속 점유하고, 뮤텍스면 B가 대기 큐로 들어가 블로킹되어 CPU를 양보함
- 3단계 [락 해제]: 소유자 A가 임계 구역을 마치고 락을 해제함
- 4단계 [재획득]: 스핀락은 B가 다음 검사 즉시 진입하고, 뮤텍스는 커널이 B를 깨워(문맥 교환) 진입시킴

> 요약: 경합 시 스핀락은 CPU를 태우며 즉시 재획득에 강하고, 뮤텍스는 CPU를 양보하되 깨우기 문맥 교환 비용을 지불함.

## Ⅳ. 특징

- 스핀락의 저지연: 문맥 교환이 없어 매우 짧은 임계 구역에서 락 해제 직후 즉시 진입함
- 스핀락의 CPU 낭비: 대기 동안 코어 하나를 100% 점유해 임계 구역이 길수록 손해가 커짐
- 뮤텍스의 CPU 효율: 블로킹으로 대기 중 CPU를 양보해 다른 작업이 진행되나 깨우기 지연이 있음
- sleep 가능 여부 제약: 인터럽트 핸들러 등 재우면 안 되는 문맥에서는 스핀락만 사용 가능함
- 적응형 결합: 실무는 짧게 스핀 후 임계값 초과 시 블로킹으로 전환해 양쪽 장점을 취함

## Ⅴ. 심화 비교 및 적용 판단

두 락을 대기 방식·비용·적용 상황 축으로 대조함(소유권·계수 제어 비교는 012 참조).

| 구분 | 스핀락 | 뮤텍스 |
|:---|:---|:---|
| 대기 방식 | 바쁜 대기(루프 반복 검사) | 블로킹(대기 큐 sleep) |
| CPU 점유 | 대기 중 계속 점유 | 대기 중 양보 |
| 문맥 교환 | 없음 | 있음(재우기·깨우기) |
| 적합 임계 구역 | 매우 짧음(수백 ns) | 김(수 μs 이상) |
| 커널 개입 | 최소(사용자 공간 가능) | 필요(블로킹·wake-up) |
| 단일 CPU 적합성 | 부적합(소유자 실행 방해) | 적합 |
| 대표 사용처 | 리눅스 커널 인터럽트 문맥 | pthread_mutex, 사용자 앱 락 |

> 요약: 임계 구역이 문맥 교환 비용보다 짧고 멀티코어면 스핀락, 길거나 단일 CPU면 뮤텍스가 유리함.

**리스크·대응:**
- 스핀락 CPU 소진 — 긴 임계 구역·과다 경합으로 코어 낭비 — 임계 구역 축소·뮤텍스/적응형 락으로 전환
- 단일 CPU 정지 — 락 소유자 선점 시 스핀 스레드가 CPU 독점 — 비선점 문맥에서 인터럽트 비활성화·스핀 금지
- 우선순위 역전 — 저순위가 락 점유 중 고순위 대기 — 우선순위 상속 프로토콜 적용(011 참조)

**점검 지표:**
- 성능: 락 대기 시간(p99), 임계 구역 평균 점유 시간
- 운영: 스핀 사이클 소모율(CPU%), 락 경합(contention) 비율

## Ⅵ. 실무 적용 및 결론

**적용 방안:**
1. 커널 짧은 보호: 인터럽트 핸들러·스케줄러 큐 등 sleep 불가·초단기 구역에 스핀락(spinlock_t) 적용
2. 사용자 앱 일반 보호: 수 μs 이상 걸리는 공유 자료구조 접근에 블로킹 뮤텍스(pthread_mutex, std::mutex) 적용
3. 경합 불확실 구간: 락 소유자 실행 여부로 스핀·블로킹을 자동 전환하는 적응형 뮤텍스(glibc adaptive, JVM 편향/경량 락) 활용

**결론:**
- 기술사 판단: 임계 구역이 문맥 교환 비용보다 짧고 멀티코어면 스핀락, 길거나 단일 CPU·sleep 필요면 뮤텍스를 선택함
- 향후 방향: 경합 자체를 줄이는 무잠금(lock-free)·CAS 기반 자료구조와 코어 수 증가에 대응하는 큐 기반 공정 스핀락(MCS lock)으로 발전함

### 🔀 문제 유형별 목차 전환 (이 키워드 출제 시)

| 유형 | 문제 신호어 | Ⅱ·Ⅲ 강조 | Ⅴ·Ⅵ 강조 |
|:---|:---|:---|:---|
| 포괄형 | "스핀락과 뮤텍스를 설명하시오" | 두 락의 획득 실패 분기·경합 흐름 | 대기 방식 차이·상황별 선택 |
| 비교형 | "바쁜 대기와 블로킹의 성능을 비교하시오" | 문맥 교환 유무·CPU 점유 흐름 | 임계 구역 길이·코어 수 기준 판단 |

> 요약: 포괄형은 두 락의 대기 분기와 경합 흐름을, 비교형은 바쁜 대기 vs 블로킹의 비용 대소와 선택 기준을 무게중심으로 둠.
