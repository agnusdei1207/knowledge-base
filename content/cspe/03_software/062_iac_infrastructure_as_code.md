## Ⅰ. 개요
- **정의**: 인프라 자원을 코드로 정의·프로비저닝·관리하는 방법론
- **배경/필요성**: 수동 콘솔 조작은 재현 불가·환경 편차를 유발하므로, 코드 기반 선언으로 일관성과 반복성을 확보할 필요
- **비유**: 건축 설계도 — 도면(코드)만 있으면 같은 건물을 몇 번이든 동일하게 지을 수 있음

| 출제 의도 | 반드시 짚을 핵심 | 감점 회피 포인트 |
|:---|:---|:---|
| 선언적 vs 명령적 차이 | 멱등성, 상태 관리, 버전 관리 | 구성관리(064 참조)와 프로비저닝 혼동 금지 |

> 요약: 인프라를 코드로 선언하여 재현 가능하고 버전 관리되는 프로비저닝을 수행하는 방법론임

## Ⅱ. 구성요소
```text
Code Files --> IaC Engine --> Cloud API --> Infrastructure
                  |
                  v
             State Store
```

| 구성요소 | 설명 | 비유 |
|:---|:---|:---|
| Code Files | 인프라 자원을 선언한 HCL·YAML 등의 정의 파일 | 건축 설계도 |
| IaC Engine | 코드를 파싱하고 API 호출로 변환하는 실행 엔진 | 시공사 |
| State Store | 현재 인프라 상태를 저장하여 Diff 계산에 사용하는 저장소 | 준공 대장 |
| Cloud API | 실제 자원 생성·수정·삭제를 수행하는 프로바이더 인터페이스 | 자재 납품 창구 |

> 요약: 코드-엔진-상태저장소-API의 4요소로 인프라를 선언적으로 관리함

## Ⅲ. 절차
```text
Write --> Plan --> Apply --> Verify
```
- 1단계: 인프라 자원을 코드로 작성함
- 2단계: Plan 명령으로 변경 사항을 미리 확인함
- 3단계: Apply 명령으로 실제 인프라에 반영함
- 4단계: 상태 파일과 실제 인프라를 비교하여 정합성을 검증함

> 요약: 작성-계획-적용-검증의 4단계로 인프라를 프로비저닝함

## Ⅳ. 문제점
- 상태 파일 충돌: 다수 작업자가 동시에 Apply 시 상태 파일 경합이 발생함
- 비밀정보 평문 노출: 상태 파일에 패스워드·키가 평문으로 기록될 수 있음
- 프로바이더 종속: 특정 클라우드 전용 리소스 타입 사용 시 이식성이 저하됨

> 요약: 상태 경합, 비밀정보 노출, 벤더 종속이 주요 문제임

## Ⅴ. 개선방안
1. 단기: 원격 백엔드와 상태 잠금(Lock) 기능을 활성화하여 동시 접근을 방지함
2. 중기: Vault 연동으로 비밀정보를 상태 파일에서 분리·암호화함
3. 장기: 추상화 모듈·멀티프로바이더 구성으로 클라우드 이식성을 확보함

> 요약: 상태 잠금, 비밀정보 분리, 멀티프로바이더 추상화로 개선함

## Ⅵ. 전망
- 발전 방향: GitOps(061 참조)와 결합하여 인프라 변경도 PR 기반 워크플로로 수렴함
- 기술사적 판단: 클라우드 네이티브 환경에서 IaC는 기본 역량이며 Terraform(063 참조)·Pulumi 등 도구 선택이 핵심임
- 기술사 제언: 상태 관리 전략과 모듈 재사용 설계를 초기부터 수립할 필요
