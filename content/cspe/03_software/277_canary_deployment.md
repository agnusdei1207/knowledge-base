## Ⅰ. 개요
- 정의: 트래픽의 일부만 신규 버전에 먼저 노출하거나, 점진적으로 서버를 교체하는 방식
- 배경: 전체 배포의 리스크를 줄이고 실제 사용자 피드백을 통해 안정성 검증 필요
- 출제 의도: 카나리(Canary)와 롤링(Rolling) 방식의 차이점 및 장단점 비교 측정

## Ⅱ. 구성요소
- 구조도
  [Canary] : User(5%) -> New / User(95%) -> Old
  [Rolling] : [V1 V1 V1] -> [V2 V1 V1] -> [V2 V2 V1] -> [V2 V2 V2]

- 구성요소 표
| 방식 | 설명 | 특징 |
| :--- | :--- | :--- |
| 카나리 | 소수 인원/트래픽 대상 선 배포 | 위험 감지(광산의 카나리아) |
| 롤링 | 서버를 순차적으로 하나씩 업데이트 | 무중단, 추가 자원 절감 |
| 피처 플래그 | 코드 수정 없이 기능 활성/비활성 | 런타임 제어 |
> 요약: 카나리는 일부 사용자·트래픽에 먼저 노출하고 롤링은 인스턴스를 순차 교체함

## Ⅲ. 절차
- 흐름도
  대상 선정 -> 부분 배포 -> 모니터링/비교 -> 전체 확산(또는 롤백)
- 4단계 설명
1. 대상 선정: 카나리 배포를 적용할 특정 사용자 그룹 또는 트래픽 비율 결정
2. 부분 배포: 선정된 그룹에 신규 버전을 배포하고 트래픽 유입 시작
3. 모니터링/비교: 배포 구간별로 기존 버전과 신규 버전의 오류율·지연 시간·업무 지표 비교
4. 전체 확산: 안정성이 검증되면 롤링 방식 등을 통해 모든 서버로 신규 버전 확대
> 요약: 단계별 지표가 기준을 충족하면 노출 범위를 늘리고 초과하면 확산 중지 또는 롤백함

## Ⅳ. 문제점
- 구버전과 신버전이 공존하는 기간 동안 세션 불일치 및 데이터 충돌 리스크
- 여러 버전이 동시에 운영됨에 따라 운영 복잡도 증가 및 모니터링 난이도 상승

## Ⅴ. 개선방안
- 스티키 세션(Sticky Session) 적용 및 하위 호환성을 유지하는 API 설계
- 프로메테우스 등 가시화 도구를 활용한 버전별 성능 비교 자동화 및 알람 설정

## Ⅵ. 전망
- 인공지능이 배포 지표를 분석하여 자동으로 확산 여부를 결정하는 스마트 배포 기술
- CSF: 배포는 기술적 행위가 아닌 비즈니스 가치 전달 과정이라는 인식 전환 필요
