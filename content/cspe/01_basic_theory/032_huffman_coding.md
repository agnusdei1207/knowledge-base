# 허프만 코딩 (Huffman Coding)

## 미리 알고가기

- **가변 길이 코드**: 기호마다 코드 비트 수가 다른 방식. 모든 글자를 8비트로 똑같이 저장하는 고정 길이와 달리, 자주 나오는 글자는 짧게, 드문 글자는 길게 담는다.
- **접두사 코드(prefix code)**: 어떤 기호의 코드도 다른 기호 코드의 앞부분이 되지 않게 만든 코드 규칙. 긴급번호 119가 있으면 11로 시작하는 다른 번호를 둘 수 없는 것과 같아서, 비트를 쭉 이어 붙여도 어디서 끊어 읽을지 헷갈리지 않는다.
- **우선순위 큐(priority queue)**: 넣은 순서와 무관하게 "가장 작은 값"을 먼저 꺼내 주는 자료구조. 허프만 트리를 만들 때 빈도가 가장 낮은 두 노드를 반복해서 뽑는 데 쓴다.

## 1. 개요

- **정의/개념**: 허프만 코딩은 기호별 출현 빈도를 세어, 자주 나오는 기호에는 짧은 비트 코드를, 드물게 나오는 기호에는 긴 코드를 붙여 전체 데이터의 평균 코드 길이를 최소로 줄이는 무손실 압축 기법이다.
- **배경/필요성**: 컴퓨터는 원래 A든 Z든 글자 하나를 똑같이 8비트로 저장한다. 규칙이 단순해 빠르지만, 실제 글에서 'e'는 수천 번 나오고 'z'는 몇 번 안 나오는데도 둘 다 같은 8비트를 쓰니 자주 나오는 글자에서 낭비가 쌓인다. 그래서 자주 나오는 기호에 짧은 코드를 주면 총 길이가 줄지만, 코드 길이가 제각각이면 `0`과 `01`처럼 이어 붙였을 때 어디서 끊어야 할지 모호해진다. 허프만 코딩은 어떤 코드도 다른 코드의 앞부분이 되지 않는 접두사 코드로 이 경계 모호성을 원천 차단하면서 동시에 평균 길이를 최소로 맞춘다.

## 2. 특징 및 비교

허프만 코딩의 자리는 "빈도가 치우친 데이터를, 복호가 헷갈리지 않게, 기호 하나 단위로 최적 압축"하는 지점이다. 앞뒤 대안과 나란히 놓으면 그 자리가 분명해진다.

| 구분 | 고정 길이 코드 | 허프만 코딩 | 산술 코딩 (Arithmetic Coding) |
|:---|:---|:---|:---|
| 코드 길이 | 모든 기호가 같은 비트 수 | 빈도 따라 기호마다 다른 비트 수 | 기호 단위가 아니라 구간 하나로 뭉쳐 표현 |
| 복호 경계 | 길이가 같아 끊기 쉬움 | 접두사 코드라 유일하게 끊김 | 확률 모델로 구간을 되짚어 복원 |
| 압축 한계 | 치우친 분포를 못 살림 | 기호당 정수 비트라 이론 최적에 근접 | 기호당 소수 비트까지 짜내 대개 더 촘촘 |
| 구현 부담 | 가장 단순 | 트리·코드표로 중간 | 정밀도 관리가 까다로워 무거움 |

> 요약: 단순함이 최우선이면 고정 길이, 빈도 편향을 간단히 살리려면 허프만, 마지막 한 비트까지 짜내려면 산술 코딩이다.

허프만이 산술 코딩에 밀리는 지점은 딱 하나, "기호마다 코드가 정수 비트여야 한다"는 제약이다. 확률이 0.9인 기호는 이론상 0.15비트면 되는데 허프만은 최소 1비트를 줘야 하니 그만큼 손해가 난다. 대신 트리를 따라 0/1을 읽어 내려가면 되는 복호의 단순함과 빠름은 허프만이 유리하다.

## 3. 구성요소/구조

허프만의 핵심은 트리를 만드는 방식이다. 빈도가 가장 낮은 두 기호를 자꾸 짝지어 위로 합쳐 올리면, 빈도가 낮은 기호일수록 트리 깊은 곳으로 밀려나 긴 코드를, 자주 나오는 기호는 뿌리 근처에 남아 짧은 코드를 받게 된다.

```text
빈도: A=5, B=2, C=1, D=1  ->  낮은 둘을 계속 합침

          ( 9 )
         /     \
        A      ( 4 )        A : 0     (뿌리 바로 아래, 1비트)
      [0]     /     \       B : 10
             B      ( 2 )   C : 110   (가장 드물어 가장 깊음, 3비트)
           [10]    /    \   D : 111
                  C      D
               [110]   [111]
```

왼쪽 간선에 `0`, 오른쪽 간선에 `1`을 붙이고 뿌리에서 각 기호까지 내려가며 비트를 모으면 그게 코드다. 어떤 기호도 다른 기호의 조상이 아니라 모두 리프에 있으므로, 자연히 어떤 코드도 다른 코드의 앞부분이 되지 않는 접두사 코드가 된다.

| 구성요소 | 하는 일 | 왜 중요한가 |
|:---|:---|:---|
| 기호(Symbol) | 압축 대상 단위 (문자·바이트 등) | 이 단위마다 코드 하나가 붙음 |
| 빈도(Frequency) | 기호별 출현 횟수 | 이 값이 코드 길이를 결정 |
| 우선순위 큐 | 빈도 최소 노드 두 개를 매번 꺼냄 | 트리를 아래에서 위로 쌓는 엔진 |
| 허프만 트리 | 합쳐 올린 이진 트리 | 리프 위치가 곧 접두사 코드 |
| 코드표(Code Table) | 기호 ↔ 비트열 대응표 | 인코딩과 디코딩이 공유하는 사전 |

> 요약: 빈도가 트리 모양을 정하고, 트리의 리프 깊이가 곧 코드 길이가 된다.

```text
+----------+     +----------+     +-----------+     +-----------+
| 빈도 계산 | --> | 트리 구성 | --> | 코드표 생성 | --> | 비트열 변환 |
+----------+     +----------+     +-----------+     +-----------+
```

빈도 하나가 바뀌면 트리 모양이 바뀌고 코드표까지 통째로 흔들리므로, 압축기와 복원기는 같은 빈도·같은 코드표를 반드시 공유해야 한다.

## 4. 문제점 및 개선방안

1. **학습한 빈도와 실제 분포의 불일치**: 파일 앞부분으로 만든 코드표를 뒷부분에 그대로 쓰면, 뒷부분 분포가 다를 때 자주 나오는 기호에 긴 코드가 붙어 오히려 커질 수 있다.
   - **개선방안**: 데이터를 블록으로 잘라 블록마다 코드표를 새로 만들거나, 읽어 가며 빈도를 갱신하는 적응형 허프만(adaptive Huffman)을 쓴다. (확인: 블록별 압축률 편차)

2. **코드표 저장 오버헤드**: 코드를 풀려면 코드표도 함께 보내야 하는데, 데이터가 작으면 이 표 크기가 압축으로 아낀 양보다 커져 손해가 난다.
   - **개선방안**: 일정 크기 이하 데이터는 압축을 건너뛰고, 트리 대신 코드 길이만 저장하면 복원되는 정준 허프만(canonical Huffman)으로 표를 줄인다. (확인: 원본 대비 코드표 비율)

3. **비트 손상 시 경계 붕괴**: 코드 길이가 제각각이라 중간 비트 하나만 뒤집혀도 이후 끊어 읽는 위치가 어긋나 그 뒤 전체가 깨진다.
   - **개선방안**: 일정 구간마다 동기화 지점을 두고 블록 경계·검사합(checksum)으로 손상 구간을 그 블록 안에 가둔다. (확인: 오류 1비트당 복원 실패 범위)

## 5. 실무 적용 사례

| 적용 영역 | 어떻게 쓰나 | 무엇으로 효과를 확인하나 |
|:---|:---|:---|
| 범용 파일 압축 | ZIP·gzip이 반복 제거(LZ77) 뒤 남은 기호를 허프만으로 마무리 압축 | 압축률, 코드표 크기 |
| 이미지·미디어 | JPEG(Joint Photographic Experts Group)이 양자화된 계수를 허프만으로 부호화 | 비트율, 복원 품질 |
| 통신 메시지 | 분포가 치우친 텍스트·로그를 전송 전 무손실 축소 | 전송량, 지연 |

> 요약: 대개 반복 제거나 변환으로 기호 분포를 치우치게 만든 뒤, 그 치우침을 허프만이 비트로 거둬들이는 마지막 단계에 놓인다.

## 6. 결론

허프만 코딩은 빈도가 치우친 데이터를 접두사 코드로 안전하게, 기호당 정수 비트 한도 안에서 최적으로 줄이는 무손실 압축의 기본기다. 실무에서 단독으로 쓰기보다 LZ77 같은 반복 제거나 JPEG의 양자화가 먼저 분포를 치우치게 만든 뒤 그 뒷단에 붙는 이유도 여기에 있다. 그래서 선택의 초점은 "허프만이냐"가 아니라, 복호의 단순함이 필요하면 허프만, 마지막 한 비트까지 짜내야 하면 산술 코딩, 분포가 계속 변하면 적응형 허프만처럼 데이터 성질과 복원 조건에 맞춰 어떤 변형을 어느 단계에 둘지로 좁혀진다.
