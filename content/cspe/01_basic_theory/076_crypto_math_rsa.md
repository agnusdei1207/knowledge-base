## 미리 알고가기

- 일방향 함수: 계산은 쉽지만 역산은 현실적으로 어려운 함수임
- 모듈러 연산: 나머지 공간에서 덧셈, 곱셈, 거듭제곱을 수행하는 연산임
- 소인수분해 문제: 큰 합성수를 원래 소수들의 곱으로 되돌리는 어려운 문제임
- 이산대수 문제: `g^x mod p = y`에서 `x`를 찾기 어려운 문제임
- 공개키 암호: 공개키로 암호화·검증하고 개인키로 복호화·서명하는 비대칭 암호 체계임
- 키 길이: 공격자가 탐색해야 할 계산 공간과 보안 강도를 좌우하는 파라미터임

## Ⅰ. 개요

- **정의**: 암호 수학은 모듈러 산술, 소인수분해, 이산대수 같은 계산 난제를 기반으로 공개키 암호의 키 생성, 암호화, 복호화, 서명을 가능하게 하는 수학적 체계임. 정방향 계산은 빠르고 역방향 계산은 어렵다는 계산 복잡도 차이를 기준으로 공개 채널의 기밀성과 인증을 확보하기 위해 사용함
- **배경/필요성**: 대칭키만으로는 처음 만나는 통신 주체가 안전하게 키를 공유하기 어렵기 때문에 공개된 정보만으로도 비밀 통신을 시작할 수 있는 비대칭 구조가 필요함
- **비유**: 자물쇠를 잠그는 방법은 누구에게나 공개하지만, 풀 수 있는 열쇠는 소유자만 가진 구조와 유사함

| 출제 의도 | 반드시 짚을 핵심 | 감점 회피 포인트 |
|:---|:---|:---|
| 공개키 암호 원리 설명 | 일방향성, 모듈러 거듭제곱, 개인키 역산 | 암호화와 서명 방향 혼동 |
| RSA·DH·ECC 근거 구분 | 소인수분해, 이산대수, 타원곡선 이산대수 | 수학 난제 혼용 |

> 요약: 암호 수학은 계산하기 쉬운 방향과 역산하기 어려운 방향의 차이를 이용해 공개키 암호의 안전성을 만듦

## Ⅱ. 특징/비교

| 판단 기준 | RSA | Diffie-Hellman/DSA | ECC |
|:---|:---|:---|:---|
| 기반 난제 | 큰 수의 소인수분해 | 유한체 이산대수 | 타원곡선 이산대수 |
| 주요 용도 | 암호화, 서명, 키 교환 기반 | 키 교환, 전자서명 | 경량 키 교환과 서명 |
| 키 크기 특성 | 동일 보안 강도에서 키가 큼 | 파라미터 선택이 중요함 | 상대적으로 짧은 키로 보안 강도를 확보함 |
| 선택 기준 | 호환성과 레거시 지원 | 표준 프로토콜 요구 | 모바일·IoT 등 자원 제약 환경 |

> 요약: 공개키 알고리즘은 사용하는 난제와 키 크기 특성이 다르므로 호환성, 성능, 장기 안전성을 기준으로 선택함

- **암호화 방향**: 기밀성은 상대 공개키로 암호화하고 상대 개인키로 복호화함
- **서명 방향**: 인증과 부인방지는 개인키로 서명하고 공개키로 검증함
- **보안 기준**: 알고리즘 이름보다 키 길이, 패딩, 난수 품질, 구현 안전성이 함께 맞아야 함

## Ⅲ. 구성요소

```text
+-------------+      +-------------+      +-------------+
| Prime /     | ---> | Modular     | ---> | Key Pair    |
| Group Param |      | Arithmetic  |      | pub / priv  |
+------+------+      +------+------+      +------+------+
       |                    |                    |
       v                    v                    v
+-------------+      +-------------+      +-------------+
| Hard        | ---> | Encrypt /   | ---> | Verify /    |
| Problem     |      | Decrypt     |      | Sign        |
+-------------+      +-------------+      +-------------+
```

| 구성요소 | 설명 | 비유 |
|:---|:---|:---|
| 난제 파라미터 | 소수, 군, 곡선 같은 안전성의 수학적 기반을 정함 | 자물쇠 재료 |
| 모듈러 연산 | 거듭제곱, 곱셈 역원, 나머지 연산으로 암호 연산을 수행함 | 기계 장치 |
| 공개키·개인키 | 공개 가능한 값과 비밀로 보관해야 하는 값을 짝으로 구성함 | 자물쇠와 열쇠 |
| 패딩·난수 | 결정적 암호화와 구조적 공격을 막기 위해 무작위성과 형식을 제공함 | 완충 포장 |
| 암호 프로토콜 | TLS, 전자서명, 키 교환에서 수학 연산을 절차화함 | 사용 매뉴얼 |

> 요약: 공개키 암호는 난제 파라미터와 모듈러 연산으로 키 쌍을 만들고 패딩·프로토콜로 안전한 사용 절차를 구성함

## Ⅳ. 절차

```text
+-----------+     +-----------+     +-----------+     +-----------+
| Generate  | --> | Publish   | --> | Encrypt / | --> | Decrypt / |
| Key Pair  |     | Pub Key   |     | Sign      |     | Verify    |
+-----------+     +-----------+     +-----------+     +-----------+
      |                 |                 |                 |
      v                 v                 v                 v
random params      certificate       modular op         valid result
```

1. **파라미터·키 생성**: 안전한 난수로 소수 또는 곡선 파라미터를 선택하고 공개키·개인키 쌍을 생성함
2. **공개키 배포**: 인증서나 신뢰 체계를 통해 공개키가 실제 소유자와 연결됨을 보장함
3. **암호화·서명 수행**: 기밀성은 공개키 암호화, 인증은 개인키 서명으로 목적에 맞는 방향의 연산을 수행함
4. **복호화·검증**: 수신자는 개인키로 복호화하거나 공개키로 서명을 검증하고 실패 시 연결을 거부함

> 요약: 공개키 암호는 안전한 키 생성과 신뢰된 공개키 배포를 전제로 암호화·서명 목적에 맞게 연산 방향을 달리함

## Ⅴ. 문제점

- **P1 양자 알고리즘 위협**: 쇼어 알고리즘은 충분한 규모의 오류 정정 양자컴퓨터에서 소인수분해와 이산대수를 다항 시간에 풀 수 있음
- **P2 구현 취약성**: 난제 자체가 안전해도 패딩 오류, 난수 재사용, 타이밍 차이 같은 구현 결함으로 개인키가 노출될 수 있음
- **P3 성능·키 관리 부담**: 공개키 연산은 대칭키보다 느리고 인증서, 개인키 보관, 교체 주기 관리가 필요함

> 요약: 암호 수학의 실무 위험은 수학 난제 약화, 구현 오류, 키 생명주기 관리 실패에서 발생함

## Ⅵ. 개선방안

- **P1 대응**: PQC 전환 계획, 하이브리드 키 교환, crypto-agility 구조를 도입함 (확인: 알고리즘 교체 가능성, PQC 적용 범위)
- **P2 대응**: 검증된 라이브러리, 안전한 패딩, 상수 시간 구현, 난수 품질 점검을 적용함 (확인: 취약점 스캔, side-channel 테스트)
- **P3 대응**: 세션키에는 대칭키를 사용하고 공개키는 키 교환·서명에 제한하며 HSM과 인증서 자동화를 도입함 (확인: 키 회전 준수율)

> 요약: 수학적 안전성뿐 아니라 구현 안전성, 알고리즘 민첩성, 키 운영 자동화가 함께 갖춰져야 공개키 암호가 안전해짐

## Ⅶ. 전망

- **발전 방향**: 공개키 암호는 RSA/ECC와 PQC가 병행되는 전환기를 거치며 하이브리드 프로토콜과 자동 교체 체계가 중요해질 전망임
- **설계 관점**: 보안 강도, 장기 기밀성, 성능, 표준 지원, 알고리즘 교체 가능성을 기준으로 RSA, ECC, PQC, 하이브리드 방식을 선택해야 함
- **검증 관점**: 키 길이, 난수 품질, 패딩 안전성, side-channel 테스트, 인증서 체인 검증을 확인해야 수학 난제와 구현 안전성을 함께 판단할 수 있음
- **운영 관점**: HSM, 인증서 자동화, 키 회전, 폐기 절차, crypto inventory를 운영해야 알고리즘 전환과 사고 대응이 가능함
- **적용 관점**: 세션 데이터 암호화는 대칭키로 처리하고 공개키는 키 교환·서명·인증에 제한해 성능과 키 관리 부담을 줄여야 함
- **보안·신뢰 관점**: 패딩 오라클, 타이밍 차이, 난수 재사용, 양자 위협이 실제 위험이므로 검증된 라이브러리와 crypto-agility가 필요함
- **기술사 제언**: 답안에서는 RSA 수식만 적기보다 기반 난제, 연산 방향, 구현 취약성, 양자 위협, PQC 대응까지 연결해야 함
