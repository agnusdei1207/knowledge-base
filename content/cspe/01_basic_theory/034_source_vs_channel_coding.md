# 소스 코딩 vs 채널 코딩 (Source Coding vs Channel Coding)

## 미리 알고가기

- **중복성(redundancy)**: 없어도 원본을 되살릴 수 있는, 뻔해서 예측되는 부분. 소스 코딩은 이 낭비를 걷어내고, 채널 코딩은 이걸 일부러 계산해 다시 붙인다는 점이 이 노트의 핵심 대비다.
- **엔트로피(entropy)**: 정보원이 실제로 담은 정보의 진짜 양. 아무리 잘 압축해도 이보다 더 줄일 수 없는 하한선이다.
- **채널 용량(channel capacity)**: 잡음이 있는 통로로 오류 없이 밀어 넣을 수 있는 최대 전송률. Shannon이 정의한 상한선이다.
- **BER(Bit Error Rate)**: 전송한 비트 중 뒤집혀 도착한 비율. 채널 코딩이 얼마나 잘 지켜 냈는지를 재는 눈금이다.

## 1. 개요

- **정의/개념**: 소스 코딩(source coding)은 정보원에서 예측 가능한 중복을 걷어내 데이터량 자체를 줄이는 압축 과정이고, 채널 코딩(channel coding)은 전송 중 생길 오류에 대비해 규칙적으로 계산한 여분 비트를 덧붙여 원본을 지켜 내는 보호 과정이다.
- **배경/필요성**: 데이터를 보내거나 저장할 때 우리는 되도록 작게, 그리고 되도록 안전하게라는 정반대 두 가지를 동시에 원한다. 그런데 무작정 작게 줄이면 남은 비트 하나하나가 정보로 꽉 차서 중간에 한 비트만 뒤집혀도 원본이 크게 망가지고, 반대로 안전하려고 백업 비트를 잔뜩 붙이면 전송량이 불어나 느리고 비싸진다. 그래서 두 목적을 한 덩어리로 뭉치지 않고, 먼저 소스 코딩이 있으나 마나 한 중복을 걷어내 알맹이만 남긴 뒤 채널 코딩이 오류를 짚어 낼 여분 비트를 다시 붙이는 식으로 단계를 나눈다. 같은 '중복'이라도 앞은 버려야 할 낭비, 뒤는 지켜야 할 안전장치라는 점이 갈림길이다.

## 2. 특징 및 비교

두 코딩은 똑같이 비트열을 주무르지만 손대는 방향이 정반대다. 소스 코딩은 짐가방을 눌러 공기를 빼듯 줄이고, 채널 코딩은 그 짐을 뽁뽁이로 감싸듯 늘린다. 그래서 둘은 경쟁 기술이 아니라, 압축한 알맹이를 안전하게 실어 보내려고 이어 붙이는 앞뒤 공정이다.

| 판단 기준 | 소스 코딩 | 채널 코딩 |
|:---|:---|:---|
| 목적 | 예측되는 중복을 걷어내 데이터량을 줄임 | 계산된 여분 비트로 오류를 검출·정정 |
| 비트열 방향 | 짧게 압축 | 길게 보강 |
| 이론 한계 | 엔트로피(더 못 줄이는 하한) | 채널 용량(오류 없이 보내는 상한) |
| 대표 기법 | Huffman, RLE(Run-Length Encoding), LZ(Lempel-Ziv) | Hamming, CRC(Cyclic Redundancy Check), LDPC(Low-Density Parity-Check) |
| 확인 지표 | 압축률, 복원 품질 | BER, FER(Frame Error Rate), 복구율 |

> 요약: 소스 코딩은 엔트로피까지 줄이는 압축, 채널 코딩은 채널 용량 안에서 지켜 내는 보호다.

여기서 헷갈리기 쉬운 대목이 '중복'이라는 같은 단어다. 소스 코딩이 없애는 중복은 한국어에서 특정 글자 뒤에 올 글자가 뻔히 예측되는 것처럼 정보가 없는 낭비여서 지워도 복원된다. 반면 채널 코딩이 더하는 중복은 어느 비트가 틀렸는지 역으로 짚어 내도록 수학적으로 설계한 패리티라서, 지우면 오히려 오류를 못 잡는다. 그래서 실제 선택은 데이터에 낭비 중복이 얼마나 있는지, 채널 오류율이 얼마나 높은지, 지연을 얼마나 참을 수 있는지로 갈린다.

## 3. 구성요소/구조

송신 측은 소스 인코더로 짧게 누른 뒤 채널 인코더로 안전 비트를 덧대 잡음 낀 채널로 내보내고, 수신 측은 채널 디코더가 먼저 오류를 바로잡은 뒤 소스 디코더가 압축을 풀어 원본으로 되돌린다.

```text
  [원본] -> [소스 인코더] -> [채널 인코더] -> [ 채널 ] -> [채널 디코더] -> [소스 디코더] -> [복원]
              중복 제거        여분 비트 추가      잡음        오류 정정         압축 해제
```

| 구성요소 | 하는 일 | 왜 중요한가 |
|:---|:---|:---|
| 소스 인코더 | 예측되는 중복을 걷어내 데이터량을 줄임 | 압축률이 곧 전송·저장 비용을 좌우 |
| 채널 인코더 | 규칙적으로 계산한 여분 비트를 덧붙임 | 이 여분이 있어야 수신 측이 오류를 짚음 |
| 채널(Channel) | 잡음이 섞여 비트가 뒤집히는 전송·저장 매체 | 오류가 생기는 지점, 코딩이 대비하는 대상 |
| 채널 디코더 | 여분 비트로 오류를 검출·정정 | 압축을 풀기 전에 먼저 원본 비트를 복구 |
| 소스 디코더 | 압축을 되돌려 원본 데이터로 환원 | 오류가 남으면 복원 품질이 무너짐 |

> 요약: 압축(소스)이 안쪽, 보호(채널)가 바깥쪽에 놓여 수신 측에서는 정확히 역순으로 풀린다.

이 순서를 잡아야 압축률과 오류율을 같은 저울에 올려놓는 착각을 피한다. 소스 코딩의 성패는 엔트로피에 얼마나 다가갔느냐로, 채널 코딩의 성패는 채널 용량 안에서 BER을 얼마나 낮췄느냐로 따로 재야 한다.

## 4. 문제점 및 개선방안

1. **두 코딩의 목적을 뒤섞음**: 압축 기법으로 오류를 잡으려 하거나 오류 정정 코드로 데이터량을 줄이려 하면, 서로 반대 방향의 도구를 엉뚱한 곳에 써서 설계가 통째로 어긋난다.
   - **개선방안**: 엔트로피 기반 압축 구간과 채널 용량 기반 보호 구간을 분리해, 소스 코딩 뒤에 채널 코딩을 두는 순서를 고정한다. (확인: 압축률과 BER을 각각 별도 지표로 측정)

2. **과압축이 오류에 취약**: 알맹이만 남기고 바짝 누른 비트열은 한 비트만 손상돼도 뒤따르는 복호가 연쇄로 어긋나 큰 구간이 깨질 수 있다.
   - **개선방안**: 압축 결과를 블록으로 끊고 각 블록에 체크섬과 채널 코딩을 압축 이후 단계에 배치해 손상 전파를 한 블록 안에 가둔다. (확인: 블록당 복호 실패율)

3. **보호 비트 과다로 유효 전송률 저하**: 채널이 깨끗한데도 여분 비트를 두껍게 붙이면 정작 실어 나르는 알맹이 비율이 줄어 처리량이 떨어진다.
   - **개선방안**: 채널 상태를 재서 오류율이 높으면 여분을 늘리고 낮으면 줄이는 적응형 부호율(adaptive coding rate)을 적용한다. (확인: 채널 상태별 유효 전송률)

## 5. 실무 적용 사례

| 적용 영역 | 어떻게 쓰나 | 무엇으로 효과를 확인하나 |
|:---|:---|:---|
| 이동통신(LTE·5G) | 음성·영상을 코덱으로 압축한 뒤 LDPC·Turbo 부호로 무선 오류를 정정 | BER, 유효 전송률(bitrate) |
| 저장장치(SSD·디스크) | 데이터를 압축해 용량을 아끼고 ECC로 셀 오류를 복구 | 저장률, 복구율 |
| 실시간 스트리밍 | 코덱으로 압축하고 FEC(Forward Error Correction) 강도를 네트워크 상태에 맞춰 조정 | 재생 지연, 재전송률 |

> 요약: 압축으로 실어 나를 양을 줄이고, 채널 코딩으로 그 양이 깨지지 않게 지키는 조합이 통신·저장 전반의 기본 골격이다.

## 6. 결론

소스 코딩과 채널 코딩은 똑같이 정보 표현을 바꾸지만 목적이 정반대여서, 하나는 낭비 중복을 걷어내 엔트로피까지 줄이고 다른 하나는 계산된 중복을 더해 채널 용량 안에서 원본을 지킨다. 그래서 시스템 설계의 출발점은 '줄일 것인가 지킬 것인가'를 먼저 갈라 소스 코딩을 안쪽, 채널 코딩을 바깥쪽에 고정하는 것이고, 이후 데이터의 중복성과 채널 오류율을 재서 압축 강도와 부호율을 함께 맞춰야 효율과 신뢰성 사이에서 흔들리지 않는다.
