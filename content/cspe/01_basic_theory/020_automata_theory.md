## 미리 알고가기

- 알파벳: 오토마타가 입력으로 읽을 수 있는 기호의 유한 집합임
- 상태: 입력을 읽는 동안 현재까지의 처리 정보를 추상화한 위치임
- 전이 함수: 현재 상태와 입력 기호를 다음 상태로 바꾸는 규칙임
- 시작 상태: 입력 처리의 출발점이 되는 상태임
- 수용 상태: 입력 문자열을 받아들인다고 판단하는 종료 상태 집합임

## Ⅰ. 개요

- **정의**: 오토마타 이론은 입력 문자열을 상태와 전이 규칙에 따라 처리해 수용 또는 거부를 판단하는 계산 모델을 연구하는 이론임. DFA와 NFA 같은 유한 오토마타는 정규 언어 수준의 패턴, 토큰, 프로토콜 상태를 명확한 기준으로 인식·검증하기 위해 사용함.
- **배경/필요성**: 오토마타는 실제 컴퓨터 구현을 단순화한 모델이지만, 컴파일러 어휘 분석, 정규식 처리, 통신 프로토콜 검증처럼 상태 전이가 핵심인 시스템 설계의 기초가 됨. 어떤 언어를 표현할 수 있는지와 결정성 여부를 구분하는 것이 중요함.
- **비유**: 입력 문자를 하나씩 읽으며 규칙표에 따라 방을 이동하고, 마지막에 도착한 방이 승인 방이면 통과시키는 검사기와 같음.

| 출제 의도 | 반드시 짚을 핵심 | 감점 회피 포인트 |
|:---|:---|:---|
| 형식언어와 계산 모델 기초 확인 | 상태, 전이, DFA/NFA, 수용 조건, 표현 한계 | 정규식과 문맥자유문법 혼동 |

> 요약: 오토마타는 문자열을 상태 전이로 처리해 언어 수용 여부를 판단하는 형식 계산 모델임.

## Ⅱ. 특징/비교

| 판단 기준 | DFA | NFA | 푸시다운 오토마타 |
|:---|:---|:---|:---|
| 전이 방식 | 상태와 입력마다 다음 상태가 하나로 결정 | 여러 다음 상태 또는 epsilon 전이 가능 | 스택 상태까지 함께 사용 |
| 표현 언어 | 정규 언어 | 정규 언어 | 문맥자유 언어 |
| 구현 관점 | 실행이 단순하고 빠름 | 설계와 표현이 간결할 수 있음 | 중첩 구조 표현 가능 |
| 변환 관계 | NFA를 부분집합 구성으로 DFA화 가능 | DFA보다 표현이 짧을 수 있음 | 유한 오토마타보다 강함 |
| 선택 기준 | 실행 엔진과 검증 단순성 | 패턴 설계와 이론 증명 | 괄호처럼 중첩 구조 필요 |

> 요약: DFA와 NFA는 표현 방식은 다르지만 같은 정규 언어를 인식하며, 스택이 필요한 구조는 더 강한 모델이 필요함.

- DFA는 실행 중 현재 상태가 항상 하나라 구현이 명확함
- NFA는 여러 가능 상태를 동시에 고려하지만, 이론적으로 DFA로 변환 가능함
- 유한 오토마타는 무한한 중첩 깊이를 기억할 수 없어 괄호 짝 같은 문맥자유 구조에는 한계가 있음

## Ⅲ. 구성요소

```text
+----------+      +----------+      +----------+
| 입력문자 | ---> | 현재상태 | ---> | 다음상태 |
+----------+      +----------+      +----------+
      |                 |                 |
      v                 v                 v
+----------+      +----------+      +----------+
| 알파벳   |      | 전이함수 |      | 수용판정 |
+----------+      +----------+      +----------+
```

| 구성요소 | 설명 | 비유 |
|:---|:---|:---|
| 알파벳 | 입력 문자열을 구성하는 허용 기호 집합임 | 검사 가능한 문자표 |
| 상태 집합 | 입력 처리 중 가능한 내부 위치의 유한 집합임 | 검사실 목록 |
| 전이 함수 | 현재 상태와 입력 기호를 다음 상태로 매핑하는 규칙임 | 이동 안내표 |
| 시작 상태 | 입력을 읽기 전 최초로 위치하는 상태임 | 출발 방 |
| 수용 상태 | 입력을 모두 읽은 뒤 도착하면 문자열을 인정하는 상태임 | 승인 방 |

> 요약: 오토마타는 알파벳, 상태 집합, 전이 함수, 시작·수용 상태로 입력 문자열의 수용 여부를 결정하는 구조임.

- DFA의 전이 함수는 하나의 다음 상태를 반환하고, NFA는 상태 집합 또는 epsilon 이동을 허용함
- 입력을 모두 소비한 뒤의 상태가 수용 상태인지가 최종 판정 기준임
- 정규 표현식, NFA, DFA는 서로 변환 가능해 같은 정규 언어를 다른 관점에서 표현함

## Ⅳ. 절차

```text
+----------+      +----------+      +----------+      +----------+
| 모델정의 | ---> | 입력읽기 | ---> | 상태전이 | ---> | 수용판정 |
+----------+      +----------+      +----------+      +----------+
      |                 |                 |                 |
      v                 v                 v                 v
+----------+      +----------+      +----------+      +----------+
| 상태/전이|      | 기호순회 |      | 규칙적용 |      | 승인/거부|
+----------+      +----------+      +----------+      +----------+
```

1. **입력/요구 식별** - 인식할 언어의 패턴, 알파벳, 수용 조건이 정규 언어 수준인지 확인함
2. **상태와 전이 설계** - 필요한 기억 정보를 상태로 정의하고 각 입력 기호에 대한 전이 규칙을 작성함
3. **문자열 처리** - 시작 상태에서 입력 기호를 순서대로 읽으며 전이 함수를 적용함
4. **검증/출력** - 입력을 모두 읽은 뒤 현재 상태 또는 가능 상태 집합이 수용 상태인지 판정함

> 요약: 오토마타 절차는 언어 조건을 상태 전이표로 만들고 입력 기호를 순서대로 적용해 수용 여부를 결정하는 흐름임.

- NFA 실행은 가능 상태 집합을 갱신하거나 DFA로 변환한 뒤 실행할 수 있음
- DFA 최소화는 같은 언어를 인식하는 상태 수를 줄여 구현 비용을 낮춤
- 전이표에 누락 상태가 있으면 정의되지 않은 입력 처리가 생기므로 sink state를 둘 수 있음

## Ⅴ. 문제점

- **P1 상태 폭발**: NFA를 DFA로 변환할 때 가능 상태 집합 조합 때문에 상태 수가 지수적으로 늘어날 수 있음
- **P2 표현력 한계**: 유한 오토마타는 제한 없는 중첩, 개수 일치, 재귀 구조처럼 정규 언어를 넘는 패턴을 표현하지 못함
- **P3 전이 정의 누락**: 일부 입력 기호나 상태 조합의 전이가 빠지면 구현에서 예외 처리나 잘못된 수용 판정이 발생함

> 요약: 오토마타 적용 문제는 상태 수 증가, 언어 표현 한계, 전이표 완전성에서 발생함.

## Ⅵ. 개선방안

- **P1 대응**: 필요한 경우 NFA 직접 시뮬레이션, lazy DFA, DFA 최소화, 상태 동치 병합을 적용함 (확인: 상태 수와 메모리 사용량)
- **P2 대응**: 중첩 구조는 푸시다운 오토마타, 문맥자유문법, 파서로 전환하고 정규식 적용 범위를 제한함 (확인: 언어 계층 분류)
- **P3 대응**: 전이표 완전성 검토, sink state 추가, 상태별 테스트 문자열로 수용·거부 사례를 검증함 (확인: 전이 커버리지)

> 요약: 오토마타 개선은 상태 수를 관리하고, 표현 한계를 넘는 요구는 더 강한 형식 모델로 분리하는 것임.

## Ⅶ. 전망

- **발전 방향**: 정규식 엔진, 컴파일러, 프로토콜 검증, 모델 체킹에서는 오토마타 기반 표현과 자동 검증이 계속 확대됨
- **기술사적 판단**: DFA/NFA의 변환 가능성과 정규 언어 한계를 함께 설명해야 실제 적용 범위를 판단할 수 있음
- **기술사 제언**: 답안에서는 상태 전이 도식과 구성요소 5개를 먼저 제시하고, 표현력 한계와 파서 전환 기준을 덧붙이면 완성도가 높아짐
