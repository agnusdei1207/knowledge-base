# 📖 【암기용】 개념 완전 이해
> 목적: IEEE 754 부동소수점 표현을 처음 봐도 완전히 이해하게 만든다. 시험 답안 양식이 아니라, 이해를 위한 친절한 설명이다.

## 한눈에
- **개요**: **IEEE 754 부동소수점의 반올림 오차(Rounding Error)**는 실수를 부호·지수·가수 유한 비트로 근사 저장할 때, 2진수로 유한하게 표현되지 않는 소수를 잘라내면서 필연적으로 발생하는 정밀도 손실이다.
- **왜 필요한가**: 부동소수점은 "정확한 값"이 아니라 "가장 가까운 표현 가능한 값"으로 반올림해 저장한다. 이 오차의 발생 원리를 모르면 `0.1 + 0.2 == 0.3`이 거짓이 되는 이유를 이해할 수 없고, 금융·AI 등 도메인별로 왜 다른 정밀도를 선택하는지도 판단할 수 없다.
- **핵심 직관**: 10진수가 2진수로 딱 떨어지지 않으면(예: 0.1), 유한한 가수 비트 안에서 어딘가 잘려나가야 한다 — 그 잘린 부분이 오차다.

## 핵심 용어 정리 (내부에 등장하는 것들)

| 용어 | 의미 | 비유 |
|:---|:---|:---|
| IEEE 754 | 부호·지수·가수로 실수를 근사 저장하는 부동소수점 표준(이 개념의 상위 개념) | 실수 저장 공용 규격 |
| 반올림 오차(Rounding Error) | 유한 가수 비트에 담기지 않는 나머지를 버리면서 생기는 근사 오차 | 자로 잴 때 눈금 사이 값을 어림잡아 읽는 것 |
| 정규화(Normalization) | `1.xxx × 2^E` 꼴로 맞추는 저장 전 필수 단계 | 모든 숫자를 같은 틀에 맞춰 정렬 |
| 가수(Mantissa/Fraction) | 유효숫자를 담는 필드(단정도 23비트) — 정밀도의 한계를 결정 | 자에 새겨진 눈금 칸 수 |
| 바이어스 지수(Biased Exponent) | 표현 범위를 결정하는 필드(단정도 127, 배정도 1023) | 확대·축소 배율 |
| 기계 엡실론(Machine Epsilon) | 1.0과 그다음으로 표현 가능한 값의 차이 — 이보다 작은 차이는 구분 불가 | 저울이 구분할 수 있는 최소 눈금 |
| ULP(Unit in the Last Place) | 가수 최하위 1비트가 나타내는 실제 크기 — 오차를 비트 단위로 잰 것 | 눈금 한 칸의 실제 길이 |
| Subnormal(비정규화수) | 지수가 최솟값(전부 0)일 때 Hidden Bit 없이 0 근처를 표현하는 특수 형태 | 저울 눈금이 바닥에 닿아 정밀도가 더 떨어지는 구간 |
| NaN / Infinity | 정의 불가 연산(0/0 등) 및 오버플로우 결과를 나타내는 특수 비트패턴(지수 전부 1) | 계산 불가·범위 초과 경고 표시등 |
| Decimal / BigDecimal | 10진 자릿수를 그대로 저장해 2진 근사 오차를 원천 차단하는 자료형 | 분수 대신 정확한 소수점 장부 |
| FP16 / BF16 | AI 연산에서 메모리·속도를 위해 가수 비트를 줄인 저정밀 포맷 | 정밀도를 낮춘 대신 더 빨리 그리는 스케치 |

## 깊이 이해

### 오차는 어디서 시작되는가 — 2진수로 안 떨어지는 소수
- 10진 소수 0.1을 2진수로 바꾸는 과정: 0.1×2=0.2→0, 0.2×2=0.4→0, 0.4×2=0.8→0, 0.8×2=1.6→1, 0.6×2=1.2→1, 0.2×2=0.4→0(여기서부터 반복). 즉 0.1 = 0.000110011001100110011...₂로 "0011"이 무한히 반복되는 순환소수다.
- 10진수에서 1/3이 0.333...으로 무한 반복되듯, 2진수에서는 분모가 2의 거듭제곱이 아닌 소수(0.1=1/10, 분모에 5가 있음)가 전부 순환소수가 된다. 가수 필드는 23비트(단정도)·52비트(배정도)로 유한하므로, 이 무한소수는 그 자리에서 반올림되어 저장된다 — 저장되는 순간 이미 원래 값과 미세하게 달라진다.
- 그래서 `0.1`과 `0.2`를 각각 반올림 저장한 뒤 더하면 두 근사값의 오차가 합쳐져 `0.30000000000000004` 같은 결과가 나온다. 수학적으로는 0.3이지만, 비트 패턴으로는 0.3을 직접 반올림 저장한 값과 다르다 — 그래서 `0.1 + 0.2 == 0.3`이 대부분의 언어에서 거짓이다.

### 워크드 예제 — 유한소수 12.375는 왜 오차 없이 표현되는가
1. 12.375를 이진수로: 정수부 12 = 1100₂. 소수부 0.375 = 0.25+0.125 → 0.011₂. 합치면 1100.011₂.
2. 정규화: 1100.011₂ = 1.100011 × 2³ (소수점을 왼쪽으로 3칸 옮겼으므로 지수는 3).
3. 부호: 양수이므로 S=0. 지수 = 3 + 127(바이어스) = 130 → 10000010₂(128+2=130).
4. 가수: 선행 1을 뗀 나머지 "100011"을 23비트가 되도록 0으로 채운다 → 10001100000000000000000.
5. 최종 비트패턴: `0 10000010 10001100000000000000000`
6. 검산: 가수 복원 1.100011₂ = 1 + 0.5 + 0.03125 + 0.015625 = 1.546875. 1.546875 × 2³ = 12.375 — 원래 값과 정확히 일치한다.
7. 이처럼 12.375는 소수부(0.375=3/8)의 분모가 2의 거듭제곱이라 2진수로 유한하게 끝나므로 반올림 없이 **정확히** 표현된다. 반면 0.1은 분모에 5가 섞여 있어 가수 비트를 아무리 늘려도 정확히 끝나지 않는다 — 이것이 "어떤 소수는 정확하고 어떤 소수는 오차가 나는지"를 가르는 기준이다.

### 기계 엡실론과 ULP — 오차의 크기를 재는 자
- 가수 비트가 유한하다는 것은 어떤 값 근처에서 "다음으로 표현 가능한 값"까지 간격이 있다는 뜻이다. 이 간격을 ULP(Unit in the Last Place)라 부르고, 1.0 기준 ULP를 기계 엡실론이라 한다(단정도 약 2⁻²³ ≈ 1.19×10⁻⁷).
- 값이 커질수록(지수가 커질수록) 같은 가수 비트 수로 더 넓은 범위를 나눠 표현해야 하므로 ULP도 커진다 — 큰 수일수록 절대오차는 커지고 작은 수일수록 절대오차는 작아진다(상대오차는 대체로 일정하다).
- 그래서 부동소수점을 비교할 때 `a == b` 절대 비교 대신 `abs(a-b) < epsilon` 형태의 오차 허용 비교를 쓴다. 다만 epsilon도 고정값이 아니라 값의 크기(ULP)에 비례해 조정해야 정확하다.

### 왜 도메인마다 다른 정밀도를 선택하는가
- **금융**: 원 단위·소수점 이하 결제 금액은 오차가 절대 허용되지 않는다. 2진 근사 오차가 회계 감사에서 치명적이므로, 부동소수점 대신 10진 자릿수를 그대로 저장하는 Decimal/BigDecimal을 쓴다 — 2진 변환 자체를 하지 않으므로 0.1 문제가 원천적으로 없다.
- **과학 계산**: 반복 연산에서 오차가 누적되므로 가수 비트가 넓은 배정도(Float64, 52비트)를 쓰거나, Kahan summation처럼 오차를 보정하는 알고리즘을 함께 쓴다.
- **AI 추론/학습**: 신경망은 개별 값의 정밀도보다 전체 통계적 경향이 중요하고, 파라미터 수가 수십억 개라 메모리·연산량이 병목이다. 그래서 가수 비트를 줄인 FP16(가수 10비트)이나, 가수는 더 줄이되 지수는 FP32와 같이 유지한 BF16(가수 7비트, 지수 8비트)을 써서 표현 범위는 유지하면서 메모리를 절반으로 줄인다.
- **그래픽스**: 화면에 그려지는 좌표는 사람 눈으로 구분 안 되는 수준의 오차는 허용되므로 속도가 더 중요한 단정도(Float32)를 쓴다.

### 특수값이 오차 처리에서 하는 역할
- 지수 필드가 전부 1이고 가수가 0이면 Infinity, 가수가 0이 아니면 NaN이다. 오버플로우(범위 초과) 결과는 프로그램을 죽이는 대신 Infinity로 이어지고, 0/0처럼 정의되지 않는 연산은 NaN으로 전파된다. 이 전파 성질 때문에 연산 체인 어딘가에 NaN이 섞이면 이후 모든 결과가 NaN이 되므로, 입력 검증(NaN guard)이 필요하다.
- 지수 필드가 전부 0이고 가수가 0이 아니면 Subnormal이다. 0에 아주 가까운 값에서 Hidden Bit(암묵 선행 1)를 포기하고 암묵 선행 0으로 처리해, 0으로 뚝 끊기지 않고 서서히 정밀도를 잃으며 언더플로우하게 만든다 — 이 구간에서는 유효숫자가 줄어들어 오차가 더 커진다.

### 비유
- 부동소수점의 반올림 오차는 "눈금이 1mm 단위인 자로 0.1mm 단위 길이를 재는 것"과 같다. 눈금 사이 값은 가장 가까운 눈금으로 어림잡아 읽을 수밖에 없고, 그 어림값들을 여러 번 더하면 오차가 쌓인다. 금융에서 정밀 저울(Decimal)을 따로 쓰는 이유도, AI에서 대충 눈대중(FP16)으로도 충분한 이유도 이 비유로 설명된다.

## 연결 개념
- 수치해석 오차 — 반올림·절단·누적 오차 분석(부동소수점 오차의 상위 이론)
- 정수 보수 표현 — 고정 폭 비트 해석과의 비교(오차 없는 정수 연산과의 대조)
- 수 체계 변환 — 10진 실수와 2진 소수 변환(순환소수 발생의 근본 원인)

> 2. **가치**: CPU·GPU·DB·프로그래밍 언어 간 실수 연산 표현과 예외 처리를 통일함
> 3. **판단 포인트**: 정밀도, 반올림 모드, NaN/Infinity, 비교 오차 허용값을 함께 설계해야 함

## Ⅰ. 개요 및 필요성

- 개요: 실수를 부호·지수·가수 비트로 나누어 표현하는 국제 표준
- 배경: 금융·과학 계산·AI 추론에서 반복되는 실수 연산은 표현 범위와 정밀도 한계를 이해하지 못하면 비교 오류·누적 오차로 이어짐
- 필요성: 표준 기반 표현과 예외 처리(NaN, Infinity, 반올림 모드 명시)로 오차를 통제

---

## Ⅱ. 구조 및 구성요소

```text
32비트 단정도(Float)
Sign 1bit -> Exponent 8bit -> Fraction 23bit
값 = (-1)^S × 1.F × 2^(E-127)
```

| 구성요소 | 역할 | 특이사항 |
|:---|:---|:---|
| 부호 S | 양수·음수 구분 | 0=양수, 1=음수 |
| 지수 E | 크기 범위 표현 | 단정도 bias 127, 배정도 bias 1023 |
| 가수 F | 유효숫자 정밀도 표현 | 단정도 23비트, 숨은 1 사용 |
| 특수값 | 예외 상태 표현 | ±0, ±∞, NaN, Subnormal |

> 요약: IEEE 754는 32비트 기준 부호 1·지수 8·가수 23비트로 범위와 정밀도를 분리함

---

## Ⅲ. 동작원리 및 흐름도

```text
10진 실수 -> 2진 변환 -> 정규화(1.x×2^e)
-> bias 지수 저장 -> 가수 반올림 -> 특수값/오차 확인
```

| 단계 | 처리 내용 | 검증 기준 |
|:---:|:---|:---|
| 1 | 부호 결정 및 절댓값 변환 | S=0 또는 1 |
| 2 | 2진 실수로 변환 | 정수부 나눗셈, 소수부 ×2 반복 |
| 3 | `1.F × 2^e`로 정규화 | E=e+bias |
| 4 | 가수 비트 반올림·특수값 판정 | NaN, Infinity, Underflow 확인 |

> 요약: 부동소수점 저장은 2진 변환, 정규화, bias 지수화, 가수 반올림 순서로 진행함

## Ⅳ. 특징

| 구분 | 단정도 Float32 | 배정도 Float64 | 수치·판단 기준 |
|:---|:---|:---|:---|
| 비트 구성 | 1/8/23 | 1/11/52 | 부호/지수/가수 |
| 십진 정밀도 | 약 7자리 | 약 15~16자리 | 센서·그래픽 vs 금융·과학 |
| 지수 bias | 127 | 1023 | 저장 지수=실제 지수+bias |
| 오차 특성 | 반올림 오차 큼 | 반올림 오차 작음 | 비교 시 epsilon 사용 |

> 요약: Float64는 Float32보다 가수 29비트(23->52)가 더 많아 십진 유효자릿수가 7자리에서 15~16자리로 증가함

> 요약: 부동소수점은 범위·처리량·정밀도 중 어느 축이 중요한지에 따라 자료형을 선택함

| 리스크 | 원인 | 대응 방안 | 확인 지표 |
|:---|:---|:---|:---|
| 비교 오류 | 2진 근사와 반올림 | 도메인별 epsilon, ULP 비교 | 비교 실패 재현 건수 |
| 누적 오차 | 반복 합산·소거 | Kahan summation, Float64 기준 검증 | 상대오차 1e-9 이하 |
| 특수값 전파 | NaN/Infinity 미처리 | 입력 검증, NaN guard | NaN 발생률 |

> 요약: 핵심 리스크는 비교·누적·특수값 오류이며, epsilon과 오차율 지표로 통제함

| 점검 항목 | 목표 기준 | 측정 방법 |
|:---|:---|:---|
| 정밀도 | 기준 FP64 대비 상대오차 허용치 | 골든 데이터 비교 |
| 예외 처리 | NaN/Infinity 처리 100% | 단위 테스트 |
| 처리 비용 | 메모리 사용량 32bit 대비 50% 절감 | 프로파일러·벤치마크 |

> 요약: IEEE 754 적용 효과는 상대오차, 예외 처리, 메모리 사용량으로 판단함

## Ⅵ. 실무 적용 및 결론

**적용 방안 3개:**
1. 비교 로직: `a == b` 대신 `abs(a-b) < 1e-9`처럼 도메인별 epsilon을 명시
2. 금융 계산: 금액은 Float 대신 정수 원 단위 또는 Decimal128을 사용해 반올림 규칙을 코드화
3. AI·그래픽 연산: 메모리 대역폭이 병목이면 FP16/BF16, 정밀도 검증은 FP32 기준 오차율 1e-3 이하로 관리

**결론 (2줄):**
- 기술사 판단: 표현 범위가 중요하면 Float32, 정밀도와 누적 오차 통제가 중요하면 Float64 또는 Decimal을 선택함
- 향후 방향: AI 가속기에서는 FP16/BF16/FP8 혼합정밀도를 사용하되, 기준 모델 대비 오차율을 지표로 검증해야 함
