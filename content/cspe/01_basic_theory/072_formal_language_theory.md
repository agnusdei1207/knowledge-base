# 📖 【암기용】 개념 완전 이해

> 목적: 형식 언어 이론을 처음 보는 사람도 완벽히 이해하게 만든다.

## 한눈에
- **개요**: 기호들의 집합에서 특정한 규칙(문법)을 따라 만들어질 수 있는 모든 문자열의 집합을 수학적으로 정의하고 분류하는 이론이다.
- **왜 필요한가**: 컴파일러 설계, 정규 표현식, 자연어 처리 등에서 컴퓨터가 구문과 문맥을 파악하고 처리할 수 있는 수학적 토대를 제공하기 위해 필요하다.
- **핵심 직관**: 인간의 언어에 주어·동사 규칙이 있듯, 컴퓨터가 인식할 수 있는 문자열의 "허락된 패턴 규칙"을 4단계 등급(촘스키 위계)으로 나눈 것이다.

## 핵심 용어 정리

| 용어/표기 | 의미 | 비유·예 |
|:---|:---|:---|
| 기호(Symbol)와 알파벳(Σ) | 언어를 구성하는 기본 문자의 집합 | 알파벳 {a, b, c}, 이진수 {0, 1} |
| 문자열(String/Word) | 기호들이 유한하게 나열된 것 | "aba", "1011" |
| 문법(Grammar) | 문자열을 생성하는 규칙의 집합 (G = {V, T, P, S}) | "S -> aSb" 같은 치환 규칙 |
| 촘스키 위계(Chomsky Hierarchy) | 형식 문법의 제약 조건에 따른 4단계 분류 체계 | "엄격함에 따른 4단계 신분제" |

## 깊이 이해
- **배경·문제의식**: 컴퓨터에게 프로그래밍 언어의 구문을 어떻게 인식시킬 것인가? 유한한 상태를 가진 기계가 무한한 조합의 문자열이 문법에 맞는지 판별할 수 있는 체계적 기준이 필요했다.
- **작동 원리**: 노암 촘스키가 제안한 촘스키 위계는 규칙의 제약에 따라 언어를 Type 3(정규 언어)부터 Type 0(재귀 열거 언어)까지 분류한다. 
  - Type 3 (정규 언어): $A \rightarrow aB$ 형태. 유한 오토마타(FSM)로 인식 가능 (정규표현식)
  - Type 2 (문맥 자유 언어): $A \rightarrow \gamma$ 형태. 푸시다운 오토마타(PDA)로 인식 가능 (대부분의 프로그래밍 언어 구문)
  - Type 1 (문맥 의존 언어): $\alpha A \beta \rightarrow \alpha \gamma \beta$ 형태. 선형 한계 오토마타(LBA)로 인식
  - Type 0 (재귀 열거 언어): 제약 없음. 튜링 머신(TM)으로 인식
- **비유**: Type 3는 기억력 없는 경비원(현재 상태만 봄). Type 2는 스택 메모리(메모장 하나)를 가진 경비원(괄호 짝맞추기 가능). Type 0는 무한한 메모장과 자유도를 가진 슈퍼컴퓨터다.
- **구체 예시**: 프로그래밍 언어에서 `if (a > b) { ... }` 구조는 중첩된 괄호 매칭이 필요하므로 기억력이 없는 정규 언어(Type 3)로는 불가능하며, 문맥 자유 언어(Type 2)로 처리해야 한다.
- **흔한 오해·주의점**: "모든 프로그래밍 언어는 문맥 자유 언어다"는 절반만 맞다. 변수 선언 여부를 확인하는 타입 체킹 같은 의미론적 검사는 문맥 자유 문법의 범위를 넘어 문맥 의존성을 띠며, 이는 파서가 아닌 기호 표(Symbol Table)로 별도 처리한다.

## 연결 개념
- (020) 오토마타 이론 — 각 형식 언어를 인식하는 추상 기계
- (073) 컴파일러 구조 — 어휘 분석(정규 언어)과 구문 분석(문맥 자유 언어)의 응용

# 📝 【답안용】 시험 답안 템플릿

## 핵심 인사이트 (3줄 요약)

> 1. **본질**: 형식 언어 이론은 촘스키 위계(Type 0~3)를 통해 문법의 생성 규칙에 제약을 가하고, 이에 대응하는 오토마타를 수학적으로 정의한 체계다.
> 2. **가치**: 컴파일러의 어휘 분석(Type 3)과 구문 분석(Type 2) 등 소프트웨어 구문 인식의 이론적 한계와 구현 방법을 제공한다.
> 3. **판단 포인트**: 해결하려는 문제의 복잡도에 따라 정규 표현식, 구문 파서, 튜링 머신 중 최적의 인식기를 선택해야 한다.

## 출제 의도 및 답안 포인트

| 출제 의도 | 반드시 짚을 핵심 | 감점 회피 포인트 |
|:---|:---|:---|
| 언어와 인식기의 1:1 매핑 이해 | 촘스키 위계 4단계와 각 오토마타(FSM, PDA, LBA, TM) 대응 | 위계 순서 혼동, 생성 규칙과 인식기의 불일치 |
| 컴파일러 적용 실무 연계 | 어휘 분석 = 정규 문법(FSM), 구문 분석 = 문맥 자유 문법(PDA) 매핑 | 추상적 이론 나열에 그침, 실무(컴파일러) 연계 누락 |

> 요약: 촘스키 위계 4단계를 정확히 분류하고, 각 언어 등급이 실제 컴퓨팅(컴파일러)에서 어떻게 쓰이는지 연결해야 한다.

---

## Ⅰ. 개요 및 필요성

- 개요: 규칙(문법)에 의해 생성될 수 있는 모든 문자열 집합을 정의하고 촘스키 위계에 따라 4단계로 분류하는 수학적 이론
- 배경: 무한한 문자열 중에서 문법적으로 유효한 문장을 컴퓨터(유한 기계)가 판별(인식)하기 위한 형식적 틀이 필요
- 필요성: 프로그래밍 언어 구문 검사, 정규표현식 매칭, 자연어 처리 등 기계적 문자열 처리 알고리즘의 한계 증명 및 최적 설계에 필수적

---

## Ⅱ. 구조 및 구성요소

```text
촘스키 위계 (포함 관계: Type 0 ⊃ Type 1 ⊃ Type 2 ⊃ Type 3)
Type 0 (재귀 열거) -> 튜링 머신 (Turing Machine)
  +-> Type 1 (문맥 의존) -> 선형 한계 오토마타 (LBA)
        +-> Type 2 (문맥 자유) -> 푸시다운 오토마타 (PDA)
              +-> Type 3 (정규) -> 유한 상태 기계 (FSM)
```

| 분류 등급 | 형식 언어 (문법) | 생성 규칙 제약 조건 | 대응 오토마타(인식기) |
|:---|:---|:---|:---|
| Type 0 | 재귀 열거 언어 | 제약 없음 ($\alpha \rightarrow \beta$) | 튜링 머신 (TM) |
| Type 1 | 문맥 의존 언어 | $\|\alpha\| \le \|\beta\|$ (길이가 줄지 않음) | 선형 한계 오토마타 (LBA) |
| Type 2 | 문맥 자유 언어 | $A \rightarrow \gamma$ (좌변이 단일 비단말) | 푸시다운 오토마타 (PDA) |
| Type 3 | 정규 언어 | $A \rightarrow aB$ 또는 $A \rightarrow a$ (우정규) | 유한 오토마타 (FSM) |

> 요약: 위계가 낮을수록(Type 3로 갈수록) 규칙 제약이 엄격하여 표현력은 낮지만, 빠르고 단순한 기계로 파싱이 가능하다.

---

## Ⅲ. 동작원리 및 흐름도

```text
문자열 W 입력 -> 문법 G의 규칙 적용 판별 -> 오토마타 M의 상태 전이 -> 인식(수락) 또는 거부
```

- 1단계 [문자열 입력]: 분석 대상 알파벳 $\Sigma$로 구성된 유한 문자열 $w$ 입력
- 2단계 [인식기 투입]: 해당 언어 계층에 맞는 오토마타(예: PDA) 초기 상태로 세팅
- 3단계 [상태 전이]: 문법 생성 규칙에 매핑된 상태 전이 함수 $\delta$를 따라 입력 기호 소비 및 메모리(스택 등) 갱신
- 4단계 [수락 판별]: 문자열이 끝났을 때 오토마타가 수락 상태(Accept State) 도달 확인 후 처리

> 요약: 문자열은 문법 규칙이 변환된 상태 전이 기계를 통과하며 유효성이 기계적으로 검증된다.

---

## Ⅳ. 특징
- [표현력과 효율성의 트레이드오프]: Type 3(정규)는 $O(N)$ 파싱이 가능하나 중첩 구조를 표현 불가, Type 2(문맥자유)는 $O(N^3)$ 파싱으로 중첩 구조 처리 가능
- [컴파일러 모듈화 기반]: 어휘 분석기(Scanner)는 FSM으로, 구문 분석기(Parser)는 PDA 기반으로 분리 설계 가능하게 함
- [튜링 등가성]: Type 0 문법은 튜링 머신이 계산 가능한 모든 알고리즘을 표현할 수 있음을 증명

> 요약: 이론적 제약이 엄격할수록(Type 3) 결정론적 고속 파싱이 가능하여 실무에 널리 쓰인다.

---

## Ⅴ. 심화 비교 및 적용 판단

| 비교 축 | Type 3 정규 언어 (FSM) | Type 2 문맥 자유 언어 (PDA) | 선택 기준 |
|:---|:---|:---|:---|
| 적용 대상 | 식별자, 키워드, 숫자 추출 | 블록 구조, 괄호 매칭, 연산자 우선순위 | 문자열 매칭인가 구조 파악인가 |
| 사용 도구 | 정규표현식, Lex, Flex | AST 생성, Yacc, Bison | 구문 트리가 필요한지 여부 |
| 한계/단점 | `a^n b^n` (괄호 짝) 인식 불가 | 선언되지 않은 변수 참조 확인 불가 | 메모리(스택 유무) 요구사항 |

> 요약: 컴파일러 설계 시 정규 언어로 토큰을 먼저 분리하고, 문맥 자유 언어로 문법 트리를 구성하는 이원화 전략을 취한다.

**리스크·대응:**
- [문맥 자유 파싱 복잡도 폭증]: 일반 PDA 파싱(CYK 알고리즘)은 $O(N^3)$ 성능 저하 → LL/LR 파서 도입으로 $O(N)$ 결정론적 선형 파싱(지표: 컴파일 속도 향상)
- [정규 표현식 백트래킹 지연]: ReDoS(정규표현식 DOS 공격) 취약점 노출 → NFA 기반 엔진을 DFA 기반 엔진으로 전환하여 $O(N)$ 보장

**도입 후 점검 지표:**
- 성능/효율: 파싱 시간 복잡도 — 토큰당 $O(1)$ 상태 전이 확인
- 품질/운영: 컴파일러 검증 커버리지 — 잘못된 구문(Syntax Error) 탐지율 100%

---

## Ⅵ. 실무 적용 및 결론

**적용 방안 3개:**
1. [어휘 분석 설계]: 식별자, 예약어, 상수 토큰 추출은 정규 언어(Type 3)를 기반으로 Regex 엔진 및 Lex 도구 활용
2. [구문 분석 설계]: IF-ELSE 블록, 수식 중첩 구조는 문맥 자유 문법(Type 2) 기반의 LALR 파서(Bison/Yacc)로 AST(추상 구문 트리) 구축
3. [의미 분석 보완]: 문맥 자유 문법의 한계(Type 1 영역)인 '변수 중복 선언' 등은 심볼 테이블(Symbol Table)을 별도로 두어 검증 보강

**결론:**
- 기술사 판단: 문자열 파싱 문제에 직면했을 때, 불필요하게 복잡한 PDA(문맥자유)를 쓰지 말고, 요구사항이 정규 언어(Type 3)로 해결 가능한지 먼저 판단해야 성능 병목을 막을 수 있다.
- 향후 방향: 최근 대형 언어 모델(LLM)의 등장으로 형식 문법에 의존하지 않는 통계/확률 기반 코드 분석이 도입되고 있으나, 컴파일러의 결정론적 구문 검증은 여전히 촘스키 위계 기반이 필수적이다.
