## Ⅰ. 개요
- **정의**: 동일 작업을 자기 호출(재귀) 또는 루프(반복)로 반복 수행하는 두 가지 제어 흐름 방식
- **배경/필요성**: 문제 구조에 따라 표현 자연스러움·메모리 사용·성능이 달라지므로 적절한 선택이 필수임
- **비유**: 거울 두 개를 마주 놓으면 끝없이 비추는 것이 재귀, 운동장을 한 바퀴씩 도는 것이 반복임

| 출제 의도 | 반드시 짚을 핵심 | 감점 회피 포인트 |
|:---|:---|:---|
| 두 방식의 구조적 차이와 변환 가능성 | 콜 스택 소비·꼬리 재귀 최적화 | 모든 재귀가 꼬리 재귀 최적화 가능한 것은 아님 |

> 요약: 자기 호출과 루프라는 두 반복 전략의 트레이드오프를 이해하는 주제임

## Ⅱ. 구성요소
```text
         제어 흐름
            |
      +-----+-----+
      |           |
    재귀         반복
      |           |
  +---+---+   +---+---+
  |       |   |       |
 기저    재귀  초기화  종료
 조건    호출  조건    조건
```

| 구성요소 | 설명 | 비유 |
|:---|:---|:---|
| 기저 조건 | 재귀 호출을 멈추는 종료 분기 | 마트료시카 인형의 가장 안쪽 인형 |
| 재귀 호출 | 문제를 축소하여 자기 자신을 다시 호출함 | 큰 상자 안의 작은 상자를 계속 여는 것 |
| 초기화 | 반복 변수와 누적값을 루프 진입 전 설정함 | 출발선에 서서 카운터를 0으로 맞추는 것 |
| 종료 조건 | 루프 탈출 여부를 매 반복마다 검사함 | 목표 바퀴 수에 도달하면 멈추는 것 |

> 요약: 재귀는 기저 조건+자기 호출, 반복은 초기화+종료 조건으로 구성됨

## Ⅲ. 절차
```text
  문제 분해        방식 선택       구현            최적화
  (부분 문제)     (재귀/반복)     (코드 작성)     (성능 개선)
    |               |               |               |
    +---판단------->+---적용------->+---측정------->+
  구조 분석       트레이드오프    콜스택/루프     꼬리재귀/메모이제이션
```
- 1단계: 문제를 동일 구조의 부분 문제로 분해 가능한지 분석함
- 2단계: 트리 구조면 재귀, 선형 누적이면 반복 등 문제 형태에 맞는 방식 선택
- 3단계: 선택한 방식으로 구현하고 콜 스택 깊이·루프 횟수를 확인함
- 4단계: 꼬리 재귀 변환·메모이제이션·루프 언롤링 등으로 성능 최적화함

> 요약: 문제 구조 분석 후 방식 선택·구현·최적화 순서로 진행함

## Ⅳ. 문제점
- 스택 오버플로: 재귀 깊이가 콜 스택 한계를 초과하면 프로그램이 비정상 종료함 — 깊은 트리 탐색 시 발생
- 가독성 저하: 복잡한 재귀를 반복으로 변환하면 명시적 스택 관리 코드가 늘어남 — 유지보수 비용 증가
- 중복 계산: 메모이제이션 없는 재귀는 동일 부분 문제를 중복 호출함 — 피보나치 수열에서 지수 시간 소요

> 요약: 스택 한계·가독성 트레이드오프·중복 계산이 주요 문제임

## Ⅴ. 개선방안
1. 단기: 꼬리 재귀 변환 또는 반복 전환으로 스택 오버플로 방지
2. 중기: 재귀 의도를 주석·문서화하고, 명시적 스택 사용 시 헬퍼 함수로 캡슐화하여 가독성 확보
3. 장기: 메모이제이션·동적 프로그래밍 테이블 적용으로 중복 계산 제거

> 요약: 꼬리 재귀·캡슐화·메모이제이션으로 각 문제를 해소함

## Ⅵ. 전망
- 발전 방향: 함수형 언어 확산으로 꼬리 호출 최적화(TCO) 지원이 표준화되는 추세
- 기술사적 판단: 컴파일러 최적화가 재귀-반복 변환을 자동 수행하는 범위가 확대될 전망
- 기술사 제언: 문제 구조에 맞는 방식 선택 역량과 변환 기법 숙지가 기술사에게 필수 소양임
