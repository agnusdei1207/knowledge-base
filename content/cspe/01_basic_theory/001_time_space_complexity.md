## 미리 알고가기

- 입력 크기 `n`: 알고리즘이 처리하는 데이터 원소 수, 문자열 길이, 정점 수처럼 비용을 좌우하는 규모임
- 시간복잡도 `T(n)`: 입력 크기 증가에 따른 기본 연산 횟수 증가율임
- 공간복잡도 `S(n)`: 입력 저장 공간 외에 추가로 필요한 메모리 증가율임
- 점근 분석: 작은 입력보다 큰 입력에서 지배적인 증가율을 보는 분석 방식임

## Ⅰ. 개요

- **정의**: 입력 증가에 따른 실행시간·메모리 증가율 분석임
- **배경/필요성**: 구현 언어·CPU 차이를 제거하고 알고리즘 자체의 확장성을 비교하려면 연산 횟수와 메모리 사용량을 입력 크기 기준으로 표현해야 함
- **비유**: 시간복잡도는 작업 시간이 늘어나는 속도, 공간복잡도는 작업대와 보관함이 늘어나는 속도임

| 출제 의도 | 반드시 짚을 핵심 | 감점 회피 포인트 |
|:---|:---|:---|
| 알고리즘 선택 기준을 설명하는 역량 확인 | `T(n)`, `S(n)`, 최악·평균·최선, 시간-공간 트레이드오프 | 시간·공간 구분 누락, 상수 시간 단정 |

> 요약: 복잡도는 실행 결과가 아니라 입력 규모 변화에 대한 비용 증가율을 판단하는 기준임.

## Ⅱ. 특징/비교

| 판단 기준 | 시간복잡도 | 공간복잡도 |
|:---|:---|:---|
| 측정 대상 | 비교·대입·산술 등 기본 연산 횟수 | 배열·해시·재귀 스택 등 메모리 사용량 |
| 설계 영향 | 응답시간, 처리량, 배치 완료 시간 결정 | 메모리 한계, 캐시 적중, 동시 처리량 결정 |
| 트레이드오프 | 전처리·인덱스로 탐색 시간을 줄일 수 있음 | 추가 저장공간이 증가하면 메모리 비용이 커짐 |

> 요약: 시간과 공간은 따로 분석하되, 실제 설계에서는 서로 교환되는 비용으로 판단해야 함.

- 같은 `O(n)`이라도 기본 연산 종류와 메모리 접근 패턴에 따라 실제 지연이 달라질 수 있음
- 복잡도는 알고리즘 후보를 줄이는 1차 판단 기준이며, 운영 환경 검증을 대체하지 않음
- 2~4교시 답안에서는 복잡도 표기보다 "왜 그 알고리즘을 선택했는가"를 비용 관점으로 설명해야 함

## Ⅲ. 구성요소

```text
+----------+      +----------+      +----------+
| 입력크기 | ---> | 비용함수 | ---> | 점근표현 |
| n        |      | T(n),S(n)|      | O,Theta |
+----------+      +----------+      +----------+
                         |
                         v
                   +----------+
                   | 선택판단 |
                   +----------+
```

| 구성요소 | 설명 | 비유 |
|:---|:---|:---|
| 입력 크기 | 비용을 좌우하는 데이터 규모를 `n`, `V`, `E` 등으로 정의함 | 작업 물량 |
| 기본 연산 | 반복문 내부 비교·교환·삽입처럼 시간 비용을 대표하는 연산임 | 한 번의 손동작 |
| 보조 공간 | 입력 데이터 외에 추가로 사용하는 배열·스택·큐·해시 공간임 | 작업 보조 도구 |
| 점근 표현 | 최고 증가율 중심으로 비용 함수를 단순화해 비교 가능하게 함 | 축척 지도 |

> 요약: 입력 크기와 기본 연산·보조 공간을 비용 함수로 만들고 점근 표현으로 선택 기준을 세움.

## Ⅳ. 절차

```text
+----------+      +----------+      +----------+      +----------+
| 입력정의 | ---> | 비용계산 | ---> | 차수정리 | ---> | 선택판단 |
+----------+      +----------+      +----------+      +----------+
```

1. **입력 정의**: 배열 길이 `n`, 그래프 정점 `V`, 간선 `E`처럼 분석 변수를 정함
2. **비용 계산**: 반복 횟수, 재귀 깊이, 동적 할당 크기를 각각 `T(n)`, `S(n)`으로 표현함
3. **차수 정리**: 지배항 중심으로 증가율을 정리하고 최악·평균·최선 범위를 구분함
4. **선택 판단**: 응답시간, 메모리 제약, 데이터 규모를 기준으로 알고리즘을 선택함

> 요약: 복잡도 분석은 입력 변수 정의에서 시작해 비용 함수와 운영 조건을 함께 판단함.

## Ⅴ. 문제점

- **P1 추상 모델 한계**: 복잡도는 상수 계수, 캐시 적중, 분기 예측, I/O 대기 시간을 숨겨 실제 지연과 차이가 생김
- **P2 사례 범위 혼동**: 최악·평균·최선 복잡도를 구분하지 않으면 퀵정렬 평균 `O(n log n)`을 항상 보장으로 오해함
- **P3 트레이드오프 누락**: 시간만 줄이거나 공간만 줄이는 선택은 메모리 비용, 캐시 효율, 장애 복구 비용을 놓칠 수 있음

> 요약: 복잡도는 강한 1차 기준이지만 실제 환경과 사례 범위를 함께 보지 않으면 선택 오류가 발생함.

## Ⅵ. 개선방안

1. **단기**: 후보 알고리즘의 `T(n)`, `S(n)`, 최악·평균 조건을 같은 표기 기준으로 정리함
2. **중기**: 대표 입력과 경계 입력으로 벤치마크를 수행해 p95 지연, 메모리 피크, 캐시 미스 등으로 검증함
3. **장기**: 데이터 규모·하드웨어·운영 SLA별 알고리즘 선택 기준을 아키텍처 표준으로 관리함

- **P1 대응**: 이론 복잡도와 프로파일링 결과를 함께 기록함 (확인: p95 지연, 메모리 피크)
- **P2 대응**: 최악·평균·최선 조건을 명시하고 입력 분포를 검증함 (확인: 경계 입력 테스트)
- **P3 대응**: 시간-공간 트레이드오프를 의사결정 표준에 포함함 (확인: SLA와 비용 기준 충족)

> 요약: 복잡도는 벤치마크와 운영 기준을 결합할 때 알고리즘 선택 근거가 됨.

## Ⅶ. 전망

- 데이터 규모가 커질수록 단일 시간복잡도보다 메모리 계층, 네트워크 전송, 병렬 처리 비용을 함께 보는 다차원 분석이 중요해짐
- 엣지·모바일 환경에서는 공간복잡도와 전력 사용량이 알고리즘 채택 조건으로 결합될 가능성이 큼
- 기술사는 복잡도 표기 자체보다 요구사항, 데이터 분포, 운영 제약을 연결해 선택 근거를 제시해야 함
