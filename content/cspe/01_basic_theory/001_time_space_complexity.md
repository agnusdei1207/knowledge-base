# 📖 【암기용】 개념 완전 이해

> 목적: 이 개념을 처음 보는 사람도 완벽히 이해하게 만든다. 시험 답안 양식이 아니라, 이해를 위한 친절한 설명이다.

## 한눈에
- **개요**: **알고리즘 효율성**을 재는 척도 — 입력 n이 커질 때 **시간 복잡도**(연산 횟수)와 **공간 복잡도**(메모리)가 얼마나 빨리 늘어나는지를 나타냄
- **왜 필요한가**: 같은 기능이라도 데이터가 100만 건이 되면 한 알고리즘은 1초에, 다른 알고리즘은 며칠에 끝난다. 이 차이를 코드 실행 전에 예측하려는 것이다.
- **핵심 직관**: 초 단위 실측이 아니다. "데이터가 2배가 되면 비용은 몇 배가 되나"라는 증가 추세를 본다.

## 핵심 용어 정리 (내부에 등장하는 것들)

| 용어 | 의미 | 비유·예 |
|:---|:---|:---|
| 시간복잡도 | 연산이 몇 번 실행되는가 | 손님이 늘 때 요리 시간이 늘어나는 정도 |
| 공간복잡도 | 입력 외에 메모리를 얼마나 더 쓰는가 | 손님이 늘 때 필요한 좌석 수 |
| 점근적 표기법 | 증가 추세만 남긴 표기(O 등) | "대충 이 급으로 늘어난다"는 등급표 |
| 증가율 등급 | O(1)·O(n)·O(n²)처럼 나눈 속도 등급 | 자판기(O(1)) vs 모두가 악수(O(n²)) |
| 트레이드오프 | 한쪽을 줄이려 다른 쪽을 늘리는 관계 | 미리 계산해 저장 → 시간↓ 공간↑ |

## 깊이 이해

### 왜 하드웨어와 무관한 척도가 필요한가 (배경)
- 같은 코드도 CPU·컴파일러·언어에 따라 실제 실행 시간(초)이 달라진다. "몇 초 걸리나"로는 알고리즘 A와 B를 공정하게 비교할 수 없다.
- 그래서 "입력 n이 커질 때 연산 횟수가 어떤 추세로 느는가"만 본다. 이 추세는 어느 컴퓨터에서 재도 같아서 알고리즘 고유의 성질이 된다.

### 코드에서 복잡도 함수 f(n)을 뽑는 법
- 반복문·재귀를 세어 연산 횟수를 n의 함수로 적는다. 단일 반복문은 n번 → O(n), 이중 중첩은 n×n → O(n²), 범위를 매번 절반으로 접으면 → O(log n)이다.
- 이렇게 얻은 f(n)(예: 3n²+5n+10)을 O(n²) 같은 대표 표기로 줄이는 규칙은 002 빅오 표기법이 담당한다.

### 증가율이 실제로 얼마나 벌어지나 (수치)
- N=1,000일 때: O(n)=1,000, O(n log n)≈10,000, O(n²)=1,000,000.
- N=1,000,000일 때: O(n)=100만, O(n log n)≈2,000만, O(n²)=1조. O(n²)는 O(n log n)보다 약 5만 배 느려진다.
- 그래서 대규모 데이터에서는 등급 하나 차이가 "가능 vs 사실상 불가능"을 가른다.

### 공간복잡도도 함께 본다
- 공간복잡도는 입력을 뺀 추가 메모리다. 재귀 호출은 호출 스택을 쌓아 깊이만큼 공간을 먹고(재귀 깊이 n이면 O(n)), 병합 정렬은 임시 배열로 O(n)을 더 쓴다.
- 시간만 좋고 공간이 폭발하면 OOM(메모리 부족)으로 프로세스가 죽으므로 두 축을 함께 봐야 한다.

### 시간-공간 트레이드오프 (실제 예)
- 피보나치를 단순 재귀로 짜면 같은 값을 반복 계산해 O(2ⁿ)로 폭발한다. 계산 결과를 배열에 저장(메모이제이션)하면 시간은 O(n)으로 줄지만 저장 공간 O(n)을 추가로 쓴다.
- 즉 "공간을 내주고 시간을 산다". 메모리 단가가 싼 현대 시스템에서 자주 택하는 전략이다.

### 흔한 오해·주의점
- 복잡도가 낮다고 항상 빠른 게 아니다. Big-O는 상수를 숨기므로(002), n이 작으면 상수가 큰 O(1)보다 O(n)이 빠를 수도 있다.
- 등급은 "n이 충분히 클 때"의 이야기다. 실제 선택은 예상되는 n의 크기를 먼저 가늠하고 판단한다.

## 연결 개념
- 002 빅오 표기법 — f(n)을 상한 표기로 줄이는 규칙과 O/Ω/Θ 정의
- 정렬·탐색 알고리즘 (003 정렬, 004 이진 탐색)
- 공간-시간 트레이드오프 (Space-Time Trade-off)

# 📝 【답안용】 시험 답안 템플릿

> 목적: 시험장에서 25분에 그대로 쓰는 답안 양식. 작성방식(추상표현 금지·수치·도식·문제유형 전환)을 엄격히 지킨다.
> 핵심: 이 시험은 정보를 많이 나열하는 시험이 아니라, 문제 신호어에서 출제자 의도를 읽고 핵심 논점을 선별해 쓰는 시험이다.

## 핵심 인사이트 (3줄 요약)

> 1. **본질**: 하드웨어와 무관하게 알고리즘의 자원 증가율을 평가하는 척도임.
> 2. **가치**: 입력 n이 커질 때 SLA 충족 여부를 코드 구현 전에 예측할 수 있음.
> 3. **판단 포인트**: 메모리 단가가 낮은 현대 시스템에서는 공간을 더 써서 시간을 줄이는 Time-Space Trade-off를 우선 검토함.

## 출제 의도 및 답안 포인트

| 출제 의도 | 반드시 짚을 핵심 | 감점 회피 포인트 |
|:---|:---|:---|
| 알고리즘 평가 척도 이해 확인 | 시간·공간 복잡도의 의미와 상충 관계 | 실행 환경(CPU) 절대 시간을 효율성 기준으로 서술 |
| 자원 예측·설계 역량 | 증가율 등급(O(1)~O(2ⁿ))과 트레이드오프 판단 | 시간·공간을 독립 지표로만 나열, 상충 관계 누락 |

> 요약: 시간과 공간은 독립적이지 않으며, 가용 자원에 맞춰 둘을 맞바꾸는 설계가 핵심임.

## Ⅰ. 개요 및 필요성

- 정의: 입력 크기 n에 따라 알고리즘의 연산 횟수와 메모리 요구량이 늘어나는 추세를 나타내는 척도
- 배경: CPU·OS에 의존하는 절대 실행 시간으로는 알고리즘을 공정하게 비교할 수 없음
- 필요성: 대용량 처리에서 O(n²) 설계는 데이터 증가 시 응답 지연 임계치를 초과하므로 사전 복잡도 분석 필수

---

## Ⅱ. 구조 및 구성요소

```text
입력 크기 n -> 코드 분석(반복·재귀 계수) -> 복잡도 함수 f(n) 도출 -> [시간 f(n) / 공간 s(n)] -> 표기법 단순화(002)
```

| 구분 | 측정 대상 | 세는 방법 |
|:---|:---|:---|
| 시간복잡도 (Time) | 연산 횟수 | 대입·비교·연산 등 기본 연산이 몇 번 실행되는지를 n의 함수로 표현 |
| 공간복잡도 (Space) | 추가 메모리 | 입력 외에 알고리즘이 별도로 쓰는 고정·가변 메모리의 합 |
| 트레이드오프 | 두 축의 교환 | 한쪽을 줄이려 다른 쪽을 늘리는 관계 (예: 캐시로 시간↓·공간↑) |

> 요약: 복잡도는 시간(연산)과 공간(메모리) 두 축으로 재며, 두 축은 서로 맞바꿀 수 있음.

---

## Ⅲ. 동작원리 및 흐름도

```text
코드 로직 분석 -> 기본 연산 횟수 계산 -> 복잡도 함수 f(n) 도출 -> (표기법 단순화는 002) -> 자원 제약에 맞춰 시간·공간 튜닝
```

- 1단계 [로직 분석]: 반복문 중첩 횟수와 재귀 깊이를 식별함
- 2단계 [연산 횟수 계산]: 기본 연산 실행 횟수를 n의 다항식 f(n)으로 작성함
- 3단계 [지배항 확인]: n이 커질 때 비용을 좌우하는 항을 파악함 (O 표기로 줄이는 규칙은 002)
- 4단계 [트레이드오프 튜닝]: 반복 계산을 캐시로 대체해 시간 O(n)→O(1)로 낮추고 대신 공간을 씀

> 요약: 코드에서 연산 횟수 함수를 뽑고, 시스템 자원 제약에 맞춰 시간·공간을 맞바꾸는 것이 핵심임.

---

## Ⅳ. 주요 증가율 등급

| 등급 | 표기 | 증가 양상 | 대표 사례 |
|:---|:---|:---|:---|
| 상수 | O(1) | 입력과 무관하게 일정 | 해시 조회, 배열 인덱스 접근 |
| 로그 | O(log n) | 데이터 2배 → 연산 1회 증가 | 이진 탐색, 균형 이진 트리 |
| 선형 | O(n) | 입력에 정비례 | 선형 탐색, 단일 반복문 |
| 선형로그 | O(n log n) | 분할 정복형 정렬 수준 | 퀵·병합·힙 정렬 |
| 제곱 | O(n²) | 입력 2배 → 연산 4배 | 이중 반복문, 버블 정렬 |
| 지수 | O(2ⁿ) | 입력 1 증가 → 연산 2배 | 부분집합 완전 탐색 |

> 요약: 대규모 시스템은 O(n log n) 이하를 확보해야 데이터가 늘어도 응답 시간을 유지함.

## Ⅴ. 심화 비교 및 적용 판단

| 비교 축 | Time 우선 (공간 투자) | Space 우선 (연산 감수) | 선택 기준 |
|:---|:---|:---|:---|
| 구조 | 메모이제이션·해싱으로 결과 저장 | In-place 처리, 변수 재사용 | 지연 민감도 vs 메모리 한계 |
| 성능/비용 | 메모리↑, 반복 계산 제거로 지연↓ | 메모리 절약, CPU 연산↑ | 대용량 캐시 인프라 확보 가능 여부 |
| 위험 | 캐시 정합성 관리 부담 | 데이터 증가 시 타임아웃 | Read 중심 서비스는 Time 우선 |

> 요약: 메모리 한계를 넘지 않는 선에서 공간을 투자해 시간을 줄이는 것이 실무 표준임.

**주요 리스크·대응:**
- 캐시 정합성 깨짐: 캐시 무효화 정책 부재가 원인 → TTL·LRU 교체 정책으로 통제 (지표: 캐시 적중률)
- 메모이제이션 메모리 고갈(OOM): 캐시가 입력 n에 비례해 무한 증가 → 캐시 크기 상한·LRU 제거 (지표: 힙 메모리 사용량)
- 조기 최적화: n이 작은데 캐시·해싱을 선도입 → 프로파일링 후 병목 구간만 최적화 (지표: 핫스팟 비율)

---

## Ⅵ. 실무 적용 및 결론

**적용 방안 3개:**
1. 대용량 정렬: O(n²) 버블 정렬 대신 O(n log n) 정렬을 적용해 수억 건 처리 지연 방지
2. 캐싱 설계: 반복 조회 결과를 인메모리 O(1) 해시에 저장해 DB의 O(log n) 인덱스 조회를 우회
3. 임베디드·엣지: 메모리가 제한된 환경에서는 캐시 없이 In-place 알고리즘으로 공간을 우선

**결론 (2줄):**
- 기술사 판단: 복잡도는 절대 지표가 아니며, n이 작으면 상수항이, 크면 최고차항이 성능을 지배하므로 n 규모를 먼저 파악해야 함.
- 향후 방향: AI 추론으로 연산량이 급증하면서, 근사 알고리즘·병렬화로 실효 복잡도를 낮추는 설계가 중요해지고 있음.
