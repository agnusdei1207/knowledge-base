# 알고리즘 시간복잡도·공간복잡도 (Time/Space Complexity)

## 미리 알고가기

- **점근 표기(Big-O)**: 입력이 아주 커졌을 때 비용이 대략 어떤 속도로 늘어나는지만 남기는 표기법. 자동차를 고를 때 "지금 몇 초 걸리나"가 아니라 "경차냐 스포츠카냐" 하는 급으로 묶어 보는 것과 같다.
- **지배항(dominant term)**: 입력이 커지면 결국 전체 비용을 좌우하는 가장 큰 항. `3n² + 100n`에서 `n`이 커지면 `n²`이 압도하므로 `O(n²)`만 남기고 상수 3과 `100n`은 버린다.
- **상각(amortized)**: 어쩌다 한 번 비싼 연산이 끼더라도 여러 번에 걸쳐 나눠 보면 평균 비용은 싸다고 보는 관점. 가끔 배열을 통째로 옮기는 동적 배열의 `push`가 평균 `O(1)`인 것이 예다.

## 1. 개요

- **정의/개념**: 시간복잡도와 공간복잡도는 입력 크기 `n`이 커질 때 알고리즘이 기본 연산을 얼마나 더 수행하고 추가 메모리를 얼마나 더 쓰는지를 `n`에 대한 함수로 나타내, 큰 입력에서의 확장성을 미리 판단하는 분석 기준이다.
- **배경/필요성**: 같은 기능을 하는 코드라도 데이터가 백 건일 때는 셋 다 눈 깜짝할 새 끝나 차이를 못 느낀다. 문제는 데이터가 백만 건, 천만 건으로 불어날 때인데, 한 알고리즘은 여전히 순식간에 끝나는 반면 다른 알고리즘은 몇 시간씩 걸리거나 메모리가 터져 버린다. 그런데 이 차이는 실제로 돌려 보기 전에는 잘 안 보인다. 그래서 초 단위 실행 시간을 재는 대신, 입력이 커질 때 비용이 늘어나는 "기울기"를 함수로 뽑아 두고, 코드를 짜기 전에 어느 알고리즘이 규모를 견디는지 고르는 기준이 필요해진다.

복잡도 분석은 실행 시간을 초 단위로 맞히는 일이 아니라, 입력이 두 배, 열 배로 커질 때 비용이 몇 배로 뛰는지 그 증가 추세를 보고 선택의 근거를 만드는 일이다.

## 2. 특징 및 비교

시간과 공간은 따로 노는 두 지표가 아니라, 하나를 아끼면 다른 하나를 더 쓰게 되는 맞바꿈 관계다.

| 구분 | 시간복잡도 | 공간복잡도 |
|:---|:---|:---|
| 무엇을 세나 | 비교·대입·탐색 같은 기본 연산 횟수 | 입력 말고 따로 잡는 보조 메모리 양 |
| 커지면 아픈 곳 | 응답 지연, CPU 사용량, 배치 시간 | 메모리 피크, GC 부담, OOM 장애 |
| 대표 표기 | `T(n) = O(f(n))` | `S(n) = O(f(n))` |

> 요약: 시간은 "얼마나 오래 도나", 공간은 "얼마나 많이 쥐고 있나"를 본다.

- 해시 테이블, 인덱스, 메모이제이션은 결과를 미리 저장해 두는 방식이라 **공간을 더 써서 시간을 산다**. 매번 다시 계산하거나 훑을 일을 미리 만들어 둔 표에서 한 번에 꺼내기 때문이다.
- 반대로 제자리(in-place) 정렬이나 스트리밍 처리는 데이터를 통째로 메모리에 올리지 않아 **공간을 아끼는 대신 시간이나 I/O를 더 감수**한다.
- 그래서 복잡도 판단은 시간만 보거나 공간만 보는 게 아니라, 이 시스템에서 지금 더 귀한 자원이 시간인지 메모리인지를 먼저 정하고 둘의 균형점을 고르는 일이 된다.

같은 `O` 표기라도 최악·평균·상각 중 어느 경우인지에 따라 실제 보장 수준이 달라지므로, 표기 옆에는 늘 "어떤 경우의 값인가"가 붙어야 한다.

## 3. 구성요소/구조

복잡도는 한 번에 튀어나오는 값이 아니라, 아래 재료를 차례로 짚어 함수로 조립하고 마지막에 지배항만 남기는 과정으로 얻는다.

```text
입력 크기 정의 -> 기본 연산/보조 공간 세기 -> 비용 함수 도출 -> 지배항만 남겨 O 표기 -> 요구사항 충족 판단
```

| 구성요소 | 하는 일 | 왜 중요한가 |
|:---|:---|:---|
| 입력 크기 | 비용을 좌우하는 변수. 배열은 `n`, 그래프는 정점 `V`·간선 `E` | 무엇을 `n`으로 볼지 잘못 잡으면 이후가 다 틀어짐 |
| 기본 연산 | 비교·대입·탐색·병합처럼 횟수를 셀 최소 단위 | 시간 비용을 세는 기준 |
| 보조 공간 | 임시 배열, 큐, DP 테이블, 재귀 콜 스택 | 공간 비용을 세는 기준 |
| 지배항 추출 | 상수·하위 항을 버리고 가장 큰 항만 남김 | 큰 입력에서의 증가율만 드러냄 |
| 경우 구분 | 최악·평균·최선·상각을 나눠 표기 | 성능을 어디까지 보장하는지 결정 |

> 요약: 입력 변수와 기본 연산을 먼저 정확히 잡아야, 뒤의 함수와 `O` 표기가 의미를 가진다.

여기서 입력 변수나 기본 연산을 헐겁게 잡으면 뒤따르는 시간·공간 판단이 통째로 어긋난다. 실제로 복잡도에서 생기는 문제 대부분이 이 첫 단추, 즉 분석 기준을 잘못 잡은 데서 시작된다.

## 4. 문제점 및 개선방안

1. **`O` 표기와 실제 실행 시간을 같은 것으로 착각**: `O`는 상수를 버린 증가율이라, 입력이 작으면 `O(n)`이 `O(log n)`보다 빠를 수도 있다. 상수가 큰 `log n` 알고리즘이 실제로는 더 느리게 도는 경우가 흔하다.
   - **개선방안**: 표기만 믿지 말고 실제 운영 입력 크기 구간에서 벤치마크를 돌려 p95/p99 지연과 캐시 적중률을 함께 본다. (확인: 실입력 구간 실측 지연)

2. **평균 성능을 항상 보장되는 값으로 오해**: 해시 조회 평균 `O(1)`, 퀵 정렬 평균 `O(n log n)`은 어디까지나 평균이고, 해시 충돌이 몰리거나 정렬 입력이 최악으로 들어오면 각각 `O(n)`, `O(n²)`으로 떨어진다.
   - **개선방안**: 표기 옆에 최악·평균·상각을 명시하고, 일부러 최악 입력을 만들어 테스트한다. (확인: 최악 입력에서의 응답 시간)

3. **시간만 보고 공간을 빠뜨림**: DP 테이블, 깊은 재귀의 콜 스택, 인덱스가 먹는 메모리를 계산에서 빼면, 개발 환경에서는 멀쩡하다가 운영에서 메모리가 터지거나(OOM) 스택 오버플로로 죽는다.
   - **개선방안**: 시간과 함께 메모리 피크, 보조 공간 크기, 동시 실행 개수를 곱해 산정한다. (확인: 최대 동시 실행 시 메모리 피크)

## 5. 실무 적용 사례

| 적용 영역 | 어떻게 쓰나 | 무엇으로 효과를 확인하나 |
|:---|:---|:---|
| API 대량 조회 | 정렬·필터 알고리즘의 시간복잡도와 인덱스가 먹는 공간을 저울질해 선택 | p95 지연, CPU, 메모리 피크 |
| 임베디드 제어 | 보조 배열·재귀 스택이 제한된 RAM을 넘지 않는 알고리즘으로 한정 | RAM 여유율, 최악 응답 시간 |
| 배치 처리 | `O(n²)`으로 도는 구간을 정렬·해시·분할 정복으로 낮춰 처리 시간 단축 | 총 처리 시간, I/O 횟수 |

> 요약: 시간이 급하면 공간을 내주고, 메모리가 빠듯하면 시간을 내주며, 어느 자원이 병목인지로 알고리즘을 고른다.

## 6. 결론

시간복잡도와 공간복잡도는 알고리즘을 실제로 돌려 보기 전에 규모를 견디는지 걸러 내는 1차 필터다. 다만 `O` 표기 하나로 끝내면 상수를 버린 증가율만 본 셈이라, 입력이 작은 구간이나 최악 입력, 메모리 한계에서 판단이 빗나간다. 그래서 실무의 선택은 입력 변수, 기본 연산, 보조 공간, 어떤 경우의 값인지, 그리고 지금 시스템에서 시간과 메모리 중 무엇이 더 귀한지를 함께 엮어, 실측 지표로 다시 확인하는 데까지 가야 쓸 수 있는 근거가 된다.
