# 001. 시간 복잡도와 공간 복잡도 (Time and Space Complexity) [출제: 131회]

## 미리 알고가기

- **점근 표기(Asymptotic Notation)**: 입력 크기가 무한히 커질 때 알고리즘 비용의 증가율 경향성을 표현하는 수학적 방법론임
- **지배항(Dominant Term)**: 복잡도 함수에서 증가율에 가장 큰 영향을 미치는 최고차항이며, 복잡도 결정의 기준임
- **상각 분석(Amortized Analysis)**: 최악의 연산이 간헐적으로 발생할 때, 전체 연산에 걸친 평균 비용을 산정하는 분석 방식임

## Ⅰ. 개요

- **정의/개념**: 알고리즘이 입력 크기 $n$ 증가에 따라 기본 연산을 얼마나 더 수행하고(시간복잡도), 추가 메모리를 얼마나 더 사용하는지(공간복잡도) 함수로 표현해 시스템의 확장성을 판단하는 수학적 분석 기준임
- **배경/필요성**: 데이터 규모가 백만 단위 이상으로 커짐에 따라 알고리즘 간 성능 차이가 기하급수적으로 벌어지므로, 실제 구현 전 설계 단계에서 요구사항(지연시간, 메모리 한계)을 충족하는지 검증할 척도가 필요함

## Ⅱ. 특징 및 비교

시간과 공간은 상호 교환(Trade-off) 관계에 있으며, 시스템 제약 조건에 따라 하나를 희생해 다른 하나를 최적화하는 설계 판단이 수반됨.

| 판단 기준 | 시간복잡도 (Time Complexity) | 공간복잡도 (Space Complexity) |
|:---|:---|:---|
| 측정 대상 | 비교, 대입, 탐색 등 기본 연산의 반복 횟수 | 입력 데이터 외 알고리즘 실행에 필요한 보조 메모리 양 |
| 핵심 지표 | 처리량(Throughput), 지연시간(Latency) | 가용 메모리(Heap/Stack), OOM 발생 가능성 |
| 제약 초과 시 현상 | 응답 지연, 타임아웃 발생, 시스템 처리 용량 포화 | Out of Memory 장애, GC 오버헤드, 스와핑 발생 |
| 표기 방식 | $T(n) = O(f(n))$ | $S(n) = O(f(n))$ |
| 최적화 기법 | 메모이제이션, 인덱싱, 해시 테이블 적용 (공간 희생) | 인플레이스(In-place) 처리, 스트리밍, 비트 마스크 (시간 희생) |
| 설계 관점 | 빠른 응답이 필요한 실시간/트랜잭션 시스템 중심 | 자원이 한정된 임베디드/IoT 또는 대용량 병렬 처리 중심 |

> 요약: 시간복잡도는 처리 속도의 한계를, 공간복잡도는 메모리 자원의 한계를 판단하며 설계 시 시스템 자원 가용성에 맞춰 양립 관계를 조율해야 함.

## Ⅲ. 구성요소/구조

시간·공간복잡도를 분석하기 위해서는 입력 변수와 기본 연산을 명확히 정의하고 비용 함수를 도출하는 구조적 접근이 필요함.

- **구성요소**: 복잡도 분석의 핵심 요소

| 구성요소 | 역할 및 산출 기준 | 핵심 포인트 |
|:---|:---|:---|
| 입력 크기 ($n$) | 배열 길이, 트리 높이, 정점($V$)/간선($E$) 수 등 변수 정의 | 환경에 맞는 지배적 입력 변수 식별 |
| 기본 연산 | 반복문 내 핵심 로직(비교, 대입)과 재귀 호출 횟수 산정 | 실제 처리 비용과 직결되는 연산 선정 |
| 보조 공간 | 임시 배열, 해시 테이블, 재귀 콜 스택 등 추가 메모리 양 | 입력 크기에 비례하여 증가하는 보조 공간 분석 |
| 분석 시나리오 | 최악(Worst), 평균(Average), 최선(Best) 케이스로 분리 | 서비스 안정성 보장을 위한 최악 케이스 중심 관리 |

- **분석 절차 (원리/흐름도)**:

```text
+----------+      +----------+      +----------+      +----------+
| 변수식별 | ---> | 함수도출 | ---> | 지배항추출 | ---> | 표기확정 |
+----------+      +----------+      +----------+      +----------+
     |                  |                  |                  |
     v                  v                  v                  v
[핵심입력 n정의]    [f(n) 다항식 도출]    [상수/하위항 제거]    [O(f(n)) 도출]
```

1. **입력/연산 식별** — 성능에 직접적인 영향을 주는 입력 변수 $n$과 가장 빈번히 발생하는 기본 연산을 정의함
2. **비용 함수 도출** — 총 연산 횟수와 공간 사용량을 $n$에 대한 다항식 $f(n)$으로 수학적으로 도출함
3. **지배항 추출** — $f(n)$에서 상수항과 하위 차수 항을 제거해 입력 크기에 가장 민감한 최고차항만 남김
4. **표기 확정** — 최종적으로 $O(n \log n)$ 등 점근적 표기법으로 확정해 알고리즘 선택과 설계의 근거로 활용함

## Ⅳ. 문제점 및 개선방안

1. **상수항 무시로 인한 실제 성능 왜곡**: $O$ 표기법은 점근적 증가율만 보므로, 입력 $n$이 작을 때 상수항이 큰 $O(1)$이 상수항이 작은 $O(n)$보다 느릴 수 있음
   - **개선방안**: 점근 표기에만 의존하지 않고, 실제 운영 데이터 규모 구간에서 벤치마킹을 수행해 $p95/p99$ 지연시간을 측정함 (확인: 실측 레이턴시 프로파일링 데이터)

2. **최악의 경우(Worst Case) 고려 누락**: 평균 $O(1)$인 해시 테이블을 적용했으나 악의적인 해시 충돌 공격(Hash Collision Attack) 시 $O(n)$으로 급격히 저하될 수 있음
   - **개선방안**: SLA가 엄격한 시스템에서는 최악의 성능을 보장하는 알고리즘(예: Balanced Tree)을 선정하거나 Timeout 및 부하 통제를 구현함 (확인: 최악 입력 시나리오 테스트)

3. **재귀 호출에 따른 공간복잡도 한계 간과**: 시간복잡도만 고려해 깊은 재귀를 수행하면 힙 메모리가 아닌 콜 스택(Call Stack) 초과로 StackOverflow 장애가 발생함
   - **개선방안**: 재귀 최대 깊이를 추정해 꼬리 재귀(Tail Recursion) 최적화를 적용하거나 명시적 반복문과 스택 자료구조로 변환함 (확인: 런타임 스택 메모리 피크 모니터링)

## Ⅴ. 실무 적용 사례

| 적용 영역 | 적용 방식 | 확인 지표 |
|:---|:---|:---|
| 데이터베이스 조인 | $O(n^2)$의 Nested Loop Join을 메모리를 추가 활용하는 Hash Join($O(n)$)으로 최적화 | 배치 실행 시간, CPU 점유율 |
| 임베디드/IoT 시스템 | 메모리 제약 환경에서 보조 배열 생성 대신 In-place 알고리즘을 적용해 공간 효율성 확보 | 가용 RAM 용량, OOM 발생률 |
| 대규모 API 서버 | 동일 요청에 대한 반복 계산 부하를 줄이기 위해 Redis 기반 캐싱(메모이제이션) 적용 | $p99$ 응답시간, 캐시 적중률 |
| 실시간 로그 분석 | 메모리에 전체를 적재하지 않고 스트리밍 방식으로 처리해 일정한 공간복잡도 유지 | 힙 메모리 사용량, 로그 유실률 |

> 요약: 인프라 제약(메모리 용량)과 서비스 제약(응답시간 SLA) 중 핵심 병목 요소를 식별해 시간-공간의 트레이드오프를 결정함.

## Ⅵ. 결론

시간복잡도와 공간복잡도는 알고리즘이 대규모 데이터 환경에서 지속 가능한지, 장애 없이 운영될 수 있는지를 평가하는 가장 기초적이고 핵심적인 설계 판단 기준임. 기술사는 단순히 표기법상 수치가 낮은 것만 추구할 것이 아니라, 가용 인프라 자원과 목표 성능(SLA)을 종합적으로 분석해 시간과 공간 중 무엇을 희생하고 최적화할지 결정해야 함. 

특히 현대의 분산 시스템 환경에서는 이론적인 점근적 복잡도 외에도 CPU 캐시 지역성(Cache Locality), 네트워크 I/O 오버헤드, 직렬화 비용 등을 고려한 실측 기반의 최적화를 병행해야 하며, 알고리즘 선택 시 확장성(Scalability)과 안정성(Stability)을 동시에 보장할 수 있는 설계 역량이 필수적임.
