# 📖 【암기용】 개념 완전 이해

> 목적: 이 개념을 처음 보는 사람도 완벽히 이해하게 만든다. 시험 답안 양식이 아니라, 이해를 위한 친절한 설명이다.

## 한눈에
- **개요**: **알고리즘 자원 소모량**을 예측하는 척도 — 입력 데이터 n이 커질 때 **시간 복잡도**(연산 횟수)와 **공간 복잡도**(메모리 사용량)가 얼마나 빠르게 증가하는지를 나타냄
- **왜 필요한가**: 동일한 기능을 수행하더라도 데이터가 100만 건으로 늘어나면, O(n) 알고리즘은 1초 만에 끝나지만 O(n²) 알고리즘은 며칠이 소요될 수 있다. 이를 실행 전에 수학적으로 예측하기 위해 필요하다.
- **핵심 직관**: "입력 데이터가 2배로 늘어날 때, 처리 비용은 몇 배로 늘어나는가"라는 증가 추세를 측정한다.

## 핵심 용어 정리

| 용어 | 의미 | 비유·예 |
|:---|:---|:---|
| 시간 복잡도 | 연산이 몇 번 실행되는지를 측정 | 손님이 늘어날 때 요리 시간이 길어지는 정도 |
| 공간 복잡도 | 입력 데이터 외에 메모리를 추가로 얼마나 사용하는지를 측정 | 손님이 늘어날 때 추가로 필요한 좌석 수 |
| 트레이드오프 | 한쪽 자원을 줄이기 위해 다른 쪽 자원을 희생하는 상충 관계 | 연산 결과를 미리 저장(공간 증가)해 계산 횟수(시간 감소)를 줄임 |
| 복잡도 함수 f(n) | 기본 연산 횟수를 입력 n에 대한 수학적 다항식으로 표현한 것 | 반복문 안의 연산이 3n² + 5n + 10번 실행됨 |

## 깊이 이해

### 왜 하드웨어와 무관한 척도가 필요한가 (배경)
- 동일한 소스 코드도 CPU 속도, 컴파일러 최적화, 프로그래밍 언어에 따라 실제 실행 시간(초)이 달라진다. 따라서 절대적인 시간(초) 단위로는 알고리즘 간 공정한 성능 비교가 불가능하다.
- 그래서 "입력 데이터 크기 n이 커짐에 따라 연산 횟수가 어떤 비율로 증가하는가"에 초점을 맞춘다. 이 추세는 환경과 무관한 알고리즘 고유의 성질이다.

### 코드에서 복잡도 함수 f(n)을 도출하는 방법
- 소스 코드의 반복문과 재귀 호출 구조를 분석하여 연산 횟수를 센다. 단일 반복문은 n번 순회하므로 선형 증가 구조를 가진다.
- 이중 반복문은 n번 순회하는 반복문 내부에 다시 n번 순회하는 구조가 있으므로 n×n, 즉 n²번 실행된다. 탐색 범위를 매번 절반으로 줄이면 밑이 2인 로그(log n) 비율로 증가한다.

### 증가율이 실제로 얼마나 벌어지는가 (수치 예시)
- 데이터 N이 1,000건일 때, 선형 알고리즘은 1,000번, 로그를 포함한 선형 알고리즘은 약 10,000번, 제곱 알고리즘은 1,000,000번 연산한다.
- 데이터 N이 1,000,000건으로 늘어나면, 제곱 알고리즘은 1조 번을 연산해야 하므로 선형로그 알고리즘보다 약 5만 배 더 긴 시간이 필요하다.
- 이 때문에 대규모 데이터 환경에서는 복잡도 등급의 작은 차이가 실제 서비스 적용 가능 여부를 결정짓는다.

### 공간복잡도도 반드시 고려해야 하는 이유
- 공간 복잡도는 입력 데이터를 제외하고 알고리즘이 별도로 사용하는 추가 메모리 공간이다.
- 깊이가 n인 재귀 함수를 호출하면 콜 스택 메모리가 깊이만큼 누적되어 선형 메모리를 차지하며, 병합 정렬은 임시 배열을 생성하므로 데이터 크기와 동일한 선형 메모리가 추가로 필요하다.
- 연산 속도가 아무리 빠르더라도 메모리 사용량이 시스템 한계를 초과하면 OOM(Out of Memory) 프로세스 강제 종료가 발생하므로 두 축을 균형 있게 고려해야 한다.

## 연결 개념
- 002 빅오 표기법 — f(n)에서 증가 추세에 지배적인 항만 남겨 상한을 표기하는 규칙
- 013 동적 계획법 — 시간-공간 트레이드오프를 극한으로 활용해 다항 시간 내에 최적해를 구하는 기법

# 📝 【답안용】 시험 답안 템플릿

> 목적: 시험장에서 25분에 그대로 쓰는 답안 양식. 작성방식(추상표현 금지·수치·도식·문제유형 전환)을 엄격히 지킨다.
> 핵심: 이 시험은 정보를 많이 나열하는 시험이 아니라, 문제 신호어에서 출제자 의도를 읽고 핵심 논점을 선별해 쓰는 시험이다.

## 핵심 인사이트 (3줄 요약)

> 1. **본질**: 하드웨어 환경과 무관하게 알고리즘의 자원 소모 증가 추세를 객관적으로 평가하는 척도임.
> 2. **가치**: 입력 데이터 n이 극단적으로 커질 때 시스템의 SLA(p99 지연시간 등) 충족 여부를 코드 구현 전에 예측함.
> 3. **판단 포인트**: 클라우드 환경에서는 연산량 감소를 위해 메모리를 추가 할당하는 Time-Space Trade-off 전략을 우선 검토함.

## 출제 의도 및 답안 포인트

| 출제 의도 | 반드시 짚을 핵심 | 감점 회피 포인트 |
|:---|:---|:---|
| 알고리즘 평가 척도의 본질 이해 검증 | 시간·공간 복잡도의 개념과 두 자원 간의 상충 관계 | 특정 하드웨어의 절대 실행 시간을 성능 기준으로 서술 |
| 자원 예측 및 시스템 설계 역량 평가 | 주요 증가율 등급(O(1)~O(n²))과 트레이드오프 판단 기준 | 시간과 공간을 서로 무관한 독립적 지표로만 병렬 나열 |

> 요약: 시간과 공간은 독립적 지표가 아니며, 가용 자원 한계에 맞춰 두 자원을 맞바꾸는 설계 역량이 핵심임.

---

## Ⅰ. 개요 및 필요성

- 정의: 입력 데이터 크기 n의 증가에 따라 알고리즘의 연산 횟수와 메모리 요구량이 증가하는 추세를 수학적으로 나타내는 척도임
- 배경: 실행 환경(CPU 클럭, OS, 언어)에 의존하는 절대 시간 측정 방식으로는 알고리즘 간 객관적 성능 비교가 불가함
- 필요성: 대용량 데이터 처리에서 O(n²) 설계는 트래픽 증가 시 응답 지연 임계치 초과 장애를 유발하므로 사전 복잡도 분석이 필수임

---

## Ⅱ. 구조 및 구성요소

```text
입력 요구사항 n -> 코드 로직 분석 -> 복잡도 함수 f(n) 도출 -> [시간 복잡도 / 공간 복잡도] -> 자원 트레이드오프 조정
```

| 구성요소 | 역할 | 특이사항 |
|:---|:---|:---|
| 시간 복잡도 | 알고리즘의 실행 연산 횟수 평가 | 대입·비교·사칙연산 등 기본 연산 횟수를 n의 함수로 표현함 |
| 공간 복잡도 | 알고리즘의 추가 메모리 소모 평가 | 입력 데이터 저장 영역을 제외한 고정 및 가변 할당 메모리를 측정함 |
| 트레이드오프 | 두 자원 축 간의 비율 교환 | 메모이제이션(공간↑)으로 중복 연산(시간↓)을 제거하는 등 상충 관계를 조율함 |

> 요약: 복잡도 분석은 코드에서 도출한 연산 횟수와 추가 메모리 요구량을 기준으로 두 자원의 상충 관계를 파악함.

---

## Ⅲ. 동작원리 및 흐름도

```text
입력 로직 파악 -> 제어 구조 내 연산 횟수 산출 -> 다항식 f(n) 결합 -> 트레이드오프 기반 최적화 수행
```

- 1단계 [제어 구조 분석]: 소스 코드 내부의 반복문 중첩 횟수와 재귀 함수 호출 깊이를 식별함
- 2단계 [연산 함수 도출]: 식별된 구조를 바탕으로 전체 기본 연산 횟수를 n에 대한 다항식으로 산출함
- 3단계 [지배항 확인]: n이 무한히 커질 때 비용 증가율을 좌우하는 최고차항을 선별함
- 4단계 [최적화 수행]: 시스템 자원 제약 사항에 맞춰 반복 계산을 캐싱으로 대체하는 등 튜닝을 진행함

> 요약: 코드 제어 구조에서 연산 함수를 도출하고 최고차항을 파악한 뒤 자원 한계에 맞춰 튜닝하는 흐름임.

---

## Ⅳ. 주요 복잡도 증가율 등급
- 상수(O(1)): 입력 데이터 크기와 무관하게 일정한 비용 발생 — 해시 테이블의 키 조회, 배열 인덱스 직접 접근
- 로그(O(log n)): 데이터 크기가 2배 늘어날 때 연산은 1회만 증가 — 이진 탐색 트리 검색, B-Tree 인덱스 탐색
- 선형(O(n)): 입력 데이터 크기에 정비례하여 비용 증가 — 정렬되지 않은 배열의 선형 탐색, 단순 단일 반복문
- 선형로그(O(n log n)): 최적화된 범용 비교 정렬 알고리즘의 한계선 수준 — 퀵 정렬, 병합 정렬, 힙 정렬
- 제곱(O(n²)): 데이터 크기가 2배 늘어날 때 연산 비용은 4배로 폭증 — 이중 중첩 반복문, 버블 정렬, 선택 정렬

> 요약: 실무의 대용량 데이터 처리 시스템은 데이터 증가에 따른 지연 방지를 위해 O(n log n) 이하의 효율성을 확보해야 함.

## Ⅴ. 심화 비교 및 적용 판단

| 구분 | Time 우선 최적화 (공간 자원 투자) | Space 우선 최적화 (연산 지연 감수) | 선택 기준 |
|:---|:---|:---|:---|
| 데이터 구조 | 메모이제이션 배열 및 캐시 활용 | 변수 재사용 및 In-place 갱신 | 응답 지연 민감도와 메모리 가용량 |
| 자원 효율성 | 추가 메모리 급증, 연산 제거로 응답성 향상 | 메모리 최소화 달성, CPU 누적 부하 증가 | 대용량 분산 캐시 인프라 구축 가능 여부 |
| 운영 위험도 | 캐시 동기화 지연 및 OOM 발생 가능성 | 대규모 요청 인입 시 CPU 타임아웃 발생 | Read Heavy 서비스는 Time 최적화 우선 |

> 요약: 클라우드 등 메모리 확장이 용이한 환경에서는 공간 자원을 소모하여 응답 시간을 단축하는 것이 실무 표준임.

**리스크·대응:**
- 캐시 정합성 훼손: 변경 데이터에 대한 캐시 무효화 통제 부재가 원인 → 캐시 갱신 정책 동기화 적용 (지표: 캐시 적중률 및 정합성 위반 건수)
- 메모리 고갈(OOM) 오류: 무제한적인 결과값 저장으로 힙 메모리 임계치 초과 → LRU 축출 정책 및 크기 상한 설정 (지표: 인스턴스 가용 힙 메모리 량)
- 과도한 조기 최적화: n이 작은 구간에서 복잡한 캐싱 구조 선도입 시 오버헤드 증가 → 프로파일링으로 병목 구간 식별 후 부분 도입 (지표: 캐시 오버헤드 지연 시간)

## Ⅵ. 실무 적용 및 결론

**적용 방안 3개:**
1. 대용량 쿼리 최적화: 테이블 풀 스캔(O(n))을 유발하는 쿼리에 B-Tree 인덱스를 생성하여 탐색 비용을 O(log n)으로 통제함
2. 반복 데이터 캐싱: 동일 파라미터를 갖는 외부 API 호출 결과를 인메모리 스토어(O(1))에 캐싱하여 전체 응답 지연을 방지함
3. 엣지 디바이스 설계: 가용 메모리가 수 MB로 제한된 환경에서는 추가 공간 할당을 배제하는 In-place 알고리즘을 도입하여 안정성을 확보함

**결론 (2줄):**
- 기술사 판단: 복잡도 지표는 절대적 기준이 아니며, 데이터 규모가 작을 때는 상수항이 실효 성능을 지배하므로 데이터 볼륨 예측이 최우선임.
- 향후 방향: 마이크로서비스 확산에 따라 단일 함수 레벨의 복잡도를 넘어 분산 노드 간 네트워크 왕복 횟수를 합산한 통합 분석 체계가 요구됨.
