# 📖 【암기용】 개념 완전 이해

## 한눈에
- **개요**: 알고리즘 시간복잡도와 공간복잡도는 입력 크기(N) 증가에 따른 연산량과 메모리 사용량의 증가율을 정량화한 지표이다.
- **왜 필요한가**: 실행 환경(CPU 속도, 언어)에 종속되지 않고 알고리즘 자체의 효율성을 객관적으로 평가하고 비교하기 위해 필요하다.
- **핵심 직관**: 10명의 데이터를 처리할 때 10초, 100명을 처리할 때 100초가 걸리는 알고리즘과 10000초가 걸리는 알고리즘은 본질적으로 다르다.

## 핵심 용어 정리

| 용어/표기 | 의미 | 비유·예 |
|:---|:---|:---|
| 시간 복잡도 (Time Complexity) | 입력 크기 N에 대한 기본 연산(비교, 덧셈 등) 수행 횟수의 함수 | 손님이 늘어날 때 주방장의 요리 횟수가 얼마나 늘어나는가 |
| 공간 복잡도 (Space Complexity) | 입력 크기 N에 대한 메모리 공간(변수, 배열 등) 사용량의 함수 | 손님이 늘어날 때 필요한 추가 접시가 몇 개나 늘어나는가 |
| 점근적 표기법 (Asymptotic Notation) | N이 무한히 커질 때의 증가 추세를 표현하는 수학적 기호 (Big-O 등) | 잔돈은 무시하고 가장 큰 단위의 지폐만 세는 것 |

## 깊이 이해
- **배경·문제의식**: 같은 알고리즘이라도 슈퍼컴퓨터와 스마트폰에서 실행 시간(초)은 다르다. 초 단위 측정은 기계 성능에 종속되므로, "입력 데이터가 10배 커질 때 연산량이 몇 배 커지는가"라는 추세(증가율)를 기계 독립적인 지표로 삼아야 했다.
- **작동 원리**: 코드 내의 루프(반복문)와 재귀 호출 횟수를 N의 함수로 도출한다. 
  - `for (i=0; i<N; i++)` -> N번 연산 -> 시간 복잡도 O(N). 
  - `int arr[N]` -> N 크기 배열 할당 -> 공간 복잡도 O(N).
  - 전체 식을 구한 뒤, 가장 빠르게 증가하는 최고차항만 남기고 상수와 하위 항은 제거한다.
- **비유**: 서울에서 부산까지 갈 때 걷기(O(N²)), 자전거(O(N)), KTX(O(1))를 비교하는 것. KTX 출발 시간이 10분 지연(상수항)되더라도, 거리가 무한히 멀어지면 결국 KTX가 압도적으로 빠르다.
- **구체 예시**: N=1,000,000일 때, O(N)은 1백만 번 연산(수 ms)이지만, O(N²)은 1조 번 연산으로 며칠이 걸린다.
- **흔한 오해·주의점**: 공간 복잡도는 메모리 가격 하락으로 경시되곤 하나, 임베디드 기기나 대규모 분산 처리 시스템(메모리 초과로 인한 OOM 현상)에서는 여전히 치명적인 병목이 된다. 시간과 공간은 종종 트레이드오프(메모이제이션 등) 관계에 있다.

## 연결 개념
- 빅오 표기법 (002 참조): 복잡도를 구체적으로 표현하는 수학적 표기 (상한, 하한 등).
- 동적 프로그래밍 (013 참조): 공간(메모리)을 희생하여 시간(연산량)을 줄이는 대표적 기법.

# 📝 【답안용】 시험 답안 템플릿

## 핵심 인사이트 (3줄 요약)

> 1. **본질**: 알고리즘 복잡도는 하드웨어 성능에 독립적으로, 입력 크기 N에 대한 연산량(시간)과 메모리(공간)의 증가 추세를 나타내는 객관적 지표다.
> 2. **가치**: 빅데이터와 실시간 서비스 환경에서, N이 극단적으로 커질 때 시스템이 멈추지 않고 SLA를 달성할 수 있는지 사전 검증하는 척도가 된다.
> 3. **판단 포인트**: 현대 시스템에서는 대용량 메모리 기반의 캐싱, 메모이제이션을 통해 공간 복잡도를 늘려 시간 복잡도를 O(1)이나 O(log N)으로 낮추는 트레이드오프 전략이 핵심이다.

## 출제 의도 및 답안 포인트

| 출제 의도 | 반드시 짚을 핵심 | 감점 회피 포인트 |
|:---|:---|:---|
| 알고리즘 평가의 객관적 기준 이해 확인 | 기계 독립적 지표, 시간-공간 트레이드오프 구조 | 특정 언어나 기기의 수행 시간(초)으로 단정 |
| 시스템 성능 병목 예측 및 최적화 역량 | 점근적 표기법, 시간/공간 복잡도의 상호 보완성 | 공간 복잡도를 불필요한 지표로 축소 |
| 대용량 데이터 처리 아키텍처 설계 판단 | 캐싱(메모이제이션), 인메모리 처리 등 실무 적용 방안 | 단순 개념 나열, 수치적 한계 누락 |

> 요약: 시간·공간 복잡도는 N 증가에 따른 성능 붕괴를 예방하기 위한 사전 검증 도구이며, 둘 간의 트레이드오프 관리가 핵심이다.

## Ⅰ. 개요 및 필요성

- 개요: 알고리즘 복잡도는 하드웨어 독립적으로 입력 크기 N 증가에 따른 연산 횟수(시간)와 메모리 할당량(공간)의 증가율을 정량화한 지표임
- 배경: 기기 성능 차이로 인한 실행 시간(초) 측정의 한계를 극복하고 알고리즘 자체의 효율성을 객관화할 필요성 대두
- 필요성: N=10^6 이상의 빅데이터 처리 시, O(N²) 설계는 SLA p95 200ms를 초과하므로 개발 전 복잡도 사전 분석이 필수임

---

## Ⅱ. 구조 및 구성요소

```text
알고리즘 설계(요구사항) -> 시간 복잡도(연산량) 분석 -> 점근적 표기법 도출 -> 시간-공간 트레이드오프 최적화
                          |
                          +-> 공간 복잡도(메모리) 분석 -> OOM(Out of Memory) 검증
```

| 구성요소 | 역할 | 특이사항 |
|:---|:---|:---|
| 시간 복잡도 (Time Complexity) | N 증가에 따른 기본 연산(비교·조건·할당 등) 횟수 추이 도출 | 최고차항이 병목 결정 (상수·하위항 무시) |
| 공간 복잡도 (Space Complexity) | N 증가에 따른 고정 공간 및 동적 할당 공간(배열·스택 등) 추이 도출 | 재귀 호출의 콜 스택 메모리 포함 |
| 점근적 표기법 (Asymptotic Notation) | 다항식으로 도출된 복잡도를 O, Ω, Θ 기호로 추상화 | 극한 추세를 표현 (002 빅오 표기법 상세) |

> 요약: 알고리즘 복잡도는 시간(연산)과 공간(메모리) 분석으로 나뉘며, 점근적 표기법을 통해 극한의 증가 추세로 추상화된다.

---

## Ⅲ. 동작원리 및 흐름도

```text
코드 구조 식별 -> 단위 연산 및 메모리 할당 산출 -> 다항식 구성 -> 최고차항 추출 -> 점근적 표기법 산출
```

- 1단계 [코드 구조 식별]: 반복문(for, while), 재귀 호출, 동적 배열, 자료구조 크기 확인
- 2단계 [단위 비용 산출]: 반복문 중첩 횟수에 따른 연산량 합산, N 비례 메모리 할당량 합산
- 3단계 [다항식 구성]: T(n) = aN² + bN + c 형태로 전체 연산량·메모리 함수 정의
- 4단계 [최고차항 추출]: 극한(N→∞) 상태에서 영향력이 작은 상수항(c)과 하위항(bN) 제거 후 표기법 산출

> 요약: 코드 내 반복·재귀 구조를 다항식으로 변환하고, 극한 조건에서 최고차항만 추출하여 복잡도를 도출한다.

---

## Ⅳ. 특징

- 기계 독립성: 실행 플랫폼(CPU, 메모리 대역폭)에 무관하게 알고리즘 자체 논리적 효율성 비교 가능
- 극한 추세 중심: N이 무한대로 수렴할 때를 가정하므로, N이 매우 작을 때는 상수항이 큰 O(1)보다 O(N)이 빠를 수도 있음
- 상호 배타적 교환성: 실행 시간을 줄이기 위해 메모리를 추가 할당(캐싱)하거나, 메모리를 아끼기 위해 재계산(시간 소요)하는 상호 교환 성질 지님

> 요약: 기계에 독립적인 극한 추세 평가 지표이며, 시간과 공간 자원은 서로 교환(Trade-off) 가능한 특징이 있다.

---

## Ⅴ. 심화 비교 및 적용 판단

| 비교 축 | 시간 집중 최적화 | 공간 집중 최적화 | 시간-공간 균형 (Trade-off) | 선택 기준 |
|:---|:---|:---|:---|:---|
| 구조 | In-place 연산 최소화, 다중 캐시 | 변수 재사용, 재계산, 직렬화 | Memoization, 동적 프로그래밍 | 시스템 요구 제약 조건 |
| 비용/성능 | 메모리 사용량 급증, 실행 지연 최소 | CPU 연산량 급증, 메모리 최저 | 메모리 일부 희생, 연산 대폭 감소 | 지연속도 vs 메모리 한계 |
| 운영/위험 | OOM(Out of Memory) 발생 위험 | CPU 과부하, SLA 타임아웃 위험 | 캐시 무효화 및 데이터 정합성 관리 | 허용 가능한 인프라 스케일링 |

> 요약: 서비스 특성(실시간성 vs 임베디드)에 따라 시간과 공간 중 어느 자원을 희생할지 트레이드오프 전략을 선택해야 한다.

**리스크·대응 (기본은 불릿):**
- 재귀 깊이 초과 리스크: N 증가로 인한 콜 스택 오버플로우 발생 -> 꼬리 재귀(Tail Recursion) 최적화 또는 반복문(Iteration) 전환 (지표: 최대 스택 깊이)
- 메모리 누수 리스크: 공간 복잡도 분석에 없는 런타임 동적 할당 미해제 -> 가비지 컬렉션(GC) 튜닝 및 명시적 메모리 해제 (지표: 메모리 사용률 추세)

**도입 후 점검 지표 (기본은 불릿):**
- 성능/효율: p99 응답시간 200ms 이하 — APM 툴을 통한 엔드포인트 응답시간 측정
- 품질/운영: 피크 타임 메모리 사용률 80% 이하 — Prometheus/Grafana 컨테이너 리소스 모니터링

## Ⅵ. 실무 적용 및 결론

**적용 방안 3개:**
1. 아키텍처 설계 시: Redis, Memcached 등 인메모리 캐시를 도입하여 공간 복잡도를 늘리고 DB 조회 시간 복잡도를 O(1)로 단축
2. 대용량 데이터 처리: O(N log N) 이상의 셔플링 방지를 위해 MapReduce 패턴 적용 및 데이터 파티셔닝(Sharding) 분산 처리
3. 코드 리뷰 파이프라인: SonarQube 등 정적 분석 도구를 CI/CD에 연동하여 중첩 루프(O(N²)) 등 고복잡도 안티패턴 자동 차단

**결론 (2줄):**
- 기술사 판단: 클라우드 환경에서는 메모리 확장이 용이하므로, 공간 복잡도를 희생(캐시 증설)하여 시간 복잡도를 단축하는 설계가 일반적인 해법임
- 향후 방향: AI 모델 최적화(Quantization, Pruning) 영역에서 시간-공간 복잡도 단축이 엣지 컴퓨팅 확산의 핵심 과제로 대두됨
