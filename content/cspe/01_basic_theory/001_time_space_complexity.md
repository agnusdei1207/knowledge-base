# 📖 【암기용】 개념 완전 이해

## 한눈에
- **개요**: 시간·공간 복잡도는 **알고리즘 효율성**을 재는 정량 지표로, 입력 크기 N이 커질 때 '연산 횟수'와 '메모리 사용량'이 얼마나 빨리 늘어나는지의 **증가율**을 나타낸다.
- **왜 필요한가**: CPU 속도·언어 같은 실행 환경에 휘둘리는 '초 단위 측정' 대신, 기계와 무관하게 알고리즘 자체를 비교할 객관적 잣대가 필요하기 때문이다.
- **핵심 직관**: N이 10→100으로 10배 커질 때 연산이 10배 느는 알고리즘(O(N))과 100배 느는 알고리즘(O(N²))은 규모가 커질수록 하늘과 땅 차이가 된다.

## 핵심 용어 정리 (내부에 등장하는 것들)

답안용 Ⅰ~Ⅵ에 나오는 내부 용어를 먼저 비유와 함께 세워 둔다. 맨 위는 이 개념이 소속된 상위 핵심 키워드다.

| 용어/표기 | 의미 | 비유·예 |
|:---|:---|:---|
| 알고리즘 효율성 (상위 키워드) | 같은 문제를 더 적은 연산·메모리로 푸는 정도 | 같은 목적지를 덜 걷고 도착하는 길 |
| 시간 복잡도 (Time Complexity) | N에 대한 기본 연산 횟수의 증가 함수 | 손님 N명일 때 주방장이 칼질하는 총 횟수 |
| 공간 복잡도 (Space Complexity) | N에 대한 추가 메모리 사용량의 증가 함수 | 손님 N명일 때 더 꺼내야 하는 접시 수 |
| 기본 연산 (Basic Operation) | 비교·대입·산술처럼 1회로 세는 최소 단위 연산 | 요리에서 "칼질 1번"을 1로 세는 것 |
| 다항식 T(n) | 연산 횟수를 N의 식으로 쓴 것 (aN²+bN+c 꼴) | 총요리시간 = 손질 + 조리 + 세팅 |
| 최고차항 | T(n)에서 N이 클 때 가장 빨리 커지는 항 | 코끼리·개미를 같이 재면 코끼리 무게가 지배 |
| 상수항·계수 | N과 무관한 고정 비용(c)·항 앞 배수(a,b) | 출발 전 준비 10분 — 거리 멀면 무의미해짐 |
| 점근적 표기법 | N→∞ 추세만 남긴 표기(O/Ω/Θ), 002에서 상세 | 잔돈은 무시하고 가장 큰 지폐 단위만 세기 |
| 콜 스택 (Call Stack) | 재귀 호출이 쌓이는 메모리 영역 | 함수가 부른 함수를 접시처럼 쌓은 탑 |
| OOM (Out of Memory) | 가용 메모리 초과로 프로세스가 죽는 장애 | 접시 둘 자리가 없어 주방이 마비됨 |
| 트레이드오프 (Trade-off) | 시간을 줄이면 공간이 늘고 반대도 성립하는 교환 | 미리 계산해 적어두면(공간↑) 다시 안 셈(시간↓) |

## 깊이 이해
- **배경·문제의식**: 같은 알고리즘도 슈퍼컴퓨터와 스마트폰에서 실행 시간(초)이 다르다. 초 단위는 기계 성능에 종속되므로, "입력이 10배 커지면 연산이 몇 배가 되는가"라는 증가율을 기계 독립적 지표로 삼는다.
- **작동 원리 (어떻게 + 왜)**:
  - 코드의 반복문·재귀를 N의 함수로 센다. `for(i<N)` → N회 → 시간 O(N), 이중 중첩 for → N×N → O(N²). `int arr[N]` → 공간 O(N), 재귀 깊이 N → 콜 스택 O(N).
  - 전체 식 `T(n)=aN²+bN+c`에서 **왜 최고차항만 남기는가**: N=10⁶이면 N²=10¹²가 되어 나머지 N=10⁶·상수 c를 완전히 압도한다. 큰 N에서 하위항·상수는 오차 수준이라 버려도 순위가 안 바뀐다.
- **비유**: 서울→부산 갈 때 걷기(O(N²))·자전거(O(N))·KTX(O(1)) 비교. KTX 준비 10분(상수항)이 붙어도 거리가 멀어질수록 KTX가 압도적으로 빠르다.
- **구체 예시 (수치로)**: 초당 10⁸ 연산 기준, N=10⁶에서 O(N)은 약 10⁶회(수 ms)로 끝나지만 O(N²)은 10¹²회(약 2.8시간)로 폭발한다. O(log₂N)은 단 20회다. 등급별 증가폭은 아래 표와 같다.

| N | O(1) | O(log₂N) | O(N) | O(N log N) | O(N²) |
|:---:|:---:|:---:|:---:|:---:|:---:|
| 10 | 1 | 약 3 | 10 | 약 33 | 100 |
| 1,000 | 1 | 약 10 | 1,000 | 약 1만 | 100만 |
| 1,000,000 | 1 | 약 20 | 100만 | 약 2천만 | 1조 |

- **흔한 오해·주의점**: 메모리가 싸져 공간 복잡도를 경시하곤 하나, 임베디드 기기나 대규모 분산 처리에서는 OOM으로 치명적 병목이 된다. 시간과 공간은 자주 트레이드오프(메모이제이션: 공간을 써서 재계산 시간을 줄임) 관계다.

## 연결 개념
- **빅오 표기법 (002)**: 여기서 도출한 복잡도를 O/Ω/Θ로 정식화하는 하위 표기 체계.
- **정렬 알고리즘 (003)**: O(N²)↔O(N log N) 성능 격차가 가장 극명하게 드러나는 사례.
- **동적 프로그래밍·메모이제이션**: 공간을 희생해 시간을 줄이는 트레이드오프의 대표 기법.

# 📝 【답안용】 시험 답안 템플릿

## 핵심 인사이트 (3줄 요약)

> 1. **본질**: 알고리즘 복잡도는 N 증가에 따른 연산량(시간)과 메모리(공간)의 증가 추세를 나타내는 기계 독립적 효율성 지표임.
> 2. **가치**: 빅데이터 환경에서 N이 비대해질 때 SLA·가용성 달성 가능 여부를 개발 이전에 사전 검증하는 척도가 됨.
> 3. **판단 포인트**: 현대 시스템은 공간 복잡도를 늘려(캐싱) 시간 복잡도를 낮추는 트레이드오프 판단이 최적화의 핵심임.

## 출제 의도 및 답안 포인트

| 출제 의도 | 반드시 짚을 핵심 | 감점 회피 포인트 |
|:---|:---|:---|
| 알고리즘 평가의 객관적 기준 이해 | 기계 독립성, 시간-공간 트레이드오프 구조 | 특정 언어·기기의 수행 시간(초)으로 단정 |
| 성능 병목 예측·최적화 역량 | 최고차항 중심 추출, 시간·공간의 상호 보완 | 공간 복잡도를 불필요 지표로 축소 |
| 대용량 처리 아키텍처 설계 판단 | 캐싱·인메모리 등 트레이드오프 적용 방안 | 개념 나열에 그치고 수치적 한계 누락 |

> 요약: 시간·공간 복잡도는 N 증가에 따른 성능 붕괴를 사전 검증하는 도구이며, 둘 간 트레이드오프 관리가 핵심임.

## Ⅰ. 개요 및 필요성
- 개요: N 증가에 따른 연산량·메모리 사용량의 증가율을 정량화한 지표임
- 배경: 기기 성능차로 인한 실행 시간(초) 측정의 한계를 극복하고 알고리즘 자체 효율을 객관화할 필요 대두
- 필요성: N=10⁶ 이상 처리 시 O(N²) 설계는 SLA p95 200ms를 초과하므로 개발 전 복잡도 사전 분석이 필수임

## Ⅱ. 구조 및 구성요소
선형 구조도 (분석 파이프라인):

    알고리즘 설계 -> 시간 복잡도 분석 -> 다항식 도출 -> 최고차항 추출 -> 트레이드오프 최적화
                 / 공간 복잡도 분석 -> OOM 검증

| 구성요소 | 역할 | 특이사항 |
|:---|:---|:---|
| 시간 복잡도 | N 증가에 따른 기본 연산(비교·조건·대입) 횟수 추이 도출 | 최고차항이 병목 결정, 상수·하위항 무시 |
| 공간 복잡도 | N 증가에 따른 고정·동적 할당 메모리 추이 도출 | 재귀 콜 스택 메모리 포함 |
| 점근적 표기법 | 도출된 다항식을 O/Ω/Θ 기호로 추상화 | 극한 추세 표현, 002 빅오에서 상세 |

> 요약: 복잡도 분석은 시간(연산)·공간(메모리) 두 축으로 나뉘며, 점근적 표기법으로 극한 증가 추세로 추상화됨.

## Ⅲ. 동작원리 및 흐름도
선형 흐름도:

    코드 구조 식별 -> 단위 연산·메모리 산출 -> 다항식 구성 -> 최고차항 추출 -> 표기법 산출

1. 코드 구조 식별: 반복문·재귀 호출·동적 배열 등 N에 비례하는 지점 확인
2. 단위 비용 산출: 반복 중첩 횟수로 연산량 합산, N 비례 메모리 할당량 합산
3. 다항식 구성: `T(n)=aN²+bN+c` 형태로 전체 연산·메모리 함수 정의
4. 최고차항 추출: N→∞ 극한에서 상수항 c·하위항 bN 제거 후 표기법 확정

> 요약: 반복·재귀 구조를 다항식으로 변환하고 극한 조건에서 최고차항만 추출해 복잡도를 도출함.

## Ⅳ. 특징
- 기계 독립성: 실행 플랫폼(CPU·메모리 대역폭)과 무관하게 알고리즘 논리 효율만 비교 가능함
- 극한 추세 중심: N→∞ 가정이므로 N이 작을 땐 상수가 큰 O(1)이 O(N)보다 느릴 수도 있음
- 시간-공간 교환성: 시간을 줄이려 메모리를 더 쓰거나(캐싱), 메모리를 아끼려 재계산하는 상호 교환 성질을 지님

## Ⅴ. 심화 비교 및 적용 판단

| 구분 | 시간 우선 최적화 | 공간 우선 최적화 | 시간-공간 균형 |
|:---|:---|:---|:---|
| 대표 기법 | 다중 캐시, 룩업 테이블 | 변수 재사용, 재계산, 스트리밍 | 메모이제이션, 동적 프로그래밍 |
| 자원 부담 | 메모리 급증·지연 최소 | CPU 급증·메모리 최소 | 메모리 일부 희생·연산 대폭 감소 |
| 주요 위험 | OOM 발생 | SLA 타임아웃 | 캐시 무효화·데이터 정합성 |

> 요약: 실시간성 요구(속도) vs 임베디드 제약(메모리)에 따라 어느 자원을 희생할지 트레이드오프 전략을 선택함.

**리스크·대응:**
- 재귀 깊이 초과: N 증가로 콜 스택 오버플로우 발생 → 꼬리 재귀 최적화 또는 반복문 전환 (지표: 최대 스택 깊이)
- 미해제 동적 할당: 분석에 없던 런타임 할당 누수 → GC 튜닝·명시적 해제 (지표: 메모리 사용률 추세)

**점검 지표:**
- 성능: p99 응답시간 200ms 이하 — APM 엔드포인트 측정
- 운영: 피크 메모리 사용률 80% 이하 — Prometheus/Grafana 리소스 모니터링

## Ⅵ. 실무 적용 및 결론

**적용 방안:**
1. 인메모리 캐시(Redis·Memcached) 도입으로 공간을 늘려 DB 조회 시간 복잡도를 O(1) 수준으로 단축
2. O(N log N) 셔플 부하 억제를 위해 MapReduce·데이터 파티셔닝(Sharding)으로 분산 처리
3. SonarQube 정적 분석을 CI/CD에 연동해 중첩 루프(O(N²)) 안티패턴을 병합 전 자동 차단

**결론:**
- 기술사 판단: 클라우드에서는 메모리 확장이 용이하므로, 공간을 희생(캐시 증설)해 시간 복잡도를 낮추는 설계가 조건부로 유효함
- 향후 방향: AI 모델 경량화(Quantization·Pruning)의 시간-공간 단축이 엣지 컴퓨팅 확산의 핵심 과제로 대두됨
