## 미리 알고가기

- **점근 표기(Asymptotic Notation)**: 입력이 무한히 커질 때 알고리즘 비용의 증가율 경향성을 표현하는 방법론임
- **지배항(Dominant Term)**: 다항식에서 증가율에 가장 큰 영향을 미치는 최고차항이며 복잡도 결정의 기준임
- **상각 분석(Amortized Analysis)**: 최악의 연산이 간헐적으로 발생할 때, 전체 연산에 걸친 평균 비용을 산정하는 방식임

## 1. 개요

- **정의/개념**: 알고리즘이 입력 크기 `n` 증가에 따라 기본 연산을 얼마나 더 수행하고(시간복잡도), 추가 메모리를 얼마나 더 사용하는지(공간복잡도) 함수로 표현해 시스템의 확장성을 판단하는 수학적 분석 기준임
- **배경/필요성**: 데이터 규모가 백만 단위 이상으로 커짐에 따라 알고리즘 간 성능 차이가 기하급수적으로 벌어지므로, 실제 구현 전 설계 단계에서 요구사항(시간 지연, 메모리 한계)을 충족하는지 검증할 척도가 필요함

## 2. 특징 및 비교

시간과 공간은 상호 교환(Trade-off) 관계에 있으며, 시스템 제약 조건에 따라 하나를 희생해 다른 하나를 최적화함.

| 판단 기준 | 시간복잡도 (Time Complexity) | 공간복잡도 (Space Complexity) |
|:---|:---|:---|
| 측정 대상 | 비교, 대입, 탐색 등 기본 연산의 반복 횟수 | 입력 데이터 외 알고리즘 실행에 필요한 보조 메모리 양 |
| 제약 초과 시 현상 | 응답 지연(Latency), 처리량 감소, 타임아웃 발생 | OOM(Out of Memory) 장애, GC 오버헤드, 스와핑 |
| 표기 방식 | `T(n) = O(f(n))` | `S(n) = O(f(n))` |
| 최적화 기법 | 메모이제이션, 인덱스, 해시 테이블 적용 (공간 희생) | 인플레이스(In-place) 처리, 스트리밍 처리 (시간 희생) |

> 요약: 시간복잡도는 처리 속도의 한계를, 공간복잡도는 메모리 자원의 한계를 판단하며 설계 시 양립 관계를 조율해야 함.

## 3. 구성요소/구조

시간·공간복잡도를 분석하기 위해서는 입력과 기본 연산을 명확히 정의하고 비용 함수를 도출해야 함.

- **구성요소**: 복잡도 분석의 핵심 요소

| 구성요소 | 역할 및 산출 기준 | 핵심 포인트 |
|:---|:---|:---|
| 입력 크기 (`n`) | 배열 길이, 정점(`V`)/간선(`E`) 등 성능을 좌우하는 중심 변수 정의 | 환경에 맞는 입력 변수 도출 |
| 기본 연산 | 반복문 내 핵심 로직(비교, 대입)과 재귀 호출 횟수 산정 | 시간 비용 산출 기준 확보 |
| 보조 공간 | 임시 배열, 해시 테이블, 콜 스택 등 추가 할당 메모리 양 | 공간 비용 산출 기준 확보 |
| 분석 시나리오 | 데이터 상태에 따른 점근적 상한(최악), 하한, 평균치 분리 | 서비스 SLA 보장 수준 결정 |

- **분석 절차**:

```text
+----------+      +----------+      +----------+      +----------+
| 변수식별 | ---> | 함수도출 | ---> | 지배항추출 | ---> | 표기확정 |
+----------+      +----------+      +----------+      +----------+
```

1. **입력/연산 식별** — 성능에 직접적인 영향을 주는 입력 `n`과 가장 빈번히 발생하는 기본 연산을 정의함
2. **비용 함수 도출** — 총 연산 횟수와 공간 사용량을 `n`에 대한 다항식 `f(n)`으로 수학적으로 도출함
3. **지배항 추출** — `f(n)`에서 상수항과 하위 차수 항을 제거해 입력 크기에 가장 민감한 최고차항만 남김
4. **표기 확정** — 최종적으로 `O(n log n)` 등 점근적 표기법으로 확정해 알고리즘 선택의 근거로 활용함

## 4. 문제점 및 개선방안

1. **상수항 무시로 인한 실제 성능 왜곡**: `O` 표기법은 점근적 증가율만 보므로, 입력 `n`이 작을 때 상수항이 큰 `O(1)`이 상수항이 작은 `O(n)` 알고리즘보다 오히려 느릴 수 있음
   - **개선방안**: 점근 표기에만 의존하지 않고, 실제 운영 데이터 규모 구간에서 벤치마킹을 수행해 p95/p99 지연시간을 측정함 (확인: 실측 레이턴시 프로파일링 데이터)

2. **최악의 경우(Worst Case) 고려 누락**: 평균 `O(1)`인 해시 테이블을 무비판적으로 적용하면 악의적인 해시 충돌 공격 시 `O(n)`으로 시스템이 마비될 수 있음
   - **개선방안**: 요구사항이 엄격한 실시간 시스템에서는 최악의 성능을 보장하는 알고리즘(예: 트리 구조 맵)을 선정하거나 Timeout 통제를 구현함 (확인: 악의적 최악 입력 시나리오 테스트)

3. **재귀 호출에 따른 공간복잡도 한계 간과**: 시간복잡도만 고려하여 깊은 재귀 연산을 수행하면 힙 메모리가 아닌 콜 스택(Call Stack) 초과로 StackOverflow 장애가 발생함
   - **개선방안**: 재귀 최대 깊이를 사전에 추정해 꼬리 재귀(Tail Recursion) 최적화를 적용하거나 명시적 반복문(Loop)과 스택 자료구조로 변환함 (확인: 런타임 스택 메모리 피크 모니터링)

## 5. 실무 적용 사례

| 적용 영역 | 적용 방식 | 확인 지표 |
|:---|:---|:---|
| 대용량 데이터 조인 처리 | `O(n²)` 수준의 Nested Loop 조인을 메모리를 더 쓰는 해시 조인(`O(n)`)으로 변경 | 총 배치 실행 시간, CPU/메모리 사용률 |
| 엣지/IoT 기기 소프트웨어 | 메모리 제약이 심한 환경에서 보조 배열이 필요한 알고리즘 대신 In-place 알고리즘 적용 | 가용 램(RAM) 용량 추이, OOM 장애 발생률 |
| API 서버 성능 최적화 | 반복 계산에 의한 CPU 부하와 응답 지연을 줄이기 위해 Redis 기반 메모이제이션 캐시 적용 | p99 응답시간 단축, 외부 스토리지 캐시 적중률 |

> 요약: 인프라 제약(메모리 용량 제한)과 서비스 제약(응답시간 SLA) 중 병목 요소를 먼저 파악해 시간-공간의 트레이드오프를 결정함.

## 6. 결론

시간복잡도와 공간복잡도는 알고리즘이 대규모 데이터 환경에서 지속 가능한지, 장애 없이 운영될 수 있는지를 평가하는 가장 기초적이고 핵심적인 설계 판단 기준임. 기술사는 단순히 표기법상 수치가 낮은 것만 추구할 것이 아니라, 가용 인프라 자원과 목표 성능(SLA)을 종합적으로 분석해 시간과 공간 중 무엇을 희생하고 최적화할지 결정해야 함. 특히 운영 환경에서는 이론적인 점근적 복잡도 외에도 캐시 지역성(Cache Locality), 상수항 오버헤드, 네트워크 I/O 등을 고려한 실측 기반 튜닝을 반드시 병행해야 함.
