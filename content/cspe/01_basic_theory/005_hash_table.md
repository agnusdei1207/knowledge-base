# 📖 【암기용】 개념 완전 이해

## 한눈에
- **개요**: 해시 테이블(Hash Table)은 **해시 함수**로 키를 배열 인덱스(버킷)로 변환해, 정렬·탐색 구간 없이 **평균 O(1)**에 삽입·검색·삭제하는 자료구조다.
- **왜 필요한가**: 이진 탐색(004)조차 O(log N)이고 정렬을 요구하지만, "키를 곧바로 저장 위치로 계산"하면 비교 없이 단번에 접근할 수 있기 때문이다(O(1)의 성능 의미는 001·002 참조).
- **핵심 직관**: "값을 어디 뒀는지 찾지 말고, 키만 보고 둘 자리를 계산해서 바로 거기 넣고 바로 거기서 꺼낸다" — 사물함 번호를 이름으로 계산하는 방식이다.

## 핵심 용어 정리 (내부에 등장하는 것들)

O(1) 탐색을 가능케 하는 핵심은 '주소 계산'과 '충돌 처리'다. 여기서 그 고유 용어를 세운다. 맨 위는 상위 핵심 키워드다.

| 용어/표기 | 의미 | 비유·예 |
|:---|:---|:---|
| 해시 테이블 (상위 키워드) | 키→인덱스 계산으로 O(1) 접근하는 구조 | 이름으로 사물함 번호를 계산해 바로 여는 방식 |
| 해시 함수 (Hash Function) | 키를 고정 범위 정수(인덱스)로 변환하는 함수 | 이름을 넣으면 사물함 번호가 나오는 계산기 |
| 버킷/슬롯 (Bucket) | 값이 실제 저장되는 배열의 한 칸 | 번호가 매겨진 사물함 한 칸 |
| 충돌 (Collision) | 서로 다른 키가 같은 인덱스로 계산되는 현상 | 두 사람의 이름이 같은 사물함 번호로 나옴 |
| 체이닝 (Chaining) | 한 버킷에 연결 리스트로 여러 값을 매다는 충돌 해결 | 같은 사물함에 칸막이 여러 개를 이어 붙임 |
| 개방 주소법 (Open Addressing) | 충돌 시 다른 빈 버킷을 찾아 넣는 방식 | 사물함이 차 있으면 다음 빈 칸으로 이동 |
| 로드 팩터 (Load Factor) | 저장된 원소 수 ÷ 버킷 수 (α) | 사물함 사용률 — 높을수록 충돌 잦음 |
| 리해싱 (Rehashing) | α가 임계치 초과 시 버킷을 늘려 재배치 | 사물함이 붐비면 더 큰 캐비닛으로 이사 |

## 깊이 이해
- **배경·문제의식**: 004까지의 탐색은 "저장된 것들과 비교해서 위치를 찾는" 방식이라 최소 O(log N)이다. "비교 없이 키에서 위치를 곧바로 산출"할 수 있다면 O(1)이 되는데, 이 산출을 담당하는 것이 해시 함수다. 다만 무한한 키를 유한한 버킷에 매핑하므로 **충돌**이 필연적으로 생긴다 — 이 충돌을 어떻게 푸느냐가 해시 테이블 설계의 핵심이다.
- **작동 원리 (어떻게+왜)**:
  - 삽입: `index = hash(key) % 버킷수`를 계산해 해당 버킷에 (키, 값)을 저장한다.
  - 검색: 같은 함수로 index를 재계산해 그 버킷만 보므로, 데이터가 아무리 많아도 비교가 상수 번이다 — O(1)의 근거다.
  - 충돌 해결: ① **체이닝** — 버킷마다 연결 리스트(006)를 달아 같은 index끼리 매단다. ② **개방 주소법** — 충돌 시 정해진 규칙(선형·이차 탐사, 이중 해싱)으로 다음 빈 버킷을 찾는다.
- **비유**: 도서관에서 책을 일일이 뒤지는(탐색) 대신, 청구기호(해시 함수)로 꽂을 서가 위치를 계산해 바로 그 칸에 넣고 바로 그 칸에서 꺼낸다. 같은 칸이 겹치면(충돌) 칸 안에 순서대로 끼워 두거나(체이닝) 옆 빈 칸으로 민다(개방 주소법).
- **구체 예시**: 버킷 10개에 키 27을 넣으면 `27 % 10 = 7`번 버킷이다. 키 37도 `37 % 10 = 7`이라 충돌한다. 로드 팩터 α가 0.75를 넘으면 충돌 연쇄로 성능이 O(N)에 근접하므로, 보통 α≥0.75에서 버킷을 2배로 리해싱한다.
- **흔한 오해·주의점**:
  - **O(1)은 평균이고 최악은 O(N)이다.** 나쁜 해시 함수나 악의적 키로 모두 한 버킷에 몰리면 체인이 리스트가 돼 O(N)으로 퇴화한다(해시 DoS).
  - **순서가 없다.** 해시 테이블은 정렬·범위 검색을 지원하지 않는다 — 그런 요구엔 이진 탐색(004)·트리가 맞다.
  - 좋은 해시 함수는 키를 버킷에 **균등 분산**시켜야 하며, 편향되면 충돌이 급증한다.

## 연결 개념
- **이진 탐색 (004)**: 정렬 기반 O(log N) 탐색으로, O(1)·무순서인 해시와 대비되는 대안.
- **연결 리스트 (006)**: 체이닝에서 각 버킷의 충돌 원소를 매다는 실제 구조.
- **B-Tree·인덱스**: 범위 검색이 필요한 DB에서 해시 인덱스 대신 쓰는 정렬형 대안.

# 📝 【답안용】 시험 답안 템플릿

## 핵심 인사이트 (3줄 요약)

> 1. **본질**: 해시 테이블은 해시 함수로 키를 버킷 인덱스로 변환해 비교 없이 평균 O(1)에 접근하는 자료구조임.
> 2. **가치**: 캐시·인덱스·중복 제거·집합 연산에서 대용량 키를 상수 시간에 조회해 시스템 응답성을 결정함.
> 3. **판단 포인트**: 충돌 해결 방식과 로드 팩터 관리가 O(1) 유지의 관건이며, 순서·범위 검색이 필요하면 부적합함.

## 출제 의도 및 답안 포인트

| 출제 의도 | 반드시 짚을 핵심 | 감점 회피 포인트 |
|:---|:---|:---|
| O(1) 탐색 원리 이해 | 해시 함수 주소 계산·평균 O(1)의 근거 | 최악 O(N) 미언급, O(1) 무조건 단정 |
| 충돌 해결 기법 숙지 | 체이닝 vs 개방 주소법 원리·장단 | 충돌을 예외로만 취급, 필연성 누락 |
| 성능 유지 전략 도출 | 로드 팩터·리해싱·균등 분산 | 정렬·범위 검색 가능하다는 오류 |

> 요약: 해시 함수 O(1) 원리, 충돌 해결 두 기법, 로드 팩터 관리로 O(1)을 유지하는 전략까지 연결해야 함.

## Ⅰ. 개요 및 필요성
- 개요: 해시 함수로 키를 버킷 인덱스로 변환해 평균 O(1)에 저장·조회하는 자료구조임
- 위치: (004 이진 탐색의 O(log N)·정렬 전제를 넘어 비교 없는 상수 시간 접근을 지향하는 탐색 구조임)
- 배경: 비교 기반 탐색은 최소 O(log N)이고 정렬 유지 비용이 발생함
- 필요성: 캐시·세션·인덱스에서 대용량 키를 상수 시간에 조회해야 하므로 필수임

## Ⅱ. 구조 및 구성요소
선형 구조도 (키 → 저장 위치):

    키(Key) -> 해시 함수 h(key) -> 인덱스 = h(key) % 버킷수 -> 버킷 배열 저장
                                            / 충돌 없음 : 해당 버킷에 직접 저장
                                            / 충돌 발생 : 체이닝(리스트 연결) 또는 개방 주소법(빈 버킷 탐사)

| 구성요소 | 역할 | 특이사항 |
|:---|:---|:---|
| 해시 함수 | 키를 버킷 인덱스로 변환 | 균등 분산·빠른 계산이 핵심 |
| 버킷 배열 | (키,값) 쌍의 실제 저장 공간 | 크기가 로드 팩터를 좌우 |
| 충돌 해결기 | 같은 인덱스 다중 키 처리 | 체이닝(리스트) / 개방 주소법(탐사) |
| 로드 팩터 관리 | α 임계 초과 시 리해싱 트리거 | 통상 α 0.75에서 버킷 2배 확장 |

> 요약: 해시 함수가 키를 버킷으로 매핑하고, 충돌 해결기와 로드 팩터 관리로 평균 O(1)을 유지함.

## Ⅲ. 동작원리 및 흐름도
선형 흐름도:

    키 입력 -> 해시 계산 -> 버킷 인덱스 산출 -> 충돌 검사 -> 저장/조회 -> (α 초과 시) 리해싱

1. 해시 계산: 해시 함수로 키를 정수로 변환 후 버킷 수로 모듈러 연산해 인덱스를 산출함
2. 충돌 검사: 해당 버킷이 비었으면 직접 저장, 이미 차 있으면 충돌로 판정함
3. 충돌 해결: 체이닝은 버킷의 리스트에 추가, 개방 주소법은 규칙에 따라 다음 빈 버킷을 탐사함
4. 부하 관리: 로드 팩터가 임계치를 넘으면 버킷을 확장하고 전체 키를 재배치(리해싱)함

> 요약: 해시 계산으로 버킷을 정하고 충돌을 해결하며, 로드 팩터 초과 시 리해싱으로 O(1)을 지킴.

## Ⅳ. 특징
- 상수 시간: 해시 함수로 위치를 직접 계산해 평균 삽입·검색·삭제가 O(1)임
- 무순서성: 키가 버킷에 분산 저장돼 정렬·범위 검색을 지원하지 못함
- 충돌 필연성: 유한 버킷에 무한 키를 매핑하므로 충돌이 불가피해 해결 기법이 필수임
- 최악 퇴화: 편향 해시나 해시 DoS로 한 버킷에 집중되면 O(N)으로 저하됨

## Ⅴ. 심화 비교 및 적용 판단

충돌 해결 두 기법을 캐시 지역성·삭제·부하 축에서 대조함.

| 구분 | 체이닝 | 개방 주소법 |
|:---|:---|:---|
| 저장 방식 | 버킷마다 연결 리스트에 매달기 | 충돌 시 다른 빈 버킷에 탐사 저장 |
| 로드 팩터 | α>1도 동작(리스트 연장) | α<1 유지 필수(빈 칸 필요) |
| 캐시 지역성 | 낮음(리스트 포인터 추적) | 높음(배열 연속 접근) |
| 삭제 처리 | 리스트 노드 제거로 단순 | 탐사 경로 보존 위해 tombstone 필요 |

> 요약: 삭제·부하 변동이 잦으면 체이닝, 캐시 효율·메모리 밀집이 중요하면 개방 주소법이 유리함.

**리스크·대응:**
- 해시 DoS: 악의적 키 집중으로 한 버킷 O(N) 퇴화 → 시드 랜덤화·암호학적 해시로 예측 차단
- 로드 팩터 과다: α 상승으로 충돌 연쇄 → 임계치(0.75) 도달 시 리해싱으로 버킷 확장
- 편향 분산: 나쁜 해시 함수로 버킷 쏠림 → 균등 분산 해시(MurmurHash 등) 채택

**점검 지표:**
- 성능: 평균 조회 시간과 최악 버킷 체인 길이 — 분포 실측
- 부하: 로드 팩터 추이와 리해싱 발생 빈도 — 메모리·지연 트레이드오프 점검

## Ⅵ. 실무 적용 및 결론

**적용 방안:**
1. 인메모리 캐시: Redis·Memcached의 키-값 저장에 해시로 O(1) 조회를 구현해 DB 부하 경감
2. DB 해시 인덱스: 등가 조회(`WHERE id = ?`) 전용 인덱스로 해시를 써 B-Tree 대비 상수 시간 조회
3. 중복 제거·집합 연산: HashSet으로 대용량 로그의 유일 키 판별을 O(1)에 수행해 O(N²) 비교 회피

**결론:**
- 기술사 판단: 등가 조회 중심이면 해시가 최적이나, 범위·정렬 요구가 있으면 B-Tree 인덱스로 전환해야 함
- 향후 방향: 분산 환경에서는 노드 증감 시 재배치를 최소화하는 일관된 해싱(Consistent Hashing)으로 확장하는 것이 표준임
