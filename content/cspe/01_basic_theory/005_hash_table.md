# 005. 해시 테이블 (Hash Table) [출제: ]

## 미리 알고가기

- **해시 충돌 (Hash Collision)**: 서로 다른 키가 동일한 해시 값을 가져 같은 버킷 위치에 배정되는 현상임
- **적재율 (Load Factor)**: 전체 버킷 개수 대비 저장된 데이터 수의 비율($\alpha = n/m$)이며, 성능 저하의 지표가 됨
- **일관 해싱 (Consistent Hashing)**: 노드 추가/삭제 시 데이터 재배치를 최소화하기 위해 해시 링(Ring) 구조를 사용하는 기법임

## Ⅰ. 개요

- **정의/개념**: 해시 테이블은 키(Key)를 해시 함수(Hash Function)에 통과시켜 얻은 인덱스를 기반으로 버킷(Bucket) 배열에 값(Value)을 저장하여, 평균 $O(1)$의 시간복잡도로 삽입·삭제·검색을 수행하는 자료구조임
- **배경/필요성**: 데이터가 방대해질수록 비교 기반 탐색($O(\log n)$)은 연산 비용이 증가함. 키와 저장 위치를 직접 매핑함으로써 비교 연산을 제거하고, 실시간 세션 관리, 캐싱, 중복 체크 등 초고속 조회가 필요한 영역에서 확장성을 보장하기 위해 사용함

## Ⅱ. 특징 및 비교

해시 테이블은 단일 건 조회의 극단적 효율성을 제공하는 대신, 메모리 낭비와 순서 정보의 부재라는 트레이드오프를 가짐.

| 비교 항목 | 해시 테이블 (Hash Table) | 이진 탐색 트리 (BST) | 정렬 배열 (Sorted Array) |
|:---|:---|:---|:---|
| 검색 복잡도 | **평균 $O(1)$**, 최악 $O(n)$ | $O(\log n)$ (균형 시) | $O(\log n)$ |
| 순서 보존 | **보존 불가** (무작위) | 보존 가능 (In-order 순회) | 보존 가능 |
| 범위 검색 | 지원 불가 (전수 조사 필요) | 효율적 지원 | 매우 효율적 지원 |
| 충돌 관리 | 해시 함수 및 충돌 처리 필수 | 균형 유지(Rotation) 필수 | 관리 요소 없음 |
| 공간 효율 | 버킷 오버헤드 존재 (희소 배열) | 포인터 오버헤드 존재 | 우수 (추가 메모리 없음) |

> 요약: 키 하나를 콕 집어 찾는 작업(Point Query)에는 해시가 최적이며, 범위(Range)나 순차 조회가 필요하면 트리 계열을 선택함.

## Ⅲ. 구성요소/구조

해시 테이블은 키를 변환하는 논리부와 충돌을 수용하는 물리 저장부로 구성됨.

- **구성요소**:
  - **해시 함수**: 키를 균등하게 흩뿌려 충돌을 최소화하는 알고리즘 (MurmurHash, CityHash 등)
  - **버킷/슬롯 (Bucket/Slot)**: 데이터가 실제로 저장되는 배열의 각 칸
  - **충돌 처리 메커니즘**: 동일 인덱스 발생 시 데이터를 수용하는 전략 (Chaining, Open Addressing)
  - **리사이즈 (Rehashing)**: 적재율 임계치 도달 시 버킷을 확장하고 재배치하는 프로세스

- **충돌 처리 방식 비교 (원리/흐름도)**:

```text
[분리 연결법 (Chaining)]           [개방 주소법 (Open Addressing)]
Bucket [0] -> [Key A] -> [Key B]   Bucket [0] [Key A]
Bucket [1] [null]                  Bucket [1] [Key B] (Next Empty Slot)
Bucket [2] [Key C]                 Bucket [2] [Key C]
(충돌 시 연결 리스트/트리 사용)      (충돌 시 빈 공간을 탐색하여 저장)
```

1. **Chaining (분리 연결법)**: 충돌 발생 시 해당 버킷에 연결 리스트나 Red-Black Tree를 연결하여 수용함. 삭제가 쉽고 버킷 확장이 덜 빈번하나, 포인터 메모리 사용량이 많음
2. **Open Addressing (개방 주소법)**: 충돌 시 선형 탐사(Linear Probing)나 이차 탐사 등을 통해 다른 빈 버킷을 찾아 저장함. 메모리 밀집도가 높아 캐시 효율이 좋으나, 클러스터링(뭉침) 현상에 취약함

## Ⅳ. 문제점 및 개선방안

1. **해시 충돌로 인한 최악 성능 ($O(n)$) 발생**: 특정 버킷에 데이터가 몰릴 경우 탐색 시간이 선형적으로 증가하여 캐시 무력화 및 시스템 지연을 유발함
   - **개선방안**: 자바의 HashMap처럼 체인 길이가 길어지면 리스트를 트리로 전환(Treeify)하거나, 고성능 해시 함수를 적용하여 균등 분포를 유도함 (확인: 최대 체인 길이 모니터링)

2. **해시 DoS (Denial of Service) 공격 취약**: 악의적으로 충돌을 유발하는 다수의 키를 전송하여 서버 CPU 자원을 고갈시킬 수 있음
   - **개선방안**: 해시 함수에 무작위 시드(Salt)를 추가하여 실행 시마다 해시 값을 예측 불가능하게 만들거나, 요청당 처리 시간을 제한함 (확인: 공격 시나리오별 CPU 점유율)

3. **리사이즈 시의 서비스 정지 (Stop-the-world)**: 버킷 확장 및 재해싱 과정에서 전체 테이블에 락(Lock)이 걸리거나 대량의 복사가 발생함
   - **개선방안**: 한 번에 다 옮기지 않고 조회/삽입 시마다 조금씩 옮기는 **점진적 재해싱 (Incremental Rehashing)**을 적용함 (확인: 리사이즈 시점의 $p99$ 지연시간)

## Ⅴ. 실무 적용 사례

| 적용 영역 | 적용 방식 | 확인 지표 |
|:---|:---|:---|
| 인메모리 DB (Redis, Memcached) | 세션 정보, 캐시 데이터를 키-값 쌍으로 저장하여 밀리초 이하의 응답 보장 | OPS (Operations Per Second), 적재율 |
| 분산 시스템 샤딩 | 일관 해싱(Consistent Hashing)을 통해 노드 추가 시 데이터 이동을 최소화하며 부하 분산 | 재배치 데이터 비율, 노드별 부하 편차 |
| 네트워크 패킷 처리 | 흐름 식별자(5-tuple)를 해시하여 상태 테이블(State Table)에서 연결 정보 고속 조회 | 초당 패킷 처리량 (PPS), 충돌 발생률 |
| 컴파일러/인터프리터 | 변수명, 함수명을 심볼 테이블(Symbol Table)에 저장하여 유효 범위 검사 및 호출 시 참조 | 컴파일 속도, 메모리 오버헤드 |

> 요약: 단일 서버 내 고속 검색부터 대규모 분산 환경의 부하 분산까지 현대 컴퓨팅의 중추적 역할을 수행함.

## Ⅵ. 결론

해시 테이블은 '비교' 대신 '계산'을 통해 데이터를 찾는 혁신적인 구조로, 현대의 실시간 대용량 시스템을 가능케 한 핵심 기법임. 기술사는 단순히 평균 $O(1)$의 속도에 만족하지 않고, 최악의 시나리오인 해시 충돌과 리사이즈에 의한 지연을 제어할 수 있는 운영 역량을 갖추어야 함.

특히 클라우드 네이티브 환경에서는 노드의 유동적 변화를 수용할 수 있는 일관 해싱에 대한 깊은 이해가 필요하며, 보안 관점에서의 해시 DoS 방어 전략도 함께 고려되어야 함. 결국 해시는 속도와 공간, 예측 가능성 사이의 균형을 맞추는 고도의 설계 기술이며, 이를 정확히 다루는 것이 시스템 안정성의 척도가 됨.
