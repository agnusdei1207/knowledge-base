## 미리 알고가기

- 해시 함수: 임의 길이의 데이터를 고정된 크기의 고유한 정수 인덱스값으로 변환하는 함수임
- 충돌(Collision): 서로 다른 두 개의 키가 해시 함수를 거친 후 동일한 버킷 인덱스로 매핑되는 현상임
- 버킷(Bucket): 해시 테이블 내부에서 데이터가 실제로 저장되는 개별 슬롯 또는 메모리 공간임
- 적재율(Load Factor): 전체 버킷 개수 대비 현재 저장된 원소 수의 비율로, 성능 저하와 확장 시점의 지표임

## Ⅰ. 개요

- **정의/개념**: 해시 테이블은 키(Key)를 해시 함수로 연산하여 얻은 고정된 인덱스를 기반으로 값을 저장하고 조회하는 키-값($Key-Value$) 기반의 고속 자료구조임
- **배경/필요성**: 대용량 세션 관리, 캐싱, 중복 검사 등에서 $O(\log n)$ 트리 검색보다 빠른 즉각적 조회가 요구되므로, 메모리 공간을 소모하는 대신 탐색 시간을 평균 $O(1)$로 단축할 구조가 필요함

## Ⅱ. 특징

- 키를 통해 데이터 저장 위치를 직접 계산하므로 삽입, 삭제, 조회의 평균 시간복잡도가 $O(1)$에 수렴하여 대규모 키 매칭 업무에 최적화됨
- 해시 충돌이 특정 버킷에 집중될 경우 내부적으로 연결 리스트나 트리 탐색 비용이 추가되어 최악의 경우 성능이 $O(n)$으로 퇴화할 수 있음
- 데이터가 함수에 의해 무작위로 분산 배치되므로 키 간의 선후 관계가 사라져 범위 검색($Range$ $Query$)이나 정렬된 순회에는 부적합함

## Ⅲ. 종류 및 비교

| 판단 기준 | 해시 테이블 (Hash Table) | 이진 탐색 트리 (BST/AVL) | 정렬 배열 (Sorted Array) |
|:---|:---|:---|:---|
| **조회 성능** | 평균 $O(1)$ / 최악 $O(n)$ | 평균·최악 $O(\log n)$ | $O(\log n)$ (이진탐색) |
| **순서 보전** | 불가 (무작위 분산) | 가능 (중위 순회) | 가능 (인덱스 순차) |
| **충돌 대응** | 체이닝, 개방 주소법 필요 | 불필요 (키 값에 따라 분기) | 불필요 |
| **주요 용도** | 단건 조회, 캐시, 중복체크 | 범위 검색, 데이터 정렬 유지 | 읽기 전용 참조 데이터 |

> 요약: 단일 키 기반의 고속 조회가 목적이면 해시 테이블이 유리하며, 범위 검색이나 정렬된 결과가 필요하면 트리 구조를 선택함.

## Ⅳ. 구성요소 및 구조

| 구성요소 | 설명 |
|:---|:---|
| 해시 함수 | 키를 버킷 인덱스로 변환하는 핵심 로직이며, 고른 분산을 통해 충돌 발생 확률을 최소화해야 함 |
| 버킷/슬롯 | 데이터(또는 데이터의 포인터)를 실제로 보관하는 배열 형태의 저장 공간임 |
| 충돌 해결 구조 | 동일 버킷 매핑 시 연결 리스트로 잇는 체이닝($Chaining$)이나 다른 빈 칸을 찾는 개방 주소법($Open$ $Addressing$)을 사용함 |
| 재해싱 정책 | 적재율 임계치 도달 시 버킷 크기를 확장하고 모든 키를 다시 배치하여 성능 저하를 방지하는 메커니즘임 |

```text
[ 해시 처리 구조 ]
+----------+      +-----------+      +----------+      +----------+
|  Input   | ---> | Hash Func | ---> | Indexing | ---> | Collision |
|   Key    |      | (Calculation)    | (Mapping) |      | Handling |
+----------+      +-----------+      +----------+      +----------+
```

## Ⅴ. 원리 및 절차 흐름도

```text
+-------------+     +--------------+     +-------------+     +-------------+
| 해시값 생성  | --> | 인덱스 매핑   | --> | 충돌 여부 확인 | --> | 데이터 입출력 |
+-------------+     +--------------+     +-------------+     +-------------+
```

1. **해시 생성** — 입력 키를 해시 함수에 입력하여 고유한 정수 형태의 해시값을 산출함
2. **인덱스 매핑** — 산출된 해시값을 테이블의 전체 버킷 크기로 나누어(나머지 연산 등) 실제 저장될 배열 위치를 결정함
3. **충돌 확인** — 결정된 위치에 이미 데이터가 있는지 확인하고, 있다면 설정된 충돌 해결 방식($Chaining$ 등)에 따라 처리함
4. **입출력** — 최종적으로 확정된 위치에 값을 저장하거나, 해당 위치의 키가 찾으려는 키와 일치하는지 대조하여 값을 반환함

## Ⅵ. 실무 적용 및 유의점

1. 특정 버킷에 의도적으로 충돌을 유발하여 시스템 부하를 높이는 해시 충돌 공격($HashDoS$)에 대비해, 매 실행 시마다 다른 무작위 시드($Salt$)를 해시 함수에 적용하고 체인 길이가 길어질 경우 이진 트리로 전환하는 방어 기법을 도입해야 함
2. 초기 버킷 크기가 작으면 빈번한 재해싱($Rehashing$)으로 인해 순간적인 성능 스파이크가 발생하므로, 예상되는 데이터 규모를 고려하여 초기 용량을 여유 있게 설정하고 적재율을 0.7~0.8 수준으로 관리해야 함

## Ⅶ. 결론

- 해시 테이블은 공간을 활용해 최적의 탐색 성능을 제공하는 핵심 자료구조이지만 충돌 처리와 재해싱 비용이 수반되므로, 업무 요건에 맞는 적절한 해시 함수 선택과 충돌 방어 전략을 함께 구축해야 함
