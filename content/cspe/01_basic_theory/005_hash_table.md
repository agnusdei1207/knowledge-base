# 📖 【암기용】 개념 완전 이해

> 목적: 이 개념을 처음 보는 사람도 완벽히 이해하게 만든다. 시험 답안 양식이 아니라, 이해를 위한 친절한 설명이다.

## 한눈에
- **개요**: **해시 함수**를 통해 입력된 키(Key)를 배열의 인덱스로 직접 변환하여 값(Value)을 저장하고 조회하는 평균 **O(1)** 자료구조
- **왜 필요한가**: 수억 건의 회원 데이터 중 특정 유저의 정보를 찾을 때, 데이터를 처음부터 순회하거나 트리를 타고 내려갈 필요 없이 키만 넣으면 즉시 저장된 메모리 위치가 튀어나오게 만들어 조회 지연 시간을 완전히 제거하기 위함이다.
- **핵심 직관**: 거대한 도서관에서 책을 찾을 때, 목차를 뒤지지 않고 책 제목을 마법의 계산기(해시 함수)에 넣었더니 "3층 15번 서가"라는 정확한 좌표가 바로 나와 걸어가는 것과 같다.

## 핵심 용어 정리

| 용어 | 의미 | 비유 |
|:---|:---|:---|
| 해시 함수 | 다양한 길이의 문자열이나 숫자(Key)를 고정된 길이의 정수 인덱스로 변환하는 수학 함수 | 이름을 넣으면 호텔 방 번호가 나오는 계산기 |
| 버킷(Bucket) | 해시 테이블 내에서 값(Value)을 실제로 저장하는 배열의 한 칸 | 호텔의 각 객실 |
| 충돌(Collision) | 서로 다른 Key가 해시 함수를 거쳤는데 하필 같은 인덱스 번호를 부여받는 현상 | 두 명의 손님이 똑같은 방 번호를 배정받음 |
| 체이닝(Chaining) | 충돌이 났을 때, 해당 버킷에 연결 리스트를 매달아 여러 데이터를 줄줄이 엮어 저장하는 기법 | 같은 방에 2층 침대를 겹쳐서 계속 더 놓음 |
| 개방 주소법(Open Addressing) | 충돌이 났을 때, 원래 배정받은 버킷을 포기하고 테이블 내의 다른 빈 버킷을 찾아 이동 저장하는 기법 | 원래 방이 찼으니, 옆의 빈 방으로 안내함 |
| 적재율(Load Factor) | 전체 버킷 개수 대비 현재 저장된 데이터 개수의 비율 — 성능 저하를 막기 위한 리해싱의 기준점 | 호텔 방이 75% 찼으니 증축 공사를 시작하라는 신호 |

## 깊이 이해

### O(1) 조회가 도대체 어떻게 가능한가 (핵심 원리)
- 원리는 매우 단순하다. 찾고자 하는 Key를 해시 함수에 넣어 무작위처럼 보이는 큰 정수(해시 코드)를 얻어낸다. 그리고 그 정수를 전체 버킷의 개수로 나눈 나머지(mod 연산)를 구하면, 그것이 바로 배열의 인덱스가 된다.
- 배열은 인덱스 번호만 알면 메모리 주소를 즉시 계산해 단번에 찾아갈 수 있다. 따라서 데이터가 10건이든 1억 건이든 계산 한 번에 위치가 나오므로 평균 속도가 O(1)이 된다.
- 이를 위해서는 좋은 해시 함수가 필요하다. 좋은 해시 함수는 입력된 Key들을 버킷 배열 전체에 고르게 흩뿌려 쏠림 현상을 막는다.

### 충돌은 왜 반드시 생기며, 왜 피할 수 없는가
- 사람이 만들 수 있는 Key의 조합(예: 모든 단어)은 사실상 무한대지만, 컴퓨터 메모리에 잡는 버킷 배열의 크기는 유한하다.
- 비둘기집 원리에 따라, n개의 방에 n+1마리의 비둘기가 들어가면 반드시 어느 한 방에는 두 마리 이상이 들어간다. 따라서 서로 다른 Key가 같은 인덱스(방 번호)로 매핑되는 충돌은 이론적으로 회피가 불가능하며, 오직 어떻게 대응할 것인가의 문제만 남는다.

### 두 가지 충돌 대응 전략 (조회 방식의 차이)
- **체이닝(Chaining)**: 충돌이 나면 그 배열 칸에 연결 리스트 포인터를 달아 데이터를 추가한다. 조회를 할 때는 인덱스에 찾아간 뒤 연결 리스트를 순차적으로 훑어 진짜 Key가 일치하는 노드를 찾는다. 데이터 삭제가 매우 쉽지만 리스트 포인터로 인한 추가 메모리를 쓴다.
- **개방 주소법(Open Addressing)**: 충돌이 나면 다음 빈칸(+1칸씩 이동하거나 2차식으로 이동)을 찾아 배열 내부를 맴돈다. 포인터 메모리가 낭비되지 않아 CPU 캐시 효율은 좋지만, 특정 구역에 데이터가 뭉치는 군집(Clustering) 현상이 생기면 조회 속도가 뚝 떨어진다. 게다가 중간에 있는 데이터를 삭제하면 연결 고리가 끊어져 후속 조회가 막히므로 삭제 처리가 매우 까다롭다.

### 적재율(Load Factor)과 지연 스파이크(리해싱)
- 통상적으로 적재율(데이터 수 / 버킷 수)이 0.75를 넘어가면 충돌 빈도가 기하급수적으로 늘어난다.
- 이를 막기 위해 버킷 배열의 크기를 약 2배로 늘리고, 기존 데이터를 전부 새 해시 함수(모듈러 연산)에 맞춰 다시 흩뿌리는 작업(리해싱)을 한다.
- 문제는 데이터가 1억 건일 때 리해싱이 발생하면 한순간에 1억 번의 O(n) 복사 작업이 일어나 수 초의 시스템 멈춤(지연 스파이크)이 발생한다는 점이다. 실무에서는 이를 막기 위해 요청이 들어올 때마다 조금씩 옮기는 점진적 리해싱(Incremental Rehashing) 기법을 쓴다 (예: Redis의 rehash).

### 최악의 성능은 왜 O(N)으로 추락하는가
- 악의적인 해커가 고의로 해시 인덱스가 똑같이 나오는 Key들만 10만 개를 생성해 서버로 날렸다고 치자 (Hash DoS 공격).
- 체이닝 구조라면 한 버킷에 10만 개의 데이터가 일렬로 매달린 거대한 연결 리스트가 된다. 결국 조회를 할 때마다 10만 개를 순차 탐색해야 하므로 O(1) 자료구조가 졸지에 O(N) 자료구조로 전락한다.
- 이를 방어하기 위해 Java의 HashMap은 한 버킷에 노드가 8개를 넘어가면 그 내부를 연결 리스트에서 이진 탐색 트리(Red-Black Tree)로 변형해 최악의 경우에도 O(log N)을 방어하도록 설계되어 있다.

## 연결 개념
- (004 이진 탐색 참조) — O(1)을 제공하는 해시 테이블과 달리 데이터의 정렬과 범위 검색을 지원하는 대안 탐색 기법
- 암호학적 해시(SHA-256) — 테이블용 해시와 달리 충돌 방지와 비가역성에 몰빵한 보안용 특수 해시 알고리즘

# 📝 【답안용】 시험 답안 템플릿

> 목적: 시험장에서 25분에 그대로 쓰는 답안 양식. 작성방식(추상표현 금지·수치·도식·문제유형 전환)을 엄격히 지킨다.
> 핵심: 이 시험은 정보를 많이 나열하는 시험이 아니라, 문제 신호어에서 출제자 의도를 읽고 핵심 논점을 선별해 쓰는 시험이다.

## 핵심 인사이트 (3줄 요약)

> 1. **본질**: 해시 함수를 거친 키(Key)를 고정 길이의 메모리 인덱스 주소로 직접 치환하여 탐색을 수행하는 구조임.
> 2. **가치**: 캐시 아키텍처 및 대규모 분산 저장소에서 데이터 볼륨(N) 증가와 독립적인 밀리초(ms) 단위 O(1) 응답시간을 제공함.
> 3. **판단 포인트**: 완전한 충돌 방지는 수학적으로 불가하므로, 적재율 통제와 충돌 우회 로직(체이닝, 개방주소법) 설계 완성도가 시스템 지연을 좌우함.

## 출제 의도 및 답안 포인트

| 출제 의도 | 반드시 짚을 핵심 | 감점 회피 포인트 |
|:---|:---|:---|
| O(1) 연산 구조 이해 검증 | 해시 함수를 통한 배열 인덱스 맵핑과 버킷 직접 접근 원리 | 충돌 상황을 예외로 치부하고 완전 무결한 알고리즘으로 단정 |
| 충돌 방어 아키텍처 역량 평가 | 체이닝과 개방주소법의 메커니즘 차이 및 메모리 효율 트레이드오프 | 단일 충돌 기법만을 서술하고 기법 간 캐시 효율 비교를 누락 |

> 요약: 해시 테이블은 충돌을 필연적 한계로 수용하며, 충돌 발생 시의 우회 기법과 배열 팽창 임계치(Load Factor) 관리가 핵심 과제임.

## Ⅰ. 개요 및 필요성

- 정의: Key 값을 해시 함수 연산을 통해 고유한 해시 코드로 변환한 뒤, 이를 고정된 버킷 배열의 인덱스로 매핑하여 저장하는 자료구조임
- 배경: 관계형 데이터베이스 인덱스의 O(log n) 트리 탐색 지연조차 수용할 수 없는 초당 수백만 트랜잭션 요구 환경 도래
- 필요성: 시스템 데이터 규모 확장에 비례하여 검색 성능이 저하되지 않도록 분산 캐시 클러스터링 인프라 구축의 근간을 이룸

---

## Ⅱ. 구조 및 구성요소

```text
Key 입력 -> [해시 함수] -> Hash Code (정수) -> Modulo 연산(크기 나눔) -> Bucket 인덱스 -> 충돌 검사 및 저장
```

| 구성요소 | 역할 | 특이사항 |
|:---|:---|:---|
| 키 (Key) | 조회할 원본 식별자 | 문자열 등 임의 길이 입력 수용 가능 |
| 해시 함수 | Key를 정수 인덱스로 해싱 | 데이터 균등 분포 확보가 핵심 성능 지표임 |
| 버킷 (Bucket) | 값(Value)이 적재되는 메모리 슬롯 | 적재율(Load Factor) 제어 필수 대상임 |
| 해시 충돌 | 이종 Key가 동일 버킷을 점유하는 현상 | 무한 입력을 유한 배열에 할당 시 회피 불가능함 |

> 요약: 해시 테이블은 메모리 공간 여유분을 추가 할당하여 선형 탐색의 지연 시간을 연산 비용으로 맞바꾼 구조임.

---

## Ⅲ. 동작원리 및 해시 충돌 제어 흐름도

```text
인덱스 매핑 -> 버킷 상태 검사 -> 비어있음: 정상 적재 처리
                            |-> 기점유 시 대응 A (해당 버킷에 리스트 연결 - Chaining)
                            |-> 기점유 시 대응 B (함수에 따른 빈칸 재탐색 - Open Addressing)
```

- 1단계 [해싱 및 매핑]: 해시 연산 후 버킷 사이즈 기준으로 모듈러(나머지) 연산하여 진입 인덱스를 도출함
- 2단계 [상태 점검]: 해당 버킷 슬롯에 이미 점유 중인 데이터가 존재하는지 확인하여 충돌을 감지함
- 3단계 [충돌 회피 수행]: 체이닝 방식을 쓰면 해당 칸에 노드를 연결하고, 개방주소법을 쓰면 빈 슬롯을 다시 찾음
- 4단계 [리사이징 임계 감시]: 전체 적재 데이터가 사전에 정의된 허용 임계(Load Factor)를 초과하면 배열 확장을 수행함

> 요약: 충돌 발생 감지 시 사전에 채택된 정책에 따라 내부 포인터를 연결하거나 인접 메모리로 대피하는 구조임.

## Ⅳ. 해시 충돌 우회 기법 심화 분할

| 기법 구분 | 처리 방식 | 성능 억제 부작용 (단점) |
|:---:|:---|:---|
| 체이닝 (Chaining) | 동일 인덱스 버킷에 연결 리스트 형태로 외부 확장 연결 | 동적 노드 객체 생성에 따른 캐시 적중률 저하 발생 |
| 개방주소법 (선형 탐사) | 충돌 시 슬롯을 +1씩 이동하며 연속된 빈 공간을 탐색 | 특정 구간에 데이터가 쏠리는 1차 군집화(Clustering) 심화 |
| 개방주소법 (이차 탐사) | 충돌 횟수의 제곱(1, 4, 9...)만큼 폭을 넓히며 공간 탐색 | 1차 군집화는 회피하나 해시값 의존적 2차 군집화 잔존 |
| 개방주소법 (이중 해싱) | 충돌 시 별도의 제2 해시 함수를 구동해 다음 이동 보폭 결정 | 군집화를 원천 억제하나 이중 연산 오버헤드 부하 상승 |

> 요약: 데이터 쏠림 현상을 방어하기 위해 체이닝을 기본 채택하되, 극도의 L1 캐시 속도가 필요할 때 이중 해싱을 접목함.

## Ⅴ. 심화 비교 및 적용 판단

| 비교 축 | 해시 테이블 (Hash Table) | 이진 탐색 트리 (BST) | 선택 기준 분기 |
|:---|:---|:---|:---|
| 평균 조회 성능 | 평균 O(1) 달성 | O(log n) 보장 | 순수 1:1 Key 맵핑 응답 속도가 최우선인가 |
| 데이터 순서 유지 | 해시 연산으로 인한 순서 무작위 산재 | 데이터 크기에 따른 정렬 상태 상시 유지 | 키 정렬 기반의 순차적 순회와 범위 조회 여부 |
| 한계 부하 리스크 | 최악 충돌 심화 시 O(n) 지연 전락 | 노드 재균형(회전) 유지 연산 부하 상존 | 최악 상황에서의 레이턴시 스파이크 통제 필요 여부 |

> 요약: 특정 단건 조회가 압도적으로 많으면 해시 구조를, 복합 범위 검색(Between 쿼리)이 수반되면 트리 구조를 선택함.

**주요 리스크·대응:**
- 동기식 리해싱 지연 락: 적재율 임계(0.75) 돌파 시 2배 확장 리해싱을 단일 스레드로 수행하여 시스템 멈춤 유발 → 클라이언트 요청 시마다 일정 수량만 이관하는 점진적 리해싱 도입 (지표: 인덱스 리빌딩 구간 응답 지연율)
- 해시 DoS 공격 표적: 악의적으로 동일 해시 인덱스를 유도하는 페이로드 대량 인입 시 서버 CPU 고갈 → 시작 시 난수 시드를 결합하는 SipHash 적용 (지표: 단일 버킷 내 최대 할당 체인 길이)

## Ⅵ. 실무 적용 및 결론

**적용 방안 3개:**
1. 메모리 기반 분산 캐시 구축: RDBMS 앞단에 Redis 등을 도입하여 해시 기반 키 맵핑 조회를 통해 백엔드 데이터베이스 I/O 병목을 제거함
2. 최악 응답 지연 방어 트리 변환 적용: Java HashMap 아키텍처와 같이 단일 버킷 체인 노드가 8개를 초과하면 연결 리스트를 레드-블랙 트리로 동적 전환함
3. 일관된 해싱(Consistent Hashing) 분산 라우팅: 노드 스케일아웃 시 전체 데이터 리해싱 방지를 위해 해시 링(Ring)에 데이터를 맵핑시켜 이동 량을 최소화함

**결론 (2줄):**
- 기술사 판단: 해시 테이블은 O(1) 획득을 위해 충돌 우회 비용을 사전 지불하는 공간-시간 치환 구조이므로 데이터 증가량 예측 기반의 버킷 사전 할당이 필수적임.
- 향후 방향: 단일 프로세스 메모리 자료구조의 역할을 넘어 대규모 마이크로서비스 클러스터의 데이터 샤딩 및 트래픽 분산 핵심 알고리즘으로 진화함.
