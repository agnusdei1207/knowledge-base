# 📖 【암기용】 개념 완전 이해

## 한눈에
- **개요**: 키(Key)를 해시 함수에 넣어 배열의 인덱스로 변환한 뒤, 해당 위치에 값(Value)을 저장하는 자료구조다.
- **왜 필요한가**: 데이터가 수백만 개라도 특정 데이터를 찾는 데 평균 **O(1)** (상수 시간)이 걸려, 이론상 가장 빠른 검색/삽입 속도를 낸다.
- **핵심 직관**: 백화점 주차장에서 차 번호(Key)를 주차 요원(해시 함수)에게 말하면 요원이 곧바로 주차장 3층 402호(인덱스)로 직행하는 구조다.

## 핵심 용어 정리

| 용어/표기 | 의미 | 비유·예 |
|:---|:---|:---|
| 해시 함수 (Hash Function) | 무한한 크기의 키를 유한한 배열의 인덱스로 매핑해주는 함수 | 차량 번호를 주차 칸 번호로 바꾸는 규칙 |
| 버킷/슬롯 (Bucket/Slot) | 해시 테이블 배열 내에서 데이터(Value)가 저장되는 실제 공간 | 주차장의 각 개별 주차 칸 |
| 해시 충돌 (Hash Collision) | 서로 다른 두 키가 해시 함수를 통해 동일한 인덱스를 부여받는 현상 | 두 대의 차가 같은 주차 칸 번호를 배정받은 상황 |
| 체이닝 (Chaining) | 충돌 시 같은 인덱스에 연결 리스트를 만들어 데이터를 이어 붙이는 해결책 | 한 주차 칸에 세로로 여러 대를 줄지어 주차시키는 것 |

## 깊이 이해
- **배경·문제의식**: 배열은 인덱스를 알면 O(1)에 찾지만 "이름이 김철수인 데이터"를 찾으려면 O(N)이나 O(log N)이 걸린다. "이름 자체를 인덱스 번호로 계산해 버리면 어떨까?"라는 발상에서 출발했다.
- **작동 원리**:
  1. 저장할 때: 키 "Apple"을 해시 함수 `H(x)`에 넣는다 -> 결과값 `5`가 나온다. 배열의 5번 버킷에 값을 저장한다.
  2. 조회할 때: "Apple"을 검색하면 똑같이 `H("Apple") = 5`가 나온다. 곧바로 배열 5번을 읽는다. 평균 조회 O(1).
- **비유**: 호텔에 1000개의 방이 있는데, 숙박객 이름을 호텔 규칙(해시함수)에 넣으면 방 번호가 바로 나온다. 프론트에서 명단을 뒤질(O(N)) 필요 없이 바로 방을 찾아가면 된다.
- **해시 충돌 (가장 중요한 문제)**: 
  - 방은 1000개인데 올 수 있는 사람 이름 종류는 무한하다(비둘기집 원리). 결국 서로 다른 이름인데 같은 방 번호가 배정되는 일이 생긴다(충돌).
  - 해결책 1 (체이닝): 방 안에 침대를 계속 이어 붙여 같이 재운다(연결 리스트).
  - 해결책 2 (개방 주소법, Open Addressing): 그 방이 찼으면 옆 빈방을 찾아 들어간다(선형 탐사).
- **흔한 오해·주의점**: 해시는 항상 O(1)이라는 것은 "충돌이 적은 평균적인 경우"다. 최악의 경우(모든 키가 같은 버킷에 몰림) 체이닝된 리스트를 선형 탐색해야 하므로 O(N)으로 추락한다. 또한, 값들이 순서대로 저장되지 않으므로 범위 검색(`10~20사이 값 찾기`)은 절대 불가능하다.

## 연결 개념
- 연결 리스트 (006 참조): 체이닝 기법에서 충돌 데이터를 연결하는 구조.
- 이진 탐색 (004 참조): 범위 조회가 필요할 때 해시 대신 선택하는 기법.

# 📝 【답안용】 시험 답안 템플릿

## 핵심 인사이트 (3줄 요약)

> 1. **본질**: 해시 테이블은 Key-Value 쌍을 관리하며, 해시 함수를 통해 Key를 즉시 배열 인덱스로 매핑하여 평균 O(1)의 접근 속도를 내는 자료구조다.
> 2. **가치**: 캐시 시스템(Redis), 세션 관리, 라우팅 테이블 등에서 데이터의 양과 무관하게 지연 없는 실시간 단건 응답을 보장한다.
> 3. **판단 포인트**: 성능 유지를 위해서는 필수불가결한 '해시 충돌(Collision)'을 어떻게 관리(체이닝, 개방 주소법)하고 적정 적재율(Load Factor)을 유지하느냐가 아키텍처 설계의 핵심이다.

## 출제 의도 및 답안 포인트

| 출제 의도 | 반드시 짚을 핵심 | 감점 회피 포인트 |
|:---|:---|:---|
| O(1) 탐색의 원리와 구조 이해 | 해시 함수, 배열 인덱스 매핑, Key-Value 구조 | 알고리즘(MD5 등) 나열에 치우쳐 자료구조 원리 누락 |
| 해시 충돌(Collision)의 필연성 및 해결책 | 비둘기집 원리, 체이닝(Chaining), 개방주소법 비교 | 충돌을 '발생하면 안 되는 에러'로 잘못 서술함 |
| 실무 데이터베이스/캐시 구조 적용 | 단건 조회 최적화 특성과 범위 검색(Range Scan) 불가 제약 | 해시를 B-Tree와 구분 없이 무분별한 만능으로 서술 |

> 요약: 해시 테이블은 O(1) 성능을 내지만 충돌(Collision) 발생이 필연적이므로, 충돌 해결 기법과 Load Factor 관리가 성능의 핵심이다.

---

## Ⅰ. 개요 및 필요성

- 개요: 해시 테이블은 해시 함수를 통해 임의 길이의 Key를 고정 길이 배열의 인덱스로 변환하여 데이터를 평균 O(1) 시간에 CRUD(저장/조회)하는 자료구조임
- 배경: 트리 기반(O(log N))이나 선형(O(N)) 탐색 구조는 N이 수억 건 단위로 증가할 때 단건 조회 응답 지연 한계가 존재함
- 필요성: Redis 캐시, DB 해시 조인, 세션 스토어 등에서 데이터 볼륨에 무관한 실시간 초고속 단건 응답(O(1))이 요구됨

---

## Ⅱ. 구조 및 구성요소

```text
입력 Key -> [해시 함수: H(k)] -> 해시 코드(정수) -> [mod 연산] -> 배열 인덱스
                                                                   |
                                                                   +-> Bucket [0]: Value
                                                                   +-> Bucket [1]: Value (충돌 시 Chaining)
```

| 구성요소 | 역할 | 특이사항 |
|:---|:---|:---|
| 해시 함수 (Hash Function) | Key 값을 고정된 정수값(해시 코드)으로 변환 | 균등 분포(Uniform Distribution) 생성이 품질 좌우 |
| 버킷 (Bucket / Slot) | 해시 테이블(배열) 내에서 Value가 저장되는 물리적 슬롯 | 인덱스 충돌 발생 가능 공간 |
| Load Factor (적재율) | 사용 중인 버킷 수 / 전체 버킷 수의 비율 (N/M) | 일반적으로 0.7~0.75 초과 시 테이블 크기 확장(Resizing) |

> 요약: 해시 테이블은 해시 함수와 배열 버킷으로 구성되며, Key를 인덱스로 즉각 매핑하여 중간 탐색 과정을 생략한다.

---

## Ⅲ. 동작원리 및 흐름도

```text
데이터 입력(Key, Value) -> 해시 함수 H(Key) 산출 -> 인덱스(Bucket) 매핑
  |
  +-> [빈 버킷] 즉시 Value 저장 (O(1))
  +-> [이미 존재] 충돌(Collision) 발생 -> 충돌 해결 알고리즘(체이닝 등) 수행 후 저장
```

- 1단계 [해시 연산]: 문자열 등의 `Key`를 해시 함수에 입력하여 고유한 정수 난수값 도출
- 2단계 [인덱스 매핑]: 도출된 정수를 `테이블 크기 M`으로 Modulo(나머지) 연산하여 최종 버킷 인덱스 확정
- 3단계 [충돌 판정]: 해당 인덱스가 비어있으면 저장, 이미 다른 데이터가 점유 중이면 해시 충돌(Collision)로 판정
- 4단계 [충돌 해결]: Chaining(리스트 연결)이나 Open Addressing(다른 빈칸 탐색) 방식으로 데이터 강제 저장

> 요약: 해시 연산을 통해 인덱스를 산출하고 데이터를 저장하며, 필연적인 충돌 시 정해진 알고리즘에 따라 우회 저장한다.

---

## Ⅳ. 특징

- 단건 처리 속도 우위: 키 기반 단건 읽기/쓰기 성능이 평균 O(1)로 모든 자료구조 중 가장 빠름
- 순서 파괴 (무작위성): 해시 연산 후 데이터가 무작위 인덱스에 산포되므로, 정렬 유지 및 범위 검색(Range Scan)이 원천적으로 불가능함
- 최악의 경우 O(N) 추락: 해시 함수 성능이 나빠 모든 Key가 하나의 버킷에 몰릴 경우, 연결 리스트 선형 탐색과 동일한 O(N)으로 성능 하락

> 요약: 단건 처리에서는 최강의 O(1) 성능을 내지만, 범위 검색이 불가하고 충돌 시 성능이 O(N)으로 저하되는 트레이드오프를 지닌다.

## Ⅴ. 심화 비교 및 적용 판단

| 비교 축 | 체이닝 (Chaining) | 개방 주소법 (Open Addressing) | 선택 기준 |
|:---|:---|:---|:---|
| 충돌 해결 구조 | 버킷에 연결 리스트를 매달아 동적 확장 | 배열 내의 다른 빈 버킷(선형 탐사 등)을 찾아 삽입 | 추가 메모리 할당 허용 여부 |
| 메모리/성능 | 추가 포인터 메모리 필요, 적재율 1 초과 가능 | 추가 메모리 불필요, 캐시 적중률 높음 (배열 연속성) | 데이터 분포 예측성 |
| 운영/위험 | 군집화(Clustering) 영향 적음 | 적재율(>0.7) 증가 시 선형 탐사 성능 급격히 저하 | 삭제 연산 빈도 (Open은 삭제 복잡) |

> 요약: 일반적으로 메모리 제약이 크지 않고 안정적 성능이 필요한 Java 등 실무 환경에서는 연결 리스트 기반의 체이닝 방식을 우선 채택한다.

**리스크·대응 (기본은 불릿):**
- 악의적 해시 충돌 공격(Hash DoS) 리스크: 고의로 같은 버킷에 몰리는 Key를 다량 주입해 서버 CPU 자원 고갈 유발 -> 보안 해시(SipHash 등) 적용 및 체이닝 시 O(log N) 탐색을 위한 Red-Black Tree로 전환 (지표: 버킷당 최대 체인 깊이)
- 적재율(Load Factor) 포화 리스크: 데이터가 가득 차 충돌이 폭증하고 성능 O(N)으로 저하 -> 적재율 75% 도달 시 테이블 크기를 2배로 늘리는 동적 리사이징(Dynamic Resizing) 및 재해시(Re-hashing) 수행 (지표: 실시간 Load Factor)

**도입 후 점검 지표 (기본은 불릿):**
- 성능/효율: 데이터 10배 증가 전후의 단건 Read 응답시간(ms) 변화율 — APM 기반 캐시 Hit/Latency 모니터링
- 품질/운영: 전체 버킷 대비 비어있는 버킷의 비율 및 최대 체인 길이 — JMX 등 런타임 지표 추출

## Ⅵ. 실무 적용 및 결론

**적용 방안 3개:**
1. 분산 캐시 아키텍처: Redis, Memcached 등의 In-Memory 세션 스토어 및 RDBMS 앞단의 룩업(Look-up) 캐시로 적용하여 DB 병목 해소
2. RDBMS 해시 조인(Hash Join): 대용량 테이블 간 동등(Equi) 조인 시 작은 테이블을 메모리에 해시 테이블로 빌드(Build)하여 O(N+M)의 고속 프로브(Probe) 처리 수행
3. 분산 시스템 라우팅: 로드밸런서(L4)나 분산 DB 샤딩(Sharding)에서 사용자 ID를 해싱(Consistent Hashing)하여 특정 노드에 요청을 균등 분산 배치

**결론 (2줄):**
- 기술사 판단: 해시 테이블은 초고속 단건 조회의 필수 구조이나, 동적 리사이징 시 순간적 병목(Stop-the-world)이 발생하므로 시스템 피크타임 전 초기 용량 산정(Capacity Planning)이 선행되어야 함
- 향후 방향: 최근 대규모 분산 스토리지에서는 단일 해시 한계를 넘어, 노드 추가/삭제 시 데이터 이동을 최소화하는 안정 해시(Consistent Hashing) 기법이 분산 아키텍처의 표준으로 자리 잡고 있음
