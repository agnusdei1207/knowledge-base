## 미리 알고가기

- 해시 함수: 키를 고정 범위 인덱스로 변환하는 함수임
- 충돌: 서로 다른 키가 같은 버킷으로 매핑되는 현상임
- 적재율: 저장 원소 수를 버킷 수로 나눈 값으로 성능 저하 지표임

## Ⅰ. 개요

- **정의/개념**: 해시 테이블은 키를 해시 함수로 인덱스화해 버킷에 값을 저장함으로써 평균 $O(1)$ 수준의 조회, 삽입, 삭제를 제공하는 자료구조임
- **배경/필요성**: 세션 관리, 캐시 조회, 중복 검사처럼 정렬 순서보다 즉시 접근이 중요한 업무에서는 비교 기반 탐색보다 키 직접 매핑 방식이 더 적합함

## Ⅱ. 특징

- 평균적으로 매우 빠른 조회 성능을 제공해 고빈도 접근 업무에 유리함
- 충돌 처리 방식과 적재율 관리에 따라 실제 성능이 크게 달라짐
- 정렬 순서를 보존하지 않으므로 범위 조회나 순차 처리에는 부적합함
- 메모리를 더 써서 시간을 줄이는 대표적 구조라서 공간 대비 성능 판단이 중요함

## Ⅲ. 종류 및 비교

| 판단 기준 | 해시 테이블 | 균형 트리 | 정렬 배열 |
|:---|:---|:---|:---|
| 평균 조회 성능 | $O(1)$ | $O(\log n)$ | $O(\log n)$ |
| 최악 조회 성능 | 충돌 시 $O(n)$ | $O(\log n)$ | $O(\log n)$ |
| 순서 보존 | 없음 | 있음 | 있음 |
| 범위 검색 | 불리함 | 유리함 | 유리함 |
| 대표 용도 | 캐시, 사전, 중복 검사 | 인덱스, 정렬 데이터 | 읽기 중심 탐색 |

## Ⅳ. 구성요소 및 구조

| 구성요소 | 설명 |
|:---|:---|
| 해시 함수 | 키를 버킷 위치로 변환하고 분포가 고르게 나와야 함 |
| 버킷 배열 | 실제 저장 위치 집합이며 크기 설정이 적재율을 좌우함 |
| 충돌 처리 | 체이닝, 개방 주소법 등으로 충돌을 해결하고 방식마다 삭제와 캐시 효율이 다름 |
| 재해싱 | 적재율 증가 시 버킷 수를 확장하고 순간 비용이 커질 수 있음 |

## Ⅴ. 원리 및 절차 흐름도

```text
+----------+     +----------+     +----------+     +----------+
| 키입력 | --> | 해시계산 | --> | 버킷탐색 | --> | 저장/조회 |
+----------+     +----------+     +----------+     +----------+
```

1. **키입력**: 문자열, 정수, 객체 식별자 등 검색 키를 받음
2. **해시계산**: 키를 해시 함수에 넣어 버킷 인덱스를 계산함
3. **버킷탐색**: 해당 버킷에서 충돌 처리 규칙에 따라 원소를 찾음
4. **저장/조회**: 같은 키면 갱신하고 없으면 삽입하거나 조회 결과를 반환함

## Ⅵ. 문제점 및 해결 방안

1. 문제: 충돌이 집중되어 성능이 저하되어 나쁜 해시 함수나 높은 적재율은 버킷 편향을 일으킴
   - 해결방안: 분포가 좋은 해시 함수를 선택하고 적재율 임계치에서 재해싱하고 버킷 길이 분포로 검증함
2. 문제: 최악 성능 보장이 약해 공격적 입력이나 동일 접두 키에서 조회가 선형으로 악화될 수 있음
   - 해결방안: 보안 민감 환경은 해시 시드 랜덤화나 트리 기반 버킷 구조를 사용하고 최악 입력 응답시간로 검증함
3. 문제: 메모리 사용량이 증가해 빠른 접근을 위해 비어 있는 버킷을 많이 유지해야 함
   - 해결방안: 접근 패턴에 맞는 초기 크기와 확장 정책을 조정하고 적재율, 메모리 사용량로 검증함

## Ⅶ. 적용 사례

- 웹 세션 저장소: 세션 ID를 키로 즉시 조회함, 확인 지표는 조회 지연시간과 충돌률임
- 캐시 시스템: 요청 키로 객체를 매핑해 반복 계산을 줄임, 확인 지표는 캐시 적중률과 평균 응답시간임
- 중복 데이터 판별: 대량 입력의 중복 여부를 빠르게 검증함, 확인 지표는 처리량과 메모리 사용량임

## Ⅷ. 결론

해시 테이블은 순서보다 즉시 접근이 중요한 업무에서 가장 실용적인 선택이지만, 성능은 해시 함수와 충돌 관리 정책을 얼마나 잘 설계했는지에 달려 있음.
