## 미리 알고가기

- 해시 함수: 키를 고정 범위 인덱스로 변환하는 함수임
- 충돌: 서로 다른 키가 같은 버킷으로 매핑되는 현상임
- 적재율: 저장 원소 수를 버킷 수로 나눈 값으로 성능 저하 지표임
- 체이닝: 같은 버킷에 여러 원소를 연결 목록이나 동적 배열로 저장하는 방식임
- 개방 주소법: 충돌이 나면 다른 빈 버킷을 따라가며 저장 위치를 찾는 방식임

## Ⅰ. 개요

- **정의/개념**: 해시 테이블은 키를 해시 함수로 버킷 인덱스로 바꿔 저장 위치를 바로 찾도록 구성한 자료구조로, 조회, 삽입, 삭제를 평균 $O(1)$에 가깝게 처리함
- **배경/필요성**: 세션 조회, 캐시 접근, 중복 검사처럼 정렬 순서보다 즉시 접근이 중요한 업무에서는 키를 직접 매핑하는 방식이 비교 기반 탐색보다 더 적합함

## Ⅱ. 특징

- 키를 직접 비교해 내려가지 않고 버킷 주소를 바로 계산하므로 조회와 삽입이 빠름
- 충돌 처리 방식과 적재율이 실제 성능을 좌우하므로 평균 $O(1)$이라는 말만으로는 충분하지 않음
- 정렬 순서를 보존하지 않으므로 범위 조회나 정렬된 순차 처리에는 맞지 않음
- 버킷 확장과 재해싱 시 순간 비용이 커질 수 있어 대량 삽입 구간에서는 용량 계획이 중요함

## Ⅲ. 종류 및 비교

| 판단 기준 | 해시 테이블 | 균형 트리 | 정렬 배열 |
|:---|:---|:---|:---|
| 평균 조회 성능 | 평균적으로 $O(1)$에 가깝게 찾을 수 있어 키 일치 조회가 매우 빠름 | 평균과 최악 모두 $O(\log n)$이므로 조회 시간이 안정적임 | 정렬 상태를 이용해 $O(\log n)$에 찾을 수 있지만 삽입은 불리함 |
| 최악 상황 | 충돌이 한 버킷에 몰리면 조회와 삽입이 $O(n)$까지 악화될 수 있음 | 트리 균형이 유지되면 최악에도 $O(\log n)$을 지킴 | 조회는 $O(\log n)$이지만 삽입과 삭제는 원소 이동 때문에 부담이 큼 |
| 순서와 범위 처리 | 키의 순서를 보존하지 않아 범위 검색에 불리함 | 키 순서를 유지하므로 범위 검색과 정렬 순회에 유리함 | 배열 자체가 정렬돼 있으므로 범위 검색과 순차 접근에 유리함 |
| 적합한 업무 | 세션 저장소, 캐시, 중복 검사처럼 즉시 조회가 중요한 업무에 적합함 | 정렬 순서와 갱신을 함께 관리해야 하는 인덱스 업무에 적합함 | 읽기 비중이 높고 데이터 변경이 적은 탐색 업무에 적합함 |

> 요약: 해시 테이블은 즉시 조회에 가장 강하지만 순서와 최악 성능 보장이 약하므로 범위 검색이 필요하면 다른 구조가 더 적합함

## Ⅳ. 구성요소 및 구조

| 구성요소 | 설명 |
|:---|:---|
| 키와 값 | 해시 테이블은 키로 위치를 찾고 값은 그 위치에 저장하므로 키의 동등성 규칙과 중복 처리 방식을 먼저 정해야 함 |
| 해시 함수 | 키를 버킷 위치로 바꾸는 함수이므로 결과가 고르게 퍼져야 특정 버킷에 데이터가 몰리지 않음 |
| 버킷 배열 | 해시 결과가 가리키는 저장 공간들의 배열이며 크기가 작으면 적재율과 충돌률이 함께 올라감 |
| 충돌 처리 | 서로 다른 키가 같은 버킷을 가리킬 때 체이닝이나 개방 주소법으로 풀어야 하며 이 선택이 삭제 방식과 캐시 효율을 바꿈 |
| 재해싱 | 적재율이 높아질 때 버킷 수를 늘리고 기존 키를 다시 배치하는 작업이므로 순간 비용은 크지만 평균 성능 유지에 필요함 |

> 요약: 해시 테이블의 성능은 키 규칙, 해시 함수 분포, 버킷 크기, 충돌 처리, 재해싱 정책이 함께 결정함

```text
+-----------+     +---------------+     +--------------+     +-----------------+
| Key input | --> | Hash function | --> | Bucket array | --> | Collision handle |
+-----------+     +---------------+     +--------------+     +-----------------+
                                           |
                                           v
                                    +--------------+
                                    | Rehash check |
                                    +--------------+
```

## Ⅴ. 원리 및 절차 흐름도

```text
+----------+     +----------+     +----------+     +----------+
| 키입력 | --> | 해시계산 | --> | 버킷탐색 | --> | 저장/조회 |
+----------+     +----------+     +----------+     +----------+
```

1. **키 입력**: 문자열, 정수, 객체 식별자처럼 조회 기준이 되는 키를 받음
2. **해시 계산**: 키를 해시 함수에 넣어 버킷 인덱스를 계산함
3. **버킷 확인**: 해당 버킷에서 같은 키가 있는지 확인하고 충돌 처리 규칙에 따라 위치를 찾음
4. **저장 또는 반환**: 같은 키면 값을 갱신하고 없으면 삽입하며 적재율이 임계치를 넘으면 재해싱함

## Ⅵ. 실무 적용 및 유의점

1. 웹 세션 저장소에서는 세션 ID를 바로 찾아야 하므로 해시 테이블을 쓰되 충돌이 늘지 않게 적재율을 관리하고 조회 지연시간과 충돌률로 확인함
2. 캐시 시스템에서는 악성 키가 한 버킷에 몰리면 응답이 급격히 느려질 수 있으므로 시드 랜덤화나 트리화를 적용하고 악성 키셋 응답시간으로 확인함

## Ⅶ. 결론

해시 테이블은 순서보다 즉시 조회가 중요한 업무에 적합하지만, 실제 성능은 해시 분포와 적재율 관리가 좌우하므로 두 요소를 함께 설계해야 함.
