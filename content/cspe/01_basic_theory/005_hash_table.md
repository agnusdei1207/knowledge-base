# 해시 테이블 (Hash Table)

## 미리 알고가기

- **적재율(load factor)**: 버킷 개수 대비 담긴 원소 수의 비율. 옷걸이 100개에 옷 70벌이 걸리면 0.7이고, 이 값이 높아질수록 한 자리에 여러 개가 몰려 느려진다.
- **일관 해싱(consistent hashing)**: 서버가 늘거나 줄어도 데이터 전체를 다시 나누지 않고 경계에 걸린 일부만 옮기도록 키와 서버를 같은 원형 공간에 배치하는 방식.

## 1. 개요

- **정의/개념**: 해시 테이블은 키를 해시 함수에 넣어 나온 숫자를 저장 위치(버킷 번호)로 삼아, 그 자리에 값을 바로 넣고 바로 꺼내는 자료구조다. 찾을 때 값들을 하나씩 비교하지 않고 위치를 계산해 곧장 짚기 때문에 삽입·검색·삭제가 평균 `O(1)`이다.
- **배경/필요성**: 배열은 순서대로 훑어 찾고 균형 트리는 한 걸음마다 후보를 절반씩 줄여 찾지만, 둘 다 "이 값이 저 값보다 큰가 작은가"를 계속 비교하느라 비용이 쌓인다. 그런데 정작 실무에서 잦은 일은 "이 사용자 ID에 걸린 값이 뭐냐", "이 토큰 본 적 있냐"처럼 크기 비교가 필요 없는 동등 검색이다. 이럴 때는 키를 아예 저장 위치로 바꿔 버리면 비교 자체가 사라지는데, 옷을 맡기고 받은 번호표로 옷걸이를 곧장 찾듯 키에서 자리를 계산해 한 번에 짚는 것이 해시 테이블이다. 대신 서로 다른 키가 같은 자리를 가리키는 충돌이 생기므로 이를 어떻게 처리하느냐가 성능을 좌우한다.

## 2. 특징 및 비교

해시 테이블의 강점과 약점은 한 뿌리에서 나온다. 위치를 계산해 곧장 짚는 방식이라 하나를 콕 집는 동등 검색은 압도적으로 빠르지만, 그 계산이 키의 순서를 흩어 놓기 때문에 "작은 것부터 훑기"나 "10에서 20 사이" 같은 순서·범위 질의는 아예 못 한다.

| 판단 기준 | 배열/리스트 | 균형 트리 | 해시 테이블 |
|:---|:---|:---|:---|
| 동등 검색(키 하나 짚기) | `O(n)` 훑어야 함 | `O(log n)` | 평균 `O(1)`, 계산해 곧장 짚음 |
| 범위·정렬 질의 | 정렬해 두면 가능 | 가장 잘함 | 순서를 흩어 놓아 불가 |
| 삽입·삭제 | 원소 밀기 비용 | 균형 유지 비용 | 평균 빠름, 리사이즈 때 순간 지연 |
| 대표 용도 | 소규모 데이터 | 범위 질의, 정렬 출력 | 캐시, 세션, 중복 검사 |

> 요약: 키 하나를 짚는 일만 잦으면 해시, 순서대로 뽑거나 범위로 뽑을 일이 있으면 트리다.

그래서 어떤 자료구조를 쓸지는 동등 검색이 대부분인지, 아니면 정렬·범위 질의가 섞이는지로 먼저 갈린다. 해시로 정하면 그다음은 충돌을 얼마나 잘 억누르느냐의 문제가 되는데, 이는 해시 함수의 분포 품질, 적재율 관리, 충돌 처리 방식, 리사이즈 정책으로 결판난다. 평균 `O(1)`은 공짜가 아니라 이 네 가지가 관리될 때만 성립하는 약속이다.

## 3. 구성요소/구조

```text
   키 "kim"                                  버킷 배열
      |                                    +----+-----------------+
      v          해시 함수                  | 0  |                 |
  hash("kim") --------> 3 (버킷 번호) ----> | 1  |                 |
                                            | 2  |                 |
                                            | 3  | ("kim", 값) --> ("lee", 값)
                                            | 4  |                 |   ^
                                            +----+-----------------+   |
                                                        같은 3번에 몰린 두 키를 사슬로 이음(체이닝)
```

키를 해시 함수에 넣으면 버킷 번호가 나오고, 그 자리에 값을 둔다. 서로 다른 키가 같은 번호를 받으면(충돌) 한 자리에 여러 개를 사슬처럼 이어 두거나, 옆의 빈자리로 밀어 넣어 해결한다.

| 구성요소 | 하는 일 | 왜 중요한가 |
|:---|:---|:---|
| 키(Key) | 값을 찾는 식별자 | 동등성 비교의 기준 |
| 해시 함수 | 키를 버킷 번호로 변환 | 고르게 흩뿌려야 충돌이 준다 |
| 버킷 배열 | 값이 실제로 놓이는 자리 | 개수가 적재율을 결정 |
| 충돌 처리 | 같은 자리에 몰린 키를 정리 | 최악 `O(n)`을 막는 장치 |
| 리사이즈 | 꽉 차면 버킷을 늘려 재배치 | 적재율을 낮춰 속도 회복 |

> 요약: 해시 함수가 자리를 정하고, 충돌 처리와 리사이즈가 그 자리를 붐비지 않게 지킨다.

충돌을 푸는 방식은 크게 둘이다. **체이닝**은 같은 버킷에 몰린 원소들을 연결 리스트로 잇는 방식으로, 삭제가 단순한 대신 포인터를 따라가는 오버헤드가 있다. **개방 주소법**은 자리가 찼으면 정해진 규칙으로 다음 빈 슬롯을 찾아 넣는 방식으로, 원소가 배열 안에 촘촘히 붙어 있어 캐시에 유리하지만 붐비면 빈자리를 찾아 헤매는 탐사 거리가 길어진다. 어느 쪽이든 적재율이 높아지면 성능이 무너지므로, 일정 수준을 넘으면 버킷 수를 늘리고 전체를 다시 흩뿌리는 **리사이즈(재해싱)**로 분포를 회복한다.

## 4. 문제점 및 개선방안

1. **한 버킷에 쏠리는 충돌**: 해시 함수가 키를 고르게 흩뿌리지 못하면 특정 버킷에 원소가 몰려, 그 자리를 뒤지는 비용이 최악 `O(n)`까지 치솟는다.
   - **개선방안**: 분포가 균등한 해시 함수를 쓰고, 시드를 랜덤화해 악의적 키 집중(해시 DoS)을 막으며, 최대 체인 길이를 모니터링한다. (확인: 버킷별 원소 수 분포, 최대 체인 길이)

2. **리사이즈 순간의 지연 스파이크**: 적재율이 기준을 넘으면 모든 원소를 새 버킷으로 다시 옮기는데, 이 재배치가 한 번에 몰리면 해당 요청만 갑자기 느려진다.
   - **개선방안**: 예상 크기에 맞춰 초기 용량을 잡아 재배치 빈도를 줄이고, 옮기는 일을 여러 연산에 나눠 조금씩 처리하는 점진 리사이즈를 쓴다. (확인: p99 지연, 리사이즈 발생 빈도)

3. **순서·범위 질의 불가**: 해시는 키의 순서를 흩어 놓으므로 정렬 출력이나 범위 검색을 근본적으로 지원하지 못한다.
   - **개선방안**: 범위·정렬이 핵심이면 균형 트리나 B-Tree, 정렬 인덱스로 바꾸거나, 해시와 정렬 구조를 함께 두어 용도를 나눈다. (확인: 질의 유형별 응답 정확도)

## 5. 실무 적용 사례

| 적용 영역 | 어떻게 쓰나 | 무엇으로 효과를 확인하나 |
|:---|:---|:---|
| 캐시·세션 저장소 | 사용자 ID나 토큰을 키로 값을 평균 `O(1)`에 조회 | 캐시 적중률, p99 조회 지연 |
| 중복 제거 | 이벤트 키를 해시로 저장해 이미 본 것인지 즉시 판단 | 충돌률, 초당 처리량 |
| 분산 캐시·샤딩 | 일관 해싱으로 노드를 늘리거나 뺄 때 옮기는 데이터를 최소화 | 재배치 비율, 노드별 부하 편차 |

> 요약: 키로 곧장 짚어야 하는 조회·중복 검사에 쓰고, 분산 환경에서는 일관 해싱으로 재배치 비용을 억누른다.

## 6. 결론

해시 테이블은 크기 비교 없이 키를 위치로 바꿔 곧장 짚는 구조라, 동등 검색이 잦은 캐시·세션·중복 검사에서 평균 `O(1)`으로 가장 강하다. 다만 이 평균은 해시 함수의 분포, 적재율, 충돌 처리, 리사이즈 정책이 관리될 때만 지켜지는 조건부 성능이고, 그 대가로 순서·범위 질의는 포기한다. 따라서 선택은 "빠르니까 무조건 해시"가 아니라, 질의가 키 하나 짚기 위주면 해시를 쓰되 충돌과 적재율을 감시하고, 정렬·범위가 필요하면 트리 계열로 넘기는 판단으로 좁혀진다.
