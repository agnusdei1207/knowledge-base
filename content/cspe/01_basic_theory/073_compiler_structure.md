# 📖 【암기용】 개념 완전 이해

> 목적: 컴파일러 구조를 처음 보는 사람도 완벽히 이해하게 만든다.

## 한눈에
- **개요**: 고급 언어로 작성된 원시 코드를 기계가 이해할 수 있는 목적 코드로 변환하는 프로그램의 단계적 처리 구조다.
- **왜 필요한가**: 기계어에 종속되지 않고 인간 친화적인 언어로 프로그래밍하며, 이를 하드웨어에 맞게 최적화하여 실행하기 위해 필요하다.
- **핵심 직관**: 통번역가가 외국어 소설을 번역할 때 단어 뜻 찾기(어휘) → 문법 맞는지 확인(구문) → 말이 되는지(의미) → 초벌 번역(중간코드) → 다듬기(최적화) → 최종 출판(목적코드) 과정을 거치는 것과 똑같다.

## 핵심 용어 정리

| 용어/표기 | 의미 | 비유·예 |
|:---|:---|:---|
| 프론트엔드 (전반부) | 소스 언어 종속적. 코드를 분석해 중간 코드로 변환 | "원문을 읽고 요지를 파악하는 과정" |
| 백엔드 (후반부) | 타겟 기계 종속적. 중간 코드를 기계어로 변환 | "요지를 타겟 언어로 깔끔하게 번역" |
| 어휘 분석 (Lexical) | 코드를 쪼개 의미 있는 최소 단위(Token)로 변환 | "알파벳을 모아 '단어'로 인식" |
| 구문 분석 (Syntax) | 토큰 나열이 문법 규칙에 맞는지 AST(추상구문트리) 생성 | "'주어+동사+목적어' 순서가 맞는지 확인" |
| 의미 분석 (Semantic) | 문법은 맞으나 논리적 모순이 없는지 (타입 체크 등) 검사 | "문법은 맞는데 '물이 불을 마신다'처럼 뜻이 이상한지 확인" |

## 깊이 이해
- **배경·문제의식**: 컴파일을 단번에 기계어로 바꾸려 하면, M개의 언어와 N개의 CPU가 있을 때 M×N개의 컴파일러가 필요하다. 이를 해결하기 위해 앞/뒤(전/후반부)로 나누고 공통의 '중간 코드'를 쓰게 되었다 (M+N 개로 단축).
- **작동 원리**: 
  1. 원시 코드 $\rightarrow$ 어휘 분석기(Token) $\rightarrow$ 구문 분석기(AST) $\rightarrow$ 의미 분석기(검증된 AST)
  2. $\rightarrow$ 중간 코드 생성기(IR) $\rightarrow$ 기계 독립적 최적화
  3. $\rightarrow$ 목적 코드 생성기(기계어/어셈블리) $\rightarrow$ 기계 종속적 최적화
  (전 과정에 심볼 테이블과 에러 핸들러가 관여)
- **구체 예시**: `int a = b + c;` 라는 코드. 
  - 어휘 분석: `[int] [id:a] [=] [id:b] [+] [id:c] [;]` 
  - 구문 분석: 대입 연산자 `=`를 루트로 하는 트리 구조 생성
  - 의미 분석: `a, b, c`가 모두 int 타입인지 심볼 테이블로 확인.
- **흔한 오해·주의점**: "인터프리터는 한 줄씩 실행하고 컴파일러는 한 번에 한다"는 겉보기 차이다. 구조적으로 컴파일러는 전체 코드를 분석해 최적화된 바이너리를 '산출'하지만, 인터프리터는 중간 코드나 AST를 직접 메모리에서 '실행'한다는 점이 핵심이다.

## 연결 개념
- (072) 형식 언어 이론 — 어휘 분석(정규), 구문 분석(문맥 자유)의 이론적 토대
- (074) 파서 LL·LR — 구문 분석을 수행하는 알고리즘
- LLVM — 프론트/백엔드 분리 구조를 극대화한 현대적 컴파일러 인프라

# 📝 【답안용】 시험 답안 템플릿

## 핵심 인사이트 (3줄 요약)

> 1. **본질**: 컴파일러 구조는 소스 언어를 분석하는 전반부(Front-end)와 기계어를 생성하는 후반부(Back-end)로 나뉘는 파이프라인 변환 시스템이다.
> 2. **가치**: 중간 코드(IR)를 매개로 전/후반부를 분리하여 플랫폼 이식성을 높이고(M×N → M+N), 공통 최적화를 가능하게 한다.
> 3. **판단 포인트**: 언어 종류, 타겟 플랫폼, 컴파일 속도와 실행 속도의 트레이드오프에 맞춰 AOT, JIT, LLVM 등 적절한 컴파일 방식을 선택해야 한다.

## 출제 의도 및 답안 포인트

| 출제 의도 | 반드시 짚을 핵심 | 감점 회피 포인트 |
|:---|:---|:---|
| 컴파일의 단계별 논리적 흐름 이해 | 어휘(Token)-구문(AST)-의미(Type)-IR-최적화-목적코드 | 단계 누락, 프론트/백엔드 분리 기준 모호 |
| 전·후반부 분리 아키텍처의 목적 확인 | 중간 코드(IR)를 통한 M×N 문제 해결, 이식성 | 단순 번역기로만 묘사, 최적화 관점 누락 |

> 요약: 각 단계를 단순히 나열하지 말고, 각 단계의 입력-산출물이 무엇이며 심볼 테이블과 어떻게 상호작용하는지 구조적으로 묘사해야 한다.

## Ⅰ. 개요 및 필요성

- 개요: 고수준 원시 프로그램을 기계가 실행 가능한 목적 코드(기계어)로 변환하는 여러 단계의 논리적 파이프라인 구조
- 배경: 다양한 프로그래밍 언어와 다양한 타겟 아키텍처 환경에서 이식성 있고 최적화된 바이너리 생성이 요구됨
- 필요성: 구문/의미 검증 오류를 사전에 차단하고, 컴파일 타임 최적화를 통해 런타임 실행 성능을 극대화하기 위해 필요

---

## Ⅱ. 구조 및 구성요소

```text
Source Code -> [Front-End (언어 종속)] -> 중간 코드(IR) -> [Back-End (기계 종속)] -> Machine Code
                  |                                         |
                  +-> 어휘/구문/의미 분석, IR 생성            +-> 최적화, 목적 코드 생성
                          (Symbol Table / Error Handler 전 구간 참조)
```

| 구성요소 | 역할 | 산출물 |
|:---|:---|:---|
| 어휘 분석기 (Lexer) | 소스를 읽어 의미 있는 최소 단위 분리 | 토큰 열 (Token Stream) |
| 구문 분석기 (Parser) | 토큰의 문법적 구조 검사 (문맥 자유 문법) | 구문 트리 (AST) |
| 의미 분석기 (Semantic) | 타입 검사, 변수 선언 확인, 논리적 모순 검증 | 검증된 AST |
| 중간 코드 생성·최적화 | 이식성 확보용 3-주소 코드 변환 및 불필요 코드 제거 | 중간 코드 (IR) |
| 목적 코드 생성·최적화 | 타겟 CPU 레지스터 할당 및 파이프라인 최적화 | 기계어 / 어셈블리 |

> 요약: 컴파일러는 심볼 테이블과 에러 핸들러를 공유하며, 언어 종속적인 전반부와 하드웨어 종속적인 후반부로 나뉜다.

---

## Ⅲ. 동작원리 및 흐름도

```text
소스 입력 -> 정규표현식 매칭(토큰화) -> 문법 규칙 트래버스(트리 구성)
-> 타입 매칭(의미 검증) -> 3주소 코드 변환 -> 레지스터 할당 -> 목적코드 산출
```

- 1단계 [토큰화]: 식별자, 예약어 등을 유한 오토마타(FSM)로 매칭해 토큰 스트림 생성
- 2단계 [AST 구성]: 푸시다운 오토마타(PDA)로 괄호 매칭 등 중첩 구조 파악 및 트리 구조화
- 3단계 [의미 검증]: 심볼 테이블 참조를 통해 선언/타입 매칭을 수행 (Type Casting 등 암묵적 변환 포함)
- 4단계 [최적화/생성]: 상수 폴딩, 루프 전개(Loop Unrolling) 후 타겟 CPU 아키텍처에 맞게 레지스터 매핑

> 요약: 원시 코드는 문자열에서 토큰, 구문 트리, 중간 코드를 거쳐 점진적으로 기계 친화적 형태로 변환된다.

---

## Ⅳ. 특징
- [이식성 및 재사용성]: 중간 코드(IR)를 중심으로 전·후반부가 분리되어 LLVM처럼 하나의 백엔드에 여러 프론트엔드를 붙일 수 있음
- [최적화 다원화]: 기계 독립적 최적화(루프 불변 코드 이동 등)와 기계 종속적 최적화(파이프라인 해저드 방지)가 분리되어 수행
- [컴파일 지연]: 복잡한 구문 분석과 최적화 알고리즘(O(N^2) 이상)으로 인해 빌드 타임이 길어짐

> 요약: 현대 컴파일러 구조는 단순한 번역을 넘어, 런타임 지연을 줄이기 위해 컴파일 타임에 최대한의 최적화 연산을 수행하는 구조다.

---

## Ⅴ. 심화 비교 및 적용 판단

| 비교 축 | 컴파일러 (AOT) | 인터프리터 | JIT (Just-In-Time) 컴파일러 | 선택 기준 |
|:---|:---|:---|:---|:---|
| 변환 단위 | 전체 파일 일괄 변환 | 한 줄씩 즉시 해석 실행 | 실행 중 런타임에 동적 컴파일 | 실행 환경 / 성능 |
| 장점(성능) | 높은 런타임 실행 속도, 최적화 극대화 | 빠른 시작, 플랫폼 독립적 | 인터프리터와 컴파일러의 장점 결합 | 최적화 vs 이식성 |
| 단점(오버헤드) | 긴 빌드 타임, 타겟 OS 종속 | 느린 실행 속도, 반복 구문 재해석 | 런타임 메모리 소모, JIT 컴파일 지연 | 메모리 가용성 |

> 요약: C/C++은 AOT, Python은 인터프리터, Java/C#은 JIT 방식을 취하여 각 언어의 목적에 맞는 런타임 특성을 확보한다.

**리스크·대응:**
- [긴 빌드 타임]: 거대 코드베이스 컴파일 지연 → 분산 빌드(Distcc), 캐시(CCache), 점진적 컴파일 도입 (지표: 빌드 시간 단축률)
- [메모리 누수 및 의존성 오류]: 의미 분석에서 포인터/타입 오류 검출 한계 → 정적 분석 도구(SonarQube, Lint) 파이프라인 통합 (지표: 결함 밀도 감소)

**도입 후 점검 지표:**
- 성능/효율: 최적화 단계 전후 목적 코드 크기 및 FLOPs 감소 비율 모니터링
- 품질/운영: CI/CD 파이프라인 내 컴파일 성공률 99% 이상 및 빌드 소요 시간 (목표: 10분 이내)

## Ⅵ. 실무 적용 및 결론

**적용 방안 3개:**
1. [플랫폼 다변화 대응]: LLVM 프레임워크를 도입하여, 프론트엔드(Clang)는 하나로 유지하고 백엔드만 ARM/x86/WASM용 단일 파이프라인 구축
2. [런타임 성능 극대화]: 프로파일 기반 최적화(PGO)를 적용하여 컴파일러가 실제 런타임 분기 빈도 데이터를 피드백 받아 재컴파일 최적화 수행
3. [빌드 파이프라인 최적화]: Incremental Build 체계와 의존성 그래프 최소화를 통해 개발자 로컬 빌드 생산성 50% 이상 향상

**결론:**
- 기술사 판단: 컴파일러 구조의 이해는 단순 툴 사용을 넘어, 성능 병목 시 루프 전개, 인라인화 등 컴파일 타임 최적화를 유도하는 코드를 작성할 수 있는 핵심 역량이다.
- 향후 방향: 머신러닝을 활용한 휴리스틱 최적화(ML-guided Optimization)가 백엔드 최적화 단계에 도입되어 컴파일러 스스로 진화하는 형태로 발전 중이다.
