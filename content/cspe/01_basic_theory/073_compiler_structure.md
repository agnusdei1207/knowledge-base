# 📖 【암기용】 개념 완전 이해

> 목적: 컴파일러 구조를 처음 봐도 완벽히 이해하게 만든다. 시험 답안 양식이 아니라, 이해를 위한 친절한 설명이다.

## 한눈에
- **개요**: 고급 언어 소스코드를 목적 기계가 실행 가능한 코드로 변환하는 단계적 번역 구조
- **왜 필요한가**: 개발자는 C, Java, Rust 같은 추상 언어로 로직을 작성하고, CPU는 기계어만 실행한다. 컴파일러는 문법 검증, 의미 검사, 최적화, 코드 생성을 맡는다.
- **핵심 직관**: 사람의 문장을 먼저 단어로 나누고 문장 구조를 확인한 뒤 의미를 점검하고 실행 계획으로 바꾸는 절차와 같다.

## 깊이 이해
- **배경·문제의식**: 소스코드를 바로 기계어로 바꾸면 오류 위치, 타입 규칙, 최적화 기회를 찾기 어렵다. 그래서 프론트엔드, 중간 표현, 백엔드로 나누어 각 단계가 검증 가능한 산출물을 만든다.
- **작동 원리**: 어휘 분석은 토큰을 만들고, 구문 분석은 parse tree/AST를 만든다. 의미 분석은 타입, 스코프, 심볼을 검사하고, 중간코드 최적화는 dead code 제거, constant folding, loop optimization을 수행한다. 백엔드는 레지스터 할당과 명령어 선택으로 목적 코드를 생성한다.
- **비유**: 번역가가 원문을 단어, 문법, 의미, 문체 순서로 다듬은 뒤 대상 언어에 맞는 표현으로 바꾸는 과정과 같다.
- **구체 예시**: `int x = a + 3;`은 토큰 7개 내외로 분해되고, AST의 assignment 노드, symbol table의 x:int 항목, IR의 add 명령, 최종 ISA의 load/add/store 명령으로 변환된다.
- **흔한 오해·주의점**: 컴파일러는 단순 번역기가 아니다. 타입 안전성, 최적화, ABI 준수, 보안 옵션(stack canary, ASLR 연계)을 코드 생성 단계에서 함께 다룬다.

## 연결 개념
- 형식 언어 이론 — 어휘·구문 분석의 수학적 기반
- 파서 LL/LR — 구문 분석 알고리즘
- 최적화 컴파일러 — IR과 제어 흐름 그래프 기반 변환

# 📝 【답안용】 시험 답안 템플릿

> 목적: 시험장에서 25분에 그대로 쓰는 답안 양식. 작성방식(추상표현 금지·수치·도식·문제유형 전환)을 엄격히 지킨다.

## 핵심 인사이트 (3줄 요약)

> 1. **본질**: 컴파일러는 소스코드를 어휘·구문·의미 분석, 최적화, 코드 생성 단계로 변환하는 번역 시스템임.
> 2. **가치**: 오류 검출, 이식성, 실행 지연시간 감소, ISA별 코드 생성을 분리해 소프트웨어 생산성과 실행 품질을 확보함.
> 3. **판단 포인트**: 프론트엔드는 언어 규칙, IR은 최적화, 백엔드는 ISA·ABI·레지스터 제약을 기준으로 설계함.

---

## Ⅰ. 개요 및 필요성

- 개요: 소스코드를 어휘·구문·의미 분석과 최적화를 거쳐 목적 코드로 변환하는 번역 시스템
- 배경: 고급 언어의 추상 구문과 CPU 명령어 사이에는 타입, 스코프, 메모리 배치, 호출 규약 차이가 존재함
- 필요성: 단계 분리형 컴파일 구조로 오류 위치 추적, 중간 최적화, 타깃 ISA 대응을 가능하게 해야 함

---

## Ⅱ. 구조 및 구성요소

```text
Source Code -> Lexer -> Parser -> Semantic Analyzer -> IR Optimizer -> Code Generator -> Object Code
               +-> Symbol Table
               +-> Error Handler
```

| 구성요소 | 역할 | 특이사항 |
|:---|:---|:---|
| 어휘 분석기 | 문자 스트림을 token으로 변환 | 정규식, DFA 사용 |
| 구문 분석기 | token을 parse tree/AST로 구성 | LL, LR, precedence 처리 |
| 의미 분석기 | 타입, 스코프, 선언 여부 검사 | symbol table, type checker |
| 백엔드 | IR 최적화와 목적 코드 생성 | register allocation, instruction selection |

> 요약: 컴파일러는 프론트엔드에서 언어 규칙을 검증하고 백엔드에서 타깃 기계 코드로 변환함.

---

## Ⅲ. 동작원리 및 흐름도

```text
문자 입력 -> 토큰화 -> AST 구성 -> 타입/스코프 검사 -> IR 생성 -> 최적화 -> 기계어 생성
            +-> 오류 발견 시 위치/원인 보고
            +-> 타깃 ISA별 백엔드 선택
```

| 단계 | 처리 내용 | 검증 기준 |
|:---:|:---|:---|
| 1 | Lexical analysis 수행 | invalid token 0건 |
| 2 | Syntax analysis 수행 | parser conflict 0건, AST 생성 |
| 3 | Semantic analysis 수행 | type error, undeclared symbol 탐지 |
| 4 | Optimization/code generation | SSA, CFG, ABI 준수, test suite 통과 |

> 요약: 컴파일은 token, AST, symbol table, IR, object code 산출물을 단계적으로 생성하며 오류를 앞 단계에서 차단함.

---

## Ⅳ. 특징

| 구분 | 내용 | 판단 포인트 |
|:---|:---|:---|
| 프론트엔드 | 언어 문법과 의미 규칙 처리 | lexer/parser/type checker |
| 중간 표현 | 언어와 기계 사이 공통 표현 | LLVM IR, SSA, CFG |
| 백엔드 | 타깃 ISA 코드 생성 | x86-64, ARM64, RISC-V |
| 한계 | 최적화 시간과 디버깅 가독성 충돌 | -O0, -O2, -O3 선택 |

> 요약: 컴파일러 구조는 언어 독립 최적화와 타깃별 코드 생성을 분리하는 것이 설계 핵심임.

## Ⅴ. 심화 비교 및 적용 판단

| 비교 축 | 기존/대안 | 본 키워드 | 선택 기준 |
|:---|:---|:---|:---|
| 실행 방식 | 인터프리터 | 컴파일러 | 반복 실행, 지연시간 요구가 크면 컴파일 |
| 구조 | 단일 패스 | 다중 패스 | 최적화와 오류 진단 요구 시 다중 패스 |
| IR 활용 | 직접 코드 생성 | LLVM IR/SSA | 다중 ISA 지원 시 IR 기반 선택 |

> 요약: 반복 실행과 다중 타깃 요구가 있으면 IR 기반 다중 패스 컴파일러가 적합함.

| 리스크 | 원인 | 대응 방안 | 확인 지표 |
|:---|:---|:---|:---|

| 진단 품질 저하 | AST 위치 정보 누락 | source span 저장, error recovery | 오류 위치 정확도 95% |
| 타깃 종속 오류 | ABI, calling convention 불일치 | backend test, conformance suite | ABI test 100% 통과 |

> 요약: 오컴파일과 타깃 오류는 IR 검증, 퍼징, ABI 테스트로 통제함.

| 점검 항목 | 목표 기준 | 측정 방법 |
|:---|:---|:---|
| 정확성 | 언어 표준 테스트 100% 통과 | conformance test |
| 컴파일 비용 | 대형 모듈 빌드 시간 10분 이하 | CI build metric |
| 코드 품질 | 기준 대비 실행시간 10% 이내 | benchmark, profiler |

> 요약: 컴파일러 품질은 정확성, 빌드 시간, 생성 코드 실행시간으로 판단함.

## Ⅵ. 실무 적용 및 결론

**적용 방안 3개 (필수 — 단계별 또는 항목별):**
1. 프론트엔드: ANTLR/Bison 또는 hand-written parser로 AST 생성, 오류 위치 line/column 저장
2. 중간단계: SSA 기반 IR, CFG, data-flow analysis로 constant folding과 dead code elimination 적용
3. 백엔드: LLVM backend 활용, x86-64/ARM64 ABI 테스트와 fuzzing 10,000건 CI 수행

**결론 (2줄):**
- 기술사 판단: 언어 구현 초기에는 인터프리터, 성숙 단계와 반복 실행 환경에서는 IR 기반 컴파일러 선택
- 향후 방향: JIT, AOT, WASM, LLVM 기반 다중 타깃 구조가 컴파일러 설계의 실무 표준임
