## Ⅰ. 개요
| 항목 | 내용 |
|---|---|
| **정의** | 하나의 노드에 여러 키와 자식을 가질 수 있게 하여 디스크 접근 횟수를 최소화한 다원 탐색 균형 트리임 |
| **배경/필요성** | 디스크 I/O는 메모리 접근보다 수십만 배 느리므로, 트리의 높이를 획기적으로 낮출 자료구조가 필수적임 |
| **출제 의도** | 노드의 분할 및 병합 원리를 이해하고, RDBMS 인덱스 구조에서 B-Tree와 B+Tree의 차이를 평가함 |

| 구성요소 | 설명 | 비유 |
|---|---|---|
| 다중 키/포인터 | 한 노드에 여러 데이터를 정렬된 상태로 담고 다수의 자식을 가짐 | 여러 권이 묶인 백과사전 한 질 |
| 분할/병합(Split/Merge) | 용량 초과 시 반으로 나누고, 부족 시 이웃 노드와 합치는 매커니즘 | 서랍장 가득 차면 새 서랍장 구매 |
| 리프 링크(B+Tree) | B+Tree에서 단말 노드들끼리 연결 리스트 형태로 묶여 순차 접근 지원 | 목차 없이 페이지 술술 넘기기 |

> 요약: B-트리 계열은 다중 키 노드를 분할/병합으로 균형을 맞추며, B+트리는 리프 링크로 순차 검색을 강화함.

1. 위치 탐색: 루트부터 대소 비교를 통해 삽입/삭제 리프 노드를 찾음
2. 키 삽입/삭제: 리프 노드에 데이터를 넣거나 빼고 내부 정렬함
3. 오버/언더플로우 검사: 노드 내 키 개수가 M 범위를 벗어나는지 확인
4. 구조 재조정: 조건 위배 시 부모로 키를 올리며 분할하거나 병합/재분배함

## Ⅳ. 문제점
- B-Tree 순차 탐색 부하: 범위 검색 시 부모와 리프 노드를 오르내려야 하므로 디스크 읽기 폭증
- 삽입/삭제 오버헤드: 데이터 구조가 복잡하여 연쇄적인 노드 분할(Root까지) 발생 시 순간적 락(Lock) 지연
- 공간 파편화: 삭제가 빈번하면 노드 내 빈 공간이 많아져 디스크 공간 효율 저하(Fill Factor 감소)

## Ⅴ. 개선방안
- (단기) B+Tree 표준 채택: RDBMS 환경에서 순차 및 범위 검색 부하 제거를 위해 리프에만 데이터를 둔 B+Tree 사용
- (중기) 지연 갱신 적용: 삽입/삭제 요청을 메모리 버퍼에 모아두고 일괄 처리(Batch)하여 분할 부하 완화
- (장기) LSM 트리 혼용: 쓰기 빈도가 높은 NoSQL 환경에서는 B-트리 대신 로그 구조 병합(LSM) 트리를 적용함

## Ⅵ. 전망
- SSD 등 플래시 스토리지가 보편화됨에 따라 블록 지우기 횟수를 줄이는 변형 B-트리 연구가 지속됨
