# 트리 구조 - B-Tree·AVL·Red-Black (Tree Data Structures)

## 미리 알고가기

- **회전(rotation)**: 부모와 자식의 위치를 서로 바꿔, 한쪽으로 기운 가지를 반대쪽으로 넘겨 높이를 맞추는 연산. 시소에서 무거운 쪽을 눌러 수평을 맞추는 것과 같다.
- **B+Tree**: B-Tree의 변형으로, 실제 값은 맨 아래 리프에만 두고 리프끼리 옆으로 사슬처럼 이어 범위 검색을 빠르게 한 구조.

## 1. 개요

- **정의/개념**: 트리는 하나의 부모 아래로 여러 자식이 갈라져 나오는 계층 구조로 데이터를 잇는 자료구조이고, 그중 검색 트리는 "왼쪽 자식은 나보다 작고 오른쪽 자식은 나보다 크다"는 크기 규칙을 지켜, 찾는 값을 뿌리에서 시작해 한 걸음마다 한쪽 가지를 통째로 버리며 좁혀 나가는 트리다.
- **배경/필요성**: 배열은 정렬해 두면 빨리 찾지만 중간에 값을 넣거나 빼려면 뒤 원소를 전부 밀어야 하고, 해시는 값 하나를 콕 집어 찾는 건 빠르지만 "작은 순서대로 훑기"나 "10에서 20 사이 뽑기" 같은 정렬·범위 검색은 아예 못 한다. 트리는 값을 넣는 순간부터 크기 순서로 가지에 걸어 두므로 삽입·삭제는 관련된 가지만 손대고 정렬·범위 검색도 그대로 되지만, 넣는 순서가 나쁘면 한쪽으로만 길게 늘어져 도로 느려지기 때문에 스스로 균형을 잡아 주는 트리가 필요해진다.

## 2. 특징 및 비교

세 트리는 모두 최악의 경우에도 높이를 `O(log n)`으로 눌러 탐색 속도를 지키지만, "균형을 얼마나 빡빡하게 잡느냐"와 "어디에 저장하느냐"에서 갈린다.

| 구분 | AVL Tree | Red-Black Tree | B-Tree |
|:---|:---|:---|:---|
| 균형 잡는 방식 | 좌우 높이차를 1 이하로 엄격히 맞춤 | 색칠 규칙으로 느슨하게 맞춤 | 한 노드에 키를 여러 개 담아 납작하게 유지 |
| 균형 유지 비용 | 회전이 잦아 갱신이 무거움 | 회전이 적어 갱신이 가벼움 | 노드 분할·병합으로 조정 |
| 가장 잘하는 것 | 조회가 대부분일 때 제일 빠름 | 조회·갱신이 섞여도 두루 무난 | 디스크를 한 번 읽어 여러 키 확보 |
| 대표 적용 | 조회 위주 인메모리 구조 | 범용 map/set (C++ STL, 리눅스 커널) | DB 인덱스, 파일시스템 |

> 요약: 조회만 많으면 AVL, 넣고 빼기가 섞이면 Red-Black, 데이터가 디스크에 있으면 B-Tree.

AVL은 좌우 높이차를 1층까지 따지는 완벽주의자라 조회는 가장 빠르지만, 삽입·삭제마다 회전으로 트리를 자주 손봐야 한다. Red-Black은 노드에 빨강·검정을 칠하고 "빨강이 연달아 오면 안 된다" 정도의 느슨한 규칙만 지켜 회전을 줄인 실용주의자여서, 넣고 빼기가 잦은 범용 컨테이너의 기본이 된다. B-Tree는 이진 트리가 아니라 한 노드에 키를 수십~수백 개씩 담아 트리를 납작하게 만든 구조인데, 디스크는 한 번 접근할 때 블록 단위로 뭉텅이째 읽어 오므로 이 납작함이 곧 디스크 접근 횟수를 줄이는 열쇠가 된다.

## 3. 구성요소/구조

```text
          [ 50 ]           <- 루트: 탐색은 언제나 여기서 시작
         /      \
     [ 30 ]     [ 70 ]     <- 왼쪽은 50보다 작고, 오른쪽은 크다
     /    \     /    \
  [20]  [40] [60]  [80]    <- 리프: 값의 끝이자 범위 검색 때 옆으로 훑는 지점
```

찾는 값이 50보다 작으면 왼쪽, 크면 오른쪽으로만 내려가므로 한 걸음마다 후보의 절반이 사라진다.

| 구성요소 | 하는 일 | 왜 중요한가 |
|:---|:---|:---|
| 루트(Root) | 모든 탐색이 시작되는 꼭대기 노드 | 여기서부터 경로가 갈라짐 |
| 키(Key) | 노드마다 담긴 비교 기준 값 | "왼쪽 < 나 < 오른쪽" 정렬 규칙의 기준 |
| 자식 포인터 | 아래 노드로 내려가는 연결선 | 한 번에 한쪽 가지로만 분기 |
| 균형 정보 | 높이차·색상·키 개수 | 트리가 한쪽으로 쏠리지 않게 감시 |
| 리프(Leaf) | 가지 끝의 노드 | 범위 검색 시 이웃 리프로 이동 |

> 요약: 정렬 규칙(키)이 내려갈 길을 절반씩 좁히고, 균형 정보가 그 길이 짧게 유지되도록 지킨다.

트리에서 값을 찾는 비용은 결국 뿌리에서 리프까지 내려가는 거리, 즉 높이에 달려 있다. 그래서 AVL·Red-Black·B-Tree가 저마다 다른 방법으로 지키려는 것은 사실 하나, "높이가 `log n`을 넘지 않게 하는 것"으로 모인다.

## 4. 문제점 및 개선방안

1. **한쪽으로 쏠린 트리(편향)**: 균형 규칙이 없는 일반 이진 탐색 트리에 이미 정렬된 키를 순서대로 넣으면, 가지가 갈라지지 못하고 한 줄로 늘어서 사실상 연결 리스트가 되어 탐색이 `O(n)`으로 떨어진다.
   - **개선방안**: 삽입·삭제 때마다 균형을 다시 잡는 AVL·Red-Black·B-Tree를 쓴다. (확인: 최악에도 높이 `O(log n)` 유지)

2. **균형 유지 자체가 비용**: 균형을 잡으려면 회전이나 노드 분할·병합이 뒤따르므로, 삽입·삭제가 잦을수록 이 조정 비용이 쌓인다.
   - **개선방안**: 조회가 압도적이면 조회에 유리한 AVL을, 갱신이 섞이면 회전이 적은 Red-Black을 골라 워크로드에 맞춘다. (확인: 조회/갱신 비율 대비 지연)

3. **저장 매체와 구조의 불일치**: 디스크 인덱스에 이진 트리를 쓰면 노드를 하나 볼 때마다 느린 디스크를 한 번씩 읽어야 해, 그 접근이 트리 높이만큼 반복된다.
   - **개선방안**: 디스크·DB 인덱스는 한 노드에 키를 몰아 담아 높이를 낮춘 B-Tree/B+Tree를 쓴다. (확인: 질의당 디스크 읽기 횟수)

## 5. 실무 적용 사례

| 적용 영역 | 어떻게 쓰나 | 무엇으로 효과를 확인하나 |
|:---|:---|:---|
| DB 인덱스 | B+Tree로 정렬 출력과 `BETWEEN` 범위 질의를 지원 | 트리 높이, 질의당 페이지 읽기 수 |
| 언어·커널의 map/set | Red-Black Tree로 정렬 순회와 로그 시간 삽입·삭제 제공 | 조회·삽입 지연 |
| 파일시스템 메타데이터 | B-Tree 계열로 디렉터리·블록 위치를 관리 | 디스크 I/O 횟수 |

> 요약: 정렬·범위가 필요하면 트리, 디스크에 얹으면 B계열, 메모리 범용 컨테이너는 Red-Black.

## 6. 결론

트리는 배열의 느린 삽입·삭제와 해시의 "순서·범위 검색 불가"를 한꺼번에 메우는 자료구조이지만, 균형이 무너지는 순간 이 장점이 통째로 사라진다. 그래서 실무의 선택은 "트리냐 아니냐"가 아니라, 조회가 많으면 AVL, 넣고 빼기가 섞이면 Red-Black, 데이터가 디스크에 있으면 B-Tree처럼 워크로드와 저장 매체에 맞춰 어떤 균형 트리를 쓸지로 좁혀진다.
