# 📖 【암기용】 개념 완전 이해

> 목적: 이 개념을 처음 보는 사람도 완벽히 이해하게 만든다. 시험 답안 양식이 아니라, 이해를 위한 친절한 설명이다.

## 한눈에
- **개요**: 트리는 노드들이 부모-자식 관계로 연결되어 계층(Hierarchy)을 이루는 **비선형 자료구조**로, 그중 각 노드가 자식을 최대 2개까지만 갖는 것을 이진 탐색 트리(BST), 자식 개수 편차를 스스로 교정하는 것을 균형 이진 탐색 트리(AVL·Red-Black), 자식을 여러 개 가질 수 있는 것을 B-Tree라 부른다.
- **왜 필요한가**: 배열은 조회는 O(1)이지만 삽입·삭제가 O(N)이고, 연결 리스트(006)는 그 반대다. 트리는 데이터를 정렬된 계층 구조로 배치해 조회·삽입·삭제를 모두 O(log N)에 가깝게 만들어 두 자료구조의 장점을 동시에 취하려는 시도다.
- **핵심 직관**: 스무고개 게임이다. 매 질문(노드 비교)마다 남은 탐색 범위가 절반(또는 1/n)으로 줄어들어, 전체를 하나씩 훑지 않고도 목표에 빠르게 도달한다.

## 핵심 용어 정리
| 용어 | 의미 | 비유 |
|:---|:---|:---|
| 비선형 자료구조 | 원소가 한 줄이 아니라 가지치기 형태로 연결되는 자료구조 | 나뭇가지, 가계도 |
| 계층 구조(Hierarchy) | 상위-하위 관계가 있는 구조 | 회사 조직도 |
| 루트(Root) | 트리의 최상위 노드, 부모가 없는 유일한 노드 | 가계도의 시조 |
| 리프(Leaf) | 자식이 없는 최말단 노드 | 가계도의 막내 세대 |
| 부모/자식 | 직접 연결된 상하 노드 관계 | 부모와 자녀 |
| 서브트리 | 어떤 노드를 루트로 삼아 그 아래 전체를 떼어낸 트리 | 조직도 안의 한 부서 |
| 높이(Height) | 루트에서 가장 먼 리프까지의 간선 수 | 가계도의 세대 수 |
| 이진 탐색 트리(BST) | 왼쪽 서브트리는 모두 작은 값, 오른쪽은 모두 큰 값인 이진 트리 | 알파벳 순서로 나뉜 서류함 |
| 편향 트리(Skewed Tree) | 한쪽으로만 가지가 뻗어 사실상 연결 리스트가 된 트리 | 외줄로 늘어선 도미노 |
| 균형 인수(Balance Factor) | AVL에서 왼쪽·오른쪽 서브트리 높이 차이 | 시소의 기울기 |
| 회전(Rotation) | 균형을 맞추기 위해 부모-자식 관계를 재배치하는 연산 | 시소 균형 맞추기 |
| Red-Black 색상 규칙 | 각 노드에 빨강/검정 색을 부여해 대략적 균형을 강제하는 규칙 | 신호등 규칙으로 줄 세우기 |
| B-Tree 차수(Order) | 한 노드가 가질 수 있는 최대 자식 수 | 한 서랍에 들어가는 칸막이 개수 |
| 노드 분할(Split) | B-Tree에서 노드가 꽉 찼을 때 둘로 쪼개고 중앙값을 부모로 올리는 연산 | 서랍이 꽉 차서 새 서랍을 만들고 대표 하나를 상위 목록에 등록 |
| B+Tree | B-Tree 변형, 실제 데이터는 리프에만 두고 리프끼리 연결 리스트로 잇는 구조 | 색인은 목차에만, 본문은 마지막 페이지들만 순서대로 |

## 깊이 이해

### 이진 탐색 트리가 왜 무너지는가 — 편향 트리 수치 예시
BST는 "왼쪽엔 작은 값, 오른쪽엔 큰 값"이라는 규칙만으로 탐색 범위를 매번 절반씩 줄인다. 그런데 데이터가 1, 2, 3, ..., 1000처럼 이미 정렬된 순서로 들어오면 매번 "오른쪽 자식"에만 붙어, 결국 높이가 999인 외줄 트리가 된다. 이 상태에서 마지막 값을 찾으려면 노드를 999번 거쳐야 하므로 O(N)이다 — 트리를 썼는데도 연결 리스트와 다를 게 없다. 반대로 같은 1,000개를 완전히 균형 잡힌 형태로 넣으면 높이는 log₂(1000)≈10이라 최대 10번 비교로 어떤 값이든 찾는다. 같은 데이터, 같은 종류의 트리라도 삽입 순서에 따라 성능이 O(N)에서 O(log N)까지 100배 가까이 벌어질 수 있다 — 이것이 균형 유지 알고리즘이 필요한 이유다.

### AVL 트리 — 엄격한 균형
AVL은 모든 노드에서 "왼쪽 서브트리 높이 - 오른쪽 서브트리 높이"(균형 인수)가 항상 -1, 0, 1 중 하나이도록 강제한다. 삽입·삭제로 이 조건이 깨지면 즉시 회전(단일 회전 LL/RR, 이중 회전 LR/RL)으로 재조정한다. 예를 들어 정렬된 데이터를 계속 넣어도 회전이 매번 발동해 높이가 항상 log₂(N) 근처로 유지된다. 다만 삽입·삭제마다 회전 여부를 검사하고 실행하는 비용이 있어, 조회가 압도적으로 많고 쓰기가 드문 경우에 유리하다.

### Red-Black 트리 — 느슨한 균형으로 쓰기 비용 절감
Red-Black은 노드마다 Red/Black 색을 부여하고 "루트는 Black", "Red 노드의 자식은 반드시 Black(Red가 연속 불가)", "루트에서 모든 리프까지 Black 노드 수가 동일" 같은 규칙을 지킨다. 이 규칙들은 "가장 긴 경로가 가장 짧은 경로의 2배를 넘지 않는다"(높이 ≤ 2×log₂(N+1))는 것만 보장할 뿐, AVL만큼 엄격하게 좌우를 맞추지는 않는다. 대신 삽입·삭제 시 재조정 범위(회전 횟수)가 AVL보다 작아 쓰기 성능이 좋다. 그래서 Java의 TreeMap, C++의 std::map, 리눅스 커널의 CFS 스케줄러처럼 삽입·삭제가 잦은 인메모리 구조의 표준으로 채택됐다.

### B-Tree — 디스크를 염두에 둔 다원 탐색
메모리와 디스크는 접근 속도 차이가 수만 배 나기 때문에(RAM 접근이 나노초 단위라면 디스크 탐색은 밀리초 단위), 디스크에서는 "몇 번 접근하느냐"(I/O 횟수)가 성능을 좌우한다. 이진 트리는 노드마다 자식이 2개뿐이라 100만 개 데이터를 담으면 높이가 log₂(1,000,000)≈20이 되어 디스크를 20번 오가야 한다. B-Tree는 노드 하나에 자식을 수백 개까지 담을 수 있다(디스크 블록 크기, 예: 8KB에 맞춰 설계). 차수가 100이라면 같은 100만 개 데이터의 높이는 log₁₀₀(1,000,000)=3에 불과해, 디스크 접근이 20번에서 3번으로 줄어든다. 이 차이가 B-Tree가 RDBMS 인덱스의 표준이 된 이유다. B+Tree는 여기서 한 발 더 나아가 실제 데이터는 리프 노드에만 두고 리프끼리 연결 리스트로 이어, `BETWEEN`이나 범위 검색 시 리프만 순차적으로 훑으면 되게 만든다.

### 판별 원리 — 언제 무엇을 쓰는가
저장 매체가 메모리(RAM)이고 조회가 압도적으로 많다면 AVL, 삽입·삭제가 잦은 범용 인메모리 컨테이너라면 Red-Black, 디스크나 SSD처럼 블록 단위 I/O가 비싼 저장소라면 B-Tree/B+Tree를 쓴다. 판단 기준은 "회전 비용을 감수하고서라도 최대한 평평하게 유지할 것인가"와 "매체 접근 1회의 비용이 얼마나 비싼가"다.

### 비유
결재 서류가 사원→대리→과장→부장 순서로 한 줄로만 올라가면(편향 트리) 병목이 생긴다. 반대로 임원 1명 아래 부서장 2명, 그 아래 팀장 4명으로 조직을 넓게 펼치면(균형 트리) 같은 인원이라도 결재 단계가 훨씬 짧아진다 — B-Tree는 한 임원 아래 팀장을 100명씩 두는 것과 같다.

### 흔한 오해
"트리를 쓰면 자동으로 O(log N)이 보장된다"는 오해가 흔하다. 실제로는 균형을 강제하는 알고리즘(회전, 색상 규칙, 노드 분할)이 탑재된 트리만 최악의 경우에도 O(log N)을 보장한다. 일반 BST는 입력 순서에 따라 O(N)까지 나빠질 수 있다.

## 핵심 인사이트 (3줄 요약)

> 1. **본질**: 데이터 탐색 공간을 매 노드마다 하위 분기 수로 분할하여 최악 O(log N) 조회·삽입을 달성하는 계층적 자료구조이다.
> 2. **가치**: 데이터가 한쪽으로 쏠리는 편향 트리 발생을 알고리즘적으로 방어하여 인프라의 응답 지연 한계(SLA)를 억제한다.
> 3. **판단 포인트**: 메인 메모리 구조(RAM)에서는 캐시 제어 유연성을 위한 Red-Black 트리를, 블록 단위 디스크 I/O가 발생하는 RDBMS 인덱스에는 B-Tree 계열을 적용해야 한다.

## 출제 의도 및 답안 포인트

| 출제 의도 | 반드시 짚을 핵심 | 감점 회피 포인트 |
|:---|:---|:---|
| 편향 트리 문제점 및 자가 균형 유지 원리 확인 | 균형 인수(AVL), 색상 규칙(Red-Black), 분할 병합(B-Tree) | 세 트리의 이름만 나열하고 회전/분할의 구조적 방어 로직 누락 |
| 매체(Memory vs Disk) 특성에 따른 자료구조 선택 | B-Tree가 디스크 친화적인 이유 (노드 단위와 블록 매핑) | "B-Tree가 무조건 제일 좋다"며 메모리 환경 특성 무시 |

> 요약: 트리 구조 설계는 탐색 속도 방어를 위한 균형 비용 지불과, 저장 매체(RAM vs Disk)의 물리적 특성 결합의 산물이다.

## Ⅰ. 개요 및 필요성

- 정의: 이진 탐색의 경직성을 극복하고 탐색 공간을 O(log N)으로 유지하기 위해 계층적으로 노드를 연결한 균형 보장 자료구조
- 배경: 단순 이진 탐색 트리는 정렬된 데이터 삽입 시 연결 리스트화 되어 O(N)으로 전락하는 편향 취약점 내재
- 필요성: 시스템 인메모리 정렬 구조 유지 및 RDBMS 대용량 스토리지 인덱싱에서 안정적 지연시간 확보를 위해 자가 균형 메커니즘 필수

## Ⅱ. 3대 주요 트리 구조 및 방어 기전

```text
[요청] -> 균형 알고리즘 -> 회전(Rotation) / 색상 변경 / 노드 분할(Split) -> 균형 유지 트리 보장
```

| 트리 구조 | 자가 균형 메커니즘 | 특이사항 |
|:---|:---|:---|
| AVL Tree | 깐깐한 균형 인수(Balance Factor) 통제 | 좌우 높이 차를 항상 1 이하로 억제해 탐색 속도 극대화 |
| Red-Black Tree | 노드 색상(Red/Black) 5대 규칙 적용 통제 | 루트-리프까지 Black 노드 개수 일치 보장 (회전 감소) |
| B-Tree | 다원 탐색 및 블록(페이지) 단위 노드 구성 | 하나의 노드에 여러 키를 담아 트리 높이를 극적으로 단축 |

> 요약: AVL은 탐색 지향, Red-Black은 밸런싱 비용 저감 지향, B-Tree는 디스크 접근 횟수 최소화를 위해 설계되었다.

## Ⅲ. B-Tree 디스크 최적화 원리 및 분할 흐름도

```text
레코드 삽입 -> 노드 허용치 검사 -> 오버플로우 발생 시 노드 Split(분할) -> 중간값 부모 노드로 승격
```

| 단계 | 처리 내용 | 검증 기준 |
|:---:|:---|:---|
| 1 | 타겟 노드 탐색 | 루트에서 하향 탐색하여 리프(Leaf) 노드 위치 확정 |
| 2 | 데이터 삽입 검증 | 타겟 노드 공간이 최대치 미만이면 삽입 후 종료 |
| 3 | 초과 분할 (Split) | 공간 초과 시 노드를 두 개로 쪼개고 중앙값을 부모 노드로 승격 |
| 4 | 연쇄 상승 (Cascade) | 부모 노드 초과 시 루트 방향으로 분할 반복 및 트리 높이 증가 |

> 요약: B-Tree 계열은 데이터가 위(Root 방향)로 밀려 올라가는 상향 증식 구조를 가져 전체 트리의 잎 깊이가 항상 일정하다.

## Ⅳ. 특징

| 구분 | AVL Tree | Red-Black Tree | 판단 포인트 |
|:---|:---|:---|:---|
| 균형 엄격도 | 좌우 서브트리 높이차 최대 1로 엄격 통제 | 색상 규칙 기반 근사 균형(최대 높이 약 2×log₂(N+1)) | 탐색 지연 허용치 |
| 삽입 시 재조정 | 최대 1회 회전(단일/이중)으로 복구 | 최대 2회 회전 + 색상 재조정으로 복구 | 삽입 빈도 |
| 삭제 시 재조정 | 루트까지 연쇄적으로 재조정 발생 가능(O(log N) 회전) | 최대 3회 회전으로 재조정 범위 제한 | 삭제 빈도가 높은 워크로드 |
| 적용 사례 | 읽기 집약적 인메모리 인덱스 | Java TreeMap/TreeSet, 리눅스 CFS 스케줄러 | 삽입·삭제 대비 조회 비율 |

> 요약: AVL은 탐색 속도를 최우선하여 균형을 엄격히 유지하고, Red-Black은 삽입·삭제 시 재조정 범위를 제한해 쓰기 비용을 낮춘다.

## Ⅴ. 심화 비교 및 매체 특성 적용 판단

| 비교 축 | Red-Black Tree | B-Tree / B+Tree | 선택 기준 |
|:---|:---|:---|:---|
| 물리 매체 | Main Memory (RAM) 캐시 지향 | Disk / SSD 블록 저장소 지향 | 접근 매체의 I/O 지연 비용 폭 |
| 노드 크기 | 고정된 작은 객체 크기 (2 pointers) | 디스크 블록 크기 맵핑 (예: 8KB) | 캐시 라인 vs 페이지 사이즈 적합성 |
| 트리의 깊이 | 이진 분할로 비교적 깊음 | 다원 분할로 극도로 얕음 | 랜덤 I/O 횟수 임계치 여부 |
| 범위 검색 | 중위 순회를 통해 순차 획득 | B+Tree 리프 간 Linked List로 압도적 | 부등호 및 BETWEEN 쿼리 빈도 |

> 요약: RAM은 포인터 추적 지연이 작아 Red-Black이 유리하지만, 디스크는 헤드 이동 지연이 크므로 트리를 납작하게 만들어(B-Tree) 읽기 횟수를 줄인다.

| 리스크 | 발생 원인 | 대응 기법 | 확인 지표 |
|:---|:---|:---|:---|
| 인덱스 파편화 | 잦은 데이터 삭제/변경으로 노드 병합/분할 빈발 | 트리 Re-build (OPTIMIZE TABLE) 주기적 수행 | 페이지 단편화율 |
| 캐시 락 경합 | 트리 순회 시 글로벌 락 점유 문제 발생 | 노드/페이지 단위 파인 그레인(Fine-grain) 락 분산 | 락 경합 대기 시간 |

> 요약: 트리 구조는 갱신 오버헤드를 수반하므로 대량 데이터 삽입 시 인덱스를 비활성화 후 일괄 빌드하는 것이 표준이다.

## Ⅵ. 실무 적용 및 결론

**적용 방안 3개:**
1. RDBMS 클러스터 인덱스 설계: MySQL InnoDB 엔진에 B+Tree를 적용, 데이터 레코드와 인덱스 리프 노드를 묶어 순차 I/O로 최적화
2. 표준 라이브러리 엔진: Java의 TreeMap, TreeSet 내부 구조에 Red-Black 트리를 채택하여 악의적 삽입 공격 시에도 O(log N) 서비스 보장
3. 리눅스 스케줄러(CFS) 구현: 운영체제 완전 공정 스케줄러에서 실행 시간을 기준으로 Red-Black 트리를 구성해 다음 타겟을 즉시 선출

**결론 (2줄):**
- 기술사 판단: 트리는 탐색 고속화와 균형 유지 오버헤드 간의 타협이며, 저장 매체의 물리적 접근 비용 차이가 적용 경계를 결정한다.
- 향후 방향: 읽기/쓰기 비율이 치우치는 빅데이터 쓰기 환경에서는 B-Tree를 넘어 LSM-Tree(Log-Structured Merge Tree)가 스토리지 표준으로 채택되고 있다.
