# 007. 스택·큐·덱 (Stack Queue Deque) [출제: ]

## 미리 알고가기

- **LIFO (Last In First Out)**: 늦게 들어온 것이 먼저 나옴. 좁은 접시 통에 접시를 쌓으면 맨 위, 즉 마지막에 올린 접시부터 집게 되는 것과 같음
- **FIFO (First In First Out)**: 먼저 들어온 것이 먼저 나옴. 매표소 줄에서 앞에 선 사람이 먼저 표를 받는 것과 같음
- **추상 자료형 (ADT)**: "무엇을 할 수 있는가" (넣기·빼기)만 정하고 "어떻게 만드는가" (배열·연결 리스트)는 따로 두는 개념. 같은 스택이라도 내부는 배열일 수도 리스트일 수도 있음

## Ⅰ. 개요

- **정의/개념**: 스택·큐·덱은 값을 어디로 넣고 어디로 빼는지를 한쪽 끝 또는 양쪽 끝으로 제한해, 먼저 넣은 것과 나중에 넣은 것 중 무엇을 먼저 꺼낼지를 규칙으로 고정하는 선형 자료구조임
- **배경/필요성**: 배열은 몇 번째 값이든 바로 접근 가능하지만, "임의 접근"이 함수 호출이나 대기 줄처럼 순서가 핵심인 문제에서는 오히려 실수의 여지가 됨. 되돌리기 기능이나 공정한 대기열 처리를 위해 넣고 빼는 위치를 한쪽 끝(스택), 앞뒤 양끝(큐), 양쪽 다(덱)로 제한하여 순서를 구조적으로 강제해야 함

## Ⅱ. 특징 및 비교

세 자료구조는 모두 삽입/삭제 위치를 제한한다는 점은 같으나, 개방 위치와 순차 논리에서 차이가 있음.

| 구분 | 넣고 빼는 위치 | 꺼내는 순서 | 특징 | 대표 활용 |
|:---|:---|:---|:---|:---|
| 스택 (Stack) | 한쪽 끝 ($Top$)에서만 | LIFO | 쌓은 접시 구조 | 함수 호출, DFS, 실행 취소 |
| 큐 (Queue) | 뒤 ($Rear$)로 넣고 앞 ($Front$)으로 빼기 | FIFO | 매표소 줄 구조 | BFS, 작업 대기열, 버퍼 |
| 덱 (Deque) | 앞·뒤 양끝 모두 | 양방향 자유 | 양쪽이 열린 줄 | 슬라이딩 윈도우, Work Stealing |

> 요약: 한쪽만 열면 스택, 앞뒤가 다르면 큐, 양끝 다 열면 큐와 스택을 겸하는 덱임.

세 자료형의 삽입·삭제는 모두 끝점만 제어하므로 $O(1)$이나, 특정 값 탐색은 $O(n)$이 소요됨.

## Ⅲ. 구성요소/구조

- **구조도**:

```text
Stack   Top -> [ D ][ C ][ B ][ A ]     push/pop 모두 Top 한 곳에서 수행
                 ^ 마지막에 넣은 D가 가장 먼저 나옴

Queue   Front -> [ A ][ B ][ C ][ D ] <- Rear
                   ^ 먼저 온 A가 먼저 나가고, 새 값 D는 뒤에 붙음

Deque   Front <-> [ A ][ B ][ C ][ D ] <-> Rear    양끝 모두 넣고 뺄 수 있음
```

- **핵심 구성요소**:

| 구성요소 | 역할 | 핵심 포인트 |
|:---|:---|:---|
| $Top$ | 스택에서 삽입/삭제가 일어나는 유일한 위치 | LIFO 논리 유지의 핵심 |
| $Front$ | 큐·덱에서 데이터가 나가는 출구 | 먼저 들어온 값의 위치 지시 |
| $Rear$ | 큐·덱에서 데이터가 들어오는 입구 | 새 데이터가 추가되는 위치 지시 |
| 원형 인덱스 | $(index + 1) \pmod n$ 연산 수행 | 배열 기반 큐의 공간 재사용 극대화 |
| Empty/Full 조건 | 빔/가득 참 상태를 판정하는 경계 조건 | Underflow·Overflow 방지 |

> 요약: $Top$, $Front$, $Rear$ 포인터가 데이터 흐름을 제어하며, 원형 구조와 경계 조건이 구조적 안정성을 보장함.

## Ⅳ. 문제점 및 개선방안

1. **순서 모델 선택 오류**: FIFO가 필요한 대기열에 스택을 적용할 경우 공정성이 깨지는 등 논리적 오류가 발생함
   - **개선방안**: 요구사항의 데이터 처리 순서를 나열해 보고 LIFO/FIFO 적합성을 검증함 (확인: 예시 입력 대비 출력 순서 일치 여부)

2. **원형 큐의 상태 판별 모호성**: $front == rear$ 조건만으로는 빔(Empty)과 가득 참(Full) 상태를 구분할 수 없음
   - **개선방안**: 현재 개수를 추적하는 $count$ 변수를 도입하거나, 배열 한 칸을 항상 비워두어 상태를 분리함 (확인: 경계 조건에서의 삽입·삭제 정상 동작)

3. **동시 접근 시 데이터 무결성 파괴**: 다중 스레드 환경에서 동일 큐에 접근할 경우 경쟁 상태(Race Condition)가 발생함
   - **개선방안**: 뮤텍스(Mutex) 등으로 임계 구역을 보호하거나, CAS(Compare-And-Swap) 기반의 Lock-free 자료구조를 적용함 (확인: 고부하 시 데이터 유실/중복 여부)

## Ⅴ. 실무 적용 사례

| 적용 영역 | 적용 방식 | 확인 지표 |
|:---|:---|:---|
| 프로그램 런타임 스택 | 함수 호출 시 복귀 주소와 지역 변수를 스택에 저장하고 반환 시 역순으로 제거 | 최대 스택 깊이, Stack Overflow 발생률 |
| 비동기 메시지 큐 | 생산자와 소비자 사이의 속도 차이를 큐(FIFO)로 완충하여 시스템 결합도 제거 | 큐 적체 길이, 메시지 처리 지연 시간 |
| 작업 훔치기 (Work Stealing) | 각 스레드가 자신의 덱 앞쪽에서 일하고, 유휴 스레드는 남의 덱 뒤쪽 작업을 가져감 | 스레드 부하 균형도, 작업 경합 오버헤드 |

> 요약: 최근 이력 추적은 스택, 순차 처리는 큐, 양단 제어가 필요하면 덱을 활용함.

## Ⅵ. 결론

스택·큐·덱은 검색 성능보다 '데이터 처리 순서의 강제'를 목적으로 하는 추상 자료형임. 기술사는 단순히 자료구조의 명칭을 아는 것에 그치지 않고, 요구사항에 맞는 처리 순서(LIFO/FIFO)를 정확히 판별하여 구조를 선택해야 함.

또한 실무 적용 시에는 배열과 연결 리스트 중 시스템 자원에 적합한 구현 방식을 결정하고, 원형 큐의 경계 조건 처리나 동시성 제어와 같은 세부 구현 이슈를 해결하여 시스템의 신뢰성을 확보할 수 있어야 함. 결국 이러한 선형 자료구조는 복잡한 시스템의 흐름을 제어하는 가장 기초적이면서도 강력한 설계 도구임.
