## 미리 알고가기

- $LIFO(Last-In, First-Out)$: 마지막에 삽입된 데이터가 가장 먼저 제거되는 후입선출 원리임
- $FIFO(First-In, First-Out)$: 가장 먼저 삽입된 데이터가 가장 먼저 제거되는 선입선출 원리임
- $Deque(Double-Ended Queue)$: 양쪽 끝(Front, Rear) 모두에서 삽입과 삭제가 가능한 선형 자료구조임
- 오버플로(Overflow): 저장 공간이 가득 찬 상태에서 데이터를 추가로 삽입하려 할 때 발생하는 오류임

## Ⅰ. 개요

- **정의/개념**: 스택, 큐, 덱은 데이터의 삽입과 삭제 위치를 특정 지점으로 제한하여 처리 순서($Order$)를 제어하는 선형 자료구조 알고리즘 군임
- **배경/필요성**: 함수 실행 이력 관리, 작업 대기열 처리, 메시지 버퍼링 등 데이터의 유입 순서가 처리 결과의 정합성을 결정하는 문제에서는 임의 접근보다 엄격한 입출력 규칙을 강제할 구조가 필요함

## Ⅱ. 특징

- 스택은 복귀 주소 관리나 실행 취소($Undo$)처럼 직전의 상태를 가장 먼저 참조해야 하는 역순 처리 작업에 최적화됨
- 큐는 프린터 스풀링이나 서버의 요청 대기열처럼 유입된 순서를 보존하여 공정하게 처리해야 하는 스케줄링 업무에 적합함
- 덱은 스택과 큐의 성질을 동시에 가져 상황에 따라 입출력 방향을 유연하게 조정할 수 있으며, 슬라이딩 윈도우 탐색 등 양방향 조작이 필요한 알고리즘에 활용됨

## Ⅲ. 종류 및 비교

| 판단 기준 | 스택 (Stack) | 큐 (Queue) | 덱 (Deque) |
|:---|:---|:---|:---|
| **입출력 원리** | $LIFO$ (후입선출) | $FIFO$ (선입선출) | 양방향 선택 가능 |
| **삽입/삭제 위치** | 한쪽 끝 ($Top$) | $Rear$ 삽입 / $Front$ 삭제 | $Front$, $Rear$ 양쪽 모두 |
| **주요 활용** | 재귀 호출, 괄호 검사, DFS | 스케줄링, 버퍼, BFS | 슬라이딩 윈도우, 우선순위 조절 |
| **시간복잡도** | 삽입·삭제 $O(1)$ | 삽입·삭제 $O(1)$ | 삽입·삭제 $O(1)$ |

> 요약: 작업의 역순 처리가 필요하면 스택을, 유입 순서대로 처리가 필요하면 큐를, 양방향 제어가 필요하면 덱을 사용함.

## Ⅳ. 구성요소 및 구조

| 구성요소 | 설명 |
|:---|:---|
| 저장체 | 데이터를 실제로 담는 배열($Array$) 또는 연결 리스트($Linked List$) 구조임 |
| 제어 포인터 | 데이터가 들어오고 나가는 위치를 지적하는 $Top$, $Front$, $Rear$ 등의 변수임 |
| 상태 판정 로직 | 현재 공간이 비어있는지($Empty$) 혹은 가득 찼는지($Full$) 확인하여 예외를 방어함 |
| 원소 전송 연산 | $Push/Pop$, $Enqueue/Dequeue$ 등 각 구조에 정의된 고유의 입출력 명령임 |

```text
[ 선형 자료구조 입출력 모델 ]
Stack:   [Data3] (Top) -> [Data2] -> [Data1]  (한 방향)
Queue:   [Data3] (Rear) -> [Data2] -> [Data1] (Front) (통로형)
Deque:   (Front) <-> [Data1] <-> [Data2] <-> (Rear)   (양방향)
```

## Ⅴ. 원리 및 절차 흐름도

```text
+-------------+     +--------------+     +-------------+     +-------------+
| 연산 요청    | --> | 용량/상태 체크 | --> | 데이터 입출력 | --> | 포인터 업데이트|
+-------------+     +--------------+     +-------------+     +-------------+
```

1. **연산 요청** — 외부 인터페이스를 통해 삽입($Push/Enqueue$) 또는 삭제($Pop/Dequeue$) 요청을 수신함
2. **상태 체크** — 삽입 시에는 가득 찼는지($Full$), 삭제 시에는 비었는지($Empty$)를 먼저 판정하여 오버플로/언더플로를 방지함
3. **입출력 수행** — 현재 포인터가 가리키는 메모리 위치에 데이터를 쓰거나, 해당 위치의 데이터를 읽어 반환함
4. **포인터 갱신** — 연산이 성공하면 $Top$을 증감시키거나, 원형 큐의 경우 나머지 연산($\%$)을 통해 $Front/Rear$ 위치를 다음 칸으로 이동함

## Ⅵ. 실무 적용 및 유의점

1. 재귀 호출 깊이가 깊어지거나 대량의 데이터를 스택에 쌓을 경우 시스템의 스택 영역 한계를 넘어 $StackOverflow$가 발생할 수 있으므로, 임계치를 설정하고 필요한 경우 반복문 기반의 명시적 스택 구조로 전환하여 메모리 안정성을 확보해야 함
2. 배열 기반의 일반 큐는 데이터 추출 시마다 남은 원소를 당겨야 하는 $O(n)$의 오버헤드가 발생하므로, 포인터만 이동하는 원형 큐($Circular$ $Queue$)를 적용하고 공백과 포화 상태를 구분하기 위해 한 칸의 여유 공간을 두는 설계를 반영해야 함

## Ⅶ. 결론

- 스택, 큐, 덱은 알고리즘의 실행 흐름과 처리 순서를 결정하는 기초 설계 단위이며, 구현 시에는 메모리 확장 한계와 경계 조건 오류($Off-by-one$)를 철저히 관리하여 시스템의 논리적 결함을 차단해야 함
