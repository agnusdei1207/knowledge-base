## 핵심 인사이트 (3줄 요약)

> 1. **본질**: 스택(Stack)은 **LIFO(Last In, First Out)**, 큐(Queue)는 **FIFO(First In, First Out)**, 덱(Deque, Double-Ended Queue)은 **양쪽 끝에서 삽입·삭제**가 가능한 선형 자료구조이다. 세 자료구조 모두 삽입·삭제가 O(1)이며, 데이터 접근 순서를 제어하는 **추상 자료형(ADT)**이다.
> 2. **가치**: 스택은 함수 호출 관리(콜 스택), 괄호 검사, 실행 취소(Undo) 등에 쓰이고, 큐는 프로세스 스케줄링, 메시지 큐(Kafka, RabbitMQ), BFS 탐색 등에 쓰인다. 덱은 슬라이딩 윈도우 최댓값, 브라우저 히스토리 등 양방향 접근이 필요한 경우에 사용된다.
> 3. **융합**: 운영체제(콜 스택·프로세스 큐), 네트워크(패킷 버퍼·QoS), 컴파일러(파싱·후위 표기법), 알고리즘(DFS=스택·BFS=큐) 등 CS 전 분야에서 데이터의 **순서와 흐름**을 제어하는 핵심 도구이다.

---

## Ⅰ. 개요 및 필요성

- **개념**: 스택은 한쪽 끝(top)에서만 삽입(push)·삭제(pop)하는 LIFO 구조이다. 큐는 뒤(rear)에서 삽입(enqueue)하고 앞(front)에서 삭제(dequeue)하는 FIFO 구조이다. 덱은 앞과 뒤 양쪽에서 삽입·삭제가 모두 가능한 일반화된 구조이다.

- **필요성**: 프로그램의 함수 호출은 본질적으로 LIFO이다 — 마지막에 호출된 함수가 먼저 반환되어야 한다. 반면 프린터 대기열은 FIFO이다 — 먼저 요청한 문서가 먼저 인쇄되어야 한다. 이처럼 데이터의 처리 순서가 문제의 성격에 의해 결정되며, 올바른 자료구조를 선택하는 것이 정확한 동작의 전제 조건이다.

- **비유**: 스택은 **접시 쌓기**이다 — 맨 위에 접시를 올리고, 맨 위의 접시를 꺼낸다. 큐는 **줄 서기**이다 — 뒤에 서고, 앞에서부터 입장한다. 덱은 **양쪽 문이 있는 복도**이다 — 어느 쪽으로든 들어오고 나갈 수 있다.

- **등장 배경 및 발전 과정**:
  1. **1946년 — 스택의 탄생**: Alan Turing이 서브루틴 호출 스택 개념을 최초로 제안했다. 이후 Friedrich Bauer가 1957년 "켈러(Keller)"라는 이름으로 공식화했다.
  2. **1960년대 — 큐의 체계화**: 운영체제의 프로세스 스케줄링과 함께 큐가 핵심 자료구조로 자리잡았다.
  3. **현대 — 메시지 큐의 부상**: Kafka, RabbitMQ, SQS 등 분산 메시지 큐는 마이크로서비스 아키텍처의 핵심 인프라가 되었다. 내부적으로 큐의 FIFO 원칙을 분산 환경에서 보장한다.

```text
+-----------------------------------------------------------------------+
|          스택·큐·덱의 동작 원리 비교                                  |
+-----------------------------------------------------------------------+
|                                                                       |
|  [스택 (LIFO)]          [큐 (FIFO)]          [덱 (양방향)]            |
|                                                                       |
|  push(A) →  |A|         enqueue(A) → [A]     pushFront(A) → [A]      |
|  push(B) →  |B|         enqueue(B) → [A,B]   pushBack(B)  → [A,B]    |
|             |A|                                                       |
|  push(C) →  |C|         enqueue(C) → [A,B,C] pushFront(C) → [C,A,B]  |
|             |B|                                                       |
|             |A|                                                       |
|                                                                       |
|  pop()   → C 반환       dequeue()  → A 반환   popFront()  → C 반환   |
|             |B|                     [B,C]     popBack()   → B 반환    |
|             |A|                                            [A]        |
|                                                                       |
|  ※ 마지막 넣은 것을    ※ 먼저 넣은 것을     ※ 양쪽 끝에서         |
|     먼저 꺼냄            먼저 꺼냄            삽입·삭제 가능         |
+-----------------------------------------------------------------------+
```

**[다이어그램 해설]** 세 자료구조의 핵심 차이를 동작 순서로 보여준다. 스택에 A, B, C를 순서대로 넣으면 pop 시 C가 먼저 나온다(LIFO). 큐에 같은 순서로 넣으면 dequeue 시 A가 먼저 나온다(FIFO). 덱은 양쪽 끝에서 자유롭게 삽입·삭제 가능하여 스택과 큐 모두를 시뮬레이션할 수 있다. Python의 `collections.deque`는 양쪽 끝 O(1) 연산을 보장하며, 스택·큐 용도로 모두 사용 가능하다.

- **📢 섹션 요약 비유**: 스택은 엘리베이터(마지막 탄 사람이 먼저 내림), 큐는 매표소(먼저 온 사람이 먼저 표를 삼), 덱은 지하철(앞뒤 문 다 열림)입니다.

## Ⅱ. 아키텍처 및 핵심 원리

### 구성 요소

| 요소명 | 스택 | 큐 | 덱 | 비유 |
|:---|:---|:---|:---|:---|
| **삽입 위치** | top만 | rear | 양쪽 끝 | 접시 위/줄 뒤/양쪽 문 |
| **삭제 위치** | top만 | front | 양쪽 끝 | 접시 위/줄 앞/양쪽 문 |
| **주요 연산** | push, pop, peek | enqueue, dequeue, front | pushFront/Back, popFront/Back | 올리기/내리기, 줄서기/입장 |
| **구현 방법** | 배열 or 연결 리스트 | 원형 배열 or 연결 리스트 | 원형 배열 or 이중 연결 리스트 | — |
| **시간 복잡도** | 모든 연산 O(1) | 모든 연산 O(1) | 모든 연산 O(1) | — |

### 구현 패턴 — 원형 큐(Circular Queue)

```text
+-----------------------------------------------------------------------+
|         원형 큐 — 배열 기반 큐의 공간 낭비 문제 해결                  |
+-----------------------------------------------------------------------+
|                                                                       |
|  [일반 배열 큐의 문제]                                                |
|  front↓         rear↓                                                |
|  [ ][ ][A][B][C][ ][ ]  ← 앞쪽 빈 공간을 재활용 못 함               |
|                         dequeue로 빈 슬롯이 앞에 쌓임                |
|                                                                       |
|  [원형 큐의 해결]                                                     |
|       front=2        rear=6                                          |
|         ↓              ↓                                             |
|  +---+---+---+---+---+---+---+                                       |
|  | D | E |   |   | A | B | C |  ← rear가 끝에 도달하면 0번으로 회전 |
|  +---+---+---+---+---+---+---+                                       |
|    0   1   2   3   4   5   6                                         |
|                                                                       |
|  인덱스 계산: rear = (rear + 1) % M                                  |
|              front = (front + 1) % M                                 |
|                                                                       |
|  가득 참 조건: (rear + 1) % M == front                               |
|  비어있음 조건: rear == front                                        |
+-----------------------------------------------------------------------+
```

**[다이어그램 해설]** 일반 배열로 큐를 구현하면 dequeue 시 앞쪽에 빈 공간이 쌓이지만 rear가 배열 끝에 도달하면 더 이상 삽입할 수 없다(앞쪽이 비어있어도). 원형 큐는 배열을 원형으로 취급하여 rear가 끝에 도달하면 인덱스 0으로 돌아간다. `% M`(모듈러 연산)으로 구현하며, 가득 참과 비어있음을 구분하기 위해 한 칸을 비워두거나 별도 변수(size)를 사용한다. 운영체제의 키보드 입력 버퍼, 네트워크의 링 버퍼(Ring Buffer) 등이 원형 큐의 대표적 실무 활용이다.

- **📢 섹션 요약 비유**: 원형 큐는 회전초밥 컨베이어 벨트입니다. 끝까지 가면 다시 처음으로 돌아오므로 공간이 낭비되지 않습니다. 일반 큐는 직선 레일이라 끝에 도달하면 멈춰야 합니다.

## Ⅲ. 비교 및 연결

### 비교 1: 스택 vs 큐의 응용 분야

| 비교 항목 | 스택 (LIFO) | 큐 (FIFO) |
|:---|:---|:---|
| **알고리즘 탐색** | DFS (깊이 우선 탐색) | BFS (너비 우선 탐색) |
| **운영체제** | 함수 호출 스택 (Call Stack) | 프로세스 스케줄링 큐 |
| **컴파일러** | 후위 표기법 변환, 괄호 검사 | 토큰 스트림 처리 |
| **사용자 인터페이스** | Undo/Redo (실행 취소·재실행) | 작업 대기열 (Print Queue) |
| **네트워크** | 프로토콜 스택 (TCP/IP 계층) | 패킷 버퍼, 메시지 큐 |
| **분산 시스템** | (드물게 사용) | Kafka, RabbitMQ, SQS |

### 비교 2: 우선순위 큐와의 차이

| 비교 항목 | 일반 큐 (Queue) | 우선순위 큐 (Priority Queue) |
|:---|:---|:---|
| **추출 순서** | 먼저 들어온 것 | 우선순위가 가장 높은 것 |
| **내부 구현** | 배열/연결 리스트 | 힙 (Heap) |
| **삽입 시간** | O(1) | O(log N) |
| **추출 시간** | O(1) | O(log N) |
| **용도** | BFS, 작업 대기열 | 다익스트라, A*, 프로세스 스케줄링 |

### 과목 융합 관점
- **운영체제**: 프로세스의 함수 호출 시 **콜 스택(Call Stack)**에 반환 주소·지역 변수·매개변수가 스택 프레임으로 push된다. 함수 반환 시 pop된다. 스택 오버플로우(Stack Overflow)는 재귀가 너무 깊어 스택 메모리 한계를 초과할 때 발생한다.
- **네트워크**: 라우터의 **패킷 버퍼**는 큐로 구현된다. 패킷이 도착하면 enqueue, 전송 시 dequeue한다. 버퍼가 가득 차면 tail drop(뒤쪽 패킷 폐기) 또는 RED(Random Early Detection)로 혼잡 제어한다.
- **웹 개발**: JavaScript의 **이벤트 루프(Event Loop)**는 콜 스택(LIFO)과 태스크 큐(FIFO)를 조합한다. 콜 스택이 비면 태스크 큐에서 다음 콜백을 꺼내 실행한다.

- **📢 섹션 요약 비유**: 스택과 큐의 관계는 계단과 에스컬레이터의 관계입니다. 계단(스택)은 마지막에 올라간 사람이 먼저 내려오고, 에스컬레이터(큐)는 먼저 탄 사람이 먼저 도착합니다. 상황에 맞는 이동 수단을 고릅시다.

## Ⅳ. 실무 적용 및 기술사 판단

### 실무 시나리오

1. **시나리오 — 괄호 유효성 검사 (스택)**: 프로그래밍 언어의 컴파일러가 소스 코드의 괄호 쌍을 검사할 때, 여는 괄호를 push하고 닫는 괄호를 만나면 pop하여 매칭 여부를 확인한다. 스택이 비어있는데 닫는 괄호가 나오거나, 코드 끝에 스택이 비어있지 않으면 문법 오류이다.

2. **시나리오 — 마이크로서비스 간 비동기 통신 (큐)**: 주문 서비스가 결제 서비스에 요청할 때, 직접 HTTP 호출 대신 메시지 큐(Kafka)에 주문 이벤트를 enqueue한다. 결제 서비스는 자신의 속도에 맞게 dequeue하여 처리한다. 이로써 두 서비스가 **시간적으로 결합(Temporal Coupling)**되지 않아 장애 전파를 막고 처리량 급증(스파이크)을 완충한다.

### 도입 체크리스트
- **기술적**: 데이터의 처리 순서가 LIFO인가 FIFO인가 양방향인가? 이 판단이 자료구조 선택의 출발점이다.
- **운영 및 보안적**: 큐의 크기 제한(Back Pressure)이 설정되어 있는가? 무제한 큐는 메모리 고갈을 유발한다.

### 안티패턴
- **무한 큐 설계**: 큐의 최대 크기를 설정하지 않으면 생산자(Producer)가 소비자(Consumer)보다 빠를 때 큐가 메모리를 고갈시킨다. 반드시 **배압(Back Pressure)** 메커니즘을 적용한다.
- **스택으로 BFS 구현 시도**: DFS와 BFS를 혼동하여 스택으로 BFS를 구현하면 탐색 순서가 잘못되어 최단 경로를 찾지 못한다.

- **📢 섹션 요약 비유**: 스택·큐를 잘못 쓰면 식당에서 줄 서기 규칙을 어기는 것과 같습니다. "먼저 온 사람이 먼저 먹는다"는 규칙(큐)을 "마지막 온 사람부터"(스택)로 바꾸면 난리가 납니다.

## Ⅴ. 기대효과 및 결론

### 정량/정성 기대효과

| 구분 | 부적절한 설계 | 적절한 스택/큐 활용 | 개선 효과 |
|:---|:---|:---|:---|
| **정량** | 동기 HTTP 호출, 피크 시 타임아웃 | 메시지 큐로 비동기 처리 | 피크 처리량 **10배** 흡수 |
| **정량** | 재귀 없이 DFS 반복 구현 시 복잡한 상태 관리 | 명시적 스택으로 깔끔한 반복 DFS | 코드 라인 **50%** 감소 |
| **정성** | 서비스 간 강결합으로 장애 전파 | 큐를 통한 느슨한 결합 | 시스템 복원력(Resilience) 확보 |

### 미래 전망
- **이벤트 소싱(Event Sourcing)**: 모든 상태 변경을 이벤트(큐의 메시지)로 기록하고, 재생하여 상태를 복원하는 아키텍처. 금융 시스템, 감사 로그 등에서 확산 중이다.
- **영속 자료구조(Persistent Data Structure)**: 이전 버전을 유지하는 스택/큐. Git의 커밋 히스토리가 영속 스택의 일종이다.

### 참고 표준
- **Turing, A. (1946)**: 서브루틴 호출 스택 개념의 최초 제안
- **Knuth, D. (1997)**: "TAOCP Vol. 1" — 스택·큐의 수학적 분석
- **Jay Kreps (2011)**: "The Log: What every software engineer should know about real-time data's unifying abstraction" — 분산 큐(Kafka)의 설계 철학

스택·큐·덱은 CS에서 가장 기본적인 추상 자료형이지만, 올바른 선택은 시스템의 동작 순서를 결정한다. "이 데이터는 LIFO로 처리해야 하는가, FIFO로 처리해야 하는가?"라는 질문에 정확히 답하는 것이 출발점이다.

- **📢 섹션 요약 비유**: 스택·큐·덱은 교통 규칙과 같습니다. "먼저 온 차가 먼저 간다"(큐), "마지막에 쌓인 짐부터 내린다"(스택) — 규칙을 어기면 사고(버그)가 납니다.

| 그래프 탐색 (BFS/DFS) | BFS=큐, DFS=스택. 탐색 알고리즘의 자료구조 선택이 탐색 순서를 결정. |
| 우선순위 큐 (Priority Queue) | 큐의 확장 — FIFO가 아닌 우선순위 기반 추출. 힙으로 구현. |
| 메시지 큐 (Kafka, RabbitMQ) | 큐 ADT를 분산 시스템으로 확장한 인프라. |

### 📈 관련 키워드 및 발전 흐름도

```text
[배열 / 연결 리스트 (기반 자료구조)]
    |
    v
[스택·큐·덱 (현재 개념, ADT)]
    |
    +---> [그래프 탐색 (BFS=큐, DFS=스택)]
    +---> [운영체제 (콜 스택, 프로세스 큐)]
    +---> [메시지 큐 (Kafka, RabbitMQ)]
    +---> [이벤트 소싱 (Event Sourcing)]
```

### 👶 어린이를 위한 3줄 비유 설명

1. 스택은 레고 블록 쌓기예요 — 맨 위에 올리고, 맨 위에서 꺼내요. 아래쪽 블록을 빼려면 위에 있는 것을 먼저 다 치워야 해요.
2. 큐는 놀이공원 줄 서기예요 — 먼저 온 사람이 먼저 놀이기구를 타요. 새치기 금지!
3. 덱은 양쪽 문이 있는 기차예요 — 앞문으로도 뒷문으로도 타고 내릴 수 있어서 제일 자유로워요!
