# 📖 【암기용】 개념 완전 이해

> 목적: 이 개념을 처음 보는 사람도 완벽히 이해하게 만든다. 시험 답안 양식이 아니라, 이해를 위한 친절한 설명이다.

## 한눈에
- **개요**: 스택·큐·덱은 데이터의 삽입·삭제가 일어나는 위치를 양 끝단으로 제한한 **선형 자료구조**이자, 구현 방식(배열이냐 연결 리스트냐)과 무관하게 "어떤 순서로 넣고 뺄 것인가"라는 정책만 정의하는 **추상 자료형(ADT, Abstract Data Type)**이다.
- **왜 필요한가**: 배열이나 연결 리스트를 아무 위치에서나 자유롭게 접근하도록 놔두면, 함수 호출 복귀 순서나 요청 처리 순서 같은 "순서 보장"이 코드마다 제각각으로 구현되어 버그가 생긴다. 입출구를 강제로 하나(또는 둘)로 좁혀 순서를 시스템적으로 보장하기 위해 만들어졌다.
- **핵심 직관**: 스택은 바닥이 막힌 프링글스 통(나중에 넣은 게 먼저 나옴), 큐는 한 줄 매표소(먼저 온 사람이 먼저 나감), 덱은 양쪽이 다 뚫린 파이프(양쪽에서 넣고 뺄 수 있음)다.

## 핵심 용어 정리
| 용어 | 의미 | 비유 |
|:---|:---|:---|
| 추상 자료형(ADT) | 내부 구현을 감추고 "무엇을 할 수 있는가"(연산 규칙)만 정의한 자료형 | 자판기 버튼(내부 기계 구조는 몰라도 규칙대로 동작) |
| 선형 자료구조 | 원소가 한 줄로 나열되는 자료구조 | 한 줄로 선 사람들 |
| 스택(Stack) | 후입선출(LIFO)만 허용 — Push/Pop 연산만 지원 | 프링글스 통 |
| LIFO | Last In First Out, 나중에 넣은 것이 먼저 나옴 | 접시 쌓기 |
| Push / Pop | 스택의 삽입 / 삭제 연산, 항상 Top에서만 발생 | 통에 넣기 / 통에서 꺼내기 |
| Top | 스택에서 가장 최근에 넣은 원소의 위치 | 쌓인 접시 맨 위 |
| 큐(Queue) | 선입선출(FIFO)만 허용 — Enqueue/Dequeue 연산만 지원 | 매표소 줄 |
| FIFO | First In First Out, 먼저 넣은 것이 먼저 나옴 | 줄 서기 |
| Enqueue / Dequeue | 큐의 삽입(Rear) / 삭제(Front) 연산 | 줄 뒤에 서기 / 맨 앞에서 나가기 |
| Front / Rear | 큐의 출구(맨 앞) / 입구(맨 뒤) | 줄의 맨 앞 / 맨 뒤 |
| 덱(Deque) | 양쪽 끝 모두에서 삽입·삭제 가능한 큐 | 양쪽이 뚫린 파이프 |
| 환형 큐(Circular Queue) | 배열의 끝과 시작을 나머지 연산(%)으로 연결해 공간을 재사용하는 큐 | 원형 트랙을 도는 계주 |
| 오버플로우 / 언더플로우 | 꽉 찬 자료구조에 삽입 / 빈 자료구조에서 삭제를 시도하는 오류 상태 | 꽉 찬 통에 더 넣기 / 빈 통에서 꺼내기 |
| 우선순위 큐(Priority Queue) | FIFO를 깨고 우선순위가 높은 원소부터 꺼내는 큐, 보통 힙(Heap)으로 구현 | 응급실 중증도 순 진료 |

## 깊이 이해

### 왜 "제약"이 기능이 되는가
배열이나 연결 리스트는 원한다면 어느 위치든 접근할 수 있지만, 스택과 큐는 이 자유를 의도적으로 없앤다. 함수 호출을 예로 들면, A가 B를 부르고 B가 C를 부른 뒤 C가 끝나면 반드시 B로, B가 끝나면 반드시 A로 돌아가야 한다 — 이 "마지막에 부른 것부터 되돌아간다"는 순서는 임의 접근이 가능한 자료구조로 짜면 매번 "지금 누구 차례인가"를 따로 추적해야 하지만, 스택 하나면 Push/Pop만으로 자동 보장된다. 제약이 곧 정확성을 공짜로 준다.

### 배열로 큐를 만들 때 생기는 함정 — 가짜 오버플로우
배열 기반 큐에서 Dequeue를 할 때마다 뒤 원소를 앞으로 당기면(Shift) O(N)이 걸리므로, 보통은 Front 포인터만 앞으로 옮긴다(O(1)). 그런데 이렇게 하면 지나간 앞쪽 칸은 비어 있는데도 재사용되지 않는다. 예를 들어 크기 5인 배열에서 5번 Enqueue 후 3번 Dequeue를 하면 실제 데이터는 2개뿐이지만 Rear 포인터는 이미 배열 끝(인덱스 5)에 도달해 있어 "배열이 꽉 찼다"고 오판하는 가짜 오버플로우(False Overflow)가 발생한다. 환형 큐는 `Rear = (Rear + 1) % N`처럼 나머지 연산으로 인덱스를 순환시켜, 비어 있는 앞쪽 칸을 다시 채울 수 있게 한다.

### 배열 기반 vs 연결 리스트 기반 구현의 트레이드오프
배열 기반은 메모리가 연속이라 CPU 캐시 적중률이 높아 실제 실행 속도가 빠르지만, 크기를 미리 정해야 해서 트래픽이 예상을 넘으면 오버플로우가 난다(또는 재할당·복사 비용 발생). 연결 리스트(006) 기반은 힙 메모리가 허용하는 한 계속 늘어나지만, 노드마다 포인터 저장 공간이 추가로 들고 메모리가 흩어져 있어 캐시 미스가 잦다. 예를 들어 임베디드 실시간 시스템(RTOS)은 메모리 예측 가능성이 생명이라 고정 크기 환형 큐를 쓰고, 트래픽 규모를 예측하기 어려운 웹 서버의 메시지 큐는 동적 확장이 가능한 연결 리스트형(또는 동적 배열)을 쓴다.

### 파생 구조 — 우선순위 큐와 락 프리 큐
FIFO 원칙을 그대로 두면 "먼저 온 순서"만 반영할 수 있는데, 실무에서는 "더 급한 것부터" 처리해야 하는 경우가 많다. 우선순위 큐는 내부적으로 힙(Heap) 자료구조를 써서 삽입·삭제를 O(log N)에 처리하면서도 항상 최우선 원소를 꺼낼 수 있게 한다 — OS 프로세스 스케줄링, 다익스트라 최단 경로(011)의 "가장 가까운 노드부터 확정"이 이 구조를 쓴다. 한편 다중 스레드 환경에서는 Push/Pop마다 락(Lock)을 걸면 스레드가 대기하며 성능이 떨어지므로, CAS(Compare-And-Swap) 같은 원자적 명령어로 락 없이 동시성을 처리하는 락 프리 큐가 고빈도 거래 시스템 등에 쓰인다.

### 흔한 오해와 리스크
재귀 함수는 내부적으로 스택(콜 스택)을 쓰므로, 재귀 깊이가 깊어지면 스택이 가득 차 StackOverflow가 난다 — 예를 들어 100만 번 재귀 호출하는 코드는 대부분의 언어에서 기본 스택 크기(보통 1~8MB)를 초과해 크래시한다. 이때는 재귀를 반복문과 명시적 스택으로 바꾸거나 꼬리 재귀 최적화를 활용한다. 큐 쪽에서는 소비자보다 생산자가 빠르면 큐가 무한정 쌓여 메모리를 고갈시키므로, 백프레셔(Backpressure)로 생산 속도를 제한하거나 처리 못한 메시지를 Dead Letter Queue로 격리한다.

## 연결 개념
- 006 연결 리스트 — 스택·큐·덱을 구현하는 기본 재료 중 하나(배열과 양자택일)
- 010 그래프 탐색 — DFS는 스택(또는 재귀), BFS는 큐를 엔진으로 사용
- 011 최단 경로 — 우선순위 큐(힙) 기반 다익스트라의 기반 자료구조

# 📝 【답안용】 시험 답안 템플릿

> 목적: 시험장에서 25분에 그대로 쓰는 답안 양식. 작성방식(추상표현 금지·수치·도식·문제유형 전환)을 엄격히 지킨다.
> 핵심: 이 시험은 정보를 많이 나열하는 시험이 아니라, 문제 신호어에서 출제자 의도를 읽고 핵심 논점을 선별해 쓰는 시험이다.

## 핵심 인사이트 (3줄 요약)

> 1. **본질**: 요소의 삽입(Push/Enqueue)과 삭제(Pop/Dequeue) 위치를 제한하여 데이터의 수명 주기와 처리 순서를 정책적으로 강제하는 추상 자료형(ADT)이다.
> 2. **가치**: 스택의 LIFO는 시스템 상태 복원에, 큐의 FIFO는 비동기 트래픽의 버퍼링 및 순차 처리에 적용되어 시스템 신뢰성을 보장한다.
> 3. **판단 포인트**: 트래픽 폭증 시 큐의 Overflow 한계를 방어하기 위해 배열 기반의 환형 큐(Circular Queue)나 동적 확장이 가능한 연결 리스트 큐를 시스템 제약에 맞춰 선택해야 한다.

## 출제 의도 및 답안 포인트

| 출제 의도 | 반드시 짚을 핵심 | 감점 회피 포인트 |
|:---|:---|:---|
| 제약적 선형 자료구조의 목적 이해 | LIFO(Stack), FIFO(Queue) 통제 정책, ADT 개념 | "데이터를 저장한다"는 일반적 자료구조 서술로 논점 이탈 |
| 컴퓨터 시스템 적용 사례 도출 역량 | DFS/함수호출(Stack), BFS/메시지브로커(Queue) 연결 | 3가지 구조의 차이점만 나열하고 실무 활용 누락 |

> 요약: 스택과 큐는 알고리즘 기초를 넘어, 프로세스 스케줄링부터 대규모 분산 메시징(Kafka)까지 운영체제와 분산 시스템의 코어 엔진이다.

## Ⅰ. 개요 및 필요성

- 정의: 데이터에 대한 접근, 삽입, 삭제가 특정 양 끝단에서만 이루어지도록 입출력 규칙을 제한한 선형 추상 자료형
- 배경: 자유로운 배열 접근은 함수 호출 스택 복원이나 작업 대기열 처리 시 데이터 무결성을 파괴하므로 제약 필요
- 필요성: 시스템 부하 시 비동기 요청을 유실 없이 O(1)에 버퍼링하고(Queue), 서브루틴의 상태를 정확히 복귀(Stack)시키기 위해 필수

## Ⅱ. 구조 및 구성요소

```text
스택 (Stack, LIFO)       큐 (Queue, FIFO)              덱 (Deque)
|  Push  |  Pop  ^      | Enqueue |       Dequeue ^    | Push/Pop |      | Push/Pop |
|   V    |       |      |   V     |          |         |   V  ^   |      |   V  ^   |
|------ Top ------|     |-- Rear --- Front -------|    |- Front -------- Rear -|
```

| 구조명 | 제한 정책 | 주요 포인터 (인덱스) | 특이사항 |
|:---|:---|:---|:---|
| 스택 | LIFO (후입선출) | Top (최상단 데이터 위치) | 재귀(Recursion), 상태 복원 기반 |
| 큐 | FIFO (선입선출) | Front (출구), Rear (입구) | 생산자-소비자 패턴 버퍼링 핵심 |
| 덱 | 양방향 입출력 허용 | Front, Rear 양쪽 모두 갱신 | 스택과 큐의 성질을 런타임에 동시 지원 |

> 요약: 이들은 물리적 구조(배열/리스트)와 독립된 '추상적 규칙(정책)'이며, 시스템은 이 규칙에 의존해 논리를 전개한다.

---

## Ⅲ. 동작원리 및 큐 한계 극복 흐름도

```text
선형 큐 동작 -> Front 위치 이동 -> 앞쪽 빈 공간 버려짐(가짜 Overflow) -> 환형 큐(Circular) 전환 적용
```

| 단계 | 처리 내용 | 검증 기준 |
|:---:|:---|:---|
| 1 | 삽입 (Enqueue) | Rear = (Rear + 1) % N 연산을 통해 공간 할당 후 데이터 삽입 |
| 2 | 삭제 (Dequeue) | Front = (Front + 1) % N 연산으로 가장 오래된 데이터 삭제 |
| 3 | 포화 상태 검사 | (Rear + 1) % N == Front 일 경우 오버플로우 방지 확충 대기 |
| 4 | 비어있음 검사 | Front == Rear 일 경우 언더플로우 방지 (소비 대기) |

> 요약: 배열로 큐를 구현할 때는 메모리 낭비를 막는 환형(Circular) 큐 로직이 필수이며, 나머지 연산(%)을 통해 O(1) 이동을 보장한다.

## Ⅳ. 심화 적용 시 트레이드오프 비교

| 비교 축 | 배열 기반 구현 | 연결 리스트 기반 구현 | 선택 기준 |
|:---|:---|:---|:---|
| 메모리 제약 | 크기 고정 (Overflow 위험 내재) | 힙 메모리 고갈 전까지 동적 확장 | 트래픽의 최대치 예측 가능 여부 |
| 캐시 효율성 | 연속 메모리 할당으로 캐시 적중 우수 | 노드 파편화로 적중률 극히 저하 | CPU 캐시 민감도 vs 동적 크기 |
| 구현 복잡도 | 환형 로직 등 인덱스 갱신 주의 | 추가 노드 메모리 동적 할당 오버헤드 | 빠른 메모리 해제가 요구되는 환경 |

> 요약: RTOS 임베디드에서는 고정 배열 환형 큐를, 웹 시스템은 메모리 한계까지 버티는 리스트 큐를 표준으로 적용한다.

## Ⅴ. 파생 자료구조 및 심화 비교

| 파생 구조 | 파생 원리 | 해결 리스크 | 실무 적용처 |
|:---|:---|:---|:---|
| 우선순위 큐 | FIFO 파괴, 우선순위 기반 Heap 정렬 | 높은 중요도의 작업 지연 방지 | OS 프로세스 스케줄링, 다익스트라 |
| 차단 큐(Blocking Q) | 포화 시 대기, 고갈 시 읽기 스레드 Sleep | 멀티 스레드 간 데이터 레이스 방지 | Thread Pool 작업 분배, MSA 이벤트 |
| 락 프리 큐 | 원자적 CAS 명령어 통제 | 락 점유 컨텍스트 스위칭 지연 제거 | 고성능 금융 거래 엔진 (Disruptor) |

> 요약: 기본 큐의 단일 스레드 구조를 다중 환경으로 확장하기 위해 락킹(Locking) 전략과 정렬을 결합한 파생 아키텍처가 실무에 활용된다.

| 리스크 | 원인 | 대응 방안 | 확인 지표 |
|:---|:---|:---|:---|
| 재귀 깊이 초과로 인한 StackOverflow | 재귀 호출 프레임이 콜 스택 한계를 초과 | 꼬리 재귀 최적화 또는 반복문·명시적 스택으로 전환 | 재귀 호출 최대 깊이 |
| 큐 포화 시 요청 유실 | 소비자 처리 속도보다 생산자 유입 속도가 빠름 | Backpressure 적용, 동적 스케일아웃, Dead Letter Queue 처리 | 큐 대기 길이, Consumer Lag |
| 우선순위 큐의 기아(Starvation) | 높은 우선순위 작업이 지속 유입되어 낮은 우선순위 작업이 무한 대기 | Aging 기법으로 대기 시간에 따라 우선순위 점진 상향 | 작업별 최대 대기 시간 |

> 요약: 스택/큐 도입 리스크는 자원 초과(스택 오버플로우·큐 포화)와 우선순위 불균형(기아)에서 발생하므로 반복 전환·백프레셔·에이징으로 통제한다.

## Ⅵ. 실무 적용 및 결론

**적용 방안 3개:**
1. 대규모 MSA 비동기 메시징 (Queue): Kafka, RabbitMQ 등 브로커를 도입하여 마이크로서비스 간 트래픽 스파이크를 큐에 버퍼링시켜 안정성 보장
2. 가상머신 생명주기 제어 (Stack): JVM 메모리의 Stack Area를 통해 메서드 호출 프레임, 로컬 변수 생명주기 관리 및 StackOverflow 제어
3. 스케줄링 큐 최적화 (Deque): Work-Stealing 알고리즘 구현 시 자신의 덱 한쪽 끝(LIFO)에서 작업을 빼고, 유휴 스레드는 반대쪽(FIFO)에서 가져와 경합 방지

**결론 (2줄):**
- 기술사 판단: 스택과 큐는 시스템 아키텍처에서 비동기적 트래픽을 완충하고 호출 상태 무결성을 통제하는 기본 메커니즘이다.
- 향후 방향: 단일 노드의 자료구조 한계를 넘어 서버 간 상태 일관성을 맞추는 분산 큐(Distributed Queue) 아키텍처로 진화 중이다.
