# 📖 【암기용】 개념 완전 이해

> 목적: 이 개념을 처음 보는 사람도 완벽히 이해하게 만든다. 시험 답안 양식이 아니라, 이해를 위한 친절한 설명이다.

## 한눈에
- **개요**: 데이터가 삽입/삭제되는 규칙(순서)을 제한하여 시스템의 작업 흐름을 통제하는 선형 자료구조들
- **왜 필요한가**: 데이터 뭉치를 규칙 없이 다루면 시스템 상태를 추적할 수 없다. "가장 최근 작업(Stack)", "가장 먼저 온 작업(Queue)"처럼 일관된 정책을 강제하여 시스템 논리적 오류를 막는다.
- **핵심 직관**: 스택(LIFO)은 프링글스 통. 큐(FIFO)는 매표소 대기줄. 덱(Deque)은 양쪽이 다 뚫린 파이프.

## 깊이 이해
- **배경·문제의식**: 함수 호출 내역을 저장하거나 웹 서버 요청을 대기시킬 때, 일반 배열이나 리스트를 쓰면 어느 위치에 데이터를 넣고 뺄지 제멋대로 되어 버그와 병목이 폭증한다. 입출구 단일화가 필요했다.
- **작동 원리**:
  - **스택 (Stack)**: 나중에 들어간 것이 먼저 나온다 (LIFO). Push와 Pop 연산만 지원.
  - **큐 (Queue)**: 먼저 들어간 것이 먼저 나온다 (FIFO). Enqueue(뒤 삽입)와 Dequeue(앞 삭제)만 지원.
  - **덱 (Deque)**: 앞/뒤 양쪽에서 삽입과 삭제가 모두 가능하다.
- **비유**: 
  - 스택: 웹 브라우저 "뒤로 가기" (방금 본 페이지부터 꺼냄)
  - 큐: 식당의 "번호표 시스템" (먼저 온 손님부터 입장)
  - 덱: 양쪽으로 타고 내릴 수 있는 기차 (유연한 대기열 처리)
- **흔한 오해·주의점**: "큐를 단순 배열로 짜면 된다"고 생각하지만, 앞쪽에서 원소를 빼면 뒤에 있는 데이터를 한 칸씩 당겨야 해서 O(N) 병목을 맞는다. 반드시 환형 큐(Circular Queue)나 연결 리스트로 짜서 O(1)을 보장해야 한다.

## 연결 개념
- 연결 리스트 (이 자료구조들을 구현하는 기본 재료)
- 스레드 동기화 (Blocking Queue)
- 탐색 알고리즘 (DFS - Stack, BFS - Queue)

# 📝 【답안용】 시험 답안 템플릿

> 목적: 시험장에서 25분에 그대로 쓰는 답안 양식. 작성방식(추상표현 금지·수치·도식·문제유형 전환)을 엄격히 지킨다.
> 핵심: 이 시험은 정보를 많이 나열하는 시험이 아니라, 문제 신호어에서 출제자 의도를 읽고 핵심 논점을 선별해 쓰는 시험이다.

## 핵심 인사이트 (3줄 요약)

> 1. **본질**: 요소의 삽입(Push/Enqueue)과 삭제(Pop/Dequeue) 위치를 제한하여 데이터의 수명 주기와 처리 순서를 정책적으로 강제하는 추상 자료형(ADT)이다.
> 2. **가치**: 스택의 LIFO는 시스템 상태 복원에, 큐의 FIFO는 비동기 트래픽의 버퍼링 및 순차 처리에 적용되어 시스템 신뢰성을 보장한다.
> 3. **판단 포인트**: 트래픽 폭증 시 큐의 Overflow 한계를 방어하기 위해 배열 기반의 환형 큐(Circular Queue)나 동적 확장이 가능한 연결 리스트 큐를 시스템 제약에 맞춰 선택해야 한다.

## 출제 의도 및 답안 포인트

| 출제 의도 | 반드시 짚을 핵심 | 감점 회피 포인트 |
|:---|:---|:---|
| 제약적 선형 자료구조의 목적 이해 | LIFO(Stack), FIFO(Queue) 통제 정책, ADT 개념 | "데이터를 저장한다"는 일반적 자료구조 서술로 논점 이탈 |
| 컴퓨터 시스템 적용 사례 도출 역량 | DFS/함수호출(Stack), BFS/메시지브로커(Queue) 연결 | 3가지 구조의 차이점만 나열하고 실무 활용 누락 |

> 요약: 스택과 큐는 알고리즘 기초를 넘어, 프로세스 스케줄링부터 대규모 분산 메시징(Kafka)까지 운영체제와 분산 시스템의 코어 엔진이다.

## Ⅰ. 개요 및 필요성

- 정의: 데이터에 대한 접근, 삽입, 삭제가 특정 양 끝단에서만 이루어지도록 입출력 규칙을 제한한 선형 추상 자료형
- 배경: 자유로운 배열 접근은 함수 호출 스택 복원이나 작업 대기열 처리 시 데이터 무결성을 파괴하므로 제약 필요
- 필요성: 시스템 부하 시 비동기 요청을 유실 없이 O(1)에 버퍼링하고(Queue), 서브루틴의 상태를 정확히 복귀(Stack)시키기 위해 필수

---

## Ⅱ. 구조 및 구성요소

```text
스택 (Stack, LIFO)       큐 (Queue, FIFO)              덱 (Deque)
|  Push  |  Pop  ^      | Enqueue |       Dequeue ^    | Push/Pop |      | Push/Pop |
|   V    |       |      |   V     |          |         |   V  ^   |      |   V  ^   |
|------ Top ------|     |-- Rear --- Front -------|    |- Front -------- Rear -|
```

| 구조명 | 제한 정책 | 주요 포인터 (인덱스) | 특이사항 |
|:---|:---|:---|:---|
| 스택 | LIFO (후입선출) | Top (최상단 데이터 위치) | 재귀(Recursion), 상태 복원 기반 |
| 큐 | FIFO (선입선출) | Front (출구), Rear (입구) | 생산자-소비자 패턴 버퍼링 핵심 |
| 덱 | 양방향 입출력 허용 | Front, Rear 양쪽 모두 갱신 | 스택과 큐의 성질을 런타임에 동시 지원 |

> 요약: 이들은 물리적 구조(배열/리스트)와 독립된 '추상적 규칙(정책)'이며, 시스템은 이 규칙에 의존해 논리를 전개한다.

---

## Ⅲ. 동작원리 및 큐 한계 극복 흐름도

```text
선형 큐 동작 -> Front 위치 이동 -> 앞쪽 빈 공간 버려짐(가짜 Overflow) -> 환형 큐(Circular) 전환 적용
```

| 단계 | 처리 내용 | 검증 기준 |
|:---:|:---|:---|
| 1 | 삽입 (Enqueue) | Rear = (Rear + 1) % N 연산을 통해 공간 할당 후 데이터 삽입 |
| 2 | 삭제 (Dequeue) | Front = (Front + 1) % N 연산으로 가장 오래된 데이터 삭제 |
| 3 | 포화 상태 검사 | (Rear + 1) % N == Front 일 경우 오버플로우 방지 확충 대기 |
| 4 | 비어있음 검사 | Front == Rear 일 경우 언더플로우 방지 (소비 대기) |

> 요약: 배열로 큐를 구현할 때는 메모리 낭비를 막는 환형(Circular) 큐 로직이 필수이며, 나머지 연산(%)을 통해 O(1) 이동을 보장한다.

## Ⅳ. 심화 적용 시 트레이드오프 비교

| 비교 축 | 배열 기반 구현 | 연결 리스트 기반 구현 | 선택 기준 |
|:---|:---|:---|:---|
| 메모리 제약 | 크기 고정 (Overflow 위험 내재) | 힙 메모리 고갈 전까지 동적 확장 | 트래픽의 최대치 예측 가능 여부 |
| 캐시 효율성 | 연속 메모리 할당으로 캐시 적중 우수 | 노드 파편화로 적중률 극히 저하 | CPU 캐시 민감도 vs 동적 크기 |
| 구현 복잡도 | 환형 로직 등 인덱스 갱신 주의 | 추가 노드 메모리 동적 할당 오버헤드 | 빠른 메모리 해제가 요구되는 환경 |

> 요약: RTOS 임베디드에서는 고정 배열 환형 큐를, 웹 시스템은 메모리 한계까지 버티는 리스트 큐를 표준으로 적용한다.

## Ⅴ. 파생 자료구조 및 심화 비교

| 파생 구조 | 파생 원리 | 해결 리스크 | 실무 적용처 |
|:---|:---|:---|:---|
| 우선순위 큐 | FIFO 파괴, 우선순위 기반 Heap 정렬 | 높은 중요도의 작업 지연 방지 | OS 프로세스 스케줄링, 다익스트라 |
| 차단 큐(Blocking Q) | 포화 시 대기, 고갈 시 읽기 스레드 Sleep | 멀티 스레드 간 데이터 레이스 방지 | Thread Pool 작업 분배, MSA 이벤트 |
| 락 프리 큐 | 원자적 CAS 명령어 통제 | 락 점유 컨텍스트 스위칭 지연 제거 | 고성능 금융 거래 엔진 (Disruptor) |

> 요약: 기본 큐의 단일 스레드 구조를 다중 환경으로 확장하기 위해 락킹(Locking) 전략과 정렬을 결합한 파생 아키텍처가 실무에 활용된다.

## Ⅵ. 실무 적용 및 결론

**적용 방안 3개:**
1. 대규모 MSA 비동기 메시징 (Queue): Kafka, RabbitMQ 등 브로커를 도입하여 마이크로서비스 간 트래픽 스파이크를 큐에 버퍼링시켜 안정성 보장
2. 가상머신 생명주기 제어 (Stack): JVM 메모리의 Stack Area를 통해 메서드 호출 프레임, 로컬 변수 생명주기 관리 및 StackOverflow 제어
3. 스케줄링 큐 최적화 (Deque): Work-Stealing 알고리즘 구현 시 자신의 덱 한쪽 끝(LIFO)에서 작업을 빼고, 유휴 스레드는 반대쪽(FIFO)에서 가져와 경합 방지

**결론 (2줄):**
- 기술사 판단: 스택과 큐는 시스템 아키텍처에서 비동기적 트래픽을 완충하고 호출 상태 무결성을 통제하는 기본 메커니즘이다.
- 향후 방향: 단일 노드의 자료구조 한계를 넘어 서버 간 상태 일관성을 맞추는 분산 큐(Distributed Queue) 아키텍처로 진화 중이다.
