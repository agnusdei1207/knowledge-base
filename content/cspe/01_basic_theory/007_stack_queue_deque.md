## Ⅰ. 개요
- **정의**: 삽입·삭제 순서를 LIFO·FIFO·양방향 중 하나로 강제하는 선형 자료구조 정책임.
- **배경/필요성**: 함수 호출 복귀는 마지막에 호출된 함수부터 되돌아가야 하는 LIFO 문제이고, 인쇄·작업 대기열은 먼저 요청한 것부터 처리해야 하는 FIFO 문제이므로, 각 정책에 맞는 전용 자료구조가 필요함.
- **출제 의도**: 문제 상황이 요구하는 처리 순서 정책(LIFO/FIFO/양방향)을 식별하고, 배열·연결 리스트 구현 방식별 트레이드오프를 판단하는 역량을 확인함.
- **답안 방향**: 정책 정의(Ⅱ) -> 구현·연산 원리(Ⅲ) -> 성능·적용 트레이드오프(Ⅳ·Ⅴ) -> 실무 리스크 대응(Ⅵ) 순으로 전개함.

| 출제 의도 | 반드시 짚을 핵심 | 감점 회피 포인트 |
|:---|:---|:---|
| 정책 식별 능력 | LIFO(스택)·FIFO(큐)·양방향(덱) 구분, 원형 큐의 배열 재사용 | 정책 언급 없이 자료구조 이름만 나열 |
| 구현·성능 트레이드오프 | 배열 기반 큐는 원형 인덱싱 조건에서만 `O(1)`, 연결 리스트 기반은 포인터 조작으로 `O(1)` | 조건 없이 전 연산 `O(1)` 단정 |
| 실무 적용·장애 대응 | DFS=스택/BFS=큐 선택 기준, 메시지 큐 백프레셔 | 큐 크기 무제한 설계, DFS·BFS 혼동 |

> 요약: 이 문제는 처리 순서 정책 식별과 구현별 성능 조건 판단 능력을 함께 확인함.

## Ⅱ. 구조 및 구성요소
```text
push(A) -> [A]          enqueue(A) -> [A]         pushFront(A) -> [A]
push(B) -> [B,A]        enqueue(B) -> [A,B]       pushBack(B)  -> [A,B]
pop()   -> B 반환       dequeue()  -> A 반환      popFront()/popBack() 중 선택
(top 한쪽만 사용)       (front 삭제/rear 삽입)    (양쪽 모두 삽입·삭제 가능)
```

| 구성요소 | 역할 | 산출물/비유 |
|:---|:---|:---|
| LIFO 정책(스택) | top 한 지점에서만 push·pop 수행 | 접시 쌓기 — 맨 위 접시부터 사용 |
| FIFO 정책(큐) | rear에서 enqueue, front에서 dequeue | 매표소 줄 — 먼저 온 사람이 먼저 입장 |
| 양방향 정책(덱) | 양쪽 끝 모두에서 삽입·삭제 허용 | 양쪽에 문이 있는 기차 칸 |
| 원형 큐(Circular Queue) | 배열 인덱스를 끝에서 0으로 회전시켜 빈 공간 재사용 | 회전초밥 벨트 |
| top / front·rear 포인터 | 각 정책이 조작을 허용하는 위치를 가리키는 상태값 | 정책 위반 여부를 `O(1)`에 판정하는 기준점 |

> 요약: 세 구조는 배열·연결 리스트(006 참조) 위에 얹는 정책 차이일 뿐이며, 노드·포인터 자체 구조는 006과 동일함.

## Ⅲ. 동작원리 및 흐름도
```text
입력 토큰 -> 정책 판정(LIFO/FIFO/양방향) -> push·pop 또는 enqueue·dequeue 실행 -> 결과 상태 확인
```

- 1단계: 처리 대상이 요구하는 정책을 판정함 — 괄호 검사·함수 복귀는 LIFO, 작업 대기열은 FIFO.
- 2단계: 판정된 정책에 따라 스택은 push/pop, 큐는 enqueue/dequeue, 덱은 양쪽 끝 연산을 수행함.
- 3단계: 연산 결과로 남은 원소 상태를 검증함 — 예를 들어 후위 표기법 `3 4 + 2 *` 계산 시 피연산자는 push하고 연산자를 만나면 두 값을 pop해 계산 후 다시 push하여 최종 `14`가 남는지 확인함.
- 4단계: 스택이 완전히 비었는지(괄호 검사), 큐가 도착 순서대로 소진됐는지(작업 처리) 등 정책 위반 여부를 최종 출력함.

> 요약: 정책 판정 -> 연산 실행 -> 상태 검증 -> 출력 확인의 순서로 동작하며, 각 단계는 판정된 정책에 종속됨.

## Ⅳ. 특징
- 핵심 연산(push/pop, enqueue/dequeue, pushFront/Back·popFront/Back)은 배열·연결 리스트 구현 모두에서 `O(1)`이 기본이나, 배열 기반 큐는 원형 인덱싱이 없으면 앞쪽 빈 공간을 재사용하지 못해 실질 성능이 저하됨.
- 덱은 popFront만 쓰면 스택처럼, popFront와 pushBack만 쓰면 큐처럼 동작을 재현할 수 있는 일반화 구조임.
- 우선순위 큐는 FIFO를 포기하는 대신 힙 기반 `O(log N)` 정렬 유지 비용을 지불하는 확장형이며, 도착 순서가 아닌 우선순위 값으로 추출함.
- 슬라이딩 윈도우 최댓값처럼 양쪽 끝을 모두 조작해야 하는 문제는 단조 감소 덱을 쓰면 각 원소가 push·pop에 최대 한 번씩만 관여해 전체 `O(N)`에 처리됨(구간마다 전수 비교하면 `O(NK)`).

> 요약: 세 구조 모두 핵심 연산은 상수 시간이 기본값이나, 배열 구현·확장형(우선순위 큐)에서는 조건부로 성능이 달라짐.

## Ⅴ. 심화 비교 및 적용 판단

| 적용 신호 | 스택(LIFO) | 큐(FIFO) | 선택 기준 |
|:---|:---|:---|:---|
| 처리 순서 요구 | 가장 최근 것부터 되돌림(콜 스택, Undo/Redo) | 도착 순서 보존(스케줄링, 메시지 처리) | 문제가 "최근 것"과 "먼저 온 것" 중 무엇을 요구하는지로 결정 |
| 그래프 탐색 | DFS(깊이 우선) | BFS(너비 우선) | 최단 경로가 필요하면 BFS, 경로 존재 여부만 확인하면 DFS로 충분 |
| 서비스 간 결합도 | 명시적 활용 제한적 | 메시지 큐로 생산자·소비자 시간 분리 | 한쪽 장애·처리량 급증이 다른 쪽에 즉시 전파되면 안 될 때 큐 도입 |

> 요약: 스택은 역순 복귀, 큐는 순서 보존과 시간 분리에 적용 신호가 있으며, 덱은 두 정책을 양쪽 끝에서 선택적으로 결합함.

**리스크·대응 (불릿):**
- 큐 크기 무제한 설정: 생산자가 소비자보다 빠른 상황에서 메모리 고갈 위험 → 최대 큐 길이·Back Pressure 적용으로 대응.
- DFS·BFS 오선택: 스택으로 최단 경로 문제를 처리하면 탐색 순서 오류 발생 → 문제가 요구하는 정책을 재확인 후 자료구조 교체.
- 슬라이딩 윈도우 전수 비교: 구간마다 전체 재비교 시 `O(NK)` → 단조 감소 덱으로 `O(N)` 처리.

**도입 후 점검 지표 (불릿):**
- 큐 적재량: 평균/최대 큐 길이 대비 소비 처리량 — 길이가 지속 증가하면 소비자 처리 능력 부족 신호.
- 스택 깊이: 재귀·콜 스택 깊이 상한 대비 실제 사용량 — 상한 근접 시 스택 오버플로우 위험 신호.

## Ⅵ. 실무 적용 및 결론
1. 단기: 처리 대상 데이터가 LIFO·FIFO·양방향 중 무엇을 요구하는지 문제 신호어로 판정함.
2. 중기: 배열 기반은 원형 인덱싱, 연결 리스트 기반은 포인터 조작으로 구현체를 선정하고, 큐에는 Back Pressure 설계를 반영함.
3. 장기: 분산 메시지 큐(예: Kafka)로 서비스 간 시간적 분리를 적용해 장애 전파 차단과 처리량 완충 체계를 구축함.

- 기술사적 판단: 세 구조의 차이는 구현 방식이 아니라 "어떤 순서로 꺼낼 것인가"라는 정책 선택이며, 배열·연결 리스트는 그 정책을 얹는 부차적 기반 구현체임.
- 기술사 제언: 정책 선택 오류(DFS·BFS 혼동, 무제한 큐)는 성능이 아닌 정확성·안정성 문제로 직결되므로, 설계 초기 단계에서 정책 판정을 명시적으로 문서화할 것을 제언함.
