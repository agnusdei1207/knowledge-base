# 📖 【암기용】 개념 완전 이해

## 한눈에
- **개요**: 데이터가 들어오고 나가는 '순서 규칙(입출구 방향)'을 제한하여, 특정 용도에 맞게 데이터를 관리하는 추상 자료형(ADT)이다.
- **왜 필요한가**: 모든 데이터를 자유롭게 넣고 빼면 관리(히스토리, 작업 대기열 등)가 꼬인다. "나중에 온 사람 먼저 처리" 또는 "먼저 온 사람 먼저 처리"라는 강제 규칙이 시스템 흐름 제어에 필수적이다.
- **핵심 직관**: 
  - 스택(Stack): 프링글스 감자칩 캔 (밑이 막힌 원통)
  - 큐(Queue): 놀이공원 매표소 줄 (양쪽이 뚫린 파이프)
  - 덱(Deque): 양방향 톨게이트 (양쪽 다 입/출력 가능)

## 핵심 용어 정리

| 용어/표기 | 의미 | 비유·예 |
|:---|:---|:---|
| 스택 (Stack) / LIFO | Last In, First Out (후입선출). 마지막에 들어간 게 제일 먼저 나옴 | 브라우저 '뒤로가기', 문서 작업 '실행 취소(Ctrl+Z)' |
| 큐 (Queue) / FIFO | First In, First Out (선입선출). 먼저 들어간 게 제일 먼저 나옴 | 맛집 웨이팅 줄, 식당 주문 순서, 프린터 대기열 |
| 덱 (Deque) | Double-Ended Queue. 양쪽 끝 어디서든 입출력이 모두 가능 | 스택과 큐의 장점을 합친 하이브리드 줄서기 |
| Push / Pop | 스택에서 데이터를 밀어 넣고(Push), 뽑아내는(Pop) 핵심 연산 | 프링글스 칩을 넣고 빼기 |
| Enqueue / Dequeue | 큐에서 데이터를 대기열에 넣고(Enq), 차례가 되어 빼는(Deq) 연산 | 줄 서기(Enq), 표 받고 나가기(Deq) |

## 깊이 이해
- **배경·문제의식**: 함수 호출이 중첩될 때(A가 B를 부르고 B가 C를 부름) 컴퓨터는 끝난 뒤 원래 자리로 어떻게 돌아갈지 기억해야 했다(스택 필요). 반대로 요청이 서버에 쏟아질 때 공평하게 순서대로 처리할 대기실이 필요했다(큐 필요).
- **작동 원리 (내부 구현)**:
  - 이들은 본질적으로 배열(Array)이나 연결 리스트(Linked List)를 이용해 구현한다.
  - 단지 **코드 수준에서 "맨 끝에서만 넣고 빼라(스택)", "앞에서 빼고 뒤에서 넣어라(큐)"라고 엄격하게 메서드(인터페이스)를 제한**해 둔 껍데기일 뿐이다.
- **비유를 통한 작동 차이**:
  - 스택: 접시 씻기. 다 먹은 접시를 위로 계속 쌓고, 씻을 때는 제일 위에 있는 접시부터 집어서 씻는다. (가장 최근 작업 우선)
  - 큐: 컨베이어 벨트. 물건이 벨트에 올라간 순서대로 끝에서 떨어진다. (공평한 순서 보장)
- **흔한 오해·주의점**: 큐를 단순 배열(Array)로 구현하면, 앞에서 데이터가 나갈 때마다 뒤에 있는 데이터를 전부 앞으로 당겨야(O(N)) 해서 느려진다. 그래서 실무에서는 빙글빙글 도는 '원형 큐(Circular Queue)'나 연결 리스트를 써서 당기는 작업을 없앤다.

## 연결 개념
- 연결 리스트 (006 참조): 크기 제한 없는 스택/큐를 만들 때 쓰는 기반 구조.
- 그래프 탐색 (010 참조): DFS(깊이 우선)는 스택, BFS(너비 우선)는 큐를 사용해 구현한다.

# 📝 【답안용】 시험 답안 템플릿

## 핵심 인사이트 (3줄 요약)

> 1. **본질**: 스택, 큐, 덱은 데이터 입출력의 방향과 순서(LIFO / FIFO)를 논리적으로 강제하는 추상 자료형(Abstract Data Type)이다.
> 2. **가치**: 컨텍스트 스위칭(함수 호출 상태 저장), 비동기 메시징(이벤트 루프 대기열) 등 컴퓨터 구조와 아키텍처의 비즈니스 흐름을 제어하는 핵심 메커니즘이다.
> 3. **판단 포인트**: 목적에 따라 LIFO(이력/복귀)와 FIFO(공평한 버퍼링)를 선택하되, 런타임 메모리 고갈 방지를 위해 내부를 배열로 구현할지, 연결 리스트로 구현할지 트레이드오프를 결정해야 한다.

## 출제 의도 및 답안 포인트

| 출제 의도 | 반드시 짚을 핵심 | 감점 회피 포인트 |
|:---|:---|:---|
| LIFO / FIFO 기반 자료구조 원리 구분 | 스택(LIFO)과 큐(FIFO)의 구조적 차이점 및 입출력 메서드 | 개념적 비유만 적고 컴퓨터 구조상의 쓰임새 누락 |
| 자료구조 한계 및 변형 구조 이해 | 배열 기반 선형 큐의 이동(Shift) 오버헤드와 원형 큐(Circular Queue) 대안 | 스택·큐 종류만 단순 나열함 |
| 실무 응용 시나리오 설계 역량 | 함수 콜 스택(Stack), 메시지 큐(Kafka/RabbitMQ) 등 실무 매핑 | 단순 알고리즘(DFS/BFS) 예시에만 머무름 |

> 요약: 데이터 접근 위치를 제한하여 흐름 제어의 목적을 달성하는 원리를 짚고, 실무의 스택 메모리와 메시지 큐 아키텍처로 확장해야 한다.

## Ⅰ. 개요 및 필요성

- 개요: 스택, 큐, 덱은 내부 배열이나 연결 리스트에 대해 데이터 입출력 지점과 순서 규칙(LIFO, FIFO)을 인터페이스로 강제한 추상 자료형임
- 배경: 프로세스 실행 추적(히스토리)과 비동기 트래픽의 병목 완화(버퍼링)를 위해 무작위 접근(Random Access)을 통제할 구조적 장치 필요
- 필요성: 인터럽트 처리, 트랜잭션 롤백, 대규모 접속자 대기열 시스템 등 일관된 실행 흐름 제어와 순차적 동시성 관리를 위해 필수적임

---

## Ⅱ. 구조 및 구성요소

```text
[Stack (LIFO)]      [Queue (FIFO)]          [Deque (Hybrid)]
   | Push / Pop        Enq -> |   | -> Deq      Push/Pop <-> |   | <-> Enq/Deq
+--v--+               +---+---+---+---+         +---+---+---+---+
| Top |               |Front|   |Rear |         |Front|   |Rear |
+-----+               +---+---+---+---+         +---+---+---+---+
(한쪽 끝 입출력)      (양쪽 끝 단방향)          (양쪽 끝 양방향)
```

| 자료형 | 운영 방식 | 추상 메서드 핵심 | 특이사항 |
|:---|:---|:---|:---|
| Stack (스택) | LIFO (Last In First Out) | Push (삽입), Pop (추출) | Top 포인터 1개 단독 관리 |
| Queue (큐) | FIFO (First In First Out) | Enqueue (삽입), Dequeue (추출) | Front(출구), Rear(입구) 포인터 2개 관리 |
| Deque (덱) | LIFO + FIFO 결합 양방향 | Push_front/back, Pop_front/back | 스택, 큐의 모든 연산 지원으로 유연성 극대화 |

> 요약: 스택은 입출구가 같아 역추적에 강하고, 큐는 입출구가 분리되어 공평한 버퍼링에 강하며, 덱은 두 성질을 모두 갖춘다.

---

## Ⅲ. 동작원리 및 흐름도 (큐 기준 한계와 진화)

```text
선형 큐 동작 -> Front에서 데이터 추출(Deq) -> 앞공간 빔(가짜 포화) -> 배열 이동(O(N) 병목)
  |
  +-> [개선] 원형 큐(Circular Queue): Rear가 끝에 닿으면 Modulo 연산으로 Front 앞 배열로 회전 (배열 이동 제거)
```

- 1단계 [선형 큐의 한계]: 배열 큐에서 Dequeue 시 빈 공간을 채우기 위해 후속 데이터를 덮어쓰는 O(N) 시프트 발생 또는 빈 공간 낭비
- 2단계 [원형 큐 전환]: `(Rear + 1) % ArraySize` 연산을 통해 포인터를 배열 처음으로 순환시켜 연속 재사용 구조 구현
- 3단계 [포인터 제어]: `Front == Rear` 시 비어있음 판정, `(Rear+1) % N == Front` 시 가득참 판정으로 오버플로우 방어

> 요약: 단순 선형 구조의 시프트(Shift) 병목 한계를 포인터의 순환(Modulo)을 이용한 원형 구조로 개선하여 영구적 O(1) 성능을 확보한다.

---

## Ⅳ. 특징

- 제약 기반의 안정성 보장: 무작위 삽입/삭제를 막고 정해진 인터페이스(Top, Front/Rear)로만 접근하게 하여 데이터 흐름의 예측 가능성 확보
- 시공간 복잡도 O(1): 삽입과 추출 연산이 포인터 이동만으로 수행되므로 데이터 크기 N과 무관하게 항상 O(1) 시간 보장
- 구현체 종속적 한계: 내부를 정적 배열로 구현 시 Stack Overflow가 발생 가능하고, 동적 연결 리스트로 구현 시 포인터 오버헤드와 캐시 미스 수반

> 요약: 의도적인 접근 제약을 통해 시스템 흐름 제어의 안정성과 O(1) 속도를 얻으나, 내부 구현 방식에 따른 메모리 제약은 존재한다.

## Ⅴ. 심화 비교 및 적용 판단

| 비교 축 | Stack (LIFO) | Queue (FIFO) | 선택 기준 (아키텍처 적용) |
|:---|:---|:---|:---|
| 구조 | 수직적 단일 입출구 통제 | 수평적 입출구 분리 통제 | 처리 순서의 방향성 (역순 vs 순방향) |
| 활용 목적 | 히스토리 기억, 상태 되돌리기 | 순서 보장, 처리량 완충(Buffer) | 트랜잭션 성격 (복귀 vs 지연 처리) |
| 알고리즘 적용 | DFS (깊이 우선 탐색), 백트래킹 | BFS (너비 우선 탐색), 최단거리 | 탐색 전략 특성 |
| 시스템 적용 | JVM 메서드 스택 프레임, 실행 취소 | Kafka, RabbitMQ, OS 스케줄링 대기열 | 비동기 아키텍처 여부 |

> 요약: 상태의 복귀나 역추적이 필요하면 스택을, 생산자와 소비자의 속도 차이 완충과 공평한 처리가 필요하면 큐를 선택한다.

**리스크·대응 (기본은 불릿):**
- Stack Overflow 리스크: 재귀 호출 누적 등 비정상 Pop 지연으로 정적 스택 메모리 한계 초과 -> 꼬리 재귀 최적화 컴파일러 적용 또는 JVM `-Xss` 파라미터 튜닝 (지표: 스택 프레임 할당량)
- Queue 병목(Backpressure) 리스크: 생산 속도가 소비 속도를 초과하여 큐 버퍼링 한계 도달 (OOM) -> 메시지 TTL(Time To Live) 설정 및 Consumer 오토스케일링 연동, Dead Letter Queue(DLQ) 격리 (지표: 큐 대기열 길이)

**도입 후 점검 지표 (기본은 불릿):**
- 성능/효율: 큐(Message Queue)의 평균 체류 시간(Lead Time) — 프로듀서 인입 시간과 컨슈머 처리 시간 간극 측정
- 품질/운영: 스택/큐 삽입/삭제 시 Lock 경합에 따른 스레드 대기 시간 — 멀티스레드 환경 Lock Contention 지표

## Ⅵ. 실무 적용 및 결론

**적용 방안 3개:**
1. MSA 비동기 분리(Queue): 주문(Order)과 결제(Payment) 마이크로서비스 간에 Kafka Message Queue를 도입하여, 결제 지연 시 주문이 롤백되지 않고 순차적 재시도(Eventual Consistency) 되도록 버퍼링
2. 작업 스틸링 알고리즘(Deque): 멀티 코어 스레드풀에서 각 스레드가 자신만의 Deque를 갖고 LIFO로 작업하되, 일거리가 없는 스레드는 다른 스레드의 Deque 반대쪽에서 작업을 훔쳐오는(Work Stealing) 포크조인(Fork/Join) 프레임워크 적용
3. 트랜잭션 롤백 매니저(Stack): DB 트랜잭션 진행 중 실행된 DML 쿼리의 역순(Undo) 쿼리를 스택에 Push하고, 장애 발생 시 Pop하면서 보상 트랜잭션을 실행하여 원상 복구

**결론 (2줄):**
- 기술사 판단: 스택과 큐는 단순 자료구조를 넘어선 '아키텍처의 흐름 통제 패턴'이므로, 시스템 결합도를 낮추는 버퍼(MQ) 설계 시 FIFO의 특성을 반드시 내재화해야 함
- 향후 방향: 최근 대규모 이벤트 드리븐 아키텍처에서는 단순 FIFO 큐를 넘어, 우선순위 큐(Priority Queue)와 지연 큐(Delay Queue)로 고도화하여 SLA 차등 보장 구조로 발전 중임
