## 핵심 인사이트 (3줄 요약)

> 1. **본질**: 스택(Stack)은 **LIFO(Last In, First Out)** 정책으로 top 한쪽에서만 push·pop을 수행하고, 큐(Queue)는 **FIFO(First In, First Out)** 정책으로 rear에서 넣고 front에서 뺀다. 덱(Deque, Double-Ended Queue)은 양쪽 끝 모두에서 삽입·삭제가 가능해 스택과 큐를 함께 표현할 수 있는 일반화 구조다. 셋 다 배열·연결 리스트 위에 구현 가능한 **추상 자료형(ADT)**이며 핵심 연산은 $O(1)$이다.
> 2. **가치**: 스택은 함수 호출 복귀(콜 스택)·괄호 검사·후위 표기법 계산처럼 "가장 최근 것부터 되돌린다"는 문제에 대응하고, 큐는 BFS 탐색·프로세스 스케줄링·메시지 큐처럼 "도착 순서를 보존한다"는 문제에 대응한다. 덱은 슬라이딩 윈도우 최댓값·브라우저 히스토리처럼 양쪽 끝을 모두 조작해야 하는 문제에 쓰인다.
> 3. **융합**: 운영체제(콜 스택, 프로세스 큐), 컴파일러(후위 표기법), 네트워크(패킷 버퍼), 분산 시스템(Kafka 등 메시지 큐)까지, "어떤 순서로 꺼낼 것인가"라는 처리 정책을 자료구조로 고정하는 것이 세 구조의 공통 역할이다.

### 🔑 핵심 용어 정리

| 용어 | 정의 | 비유 |
|:---|:---|:---|
| LIFO | 마지막에 넣은 원소를 가장 먼저 꺼내는 정책 | 접시 쌓기 — 맨 위 접시부터 사용 |
| FIFO | 먼저 넣은 원소를 먼저 꺼내는 정책 | 매표소 줄 — 먼저 온 사람이 먼저 입장 |
| 스택 (Stack) | top 한쪽에서만 push·pop하는 LIFO ADT | 입구가 하나뿐인 우물 — 넣은 순서 역순으로만 꺼냄 |
| 큐 (Queue) | rear에서 enqueue, front에서 dequeue하는 FIFO ADT | 입구·출구가 다른 한쪽씩뿐인 터널 |
| 덱 (Deque) | 양쪽 끝 모두 삽입·삭제 가능한 ADT | 양쪽에 문이 있는 기차 칸 |
| 원형 큐 (Circular Queue) | 배열 끝에서 인덱스 0으로 회전해 공간을 재사용하는 큐 구현 | 회전초밥 벨트 |
| 우선순위 큐 (Priority Queue) | 도착 순서 대신 우선순위 값으로 추출 순서를 정하는 큐 | 응급실 — 중증 환자부터 |

> 요약: 스택=LIFO, 큐=FIFO, 덱=양방향이며, 원형 큐는 배열 재사용을, 우선순위 큐는 정렬 기반 추출을 위한 확장이다.

## Ⅰ. 개요 및 필요성

- **개념**: 스택은 top 하나만 열려 있어 push·pop이 같은 쪽에서 일어나는 LIFO 구조이고, 큐는 rear로 넣고 front로 빼는 FIFO 구조이며, 덱은 양쪽 끝이 모두 열려 있어 push·pop을 앞뒤 어디서든 수행하는 구조다.
- **필요성**: 함수 호출은 마지막에 호출된 함수가 먼저 반환돼야 하는 LIFO 문제이고, 인쇄 대기열은 먼저 요청한 문서가 먼저 나와야 하는 FIFO 문제다. 문제가 요구하는 정책이 무엇인지 식별하는 것이 자료구조 선택의 출발점이며, 잘못 고르면 정확성 자체가 깨진다.
- **비유**: 스택은 접시 쌓기(맨 위부터 사용)이고, 큐는 줄 서기(먼저 온 순서대로 입장)이며, 덱은 양쪽 문이 있는 기차 칸(어느 쪽으로도 타고 내림)이다.
- **구현과 006(연결 리스트)의 관계**: 세 구조 모두 특정 구현체가 아니라 배열·연결 리스트 위에 얹을 수 있는 **정책(policy)**이다. 배열 기반 큐는 원형 큐(순환 인덱스)로 공간 낭비를 피하고, 연결 리스트 기반 구현은 006에서 다룬 노드·포인터 조작으로 삽입·삭제 $O(1)$을 얻는다 — 노드·포인터 구조 자체는 006을 참고하고, 이 파일은 LIFO·FIFO·양방향이라는 정책과 그 응용에 집중한다.

```text
[스택 (LIFO)]         [큐 (FIFO)]            [덱 (양방향)]
push(A) -> [A]         enqueue(A) -> [A]       pushFront(A) -> [A]
push(B) -> [B,A]       enqueue(B) -> [A,B]     pushBack(B)  -> [A,B]
push(C) -> [C,B,A]     enqueue(C) -> [A,B,C]   pushFront(C) -> [C,A,B]

pop()   -> C 반환      dequeue()  -> A 반환    popFront() -> C 반환
남음: [B,A]            남음: [B,C]             popBack()  -> B 반환
                                               남음: [A]
```

**[다이어그램 해설]** 같은 순서(A, B, C)로 값을 넣어도 꺼내는 정책에 따라 결과가 갈린다. 스택은 pop 시 마지막에 넣은 C가 먼저 나오고(LIFO), 큐는 dequeue 시 처음 넣은 A가 먼저 나온다(FIFO). 덱은 popFront·popBack을 선택할 수 있어 스택(popFront만 사용)과 큐(popFront+pushBack만 사용) 동작을 모두 흉내 낼 수 있다 — 예를 들어 파이썬 `collections.deque`는 스택·큐 용도로 모두 쓰인다.

## Ⅱ. 아키텍처 및 핵심 원리

### 구성 요소

| 구분 | 스택 | 큐 | 덱 |
|:---|:---|:---|:---|
| 삽입 위치 | top | rear | 양쪽 끝 |
| 삭제 위치 | top | front | 양쪽 끝 |
| 주요 연산 | push, pop, peek | enqueue, dequeue, peek | pushFront/Back, popFront/Back |
| 배열 구현 시 주의점 | top 인덱스만 증감하면 됨 | 원형 큐 없이는 앞쪽 빈 공간 재사용 불가 | 원형 배열 또는 이중 연결 리스트 필요 |
| 대표 시간복잡도 | $O(1)$ | $O(1)$ (원형 큐 기준) | $O(1)$ |

> 요약: 세 구조 모두 핵심 연산은 $O(1)$이나, 배열로 큐·덱을 만들 때는 원형 인덱스 설계가 없으면 실질 성능이 무너진다.

### 핵심 원리 — 스택으로 후위 표기법(Postfix) 계산

```text
중위식: (3 + 4) * 2        후위식: 3 4 + 2 *

토큰   스택 상태(왼쪽이 top)   동작
3      [3]                     피연산자 push
4      [4,3]                   피연산자 push
+      [7]                     4, 3 pop -> 3+4=7 push
2      [2,7]                   피연산자 push
*      [14]                    2, 7 pop -> 7*2=14 push
```

**[다이어그램 해설]** 후위 표기법은 연산자를 피연산자 뒤에 두어 괄호 없이도 연산 순서를 표현한다. 피연산자는 만나는 즉시 push하고, 연산자를 만나면 스택에서 값 두 개를 pop해 연산한 뒤 결과를 다시 push한다. 마지막에 스택에 남는 값이 최종 결과다. 컴파일러가 중위식을 후위식으로 변환한 뒤 이 방식으로 계산하면, 괄호와 연산자 우선순위를 별도로 추적하지 않고 스택만으로 식을 평가할 수 있다.

## Ⅲ. 비교 및 연결

### 비교: 스택 vs 큐 — 적용 분야

| 구분 | 스택 (LIFO) | 큐 (FIFO) |
|:---|:---|:---|
| 그래프 탐색 | DFS(깊이 우선 탐색) | BFS(너비 우선 탐색) |
| 운영체제 | 함수 호출 스택(Call Stack) | 프로세스 스케줄링 큐 |
| 컴파일러 | 후위 표기법 계산, 괄호 검사 | 토큰 스트림 처리 |
| 알고리즘 패턴 | Undo/Redo(실행 취소) | 작업 대기열 |
| 분산 시스템 | 드묾(명시적 스택 활용 제한적) | Kafka, RabbitMQ 등 메시지 큐 |

> 요약: 스택은 "역순 복귀"가 필요한 문제, 큐는 "도착 순서 보존"이 필요한 문제에 대응한다.

- 덱은 이 두 정책을 양쪽 끝에서 선택적으로 결합한 구조로, 슬라이딩 윈도우 최댓값(단조 감소 덱)이나 브라우저 히스토리(뒤로/앞으로 이동)처럼 앞뒤를 모두 조작해야 하는 문제에 쓰인다.

### 우선순위 큐와의 차이

| 구분 | 일반 큐 | 우선순위 큐 |
|:---|:---|:---|
| 추출 기준 | 도착 순서(FIFO) | 우선순위 값 |
| 내부 구현 | 배열/연결 리스트 | 힙(Heap) |
| 삽입·추출 시간 | $O(1)$ | $O(\log N)$ |
| 대표 용도 | BFS, 작업 대기열 | 다익스트라 알고리즘, 프로세스 스케줄링 |

> 요약: 우선순위 큐는 FIFO를 포기하는 대신 정렬 유지 비용 $O(\log N)$을 지불한다.

### 과목 융합 관점
- 운영체제 콜 스택은 반환 주소·지역 변수를 스택 프레임으로 push하며, 재귀가 깊어지면 스택 오버플로우로 이어짐
- 라우터 패킷 버퍼는 큐로 구현되며, 버퍼 초과 시 tail drop 또는 RED(Random Early Detection)로 혼잡을 제어함
- 자바스크립트 이벤트 루프는 콜 스택(LIFO)이 비면 태스크 큐(FIFO)에서 다음 콜백을 꺼내 실행함

## Ⅳ. 실무 적용 및 기술사 판단

### 실무 시나리오

1. **시나리오 — 컴파일러 괄호·표현식 검사(스택)**
   - 여는 괄호를 만나면 push, 닫는 괄호를 만나면 pop해 종류를 대조함
   - 스택이 빈 상태에서 닫는 괄호가 나오거나, 처리 종료 후 스택이 비어있지 않으면 문법 오류로 판정함

2. **시나리오 — 마이크로서비스 간 비동기 처리(큐)**
   - 주문 서비스가 결제 서비스를 직접 호출하는 대신 메시지 큐(Kafka)에 주문 이벤트를 enqueue함
   - 결제 서비스는 자신의 처리 속도로 dequeue하여, 두 서비스가 시간적으로 분리(Temporal Decoupling)됨
   - 이 분리로 한쪽 장애가 다른 쪽으로 즉시 전파되지 않고 처리량 급증도 큐가 완충함

3. **시나리오 — 슬라이딩 윈도우 최댓값(덱)**
   - 크기 $K$ 윈도우가 배열을 이동하며 매 구간 최댓값을 구할 때, 단조 감소 덱(Monotonic Deque)을 사용함
   - 새 원소보다 작은 값은 뒤(back)에서 pop해 제거하고, 윈도우를 벗어난 인덱스는 앞(front)에서 pop함
   - 각 원소가 push·pop에 최대 한 번씩만 관여해 전체 $O(N)$에 처리됨(구간마다 전수 비교하면 $O(NK)$)

### 도입 체크리스트
- **기술적**: 데이터 처리 순서가 LIFO·FIFO·양방향 중 무엇인지 먼저 판별함
- **운영 및 보안적**: 큐 크기 제한(Back Pressure)이 설정돼 있는지 확인함 — 무제한 큐는 생산자가 소비자보다 빠를 때 메모리 고갈로 이어짐

### 안티패턴
- 큐 최대 크기를 정하지 않아 생산자가 소비자보다 빠른 상황에서 메모리를 고갈시키는 설계
- DFS와 BFS를 혼동해 스택으로 BFS를 구현하여 최단 경로 탐색 순서가 깨지는 실수

## Ⅴ. 기대효과 및 결론

### 정량/정성 기대효과

| 구분 | 부적절한 설계 | 적절한 활용 | 개선 효과 |
|:---|:---|:---|:---|
| 정량 | 동기 HTTP 호출로 피크 시 응답 지연·타임아웃 발생 | 메시지 큐로 비동기 처리, 생산자·소비자 속도 분리 | 피크 처리량 버퍼링으로 타임아웃 발생 건수 감소 |
| 정량 | 매 윈도우 전수 비교로 최댓값 탐색, 시간복잡도 $O(NK)$ | 단조 덱으로 시간복잡도 $O(N)$ 처리 | 윈도우 크기 $K$에 비례한 연산량 절감 |
| 정성 | 서비스 간 직접 호출로 장애가 즉시 전파됨 | 큐를 통한 시간적 분리로 장애 격리 | 시스템 복원력(Resilience) 확보 |

> 요약: 스택·큐·덱 적용의 효과는 속도 자체보다 "처리 순서 정책을 명시적으로 강제해 논리 오류와 장애 전파를 막는다"는 데 있다.

### 미래 전망
- 이벤트 소싱(Event Sourcing): 상태 변경을 큐의 메시지로 기록하고 재생해 상태를 복원하는 아키텍처로 금융·감사 로그 시스템에서 확산 중임
- 락 프리(Lock-Free) 큐: CAS(Compare-and-Swap) 연산으로 락 없이 enqueue·dequeue하는 동시성 큐가 고성능 메시징 시스템에서 쓰임

### 참고 자료
- Samelson, K. & Bauer, F.L.: 1955년 스택 개념(Operationskeller)을 고안하고 1957년 독일 특허(DBP 1094019, "Kellerprinzip")로 push·pop 연산을 최초로 공식화함
- Turing, A. (1945): ACE 설계 제안서에서 BURY·UNBURY 개념으로 서브루틴 복귀용 스택형 메커니즘을 최초로 제안함
- Kreps, J. (2013): "The Log: What every software engineer should know about real-time data's unifying abstraction" — 분산 메시지 큐(Kafka) 설계 철학을 정리한 글

스택·큐·덱은 CS에서 가장 기본적인 ADT이지만, 셋의 차이는 결국 "이 데이터를 어떤 순서로 꺼내야 하는가"라는 질문에 대한 답이다. 배열과 연결 리스트 중 무엇으로 구현할지는 부차적 선택이며, LIFO·FIFO·양방향 정책 중 문제가 요구하는 것을 정확히 식별하는 판단이 우선한다.

```text
    +---> [그래프 탐색 (BFS=큐, DFS=스택)]
    +---> [우선순위 큐 (힙 기반)]
    +---> [메시지 큐 (Kafka, RabbitMQ)]
    +---> [락 프리 큐 (CAS 기반)]
```

### 👶 어린이를 위한 3줄 비유 설명

1. 스택은 접시 쌓기예요 — 맨 위에 올리고, 맨 위 것부터 써요. 아래 접시를 쓰려면 위에 쌓인 걸 다 치워야 해요.
2. 큐는 놀이공원 줄 서기예요 — 먼저 온 사람이 먼저 놀이기구를 타요. 새치기는 안 돼요!
3. 덱은 양쪽 문이 있는 기차예요 — 앞문으로도 뒷문으로도 타고 내릴 수 있어서 제일 자유로워요.
