## 미리 알고가기

- **추상 자료형($ADT$)**: 데이터의 논리적 행동(연산)만을 정의하고 구체적인 구현 방법은 명시하지 않은 자료형임
- **$LIFO$ / $FIFO$**: 데이터 처리 순서를 나타내는 정책($Last-In$ $First-Out$ / $First-In$ $First-Out$)임
- **$Overflow$ / $Underflow$**: 자료구조가 수용할 수 있는 한계를 초과하거나, 빈 공간에서 삭제를 시도할 때 발생하는 상태임

## Ⅰ. 개요

- **통합 정의**: 데이터의 삽입과 삭제 위치를 제한하여 처리 순서를 구조적으로 강제하는 선형 자료구조($Linear$ $Data$ $Structure$)의 총칭임
- **개별 정의**:
  - **스택 ($Stack$)**: 한쪽 끝($Top$)에서만 데이터 입출력이 발생하는 후입선출($LIFO$) 방식의 자료구조임
  - **큐 ($Queue$)**: 한쪽($Rear$)으로 삽입하고 반대쪽($Front$)으로 삭제하는 선입선출($FIFO$) 방식의 자료구조임
  - **덱 ($Deque$)**: 양쪽 끝($Front, Rear$) 모두에서 삽입과 삭제가 가능한 양방향 입출력 자료구조임
- **배경/필요성**: 임의 접근($Random$ $Access$)이 가능한 배열과 달리, 함수 호출 이력 관리, 실행 취소($Undo$), 프로세스 스케줄링 등 순서 보장이 핵심인 제어 흐름에서 논리적 일관성을 확보하기 위해 필수적임

## Ⅱ. 특징 및 비교

### 가. 선형 자료구조별 상세 비교

| 비교 항목 | 스택 ($Stack$) | 큐 ($Queue$) | 덱 ($Deque$) |
|:---|:---|:---|:---|
| **입출력 논리** | $LIFO$ | $FIFO$ | 양방향 ($Bi-directional$) |
| **접근 포인터** | $Top$ (단일) | $Front, Rear$ (분리) | $Front, Rear$ (양단) |
| **시간 복잡도** | 삽입/삭제 $O(1)$ | 삽입/삭제 $O(1)$ | 삽입/삭제 $O(1)$ |
| **주요 연산** | $push, pop, peek$ | $enqueue, dequeue$ | $push\_front, pop\_back$ 등 |
| **PPA 관점** | 메모리 효율적, $O(1)$ 접근 | 버퍼링 특화, 응답성 우수 | 유연성 높음, 오버헤드 존재 |

### 나. 기술적 통찰 (Architecture Insight)

1. **순서 모델의 결정**: 실행 취소($Undo$)나 브라우저 뒤로 가기처럼 **최신 이력**이 우선인 경우 스택을, 패킷 버퍼나 작업 대기열처럼 **도착 순서**가 우선인 경우 큐를 선정함
2. **공간 효율화 ($Circular$ $Queue$)**: 선형 배열로 큐 구현 시 발생하는 데이터 이동 오버헤드($O(n)$)를 극복하기 위해, 인덱스를 순환시키는 원형 큐 구조를 사용하여 $O(1)$의 성능을 유지함
3. **제어 유연성**: 덱은 스택과 큐의 특성을 모두 포함하므로, 슬라이딩 윈도우 최적화나 스케줄링 우선순위 조정 등 동적 입출력이 필요한 복합 시나리오에 강력한 도구가 됨

## Ⅲ. 구성요소 및 구현 구조

### 가. 구현 방식별 특징 비교

| 구현 방식 | 설명 및 특징 | 장단점 |
|:---|:---|:---|
| **$Array-based$** | 고정 크기 배열 기반 인덱스 제어 | 접근 속도 빠름, 크기 확장 경직성 |
| **$Linked-based$** | 노드 연결 기반 동적 메모리 할당 | 크기 확장 유연, 포인터 공간 오버헤드 |

### 나. 원형 큐(Circular Queue)의 상태 판별 원리

```text
[Empty 상태]                      [Full 상태]
Front == Rear                     (Rear + 1) % Size == Front
* 한 칸을 비워두거나 (Sentinel)     * 인덱스 순환 연산 (%) 필수 적용
* Count 변수 병행 관리             * 공간 낭비와 판정 로직의 Trade-off
```

## Ⅳ. Real-world Troubleshooting

1. **$Stack$ $Overflow$ 및 재귀 한계**
   - **문제**: 깊은 재귀 호출로 인해 $Call$ $Stack$이 가용 메모리를 초과하여 시스템 런타임 오류 발생
   - **대응**: 명시적 스택 자료구조와 반복문을 사용하는 반복($Iterative$) 방식으로 전환하거나 꼬리 재귀 최적화($Tail$ $Recursion$)를 적용함

2. **선형 큐의 가짜 포화 ($False$ $Overflow$)**
   - **문제**: 데이터 삭제 후 앞부분에 빈 공간이 있음에도 $Rear$가 배열 끝에 도달하여 삽입이 거부되는 현상
   - **대응**: 모듈로($\%$) 연산을 이용한 **원형 큐($Circular$ $Queue$)** 구조를 도입하여 논리적 연속성을 확보함

3. **멀티스레드 환경의 경쟁 상태 ($Race$ $Condition$)**
   - **문제**: 여러 스레드가 동시에 자료구조를 갱신할 때 데이터 오염이나 $Pointer$ 손상 발생
   - **대응**: $Mutex, Semaphore$ 등 동기화 기법을 적용하거나, 높은 처리량이 필요한 경우 $Compare-and-Swap$($CAS$) 기반의 **$Lock-free$ $Queue$**를 설계함

## Ⅴ. 실무 적용 사례

| 적용 영역 | 적용 방식 | 확인 지표 |
|:---|:---|:---|
| **JVM 런타임** | **$Stack$ $Area$** 관리 | 메서드 호출 프레임, 지역 변수 유효 범위 |
| **OS 스케줄러** | **$Multi-level$ $Feedback$ $Queue$** | 프로세스 우선순위, $Time$ $Slice$ 소모량 |
| **네트워크 스위치** | **$Packet$ $Buffer$** ($FIFO$ 기반) | 패킷 유실률 ($Drop$ $Rate$), 지연 시간 |
| **고급 알고리즘** | **$Monotonic$ $Queue$ / $Deque$** | 슬라이딩 윈도우 최적화, 최댓값/최솟값 유지 |

## Ⅵ. 결론

스택·큐·덱은 단순한 데이터 저장소를 넘어 **시스템의 논리적 흐름과 공정성($Fairness$)을 결정**하는 기초 설계 자산임. 기술사는 단순히 자료구조의 정의를 넘어, 물리적 메모리 구조와 런타임 환경(멀티스레드, 실시간성)을 고려하여 최적의 데이터 패스를 설계할 수 있어야 함.

특히 현대의 대규모 분산 메시징 시스템($Kafka, RabbitMQ$)의 근간이 이러한 기본 자료구조에 있음을 인지하고, 성능 병목 시 내부 버퍼링 구조와 동기화 메커니즘을 튜닝할 수 있는 아키텍처적 통찰력이 요구됨.
