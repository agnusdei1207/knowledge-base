## Ⅰ. 개요
- **정의**: 삽입·삭제 위치를 제한하여 특정 접근 순서를 보장하는 선형 자료구조
- **배경/필요성**: 데이터 처리 순서가 문제의 정합성을 결정하므로, 접근 규칙을 구조 수준에서 강제할 수단이 필요함
- **비유**: 스택은 접시 쌓기(맨 위만 꺼냄), 큐는 매표소 줄(먼저 온 사람 먼저 처리), 덱은 양쪽 문이 있는 복도

| 출제 의도 | 반드시 짚을 핵심 | 감점 회피 포인트 |
|:---|:---|:---|
| 세 구조의 연산 규칙 차이 이해 | LIFO·FIFO·양방향 접근의 정의와 시간 복잡도 | 덱을 단순 "스택+큐"로만 설명하면 감점, 슬라이딩 윈도우 등 고유 활용 언급 필요 |

> 요약: 삽입·삭제 위치 제한으로 LIFO·FIFO·양방향 접근을 보장하는 세 가지 선형 자료구조임

## Ⅱ. 구성요소
```text
+--------+    +--------+    +--------+
| Stack  |    | Queue  |    | Deque  |
+--------+    +--------+    +--------+
| top -> |    | front->|    |<-front |
| push   |    | enqueue|    | push_f |
| pop    |    | dequeue|    | push_b |
|        |    | <-rear |    | pop_f  |
|        |    |        |    | pop_b  |
+--------+    +--------+    +--------+
  LIFO          FIFO        양방향
```

| 구성요소 | 설명 | 비유 |
|:---|:---|:---|
| Stack | `top` 한쪽에서만 삽입(`push`)·삭제(`pop`), O(1) | 되돌리기(Undo) 버튼: 마지막 작업부터 취소 |
| Queue | `front`에서 삭제(`dequeue`), `rear`에서 삽입(`enqueue`), O(1) | 프린터 대기열: 먼저 요청한 문서부터 출력 |
| Deque | 양쪽 끝에서 삽입·삭제 모두 가능, O(1) | 양방향 에스컬레이터: 어느 쪽에서든 탑승·하차 가능 |

> 요약: 세 구조 모두 삽입·삭제가 O(1)이며, 허용되는 접근 위치만 다름

## Ⅲ. 절차
```text
[문제 분석] --> [접근 순서 결정] --> [구조 선택] --> [연산 적용]
```
- 1단계: 문제에서 요구하는 데이터 처리 순서를 분석함
- 2단계: LIFO(역순 처리), FIFO(순차 처리), 양방향 중 적합한 접근 순서를 결정함
- 3단계: 접근 순서에 따라 스택·큐·덱 중 구조를 선택함
  - 스택: 함수 호출 관리, 괄호 검사, DFS
  - 큐: BFS, 작업 스케줄링, 버퍼
  - 덱: 슬라이딩 윈도우 최솟값/최댓값, 양방향 탐색
- 4단계: 선택한 구조의 연산(`push`/`pop`, `enqueue`/`dequeue`, `push_front`/`pop_back` 등)을 적용하여 문제를 해결함

> 요약: 문제의 처리 순서 요구사항을 분석한 뒤 적합한 구조를 선택하고 해당 연산을 적용함

## Ⅳ. 문제점
- 스택 오버플로: 재귀 깊이 제한 없이 스택을 사용할 경우 메모리 초과 발생 — 함수 호출 스택이 OS 스택 크기를 초과하면 프로그램이 비정상 종료함
- 큐의 공간 낭비: 배열 기반 큐에서 `front` 이동 시 앞쪽 공간이 재사용되지 않음 — 삭제된 인덱스가 빈 채로 남아 실제 저장 가능 원소 수가 줄어듦
- 덱의 구현 복잡도: 양방향 연산 지원으로 연결 리스트(006 참조) 또는 순환 배열 구현이 필요함 — 단순 배열 대비 캐시 미스율 증가 또는 포인터 관리 오버헤드 발생

> 요약: 스택은 오버플로, 큐는 공간 낭비, 덱은 구현 복잡도에서 각각 취약점을 가짐

## Ⅴ. 개선방안
1. 단기: 스택 깊이 제한 설정 또는 반복문 변환으로 오버플로 방지
2. 중기: 원형 큐(Circular Queue) 도입으로 배열 앞쪽 공간을 재활용하여 공간 낭비 해소
3. 장기: 덱 구현 시 순환 배열 기반 블록 할당(예: C++ `std::deque`의 청크 맵 방식) 적용으로 캐시 효율과 양방향 연산을 동시에 확보

> 요약: 깊이 제한, 원형 큐, 블록 기반 덱으로 각 문제를 해결함

## Ⅵ. 전망
- 발전 방향: Lock-Free 큐·덱 등 동시성 환경에 최적화된 변형 구조의 활용 확대
- 기술사적 판단: 스택·큐·덱은 알고리즘 설계의 기본 빌딩 블록이므로, 트리(008 참조)·그래프 등 상위 구조 이해의 전제 조건임
- 기술사 제언: 자료구조 선택 시 접근 순서 요구사항을 먼저 정의하고, 메모리 레이아웃과 동시성 요건까지 고려한 구조 선정이 필요함
