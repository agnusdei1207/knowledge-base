## 미리 알고가기

- `n`: 입력 데이터의 크기이며 원소 수, 정점 수, 비트 수처럼 문제별 단위가 달라짐
- 기본 연산: 비교, 대입, 산술, 해시 계산처럼 비용을 세는 기준 동작임
- 점근 분석: `n`이 충분히 커질 때 지배적인 증가 추세를 보는 분석 방식임
- 상한: 실제 비용이 특정 함수의 상수배 안에 들어간다는 보수적 경계임
- 최악/평균/최선: 같은 알고리즘도 입력 분포에 따라 비용 함수가 달라짐

## Ⅰ. 개요

- **정의**: 빅오 표기법은 알고리즘의 실행시간·추가 메모리 증가율을 입력 크기 `n`에 대한 상한 함수 `O(f(n))`로 표현해 대규모 입력의 확장성을 비교하는 기준임
- **배경/필요성**: 상수항·하위항을 제거하고 지배항만 남기면 언어·하드웨어 구현 차이에 가려진 구조적 비용이 드러나지만, 빅오는 상한 표기라서 평균 성능·작은 입력·입출력(Input/Output, I/O) 병목까지 자동으로 설명하지는 못함.
- **비유**: 도시 교통에서 특정 도로의 제한속도보다 출퇴근 시간에 차선 수가 얼마나 감당할 수 있는지를 보는 것과 같음.

| 출제 의도 | 반드시 짚을 핵심 | 감점 회피 포인트 |
|:---|:---|:---|
| 알고리즘 비용 판단 역량 확인 | 입력 크기, 기본 연산, 점근 상한, 복잡도 계층 | 상수 제거 의미 오해, 평균/최악 혼동 |

> 요약: 빅오는 입력 증가 시 비용이 얼마나 빨리 커지는지 상한 성장률로 고정해 알고리즘을 비교하는 표기법임.

## Ⅱ. 특징/비교

| 판단 기준 | 실제 측정 시간 | 빅오 표기 | 세타/오메가(Θ/Ω) 표기 |
|:---|:---|:---|:---|
| 관심 대상 | 특정 장비의 실행 초 | 입력 증가에 따른 상한 증가율 | 정확한 증가율 또는 하한 |
| 비교 가능성 | 언어·중앙처리장치(Central Processing Unit, CPU)·캐시에 민감함 | 구현 환경 차이를 줄여 구조 비교 가능 | 증명 조건이 더 엄격함 |
| 선택 기준 | 운영 튜닝, 벤치마크에 적합 | 알고리즘 후보 1차 선별에 적합 | 이론적 tight bound 판단에 적합 |
| 한계 | 입력 규모 변화 설명이 약함 | 작은 입력의 상수 비용을 숨김 | 표기 목적을 구분해야 함 |

> 요약: 빅오는 실제 시간을 대체하는 수치가 아니라 입력 규모가 커질 때 버틸 수 있는 알고리즘을 고르는 1차 판단 기준임.

- `O(1)`, `O(log n)`, `O(n)`, `O(n log n)`, `O(n^2)` 순으로 일반적으로 성장 부담이 커짐
- 같은 `O(n log n)`이라도 메모리 접근 패턴, 안정성, 병렬화 가능성은 별도로 비교해야 함
- 시험 답안에서는 표기 결과보다 어떤 기본 연산을 기준으로 식을 세웠는지 설명해야 함
- 세타(Big-Theta, Θ) 표기는 상한과 하한이 일치하는 정확한 증가율을, 오메가(Big-Omega, Ω) 표기는 하한을 나타내므로 빅오보다 증명 조건이 엄격함

## Ⅲ. 구성요소

```text
+-------------+      +-------------+      +-------------+
| 입력 크기 n | ---> | 비용 함수 T | ---> | O(f(n))     |
+-------------+      +-------------+      +-------------+
        |                    |                    |
        v                    v                    v
+-------------+      +-------------+      +-------------+
| 기본 연산   |      | 지배항 추출 |      | 선택 기준   |
+-------------+      +-------------+      +-------------+
```

| 구성요소 | 설명 | 비유 |
|:---|:---|:---|
| 입력 크기 | 문제 규모를 나타내는 변수로 원소 수, 노드 수, 비트 수 등을 사용함 | 손님 수 |
| 기본 연산 | 비용을 세는 단위 동작이며 비교, 삽입, 이동, 접근 등이 해당함 | 계산대 처리 1건 |
| 비용 함수 | 입력 크기별 기본 연산 수행 횟수나 추가 메모리 사용량을 식으로 표현함 | 총 대기 시간 |
| 지배항 | `n`이 커질 때 전체 비용을 사실상 결정하는 최고 성장 항임 | 병목 차선 |
| 상한 표기 | 지배항을 기준으로 상수배 안에 비용이 들어감을 나타냄 | 최대 수용 한계 |

> 요약: 빅오 분석은 입력 크기와 기본 연산으로 비용 함수를 만들고, 지배항을 상한 표기로 바꾸는 구조임.

- 구성요소 중 기본 연산 선택이 흔들리면 같은 코드도 다른 복잡도로 설명될 수 있음
- 공간 복잡도는 입력 자체를 제외한 추가 메모리 기준인지 포함 기준인지 밝혀야 함
- 재귀 알고리즘은 호출 수와 호출 스택을 모두 구조에 포함해야 함

## Ⅳ. 절차

```text
+----------+      +----------+      +----------+      +----------+
| 입력정의 | ---> | 연산선정 | ---> | 함수도출 | ---> | 표기결정 |
+----------+      +----------+      +----------+      +----------+
                                      |                  |
                                      v                  v
                                +----------+      +----------+
                                | 지배항화 |      | 비교/선택|
                                +----------+      +----------+
```

1. **입력/요구 식별** - `n`, `V`, `E`처럼 문제 규모를 나타내는 변수를 정하고 분석 대상을 시간 또는 공간으로 구분함
2. **기본 연산 선정** - 반복문, 재귀 호출, 자료구조 접근 중 비용을 대표하는 연산을 하나 이상 선택함
3. **비용 함수 도출** - 반복 횟수, 재귀식, 자료구조 연산 비용을 합산해 `T(n)` 또는 `S(n)`을 구성함
4. **지배항 표기** - 하위항과 계수를 제거하고 상한 함수 `O(f(n))`으로 표현한 뒤 대안 알고리즘과 비교함

> 요약: 빅오 절차는 문제 규모를 정하고 비용식을 만든 뒤, 지배항 상한으로 바꿔 선택 기준으로 쓰는 흐름임.

- 중첩 반복문은 반복 범위가 독립인지 종속인지 확인해야 함
- 로그 밑은 상수배 차이로 처리되지만, 로그가 생기는 이유는 분할·탐색 구조로 설명해야 함
- 해시, 정렬, 그래프 알고리즘은 평균·최악 조건을 함께 밝히는 것이 안전함

## Ⅴ. 문제점

- **P1 상한 표기의 과잉 일반화**: 빅오는 최악 또는 상한을 강조하므로 평균 입력에서의 실제 비용이나 캐시 친화성 차이를 숨길 수 있음
- **P2 작은 입력의 상수 비용 은폐**: 상수와 하위항을 제거하기 때문에 입력이 작거나 함수 호출 비용이 큰 경우 실제 실행 시간이 역전될 수 있음
- **P3 분석 변수 누락**: 그래프의 `V/E`, 분산 처리의 네트워크, 외부 정렬의 I/O처럼 비용을 좌우하는 변수를 하나의 `n`으로 과도하게 단순화할 수 있음

> 요약: 빅오는 큰 입력의 구조적 상한을 보는 도구이므로 실제 운영 비용과 다변수 조건을 별도로 보완해야 함.

## Ⅵ. 개선방안

- **P1 대응**: 빅오와 함께 평균/최악 조건, 벤치마크, p95(95th percentile) 지연, 메모리 접근 패턴을 병기함 (확인: 입력 분포별 측정 결과)
- **P2 대응**: 작은 입력 구간은 마이크로벤치마크와 임계값 기반 알고리즘 전환으로 검증함 (확인: `n` 구간별 실행시간 교차점)
- **P3 대응**: 문제 특성에 맞게 `V`, `E`, 블록 수, 네트워크 왕복 횟수 등 복수 변수를 비용식에 포함함 (확인: 병목 자원별 비용 모델)

> 요약: 빅오의 추상화를 유지하되 측정, 입력 조건, 다변수 모델로 실제 선택 오류를 줄여야 함.

## Ⅶ. 전망

- **발전 방향**: 대용량 데이터, 병렬 처리, 클라우드 비용 최적화에서는 시간 복잡도뿐 아니라 메모리, 네트워크, 에너지 비용까지 함께 모델링하는 방향으로 확장됨
- **기술사적 판단**: 알고리즘 선정 시 빅오 계층으로 후보를 줄이고, 운영 환경의 데이터 분포와 자원 병목으로 최종 선택해야 함
- **기술사 제언**: 답안에서는 표기 결과를 외우는 데서 멈추지 말고 입력 변수, 기본 연산, 적용 조건을 함께 제시하는 것이 핵심임
