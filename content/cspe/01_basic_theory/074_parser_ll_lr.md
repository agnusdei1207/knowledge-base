## 미리 알고가기

- 파서: 토큰 열이 문법에 맞는지 검사하고 파스 트리 또는 AST를 만드는 구문 분석기임
- LL 파싱: 입력을 왼쪽부터 읽고 좌측 유도를 수행하는 하향식 파싱 방식임
- LR 파싱: 입력을 왼쪽부터 읽고 우측 유도의 역순으로 reduce하는 상향식 파싱 방식임
- Lookahead `k`: 다음 몇 개 토큰을 보고 생성 규칙이나 동작을 결정하는지 나타내는 값임
- FIRST/FOLLOW: LL 파싱 테이블을 만들 때 사용하는 시작 가능 토큰과 후속 가능 토큰 집합임
- Shift/Reduce: LR 파서가 토큰을 스택에 넣거나 규칙으로 축약하는 기본 동작임

## Ⅰ. 개요

- **정의**: 파서는 어휘 분석기가 만든 토큰 스트림을 문법 규칙과 lookahead 기준으로 검사해 계층적 구문 구조인 AST로 변환하는 컴파일러 프론트엔드 구성요소임. 소스 코드의 구조적 오류를 찾고 이후 의미 분석과 코드 생성이 사용할 문법 구조를 만들기 위해 사용함
- **배경/필요성**: 소스 코드는 단순 토큰 나열이 아니라 중첩된 구문 구조를 가지므로, 기계가 타입 검사와 최적화를 수행하려면 먼저 문법 구조를 확정해야 함
- **비유**: 문장을 단어 목록으로 보는 데서 끝내지 않고 주어, 목적어, 절 구조로 나누어 문법적으로 맞는지 검사하는 과정과 유사함

| 출제 의도 | 반드시 짚을 핵심 | 감점 회피 포인트 |
|:---|:---|:---|
| LL과 LR 비교 | 하향식 예측, 상향식 shift-reduce | lookahead 의미 누락 |
| 파싱 테이블 역할 설명 | FIRST/FOLLOW, ACTION/GOTO | 모호 문법과 충돌 원인 미구분 |

> 요약: 파서는 토큰 열을 문법 기준으로 구조화하고, LL과 LR은 구조를 위에서 만들지 아래에서 조립할지의 차이를 가짐

## Ⅱ. 특징/비교

| 판단 기준 | LL 파서 | LR 파서 |
|:---|:---|:---|
| 분석 방향 | 시작 기호에서 입력 토큰 방향으로 전개함 | 입력 토큰을 스택에 쌓아 시작 기호로 축약함 |
| 구현 방식 | 재귀 하강 파서로 직접 구현하기 쉬움 | 파서 생성기와 ACTION/GOTO 테이블을 주로 사용함 |
| 문법 제약 | 좌측 재귀에 취약하고 좌측 인수분해가 필요할 수 있음 | 더 넓은 문법을 처리하지만 테이블과 충돌 관리가 필요함 |
| 선택 기준 | 단순 문법, 오류 메시지 제어, 수동 구현 | 복잡 문법, 강한 인식력, 자동 생성 도구 |

> 요약: LL은 단순성과 직접 제어에, LR은 인식력과 복잡 문법 처리에 강점이 있어 언어 문법 특성에 따라 선택함

- **LL 핵심 판단**: FIRST/FOLLOW 충돌이 없고 좌측 재귀를 제거할 수 있으면 적합함
- **LR 핵심 판단**: shift/reduce 또는 reduce/reduce 충돌을 관리할 수 있으면 복잡 문법에 적합함
- **현대 도구 판단**: Tree-sitter 같은 증분 파서는 IDE 실시간 분석 요구에 맞춰 선택됨

## Ⅲ. 구성요소

```text
+-------------+      +-------------+      +-------------+
| Token       | ---> | Parsing     | ---> | Parse Tree  |
| Stream      |      | Table/Rules |      | or AST      |
+------+------+      +------+------+      +------+------+
       |                    |                    |
       v                    v                    v
+-------------+      +-------------+      +-------------+
| Stack       | <--- | LL / LR     | ---> | Error       |
| State       |      | Engine      |      | Recovery    |
+-------------+      +-------------+      +-------------+
```

| 구성요소 | 설명 | 비유 |
|:---|:---|:---|
| 토큰 스트림 | Lexer가 만든 입력이며 파서가 순서대로 소비하는 대상임 | 문장 재료 |
| 문법 규칙 | 허용 가능한 구문 구조와 생성 규칙을 정의함 | 문법 설명서 |
| 파싱 테이블 | 현재 상태와 lookahead에 따라 적용할 규칙 또는 동작을 지정함 | 행동 지침표 |
| 스택 | LR 파서에서 상태와 심볼을 저장하고 reduce 판단에 사용함 | 조립 받침대 |
| AST/오류 처리 | 성공 시 구조 트리를 반환하고 실패 시 오류 위치와 복구 전략을 제공함 | 결과 보고서 |

> 요약: 파서는 토큰, 문법, 테이블, 스택, 오류 처리를 결합해 입력 프로그램의 구문 구조를 결정함

## Ⅳ. 절차

```text
+-----------+     +-----------+     +-----------+     +-----------+
| Read      | --> | Decide    | --> | Build     | --> | Accept /  |
| Token     |     | Rule/Act  |     | AST Node  |     | Report    |
+-----------+     +-----------+     +-----------+     +-----------+
      |                 |                 |                 |
      v                 v                 v                 v
lookahead          table lookup       tree update       parse result
```

1. **토큰 입력**: Lexer에서 토큰과 위치 정보를 받아 lookahead로 사용할 현재 입력을 확인함
2. **동작 결정**: LL은 FIRST/FOLLOW로 생성 규칙을 고르고 LR은 ACTION/GOTO로 shift 또는 reduce를 선택함
3. **구조 생성**: 선택된 규칙에 따라 파스 트리 또는 AST 노드를 만들고 스택·상태를 갱신함
4. **수용·오류 처리**: 시작 기호로 완성되면 AST를 반환하고, 불일치하면 위치와 원인을 보고하며 복구를 시도함

> 요약: 파싱은 토큰을 읽고 테이블로 동작을 정한 뒤 트리를 갱신하며 수용 또는 오류 상태에 도달할 때까지 반복함

## Ⅴ. 문제점

- **P1 좌측 재귀와 문법 변환 부담**: LL 파서는 `A -> Aα` 형태에서 무한 재귀가 발생해 문법 재작성 비용이 생김
- **P2 LR 테이블 충돌·상태 폭증**: 복잡 문법에서는 shift/reduce 충돌이나 큰 상태 집합으로 메모리와 디버깅 부담이 증가함
- **P3 오류 복구 품질 한계**: 잘못된 토큰 하나가 뒤쪽 구문 오류를 연쇄적으로 발생시켜 사용자에게 혼란스러운 메시지를 줄 수 있음

> 요약: 파서 실무 문제는 문법 변환, 테이블 충돌, 오류 복구 품질에서 주로 발생함

## Ⅵ. 개선방안

- **P1 대응**: 좌측 재귀 제거, 좌측 인수분해, 반복문 기반 규칙 재작성으로 LL 문법을 정리함 (확인: FIRST/FOLLOW 충돌 수)
- **P2 대응**: LALR(1), precedence 선언, parser generator 경고 분석으로 충돌과 상태 수를 통제함 (확인: conflict count, table size)
- **P3 대응**: panic mode, phrase-level recovery, IDE용 incremental parsing으로 오류 위치와 복구 품질을 개선함 (확인: 연쇄 오류 수)

> 요약: 문법을 파서 계열에 맞게 정리하고 충돌과 오류 복구를 지표로 관리해야 파서를 안정적으로 운영할 수 있음

## Ⅶ. 전망

- **발전 방향**: IDE, LSP, 코드 분석 도구 확산으로 전체 파일 재파싱보다 증분 파싱과 오류 내성 파싱의 중요성이 커질 전망임
- **기술사적 판단**: 파서 선택은 이론적 인식력뿐 아니라 문법 유지보수, 오류 메시지 품질, 도구 생태계까지 함께 고려해야 함
- **기술사 제언**: 답안에서는 LL/LR을 표로 비교한 뒤 각각의 충돌 원인과 실무 선택 기준을 연결해야 함
