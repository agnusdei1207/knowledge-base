# 074. 파싱 기법 — LL·LR 파서 (Parsing LL LR)

## Ⅰ. 개요

- **정의/개념**: 소스 코드의 토큰($Token$) 시퀀스를 문법 규칙에 따라 분석하여 계층적 구조를 가진 파스 트리($Parse$ $Tree$)를 생성하는 구문 분석 공정임
  - **$LL$ 파서**: 입력의 왼쪽부터 읽으며($L$), 좌단 유도($L$)를 수행하는 **하향식($Top$-$down$)** 방식임
  - **$LR$ 파서**: 입력의 왼쪽부터 읽으며($L$), 우단 유도의 역순($R$)을 수행하는 **상향식($Bottom$-$up$)** 방식임
- **배경/필요성**: 어휘 분석으로 생성된 토큰 나열은 단순 선형 데이터임. 이를 프로그램의 논리적 실행 단위(제어문, 표현식 등)로 구조화하고 문법적 정합성을 $O(n)$ 시간 복잡도 내에 검증하기 위해 정밀한 파싱 알고리즘이 필수적임

## Ⅱ. 특징 및 비교

### 1. $LL$ 파서 vs $LR$ 파서 심층 비교

| 판단 기준 | $LL(k)$ 파서 ($Top$-$down$) | $LR(k)$ 파서 ($Bottom$-$up$) |
|:---|:---|:---|
| **분석 패러다임** | 시작 기호 $\rightarrow$ 단말 기호 (예측) | 단말 기호 $\rightarrow$ 시작 기호 (축약) |
| **핵심 연산** | $Predict$ (다음에 올 규칙 예측) | $Shift$ (적재) & $Reduce$ (축약) |
| **문법 수용 범위** | 좁음 (좌재귀 제거 필수) | 넓음 (대부분의 $CFG$ 수용 가능) |
| **구현 난이도** | 낮음 (재귀 호출로 수동 구현 용이) | 높음 (파싱 테이블 도구 활용 권장) |
| **오류 진단** | 우수 (예측 지점에서 즉시 인지) | 보통 ($Reduce$ 실패 전까지 지연 가능) |

> 요약: $LL$은 직관적이고 구현이 단순하여 $DSL$에 유리하며, $LR$은 강력한 표현력으로 상용 언어 컴파일러의 표준으로 활용됨

### 2. $PPA$ 및 트레이드오프 ($Trade$-$offs$)
- **Performance**: 두 방식 모두 결정적($Deterministic$)인 경우 $O(n)$의 선형 시간을 보장하나, $LR$은 테이블 조회 오버헤드가 발생함
- **Area(Memory)**: $LR(1)$은 상태 수가 기하급수적으로 늘어나 메모리 점유가 큼. 이를 최적화한 $LALR(1)$이 실무적 대안으로 쓰임
- **Trade-off**: $Lookahead(k)$를 늘릴수록 더 복잡한 문법을 판별할 수 있으나($Precision$ 향상), 테이블 크기와 분석 지연($Latency$)이 급증함

## Ⅲ. 구성요소/구조

### 1. $LR$ 파서 아키텍처 인사이트 ($Architecture$ $Insight$)
- **Input Buffer**: 분석 대기 중인 토큰들의 시퀀스
- **Stack**: 현재까지 분석된 문법 기호와 상태($State$) 번호를 유지하는 메모리 공간
- **Parsing Table**: 핵심 로직이 담긴 제어판
  - **$Action$ 표**: 현재 상태와 입력 토큰에 따라 $Shift, Reduce, Accept, Error$ 결정
  - **$Goto$ 표**: $Reduce$ 후 비단말 기호($Non$-$terminal$)에 따른 다음 상태 결정
- **Driver Program**: 테이블과 스택을 조작하여 분석을 수행하는 공통 알고리즘

### 2. 파싱 프로세스 흐름도 ($LR$ 기준)
```text
[Input Buffer] ----> [Driver Program] <----> [Parsing Table]
                          |
                   [Parsing Stack] ----> [Parse Tree/AST]
```

## Ⅳ. 문제점 및 개선방안

### 1. 실무적 문제점 및 대응 전략
1. **[좌재귀($Left$ $Recursion$)에 의한 무한 루프 ($LL$)]**: $A \rightarrow A\alpha$ 와 같은 규칙 시 끝없이 하강함
   - **개선방안**: 문법을 우재귀($Right$ $Recursion$) 형태로 변환하거나, 반복문을 사용하는 $EBNF$ 확장 기법 적용 (확인: 스택 깊이 제어)
2. **[동작 결정 모호성 ($Shift$-$Reduce$ $Conflict$)]**: 다음에 올 토큰을 쌓을지, 현재 스택을 합칠지 결정 불능
   - **개선방안**: 연산자 우선순위($Precedence$)와 결합 법칙($Associativity$)을 명시하여 테이블 생성 시 우선순위 부여 (확인: 테이블 충돌 제거)
3. **[방대한 파싱 테이블 크기 ($LR$)]**: 수천 개의 상태가 발생하여 임베디드 등 저사양 환경에서 메모리 부족
   - **개선방안**: 공통 상태를 통합하는 $LALR$($Look$-$Ahead$ $LR$) 기법을 사용하거나 테이블 압축($Row/Column$ $Compression$) 수행 (확인: 메모리 점유율)

### 2. 리얼월드 트러블슈팅 ($Real$-$world$ $Troubleshooting$)
- **상황**: 문법 수정 후 컴파일러 빌드 시 $Reduce$-$Reduce$ $Conflict$ 발생하여 특정 구문 해석이 오작동함
- **해결**: 모호한 생성 규칙($Production$)을 분리하고, 문법의 $First$ 집합과 $Follow$ 집합을 수동 검증하여 겹치는 지점을 제거함

## Ⅴ. 실무 적용 사례

| 적용 영역 | 적용 기술 | 확인 지표 |
|:---|:---|:---|
| **상용 컴파일러 ($GCC, LLVM$)** | $LALR(1) / LR(1)$ | 문법 지원 완전성, 대용량 파일 파싱 속도 |
| **$IDE$ 구문 강조 ($Syntax$ $Highlight$)** | $Incremental$ $Parsing$ | 타이핑 시 실시간 반영 지연 시간 ($<10ms$) |
| **수식 계산기 / $JSON$ 파서** | $Recursive$ $Descent$ ($LL$) | 코드 가독성, 유지보수 용이성 |

## Ⅵ. 결론

파싱 기법은 텍스트라는 비정형의 흐름을 논리라는 정형의 구조로 바꾸는 전산학의 정수임. 최근에는 고정된 문법을 넘어 $LLM$이 생성한 자유 텍스트 내에서 구조적 데이터를 추출하기 위한 제약 파싱($Grammar$-$constrained$ $Decoding$) 기술로 응용 범위가 확장되고 있음. 기술사는 언어의 사양과 실행 환경의 자원 제약을 고려하여 최적의 파서 아키텍처를 선택 및 설계할 수 있는 역량을 갖춰야 함.
