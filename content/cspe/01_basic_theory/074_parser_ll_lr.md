## Ⅰ. 개요
- **정의**: 토큰 열을 문법 규칙에 따라 AST(추상 구문 트리)로 변환하는 구문 분석 알고리즘임
- **배경/필요성**: 컴파일러 프론트엔드(073 참조)에서 소스 코드의 구조적 유효성을 기계적으로 판별 필수
- **비유**: 문장을 주어·서술어·목적어로 분해하여 문법에 맞는지 검사하는 교정기

| 출제 의도 | 반드시 짚을 핵심 | 감점 회피 포인트 |
|:---|:---|:---|
| LL vs LR 방식 차이 | 하향식(예측)/상향식(Shift-Reduce) 메커니즘 | LL(k)와 LR(k)의 k=lookahead 수임을 명시 |
| 파싱 테이블 구성 원리 | FIRST/FOLLOW 집합, Action/Goto 테이블 | SLR·LALR·CLR 차이를 혼동하지 않도록 구분 |

> 요약: 토큰 열을 문법 기반으로 트리화하는 구문 분석기로, LL(하향식)과 LR(상향식) 두 계열로 구분됨

## Ⅱ. 구성요소
```text
+----------+     +----------+     +----------+
| Token    | --> | Parsing  | --> | AST      |
| Stream   |     | Engine   |     | Output   |
+----------+     +----------+     +----------+
                      |
               +------+------+
               |             |
          +----+----+   +----+----+
          | LL(Top  |   | LR(Bot  |
          |  Down)  |   |  Up)    |
          +---------+   +---------+
```

| 구성요소 | 설명 | 비유 |
|:---|:---|:---|
| LL 파서 | 시작 기호→입력 방향으로 좌측 유도, 예측 파싱 테이블(FIRST/FOLLOW) 기반 | 목차→본문 탐색 |
| LR 파서 | 입력→시작 기호 방향으로 Shift-Reduce, Action/Goto 테이블 기반 | 퍼즐 조립→완성 |
| 파싱 테이블 | 현재 상태·입력 심볼 조합으로 Shift/Reduce/Accept/Error 동작을 결정하는 2D 표 | 행동 매뉴얼 |

> 요약: LL은 예측 기반 하향식, LR은 Shift-Reduce 상향식이며, 파싱 테이블이 동작을 결정함

## Ⅲ. 절차
```text
+----------+    +----------+    +----------+    +----------+
| Read     | -> | Lookup   | -> | Build    | -> | Report   |
| Token    |    | Table    |    | AST Node |    | or Error |
+----------+    +----------+    +----------+    +----------+
```

1. **토큰 읽기** — 어휘 분석기(Lexer)에서 전달된 토큰을 순차적으로 소비함
2. **테이블 조회** — LL: FIRST/FOLLOW로 생성 규칙 선택, LR: Action 테이블에서 Shift/Reduce 결정
3. **트리 구축** — LL: 좌측 유도로 파스 트리 상→하 생성, LR: Reduce 시 하→상 노드 병합
4. **결과 반환** — Accept 상태 도달 시 AST 반환, 미도달 시 구문 오류 위치·원인 보고

> 요약: 토큰 소비 → 테이블 기반 상태 전이 → AST 노드 조립 → 수용/오류 판정의 반복 루프임

## Ⅳ. 문제점
- [좌측 재귀]: LL 파서에서 A → Aα 형태 규칙 존재 시 무한 루프 발생, 문법 변환 필수
- [테이블 폭발]: CLR 파서의 상태 수가 수천 개에 달해 메모리 사용량 과다 (예: C 문법 10,000+ 상태)
- [오류 복구 미흡]: 구문 오류 발생 시 Panic-Mode 복구가 후속 오류를 연쇄 유발하는 문제

> 요약: LL의 재귀 제약, LR의 상태 폭발, 양 방식 공통의 오류 복구 품질이 주요 한계임

## Ⅴ. 개선방안
1. 단기: 좌측 재귀 제거·좌측 인수분해로 LL 문법 변환, Recursive Descent 수동 구현으로 유연성 확보
2. 중기: LALR(1) 파서(Yacc/Bison)를 적용하여 CLR 대비 상태 수를 1/10로 축소하면서 동일 인식력 유지
3. 장기: PEG(Parsing Expression Grammar) 또는 GLL/GLR 범용 파서로 모호 문법까지 선형~준선형 시간 처리

- [오류 복구 연쇄]: Panic-Mode 한계 → 문맥 인식 에러 복구(Burke-Fisher) 도입 (지표: 연쇄 오류 수 ≤ 1)

> 요약: 문법 변환 → LALR 축소 → 범용 파서 전환 순으로 재귀·상태·오류 문제를 해소함

## Ⅵ. 전망
- 향후 발전 방향: IDE의 실시간 구문 분석(Incremental Parsing — Tree-sitter 등)이 표준화되며 부분 재파싱 기술 확산
- 기술사적 판단: 프로그래밍 언어 도구 체인에서 파서는 대체 불가 구성요소이며, LSP 기반 에디터 통합으로 중요도 상승 중
- 기술사 제언: 신규 언어 설계 시 LL(1) 파싱 가능 문법을 우선 목표로 설정하여 도구 생태계 구축 비용 최소화 필요
