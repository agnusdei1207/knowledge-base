# 📖 【암기용】 개념 완전 이해

> 목적: LL과 LR 파서의 차이를 처음 보는 사람도 직관적으로 이해하게 만든다.

## 한눈에
- **개요**: 컴파일러의 구문 분석 단계에서, 토큰들이 문법에 맞는지 확인하며 구문 트리(AST)를 만들어가는 두 가지 결정론적(선형 시간) 파싱 알고리즘이다.
- **왜 필요한가**: 일반적인 문맥자유문법(PDA) 파싱은 $O(N^3)$ 시간이 걸려 컴파일이 너무 느리다. 모호성이 없는 특정 문법 부분집합(LL, LR)만 허용하여 $O(N)$ 속도를 내기 위해 필요하다.
- **핵심 직관**: 트리를 뿌리에서 잎으로 내려가며 그릴 것인가(LL, Top-Down), 아니면 잎에서부터 뭉쳐서 뿌리로 올라갈 것인가(LR, Bottom-Up)의 차이다.

## 핵심 용어 정리

| 용어/표기 | 의미 | 비유·예 |
|:---|:---|:---|
| 파서(Parser) | 토큰 열을 입력받아 구문 트리를 구성하는 도구 | "단어들을 문장 구조로 조립하는 기계" |
| Top-Down 파싱 | 루트(Root)에서 시작해 자식 노드를 전개해가는 방식 | "큰 그림을 먼저 그리고 세부를 채움" |
| Bottom-Up 파싱 | 단말 노드(토큰)들을 묶어 상위 부모 노드로 축약해가는 방식 | "벽돌들을 쌓아 올려 지붕을 완성함" |
| LL 파서 | Left-to-right 입력, Left-most 도출 (Top-Down) | "왼쪽부터 읽으며, 가장 왼쪽 변수부터 전개" |
| LR 파서 | Left-to-right 입력, Right-most 역도출 (Bottom-Up) | "왼쪽부터 읽지만, 오른쪽 끝부터 묶어 올라감" |

## 깊이 이해
- **배경·문제의식**: 재귀 하향 파싱 등은 예측을 잘못하면 되돌아가기(Backtracking)를 해야 해서 최악의 경우 지수 시간이 걸린다. 앞을 몇 개만 내다보고(Look-ahead) 백트래킹 없이 단번에 트리를 만들 수학적 알고리즘이 필요했다.
- **작동 원리**:
  - **LL(k) 파서**: 왼쪽에서 오른쪽으로 읽으며, 최좌단 유도(Left-most derivation) 수행. k개의 토큰을 미리 보고(look-ahead) 어떤 규칙을 적용할지 결정한다. 모호성이 없어야 하며 좌순환(Left Recursion) 규칙이 허용되지 않는다.
  - **LR(k) 파서**: 왼쪽에서 오른쪽으로 읽으며, 최우단 유도의 역순(Right-most derivation in reverse)을 수행한다. 스택에 상태와 토큰을 넣다가(Shift), 규칙이 맞으면 부모 노드로 묶어 줄인다(Reduce).
- **비유**: LL은 "다음에 올 단어를 예측"하는 방식이다. LR은 "일단 읽어두고(Shift) 나중에 문맥이 맞으면 조립(Reduce)"하는 방식이다.
- **구체 예시**: `E -> E + T` 문법이 있을 때, LL 파서는 무한루프(좌순환)에 빠지므로 `E -> T E'`로 문법을 고쳐야 한다. LR 파서는 이런 좌순환 문법도 자연스럽게 Shift-Reduce로 잘 처리한다.
- **흔한 오해·주의점**: "LL은 재귀 하향, LR은 Shift-Reduce 방식"이라고만 외우면 안 된다. 근본 차이는 유도(Derivation) 방향(Top-Down vs Bottom-Up)과 표현 가능한 문법의 크기(LR이 LL보다 넓음)에 있다.

## 연결 개념
- (073) 컴파일러 구조 — 파서가 속한 구문 분석 단계
- AST (추상 구문 트리) — 파서의 최종 산출물

# 📝 【답안용】 시험 답안 템플릿

## 핵심 인사이트 (3줄 요약)

> 1. **본질**: 파서는 컴파일러의 핵심으로, 문맥자유문법(CFG) 기반 토큰 열의 구조적 유효성을 $O(N)$ 선형 시간에 검증하는 알고리즘이다.
> 2. **가치**: Top-Down 방식의 LL 파서는 구현이 직관적(재귀 하향)이고 에러 복구가 용이하며, Bottom-Up 방식의 LR 파서는 표현력이 넓고(대부분의 프로그래밍 언어 커버) 성능이 뛰어나다.
> 3. **판단 포인트**: 언어의 복잡도와 파서 생성 도구(LL: ANTLR, LR: YACC/Bison) 생태계에 맞춰 최적의 구문 분석 전략을 선택해야 한다.

## 출제 의도 및 답안 포인트

| 출제 의도 | 반드시 짚을 핵심 | 감점 회피 포인트 |
|:---|:---|:---|
| 파싱 알고리즘의 동작 방식 차이 이해 | LL(Top-Down, 최좌단 유도), LR(Bottom-Up, 최우단 역도출, Shift/Reduce) | 단순히 '위에서 아래', '아래서 위'라는 일상어만 나열 |
| 적용 문법 범위와 한계 인식 | LR이 LL보다 수용 범위가 넓음, LL은 좌순환 제거 필수 | LL과 LR의 성능/표현력을 동일 선상으로 간주하는 오류 |

> 요약: LL과 LR의 탐색 방향(Top-Down vs Bottom-Up), 유도 방식, 그리고 허용 문법 범위의 차이를 정확히 비교해야 한다.

---

## Ⅰ. 개요 및 필요성

- 개요: 어휘 분석기가 출력한 토큰(Token) 열을 입력으로 받아, 미리 정의된 문법 규칙을 통해 구문 트리(Syntax Tree)를 생성하는 과정 및 알고리즘
- 배경: 백트래킹(Backtracking)이 발생하는 일반 파싱은 비효율적이므로, 문맥을 k개 토큰 앞서 확인(Look-ahead)하여 결정론적으로 구문 트리를 완성하는 체계 필요
- 필요성: 프로그래밍 언어의 구문 오류(Syntax Error)를 신속히 탐지하고, 이후 의미 분석 및 중간 코드 생성을 위한 구조화된 데이터(AST)를 제공하기 위해 필수

---

## Ⅱ. 구조 및 구성요소

```text
Token Stream -> [Parser Engine] -> AST (Abstract Syntax Tree)
                   |
                   +-> LL: 예측 파싱표 기반 (Top-Down 전개)
                   +-> LR: 상태 스택 + Shift/Reduce 테이블 (Bottom-Up 축약)
```

| 구성요소 | 역할 | 특이사항 |
|:---|:---|:---|
| 파싱 테이블 (Parsing Table) | 상태와 입력 토큰에 따라 파서가 취할 다음 행동 지시 | 파서 제너레이터가 문법을 기반으로 자동 생성 |
| 스택 (Stack) | 현재까지 분석된 심볼이나 상태를 저장하는 메모리 구조 | PDA(푸시다운 오토마타) 구조의 구현체 |
| 룩어헤드 (Look-ahead, k) | 파싱 결정을 위해 미리 읽어보는 미래 토큰의 개수 | 통상 k=1 (LL(1), LALR(1))을 실무에서 사용 |

> 요약: LL과 LR 모두 스택과 테이블을 사용하는 공통 구조를 가지나, 테이블의 행동(전개 vs 축약) 방식이 근본적으로 다르다.

---

## Ⅲ. 동작원리 및 흐름도

```text
[LL(1) 동작] 입력 토큰 확인 -> 테이블 참조(비단말 전개 규칙) -> 스택에 우변 Push -> 단말 기호 매칭
[LR(1) 동작] 토큰 스택에 넣음(Shift) -> 규칙 우변 발견 시 좌변 비단말로 변경(Reduce) -> 루트(Accept) 도달
```

- 1단계 [토큰 입력]: 어휘 분석기에서 룩어헤드 버퍼로 토큰을 순차 입력
- 2단계 [테이블 조회]: (LL) 현재 스택 최상단과 토큰 교차점 조회 / (LR) 현재 상태와 토큰 교차점(Action/Goto) 조회
- 3단계 [핵심 처리]: 
  - LL: 선택된 규칙으로 비단말을 확장(Top-Down)
  - LR: 토큰을 쌓다가(Shift), 매칭되면 부모 기호로 축약(Reduce)
- 4단계 [결과/에러]: 최종 Root 도달 시 수락(Accept), 파싱 테이블 빈칸 참조 시 구문 오류(Syntax Error) 처리

> 요약: LL은 시작 심볼에서 목적 문장으로 내려가는 최좌단 유도, LR은 목적 문장에서 시작 심볼로 올라가는 최우단 역도출이다.

---

## Ⅳ. 특징
- [표현 범위의 우위]: LR 문법 집합이 LL 문법 집합을 포함하므로(LL ⊂ LR), LR이 훨씬 복잡하고 다양한 프로그래밍 언어 구문을 충돌 없이 수용 가능
- [구조적 제약]: LL 문법은 좌순환(Left Recursion, $A \rightarrow A\alpha$)과 좌인수분해 미처리 시 무한루프에 빠지므로 문법 변형이 강제됨
- [에러 처리 직관성]: LL 방식(재귀 하향 구현 시)은 콜스택을 활용해 개발자가 에러 위치와 원인을 파악하고 복구 로직을 짜기 쉬움

> 요약: 성능과 표현력은 LR이 우수하나, 오류 메시지 친화도와 수작업 구현 편의성은 LL(재귀 하향)이 유리하다.

---

## Ⅴ. 심화 비교 및 적용 판단

| 비교 축 | LL 파서 | LR 파서 | 선택 기준 |
|:---|:---|:---|:---|
| 파싱 방향 | Top-Down (위에서 아래로) | Bottom-Up (아래서 위로) | 트리를 그리는 접근법 |
| 유도(Derivation) | 최좌단 유도 (Left-most) | 최우단 역도출 (Right-most Reverse) | 알고리즘 토대 |
| 대표 방식/도구 | 재귀 하향, ANTLR, JavaCC | SLR, LALR, Yacc, Bison | 생태계 및 도구 지원 |
| 상태 크기 | 비교적 작고 단순함 | 상태 전이 테이블이 매우 큼 (LALR로 압축) | 메모리 제약 여부 |

> 요약: 일반적인 상용 컴파일러는 표현력이 높은 LALR(1) 기반 도구(Bison 등)를 채택하며, 최근에는 유연한 IDE 연동을 위해 LL(k) 기반(ANTLR)도 혼용된다.

**리스크·대응:**
- [LR 파서의 Shift/Reduce 충돌]: `if-else`의 Dangling Else 문제 등 모호한 문법 → 우선순위 규칙 부여 및 LALR 테이블 압축으로 모호성 해소 (지표: 파서 제너레이터 충돌 경고 0건)
- [LL 파서의 무한루프]: 좌순환 문법($E \rightarrow E+T$) 허용 불가 → 우순환 문법($E \rightarrow TE'$)으로 문법 변환 자동화 (지표: 구문 분석 지연 시간)

**도입 후 점검 지표:**
- 성능/효율: 파싱 테이블 메모리 점유율 및 토큰당 분석 시간 ($O(1)$ 상태 전이)
- 품질/운영: Syntax Error 발생 시 정확한 라인 번호와 기대 토큰(Expected Token) 제시율 100% 보장

---

## Ⅵ. 실무 적용 및 결론

**적용 방안 3개:**
1. [DSL(도메인 특화 언어) 개발]: 사내 설정 파일이나 단순 쿼리 파싱용 DSL 제작 시, 디버깅과 확장이 쉬운 ANTLR(LL 기반) 활용
2. [컴파일러 프론트엔드 구축]: C/C++ 등 복잡한 구문을 가진 시스템 언어의 경우, 강력한 표현력을 가진 Yacc/Bison(LALR 기반)을 활용해 모호성 배제
3. [IDE 인텔리센스 연동]: 에러가 난 불완전한 코드에서도 문맥을 추론(에러 복구)해야 하므로, AST 재구축이 유연한 Recursive Descent(재귀 하향 LL) 방식을 핸드코딩으로 최적화

**결론:**
- 기술사 판단: 파싱 전략은 표현력(LR)과 구현/유지보수 편의성(LL)의 트레이드오프다. 대형 시스템 언어는 LALR을, 가벼운 DSL이나 IDE 도구는 LL 또는 재귀 하향 파서를 선택하는 것이 아키텍처 원칙이다.
- 향후 방향: 최근 프로그래밍 언어 발전(예: C#, Swift, Rust)에서는 파서 생성기 의존도를 낮추고 빠르고 친절한 에러 메시지를 위해 재귀 하향(LL) 방식을 직접 구현하는 수제(Hand-written) 파서 선호도가 높아지고 있다.
