# 📖 【암기용】 개념 완전 이해

> 목적: 구문 분석의 양대 산맥인 하향식(LL)과 상향식(LR) 파서가 트리를 만드는 방향성과 장단점을, 실제 문법과 입력을 손으로 추적하며 완벽히 이해하게 만든다.

## 한눈에
- **개요**: 파서(Parser)는 컴파일러의 2단계인 **구문 분석(Syntax Analysis)**을 수행하는 알고리즘으로, 어휘 분석이 넘긴 토큰 열을 받아 **문맥 자유 문법(CFG)** 규칙에 맞는지 검증하며 **추상 구문 트리(AST)**를 조립한다.
- **왜 필요한가**: `if (a > 0) x = 1;`이라는 토큰 조각들이 괄호 짝 규칙과 주어-동사 문법(문맥 자유 문법)에 부합하는지, 사람이 눈으로 보듯 대충 판단할 수 없다. 컴파일러는 결정론적 스택 기계로 이를 기계적으로 검증하고 트리 구조로 확정해야 다음 단계(의미 분석)가 안전하게 작업할 수 있다.
- **핵심 직관**: **LL 파서(하향식)**는 최상단 '문장'에서 시작해 "이건 if문일 거야"라고 다음 토큰을 보고 짐작하며 위에서 아래로 가지를 뻗어 내려가는 방식이고, **LR 파서(상향식)**는 토큰(잎사귀)을 스택에 하나씩 쌓다가 규칙에 맞으면 묶어 올리며 "어, 묶고 보니 if문이 됐네" 하고 아래에서 위로 뿌리(문장)까지 조립해 올라가는 방식이다.

## 핵심 용어 정리

| 용어 | 의미 | 비유 |
|:---|:---|:---|
| 구문 분석 (Syntax Analysis) | 파서가 속한 상위 단계. 토큰 열이 문법에 맞는지 검증해 AST를 만드는 컴파일러 2단계 | 단어 카드를 문법 규칙대로 줄 세우는 작업 |
| 문맥 자유 문법 (CFG) | 파서가 검증 기준으로 삼는 규칙 집합. `E → E + T`처럼 좌변 1개 비단말 기호가 우변 문자열로 치환되는 생성 규칙 | 요리 레시피 — "이 재료 조합이면 이 요리가 된다"는 규칙표 |
| AST (추상 구문 트리) | 파서의 최종 산출물. 토큰들이 문법 규칙에 따라 계층적으로 조립된 트리 | 문장의 주어-동사-목적어 구조도 |
| LL 파서 | Left-to-right 스캔, Leftmost derivation(좌단 유도)으로 위(시작 기호)에서 아래(토큰)로 예측해 내려가는 하향식 파서 | 완성될 레고 도면을 보며 위층부터 아래층으로 맞춰가는 것 |
| LR 파서 | Left-to-right 스캔, Rightmost derivation을 역순으로 밟아 아래(토큰)에서 위(시작 기호)로 묶어 올라가는 상향식 파서 | 바닥 블록부터 쌓아 올려 도면에 맞는 완성품을 만드는 것 |
| Look-ahead | 파서가 다음에 어떤 규칙을 적용할지 판단하기 위해 미리 훔쳐보는 토큰 개수. LL(1)·LR(1)은 1개를 본다는 뜻 | 다음 카드를 한 장 미리 보고 패를 결정하는 카드 게임 |
| 좌측 재귀 (Left Recursion) | `E → E + T`처럼 규칙 우변 맨 앞에 자기 자신이 다시 나오는 형태 | 제자리에서 "나는 나다"를 계속 되뇌며 한 발짝도 못 나가는 상태 |
| Shift | LR 파서가 입력 토큰 1개를 그대로 스택 위에 쌓는 동작 | 벽돌을 하나 더 쌓기 |
| Reduce | LR 파서가 스택 맨 위 패턴이 문법 규칙 우변과 일치하면, 그 규칙의 좌변 기호 하나로 압축 치환하는 동작 | 쌓은 벽돌 묶음을 완성된 블록 1개로 인정하기 |
| 파싱 테이블 | LL은 "비단말+다음토큰 → 적용 규칙", LR은 "상태+토큰 → Shift/Reduce/Accept/Error"를 미리 계산해 둔 조회표 | 신호등 규칙표 — 현재 상태와 신호를 보고 다음 행동을 즉시 결정 |
| 재귀 하향 파서 (Recursive Descent) | 문법 규칙 하나마다 함수 하나를 대응시켜 직접 손으로 짜는 LL 파서 구현 방식 | 목차 항목마다 담당자를 정해 순서대로 호출하는 방식 |
| Yacc/Bison, ANTLR | LR·LL 파싱 테이블과 파서 코드를 문법 정의(BNF)로부터 자동 생성해 주는 파서 생성기 도구 | 레시피만 넣으면 조리 순서표를 자동으로 뽑아주는 기계 |
| Shift/Reduce 충돌 | LR 파서가 다음 토큰에서 Shift할지 Reduce할지 두 선택이 동시에 유효해 결정할 수 없는 상태 | 갈림길에서 두 표지판이 동시에 "직진"과 "정지"를 가리키는 상황 |

## 깊이 이해

### LL(1) 파싱을 손으로 끝까지 추적하기 (예제)
- 좌측 재귀를 제거한 문법을 쓴다: `E → T E'`, `E' → + T E' | ε`, `T → id`.
- 입력: `id + id`. LL 파서는 스택(왼쪽이 top)과 입력을 맞대고 "예측 후 매치"를 반복한다.

| 단계 | 스택 | 남은 입력 | 동작 |
|:---:|:---|:---|:---|
| 1 | E | id + id $ | 다음 토큰이 id → `E → T E'` 규칙 예측, 스택을 `T E'`로 치환 |
| 2 | T E' | id + id $ | 다음 토큰이 id → `T → id` 예측, 스택을 `id E'`로 치환 |
| 3 | id E' | id + id $ | 스택 top(id)과 입력(id) 일치 → 둘 다 소모(Match) |
| 4 | E' | + id $ | 다음 토큰이 + → `E' → + T E'` 예측, 스택을 `+ T E'`로 치환 |
| 5 | + T E' | + id $ | + 매치 → 소모 |
| 6 | T E' | id $ | 다음 토큰이 id → `T → id` 예측 |
| 7 | id E' | id $ | id 매치 → 소모 |
| 8 | E' | $ | 다음 토큰이 $ → `E' → ε` 예측(더 볼 게 없다는 뜻) |
| 9 | (빈 스택) | $ | 스택·입력 모두 소진 → Accept |

- 9단계 만에 짐작(Predict)과 소모(Match)만 반복해 트리가 완성된다. 만약 문법이 `E → E + T`(좌측 재귀)였다면 1단계에서 스택 top이 다시 `E`가 되어 같은 규칙을 무한히 예측하며 토큰을 하나도 소모하지 못하는 무한루프(재귀 하향 구현에서는 스택 오버플로 크래시)에 빠진다. 이것이 좌측 재귀 제거가 LL의 필수 전처리인 이유다.

### LR 파싱을 손으로 끝까지 추적하기 (예제)
- 문법: `S → ( S ) | a`. 입력: `( a )`.

| 단계 | 스택 | 남은 입력 | 동작 |
|:---:|:---|:---|:---|
| 1 | $ | ( a ) $ | Shift `(` |
| 2 | $ ( | a ) $ | Shift `a` |
| 3 | $ ( a | ) $ | 스택 top(a)이 규칙 `S → a`의 우변과 일치 → Reduce (a를 S로 치환) |
| 4 | $ ( S | ) $ | Shift `)` |
| 5 | $ ( S ) | $ | 스택 top(`( S )`)이 규칙 `S → ( S )`의 우변과 일치 → Reduce |
| 6 | $ S | $ | 스택에 시작 기호 S만 남고 입력도 비었음 → Accept |

- LR은 미리 규칙을 짐작하지 않고, 일단 쌓다가(Shift) 패턴이 맞아떨어지는 순간에만 압축(Reduce)한다. 그래서 짐작이 틀려 되돌아갈 일이 없고, LL이 감당 못 하는 더 넓은 문법 집합을 처리할 수 있다.

### 왜 LR이 LL보다 표현력이 넓은가
- LL은 "다음 토큰 1개만 보고 어떤 규칙을 펼칠지" 그 자리에서 확정해야 하므로, 같은 접두어로 시작하는 규칙이 여럿이면(좌측 인수분해 필요) 또는 좌측 재귀가 있으면 예측이 불가능하다.
- LR은 이미 스택에 쌓인 전체 문맥(이전에 Shift/Reduce한 이력)을 상태로 들고 있다가 판단하므로, 훨씬 더 많은 문맥 정보를 활용해 결정할 수 있다. 그 대신 이 상태 전이 표(파싱 테이블)가 손으로 짤 수 없을 만큼 커져서 Yacc/Bison 같은 자동 생성 도구가 필수다.

### 비유
- LL 파서는 완성될 레고 도면을 1번부터 차근차근 보며 위층에서 아래층으로 예측해 맞추는 것이고, LR 파서는 무작정 바닥부터 블록을 쌓고(Shift) 합치다(Reduce) 보니 도면에 맞는 완성품 구조로 끝나는 것과 같다.

### 흔한 오해
- "LR이 LL보다 항상 빠르다"는 오해가 있지만, 둘 다 입력 토큰 수에 비례하는 $O(n)$ 시간에 끝난다. 차이는 속도가 아니라 **처리 가능한 문법의 범위**와 **구현 난이도**다.

## 연결 개념
- 구문 트리 (Syntax Tree / AST) — 파서가 성공적으로 분석을 마치고 뱉어내는 뼈대 형태의 계층적 데이터 구조
- 문맥 자유 문법 (Context-Free Grammar) — LL/LR 파서가 검증하는 대상 문법 (촘스키 계층 Type 2)
- 좌측 재귀 (Left Recursion) — `A → Aα`와 같이 자기 자신을 바로 부르는 규칙. LL 파서는 이를 만나면 하향 예측 중 무한루프에 빠지므로 사전 문법 변환이 반드시 필요하다

# 📝 【답안용】 시험 답안 템플릿

> 목적: 시험장에서 25분에 그대로 쓰는 답안 양식. 작성방식(추상표현 금지·수치·도식·문제유형 전환)을 엄격히 지킨다.
> 핵심: 구문 분석의 Top-Down(LL)과 Bottom-Up(LR) 메커니즘을 대조(예측 vs 환원)하고, 파서의 문법 표현력(LR 우세)과 디버깅 구현 용이성(LL 우세) 간의 트레이드오프를 제시한다.

## 핵심 인사이트 (3줄 요약)

> 1. **본질**: 파서(Parser)는 어휘 분석기가 넘긴 토큰 열이 프로그래밍 언어의 문맥 자유 문법(BNF)에 적합한지 결정론적 스택 기계(PDA)로 검증하여 구문 트리를 생성하는 알고리즘이다.
> 2. **가치**: 시작 기호에서 단말 기호로 하향 예측하는 LL 방식은 수동 코드 구현이 직관적이며, 단말 토큰부터 조립 상향하는 LR 방식은 복잡한 언어 문법 대부분을 포괄할 수 있는 강력한 표현력을 제공한다.
> 3. **판단 포인트**: 현대 범용 컴파일러는 Yacc/Bison 도구를 통한 강력한 LALR(상향식) 파서를 주로 활용하나, 오류 메시지 튜닝과 가벼운 DSL 파서 제작 시에는 ANTLR 프레임워크 중심의 LL 계열 파서를 전략 채택하기도 한다.

## 출제 의도 및 답안 포인트

| 출제 의도 | 반드시 짚을 핵심 | 감점 회피 포인트 |
|:---|:---|:---|
| 구문 분석(Syntax) 트리 메커니즘 차이 검증 | LL(Leftmost, 하향식 트리) vs LR(Rightmost Reverse, 상향식 병합) 방향성 | LL/LR 영문 약자 해석을 생략하거나 스택 매커니즘 없이 모호하게 기술 |
| 파싱 알고리즘별 문법 한계와 제약조건 | LL 파서의 좌측 재귀(Left Recursion) 금지 제약 및 전처리(문법 변환) 필요성 | 단지 LR 파서가 하향식 LL 파서보다 무조건 속도가 빠르다고 단정하는 오류 |
| 파서 오토마타 동작(Shift/Reduce) 원리 | 상향식(LR) 파서의 상태 전이 액션 구분 (Shift, Reduce, Accept, Error) | 구문 파서 트리를 어휘 분석(토크나이저 정규식) 동작과 혼동하여 서술 |

> 요약: 예측(Predict) 하향 중심의 LL 파서와 이동-환원(Shift-Reduce) 상향 중심의 LR 파서 오토마타 구조를 대조하고, 좌측 재귀 한계 유무 등 수용성 차이를 명시해야 한다.

## Ⅰ. 개요 및 필요성

- 정의: 입력 토큰 스트림을 받아 정의된 문맥 자유 문법(CFG) 치환 규칙에 따라 구문적 무결성을 검증하고 추상 구문 트리(AST) 뼈대를 구성하는 컴파일러 핵심 모듈
- 배경: 모든 경우의 수를 비결정적으로 시도하는 파싱은 역추적(Backtracking) 탓에 시간 복잡도가 지수 $O(C^N)$로 폭증하여 수만 라인 실시간 컴파일이 원천 불가능
- 필요성: Look-ahead(앞선 K개 토큰을 미리 확인) 버퍼를 도입하여 파서의 다음 상태 전이를 유일하게 결정짓는 $O(N)$ 성능의 결정론적 파싱 기법(LL, LR) 필수 도입

## Ⅱ. 구문 파서 분류 및 트리 생성 구조

```text
Syntax Analysis (Parser) 아키텍처
  +-> Top-Down (하향식 트리) : Root -> Leaf.  LL 파서 (테이블 예측 기반)
  +-> Bottom-Up (상향식 트리): Leaf -> Root.  LR 파서 (스택 이동-환원 기반)
```

| 파서 분류명 | 약자 메커니즘 의미 | 구문 트리 탐색 방향 | 주요 작동 특이사항 |
|:---|:---|:---|:---|
| **LL(k) 파서** | **L**: Left-to-right (좌측 스캔)<br>**L**: Leftmost derivation (좌단 유도) | Root(시작 기호)에서 출발하여 아래쪽 Leaf(단말 기호) 방향으로 하향 확장 | 파싱 테이블을 보고 어떤 규칙을 적용해 뻗어갈지 먼저 '예측(Predict)' |
| **LR(k) 파서** | **L**: Left-to-right (좌측 스캔)<br>**R**: Rightmost derivation Reverse (우단 유도 역순) | Leaf(입력 토큰)에서 차례로 묶어(Reduce) 위쪽 Root로 상향 병합 조립 | 상태 스택(State Stack) 기반 이동과 치환 반복, 범용 문법 대다수 커버 |

> 요약: 파싱 트리를 구성할 때 LL은 위에서 아래로 예측 가지를 치며 내려오고, LR은 아래에서 토큰을 주워 모아 위로 병합해 기둥을 완성한다.

## Ⅲ. 동작원리 메커니즘 및 파싱 흐름도

```text
[LL 동작 사이클] (1)토큰 확인 -> (2)파싱 테이블 참조 -> (3)생성규칙 스택 Push(예측) -> (4)단말 기호 매칭(Match) 삭제
[LR 동작 사이클] (1)토큰 스택 Push(Shift) -> (2)우변 핸들(Handle) 패턴 일치 탐색 -> (3)비단말 기호 치환(Reduce) -> (4)Accept
```

| 단계 흐름 | LL 파서 메커니즘 (Top-Down) | LR 파서 메커니즘 (Bottom-Up) |
|:---:|:---|:---|
| 파싱 액션 원리| **Predict (예측) 및 Match (일치)** | **Shift (이동) 및 Reduce (환원 치환)** |
| 1단계 전이 | 스택 Top 요소가 비단말 기호면 테이블을 보고 적용 규칙을 찾아 역순 스택 푸시 | 입력 스트림 앞단 토큰 1개를 상태 버퍼 스택 최상단에 단순 PUSH (Shift 동작) |
| 2단계 전이 | 스택 Top 요소가 단말 토큰이면 실제 입력 토큰과 비교(Match)하여 일치 시 쌍방 소모 제거 | 스택 최상단 패턴 묶음이 문법 규칙 우변(Handle)과 일치 시 좌변 비단말 기호 한 개로 치환 (Reduce) |
| 3단계 종료 | 예측 스택과 입력 스트림이 동시에 비워지면 뼈대 파싱 성공 판정 | 환원을 거듭해 스택에 시작 기호($S$)만 남고 입력이 비면 최종 Accept 승인 |
| 에러 처리 | 테이블 칸(Entry) 참조 시 유효 규칙이 없으면 에러 복구 모드 즉각 진입 | Shift/Reduce 상태 머신 중 유효 액션 부재 시 패닉 에러 복구 전개 |

> 요약: LL은 스택에 미리 규칙을 펴 놓고 들어오는 토큰과 소모전(Match)을 치르는 방식이며, LR은 들어오는 토큰을 쌓아 두고(Shift) 거대 패턴으로 압축 치환(Reduce)하는 방식이다.

## Ⅳ. 특징 및 아키텍처 한계 트레이드오프

| 비교 분석 축 | LL(1) 파서 (하향식, Top-Down) | LR(1) / LALR 파서 (상향식, Bottom-Up) | 백엔드 설계 판단 기준 |
|:---|:---|:---|:---|
| 문법 표현력 크기| 좁음 (LR 집합에 논리적으로 완전 포함됨) | 매우 넓고 강력함 (대다수 C/Java CFG 커버 방어력 보장) | 언어 설계 시 스펙 문법의 제약 우회 난이도 |
| 좌측 재귀 허용도| **절대 불가** (무한 예측 루프 발생 치명상) | 역추적 없이 유연하게 허용 및 정상 처리 가능 | $A \rightarrow A\alpha$ 패턴의 전처리(좌측인수분해 등) 문법 튜닝 여부 |
| 엔진 구현 난이도| 상대적으로 직관적 (재귀 하향 방식 수동 하드코딩 용이) | 오토마타 구조가 방대하여 Yacc 등 제너레이터 자동화 필수 강제 | 컴파일 에러 메시지 사용자 튜닝 통제권 |

> 요약: LL 파서는 좌측 재귀 무한루프 취약점을 피하기 위해 억지 문법 변환 공수가 따르지만 개발 통제력이 높고, LR 파서는 도구 의존도가 강하나 파싱 포용력이 압도적이다.

## Ⅴ. 심화 비교 및 파싱 리스크 모호성 통제

| 비교 축 | 수동 구현 (Recursive Descent, 손코딩) | 자동 생성 (Parser Generator: Yacc/ANTLR) | 선택 기준 |
|:---|:---|:---|:---|
| 구현 방식 | 문법 규칙마다 함수를 직접 작성해 재귀 호출로 하향 예측 수행 | BNF/EBNF 문법 파일을 입력하면 파싱 테이블·상태 머신을 자동 산출 | 문법 규모가 작고 커스텀 제어가 필요하면 수동, 표준 CFG 전반을 커버해야 하면 자동 |
| 문법 변경 대응 | 규칙 추가·수정 시 해당 함수 코드를 수작업 재작성 | 문법 파일 갱신 후 재생성(Regenerate)만 하면 파싱 테이블 자동 반영 | 문법이 자주 바뀌는 DSL·설정 언어는 자동 생성이 유리 |
| 에러 메시지 품질 | 개발자가 원하는 지점에 임의 진단 메시지 삽입 가능 | 제너레이터가 산출하는 범용 상태 오류 메시지, 커스터마이징 제약 | LSP처럼 정밀한 오류 위치·설명이 필요하면 수동 구현이 우세 |

> 요약: 표준 CFG 전체를 안정적으로 커버해야 하면 자동 생성 파서를, 진단 메시지 통제권과 소규모 DSL 대응이 우선이면 수동 재귀 하향 파서를 선택한다.

| 발생 가능 리스크 | 트리 모호성 유발 원인 | 대응 통제 방안 아키텍처 | 위험 통제 지표 |
|:---|:---|:---|:---|
| 파서 Shift/Reduce 충돌 | LR 스택 상태에서 다음 토큰을 스택에 Shift 할지 Reduce 묶을지 두 가지 경로가 공존(Dangling Else 문제) | 파서 제너레이터 지시어에 연산자 우선순위(Precedence)/결합성 강제 부여로 의사결정 고정 | 문법 테이블 Build 시점 Shift/Reduce Conflict 0건 |
| 파서 Reduce/Reduce 충돌 | LR 스택 최상단 패턴이 두 개 이상의 다른 비단말 문법 규칙 우변과 동시 일치하는 최악의 조건 | 파싱 자체 불가 설계 결함이므로 문법 구조 자체(CFG 단계)를 재설계 병행 개편 강제 | 제너레이터 Fatal Error 정지 발생 유무 |
| LL 파서 좌측 재귀 무한 예측 | 규칙 $A \rightarrow A + B$ 적용 시 토큰 소모 없이 자기 자신을 계속 스택에 예측(Predict) 푸시 루프 | 좌측 재귀 구조를 우측 재귀 동치 형태($A \rightarrow B A'$)로 문법 강제 리팩토링 (Elimination) | 재귀 하향 파서 Stack Overflow 셧다운 방어율 |

> 요약: 실무 파서 설계 시 하향식 LL 파서는 좌측 재귀 루프를 튜닝 억제해야 하고, 상향식 LR 파서는 모호성에 의한 Reduce 충돌 결함을 최우선 디버깅해야 한다.

## Ⅵ. 실무 적용 및 결론

**적용 방안 3개:**
1. 범용 랭귀지 상향식 컴파일러 구축: C/C++ 등 문맥 조건이 얽힌 복잡한 CFG 문법 언어의 프론트엔드 제작 시, 수동 코딩을 배제하고 Yacc(Bison) 제너레이터를 투입해 상태가 압축된 LALR(Look-Ahead LR) 상향식 파서를 자동 생성
2. 커스텀 DSL/스크립트 하향식 파서 구현: 룰 엔진 설정 파일(Config)이나 사내 특화 쿼리 검증기 제작 시, ANTLR 프레임워크를 기반으로 LL(*) 하향 파서를 세팅하여 직관적 구조 파악과 AST 트리 순회용 리스너(Listener) 이점 선점
3. 컴파일러 에러 진단(Diagnostics) 최적화 포팅: Clang 컴파일러 인프라 설계처럼, $O(N)$ 고속 처리를 지키면서도 사용자 관점의 세밀한 "세미콜론 누락" 에러 라인 위치 피드백 통제권을 강화하기 위해 수동으로 튜닝 제작된 재귀 하향(Recursive Descent) LL(1) 파서 엔진을 강제 이식

**결론 (2줄):**
- 기술사 판단: 파서 아키텍처 설계는 표현 수용력 극대화가 우선일 때 LALR(상향식) 제너레이터 루트를 밟고, 오류 위치 진단의 유연성과 커스텀 DSL의 통제성 장악이 우선일 때 재귀적 LL(하향식) 모듈을 선택하는 양립 구조다.
- 향후 방향: 전통적인 단발성 컴파일 파이프라인에서 벗어나 최근 LSP(Language Server Protocol) 기반 IDE 실시간 구문 검증 시장에서는 입력 중 오류가 나도 끊기지 않는 점진적 부분 파싱(Incremental Parsing)이 유리한 LL 계열 프레임워크가 부상하고 있다.
