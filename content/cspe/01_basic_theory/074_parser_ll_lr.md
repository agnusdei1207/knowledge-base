## 미리 알고가기

- 하향식 파싱($Top-down$): 트리의 최상단 루트 노드(시작 기호)로부터 출발하여 단말 기호 방향으로 규칙을 전개해 나가는 구문 분석 방식임
- 상향식 파싱($Bottom-up$): 입력받은 문자열(단말 기호)을 시작으로 위로 묶어 올라가며 최상단 루트 기호로 환원($Reduce$)하는 구문 분석 방식임
- 좌재귀($Left$ $Recursion$): 생성 규칙이 $A \rightarrow A\alpha$ 와 같이 자기 자신을 좌변의 첫 기호로 참조하는 구조로, 하향식 파싱 시 무한 루프를 유발함
- 시프트-리듀스($Shift-Reduce$): 상향식 파서의 기본 동작으로, 입력 토큰을 스택에 밀어 넣는(Shift) 동작과 스택 상단 기호들을 비단말 기호로 치환하는(Reduce) 동작임

## Ⅰ. 개요

- **정의/개념**: LL 파서와 LR 파서는 프로그래밍 언어의 문법 구조를 검증하는 구문 분석기의 두 갈래로, LL은 입력의 왼쪽부터 보며 하향식으로 예측하는 파서이고, LR은 상향식으로 스택에 토큰을 쌓았다가 축약하는 파서임
- **배경/필요성**: 텍스트 형태의 프로그램 구조를 기계가 실행 가능한 트리 구조($AST$)로 빈틈없이 전격 번역해 내기 위해, 수학적으로 충돌이 없는 결정론적 파싱 알고리즘 설계가 필요해짐

## Ⅱ. 특징

- LL 파서(주로 $LL(k)$)는 사람이 글을 읽는 방식과 유사한 하향식 추론을 사용하여 구현이 직관적이며, 손으로 직접 코딩하는 '재귀 하강 파서($Recursive$ $Descent$ $Parser$)'의 근간이 됨
- LR 파서(주로 $LR(k)$, $LALR$)는 스택의 상태 천이를 기록한 파싱 테이블에 의존하므로 사람이 손으로 직접 짜기 어렵지만, 거의 모든 문맥 자유 문법을 수용할 수 있을 정도로 표현력이 극도로 뛰어남
- LL은 생성 규칙의 첫 문자열이 겹치지 않아야 하므로 좌인수분해($Left$ $Factoring$)와 좌재귀 제거 등의 문법 변환이 필히 선행되어야 함

## Ⅲ. 종류 및 비교

| 판단 기준 | 하향식 LL 파서 (LL Parsing) | 상향식 LR 파서 (LR Parsing) |
|:---|:---|:---|
| **이름의 의미** | 좌에서 우로 읽고($L$), 가장 왼쪽 유도($L$)를 적용 | 좌에서 우로 읽고($L$), 가장 오른쪽 유도 역순($R$) 적용 |
| **파싱 원리** | 루트에서 시작하여 리프 노드로 예측 전개 | 리프(입력)에서 스택에 쌓으며 루트로 환원 |
| **핵심 액션** | 테이블 매칭 후 생성 규칙 적용 ($Expand$) | 시프트($Shift$), 리듀스($Reduce$), 수용($Accept$) |
| **문법 수용력** | 비교적 낮음 (좌재귀 문법 처리 불가) | 매우 높음 (대부분의 실무 프로그래밍 언어 수용) |
| **구현 방식** | 재귀적 함수 호출로 직접 구현 가능 | 파서 생성 도구($Yacc, Bison$)로 테이블 자동 생성 |

> 요약: LL은 '위에서 아래로 펼치기'이고, LR은 '스택에 쌓아서 위로 합치기'임.

## Ⅳ. 구성요소 및 구조

| 구성요소 | 설명 |
|:---|:---|
| 파싱 스택 | 파서의 현재 진행 맥락과 상태(LR의 경우 스테이트 번호)를 일시 저장하는 메모리 공간임 |
| 파싱 테이블 | 현재 상태와 입력 토큰(Lookahead)을 대조하여 취해야 할 다음 동작을 리턴해 주는 테이블임 |
| $First$ & $Follow$ | LL 파싱 테이블 구축 시 각 비단말 기호가 시작할 수 있는 토큰 집합과 그 뒤를 잇는 토큰 집합임 |
| $Shift/Reduce$ 충돌 | LR 파서에서 스택에 더 쌓아야 할지($Shift$), 현재 뭉치를 치환해야 할지($Reduce$) 결정을 못 내리는 문법 오류 상태임 |

```text
[ LR 파서의 작동 원리 모형 ]
Input Buffer:  [ identifier ] [ + ] [ number ] ... 
                   |
                   v (Read Token / Lookahead)
[ Parser Stack: State 0, identifier ] ---> (Look up Parsing Table) ---> Action: Reduce by (Factor -> id)
```

## Ⅴ. 원리 및 절차 흐름도

```text
+-------------+     +--------------+     +-------------+     +-------------+
| 토큰 입력   | --> | 테이블/룩어헤드| --> | 스택 상태천이| --> | 구문 트리도출|
+-------------+     +--------------+     +-------------+     +-------------+
```

1. **포인터 이동** — 입력 버퍼로부터 파서 지시자가 다음 토큰을 읽고, 파서 방식에 따라 지정된 수($k$)만큼의 앞선 토큰(Lookahead)을 확보함
2. **테이블 조회** — 현재 파서 스택의 최상단 상태와 들어온 토큰의 결합 조합을 파싱 테이블(액션 및 고투 테이블)에서 검색함
3. **상태 천이 수행** — 액션 규칙에 따라, LL 파서는 현재 기호를 하위 규칙으로 대입 분기하고, LR 파서는 스택에 넣거나($Shift$) 규칙에 부합하는 만큼 스택을 터트려 축약($Reduce$)함
4. **검증 완료** — 모든 입력 버퍼를 다 소모하고 스택에 시작 기호($S$) 또는 성공 수용 상태($Accept$)만 남을 때까지 반복함

## Ⅵ. 실무 적용 및 유의점

1. 문법 명세 작성 시 LR 파서에서 '이중 정의'로 인해 $Shift/Reduce$ 충돌이나 $Reduce/Reduce$ 충돌이 발생하면 파서가 오동작하므로, 연산자 우선순위($Precedence$)와 결합 법칙($Associativity$)을 테이블 생성기에 명확히 선언해 주어야 함
2. 파서 개발 시 예외 문자열이 들어왔을 때 즉각 멈추는 대신, 가장 가까운 동기화 토큰(예: 닫는 괄호 `)`나 세미콜론 `;`)이 나올 때까지 입력 스택을 비우고 파싱을 재시작하는 '패닉 모드($Panic$ $Mode$)' 복구 로직을 장착해야 한 번의 컴파일에 여러 에러를 찾아낼 수 있음

## Ⅶ. 결론

- 파서는 프로그래밍 언어의 뼈대를 조립하는 컴퓨터 공학의 조립 라인이며, 설계자는 개발할 언어의 구조적 복잡도와 파서 제네레이터 도구와의 호환성을 검토하여 충돌 없는 최적의 구문 분석 테이블을 구현해야 함
