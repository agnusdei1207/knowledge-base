# 📖 【암기용】 개념 완전 이해
> 목적: 문맥 자유 문법을 처음 봐도 완전히 이해하게 만든다. 시험 답안 양식이 아니라, 이해를 위한 친절한 설명이다.

## 한눈에
- **개요**: 비단말 하나를 다른 문자열로 치환해 중첩 구조를 생성하는 문법
- **왜 필요한가**: 프로그래밍 언어의 괄호, 블록, 수식 우선순위처럼 재귀 구조를 표현해야 함
- **핵심 직관**: 문자열을 왼쪽에서 오른쪽으로 읽되, 아직 닫히지 않은 구조를 스택에 기억하는 문법임
## 깊이 이해
- **배경·문제의식**: 정규 언어는 현재 상태만 기억하므로 괄호 개수 일치나 재귀 호출 구조를 표현하지 못함
- **작동 원리**: CFG는 `A -> α` 형태로 비단말 1개를 단말·비단말 문자열로 바꾼다. 시작기호에서 반복 치환하면 파스 트리와 문장이 생성됨
- **비유**: 수학식 괄호를 열 때마다 메모를 쌓고 닫을 때 하나씩 제거하는 방식과 같음
- **구체 예시**: `S -> (S)S | ε`는 `()`, `(())`, `()()`를 생성하며 스택 높이는 최대 중첩 깊이와 같음
- **흔한 오해·주의점**: CFG가 모든 언어 구조를 처리하지는 못함. `a^n b^n c^n`처럼 세 구간 개수를 동시에 맞추는 언어는 문맥 민감 영역임
## 연결 개념
- 파스 트리(Parse Tree) — 문장 구조의 계층 표현
- 푸시다운 오토마타(PDA) — CFG의 인식 모델
- LL/LR 파서 — CFG를 실제 컴파일러에 적용하는 구문 분석기

# 📝 【답안용】 시험 답안 템플릿

> 목적: 시험장에서 25분에 그대로 쓰는 답안 양식. 작성방식(추상표현 금지·수치·도식·문제유형 전환)을 엄격히 지킨다.

## 핵심 인사이트 (3줄 요약)
> 1. **본질**: CFG는 `A -> α` 생성 규칙으로 재귀·중첩 구조를 표현하는 형식 문법임
> 2. **가치**: 컴파일러 구문 분석에서 프로그램 문장을 파스 트리로 변환하는 기준을 제공함
> 3. **판단 포인트**: 모호성, 좌재귀, FIRST/FOLLOW 충돌을 제거해야 LL/LR 파서 적용 가능함

---

## Ⅰ. 개요 및 필요성

문맥 자유 문법은 비단말 기호 하나를 문자열로 치환해 문장 구조를 생성하는 문법이다. 프로그래밍 언어는 조건문·반복문·수식처럼 계층 구조를 가지므로 정규식만으로 표현할 수 없다. CFG는 구문 분석기와 언어 명세의 공통 기준임

---

## Ⅱ. 구조 및 구성요소

```text
G = (V, T, P, S)
비단말 V -> 생성규칙 P -> 단말열 T
시작기호 S -> 규칙 적용 -> 파스 트리
```

| 구성요소 | 역할 | 특이사항 |
|:---|:---|:---|
| V 비단말 | 구문 범주 표현 | Expr, Stmt, Block |
| T 단말 | 실제 토큰 표현 | id, num, `+`, `(` |
| P 생성규칙 | 치환 규칙 집합 | `A -> α`, 좌재귀 점검 |
| S 시작기호 | 전체 문장 출발점 | Program 또는 Expr |

> 요약: CFG는 비단말·단말·생성규칙·시작기호 4요소로 문장 생성과 구문 분석 기준을 제공함

---

## Ⅲ. 동작원리 및 흐름도

```text
시작기호 S -> 생성규칙 선택 -> 비단말 치환 -> 단말열 생성
규칙 적용 이력 -> 파스 트리 구성 -> 입력 수락/거부
```

| 단계 | 처리 내용 | 검증 기준 |
|:---:|:---|:---|
| 1 | 토큰열 입력 | 어휘 분석 결과와 단말 T 일치 |
| 2 | 시작기호에서 규칙 선택 | FIRST/FOLLOW 또는 ACTION/GOTO 사용 |
| 3 | 비단말을 반복 치환 | 스택 top과 입력 토큰 매칭 |
| 4 | 파스 트리 생성·수락 | 입력 종료, 스택 공백 또는 수락 상태 |

> 요약: CFG 파싱은 입력 토큰과 스택 상태를 대조하며 생성규칙 적용 순서를 파스 트리로 남기는 과정임

---

## Ⅳ. 특징

| 구분 | 정규 문법 | 문맥 자유 문법 | 수치·판단 기준 |
|:---|:---|:---|:---|
| 생성 규칙 | `A -> aB`, `A -> a` | `A -> α` | 우변 길이 제한 없음 |
| 인식 모델 | 유한 오토마타 | 푸시다운 오토마타 | 스택 1개 사용 |
| 표현 대상 | 토큰 패턴 | 중첩·재귀 구조 | 괄호 깊이 n 처리 |
| 파싱 비용 | O(n) | LL/LR O(n), 일반 CYK O(n^3) | 언어 설계는 결정적 CFG 선호 |

> 요약: CFG는 스택을 사용해 정규 언어보다 넓은 중첩 구조를 표현하되, 파서 충돌 관리가 필수임

---

## Ⅴ. 심화 비교 및 적용 판단

| 비교 축 | 기존/대안 | 본 키워드 | 선택 기준 |
|:---|:---|:---|:---|
| 표현력 | 정규 문법 | CFG | 괄호·블록·재귀 구조 포함 시 |
| 비용/성능 | 일반 CYK 파싱 | LL/LR 결정적 파싱 | 컴파일러는 O(n) 파싱 가능 문법 선호 |
| 운영/위험 | 모호 문법 방치 | FIRST/FOLLOW·ACTION/GOTO 검증 | 충돌 0건, 오류 위치 추적 필요 |

> 요약: CFG는 중첩 표현이 필요할 때 선택하되, 실무 파서는 결정적 LL/LR 조건을 맞춰야 함

| 리스크 | 원인 | 대응 방안 | 확인 지표 |
|:---|:---|:---|:---|
| 모호성 | 한 문장에 파스 트리 2개 이상 | 우선순위·결합규칙 명시 | shift/reduce conflict 0건 |
| 좌재귀 충돌 | LL 파서가 무한 재귀 | 좌재귀 제거, left factoring | FIRST/FOLLOW 충돌 0건 |
| 자원 고갈 | 깊은 중첩 입력 | 길이 1MB, 깊이 1,000 제한 | 파싱 시간 p99, 최대 스택 깊이 |

> 요약: CFG 적용 리스크는 문법 충돌과 중첩 입력이며, 충돌 수와 스택 깊이로 통제함

| 점검 항목 | 목표 기준 | 측정 방법 |
|:---|:---|:---|
| 문법 품질 | 모호성·좌재귀 제거 | parser generator 리포트 |
| 파싱 성능 | 결정적 파서 O(n) | 토큰 수별 벤치마크 |
| 오류 진단 | 오류 위치 line/column 제공 | 부정 입력 테스트 |

> 요약: CFG 성공 여부는 충돌 0건, O(n) 파싱, 오류 위치 진단으로 판단함

---

## Ⅵ. 실무 적용 및 결론

**적용 방안 3개:**
1. 언어 문법 설계: EBNF로 문법 작성 후 좌재귀 제거, 공통 접두어 인수분해로 LL 파서 충돌 축소
2. 컴파일러 구현: Lexer는 정규식, Parser는 CFG로 분리하고 AST 노드 수·파싱 오류 위치를 진단 지표로 관리
3. 보안 파서 적용: 입력 길이 1MB 제한, 재귀 깊이 1,000 제한, 오류 복구 규칙으로 파서 자원 고갈 차단

**결론 (2줄):**
- 기술사 판단: 토큰 인식은 정규 문법, 구문 구조는 CFG, 의미 제약은 타입 검사 단계로 분리함
- 향후 방향: DSL·API 스키마 설계에서 CFG 기반 명세와 자동 파서 생성으로 구현 일관성을 확보해야 함
