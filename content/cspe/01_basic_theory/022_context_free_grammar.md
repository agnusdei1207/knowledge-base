## 미리 알고가기

- CFG: 생성 규칙의 좌변이 단일 비단말 기호인 Type-2 문법임
- 비단말 기호: 아직 더 전개될 수 있는 문법 변수이며 보통 `S`, `A`, `B`로 표기함
- 단말 기호: 최종 문자열에 실제로 나타나는 기호이며 더 전개되지 않음
- 파스 트리: 시작 기호에서 단말 문자열까지의 유도 과정을 트리로 표현한 구조임
- 모호성: 하나의 문자열에 대해 서로 다른 파스 트리가 둘 이상 존재하는 성질임

## Ⅰ. 개요

- **정의**: 문맥 자유 문법은 단일 비단말 기호를 기호열로 치환하는 생성 규칙으로 문자열의 중첩 구조를 표현하는 문법 체계임
- **배경/필요성**: 정규 언어는 괄호 짝, 블록 중첩, 재귀 구문을 표현하지 못하므로 프로그래밍 언어 문법과 데이터 포맷을 파스 트리로 구조화할 수 있는 문법이 필요함.
- **비유**: 문장을 명사구, 동사구, 목적어로 계속 쪼개며 문장 구조를 만드는 문법 설명서와 같음.

| 출제 의도 | 반드시 짚을 핵심 | 감점 회피 포인트 |
|:---|:---|:---|
| CFG의 정의와 구성 설명 | G=(V,T,P,S), 생성 규칙, 파스 트리 | 정규 문법과 표현력 차이 누락 |
| 파싱 관점의 문제 이해 | 모호성, 좌재귀, LL/LR 파서 연결 | 문법 생성과 문자열 인식 혼동 |

> 요약: CFG는 단순 패턴을 넘어 중첩된 구문 구조를 생성하고 분석하는 형식 문법임.

## Ⅱ. 특징/비교

| 판단 기준 | 정규 문법 | 문맥 자유 문법 |
|:---|:---|:---|
| 생성 규칙 제한 | `A -> aB`처럼 우변 형태가 매우 제한됨 | `A -> alpha` 형태로 임의 기호열 전개가 가능함 |
| 기억 모델 | 유한 오토마타로 인식 가능함 | 스택을 가진 푸시다운 오토마타로 인식함 |
| 표현 대상 | 토큰, 식별자, 단순 패턴 검증에 적합함 | 수식, 괄호, 블록, 재귀 구조 표현에 적합함 |
| 구현 선택 | 어휘 분석 단계에 주로 적용함 | 구문 분석 단계에서 파서 생성의 기준이 됨 |

> 요약: CFG는 스택 기반 구조 표현이 필요할 때 선택하며, 정규 언어와 역할을 어휘 분석과 구문 분석으로 나누는 것이 핵심임.

- **적용 기준**: 구조적 중첩과 재귀가 문법의 핵심이면 CFG를 선택함.
- **분리 기준**: 토큰 자체의 모양은 정규식으로 처리하고 토큰 배열의 문장 구조는 CFG로 처리함.
- **주의 기준**: 모호 문법은 파서 충돌과 의미 해석 오류를 만들 수 있으므로 우선 제거함.

## Ⅲ. 구성요소

```text
+------------+      +------------+      +------------+
| Start      | ---> | Production | ---> | Derivation |
| Symbol S   |      | Rules P    |      | Steps      |
+------------+      +------------+      +------------+
       |                   |
       v                   v
+------------+      +------------+
| Nonterm V  |      | Terminals  |
| Variables  |      | Tokens T   |
+------------+      +------------+
```

| 구성요소 | 설명 | 비유 |
|:---|:---|:---|
| 비단말 기호 V | 문법 전개 중간 단계에서 구조 단위를 나타내는 변수임 | 문장 틀 이름 |
| 단말 기호 T | 더 이상 전개되지 않고 최종 문자열을 구성하는 실제 토큰임 | 실제 단어 |
| 생성 규칙 P | 비단말을 단말·비단말 기호열로 치환해 유도 과정을 정의함 | 조립 규칙 |
| 시작 기호 S | 전체 문장이 유도되는 최초 비단말 기호임 | 출발 설계도 |
| 파스 트리 | 생성 규칙 적용 순서를 계층 구조로 나타내 의미 분석의 입력이 됨 | 문장 구조도 |

> 요약: CFG는 시작 기호에서 생성 규칙을 적용해 단말 문자열과 파스 트리를 만들며, 이 구조가 구문 분석의 근거가 됨.

## Ⅳ. 절차

```text
+------------+      +------------+      +------------+      +------------+
| Grammar    | ---> | Derive     | ---> | Parse Tree | ---> | Validate   |
| Define     |      | String     |      | Build      |      | Ambiguity  |
+------------+      +------------+      +------------+      +------------+
```

1. **문법 정의**: 비단말, 단말, 생성 규칙, 시작 기호를 정하고 문법의 범위를 명확히 함.
2. **문자열 유도**: 시작 기호에서 규칙을 반복 적용해 목표 문자열이 생성되는지 확인함.
3. **파스 트리 구성**: 유도 과정을 트리로 나타내 연산자 우선순위와 결합 방향을 확인함.
4. **문법 검증**: 모호성, 좌재귀, 파서 충돌 가능성을 점검하고 필요한 경우 문법을 변환함.

> 요약: CFG 적용은 문법을 정의한 뒤 문자열 유도와 파스 트리 생성을 통해 구조적 타당성을 검증하는 과정임.

## Ⅴ. 문제점

- **P1 모호성 발생**: 하나의 문자열에 여러 파스 트리가 존재하면 연산자 우선순위나 의미 해석이 달라질 수 있음.
- **P2 파서 제약 충돌**: 좌재귀, 공통 접두어, shift/reduce 충돌은 LL/LR 파서 구현을 어렵게 만듦.
- **P3 의미 제약 표현 한계**: CFG는 변수 선언 여부나 타입 일치처럼 문맥 정보가 필요한 제약을 문법만으로 처리하기 어려움.

> 요약: CFG는 구문 구조 표현에는 강하지만 모호성, 파서 적합성, 문맥 의미 제약에서 별도 통제가 필요함.

## Ⅵ. 개선방안

- **P1 대응**: 우선순위와 결합 규칙을 문법에 반영하고 모호한 생성 규칙을 분리함. (확인: 동일 문자열의 파스 트리 수)
- **P2 대응**: 좌재귀 제거, 좌인수분해, 파서 유형별 문법 변환으로 충돌을 줄임. (확인: LL/LR 파서 충돌 로그)
- **P3 대응**: 심볼 테이블과 의미 분석 단계로 선언, 타입, 범위 규칙을 별도 검증함. (확인: 의미 오류 검출 테스트)

> 요약: CFG의 문제는 문법 정규화와 의미 분석 분리로 해결하며, 문법은 구문 구조 표현에 집중시키는 것이 바람직함.

## Ⅶ. 전망

- **발전 방향**: DSL, API 스키마, 데이터 직렬화 포맷에서 CFG 기반 파서 생성과 문법 검증은 계속 활용될 전망임.
- **기술사적 판단**: 토큰 검증은 정규 언어, 구문 구조는 CFG, 의미 제약은 의미 분석으로 계층을 나누어 설계해야 함.
- **기술사 제언**: 답안에서는 G=(V,T,P,S) 정의와 파스 트리, 모호성 대응을 함께 제시해 구현 관점까지 연결해야 함.
