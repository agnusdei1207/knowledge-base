## Ⅰ. 개요

- **정의**: 소스 코딩은 데이터의 통계적 중복을 제거해 크기를 줄이는 압축 기법이고, 채널 코딩은 전송 오류에 대비해 의도적으로 중복을 추가하는 보호 기법임.
- **배경/필요성**: 압축만 하면 잡음이 섞인 채널에서 손상에 취약해지고, 오류 정정 부호만 추가하면 불필요한 원본 중복까지 실어 대역폭을 낭비하므로, 두 기법을 순차 결합해 "최소 비트로 안전하게" 전송하는 구조가 필요함.
- **출제 의도**: 두 기법이 중복을 다루는 방향(제거 vs 추가)이 정반대라는 점과, 통신 파이프라인에서 반드시 소스 코딩 다음에 채널 코딩을 적용해야 하는 이유를 이해하는지 확인함.
- **답안 방향**: 구조(파이프라인 배치) → 동작(순서 고정 근거) → 심화 비교(목적·한계 축) → 실무 적용 순으로 전개함.

| 출제 의도 | 반드시 짚을 핵심 | 감점 회피 포인트 |
|:---|:---|:---|
| 두 코딩의 목적 차이와 결합 순서 설명 요구 | 중복 제거(엔트로피 하한) vs 중복 추가(채널 용량 상한), 소스→채널 고정 순서 | 순서 근거 누락, 허프만·해밍 알고리즘 세부 재설명으로 분량 소모 |

> 요약: 이 답안은 두 코딩을 개별 알고리즘이 아니라 "제거 vs 추가"라는 상반된 목적 축과 그 결합 순서로 설명해야 함.

## Ⅱ. 구조 및 구성요소

```text
원본 데이터 -> 소스 인코더(중복 제거) -> 채널 인코더(중복 추가) -> 변조 -> 채널(잡음)
                                                                         |
                                                                         v
복원 데이터 <- 소스 디코더(압축 해제) <- 채널 디코더(오류 검출·정정) <- 복조
```

| 구성요소 | 역할 | 예시/비유 |
|:---|:---|:---|
| 소스 인코더 | 통계적 중복을 제거해 평균 비트 수를 엔트로피 $H$에 근접시킴 | 허프만 코딩(032 참조)이 대표 예 |
| 채널 인코더 | 오류 검출·정정에 쓸 중복 비트를 부호에 추가함 | 해밍 코드(030 참조)가 대표 예 |
| 변조·채널 | 부호화된 비트를 물리 신호로 바꿔 전송하며 잡음이 유입되는 구간 | 무선 링크, 광케이블 |
| 채널 디코더 | 신드롬 등으로 오류 위치를 특정하고 정정·검출함 | FEC(전방 오류 정정), ARQ(재전송 요청) |
| 소스 디코더 | 압축을 해제해 원본 데이터를 복원함 | 무손실/손실 복원 |

> 요약: 송신측은 소스 인코더가 크기를 줄인 뒤 채널 인코더가 보호용 중복을 더하고, 수신측은 역순으로 오류를 먼저 정정한 뒤 압축을 해제함.

## Ⅲ. 동작원리 및 흐름도

```text
원본 -> [소스 인코딩: 압축] -> [채널 인코딩: 중복 추가] -> 전송(잡음) -> [채널 디코딩: 오류 정정] -> [소스 디코딩: 압축 해제] -> 복원
```

- 1단계(압축): 원본 데이터의 통계적 중복을 제거해 최소 비트로 표현함. 허프만 코딩(032)이 대표적 소스 코딩 예임.
- 2단계(보호): 압축된 데이터에 오류 검출·정정용 중복 비트를 추가함. 해밍 코드(030)가 대표적 채널 코딩 예임.
- 3단계(전송·정정): 잡음 채널을 통과한 신호를 복조한 뒤, 채널 디코더가 신드롬으로 오류 위치를 찾아 먼저 정정함.
- 4단계(압축 해제): 오류가 정정된 데이터를 소스 디코더가 압축 해제해 원본을 복원함. 순서가 바뀌어 채널 인코딩 후 소스 인코딩을 적용하면, 압축 알고리즘이 오류 정정용 중복 패턴을 통계적 중복으로 오인해 제거하므로 오류 정정 능력이 사라짐.

> 요약: 압축(소스)이 먼저, 보호(채널)가 나중이라는 순서를 지켜야 두 기법이 서로의 기능을 해치지 않음.

## Ⅳ. 특징

- 목적 상반: 소스 코딩은 데이터 크기를 줄이고 채널 코딩은 데이터 크기를 늘림 — 방향이 반대인 두 부호화가 한 파이프라인에서 공존함.
- 순서 고정: 압축 후 보호 순서를 지켜야 하며, 반대로 적용하면 채널 코딩이 추가한 중복을 소스 코딩이 제거해 오류 정정 능력이 사라짐.
- 독립 최적화 가능: Shannon 분리 정리(031 참조)에 따라 두 기법을 각자 최적화해도 결합 시 전체 성능에 근접할 수 있음. 단 지연 제약이 큰 실시간 서비스는 두 기법을 통합 설계하는 공동 소스-채널 코딩(JSCC) 검토가 필요함.
- 이론적 한계 위치가 다름: 소스 코딩은 엔트로피 $H$가 압축 하한이고, 채널 코딩은 채널 용량 $C$가 전송률 상한임 — 같은 파이프라인 안에서도 목적에 따라 성능을 판단하는 기준 물리량이 다름.

> 요약: 두 기법은 방향(제거/추가)·한계(H/C)가 반대이면서도 순서와 분리 설계 원칙으로 하나의 통신 파이프라인 안에 공존함.

## Ⅴ. 심화 비교 및 적용 판단

| 판단 축 | 소스 코딩 | 채널 코딩 | 선택 기준 |
|:---|:---|:---|:---|
| 목적 | 통계적 중복 제거(압축) | 오류 검출·정정용 중복 추가 | 저장·전송 비용 절감이 우선이면 압축 비중 확대, 무결성 확보가 우선이면 보호 비중 확대 |
| 이론적 한계 | 엔트로피 $H$ (더 못 줄임) | 채널 용량 $C$ (이 이상 전송 시 오류 불가피) | 목표 전송률이 $C$에 근접할수록 LDPC·Polar 등 강한 채널 코딩 필요 |
| 지연 민감도 | 지연에 비교적 둔감 | 지연 제약 시 재전송(ARQ)보다 FEC 선호 | 실시간 스트리밍은 재전송을 배제하고 FEC 중심 채널 코딩 채택 |

> 요약: 목적·한계 축에서는 서로 반대이며, 지연 허용 범위가 두 기법의 결합 비중과 방식(ARQ vs FEC)을 결정함.

**리스크·대응 (불릿):**
- 순서 오류: 채널 인코딩 후 소스 인코딩을 적용하는 설계 실수가 원인 → 파이프라인 순서(소스 먼저)를 아키텍처 표준으로 고정해 대응함(지표: 파이프라인 순서 코드 리뷰 통과율).
- 과잉 보호: 채널 상태 대비 과도한 부호율로 FEC 중복을 설정하는 것이 원인 → 채널 SNR을 측정해 부호율을 조정하는 적응적 채널 코딩으로 대응함(지표: 유효 처리량 대비 중복 오버헤드 비율).

## Ⅵ. 실무 적용 및 결론

1. 단기: 파이프라인에서 소스 코딩 다음에 채널 코딩이 적용되는지, 현재 압축률·오류율 수준이 목표치를 만족하는지 점검함.
2. 중기: 채널 상태(SNR)에 따라 부호율을 조정하는 적응적 채널 코딩(LDPC/Polar의 가변 코드율)을 도입함.
3. 장기: 저지연 요구가 큰 서비스에서는 분리 설계의 한계를 검토해 공동 소스-채널 코딩(JSCC) 적용 여부를 판단함.

- 기술사적 판단: 두 코딩은 중복을 다루는 방향이 반대이므로 병렬이 아닌 직렬(소스 먼저)로 설계해야 하며, 분리 설계가 유효한지는 서비스의 지연 허용 범위로 판단함.
- 기술사 제언: 압축률과 오류 정정 여유율(코드율)을 하나의 설계 지표 쌍으로 함께 관리해, 대역폭 절감과 신뢰성 확보 사이의 트레이드오프를 명시적으로 통제함.
