# 📖 【암기용】 개념 완전 이해

## 한눈에
- **개요**: 응답 시간 분해는 **응답시간(W)**(001 성능지표 참조)을 **대기시간(Wq)** 과 **서비스시간(Ws)** 의 합으로 쪼개 지연의 원인 구간을 찾는 관점이다.
- **왜 필요한가**: 응답시간이 늘었을 때 원인이 "처리 자체가 느려서(서비스시간)"인지 "줄 서서 기다려서(대기시간)"인지 구분해야 올바른 개선책을 고르기 때문이다.
- **핵심 직관**: 은행에서 체감하는 시간 = 줄 서서 기다린 시간(대기) + 창구에서 실제 업무를 본 시간(서비스). 앞이 길면 창구를 늘리고, 뒤가 길면 업무 절차를 바꿔야 한다.

## 핵심 용어 정리

응답시간의 전체 정의는 001에 있으므로, 여기서는 그것을 쪼갠 하위 용어와 큐잉 변수에 집중한다.

| 용어/표기 | 의미 | 비유·예 |
|:---|:---|:---|
| 응답시간(W) | 요청~응답 완료까지 총 시간 (001 참조) | 은행 문을 들어가 나오기까지 전체 시간 |
| 대기시간(Wq) | 큐(대기열)에서 자원 할당을 기다린 시간 | 줄 서서 내 차례를 기다린 시간 |
| 서비스시간(Ws=1/μ) | 자원이 실제로 처리한 시간 | 창구 직원이 내 업무를 처리한 시간 |
| 도착률(λ, lambda) | 단위 시간당 들어오는 요청 수 | 1분에 손님이 몇 명 오는가 |
| 서비스율(μ, mu) | 단위 시간당 자원이 처리 가능한 수 | 창구가 1분에 몇 명 처리하는가 |
| 이용률(ρ=λ/μ) | 자원이 바쁜 시간 비율(0~1) | 창구가 쉬지 않고 일한 시간 비율 |
| 대기열 길이(Lq) | 큐에서 대기 중인 평균 요청 수 | 줄에 서 있는 평균 인원 |
| 리틀의 법칙 | Lq = λ × Wq (대기 인원 = 도착률 × 대기시간) | 줄 선 인원 = 분당 도착 × 평균 대기분 |

## 깊이 이해
- **배경·문제의식**: 응답시간이 늘었을 때 서버 CPU·코드만 들여다보면, 실제 원인이 요청 폭주로 인한 대기열 적체일 때 이를 놓친다. 그래서 "총 시간이 어느 구간에서 늘었나"를 먼저 나눠 본다.
- **작동 원리 — W = Wq + Ws**: 응답시간 W는 대기시간 Wq와 서비스시간 Ws(=1/μ)의 합이다. Ws는 자원 성능(처리율 μ)이 정하고, Wq는 대기행렬 이론(큐잉)이 정한다.
- **이용률 ρ가 대기시간을 비선형으로 키운다**: M/M/1 모델에서 대기시간 Wq = ρ/(μ−λ)로, ρ가 1에 가까워지면 Wq가 급격히(비선형으로) 폭증한다. 즉 자원을 80%→90%로 더 채우면 대기시간이 몇 배로 뛴다 — "포화 직전에 응답시간이 절벽처럼 나빠지는" 이유다.
- **비유**: 병원에서 체감 시간 = 진료실 앞에서 기다린 시간(Wq) + 의사가 실제 진료한 시간(Ws). 환자가 몰려 대기줄(ρ↑)이 길어지면, 진료 자체는 그대로여도 체감 시간만 폭증한다.
- **구체 예시**: 어떤 API의 서비스시간이 평균 20ms인데 트래픽 급증으로 대기시간이 180ms 추가되면 응답시간은 200ms가 된다. 이때 Wq/W = 90%이므로 서버 로직 최적화(Ws 개선)는 효과가 미미하고, 동시 처리 용량 확충(서버 c 증설로 Wq 감소)이 정답이다.
- **흔한 오해·주의점**: 응답시간이 늘었다고 늘 서버 로직이 느려진 것은 아니다. 대기시간이 원인이면 코드 최적화의 개선 효과는 제한적이다. 반대로 부하와 무관하게 항상 느리면 서비스시간 문제다.

## 연결 개념
- 시스템 성능 지표(001) — 응답시간의 상위 정의와 SLA 위치
- 큐잉 이론(M/M/1·M/M/c) — 대기시간 Wq를 산출하는 수학 모델
- 병목 분석 — 서비스시간이 긴 자원을 식별하는 절차

# 📝 【답안용】 시험 답안 템플릿

## 핵심 인사이트 (3줄 요약)

> 1. **본질**: 응답시간(W)은 대기시간(Wq, 큐에서 기다린 시간)과 서비스시간(Ws, 자원이 실제 처리한 시간)의 합임.
> 2. **가치**: 두 구간을 분리해야 자원 증설(Ws 개선)과 큐 관리(Wq 개선) 중 올바른 조치를 고를 수 있음.
> 3. **판단 포인트**: 대기시간 비중이 크면 동시 처리 용량·큐 정책을, 서비스시간 비중이 크면 로직·자원 성능을 개선 대상으로 삼음.

## 출제 의도 및 답안 포인트

| 출제 의도 | 반드시 짚을 핵심 | 감점 회피 포인트 |
|:---|:---|:---|
| 응답시간 구조 이해 확인 | W = Wq + Ws 산식과 구간 정의 | 응답시간을 단일 값으로만 서술 |
| 원인 분석 역량 확인 | 이용률 ρ와 대기시간의 비선형 관계 | 두 구간 구분 없이 "느려졌다"로 서술 |
| 개선 조치 적합성 확인 | 구간별로 다른 개선 방향 | 원인 진단 없이 자원 증설만 제시 |

> 요약: 수치보다 대기·서비스 구간 분해와 그에 맞는 개선 조치 선택을 보여야 함.

## Ⅰ. 개요 및 필요성

- 개요: 응답시간(W)을 대기시간(Wq)과 서비스시간(Ws)으로 분해해 지연 원인을 구간별로 특정하는 관점
- 배경: 응답시간의 전체 정의는 상위 지표(001)에 있고, 본 키워드는 그 값을 W = Wq + 1/μ로 쪼개 원인을 분리함
- 필요성: 지연 원인이 자원 처리 속도인지 대기행렬 적체인지 구분해야 개선 투자 방향을 정할 수 있음

---

## Ⅱ. 구조 및 구성요소

- 처리 경로(선형 구조도):

```text
요청 도착 -> Queue(대기열, Wq 발생) -> Server(처리 자원, Ws 발생)
  -> 대기시간(Wq) 측정 + 서비스시간(1/μ) 측정
  -> 응답시간(W) = Wq + Ws 합산 -> 병목 구간 판정
```

| 구성요소 | 역할 | 특이사항 |
|:---|:---|:---|
| Queue | 처리 대기 요청 보관 | 대기열 길이 Lq, 대기시간 Wq |
| Server | 실제 트랜잭션 처리 자원 | 서비스율 μ, 서비스시간 1/μ |
| Wq Monitor | 대기 구간 시간 측정 | 큐 진입~서버 할당 시각 차 |
| Service Monitor | 처리 구간 시간 측정 | 서버 할당~처리 완료 시각 차 |

> 요약: 응답시간은 대기열의 Wq와 서버 처리의 Ws로 나뉘어 각각 측정됨.

---

## Ⅲ. 동작원리 및 흐름도

- 구간 측정 흐름(선형 흐름도):

```text
요청 도착 -> 큐 진입 시각 기록 -> 서버 할당(Wq 확정)
  -> 처리 시작 -> 처리 완료(Ws 확정) -> W=Wq+Ws -> 구간 비중 비교
```

1. 요청 도착·큐 진입 시각을 기록해 큐 진입 지연 유무를 확인함
2. 서버 할당까지의 대기시간(Wq)과 큐 길이(Lq)를 측정함
3. 처리 완료까지의 서비스시간(Ws)과 서버 이용률(ρ)을 측정함
4. W를 합산해 Wq/W·Ws/W 비중을 비교하고 지배 구간을 병목으로 판정함

---

## Ⅳ. 특징

- 대기시간(Wq)은 큐에서, 서비스시간(Ws)은 서버에서 발생해 개선 대상 자체가 다름
- 대기시간은 이용률 ρ=λ/μ가 1에 가까워질수록 비선형으로 급증함(포화 직전 절벽 현상)
- 서비스시간은 처리 로직·자원 성능이 정하며 부하와 대체로 무관하게 일정함
- 리틀의 법칙(Lq = λ × Wq)으로 대기 인원과 대기시간이 연결돼 큐 상태를 역산할 수 있음
- 구간 분해 없이 평균 응답시간만 관리하면 원인을 오판해 잘못된 자원에 투자하게 됨

---

## Ⅴ. 심화 비교 및 적용 판단

- 지배 구간별 진단·대응:

| 구분 | 대기시간(Wq) 지배 | 서비스시간(Ws) 지배 |
|:---|:---|:---|
| 증상 | 유입량 급증 시 응답시간 급격 악화 | 유입량 무관하게 항상 지연 |
| 원인 | 도착률 λ 증가, 서버 수 c 부족(ρ→1) | 처리 로직 비효율, 자원 성능 한계 |
| 대응 | 서버 증설·오토스케일링·큐 우선순위 | 코드 프로파일링·쿼리 튜닝·캐시 |

> 요약: 부하 급증에 민감하면 대기시간 문제, 부하와 무관하게 느리면 서비스시간 문제임.

- 리스크와 대응(불릿):
  - 대기열 폭주 → 도착률이 처리율 초과(ρ≥1) → 서버 증설·백프레셔·큐 제한(확인: 큐 길이, ρ)
  - 서비스시간 오진 → 프로파일링 없이 자원 증설 우선 → 병목 분석으로 지연 구간 특정 후 조치(확인: CPU·I/O 대기, 핫스팟)
  - SLA 위반 → 구간 분해 없이 평균만 관리 → Wq·Ws를 SLA에 각각 명시(확인: 구간별 p95)

---

## Ⅵ. 실무 적용 및 결론

- 적용 방안:
  1. APM 트랜잭션 트레이스에서 대기시간과 서비스시간을 구간별로 분리해 로깅함
  2. Wq 비중이 높으면 오토스케일링·큐 정책 조정, Ws 비중이 높으면 프로파일링 기반 로직 최적화를 적용함
  3. SLA 문서에 전체 응답시간뿐 아니라 구간별 목표치(예: Wq/W 30% 이하)를 별도 명시함
- 결론:
  - 응답시간 개선은 대기·서비스 구간을 분해 진단한 뒤 구간에 맞는 조치를 골라야 함
  - 분산 트레이싱으로 마이크로서비스 간 구간별 지연을 자동 분해·시각화하는 체계로 확장 필요
