## 미리 알고가기

- 응답시간 $W$: 요청이 시스템에 들어와 응답이 끝날 때까지 머문 전체 시간임
- 서비스 시간 $W_s$: CPU, DB, 외부 API 호출처럼 실제 처리가 수행된 시간임
- 대기 시간 $W_q$: 스레드, 커넥션, 락, 큐 같은 자원을 기다린 시간임
- 이용률 $\rho$: 처리 자원이 사용 중인 비율이며 포화에 가까울수록 대기 시간이 커짐
- Thread State: RUNNABLE, WAITING, BLOCKED처럼 스레드가 처리 중인지 대기 중인지 나타내는 상태임

## Ⅰ. 개요

- **정의/개념**: 응답 시간 분해는 전체 지연을 서비스 시간과 대기 시간으로 나누어 코드 처리 지연인지 자원 경합 지연인지 판단하는 성능 분석 기법임
- **배경/필요성**: 느린 응답을 서버 증설로 해결할지 코드와 쿼리를 고칠지 판단하려면 지연이 발생한 구간과 성격을 먼저 구분해야 함

## Ⅱ. 특징

- 전체 응답시간은 일반적으로 $W = W_q + W_s$로 분해해 해석함
- $W_s$가 크면 코드, 쿼리, 외부 호출 같은 처리 자체가 병목임
- $W_q$가 크면 스레드 풀, 커넥션 풀, 락, 큐 같은 공유 자원 경합이 병목임
- 이용률이 높아질수록 처리 시간보다 대기 시간이 먼저 사용자 지연을 키우는 경우가 많음

## Ⅲ. 종류 및 비교

| 판단 기준 | 서비스 시간 $W_s$ | 대기 시간 $W_q$ |
|:---|:---|:---|
| 지연 위치 | 요청을 실제 처리하는 구간임 | 처리 전 자원 할당을 기다리는 구간임 |
| 주요 원인 | 비효율 쿼리, 복잡한 로직, 느린 외부 API | 스레드 부족, DB 커넥션 부족, 락 경합 |
| 개선 방향 | 인덱스, 캐시, 알고리즘, I/O 조정 | 풀 크기 조정, 동시성 제한, 큐 분리 |
| 확인 지표 | Self Time, SQL 실행시간, 외부 호출 시간 | Queue Time, WAITING/BLOCKED 시간, pool wait |

## Ⅳ. 구성요소 및 구조

| 구성요소 | 설명 |
|:---|:---|
| 요청 시작 시각 | 사용자가 요청을 보낸 시점으로 전체 응답시간의 기준점을 만듦 |
| 대기 구간 | 스레드, 커넥션, 락을 기다린 시간을 기록해 경합 원인을 찾음 |
| 처리 구간 | 애플리케이션 로직, DB, 외부 API 수행 시간을 기록해 실제 처리 비용을 찾음 |
| 응답 완료 시각 | 사용자에게 응답이 끝난 시점으로 전체 지연과 구간 합의 일치 여부를 확인함 |

```text
+---------+     +---------+     +---------+     +---------+
| 요청 도착  | --> | 자원 대기  | --> | 실제 처리  | --> | 응답 완료  |
+---------+     +---------+     +---------+     +---------+
                  Wq              Ws
```

## Ⅴ. 원리 및 절차 흐름도

```text
+---------+     +---------+     +---------+     +---------+
| Trace 수집 | --> | 구간 분해  | --> | 지배 지연 판정 | --> | 개선안 선택 |
+---------+     +---------+     +---------+     +---------+
```

1. **Trace 수집**: 요청 단위로 시작, 대기, 처리, 응답 완료 시각을 수집함
2. **구간 분해**: 전체 응답시간을 $W_q$와 $W_s$로 나누어 계산함
3. **지배 지연 판정**: 지연 비중이 큰 구간을 찾아 병목 성격을 판단함
4. **개선안 선택**: 처리 지연은 튜닝으로, 대기 지연은 동시성·용량 조정으로 대응함

## Ⅵ. 실무 적용 및 유의점

1. WAS 성능 분석에서는 평균 RT만 보지 말고 스레드 대기와 DB 실행 시간을 분리해야 하므로 APM trace, thread dump, connection pool wait time을 함께 확인함
2. 고부하 상황에서는 서버 증설 전에 $W_q$와 $W_s$ 중 어느 쪽이 지배적인지 확인해야 하므로 전후 비교에서 p95 latency와 dominant span 비율을 확인함

## Ⅶ. 결론

응답 시간 분해는 느리다는 현상을 처리 지연과 대기 지연으로 나누어 서버 증설, 동시성 조정, 코드 튜닝 중 어떤 조치가 맞는지 결정하게 함.

## 작성 근거(검토용)

- 이 키워드는 산식보다 지연 원인 분리가 답안 축이므로 $W_q$와 $W_s$의 역할을 먼저 정의함
- 넓은 평가어 대신 지연 위치, 주요 원인, 확인 지표를 비교축으로 사용함
- 결론은 추상적 조정 표현이 아니라 조치 선택 기준으로 마무리해 평가·지표형 답안 흐름에 맞춤
