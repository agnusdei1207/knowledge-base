# 📖 【암기용】 개념 완전 이해

> 목적: 프로파일링을 CPU 사용량 확인이 아니라, 코드 레벨에서 자원을 가장 많이 소모하는 함수·구간(핫스팟)을 찾아내는 정밀 측정 기법으로 이해하게 만든다.

## 한눈에
- **개요**: 프로파일링은 프로그램 실행 중 함수·메서드별 CPU 시간, 메모리 할당, 호출 횟수를 측정해 자원을 가장 많이 쓰는 핫스팟을 찾는 기법이다.
- **왜 필요한가**: APM은 서비스 구간까지는 좁히지만, 정확히 어느 함수·쿼리·알고리즘이 병목인지는 프로파일링으로 확인해야 한다.
- **핵심 직관**: 자동차 정비사가 계기판(APM) 이상을 본 뒤 엔진을 분해해 정확한 부품(핫스팟)을 찾는 과정과 같다.

## 깊이 이해
- **배경·문제의식**: 서비스 구간이 느리다는 것을 알아도, 그 안의 어떤 반복문·직렬화·락 대기가 원인인지 모르면 개선이 불가능하다.
- **배경·문제의식**: 평균 CPU 사용률만으로는 특정 함수의 과다 호출이나 비효율 알고리즘을 발견할 수 없다.
- **작동 원리**: 샘플링 프로파일러는 일정 주기로 스택을 캡처해 통계적으로 시간 소모가 큰 함수를 추정한다.
- **작동 원리**: 계측(instrumentation) 프로파일러는 함수 진입·종료 시점에 코드를 삽입해 정확한 호출 횟수와 소요 시간을 기록하되 오버헤드가 더 크다.
- **비유**: 샘플링은 여러 층 사무실을 순찰하며 누가 일하는지 스냅샷을 찍는 방식이고, 계측은 모든 직원에게 출퇴근 태그를 채우는 방식이다.
- **구체 예시**: 예시로 async-profiler로 채집한 flame graph에서 특정 JSON 직렬화 함수가 전체 CPU 시간의 35%를 차지하면 해당 함수를 최우선 개선 대상으로 지정한다.
- **흔한 오해·주의점**: 프로파일링 결과의 "가장 위에 있는 함수"가 항상 근본 원인은 아니다.
- **흔한 오해·주의점**: 호출 트리 상위(caller)까지 확인해 반복 호출을 유발한 원인 로직을 함께 봐야 한다.

## 연결 개념
- APM — 서비스 구간 단위로 병목 후보를 좁힌 뒤 프로파일링으로 정밀 분석
- 성능 테스트 지표 — 프로파일링 결과를 개선 전후 비교 근거로 사용
- 코드 복잡도 — 핫스팟과 순환 복잡도가 높은 코드가 겹치는 경우 리팩터링 우선순위 상향

# 📝 【답안용】 시험 답안 템플릿

> 목적: 프로파일링 기법 분류, 핫스팟 식별 절차, 개선 우선순위 판단 기준을 시험 답안으로 전개한다.
> 핵심: 프로파일링은 샘플링과 계측 방식의 오버헤드·정확도 트레이드오프를 이해하고 호출 트리 근본 원인까지 추적하는 것이 핵심이다.

## 핵심 인사이트 (3줄 요약)

> 1. **본질**: 프로파일링은 함수·메서드 단위로 CPU 시간, 메모리 할당, 호출 횟수를 측정해 핫스팟을 식별하는 정밀 분석 기법이다.
> 2. **가치**: APM으로 좁힌 병목 서비스 구간 내부에서 정확히 어느 코드가 자원을 소모하는지 근거를 제공한다.
> 3. **판단 포인트**: 샘플링과 계측 방식의 오버헤드·정확도 차이, 그리고 호출 트리 상위 원인까지 추적하는지가 개선 효과를 좌우한다.

## 출제 의도 및 답안 포인트

| 출제 의도 | 반드시 짚을 핵심 | 감점 회피 포인트 |
|:---|:---|:---|
| 프로파일링 기법 이해 확인 | 샘플링 vs 계측(instrumentation) 방식 차이 | 프로파일링을 APM과 동일하게 서술 |
| 핫스팟 식별 역량 확인 | flame graph, 함수별 CPU 시간·호출 횟수 | 최상위 함수만 보고 근본 원인 누락 |
| 개선 우선순위 판단 확인 | 호출 트리, 반복 호출 원인 로직 | 수치 없이 "느린 함수 개선"으로 서술 |

> 요약: 이 문제는 프로파일링 기법의 오버헤드 차이와 호출 트리 기반 근본 원인 추적 역량을 요구한다.

---

## Ⅰ. 개요 및 필요성

- 개요: 함수·메서드 단위 CPU 시간·메모리 할당·호출 횟수를 측정해 핫스팟을 찾는 정밀 분석 기법
- 배경: 서비스 구간 단위 분석(APM)만으로는 정확한 코드 레벨 원인 파악이 어려움
- 필요성: 개선 우선순위를 정량 근거로 정하고 리팩터링·튜닝 효과를 사전 예측하기 위해 필요

---

## Ⅱ. 구조 및 구성요소

```text
실행 중 애플리케이션 -> 프로파일러(샘플링/계측) -> 스택·호출 데이터 수집 -> Flame Graph 생성 -> 핫스팟 판정
```

| 구성요소 | 역할 | 특이사항 |
|:---|:---|:---|
| 샘플링 프로파일러 | 주기적 스택 캡처로 통계적 추정 | async-profiler, perf, JFR |
| 계측 프로파일러 | 함수 진입·종료 지점 코드 삽입 | 정확도 높음, 오버헤드 큼 |
| Flame Graph | 호출 스택을 시각화해 CPU 비중 표시 | 폭이 넓을수록 소모 시간 큼 |
| 메모리 프로파일러 | 객체 할당·GC 압박 측정 | heap dump, allocation profiling |

> 요약: 프로파일링은 샘플링·계측 방식으로 데이터를 수집해 Flame Graph로 핫스팟을 시각화하는 구조다.

---

## Ⅲ. 동작원리 및 흐름도

```text
프로파일링 시작 -> 스택/호출 캡처 -> 함수별 시간·횟수 집계 -> Flame Graph 렌더링 -> 핫스팟·원인 함수 특정
```

| 단계 | 처리 내용 | 검증 기준 |
|:---:|:---|:---|
| 1 | 대상 프로세스에 프로파일러 연결 | 오버헤드 5% 이하 목표 |
| 2 | 일정 주기 스택 캡처 또는 함수 계측 | 샘플링 주기, 계측 지점 수 |
| 3 | 함수별 누적 CPU 시간·호출 횟수 집계 | self time, total time 구분 |
| 4 | Flame Graph로 시각화 후 상위 함수 확인 | CPU 비중 상위 5개 함수 |
| 5 | 호출 트리 상위 원인 로직까지 추적 | caller 반복 호출 여부 |

> 요약: 프로파일링은 스택을 수집·집계해 Flame Graph로 시각화한 뒤 호출 트리 상위까지 원인을 추적하는 순서로 진행된다.

## Ⅳ. 특징

| 구분 | 샘플링 프로파일링 | 계측 프로파일링 | 수치 컬럼 |
|:---|:---|:---|:---|
| 정확도 | 통계적 추정 | 정확한 호출 횟수·시간 | 샘플링 주기 1~10ms |
| 오버헤드 | 낮음(1~5%) | 높음(수십 % 가능) | 계측 지점 수에 비례 |
| 적용 환경 | 운영 환경 상시 적용 가능 | 개발·테스트 환경 위주 | 운영 적용 시 오버헤드 검증 필수 |

> 요약: 샘플링은 저오버헤드로 운영 환경에 적합하고, 계측은 고정밀도가 필요한 개발 단계에 적합하다.

## Ⅴ. 심화 비교 및 적용 판단

| 비교 축 | 샘플링 | 계측 | 선택 기준 |
|:---|:---|:---|:---|
| 구조 | 스택 스냅샷 통계 추정 | 함수 진입·종료 코드 삽입 | 운영 환경 여부 |
| 비용/성능 | 낮은 오버헤드 | 높은 오버헤드 가능 | 성능 영향 허용치 |
| 운영/위험 | 통계적 오차 존재 | 정밀하나 배포 변경 필요 | 정밀도 요구 수준 |

> 요약: 운영 환경 상시 분석은 샘플링, 개발 단계 정밀 분석은 계측 방식을 선택한다.

| 리스크 | 원인 | 대응 방안 | 확인 지표 |
|:---|:---|:---|:---|
| 근본 원인 오판 | 최상위 함수만 보고 호출 원인 미추적 | 호출 트리 caller까지 분석 | caller 반복 호출 횟수 |
| 운영 성능 저하 | 계측 프로파일러를 운영에 직접 적용 | 운영은 샘플링, 계측은 스테이징 적용 | 오버헤드 5% 이하 |
| 개선 효과 미검증 | 개선 후 재측정 누락 | 개선 전후 Flame Graph 비교 | CPU 비중 감소율 |

> 요약: 프로파일링 리스크는 호출 트리 추적, 환경별 기법 분리, 개선 전후 재측정으로 통제한다.

| 점검 항목 | 목표 기준 | 측정 방법 |
|:---|:---|:---|
| 핫스팟 개선 | 상위 함수 CPU 비중 30%->15% 이하로 감소 | Flame Graph 비교 |
| 오버헤드 | 프로파일링 적용 시 응답시간 증가 5% 이하 | 프로파일링 전후 p95 비교 |
| GC 압박 | Full GC 빈도·정지시간 감소 | 메모리 프로파일러, GC 로그 |

> 요약: 프로파일링 성과는 핫스팟 CPU 비중 감소, 낮은 오버헤드, GC 압박 완화로 판단한다.

## Ⅵ. 실무 적용 및 결론

**적용 방안 3개 (필수 — 단계별 또는 항목별):**
1. 운영 환경에는 async-profiler, JFR 같은 저오버헤드 샘플링 프로파일러를 상시 적용해 Flame Graph를 주기적으로 수집함
2. 상위 CPU 비중 함수를 확인한 뒤 호출 트리 caller까지 추적해 반복 호출을 유발한 로직을 근본 원인으로 특정함
3. 개선 전후 Flame Graph와 p95 응답시간을 비교해 리팩터링 효과를 정량 검증함

**결론 (2줄):**
- 기술사 판단: 프로파일링은 최상위 함수 교체가 아니라 호출 트리 근본 원인 추적을 통한 우선순위 개선이 핵심임
- 향후 방향: eBPF 기반 지속적 프로파일링(continuous profiling)이 운영 환경 상시 적용으로 확대되어 성능 회귀를 자동 탐지하는 방향으로 발전함
