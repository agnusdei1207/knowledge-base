## 미리 알고가기

- 샘플링 프로파일링: 일정 주기로 호출 스택을 수집해 통계적으로 병목을 찾는 방식임
- 계측 프로파일링: 함수 진입과 종료를 직접 기록해 실행 시간을 정밀하게 재는 방식임
- Self Time: 하위 함수 시간을 제외하고 해당 함수 내부에서만 소모한 시간임
- Off-CPU 대기: 락, I/O, sleep 때문에 CPU를 쓰지 못하고 기다리는 시간임

## Ⅰ. 개요

- **정의/개념**: 프로파일링은 프로그램이 실행되는 동안 함수 호출, CPU 사용, 메모리 할당, 대기 시간을 수집해 병목 구간을 찾는 동적 분석 기법이며, 핫스팟 분석은 그중 전체 지연에 가장 큰 영향을 주는 코드 경로를 우선순위로 도출하는 작업임
- **배경/필요성**: CPU 사용률이나 응답시간이 나빠졌다는 사실만으로는 어느 코드가 원인인지 알 수 없으므로, 추측에 의존한 튜닝 대신 실행 데이터로 병목 지점을 바로 찾는 절차가 필요함

## Ⅱ. 특징

- 실행 중인 실제 호출 경로를 기준으로 병목을 찾으므로 설계 문서보다 현재 코드 상태를 더 직접적으로 보여줌
- 샘플링과 계측은 정확도와 오버헤드가 다르므로 운영 환경과 개발 환경에서 같은 방식으로 쓰지 않음
- CPU를 많이 쓰는 구간뿐 아니라 락 대기나 외부 I/O 대기처럼 Off-CPU 지연도 함께 봐야 전체 지연 원인을 놓치지 않음
- Total Time과 Self Time을 구분해야 호출자 비용과 해당 함수 내부 비용을 나누어 볼 수 있음

## Ⅲ. 종류 및 비교

| 판단 기준 | 샘플링 프로파일링 | 계측 프로파일링 |
|:---|:---|:---|
| 수집 방식 | 일정 주기로 호출 스택을 가져와 통계적으로 실행 비중을 추정함 | 함수 진입과 종료를 직접 기록해 호출 횟수와 시간을 계산함 |
| 측정 정밀도 | 짧은 함수는 놓치지만 전체 병목 분포를 먼저 파악함 | 개별 함수 시간은 정확하지만 수집량이 많아짐 |
| 실행 오버헤드 | 상대적으로 낮아 운영 환경에도 적용하기 쉬움 | 오버헤드가 커서 개발과 시험 환경에 더 적합함 |
| 주요 활용 | 지속적 프로파일링, 운영 병목 탐지에 적합함 | 세밀한 코드 분석, 특정 함수 검증에 적합함 |

## Ⅳ. 구성요소 및 구조

| 구성요소 | 설명 |
|:---|:---|
| 대상 프로세스 | 병목이 의심되는 애플리케이션이며, 요청 경로와 부하 조건이 실제 문제 상황과 같아야 의미 있는 결과가 나옴 |
| 프로파일러 수집기 | 샘플링 또는 계측 방식으로 호출 스택과 자원 사용 정보를 모아 분석의 기초 데이터를 만듦 |
| 결과 저장 및 시각화 | 함수별 시간, 호출 횟수, 플레임 그래프 같은 형태로 결과를 보여 주어 병목 위치를 식별하게 함 |
| 분석 기준 | Total Time, Self Time, Off-CPU 대기, 메모리 할당량처럼 어떤 지표를 우선 볼지 정해 실제 튜닝 대상을 좁힘 |

```text
+-------------+     +-------------+     +-------------+     +-------------+
| 대상 프로세스   | --> | 프로파일러 수집기 | --> | 결과 저장/시각화 | --> | 병목 우선순위 도출 |
+-------------+     +-------------+     +-------------+     +-------------+
```

## Ⅴ. 원리 및 절차 흐름도

```text
+-------------+     +-------------+     +-------------+     +-------------+
| 부하 재현      | --> | 실행 데이터 수집 | --> | 핫스팟 정렬    | --> | 수정 후 재측정  |
+-------------+     +-------------+     +-------------+     +-------------+
```

1. **부하 재현**: 문제가 나타나는 요청 패턴과 데이터 규모를 같은 조건으로 재현함
2. **실행 데이터 수집**: 샘플링 또는 계측으로 함수별 시간과 대기 정보를 수집함
3. **핫스팟 정렬**: 전체 지연 기여도가 큰 함수와 코드 경로를 우선순위로 정렬함
4. **수정 후 재측정**: 코드나 설정을 바꾼 뒤 같은 조건으로 다시 측정해 실제 개선 여부를 확인함

## Ⅵ. 실무 적용 및 유의점

1. 운영 API 서버나 배치 시스템에서는 샘플링 기반 지속 프로파일링을 쓰되 오버헤드가 커지거나 CPU 지표만 보고 대기 병목을 놓치지 않도록 Off-CPU 분석을 함께 수행하고 profiler overhead와 p99 latency와 상위 함수 점유율로 확인함
2. 개발과 성능 시험 환경에서는 계측 프로파일링으로 특정 함수와 메모리 경로를 깊게 보되 계측 자체가 실행 흐름을 바꾸지 않도록 동일 시나리오로 전후 비교를 수행하고 Self Time 감소율과 처리량 증가율로 확인함

## Ⅶ. 결론

프로파일링과 핫스팟 분석은 자원이 많이 쓰인다는 현상을 코드 경로, 대기 시간, 함수 비용으로 좁혀 튜닝 우선순위를 정하게 함.

## 작성 근거(검토용)

- 프로파일링은 실행 데이터로 코드 병목을 찾는 키워드이므로 샘플링, 계측, Self Time, Off-CPU를 미리 설명함
- 넓은 평가어를 제거하고 Total Time, Self Time, profiler overhead, p99 latency처럼 확인 가능한 지표로 바꿈
- 실무 절은 운영 샘플링과 시험 계측으로 나누어 오버헤드와 재측정 조건을 함께 제시함
