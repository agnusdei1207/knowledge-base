# 📖 【암기용】 개념 완전 이해

## 한눈에
- **개요**: 프로파일링(Profiling)은 **실행 중 프로그램의 시간·자원 소비를 함수·코드 라인 단위로 계측해, 부하가 집중되는 핫스팟(Hotspot)을 식별하는 성능 진단 기법**이다.
- **왜 필요한가**: 병목이 어느 "자원"인지는 병목 분석(004)이 알려주지만, 그 안에서 어느 "코드·쿼리"가 시간을 먹는지는 실제 실행을 측정해야만 특정되기 때문이다.
- **핵심 직관**: 소스 코드 전체를 열화상 카메라로 찍어 뜨거운(시간을 많이 쓰는) 구간을 붉게 표시하는 것과 같다 — 짐작이 아니라 측정으로 최적화 대상을 좁힌다.

## 핵심 용어 정리 (내부에 등장하는 것들)

답안 Ⅰ~Ⅵ에 쓰이는 용어를 비유와 함께 먼저 못 박는다. 병목·이용률 등 기초는 004에서 정의했으므로 여기서는 코드 계측 관점으로 연결한다. 맨 위가 상위 핵심 키워드다.

| 용어/표기 | 의미 | 비유·예 |
|:---|:---|:---|
| 프로파일링(Profiling) | 실행 중 시간·자원 소비를 코드 단위로 계측 | 실행 코드를 찍는 열화상 카메라 |
| 핫스팟(Hotspot) | 전체 실행시간을 가장 많이 차지하는 코드 구간 | 지도에서 붉게 칠해진 정체 구간 |
| 샘플링(Sampling) 프로파일링 | 일정 주기로 스택을 엿봐 통계로 추정 | 1초마다 사진 찍어 어디 있었나 집계 |
| 계측(Instrumentation) 프로파일링 | 함수 진입·종료에 코드를 심어 전수 측정 | 모든 문에 출입 기록기를 붙임 |
| self time / total time | 함수 자체 소요 / 하위 호출 포함 소요 | 창구 직원 손시간 / 뒷단계 포함 총시간 |
| 콜 그래프(Call Graph) | 함수 호출 관계와 시간을 잇는 트리 | 누가 누구를 불렀나 계보도 |
| 플레임 그래프(Flame Graph) | 스택 깊이×점유시간을 가로막대로 시각화 | 넓은 막대일수록 오래 머문 구간 |
| CPU/off-CPU 프로파일 | 연산 대기 / I/O·락 대기 시간 구분 계측 | 일한 시간 / 멍하니 기다린 시간 |
| 오버헤드(Overhead) | 계측 자체가 유발하는 성능 왜곡 | 체온 재느라 환자를 깨우는 부작용 |

## 깊이 이해
- **배경·문제의식**: 병목 분석(004)으로 "DB가 병목"까지 좁혀도, DB 안의 어느 쿼리·인덱스가 원인인지는 알 수 없다. 프로파일링은 실행 프로파일(어느 함수가 몇 %의 시간을 썼는지)을 수집해 최적화 대상을 코드 라인까지 지목한다.
- **작동 원리(두 방식의 원리와 차이)**: 샘플링은 일정 주기(예: 10ms)마다 실행 스택을 엿봐 "그 순간 어느 함수에 있었나"를 세고, 표본이 많이 잡힌 함수를 핫스팟으로 추정한다 — 오버헤드가 낮아 운영 환경에 붙일 수 있으나 짧게 자주 호출되는 함수는 놓칠 수 있다. 계측은 함수 진입·종료에 측정 코드를 심어 호출 횟수·시간을 전수 기록한다 — 정확하지만 오버헤드가 커 측정 대상 자체를 느리게 만든다(관측자 효과).
- **핵심 원칙 — 파레토(80/20)**: 대개 전체 실행시간의 대부분을 소수 핫스팟이 차지한다. 프로파일은 이 소수를 찾아 "측정 없이 짐작으로 최적화(premature optimization)"하는 낭비를 막는다.
- **비유**: 전기요금이 많이 나올 때 집안 모든 콘센트를 새로 사는 대신, 계량기를 방마다 달아 전력을 가장 많이 먹는 가전 하나를 찾아 교체하는 것과 같다.
- **구체 예시(워크드)**: 응답시간 800ms 트랜잭션을 프로파일링하니 self time 기준 JSON 직렬화 함수가 520ms(65%)를 차지함이 드러났다. 이 한 함수를 스트리밍 방식으로 교체해 120ms로 줄이면 전체가 400ms로 개선된다 — 나머지 함수를 아무리 손봐도 얻지 못할 효과다.
- **흔한 오해·주의점**: ① CPU 프로파일만 보면 I/O·락 대기(off-CPU)로 느린 경우를 놓친다 — 대기 시간도 프로파일해야 한다. ② 계측 오버헤드가 크면 프로파일 결과 자체가 왜곡된다(느려진 함수가 실제보다 부풀려 보임). ③ 개발 환경 프로파일은 데이터량·동시성이 달라 운영 핫스팟과 다를 수 있어, 가능하면 운영 부하에서 샘플링해야 한다.

## 연결 개념
- 병목 분석(004) — 자원 병목을 좁힌 뒤 그 안의 코드 핫스팟을 지목하는 후속 단계
- APM(011) — 분산 추적으로 서비스 간 핫스팟을 찾고, 코드 프로파일러로 함수까지 내려감
- 암달의 법칙(007) — 핫스팟이 차지하는 비율이 곧 최적화로 얻을 수 있는 개선 상한

# 📝 【답안용】 시험 답안 템플릿

## 핵심 인사이트 (3줄 요약)

> 1. **본질**: 프로파일링은 실행 프로파일을 코드 단위로 계측해 시간을 지배하는 핫스팟을 측정으로 특정하는 진단 기법임.
> 2. **가치**: 소수 핫스팟이 실행시간 대부분을 차지하므로, 짐작 최적화 대신 측정 기반으로 대상을 좁혀 최소 노력으로 최대 개선을 얻음.
> 3. **판단 포인트**: 오버헤드 낮은 샘플링은 운영 진단에, 정밀한 계측은 개발 분석에 쓰며 CPU·off-CPU를 함께 봐야 함.

## 출제 의도 및 답안 포인트

| 출제 의도 | 반드시 짚을 핵심 | 감점 회피 포인트 |
|:---|:---|:---|
| 프로파일링 원리 이해 | 실행 계측으로 핫스팟 self/total time 식별 | 코드 특정 없이 추상 서술 |
| 방식 선택 판단 | 샘플링 vs 계측 오버헤드·정밀도 트레이드오프 | 방식 구분 없이 단일 도구 단정 |
| 최적화 연계 | 파레토 핫스팟 집중, CPU·off-CPU 병행 | CPU만 보고 I/O 대기 누락 |

> 요약: 정의보다 실행 계측으로 핫스팟을 특정하는 원리와 샘플링·계측 선택 판단을 보여야 함.

---

## Ⅰ. 개요 및 필요성

- 개요: 실행 중 프로그램의 시간·자원 소비를 코드 단위로 계측해 핫스팟을 식별하는 성능 진단 기법
- 배경: 자원 병목(004)을 좁혀도 그 안의 어느 코드·쿼리가 원인인지는 실행 측정 없이 특정 불가함
- 필요성: 소수 핫스팟이 실행시간 대부분을 차지해, 측정으로 대상을 좁혀야 최적화 노력이 효과로 연결됨

---

## Ⅱ. 구조 및 구성요소

- 프로파일링 파이프라인(선형 구조도):

```text
Workload 실행 -> 프로파일 수집(샘플링/계측)
  -> 콜 그래프·플레임 그래프 집계 -> self/total time 정렬
  -> 핫스팟 식별 -> 최적화 적용 -> 재프로파일로 효과 확인
```

| 구성요소 | 역할 | 특이사항 |
|:---|:---|:---|
| 프로파일러 | 스택 샘플링 또는 함수 계측 수집 | perf·async-profiler·pprof |
| 콜 그래프 집계기 | 호출 관계·시간 트리 구성 | self/total time 분리 |
| 플레임 그래프 | 스택×점유시간 시각화 | 넓은 막대가 핫스팟 |
| off-CPU 계측 | I/O·락 대기 시간 수집 | CPU 외 지연 포착 |

> 요약: 실행을 샘플링·계측으로 수집해 콜/플레임 그래프로 집계하고 핫스팟을 정렬해 지목함.

---

## Ⅲ. 동작원리 및 흐름도

- 수집~최적화 흐름(선형 흐름도):

```text
프로파일 수집 -> 함수별 self/total time 집계 -> 핫스팟 정렬(상위 점유)
  -> 원인 분석(CPU/off-CPU) -> 코드·쿼리 최적화 -> 재프로파일 검증
```

1. 프로파일러가 운영 부하에서 실행 스택을 주기 샘플링하거나 함수 진입·종료를 계측함
2. 수집 데이터를 함수별 self time·total time으로 집계해 점유 비율 상위를 핫스팟으로 정렬함
3. 분석자가 핫스팟이 연산(CPU)인지 대기(off-CPU I/O·락)인지 구분해 원인을 판정함
4. 해당 코드·쿼리를 최적화한 뒤 재프로파일해 점유율 감소와 다음 핫스팟을 확인함

---

## Ⅳ. 특징

- 실행 프로파일을 코드·라인 단위로 계측해 최적화 대상을 짐작이 아닌 측정으로 특정함
- 소수 핫스팟이 실행시간 대부분을 차지하는 파레토 구조라 집중 최적화 효과가 큼
- 샘플링은 오버헤드가 낮아 운영 상시 진단이 가능하나 드문 짧은 함수는 놓칠 수 있음
- 계측은 전수 정밀 측정이나 오버헤드가 커 관측자 효과로 결과가 왜곡될 수 있음
- CPU 프로파일만 보면 I/O·락 대기(off-CPU) 지연을 놓쳐 원인 오판 위험이 있음

---

## Ⅴ. 심화 비교 및 적용 판단

- 샘플링 프로파일링 vs 계측 프로파일링:

| 구분 | 샘플링 프로파일링 | 계측 프로파일링 |
|:---|:---|:---|
| 측정 방식 | 주기적 스택 표본 통계 추정 | 함수 진입·종료 전수 기록 |
| 오버헤드 | 낮음(운영 상시 부착 가능) | 높음(대상 자체를 느리게 함) |
| 정밀도 | 통계적, 드문 함수 누락 가능 | 호출 횟수·시간 정확 |
| 적용 국면 | 운영 환경 상시 진단 | 개발·재현 환경 정밀 분석 |

> 요약: 운영 상시 진단은 저오버헤드 샘플링, 정밀 재현 분석은 계측을 선택함.

- 리스크와 대응(불릿):
  - 계측 오버헤드로 왜곡 → 무거운 계측을 운영에 부착 → 운영은 샘플링, 계측은 재현 환경 한정(확인: 프로파일 전후 응답시간 차)
  - off-CPU 누락 → CPU 프로파일만 수집 → I/O·락 대기 프로파일 병행(확인: 총 응답시간 대비 CPU 시간 합)
  - 환경 불일치 → 개발 데이터로 핫스팟 판정 → 운영 부하·데이터량에서 재측정(확인: 운영·개발 핫스팟 일치도)

---

## Ⅵ. 실무 적용 및 결론

- 적용 방안:
  1. 운영 환경에 async-profiler·perf 등 저오버헤드 샘플러를 상시 부착해 플레임 그래프로 핫스팟을 관측함
  2. 재현 가능한 개발 환경에서 계측 프로파일러로 상위 핫스팟의 호출 횟수·self time을 정밀 분석해 원인을 확정함
  3. CPU·off-CPU를 함께 수집해 연산·I/O·락 대기를 구분하고 최적화 후 재프로파일로 점유율 감소를 검증함
- 결론:
  - 프로파일링은 병목 분석(004)이 좁힌 자원 안에서 코드 핫스팟을 측정으로 특정하는 최적화의 선행 절차임
  - 운영 상시 프로파일링을 관측성 플랫폼과 연계해 지속적 성능 회귀를 자동 탐지하는 체계로 확장 필요
