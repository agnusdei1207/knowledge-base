# 📖 【암기용】 개념 완전 이해

## 한눈에
- **개요**: 시스템 성능 지표(System KPI)는 시스템의 처리 능력·응답 속도·연속성을 정량화하는 **TPS·응답시간·처리량·가용성** 4대 핵심 지표다.
- **왜 필요한가**: "느리다·불안정하다"는 주관적 표현으로는 SLA 계약도 튜닝 우선순위도 정할 수 없어, 정의·단위·측정구간이 합의된 객관적 잣대가 필요하다.
- **핵심 직관**: 응급실을 볼 때 시간당 진료 환자 수(TPS), 환자 1명이 접수부터 진료 완료까지 걸린 시간(응답시간), 하루 총 진료량(처리량), 응급실이 정상 운영된 시간 비율(가용성)을 각각 재는 것과 같다 — 네 지표는 서로 다른 축을 본다.

## 핵심 용어 정리

아래는 이 문서 답안부에 등장하는 모든 용어다. 네 지표가 각각 무엇을 재는지부터 몸에 익힌다.

| 용어/표기 | 의미 | 비유·예 |
|:---|:---|:---|
| 시스템 성능 지표(KPI) | 성능을 수치로 나타낸 핵심 성과 지표의 집합 | 자동차 계기판 — 속도·연비·주행거리를 한눈에 |
| TPS (Transactions Per Second) | 1초에 완료된 트랜잭션(작업) 수, 처리 속도 | 톨게이트를 1초에 몇 대가 통과하는가 |
| 응답시간(Response Time) | 요청 시작~응답 완료까지 걸린 시간(체감 지연) | 차 1대가 진입~출차까지 걸린 시간 |
| 처리량(Throughput) | 단위 시간당 처리한 총 작업·데이터량(용량) | 하루 동안 통과한 총 차량 수 |
| 가용성(Availability) | 전체 시간 중 정상 서비스한 시간의 비율(연속성) | 도로가 통제 없이 개통돼 있던 시간 비율 |
| p95·p99 | 응답시간을 정렬해 하위 95%·99%가 넘지 않는 값(꼬리 지연) | 100명 중 95번째로 느린 사람의 대기시간 |
| 리틀의 법칙(Little's Law) | 시스템 내 평균 개수 L = 도착률 λ × 체류시간 W | 매장 내 평균 손님 수 = 분당 입장객 × 평균 체류분 |
| 동시 사용자(Concurrency) | 같은 순간 시스템 안에 머무는 요청 수(N = TPS × 응답시간) | 지금 이 순간 매장 안에 있는 손님 수 |
| SLA (Service Level Agreement) | 성능·가용성 목표치를 문서로 약속한 서비스 수준 협약 | "응답 300ms 이내, 가용성 99.9%"라는 계약서 |
| Downtime(정지시간) | 서비스가 비정상이었던 누적 시간(가용성의 분자 반대편) | 도로가 통제됐던 총 시간 |

## 깊이 이해
- **배경·문제의식**: 성능 문제를 "느리다" 한마디로 보고하면 원인(자원 포화·대기 적체·장애)을 구분할 수 없어 개선 대상을 특정하지 못한다. 그래서 서로 다른 축을 재는 여러 지표로 분해한다.
- **작동 원리 — 네 지표의 산식**:
  - TPS = (기간 내 완료 트랜잭션 수) ÷ (기간 초). 성공 트랜잭션만 셀지, 실패도 포함할지 정의가 선행돼야 한다.
  - 응답시간 = 응답 완료 시각 − 요청 시작 시각. 평균은 이상치에 왜곡되므로 실무는 p95·p99(꼬리 지연)로 본다.
  - 처리량 = 단위 시간당 처리한 총량. 단위가 TPS(건/초)일 수도, Mbps(비트/초)일 수도 있어 단위 명시가 필수다.
  - 가용성 = MTBF ÷ (MTBF + MTTR) = 정상시간 ÷ 전체시간. 즉 얼마나 자주 고장 안 나고(MTBF), 나면 얼마나 빨리 복구하느냐(MTTR)의 함수다.
- **리틀의 법칙으로 세 지표를 잇기**: 동시 사용자 N = TPS × 응답시간(W). 예를 들어 TPS 500건, 평균 응답시간 0.2초면 시스템 안에는 늘 평균 500 × 0.2 = 100개의 요청이 처리 중이다. 이 식 덕분에 "동시 사용자 100명, 응답 0.2초 목표 → 필요 TPS 500"처럼 용량을 역산할 수 있다.
- **비유**: 고속도로에서 TPS는 톨게이트 통과 대수(속도), 응답시간은 한 차의 진입~출차 시간(지연), 처리량은 하루 총 통행량(용량), 가용성은 도로 개통 시간 비율(연속성)이다. 톨게이트가 빨라도(높은 TPS) 도로가 막히면(대기) 한 차의 출차 시간(응답시간)은 길어질 수 있다.
- **구체 예시 — 가용성 %의 실제 무게**: 99.9%는 연간 약 8.76시간, 99.99%는 약 52.6분, 99.999%(파이브 나인)는 약 5.26분의 downtime만 허용한다. "9" 하나 늘릴 때마다 허용 정지시간이 1/10로 줄어 이중화·자동 페일오버 비용이 급증한다.
- **흔한 오해·주의점**: TPS가 높다고 응답시간이 짧은 것은 아니다. 자원이 포화에 근접하면 TPS는 목표를 유지해도 대기시간만 폭증해 응답시간이 급격히 나빠진다(throughput↔latency 혼동 금지). 또 평균 응답시간만 보고하면 소수 사용자의 극심한 지연(꼬리 지연)을 놓친다.

## 연결 개념
- 응답 시간 분해(002) — 응답시간을 대기시간+서비스시간으로 쪼개는 하위 관점
- 처리율·대역폭(003) — 처리량을 이론 상한(대역폭)과 실측치로 구분하는 하위 관점
- 리틀의 법칙·큐잉 이론 — TPS·응답시간·동시 사용자를 잇고, 대기가 생기는 수학적 근거

# 📝 【답안용】 시험 답안 템플릿

## 핵심 인사이트 (3줄 요약)

> 1. **본질**: 시스템 성능은 TPS(속도)·응답시간(지연)·처리량(용량)·가용성(연속성) 4개 축으로 정량화하며 각 축은 서로 다른 것을 잼.
> 2. **가치**: 지표를 분리해야 병목 원인(자원 포화 vs 대기 적체 vs 장애)을 구분하고 개선 우선순위를 정할 수 있음.
> 3. **판단 포인트**: SLA는 TPS 목표·응답시간 백분위수(p95·p99)·가용성 %·측정구간을 함께 명시해야 분쟁을 예방함.

## 출제 의도 및 답안 포인트

| 출제 의도 | 반드시 짚을 핵심 | 감점 회피 포인트 |
|:---|:---|:---|
| 4대 지표 정의·구분 역량 확인 | 지표별 정의·단위·산식과 측정 축 차이 | 단위·측정구간 구분 없는 추상 서술 |
| SLA 설계 역량 확인 | 평균이 아닌 p95·p99, 가용성 계산식 | 평균값만 제시·백분위수 누락 |
| 지표 간 상충 이해 확인 | 자원 포화 시 TPS 유지·응답시간 악화 | TPS·응답시간을 비례 관계로 단정 |

> 요약: 지표 나열이 아니라 산식과 SLA 설계 시 지표 간 상충(trade-off)을 보여야 함.

---

## Ⅰ. 개요 및 필요성

- 개요: 시스템의 처리 속도·응답 속도·용량·연속성을 수치화한 4대 성능 지표
- 배경: "느리다·불안정하다"는 주관적 표현은 원인을 특정하지 못해 객관적 잣대가 요구됨
- 필요성: SLA 계약·용량 산정·장애 판단의 공통 기준이 되려면 정의·단위·측정구간의 합의가 선행돼야 함

---

## Ⅱ. 구조 및 구성요소

- 측정 흐름(선형 구조도):

```text
Workload(요청) -> 측정 지점(Probe/APM)
  -> [TPS 집계] [응답시간 집계 p50/p95/p99] [처리량 집계] [가용성 집계 Uptime]
  -> SLA 기준값과 비교 -> 위반 시 경보/튜닝 피드백
```

| 구성요소 | 역할 | 특이사항 |
|:---|:---|:---|
| TPS Counter | 초당 완료 트랜잭션 수 집계 | 성공 트랜잭션 포함 범위 정의 필요 |
| Response Time Probe | 요청~응답 완료 시간 측정 | 평균이 아닌 p95·p99로 보고 |
| Throughput Meter | 단위 시간당 처리 데이터·작업량 집계 | 단위(TPS·RPS·Mbps) 명시 필수 |
| Availability Monitor | 정상 서비스 시간 비율 산출 | 계획·비계획 정지 구분 |

> 요약: 4대 지표는 각각 별도 측정 지점·산식을 가지며 SLA 비교를 위해 함께 수집됨.

---

## Ⅲ. 동작원리 및 흐름도

- 수집~판정 흐름(선형 흐름도):

```text
요청 발생 -> 응답시간 측정 -> TPS·처리량 누적 집계
  -> 정지시간 기록 -> 가용성 산출 -> SLA 비교 -> 초과 시 경보
```

1. 각 요청 단위로 시작~완료 시각을 기록해 응답시간을 측정하고 분포(p95·p99)를 계산함
2. 완료 트랜잭션을 누적해 TPS·처리량을 초당 단위로 집계함
3. 장애·정지 구간을 누적해 가용성(= 정상시간 ÷ 전체시간)을 산출함
4. 네 지표를 SLA 목표값과 비교해 위반 시 경보·오토스케일링을 촉발함

---

## Ⅳ. 특징

- TPS·응답시간·처리량은 성능(speed·capacity), 가용성은 연속성(continuity)을 재는 서로 다른 축임
- 응답시간은 평균이 이상치에 왜곡되므로 p95·p99(꼬리 지연)로 보고해야 사용자 체감을 반영함
- 리틀의 법칙(N = TPS × 응답시간)으로 세 지표가 연결돼 용량을 역산할 수 있음
- 가용성은 "9" 하나 늘 때마다(99.9%→99.99%) 허용 downtime이 1/10로 줄어 이중화 비용이 급증함
- 처리량 단위(TPS·RPS·Mbps)를 명시하지 않으면 서로 다른 값이 혼동돼 용량 산정이 틀어짐

---

## Ⅴ. 심화 비교 및 적용 판단

- 응답시간 대푯값 선택 — 평균 vs 백분위수:

| 구분 | 평균 응답시간 | 백분위수(p95·p99) |
|:---|:---|:---|
| 대표성 | 이상치에 왜곡됨 | 꼬리 지연 반영 |
| 계산 비용 | 단순 합산·나눗셈 | 분포 정렬·백분위 계산 |
| 활용 | 용량 산정 참고치 | SLA 위반 판정 기준 |

> 요약: 용량 산정은 평균, SLA 판정은 p95·p99를 기준으로 삼음.

- 리스크와 대응(단일 축이라 불릿):
  - TPS 충족·응답시간 악화 → 자원 포화로 대기 증가 → 사용률 모니터링·오토스케일링(확인: CPU·커넥션 사용률, p95)
  - 평균값 왜곡 보고 → 이상치 미반영 → p95·p99 병행 보고(확인: 응답시간 분포, tail latency)
  - 가용성 정의 불일치 → 계획 정지 포함 여부 미합의 → SLA에 정지 유형·측정구간 명시(확인: downtime 로그)

---

## Ⅵ. 실무 적용 및 결론

- 적용 방안:
  1. SLA 문서에 TPS 목표·응답시간 p95·p99·가용성 %·측정구간을 함께 명시함
  2. APM(예: Pinpoint·Datadog)으로 4대 지표를 동시 수집하고 대시보드에서 상관관계를 확인함
  3. 부하테스트로 TPS 증가 시 응답시간 변곡점을 사전 파악해 오토스케일링 임계값을 설정함
- 결론:
  - 성능 평가는 단일 지표가 아니라 4대 지표를 함께 정의해야 SLA 분쟁을 예방함
  - 지표 수집을 관측성(Observability) 플랫폼과 연계해 실시간 상관 분석·자동 경보로 확장 필요
