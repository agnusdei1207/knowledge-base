## 미리 알고가기

- SPOF: 한 구성 요소만 고장 나도 전체 서비스가 멈추는 단일 장애점임
- Fault Domain: 같은 장애 원인을 공유하는 범위이며 전원, 랙, AZ, 리전까지 포함함
- 공통 원인 고장: 장비는 여러 대여도 같은 전원이나 같은 센터를 써서 함께 멈추는 장애임
- N+1: 필요한 수량보다 하나 이상의 예비 자원을 더 두는 이중화 방식임

## Ⅰ. 개요

- **정의/개념**: SPOF 제거는 서비스 요청이 지나가는 경로에서 단독으로 존재하는 구성 요소와 공통 원인 고장을 일으키는 공유 자원을 찾아 이중화하거나 분리하는 아키텍처 개선 활동임
- **배경/필요성**: 서버 수를 많이 늘려도 전원, 로드밸런서, 회선, 단일 DB처럼 한 지점이 전체를 멈추게 하면 목표 가용성을 달성할 수 없으므로 경로 전체를 기준으로 취약 지점을 제거해야 함

## Ⅱ. 특징

- 서버만이 아니라 전원, 네트워크, 스토리지, 외부 의존 서비스까지 모두 점검 대상이 됨
- 장비 수량을 늘리는 것만으로는 충분하지 않고 장애 도메인을 실제로 분리해야 효과가 남음
- 직렬 경로가 길수록 전체 가용성은 약한 고리에 의해 제한되므로 병목보다 취약 경로가 먼저 보일 수 있음
- 설계 문서상 이중화와 실제 장애 복원력은 다를 수 있어 장애 주입 시험이 필요함

## Ⅲ. 종류 및 비교

| 판단 기준 | 논리적 SPOF | 공통 원인 고장 |
|:---|:---|:---|
| 발생 형태 | 특정 기능을 수행하는 장비나 서비스가 한 대뿐임 | 장비는 여러 대지만 같은 전원, 랙, AZ, 리전을 공유해 함께 영향을 받음 |
| 대표 예 | 단일 로드밸런서, 단일 DB 인스턴스, 단일 DNS 경로 | 같은 랙에 놓인 이중화 서버, 같은 회선을 쓰는 이중 ISP 구성 |
| 대응 방식 | N+1, Active-Standby, Active-Active처럼 직접 이중화함 | 전원, 네트워크, 물리 위치까지 장애 도메인을 분리함 |
| 검증 포인트 | 대체 노드가 실제로 승계하는지 확인함 | 공통 자원 단절 시에도 서비스가 유지되는지 확인함 |

## Ⅳ. 구성요소 및 구조

| 구성요소 | 설명 |
|:---|:---|
| 종단 간 의존성 맵 | 사용자 요청이 DNS, LB, 앱, DB, 저장소를 거쳐 응답되는 전체 경로를 그려 취약 지점을 찾게 함 |
| 이중화 설계 | 단일 장비나 서비스에 예비 경로와 대체 노드를 두어 장애 시 우회 가능하게 만듦 |
| 장애 도메인 분리 | 랙, 전원, AZ, 리전 같은 물리·논리 경계를 나눠 공통 원인 고장을 줄임 |
| 복원력 검증 절차 | 장애 주입과 모의 훈련으로 설계가 실제로 동작하는지 검증함 |

```text
+-------------+     +-------------+     +-------------+     +-------------+
| 의존 경로 도식화 | --> | 단일 요소 식별  | --> | 이중화/분리 설계 | --> | 장애 시험 검증  |
+-------------+     +-------------+     +-------------+     +-------------+
```

## Ⅴ. 원리 및 절차 흐름도

```text
+-------------+     +-------------+     +-------------+     +-------------+
| 서비스 경로 분석 | --> | SPOF 후보 선정 | --> | 대체 경로 구축  | --> | 장애 주입 확인  |
+-------------+     +-------------+     +-------------+     +-------------+
```

1. **서비스 경로 분석**: 사용자 요청이 지나가는 모든 구성 요소를 정리함
2. **SPOF 후보 선정**: 단일 장비와 공통 자원 의존 구간을 찾아냄
3. **대체 경로 구축**: 이중화와 장애 도메인 분리로 우회 경로를 만듦
4. **장애 주입 확인**: 실제로 장애를 주입해 서비스가 유지되는지 검증함

## Ⅵ. 실무 적용 및 유의점

1. 데이터센터와 대형 서비스 점검에서는 서버만 보지 말고 DNS, LB, DB, 전원, 회선까지 종단 경로를 같이 그려야 하므로 의존성 맵과 우회 설계를 운영하고 SPOF count와 failover success rate로 확인함
2. 클라우드와 멀티 AZ 구조에서는 논리적 이중화만 믿지 말고 전원, 랙, AZ, 리전 분리까지 적용한 뒤 정기 장애 주입 시험을 수행하고 common-cause incident count와 chaos drill pass rate로 확인함

## Ⅶ. 결론

SPOF 제거의 핵심은 장비를 두 대 두는 데 있지 않고 서비스 경로 전체에서 공유 장애 도메인까지 끊어 내는 데 있음.
