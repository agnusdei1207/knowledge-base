## 📖 【암기용】 핵심 요약

*   **한눈에**: 시스템 구성 요소 중 이중화되지 않아, 해당 요소 하나만 장애가 나도 시스템 전체가 마비되는 **'단일 고장점(SPOF)'**을 식별하고 제거하는 아키텍처 개선 활동.
*   **깊이 이해**:
    *   **배경**: 서버를 100대나 사서 Active-Active로 묶어놨는데, 그 앞단에 있는 1대의 로드밸런서(L4 스위치) 전원이 나갔더니 전체 서비스가 중단됨. 이처럼 시스템 가용성은 **가장 취약한 단일 링크(SPOF)**의 가용성을 절대 넘을 수 없음.
    *   **작동 원리**: 사용자 요청이 들어와서 응답이 나갈 때까지 거치는 모든 경로(DNS, CDN, L4, Web, WAS, DB, Storage, Network, Power)를 도식화함. 경로 상에 '단일 박스'로 존재하는 녀석을 찾아내어, 모두 다중화(N+1, Active-Standby 등) 처리함.
    *   **비유**: **다리 건설**. 교각 100개를 아무리 튼튼하게 지어도, 상판을 받치는 케이블 하나가 끊어졌을 때 다리 전체가 무너진다면 그 케이블이 바로 SPOF임. 케이블을 2중, 3중으로 엮어(Redundancy) 하나가 끊어져도 버틸 수 있게 만들어야 함.
    *   **구체 예시**: 카카오톡 데이터센터 화재 사태. 수만 대의 서버가 있었으나, 전원을 공급하는 배터리실(SPOF) 화재 하나로 전체 시스템이 다운됨. 이를 막기 위해 데이터센터 자체를 이중화(Multi-Region)해야 함.
    *   **흔한 오해/주의점**: "모든 장비를 두 대씩 샀으니 SPOF는 완벽히 제거됐다!" $\rightarrow$ **오답**. 장비가 두 대라도 동일한 랙(Rack)에 꽂혀 있거나 동일한 멀티탭(Power)을 쓰고 있다면, 논리적 이중화만 되었을 뿐 물리적 SPOF는 여전히 존재하는 것임(공통 원인 고장, Common Cause Failure). 
*   **연결 개념**: 직렬/병렬 가용성 계산, Fault Tolerance, 고가용성(HA), Multi-AZ, Chaos Engineering

## 📝 【답안용】 서술 골격

> **💡 핵심 인사이트**
> *   **본질**: 사슬의 강도는 가장 약한 고리에 의해 결정된다는 원리에 따라, 인프라 내의 **비이중화 노드 및 공통 공유 자원**을 제거하는 작업.
> *   **가치**: 고가의 서버 증설 효과가 단일 네트워크 장비 장애로 무효화되는 것을 방지하여, IT 투자 대비 실제 가용성(ROI)을 보장.
> *   **판단 포인트**: 장비(H/W) 수준의 논리적 SPOF뿐만 아니라, 전원, 회선, 물리적 위치(Data Center)까지 고려하는 **다차원적 장애 도메인(Fault Domain) 분리**가 핵심.

### Ⅰ. 아키텍처의 아킬레스건, SPOF (Single Point of Failure) 개요
*   **정의**: 시스템 구성 요소 중에서 단독으로 동작하며 이중화되어 있지 않아, 해당 요소에 장애 발생 시 전체 시스템의 중단을 초래하는 취약 지점.
*   **직렬 가용성의 법칙**: 시스템 내 노드들이 직렬로 연결되어 있을 때 전체 가용성은 각 노드 가용성의 곱($A = A_1 \times A_2 \times A_3$)이 됨. 즉, SPOF가 하나라도 존재하면 전체 가용성은 기하급수적으로 하락함.

### Ⅱ. SPOF 식별을 위한 계층별(Layer) 점검 체계
*   **Facility (물리 환경)**: 전원(UPS), 냉각 장치(항온항습기), 물리적 건물.
*   **Network (통신망)**: 라우터, L4/L7 로드밸런서, 방화벽, 전용선, DNS.
*   **System (서버/스토리지)**: 단일 Web/WAS 서버, 단일 DB 인스턴스, 공유 스토리지(SAN).
*   **Application (소프트웨어)**: 단일 인증(SSO) 서버, 타 서비스에 동기식으로 연결된 외부 API 의존성.

### Ⅲ. SPOF 제거(Elimination) 전략 및 기법
*   **Redundancy (이중화/다중화)**: 
    *   Stateless 노드: N+1 단위의 Active-Active 구성 및 오토스케일링.
    *   Stateful 노드(DB): Active-Standby 동기/비동기 복제 클러스터링.
*   **Decoupling (의존성 분리)**:
    *   메시지 큐(Kafka, RabbitMQ)를 도입하여, 뒷단 시스템(SPOF)이 죽더라도 앞단에서 메시지를 유실하지 않고 버퍼링할 수 있도록 비동기 분리.
*   **Graceful Degradation (우아한 성능 저하)**:
    *   추천 알고리즘 API(SPOF)가 죽었을 때 서비스 전체를 다운시키지 않고, 캐싱된 기본 상품 목록을 보여주도록 Fallback 로직 설계 (Circuit Breaker 패턴).

### Ⅳ. 은닉된 SPOF: 공통 원인 고장 (Common Cause Failure) 방어
*   논리적으로는 서버를 2대 샀더라도 물리적 환경이 겹치면 진정한 SPOF 제거가 아님.
*   **장애 도메인(Fault Domain)의 분리**:
    *   **랙(Rack) 분산**: 이중화된 서버를 서로 다른 랙에 배치 (ToR 스위치 장애 대비).
    *   **전원 분산**: A 서버는 한국전력 A 라인, B 서버는 B 라인에서 이중 급전.
    *   **AZ(Availability Zone) 분산**: 클라우드 환경에서는 노드를 서로 다른 가용 영역에 분산 배치하여 지진/화재 등 데이터센터 단위 재난 대피.

### Ⅴ. 지속적 SPOF 탐지: 카오스 엔지니어링 (Chaos Engineering)
*   SPOF 제거는 도면상의 설계만으로는 검증할 수 없음. 
*   Netflix의 Chaos Monkey처럼 운영 환경(또는 스테이징)에서 **의도적으로 스위치 전원을 끄고 DB 인스턴스를 죽이는 장애 주입(Fault Injection)** 실험을 통해, 숨겨진 SPOF와 복원력을 정기적으로 검증해야 함.
