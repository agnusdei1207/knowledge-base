# 📖 【암기용】 개념 완전 이해

## 한눈에
- **개요**: SPOF(Single Point of Failure)는 **시스템 신뢰성 분석**에서 그 하나가 장애나면 전체 서비스가 중단되는 **비이중화 지점**을 가리키며, 이를 식별·제거하는 것이 가용성 확보의 출발점임.
- **왜 필요한가**: 나머지 구성요소를 아무리 이중화해도 SPOF 하나가 남아 있으면 직렬 가용성 곱셈에 의해 시스템 전체 가용성이 그 SPOF의 가용성에 묶임.
- **핵심 직관**: 체인은 가장 약한 고리 하나가 끊어지면 전체가 끊어짐 — 이중화 안 된 지점 하나가 시스템 전체를 무너뜨림.

## 핵심 용어 정리 (내부에 등장하는 것들)

023이 HA 이중화 구조(Active-Active/Standby)를, 030이 N+1·2N 용량 모델을 다루므로 여기서는 SPOF 고유의 식별·제거 용어에 집중함.

| 용어/표기 | 의미 | 비유·예 |
|:---|:---|:---|
| SPOF (상위 키워드) | 단독 장애로 전체 서비스를 중단시키는 비이중화 구성요소 | 체인의 가장 약한 고리 |
| 직렬 가용성 | 직렬 연결 시 전체 가용성 = 각 요소 가용성의 곱 | A₁×A₂×...×Aₙ |
| 장애 도메인 | 동일 물리 자원(랙·전원·AZ)을 공유하는 범위 | 같은 전기 회로에 물린 장비들 |
| 상관 장애 | 장애 도메인 공유로 복수 구성요소가 동시 장애나는 현상 | 정전 시 같은 회로의 장비 전부 꺼짐 |
| FTA(032) | Fault Tree Analysis, SPOF를 체계적으로 도출하는 분석 기법 | 장애 원인의 나무 구조 역추적 |
| 카오스 엔지니어링 | 의도적 장애 주입으로 SPOF 잔존 여부를 검증하는 실험 | 일부러 불 끄고 비상등 작동 확인 |

## 깊이 이해
- **배경·문제의식**: (023 참조) 서버만 Active-Active로 이중화하고 LB·전원·네트워크 스위치·DB를 단일 구성으로 두면 이중화 효과가 무효화됨. 직렬 연결된 구성요소의 전체 가용성은 각 요소 가용성의 곱이므로 — 예: 서버 99.99% × LB 99.9% × DB 99.9% = 99.79% — SPOF 하나의 낮은 가용성이 전체를 지배함.
- **작동 원리 — SPOF 식별**:
  - 아키텍처 다이어그램의 전 구성요소(전원/UPS, 네트워크 스위치, LB, WAS, DB, 스토리지, DNS, 인증서 발급 시스템 등)를 나열함.
  - 각 요소의 이중화 여부를 점검하고 단일 구성 요소를 SPOF 후보로 분류함.
  - FTA(032)로 최상위 장애 이벤트에서 역추적하면 은닉 SPOF(DNS, 인증서, 설정 저장소 등)까지 체계적으로 도출 가능.
- **작동 원리 — SPOF 제거**:
  - 이중화 방식 적용: Active-Active(023), Active-Standby(023), N+1/2N(030) 중 적합한 방식 선택.
  - 물리적 분리 검증: 이중화 노드가 같은 랙·전원·AZ에 배치되면 논리적 이중화가 물리적 상관 장애로 무효화됨 → 반드시 서로 다른 장애 도메인에 분산 배치.
  - 관리형 서비스 대체: LB·DNS 같은 인프라 요소를 클라우드 관리형(Managed) 서비스로 대체하면 제공자가 이중화를 보장.
- **비유**: 자동차 타이어 4개 중 스페어가 없으면 1개 펑크로 운행 중단. 4개 타이어 각각에 스페어를 두되, 스페어가 같은 타이어 가게(장애 도메인)에 보관되면 가게 화재 시 스페어도 쓸 수 없음.
- **구체 예시**: 서버 2대 이중화 + LB 1대 단일 구성 → LB 장애 시 서버 2대가 살아있어도 트래픽 유입 불가 → LB를 Active-Standby 2대(VIP 이중화)로 구성해 SPOF 제거. AWS 환경에서는 ALB가 멀티 AZ 이중화를 기본 제공.
- **흔한 오해·주의점**: ① 서버 이중화만으로 SPOF 제거 완료라고 오판하기 쉬움 — 전원·네트워크·DNS·인증서도 SPOF 후보. ② 이중화 노드가 같은 랙·전원·AZ에 있으면 물리적 SPOF가 잔존. ③ 이중화 후 페일오버 테스트를 하지 않으면 실제 장애 시 전환 실패 가능 — 카오스 엔지니어링으로 검증 필수.

## 연결 개념
- **고가용성 설계 (023)**: SPOF 제거를 구현하는 이중화 아키텍처(AA/AS). 023이 구조를, 024가 식별·제거를 담당.
- **이중화 구성 N+1·2N (030)**: SPOF 제거를 용량 관점에서 정량화한 모델.
- **FTA 결함 나무 분석 (032)**: SPOF 후보를 체계적으로 도출하는 분석 기법.

# 📝 【답안용】 시험 답안 템플릿

## 핵심 인사이트 (3줄 요약)

> 1. **본질**: SPOF는 비이중화 구성요소로, 단독 장애 시 전체 서비스를 중단시키는 지점임.
> 2. **가치**: SPOF를 제거하면 직렬 가용성 곱에서 병목이 사라져 목표 SLO(021) 달성이 가능해짐.
> 3. **판단 포인트**: 논리적 이중화 + 물리적 분리(장애 도메인 분산) + 페일오버 검증 3단계를 모두 거쳐야 SPOF 제거가 완성됨.

## 출제 의도 및 답안 포인트

| 출제 의도 | 반드시 짚을 핵심 | 감점 회피 포인트 |
|:---|:---|:---|
| SPOF 식별 역량 | 전 계층(전원·네트워크·LB·DB) 점검 | 서버 계층만 언급 |
| 가용성 정량화 이해 | 직렬 가용성 곱셈 관계(A₁×A₂×...Aₙ) | 정성적 "약하다"만 서술 |
| 물리적 분리 이해 | 장애 도메인(랙·전원·AZ) 분산 배치 | 논리적 이중화만 언급, 물리 분리 누락 |

> 요약: 전 계층 SPOF 식별 + 직렬 가용성 곱 + 물리적 분리까지의 검증을 보여야 함.

---

## Ⅰ. 개요 및 필요성

- 개요: SPOF는 단독 장애 시 전체 서비스를 중단시키는 비이중화 구성요소
- 배경: 일부 계층만 이중화(023)하면 나머지 단일 계층이 직렬 곱으로 전체 가용성을 지배하는 병목이 됨
- 필요성: 전원~DB 전 계층을 점검해 SPOF를 식별·제거하고 물리적 분리까지 검증해야 목표 가용성(019) 달성 가능

---

## Ⅱ. 구조 및 구성요소

```text
전원/UPS -> 네트워크 스위치 -> LB -> WAS/서버 -> DB/스토리지
  각 계층: SPOF 식별 -> 이중화 방식 결정(023·030)
         -> 장애 도메인 분리 확인 -> 페일오버 검증
```

| 구성요소 | 역할 | SPOF 제거 방식 |
|:---|:---|:---|
| 전원/UPS | 전력 공급 | 이중 급전, 비상 발전기 |
| 네트워크 스위치 | 통신 경로 | 이중 경로(LACP/MC-LAG) |
| LB | 트래픽 진입점 | Active-Standby VIP 이중화 |
| WAS/서버 | 요청 처리 | Active-Active(023) + 오토스케일링 |
| DB/스토리지 | 데이터 저장 | 클러스터·복제·쿼럼(027) |

> 요약: 전원~DB까지 전 계층을 순차 점검하고 계층별 적합한 이중화 방식을 적용하는 구조임.

---

## Ⅲ. 동작원리 및 흐름도

```text
아키텍처 전수 도식화 -> 계층별 이중화 여부 점검 -> SPOF 후보 식별
  -> 이중화 방식 적용(023·030) -> 장애 도메인 분리 검증
  -> 카오스 엔지니어링/페일오버 훈련 -> 잔존 SPOF 재점검
```

1. 전체 아키텍처를 전원~애플리케이션까지 계층별로 도식화하고, 지원 시스템(DNS·인증서·설정 저장소)까지 포함함
2. 각 계층의 이중화 여부를 점검해 단일 구성 요소를 SPOF 후보로 분류하고, FTA(032)로 은닉 SPOF를 추가 도출함
3. SPOF 후보에 AA/AS(023) 또는 N+1/2N(030) 이중화를 적용하고, 이중화 노드가 서로 다른 장애 도메인(랙·전원·AZ)에 배치되는지 확인함
4. 카오스 엔지니어링·정기 페일오버 훈련으로 전환 성공을 검증하고, 잔존 SPOF를 재점검함

> 요약: 전수 도식화 → SPOF 식별 → 이중화 적용 → 물리 분리 검증 → 페일오버 훈련 순으로 진행함.

---

## Ⅳ. 특징

- 직렬 곱 지배: 직렬 구성에서 가장 낮은 가용성의 요소가 전체를 지배(예: 99.99% × 99.9% = 99.89%)
- 은닉 SPOF: 서버·DB 외에 DNS·인증서·설정 저장소·NTP 같은 지원 시스템도 SPOF 후보임
- 물리적 분리 필수: 논리적 이중화만으로는 상관 장애(같은 랙·전원·AZ 공유) 방어 불가
- 검증 의존: 이중화 후 페일오버 테스트 없이는 실제 장애 시 전환 실패 가능 — 정기 훈련 필수
- 비용 비례: 전 계층 SPOF 제거와 물리 분리는 이중 회선·전원·AZ 비용을 수반, 목표 가용성(019)에 맞춘 투자 판단 필요

---

## Ⅴ. 심화 비교 및 적용 판단

| 구분 | 부분 이중화(서버만) | 전 계층 SPOF 제거 | 선택 기준 |
|:---|:---|:---|:---|
| 범위 | WAS/서버 계층만 이중화 | 전원·네트워크·LB·DB·지원 시스템 포함 | 목표 가용성 수준(99.9% vs 99.99%) |
| 잔존 위험 | 미제거 SPOF에서 전체 장애 발생 가능 | 상관 장애 확률 최소화 | 업무 중요도·장애 영향 범위 |
| 비용 | 구축 비용 낮음 | 이중 회선·전원·AZ 분산 비용 발생 | 다운타임 비즈니스 손실 vs 이중화 비용 |

> 요약: 목표 가용성이 높을수록 전 계층 SPOF 제거와 물리적 분리 투자가 정당화됨.

**리스크·대응:**
- 은닉 SPOF 누락: DNS·인증서·설정 저장소 미점검 → 지원 시스템까지 포함한 아키텍처 전수 점검 + FTA(032) 활용 (지표: SPOF 점검 커버리지율)
- 물리적 상관 장애: 이중화 노드가 동일 장애 도메인 → 랙·전원·AZ 단위 분산 배치 정책 수립 (지표: 동일 장애 도메인 배치 건수 0건)
- 이중화 미검증: 페일오버 테스트 미실시 → 분기별 카오스 엔지니어링·페일오버 훈련 실시 (지표: 훈련 성공률, 실측 전환 시간)

**점검 지표:**
- 성능: SPOF 점검 커버리지(전원~지원 시스템 100%) — 아키텍처 점검표
- 운영: 이중화 노드 간 동일 장애 도메인 배치 0건 + 분기별 페일오버 훈련 실시 — 배치도 감사·훈련 로그

---

## Ⅵ. 실무 적용 및 결론

**적용 방안:**
1. 전원~DB·지원 시스템까지 전 계층 아키텍처 다이어그램을 작성하고 계층별 이중화 여부를 점검해 SPOF 후보를 도출함
2. SPOF 후보에 AA/AS(023) 또는 N+1(030) 중 적합한 이중화를 적용하고, 이중화 노드를 서로 다른 장애 도메인에 배치함
3. 분기별 카오스 엔지니어링·페일오버 훈련으로 전환 성공을 검증하고, 잔존 SPOF를 재점검해 아키텍처 점검표를 갱신함

**결론:**
- 기술사 판단: SPOF 제거는 논리적 이중화 + 물리적 분리 + 페일오버 검증 3단계를 모두 거쳐야 완성됨
- 향후 방향: 카오스 엔지니어링 자동화와 인프라 코드(IaC) 기반 SPOF 탐지 도구로 상시 점검 체계를 고도화하는 추세임
