## 📖 【암기용】 핵심 요약

*   **한눈에**: 시스템에 머무는 평균 개체 수($L$)는 단위 시간당 유입량($\lambda$)과 개체가 머무는 평균 시간($W$)의 곱과 같다는 대기행렬 이론의 절대 항등식. ($L = \lambda \times W$)
*   **깊이 이해**:
    *   **배경**: 시스템 내부의 동시 처리 건수($L$)를 직접 카운팅하기 어려울 때, 외부에서 측정하기 쉬운 TPS($\lambda$)와 응답 시간($W$)만으로 시스템 내부의 상태(부하/동시성)를 정확히 역산하기 위해 사용.
    *   **작동 원리**: **"매장 안의 손님 수 = 분당 입장객 수 × 평균 쇼핑 시간"**. 이 법칙의 가장 강력한 점은 시스템의 내부 구조(블랙박스), 요청의 도착 확률 분포(포아송 등), 서비스 순서(FIFO, LIFO)에 **전혀 구애받지 않고 언제나 성립**한다는 것(Distribution-Free).
    *   **비유**: **물탱크**. 수도꼭지에서 초당 1L의 물이 흘러나오고($\lambda=1$), 물 한 방울이 탱크를 통과해 배수구로 빠져나가는 데 10초가 걸린다면($W=10$), 물탱크 안에는 항상 10L의 물이 차 있음($L=10$).
    *   **구체 예시**: 목표 TPS 500, 평균 응답 시간 0.2초인 시스템을 구축한다면, 동시 처리량 $L = 500 \times 0.2 = 100$. 즉, WAS의 Thread Pool이나 DB Connection Pool 사이즈는 최소 100개 이상 확보해야 함을 수학적으로 증명함.
    *   **흔한 오해/주의점**: 리틀의 법칙은 **안정 상태(Steady State)**, 즉 유입량과 유출량이 장기적으로 균형을 이루는 상태에서만 성립함. 시스템이 마비되어 요청이 무한히 쌓이는 붕괴 상태에서는 적용 불가.
*   **연결 개념**: 큐잉 이론(Queuing Theory), TPS 산정, 동시 사용자 수(Concurrent User), 성능 테스트 Sizing, 응답 시간 분해

## 📝 【답안용】 서술 골격

> **💡 핵심 인사이트**
> *   **본질**: 시스템의 동시성(Concurrency), 처리량(Throughput), 응답성(Latency)을 하나의 수식으로 묶어낸 수학적 보존 법칙(Conservation Law).
> *   **가치**: 블랙박스 시스템이라도 외부에서 관찰 가능한 지표(TPS, RT)만으로 내부 자원 소모량(Active Thread/Connection)을 정확히 추론 가능.
> *   **판단 포인트**: 특정 구간(전체 시스템, 특정 Queue 단일 구간, 특정 서버) 어디에나 적용 가능하므로, 병목 구간 Sizing의 가장 기초적인 설계 근거로 활용됨.

### Ⅰ. 성능 엔지니어링의 황금 방정식, 리틀의 법칙 개요
*   **정의**: 안정 상태(Steady State)의 대기 시스템에서, 시스템 내 평균 고객 수($L$)는 평균 도착률($\lambda$)과 평균 체류 시간($W$)의 곱과 같다는 법칙.
*   **목적**: 복잡한 대기행렬 모델링 이전에, 거시적인 관점에서 IT 인프라 자원의 목표 용량(Sizing)을 산정하고 성능 테스트 결과를 검증.

### Ⅱ. 리틀의 법칙 핵심 산식 및 메커니즘
*   **산식**: `L = λ × W`
    *   **$L$ (Inventory/Load)**: 시스템 내 존재하는 평균 개체 수 $\rightarrow$ **동시 사용자, 동시 처리 쓰레드 수**
    *   **$\lambda$ (Arrival Rate)**: 단위 시간당 평균 유입량 $\rightarrow$ **TPS (Transactions Per Second)**
    *   **$W$ (Wait/Response Time)**: 개체가 시스템에 머무는 평균 시간 $\rightarrow$ **응답 시간 (Response Time)**
*   **성립 전제 (Steady State)**: 장기적으로 평균 유입량($\lambda_{in}$)과 평균 유출량($\lambda_{out}$)이 동일하여 시스템 내 요청이 무한 발산하지 않는 상태.

### Ⅲ. 법칙의 강력함: 2대 수학적 특징
*   **1. 분포 무관성 (Distribution-Free)**:
    *   도착 분포(포아송, 균등 등)나 서비스 분포에 독립적.
    *   처리 순서(FIFO, LIFO, Priority)와 무관하게 시스템 전체 평균값에 대해 항상 항등식 성립.
*   **2. 경계 가변성 (Boundary Invariance)**: 
    *   시스템 경계(Boundary)를 어떻게 설정하느냐에 따라 유연한 해석 가능.
    *   **시스템 전체**: $L = \lambda W$ (전체 동시 사용자 = TPS × 전체 응답시간)
    *   **Queue 구간**: $L_q = \lambda W_q$ (큐 대기자 수 = TPS × 큐 대기시간)
    *   **Server 구간**: $L_s = \lambda W_s = \lambda / \mu = \rho$ (서버 처리 중인 수 = TPS × 처리시간 = 이용률)

### Ⅳ. 리틀의 법칙을 활용한 실무 용량 산정 (Sizing)
*   **WAS Thread Pool 산정**:
    *   [요구사항] Peak TPS = 2000, 목표 응답시간 = 0.3초
    *   [산출] $L = 2000 \times 0.3 = 600$. 즉 최소 600개의 Active Thread 대역폭 보장 필요.
*   **DB Connection Pool 설계**:
    *   앱의 TPS와 DB 구간의 응답시간($W_{DB}$)을 산식에 대입하여, 타임아웃을 유발하지 않는 최적의 Connection 개수 도출.

### Ⅴ. 병목 및 시스템 이상 징후 검증 (Validation)
*   **부하 테스트(Load Test) 신뢰도 검증**:
    *   성능 테스팅 툴(JMeter 등)에서 리포팅한 Active User 수와 `측정 TPS × 평균 RT` 값이 일치하지 않는다면, 툴의 부하 발생 모델이나 네트워크 구간에 누수(Leak)가 있음을 진단.

### Ⅵ. 확장: 마이크로서비스(MSA)에서의 리틀의 법칙
*   **Distributed Tracing 연계**:
    *   End-to-End TPS는 동일($\lambda$)할 때, 특정 마이크로서비스(A)의 $W_A$가 급증하면 해당 서비스 컨테이너 내의 동시 처리 요청($L_A$)이 급증하여 OOM(Out of Memory)이나 쓰레드 고갈이 발생함을 예측, 오토스케일링 지표로 활용.
