# 📖 【암기용】 개념 완전 이해

## 한눈에
- **개요**: 리틀의 법칙(Little's Law)은 안정 상태(Steady State)의 시스템에서 **평균 재고량($L$)은 평균 유입률($\lambda$)과 평균 체류 시간($W$)의 곱과 같다**는 대기행렬 이론의 핵심 항등식이다. ($L = \lambda \times W$)
- **왜 필요한가**: 시스템 내부의 동시 처리 건수($L$)를 직접 세기 어려울 때, 외부에서 측정 가능한 TPS($\lambda$)와 응답 시간($W$)만으로 시스템의 부하를 정확히 역산할 수 있기 때문이다.
- **핵심 직관**: **"매장 안의 평균 손님 수 = 분당 입장객 수 $\times$ 평균 쇼핑 시간"**. 얼마나 빨리 들어오고($\lambda$) 얼마나 오래 머무느냐($W$)가 시스템 안에 몇 명($L$)이 있는지를 결정한다.

## 핵심 용어 정리

| 용어/표기 | 의미 | 기술적 포인트 |
|:---|:---|:---|
| **$L$ (Inventory/Load)** | 시스템 내 평균 개체 수 | 동시 사용자 수, 동시 처리 트랜잭션 수 |
| **$\lambda$ (Arrival/Throughput)** | 단위 시간당 평균 유입(또는 처리)량 | TPS (Transactions Per Second) |
| **$W$ (Wait/Response Time)** | 개체가 시스템에 머무는 평균 시간 | 응답 시간 (Latency) |
| **Steady State** (안정 상태) | 유입량과 유출량이 균형을 이루는 상태 | 법칙 성립의 필수 전제 조건 |
| **Conservation Law** | 보존 법칙 | 분포나 처리 순서(FIFO 등)에 관계없이 성립 |

## 깊이 이해
- **범용성의 원리 (Distribution Free)**: 리틀의 법칙이 강력한 이유는 도착 분포(포아송 등)나 서비스 시간 분포(지수 분포 등)에 **전혀 구애받지 않는다**는 점이다. 시스템 내부가 블랙박스여도 입구($\lambda$)와 출구($W$)만 알면 내부 상태($L$)를 100% 확신할 수 있다.
- **경계의 확장 (Boundary Application)**:
  - **전체 시스템 적용**: $L = \lambda W$ (동시 사용자 수 = TPS $\times$ 응답시간)
  - **대기열(Queue)에만 적용**: $L_q = \lambda W_q$ (평균 대기 인원 = TPS $\times$ 대기시간)
  - **서버(Processing)에만 적용**: $L_s = \lambda W_s = \lambda / \mu = \rho$ (이용률 $\rho$ 도 리틀의 법칙의 변형)
- **비유 (물탱크)**: 수도꼭지에서 초당 1L의 물이 나오고($\lambda=1$), 물 한 방울이 탱크를 통과하는 데 10초가 걸린다면($W=10$), 물탱크 안에는 항상 10L의 물이 차 있다($L=10$).
- **구체 예시 (서버 용량 산정)**:
  - 목표 TPS: 500
  - 평균 응답 시간: 0.2초
  - 필요 동시 처리량($L$): $500 \times 0.2 = 100$
  - 즉, 서버의 Thread Pool이나 DB Connection Pool은 최소 100개 이상 확보되어야 함을 수학적으로 증명함.

## 연결 개념
- **시스템 성능 지표(001)**: TPS, 응답 시간, 동시 사용자의 상관관계를 규명.
- **큐잉 이론(005)**: 리틀의 법칙을 기초로 하여 복잡한 확률 모델을 구축.
- **응답 시간 분해(002)**: 전체 $W$를 $W_q$와 $W_s$로 나눌 때 리틀의 법칙을 구간별로 적용.

## Ⅰ. 리틀의 법칙(Little's Law)의 개요

### 1. 정의
- 대기 시스템이 안정 상태에 있을 때, 시스템 내 평균 고객 수($L$)는 고객의 평균 도착률($\lambda$)과 고객이 시스템에 머무는 평균 시간($W$)의 곱과 같다는 법칙

### 2. 성립 조건: 안정 상태 (Steady State)
- 유입되는 요청의 수와 처리되어 나가는 요청의 수가 장기적으로 균형을 이루어, 시스템 내 요청 수가 무한히 발산하거나 0으로 소멸하지 않는 상태

---

## Ⅱ. 리틀의 법칙의 구성 요소 및 메커니즘

### 1. 핵심 산식 및 변수 정의

```text
    L (Average Number of Customers) = λ (Arrival Rate) × W (Average Wait Time)
```

| 변수 | 의미 | IT 시스템 대응 |
|:---|:---|:---|
| **$L$** | 시스템 내 평균 개체 수 | **Concurrency** (동시 사용자 수) |
| **$\lambda$** | 단위 시간당 평균 도착률 | **TPS** (Transactions Per Second) |
| **$W$** | 평균 체류 시간 | **Response Time** (응답 시간) |

### 2. 동작 원리 도식

```text
       Arrival (λ)          System Boundary           Departure (λ)
    ---------------> +--------------------------+ --------------->
                     |   (L) Average Number     |
                     |       in System          |
                     |                          |
                     +--------------------------+
                          Wait Time (W)
    * 관계: L = λ * W (분포와 무관하게 경계 내에서 항상 성립)
```

---

## Ⅲ. 리틀의 법칙의 주요 특징

### 1. 분포 무관성 (Distribution-Free)
- 도착 분포(Poisson, Constant 등)나 서비스 분포(Exponential, Erlang 등)와 무관하게 성립
- 서비스 정책(FIFO, LIFO, Priority)에 관계없이 평균값에 대해 항등식 유지

### 2. 경계 가변성 (Boundary Invariance)
- 시스템의 범위를 어떻게 설정하느냐에 따라 다양한 지표 도출 가능
  - **Queue 구간**: $L_q = \lambda W_q$ (평균 대기자 수 = TPS $\times$ 대기시간)
  - **Server 구간**: $L_s = \lambda W_s$ (평균 처리자 수 = TPS $\times$ 서비스시간 = 이용률 $\rho$)

---

## Ⅳ. 실무적 활용 방안: 용량 산정 및 진단

### 1. 인프라 자원 규모 산정 (Sizing)
- **Thread Pool 설계**: 목표 TPS가 1000이고 응답 시간이 0.5초라면, 동시 처리량 $L = 1000 \times 0.5 = 500$ 이므로 최소 500개의 Worker Thread 필요
- **Connection Pool 설계**: DB 쿼리 평균 응답 시간을 고려한 최적의 DB Connection 수 산정

### 2. 성능 병목 진단 및 검증
- 실측된 동시 사용자 수와 $L = \lambda W$ 로 계산된 값이 크게 다를 경우, 시스템 내 비정상적인 지연이나 누수(Leak) 존재 여부 판단

## Ⅴ. 리틀의 법칙 적용 사례 (Case Study)

| 구분 | 온라인 쇼핑몰 (이벤트) | 제조 공정 (재공품) |
|:---|:---|:---|
| **유입량($\lambda$)** | 10,000 명/시간 | 100 개/일 |
| **체류시간($W$)** | 0.5 시간 (30분 쇼핑) | 5 일 (리드타임) |
| **평균 재고($L$)** | **5,000 명 (동시접속자)** | **500 개 (재공품 수)** |
| **활용** | 서버 증설 규모 결정 | 재고 비용 및 창고 면적 산정 |

## Ⅵ. 결론 및 제언

- 리틀의 법칙은 **"복잡한 시스템도 입구와 출구의 데이터만으로 본질을 꿰뚫을 수 있다"**는 통찰을 제공함.
- 성능 엔지니어링의 시작은 이 법칙을 통해 시스템의 **'동시성(Concurrency)'**을 정량화하는 것이며, 이를 기반으로 큐잉 이론 등 고도화된 분석으로 나아가야 함.
