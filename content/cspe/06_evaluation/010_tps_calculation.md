# 📖 【암기용】 개념 완전 이해

## 한눈에
- **개요**: TPS 계산은 리틀의 법칙(L=λW)을 용량 산정에 적용해 동시 사용자 수·TPS·평균 응답시간 세 값을 서로 역산하는 계산법(성능 지표 정의는 001, 응답시간은 002, 리틀의 법칙은 006 참조)
- **왜 필요한가**: 부하테스트 도구는 동시 사용자 수(가상 사용자 수)를 입력받지만 SLA는 TPS로 표기되어, 응답시간을 매개로 정확히 환산해야 테스트 설계와 목표가 일치
- **핵심 직관**: 초당 회전문을 통과하는 사람 수(TPS)와 회전문 안에 늘 머무는 사람 수(동시 사용자 수)는, 한 사람이 통과하는 데 걸리는 시간(응답시간)으로 연결됨

## 핵심 용어 정리 (내부에 등장하는 것들)
아래 표기는 답안용 Ⅰ~Ⅵ의 산식·표에 그대로 등장하므로 먼저 직관적으로 풀어 둔다. 상위 핵심 키워드는 **리틀의 법칙 기반 TPS 환산식**이다.

| 용어/표기 | 의미 | 비유·예 |
|:---|:---|:---|
| TPS(λ) | 초당 완료되는 트랜잭션 수(처리량, 001 참조) | 톨게이트를 초당 통과하는 차량 수 |
| 동시 사용자 수(L) | 특정 시점 시스템 안에 머무는 평균 요청(사용자) 수 | 도로 위에 늘 존재하는 차량 대수 |
| 평균 응답시간(W) | 요청 시작~완료까지 걸린 평균 시간(002 참조) | 차 1대가 도로 구간을 통과하는 시간 |
| L=λW | 리틀의 법칙(006 참조): 체류 수 = 도착률 × 체류시간 | "안에 있는 수 = 초당 들어오는 수 × 머무는 시간" |
| Think Time(Z) | 한 사용자가 응답을 받은 뒤 다음 요청까지 쉬는 시간 | 화면을 읽고 다음 버튼을 누르기까지의 시간 |
| TPS = L/(W+Z) | Think Time 포함 시 실질 TPS 산식 | 사람이 쉬는 시간까지 회전 주기에 더함 |
| steady state | 도착률과 처리율이 균형을 이룬 정상 상태 | 물이 들어오고 나가는 양이 같아 수위 일정 |
| p95 응답시간 | 응답시간을 정렬했을 때 95% 지점 값 | 100명 중 95번째로 느린 사람의 대기시간 |

## 깊이 이해
- **배경·문제의식**: 부하 스크립트를 "동시 사용자 500명"으로 잡았는데 실제 목표가 "TPS 500"이면, 응답시간에 따라 발생 부하가 크게 달라져 테스트 결과가 목표와 어긋남
- **작동 원리(어떻게+왜)**: 리틀의 법칙 L=λW를 응용해 TPS(λ)=동시 사용자 수(L)/응답시간(W), 역으로 L=λ×W로 상호 환산. 사용자가 응답 후 쉬는 구간이 있으면 회전 주기가 W+Z가 되어 TPS=L/(W+Z)로 보정. 이는 한 사용자가 (응답시간+Think Time)마다 1건씩 요청을 내보내기 때문
- **비유**: 고속도로에서 초당 통과 차량 수(TPS)와 도로 위 상시 차량 수(동시 사용자 수)는, 차 1대의 통과 시간(응답시간)을 매개로 이어짐
- **구체 예시**: 목표 TPS 500, 응답시간 0.4초, Think Time 0이면 필요 동시 사용자 L=λW=500×0.4=200명. Think Time 0.6초를 더하면 L=λ(W+Z)=500×(0.4+0.6)=500명이 필요. 반대로 동시 사용자 200명·응답시간 0.4초·Think Time 0이면 λ=L/W=200/0.4=500건/초로 역산(수치는 예시이며 부하테스트로 검증 필요)
- **흔한 오해**: 동시 사용자 수만 늘리면 TPS가 비례해 오른다고 오해하기 쉬우나, 부하 증가로 응답시간 W가 함께 커지면 TPS는 정체·감소함. Think Time을 0으로 두고 계산하면 실제보다 훨씬 공격적인 부하가 걸림

## 연결 개념
- 리틀의 법칙(006) — 이 계산법의 수학적 근거 L=λW
- 시스템 성능 지표(001)·응답시간(002) — 계산에 투입되는 원천 지표의 정의
- 성능 테스트(부하·스트레스·스파이크) — 계산된 동시 사용자 수·Think Time을 시나리오 파라미터로 반영

# 📝 【답안용】 시험 답안 템플릿

## 핵심 인사이트 (3줄 요약)

> 1. **본질**: TPS 계산은 리틀의 법칙(L=λW)을 응용해 동시 사용자 수·TPS·응답시간을 상호 환산하는 실무 공식임.
> 2. **가치**: 부하테스트 도구의 동시 사용자 설정값과 SLA 목표 TPS를 응답시간·Think Time을 매개로 일치시킬 수 있음.
> 3. **판단 포인트**: 부하 증가로 응답시간이 함께 늘면 TPS는 비례 증가하지 않으므로 응답시간 변화를 반드시 병행 검증해야 함.

## 출제 의도 및 답안 포인트

| 출제 의도 | 반드시 짚을 핵심 | 감점 회피 포인트 |
|:---|:---|:---|
| 산식 이해·적용 확인 | TPS=L/W, L=λ×W (리틀의 법칙 응용) | 유도 근거(리틀의 법칙) 없이 결과값만 제시 누락 |
| 상호 환산 역량 확인 | 세 값 중 둘로 나머지 계산, Think Time 반영 | 세 값을 독립 상수로 단정 |
| 실무 한계 이해 확인 | 부하 증가 시 응답시간 변화가 계산값에 영향 | 동시 사용자 증가=TPS 비례 증가로 단정 |

> 요약: 이 문제는 결과값보다 리틀의 법칙 기반 환산 절차와 응답시간·Think Time 반영 여부를 요구함.

---

## Ⅰ. 개요 및 필요성

- 개요: 동시 사용자 수·TPS·응답시간을 리틀의 법칙으로 상호 환산하는 실무 계산법
- 배경: 부하 도구는 동시 사용자 수를, SLA는 TPS를 기준으로 하여 단위 불일치가 발생
- 필요성: 테스트 시나리오와 SLA 목표를 일치시키려면 응답시간·Think Time을 매개로 한 정확한 환산이 필요

---

## Ⅱ. 구조 및 구성요소

```text
SLA 목표(TPS 또는 동시 사용자 수) 확인 -> 예상 응답시간·Think Time 산정
  -> 리틀의 법칙(L=λW) 적용 -> 나머지 변수 계산
  -> 부하테스트 파라미터 설정 -> 실측 검증
```

| 구성요소 | 역할 | 특이사항 |
|:---|:---|:---|
| TPS(λ) | 초당 완료 트랜잭션 목표치 | SLA 문서에 명시된 처리 목표 |
| 응답시간(W) | 요청 시작~완료 평균 시간 | 실측 또는 목표 SLO 값 사용 |
| Think Time(Z) | 사용자 간 요청 대기 시간 | 0으로 두면 부하 과대 산정 |
| 동시 사용자 수(L) | 시점당 평균 존재 요청 수 | 가상 사용자 수 파라미터로 사용 |

> 요약: TPS·응답시간·동시 사용자 수 중 둘과 Think Time을 알면 나머지 값을 산출함.

---

## Ⅲ. 동작원리 및 흐름도

```text
SLA 목표 확인 -> 예상 응답시간·Think Time 확보 -> L=λ(W+Z) 계산
  -> 부하 도구에 가상 사용자 수 반영 -> 실행 후 실측 TPS·응답시간 수집 -> 목표 대비 검증
```

- 1단계: 성능 엔지니어가 SLA 목표 TPS 또는 동시 사용자 수를 문서에서 확인함
- 2단계: 성능 엔지니어가 과거 실측 또는 목표 SLO에서 응답시간 W와 Think Time Z를 확보함
- 3단계: 리틀의 법칙 L=λ(W+Z)로 나머지 변수를 계산해 가상 사용자 수 파라미터를 산출함
- 4단계: 부하테스트 실행 후 수집된 실측 TPS·응답시간을 계산값과 비교해 오차·병목을 판정함

> 요약: 성능 엔지니어가 목표와 응답시간을 확보해 리틀의 법칙으로 파라미터를 계산하고 실측치로 검증함.

---

## Ⅳ. 특징

- 양방향 환산 가능함: 설계 단계는 L=λ(W+Z)로 사용자 수를 산정, 분석 단계는 λ=L/(W+Z)로 TPS를 역산함
- 응답시간이 매개 변수임: 동일 사용자 수라도 W가 커지면 TPS가 감소하므로 두 값은 종속 관계임
- Think Time이 부하 강도를 좌우함: Z=0 가정은 실제보다 공격적 부하를 만들어 과대 산정 위험이 있음
- steady state 전제임: 도착률과 처리율이 균형인 정상 상태에서만 산식이 성립하며 램프업 구간은 제외함
- 평균값 왜곡에 취약함: 이상치 포함 평균 응답시간은 계산을 왜곡하므로 p95 병행 확인이 필요함

## Ⅴ. 심화 비교 및 적용 판단

| 구분 | 이론 계산값 | 실측 부하테스트값 |
|:---|:---|:---|
| 목적 | 테스트 시나리오 사전 설계 | 실제 시스템 성능 검증 |
| 정확도 | 예상 응답시간 가정에 의존 | 자원 포화 시 응답시간 변화 반영 |
| 활용 | 가상 사용자 수 파라미터 결정 | SLA 달성 여부 판정 |
| 판단 | 설계 출발점으로 사용 | 계산값과 괴리 시 병목 의심 |

> 요약: 계산값은 시나리오 설계의 출발점이며 실측값과 비교해 응답시간 변화에 따른 괴리를 확인함.

- 리스크 — 시나리오 파라미터 오설정: 사용자 수·TPS를 응답시간 반영 없이 임의 설정 — 대응: 리틀의 법칙 환산 후 파라미터 설정, 확인 지표 계산-실측 오차율
- 리스크 — 응답시간 변화 미반영: 부하 증가 시 W 증가를 무시하고 선형 예측 — 대응: 단계적 부하 증가로 응답시간 변곡점 확인, 확인 지표 부하 구간별 응답시간 추이
- 리스크 — 평균값 왜곡: 이상치 포함 평균으로 계산 — 대응: p95 응답시간 병행 계산, 확인 지표 응답시간 분포·이상치 비율

- 지표 — 계산-실측 TPS 일치도: 목표 오차율 10% 이내 — 측정: 부하테스트 결과 비교
- 지표 — 응답시간 변곡점: 급증 구간 문서화 — 측정: 단계적 부하 증가 테스트
- 지표 — 시나리오 재현성: 반복 시 결과 일관성 — 측정: 동일 파라미터 반복 테스트·통계 분석

## Ⅵ. 실무 적용 및 결론

**적용 방안 3개 (필수 — 단계별 또는 항목별):**
1. 시나리오 설계 시 SLA 목표 TPS·예상 응답시간·Think Time으로 L=λ(W+Z)를 적용해 가상 사용자 수를 산정함
2. 실행 후 실측 사용자 수·응답시간으로 λ=L/(W+Z)를 계산해 달성 TPS를 목표치와 비교함
3. 부하 구간별 단계 테스트로 응답시간 변곡점을 파악하고 계산값 대비 괴리 원인을 분석함

**결론 (2줄):**
- 기술사 판단: 목표 TPS가 고정이면 응답시간 단축이 사용자 수 절감으로 이어지고, 사용자 수가 고정이면 응답시간 악화가 TPS 저하로 이어지므로 세 값을 함께 검증해야 함
- 향후 방향: 부하테스트 자동화 파이프라인에 리틀의 법칙 기반 파라미터 계산기를 내장해 시나리오 설계 오류를 사전에 줄여야 함
