## 📖 【암기용】 핵심 요약

*   **한눈에**: 리틀의 법칙을 확장하여, 시스템 처리량인 **초당 트랜잭션 수(TPS)**, 시스템 부하인 **동시 사용자 수(Concurrency)**, 사용자 체감인 **응답 시간(RT)** 간의 상관관계를 수학적으로 도출하는 기법.
*   **깊이 이해**:
    *   **배경**: 부하 테스트 도구(JMeter, nGrinder)는 'Vuser(가상 사용자 수)'를 입력값으로 받지만, 비즈니스 요구사항(SLA)은 주로 '목표 TPS'로 정의됨. 이 두 값의 단위를 맞추고 정확한 부하를 인가하기 위해 수학적 환산이 필수적.
    *   **작동 원리**: 리틀의 법칙($L = \lambda W$)에서, 사용자들은 요청을 보낸 후 응답을 받고 나면 다음 클릭까지 고민하는 시간(Think Time, $Z$)을 가짐. 따라서 전체 사이클 시간은 $W + Z$ 가 되며, 산식은 **$L = TPS \times (W + Z)$** 가 됨.
    *   **비유**: **회전목마의 처리량**. 회전목마에 한 번에 10명이 타고($L=10$), 한 바퀴 도는 데 1분이 걸리며($W=1$), 다음 사람으로 교체되는 대기 시간이 1분($Z=1$)이라면, 총 사이클은 2분. 즉 분당 처리량(TPS)은 10명 / 2분 = 5명. 
    *   **구체 예시**: 목표 TPS가 100이고, 예상 응답시간($W$)이 0.5초, 사용자가 화면을 읽는 시간($Z$)이 4.5초라면, 성능 테스트 시 세팅해야 할 Vuser($L$)는 $100 \times (0.5 + 4.5) = 500$명.
    *   **흔한 오해/주의점**: 성능 테스트 시 $Z$ (Think Time)를 0으로 두는 경우가 많은데, 이는 기계적인 봇(Bot) 공격이나 다름없음. 실제 사용자의 행위를 모사하려면 화면의 복잡도를 고려한 현실적인 Think Time 적용이 테스트의 신뢰도를 결정함.
*   **연결 개념**: 리틀의 법칙(Little's Law), 부하 테스트(Load Testing), 용량 산정(Capacity Planning), SLA, Think Time, Pacing

## 📝 【답안용】 서술 골격

> **💡 핵심 인사이트**
> *   **본질**: `TPS = 동시 사용자 수 / (응답 시간 + Think Time)` 이라는 시스템 성능의 동적 평형(Dynamic Equilibrium) 공식.
> *   **가치**: 비즈니스 부서의 요구사항(목표 TPS)을 엔지니어링 지표(Vuser Thread 수)로 변환하여, 정밀하고 재현 가능한 용량 산정(Sizing) 수행.
> *   **판단 포인트**: 부하($L$)를 늘리면 시스템 포화로 인해 응답 시간($W$)도 길어지므로, TPS가 선형적으로 증가하지 않는다는 '자기 조절(Self-throttling)' 메커니즘을 이해하는 것이 핵심.

### Ⅰ. 성능 설계의 기준점, TPS 계산(TPS Calculation) 개요
*   **정의**: 목표 서비스 수준(SLA)을 달성하기 위해 필요한 시스템 처리량(TPS)과 이를 유발하는 동시 사용자 수(Concurrent Users)의 관계를 수리적으로 환산하는 작업.
*   **목적**: H/W 및 Cloud 인프라의 적정 규모 산정(Capacity Planning) 및 성능 테스트 스크립트의 부하 프로파일링 설계.

### Ⅱ. TPS 계산의 핵심 모델링: 확장된 리틀의 법칙
*   **기본 산식**: 
    $$TPS = \frac{L}{W + Z}$$
*   **변수 상세 정의**:
    *   **TPS ($\lambda$)**: 초당 처리되는 비즈니스 트랜잭션 건수 (목표 처리량).
    *   **$L$ (Concurrency)**: 시스템과 세션을 맺고 상호작용 중인 동시 접속 사용자 수 (Vuser).
    *   **$W$ (Response Time)**: 서버가 요청을 받아 처리 후 응답을 완료할 때까지의 체류 시간.
    *   **$Z$ (Think Time)**: 사용자가 응답을 받은 후, 다음 요청을 보낼 때까지 화면을 읽고 고민하는 대기 시간.

### Ⅲ. 실무적 TPS Sizing 시나리오 (Case Study)
*   **시나리오 A: 목표 TPS 기반의 Vuser 산정 (Planning 단계)**
    *   요구사항: 이벤트 페이지의 피크 TPS 500 보장
    *   전제조건: 평균 응답시간 0.2초, 평균 Think Time 2.8초
    *   계산: $L = 500 \times (0.2 + 2.8) = 1,500$. 즉, 부하 발생기(Load Generator)에서 1,500개의 Vuser Thread를 할당하여 테스트 수행.
*   **시나리오 B: 시스템 포화 상태 진단 (Monitoring 단계)**
    *   측정값: 접속자 2,000명, 체감 응답시간 급증(4초), Think Time 6초
    *   계산: $TPS = 2,000 / (4 + 6) = 200$. 
    *   해석: 접속자는 많으나, 긴 응답시간($W$)이 분모를 키워 실제 시스템의 처리 효율(TPS)은 200에 불과한 병목 상태.

### Ⅳ. TPS 계산의 정확도를 좌우하는 주요 팩터
*   **Think Time의 분포 (Distribution)**: 모든 사용자가 동일한 $Z$값을 가지지 않으므로, 정규 분포나 가우시안 랜덤 값을 부여하여 실사용자와 유사한 부하 패턴 형성 (JMeter의 Gaussian Random Timer 활용).
*   **Pacing (페이싱)**: 트랜잭션과 트랜잭션 사이의 일정한 간격을 강제하는 설정. 응답시간($W$)의 변동에 상관없이 목표 TPS를 고정적으로 쏘기 위해 사용.

### Ⅴ. 비선형적 성능 곡선과 TPS의 역설
```text
  TPS / RT
       │                   ↗ (응답시간 W 급증)
       │                 /
       │               /
       │             / ← Knee Point
       │    ________/ ────── (TPS 정체)
       │  / 
       │/ (W가 짧아 TPS 선형 증가)
       └───────────────────────────→ 동시 사용자 수 (L)
```
*   $L$을 무한히 늘린다고 TPS가 무한히 늘지 않음. 임계점(Knee Point)을 넘어서면 CPU 등 자원 고갈로 $W$가 급증하여 분모가 커지므로, 오히려 TPS는 정체(Flat)되거나 하락함.

### Ⅵ. 결론 및 마이크로서비스(MSA) 환경에서의 TPS Sizing
*   단일 Monolithic과 달리 MSA 환경에서는 트랜잭션 1건이 10개의 내부 API 호출(Amplification)로 확산될 수 있음.
*   따라서 Front-end의 사용자 체감 TPS 계산과 별도로, API Gateway 인그레스(Ingress) 단의 실질 부하(RPS: Requests Per Second)를 고려한 곱연산 기반의 정밀한 Sizing 체계가 필요.
