# 📖 【암기용】 개념 완전 이해

## 한눈에
- **개요**: TPS 계산은 시스템 성능 목표인 **초당 트랜잭션 수(TPS)**, 시스템 부하인 **동시 사용자 수(Concurrency)**, 사용자 체감인 **응답 시간(Response Time)** 간의 수학적 상관관계를 도출하는 과정이다.
- **왜 필요한가**: 부하 테스트 도구(JMeter, nGrinder 등)는 보통 '사용자 수'를 입력값으로 받지만, 비즈니스 요구사항(SLA)은 'TPS'로 정의되는 경우가 많아, 둘 사이를 정확히 환산해야 목표 성능을 제대로 검증할 수 있기 때문이다.
- **핵심 직관**: **"회전목마의 처리량"**. 목마에 한 번에 10명이 타고($L$), 한 바퀴 도는 데 1분($W$)이 걸린다면, 이 목마의 분당 처리량($TPS$)은 10명이다. 만약 한 바퀴 도는 시간을 30초로 줄이면 처리량은 20명으로 늘어난다.

## 핵심 용어 정리

| 용어/표기 | 의미 | 기술적 포인트 |
|:---|:---|:---|
| **TPS ($\lambda$)** | 초당 완료된 트랜잭션 수 | 시스템의 실질적 처리량 (Throughput) |
| **Concurrency ($L$)** | 시스템 내 상주하는 평균 요청 수 | 가상 사용자(Vuser) 수와 대응 |
| **Response Time ($W$)** | 요청부터 응답까지의 평균 시간 | Latency (지연 시간) |
| **Think Time ($Z$)** | 사용자 요청 사이의 대기 시간 | 실제 사용자의 비즈니스 행위 모사 |
| **$L = \lambda \times (W + Z)$** | 확장된 리틀의 법칙 | TPS 계산의 근간이 되는 핵심 공식 |

## 깊이 이해
- **Think Time의 중요성**: $Z$를 0으로 설정하면 사용자가 응답을 받자마자 0.001초 만에 다음 요청을 보내는 '기계적 부하'가 되어, 실제 사용자 시나리오보다 훨씬 가혹한 부하가 걸린다. 현실적인 $Z$ 설정이 테스트의 유효성을 결정한다.
- **응답 시간과의 종속성**: $TPS = L / (W + Z)$ 식에서 알 수 있듯이, 사용자 수($L$)가 고정되어 있어도 시스템이 느려져서 응답 시간($W$)이 길어지면 TPS는 자동으로 떨어진다. 즉, 성능이 나빠지면 부하(TPS)도 스스로 줄어드는 **자기 조절(Self-throttling)** 현상이 발생한다.
- **산출 예시 (Sizing)**:
  - 목표 TPS: 100
  - 평균 응답 시간($W$): 0.5초
  - 평균 Think Time($Z$): 4.5초
  - 필요 동시 사용자 수($L$): $100 \times (0.5 + 4.5) = 500$명
- **흔한 오해·주의점**: "동시 사용자 1,000명이면 1,000 TPS가 나와야 한다" → **오답**. 응답 시간과 Think Time의 합이 1초일 때만 성립한다. 대부분의 경우 TPS는 사용자 수보다 훨씬 작거나 크다.

## 연결 개념
- **리틀의 법칙(006)**: TPS 계산의 이론적 토대.
- **성능 테스트 유형(009)**: 계산된 TPS와 사용자 수를 바탕으로 시나리오 설계.
- **SLA(020)**: 목표 TPS 수치를 결정하는 비즈니스 계약.

# 📝 【답안용】 시험 답안 템플릿

## 핵심 인사이트 (3줄 요약)

> 1. **본질**: 리틀의 법칙($L = \lambda W$)을 확장하여 동시 사용자 수, TPS, 응답 시간, Think Time 간의 상관관계를 정량화하는 계산 기법임.
> 2. **수식**: **$TPS = L / (W + Z)$** 를 기본으로 하며, 이를 통해 비즈니스 목표(TPS) 달성을 위한 인프라 부하(Vuser) 규모를 산정함.
> 3. **실무 가치**: 단순 사용자 수 증설이 아닌, 응답 시간과 Think Time을 고려한 **입체적 용량 산정(Sizing)**을 통해 부하 테스트의 재현성과 정확도를 확보함.

## 출제 의도 및 답안 포인트

| 출제 의도 | 반드시 짚을 핵심 | 감점 회피 포인트 |
|:---|:---|:---|
| TPS 산출 공식 및 변수 이해 | $TPS = L / (W + Z)$ 산식 도출 | Think Time($Z$)을 누락하여 과도하게 산정하는 오류 방지 |
| 상황별 변수 역산 능력 | $L, \lambda, W, Z$ 중 주어진 값으로 미지수 계산 | 산식만 나열하지 말고 구체적인 수치 대입 사례 제시 |
| 성능 지표 간의 동적 관계 | 부하 증가에 따른 응답 시간 변화와 TPS의 상관관계 | $L$과 $TPS$가 항상 정비례한다고 서술하지 말 것 |

## Ⅰ. TPS 계산(TPS Calculation)의 개요

### 1. 정의
- 목표 서비스 수준(SLA)을 달성하기 위해 필요한 초당 처리량(TPS)과 이를 수용하기 위한 동시 사용자 수(Concurrency)의 상관관계를 수학적으로 산출하는 과정

### 2. 필요성
- **테스트 정합성**: 부하 테스트 도구의 설정값($L$)과 비즈니스 목표($\lambda$)를 일치시킴
- **인프라 최적화**: 목표 성능 대비 과도하거나 부족한 자원 할당 방지

---

## Ⅱ. TPS 계산의 핵심 공식 및 구성 요소

### 1. 확장된 리틀의 법칙 기반 산식

```text
               Concurrency (L)
    TPS (λ) = --------------------
              Resp Time(W) + Think Time(Z)
```

### 2. 주요 변수 상세 분석

| 변수 | 의미 | 실무적 적용 |
|:---|:---|:---|
| **TPS ($\lambda$)** | 처리량 (Throughput) | 성능 테스트의 최종 합격/불합격 기준 지표 |
| **Concurrency ($L$)** | 동시 사용자 수 | 테스트 도구의 Vuser(Virtual User) 설정값 |
| **Response Time ($W$)** | 응답 시간 | 서버가 요청을 처리하는 데 걸리는 시간 |
| **Think Time ($Z$)** | 사용자 대기 시간 | 사용자가 페이지를 읽고 다음 클릭을 할 때까지의 시간 |

---

## Ⅲ. TPS 계산 및 환산 시나리오 (Case Study)

### 1. 목표 TPS 달성을 위한 Vuser 산정 (Planning)
- **주어진 값**: 목표 TPS 200, 예상 응답 시간 0.2s, 평균 Think Time 0.8s
- **계산**: $L = 200 \times (0.2 + 0.8) = 200$명
- **결론**: 200명의 Vuser로 테스트를 수행해야 목표인 200 TPS가 발생함.

### 2. 고정 사용자 부하 하에서의 TPS 역산 (Monitoring)
- **주어진 값**: Vuser 1,000명, 실측 응답 시간 2s, Think Time 3s
- **계산**: $TPS = 1,000 / (2 + 3) = 200$ TPS
- **결론**: 사용자 수는 많지만 응답 시간이 길어 실질 처리량은 200 TPS에 불과함.

---

## Ⅳ. TPS 계산 시 주의사항 및 관리 포인트

### 1. Think Time의 실효성 확보
- **현실성**: 실제 사용 로그를 분석하여 화면별 적정 Think Time을 산출 적용.
- **임계점**: $Z$가 작을수록 시스템에 가해지는 압박이 커지며 병목이 빠르게 드러남.

### 2. 응답 시간의 비선형성 고려
- 부하($L$)를 늘리면 응답 시간($W$)도 함께 늘어나므로, 분모값이 커져 TPS 증가 폭이 둔화됨.
- **임계 부하(Saturation)**에 도달하면 $L$을 늘려도 $W$만 늘어나고 $TPS$는 정체됨.

---

## Ⅴ. TPS 계산의 활용 및 확장

- **Sizing Guide**: 신규 시스템 구축 시 사용자 수와 서비스 시나리오를 바탕으로 필요한 서버 대수와 스펙 결정.
- **SLA 도출**: 성능 테스트 결과와 비즈니스 요구사항을 비교하여 최적의 서비스 목표치(SLO) 확정.
- **Auto-scaling 기준**: 특정 TPS 도달 시 CPU 부하와 응답 시간의 상관관계를 파악하여 확장 임계값 설정.

---

## Ⅵ. 결론 및 제언

- TPS 계산은 성능 엔지니어링에서 **'측정할 수 없는 것을 측정할 수 있게 만드는'** 첫 단계임.
- 단순히 산식에 대입하는 것을 넘어, **Think Time의 변동성과 응답 시간의 꼬리 지연(Tail Latency)**이 계산 결과에 미치는 영향을 입체적으로 분석하는 통찰력이 요구됨.
