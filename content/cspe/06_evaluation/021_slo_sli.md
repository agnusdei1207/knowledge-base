## 📖 【암기용】 핵심 요약

*   **한눈에**: 서비스의 신뢰성을 관리하기 위해, 사용자 체감 품질을 실측하는 지표(**SLI**)와 해당 지표가 도달해야 할 내부 기술 목표치(**SLO**)를 정의하는 구글 SRE(Site Reliability Engineering)의 핵심 프레임워크.
*   **깊이 이해**:
    *   **배경**: 기존 하드웨어 중심의 가용성 지표(MTBF 등)는 "서버는 켜져 있는데 로그인이 안 돼요"라는 사용자 체감 품질과 큰 괴리가 있었음. 또한, SLA는 법적 계약이라 엔지니어가 매일 보면서 배포 속도를 조절할 기준이 되지 못함.
    *   **작동 원리**: 사용자가 가장 빈번하게 겪는 Critical Path(예: 로그인 성공률, 결제 응답시간)를 측정 기준인 **SLI**(Indicator)로 정의함. 그리고 이 SLI가 도달해야 할 타깃 수치(예: 99.9%)를 정하면 **SLO**(Objective)가 됨.
    *   **비유**: **다이어트 목표**. 
        *   **SLI (체중계 눈금)**: "현재 내 몸무게는 75kg이다." (매일 측정되는 팩트 데이터)
        *   **SLO (감량 목표)**: "이번 달 말까지 70kg 이하를 유지하겠다." (내부적인 목표치)
        *   **SLA (내기 계약)**: "이번 달 말까지 72kg을 못 만들면 친구한테 10만 원을 주겠다." (SLO보다 약간 널널하게 잡는 외부와의 계약)
    *   **구체 예시**: `SLI = (HTTP 200번대 응답 수) / (전체 HTTP 요청 수)`. 이를 한 달(Rolling Window) 측정해보니 99.95%가 나옴. 우리의 내부 목표인 `SLO = 99.9%`를 초과 달성했으므로, 엔지니어링 팀은 이번 주에 신규 기능을 마음껏 배포해도 됨.
    *   **흔한 오해/주의점**: "SLO는 무조건 100%로 잡아야 하는 거 아님?" $\rightarrow$ **오답**. SLO를 100%로 잡으면 단 한 번의 에러도 허용되지 않으므로 그 어떤 신규 기능도 배포할 수 없게 됨(혁신 멈춤). 100% 미만의 적정 SLO를 설정하여 '오류 예산(Error Budget)'을 확보하는 것이 SRE의 핵심 철학임.
*   **연결 개념**: SRE(Site Reliability Engineering), SLA(Service Level Agreement), Error Budget(오류 예산), APM, 꼬리 지연(Tail Latency, p99)

## 📝 【답안용】 서술 골격

> **💡 핵심 인사이트**
> *   **본질**: 추상적인 서비스 품질을 개발팀과 운영팀이 공통으로 합의할 수 있는 **정량적 측정값(SLI)**과 **통제 가능 목표(SLO)**로 치환하는 거버넌스.
> *   **가치**: 엔지니어링 팀이 '신규 기능 배포 속도'와 '서비스 안정성 유지' 사이에서 데이터 기반의 의사결정을 내릴 수 있도록 기준을 제공함.
> *   **판단 포인트**: SLI를 정의할 때 평균(Average)이 아닌 **백분위수(Percentile, p95/p99)**를 사용해야만 사용자 체감 지연(Tail Latency)을 정확히 포착할 수 있음.

### Ⅰ. 현대적 서비스 신뢰성 관리의 핵심, SLI와 SLO 개요
*   **정의**: 
    *   **SLI (Service Level Indicator)**: 서비스 수준을 나타내는 실제 관측 데이터 (예: 에러율, 지연시간, 처리량).
    *   **SLO (Service Level Objective)**: SLI 기반의 내부적 기술 목표치 (예: 지난 30일간 99.9% 요청이 200ms 이내 처리).
*   **목적**: MTBF 중심의 인프라 관점에서 벗어나 사용자 체감 중심의 품질 관리 체계 확립 및 DevOps 환경에서의 배포 속도 통제 기준(오류 예산) 마련.

### Ⅱ. SLI (Service Level Indicator)의 선정 및 측정 기법
*   **선정 원칙 (VALET / USE Method)**:
    *   **Volume**: 서비스 처리량 (TPS).
    *   **Availability**: 정상 처리된 요청의 비율 (HTTP 5xx 에러 제외 비율).
    *   **Latency**: 요청 처리 시간 (응답 속도).
*   **측정의 핵심: 평균의 함정 회피**: 
    *   단순 평균(Average)을 사용하면 소수의 극단적 지연(Outlier)이 묻힘.
    *   반드시 **p95, p99 (상위 95%, 99% 백분위수)**를 SLI 기준으로 삼아 꼬리 지연(Tail Latency)을 겪는 사용자 경험을 관리해야 함.

### Ⅲ. SLO (Service Level Objective) 수립 전략
*   **Target % 설정 원칙**: 100% SLO는 불가능하며 비효율적임. 사용자가 차이를 인지할 수 없는 수준(예: 99.9%)을 최적의 타깃으로 설정함.
*   **Rolling Window 적용**: "이번 달 1일부터 말일까지" 형태의 고정 기간(Calendar Window)은 월초/월말 편향이 생기므로, "최근 30일(Rolling Window)" 기준으로 상시 평가함.
*   **SLA와의 관계**: SLO는 항상 SLA(대외 계약)보다 타이트하게(보수적으로) 설정하여, SLA 위반 전 내부적으로 대응할 마진을 확보함. (예: SLO 99.9% $\to$ SLA 99.5%)

### Ⅳ. SLO 기반의 SRE(Site Reliability Engineering) 운영 사이클
1.  **SLI 측정**: APM, 프로메테우스를 통해 실시간 SLI 데이터 수집.
2.  **SLO 비교**: 수집된 SLI가 목표 SLO 구간 내에 있는지 평가.
3.  **Error Budget 산출**: `1 - SLO` 값을 통해 이번 달 허용 가능한 에러 총량 계산.
4.  **배포 게이팅 (Gating)**: 에러 예산이 넉넉하면 하루 10번 배포 허용, 예산이 고갈되면 신규 배포를 동결하고 안정화(버그 픽스)에만 인력 투입.

### Ⅴ. SLI/SLO 도입 시 실패를 막기 위한 실무 제언
*   **지표의 범람 방지**: 모든 API에 SLI를 걸면 경고(Alert) 피로도만 높아짐. 사용자 경험에 치명적인 **Critical Path (예: 결제 완료, 장바구니 담기 등 3~5개)**에만 집중해야 함.
*   **문화적 수용성**: SLO 미달 시 개발팀의 배포를 중단시키는 강력한 거버넌스가 작동하려면, 경영진의 전폭적인 SRE 문화 지지가 필수적임.
