# 📖 【암기용】 개념 완전 이해

## 한눈에
- **개요**: SLI(Service Level Indicator)는 **서비스 품질을 정량화하는 실측 지표**이고, SLO(Service Level Objective)는 SLI에 대한 **내부 목표치**임. 둘은 SLA(020)를 내부적으로 뒷받침하는 관측·목표 체계임.
- **왜 필요한가**: 응답시간·오류율·가용성의 실측값(SLI)과 목표선(SLO)이 없으면 장애 여부를 판정할 수 없고, 배포 속도와 안정성을 같은 기준으로 논의할 수 없음.
- **핵심 직관**: 온도계 눈금이 SLI, 실내 적정 온도 기준(22~26도)이 SLO, 그 기준을 어기면 위약금을 내는 임대 계약서가 SLA(020)임.

## 핵심 용어 정리 (내부에 등장하는 것들)

020이 SLA 계약 구조를, 022가 오류 예산을 다루므로 여기서는 SLI·SLO 고유의 측정·목표 설정 용어에 집중함.

| 용어/표기 | 의미 | 비유·예 |
|:---|:---|:---|
| SLI (상위 키워드) | Service Level Indicator, 서비스 품질 실측 지표 | 온도계 눈금값 |
| SLO (상위 키워드) | Service Level Objective, SLI에 대한 내부 목표치 | 관리사무소의 "22~26도 유지" 기준 |
| 측정 윈도우 | SLO 평가 기간(7일·30일·90일 롤링) | 월간 성적표 산출 기간 |
| 오류 예산 | 1 − SLO, 측정 기간 내 허용 실패 총량(022 상세) | 한 달 용돈 중 쓸 수 있는 한도 |
| 번 레이트(Burn Rate) | 오류 예산이 소진되는 속도 | 용돈을 쓰는 속도(빨리 쓰면 월말 부족) |
| p95/p99 백분위수 | 응답시간 SLI에서 95%/99%의 요청이 이 시간 내 완료 | 100명 중 95번째로 느린 사람의 대기 시간 |
| Critical Path | 사용자 체감에 직결되는 핵심 요청 경로 | 결제 API, 로그인 API 같은 핵심 호출 |

## 깊이 이해
- **배경·문제의식**: 기존 가용성 논의는 MTBF·MTTR(018) 같은 하드웨어 신뢰성 지표 중심이어서, API 오류율·응답시간 같은 사용자 체감 품질과 괴리가 있었음. Google SRE가 SLI/SLO/SLA 계층을 제시하면서 관측 지표(SLI)·조직 목표(SLO)·계약 의무(SLA)를 분리해 정의함.
- **작동 원리 — SLI 정의**:
  - SLI는 관측 가능한 비율·시간 지표로 정의함. 대표 유형: 요청 성공률(HTTP 2xx/3xx 비율), 응답시간(p95·p99), 처리량(TPS).
  - SLI 선정 기준: 사용자 체감에 직결되는 Critical Path 위주로 선정. 내부 배치 작업은 별도 SLI로 분리.
- **작동 원리 — SLO 설정**:
  - SLO는 SLI에 목표값과 측정 윈도우를 붙인 것임. 예: "30일 롤링 윈도우에서 가용성 SLI ≥ 99.9%".
  - SLO를 100%로 설정하면 오류 예산(022)이 0이 되어 어떤 배포도 리스크로 간주됨 → 실무에서는 99.9%처럼 여유를 둔 목표를 씀.
  - SLA(020)와의 관계: SLA는 SLO를 근거로 대외 계약을 맺되, SLO보다 완화된 값(예: SLO 99.9% → SLA 99.5%)으로 설정해 운영 마진을 확보함.
- **비유**: 건강검진에서 혈압계(SLI)로 혈압을 재고, 의사의 정상 기준(120/80 이하, SLO)과 비교해, 보험 약관(SLA)의 "정상 범위 벗어나면 보험금 지급" 조건을 판정하는 구조임.
- **구체 예시**: SLI = 5분 단위 HTTP 2xx/3xx 응답 비율, SLO = 해당 SLI ≥ 99.9%(30일 롤링), 오류 예산 = 0.1% × 43,200분 = 43.2분/월. 이번 달 이미 40분 소진 → 잔여 3.2분, 배포 동결 경보 발동.
- **흔한 오해·주의점**: ① SLA가 없어도 SLO는 운영 가능 — 내부 서비스에도 SLO를 설정하는 것이 SRE 관행. ② SLI를 너무 많이 정의하면 관리 복잡도가 급증 — 사용자 영향이 큰 3~5개 SLI에 집중하는 것이 관례. ③ 평균이 아닌 백분위수(p95·p99)로 SLI를 정의해야 꼬리 지연(tail latency)을 포착함.

## 연결 개념
- **SLA (020)**: SLO를 근거로 대외 계약을 맺는 상위 계약 구조. 020이 계약 구성요소를, 021이 내부 관측 체계를 담당.
- **오류 예산 (022)**: 1−SLO로 산출, 배포 속도 조절에 사용하는 운영 기법. SLO의 실행 도구.
- **가용성 계산 (019)**: 가용성 SLI의 산출 근거가 되는 MTBF/(MTBF+MTTR) 공식.

# 📝 【답안용】 시험 답안 템플릿

## 핵심 인사이트 (3줄 요약)

> 1. **본질**: SLI는 서비스 품질의 실측값, SLO는 SLI에 대한 내부 목표치로, SLA(020)를 내부적으로 뒷받침하는 관측·목표 체계임.
> 2. **가치**: 관측(SLI)·목표(SLO)·계약(SLA) 계층을 분리하면 장애 판정·배포 판단·계약 이행의 근거가 통일됨.
> 3. **판단 포인트**: SLI는 사용자 체감 Critical Path 위주 p95/p99로 정의하고, SLO는 100% 미만으로 설정해 오류 예산(022)을 확보해야 함.

## 출제 의도 및 답안 포인트

| 출제 의도 | 반드시 짚을 핵심 | 감점 회피 포인트 |
|:---|:---|:---|
| SLI·SLO·SLA 계층 구분 | 실측 지표 vs 내부 목표 vs 대외 계약 | 세 용어를 혼용 서술 |
| SLI 선정 기준 이해 | Critical Path 위주, p95/p99 백분위수 | 평균값 SLI만 언급 |
| SLO 설정 근거 확인 | 100% 미만 설정, 오류 예산(022) 연계 | 수치 없이 "높게 설정" 서술 |

> 요약: 계층 구분, SLI 선정 기준(Critical Path·백분위수), SLO-오류 예산 연계를 보여야 함.

---

## Ⅰ. 개요 및 필요성

- 개요: SLI는 서비스 품질 실측 지표, SLO는 SLI에 대한 내부 목표치
- 배경: MTBF·MTTR(018) 중심 신뢰성 논의가 사용자 체감 품질과 괴리 → Google SRE가 SLI/SLO/SLA 계층을 제시
- 필요성: SLI 측정값과 SLO 목표를 연결해야 장애 판정·오류 예산(022) 산출·SLA(020) 위반 여부를 정량 판단 가능

---

## Ⅱ. 구조 및 구성요소

```text
사용자 요청 -> SLI 수집(성공률/지연/처리량)
  -> SLO 목표 비교 -> 오류 예산(022) 산출 -> SLA(020) 위반 판정
                                          -> 배포 게이팅 정책
```

| 구성요소 | 역할 | 특이사항 |
|:---|:---|:---|
| SLI | 요청 성공률·응답시간·처리량 등 실측 지표 | p95/p99 백분위수 사용 |
| SLO | SLI에 대한 내부 목표값 + 측정 윈도우 | 예: 30일 롤링 99.9% |
| 측정 윈도우 | SLO 평가 기간 | 7일·30일·90일 롤링 |
| 오류 예산(022) | 1−SLO, 허용 실패 총량 | 배포 게이팅 입력값 |
| SLA(020) | SLO를 근거로 한 대외 계약 | SLO보다 완화된 값으로 설정 |

> 요약: SLI로 측정 → SLO와 비교 → 오류 예산 산출 → SLA 판정·배포 통제로 이어지는 3계층 구조임.

---

## Ⅲ. 동작원리 및 흐름도

```text
SLI 대상 정의(Critical Path) -> APM·로그 데이터 수집 -> SLI 산출
  -> SLO 대비 평가 -> 오류 예산 갱신 -> 대시보드 알림·배포 게이팅
```

1. 사용자 여정에서 체감 영향이 큰 Critical Path 요청군을 SLI 대상으로 정의함(결제·로그인 API 등)
2. APM·로그에서 성공/실패·응답시간 데이터를 수집하고 p95/p99 백분위수로 SLI를 산출함
3. 측정 윈도우(30일 롤링 등) 기준으로 SLI를 SLO 목표와 비교해 충족 여부를 판정함
4. 오류 예산(022) 잔량을 갱신하고 임계치(예: 소진율 80%) 초과 시 배포 동결 알림을 발동함

> 요약: Critical Path SLI 정의 → 수집·산출 → SLO 비교 → 오류 예산 갱신 순으로 목표 준수를 상시 판정함.

---

## Ⅳ. 특징

- 계층 분리: SLI(측정)·SLO(목표)·SLA(계약)를 분리해 관측·의사결정·계약 책임을 각각 독립 관리함
- 사용자 체감 중심: MTBF·MTTR(018) 같은 인프라 지표가 아니라 요청 성공률·p95 응답시간 등 사용자 체감을 직접 측정함
- SLO < 100%: 100% 설정 시 오류 예산(022)이 0이 되어 배포 정체 → 99.9%처럼 여유를 두는 것이 관례
- 백분위수 기반: 평균이 아닌 p95·p99로 정의해야 꼬리 지연(tail latency) 문제를 포착 가능
- SLA 대비 여유: SLO를 SLA보다 촘촘하게 설정해 내부 마진 확보(예: SLO 99.9% → SLA 99.5%)

---

## Ⅴ. 심화 비교 및 적용 판단

| 구분 | MTBF·MTTR 기반 관리(018) | SLI·SLO 기반 관리 | 선택 기준 |
|:---|:---|:---|:---|
| 측정 대상 | 하드웨어 고장 간격·복구 시간 | API 성공률·응답시간·처리량 | 인프라 vs 애플리케이션 관점 |
| 사용자 체감 | 간접(인프라 가동률) | 직접(요청 성공·지연) | 사용자 체감 품질 중요도 |
| 배포 연계 | 연계 없음 | 오류 예산(022) → 배포 게이팅 | DevOps·SRE 조직 유무 |
| 계약 구조 | 가용성 % 단일 지표 SLA | 다중 SLI 기반 계층형 SLA | 서비스 복잡도·계약 정밀도 |

> 요약: 사용자 체감 품질과 배포 연계가 중요하면 SLI·SLO 기반, 인프라 수명 관리 중심이면 MTBF·MTTR 기반을 적용함.

**리스크·대응:**
- SLI 과다 정의: 3~5개 초과 시 관리 복잡도 급증 → Critical Path 위주 3~5개로 제한하고 주기적 재정비 (지표: SLI 커버리지율 vs 관리 비용)
- SLO 과설정: 99.99% 이상으로 설정 시 오류 예산 부족 → 사용자 영향 데이터 기반 현실적 목표 재산정 (지표: 오류 예산 소진 빈도)
- SLA·SLO 역전: SLA가 SLO보다 타이트하게 계약 → SLA는 SLO 대비 0.1~0.5% 완화값으로 협상 (지표: 계약 목표 대비 실측 여유)

**점검 지표:**
- 품질: SLO 준수율(30일 롤링 기준 미달 0건) — SLO 대시보드
- 운영: SLI 커버리지(Critical Path 대비 SLI 적용률 95% 이상) — 사용자 여정 매핑 감사

---

## Ⅵ. 실무 적용 및 결론

**적용 방안:**
1. 사용자 여정 매핑으로 Critical Path를 식별하고, 요청 성공률·p95 응답시간 두 축으로 SLI를 3~5개 정의함
2. SLO는 30일 롤링 윈도우 기준 99.9%처럼 오류 예산(022)이 남는 값으로 설정하고 SLA(020)보다 촘촘히 운영함
3. APM·대시보드로 SLI를 실시간 수집해 SLO 대비 판정하고, 번 레이트 급증 시 자동 알림·배포 동결 파이프라인을 연계함

**결론:**
- 기술사 판단: SLI·SLO는 MTBF·MTTR(018)의 인프라 관점을 사용자 체감 관점으로 확장한 관측·목표 체계이며, SLA(020)와 오류 예산(022) 사이의 연결 고리임
- 향후 방향: 다중 SLI를 조합한 복합 SLO와 ML 기반 번 레이트 예측으로 사전 경보 정확도를 높이는 방향으로 발전 중임
