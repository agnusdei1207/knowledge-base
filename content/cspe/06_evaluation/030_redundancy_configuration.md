## 📖 【암기용】 핵심 요약

*   **한눈에**: 인프라(서버, 전력, 항온항습기 등) 장애 시 서비스를 유지하기 위해 예비(Standby) 자원을 얼마나 확보할 것인지를 수학적 기호로 나타낸 **'용량 이중화 설계 표준'**.
*   **깊이 이해**:
    *   **배경**: 단순히 "우리 데이터센터는 이중화되어 있습니다"라는 말은 엔지니어링의 언어가 아님. 장비 1대가 죽었을 때 버틸 수 있는지, 장비군 전체가 죽었을 때 버틸 수 있는지를 명확히 규정해야 Uptime Institute Tier 등급(데이터센터 안정성 등급)을 받을 수 있음.
    *   **N의 의미**: Need. 평상시 최대 피크(Peak) 부하를 처리하기 위해 필요한 **최소한의 장비 대수**.
    *   **N+1**: 최소 필요 대수(N)에 **예비 장비 1대(+1)**를 추가. 장비 1대의 동시 고장까지만 버틸 수 있음.
    *   **2N**: 최소 필요 대수(N)와 **완벽히 동일한 규모의 예비 그룹(N)**을 통째로 구축. 그룹 1개가 통째로 날아가도 버틸 수 있음.
    *   **2N+1**: 2N 구성에 예비 장비 1대를 추가. 그룹 하나가 통째로 날아간 상황에서, 남은 그룹의 장비 1대가 또 고장 나도 버틸 수 있는 초고가용성 구성.
    *   **비유**: **축구 국가대표팀 명단**. (시합을 뛰려면 N=11명이 필요함)
        *   **N+1**: 선발 11명 + 벤치 멤버 1명 (총 12명). 1명 부상당하면 교체 가능하지만, 2명 부상당하면 몰수패.
        *   **2N**: 선발 11명 + 후보팀 11명 (총 22명). 1군 버스가 전복되어도 2군 팀으로 100% 전력 대체 가능.
        *   **2N+1**: 1군 11명 + 2군 11명 + 스페어 1명 (총 23명). 1군이 전멸하고 2군에서 1명이 부상당해도 문제없음.
    *   **흔한 오해/주의점**: "웹 서버 4대가 필요하니, 안전하게 2N으로 8대를 구축합시다!" $\rightarrow$ 전력이나 핵심 원장이 아닌 웹 서버에 2N을 구성하는 것은 극도의 예산 낭비임. Stateless한 서버는 N+1 (또는 N+2)로 구성하고 오토스케일링을 붙이는 것이 현대 클라우드 아키텍처의 정답.
*   **연결 개념**: 고가용성(HA), Uptime Institute Tier 등급, 단일 장애점(SPOF), 용량 산정(Capacity Planning)

## 📝 【답안용】 서술 골격

> **💡 핵심 인사이트**
> *   **본질**: 시스템의 목표 가용성(SLA)과 투자 예산(TCO) 사이의 균형을 맞추기 위한 정량적 용량 산정(Capacity Sizing) 모델.
> *   **가치**: SPOF를 제거하는 수준을 넘어, 다중 장애(Multiple Failures) 상황에서 어느 수준까지 서비스 연속성을 보장할 것인지 명확한 아키텍처 가이드라인을 제시.
> *   **판단 포인트**: 데이터센터의 전기/냉방 시스템 같은 핵심 인프라는 2N 계열을, 일반 애플리케이션 계층은 N+1 또는 클라우드 네이티브 기반의 N+M 설계를 적용하는 것이 베스트 프랙티스.

### Ⅰ. 데이터센터 및 IT 인프라 가용성 척도, 이중화 구성 개요
*   **N (Need)의 정의**: 시스템이 최고 부하(Peak Load) 상태일 때 요구되는 최소한의 컴포넌트 수량.
*   **이중화 구성의 목적**: 컴포넌트 장애 또는 정기 유지보수 시 발생하는 용량 결손을 보완하여 무중단 서비스를 제공하기 위한 예비 용량(Reserve Capacity)의 표준화 모델.

### Ⅱ. 이중화 구성 수준별 아키텍처 분석
| 구성 모델 | 의미 및 산식 | 허용 가능한 장애 범위 | 주요 적용 대상 및 Tier 등급 |
| :--- | :--- | :--- | :--- |
| **N** | 예비 용량 없음 | 장애 허용 안 됨 (장애 시 즉시 다운) | 비핵심 시스템 / Tier I |
| **N+1** | 최소 필요 용량 + **예비 1기** | **단일 컴포넌트 1개**의 동시 고장 허용 | Web, WAS, 냉방기 / Tier II, III |
| **2N** | 최소 필요 용량의 **2배수 (A/B 이중계통)** | 단일 컴포넌트 뿐만 아니라 **시스템 계통(A 라인) 전체**의 장애 허용 | 전력망(UPS, 수전), 핵심 DB / Tier III, IV |
| **2N+1** | 2N 계통 + **예비 1기** | 한쪽 계통 전체 장애 발생 시, 살아남은 계통에서 추가 1개 장애 동시 허용 | Mission Critical 인프라 / Tier IV |

### Ⅲ. 이중화 설계 시 실무적 제약 및 고려사항
*   **연쇄 과부하 (Cascading Failure)**: 
    *   N+1 구성에서 평상시 장비 로드가 100%에 가깝다면, 1대 장애 시 남은 장비들이 부하를 견디지 못하고 연쇄 다운됨.
    *   따라서 평상시 목표 자원 사용률은 반드시 `N / (N+1)` 이하로 설계되어야 함.
*   **공통 원인 고장 (Common Cause Failure)**:
    *   2N 구성을 했더라도 A계통과 B계통의 전원 소스나 물리적 위치(Rack)가 같다면 무용지물. 반드시 물리적, 논리적 장애 도메인(Fault Domain) 분리가 동반되어야 함.

### Ⅳ. 데이터센터 Tier 인증 (Uptime Institute) 연계
*   **Tier I (Basic Capacity)**: N 구성. 무정전 전원장치나 발전기가 단일 경로.
*   **Tier II (Redundant Capacity)**: N+1 구성. 전원/냉각 장비 중 1개 고장 시 대응 가능.
*   **Tier III (Concurrently Maintainable)**: N+1 또는 2N 혼합. 서비스 중단 없이 모든 인프라 구성 요소의 동시 유지보수(점검/교체) 가능.
*   **Tier IV (Fault Tolerant)**: 2N 또는 2N+1 구성. 모든 장비와 경로가 완전 이중화되어 어떠한 단일 고장(화재 등)에도 자체 복원 및 서비스 지속 가능.

### Ⅴ. 현대 클라우드 환경의 이중화 패러다임 변화 (N+M)
*   **정적 H/W 의존 탈피**: H/W로 예비를 쌓아두는 방식은 TCO가 과도함.
*   **클라우드 네이티브 N+M**: 컨테이너 오케스트레이션(K8s) 및 Auto-scaling을 활용, 특정 AZ나 리전에 고정된 예비 자원을 두지 않고, 필요한 순간에 인스턴스를 무한대로 확장(N $\to$ N+M)하여 장애를 극복하는 S/W 기반 이중화로 진화 중.
