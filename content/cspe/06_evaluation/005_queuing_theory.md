## 📖 【암기용】 핵심 요약

*   **한눈에**: 큐잉 이론(대기행렬 이론)은 고객(요청)의 도착(Arrival)과 서비스(Service) 과정을 확률 모델로 정의하여, **시스템 내 대기 시간과 큐 길이를 정량적으로 예측**하는 수학적 프레임워크.
*   **깊이 이해**:
    *   **배경**: 트래픽 증가에 대비해 서버를 무작정 늘리는 대신 "목표 응답시간 200ms를 달성하려면 최소 몇 대의 서버가 필요한가?", "이용률이 몇 %일 때 시스템이 뻗는가?"에 대한 **수학적 근거(Sizing Reference)**를 확보하기 위해 등장.
    *   **작동 원리**: 유입 속도($\lambda$)와 처리 속도($\mu$)의 비율인 **이용률($\rho$)**이 1(100%)에 가까워지면, 대기열 길이($L_q$)와 대기 시간($W_q$)이 지수함수적으로 폭발(Explosion)함. 즉 $\rho = \frac{\lambda}{\mu}$일 때, 대기 인원 $L = \frac{\rho}{1-\rho}$가 됨.
    *   **비유**: **은행 창구 (M/M/c 모델)**. 창구가 1개(M/M/1)일 때는 앞 손님이 진상 피우면 뒷사람들 전체가 마비됨. 번호표 시스템을 도입하고 창구를 여러 개 두면(M/M/c), 한 곳이 막혀도 다른 창구로 분산되어 전체 대기 시간이 획기적으로 줄어듦(Pooling Effect).
    *   **구체 예시**: 1대의 서버(M/M/1)가 초당 100건($\mu=100$)을 처리하는데 90건($\lambda=90$)이 들어오면 $\rho=0.9$, 평균 고객 수 $L=9$. 하지만 99건이 들어오면 $\rho=0.99$, $L=99$명으로 대기열이 10배 폭증함.
    *   **흔한 오해/주의점**: "시스템 이용률 100% 달성 = 가장 효율적"이라는 착각. 이용률이 100%가 되면 수학적으로 응답시간은 무한대($\infty$)가 됨. 반드시 여유 용량(Headroom, 보통 30%)을 남겨두어야 함.
*   **연결 개념**: Kendall's Notation, 리틀의 법칙(Little's Law), 병목 분석, 로드밸런싱(Load Balancing), Auto-scaling

## 📝 【답안용】 서술 골격

> **💡 핵심 인사이트**
> *   **본질**: 시스템 대기 시간은 **"자원 사용의 효율성"**과 **"응답성의 훼손"** 사이의 확률적 트레이드오프(Trade-off).
> *   **가치**: 맹목적인 자원 증설(Over-provisioning)을 지양하고, Erlang-C 모델 기반의 과학적 Sizing을 통해 H/W 투자 최적화.
> *   **판단 포인트**: 단일 처리 구조(M/M/1)를 로드밸런서 기반 분산 구조(M/M/c)로 전환할 때 발생하는 '서버 풀링 효과(Server Pooling Effect)'를 수리적으로 증명하는 것이 핵심.

### Ⅰ. 성능 예측의 수학적 척도, 큐잉 이론의 개요
*   **정의**: 임의의 간격으로 유입되는 요청(Arrival)과 이를 처리하는 서버(Service) 간의 역학을 모델링하여, 대기행렬(Queue)의 동작을 수치로 예측하는 이론.
*   **목적**: 병목 지점 예측, 목표 응답시간 도출, 클라우드 워크로드 Sizing 및 스케일링 임계치(Threshold) 수립.

### Ⅱ. 큐잉 모델 분류 체계 (Kendall's Notation)
*   **표기법**: $A / S / c$ (Arrival Distribution / Service Distribution / No. of Servers)
*   **M/M/1 모델**: 포아송 도착(M) / 지수 서비스 시간(M) / 단일 서버(1). 시스템 병목 지점의 기초 분석.
*   **M/M/c 모델**: 복수 서버($c$)가 단일 대기열을 공유. 부하 분산(Load Balancing) 시스템의 근간.

### Ⅲ. M/M/1 핵심 지표 및 비선형 성능 곡선
*   **이용률 ($\rho$)**: $\rho = \lambda / \mu$ (단, 안정 상태를 위해 $\rho < 1$ 필수)
*   **평균 고객 수 ($L$)**: $L = \frac{\rho}{1-\rho}$ (이용률 90% 시 $L=9$, 99% 시 $L=99$로 지수적 폭증)
*   **성능 포화 곡선**:
```text
  Queue Length (Lq)
       │                         / ← ρ ≒ 1 (무한대 발산)
       │                        /
       │                      _/
       │                   __/   ← Knee Point (ρ ≒ 0.7~0.8)
       │       ___________/
       └───────┴────────┴────────┴──→ Utilization (ρ)
              0.5      0.8      1.0
```

### Ⅳ. M/M/c 다중 서버 구조의 Pooling Effect
*   **원리**: N개의 독립된 대기열(각 1대의 서버)을 운영하는 것보다, 1개의 통합 대기열을 N대의 서버가 공유할 때 자원 유휴 시간이 줄어들어 시스템 전체 대기 시간($W_q$)이 획기적으로 단축됨.
*   **아키텍처 적용**: Nginx/HAProxy 등 L7 Load Balancer를 앞단에 두고 뒤에 다수의 WAS(Tomcat, Node.js)를 배치하는 것이 서버 풀링 이론의 실체화.

### Ⅴ. 큐잉 이론 기반 용량 산정(Sizing) 프로세스
1.  **목표 설정**: 요구 SLA 기준 p95 응답시간 임계치($W_{target}$) 설정.
2.  **부하 산출**: 예상 최고 피크 타임 TPS($\lambda$) 도출.
3.  **단일 역량 평가**: 부하 테스트를 통해 단일 서버의 한계 처리율($\mu$) 도출.
4.  **C 값 도출**: Erlang-C 공식을 활용하여 $W_q \le W_{target}$을 만족하는 최소 서버 개수($c$) 산출.

### Ⅵ. Cloud-Native 시대의 큐잉 이론 한계 극복
*   **일반 분포 적용 (M/G/1)**: 실제 MSA 환경에서 API 처리 시간은 고정 분포(General)에 가깝기 때문에 P-K(Pollaczek-Khinchin) 공식을 응용.
*   **이벤트 기반 스케일링**: KEDA 등을 통해 큐(Kafka, RabbitMQ)의 Lag(대기열 길이)을 실시간 모니터링하여 $\rho$가 임계점을 넘기 전 선제적 Pod 스케일 아웃.
