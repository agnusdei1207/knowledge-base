# 📖 【암기용】 개념 완전 이해

> 목적: 일회성 검증인 '성능 테스트'와 상시 활동인 '성능 관리'가 어떻게 다른지, 운영 중인 시스템이 뻗지 않도록 어떻게 지속적으로 튜닝하는지 이해하게 만든다.

## 한눈에
- **개요**: 목표 설정(SLO) - 수집/모니터링(APM) - 진단/분석 - 튜닝 - 재검증 과정을 끝없이 반복하여, 운영 중인 시스템의 성능 저하를 방지하고 쾌적한 상태를 유지하는 영속적 관리 체계.
- **왜 필요한가**: 시스템 오픈 전에 아무리 성능 테스트(BMT/부하시험)를 완벽하게 했어도, 운영 중에는 사용자가 늘고, 데이터가 쌓이고(DB 비대화), 패치가 적용되면서 성능이 서서히 좀먹어 들어간다. 놔두면 결국 장애가 나기 때문에 상시 관리가 필요하다.
- **핵심 직관**: 성능 테스트가 자동차를 출고하기 전 공장에서 하는 "엔진 최고 속도 검사(1회성)"라면, 성능 관리는 주행 중에 계기판(APM)을 보면서 주기적으로 엔진 오일을 갈고 타이어 공기압을 조절하는 "차량 유지보수 사이클"이다.

## 깊이 이해
- **배경·문제의식**: "오픈 때는 날아다니던 시스템이 1년 지나니 클릭하고 5초를 기다려야 한다." 이는 데이터베이스에 인덱스가 깨지거나 풀 스캔(Full-Scan)이 도는 등 '점진적 저하'를 방치했기 때문이다.
- **작동 원리**: 
  - **SLO 설정**: 응답시간 3초 이내, CPU 70% 이하 등 목표치 설정.
  - **모니터링**: APM(Application Performance Management)이나 SMS/NMS 도구로 실시간 계측.
  - **분석/진단**: 지표가 임계치를 넘으면, 트랜잭션을 추적해 DB 구간인지 로직 구간인지 병목 지점 파악.
  - **튜닝**: SQL 인덱스 추가, 캐시(Redis) 적용, JVM GC(Garbage Collection) 최적화 등 수행.
  - **재검증**: 튜닝 후 SLO 이내로 회복되었는지 확인.
- **비유**: 성능 관리는 "정기 건강 검진 체계"와 같다. 콜레스테롤 목표치(SLO)를 정하고, 주기적으로 혈액검사(모니터링)를 한 뒤, 수치가 높으면 식단 조절(튜닝)을 하고, 다시 피검사(재검증)를 하는 무한 루프다.
- **구체 예시**: 블랙프라이데이를 앞두고, 평소 0.5초이던 결제 응답시간이 1.5초로 느려지는 패턴을 APM으로 사전 감지했다. 분석 결과 결제 내역 테이블 풀스캔이 원인이라, 결제 일자 컬럼에 인덱스를 걸어 0.3초로 튜닝하고 사태를 막았다.
- **흔한 오해·주의점**: APM 대시보드를 띄워놓고 바라보는 것만으로는 성능 관리가 아니다. 지표를 보고 -> 원인을 진단해서 -> 코드를 고치거나 자원을 늘리는 '액션(튜닝)'이 결합되어야 비로소 관리 방법론이 성립한다.

## 연결 개념
- **APM (011)**: 성능 관리 방법론의 '모니터링'과 '분석' 단계를 수행하는 핵심 무기.
- **용량 계획 (058)**: 성능 관리 데이터를 바탕으로, "3개월 뒤면 서버가 터지겠군" 하고 미리 하드웨어를 구매하는 상위 계획.
- **성능 테스트 (009)**: 관리 방법론 사이클 중 '재검증' 시점이나 시스템 오픈 시점에 수행되는 일회성 확인 작업.

# 📝 【답안용】 시험 답안 템플릿

> 목적: 시험장에서 25분에 그대로 쓰는 답안 양식. 작성방식(추상표현 금지·수치·도식·문제유형 전환)을 엄격히 지킨다.

## 핵심 인사이트 (3줄 요약)

> 1. **본질**: 정보시스템 성능 관리는 목표 설정부터 튜닝, 재검증까지의 순환 사이클(PDCA)을 통해 시스템의 가용성과 응답성을 유지하는 지속적 관리 체계이다.
> 2. **가치**: 데이터 누적과 트래픽 변화로 인한 '점진적 성능 저하'를 조기에 탐지하여, 대형 장애 발생 이전에 시스템을 최적화(Shift-Left)한다.
> 3. **판단 포인트**: 단발성 이벤트인 부하 테스트와의 차별성을 강조하고, APM을 활용한 구간별 병목 진단 역량과 구체적인 튜닝 방안을 명시해야 한다.

## 출제 의도 및 답안 포인트

| 출제 의도 | 반드시 짚을 핵심 | 감점 회피 포인트 |
|:---|:---|:---|
| 관리 프레임워크 이해 | **목표설정-모니터링-진단-튜닝-검증의 순환 구조** | 모니터링만 언급하고 '튜닝과 검증' 절차 누락 |
| 실질적 병목 원인 진단 | APM 기반의 End-to-End 트랜잭션 추적 및 Tier별 분해 | 단순히 "느려지면 서버를 늘린다"식의 1차원적 서술 |
| 성능 테스트와의 구분 | **1회성 검증(테스트) vs 생명주기 전반의 지속 관리(관리)** | 성능 테스트 기법(스트레스 테스트 등)만 나열 |

> 요약: 이 문제는 "성능을 향상시키는 스킬(SQL 튜닝 등)" 하나만 묻는 것이 아니라, "문제를 발견하고 고치는 시스템적 절차(방법론)"를 묻는 것이다.

---

## Ⅰ. 개요 및 필요성

- **개요**: 정보시스템의 응답시간과 처리량(TPS) 목표를 설정하고, 운영 환경에서 이를 지속 모니터링·분석·개선하는 생명주기 관리 방법론.
- **배경**: 시스템 오픈 전 성능 부하 시험을 통과했더라도, 운영 중 데이터 누적, 코드 패치, 사용자 패턴 변화로 인해 필연적인 성능 저하가 발생함.
- **필요성**: 장애가 발생한 후 사후 대응(Fire-fighting)하는 악순환을 끊고, APM 지표 기반으로 병목을 조기 진단하여 시스템 중단을 예방해야 함.

## Ⅱ. 구조 및 구성요소

```text
[목표 설정] -> [수집/모니터링] -> [진단/분석] -> [튜닝/최적화] -> [재검증]
    ^                                                            |
    +------------------------ < 지속적 순환 > ---------------------+
```

| 구성요소 | 핵심 역할 | 주요 산출물 및 도구 |
|:---|:---|:---|
| **목표 설정 (Plan)** | 업무 중요도에 따른 성능 지표(응답시간, TPS, CPU 등) 및 SLO 정의 | 서비스 수준 협약서(SLA), 목표 성능 정의서 |
| **모니터링 (Do)** | SMS/APM 도구를 이용한 실시간 지표 수집 및 임계치 알람 발생 | APM 대시보드, 알람 발생 이력 로그 |
| **진단/분석 (Check)**| 임계치 초과 트랜잭션의 구간별(WEB-WAS-DB) 소요시간 분해 및 병목 지점 도출 | 병목 진단 보고서, 트랜잭션 프로파일링 |
| **튜닝 적용 (Act)** | 애플리케이션 코드 수정, DB 인덱스 조정, JVM 파라미터 최적화 | 튜닝 조치 내역서, 패치 적용 내역 |
| **재검증 (Feedback)**| 튜닝 적용 후 동일 시나리오 하에서 목표(SLO) 달성 여부 재측정 | 재검증 성능 평가 결과서 |

> 요약: 성능 관리는 한 번 고치고 끝나는 것이 아니라, 환경 변화에 맞추어 끊임없이 목표를 조정하고 최적화하는 데브옵스(DevOps)적 무한 순환 고리다.

---

## Ⅲ. 동작원리 및 흐름도 (진단/분석 단계 상세)

장애 임계치가 발생했을 때, 어떻게 병목을 찾아내는지가 성능 관리의 핵심 동작 원리이다.

```text
[임계치 초과 알람] -> [트랜잭션 추적(Trace)] -> [티어(Tier)별 시간 분해]
   -> [DB 지연 판단 시: SQL 추출] -> [실행계획(Explain) 분석] -> [인덱스/조인 튜닝]
```

| 단계 | 처리 내용 | 검증 및 판단 기준 |
|:---|:---|:---|
| **1. 알람 감지** | 특정 URL의 응답시간이 설정된 P95(상위 95%) 임계치인 3초를 초과 | 임계치 및 경고 알람 룰셋 |
| **2. 구간 분해** | APM을 통해 총 3초 중 WEB(0.1s), WAS(0.4s), DB(2.5s)로 소요시간 분리 | Tier별 응답시간 점유율 |
| **3. 병목 심층 분석**| DB 지연으로 판단 시, 해당 트랜잭션을 유발한 악성 SQL 식별 및 실행계획 확인 | Full Table Scan 여부, Lock 대기 시간 |
| **4. 튜닝 및 배포** | 누락된 결합 인덱스 생성 또는 로직상 반복 쿼리(N+1 문제) 캐시 처리 | 튜닝 후 논리적/물리적 I/O 감소율 |

> 요약: 성능 진단은 "느리다"는 현상을 "WAS 구간의 쓰레드 락" 혹은 "DB 구간의 풀스캔"이라는 구체적 원인으로 쪼개어 들어가는 과학적 분석 과정이다.

## Ⅳ. 특징

| 구분 | 내용 | 판단 포인트 |
|:---|:---|:---|
| **장점** | 고객이 불만을 제기하기 전에 선제적으로 성능 저하 요소를 제거하여 브랜드 신뢰도 유지 | **MTBF(평균 무고장 시간) 증가 및 사전 예방률** |
| **한계** | 24시간 모니터링을 위한 고가의 APM 솔루션 도입 비용과 전담 분석(Tuning) 인력 유지 비용 발생 | 시스템 중요도 등급(Tier)에 따른 관리 수준 차등화 |
| **비교 포인트** | 성능 테스트는 릴리즈 전 '버전'의 완성도를, 성능 관리는 운영 중인 '환경'의 안정성을 목표로 함 | 시점(개발/오픈전 vs 운영)의 차이 |

> 요약: 우수한 성능 관리는 소 잃고 외양간 고치는 비용을 막아주지만, 모든 시스템에 동일한 에너지를 쏟는 것은 낭비이므로 BIA 기반의 차등 관리가 필수다.

## Ⅴ. 심화 비교 및 적용 판단 (튜닝 영역별 접근 전략)

| 튜닝 영역 | 주요 병목 원인 | 핵심 튜닝 기법 (해결책) | 성능 개선 효과 |
|:---|:---|:---|:---|
| **애플리케이션(코드)** | 동기 처리 대기, 비효율적 루프, N+1 쿼리 문제 | 비동기(Async) 처리, 로컬/글로벌 캐시(Redis) 적용, 코드 리팩토링 | WAS CPU 점유율 하락, 처리량 증가 |
| **데이터베이스(DB)** | 인덱스 부재, 악성 조인(Cartesian), 데드락(Deadlock) | 인덱스 재구성, SQL 실행계획 튜닝, 파티셔닝(Partitioning), 트랜잭션 분리 | 물리적 I/O 대폭 감소, 응답시간 개선 |
| **시스템/아키텍처** | 물리적 메모리 고갈, 커넥션 풀(Connection Pool) 부족 | JVM GC 튜닝, 스레드/커넥션 풀 사이징 조정, Auto-Scaling 구성 | 시스템 멈춤(Hang) 및 병목 구간 해소 |

> 요약: 성능 튜닝은 무턱대고 CPU를 증설하는 것(Scale-up)이 아니라, 가장 병목이 심한 구간(통상 DB I/O)부터 논리적으로 최적화하는 것이 정석이다.

| 리스크 | 발생 원인 | 대응 방안 (실무 관점) | 확인 지표 |
|:---|:---|:---|:---|
| **가짜 경보(False Alarm)** | 임계치를 너무 빡빡하게 고정값으로 설정 | 머신러닝 기반의 이상 탐지(Anomaly Detection)를 통한 동적 임계치 적용 | 일평균 오탐 알람 건수 축소 |
| **튜닝 부작용 발생** | A 쿼리 튜닝용 인덱스가 B 쿼리를 느리게 만듦 | 튜닝 스크립트를 즉시 운영 반영하지 않고 상용과 동일한 스테이징 환경에서 회귀 테스트 | 튜닝 후 재검증 통과율 |

> 요약: 성능 관리 체계 자체가 시스템에 독이 되지 않으려면, 동적 알람 체계와 안전한 재검증(Regression Test) 절차를 확보해야 한다.

## Ⅵ. 실무 적용 및 결론

**적용 방안 3개 (필수 — 단계별 또는 항목별):**
1. **기반 구축**: 운영 이관 전, 핵심 트랜잭션 식별 후 APM 대시보드에 P95(상위 95% 응답시간) 기반의 동적 임계치 알람을 구성함.
2. **정기 진단**: 주간 단위로 가장 오래 걸리는 'Top 10 악성 SQL' 및 '빈번한 GC 발생 노드'를 추출하여 원인을 분석하고 튜닝 과제로 도출함.
3. **용량 연계**: 성능 튜닝(논리적 개선)으로도 해결이 불가능한 한계선 도달 시, 즉각 용량 계획(Capacity Planning) 프로세스로 이관하여 물리적 증설을 추진함.

**결론 (2줄):**
- **기술사 판단**: 정보시스템 성능 관리는 1회성 테스트로 끝나는 것이 아니며, 모니터링-진단-튜닝이 데브옵스 문화 속에 내재화된 무한 순환 체계로 작동해야 함.
- **향후 방향**: 단순 지표 수집(APM)을 넘어, AI가 스스로 병목 원인을 진단하고 최적의 설정을 제안하는 AIOps(AI for IT Operations) 기반 자율 튜닝 시스템으로 진화해야 함.
