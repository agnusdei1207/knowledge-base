# 📖 【암기용】 개념 완전 이해

> 목적: 성능 테스트(1회성 검증)와 성능 관리(지속 활동)가 왜 다른지, 운영 중 시스템 성능을 어떻게 계속 관리하는지 이해하게 만든다. 시험 답안 양식이 아니라, 이해를 위한 친절한 설명이다.

## 한눈에
- **개요**: 목표 설정 - 모니터링 - 분석 - 튜닝 - 재검증을 반복해 운영 중인 정보시스템의 성능을 지속적으로 관리하는 방법론
- **왜 필요한가**: BMT나 성능 테스트는 특정 시점의 목표 충족 여부만 확인한다. 운영 중에는 트래픽 증가, 데이터 누적, 코드 변경으로 성능이 계속 변하므로 지속 관리 체계가 필요하다
- **핵심 직관**: 성능 테스트가 자동차 출고 전 1회 검사라면, 성능 관리는 운행 중 계기판을 계속 지켜보며 정비 시점을 판단하는 활동이다

## 깊이 이해
- **배경·문제의식**: 오픈 시점에 목표 TPS를 달성했더라도 데이터가 누적되고 사용자가 늘면 동일 코드에서도 응답시간이 저하된다
- **작동 원리**: SLO 기반으로 목표 지표를 정하고, APM으로 실시간 모니터링하며, 병목 구간을 분석해 튜닝한 뒤 재검증으로 개선 효과를 확인하는 순환 구조로 동작한다
- **비유**: 목표 설정은 건강검진 기준치 설정, 모니터링은 웨어러블 기기의 상시 측정, 분석·튜닝은 원인 파악 후 처방, 재검증은 다음 검진에서 개선 확인에 해당한다
- **구체 예시**: 오픈 6개월 후 데이터가 1000만 건으로 늘어 조회 응답시간이 200ms에서 800ms로 늘면, 인덱스 재설계로 튜닝하고 재검증에서 300ms로 회복했는지 확인한다
- **흔한 오해·주의점**: 성능 테스트를 통과했다고 성능 관리가 끝난 것이 아니다. 성능 테스트는 특정 시점의 결함을 잡는 활동이고, 성능 관리는 운영 기간 내내 반복하는 활동이라는 점을 구분해야 한다

## 연결 개념
- BMT 방법론(015) — 도입 전 1회성 검증과 운영 중 지속 관리의 차이 비교 대상
- APM(011) — 성능 관리 방법론의 모니터링 단계 핵심 도구
- 용량 계획(058) — 성능 관리에서 얻은 추세 데이터를 미래 자원 예측에 활용하는 연계 활동

# 📝 【답안용】 시험 답안 템플릿

> 목적: 시험장에서 25분에 그대로 쓰는 답안 양식. 작성방식(추상표현 금지·수치·도식·문제유형 전환)을 엄격히 지킨다.
> 핵심: 성능 관리 답안은 목표-모니터링-분석-튜닝-재검증 순환 구조와 성능 테스트 대비 차이를 함께 제시한다.

## 핵심 인사이트 (3줄 요약)

> 1. **본질**: 정보시스템 성능 관리는 목표 설정부터 재검증까지 순환하며 운영 중 성능을 지속 관리하는 방법론이다.
> 2. **가치**: 트래픽·데이터 증가로 인한 점진적 성능 저하를 조기에 발견해 장애로 이어지기 전에 튜닝한다.
> 3. **판단 포인트**: 1회성 검증인 성능 테스트와 달리, 운영 기간 내내 반복되는 순환 활동인지로 구분한다.

## 출제 의도 및 답안 포인트

| 출제 의도 | 반드시 짚을 핵심 | 감점 회피 포인트 |
|:---|:---|:---|
| 성능 테스트와 차이 이해 확인 | 1회성 검증 vs 지속 순환 관리 | 성능 테스트와 성능 관리를 동일하게 서술 |
| 관리 순환 구조 이해 확인 | 목표-모니터링-분석-튜닝-재검증 단계 | 모니터링만 언급하고 튜닝·재검증 누락 |
| 지표 연계 이해 확인 | SLO·APM 지표를 관리 순환에 연결 | 지표 없이 정성적 서술만 나열 |

> 요약: 이 문제는 튜닝 기법 나열보다 성능 테스트와의 차이와 지속 순환 관리 구조를 보여야 한다.

---

## Ⅰ. 개요 및 필요성

- 정의: 목표-모니터링-분석-튜닝-재검증을 반복하는 운영 중 성능 지속 관리 방법론
- 배경: 성능 테스트는 특정 시점만 검증해 트래픽·데이터 증가에 따른 점진적 저하를 잡지 못함
- 필요성: 운영 기간 내내 성능 지표를 추적해 장애 전이 아닌 저하 초기 단계에서 튜닝해야 함

---

## Ⅱ. 구조 및 구성요소

```text
목표 설정(SLO) -> 모니터링(APM) -> 분석(병목 진단)
  -> 튜닝(인덱스/캐시/자원) -> 재검증 -> 목표 설정으로 순환
```

| 구성요소 | 역할 | 산출물 |
|:---|:---|:---|
| 목표 설정 | 응답시간·처리량 목표(SLO) 정의 | 성능 목표 정의서 |
| 모니터링 | 실시간 지표 수집 | APM 대시보드, 알림 이력 |
| 분석 | 병목 구간과 원인 진단 | 병목 분석 보고서 |
| 튜닝 | 인덱스, 캐시, 자원 조정 적용 | 튜닝 적용 내역서 |
| 재검증 | 튜닝 효과를 지표로 재확인 | 재검증 결과 보고서 |

> 요약: 성능 관리는 목표-모니터링-분석-튜닝-재검증 5단계를 순환하며 운영 성능을 유지한다.

---

## Ⅲ. 동작원리 및 흐름도

```text
SLO 설정 -> 지표 상시 수집 -> 임계치 초과 알림
  -> 병목 원인 분석 -> 튜닝 적용 -> 재검증 후 SLO 재확인
```

| 단계 | 처리 내용 | 검증 기준 |
|:---|:---|:---|
| 1 | 응답시간·처리량 목표를 SLO로 정의 | 목표치와 허용 오차 |
| 2 | APM으로 실시간 지표 수집과 임계치 알림 설정 | 알림 지연시간 |
| 3 | 병목 구간(DB, 네트워크, 애플리케이션)을 분석 | 구간별 소요시간 분해 |
| 4 | 튜닝 적용 후 동일 조건에서 재검증 | 튜닝 전후 지표 개선폭 |

> 요약: 성능 관리는 목표 대비 실측치를 상시 비교하며 임계치 초과 시 분석과 튜닝, 재검증을 반복한다.

---

## Ⅳ. 특징

| 구분 | 내용 | 판단 포인트 |
|:---|:---|:---|
| 장점 | 점진적 성능 저하를 장애 발생 이전에 발견 | 조기 튜닝으로 장애 예방 |
| 한계 | 순환 체계 운영에 지속적 인력·도구 투입 필요 | 모니터링·튜닝 비용 대비 효과 |
| 비교 포인트 | 성능 테스트는 특정 시점 검증, 성능 관리는 운영 기간 내내 반복 | 검증 시점의 1회성 여부 |

> 요약: 성능 관리는 점진적 저하를 조기 발견하지만 지속 운영 비용이 수반되어 대상 시스템 중요도에 따라 범위를 조정한다.

## Ⅴ. 심화 비교 및 적용 판단

| 비교 축 | 성능 테스트(BMT 등) | 성능 관리 방법론 | 선택 기준 |
|:---|:---|:---|:---|
| 구조 | 도입 전 1회성 부하 시험 | 운영 기간 내내 순환 관리 | 시스템 생애주기 단계 |
| 비용/성능 | 시험 기간 한정 비용 | 모니터링·튜닝 지속 비용 | 운영 중요도, SLA 수준 |
| 운영/위험 | 도입 시점 목표 미달 위험 | 운영 중 점진적 저하 위험 | 트래픽·데이터 증가 속도 |

> 요약: 도입 전에는 성능 테스트로 목표 달성을 확인하고, 운영 중에는 성능 관리로 점진적 저하에 대응한다.

| 리스크 | 원인 | 대응 방안 | 확인 지표 |
|:---|:---|:---|:---|
| 저하 미탐지 | 임계치 알림 미설정 | SLO 기반 임계치와 알림 채널 구성 | 임계치 초과 탐지 소요시간 |
| 원인 오진단 | 구간별 소요시간 분해 없이 추정 | APM 트레이싱으로 구간별 원인 분리 | 구간별 응답시간 비중 |
| 튜닝 효과 미검증 | 튜닝 후 재검증 생략 | 튜닝 전후 지표 비교 절차 의무화 | 재검증 이행률 |

> 요약: 성능 관리 리스크는 임계치 알림, 구간별 원인 분리, 재검증 절차 의무화로 통제한다.

| 점검 항목 | 목표 기준 | 측정 방법 |
|:---|:---|:---|
| 응답시간 | SLO 목표치(p95 등) 유지 | APM 지표 |
| 처리량 | 목표 TPS 대비 실측 처리량 유지 | 트랜잭션 로그 |
| 튜닝 효과 | 튜닝 전후 지표 개선폭 확보 | 재검증 결과 비교 |

> 요약: 성능 관리 성과는 SLO 유지 여부, 목표 처리량 달성, 튜닝 전후 개선폭으로 판단한다.

---

## Ⅵ. 실무 적용 및 결론

**적용 방안 3개 (필수 — 단계별 또는 항목별):**
1. 운영 착수 전 SLO를 응답시간·처리량 수치로 정의하고 APM 알림 임계치를 함께 설정함
2. 임계치 초과 시 구간별 소요시간을 분해해 병목 원인을 진단하고 튜닝 방안을 적용함
3. 튜닝 적용 후 동일 조건에서 재검증해 개선 효과를 지표로 확인하고 SLO를 재조정함

**결론 (2줄):**
- 기술사 판단: 정보시스템 성능은 도입 시점 테스트로 끝나지 않으며 운영 기간 내내 순환 관리 체계를 유지해야 함
- 향후 방향: AIOps 기반 이상탐지·자동 튜닝 제안 도구를 순환 관리 체계에 결합하는 방향으로 발전해야 함
