# 📖 【암기용】 개념 완전 이해

> 목적: 정보시스템 성능 관리를 장애 이후 튜닝이 아니라 목표 지표를 정하고 지속 측정·개선하는 운영 방법론으로 이해하게 만든다.

## 한눈에
- **개요**: 성능 목표를 지표화해 측정·분석·개선하는 운영 관리 체계
- **왜 필요한가**: 서비스 지연은 CPU 부족만으로 발생하지 않는다. TPS, p95 지연, 오류율, 자원 사용률을 함께 봐야 병목 위치를 특정할 수 있다.
- **핵심 직관**: 성능 관리는 "느낌"이 아니라 기준선, 임계치, 추세, 개선 조치의 반복 사이클이다.

## 깊이 이해
- **배경·문제의식**: 클라우드·마이크로서비스 환경은 의존 서비스가 많아 단일 서버 지표만으로 체감 지연을 설명하기 어렵다.
- **작동 원리**: SLI를 정의하고, 기준선과 목표치를 설정한 뒤, APM·로그·메트릭으로 병목을 찾고 개선 전후를 비교한다.
- **비유**: 병원에서 체온·혈압·혈당을 계속 기록해 원인을 좁히는 방식과 같다.
- **구체 예시**: 주문 API p95 800ms, 오류율 2%, DB CPU 85%가 동시에 관측되면 쿼리 실행계획과 커넥션 풀부터 점검한다.
- **흔한 오해·주의점**: 평균 응답시간만 보면 tail latency와 특정 구간 장애를 놓친다.

## 연결 개념
- SLI/SLO - 성능 목표 수치화 기준
- APM - 트랜잭션 추적과 병목 분석 도구
- 용량 계획 - 성능 추세 기반 자원 증설 판단

# 📝 【답안용】 시험 답안 템플릿

> 목적: 시험장에서 25분에 그대로 쓰는 답안 양식. 작성방식(추상표현 금지·수치·도식·문제유형 전환)을 엄격히 지킨다.
> 핵심: 출제자는 성능관리의 PDCA 흐름과 정량 지표 기반 병목 판단을 확인한다.

## 핵심 인사이트 (3줄 요약)

> 1. **본질**: 정보시스템 성능 관리는 목표 지표 설정, 측정, 분석, 개선, 검증의 반복 체계다.
> 2. **가치**: p95 지연, TPS, 오류율, CPU·DB 지표를 연결해 장애 전 조기 경보와 튜닝 우선순위를 만든다.
> 3. **판단 포인트**: 평균값보다 p95/p99, 기준선 대비 편차, 병목 원인별 개선 조치를 제시해야 한다.

## 출제 의도 및 답안 포인트

| 출제 의도 | 반드시 짚을 핵심 | 감점 회피 포인트 |
|:---|:---|:---|
| 성능관리 절차 이해 확인 | 목표 수립 -> 측정 -> 분석 -> 개선 -> 검증 | 지표 없이 추상 서술 |
| 병목 판단 역량 확인 | APM trace, DB wait, CPU, network, queue depth | 서버 증설만 답안으로 제시 |
| 운영 통제 관점 확인 | 기준선, 임계치, 경보, 변경 후 검증 | 일회성 튜닝으로만 설명 |

> 요약: 이 문제는 성능을 지속 관리할 운영 프로세스와 지표 기반 판단을 묻는다.

## Ⅰ. 개요 및 필요성

- 개요: 성능 지표 기반 지속 개선 체계
- 배경: 분산 시스템은 병목이 애플리케이션, DB, 네트워크, 외부 API 중 어디서든 발생할 수 있음
- 필요성: p95 500ms, 오류율 1% 이하, CPU 70% 이하 같은 목표로 SLA 위반 전 조치가 필요함

## Ⅱ. 구조 및 구성요소

```text
서비스 목표 -> SLI/SLO 정의 -> 모니터링 수집 -> 병목 분석
  -> 개선 조치 -> 회귀 검증 -> 기준선 갱신
```

| 구성요소 | 역할 | 특이사항 |
|:---|:---|:---|
| 성능 목표 | 업무별 응답시간·처리량 기준 설정 | SLA·SLO와 연결 |
| 측정 체계 | APM, 로그, 메트릭, synthetic test 수집 | p95/p99와 오류율 포함 |
| 분석 체계 | 병목 구간과 원인 식별 | trace, wait event, queue depth |
| 개선 체계 | 튜닝·캐시·스케일링·쿼리 개선 수행 | 변경 전후 비교 필요 |

> 요약: 목표, 측정, 분석, 개선, 검증이 닫힌 루프로 연결되어야 성능관리 체계가 된다.

## Ⅲ. 동작원리 및 흐름도

```text
기준선 설정 -> 실측 수집 -> 임계치 초과 탐지
  -> 병목 구간 분해 -> 개선안 적용 -> 재측정
```

| 단계 | 처리 내용 | 검증 기준 |
|:---:|:---|:---|
| 1 | 업무별 SLI/SLO와 기준선 설정 | p95, TPS, error rate |
| 2 | APM·로그·인프라 메트릭 수집 | trace coverage 90% 이상 |
| 3 | 병목 원인 분석 | CPU, DB wait, network, lock |
| 4 | 개선 후 재측정 | 개선 전후 동일 부하 비교 |

> 요약: 성능관리는 기준선과 실측값 차이를 원인별로 분해하고 동일 조건에서 개선 효과를 검증한다.

## Ⅳ. 특징

| 구분 | 내용 | 판단 포인트 |
|:---|:---|:---|
| 장점 | 장애 전 성능 저하 조기 탐지 | SLO burn rate, p95 추세 |
| 한계 | 지표 누락 시 원인 오판 | trace sampling, 로그 누락 |
| 비교 대상 | 사후 장애 대응 | 사전 기준선·경보 기반 운영 |

> 요약: 성능관리는 장애 발생 후 조치가 아니라 기준선 이탈을 조기에 잡는 운영 체계다.

## Ⅴ. 심화 비교 및 적용 판단

| 비교 축 | 사후 튜닝 | 성능 관리 방법론 | 선택 기준 |
|:---|:---|:---|:---|
| 구조 | 장애 후 원인 분석 | 상시 측정·임계치·개선 루프 | SLA가 있으면 방법론 필요 |
| 비용/성능 | 단기 비용 낮음 | 관측 도구·운영 절차 비용 발생 | 장애 비용과 비교 |
| 운영/위험 | 반복 장애 가능 | 기준선 갱신으로 재발률 관리 | 변경 빈도 높은 서비스 |

> 요약: 고객 영향이 큰 서비스는 사후 튜닝보다 SLO 기반 성능관리 체계가 적합하다.

| 리스크 | 원인 | 대응 방안 | 확인 지표 |
|:---|:---|:---|:---|
| 오탐 경보 | 임계치가 기준선과 무관 | 동적 기준선·burn rate 적용 | alert precision |
| 병목 오판 | 단일 지표만 해석 | trace와 자원 지표 상관 분석 | root cause hit rate |
| 개선 역효과 | 변경 후 검증 누락 | 동일 부하 재시험·canary 적용 | p95, error rate 변화 |

> 요약: 오탐, 오판, 역효과는 기준선·상관분석·변경 후 재측정으로 통제한다.

| 점검 항목 | 목표 기준 | 측정 방법 |
|:---|:---|:---|
| 응답시간 | p95 500ms 이하 | APM, synthetic test |
| 처리량 | 목표 TPS 대비 120% 여유 | 부하 테스트 |
| 오류율 | 1% 이하 | 로그·APM error rate |

> 요약: 성공 여부는 응답시간, 처리량 여유, 오류율을 같은 시간대 기준으로 비교해 판단한다.

## Ⅵ. 실무 적용 및 결론

**적용 방안 3개:**
1. 핵심 업무 API별 p95, p99, TPS, error rate SLI를 정하고 SLO와 알림 임계치를 설정함
2. APM trace, DB wait event, node metric을 correlation id로 연결해 병목 원인 분석 시간을 단축함
3. 배포 전후 동일 부하 조건으로 성능 회귀를 확인하고 기준선 변경 이력을 남김

**결론 (2줄):**
- 기술사 판단: SLA가 있는 서비스는 사후 튜닝보다 SLO·APM 기반 성능관리 체계를 우선 적용함
- 향후 방향: AIOps와 SLO burn rate를 결합해 장애 전 성능 저하를 자동 탐지하는 방향으로 발전함
