## 📖 【암기용】 핵심 요약

*   **한눈에**: 토마스 맥케이브(Thomas McCabe)가 제안한 지표로, 프로그램 소스 코드 내에 존재하는 **'독립적인 실행 경로(Path)의 개수'**를 수학적 그래프 이론으로 계산하여 코드의 복잡도를 측정하는 방법.
*   **깊이 이해**:
    *   **배경**: 1,000줄짜리 단순 계산 프로그램보다, 100줄이지만 `if`, `for`, `while` 문이 꼬리에 꼬리를 무는 프로그램이 디버깅하기도 어렵고 버그도 많음. 즉, 소프트웨어의 진짜 복잡도는 '길이(LOC)'가 아니라 '갈림길(분기문)의 개수'에서 나온다는 통찰.
    *   **작동 원리**: 코드를 노드(Node, 실행 문장)와 간선(Edge, 실행 흐름)으로 이루어진 제어 흐름 그래프(Control Flow Graph)로 그림. 
    *   **계산 공식**: 
        1.  기본 공식: **$V(G) = E - N + 2$** (E: 간선 수, N: 노드 수)
        2.  실무 꿀팁(빠른 공식): **$V(G) = P + 1$** (P: 조건 분기문(if, while, case 등)의 개수)
    *   **비유**: **미로 찾기 혹은 배관 공사**. 일직선으로 뻗은 파이프는 물(데이터)이 샐 곳이 없음. 하지만 파이프가 여러 갈래로 나뉘고(if) 다시 합쳐지는(for) T자형 밸브(조건문)가 10개 있다면, 물이 제대로 흐르는지 확인하기 위해 최소 11번(10+1)의 각기 다른 테스트 펌프질이 필요함.
    *   **임계치 (McCabe의 권고)**: **$V(G) \le 10$**. 10 이하가 아주 이상적이고, 20을 넘어가면 이해하기 어렵고 테스트가 힘들어지며, 50을 넘어가면 "유지보수 불가(스파게티 코드)"로 판정하여 즉각적인 리팩토링(함수 쪼개기) 대상이 됨.
*   **연결 개념**: 제어 흐름 그래프(CFG), 화이트박스 테스트(경로 테스트), 리팩토링, 정적 분석(SonarQube), 테스트 커버리지

## 📝 【답안용】 서술 골격

> **💡 핵심 인사이트**
> *   **본질**: 프로그램의 제어 흐름(Control Flow)을 방향성 그래프(Directed Graph)로 모델링하고, 그래프 내의 선형 독립적인(Linearly Independent) 경로의 최소 개수를 정량화한 위상 수학적(Topological) 지표.
> *   **가치**: 개발자에게는 "함수를 얼마나 작게 쪼개야 하는가(Refactoring)"의 기준선을 제시하고, 테스터에게는 베이시스 패스 테스팅(Basis Path Testing)을 위해 작성해야 할 **최소 테스트 케이스(TC)의 개수**를 수학적으로 보장해줌.
> *   **판단 포인트**: 단순히 공식을 외우는 것을 넘어, 현업에서 CI/CD 파이프라인의 SonarQube 정적 분석 규칙(Quality Profile)으로 V(G) 임계치를 설정하고 자동화된 코드 통제에 활용된다는 점을 강조해야 함.

### Ⅰ. 코드 품질의 정량적 척도, 순환 복잡도(Cyclomatic Complexity) 개요
*   **정의**: 토마스 맥케이브(1976)가 고안한 소프트웨어 메트릭으로, 제어 흐름 그래프(CFG) 기반에서 도출되는 논리적이고 독립적인 실행 경로의 총개수.
*   **목적**: 모듈의 응집도/결합도 외에 내부 로직의 난이도를 정량화하여 잠재적 결함(Defect) 발생 가능성을 예측하고 화이트박스 테스트의 규모를 산정함.

### Ⅱ. 제어 흐름 그래프(CFG)와 복잡도 산출 공식
*   **제어 흐름 그래프 (Control Flow Graph)**: 프로그램의 실행 순서를 노드(명령어 블록)와 간선(제어의 흐름 방향)으로 도식화한 모델.
*   **순환 복잡도 산출 공식 (3가지 방법)**
    1.  **그래프 이론 기본 공식**: $V(G) = E - N + 2P$
        *   $E$ (Edge): 간선의 수
        *   $N$ (Node): 노드의 수
        *   $P$ (Predicate): 연결된 컴포넌트의 수 (일반적인 단일 프로그램/함수는 $P=1$이므로 $E - N + 2$ 사용)
    2.  **닫힌 영역(Region) 공식**: $V(G) = \text{그래프 내의 닫힌 영역(면)의 수} + 1$
    3.  **의사결정 노드(Predicate Node) 공식 (가장 실용적)**: $V(G) = \text{조건문(if, while, for, case, \&\&, ||)의 개수} + 1$

### Ⅲ. McCabe의 복잡도 지수 평가 기준 (가이드라인)
| $V(G)$ 수치 구간 | 코드 상태 진단 | 대응 조치 (Action Item) |
| :--- | :--- | :--- |
| **1 ~ 10** | 매우 양호하고 구조적인 코드 | 현 상태 유지 (Best Practice) |
| **11 ~ 20** | 다소 복잡함 (위험 내포) | 코드 리뷰 강화, 분기가 많은 Switch/If문 점검 |
| **21 ~ 50** | 매우 복잡함 (테스트 난이도 급증) | **Extract Method** 리팩토링 등을 통해 함수 분할 |
| **50 이상** | 유지보수 불가 (비구조적 스파게티) | 전면 재설계 (Redesign) 및 아키텍처 재검토 |

### Ⅳ. 순환 복잡도의 소프트웨어 공학적 활용 가치
1.  **테스트 케이스(TC) 최소 요구량 도출**: $V(G)$ 값은 모든 분기 구문을 최소 한 번씩 타보기 위해(분기 커버리지 100%) 필요한 최소한의 테스트 케이스 개수와 정확히 일치함.
2.  **리팩토링(Refactoring)의 지시자**: 모듈의 크기가 작더라도 $V(G)$가 15를 넘어가면 해당 모듈은 단일 책임 원칙(SRP)을 위배했을 확률이 높으므로 코드 스멜(Code Smell)의 강력한 식별 지표가 됨.
3.  **기능점수(FP)의 한계 보완**: 데이터 흐름 중심인 FP(기능점수) 산정 방식이 놓치기 쉬운 '알고리즘적 처리 난이도'를 정량적으로 보완하는 대가 산정 참조 지표로 활용.

### Ⅴ. 현대 개발 환경(DevOps)에서의 적용 한계 및 전략
*   **한계**: 순환 복잡도는 '데이터 구조의 복잡성'이나 다형성(Polymorphism)을 활용한 '객체지향 설계의 복잡성(예: CK Metrics)'을 온전히 반영하지 못함.
*   **대응 전략 (정적 분석 자동화)**:
    *   개발자가 매번 계산할 수 없으므로, SonarQube, PMD 등의 정적 분석 툴을 CI 파이프라인에 통합.
    *   Quality Gate 규칙에 `Cyclomatic Complexity > 15` 조항을 삽입하여, 복잡도가 초과된 코드는 Git PR(Pull Request) 시 자동으로 Merge를 차단하는 강제적 품질 통제 환경 구축.
