## 미리 알고가기

- Split Brain: 이중화 노드가 동시에 자신을 주 노드로 판단해 중복 쓰기가 발생하는 상태임
- Heartbeat: 노드 간 생존 여부를 확인하려고 주기적으로 주고받는 신호임
- Quorum: 클러스터가 정상 권한을 유지하려고 필요한 최소 과반수 노드 수임
- Fencing: 고립된 노드가 더 이상 쓰기나 서비스 승격을 하지 못하게 강제로 차단하는 절차임

## Ⅰ. 개요

- **정의/개념**: Split Brain은 네트워크 분리나 상태 감시 오류 때문에 여러 노드가 동시에 Active 역할을 수행하는 장애이며, 쿼럼은 이런 상황에서 과반수를 확보한 쪽만 서비스 권한을 유지하도록 하는 합의 기준임
- **배경/필요성**: 고가용성 클러스터는 장애 전환 자체보다 잘못된 이중 승격이 더 큰 데이터 오염을 만들 수 있으므로, 누가 살아 있는지보다 누가 권한을 가져야 하는지 판단하는 기준이 필요함

## Ⅱ. 특징

- Split Brain은 서버가 죽지 않아도 네트워크만 끊기면 발생할 수 있어 단순 생존 확인만으로 막기 어려움
- 쿼럼은 가용성을 약간 희생하더라도 데이터 정합성을 지키는 기준으로 동작함
- 2노드만으로는 동률을 깨기 어려워 Witness나 Arbiter 같은 제3의 투표 지점이 중요함
- 쿼럼만으로 부족한 경우가 있어 Fencing을 함께 둬야 실제 중복 쓰기를 막을 수 있음

## Ⅲ. 종류 및 비교

| 판단 기준 | Split Brain | Quorum |
|:---|:---|:---|
| 의미 | 여러 노드가 동시에 Active가 되어 데이터 정합성이 깨지는 장애 상태임 | 과반수 노드만 서비스 권한을 유지하게 하는 합의 기준임 |
| 발생 조건 | Heartbeat 단절, 잘못된 승격 정책, 2노드 동률 상황에서 자주 나타남 | 홀수 노드 구성이나 Witness 노드가 있을 때 안정적으로 동작함 |
| 위험 | 중복 쓰기, 역할 충돌, 복구 불가능한 데이터 오염으로 이어질 수 있음 | 과반수 미달 노드는 스스로 중지하므로 일시적 가용성 손실이 생길 수 있음 |
| 대응 방향 | 고립 노드 차단과 재동기화가 필요함 | 과반수 계산, Witness, Fencing 정책을 명확히 설계함 |

## Ⅳ. 구성요소 및 구조

| 구성요소 | 설명 |
|:---|:---|
| Active와 Standby 노드 | 주 서비스와 대기 서비스를 담당하며 장애 시 역할 전환 대상이 됨 |
| Heartbeat 경로 | 노드 상태를 감시하지만 네트워크 분리 시 오판 원인이 되므로 다중 경로 구성이 중요함 |
| Witness 또는 Arbiter | 데이터는 저장하지 않더라도 투표를 도와 동률 상황을 해소하는 보조 노드임 |
| Fencing 장치 | 전원 차단, 스토리지 잠금, 쓰기 금지로 고립된 노드를 강제로 배제함 |

```text
+-------------+     +-------------+     +-------------+     +-------------+
| 노드 상태 감시   | --> | 과반수 판단    | --> | 고립 노드 차단  | --> | 단일 Active 유지 |
+-------------+     +-------------+     +-------------+     +-------------+
```

## Ⅴ. 원리 및 절차 흐름도

```text
+-------------+     +-------------+     +-------------+     +-------------+
| Heartbeat 이상 감지 | --> | Quorum 계산  | --> | 승격 또는 중지 결정 | --> | 재동기화 검증   |
+-------------+     +-------------+     +-------------+     +-------------+
```

1. **Heartbeat 이상 감지**: 노드 간 통신 단절이나 상태 이상을 탐지함
2. **Quorum 계산**: 현재 통신 가능한 노드 수가 과반수인지 판단함
3. **승격 또는 중지 결정**: 과반수 쪽만 Active를 유지하고 나머지는 쓰기나 서비스를 중지함
4. **재동기화 검증**: 네트워크 복구 후 데이터와 역할 상태를 다시 맞춤

## Ⅵ. 실무 적용 및 유의점

1. DB와 스토리지 클러스터는 2노드만으로 운영하면 Split Brain 위험이 커지므로 감시 노드와 강제 격리를 함께 두고 쿼럼 상실 건수와 이중 활성화 발생 건수와 절체 성공률로 확인함
2. 분산 저장소와 제어 평면은 과반수 규칙이 강하게 작동해야 하므로 하트비트 경로와 승격 임계값을 보수적으로 조정하고 리더 선출 시간과 강제 격리 건수로 확인함

## Ⅶ. 결론

Split Brain 대응의 핵심은 빠른 승격 자체보다 과반수와 Fencing으로 단 하나의 쓰기 주체만 남기도록 통제하는 데 있음.
