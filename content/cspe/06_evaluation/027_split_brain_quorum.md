# 📖 【암기용】 개념 완전 이해

## 한눈에
- **개요**: Split-brain은 **클러스터 장애 유형**으로, 네트워크 분단(partition)으로 클러스터가 둘로 갈라져 각 파티션이 자신을 Primary로 판단해 동시에 쓰기를 수행하는 상태임. 쿼럼(Quorum)은 과반수 투표로 정상 파티션을 결정해 이를 예방하는 메커니즘임.
- **왜 필요한가**: HA 클러스터(023)에서 heartbeat 통신이 끊기면 "상대가 죽었는지, 네트워크만 끊겼는지" 구분이 불가. 양쪽 모두 Active로 승격하면 데이터 정합성이 깨짐.
- **핵심 직관**: 이사회 두 그룹이 통신 끊긴 채 각자 "우리가 정족수"라며 서로 다른 결정을 내리는 상황 → "과반수를 확보한 쪽만 유효"라는 규칙(쿼럼)이 필요.

## 핵심 용어 정리 (내부에 등장하는 것들)

023이 HA 구조를, 028이 페일오버를 다뤘으므로 여기서는 split-brain 고유의 분단·투표 용어에 집중함.

| 용어/표기 | 의미 | 비유·예 |
|:---|:---|:---|
| Split-brain (상위 키워드) | 네트워크 분단으로 양쪽 파티션이 모두 Primary를 주장하는 상태 | 이사회 양 그룹이 각자 결의 |
| 쿼럼 (Quorum) | 과반수(N/2+1)를 확보한 파티션만 서비스를 계속하는 투표 규칙 | 이사회 정족수 |
| 네트워크 파티션 | 클러스터 노드 간 통신이 물리적/논리적으로 단절된 상태 | 전화선 끊김 |
| Heartbeat | 노드 간 생존 확인 주기적 신호 | "나 살아있어" 핑 |
| Witness/Arbiter | 짝수 노드 클러스터에서 쿼럼 판정용 추가 투표자 | 캐스팅보트 역할 |
| STONITH/Fencing | 쿼럼 미달 노드를 강제 차단(전원 차단 등)해 이중 쓰기 방지 | 불량 선수 퇴장 |
| Raft/Paxos | 분산 합의 알고리즘, 리더 선출과 로그 복제를 쿼럼 기반으로 수행 | 위원회 투표 프로토콜 |

## 깊이 이해
- **배경·문제의식**: (023 참조) Active-Active 또는 Active-Standby 클러스터에서 노드 간 heartbeat가 끊기면, 각 노드는 "상대가 죽었다"와 "네트워크만 끊겼다"를 구분할 수 없음. 이 모호성 때문에 양쪽이 모두 Active로 승격하면 같은 데이터에 서로 다른 쓰기가 발생(split-brain) → 데이터 정합성 파괴.
- **작동 원리 — 쿼럼**:
  - 클러스터 전체 노드 수의 과반수(N/2+1)를 확보한 파티션만 서비스를 계속할 수 있게 하는 투표 메커니즘.
  - 3노드 클러스터 → 분단 2:1 → 2노드 쪽이 쿼럼(≥2) 만족해 Active 유지, 1노드 쪽은 서비스 중단.
  - 5노드 클러스터 → 분단 3:2 → 3노드 쪽이 쿼럼(≥3) 만족.
- **짝수 노드 문제**: 2노드·4노드 클러스터는 정확히 절반씩 분단 가능 → 쿼럼 판정 불가 → Witness/Arbiter 노드를 추가해 홀수로 만들어야 함.
- **STONITH/Fencing**: 쿼럼 미달 파티션의 노드를 강제 전원 차단(STONITH: Shoot The Other Node In The Head)하거나 네트워크 격리(fencing)해 이중 쓰기를 물리적으로 차단함.
- **Raft/Paxos**: 분산 합의 알고리즘으로, 리더 선출과 로그 복제를 쿼럼 기반으로 수행함. etcd(Raft)·ZooKeeper(ZAB, Paxos 변형)가 대표 구현체.
- **비유**: 국회 의결 정족수. 국회의원이 두 건물로 나뉘어 통신이 끊기면, 과반수가 있는 건물만 법안 의결이 유효하고, 소수 쪽은 회의를 중단해야 함.
- **구체 예시**: PostgreSQL + Patroni 3노드 클러스터. 네트워크 분단으로 2:1 → 2노드 쪽이 etcd 쿼럼 유지, 리더 선출 유효 → 서비스 지속. 1노드 쪽은 read-only 또는 자동 shutdown.
- **흔한 오해·주의점**: ① 쿼럼은 split-brain을 "감지"하는 것이 아니라 "예방"하는 것 — 과반수 미달 쪽이 애초에 Active로 승격되지 않음. ② 2노드 클러스터는 쿼럼이 성립하지 않음 — 반드시 Witness를 추가하거나 3노드 이상으로 구성. ③ 네트워크만 복구되면 분단이 해소되지만, 분단 중 양쪽에서 쓰기가 발생했다면 데이터 충돌 해소(conflict resolution)가 별도로 필요함.

## 연결 개념
- **고가용성 설계 (023)**: split-brain이 발생하는 이중화 구조. 023이 구조를, 027이 분단 대응을 담당.
- **자동 페일오버 (028)**: 쿼럼 판정 후 리더 전환을 수행하는 메커니즘.
- **이중화 구성 (030)**: 노드 수(홀수/짝수)가 쿼럼 성립에 직결.

# 📝 【답안용】 시험 답안 템플릿

## 핵심 인사이트 (3줄 요약)

> 1. **본질**: Split-brain은 네트워크 분단 시 양쪽 파티션이 모두 Primary로 동작해 데이터 정합성이 깨지는 장애이며, 쿼럼(과반수 투표)으로 예방함.
> 2. **가치**: 쿼럼은 과반수 미달 파티션의 서비스를 차단해 이중 쓰기를 원천 방지함.
> 3. **판단 포인트**: 홀수 노드 구성(또는 Witness 추가) + STONITH/Fencing + 분단 후 데이터 충돌 해소 절차가 필수임.

## 출제 의도 및 답안 포인트

| 출제 의도 | 반드시 짚을 핵심 | 감점 회피 포인트 |
|:---|:---|:---|
| Split-brain 원인 이해 | 네트워크 분단 + heartbeat 단절 + 이중 승격 | "노드 장애"와 "네트워크 분단" 혼동 |
| 쿼럼 메커니즘 이해 | 과반수(N/2+1) 투표, 홀수 노드 필요 | 쿼럼을 장애 감지로 잘못 서술 |
| 펜싱·합의 이해 | STONITH/Fencing, Raft/Paxos | 쿼럼만 언급하고 강제 차단 메커니즘 누락 |

> 요약: split-brain 원인 + 쿼럼 투표(과반수·홀수) + STONITH/Fencing + 합의 알고리즘을 보여야 함.

## Ⅰ. 개요 및 필요성

- 개요: split-brain은 네트워크 분단으로 양쪽 파티션이 모두 Primary를 주장하는 장애이며 쿼럼(과반수 투표)으로 예방함
- 배경: HA 클러스터(023)에서 heartbeat 단절 시 "노드 장애 vs 네트워크 분단" 구분 불가 → 이중 승격 위험
- 필요성: 이중 쓰기에 의한 데이터 정합성 파괴를 원천 방지하려면 쿼럼 기반 파티션 판정 + 강제 차단(Fencing) 필수

---

## Ⅱ. 구조 및 구성요소

```text
클러스터 노드(A, B, C) -> Heartbeat 통신 -> 네트워크 분단 발생
  -> 각 파티션 노드 수 집계 -> 쿼럼(N/2+1) 판정
  -> 과반수 파티션: 서비스 지속 / 소수 파티션: Fencing·서비스 중단
```

| 구성요소 | 역할 | 특이사항 |
|:---|:---|:---|
| Heartbeat | 노드 간 생존 확인 주기적 신호 | 끊기면 분단/장애 모호성 발생 |
| 쿼럼 투표 | 과반수(N/2+1) 확보 파티션 판정 | 홀수 노드 필수, 짝수 시 Witness 추가 |
| STONITH/Fencing | 소수 파티션 노드 강제 차단 | 전원 차단·네트워크 격리 |
| Witness/Arbiter | 짝수 노드 시 투표권 추가 | 데이터 미보유, 투표만 참여 |
| 합의 알고리즘 | Raft/Paxos 기반 리더 선출·로그 복제 | etcd, ZooKeeper 등 |

> 요약: Heartbeat 단절 시 쿼럼 투표로 정상 파티션을 결정하고, 소수 쪽은 Fencing으로 강제 차단하는 구조임.

---

## Ⅲ. 동작원리 및 흐름도

```text
정상 Heartbeat -> 네트워크 분단 발생 -> Heartbeat 타임아웃
  -> 각 파티션 노드 수 집계 -> 쿼럼(N/2+1) 판정
  -> 과반수: Active 유지, 리더 재선출
  -> 소수: STONITH/Fencing, 서비스 중단
```

1. 정상 상태에서 클러스터 노드들이 Heartbeat로 상호 생존을 확인하고 데이터를 동기화함
2. 네트워크 분단이 발생하면 Heartbeat 타임아웃(예: 5초 × 3회)으로 분단을 감지함
3. 각 파티션이 자신 쪽 노드 수를 집계해 쿼럼(N/2+1) 충족 여부를 판정함 — 3노드 분단 2:1이면 2노드 쪽만 쿼럼 만족
4. 과반수 파티션은 Active를 유지하고 필요 시 리더를 재선출, 소수 파티션은 STONITH/Fencing으로 강제 차단되어 이중 쓰기를 방지함

> 요약: Heartbeat 타임아웃 → 파티션 노드 수 집계 → 쿼럼 판정 → 과반수 Active/소수 Fencing 순으로 처리함.

---

## Ⅳ. 특징

- 예방 메커니즘: 쿼럼은 split-brain을 "감지"가 아니라 "예방" — 소수 파티션이 애초에 Active로 승격되지 않음
- 홀수 노드 필수: 짝수 노드(2, 4)는 균등 분단 시 쿼럼 판정 불가 → Witness/Arbiter 추가 필요
- Fencing 강제성: 소수 파티션 노드를 논리적(서비스 중단)·물리적(전원 차단)으로 격리해 이중 쓰기를 원천 차단
- 합의 알고리즘 연계: Raft(etcd)·Paxos(ZooKeeper)가 쿼럼 기반 리더 선출·로그 복제를 자동 수행
- 분단 해소 후 충돌: 분단 중 양쪽에서 쓰기가 발생했다면 merge 시 데이터 충돌 해소(conflict resolution) 별도 필요

## Ⅴ. 심화 비교 및 적용 판단

| 구분 | 쿼럼 미적용 클러스터 | 쿼럼 적용 클러스터 | 선택 기준 |
|:---|:---|:---|:---|
| 분단 대응 | 양쪽 모두 Active 승격(split-brain 발생) | 과반수만 Active, 소수 차단 | 데이터 정합성 요구 수준 |
| 노드 구성 | 2노드 구성 가능 | 홀수 노드 또는 Witness 추가 필수 | 인프라 비용·복잡도 |
| 데이터 보호 | 이중 쓰기로 정합성 파괴 위험 | 단일 Active로 정합성 보장 | 금융·원장 등 무결성 필수 여부 |
| 가용성 영향 | 분단 시 양쪽 서비스(위험) | 소수 쪽 서비스 중단(안전) | 가용성 vs 정합성 트레이드오프 |

> 요약: 데이터 정합성이 중요하면 쿼럼 적용(소수 차단), 가용성 극대화가 필요하면 conflict resolution 기반 AA 구조를 검토함.

**리스크·대응:**
- 짝수 노드 쿼럼 미성립: 2·4노드에서 균등 분단 → Witness/Arbiter 노드 추가로 홀수 투표 확보 (지표: 클러스터 노드 수 홀수 여부)
- Fencing 실패: STONITH 미구성으로 소수 노드가 계속 쓰기 수행 → STONITH 에이전트 구성 필수 + 테스트 (지표: Fencing 성공률)
- 분단 후 데이터 충돌: 분단 중 양쪽 쓰기 발생 후 merge 시 충돌 → 충돌 해소 정책(LWW, 수동 merge) 사전 정의 (지표: 충돌 해소 소요 시간)

**점검 지표:**
- 성능: 쿼럼 판정 소요 시간(Heartbeat 타임아웃 × 횟수) — 클러스터 로그
- 운영: Fencing 성공률 100% + 분기별 분단 시뮬레이션 테스트 — 테스트 로그

## Ⅵ. 실무 적용 및 결론

**적용 방안:**
1. 클러스터를 3노드 이상 홀수로 구성하고, 2노드 환경에서는 Witness/Arbiter를 별도 AZ에 배치해 쿼럼을 확보함
2. STONITH/Fencing 에이전트를 구성해 소수 파티션 노드를 자동 차단하고, 정기 분단 시뮬레이션으로 동작을 검증함
3. 분단 해소 후 데이터 충돌 해소 정책(LWW·수동 merge·알림)을 사전 정의하고 런북에 명시함

**결론:**
- 기술사 판단: split-brain 방지는 쿼럼(홀수 노드) + STONITH/Fencing + 충돌 해소 정책의 3요소가 갖춰져야 완성됨
- 향후 방향: Raft/Paxos 기반 자동 합의와 멀티 리전 쿼럼으로 글로벌 분산 클러스터의 split-brain 방지가 표준화되는 추세임
