# 📖 【암기용】 개념 완전 이해

> 목적: 정적 분석 결과 보고서를 처음 봐도 어떤 결과를 먼저 조치해야 하는지 판단하게 만든다. 시험 답안 양식이 아니라, 이해를 위한 친절한 설명이다.

## 한눈에
- **개요**: 프로그램을 실행하지 않고 소스코드·바이트코드 구조를 분석해 결함·취약점·코드스멜을 탐지하고 그 결과를 심각도·오탐 여부로 판단하는 활동
- **왜 필요한가**: 정적 분석 도구는 대량의 경고를 쏟아내는데, 전부 실결함은 아니다. 결과를 해석하는 기준이 없으면 오탐 처리에 시간을 낭비하거나 심각한 결함을 놓친다.
- **핵심 직관**: 건강검진 결과지에서 정상 범위·주의·재검사 항목을 구분해 우선순위대로 병원을 찾아가는 것과 같다.

## 깊이 이해
- **배경·문제의식**: 대규모 코드베이스는 수동 리뷰만으로 모든 결함을 찾기 어렵고, 정적 분석 도구는 실행 없이 화이트박스 방식으로 코드 구조를 훑어 잠재 결함을 찾는다.
- **작동 원리**: 규칙셋(코딩표준, 보안취약점 패턴, 코드스멜 패턴)을 정의하고 소스를 스캔해 위반 항목을 결함 목록으로 산출한다.
- **작동 원리**: 각 결함을 심각도(Critical/Major/Minor/Info)와 유형(보안취약점, 버그, 코드스멜)으로 분류하고 CWE(Common Weakness Enumeration) 같은 표준 취약점 분류체계에 매핑한다.
- **작동 원리**: 결함 목록에서 오탐(False Positive, 실제로는 문제 없는 경고)과 실결함(True Positive)을 사람이 검토(triage)해 구분한다.
- **작동 원리**: 실결함은 심각도·CVSS 점수 기준으로 우선순위를 정해 수정하고, 수정 후 재스캔(회귀 스캔)으로 해결 여부를 검증한다.
- **비유**: 스팸 필터가 걸러낸 메일함에서 진짜 스팸과 오분류된 정상 메일을 사람이 다시 확인하는 과정과 유사하다.
- **구체 예시**: SonarQube가 SQL 조립 코드를 SQL Injection(CWE-89) 위험으로 분류하면, 실제로 파라미터 바인딩을 이미 사용 중인 코드인지 확인해 오탐이면 종료 처리하고 실결함이면 즉시 수정한다.
- **흔한 오해·주의점**: 정적 분석 결과가 0건이라고 해서 결함이 없다는 뜻은 아니며, 런타임에서만 드러나는 동시성 문제나 실제 메모리 사용량은 놓칠 수 있다.
- **흔한 오해·주의점**: 결함 밀도(결함수/KLOC)는 코드량 대비 결함 비율이지 절대적 품질 등급이 아니므로 프로젝트 특성(도메인 위험도)을 함께 고려해야 한다.

## 연결 개념
- 결함 밀도·결함 제거율 — 정적 분석 결과를 정량화하는 지표
- 순환 복잡도 — 정적 분석 도구가 함께 산출하는 구조적 복잡도 지표
- DAST·동적 분석 — 정적 분석이 놓치는 런타임 결함을 보완하는 대응 기법

# 📝 【답안용】 시험 답안 템플릿

> 목적: 시험장에서 25분에 그대로 쓰는 답안 양식. 작성방식(추상표현 금지·수치·도식·문제유형 전환)을 엄격히 지킨다.
> 핵심: 정적 분석 답안은 심각도·CWE 분류, 오탐 triage 절차, 정적·동적 분석 역할 분리를 함께 제시한다.

## 핵심 인사이트 (3줄 요약)

> 1. **본질**: 정적 분석 결과 해석은 도구가 산출한 경고를 심각도·오탐 여부로 분류해 실결함 우선순위를 정하는 활동이다.
> 2. **가치**: 대량 경고 중 실제 위험을 선별해 수정 자원을 결함 심각도 순으로 배분한다.
> 3. **판단 포인트**: 오탐 triage 절차, CWE 매핑, 정적·동적 분석 역할 분담 기준을 제시해야 한다.

## 출제 의도 및 답안 포인트

| 출제 의도 | 반드시 짚을 핵심 | 감점 회피 포인트 |
|:---|:---|:---|
| 결과 해석 절차 이해 확인 | 심각도 분류, 오탐 triage, 재스캔 검증 | 도구 실행만 서술하고 해석 절차 누락 |
| 정량 지표 활용 확인 | 결함 밀도, CVSS, CWE 매핑 | 수치·표준 없이 "결함을 고친다"만 서술 |
| 정적·동적 분석 구분 확인 | 정적은 실행 없이 구조 분석, 동적은 런타임 결함 탐지 | 정적 분석만으로 모든 결함을 찾는다고 서술 |

> 요약: 이 문제는 심각도 기반 우선순위화, 오탐 triage 절차, 동적 분석과의 역할 분리를 함께 보여야 한다.

## Ⅰ. 개요 및 필요성

- 개요: 정적 분석 도구가 산출한 결함 목록을 심각도·오탐 여부로 판단하는 활동
- 배경: 대규모 코드베이스는 수동 리뷰만으로 전수 결함 탐지가 불가능함
- 필요성: 대량 경고 중 실결함을 선별하고 우선순위대로 수정하려면 해석 절차와 기준이 필요함

---

## Ⅱ. 구조 및 구성요소

```text
소스코드 -> 규칙셋 적용 스캔 -> 결함 목록 생성
  -> 심각도/유형 분류 -> 오탐 triage
  -> 실결함 우선순위화 -> 수정 -> 회귀 스캔
```

| 구성요소 | 역할 | 산출물 |
|:---|:---|:---|
| 규칙셋 | 코딩표준·보안취약점·코드스멜 패턴 정의 | 스캔 기준 |
| 결함 목록 | 규칙 위반 항목 전수 산출 | 심각도별 결함 리스트 |
| CWE 매핑 | 보안취약점을 표준 분류체계에 연결 | 취약점 유형 코드 |
| 오탐 triage | 실결함과 오탐을 사람이 구분 | True Positive 목록 |

> 요약: 정적 분석은 규칙셋 스캔으로 결함 목록을 만들고 사람의 triage를 거쳐 실결함만 선별한다.

---

## Ⅲ. 동작원리 및 흐름도

```text
스캔 실행 -> 결함 분류(심각도/유형) -> CWE 매핑
  -> 오탐 triage -> CVSS·심각도 기준 우선순위화
  -> 수정 -> 회귀 스캔으로 해결 검증
```

| 단계 | 처리 내용 | 검증 기준 |
|:---:|:---|:---|
| 1 | 규칙셋 기반 전체 코드 스캔 | 규칙셋 최신화 여부 |
| 2 | 심각도·유형·CWE 분류 | 분류 일관성 |
| 3 | 오탐 triage 및 실결함 우선순위화 | 오탐률, CVSS 점수 |
| 4 | 수정 후 회귀 스캔으로 재검증 | 동일 결함 재발 여부 |

> 요약: 정적 분석 결과 해석은 분류, triage, 우선순위화, 재검증 순서로 진행된다.

---

## Ⅳ. 특징

| 구분 | 내용 | 판단 포인트 |
|:---|:---|:---|
| 장점 | 실행 없이 전체 코드 경로 점검, 조기 결함 발견 | 빌드·커밋 단계에서 자동 게이트 적용 가능 |
| 한계 | 런타임 전용 결함(동시성, 실제 메모리 사용)은 미탐지 | 동적 분석·DAST와 병행 필요 |
| 비교 포인트 | 정적은 구조 분석, 동적은 실행 기반 분석 | 결함 유형별 도구 역할 분담 필요 |

> 요약: 정적 분석은 조기·전수 점검에 강점이 있으나 런타임 결함은 동적 분석으로 보완해야 한다.

## Ⅴ. 심화 비교 및 적용 판단

| 구분 | 정적 분석 | 동적 분석(DAST) | 선택 기준 |
|:---|:---|:---|:---|
| 실행 여부 | 코드 실행 없이 구조 분석 | 실제 실행 환경에서 결함 탐지 | 조기 발견은 정적, 런타임 검증은 동적 |
| 탐지 범위 | 코딩표준·취약점 패턴·복잡도 | 인증우회, 실제 입력값 처리 결함 | 보안 종합 점검은 두 방식 병행 |
| 적용 시점 | 커밋·빌드 단계 | 스테이징·운영 유사 환경 | CI에는 정적, 배포 전에는 동적 배치 |

> 요약: 조기 결함 차단은 정적 분석, 런타임 검증은 동적 분석으로 역할을 분리한다.

| 리스크 | 원인 | 대응 방안 | 확인 지표 |
|:---|:---|:---|:---|
| 오탐 과다 | 규칙셋이 프로젝트 특성에 맞지 않음 | 규칙셋 커스터마이징, 예외 처리 등록 | 오탐률(False Positive Rate) |
| 실결함 방치 | Critical 결함 triage 지연 | SLA 기반 수정 기한 설정 | Critical 결함 평균 조치 시간 |
| 지표 오독 | 결함 밀도만으로 품질 등급 단정 | 도메인 위험도·순환복잡도와 교차 검증 | 결함 밀도(건/KLOC) 추세 |

> 요약: 오탐률 관리, Critical 결함 SLA, 교차 검증 지표로 정적 분석 결과 해석 리스크를 통제한다.

| 점검 항목 | 목표 기준 | 측정 방법 |
|:---|:---|:---|
| 오탐 관리 | 오탐률 임계치 이내 유지 | 스캔 이력 대비 triage 결과 비교 |
| 결함 해소율 | Critical/Major 결함 제거율 목표 달성 | 결함 제거율(해결 건수/발견 건수) |
| 재발 방지 | 회귀 스캔에서 동일 결함 재발 없음 | 회귀 스캔 결과 비교 |

> 요약: 도입 후 성공 여부는 오탐률, 결함 제거율, 회귀 스캔 재발 여부로 판단한다.

## Ⅵ. 실무 적용 및 결론

**적용 방안 3개 (필수 — 단계별 또는 항목별):**
1. CI 파이프라인에 정적 분석 게이트를 넣고 Critical 결함 발견 시 빌드를 차단함
2. 오탐 triage 결과를 규칙셋 예외 목록으로 축적해 반복 오탐 검토 시간을 줄임
3. 정적 분석으로 잡히지 않는 런타임 결함은 DAST·부하테스트로 보완하고 결과를 통합 대시보드로 관리함

**결론 (2줄):**
- 기술사 판단: 조기·전수 결함 차단은 정적 분석, 런타임 검증은 동적 분석으로 역할을 분리해 적용함
- 향후 방향: AI 기반 오탐 필터링과 CWE 자동 매핑으로 triage 시간을 단축하고 결함 해소율을 지속 관리해야 함
