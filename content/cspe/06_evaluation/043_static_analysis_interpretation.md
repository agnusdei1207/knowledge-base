## 📖 【암기용】 핵심 요약

*   **한눈에**: 코드를 실행하지 않고 소스코드 자체의 패턴과 구조를 스캔(SonarQube 등)하여 쏟아져 나온 수많은 **경고(Warnings)와 결함(Defects)들을 어떻게 읽고, 거르고, 우선순위를 매겨 조치할 것인지**에 대한 실무적 판단 가이드.
*   **깊이 이해**:
    *   **배경**: 정적 분석 도구를 처음 도입하면 수백~수만 개의 에러 리포트가 쏟아짐. 개발자들은 멘붕에 빠지고 "이거 다 고쳐야 해요?"라고 묻게 됨. 이 리포트에는 진짜 치명적인 보안 취약점도 있지만, 그냥 띄어쓰기 안 맞췄다고 낸 경고(오탐)도 섞여 있음. 이를 해석하는 능력이 없으면 도구는 쓸모가 없어짐.
    *   **결과(이슈)의 3대 유형**:
        1.  **Bug (버그)**: 당장 실행하다가 런타임 에러(Null Pointer 등)를 낼 수 있는 확실한 결함. $\to$ **즉시 수정**
        2.  **Vulnerability (보안 취약점)**: 해킹당할 수 있는 뒷문(SQL Injection 등). $\to$ **즉시 수정**
        3.  **Code Smell (코드 스멜)**: 당장 에러는 안 나지만, 구조가 더러워서 나중에 유지보수하기 힘든 코드(중복 코드, 너무 긴 함수). $\to$ **여유 될 때 리팩토링**
    *   **오탐 (False Positive) 처리**: 도구가 "여기 SQL 인젝션 위험해요!"라고 했는데, 사람이 보니 내부망에서만 도는 배치 코드라 안전함. 이럴 땐 코드를 고치는 게 아니라, 분석 도구 설정에서 예외(Ignore/Resolve as False Positive) 처리를 해줘야 다음 스캔 때 똑같은 잔소리를 안 함. (이 과정을 **Triage**라고 부름).
    *   **비유**: **초음파 건강검진 결과지 읽기**. 
        결과지에 수십 개의 이상 소견이 나옴. 의사(리드 개발자)가 보고 "용종(버그)은 당장 뗍시다", "지방간(코드 스멜)은 운동하면서 천천히 빼봅시다", "이 낭종은 사진에만 이렇게 나왔지 정상(오탐)입니다"라고 선별해 주는 과정.
    *   **흔한 오해/주의점**: "정적 분석에서 에러가 0개면 무결점 시스템인가요?" $\rightarrow$ **오답**. 정적 분석은 문법/패턴 기반 검사일 뿐, 비즈니스 로직의 결함이나 성능 병목 현상(메모리 누수, DB 락) 같은 동적인 결함은 절대 잡아낼 수 없음. 동적 분석(DAST)과 반드시 병행해야 함.
*   **연결 개념**: SonarQube, 코드 스멜, 기술 부채(Technical Debt), Triage, False Positive(오탐), CWE(보안 취약점 표준), 순환 복잡도

## 📝 【답안용】 서술 골격

> **💡 핵심 인사이트**
> *   **본질**: 자동화된 정적 분석(SAST) 도구가 쏟아내는 대량의 결함(Defect) 리포트를 비즈니스 리스크 기반으로 필터링하고(Triage), 오탐(False Positive)을 제거하여 실행 가능한 리팩토링 계획으로 전환하는 프로세스.
> *   **가치**: 개발자의 피로도를 높이는 '경고 폭탄(Alert Fatigue)'을 방지하고, 한정된 리소스를 가장 치명적인 버그 및 보안 취약점에 먼저 투입할 수 있도록 함.
> *   **판단 포인트**: 정적 분석 결과만으로는 시스템 품질의 50%만 알 수 있음. 정적 분석의 맹점(비즈니스 로직 오류, 런타임 성능 저하 미탐지)을 동적 분석 도구 및 코드 리뷰어의 휴먼 에러 필터링으로 보완해야 함을 서술해야 함.

### Ⅰ. 정적 분석의 한계와 능동적 결과 해석의 필요성
*   **정적 분석(Static Analysis)의 정의**: 소스코드를 실행하지 않고(Non-runtime) 코드의 문법, 구조, 패턴을 검사하여 잠재적 오류를 도출하는 화이트박스 검증 기법.
*   **해석의 필요성**: 패턴 매칭 기반으로 동작하므로 오탐률(False Positive)이 높고, 리포트된 이슈가 비즈니스에 미치는 실제 파급력을 도구 스스로 판별할 수 없으므로 아키텍트/리드 개발자의 Triage(중증도 분류) 과정이 필수적임.

### Ⅱ. 정적 분석 결과물의 핵심 분류 지표 (SonarQube 기준)
정적 분석 도구의 출력물은 크게 3가지 축(Axis)으로 해석됨.

1.  **이슈의 성격 (Issue Types)**:
    *   **Bugs (신뢰성)**: Null Pointer Dereference, 메모리 누수 가능성 등 런타임 오류 유발 코드.
    *   **Vulnerabilities (보안성)**: 하드코딩된 비밀번호, SQL Injection 등 CWE 기준 보안 취약점.
    *   **Code Smells (유지보수성)**: 비효율적 순환문, 과도한 순환 복잡도, 중복 코드 등 당장 장애는 없으나 기술 부채(Technical Debt)를 가중시키는 코드.
2.  **이슈의 심각도 (Severity)**: Blocker $\to$ Critical $\to$ Major $\to$ Minor $\to$ Info.
3.  **정량적 복잡도 및 커버리지 (Metrics)**:
    *   순환 복잡도 (McCabe's V(G)): 함수당 10 미만 권장.
    *   코드 중복률 (Duplication): 5% 미만 권장.

### Ⅲ. 실무적 결과 해석 및 조치 프로세스 (Triage Process)
*   **1단계: 스캔 및 취합**: CI 파이프라인에서 빌드 시 Sonar Scanner 작동.
*   **2단계: 자동 분류 및 임계치 대조**: Quality Gate(품질 임계치) 통과 여부 확인.
*   **3단계: Triage (전문가 해석)**:
    *   **True Positive (진성 결함)**: 심각도에 따라 조치 기한(SLA) 할당. (예: Blocker는 당일 수정).
    *   **False Positive (오탐)**: 정규식 오류나 툴의 컨텍스트 파악 실패로 인한 오보. 도구 대시보드에서 `Resolve as False Positive` 처리하여 다음 스캔 시 무시하도록 규칙 갱신.
*   **4단계: Refactoring & Remediation**: 기술 부채 감축 일정에 맞춰 코드 스멜 제거.

### Ⅳ. 정적 분석 메트릭의 오독 방지 및 보완 전략
| 정적 분석의 맹점 | 잘못된 해석 사례 | 올바른 해석 및 보완 전략 (Best Practice) |
| :--- | :--- | :--- |
| **비즈니스 로직 미인식** | "버그(Bug)가 0개이므로 고객이 요구한 송금 로직은 완벽하다." | 비즈니스 로직의 정합성은 동적 **단위 테스트(Unit Test)** 및 **블랙박스 테스트**로 별도 검증해야 함. |
| **과도한 규칙 적용** | Minor한 띄어쓰기 룰 위반 수천 개를 보고 "우리 코드는 쓰레기다." | 프로젝트 특성에 맞지 않는 룰은 **Quality Profile에서 과감히 제외(De-activate)** 시켜 노이즈를 줄여야 함. |
| **보안 점검의 한계** | SAST에서 Vulnerability 0건이므로 해킹에서 안전하다. | 동적 분석(DAST) 및 모의 해킹(Penetration Test)을 통해 서버 환경에서의 런타임 취약점 점검 필수. |

### Ⅴ. 현대 CI/CD 파이프라인 내에서의 결과 해석 자동화
*   정적 분석 해석이 개발자 개인의 성향에 좌우되지 않도록, 팀의 합의된 기준을 **Quality Gate(품질 게이트)**로 시스템화함.
*   **적용 예시**: 신규 작성된 코드(New Code)에 대하여 1) Blocker 이슈 존재 시, 2) 순환 복잡도 15 이상 시, 3) 코드 커버리지 80% 미만 시 **Git Pull Request(PR)의 Merge 버튼을 비활성화(Build Fail)** 시킴.
