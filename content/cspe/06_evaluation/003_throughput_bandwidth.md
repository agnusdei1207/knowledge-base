# 📖 【암기용】 개념 완전 이해

## 한눈에
- **개요**: **대역폭(Bandwidth)**은 매체나 장치가 이론적으로 낼 수 있는 최대 전송 용량이고, **처리율(Throughput)**은 실제 환경에서 다양한 제약 조건을 뚫고 실질적으로 처리된 성능을 의미한다.
- **왜 필요한가**: 장비 카탈로그의 '대역폭(예: 10Gbps)'만 믿고 시스템을 설계하면, 실제 운영 시 발생하는 프로토콜 오버헤드나 혼잡으로 인해 성능이 기대치에 못 미치는 '용량 부족' 사태를 겪게 되기 때문이다.
- **핵심 직관**: **대역폭**은 수도관의 굵기(최대 유량)이고, **처리율**은 수도꼭지를 틀었을 때 실제로 나오는 물의 양이다. 수도관이 굵어도(High Bandwidth) 밸브가 덜 열렸거나 녹이 슬었다면 실제 나오는 물(Throughput)은 적을 수밖에 없다.

## 핵심 용어 정리

| 용어/표기 | 의미 | 기술적 포인트 |
|:---|:---|:---|
| **Bandwidth** (대역폭) | 이론적 최대 전송 능력 | 물리 계층(L1)의 하드웨어 한계치 |
| **Throughput** (처리율) | 실측된 단위 시간당 데이터 전송량 | 실제 성능의 지표 (bps, TPS 등) |
| **Goodput** (유효 처리율) | 실제 사용자 데이터의 순수 처리율 | 헤더, 재전송, 제어 정보를 제외한 알맹이 값 |
| **Protocol Overhead** | 전송을 위해 붙는 부가 정보 | TCP/IP 헤더, 인코딩 비용 등 |
| **Congestion Control** | 네트워크 혼잡 시 전송 속도 조절 | TCP의 Sliding Window 등 처리율 저하 요인 |
| **RTT** (Round Trip Time) | 왕복 지연 시간 | RTT가 크면 확인 응답(ACK) 대기로 처리율 저하 |

## 깊이 이해
- **격차가 발생하는 이유 (The Gap)**:
  1. **오버헤드**: 데이터 하나를 보낼 때마다 TCP/IP 헤더가 붙어 실제 대역폭의 일부를 소모한다.
  2. **혼잡 및 오류**: 패킷 손실 시 재전송(Retransmission)이 발생하며, 이는 대역폭을 소모하지만 Goodput에는 기여하지 못한다.
  3. **윈도우 크기**: 수신측의 수용 능력(Window Size)이 작으면 대역폭이 아무리 넓어도 처리율은 제약을 받는다.
- **계층적 관계**: $Goodput \leq Throughput \leq Bandwidth$
  - 규격(Bandwidth) 내에서 전송(Throughput)이 이루어지고, 그중 유효한 데이터만(Goodput) 남는다.
- **비유 (택배 서비스)**:
  - **대역폭**: 택배 트럭의 적재함 크기.
  - **처리율**: 트럭에 실린 전체 박스 수.
  - **Goodput**: 박스 안의 포장재를 제외한 실제 상품의 양.
- **구체 예시 (1Gbps 네트워크)**:
  - 물리 대역폭: 1,000 Mbps
  - 실측 처리율: 약 940 Mbps (MTU 1500 기준, TCP 오버헤드 차감)
  - 유효 처리율(Goodput): 애플리케이션 계층 헤더까지 고려하면 더 낮아짐.

## 연결 개념
- **시스템 성능 지표(001)**: 처리율은 성능의 양적 지표 중 하나.
- **병목 분석(004)**: 대역폭과 처리율의 격차가 가장 큰 지점을 찾는 과정.
- **TCP 혼잡 제어**: 처리율을 동적으로 결정하는 네트워크 메커니즘.

# 📝 【답안용】 시험 답안 템플릿

## 핵심 인사이트 (3줄 요약)

> 1. **본질**: 대역폭은 전송 가능한 이론적 상한선(Potential)이며, 처리율은 실제 환경에서 달성된 실효 성능(Performance)임.
> 2. **격차**: 프로토콜 오버헤드, 재전송, 혼잡 제어 메커니즘으로 인해 $Throughput$은 항상 $Bandwidth$보다 낮게 측정됨.
> 3. **설계 전략**: 시스템 가용 용량 산정 시 대역폭의 70~80% 수준을 실질 처리율 목표로 설정하고, $Goodput$ 극대화를 위한 프로토콜 튜닝이 병행되어야 함.

## 출제 의도 및 답안 포인트

| 출제 의도 | 반드시 짚을 핵심 | 감점 회피 포인트 |
|:---|:---|:---|
| 대역폭과 처리율의 개념적 차이 | 이론치(B) vs 실측치(T) | 두 용어를 혼용하거나 동일한 값으로 서술 방지 |
| 처리율 저하 요인 분석 | 오버헤드, 혼잡 제어, RTT, 재전송 | 단순히 "네트워크 상태"라고 뭉뚱그리지 말 것 |
| Goodput 개념의 가치 | 유효 데이터 기준의 성능 지표 | Goodput과 Throughput의 차이 명확히 제시 |

## Ⅰ. 대역폭(Bandwidth)과 처리율(Throughput)의 개요

### 1. 정의 및 비교
- **대역폭**: 주어진 시간 동안 네트워크 매체를 통해 전송 가능한 이론적 최대 데이터 전송량 (The Pipe Size)
- **처리율**: 특정 기간 실제 전송되거나 처리된 데이터의 양 (The Flow)

### 2. 성능 평가에서의 중요성
- **용량 계획**: 하드웨어 사양(대역폭)과 실측 성능(처리율)의 격차를 파악하여 과소 산정 리스크 방지
- **SLA 관리**: 고객에게 보장해야 할 실효 속도(Goodput)의 기준점 제시

---

## Ⅱ. 대역폭과 처리율의 상관관계 및 계층 구조

### 1. 성능 계층 구조도 (Performance Hierarchy)

```text
    +------------------------------------------+
    |           Bandwidth (Theoretical Max)    |
    |  +------------------------------------+  |
    |  |        Throughput (Measured)       |  |
    |  |  +------------------------------+  |  |
    |  |  |     Goodput (Useful Data)    |  |  |
    |  +--+------------------------------+--+  |
    +------------------------------------------+
    * 관계식: Goodput = Throughput - Overhead - Retransmissions
```

### 2. 주요 차이점 비교

| 구분 | 대역폭 (Bandwidth) | 처리율 (Throughput) |
|:---|:---|:---|
| **성격** | 잠재적 역량 (Capacity) | 실제 달성치 (Actual) |
| **결정 요인** | 물리 매체 규격, HW 성능 | 부하, 혼잡, 오류, 프로토콜 |
| **단위** | bps (bits per second) | bps, TPS, RPS 등 |
| **측정 시점** | 장비 도입 전 (사양서) | 시스템 운영 중 (모니터링) |

---

## Ⅲ. 처리율 저하의 기술적 요인 및 격차 분석

### 1. 격차 발생 요인 (Performance Degradation Factors)
- **프로토콜 오버헤드**: TCP(20byte), IP(20byte), Ethernet(18byte) 헤더 부착에 따른 가용 대역폭 소모
- **혼잡 제어 (Congestion Control)**: 패킷 손실 감지 시 윈도우 크기를 축소하여 처리율을 강제로 하락시킴
- **RTT 지연**: 요청에 대한 확인 응답(ACK)이 올 때까지의 대기 시간으로 인한 링크 유휴 발생
- **재전송 (Retransmission)**: 오류 패킷 복구를 위해 동일 데이터를 중복 전송하며 유효 대역폭 낭비

### 2. Goodput 극대화 방안
- **MTU 최적화**: 점보 프레임(Jumbo Frame) 사용으로 헤더 비중 감소 및 처리율 향상
- **TCP Window Tuning**: 대역폭-지연 곱(BDP)에 맞춰 윈도우 크기를 확대하여 대역폭 활용도 제고
- **Compression**: 데이터 압축을 통해 동일 처리율 내에서 더 높은 Goodput 달성

---

## Ⅳ. 실무적 고려사항: 성능 측정 및 관리

- **측정 도구 활용**: `iperf3`(네트워크 처리율), `ab`/`wrk`(HTTP 처리율) 등을 활용한 정기적 벤치마킹
- **임계치 관리**: 대역폭 대비 처리율이 90%를 상회할 경우 큐 지연 급증에 대비한 증설 검토
- **병목 구간 식별**: 종단 간(End-to-End) 전 구간 중 가장 대역폭이 좁은 '최소 대역폭 구간'을 집중 관리

---

## Ⅴ. 처리율과 대역폭의 종합 비교

| 비교 항목 | 대역폭 | 처리율 | Goodput |
|:---|:---|:---|:---|
| **관점** | 물리적 / 이론적 | 시스템적 / 실질적 | 사용자 / 비즈니스적 |
| **기준** | 하드웨어 사양 | 네트워크 소통량 | 실제 앱 데이터량 |
| **최적화** | 장비 업그레이드 | 프로토콜/설계 튜닝 | 데이터 효율화 / 압축 |

---

## Ⅵ. 결론 및 제언

- 성능 평가는 **대역폭이라는 환상**에서 벗어나 **처리율과 Goodput이라는 실체**를 측정하는 것에서 시작함.
- 설계 단계에서 **75% 법칙**(대역폭의 75%만 실질 처리율로 가정)을 적용하여 안전 마진을 확보하고, 실측 기반의 용량 산정 체계를 구축해야 함.
