# 📖 【암기용】 개념 완전 이해

## 한눈에
- **개요**: 자동 페일오버·페일백은 **HA 전환 메커니즘**으로, 페일오버는 장애 노드에서 정상 노드로 서비스를 자동 전환하는 것이고, 페일백은 복구된 원래 노드로 서비스를 되돌리는 것임.
- **왜 필요한가**: 수동 전환은 담당자 인지·판단·조작 시간이 더해져 RTO(026) 목표(분 단위)를 만족하기 어려움. 자동화하면 감지~전환 소요 시간을 초 단위로 단축 가능.
- **핵심 직관**: 페일오버 = 고장 난 주 엔진에서 보조 엔진으로 자동 전환, 페일백 = 수리된 주 엔진을 재검증한 뒤 다시 주력으로 복귀.

## 핵심 용어 정리 (내부에 등장하는 것들)

023이 HA 구조를, 027이 split-brain·쿼럼을 다뤘으므로 여기서는 전환 메커니즘 고유의 감지·전환·복귀 용어에 집중함.

| 용어/표기 | 의미 | 비유·예 |
|:---|:---|:---|
| 페일오버 (상위 키워드) | 장애 노드→정상 노드로 서비스 자동 전환 | 주 엔진→보조 엔진 자동 교대 |
| 페일백 | 복구된 원래 노드로 서비스 복귀 | 수리 끝난 주 엔진으로 되돌림 |
| Health Check | 노드 생존 확인 주기적 검사 | 맥박 확인 |
| 연속 실패 임계치 | 페일오버 발동 기준(예: 3회 연속 실패) | 3번 맥박 없으면 사망 판정 |
| Flapping | 페일오버·페일백이 반복 왕복하는 불안정 상태 | 스위치 깜빡임 |
| 유예 시간(Grace Period) | 페일백 전 안정성 검증을 위한 대기 시간 | 수리 후 시운전 시간 |
| 점진적 전환 | 트래픽을 10%→50%→100%로 단계적 이전 | 물 조금씩 채우기 |

## 깊이 이해
- **배경·문제의식**: (023 참조) Active-Standby 구조에서 Active 장애 시, 수동 전환은 담당자가 상황 인지(수 분)→판단(수 분)→조작(수 분) 과정을 거쳐 RTO(026)가 10분 이상으로 늘어남. 자동화하면 Health Check 감지(초)→쿼럼 판정(027, 초)→전환(초)으로 RTO를 수십 초 이내로 단축 가능.
- **작동 원리 — 자동 페일오버**:
  - Health Check가 설정 주기(예: 5초)마다 노드 생존을 확인함.
  - 연속 실패 횟수가 임계치(예: 3회, 총 15초)에 도달하면 장애로 판정함.
  - 쿼럼(027)으로 split-brain을 방지한 뒤 Standby 노드를 Active로 승격(promote)하고 VIP/DNS를 전환함.
  - 전환 후 서비스 정상 여부를 검증(헬스체크 통과, 요청 처리 확인).
- **작동 원리 — 페일백**:
  - 복구된 원래 노드의 OS·앱·데이터 정합성을 재확인함.
  - 유예 시간(예: 30분) 동안 안정적으로 Health Check를 통과하는지 확인함.
  - 트래픽을 점진적(10%→50%→100%)으로 이전해 Flapping을 방지함.
  - 페일오버는 신속성이 최우선이지만 페일백은 안정성 재검증이 최우선 — 비대칭 설계.
- **비유**: 페일오버 = 야구에서 부상 투수 대신 불펜 투수가 즉시 등판(빠른 교대), 페일백 = 부상 투수가 완전 회복 후 재활 등판을 거쳐 선발 복귀(신중한 복귀).
- **구체 예시**: PostgreSQL + Patroni: Health Check 5초 주기 × 3회 연속 실패(15초) → Patroni가 etcd 쿼럼(027) 확인 후 Standby를 promote, VIP 전환 → 전체 페일오버 30초 이내. 페일백: 원래 노드 복구 후 30분 유예 → pg_basebackup으로 데이터 동기화 → 트래픽 10%→50%→100% 점진 이전.
- **흔한 오해·주의점**: ① 페일오버와 페일백을 대칭적으로 자동화하면 안 됨 — 페일오버는 즉시, 페일백은 유예·점진 필수. ② 즉시 100% 페일백은 Flapping(전환 반복)을 유발할 수 있어 점진적 전환과 유예 시간 설계가 필수. ③ Health Check 임계치가 너무 낮으면 일시적 지연을 장애로 오탐, 너무 높으면 감지가 느려 RTO 초과.

## 연결 개념
- **고가용성 설계 (023)**: 페일오버 대상이 되는 이중화 노드 구조(AA/AS).
- **Split-brain·쿼럼 (027)**: 페일오버 시 이중 승격을 막는 투표 메커니즘.
- **RTO·RPO (026)**: 페일오버 소요 시간이 RTO에 직결, 복제 방식이 RPO를 결정.

# 📝 【답안용】 시험 답안 템플릿

## 핵심 인사이트 (3줄 요약)

> 1. **본질**: 페일오버는 장애→정상 노드 자동 전환(신속성 우선), 페일백은 복구 노드로 복귀(안정성 우선)이며 비대칭 설계가 핵심임.
> 2. **가치**: 자동화로 수동 전환 대비 RTO(026)를 수십 초 이내로 단축하고 인적 오류를 제거함.
> 3. **판단 포인트**: Health Check 임계치(오탐 vs 지연 트레이드오프) + 쿼럼(027) + 페일백 유예·점진 전환이 설계 핵심임.

## 출제 의도 및 답안 포인트

| 출제 의도 | 반드시 짚을 핵심 | 감점 회피 포인트 |
|:---|:---|:---|
| 페일오버·페일백 구분 | 방향 차이(장애→정상 vs 복구→원래) | 둘을 동일 메커니즘으로 서술 |
| 자동화 메커니즘 | Health Check 임계치, 쿼럼(027) 연계 | Health Check 없이 "자동 전환" 서술 |
| 비대칭 설계 이해 | 페일오버=즉시, 페일백=유예·점진 | 대칭적 즉시 전환으로 설계 |

> 요약: 방향 구분 + Health Check·쿼럼 메커니즘 + 페일오버/페일백 비대칭 설계를 보여야 함.

---

## Ⅰ. 개요 및 필요성

- 개요: 페일오버는 장애→정상 노드 자동 전환, 페일백은 복구 노드로 복귀하는 HA 전환 메커니즘
- 배경: 수동 전환은 인지·판단·조작 시간으로 RTO(026)가 10분 이상으로 증가, 분 단위 RTO 달성 불가
- 필요성: Health Check + 쿼럼(027) 기반 자동 전환으로 RTO를 수십 초 이내로 단축하고 인적 오류를 제거해야 함

---

## Ⅱ. 구조 및 구성요소

```text
Active Node <-> Heartbeat/Health Check <-> Standby Node
  -> Health Check 연속 실패 -> 쿼럼(027) 판정
  -> 페일오버: Standby promote, VIP 전환
  -> 복구 후: 유예 시간 -> 점진적 페일백
```

| 구성요소 | 역할 | 특이사항 |
|:---|:---|:---|
| Health Check | 노드 생존 주기적 확인 | 주기 5초, 임계치 3회 연속 등 |
| 쿼럼(027) | split-brain 방지 투표 | 페일오버 전 과반수 확인 필수 |
| VIP/DNS 전환 | 트래픽 경로를 새 Active로 변경 | VIP 이동 또는 DNS TTL 갱신 |
| 유예 시간 | 페일백 전 안정성 검증 대기 | 30분 이상 Health Check 통과 |
| 점진적 전환 | 페일백 시 트래픽 단계적 이전 | 10%→50%→100%, Flapping 방지 |

> 요약: Health Check 감지 → 쿼럼 확인 → 페일오버(VIP 전환) → 복구 후 유예·점진 페일백의 비대칭 구조임.

---

## Ⅲ. 동작원리 및 흐름도

```text
[페일오버] Health Check 실패 감지 -> 연속 실패 임계치 도달 -> 쿼럼(027) 확인
  -> Standby promote -> VIP/DNS 전환 -> 서비스 검증
[페일백] 원래 노드 복구 -> 데이터 동기화 -> 유예 시간(30분) -> 점진 전환(10%→50%→100%)
```

1. Health Check가 설정 주기(5초)마다 Active 노드 생존을 확인하고, 연속 실패 횟수가 임계치(3회, 총 15초)에 도달하면 장애로 판정함
2. 쿼럼(027)으로 split-brain을 방지한 뒤 Standby 노드를 Active로 승격(promote)하고 VIP/DNS를 전환해 트래픽을 리다이렉트함
3. 전환 후 서비스 정상 여부(요청 처리·응답 코드)를 자동 검증함 — 여기까지가 페일오버이며 RTO(026) 카운트가 종료됨
4. 원래 노드 복구 후 데이터 동기화 → 유예 시간(30분) 동안 안정성 검증 → 트래픽 10%→50%→100% 점진 이전으로 페일백 완료(Flapping 방지)

> 요약: 페일오버는 감지→쿼럼→promote→VIP 전환(즉시), 페일백은 복구→동기화→유예→점진 전환(신중) 비대칭 흐름임.

---

## Ⅳ. 특징

- 비대칭 설계: 페일오버는 신속성(초 단위), 페일백은 안정성(유예·점진)이 최우선 — 대칭 설계는 Flapping 유발
- Health Check 트레이드오프: 임계치 낮으면 일시 지연 오탐, 높으면 감지 지연 → RTO 목표에 맞춰 조정
- 쿼럼 필수 연계: 페일오버 전 쿼럼(027) 확인 없으면 split-brain 위험 — 독립 메커니즘이 아님
- RTO 직결: 페일오버 소요 시간(Health Check 주기 × 임계치 + 전환 시간) = 실측 RTO(026)
- 점진적 페일백: 즉시 100% 복귀는 복구 불완전 시 재장애 유발 → 10%→50%→100% 단계적 이전 권장

---

## Ⅴ. 심화 비교 및 적용 판단

| 구분 | 수동 페일오버 | 자동 페일오버 | 선택 기준 |
|:---|:---|:---|:---|
| RTO | 10분 이상(인지·판단·조작) | 수십 초 이내(감지·쿼럼·전환) | RTO 목표(분 이내 vs 수십 분 허용) |
| 인적 오류 | 판단 착오·조작 실수 위험 | 로직 기반 자동 판정 | 운영 인력·온콜 체계 |
| Split-brain | 수동 판단으로 이중 승격 방지 | 쿼럼(027) 자동 판정 | 클러스터 규모·정합성 요구 |
| 적합 시나리오 | 전환 영향이 큰 대형 DB 마이그레이션 | 일상적 노드 장애 대응 | 전환 빈도·자동화 성숙도 |

> 요약: RTO 분 이내 목표이고 자동화 성숙도가 확보됐으면 자동 페일오버, 전환 영향이 대규모이면 수동 검토 후 전환함.

**리스크·대응:**
- 오탐(False Positive): Health Check 임계치 과소로 일시 지연을 장애로 판정 → 임계치 튜닝(주기·횟수) + 지연 vs 장애 구분 로직 (지표: 오탐 발동 건수)
- Flapping: 페일백 즉시 100% 전환으로 전환 반복 → 유예 시간(30분) + 점진적 전환(10%→50%→100%) (지표: 페일백 후 재페일오버 발생 건수)
- 동기화 불일치: 페일백 시 데이터 정합성 미확인 → 복구 노드 데이터 동기화 완료 후 페일백 개시 (지표: 복제 lag 0 확인)

**점검 지표:**
- 성능: 페일오버 소요 시간(실측) ≤ RTO(026) 목표 — 정기 페일오버 훈련 로그
- 운영: 오탐 건수 0건 + 페일백 후 재장애 0건 — Health Check 이벤트 로그

---

## Ⅵ. 실무 적용 및 결론

**적용 방안:**
1. Health Check 주기(5초)·연속 실패 임계치(3회)를 RTO(026) 목표에 맞춰 설정하고, 쿼럼(027)과 연계해 자동 페일오버를 구성함
2. 페일백은 복구 노드 데이터 동기화 완료 + 유예 시간(30분) + 점진적 전환(10%→50%→100%)으로 비대칭 설계함
3. 분기별 페일오버·페일백 훈련을 실시해 실측 전환 시간을 RTO와 대조하고 Health Check 임계치를 재조정함

**결론:**
- 기술사 판단: 페일오버는 즉시·자동, 페일백은 유예·점진의 비대칭 설계가 핵심이며 쿼럼(027) 연계 없이 단독 운영하면 split-brain 위험
- 향후 방향: Kubernetes Operator 기반 자동 페일오버와 GitOps 기반 페일백 자동화로 운영 부담을 줄이는 추세임
