# 📖 【암기용】 개념 완전 이해

## 한눈에
- **개요**: 하드웨어 규모 산정(TPS 기반)은 피크 TPS를 출발점으로 CPU·메모리·디스크 필요 용량을 산식으로 계산하고 보정계수로 여유·성장·부하를 반영해 서버 사양을 도출하는 용량 설계 기법(TPS 계산은 010, 성능 지표는 001 참조)
- **왜 필요한가**: 과소 산정은 성능 미달·장애를, 과대 산정은 예산 낭비를 유발하므로, 목표 처리량에 근거한 정량 산식과 검증 가능한 보정계수로 사양을 확정해야 함
- **핵심 직관**: 초당 처리할 손님 수(피크 TPS)를 기준으로 계산대 수(CPU)·대기 공간(메모리)·창고 크기(디스크)를 정하되, 몰리는 시간과 미래 증가분을 곱해 여유를 남기는 것과 같음

## 핵심 용어 정리 (내부에 등장하는 것들)
아래 표기는 답안용 Ⅰ~Ⅵ의 산식·표에 그대로 등장하므로 먼저 직관적으로 풀어 둔다. 상위 핵심 키워드는 **피크 TPS 기반 컴포넌트별 용량 산식과 보정계수**이다.

| 용어/표기 | 의미 | 비유·예 |
|:---|:---|:---|
| 피크 TPS | 최번시(가장 붐비는 시간)의 초당 트랜잭션 수(001 참조) | 점심시간 계산대에 몰리는 손님 밀도 |
| tpmC | TPC-C 벤치마크로 측정한 분당 처리 트랜잭션(CPU 처리능력 단위, 014 참조) | 서버 1대가 낼 수 있는 처리력 등급표 |
| 트랜잭션 부하값 | 1건 처리에 드는 상대적 자원 소모 가중치 | 주문 1건이 조회 1건보다 무거운 정도 |
| 보정계수 | 피크·부하·미래성장·여유를 반영해 곱하는 계수 | 예상보다 붐빌 때를 대비한 곱셈 여유분 |
| 목표 이용률 | 산정 시 상정하는 자원 사용률 상한(보통 CPU 40~70%) | 계산대를 100%가 아니라 60%만 쓰도록 설계 |
| 여유율(headroom) | 1 - 목표 이용률, 급증·장애 대비 남기는 비율 | 갑작스런 손님 급증을 흡수할 빈 공간 |
| 성장률(CAGR) | 연평균 데이터·부하 증가율(장비 수명 N년 반영) | 매년 20%씩 늘어나는 손님 수 추세 |
| 세션당 메모리 | 동시 사용자 1명이 점유하는 메모리량 | 손님 1명이 차지하는 자리 크기 |
| RAID 보정 | RAID 패리티·미러로 늘어나는 디스크 오버헤드 | 백업본을 위해 창고를 더 넓히는 비율 |
| OS/DBMS 상주분 | 애플리케이션과 무관하게 고정 점유하는 메모리 | 매장 운영에 늘 필요한 기본 집기 공간 |

## 깊이 이해
- **배경·문제의식**: 부하테스트 실측이 없는 설계·제안 단계에서는 목표 TPS와 표준 산식으로 사양을 미리 정해야 하며, 근거 없는 "넉넉히"는 예산 심사·감리에서 탈락함. 국내는 NIA 정보시스템 하드웨어 규모산정 지침·TTA 표준이 산식과 보정계수를 규정함
- **작동 원리(어떻게+왜)**: CPU는 필요 처리능력(tpmC) = 피크 TPS × 60 × 트랜잭션 부하값 × 보정계수 ÷ 여유율로, 목표 tpmC를 낼 장비 사양·대수를 매핑함. 메모리는 OS/DBMS 상주분 + (동시 사용자 수 × 세션당 메모리) + 캐시·버퍼 + 여유로, 디스크는 순수 데이터량 × (1+성장률)^N × RAID 보정 × 인덱스·로그·임시 오버헤드로 산정. 여유율로 나누는 이유는 자원이 포화(이용률 100%)에 다가갈수록 대기행렬 지연이 급증(005 큐잉이론)하기 때문
- **비유**: 마트를 지을 때 최번시 손님 수(피크 TPS)를 기준으로 계산대(CPU)·대기공간(메모리)·창고(디스크)를 정하되, 명절 급증분과 3년 뒤 확장을 곱해 여유를 두는 설계와 같음
- **구체 예시**: 피크 TPS 200, 트랜잭션 부하값 1.0, 목표 CPU 이용률 60%(여유율 0.6), 보정계수 1.2이면 필요 처리능력 = 200 × 60 × 1.0 × 1.2 ÷ 0.6 = 24,000 tpmC 상당 장비 필요. 동시 사용자 5,000명·세션당 2MB면 세션 메모리 10GB + OS/DBMS 상주 16GB + 캐시 여유로 산정(수치는 예시이며 BMT·부하테스트로 검증 필요, 015 참조)
- **흔한 오해**: 피크 TPS 대신 평균 TPS로 산정하면 최번시에 포화됨. 목표 이용률을 100%로 두면 대기 지연이 폭증하므로 반드시 여유율을 확보해야 하고, 산정값은 확정이 아니라 BMT로 검증할 출발점임

## 연결 개념
- TPS 계산(010) — 동시 사용자·응답시간에서 피크 TPS를 도출하는 선행 계산
- 벤치마크(014) — tpmC 등 CPU 처리능력 단위를 제공해 산정값을 장비 사양에 매핑
- BMT(015) — 산정된 사양을 실제 워크로드로 검증·비교하는 후속 절차

## 핵심 인사이트 (3줄 요약)

> 1. **본질**: HW 규모 산정(TPS 기반)은 피크 TPS를 기준으로 CPU·메모리·디스크 필요 용량을 산식화하고 보정계수로 여유·성장을 반영하는 정량 설계임.
> 2. **가치**: 근거 있는 산식과 검증 가능한 계수로 과소·과대 산정을 방지해 성능·예산을 동시에 만족함.
> 3. **판단 포인트**: 평균이 아닌 피크 TPS·여유율(목표 이용률)·미래 성장률을 반영하고 산정값은 BMT로 검증해야 함.

| 보정·검증 이해 확인 | 여유율·성장률·BMT 검증 병행 | 산정값을 확정 사양으로 단정 |

> 요약: 이 문제는 단일 수치보다 피크 기반 산식·보정계수·검증 절차의 논리적 연결을 요구함.

## Ⅰ. 개요 및 필요성

- 개요: 피크 TPS를 기준으로 CPU·메모리·디스크 필요 용량을 산식·보정계수로 도출하는 용량 설계 기법
- 배경: 실측 부하테스트 이전 설계·제안 단계에서 정량 근거로 서버 사양을 확정해야 함
- 필요성: 과소 산정은 성능 미달·장애를, 과대 산정은 예산 낭비를 유발하므로 검증 가능한 산식이 필요
- 표준 근거: NIA 하드웨어 규모산정 지침·TTA 표준이 산식과 보정계수를 규정

---

## Ⅱ. 구조 및 구성요소

```text
요구사항 수집(피크 TPS·동시 사용자·데이터량) -> 기준 지표 선정(tpmC·부하값)
  -> 컴포넌트별 산정 분기: CPU 산정 / 메모리 산정 / 디스크 산정
  -> 보정계수 적용(피크·부하·성장·여유율) -> 장비 사양 매핑 -> BMT 검증(015)
```

| 구성요소 | 역할 | 특이사항 |
|:---|:---|:---|
| 입력 요구사항 | 피크 TPS·동시 사용자·데이터량·수명 N년 | 평균 아닌 최번시 기준 |
| CPU 산정식 | 피크 TPS × 60 × 부하값 × 보정 ÷ 여유율 | 결과를 tpmC로 장비 매핑(014) |
| 메모리 산정식 | OS/DBMS 상주 + 세션 + 캐시 + 여유 | 세션당 메모리 × 동시 사용자 |
| 디스크 산정식 | 데이터 × (1+성장률)^N × RAID × 오버헤드 | 인덱스·로그·임시영역 포함 |
| 보정계수 | 피크·부하·성장·여유율 반영 계수 | 근거 문서화 필수 |

> 요약: 입력 요구사항을 컴포넌트별 산식에 넣고 보정계수를 적용해 장비 사양으로 매핑함.

---

## Ⅲ. 동작원리 및 흐름도

```text
성능 요구 확보(피크 TPS·동시 사용자·데이터) -> 컴포넌트별 산식 계산
  -> 보정계수(여유율·성장률) 적용 -> 장비 사양·대수 매핑 -> BMT·부하테스트로 검증
```

- 1단계: 설계자가 업무량 분석으로 피크 TPS·동시 사용자 수·초기 데이터량·장비 수명 N년을 확보함
- 2단계: 설계자가 CPU는 tpmC 산식, 메모리는 상주+세션+캐시 합산, 디스크는 성장·RAID 보정식으로 각각 계산함
- 3단계: 설계자가 목표 이용률에 따른 여유율과 성장률·부하 보정계수를 곱해 필요 용량을 확정함
- 4단계: 설계자가 산정 결과를 벤치마크 등급(014)으로 장비에 매핑하고 BMT(015)로 실측 검증함

> 요약: 설계자가 요구량을 컴포넌트별 산식에 넣고 보정계수를 적용한 뒤 벤치마크 매핑·BMT로 검증함.

---

## Ⅳ. 특징

- 피크 기준으로 산정함: 평균이 아닌 최번시 TPS를 입력해 붐비는 시간에도 SLA를 유지함
- 컴포넌트별로 분리 산정함: CPU·메모리·디스크가 각기 다른 지표·산식을 사용해 병목 편중을 방지함
- 보정계수로 불확실성을 흡수함: 피크·부하·성장·여유율을 곱해 예측 오차와 미래 증가를 반영함
- 여유율이 지연을 좌우함: 목표 이용률을 높게 잡을수록 대기행렬 지연이 급증하므로 40~70% 상한을 둠
- 검증 전 확정이 아님: 산정값은 BMT·부하테스트로 검증할 출발점이며 실측 괴리 시 재산정이 필요함

## Ⅴ. 심화 비교 및 적용 판단

| 구분 | CPU 산정 | 메모리 산정 | 디스크 산정 |
|:---|:---|:---|:---|
| 기준 지표 | 피크 TPS·트랜잭션 부하값 | 동시 사용자·세션당 메모리 | 초기 데이터량·성장률 |
| 핵심 보정 | 여유율·피크 보정계수 | OS/DBMS 상주·캐시 여유 | RAID·인덱스/로그 오버헤드 |
| 단위·매핑 | tpmC·OPS로 장비 매핑(014) | GB, 상주+세션 합산 | TB, (1+성장률)^N |
| 포화 위험 | 이용률 100% 접근 시 지연 폭증 | swap 발생 시 성능 급락 | 사용률 80% 초과 시 단편화 |

> 요약: 세 컴포넌트는 기준 지표·보정 항목·포화 신호가 달라 각각의 산식과 여유 기준을 분리 적용해야 함.

- 리스크 — 평균 기반 과소 산정: 평균 TPS로 계산해 최번시 포화 — 대응: 최번시 로그로 피크 TPS 산출, 확인 지표 피크/평균 비율
- 리스크 — 여유율 미확보: 목표 이용률 과다로 대기 지연 급증 — 대응: CPU 60%·디스크 80% 상한 설정, 확인 지표 이용률 헤드룸
- 리스크 — 성장 미반영: 초기 데이터량만 산정해 수명 내 부족 — 대응: CAGR 기반 (1+성장률)^N 적용, 확인 지표 연간 증가율

- 지표 — 산정-실측 오차: 목표 20% 이내 — 측정: BMT·부하테스트 대비 비교
- 지표 — 목표 이용률 준수: CPU 피크 70% 이하 — 측정: 운영 후 sar·모니터링
- 지표 — 용량 소진 시점: 수명 N년 내 미소진 — 측정: 성장률 기반 추세 예측

## Ⅵ. 실무 적용 및 결론

**적용 방안 3개 (필수 — 단계별 또는 항목별):**
1. 최번시 트랜잭션 로그로 피크 TPS·트랜잭션 부하값을 도출하고 tpmC 산식에 보정계수·여유율을 적용해 CPU 사양을 산정함
2. 동시 사용자 수 × 세션당 메모리에 OS/DBMS 상주분·캐시 여유를 더하고, 디스크는 성장률·RAID 오버헤드를 반영해 컴포넌트별로 분리 산정함
3. 산정 결과를 벤치마크 등급(014)으로 장비에 매핑한 뒤 BMT(015)·부하테스트로 실측 검증하고 오차 20% 초과 시 재산정함

**결론 (2줄):**
- 기술사 판단: 워크로드가 OLTP면 tpmC·CPU 여유율 중심으로, 대용량 분석·저장이면 디스크 성장률·처리량 중심으로 산정 축을 달리해야 함
- 향후 방향: 클라우드 오토스케일·서버리스 환경에서는 고정 산정 대신 기준선 산정 후 탄력 확장 정책과 결합해 과대 산정을 줄여야 함
