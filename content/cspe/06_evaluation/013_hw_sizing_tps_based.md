## 📖 【암기용】 핵심 요약

*   **한눈에**: 신규 시스템 구축 시 예상되는 비즈니스 부하(Peak TPS, 동시 사용자 수, 데이터량 등)를 기반으로, 필요한 하드웨어 자원(CPU, Memory, Disk)의 용량을 수학적 산식으로 역산하는 공학적 설계 과정.
*   **깊이 이해**:
    *   **배경**: 서버 용량을 감으로 때려잡으면? 과소 산정(Under-sizing) 시 오픈 첫날 서버가 터져 9시 뉴스에 나오고, 과대 산정(Over-sizing) 시 수십억 원의 예산 낭비로 감사를 받게 됨. 이를 막기 위해 공공기관(NIA) 가이드라인 등 표준화된 공식이 도입됨.
    *   **작동 원리 (CPU Sizing)**: 기준은 평균이 아닌 **Peak TPS**(가장 붐빌 때). `Peak TPS × 60초 × 업무가중치(조회/갱신 복잡도) × 각종 보정계수(네트워크, 클러스터링 오버헤드) ÷ 목표 이용률(보통 70%)`을 통해 요구되는 **tpmC(CPU 처리 성능 단위)**를 산출함.
    *   **비유**: **뷔페식당 개업 준비**. 
        *   **CPU (셰프)**: 피크 타임(점심 12시)에 밀려드는 주문(TPS)을 소화하기 위해 셰프가 몇 명 필요한가?
        *   **Memory (테이블)**: 손님이 한 번에 몇 명(Concurrency)이나 앉아서 밥을 먹는가?
        *   **Disk (냉장고)**: 향후 5년간 늘어날 식재료(Data Growth)를 얼마나 보관할 수 있는가?
    *   **구체 예시**: 계산 결과 시스템 요구량이 500,000 tpmC가 나옴. 서버 스펙 카탈로그를 보니 A사 장비 1대가 100,000 tpmC를 지원함. 따라서 A사 장비 5대를 병렬로 묶어 도입(Scale-out)하기로 결정함.
    *   **흔한 오해/주의점**: "클라우드 쓰면 오토스케일링 되니까 Sizing 필요 없는 거 아님?" $\rightarrow$ **오답**. 클라우드라도 초기 Base Capacity를 잘못 잡으면 스케일 아웃이 발생하기 전에 시스템이 먼저 죽어버리거나(Cold Start), 무한 스케일 아웃으로 클라우드 요금 폭탄(Bill Shock)을 맞음. 클라우드에서도 FinOps 관점의 Sizing은 필수임.
*   **연결 개념**: Peak TPS, tpmC(Transaction Processing Performance Council), BMT(Benchmark Test), NIA 산정 지침, FinOps

## 📝 【답안용】 서술 골격

> **💡 핵심 인사이트**
> *   **본질**: 비즈니스 요구사항(추상적 트래픽)을 하드웨어 성능 규격(물리적 자원량: tpmC, GB, TB)으로 매핑하는 **정량적 용량 계획(Capacity Planning)**.
> *   **가치**: 근거 없는 H/W 오버프로비저닝을 방지하여 IT 투자 대비 효율(ROI)을 극대화하고, 피크 타임 서비스 연속성을 보장함.
> *   **판단 포인트**: 단순히 수식을 푸는 것을 넘어, 클러스터링 오버헤드, 미래 데이터 증가율(CAGR), 목표 자원 여유율(Headroom) 등의 **보정 계수(Correction Factor)**를 얼마나 타당하게 적용하느냐가 Sizing의 핵심.

### Ⅰ. 인프라 투자의 나침반, 하드웨어 규모 산정 개요
*   **정의**: 목표 시스템의 SLA(응답시간, 가용성 등)를 충족하기 위해 요구되는 최적의 서버 시스템 크기(CPU, Memory, Disk, Network)를 객관적 산식에 의해 산출하는 일련의 과정.
*   **산정 기준**: 
    *   **TPS 기반 (Transaction)**: 온라인 거래가 빈번한 OLTP 시스템 (금융, 커머스).
    *   **사용자 수 기반 (Concurrent User)**: 정적인 콘텐츠 조회가 많은 Web/Portal 시스템.

### Ⅱ. 컴포넌트별 세부 산정 매커니즘 (NIA 지침 기준)
*   **1. CPU 산정 공식 (tpmC 방식)**
    *   `요구 tpmC = (Peak TPS × 60) × 업무가중치 × 여유율 × 클러스터 보정 / 목표 이용률`
    *   **Peak TPS**: 일일 총 트랜잭션을 분석하여 도출한 최고점 트래픽.
    *   **목표 이용률**: 병목(Queueing)을 막기 위해 통상 70% 이하로 설정.
*   **2. Memory 산정 공식**
    *   `요구 RAM = OS/SW 기본 메모리 + (동시 사용자 수 × Session Size) + Buffer Cache`
    *   Swap 현상을 방지하기 위해 사용량 비례 변수(Session)와 I/O 최적화 변수(Cache)를 모두 포함.
*   **3. Disk 산정 공식**
    *   `요구 Storage = Base Data × (1 + CAGR)^n × (RAID/Backup 보정율)`
    *   연평균 데이터 증가율(CAGR)을 고려하여 시스템 수명 주기(통상 3~5년) 동안의 용량 확보.

### Ⅲ. 규모 산정 4단계 수행 프로세스
1.  **환경 분석**: As-Is 성능 데이터 분석, 목표 업무 특성(OLTP vs Batch) 및 To-Be 요구사항(SLA) 정의.
2.  **기초 산정**: 동시 사용자 및 Peak TPS 도출 후 표준 산식 적용.
3.  **계수 보정**: 시스템 가용성(HA/DR), 미래 확장성(성장률), 피크 변동성을 반영한 팩터(Factor) 보정.
4.  **검토 확정**: 도출된 수치(tpmC, 메모리)를 벤더의 H/W 스펙표(Benchmark Data)와 대조하여 실제 장비 모델 및 대수 확정.

### Ⅳ. 정확한 Sizing을 위한 보정 계수(Correction Factor)의 이해
*   **피크 보정(Peak Factor)**: 평상시 대비 특정 이벤트 발생 시의 트래픽 폭증률 (통상 1.2~1.5).
*   **클러스터 보정(Cluster Factor)**: Active-Active 이중화 시 노드 간 Heartbeat 및 동기화 통신으로 발생하는 성능 오버헤드 보정 (통상 1.1~1.3).
*   **여유율(Headroom)**: 산정되지 않은 백그라운드 프로세스(백업, 배치) 작동을 위한 기본 여유 공간.

### Ⅴ. 이론적 한계 극복을 위한 실증적 검증
*   이론적인 산식(Sizing)은 반드시 **BMT(Bench Mark Test)**나 **PoC(Proof of Concept)**를 통해 실제 워크로드에서의 성능을 검증받아야 함.
*   특히 CPU 아키텍처(x86 vs ARM) 전환이나 가상화(Hypervisor) 레이어 추가 시 성능 감쇄가 발생하므로 실측 기반의 보정이 필수적임.

### Ⅵ. Cloud-Native 환경의 Sizing 패러다임 변화 (FinOps)
*   과거의 `Max-Peak Sizing`(최대치 기준 도입)에서 클라우드 환경의 `Right-Sizing`(최적 Base 설정 + Auto-scaling 결합)으로 진화.
*   무한정 확장이 가능하더라도 Base Pod 용량(Limit/Request)을 잘못 Sizing하면 리소스 낭비(Bill Shock)가 발생하므로 비용 가시성(FinOps) 관점의 촘촘한 산정이 여전히 중요함.
