# 📖 【암기용】 개념 완전 이해

## 한눈에
- **개요**: CPU 이용률·메모리 사용률 측정은 단위 시간 동안 자원이 실제 사용된 비율을 user/system/iowait, used/cache/swap으로 세분화해 병목 원인과 여유 용량을 판단하는 지표
- **왜 필요한가**: 응답시간이 느려졌을 때 CPU 포화인지, 메모리 부족에 따른 swap인지, I/O 대기인지 구분해야 원인별 대응이 가능
- **핵심 직관**: 도로 정체를 볼 때 차량 대수(이용률)만 아니라 정체 원인(사고·신호·공사)을 구분해야 대책이 정확해지는 것과 같음

## 핵심 용어 정리 (내부에 등장하는 것들)
아래 항목은 답안용 Ⅰ~Ⅵ의 산식·표에 그대로 등장하므로 먼저 비유로 풀어 둔다. 상위 핵심 키워드는 **자원 사용률의 세부 구간 분해 진단**이다.

| 용어/표기 | 의미 | 비유·예 |
|:---|:---|:---|
| CPU 이용률 | 단위 시간 중 CPU가 일한 시간 비율 | 계산대 직원이 몇 % 시간 동안 일했는가 |
| us(user) | 애플리케이션 코드 실행에 쓴 CPU 비율 | 직원이 손님 응대에 쓴 시간 |
| sy(system) | 커널·시스템 콜 처리에 쓴 CPU 비율 | 직원이 내부 정산·서류에 쓴 시간 |
| wa(iowait) | 디스크·네트워크 I/O 완료를 기다린 비율 | 창고 물건 오길 기다려 멈춘 시간 |
| idle | CPU가 아무것도 안 한 유휴 비율 | 손님 없어 대기한 시간 |
| run queue(r) | 실행 대기 중인 프로세스 수(vmstat r 컬럼) | 계산대 앞에 늘어선 대기 줄 길이 |
| context switch | CPU가 프로세스를 바꿔 다는 전환 횟수 | 직원이 업무를 계속 바꿔 잡는 횟수 |
| used | 실제 프로세스가 점유한 메모리 | 창고에서 물건이 실제 찬 선반 |
| buffer/cache | 재사용 위해 커널이 잡아둔 메모리 | 자주 쓰는 물건을 앞칸에 둔 여유분 |
| free | 즉시 할당 가능한 미사용 메모리 | 완전히 빈 선반 |
| swap in/out | 메모리 부족 시 디스크로 페이지를 밀어냄 | 창고가 꽉 차 외부 컨테이너로 이동 |
| page fault | 필요한 페이지가 메모리에 없어 로드하는 사건 | 찾는 물건이 앞칸에 없어 창고에서 꺼냄 |

## 깊이 이해
- **배경·문제의식**: CPU 이용률 100%는 포화지만 원인은 연산 과다일 수도, context switch 과다일 수도 있음. 메모리 사용률이 높아도 buffer/cache면 정상이고 swap 발생이면 실제 병목임
- **작동 원리(어떻게+왜)**: `sar`·`vmstat`·`top`·`mpstat`이 `/proc/stat`의 CPU tick(us/sy/wa/idle)과 `/proc/meminfo`의 메모리 페이지 상태를 주기적으로 샘플링함. 커널이 누적한 tick 차이를 수집 간격으로 나눠 비율을 산출하기 때문에, used와 buffer/cache를 나눠 봐야 실사용과 재사용 캐시를 구분할 수 있음
- **비유**: CPU 이용률은 계산대 직원이 몇 % 시간 동안 일했는지, 메모리는 창고 선반이 몇 % 찼는지에 비유됨
- **구체 예시**: CPU us 60%·sy 25%·wa 10%면 애플리케이션 연산보다 커널 처리와 I/O 대기 비중이 큼을 의미. 이때 run queue가 코어 수를 넘고 context switch가 급증하면 대기 지연이 실제 병목임
- **흔한 오해**: CPU 이용률 70% 미만이라고 늘 안전한 것은 아님. run queue 길이·context switch·swap in/out을 함께 봐야 대기 지연과 메모리 병목을 놓치지 않음. free가 작아도 buffer/cache가 크면 회수 가능하므로 정상일 수 있음

## 연결 개념
- 병목 분석 — CPU·메모리 세부 지표로 병목 원인 후보를 좁히는 선행 단계
- 하드웨어 규모 산정 — 이용률 목표치를 기반으로 서버 대수 산정
- APM(011) — 애플리케이션 구간 지표와 결합해 자원 병목 원인 특정

# 📝 【답안용】 시험 답안 템플릿

## 핵심 인사이트 (3줄 요약)

> 1. **본질**: CPU·메모리 이용률 측정은 자원 사용 비율을 us/sy/wa/idle, used/cache/swap 단위로 세분화해 산출하는 것임.
> 2. **가치**: 병목 원인을 연산 과다·커널 오버헤드·I/O 대기·메모리 부족 중 어디인지 구분해 정확한 대책을 세움.
> 3. **판단 포인트**: 이용률 절대 수치보다 run queue 길이·context switch·swap in/out 발생 여부가 실질 병목 판단 기준임.

## 출제 의도 및 답안 포인트

| 출제 의도 | 반드시 짚을 핵심 | 감점 회피 포인트 |
|:---|:---|:---|
| 측정 항목 이해 확인 | us/sy/wa/idle, used/cache/swap | CPU·메모리를 단일 퍼센트로만 설명 |
| 병목 원인 구분 역량 확인 | run queue, context switch, page fault | 이용률 높음=무조건 증설로 단정 |
| 측정 도구 활용 확인 | sar, vmstat, top, /proc | 도구명 나열만 하고 판단 기준 누락 |

> 요약: 이 문제는 이용률 수치 자체보다 세부 구간 분해와 병목 원인 판단 근거를 요구함.

## Ⅰ. 개요 및 필요성

- 개요: 단위 시간 동안 CPU·메모리 자원의 실제 사용 비율을 세부 항목으로 분해해 측정하는 지표
- 배경: 단일 퍼센트 수치만으로는 연산 과다·I/O 대기·메모리 부족을 구분할 수 없음
- 필요성: 병목 원인별 대응책 수립과 하드웨어 규모 산정의 실측 근거 확보에 필수

---

## Ⅱ. 구조 및 구성요소

```text
자원 사용 이벤트 -> 커널 카운터 수집 -> 샘플링 도구(sar/vmstat/top) -> 지표 집계 -> 병목 판정
  커널 카운터 분기: user / system / iowait / swap
```

| 구성요소 | 역할 | 특이사항 |
|:---|:---|:---|
| 커널 카운터 | CPU tick·메모리 페이지 상태 기록 | /proc/stat, /proc/meminfo |
| 샘플링 도구 | 주기적 수치 수집 | sar, vmstat, top, mpstat |
| 집계·시각화 | 시계열 추이·임계값 비교 | Grafana, Zabbix |
| 병목 판정 로직 | run queue·swap 발생 여부 판단 | 임계값, 추세 분석 |

> 요약: CPU·메모리 이용률 측정은 커널 카운터, 샘플링 도구, 집계·판정 단계로 구성됨.

---

## Ⅲ. 동작원리 및 흐름도

```text
수집 주기 도래 -> 커널 카운터 읽기 -> us/sy/wa/idle 분리
  -> used/cache/free/swap 분리 -> run queue·context switch 결합 -> 병목 원인 판정
```

- 1단계: 샘플링 도구가 1~5초 주기마다 /proc의 CPU tick과 메모리 페이지 상태를 조회함
- 2단계: 도구가 CPU 시간을 us·sy·wa·idle 비율로 분리하며 합계가 100%가 되도록 정규화함
- 3단계: 도구가 메모리를 used·buffer/cache·free·swap in/out으로 분리해 실사용과 캐시를 구분함
- 4단계: 판정 로직이 run queue·context switch와 결합해 병목 원인을 연산·커널·I/O·메모리 중 하나로 판정함

> 요약: 샘플링 도구가 커널 카운터를 세부 항목으로 분리한 뒤 대기 지표와 결합해 병목 원인을 판정함.

---

## Ⅳ. 특징

- CPU는 시간 구간으로 분해함: us·sy·wa·idle로 나눠 연산·커널·I/O 대기 중 어디에 시간이 쏠렸는지 드러냄
- 메모리는 사용 목적으로 분해함: used·buffer/cache·free·swap으로 나눠 실사용과 회수 가능 캐시를 구분함
- 대기 지표가 병목 신호임: run queue 길이 증가·context switch 급증·swap in/out 발생이 실질 포화 신호임
- 절대 수치가 안전을 보장하지 않음: 이용률 70% 미만이어도 run queue가 코어 수를 넘으면 대기 지연이 존재함
- 지속시간이 판단 기준임: 순간 스파이크와 지속 포화를 이동평균·지속시간으로 구분해야 오탐을 피함

## Ⅴ. 심화 비교 및 적용 판단

| 구분 | 단일 이용률 퍼센트 확인 | 세부 항목 분해 측정 |
|:---|:---|:---|
| 관측 단위 | CPU·메모리 총 사용률만 | us/sy/wa, used/cache/swap |
| 병목 특정 | 원인 미상, 증설로 직행 | 연산·I/O·메모리 원인 구분 |
| 증설 판단 | 임계값 초과 시 즉시 증설 | run queue·swap 근거 기반 판단 |
| 오탐 위험 | 순간 스파이크를 포화로 오판 | 이동평균·지속시간으로 통제 |

> 요약: 단일 이용률보다 세부 항목 분해와 지속시간 기준이 병목 원인 특정과 증설 판단을 정확하게 함.

- 리스크 — 오탐 증설: 순간 스파이크를 포화로 오판 — 대응: 5분 이동평균 기반 판정, 확인 지표 지속시간 5분 이상
- 리스크 — 메모리 부족 미탐지: free만 보고 swap 누락 — 대응: swap in/out 별도 모니터링, 확인 지표 swap 발생 0회 목표
- 리스크 — I/O 병목 오판: iowait을 CPU 부족으로 오인 — 대응: iowait과 디스크 latency 교차 확인, 확인 지표 disk await ms

- 지표 — CPU 이용률: 평상시 70% 이하·피크 85% 이하 — 측정: sar -u, mpstat
- 지표 — 메모리 사용률: swap 발생 0회 유지 — 측정: sar -r, vmstat
- 지표 — 대기 상태: run queue 길이 코어 수 이하 — 측정: vmstat r 컬럼

## Ⅵ. 실무 적용 및 결론

**적용 방안 3개 (필수 — 단계별 또는 항목별):**
1. sar·vmstat·mpstat으로 us/sy/wa, used/cache/swap을 5초 주기로 수집하고 5분 이동평균으로 판정함
2. CPU 이용률 평상시 70%·피크 85% 이하를 기준으로 설정하고 초과 지속 5분 이상일 때 증설 검토를 트리거함
3. swap in/out 발생 시 즉시 알람을 발송하고 메모리 증설 또는 애플리케이션 메모리 누수 점검을 병행함

**결론 (2줄):**
- 기술사 판단: wa·run queue가 높으면 I/O·대기 병목이므로 디스크·구조 개선을, us가 높으면 연산 병목이므로 CPU 증설·코드 최적화를 선택해야 함
- 향후 방향: eBPF 기반 세밀한 커널 이벤트 수집과 AIOps 이상 탐지로 병목 원인 자동 분류가 확대됨
