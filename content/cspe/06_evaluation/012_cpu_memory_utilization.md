# 📖 【암기용】 개념 완전 이해

> 목적: CPU·메모리 이용률을 단순 퍼센트 숫자가 아니라, 병목 원인을 구분하는 측정 근거로 이해하게 만든다.

## 한눈에
- **개요**: CPU 이용률·메모리 사용률은 단위 시간 동안 자원이 실제로 사용된 비율을 측정해 병목과 여유 용량을 판단하는 지표다.
- **왜 필요한가**: 응답시간이 느려졌을 때 CPU 포화인지, 메모리 부족으로 인한 swap인지, I/O 대기인지 구분해야 원인별 대응이 가능하다.
- **핵심 직관**: 도로 정체를 볼 때 차량 대수(이용률)와 정체 원인(사고, 신호, 공사)을 구분해야 대책이 정확해지는 것과 같다.

## 깊이 이해
- **배경·문제의식**: CPU 이용률 100%는 포화 상태를 의미하지만, 원인은 연산 과다일 수도, context switching 과다일 수도 있다.
- **배경·문제의식**: 메모리 사용률이 높아도 캐시 사용이면 정상이고, swap 발생이면 실제 병목이다.
- **작동 원리**: `sar`, `vmstat`, `top`, `/proc/stat`은 user/system/idle/iowait CPU 시간 비율을 주기적으로 샘플링한다.
- **작동 원리**: 메모리는 used, buffer/cache, free, swap in/out을 구분해 실사용과 캐시를 나눠 본다.
- **비유**: CPU 이용률은 계산대 직원이 몇 % 시간 동안 일했는지, 메모리는 창고 선반이 몇 % 찼는지에 비유된다.
- **구체 예시**: 예시로 CPU user 60%, system 25%, iowait 10%면 애플리케이션 연산보다 커널 처리와 I/O 대기가 상당 비중을 차지한다고 판단한다.
- **흔한 오해·주의점**: CPU 이용률 70% 미만이라고 항상 안전한 것은 아니다.
- **흔한 오해·주의점**: run queue 길이와 context switch 횟수를 함께 봐야 대기 지연을 놓치지 않는다.

## 연결 개념
- 병목 분석 — CPU·메모리 지표로 병목 원인 후보를 좁히는 선행 단계
- 하드웨어 규모 산정 — 이용률 목표치를 기반으로 서버 대수 산정
- APM — 애플리케이션 구간 지표와 결합해 자원 병목 원인 특정

# 📝 【답안용】 시험 답안 템플릿

> 목적: CPU·메모리 이용률 측정 항목, 도구, 병목 판단 기준을 시험 답안으로 전개한다.
> 핵심: 이용률 수치 자체보다 user/system/iowait, used/cache/swap 구분이 병목 판단의 핵심이다.

## 핵심 인사이트 (3줄 요약)

> 1. **본질**: CPU·메모리 이용률 측정은 단위 시간 동안 자원 사용 비율을 user/system/iowait, used/cache/swap 단위로 세분화해 산출하는 것이다.
> 2. **가치**: 자원 병목의 원인을 연산 과다, 커널 오버헤드, I/O 대기, 메모리 부족 중 어디인지 구분해 정확한 개선 대책을 세운다.
> 3. **판단 포인트**: 이용률 절대 수치보다 run queue 길이, context switch, swap in/out 발생 여부가 실질 병목 판단 기준이다.

## 출제 의도 및 답안 포인트

| 출제 의도 | 반드시 짚을 핵심 | 감점 회피 포인트 |
|:---|:---|:---|
| 측정 항목 이해 확인 | user/system/idle/iowait, used/cache/swap | CPU·메모리를 단일 퍼센트로만 설명 |
| 병목 원인 구분 역량 확인 | run queue, context switch, page fault | 이용률 높음 = 무조건 증설로 단정 |
| 측정 도구 활용 확인 | sar, vmstat, top, /proc | 도구명 나열만 하고 판단 기준 누락 |

> 요약: 이 문제는 이용률 수치 자체보다 세부 구간 분해와 병목 원인 판단 근거를 요구한다.

---

## Ⅰ. 개요 및 필요성

- 정의: 단위 시간 동안 CPU·메모리 자원이 실제 사용된 비율을 세분화해 측정하는 지표
- 배경: 단일 퍼센트 수치만으로는 연산 과다, I/O 대기, 메모리 부족을 구분할 수 없음
- 필요성: 병목 원인별 대응책 수립과 하드웨어 규모 산정의 실측 근거 확보에 필수

---

## Ⅱ. 구조 및 구성요소

```text
자원 사용 이벤트 -> 커널 카운터 수집 -> 샘플링 도구(sar/vmstat/top) -> 지표 집계 -> 병목 판정
                                     / user / system / iowait / swap
```

| 구성요소 | 역할 | 특이사항 |
|:---|:---|:---|
| 커널 카운터 | CPU tick, 메모리 페이지 상태 기록 | /proc/stat, /proc/meminfo |
| 샘플링 도구 | 주기적 수치 수집 | sar, vmstat, top, mpstat |
| 집계·시각화 | 시계열 추이와 임계값 비교 | Grafana, Zabbix |
| 병목 판정 로직 | run queue, swap 발생 여부 판단 | 임계값, 추세 분석 |

> 요약: CPU·메모리 이용률 측정은 커널 카운터, 샘플링 도구, 집계·판정 단계로 구성된다.

---

## Ⅲ. 동작원리 및 흐름도

```text
수집 주기 도래 -> 커널 카운터 읽기 -> user/system/iowait 분리 -> used/cache/swap 분리 -> 병목 원인 판정
```

| 단계 | 처리 내용 | 검증 기준 |
|:---:|:---|:---|
| 1 | 수집 주기마다 CPU tick, 메모리 페이지 상태 조회 | 수집 주기 1~5초 |
| 2 | user, system, iowait, idle 비율 분리 | 각 항목 합계 100% |
| 3 | used, buffer/cache, free, swap in/out 분리 | swap 발생 여부 |
| 4 | run queue, context switch와 결합해 병목 판정 | 임계값 초과 지속시간 |

> 요약: CPU·메모리 이용률 측정은 커널 카운터를 세부 항목으로 분리한 뒤 병목 원인을 판정하는 순서로 진행된다.

---

## Ⅳ. 특징

| 구분 | CPU 이용률 | 메모리 사용률 | 수치 컬럼 |
|:---|:---|:---|:---|
| 세부 구분 | user, system, iowait, idle | used, buffer/cache, free, swap | CPU 70% 이하 권장 |
| 병목 신호 | run queue 길이 증가 | swap in/out 발생 | swap 0 유지 목표 |
| 측정 도구 | sar -u, mpstat, top | sar -r, vmstat, free | 수집 주기 1~5초 |

> 요약: CPU는 시간 구간 분해, 메모리는 사용 목적 분해가 병목 판단의 핵심 특징이다.

---

## Ⅴ. 심화 비교 및 적용 판단

| 비교 축 | 기존/대안 | 본 키워드 | 선택 기준 |
|:---|:---|:---|:---|
| 구조 | 단일 이용률 퍼센트 확인 | user/system/iowait, used/cache/swap 분해 | 병목 원인 특정 필요 여부 |
| 비용/성능 | 이용률 초과 시 즉시 증설 | run queue·swap 근거 기반 증설 판단 | 증설 비용과 실측 근거 |
| 운영/위험 | 임계값 단순 경보 | 추세·지속시간 기반 경보 | 일시 스파이크와 지속 포화 구분 |

> 요약: 단순 이용률 임계값보다 세부 항목 분해와 지속시간 기준으로 증설을 판단한다.

| 리스크 | 원인 | 대응 방안 | 확인 지표 |
|:---|:---|:---|:---|
| 오탐 증설 | 순간 스파이크를 포화로 오판 | 5분 이동평균 기반 판정 | 지속시간 5분 이상 |
| 메모리 부족 미탐지 | free 수치만 확인하고 swap 누락 | swap in/out 별도 모니터링 | swap 발생 횟수 0 목표 |
| I/O 병목 오판 | iowait을 CPU 부족으로 오인 | iowait과 디스크 latency 교차 확인 | disk await ms |

> 요약: CPU·메모리 병목 판단 리스크는 이동평균, swap 별도 관측, iowait·디스크 교차 확인으로 통제한다.

| 점검 항목 | 목표 기준 | 측정 방법 |
|:---|:---|:---|
| CPU 이용률 | 평상시 70% 이하, 피크 85% 이하 | sar -u, mpstat |
| 메모리 사용률 | swap 발생 0회 유지 | sar -r, vmstat |
| 병목 대응 | run queue 길이 CPU 코어 수 이하 | vmstat r 컬럼 |

> 요약: CPU·메모리 측정 성과는 이용률 임계값 준수와 swap·run queue 이상 징후 부재로 판단한다.

## Ⅵ. 실무 적용 및 결론

**적용 방안 3개 (필수 — 단계별 또는 항목별):**
1. sar, vmstat, mpstat으로 user/system/iowait, used/cache/swap을 5초 주기로 수집하고 5분 이동평균으로 판정함
2. CPU 이용률 평상시 70% 이하, 피크 85% 이하를 기준으로 설정하고 초과 지속 5분 이상일 때 증설 검토를 트리거함
3. swap in/out 발생 시 즉시 알람을 발송하고 메모리 증설 또는 애플리케이션 메모리 누수 점검을 병행함

**결론 (2줄):**
- 기술사 판단: 이용률 단일 수치보다 user/system/iowait, used/cache/swap 세부 분해가 병목 원인 판단의 핵심임
- 향후 방향: eBPF 기반 세밀한 커널 이벤트 수집과 AIOps 이상 탐지로 병목 원인 자동 분류가 확대됨
