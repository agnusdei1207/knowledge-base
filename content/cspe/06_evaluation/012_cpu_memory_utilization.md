# 📖 【암기용】 개념 완전 이해

## 한눈에
- **개요**: CPU 이용률 및 메모리 사용률 측정은 시스템의 물리 자원이 얼마나 효율적으로 사용되고 있는지를 정량화하고, **자원 고갈에 따른 병목 현상을 진단**하는 가장 기본적인 성능 관리 활동이다.
- **왜 필요한가**: 단순히 "시스템이 느리다"는 현상 뒤에 숨겨진 **"연산 능력이 부족한가(CPU)", "작업 공간이 부족한가(Memory)", "기다림이 긴가(I/O Wait)"**와 같은 구체적인 원인을 파악하기 위함이다.
- **핵심 직관**: **"직원의 업무량과 책상의 여유 공간"**. 직원이 쉴 새 없이 움직이면(High CPU) 손님 대기가 길어지고, 책상에 서류가 꽉 차면(High Memory) 업무 속도가 급격히 떨어진다.

## 핵심 용어 정리

| 용어/표기 | 의미 | 기술적 포인트 |
|:---|:---|:---|
| **CPU User (%us)** | 애플리케이션(User Space) 실행 비율 | 실제 비즈니스 로직 수행 시간 |
| **CPU System (%sy)** | 커널(Kernel Space) 처리 비율 | 시스템 콜, 컨텍스트 스위칭 오버헤드 |
| **I/O Wait (%wa)** | I/O 처리가 완료될 때까지 CPU가 대기한 비율 | 디스크/네트워크 병목의 강력한 징후 |
| **Load Average** | 실행 대기 중인 프로세스 수의 평균 | 시스템 전체의 부하 정도 (코어 수와 비교) |
| **Used / Free / Cache** | 실제 사용, 미사용, 캐시용 메모리 구분 | Linux의 'Free'는 작아도 'Cache'는 여유분임 |
| **Swap In/Out** | 메모리 부족 시 디스크를 메모리처럼 사용 | 성능 저하의 결정적 원인 (Thrashing 위험) |

## 깊이 이해
- **CPU 이용률의 함정**: CPU가 100%라고 해서 항상 나쁜 것은 아니다. 병렬 처리가 잘 되어 효율적으로 자원을 쓰고 있는 상태일 수도 있다. 중요한 것은 **Run Queue(실행 대기열)**의 길이다. 코어 수보다 대기열이 길어지면 그때부터 실제 지연이 발생한다.
- **메모리 측정의 오해 (Free vs Available)**: 리눅스 커널은 남는 메모리를 최대한 캐시로 활용한다. 따라서 `free` 명령의 `free` 수치가 낮다고 메모리 부족으로 단정하면 안 된다. **`available` 수치**와 **Swap 발생 여부**를 보아야 한다.
- **비유 (도서관 책상)**:
  - **CPU**: 사서의 책 정리 속도.
  - **Memory**: 열람실 책상의 수.
  - **Cache**: 자주 보는 책을 책상 위에 미리 꺼내둔 것.
  - **Swap**: 책상이 모자라 멀리 있는 창고(Disk)에 책을 가지러 가는 것. (엄청나게 느려짐)
- **구체 예시 (병목 판단)**:
  - `%us`는 낮은데 `%sy`가 높다 → 시스템 콜 과다 또는 과도한 컨텍스트 스위칭 의심.
  - `%wa`가 10% 이상 지속된다 → 디스크 I/O 속도가 CPU를 못 따라가고 있음.

## 연결 개념
- **병목 분석(004)**: 자원 이용률을 바탕으로 병목 지점 특정.
- **용량 계획(058)**: 현재 이용률 추이를 기반으로 미래 증설 시점 예측.
- **응답 시간 분해(002)**: 자원 이용률과 응답 시간 사이의 비선형 관계 분석.

# 📝 【답안용】 시험 답안 템플릿

## 핵심 인사이트 (3줄 요약)

> 1. **본질**: CPU와 메모리의 세부 지표(User/System/Wait, Used/Cache/Swap)를 분석하여 시스템의 **자원 포화도(Saturation)와 병목 원인**을 규명하는 활동임.
> 2. **판단 기준**: CPU는 단순 이용률보다 **Load Average 및 Run Queue**를, 메모리는 Free 영역보다 **Available 영역 및 Swap 발생 여부**를 핵심 지표로 삼음.
> 3. **최적화**: 지표별 임계치(Knee Point)를 설정하고, 자원 부족 시 **Scale-up(스펙 상향)** 또는 **Scale-out(대수 증설)** 등의 인프라 대응 전략을 수립함.

## 출제 의도 및 답안 포인트

| 출제 의도 | 반드시 짚을 핵심 | 감점 회피 포인트 |
|:---|:---|:---|
| 자원별 세부 측정 항목 이해 | CPU(%us, %sy, %wa), Memory(Used, Shared, Cache) | 단순히 "CPU 80% 이상" 식의 단편적 서술 지양 |
| 병목 현상 진단 역량 | I/O Wait의 의미, Swap 발생의 위험성 | CPU 사용량이 높으면 무조건 나쁘다고 단정하지 말 것 |
| 측정 도구 및 명령어 활용 | vmstat, iostat, sar, top, free | 명령어 나열에 그치지 말고 출력값 해석 방법 제시 |

## Ⅰ. CPU 및 메모리 이용률 측정의 개요

### 1. 정의
- 운영체제 커널이 제공하는 자원 사용 통계 정보를 주기적으로 수집하여, 시스템의 부하 상태와 성능 한계를 분석하는 기법

### 2. 목적
- **가용성 보장**: 자원 고갈(OOM, CPU Saturation)로 인한 시스템 다운 예방
- **Sizing 검증**: 현재 할당된 하드웨어 사양의 적정성 평가 및 증설 근거 확보

---

## Ⅱ. CPU 이용률 측정 지표 및 분석 방법

### 1. 세부 항목별 의미 (Mnemonic: U-S-I-D)

| 항목 | 의미 | 분석 포인트 |
|:---|:---|:---|
| **User (%us)** | 유저 영역 프로세스 실행 | 애플리케이션 로직 부하, 연산 집약적 작업 |
| **System (%sy)** | 커널 영역 프로세스 실행 | 인터럽트 처리, 컨텍스트 스위칭 과다 의심 |
| **I/O Wait (%wa)** | 입출력 완료 대기 시간 | 디스크/네트워크 지연, 동기식 I/O 병목 |
| **Idle (%id)** | 유휴 시간 | 시스템의 여유 용량 (Headroom) |

### 2. 부하 판단의 핵심: Load Average
- 실행 중이거나 실행을 기다리는 프로세스의 수
- **기준**: Load Average > CPU 코어 수 이면 시스템 정체(Congestion) 발생으로 판단

---

## Ⅲ. 메모리 사용률 측정 및 상태 진단

### 1. 리눅스 메모리 구조 및 측정 지표

```text
 [ Total Memory ]
 +-----------------------+-----------------------+-----------------------+
 |   Used (Active App)   |   Buff/Cache (Disk)   |     Free (Literal)    |
 +-----------------------+-----------------------+-----------------------+
            ^                        ^
            |                        +-- 실제로는 'Available'에 포함됨
            +---------------------------+
```

### 2. 메모리 부족 신호: Swap & Page Fault
- **Swap Out**: 메모리 부족 시 덜 쓰는 데이터를 디스크로 이동 (성능 저하의 시초)
- **Thrashing**: 과도한 Swap Out/In으로 인해 CPU가 실제 일은 못 하고 메모리 관리만 하는 상태
- **OOM (Out Of Memory) Killer**: 메모리 임계치 도달 시 커널이 강제로 프로세스를 종료함

---

## Ⅳ. 주요 측정 도구 및 활용 시나리오

### 1. 실시간 모니터링 도구 비교

| 도구 | 주요 확인 지표 | 특장점 |
|:---|:---|:---|
| **top / htop** | 프로세스별 자원 점유율 | 직관적, 특정 프로세스 추적 용이 |
| **vmstat** | r(대기열), swpd(스왑), free | 시스템 전체 자원 흐름을 한눈에 파악 |
| **iostat** | %util, await, svctm | 디스크 I/O 병목 분석의 정석 |
| **sar** | 과거 시계열 데이터 저장 | 장애 시점의 사후 분석(Post-mortem) 필수 |

### 2. 진단 시나리오
- **RT 증가 + %us 높음**: 애플리케이션 로직 튜닝 또는 Scale-up 필요
- **RT 증가 + %wa 높음**: 인덱스 튜닝, DB 캐시 확대, 스토리지 교체 검토
- **Free 낮음 + Swap 발생**: 메모리 증설 혹은 Memory Leak 점검

---

## Ⅴ. 자원 이용률 관리 가이드라인

- **임계치(Threshold)**: 평상시 70% 이하 유지, 피크 시 85% 상한선 관리
- **지속성**: 순간적인 스파이크(Spike)보다는 일정 시간(예: 5분 이상) 지속되는 포화를 경계
- **안전 마진(Headroom)**: 갑작스러운 부하 유입을 대비한 15~20%의 유휴 자원 상시 확보

---

## Ⅵ. 결론 및 제언

- 자원 이용률 측정은 시스템의 **'건강 검진'**과 같으며, 단일 수치보다는 지표 간의 **상관관계(Correlation)** 분석이 중요함.
- 클라우드 네이티브 환경에서는 개별 서버 지표를 넘어, 컨테이너 단위의 자원 제한(Limit/Request)과 전체 클러스터의 자원 효율성(Efficiency) 관점으로 패러다임이 이동 중임.

### 🔀 문제 유형별 목차 전환 (이 키워드 출제 시)

| 유형 | Ⅱ·Ⅲ 강조 (기술/항목) | Ⅳ·Ⅴ 강조 (진단/대응) |
|:---|:---|:---|
| **설명형** | CPU/Memory 세부 항목 정의, vmstat 출력값 해석 | 임계치 설정 기준, 자원 포화 시 증상 |
| **해결형** | 병목 지점 탐색 절차 (CPU->Mem->I/O) | 원인별 인프라/애플리케이션 대응 방안 |

> 요약: 자원 이용률 측정은 성능 분석의 출발점이며, 시스템의 안정성과 효율성 사이의 균형을 찾는 핵심 나침반임.
