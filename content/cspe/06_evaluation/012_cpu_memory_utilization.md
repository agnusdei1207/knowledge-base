## 미리 알고가기

- CPU Utilization: CPU가 idle이 아닌 상태로 일한 시간의 비율임
- Load Average: 실행 중이거나 실행 대기 중인 작업 수의 평균임
- Run Queue: CPU를 배정받기 위해 기다리는 실행 가능 작업 큐임
- RSS: 프로세스가 실제 물리 메모리에 점유한 크기임
- Swap: 메모리 부족 시 디스크를 메모리처럼 사용하는 영역이며 지연을 크게 키울 수 있음

## Ⅰ. 개요

- **정의/개념**: CPU 이용률과 메모리 사용률 측정은 운영체제 자원 점유와 대기 상태를 수집해 애플리케이션 병목과 용량 여유를 판단하는 성능 분석 활동임
- **배경/필요성**: 높은 사용률만으로 병목을 단정하면 실제 대기, 누수, I/O 지연을 놓칠 수 있으므로 사용률과 대기 지표를 함께 봐야 함

## Ⅱ. 특징

- CPU 사용률은 바쁜 정도를 보여 주지만 Run Queue를 같이 봐야 CPU 대기 여부를 알 수 있음
- 메모리 사용률은 cache와 buffer 때문에 높게 보일 수 있어 RSS, swap, page fault와 함께 해석해야 함
- CPU 병목과 I/O 대기는 모두 응답시간을 늘리지만 확인해야 할 지표가 다름
- 컨테이너 환경에서는 노드 전체 사용률보다 request, limit, throttling 지표가 더 직접적인 원인이 될 수 있음

## Ⅲ. 종류 및 비교

| 판단 기준 | CPU 지표 | 메모리 지표 |
|:---|:---|:---|
| 측정 대상 | 연산 수행과 실행 대기 상태 | 프로세스 점유, 캐시, swap 상태 |
| 대표 지표 | `%us`, `%sy`, load average, run queue | RSS, heap, page fault, swap in/out |
| 병목 신호 | 높은 사용률과 Run Queue 증가 | swap 발생, OOM, GC pause 증가 |
| 대응 방향 | 코드 경로 조정, 병렬도 조정, scale-out | 누수 제거, 캐시 조정, heap·메모리 증설 |

## Ⅳ. 구성요소 및 구조

| 구성요소 | 설명 |
|:---|:---|
| OS 지표 | CPU mode, load, memory, swap을 수집해 자원 상태의 기준 데이터를 만듦 |
| 프로세스 지표 | PID별 CPU, RSS, thread 수를 확인해 자원 점유 주체를 찾음 |
| 런타임 지표 | JVM heap, GC, thread pool 같은 애플리케이션 내부 지표로 원인을 좁힘 |
| 컨테이너 지표 | limit, request, throttling, OOMKilled를 확인해 격리 환경의 제약을 반영함 |

```text
+-----------+     +-----------+     +-----------+     +-----------+
| OS 지표     | --> | 프로세스 식별 | --> | 런타임 확인  | --> | 원인 판정    |
+-----------+     +-----------+     +-----------+     +-----------+
```

## Ⅴ. 원리 및 절차 흐름도

```text
+-----------+     +-----------+     +-----------+     +-----------+
| 사용률 확인  | --> | 대기 지표 확인 | --> | 점유 주체 식별 | --> | 개선 검증    |
+-----------+     +-----------+     +-----------+     +-----------+
```

1. **사용률 확인**: CPU와 메모리 사용률이 평소보다 증가했는지 확인함
2. **대기 지표 확인**: Run Queue, swap, page fault, throttling으로 실제 병목 여부를 봄
3. **점유 주체 식별**: 프로세스와 스레드 단위로 자원을 많이 쓰는 대상을 찾음
4. **개선 검증**: 변경 후 응답시간, 오류율, 자원 대기 지표가 줄었는지 확인함

## Ⅵ. 실무 적용 및 유의점

1. CPU 90% 상황에서도 Run Queue가 낮으면 즉시 증설보다 처리량과 지연을 먼저 봐야 하므로 load average, run queue, p95 latency를 함께 확인함
2. 메모리 사용률이 높아도 page cache 때문일 수 있으므로 swap, major page fault, OOMKilled, GC pause를 같이 확인해 누수와 정상 캐시를 구분함

## Ⅶ. 결론

CPU와 메모리 측정은 사용률 숫자를 보는 일이 아니라 사용 중인지, 기다리는지, 제한에 막혔는지를 구분해 병목 여부를 판단하는 절차임.

## 작성 근거(검토용)

- 자원 지표는 오판 가능성이 크므로 사용률과 대기 지표를 분리해 설명함
- 비유적 표현을 제거하고 OS, 프로세스, 런타임, 컨테이너 지표로 구체화함
- 결론은 측정의 역할을 병목 판단 절차로 정리해 추상 표현을 피함
