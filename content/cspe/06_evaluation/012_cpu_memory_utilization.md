## 📖 【암기용】 핵심 요약

*   **한눈에**: 시스템의 기초 체력인 CPU와 메모리가 얼마나 효율적으로(또는 혹사당하며) 사용되고 있는지 세부 지표를 통해 측정하고, **병목(Bottleneck)의 근본 원인을 진단**하는 가장 기본적인 관측 활동.
*   **깊이 이해**:
    *   **배경**: "시스템이 느려요"라는 막연한 현상 뒤에는 "연산 능력이 부족한가?(CPU)", "작업 공간이 부족한가?(Memory)", 아니면 "디스크를 기다리느라 멈춰있는가?(I/O Wait)"라는 구체적인 원인이 숨어 있으며, 이를 정확히 해부해야 함.
    *   **작동 원리 (CPU)**: CPU 사용률은 크게 `%us(사용자 앱 로직)`, `%sy(커널/OS 통신)`, `%wa(디스크 I/O 대기)`로 나뉨. 총사용률이 100%라도 `%us`가 높으면 자원을 잘 쓰는 것이지만, `%wa`나 `%sy`가 높으면 시스템 구조적 병목 상태임.
    *   **작동 원리 (Memory)**: 리눅스는 남는 메모리를 무조건 디스크 캐시(Cache)로 끌어다 씀. 따라서 `Free`가 0이라고 메모리 부족이 아님. 진짜 메모리가 부족하면 디스크를 메모리처럼 쓰는 **Swap**이 발생하며, 이때부터 성능이 수천 배 느려지는 **Thrashing(스래싱)** 현상이 발생함.
    *   **비유**: **도서관 사서와 책상**. 
        *   **CPU**: 사서의 업무 처리 속도.
        *   **Memory**: 책상의 넓이.
        *   **Cache**: 자주 찾는 책을 책상 위에 미리 쌓아둔 것.
        *   **Swap**: 책상이 꽉 차서 지하 창고(Disk)에 책을 가지러 뛰어갔다 오는 것. (시간 낭비의 주범)
    *   **흔한 오해/주의점**: "CPU 이용률 90%니까 당장 서버 늘리자!" → **안티패턴**. 대기열(Load Average, Run Queue)을 같이 봐야 함. CPU가 90%여도 큐에 대기가 없으면 그냥 일처리를 매우 효율적으로 하고 있는 상태일 수 있음.
*   **연결 개념**: 병목 분석(Bottleneck Analysis), USE Method, APM, OOM(Out Of Memory), Context Switching, `top`, `vmstat`

## 📝 【답안용】 서술 골격

> **💡 핵심 인사이트**
> *   **본질**: 겉으로 드러나는 단일 숫자(예: CPU 80%)가 아닌, 내부 구성 요소(User, Sys, Wait)와 대기열(Queue) 상태를 입체적으로 해석하는 과정.
> *   **가치**: 불필요한 하드웨어 스펙업(Scale-up) 비용을 낭비하기 전, 애플리케이션 코드 튜닝이나 아키텍처 개선으로 해결할 수 있는 영역인지 판별하는 근거.
> *   **판단 포인트**: CPU의 **I/O Wait** 지표와 메모리의 **Swap In/Out** 발생 여부가 시스템 포화 상태(Saturation)를 경고하는 가장 강력한 레드 플래그(Red Flag).

### Ⅰ. 성능 트러블슈팅의 첫걸음, 자원 이용률 측정 개요
*   **정의**: OS 커널에서 제공하는 CPU 및 메모리의 상태 지표를 주기적으로 수집하여, 애플리케이션의 자원 점유 효율성과 인프라의 여유 용량(Headroom)을 평가하는 활동.
*   **목적**: 병목(Bottleneck) 구간의 조기 식별, 인프라 용량 산정(Capacity Sizing), 자원 고갈에 따른 시스템 다운(System Crash) 예방.

### Ⅱ. CPU 이용률(Utilization) 핵심 지표 분석
*   **세부 구성 (top/vmstat 기준)**:
    *   `%us (User)`: 사용자 프로세스 연산 처리 비율. 높을수록 시스템이 본연의 비즈니스 로직에 집중하고 있다는 의미.
    *   `%sy (System)`: 커널 모드 처리 비율. 너무 높다면 잦은 Context Switching이나 과도한 System Call 발생 의심.
    *   `%wa (I/O Wait)`: 디스크나 네트워크의 I/O가 끝날 때까지 CPU가 아무 일도 못 하고 대기한 비율. 디스크/네트워크 병목의 강력한 증거.
    *   `%id (Idle)`: 순수 유휴 상태 비율.
*   **Load Average (대기열)**: 실행 대기 중인 프로세스의 평균 수. `Load Avg > 논리적 코어 수` 이면 처리가 지연되고(Queueing) 있음을 의미.

### Ⅲ. Memory 사용률 구조 및 진단 포인트
*   **리눅스 메모리 구조 (free 기준)**:
    *   `Used`: 애플리케이션이 명시적으로 할당받아 사용 중인 실 메모리.
    *   `Buff/Cache`: OS가 파일 I/O 속도 향상을 위해 램의 잔여 공간을 활용 중인 캐시 영역.
    *   `Available`: 새로운 프로세스 기동 시 즉시 할당 가능한 실질적 여유 공간 (Free + 회수 가능한 Cache).
*   **위험 신호**:
    *   **Swap Activity**: 메모리 부족 시 데이터를 디스크(Swap Space)로 밀어내는(Swap-out) 현상. 디스크 I/O를 유발하여 치명적 응답 지연 발생.
    *   **OOM Killer**: 가용 메모리가 극단적으로 부족해질 경우, 커널이 임의의 프로세스(보통 메모리 점유가 높은 DB나 WAS)를 강제 종료함.

### Ⅳ. USE Method 기반 자원 병목 진단 시나리오
| 관측 증상 | Utilization(이용률) | Saturation(포화) | 조치/튜닝 방향 |
| :--- | :--- | :--- | :--- |
| **CPU 병목** | `%us` 지속 90% 이상 | `Load Avg` 수치 급증 | Scale-out(서버 증설), 비효율적 반복 루프 제거 |
| **I/O 병목** | `%wa` 지속 20% 이상 | Disk Queue 증가 | 인덱스 튜닝으로 DB I/O 축소, SSD 교체, 캐시 서버(Redis) 도입 |
| **Mem 병목** | `Used` 지속 90% 이상 | `Swap In/Out` 급증 | Memory Leak(메모리 누수) 코드 수정, RAM 증설 |

### Ⅴ. 클라우드 네이티브 환경에서의 자원 모니터링 변화
*   **cgroups 기반 격리**: Docker/K8s 환경에서는 호스트 머신의 전체 자원 대신, 컨테이너에 할당된 `Limit` 대비 사용률 수집이 필수.
*   **OOMKilled 컨테이너**: K8s 환경에서 애플리케이션이 메모리 Limit을 초과하면 즉각 `OOMKilled` 상태가 되며 재시작되므로, Limit 설정의 정밀한 최적화(Right-sizing) 요구.
