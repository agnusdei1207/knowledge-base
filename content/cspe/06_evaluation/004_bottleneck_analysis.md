# 📖 【암기용】 개념 완전 이해

## 한눈에
- **개요**: 병목 분석(Bottleneck Analysis)은 **직렬 처리 경로에서 전체 처리량이 가장 느린 단일 자원(병목)에 의해 상한이 정해진다는 제약이론**에 기반해, 그 자원을 식별·해소하는 성능 진단 방법론이다.
- **왜 필요한가**: 성능을 균등하게 개선하면 병목이 아닌 자원에 투자해 효과가 0에 가깝고, 병목 한 곳만 풀어야 전체 처리량이 실제로 올라가기 때문이다.
- **핵심 직관**: 여러 관이 이어진 파이프라인에서 물의 총 흐름은 가장 좁은 관 하나가 결정한다 — 다른 관을 넓혀도 좁은 관을 그대로 두면 흐름은 변하지 않는다.

## 핵심 용어 정리 (내부에 등장하는 것들)

답안에 등장하는 용어를 먼저 비유와 함께 못 박는다. 이용률·대기행렬 등 기초는 001·005에서 정의했으므로 여기서는 진단 관점으로 연결한다. 맨 위가 상위 키워드다.

| 용어/표기 | 의미 | 비유·예 |
|:---|:---|:---|
| 병목(Bottleneck) | 전체 처리량 상한을 지배하는 가장 느린 자원 | 파이프라인에서 가장 좁은 관 |
| 제약이론(TOC) | 시스템 성능은 제약(가장 약한 고리)이 좌우한다는 이론 | 사슬의 세기는 가장 약한 고리가 결정 |
| 처리량 상한 | 직렬 경로 처리량 = min(각 단계 처리율) | 릴레이 속도는 가장 느린 주자가 좌우 |
| 자원 포화(Saturation) | 자원 이용률이 100%에 도달해 더 못 받는 상태 | 꽉 찬 창구 — 새 손님은 줄만 늘림 |
| 이용률 ρ | 자원이 바쁜 시간 비율 (001·005 참조) | 창구가 쉬지 않고 일한 비율 |
| USE 방법 | 자원별 Utilization·Saturation·Errors를 함께 보는 점검법 | 이용률·대기·오류 3종 계기판 |
| 핫스팟(Hotspot) | 부하가 집중돼 시간을 가장 많이 쓰는 코드·자원 구간 | 프로파일러가 빨갛게 칠하는 구간 |
| 병목 이동(풍선 효과) | 병목 해소 시 다음으로 느린 자원이 새 병목이 됨 | 풍선 한쪽 누르면 다른 쪽이 부풂 |

## 깊이 이해
- **배경·문제의식**: 성능 지표(001)로 "느리다"를 감지해도, 여러 자원(CPU·메모리·디스크 I/O·네트워크·DB) 중 어디가 원인인지 모르면 개선 대상을 특정할 수 없다. 병목 분석은 "가장 느린 한 곳"을 찾는 데 집중한다.
- **작동 원리(왜 한 자원이 전체를 지배하는가)**: 요청이 여러 단계를 직렬로 거치면 전체 처리량은 각 단계 처리율의 최솟값, 즉 처리량 = min(μ₁, μ₂, …)로 묶인다. 가장 처리율이 낮은 단계가 먼저 이용률 100%(포화)에 도달하고, 그 앞에 큐가 쌓여 대기시간(005의 Wq)이 급증한다. 그래서 "이용률이 먼저 1에 근접하고 앞에 대기가 쌓이는 자원"이 병목 신호다.
- **식별 방법 — 이용률만으로는 부족하다(USE)**: CPU 사용률이 높다고 곧 병목은 아니다. 이용률(Utilization)·포화/대기(Saturation)·오류(Errors)를 함께 봐야 한다. 이용률이 높아도 대기 큐가 없으면 여유가 있는 것이고, 이용률이 중간이어도 큐가 쌓이면 그 자원이 병목일 수 있다.
- **비유**: 여러 톨게이트를 거치는 고속도로에서, 대기 줄이 가장 긴 톨게이트 하나가 전체 통행 속도를 정한다. 한산한 톨게이트를 아무리 넓혀도 소용없다.
- **구체 예시(워크드)**: 웹(ρ=40%)-App(ρ=50%)-DB(ρ=95%) 3계층에서 DB가 병목이다. 웹서버를 2배로 늘려도 요청은 결국 DB에서 막혀 처리량은 그대로다. DB에 인덱스·캐시·커넥션풀을 개선해 ρ를 낮추면 전체 처리량이 오른다. 단, DB를 풀면 다음으로 App(50%)이 새 병목이 될 수 있다.
- **흔한 오해·주의점**: ① 병목을 없애면 병목이 사라지는 게 아니라 다음 자원으로 "이동"한다(풍선 효과) — 개선 후 재측정이 필수다. ② 병목은 부하 패턴에 따라 바뀐다(주간엔 CPU, 야간 배치엔 디스크). ③ 이용률 최댓값만 보고 판정하면 오판한다 — 대기 큐·응답시간 기여도를 함께 봐야 한다.

## 연결 개념
- 시스템 성능 지표(001) — 병목 탐지의 입력이 되는 이용률·응답시간 지표
- 큐잉 이론(005) — 병목 자원에서 ρ→1로 대기(Wq)가 급증하는 수학적 근거
- 암달의 법칙(007) — 병렬화해도 개선 안 되는 순차 구간이 곧 새 병목이 되는 원리

# 📝 【답안용】 시험 답안 템플릿

## 핵심 인사이트 (3줄 요약)

> 1. **본질**: 병목은 직렬 경로에서 전체 처리량 상한을 지배하는 가장 느린 자원으로, 처리량=min(각 단계 처리율)임.
> 2. **가치**: 병목만 정확히 식별해 집중 개선해야 자원 투자가 실제 처리량 향상으로 연결됨.
> 3. **판단 포인트**: 이용률·대기(큐)·오류(USE)를 함께 보고 병목을 특정하며, 해소 후 병목 이동을 재측정으로 확인함.

## 출제 의도 및 답안 포인트

| 출제 의도 | 반드시 짚을 핵심 | 감점 회피 포인트 |
|:---|:---|:---|
| 병목 원리 이해 확인 | 처리량=min(단계 처리율), 포화·대기 급증 | 병목을 자원 특정 없이 추상 서술 |
| 식별 방법론 확인 | 이용률+대기+오류(USE) 교차 진단 | 이용률 최댓값만으로 단정 |
| 개선 우선순위 판단 | 병목 집중 개선·비병목 투자 보류 | 모든 자원 동시 증설 제시 |

> 요약: 정의보다 처리량 상한 원리와 USE 기반 식별·병목 이동 재측정을 보여야 함.

---

## Ⅰ. 개요 및 필요성

- 개요: 직렬 경로에서 전체 처리량을 제한하는 가장 느린 단일 자원을 식별·해소하는 진단 방법론
- 배경: 처리량은 병목 자원의 처리율을 넘을 수 없어 비병목 자원 증설은 개선 효과가 제한적임
- 필요성: 한정된 예산으로 성능을 올리려면 병목을 특정해 투자 우선순위를 정해야 효과가 발생함

---

## Ⅱ. 구조 및 구성요소

- 진단 파이프라인(선형 구조도):

```text
Workload -> 자원별 계측(CPU/Mem/Disk I/O/Network/DB)
  -> 이용률·대기(큐)·오류(USE) 수집 -> 병목 자원 식별
  -> 집중 개선 조치 -> 재측정으로 병목 이동 확인
```

| 구성요소 | 역할 | 특이사항 |
|:---|:---|:---|
| 자원 계측기 | 자원별 이용률·대기·오류 수집 | OS 카운터·APM 에이전트 |
| 병목 판정 로직 | USE 지표로 상한 지배 자원 특정 | 이용률+큐 교차 검증 |
| 프로파일러 | 코드·쿼리 핫스팟 지목 | 서비스시간 큰 구간 식별 |
| 재측정 관리 | 조치 전후 병목 이동 추적 | 풍선 효과 대응 |

> 요약: 자원별 USE 지표를 계측해 상한 지배 자원을 식별하고 개선 후 재측정함.

---

## Ⅲ. 동작원리 및 흐름도

- 식별~해소 흐름(선형 흐름도):

```text
자원별 이용률·대기·오류 수집 -> 상한 지배 자원 판정(병목 식별)
  -> 핫스팟 프로파일링 -> 병목 개선 조치 -> 재측정 -> 병목 이동 확인
```

1. 자원별 이용률·대기 큐·오류율(USE)을 동시 수집해 포화·대기 신호를 확인함
2. 이용률이 먼저 1에 근접하고 앞에 대기가 쌓이는 자원을 병목으로 판정함
3. 병목 자원을 프로파일링해 핫스팟(코드·쿼리)을 지목하고 튜닝·증설·캐시를 적용함
4. 부하테스트로 재측정해 처리량 향상과 병목이 다음 자원으로 이동했는지 확인함

---

## Ⅳ. 특징

- 전체 처리량은 병목 자원의 처리율로 상한이 묶여 비병목 개선은 효과가 제한적임
- 병목 자원은 이용률이 먼저 포화(ρ→1)하고 그 앞에 대기 큐가 급증함(005 근거)
- 이용률 단독이 아니라 대기·오류를 함께 보는 USE 관점이라야 오판을 피함
- 병목 해소 시 다음 자원이 새 병목이 되는 이동(풍선 효과)이 발생해 재측정이 필수임
- 병목은 부하 패턴에 따라 이동해 1회 식별로 고정 유효하다고 볼 수 없음

---

## Ⅴ. 심화 비교 및 적용 판단

- 균등 증설 vs 병목 집중 개선:

| 구분 | 균등·직관적 증설 | 병목 집중 개선 |
|:---|:---|:---|
| 효과 | 비병목 증설 시 처리량 불변 | 상한 자원 해소로 즉시 향상 |
| 비용 | 불필요 증설로 낭비 | 최소 투자로 최대 효과 |
| 리스크 | 병목 오판 시 재작업 | 병목 이동 미추적 시 반복 |
| 판단 | 감·관행 기반 | 이용률·대기·ROI 기반 |

> 요약: 병목을 특정해 집중 개선해야 투자 대비 처리량 향상이 극대화됨.

- 리스크와 대응(불릿):
  - 병목 오판 → 이용률만 보고 자원 증설 → USE(이용률·대기·오류) 교차 진단(확인: ρ, 큐 길이, 오류율)
  - 병목 이동 미추적 → 개선 후 재측정 생략 → 재측정을 표준 절차로 고정(확인: 개선 전후 처리량·병목 위치)
  - 과다 증설 → 비병목까지 증설 → 병목 식별 기반 선택 투자(확인: 자원별 비용 대비 개선 효과)

---

## Ⅵ. 실무 적용 및 결론

- 적용 방안:
  1. APM·OS 카운터로 자원별 이용률·대기 큐·오류를 동시 수집해 상한 지배 자원을 병목으로 식별함
  2. 병목 자원에 한정해 프로파일링 기반 튜닝·캐시·증설을 적용하고 비병목 투자는 보류함
  3. 부하테스트로 재측정해 처리량 향상과 병목 이동 여부를 확인하고 다음 병목으로 반복함
- 결론:
  - 성능 개선은 병목 식별을 선행한 뒤 해당 자원에 집중 투자해야 실제 효과가 발생함
  - 관측성 플랫폼의 자동 병목 탐지와 연계해 실시간으로 병목 이동을 추적하는 체계로 확장 필요
