## 📖 【암기용】 핵심 요약

*   **한눈에**: 병목 분석(Bottleneck Analysis)은 시스템의 전체 처리 성능을 결정짓는 가장 느린 단일 지점(The Weakest Link)을 찾아내어 개선하는 성능 진단 방법론.
*   **깊이 이해**:
    *   **배경**: 전체 시스템 성능은 가장 성능이 낮은 자원에 의해 상한(Upper Bound)이 정해짐. 병목이 아닌 지점을 개선하는 것은 전체 시스템 성능 향상에 기여하지 못하는 자원 낭비(ROI 저하)가 되기 때문에 정확한 타겟팅이 필수적임.
    *   **작동 원리**: **USE Method(Utilization, Saturation, Errors)**를 기반으로 분석. 특정 자원의 이용률(U)이 100%에 근접하고, 해당 자원을 할당받기 위해 대기열(Saturation)이 급증하는 지점이 바로 병목임.
    *   **비유**: **깔대기(Funnel)**. 입구가 좁은 깔대기에는 물을 아무리 많이 부어도 통과하는 물의 양은 깔대기 입구 크기에 맞춰짐. 깔대기 위의 물통을 키우는 것(비병목 자원 증설)보다 좁은 입구 자체를 넓히는 것(병목 해소)이 정답.
    *   **구체 예시**: 3-Tier 아키텍처에서 Web 서버 사용률 10%, WAS 사용률 20%, DB 사용률 99%인 상태. 이때 WAS 서버 100대를 증설해봐야 전체 TPS는 단 1도 오르지 않음. DB의 Slow Query를 튜닝하거나 인덱스를 추가해야 TPS가 획기적으로 상승함.
    *   **흔한 오해/주의점**: 병목 하나를 해결했다고 끝이 아님. 현재 병목을 풀면 그동안 가려져 있던 다음 단계의 느린 자원이 새로운 병목으로 떠오르는 **병목 이동(Bottleneck Shift, 풍선 효과)**이 반드시 발생함.
*   **연결 개념**: 제약 이론(TOC), USE Method, 암달의 법칙(Amdahl's Law), 대기행렬 이론(Queuing Theory), APM

## 📝 【답안용】 서술 골격

> **💡 핵심 인사이트**
> *   **본질**: 시스템 전체 처리량은 병목 자원의 처리율($min(\mu_i)$)에 의해 상한선이 결정된다는 제약 이론(TOC)에 기반.
> *   **가치**: 자원별 **USE 지표**(Utilization, Saturation, Errors)를 교차 분석하여 핀포인트 튜닝을 수행함으로써 투자 대비 효과(ROI)를 극대화.
> *   **판단 포인트**: 이용률(CPU Usage) 수치만 맹신하지 말고, 실질적인 대기열(Queue Size, Thread Blocked)이 어디서 발생하는지(Saturation)를 추적해야 함.

### Ⅰ. 성능 최적화의 나침반, 병목 분석(Bottleneck Analysis) 개요
*   **정의**: 시스템의 직렬 처리 경로 중 전체 처리량(Throughput)을 제한하고 응답 시간을 지연시키는 지배적 제약 요인을 식별하고 제거하는 성능 개선 활동.
*   **필요성**: 전체 성능 향상에 기여도가 낮은 비병목 구간의 과잉 투자를 방지하고, 포화 상태의 자원을 선제 조치하여 시스템 붕괴(System Crash) 예방.

### Ⅱ. 병목 식별 방법론: USE Method (Brendan Gregg)
*   **Utilization (이용률)**: 자원이 실제 일을 한 시간의 비율. 일반적으로 70~80% 이상 지속 시 병목 후보군으로 분류.
*   **Saturation (포화도)**: 자원 할당을 못 받아 대기 중인 작업량. **Queue(대기열)** 발생 및 증가 여부가 병목을 확정 짓는 가장 강력한 징후.
*   **Errors (오류)**: 자원 처리 중 발생한 에러 횟수. 타임아웃, Connection Drop 등의 에러는 성능 지표를 왜곡시킬 수 있으므로 병행 확인 필수.

### Ⅲ. 병목 구간 판단 및 추적 흐름도 (Decision Flow)
```text
[병목 탐지 Flow]
  ┌─ 1. End-to-End 성능 모니터링 (시스템 전체 TPS, RT 정체 확인)
  │
  ├─ 2. 자원별 Utilization 스캔 (CPU 100% 근접, Memory Swap 발생 등 후보군 도출)
  │
  ├─ 3. Saturation (대기열) 검증 ──> [Queue 미발생] → 병목 아님 (다른 자원 점검)
  │                                └> [Queue 발생]   → 🎯 병목 지점 확정
  │
  └─ 4. APM / Profiler 연동을 통한 심층 원인(Root Cause) 분석
```

### Ⅳ. 지배적 원인별 병목 유형 및 대응 전략
*   **인프라/하드웨어 병목**:
    *   **CPU**: 연산 집약적 작업. 로직 튜닝 또는 Scale-up.
    *   **Memory**: 가용 메모리 부족에 따른 Swap 발생. 증설 및 Memory Leak 수정.
    *   **Disk I/O**: 빈번한 Read/Write 경합. SSD 교체 및 로깅 레벨 조정.
*   **소프트웨어/애플리케이션 병목**:
    *   **DB**: Lock Contention, Slow Query. 인덱스 최적화 및 쿼리 리팩토링.
    *   **WAS**: Thread/Connection Pool 고갈. Pool Size 튜닝 및 비동기 처리 도입.

### Ⅴ. 병목 해소 5단계 프로세스 (제약 이론 기반)
1.  **Identify (식별)**: 시스템 내 가장 약한 고리(병목) 찾기.
2.  **Exploit (착취)**: 기존 자원을 최대한 효율적으로 사용하기(예: 코드 튜닝).
3.  **Subordinate (종속)**: 나머지 비병목 구간의 속도를 병목 구간에 맞춰 조절(예: Rate Limiting).
4.  **Elevate (확충)**: 착취로도 부족하면 자원을 증설(예: 서버 추가).
5.  **Repeat (반복)**: 병목이 타 구간으로 전이(Bottleneck Shift)되었는지 확인하고 1단계로 회귀.

### Ⅵ. Cloud-Native 환경의 실시간 모니터링 체계
*   **eBPF 기반 가시성 확보**: 커널 레벨에서 애플리케이션 수정 없이 네트워크 I/O 및 디스크 지연 등 초정밀 병목 추적.
*   **Continuous Profiling**: Pyroscope 등의 도구를 활용해 운영 환경의 CPU/Memory 핫스팟(Hotspot)을 상시 프로파일링.
