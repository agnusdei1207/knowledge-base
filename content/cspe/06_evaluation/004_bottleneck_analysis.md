## 미리 알고가기

- 병목: 전체 처리량이나 응답시간을 제한하는 가장 먼저 포화되는 자원 또는 구간임
- USE Method: Utilization, Saturation, Errors로 자원 상태를 점검하는 분석 방법임
- Saturation: 요청이 즉시 처리되지 못하고 큐나 대기 상태로 쌓이는 현상임
- Critical Path: 사용자 요청 완료 시간에 직접 영향을 주는 처리 경로임

## Ⅰ. 개요

- **정의/개념**: 병목 분석은 시스템 처리량과 응답시간을 제한하는 자원, 코드, 네트워크, 데이터 경합 구간을 지표와 추적으로 식별하는 성능 진단 활동임
- **배경/필요성**: 느린 구간을 확인하지 않고 자원을 늘리면 병목이 아닌 곳에 비용을 쓰게 되므로, 전체 지연을 결정하는 지점을 먼저 찾아야 함

## Ⅱ. 특징

- 병목은 가장 사용률이 높은 자원 하나가 아니라 포화와 오류가 함께 나타나는 구간으로 판단해야 함
- 한 병목을 제거하면 다음 제약 구간이 드러나므로 분석은 반복 수행이 필요함
- CPU, 메모리, 디스크, 네트워크 지표만으로는 애플리케이션 락과 외부 호출 병목을 놓칠 수 있음
- 요청 흐름 기준의 trace와 자원 기준의 metric을 같은 시간축에 맞춰야 원인을 좁힐 수 있음

## Ⅲ. 종류 및 비교

| 병목 위치 | 주요 증상 | 확인 지표 | 대응 방향 |
|:---|:---|:---|:---|
| CPU | Run Queue 증가와 사용자 CPU 지속 상승 | load average, run queue, `%us` | 알고리즘 개선, 병렬도 조정, 수평 확장 |
| 메모리 | GC 지연, swap, OOM 발생 | heap usage, page fault, swap in/out | 누수 제거, 캐시 크기 조정, 메모리 증설 |
| DB | slow query와 lock wait 증가 | query time, lock wait, I/O wait | 인덱스, 쿼리 개선, 트랜잭션 축소 |
| 네트워크 | 재전송과 RTT 증가 | retransmission, RTT, packet loss | 경로 점검, 윈도우 조정, 회선 증설 |

## Ⅳ. 구성요소 및 구조

| 구성요소 | 설명 |
|:---|:---|
| 지표 수집 | CPU, 메모리, 디스크, 네트워크, 애플리케이션 지표를 같은 시간 기준으로 모음 |
| 요청 추적 | Trace ID로 호출 구간과 지연 span을 연결해 사용자 지연의 실제 경로를 찾음 |
| 포화 판단 | 이용률, 대기열, 오류를 함께 보아 병목 후보와 단순 사용 증가를 구분함 |
| 개선 검증 | 변경 전후의 TPS, p95 응답시간, 오류율을 비교해 병목 제거 여부를 확인함 |

```text
+-----------+     +-----------+     +-----------+     +-----------+
| 증상 수집    | --> | 후보 식별    | --> | 원인 검증    | --> | 개선 확인    |
+-----------+     +-----------+     +-----------+     +-----------+
```

## Ⅴ. 원리 및 절차 흐름도

```text
+-----------+     +-----------+     +-----------+     +-----------+
| Utilization | --> | Saturation | --> | Errors     | --> | Trace 대조 |
+-----------+     +-----------+     +-----------+     +-----------+
```

1. **Utilization 확인**: 자원이 실제로 일한 비율을 확인해 후보를 좁힘
2. **Saturation 확인**: 큐 길이, wait time, run queue로 대기 발생 여부를 봄
3. **Errors 확인**: timeout, retry, dropped request가 병목 영향인지 확인함
4. **Trace 대조**: 사용자 요청 경로와 자원 지표 시간을 맞춰 실제 원인을 판정함

## Ⅵ. 실무 적용 및 유의점

1. 장애 대응에서는 CPU 90% 같은 단일 수치로 증설을 결정하지 말고 대기열과 오류를 함께 확인해야 하므로 utilization, saturation, error를 같은 구간에서 비교함
2. MSA 환경에서는 느린 서비스가 호출 전체를 지연시킬 수 있으므로 distributed trace에서 critical span을 찾고 p95 span duration과 retry count로 확인함

## Ⅶ. 결론

병목 분석은 가장 바쁜 자원을 찾는 절차가 아니라 사용자 지연과 처리량 한계를 실제로 만드는 포화 구간을 지표와 trace로 검증하는 절차임.

## 작성 근거(검토용)

- 병목은 평가·지표형이면서 트러블슈팅 절차가 답안 축이므로 USE Method와 trace 대조를 중심으로 구성함
- 추상 평가어를 제거하고 지표, 증상, 대응 방향으로 치환함
- 결론에서 병목을 단순 사용률이 아닌 포화 구간 검증으로 정리해 문맥상 정확한 단어를 사용함
