# 📖 【암기용】 개념 완전 이해

> 목적: 시스템 전체 성능이 가장 취약한 한 자원에 의해 결정된다는 원리를 이해하게 만든다. 시험 답안 양식이 아니라, 이해를 위한 친절한 설명이다.

## 한눈에
- **개요**: CPU·메모리·디스크 I/O·네트워크 등 여러 자원 중 이용률이 가장 높아 전체 처리량을 제한하는 자원(병목)을 찾는 절차
- **왜 필요한가**: 병목이 아닌 자원을 증설하면 비용만 늘고 성능은 개선되지 않으므로 정확한 원인 자원 식별이 필요
- **핵심 직관**: 여러 차선이 합류하는 도로에서 전체 통행 속도는 가장 좁은 차선(병목 구간)의 용량으로 결정되는 것과 같음

## 깊이 이해
- **배경·문제의식**: 성능 저하 시 CPU만 늘리거나 메모리만 늘리는 식의 직관적 대응은, 실제 병목이 디스크 I/O나 네트워크 대역폭이면 효과가 없음
- **작동 원리**: 각 자원의 이용률(ρ)은 해당 자원에 대한 요청 도착률과 자원별 서비스 요구시간(service demand)의 곱으로 계산되며, 이용률이 가장 높은 자원이 병목으로 식별됨
- **비유**: 여러 톨게이트 중 대기 줄이 가장 긴 톨게이트가 전체 도로 흐름을 늦추는 병목이 되는 것과 같음
- **구체 예시**: 예시로 웹 요청 처리 과정에서 CPU 이용률 40%, 디스크 I/O 이용률 85%, 네트워크 이용률 30%로 측정되면 디스크 I/O가 병목이며, 이 경우 CPU 증설보다 디스크 I/O 개선(SSD 전환, 인덱스 최적화)이 우선
- **흔한 오해·주의점**: 병목은 고정된 자원이 아니라 부하 패턴 변화에 따라 이동할 수 있으므로 한 번 식별했다고 지속적으로 유효하다고 가정하면 안 됨

## 연결 개념
- 처리율·대역폭 — 병목 자원이 곧 시스템 전체 처리율의 상한을 결정
- 암달의 법칙 — 병렬화 시 개선되지 않는 구간이 새로운 병목이 되는 원리
- 큐잉 이론 — 병목 자원에서 대기행렬이 형성되는 수학적 근거

# 📝 【답안용】 시험 답안 템플릿

> 목적: 시험장에서 25분에 그대로 쓰는 답안 양식. 작성방식(추상표현 금지·수치·도식·문제유형 전환)을 엄격히 지킨다.
> 핵심: 병목 분석 답안은 자원별 이용률 비교 방법, 병목이 전체 처리량을 제한하는 원리, 식별 후 개선 절차를 함께 제시한다.

## 핵심 인사이트 (3줄 요약)

> 1. **본질**: 병목은 CPU·메모리·디스크 I/O·네트워크 중 이용률(ρ)이 가장 높아 전체 처리량을 제한하는 자원이다.
> 2. **가치**: 병목 자원을 정확히 식별해야 자원 증설 투자의 효과를 실제 성능 개선으로 연결할 수 있다.
> 3. **판단 포인트**: 자원별 이용률·대기시간·큐 길이를 동시 모니터링해 이용률이 가장 높은 자원부터 개선 우선순위를 정한다.

## 출제 의도 및 답안 포인트

| 출제 의도 | 반드시 짚을 핵심 | 감점 회피 포인트 |
|:---|:---|:---|
| 병목 개념 이해 확인 | 시스템 전체 처리량은 병목 자원 용량으로 제한됨 | 병목을 특정 자원 없이 추상적으로 서술 |
| 식별 방법론 확인 | 자원별 이용률(ρ) 비교, 큐 길이·대기시간 관찰 | 이용률 수치 없이 "느린 자원을 찾는다"로만 서술 |
| 개선 우선순위 판단 확인 | 병목 자원 우선 개선, 비병목 자원 증설 지양 | 모든 자원을 동시에 증설하는 방안 제시 |

> 요약: 이 문제는 병목의 정의보다 자원별 이용률 비교를 통한 식별 절차와 우선순위 판단을 보여야 한다.

---

## Ⅰ. 개요 및 필요성

- 개요: 여러 자원 중 이용률이 가장 높아 시스템 전체 처리량을 제한하는 자원을 찾는 분석
- 원리: 시스템 처리량은 병목 자원의 처리 능력을 초과할 수 없으며, 비병목 자원 증설은 개선 효과가 제한적
- 필요성: 한정된 예산으로 성능을 개선하려면 병목 자원을 정확히 특정해 투자 우선순위를 정해야 함

---

## Ⅱ. 구조 및 구성요소

```text
Workload -> 자원별 모니터링(CPU/Memory/Disk I/O/Network)
  -> 이용률(ρ) 산출 -> 병목 자원 식별
  -> 개선 조치 적용 -> 재측정으로 병목 이동 확인
```

| 구성요소 | 역할 | 특이사항 |
|:---|:---|:---|
| 자원 모니터 | CPU·메모리·디스크·네트워크 이용률 수집 | OS 카운터, APM 에이전트 |
| 이용률 산출기 | 자원별 ρ(이용률) 계산 | ρ = 자원 사용 시간 / 전체 시간 |
| 병목 식별 로직 | 이용률 최대 자원 판정 | 큐 길이·대기시간 교차 검증 |
| 개선 이력 관리 | 조치 전후 병목 이동 추적 | 병목이 다른 자원으로 이동 가능 |

> 요약: 자원별 이용률을 지속 모니터링하고 최댓값 자원을 병목으로 식별해 개선 후 재측정한다.

---

## Ⅲ. 동작원리 및 흐름도

```text
자원별 사용 시간 측정 -> 이용률(ρ) 계산
  -> 자원 간 이용률 비교 -> 최대 이용률 자원 = 병목 식별
  -> 병목 자원 개선 조치 -> 재측정 후 병목 이동 여부 확인
```

| 단계 | 처리 내용 | 검증 기준 |
|:---:|:---|:---|
| 1 | CPU·메모리·디스크·네트워크 사용 시간 측정 | 자원별 사용률(%) |
| 2 | 자원별 이용률(ρ) 산출 및 비교 | 최대 이용률 자원 특정 |
| 3 | 병목 자원 대상 개선 조치 수립 | 증설, 튜닝, 캐시 도입 등 |
| 4 | 조치 후 재측정, 병목 이동 여부 확인 | 이용률 재분포, 신규 병목 유무 |

> 요약: 자원별 이용률을 비교해 최댓값 자원을 병목으로 식별하고, 개선 후에는 병목 이동 여부를 재확인한다.

---

## Ⅳ. 특징

| 구분 | CPU 병목 | 디스크 I/O 병목 | 수치·표준 포인트 |
|:---|:---|:---|:---|
| 증상 | CPU 사용률 90% 이상 지속 | I/O wait 비율 증가, 큐 길이 증가 | 자원별 목표 이용률 70% 이하 권장 |
| 원인 | 비효율 알고리즘, 과도한 연산 | 랜덤 I/O, 인덱스 부재, 낮은 IOPS | O(n^2) 로직, 디스크 IOPS 한계 |
| 개선 방향 | 알고리즘 최적화, 코어 증설 | SSD 전환, 인덱스 추가, 캐시 도입 | 프로파일링 결과 기반 조치 |
| 재발 가능성 | 트래픽 증가 시 재발 | 데이터량 증가 시 재발 | 정기 재측정 필요 |

> 요약: 병목 유형에 따라 증상·원인·개선 방향이 다르므로 자원별 특성에 맞는 조치가 필요하다.

## Ⅴ. 심화 비교 및 적용 판단

| 비교 축 | 단일 자원 증설 | 병목 기반 우선순위 개선 | 선택 기준 |
|:---|:---|:---|:---|
| 효과 | 병목 아닌 자원 증설 시 개선 미미 | 병목 자원 우선 개선 시 즉각 효과 | 이용률 최대 자원 우선 투자 |
| 비용 | 불필요한 증설로 비용 낭비 | 최소 투자로 최대 효과 | ROI 기준 투자 순위 결정 |
| 리스크 | 병목 오판 시 재작업 발생 | 병목 이동 미추적 시 반복 문제 | 개선 후 재측정 필수 |

> 요약: 병목 자원을 정확히 식별해 우선 개선해야 투자 대비 성능 개선 효과가 극대화된다.

| 리스크 | 원인 | 대응 방안 | 확인 지표 |
|:---|:---|:---|:---|
| 병목 오판 | 이용률 비교 없이 직관적 자원 증설 | 자원별 이용률·큐 길이 동시 모니터링 후 판단 | 자원별 ρ, 큐 길이 |
| 병목 이동 미추적 | 개선 후 재측정 생략 | 조치 후 재측정을 표준 절차로 고정 | 개선 전후 이용률 비교 |
| 과다 증설 | 병목 아닌 자원까지 증설 | 병목 식별 결과 기반 선택적 증설 | 자원별 비용 대비 개선 효과 |

> 요약: 병목 오판과 이동 미추적은 비용 낭비와 반복 성능 문제로 이어지므로 재측정 절차가 필요하다.

| 점검 항목 | 목표 기준 | 측정 방법 |
|:---|:---|:---|
| 자원별 이용률 | 목표 이용률 70% 이하 유지 | OS 카운터, APM 모니터링 |
| 병목 식별 정확도 | 개선 조치 후 처리량 실제 향상 확인 | 부하테스트 전후 비교 |
| 병목 이동 여부 | 개선 후 신규 병목 발생 유무 | 재측정, 지속 모니터링 |

> 요약: 도입 후 성공 여부는 자원별 이용률 개선, 처리량 향상, 병목 이동 여부로 판단한다.

## Ⅵ. 실무 적용 및 결론

**적용 방안 3개 (필수 — 단계별 또는 항목별):**
1. CPU·메모리·디스크 I/O·네트워크 이용률을 동시에 모니터링해 최대 이용률 자원을 병목으로 식별함
2. 병목 자원에 한정해 프로파일링·튜닝·증설을 적용하고 비병목 자원 투자는 보류함
3. 개선 조치 후 부하테스트로 재측정해 병목이 다른 자원으로 이동했는지 확인함

**결론 (2줄):**
- 기술사 판단: 성능 개선은 병목 자원 식별을 선행한 뒤 해당 자원에 집중 투자해야 효과가 있음
- 향후 방향: APM·관측성 플랫폼의 자동 병목 탐지 기능과 연계해 실시간으로 병목 이동을 추적하는 체계로 확장해야 함
