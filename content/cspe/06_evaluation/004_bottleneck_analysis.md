# 📖 【암기용】 개념 완전 이해

## 한눈에
- **개요**: 병목 분석(Bottleneck Analysis)은 시스템의 전체 처리 성능을 결정짓는 가장 느린 단일 지점(The Weakest Link)을 찾아내어 개선하는 성능 진단 방법론이다.
- **왜 필요한가**: 시스템의 전체 성능은 가장 성능이 낮은 자원에 의해 상한(Upper Bound)이 정해지기 때문에, 병목이 아닌 지점을 개선하는 것은 전체 시스템 성능 향상에 기여하지 못하는 자원 낭비가 되기 때문이다.
- **핵심 직관**: 여러 개의 파이프를 이어 붙인 수로에서 물의 흐름은 가장 직경이 좁은 파이프 하나에 의해 결정된다. 다른 넓은 파이프들을 아무리 더 넓혀봐야 물의 총 흐름량은 변하지 않는다.

## 핵심 용어 정리

| 용어/표기 | 의미 | 기술적 포인트 |
|:---|:---|:---|
| **Bottleneck** (병목) | 처리 용량이 가장 작아 전체 흐름을 막는 구간 | 임계점(Knee Point)에서 먼저 포화됨 |
| **USE Method** | Utilization, Saturation, Errors 기반 진단법 | 브렌든 그레그(Brendan Gregg)의 자원 진단법 |
| **Critical Path** | 전체 작업 완료 시간을 결정하는 최장 경로 | 병목 분석의 집중 대상 |
| **Saturation** (포화) | 자원이 100% 사용되어 요청이 대기열에 쌓임 | 병목의 가장 강력한 징후 |
| **Throughput Ceiling** | 병목에 의해 제한된 최대 처리량 상한 | 병목 해소 전까지는 넘을 수 없는 벽 |
| **Hotspot** | 부하가 집중되어 성능이 저하되는 특정 코드/영역 | 프로파일링을 통해 식별 가능 |

## 깊이 이해
- **제약 이론 (Theory of Constraints, TOC)**: 시스템의 목표 달성을 방해하는 제약 요인(병목)을 찾아내고 이를 집중적으로 개선하여 전체 성과를 극대화한다는 경영/공학 이론.
- **병목 이동 (Bottleneck Shift)**: 현재의 병목을 해결하면, 그동안 가려져 있던 다음 단계의 느린 자원이 새로운 병목으로 떠오르는 현상. (풍선 효과와 유사)
- **식별 로직 (Where is the Bottleneck?)**:
  - **이용률(Utilization)**이 100%에 근접하고,
  - **대기열(Saturation/Queue)**이 급증하며,
  - 해당 자원 앞단계에서 **백프레셔(Back-pressure)**가 발생하는 지점.
- **비유 (깔대기)**: 아무리 물을 많이 부어도(High Load) 깔대기의 좁은 입구(Bottleneck)를 통과하는 양은 일정하다. 입구 위의 물통을 키우는 것보다 입구 자체를 넓히는 것이 정답이다.
- **구체 예시 (3-Tier Architecture)**:
  - Web: 10% 사용, App: 20% 사용, DB: 99% 사용.
  - 이 경우 Web/App 서버를 100대 늘려도 DB 병목을 풀지 않으면 전체 TPS는 1도 증가하지 않는다.

## 연결 개념
- **암달의 법칙(007)**: 병렬화가 불가능한 순차 구간(병목)에 의한 성능 향상 한계.
- **큐잉 이론(005)**: 병목 지점에서 대기 행렬이 발생하는 수학적 원리.
- **응답 시간 분해(002)**: 병목이 $W_q$ 구간인지 $W_s$ 구간인지 식별하는 기초 분석.

# 📝 【답안용】 시험 답안 템플릿

## 핵심 인사이트 (3줄 요약)

> 1. **본질**: 시스템 전체 처리량은 병목 자원의 처리율($min(\mu_i)$)에 의해 상한이 결정된다는 제약 이론에 기반함.
> 2. **방법론**: 자원별 **USE 지표**(Utilization, Saturation, Errors)를 교차 분석하여 임계치 초과 및 대기열 발생 지점을 병목으로 특정함.
> 3. **최적화**: 비병목 자원에 대한 과잉 투자를 지양하고, 식별된 병목 지점에 튜닝·증설을 집중하여 ROI(투자 대비 효과)를 극대화함.

## 출제 의도 및 답안 포인트

| 출제 의도 | 반드시 짚을 핵심 | 감점 회피 포인트 |
|:---|:---|:---|
| 병목의 개념 및 원리 | 제약 이론(TOC), $Throughput = min(\mu_i)$ | 단순히 "느린 곳"이라는 모호한 서술 지양 |
| 병목 식별 방법론 | **USE Method**, Utilization vs Saturation 구분 | 이용률(CPU 사용률)만으로 병목을 단정하지 말 것 |
| 개선 프로세스 및 리스크 | 병목 해소 후 병목 이동(Shift) 가능성 | 병목을 해결하면 성능 문제가 완전히 끝난다고 서술 방지 |

---

## Ⅰ. 병목 분석(Bottleneck Analysis)의 개요

### 1. 정의
- 시스템의 직렬 처리 경로 중 전체 처리량(Throughput)을 제한하고 응답 시간을 지연시키는 지배적 제약 요인을 식별하고 제거하는 성능 개선 활동

### 2. 필요성 (ROI 관점)
- **효율적 자원 배분**: 전체 성능 향상에 기여도가 낮은 비병목 구간의 과잉 개선 방지
- **장애 예방**: 포화 상태의 자원을 선제적으로 식별하여 시스템 붕괴(System Crash) 방지

---

## Ⅱ. 병목 식별 방법론: USE Method (Brendan Gregg)

### 1. 3대 진단 지표

| 지표 | 의미 | 병목 징후 |
|:---|:---|:---|
| **Utilization** (이용률) | 자원이 실제 사용된 시간의 비율 (%) | 80~90% 상회 시 위험군 분류 |
| **Saturation** (포화) | 자원 할당을 못 받아 대기 중인 작업량 | **Queue(대기열)** 발생 시 해당 자원이 확실한 병목 |
| **Errors** (오류) | 자원 처리 중 발생한 에러 횟수 | 에러 발생 시 성능 지표 왜곡 가능성 존재 |

### 2. 병목 구간 판단 흐름 (Decision Flow)

```text
 [단계 1] 전 구간 성능 모니터링 (TPS, RT)
    ↓
 [단계 2] 자원별 이용률(U) 확인 -> 100% 근접 자원 후보군 선정
    ↓
 [단계 3] 대기열(S) 발생 여부 확인 -> 큐가 쌓이면 해당 구간을 '병목'으로 확정
    ↓
 [단계 4] 프로파일링을 통한 원인 분석 (App 로직 vs 인프라 자원)
```

---

## Ⅲ. 병목의 원인 유형 및 대응 전략

### 1. 하드웨어/인프라 병목 (Resource Bottleneck)
- **CPU**: 연산 집약적 작업 과다 → Scale-up, 알고리즘 튜닝
- **Memory**: 메모리 부족에 따른 Swap 발생 → Memory 증설, Leak 제거
- **Disk I/O**: 빈번한 Read/Write 경합 → SSD 교체, DB 인덱싱 최적화
- **Network**: 대역폭 포화 혹은 패킷 손실 → 대역폭 증설, 전송 데이터 압축

### 2. 소프트웨어/애플리케이션 병목 (Software Bottleneck)
- **Database**: Lock 경합, Slow Query → 쿼리 튜닝, Sharding, Read Replica
- **Middleware**: Thread Pool, Connection Pool 부족 → Pool 크기 최적화
- **Algorithm**: 비효율적인 루프, 불필요한 동기화(Synchronized) → 코드 리팩토링

---

## Ⅳ. 병목 해소 프로세스 및 고려사항

### 1. 5단계 개선 프로세스 (기반: 제약 이론)
1. **식별(Identify)**: 시스템 내 병목 지점을 찾음 (USE Method 활용)
2. **착취(Exploit)**: 추가 투자 없이 현재 병목 자원의 효율을 극대화함 (튜닝)
3. **종속(Subordinate)**: 비병목 자원들을 병목 자원의 속도에 맞게 조절함 (흐름 최적화)
4. **확충(Elevate)**: 병목 자원을 증설하여 물리적 한계를 높임 (Scale-up/out)
5. **반복(Repeat)**: 병목이 이동했는지 확인하고 다시 1단계로 돌아감

### 2. 병목 이동(Bottleneck Shift) 주의
- DB 병목을 풀면 그동안 쌓여있던 요청이 App 서버로 몰려 App 서버가 새로운 병목이 될 수 있음. **전 구간 재측정** 필수.

## Ⅴ. 병목 분석 결과 비교 및 시각화 (사례)

| 구분 | 개선 전 (DB 병목) | 개선 후 (병목 이동 발생) |
|:---|:---|:---|
| **Web Utilization** | 10% | 40% |
| **App Utilization** | 20% | **95% (New Bottleneck)** |
| **DB Utilization** | **98% (Bottleneck)** | 60% |
| **System TPS** | 100 TPS | 350 TPS (향상됨) |

## Ⅵ. 결론 및 제언

- 병목 분석은 **"가장 약한 고리가 전체 사슬의 강도를 결정한다"**는 사실을 인지하는 것에서 시작함.
- 실무에서는 특정 시점의 단발성 분석보다, **Continuous Profiling**과 실시간 **USE 대시보드**를 통해 병목의 변화 추이를 지속 관리하는 체계 구축이 필수적임.
