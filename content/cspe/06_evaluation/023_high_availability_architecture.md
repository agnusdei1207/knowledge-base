# 📖 【암기용】 개념 완전 이해

> 목적: Active-Active와 Active-Standby가 왜 나뉘고 각각 어떤 트레이드오프를 갖는지 이해하게 만든다. 시험 답안 양식이 아니라, 이해를 위한 친절한 설명이다.

## 한눈에
- **개요**: 고가용성 설계는 두 대 이상의 노드를 이중화해 한 노드 장애가 서비스 중단으로 이어지지 않게 하는 구조다
- **왜 필요한가**: 단일 노드는 하드웨어·소프트웨어 장애 시 즉시 서비스가 중단된다. 이중화 구조를 두면 장애 노드를 배제하고 나머지 노드로 서비스를 지속할 수 있다.
- **핵심 직관**: Active-Active는 두 계산대가 동시에 손님을 받는 구조이고, Active-Standby는 한 계산대만 열고 다른 계산대는 대기하다가 문제 생기면 여는 구조다

## 깊이 이해
- **배경·문제의식**: 가용성 99.9% 이상을 요구하는 서비스는 단일 노드 MTBF만으로는 목표를 만족하기 어렵다
- **배경·문제의식**: 이중화 없이 SLO를 세우면 오류 예산이 노드 하나의 장애만으로 소진되는 문제가 생긴다
- **작동 원리**: Active-Active는 모든 노드가 동시에 요청을 처리하며 로드밸런서가 트래픽을 분산한다
- **작동 원리**: Active-Standby는 Active 노드만 요청을 처리하고 Standby는 대기하다가 Active 장애 시 페일오버로 전환한다
- **비유**: Active-Active는 두 계산대를 동시에 열어 손님을 나눠 받는 마트이고, Active-Standby는 계산대 하나만 열고 옆 계산대 직원은 대기하다 문제 생기면 투입되는 마트다
- **구체 예시**: Active-Active 2노드 구성에서 각 노드가 정상 처리량의 50%씩 분담하다가 한 노드 장애 시 남은 노드가 100%를 단독 처리, Active-Standby 구성에서는 평상시 Standby가 0%를 처리하다 페일오버 후 100%를 인수
- **흔한 오해·주의점**: Active-Active가 항상 더 좋은 것은 아니다. 상태 동기화, 데이터 정합성 요구가 높은 시스템은 Standby 구조가 설계·검증이 단순하다
- **흔한 오해·주의점**: Active-Active 구성도 트래픽 100%를 처리하려면 각 노드가 정상 시 50% 이하 사용률을 유지해야 하며, 그렇지 않으면 장애 시 남은 노드가 과부하로 연쇄 장애를 일으킨다

## 연결 개념
- SPOF 제거 — 이중화 설계가 제거하려는 대상
- 자동 페일오버·페일백 — Active-Standby 전환을 수행하는 메커니즘
- 이중화 구성 N+1·2N·2N+1 — Active-Active/Standby를 일반화한 용량 설계 모델

# 📝 【답안용】 시험 답안 템플릿

> 목적: 시험장에서 25분에 그대로 쓰는 답안 양식. 작성방식(추상표현 금지·수치·도식·문제유형 전환)을 엄격히 지킨다.
> 핵심: 고가용성 답안은 Active-Active/Standby 구조 차이, 용량 설계, 페일오버 조건, 데이터 정합성을 함께 제시한다.

## 핵심 인사이트 (3줄 요약)

> 1. **본질**: 고가용성 설계는 노드 이중화로 단일 장애가 서비스 중단으로 전이되지 않게 하는 구조다.
> 2. **가치**: Active-Active는 자원 활용률과 처리량을, Active-Standby는 구성 단순성과 정합성 보장을 우선한다.
> 3. **판단 포인트**: 상태 동기화 복잡도와 자원 활용률 요구를 기준으로 두 구조 중 선택한다.

## 출제 의도 및 답안 포인트

| 출제 의도 | 반드시 짚을 핵심 | 감점 회피 포인트 |
|:---|:---|:---|
| 구조 차이 이해 확인 | 동시 처리 vs 대기-전환 | 두 구조를 이중화라는 말로만 뭉뚱그림 |
| 용량 설계 역량 확인 | 노드당 사용률, 장애 시 부하 재분배 | 정상 시 사용률 수치 누락 |
| 데이터 정합성 이해 확인 | 상태 동기화, split-brain 위험 | 동기화 이슈 누락 |

> 요약: 이 문제는 이중화 나열보다 자원 활용률과 정합성 트레이드오프에 따른 구조 선택 근거를 보여야 한다.

---

## Ⅰ. 개요 및 필요성

- 개요: 고가용성 설계는 노드 이중화로 단일 장애의 서비스 영향을 차단하는 아키텍처
- 배경: 단일 노드 구조는 하드웨어·소프트웨어 장애 시 즉시 서비스 중단으로 이어져 SLO 준수가 어려움
- 필요성: Active-Active·Active-Standby 중 자원 활용률과 상태 정합성 요구에 맞는 구조를 선택해야 오류 예산 소진을 방지함

---

## Ⅱ. 구조 및 구성요소

```text
Client -> LB/VIP -> Active Node A / Active Node B (Active-Active)
                  -> Active Node / Standby Node (Active-Standby)
  -> Health Check -> 상태 동기화 -> 장애 시 재분배/페일오버
```

| 구성요소 | 역할 | 특이사항 |
|:---|:---|:---|
| LB/VIP | 트래픽 분산 또는 단일 진입점 | Active-Active는 분산, Standby는 단일 경로 |
| Active Node | 정상 시 요청 처리 노드 | 정상 시 사용률 50% 이하 설계 |
| Standby Node | 평상시 대기, 장애 시 전환 노드 | 콜드/웜/핫 스탠바이로 세분화 |
| Health Check | 노드 장애 감지 | 연속 실패 임계치로 오탐 방지 |
| 상태 동기화 | 세션·데이터 정합성 유지 | 동기·비동기 복제 선택 |

> 요약: Active-Active는 분산 처리, Active-Standby는 대기-전환 구조로 노드 이중화를 구현한다.

---

## Ⅲ. 동작원리 및 흐름도

```text
정상 상태 트래픽 처리 -> Health Check 지속 -> 장애 감지
  -> Active-Active: 부하 재분배 / Active-Standby: 페일오버 전환
  -> 상태 동기화 재확인 -> 서비스 지속
```

| 단계 | 처리 내용 | 검증 기준 |
|:---:|:---|:---|
| 1 | 정상 상태에서 Active 노드(들)가 트래픽 처리 | 노드별 사용률 |
| 2 | Health Check로 장애 노드 감지 | 연속 실패 횟수(예: 3회) |
| 3 | Active-Active는 재분배, Standby는 페일오버 수행 | 전환 소요 시간 |
| 4 | 전환 후 상태 동기화 정합성 재확인 | 데이터 정합성 오류 수 |

> 요약: 장애 감지 후 Active-Active는 부하 재분배로, Active-Standby는 페일오버로 서비스를 지속한다.

---

## Ⅳ. 특징

| 구분 | Active-Active | Active-Standby | 수치·표준 포인트 |
|:---|:---|:---|:---|
| 자원 활용률 | 전 노드 활용, 정상 시 노드당 50% 이하 권장 | Standby 노드는 평상시 유휴 | 사용률 %, 유휴 자원 비율 |
| 페일오버 방식 | 부하 재분배(전환 지연 최소) | 명시적 전환(전환 지연 존재) | RTO 초·분 단위 |
| 데이터 정합성 | 양방향 동기화 복잡도 높음 | 단방향 복제로 상대적 단순 | 복제 지연(replication lag) |
| 구성 복잡도 | split-brain 위험 관리 필요 | 쿼럼·전환 로직 단순 | 쿼럼 노드 수 |

> 요약: Active-Active는 자원 효율이 높고, Active-Standby는 구성과 정합성 관리가 단순하다.

---

## Ⅴ. 심화 비교 및 적용 판단

| 비교 축 | Active-Active | Active-Standby | 선택 기준 |
|:---|:---|:---|:---|
| 구조 | 다중 노드 동시 처리 | 주-대기 노드 구조 | 처리량 요구와 정합성 요구 |
| 비용/성능 | 유휴 자원 최소, 인프라 비용 효율 | Standby 자원 유휴로 비용 증가 | 자원 활용률 목표 |
| 운영/위험 | split-brain·쿼럼 설계 필요 | 페일오버 누락·지연 위험 | 상태 동기화 신뢰도 |

> 요약: 처리량과 자원 효율이 중요하면 Active-Active, 정합성과 단순한 운영이 중요하면 Active-Standby를 선택한다.

| 리스크 | 원인 | 대응 방안 | 확인 지표 |
|:---|:---|:---|:---|
| 과부하 연쇄 장애 | 정상 시 노드 사용률을 50% 초과로 설계 | 사용률 상한 설계, 오토스케일링 병행 | 장애 후 잔존 노드 CPU/커넥션 |
| split-brain | 네트워크 분단 시 양 노드 모두 Active 판단 | 쿼럼 기반 판정 도입 | 동시 Active 판정 이벤트 수 |
| 페일오버 지연 | Standby 웜업 미비, health check 지연 | 웜 스탠바이 유지, health check 주기 단축 | 페일오버 소요 시간(RTO) |

> 요약: 고가용성 운영은 노드 사용률 상한, 쿼럼 기반 split-brain 방지, 페일오버 시간 관리로 통제한다.

| 점검 항목 | 목표 기준 | 측정 방법 |
|:---|:---|:---|
| 정상 시 노드 사용률 | 50% 이하 유지(2노드 기준) | 모니터링 대시보드 |
| 페일오버 소요 시간 | RTO 목표 이내(예: 1분 이내) | 페일오버 훈련 로그 |
| 데이터 정합성 | 복제 지연 목표 이내(예: 1초 이내) | 복제 lag 모니터링 |

> 요약: 도입 후 성공 여부는 노드 사용률 상한 준수, 페일오버 소요 시간, 복제 지연으로 판단한다.

## Ⅵ. 실무 적용 및 결론

**적용 방안 3개 (필수 — 단계별 또는 항목별):**
1. 처리량 중심 서비스는 Active-Active 2노드 이상으로 구성하고 정상 시 노드당 사용률을 50% 이하로 설계함
2. 정합성 중심 서비스는 Active-Standby로 구성하고 웜 스탠바이 유지와 자동 페일오버 체계를 결합함
3. 두 구조 모두 쿼럼 기반 split-brain 방지 로직과 정기 페일오버 훈련을 실시함

**결론 (2줄):**
- 기술사 판단: 자원 효율은 Active-Active, 정합성·단순성은 Active-Standby가 우선하며 요구사항에 따라 선택함
- 향후 방향: 멀티 리전 Active-Active와 컨센서스 기반 자동 쿼럼 판정으로 발전해야 함
