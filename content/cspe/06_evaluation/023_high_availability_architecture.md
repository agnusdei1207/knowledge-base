## 미리 알고가기

- Stateless 계층: 세션 상태를 오래 보관하지 않아 여러 노드에 쉽게 분산할 수 있는 계층임
- Stateful 계층: 데이터 정합성과 복제 방식이 가용성 구조를 직접 제한하는 계층임
- Failover: 장애가 난 주 노드 대신 대기 노드가 서비스를 이어받는 절차임
- Split Brain: 이중화 노드가 모두 자신을 주 노드로 판단해 데이터가 충돌하는 상태임

## Ⅰ. 개요

- **정의/개념**: 고가용성 설계는 일부 서버, 네트워크, 소프트웨어 구성 요소에 장애가 나더라도 대체 노드와 우회 경로로 서비스를 계속 제공하도록 구성하는 아키텍처 설계 방식임
- **배경/필요성**: 단일 장비의 높은 신뢰도만으로는 목표 가용성을 만족하기 어려우므로, 장애를 없애는 대신 장애 발생 시 서비스 중단을 짧게 만들 수 있는 구조가 필요함

## Ⅱ. 특징

- 단일 노드 장애를 전체 서비스 중단으로 확대하지 않도록 중복 자원과 자동 전환 절차를 함께 설계함
- Active-Active는 자원 활용이 높지만 장애 시 남은 노드가 추가 부하를 감당할 여유가 있어야 함
- Active-Standby는 정합성 관리가 비교적 단순하지만 대기 자원이 평소에는 유휴 상태로 남음
- 상태 없는 계층과 상태 있는 계층은 같은 방식으로 이중화하기 어려워 계층별로 다른 구조를 섞어야 함

## Ⅲ. 종류 및 비교

| 판단 기준 | Active-Active | Active-Standby |
|:---|:---|:---|
| 운영 방식 | 여러 노드가 동시에 요청을 나눠 처리함 | 주 노드가 처리하고 대기 노드가 장애 시 승계함 |
| 자원 활용 | 평상시 자원을 적극적으로 활용할 수 있음 | 대기 자원이 남아 활용률은 낮음 |
| 장애 전환 | 헬스체크와 라우팅만 맞으면 즉시 우회하기 쉬움 | 승격과 연결 전환 절차가 필요해 약간의 전환 시간이 생길 수 있음 |
| 적합한 계층 | 웹, 애플리케이션 같은 Stateless 계층에 잘 맞음 | DB, 스토리지 같은 Stateful 계층에 더 잘 맞음 |

## Ⅳ. 구성요소 및 구조

| 구성요소 | 설명 |
|:---|:---|
| 이중화 노드 | 같은 역할을 수행하는 복수 노드이며 장애 시 처리 여유를 남겨 두어야 함 |
| 상태 감시와 전환 장치 | 헬스체크, 로드밸런서, 클러스터 매니저가 장애를 감지하고 트래픽이나 역할을 바꿈 |
| 데이터 복제 구조 | 세션 저장소나 DB 복제 방식이 정합성과 복구 시간을 결정함 |
| 쿼럼과 보호 장치 | Split Brain을 막기 위한 투표 기준과 펜싱 정책이 상태 있는 계층에서 중요함 |

```text
+-------------+     +-------------+     +-------------+     +-------------+
| 이중화 노드 구성 | --> | 상태 감시 수행  | --> | 우회/승격 처리  | --> | 서비스 지속 확인 |
+-------------+     +-------------+     +-------------+     +-------------+
```

## Ⅴ. 원리 및 절차 흐름도

```text
+-------------+     +-------------+     +-------------+     +-------------+
| 장애 징후 감지   | --> | 실패 노드 격리  | --> | 트래픽 우회 또는 승격 | --> | 정합성 검증    |
+-------------+     +-------------+     +-------------+     +-------------+
```

1. **장애 징후 감지**: 헬스체크와 메트릭으로 노드 이상을 탐지함
2. **실패 노드 격리**: 장애 노드를 트래픽 경로와 클러스터 역할에서 분리함
3. **트래픽 우회 또는 승격**: 남은 Active 노드로 우회하거나 Standby 노드를 주 역할로 올림
4. **정합성 검증**: 세션, 데이터 복제, 연결 상태가 정상인지 확인함

## Ⅵ. 실무 적용 및 유의점

1. 웹과 애플리케이션 계층은 Active-Active가 유리하지만 평상시 자원을 과도하게 쓰면 장애 시 연쇄 과부하가 생기므로 노드 여유 용량과 헬스체크 정책을 함께 두고 failover success rate와 node utilization으로 확인함
2. DB와 스토리지는 Active-Standby나 통제된 동기 복제가 현실적이지만 복제 지연과 Split Brain이 정합성을 깨뜨릴 수 있으므로 쿼럼과 승격 절차를 명확히 하고 RTO와 replication lag와 split-brain incident count로 확인함

## Ⅶ. 결론

고가용성 설계의 핵심은 장애를 없애는 데 있지 않고 계층 특성에 맞는 이중화와 자동 전환으로 서비스 중단 시간을 통제하는 데 있음.
