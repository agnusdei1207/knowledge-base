## 📖 【암기용】 핵심 요약

*   **한눈에**: 시스템의 단일 노드 장애가 전체 서비스 중단으로 이어지지 않도록(SPOF 제거), 두 대 이상의 장비를 병렬로 배치하여 **서비스 연속성(99.99% 이상)**을 보장하는 아키텍처 설계 기법.
*   **깊이 이해**:
    *   **배경**: 서버 부품(디스크, 파워)은 언젠가 반드시 고장 남(MTBF의 한계). 서버 1대가 죽어도 사용자는 전혀 눈치채지 못하게 하려면, 쌍둥이 서버를 옆에 두고 즉시 역할을 넘겨받는 '이중화(Redundancy)'가 유일한 해답임.
    *   **작동 원리**: 크게 두 가지 패턴.
        1) **Active-Active**: 두 서버가 50:50으로 일을 나눠서 하다가, 한 놈이 죽으면 남은 놈이 100%를 다 처리함.
        2) **Active-Standby**: 한 놈이 100% 일하고, 한 놈은 놀면서 대기함. 일하던 놈이 죽으면 대기하던 놈이 깨어나서 100%를 이어받음.
    *   **비유**: **마트 계산대**.
        *   **Active-Active**: 1번, 2번 계산대 모두 열어두고 손님을 받음. 1번 직원이 쓰러지면 모든 손님이 2번으로 감. (효율적이지만 2번 직원이 과로사할 위험 있음)
        *   **Active-Standby**: 1번 계산대만 열고, 2번 직원은 휴게실에서 대기함. 1번 직원이 쓰러지면 2번 직원이 튀어나옴. (안전하지만 인건비 낭비)
    *   **구체 예시**: 웹 서버(WAS)는 세션(상태)이 없으므로 로드밸런서를 앞에 두고 **Active-Active**로 묶기 쉬움. 반면, 데이터베이스(DB)는 양쪽에서 동시에 쓰기(Write)를 하면 데이터가 꼬이므로, 주 DB만 쓰기를 전담하는 **Active-Standby**로 구성하는 것이 정석임.
    *   **흔한 오해/주의점**: "Active-Active로 2대를 뒀으니 각각 90%씩 꽉꽉 채워서 일 시키자!" $\rightarrow$ **가장 위험한 안티패턴(Cascading Failure)**. 한 대가 죽으면 남은 한 대가 180%의 트래픽을 받아야 하므로 즉시 연쇄 다운됨. 이중화된 Active-Active 노드의 평상시 목표 CPU 사용률은 반드시 **50% 이하**로 설계해야 함.
*   **연결 개념**: SPOF(Single Point of Failure), Failover(페일오버), Split-Brain(스플릿 브레인), 로드밸런서(L4/L7), Quorum(쿼럼)

## 📝 【답안용】 서술 골격

> **💡 핵심 인사이트**
> *   **본질**: 장애를 막는 것(Fault Prevention)이 아니라, 장애가 나더라도 정상적으로 복구/우회하는 **결함 허용(Fault Tolerance)과 복원력(Resiliency)** 체계.
> *   **가치**: 계획되지 않은 다운타임을 최소화하여 비즈니스 서비스 연속성(BCP)과 목표 가용성(SLA 99.99%)을 달성함.
> *   **판단 포인트**: 트래픽 처리 효율(Active-Active)과 데이터 정합성 보장(Active-Standby) 사이의 Trade-off를 이해하고, 티어(Web/WAS/DB)별로 적합한 아키텍처를 혼합 적용하는 것이 설계의 핵심.

### Ⅰ. 중단 없는 서비스의 뼈대, 고가용성(HA) 아키텍처 개요
*   **정의**: 시스템의 하드웨어, 소프트웨어, 네트워크 구성 요소 중 일부에 장애가 발생하더라도, 예비 노드로 작업을 즉시 이관하여 사용자에게 정상적인 서비스를 지속 제공하는 설계 기법.
*   **핵심 원리**: 단일 장애점(SPOF) 제거, 구성 요소의 이중화(Redundancy), 지속적인 상태 감시(Health Check) 및 자동 장애 조치(Failover).

### Ⅱ. HA 핵심 패턴: Active-Active vs Active-Standby 비교
| 비교 항목 | Active-Active (Load Balancing) | Active-Standby (Failover) |
| :--- | :--- | :--- |
| **운영 방식** | 모든 노드가 동시에 트래픽 분산 처리 | 주 노드 처리, 부 노드 대기(대기 중 복제) |
| **자원 효율성** | **높음** (모든 자원 상시 활용) | **낮음** (Standby 노드 유휴 상태) |
| **장애 전환 시간** | **즉시 (Zero-Downtime)** | **수 초 ~ 수 분 소요 (RTO 발생)** |
| **데이터 정합성** | 양방향 동기화(Sync) 복잡도 높음 | 단방향 복제(Replication)로 관리 용이 |
| **적용 레이어** | Web, WAS 등 **Stateless** 계층 | DBMS, Storage 등 **Stateful** 계층 |

### Ⅲ. Active-Standby의 3가지 대기 모델 (Standby Types)
*   **Cold Standby**: 대기 장비의 전원을 끄거나 서비스를 올려두지 않은 상태. 장애 시 수동으로 켜고 데이터를 복구함. (비용 최저, RTO 가장 김)
*   **Warm Standby**: 대기 장비 전원 ON, OS 및 DB 인스턴스 기동 상태로 비동기 데이터 복제 중. 장애 시 DB Recovery 후 서비스 투입. (비용/RTO 중간)
*   **Hot Standby**: 대기 장비가 주 장비와 실시간 동기화(Sync) 됨. 장애 시 L4/L7 스위치나 클러스터링 솔루션에 의해 수 초 내에 자동 Failover 됨. (비용 최고, RTO 최소)

### Ⅳ. 고가용성 아키텍처 설계 시 치명적 리스크와 해결책
*   **연쇄 장애 (Cascading Failure)**: 
    *   원인: Active-Active에서 평소 노드별 CPU 사용률이 70%일 때, A 노드 장애 시 B 노드가 140% 부하를 맞아 연쇄 다운됨.
    *   해결: 정상 시 각 노드의 자원 사용률 상한을 **50% 이하(N+1 구성 시 $\frac{100}{N}$%)**로 강제하는 용량 설계(Capacity Planning) 필수.
*   **스플릿 브레인 (Split-Brain)**:
    *   원인: 클러스터 간 하트비트(Heartbeat) 네트워크만 단절되고 양쪽 서버는 살아있을 때, 서로가 "상대방이 죽었으니 내가 Active다!"라고 판단하여 DB 양쪽에서 데이터 오염이 발생.
    *   해결: 홀수 개의 노드로 투표하는 **쿼럼(Quorum)** 도입, 펜싱(STONITH: 상대 서버 전원을 강제로 내림) 기술 적용.

### Ⅴ. 클라우드 네이티브 환경의 고가용성 패러다임
*   **Auto-Scaling (Scale-out)**: 전통적인 1:1 고정 이중화를 넘어, 트래픽과 장애 상태에 따라 컨테이너(Pod)를 무한대로 늘리고 줄이는 동적 HA 구성.
*   **Multi-AZ 및 Multi-Region**: 데이터센터 전체 화재(재해)에 대비하여, 지리적으로 분리된 가용 영역(AZ)에 Active-Active 인스턴스를 분산 배치(Multi-AZ)하는 클라우드 표준 아키텍처 적용.
