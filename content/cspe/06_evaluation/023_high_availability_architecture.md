# 📖 【암기용】 개념 완전 이해

## 한눈에
- **개요**: 고가용성(HA) 설계는 **시스템 이중화 아키텍처**로, 두 대 이상의 노드를 배치해 단일 노드 장애가 서비스 중단으로 전이되지 않게 하는 구조임. 대표 패턴이 Active-Active와 Active-Standby임.
- **왜 필요한가**: 단일 노드는 하드웨어·소프트웨어 장애 시 즉시 서비스가 중단됨. 가용성 99.99%(019)를 달성하려면 장애 노드를 배제하고 나머지 노드로 서비스를 지속하는 이중화 구조가 필수임.
- **핵심 직관**: Active-Active는 두 계산대가 동시에 손님을 받는 구조, Active-Standby는 한 계산대만 열고 다른 하나는 대기하다가 문제 시 교대하는 구조임.

## 핵심 용어 정리 (내부에 등장하는 것들)

019·018이 가용성 계산·신뢰성 지표를, 024가 SPOF 제거를, 028이 자동 페일오버를 다루므로 여기서는 HA 구조 고유의 이중화·전환 용어에 집중함.

| 용어/표기 | 의미 | 비유·예 |
|:---|:---|:---|
| 고가용성(HA, 상위 키워드) | 단일 장애 시에도 서비스를 지속하는 이중화 아키텍처 | 비상 발전기가 있는 건물 |
| Active-Active | 모든 노드가 동시에 요청을 처리하는 구조 | 두 계산대 동시 운영 |
| Active-Standby | 주 노드만 처리, 대기 노드는 장애 시 전환 | 교대 계산대 운영 |
| 페일오버(Failover) | Active→Standby로 자동 전환(028 상세) | 계산대 직원 교대 |
| Health Check | 노드 생존 여부를 주기적으로 확인하는 검사 | 계산대 직원이 자리에 있는지 확인 |
| Split-brain | 네트워크 분단 시 양 노드가 모두 Active로 판단하는 장애(027 상세) | 두 계산대가 서로 상대가 없어졌다고 오판 |
| 쿼럼(Quorum) | 과반수 투표로 정상 파티션을 결정하는 메커니즘(027 상세) | 3명 중 2명의 동의로 결정 |
| 웜 스탠바이 | Standby가 OS·앱까지 구동 상태로 대기 | 엔진 걸고 대기하는 차 |

## 깊이 이해
- **배경·문제의식**: (019 참조) 가용성 99.99%는 연간 52.6분의 다운타임만 허용하므로 단일 노드 MTBF(018)만으로는 달성이 어려움. 이중화 없이 SLO(021)를 설정하면 노드 하나의 장애만으로 오류 예산(022)이 즉시 소진됨.
- **작동 원리 — Active-Active**:
  - 모든 노드가 동시에 요청을 처리하며, 로드밸런서(LB)가 트래픽을 분산함.
  - 정상 시 각 노드 사용률을 50% 이하로 설계해야 한 노드 장애 시 나머지가 100%를 처리할 수 있음.
  - 양방향 상태 동기화가 필요해 데이터 정합성 관리가 복잡하며 split-brain(027) 위험이 존재함.
  - 장점: 자원 활용률 극대화, 전환 지연 최소(부하 재분배만 수행).
- **작동 원리 — Active-Standby**:
  - Active 노드만 요청을 처리하고, Standby는 대기 상태로 유지함.
  - Active 장애 시 Health Check가 감지 → 페일오버(028)로 Standby가 Active로 전환.
  - 단방향 복제(Active→Standby)로 동기화가 상대적으로 단순하나, 페일오버 시 전환 지연(RTO)이 발생함.
  - Standby 유형: 콜드(전원 꺼짐, 수십 분), 웜(OS·앱 구동, 수 분), 핫(실시간 동기화, 수 초).
- **비유**: Active-Active는 2차선 도로(양쪽 다 차가 다니고, 한쪽 막히면 다른 쪽이 전량 흡수), Active-Standby는 1차선 도로 + 비상 우회로(평소 1차선만, 사고 시 우회로 개방).
- **구체 예시**: DB 이중화 — Active-Active: MySQL Group Replication(다중 마스터, 양방향 동기화). Active-Standby: PostgreSQL Streaming Replication(주→복제 단방향, 장애 시 promote). 정상 시 각 노드 CPU 40% 이하 유지, 장애 시 단일 노드 80%까지 허용하도록 용량 설계.
- **흔한 오해·주의점**: ① Active-Active가 항상 우월한 것이 아님 — 상태 동기화 복잡도와 split-brain(027) 위험이 커 정합성 요구가 높은 시스템에서는 Active-Standby가 적합. ② Active-Active도 정상 시 노드당 사용률 50% 초과 설계면 장애 시 연쇄 과부하(cascading failure) 발생. ③ 이중화만으로 SPOF(024)가 모두 제거되지 않음 — LB·네트워크·스토리지도 이중화해야 함.

## 연결 개념
- **SPOF 제거 (024)**: HA가 해결하려는 대상. 024가 SPOF 식별 방법, 023이 이중화 구조를 담당.
- **자동 페일오버·페일백 (028)**: Active-Standby 전환을 수행하는 메커니즘.
- **Split-brain·쿼럼 (027)**: Active-Active에서 네트워크 분단 시 발생하는 장애와 해결책.
- **이중화 구성 N+1·2N (030)**: Active-Active/Standby를 용량 관점에서 일반화한 설계 모델.

# 📝 【답안용】 시험 답안 템플릿

## 핵심 인사이트 (3줄 요약)

> 1. **본질**: 고가용성 설계는 노드 이중화로 단일 장애의 서비스 전이를 차단하며, Active-Active와 Active-Standby가 대표 패턴임.
> 2. **가치**: Active-Active는 자원 활용률 극대화·전환 지연 최소, Active-Standby는 구성 단순성·정합성 보장을 우선함.
> 3. **판단 포인트**: 상태 동기화 복잡도(split-brain 위험)와 자원 활용률 요구를 기준으로 구조를 선택함.

## 출제 의도 및 답안 포인트

| 출제 의도 | 반드시 짚을 핵심 | 감점 회피 포인트 |
|:---|:---|:---|
| 구조 차이 이해 | 동시 처리(AA) vs 대기-전환(AS) 원리 | 이중화라는 용어로만 뭉뚱그림 |
| 용량 설계 역량 | 정상 시 노드당 사용률 50% 이하 설계 | 정상 시 사용률 수치 누락 |
| 정합성·Split-brain | 양방향 동기화 복잡도, 쿼럼 필요성 | 동기화 이슈·split-brain 누락 |

> 요약: Active-Active/Standby 구조 차이 + 용량 설계(사용률 50%) + 정합성·split-brain 트레이드오프를 보여야 함.

---

## Ⅰ. 개요 및 필요성

- 개요: 노드 이중화로 단일 장애의 서비스 중단 전이를 차단하는 아키텍처
- 배경: 단일 노드 구조는 하나의 장애로 SLO(021) 오류 예산(022)이 즉시 소진되어 가용성 99.99%(019) 달성 불가
- 필요성: 자원 활용률·상태 정합성 요구에 따라 Active-Active 또는 Active-Standby를 선택하는 설계 판단 필수

---

## Ⅱ. 구조 및 구성요소

```text
Client -> LB/VIP
  -> Active-Active: Node A + Node B (동시 처리, 부하 분산)
  -> Active-Standby: Active Node + Standby Node (대기-전환)
     -> Health Check -> 장애 감지 -> 페일오버(028)/부하 재분배
     -> 상태 동기화(양방향/단방향)
```

| 구성요소 | 역할 | 특이사항 |
|:---|:---|:---|
| LB/VIP | 트래픽 분산(AA) 또는 단일 진입점(AS) | AA는 라운드로빈, AS는 VIP 전환 |
| Active Node | 정상 시 요청 처리 노드 | 정상 시 사용률 50% 이하 설계 |
| Standby Node | 대기 노드, 장애 시 전환 | 콜드/웜/핫 스탠바이 세분화 |
| Health Check | 노드 생존 확인(연속 실패 임계치) | 오탐 방지 위해 3회 연속 실패 등 |
| 상태 동기화 | 세션·데이터 정합성 유지 | AA=양방향(복잡), AS=단방향(단순) |

> 요약: AA는 LB 기반 분산 처리, AS는 대기-전환 구조이며 Health Check와 상태 동기화가 공통 필수 요소임.

---

## Ⅲ. 동작원리 및 흐름도

```text
정상 트래픽 처리 -> Health Check 지속 -> 장애 감지
  -> AA: 장애 노드 제외, 부하 재분배
  -> AS: 페일오버(028) 전환
  -> 상태 동기화 재확인 -> 서비스 지속
```

1. 정상 상태에서 Active 노드(AA: 전체, AS: 주 노드)가 트래픽을 처리하고, 상태 동기화를 지속함
2. Health Check가 노드 장애를 감지함(연속 실패 3회 등 임계치 기반, 오탐 방지)
3. AA는 장애 노드를 LB에서 제외하고 부하를 재분배, AS는 페일오버(028)로 Standby를 Active로 전환함
4. 전환 후 상태 동기화 정합성을 재확인하고, 복구된 노드는 페일백 절차로 원래 역할에 복귀함

> 요약: 장애 감지 → AA는 부하 재분배, AS는 페일오버 전환 → 동기화 재확인 순으로 서비스를 지속함.

---

## Ⅳ. 특징

- 자원 활용률: AA는 전 노드 활용(정상 시 50% 이하), AS는 Standby 유휴로 자원 낭비 발생
- 전환 지연: AA는 부하 재분배만으로 전환 지연이 최소, AS는 페일오버 시간(웜: 수 분, 핫: 수 초)이 RTO에 직결
- 정합성 복잡도: AA는 양방향 동기화 + split-brain(027) 위험, AS는 단방향 복제로 상대적 단순
- 용량 설계 전제: 정상 시 노드당 50% 초과 시 장애 후 연쇄 과부하(cascading failure) 발생 가능
- SPOF 완전 제거 한계: 노드 이중화만으로는 LB·네트워크·스토리지 SPOF(024)가 잔존함

## Ⅴ. 심화 비교 및 적용 판단

| 구분 | Active-Active | Active-Standby | 선택 기준 |
|:---|:---|:---|:---|
| 트래픽 처리 | 전 노드 동시 처리, LB 분산 | 주 노드만 처리, Standby 대기 | 처리량·자원 활용률 요구 |
| 전환 방식 | 부하 재분배(밀리초) | 페일오버(초~분) | RTO 요구(1분 이내 vs 수 분 허용) |
| 동기화 | 양방향, split-brain 위험 | 단방향 복제, 상대적 단순 | 정합성 요구 수준 |
| 적합 시스템 | 웹·API(무상태/경량 상태) | DB·금융 원장(강한 정합성) | 데이터 정합성 중요도 |

> 요약: 처리량·자원 효율 중심이면 AA, 정합성·단순 운영 중심이면 AS를 선택하고 요구에 따라 혼합 적용함.

**리스크·대응:**
- 연쇄 과부하: 정상 시 노드 사용률 50% 초과 설계 → 용량 설계 시 N+1(030) 기준 50% 상한 적용 + 오토스케일링 병행 (지표: 장애 후 잔존 노드 CPU·커넥션)
- Split-brain(027): 네트워크 분단 시 양 노드 Active 오판 → 쿼럼(027) 기반 판정 + STONITH 펜싱 (지표: 동시 Active 판정 이벤트 수)
- 페일오버 지연: Standby 웜업 미비·Health Check 주기 과대 → 웜/핫 스탠바이 유지 + Health Check 5초 이하 주기 (지표: 페일오버 소요 시간 vs RTO)

**점검 지표:**
- 성능: 정상 시 노드당 사용률 50% 이하 유지 — 모니터링 대시보드
- 운영: 페일오버 소요 시간 RTO 이내(예: 1분) — 정기 페일오버 훈련 로그, 복제 지연(lag) 1초 이내

---

## Ⅵ. 실무 적용 및 결론

**적용 방안:**
1. 무상태 웹·API 서비스는 Active-Active + LB로 구성하고 노드당 사용률 50% 이하를 설계 기준으로 설정함
2. 정합성 중심 DB·원장 서비스는 Active-Standby + 웜/핫 스탠바이로 구성하고 자동 페일오버(028) 체계를 연계함
3. 두 구조 모두 쿼럼(027) 기반 split-brain 방지와 분기별 페일오버 훈련을 실시해 전환 시간을 검증함

**결론:**
- 기술사 판단: 자원 효율·처리량은 AA, 정합성·운영 단순성은 AS가 우선이며, 서비스 특성에 따라 계층별 혼합 적용이 현실적임
- 향후 방향: 멀티 리전 Active-Active + Raft/Paxos 기반 자동 쿼럼 판정으로 글로벌 HA가 표준화되는 추세임
