# 📖 【암기용】 개념 완전 이해

## 한눈에
- **개요**: RTO(Recovery Time Objective)와 RPO(Recovery Point Objective)는 **재해복구 목표 지표**로, RTO는 장애 후 서비스 복구까지 허용 가능한 최대 시간, RPO는 허용 가능한 최대 데이터 손실 시간을 정의함.
- **왜 필요한가**: "빨리 복구", "데이터 손실 최소화"만으로는 백업 주기·복구 절차·DR 사이트 등급(025)을 설계할 수 없음. 두 지표를 숫자로 정해야 아키텍처와 예산을 결정할 수 있음.
- **핵심 직관**: RTO = "정전 후 불이 다시 켜지기까지 걸리는 시간", RPO = "정전 직전 마지막으로 저장된 메모가 몇 분 전 것인지".

## 핵심 용어 정리 (내부에 등장하는 것들)

025가 DR 사이트 등급을, 028이 자동 페일오버를 다뤘으므로 여기서는 RTO·RPO 고유의 시간축·측정 용어에 집중함.

| 용어/표기 | 의미 | 비유·예 |
|:---|:---|:---|
| RTO (상위 키워드) | 장애 발생~서비스 정상화까지 허용 최대 시간 | 정전 후 발전기 가동까지 시간 |
| RPO (상위 키워드) | 마지막 복제/백업 시점~장애 발생까지 데이터 손실 허용 최대 시간 | 마지막 저장 이후 작성한 문서 손실 범위 |
| BIA | Business Impact Analysis, 업무 영향도 분석 | 어떤 업무가 얼마나 급한지 등급 매기기 |
| 복제 주기 | 주 센터→DR 사이트 데이터 복제 간격 | 동기(RPO≈0)·비동기(RPO=복제 주기) |
| 백업 주기 | 전체/증분 백업 수행 간격 | 일간 백업 → RPO 최대 24h |
| 복구 절차(런북) | 장애 시 서비스 복구 단계별 체크리스트 | RTO를 결정하는 실행 시간 |

## 깊이 이해
- **배경·문제의식**: 장애 대응은 "언제까지 복구할 것인가(RTO)"와 "얼마나 오래된 데이터까지 복구할 것인가(RPO)"라는 서로 다른 두 질문에 답해야 함. 두 지표를 구분하지 않으면 백업 주기(RPO)와 복구 자동화(RTO) 투자 우선순위를 잘못 정하게 됨.
- **작동 원리 — RTO**:
  - 측정 구간: 장애 발생 시점 → 장애 인지 → 재해 선언(025) → 복구 절차 수행 → 서비스 정상화 시점.
  - 결정 요인: 복구 절차 자동화 수준, DR 사이트 등급(025), 자동 페일오버(028) 적용 여부.
  - RTO가 0에 가까우려면 핫 사이트(025) + 자동 페일오버(028)가 필수.
- **작동 원리 — RPO**:
  - 측정 구간: 마지막 백업/복제 시점 → 장애 발생 시점. 이 구간 동안 작성된 데이터가 손실됨.
  - 결정 요인: 백업·복제 주기. 동기 복제 → RPO≈0(무손실), 비동기 복제 → RPO=복제 지연, 일간 백업 → RPO 최대 24h.
  - RPO 0은 동기 복제를 요구하며, 이는 쓰기 성능에 영향을 줌(RPO↔성능 트레이드오프).
- **비유**: 시험 답안을 작성 중 정전됨. RTO = 전기가 다시 들어와 답안 작성을 재개할 때까지 시간. RPO = 마지막으로 저장한 답안 이후 새로 작성한 부분의 손실 범위.
- **구체 예시**: 금융 원장 — RTO 5분(핫 사이트+자동 페일오버), RPO 0(동기 복제). 이메일 — RTO 4h(웜 사이트), RPO 15분(15분 주기 비동기 복제). 아카이브 — RTO 3일(콜드 사이트), RPO 24h(일간 백업).
- **흔한 오해·주의점**: ① RTO와 RPO를 바꿔 쓰는 것이 가장 흔한 실수 — RTO는 "복구 시간", RPO는 "데이터 시점"으로 항상 구분. ② RPO 0 ≠ RTO 0. RPO 0은 데이터 무손실(동기 복제)이지 복구 시간이 짧다는 뜻이 아님. ③ RTO·RPO는 독립 변수 — 각각 별도로 설계·투자해야 함.

## 연결 개념
- **DR 사이트 (025)**: RTO·RPO 목표에 따라 핫·웜·콜드 등급이 결정됨. 025가 시설을, 026이 시간 목표를 담당.
- **자동 페일오버 (028)**: RTO를 초 단위로 단축하는 핵심 메커니즘.
- **가용성 계산 (019)**: MTTR(복구 시간)이 RTO와 밀접. MTTR ≤ RTO 설계가 전제.

# 📝 【답안용】 시험 답안 템플릿

## 핵심 인사이트 (3줄 요약)

> 1. **본질**: RTO는 장애~복구까지 허용 최대 시간, RPO는 마지막 복제~장애까지 데이터 손실 허용 최대 시간임.
> 2. **가치**: 두 지표를 분리해 정량화해야 DR 사이트 등급(025)·백업 주기·페일오버(028) 설계의 근거가 됨.
> 3. **판단 포인트**: RTO는 복구 자동화·DR 등급이, RPO는 복제·백업 주기가 결정 요인이며 독립적으로 설계·투자해야 함.

## 출제 의도 및 답안 포인트

| 출제 의도 | 반드시 짚을 핵심 | 감점 회피 포인트 |
|:---|:---|:---|
| 두 지표 구분 | RTO=복구 시간, RPO=데이터 손실 시점 | RTO와 RPO 혼용 서술 |
| 설계 연계 이해 | BIA→RTO/RPO 산정→DR 등급·백업 주기 | 정의만 나열하고 설계 연계 누락 |
| 독립성 이해 | RPO 0 ≠ RTO 0, 별도 투자 필요 | RPO 0이면 즉시 복구로 단정 |

> 요약: RTO·RPO 정의 구분 + BIA 기반 산정 + 독립 설계(DR 등급·백업 주기)를 보여야 함.

---

## Ⅰ. 개요 및 필요성

- 개요: RTO는 복구 목표 시간, RPO는 데이터 손실 목표 시점을 정량화하는 재해복구 지표
- 배경: "빨리 복구"·"손실 최소화"만으로는 DR 사이트 등급(025)·백업 주기·페일오버(028) 투자를 결정할 수 없음
- 필요성: BIA로 업무별 RTO·RPO를 정량 산정해야 아키텍처·예산·훈련 범위를 결정 가능

---

## Ⅱ. 구조 및 구성요소

```text
BIA(업무 영향 분석) -> 업무별 RTO·RPO 목표 산정
  -> RTO: DR 사이트 등급(025) + 페일오버(028) 설계
  -> RPO: 복제 방식(동기/비동기) + 백업 주기 설계
  -> 정기 훈련 -> 실측 RTO·RPO vs 목표 비교
```

| 구성요소 | 역할 | 특이사항 |
|:---|:---|:---|
| BIA | 업무 중요도·중단 손실 평가 | RTO·RPO 산정의 입력 |
| RTO 목표 | 복구 시간 상한 설정 | 분~일 단위, 업무별 차등 |
| RPO 목표 | 데이터 손실 시간 상한 설정 | 0~24h, 복제/백업 방식 결정 |
| 복제·백업 | 데이터 보호 수단 | 동기(RPO≈0), 비동기, 일간 백업 |
| 복구 절차(런북) | RTO 내 복구 실행 체크리스트 | 자동화 수준이 RTO를 좌우 |

> 요약: BIA로 RTO·RPO를 산정하고, RTO는 DR 등급·페일오버로, RPO는 복제·백업으로 각각 달성하는 구조임.

---

## Ⅲ. 동작원리 및 흐름도

```text
장애 발생 -> 장애 인지 -> 재해 선언(025) -> 복구 절차 수행
  -> 서비스 정상화(RTO 내)
  장애 시점 기준 RPO 내 데이터는 복제/백업으로 보존됨
```

1. BIA로 업무별 RTO·RPO 목표를 산정하고 문서화함(예: 금융 원장 RTO 5분/RPO 0, 이메일 RTO 4h/RPO 15분)
2. RTO 목표에 따라 DR 사이트 등급(025)과 자동 페일오버(028) 수준을 설계하고, RPO 목표에 따라 복제 방식(동기/비동기)과 백업 주기를 결정함
3. 장애 발생 시 런북에 따라 복구 절차를 수행하고, 실측 RTO(장애~정상화 소요시간)와 RPO(마지막 복제~장애 시점 데이터 손실)를 목표와 대조함
4. 정기 DR 훈련(반기 1회 이상)으로 실측 RTO·RPO를 검증하고, 목표 미달 시 설계를 재조정함

> 요약: BIA 산정 → DR 등급·복제 설계 → 장애 시 런북 수행 → 실측 vs 목표 검증 순으로 진행함.

---

## Ⅳ. 특징

- 시간축 분리: RTO는 "장애 이후(복구 속도)", RPO는 "장애 이전(데이터 신선도)"으로 방향이 반대
- 독립 설계: RTO 결정 요인(DR 등급·페일오버)과 RPO 결정 요인(복제·백업 주기)이 서로 다르므로 별도 투자 필요
- RPO 0 ≠ RTO 0: 동기 복제(RPO=0)는 데이터 무손실이지 즉시 복구가 아님 — 두 지표를 혼동하면 설계 오류
- 비용 반비례: RTO·RPO가 0에 가까울수록 DR 인프라·복제 비용이 급증(019 나인 등급과 동일 구조)
- BIA 갱신 필요: 업무 중요도가 변하면 RTO·RPO 목표도 재산정 — 연 1회 이상 BIA 갱신 필수

---

## Ⅴ. 심화 비교 및 적용 판단

| 구분 | RTO 중심 설계 | RPO 중심 설계 | 선택 기준 |
|:---|:---|:---|:---|
| 핵심 수단 | 핫 사이트(025) + 자동 페일오버(028) | 동기/근실시간 복제 + 빈번 백업 | 다운타임 손실 vs 데이터 손실 민감도 |
| 주요 비용 | 상시 대기 인프라(이중 DC) | 복제 대역폭·스토리지 비용 | BIA 기반 업무별 손실 비용 비교 |
| 주요 위험 | 절차 미숙 시 RTO 초과 | 복제 lag 누적 시 RPO 초과 | 실측 지표의 목표 대비 편차 |

> 요약: 다운타임 민감 업무는 RTO 중심, 데이터 손실 민감 업무는 RPO 중심으로 설계 우선순위를 정함.

**리스크·대응:**
- RTO·RPO 혼용: 요구사항 문서에서 두 지표를 바꿔 씀 → 정의를 표준 용어로 명문화하고 교차 검토 (지표: 요구사항 용어 일관성)
- RPO 미달: 백업·복제 주기가 목표보다 길어 데이터 손실 → 복제 주기 단축 또는 동기 복제 전환 (지표: 복제 lag vs RPO 목표)
- RTO 미달: 복구 절차 미자동화·훈련 부족 → 자동 페일오버(028) 도입 + 정기 DR 훈련 (지표: 실측 RTO vs 목표)

**점검 지표:**
- 성능: 실측 RTO·RPO가 목표 이내 — DR 훈련·인시던트 타임라인
- 운영: BIA 갱신 주기 연 1회 이상 + 복제 lag 상시 모니터링 — BIA 문서 이력·복제 대시보드

---

## Ⅵ. 실무 적용 및 결론

**적용 방안:**
1. BIA로 업무별 RTO·RPO 목표를 정량 산정하고 핵심 업무(RTO 분 단위/RPO 0)부터 비핵심(RTO 일 단위/RPO 24h)까지 차등 문서화함
2. RPO 목표에 맞춰 복제 방식(동기/비동기)과 백업 주기를 설계하고, RTO 목표에 맞춰 DR 사이트 등급(025)과 자동 페일오버(028)를 구성함
3. 반기 1회 이상 DR 훈련으로 실측 RTO·RPO를 목표와 대조하고, 미달 시 복제 주기·페일오버 설계를 재조정함

**결론:**
- 기술사 판단: RTO와 RPO는 시간축이 반대인 독립 지표이므로 분리 설계·별도 투자해야 요구사항을 정확히 충족함
- 향후 방향: 클라우드 네이티브 백업·복제 자동화로 RTO·RPO를 실시간 모니터링하고 목표 미달을 사전 예측하는 방향으로 발전 중임
