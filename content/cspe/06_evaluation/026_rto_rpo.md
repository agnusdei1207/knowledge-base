## 미리 알고가기

- RTO: 장애 발생 후 서비스를 다시 열어야 하는 최대 허용 중단 시간임
- RPO: 장애 발생 시 복구 시점에서 감내할 수 있는 최대 데이터 손실 범위임
- BIA: 업무 중단이 매출, 법규, 운영에 미치는 영향을 분석해 복구 목표를 정하는 절차임
- 동기 복제: 두 사이트에 거의 같은 시점으로 데이터를 반영하는 방식임

## Ⅰ. 개요

- **정의/개념**: RTO와 RPO는 재해 복구와 서비스 연속성 계획에서 각각 허용 가능한 최대 서비스 중단 시간과 허용 가능한 최대 데이터 손실 시점을 정하는 핵심 복구 목표 지표임
- **배경/필요성**: 모든 시스템을 무중단·무손실로 설계하면 비용이 과도해지므로, 업무별 손실 허용 범위를 먼저 정해 복구 구조와 투자 수준을 구분할 기준이 필요함

## Ⅱ. 특징

- RTO는 장애 이후 서비스를 다시 시작하는 속도를, RPO는 복구 시 되돌아갈 수 있는 데이터 시점을 통제함
- 두 지표는 서로 연관되지만 같은 값으로 움직이지 않으므로 각각 다른 기술과 비용이 필요함
- 업무 중요도가 높을수록 둘 다 짧아지지만, 짧아질수록 이중화와 복제 비용이 급격히 증가함
- 목표 수치보다 실제 복구 성과가 중요하므로 정기 훈련으로 실제 복구 시간과 실제 데이터 손실 범위를 검증해야 함

## Ⅲ. 종류 및 비교

| 판단 기준 | RTO | RPO |
|:---|:---|:---|
| 통제 대상 | 서비스 중단 시간을 줄이는 것이 목적임 | 데이터 손실 범위를 줄이는 것이 목적임 |
| 시간 방향 | 장애 시점 이후 미래 방향으로 측정함 | 장애 시점 이전 과거 방향으로 측정함 |
| 주된 기술 수단 | 자동 페일오버, 빠른 기동, 표준 복구 절차가 영향을 줌 | 동기·비동기 복제, 백업 주기, 로그 보존 정책이 영향을 줌 |
| 대표 판단 질문 | 언제까지 서비스를 다시 열어야 하는가 | 어디 시점까지의 데이터 손실을 허용할 수 있는가 |

## Ⅳ. 구성요소 및 구조

| 구성요소 | 설명 |
|:---|:---|
| 업무 영향 분석 | 서비스 중단과 데이터 손실이 업무에 주는 영향을 수치화해 목표 수준을 정함 |
| 데이터 보호 체계 | 백업, 스냅샷, 로그, 복제가 RPO 수준을 결정함 |
| 복구 실행 체계 | 예비 인프라, 자동 전환, 표준 복구 절차가 RTO 수준을 결정함 |
| 검증 절차 | 모의 훈련과 실제 장애 기록을 통해 목표와 실측치 차이를 확인함 |

```text
+-------------+     +-------------+     +-------------+     +-------------+
| BIA 수행      | --> | RTO/RPO 설정 | --> | 복구 구조 설계  | --> | 훈련으로 검증   |
+-------------+     +-------------+     +-------------+     +-------------+
```

## Ⅴ. 원리 및 절차 흐름도

```text
+-------------+     +-------------+     +-------------+     +-------------+
| 업무 등급 분류   | --> | 복구 목표 정의  | --> | 보호/전환 절차 구축 | --> | 실측값 점검    |
+-------------+     +-------------+     +-------------+     +-------------+
```

1. **업무 등급 분류**: 중단 시 손실이 큰 업무와 낮은 업무를 구분함
2. **복구 목표 정의**: 각 업무에 맞는 RTO와 RPO를 설정함
3. **보호와 전환 절차 구축**: 복제, 백업, 예비 사이트, 자동 전환 절차를 준비함
4. **실측값 점검**: 훈련과 사고 대응 결과로 목표 달성 여부를 확인함

## Ⅵ. 실무 적용 및 유의점

1. 금융 결제나 핵심 거래 시스템은 짧은 RTO와 낮은 RPO가 필요하지만 목표만 낮게 적어 두면 의미가 없으므로 동기 복제와 자동 전환 절차를 같이 운영하고 실제 복구 시간과 실제 데이터 손실 범위와 복구 훈련 성공률로 확인함
2. 내부 업무나 정보계 시스템은 웜·콜드 복구가 현실적이지만 업무 손실보다 낮은 수준으로 목표를 잡으면 복구 지연이 길어지므로 BIA 기반으로 목표를 재조정하고 복구 준비 시간과 백업 최신성으로 확인함

## Ⅶ. 결론

RTO와 RPO의 핵심은 더 짧은 수치를 선언하는 데 있지 않고 업무 손실 허용 범위에 맞춰 복구 속도와 데이터 보호 수준을 현실적으로 정하는 데 있음.
