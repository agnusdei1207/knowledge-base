# 📖 【암기용】 개념 완전 이해

> 목적: 테스트 커버리지를 처음 봐도 구문·분기·MC/DC가 왜 점점 더 엄격해지는 기준인지 이해하게 만든다. 시험 답안 양식이 아니라, 이해를 위한 친절한 설명이다.

## 한눈에
- **개요**: 테스트가 소스 코드의 얼마만큼을 실행했는지 정량화하는 지표이며, 구문 커버리지 < 분기 커버리지 < MC/DC 순으로 요구 수준이 엄격해진다
- **왜 필요한가**: "테스트를 많이 했다"는 말로는 어떤 코드 경로가 실제로 검증되지 않았는지 알 수 없다. 커버리지 기준을 명확히 해야 안전 필수 시스템에서 "이 조건 분기는 검증되지 않았다"를 놓치지 않는다.
- **핵심 직관**: 구문 커버리지는 "모든 방을 한 번씩 들어가 봤는가", 분기 커버리지는 "모든 문을 열고 닫아 봤는가", MC/DC는 "각 문의 잠금장치 하나하나가 실제로 문을 여닫는 데 영향을 주는지 개별 확인했는가"에 해당한다.

## 깊이 이해
- **구문 커버리지(Statement Coverage)**: 테스트 실행 중 소스 코드의 모든 실행 가능한 문장(line)이 최소 한 번 실행되었는지를 측정하는 가장 기본적인 커버리지다.
- **분기 커버리지(Branch/Decision Coverage)**: `if`, `while` 같은 각 분기(decision)가 참(True)과 거짓(False) 양쪽 방향으로 모두 실행되었는지를 측정하며, 구문 커버리지보다 엄격하다.
- **분기 커버리지가 구문 커버리지보다 엄격한 이유**: 구문 커버리지 100%여도 `if` 조건이 항상 참으로만 실행되면 거짓 분기(else)의 코드는 실행되지 않을 수 있어, 분기 커버리지가 이를 추가로 요구한다.
- **MC/DC(Modified Condition/Decision Coverage)**: 하나의 decision(분기 조건식)이 여러 개별 조건(condition)의 논리 결합으로 구성될 때, 각 개별 조건이 다른 조건 값을 고정한 채로 그 조건 하나만 변화시켜 decision의 결과를 독립적으로 변화시키는 것을 모두 확인하는 커버리지다.
- **MC/DC가 분기 커버리지보다 엄격한 이유**: 분기 커버리지는 decision 전체의 참/거짓만 확인하면 되지만, MC/DC는 `A AND B` 같은 복합 조건에서 A와 B 각각이 독립적으로 결과에 영향을 미치는지까지 확인해야 하므로 요구 테스트 케이스 수가 더 많다.
- **엄격성 순서**: 구문 커버리지(가장 느슨) < 분기 커버리지 < MC/DC(가장 엄격)이며, 상위 커버리지를 만족하면 하위 커버리지는 자동으로 만족된다.
- **비유**: 구문 커버리지는 스위치를 한 번 눌러봤는지, 분기 커버리지는 켜기/끄기를 모두 눌러봤는지, MC/DC는 여러 스위치가 동시에 연결된 회로에서 각 스위치 하나하나가 실제로 전등을 켜고 끄는 데 영향을 주는지 개별 검증한 것이다.
- **활용 맥락**: MC/DC는 DO-178C(항공 소프트웨어 안전 표준)의 Level A(치명적 결함 시 인명 피해 가능) 소프트웨어에서 요구되는 최고 수준의 커버리지 기준이다.
- **흔한 오해·주의점**: 구문 커버리지 100%를 "테스트가 완벽하다"로 오해하기 쉽지만, 구문 커버리지는 분기 미실행이나 조건 조합 누락을 전혀 보장하지 않는 가장 약한 기준이다.

## 연결 개념
- 결함 밀도·결함 제거율 — 커버리지 확대가 결함 제거율을 높이는 실행 근거
- FMEA — 안전 필수 소프트웨어에서 MC/DC 요구 여부를 결정하는 위험도 분석과 연계
- ISO/IEC 25010 기능 적합성 — 테스트 커버리지가 뒷받침하는 품질 특성

# 📝 【답안용】 시험 답안 템플릿

> 목적: 시험장에서 25분에 그대로 쓰는 답안 양식. 작성방식(추상표현 금지·수치·도식·문제유형 전환)을 엄격히 지킨다.
> 핵심: 테스트 커버리지 답안은 구문·분기·MC/DC의 정의, 엄격성 순서, DO-178C 등 적용 맥락, 상위-하위 포함 관계를 함께 제시한다.

## 핵심 인사이트 (3줄 요약)

> 1. **본질**: 테스트 커버리지는 구문 < 분기 < MC/DC 순으로 요구 수준이 엄격해지는 코드 실행 검증 지표다.
> 2. **가치**: MC/DC는 복합 조건의 개별 조건이 decision 결과에 독립적으로 영향을 미치는지까지 검증해 안전 필수 소프트웨어의 결함을 최소화한다.
> 3. **판단 포인트**: 일반 상용 소프트웨어는 분기 커버리지 수준으로 충분하지만, DO-178C Level A 등 안전 필수 시스템은 MC/DC를 요구한다.

## 출제 의도 및 답안 포인트

| 출제 의도 | 반드시 짚을 핵심 | 감점 회피 포인트 |
|:---|:---|:---|
| 커버리지 종류 이해 확인 | 구문·분기·MC/DC 정의와 계층 관계 | 세 커버리지를 동일 수준으로 서술 |
| 엄격성 순서 이해 확인 | 구문 < 분기 < MC/DC | 순서를 반대로 서술 |
| 적용 맥락 이해 확인 | MC/DC와 DO-178C Level A 연계 | 적용 맥락 없이 정의만 나열 |

> 요약: 이 문제는 세 커버리지의 정의와 엄격성 순서, 안전 필수 시스템 적용 맥락을 정확히 짚어야 한다.

## Ⅰ. 개요 및 필요성

- 정의: 테스트가 코드를 실행한 범위를 정량화하는 지표로 구문·분기·MC/DC 순으로 엄격
- 배경: 구문 커버리지 100%만으로는 조건 분기와 복합 조건 결합 누락을 보장하지 못해 상위 기준이 요구됨
- 필요성: 안전 필수 소프트웨어는 결함 하나가 인명 피해로 이어질 수 있어 MC/DC 같은 엄격한 커버리지 기준이 필요

---

## Ⅱ. 구조 및 구성요소

```text
소스 코드 -> 구문 커버리지(모든 라인 1회 실행)
  -> 분기 커버리지(모든 분기 참/거짓 실행)
  -> MC/DC(각 조건이 decision에 독립적 영향 확인)
  -> 커버리지 도구 측정 -> 목표치 대조
```

| 구성요소 | 역할 | 특이사항 |
|:---|:---|:---|
| 구문 커버리지 | 모든 실행 가능 라인의 실행 여부 확인 | 가장 느슨한 기준 |
| 분기 커버리지 | 모든 분기의 참/거짓 실행 여부 확인 | 구문 커버리지 포함 |
| MC/DC | 개별 조건의 독립적 영향 확인 | 분기 커버리지 포함, 가장 엄격 |
| 커버리지 측정 도구 | 실행 경로를 계측해 커버리지 산출 | 코드 계측(instrumentation) 기반 |

> 요약: 세 커버리지는 상위 기준이 하위 기준을 포함하는 계층 구조를 이룬다.

---

## Ⅲ. 동작원리 및 흐름도

```text
테스트 케이스 설계 -> 코드 계측(instrumentation)
  -> 테스트 실행 -> 구문/분기/조건 실행 여부 기록
  -> 커버리지 비율 산출 -> 목표 기준 대조
  -> 미달 시 테스트 케이스 추가
```

| 단계 | 처리 내용 | 검증 기준 |
|:---:|:---|:---|
| 1 | 요구 커버리지 수준(구문/분기/MC-DC) 결정 | 안전 등급·표준 요구 여부 |
| 2 | 코드 계측 후 테스트 케이스 실행 | 계측 도구의 정확성 |
| 3 | 실행 결과로 커버리지 비율 산출 | 목표치 대비 달성률 |
| 4 | 미달 구간에 대해 테스트 케이스 추가 설계 | 추가 케이스로 커버리지 개선 여부 |

> 요약: 커버리지 측정은 목표 수준 결정, 계측·실행, 비율 산출, 미달 보완 순으로 진행된다.

## Ⅳ. 특징

| 구분 | 내용 | 판단 포인트 |
|:---|:---|:---|
| 구문 커버리지 | 모든 라인 1회 실행 여부만 확인 | 조건 분기 누락 가능성 존재 |
| 분기 커버리지 | 모든 분기의 참/거짓 실행 확인 | 복합 조건 개별 영향은 미확인 |
| MC/DC | 복합 조건의 개별 조건 독립적 영향까지 확인 | 안전 필수 소프트웨어(DO-178C Level A)에서 요구 |

> 요약: 세 커버리지는 검증 범위가 순차적으로 확장되며 MC/DC가 가장 엄격하다.

## Ⅴ. 심화 비교 및 적용 판단

| 비교 축 | 구문 커버리지 | 분기 커버리지 | MC/DC |
|:---|:---|:---|:---|
| 검증 범위 | 모든 라인 1회 실행 | 모든 분기 참/거짓 실행 | 개별 조건의 독립적 decision 영향 |
| 요구 테스트 케이스 수 | 최소 | 중간 | 최대 |
| 적용 맥락 | 일반 상용 소프트웨어 최소 기준 | 대부분 산업 소프트웨어 표준 기준 | DO-178C Level A 등 안전 필수 시스템 |

> 요약: 일반 소프트웨어는 분기 커버리지, 안전 필수 시스템은 MC/DC를 적용 기준으로 선택한다.

| 리스크 | 원인 | 대응 방안 | 확인 지표 |
|:---|:---|:---|:---|
| 낮은 커버리지 수준 오인 | 구문 커버리지 100%를 완전 검증으로 오해 | 분기·MC/DC 기준으로 재평가 | 분기 커버리지, MC/DC 비율 |
| 복합 조건 결함 누락 | 분기 커버리지만 적용해 조건 조합 미검증 | 안전 등급 판정 후 MC/DC 적용 여부 결정 | 조건 조합별 테스트 케이스 존재 여부 |
| 테스트 비용 과다 | MC/DC를 불필요한 영역까지 일괄 적용 | 위험도(FMEA 결과) 기반 커버리지 등급 차등 적용 | 등급별 커버리지 목표 대비 실적 |

> 요약: 리스크는 낮은 커버리지 수준을 완전 검증으로 오인하는 것이므로 위험도 기반 등급 차등 적용으로 통제한다.

| 점검 항목 | 목표 기준 | 측정 방법 |
|:---|:---|:---|
| 구문 커버리지 | 100% | 커버리지 도구 측정 결과 |
| 분기 커버리지 | 90% 이상(프로젝트 기준에 따라 조정) | 커버리지 도구 측정 결과 |
| MC/DC | 안전 필수 모듈 100% | DO-178C 등 표준 준수 점검 |

> 요약: 성공 여부는 등급별 목표 커버리지 달성률로 판단하며 안전 필수 모듈은 MC/DC 100%를 기준으로 한다.

## Ⅵ. 실무 적용 및 결론

**적용 방안 3개 (필수 — 단계별 또는 항목별):**
1. 일반 모듈은 구문·분기 커버리지 목표치를 설정하고 CI 파이프라인에서 자동 측정함
2. FMEA 등으로 식별한 안전 필수 모듈은 MC/DC 100%를 목표로 별도 테스트 케이스를 설계함
3. 커버리지 미달 구간은 조건 조합별 테스트 케이스를 추가해 결함 제거율을 함께 향상시킴

**결론 (2줄):**
- 기술사 판단: 커버리지 기준은 위험도에 따라 차등 적용하며 안전 필수 영역은 MC/DC를 필수 기준으로 선택함
- 향후 방향: 커버리지 측정을 CI/CD 품질 게이트에 내재화하고 위험 등급별 목표치를 자동 검증해야 함
