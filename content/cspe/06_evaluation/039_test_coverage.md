## 📖 【암기용】 핵심 요약

*   **한눈에**: 우리가 만든 테스트 케이스(Test Case)가 소스 코드의 구석구석을 **얼마나 빠짐없이 훑고 지나갔는가(실행했는가)**를 비율(%)로 정량화한 지표. 구문 $\to$ 분기 $\to$ MC/DC 순으로 검증 기준이 깐깐해짐.
*   **깊이 이해**:
    *   **배경**: 개발자가 "나 테스트 엄청 많이 했어!"라고 말해도 믿을 수 없음. 전체 코드가 1만 줄인데, 매번 똑같은 1,000줄만 반복해서 테스트했을 수도 있기 때문임. 실행되지 않은 나머지 9천 줄에서 버그가 터지는 것을 막기 위해, 코드의 구조적 실행 범위를 숫자로 증명해야 함.
    *   **1. 구문 커버리지 (Statement Coverage)**:
        *   코드의 모든 '줄(Line)'이 최소 한 번은 실행되었는가? (가장 널널한 기준).
        *   *문제점*: `if (A && B)` 조건문이 참(True)인 경우만 테스트하면 코드는 다 훑고 지나감. 하지만 거짓(False)일 때 어떤 에러가 나는지는 전혀 알 수 없음.
    *   **2. 분기/결정 커버리지 (Branch/Decision Coverage)**:
        *   모든 조건문(if, while)의 결과가 **참(True)**인 경우와 **거짓(False)**인 경우를 모두 한 번씩은 타보았는가? (일반적인 기업의 S/W 테스트 표준).
        *   *문제점*: `if (A && B)`의 결과가 T/F가 되는 것만 볼 뿐, 조건식 내부의 `A`나 `B`라는 개별 변수가 각자 결괏값에 어떤 영향을 미치는지는 무시함.
    *   **3. MC/DC (Modified Condition / Decision Coverage)**:
        *   가장 깐깐한 최고 등급. 개별 조건(`A`, `B` 각각)이 독립적으로 전체 결과(Decision)에 영향을 미치는 모든 조합을 테스트했는가?
        *   다른 조건들을 고정해 놓은 상태에서, 오직 `A` 하나만 참/거짓으로 바꿨을 때 전체 결과도 참/거짓으로 바뀌는지를 증명해야 함. N개의 조건식이면 `N+1`개의 테스트 케이스가 필요함.
    *   **비유**: **미로 찾기 검증**.
        *   구문: 미로 안의 모든 '방'에 한 번씩 불을 켜봤는가.
        *   분기: 미로 안의 모든 '문'을 한 번씩 열고 닫아봤는가.
        *   MC/DC: 그 문을 여는 '여러 개의 자물쇠(조건)'들이 각각 제대로 작동하는지 하나하나 돌려봤는가.
*   **연결 개념**: 화이트박스 테스트, 정적/동적 분석, 결함 제거율(DRE), DO-178C (항공 S/W 국제 표준)

## 📝 【답안용】 서술 골격

> **💡 핵심 인사이트**
> *   **본질**: 소스 코드의 논리적 제어 흐름(Control Flow)을 기반으로, 테스트 데이터가 코드를 실행한 궤적을 측정하는 동적 분석(Dynamic Analysis) 기반의 화이트박스(White-box) 테스트 메트릭.
> *   **가치**: 테스팅의 완전성(Completeness)을 정량적으로 증명하여, 릴리즈 후 발생할 수 있는 미실행 코드(Dead Code)나 예외 경로에서의 치명적 결함을 사전에 통제함.
> *   **판단 포인트**: 커버리지 수치 자체가 S/W의 절대적 품질을 보증하는 것은 아님. 도메인의 특성(예: 항공/국방 vs 일반 웹)에 따라 TCO를 고려하여 구문 $\to$ 분기 $\to$ MC/DC 커버리지의 목표 수준을 차등 적용하는 것이 핵심임.

### Ⅰ. 구조적 테스팅의 척도, 테스트 커버리지 개요
*   **정의**: 소프트웨어 테스트 수행 시, 테스트 대상이 되는 소스 코드의 제어 흐름이 테스트 케이스에 의해 어느 정도 수준으로 실행(Executed)되었는가를 나타내는 비율.
*   **목적**: 화이트박스 테스트의 검증 수준을 정량화하고, 누락된 테스트 케이스를 식별하여 결함 제거율(DRE)을 극대화함.

### Ⅱ. 커버리지 3대 지표의 계층적 진화 (구문 $\to$ 분기 $\to$ MC/DC)
커버리지는 하위 수준을 만족한다고 상위를 만족하지 않으나, 상위 수준을 만족하면 하위를 자연스럽게 포함(Subsume)하는 계층 구조를 가짐.

| 커버리지 유형 | 측정 기준 및 로직 | 엄격성 | 주요 적용 대상 |
| :--- | :--- | :--- | :--- |
| **구문 커버리지**<br>(Statement) | $\frac{\text{실행된 구문 수}}{\text{전체 구문 수}}$<br>코드의 모든 문장이 최소 1번 이상 실행. | 하 (Low) | 개발자 단위 테스트 (Unit Test) 최소 요건 |
| **분기 커버리지**<br>(Branch/Decision) | $\frac{\text{실행된 분기 수}}{\text{전체 분기 수}}$<br>모든 결정 포인트(if, case)가 True/False를 최소 1번 이상 가짐. | 중 (Medium) | 일반 상용 S/W (금융, 커머스 등) 표준 |
| **MC/DC**<br>(Modified Condition / Decision) | 개별 조건식(Condition)이 다른 조건의 영향을 받지 않고 **독립적으로 전체 결과(Decision)를 변경**시키는 조합을 테스트. | 최상 (High) | 항공우주, 원자력, 의료 등 미션 크리티컬 시스템 |

### Ⅲ. 분기 커버리지의 한계와 MC/DC의 수학적 해결
*   `if (A and B)` 라는 결정(Decision)에서,
*   **분기 커버리지의 맹점**:
    *   TC 1: `A=T, B=T` $\to$ 전체 결과: **True**
    *   TC 2: `A=F, B=F` $\to$ 전체 결과: **False**
    *   이 2개의 테스트만으로 전체의 True/False가 1번씩 나왔으므로 분기 커버리지는 100%가 됨. 하지만 이 경우 `B`가 혼자서 결과에 미치는 영향은 전혀 테스트되지 않은 상태임.
*   **MC/DC의 조건 독립성 증명**:
    *   N개의 조건식이 있을 때 $2^N$ 개의 모든 조합(다중 조건 커버리지)을 테스트하는 것은 불가능함(조합 폭발).
    *   MC/DC는 **$N+1$개의 테스트 케이스만으로** 각 조건이 결과에 독립적인 영향을 미치는지 증명하는 최적화된 조합을 수학적으로 도출함.

### Ⅳ. 최신 트렌드: 코드 커버리지 기반의 지속적 품질 통제 (CI/CD)
*   과거에는 프로젝트 종료 시점에 일회성으로 커버리지를 측정했음.
*   최근에는 SonarQube, JaCoCo, Cobertura 등의 정적/동적 코드 분석 도구를 DevOps 파이프라인(Jenkins, GitLab CI)에 연동함.
*   **Quality Gate (품질 게이트)** 설정: "신규 작성된 코드의 분기 커버리지가 80% 미만일 경우 Git Merge 및 빌드를 강제 차단(Build Fail)"하는 방식의 Shift-Left 자동화 테스팅이 글로벌 표준으로 자리 잡음.
