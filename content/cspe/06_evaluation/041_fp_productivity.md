## 📖 【암기용】 핵심 요약

*   **한눈에**: 소프트웨어의 크기(규모)를 코딩 줄 수(LOC)가 아니라, 사용자가 실제로 체감하는 **요구 기능(화면, 출력물, 파일 등)의 개수와 복잡도**를 기준으로 계산하여 개발 비용과 기간을 산정하는 국제 표준 기법(IFPUG).
*   **깊이 이해**:
    *   **배경**: 예전에는 "프로그램 몇 줄(LOC) 짰어?"로 돈을 줬음. 하지만 C언어로 1,000줄 짤 것을 파이썬으로는 100줄이면 짬. 또한, 고수 개발자가 짠 짧고 효율적인 코드가, 초보자가 짠 길고 지저분한 코드보다 돈을 덜 받는 모순이 발생함.
    *   **작동 원리**: "내부 코드가 어떤 언어든 알 바 아니고, 고객 입장에서 눈에 보이는 기능이 몇 개야?"로 접근함. 
        1.  데이터 기능(저장소): 내부 파일(ILF), 외부 연계 파일(EIF).
        2.  트랜잭션 기능(화면 조작): 외부 입력(EI, 등록/수정), 외부 출력(EO, 계산 후 보고서 출력), 외부 조회(EQ, 단순 목록 조회).
    *   **비유**: **건축 설계와 평당 단가**. 건물의 크기를 벽돌 개수(LOC)로 세지 않음. 방이 3개(내부 파일), 화장실 2개(외부 연계), 창문 5개(외부 조회), 출입문 2개(외부 입력) 등 사용자가 체감하는 '기능적 공간(FP)'의 개수와 복잡도로 평수를 재고, 거기에 평당 단가를 곱해서 건축비를 산정하는 원리.
    *   **보정(Adjustment)**: 기능 개수(UFP)를 다 세었다고 끝이 아님. "분산 처리해야 하나?", "성능이 아주 중요하게 요구되나?" 등 14가지 일반 시스템 특성(GSC)을 고려해 보정 계수(VAF)를 곱해 최종 FP를 도출함.
    *   **흔한 오해/주의점**: "FP는 복잡한 내부 알고리즘의 난이도까지 정확히 계산해 준다?" $\rightarrow$ **오답**. FP의 최대 단점이 바로 화면 없는 복잡한 내부 로직(수학적 연산, 딥러닝 가중치 계산 등)의 난이도를 제대로 평가하지 못한다는 점임. 철저히 '데이터 트랜잭션 중심'의 비즈니스 앱 산정에 특화되어 있음.
*   **연결 개념**: LOC(Line of Code), COCOMO 모델, IFPUG 표준, 소프트웨어 사업 대가 기준(공공기관), 생산성(FP/Man-Month)

## 📝 【답안용】 서술 골격

> **💡 핵심 인사이트**
> *   **본질**: 구현 기술이나 언어에 종속되지 않고, 철저히 사용자 관점(User View)의 비즈니스 기능 요구사항을 기반으로 소프트웨어의 논리적 규모를 계수하는 방법론.
> *   **가치**: 프로젝트 초기(요구사항 분석 단계)에도 정확한 규모 예측이 가능하여, 공공 정보화 사업의 예산 편성 및 대가 산정의 절대적인 기준점(Baseline)으로 작용함.
> *   **판단 포인트**: 과거의 LOC 기반 방식과 대조되는 강점을 부각하되, 알고리즘 중심 시스템(AI, 과학연산)에서는 FP의 표현력이 떨어져 별도의 보정 지표(예: 복잡도)가 필요함을 논리적으로 방어해야 함.

### Ⅰ. 언어 독립적 규모 산정의 표준, 기능점수(FP) 개요
*   **정의**: 사용자에게 제공되는 소프트웨어 기능의 양과 복잡도를 정량화하여 소프트웨어의 규모(Size)를 측정하는 기법 (ISO/IEC 20926 표준).
*   **도입 목적**: 기존 LOC(Line of Code) 산정 방식의 한계(개발 언어 종속성, 설계 단계 산정 불가, 개발자 역량에 따른 왜곡)를 극복하고, 객관적인 개발 비용, 일정, 생산성 측정 지표를 확보하기 위함.

### Ⅱ. FP 산정을 위한 5대 기본 유형 (Data & Transaction)
기능점수 측정은 시스템 경계(Boundary)를 식별한 후 다음 5가지 요소를 계수함.

1.  **데이터 기능 (Data Functions)**: 시스템이 보관/참조하는 데이터 집합.
    *   **ILF (Internal Logical File, 내부 논리 파일)**: 애플리케이션 내에서 직접 생성 및 유지보수되는 데이터 (예: 회원 마스터 테이블).
    *   **EIF (External Interface File, 외부 연계 파일)**: 애플리케이션 내에서는 참조만 하고 다른 시스템이 유지보수하는 데이터 (예: 타 기관 신용정보 DB 연계).
2.  **트랜잭션 기능 (Transaction Functions)**: 시스템 외부와 내부 간의 데이터 이동.
    *   **EI (External Input, 외부 입력)**: 외부에서 시스템 내부로 들어와 데이터를 갱신(C/U/D)하는 작업.
    *   **EO (External Output, 외부 출력)**: 데이터를 계산/가공하여 시스템 외부로 내보내는 작업 (예: 통계 보고서 생성).
    *   **EQ (External Inquiry, 외부 조회)**: 계산이나 데이터 갱신 없이 단순 데이터 검색 및 조회 (예: 회원 목록 조회).

### Ⅲ. FP (기능점수) 산출 메커니즘 및 수식
*   **1단계: 미조정 기능점수 (UFP, Unadjusted FP) 산출**
    *   5대 요소별로 DET(데이터 요소 개수)와 RET/FTR(참조 파일 수)를 세어 복잡도(단순/보통/복잡)를 판정.
    *   판정된 복잡도 가중치를 곱해 UFP를 합산.
*   **2단계: 값 조정 계수 (VAF, Value Adjustment Factor) 산출**
    *   데이터 통신, 분산 데이터 처리, 성능, 다중 사이트 사용 등 14개 일반 시스템 특성(GSC)을 0~5점으로 평가.
    *   $VAF = (TDI \times 0.01) + 0.65$  (단, $TDI$는 14개 특성 점수의 총합)
*   **3단계: 최종 조정 기능점수 (AFP, Adjusted FP) 산출**
    *   **$AFP = UFP \times VAF$**

### Ⅳ. 생산성 지표 활용 및 공공 SW 사업 대가 산정
*   **FP 기반 생산성 지표**: $Productivity = \frac{FP}{MM(Man-Month)}$ (1인당 월평균 몇 FP를 개발하는가)
*   **SW 사업 대가 가이드 연계**: (국내 공공발주 기준)
    *   **개발비** = $FP \times$ 기능점수당 단가 $\times$ 보정계수(규모, 애플리케이션 유형, 언어, 품질/보안 등) + 직접 경비 및 이윤.
    *   **특징**: 공공 소프트웨어 사업에서 예산 및 대가 산정 시 FP 방식을 의무화하고 있음.

### Ⅴ. FP 방식의 한계와 실무적 대응 전략 (LOC와의 융합)
| 비교 항목 | FP (기능점수) | LOC (코드 라인 수) / 다른 방식 보완 |
| :--- | :--- | :--- |
| **강점 영역** | 비즈니스 애플리케이션, SI 프로젝트 | 임베디드, 알고리즘 특화 SW, 레거시 마이그레이션 |
| **산정 시점** | 기획, 요구사항 분석, 설계 단계 | 구현 단계 이후, 리팩토링 시점 |
| **한계점** | 화면/DB 연계가 적은 **수학/AI 내부 알고리즘의 복잡도**를 점수화하지 못해 대가가 과소 계상됨. | 백 파이어링(Back-firing, FP $\to$ LOC 변환표) 적용이나, **순환 복잡도(McCabe)** 등 구조적 복잡도 지표를 보완 대가로 요구해야 함. |

### 🔄 문제 유형별 목차 전환 (실전 팁)
*   **"소프트웨어 프로젝트 규모 산정 및 비용 예측"** 문제: Ⅱ·Ⅲ을 전진 배치하여 `[Ⅱ. 데이터(ILF, EIF) 및 트랜잭션(EI, EO, EQ) 관점의 5대 계수 로직]`, `[Ⅲ. UFP, VAF 도출 및 최종 AFP 산정의 수학적 알고리즘]`으로 공학적 산출 능력을 입증.
*   **"SW 발주/계약, 프로젝트 생산성(PMO)"** 문제: Ⅳ·Ⅴ를 강조하여 `[Ⅳ. 공공 SW 사업 대가 산정 가이드라인 기반의 FP 연동 견적 프레임워크]`, `[Ⅴ. 내부 로직 중심 시스템(AI/빅데이터)에서의 FP 과소 계상 한계 및 복잡도 지표(McCabe 등) 연계를 통한 보완 전략]`으로 컨설턴트급 대응력을 어필.
