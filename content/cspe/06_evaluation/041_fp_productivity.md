# 📖 【암기용】 개념 완전 이해

> 목적: FP(Function Point)를 처음 봐도 왜 LOC 대신 기능 개수로 소프트웨어 규모를 재는지 이해하게 만든다. 시험 답안 양식이 아니라, 이해를 위한 친절한 설명이다.

## 한눈에
- **개요**: 사용자 관점의 기능 요구사항(입력·출력·조회·파일) 개수를 계수해 소프트웨어 규모를 산정하는 기법
- **왜 필요한가**: LOC(Line of Code) 기반 산정은 언어·개발자 숙련도에 따라 편차가 크다. FP는 기능 요구사항 개수 기반이라 언어·플랫폼이 달라도 규모와 생산성을 비교할 수 있다.
- **핵심 직관**: 집 면적을 벽돌 개수로 재지 않고 방·화장실·주방 개수로 재는 것과 같은 방식이다.

## 깊이 이해
- **배경·문제의식**: 1970년대 IBM은 LOC 기반 생산성 비교가 언어별로 왜곡됨을 확인했다.
- **배경·문제의식**: Allan Albrecht가 1979년 사용자 기능 요구사항 기반 FP를 제안했고, 이후 IFPUG(International Function Point Users Group) 표준으로 정착했다.
- **작동 원리**: 트랜잭션 기능인 EI(External Input, 외부입력)·EO(External Output, 외부출력)·EQ(External Inquiry, 외부조회)와 데이터 기능인 ILF(Internal Logical File, 내부논리파일)·EIF(External Interface File, 외부연계파일) 5종을 식별한다.
- **작동 원리**: 각 기능을 데이터요소 개수·파일참조 개수 기준으로 단순·보통·복잡 3단계로 분류하고 IFPUG 가중치 표를 곱해 UFP(Unadjusted Function Point)를 합산한다.
- **작동 원리**: GSC(General System Characteristics) 14개 항목(분산처리, 성능, 트랜잭션량 등)을 0~5점으로 평가해 VAF(Value Adjustment Factor, 통상 0.65~1.35 범위)를 산출한다.
- **작동 원리**: AFP(Adjusted Function Point) = UFP × VAF로 최종 보정 기능점수를 구한다.
- **작동 원리**: 생산성 지수 = 총 개발 AFP ÷ 투입 인월(Man-Month)로 계산하고, 역산하면 소요 인월 = 목표 AFP ÷ 생산성 지수로 공수를 추정한다.
- **비유**: 음식점 규모를 매출이 아니라 메뉴 종류 수와 식자재 창고 개수로 가늠하는 것과 유사하다.
- **구체 예시**: 로그인 화면 1개(EI), 결과 조회 화면 1개(EQ), 회원 테이블 1개(ILF)를 각각 보통 등급으로 계수하면 EI 4점 + EQ 4점 + ILF 7점 = UFP 15점이 되고, VAF 1.0을 곱하면 AFP도 15점이다.
- **흔한 오해·주의점**: FP는 기능 요구사항 규모이지 구현 난이도를 반영하지 않는다.
- **흔한 오해·주의점**: 알고리즘이 복잡한 모듈과 단순한 모듈이 같은 FP로 계수될 수 있어 순환복잡도 같은 별도 지표와 병행 판단이 필요하다.

## 연결 개념
- LOC(Line of Code) — 코드량 기반 규모 산정과의 대비 대상
- 맥케이브 순환 복잡도 — FP가 놓치는 구현 난이도 보완 지표
- 소프트웨어사업 대가기준 — FP 기반 국내 SW 사업 비용 산정 근거

# 📝 【답안용】 시험 답안 템플릿

> 목적: 시험장에서 25분에 그대로 쓰는 답안 양식. 작성방식(추상표현 금지·수치·도식·문제유형 전환)을 엄격히 지킨다.
> 핵심: FP 답안은 5종 기능 유형, UFP·VAF·AFP 산출식, 생산성 지수 활용을 함께 제시한다.

## 핵심 인사이트 (3줄 요약)

> 1. **본질**: FP는 EI·EO·EQ·ILF·EIF 5종 기능 요구사항 개수를 계수해 소프트웨어 규모를 정량화하는 기법이다.
> 2. **가치**: 언어·플랫폼과 무관하게 규모를 비교할 수 있어 생산성(FP/인월) 측정과 공수·비용 산정 근거가 된다.
> 3. **판단 포인트**: UFP 산출 등급표, VAF 보정, 생산성 지수 역산 공식을 정확히 제시해야 한다.

## 출제 의도 및 답안 포인트

| 출제 의도 | 반드시 짚을 핵심 | 감점 회피 포인트 |
|:---|:---|:---|
| LOC 대비 FP 우위 이해 확인 | 언어 독립성, 기능 요구사항 기반 계수 | LOC와 FP를 혼용 서술 |
| 산출 공식 이해 확인 | UFP, VAF(0.65~1.35), AFP = UFP × VAF | VAF 곱셈 관계 누락 |
| 생산성 활용 확인 | 생산성 지수 = AFP ÷ 인월, 공수 역산식 | 생산성 정의 없이 결론만 서술 |

> 요약: 이 문제는 5종 기능 분류와 UFP·VAF·AFP 산출식, 생산성 지수 활용 근거를 함께 보여야 한다.

## Ⅰ. 개요 및 필요성

- 개요: 기능 요구사항 개수로 소프트웨어 규모를 산정하는 기법
- 배경: LOC 기반 산정은 언어·개발자 숙련도에 따라 편차가 커서 프로젝트 간 비교가 어려움
- 필요성: 규모 산정, 비용 견적, 생산성(FP/인월) 비교, 프로젝트 간 벤치마킹에 언어 독립적 지표가 필요함

---

## Ⅱ. 구조 및 구성요소

```text
요구사항 분석 -> 트랜잭션 기능 식별 -> 데이터 기능 식별
  -> 복잡도 등급 부여 -> UFP 합산 -> GSC 14개 평가
  -> VAF 산출 -> AFP = UFP x VAF
```

| 구성요소 | 역할 | 산출물 |
|:---|:---|:---|
| EI/EO/EQ | 외부입력·출력·조회 트랜잭션 계수 | 트랜잭션 기능점수 |
| ILF/EIF | 내부논리파일·외부연계파일 계수 | 데이터 기능점수 |
| GSC 14항목 | 분산처리·성능·트랜잭션량 등 보정 요인 평가 | VAF 0.65~1.35 |
| AFP | UFP에 VAF를 곱한 최종 보정 규모 | 생산성·비용 산정 기준값 |

> 요약: FP는 트랜잭션·데이터 기능을 계수한 UFP에 GSC 보정계수 VAF를 곱해 최종 규모를 산출한다.

---

## Ⅲ. 동작원리 및 흐름도

```text
기능 식별 -> 복잡도 등급(단순/보통/복잡) 판정
  -> 가중치 표 조회 -> UFP 합산
  -> VAF 곱셈 -> AFP 확정 -> 생산성 지수 계산
```

| 단계 | 처리 내용 | 검증 기준 |
|:---:|:---|:---|
| 1 | 5종 기능 유형별 데이터요소·파일참조 개수 식별 | 요구사항 명세 완결성 |
| 2 | 복잡도 등급별 IFPUG 가중치 적용 | 등급 분류 일관성 |
| 3 | GSC 14항목 평가 후 VAF 산출 | 0.65~1.35 범위 준수 |
| 4 | AFP 확정 후 생산성 지수·공수 산정 | AFP ÷ 인월 값 신뢰도 |

> 요약: FP 산정은 기능 계수, 등급 가중치, VAF 보정을 거쳐 AFP를 확정하고 이를 생산성·공수 산정에 사용한다.

## Ⅳ. 특징

| 구분 | 내용 | 판단 포인트 |
|:---|:---|:---|
| 장점 | 언어·플랫폼 독립적 규모 비교, 사용자 관점 요구사항 기반 계수 | 프로젝트 간 생산성(FP/인월) 벤치마킹 가능 |
| 한계 | 구현 알고리즘 난이도·비기능 성능 요구는 반영 못 함 | 순환복잡도·정적분석과 병행 필요 |
| 비교 포인트 | LOC는 코드량, FP는 기능 요구사항 개수 | 산정 시점(LOC는 구현 후, FP는 설계 전 가능) |

> 요약: FP는 조기 산정과 언어 독립 비교가 강점이나 구현 난이도는 별도 지표로 보완해야 한다.

## Ⅴ. 심화 비교 및 적용 판단

| 구분 | LOC 기반 산정 | FP 기반 산정 | 선택 기준 |
|:---|:---|:---|:---|
| 산정 시점 | 코드 작성 후에만 가능 | 요구사항·설계 단계부터 가능 | 사전 견적이 필요하면 FP 우선 |
| 언어 의존성 | 언어·개발자 숙련도에 따라 편차 큼 | 기능 요구사항 개수 기반으로 언어 독립적 | 이기종 언어 프로젝트 비교 시 FP |
| 활용 목적 | 코드 유지보수량 추정 | 생산성·비용·공수 산정 | 사업 대가 산정은 FP 기준 채택 |

> 요약: 사전 견적과 이기종 비교에는 FP, 완료 후 코드 유지보수 분석에는 LOC를 함께 사용한다.

| 리스크 | 원인 | 대응 방안 | 확인 지표 |
|:---|:---|:---|:---|
| 등급 오분류 | 데이터요소·파일참조 개수 판단 기준 미숙지 | IFPUG 가이드 기준표 준수, 계수자 교육 | 등급 분류 재검토 편차율 |
| 구현 난이도 과소평가 | FP만으로 알고리즘 복잡도 무시 | 순환복잡도·정적분석 결과 병행 검토 | 모듈별 V(G) 분포 |
| 생산성 지수 왜곡 | 인월 집계 기준(외주 포함 여부) 불일치 | 인월 집계 기준 사전 정의, 프로젝트별 통일 | 인월 집계 표준 준수율 |

> 요약: FP 산정 신뢰도는 등급 분류 정확도, 구현 난이도 보완, 인월 집계 기준 통일로 관리한다.

| 점검 항목 | 목표 기준 | 측정 방법 |
|:---|:---|:---|
| 산정 정확도 | 계수자 간 등급 분류 편차 10% 이내 | 이중 계수 후 교차 검증 |
| 생산성 안정성 | 유사 프로젝트 간 FP/인월 편차 관리 | 과거 프로젝트 생산성 이력 비교 |
| 비용 산정 신뢰도 | AFP 기반 견적과 실제 투입 인월 차이 관리 | 사후 정산 대비 견적 오차율 |

> 요약: FP 활용 성공 여부는 등급 분류 편차, 생산성 지수 안정성, 견적 대비 오차율로 판단한다.

## Ⅵ. 실무 적용 및 결론

**적용 방안 3개 (필수 — 단계별 또는 항목별):**
1. 요구사항 정의 단계에서 EI·EO·EQ·ILF·EIF를 식별해 UFP를 산출하고 계수 기준을 문서화함
2. GSC 14항목 평가로 VAF를 산출하고 AFP를 확정해 소프트웨어사업 대가기준 견적에 반영함
3. 프로젝트 완료 후 실제 투입 인월과 AFP로 생산성 지수를 갱신해 다음 사업 산정 근거로 축적함

**결론 (2줄):**
- 기술사 판단: 사전 견적·이기종 비교는 FP, 완료 후 코드 유지보수 분석은 LOC를 병행 적용함
- 향후 방향: FP 계수 자동화 도구와 정적분석 지표를 결합해 규모 산정과 구현 난이도 평가를 함께 고도화해야 함
