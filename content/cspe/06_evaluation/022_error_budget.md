# 📖 【암기용】 개념 완전 이해

## 한눈에
- **개요**: 오류 예산(Error Budget)은 **SRE 운영 기법**으로, `1 − SLO`로 산출되는 **측정 기간 내 허용 실패 총량**임. 이 예산의 잔량으로 배포 속도를 자동 조절하는 것이 핵심 용도임.
- **왜 필요한가**: SLO를 100%로 설정하면 어떤 변경도 리스크로 간주되어 배포가 멈춤. 예산 개념을 두면 "얼마나 실패해도 되는지"를 숫자로 관리해 안정성과 배포 속도를 같은 기준으로 조율할 수 있음.
- **핵심 직관**: 한 달 용돈(오류 예산)에서 이번 달 이미 다 썼으면 추가 지출(위험한 배포)을 자제하고, 남았으면 투자(실험적 배포)를 허용하는 것과 같음.

## 핵심 용어 정리 (내부에 등장하는 것들)

021이 SLI·SLO 정의와 설정을, 020이 SLA 계약 구조를 다뤘으므로 여기서는 오류 예산 고유의 산출·운영 용어에 집중함.

| 용어/표기 | 의미 | 비유·예 |
|:---|:---|:---|
| 오류 예산 (상위 키워드) | 1−SLO, 측정 기간 내 허용 실패 총량 | 한 달 용돈 한도 |
| 소진율(Burn Rate) | 오류 예산이 소비되는 속도 | 용돈 쓰는 속도(일 평균 지출) |
| 측정 윈도우 | 예산이 리셋되는 주기(7일·30일·90일 롤링) | 용돈 리셋 주기(매월 1일) |
| 배포 게이팅 | 예산 잔량에 따라 배포를 허용·동결하는 자동 통제 | 잔액 부족 시 카드 결제 차단 |
| Freeze(동결) | 예산 임계치 초과 시 신규 배포를 중단하는 정책 | 용돈 바닥나면 지출 금지 |
| SLO(021) | 오류 예산 산출의 분모가 되는 내부 목표치 | 적정 온도 기준 |
| 번 레이트 알림 | 소진 속도가 급증할 때 발동하는 경보 | 지출 급증 알림 |

## 깊이 이해
- **배경·문제의식**: SRE 조직에서 신뢰성 팀은 변경을 줄이려 하고 개발 팀은 배포를 늘리려 해 목표가 충돌함. Google SRE가 이 갈등을 **하나의 숫자**로 중재하기 위해 오류 예산 개념을 제시함. SLO(021)가 목표를 세우는 것이라면, 오류 예산은 그 목표를 **실행 가능한 배포 정책으로 전환**하는 도구임.
- **작동 원리 — 산출과 환산**:
  - 공식: `오류 예산 = (1 − SLO) × 측정 윈도우 시간`.
  - 예: SLO 99.9%(30일) → 오류 예산 = 0.1% × 43,200분 = **43.2분**. 이것이 30일 동안 허용되는 총 실패 시간임.
  - 예: SLO 99.95%(30일) → 오류 예산 = 0.05% × 43,200분 = **21.6분**.
- **작동 원리 — 소진과 게이팅**:
  - 실측 실패(다운타임·오류 요청)를 누적해 예산에서 차감함.
  - 소진율(Burn Rate)을 산출: 현재 소진 속도로 윈도우 종료 전 예산이 바닥나는지 예측함.
  - 소진율이 임계치(예: 80%) 초과 → **Freeze**: 신규 기능 배포 동결, 안정화·롤백 우선.
  - 소진율이 여유 → 실험적 배포·카나리·A/B 테스트 허용.
- **비유**: 한 달 용돈 10만 원 중 첫째 주에 9만 원을 썼다면 남은 3주는 지출(배포)을 자제해야 함. 반대로 첫째 주에 1만 원만 썼으면 투자(실험)를 늘릴 여유가 있음.
- **구체 예시(워크드)**: SLO 99.95%(월간) → 오류 예산 21.6분. 이번 달 18분 소진(대형 장애 1건) → 잔여 3.6분. Burn Rate = 18분/10일 = 1.8분/일 → 윈도우 종료까지 20일 남았으나 잔여 3.6분이므로 2일분만 여유 → **Freeze 발동**, 안정화 우선.
- **흔한 오해·주의점**: ① 오류 예산 소진 ≠ 장애 발생. "이번 측정 기간에 허용치를 초과했다"는 의미로, SLA(020) 위반과는 별개(SLA는 보통 SLO보다 완화된 값). ② 예산이 남았다고 "장애를 내도 된다"는 뜻이 아님 — 예산은 불가피한 실패에 대한 여유지, 의도적 장애 허용이 아님. ③ Freeze 해제 기준을 사전에 문서화하지 않으면 동결이 장기화돼 개발 정체 유발.

## 연결 개념
- **SLO·SLI (021)**: 오류 예산 산출의 분모가 되는 목표치와 실측값. 021이 정의를, 022가 실행 도구를 담당.
- **SLA (020)**: SLA 위반과 오류 예산 소진은 별개 판정 — SLA는 보통 SLO보다 완화된 별도 계약값.
- **자동 페일오버·페일백 (028)**: 장애 복구 속도가 오류 예산 소진량을 직접 좌우함.

# 📝 【답안용】 시험 답안 템플릿

## 핵심 인사이트 (3줄 요약)

> 1. **본질**: 오류 예산은 (1−SLO) × 윈도우 시간으로 산출되는 허용 실패 총량임.
> 2. **가치**: 소진율을 기준으로 배포 속도를 자동 조절해, 안정성과 개발 속도의 충돌을 정량 중재함.
> 3. **판단 포인트**: 소진율 임계치(예: 80%) 초과 시 Freeze, 여유 시 실험 허용이며 Freeze 해제 기준 사전 문서화가 필수임.

## 출제 의도 및 답안 포인트

| 출제 의도 | 반드시 짚을 핵심 | 감점 회피 포인트 |
|:---|:---|:---|
| SLO-오류예산 산출 관계 | (1−SLO) × 윈도우 시간 공식, 수치 환산 | 공식 없이 정성적 설명만 서술 |
| 배포 게이팅 메커니즘 | 소진율 기반 Freeze/허용 정책 | 오류 예산을 장애 지표로만 한정 |
| 측정 윈도우 이해 | 롤링 윈도우·리셋 주기 | 윈도우 없이 누적만 서술 |

> 요약: 산출 공식 + 소진율 기반 배포 게이팅 메커니즘 + 윈도우 리셋을 모두 보여야 함.

---

## Ⅰ. 개요 및 필요성

- 개요: (1−SLO) × 윈도우 시간으로 산출되는 측정 기간 내 허용 실패 총량
- 배경: SLO 100% 설정 시 모든 변경이 리스크로 간주되어 배포 정체 → 안정성·속도 갈등 중재 장치 필요
- 필요성: 예산 소진율을 배포 승인 기준으로 삼아야 신뢰성 목표와 배포 속도를 동일 수치로 조율 가능

---

## Ⅱ. 구조 및 구성요소

```text
SLO(021) 확정 -> 오류 예산 = (1-SLO) x 윈도우 시간 산출
  -> 실측 실패 집계 -> 소진율 계산 -> 임계치 비교
  -> 배포 허용/Freeze -> 윈도우 리셋
```

| 구성요소 | 역할 | 특이사항 |
|:---|:---|:---|
| SLO(021) | 예산 산출 기준값 | 예: 가용성 99.9% |
| 측정 윈도우 | 예산 리셋 주기 | 7일·30일·90일 롤링 |
| 소진 실적 | 실측 실패·다운타임 누적 | 분 또는 요청 실패 수 단위 |
| 소진율(Burn Rate) | 예산 소비 속도 | 급증 시 번 레이트 알림 |
| 게이팅 정책 | 소진율 기반 배포 허용/동결 판단 | Freeze·Canary 축소 등 |

> 요약: SLO에서 예산을 산출하고, 실측 소진율을 임계치와 비교해 배포 정책을 자동 결정하는 구조임.

---

## Ⅲ. 동작원리 및 흐름도

```text
SLO 확정 -> 예산 총량 산출 -> 실패 이벤트 누적 차감
  -> 소진율 산출 -> 임계치(80%) 비교 -> Freeze 또는 배포 허용
```

1. SLO(021)와 윈도우 기준으로 `(1−SLO) × 윈도우 시간`을 계산해 예산 총량을 확정함(예: 99.9%, 30일 → 43.2분)
2. 실측 실패·다운타임 이벤트를 누적 집계해 예산에서 차감하고, 소진율(Burn Rate)을 산출함
3. 소진율이 임계치(예: 80%) 초과 시 신규 기능 배포를 자동 동결(Freeze)하고 안정화·롤백 작업으로 전환함
4. 윈도우 리셋 시점(예: 30일 롤링)에 예산을 초기화하고, SLO 대비 소진 이력을 리뷰해 다음 윈도우 SLO·게이팅 정책을 재산정함

> 요약: 예산 산출 → 소진 차감 → 임계치 비교 → Freeze/허용 → 윈도우 리셋 순으로 순환함.

---

## Ⅳ. 특징

- 정량 중재: 신뢰성 팀과 개발 팀의 목표 갈등을 소진율이라는 하나의 숫자로 중재함
- 자동 전환: 예산 여유 시 실험·카나리 확대 허용, 소진 시 Freeze·롤백 우선으로 정책이 자동 전환됨
- 윈도우 리셋: 측정 기간 종료 시 예산이 초기화되어 Freeze 장기화를 방지함
- SLA 독립: 오류 예산 소진 ≠ SLA(020) 위반. SLA는 SLO보다 완화된 값이므로 별도 판정임
- 한계: Freeze 해제 기준이 없으면 동결이 장기화돼 개발 정체, 외부 장애(서드파티) 소진은 통제 불가

---

## Ⅴ. 심화 비교 및 적용 판단

| 구분 | 정적 배포 승인 | 오류 예산 기반 게이팅 | 선택 기준 |
|:---|:---|:---|:---|
| 승인 기준 | 고정 주기·수동 승인 | SLO 소진율 기반 동적 승인 | SRE 조직·SLO 체계 유무 |
| 배포 속도 | 과도한 검토로 배포 지연 | 예산 여유 시 배포 가속 | 배포 빈도·리드타임 중요도 |
| 장애 연계 | 장애 원인과 배포 관계 불투명 | 소진율로 인시던트-배포 상관 추적 가능 | 인시던트 관리 성숙도 |
| 갈등 해소 | 팀 간 정치적 협상 | 숫자(소진율) 기반 합의 | 조직 내 안정성-속도 갈등 수준 |

> 요약: SLO 체계와 SRE 조직이 갖춰진 서비스는 오류 예산 기반 게이팅이 정적 승인보다 속도·안정성 균형에 유리함.

**리스크·대응:**
- 대형 장애 조기 소진: 단일 인시던트로 예산 대부분 소진 → 원인 배포 즉시 롤백 + 소진율 급증 구간 알림 자동화 (지표: 단건 소진량 비율)
- Freeze 장기화: 해제 기준 부재로 개발 정체 → 윈도우 리셋 시점과 재개 조건(안정화 완료·소진율 정상화)을 사전 문서화 (지표: Freeze 지속 일수)
- 외부 장애 소진: 서드파티 장애가 예산을 부당하게 소진 → 서드파티 SLI를 분리 측정해 내부 예산에서 제외하는 정책 수립 (지표: 외부 원인 소진 비율)

**점검 지표:**
- 성능: 윈도우 종료 시점 예산 소진율 100% 이하 — SLO 대시보드
- 운영: Freeze 발동 정확도(임계치 초과 시 자동 알림 100%) — 배포 파이프라인 게이트 로그

---

## Ⅵ. 실무 적용 및 결론

**적용 방안:**
1. SLO(021) 확정 즉시 `(1−SLO) × 윈도우 시간`으로 오류 예산 총량을 산출해 대시보드에 실시간 표시함
2. CI/CD 파이프라인에 소진율 80% 초과 시 배포 자동 동결(Freeze) 게이트를 삽입하고, Freeze 해제 조건(안정화 완료·소진율 정상화)을 런북에 명시함
3. 윈도우 리셋 주기(30일)마다 SLO 대비 실제 소진 이력을 리뷰하고, SLO 값·임계치·윈도우 길이를 재산정함

**결론:**
- 기술사 판단: 오류 예산은 SLO(021)를 실행 가능한 배포 정책으로 전환하는 정량 중재 장치이며, Freeze 해제 기준 사전 문서화가 실효성의 핵심임
- 향후 방향: 다중 서비스 예산을 조합한 조직 단위 신뢰성 예산 관리와 ML 기반 소진율 예측 자동 게이팅으로 확장 중임
