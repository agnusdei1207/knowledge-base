# 📖 【암기용】 개념 완전 이해

## 한눈에
- **개요**: 성능 테스트(Performance Testing)는 **시스템에 인위적 부하를 가해 응답시간·처리량·자원 사용률을 측정하는 검증 활동**으로, 부하·스트레스·소크·스파이크 등 부하 패턴별 유형으로 나뉜다.
- **왜 필요한가**: 운영 배포 전에 목표 성능 충족 여부와 한계점·누수·순간 폭주 취약성을 미리 드러내, 장애를 사전에 차단하기 위함이다.
- **핵심 직관**: 다리를 개통하기 전 트럭을 올려 본다. 예상 무게(부하)·한계 무게(스트레스)·장시간 통행(소크)·순간 몰림(스파이크)을 각각 다르게 실어 봐야 어디서 무너지는지 안다.

## 핵심 용어 정리 (내부에 등장하는 것들)

각 테스트 유형은 "부하를 어떻게 거는가(양·시간·변화율)"로 갈리므로, 부하 프로파일의 차이를 정확히 구분하는 것이 핵심이다. 맨 위 상위 키워드가 정체성이다.

| 용어/표기 | 의미 | 비유·예 |
|:---|:---|:---|
| 성능 테스트(Performance Testing) | 부하를 가해 성능 지표를 측정하는 검증 활동 | 개통 전 다리에 트럭 올리기 |
| 부하 테스트(Load Test) | 예상 최대 부하까지 걸어 목표 지표 충족 확인 | 설계 하중까지 트럭 올리기 |
| 스트레스 테스트(Stress Test) | 한계 초과까지 밀어 붕괴점·복구 확인 | 무너질 때까지 하중 증가 |
| 소크 테스트(Soak/Endurance) | 중간 부하를 장시간 유지해 누수 확인 | 며칠간 계속 통행시키기 |
| 스파이크 테스트(Spike Test) | 짧은 시간 급격히 부하 폭증 후 관찰 | 순간에 트럭 수십 대 몰림 |
| 처리량 TPS | 초당 처리 트랜잭션 수(003·010 참조) | 다리를 지나는 초당 차량 수 |
| 응답시간(Response Time) | 요청~응답 완료 소요 시간(002 참조) | 진입~통과까지 걸린 시간 |
| 임계점(saturation point) | 부하 증가에도 처리량이 안 오르는 한계 | 더 실어도 통행량 안 느는 지점 |
| 가상 사용자(VU) | 부하 생성기가 흉내내는 동시 사용자 | 트럭을 대신 올리는 로봇 대수 |

## 깊이 이해
- **배경·문제의식**: 기능 테스트는 "맞게 동작하는가"만 보지만, 운영 장애의 상당수는 부하가 몰릴 때 느려지거나 메모리가 새거나 순간 폭증에 무너지는 성능 결함이다. 이를 배포 전에 드러내려면 부하 패턴을 의도적으로 설계해 가하는 별도 검증이 필요하다는 문제의식이다.
- **작동 원리(어떻게+왜)**: 가상 사용자(VU)를 늘려 목표 TPS를 만들고, 램프업(점증)→유지(sustain)→램프다운 구간으로 부하 프로파일을 설계한다. 부하를 올리며 응답시간·TPS·CPU·메모리를 동시에 기록하면, 처리량이 더 안 오르는 임계점(saturation)과 응답시간이 급증하는 무릎(knee) 지점이 드러난다 — 이 곡선의 형태가 시스템의 한계를 말해 준다.
- **비유**: 러닝머신 속도를 서서히 올리며 심박·호흡을 잰다. 평소 속도(부하)·한계 속도(스트레스)·장거리 지속(소크)·갑작스런 전력질주(스파이크)를 나눠 재야 어떤 상황에서 쓰러지는지 알 수 있다.
- **구체 예시(워크드)**: 목표가 500 TPS·응답시간 200ms 이내인 서비스라면 — 부하 테스트로 VU를 늘려 500 TPS에서 200ms 충족을 확인하고, 스트레스로 800 TPS까지 밀어 700 TPS에서 응답시간이 2초로 꺾이는 임계점을 찾고, 소크로 300 TPS를 12시간 유지해 힙 메모리가 시간당 증가하는 누수를 잡고, 스파이크로 5초 만에 0→1000 VU를 던져 오토스케일링 반응 지연을 검증한다.
- **흔한 오해·주의점**: ① 부하 테스트와 스트레스 테스트를 혼용하는 오해 — 전자는 목표 부하 충족 확인, 후자는 한계 초과 붕괴·복구 확인으로 목적이 다르다. ② 짧은 테스트만 하면 메모리 누수·커넥션 고갈 같은 장시간 결함(소크로만 잡힘)을 놓친다. ③ 테스트 환경이 운영과 다르면(데이터량·네트워크) 결과를 그대로 신뢰할 수 없어 운영 유사 환경이 전제다.

## 연결 개념
- 응답 시간 분해(002)·처리량(003) — 성능 테스트가 측정하는 핵심 지표의 정의 제공
- BMT 방법론(015) — 성능 테스트를 발주·검증 절차로 표준화한 벤치마크 테스트 체계
- APM(011) — 테스트 중 구간별 병목·자원 사용률을 실시간 관측하는 도구

# 📝 【답안용】 시험 답안 템플릿

## 핵심 인사이트 (3줄 요약)

> 1. **본질**: 성능 테스트는 부하 패턴(부하·스트레스·소크·스파이크)을 설계해 응답시간·TPS·자원 사용률을 측정하는 검증 활동임.
> 2. **가치**: 배포 전 목표 충족·한계점·메모리 누수·순간 폭주 취약성을 드러내 운영 장애를 사전 차단함.
> 3. **판단 포인트**: 목적별로 유형을 조합해야 하며, 운영 유사 환경과 장시간 소크 없이는 결함을 놓침.

## 출제 의도 및 답안 포인트

| 출제 의도 | 반드시 짚을 핵심 | 감점 회피 포인트 |
|:---|:---|:---|
| 유형별 목적 구분 확인 | 부하·스트레스·소크·스파이크 목적 차이 | 부하와 스트레스 목적 혼용 |
| 측정 지표 이해 확인 | 응답시간·TPS·자원 사용률·임계점 | 지표 없이 유형 나열만 |
| 실무 적용 확인 | 목표 기반 시나리오·운영 유사 환경 | 단일 유형만 수행 전제 |

> 요약: 유형 나열이 아니라 목적 차이와 측정 지표·환경 전제를 함께 보여야 함.

---

## Ⅰ. 개요 및 필요성

- 개요: 인위적 부하를 가해 응답시간·처리량·자원 사용률을 측정하는 검증 활동으로 부하 패턴별 유형으로 구분
- 배경: 기능 테스트가 못 잡는 부하 상황의 지연·누수·폭주 취약성이 운영 장애의 주원인
- 필요성: 배포 전 목표 성능 충족과 한계점·장기 안정성을 검증해 장애를 사전 차단하기 위함

---

## Ⅱ. 구조 및 구성요소

- 부하 프로파일 구조(선형 구조도):

```text
가상 사용자(VU) 생성 -> 램프업(부하 점증) -> 유지(sustain) -> 램프다운
  -> 지표 수집(응답시간/TPS/CPU/메모리)
  -> 임계점·무릎 지점 분석 -> 리포트
```

| 구성요소 | 역할 | 특이사항 |
|:---|:---|:---|
| 부하 생성기 | VU로 목표 TPS 부하 발생 | JMeter·k6·nGrinder |
| 부하 프로파일 | 램프업·유지·램프다운 설계 | 유형별 형태가 다름 |
| 지표 수집 | 응답시간·TPS·자원 사용률 기록 | APM(011) 연계 |
| 분석 | 임계점·knee·누수 판별 | 목표 대비 합격 판정 |

> 요약: VU로 부하 프로파일을 만들고 지표를 수집해 임계점과 결함을 분석함.

---

## Ⅲ. 동작원리 및 흐름도

- 성능 테스트 수행 흐름(선형 흐름도):

```text
목표 지표·시나리오 정의 -> 운영 유사 환경 구성 -> 부하 프로파일 설계
  -> 부하 인가 + 지표 수집 -> 임계점·누수 분석 -> 튜닝 후 재수행
```

1. 목표 TPS·응답시간·동시 사용자와 테스트 유형별 시나리오를 정의함
2. 데이터량·네트워크를 운영과 유사하게 맞춘 환경을 구성함
3. 유형에 맞는 부하 프로파일(부하는 목표까지, 스트레스는 한계 초과, 소크는 장시간, 스파이크는 급증)로 부하를 인가하며 지표를 수집함
4. 임계점·응답시간 무릎·메모리 누수를 분석하고 병목을 튜닝한 뒤 회귀 검증을 위해 재수행함

---

## Ⅳ. 특징

- 부하를 거는 방식(양·지속시간·변화율)에 따라 목적이 다른 유형으로 나뉨
- 부하 테스트는 목표 부하에서의 지표 충족을, 스트레스 테스트는 한계 붕괴점과 복구력을 확인함
- 소크 테스트는 중간 부하 장시간 유지로 메모리 누수·커넥션 고갈 등 시간 의존 결함을 드러냄
- 스파이크 테스트는 순간 폭증에 대한 오토스케일링·큐잉의 대응 지연을 검증함
- 결과 신뢰성은 운영 유사 환경과 충분한 지속시간에 좌우되어 환경·시간 설계가 전제임

---

## Ⅴ. 심화 비교 및 적용 판단

- 유형별 부하 프로파일·목적 비교:

| 구분 | 부하 테스트 | 스트레스 테스트 | 소크 테스트 | 스파이크 테스트 |
|:---|:---|:---|:---|:---|
| 부하 수준 | 예상 최대까지 | 한계 초과까지 | 중간 부하 | 순간 폭증 |
| 지속 시간 | 수십 분~시간 | 붕괴 시점까지 | 수 시간~수일 | 수 초~수 분 |
| 확인 대상 | 목표 지표 충족 | 붕괴점·복구력 | 메모리 누수·안정성 | 폭주 대응·회복 |
| 대표 결함 | 응답시간 초과 | 임계점 붕괴 | 리소스 누수 | 스케일링 지연 |

> 요약: 목표 검증은 부하, 한계 파악은 스트레스, 장기 안정성은 소크, 순간 폭주는 스파이크로 목적에 맞춰 조합함.

- 리스크와 대응(불릿):
  - 환경 불일치 → 축소 환경 결과를 운영에 오적용 → 데이터량·네트워크를 운영과 정합(확인: 환경 대비표)
  - 유형 편중 → 부하만 하고 소크·스파이크 누락 → 목적별 유형을 시나리오에 포함(확인: 유형 커버리지)
  - 부하 도구 병목 → 생성기가 먼저 한계 → 분산 부하 생성·생성기 자원 모니터(확인: 생성기 CPU·네트워크)

---

## Ⅵ. 실무 적용 및 결론

- 적용 방안:
  1. 목표 TPS·응답시간 SLA를 기준으로 부하 테스트를 설계하고 nGrinder·k6·JMeter로 VU를 램프업해 임계점을 식별함
  2. 릴리스 파이프라인에 소크(12시간+)·스파이크 테스트를 정기 편성해 메모리 누수와 오토스케일링 지연을 사전 검출함
  3. 테스트 중 APM(011)으로 구간별 병목·자원 사용률을 실시간 수집해 튜닝 근거를 확보함
- 결론:
  - 성능 테스트는 단일 유형이 아니라 목적별(부하·스트레스·소크·스파이크) 조합으로 설계해야 사각지대를 없앰
  - 운영 유사 환경과 충분한 지속시간을 전제로 임계점·누수를 정량화해 용량 산정·SLA 근거로 연계할 필요가 있음
