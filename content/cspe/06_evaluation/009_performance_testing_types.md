# 📖 【암기용】 개념 완전 이해

> 목적: 성능 테스트 4종이 서로 다른 목적(용량 확인·한계 파악·장기 안정성·급증 대응)을 갖는다는 점을 이해하게 만든다. 시험 답안 양식이 아니라, 이해를 위한 친절한 설명이다.

## 한눈에
- **개요**: 부하테스트(예상 트래픽 검증)·스트레스테스트(한계 이상 부하로 breaking point 확인)·소크테스트(장시간 지속 부하로 누적 결함 확인)·스파이크테스트(급격한 순간 폭증 대응 확인) 4종의 성능 검증 방법
- **왜 필요한가**: 한 가지 테스트만으로는 "평상시 잘 버티는지", "한계는 어디인지", "오래 켜두면 문제가 없는지", "갑자기 몰리면 견디는지"를 모두 확인할 수 없음
- **핵심 직관**: 자동차를 살 때 일반 도로 주행(부하), 최고속 주행 한계 확인(스트레스), 장거리 연속 운행(소크), 급가속 반응(스파이크)을 각각 다르게 테스트하는 것과 같음

## 깊이 이해
- **배경·문제의식**: 신규 시스템 오픈 전 부하테스트만 통과시키고 배포하면, 장시간 운영 중 메모리 누수나 이벤트성 트래픽 폭증 상황을 대비하지 못해 운영 중 장애로 이어짐
- **작동 원리**: 부하테스트는 예상 트래픽 수준을 유지하며 목표 TPS·응답시간 달성 여부를 확인하고, 스트레스테스트는 부하를 계속 늘려 시스템이 정상 처리 한계를 넘어 실패하는 지점(breaking point)과 실패 양상을 관찰하며, 소크테스트는 예상 부하를 장시간(수 시간~수 일) 유지해 메모리 누수·자원 고갈·성능 저하를 탐지하고, 스파이크테스트는 짧은 시간에 부하를 급격히 증가·감소시켜 시스템의 급변 대응력을 확인
- **비유**: 마라톤 선수 체력 측정 시 평소 페이스 유지(부하), 한계까지 전력질주(스트레스), 장거리 완주 지구력(소크), 구간 스퍼트 대응(스파이크)을 각각 다르게 측정하는 것과 같음
- **구체 예시**: 예시로 이커머스 서비스가 평시 TPS 500을 부하테스트로 검증하고, 스트레스테스트로 TPS 1,200에서 오류율이 급증하는 한계점을 확인하며, 소크테스트로 72시간 지속 운영 후 메모리 사용량이 지속 증가하는 누수를 발견하고, 스파이크테스트로 세일 시작 순간 TPS가 10초 만에 500에서 3,000으로 급증하는 상황에서 응답시간이 어떻게 변하는지 확인
- **흔한 오해·주의점**: 스트레스테스트는 "시스템을 망가뜨리는 것이 목적"이 아니라 한계와 실패 양상(graceful degradation 여부)을 파악하는 것이 목적이며, 소크테스트를 스트레스테스트와 혼동해 짧은 시간에 높은 부하만 주는 것으로 대체하면 안 됨

## 연결 개념
- 시스템 성능 지표(TPS·응답시간) — 각 테스트에서 측정하는 공통 지표
- 병목 분석 — 스트레스·소크테스트에서 발견된 병목 자원을 특정하는 절차
- 큐잉 이론 — 스파이크테스트에서 순간 도착률 급증 시 대기행렬 급증을 설명하는 근거

# 📝 【답안용】 시험 답안 템플릿

> 목적: 시험장에서 25분에 그대로 쓰는 답안 양식. 작성방식(추상표현 금지·수치·도식·문제유형 전환)을 엄격히 지킨다.
> 핵심: 성능 테스트 답안은 4종 테스트의 목적·부하 패턴 차이, 각 테스트로 발견하는 결함 유형, 배포 전 필수 조합을 함께 제시한다.

## 핵심 인사이트 (3줄 요약)

> 1. **본질**: 성능 테스트는 목적에 따라 부하(예상 트래픽 검증)·스트레스(한계 확인)·소크(장기 안정성)·스파이크(급증 대응) 4종으로 구분한다.
> 2. **가치**: 각 테스트가 서로 다른 결함(용량 부족, 붕괴 지점, 누적 누수, 순간 폭증 취약점)을 발견하므로 하나만으로는 배포 위험을 커버할 수 없다.
> 3. **판단 포인트**: 신규 배포 전 4종을 모두 조합하되, 이벤트성 트래픽이 예상되면 스파이크테스트를, 장기 운영 서비스면 소크테스트를 반드시 포함한다.

## 출제 의도 및 답안 포인트

| 출제 의도 | 반드시 짚을 핵심 | 감점 회피 포인트 |
|:---|:---|:---|
| 4종 테스트 정의 구분 확인 | 부하·스트레스·소크·스파이크 각각의 목적과 부하 패턴 | 스트레스테스트와 스파이크테스트를 동일 개념으로 서술 |
| 발견 결함 유형 구분 확인 | 소크=누적 누수, 스파이크=급증 대응, 스트레스=붕괴 지점 | 모든 테스트가 같은 결함(단순 응답 지연)만 찾는다고 서술 |
| 배포 전 조합 전략 확인 | 서비스 특성별 필수 테스트 조합 | 부하테스트 하나만으로 배포 준비 완료로 서술 |

> 요약: 이 문제는 테스트 명칭 나열보다 목적·부하 패턴·발견 결함 유형의 차이와 조합 전략을 보여야 한다.

## Ⅰ. 개요 및 필요성

- 정의: 시스템 성능·안정성을 검증하기 위해 목적별로 부하 패턴을 다르게 설계한 4종의 테스트 기법
- 구분: 부하(예상 트래픽 유지)·스트레스(한계 초과 부하)·소크(장시간 지속 부하)·스파이크(급격한 순간 폭증)
- 필요성: 배포 전 용량 검증, 한계점 파악, 장기 운영 안정성, 이벤트성 폭증 대응력을 각각 확인해야 운영 리스크를 최소화할 수 있음

---

## Ⅱ. 구조 및 구성요소

```text
테스트 계획 수립 -> 부하 패턴 정의(부하/스트레스/소크/스파이크)
  -> 시나리오 실행 -> 지표 수집(TPS/응답시간/오류율/자원 사용률)
  -> 결과 분석 -> 병목·결함 보고서 작성
```

| 구성요소 | 역할 | 특이사항 |
|:---|:---|:---|
| 부하테스트 | 예상 트래픽에서 목표 성능 달성 확인 | 평시 피크 TPS 기준 |
| 스트레스테스트 | 부하를 점증시켜 붕괴 지점 확인 | 오류율 급증 임계점 관찰 |
| 소크테스트 | 예상 부하를 장시간 유지 | 수 시간~수 일, 메모리·자원 추이 관찰 |
| 스파이크테스트 | 부하를 짧은 시간에 급증·급감 | 초 단위 급변, 오토스케일링 반응 확인 |

> 요약: 4종 테스트는 서로 다른 부하 패턴으로 실행되며 각각 다른 지표 추이를 관찰 대상으로 삼는다.

---

## Ⅲ. 동작원리 및 흐름도

```text
테스트 목적 정의 -> 부하 패턴 설계(수준/지속시간/변화율)
  -> 부하 생성 도구로 시나리오 실행 -> 실시간 지표 모니터링
  -> 임계점·이상 징후 기록 -> 결과 분석 및 개선 조치 도출
```

| 단계 | 처리 내용 | 검증 기준 |
|:---:|:---|:---|
| 1 | 테스트 목적과 부하 패턴(수준·지속시간) 설계 | 목적별 시나리오 문서화 |
| 2 | 부하 생성 도구로 트래픽 발생 | 목표 부하 수준 도달 여부 |
| 3 | TPS·응답시간·오류율·자원 사용률 실시간 수집 | 지표 임계값 초과 시점 |
| 4 | 결과 분석 후 병목·결함 개선 조치 도출 | 재현 테스트로 개선 검증 |

> 요약: 목적에 맞는 부하 패턴을 설계해 실행하고, 임계점과 이상 징후를 실시간으로 기록해 개선 조치로 연결한다.

## Ⅳ. 특징

| 구분 | 부하테스트 | 스트레스테스트 | 소크테스트 | 스파이크테스트 |
|:---|:---|:---|:---|:---|
| 목적 | 예상 트래픽에서 목표 성능 검증 | 한계 초과 시 붕괴 지점·실패 양상 확인 | 장시간 지속 부하로 누적 결함 확인 | 급격한 순간 폭증 대응력 확인 |
| 부하 패턴 | 평시 피크 수준 유지 | 목표치 이상으로 지속 증가 | 예상 부하로 장시간(수 시간~수 일) 유지 | 초 단위 급증 후 급감 반복 |
| 주요 발견 결함 | 용량 부족, 목표 미달 | 오류율 급증 임계점, 장애 전파 | 메모리 누수, 커넥션 고갈, 성능 저하 | 오토스케일링 지연, 큐 폭증 |
| 판정 지표 | TPS·응답시간 목표 달성 여부 | breaking point TPS, 오류율 곡선 | 자원 사용량 추이(메모리·커넥션) | 급증 구간 응답시간, 스케일 아웃 소요시간 |

> 요약: 4종 테스트는 목적·부하 패턴·발견 결함 유형이 모두 달라 서로 대체할 수 없다.

## Ⅴ. 심화 비교 및 적용 판단

| 비교 축 | 정기 운영 서비스 | 이벤트성 트래픽 서비스 | 선택 기준 |
|:---|:---|:---|:---|
| 필수 테스트 | 부하 + 소크테스트 우선 | 부하 + 스파이크 + 스트레스테스트 우선 | 트래픽 패턴의 예측 가능성으로 판단 |
| 리스크 초점 | 장시간 운영 중 자원 누수 | 순간 폭증 시 오토스케일링 지연 | 이벤트 예정(세일·티켓 오픈) 여부 |
| 테스트 주기 | 정기 배포마다 소크테스트 병행 | 이벤트 직전 스파이크테스트 필수 | 서비스 특성별 테스트 캘린더 수립 |

> 요약: 정기 서비스는 소크테스트, 이벤트성 서비스는 스파이크·스트레스테스트를 우선순위로 조합한다.

| 리스크 | 원인 | 대응 방안 | 확인 지표 |
|:---|:---|:---|:---|
| 배포 후 메모리 누수 장애 | 소크테스트 생략, 부하테스트만 수행 | 배포 전 장시간 소크테스트 의무화 | 메모리·커넥션 사용량 추이 |
| 이벤트 시 서비스 다운 | 스파이크테스트 없이 평시 부하로만 검증 | 이벤트 직전 스파이크테스트로 오토스케일링 검증 | 급증 구간 응답시간, 스케일 아웃 소요시간 |
| 한계점 미파악 | 스트레스테스트 없이 목표 TPS만 확인 | 목표치 초과 부하로 breaking point 사전 파악 | 오류율 급증 임계 TPS |

> 요약: 테스트 종류를 누락하면 각기 다른 유형의 배포 후 장애로 이어지므로 목적별 테스트를 모두 조합해야 한다.

| 점검 항목 | 목표 기준 | 측정 방법 |
|:---|:---|:---|
| 부하테스트 통과 기준 | 목표 TPS에서 p95 응답시간 SLO 이내 | 부하 생성 도구, APM |
| 스트레스 한계점 | breaking point TPS와 실패 양상 문서화 | 점증 부하 테스트, 오류율 모니터링 |
| 소크 안정성 | 장시간 운영 후 자원 사용량 증가율 목표치 이내 | 장시간 모니터링, 메모리 프로파일러 |
| 스파이크 대응력 | 급증 구간 오토스케일링 완료 시간 목표치 이내 | 스파이크 시나리오 테스트, 스케일링 로그 |

> 요약: 도입 후 성공 여부는 4종 테스트 각각의 통과 기준(목표 TPS, breaking point, 자원 증가율, 스케일링 시간)으로 판단한다.

## Ⅵ. 실무 적용 및 결론

**적용 방안 3개 (필수 — 단계별 또는 항목별):**
1. 신규 배포 전 부하테스트로 목표 TPS·응답시간 달성 여부를 확인하고 스트레스테스트로 breaking point를 문서화함
2. 장기 운영 서비스는 배포 전 수 시간 이상 소크테스트를 의무화해 메모리 누수·자원 고갈을 사전 탐지함
3. 이벤트성 트래픽이 예상되는 서비스는 스파이크테스트로 오토스케일링 반응 시간을 사전 검증함

**결론 (2줄):**
- 기술사 판단: 성능 테스트는 4종을 목적별로 조합해야 배포 후 장애 유형을 사전에 포괄적으로 예방할 수 있음
- 향후 방향: CI/CD 파이프라인에 부하·스트레스·소크·스파이크테스트를 자동화 단계로 편입해 배포 전 상시 검증 체계로 발전시켜야 함
