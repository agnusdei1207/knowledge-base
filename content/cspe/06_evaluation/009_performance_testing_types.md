# 📖 【암기용】 개념 완전 이해

## 한눈에
- **개요**: 성능 테스트(Performance Testing)는 시스템의 응답성, 처리량, 확장성 및 안정성을 확인하기 위해 **다양한 부하 시나리오를 인위적으로 생성하여 시스템의 거동을 검증**하는 품질 보증 활동이다.
- **왜 필요한가**: 실제 운영 환경에서 예상치 못한 트래픽 폭증이나 장시간 가동에 따른 리소스 고갈로 발생하는 **대형 장애(System Crash)를 사전에 방지**하기 위함이다.
- **핵심 직관**: 신차를 출시하기 전 일반 도로 주행(**부하**), 한계 속도 주행(**스트레스**), 며칠 밤낮 주행(**소크**), 급가속/급제동(**스파이크**)을 반복하며 차량의 성능과 내구성을 테스트하는 것과 같다.

## 핵심 용어 정리

| 용어/표기 | 의미 | 기술적 포인트 |
|:---|:---|:---|
| **Vuser** (Virtual User) | 시스템에 부하를 가하는 가상 사용자 | 실제 사용자의 행위를 스크립트로 모사 |
| **Ramp-up / Ramp-down** | 부하를 서서히 올리고 내리는 구간 | 시스템의 적응 및 회복력을 관찰 |
| **Throughput (TPS)** | 초당 처리된 트랜잭션 건수 | 시스템의 처리 역량 지표 |
| **Knee Point** | 응답 시간이 급격히 증가하기 시작하는 변곡점 | 최적의 부하 수용 한계점 |
| **Saturation Point** | 처리량이 더 이상 늘지 않는 포화 지점 | 시스템의 절대적 물리 한계치 |

## 깊이 이해
- **유형별 목적의 명확화**:
  - **Load Test (부하)**: "우리 시스템이 원래 목표했던 1,000 TPS를 견디는가?" (SLA 준수 여부 확인)
  - **Stress Test (스트레스)**: "1,000 TPS를 넘어 2,000, 3,000까지 밀어붙이면 언제 무너지는가? 무너진 후 스스로 살아나는가?" (한계점 및 복원력 확인)
  - **Soak Test (소크)**: "평상시 부하로 72시간 동안 켜두면 메모리 누수나 커넥션 누수가 생기지 않는가?" (장기 안정성 확인)
  - **Spike Test (스파이크)**: "수강신청이나 티켓팅처럼 1초 만에 사용자가 100배 늘면 시스템이 버티는가?" (급격한 부하 변동 대응력 확인)
- **성능 곡선 분석**: 부하를 늘림에 따라 TPS는 선형적으로 늘어나다 Saturation Point에서 멈추고, 응답 시간은 Knee Point에서 기하급수적으로 폭증한다. 이 두 지점을 찾는 것이 성능 테스트의 핵심이다.
- **비유 (엘리베이터)**:
  - **부하**: 정원 15명에 맞춰 15명을 태우고 잘 올라가는지 봄.
  - **스트레스**: 20명, 30명을 태워서 언제 경보가 울리고 멈추는지 봄.
  - **소크**: 하루 종일 쉬지 않고 엘리베이터를 가동해 모터 과열을 봄.
  - **스파이크**: 한꺼번에 15명이 뛰어 들어올 때의 충격을 봄.

## 연결 개념
- **시스템 성능 지표(001)**: 테스트를 통해 측정하려는 데이터(TPS, RT).
- **APM(011)**: 테스트 중 내부 병목을 실시간으로 관찰하는 도구.
- **SLA(020)**: 성능 테스트 합격 여부를 판정하는 비즈니스 기준.

# 📝 【답안용】 시험 답안 템플릿

## 핵심 인사이트 (3줄 요약)

> 1. **본질**: 성능 테스트는 단순한 '부하 인가'를 넘어, 부하 패턴(부하·스트레스·소크·스파이크)의 차별화된 설계를 통해 시스템의 **한계와 안정성을 입체적으로 검증**하는 활동임.
> 2. **지표**: TPS와 응답 시간의 상관관계 분석을 통해 **Knee Point(최적점)**와 **Saturation Point(임계점)**를 도출하여 인프라 증설 및 튜닝의 근거로 활용함.
> 3. **가치**: 장시간 부하를 통한 **리소스 누수(Leak)** 발견과 급격한 부하 변동에 대한 **자동 확장(Auto-scaling) 메커니즘의 유효성**을 검증하여 운영 안정성을 확보함.

## 출제 의도 및 답안 포인트

| 출제 의도 | 반드시 짚을 핵심 | 감점 회피 포인트 |
|:---|:---|:---|
| 성능 테스트 4대 유형의 구분 | 부하, 스트레스, 소크, 스파이크의 목적과 차이 | 유형별 이름만 나열하지 말고 '부하 패턴 그래프'와 연계 |
| 성능 측정 및 분석 기법 | Knee Point, Saturation Point의 개념 | 단순히 "느려진다"가 아닌 지표의 변곡점을 기술할 것 |
| 테스트 설계 및 수행 절차 | 시나리오 설계, 환경 구성, 지표 수집 및 분석 | 도구(JMeter 등) 사용법이 아닌 '테스트 전략' 중심 기술 |

## Ⅰ. 성능 테스트(Performance Testing)의 개요

### 1. 정의
- 시스템의 처리량, 응답시간, 자원 사용률 등을 측정하여 목표 성능 달성 여부와 한계를 검증하는 일련의 활동

### 2. 성능 테스트의 3대 목표
- **합격 판정**: SLA(Service Level Agreement)에 명시된 성능 목표 달성 확인
- **한계 파악**: 시스템이 무너지는 지점과 복구 가능성 진단
- **병목 제거**: 자원 경합이 발생하는 핫스팟(Hotspot)을 찾아 튜닝

---

## Ⅱ. 성능 테스트의 4대 주요 유형 및 특징

### 1. 유형별 부하 패턴 및 목적 비교

| 유형 | 부하 패턴 (Load Profile) | 주요 목적 | 검증 포인트 |
|:---|:---|:---|:---|
| **Load Test** | 예상 최대 부하 유지 | 목표 성능(SLA) 충족 여부 | 응답시간, 처리량 달성률 |
| **Stress Test** | 한계치 초과 부하 인가 | 시스템의 파괴점 및 복구력 | 붕괴 지점(Point of Failure) |
| **Soak Test** | 일정한 부하 장시간 유지 | 리소스 누수 및 장기 안정성 | Memory Leak, File Descriptor |
| **Spike Test** | 순간적 부하 폭증 | 급격한 변동에 대한 대응성 | Auto-scaling 반응 속도 |

### 2. 성능 지표 상관관계 그래프 (The Performance Curve)

```text
    Response Time / Throughput
      ^
      |                RT (Response Time)
      |               /
      |      ________/ <--- Knee Point (최적 한계)
      |     /  ______------ TPS (Throughput)
      |____/--/________ <--- Saturation Point (물리 한계)
      +-------------------> Load (Vusers)
```

---

## Ⅲ. 성능 테스트 수행 프로세스 및 구성 요소

### 1. 수행 5단계 절차
1. **분석/계획**: 대상 업무 선정, 목표 지표(TPS, RT) 및 시나리오 확정
2. **환경 구성**: 운영 유사 환경(Staging) 구축 및 테스트 데이터 준비
3. **스크립트 개발**: Vuser 행위를 모사하는 부하 스크립트 작성 (JMeter, k6 등)
4. **테스트 수행**: 부하 인가 및 자원 모니터링 (APM 연계)
5. **결과 분석**: 병목 구간 특정, 튜닝 포인트 도출 및 보고

### 2. 핵심 구성 요소

| 요소 | 역할 | 비고 |
|:---|:---|:---|
| **Generator** | 가상 사용자 부하를 실제로 생성하는 서버 | 부하 분산 처리 기능 필수 |
| **Controller** | 테스트 시나리오 제어 및 전체 노드 관리 | 테스트 중앙 통제 |
| **Agent** | 생성기에 설치되어 부하를 인가하는 모듈 | 가상 사용자 엔진 |
| **Monitor/APM** | 서버 내부 자원 및 트랜잭션 흐름 관측 | Bottleneck 탐지의 핵심 |

---

## Ⅳ. 성능 테스트 분석의 핵심: 임계치 판정 기준

- **Knee Point**: 응답 시간이 증가하기 시작하는 지점. 실무적으로 **'정상 서비스 한계'**로 간주.
- **Saturation Point**: CPU/Memory 이용률이 100%에 도달하여 처리량이 꺾이는 지점. **'시스템 붕괴 지점'**으로 간주.
- **Error Rate**: 부하 증가에 따라 에러 발생률이 1%를 상회할 경우 성능 목표 미달로 판정.

---

## Ⅴ. 실무적 고려사항 및 실패 방지 전략

- **Think Time 반영**: 실제 사용자처럼 페이지 간 대기 시간을 스크립트에 포함하여 과도한 부하(DDoS 공격 형태) 방지.
- **Data Cleanup**: 각 테스트 수행 전후 DB 및 로그 데이터를 초기화하여 결과의 일관성(Repeatability) 확보.
- **Isolation**: 외부 인터페이스(API) 등 통제 불가능한 구간은 **Stub/Mock**을 활용하여 테스트 대상 시스템의 순수 성능 측정.

---

## Ⅵ. 결론 및 제언

- 성능 테스트는 단순히 **"빨리 돌아가는가"**를 보는 것이 아니라, **"안전하게 지켜낼 수 있는가"**를 검증하는 보험과 같음.
- 최근 클라우드 환경에서는 고정된 서버 성능보다 **Auto-scaling의 탄력성(Elasticity)**을 검증하는 스파이크 테스트와 소크 테스트의 비중이 더욱 커지고 있는 추세임.
