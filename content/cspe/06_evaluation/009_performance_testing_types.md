## 미리 알고가기

- Load Test: 예상 정상 부하에서 목표 성능을 만족하는지 확인하는 시험임
- Stress Test: 한계 이상 부하를 주어 파괴점과 복구 거동을 확인하는 시험임
- Soak Test: 장시간 부하를 유지해 누수와 성능 저하 누적을 확인하는 시험임
- Spike Test: 짧은 시간의 급격한 부하 증가에 대한 응답과 회복을 확인하는 시험임
- Ramp-up: 부하를 목표 수준까지 점진적으로 올리는 구간임

## Ⅰ. 개요

- **정의/개념**: 성능 테스트는 목표 부하와 비정상 부하를 재현해 처리량, 응답시간, 오류율, 자원 사용률이 운영 기준을 만족하는지 검증하는 시험 활동임
- **배경/필요성**: 기능이 정상이어도 피크 트래픽, 장시간 운영, 순간 폭증에서 장애가 발생할 수 있으므로 운영 조건별 시험 유형을 나누어 검증해야 함

## Ⅱ. 특징

- 시험 유형은 도구가 아니라 부하 패턴과 확인하려는 위험으로 구분함
- 목표 TPS 달성 여부만으로는 부족하고 응답시간, 오류율, 자원 포화 지점을 함께 봐야 함
- 테스트 데이터, 계정, 외부 연동 모의가 실제 업무 비율과 다르면 결과 해석이 흔들림
- 성능 시험 결과는 튜닝 전후 비교가 가능하도록 같은 시나리오와 같은 측정 기준으로 반복해야 함

## Ⅲ. 종류 및 비교

| 시험 유형 | 부하 패턴 | 확인 대상 | 주요 지표 |
|:---|:---|:---|:---|
| Load Test | 예상 정상 또는 피크 부하를 인가함 | 목표 성능 충족 여부 | TPS, p95 latency, error rate |
| Stress Test | 한계 이상 부하까지 올림 | 파괴점과 장애 후 거동 | saturation point, timeout, recovery time |
| Soak Test | 일정 부하를 장시간 유지함 | 메모리 누수와 성능 저하 누적 | heap growth, GC time, handle count |
| Spike Test | 짧은 시간에 부하를 급증시킴 | 급증 대응과 회복 시간 | queue depth, autoscale time, p99 latency |

## Ⅳ. 구성요소 및 구조

| 구성요소 | 설명 |
|:---|:---|
| 시나리오 | 사용자 행동, 업무 비율, Think Time을 정의해 실제 부하 패턴을 재현함 |
| 부하 발생기 | 목표 동시 사용자와 요청률을 만들어 시스템에 트래픽을 인가함 |
| 관측 지표 | 응답시간, 처리량, 오류율, 자원 사용률을 수집해 합격 기준과 비교함 |
| 병목 분석 도구 | APM, 로그, metric을 연결해 실패 원인을 시험 중 확인함 |

```text
+-----------+     +-----------+     +-----------+     +-----------+
| 시나리오 작성 | --> | 부하 인가    | --> | 지표 수집    | --> | 결과 판정    |
+-----------+     +-----------+     +-----------+     +-----------+
```

## Ⅴ. 원리 및 절차 흐름도

```text
+-----------+     +-----------+     +-----------+     +-----------+
| 목표 설정    | --> | 환경 구성    | --> | 시험 실행    | --> | 원인 분석    |
+-----------+     +-----------+     +-----------+     +-----------+
```

1. **목표 설정**: 목표 TPS, p95 응답시간, 오류율, 지속 시간을 정함
2. **환경 구성**: 테스트 데이터, 계정, 외부 연동 mock, 모니터링을 준비함
3. **시험 실행**: 유형별 부하 패턴에 따라 트래픽을 인가하고 지표를 수집함
4. **원인 분석**: 목표 미달 구간의 병목과 실패 원인을 trace와 metric으로 확인함

## Ⅵ. 실무 적용 및 유의점

1. 릴리스 전 성능 검증에서는 Load Test만으로 장시간 누수를 확인할 수 없으므로 Soak Test를 별도로 수행하고 heap growth와 GC pause trend로 확인함
2. 이벤트 서비스에서는 평균 부하보다 순간 폭증이 장애를 만들 수 있으므로 Spike Test를 수행하고 queue depth, autoscale delay, p99 latency로 확인함

## Ⅶ. 결론

성능 테스트 유형의 선택 기준은 시험 도구가 아니라 정상 부하, 한계 부하, 장시간 부하, 순간 폭증 중 어떤 운영 위험을 검증할지임.

## 작성 근거(검토용)

- 131회 기출 키워드이므로 유형 이름보다 부하 패턴과 확인 대상을 비교축으로 둠
- 추상 평가어를 제거하고 지표와 위험 조건으로 문장을 구성함
- 결론은 `선택 기준`을 도구가 아닌 운영 위험으로 명확히 정리함
