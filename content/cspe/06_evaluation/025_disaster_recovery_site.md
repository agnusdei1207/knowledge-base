## 미리 알고가기

- Primary Site: 평상시 서비스를 운영하는 주 데이터센터임
- DR Site: 주 센터 재해 시 서비스를 이어받도록 준비한 대체 센터임
- RTO: 서비스 재개까지 허용되는 최대 중단 시간임
- RPO: 복구 시점에서 허용되는 최대 데이터 손실 범위임

## Ⅰ. 개요

- **정의/개념**: DR 사이트는 주 데이터센터가 화재, 정전, 재난 같은 대규모 장애로 서비스 불능 상태가 되었을 때 목표 시간 안에 서비스를 재개하도록 다른 위치에 준비한 대체 운영 환경임
- **배경/필요성**: 같은 건물이나 같은 센터 안의 이중화는 지역 재난이나 센터 전체 장애를 막지 못하므로, 비즈니스 연속성을 유지하려면 지리적으로 분리된 복구 거점이 필요함

## Ⅱ. 특징

- 장애 복구 사이트는 고가용성과 달리 센터 단위 재난까지 고려하므로 위치 분리와 데이터 복제가 핵심이 됨
- 준비 수준이 높을수록 RTO와 RPO는 짧아지지만 구축 비용과 운영 복잡도는 커짐
- 사이트 유형 선택은 기술 선호보다 업무 중단 손실과 데이터 손실 허용 범위를 기준으로 해야 함
- 구축보다 더 중요한 것은 정기 복구 훈련이며 훈련이 없으면 문서상 목표와 실제 복구 시간이 크게 벌어질 수 있음

## Ⅲ. 종류 및 비교

| 판단 기준 | 핫 사이트 | 웜 사이트 | 콜드 사이트 |
|:---|:---|:---|:---|
| 준비 상태 | 인프라와 애플리케이션이 거의 즉시 전환 가능하도록 준비됨 | 기본 인프라와 일부 데이터가 준비되어 추가 기동 절차가 필요함 | 공간과 최소 설비만 준비되어 재해 후 구축과 복원이 많이 필요함 |
| 복구 시간 | 수분 이내 또는 매우 짧은 시간 안에 복구하기 쉬움 | 수시간 수준의 복구를 목표로 잡는 경우가 많음 | 수일 이상이 걸릴 수 있음 |
| 데이터 최신성 | 실시간 또는 준실시간 복제를 적용하기 쉬움 | 주기적 복제나 백업 기반이 많음 | 백업본 기준으로 복구하는 경우가 많음 |
| 적합 업무 | 금융 결제, 핵심 거래, 24시간 서비스에 적합함 | 정보계, 내부 업무, 일부 중단 허용 서비스에 적합함 | 장기 보관, 비핵심 시스템, 개발 환경에 적합함 |

## Ⅳ. 구성요소 및 구조

| 구성요소 | 설명 |
|:---|:---|
| 주 센터 | 평상시 서비스와 원본 데이터를 운영하며 DR 전환의 출발점이 됨 |
| 데이터 복제 또는 백업 경로 | 동기 또는 비동기 복제, 주기 백업으로 DR 사이트의 데이터 최신성을 결정함 |
| 대체 인프라 | 서버, 네트워크, 보안, 운영 도구를 포함한 복구 실행 환경이며 사이트 유형에 따라 준비 수준이 달라짐 |
| 전환 절차와 훈련 | 재해 선언, 서비스 승계, 검증, 복귀 절차를 문서화하고 실제 훈련으로 검증함 |

```text
+-------------+     +-------------+     +-------------+     +-------------+
| 주 센터 운영    | --> | 데이터 복제/백업 | --> | DR 인프라 대기  | --> | 재해 시 전환    |
+-------------+     +-------------+     +-------------+     +-------------+
```

## Ⅴ. 원리 및 절차 흐름도

```text
+-------------+     +-------------+     +-------------+     +-------------+
| 재해 선언      | --> | DR 사이트 활성화 | --> | 데이터/서비스 복구 | --> | 트래픽 전환 검증 |
+-------------+     +-------------+     +-------------+     +-------------+
```

1. **재해 선언**: 주 센터 복구 가능성과 업무 영향 범위를 평가해 전환 여부를 결정함
2. **DR 사이트 활성화**: 준비된 인프라와 네트워크를 운영 상태로 전환함
3. **데이터와 서비스 복구**: 최신 복제본이나 백업본을 기준으로 서비스 구성을 복구함
4. **트래픽 전환 검증**: 실제 사용자 요청이 DR 사이트로 정상 처리되는지 확인함

## Ⅵ. 실무 적용 및 유의점

1. 금융 결제나 핵심 거래 시스템은 핫 사이트가 필요하지만 복제만 믿고 훈련을 생략하면 목표를 달성하지 못하므로 실시간 복제와 정기 DR Drill을 함께 운영하고 RTO achieved와 RPO achieved와 drill success rate로 확인함
2. 내부 업무와 비핵심 시스템은 웜 또는 콜드 사이트가 현실적이지만 업무 영향 분석 없이 등급을 낮추면 복구 지연이 커질 수 있으므로 BIA 기반으로 유형을 정하고 recovery lead time과 backup freshness로 확인함

## Ⅶ. 결론

DR 사이트 선택의 핵심은 사이트 이름이 아니라 업무별 RTO와 RPO를 기준으로 복구 속도와 비용의 균형을 맞추는 데 있음.
