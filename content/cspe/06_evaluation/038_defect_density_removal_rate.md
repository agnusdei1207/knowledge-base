## 📖 【암기용】 핵심 요약

*   **한눈에**: 소프트웨어 프로젝트의 전반적인 품질을 측정하는 두 가지 핵심 지표. **결함 밀도(Defect Density)**는 '코드가 얼마나 지저분한가(결함의 양)'를, **결함 제거율(DRE, Defect Removal Efficiency)**은 '테스트팀이 얼마나 꼼꼼하게 일했는가(테스트 효율)'를 나타냄.
*   **깊이 이해**:
    *   **배경**: "이번 프로젝트에 버그가 100개 나왔어요!"라는 보고는 의미가 없음. 프로그램 크기가 1천 줄일 때 100개인 것과, 100만 줄일 때 100개인 것은 하늘과 땅 차이. 또한, 그 100개의 버그를 고객에게 오픈하기 전에 잡았는지, 오픈한 후에 터진 건지에 따라 프로젝트의 성패가 갈림.
    *   **작동 원리 (결함 밀도)**: `전체 결함 수 / 소프트웨어 크기(KLOC 또는 FP)`. 보통 1,000라인당 몇 개의 결함이 있는지 계산함. 숫자가 높을수록 개발팀의 코딩 품질이 나쁘다는 뜻.
    *   **작동 원리 (결함 제거율 - DRE)**: `출시 전 발견된 결함 수 / (출시 전 발견된 결함 + 출시 후 고객이 찾은 결함) * 100`. 전체 결함 중 QA(테스트) 단계에서 미리 걸러낸 비율. 숫자가 100%에 가까울수록 테스트팀이 일을 잘했다는 뜻.
    *   **비유**: **과수원 사과 수확**. 
        *   **결함 밀도**: 사과 1박스당 썩은 사과가 몇 개 들어있는가? (농사를 얼마나 잘 지었는가)
        *   **결함 제거율**: 수확한 사과를 마트에 납품하기 전에, 선별장에서 썩은 사과를 몇 퍼센트나 솎아냈는가? (검수 작업을 얼마나 깐깐하게 했는가)
    *   **흔한 오해/주의점**: "결함 밀도가 낮으면 무조건 좋은 프로젝트인가요?" $\rightarrow$ **오답**. 개발자가 코드를 잘 짜서 밀도가 낮을 수도 있지만, **QA팀이 대충 테스트해서 버그를 못 찾았을 때도 결함 밀도는 낮게 나옴**. 따라서 반드시 '결함 밀도'와 '결함 제거율(또는 테스트 커버리지)'을 교차 검증해야만 진정한 품질을 알 수 있음.
*   **연결 개념**: LOC/KLOC(코드 라인 수), FP(기능점수), 테스트 커버리지, 소프트웨어 신뢰성 성장 모델(SRGM)

## 📝 【답안용】 서술 골격

> **💡 핵심 인사이트**
> *   **본질**: 소프트웨어 개발 수명주기(SDLC)에서 개발의 '생산 품질'과 테스팅의 '검출 능력'을 정량화하는 두 가지 직교(Orthogonal) 지표.
> *   **가치**: 직관과 경험에 의존하던 품질 판단 및 출시(Release) 의사결정을 객관적인 수치 기반의 데이터 드리븐(Data-driven) 방식으로 전환시켜줌.
> *   **판단 포인트**: 결함 밀도는 '개발 프로세스'의 문제점을 진단하고, 결함 제거율(DRE)은 '테스트 프로세스'의 허점을 진단하는 지표이므로 두 지표를 조합한 사분면(Quadrant) 분석을 통해 조직의 역량을 평가해야 함.

### Ⅰ. 데이터 기반 S/W 품질 통제, 결함 지표의 개요
*   **정의**: 소프트웨어에 내재된 결함의 양을 규모 대비 비율로 산출한 **결함 밀도(Defect Density)**와, 전체 결함 중 배포 전 단계에서 검출 및 제거된 결함의 비율을 나타내는 **결함 제거율(DRE)**.
*   **도입 목적**: 개발 산출물의 품질 수준을 정량화하고, 테스트 활동의 적절성을 평가하여 제품 릴리즈(Go/No-go)의 기준선(Baseline)으로 활용.

### Ⅱ. 결함 밀도 (Defect Density) 산출 매커니즘
*   **산출 공식**: $\frac{\text{일정 기간 동안 발견된 총 결함 수}}{\text{소프트웨어 규모 (KLOC 또는 Function Point)}}$
*   **의미**: S/W의 체적 대비 결함의 집중도.
*   **활용 방안**:
    *   과거 프로젝트들의 평균 결함 밀도를 베이스라인으로 설정.
    *   모듈별 결함 밀도를 비교하여, 수치가 비정상적으로 높은 모듈(파레토 법칙 적용)에 대해 집중적인 코드 인스펙션(Code Inspection) 및 리팩토링 수행.

### Ⅲ. 결함 제거율 (DRE: Defect Removal Efficiency) 산출 매커니즘
*   **산출 공식**: $\frac{E}{E + D} \times 100 (\%)$
    *   **E (Errors)**: S/W 배포 전(사전 테스트)에 발견된 결함 수.
    *   **D (Defects)**: S/W 배포 후(운영 환경) 사용자에 의해 발견된 결함 수.
*   **의미**: QA 및 테스트 프로세스의 필터링(Filtering) 능력.
*   **활용 방안**:
    *   통상 DRE의 목표치를 90~95% 수준으로 설정.
    *   DRE가 현저히 낮을 경우, 테스트 케이스의 누락, 테스트 커버리지 부족, 테스트 환경의 한계(실운영 환경과 다름) 등을 의심하고 테스트 전략을 재수립해야 함.

### Ⅳ. 결함 밀도와 DRE의 결합: 품질 역량 사분면 분석
두 지표를 결합하면 개발 조직의 현재 상태를 입체적으로 진단할 수 있음.

| 진단 영역 | 현상 (결함 밀도 / DRE) | 조직 역량 분석 및 대응 전략 |
| :--- | :--- | :--- |
| **A (우수)** | 결함 밀도 **Low** / DRE **High** | 이상적인 상태. 코드 품질도 좋고 테스트도 꼼꼼함. |
| **B (위험)** | 결함 밀도 **Low** / DRE **Low** | 착시 현상. 코드가 좋은 게 아니라 테스트가 부실해서 버그를 못 찾은 것. $\to$ **테스트 커버리지 확대, QA 조직 강화 필수.** |
| **C (경고)** | 결함 밀도 **High** / DRE **High** | 테스트팀이 고생해서 막고는 있지만, 개발팀이 버그를 너무 많이 만듦. $\to$ **TDD 적용, 페어 프로그래밍, 시큐어 코딩 교육 필요.** |
| **D (최악)** | 결함 밀도 **High** / DRE **Low** | 버그도 많이 만들고 잡지도 못함. 배포 시 대형 장애 확정. $\to$ **릴리즈 중단 및 프로젝트 프로세스 전면 재검토.** |

### Ⅴ. 최신 소프트웨어 환경에서의 결함 지표 고도화
*   **규모 산정의 어려움**: MSA(마이크로서비스), Agile, Cloud Native 환경에서는 전체 LOC를 명확히 산정하기 어려움.
*   **대안 지표**: 스토리 포인트(Story Point) 당 결함 수, 스프린트(Sprint)별 결함 발생률, PR(Pull Request) 리뷰 시 발견된 결함 수 등을 결함 밀도의 대체 지표로 활용.
*   **지속적 통합(CI/CD) 연계**: SonarQube 등 정적 분석 도구와 연동하여 빌드 시점에 결함 밀도가 임계치를 초과하면 파이프라인(Pipeline)을 자동 차단하는 방식으로 발전 중.
