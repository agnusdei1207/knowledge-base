## 📖 【암기용】 핵심 요약

*   **한눈에**: 테스트를 진행하면서 결함(버그)을 찾아내고 고칠수록 소프트웨어의 신뢰도가 **시간의 흐름에 따라 어떻게 성장(개선)하는지**를 통계적 곡선으로 그려내어, **"언제 출시해도 안전할까?"**를 수학적으로 예측하는 기법.
*   **깊이 이해**:
    *   **배경**: H/W는 쓰다 보면 닳아서 고장 나지만(마모 고장), S/W는 마모되지 않음. S/W의 고장은 오직 '개발자가 실수로 남겨둔 버그' 때문에 발생함. 따라서 테스트 기간에 버그를 많이 잡아서 고칠수록, 남은 버그(잔존 결함)는 줄어들고 고장 날 확률도 점점 낮아짐.
    *   **작동 원리**: 테스트 1주차에 버그 50개 발견 $\to$ 2주차에 30개 $\to$ 3주차에 15개 발견. 발견되는 버그 수가 점점 줄어드는 추세를 수학적 그래프(곡선 피팅)로 그림. 이 그래프를 연장해 보면 "아, 5주차쯤 되면 일주일에 버그가 1개 미만으로 나오겠구나. 그때 출시하자!"라고 예측할 수 있음.
    *   **비유**: **호수에서 낚시하기**. 
        *   호수(소프트웨어)에 물고기(결함)가 몇 마리 있는지 모름.
        *   첫날 그물을 던지니 100마리가 잡힘. 둘째 날엔 50마리, 셋째 날엔 20마리가 잡힘.
        *   "잡히는 마릿수가 점점 줄어드는 걸 보니, 호수에 남은 물고기가 거의 없구나. 이제 낚시를 끝내도 되겠다"라고 추론하는 원리.
    *   **대표 모델 3가지**:
        1.  **Jelinski-Moranda (JM) 모델**: "모든 버그는 발견하기 쉬운 정도가 똑같고, 하나 고칠 때마다 고장 확률이 일정하게 줄어든다"는 초기/기본 모델 (비현실적).
        2.  **Goel-Okumoto (GO) 모델**: 시간에 따른 누적 결함 발견 수가 지수 함수 형태로 포화(Saturation) 곡선을 그린다고 가정하는 가장 대중적인 NHPP 모델.
        3.  **Musa-Okumoto (MO) 대수 포아송 모델**: "잡기 쉬운 버그가 먼저 잡히고, 나중에는 잡기 어려운 버그만 남는다"는 가장 현실적인 가정을 반영하여, 후반부 결함 발견율이 로그(Log) 형태로 서서히 감소하는 모델.
    *   **흔한 오해/주의점**: "HW 신뢰성 성장 모델(Duane/Crow-AMSAA)이랑 똑같은 거 아닌가요?" $\rightarrow$ **오답**. HW는 마모/교체를 다루지만, SW 모델은 마모가 없다는 전제하에 '테스트 실행 시간(Execution Time)'에 따른 결함 발견 확률을 다루므로 가정 자체가 다름.
*   **연결 개념**: NHPP (비동질 포아송 과정), 잔존 결함 수, 고장 강도(Failure Intensity), MTBF, 결함 제거율(DRE)

## 📝 【답안용】 서술 골격

> **💡 핵심 인사이트**
> *   **본질**: S/W 테스팅 과정에서 수집된 고장 시간(Time-between-failures) 또는 구간별 결함 발견 수 데이터를 확률 모델(Probability Model)에 적합(Fitting)시켜, 미래의 신뢰성을 추정하는 공학적 의사결정 도구.
> *   **가치**: "테스트를 언제 멈추고 제품을 릴리즈(Release)할 것인가?"라는 관리자의 최대 난제에 대해, 경험이나 감이 아닌 **목표 고장 강도(Target Failure Intensity)**를 기준선으로 명확한 수학적 해답을 제공함.
> *   **판단 포인트**: S/W의 결함은 크기와 난이도가 모두 다르므로, 단순 선형 모델(JM)보다는 결함의 발견 난이도 차이를 반영한 비선형 포아송 모델(GO, MO)을 적용해야 예측의 정확도(Goodness of fit)를 높일 수 있음.

### Ⅰ. 정량적 출시 판단의 근거, S/W 신뢰도 성장 모델(SRGM) 개요
*   **정의**: 소프트웨어 테스트 및 디버깅 과정에서 결함이 제거됨에 따라 신뢰도(MTBF)가 점진적으로 향상되는 과정을 수학적 함수로 표현하여, 잔존 결함 수와 목표 신뢰도 도달 시간을 예측하는 통계 모델.
*   **도입 목적**: 최적의 테스트 종료 시점(Optimal Release Time) 결정, 잔존 결함 예측을 통한 유지보수 예산 산정, 소프트웨어 릴리즈의 객관적 기준(Go/No-go) 확보.

### Ⅱ. 대표적인 S/W 신뢰도 성장 모델 3선
| 모델명 | 통계적 기반 및 가정 | 곡선의 형태 및 특징 |
| :--- | :--- | :--- |
| **Jelinski-Moranda (JM) 모델** | - 초기 고장 수는 N개로 유한함.<br>- **모든 결함의 발견 확률(크기)은 동일함**.<br>- 결함 1개 제거 시 고장 강도가 **계단식(Step)으로 일정하게 감소**. | 고장 강도가 시간에 따라 선형/계단식으로 하락함 (현실성 부족). |
| **Goel-Okumoto (GO) 모델** | - NHPP (Non-Homogeneous Poisson Process) 기반.<br>- 누적 결함 발견 횟수가 **지수 분포(Exponential)**를 따름. | 테스트 초기에 결함 발견율이 급증하다가 점차 **포화(Saturation)**되는 지수형 감소 곡선 (대중적). |
| **Musa-Okumoto (MO) 대수 포아송 모델** | - NHPP 기반.<br>- **결함마다 발견/수정 난이도가 다름**을 인정.<br>- 시간이 지날수록 고장 강도가 **대수적(Logarithmic)으로 서서히 감소**. | 테스트 후반부에 도달해도 결함 발견율이 0으로 급감하지 않고 꼬리가 길게 유지되는 가장 현실적인 모델. |

### Ⅲ. SRGM 분석 및 출시 의사결정 절차
1.  **데이터 수집**: 시스템 실행 시간(Execution Time) 대비 고장 발생 시점(Time-to-Failure) 또는 테스트 주기당 발견된 결함 수 기록.
2.  **모델 선택 및 적합(Fitting)**: 수집된 산점도 데이터를 바탕으로 GO, MO 등 여러 모델에 최대우도추정(MLE) 기법을 적용하여 파라미터를 추정하고 곡선을 그림.
3.  **적합도 검정**: AIC, R-Square 등을 통해 실제 데이터와 가장 오차가 적은 최적의 모델 선정.
4.  **목표 고장 강도 도달 시점 예측**: 
    *   현재의 고장 강도 추세선을 연장(Extrapolation)함.
    *   경영진이 요구하는 **목표 고장 강도(Target Failure Intensity, 예: 1000시간당 1건 미만)**와 교차하는 시간 축(x축)의 좌표를 산출하여 **최적 출시일**을 확정.

### Ⅳ. H/W 신뢰성 성장 모델(Duane/Crow-AMSAA)과의 비교
| 비교 기준 | H/W 신뢰성 성장 모델 (031 참조) | S/W 신뢰성 성장 모델 (SRGM) |
| :--- | :--- | :--- |
| **고장 원인** | 마모, 노후화, 환경적 스트레스 (물리적) | 설계 오류, 논리적 버그 (논리적) |
| **고장의 재발** | 부품을 새것으로 교체해도 시간이 지나면 **다시 고장 남** | 버그를 완벽히 수정하면 동일 원인으로 **다시 고장 나지 않음** |
| **욕조 곡선 적용** | 초기 고장 $\to$ 우발 고장 $\to$ **마모 고장** 증가 | 테스트 후반부로 갈수록 고장률이 **지속적으로 하락** |
| **대표 모델** | Duane, Crow-AMSAA 모델 | JM, GO, MO 모델 |

### Ⅴ. 모델 적용 시 실무적 한계 및 보완 전략
*   **데이터의 왜곡 (Testing Profile 편향)**: 운영 환경과 전혀 다른 시나리오로만 테스트하거나 커버리지(039)가 낮을 경우, 그래프 상으로는 고장 강도가 0에 수렴하는 것으로 착시가 발생함.
    $\to$ **대응**: 운영 환경 프로파일(Operational Profile)과 동일한 비중으로 테스트를 수행해야 모델의 예측력이 유효함.
*   **새로운 결함의 유입 (Imperfect Debugging)**: 모델들은 버그를 수정하면 완벽히 고쳐진다고 가정하지만, 실제로는 A를 고치다 B 버그를 새로 만드는 경우가 잦음.
    $\to$ **대응**: 불완전 디버깅 가정을 포함하는 확장된 SRGM 모델을 사용하거나, 수정 후 회귀 테스트(Regression Test)를 의무화해야 함.
