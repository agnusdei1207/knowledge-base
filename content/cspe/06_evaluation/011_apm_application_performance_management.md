# 📖 【암기용】 개념 완전 이해

## 한눈에
- **개요**: APM은 요청 단위 Trace·Metric·Log를 수집·상관분석해 응답시간·처리량·오류율과 코드 레벨 병목을 진단하는 애플리케이션 성능 관리 체계(성능 지표 정의는 001, 응답시간은 002 참조)
- **왜 필요한가**: MSA·클라우드에서 하나의 요청이 여러 서비스·DB·외부 API를 거쳐, 서버별 CPU·로그만으로는 어느 구간이 목표를 위반했는지 특정하기 어려움
- **핵심 직관**: 자동차 계기판이 속도·RPM·연료를 숫자로 보여주듯, APM은 요청이 지나온 각 구간의 지연·오류를 숫자와 경로로 보여줌

## 핵심 용어 정리 (내부에 등장하는 것들)
아래 용어는 답안용 Ⅰ~Ⅵ에 그대로 쓰이므로 먼저 비유로 풀어 둔다. 상위 핵심 키워드는 **분산 추적 기반 코드 레벨 성능 진단**이다.

| 용어/표기 | 의미 | 비유·예 |
|:---|:---|:---|
| Trace | 하나의 요청이 지나온 전체 경로 기록 | 택배 1건의 출발~도착 전체 배송 추적표 |
| Span | Trace 안의 단일 작업 구간(서비스 호출·SQL 등) | 배송 추적표의 각 물류센터 경유 기록 1건 |
| trace id | 요청 전체를 하나로 묶는 고유 식별자 | 택배 송장 번호 |
| 분산 추적(Distributed Tracing) | trace id를 서비스 간 전파해 경로를 잇는 기법 | 여러 택배사 거쳐도 송장 하나로 추적 |
| 코드 레벨 진단 | 느린 메서드·SQL을 소스 위치까지 짚는 것 | 정체 원인을 "어느 신호등"까지 특정 |
| Metric | 시간 단위로 집계된 수치(TPS·error rate 등) | 시간당 처리 택배 수·분실률 통계 |
| p95/p99 | 응답시간 정렬 시 95%/99% 지점 값(002 참조) | 100건 중 95·99번째로 느린 건의 시간 |
| error rate | 전체 요청 중 오류(5xx·예외) 비율 | 배송 100건 중 파손·오배송 비율 |
| 샘플링(sampling) | 전체 요청 중 일부만 Trace로 저장하는 비율 | 택배 100건 중 10건만 상세 기록 |
| tail sampling | 느리거나 오류난 요청을 우선 저장하는 방식 | 문제 있는 배송만 골라 상세 보관 |
| trace coverage | 실제 트래픽 중 Trace로 포착된 비율 | 전체 배송 중 추적표가 남은 비율 |

## 깊이 이해
- **배경·문제의식**: MSA·클라우드에서 요청은 다수 서비스·DB·외부 API를 거치며, 호스트별 지표만으로는 지연·오류가 발생한 코드 구간을 특정하기 어려움
- **작동 원리(어떻게+왜)**: Agent 또는 OpenTelemetry SDK가 요청에 trace id를 부여하고 서비스 호출·DB Query·외부 API를 span으로 기록함. trace id를 HTTP 헤더·메시지 속성으로 전파(분산 추적)해 서비스 경계를 넘어 하나의 Trace로 잇고, span duration을 집계해 p95·TPS·error rate를 산출하며, 느린 span의 메서드·SQL 위치까지 내려가 코드 레벨로 진단함
- **비유**: 병원 종합검진이 여러 장기를 동시 촬영해 이상 부위를 짚듯, APM은 요청의 여러 구간을 동시에 측정해 병목 구간을 특정함
- **구체 예시**: 주문 API p95 1.2초 중 결제 API 700ms·DB Query 300ms로 분해되면 결제 구간을 개선 대상으로 지정하고, 결제 서비스 내 특정 SQL의 full scan을 코드 레벨로 확인함
- **흔한 오해**: APM 설치 자체가 성능 보증은 아님. 낮은 샘플링 비율은 느린 요청을 놓치므로, 측정 구간 정의·샘플링 비율·집계 주기가 함께 명시되어야 지표를 신뢰할 수 있음

## 연결 개념
- CPU·메모리 이용률 측정(012) — APM 구간 지표와 결합해 자원 병목 원인 판단
- 시스템 성능 지표(001) — APM이 산출하는 TPS·응답시간·오류율의 정의 원천
- SLA·SLO — APM 지표가 계약·목표 준수 여부의 실측 근거

# 📝 【답안용】 시험 답안 템플릿

## 핵심 인사이트 (3줄 요약)

> 1. **본질**: APM은 요청 단위 Trace·Metric·Log를 분산 추적으로 상관분석해 응답시간·처리량·오류율과 코드 레벨 병목을 진단하는 체계임.
> 2. **가치**: 평가·감리가 요구하는 p95 응답시간·TPS·error rate 실측치를 서비스 구간별로 제공함.
> 3. **판단 포인트**: 도구 설치 여부가 아니라 측정 구간 정의·샘플링 비율·집계 주기가 평가 신뢰도를 좌우함.

## 출제 의도 및 답안 포인트

| 출제 의도 | 반드시 짚을 핵심 | 감점 회피 포인트 |
|:---|:---|:---|
| 성능 지표 산출 이해 확인 | Trace·Metric·Log, p95·TPS·error rate | 특정 제품명 나열 |
| 병목 구간 특정 역량 확인 | span 분해, DB Query·외부 호출 구간, 코드 레벨 진단 | 평균 응답시간만 제시 |
| 평가 신뢰성 확보 확인 | 샘플링 비율·측정 구간·집계 주기 명시 | 지표 정의 없이 수치만 제시 |

> 요약: 이 문제는 도구 소개가 아니라 평가에 쓰이는 정량 지표의 산출 근거와 신뢰도 확보 방법을 요구함.

---

## Ⅰ. 개요 및 필요성

- 개요: 요청 단위 Trace·Metric·Log로 응답시간·처리량·오류율과 코드 병목을 진단하는 성능 관리 체계
- 배경: MSA·클라우드는 한 요청이 다수 서비스를 거쳐 장애·지연 구간 특정이 어려움
- 필요성: 평가·감리에서 p95 응답시간·TPS·error rate 실측 근거 확보와 코드 레벨 원인 규명이 필수

---

## Ⅱ. 구조 및 구성요소

```text
Client Request -> App Agent/SDK -> Collector -> Storage/Index -> Evaluation Dashboard
  App Agent/SDK 분기: DB Query span / External API span / Error Event
```

| 구성요소 | 역할 | 특이사항 |
|:---|:---|:---|
| Agent/SDK | 요청·메서드·SQL 지연 수집, trace id 부여 | OpenTelemetry, Java Agent |
| Collector | Trace·Metric·Log 수신·가공·샘플링 | 샘플링 비율, 태그 표준 |
| Storage/Index | 시계열·Trace 검색 저장 | 보관 기간, 카디널리티 관리 |
| Evaluation Dashboard | p95·TPS·error rate·코드 구간 표시 | 평가 보고서 연동 |

> 요약: APM은 수집 Agent, Collector, 저장소, 평가 대시보드가 요청 단위 지표와 코드 구간을 산출하는 구조임.

---

## Ⅲ. 동작원리 및 흐름도

```text
요청 수신 -> trace id 생성·전파 -> 서비스·DB·외부 호출 span 기록
  -> p95·TPS·error rate 집계 -> 느린 span 코드 레벨 진단 -> 평가 기준 대비 판정
```

- 1단계: Agent가 요청 진입 시 trace id를 생성해 HTTP 헤더·메시지 속성으로 하위 서비스에 전파함
- 2단계: 각 서비스가 자신의 호출·DB Query·외부 API를 span으로 기록하고 duration·error tag를 남김
- 3단계: Collector가 span을 집계 주기·샘플링 비율에 따라 p50·p95·p99, TPS, error rate로 산출함
- 4단계: 평가자가 느린 span의 메서드·SQL을 코드 레벨로 진단하고 지표를 SLO 대비 충족 여부로 판정함

> 요약: Agent가 trace id로 요청을 잇고 span별 지연을 집계·코드 진단해 평가 기준 대비 지표를 산출함.

---

## Ⅳ. 특징

- 관점이 요청 중심임: 호스트 CPU·메모리가 아니라 요청·API·DB Query 구간을 분석 단위로 삼음
- 분산 추적으로 경계를 넘음: trace id 전파로 서비스가 나뉘어도 하나의 요청 경로를 재구성함
- 코드 레벨까지 진단함: 느린 span을 메서드·SQL 위치까지 내려가 병목 원인을 소스 단위로 특정함
- 백분위 지표를 제공함: 평균이 아닌 p95·p99로 꼬리 지연을 드러내 평가 근거로 활용함
- 신뢰도가 설계에 의존함: 샘플링 비율·측정 구간 정의·집계 주기가 지표 신뢰도를 좌우함

## Ⅴ. 심화 비교 및 적용 판단

| 구분 | 전통 인프라 모니터링 | APM |
|:---|:---|:---|
| 분석 단위 | 호스트 CPU·메모리 | 요청 Trace/Span |
| 상관분석 | 로그·메트릭 분리 관측 | trace id 기반 구간 상관분석 |
| 병목 특정 | 장애 후 로그 검색 | 코드 레벨 span 분해 |
| 평가 활용 | 자원 임계값 경보 | p95·TPS·error rate 실측 지표 |

> 요약: 전통 모니터링은 인프라 상태를, APM은 요청 경로 구간별·코드 레벨 지표를 평가 근거로 제공함.

- 리스크 — 평가 왜곡: 낮은 샘플링 비율로 느린 요청 누락 — 대응: tail sampling·coverage 목표 설정, 확인 지표 trace coverage 95% 이상
- 리스크 — 저장 비용 증가: 고카디널리티 tag 남용 — 대응: tag whitelist·샘플링 정책, 확인 지표 GB/day·series count
- 리스크 — 지표 불일치: 측정 구간 정의 부재 — 대응: 평가 보고서에 측정 구간 명시, 확인 지표 구간 정의 문서화율

- 지표 — 지연: 주요 API p95 300ms 이하 — 측정: APM percentile 집계
- 지표 — 처리량: 목표 TPS 대비 90% 이상 — 측정: 부하테스트 병행 측정
- 지표 — 오류: error rate 0.1% 이하 — 측정: 5xx·exception count

## Ⅵ. 실무 적용 및 결론

**적용 방안 3개 (필수 — 단계별 또는 항목별):**
1. OpenTelemetry로 trace id·service.name·deployment.version 표준을 정의해 평가 대상 서비스 전체에 적용함
2. 평가 보고서에 측정 구간·샘플링 비율·집계 주기를 명시해 p95 300ms·TPS 목표 대비 실측 근거를 제시함
3. 배포 이력과 연동해 배포 전후 p95·error rate 변화를 비교하고 회귀 구간을 코드 레벨로 진단함

**결론 (2줄):**
- 기술사 판단: 호출 깊이가 3단계 이상인 MSA면 분산 추적 기반 APM이 필수이고, 단일 서비스면 인프라 모니터링과 APM 샘플링을 절충해 비용을 통제해야 함
- 향후 방향: APM은 OpenTelemetry 표준과 AIOps 이상 탐지로 확장되어 평가 보고서 자동 생성까지 지원하는 체계로 발전함
