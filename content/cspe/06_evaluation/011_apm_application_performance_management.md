# 📖 【암기용】 개념 완전 이해

> 목적: APM을 단순 모니터링 화면이 아니라, 시스템 평가에서 응답시간·처리량·오류율을 정량 근거로 산출하는 측정 체계로 이해하게 만든다.

## 한눈에
- **개요**: APM은 애플리케이션 요청의 응답시간, 처리량, 오류율, 자원 사용을 수집·상관분석해 성능 평가 근거 지표를 제공하는 체계다.
- **왜 필요한가**: 시스템 평가·감리에서 "성능이 좋다"는 주장은 근거가 아니다. p95 응답시간, TPS, error rate 같은 실측 수치가 평가 판정 기준이 된다.
- **핵심 직관**: 자동차 계기판이 속도·RPM·연료를 숫자로 보여주듯, APM은 서비스 구간별 지연과 오류를 숫자로 보여준다.

## 깊이 이해
- **배경·문제의식**: MSA와 클라우드 환경에서 요청은 여러 서비스와 DB를 거친다.
- **배경·문제의식**: 서버별 CPU·로그만 보면 어느 구간이 성능 목표를 위반했는지 특정하기 어렵다.
- **작동 원리**: Agent 또는 OpenTelemetry SDK가 요청에 trace id를 부여하고 서비스 호출·DB Query·외부 API 구간을 span으로 기록한다.
- **작동 원리**: 수집된 span과 metric을 집계해 p50·p95·p99 응답시간, 처리량(TPS), error rate를 산출한다.
- **비유**: 병원 종합검진처럼 APM은 애플리케이션의 여러 구간을 동시에 측정해 이상 구간을 짚어낸다.
- **구체 예시**: 예시로 주문 API p95 1.2초 중 결제 API 700ms, DB Query 300ms 구간이 확인되면 결제 구간을 성능 평가 개선 대상으로 지정한다.
- **흔한 오해·주의점**: APM 도입 자체가 성능 보증이 아니다.
- **흔한 오해·주의점**: 평가에는 수집 지표의 samplig 비율과 측정 구간 정의가 함께 명시되어야 신뢰할 수 있다.

## 연결 개념
- CPU·메모리 이용률 측정 — APM 지표와 결합해 자원 병목 원인 판단
- 성능 모델링 — APM 실측치를 모델 검증 입력으로 사용
- SLA·SLO — APM 지표가 계약·목표 준수 여부의 실측 근거

# 📝 【답안용】 시험 답안 템플릿

> 목적: APM 구성요소, 수집 흐름, 평가 지표 산출 기준을 시험 답안으로 전개한다.
> 핵심: APM은 도구 소개가 아니라 시스템 평가에 쓰이는 정량 지표(p95, TPS, error rate)의 산출 근거를 제시하는 것이 핵심이다.

## 핵심 인사이트 (3줄 요약)

> 1. **본질**: APM은 요청 단위 Trace·Metric·Log를 수집·상관분석해 응답시간·처리량·오류율 지표를 산출하는 성능 관리 체계다.
> 2. **가치**: 시스템 평가·감리에서 요구하는 p95 응답시간, TPS, error rate 실측치를 서비스 구간별로 제공한다.
> 3. **판단 포인트**: 도구 설치 여부가 아니라 측정 구간 정의, 샘플링 비율, 집계 주기가 평가 신뢰도를 좌우한다.

## 출제 의도 및 답안 포인트

| 출제 의도 | 반드시 짚을 핵심 | 감점 회피 포인트 |
|:---|:---|:---|
| 성능 평가 지표 산출 이해 확인 | Trace·Metric·Log, p95, TPS, error rate | 특정 제품명 나열 |
| 병목 구간 특정 역량 확인 | span, DB query, external call 구간 분해 | 평균 응답시간만 제시 |
| 평가 신뢰성 확보 확인 | 샘플링 비율, 측정 구간, 집계 주기 명시 | 지표 정의 없이 수치만 제시 |

> 요약: 이 문제는 APM 도구 설명이 아니라 성능 평가에 쓰이는 정량 지표의 산출 근거와 신뢰도 확보 방법을 요구한다.

---

## Ⅰ. 개요 및 필요성

- 개요: 요청 단위 Trace·Metric·Log로 응답시간·처리량·오류율을 산출하는 성능 관리 체계
- 배경: MSA·클라우드 환경은 요청이 다수 서비스를 거쳐 장애 구간 특정이 어려움
- 필요성: 시스템 평가·감리에서 p95 응답시간, TPS, error rate 같은 실측 근거 지표 확보가 필수

---

## Ⅱ. 구조 및 구성요소

```text
Client Request -> App Agent -> Trace/Metric/Log Collector -> Storage -> Evaluation Dashboard
                                      / DB Query / External API / Error Event
```

| 구성요소 | 역할 | 특이사항 |
|:---|:---|:---|
| Agent/SDK | 요청·메서드·SQL 지연 수집 | OpenTelemetry, Java Agent |
| Collector | Trace·Metric·Log 수신·가공 | 샘플링 비율, 태그 표준 |
| Storage/Index | 시계열·Trace 검색 저장 | 보관 기간, 카디널리티 관리 |
| Evaluation Dashboard | p95, TPS, error rate 평가 지표 표시 | 평가 보고서 연동 |

> 요약: APM은 수집 Agent, Collector, 저장소, 평가 대시보드가 요청 단위 성능 지표를 산출하는 구조다.

---

## Ⅲ. 동작원리 및 흐름도

```text
요청 수신 -> Trace ID 생성 -> Span 수집 -> 지표 집계 -> 평가 판정
```

| 단계 | 처리 내용 | 검증 기준 |
|:---:|:---|:---|
| 1 | 요청 진입 시 trace id 생성·전파 | HTTP header, message attribute |
| 2 | 서비스·DB·외부 호출 span 기록 | span duration, error tag |
| 3 | p50·p95·p99, TPS, error rate 집계 | 집계 주기, 샘플링 비율 |
| 4 | 평가 기준 대비 지표 판정 | SLO 대비 충족 여부 |

> 요약: APM은 trace id로 요청을 연결하고 span별 지연을 집계해 평가 기준 대비 지표를 산출한다.

---

## Ⅳ. 특징

| 구분 | 전통 모니터링 | APM | 수치 컬럼 |
|:---|:---|:---|:---|
| 관점 | 서버 CPU·메모리 | 요청·API·DB Query 구간 | p95 300ms 이하 |
| 분석 단위 | 호스트 | Trace/Span | span 50개 이하 |
| 평가 활용 | 장애 발생 후 로그 검색 | 평가 보고서용 실측 지표 | error rate 0.1% 이하 |

> 요약: APM은 인프라 상태보다 요청 경로 구간별 지표를 평가 근거로 제공한다는 점이 특징이다.

## Ⅴ. 심화 비교 및 적용 판단

| 비교 축 | 기존/대안 | 본 키워드 | 선택 기준 |
|:---|:---|:---|:---|
| 구조 | 로그·메트릭 분리 | Trace 중심 상관분석 | MSA 호출 깊이 3단계 이상 |
| 비용/성능 | 전체 요청 수집 | 샘플링·tail sampling | 저장 비용과 평가 누락 위험 |
| 운영/위험 | 임계값 경보 | SLO burn rate 경보 | 경보 피로와 평가 신뢰도 |

> 요약: APM은 무조건 많은 데이터를 모으기보다 샘플링과 집계 기준을 평가 목적에 맞게 설계해야 한다.

| 리스크 | 원인 | 대응 방안 | 확인 지표 |
|:---|:---|:---|:---|
| 평가 왜곡 | 낮은 샘플링 비율로 지표 누락 | trace coverage 목표치 설정 | trace coverage 95% 이상 |
| 저장 비용 증가 | 고카디널리티 tag 남용 | tag whitelist, sampling 정책 | GB/day, series count |
| 지표 불일치 | 측정 구간 정의 부재 | 평가 보고서에 측정 구간 명시 | 구간 정의 문서화율 |

> 요약: APM 평가 리스크는 샘플링 비율, 저장 비용, 측정 구간 정의로 통제한다.

| 점검 항목 | 목표 기준 | 측정 방법 |
|:---|:---|:---|
| 지연 | 주요 API p95 300ms 이하 | APM percentile |
| 처리량 | 목표 TPS 대비 90% 이상 달성 | 부하 테스트 병행 측정 |
| 오류 | error rate 0.1% 이하 | 5xx, exception count |

> 요약: APM 평가 성과는 지연·처리량·오류율 실측치가 평가 목표 대비 충족되는지로 판단한다.

## Ⅵ. 실무 적용 및 결론

**적용 방안 3개 (필수 — 단계별 또는 항목별):**
1. OpenTelemetry 기반 trace id, service.name, deployment.version 표준을 정의하고 평가 대상 서비스 전체에 적용함
2. 평가 보고서에 측정 구간, 샘플링 비율, 집계 주기를 명시해 p95 300ms, TPS 목표치 대비 실측 근거를 제시함
3. 배포 이력과 연동해 배포 전후 p95·error rate 변화를 평가 지표로 비교함

**결론 (2줄):**
- 기술사 판단: 시스템 평가에서 성능 주장은 반드시 APM 실측 지표와 측정 구간 정의를 동반해야 함
- 향후 방향: APM은 OpenTelemetry 표준과 AIOps 이상 탐지로 확장되어 평가 보고서 자동 생성까지 지원하는 체계로 발전함
