## 미리 알고가기

- APM: 애플리케이션 요청 흐름, 지연 구간, 오류를 수집해 성능 저하 원인을 분석하는 관리 방식임
- Trace: 하나의 요청이 여러 서비스와 구간을 거친 기록임
- Span: Trace 안에서 특정 서비스나 함수 호출 하나의 수행 구간임
- Metric: 응답시간, TPS, 오류율, CPU 사용률처럼 시간 단위로 집계되는 수치임
- Sampling: 전체 요청 중 일부만 추적해 수집 오버헤드를 줄이는 방식임

## Ⅰ. 개요

- **정의/개념**: APM은 사용자 요청부터 코드, DB, 외부 호출까지의 실행 정보를 수집해 애플리케이션 성능 저하와 장애 원인을 찾는 관리 방식임
- **배경/필요성**: 분산 환경에서는 인프라 지표만으로 어떤 서비스와 코드 구간이 사용자 지연을 만들었는지 알기 어려우므로 요청 단위 추적이 필요함

## Ⅱ. 특징

- 사용자 체감 응답시간과 내부 서비스 호출 시간을 같은 Trace로 연결함
- 오류율, TPS, 지연 시간, 로그를 함께 보아 장애 증상과 원인을 좁힘
- 에이전트와 계측 코드는 오버헤드를 만들 수 있어 샘플링과 수집 범위 조정이 필요함
- MSA에서는 Trace ID 전파가 끊기면 전체 호출 경로를 재구성하기 어려움

## Ⅲ. 종류 및 비교

| 판단 기준 | Metric 중심 모니터링 | APM Trace 중심 분석 |
|:---|:---|:---|
| 측정 단위 | 시스템이나 서비스의 집계 수치 | 요청 하나의 호출 경로 |
| 주요 활용 | 이상 징후 탐지와 경보 | 지연 구간과 오류 원인 추적 |
| 장점 | 수집 비용이 낮고 추세 확인이 쉬움 | 어떤 호출이 느린지 직접 확인 가능 |
| 한계 | 원인 구간을 바로 특정하기 어려움 | 샘플링과 계측 오버헤드 관리가 필요함 |

## Ⅳ. 구성요소 및 구조

| 구성요소 | 설명 |
|:---|:---|
| Agent·SDK | 애플리케이션 실행 정보를 계측해 trace, metric, log를 수집함 |
| Collector | 여러 서비스의 데이터를 모아 저장소와 분석 시스템으로 전달함 |
| Trace 저장소 | Trace ID와 span 관계를 보관해 요청 경로와 지연 구간을 조회하게 함 |
| 대시보드·알림 | SLO 위반, 오류 증가, 지연 증가를 시각화하고 담당자에게 알림을 보냄 |

```text
+-----------+     +-----------+     +-----------+     +-----------+
| App Agent  | --> | Collector  | --> | Trace Store | --> | 분석/알림   |
+-----------+     +-----------+     +-----------+     +-----------+
```

## Ⅴ. 원리 및 절차 흐름도

```text
+-----------+     +-----------+     +-----------+     +-----------+
| Trace ID 생성 | --> | Span 기록   | --> | 경로 재구성  | --> | 병목 판정    |
+-----------+     +-----------+     +-----------+     +-----------+
```

1. **Trace ID 생성**: 사용자 요청에 고유 식별자를 부여함
2. **Span 기록**: 서비스 호출, DB 쿼리, 외부 API 호출의 시작과 종료를 기록함
3. **경로 재구성**: 여러 서비스의 span을 시간 순서와 부모·자식 관계로 연결함
4. **병목 판정**: 긴 span, 오류 span, 재시도 구간을 확인해 개선 대상을 정함

## Ⅵ. 실무 적용 및 유의점

1. MSA 운영에서는 trace context 전파가 끊기면 원인 분석이 어려우므로 gateway부터 내부 서비스까지 Trace ID를 유지하고 missing span ratio로 확인함
2. 고트래픽 서비스에서는 전체 요청을 모두 수집하면 오버헤드가 커질 수 있으므로 head 또는 tail sampling을 적용하고 agent overhead와 p99 latency 변화로 확인함

## Ⅶ. 결론

APM은 시스템이 살아 있는지 보는 도구가 아니라 사용자 요청의 어느 호출 구간이 지연과 오류를 만들었는지 추적해 조치 대상을 정하는 관리 방식임.

## 작성 근거(검토용)

- 137회 기출이며 관측성 키워드와 연결되므로 metric과 trace의 역할 차이를 비교축으로 배치함
- 과장 표현을 제거하고 Trace ID, span, sampling으로 구체화함
- 실무 절은 trace 전파와 수집 오버헤드로 제한해 APM의 실제 운영 리스크를 반영함
