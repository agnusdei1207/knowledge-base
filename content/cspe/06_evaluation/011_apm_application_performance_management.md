# 📖 【암기용】 개념 완전 이해

## 한눈에
- **개요**: APM(Application Performance Management)은 애플리케이션의 가용성, 성능 지표(RT, TPS 등) 및 사용자 경험을 실시간으로 모니터링하고, **코드 레벨의 병목 지점을 정밀 진단**하는 관리 체계다.
- **왜 필요한가**: 복잡해진 MSA(Microservices Architecture) 환경에서 하나의 요청이 거치는 수많은 서비스와 DB 구간 중 **"정확히 어디서, 왜 느린지"**를 서버 로그만으로는 파악하기 불가능하기 때문이다.
- **핵심 직관**: 환자의 몸속에 조영제를 투입해 혈관의 흐름을 관찰하는 '혈관 조영술'과 같다. 요청(Request)에 식별자(Trace ID)를 붙여 시스템 구석구석을 지나가는 과정을 실시간으로 추적한다.

## 핵심 용어 정리

| 용어/표기 | 의미 | 기술적 포인트 |
|:---|:---|:---|
| **Distributed Tracing** | 서비스 간 요청 흐름을 추적하는 기법 | Trace ID를 통한 전 구간 가시성 확보 |
| **Trace & Span** | 전체 요청(Trace)과 그 내부의 단위 작업(Span) | 부모-자식 관계의 트리 구조로 시각화 |
| **Instrumentation** | 코드에 모니터링 코드를 삽입하는 행위 | Bytecode 조작(Agent) 또는 SDK 방식 |
| **Sampling** | 전체 트래픽 중 일부만 추출하여 기록하는 것 | 부하(Overhead)와 데이터 정밀도 간의 절충 |
| **Profiling** | 메서드 단위의 실행 시간 및 자원 점유 분석 | 코드 레벨의 핫스팟(Hotspot) 탐지 |
| **OpenTelemetry** | 클라우드 네이티브 관측성(Observability) 표준 | 벤더 종속성 없는 데이터 수집 프레임워크 |

## 깊이 이해
- **관측성(Observability)의 3요소**:
  1. **Metrics**: 시스템의 상태를 나타내는 수치(CPU, TPS 등). "무슨 일이 일어나는가?"
  2. **Logging**: 특정 시점의 이벤트 기록. "어떤 일이 일어났는가?"
  3. **Tracing**: 요청의 전 여정 추적. "어디서 일이 일어났는가?" (APM의 핵심)
- **에이전트 방식 vs SDK 방식**:
  - **에이전트**: 소스 수정 없이 Java Agent 등을 통해 런타임에 삽입. 편리하지만 오버헤드 발생 가능.
  - **SDK**: 개발자가 직접 코드에 심는 방식. 정밀한 제어가 가능하지만 개발 공수 필요.
- **비유 (택배 배송)**:
  - **전통 모니터링**: "택배 터미널에 트럭이 몇 대 서 있는가?" (Resource 중심)
  - **APM**: "내 택배가 지금 어느 허브를 지나고 있으며, 상차 작업에 몇 분이 걸렸는가?" (Request 중심)
- **구체 예시 (병목 진단)**:
  - 전체 응답 시간 3초 중, `OrderService` 내부의 `getDiscount` 메서드에서 2.5초가 소모됨을 발견. 해당 메서드 내의 비효율적인 DB 쿼리가 원인임을 단번에 식별.

## 연결 개념
- **분산 트레이싱(016)**: APM의 핵심 기술적 근거.
- **SLA/SLO/SLI(020, 021)**: APM 지표를 기반으로 서비스 수준 목표 설정.
- **에러 예산(022)**: APM의 에러율 지표를 바탕으로 배포 여부 결정.

# 📝 【답안용】 시험 답안 템플릿

## 핵심 인사이트 (3줄 요약)

> 1. **본질**: APM은 애플리케이션 트랜잭션의 **전 구간 흐름(End-to-End Trace)**을 추적하여 가시성을 확보하고 성능을 최적화하는 통합 관리 도구임.
> 2. **방법론**: 분산 추적(Distributed Tracing)과 코드 프로파일링을 통해 **메서드/SQL 레벨의 병목**을 정량적으로 식별하며, 최근에는 AI/ML을 결합한 이상 탐지(AIOps)로 진화 중임.
> 3. **가치**: 장애 인지 시간(MTTD)과 복구 시간(MTTR)을 획기적으로 단축하여 고가용성 서비스 운영 및 사용자 경험(UX) 개선의 핵심 기반이 됨.

## 출제 의도 및 답안 포인트

| 출제 의도 | 반드시 짚을 핵심 | 감점 회피 포인트 |
|:---|:---|:---|
| APM의 정의 및 필요성 | MSA 환경에서의 가시성(Visibility) 확보 | 단순히 "서버 감시 도구"라고 정의하지 말 것 |
| 주요 기능 및 메커니즘 | 분산 추적, Trace/Span, 코드 레벨 프로파일링 | 특정 제품 기능 나열보다는 공통 기술 메커니즘 강조 |
| 관측성(Observability)으로의 진화 | Metrics, Logs, Traces의 통합 | APM과 단순 모니터링의 차별점 명확화 |

## Ⅰ. APM(Application Performance Management)의 개요

### 1. 정의
- 애플리케이션의 실행 단계부터 운영 단계까지 전 과정의 성능 지표를 수집·분석하여 최적의 서비스 수준을 유지하도록 관리하는 솔루션 및 방법론

### 2. 패러다임의 변화: 모니터링에서 관측성(Observability)으로
- **Monitoring**: "시스템이 살아있는가?" (Passive, Resource-centric)
- **Observability**: "왜 시스템이 이렇게 동작하는가?" (Active, Context-centric)

---

## Ⅱ. APM의 핵심 기술 및 아키텍처

### 1. 데이터 수집 및 처리 구조

```text
 [ Application ]        [ Collector / Server ]        [ Storage / Analysis ]
 +-------------+        +--------------------+        +--------------------+
 |  Agent/SDK  | ---->  |   Data Processor   | ---->  |  Time-series DB    |
 | (Trace/Span)|        |   (Aggregator)     |        |  Elasticsearch/etc |
 +-------------+        +--------------------+        +--------------------+
        ^                          |                          |
        |                          v                          v
 [ Performance ] <------- [ Alert / AIOps ] <------- [ Visualization / UI ]
```

### 2. 5대 핵심 기능 요소

| 기능 | 설명 | 기대 효과 |
|:---|:---|:---|
| **Transaction Tracing** | 사용자 요청의 전 구간(End-to-End) 경로 추적 | 구간별 지연 시간(Latency) 식별 |
| **Code Profiling** | 소스 코드 내 메서드 실행 시간 측정 | 핫스팟(Hotspot) 소스 코드 특정 |
| **SQL Monitoring** | DB 쿼리 실행 계획 및 지연 쿼리 분석 | Slow Query 원인 파악 및 튜닝 |
| **Real User Monitoring** | 실제 사용자의 브라우저/모바일 단말 성능 측정 | 최종 사용자 체감 성능(Front-end) 개선 |
| **Dependency Mapping** | 서비스 간 호출 관계 및 의존성 시각화 | 장애 전파 경로 파악 및 아키텍처 분석 |

---

## Ⅲ. APM의 분산 추적(Distributed Tracing) 메커니즘

### 1. Trace ID와 Span ID의 전파
- **Trace ID**: 전체 트랜잭션을 관통하는 고유 식별자 (HTTP Header 등에 삽입)
- **Span ID**: 각 서비스 호출 구간을 나타내는 식별자 (부모-자식 관계 형성)

### 2. 가시성 확보 결과 예시

```text
 [Client] --- (Trace ID: A) ---> [API Gateway] (Span 1: 100ms)
                                     |
                                     +--- [Order Service] (Span 2: 800ms)
                                              |
                                              +--- [DB Query] (Span 3: 700ms) !!
```
- 분석 결과: 전체 900ms 중 700ms가 DB 쿼리에서 소요됨을 즉각 파악

---

## Ⅳ. 실무적 적용 전략 및 고려사항

### 1. 도입 및 운영 전략
- **샘플링 정책**: 트래픽이 높은 환경에서는 1~5% 수준의 샘플링으로 오버헤드 최소화.
- **Alert 설정**: 단순 임계치(Threshold) 방식보다는 통계적 이상 탐지(Anomaly Detection) 도입 권고.

### 2. 구축 시 고려사항 (Antipattern 경계)
- **오버헤드 관리**: 에이전트 삽입으로 인한 애플리케이션 성능 저하(보통 3~5% 내외) 모니터링.
- **데이터 보안**: 로그/트레이스에 포함될 수 있는 개인정보(PII) 마스킹 처리 필수.

## Ⅴ. APM 도입 전후 효과 비교

| 비교 항목 | 도입 전 (Manual) | 도입 후 (APM 기반) |
|:---|:---|:---|
| **장애 인지** | 고객 불만 접수 후 인지 | 실시간 알림을 통한 선제적 인지 |
| **원인 분석** | 서버별 로그 전수 조사 (수 시간) | 트레이스 추적으로 병목 즉시 특정 (수 분) |
| **튜닝 근거** | 개발자의 직관 및 추측 | 정량적인 코드/SQL 프로파일링 데이터 |
| **커뮤니케이션** | 유관 부서 간 책임 회피 (핑퐁) | 공통 데이터를 통한 협업(DevOps) 활성화 |

## Ⅵ. 결론 및 제언

- APM은 더 이상 부가적인 도구가 아니라, 복잡한 현대적 아키텍처에서 **'시스템의 내부를 들여다볼 수 있는 유일한 창'**임.
- 향후에는 수집된 방대한 성능 데이터를 기반으로 자원을 자동으로 증설하거나 코드를 최적화하는 **Self-healing** 시스템으로의 확장이 가속화될 것임.
