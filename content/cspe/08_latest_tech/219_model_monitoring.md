# 📖 【암기용】 개념 완전 이해

> 목적: Model Monitoring을 처음 봐도 완벽히 이해하게 만든다. 시험 답안 양식이 아니라, 이해를 위한 친절한 설명이다.

## 한눈에
- **개요**: 운영 환경에 배포된 머신러닝 모델의 성능, 데이터 분포, 시스템 상태를 실시간으로 감시하고 이상 발생 시 알람을 보내는 체계
- **왜 필요한가**: 모델은 시간이 지나면 외부 환경 변화로 인해 정확도가 떨어지기 마련인데(성능 퇴화), 이를 방치하면 비즈니스 손실로 이어지기 때문
- **핵심 직관**: 건강검진을 정기적으로 받는 것처럼, 배포된 모델이 여전히 "정상적인 데이터"를 받아 "정확한 예측"을 하고 있는지 실시간으로 체크하는 청진기

## 깊이 이해
- **배경·문제의식**: 소프트웨어는 코드가 안 바뀌면 결과가 일정하지만, ML 모델은 입력 데이터가 바뀌면 결과가 틀려진다. 예를 들어, 어제까지 유행하던 패션이 오늘 바뀌면 어제 학습한 추천 모델의 정확도는 급락한다. 문제는 사용자가 피드백을 주기 전까지는 모델이 조용히 틀린 답을 내놓고 있다는 점이다(Silent Failure).
- **작동 원리**: 크게 세 가지 영역을 감시한다. ① **시스템 지표**(응답 속도, 에러율), ② **데이터 지표**(입력 데이터의 값이 평소와 다른지 - Data Drift), ③ **모델 지표**(예측값의 분포가 변했는지, 실제 정답과 얼마나 차이 나는지 - Concept Drift).
- **비유**: 고속도로 자율주행 차가 도로 상황(Data)을 잘 보고 있는지, 차선 변경 결정(Model Output)이 여전히 안전한지 관제 센터에서 계속 원격 감시하는 것과 같다.
- **구체 예시**: 신용카드 부정 결제 탐지 모델에서 갑자기 해외 결제 비중이 급증하면, 시스템이 "평소와 데이터 분포가 다르다"며 데이터 드리프트(Data Drift) 알람을 보내고 관리자가 모델 재학습 여부를 판단하게 한다.
- **흔한 오해·주의점**: "일반적인 IT 모니터링(CPU, 메모리)만 하면 충분하다"는 오해다. 시스템이 살아있어도 모델의 예측값은 엉망일 수 있으므로, 반드시 '데이터의 통계적 속성'과 '모델의 정확도'를 함께 봐야 한다.

## 연결 개념
- Data Drift — 입력 데이터의 분포가 변하는 현상
- Concept Drift — 입력과 정답 사이의 관계가 변하는 현상
- MLOps — 모델 모니터링은 MLOps의 선순환(Feedback Loop)을 완성하는 핵심 단계

# 📝 【답안용】 시험 답안 템플릿

> 목적: 시험장에서 25분에 그대로 쓰는 답안 양식. 작성방식(추상표현 금지·수치·도식·문제유형 전환)을 엄격히 지킨다.

## 핵심 인사이트 (3줄 요약)

> 1. **본질**: Model Monitoring은 운영 환경 모델의 예측 성능 퇴화, 데이터 분포 변화(Drift), 시스템 가용성을 지속적으로 감시하는 품질 관리 체계이다.
> 2. **가치**: 성능 저하로 인한 비즈니스 리스크를 사전 방지하고, 최적의 재학습(Retraining) 시점을 도출하여 모델 신뢰성을 유지한다.
> 3. **판단 포인트**: 정답(Label) 확보 지연 시 대리 지표(Proxy Metric)인 데이터/예측값 드리프트 분석을 통해 선제적 대응 체계를 구축해야 한다.

## 출제 의도 및 답안 포인트

| 출제 의도 | 반드시 짚을 핵심 | 감점 회피 포인트 |
|:---|:---|:---|
| ML 운영의 특수성 이해 확인 | 데이터/컨셉 드리프트, 성능 퇴화(Decay) | 일반적인 서버 모니터링 지표만 서술 |
| 실무적 모니터링 전략 수립 역량 확인 | 정답 확보 유무에 따른 모니터링 기법(PSI, KS-test) | 단순히 "성능 확인"이라고 추상적으로 기술 |
| MLOps 환류 체계 구성 능력 확인 | 모니터링 기반 재학습 트리거 및 폐쇄 루프 | 알람 발생 이후의 대응 절차(재학습 등) 누락 |

> 요약: 데이터의 통계적 변화와 모델의 예측 품질 변화를 감지하여 모델의 신뢰 유효 기간을 연장하는 방안 제시가 핵심이다.

## Ⅰ. 개요 및 필요성

- 정의: 운영 중인 머신러닝 모델의 시스템 가용성, 데이터 정합성, 예측 성능을 실시간으로 추적하여 모델의 유효성을 검증하는 활동
- 배경: 현실 세계의 데이터 변화로 인한 학습 모델의 유효성 상실(Model Decay), 소리 없는 실패(Silent Failure) 예방 필요
- 필요성: 일관된 사용자 경험 유지, 장애 조치 시간(MTTR) 단축, 데이터/알고리즘 편향에 따른 법적/윤리적 리스크 통제

## Ⅱ. 구조 및 구성요소

```text
Prediction Request/Response -> Data Collector (Streaming/Batch)
                                       |
                +----------------------+----------------------+
                |                      |                      |
        System Monitor        Data/Model Monitor       Evaluation Engine
        (Latency/Error)       (Drift/Outliers)         (Accuracy/F1/AUC)
                |                      |                      |
                +----------------------+----------------------+
                                       |
                                Alerting & Trigger (Retraining)
```

| 구성요소 | 역할 | 특이사항 |
|:---|:---|:---|
| System Metrics | 응답 지연(Latency), 처리량, 에러율 감시 | P99 Latency, 5xx Error |
| Drift Detector | 입력 데이터 및 예측 분포 변화 감지 | PSI, KS-test, KL-divergence |
| Quality Monitor | 데이터 누락, 타입 불일치 등 정합성 체크 | Schema Validation |
| Performance Evaluator | 실제 정답(Label) 기반 정확도 측정 | AUC, Precision, Recall |

> 요약: 시스템(인프라), 데이터(통계), 모델(성능)의 세 가지 관점을 통합하여 관측성(Observability)을 확보함.

---

## Ⅲ. 동작원리 및 흐름도

```text
실시간 데이터 수집 -> 기준(Baseline) 대조 -> 통계적 유의성 검정 -> 임계치 위반 시 알람 -> 원인 분석(RCA) -> 재학습/모델 롤백
      |                 |                |                 |                   |                   |
      +-----------------+----------------+-----------------+-------------------+-------------------+-----> 성능 지표 업데이트
```

| 단계 | 처리 내용 | 검증 기준 |
|:---:|:---|:---|
| 1 | 운영 데이터 수집 및 전처리 | 학습 데이터셋과 동일 스키마 준수 |
| 2 | 드리프트 통계 분석 (Drift Analysis) | PSI > 0.2 또는 P-value < 0.05 |
| 3 | 성능 지표 산출 (Label 확보 시) | 정확도 하락폭 5%p 이상 감지 |
| 4 | 자동 대응 및 재학습 트리거 | 재학습 파이프라인 자동 호출 |

> 요약: 배포 시점의 데이터 분포를 기준(Baseline)으로 삼아 운영 데이터의 이질성을 상시 검정함.

## Ⅳ. 특징

| 구분 | IT 인프라 모니터링 | Model Monitoring | 판단 포인트 |
|:---|:---|:---|:---|
| 감시 대상 | 서버, 네트워크, DB 상태 | 데이터 분포, 모델 예측 품질 | 도메인 특성 |
| 실패 형태 | 하드 장애 (Crash/Error) | 소프트 장애 (Wrong Prediction) | Silent Failure 유무 |
| 지표 종류 | CPU, Memory, Latency | PSI, Accuracy, F1-Score | 통계 지표 포함 여부 |
| 대응 방식 | 재시작, 스케일 업 | 재학습, 모델 롤백, 데이터 보정 | 대응 조치의 성격 |

> 요약: 모델 모니터링은 인프라 정상 여부를 넘어 "내용물의 품질"이 여전히 유효한지를 검증하는 상위 계층의 모니터링임.

## Ⅴ. 심화 비교 및 적용 판단

| 구분 | 데이터 드리프트 (Data Drift) | 컨셉 드리프트 (Concept Drift) | 선택 기준 |
|:---|:---|:---|:---|
| 변화 주체 | 입력 데이터 $P(X)$ | 입력-정답 관계 $P(Y \mid X)$ | 변화의 근원 |
| 탐지 용이성 | 높음 (정답 필요 없음) | 낮음 (정답 확보 필요) | 피드백 가용성 |
| 해결 방안 | 데이터 수집 범위 확대 | 모델 구조 변경 또는 전면 재학습 | 조치 난이도 |

> 요약: 정답 확보가 늦은 환경에서는 데이터 드리프트를 조기 경보 지표로 활용하고, 정답 확보 후 컨셉 드리프트를 최종 확정 지표로 사용함.

| 리스크 | 원인 | 대응 방안 | 확인 지표 |
|:---|:---|:---|:---|
| 성능 퇴화 (Decay) | 현실 세계 데이터 패턴 변화 | 정기적 재학습 및 Drift 기반 트리거 | 운영 정확도 추세선 |
| 알람 과부하 | 너무 민감한 임계치 설정 | 통계적 유의 수준(P-value) 조정 | 오탐률(False Alarm Rate) |
| 정답 지연 (Label Lag) | 실제 정답 확인에 긴 시간 소요 | 프록시 지표(예측 분포) 모니터링 | 예측값 분포 안정성 지표 |

> 요약: 성능 퇴화는 재학습으로, 알람 소음은 임계치 최적화로, 정답 지연은 대리 지표로 대응함.

| 점검 항목 | 목표 기준 | 측정 방법 |
|:---|:---|:---|
| 드리프트 감지 정확도 | 주요 성능 하락 전 80% 사전 감지 | 성능 하락과 드리프트 알람 시점 비교 |
| 서비스 지연시간 | 모니터링 부하 포함 Latency 100ms 이내 | API 응답 시간 프로파일링 |
| 재학습 자동화율 | 드리프트 발생 시 자동 재학습 90% | 수동 개입 없는 파이프라인 실행 비율 |

> 요약: 도입 효과는 사전 탐지율, 운영 부하 최소화, 대응 자동화 수준으로 측정함.

## Ⅵ. 실무 적용 및 결론

**적용 방안 3개:**
1. 드리프트 기반 조기 경보: 실제 정답을 알기 전, 입력 데이터의 PSI(Population Stability Index)가 0.2를 초과하면 모델 성능 하락을 예측하고 즉시 분석 착수
2. 성능 하락 자동 차단: 운영 정확도가 임계치 이하로 하락할 경우, 안전한 이전 버전 모델(Champion-Challenger 구조)로 자동 롤백하여 비즈니스 손실 최소화
3. 데이터 품질 감사: 실시간 데이터 검증(Data Validation) 게이트를 두어 스키마 위반이나 결측치가 급증한 데이터가 모델로 유입되는 것을 원천 차단

**결론 (2줄):**
- 기술사 판단: 모델 모니터링은 모델을 배포한 이후의 "신뢰"를 유지하기 위한 기술적 약속이며, MLOps의 완성도를 결정짓는 척도임
- 향후 방향: 생성형 AI의 확산에 따라 텍스트의 유해성, 환각 현상, 응답의 일관성을 감시하는 "Semantic Monitoring" 영역으로 확장될 것임
