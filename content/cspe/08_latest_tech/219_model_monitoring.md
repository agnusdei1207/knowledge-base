# 📖 【암기용】 개념 완전 이해

> 목적: 모델 모니터링을 처음 봐도 운영 관점에서 이해하게 만든다.

## 한눈에
- **개요**: 배포된 ML 모델의 예측 품질, 입력 분포, 지연시간, 오류를 계속 관측하는 운영 활동
- **왜 필요한가**: 모델은 배포 후 데이터와 업무 규칙이 바뀌면 학습 시점의 정확도를 유지하지 못한다.
- **핵심 직관**: 모델 모니터링은 공장 출하 후 제품 불량률을 계속 재는 품질 검사와 같다.

## 깊이 이해
- **배경·문제의식**: 일반 애플리케이션은 오류 로그와 CPU 사용률을 보면 장애를 찾을 수 있지만, ML 모델은 HTTP 200을 반환해도 예측 품질이 하락할 수 있다.
- **작동 원리**: 입력 feature, 예측값, 실제 label, 지연시간, 오류율을 수집하고 PSI, KS-test, AUC, F1, p95 latency 같은 지표가 기준을 벗어나면 알람과 재학습 절차를 실행한다.
- **비유**: 병원 건강검진처럼 혈압만 보지 않고 혈당, 심전도, 체중 변화를 함께 보아 이상 징후를 찾는 방식이다.
- **구체 예시**: 추천 모델의 CTR이 7일 이동평균 4.0%에서 3.2%로 20% 하락하고 PSI가 0.25를 넘으면 모델 재평가와 롤백 후보 검토를 시작한다.
- **흔한 오해·주의점**: 모델 모니터링은 서버 모니터링의 다른 이름이 아니며, label 지연과 데이터 품질 문제까지 포함해야 원인 추적이 가능하다.

## 연결 개념
- Data Drift — 입력 데이터 분포 변화 감지
- Concept Drift — 입력과 정답 관계 변화 감지
- MLOps — 모니터링 결과를 재학습과 승인 배포로 연결

# 📝 【답안용】 시험 답안 템플릿

> 목적: 시험장에서 25분에 그대로 쓰는 답안 양식.
> 핵심: 모델 장애는 시스템 장애와 품질 저하를 함께 보아야 하므로 지표, 임계값, 대응 절차를 연결한다.

## 핵심 인사이트 (3줄 요약)

> 1. **본질**: Model Monitoring은 배포 모델의 입력, 출력, 품질, 운영 지표를 지속 관측하는 MLOps 통제 활동임.
> 2. **가치**: AUC 5%p 하락, PSI 0.2 초과, p95 지연 500ms 초과 같은 조건을 감지하여 재학습·롤백 의사결정을 지원함.
> 3. **판단 포인트**: 데이터 drift와 model performance degradation을 구분하고 label 지연이 있는 업무에는 proxy metric을 함께 설계해야 함.

## 출제 의도 및 답안 포인트

| 출제 의도 | 반드시 짚을 핵심 | 감점 회피 포인트 |
|:---|:---|:---|
| 운영 ML의 품질 통제 역량 확인 | 입력 분포, 예측 품질, 시스템 지표, 알람 기준 연결 | CPU·메모리 관측만 쓰고 모델 품질 지표 누락 |
| MLOps 생명주기 이해 확인 | 모니터링 -> 분석 -> 재학습 -> 승인 배포 흐름 | 알람 후 조치 기준 없이 지표만 나열 |
| 실무 적용 판단 확인 | label 지연, shadow label, proxy metric, drift 임계값 | 모든 지표에 동일 임계값 적용 |

> 요약: 이 문제는 모델 운영 지표를 재학습과 배포 통제로 연결하는 판단력을 요구한다.

---

## Ⅰ. 개요 및 필요성

- 개요: 배포 모델 품질 관측 체계
- 배경: ML 모델은 운영 데이터 분포와 업무 정책 변화로 학습 시점 성능을 그대로 유지하지 못함.
- 필요성: PSI 0.2 초과, AUC 5%p 하락, p95 지연 500ms 초과 같은 조건을 탐지해 재학습·롤백을 실행해야 함.

---

## Ⅱ. 구조 및 구성요소

```text
Online Request -> Feature Log -> Prediction Log -> Metric Store
Batch Label -> Performance Eval -> Alert Rule -> Retraining / Rollback
```

| 구성요소 | 역할 | 특이사항 |
|:---|:---|:---|
| Feature Logger | 입력 feature와 schema 기록 | PII masking, sampling rate 관리 |
| Prediction Logger | 예측값·확률·모델 버전 기록 | model_id와 request_id 연결 |
| Metric Store | 품질·drift·지연 지표 저장 | PSI, AUC, F1, p95 latency |
| Alert Manager | 임계값 초과 시 담당자·워크플로 호출 | severity, SLA, runbook 연동 |

> 요약: 모델 모니터링은 feature, prediction, label, 운영 지표를 model_id 기준으로 연결해 원인 추적성을 확보한다.

---

## Ⅲ. 동작원리 및 흐름도

```text
로그 수집 -> 지표 계산 -> 임계값 비교 -> 원인 분류 -> 재학습 / 롤백 / 관찰 지속
```

| 단계 | 처리 내용 | 검증 기준 |
|:---:|:---|:---|
| 1 | 입력 feature와 예측 결과 수집 | 누락 로그 1% 이하 |
| 2 | drift와 품질 지표 계산 | PSI, KS-test, AUC, F1 |
| 3 | 알람 임계값과 SLO 비교 | PSI 0.2 초과, AUC 5%p 하락 |
| 4 | 원인 분석 후 조치 실행 | 재학습 승인, canary rollback |

> 요약: 모니터링은 로그 수집에서 끝나지 않고 임계값 판단과 운영 조치까지 이어질 때 실효성을 갖는다.

---

## Ⅳ. 특징

| 구분 | 일반 시스템 모니터링 | 모델 모니터링 | 수치 기준 |
|:---|:---|:---|:---|
| 관측 대상 | CPU, 메모리, 오류율 | feature, prediction, label, drift | PSI 0.2, AUC 5%p |
| 장애 형태 | 예외, 타임아웃, 리소스 고갈 | 무오류 품질 하락 | CTR 10% 이상 하락 |
| 대응 방식 | 재시작, scale-out, 패치 | 재학습, threshold 조정, 롤백 | canary error 1% 이하 |

> 요약: 모델 모니터링은 시스템 정상 응답 상황에서도 예측 품질 하락을 감지해야 한다.

---

## Ⅴ. 심화 비교 및 적용 판단

| 비교 축 | 기존/대안 | 본 키워드 | 선택 기준 |
|:---|:---|:---|:---|
| 관측 범위 | APM 중심 | APM + drift + 품질 지표 | ML 의사결정 자동화 여부 |
| 데이터 요구 | 실시간 로그만 사용 | feature·prediction·label 결합 | label 지연 1일 이상이면 proxy metric 병행 |
| 운영 조치 | 장애 복구 중심 | 재학습·롤백·검증 배포 | 승인 게이트와 model registry 보유 |

> 요약: 모델 모니터링은 label 확보 주기와 업무 리스크에 따라 실시간 지표와 사후 품질 지표를 조합한다.

| 리스크 | 원인 | 대응 방안 | 확인 지표 |
|:---|:---|:---|:---|
| 알람 과다 | 임계값 단일 적용 | 업무군별 threshold와 hysteresis 적용 | false alert rate 10% 이하 |
| 품질 하락 미탐지 | label 지연 | proxy metric, shadow label, delayed evaluation | label coverage 95% 이상 |
| 원인 추적 실패 | model_id와 데이터 lineage 누락 | request_id, feature version, model version 기록 | lineage 누락 0건 |

> 요약: 운영 리스크는 알람 기준, label 지연, lineage 누락을 통제해야 줄일 수 있다.

| 점검 항목 | 목표 기준 | 측정 방법 |
|:---|:---|:---|
| 예측 품질 | AUC 5%p 이내 하락 | batch evaluation, holdout label |
| 데이터 분포 | PSI 0.2 이하 유지 | feature histogram 비교 |
| 운영 SLO | p95 latency 500ms 이하 | APM, serving log |

> 요약: 도입 효과는 예측 품질, 데이터 분포, 운영 SLO를 같은 대시보드에서 확인해야 판단 가능하다.

---

## Ⅵ. 실무 적용 및 결론

**적용 방안 3개:**
1. 관측 설계: request_id, model_id, feature_version, prediction_score를 100% 기록하고 PII 필드는 hashing 또는 masking 처리함.
2. 알람 설계: PSI 0.2 초과, AUC 5%p 하락, p95 latency 500ms 초과를 severity별 runbook에 연결함.
3. 조치 설계: 알람 발생 후 재평가 데이터셋 생성, model registry 승인, canary 5% 배포, rollback 기준을 배포 파이프라인에 포함함.

**결론 (2줄):**
- 기술사 판단: 업무 손실이 큰 모델은 정확도 모니터링보다 drift, latency, lineage, 승인 게이트를 함께 설계해야 함.
- 향후 방향: 모델 모니터링은 LLMOps 평가, AI Governance 감사, 자동 재학습 파이프라인과 통합되는 방향임.
