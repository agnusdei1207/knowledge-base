# 📖 【암기용】 개념 완전 이해

## 한눈에
- **개요**: 에이전트 감사로그는 AI 에이전트의 **요청·추론·도구 호출·승인·결과**를 **Trace ID**로 연결해 기록하는 **감사 추적(Audit Trail)** 체계다. 일반 애플리케이션 로그가 API 호출만 남기는 것과 달리, 모델 버전·프롬프트 버전·판단 근거까지 포함해 "누가, 왜, 어떤 AI 판단으로 시스템을 변경했는가"를 증명한다.
- **왜 필요한가**: 에이전트가 방화벽 규칙 변경·결제 처리·데이터 삭제 등 시스템 상태를 바꾸면, 사고 발생 시 "어떤 모델이 어떤 입력에 기반해 이 결정을 내렸는가"를 재현할 수 있어야 한다. 대화 로그만으로는 도구 실행의 책임 추적과 모델 버전 재현이 불가능하다.
- **핵심 직관**: 금융 거래에서 계좌이체의 요청자·승인자·처리 시스템·금액·시각을 모두 거래번호(Trace ID)로 묶어 보관하는 것과 같다. AI 에이전트의 "거래 내역서"다.

## 핵심 용어 정리 (내부에 등장하는 것들)

| 용어/표기 | 의미 | 비유·예 |
|:---|:---|:---|
| 감사 추적(Audit Trail, 상위 키워드) | 시스템 활동의 시간순 기록으로 책임 소재를 증명하는 체계 | 은행 거래 내역서 |
| Trace ID | 하나의 요청이 거치는 전체 호출 경로를 추적하는 고유 식별자 | 택배 송장번호 — 전 구간 추적 |
| 입력 해시(Input Hash) | 프롬프트·도구 입력의 원문 대신 해시값을 저장해 재현 검증에 사용 | 서류 원본 대신 "지문"을 보관 |
| WORM(Write Once Read Many) | 한 번 쓰면 수정·삭제가 불가능한 저장 방식으로 로그 무결성 보장 | 볼펜으로 쓴 장부 — 지울 수 없음 |
| Hash Chain | 각 로그 엔트리에 이전 엔트리의 해시를 포함시켜 위변조를 감지 | 블록체인의 연결 원리 |
| 부인방지(Non-repudiation) | 행위자가 자신의 행위를 부정할 수 없게 하는 보안 속성 | 서명한 계약서 — "안 했다"고 할 수 없음 |
| 토큰화/마스킹 | 민감정보(개인정보·비밀키)를 대체 토큰이나 마스킹 처리해 노출을 방지 | 카드번호 1234-****-****-5678 |

## 깊이 이해
- **배경·문제의식**: 에이전트 권한통제(020)가 "실행할 자격이 있는가"를 판단한다면, 감사로그는 "실행한 결과를 어떻게 증명하는가"를 담당한다. 기존 애플리케이션 로그는 API 요청·응답만 기록해, 모델이 왜 이 도구를 호출했는지(모델 버전·프롬프트·추론 근거)를 재현할 수 없다. 규제(개인정보보호법·전자금융감독규정 등)에서 요구하는 "AI 의사결정의 설명 가능성"도 감사로그 없이는 충족이 불가능하다.
- **작동 원리(어떻게+왜)**: ① 에이전트 요청이 들어오면 Trace ID를 생성해 전체 실행 경로에 부착한다. ② 각 단계(모델 호출, 도구 호출, 승인, 결과)에서 {Trace ID, 타임스탬프, 행위자, 모델 버전, 프롬프트 버전, 도구명, 입력 해시, 응답 코드, 승인자}를 구조화된 JSON 이벤트로 기록한다. ③ 민감정보(프롬프트 내 개인정보, 비밀키)는 원문 저장하지 않고 토큰화·마스킹·해시로 대체한다. ④ WORM 저장소에 Hash Chain으로 적재해 위변조를 방지하고, SIEM으로 전송해 이상 패턴을 탐지한다.
- **비유**: 수술 기록과 같다. 집도의(에이전트), 마취의(도구), 수술 방법(모델·프롬프트), 환자 정보(입력 해시), 결과(응답 코드), 보호자 동의(승인)를 모두 차트 번호(Trace ID)로 묶어 의무 보존 기간 동안 보관한다. 차트 없이 수술하면 의료 사고 시 책임 입증이 불가능하다.
- **구체 예시**: 방화벽 정책 변경 에이전트가 ① 요청자: ops-user-0042, ② 모델: gpt-4o-2025-06-01, ③ 프롬프트: v2.3, ④ 도구: firewall-api, ⑤ 입력 해시: SHA-256(규칙 JSON), ⑥ 승인자: sec-admin-007, ⑦ 결과: 200 OK, ⑧ Trace ID: tr-20260705-001을 하나의 감사 레코드로 남긴다.
- **흔한 오해·주의점**: "대화 로그를 저장하면 감사로그 대용이 된다"는 오해가 있다. 대화 로그는 비정형이고 도구 실행 책임·모델 버전 재현이 빠져 감사 증거로 부적합하다. 또한 프롬프트 원문을 그대로 저장하면 개인정보·영업비밀 노출 위험이 있으므로 반드시 마스킹·해시를 적용해야 한다.

## 연결 개념
- 에이전트 권한통제(020) — 허용·거부 판단의 감사 기록을 감사로그가 보존함
- 에이전트 관측성(030) — 실행 추적·메트릭 수집의 모니터링 측면
- 에이전트 상태관리(019) — 상태 전이 이력이 감사로그와 연동됨

> 2. **가치**: 사고 원인 분석, 모델 버전 재현, 규제 대응, 부인방지 증거를 제공함.
> 3. **판단 포인트**: 민감정보 마스킹, WORM/Hash Chain 무결성, 모델·프롬프트 버전 기록, 보존 기간을 함께 설계해야 함.

| 기존 앱 로그와 차별적 설계 역량 | 모델 판단 근거·승인자·입력 해시 포함 | 민감정보 원문 저장 금지(토큰화·마스킹·해시 필수) |

> 요약: AI 도구 호출의 모델 버전 재현과 로그 무결성 설계 역량을 증명해야 함.

---

## Ⅰ. 개요 및 필요성

- 개요: AI 에이전트 실행의 전 과정을 Trace ID로 연결한 정형 감사 기록 체계임
- 배경: 기존 앱 로그는 API 호출만 남겨 모델 판단·도구 호출 근거를 재현할 수 없음
- 필요성: 사고 원인 분석·규제 대응·부인방지에 모델 버전·프롬프트·승인 이력 포함 감사 기록이 필수임

---

## Ⅱ. 구조 및 구성요소

```text
사용자 요청 -> Trace ID 생성 -> 모델 호출 기록 -> 도구 호출 기록
                                                      |
                  승인 기록 <-  결과 기록  <-  마스킹/해시 적용
                      |
                      +-> WORM 저장(Hash Chain) -> SIEM 연동
```

| 구성요소 | 역할 | 특이사항 |
|:---|:---|:---|
| Trace ID | 전체 실행 경로를 하나의 식별자로 연결 | 요청-모델-도구-결과 추적 |
| Model Context Log | 모델 버전·프롬프트 버전·파라미터 기록 | 재현성 확보의 핵심 |
| Tool Call Log | 도구명·입력 해시·응답 코드·승인자 기록 | 입력 원문 대신 해시 저장 |
| Integrity Layer | WORM 저장소+Hash Chain으로 위변조 방지 | 보존 기간 규정 준수 |

> 요약: Trace ID를 중심으로 모델·도구·승인 로그를 연결하고, WORM+Hash Chain으로 무결성을 보장함.

---

## Ⅲ. 동작원리 및 흐름도

```text
요청 수신 -> Trace ID 생성 -> 모델 호출 기록 -> 도구 호출 기록
  -> 승인 기록 -> 결과 저장 -> 마스킹 검증 -> WORM 적재
```

1. Trace 생성: 요청 수신 시 Trace ID를 생성하고 사용자 ID·요청 목적·타임스탬프를 기록함
2. 실행 기록: 모델 버전·프롬프트 버전·도구명·입력 해시·응답 코드를 단계별로 기록함
3. 민감정보 처리: 프롬프트·응답에 포함된 개인정보·비밀키를 토큰화·마스킹·해시로 대체함
4. 보존·검증: WORM 저장소에 Hash Chain으로 적재하고, 보존 기간(변경형 1년 이상) 동안 무결성 검증을 실행함

> 요약: Trace 생성→실행 기록→민감정보 처리→WORM 보존 순서로 위변조 불가 감사 증거를 구축함.

---

## Ⅳ. 특징

- 재현성: 모델 ID·프롬프트 버전·파라미터를 기록해 동일 입력으로 판단 과정을 재현 가능함
- 무결성: WORM+Hash Chain으로 로그 수정·삭제가 불가능하며 위변조를 즉시 감지함
- 민감정보 보호: 원문 저장을 금지하고 토큰화·마스킹·해시를 적용해 노출 위험을 차단함
- 정형 구조: JSON 이벤트 형식으로 SIEM·분석 도구와 연동이 용이함
- 부인방지: Trace ID로 행위자·판단·결과를 연결해 "AI가 했다/안 했다"의 부인을 방지함

---

## Ⅴ. 심화 비교 및 적용 판단

| 구분 | 기존 앱 로그 | Agent Audit Log | 선택 기준 |
|:---|:---|:---|:---|
| 기록 범위 | API 요청·응답 | 모델 버전·프롬프트·도구·승인 포함 | 모델 판단 재현이 필요하면 Agent 로그 |
| 무결성 | DB/파일 로그(수정 가능) | WORM+Hash Chain(수정 불가) | 규제·감사 요구 시 WORM 필수 |
| 민감정보 | 앱 레벨 마스킹 | 입력 해시·토큰화·프롬프트 마스킹 | 개인정보보호법·내부 정책 준수 |

> 요약: 모델 판단 재현과 규제 감사가 필요하면 기존 앱 로그가 아닌 Agent Audit Log를 설계함.

**리스크·대응:**
- 민감정보 노출: 프롬프트·응답 원문 저장 → 토큰화·마스킹·해시 적용, 원문 저장 금지 정책 (지표: 마스킹 적용률 100%)
- 로그 위변조: 수정·삭제 가능 저장소 사용 → WORM+Hash Chain, 접근 권한 분리 (지표: 무결성 검증 통과율 100%)
- 재현 불가: 모델·프롬프트 버전 미기록 → 모델 ID·프롬프트 버전·파라미터를 Trace에 포함 (지표: 재현 가능 건수/전체 건수)

**도입 후 점검 지표:**
- Trace 연결률: 요청-모델-도구-결과 100% 연결 — Trace ID 누락 건수 모니터링
- 보존 기간: 변경형 작업 로그 1년 이상 보존 — 보존 만료 전 알림·아카이빙

---

## Ⅵ. 실무 적용 및 결론

**적용 방안 3개:**
1. 요청마다 Trace ID를 생성하고 모델 버전·프롬프트 버전·도구명·입력 해시·승인자·결과를 정형 JSON으로 기록함
2. 민감정보는 토큰화·마스킹·해시로 대체하고, 원문 저장 금지 정책을 CI/CD 파이프라인에서 자동 검증함
3. WORM 저장소에 Hash Chain으로 적재하고 SIEM으로 전송해 이상 호출 패턴을 자동 탐지함

**결론:**
- 기술사 판단: AI가 시스템 상태를 변경하는 업무는 Agent Audit Log 없이 운영 승인 대상이 아님
- 향후 방향: Agent Audit Log는 AI 거버넌스(161)·규제 대응·보안 관제의 핵심 증거 계층으로 발전함
