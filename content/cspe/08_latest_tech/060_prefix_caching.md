## 미리 알고가기

- 접두 캐싱 ($Prefix$ $Caching$): 여러 요청이 공통으로 사용하는 시스템 프롬프트나 동일 지식 문서(접두부, $Prefix$)의 $KV$ 캐시를 VRAM에 영구 박제하여 연산 재활용률을 극대화하는 서빙 기법임
- 해시 매칭 ($Hash$ $Match$): 프롬프트 텍스트를 해시 키값으로 치환하여 기존 메모리에 완벽히 적중하는 캐시가 있는지 1대1 매핑하는 초고속 검색 구조임
- 메모리 수명 정책 ($TTL$ / $LRU$): 유한한 VRAM 캐시 공간을 보존하기 위해 보관 기한($TTL$)을 설정하거나 가장 오래 참조되지 않은 캐시($LRU$)부터 밀어내는 자원 해제 규칙임
- 복사 쓰기 ($Copy-on-Write$): 여러 요청이 동일 블록을 안전히 읽고 있다가, 한 요청이 개별 답변(새 단어)을 덧붙이기 시작하는 지점부터 해당 물리 블록을 새로 복사해 분기하는 메모리 격리 장치임

## Ⅰ. 개요

- **정의/개념**: Prefix Caching은 LLM 호출 시 중복 유입되는 고정형 시스템 프롬프트나 RAG 기반의 참조 문서들의 $KV$ 캐시 해시($Hash$) 값을 매핑 테이블에 저장해 두고, 후속 질의 인입 시 프리필($Prefill$) 연산을 완전 스킵하여 첫 단어 출력 지연($TTFT$)을 대폭 절감하는 지능형 서빙 캐시 기술임
- **배경/필요성**: RAG 파이프라인이나 멀티턴 대화 세션에서는 전체 프롬프트의 $80 \sim 95\%$ 영역이 동일한 텍스트로 구성되는데, 매 질문마다 수만 단어의 프리필 연산을 GPU에서 반복 수행하면 막대한 가중치 로드 시간과 비용이 발생하므로 캐싱 계층이 강력히 필요해짐

## Ⅱ. 특징

- 긴 사내 지식 데이터베이스 문서나 고정 안내문이 섞인 환경에서, 모델 순방향 연산 비용을 획기적으로 낮추어 기업의 추론 서빙 수지를 안정화함
- 가상 메모리 블록 관리 기반(PagedAttention)과 완벽히 융합하여, 블록 주소 체계 단위로 읽기 전용 공유($Sharing$) 계수를 유연하게 제어함
- 단어의 순서나 글자 하나(마침표 하나 등)만 달라져도 해시 매칭이 전체 불일치 판정을 받아 캐시가 통째로 만료될 수 있는 민감성을 가짐

## Ⅲ. 종류 및 비교

| 판단 기준 | 캐싱 없는 기본 프리필 | 접두 캐싱 (Prefix Caching) | 세션 단위 이력 재사용 (Session Reuse) |
|:---|:---|:---|:---|
| **가속 원리** | 매번 처음부터 전체 텍스트 연산 | 공통 해시 매칭 시 프리필 생략 | 동일 유저 세션의 특정 캐시 점유 |
| **TTFT 단축율** | 0% (기준선) | 극도로 우수함 (최대 90% 이상) | 우수함 |
| **자원 공유 범위** | 공유 없음 | 전체 세션 대상 (다중 사용자 공유) | 동일 세션 내에서만 제약적으로 공유 |
| **캐시 파열 민감도** | 없음 | 매우 높음 (글자 변경 시 전체 미적중) | 높음 |

> 요약: 기본 프리필은 단순 서빙에, 접두 캐싱은 공통 프롬프트를 쓰는 대다수 동접 세션 가속에, 세션 재사용은 1대1 장기 채팅 대화 안정성에 적합함.

## Ⅳ. 구성요소 및 구조

| 구성요소 | 설명 |
|:---|:---|
| 해시 매처 ($Matcher$) | 유입된 프롬프트의 토큰 문자열을 순차적으로 청킹하고 $SHA-256$ 등으로 해싱하여 기존 적중 캐시를 찾는 비교기임 |
| 캐시 저장소 | 물리 VRAM 주소 정보와 매칭된 텍스트 해시 키값을 보관하고 있는 인덱스 테이블임 |
| $CoW$ 제어 장치 | 하나의 캐시 블록을 공유하던 세션들이 독자 답변을 뱉을 때 충돌 없이 주소를 복사 격리하는 모듈임 |
| 회수 매니저 ($Evictor$) | VRAM 임계치 도달 시 사용 빈도가 가장 떨어지는 캐시를 밀어내는 $LRU/LFU$ 제어부임 |

```text
[ Prefix Caching 해시 매칭 처리 ]
User 1: [System Prompt (Hash: 0xFA)] + [Query A] ---> Hit 0xFA (Skip Prefill) -> Compute Query A
User 2: [System Prompt (Hash: 0xFA)] + [Query B] ---> Hit 0xFA (Skip Prefill) -> Compute Query B
- 공통 시스템 프롬프트(0xFA)의 연산을 생략하고 오직 개별 질문 영역(A, B)만 빠르게 연산함
```

## Ⅴ. 원리 및 절차 흐름도

```text
+-------------+     +--------------+     +-------------+     +-------------+
| 프롬프트인입| --> | 접두 해싱 및 | --> | 매칭 블록   | --> | 독자 생성   |
| 및 토큰 분석|     | 매칭 조회    |     | 즉시 바인딩 |     | 및 캐시 분기|
+-------------+     +--------------+     +-------------+     +-------------+
```

1. **프롬프트 분리** — 들어온 텍스트 프롬프트를 기본 캐시 단위(예: 16토큰의 배수)로 묶어 접두부 구간을 추출함
2. **해시 검색** — 추출한 텍스트 블록 체인을 해시 키로 변환하고 캐시 저장소 인덱스를 조회하여 일치 주소를 검출함
3. **연산 스킵** — 적중한 물리 블록들을 블록 테이블에 즉시 복사 연결하고, 이에 해당하는 프리필 신경망 연산을 스킵 처리함
4. **분기 쓰기** — 캐시가 불일치하는 독자 질문 단락부터 물리 블록을 새로 개설하고, 생성 완료 후 사용 기한을 갱신함

## Ⅵ. 실무 적용 및 유의점

1. 프롬프트 시작 단락에 '실시간 날짜/시간(예: `현재 시각은 13:45입니다`)'이나 동적 세션 $ID$를 집어넣으면 전체 해시 적중률이 0%로 무너져 캐싱 효과를 전혀 누릴 수 없으므로, 반드시 고정형 규칙 텍스트를 프롬프트 최선두에 배치하고 동적 팩터는 맨 하단에 꼬리표로 미는 '프롬프트 순서 구조 설계'를 수립해야 함
2. 너무 많은 공통 문서를 무분별하게 캐싱 풀에 적재하면 서빙 VRAM이 꽉 차서 신규 세션의 배칭 슬롯이 찌그러지는 주객전도가 발생하므로, 반드시 캐시 최대 허용량 가이드라인을 지정하고, 캐시 적중률($Cache$ $Hit$ $Rate$) 대비 VRAM 마진을 데일리 모니터링해야 함

## Ⅶ. 결론

- Prefix Caching은 자연어 데이터 구조에 전산학적 캐시 인덱싱을 덧입혀 인프라 효율성을 개척한 혁신 메커니즘이며, 설계자는 높은 캐시 적중률을 유도하기 위한 프롬프트 가이드라인 설계와 VRAM 자원의 균형 있는 메모리 회수 정책을 반드시 결합해 구현해야 함
