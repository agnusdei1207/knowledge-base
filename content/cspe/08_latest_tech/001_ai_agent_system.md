# 📖 【암기용】 개념 완전 이해

> 목적: AI 에이전트 시스템을 처음 봐도 완벽히 이해하게 만든다.

## 한눈에
- **개요**: LLM이 목표를 해석하고 도구를 호출해 작업을 완수하는 시스템
- **왜 필요한가**: 기존 챗봇은 답변 생성에서 멈추지만 업무 자동화는 조회·계산·승인·기록까지 필요함.
- **핵심 직관**: LLM은 두뇌, 도구는 손, 메모리와 정책은 업무 규정임.

## 깊이 이해
- **배경·문제의식**: RAG는 지식 검색을 보강하지만, 티켓 생성·DB 조회·코드 실행 같은 행위 수행은 별도 오케스트레이션이 필요함.
- **작동 원리**: 목표를 계획으로 분해하고, 필요한 도구를 선택하며, 실행 결과를 관찰해 다음 행동을 반복함.
- **비유**: 신입 직원에게 업무 목표·사내 시스템 권한·체크리스트를 주고, 결과를 검토하며 단계별 수행시키는 구조.
- **구체 예시**: 장애 분석 에이전트가 로그 검색 -> 원인 후보 3개 산출 -> Runbook 조회 -> Jira 티켓 생성까지 수행함.
- **흔한 오해·주의점**: 에이전트는 자율 실행 범위가 넓어질수록 권한 오남용·도구 비용·감사 누락 위험이 증가함.

## 연결 개념
- MCP — 외부 도구·자원 연결 표준
- ReAct — 추론과 행동을 번갈아 수행하는 패턴
- LLMOps — 배포 후 평가·감사·비용 통제 체계

# 📝 【답안용】 시험 답안 템플릿

> 목적: 시험장에서 25분에 그대로 쓰는 답안 양식.

## 핵심 인사이트 (3줄 요약)

> 1. **본질**: AI 에이전트 시스템은 LLM 추론을 계획·도구호출·관찰·메모리와 결합한 작업 수행 아키텍처임.
> 2. **가치**: 단순 질의응답을 업무 처리 단위로 확장하여 검색·분석·실행·기록을 하나의 흐름으로 묶음.
> 3. **판단 포인트**: 자율성보다 권한 경계, 감사로그, 실패 복구, 비용 한도를 먼저 설계해야 함.

## 출제 의도 및 답안 포인트

| 출제 의도 | 반드시 짚을 핵심 | 감점 회피 포인트 |
|:---|:---|:---|
| LLM 기반 작업 수행 아키텍처의 구조와 실행 흐름 이해 | Planner-Reasoner-Executor-Memory-Policy 폐루프 구조, 도구 호출 통제 | 단순 챗봇과의 차이를 명확히 구분하지 않으면 개념 혼동으로 감점 |
| 자율 실행의 위험과 통제 방안 설계 능력 | RBAC, 감사로그, 호출 한도, Human Approval 분기 | 권한·비용·감사 통제 없이 자율성만 강조하면 실무 이해 부족으로 감점 |

> 요약: AI 에이전트 시스템은 실행 능력의 구조화와 권한·감사 통제를 함께 제시해야 출제 의도를 충족함.

---

## Ⅰ. 개요 및 필요성

- 정의: LLM 추론과 도구 호출을 결합한 작업 수행 아키텍처
- 배경: 생성형 AI 활용이 답변 생성에서 업무 자동화로 이동하면서 도구 호출·상태관리 필요
- 필요성: 조회·분석·실행·기록을 하나의 흐름으로 묶되, 감사·보안 통제를 내장해야 함

---

## Ⅱ. 구조 및 구성요소

```text
사용자 목표 -> Planner -> LLM Reasoner -> Tool Executor
             |           |              |
             +-> Memory  +-> Policy     +-> Audit Log
```

| 구성요소 | 역할 | 특이사항 |
|:---|:---|:---|
| Planner | 목표를 하위 작업으로 분해 | 단계 수·종료조건 정의 |
| Tool Executor | API·DB·검색·코드 실행 | RBAC·허용목록 적용 |
| Memory | 대화·업무 상태 저장 | 개인정보 TTL·암호화 필요 |
| Policy Engine | 권한·비용·위험 통제 | 승인 필요 작업 분기 |

> 요약: 에이전트 구조는 계획-추론-도구실행-메모리-정책통제의 폐루프 구조임.

---

## Ⅲ. 동작원리 및 흐름도

```text
목표 입력 -> 계획 생성 -> 도구 선택 -> 실행/관찰
             |           |              |
             +-> 검증    +-> 정책 체크  +-> 결과 평가
```

| 단계 | 처리 내용 | 검증 기준 |
|:---:|:---|:---|
| 1 | 목표·제약조건 수집 | 업무 범위, 권한, 비용 한도 |
| 2 | 작업 계획 생성 | 단계 수, 의존관계, 종료조건 |
| 3 | 도구 호출·관찰 | API 응답코드, p95 지연, 오류율 |
| 4 | 결과 검증·기록 | 근거 링크, 로그ID, 승인 이력 |

> 요약: 에이전트는 계획과 실행을 반복하되, 도구 호출마다 정책 검증을 거치고 결과를 로그로 남김.

## Ⅳ. 특징

| 구분 | 기존 챗봇 | AI 에이전트 | 수치·판단 포인트 |
|:---|:---|:---|:---|
| 처리 범위 | 답변 생성 | 조회·실행·기록 | 작업 성공률, 도구 오류율 |
| 상태관리 | 대화 이력 중심 | 메모리·워크플로우 상태 | TTL, 암호화, 재시도 횟수 |
| 위험 | 부정확 답변 | 권한 오남용·비용 폭증 | RBAC, 승인, 호출 한도 |

> 요약: AI 에이전트는 실행 능력을 얻는 대신 권한·비용·감사 통제가 필수 설계축이 됨.

---

## Ⅴ. 심화 비교 및 적용 판단

| 구분 | 기존/대안 | AI 에이전트 시스템 | 선택 기준 |
|:---|:---|:---|:---|
| 실행 범위 | RPA: 정해진 규칙 기반 반복 | LLM 추론 기반 동적 작업 분해 | 업무 변동성이 높으면 에이전트, 고정 프로세스는 RPA |
| 통합 방식 | API Gateway 중심 수동 연결 | MCP·Tool Registry 동적 연결 | 도구 수 50개 이상이면 동적 레지스트리 필요 |
| 비용 구조 | 건당 고정 비용 | 토큰·도구호출 종량제 | 작업당 평균 토큰 2,000 이상이면 비용 한도 설정 |

> 요약: 업무 변동성이 높고 도구 수가 많으면 AI 에이전트, 고정 프로세스는 RPA가 적합함.

| 리스크 | 원인 | 대응 방안 | 확인 지표 |
|:---|:---|:---|:---|
| 권한 오남용 | 도구별 권한 미분리 | RBAC·allowlist·Human Approval | 비인가 호출 건수 0건/일 |
| 비용 폭증 | 루프 폭주·대량 도구 호출 | 일일 토큰 한도 100K, 최대 루프 10회 | 작업당 비용 0.50 이내 |
| 감사 누락 | Trace ID 미연결 | OpenTelemetry 기반 단일 Trace 연결 | 감사로그 누락률 0% |

> 요약: 권한 분리·비용 한도·감사 연결이 에이전트 운영의 3대 리스크 통제축임.

| 점검 항목 | 목표 기준 | 측정 방법 |
|:---|:---|:---|
| 작업 성공률 | 95% 이상 | 완료/시도 비율, 일별 집계 |
| 도구 호출 지연 | p95 ≤ 500ms | OpenTelemetry span 분석 |
| 정책 위반률 | 0건/주 | 감사로그 필터링·알림 |

> 요약: 성공률·지연·위반률 3개 지표로 에이전트 운영 건전성을 판단함.

---

## Ⅵ. 실무 적용 및 결론

**적용 방안 3개:**
1. 도구 허용목록·RBAC·mTLS를 적용하고 고위험 작업은 Human Approval 단계로 분기
2. 호출당 비용, 일일 토큰 한도, p95 지연, 성공률을 OpenTelemetry로 수집
3. 입력·계획·도구호출·출력·승인자를 단일 Trace ID로 묶어 감사로그 보관

**결론 (2줄):**
- 기술사 판단: 사내 조회형 업무는 자율 실행형, 결제·권한변경 업무는 승인 대기형 에이전트로 이원화 설계함.
- 향후 방향: MCP 기반 도구 표준화와 LLMOps 체계를 결합하여 전사적 업무 오케스트레이션 계층으로 확장됨.
