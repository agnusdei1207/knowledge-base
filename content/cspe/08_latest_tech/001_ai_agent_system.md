# 📖 【암기용】 개념 완전 이해

## 한눈에
- **개요**: **AI 에이전트 시스템**은 **LLM**(대형 언어모델)을 두뇌로 삼아, 목표를 계획으로 쪼개고 **도구**(API·DB·코드)를 호출해 실제 업무를 완수하는 소프트웨어 아키텍처다.
- **왜 필요한가**: 챗봇·RAG는 "말·답변"까지만 만들고 멈추지만, 실무는 조회 → 계산 → 시스템 변경 → 기록까지 "행동"이 필요하다. 이 행동을 안전하게 오케스트레이션하는 계층이 필요해서 등장했다.
- **핵심 직관**: LLM은 두뇌, 도구는 손발, 메모리는 업무 수첩, 정책 엔진은 사내 규정이다. 이 넷을 하나의 반복 루프로 묶은 것이 에이전트 시스템이다.

## 핵심 용어 정리 (내부에 등장하는 것들)
아래 용어들은 답안 본문에 그대로 등장하므로, 처음 보는 사람도 이해하도록 비유와 함께 먼저 정리한다.

| 용어/표기 | 의미 | 비유·예 |
|:---|:---|:---|
| AI 에이전트 시스템(핵심) | LLM 추론 + 도구 실행 + 메모리 + 정책을 묶은 업무 수행 아키텍처 | "지시하면 스스로 일 처리하는 신입 직원 + 사내 시스템 권한" |
| LLM(대형 언어모델) | 방대한 텍스트로 학습해 언어를 이해·생성하는 신경망. 에이전트의 추론 엔진 | 판단을 내리는 "두뇌" |
| 에이전트(Agent) | 목표를 받아 스스로 행동을 선택·실행하는 자율 개체 | 심부름을 알아서 하는 "대리인" |
| 오케스트레이터(Orchestrator) | 계획·추론·도구·메모리 호출 순서를 조율하는 제어 루프 | 여러 악기를 지휘하는 "지휘자" |
| 플래닝(Planning) | 큰 목표를 실행 가능한 하위 단계로 분해하는 과정 | 요리 전에 "레시피 순서 짜기" |
| 툴 콜링(Tool Calling)/도구 호출 | LLM이 정해진 형식(JSON)으로 외부 함수·API를 부르는 동작 | 두뇌가 "손에 내리는 명령" |
| 툴 레지스트리(Tool Registry) | 에이전트가 쓸 수 있는 도구 목록·명세·권한을 등록·관리하는 저장소 | 쓸 수 있는 "연장통 목록" |
| 메모리(Memory) | 대화·업무 상태를 저장하는 공간. 단기(현재 세션)·장기(누적 지식)로 구분 | 진행 중 업무를 적는 "수첩" |
| 정책 엔진(Policy Engine)/가드레일 | 권한·비용·금지행위를 실행 전에 검사·차단하는 통제 계층 | 결제 전 "승인 규정·한도 체크" |
| RBAC | 역할 기반 접근통제. 도구·데이터 권한을 역할 단위로 부여 | 직급별 "출입증 등급" |
| 감사로그(Audit Log) | 누가·언제·무슨 도구를·왜 호출했는지 남기는 추적 기록 | CCTV·"출입 기록부" |
| Human-in-the-Loop(HITL) | 고위험 행동 직전 사람이 승인·개입하는 지점 | 큰 계약 전 "상사 결재" |
| MCP(Model Context Protocol) | 에이전트-도구/데이터를 표준 규격으로 연결하는 개방형 프로토콜 | 도구용 "USB-C 표준 단자" |
| 관측성(Observability) | 지연·비용·성공률·오류를 추적 가능한 상태로 만드는 것 | 계기판이 달린 "대시보드" |

## 깊이 이해
- **배경·문제의식**: 생성형 AI 도입 초기에는 "질문하면 문장으로 답하는" 수준이었다. 그러나 기업 현장 요구는 "장애 티켓 생성", "재고 DB 조회 후 발주", "코드 실행·배포"처럼 시스템을 실제로 움직이는 것이다. RAG는 지식을 검색해 답의 정확도를 높일 뿐 행위 수행 능력은 없다. 그래서 LLM에 "손발(도구)"과 "규정(정책)"을 붙여 행동까지 완결시키는 시스템이 필요해졌다.
- **작동 원리(어떻게+왜)**: 오케스트레이터가 ① 목표를 Planner로 하위 단계로 분해하고 ② LLM이 각 단계에서 어떤 도구를 어떤 입력으로 부를지 판단하며 ③ Tool Executor가 실제 호출하고 ④ 그 결과(Observation)를 메모리에 반영해 다음 판단의 입력으로 되돌린다. 이 "판단→행동→관찰"의 폐루프 덕분에 한 번의 프롬프트로 안 되는 다단계 업무를 단계적으로 완수한다. 도구 호출마다 정책 엔진을 통과시키는 이유는, LLM의 자율 판단이 잘못돼도 권한·비용·금지행위 선에서 막기 위함이다.
- **비유**: 신입 직원에게 "이 업무 처리해줘"라고 목표만 준 뒤, 사내 시스템 권한(도구)·업무 매뉴얼(정책)·업무 수첩(메모리)을 쥐여주고, 단계마다 결과를 확인하며 다음 일을 시키는 구조다. 결재가 필요한 큰일은 상사 승인(HITL)을 거친다.
- **구체 예시(실제 프레임워크·사례)**: LangChain·LangGraph는 도구·상태·분기를 그래프로 구성하고, AutoGPT는 목표를 스스로 하위 작업으로 쪼개 반복 실행하며, Anthropic MCP는 에이전트-도구 연결을 표준화한다. 예: 장애 분석 에이전트가 로그 검색 → 원인 후보 3개 산출 → Runbook 조회 → Jira 티켓 생성까지 자동 수행한다.
- **흔한 오해·주의점**: "에이전트 = 더 똑똑한 챗봇"이 아니다. 챗봇은 틀리면 오답으로 끝나지만, 에이전트는 틀린 판단이 실제 시스템 변경·과금·데이터 삭제로 이어질 수 있다. 자율 실행 범위가 넓어질수록 권한 오남용·도구 비용 폭증·감사 누락 위험이 함께 커진다.

> 1. **본질**: AI 에이전트 시스템은 LLM 추론을 계획·도구호출·관찰·메모리·정책과 하나의 폐루프로 묶은 업무 수행 아키텍처임.
> 2. **가치**: 단순 질의응답을 조회-분석-실행-기록의 완결형 업무 단위로 확장함.
> 3. **판단 포인트**: 자율성 확대보다 권한 경계·감사로그·비용 한도·실패 복구를 먼저 설계해야 함.

## Ⅰ. 개요 및 필요성

- 개요: LLM 추론과 도구 호출을 폐루프로 결합한 업무 수행 아키텍처임
- 배경: 챗봇·RAG는 답변 생성까지만 수행하고 시스템 변경·기록 등 실제 행위는 못함
- 필요성: 조회·분석·실행·기록을 한 흐름으로 묶되 권한·비용·감사 통제를 내장해야 함
- 위치: 에이전틱 AI(002)의 자율성 패러다임을 구현하는 시스템 계층에 해당함

---

## Ⅱ. 구조 및 구성요소

- 선형 구조도

```text
사용자 목표 -> Orchestrator -> Planner(단계 분해) -> LLM Reasoner(도구 선택)
  -> Tool Executor(API·DB·코드 실행) -> Observation(결과 관찰)
  -> Memory(상태 저장) / Policy Engine(권한·비용 검사) -> 재계획 또는 완료
```

| 구성요소 | 역할 | 특이사항 |
|:---|:---|:---|
| Orchestrator | 계획·추론·도구·메모리 호출 순서 조율 | 루프 상태·종료조건 관리 |
| Planner | 목표를 하위 작업으로 분해 | 단계 수·의존관계·완료조건 정의 |
| LLM Reasoner | 다음 도구·입력 파라미터 판단 | JSON Schema 기반 툴 콜링 |
| Tool Executor | API·DB·검색·코드 실행 | RBAC·allowlist 적용 |
| Memory | 단기·장기 상태 저장 | 개인정보 TTL·KMS 암호화 |
| Policy Engine | 권한·비용·금지행위 통제 | 고위험 작업 HITL 분기 |

> 요약: 계획-추론-도구실행-관찰-메모리-정책의 폐루프가 에이전트 시스템의 골격임.

---

## Ⅲ. 동작원리 및 흐름도

- 선형 흐름도

```text
목표 입력 -> 계획 생성 -> 도구 선택/정책 검사 -> 실행·관찰 -> 결과 평가 -> 재계획 또는 종료
```

1. 목표·제약 수집: 업무 범위, 권한 등급, 비용 한도, 금지 작업 확정
2. 계획 생성: 하위 단계·의존관계·완료조건 정의, 필요한 도구 식별
3. 도구 호출·관찰: 정책 통과 후 실행, 응답코드·p95 지연·오류 확인
4. 결과 검증·기록: 완료조건 충족 시 종료, 근거·로그ID·승인이력을 단일 Trace로 보관

> 요약: 도구 호출마다 정책 검사를 거치고, 관찰 결과가 다음 계획의 입력이 됨.

---

## Ⅳ. 특징

- 실행 능력: 답변 생성을 넘어 API·DB·코드로 시스템을 실제로 변경함
- 동적 도구 연동: MCP·Tool Registry로 도구를 정적 배선 없이 런타임에 선택함
- 상태 보존: 단기·장기 메모리로 다단계 업무의 문맥·진행 상태를 유지함
- 통제 필수성: 실행 권한을 얻는 대신 RBAC·비용 한도·감사로그가 설계 필수축이 됨
- 관측 가능성: 지연·비용·성공률·정책 위반을 단일 Trace로 추적해야 운영이 가능함

## Ⅴ. 심화 비교 및 적용 판단

- 프로세스 자동화 관점에서 규칙 기반 RPA·BPM 엔진과 대비함

| 구분 | RPA | BPM 워크플로우 엔진 | AI 에이전트 시스템 |
|:---|:---|:---|:---|
| 실행 논리 | 화면·규칙 기반 고정 반복 | 사전 정의 프로세스 흐름 | LLM 추론 기반 동적 단계 분해 |
| 변동 대응 | 규칙 변경 시 재개발 | 프로세스 재모델링 | 목표 재해석으로 자율 대응 |
| 통합 방식 | UI 스크래핑·커넥터 | 정적 API 연동 | MCP·Tool Registry 동적 호출 |
| 리스크 | 화면 변경 시 중단 | 경직된 예외 처리 | 권한 오남용·비용 폭증 |

> 요약: 업무 변동성이 크고 도구가 많으면 에이전트, 고정·정형 프로세스는 RPA·BPM이 적합함.

- 주요 리스크와 대응(불릿)
  - 권한 오남용: 도구별 권한 미분리가 원인 → RBAC·allowlist·HITL 승인으로 통제
  - 비용 폭증: 루프 폭주·대량 호출이 원인 → 일일 토큰 한도·최대 루프 10회 제한
  - 감사 누락: Trace ID 미연결이 원인 → OpenTelemetry 단일 Trace로 입력~승인 연결

- 운영 건전성 지표(불릿)
  - 작업 성공률 95% 이상(완료/시도 비율)
  - 도구 호출 p95 500ms 이하(Trace span 분석)
  - 정책 위반 0건/주(감사로그 필터·알림)

## Ⅵ. 실무 적용 및 결론

- 적용 방안
  1. LangGraph로 상태·분기를 그래프화하고 도구는 MCP로 표준 연결, 고위험 작업은 HITL로 분기
  2. RBAC·allowlist·mTLS로 도구 권한을 격리하고 일일 토큰·루프 한도를 정책 엔진에 강제
  3. 입력·계획·도구호출·출력·승인자를 단일 Trace ID로 묶어 감사로그로 보관
- 결론
  - 기술사 판단: 조회형 업무는 자율 실행형, 결제·권한변경 업무는 승인 대기형으로 이원화 설계함
  - 향후 방향: MCP 도구 표준화와 LLMOps를 결합해 전사 업무 오케스트레이션 계층으로 확장됨
