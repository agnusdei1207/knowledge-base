# 📖 【암기용】 개념 완전 이해

## 한눈에
- **개요**: **MCP 리소스**(MCP Resource)는 MCP 서버가 노출하는 3대 프리미티브 중 **읽기 전용 컨텍스트 데이터**이다(파일·로그·DB 레코드 등).
- **왜 필요한가**: AI가 답하려면 근거 자료가 필요하다. 리소스는 데이터가 어디 있든 주소(URI)만 알면 모델이 표준 방식으로 읽어오게 한다.
- **핵심 직관**: 도서관 자료. AI는 도서관(서버)에서 책(리소스)을 대출(Read)해 내용을 확인하고 지식을 보충한다. 책을 "고쳐 쓰는" 것은 리소스가 아니라 툴의 몫이다.

## 핵심 용어 정리 (내부에 등장하는 것들)
답안 본문에 등장하는 용어를 처음 보는 사람도 이해하도록 비유와 함께 먼저 정리한다.

| 용어/표기 | 의미 | 비유·예 |
|:---|:---|:---|
| MCP 리소스(핵심) | 서버가 노출하는 읽기 전용 컨텍스트 데이터 | 대출하는 "책" |
| 3대 프리미티브 | 툴(실행)·리소스(읽기)·프롬프트(템플릿) | 기능 버튼/자료/서식 |
| URI | 리소스를 식별하는 고유 주소 `mcp://server/path` | 자료의 "청구기호" |
| List / Read | 목록 조회 / 본문 읽기 두 요청 | 목록 훑기 / 대출 |
| MIME 타입 | 데이터 형식 규격 (text/plain, application/json) | 자료의 "형태 표시" |
| 리소스 템플릿 | 변수를 포함한 동적 URI 패턴 `mcp://logs/{date}` | 빈칸 채우는 청구서 |
| Subscription(구독) | 데이터가 바뀌면 클라이언트에 알리는 기능 | 신간 알림 |
| 읽기 전용 | 서버 상태를 바꾸지 않는 성질 (부작용 없음) | 열람만 가능 |
| Blob | Base64로 실어 보내는 바이너리 콘텐츠 | 사진·PDF 원본 |
| ACL | 리소스별 접근 권한 목록 | 열람 자격 명단 |

## 깊이 이해
- **배경·문제의식**: MCP 전체 구조는 006, 서버·클라이언트는 007·008에서 다룬다. 리소스 관점의 문제는 "모델에 데이터를 한꺼번에 다 주면(Context Overflow) 낭비이고, 매번 RAG 검색 로직을 짜면 무겁다"는 것이다. 주소만 알면 모델이 필요할 때 직접 읽는 표준이 필요했다.
- **작동 원리(어떻게+왜)**: 모든 리소스는 `mcp://server/path` 형태의 고유 URI를 가진다. 서버는 목록(List)과 본문(Read), 형식을 알리는 MIME 타입을 제공한다. 모델이 URI를 지정해 Read하면 서버가 권한을 확인하고 본문(텍스트 또는 Base64 Blob)을 반환한다. 읽기 전용이라 부작용이 없어 자유롭게 참조해도 안전하다.
- **비유**: 웹페이지 URL. 주소창에 URL을 치고 내용을 보듯, AI는 URI로 데이터 전문을 가져와 읽는다. 다만 페이지를 "수정"하려면 URL이 아니라 별도 동작(툴)이 필요하다.
- **구체 예시(실제 사례)**: 로그 감시 서버가 실시간 에러 로그를 `mcp://logs/error_latest` 리소스로 제공하면, AI가 이를 읽어 장애 원인을 분석한다. `mcp://logs/{date}` 템플릿으로 날짜별 로그를 정밀 인출할 수도 있다.
- **흔한 오해·주의점**: 리소스는 읽기 전용이다. 데이터 수정·서버 상태 변경은 반드시 툴(Tool)로 해야 한다. 리소스로 부작용을 일으키려는 설계는 프리미티브 오용이다. 또한 대용량·기밀 데이터는 페이징·ACL·마스킹으로 통제해야 한다.

## 연결 개념
- MCP 서버(007) — 리소스를 노출·통제하는 제공자
- MCP 툴·프롬프트 — 리소스와 함께 노출되는 나머지 두 프리미티브
- RAG(관련 기법) — 리소스가 보완하는 능동적 데이터 참조 방식

# 📝 【답안용】 시험 답안 템플릿

## 핵심 인사이트 (3줄 요약)

> 1. **본질**: MCP 리소스는 URI로 식별되고 모델이 필요시 참조하는 읽기 전용 컨텍스트 데이터임.
> 2. **가치**: 필요한 데이터만 적시에 주입(Just-in-Time)해 토큰 효율과 답변 최신성을 확보함.
> 3. **판단 포인트**: URI 스키마·MIME 최적화·대용량 요약·민감정보 필터링 설계가 필수적임.

## 출제 의도 및 답안 포인트

| 출제 의도 | 반드시 짚을 핵심 | 감점 회피 포인트 |
|:---|:---|:---|
| 데이터 제공 메커니즘 이해 | URI 체계, List/Read, MIME, Subscription | 실행 툴(Tool)과 혼동 기술 시 감점 |
| RAG와의 관계·차이 | 능동적 URI 참조, 실시간성, 명시적 지칭 | 단순 정적 파일 공유로 한정 시 감점 |
| 데이터 거버넌스 | 읽기 권한 제어(ACL), 마스킹, 접근 감사 | 무제한 공개 강조 시 감점 |

> 요약: URI 기반 표준 참조 구조와 이를 통한 지식 확장·보안 통제를 확인하려는 문제임.

## Ⅰ. 개요 및 필요성

- 개요: 서버의 파일·DB·상태를 모델이 식별·읽도록 표준 주소·형식으로 노출한 읽기 전용 데이터 자원임
- 배경: 비정형(로그·코드)·정형(DB) 데이터 혼재로 주입 방식이 파편화되고 컨텍스트가 낭비됨 (전체 구조는 006·007 참조)
- 필요성: 모델이 필요 시점에 스스로 인출하는 능동적 RAG를 구현하고 최신성·전송 효율을 확보해야 함
- 위치: 서버(007)가 노출하는 3대 프리미티브 중 부작용 없는 읽기 계열임

---

## Ⅱ. 구조 및 구성요소

- 선형 구조도

```text
mcp://[서버명]/[리소스 경로]
  스키마 mcp:// -> 식별자(서버) -> 계층 경로
    -> MIME 타입(text/md, application/json)
    -> 콘텐츠(String 또는 Base64 Blob)
  변경 시 -> Subscription 알림
```

| 구성요소 | 역할 | 특이사항 |
|:---|:---|:---|
| URI | 리소스 식별 고유 주소 | mcp:// 스키마 계층 구조 |
| 리소스 메타데이터 | 형식·속성 설명 | MIME, Name, Description |
| 리소스 템플릿 | 동적 URI 생성 패턴 | `mcp://logs/{date}` 변수화 |
| 콘텐츠 | 실제 전달 값 | UTF-8 텍스트 또는 Base64 Blob |
| Subscription | 변경 시 알림 송신 | 실시간 동기화 |

> 요약: URI로 리소스를 식별하고, 메타데이터·콘텐츠가 결합돼 모델용 형식으로 전달되며 변경은 구독으로 알림.

---

## Ⅲ. 동작원리 및 흐름도

- 선형 흐름도

```text
List Resources -> 목록 수신 -> 모델이 데이터 필요 판단 -> Read(URI) 요청 -> 권한 확인 -> 본문 반환 -> 컨텍스트 주입
```

1. 발견: 클라이언트가 서버의 정적 리소스·템플릿 목록을 획득함
2. 판단: 모델이 질문 해결에 특정 URI 내용이 필요함을 결정함
3. 읽기: 클라이언트가 URI로 Read를 요청하고, 서버가 존재·읽기 권한을 확인함
4. 주입: 반환된 데이터를 모델 입력 프롬프트에 포함해 추론을 완료함

> 요약: 발견된 목록 중 필요한 URI를 모델이 고르고, 서버가 권한 확인 후 본문을 근거로 제공함.

---

## Ⅳ. 특징

- 읽기 전용: 서버 상태를 바꾸지 않아 부작용 없이 자유롭게 참조 가능함
- 명시적 지칭: 유사도 검색이 아니라 URI로 정확한 데이터를 직접 가리킴
- 실시간성: 인덱싱 지연 없이 원천의 최신(Live) 데이터에 접근함
- 적시 주입: 필요한 데이터만 Just-in-Time으로 넣어 컨텍스트 낭비를 줄임
- 서버 통제: 접근 권한(ACL)을 서버가 직접 관리해 세밀한 거버넌스가 가능함

---

## Ⅴ. 심화 비교 및 적용 판단

- 리소스의 성격은 나머지 두 프리미티브(툴·프롬프트)와 대비할 때 가장 분명함

| 구분 | 리소스(Resource) | 툴(Tool) | 프롬프트(Prompt) |
|:---|:---|:---|:---|
| 목적 | 읽기용 컨텍스트 데이터 | 실행용 함수·동작 | 재사용 작업 템플릿 |
| 부작용 | 없음(상태 불변) | 있음(상태 변경) | 없음(생성만) |
| 제어 주체 | 모델·클라이언트가 읽기 선택 | 모델이 호출 결정 | 사용자·앱이 선택 적용 |
| 식별 | URI | 이름·JSON Schema | 이름·인자 |
| 승인 필요 | 낮음(읽기) | 높음(고위험 시 HITL) | 낮음 |

> 요약: 부작용 유무가 핵심 축으로, 리소스는 읽기·불변, 툴은 실행·변경, 프롬프트는 템플릿 제공으로 갈림.

- 정적 vs 동적(템플릿) 리소스 선택
  - 정적(Static) — 고정 경로(config·매뉴얼), List Resources로 즉시 확인
  - 동적(Template) — 변수 경로(`logs/{id}`), List Resource Templates로 확인, 정밀 인출용

- 주요 리스크와 대응(불릿)
  - 대용량 과부하 — 수백 MB 로그를 한 번에 읽음이 원인 → 페이징·최대 크기 제한·요약 후 반환
  - 기밀 노출 — 미인가자의 URI 추측 호출이 원인 → 서버 ACL 강화
  - 해석 오류 — 모델이 이해 못 할 포맷 제공이 원인 → Markdown·JSON 정제 변환

- 운영 지표(불릿)
  - 최신성(Freshness) — 반영 지연 1s 이내 목표 — 서버-백엔드 동기화 지연 측정
  - 토큰 효율 — 유효 정보 80% 이상 목표 — 토큰 내 유효 비중 분석
  - 마스킹 적용 — 민감 필드 100% 목표 — DLP 감사·패턴 매칭

---

## Ⅵ. 실무 적용 및 결론

- 적용 방안
  1. 실시간 모니터링: 장애 시 모델이 `mcp://monitoring/events`를 읽어 발생 시점 스택 트레이스를 자동 분석
  2. 지식 그래프 통합: 리소스 URI 체계를 지식 그래프 노드 ID와 매핑해 복합 관계 데이터를 정밀 인출
  3. 계층적 보안: 일반 리소스는 익명 접근, 민감 리소스(인사·재무)는 사용자 토큰 기반 읽기 권한 검증
- 결론
  - 기술사 판단: 실시간·정형 데이터는 리소스로 명시 참조하고, 상태 변경이 필요하면 반드시 툴로 분리함
  - 향후 방향: 리소스 변화를 실시간 스트리밍해 모델이 즉각 반응하는 반응형 에이전트로 진화함
