# 📖 【암기용】 개념 완전 이해

> 목적: MCP 리소스(MCP Resource)를 처음 봐도 완벽히 이해하게 만든다. 시험 답안 양식이 아니라, 이해를 위한 친절한 설명이다.

## 한눈에
- **개요**: MCP 서버가 AI에게 제공하는 "읽기 전용 데이터" (파일, 로그, DB 레코드 등)
- **왜 필요한가**: AI가 답변을 하려면 근거 자료가 필요하다. MCP 리소스를 통해 AI가 필요한 시점에 특정 파일이나 최신 데이터를 표준 방식으로 읽어올 수 있게 한다.
- **핵심 직관**: AI 전용 "도서관 자료". AI는 도서관(Server)에서 책(Resource)을 대출(Read)해서 내용을 확인하고 지식을 보충한다.

## 깊이 이해
- **배경·문제의식**: 기존에는 AI에게 데이터를 줄 때 한꺼번에 다 주거나(Context Overflow), 복잡한 검색 로직(RAG)을 따로 짜야 했다. 데이터가 어디에 있든 주소(URI)만 알면 모델이 직접 읽을 수 있는 표준이 필요했다.
- **작동 원리**: 모든 리소스는 `mcp://server/path/to/data`와 같은 고유한 주소(URI)를 갖는다. 서버는 리소스의 목록과 상세 내용, 그리고 형식을 설명하는 MIME 타입(text/plain, application/json 등)을 제공한다.
- **비유**: 웹페이지의 URL. 우리가 주소창에 URL을 치고 페이지 내용을 보듯, AI는 URI를 통해 필요한 데이터의 전문을 가져와 읽는다.
- **구체 예시**: "로그 감시 MCP 서버"가 서버의 실시간 에러 로그를 `mcp://logs/error_latest` 리소스로 제공하면, AI가 이 리소스를 읽어 장애 원인을 분석할 수 있다.
- **흔한 오해·주의점**: 리소스는 기본적으로 "읽기 전용"이다. 데이터를 수정하거나 서버의 상태를 바꾸는 행위는 리소스가 아니라 도구(Tool)를 통해 이루어져야 한다.

## 연결 개념
- MCP URI — 리소스를 식별하는 고유 주소 체계
- MIME Type — 리소스 데이터의 형식을 정의하는 규격 (JSON, Markdown 등)
- Subscription — 리소스의 내용이 바뀔 때 클라이언트에게 알려주는 구독 기능

# 📝 【답안용】 시험 답안 템플릿

> 목적: 시험장에서 25분에 그대로 쓰는 답안 양식. 작성방식(추상표현 금지·수치·도식·문제유형 전환)을 엄격히 지킨다.
> 핵심: MCP 리소스는 AI 에이전트의 지식 근거를 표준화된 방식으로 확장하며, 정적/동적 데이터를 모델의 컨텍스트에 효율적으로 주입하는 핵심 자원이다.

## 핵심 인사이트 (3줄 요약)

> 1. **본질**: MCP 리소스는 URI(Uniform Resource Identifier)를 통해 식별되고 모델이 필요시 참조할 수 있는 읽기 전용 컨텍스트 데이터이다.
> 2. **가치**: 모델에게 필요한 최소한의 데이터만 적시에 주입(Just-in-Time Context)하여 토큰 효율성을 높이고 답변의 최신성(Freshness)을 확보한다.
> 3. **판단 포인트**: 리소스 설계 시 URI 스키마 설계, 데이터 포맷(MIME) 최적화, 대용량 데이터의 요약 전략 및 민감 정보 필터링이 중요하다.

## 출제 의도 및 답안 포인트

| 출제 의도 | 반드시 짚을 핵심 | 감점 회피 포인트 |
|:---|:---|:---|
| MCP 리소스의 데이터 제공 메커니즘 이해 | URI 체계, List/Read 요청, MIME 타입, Subscription | 리소스를 실행 가능한 도구(Tool)와 혼동하여 기술 |
| RAG 아키텍처와의 연관성 및 차이점 | 동적 데이터 참조, 지식 확장성, 모델의 능동적 읽기 | 단순한 정적 파일 공유로만 한정하여 기술 |
| 정보 보안 및 데이터 거버넌스 관리 | 읽기 권한 제어, 데이터 마스킹, 접근 이력 감사 | 모든 데이터의 무제한 공개 강조(기밀 유출 위험 방치) |

> 요약: URI 기반의 표준화된 데이터 참조 구조와 이를 통한 모델의 지식 확장 및 보안 통제 방안을 기술한다.

---

## Ⅰ. 개요 및 필요성

- 정의: MCP 서버에 존재하는 파일, DB, 시스템 상태 등을 모델이 식별하고 읽을 수 있도록 표준화된 주소와 형식으로 노출한 데이터 자원
- 배경: 비정형 데이터(로그, 코드)와 정형 데이터(DB)의 혼재로 인한 모델 주입 방식의 파편화 및 컨텍스트 윈도우 낭비 문제 해결 필요
- 필요성: 모델이 필요한 시점에 스스로 데이터를 인출하는 능동적 RAG 구현, 데이터 최신성 유지 및 전송 효율 극대화

---

## Ⅱ. 구조 및 구성요소

```text
[MCP 리소스 식별 및 참조 구조]
mcp://[Server Name]/[Resource Path]
  |         |               |
[Schema] [Identifier]    [Hierarchy] -> MIME Type (text/md, application/json)
                                     -> Contents (String or Blob)
```

| 구성요소 | 역할 | 주요 사양 |
|:---|:---|:---|
| URI (Uniform Resource Id) | 리소스를 식별하는 고유 주소 | mcp:// 스키마 기반 계층 구조 |
| Resource Metadata | 데이터의 형식 및 속성 설명 | MIME Type, Name, Description |
| Resource Template | 동적 URI 생성을 위한 패턴 | `mcp://logs/{date}` 형태의 변수화 |
| Contents | 실제 모델에게 전달되는 값 | UTF-8 텍스트 또는 Base64 바이너리 |
| Subscriptions | 데이터 변경 시 알림 송신 | 실시간 데이터 동기화 기능 |

> 요약: URI를 통해 리소스를 식별하며, 메타데이터와 실제 콘텐츠가 결합되어 모델에게 최적화된 형식으로 전달된다.

## Ⅲ. 동작원리 및 흐름도

```text
[MCP 리소스 읽기 프로세스]
Client -> List Resources -> Server Response -> LLM Needs Data -> Read Request -> Data Return -> Context Feed
(Sync)    (Discovery)        (Registry)      (Reasoning)      (URI Call)     (Payload)     (Input)
```

| 단계 | 처리 내용 | 주요 검증 지점 |
|:---:|:---|:---|
| 1 | 리소스 카탈로그 발견 | 서버가 제공하는 모든 정적 리소스 및 템플릿 목록 획득 |
| 2 | 모델의 데이터 참조 결정 | 질문 해결을 위해 특정 리소스(URI)의 내용이 필요함을 모델이 판단 |
| 3 | 리소스 본문 읽기 요청 | URI 기반 호출, 서버 측에서 해당 데이터의 존재 및 읽기 권한 확인 |
| 4 | 컨텍스트 주입 및 답변 | 획득한 데이터를 모델의 입력 프롬프트에 포함하여 추론 완료 |

> 요약: 발견된 목록 중 필요한 주소를 모델이 선택하고, 클라이언트가 본문을 요청하여 추론 근거로 활용한다.

## Ⅳ. 특징

| 구분 | MCP 리소스 | 기존 RAG (Vector DB) | 기술사 판단 포인트 |
|:---|:---|:---|:---|
| 데이터 성격 | 구조화/시스템 데이터 중심 | 비정형 문서/지식 중심 | 데이터 원천(Source)에 따른 선택 |
| 참조 방식 | 명시적 URI 기반 호출 | 유사도(Similarity) 기반 검색 | 데이터의 정확한 지칭 가능 여부 |
| 최신성 | 실시간(Live) 데이터 접근 | 인덱싱 지연 존재 (Batch) | 실시간성 요구 업무에 MCP 우위 |
| 통제권 | 서버가 접근 권한 직접 관리 | 검색 엔진 보안 설정에 의존 | 세밀한 데이터 거버넌스 구현 |

> 요약: MCP 리소스는 URI를 통한 명시적이고 실시간적인 데이터 참조를 제공하여 기존 RAG를 보완한다.

## Ⅴ. 심화 비교 및 적용 판단

| 구분 | 정적 리소스 (Static) | 동적 리소스 (Template) | 선택 기준 |
|:---|:---|:---|:---|
| 정의 | 고정된 경로의 데이터 (config 등) | 변수를 포함한 경로 (log/{id} 등) | 데이터의 가변성 및 규모 |
| 발견 방식 | List Resources로 즉시 확인 | List Resource Templates로 확인 | 경로 미리 알기 가능 여부 |
| 주 용도 | 매뉴얼, 설정값, 고정 지식 | 개별 로그, 특정 DB 레코드, 파일 | 데이터 인출의 정밀도 |

> 요약: 고정된 지식은 정적으로, 파라미터 기반의 정밀 인출은 템플릿 기반 리소스로 설계한다.

| 리스크 | 원인 | 대응 방안 | 확인 지표 |
|:---|:---|:---|:---|
| 대용량 데이터 과부하 | 수백 MB의 로그 등을 한 번에 읽기 | 페이징(Paging), 최대 크기 제한, 요약 후 반환 | 리소스 호출 당 평균 데이터 크기 |
| 기밀 데이터 노출 | 미인가 사용자의 URI 추측 호출 | 서버 측 ACL(Access Control List) 강화 | 비인가 리소스 접근 차단율 (100%) |
| 데이터 해석 오류 | 모델이 이해하기 어려운 포맷 제공 | 텍스트 기반 Markdown/JSON 변환 정제 | 모델의 리소스 활용 성공률 |

> 요약: 용량 제한, 접근 제어, 데이터 정제를 통해 리소스 제공의 안전성과 효율성을 확보한다.

| 점검 항목 | 목표 기준 | 측정 방법 |
|:---|:---|:---|
| 가용성 (Freshness) | 실시간 데이터 반영 지연 1s 이내 | 서버-백엔드 간 동기화 지연 측정 |
| 효율성 (Token Efficiency) | 필요 데이터의 80% 이상이 정제된 형태 | 토큰 내 유효 정보 비중 분석 |
| 보안 (Governance) | 민감 필드 마스킹 적용률 100% | DLP 감사 로그, 개인정보 패턴 매칭 |

> 요약: 최신성, 토큰 효율성, 보안 준수율을 지표로 리소스 서비스의 품질을 관리한다.

## Ⅵ. 실무 적용 및 결론

**적용 방안 3개:**
1. 실시간 모니터링: 장애 발생 시 모델이 `mcp://monitoring/events`를 읽어 발생 시점의 스택 트레이스 자동 분석
2. 지식 그래프 통합: 리소스 URI 체계를 지식 그래프의 노드 ID와 매핑하여 복합 관계 데이터의 정밀 인출 구현
3. 계층적 보안 적용: 일반 리소스는 익명 접근, 민감 리소스(인사/재무)는 개별 사용자 토큰 기반 읽기 권한 검증

**결론 (2줄):**
- 기술사 판단: MCP 리소스는 AI가 "아는 것"과 "찾아보는 것"의 경계를 허무는 기술이며, 데이터의 최소 노출 원칙이 설계의 핵심이다.
- 향후 방향: 리소스의 변화를 실시간으로 스트리밍하여 모델이 즉각 반응하는 '반응형 에이전트(Reactive Agent)'로 진화할 전망이다.
