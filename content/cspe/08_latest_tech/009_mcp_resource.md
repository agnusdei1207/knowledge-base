# 📖 【암기용】 개념 완전 이해

## 한눈에
- **개요**: **MCP 리소스**는 AI 모델이 읽고 참고할 수 있도록 MCP 서버가 제공하는 **정적 또는 동적 데이터**이다. 파일 내용, 데이터베이스 레코드, API 응답 등이 리소스에 해당한다.
- **필요성**: 모델에게 어떤 정보가 필요할 때마다 매번 "도구"를 실행하는 것은 비효율적이다. 리소스는 모델의 컨텍스트 윈도우에 직접 주입될 수 있는 배경 지식(Background Knowledge)을 표준화된 방식으로 제공한다.
- **핵심 직관**: **"AI를 위한 전용 도서관의 책"**. 모델이 필요할 때 꺼내 볼 수 있는 데이터의 뭉치이며, 각각 고유한 주소(URI)를 가진다.

## 깊이 이해
- **배경 (Standardized Context Injection)**: 이전에는 RAG 시스템 등에서 검색된 결과를 모델에게 전달할 때 형식이 제각각이었다. MCP 리소스는 `URI` 형식을 빌려 데이터의 위치와 종류를 정의함으로써 어떤 모델이든 일관되게 데이터를 읽을 수 있게 한다.
- **작동 원리 (Resource Anatomy)**:
    - **URI**: 각 리소스를 식별하는 고유 주소 (예: `postgres://db1/users/123`).
    - **MIME Type**: 리소스의 형식 정의 (예: `text/plain`, `application/json`).
    - **Resource Templates**: 파라미터가 포함된 동적 리소스 주소 (예: `logs://{date}/error.log`).
    - **Metadata**: 리소스의 이름, 설명 등 모델이 이를 언제 읽어야 할지 판단하는 데 도움을 주는 정보.
- **비유**: 웹 브라우저 주소창에 URL을 입력하면 페이지가 뜨는 것처럼, 에이전트가 리소스 URI를 통해 필요한 데이터 페이지를 직접 열어보는 것과 같다.
- **구체 예시**: `GitHub MCP Server`는 특정 리포지토리의 `README.md`를 리소스로 제공할 수 있다. 모델은 이 리소스를 읽어 프로젝트의 개요를 파악한다.
- **주의점**: 리소스는 기본적으로 **읽기 전용(Read-only)** 성격이 강하다. 데이터를 수정하거나 시스템 상태를 바꾸는 행위는 '툴(Tool)'의 영역이다.

## 연결 개념
- **MCP Tool (010)**: 리소스가 '정보'라면, 툴은 그 정보를 바탕으로 무언가를 수행하는 '행동'이다.
- **URI (Uniform Resource Identifier)**: 리소스를 식별하는 표준 체계.
- **RAG (101)**: 리소스는 RAG의 검색 결과물을 표준화된 방식으로 모델에 주입하는 수단이 될 수 있다.

# 📝 【답안용】 시험 답안 템플릿

## 핵심 인사이트 (3줄 요약)
> 1. **본질**: MCP 서버가 노출하는 데이터를 모델이 고유 식별자(URI)를 통해 읽고 참조할 수 있도록 구조화한 **컨텍스트 단위**.
> 2. **가치**: 파편화된 데이터 소스를 표준화된 URI 체계로 통합하여, 모델의 정보 접근성(Information Accessibility)을 극대화.
> 3. **판단 포인트**: 정적인 데이터 집합(Resources)과 동적인 함수 실행(Tools)을 명확히 구분하여 설계함으로써 모델의 추론 효율을 향상.

## 출제 의도 및 답안 포인트
- **출제 의도**: MCP의 데이터 모델인 리소스의 개념, 식별 체계(URI), 모델 컨텍스트 보강 원리 이해 여부.
- **핵심 포인트**: URI 식별자, 리소스 템플릿, MIME Type, 컨텍스트 주입.

---

## Ⅰ. MCP 리소스(MCP Resource)의 정의 및 설계 목적
### 1. MCP 리소스의 정의
- AI 모델이 추론에 필요한 배경 지식이나 실시간 데이터를 획득할 수 있도록 MCP 서버가 표준화된 URI를 통해 노출하는 데이터 개체.
### 2. 설계 목적
- **데이터 식별 표준화**: URI 체계를 활용하여 어떤 데이터 소스든 일관된 방식으로 참조.
- **컨텍스트 보강**: 모델의 지식 한계를 외부 리소스 연결을 통해 실시간으로 보완(Grounding).
- **정보 계층화**: 방대한 데이터 중 모델이 필요한 부분만 선택적으로 읽도록 지원하여 토큰 효율성 증대.

---

## Ⅱ. 리소스의 핵심 구성 요소 및 기술 규격
- **데이터 참조를 위한 메타데이터 구조**
| 구성 요소 | 상세 설명 | 기술적 예시 |
|:---:|:---|:---|
| **URI** | 리소스의 고유 주소 체계 | `file:///home/user/notes.txt` |
| **Name** | 인간 및 모델이 이해할 수 있는 리소스 명칭 | `System Logs`, `User Profile` |
| **MIME Type** | 데이터의 형식 및 인코딩 정의 | `text/markdown`, `application/pdf` |
| **Templates** | 변수를 포함한 동적 리소스 정의 체계 | `db://{table_name}/schema` |
| **Annotations** | 리소스에 대한 추가적인 제약 사항이나 설명 | `priority: high`, `auth: required` |

---

## Ⅲ. 리소스 제공 및 소비 프로세스
1. **List Resources**: 클라이언트가 서버에 현재 사용 가능한 리소스 목록을 요청.
2. **Resource Discovery**: 모델이 목록 중 현재 과업에 필요한 리소스의 URI를 식별.
3. **Read Resource**: 클라이언트가 해당 URI로 서버에 읽기 요청을 보냄.
4. **Context Injection**: 서버가 반환한 데이터를 클라이언트가 모델의 프롬프트 컨텍스트에 삽입.

---

## Ⅳ. 정적 리소스 vs 동적 리소스 (Templates)

| 구분 | 정적 리소스 (Static) | 동적 리소스 (Templates) |
|:---:|:---|:---|
| **정의** | 고정된 URI를 가지는 단일 데이터 | 파라미터에 따라 URI가 생성되는 데이터 세트 |
| **호출 예시** | `company://policy/it_security.pdf` | `weather://{city}/forecast` |
| **장점** | 구조가 단순하고 즉시 참조 가능 | 무수히 많은 데이터 개체를 패턴으로 관리 가능 |
| **사용 시점** | 불변하는 규정, 매뉴얼 등 | 특정 ID 기반 검색, 시계열 데이터 조회 등 |

---

## Ⅴ. MCP 리소스 설계 시 고려사항
- **Granularity (입도)**: 리소스 하나에 너무 많은 데이터를 담으면 컨텍스트 윈도우 초과 위험이 있으므로, 의미 있는 단위로 쪼개어 제공.
- **Searchability**: 리소스의 `Description` 필드에 모델이 언제 이 데이터를 참조해야 하는지 명확한 지침(Trigger Keywords)을 포함.
- **Security**: 민감 정보가 포함된 리소스는 클라이언트 단에서 접근 권한을 확인한 후 모델에게 전달하도록 설계.

---

## Ⅵ. 실무 관점의 결론 및 제언
- **데이터 자산의 표준화**: 기업 내 산재한 Wiki, DB, 파일 등을 MCP 리소스로 추상화함으로써 전사적 AI 지식 베이스 구축 가능.
- **결론**: 리소스는 에이전트의 **"디지털 감각 기관"** 중 시각(읽기)에 해당하며, 정확하고 정제된 리소스 설계가 에이전트 답변의 품질(Grounding)을 결정함.

### 🔀 문제 유형별 목차 전환
- **개념형**: Ⅱ. 구성 요소 및 Ⅲ. 프로세스 중심으로 기술.
- **설계형**: Ⅳ. 정적/동적 구분 및 Ⅴ. 설계 시 고려사항(입도, 보안) 강조.
