> 1. **본질**: 파이썬 주피터 노트북에서 혼자 장난치던 무거운 딥러닝 모델(LLM)을, 클라우드 환경의 고성능 GPU 서버에 올려 **동시에 접속하는 수만 명의 사용자에게 실시간 API 형태로 안정적이고 빠르게(Low Latency) 대답을 쏴주는 백엔드 인프라 아키텍처 및 소프트웨어 기술의 총체**다.

> 3. **판단 포인트**: 기존 웹 서버(Spring, Node.js) 아키텍처와 달리, 왜 GPU의 VRAM 병목(Memory Wall)을 관리해야 하는지, 단일 GPU로 안 될 때 여러 GPU로 모델을 찢어 올리는 **분산 서빙(Tensor/Pipeline Parallelism)** 아키텍처가 어떻게 동작하는지 서술해야 한다.

## Ⅰ. 개요 및 필요성
- **개요**: LLM 서빙(LLM Serving)은 학습이 완료된 거대 언어 모델 가중치(Weights)를 프로덕션(Production) 환경에 배포하고, 추론(Inference) 엔진을 통해 사용자 요청(Prompt)을 수신, 스케줄링, 연산하여 텍스트 스트리밍 결과를 반환하는 고도의 분산 시스템 엔지니어링 과정이다.
- **배경**: 과거의 머신러닝(이미지 분류 등) 서빙은 가벼웠다. 요청이 오면 0.01초 만에 CPU에서 계산하고 "이건 고양이"라고 답하면 끝이었다 (Stateless). 
- **필요성**: LLM은 달랐다. 모델 덩치만 100기가바이트(GB)가 넘어 GPU 1대에 들어가지도 않았고, 글자를 뱉어내는 수 초 동안 거대한 이전 대화 기록(KV 캐시)을 계속 램에 들고 있어야 했다 (Stateful). 일반 웹 서버(Nginx, Tomcat)로는 감당할 수 없는 엄청난 메모리 및 연산 부하를 제어할 완전히 새로운 패러다임의 '전용 AI 서빙 웹 엔진'이 필요해졌다.

## Ⅱ. 아키텍처 및 핵심 원리

```text
  [ 엔터프라이즈 LLM Serving 인프라 파이프라인 (예: vLLM, TensorRT-LLM) ]

       [ 사용자 수만 명의 동시 접속 (API Requests) ]
                   │
  ┌────────────────▼─────────────────────────────────────────────────────┐
  │ 1. [ 로드 밸런서 (Load Balancer & API Gateway) ]                        │
  │    "어느 GPU 서버가 놀고 있지? Prefix Caching이 남아있는 서버로 쏴주자!"          │
  ├──────────────────────────────────────────────────────────────────────┤
  │ 2. [ 스케줄링 및 배치 엔진 (Continuous Batching) ]                        │
  │    - 큐(Queue)에 들어온 질문 100개를 하나로 묶어서(Batch) 틈새에 끼워 넣음.     │
  ├──────────────────────────────────────────────────────────────────────┤
  │ 3. [ 메모리 풀 매니저 (PagedAttention) ]                                │
  │    - 16토큰짜리 블록 단위로 램(VRAM)을 할당하여 메모리 파편화를 막고 낭비율 0% 달성. │
  ├──────────────────────────────────────────────────────────────────────┤
  │ 4. [ 분산 추론 연산 (Tensor Parallelism) ]                               │
  │    - 모델이 140GB라서 A100(80GB) 1대에 안 들어감!                           │
  │    - ──▶ [ GPU 1 (앞부분 70GB) ] ─(초고속 통신 NVLink)─ [ GPU 2 (뒷부분) ] │
  │    - 8대의 GPU가 마치 하나의 뇌처럼 행렬을 쪼개서 병렬 연산(Compute) 수행!          │
  └────────────────────────┬─────────────────────────────────────────────┘
                           ▼
       [ 실시간 토큰 스트리밍 반환 (Server-Sent Events) ] ──▶ "안..녕..하..세..요"
```

- **1단계 [입력 및 스케줄링]**: 수많은 유저의 프롬프트가 들어오면, 서빙 엔진은 정적 배치가 아닌 **연속 배치(Continuous Batching)**를 사용하여 유저들을 토큰 단위로 실시간으로 묶고 해체하며 GPU 연산기에 끊임없이 일감을 공급한다.
- **2단계 [메모리 및 캐시 최적화]**: VRAM 병목을 뚫기 위해 앞서 배운 **PagedAttention**, **KV Cache 양자화**, **Prefix Caching** 등의 꼼수 기술을 총동원하여 수천 명의 동시 접속을 튕겨내지 않고 메모리에 꾸역꾸역 우겨넣는다.
- **3단계 [멀티 GPU 분산 서빙]**: 70B 이상의 거대 모델은 무조건 여러 대의 GPU로 쪼개야 한다.
  - **텐서 병렬화 (Tensor Parallelism, TP)**: 하나의 거대한 행렬 곱셈을 4등분 해서 GPU 4대가 동시에 쪼개서 계산하고 즉시 합치는 방식 (가장 빠름, 같은 서버 내에서만 가능).
  - **파이프라인 병렬화 (Pipeline Parallelism, PP)**: 트랜스포머 레이어 1~10층은 GPU 1이, 11~20층은 GPU 2가 맡아서 앞사람이 던져주면 뒷사람이 받아서 계산하는 공장식 컨베이어 벨트 방식 (느리지만 서버를 넘나들 수 있음).
- **4단계 [스트리밍 출력]**: 모든 글자가 다 만들어질 때까지(10초) 기다렸다가 보내면 유저가 답답해서 앱을 끈다. 글자(Token) 하나가 생성될 때마다 HTTP SSE(Server-Sent Events)나 gRPC 스트리밍 프로토콜을 통해 유저의 웹브라우저로 즉각 쏴주는 비동기 네트워크 처리를 수행한다.

## Ⅲ. 비교 일반 웹 서빙 vs LLM 서빙

| 비교 축 | 일반 웹 서빙 (Spring, Node.js) | LLM 서빙 (vLLM, TGI, Triton) |
|:---:|:---|:---|
| **상태 관리** | 기본적으로 Stateless (DB에 저장) | **Stateful (거대한 KV 캐시를 램에 강제 들고 있음)** |
| **병목 지점** | CPU 연산, DB I/O, 네트워크 대역폭 | **GPU VRAM(메모리 벽) 및 GPU 코어 연산(행렬 곱)** |
| **처리 단위** | Request (요청-응답 한 방에 끝) | **Iteration/Token (한 글자 뱉고 또 루프 도는 스트리밍)** |
| **인프라 비용** | 서버 1대당 월 수만 원 수준 | **GPU 노드 1대당 월 수천만 원 (극악의 단가)** |

> ※ **연결 포인트**: 이러한 고난도의 LLM 서빙 인프라를 바닥부터 짜는 것은 구글/MS 같은 빅테크 외엔 불가능하다. 그래서 일반 스타트업과 기업들은 오픈소스 서빙 프레임워크인 **vLLM(버클리대)**, **TGI(허깅페이스)**, **TensorRT-LLM(엔비디아)** 중 하나를 골라 도커(Docker) 컨테이너로 띄워서 인프라를 거저먹고 있다.

## Ⅳ. 실무 적용 및 기술사 판단

- **적용 사례 1 (로컬 sLLM 기반의 사내 보안 챗봇)**: 금융권 A 은행은 챗GPT(OpenAI)를 쓰면 고객 금융 정보가 미국으로 넘어가므로(보안 위반), Llama 3 8B 모델을 다운받아 사내 서버망(On-Premise)에 폐쇄형으로 서빙(Local Serving)한다. 8B 모델은 RTX 4090 1대에 쏙 들어가므로 텐서 병렬화(TP) 같은 복잡한 세팅 없이, vLLM을 띄우고 PagedAttention만 켜두면 은행원 100명의 동시 질의를 안전하게 감당할 수 있다.
- **적용 사례 2 (로라(LoRA) 어댑터 동적 서빙 - LoRAX)**: 부서가 50개면 50개의 커스텀 모델이 필요하다(인사과 봇, 재무과 봇). 이걸 GPU 50대에 각각 서빙(Serving)하면 인프라 팀이 파산한다. 최신 서빙 기술인 `LoRAX`나 `S-LoRA`를 쓰면, 베이스 모델(뇌의 뼈대)은 VRAM에 딱 1개만 올려두고, 50개의 가벼운 로라(LoRA, 뇌의 껍질) 파일만 동적으로 갈아 끼우며 서빙한다. 1대의 GPU가 50개의 다른 챗봇 역할을 미친 가성비로 동시에 수행한다.
- **기술사 판단**: 아키텍트는 서빙 엔진 도입 시 **'에지 케이스(Edge Case)로 인한 GPU 멈춤(OOM)' 방어**에 사활을 걸어야 한다. 악성 유저가 "아무 말 대잔치"를 10만 자로 길게 반복해서 쳐보내면, VRAM에 KV 캐시가 미친 듯이 쌓이다가 서버 전체가 죽어버린다(Out of Memory). 이를 막기 위해 서빙 레이어 앞에 **API Gateway를 두어 `max_tokens` 강제 제한, Rate Limiting(호출 제한), 그리고 VRAM이 95% 찼을 때 초과 유저의 캐시를 CPU 램으로 빼버리는 스왑(Swapping/Preemption) 아키텍처**를 완벽히 구성해야 무중단 서빙이 보장된다.

## Ⅴ. 기대효과 및 결론

- **기대효과**: 실험실의 장난감(Jupyter Notebook)이었던 초거대 AI 모델을, 실시간으로 수만 명이 끊김 없이 사용할 수 있는 튼튼한 '상용 서비스(Production)' 인프라로 격상시키는 소프트웨어 공학의 기적을 이뤘다.
- **향후 발전 방향**: 클라우드의 가장 비싼 GPU 자원을 낭비하지 않기 위해, 낮에는 B2C 챗봇 유저들의 실시간 트래픽을 처리하다가, 유저가 잠든 밤에는 GPU를 쉬게 하지 않고 '사내 문서 100만 건 일괄 요약' 같은 배치(Offline Batch) 작업으로 자원을 100% 쥐어짜는 **'Serverless LLM 서빙 및 하이브리드 라우팅'** 플랫폼이 백엔드의 대세로 굳어지고 있다.

### 📌 관련 개념 맵
- **텐서 병렬화 (Tensor Parallelism, TP)**: 100kg짜리 돌멩이(거대 행렬)를 1명이 들지 않고, 4명이서 25kg씩 쪼개서(행렬 분할) 동시에 들고 뛰는 멀티 GPU 기술. 같은 보드에 꽂혀서 통신 속도가 빛처럼 빠른 NVLink로 연결된 GPU들 사이에서만 가능하다.
- **서버-센트 이벤트 (Server-Sent Events, SSE)**: 한 방에 답이 나오는 게 아니라 타자 치듯 찔끔찔끔 나오는 LLM의 결과를 웹브라우저 화면에 실시간으로 뿌려주기 위해 쓰이는 단방향 네트워크 통신 프로토콜. (웹소켓보다 가볍고 편해서 LLM 스트리밍의 표준이 되었다).

### 📈 관련 키워드 및 발전 흐름도
`단일 GPU / 단순 Python 코드 서빙` $\to$ `메모리/연산 병목으로 뻗음` $\to$ `Nvidia Triton, FasterTransformer 등장` $\to$ `vLLM (PagedAttention 혁명)` $\to$ `TGI / TensorRT-LLM (엔터프라이즈 최적화 경쟁)` $\to$ `멀티 로라(Multi-LoRA) 동적 다중 서빙 체계`

### 👶 어린이를 위한 3줄 비유 설명
1. 천재 요리사(LLM)가 집에서 혼자 라면 1개 끓여 먹는 건(모델 개발) 아주 쉬워요.
2. 하지만 **'LLM 서빙'**은 이 요리사를 백화점 한가운데 데려다 놓고, **배고픈 손님 1,000명이 한꺼번에 몰려왔을 때 1초도 안 쉬고 라면 1,000그릇을 동시에 끓여서 내보내는 '거대한 공장식 식당 시스템'**을 만드는 일이에요.
3. 이를 위해서 냄비를 10개로 늘리고(분산 병렬화), 손님 빈자리가 나면 즉시 다음 손님을 채워 넣고(연속 배치), 재료를 한곳에 효율적으로 보관하는(메모리 최적화) 치열한 주방 관리의 묘기랍니다!
