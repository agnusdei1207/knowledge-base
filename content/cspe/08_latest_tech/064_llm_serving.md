## 미리 알고가기

- $LLM$ 서빙 ($LLM$ $Serving$): 초대형 학습 완료 모델을 엔터프라이즈 업무용 서비스로 상용 배포하여, 동시 접속자의 토큰 질의 요청을 안전하고 빠른 속도로 연산 반환하는 서비스 운영 계층임
- 텐서 병렬화 ($Tensor$ $Parallelism$): 하나의 모델 레이어 가중치를 여러 장의 GPU에 수평으로 분할하여 배치하고, 동시 병렬 연산 및 $All-Reduce$ 통신으로 융합하는 분산 처리 기법임
- 추론 엔진 ($Inference$ $Engine$): 서빙의 심장부로, PagedAttention이나 FlashAttention 같은 가속 알고리즘이 탑재된 가동 코어임
- 서비스 수준 협약 ($SLA$): 서비스 공급자와 수요자 간에 합의된 응답 속도, 가동율 등 품질 보증 마지노선 지표임

## Ⅰ. 개요

- **정의/개념**: LLM Serving은 수백억 개 이상의 매개변수를 지닌 대형 언어 모델을 웹 API 형태로 래핑하여 상용 배포하고, 연속 배칭 스케줄러와 가상 페이지 메모리를 동적으로 가동해 다수 사용자의 토큰 생성을 비동기 제어하는 인프라 추론 서빙 및 최적화 체계임
- **배경/필요성**: 기존 범용 웹 서비스 스택은 한 번의 연산(Stateless)으로 끝나는 반면, LLM은 매 단어마다 $KV$ 캐시를 유지하고 수백 번 순방향 연산 루프를 돌며 자원을 소모하는 독특한 상태 유지형($Stateful$) 병목이 발생하여 특화된 가속 서빙 계층이 필수 요구됨

## Ⅱ. 특징

- 사용자의 응답 체감 품질을 위해 단순히 요율이나 성공율이 아닌, 최초 반응 지연($TTFT$)과 단어 생성 속도($TPOT$)를 1밀리초 단위로 쪼개 감시함
- GPU 하드웨어의 초고가 비용 문제를 통제하기 위해, 텐서 코어의 플롭스 가동률과 VRAM 파편화율을 통제하는 시스템 소프트웨어적 최적화가 필수적임
- $vLLM$, $TensorRT-LLM$, $TGI$(Text Generation Inference) 등 전용 가속 소프트웨어 스택을 활용해 배포 생태계가 표준화되어 가고 있음

## Ⅲ. 종류 및 비교

| 판단 기준 | 일반 웹/마이크로서비스 서빙 | 범용 딥러닝 모델 서빙 (Triton 등) | LLM 전용 특화 서빙 (vLLM 등) |
|:---|:---|:---|:---|
| **상태 관리 속성** | 상태 없음 ($Stateless$) | 상태 없음 (단발 추론 위주) | 상태 깊음 ($KV$ 캐시 VRAM 점유 유지) |
| **핵심 하드웨어 병목** | CPU, 데이터베이스 I/O, 네트워크 | CPU/GPU 단순 연산 (단발성) | GPU 메모리 대역폭, 스케줄 큐 지연 |
| **기본 스케줄링 단위** | 요청 ($Request$) 단위 | 요청 ($Request$) 단위 | 단어 토큰 스텝 ($Token$ $Step$) 단위 |
| **핵심 탑재 기술** | HTTP/gRPC 로드밸런싱, 캐시 | 동적 배칭 ($Dynamic$ $Batching$) | 연속 배칭, PagedAttention, Prefix 캐싱 |

> 요약: 일반 웹은 요청 흐름 조율에, 범용 딥러닝은 배치화에, LLM 서빙은 $KV$ 캐시 메모리 가상화와 토큰 스텝 스케줄링에 각각 특화됨.

## Ⅳ. 구성요소 및 구조

| 구성요소 | 설명 |
|:---|:---|
| API 게이트웨이 프론트 | OpenAI 규격 포맷을 매핑하고, 사용자 인증, 유량 제한($Rate$ $Limit$)을 거르는 1차 방어 장치임 |
| 동적 토큰 스케줄러 | 대기 큐의 우선순위를 분석하고 연속 배칭($Continuous$ $Batching$)으로 자원을 밀착 배분하는 조타수임 |
| 가상 캐시 매니저 | PagedAttention 및 Copy-on-Write 기법을 구동하여 GPU VRAM의 메모리 조각화를 억제하는 가용 공간 관리자임 |
| 분산 하드웨어 엔진 | 텐서 병렬화($TP$) 및 파이프라인 병렬화($PP$)를 수행하여 단일 카드를 넘어 연산을 분산 가동하는 하부 커널임 |

```text
[ LLM Serving 아키텍처 다이어그램 ]
User Request -> [API Frontend (Rate Limit)] -> [Token Scheduler (Continuous Batching)]
                                                               |
Output Stream <- [Execution Engine (TP / GPU)]  <- [PagedAttention Cache Manager]
```

## Ⅴ. 원리 및 절차 흐름도

```text
+-------------+     +--------------+     +-------------+     +-------------+
| 요청 수신 및| --> | 연속배칭 및  | --> | 텐서 분산   | --> | 토큰단위    |
| 유량 제한   |     | 가상메모리 할당|     | 병렬 실행   |     | 스트림 반환 |
+-------------+     +--------------+     +-------------+     +-------------+
```

1. **관문 통과** — 사용자의 입력이 도달하면 API 게이트웨이가 동접 트래픽 쿼타를 확인하고 자연어 문자열을 토큰 시퀀스로 인코딩함
2. **블록 할당** — 스케줄러가 활성 슬롯에 작업을 바인딩하고 가상 메모리 매니저가 $16$ 토큰 단위의 빈 물리 페이지 블록을 동적 지정함
3. **분산 추론** — 만약 단일 GPU 용량을 초과하면 NVLink 통신망을 통해 가중치 행렬을 쪼개 각 카드에 분산 연산($Tensor$ $Parallelism$)을 구동함
4. **스트리밍 반환** — 매 디코드 스텝마다 출력 토큰을 SSE(Server-Sent Events) 프로토콜을 태워 사용자 터미널 화면에 지연 없이 직송함

## Ⅵ. 실무 적용 및 유의점

1. 사내 대규모 문서 요약(Batch)과 실시간 상담 채팅(Interactive)이 단일 GPU 서빙 풀에 공존하면 Batch의 거대한 Prefill 연산이 채팅의 TPOT를 망가뜨리므로, 반드시 ' interactive-batch 자원 격리 분기 정책'을 수립하고, 실시간 API 서버의 지연 목표($SLA$) 달성률을 모니터링해야 함
2. 서빙 엔진의 텐서 병렬화(TP) 수치를 높일수록 다중 GPU 간의 All-Reduce 동기화 통신 비용이 커져 성능이 역행할 수 있으므로, 반드시 동일 노드 내의 NVLink 탑재 여부를 검증하고, GPU 개수 스케일 확장에 따른 토큰 처리 가성비 곡선을 실측하여 인프라 비용을 통제해야 함

## Ⅶ. 결론

- LLM 서빙은 초대형 지능 모델을 비즈니스의 통제 영역 내로 수용하고 가용 서버 단가를 통제하는 현대 인프라 운영의 핵심 중심축이며, 설계자는 interactive-batch 자원 격리 및 올바른 텐서 병렬화 스케일 한계점을 명확히 짚어 경제성 높고 강건한 서빙 플랫폼을 구축해야 함
