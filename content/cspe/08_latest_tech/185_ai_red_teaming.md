# 📖 【암기용】 개념 완전 이해

> 목적: AI Red Teaming을 처음 봐도 완벽히 이해하게 만든다.

## 한눈에
- **개요**: AI 시스템을 공격자 관점에서 시험해 유해 출력, 프롬프트 공격, 데이터 유출, 안전장치 우회 취약점을 찾는 검증 활동
- **왜 필요한가**: LLM과 AI 에이전트는 일반 기능 테스트만으로 jailbreak, prompt injection, tool abuse 위험을 발견하기 어려움.
- **핵심 직관**: 배포 전 AI에게 일부러 곤란한 질문과 공격 입력을 던져 안전장치의 실제 한계를 확인하는 과정임.

## 깊이 이해
- **배경·문제의식**: 생성형 AI는 입력 범위가 열려 있고 외부 도구·문서·API와 연결되면서 공격면이 대화 흐름 전체로 확장됨.
- **작동 원리**: 위협 시나리오를 만들고, 악성 프롬프트·간접 입력·권한 오남용·데이터 추출 시도를 수행한 뒤 재현 가능한 결함을 티켓화함.
- **비유**: 건물 보안 점검자가 출입증 위조, 비상문, 내부자 도움 시나리오까지 시험해 침입 경로를 찾는 활동임.
- **구체 예시**: 고객지원 LLM에 indirect prompt injection 문서를 입력해 내부 정책 노출 여부를 확인하고 leakage 0건 기준으로 재검증.
- **흔한 오해·주의점**: 레드팀은 일회성 이벤트가 아니다. 모델 업데이트, 도구 연결, 정책 변경 때마다 회귀 테스트가 필요함.

## 연결 개념
- Prompt Injection — LLM 입력 기반 명령 변조 공격
- Jailbreak — 안전 정책 우회 공격
- AI Risk Management — 취약점 발견 후 위험 수용·완화 절차

# 📝 【답안용】 시험 답안 템플릿

> 목적: 시험장에서 25분에 그대로 쓰는 답안 양식.

## 핵심 인사이트 (3줄 요약)

> 1. **본질**: AI Red Teaming은 공격자 관점으로 AI 시스템의 안전·보안 취약점을 검증하는 활동임.
> 2. **가치**: jailbreak, prompt injection, data leakage, tool abuse를 배포 전 발견해 사고 가능성을 낮춤.
> 3. **판단 포인트**: 시나리오, 성공 기준, 재현 로그, 완화 후 회귀 테스트를 체계화해야 함.

## Ⅰ. 개요 및 필요성

- 개요: AI 공격 시나리오 기반 검증 활동이다.
- 배경: 생성형 AI는 자연어 입력, 외부 문서, 도구 호출이 결합되어 기존 테스트만으로 공격면을 식별하기 어렵다.
- 필요성: AI Red Teaming은 prompt attack, data exfiltration, tool abuse 시나리오로 배포 전 위험을 검증한다.

## Ⅱ. 구조 및 구성요소

```text
Threat Scenario -> Attack Prompt/Tool Test
  -> Finding Triage -> Mitigation -> Regression Test
```

| 구성요소 | 역할 | 특이사항 |
|:---|:---|:---|
| Threat Scenario | 공격 목표·자산 정의 | prompt injection, leakage |
| Test Harness | 프롬프트·도구 호출 자동화 | 반복 재현 |
| Triage | 심각도·영향도 분류 | CVSS 유사 등급 |
| Mitigation | 정책·필터·권한 보완 | 회귀 테스트 필수 |

> 요약: AI 레드팀은 공격 시나리오를 실행하고 발견사항을 완화한 뒤 회귀 테스트로 재검증함.

## Ⅲ. 동작원리 및 흐름도

```text
자산 식별 -> 공격 시나리오 작성 -> 실행·기록
  -> 위험 등급화 -> 보완·재시험
```

| 단계 | 처리 내용 | 검증 기준 |
|:---:|:---|:---|
| 1 | 보호 대상과 오용 사례 정의 | 데이터·도구 목록 100% |
| 2 | jailbreak·injection 테스트 수행 | 성공률·재현 로그 |
| 3 | 유출·오남용 결과 등급화 | High 0건 배포 기준 |
| 4 | guardrail·권한 수정 후 재시험 | 회귀 성공률 100% |

> 요약: AI Red Teaming은 자산 기반 공격을 실행하고 High 위험 제거 후 배포 승인으로 연결함.

## Ⅳ. 특징

| 구분 | 일반 QA | AI Red Teaming | 판단 포인트 |
|:---|:---|:---|:---|
| 관점 | 정상 기능 검증 | 악성·오용 입력 검증 | 공격자 사고 |
| 대상 | 요구사항·UI | 프롬프트·모델·도구·데이터 | AI 전체 체인 |
| 지표 | 결함 수·통과율 | 유출률·우회율·재현율 | 배포 차단 기준 |
| 주기 | 릴리스 전 | 모델·정책 변경마다 | 지속 검증 |

> 요약: AI Red Teaming은 일반 QA가 다루지 않는 공격 입력과 오용 시나리오를 반복 검증하는 보안 활동임.

## Ⅴ. 실무 적용 및 결론

**적용 방안 3개:**
1. LLM 서비스: OWASP LLM 위험군 기준으로 prompt injection, data leakage, excessive agency 테스트셋 구성
2. 에이전트: 도구 호출 권한을 RBAC와 allowlist로 제한하고 임의 결제·삭제 API 호출 성공률 0% 기준 적용
3. 운영 체계: 모델 변경마다 200개 이상 공격 프롬프트 회귀 테스트를 수행하고 High finding 0건 시 배포 승인

**결론 (2줄):**
- 기술사 판단: 외부 입력과 도구를 연결한 AI는 AI Red Teaming을 배포 승인 게이트로 적용
- 향후 방향: AI Red Teaming은 자동 평가, 보안 모니터링, AI RMF 기반 위험관리와 결합됨
