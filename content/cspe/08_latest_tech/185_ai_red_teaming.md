## 미리 알고가기

- AI 레드팀은 일반 보안 모의해킹보다 넓게 모델 안전성과 유해 출력과 데이터 유출 가능성까지 시험함
- 생성형 AI는 입력 공간이 열려 있어 자동화된 공격 생성과 반복 검증이 중요함
- 레드팀 결과는 단순 보고서가 아니라 가드레일과 파인튜닝과 운영 정책 개선으로 연결되어야 함

## Ⅰ. 개요

- **정의/개념**: AI 레드팀은 적대적 관점에서 프롬프트와 데이터와 도구 사용 경로를 공격해 생성형 AI와 에이전트 시스템의 취약점과 실패 모드를 찾는 평가 활동임
- **배경/필요성**: 생성형 AI는 비결정적 출력과 광범위한 권한 연결로 인해 전통적 QA만으로는 유해 응답과 데이터 유출과 권한 오남용을 충분히 검증하기 어려워졌음

## Ⅱ. 특징

- 프롬프트 인젝션과 탈옥과 민감정보 유출처럼 자연어 기반 공격을 중점적으로 다룸
- 모델 단독 평가가 아니라 RAG와 플러그인과 에이전트 도구 호출까지 함께 검증함
- 자동화 공격 생성과 인간 검토를 결합해 대규모 적대 시나리오를 반복 시험할 수 있음
- 결과를 severity와 exploitability 기준으로 구조화하지 않으면 개선 우선순위가 흐려질 수 있음

## Ⅲ. 종류 및 비교

| 판단 기준 | Traditional QA | Cyber Red Team | AI Red Teaming |
|:---|:---|:---|:---|
| 주 대상 | 기능 요구사항 | 인프라와 네트워크 | 모델과 프롬프트와 에이전트 |
| 공격 수단 | 테스트 케이스 | 익스플로잇, 침투 | 자연어, 데이터, 도구 악용 |
| 핵심 산출물 | 버그 목록 | 침투 결과와 경로 | 유해 출력, 유출, 권한 오남용 결과 |
| 운영 가치 | 기능 안정성 | 보안 통제 검증 | 안전성·신뢰성 검증 |

## Ⅳ. 구성요소 및 구조

| 구성요소 | 설명 |
|:---|:---|
| Threat Scope | 어떤 모델과 도구와 데이터 흐름을 공격 대상으로 볼지 범위를 정함 |
| Attack Corpus, Generator | 수동 프롬프트와 자동 생성 공격 세트를 준비해 다양한 실패 모드를 자극함 |
| Execution Harness | 대량 질의와 로그 수집과 결과 분류를 자동화해 반복 실험을 가능하게 함 |
| Evaluation Rubric | 유해성, 성공률, 영향도, 재현성 기준으로 취약점을 점수화함 |
| Mitigation Feedback Loop | 가드레일과 파인튜닝과 정책 수정을 적용하고 재시험으로 개선 효과를 확인함 |

```text
+-------------------+      +-------------------+      +-------------------+
| Threat Scope      | ---> | Attack Generator  | ---> | Execution Harness |
+-------------------+      +-------------------+      +-------------------+
                                                           |
                                                           v
                                                   +-------------------+
                                                   | Evaluate / Fix    |
                                                   +-------------------+
```

## Ⅴ. 원리 및 절차 흐름도

```text
+-------------+     +-------------+     +-------------+     +-------------+
| 공격 범위 정의   | --> | 적대 입력 생성  | --> | 실행/결과 분류  | --> | 완화 후 재시험  |
+-------------+     +-------------+     +-------------+     +-------------+
```

1. **공격 범위 정의**: 모델과 권한과 데이터 경로를 정함
2. **적대 입력 생성**: 탈옥과 인젝션과 유출 시나리오를 만듦
3. **실행 및 결과 분류**: 성공 여부와 영향도를 체계적으로 측정함
4. **완화 후 재시험**: 수정된 가드레일과 모델을 다시 공격해 효과를 검증함

## Ⅵ. 문제점 및 해결 방안

1. 문제: 수작업 중심 레드팀은 커버리지가 좁아 최신 우회 기법과 대규모 변형 프롬프트를 충분히 검증하지 못할 수 있음
   - 해결방안: automated adversarial generation을 도입하고 attack coverage와 attack success rate로 검증함
2. 문제: 모델만 테스트하고 플러그인과 외부 API 권한은 보지 않으면 실제 서비스의 가장 큰 오남용 경로를 놓칠 수 있음
   - 해결방안: end-to-end agent red teaming을 수행하고 tool abuse detection rate와 privileged action block rate로 검증함
3. 문제: 취약점 결과가 개선 파이프라인으로 연결되지 않으면 같은 문제가 반복적으로 재발할 수 있음
   - 해결방안: severity-based remediation backlog를 운영하고 patch lead time과 regression recurrence rate로 검증함

## Ⅶ. 적용 사례

- 고객지원 챗봇이 환불 정책 우회와 쿠폰 남발 시도를 레드팀으로 검증하며 확인 지표는 prompt abuse success rate와 human escalation rate임
- 기업 내부 에이전트가 사내 문서와 메일 도구를 연결한 상태에서 데이터 유출 경로를 시험하며 확인 지표는 exfiltration success rate와 privileged tool block rate임
- 의료 상담형 AI가 유해 조언과 환각 시나리오를 지속 점검하며 확인 지표는 harmful response rate와 mitigation turnaround time임

## Ⅷ. 결론

AI 레드팀은 생성형 AI의 실패를 출시 전에 현실적으로 체험하게 만드는 검증 체계이므로 자동화와 운영 연결성을 갖춘 반복 프로세스로 설계해야 함.
