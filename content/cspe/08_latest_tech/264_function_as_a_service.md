# 📖 【암기용】 개념 완전 이해

> 목적: FaaS를 서버를 직접 관리하지 않고 이벤트가 발생할 때 함수 단위 코드를 실행하는 서버리스 실행 모델로 이해하게 만든다.

## 한눈에
- **개요**: 이벤트 발생 시 짧은 함수 코드를 실행하고 실행 시간·호출 수 기준으로 과금하는 컴퓨팅 모델
- **왜 필요한가**: 상시 트래픽이 아닌 업무에서 VM이나 컨테이너를 계속 유지하면 유휴 비용과 운영 작업이 발생한다.
- **핵심 직관**: 매장을 하루 종일 열어 두는 대신 주문이 들어올 때만 조리 공간을 배정받아 처리하는 방식이다.

## 깊이 이해
- **배경·문제의식**: 웹훅, 이미지 변환, 배치 트리거, IoT 이벤트는 실행 시간이 짧고 호출 간 간격이 불규칙하다.
- **작동 원리**: 클라우드 플랫폼이 이벤트를 수신하고 런타임을 준비한 뒤 함수 핸들러를 호출하며, 함수는 외부 저장소·API에 상태를 위임한다.
- **비유**: 콜센터 상담사가 상주하지 않고 콜이 들어올 때마다 배정되는 임시 상담석과 유사하다.
- **구체 예시**: 객체 저장소에 이미지가 업로드되면 썸네일 생성 함수가 512MB 메모리로 3초 실행되고 결과를 다른 버킷에 저장한다.
- **흔한 오해·주의점**: FaaS는 서버가 없는 것이 아니라 서버 운영 책임이 제공자에게 이동한 구조이며, cold start와 실행 시간 제한을 고려해야 한다.

## 연결 개념
- Serverless Computing — FaaS를 포함하는 운영 모델
- Event-Driven Architecture — FaaS 호출을 유발하는 이벤트 구조
- API Gateway — HTTP 요청을 함수 호출로 변환하는 대표 진입점

# 📝 【답안용】 시험 답안 템플릿

> 목적: 시험장에서 25분에 그대로 쓰는 답안 양식.
> 핵심: FaaS는 이벤트, 함수, 런타임, 상태 외부화, 과금 단위를 함께 설명해야 한다.

## 핵심 인사이트 (3줄 요약)

> 1. **본질**: FaaS는 이벤트 발생 시 함수 단위 코드를 실행하는 서버리스 컴퓨팅 모델임.
> 2. **가치**: 호출 수, 실행 시간, 메모리 할당량 기준 과금으로 불규칙 트래픽의 유휴 자원 비용을 줄임.
> 3. **판단 포인트**: 짧은 stateless 작업에는 적합하지만 long-running transaction, 낮은 cold start 지연 요구에는 별도 검토가 필요함.

## 출제 의도 및 답안 포인트

| 출제 의도 | 반드시 짚을 핵심 | 감점 회피 포인트 |
|:---|:---|:---|
| 서버리스 실행 모델 이해 확인 | event trigger, function runtime, stateless, pay-per-use | 서버리스와 컨테이너 호스팅을 동일시 |
| 적용 판단 확인 | cold start, 실행 시간 제한, 상태 외부화 | 무상 운영 또는 서버 부재로 오기술 |
| 아키텍처 설계 확인 | API Gateway, Queue, Object Storage, IAM | 권한·관측성·재시도 설계 누락 |

> 요약: 이 문제는 함수 실행 구조와 운영 제약을 기준으로 FaaS 적용 여부를 판단하는 역량을 요구한다.

---

## Ⅰ. 개요 및 필요성

- 개요: 이벤트 기반 함수 실행 모델
- 배경: 불규칙 호출 업무에 상시 서버를 유지하면 유휴 비용과 패치·스케일 작업이 발생함.
- 필요성: 웹훅, 파일 처리, 이벤트 배치처럼 초·분 단위 작업은 호출 기반 실행과 상태 외부화가 적합함.

---

## Ⅱ. 구조 및 구성요소

```text
Event Source -> Trigger -> Function Runtime -> Managed Service
Function Runtime -> Log / Metric / Trace -> Monitoring
IAM Policy -> Function Runtime -> Secret / Storage / Queue
```

| 구성요소 | 역할 | 특이사항 |
|:---|:---|:---|
| Event Source | HTTP, Queue, Object, Schedule 이벤트 발생 | 비동기·동기 호출 구분 |
| Function Runtime | 코드 로딩과 핸들러 실행 | 언어 런타임·메모리 설정 |
| Managed Service | 상태 저장과 외부 처리 | DB, Storage, Message Queue |
| IAM Policy | 최소 권한 접근 제어 | 함수 단위 권한 분리 |

> 요약: FaaS는 이벤트 진입, 함수 실행, 관리형 서비스 연계, 권한 통제가 결합된 실행 구조다.

---

## Ⅲ. 동작원리 및 흐름도

```text
이벤트 수신 -> 트리거 매핑 -> 컨테이너 준비 / 재사용
-> 핸들러 실행 -> 외부 서비스 호출 -> 결과 반환 / 재시도 -> 로그 기록
```

| 단계 | 처리 내용 | 검증 기준 |
|:---:|:---|:---|
| 1 | 이벤트와 함수 매핑 확인 | trigger rule 일치 |
| 2 | 런타임 인스턴스 준비 또는 재사용 | cold start 시간 |
| 3 | 함수 핸들러 실행 | timeout, memory 사용률 |
| 4 | 결과 반환과 실패 재시도 처리 | retry count, DLQ 적재 |

> 요약: FaaS는 이벤트를 함수 호출로 변환하고 실행 결과와 실패 이벤트를 플랫폼 정책으로 관리한다.

---

## Ⅳ. 특징

| 구분 | VM/컨테이너 상시 실행 | FaaS | 판단 기준 |
|:---|:---|:---|:---|
| 실행 단위 | 서버·서비스 프로세스 | 함수 핸들러 | 업무 경계가 짧은 작업 |
| 과금 | 인스턴스 유지 시간 | 호출 수·실행 시간·메모리 | 유휴 시간 비율 |
| 상태 | 로컬 상태 가능 | 외부 저장소 위임 | stateless 가능 여부 |
| 지연 | 예측 가능한 상주 프로세스 | cold start 발생 가능 | p95 지연 요구 |

> 요약: FaaS는 유휴 시간이 큰 이벤트성 업무에 적합하며, 지연 민감 업무는 cold start와 timeout을 먼저 검증해야 한다.

---

## Ⅴ. 심화 비교 및 적용 판단

| 비교 축 | 기존/대안 | 본 키워드 | 선택 기준 |
|:---|:---|:---|:---|
| 구조 | 컨테이너 서비스 | 함수 단위 실행 | 요청 처리 시간이 짧은지 |
| 비용/성능 | 상시 인스턴스 비용 | 호출 기반 비용 | 유휴 시간 50% 이상 |
| 운영/위험 | 서버 패치·스케일 직접 관리 | 플랫폼 관리, 제한 존재 | timeout·vendor lock-in 허용 여부 |

> 요약: 호출 간 공백이 크고 상태를 외부화할 수 있으면 FaaS, 지속 연결과 장시간 처리에는 컨테이너가 적합하다.

| 리스크 | 원인 | 대응 방안 | 확인 지표 |
|:---|:---|:---|:---|
| Cold Start | 런타임 신규 준비 | provisioned concurrency, 경량 런타임 | init duration |
| 중복 처리 | 비동기 재시도 | idempotency key, DLQ | duplicate event count |
| 권한 과다 | 함수별 IAM 미분리 | least privilege policy | denied/allowed audit log |

> 요약: FaaS 리스크는 초기 지연, 중복 처리, 권한 과다이며 실행 지표와 감사 로그로 통제한다.

| 점검 항목 | 목표 기준 | 측정 방법 |
|:---|:---|:---|
| 지연 | p95 응답시간 SLA 이내 | APM, platform metric |
| 비용 | 월 호출·GB-second 기준 예산 이내 | billing report |
| 장애 처리 | DLQ 적재 후 재처리 가능 | queue depth, replay test |

> 요약: FaaS 도입 후 지연, 비용, 실패 이벤트 재처리 지표가 기준 안에 있어야 한다.

---

## Ⅵ. 실무 적용 및 결론

**적용 방안 3개:**
1. API Gateway, Queue, Object Storage 이벤트를 함수별로 분리하고 함수당 단일 책임을 유지함.
2. timeout, memory, concurrency limit, DLQ를 배포 산출물에 명시해 장애 전파를 제한함.
3. idempotency key와 correlation id를 로그에 남겨 재시도와 분산 추적을 함께 검증함.

**결론 (2줄):**
- 기술사 판단: 이벤트성 stateless 작업이면 FaaS를 선택하고, 장시간 연결·상시 메모리 상태가 필요하면 컨테이너 서비스를 선택함.
- 향후 방향: FaaS는 EDA, API Gateway, Observability와 결합되어 클라우드 네이티브 자동 실행 계층으로 확장됨.
