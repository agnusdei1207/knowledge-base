# 📖 【암기용】 개념 완전 이해

> 목적: FaaS를 처음 봐도 완벽히 이해하게 만든다. 시험 답안 양식이 아니라, 이해를 위한 친절한 설명이다.

## 한눈에
- **개요**: 애플리케이션을 거대한 프로그램 단위가 아니라, 작은 '함수(Function)' 단위로 쪼개어 필요할 때만 실행시키는 클라우드 컴퓨팅 서비스
- **왜 필요한가**: 서버 전체를 빌릴 필요 없이, 특정 기능(예: 회원가입 메일 발송) 하나만 딱 실행하고 싶을 때 가장 효율적이기 때문이다.
- **핵심 직관**: "완성된 요리(애플리케이션)를 파는 식당이 아니라, 손님이 재료를 넣으면 요리 기계가 그 순간에만 작동해서 결과를 내놓는 '자동 자판기' 같은 서비스"

## 깊이 이해
- **배경·문제의식**: 기존의 가상 머신(IaaS)이나 컨테이너(PaaS)는 코드가 실행되지 않을 때도 서버가 켜져 있어 자원을 낭비했다. 이를 해결하기 위해 실행 시간과 횟수에만 과금하는 더 세밀한(Fine-grained) 서비스 모델이 필요해졌다.
- **작동 원리**:
  1. **이벤트 트리거**: 특정 사건(파일 업로드, 시간 예약 등)이 발생하면 호출된다.
  2. **에페머럴(Ephemeral) 환경**: 함수는 잠깐 실행되고 사라지는 일시적인 컨테이너에서 돌아간다.
  3. **무상태성(Stateless)**: 함수는 이전 실행 결과를 기억하지 않는다. 필요한 정보는 외부 DB나 스토리지에 저장해야 한다.
- **비유**: 센서 등(Light)과 같다. 사람이 지나갈 때만(이벤트) 잠시 켜지고(함수 실행), 사람이 없으면 꺼진다. 등이 켜져 있는 동안의 전기료만 내면 된다.
- **구체 예시**: AWS Lambda가 가장 유명하며, Azure Functions, Cloud Functions 등이 있다. 사용자가 프로필 사진을 바꾸면(이벤트), 이미지를 압축하는 함수(FaaS)가 실행되어 썸네일을 만든다.
- **흔한 오해·주의점**: FaaS가 서버리스와 완전히 같은 말은 아니다. 서버리스는 FaaS와 BaaS(백엔드 서비스)를 모두 포함하는 더 넓은 개념이며, FaaS는 그중 '연산' 부분을 담당하는 핵심 서비스다.

## 연결 개념
- Serverless Computing — FaaS를 포함하는 상위 비즈니스 모델
- Event-Driven Architecture — FaaS가 동작하는 근본적인 아키텍처 방식
- Microservices — FaaS를 통해 구현할 수 있는 서비스 구조

# 📝 【답안용】 시험 답안 템플릿

> 목적: 시험장에서 25분에 그대로 쓰는 답안 양식. 작성방식(추상표현 금지·수치·도식·문제유형 전환)을 엄격히 지킨다.
> 핵심: FaaS는 이벤트 기반 트리거와 무상태성(Stateless), 그리고 인프라 추상화 가치를 중심으로 기술한다.

## 핵심 인사이트 (3줄 요약)

> 1. **본질**: FaaS(Function as a Service)는 개별 로직을 독립된 함수 단위로 배포하고, 이벤트 발생 시에만 클라우드 자원을 할당받아 실행하는 서버리스 연산 모델이다.
> 2. **가치**: 인프라 관리 부담을 제거(NoOps)하고 호출 횟수 및 실행 시간 기반의 정밀 과금을 통해 운영 효율성과 경제성을 극대화한다.
> 3. **판단 포인트**: 실행 지연(Cold Start) 및 최대 실행 시간(Timeout) 제약을 확인하여, 실시간성보다는 비동기 및 이벤트 처리 워크로드에 우선 적용한다.

## 출제 의도 및 답안 포인트

| 출제 의도 | 반드시 짚을 핵심 | 감점 회피 포인트 |
|:---|:---|:---|
| 클라우드 서비스 모델 분류 역량 | IaaS / PaaS / SaaS / FaaS 차이점 | PaaS와 FaaS를 혼동하여 기술 |
| 기술적 제약 사항 인지 여부 | Stateless, Ephemeral, Cold Start | 무조건적인 확장성만 강조 |
| 서비스 설계 및 비용 최적화 능력 | Event-driven 아키텍처, 사용량 기반 과금 | 고정 부하 환경에서의 비용 역전 현상 간과 |

> 요약: 함수 단위의 독립적 배포와 실행, 이벤트 트리거 메커니즘을 중심으로 아키텍처적 장단점을 기술한다.

## Ⅰ. 개요 및 필요성

- 정의: 애플리케이션 로직을 독립적인 함수 단위로 개발하고, 인프라 관리 없이 이벤트에 반응하여 실행하는 클라우드 컴퓨팅 서비스
- 배경: 마이크로서비스의 세분화(Nano-services) 및 인프라 운영 자동화(NoOps)에 대한 시장 요구 증가
- 필요성: 개발 생산성 향상, 유휴 자원 낭비 제거 및 1ms 단위의 정밀 과금을 통한 비용 최적화

---

## Ⅱ. 구조 및 구성요소

```text
[FaaS 아키텍처 및 통신 구조]
Event Source ----> [Trigger Handler] ----> [Ephemeral Container]
(S3, SNS, HTTP)      (Auth/Route)           (Function Logic)
                                               | (Stateless)
                                         External DB / Storage
```

| 구성요소 | 역할 | 특이사항 |
|:---|:---|:---|
| Function Code | 사용자가 작성한 비즈니스 로직 | 특정 핸들러 함수 형태로 작성 |
| Event Source | 함수 실행을 유도하는 외부/내부 신호 | API 호출, 메시지 큐, DB 변경 등 |
| Runtime Environment | 함수가 실행되는 격리된 런타임 공간 | Node.js, Python, Java 등 지원 |
| Control Plane | 요청에 따른 인프라 할당 및 스케일링 관리 | 클라우드 사업자가 운영 (Invisible) |

> 요약: 트리거 신호를 받아 즉석에서 만들어진 격리 환경(Container)에서 함수 코드가 돌아가는 구조다.

## Ⅲ. 동작원리 및 흐름도

```text
[FaaS 호출 및 실행 프로세스]
Event Detect -> Auth/Limit Check -> Warm/Cold Start -> Code Download -> Execution -> Result & Cleanup
```

| 단계 | 처리 내용 | 검증 기준 |
|:---:|:---|:---|
| 1 | 구성된 이벤트 소스로부터 실행 요청 수신 | 트리거 규칙 및 IAM 권한 확인 |
| 2 | 가용 컨테이너 확인 및 필요 시 신규 생성 | Cold Start 발생 여부 (수백 ms 이내) |
| 3 | 작성된 소스 코드를 실행 환경으로 로드 및 인스턴스화 | 패키지 크기(Zip/Image) 최적화 |
| 4 | 사용자 정의 핸들러 호출 및 비즈니스 로직 수행 | 실행 시간 제한(예: 15분) 준수 |

> 요약: 이벤트 발생 시마다 독립적 환경을 프로비저닝하고 로직을 수행한 후 자원을 즉시 회수한다.

## Ⅳ. 특징

| 구분 | 내용 | 판단 포인트 |
|:---|:---|:---|
| 무상태성 | 실행 간 데이터 공유 불가 (Stateless) | 외부 캐시(Redis) 또는 DB 필수 |
| 자동 확장 | 요청 수에 따른 수평적 자동 확장 | 동시 실행(Concurrency) 한도 점검 |
| 일시성 | 실행 후 환경 파괴 (Ephemeral) | 로컬 파일 시스템 영구 저장 불가 |

> 요약: 관리 포인트가 거의 없는 대신, 함수의 독립성과 일시성이라는 제약을 설계에 반영해야 한다.

## Ⅴ. 심화 비교 및 적용 판단

| 구분 | PaaS (기존 컨테이너) | FaaS (서버리스 함수) | 선택 기준 |
|:---|:---|:---|:---|
| 추상화 단위 | 애플리케이션 (Service) | 코드 조각 (Function) | 로직의 분할 가능 수준 |
| 확장 방식 | 인스턴스/파드 단위 확장 | 요청/호출 단위 즉시 확장 | 트래픽의 급격한 변동성 |
| 과금 방식 | 예약된 자원 기반 (Fixed) | 실제 실행 시간 기반 (Usage) | 유휴 시간 비율 (Idle Time) |

> 요약: 지속적인 웹 서비스는 PaaS가, 간헐적인 비즈니스 로직 처리는 FaaS가 경제적이다.

| 리스크 | 원인 | 대응 방안 | 확인 지표 |
|:---|:---|:---|:---|
| Cold Start 지연 | 초기 기동 시 런타임 환경 구축 시간 | Provisioned Concurrency, 코드 최적화 | 99th Percentile Latency |
| 실행 시간 제한 | 장기 연산 시 강제 종료 (Timeout) | 단계를 쪼개어 연쇄 호출(Chaining) 적용 | Timeout 발생 에러 로그 |
| 보안 경계 약화 | 다수의 함수 노출에 따른 공격 표면 증가 | 최소 권한 원칙(Principle of MLP) 적용 | IAM 정책 준수율 및 감사 로그 |

> 요약: 지연 시간은 워밍업 기법으로, 실행 제한은 아키텍처 분할로, 보안은 세밀한 권한 제어로 관리한다.

| 점검 항목 | 목표 기준 | 측정 방법 |
|:---|:---|:---|
| 평균 응답 시간 | 200ms 이내 (Cold Start 포함 시 1s) | APM 및 클라우드 로그 분석 |
| 실행 성공률 | 99.9% (HTTP 200 OK 비중) | 에러 모니터링 대시보드 |
| 인프라 비용 절감 | 기존 대비 50% 이상 (저부하 시) | 클라우드 청구서 월별 비교 |

> 요약: 가용성과 응답성, 그리고 비용 효율성을 통해 FaaS 도입의 성공 여부를 측정한다.

## Ⅵ. 실무 적용 및 결론

**적용 방안 3개:**
1. 실시간 이미지 가공: S3 이미지 업로드 이벤트를 받아 즉시 리사이징 및 워터마크 처리를 수행하는 FaaS 워크플로우 구축
2. 서버리스 백엔드 API: API Gateway와 Lambda를 조합하여 서버 관리 없이 프론트엔드용 RESTful API 제공
3. 비동기 작업 큐 처리: SQS/Kinesis 메시지를 소비하여 대량의 데이터를 병렬로 처리하는 데이터 파이프라인 구현

**결론 (2줄):**
- 기술사 판단: FaaS는 '운영의 추상화'를 완성한 기술이며, 성공적인 도입을 위해서는 무상태성 원칙 준수와 Cold Start 최적화가 필수적이다
- 향후 방향: 에지 컴퓨팅(Edge Computing)과 결합하여 사용자 근거리에서 로직을 실행하는 Edge Functions로 진화할 것이다
