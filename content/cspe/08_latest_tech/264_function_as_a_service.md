# 📖 【암기용】 개념 완전 이해

> 목적: 서버리스(Serverless)의 심장부이자, 개발자가 오직 '함수(Function)' 하나만 짜서 던지면 전 세계 수백만 명의 요청을 처리해주는 FaaS의 본질을 이해한다.

## 한눈에
- **정의**: 개발자가 전체 애플리케이션이나 서버 인프라를 구축할 필요 없이, 딱 **하나의 기능(Function)을 수행하는 짧은 코드 조각만 클라우드에 올려서 실행**할 수 있게 해주는 클라우드 서비스
- **필요성**: 기존에는 "회원가입 기능" 하나를 추가하려고 해도 프레임워크를 띄우고 WAS를 설정해야 했으나, 이제는 그냥 `def signup():` 함수 하나만 뚝 떼어내서 별도로 관리하고 무한대로 스케일링하고 싶기 때문
- **핵심 직관**: "거대한 뷔페 식당(Monolithic)을 차리는 대신, 오직 '계란 프라이'만 기가 막히게 만드는 로봇(FaaS)을 하나 만들어두고 주문(이벤트)이 들어올 때마다 로봇이 튀어나와 요리하고 사라지는 것"

## 깊이 이해
- **배경(왜 등장했나?)**: 마이크로서비스(MSA)가 발전하면서 서비스 단위가 점점 작아졌다. 그러다 보니 "서비스 단위가 아니라 아예 '함수(메서드)' 단위로 쪼개면 어떨까?"라는 생각에 도달했다. AWS가 2014년에 'Lambda(람다)'를 발표하면서 이 미친 아이디어(FaaS)가 현실이 되었고, 클라우드 시장의 판도를 바꿨다.
- **작동 원리(어떻게 달성했나?)**: 
  1. **배포**: 개발자가 파이썬, 노드JS 등으로 짠 100줄짜리 함수 코드만 달랑 압축해서 AWS에 올린다.
  2. **트리거 대기**: 이 함수는 잠들어 있다. 누군가 "API 호출"을 하거나 "DB에 데이터가 삽입"되는 등 약속된 '이벤트(트리거)'가 발생하면 깨어난다.
  3. **순간 실행 & 소멸**: AWS가 0.1초 만에 마이크로VM(Firecracker 등)을 띄워 함수를 실행하고 결과를 뱉은 뒤(통상 15분 이내), 컨테이너를 파괴해 버린다.
- **일상 비유**: 자판기와 같다. 평소에는 전기(비용)를 최소한만 쓰며 조용히 있다가, 누군가 동전을 넣고 버튼을 누르는 순간(이벤트) 기계가 '징~' 하고 작동해서 캔 커피를 꺼내주고(실행) 다시 대기 상태로 돌아가는 구조다.
- **구체 예시**: 사용자가 프로필 사진을 S3(스토리지)에 올린다 ➔ S3가 `ResizeImage`라는 FaaS 함수를 트리거한다 ➔ FaaS가 사진을 썸네일 크기로 줄여서 다시 S3에 저장하고 종료된다. (이 과정에서 개발자가 세팅한 서버는 단 0대다.)
- **흔한 오해/주의점**: "FaaS에 무거운 딥러닝 학습 코드를 올려도 될까?" → 절대 안 된다. FaaS는 최대 실행 시간 제한(보통 15분)이 있고, RAM 제한(보통 10GB 이하), 그리고 상태를 보존하지 않기 때문에 무겁고 오래 걸리는 작업이나 Stateful한 워크로드에는 최악이다.

## 연결 개념
- **Serverless Computing**: FaaS가 작동하기 위한 기반 철학. (서버리스 = FaaS + BaaS)
- **Cold Start**: FaaS의 최대 단점. 함수가 처음 불리거나 오랫동안 안 불렸다가 불릴 때 컨테이너를 준비하느라 생기는 초기 지연 시간.
- **AWS Lambda**: 전 세계에서 가장 유명하고 널리 쓰이는 대명사격 FaaS 제품.

# 📝 【답안용】 시험 답안 템플릿

## 핵심 인사이트 (3줄 요약)
> 1. **본질**: FaaS(Function as a Service)는 서버리스 컴퓨팅을 구현하는 핵심 아키텍처로, 애플리케이션을 '상태가 없는(Stateless)' 단일 목적의 함수 단위로 분할하여 이벤트 주도(Event-Driven)로 실행하는 클라우드 서비스다.
> 2. **가치**: 인프라 프로비저닝 없이 오직 비즈니스 로직(Code)에만 집중할 수 있게 하며, 100ms 단위의 극단적인 종량제 과금과 요청량에 비례하는 무한한 오토 스케일링을 제공한다.
> 3. **판단 포인트**: 초단기/비동기 작업에 최적화되어 있으나, Cold Start 지연 및 실행 시간 제한(Timeout)이 존재하므로, 무거운 배치 처리나 연결(Connection)을 계속 유지해야 하는 워크로드에는 부적합하다.

## Ⅰ. 개요 및 필요성
- **정의**: 개발자가 작성한 비즈니스 로직(함수)을 클라우드에 등록하고, 특정 이벤트(Trigger)가 발생할 때만 서버 자원을 일시적으로 할당하여 코드를 실행하는 컴퓨팅 서비스 모델
- **배경**: IaaS/PaaS는 유휴 상태(Idle)에서도 과금이 발생하며, 마이크로서비스(MSA)보다 더 세밀한 수준(Nano-services)의 모듈화 및 배포 단축 요구 증가
- **필요성**: 트래픽 패턴 예측이 불가능한 서비스의 비용 효율화, NoOps를 통한 개발 생산성 극대화, 클라우드 네이티브 아키텍처의 완성

## Ⅱ. FaaS의 핵심 특징 및 동작 원리
FaaS는 철저하게 **이벤트 주도(Event-Driven)**와 **상태 비저장(Stateless)** 원칙에 따라 동작한다.

1. **Event-Driven (이벤트 주도 호출)**
   - HTTP 요청(API Gateway 연동), 데이터베이스 변경(DynamoDB Stream), 메시지 큐 알림(Kafka/SQS) 등 사전에 정의된 '트리거'에 의해서만 함수가 기동됨.
2. **Stateless (상태 비저장)**
   - 함수가 한 번 실행되고 나면 메모리와 로컬 디스크의 데이터는 모두 파기됨. 세션이나 영구 데이터는 반드시 외부 스토리지(S3, Redis)에 저장해야 함.
3. **Ephemeral (단명성 및 제한 시간)**
   - 짧은 실행을 목적으로 설계되어, 대부분의 퍼블릭 FaaS는 1회 실행 시간을 최대 15분 이내로 강제 제한(Timeout)함.

## Ⅲ. PaaS, CaaS, FaaS 서비스 모델 비교
| 구분 | PaaS (Platform as a Service) | CaaS (Container as a Service) | FaaS (Function as a Service) |
|:---|:---|:---|:---|
| **배포 단위** | 애플리케이션 전체 (App) | 컨테이너 이미지 (Container) | **코드 조각 (Function)** |
| **운영 체제/런타임**| 벤더가 제공/관리 | 개발자가 이미지 내부에 구성 | **벤더가 전적으로 제공 (Python, Node 등)** |
| **스케일링 방식** | 인스턴스 개수 기반 조절 | K8s HPA를 통한 컨테이너 확장 | **이벤트 1개당 1함수 (동시 다발적 무한 확장)** |
| **비용 구조** | 프로비저닝된 용량 기반 (고정비) | 클러스터/노드 유지 비용 | **호출 횟수 및 100ms 단위 실행 시간 (변동비)** |

## Ⅳ. 기술적 한계 (리스크) 및 극복 방안
| 한계 요인 | 상세 원인 분석 | 대응 방안 (Architecture Pattern) |
|:---|:---|:---|
| **Cold Start (초기 지연)** | 함수 호출 시 클라우드가 백단에서 컨테이너 공간을 만들고 런타임을 로드하느라 발생하는 1~3초의 Latency | **Provisioned Concurrency** (사전 예열), 무거운 프레임워크(Spring Boot) 대신 경량 런타임(Go, Node.js) 사용 |
| **실행 시간 및 리소스 제한**| 장시간(15분 이상) 실행되거나 거대한 메모리(10GB 이상)를 요구하는 작업 불가 | 무거운 작업은 AWS Step Functions로 함수들을 쪼개어 체이닝(Chaining)하거나, Fargate(CaaS)로 이관 |
| **DB 커넥션 고갈** | 10,000개의 함수가 동시에 뜨면 DB에 10,000개의 Connection을 맺어 RDBMS가 다운됨 | **RDS Proxy** 등 커넥션 풀링(Connection Pooling) 미들웨어 레이어 도입 필수 |

## Ⅴ. 오케스트레이션 기반의 오픈소스 FaaS (K8s 연계)
클라우드 벤더(AWS Lambda 등)에 종속되는 현상(Vendor Lock-in)을 막기 위해, 자체 구축한 쿠버네티스(K8s) 위에서 FaaS를 구현하는 오픈소스 생태계가 발전하고 있다.
- **Knative (K-네이티브)**: 구글이 주도. K8s 기반으로 서버리스 워크로드를 빌드/서빙/이벤트 라우팅하는 플랫폼. Scale-to-Zero(트래픽 없을 때 0개로 줄임) 완벽 지원.
- **OpenFaaS**: 도커 컨테이너만 만들 줄 알면 어떤 언어로든 람다처럼 사용할 수 있게 해주는 가장 대중적인 오픈소스 FaaS 프레임워크.

## Ⅵ. 실무 적용 및 결론
**적용 방안 및 실무 가이드:**
1. **이벤트 드리븐 백그라운드 처리**: 사용자가 이미지를 업로드하면 S3 이벤트가 FaaS를 깨워 썸네일을 생성하거나, 주문이 들어오면 메일을 발송하는 비동기 워크로드에 1순위로 도입한다.
2. **Serverless BFF(Backend For Frontend) 패턴**: 모바일 앱과 마이크로서비스들 사이에 FaaS 기반의 API Gateway를 두어, 프론트엔드 요구사항에 맞는 데이터 취합 및 가공 로직을 함수 단위로 민첩하게 수정 및 배포한다.

**결론:**
- FaaS는 인프라 관리라는 무거운 짐을 클라우드 벤더에게 완전히 떠넘기고, **'코드가 곧 인프라'**가 되는 패러다임 시프트를 이뤄냈다.
- 상태 비저장(Stateless)과 짧은 생명주기라는 제약 조건을 아키텍처 설계 단계부터 철저히 고려(Design for Serverless)한다면, 엔터프라이즈 환경에서 비즈니스 민첩성과 비용 효율을 극대화하는 강력한 무기가 될 것이다.
