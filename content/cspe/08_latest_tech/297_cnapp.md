# 📖 【암기용】 개념 완전 이해

> 목적: 클라우드 보안 도구(CSPM, CWPP 등)가 너무 많아져서 오히려 보안팀이 알람 지옥에 빠지는 문제를 해결하기 위해, 모든 보안 툴을 하나로 합친 궁극의 '클라우드 통합 보안 플랫폼(CNAPP)'을 이해한다.

## 한눈에
- **정의**: 클라우드 인프라 설정(CSPM)부터 컨테이너 워크로드(CWPP), 계정 권한(CIEM) 보호까지 **클라우드 네이티브 환경의 모든 보안 기능을 하나의 플랫폼으로 통합한 보안 아키텍처** (가트너 정의)
- **필요성**: 개발자가 클라우드에 앱을 하나 올리면, 설정 검사 툴(CSPM)에서 알람 100개, 컨테이너 검사 툴(CWPP)에서 100개가 울린다. 보안팀은 뭐가 진짜 위험한지 파악하다가 밤을 새운다. 파편화된 보안 툴을 하나로 합쳐서(Consolidation) '맥락(Context)'을 파악하기 위함
- **핵심 직관**: "병원 종합 건강검진 센터. 예전엔 피검사(CSPM)는 A병원, X레이(CWPP)는 B병원, 시력검사(CIEM)는 C병원에서 따로 받고 결과지를 3장 받았다(파편화). CNAPP는 한 병원에서 모든 검사를 한 번에 끝내고, '피검사 수치와 X레이를 종합해 보니 당신은 심장병 위험이 높다'고 정확한 맥락(Context)을 짚어주는 종합 플랫폼이다."

## 깊이 이해
- **배경(왜 등장했나?)**: 클라우드가 도입되면서 보안 벤더들은 앞다퉈 CSPM(설정 오류 찾기), CWPP(도커 보안), CIEM(과도한 권한 찾기) 등 개별 솔루션(Point Solution)을 쏟아냈다. 기업들은 불안해서 이걸 다 샀는데, 각 솔루션이 서로 소통을 안 하니 오탐(False Positive) 알람만 하루에 수만 개가 쏟아졌다(Alert Fatigue). 이에 가트너는 "이것들을 전부 하나로 통합(Consolidation)해서 맥락을 분석하라!"며 CNAPP라는 개념 제시했다.
- **작동 원리 (맥락 기반의 위험 분석)**:
  - 분리된 환경: CSPM은 "DB가 퍼블릭으로 열려있네? 위험해!"라고 알람을 주고, CWPP는 "컨테이너에 악성코드가 있네? 위험해!"라고 따로 알람을 준다.
  - CNAPP의 통합 환경 (Context Analysis): "이 컨테이너에 악성코드가 있는데(CWPP), 하필 이 컨테이너가 퍼블릭으로 열려있는 DB(CSPM)에 접근할 수 있는 과도한 관리자 권한(CIEM)까지 가지고 있네? **이건 당장 해킹당하기 일보 직전인 초특급 위험(Critical Risk)이다!**"라며 단 하나의 정확한 경고를 발생시킨다.
- **일상 비유**: 범죄 수사망. 파출소(CSPM)는 도둑이 창문을 깼다고 보고하고, 교통계(CWPP)는 뺑소니가 났다고 보고한다. 둘이 소통이 안 되면 그냥 잡범 두 명이다. 하지만 CNAPP(경찰청 컨트롤타워)가 두 사건을 묶어보니, 창문을 깬 놈이 뺑소니 차를 타고 도망친 '연쇄 살인마'라는 맥락(Context)을 파악해 내는 것.
- **구체 예시**: 개발자가 GitHub에 코드를 올렸다. CNAPP는 코드가 빌드될 때(Shift-Left)부터 소스코드의 취약점을 검사하고, 배포된 컨테이너(CWPP)를 지켜보며, AWS 인프라 설정(CSPM)이 안전한지 태어날 때부터 죽을 때까지(End-to-End) 하나의 화면에서 감시한다. 대표 솔루션으로 Wiz, Palo Alto Prisma Cloud 등이 있다.
- **흔한 오해/주의점**: "CNAPP는 새로운 보안 기술인가요?" → 완전히 새로운 마법의 기술이 아니다! 기존에 있던 훌륭한 기술(CSPM, CWPP, CIEM 등)을 하나의 플랫폼에 **결합(Consolidation)**하여, **맥락(Context)**을 파악하게 만든 융합 아키텍처다.

## 연결 개념
- **CSPM (클라우드 보안 형상 관리)**: 클라우드 인프라(AWS/Azure)의 설정 오류(예: S3 버킷 퍼블릭 오픈)를 찾아주는 도구. CNAPP의 한쪽 팔.
- **CWPP (클라우드 워크로드 보호 플랫폼)**: 컨테이너(Docker), 서버리스(Lambda) 등 앱이 실행되는 환경의 취약점을 막아주는 도구. CNAPP의 또 다른 팔.
- **Shift-Left (시프트 레프트)**: 배포된 후가 아니라 코딩/빌드 단계부터 보안을 점검하는 철학. CNAPP가 완벽해지려면 운영(오른쪽)뿐만 아니라 개발(왼쪽) 단계까지 스캔할 수 있어야 한다.

# 📝 【답안용】 시험 답안 템플릿

## 핵심 인사이트 (3줄 요약)
> 1. **본질**: CNAPP(Cloud Native Application Protection Platform)는 CSPM(인프라 설정), CWPP(워크로드 보호), CIEM(계정 권한) 등 파편화된 클라우드 보안 도구들을 단일 플랫폼으로 통합(Consolidation)한 차세대 보안 아키텍처이다.
> 2. **가치**: 이기종 보안 솔루션이 유발하는 극심한 '알림 피로(Alert Fatigue)'를 해소하고, 여러 취약점이 결합될 때 발생하는 **'위해 맥락(Attack Path Context)'**을 분석하여 보안팀이 가장 치명적인 위험부터 조치할 수 있게 돕는다.
> 3. **판단 포인트**: 기존 개별 포인트 솔루션(Point Solution)의 한계를 지적하고, CNAPP를 구성하는 핵심 컴포넌트(CSPM+CWPP+CIEM)의 결합 시너지와 Shift-Left 개발 주기 연동 방안을 제시해야 한다.

## Ⅰ. 개요 및 필요성
- **정의**: 클라우드 네이티브 애플리케이션의 전체 생명주기(Build-Deploy-Run)에 걸쳐 위협을 식별, 평가, 방어하는 통합 클라우드 보안 플랫폼 (Gartner)
- **배경**: MSA, 컨테이너, 서버리스 등 클라우드 아키텍처의 복잡성 증가. 개별 보안 솔루션(Silo) 난립으로 인한 보안 사각지대(Blind Spot) 및 수만 개의 오탐 경고 발생
- **필요성**: 파편화된 클라우드 보안 가시성 일원화, 리스크의 우선순위 도출(Context-aware), DevSecOps(Shift-Left) 체계와의 매끄러운 연동

## Ⅱ. 기존 보안 체계의 한계 vs CNAPP의 패러다임 전환
단순한 '기능의 합'이 아니라 '위협 맥락의 이해'가 CNAPP의 핵심이다.

| 구분 | 기존 개별 포인트 솔루션 (Point Solutions) | 통합 플랫폼 (CNAPP) |
|:---|:---|:---|
| **가시성** | 인프라(CSPM) / 앱(CWPP) 대시보드 분리 | 단일 대시보드(Single Pane of Glass) |
| **경고 방식** | 각 솔루션이 개별적으로 수백 개의 경고 발생 | 데이터를 교차 분석하여 **치명적 공격 경로(Attack Path) 1개로 압축** |
| **위협 인지** | "여기에 취약점이 있다" (정적 인지) | "이 취약점이 탈취되면 저 DB까지 뚫린다" (맥락 인지) |
| **조직/비용**| 부서별 별도 솔루션 구매, 과도한 라이선스 비용 | 단일 벤더 구매(Consolidation), TCO 절감 및 보안/개발팀 협업 강화 |

## Ⅲ. CNAPP를 구성하는 3대 핵심 컴포넌트
CNAPP = CSPM + CWPP + CIEM (+ 기타 보안 요소)의 융합이다.

1. **CSPM (Cloud Security Posture Management) - 인프라/설정 보안**
   - AWS, Azure 인프라의 설정 오류(예: S3 버킷 공개, 암호화 미적용)를 탐지하고 컴플라이언스(ISMS-P, GDPR) 위반 여부를 검사
2. **CWPP (Cloud Workload Protection Platform) - 런타임/앱 보안**
   - VM, 컨테이너, 서버리스 등 워크로드 내부에서 실행되는 악성코드 탐지 및 런타임 공격(예: 랜섬웨어, 코인 채굴) 방어
3. **CIEM (Cloud Infrastructure Entitlement Management) - 권한 보안**
   - IAM 계정 및 기계 계정(Service Account)의 과도한 권한(Over-privileged)을 식별하고 최소 권한의 원칙(Least Privilege)을 강제 적용

## Ⅳ. CNAPP의 핵심 메커니즘: 그래프 기반 맥락 분석 (Context Graph)
CNAPP가 알람 지옥을 해결하는 마법은 **'공격 표면 그래프(Attack Graph)'** 기술에 있다.
- **원리**: 인프라 설정(오픈된 포트), 취약한 워크로드(오래된 라이브러리), 과도한 권한(Admin 롤)이라는 점(Node)들을 선(Edge)으로 연결하여 분석한다.
- **효과**: 해커가 외부에서 시작해 핵심 데이터베이스에 도달할 수 있는 '공격 경로(Attack Path)'를 시각적으로 그려주고, "이 중간의 컨테이너 하나만 패치하면 공격 경로가 끊어집니다"라고 **가장 가성비 좋은 조치 방법(Prioritization)**을 알려준다.

## Ⅴ. 기술적 한계(리스크) 및 해결 방안
| 리스크 요인 | 현상 및 문제점 | 대응 방안 (엔지니어링 가이드) |
|:---|:---|:---|
| **빅 브라더(단일 벤더) 종속** | 단일 CNAPP 벤더(예: Wiz, Palo Alto)에 클라우드의 모든 보안을 의존하게 되어, 벤더 Lock-in 리스크 발생 | CNAPP 도입 시 글로벌 개방형 표준(OpenTelemetry 등) 연동을 지원하고 멀티 클라우드 환경을 100% 커버하는지 검증 필수 |
| **운영 중심(Right-side)의 한계** | 앱이 이미 클라우드에 배포된 후(Run)에만 취약점을 찾게 되어, 수정 비용(Rework Cost) 기하급수적 증가 | **Shift-Left 연동**: CI/CD 파이프라인(GitHub Actions, Jenkins) 단계에 CNAPP 스캐너를 통합(플러그인)하여, 빌드 전 IaC(Terraform) 코드를 사전 검사 |

## Ⅵ. 실무 적용 및 결론
**적용 방안 및 실무 가이드:**
1. **Agentless(에이전트리스) 기반 스캔 도입**: 컨테이너마다 보안 에이전트를 설치(CWPP)하면 성능 저하가 심하다. 최근 CNAPP는 클라우드 API와 스냅샷(Snapshot)을 활용해 서버에 에이전트를 깔지 않고도 1분 만에 취약점을 스캔하는 Agentless 방식을 우선적으로 채택해야 한다.
2. **DevSecOps 파이프라인 통합**: 보안팀의 전유물이 아니라, CNAPP의 스캔 결과를 개발팀의 Jira 티켓이나 Slack 알람으로 즉시 연동되게 구성하여 보안 조치의 피드백 루프를 단축한다.

**결론:**
- CNAPP는 단순히 여러 보안 도구를 묶어 파는 패키지 상품이 아니라, 고도로 파편화된 클라우드 네이티브 환경에서 **'위협의 맥락(Context)'을 읽어내는 보안의 뇌(Brain)**이다.
- 무수히 많은 보안 알람 속에서 허우적대는 보안팀에게 '진짜 위험한 단 하나의 적'을 알려주는 CNAPP의 도입은, 속도와 안정성을 동시에 추구하는 현대 DevSecOps 생태계의 필수 불가결한 진화 방향이다.

|:---|:---|:---|:---|
| **클라우드 보안/아키텍처형**| "CSPM", "클라우드 보안 통합" | 개별 포인트 솔루션(Silo)의 한계점과 Ⅲ CSPM, CWPP, CIEM의 3대 구성요소 중심 서술 | Ⅳ 공격 경로 그래프(Attack Graph)를 통한 맥락(Context) 분석 메커니즘 전면 배치 |
