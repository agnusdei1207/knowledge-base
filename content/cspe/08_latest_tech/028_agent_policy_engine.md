# 📖 【암기용】 개념 완전 이해

> 목적: 에이전트 정책 엔진을 처음 봐도 완벽히 이해하게 만든다.

## 한눈에
- **정의**: AI 에이전트의 행동을 규칙·조건·한도로 통제하는 의사결정 계층
- **왜 필요한가**: 에이전트가 자율적으로 도구를 호출하므로 권한 초과·비용 폭증·민감 데이터 노출을 사전 차단해야 함
- **핵심 직관**: 회사 결재 규정처럼 "이 금액 이상은 상위 승인 필요, 이 시스템은 접근 불가"를 실시간 적용하는 엔진

## 깊이 이해
- **배경·문제의식**: 에이전트에게 도구 목록만 주고 정책 없이 실행하면, 프로덕션 DB 삭제·무한 API 호출·개인정보 외부 전송 같은 사고가 발생함
- **작동 원리**: ① 에이전트가 도구 호출 요청 ② 정책 엔진이 OPA/Rego 규칙으로 허용/거부/승인 필요 판정 ③ 허용이면 실행, 거부면 차단+로그, 승인 필요면 Human-in-the-loop ④ 실행 후 비용·호출 횟수를 누적 검증
- **비유**: 공항 보안 게이트처럼 모든 행동이 통과 전 검사를 받고, 위험물은 차단, 의심 항목은 추가 검사를 거침
- **구체 예시**: 결제 API 호출 시 정책 엔진이 "단건 100만원 이상 → Human Approval" 규칙을 적용하여 자동 분기
- **흔한 오해·주의점**: 정책을 너무 세밀하게 설정하면 모든 행동이 승인 대기에 빠져 자동화 효과가 사라짐. 위험도 등급별 차등 적용이 핵심

## 연결 개념
- 에이전트 가드레일 — 입출력 필터링(정책 엔진의 하위 실행 수단)
- RBAC/ABAC — 정책 규칙의 접근 제어 모델
- OPA(Open Policy Agent) — 정책 규칙 평가 엔진 구현체


# 📝 【답안용】 시험 답안 템플릿

> 목적: 시험장에서 25분에 그대로 쓰는 답안 양식.

## 핵심 인사이트 (3줄 요약)

> 1. **본질**: 정책 엔진은 에이전트의 모든 도구 호출을 규칙 기반으로 허용/거부/승인 분기하는 통제 계층임.
> 2. **가치**: 권한 초과 차단율 100%, 비용 한도 초과 방지, 민감 데이터 노출 사전 차단.
> 3. **판단 포인트**: 위험도 3등급(Low·Med·High)으로 분류하고 High만 Human Approval로 설계해야 자동화율 유지.


## Ⅰ. 개요 및 필요성

에이전트 정책 엔진은 AI 에이전트 행동의 규칙 기반 통제 계층임. 에이전트 자율성이 높아질수록 권한 오남용·비용 폭증·데이터 유출 위험이 증가하며, 모든 도구 호출 전 실시간 정책 평가가 필수적임.


## Ⅱ. 구조 및 구성요소

```text
Agent Request → Policy Evaluation → Decision
                     │                 │
              ┌──────┴──────┐    ┌─────┴─────┐
           Rule Store    Context   Allow/Deny/
          (OPA/Rego)    Enricher   Escalate
```

| 구성요소 | 역할 | 특이사항 |
|:---|:---|:---|
| Rule Store | 정책 규칙 저장·버전 관리 | OPA/Rego, JSON 정책, GitOps 배포 |
| Context Enricher | 요청에 사용자·세션·비용 컨텍스트 부착 | 누적 비용, 호출 횟수, 시간대 |
| Decision Engine | 규칙 평가 후 Allow/Deny/Escalate 판정 | 평가 지연 p99 <10ms |
| Audit Logger | 판정 결과·근거 규칙 기록 | 단일 Trace ID, 보관 90일 |

> 요약: 규칙 저장소와 컨텍스트를 결합해 실시간 판정하고, 모든 결과를 감사 로그로 기록함.


## Ⅲ. 동작원리 및 흐름도

```text
도구 호출 요청 → 컨텍스트 수집 → 규칙 평가(OPA)
→ Allow → 실행 → 비용 누적 검증
→ Deny → 차단 + 로그 + 에이전트 대안 안내
→ Escalate → Human Approval 대기 → 승인/거부
```

| 단계 | 처리 내용 | 검증 기준 |
|:---:|:---|:---|
| 1 | 도구 호출 요청 수신·컨텍스트 수집 | 사용자 ID, 역할, 누적 비용 |
| 2 | OPA/Rego 규칙 평가 | 평가 지연 p99 <10ms |
| 3 | 판정(Allow/Deny/Escalate) 실행 | Deny 시 차단 사유 로그 |
| 4 | 실행 후 비용·횟수 누적 검증 | 일일 한도 $100, 호출 500회 |

> 요약: 모든 도구 호출이 정책 평가를 통과한 후 실행되며, 사후에도 누적 한도를 검증함.


## Ⅳ. 특징

| 구분 | 정책 미적용 | 정책 엔진 적용 | 수치·판단 포인트 |
|:---|:---|:---|:---|
| 권한 통제 | 전체 허용 | RBAC+ABAC 규칙 평가 | 비인가 호출 차단율 100% |
| 비용 관리 | 무제한 | 일일·건당 한도 | 일일 $100, 건당 $10 |
| 감사 추적 | 로그 없음 | 판정+근거 규칙 기록 | 보관 90일, Trace ID 연동 |

> 요약: 정책 엔진은 권한·비용·감사를 실시간으로 통제하여 에이전트 자율 실행의 안전성을 보장함.


## Ⅴ. 실무 적용 및 결론

**적용 방안 3개:**
1. OPA/Rego로 도구별 RBAC·ABAC 규칙을 정의하고 GitOps로 정책을 버전 관리·배포
2. 위험도 3등급(Low 자동실행·Med 로그강화·High Human Approval)으로 분류하여 자동화율 85% 유지
3. 판정 결과를 OpenTelemetry Trace ID와 연동하여 감사로그 90일 보관

**결론 (2줄):**
- 기술사 판단: 조회·검색은 Low(자동), 데이터 변경은 Med(로그 강화), 결제·삭제는 High(승인)로 설계
- 향후 방향: LLM이 정책 규칙을 자연어로 해석·생성하는 Policy-as-Code 자동화로 발전함
