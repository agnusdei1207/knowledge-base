# 📖 【암기용】 개념 완전 이해

## 한눈에
- **개요**: 에이전트 정책 엔진은 AI 에이전트의 모든 **도구 호출·행동**을 **규칙 기반으로 허용·거부·승인 분기**하는 실시간 **의사결정 계층**이다. 권한통제(020)가 "이 에이전트가 이 도구를 쓸 자격이 있는가"의 RBAC/ABAC 판단이라면, 정책 엔진은 "이 호출의 맥락(금액·횟수·시간·누적 비용)에서 허용할 것인가"까지 동적으로 판단한다.
- **왜 필요한가**: 에이전트에게 도구 목록(027 레지스트리)을 주고 정책 없이 실행하면, 프로덕션 DB 삭제·무한 API 호출·개인정보 외부 전송 같은 사고가 발생한다. 정책 없이 자율 실행하면 권한 초과·비용 폭증·민감 데이터 노출을 사전 차단할 수 없다.
- **핵심 직관**: 회사 결재 규정과 같다. "100만원 미만은 팀장 결재, 100만원 이상은 임원 결재, 1,000만원 이상은 대표 결재"처럼 금액·위험도에 따라 자동/승인/차단을 실시간으로 분기한다.

## 핵심 용어 정리 (내부에 등장하는 것들)

| 용어/표기 | 의미 | 비유·예 |
|:---|:---|:---|
| 정책 엔진(상위 키워드) | 규칙을 평가해 허용·거부·에스컬레이션을 실시간 판정하는 시스템 | 공항 보안 게이트 |
| OPA(Open Policy Agent) | CNCF 오픈소스 정책 평가 엔진. Rego 언어로 규칙을 작성 | 보안 검색대의 X-ray 기계 |
| Rego | OPA의 선언형 정책 언어. 조건·논리를 코드로 정의 | X-ray 판독 규칙서 |
| Context Enricher | 요청에 사용자·세션·누적 비용·시간대 컨텍스트를 부착하는 모듈 | 승객 정보를 탑승권에 추가 |
| Allow/Deny/Escalate | 정책 판정 결과의 3가지 유형 | 통과/차단/추가 검사 |
| GitOps 정책 배포 | 정책 규칙을 Git으로 버전 관리하고 PR 승인 후 배포 | 법률 개정안 심의·공포 |
| 일일 비용 한도(Budget Cap) | 에이전트별 하루 최대 사용 비용 | 법인카드 일일 한도 |
| 건당 비용 한도 | 단일 도구 호출의 최대 비용 | 1회 결제 한도 |

## 깊이 이해
- **배경·문제의식**: 도구 레지스트리(027)가 "어떤 도구를 선택하는가"를 관리하고, 권한통제(020)가 "사용 자격이 있는가"를 판단한다면, 정책 엔진은 "이 맥락에서 이 행동을 허용하는가"를 동적으로 결정한다. 예를 들어 결제 에이전트가 결제 API 호출 권한(020)을 가지고 있더라도, 단건 100만원 이상이면 사람 승인을 요구하고, 일일 누적 500만원을 넘으면 자동 차단하는 것이 정책 엔진의 역할이다.
- **작동 원리(어떻게+왜)**: ① 에이전트가 도구 호출을 요청하면 Context Enricher가 {사용자 ID, 에이전트 역할, 도구 위험등급, 누적 비용, 호출 횟수, 시간대}를 부착한다. ② Decision Engine이 OPA/Rego 규칙으로 평가한다. 예: `deny if { input.cost > 1000000 AND input.approval == false }`. ③ 결과가 Allow면 도구를 실행하고, Deny면 차단+차단 사유를 로그에 기록하며 에이전트에 대안을 안내한다. Escalate면 HITL(022) 승인 대기로 분기한다. ④ 실행 후에도 누적 비용·호출 횟수를 검증해 일일 한도 초과 시 이후 호출을 자동 차단한다.
- **비유**: 공항 보안 게이트와 같다. 모든 승객(도구 호출)이 보안 검색(정책 평가)을 통과해야 한다. 일반 짐(Low)은 X-ray만 통과하고, 의심 물품(Med)은 개봉 검사, 위험물(High)은 압수·보안관 호출(Escalate)한다.
- **구체 예시**: 결제 에이전트가 `payment_api.charge(amount=1,500,000)` 호출을 요청한다. Context Enricher가 {role: payment-agent, amount: 1,500,000, daily_total: 3,200,000, daily_limit: 5,000,000}을 부착한다. OPA 규칙: `escalate if amount > 1,000,000`. 판정: Escalate → 재무 담당자에게 승인 요청. 담당자 승인 후 실행, daily_total을 4,700,000으로 갱신한다.
- **흔한 오해·주의점**: "정책을 세밀하게 설정할수록 안전하다"는 함정이다. 모든 호출에 승인을 요구하면 자동화 효과가 사라지고(자동화율 <50%), 승인 피로로 형식적 승인이 증가한다. 위험등급 3등급(Low·Med·High) 차등 적용으로 Low는 자동 허용해야 자동화율 85%를 유지할 수 있다.

## 연결 개념
- 에이전트 권한통제(020) — PDP/PEP 기반 도구 호출 자격 판단. 정책 엔진은 자격+맥락 판단
- 에이전트 도구 레지스트리(027) — 도구 선택을 관리. 정책 엔진은 선택된 도구의 실행을 통제
- 에이전트 가드레일(029) — 입출력 필터링. 정책 엔진의 하위 실행 수단

# 📝 【답안용】 시험 답안 템플릿

## 핵심 인사이트 (3줄 요약)

> 1. **본질**: 정책 엔진은 에이전트 도구 호출을 OPA/Rego 규칙으로 실시간 Allow/Deny/Escalate 판정하는 통제 계층임.
> 2. **가치**: 비인가 호출 차단율 100%, 비용 한도 초과 방지, 위험등급별 승인 분기로 자동화율 85%를 유지함.
> 3. **판단 포인트**: Low(자동허용)·Med(로그강화)·High(Human Approval) 3등급 분류와 누적 비용 한도를 함께 설계해야 함.

## 출제 의도 및 답안 포인트

| 출제 의도 | 반드시 짚을 핵심 | 감점 회피 포인트 |
|:---|:---|:---|
| 에이전트 자율 행동의 통제 설계 | OPA/Rego, RBAC+ABAC, 위험등급 3등급, 감사 로그 | 전체 허용/전체 차단 이분법, 등급 분류 누락 |
| 자동화율과 안전성 균형 설계 | Low 자동 85%·Med 로그·High Approval 분기 | 모든 호출에 승인 요구(자동화 효과 상실) |

> 요약: 위험등급 3등급→OPA 규칙→등급별 판정 분기→감사 로그가 핵심 채점 축임.

---

## Ⅰ. 개요 및 필요성

- 개요: 에이전트 도구 호출을 OPA/Rego 규칙으로 실시간 허용·거부·승인 분기하는 통제 계층임
- 배경: 에이전트 자율성 증가로 권한 초과·비용 폭증·민감 데이터 노출 위험이 확대됨
- 필요성: 모든 도구 호출 전 실시간 정책 평가 없이는 비인가 차단율 100%와 비용 통제가 불가능함

---

## Ⅱ. 구조 및 구성요소

```text
에이전트 요청 -> Context Enricher(맥락 부착)
  -> Decision Engine(OPA/Rego 규칙 평가)
     -> Allow: 실행 -> 누적 비용 검증
     -> Deny: 차단 + 사유 로그 + 대안 안내
     -> Escalate: HITL 승인 대기
  -> Audit Logger(판정·근거 기록)
```

| 구성요소 | 역할 | 특이사항 |
|:---|:---|:---|
| Rule Store | OPA/Rego 정책 규칙 저장·버전 관리 | GitOps 배포, PR 승인 후 반영 |
| Context Enricher | 요청에 누적 비용·역할·시간대 부착 | 실시간 컨텍스트 수집 |
| Decision Engine | 규칙 평가 후 Allow/Deny/Escalate 판정 | 평가 지연 p99 <10ms |
| Audit Logger | 판정 결과·적용 규칙·사유 기록 | Trace ID 연동, 보관 90일 |

> 요약: 맥락 수집→OPA 규칙 평가→판정 분기→감사 기록의 실시간 통제 파이프라인임.

---

## Ⅲ. 동작원리 및 흐름도

```text
도구 호출 요청 -> 컨텍스트 수집(역할/비용/횟수/시간)
  -> OPA/Rego 규칙 평가 -> Allow/Deny/Escalate 판정
  -> 실행 후 누적 비용·횟수 검증 -> 한도 초과 시 자동 차단
```

1. 컨텍스트 수집: 요청에 {사용자 ID, 에이전트 역할, 도구 위험등급, 누적 비용, 호출 횟수, 시간대}를 부착함
2. 규칙 평가: OPA/Rego로 위험등급·금액·누적치를 평가해 Allow(Low)/Deny(위반)/Escalate(High) 판정함
3. 판정 실행: Allow면 도구 실행, Deny면 차단+사유 로그+대안 안내, Escalate면 HITL(022) 승인 대기로 분기함
4. 사후 검증: 실행 후 누적 비용·호출 횟수를 갱신하고, 일일 한도 초과 시 이후 호출을 자동 차단함

> 요약: 컨텍스트 수집→OPA 평가→판정 분기→사후 검증으로 실시간 통제와 누적 관리를 수행함.

---

## Ⅳ. 특징

- 실시간 판정: 모든 도구 호출 전 p99 <10ms로 정책을 평가해 지연 없이 통제함
- 3등급 분기: Low(자동허용)·Med(로그강화)·High(Human Approval)로 자동화율 85%를 유지함
- 누적 관리: 일일 비용·호출 횟수를 실시간 추적해 한도 초과를 사전 차단함
- GitOps 배포: 정책 규칙을 Git으로 버전 관리하고 PR 승인 후 배포해 무관리 변경을 방지함
- 감사 연동: 모든 판정 결과·적용 규칙·사유를 Trace ID로 감사 로그에 기록함

---

## Ⅴ. 심화 비교 및 적용 판단

| 구분 | 정책 미적용 | 정책 엔진 적용 | 선택 기준 |
|:---|:---|:---|:---|
| 권한 통제 | 전체 허용(비인가 미차단) | OPA RBAC+ABAC 규칙 평가 | 민감 API·프로덕션 DB 접근 시 필수 |
| 비용 관리 | 무제한(예측 불가) | 일일 한도·건당 한도 적용 | 일일 에이전트 비용 $50 이상 시 필수 |
| 감사 추적 | 로그 없음(사후 추적 불가) | 판정+근거 규칙 기록(90일 보관) | 금융·의료 등 규제 산업 시 필수 |

> 요약: 민감 API·비용 $50+·규제 산업 조건 중 하나 이상이면 정책 엔진 도입이 필수임.

**리스크·대응:**
- 과잉 차단: 규칙 과도 설정 → 위험등급 3등급 차등 적용, Low는 자동 허용 (지표: 자동화율 85% 이상)
- 규칙 우회: 정책 미적용 경로 존재 → 모든 도구 호출을 정책 엔진 게이트웨이 경유로 강제 (지표: 우회 호출률 0%)
- 판정 지연: OPA 평가 부하 증가 → 규칙 캐싱(TTL 60초), OPA 인스턴스 수평 확장 (지표: p99 <10ms)

**도입 후 점검 지표:**
- 비인가 차단율: 100% — ACL 통과/차단 로그 비율 주간 감사
- 자동화율: 85% 이상 — 전체 판정 중 Allow 비율

---

## Ⅵ. 실무 적용 및 결론

**적용 방안 3개:**
1. OPA/Rego로 도구별 RBAC·ABAC·비용 한도 규칙을 정의하고 GitOps로 정책을 버전 관리·배포함
2. Low(조회·검색) 자동 허용·Med(데이터 변경) 로그 강화·High(결제·삭제) Human Approval로 3등급 분류함
3. 판정 결과를 OpenTelemetry Trace ID와 연동해 감사 로그 90일 보관하고, 누적 비용을 실시간 모니터링함

**결론:**
- 기술사 판단: 조회·검색은 Low 자동, 데이터 변경은 Med 로그, 결제·삭제는 High 승인으로 설계함
- 향후 방향: LLM이 정책 규칙을 자연어로 해석·생성하는 Policy-as-Code 자동화로 발전함
