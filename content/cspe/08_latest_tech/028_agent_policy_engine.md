## Ⅰ. 개요
- **정의**: 에이전트의 도구 호출·파라미터를 사전 정의된 비즈니스 규칙과 대조하여 결정론적 코드로 Allow/Deny를 판별하는 행동 통제 미들웨어
- **배경/필요성**: LLM은 확률 모델이므로 시스템 프롬프트만으로 100% 규칙 준수를 수학적으로 보장 불가하며, 프롬프트 인젝션 1회로 모든 Soft 제약이 무력화되는 구조적 취약점이 존재함
- **비유**: 은행 창구 직원(LLM)이 아무리 규정을 숙지해도, 출금 한도를 물리적으로 차단하는 전산 시스템이 별도로 필요한 것과 유사

| 출제 의도 | 반드시 짚을 핵심 | 감점 회피 포인트 |
|:---|:---|:---|
| 프롬프트 기반 Soft 통제 vs 코드 기반 Hard 통제 구분 | Policy as Code(OPA/Rego) + Interception 아키텍처 | 029 가드레일(의미론적 필터)과의 역할 분리 미서술 시 감점 |

> 요약: 정책 엔진은 LLM 외부에서 결정론적 코드로 에이전트 행동을 강제 통제하는 Hard Guardrail임

## Ⅱ. 구성요소
```text
+------------------------------------------------------------------+
|                      Policy Engine Layer                          |
|  +------------+    +------------+    +----------+    +----------+ |
|  | Policy     |--->| Interceptor|--->| Evaluator|--->| Enforcer | |
|  | Repository |    | (Proxy)    |    | (Rego)   |    | (Block/  | |
|  |            |    |            |    |          |    |  Allow)  | |
|  +------------+    +------------+    +----------+    +----------+ |
|   규칙 저장소       트래픽 가로채기   규칙 대조 평가    강제 집행     |
+------------------------------------------------------------------+
```

| 구성요소 | 설명 | 비유 |
|:---|:---|:---|
| Policy Repository | 비즈니스 룰을 Rego·JSON·YAML 등 코드로 정의하여 버전 관리(Git) 저장 | 법률 조문 데이터베이스 |
| Interceptor | 에이전트→도구 간 트래픽을 프록시로 가로채어 정책 엔진으로 라우팅 | 검문소 출입 게이트 |
| Evaluator | 도구명·파라미터를 정책 코드와 결정론적으로 대조(if amount < 20000 → DENY) | 규정 대조 심사관 |
| Enforcer | Allow 시 도구 서버로 전달, Deny 시 차단 후 위반 사유를 에이전트에 피드백 | 차단기 + 사유 통보서 |

> 요약: 저장소→가로채기→대조→집행의 4계층으로 결정론적 행동 통제 수행

## Ⅲ. 절차
```text
+----------+     +----------+     +----------+     +----------+
| 에이전트  |---->| 트래픽   |---->| 정책     |---->| 집행     |
| 행동 요청 |     | 가로채기 |     | 대조평가 |     | Allow/   |
| (Action) |     | (Proxy)  |     | (Rego)   |     | Deny     |
+----------+     +----------+     +----------+     +----------+
                                                        |
                   Deny 시 에이전트에 위반 사유 피드백 <---+
```

1. **정책 정의(Policy as Code)** — 보안팀·법무팀이 비즈니스 규칙을 OPA Rego 언어로 코드화하여 Git 저장소에 커밋, CI/CD로 엔진에 배포
2. **트래픽 가로채기(Interception)** — 에이전트가 도구 호출 또는 최종 출력을 생성할 때, 오케스트레이터가 해당 요청을 정책 엔진 프록시로 전달
3. **결정론적 평가(Evaluation)** — 엔진이 도구명·파라미터·사용자 컨텍스트를 정책 코드와 수학적으로 비교(LLM 미사용, 100% 재현 가능)
4. **강제 집행(Enforcement)** — Allow 판정 시 실제 API 서버로 트래픽 전달, Deny 시 즉시 차단 후 위반 정책명·사유를 에이전트 컨텍스트에 주입

> 요약: 코드 정의→가로채기→대조→집행 파이프라인으로 LLM 판단과 규칙 집행을 완전 분리

## Ⅳ. 문제점
- **정책 작성 난도**: Rego 등 전용 언어 학습 부담으로 법무팀·비즈니스 부서의 직접 참여 곤란 — 개발팀 병목
- **과잉 차단(False Positive)**: 정책이 지나치게 보수적이면 정상 요청까지 Deny하여 에이전트 가용성 저하 — 규칙 세분화 부족
- **정책 드리프트**: 비즈니스 규칙 변경 시 코드 업데이트 지연으로 현행 규정과 엔진 간 불일치 발생 — 동기화 프로세스 부재

> 요약: 정책 작성 난도, 과잉 차단, 규칙-코드 불일치가 정책 엔진의 3대 과제임

## Ⅴ. 개선방안
1. 단기: 자연어→Rego 자동 변환 LLM 파이프라인 도입(법무팀이 한글 규칙 입력 → AI가 Rego 코드 생성 → 보안팀 리뷰)
2. 중기: 정책별 Allow/Deny 비율 대시보드 구축 + False Positive 임계치(5%) 초과 시 자동 알림 → 규칙 세분화 유도
3. 장기: 규정 문서(사내 위키)와 Rego 코드 간 자동 동기화 CI/CD 구축(규정 변경 PR → Rego 자동 생성 → 테스트 → 배포)

- **작성 난도**: NL-to-Rego 변환 + 인간 리뷰 이중 체계 (지표: 정책 등록 소요 시간 48h → 4h)
- **과잉 차단**: 정책별 Deny 로그 분석 → 예외 화이트리스트 세분화 (지표: False Positive율 < 5%)
- **정책 드리프트**: 규정 문서 변경 시 자동 PR 생성 + 정책 커버리지 테스트 필수화 (지표: 규정-코드 일치율 > 98%)

> 요약: 자동 코드 생성·모니터링·동기화 CI/CD로 정책 엔진 운영 부담 해소

## Ⅵ. 전망
- 향후 발전 방향: 정적 Rule 기반에서, 실시간 컨텍스트(시간대·사용자 행동 패턴·위험 점수)를 반영하는 Adaptive Policy로 진화하며, 가드레일(029번 참조)과 통합된 심층 방어(Defense-in-Depth) 아키텍처로 수렴
- 기술사적 판단: 정책 엔진은 '의미론적 필터(가드레일)'과 상호 보완 관계이며, 행동(도구 호출)은 정책 엔진이, 언어(입출력 텍스트)는 가드레일이 담당하는 관심사 분리가 엔터프라이즈 AI 보안의 표준 패턴임
- 기술사 제언: OPA 기반 정책 엔진을 에이전트 오케스트레이터와 도구 서버 사이에 독립 계층으로 배치하고, Allow/Deny 로그를 관측성(030번 참조) 파이프라인과 연동하여 감사 추적성을 확보할 것
