# 📖 【암기용】 개념 완전 이해

> 목적: Experiment Tracking을 처음 봐도 완벽히 이해하게 만든다. 시험 답안 양식이 아니라, 이해를 위한 친절한 설명이다.

## 한눈에
- **개요**: 머신러닝 모델을 개발하는 과정에서 시도한 수많은 실험의 조건(파라미터, 코드)과 결과(지표, 차트)를 자동으로 기록하고 비교하는 활동
- **왜 필요한가**: 모델 성능을 올리려 수백 번 실험하다 보면, "어제 성능이 좋았던 그 모델 설정이 뭐였지?" 하고 잊어버리거나 동료의 결과를 재현하지 못하는 혼란을 막기 위함
- **핵심 직관**: 요리사가 최고의 맛을 찾기 위해 소금 양, 불 세기, 조리 시간을 매번 꼼꼼히 기록하고 결과를 시식평으로 남기는 "디지털 실험 일지"

## 깊이 이해
- **배경·문제의식**: 데이터 과학은 반복적인 실험의 산물이다. 예전에는 엑셀에 손으로 기록하거나 파일명에 성능을 적었다(ex: model_acc0.92.pkl). 하지만 실험 횟수가 많아지고 팀원이 늘어나면 관리가 불가능해진다. 특히 결과는 있는데 원인이 된 코드 버전이나 데이터 셋을 모르면 그 모델은 "우연의 산물"이 되어 실무에 쓸 수 없게 된다.
- **작동 원리**: 코드에 몇 줄의 로깅 명령어(ex: `log_param`, `log_metric`)를 추가하면, 실험이 실행될 때마다 중앙 서버로 하이퍼파라미터(학습률, 배치 크기 등), 성능 지표(Accuracy, Loss), 시각화 결과(Confusion Matrix)가 전송된다. 이후 웹 대시보드에서 여러 실험을 한눈에 비교하고 최적의 조합을 찾는다.
- **비유**: 운동선수가 체력 향상을 위해 매일 식단, 운동량, 수면 시간을 스마트워치와 앱에 기록하고 한 달간의 변화 그래프를 보며 훈련 강도를 조절하는 것과 같다.
- **구체 예시**: Weights & Biases(W&B)를 사용하여 GPU 사용량과 학습 곡선을 실시간으로 모니터링한다. 특정 파라미터 조합에서 모델이 발산(Divergence)하는 것을 확인하고 조기에 실험을 중단(Early Stopping)하여 비용을 절감한다.
- **흔한 오해·주의점**: "실험 추적은 모델 저장(Registry)과 같다"라고 생각할 수 있으나, 실험 추적은 '시행착오의 과정'을 기록하는 것이고, 모델 레지스트리는 그중 선택된 '최종 결과물'을 관리하는 것이다.

## 연결 개념
- Hyperparameter Tuning — 실험 추적을 통해 최적의 값을 찾아가는 과정
- Reproducibility (재현성) — 실험 추적의 가장 큰 궁극적 목적
- Model Registry — 실험 추적 중 선별된 우수 모델이 넘어가는 다음 단계

# 📝 【답안용】 시험 답안 템플릿

> 목적: 시험장에서 25분에 그대로 쓰는 답안 양식. 작성방식(추상표현 금지·수치·도식·문제유형 전환)을 엄격히 지킨다.

## 핵심 인사이트 (3줄 요약)

> 1. **본질**: Experiment Tracking은 ML 모델 학습 과정의 모든 메타데이터(코드·파라미터·지표)를 자동 로깅하고 시각화하여 비교 분석하는 활동이다.
> 2. **가치**: 실험의 투명성과 재현성을 확보하고, 협업 시 중복 실험을 방지하며 최적의 하이퍼파라미터 조합을 신속히 도출한다.
> 3. **판단 포인트**: 정적 지표 기록뿐만 아니라 학습 곡선(Learning Curve)과 시스템 리소스(GPU/MEM)의 실시간 모니터링 연계가 중요하다.

## 출제 의도 및 답안 포인트

| 출제 의도 | 반드시 짚을 핵심 | 감점 회피 포인트 |
|:---|:---|:---|
| ML 개발 프로세스 표준화 역량 확인 | 로깅 자동화, 재현성(Reproducibility), 하이퍼파라미터 비교 | 단순히 "실험 결과 기록"이라고만 서술 |
| MLOps 생명주기 내 위치 이해 확인 | 실험 단계(Exploration)와 배포 단계(Registry)의 구분 | 모델 레지스트리와 혼동하여 서술 |
| 협업 및 효율성 제고 능력 확인 | 대시보드 공유, 자원 사용 최적화, 실험 이력 자산화 | 기술적 요소(Git Hash, Dataset ID) 누락 |

> 요약: 무수한 실험 데이터를 체계화하여 모델 개선의 근거를 마련하고 팀 내 지식 공유를 활성화하는 체계 제시가 핵심이다.

## Ⅰ. 개요 및 필요성

- 정의: 머신러닝 실험의 재현성을 보장하기 위해 학습 시의 입력(코드, 데이터, 설정)과 출력(지표, 아티팩트)을 기록하고 관리하는 체계
- 배경: 실험 횟수 증가에 따른 관리 복잡도 심화, 팀 단위 협업 시 실험 이력 공유 부재로 인한 비효율 발생
- 필요성: 성능 개선 원인 분석을 위한 투명성 확보, 실패한 실험으로부터의 학습(Lessons Learned), 자원 사용 효율화

## Ⅱ. 구조 및 구성요소

```text
Training Script -> Tracking API (Log) -> Central Tracking Server (Storage)
      |                  |                        |
      +-> Git Hash       +-> Params/Metrics       +-> Dashboard (Compare)
      +-> Dataset Version+-> Artifacts            +-> Reports
```

| 구성요소 | 역할 | 특이사항 |
|:---|:---|:---|
| Tracking Server | 실험 데이터 수집 및 저장 허브 | MLflow Tracking, W&B 등 |
| Metadata | 하이퍼파라미터, 환경 설정, 지표 | Key-Value 형태 저장 |
| Artifact Store | 모델 가중치, 차트, 데이터 샘플 저장 | S3, GCS 등 대용량 저장소 |
| Visualization UI | 실험 간 비교 및 학습 곡선 대시보드 | Parallel Coordinates 등 활용 |

> 요약: 학습 스크립트와 연동된 API를 통해 메타데이터와 아티팩트를 수집하고 UI로 분석함.

## Ⅲ. 동작원리 및 흐름도

```text
실험 환경 설정 -> 로깅 라이브러리 초기화 -> 학습 루프 실행 -> 매 에포크별 지표 전송 -> 실험 종료 및 요약 기록 -> 대시보드 비교 분석
      |                 |                   |                 |                       |                       |
      +-----------------+-------------------+-----------------+-----------------------+-----------------------+-----> Best 모델 선정
```

| 단계 | 처리 내용 | 검증 기준 |
|:---:|:---|:---|
| 1 | 실험 컨텍스트 로깅 | Git 커밋 해시, 데이터셋 버전 포함 |
| 2 | 파라미터 및 하이퍼파라미터 기록 | Learning Rate, Batch Size 등 |
| 3 | 실시간 지표(Metrics) 추적 | Epoch당 Loss, Accuracy 기록 |
| 4 | 실험 비교 및 결과 자산화 | 리더보드(Leaderboard) 생성 |

> 요약: 코드 및 데이터의 정적 상태와 학습 과정의 동적 지표를 실시간으로 연결하여 기록함.

## Ⅳ. 특징

| 구분 | 수동 기록 (Excel/파일명) | Experiment Tracking Tool | 판단 포인트 |
|:---|:---|:---|:---|
| 자동화 | 매우 낮음 (인적 오류 빈번) | 높음 (SDK/API 자동 전송) | 신뢰성 및 생산성 |
| 재현성 | 보장 불가 (환경 정보 누락) | 높음 (Git/Dataset 버전 결합) | 과학적 엄밀성 |
| 시각화 | 수동 차트 작성 필요 | 실시간 대시보드 자동 생성 | 분석 신속성 |
| 협업 | 파일 공유 형태 (파편화) | 중앙 서버 기반 실시간 공유 | 팀 생산성 |

> 요약: Experiment Tracking은 ML 개발을 개인의 감이 아닌 데이터 기반의 체계적인 공학 프로세스로 전환함.

| 시각화 기능 | 표준적 (기본 차트) | 강력함 (Deep Analysis 툴) | 분석 정교함 요구 수준 |
| 데이터 보안 | 폐쇄망 구축 가능 (유리) | 클라우드 전송 (검토 필요) | 보안 규정 및 정책 |

> 요약: 인프라 통제가 중요한 폐쇄망 환경은 MLflow를, 빠른 도입과 풍부한 분석 기능이 우선이면 W&B를 선택함.

| 리스크 | 원인 | 대응 방안 | 확인 지표 |
|:---|:---|:---|:---|
| 로깅 오버헤드 | 과도한 실시간 지표 전송 | 로깅 주기 조절 및 비동기 전송 | 학습 속도 저하율 < 5% |
| 데이터 스토리지 폭증 | 대량의 아티팩트(이미지 등) 저장 | 보관 정책 설정 및 선별적 저장 | 스토리지 사용량 및 비용 |
| 재현 불가능 실험 | 하드웨어/라이브러리 버전 누락 | Docker 컨테이너 정보 자동 기록 | 동일 조건 재현 성공률 |

> 요약: 로깅 부하는 주기 조절로, 저장소 비용은 정책 관리로, 재현 실패는 환경 정보 기록으로 대응함.

| 점검 항목 | 목표 기준 | 측정 방법 |
|:---|:---|:---|
| 실험 재현 가능성 | 주요 실험 재현 성공률 100% | 과거 실험 조건 재실행 결과 대조 |
| 분석 효율성 | 실험 간 비교 보고서 생성 10분 이내 | UI상 자동 리포트 생성 기능 활용 |
| 실험 자산화 | 퇴사/인사이동 시 업무 인계 가능 | 실험 로그의 가독성 및 문서화 수준 |

> 요약: 도입 효과는 실험의 무결점 재현, 분석 신속성, 팀 내 지식 자산화 수준으로 측정함.

## Ⅵ. 실무 적용 및 결론

**적용 방안 3개:**
1. 재현성 보장: 모든 실험에 `git_commit_hash`와 `dataset_version`을 태깅하여 6개월 전 실험도 동일하게 100% 재현 가능하게 구성
2. 최적화 가속: 파라미터별 성능 분포를 시각화하는 'Parallel Coordinates Plot'을 활용하여 하이퍼파라미터 튜닝 시간을 30% 단축
3. 리소스 최적화: 학습 중 GPU 온도 및 메모리 사용량을 실시간 추적하여 인프라 병목을 제거하고 작업 스케줄링 효율화

**결론 (2줄):**
- 기술사 판단: Experiment Tracking은 "예술"로 치부되던 모델링 과정을 "데이터 기반의 투명한 공정"으로 바꾸는 MLOps의 첫 단추임
- 향후 방향: 모델의 편향성이나 탄소 배출량(Carbon Footprint) 같은 ESG 지표까지 자동으로 기록하는 형태로 책임감 있는 AI 개발 지원
