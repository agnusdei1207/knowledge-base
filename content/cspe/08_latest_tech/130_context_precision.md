# 📖 【암기용】 개념 완전 이해

## 한눈에
- **정의**: RAG의 1차 검색기(Retriever)가 찾아온 문서들(Top-K) 중에서, **"질문에 진짜 필요한 알짜배기 문서들이 쓰레기 문서들보다 윗순위(상위 랭크)에 제대로 잘 배치되어 있는가?"**를 평가하는 지표.
- **필요성**: 아무리 정답 문서를 찾아왔어도, 1~9등이 엉뚱한 문서고 정답이 10등에 처박혀 있으면 LLM은 앞부분의 엉뚱한 정보에 휘둘려 오답을 내뱉음(Lost in the middle 현상). 정답 문서가 맨 위에 꽂혀야 함!
- **핵심 직관**: 구글 검색과 같음. '근처 맛집'을 검색했는데, 1페이지 최상단(Top-1)에 진짜 맛집이 뜨면 정밀도(Precision) 만점. 1페이지엔 광고만 뜨고 3페이지 구석에 맛집이 있으면 정밀도 꽝.

## 깊이 이해
- **배경**: 초기 검색 평가는 단순 재현율(Recall: 100개 중에 1개라도 가져왔나?)에 집중했으나, LLM 컨텍스트 윈도우의 집중력 한계 때문에 '순위(Ranking)'의 품질이 RAG 답변의 성패를 가른다는 사실이 밝혀지며 도입됨.
- **작동 원리 (순위 가중치 평가)**:
  1. 평가기가 사용자의 질문과 그 정답(Ground Truth)을 미리 알고 있음.
  2. RAG 검색기가 5개의 문서 청크(Top-5)를 가져옴.
  3. 평가기는 1등부터 5등 문서까지 순서대로 보면서, 정답을 맞히는 데 쓸모 있는 문서인지(Hit) 쓸모없는지(Miss) 판별.
  4. 수학 공식을 써서 점수를 매김. 정답 문서가 1등에 있으면 가중치 최고점, 5등에 있으면 가중치 꼴찌를 부여하여 최종 $0 \sim 1$ 사이의 점수로 환산함.
- **구체 예시**:
  - 케이스 A: `[쓸모있음, 쓸모없음, 쓸모없음, 쓸모없음, 쓸모없음]` $\rightarrow$ 정답 문서가 1등! (Precision = 1.0)
  - 케이스 B: `[쓸모없음, 쓸모없음, 쓸모없음, 쓸모없음, 쓸모있음]` $\rightarrow$ 정답 문서를 찾긴 찾았는데 5등에 박혀있음! (Precision = 0.2)
- **흔한 오해/주의점**: 이 지표가 낮게 나왔다고 프롬프트나 LLM을 튜닝하는 건 바보짓임. 이 지표는 100% 검색 엔진(Vector DB, 임베딩 모델)과 랭킹(Reranker) 시스템의 성적표임. 검색쪽 인프라를 뜯어고쳐야 함.

## 연결 개념
- **Context Recall (문맥 재현율)**: 쌍둥이 지표. "정답을 맞히는 데 필요한 조각을 하나라도 빠짐없이 다 가져왔는가?"를 평가함 (순위 상관없음).
- **Reranker (리랭커)**: Context Precision 점수가 낮을 때, 이걸 멱살 잡고 단번에 최고점으로 끌어올려 주는 해결사 딥러닝 모델.
- **MRR (Mean Reciprocal Rank) / NDCG**: 고전 정보 검색 시절부터 순위의 퀄리티를 매기던 근본 수학 공식들. Context Precision의 뼈대.

# 📝 【답안용】 시험 답안 템플릿
## 핵심 인사이트 (3줄 요약)
- **본질**: RAG 검색 파이프라인에서 추출된 문맥 뭉치(Retrieved Contexts) 중, Ground Truth(정답) 도출에 기여하는 유효한 컨텍스트가 얼마나 상위 랭킹(High Rank)에 배치되어 있는지를 가중 연산하는 정보 검색(IR) 정밀도 지표.
- **가치**: LLM의 어텐션(Attention) 기전이 컨텍스트의 앞부분에 치중되는 현상(Lost in the middle)을 극복하기 위해, 프롬프트 최상단에 고밀도의 정답 정보를 주입했는지를 수치화하여 Hallucination 발생 원인을 검색 단에서 차단함.
- **판단 포인트**: 이 지표가 낮을 경우 임베딩 모델(Encoder)의 성능 미달 또는 하이퍼파라미터 오류이며, 해결책으로 Hybrid Search 가중치(Alpha) 조절 및 2-Stage Cross-Encoder(Reranker) 아키텍처 도입이 필수적으로 요구됨.

## Ⅰ. 개요 및 필요성
- **정의**: 검색기(Retriever)가 반환한 K개의 컨텍스트 중에서 실제 유용한(Relevant) 문서의 비율을 평가하되, 해당 유용한 문서가 상단(Top rank)에 나타날수록 높은 페널티 가중치(Reward)를 부여하여 $0 \sim 1$로 환산하는 품질 척도.
- **배경**: 기존 정보 검색 평가지표 중 Precision@K는 단순히 "K개 중 몇 개가 맞나"만 따져 1등에 있으나 10등에 있으나 같은 점수를 부여하여 순위 품질(Ranking Quality)을 왜곡함.
- **필요성**: 생성형 AI는 입력 텍스트의 순서에 극도로 민감하므로, 가장 연관성 높은 텍스트를 최상단에 배치(Prioritization)시키는 검색/재순위화 파이프라인의 튜닝 성과를 정밀하게 모니터링하기 위함.

## Ⅱ. 수식 및 작동 메커니즘 (Rank-Aware Evaluation)
Context Precision은 전통적인 정보 검색 지표인 **AP(Average Precision)**의 수학적 뼈대를 차용함.
- **수식 구조**:
  $Context Precision@K = \frac{\sum_{k=1}^{K} (Precision@k \times v_k)}{\text{Total number of relevant items in top K}}$
  *(단, $v_k$는 $k$번째 문서가 관련 있으면 1, 아니면 0인 Indicator 함수)*
- **메커니즘 (예시: Top-3 검색)**
  1. 검색 결과 3개: `[Rank 1: 오답], [Rank 2: 정답], [Rank 3: 정답]`
  2. Rank 1까지 정밀도 (P@1): 0/1 = 0
  3. Rank 2까지 정밀도 (P@2): 1/2 = 0.5
  4. Rank 3까지 정밀도 (P@3): 2/3 = 0.66
  5. **최종 Context Precision**: 정답인 Rank 2와 3의 Precision만 더해서 평균냄 = $(0.5 + 0.66) / 2 = 0.58$ 점.
  *(만약 정답이 Rank 1, 2에 있었다면 (1.0 + 1.0)/2 = 1.0 만점 부여됨. 즉 순위가 점수를 결정!)*

## Ⅲ. 품질 매트릭스: Context Recall과의 상호 보완성
검색 품질은 Precision(정밀도)과 Recall(재현율)의 십자 포화로 평가해야 함.
| 케이스 분류 | Context Precision | Context Recall | 아키텍처 분석 및 처방 |
|:---:|:---:|:---:|:---|
| **이상적 검색** | **높음 (0.9)** | **높음 (0.9)** | 완벽함. 필요한 문서를 다 찾았고, 랭킹도 상단에 잘 꽂힘. |
| **랭킹 엔진 부실**| 낮음 (0.3) | **높음 (0.9)** | 문서는 다 퍼왔는데(Recall 좋음), 쓸데없는 문서가 1등이고 정답은 뒤에 박혀 있음. $\rightarrow$ **해결책: Reranker 모델 즉시 도입.** |
| **DB 파편화** | **높음 (0.9)** | 낮음 (0.3) | 가져온 1등 문서는 정답이 맞는데, 문제를 푸는데 필요한 나머지 조각 문서를 못 찾음. $\rightarrow$ **해결책: Chunking 사이즈 증대, Hybrid 검색 도입.** |
| **총체적 난국** | 낮음 (0.1) | 낮음 (0.1) | 그냥 다 틀림. 임베딩 모델(Encoder) 교체 시급. |

## Ⅳ. 고도화: Ragas의 LLM-as-a-Judge 평가 방식
- 사람이 직접 K개의 문서가 "정답에 쓸모 있는지(Relevant)" 라벨링하는 것은 불가능함.
- Ragas 프레임워크는 LLM에게 `Question`과 `Ground Truth(정답)`, 그리고 검색된 각각의 `Context`를 프롬프트로 줌.
- "이 Context 내용만으로 Ground Truth의 정보를 도출할 수 있냐?"라고 LLM에게 O/X 채점을 시켜 무인(Unsupervised) 자동 산출 파이프라인을 구축함.

## Ⅴ. 운영 시 한계점 및 최적화 전략
- **리스크 1: K값 (Top-K) 설정에 따른 점수 왜곡**:
  - LLM 컨텍스트 윈도우에 실제로 주입할 K값이 5인데, 평가를 Precision@20으로 세팅하면 현실 시스템과 평가 점수 간의 극심한 괴리가 발생함.
  - **대응 전략**: RAG 파이프라인에서 LLM Generator에 실제로 주입되는 청크의 개수(통상 3~5개)와 정확히 동일한 $K$ 값으로 메트릭 임계값(Threshold)을 맞추어 측정(Alignment)해야 함.
- **리스크 2: 의미적 중복 문서(Redundancy)에 대한 관대함**:
  - Rank 1, 2, 3이 완벽한 정답 문서인데, 사실 3개가 다 똑같은 내용의 문서일 수 있음. Precision은 1.0이 나오지만 컨텍스트 토큰이 심각하게 낭비됨.
  - **대응 전략**: MMR(Maximal Marginal Relevance) 등 다형성(Diversity) 보장 검색 알고리즘을 추가하여 정밀도뿐 아니라 정보의 커버리지를 함께 방어.

## Ⅵ. 실무 적용 및 결론
- **판단 지표**: Context Precision@5 (0.85 이상 임계치), NDCG@10.
- **실무 설계**: e-커머스 고객센터 RAG 구축. "반품 배송비 얼마야?" 질의 시, Dense 임베딩이 '반품'에 꽂혀 모든 상품의 반품 규정 문서 100개를 가져옴. Context Recall은 만점이나, 정작 질문한 고객의 회원 등급에 맞는 반품 문서는 15위에 랭크되어 Context Precision@5가 0.0을 기록(오답 발생). 해결책으로 Lexical(BM25)과 Dense 검색을 앙상블(RRF 결합)하고, Cohere Rerank API를 2차 파이프라인에 추가함. 이를 통해 Precision@5를 0.95로 끌어올려 정확한 회원별 배송비를 1등 문서로 맵핑, 환각률을 0%로 통제함.
- **결론**: Context Precision은 RAG 시스템의 '순위 결정력'을 뼈저리게 드러내는 X-ray 지표이며, Reranking 기술과의 결합을 통해 검색의 양(Quantity)을 질(Quality)로 압축시키는 정보 고도화의 최전선이다.

### 🔀 문제 유형별 목차 전환
- **Ⅱ·Ⅲ 강조 (개념/원리형)**: AP(Average Precision) 및 CG(Cumulative Gain), DCG의 할인율(Discount Factor) $\log_2(i+1)$ 수학적 전개 및 패널티 부과 원리 상세 서술.
- **Ⅴ·Ⅵ 강조 (실무/설계형)**: Vector DB 기반 Retrieval 파이프라인에서 Cross-Encoder 리랭킹 최적화를 통한 Context Precision 지표 점프 사례 중심 작성, Ragas 라이브러리 CI/CD 적용 방안.
