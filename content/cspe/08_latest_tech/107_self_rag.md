# 📖 【암기용】 개념 완전 이해

## 한눈에
- **정의**: 대형 언어 모델(LLM) 자신이 답변을 생성하는 과정에서 "검색이 필요한가?", "검색된 정보가 관련이 있는가?", "내 답변이 정확한가?"를 스스로 평가하는 '반성 토큰(Reflection Tokens)'을 발행하며 답변의 퀄리티를 자율적으로 제어하는 프레임워크.
- **필요성**: 기존 RAG는 "한국의 수도는?" 같은 뻔한 질문에도 무조건 검색을 돌려 시간을 낭비(비효율)하거나, 엉터리 정보가 들어와도 의심 없이 답변(환각)을 내뱉음.
- **핵심 직관**: 시험을 볼 때, 1번 문제(1+1)는 그냥 머릿속으로 풀고, 2번 문제(복잡한 공식)는 교과서를 찾아본 뒤(On-demand Retrieval), 답을 적으면서 "잠깐, 이 공식이 책 내용이랑 맞나?"라고 끊임없이 자문자답(Self-Reflection)하는 우등생의 풀이 과정.

## 깊이 이해
- **배경**: 2023년 워싱턴 대학교 등 연구진 제안. 검색 파이프라인을 외부에 두는 대신(CRAG 방식 등), LLM 자체에 크리틱(Critic) 능력을 훈련시켜 모델 내부에서 End-to-End로 RAG 품질을 통제하려는 시도.
- **작동 원리 (특수 토큰의 마법)**: 
  모델을 튜닝할 때 특정 상황에 특수 토큰을 뱉도록 훈련시킴.
  1. `[Retrieve]`: 질문을 보고 검색이 필요하면 이 토큰을 뱉음 $\rightarrow$ 이때만 벡터 DB 검색 실행. (검색 불필요하면 바로 답변)
  2. `[ISREL]`: 검색된 문서가 질문과 관련(Relevant) 있는지 평가.
  3. `[ISSUP]`: 자기가 쓴 문장이 검색된 문서에 의해 지지(Supported)되는지 평가.
  4. `[ISUSE]`: 이 답변이 질문에 대해 유용(Useful)한지 종합 평가.
  이 토큰 점수들의 조합으로 최적의 답변 조각(Segment)을 골라냄.
- **비유**: 실시간으로 팩트체커(Fact-checker)가 옆에 앉아, 내가 한 문장을 말할 때마다 빨간펜, 파란펜을 들고 점수를 매기며 교정해 주는 훈련 방식.
- **흔한 오해/주의점**: 프롬프트 엔지니어링만으로 흉내 낼 수도 있지만, 진짜 Self-RAG의 파워를 내려면 수만 건의 평가 데이터셋으로 LLM의 파라미터 자체를 파인튜닝(SFT)해야 함. 베이스 모델 변경이 불가능한 폐쇄형 API 환경에서는 제 기능을 100% 발휘하기 어려움.

## 연결 개념
- **On-demand Retrieval (적응형 검색)**: 모든 질의에 검색을 수행하지 않고, 모델이 필요할 때만 검색기를 호출하는 기술.
- **CRAG (교정형 RAG)**: 외부의 평가자(Evaluator)가 검색된 '문서'를 교정. 반면 Self-RAG는 LLM이 생성 중인 '답변'을 스스로 반성.
- **Supervised Fine-Tuning (SFT)**: Self-RAG 능력을 모델에 주입하기 위해 필수적으로 거쳐야 하는 학습 과정.

# 📝 【답안용】 시험 답안 템플릿
## 핵심 인사이트 (3줄 요약)
- **본질**: LLM이 토큰 생성 과정 중 메타데이터 역할을 하는 '반성 토큰(Reflection Tokens)'을 스스로 발행하여, 검색 시점 제어 및 생성 결과물의 사실적 일관성을 자가 검증(Self-Correction)하는 아키텍처.
- **가치**: 단순 질의에는 검색을 생략하여 응답 지연(Latency)과 API 비용을 대폭 삭감(검색 호출 40% 감소)함과 동시에, 생성 중 실시간 팩트체크를 통해 환각 방지 능력을 극대화(PubHealth 기준 정확도 약 9% 향상).
- **판단 포인트**: 별도의 외부 평가 모듈 없이 End-to-End로 최적화가 가능하나, 반성 토큰 발행 능력을 주입하기 위한 초기 파인튜닝(SFT) 비용 및 고도화된 훈련 데이터(Critic Data) 확보 난이도.

## Ⅰ. 개요 및 필요성
- **정의**: 언어 모델 파인튜닝을 통해 질의 분석, 문서 평가, 답변 검증을 의미하는 특수 토큰(Reflection Token)을 학습시키고, 이 토큰의 확률(Logit)을 기반으로 검색기 호출 여부와 답변의 품질을 동적으로 제어하는 차세대 RAG 프레임워크.
- **배경**: 기존 Always-Retrieve 방식은 불필요한 검색 지연을 유발하며, 외부의 Reranker나 Evaluator(CRAG)를 연동하는 방식은 파이프라인의 복잡도와 시스템 장애 지점(SPOF)을 증가시킴.
- **필요성**: 파이프라인의 복잡도를 줄이면서도 모델 스스로가 도메인 특화된 팩트체크 능력을 내재화(Internalize)하여, 가장 빠르고 정확한 단일 통합 추론 모델을 구축하기 위함.

## Ⅱ. Self-RAG 작동 메커니즘 (4대 반성 토큰)
```text
[ User Query ] -> [ LLM (Self-RAG 튜닝 모델) 추론 시작 ]

1. 검색 여부 판단: [Retrieve=Yes] or [Retrieve=No]
   -> Yes일 경우 외부 Vector DB에서 Top-K 문서 검색

2. 관련성 평가 (문서별): [ISREL] 토큰 발행 (Relevant / Irrelevant)
   -> Irrelevant 문서는 프롬프트에서 즉시 폐기

3. 답변 생성 및 지지성 평가: 답변 텍스트 생성 중 [ISSUP] 발행
   -> (Fully Supported / Partially Supported / No Support)
   -> 팩트에 기반하지 않은 환각(Hallucination) 문장 탐지

4. 유용성 종합 평가: [ISUSE] 토큰 발행 (1점 ~ 5점)
   -> 최종적으로 가장 점수가 높은 텍스트 세그먼트를 선택(Decoding)하여 응답
```

## Ⅲ. 기존 RAG 모델들과의 비교 아키텍처
| 구분 | Naive RAG | CRAG (외부 교정형) | Self-RAG (자가 검증형) |
|:---:|:---|:---|:---|
| **검색 빈도** | 항상 검색 (Always) | 항상 검색 (Always) | **필요시 검색 (On-demand)** |
| **품질 평가 주체**| 없음 | 외부 평가 모듈 (Evaluator) | **LLM 자신 (Reflection Token)** |
| **통제 시점** | 평가 불가 | 생성 이전 (Pre-generation) | **생성 중 실시간 (In-generation)** |
| **지연 시간** | 중간 | 높음 (평가기 + 생성기 대기) | 유동적 (단순 질문 시 매우 빠름) |

## Ⅳ. 모델 훈련 파이프라인 (How to Train)
1. **Critic Data 수집**: GPT-4 등 뛰어난 상용 모델을 프롬프팅하여, 질의-응답 쌍 사이에 적절한 [반성 토큰]을 삽입한 수만 건의 라벨링 데이터 셋(Critic Dataset)을 구축 (지식 증류).
2. **Generator SFT**: LLaMA 등 오픈소스 베이스 모델에 해당 데이터셋을 지도 학습(Supervised Fine-Tuning)하여, 특정 컨텍스트에서 반성 토큰을 자연스럽게 뱉어내도록 모델 파라미터 업데이트.
3. **Inference**: 추론 단계에서 반성 토큰의 확률값(Log Probabilities)을 계산하여, 다양한 생성 분기 중 가장 신뢰도 높은 경로(Path)를 선택하는 디코딩(Segment-level beam search) 수행.

## Ⅴ. 한계점(리스크) 및 해결 방안
- **리스크 1: SFT 훈련 비용 및 폐쇄형 LLM 적용 한계**:
  - 모델의 파라미터를 직접 수정해야 하므로 GPU 컴퓨팅 자원이 소모되며, 가중치 접근이 불가능한 OpenAI API 기반 환경에서는 논문과 동일한 구현이 어려움.
  - **대응 방안**: 오픈소스 모델(Llama 3 등)을 자사 인프라(On-premise)에 내재화할 때 Self-RAG 아키텍처를 도입. API 환경에서는 프롬프트 상에서 "스스로 평가 점수를 매겨라"라고 지시하는 Prompt-based Self-Reflection 방식으로 우회 적용.
- **리스크 2: 추론 오버헤드 (Inference Overhead)**:
  - 여러 문서에 대해 병렬적으로 답변 조각(Segment)을 생성하고 점수를 매기는 디코딩 연산으로 인해 메모리 사용량과 추론 비용 상승.
  - **대응 방안**: 빔 서치(Beam Search)의 폭(Width)을 제한하고, 동시 평가할 문서 수(K)를 3 이하로 제한하여 Latency 타협점 도출.

## Ⅵ. 실무 적용 및 결론
- **판단 지표**: 단순 질문에 대한 검색 우회율(Bypass Rate), Hallucination 탐지율, 토큰 발행 비용 절감률.
- **실무 설계**: 금융 상품 상담 콜센터 챗봇 구축 시, "안녕하세요", "영업시간" 같은 단순 질의(약 40%)와 "정기예금 금리 비교" 같은 복합 질의(60%)가 혼재됨. Self-RAG 파이프라인을 구축하여, 단순 질의 시 `[Retrieve=No]`가 발동되어 벡터 검색 없이 즉각 밀리초 단위로 응답하고, 복합 질의에만 정확한 문서를 찾아와 팩트체크(`[ISSUP]`)를 수행함으로써 월간 API 호출 비용 40% 절감 및 환각 0% 달성.
- **결론**: Self-RAG는 맹목적인 파이프라인의 노예였던 언어 모델에게 '메타인지(Meta-cognition)' 능력을 부여한 혁신이며, 추론 효율성과 사실성을 동시에 잡아야 하는 상용 AI 서비스의 핵심 엔진으로 자리매김할 것임.

### 🔀 문제 유형별 목차 전환
- **Ⅱ·Ⅲ 강조 (개념/원리형)**: 4가지 반성 토큰(Retrieve, ISREL, ISSUP, ISUSE)의 세밀한 역할 분류와, 확률 기반 Segment-level Beam Search 디코딩 메커니즘 중심 서술.
- **Ⅴ·Ⅵ 강조 (실무/설계형)**: 항상 검색하는 Naive/CRAG와의 FinOps(클라우드 비용) 및 성능 지표 벤치마크(PubHealth 등) 정량적 비교, 사내 오픈소스 LLM 도입 시나리오 중심 작성.
