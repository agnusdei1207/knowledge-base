## 미리 알고가기

- $TTFT$ ($Time$ $To$ $First$ $Token$): 사용자가 입력 질문(프롬프트)을 전송한 시점부터, 모델 서버가 연산을 거쳐 첫 번째 글자(토큰)를 사용자 브라우저에 출력하기까지 소요된 총 지연 시간임
- 프리필 ($Prefill$): 유입된 질문 전체를 한 번에 인코딩하며 멀티 헤드 어텐션 점수를 구하고 $KV$ 캐시를 최초 수립하는 가장 무겁고 연산 집약적인 초기화 단계임
- 대기열 지연 ($Queue$ $Delay$): GPU 물리 서빙 슬롯이 모두 가동 중일 때, 앞선 작업들이 끝나거나 동적 배치에 자리가 나기까지 큐에서 대기하는 시간임
- 청크 프리필 ($Chunked$ $Prefill$): 무거운 프리필 연산을 한 번에 다 처리하지 않고, 수천 토큰 단위의 조각(청크)으로 나누어 디코드 연산과 병행 처리해 간섭을 방지하는 기술임

## Ⅰ. 개요

- **정의/개념**: TTFT(Time To First Token)는 최종 사용자의 프롬프트 전송 버튼 클릭 시점부터 서버의 프리필($Prefill$) 처리 및 스케줄러 대기를 완료하고 첫 번째 출력 토큰이 사용자 디바이스에 스트리밍 도달하기까지의 경과 시간이며, 서비스의 첫인상과 이탈률을 가르는 핵심 초기 반응성 지표임
- **배경/필요성**: 장문맥 데이터나 RAG의 도입으로 인해 프롬프트의 길이가 평균 수만 토큰 이상으로 급증하면서 프리필 단계의 계산 시간과 VRAM 선점 대기 지연이 동반 폭증함에 따라, 사용자에게 서비스가 다운되지 않았음을 실시간으로 알리는 TTFT 단축이 인프라 최우선 목표가 됨

## Ⅱ. 특징

- 사용자의 입력 데이터 크기(프롬프트 길이), 서빙 서버의 혼잡도(큐 대기시간), 기반 신경망의 연산 복잡도에 따라 비선형적으로 시간이 증가함
- 생성 완료 시까지 걸리는 전체 추론 시간과는 상관관계가 없으므로, 서비스의 병목 진단 시에는 TTFT와 단어 간 생성 속도($TPOT$)를 반드시 이원 분리하여 분석해야 함
- 플래시어텐션을 통한 HBM 입출력 단축 효율 및 접두 캐싱($Prefix$ $Caching$)의 유효성을 정량적으로 판독할 수 있는 대표적인 관측 지표임

## Ⅲ. 종류 및 비교

| 판단 기준 | 짧은 입력 TTFT (단답형 질의) | 긴 입력 TTFT (RAG, 장문 분석) | 접두사 캐시 적중 TTFT (Prefix Hit) |
|:---|:---|:---|:---|
| **지연 발생의 주역** | 네트워크 왕복 및 스케줄 큐 대기 | $O(N^2)$ 복잡도의 대규모 프리필 연산 | 오직 큐 대기 및 변수 부분 프리필 연산 |
| **속도 절감 장치** | 경량화 모델 배포, 동적 배칭 | 플래시어텐션, 청크 프리필 분할 적용 | 접두사 캐싱 ($Prefix$ $Caching$) 적용 |
| **체감 사용자 경험** | 매우 쾌적함 (밀리초 단위 응답) | 답답함 (수 초 이상의 화면 멈춤 발생) | 최상의 반응 속도 (즉시 타이핑 스트리밍) |

> 요약: 짧은 입력은 네트워크 최적화로, 긴 입력은 프리필 연산 최적화로, 캐시 적중은 공통 문맥 캐싱 설계로 각각 TTFT를 극복함.

## Ⅳ. 구성요소 및 구조

| 구성요소 | 설명 |
|:---|:---|
| 프로토콜 핸들러 | 사용자의 HTTP/WebSocket 연결을 수립하고 자연어 텍스트를 토큰 ID 시퀀스로 쪼개는 진입 장치임 |
| 스케줄 대기열 | GPU 가용 배치 공간과 VRAM 마진이 확보될 때까지 요청을 임시 파킹하고 순서를 배정하는 큐임 |
| 프리필 연산 엔진 | 질문 토큰 전체에 대해 동시 다발적인 멀티 쿼리 어텐션 계산을 쳐서 초기 $KV$ 캐시를 조립하는 가동부임 |
| 첫 토큰 샘플러 | 생성된 첫 단어의 확률 분포에 템퍼러처를 가미해 최종 1단어를 골라 네트워크 패킷에 직송하는 송신 장치임 |

```text
[ TTFT (Time To First Token) 시간 측정 구역 ]
User Click -> [Handler] -> [Queue Delay] -> [Prefill Engine] -> [Sampler] -> First Word Output (TTFT)
|<----------------------------- Total TTFT Duration ------------------------>|
```

## Ⅴ. 원리 및 절차 흐름도

```text
+-------------+     +--------------+     +-------------+     +-------------+
| 프롬프트 전송| --> | 배칭 자원대기| --> | 프리필 가동 | --> | 첫 단어 추출|
| 및 토큰 정제|     | (큐 스캔)    |     | (KV캐시 생성) |     | 및 전송/종료|
+-------------+     +--------------+     +-------------+     +-------------+
```

1. **연결 및 토큰화** — 사용자 화면에서 질문이 전송되면 서버 API 게이트웨이가 토큰화와 악성 인젝션 소독을 즉시 수행함
2. **배치 배정 대기** — 스케줄러가 GPU VRAM의 활성 페이지 공간을 진단하고, 배치 슬롯에 여유가 날 때까지 큐 메모리에 작업을 파킹함
3. **프리필 순방향 연산** — 배치가 바인딩되면 플래시어텐션 커널을 구동해 프롬프트 전체 차원의 행렬 곱을 쳐서 KV 캐시를 고속 셋업함
4. **첫 패킷 릴리즈** — 도출된 첫 번째 토큰의 정수 ID를 문자열로 복원하여 네트워크 채널(SSE)로 전보처럼 즉각 릴리즈하고 TTFT 측정을 종료함

## Ⅵ. 실무 적용 및 유의점

1. 프롬프트 길이가 만 토큰을 초과하여 프리필 시간이 크게 늘어날 경우, PagedAttention의 메모리 블록 할당과 CPU-GPU 오프로딩 간의 지연이 TTFT를 가중시키므로, 반드시 고정 접두 문맥을 VRAM에 고정해 두는 '접두 캐싱($Prefix$ $Caching$)'을 켜서 중복 프리필 계산을 소거하고 적중률을 모니터링해야 함
2. 서빙 시스템의 혼잡 시 평균($Average$) TTFT는 극단적인 지연(예: 대기열 30초 대기)을 숨기는 왜곡을 범하므로, 반드시 백엔드 로그 모니터링 시 신뢰 구간 최악 수준 지표인 **p95, p99 TTFT**와 사용자 강제 이탈율($Abandonment$ $Rate$)을 결합하여 인프라 성능을 지속 감사해야 함

## Ⅶ. 결론

- TTFT는 사용자가 대기하며 느끼는 심리적 반응성을 정량화한 LLM 인프라 운영의 핵심 바로미터이며, 설계자는 평균값에 속아 사용자 이탈을 간과하지 않도록 p95/p99 지연 관측 체계를 수립하고 접두 캐싱과 비동기 큐잉을 동반 구현해야 함
