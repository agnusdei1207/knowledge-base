# 📖 【암기용】 개념 완전 이해

> 목적: Model Registry를 처음 봐도 완벽히 이해하게 만든다. 시험 답안 양식이 아니라, 이해를 위한 친절한 설명이다.

## 한눈에
- **개요**: 학습이 완료된 머신러닝 모델 파일(Artifact)을 버전별로 저장하고, 배포 승인 및 생명주기를 관리하는 중앙 저장소
- **왜 필요한가**: 어떤 모델이 최신인지, 누가 만들었는지, 성능은 어떠했는지, 그리고 현재 운영 환경에 배포된 모델이 정확히 어떤 데이터로 학습된 것인지 추적하기 위함
- **핵심 직관**: 소프트웨어 개발의 'GitHub'이나 'Docker Hub'처럼, 모델을 체계적으로 보관하고 출고(배포)를 관리하는 "ML 모델 전용 물류 창고"

## 깊이 이해
- **배경·문제의식**: 실험 단계에서 데이터 과학자들은 수많은 모델을 만든다. 하지만 관리가 안 되면 "final_model_v2_final.pkl" 같은 파일들이 서버에 난립하게 된다. 운영 중 장애가 발생했을 때 이 모델이 어떤 코드와 데이터로 만들어졌는지 모르면(Lineage 결여) 복구가 불가능해진다.
- **작동 원리**: 모델 학습이 끝나면 모델 파일, 하이퍼파라미터, 성능 지표를 묶어 레지스트리에 등록한다. 이후 'Staging', 'Production', 'Archived' 등 상태(Stage)를 부여하며, 권한이 있는 관리자의 승인을 거쳐야만 다음 단계로 넘어갈 수 있다.
- **비유**: 대형 마트의 검수실과 같다. 새로 들어온 제품(Model)이 품질 검사를 통과하면 진열대(Staging)에 올리고, 최종 확인 후 고객에게 판매(Production)하며, 유통기한이 지나면 창고(Archived)로 보낸다.
- **구체 예시**: MLflow Model Registry를 사용하여 v1 모델을 운영(Production) 중인 상태에서, 성능이 개선된 v2 모델을 검증(Staging) 단계로 올리고, 테스트 결과가 좋으면 관리자의 승인을 받아 v1과 교체한다.
- **흔한 오해·주의점**: "Model Registry는 단순히 파일을 저장하는 S3와 같다"라고 생각하기 쉬우나, 모델의 메타데이터, 버전 간 비교, 승인 워크플로우, 데이터 계보(Lineage) 추적이 결합된 통합 관리 플랫폼이다.

## 연결 개념
- MLOps — Model Registry가 모델 배포의 중심 관문 역할을 함
- Model Lineage — 모델이 생성된 기원(데이터, 코드)을 추적함
- Experiment Tracking — 모델 등록 전 실험 단계를 관리함 (Registry의 전 단계)

# 📝 【답안용】 시험 답안 템플릿

> 목적: 시험장에서 25분에 그대로 쓰는 답안 양식. 작성방식(추상표현 금지·수치·도식·문제유형 전환)을 엄격히 지킨다.

## 핵심 인사이트 (3줄 요약)

> 1. **본질**: Model Registry는 학습된 모델의 아티팩트와 메타데이터를 통합 관리하고 배포 생명주기를 통제하는 중앙 리포지토리이다.
> 2. **가치**: 모델 버전 관리의 혼선을 방지하고, 모델 생성 이력(Lineage) 추적을 통해 운영의 투명성과 재현성을 확보한다.
> 3. **판단 포인트**: 모델의 상태 전이(Stage Transition) 시 자동화된 검증 게이트와 역할 기반 접근 제어(RBAC) 적용이 핵심이다.

## 출제 의도 및 답안 포인트

| 출제 의도 | 반드시 짚을 핵심 | 감점 회피 포인트 |
|:---|:---|:---|
| 모델 관리 및 배포 통제 역량 확인 | 버전 관리, 상태 관리(Stage), 모델 계보(Lineage) | 단순히 "모델 저장소"라고 모호하게 서술 |
| MLOps 파이프라인 내 역할 이해 확인 | CI/CD 연계, 승인 워크플로우, 메타데이터 기록 | 기술적 관리 요소(버전, 태그) 누락 |
| 거버넌스 및 보안 리스크 인식 확인 | RBAC, 감사 로그, 모델 서명(Signature) | "관리가 편해짐"과 같은 추상적 표현 사용 |

> 요약: 모델의 전 생명주기를 시각화하고 승인되지 않은 모델의 배포를 원천 차단하는 거버넌스 체계 제시가 핵심이다.

## Ⅰ. 개요 및 필요성

- 정의: 머신러닝 모델의 버전, 파라미터, 성능 지표를 중앙에서 관리하고 배포 상태를 통제하는 특화된 저장소 및 관리 시스템
- 배경: 모델 파일 난립으로 인한 관리 부재, 운영 중인 모델의 생성 이력 추적 불가(Black Box화), 수동 배포에 따른 인적 오류 발생
- 필요성: 모델의 재현성(Reproducibility) 확보, 배포 전 품질 게이트(Quality Gate) 구현, 감사(Audit) 대응을 위한 모델 이력 보존

## Ⅱ. 구조 및 구성요소

```text
Experiment Tracking -> Model Registration -> Model Registry (Central Hub)
                                                    |
                   +--------------------------------+-------------------------------+
                   |                                |                               |
        Version Control (v1, v2)          Stage Mgmt (Staging/Prod)        Lineage (Data/Code)
```

| 구성요소 | 역할 | 특이사항 |
|:---|:---|:---|
| Model Artifacts | 실제 학습된 모델 파일 저장 | pkl, onnx, pt 등 형식 |
| Metadata Store | 파라미터, 성능 지표, 학습 일시 기록 | SQL 기반 메타데이터 저장 |
| Versioning System | 동일 모델명에 대한 순차적 버전 관리 | Semantic Versioning |
| Stage Manager | 배포 상태 전이(Transition) 관리 | Staging, Production, Archived |

> 요약: 모델 실체(Artifact)와 정보(Metadata)를 결합하여 생명주기(Stage)를 제어함.

---

## Ⅲ. 동작원리 및 흐름도

```text
학습 완료 -> 레지스트리 등록 -> Candidate 상태 -> 검증/테스트 -> Staging 승인 -> Production 전환 -> 이전 버전 Archive
      |                |               |               |                |                 |
      +----------------+---------------+---------------+----------------+-----------------+-----> Lineage 추적
```

| 단계 | 처리 내용 | 검증 기준 |
|:---:|:---|:---|
| 1 | 모델 등록 및 메타데이터 기록 | 학습 코드/데이터 버전 링크 필수 |
| 2 | 테스트 단계 (Staging) | Accuracy > 0.9, Latency 통과 |
| 3 | 승인 워크플로우 실행 | 담당자(Owner) 승인 100% |
| 4 | 운영 환경 배포 (Production) | Canary/Blue-Green 배포 연동 |

> 요약: 모델을 등록하고 검증을 거쳐 승인된 모델만 운영 환경으로 전이시키는 엄격한 프로세스를 따름.

## Ⅳ. 특징

| 구분 | 일반 파일 시스템 (S3/NFS) | Model Registry | 판단 포인트 |
|:---|:---|:---|:---|
| 관리 단위 | 파일 (Blob) | 모델 개체 (Model Object) | 객체 중심 관리 |
| 생명주기 관리 | 수동 폴더 구분 | 논리적 상태(Stage) 기반 | 워크플로우 자동화 |
| 계보 추적 | 불가능 | 데이터/코드/환경 추적 가능 | 투명성 확보 |
| 접근 제어 | 파일 단위 권한 | 모델별/상태별 RBAC 적용 | 보안 및 거버넌스 |

> 요약: Model Registry는 모델의 의미적 정보와 운영 상태를 관리하는 전문 거버넌스 도구임.

## Ⅴ. 심화 비교 및 적용 판단

| 비교 축 | 오픈소스 (MLflow Registry) | 클라우드 전용 (SageMaker/Vertex) | 선택 기준 |
|:---|:---|:---|:---|
| 확장성 | 직접 구축/관리 필요 | 자동 확장 및 관리형 서비스 | 운영 리소스 가용성 |
| 통합성 | 다양한 플랫폼 연동 가능 | 해당 클라우드 서비스 최적화 | 기존 인프라 환경 |
| 비용 구조 | 인프라 비용 중심 | 사용량 기반 과금 | 장기 운영 예산 |

> 요약: 멀티 클라우드 환경이면 MLflow를, 특정 클라우드 생태계에 종속되어 효율을 높이려면 전용 서비스를 선택함.

| 리스크 | 원인 | 대응 방안 | 확인 지표 |
|:---|:---|:---|:---|
| 미승인 모델 배포 | 승인 워크플로우 우회 | Registry-CI/CD 강제 연동 | 운영 모델의 승인 로그 일치율 |
| 재현 실패 | 학습 환경 정보 누락 | Docker 이미지 및 하이퍼파라미터 기록 | 동일 조건 재학습 오차 범위 |
| 모델 유출 | 부적절한 권한 설정 | 프로젝트/상태별 RBAC 및 감사 로그 | 비인가 접근 시도 로그 |

> 요약: 배포 리스크는 강제 연동으로, 재현 리스크는 환경 기록으로, 보안은 RBAC로 대응함.

| 점검 항목 | 목표 기준 | 측정 방법 |
|:---|:---|:---|
| 모델 추적성 | 운영 모델의 학습 데이터 추적 100% | 리네이지 그래프 조회 |
| 배포 성공률 | 모델 교체 시 장애 발생률 1% 이하 | 이전 버전 롤백 빈도 측정 |
| 모델 승인 시간 | 등록 후 승인까지 24시간 이내 | 워크플로우 단계별 소요 시간 |

> 요약: 도입 효과는 모델의 추적 가능성, 배포 안정성, 거버넌스 효율성 지표로 판정함.

## Ⅵ. 실무 적용 및 결론

**적용 방안 3개:**
1. 배포 통제 표준화: 모델 등록 시 성능 지표가 기준치 미달이면 Staging 진입을 자동 차단하는 품질 게이트 구축
2. 장애 대응 신속화: 운영 중인 모델의 ID만으로 학습에 쓰인 데이터 셋과 소스 코드 커밋 번호를 즉시 확인(Lineage 100% 확보)
3. 거버넌스 강화: 금융권 등 규제 산업에서 모델의 변경 이력과 승인권자를 감사 로그로 남겨 EU AI Act 등 법규 준수 증명

**결론 (2줄):**
- 기술사 판단: Model Registry는 모델을 개발 산출물에서 신뢰할 수 있는 "기업 자산"으로 승격시키는 핵심 관리 지점임
- 향후 방향: 모델의 위변조 방지를 위한 블록체인 기반 무결성 검증이나 모델 서명(Code Signing) 기술과 결합할 것으로 전망됨
