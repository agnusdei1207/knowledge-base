# 📖 【암기용】 개념 완전 이해

## 한눈에
- **정의**: 학습이 완료된 머신러닝 모델 파일(Artifact)을 버전별로 안전하게 보관하고, 이 모델들이 운영 서버로 나갈 수 있는지 '승인 및 배포 상태(Stage)'를 중앙에서 관리하는 **ML 전용 형상관리 및 배포 관문**.
- **필요성**: 데이터 사이언티스트의 노트북 안에는 `final_model.pkl`, `진짜_최종_model_v2.pkl` 같은 파일들이 수십 개 굴러다님. 만약 상용 서버에서 모델이 오작동을 일으켰는데, "도대체 어떤 파일을 가져다 배포한 거지?"를 아무도 모르면(추적성 상실) 롤백(Rollback)도 못 하고 대형 사고가 터짐. 
- **핵심 직관**: 모델들의 '물류 창고 겸 검수대'. 소프트웨어 소스코드를 'GitHub'에 올리고 도커 이미지를 'Docker Hub'에 올리듯, ML 모델 파일(Pickle, ONNX 등)은 'Model Registry'에 올려야 함. 창고 관리자(레지스트리)는 입고된 모델에 바코드(버전)를 붙이고, 품질 검사를 통과한 놈만 'Staging(대기)' $\rightarrow$ 'Production(상용 배포)' 칸으로 옮겨줌.

## 깊이 이해
- **배경**: 초기 MLOps는 '어떻게 자동 학습시킬까'에만 집중하다 보니, 기껏 파이프라인이 뱉어낸 훌륭한 모델들이 제대로 관리되지 못하고 USB나 사내 메신저로 전달되는 원시적 배포를 겪음. 배포된 모델의 버저닝과 투명한 권한 통제가 필요해짐.
- **작동 원리 (라이프사이클 기반 통제)**:
  1. **등록 (Register)**: 모델 학습(Experiment)이 끝나면 모델 바이너리 파일과 함께 "이 모델은 파이썬 3.8 환경에서, XGBoost 라이브러리를 썼고, 정확도는 95%야"라는 메타데이터를 Registry에 던짐 (예: v1.0 등록).
  2. **상태 관리 (Stage Transition)**: 방금 들어온 모델은 `None(후보)` 상태임. 모델 검증팀이 평가 후 합격하면 버튼을 눌러 `Staging`으로 상태 변경. 최종 경영진 승인이 나면 `Production(운영)`으로 상태 승격.
  3. **CD 파이프라인 연동**: ArgoCD나 KServe 같은 배포 도구는 레지스트리를 쳐다보다가 "오, v2.0 모델이 Production 태그를 달았네?" 하면 자동으로 실시간 운영 서버에 배포함.
  4. **보관/일몰 (Archived)**: 기존에 돌던 v1.0 모델은 자동으로 `Archived(폐기)` 상태로 밀려남.
- **구체 예시**: 자율주행 회사의 보행자 인식 모델. 매일 새로운 주행 데이터로 모델 수백 개가 자동 학습됨. 레지스트리는 이 중 테스트셋 정확도가 제일 높은 모델을 'Staging' 상태로 올리고 담당자에게 슬랙 알람을 보냄. 담당자가 `[Approve]` 버튼을 누르면 'Production'으로 전환되고, 테슬라 차량들의 OTA(무선 업데이트) 서버가 레지스트리에서 이 모델을 끌어가 차량에 배포함.
- **흔한 오해/주의점**: "그냥 S3나 파일서버(NAS)에 폴더 만들고 v1, v2 저장하면 안 됨?" $\rightarrow$ 안 됨. S3는 그냥 파일만 저장함. Registry는 파일 보관을 넘어, '이 모델이 어떤 학습 코드로 만들어졌는지(계보 추적)', '운영에 배포할 권한 승인이 났는지(거버넌스)'를 소프트웨어적으로 통제하는 워크플로우 엔진임.

## 연결 개념
- **Experiment Tracking (실험 추적)**: 레지스트리의 앞 단계. 요리 과정(파라미터 튜닝)을 기록하는 게 실험 추적이라면, 그중 1등을 한 요리 완성품(모델)을 냉장고에 보관하는 게 레지스트리임.
- **Model Lineage (모델 계보)**: 레지스트리가 제공하는 핵심 기능. "이 모델의 족보가 어떻게 되느냐?". 학습 데이터 해시값, 소스코드 Git 커밋 해시 등을 연결해 장애 시 원인 역추적을 가능하게 함.
- **ModelOps**: 레지스트리는 전사적 모델 통제(ModelOps) 거버넌스를 물리적으로 구현하는 핵심 저장소 인프라임.

# 📝 【답안용】 시험 답안 템플릿
## 핵심 인사이트 (3줄 요약)
- **본질**: 머신러닝 개발 수명주기(MLSDLC) 내에서 생성된 모델 아티팩트(Artifact)와 메타데이터를 저장, 버저닝(Versioning)하고, 모델의 논리적 배포 상태(Stage)를 중앙 제어하는 ML 전용 형상관리 저장소(Repository).
- **가치**: 모델 배포 과정의 휴먼 에러를 방지하고 승인되지 않은 모델의 운영 환경 유입을 차단하는 통제 게이트(Approval Gate) 역할을 수행하며, 장애 발생 시 모델 족보(Lineage)를 통한 즉각적인 원인 규명 및 롤백(Rollback)을 보장함.
- **판단 포인트**: Model Registry 구축의 핵심은 단순한 파일 저장이 아니라, CI/CD 파이프라인과의 자동 연동(Webhook/API) 체계 및 역할 기반 접근 제어(RBAC)를 통한 IT 감사(Audit) 요건 준수 메커니즘을 설계하는 데 있음.

## Ⅰ. 개요 및 필요성
- **정의**: 기계학습 실험을 통해 검증된 최종 모델의 이진 파일(pkl, pt, onnx 등)과 환경 의존성, 성능 지표를 묶어 버전별로 카탈로그화하고 릴리스 승인 워크플로우를 관장하는 MLOps 인프라.
- **배경**: AI 서비스의 스케일 아웃에 따라 수많은 모델이 동시다발적으로 업데이트되면서 배포 버전의 충돌, 재현성(Reproducibility) 결여, 운영 중인 모델의 블랙박스화(어떤 코드로 학습되었는지 알 수 없음) 문제가 심화.
- **필요성**: 모델 배포 파이프라인(CD)의 자동화 트리거 지점 확보, 운영 환경 장애 시 1-Click 이전 버전 롤백, 규제 대응을 위한 AI 모델 계보(Lineage) 및 변경 이력 추적성(Traceability) 100% 확보.

## Ⅱ. Model Registry 4대 핵심 아키텍처 및 기능
파일 서버를 넘어서는 거버넌스 워크플로우 엔진.
| 핵심 기능 | 메커니즘 (Mechanism) 및 상세 역할 | MLOps 가치 |
|:---:|:---|:---|
| **Artifact Repository**<br>(모델 자산 저장) | 모델 바이너리, Conda/Pip 환경 파일, 모델 서명(Signature, 입출력 스키마)을 S3/Blob Storage에 불변(Immutable) 상태로 포장하여 저장. | 100% 재현 가능한 모델 실행 환경 보장. |
| **Model Versioning**<br>(버전 및 카탈로그) | 동일한 모델명(Model Name) 아래에 시간순으로 순차적 버전 번호(v1, v2)를 강제 할당. | 버전 충돌 방지 및 히스토리 관리. |
| **Stage Transition**<br>(상태 전이 워크플로우) | 모델의 배포 생애주기를 `None` $\rightarrow$ `Staging` $\rightarrow$ `Production` $\rightarrow$ `Archived`의 상태 머신(State Machine)으로 통제. | 승인 없는 운영 배포 원천 차단 (Approval Gate). |
| **Lineage Tracking**<br>(계보 추적 및 메타데이터) | 등록된 모델과 MLflow/W&B의 실험(Experiment) Run ID를 연결. 학습에 사용된 Git 커밋 해시와 데이터 버전을 맵핑. | AI 감사(Audit) 대응 및 디버깅 추적성. |

## Ⅲ. 배포 파이프라인 (CD) 통합 메커니즘 (Workflow)
모델 레지스트리가 주도하는 배포 자동화.
1. **이벤트 감지 (Webhook Trigger)**:
   - 품질 검증을 마친 `Model_A v3.0`이 담당자 승인을 얻어 Registry 내에서 `Production` 상태(Stage)로 변경됨.
2. **이벤트 페이로드 전송**:
   - Registry가 이 상태 변경 이벤트를 감지하고 Webhook을 통해 Jenkins/ArgoCD 같은 CD 툴에 배포 파이프라인 가동 신호를 쏨.
3. **자동 배포 및 서빙 (Model Serving)**:
   - KServe/Seldon Core는 Registry의 API를 찔러 `Production` 태그가 달린 최신 모델 아티팩트를 K8s 클러스터로 끌어옴(Pull).
   - 카나리(Canary) 또는 블루-그린 배포 방식으로 트래픽을 신규 v3.0 모델로 안전하게 전환.

## Ⅳ. 일반 소스코드 형상관리(Git)와의 차이점 비교
| 구분 | Source Code (Git) | Model Registry (MLflow, SageMaker) |
|:---:|:---|:---|
| **저장 대상** | Text 기반 소스 코드 (KB~MB 단위) | **대용량 이진 바이너리(Weight) 및 메타데이터 (GB 단위)** |
| **병합/충돌 제어**| 브랜치 분기(Branching) 및 병합(Merge) | **병합 불가 (가중치 파일의 특성). 순차적 버전 업그레이드만 존재** |
| **배포 패키징** | Docker Image 빌드 | **모델 파일 + 의존성 패키지 명세서 + 입출력 텐서 스키마** |
| **관리의 본질** | 로직의 "문법 및 구조" 버전 관리 | **데이터에 의해 생성된 "수학적 확률 공간(행렬)"의 버전 관리** |

## Ⅴ. 실무 적용 및 결론
- **판단 지표**: 운영 배포된 모델의 Lineage(소스코드/데이터) 추적 성공률 100%, 승인 우회(Bypass) 배포 시도 건수(0건 타겟), 장애 발생 시 이전 정상 버전(Production $\rightarrow$ Archived 롤백) 전환 소요 시간(MTTR).
- **실무 설계**: 금융 보안 기업 S사의 'FDS(이상거래탐지) 모델 배포 체계' 구축. 기존엔 데이터 과학자가 모델 피클(pickle) 파일을 운영자에게 메일로 던져 수동 배포(보안 및 휴먼 에러 리스크 심각). 조치 방안: MLflow Model Registry 도입. 1) 학습 파이프라인 종료 시 정확도 90% 이상인 경우만 Registry에 `Staging` 상태로 자동 등록. 2) C-Level 보안 관리자가 Registry 웹 UI에 접속해 모델의 SHAP(설명가능성) 리포트를 확인 후 승인(`Production` 전환) 버튼 클릭(RBAC 적용). 3) Kubernetes의 롤아웃 컨트롤러가 즉시 상태 변경을 감지하고 기존 파드를 교체. 무중단 보안 배포 체계 확립.
- **결론**: Model Registry는 데이터 과학자의 "내 로컬 노트북에서는 잘 돌아갔는데요?"라는 변명을 원천 차단하는 도구다. 단순한 파일 보관함을 넘어 배포의 투명성과 권한(Governance)을 시스템적으로 강제함으로써, AI 모델이 엔터프라이즈의 신뢰할 수 있는 소프트웨어 자산(Asset)으로 거듭나기 위한 필수 관문 역할을 한다.

### 🔀 문제 유형별 목차 전환
- **Ⅱ·Ⅲ 강조 (개념/원리형)**: Model Registry 아키텍처 내부의 '모델 서명(Model Signature)' 기능. 배포 전 모델이 받을 입력 데이터의 스키마(Tensor 형, 크기)와 출력 스키마를 강제 저장하여, 서빙 단계에서 형(Type) 불일치로 인한 런타임 크래시를 컴파일 타임(등록 타임)에 사전에 차단하는 원리.
- **Ⅴ·Ⅵ 강조 (실무/설계형)**: 거버넌스와 보안(Compliance-as-Code) 설계. OPA(Open Policy Agent)를 Registry의 Webhook에 연동하여, "취약점 스캔(CVE) 결과 심각도가 High인 파이썬 패키지가 포함된 모델은 Production Stage 전이를 시스템 레벨에서 원천 차단한다"는 정책을 배포 파이프라인에 주입하는 방안.
