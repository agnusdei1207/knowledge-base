# 📖 【암기용】 개념 완전 이해

> 목적: Apache Iceberg를 처음 봐도 완벽히 이해하게 만든다. 시험 답안 양식이 아니라, 이해를 위한 친절한 설명이다.

## 한눈에
- **개요**: 거대한 데이터 세트를 위해 설계된 개방형 테이블 포맷 (데이터 레이크의 '테이블' 규칙)
- **왜 필요한가**: 기존 하이브(Hive) 방식은 파일이 너무 많아지면 목록을 읽는 데만 한 세월이 걸리고, 데이터를 수정하면 전체를 다 뒤집어야 하는 등 대규모 데이터 처리에 한계가 있었기 때문이다.
- **핵심 직관**: "파일 목록을 폴더 구조가 아닌 별도의 '스냅샷' 계층으로 관리하여, 수십억 개의 파일도 눈 깜짝할 새 찾아낸다."

## 깊이 이해
- **배경·문제의식**: 넷플릭스처럼 하루에 수조 건의 데이터가 쌓이는 곳에서는 기존의 '디렉터리 기반' 관리가 불가능했음. 파일 하나가 바뀌면 전체 파티션을 다시 스캔해야 했고, 실수로 데이터를 지우면 복구가 어려웠음.
- **작동 원리**: 아이스버그는 '계층 구조'로 동작함. ① **스냅샷**: 특정 시점의 전체 파일 목록. ② **매니페스트 리스트**: 매니페스트 파일들의 목록. ③ **매니페스트 파일**: 실제 데이터 파일(Parquet 등)의 위치와 통계 정보. 이를 통해 쿼리 엔진은 실제로 필요한 파일이 무엇인지 폴더를 뒤지지 않고도 정확히 알 수 있음.
- **비유**: 도서관에서 책을 찾을 때 모든 서가를 다 돌아다니는 게 아니라, 컴퓨터 인덱스(스냅샷)에서 책의 정확한 위치를 확인한 뒤 그 칸으로 바로 가는 것과 같음.
- **구체 예시**: 수천 개의 날짜별 파티션이 있는 테이블에서 '특정 ID'를 찾을 때, 아이스버그는 메타데이터를 보고 해당 ID가 포함된 파일만 골라냄(Data Skipping).
- **흔한 오해·주의점**: 컴퓨팅 엔진이 아님. 데이터를 어떻게 파일로 구성하고 메타데이터를 남길지에 대한 '약속(Format)'임. Spark, Trino, Flink 등 다양한 도구가 이 약속을 따름.

## 연결 개념
- Apache Hive - Iceberg가 해결하고자 한 기존의 느린 테이블 포맷
- Data Lakehouse - Iceberg가 핵심 기술로 쓰이는 아키텍처
- Open Table Format (Delta, Hudi) - Iceberg와 경쟁 및 공존하는 기술들

# 📝 【답안용】 시험 답안 템플릿

> 목적: 시험장에서 25분에 그대로 쓰는 답안 양식. 작성방식(추상표현 금지·수치·도식·문제유형 전환)을 엄격히 지킨다.
> 핵심: Iceberg의 3계층 메타데이터 구조(Snapshot -> Manifest List -> Manifest File)와 이를 통한 Partition Evolution, Schema Evolution의 기술적 우위를 강조한다.

## 핵심 인사이트 (3줄 요약)

> 1. **본질**: Apache Iceberg는 거대 규모의 데이터 레이크에서 성능과 신뢰성을 보장하기 위해 설계된 고성능 개방형 테이블 포맷이다.
> 2. **가치**: 파티션 진화(Partition Evolution)와 스냅샷 격리를 통해 대규모 데이터의 물리적 구조 변경 없이도 쿼리 최적화와 트랜잭션을 지원한다.
> 3. **판단 포인트**: 디렉터리 리스팅이 아닌 메타데이터 파일 기반의 탐색 구조로 파일 스캔 범위를 최소화하여 대규모 데이터 성능을 혁신한다.

## 출제 의도 및 답안 포인트

| 출제 의도 | 반드시 짚을 핵심 | 감점 회피 포인트 |
|:---|:---|:---|
| 대규모 데이터 관리 기법 이해 확인 | 3계층 메타데이터 구조, 스냅샷 기반 관리 | 단순히 "성능이 빠르다"는 식의 결과만 서술 |
| 하이브(Hive) 방식과의 차별점 파악 | 디렉터리 리스팅 vs 메타데이터 트리 탐색 | 물리적 파티션 관리의 한계 언급 누락 |
| 현대적 데이터 엔지니어링 역량 확인 | Partition Evolution, Schema Evolution, Time Travel | 구체적 용어 대신 "유연하다"는 추상 표현 사용 |

> 요약: Iceberg는 트리 구조의 메타데이터를 통해 수십억 개의 파일을 관리하는 데이터 레이크의 차세대 표준이다.

## Ⅰ. 개요 및 필요성

- 정의: 대규모 분석 데이터 세트를 위해 설계된 고성능 개방형 테이블 포맷 (v2 기준 ACID 지원)
- 배경: Hive의 S3/HDFS 디렉터리 리스팅 부하, 원자적 작업 불가, 파티션 변경 시 데이터 재처리 비용 발생
- 필요성: 클라우드 오브젝트 스토리지의 지연(Latency) 극복, 엔진 독립적인 데이터 공유, 데이터 무결성 보장

---

## Ⅱ. 구조 및 구성요소 (3계층 메타데이터 트리)

```text
[ Iceberg Table Hierarchy ]
  / Metadata File (v1, v2...) -> 현재 스냅샷 포인터
    -> [ Manifest List ] -> 스냅샷에 포함된 매니페스트 파일들
       -> [ Manifest File ] -> 데이터 파일 목록 + 통계(Min/Max)
          -> [ Data File (Parquet) ] -> 실제 데이터
```

| 구성요소 | 역할 | 특이사항 |
|:---|:---|:---|
| Metadata File | 테이블 스키마, 파티션 설정, 스냅샷 로그 관리 | 엔트리 포인트 |
| Manifest List | 특정 스냅샷을 구성하는 매니페스트 파일 집합 기록 | 파티션 필터링에 활용 |
| Manifest File | 개별 데이터 파일의 경로와 컬럼별 통계 정보 저장 | 파일 레벨 스킵(Data Skipping) |

> 요약: 상위 계층에서 하위 파일 목록을 트리 구조로 관리하여 불필요한 스캔을 제거하는 구조이다.

---

## Ⅲ. 동작원리 및 흐름도 (Snapshot Isolation)

```text
Query -> [ 1. Metadata File 읽기 ] -> [ 2. Manifest List 필터링 ]
                 |                            |
              최신 버전 확인                파티션 조건 기반 선별
                 |                            |
          [ 4. Data Read ] <- [ 3. Manifest File 기반 파일 선택 ]
                 |                            |
            최종 파일 스캔                 컬럼 통계(Min/Max) 활용
```

| 단계 | 처리 내용 | 검증 기준 |
|:---:|:---|:---|
| 1 | 최신 버전 식별 | Metadata File을 통해 현재 유효한 스냅샷 확인 | 스냅샷 버전 관리 |
| 2 | 파티션 가지치기 | Manifest List에서 쿼리 조건에 맞는 파티션만 선별 | Partition Pruning |
| 3 | 파일 단위 스킵 | Manifest File의 통계(Min/Max)로 불필요한 파일 제외 | Row Group Skip |
| 4 | 결과 반환 | 선택된 데이터 파일만 병렬로 읽어 쿼리 수행 | 성능 최적화 |

> 요약: 메타데이터를 미리 읽어 읽어야 할 파일 목록을 확정한 뒤, 실제 데이터에 접근하여 IO를 최소화한다.

---

## Ⅳ. 특징 (Iceberg만의 차별점)

| 구분 | 주요 특징 | 상세 내용 |
|:---|:---|:---|
| 파티션 진화 | Partition Evolution | 테이블 물리 구조 변경 없이 파티션 컬럼/방식 변경 가능 |
| 스키마 진화 | Schema Evolution | 컬럼 추가/삭제/이름 변경 시 데이터 재작성 불필요 |
| 타임 트래블 | Time Travel | 스냅샷 ID 또는 시점을 지정하여 과거 데이터 즉시 조회 |
| 격리 수준 | Serializable Isolation | 낙관적 동시성 제어(OCC)를 통해 쓰기 작업의 무결성 보장 |
| 개방성 | Engine Agnostic | Spark, Trino, Flink, Presto 등과 동일 메타데이터 공유 |

> 요약: 파티션과 스키마의 '진화(Evolution)' 기능은 운영 효율성을 혁신적으로 높여준다.

## Ⅴ. 심화 비교 및 적용 판단

| 구분 | Apache Hive (기존) | Apache Iceberg | 선택 기준 |
|:---|:---|:---|:---|
| 파일 탐색 방식 | 디렉터리 전체 리스팅 | 메타데이터 파일 트리 탐색 | 파일 개수 및 데이터 규모 |
| 파티션 관리 | 물리적 경로(Folder) 고정 | 논리적 매핑 (Hidden Partitioning) | 데이터 구조 변경 빈도 |
| 트랜잭션 | 없음 (원자성 부족) | 스냅샷 기반 ACID 지원 | 데이터 신뢰성 요건 |
| 클라우드 최적화 | S3 등에서 리스팅 속도 저하 | 메타데이터 기반으로 IO 최소화 | 클라우드 환경 여부 |

> 요약: 대규모(페타바이트급) 데이터와 잦은 스키마 변경이 있는 클라우드 환경에서는 Iceberg가 압도적으로 유리하다.

| 리스크 | 원인 | 대응 방안 | 확인 지표 |
|:---|:---|:---|:---|
| 메타데이터 비대화 | 잦은 커밋으로 스냅샷/로그 누적 | 이력 삭제(Expire Snapshots) 주기적 수행 | 메타데이터 파일 크기/개수 |
| 고립된 파일 (Orphan) | 비정상 종료로 인한 미참조 파일 | 파일 정리(Delete Orphan Files) 도구 실행 | 스토리지 내 미참조 용량 |
| 쿼리 복잡도 | 파티션 진화가 잦을 시 매핑 부하 | 주기적 데이터 재정렬(Rewrite Data Files) | 쿼리 플래닝 시간 |

> 요약: 메타데이터와 고립된 파일들에 대한 주기적인 가비지 컬렉션(GC)이 운영의 핵심이다.

| 점검 항목 | 목표 기준 | 측정 방법 |
|:---|:---|:---|
| 쿼리 응답 시간 | Hive 대비 대규모 조회 50% 이상 단축 | 벤치마크 테스트 수행 |
| 파티션 변경 시간 | 무중단, 무작업(데이터 이동 없음) | Partition Evolution 기능 테스트 |
| 데이터 신뢰도 | 동시 쓰기 시 데이터 깨짐 발생 0건 | 동시성 테스트(Stress Test) |

> 요약: 쿼리 성능 향상과 운영 편의성(진화 기능), 그리고 트랜잭션 안정성을 지표로 도입 효과를 검증한다.

## Ⅵ. 실무 적용 및 결론

**적용 방안 3개:**
1. **Hidden Partitioning 활용**: 사용자가 파티션 컬럼을 몰라도 쿼리 조건에서 자동으로 파티션을 찾아내도록 설계하여 쿼리 편의성 증대
2. **증분 가공(Incremental Processing)**: 스냅샷 간의 차이(Diff)만 읽어 들이는 기능을 활용하여 효율적인 CDC 파이프라인 구축
3. **멀티 엔진 분석 공유**: Spark로 데이터를 쓰고(ETL), Trino로 실시간 조회(BI)하며 동일한 Iceberg 테이블을 공유하여 정합성 유지

**결론 (2줄):**
- 기술사 판단: Apache Iceberg는 물리적 저장 방식과 논리적 테이블 구조를 완벽히 분리한 진정한 의미의 데이터 추상화 레이어이며, 엔터프라이즈 레이크하우스의 표준이다.
- 향후 방향: Snowflake, BigQuery 등 주요 클라우드 DW와의 상호운용성 강화(Apache XTable 등)를 통해 데이터 사일로 현상을 해결하는 핵심 역할을 할 것이다.
