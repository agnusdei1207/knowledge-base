# 📖 【암기용】 개념 완전 이해

> 목적: Apache Flink를 처음 봐도 완벽히 이해하게 만든다. 시험 답안 양식이 아니라, 이해를 위한 친절한 설명이다.

## 한눈에
- **개요**: 데이터가 발생하는 즉시 하나씩 처리하는 '진정한 실시간(True Streaming)' 처리를 위해 설계된 오픈소스 분산 연산 엔진
- **왜 필요한가**: 기존 기술(Spark Streaming)은 데이터를 아주 짧은 시간(초 단위) 모아서 처리하는 방식이라 0.1초가 급한 상황에는 한계가 있었다. 플링크는 들어오는 즉시 처리하면서도, 사고가 났을 때 데이터를 한 건도 빠뜨리지 않는 능력이 탁월하기 때문이다.
- **핵심 직관**: "데이터 한 건 한 건을 놓치지 않고 실시간으로 연산하면서, 장애가 나도 정확히 기억해내는 '천재적인 실시간 요리사'."

## 깊이 이해
- **배경·문제의식**: 스트리밍 처리에서 가장 어려운 점은 '장애가 났을 때 어디까지 처리했는지 정확히 아는 것'임. 또한 네트워크 지연으로 데이터 순서가 뒤바뀔 때(Out-of-order) 이를 어떻게 바로잡느냐가 관건이었음.
- **작동 원리**: '상태(State)'와 '체크포인트(Checkpoint)'가 핵심임. 계산 중간값을 메모리에 저장(State)해두고, 주기적으로 이 상태를 안전한 곳에 백업(Checkpoint)함. 또한 '워터마크(Watermark)'라는 가상의 시계로 늦게 온 데이터를 기다려줌.
- **비유**: 실시간으로 주문을 받아 요리하는 주방과 같음. 요리사(Flink)는 주문서가 들어오자마자 요리를 시작함. 중간중간 "지금까지 설탕 5스푼 썼음" 같은 기록을 메모판(State)에 적어둠. 만약 정전(장애)이 되면, 마지막으로 백업된 메모판을 보고 정확히 다음 단계부터 요리를 다시 시작함.
- **구체 예시**: 금융권에서 실시간 이상 거래 탐지(FDS)를 할 때, 최근 1분간의 거래 패턴을 실시간으로 분석하여 0.01초 만에 사기 여부를 판단함.
- **흔한 오해·주의점**: '스트리밍 전용'이라고 생각하기 쉽지만, '배치(Batch) 처리'도 스트리밍의 특수한 경우로 보고 아주 잘 처리함. (Batch as a special case of Streaming)

## 연결 개념
- Apache Spark - 플링크와 경쟁하는 대표적인 분산 연산 엔진
- Exactly-once - 장애 시에도 데이터가 정확히 한 번만 처리됨을 보장하는 속성
- State Backend - 플링크가 상태 정보를 어디에 저장할지 결정하는 설정 (RocksDB 등)

# 📝 【답안용】 시험 답안 템플릿

> 목적: 시험장에서 25분에 그대로 쓰는 답안 양식. 작성방식(추상표현 금지·수치·도식·문제유형 전환)을 엄격히 지킨다.
> 핵심: 이벤트 단위 처리(One-at-a-time), 상태 관리(Managed State), 비동기 체크포인팅(Chandy-Lamport 알고리즘), 워터마크 기반 시간 처리를 기술적으로 강조한다.

## 핵심 인사이트 (3줄 요약)

> 1. **본질**: Apache Flink는 무한한 데이터 스트림(Unbounded Streams)과 유한한 데이터 세트(Bounded Streams)를 모두 처리하는 상태 기반 분산 스트림 처리 엔진이다.
> 2. **가치**: 마이크로 배치 방식의 한계를 넘어 밀리초(ms) 단위의 낮은 지연 시간과 강력한 상태 관리를 통해 복잡한 비즈니스 로직의 실시간 정합성을 보장한다.
> 3. **판단 포인트**: 장애 복구 시 데이터 유실/중복 없는 Exactly-once 보장 능력과 워터마크를 활용한 이벤트 시간(Event Time) 처리 능력이 핵심 선택 기준이다.

## 출제 의도 및 답안 포인트

| 출제 의도 | 반드시 짚을 핵심 | 감점 회피 포인트 |
|:---|:---|:---|
| 스트리밍 처리 방식의 차별점 이해 확인 | Native Streaming (Event-at-a-time) vs Micro-batch | 단순히 "빠르다"는 서술 지양 |
| 상태 관리 및 장애 복구 메커니즘 파악 | Checkpoint, Savepoint, State Backend (RocksDB) | Exactly-once 구현 원리(Barrier) 누락 |
| 시간 처리 및 윈도우 연산 역량 | Event Time, Watermark, Late Data 처리 | Processing Time과의 차별성 부각 실패 |

> 요약: 플링크는 저지연(Low Latency)과 고정합성(Exactly-once)을 동시에 실현하는 4세대 스트림 처리 엔진이다.

## Ⅰ. 개요 및 필요성

- 정의: 데이터의 흐름을 이벤트 단위로 즉시 처리하며, 강력한 상태 관리와 장애 복구 기능을 갖춘 오픈소스 분산 스트림 엔진
- 배경: 기존 마이크로 배치 방식의 지연(Latency) 한계, 데이터 순서 뒤바뀜(Out-of-order) 대응 필요성 증대
- 필요성: 실시간 사기 탐지(FDS), 실시간 지표 분석, 지연 없는 반응형 서비스 아키텍처(Event-driven) 구축

---

## Ⅱ. 구조 및 구성요소 (Runtime Architecture)

```text
[ Job Manager ] <---- (RPC/Heartbeat) ----> [ Task Manager ]
  - Scheduler                                 - Task Execution
  - Checkpoint Coordinator                    - Buffer Management
  - Resource Manager                          - State Management
                                               |
[ Storage: HDFS, S3 ] <------------------------+ (State Checkpointing)
```

| 구성요소 | 역할 | 특이사항 |
|:---|:---|:---|
| Job Manager | 작업 스케줄링, 체크포인트 관리, 리소스 할당 | 클러스터의 마스터 노드 |
| Task Manager | 실제 데이터 처리 태스크 실행 및 상태 유지 | 워커 노드, 슬롯(Slot) 단위 자원 분할 |
| State Backend | 연산 중간 상태(State)를 저장하는 메커니즘 | Memory, FileSystem, RocksDB |
| DataStream API | 실시간 데이터 흐름 처리를 위한 상위 API | Java/Scala/Python 지원 |

> 요약: 마스터(Job Manager)가 제어하고 워커(Task Manager)가 상태를 유지하며 연산을 수행하는 구조이다.

## Ⅲ. 동작원리 및 흐름도 (Exactly-once 및 체크포인트)

```text
Stream Source -> [ 1. Barrier 주입 ] -> [ 2. Operator 연산 ] -> [ 3. State 스냅샷 ]
                      |                       |                       |
               (일관성 지점 표시)         (상태 업데이트)         (외부 저장소 백업)
                      |                       |                       |
        [ 5. Rollback ] <- [ 4. 장애 감지 및 복구 ] <------------------+
```

| 단계 | 처리 내용 | 검증 기준 |
|:---:|:---|:---|
| 1 | 체크포인트 시작 | 소스에서 제어 메시지(Barrier)를 데이터 흐름에 삽입 | Chandy-Lamport 알고리즘 기반 |
| 2 | 상태 연산 | 각 연산자(Operator)가 데이터를 처리하며 상태(State) 갱신 | Managed State 활용 |
| 3 | 스냅샷 저장 | Barrier가 도착하면 현재 상태를 영구 저장소에 비동기 저장 | 비차단(Non-blocking) 방식 |
| 4 | 장애 복구 | 장애 발생 시 마지막 성공 체크포인트 시점으로 전체 리셋 | 원자적 복구 |

> 요약: 데이터 흐름 속에 삽입된 배리어(Barrier)를 통해 전역적인 일관된 상태 스냅샷을 만들어 Exactly-once를 실현한다.

## Ⅳ. 특징

| 구분 | 주요 특징 | 상세 내용 |
|:---|:---|:---|
| 지연 시간 | Low Latency | 마이크로 배치가 아닌 이벤트 즉시 처리 (수 밀리초 수준) |
| 시간 처리 | Event Time 지원 | 시스템 시각이 아닌 실제 발생 시각 기준 연산 (Watermark 활용) |
| 정합성 | Exactly-once | 장애 복구 후에도 데이터 중복이나 유실 없는 정확한 결과 보장 |
| 유연성 | Savepoint | 작업 중단 후 상태를 유지한 채 버전 업그레이드나 재배포 가능 |
| 확장성 | Scalable State | 페타바이트급 상태를 관리할 수 있는 분산 상태 백엔드 지원 |

> 요약: '저지연'과 '정확성'을 모두 포기하지 않는 설계가 가장 큰 강점이다.

## Ⅴ. 심화 비교 및 적용 판단

| 구분 | Apache Spark Streaming | Apache Flink | 선택 기준 |
|:---|:---|:---|:---|
| 처리 방식 | 마이크로 배치 (Micro-batch) | 네이티브 스트리밍 (Event-at-a-time) | 지연 시간 요건 (ms vs sec) |
| 지연 시간 | 초 단위 (Seconds) | 밀리초 단위 (Milliseconds) | 실시간성 중요도 |
| 상태 관리 | 상대적으로 단순 | 매우 정교하고 강력 (Managed State) | 비즈니스 로직 복잡도 |
| 장애 복구 | RDD 계보(Lineage) 기반 재계산 | 체크포인트 기반 상태 복구 | 복구 시간 및 정합성 요건 |

> 요약: 범용적인 데이터 처리는 Spark가 유리하지만, 극한의 실시간성과 복잡한 상태 관리는 Flink가 우수하다.

| 리스크 | 원인 | 대응 방안 | 확인 지표 |
|:---|:---|:---|:---|
| 체크포인트 지연 | 상태 크기가 너무 크거나 정렬 부하 | 증분 체크포인트(Incremental), Unaligned CP 적용 | Checkpoint Duration |
| 상태 비대화 | 윈도우 수명이 너무 길거나 키가 많음 | 상태 만료 시간(TTL) 설정, RocksDB 튜닝 | State Size per Task |
| 역압 (Backpressure) | 하류 연산 속도가 상류보다 느림 | 연산 최적화, 병렬도(Parallelism) 조정 | Backpressure Monitor (Web UI) |

> 요약: 상태 크기 관리(TTL)와 체크포인트 최적화가 성능 유지의 핵심이다.

| 점검 항목 | 목표 기준 | 측정 방법 |
|:---|:---|:---|
| 데이터 처리 정합성 | 중복/누락 0건 (Exactly-once) | 체크포인트 성공률 및 데이터 검증 |
| 지연 시간 (Latency) | 99% 이벤트 100ms 이내 처리 | 엔드투엔드 지연 측정 지표 |
| 복구 시간 (MTTR) | 장애 시 1분 이내 상태 복구 및 재개 | 고의 장애 유발 테스트 |

> 요약: 도입 효과는 초저지연 처리 성공률과 장애 시의 데이터 무결성 지표로 평가한다.

## Ⅵ. 실무 적용 및 결론

**적용 방안 3개:**
1. **실시간 FDS(이상 거래 탐지)**: 사용자의 과거 결제 패턴을 상태(State)로 유지하며 유입되는 결제 이벤트를 윈도우 연산하여 즉시 차단
2. **실시간 광고 성과 집계**: 클릭 이벤트의 뒤바뀐 순서를 워터마크로 보정하며 분 단위 노출/클릭률을 Exactly-once로 정확히 집계
3. **이벤트 주도 마이크로서비스(EDM)**: 서비스 간의 복합 이벤트 처리(CEP) 엔진으로 활용하여 특정 조건 충족 시 비즈니스 워크플로우 트리거

**결론 (2줄):**
- 기술사 판단: 플링크는 단순한 연산 도구를 넘어 '상태를 가진 애플리케이션'을 분산 환경에서 완벽하게 구현할 수 있게 해주는 스트림 프로세싱의 완성형이다.
- 향후 방향: Flink SQL의 고도화와 Flink CDC를 통한 DB 연동 강화, 클라우드 네이티브 환경에서의 서버리스 서비스(Flink on K8s)가 주류가 될 것이다.
