# 📖 【암기용】 개념 완전 이해

## 한눈에
- **정의**: 대형 언어 모델(LLM)이 답변을 생성하기 전에, 외부 데이터베이스에서 관련된 문서를 먼저 검색(Retrieval)하여 읽어보고, 그 정보(Context)를 바탕으로 답변을 생성(Generation)하는 AI 아키텍처.
- **필요성**: LLM은 자신이 학습한 시점까지만 알고 있으며(Knowledge Cut-off), 기업 내부의 비공개 데이터는 전혀 모름. 또한 모르는 것을 지어내는 환각(Hallucination) 문제가 치명적임.
- **핵심 직관**: 시험을 칠 때 수험생(LLM)이 자기 기억(파라미터)에만 의존해서 답을 쓰는 게 아니라, 도서관(Vector DB)에서 관련 전공서적 3권을 찾아 책상에 펼쳐놓고(오픈북 테스트) 정답을 작성하는 것.

## 깊이 이해
- **배경**: 2020년 Meta(구 Facebook) AI 연구진이 처음 제안. 파인튜닝(Fine-tuning)을 통한 지식 주입은 비용이 너무 비싸고 잊어버리기 쉽다는 한계를 극복하기 위해 등장. 현재 엔터프라이즈 AI의 사실상 표준(De facto standard) 아키텍처임.
- **작동 원리**:
  1. (사전 작업) 기업의 문서들을 잘게 쪼개어(Chunking), 의미를 담은 숫자의 배열(Embedding Vector)로 바꾸어 벡터 DB에 저장.
  2. 사용자가 질문하면, 질문도 벡터로 변환.
  3. 벡터 DB에서 질문과 의미(방향)가 가장 비슷한 문서 N개를 가져옴 (Retrieval).
  4. 프롬프트에 "다음 문서들을 참고해서 질문에 답해:"라고 넣은 뒤 LLM에게 응답 생성 지시 (Generation).
- **비유**: 판사(LLM)가 판결을 내릴 때 자기 기억에 의존하지 않고, 법원 서기(Retriever)에게 관련 과거 판례(문서)를 찾아오라고 지시한 뒤, 그 판례들을 꼼꼼히 읽고 판결문을 쓰는 것과 같음.
- **구체 예시**: 사내 취업규칙 챗봇. "경조사 휴가 며칠이야?" -> LLM 자체는 모르지만, 사내 규정 PDF에서 "본인 결혼 5일, 자녀 결혼 1일" 부분을 검색해 온 뒤, "규정에 따라 본인 결혼 시 5일입니다. (출처: 취업규칙 14조)"라고 정확히 답함.
- **흔한 오해/주의점**: RAG의 품질은 LLM보다 **검색(Retrieval)의 품질**이 8할 이상을 결정함. 쓰레기를 찾아오면 쓰레기 답변을 만듦(Garbage in, Garbage out).

## 연결 개념
- **Vector Database**: RAG의 핵심 인프라. 문서를 숫자의 의미 공간에 저장하고 매우 빠르게 검색(ANN)해줌.
- **Fine-Tuning (미세조정)**: RAG의 경쟁재이자 보완재. 말투나 도메인 스타일을 바꿀 땐 파인튜닝, 지식을 주입할 땐 RAG.
- **Advanced RAG**: 단순 검색을 넘어 질의를 재작성하고 검색 결과를 재정렬(Reranking)하는 고도화된 RAG 기법.

# 📝 【답안용】 시험 답안 템플릿
## 핵심 인사이트 (3줄 요약)
- **본질**: 파라메트릭 메모리(LLM 내부 지식)의 한계를 극복하기 위해, 논파라메트릭 메모리(외부 DB)를 실시간으로 결합하는 하이브리드 추론 프레임워크.
- **가치**: 모델 재학습 없이 최신/도메인 지식을 실시간으로 반영하며, 답변의 출처(Source)를 명시하여 환각(Hallucination)을 원천 차단하고 기업 AI 도입의 법적/신뢰성 리스크를 해소함.
- **판단 포인트**: 정보 갱신 주기(Frequency), 도메인 특화 정도, 예산(비용) 관점에서 Fine-Tuning과 RAG의 Trade-off를 분석하고 최적의 조합(Hybrid)을 설계하는 역량.

## Ⅰ. 개요 및 필요성
- **정의**: 사용자의 질의에 대해 외부 지식 베이스(Knowledge Base)에서 관련 문서를 검색(Retrieval)하고, 이를 프롬프트의 문맥(Context)으로 주입하여 LLM이 정확하고 신뢰성 있는 응답을 생성(Generation)하도록 하는 기술.
- **배경**: 파운데이션 모델은 사전 학습(Pre-training) 이후의 지식 갱신이 불가능(Knowledge Cut-off)하고, 보유하지 않은 지식에 대해 그럴싸한 거짓말(Hallucination)을 생성하는 구조적 결함을 가짐.
- **필요성**: 수시로 변하는 기업 내부 문서(규정, 매뉴얼)를 파인튜닝(수억 원 비용) 없이 실시간으로 반영하고, 답변의 "출처 추적성(Traceability)"을 확보하기 위해 필수적임.

## Ⅱ. RAG의 구조 및 동작 원리 (파이프라인)
```text
[ 1. Data Indexing Pipeline (사전 작업) ]
사내 문서(PDF/DB) -> 청킹(Chunking) -> 임베딩 모델(Embedding) -> [ 벡터 데이터베이스 ]

[ 2. Retrieval & Generation Pipeline (실시간 서비스) ]
사용자 질의(Query)
      |
(1) 임베딩 변환 (Query Embedding)
      |
(2) 벡터DB 검색 (Top-K Similarity Search) ------> [ 관련 문서 조각들 반환 ]
      |
(3) 프롬프트 조합 (Context Injection)
      └─ "주어진 [문서]를 바탕으로 [질의]에 답하라."
      |
(4) LLM 생성 (Generation) -> 최종 답변 출력 (출처 포함)
```

## Ⅲ. RAG vs Fine-Tuning 비교 (기술사 판단)
| 구분 | RAG (검색증강생성) | Fine-Tuning (미세조정) |
|:---:|:---|:---|
| **핵심 목적** | 새로운 **지식(Knowledge)** 주입 | 새로운 **태스크/스타일(Skills)** 훈련 |
| **지식 갱신** | 실시간 (DB에 문서만 추가하면 끝) | 매우 느림 (전체 파라미터 재학습 필요) |
| **출처 제시** | **가능** (인용 문서 링크 제공) | 불가 (블랙박스) |
| **도입 비용** | 상대적 저렴 (벡터 DB 및 임베딩 API 비용) | 매우 비쌈 (GPU 연산 자원 대량 소모) |
| **환각 방지** | 탁월 (근거 기반 생성) | 한계 존재 (과적합 위험) |

## Ⅳ. RAG 파이프라인의 핵심 기술 요소
1. **청킹 (Chunking) 기법**:
   - 문서를 몇 개의 토큰 단위로 자를 것인가. 너무 크면 노이즈가 많고, 너무 작으면 문맥(Context)이 소실됨. (Semantic Chunking 등 적용)
2. **임베딩 (Embedding) 최적화**:
   - 텍스트를 다차원 벡터 공간에 매핑. 오픈소스 BGE-M3 모델이나 OpenAI `text-embedding-3` 등을 활용해 다국어 및 도메인 전문 용어 인식력 향상.
3. **벡터 DB (Vector Database)**:
   - 밀리초 단위의 근사 최근접 이웃(ANN: Approximate Nearest Neighbor) 검색을 수행하는 Milvus, Pinecone, Qdrant 등 인프라 적용.

## Ⅴ. 한계점 및 극복 방안 (고도화 전략)
- **리스크 1: 검색 품질 저하에 따른 생성 오류 (Retrieval Failure)**:
  - 질문에 사용된 단어와 문서에 쓰인 단어가 다를 경우(어휘적 불일치), 벡터 검색이 정답 문서를 찾아내지 못함(Recall 저하).
  - **대응 방안**: 순수 벡터 검색(Dense)과 키워드 검색(Sparse, BM25)을 결합하는 **하이브리드 검색(Hybrid Search)** 도입. 검색 결과를 재정렬하는 **리랭커(Cross-Encoder Reranker)** 파이프라인 구축.
- **리스크 2: "Lost in the Middle" 현상**:
  - 검색된 문서를 10개 이상 너무 많이 프롬프트에 주입하면, LLM이 중간에 위치한 문서를 무시하고 앞뒤만 보고 답을 생성함.
  - **대응 방안**: 프롬프트 압축(Prompt Compression) 기법 사용, Top-K를 3~5개로 최적화, 최신 Long-context 모델 연계.

## Ⅵ. 실무 적용 및 결론
- **판단 지표**: RAGAS 프레임워크 기반의 Faithfulness(답변-문서 일치도), Answer Relevancy(질의-답변 관련도), Context Precision(검색 정확도) 지표 측정.
- **실무 설계**: 금융권 대고객 챗봇 구축 시, 금융상품설명서를 RAG로 연동함. 1단계로 BM25+Dense 하이브리드 검색 적용, 2단계로 부서별 권한 접근 제어(RBAC)를 메타데이터 필터링에 결합, 3단계로 답변 시 반드시 원문 PDF 페이지 링크를 제공하여 컴플라이언스(금융소비자보호법) 이슈 차단.
- **결론**: RAG는 생성형 AI의 한계를 극복하고 엔터프라이즈 환경에서 "신뢰할 수 있는 AI(Trustworthy AI)"를 구현하기 위한 필수 아키텍처이며, 향후 Agentic RAG와 Graph RAG 형태로 진화하며 기업 지식 관리의 패러다임을 혁신할 것임.

### 🔀 문제 유형별 목차 전환
- **Ⅱ·Ⅲ 강조 (개념/원리형)**: 인덱싱 과정(ETL -> 임베딩 -> 벡터DB)과 검색 과정의 수학적 유사도(Cosine Similarity) 산출 방식 중심 서술.
- **Ⅴ·Ⅵ 강조 (실무/설계형)**: RAG 파이프라인의 병목(Bottleneck) 현상 분석, 리랭커 적용 등 Advanced RAG 최적화 기법, 온프레미스 보안 환경에서의 벡터 DB 아키텍처 구성 방안.
