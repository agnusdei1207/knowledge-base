# 📖 【암기용】 개념 완전 이해

> 목적: Feature Store를 처음 봐도 완벽히 이해하게 만든다. 시험 답안 양식이 아니라, 이해를 위한 친절한 설명이다.

## 한눈에
- **개요**: 머신러닝 모델 학습과 추론에 필요한 특징(Feature) 데이터를 중앙에서 관리하고 공유하는 저장소
- **왜 필요한가**: 모델마다 데이터를 중복 가공하는 낭비를 줄이고, 학습(Offline)과 서빙(Online) 시의 데이터가 달라 성능이 떨어지는 현상(Training-Serving Skew)을 막기 위함
- **핵심 직관**: 모든 요리사가 재료를 직접 손질하는 대신, 미리 손질된 신선한 재료가 정해진 버전으로 준비되어 있는 "ML 전용 중앙 식재료 창고"

## 깊이 이해
- **배경·문제의식**: ML 모델을 만들 때 시간의 80%는 데이터 전처리에 쓰인다. 그런데 여러 팀이 비슷한 특징(예: 고객의 최근 7일간 구매 총액)을 각자 계산하면 계산 비용이 낭비된다. 더 심각한 문제는 학습 때는 과거 데이터를 썼는데, 실제 서비스(서빙) 때는 계산 로직이 미세하게 달라져 모델이 엉뚱한 예측을 하는 것이다.
- **작동 원리**: 특징 로직을 한 번 정의하면, 이를 중앙 저장소에 등록한다. 대량 학습을 위한 **Offline Store**(Hive, S3 등)와 실시간 서빙을 위한 **Online Store**(Redis, Cassandra 등)로 데이터를 자동 동기화하여 일관성을 보장한다.
- **비유**: 편의점 도시락 공장에서 소스 레시피(Feature Definition)를 본사에서 관리하고, 공장(Offline)과 개별 점포(Online)에 동일한 소스를 공급하여 전국 어디서나 같은 맛(Performance)을 내게 하는 것과 같다.
- **구체 예시**: 사기 탐지 모델에서 "사용자의 최근 1시간 결제 횟수"라는 특징을 Feature Store에 등록해두면, 모델 학습 시에는 1년 치 데이터를 가져오고, 실제 결제 시점에는 Redis에서 10ms 안에 최신값을 가져와 실시간으로 판별한다.
- **흔한 오해·주의점**: "Feature Store는 단순한 데이터베이스다"라고 생각하기 쉬우나, 데이터의 버전 관리(Versioning), 선후 관계 추적(Lineage), 시간 여행(Time-travel) 기능을 포함하는 고도화된 메타데이터 관리 시스템이다.

## 연결 개념
- MLOps — Feature Store가 핵심 인프라로 작동하는 운영 체계
- Training-Serving Skew — Feature Store 도입으로 해결하려는 핵심 문제
- Point-in-time Correctness — 특정 시점의 정확한 데이터 조회를 가능하게 함

# 📝 【답안용】 시험 답안 템플릿

> 목적: 시험장에서 25분에 그대로 쓰는 답안 양식. 작성방식(추상표현 금지·수치·도식·문제유형 전환)을 엄격히 지킨다.

## 핵심 인사이트 (3줄 요약)

> 1. **본질**: Feature Store는 ML 특징(Feature)의 정의·저장·공유를 자동화하여 데이터의 재사용성과 일관성을 보장하는 데이터 인프라이다.
> 2. **가치**: 학습-서빙 간 데이터 불일치(Skew)를 해결하고, 특징 엔지니어링의 중복 작업을 제거하여 모델 출시 시간을 단축한다.
> 3. **판단 포인트**: 낮은 지연시간(Online)과 대용량 처리(Offline)를 동시에 만족하는 이중 저장소 구조와 데이터 거버넌스(Lineage) 확보가 핵심이다.

## 출제 의도 및 답안 포인트

| 출제 의도 | 반드시 짚을 핵심 | 감점 회피 포인트 |
|:---|:---|:---|
| ML 파이프라인 병목 해결 역량 확인 | Training-Serving Skew 해결, 특징 재사용성 | 단순히 "데이터 저장소"라고만 서술 |
| 아키텍처 설계 이해도 확인 | Online/Offline Store 이중 구조, 시점 정합성 | 기술적 구성 요소(Redis, S3 등) 누락 |
| 실무적 데이터 관리 역량 확인 | Point-in-time Join, Feature Versioning | "데이터가 일관됨"과 같은 추상적 표현 사용 |

> 요약: 학습과 서빙 환경의 데이터 일관성 확보 메커니즘과 중복 개발 방지를 위한 공유 체계 제시가 핵심이다.

---

## Ⅰ. 개요 및 필요성

- 정의: 머신러닝 모델의 특징(Feature) 데이터를 관리, 버전화, 서빙하여 모델 생명주기 전반의 효율성을 높이는 전용 플랫폼
- 배경: 팀별 중복 특징 생성으로 인한 리소스 낭비, 학습(Batch)과 서빙(Real-time) 간 로직 불일치로 인한 모델 성능 저하
- 필요성: 특징 생성 가속화를 통한 실험 주기 단축, 특징 재사용을 통한 데이터 거버넌스 확보, 대규모 실시간 추론 성능 보장

---

## Ⅱ. 구조 및 구성요소

```text
Data Source -> Ingestion (ETL) -> Feature Registry (Metadata)
                                          |
                +-------------------------+-------------------------+
                |                                                   |
        Offline Store (S3/Hive)                           Online Store (Redis/DynamoDB)
        (Training/Batch/Time-travel)                      (Inference/Low-latency)
```

| 구성요소 | 역할 | 특이사항 |
|:---|:---|:---|
| Registry | 특징의 정의, 버전, 메타데이터 관리 | 특징 검색 및 카탈로그 |
| Offline Store | 대규모 과거 데이터 저장 및 학습용 제공 | Point-in-time Correctness |
| Online Store | 실시간 추론을 위한 낮은 지연시간 서빙 | KV 저장소 (Redis 등) |
| Transformation | 원천 데이터로부터 특징 계산 및 인계 | Batch/Stream 처리 |

> 요약: 메타데이터 관리(Registry)와 용도별 저장소(Online/Offline)를 통해 특징의 일관성을 유지함.

---

## Ⅲ. 동작원리 및 흐름도

```text
특징 정의/등록 -> 특징 추출(Batch/Stream) -> Offline/Online 동시 적재 -> 학습용 데이터 조회 -> 실시간 서빙 조회
      |                 |                       |                       |                      |
      +-----------------+-----------------------+-----------------------+----------------------+-----> 품질 모니터링
```

| 단계 | 처리 내용 | 검증 기준 |
|:---:|:---|:---|
| 1 | 특징 정의 및 레지스트리 등록 | 동일 이름 중복 여부 체크 |
| 2 | 데이터 인입 및 특징 가공 | 학습-서빙 로직 동일성 검증 |
| 3 | 시점 정합성 기반 Join (Training) | Data Leakage 방지 확인 |
| 4 | 낮은 지연시간 특징 인출 (Inference) | P99 Latency < 50ms |

> 요약: 로직을 한 번 정의하여 학습과 서빙에 동시에 배포함으로써 환경 간 불일치를 근본적으로 제거함.

## Ⅳ. 특징

| 구분 | 일반 데이터베이스/DW | Feature Store | 판단 포인트 |
|:---|:---|:---|:---|
| 주 목적 | 단순 저장 및 쿼리 | ML 모델 학습 및 서빙 | ML 생명주기 최적화 |
| 시간 관리 | 현재 상태 중심 | 시점별 정확성 (Time-travel) | Point-in-time Join |
| 데이터 구조 | 정형/비정형 테이블 | 특징 벡터 (Feature Vector) | 모델 입력 형태 |
| 일관성 | ACID 준수 | 학습-서빙 일관성 (Skew 방지) | 온라인/오프라인 대칭 |

> 요약: Feature Store는 ML의 특수한 요구사항인 시간 여행 기능과 학습-서빙 일관성에 특화된 저장 시스템임.

## Ⅴ. 심화 비교 및 적용 판단

| 비교 축 | DIY (자체 구축) | Managed/OSS (Feast/Tecton) | 선택 기준 |
|:---|:---|:---|:---|
| 초기 구축 비용 | 높음 (인프라 엔지니어링 필요) | 낮음 (표준 인터페이스 제공) | 전문 인력 및 예산 |
| 유연성 | 최고 (사내 환경 최적화) | 높음 (표준 기능 활용) | 특수 요구사항 유무 |
| 유지보수 부하 | 매우 높음 (버전 관리 등) | 낮음 (패키지화된 기능) | 장기 운영 역량 |

> 요약: 초기에는 Feast와 같은 오픈소스로 시작하여 규모 확장 시 전용 솔루션 또는 자체 고도화를 선택함.

| 리스크 | 원인 | 대응 방안 | 확인 지표 |
|:---|:---|:---|:---|
| Data Leakage | 미래 데이터가 학습에 포함됨 | Point-in-time Join 알고리즘 적용 | 모델 오버피팅 발생률 |
| Serving Latency | Online Store 성능 저하 | Redis 클러스터링 및 메모리 최적화 | P95 Latency 20ms 이하 |
| Feature Drift | 원천 데이터 분포 변화 | 특징별 모니터링 및 알람 설정 | PSI (Population Stability Index) |

> 요약: 데이터 누출은 시점 관리로, 지연은 인프라 최적화로, 분포 변화는 모니터링으로 통제함.

| 점검 항목 | 목표 기준 | 측정 방법 |
|:---|:---|:---|
| 특징 재사용률 | 특징 30% 이상 타 모델 공유 | 카탈로그 내 특징 참조 수 분석 |
| 학습 데이터 준비 시간 | 데이터 준비 시간 50% 단축 | 데이터 엔지니어링 투입 시간 측정 |
| 서빙 지연 시간 | 서빙 지연 100ms 이내 | API 응답 시간 프로파일링 |

> 요약: 도입 효과는 특징 공유 정도, 데이터 준비 속도, 추론 시 특징 인출 성능으로 판정함.

## Ⅵ. 실무 적용 및 결론

**적용 방안 3개:**
1. 중복 개발 방지: 사내 특징 카탈로그를 구축하여 유사 모델 개발 시 기존 특징을 40% 이상 재사용하여 생산성 향상
2. Skew 제거: "고객 등급" 등의 특징 로직을 단일화하여 학습 시 사용한 로직과 실시간 서빙 로직의 100% 일치 보장
3. 실시간 추천 강화: 스트리밍 데이터(Kafka)와 연동하여 사용자의 실시간 행동 특징을 1초 이내에 반영하는 실시간 추천 시스템 구축

**결론 (2줄):**
- 기술사 판단: Feature Store는 단순히 데이터를 담는 그릇이 아니라 ML 모델의 성능과 품질을 결정짓는 "데이터 공급망"의 핵심임
- 향후 방향: 비정형 데이터를 처리하는 임베딩 저장소(Vector DB) 기능을 포함한 통합 특징 플랫폼으로 발전할 것임
