# 📖 【암기용】 개념 완전 이해

## 한눈에
- **정의**: 머신러닝 모델 학습(Offline)과 실시간 추론(Online)에 사용되는 데이터 특징(Feature)들을 일관되게 생성, 저장, 공유, 서빙하는 **중앙 집중형 ML 데이터 플랫폼**.
- **필요성**: 데이터 사이언티스트들이 똑같은 데이터(예: "유저의 최근 7일 평균 결제액")를 각자 주피터 노트북에서 중복으로 짬(시간 낭비). 더 큰 문제는, 학습할 때 썼던 과거 데이터 가공 로직과 상용 서버에서 실시간으로 돌아가는 가공 로직이 미세하게 달라서 모델이 엉뚱한 답을 뱉는 'Training-Serving Skew(학습-서빙 불일치)' 현상이 빈발함.
- **핵심 직관**: 대형 프랜차이즈의 '중앙 식재료 전처리 공장'. 예전엔 각 지점(모델)의 요리사가 직접 양파를 썰고 고기를 재웠음(중복 작업, 지점마다 맛이 다름). Feature Store는 중앙에서 레시피대로 양파와 고기를 완벽하게 손질(Feature Engineering)한 뒤, 냉동창고(오프라인-학습용)와 배달용 냉장고(온라인-실시간 추론용)에 넣어두어 누구나 똑같은 맛을 내게 함.

## 깊이 이해
- **배경**: 우버(Uber)의 Michelangelo 플랫폼에서 최초로 등장. AI 프로젝트의 80%가 데이터 전처리에 소모됨. 모델 알고리즘은 고도화됐으나, 데이터를 공급하는 파이프라인은 여전히 스파게티 코드였음.
- **작동 원리 (이중 저장소 아키텍처)**:
  1. **Registry (메타데이터 등록)**: "최근 30일 접속 횟수"라는 Feature의 SQL/Python 생성 로직과 오너십을 중앙에 등록.
  2. **Offline Store (배치/학습용)**: S3나 하둡 기반의 대용량 저장소. 모델을 학습시키기 위해 과거 수년 치의 엄청난 Feature 데이터를 한 번에 던져줌. (Point-in-Time Join 지원 - 과거 특정 시점의 데이터 뷰를 정확히 재현해 Data Leakage 방지).
  3. **Online Store (실시간/추론용)**: Redis나 DynamoDB 기반. 사용자가 결제 버튼을 누르는 순간, 밀리초(ms) 단위로 최신 Feature 값(예: 1초 전까지의 누적 결제액)을 모델 추론 API에 쏴줌.
- **구체 예시**: 사기 탐지(FDS) 시스템. "이 카드의 최근 10분간 결제 횟수"라는 Feature. 이걸 Feature Store에 정의해 두면, 학습 파이프라인(Airflow)은 작년 1년 치 과거 데이터를 쫙 뽑아가서 모델을 훈련함. 동시에, 실시간 카프카(Kafka) 스트림이 Redis(Online Store)의 값을 계속 업데이트하고, 결제가 들어오면 추론 서버는 Redis에서 5ms 만에 값을 읽어와 사기 여부를 판단함. 로직 불일치 0%.
- **흔한 오해/주의점**: "Feature Store는 그냥 DB나 데이터 웨어하우스(DW) 아닌가요?" $\rightarrow$ 다름. DW는 사람이 보기 위한 분석(BI)용이고, Feature Store는 철저히 **'머신러닝 모델(Machine)'이 읽기 위한 맞춤형 데이터 서빙** 및 **온/오프라인 동기화** 시스템임.

## 연결 개념
- **Training-Serving Skew (학습-서빙 불일치)**: Feature Store가 해결하려는 가장 큰 적. 학습할 때 쓴 데이터 로직과 실제 서비스 서버의 데이터 로직이 달라 성능이 박살나는 현상.
- **Point-in-Time Correctness (시점 정합성)**: 과거 데이터를 가져올 때 '미래의 정보'가 실수로 끼어들지(Data Leakage) 않도록, 정확히 "그 사건이 일어났던 시점"의 데이터만 잘라주는 Feature Store의 핵심 알고리즘.
- **MLOps**: Feature Store는 데이터(DataOps)와 모델(MLOps)을 이어주는 가장 중요한 인프라 다리임.

# 📝 【답안용】 시험 답안 템플릿
## 핵심 인사이트 (3줄 요약)
- **본질**: 머신러닝 파이프라인의 핵심인 피처(Feature) 데이터의 정의, 가공, 저장, 서빙 메커니즘을 중앙화하여, 다수 모델 간 피처의 재사용성을 극대화하고 데이터 파편화를 방지하는 MLOps 핵심 데이터 플랫폼.
- **가치**: 모델 학습(Batch)과 실시간 서빙(Stream) 환경 간의 피처 가공 로직 불일치로 인한 **Training-Serving Skew** 문제를 원천 차단하고, 피처 엔지니어링의 중복을 제거하여 AI 서비스의 Time-to-Market을 획기적으로 단축함.
- **판단 포인트**: Feature Store의 아키텍처 설계 시, 대규모 과거 데이터를 위한 Offline Store(Data Lake)와 초저지연(Low-latency) 실시간 추론을 위한 Online Store(In-memory DB) 간의 양방향 동기화 및 시점 정합성(Point-in-time Correctness) 조인이 필수적임.

## Ⅰ. 개요 및 필요성
- **정의**: 기계학습 모델의 훈련(Training)과 추론(Inference) 단계에 필요한 특징 변수(Feature)들을 일관되게 생성하고 제공하는 이중화된(온/오프라인) 저장소 및 메타데이터 관리 시스템.
- **배경**: AI/ML 도입 확대로 부서마다 동일한 피처를 중복 가공(Silo)하여 컴퓨팅/인력 리소스가 낭비되고, 로컬 노트북 환경의 스크립트가 상용 배포 환경으로 매끄럽게 이관되지 못하는 병목 발생.
- **필요성**: 피처 로직의 단일 진실 공급원(SSOT, Single Source of Truth) 확보, 미래 데이터 누수(Data Leakage)를 방지하는 안전한 과거 데이터 스냅샷 제공, 모델 서빙 API에 대한 P99(99퍼센타일) 지연 시간 보장.

## Ⅱ. Feature Store 아키텍처 4대 구성요소
온/오프라인 듀얼 엔진 구조.
| 구성 요소 | 핵심 기능 및 메커니즘 | 구현 기술 예시 |
|:---:|:---|:---|
| **Feature Registry**<br>(레지스트리) | 피처의 생성 로직(SQL/Python), 소유자, 버전, 설명 등의 메타데이터 카탈로그. 검색 및 재사용 촉진. | Hive Metastore, MLflow |
| **Offline Store**<br>(오프라인 스토어) | 모델 학습 및 일괄(Batch) 추론용 대용량 히스토리 데이터 저장. Point-in-time Join 수행. | AWS S3, Snowflake, BigQuery |
| **Online Store**<br>(온라인 스토어) | 실시간 추론(Inference) 시 모델에 피처 벡터를 밀리초 단위로 서빙. 최신 상태값(KV)만 유지. | Redis, DynamoDB, Cassandra |
| **Data Transformation**<br>(변환 엔진) | 원천 데이터(Source)를 주기적(배치) 또는 실시간(스트리밍)으로 가공하여 스토어에 동기화 적재. | Apache Spark, Flink, dbt |

## Ⅲ. Training-Serving Skew 방지 메커니즘
동일 로직, 양방향 서빙.
1. **문제 발생 구조 (Skew)**:
   - 데이터 사이언티스트는 Python(Pandas)으로 과거 1년 치 DB를 덤프 떠서 학습함(Offline).
   - 백엔드 개발자는 Java/Go로 동일한 로직을 재구현하여 실시간 API에서 데이터를 가져옴(Online). (언어/환경 차이로 값의 미세한 불일치 발생 $\rightarrow$ 모델 성능 하락).
2. **Feature Store 기반 해결책**:
   - 피처 생성 로직을 Registry에 **단 1회만 선언(Declare)**.
   - 변환 엔진(Spark/Flink)이 이 단일 로직을 물고 배치는 Offline Store에, 실시간 스트림은 Online Store에 **동시 업데이트**.
   - 모델은 학습 시 Offline에서, 서빙 시 Online에서 값을 당겨 쓰므로 논리적 불일치가 수학적으로 0%가 됨.

## Ⅳ. Point-in-Time Correctness (데이터 누수 방지 조인)
타임머신(Time-travel) 데이터 추출 기술.
- **정의**: 모델을 학습하기 위해 과거 $T_1$ 시점의 데이터를 추출할 때, $T_1$ 이후에 발생한 미래의 정보가 실수로 포함되는 데이터 누수(Data Leakage)를 방지하는 시계열 조인(Asof Join) 기법.
- **동작**: "2023-10-01 14:00의 사기 결제 내역"을 기준으로 학습 데이터를 만들 때, 일반 SQL 조인을 쓰면 14:00 이후에 업데이트된 유저 정보가 딸려 올 위험이 있음. Feature Store는 레코드별 타임스탬프를 엄격히 대조하여 정확히 "14:00 시점까지 알려진 최신값"만을 매핑하여 훈련용 데이터셋을 생성함.

## Ⅴ. 실무 적용 및 결론
- **판단 지표**: 모델 배포 전 피처 파이프라인 재구축 소요 시간(주 $\rightarrow$ 일), 사내 모델 간 피처 재사용률(Feature Reuse Rate, 30% 이상 목표), 실시간 추론 시 Online Store P95 응답 지연(Latency < 10ms).
- **실무 설계**: 금융권 B사의 '초개인화 추천 시스템' 구축. 기존엔 "고객의 최근 1시간 검색 키워드" 피처를 만들기 위해 추론 서버가 매번 실시간으로 RDB를 풀스캔하여 부하 발생 및 2초 이상의 지연. 조치 방안: 오픈소스 Feast 기반 Feature Store 구축. 1) 카프카(Kafka)를 통해 유저 행동 로그를 스트리밍으로 수집하고, Flink가 슬라이딩 윈도우로 집계하여 Redis(Online)에 1초 단위로 업데이트. 2) 추천 모델은 Redis에서 `user_id`를 Key로 O(1) 시간에 즉시 피처를 조회해 P99 응답을 15ms 이내로 단축. 3) 야간에 Spark 배치가 S3(Offline)로 데이터를 스냅샷하여 재학습 파이프라인(CT) 가동.
- **결론**: 알고리즘 혁신이 한계에 다다른 현 MLOps 생태계에서, 모델의 성능 우위는 "얼마나 양질의 데이터를, 얼마나 적시(Right Time)에 주입할 수 있는가(Data-centric AI)"에 달려있다. Feature Store는 파편화된 데이터 전처리 과정을 중앙 통제형 '피처 공급망'으로 혁신하여, AI 조직의 생산성과 모델의 상용 환경 안정성을 동시에 보장하는 인프라의 마스터키다.

### 🔀 문제 유형별 목차 전환
- **Ⅱ·Ⅲ 강조 (개념/원리형)**: MLOps 성숙도 모델과 연계. MLOps Level 0(수동)에서 Level 2(자동화 파이프라인)로 넘어가기 위한 선제 조건으로서의 Feature Store 아키텍처 및 메타데이터 카탈로그(Registry)의 엔티티-피처-뷰(Entity-Feature-View) 추상화 데이터 모델 설계.
- **Ⅴ·Ⅵ 강조 (실무/설계형)**: 거대 언어 모델(LLM) 환경에서의 Vector DB와의 결합 방안. 정형 데이터(나이, 구매력)는 전통적 Feature Store(Redis)에서, 비정형 데이터(문서, 리뷰 임베딩)는 Vector Store(Milvus 등)에서 동시에 밀리초(ms) 단위로 호출하여 프롬프트를 동적으로 구성(RAG)하는 복합 추론 아키텍처.
