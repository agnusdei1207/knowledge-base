# 📖 【암기용】 개념 완전 이해

> 목적: SLSA를 처음 봐도 완벽히 이해하게 만든다. 시험 답안 양식이 아니라, 이해를 위한 친절한 설명이다.

## 한눈에
- **개요**: 소프트웨어 공급망 전체의 무결성을 확보하기 위한 보안 등급 체계 (프레임워크)
- **왜 필요한가**: 소스 코드 작성부터 빌드, 배포까지의 과정 중 어디서든 코드가 변조될 수 있기 때문에, 이를 방지하고 추적할 수 있는 표준이 필요하다.
- **핵심 직관**: "소프트웨어 탄생의 모든 과정을 증명서(Attestation)로 남기고 등급을 매겨 관리하자."

## 깊이 이해
- **배경·문제의식**: SolarWinds, Log4j 사태처럼 오픈소스나 빌드 시스템을 직접 공격하는 '공급망 공격'이 급증함. 단순히 코드만 검사하는 것으로는 부족하고, '빌드 과정 자체가 안전했는가'를 보증해야 함.
- **작동 원리**: SLSA는 빌드 과정의 무결성을 4단계 등급(Level 1~4)으로 나눔. 소스 코드 관리, 빌드 프로세스, 배포 과정을 '증명서'라는 형태로 기록하고, 이를 검증함. 빌드 환경의 격리성, 비변조성, 2인 검토 등을 핵심 요건으로 함.
- **비유**: 식료품의 'HACCP 인증'과 같음. 재료(소스)부터 공장(빌드), 유통(배포) 전 과정을 기록하고 등급을 매겨 안전함을 보증함.
- **구체 예시**: GitHub Actions로 빌드할 때 SLSA Generator를 쓰면 빌드 결과물과 함께 '누가, 언제, 어떤 코드로 빌드했는지' 적힌 비변조 JSON 증명서가 생성됨.
- **흔한 오해·주의점**: SLSA는 취약점 스캔 툴이 아님. 코드가 안전한지가 아니라, '코드가 빌드되어 배포되는 과정이 투명하고 믿을 수 있는가'를 다룸.

## 연결 개념
- SBOM (Software Bill of Materials) - SLSA를 위한 핵심 구성 요소
- Sigstore - SLSA 증명서 서명 및 검증 기술
- DevSecOps - 공급망 보안이 내재화된 개발 운영 환경

# 📝 【답안용】 시험 답안 템플릿

> 목적: 시험장에서 25분에 그대로 쓰는 답안 양식. 작성방식(추상표현 금지·수치·도식·문제유형 전환)을 엄격히 지킨다.
> 핵심: 단순히 등급만 나열하지 말고, 공급망 위협 모델과 대응 기술(Attestation, Provenance)을 연결해 실무적 무결성 확보 방안을 제시한다.

## 핵심 인사이트 (3줄 요약)

> 1. **본질**: SLSA는 소프트웨어 공급망의 아티팩트 무결성을 보장하기 위해 구글이 제안한 체크리스트 기반 보안 성숙도 모델이다.
> 2. **가치**: 빌드 부산물(Provenance) 생성을 강제하여 소스 변조, 빌드 시스템 침해 등 공급망 전반의 위협을 정량적 등급으로 통제한다.
> 3. **판단 포인트**: 빌드 환경의 격리(Isolation)와 증명서의 비변조성(Non-falsifiability) 확보 여부가 등급 결정의 핵심이다.

## 출제 의도 및 답안 포인트

| 출제 의도 | 반드시 짚을 핵심 | 감점 회피 포인트 |
|:---|:---|:---|
| 공급망 보안 체계 이해도 확인 | SLSA 4단계 등급, Provenance(출처), 증명서 기반 검증 | SBOM과 혼동 주의 (SLSA는 프로세스 중심) |
| 실제 공격 대응 시나리오 확인 | 빌드 침해, 소스 주입 방어 메커니즘 | 단순 체크리스트 나열에 그침 (기술적 근거 부족) |
| 보안 아키텍처 설계 역량 확인 | 증명서 생성 및 검증 파이프라인 (Sigstore 연계) | 추상적인 "보안 강화" 표현 사용 |

> 요약: SLSA는 '누가, 어떻게 만들었는가'를 증명하여 공급망 신뢰 사슬(Chain of Trust)을 구축하는 프레임워크이다.

---

## Ⅰ. 개요 및 필요성

- 정의: 소프트웨어 공급망의 무결성을 보장하기 위한 체크리스트 형태의 보안 표준 및 등급 체계 (v1.0 기준)
- 배경: SolarWinds 사태 등 빌드/배포 파이프라인을 직접 겨냥한 공급망 공격(Supply Chain Attack) 가속화
- 필요성: 빌드 과정의 투명성 확보, 신뢰할 수 없는 아티팩트의 배포 차단, 보안 위협의 가시성 확보

---

## Ⅱ. 구조 및 구성요소

```text
Source -> Build -> Distribution -> Deployment
  |         |           |             |
  +-> Metadata Generation (Provenance) -> Verification
             | (Signed by Sigstore)
             V
        SLSA Level (1~4) / 무결성 보장
```

| 구성요소 | 역할 | 특이사항 |
|:---|:---|:---|
| Provenance | 아티팩트의 출처, 빌드 도구, 파라미터 기록 | 증명서(Attestation) 형태 |
| Build System | 소스를 아티팩트로 변환하는 격리된 환경 | Ephemeral(휘발성) 환경 권장 |
| Policy Engine | SLSA 요건 충족 여부를 판단하고 배포 통제 | Admission Controller 연계 |

> 요약: 소스에서 배포까지의 모든 이벤트를 증명서(Provenance)로 남기고, 이를 정책 엔진이 검증하는 구조이다.

---

## Ⅲ. 동작원리 및 흐름도

```text
개발자 -> 소스 Commit -> CI/CD 트리거 -> 격리 빌드 실행 -> Provenance 생성
                                          |                |
                                          +-> 서명/저장 <----+
                                          |
                                      운영 환경 배포 -> 증명서 검증 -> 실행 승인
```

| 단계 | 처리 내용 | 검증 기준 |
|:---:|:---|:---|
| 1 | 빌드 프로세스 시작 | 빌드 정의 파일(예: YAML) 존재 여부 |
| 2 | Provenance 생성 | 빌드 결과물에 대한 메타데이터 기록 자동화 |
| 3 | 무결성 서명 | Sigstore 등을 통한 비변조 증명서 서명 |
| 4 | 배포 시 검증 | 정책 엔진이 요구 등급(L3 이상 등) 충족 확인 |

> 요약: 빌드 시점에 생성된 서명된 증명서를 배포 시점에 검증하여 공급망의 신뢰를 유지한다.

---

## Ⅳ. 특징 (SLSA 등급 체계)

| 등급 | 주요 요건 | 보안 수준 |
|:---|:---|:---|
| Level 1 | 빌드 프로세스 기록 및 문서화 | 가시성 확보 시작 |
| Level 2 | 빌드 도구에 의한 서명된 Provenance 생성 | 소프트웨어 변조 방지 기초 |
| Level 3 | 빌드 플랫폼의 보안성 및 격리성 확보 | 신뢰할 수 있는 빌드 환경 |
| Level 4 | 2인 검토(Two-person review), Hermetic 빌드 | 고도의 무결성 보장 (최고 수준) |

> 요약: 등급이 높을수록 빌드 환경의 격리성과 프로세스의 비변조성이 강화되며, L4는 완벽한 폐쇄형 빌드를 지향한다.

---

## Ⅴ. 심화 비교 및 적용 판단

| 비교 축 | SBOM (Software Bill of Materials) | SLSA (Supply-chain Levels) | 선택 기준 |
|:---|:---|:---|:---|
| 중심 영역 | 아티팩트 구성 성분 (What) | 빌드 및 배포 프로세스 (How) | 성분 분석 vs 프로세스 신뢰 |
| 표준 포맷 | SPDX, CycloneDX | SLSA Provenance (In-toto) | 호환성 및 자동화 요건 |
| 가치 | 취약점 라이브러리 추적 | 공급망 무결성 및 변조 방지 | 위협 모델에 따른 병행 적용 |

> 요약: SBOM은 '무엇'이 들어있는지를, SLSA는 '어떻게' 만들어졌는지를 다루며 상호 보완적으로 작용한다.

| 리스크 | 원인 | 대응 방안 | 확인 지표 |
|:---|:---|:---|:---|
| 빌드 플랫폼 오염 | 빌드 서버 영구적 침해 | Ephemeral Build 환경 사용, 빌드 후 즉시 폐기 | 빌드 노드 생존 시간 (TTL) |
| Provenance 위조 | 비인증된 주체의 증명서 생성 | OIDC 기반 ID 바인딩 및 Sigstore 서명 강제 | 서명 검증 성공률 100% |
| 보안 피로도 증가 | 단계별 증명 및 검토 부하 | CI/CD 파이프라인에 SLSA Generator 자동화 내재화 | 빌드 당 수동 개입 횟수 (0회 목표) |

> 요약: 자동화된 빌드 환경과 비변조 증명 메커니즘을 통해 공급망 보안의 운영 복잡성을 통제해야 한다.

| 점검 항목 | 목표 기준 | 측정 방법 |
|:---|:---|:---|
| 무결성 검증 | 비인가 아티팩트 배포 차단 100% | 정책 엔진 거부 로그 분석 |
| 빌드 격리성 | 빌드 간 네트워크/파일 시스템 차단 | 정적/동적 샌드박스 환경 점검 |
| 검토 준수율 | Critical 코드에 대한 2인 검토 100% | 코드 리뷰 로그 및 승인 데이터 |

> 요약: SLSA 도입 효과는 증명서 기반 배포 통제 성공률과 빌드 환경의 격리 지표로 측정한다.

---

## Ⅵ. 실무 적용 및 결론

**적용 방안 3개:**
1. **CI/CD 내재화**: GitHub Actions 또는 Tekton에 SLSA Provenance Generator를 적용하여 빌드 시점에 자동으로 L3 수준의 증명서 생성
2. **Admission Control 연계**: Kubernetes 환경에서 Kyverno나 OPA를 사용하여 SLSA 증명서가 없는 컨테이너 이미지의 실행을 차단
3. **오픈소스 거버넌스**: 외부 오픈소스 도입 시 해당 프로젝트의 SLSA 등급을 확인하고, L3 미만인 경우 내부 보안 검수를 강화하는 기준 수립

**결론 (2줄):**
- 기술사 판단: SLSA는 보안 사후 대응이 아닌 '보안 설계(Secure by Design)' 관점의 접근이며, 클라우드 네이티브 환경에서 필수적인 공급망 신뢰 기반이다.
- 향후 방향: V2.0에서는 빌드뿐만 아니라 소스 및 종속성 관리 요건이 구체화될 전망이므로, 전사적 DevSecOps 성숙도 모델과 연계한 로드맵이 필요하다.
