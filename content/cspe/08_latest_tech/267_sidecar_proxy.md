# 📖 【암기용】 개념 완전 이해

> 목적: 애플리케이션 코드를 1줄도 수정하지 않고도 통신, 로깅, 모니터링 기능을 추가할 수 있는 클라우드 네이티브의 핵심 디자인 패턴을 이해한다.

## 한눈에
- **정의**: 오토바이에 붙은 '사이드카(보조석)'처럼, **메인 애플리케이션 컨테이너 옆에 동일한 생명주기를 가진 보조 컨테이너(Proxy)를 띄워 네트워크와 모니터링 등의 부가 기능을 대신 처리하게 하는 아키텍처 패턴**
- **필요성**: 기존에는 로깅, 보안, 통신 코드를 비즈니스 로직에 섞어서 짜야 했지만, 언어가 바뀌면 코드를 다시 짜야 하고 유지보수가 지옥 같았기 때문에 이를 완전히 분리(Decoupling)하기 위함
- **핵심 직관**: "연예인(메인 앱)이 직접 짐 들고 운전하고 스케줄을 잡는 게 아니라, 매니저(사이드카 프록시)를 무조건 1명씩 붙여줘서 연예인은 '노래(비즈니스 로직)'만 부르게 하는 것"

## 깊이 이해
- **배경(왜 등장했나?)**: 마이크로서비스(MSA)가 도입되자, 하나의 앱이 수백 개의 서비스로 쪼개졌다. Java, Python, Go 등 다양한 언어로 개발되었는데, 모든 서비스에 공통으로 필요한 "A 서비스 호출 시 3번 실패하면 포기해(Retry)" 같은 코드를 언어마다 따로 라이브러리로 만들어 배포해야 했다. 넷플릭스 OSS가 이 방식으로 고통받다가 결국 포기했다.
- **작동 원리(어떻게 달성했나?)**: 
  1. K8s의 **Pod(파드)** 구조를 절묘하게 이용한다. Pod 안에는 여러 개의 컨테이너를 띄울 수 있고, 이들은 IP 주소와 볼륨을 공유한다.
  2. 메인 앱 컨테이너 옆에 'Envoy' 같은 프록시 컨테이너를 띄운다.
  3. K8s의 iptables(네트워크 라우팅 규칙)를 조작해서, **메인 앱이 밖으로 내보내는 모든 네트워크 통신 전반을 사이드카가 강제로 가로채게(Intercept) 만든다.**
  4. 사이드카가 암호화, 로깅 등을 싹 처리하고 진짜 목적지로 보내준다.
- **일상 비유**: 정수기를 쓸 때, 물통(앱) 자체에 필터(통신/보안 로직)를 내장하는 게 아니라, 물이 나오는 배관 중간에 '외장형 필터(사이드카)'를 다는 것. 물통은 그냥 물만 쏟아내면 되고, 불순물 제거나 온수 변환은 필터가 알아서 해준다.
- **구체 예시**: 서비스 메시의 절대 표준인 'Istio'가 사용하는 'Envoy' 프록시가 가장 대표적인 사이드카 프록시다. 로깅을 모아주는 Fluentd를 사이드카로 붙이는 패턴도 흔하다.
- **흔한 오해/주의점**: "사이드카는 무조건 좋은가?" → 아니다. 앱이 통신할 때마다 `App ➔ Sidecar ➔ Sidecar ➔ App`으로 거쳐 가야 하므로 **네트워크 지연(Latency)**이 무조건 증가한다. 또한 1,000개의 Pod를 띄우면 사이드카도 1,000개가 떠야 해서 **메모리/CPU 낭비**가 극심하다. (이 때문에 최근 Sidecarless 아키텍처가 연구되고 있다.)

## 연결 개념
- **Service Mesh**: 사이드카 패턴을 클러스터 전체에 수백, 수천 개 단위로 깔아서 거대한 그물망(Mesh)을 만든 시스템
- **Envoy**: 사이드카 패턴을 위해 Lyft에서 C++로 개발한 극도로 빠르고 가벼운 오픈소스 프록시
- **Separation of Concerns (관심사의 분리)**: 사이드카 패턴을 관통하는 철학. 비즈니스 로직과 인프라 로직을 물리적으로 분리함.

# 📝 【답안용】 시험 답안 템플릿

## 핵심 인사이트 (3줄 요약)
> 1. **본질**: 사이드카 프록시(Sidecar Proxy)는 K8s의 Pod 내에 메인 애플리케이션과 동일한 라이프사이클을 공유하는 프록시 컨테이너를 배치하여, 트래픽을 가로채고(Intercept) 통제하는 디자인 패턴이다.
> 2. **가치**: 애플리케이션 코드에 침투하지 않는(Non-invasive) 방식으로 통신, 보안, 로깅 기능을 제공하여 관심사의 분리(Separation of Concerns)를 실현하고 Polyglot(다국어) 환경의 운영을 단순화한다.
> 3. **판단 포인트**: 서비스 메시(Service Mesh)를 구현하는 핵심 요소이나, 수만 개의 컨테이너 환경에서는 자원 오버헤드와 레이턴시 페널티가 발생하므로 최근 eBPF 기반의 Sidecarless 패턴과의 트레이드오프 분석이 필요하다.

## Ⅰ. 개요 및 필요성
- **정의**: 클라우드 네이티브 환경에서 메인 컨테이너의 기능을 확장하거나 보조하기 위해, 동일한 논리적 호스트(Pod) 내에 별도의 컨테이너를 배치하는 디자인 패턴
- **배경**: 분산 시스템 환경에서 서비스 디스커버리, 로드 밸런싱, 서킷 브레이킹 등의 인프라 로직을 비즈니스 코드와 결합할 경우(Fat-client), 코드 복잡도 증가 및 언어별 라이브러리 파편화 문제 발생
- **필요성**: 비즈니스 로직의 순수성 유지, 인프라 계층(Layer 7)에 대한 일관된 통제권 확보, 코드 수정 없는 투명한 네트워크 프록싱(Transparent Proxying) 적용

## Ⅱ. Sidecar Proxy 작동 메커니즘 (iptables 트래픽 가로채기)
쿠버네티스 환경에서 사이드카 프록시는 iptables NAT 룰 조작을 통해 투명하게 트래픽을 가로챈다.

```text
  ┌───────────────── K8s Pod (Shared Network Namespace) ─────────────────┐
  │                                                                      │
  │  ┌──────────────┐         (localhost)         ┌───────────────────┐  │
  │  │              │ ◀─────── 1. 수신 ─────────  │                   │  │
  │  │ Main App (A) │                             │ Sidecar (Envoy)   │  │
  │  │              │ ─── 2. 발신 (Intercept) ──▶ │                   │  │
  │  └──────────────┘                             └────▲─────────┬────┘  │
  │                                                    │         │       │
  └────────────────────────────────────────────────────┼─────────┼───────┘
                                                       │         ▼
                                            [ Inbound Traffic ] [ Outbound Traffic ]
```

1. **공유 네트워크 공간**: Pod 내의 컨테이너들은 하나의 IP와 `localhost`를 공유한다.
2. **Outbound Intercept**: App A가 외부(Service B)로 API를 호출하면, K8s iptables 규칙에 의해 트래픽이 App A 몰래 사이드카(Envoy)로 리다이렉트된다.
3. **Proxying & mTLS**: 사이드카는 목적지 Service B의 사이드카와 mTLS(상호 암호화) 세션을 맺고 트래픽을 전달한다.
4. **Inbound Intercept**: 외부에서 들어오는 트래픽도 반드시 사이드카를 거쳐 암호화 해제 후 `localhost`를 통해 App A로 전달된다.

## Ⅲ. 사이드카 패턴의 3대 핵심 적용 사례
| 패턴 종류 | 역할 | 구체적 유스케이스 | 대표 도구 |
|:---|:---|:---|:---|
| **Ambassador (대사)** | 앱을 대신하여 **외부 네트워크 통신** 전담 | 서비스 메시 라우팅, 서킷 브레이커, 타임아웃, 재시도 제어 | **Envoy, Nginx** |
| **Adapter (어댑터)** | 이기종 시스템 간의 **데이터 포맷 변환** | 레거시 앱이 뱉는 로그 형식을 K8s 표준 메트릭 포맷으로 변환 | **Prometheus Exporter** |
| **Sidecar (로그/파일)** | 메인 앱의 **보조 작업 (동기화/로깅)** 전담 | 메인 앱이 디렉토리에 로그를 쌓으면 사이드카가 중앙 서버로 전송 | **Fluentd, Logstash** |

## Ⅳ. 기존 방식(Fat Client) vs Sidecar 방식 비교
| 비교 지표 | 라이브러리 방식 (Spring Cloud 등) | Sidecar Proxy 방식 (Istio/Envoy) |
|:---|:---|:---|
| **비즈니스 코드 결합도** | 매우 높음 (코드 내부에 침투) | **완전 분리 (코드는 통신 사실을 모름)** |
| **다국어(Polyglot) 지원**| 언어별 라이브러리 별도 개발 필요 (Java 중심) | **모든 언어 및 프레임워크에 100% 호환** |
| **업데이트 및 배포** | 통신 로직 변경 시 모든 앱 재빌드 및 재배포 | **앱 중단 없이 프록시 설정만 중앙에서 동적 변경** |
| **자원 소모 (Overhead)** | 앱 메모리 일부만 소모 | **별도의 컨테이너 구동으로 CPU/Memory 추가 소모** |

## Ⅴ. 기술적 한계(리스크) 및 최신 대안 (Sidecarless)
| 리스크 요인 | 아키텍처적 한계 | 극복 동향: Sidecarless (eBPF) |
|:---|:---|:---|
| **리소스 오버헤드** | 클러스터에 10,000개의 Pod가 있으면 Envoy 컨테이너도 10,000개가 추가로 실행되어야 함 | 리눅스 커널의 **eBPF(Cilium)**를 활용하여, 컨테이너 없이 커널 레벨에서 트래픽을 라우팅/암호화하여 리소스 낭비 제로화 |
| **네트워크 레이턴시** | 통신 1회당 `App ➔ Sidecar ➔ Sidecar ➔ App` 4번의 TCP 스택을 타야 하므로 지연 시간 2~3ms 증가 | 커널 내 소켓 우회(Socket Bypass)를 통해 프록시를 거치지 않고 직접 통신 |
| **시작/종료 순서 문제** | 앱이 먼저 뜨고 사이드카가 나중에 뜨면 통신 실패 발생 | K8s 1.28부터 **Sidecar Container** 기능이 정식 도입되어 생명주기 순서 제어 기능 제공 |

## Ⅵ. 실무 적용 및 결론
**적용 방안 및 실무 가이드:**
1. **OOM(Out Of Memory) 방지 설정**: Envoy 사이드카도 엄연한 컨테이너이므로, 반드시 K8s YAML에 CPU/Memory `Request`와 `Limit`을 명시해야 한다. 그렇지 않으면 트래픽 폭주 시 사이드카가 노드 자원을 다 먹어버리는 장애가 발생한다.
2. **K8s Native Sidecar 활용**: 과거에는 일반 컨테이너를 사이드카처럼 취급했으나, 최근 K8s 업데이트에 추가된 `restartPolicy: Always` 기반의 네이티브 사이드카 속성을 사용하여 안정적인 초기화(Init)를 보장해야 한다.

**결론:**
- 사이드카 프록시는 애플리케이션에서 **'네트워크 인프라 로직을 완전히 도려내어 인프라 계층으로 넘겨준'** 클라우드 네이티브 역사상 가장 위대한 디자인 패턴이다.
- 자원 오버헤드라는 명확한 단점이 있으나, 이는 인프라 비용과 개발자의 생산성을 맞바꾼 트레이드오프이며, 향후 eBPF 기반의 차세대 메시 아키텍처로 넘어가기 전까지 엔터프라이즈 MSA 네트워크를 지배할 핵심 기술이다.
