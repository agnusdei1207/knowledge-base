## Ⅰ. 개요
- **정의**: LLM의 무상태(Stateless) 한계를 보완하여 과거 맥락을 저장·인출하는 정보 관리 계층
- **배경/필요성**: LLM API는 호출마다 초기화되어 이전 대화를 알지 못함. 대명사("그 파일"), 과거 선호("지난번처럼") 해석을 위해 외부 메모리 모듈이 필수적임
- **비유**: 단기 기억은 칠판(세션 끝나면 지워짐), 장기 기억은 일기장(영구 보관)

| 출제 의도 | 반드시 짚을 핵심 | 감점 회피 포인트 |
|:---|:---|:---|
| LLM 무상태 한계 극복 구조 | 단기(Context Window)·장기(Vector DB) 이원 구조 | 단순 "메모리 추가"가 아닌 인코딩→저장→인출→디코딩 파이프라인 설명 필요 |
| 개인화 에이전트 설계 역량 | RAG와 메모리의 관계(개인화 RAG) | 토큰 폭발·기억 충돌 문제를 문제점으로 반드시 언급 |

> 요약: Stateless LLM에 단기·장기 이원 메모리를 부착하여 맥락 유지 및 개인화를 구현하는 아키텍처

## Ⅱ. 구성요소
```text
+--------------------------------------------------+
|            Agent Memory Architecture             |
|  +--------------------+  +---------------------+ |
|  | Short-term Memory  |  | Long-term Memory    | |
|  | (Context Window)   |  | (Vector DB/Graph)   | |
|  | - Message History  |  | - Embedding Store   | |
|  | - Scratchpad       |  | - Knowledge Graph   | |
|  +--------+-----------+  +---------+-----------+ |
|           |                        |              |
|           v                        v              |
|  +--------------------------------------------+  |
|  |     Memory Retrieval & Fusion Engine        |  |
|  |  (Cosine Similarity + Recency Scoring)      |  |
|  +--------------------+------------------------+  |
|                       |                           |
|                       v                           |
|              +------------------+                 |
|              | Prompt Injection |                 |
|              | (Context 증강)    |                 |
|              +--------+---------+                 |
|                       |                           |
|                       v                           |
|                  [ LLM 추론 ]                      |
+--------------------------------------------------+
```

| 구성요소 | 설명 | 비유 |
|:---|:---|:---|
| Short-term Memory | 세션 내 대화 이력을 Context Window에 유지하는 휘발성 저장소 | 칠판 — 수업 끝나면 지움 |
| Long-term Memory | 임베딩 벡터 또는 지식 그래프로 영구 보존하는 비휘발성 저장소 | 일기장 — 서랍에 보관 |
| Retrieval & Fusion | 유사도·최신성 기반으로 관련 기억을 검색하여 프롬프트에 병합하는 엔진 | 사서 — 질문에 맞는 책을 찾아줌 |

> 요약: 단기(휘발)·장기(영구) 저장소 + 검색·융합 엔진 + 프롬프트 주입의 4계층 구조

## Ⅲ. 절차
```text
+----------------+     +----------------+     +----------------+     +----------------+
| 1. Encoding    | --> | 2. Storage     | --> | 3. Retrieval   | --> | 4. Decoding    |
| (정보 추출)     |     | (계층별 저장)   |     | (유사도 인출)   |     | (프롬프트 주입) |
+----------------+     +----------------+     +----------------+     +----------------+
```

1. **Encoding(정보 추출)** — 대화·도구 결과에서 기억 가치가 있는 핵심 팩트(취향, 이벤트)를 LLM으로 추출함
2. **Storage(계층별 저장)** — 단기 기억은 Message History 배열에 누적, 장기 기억은 임베딩 변환 후 Vector DB에 적재함
3. **Retrieval(유사도 인출)** — 새 질의 입력 시 Cosine Similarity 기반으로 관련 과거 기억을 장기 저장소에서 검색함
4. **Decoding(프롬프트 주입)** — 인출된 기억을 현재 프롬프트의 시스템 컨텍스트로 삽입하여 개인화 응답을 생성함

> 요약: 추출 → 계층 저장 → 유사도 인출 → 프롬프트 주입의 4단계 파이프라인

## Ⅳ. 문제점
- **토큰 폭발(Token Explosion)**: 장기 기억을 무분별하게 인출하면 1회 호출 토큰 비용이 급증함 — 기억 누적량과 비용이 비례하는 구조적 원인
- **기억 충돌(Memory Conflict)**: "학생임(과거)" vs "직장인임(현재)" 등 시점이 다른 팩트가 동시 인출될 때 모순 응답 생성 — 기억에 시간 메타데이터가 부재한 원인
- **기억 환각(Memory Hallucination)**: 검색된 기억 조각을 LLM이 잘못 연결하여 왜곡된 사실을 주장함 — 유사도 검색의 의미적 오매칭이 원인

> 요약: 비용 급증, 시점 모순, 의미 왜곡이 메모리 아키텍처의 3대 난제

## Ⅴ. 개선방안
1. 단기: Summary Buffer 도입 — 오래된 단기 기억을 LLM으로 1줄 요약하여 토큰 소모 50% 이상 절감
2. 중기: Memory Lifecycle Management — 기억에 타임스탬프를 부여하고 Recency 가중치로 최신 팩트를 우선 적용, 낡은 기억은 자동 아카이브
3. 장기: Prompt Caching 연동 — 변경 없는 기억 프리픽스를 GPU VRAM에 캐싱하여 반복 과금 제거(Anthropic Prompt Caching 등)

- **기억 환각**: 유사도 임계값 미달 기억 인출 → Top-K 필터링 + 팩트 검증 체인 추가 (지표: 환각률 < 2%)

> 요약: 요약 압축 → 생애주기 관리 → 캐싱 최적화 순으로 비용·정합성·성능 동시 개선

## Ⅵ. 전망
- **향후 발전 방향**: 200만 토큰급 Context Window(Gemini 1.5 Pro)와 KV Cache의 발전으로, 외부 DB 없이 모델 내부에 전체 기억을 적재하는 In-context Memory 방식이 병행 확산될 전망
- **기술사적 판단**: Vector DB 기반 장기 기억과 거대 컨텍스트 윈도우는 대체 관계가 아닌 보완 관계임. 비용·지연·정합성 트레이드오프에 따라 하이브리드 설계가 현실적임
- **기술사 제언**: 메모리 계층 설계 시 PII 스크러빙 전처리와 GDPR 삭제권(Right to Erasure) 대응을 아키텍처 초기 단계에서 반영할 것을 권고함
