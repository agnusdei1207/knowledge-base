# 📖 【암기용】 개념 완전 이해

## 한눈에
- **개요**: **에이전트 메모리**는 **AI 에이전트**(001 참조)가 대화·업무 상태·과거 결과·사용자 선호를 저장하고 필요할 때 다시 꺼내 판단에 반영하는 상태 저장 계층이다. 지속 기간에 따라 단기(현재 세션)와 장기(세션을 넘는 누적 지식)로 나뉜다.
- **왜 필요한가**: **LLM**은 호출이 끝나면 방금 나눈 대화를 잊는 무상태(stateless) 함수라, 다단계 업무에서 이전 결정·실패 이력·도구 결과를 이어가려면 외부 기억 장치가 필요하다.
- **핵심 직관**: 메모리는 에이전트가 매번 처음 만난 것처럼 행동하지 않게 하는 "업무 수첩"이다. 짧게 쓰고 지울 메모(단기)와 오래 보관할 서류철(장기)을 나눠 관리한다.

## 핵심 용어 정리 (내부에 등장하는 것들)
아래 용어는 답안 본문(Ⅰ~Ⅵ·표)에 그대로 등장하므로, 처음 보는 사람도 이해하도록 비유와 함께 먼저 정리한다.

| 용어/표기 | 의미 | 비유·예 |
|:---|:---|:---|
| 에이전트 메모리(핵심) | 대화·상태·이력·선호를 저장·인출해 에이전트 판단에 반영하는 상태 계층 | 업무를 이어가려 적어두는 "수첩" |
| 무상태(Stateless) LLM | 호출이 끝나면 직전 맥락을 보존하지 않는 LLM의 기본 성질 | 매번 기억을 잃는 "단기 기억상실" |
| 단기 메모리(Short-Term) | 현재 세션·대화 안에서만 유지되는 휘발성 맥락. 상세는 018 참조 | 지금 통화 중 손에 든 "메모지" |
| 장기 메모리(Long-Term) | 세션을 넘어 지속 저장되는 누적 지식. 상세는 017 참조 | 캐비닛에 보관한 "서류철" |
| 에피소딕(Episodic) 메모리 | "언제 무슨 일이 있었나"를 기록하는 사건 기억 | 개인의 "일기·경험담" |
| 시맨틱(Semantic) 메모리 | 사실·개념·규칙을 정리한 지식 기억 | 머릿속 "백과사전" |
| 절차적(Procedural) 메모리 | 특정 작업을 수행하는 방법·절차 기억 | 몸으로 익힌 "자전거 타는 법" |
| 인출(Recall)/검색 | 저장된 기억 중 현재 맥락에 맞는 것을 찾아 컨텍스트에 주입 | 캐비닛에서 필요한 서류만 꺼냄 |
| 메모리 매니저(Manager) | 저장 여부·중요도·요약·삭제를 판단하는 제어 로직 | 서류를 분류·폐기하는 "총무" |
| 벡터DB(Vector DB) | 텍스트를 임베딩(숫자벡터)해 의미 유사도로 검색하는 저장소. 상세는 017 참조 | 뜻이 비슷한 서류를 찾아주는 색인 |
| TTL(Time To Live) | 저장된 기억의 보존 기간. 만료 시 자동 삭제 | 서류의 "폐기 예정일" |
| PII(개인식별정보) | 이름·연락처 등 개인을 식별하는 민감정보 | 함부로 못 두는 "주민번호" |

## 깊이 이해
- **배경·문제의식**: 초기 챗봇은 한 번의 질문-답변으로 끝나 기억이 필요 없었다. 그러나 에이전트는 "장애 원인 조사 → 조치 → 재발 방지 기록"처럼 여러 턴에 걸쳐 목표를 완수하므로, 이전 단계의 결과와 사용자 선호를 이어가야 한다. LLM 컨텍스트 윈도우에 전부 넣으면 토큰 비용이 폭증하고 오래된 이력은 잘려 나가므로, 외부 저장소로 분리하는 메모리 계층이 필요해졌다.
- **작동 원리(어떻게+왜)**: 에이전트는 상호작용마다 저장 후보(대화·도구 결과·선호)를 수집하고, 메모리 매니저가 중요도·민감도를 평가해 단기/장기 저장소를 고른다. 다음 판단 시에는 전체를 넣지 않고 현재 맥락과 관련된 것만 인출(recall)해 컨텍스트에 주입한다. 저장(무엇을 남길까)과 인출(무엇을 꺼낼까)을 분리하는 이유는, 무한정 쌓기만 하면 비용과 노이즈가 커지고 관련 없는 오래된 기억이 판단을 오염시키기 때문이다.
- **비유**: 상담사가 고객 이력·이전 조치·금지 요청을 CRM에서 확인한 뒤 상담하는 방식과 같다. 통화 중 손에 든 메모지(단기)는 통화가 끝나면 버리고, 중요한 결정은 고객 파일(장기)에 옮겨 보관한다.
- **구체 예시(실제 사례)**: LangGraph는 세션 내 상태를 `checkpointer`로 단기 보존하고, `store`로 사용자별 장기 기억을 유지한다. MemGPT/Letta는 컨텍스트를 넘는 정보를 외부 저장소로 페이징(paging)해 무제한 대화를 흉내 낸다. 예: 코딩 에이전트가 사용자가 선호하는 코드 스타일(장기·시맨틱)과 방금 수정한 파일 경로(단기·에피소딕)를 분리 관리한다.
- **흔한 오해·주의점**: "메모리 = 단순 캐시"가 아니다. 캐시는 성능용 임시 데이터지만, 메모리는 개인정보·영업비밀이 장기 축적되는 저장소가 될 수 있어 TTL·삭제권·암호화가 필수다. 또한 검증 없이 오래된 기억을 재사용하면 이미 바뀐 사실로 잘못 판단하는 위험이 있다.

## 연결 개념
- 단기 메모리(018) — 컨텍스트 윈도우·대화 버퍼·토큰 한계 중심의 세션 기억
- 장기 메모리(017) — 벡터DB·RAG·지식그래프 기반의 지속 저장·인출
- 상태 관리(019) — 메모리를 포함한 에이전트 전체 실행 상태의 저장·복원

## 핵심 인사이트 (3줄 요약)

> 1. **본질**: 에이전트 메모리는 무상태 LLM에 지속성을 부여해, 대화·이력·선호·도구 결과를 저장·인출하는 상태 계층임.
> 2. **가치**: 단기·장기와 에피소딕·시맨틱·절차 유형으로 기억을 분리해 다단계 업무의 맥락 손실과 토큰 비용을 동시에 통제함.
> 3. **판단 포인트**: 저장뿐 아니라 인출 정확도, TTL·삭제권, 오래된 기억 재검증을 함께 설계해야 함.

## Ⅰ. 개요 및 필요성

- 개요: 대화·상태·이력·선호를 저장·인출해 에이전트 판단에 반영하는 상태 계층임
- 배경: LLM은 호출 후 맥락을 잃는 무상태 함수라 다단계 업무의 연속성 확보가 불가함
- 필요성: 컨텍스트 윈도우 전체 주입은 토큰 비용·누락을 유발하므로 외부 메모리 분리가 필요함
- 위치: 단기(018)·장기(017) 메모리를 포괄하는 상위 기억 체계에 해당함

---

## Ⅱ. 구조 및 구성요소

- 선형 구조도

```text
상호작용 -> Memory Manager(중요도·민감도 평가)
  -> 단기 메모리(세션 버퍼) / 장기 메모리(벡터DB·지식그래프)
  -> 인출(Recall) -> LLM 컨텍스트 주입 -> 응답
  -> Privacy Filter(TTL·삭제·암호화)
```

| 구성요소 | 역할 | 특이사항 |
|:---|:---|:---|
| Memory Manager | 저장 여부·중요도·요약·삭제 판단 | 단기/장기 라우팅 결정 |
| 단기 메모리 | 세션 내 대화·상태 유지 | 토큰 한도 관리(018) |
| 장기 메모리 | 세션 초과 누적 지식 저장 | 벡터DB·지식그래프(017) |
| 인출(Recall) 엔진 | 현재 맥락 관련 기억만 검색·주입 | recall 정확도·최신성 |
| Privacy Filter | PII 통제·보존기간 관리 | TTL·KMS 암호화·삭제 API |

> 요약: 메모리는 매니저의 라우팅 아래 단기·장기 저장소, 인출 엔진, 개인정보 필터로 구성됨.

---

## Ⅲ. 동작원리 및 흐름도

- 선형 흐름도

```text
상호작용 수집 -> Manager 중요도·민감도 평가 -> 저장소 선택(단기/장기)
  -> 다음 턴 관련 기억 인출 -> 컨텍스트 주입 -> 사용 후 TTL·삭제 관리
```

1. 저장 후보 수집: Manager가 대화·도구 결과·사용자 ID·선호를 수집함
2. 중요도·민감도 평가: PII·비밀 등급을 판정해 단기/장기 저장소와 TTL을 정함
3. 인출·주입: 현재 맥락과 유사한 기억만 검색해 recall·출처·생성시각과 함께 주입함
4. 보존·폐기: 사용 이력을 기록하고 TTL 만료·삭제 요청 시 Privacy Filter가 폐기함

> 요약: 저장 전 민감도 평가와 인출 시 관련성 필터, 사용 후 보존기간 관리가 하나의 순환으로 동작함.

---

## Ⅳ. 특징

- 지속성: 무상태 LLM에 세션·업무를 넘는 기억을 부여해 다단계 업무를 이어감
- 유형 분리: 에피소딕(사건)·시맨틱(사실)·절차(방법)로 나눠 인출 목적에 맞게 관리함
- 계층 구조: 단기(휘발·저지연)와 장기(지속·검색)를 분리해 비용과 정확도를 균형함
- 선택적 인출: 전체 주입이 아니라 관련 기억만 recall해 토큰 비용과 노이즈를 줄임
- 통제 필수성: 개인정보·비밀이 축적되므로 TTL·삭제권·암호화가 설계 필수축이 됨

## Ⅴ. 심화 비교 및 적용 판단

- 지속 기간과 목적에 따라 단기 메모리와 장기 메모리를 대비함

| 구분 | 단기 메모리(018) | 장기 메모리(017) |
|:---|:---|:---|
| 지속 범위 | 현재 세션·대화(휘발) | 세션 초과 영구 저장 |
| 저장 위치 | 컨텍스트 윈도우·대화 버퍼 | 벡터DB·지식그래프·RDB |
| 인출 방식 | 순차 참조(최근 N턴) | 임베딩 유사도·그래프 탐색 |
| 주 관심사 | 토큰 한도·요약 압축 | recall 정확도·최신성·개인정보 |
| 적용 상황 | 단일 세션 내 연속 대화 | 사용자 선호·업무 이력 재사용 |

> 요약: 세션 내 맥락은 단기, 세션을 넘는 누적 지식은 장기로 분리하되 매니저가 승격·요약을 중개함.

- 주요 리스크와 대응(불릿)
  - 민감정보 장기 잔류: TTL·삭제 API 미구현이 원인 → TTL 30~90일 + 삭제 SLA 24시간
  - 오래된 기억 재사용 오류: 검증 없는 과거 이력 주입이 원인 → 90일 미사용 기억 재검증·폐기
  - 메모리 오염(인젝션): 악의적 입력이 그대로 저장됨 → 저장 전 입력 검증·출처 신뢰도 태깅

- 운영 건전성 지표(불릿)
  - 인출 recall 85% 이상, p95 지연 200ms 이하(벤치마크 질의셋·APM)
  - 개인정보 삭제 요청 24시간 이내 처리(삭제 API 로그·감사 리포트)
  - 월간 저장 비용 증가율 15% 이내(클라우드 빌링·저장 건수 추이)

## Ⅵ. 실무 적용 및 결론

- 적용 방안
  1. 세션 상태·사용자 선호·업무 이력·감사 로그를 유형별로 분리 저장하고 목적 외 사용을 차단함
  2. 개인정보는 KMS 암호화·TTL 30~90일·삭제 SLA 24시간을 정책 엔진에 강제함
  3. 인출 결과에 출처·생성시각·신뢰도 점수를 함께 주입하고 90일 이상 미사용 이력은 재검증함
- 결론
  - 기술사 판단: 장기 반복 업무는 단기·장기 메모리를 함께 두고, 일회성 고위험 업무는 장기 저장을 최소화함
  - 향후 방향: RAG·LLMOps·개인정보 거버넌스와 결합해 AI 상태관리 표준 계층으로 발전함
