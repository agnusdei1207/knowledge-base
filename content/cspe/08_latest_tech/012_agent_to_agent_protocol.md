# 📖 【암기용】 개념 완전 이해

## 한눈에
- **개요**: **A2A**(Agent-to-Agent Protocol)는 서로 다른 벤더·프레임워크로 만든 **자율 에이전트끼리 능력을 발견하고 작업을 위임·협업하게 하는 개방형 통신 프로토콜**이다(HTTP·JSON-RPC·SSE 기반).
- **왜 필요한가**: MCP(006)가 "앱↔도구" 연결을 표준화했다면, 에이전트가 늘면서 "에이전트↔에이전트"의 협업 배선도 제각각이 됐다. A2A는 이 협업 방식을 한 규격으로 표준화한다.
- **핵심 직관**: MCP가 "직원이 도구를 쓰는 법"이라면, A2A는 "직원끼리 일을 나눠 맡기는 법"이다. 상대 전문가에게 명함(Agent Card)을 보고 업무를 의뢰하는 것과 같다.

## 핵심 용어 정리 (내부에 등장하는 것들)
답안 본문에 등장하는 용어를 처음 보는 사람도 이해하도록 비유와 함께 먼저 정리한다.

| 용어/표기 | 의미 | 비유·예 |
|:---|:---|:---|
| A2A(핵심) | 에이전트 간 발견·위임·협업 표준 프로토콜 | 전문가끼리 "업무 의뢰 규약" |
| 에이전트↔에이전트 | A2A가 잇는 대상(대등한 자율 주체) | MCP의 앱↔도구와 대비되는 축 |
| Agent Card | 에이전트 능력·엔드포인트를 담은 명세 | 능력이 적힌 "명함" |
| 클라이언트/리모트 에이전트 | 작업을 맡기는 쪽 / 수행하는 쪽 | 의뢰인 / 수임 전문가 |
| Task | 위임되는 작업 단위(상태·수명 있음) | 배정된 "업무 티켓" |
| Artifact | 작업 결과물 | 완성해 넘기는 "산출물" |
| Message/Part | 주고받는 메시지와 콘텐츠 조각 | 대화 한 마디/첨부 |
| 능력 발견(Discovery) | Agent Card로 상대 능력을 확인 | 명함 보고 전문 분야 파악 |
| SSE·푸시 알림 | 장기 작업 진행을 스트리밍·통지 | 진행 상황 실시간 보고 |
| Opaque 실행 | 내부 로직·상태를 숨기고 결과만 교환 | 내부 비공개, 결과만 인계 |

## 깊이 이해
- **배경·문제의식**: MCP(006)는 한 에이전트가 도구·데이터를 쓰는 법을 표준화했지만, 서로 다른 조직·벤더의 에이전트가 협업하려면 별도 배선이 필요했다. A2A는 "에이전트가 서로를 발견하고 작업을 위임·조율"하는 계층을 표준화해, 이기종 에이전트 생태계의 상호운용을 만든다.
- **작동 원리(어떻게+왜)**: 각 에이전트는 자신의 능력·엔드포인트·인증을 담은 Agent Card를 공개한다. 클라이언트 에이전트가 이를 발견해 리모트 에이전트에게 Task를 위임하면, 수임 에이전트가 내부 로직은 숨긴 채(Opaque) 작업을 수행하고 Message·Artifact로 결과를 돌려준다. 오래 걸리는 작업은 SSE·푸시 알림으로 진행을 통지한다. HTTP·JSON-RPC 기반이라 기존 웹 인프라·인증을 재사용한다.
- **비유**: 회사 간 아웃소싱. 상대 회사의 소개서(Agent Card)를 보고 업무(Task)를 맡기면, 그 회사는 내부 방식을 공개하지 않고 결과물(Artifact)만 납품한다. 진행이 길면 중간 보고(SSE)를 한다.
- **구체 예시(실제 사례)**: Google이 2025년 주도해 공개한 A2A는 여러 벤더가 참여했다. 채용 시나리오에서 총괄 에이전트가 이력서 스크리닝 에이전트·일정 조율 에이전트에게 각각 Task를 위임하고, 각자의 Artifact를 모아 최종 결정을 조립한다.
- **흔한 오해·주의점**: A2A는 MCP의 대체재가 아니라 보완재다. MCP는 에이전트가 도구·데이터에 접근하는 수직 연결, A2A는 에이전트끼리의 수평 협업으로 층이 다르다. 한 시스템에서 둘을 함께 쓴다. 또한 외부 에이전트에 작업을 맡기므로 상호 인증·권한 위임·결과 신뢰 검증이 필수다.

## 연결 개념
- MCP(006) — 앱↔도구 표준(수직), A2A(에이전트↔에이전트 수평)와 상호 보완
- 멀티 에이전트 협업(013)·에이전트 오케스트레이션(014) — A2A가 통신 기반을 제공하는 상위 구조
- 에이전트 권한 통제(020)·감사 로그(021) — 위임 시 필요한 인증·추적 장치

# 📝 【답안용】 시험 답안 템플릿

## 핵심 인사이트 (3줄 요약)

> 1. **본질**: A2A는 이기종 자율 에이전트가 능력을 발견하고 작업을 위임·협업하는 개방형 통신 프로토콜임.
> 2. **가치**: 에이전트↔에이전트 협업 배선을 표준화해 벤더·프레임워크를 넘는 상호운용을 확보함.
> 3. **판단 포인트**: MCP(앱↔도구)와 층을 구분해 병용하고 위임 시 상호 인증·신뢰 검증을 설계해야 함.

## 출제 의도 및 답안 포인트

| 출제 의도 | 반드시 짚을 핵심 | 감점 회피 포인트 |
|:---|:---|:---|
| 에이전트 협업 표준 구조 이해 | Agent Card, Task·Artifact, 발견·위임 | MCP와 역할 혼동 기술 시 감점 |
| MCP와의 관계 인식 | 수평 협업 vs 수직 도구 연결, 병용 | A2A를 MCP 대체재로 단정 시 감점 |
| 위임 보안 인식 | 상호 인증·권한 위임·결과 검증 | 신뢰·인증 통제 누락 시 감점 |

> 요약: 에이전트 간 협업을 무엇으로 표준화하고 MCP와 어떻게 구분·병용하며 어떻게 신뢰하는지 확인하려는 문제임.

---

## Ⅰ. 개요 및 필요성

- 개요: 이기종 자율 에이전트가 능력을 발견해 작업을 위임·협업하게 하는 개방형 통신 프로토콜임
- 배경: MCP(006)는 앱↔도구 연결을 표준화했으나 에이전트↔에이전트 협업은 제각각임
- 필요성: 벤더·프레임워크가 다른 에이전트가 상호운용하며 복합 작업을 분담해야 확장이 가능함
- 위치: 도구 연결(MCP) 위에서 에이전트 간 수평 협업을 담당하는 통신 계층임

---

## Ⅱ. 구조 및 구성요소

- 선형 구조도

```text
클라이언트 에이전트 -> Agent Card 발견(상대 능력·엔드포인트·인증)
  -> Task 위임(HTTP·JSON-RPC) -> 리모트 에이전트(내부 Opaque 실행)
    -> 진행 통지(SSE·푸시 알림) -> Message·Artifact 반환
  결과 조립 -> 최종 응답
```

| 구성요소 | 역할 | 특이사항 |
|:---|:---|:---|
| Agent Card | 능력·엔드포인트·인증 명세 | 발견의 진입점 |
| 클라이언트/리모트 에이전트 | 위임 주체 / 수행 주체 | 대등한 자율 주체 |
| Task | 위임 작업 단위·상태 관리 | 수명·진행 상태 보유 |
| Message·Part | 교환 메시지·콘텐츠 조각 | 멀티모달 지원 |
| Artifact | 작업 산출물 | 결과 인계 단위 |

> 요약: Agent Card로 상대를 발견해 Task를 위임하고, 리모트 에이전트가 Opaque 실행 후 Artifact로 결과를 인계함.

---

## Ⅲ. 동작원리 및 흐름도

- 선형 흐름도

```text
Agent Card 발견 -> 상호 인증 -> Task 위임 -> 리모트 에이전트 실행 -> (SSE·푸시로 진행 통지) -> Message·Artifact 반환 -> 클라이언트 결과 조립
```

1. 발견: 클라이언트 에이전트가 리모트 에이전트의 Agent Card로 능력·엔드포인트를 확인함
2. 위임: 상호 인증 후 클라이언트가 HTTP·JSON-RPC로 Task를 리모트 에이전트에 전달함
3. 실행: 리모트 에이전트가 내부 로직을 숨긴 채 작업을 수행하고 장기 작업은 SSE·푸시로 진행을 통지함
4. 조립: 반환된 Message·Artifact를 클라이언트가 모아 최종 결과를 구성함

> 요약: 클라이언트가 Agent Card로 상대를 찾아 인증 후 Task를 위임하고, 결과 Artifact를 조립해 완결함.

---

## Ⅳ. 특징

- 능력 발견: Agent Card로 상대 에이전트의 기능·인증을 표준 방식으로 확인함
- 벤더 중립: 서로 다른 프레임워크로 만든 에이전트도 동일 규격으로 협업함
- Opaque 실행: 내부 로직·상태를 공개하지 않고 결과만 교환해 자율성과 보안을 유지함
- 장기 작업 지원: SSE·푸시 알림으로 오래 걸리는 Task의 진행을 실시간 통지함
- 웹 표준 재사용: HTTP·JSON-RPC 기반이라 기존 인증·인프라를 그대로 활용함

---

## Ⅴ. 심화 비교 및 적용 판단

- A2A의 위치는 도구 연결 표준인 MCP(006)와 대비할 때 가장 분명함(대체 아닌 보완)

| 구분 | A2A | MCP |
|:---|:---|:---|
| 연결 대상 | 에이전트 ↔ 에이전트 | LLM 앱 ↔ 도구·데이터 |
| 관계 성격 | 대등한 협업(수평) | 도구 사용(수직) |
| 핵심 단위 | Task·Artifact | 툴·리소스·프롬프트 |
| 발견 방식 | Agent Card | capability negotiation |
| 실행 가시성 | Opaque(내부 은닉) | 툴·리소스 명시 노출 |
| 병용 관계 | 협업 계층 | A2A 에이전트가 내부에서 MCP 사용 |

> 요약: 에이전트 간 협업이면 A2A, 단일 에이전트의 도구 접근이면 MCP이며, 실제 시스템은 둘을 함께 씀.

- 협업 토폴로지 선택(불릿)
  - 총괄-전문가형 — 오케스트레이터가 다수 리모트 에이전트에 Task 분배
  - 파이프라인형 — 에이전트가 순차로 Artifact를 넘겨 정제
  - 피어 협상형 — 대등 에이전트가 상호 위임·조율

- 주요 리스크와 대응(불릿)
  - 위임 남용 — 미검증 에이전트에 과도 위임이 원인 → 상호 인증·허용 목록·범위 제한
  - 결과 신뢰 저하 — 외부 Artifact의 오류·조작이 원인 → 결과 검증·출처 서명
  - 순환·폭주 — 에이전트 간 무한 위임이 원인 → 홉 수 제한·타임아웃·비용 상한

- 운영 지표(불릿)
  - 위임 성공률 — Task 완료율 99% 이상 목표 — Task 상태 집계
  - 인증 준수 — 미인증 위임 0건 목표 — 통신 감사로그
  - 협업 지연 — 위임 왕복 시간 목표치 이내 — SSE 진행 로그 측정

---

## Ⅵ. 실무 적용 및 결론

- 적용 방안
  1. 이기종 오케스트레이션: 총괄 에이전트가 Agent Card로 벤더가 다른 전문가 에이전트를 발견해 Task를 분배하고 Artifact를 조립
  2. 계층 병용: A2A로 에이전트 협업을 잇고 각 에이전트 내부는 MCP로 도구·데이터에 접근하도록 층을 분리
  3. 위임 통제: 상호 인증·범위 토큰으로 위임 권한을 제한하고 홉 수 제한·감사로그로 폭주·오남용을 차단
- 결론
  - 기술사 판단: 이기종 에이전트 협업은 A2A로 표준화하되 도구 접근은 MCP로 병용하고, 위임 시 인증·검증을 필수화함
  - 향후 방향: A2A는 에이전트 레지스트리·신뢰 프레임워크와 결합해 조직 간 에이전트 협업의 개방 상호운용 기반으로 정착됨
