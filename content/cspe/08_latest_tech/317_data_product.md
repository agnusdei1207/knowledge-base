# 📖 【암기용】 개념 완전 이해

> 목적: 데이터 제품을 처음 봐도 완벽히 이해하게 만든다. 시험 답안 양식이 아니라, 이해를 위한 친절한 설명이다.

## 한눈에
- **개요**: 데이터를 단순히 '모아둔 파일'이 아니라, 누군가에게 가치를 주기 위해 잘 가공되고 관리되는 '상품'처럼 취급하는 개념
- **왜 필요한가**: 데이터 레이크에 데이터는 많지만, 정작 쓰려 하면 쓸모없거나 찾기 힘든 경우가 많다. 데이터를 '상품'으로 생각하고 만들면, 쓰는 사람이 만족할 만큼 품질과 사용성이 좋아지기 때문이다.
- **핵심 직관**: "데이터 세계의 '아이폰'이나 '쿠팡 서비스'처럼, 사용자의 만족을 목표로 설계된 완성된 데이터 패키지."

## 깊이 이해
- **배경·문제의식**: 기업들은 데이터를 '자산'이라고 부르지만, 실제로는 관리 안 되는 '부산물'처럼 방치함. 데이터가 어디에 쓰이는지, 누가 책임지는지 모른 채 쌓이기만 함. 이를 비즈니스 가치로 연결하려면 '제품적 사고(Product Thinking)'가 필요해짐.
- **작동 원리**: 데이터 제품은 5가지 특성을 갖춰야 함. ① **발견 가능**: 카탈로그에서 쉽게 검색됨. ② **주소 지정 가능**: 표준 API나 테이블로 접근 가능. ③ **신뢰 가능**: 품질 보증(SLA)이 있음. ④ **자기 설명적**: 설명서가 잘 되어 있음. ⑤ **상호운용 가능**: 다른 데이터와 합치기 쉬움.
- **비유**: 산에서 갓 길어 올린 '샘물'이 원천 데이터라면, 깨끗하게 정수해서 예쁜 병에 담아 성분 표시를 하고 유통기한을 적어 편의점에 진열한 '생수(에비앙 등)'가 데이터 제품임.
- **구체 예시**: 마케팅 팀이 만든 "고객 360도 통합 뷰"가 데이터 제품임. 이 제품은 매일 아침 업데이트되고, 데이터 형식은 고정되어 있으며, 궁금한 건 담당자에게 물어볼 수 있고, 타 부서에서도 API로 가져다 쓸 수 있음.
- **흔한 오해·주의점**: 단순한 '대시보드'나 '보고서'가 아님. 데이터를 원재료로 하여 가치를 만들어내는 '시스템'이나 '재사용 가능한 데이터 세트' 전체를 포괄함.

## 연결 개념
- Data Mesh - 데이터 제품은 데이터 메시를 구성하는 가장 핵심적인 단위임
- Product Thinking - 사용자의 니즈를 분석하여 가치를 설계하는 사고방식
- Data Contract - 데이터 제품의 '품질 보증서' 역할을 하는 협약

# 📝 【답안용】 시험 답안 템플릿

> 목적: 시험장에서 25분에 그대로 쓰는 답안 양식. 작성방식(추상표현 금지·수치·도식·문제유형 전환)을 엄격히 지킨다.
> 핵심: 데이터 제품의 8가지 특성(DATSIS: Discoverable, Addressable, Trustworthy, Self-describing, Interoperable, Secure)과 데이터 라이프사이클 관리를 강조한다.

## 핵심 인사이트 (3줄 요약)

> 1. **본질**: 데이터 제품은 데이터를 단순히 관리 대상인 자산으로 보지 않고, 비즈니스 가치 창출을 위해 사용성, 품질, 신뢰성이 보장된 '소비 가능한 상품'으로 정의한 단위이다.
> 2. **가치**: 데이터 소비자의 경험(UX)을 최우선으로 하여 데이터 탐색 비용을 줄이고, 도메인 팀의 데이터 책임(Ownership)을 실현한다.
> 3. **판단 포인트**: 데이터 제품은 코드(ETL), 메타데이터, 정책, 그리고 실제 데이터가 결합된 자립형(Autonomous) 아키텍처 단위를 의미한다.

## 출제 의도 및 답안 포인트

| 출제 의도 | 반드시 짚을 핵심 | 감점 회피 포인트 |
|:---|:---|:---|
| 데이터 아키텍처 변화 철학 파악 | 데이터 자산(Asset) vs 데이터 제품(Product) 차이 | 단순히 "잘 가공된 데이터"로만 정의 지양 |
| 데이터 제품의 핵심 특성 이해 | 발견성, 신뢰성, 상호운용성, 자기 설명성 등 (DATSIS) | 특성 중 일부 누락 및 기술적 근거 미흡 |
| 데이터 메시(Data Mesh)와의 연계성 | 도메인 소유권, 셀프 서비스 플랫폼과 제품의 관계 | 조직 문화적 요소(Product Thinking) 간과 |

> 요약: 데이터 제품은 데이터의 '기술적 저장'보다 '비즈니스적 소비'에 집중하여 데이터 사일로를 해결하는 개념이다.

## Ⅰ. 개요 및 필요성

- 정의: 특정 비즈니스 목적을 위해 독립적으로 소비 가능하도록 품질, 설명서, 보안 정책이 완비된 데이터의 패키지 형태
- 배경: 데이터 레이크의 거버넌스 부재(Data Swamp), 데이터 준비 과정의 비효율성(전체 분석 시간의 80%), 부서 간 데이터 책임 전가
- 필요성: 데이터 활용의 민첩성(Agility) 확보, 데이터 품질의 상향 평준화, 데이터 기반 의사결정의 신뢰도 향상

---

## Ⅱ. 구조 및 구성요소 (Data Product Container)

```text
[ Data Product Container ]
  / 1. Code: ETL, Data Pipeline, API Logic
  / 2. Metadata: Data Contract, Lineage, Documentation
  / 3. Policy: Access Control, Retention, Masking
  / 4. Data: Tables, Files, Stream (Actual Content)
-------------------------------------------------------
[ Interface: SQL, REST API, Event Stream ]
```

| 구성요소 | 역할 | 특이사항 |
|:---|:---|:---|
| Data & Metadata | 실제 데이터 값과 이를 설명하는 정보(Schema, Owner) | 제품의 내용물과 성분표 |
| Code | 데이터를 수집, 가공, 배포하는 실행 로직 | 제품 생산 공정 |
| Policy & Security | 데이터 보호 및 접근 권한 설정 | 제품의 안전 장치 및 유통 규칙 |
| Infrastructure | 제품이 구동되는 컴퓨팅 및 저장 자원 | 제품의 보관 및 서비스 환경 |

> 요약: 데이터뿐만 아니라 그 데이터를 만드는 코드와 정책을 하나의 컨테이너(단위)로 묶어 자립성을 부여한다.

## Ⅲ. 동작원리 및 흐름도 (Product Lifecycle)

```text
Problem ID -> [ 1. Design ] -> [ 2. Develop ] -> [ 3. Publish ] -> [ 4. Monitor ]
      |              |                |                |                 |
(사용자 니즈)  (계약/스키마 설계)   (Pipeline 구축)   (Catalog 등록)     (품질/피드백)
```

| 단계 | 처리 내용 | 검증 기준 |
|:---:|:---|:---|
| 1 | 사용자 정의 | 누가, 왜 이 데이터를 쓰는지 페르소나와 유스케이스 정의 | 비즈니스 가치 명확화 |
| 2 | 설계 및 계약 | 데이터 형식, 업데이트 주기, 품질 지표(SLA) 합의 | Data Contract 수립 |
| 3 | 제품 구현 | 로직 코딩 및 데이터 파이프라인 자동화 구축 | CI/CD 기반 배포 |
| 4 | 발견 및 소비 | 데이터 카탈로그에 등록하여 타 부서에서 검색 및 사용 가능하게 함 | 발견 가능성(Discoverable) |
| 5 | 운영 및 고도화 | 사용자 피드백과 품질 지표를 바탕으로 제품 버전 업그레이드 | 지속적 개선 (Iterative) |

> 요약: 일반 소프트웨어 제품처럼 기획, 개발, 출시, 운영의 생애 주기를 통해 품질을 관리한다.

## Ⅳ. 특징 (DATSIS 원칙)

| 구분 | 주요 특성 | 상세 내용 |
|:---|:---|:---|
| Discoverable | 발견 가능성 | 중앙 카탈로그에서 쉽게 검색되고 의미를 파악할 수 있음 |
| Addressable | 주소 지정 가능성 | 고유한 식별자(URL/Path)를 통해 표준 방식으로 접근 가능 |
| Trustworthy | 신뢰 가능성 | 정의된 SLA와 품질 지표를 만족하며 무결성이 보장됨 |
| Self-describing | 자기 설명성 | 외부 도움 없이 메타데이터와 샘플만으로 이해 가능함 |
| Interoperable | 상호운용성 | 전사 공통 표준(ID 등)을 준수하여 타 제품과 결합 용이 |
| Secure | 보안성 | RBAC, PII 마스킹 등 보안 정책이 내장되어 안전함 |

> 요약: 사용자가 데이터를 쉽게 찾고, 이해하고, 믿고 쓸 수 있게 만드는 것이 핵심 특징이다.

## Ⅴ. 심화 비교 및 적용 판단

| 비교 축 | 데이터 자산 (Asset) | 데이터 제품 (Product) | 선택 기준 |
|:---|:---|:---|:---|
| 관점 | 내부 관리 및 저장 중심 | 외부 소비자 및 가치 중심 | 데이터의 목적 (보관 vs 공유) |
| 책임 주체 | 중앙 데이터 팀/IT 부서 | 도메인 팀 (비즈니스 부서) | 데이터 소유권 및 도메인 지식 |
| 품질 보증 | 수동적, 사후 처리 | 능동적, 계약 기반 (SLA) | 분석 신뢰도 요건 |
| 성공 지표 | 저장 용량, 가동률 | 사용자 수, 재사용률, 만족도 | 거버넌스 목표 지표 |

> 요약: 데이터 자산이 '보관'에 집중한다면, 데이터 제품은 '유통과 가치'에 집중한다.

| 리스크 | 원인 | 대응 방안 | 확인 지표 |
|:---|:---|:---|:---|
| 제품의 난립 | 중복된 목적의 데이터 제품 다수 생성 | 데이터 제품 심의 및 카탈로그 기반 중복 체크 | 제품 당 재사용률 |
| 품질 저하 | 도메인 팀의 운영 역량 부족 | 플랫폼 팀에서 표준 템플릿 및 자동화 도구 제공 | SLA 준수율 |
| 사일로 현상 | 제품 간 데이터 표준 불일치 | 전사 공통 식별자(ID) 및 연합 거버넌스 강화 | 제품 간 조인(Join) 성공률 |

> 요약: 제품의 '중복성'과 '표준성'을 통제하는 중앙 플랫폼의 역할이 운영의 핵심이다.

| 점검 항목 | 목표 기준 | 측정 방법 |
|:---|:---|:---|
| 데이터 준비 시간 | 분석가의 데이터 전처리 시간 50% 단축 | 분석 프로젝트 리드타임 조사 |
| 데이터 재사용률 | 생성된 제품의 3개 이상 도메인 동시 활용 | 카탈로그 접근 로그 분석 |
| 사용자 만족도 (NPS) | 소비자 대상 만족도 80점 이상 유지 | 정기 피드백 조사 및 평점 |

> 요약: 도입 효과는 데이터의 '활용도 증가'와 '분석 생산성 향상'으로 정량화하여 평가한다.

## Ⅵ. 실무 적용 및 결론

**적용 방안 3개:**
1. **도메인 전담 팀 구성**: 영업팀 내에 데이터 제품 매니저(DPM)를 두어 영업 데이터를 '제품'으로 가공하고 타 부서에 서비스
2. **데이터 쇼핑몰 구축**: 전사 데이터 제품을 검색, 리뷰, 샘플 확인 후 클릭 한 번으로 권한을 신청하는 셀프 서비스 포털 운영
3. **SLA 기반 품질 모니터링**: 데이터 제품별로 '최신성 99% 준수', '결측치 1% 미만' 등의 지표를 실시간 공개하여 소비자 신뢰 확보

**결론 (2줄):**
- 기술사 판단: 데이터 제품은 기술의 문제가 아닌 '문화와 조직'의 변화이며, 데이터 기반 혁신을 위한 가장 성숙한 아키텍처 단위이다.
- 향후 방향: 생성형 AI가 데이터 제품의 메타데이터를 학습하여 필요한 제품을 자동 추천하고 조합해주는 '에이전틱 데이터 마켓'으로 발전할 것이다.

| 요구사항 명시형 | "데이터 가용성 및 재사용성 증대 방안" | 데이터 제품 라이프사이클 관리 프로세스 | 데이터 메시 아키텍처 내에서의 역할 및 Ⅵ 사례 |
