# 📖 【암기용】 개념 완전 이해

> 목적: Data Product를 사용자가 재사용할 수 있도록 소유권·품질·접근·문서를 갖춘 데이터 산출물로 이해하게 만든다.

## 한눈에
- **개요**: 데이터셋을 제품처럼 소유자, 사용자, SLA, 품질, 사용 방법까지 묶어 제공하는 단위
- **왜 필요한가**: 데이터 레이크에 파일과 테이블만 쌓이면 사용자는 의미, 신뢰 범위, 접근 방법을 몰라 같은 데이터를 반복 가공한다.
- **핵심 직관**: 창고에 부품을 던져두는 것이 아니라, 규격서와 보증 조건이 붙은 부품으로 판매하는 것과 같다.

## 깊이 이해
- **배경·문제의식**: Data Mesh는 중앙 데이터팀이 모든 데이터를 해석하는 한계를 줄이기 위해 도메인 팀이 자신들의 데이터를 제품으로 책임지게 한다.
- **작동 원리**: 도메인 팀이 데이터 계약, 품질 지표, lineage, API/SQL 접근, 카탈로그 설명, SLA, 비용 태그를 붙여 소비 가능한 단위로 배포한다.
- **비유**: 원재료만 제공하면 요리사가 매번 손질해야 하지만, 세척·포장·유통기한이 붙은 식재료는 여러 식당에서 바로 쓸 수 있다.
- **구체 예시**: 고객 360 데이터 제품은 고객 ID, 동의 상태, 최근 거래, 세그먼트, 갱신 주기, 접근 권한, 품질 점수를 함께 제공한다.
- **흔한 오해·주의점**: Data Product는 테이블 이름을 바꾸는 작업이 아니다. 사용자가 업무 결정을 내릴 수 있도록 품질·소유권·지원 절차가 있어야 한다.

## 연결 개념
- Data Mesh — 도메인 소유 Data Product를 전사적으로 연결하는 운영 모델
- Data Contract — Data Product의 인터페이스와 품질 기준을 명시
- Data Catalog — Data Product를 검색하고 권한을 요청하는 진입점

# 📝 【답안용】 시험 답안 템플릿

> 목적: 시험장에서 25분에 그대로 쓰는 답안 양식.
> 핵심: Data Product는 데이터셋에 소유권·계약·품질·접근·SLA를 부여해 재사용 가능한 제품으로 운영하는 단위임.

## 핵심 인사이트 (3줄 요약)

> 1. **본질**: Data Product는 특정 비즈니스 문제 해결을 위해 데이터, 메타데이터, 품질, 접근 인터페이스, 운영 책임을 결합한 제품 단위임.
> 2. **가치**: 데이터 소비자는 의미와 품질을 재검증하지 않고 정해진 SLA와 접근 경로로 데이터를 사용할 수 있음.
> 3. **판단 포인트**: 도메인 소유자, 데이터 계약, 품질 지표, 접근 통제, 비용/사용량 측정이 함께 있어야 함.

## 출제 의도 및 답안 포인트

| 출제 의도 | 반드시 짚을 핵심 | 감점 회피 포인트 |
|:---|:---|:---|
| Data Mesh 구성 원리 확인 | 도메인 소유권, 제품 책임, 셀프서비스 | 단순 데이터셋으로 설명 |
| 데이터 재사용 구조 판단 확인 | 카탈로그, 계약, 품질, SLA | 저장소 기술만 나열 |
| 거버넌스와 사용성 균형 확인 | RBAC/ABAC, lineage, usage metric | 권한 통제 또는 사용 경험 누락 |

> 요약: 이 문제는 데이터를 저장물이 아니라 책임 있는 제품으로 운영하는 조직·기술 결합을 설명해야 한다.

---

## Ⅰ. 개요 및 필요성

- 개요: 재사용 가능한 데이터 제품
- 배경: 데이터 레이크 중심 운영은 의미 해석과 품질 책임이 소비자에게 전가되는 문제가 있음.
- 필요성: 도메인 팀이 소유자와 SLA를 명시해 분석·AI·업무 프로세스가 같은 데이터를 반복 가공하지 않게 해야 함.

---

## Ⅱ. 구조 및 구성요소

```text
Domain Source -> Data Product
  +-> Dataset / API / Feature
  +-> Contract / Quality / SLA / Owner
  +-> Catalog / Access Control / Usage Metrics
```

| 구성요소 | 역할 | 특이사항 |
|:---|:---|:---|
| 데이터 자산 | 테이블·이벤트·API·feature 제공 | batch, streaming, serving |
| 제품 메타데이터 | 목적·소유자·용어·lineage 설명 | catalog 등록 |
| 품질·계약 | 스키마·freshness·정확성 기준 | Data Contract 연계 |
| 접근·운영 | 권한·SLA·지원·비용 측정 | RBAC/ABAC, FinOps tag |

> 요약: Data Product는 데이터 자체보다 사용 가능한 조건과 운영 책임을 함께 제공할 때 제품 단위가 된다.

---

## Ⅲ. 동작원리 및 흐름도

```text
도메인 요구 식별 -> 데이터 제품 설계 -> 계약·품질 정의
-> 카탈로그 등록 -> 접근 승인 -> 사용량·품질 모니터링
```

| 단계 | 처리 내용 | 검증 기준 |
|:---:|:---|:---|
| 1 | 대상 사용자와 의사결정 문제를 정의함 | persona, use case |
| 2 | 데이터셋·API·feature와 계약을 설계함 | schema, SLA, owner |
| 3 | 품질 테스트와 lineage를 연결함 | freshness, completeness |
| 4 | 카탈로그 공개 후 사용량과 이슈를 관리함 | active consumers, ticket |

> 요약: Data Product는 요구 식별부터 사용량 측정까지 제품 수명주기로 운영된다.

## Ⅳ. 특징

| 구분 | 데이터셋 | Data Product | 판단 기준 |
|:---|:---|:---|:---|
| 초점 | 저장된 데이터 | 소비 가능한 가치 단위 | 사용자·문제 명확성 |
| 책임 | 저장소 관리자 | 도메인 제품 소유자 | owner 지정 여부 |
| 품질 | 임의 점검 | 계약·SLA 기반 검증 | 품질 지표 공개 |
| 소비 | 테이블 직접 탐색 | 카탈로그·API·권한 요청 | 셀프서비스 수준 |

> 요약: Data Product는 데이터셋에 책임, 사용성, 품질 기준을 붙여 전사 재사용 단위로 만든다.

## Ⅴ. 심화 비교 및 적용 판단

| 비교 축 | 기존/대안 | 본 키워드 | 선택 기준 |
|:---|:---|:---|:---|
| 조직 | 중앙 데이터팀 | 도메인 소유 팀 | 도메인 지식 필요도 |
| 제공 방식 | 원천 테이블 공유 | 목적별 제품 제공 | 소비자 수와 반복 가공 |
| 거버넌스 | 사후 승인 | 제품별 정책 내장 | 민감정보·규제 범위 |

> 요약: 도메인 해석과 반복 소비가 큰 데이터는 Data Product로 전환하고, 단발 분석 데이터는 임시 자산으로 관리한다.

| 리스크 | 원인 | 대응 방안 | 확인 지표 |
|:---|:---|:---|:---|
| 제품 남발 | 소유자 없는 테이블을 제품으로 등록 | 제품 승인 기준과 lifecycle 적용 | inactive product 비율 |
| 품질 불신 | SLA·계약 미정의 | 품질 점수와 위반 이력 공개 | freshness SLA 달성률 |
| 권한 지연 | 수동 승인 절차 | 정책 기반 접근 요청 자동화 | access lead time |

> 요약: Data Product 운영 리스크는 제품 기준, 품질 공개, 접근 자동화로 통제한다.

| 점검 항목 | 목표 기준 | 측정 방법 |
|:---|:---|:---|
| 재사용성 | 활성 소비자·쿼리 수 증가 | catalog usage |
| 품질 | SLA 위반 건수 추적 | quality dashboard |
| 운영 책임 | owner 응답 시간 관리 | ticket SLA |

> 요약: Data Product 성과는 등록 수보다 활성 사용, 품질 SLA, 소유자 대응 시간으로 판단한다.

## Ⅵ. 실무 적용 및 결론

**적용 방안 3개:**
1. 매출, 고객, 상품, 설비 같은 핵심 도메인부터 owner, consumer, SLA, 계약, lineage를 갖춘 Data Product 후보를 선정함.
2. Data Catalog에 제품 목적, 접근 방식, 품질 점수, 민감정보 등급, 비용 태그를 등록해 셀프서비스 요청 경로를 제공함.
3. 제품별 active consumer, SLA 위반, 이슈 처리 시간, 비용을 측정해 폐기·개선·확장 결정을 수행함.

**결론 (2줄):**
- 기술사 판단: 반복 소비와 도메인 해석이 필요한 데이터는 Data Product로 운영하고, 일회성 분석 산출물은 임시 데이터셋으로 분리함.
- 향후 방향: Data Product는 AI agent가 신뢰 가능한 데이터를 탐색·요청·사용하는 메타데이터 단위로 확장됨.
