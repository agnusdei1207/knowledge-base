# 📖 【암기용】 개념 완전 이해

> 목적: 데이터 리니지를 처음 봐도 완벽히 이해하게 만든다. 시험 답안 양식이 아니라, 이해를 위한 친절한 설명이다.

## 한눈에
- **개요**: 데이터가 어디서 태어나서(Source), 어떤 경로를 거쳐(Transformation), 어디에 쓰이는지(Target)를 보여주는 '데이터의 족보' 또는 '데이터 지도'
- **왜 필요한가**: 대시보드의 숫자가 틀렸을 때 어디가 잘못되었는지(원인 파악), 혹은 소스 DB를 수정할 때 어떤 시스템이 고장 날지(영향 분석)를 알기 위해서다.
- **핵심 직관**: "데이터의 과거, 현재, 미래를 연결하는 내비게이션."

## 깊이 이해
- **배경·문제의식**: 현대 기업의 데이터는 수많은 ETL, 스크립트, 뷰(View)를 거치며 복잡하게 얽혀 있음. 데이터에 문제가 생겨도 역추적이 불가능하고(Traceability 부재), 불필요한 중복 가공이 빈번하여 비용이 낭비됨.
- **작동 원리**: 데이터 처리 과정의 '로그'나 '소스 코드(SQL 등)'를 분석하여 데이터 간의 관계를 추출함. 이를 시각적인 그래프(Node-Edge) 구조로 나타내어 테이블 단위, 혹은 더 정밀하게 컬럼 단위까지의 흐름을 보여줌.
- **비유**: 강물의 상류에서 하류까지의 흐름과 같음. 하류(보고서)가 오염되었다면 상류(소스 DB)의 어디서 오염물질이 들어왔는지 확인하고, 상류에 댐(시스템 수정)을 지으면 하류의 어느 마을이 가뭄(장애)을 겪을지 미리 계산하는 것.
- **구체 예시**: 개발자가 "고객 주소" 컬럼 길이를 줄이려고 할 때, 리니지를 조회하면 이 컬럼이 마케팅 발송 시스템, 배송 앱, 재무 보고서까지 15개 시스템에 연결되어 있음을 즉시 확인하고 장애를 예방함.
- **흔한 오해·주의점**: 단순히 그림을 그려놓은 정적 도표가 아님. 실제 시스템의 변경 사항을 실시간으로 반영하여 자동으로 그려지는 '살아있는 지도'여야 함.

## 연결 개념
- Metadata Management - 데이터 리니지의 기반이 되는 정보 관리
- Impact Analysis - 리니지를 활용한 변경 영향 분석
- OpenLineage - 리니지 정보를 표준화하여 주고받기 위한 오픈 표준

# 📝 【답안용】 시험 답안 템플릿

> 목적: 시험장에서 25분에 그대로 쓰는 답안 양식. 작성방식(추상표현 금지·수치·도식·문제유형 전환)을 엄격히 지킨다.
> 핵심: 데이터 가시성(Traceability) 확보를 위한 기술적 메커니즘(SQL 파싱, API 수집)과 영향 분석/장애 추적/컴플라이언스 대응 관점의 가치를 제시한다.

## 핵심 인사이트 (3줄 요약)

> 1. **본질**: 데이터 리니지는 데이터의 생애 주기(Source-to-Target) 동안 발생하는 이동 및 변환 과정을 시각화하고 추적하는 데이터 자산의 흐름 지도이다.
> 2. **가치**: 데이터 오류의 근본 원인 분석(Root Cause Analysis) 시간을 단축하고, 시스템 변경 시 영향도를 사전에 파악하여 운영 리스크를 최소화한다.
> 3. **판단 포인트**: 테이블 수준을 넘어 컬럼 수준(Column-level)의 세밀한 추적과 자동화된 코드 분석을 통한 동적 리니지 확보가 기술적 완성도의 척도이다.

## 출제 의도 및 답안 포인트

| 출제 의도 | 반드시 짚을 핵심 | 감점 회피 포인트 |
|:---|:---|:---|
| 데이터 추적성(Traceability) 이해 확인 | 데이터 소스, 변환 로직, 최종 소비처 연결 구조 | 단순히 "데이터 흐름도"로만 정의 지양 |
| 데이터 거버넌스 및 운영 효율성 | 영향 분석(Impact Analysis), 원인 분석(RCA) | 비즈니스 가치(컴플라이언스 등) 설명 누락 |
| 기술적 구현 방식 파악 | SQL 파싱, 로그 분석, 메타데이터 하베스팅 | 수동 작성 방식에 한정된 설명 경계 |

> 요약: 데이터 리니지는 복잡한 데이터 파이프라인의 투명성을 확보하여 데이터 신뢰의 근거를 제공하는 핵심 기술이다.

## Ⅰ. 개요 및 필요성

- 정의: 데이터의 생성, 변환, 이동 및 최종 소비에 이르는 전 과정을 시각화하여 데이터의 출처와 흐름을 추적하는 메타데이터 관리 체계
- 배경: 데이터 파이프라인 복잡도 증가로 인한 블랙박스화, 데이터 정합성 오류 시 추적 지연, 규제 대응(BCBS 239 등) 요구 강화
- 필요성: 시스템 변경 시 영향도 사후 방지, 데이터 품질 이슈의 근본 원인 규명, 중복 데이터 식별을 통한 인프라 비용 최적화

## Ⅱ. 구조 및 구성요소 (데이터 흐름의 3요소)

```text
[ Source System ] ---- ( Transformation ) ----> [ Target System ]
       |                      |                        |
  / 1. Origin (기원)    / 2. Journey (여정)      / 3. Destination (목적지)
  - DB, File, IoT       - ETL, SQL, API, Code    - BI, ML Model, App

[ Metadata Repository: Metadata 수집/분석 -> 시각화(Graph) -> 검색/조회 ]
```

| 구성요소 | 역할 | 특이사항 |
|:---|:---|:---|
| Nodes | 데이터 객체 (Table, Column, Dashboard 등) | 리니지의 개별 단위 |
| Edges | 데이터 간의 흐름 및 의존 관계 (Line) | 방향성(Directional) 존재 |
| Transformation Log | 데이터가 어떻게 변했는지에 대한 로직(Logic) | SQL 쿼리, ETL 스크립트 등 |
| Granularity | 리니지의 상세 수준 | 시스템/테이블/컬럼 단위 |

> 요약: 데이터 객체(Node)와 관계(Edge)를 통해 흐름을 정의하고, 변환 로직을 포함하여 의미를 부여한다.

## Ⅲ. 동작원리 및 흐름도 (리니지 자동 생성 과정)

```text
Log/Code -> [ 1. Metadata Ingestion ] -> [ 2. SQL Parsing ] -> [ 3. Mapping ]
                  |                             |                    |
            (소스 코드 수집)               (로직 분석/추출)      (S-to-T 관계 설정)
                  |                             |                    |
        [ 5. Impact Analysis ] <- [ 4. Visualization (Graph) ] <-----+
                  |                             |
           (영향 범위 도출)                (사용자 UI 제공)
```

| 단계 | 처리 내용 | 검증 기준 |
|:---:|:---|:---|
| 1 | 메타데이터 수집 | ETL 도구, DB 로그, 소스 코드 레포지토리에서 정보 획득 | 데이터 최신성(Sync) |
| 2 | 구문 분석 (Parsing) | SQL 쿼리나 스크립트를 분석하여 입/출력 관계 추출 | 파싱 정확도 |
| 3 | 관계 매핑 | 추출된 정보를 바탕으로 데이터 간의 상하류 관계 연결 | 전 구간 연결성 (Connectivity) |
| 4 | 지식화 및 시각화 | 그래프 데이터베이스 등을 활용하여 사용자가 보기 쉽게 표현 | 직관적 UI/UX |

> 요약: 시스템 이력을 자동으로 읽어 파싱하고 매핑함으로써 사람이 직접 그리지 않아도 실시간 지도를 완성한다.

## Ⅳ. 특징

| 구분 | 주요 특징 | 상세 내용 |
|:---|:---|:---|
| 가시성 (Visibility) | End-to-End 추적 | 소스에서 보고서까지 전체 구간에 대한 투명성 확보 |
| 상세도 (Granularity) | 컬럼 레벨 리니지 | 특정 컬럼의 값이 어떤 계산을 거쳐 생성되었는지 확인 |
| 분석 도구 | Forward/Backward Analysis | 상류 변경 시 하류 영향 분석 + 하류 오류 시 상류 원인 분석 |
| 자동화 | Automated Scanning | 수동 입력이 아닌 소스 코드 분석을 통한 자동 업데이트 |

> 요약: 실시간성, 자동화, 그리고 컬럼 단위의 정밀도가 현대적 리니지의 핵심 특징이다.

## Ⅴ. 심화 비교 및 적용 판단

| 구분 | 정적 리니지 (수동 관리) | 동적 리니지 (자동 관리) | 선택 기준 |
|:---|:---|:---|:---|
| 생성 방식 | 문서화, 엑셀 관리 | 시스템 로그/코드 자동 분석 | 시스템 복잡도 |
| 정확성 | 실시간 반영 불가 (Human Error) | 소스 코드 기반의 높은 정확도 | 데이터 정합성 중요도 |
| 관리 비용 | 초기 낮음, 유지보수 매우 높음 | 초기 높음(솔루션), 유지보수 낮음 | 장기적 운영 효율 |
| 주요 활용 | 단순 가이드용 | 장애 대응, 자동 영향 분석 | 실무 활용 수준 |

> 요약: 데이터 환경이 복잡할수록 자동화된 '동적 리니지' 도입이 필수적이다.

| 리스크 | 원인 | 대응 방안 | 확인 지표 |
|:---|:---|:---|:---|
| 끊김 현상 (Gaps) | 복잡한 코딩이나 수동 파일 이동 | OpenLineage 등 표준 API 도입, 수동 매핑 보완 | 리니지 연결 성공률 |
| 성능 부하 | 대량의 로그 분석 시 시스템 부하 | 증분 분석(Incremental Parsing) 적용 | 메타데이터 수집 소요 시간 |
| 오탐 (False Positive) | 동적 SQL이나 복잡한 프로시저 오분석 | 정교한 파서(Parser) 고도화 및 검증 | 리니지 정확도 (Precision) |

> 요약: 복잡한 로직에 따른 '연결 끊김'과 '오분석' 방지가 리니지 신뢰도의 관건이다.

| 점검 항목 | 목표 기준 | 측정 방법 |
|:---|:---|:---|
| 원인 분석 시간 (RCA) | 기존 대비 70% 이상 단축 | 장애 조치 리드타임 비교 |
| 영향 분석 정확도 | 변경 전 영향 범위 식별 100% | 실제 장애 발생 유무 확인 |
| 리니지 자동화율 | 전체 파이프라인의 90% 이상 자동 생성 | 전체 테이블 대비 자동 연결 비율 |

> 요약: 도입 효과는 장애 대응 속도 향상과 시스템 변경 리스크 감소로 측정한다.

## Ⅵ. 실무 적용 및 결론

**적용 방안 3개:**
1. **셀프 서비스 영향 분석**: 개발자가 코드 배포 전 카탈로그에서 리니지를 조회하여 본인의 변경이 어느 대시보드에 영향을 주는지 직접 확인
2. **품질 이슈 역추적(RCA)**: 보고서 숫자에 오류 발생 시 리니지를 거슬러 올라가(Backward) 어느 단계의 ETL에서 로직 오류가 발생했는지 즉시 특정
3. **GDPR/컴플라이언스 준수**: 고객 동의 철회 시 리니지를 통해 해당 고객 데이터가 전파된 모든 하위 저장소를 찾아내어 삭제 조치 증명

**결론 (2줄):**
- 기술사 판단: 데이터 리니지는 데이터 거버넌스의 '눈'과 같으며, 데이터의 신뢰를 기술적으로 담보하는 가장 강력한 수단이다.
- 향후 방향: '액티브 메타데이터'와 결합하여 소스 변경 시 하류 시스템에 자동으로 알람을 보내거나 파이프라인을 일시 중단하는 '지능형 리니지'로 진화할 것이다.
