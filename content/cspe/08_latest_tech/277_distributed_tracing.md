# 📖 【암기용】 개념 완전 이해

> 목적: 하나의 요청이 수십 개의 서버를 핑퐁 치며 돌아다니는 MSA 환경에서, 이 요청이 정확히 언제/어디서/얼마나 머물렀는지 흐름을 꿰뚫어 보는 기술을 이해한다.

## 한눈에
- **정의**: 사용자의 단일 요청이 분산 시스템(마이크로서비스) 내부의 여러 구성 요소를 거쳐 가는 **전체 경로와 각 구간의 소요 시간, 상태를 추적하고 시각화하는 기술**
- **필요성**: MSA에서는 결제 버튼을 한 번 눌렀을 뿐인데 뒤에서 10개의 서버가 서로 API를 호출한다. 만약 5초나 걸렸다면, 10개 서버 중 '어떤 서버'의 '어느 구간'에서 병목이 생겼는지 일반적인 로그 파일만으로는 절대 찾을 수 없기 때문
- **핵심 직관**: "우체국 택배의 '송장 번호(Trace ID)' 조회 시스템. 서울에서 출발해 대전 허브, 부산 대리점을 거치는 모든 과정에 바코드(Span)를 찍어서 전체 배송 경로와 지연 구간을 한눈에 보게 해주는 것"

## 깊이 이해
- **배경(왜 등장했나?)**: 구글은 이미 2010년에 Dapper라는 내부 시스템으로 이 문제를 해결하고 논문을 썼다. 이 논문을 보고 "우리도 구글처럼 만들자!" 해서 나온 오픈소스가 Twitter의 Zipkin과 Uber의 Jaeger다. 이들이 MSA 디버깅의 구세주가 되면서 분산 추적이라는 장르가 확립되었다.
- **작동 원리(어떻게 달성했나?)**: 
  1. 사용자가 처음 접속하면 API Gateway가 **Trace ID**(전체 여정의 고유 식별자)를 하나 파서 HTTP 헤더에 몰래 끼워 넣는다.
  2. A 서버가 B 서버를 부를 때 이 헤더(Trace ID)를 같이 넘겨준다(Context Propagation).
  3. B 서버는 자신이 일한 시간(시작~끝)을 기록하는데, 이것을 **Span(스팬, 여정의 한 조각)**이라고 한다. Span에도 고유 ID가 있다.
  4. 모든 서버가 각자의 Span 조각들을 중앙 수집기(Jaeger 등)로 보낸다.
  5. 수집기는 같은 Trace ID를 가진 Span들을 시간순으로 예쁘게 조립하여 폭포수(Waterfall) 차트로 그려준다.
- **일상 비유**: 놀이공원에서 입장할 때 '전자 팔찌(Trace ID)'를 찬다. 바이킹 탈 때 태그(Span), 범퍼카 탈 때 태그(Span)를 하면, 집에 갈 때 "내가 오늘 하루 종일 어디서 몇 분 기다리고 무슨 놀이기구를 탔는지" 타임라인 차트로 쫙 뽑아볼 수 있는 것과 같다.
- **구체 예시**: 결제 요청(Trace) ➔ [A: API Gateway 10ms] ➔ [B: 인증 서버 20ms] ➔ [C: 결제 DB 연동 3000ms] ➔ 이렇게 폭포수 차트가 그려지면, 0.1초 만에 "아, DB 쿼리(C)가 미친 듯이 느리구나!" 하고 바로 범인을 잡을 수 있다.
- **흔한 오해/주의점**: "트레이스만 있으면 로그는 필요 없나?" → 아니다! 트레이스는 '어디서 멈췄는지(위치와 시간)'만 알려줄 뿐, '왜 멈췄는지(Null 에러 등)'는 알려주지 않는다. 그래서 트레이스 화면에서 그 에러가 난 Span을 클릭하면 해당 시간대의 '로그'로 넘어가도록 연동하는 것이 필수다.

## 연결 개념
- **Observability (관측성)**: 메트릭, 로그, 분산 추적이 합쳐져서 만들어지는 시스템 파악 능력.
- **W3C Trace Context**: "A 서버에서 B 서버로 Trace ID를 넘길 때, HTTP 헤더 이름을 제발 하나로 통일하자"라고 W3C에서 정한 글로벌 국제 표준 (`traceparent` 헤더).
- **Service Mesh (Istio)**: 개발자가 멍청해서 HTTP 헤더를 안 넘겨주는 불상사를 막기 위해, 인프라 레이어(사이드카)가 강제로 헤더를 전달하게 해주는 기술.

# 📝 【답안용】 시험 답안 템플릿

## 핵심 인사이트 (3줄 요약)
> 1. **본질**: 분산 추적(Distributed Tracing)은 MSA 및 클라우드 환경에서 발생하는 단일 트랜잭션의 전체 호출 경로(Topology)와 구간별 성능(Latency)을 가시화하는 관측성 핵심 기술이다.
> 2. **가치**: Trace ID 기반의 Context Propagation(문맥 전파)을 통해 블랙박스화된 분산 시스템의 병목 구간과 장애 근본 원인(Root Cause)을 신속하게 식별하여 MTTR을 극단적으로 단축한다.
> 3. **판단 포인트**: Trace와 Span의 계층적 구조를 명확히 이해하고, 시스템 부하를 막기 위한 Tail-based Sampling 적용과 W3C Trace Context 표준 준수가 성공적인 구축의 핵심 과제임을 제시해야 한다.

## Ⅰ. 개요 및 필요성
- **정의**: 분산 시스템 환경에서 하나의 비즈니스 트랜잭션이 여러 마이크로서비스를 통과하는 과정을 추적, 기록, 시각화하는 기술 (Dapper 논문 기반)
- **배경**: 모놀리식 시스템과 달리, MSA 환경에서는 네트워크 지연(Network Hop) 증가와 장애의 도미노 전파로 인해 기존의 단일 머신 기반 로그 분석이 무용지물이 됨
- **필요성**: End-to-End Latency 병목 구간 식별, 서비스 간의 동적 의존성 토폴로지 맵(Dependency Map) 자동 생성, 분산 에러 트래킹

## Ⅱ. 분산 추적의 핵심 구성 요소 (Trace와 Span)
분산 추적의 데이터 구조는 거대한 나무(Trace)와 가지(Span)의 트리(Tree) 구조로 되어 있다.

```text
Trace ID: [ 12345678 ] (단일 사용자 요청 전체를 관통하는 고유 ID)
 ├── Span A (API Gateway) [ 0 ~ 100ms ] 
 │     ├── Span B (Auth Service) [ 10 ~ 30ms ]
 │     └── Span C (Order Service) [ 30 ~ 100ms ]
 │           ├── Span D (Inventory DB) [ 40 ~ 60ms ]
 │           └── Span E (Payment API) [ 60 ~ 90ms ] ◀ (병목 발생 지점 파악 가능)
```

1. **Trace (트레이스)**: 사용자의 최초 요청부터 최종 응답까지의 전체 여정. (여러 개의 Span으로 구성)
2. **Span (스팬)**: 트레이스를 구성하는 기본 작업 단위. (작업명, 시작 시간, 종료 시간, 에러 여부, 커스텀 태그 포함)
3. **Context Propagation (문맥 전파)**: A 서비스가 B 서비스를 호출할 때 HTTP 헤더(또는 메시지 브로커 메타데이터)에 `Trace ID`와 부모의 `Span ID`를 실어서 보내는 행위.

## Ⅲ. 글로벌 표준: W3C Trace Context
과거에는 Zipkin(`X-B3-TraceId`), Datadog 등 도구마다 헤더 이름이 달라 서로 다른 툴 간에 추적이 끊어지는 현상이 발생했다. 이를 통합한 것이 W3C 표준이다.

- **`traceparent` 헤더**: 추적 정보를 전달하는 핵심 헤더. (포맷: `버전-TraceID-ParentSpanID-플래그`)
- **`tracestate` 헤더**: 특정 벤더(Datadog 등)에 특화된 추가적인 추적 데이터를 전달하기 위한 공간.

## Ⅳ. 분산 추적 시스템의 아키텍처 및 도구
| 구분 | 기능 및 역할 | 대표적인 오픈소스 도구 |
|:---|:---|:---|
| **Instrumentation (계측)** | 소스 코드 수준에서 Span을 생성하고 HTTP 헤더에 Trace 정보를 삽입/추출 | **OpenTelemetry SDK**, Spring Cloud Sleuth |
| **Collection (수집)** | 각 서비스에서 비동기적으로 전송된 Span 데이터를 중앙으로 수집/버퍼링 | **OpenTelemetry Collector** |
| **Storage (저장)** | 대규모 Span 데이터를 시간순으로 영속성 있게 저장하고 검색 인덱싱 처리 | **ElasticSearch**, Cassandra |
| **UI / Visualization (시각화)** | 수집된 Span들을 Trace ID 기준으로 조립하여 폭포수(Waterfall) 차트 렌더링 | **Jaeger**, Zipkin, Grafana Tempo |

## Ⅴ. 기술적 한계(리스크) 및 최적화 전략 (Sampling)
| 리스크 요인 | 현상 및 문제점 | 대응 전략: Sampling (샘플링) |
|:---|:---|:---|
| **스토리지 비용 폭발** | 트래픽 100%의 트레이스를 모두 저장하면 앱 자체 데이터보다 모니터링 데이터가 커져버림 | 트레이스 데이터 중 일부만 선별하여 저장하는 **Sampling 기법** 필수 적용 |
| **Head-based Sampling** | 요청이 '시작'될 때 주사위를 굴려 10%만 무작위 수집. 비용은 싼데 정작 진짜 에러난 요청이 수집 안 될 확률이 높음 | (한계 극복을 위해 Tail-based 도입) |
| **Tail-based Sampling** | (해결책) | 요청이 **'끝난' 후** 에러가 났거나 3초 이상 걸린 요청만 100% 선별 수집하고, 정상 요청은 1%만 수집하여 비용/효과 극대화 |

## Ⅵ. 실무 적용 및 결론
**적용 방안 및 실무 가이드:**
1. **Log-Trace Correlation (로그 연동)**: 에러가 발생했을 때 Trace 화면만으로는 부족하므로, 사내 표준 로깅 프레임워크(예: Logback)를 수정하여 모든 로그의 접두어(Prefix)로 `[TraceID]`가 자동으로 찍히게 설정(MDC 적용)해야 한다.
2. **Service Mesh(Istio) 연동**: 레거시 코드를 일일이 수정하기 힘들다면, Istio를 도입하여 Envoy 프록시가 네트워크 단에서 자동으로 Span을 생성하고 헤더를 포워딩하도록 구성한다.

**결론:**
- 분산 추적은 마이크로서비스라는 거대한 미로 속에서, 엔지니어가 길을 잃지 않게 해주는 **가장 확실한 '아리아드네의 실'**이다.
- 성공적인 정착을 위해서는 도구의 도입을 넘어, 개발 조직 전체가 Context Propagation과 Sampling 정책을 이해하고 표준에 맞게 코드를 계측(Instrumentation)하는 문화적 정렬이 필수적이다.
