# 📖 【암기용】 개념 완전 이해

> 목적: 분산 추적을 처음 봐도 완벽히 이해하게 만든다. 시험 답안 양식이 아니라, 이해를 위한 친절한 설명이다.

## 한눈에
- **개요**: 마이크로서비스(MSA)처럼 여러 서버로 쪼개진 환경에서, 하나의 사용자 요청이 어떤 서비스들을 거쳐 처리되는지 전체 경로를 추적하는 기술
- **왜 필요한가**: 사용자가 "주문이 안 돼요"라고 할 때, 주문 서비스, 결제 서비스, 재고 서비스 중 어디가 문제인지 알기 어렵다. 요청마다 고유한 ID를 붙여서 이동 경로를 따라가면 범인을 바로 잡을 수 있다.
- **핵심 직관**: 요청 하나하나에 '송장 번호(Trace ID)'를 붙여서 택배가 어느 허브(서비스)를 거치고 어디서 정체되는지 실시간으로 확인하는 시스템이다.

## 깊이 이해
- **배경·문제의식**: 서비스 간 호출이 얽히면(Service Chain) 병목 구간을 찾기 힘들다. 로그만 봐서는 서비스 A의 에러가 서비스 B 때문인지 알 수 없다. 전체 흐름을 관통하는 "맥락(Context)"이 필요해졌다.
- **작동 원리**: **Trace ID**와 **Span ID**를 사용한다. 요청이 들어올 때 Trace ID를 만들고, 다음 서비스로 넘길 때 이 ID를 헤더에 담아 보낸다(Context Propagation). 각 서비스는 자기가 한 일(Span)의 시작/종료 시간과 ID를 기록한다. 나중에 이를 모으면 하나의 커다란 흐름도(Gantt chart)가 된다.
- **비유**: 릴레이 달리기와 같다. 첫 주자가 바통(Trace ID)을 들고 뛰고, 다음 주자에게 넘긴다. 각 주자가 자기가 뛴 구간(Span)의 기록을 제출하면, 전체 달리기 기록과 어떤 주자가 느렸는지 한눈에 알 수 있는 것과 같다.
- **구체 예시**: 사용자가 클릭한 '구매' 버튼 요청이 [API 게이트웨이] -> [주문] -> [결제] -> [포인트] 서비스를 거치는 과정을 Jaeger나 Zipkin 화면에서 막대 그래프로 확인.
- **흔한 오해·주의점**: 모든 요청을 다 추적하면 서버 부하가 커질 수 있다. 그래서 일부 요청만 골라서 추적하는 **샘플링(Sampling)** 기법을 흔히 쓴다.

## 연결 개념
- Span — 분산 추적의 최소 작업 단위
- Context Propagation — 서비스 간에 추적 정보를 전달하는 메커니즘
- Jaeger, Zipkin — 대표적인 분산 추적 오픈소스 도구
- W3C Trace Context — 추적 정보 전달 방식의 글로벌 표준 규격

# 📝 【답안용】 시험 답안 템플릿

> 목적: 시험장에서 25분에 그대로 쓰는 답안 양식. 작성방식(추상표현 금지·수치·도식·문제유형 전환)을 엄격히 지킨다.
> 핵심: Trace ID 기반의 문맥 전파(Context Propagation) 메커니즘과 병목 분석(Bottleneck Analysis) 관점을 중심으로 서술한다.

## 핵심 인사이트 (3줄 요약)

> 1. **본질**: 분산 추적은 분산 아키텍처 환경에서 개별 요청의 전 생애주기(End-to-End)를 추적하여 서비스 간 호출 관계와 소요 시간을 시각화하는 관측 기술이다.
> 2. **가치**: 마이크로서비스 간 연쇄 장애(Cascading Failure)의 근본 원인(Root Cause)을 특정하고, 복잡한 호출 체인에서의 성능 병목 구간을 정확히 진단한다.
> 3. **판단 포인트**: 데이터 폭증에 따른 저장소 부하를 제어하기 위한 샘플링 전략과 W3C Trace Context 표준 준수를 통한 상호 운용성 확보가 중요하다.

## 출제 의도 및 답안 포인트

| 출제 의도 | 반드시 짚을 핵심 | 감점 회피 포인트 |
|:---|:---|:---|
| 분산 추적의 기본 동작 원리 이해 확인 | Trace ID, Span ID, Context Propagation | 단순히 "로그를 모은다"고만 서술 |
| 주요 구성요소 및 용어 정의 확인 | Span, Tag, Log, Annotation | 핵심 용어 혼용 및 오용 |
| 실무적 제약 사항 및 해결 방안 확인 | 샘플링 (Head/Tail-based), 오버헤드 관리 | 무조건적인 전수 조사 강조 (비현실성) |

> 요약: 요청 단위의 흐름 파악을 위한 식별자 체계와 이를 전파하는 메커니즘을 도식화하여 설명한다.

## Ⅰ. 개요 및 필요성

- 정의: 분산 시스템 내에서 발생한 하나의 요청이 여러 서비스를 거치며 처리되는 전체 경로를 추적하고 시각화하는 기술
- 배경: 마이크로서비스(MSA) 확산으로 서비스 간 의존성이 복잡해짐에 따라, 전통적 로깅으로는 장애 지점 및 병목 구간 특정 불가능
- 필요성: 시스템 가시성(Visibility) 확보를 통한 MTTR(평균 복구 시간) 단축, 지연 시간(Latency) 최적화, 서비스 간 호출 토폴로지 파악

---

## Ⅱ. 구조 및 구성요소

```text
User Request (Trace ID: T1)
      |
[ Service A ] --(Span: S1)--> [ Service B ] --(Span: S2)--> [ DB ]
      |                         |                             |
      +--------(Context Propagation: Trace ID 전달)-----------+
                                |
[ Collector ] <--- (Span Data: ID, Start/End Time, Tags) ---+
      |
[ Storage / UI ] (Visualize as Gantt Chart / Dependency Graph)
```

| 구성요소 | 역할 | 특이사항 |
|:---|:---|:---|
| Trace (트레이스) | 하나의 사용자 요청을 나타내는 전체 여정 | 여러 Span의 집합 |
| Span (스팬) | 서비스 내부의 논리적 작업 단위 (예: DB 쿼리, API 호출) | 시작/종료 시간, 상태 정보 포함 |
| Context Propagation | 서비스 간 호출 시 추적 식별자를 헤더 등으로 전달 | W3C Trace Context 표준 사용 |
| Instrumentation | 소스 코드에 추적 코드를 삽입하는 행위 | OpenTelemetry SDK 등 활용 |

> 요약: 요청 전체를 관통하는 Trace ID와 각 구간을 정의하는 Span ID의 계층적 구조를 가진다.

---

## Ⅲ. 동작원리 및 흐름도

```text
[동작 흐름: 생성 -> 전파 -> 기록 -> 수집 -> 분석]
1. Start Trace (Generate Trace ID)
2. Inject Context into Header (e.g., traceparent)
3. Extract Context & Create Child Span (Service B)
4. Export Spans to Collector (Async)
5. Stitch Spans via Trace ID (Analysis)
```

| 단계 | 처리 내용 | 검증 기준 |
|:---:|:---|:---|
| 1 | 문맥 주입 (Inject) | 호출 측 서비스가 HTTP 헤더 등에 Trace ID를 포함시켜 요청 전송 |
| 2 | 문맥 추출 (Extract) | 수신 측 서비스가 헤더에서 ID를 읽어 자신의 작업과 연계 (Parent-Child 관계) |
| 3 | 스팬 기록 | 각 서비스 내에서 작업의 성공 여부, 소요 시간, 예외 메시지 등을 Span에 저장 |
| 4 | 비동기 전송 | 애플리케이션 성능에 영향이 없도록 수집기(Collector)로 별도 전송 |

> 요약: 서비스 경계를 넘을 때 식별자를 전파(Propagation)하고, 나중에 이들을 식별자 기반으로 재조합하는 원리다.

## Ⅳ. 특징

| 구분 | 내용 | 판단 포인트 |
|:---|:---|:---|
| 인과 관계 파악 | 요청의 전후 맥락을 통해 장애의 근본 원인(Root Cause) 식별 | 상관관계 분석 능력 |
| 성능 가시화 | 각 구간별 소요 시간을 Gantt 차트 형태로 제공 | Latency Bottleneck 특정 |
| 토폴로지 자동 생성 | 서비스 간 실제 호출 관계를 그래프 형태로 자동 도식화 | 시스템 구조의 정기적 현행화 |
| 샘플링 지원 | 비용과 오버헤드를 고려하여 특정 비율의 요청만 추적 가능 | 데이터 비용 최적화 |

> 요약: 서비스 간의 '연결'과 '시간'을 데이터화하여 복잡한 시스템을 투명하게 만드는 특징을 가진다.

## Ⅴ. 심화 비교 및 적용 판단

| 비교 축 | 분산 로깅 (Distributed Logging) | 분산 추적 (Distributed Tracing) | 선택 기준 |
|:---|:---|:---|:---|
| 데이터 관점 | 개별 서비스의 이벤트 기록 (결과) | 요청의 흐름과 소요 시간 (과정) | 분석 대상의 범위 |
| 연결 고리 | 주로 타임스탬프, 서비스명 | Trace ID, Span ID (인과 관계) | 인과 관계 필요성 |
| 주 용도 | 구체적 에러 메시지 확인 | 병목 구간 찾기, 호출 관계 파악 | 장애 원인 특정 단계 |

> 요약: 로그는 '무슨 일이 일어났는가'를, 추적은 '어디서 왜 지연되는가'를 설명하는 데 특화되어 있다.

| 리스크 | 원인 | 대응 방안 | 확인 지표 |
|:---|:---|:---|:---|
| 성능 오버헤드 | 추적 데이터 생성/전송에 따른 자원 소모 | 확률적 샘플링(Adaptive Sampling) 적용 | 추적 활성 시 Latency 증가율 |
| 데이터 저장 비용 | 방대한 Span 데이터 적재로 인한 비용 증가 | 보관 주기 단축 및 중요한 요청 위주 샘플링 | 저장소 사용량 및 검색 속도 |
| 문맥 소실 | 일부 서비스나 미들웨어에서 ID 전달 누락 | 표준 라이브러리 및 에이전트 활용 강제 | 트레이스 완결성(Completeness) |

> 요약: 오버헤드 최소화를 위한 샘플링 전략과 모든 구간의 ID 전달 보장이 실무 적용의 성패를 가른다.

| 점검 항목 | 목표 기준 | 측정 방법 |
|:---|:---|:---|
| 추적 완결성 | 시작부터 끝까지 중간 끊김 없는 트레이스 비율 90% 이상 | Orphan Span(부모 없는 스팬) 비율 |
| 샘플링 비율 | 통상 1~5% (서비스 특성에 따라 조절) | 전체 트래픽 대비 추적 요청 수 |
| MTTR 단축 | 도입 전 대비 원인 특정 시간 50% 단축 | 장애 분석 로그 비교 |

> 요약: 시스템 가시성 확보라는 목표를 위해 추적 데이터의 연속성과 품질을 주기적으로 점검해야 한다.

## Ⅵ. 실무 적용 및 결론

**적용 방안 3개:**
1. 엔드투엔드 가시성 확보: 모바일 앱부터 백엔드 DB 쿼리까지 하나의 Trace ID로 엮어 전 구간 성능 모니터링
2. 병목 구간 자동 탐지: 특정 서비스의 p99 지연 시간이 급증할 때 해당 구간의 Span 정보를 통해 원인 즉시 파악
3. 서비스 의존성 관리: 시각화된 토폴로지를 통해 예상치 못한 순환 참조나 불필요한 API 호출 제거

**결론 (2줄):**
- 기술사 판단: 분산 추적은 MSA의 복잡성을 통제할 수 있는 유일한 '내시경'과 같은 기술로, 시스템 안정 운영의 필수 요건이다.
- 향후 방향: OpenTelemetry의 확산으로 벤더 독립적인 추적 체계가 안착되고, AI 기반의 자동 장애 원인 분석과 결합될 것이다.
