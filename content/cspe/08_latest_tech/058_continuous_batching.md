## 미리 알고가기

- 정적 배치는 모든 요청을 한 번에 묶어 같은 길이로 처리하는 전통 배치 방식임
- Continuous Batching은 토큰 단위로 빈 슬롯을 실시간 재사용하는 스케줄링 방식임
- Scheduler는 어떤 요청을 어느 타임슬롯에 넣을지 결정하는 실행 제어 계층임

## Ⅰ. 개요

- **정의/개념**: Continuous Batching은 요청이 끝나기를 기다리지 않고 디코딩 루프의 빈 슬롯에 새 요청을 즉시 삽입해 GPU를 지속적으로 바쁘게 유지하는 토큰 단위 스케줄링 기법임
- **배경/필요성**: 정적 배치는 가장 느린 요청에 전체 배치가 묶이기 쉬워 GPU 활용률이 낮아지므로, 가변 길이 요청이 많은 LLM 서빙에서는 요청 종료 시점마다 즉시 새로운 요청을 끼워 넣는 연속 배칭이 필요함

## Ⅱ. 특징

- 유휴 슬롯을 줄여 GPU utilization과 throughput을 높임
- 짧은 요청과 긴 요청이 섞인 환경에서 정적 배치보다 효율적임
- 스케줄링 정책에 따라 TTFT와 TPOT과 fairness 특성이 달라짐
- PagedAttention과 결합할 때 메모리 할당 효율이 더 좋아짐

## Ⅲ. 종류 및 비교

| 판단 기준 | 정적 배치 | Continuous Batching | Chunked Prefill 결합형 |
|:---|:---|:---|:---|
| 배치 갱신 시점 | 배치 종료 후 | 토큰 스텝마다 | 토큰 + prefill 단위 |
| GPU 활용률 | 낮을 수 있음 | 높음 | 더 높음 |
| 구현 복잡도 | 낮음 | 높음 | 매우 높음 |
| 대표 활용 | 단순 추론 | 실시간 챗봇 서빙 | 대용량 문서 혼합 처리 |

## Ⅳ. 구성요소 및 구조

| 구성요소 | 설명 |
|:---|:---|
| Request Queue | 새로 들어온 요청을 대기시키고 우선순위에 따라 스케줄러에 전달함 |
| Token Scheduler | 현재 배치에서 끝난 요청을 제거하고 빈 슬롯에 새 요청을 주입함 |
| Slot Manager | 요청별 상태와 토큰 진행 위치를 추적해 디코딩 루프에서 재배치를 가능하게 함 |
| Fairness Policy | 긴 요청과 짧은 요청 간 지연 편향을 줄이기 위한 우선순위 규칙을 담당함 |

```text
+------------------+     +------------------+     +------------------+     +------------------+
| Request Queue    | --> | Token Scheduler  | --> | Slot Manager     | --> | Fairness Policy  |
+------------------+     +------------------+     +------------------+     +------------------+
```

## Ⅴ. 원리 및 절차 흐름도

```text
+-------------+     +-------------+     +-------------+     +-------------+
| 요청 수신    | --> | 현재 배치 구성 | --> | 종료 슬롯 회수 | --> | 새 요청 즉시 투입 |
+-------------+     +-------------+     +-------------+     +-------------+
```

1. **요청 수신**: 여러 사용자의 요청이 큐에 들어오고 길이와 우선순위가 기록됨
2. **현재 배치 구성**: 실행 중인 요청들로 디코딩 배치를 형성함
3. **종료 슬롯 회수**: 특정 요청이 끝나면 해당 슬롯과 메모리 블록을 즉시 회수함
4. **새 요청 즉시 투입**: 회수된 슬롯에 대기 중인 새 요청을 바로 넣어 다음 토큰 스텝부터 실행함

## Ⅵ. 문제점 및 해결 방안

1. 문제: 짧은 요청을 우선적으로 계속 투입하면 긴 요청이 뒤로 밀려 starvation이나 불공정 지연이 발생할 수 있음
   - 해결방안: fairness-aware scheduling을 적용하고 queue wait time과 request completion variance로 공정성을 검증함
2. 문제: prefill이 매우 큰 요청이 들어오면 decode 중심 배치 흐름을 방해해 기존 사용자 TPOT이 흔들릴 수 있음
   - 해결방안: chunked prefill과 우선순위 분리를 적용하고 active user TPOT과 TTFT로 간섭 정도를 검증함
3. 문제: 빈번한 배치 재구성이 메모리 관리와 스케줄링 오버헤드를 키워 기대한 처리량 개선을 상쇄할 수 있음
   - 해결방안: batch update granularity와 slot 정책을 튜닝하고 scheduler overhead와 throughput으로 실제 이득을 검증함

## Ⅶ. 적용 사례

- 실시간 챗봇 플랫폼: 길이가 다른 다수의 요청을 동시에 처리함, 확인 지표는 throughput과 p95 latency임
- 코드 생성 서비스: 짧은 질의와 긴 생성 요청이 혼재된 환경을 운영함, 확인 지표는 GPU utilization과 queue wait time임
- vLLM 기반 API 서버: continuous batching을 기본 스케줄링으로 사용함, 확인 지표는 requests/sec와 TPOT임

## Ⅷ. 결론

Continuous Batching의 핵심은 배치를 크게 만드는 데 있지 않고 각 토큰 스텝마다 빈 슬롯을 즉시 재활용해 처리량과 응답성을 함께 끌어올리는 스케줄링 설계에 있음.
