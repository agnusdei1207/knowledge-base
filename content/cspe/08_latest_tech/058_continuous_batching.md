## 미리 알고가기

- 연속 배칭 ($Continuous$ $Batching$): 모든 요청이 끝날 때까지 대기하지 않고, 개별 요청의 종료와 인입 시점(토큰 단위)마다 배치를 동적으로 재조립하는 실시간 스케줄링 기법임
- 정적 배칭 ($Static$ $Batching$): 전통적인 배치 방식으로, 배치에 속한 모든 요청 중 '가장 긴 문맥의 응답'이 끝날 때까지 배치 내 다른 짧은 요청들까지 붙잡아두는 구조임
- 프리필 분할 ($Chunked$ $Prefill$): 새로 유입되는 긴 프롬프트 연산(Prefill)을 작은 청크로 쪼개어, 현재 진행 중인 디코드(Decode) 연산 루프 사이에 나누어 끼워 넣는 과부하 방지 기술임
- 아사 현상 ($Starvation$): 우선순위 스케줄링 오류로 인해 특정 긴 연산이나 백그라운드 요청이 CPU/GPU 자원을 영구히 얻지 못하고 대기 상태에 고사하는 버그임

## Ⅰ. 개요

- **정의/개념**: Continuous Batching은 LLM 추론 시 각 세션의 생성 완료 여부를 토큰 슬롯 단위로 매 스텝($Token$ $Step$) 실시간 판정하여, 먼저 끝난 요청은 즉시 배치에서 방출하고 대기 중인 새 요청을 그 빈 슬롯에 무중단 주입하는 미세 주행 스케줄링 기법임
- **배경/필요성**: 기존 정적 배칭은 가장 길게 말하는 한 명의 답변이 완료되어야만 전체 배치의 자원(VRAM)이 해제되므로, 생성 응답의 편차가 심한 LLM 환경에서 GPU의 연산 텐서 코어가 공회전하며 처리량($Throughput$)이 곤두박질치는 낭비를 해결하고자 고안됨

## Ⅱ. 특징

- GPU 연산 코어를 유휴 상태($Idle$)로 두지 않고 매 사이클마다 최대 가동하여, 물리 인프라의 처리 효율성을 기존 정적 대비 수 배 이상 높여줌
- 가상 메모리 관리 기술인 PagedAttention과 필연적으로 엮여 돌아가며, 비연속 VRAM 블록을 동적 배칭 주소로 고속 스와핑하여 가동함
- 새로 인입되는 프리필 연산과 기존 디코드 루프의 충돌을 제어하기 위해, 스케줄링의 우선순위와 배치 크기 동적 조율이 요구됨

## Ⅲ. 종류 및 비교

| 판단 기준 | 정적 배칭 (Static Batching) | 연속 배칭 (Continuous Batching) | 프리필 분할형 연속 배칭 (Chunked Prefill) |
|:---|:---|:---|:---|
| **배치 교체 주기** | 배치 내 전원 응답 완료 시점 | 매 단어 토큰 생성 스텝 시점 | 토큰 스텝 + 분할된 프리필 청크 단위 |
| **GPU 가동율** | 낮음 (대기 작업으로 인한 낭비) | 매우 높음 (유휴 슬롯 즉시 채움) | 극대화 (프리필-디코드 간섭 완전 차단) |
| **새 요청 인입 반응성** | 나쁨 (배치 전체가 비어야만 수용) | 좋음 (빈 슬롯 발생 시 즉각 수용) | 최상 (프리필 청크 삽입으로 즉각 처리) |
| **스케줄링 난이도** | 단순함 | 중간 (동적 텐서 결합 관리 필요) | 매우 높음 (청크 분할 및 연산 동기화) |

> 요약: 정적 배칭은 단답 대량 오프라인 연산에, 연속 배칭은 동적 실시간 대화 서빙에, 프리필 분할은 극단적인 혼합 길이 폭증 환경의 안정화에 적합함.

## Ⅳ. 구성요소 및 구조

| 구성요소 | 설명 |
|:---|:---|
| 우선순위 요청 큐 | 외부 유입 요청의 만료 시간 및 질문 길이를 기준으로 가중치를 계산하는 진입 대기열임 |
| 동적 토큰 스케줄러 | 매 생성 루프마다 배치 슬롯의 온/오프 상태를 검지하여 신구 세션을 갈아 끼우는 조율기임 |
| 텐서 스티칭 인터페이스 | 서로 다른 길이의 쿼리 텐서들을 하나의 GPU 배치 행렬로 결합 및 격리하는 동적 텐서 결합 장치임 |
| 분할 실행 밸브 | prefill을 수천 토큰 단위로 나누어 디코드 연산 사이에 번갈아 공급하는 청킹 제어기임 |

```text
[ Continuous Batching 동적 슬롯 재배치 ]
Step 1: [Req A (Decode)] [Req B (Decode)] [Req C (Decode)]
Step 2: [Req A (Decode)] [Req B (Finished) -> Swap in Req D (Prefill)] [Req C (Decode)]
- Req B가 끝나자마자 다음 스텝에서 대기 중이던 Req D의 프리필 연산을 그 자리에 즉시 태움
```

## Ⅴ. 원리 및 절차 흐름도

```text
+-------------+     +--------------+     +-------------+     +-------------+
| 다중 사용자 | --> | 토큰 스텝마다| --> | 완료 세션   | --> | 대기 큐에서 |
| 쿼리 유입   |     | 슬롯 상태검지|     | 즉시 방출   |     | 신규 세션바인|
+-------------+     +--------------+     +-------------+     +-------------+
```

1. **대기열 적재** — 동시다발적으로 들어오는 세션 요청들을 큐 메모리에 수집하고, 프리필에 필요한 토큰 소요량을 계측함
2. **단어 생성 연산** — 현재 배치에 묶인 활성 요청들에 대해 한 단어($1$ $Token$)를 생성하는 디코드 순방향 연산을 동시 가동함
3. **완료 슬롯 방출** — 생성된 토큰이 문장 끝 기호($EOS$)이거나 최대 길이에 도달하면, 해당 슬롯의 데이터 바인딩을 해제하고 즉시 방출함
4. **새 요청 주입** — 방출된 슬롯의 빈자리에 대기열의 다음 요청을 이식하고, 다음 토큰 스텝 시작 시점에 프리필 연산과 디코드를 함께 구동함

## Ⅵ. 실무 적용 및 유의점

1. 짧은 질문들을 우선 처리하다가 긴 프롬프트나 백그라운드 태스크가 영원히 VRAM을 얻지 못하고 큐에 고사하는 '아사($Starvation$)'를 막기 위해, 대기 시간에 가중치를 주는 공정 스케줄링($Fairness-aware$)을 설계하고, 대기 시간 분산 지표로 안전성을 검증해야 함
2. 디코드 연산 도중 방대한 책 분량의 텍스트 분석(대규모 Prefill) 요청이 갑자기 배치 슬롯으로 유입되면 연산 지연이 급격히 전이되어 기존 사용자들의 응답 속도($TPOT$)가 일시적으로 수 초 이상 튀는 불쾌한 경험을 주므로, 반드시 프리필 연산을 쪼개어 번갈아 실행하는 '프리필 분할($Chunked$ $Prefill$)' 옵션을 적용하고 응답 지연의 p95 신뢰도로 이를 점검해야 함

## Ⅶ. 결론

- Continuous Batching은 GPU의 강력한 행렬 코어를 단 1밀리초도 놀리지 않고 동적 세션으로 채워 넣는 현대 추론 스케줄링의 근간이며, 설계자는 긴 요청의 아사 방지 공정 배분 정책과 긴 입력 진입 시의 간섭을 차단할 프리필 분할 장치를 동시 수립하여 가용성 높은 서빙 플랫폼을 보장해야 함
