# 📖 【암기용】 개념 완전 이해

> 목적: Offline Evaluation을 처음 봐도 완벽히 이해하게 만든다. 시험 답안 양식이 아니라, 이해를 위한 친절한 설명이다.

## 한눈에
- **개요**: 머신러닝 모델을 실제 서비스에 배포하기 전, 이미 확보된 과거 데이터(Test Set)를 사용하여 모델의 예측 성능을 측정하고 검증하는 과정
- **왜 필요한가**: 모델이 실제 운영 환경에서 사고를 치기 전에 미리 "실력"을 확인하고, 여러 알고리즘 중 가장 우수한 것을 선별하여 배포 리스크를 줄이기 위함
- **핵심 직관**: 실제 수능 시험(Online)을 치르기 전에, 기출문제(Offline Data)를 풀면서 자신의 예상 점수와 취약점을 파악하는 "모의고사" 과정

## 깊이 이해
- **배경·문제의식**: 모델을 만들자마자 실제 사용자에게 노출하는 것은 매우 위험하다. 모델이 엉뚱한 답을 내놓거나 성능이 형편없을 수 있기 때문이다. 따라서 이미 정답을 알고 있는 과거 데이터를 가지고 모델이 얼마나 잘 맞히는지 테스트하는 안전한 검증 단계가 필요하다.
- **작동 원리**: 데이터를 학습(Train), 검증(Validation), 평가(Test) 셋으로 나눈다. 모델은 학습 셋으로 공부하고, 평가 셋으로 시험을 치른다. 이때 정확도(Accuracy), 정밀도(Precision), 재현율(Recall), F1-Score 등 수학적 지표를 사용하여 모델의 성능을 정량화한다.
- **비유**: 새로운 자율주행 알고리즘을 개발했을 때, 바로 복잡한 시내 도로로 나가는 것이 아니라 컴퓨터 시뮬레이션 환경(Offline)에서 수만 번 주행 테스트를 해보는 것과 같다.
- **구체 예시**: 개와 고양이를 분류하는 모델을 만들고, 학습에 쓰지 않은 1,000장의 사진을 보여준다. 모델이 950장을 맞혔다면 "이 모델의 오프라인 정확도는 95%다"라고 결론짓고 배포 준비를 한다.
- **흔한 오해·주의점**: "오프라인 성능이 좋으면 무조건 온라인에서도 잘 작동한다"는 위험한 생각이다. 과거 데이터에만 너무 맞춰진 '과적합(Overfitting)'이 발생했거나, 과거와 현재의 데이터 성격이 다르면 오프라인 성적은 좋아도 실제 서비스에선 실패할 수 있다.

## 연결 개념
- Hold-out Method — 데이터를 학습/평가용으로 나누는 가장 기본적 방식
- Cross-Validation (교차 검증) — 데이터가 적을 때 신뢰도를 높이기 위한 평가 기법
- Data Leakage — 학습 데이터에 평가 정보가 섞여 성능이 부풀려지는 치명적 실수

## 핵심 인사이트 (3줄 요약)

> 1. **본질**: 오프라인 평가는 과거의 정답이 포함된 독립적 데이터셋(Hold-out/Test Set)을 활용하여 모델의 수학적·통계적 성능을 정량적으로 측정하는 과정이다.
> 2. **가치**: 배포 전 모델의 품질을 객관적으로 검증하여 운영 리스크를 최소화하고, 다수의 하이퍼파라미터 조합 중 최적의 모델을 선별하는 근거를 제공한다.
> 3. **판단 포인트**: 단순 정확도(Accuracy) 외에 데이터 불균형을 고려한 지표(F1, AUC)와 일반화 성능(Generalization) 확보 여부를 중점적으로 평가해야 한다.

## 출제 의도 및 답안 포인트

| 출제 의도 | 반드시 짚을 핵심 | 감점 회피 포인트 |
|:---|:---|:---|
| 모델 검증 방법론 이해 확인 | 데이터 분할(Train/Val/Test), 교차 검증(Cross-validation) | 단순히 "테스트 데이터로 평가"라고 서술 |
| 문제 유형별 적정 지표 선정 역량 확인 | Confusion Matrix 기반 지표(Precision, Recall, F1), AUC-ROC | 모든 문제에 "정확도(Accuracy)"만 사용 |
| 일반화 성능 및 과적합 방지 전략 확인 | Overfitting 감지, 데이터 누출(Data Leakage) 방지 | "성능이 높다"와 같은 주관적 서술 |

> 요약: 모델의 기술적 완성도를 수학적 지표로 증명하고, 실제 환경에서도 통용될 수 있는 일반화 능력을 검증하는 체계 제시가 핵심이다.

## Ⅰ. 개요 및 필요성

- 정의: 모델 개발 단계에서 이미 수집된 과거의 라벨링된 데이터를 사용하여 모델의 예측력을 평가하고 튜닝하는 프로세스
- 배경: 실제 배포 전 모델의 신뢰성 확보 필요, 다양한 알고리즘 및 하이퍼파라미터 조합 간의 객관적 비교 우위 판단 요구
- 필요성: 과적합(Overfitting) 조기 발견 및 수정, 비즈니스 목표에 부합하는 최적의 임계치(Threshold) 설정, 모델 성능의 벤치마크 확립

## Ⅱ. 구조 및 구성요소

```text
Full Dataset -> Data Splitter (Hold-out/K-fold)
                      |
        +-------------+-------------+-------------+
        | (60~80%)    | (10~20%)    | (10~20%)    |
    Training Set   Validation Set    Test Set
        |             |             |
     Learning ->   Tuning  ->    Final Evaluation (KPI)
```

| 구성요소 | 역할 | 특이사항 |
|:---|:---|:---|
| Training Set | 모델의 가중치 학습에 직접 사용되는 데이터 | 모델의 '교과서' |
| Validation Set | 하이퍼파라미터 튜닝 및 모델 선택에 활용 | 학습 중 '모의고사' |
| Test Set | 최종 모델의 일반화 성능 측정에만 사용 | 단 한 번의 '수능' |
| Evaluation Metrics | 수치화된 성능 평가 기준 | 분류/회귀/랭킹 지표 |

> 요약: 데이터를 엄격히 분리하여 모델이 보지 못한 데이터에 대해 얼마나 잘 대응하는지(일반화)를 측정함.

## Ⅲ. 동작원리 및 흐름도

```text
데이터 전처리 -> 데이터셋 분할 -> 모델 학습(Train) -> 성능 검증(Val) -> 파라미터 튜닝 -> 최종 평가(Test) -> 리포트 생성
      |               |               |               |                |                |               |
      +---------------+---------------+---------------+----------------+----------------+---------------+-----> 배포 승인 여부 결정
```

| 단계 | 처리 내용 | 검증 기준 |
|:---:|:---|:---|
| 1 | 데이터 분할 및 샘플링 | 레이블 비율 유지(Stratified Sampling) |
| 2 | 반복적 학습 및 하이퍼파라미터 튜닝 | Validation Loss 하락 여부 확인 |
| 3 | 최종 모델 선정 및 Test Set 평가 | Test 성능 vs Train 성능 격차 확인 |
| 4 | 성능 지표(Confusion Matrix) 도출 | Precision, Recall, F1 지표 산출 |

> 요약: 학습 과정에서 배제된 데이터를 통해 모델의 객관적인 성적표를 도출하고 과적합 여부를 판정함.

## Ⅳ. 특징 (문제 유형별 주요 지표)

| 문제 유형 | 주요 평가지표 | 공식/의미 | 판단 포인트 |
|:---|:---|:---|:---|
| 이진 분류 (Binary) | Accuracy, F1-Score | $(TP+TN) / Total$, Precision/Recall 조화 평균 | 클래스 불균형 고려 |
| 분류 확률 (Prob) | AUC-ROC, Log Loss | 임계치 무관 성능, 실제 확률값과 차이 | 분류 경계 안정성 |
| 회귀 (Regression) | RMSE, MAE, R-squared | 오차 제곱근 평균, 설명력 지표 | 이상치(Outlier) 민감도 |
| 추천/랭킹 (Ranking) | NDCG, MRR, HR | 순위 가중치 고려 관련성 | 상위 결과의 정확성 |

> 요약: 문제의 특성(분류, 회귀, 랭킹)과 데이터의 분포(불균형 등)에 맞는 최적의 평가지표를 선정해야 함.

## Ⅴ. 심화 비교 및 적용 판단

| 비교 축 | Hold-out Method | K-fold Cross Validation | 선택 기준 |
|:---|:---|:---|:---|
| 데이터 활용도 | 낮음 (일부만 학습 사용) | 높음 (모든 데이터가 학습/평가 활용) | 전체 데이터 양 |
| 계산 비용 | 낮음 (1회 학습) | 높음 (K회 반복 학습) | 가용 리소스 및 시간 |
| 신뢰도 | 중간 (분할 운에 좌우됨) | 높음 (평균치 사용으로 변동성 감소) | 모델 평가의 엄밀성 |

> 요약: 데이터가 충분하면 빠른 Hold-out을, 데이터가 적거나 신뢰도가 중요하면 K-fold를 선택함.

| 리스크 | 원인 | 대응 방안 | 확인 지표 |
|:---|:---|:---|:---|
| Data Leakage | 미래 정보나 정답이 학습 셋 유입 | 시간순 분할(Time-series split) 적용 | 비정상적으로 높은 성능 |
| Overfitting | 모델이 학습 데이터만 암기함 | 규제화(Regularization), 드롭아웃 | Train vs Test 성능 격차 |
| Sample Bias | 평가 데이터가 실제 운영과 다름 | 실제 운영 데이터와 통계적 대조 | 데이터 드리프트 지표(PSI) |

> 요약: 누출은 시간순 분할로, 과적합은 규제화로, 편향은 운영 데이터 대조로 대응함.

| 점검 항목 | 목표 기준 | 측정 방법 |
|:---|:---|:---|
| 일반화 성능 | Train/Test Accuracy 차이 5% 이내 | 두 세트 간 성능 차이 모니터링 |
| 지표 적합성 | 비즈니스 목표와 지표 간 상관관계 | 예: 스팸 차단은 Precision 우선 |
| 모델 안정성 | 교차 검증 간 성능 편차 2% 이내 | Fold별 지표의 표준편차 분석 |

> 요약: 도입 효과는 모델의 일반화 능력, 지표의 비즈니스 정렬도, 결과의 재현성으로 판정함.

## Ⅵ. 실무 적용 및 결론

**적용 방안 3개:**
1. 불균형 데이터 처리: 이상 탐지(FDS) 모델 평가 시, 정확도 대신 F1-Score와 AUPRC(Precision-Recall 곡선 하단 면적)를 사용하여 소수 클래스 탐지력 확보
2. 시계열 데이터 검증: 과거 11개월로 학습하고 최근 1개월로 평가하는 'Time-series Rolling Window' 방식을 적용하여 데이터 누출(Leakage)을 원천 차단
3. 자동화된 벤치마크: 신규 모델 개발 시 기존 베이스라인 모델(Baseline)과의 오프라인 성능 비교 리포트를 자동 생성하여 배포 승인 프로세스 효율화

**결론 (2줄):**
- 기술사 판단: 오프라인 평가는 모델의 "이론적 한계치"를 확인하는 필수 과정이며, 여기서 검증되지 않은 모델은 결코 온라인에 배포되어서는 안 됨
- 향후 방향: 단순 지표 측정을 넘어 모델의 취약 구간을 자동으로 찾아내고 설명(XAI)해주는 지능형 평가 플랫폼으로 진화할 것임
