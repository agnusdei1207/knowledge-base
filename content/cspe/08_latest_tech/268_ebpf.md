# 📖 【암기용】 개념 완전 이해

> 목적: 리눅스 커널 소스코드를 고치지 않고도, 커널의 심장부에서 내 코드를 실행시켜 네트워크와 보안을 초고속으로 통제하는 마법의 기술 eBPF를 이해한다.

## 한눈에
- **정의**: 리눅스 커널(Kernel) 내부에서 샌드박스(안전한 격리 공간) 형태로 사용자 정의 코드를 실행할 수 있게 해주는 **커널 프로그래밍 기술**
- **필요성**: 기존에는 네트워크 패킷을 분석하거나 차단하려면 커널 모듈을 새로 컴파일해서 재부팅해야 했다. 커널이 뻗으면 시스템 전체가 죽는 위험을 감수해야 했는데, 이를 재부팅 없이 안전하고 10배 이상 빠르게 하기 위함
- **핵심 직관**: "스마트폰(운영체제)의 핵심 코드를 고치지 않고도, 안전한 '앱(eBPF 프로그램)'을 깔아서 스마트폰의 배터리, 통신, 보안 기능을 마음대로 조작할 수 있게 된 것"

## 깊이 이해
- **배경(왜 등장했나?)**: 초창기 BPF는 `tcpdump`처럼 네트워크 패킷을 필터링하는 작은 도구였다. 그런데 넷플릭스나 메타(페이스북) 같은 거대 기업들이 "리눅스 네트워크 스택이 너무 느리다! 커널 깊은 곳에서 바로 패킷을 버리거나 관찰하고 싶다!"고 요구했다. 그래서 BPF를 확장(Extended)하여, 네트워크뿐만 아니라 파일 시스템, 함수 호출 등 커널의 '모든 이벤트'에 코드를 꽂아 넣을 수 있게 만든 것이 eBPF다.
- **작동 원리(어떻게 달성했나?)**: 
  1. 개발자가 C나 Rust로 코드를 짠다.
  2. eBPF 바이트코드로 컴파일해서 커널에 쑤셔 넣는다.
  3. **Verifier(검증기)**: 커널이 "이 코드가 무한 루프를 도는지, 커널을 박살 낼 위험이 있는지" 깐깐하게 검사한다. 통과하면 커널 메모리에 적재한다.
  4. **Hook(후킹)**: 시스템 콜이 불리거나 네트워크 패킷이 들어올 때마다, 그 이벤트에 갈고리(Hook)를 걸어둔 eBPF 코드가 빛의 속도로 실행된다.
- **일상 비유**: 식당 주방(커널)은 원래 관계자 외 출입 금지다. 요리법(커널 소스코드)을 바꾸려면 주방장을 해고하고 새로 뽑아야 했다. eBPF는 '안전한 투명 유리 상자(샌드박스)'를 주방에 들여놓고, 외부 컨설턴트가 그 안에서 조리 과정(이벤트)을 감시하거나 조미료를 칠 수 있게 허락해 준 것이다. 유리가 깨지면 즉시 쫓아내므로(Verifier) 주방은 절대 마비되지 않는다.
- **구체 예시**: eBPF를 활용한 대표적인 킬러 앱이 **Cilium(실리움)**이다. K8s 환경에서 iptables의 느려터진 룰을 버리고 eBPF를 써서 네트워크 속도를 비약적으로 끌어올렸다.
- **흔한 오해/주의점**: "eBPF로 어떤 코드든 짤 수 있나?" → 불가능하다. 보안을 위해 깐깐한 제약이 있다. 무한 루프 불가, 접근할 수 있는 커널 메모리 제한, 크기 제한 등이 있어서 복잡한 비즈니스 로직을 돌리기보다는 '가벼운 관측, 차단, 라우팅'에 특화되어 있다.

## 연결 개념
- **Kernel Space vs User Space**: 리눅스 OS의 권한 분리. eBPF는 User Space의 개발자가 Kernel Space의 이벤트를 다룰 수 있게 해주는 다리 역할을 한다.
- **Cilium**: eBPF를 기반으로 만들어진 K8s용 초고성능 네트워크 및 보안 솔루션.
- **Sidecarless Mesh**: 기존의 무거운 사이드카(Envoy) 대신 eBPF를 이용해 커널 단에서 통신을 제어하려는 최신 서비스 메시 트렌드.

# 📝 【답안용】 시험 답안 템플릿

## 핵심 인사이트 (3줄 요약)
> 1. **본질**: eBPF(Extended BPF)는 리눅스 커널 코드를 수정하거나 커널 모듈을 로드하지 않고도, 커널의 다양한 이벤트(Hook)에 샌드박스화된 프로그램을 동적으로 실행시키는 커널 기술이다.
> 2. **가치**: User Space로의 문맥 교환(Context Switching) 비용을 제거하여 네트워크 라우팅, 보안 감시, 텔레메트리 수집의 성능을 극대화하며, 커널 크래시의 위험을 원천 차단(Verifier)한다.
> 3. **판단 포인트**: 클라우드 네이티브 생태계에서 K8s의 iptables/Kube-proxy 병목을 대체하는 Cilium의 기반 기술이며, 향후 Sidecar 없는 서비스 메시(Ambient Mesh)를 견인할 핵심 동력이다.

## Ⅰ. 개요 및 필요성
- **정의**: 시스템 콜, 네트워크 패킷, 커널 함수 추적 등의 커널 이벤트가 발생할 때, 샌드박스 내에서 안전하게 사용자 정의 코드를 실행할 수 있는 리눅스 커널 내장 가상 머신(JIT 컴파일러 지원)
- **배경**: 기존 커널 모듈(Kernel Module) 방식은 시스템 패닉(Kernel Panic) 위험이 컸으며, User Space 애플리케이션은 커널과의 끊임없는 문맥 교환으로 인해 마이크로서비스 환경의 엄청난 네트워크 트래픽을 감당할 수 없었음
- **필요성**: 커널의 안정성(Safety)을 해치지 않으면서도, 고성능 네트워크 패킷 처리 및 심층적인 시스템 관측성(Observability) 확보

## Ⅱ. eBPF 아키텍처 및 동작 메커니즘
eBPF는 User Space에서 작성된 코드를 커널에 주입하고 안전하게 실행하는 엄격한 파이프라인을 거친다.

```text
[ User Space ]
  1. C/Rust 코드 작성 ──(Clang/LLVM)──> [ eBPF Bytecode ]
                                              │ (bpf() 시스템 콜)
──────────────────────────────────────────────┼─────────────────────────
[ Kernel Space ]                              ▼
                                      ┌───────────────┐
                                      │ 2. Verifier   │ (안전성/무한루프 검증)
                                      └───────┬───────┘
                                              ▼
                                      ┌───────────────┐
                                      │ 3. JIT Compiler│ (네이티브 기계어 변환)
                                      └───────┬───────┘
  [ Kprobe / Uprobe ] ◀── Hooking ──── 4. eBPF Program ─── (eBPF Maps로 User Space와 데이터 공유)
  [ Tracepoint ]      ◀── Hooking
  [ XDP / TC ] (네트워크)◀── Hooking
```

1. **컴파일**: 소스 코드를 eBPF 바이트코드로 컴파일.
2. **검증 (Verifier)**: 커널을 다운시킬 수 있는 불법 메모리 접근, 무한 루프, 크기 초과 여부를 정적 분석하여 안전성 보장.
3. **JIT 컴파일**: 바이트코드를 CPU가 즉시 실행할 수 있는 네이티브 기계어로 변환하여 실행 속도 극대화.
4. **후킹 (Hooking)**: XDP(네트워크 스택 최하단), 시스템 콜 등에 갈고리를 걸어 이벤트 발생 시 코드 실행.

## Ⅲ. eBPF의 3대 핵심 유스케이스
1. **Networking (초고속 네트워킹 - XDP)**
   - 패킷이 네트워크 카드(NIC)에서 커널 스택(TCP/IP)으로 올라가기 전에, **가장 밑단(XDP)**에서 패킷을 낚아채어 드랍(DDoS 방어)하거나 다른 곳으로 라우팅.
2. **Security (보안 및 런타임 제어)**
   - 컨테이너가 띄우는 특정 프로세스나 비정상적인 시스템 콜(`execve`) 호출을 커널 레벨에서 즉각 탐지하고 차단 (예: Tetragon).
3. **Observability (심층 관측성)**
   - 애플리케이션 코드의 수정(Instrumentation) 없이도, 커널의 함수 호출을 추적(Kprobes)하여 모든 앱의 성능 병목 및 TCP 지연 시간을 시각화 (예: Hubble).

## Ⅳ. eBPF vs 기존 방식 (커널 모듈 & iptables)
| 비교 항목 | Linux 커널 모듈 (LKM) | iptables (Kube-proxy) | eBPF (XDP/TC) |
|:---|:---|:---|:---|
| **안전성** | 매우 낮음 (버그 시 Kernel Panic) | 안정적임 | **매우 높음 (Verifier가 사전에 차단)** |
| **성능/속도** | 빠름 | 규칙이 많아질수록 $O(N)$으로 느려짐 | **$O(1)$ 해시 테이블(Maps) 기반 압도적 속도** |
| **업데이트** | 커널 재컴파일 및 재부팅 필요 | 룰 변경 시 전체 동기화로 병목 | **재부팅/재기동 없이 동적으로 프로그램 교체** |
| **활용 분야** | 하드웨어 드라이버 개발 | 기본 방화벽, 레거시 K8s 라우팅 | **클라우드 네이티브 네트워크, Service Mesh** |

## Ⅴ. 기술적 한계(리스크) 및 최신 발전 동향
| 리스크 요인 | 원인 분석 | 최신 극복 동향 및 엔지니어링 가이드 |
|:---|:---|:---|
| **극악의 개발 난이도** | C 언어로 커널 자료구조를 다뤄야 하며, Verifier의 엄격한 제약(루프 금지 등)을 우회하며 코딩해야 함 | **BCC, bpftrace, Cilium** 등 eBPF를 추상화한 고수준 오픈소스 프레임워크를 적극 활용 |
| **커널 버전 종속성 (CO-RE)** | 과거 eBPF 프로그램은 커널 버전이 바뀌면 구조체 오프셋이 달라져 다시 컴파일해야 했음 | **CO-RE (Compile Once – Run Everywhere)** 기술 도입으로, 한 번 컴파일하면 모든 최신 리눅스 커널에서 동작 보장 |

## Ⅵ. 실무 적용 및 결론
**적용 방안 및 실무 가이드:**
1. **K8s 클러스터 네트워킹 교체 (Cilium)**: 쿠버네티스 도입 시 기본 네트워크 플러그인(CNI)인 Flannel이나 Calico의 iptables 모드 대신, **eBPF 기반의 Cilium CNI**를 도입하여 대규모 클러스터에서의 라우팅 성능 저하를 방지한다.
2. **Zero-Instrumentation Observability**: 소스 코드를 건드릴 수 없는 레거시 시스템이나 타사 솔루션의 경우, eBPF 에이전트(Pixie 등)를 노드에 설치하여 앱 코드 수정 없이 HTTP 트래픽과 DB 쿼리 응답 시간을 즉시 모니터링한다.

**결론:**
- eBPF는 **"JavaScript가 웹 브라우저를 동적 프로그래밍 가능하게 만든 것처럼, 리눅스 커널을 동적 프로그래밍 가능하게 만든"** 10년에 한 번 나올 법한 시스템 소프트웨어의 혁명이다.
- 컨테이너 오케스트레이션(K8s)의 폭발적 성장으로 인해 발생한 네트워크/보안 성능의 한계를 커널 깊숙한 곳에서 타파하며, 클라우드 네이티브 2.0 시대를 견인하는 핵심 기반 기술이 되었다.
