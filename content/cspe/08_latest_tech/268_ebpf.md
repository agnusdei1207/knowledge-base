# 📖 【암기용】 개념 완전 이해

> 목적: eBPF를 처음 봐도 완벽히 이해하게 만든다. 시험 답안 양식이 아니라, 이해를 위한 친절한 설명이다.

## 한눈에
- **개요**: 운영체제 커널(Kernel)을 수정하거나 재부팅 하지 않고도, 커널 내부에서 안전하게 사용자 정의 프로그램을 실행할 수 있게 해주는 혁신적인 기술
- **왜 필요한가**: 예전에는 운영체제 기능을 바꾸려면 커널 코드를 직접 고치고 재컴파일해야 했다. 이건 너무 위험하고 어렵다. eBPF는 커널이라는 견고한 성 안에서 안전하게 샌드박스(Sandbox) 프로그램을 돌릴 수 있게 해준다.
- **핵심 직관**: "컴퓨터 운영체제(커널)의 핵심 기능을 실시간으로 확장하고 커스터마이징 할 수 있는 '커널용 자바스크립트' 또는 '커널 플러그인 시스템'"

## 깊이 이해
- **배경·문제의식**: 네트워크 패킷 처리, 시스템 보안 감시, 성능 프로파일링을 하려면 커널 깊숙한 곳을 건드려야 한다. 하지만 커널은 아주 민감해서 작은 실수로도 전체 시스템이 뻗어버린다(Kernel Panic). 안전하면서도 강력한 성능을 내는 커널 확장 방식이 필요해졌다.
- **작동 원리**:
  1. **이벤트 트리거**: 시스템 콜(syscall), 패킷 도착, 함수 실행 등 특정 사건에 프로그램을 연결(Hook)한다.
  2. **검증기(Verifier)**: 프로그램이 커널을 망가뜨리지 않는지(무한 루프, 불법 메모리 접근 등) 미리 검사한다.
  3. **JIT 컴파일**: 안전이 확인되면 즉시 기계어로 바꿔서 하드웨어 수준의 속도로 실행한다.
  4. **맵(Maps)**: 실행 결과를 사용자 프로그램과 공유하기 위해 효율적인 데이터 저장소(Maps)를 사용한다.
- **비유**: 웹 브라우저(커널) 자체를 다시 만들지 않고도 크롬 확장 프로그램(eBPF)을 깔아서 새로운 기능을 추가하는 것과 같다. 확장 프로그램이 브라우저 전체를 죽이지 않도록 안전장치가 있는 것도 비슷하다.
- **구체 예시**: Cilium은 eBPF를 써서 쿠버네티스의 네트워크 속도를 획기적으로 높였다. 사이드카 프록시를 거치지 않고 커널에서 바로 패킷을 전달하기 때문이다.
- **흔한 오해·주의점**: "eBPF는 네트워크 필터일 뿐이다"라는 말은 옛날 말이다(Classic BPF). 최신 eBPF는 보안, 관측성, 성능 최적화 등 거의 모든 영역에서 커널의 능력을 확장하는 범용 도구다.

## 연결 개념
- XDP (Express Data Path) — eBPF를 이용해 패킷을 가장 빠르게 처리하는 경로
- Cilium — eBPF 기반의 차세대 클라우드 네이티브 네트워크(CNI)
- Observability — eBPF를 통해 애플리케이션 수정 없이 얻는 깊은 통찰력

# 📝 【답안용】 시험 답안 템플릿

> 목적: 시험장에서 25분에 그대로 쓰는 답안 양식. 작성방식(추상표현 금지·수치·도식·문제유형 전환)을 엄격히 지킨다.
> 핵심: eBPF는 커널 내 샌드박스 실행 구조(Hook, Verifier, JIT)와 이를 통한 가속/보안/관측 가치를 기술한다.

## 핵심 인사이트 (3줄 요약)

> 1. **본질**: eBPF(Extended Berkeley Packet Filter)는 리눅스 커널을 수정하거나 모듈을 로드하지 않고도 커널 내부에서 안전하고 효율적으로 사용자 정의 프로그램을 실행하는 기술이다.
> 2. **가치**: 커널 수준의 이벤트 훅(Hooking)을 통해 네트워크 성능 가속, 제로 트러스트 보안, 코드 수정 없는 관측성(Observability)을 제공한다.
> 3. **판단 포인트**: 기존의 무거운 사이드카 프록시 기반 아키텍처를 탈피하여, 커널 수준에서 성능 오버헤드를 최소화하려는 클라우드 네이티브 환경의 핵심 기반 기술로 채용된다.

## 출제 의도 및 답안 포인트

| 출제 의도 | 반드시 짚을 핵심 | 감점 회피 포인트 |
|:---|:---|:---|
| 차세대 커널 확장 기술 이해도 | Hooking, Verifier, JIT Compiler, Maps | 단순히 "패킷 필터링 기술"로만 한정하여 서술 |
| 클라우드 네이티브 성능 최적화 파악 | XDP 가속, 사이드카 우회(Sidecar-less) | 네트워크 영역에만 국한(보안, 관측성 누락) |
| 안정성 및 보안 메커니즘 확인 | Verifier의 정적 분석 역할, 샌드박스 환경 | 커널 직접 수정과의 위험성 차이 부각 부족 |

> 요약: 안전한 실행 환경(Verifier)과 고성능 처리(JIT)라는 기술적 실체와 이를 통한 시스템 전반의 혁신 가치를 기술한다.

## Ⅰ. 개요 및 필요성

- 정의: 운영체제 커널 내의 샌드박스 환경에서 사용자 정의 프로그램을 실행하여 기능을 확장하는 커널 가상 머신 기술
- 배경: 인프라의 복잡도 증가에 따른 커널 모듈 개발의 위험성 및 기존 사용자 공간 처리의 성능 한계(Context Switch) 발생
- 필요성: 시스템 재부팅 없는 실시간 커널 기능 확장, 고성능 네트워킹(XDP) 및 커널 수준의 보안 가시성 확보

---

## Ⅱ. 구조 및 구성요소

```text
[eBPF 실행 아키텍처]
User Space: [eBPF Loader / Program] <--- Maps (Data Sharing) ---> [App]
                  | (Load/Attach)
Kernel Space: [Verifier] -> [JIT Compiler] -> [Hook Point] (syscall, kprobes)
                  |             |                 |
                Check         Compile          Execute
```

| 구성요소 | 역할 | 특이사항 |
|:---|:---|:---|
| Hook Point | 프로그램이 트리거되는 특정 지점 | syscall, kprobes, uprobes, tracepoints 등 |
| Verifier | 프로그램의 안전성(루프, 메모리 접근) 검증 | 커널 패닉 방지를 위한 정적 분석 수행 |
| JIT Compiler | 바이트코드를 하드웨어 기계어로 즉시 변환 | 인터프리터 대비 비약적 성능 향상 |
| eBPF Maps | 커널과 사용자 공간 간 데이터 공유 저장소 | Hash, Array, LRU 등 다양한 데이터 구조 제공 |

> 요약: 사용자가 작성한 코드가 검증(Verifier)과 컴파일(JIT)을 거쳐 커널의 특정 이벤트(Hook)에 결합되어 실행되는 구조다.

---

## Ⅲ. 동작원리 및 흐름도

```text
[eBPF 프로그램의 생명주기]
Compile (C/Rust to Bytecode) -> Load (bpf syscall) -> Verification -> JIT -> Attach -> Event Trigger -> Maps Update
```

| 단계 | 처리 내용 | 검증 기준 |
|:---:|:---|:---|
| 1 | C 또는 Rust로 작성된 코드를 LLVM/Clang으로 바이트코드화 | eBPF 표준 명령어 셋 준수 |
| 2 | `bpf()` 시스템 콜을 통해 커널에 프로그램 로드 요청 | 사용자 권한(root 또는 CAP_BPF) 확인 |
| 3 | Verifier가 모든 실행 경로를 탐색하여 안전성 검증 | 무한 루프 부재, 유효한 포인터 접근 |
| 4 | 이벤트 발생 시 JIT 컴파일된 코드가 커널 문맥에서 실행 | 최소한의 지연 시간(Zero Copy) |

> 요약: 안전이 보장된 코드를 커널에 직접 심어 이벤트가 발생할 때마다 즉시 실행함으로써 컨텍스트 스위칭 없는 고속 처리를 달성한다.

## Ⅳ. 특징

| 구분 | 내용 | 판단 포인트 |
|:---|:---|:---|
| 안전성 | Verifier를 통한 커널 보호 및 샌드박스 실행 | 커널 모듈 대비 시스템 안정성 우위 |
| 성능 | JIT 컴파일 및 커널 내 직접 실행 (Zero Copy) | 사용자 공간 처리 대비 처리량 2~10배 향상 |
| 유연성 | 시스템 재부팅이나 소스 수정 없이 실시간 적용 | 인프라 운영 중단 없는 기능 업데이트 |

> 요약: 커널의 강력함과 샌드박스의 안전함을 동시에 확보하여 '커널의 프로그래밍화'를 실현한다.

## Ⅴ. 심화 비교 및 적용 판단

| 구분 | 커널 모듈 (LKM) | eBPF 프로그램 | 선택 기준 |
|:---|:---|:---|:---|
| 안전성 | 낮음 (버그 시 커널 패닉) | 매우 높음 (Verifier가 차단) | 시스템 안정성 중요도 |
| 개발 속도 | 느림 (커널 버전 의존성 높음) | 빠름 (추상화된 헬퍼 함수 활용) | 기능 배포의 민첩성 |
| 적용 범위 | 커널 모든 영역 접근 가능 | 제한적 (정해진 Hook Point 및 헬퍼) | 필요한 커널 제어의 깊이 |

> 요약: 커널 핵심 로직 수정은 LKM을, 네트워크/보안/관측성 확장은 안전한 eBPF를 선택한다.

| 리스크 | 원인 | 대응 방안 | 확인 지표 |
|:---|:---|:---|:---|
| 검증 실패 | 코드 복잡도가 Verifier 제한 초과 | 프로그램 분할(Tail Call) 및 논리 단순화 | Verifier 로그 및 거절 횟수 |
| 성능 오버헤드 | 너무 많은 훅 사용 시 CPU 부하 증가 | 훅 포인트 최적화 및 샘플링 적용 | eBPF 런타임 CPU 점유율 |
| 보안 악용 | 악의적인 eBPF 프로그램에 의한 감시 | CAP_BPF 권한 통제 및 서명 기반 로드 | 비인가 eBPF 로딩 시도 로그 |

> 요약: 복잡도 한계는 분할 실행으로, 부하 리스크는 최적화된 훅 포인트 선정으로 관리한다.

| 점검 항목 | 목표 기준 | 측정 방법 |
|:---|:---|:---|
| 패킷 처리량 | XDP 적용 시 PPS(Packets Per Second) 2배 향상 | `pktgen` 벤치마크 테스트 |
| 관측 데이터 정확도 | 샘플링 누락률 1% 미만 | 사용자 공간 수집 데이터와 대조 |
| 실행 안정성 | 커널 패닉 또는 런타임 에러 0건 | 시스템 커널 로그(`dmesg`) 모니터링 |

> 요약: 패킷 처리 성능 향상분과 시스템 안정성을 통해 eBPF 도입의 정량적 가치를 측정한다.

## Ⅵ. 실무 적용 및 결론

**적용 방안 3개:**
1. 고성능 네트워크 가속 (XDP): DDoS 공격 차단 시 IP 스택에 진입하기 전 네트워크 드라이버 계층에서 패킷을 즉시 폐기하여 시스템 부하 90% 절감
2. 런타임 보안 감시 (Tetragon): 특정 파일 접근, 권한 변경 등 민감한 시스템 호출을 실시간 감시하고 정책 위반 시 즉시 차단하는 제로 트러스트 보안 구현
3. 코드 수정 없는 분산 추적: 애플리케이션에 SDK를 심지 않고도 커널 수준에서 HTTP/gRPC 호출을 가로채어 마이크로서비스 간 가시성(L7 Observability) 확보

**결론 (2줄):**
- 기술사 판단: eBPF는 리눅스 커널의 패러다임을 바꾼 기술이며, 특히 클라우드 네이티브 환경에서 '성능'과 '관측성'의 병목을 해결할 핵심 열쇠다
- 향후 방향: Windows 커널(eBPF for Windows)로의 확장과 더불어, 사이드카를 완전히 대체하는 서비스 메시 아키텍처의 주류가 될 것이다
