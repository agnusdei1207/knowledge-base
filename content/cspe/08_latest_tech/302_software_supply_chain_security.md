# 📖 【암기용】 개념 완전 이해

> 목적: 소프트웨어 공급망 보안을 소스, 의존성, 빌드, 배포, 운영까지 이어지는 신뢰 체인 보호 관점으로 이해하게 만든다.

## 한눈에
- **개요**: 개발부터 배포까지 소프트웨어 산출물의 출처, 무결성, 취약점을 통제하는 보안 체계
- **왜 필요한가**: 오픈소스 패키지, CI/CD 권한, 컨테이너 이미지가 공격 경로가 되면 정상 서비스 배포 절차가 악성코드 유통 채널이 된다.
- **핵심 직관**: 완제품 검사만으로는 부족하고 부품 공급자, 조립 공정, 물류 봉인, 입고 검수를 함께 확인해야 함.

## 깊이 이해
- **배경·문제의식**: 현대 애플리케이션은 직접 작성 코드보다 외부 패키지, 빌드 플러그인, 베이스 이미지 의존이 많아 개발 조직 바깥의 위험이 제품 위험으로 전이된다.
- **작동 원리**: 소스 저장소 보호, 의존성 검증, 빌드 격리, SBOM 생성, 산출물 서명, 배포 게이트, 런타임 모니터링을 DevSecOps 파이프라인에 배치한다.
- **비유**: 병원 의약품 관리처럼 처방전, 제조 로트, 유통 온도, 입고 검수, 투약 기록이 모두 연결되어야 사고 범위를 추적할 수 있다.
- **구체 예시**: 신규 CVE가 npm 패키지에 공개되면 SCA와 SBOM으로 영향 서비스를 찾고, 서명 없는 컨테이너 이미지는 Kubernetes admission 단계에서 차단한다.
- **흔한 오해·주의점**: 공급망 보안은 오픈소스 차단 정책이 아니다. 허용 목록, 취약점 SLA, provenance, 보상 통제를 통해 사용 가능한 의존성을 관리하는 체계다.

## 연결 개념
- NIST SSDF — 보안 개발 활동 프레임워크
- SLSA — 빌드 산출물 신뢰 수준
- SBOM — 구성요소와 취약점 영향 분석 데이터

# 📝 【답안용】 시험 답안 템플릿

> 목적: 시험장에서 25분에 그대로 쓰는 답안 양식.
> 핵심: 공급망 보안은 도구 목록이 아니라 소스-의존성-빌드-배포-운영 단계별 공격면과 통제 연결을 답해야 한다.

## 핵심 인사이트 (3줄 요약)

> 1. **본질**: Software Supply Chain Security는 소프트웨어 산출물 생성·전달·실행 경로의 신뢰를 보장하는 통제 체계임.
> 2. **가치**: 악성 의존성, 빌드 변조, 위조 이미지, 취약 라이브러리 반입을 배포 전후 지점에서 차단함.
> 3. **판단 포인트**: SSDF, SCA, SBOM, SLSA, Sigstore, 배포 정책, 취약점 SLA를 단계별로 연결해야 함.

## 출제 의도 및 답안 포인트

| 출제 의도 | 반드시 짚을 핵심 | 감점 회피 포인트 |
|:---|:---|:---|
| 공급망 공격면 식별 확인 | source, dependency, build, artifact, deploy | 오픈소스 취약점만 설명 |
| 통제 설계 역량 확인 | SCA, SBOM, signing, provenance, admission | CI/CD 마지막 스캔으로 축소 |
| 운영 지표 판단 확인 | critical CVE SLA, unsigned artifact, policy violation | 보안 인식 교육 중심 답안 |

> 요약: 이 문제는 공급망 각 단계의 공격면과 자동화 통제를 매핑하는 답안을 요구한다.

---

## Ⅰ. 개요 및 필요성

- 개요: 소프트웨어 신뢰 체인 보호
- 배경: 패키지 저장소, 빌드 스크립트, CI 토큰, 컨테이너 레지스트리가 공격 대상이 됨.
- 필요성: 배포 산출물이 승인된 소스와 검증된 의존성에서 생성됐는지 증명해야 함.

---

## Ⅱ. 구조 및 구성요소

```text
Source Control -> Dependency Intake -> Build / CI -> Artifact Registry
       +-> SAST / SCA / Secret Scan
       +-> SBOM / SLSA / Signature -> Deployment Gate -> Runtime Monitor
```

| 구성요소 | 역할 | 특이사항 |
|:---|:---|:---|
| 소스 통제 | 코드 변경, 브랜치, 리뷰 권한 관리 | MFA, branch protection |
| 의존성 통제 | 오픈소스 패키지 취약점·라이선스 점검 | SCA, allowlist |
| 빌드 통제 | 빌더 격리와 산출물 증명 생성 | SLSA, provenance |
| 배포 통제 | 서명·정책 위반 산출물 차단 | admission policy |

> 요약: 공급망 보안은 개발 단계 검사를 넘어 빌드 증명과 배포 정책까지 포함하는 연속 통제 구조다.

---

## Ⅲ. 동작원리 및 흐름도

```text
요구사항 / 코드 변경 -> 저장소 정책 검사 -> 의존성 스캔
-> 격리 빌드 -> SBOM / 서명 / provenance 생성
-> registry 저장 -> 배포 정책 검증 -> 런타임 탐지
```

| 단계 | 처리 내용 | 검증 기준 |
|:---:|:---|:---|
| 1 | 코드 변경 승인과 시크릿 유출 검사 | reviewer, secret scan |
| 2 | 의존성 취약점·라이선스·평판 확인 | CVSS, license policy |
| 3 | 빌드 산출물 SBOM·서명·provenance 생성 | SPDX/CycloneDX, signature |
| 4 | 배포 게이트와 런타임 정책으로 위반 차단 | policy violation count |

> 요약: 공급망 보안은 개발 중 검사와 배포 시 검증을 분리하지 않고 산출물 메타데이터로 연결한다.

---

## Ⅳ. 특징

| 구분 | 취약점 관리 중심 | 공급망 보안 중심 | 판단 기준 |
|:---|:---|:---|:---|
| 범위 | 코드와 라이브러리 | 소스·빌드·배포 경로 | 공격면 범위 |
| 산출물 | 스캔 리포트 | SBOM, provenance, signature | 자동 검증 가능성 |
| 통제 시점 | 릴리스 전 점검 | 개발·빌드·배포·운영 연속 | 배포 빈도 |
| 책임 | 보안팀 중심 | 개발·플랫폼·보안 공동 | DevSecOps 성숙도 |

> 요약: 공급망 보안은 취약점 점검을 포함하지만 핵심은 산출물 출처와 전달 경로의 신뢰 검증이다.

---

## Ⅴ. 심화 비교 및 적용 판단

| 비교 축 | 기존/대안 | 본 키워드 | 선택 기준 |
|:---|:---|:---|:---|
| 의존성 | 수동 승인 | SCA+SBOM 자동 매핑 | 패키지 변경 빈도 |
| 산출물 | 파일 해시 보관 | 서명+provenance 검증 | 외부 배포 여부 |
| 운영 | 사고 후 조사 | CVE 영향 분석 SLA | 서비스 중요도 |

> 요약: 외부 패키지와 자동 배포 비중이 높을수록 공급망 보안을 릴리스 게이트로 구현해야 한다.

| 리스크 | 원인 | 대응 방안 | 확인 지표 |
|:---|:---|:---|:---|
| 악성 패키지 반입 | typosquatting, dependency confusion | private registry, package pinning | blocked package count |
| 빌드 자격증명 탈취 | CI 토큰 과권한 | OIDC short-lived token, least privilege | token scope audit |
| 위조 산출물 배포 | 서명 검증 부재 | cosign verify, admission control | unsigned artifact deploy |

> 요약: 공급망 리스크는 패키지 반입, CI 권한, 산출물 위조로 나누어 통제해야 한다.

| 점검 항목 | 목표 기준 | 측정 방법 |
|:---|:---|:---|
| 취약점 대응 | critical CVE SLA 준수 | SCA issue aging |
| 산출물 신뢰 | 릴리스 100% 서명 검증 | registry/admission log |
| 의존성 투명성 | 핵심 서비스 SBOM 보유 | artifact-SBOM 매핑 |

> 요약: 공급망 보안 성과는 스캔 횟수가 아니라 CVE 대응 시간, 서명 검증률, SBOM 완전성으로 측정한다.

---

## Ⅵ. 실무 적용 및 결론

**적용 방안 3개:**
1. NIST SSDF 기준으로 보안 요구, 소스 통제, 취약점 대응, 릴리스 검증 활동을 SDLC 체크포인트에 배치함.
2. CI/CD에서 SAST, SCA, secret scan, SBOM 생성, SLSA provenance, cosign 서명을 릴리스 게이트로 자동화함.
3. Kubernetes admission controller에서 서명, 이미지 출처, critical CVE 예외 승인 여부를 검사하고 위반 배포를 차단함.

**결론 (2줄):**
- 기술사 판단: 자동 배포와 오픈소스 의존이 큰 조직은 공급망 보안을 개발 보안이 아니라 제품 신뢰 체계로 설계해야 함.
- 향후 방향: SBOM, VEX, SLSA, Sigstore가 결합되어 취약점 영향성과 산출물 무결성을 정책 기반으로 검증하는 구조가 확산됨.
