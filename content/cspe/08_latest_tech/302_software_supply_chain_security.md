# 📖 【암기용】 개념 완전 이해

> 목적: 소프트웨어 공급망 보안을 처음 봐도 완벽히 이해하게 만든다. 시험 답안 양식이 아니라, 이해를 위한 친절한 설명이다.

## 한눈에
- **개요**: 소프트웨어가 개발되어 사용자에게 도달하기까지의 전 과정(소스, 빌드, 배포, 운영)을 보호하는 보안 활동
- **왜 필요한가**: 과거에는 완제품 소프트웨어의 취약점을 공격했다면, 이제는 소프트웨어를 만드는 '공료 과정'이나 '재료(오픈소스)'에 독을 타는 공격이 더 효과적이고 치명적이기 때문이다.
- **핵심 직관**: "음식의 위생만큼이나 식재료의 원산지와 요리 과정의 청결함이 중요하다."

## 깊이 이해
- **배경·문제의식**: 현대 소프트웨어의 80~90%는 오픈소스 라이브러리로 구성됨. 공격자가 유명 라이브러리를 탈취해 악성 코드를 심으면(SolarWinds, Log4j), 이를 사용하는 전 세계 모든 시스템이 한꺼번에 오염됨.
- **작동 원리**: 공급망 보안은 '가시성(Visibility)'과 '무결성(Integrity)' 확보가 핵심임. ① **가시성**: 어떤 재료(SBOM)가 들어갔는지 파악. ② **무결성**: 재료와 조리 과정(SLSA)이 변조되지 않았는지 증명. ③ **지속성**: 도입 이후에도 실시간 취약점 모니터링.
- **비유**: 아파트 건설 보안. 설계도(소스) 보안은 물론, 자재(오픈소스)가 불량인지, 시공 과정(빌드)에서 철근을 빼먹지는 않는지, 완공 후 입주까지 안전하게 관리되는지를 모두 살피는 것.
- **구체 예시**: 개발자가 `npm install`을 할 때, 이미 알려진 취약점이 있거나(CVE), 최근에 갑자기 소유자가 바뀌어 악성 코드가 삽입된 패키지인지 자동 스캔하여 차단함.
- **흔한 오해·주의점**: 소스 코드 스캔(SAST)만 한다고 공급망 보안이 끝나는 게 아님. 빌드 서버 자체의 보안, 배포 이미지의 서명, 외부 종속성 관리(Dependency Management)가 모두 포함되어야 함.

## 연결 개념
- SBOM (Software Bill of Materials) - 공급망 보안의 가시성 도구
- SLSA (Supply-chain Levels) - 빌드 프로세스 신뢰 표준
- DevSecOps - 개발/운영 전반에 보안을 내장하는 문화

# 📝 【답안용】 시험 답안 템플릿

> 목적: 시험장에서 25분에 그대로 쓰는 답안 양식. 작성방식(추상표현 금지·수치·도식·문제유형 전환)을 엄격히 지킨다.
> 핵심: 단순히 위협을 나열하지 말고, 위협 모델(STRIDE 등)과 대응 프레임워크(SLSA, SBOM, NIST SSDF)를 연결한 입체적 방어 체계를 제시한다.

## 핵심 인사이트 (3줄 요약)

> 1. **본질**: 소프트웨어 공급망 보안은 SDLC 전 과정에 걸쳐 소스 코드, 빌드 환경, 외부 라이브러리 및 배포 아티팩트의 무결성과 신뢰를 보장하는 보안 통제 활동이다.
> 2. **가치**: 업스트림(Upstream) 위협이 다운스트림(Downstream)으로 전이되는 것을 차단하여 대규모 전파(Wildfire)형 침해 사고를 방지한다.
> 3. **판단 포인트**: '신뢰하되 검증(Trust but Verify)'에서 '검증 후 신뢰(Verify then Trust, Zero Trust)'로의 관점 전환과 자동화된 거버넌스 체계 구축이 핵심이다.

## 출제 의도 및 답안 포인트

| 출제 의도 | 반드시 짚을 핵심 | 감점 회피 포인트 |
|:---|:---|:---|
| 공급망 공격 벡터 이해 확인 | 오픈소스 오염, 빌드 침해, 배포 경로 탈취 (SolarWinds 사례) | 단순히 "오픈소스 보안"으로만 한정하지 말 것 |
| 대응 프레임워크 활용 역량 | SBOM(CycloneDX/SPDX), SLSA, NIST SSDF | 추상적인 "보안 강화" 대신 구체적 표준명 명시 |
| 실무적 무결성 확보 방안 | 디지털 서명, 코드 사인, SCA(Software Composition Analysis) | 기술적 도구만 나열하지 말고 프로세스와 거버넌스 연결 |

> 요약: 공급망 보안은 가시성(SBOM)과 신뢰 사슬(SLSA)을 통해 소프트웨어 신뢰성을 정량화하는 체계이다.

---

## Ⅰ. 개요 및 필요성

- 정의: 소프트웨어 개발 및 배포 전 주기(SDLC)에서 발생하는 소스, 빌드, 종속성, 배포물의 무결성을 보호하는 보안 활동
- 배경: 오픈소스 사용량 급증(90% 이상), 빌드 시스템(CI/CD)을 직접 겨냥한 지능형 지속 위협(APT)의 일상화
- 필요성: Log4j 등 광범위한 취약점 영향도 즉시 파악(MTTI 단축), 비인가 변조 차단을 통한 서비스 신뢰성 확보

---

## Ⅱ. 구조 및 구성요소 (공급망 위협 모델 기반)

```text
Source (A) -> Build (B) -> Distribution (C) -> Operation (D)
   |           |              |                |
   +-> (1)     +-> (2)        +-> (3)          +-> (4)

(1) 소스 변조/유출 (2) 빌드 시스템 침해 (3) 아티팩트 교체 (4) 런타임 취약점
대응: SAST/Review  대응: SLSA/Hardening 대응: Code Sign  대응: SBOM/SCA
```

| 구성요소 | 핵심 기술/표준 | 특이사항 |
|:---|:---|:---|
| 가시성 (What) | SBOM (SPDX, CycloneDX) | 구성 요소 및 취약점 추적 |
| 무결성 (How) | SLSA, Attestation, Sigstore | 빌드 프로세스 및 출처 증명 |
| 보안 개발 (SDLC) | NIST SSDF, BSIMM, SAMM | 보안 내재화 성숙도 모델 |

> 요약: 위협 지점(A~D)별로 적절한 기술적 통제와 표준 프레임워크를 매핑하여 방어 체계를 구축한다.

---

## Ⅲ. 동작원리 및 흐름도 (Secure Software Pipeline)

```text
Upstream (오픈소스) -> Ingestion (검증) -> Inner-source (개발) -> Build/Sign (증명) -> Runtime (관제)
         |               |                 |                 |                  |
         +-> CVE DB 스캔  +-> Proxy 레포 저장 +-> SLSA Provenance  +-> SBOM 기반 추적 +-> 드리프트 감지
```

| 단계 | 처리 내용 | 검증 기준 |
|:---:|:---|:---|
| 1 | Ingestion | 외부 라이브러리 반입 시 SCA 스캔 및 라이선스 검토 | 허용된 버전/라이선스 여부 |
| 2 | Development | 소스 코드 정적 분석(SAST) 및 기밀정보 스캔 | 취약점 점수(CVSS) 임계치 |
| 3 | Build & Sign | 격리된 빌드 및 아티팩트 디지털 서명 (SLSA) | 증명서(Provenance) 무결성 |
| 4 | Monitoring | 운영 중인 소프트웨어의 신규 취약점 실시간 매칭 | SBOM-to-Vulnerability 대응 |

> 요약: 반입부터 운영까지 각 단계의 게이트웨이에서 자동화된 검증을 수행하여 신뢰 사슬을 유지한다.

---

## Ⅳ. 특징 (위협 유형별 대응 기술)

| 구분 | 주요 위협 | 핵심 대응 기술 | 효과 |
|:---|:---|:---|:---|
| 종속성 (Dependency) | Typosquatting, 악성 패키지 주입 | SCA, Private Repository, Hash 검증 | 알려진 취약점 및 악성 코드 차단 |
| 파이프라인 (Pipeline) | CI/CD 환경 권한 탈취, 빌드 스크립트 변조 | SLSA L3+, Ephemeral Build, RBAC | 빌드 과정의 비변조성 보장 |
| 배포 (Distribution) | 이미지 레지스트리 오염, 중간자 공격 | Code Signing, Cosign, Notary | 배포물의 정당성 증명 |

> 요약: 공급망 보안은 도구 하나로 해결되지 않으며, SCA, SLSA, Code Signing이 유기적으로 결합되어야 한다.

---

## Ⅴ. 심화 비교 및 적용 판단

| 구분 | 기존 앱 보안 (AppSec) | 공급망 보안 (Supply Chain Sec) | 선택 기준 |
|:---|:---|:---|:---|
| 보호 대상 | 자체 작성 코드 (First-party) | 종속성 및 프로세스 (Third-party/Infra) | 개발자 실수 vs 외부 위협 |
| 핵심 도구 | SAST, DAST | SCA, SBOM, SLSA | 분석 범위 및 생태계 신뢰도 |
| 위협 모델 | Logic 취약점, 인젝션 | 무결성 침해, 의존성 오염 | 공격 표면적의 위치 |

> 요약: AppSec이 소프트웨어의 '품질'을 다룬다면, 공급망 보안은 '출처와 과정의 신뢰'를 다룬다.

| 리스크 | 원인 | 대응 방안 | 확인 지표 |
|:---|:---|:---|:---|
| Shadow IT 라이브러리 | 개발자의 임의 외부 패키지 도입 | Private Repo만 사용 허용, 비인가 도메인 차단 | 레포지토리 외 반입 시도 횟수 |
| 취약점 폭증 (Noise) | SCA 툴의 과도한 탐지 | Reachability 분석 (실제 호출 여부 판단) | 실제 조치 필요한 취약점 비율 |
| 런타임 변조 | 배포 이후의 악의적 파일 교체 | 무결성 기반 Admission Control (K8s) | 서명 검증 실패에 따른 차단 건수 |

> 요약: 탐지 성능(Noise 제거)과 강제성(Admission Control)의 균형이 실무 적용의 성패를 결정한다.

| 점검 항목 | 목표 기준 | 측정 방법 |
|:---|:---|:---|
| SBOM 커버리지 | 전사 서비스의 100% SBOM 보유 | 중앙 자산 관리 시스템 연동률 |
| 취약점 대응 속도 | Critical 취약점 공표 후 24시간 내 패치 | MTTR (Mean Time To Remediate) |
| 빌드 신뢰 등급 | 주요 서비스 SLSA Level 3 달성 | SLSA 평가 도구 (Scorecard) 점수 |

> 요약: 도입 효과는 가시성(SBOM), 신뢰도(SLSA), 대응 속도(MTTR)로 정량화하여 관리한다.

---

## Ⅵ. 실무 적용 및 결론

**적용 방안 3개:**
1. **SBOM 파이프라인 구축**: 빌드 시 CycloneDX 포맷의 SBOM을 자동 생성하고 VEX(Vulnerability Exploitability eXchange)를 통해 실제 위험 관리
2. **신뢰 기반 배포 통제**: Sigstore/Cosign을 활용하여 서명된 이미지와 검증된 SLSA Provenance가 있는 경우에만 운영 환경 배포 승인
3. **오픈소스 거버넌스 체계**: OpenChain(ISO/IEC 5230) 표준을 준수하는 오픈소스 관리 규정을 수립하고 전용 SCA 도구를 통한 라이선스/취약점 상시 점검

**결론 (2줄):**
- 기술사 판단: 공급망 보안은 단순한 기술 도입이 아닌 '신뢰할 수 없는 외부 요소'를 관리 영역으로 끌어들이는 거버넌스의 확장이며 Zero Trust의 실현이다.
- 향후 방향: AI를 활용한 비정상 패키지 탐지 및 자동 패치 기술이 고도화될 것이며, 민관 협력 기반의 공급망 위협 정보 공유 체계(ISAC 등) 강화가 필수적이다.
