# 📖 【암기용】 개념 완전 이해

> 목적: 데이터 레이크하우스를 처음 봐도 완벽히 이해하게 만든다. 시험 답안 양식이 아니라, 이해를 위한 친절한 설명이다.

## 한눈에
- **개요**: 데이터 웨어하우스(DW)의 데이터 관리 기능과 데이터 레이크(DL)의 유연성/저비용을 결합한 통합 데이터 아키텍처
- **왜 필요한가**: DW는 정형 데이터 처리에 강하지만 비싸고 유연성이 떨어지며, DL은 모든 데이터를 담을 수 있지만 관리가 안 되어 '데이터 늪(Swamp)'이 되기 쉽기 때문에 두 장점을 합친 대안이 필요했다.
- **핵심 직관**: "데이터 레이크의 넓은 저장 공간에 데이터 웨어하우스의 질서(트랜잭션, 스키마)를 부여한 것."

## 깊이 이해
- **배경·문제의식**: 기업들은 비정형 데이터(이미지, 로그) 분석과 머신러닝(ML)을 위해 DL을 구축했지만, DW처럼 신뢰성 있는 ACID 트랜잭션이 안 되어 데이터 품질 관리에 어려움을 겪음. 결국 DL에서 데이터를 가공해 다시 DW로 옮기는 중복 투자와 지연(Latency)이 발생함.
- **작동 원리**: 저렴한 클라우드 오브젝트 스토리지(S3, GCS 등) 위에 '오픈 테이블 포맷(Delta Lake, Iceberg 등)' 레이어를 얹음. 이 레이어가 메타데이터를 관리하여 SQL 쿼리, 트랜잭션, 버전 관리(Time Travel)를 가능하게 함. 이를 통해 하나의 저장소에서 BI(비즈니스 인텔리전스)와 AI/ML을 동시에 수행함.
- **비유**: DL이 아무렇게나 쌓인 '창고'라면, DW는 칸칸이 정리된 '백화점 매장'임. 레이크하우스는 창고처럼 대용량을 저렴하게 수용하면서도, 첨단 재고 관리 시스템을 도입해 백화점처럼 즉시 원하는 물건을 찾고 거래할 수 있게 만든 '스마트 물류 센터'.
- **구체 예시**: 넷플릭스나 우버 같은 기업이 페타바이트급 데이터를 S3에 쌓아두면서도, 데이터 레이크하우스 기술(Iceberg 등)을 써서 실시간 결제 정보 업데이트(UPSERT)를 수행하고 동시에 ML 모델 학습에 활용함.
- **흔한 오해·주의점**: 특정 벤더의 솔루션이 아님. 오픈 테이블 포맷과 컴퓨팅 엔진(Spark, Trino 등)이 결합된 아키텍처 개념임.

## 연결 개념
- Data Warehouse (DW) - 엄격한 스키마 기반의 분석용 저장소
- Data Lake (DL) - 가공되지 않은 모든 데이터의 저렴한 저장소
- Open Table Format (Delta, Iceberg, Hudi) - 레이크하우스 구현의 핵심 기술

# 📝 【답안용】 시험 답안 템플릿

> 목적: 시험장에서 25분에 그대로 쓰는 답안 양식. 작성방식(추상표현 금지·수치·도식·문제유형 전환)을 엄격히 지킨다.
> 핵심: DW와 DL의 한계를 기술적으로 어떻게 극복했는지(ACID, Schema Enforcement)를 명시하고, BI와 AI/ML 통합 활용 관점을 강조한다.

## 핵심 인사이트 (3줄 요약)

> 1. **본질**: 데이터 레이크하우스는 데이터 레이크의 저비용·유연성과 데이터 웨어하우스의 성능·신뢰성을 통합한 개방형 데이터 아키텍처이다.
> 2. **가치**: 데이터 중복 저장을 제거하여 TCO(총 소유 비용)를 절감하고, 단일 진실 공급원(SSOT) 기반의 실시간 BI 및 AI/ML 분석 환경을 제공한다.
> 3. **판단 포인트**: 오픈 테이블 포맷(Delta, Iceberg)을 통한 ACID 트랜잭션 보장과 스토리지-컴퓨팅 분리 구조가 핵심 기술적 특징이다.

## 출제 의도 및 답안 포인트

| 출제 의도 | 반드시 짚을 핵심 | 감점 회피 포인트 |
|:---|:---|:---|
| 데이터 아키텍처 진화 단계 이해 확인 | DW -> DL -> Lakehouse 발전 배경 및 한계 극복 | 단순히 "둘을 합쳤다"는 식의 추상적 서술 지양 |
| 핵심 구현 기술 파악 능력 | ACID 트랜잭션, 스키마 관리, 오픈 테이블 포맷 | 특정 벤더(Databricks 등)에 편향된 서술 경계 |
| 활용 및 기대효과 분석 역량 | 데이터 중복 제거, BI/ML 통합, Time Travel 기능 | 성능이 "좋다" 대신 "저장/처리 분리 통한 확장성" 명시 |

> 요약: 데이터 레이크하우스는 메타데이터 레이어를 통해 DL에 DW급 거버넌스를 부여하는 차세대 데이터 플랫폼이다.

---

## Ⅰ. 개요 및 필요성

- 정의: 저렴한 오브젝트 스토리지 위에서 DW급 데이터 관리 및 트랜잭션 기능을 구현한 통합 데이터 아키텍처
- 배경: DL의 데이터 품질 저하(Data Swamp), DW의 비정형 데이터 처리 한계 및 높은 스토리지 비용
- 필요성: BI(과거 분석)와 ML(미래 예측)을 위한 데이터 파이프라인 단일화 필요, 데이터 중복 및 이동에 따른 지연(Latency) 해소

---

## Ⅱ. 구조 및 구성요소

```text
Data Sources (정형/비정형) -> Ingestion -> [ Data Lakehouse ] -> Analytics/AI
                                          |
                                          +-> (1) Metadata Layer (Delta/Iceberg)
                                          |   - ACID, Schema, Indexing
                                          +-> (2) Cloud Storage (S3/GCS/Azure)
                                          |   - Parquet/Avro (Open Format)
                                          +-> (3) Compute Engines (Spark/Trino)
```

| 구성요소 | 역할 | 특이사항 |
|:---|:---|:---|
| Metadata Layer | ACID 트랜잭션, 버전 관리, 스키마 제어 | Delta Lake, Apache Iceberg, Hudi |
| Storage Layer | 대용량 데이터의 저비용 저장 | 오픈 파일 포맷 (Parquet, ORC) |
| Compute Layer | SQL 쿼리 및 분산 데이터 처리 | 스토리지와 독립적으로 스케일링 |

> 요약: 저렴한 저장소(Storage)와 강력한 관리층(Metadata)을 분리하여 유연성과 신뢰성을 동시에 확보한다.

---

## Ⅲ. 동작원리 및 흐름도

```text
Data Write -> [ Metadata Update ] -> [ Data File Write ] -> Commit
                 |                      |
                 +-> Log 관리            +-> Parquet 파일 생성
                 
Data Read  <- [ Metadata Query ] <- [ File Selection ] <- Query Engine
                 |                      |
                 +-> 스냅샷 확인          +-> 필요한 파일만 스캔
```

| 단계 | 처리 내용 | 검증 기준 |
|:---:|:---|:---|
| 1 | 데이터 유입 | 스트리밍/배치 데이터를 오브젝트 스토리지에 기록 | 쓰기 실패 시 롤백 보장 (ACID) |
| 2 | 스키마 검증 | 유입 데이터가 정의된 스키마에 맞는지 확인 | Schema Enforcement/Evolution |
| 3 | 메타데이터 갱신 | 파일 위치, 통계 정보, 트랜잭션 로그 기록 | Time Travel을 위한 버전 관리 |
| 4 | 쿼리 최적화 | 인덱스 및 메타데이터 기반으로 데이터 스킵 수행 | Z-Order, 데이터 클러스터링 |

> 요약: 메타데이터 로그를 통해 트랜잭션을 관리함으로써 데이터 일관성과 쿼리 성능을 보장한다.

---

## Ⅳ. 특징

| 구분 | 주요 특징 | 상세 내용 |
|:---|:---|:---|
| 트랜잭션 지원 | ACID 보장 | 여러 사용자가 동시에 데이터를 읽고 써도 무결성 유지 |
| 스키마 거버넌스 | Schema Enforcement | 잘못된 형식의 데이터 유입을 차단하여 데이터 품질 관리 |
| 개방성 | Open Table Format | 특정 벤더 종속 없이 다양한 엔진(Spark, Presto 등) 활용 가능 |
| 분석 통합 | BI + AI/ML | SQL 기반 분석과 라이브러리 기반 ML 학습을 단일 저장소에서 수행 |

> 요약: DW의 관리 기술을 DL에 이식하여 '데이터 늪' 현상을 방지하고 기업급 거버넌스를 제공한다.

---

## Ⅴ. 심화 비교 및 적용 판단

| 비교 축 | 데이터 웨어하우스 (DW) | 데이터 레이크 (DL) | 데이터 레이크하우스 |
|:---|:---|:---|:---|
| 데이터 형태 | 정형 중심 | 모든 형태 (비정형 포함) | 모든 형태 (고급 관리) |
| 비용 | 높음 (전용 스토리지) | 낮음 (오브젝트 스토리지) | 낮음 (오브젝트 스토리지) |
| 트랜잭션 | 강력함 (ACID) | 지원 안 함 (또는 미흡) | 강력함 (Metadata 기반) |
| 주요 용도 | BI, 보고서 | ML, 원천 데이터 보관 | BI + ML 통합 분석 |

> 요약: 비용 효율성은 DL을 따르고, 기능적 신뢰성은 DW를 따르는 최적의 절충안이다.

| 리스크 | 원인 | 대응 방안 | 확인 지표 |
|:---|:---|:---|:---|
| 작은 파일 문제 (Small Files) | 잦은 쓰기로 인한 파편화 | 주기적 데이터 최적화 (Compaction/Optimize) | 파일 당 평균 크기 (128MB~1GB 권장) |
| 메타데이터 부하 | 대규모 파티션 시 조회 지연 | 메타데이터 캐싱, 통계 정보 고도화 | 쿼리 플래닝 시간 (ms 단위) |
| 거버넌스 복잡도 | 다수의 엔진 접근 시 권한 불일치 | 중앙 집중식 카탈로그 (Unity, Glue) 도입 | 접근 제어 정책 일치율 |

> 요약: 아키텍처 특성상 발생하는 파일 파편화와 메타데이터 관리가 운영 성능의 핵심 리스크이다.

| 점검 항목 | 목표 기준 | 측정 방법 |
|:---|:---|:---|
| 데이터 신선도 | 실시간성 데이터 5분 이내 가공 완료 | End-to-End Latency 측정 |
| 쿼리 성능 | DW 대비 90% 이상의 성능 달성 | 벤치마크 (TPC-DS) 수행 |
| 스토리지 절감액 | 기존 DW 대비 비용 50% 이상 절감 | 클라우드 청구서 비교 분석 |

> 요약: 도입 효과는 분석 파이프라인의 단순화와 비용 절감, 그리고 데이터 신뢰도 향상으로 측정한다.

## Ⅵ. 실무 적용 및 결론

**적용 방안 3개:**
1. **메달리온 아키텍처 도입**: 데이터를 Bronze(Raw) -> Silver(Cleaned) -> Gold(Aggregated) 단계로 가공하며 레이크하우스의 트랜잭션 기능 활용
2. **증분 업데이트(CDC) 구현**: 외부 DB의 변경 사항을 Delta Lake 등으로 실시간 반영하여 DW 없이도 최신 데이터 분석 환경 구축
3. **MLOps 연계**: Time Travel 기능을 활용하여 과거 시점의 데이터를 재현하고 모델 학습 및 검증의 일관성 확보

**결론 (2줄):**
- 기술사 판단: 데이터 레이크하우스는 '저장' 중심에서 '거버넌스' 중심으로 데이터 전략이 이동하는 이정표이며, 클라우드 네이티브 데이터 전략의 핵심이다.
- 향후 방향: 단순 저장을 넘어 데이터 메시(Data Mesh), 데이터 패브릭(Data Fabric)과 결합하여 전사적 데이터 민주화를 가속화할 전망이다.
