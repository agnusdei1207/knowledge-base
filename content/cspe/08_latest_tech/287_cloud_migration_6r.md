# 📖 【암기용】 개념 완전 이해

> 목적: 온프레미스 전산실에 있는 100개의 낡은 시스템을 클라우드로 이사할 때, 시스템마다 어떤 방식(그냥 옮길지, 다 뜯어고칠지)으로 이사할지 결정하는 AWS의 6가지 핵심 전략을 이해한다.

## 한눈에
- **정의**: 기업의 IT 인프라와 애플리케이션을 온프레미스에서 클라우드로 마이그레이션할 때 적용하는 **6가지 이행 전략 (Rehost, Replatform, Repurchase, Refactor, Retire, Retain)**
- **필요성**: 모든 시스템을 클라우드 네이티브(MSA)로 다 뜯어고쳐서 이사하려면 10년이 걸려도 못 끝낸다. 시스템의 중요도와 예산에 맞게 '빠르게 옮길 놈'과 '천천히 고칠 놈'을 분류해야 하기 때문
- **핵심 직관**: "오래된 단독주택(온프레미스)에서 새 아파트(클라우드)로 이사할 때, 헌 냉장고를 그대로 들고 갈지(Rehost), 모터만 새걸로 갈아 끼울지(Replatform), 버리고 비스포크를 새로 살지(Repurchase) 결정하는 것."

## 깊이 이해
- **배경(왜 등장했나?)**: 2011년 가트너(Gartner)가 최초로 5R 제안했고, 이후 클라우드 제왕 AWS가 이를 다듬어 6R(현재는 7R까지도 말함)을 클라우드 마이그레이션의 글로벌 표준 프레임워크로 정립했다.
- **작동 원리 (6R의 종류)**:
  1. **Rehost (리호스트, Lift & Shift)**: **"그냥 들고 옮기기"**. 소스코드 수정 없이 온프레미스 VM을 그대로 AWS EC2로 복사한다. 가장 빠르지만, 클라우드의 이점(Auto-scaling 등)은 못 누린다.
  2. **Replatform (리플랫폼, Lift, Tinker & Shift)**: **"살짝만 튜닝하기"**. 코드는 놔두되, DB만 AWS RDS(관리형 DB)로 바꾸거나 톰캣을 Docker 컨테이너로만 감싸서 옮긴다. 가성비가 제일 좋다.
  3. **Repurchase (리퍼체이스, Drop & Shop)**: **"다 버리고 새로 사기"**. 자체 구축했던 사내 그룹웨어를 버리고, 그냥 잔디(Jandi)나 슬랙(Slack), 세일즈포스 같은 SaaS를 월정액 내고 쓴다.
  4. **Refactor / Re-architect (리팩터)**: **"다 뜯어고치기"**. 모놀리식 코드를 완전히 분해해서 MSA, Serverless(AWS Lambda) 기반의 클라우드 네이티브로 재설계한다. 제일 비싸고 오래 걸리지만, 성공 시 파급력은 최고다.
  5. **Retire (리타이어)**: **"폐기"**. 이사 가려다 보니 안 쓰는 시스템(서버의 10~20%)이 발견됐다. 클라우드로 안 옮기고 그냥 전원을 뽑아버린다.
  6. **Retain (리테인)**: **"보류 (안 옮김)"**. 보안 규제(망분리)가 걸려 있거나, 아직 상각이 안 끝난 삐까뻔쩍한 장비가 있다. 당분간 그냥 온프레미스에 내버려 둔다.
- **일상 비유**: 집 이사 전략. 1) 쓰던 TV 그대로 가져감(Rehost). 2) 쓰던 TV에 넷플릭스 셋톱박스만 달음(Replatform). 3) 넷플릭스 앱이 내장된 새 스마트TV를 삼(Repurchase). 4) 거실 벽을 허물고 빔프로젝터 영화관을 만듦(Refactor). 5) 고장 난 VCR은 버림(Retire). 6) 너무 무거운 피아노는 일단 옛날 집에 두고 옴(Retain).

## 연결 개념
- **Lift and Shift (리프트 앤 시프트)**: Rehost의 다른 이름. 포크레인으로 떠서(Lift) 그대로 옮긴다(Shift)는 뜻. 마이그레이션의 70%가 이 방식으로 시작된다.
- **Cloud Native (클라우드 네이티브)**: 6R 중 'Refactor' 전략을 선택했을 때 도달하게 되는 궁극의 아키텍처 형태 (MSA, 컨테이너, 데브옵스).

# 📝 【답안용】 시험 답안 템플릿

## 핵심 인사이트 (3줄 요약)
> 1. **본질**: 클라우드 마이그레이션 6R은 기업의 기존 IT 포트폴리오를 클라우드로 이전할 때, 각 시스템의 특성(비용, 시간, 중요도)에 맞춰 이행 방식을 결정하는 의사결정 프레임워크다.
> 2. **가치**: 맹목적인 '클라우드 네이티브(Refactor)' 전환이 초래하는 막대한 예산 및 시간의 낭비를 막고, Lift & Shift부터 SaaS 전환까지 하이브리드한 마이그레이션 전략을 수립할 수 있게 한다.
> 3. **판단 포인트**: 6가지 R의 명확한 영문 명칭과 정의를 나열하고, 이 중 가장 많은 비중을 차지하는 Rehost(초기 이전)와 궁극적 지향점인 Refactor(가치 극대화) 간의 2-Step 전환(단계적 고도화) 전략을 제시해야 한다.

## Ⅰ. 개요 및 필요성
- **정의**: 온프레미스 환경의 워크로드를 클라우드로 마이그레이션하기 위해 시스템을 분석하고 최적의 이행 경로를 6가지(Rehost, Replatform, Repurchase, Refactor, Retire, Retain)로 분류한 가이드라인
- **배경**: 클라우드 전환 시 빅뱅(Big Bang) 방식의 일괄 재개발은 실패 확률이 90%에 달함. 포트폴리오 디스커버리(Discovery)를 통한 선별적 접근 필요성 대두
- **필요성**: 시스템별 마이그레이션 리스크(Risk) 및 소요 시간(Lead Time) 최소화, 예산 내에서의 ROI(투자 대비 수익) 극대화, 비즈니스 연속성(BCP) 보장

## Ⅱ. 클라우드 마이그레이션 6R의 상세 분석
| 전략 명칭 | 이행 방식 (Keyword) | 특징 및 적용 사례 | 난이도 / 비용 |
|:---|:---|:---|:---|
| **1. Rehost**<br>(Lift & Shift) | **재배치** (그냥 복사) | - 소스코드/아키텍처 변경 없이 VM 이미지를 그대로 클라우드(IaaS)로 이전<br>- 사례: 온프레미스 Linux 서버 ➔ AWS EC2 이전 | 하 / 최저 |
| **2. Replatform**<br>(Lift, Tinker & Shift) | **플랫폼 변경** (일부 튜닝) | - 코드는 유지하되, 인프라의 핵심 컴포넌트만 관리형 서비스로 교체<br>- 사례: 로컬 Oracle DB ➔ AWS RDS 교체, WAS ➔ Docker화 | 중 / 중간 |
| **3. Repurchase**<br>(Drop & Shop) | **재구매** (SaaS 전환) | - 기존 라이선스(또는 자체 구축)를 폐기하고 클라우드 기반 SaaS로 갈아탐<br>- 사례: 자체 구축 HR/CRM 시스템 ➔ Salesforce, Workday 도입 | 하 / 구독료 |
| **4. Refactor**<br>(Re-architect) | **재구축** (아키텍처 변경) | - 클라우드 네이티브(Cloud Native) 기능을 극대화하기 위해 코드 전체를 재설계<br>- 사례: Monolithic Java 앱 ➔ MSA 기반 분산 구조, AWS Lambda 적용 | **최상 / 최고** |
| **5. Retire** | **폐기** (제거) | - 포트폴리오 분석 결과 트래픽이 없거나 불필요한 시스템을 이관하지 않고 종료<br>- 사례: 1년에 한 번 쓰는 레거시 통계 시스템 폐기 | 최하 / 0원 |
| **6. Retain** | **유지** (보류) | - 컴플라이언스(보안) 이슈나 최근 장비 도입으로 당장 이전하기 어려운 시스템<br>- 사례: 망분리 규제가 걸린 개인정보 처리 DB를 온프레미스에 잔류시킴 | 하 / 유지비 |

## Ⅲ. 난이도-비즈니스 가치 매트릭스 (의사결정 모델)
어떤 R을 선택할지는 'Migration Effort(노력)'와 'Business Value(가치)'의 트레이드오프다.

```text
 ▲ (Business Value: 클라우드 이점 극대화)
 │                           [ Refactor ] (Cloud Native, MSA)
 │                                ▲
 │                 [ Replatform ] ┘ (PaaS, RDS)
 │                      ▲
 │       [ Rehost ] ────┘ (IaaS, EC2)
 │         (Lift & Shift)
 │
 └───────────────────────────────────────────────────▶ (Migration Effort / Cost)
    (빠름, 저렴함)                                   (느림, 매우 비쌈)
```
- 초기 마이그레이션의 **70%는 Rehost**로 빠르게 IaaS로 옮긴 후, 향후 비즈니스 핵심 코어만 **Refactor로 진화시키는 2-Step 전략**이 가장 권장된다.

## Ⅳ. 성공적인 마이그레이션을 위한 핵심 고려사항 (CAF 프레임워크)
6R을 기술적으로만 접근하면 실패한다. AWS CAF(Cloud Adoption Framework) 관점의 검토가 필요하다.
1. **비즈니스 & 인력 (Business & People)**: 클라우드로 넘어가면 운영 조직(Ops)의 역할이 바뀐다. 기존 인프라 엔지니어들을 클라우드 아키텍트나 FinOps 담당자로 재교육(Re-skilling)해야 한다.
2. **보안 & 거버넌스 (Security & Governance)**: Rehost를 할 때 온프레미스의 방화벽 정책을 클라우드의 Security Group(보안 그룹)과 IAM 정책으로 정확히 매핑하는 아키텍처 설계가 필수적이다.

## Ⅴ. 6R의 발전 트렌드 (7R 모델로의 진화)
최근에는 VMware나 가트너를 중심으로 기존 6R에 한 가지를 더 추가하여 7R로 부르기도 한다.
- **Relocate (리로케이트)**: 온프레미스에서 'VMware'를 쓰고 있었다면, 아키텍처나 장비 변경 없이 클라우드 위의 VMware 환경(VMware Cloud on AWS 등)으로 클러스터 단위로 **'하이퍼바이저 통째로 옯기기'**. Rehost보다 훨씬 빠르고 다운타임이 0에 가깝다.

## Ⅵ. 실무 적용 및 결론
**적용 방안 및 실무 가이드:**
1. **Discovery (현황 파악) 자동화**: 수백 대의 서버를 사람이 엑셀로 조사하는 것은 불가능하다. AWS Application Discovery Service 같은 에이전트를 설치하여 서버 간의 의존성(Dependency)을 자동으로 그려낸 후 6R 전략을 매핑해야 한다.
2. **Landing Zone (랜딩 존) 선행 구축**: 6R로 시스템을 이사 오기 전에, 클라우드 환경에 네트워크, 보안, 계정 체계가 완벽히 세팅된 기초 공사(Landing Zone)가 먼저 완료되어 있어야만 대규모 이전이 가능하다.

**결론:**
- 클라우드 마이그레이션 6R은 복잡하고 거대한 레거시 시스템의 바다를 건너기 위한 **가장 현실적이고 검증된 항해 지도**이다.
- 모든 것을 한 번에 클라우드 네이티브로 바꾸려는 비현실적인 욕심을 버리고, Rehost의 '속도'와 Refactor의 '가치'를 비즈니스 중요도에 따라 현명하게 배합하는 전략이 마이그레이션 프로젝트 성패를 좌우한다.
