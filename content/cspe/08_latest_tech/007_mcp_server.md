# 📖 【암기용】 개념 완전 이해

> 목적: MCP 서버(MCP Server)를 처음 봐도 완벽히 이해하게 만든다. 시험 답안 양식이 아니라, 이해를 위한 친절한 설명이다.

## 한눈에
- **개요**: AI 에이전트가 외부 시스템과 통신할 때 사용하는 "기능 제공 서버"
- **왜 필요한가**: 개별 AI 앱이 직접 DB나 SaaS에 접속하면 보안 정책이 파편화된다. MCP 서버를 통하면 중앙에서 어떤 도구를 공개할지, 누가 쓸지 통제할 수 있다.
- **핵심 직관**: AI 전용 "키오스크". AI(Client)는 키오스크(Server)가 보여주는 메뉴(Tool/Resource) 중 하나를 골라 주문(Call)하고 결과만 받아간다.

## 깊이 이해
- **배경·문제의식**: 기업 내 다양한 레거시 시스템과 클라우드 서비스를 AI와 연결할 때, 매번 커스텀 코드를 짜는 것은 비효율적이다. 또한 AI가 직접 시스템의 모든 권한을 갖는 것은 보안상 위험(Excessive Agency)하다.
- **작동 원리**: 서버는 자신을 등록할 때 "나는 이런 도구(Tool)와 데이터(Resource)가 있어"라고 광고(Discovery)한다. 클라이언트가 특정 도구를 호출하면, 서버는 입력을 검증하고 실제 백엔드 API를 실행한 후 결과만 정제해서 돌려준다.
- **비유**: 회사의 공용 프린터 서버. 직원이 프린터 모델을 몰라도 서버에 "출력해줘"라고 요청하면 서버가 알맞은 드라이버로 실제 프린터를 동작시키는 것과 같다.
- **구체 예시**: "사내 지식베이스 MCP 서버"는 DB 쿼리를 직접 노출하는 대신 `search_documents`라는 도구만 제공하여, AI가 정해진 범위 내에서만 데이터를 읽게 제한한다.
- **흔한 오해·주의점**: MCP 서버 자체가 지능을 가진 것은 아니다. 서버는 오직 정의된 인터페이스만 제공할 뿐이며, 어떤 상황에 어떤 도구를 쓸지는 전적으로 클라이언트(LLM)의 판단에 달려 있다.

## 연결 개념
- MCP Client — 서버 기능을 소비하고 모델에 전달하는 주체
- Tool Discovery — 서버가 제공 가능한 기능 목록을 노출하는 과정
- Sandboxing — MCP 서버 실행 환경을 격리하여 보안을 강화하는 기술

# 📝 【답안용】 시험 답안 템플릿

> 목적: 시험장에서 25분에 그대로 쓰는 답안 양식. 작성방식(추상표현 금지·수치·도식·문제유형 전환)을 엄격히 지킨다.
> 핵심: MCP 서버는 AI 연동의 접점이자 신뢰 경계(Trust Boundary)이므로, 실행 통제와 감사(Audit) 관점의 아키텍처 설계가 핵심이다.

## 핵심 인사이트 (3줄 요약)

> 1. **본질**: MCP 서버는 AI 애플리케이션에 도구(Tool), 리소스(Resource), 프롬프트(Prompt)를 표준 인터페이스로 제공하는 기능 노출 계층이다.
> 2. **가치**: 연동 로직과 모델 비즈니스 로직을 분리하여 시스템 독립성을 확보하고, 서버 단위의 RBAC와 SBOM 기반 보안 통제를 가능케 한다.
> 3. **판단 포인트**: 서버 도입 시 입력 인자 스키마(JSON Schema) 검증, 실행 환경 격리(Sandboxing), 백엔드 API와의 인증 대리(Delegation) 설계가 필수적이다.

## 출제 의도 및 답안 포인트

| 출제 의도 | 반드시 짚을 핵심 | 감점 회피 포인트 |
|:---|:---|:---|
| MCP 서버 아키텍처 이해도 확인 | 3대 리소스(Tool, Resource, Prompt), Discovery 메커니즘 | 서버를 단순 API 래퍼로만 기술(보안/통제 관점 누락) |
| 실행 보안 및 리스크 통제 역량 | 입력 스키마 검증, 실행 격리, 감사로그 수집 | "연동이 간편하다"는 식의 사용자 편의성 중심 서술 |
| 엔터프라이즈 확장성 판단 | 다수 클라이언트 연결, 서버 라이프사이클 관리 | 특정 벤더(Anthropic 등) 종속 기술로 한정하여 기술 |

> 요약: MCP 서버를 통한 기능 추상화와 이를 보안 거버넌스 체계와 연결하는 논리적 흐름을 구축한다.

## Ⅰ. 개요 및 필요성

- 정의: AI 에이전트의 요청을 받아 백엔드 기능을 실행하고 결과를 반환하는 프로토콜 기반 기능 제공 서버
- 배경: AI 연동 대상 시스템 증가에 따른 관리 복잡도(N:M) 해결 및 AI의 과잉 권한 실행 방지 필요성 증대
- 필요성: 시스템별 연동 로직의 캡슐화, 도구 실행에 대한 중앙 집중식 정책 집행 및 감사(Centralized Policy Enforcement)

---

## Ⅱ. 구조 및 구성요소

```text
[MCP 서버 내부 구조도]
MCP Client <-> [ Server Interface (JSON-RPC) ]
                         |
           +-------------+-------------+
           |             |             |
     [ Tool Manager ] [ Resource Mgr ] [ Prompt Mgr ]
           |             |             |
     [  Executor  ] [ Data Adapter ] [ Template Eng ] <-> Backend Systems
```

| 구성요소 | 역할 | 주요 사양 |
|:---|:---|:---|
| Server Interface | 클라이언트와의 메시지 교환 | JSON-RPC 2.0, Capabilities 협상 |
| Tool Manager | 실행 가능한 함수 목록 관리 | 이름, 설명, JSON Schema 정의 |
| Executor | 실제 로직 실행 및 검증 | Timeout 설정, 입력 범위 체크, 롤백 로직 |
| Data Adapter | 리소스 매핑 및 정제 | URI 기반 접근, MIME 타입 변환 |
| Audit/Log | 호출 이력 및 상태 기록 | Trace ID, 사용자 정보, 실행 파라미터 |

> 요약: 인터페이스 계층을 통해 요청을 수신하고, 관리자 계층에서 리소스를 선별하여 백엔드와 연동을 수행한다.

---

## Ⅲ. 동작원리 및 흐름도

```text
[MCP 서버 실행 시퀀스]
Connect -> List Capabilities -> Call Tool Request -> Schema Validation -> Execution -> Formatting -> Return
(SSE/Stdio)   (Discovery)          (Input)           (Security)        (Backend)    (Refining)   (Context)
```

| 단계 | 처리 내용 | 검증/제어 기준 |
|:---:|:---|:---|
| 1 | 서버 등록 및 발견 | 서버가 제공하는 Tool/Resource 목록을 클라이언트에 전송 |
| 2 | 호출 요청 수신 및 검증 | 수신된 파라미터를 사전에 정의된 JSON Schema와 대조하여 유효성 검사 |
| 3 | 백엔드 기능 실행 | 격리된 환경(Container/Sandbox)에서 실제 로직 수행 및 예외 처리 |
| 4 | 결과 정제 및 반환 | 실행 결과 중 AI에게 필요한 정보만 선별하여 표준 형식으로 응답 |

> 요약: 클라이언트에게 기능을 광고한 후, 요청 시마다 스키마 및 보안 검증을 거쳐 백엔드 기능을 안전하게 대행한다.

---

## Ⅳ. 특징

| 구분 | MCP 서버 방식 | 직접 API 호출 방식 | 기술사 판단 포인트 |
|:---|:---|:---|:---|
| 연동 규격 | 표준화 (JSON-RPC) | 개별 규격 (REST, gRPC) | 연동 시간 50% 이상 단축 가능 |
| 보안 경계 | 서버 단위 통제 가능 | 앱별 개별 통제 필요 | 보안 사고 시 서버 단위 즉시 차단 |
| 유지보수 | 서버 업데이트로 전체 적용 | 모든 앱 코드 수정 필요 | 도구 추가/변경의 유연성 확보 |
| 모델 최적화 | 도구 설명(Hint) 중앙 관리 | 앱 개발자마다 상이 | 모델의 도구 선택 정확도(Hit Rate) 향상 |

> 요약: MCP 서버는 연동의 표준화와 보안의 중앙 집중화를 통해 대규모 AI 에이전트 운영 효율을 극대화한다.

## Ⅴ. 심화 비교 및 적용 판단

| 비교 축 | 로컬 서버 (Stdio) | 원격 서버 (SSE) | 선택 기준 |
|:---|:---|:---|:---|
| 구동 환경 | 동일 머신 내 프로세스 | 별도 호스트/컨테이너 | 서비스 가용성 및 확장 요건 |
| 통신 방식 | Pipe (stdin/stdout) | HTTP/HTTPS (SSE) | 네트워크 지연 및 암호화 필요성 |
| 주 용도 | 개인용 도구, IDE 에이전트 | 전사 공용 서비스, SaaS 연동 | 동시 접속 사용자 수 및 공유 범위 |

> 요약: 로컬 환경의 민첩성이 필요할 땐 Stdio를, 전사적 공유와 안정적 운영이 필요할 땐 SSE 방식을 채택한다.

| 리스크 | 원인 | 대응 방안 | 확인 지표 |
|:---|:---|:---|:---|
| 실행 환경 오염 | 악성 입력에 의한 RCE 등 | 서버 실행 환경 격리(Docker/gVisor), 최소 권한 원칙 | Sandbox 탈출 시도 감지 건수 |
| 입력 스키마 우회 | 느슨한 스키마 정의 | 정규식(Regex), enum, 범위 제약 엄격화 및 재검증 | 스키마 오류(400 Bad Request) 비율 |
| 가용성 저하 | 특정 도구의 자원 독점 | 도구별 Timeout(예: 30s), Rate Limiting 적용 | 평균 응답 시간 및 에러율(SLI) |

> 요약: 격리 실행, 엄격한 검증, 자원 할당 제어를 통해 MCP 서버의 안정성과 보안성을 확보한다.

| 점검 항목 | 목표 기준 | 측정 방법 |
|:---|:---|:---|
| 처리량 (Throughput) | 서버당 500 TPS 이상 (최적화 시) | 부하 테스트 도구 (Locust, JMeter) |
| 신뢰성 (Reliability) | 가동률 99.9% 이상, 패치 지연 24h 이내 | 모니터링 시스템, SBOM 스캔 로그 |
| 보안 (Security) | 인증되지 않은 호출 시도 0건 | 접근 제어 로그(ACL Audit) |

> 요약: 처리량, 가동률, 무단 접근 차단 여부를 통해 서버의 운영 건전성을 정량적으로 평가한다.

## Ⅵ. 실무 적용 및 결론

**적용 방안 3개:**
1. 보안 강화: 서버 실행 단에 gVisor 등 경량 샌드박스를 적용하여 호스트 시스템과의 커널 격리 및 자원 제한 실시
2. 도구 그룹화: 업무 성격(인사, 재무, IT)에 따라 MCP 서버를 분리 운영하여 권한 오남용 방지 및 관리 효율 증대
3. 지능형 프롬프팅: 서버 측에서 `Prompts` 리소스를 통해 모델에게 최적의 도구 사용법(Few-shot)을 동적으로 제공

**결론 (2줄):**
- 기술사 판단: MCP 서버는 단순한 게이트웨이가 아닌 AI의 "손과 발"을 정의하는 규격이며, 서버의 신뢰성 검증(Certification)이 도입의 전제조건이다.
- 향후 방향: 서버 간 연쇄 호출(Chaining)과 서버리스(Serverless) 기반의 동적 MCP 서버 할당 기술이 핵심 트렌드가 될 전망이다.
