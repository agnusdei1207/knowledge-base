# 📖 【암기용】 개념 완전 이해

## 한눈에
- **개요**: **MCP 서버**(MCP Server)는 MCP(006 참조)의 세 계층 중 도구·리소스·프롬프트를 규격대로 **노출(제공)하는 쪽**의 프로세스이다.
- **왜 필요한가**: LLM 앱마다 DB·SaaS에 직접 붙으면 연동·권한이 파편화된다. 서버가 "무엇을 어떻게 공개할지"를 한곳에 모으면, 서버 1개를 여러 호스트가 재사용하고 신뢰 경계도 서버 단위로 그을 수 있다.
- **핵심 직관**: USB-C 주변장치. 본체(호스트)가 포트(클라이언트)로 꽂으면, 주변장치(서버)가 "내가 할 수 있는 일(capability)"을 광고하고 요청받은 기능만 실행해 결과를 돌려준다.

## 핵심 용어 정리 (내부에 등장하는 것들)
답안 본문에 등장하는 용어를 처음 보는 사람도 이해하도록 비유와 함께 먼저 정리한다.

| 용어/표기 | 의미 | 비유·예 |
|:---|:---|:---|
| MCP 서버(핵심) | 도구·리소스·프롬프트를 규격대로 노출하는 제공자 프로세스 | 꽂아 쓰는 "주변장치" |
| capability 등록 | 연결 초기에 "내가 제공하는 기능"을 선언·협상 | 메뉴판을 펼쳐 보임 |
| 3대 프리미티브 | 툴(실행)·리소스(읽기)·프롬프트(템플릿) | 기능 버튼/자료/서식 |
| transport(전송) | 메시지를 나르는 통로 (stdio 또는 SSE·HTTP) | 유선 케이블 / 무선 |
| stdio | 같은 머신에서 표준입출력으로 붙는 로컬 전송 | 본체에 직결된 케이블 |
| SSE·HTTP | 별도 호스트와 스트리밍으로 붙는 원격 전송 | 네트워크 연결 |
| 신뢰 경계(Trust Boundary) | 외부 코드·데이터 접근이 시작되는 보안 분기선 | 출입 검문소 |
| JSON Schema | 입력 인자의 타입·범위를 강제하는 규격 | 서식의 빈칸 규칙 |
| Sandbox | 실행 환경을 격리해 호스트 피해를 막는 기술 | 방화 격벽 |
| Excessive Agency | AI가 필요 이상 넓은 권한을 갖는 위험 | 만능 마스터키 |

## 깊이 이해
- **배경·문제의식**: MCP 전체 구조·N×M 문제는 006에서 다룬다. 서버 관점의 핵심 문제는 "외부 시스템 접근권을 어디까지, 누구에게 열 것인가"이다. 서버는 백엔드(DB·API)와 LLM 사이에 놓여, 백엔드의 넓은 권한을 좁은 인터페이스로 감싸는 역할을 한다.
- **작동 원리(어떻게+왜)**: 서버는 연결 초기 핸드셰이크에서 자신이 지원하는 capability(툴·리소스·프롬프트 제공 여부)를 선언한다. 클라이언트가 툴을 호출하면 ① 입력을 JSON Schema로 검증하고 ② 격리 환경에서 실제 백엔드를 실행한 뒤 ③ AI에 필요한 결과만 정제해 반환한다. 규격을 서버가 소유하므로, 도구가 바뀌어도 서버만 갱신하면 모든 호스트에 전파된다.
- **비유**: 회사 공용 프린터 서버. 직원(호스트)은 프린터 모델을 몰라도 "출력해줘"만 보내면, 서버가 알맞은 드라이버로 실제 장치를 돌린다. 세부 권한·드라이버는 서버가 숨긴다.
- **구체 예시(실제 사례)**: 사내 지식베이스 서버는 DB 쿼리를 직접 노출하는 대신 `search_documents(query)` 툴 하나만 공개해, LLM이 정해진 범위만 읽게 제한한다. 파일시스템·GitHub·Slack용 공식 서버가 대표적이다.
- **흔한 오해·주의점**: 서버 자체는 지능이 없다. 어떤 도구를 언제 쓸지는 클라이언트(LLM)가 판단하고, 서버는 정의된 인터페이스만 실행한다. 또한 서버는 외부 접근의 신뢰 경계이므로, 툴 설명에 숨긴 지시·과잉 권한·느슨한 스키마가 그대로 위협이 된다.

## 연결 개념
- MCP(006) — 서버가 속한 전체 프로토콜·아키텍처
- MCP 클라이언트(008) — 서버와 1:1로 연결해 기능을 소비하는 상대
- MCP 리소스(009)·툴·프롬프트 — 서버가 노출하는 3대 프리미티브

# 📝 【답안용】 시험 답안 템플릿

## 핵심 인사이트 (3줄 요약)

> 1. **본질**: MCP 서버는 도구·리소스·프롬프트를 표준 규격으로 노출하는 제공자 계층이자 외부 접근의 신뢰 경계임.
> 2. **가치**: 백엔드 권한을 좁은 인터페이스로 캡슐화해 서버 1개를 다수 호스트가 재사용하고 보안을 서버 단위로 통제함.
> 3. **판단 포인트**: 입력 스키마 검증·실행 격리·최소 권한·감사로그를 갖춘 서버만 도입해야 함.

## 출제 의도 및 답안 포인트

| 출제 의도 | 반드시 짚을 핵심 | 감점 회피 포인트 |
|:---|:---|:---|
| 서버의 제공자 역할 이해 | capability 등록, 3대 프리미티브 노출, transport | 단순 API 래퍼로 축소 기술 시 감점 |
| 실행 보안 통제 역량 | JSON Schema 검증, Sandbox 격리, 최소 권한 | 연동 편의성 위주 서술 시 감점 |
| 신뢰 경계 인식 | 툴 설명 인젝션·과잉 권한 대응, 감사로그 | 신뢰 경계 관점 누락 시 감점 |

> 요약: 서버가 무엇을 어떻게 노출하고, 그 접근을 어떤 보안 경계로 통제하는지 확인하려는 문제임.

---

## Ⅰ. 개요 및 필요성

- 개요: 도구·리소스·프롬프트를 MCP 규격대로 노출·실행하고 결과를 반환하는 제공자 프로세스임
- 배경: LLM 앱마다 백엔드에 직접 연동하면 권한·규격이 파편화되고 과잉 권한 위험이 커짐 (전체 배경은 006 참조)
- 필요성: 연동 로직을 서버에 캡슐화해 재사용하고, 접근 통제·감사를 서버 단위로 중앙 집행해야 함
- 위치: 호스트-클라이언트-서버 3계층(006) 중 기능을 제공하고 백엔드에 접하는 최말단 계층임

---

## Ⅱ. 구조 및 구성요소

- 선형 구조도

```text
클라이언트 -> 서버 인터페이스(JSON-RPC, capability 협상)
  -> 툴 관리자 / 리소스 관리자 / 프롬프트 관리자
    -> 실행기·데이터 어댑터(스키마 검증 -> 격리 실행) -> 백엔드(DB·API·파일)
  -> 감사로그(호출 이력·파라미터 기록)
```

| 구성요소 | 역할 | 특이사항 |
|:---|:---|:---|
| 서버 인터페이스 | 클라이언트와 메시지 교환 | JSON-RPC 2.0, capability 협상 |
| 툴 관리자 | 실행 가능 함수 목록 관리 | 이름·설명·JSON Schema 정의 |
| 리소스/프롬프트 관리자 | 읽기 데이터·템플릿 노출 | URI 접근, MIME 변환 |
| 실행기 | 실제 로직 실행·검증 | Timeout, 입력 범위 체크, 격리 |
| 감사로그 | 호출 이력·상태 기록 | Trace ID, 사용자·파라미터 |

> 요약: 인터페이스가 요청을 받고, 관리자·실행기가 스키마 검증 후 백엔드를 격리 대행하며 감사로그를 남김.

---

## Ⅲ. 동작원리 및 흐름도

- 선형 흐름도

```text
연결(stdio/SSE) -> capability 광고 -> 툴 호출 수신 -> 스키마 검증 -> 격리 실행 -> 결과 정제 -> 반환
```

1. 등록·발견: 서버가 제공하는 툴·리소스·프롬프트 목록을 클라이언트에 광고함
2. 검증: 클라이언트가 보낸 인자를 사전 정의된 JSON Schema와 대조해 유효성을 확인함
3. 실행: 서버가 격리 환경(Container·gVisor)에서 백엔드 로직을 수행하고 예외를 처리함
4. 반환: 서버가 결과 중 AI에 필요한 정보만 선별해 표준 형식으로 응답함

> 요약: 서버가 기능을 광고한 뒤, 호출마다 스키마·보안 검증을 거쳐 백엔드를 안전하게 대행함.

---

## Ⅳ. 특징

- 제공자 역할: 서버는 판단하지 않고, 클라이언트(LLM)가 고른 기능만 실행함
- capability 소유: 도구 정의·설명·스키마를 서버가 중앙 관리해 도구 변경을 서버 갱신만으로 전파함
- 신뢰 경계: 외부 백엔드 접근이 서버에서 시작되므로 출처 검증·최소 권한이 필수축이 됨
- 전송 이중성: 로컬 stdio와 원격 SSE·HTTP를 동일 규격으로 지원함
- 격리 실행: 악성 입력·RCE에 대비해 Sandbox와 Timeout으로 실행을 봉쇄함

---

## Ⅴ. 심화 비교 및 적용 판단

- 같은 "서버"라도 범용 REST API 서버와 대비하면 MCP 서버의 성격이 드러남

| 구분 | MCP 서버 | REST API 서버 |
|:---|:---|:---|
| 소비 주체 | LLM(비결정적 호출) | 사람·앱(결정적 호출) |
| 기능 발견 | capability 협상·동적 발견 | 문서·OpenAPI 사전 하드코딩 |
| 인터페이스 | 툴·리소스·프롬프트 3종 프리미티브 | 엔드포인트·메서드 |
| 입력 신뢰 | 모델 생성 인자라 스키마 재검증 필수 | 클라이언트 코드가 형식 보장 |
| 결과 형태 | 모델용으로 정제·요약해 반환 | 원본 JSON 그대로 반환 |

> 요약: 소비자가 LLM이라 발견은 동적이고 입력은 재검증해야 하며 결과는 모델용으로 정제함이 REST 서버와의 차이임.

- 로컬(stdio) vs 원격(SSE) 선택
  - stdio — 같은 머신 프로세스, 개인 도구·IDE 에이전트, 지연 최소
  - SSE·HTTP — 별도 호스트, 전사 공용·SaaS 연동, 암호화·동시접속 필요 시

- 주요 리스크와 대응(불릿)
  - 실행 환경 오염 — 악성 입력에 의한 RCE가 원인 → Docker·gVisor 격리·최소 권한
  - 스키마 우회 — 느슨한 스키마 정의가 원인 → enum·범위·정규식 제약 강화·재검증
  - 가용성 저하 — 특정 툴의 자원 독점이 원인 → 툴별 Timeout(예: 30s)·Rate Limiting

- 운영 지표(불릿)
  - 처리량 — 서버당 500 TPS 이상 목표 — 부하 테스트(Locust·JMeter)
  - 무단 호출 — 0건 목표 — 접근제어 로그(ACL Audit)
  - 패치 지연 — 24h 이내 목표 — SBOM 스캔 로그

---

## Ⅵ. 실무 적용 및 결론

- 적용 방안
  1. 실행 격리: 서버 실행단에 gVisor 등 경량 샌드박스를 적용해 호스트 커널과 분리하고 자원을 제한
  2. 도구 분리 운영: 업무 도메인(인사·재무·IT)별로 서버를 나눠 권한 오남용을 차단하고 관리 효율을 확보
  3. 감사 표준화: 모든 툴 호출을 Trace ID·파라미터와 함께 감사로그로 남겨 신뢰 경계 추적성 확보
- 결론
  - 기술사 판단: 전사 공용·민감 백엔드는 SSE 서버로 격리·인증하고, 개인 도구는 stdio 서버로 경량 운영함
  - 향후 방향: 서버 레지스트리·서버 간 체이닝·서버리스 동적 할당과 결합해 개방 도구 생태계로 정착됨
