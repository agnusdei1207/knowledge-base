# 📖 【암기용】 개념 완전 이해

> 목적: SCI를 소프트웨어 기능 단위당 탄소 배출량을 계산하는 표준 지표로 이해하게 만든다.

## 한눈에
- **개요**: 소프트웨어가 기능 1단위를 처리할 때 배출한 탄소량을 나타내는 지표
- **왜 필요한가**: 전체 서버 배출량만 보면 사용자 요청, 학습 job, 거래 1건의 배출량이 줄었는지 판단하기 어렵다.
- **핵심 직관**: 자동차 연료 총량보다 km당 연비를 봐야 차량 간 비교가 가능한 것과 같다.

## 깊이 이해
- **배경·문제의식**: 서비스 규모가 커지면 총배출량은 사용량 증가의 영향을 받으므로, 설계 개선 효과를 보기 위해 기능 단위 기준이 필요하다.
- **작동 원리**: SCI는 일반적으로 `((E * I) + M) / R` 구조로 계산한다. E는 에너지, I는 전력망 탄소집약도, M은 내재탄소, R은 기능 단위이다.
- **비유**: 카페가 하루 전기 사용량만 보는 것이 아니라 커피 한 잔당 전기·원두·컵 영향을 계산하는 방식이다.
- **구체 예시**: 추론 API 100만 건에 운영 배출 80kgCO2e와 내재탄소 배분 20kgCO2e가 있으면 요청 1건 SCI는 0.1gCO2e/request이다.
- **흔한 오해·주의점**: SCI는 조직 전체 탄소회계 대체 지표가 아니다. 특정 소프트웨어 경계와 기능 단위 안에서 비교하는 운영 지표다.

## 연결 개념
- Green Software — SCI를 개선 목표로 사용하는 소프트웨어 공학
- Carbon-aware Scheduling — E*I 중 I를 낮추는 시간·지역 선택
- Embodied Carbon — M 항목으로 반영되는 하드웨어 생산·폐기 배출량

# 📝 【답안용】 시험 답안 템플릿

> 목적: 시험장에서 25분에 그대로 쓰는 답안 양식.
> 핵심: SCI는 소프트웨어 경계 안의 운영 배출량과 내재탄소를 기능 단위로 나누어 비교 가능한 탄소 지표로 만든 표준임.

## 핵심 인사이트 (3줄 요약)

> 1. **본질**: Software Carbon Intensity는 `((E * I) + M) / R`로 기능 단위당 탄소 배출량을 산정하는 지표임.
> 2. **가치**: 서비스 규모 차이를 보정해 배포, 아키텍처, region, 모델 변경의 탄소 영향을 비교함.
> 3. **판단 포인트**: 측정 경계, 기능 단위 R, 전력망 탄소집약도 I, 내재탄소 M의 산정 근거가 핵심임.

## 출제 의도 및 답안 포인트

| 측정 설계 판단 확인 | 시스템 경계, 기능 단위, 데이터 출처 | 임의 수치 산정 |
| 개선 전략 연결 확인 | 에너지 절감, 저탄소 시간, 내재탄소 배분 | 코드 튜닝만 제시 |

> 요약: 이 문제는 SCI 산식보다 경계와 기능 단위를 어떻게 잡는지가 채점 포인트다.

## Ⅰ. 개요 및 필요성

- 개요: 기능 단위 탄소 지표
- 배경: 총배출량은 사용량 증가와 설계 개선 효과가 섞여 비교 기준으로 부족함.
- 필요성: 배포 전후, region 변경, 모델 경량화 효과를 gCO2e/request 같은 기능 단위로 검증해야 함.

---

## Ⅱ. 구조 및 구성요소

```text
Energy(E) * Carbon Intensity(I) -> Operational Emissions
Embodied Carbon(M) -> Allocated Emissions
Operational + Embodied -> / Functional Unit(R) -> SCI
```

| 구성요소 | 역할 | 특이사항 |
|:---|:---|:---|
| E | 소프트웨어 실행 에너지 | kWh |
| I | 전력망 탄소집약도 | gCO2e/kWh |
| M | 하드웨어 내재탄소 배분 | manufacturing, disposal |
| R | 기능 단위 | request, transaction, job |

> 요약: SCI는 운영 배출량과 내재탄소를 더한 뒤 기능 단위로 나눠 비교 가능한 값으로 만든다.

---

## Ⅲ. 동작원리 및 흐름도

```text
측정 경계 정의 -> E 수집 -> I 매핑 -> M 배분
-> R 집계 -> SCI 계산 -> 변경 전후 비교
```

| 단계 | 처리 내용 | 검증 기준 |
|:---:|:---|:---|
| 1 | 서비스·기간·포함 자원을 정의함 | boundary document |
| 2 | 클라우드·서버 자원 사용량을 kWh로 환산함 | energy model |
| 3 | 지역·시간별 탄소집약도와 내재탄소를 반영함 | data source |
| 4 | 기능 단위로 나누고 추세를 비교함 | gCO2e/R |

> 요약: SCI 계산은 경계 정의, 데이터 수집, 배출량 환산, 기능 단위 정규화 순서로 수행된다.

## Ⅳ. 특징

| 구분 | 총탄소배출량 | SCI | 판단 기준 |
|:---|:---|:---|:---|
| 단위 | kgCO2e/기간 | gCO2e/기능 단위 | 개선 효과 비교 |
| 사용량 영향 | 규모 증가 반영 | 기능 단위로 보정 | 사용자 증가 상황 |
| 의사결정 | 조직 보고 | 설계·배포 선택 | 엔지니어링 적용 |
| 한계 | 기능 단위 비교 어려움 | 경계 설정 민감 | 산정 근거 필요 |

> 요약: SCI는 총배출량을 대체하지 않고 소프트웨어 설계 변경 효과를 기능 단위로 평가하는 보조 지표다.

## Ⅵ. 실무 적용 및 결론

**적용 방안 3개:**
1. API 요청, 배치 job, AI 추론 1회처럼 업무 의미가 있는 R을 정하고 서비스 경계와 기간을 문서화함.
2. 클라우드 자원 사용량, region별 carbon intensity, 하드웨어 내재탄소 배분 근거를 수집해 SCI 계산 파이프라인을 구성함.
3. 배포 전후 SCI, 총 gCO2e, p95 지연을 함께 비교해 탄소 감축과 SLA 충돌 여부를 판단함.

**결론 (2줄):**
- 기술사 판단: SCI는 대규모 클라우드·AI 서비스의 설계 변경 평가에 적합하며, 단일 수치만으로 조직 탄소 성과를 단정하지 않음.
- 향후 방향: SCI는 ISO/IEC 21031:2024 기반 측정 체계와 결합해 GreenOps와 지속가능 SW 품질 지표로 확산됨.
