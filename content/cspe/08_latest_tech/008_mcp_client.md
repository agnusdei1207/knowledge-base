# 📖 【암기용】 개념 완전 이해

## 한눈에
- **개요**: **MCP 클라이언트**(MCP Client)는 호스트(LLM 앱) 안에서 서버 1개와 **1:1로 연결**해 프로토콜을 협상하고 요청을 중계하는 커넥터이다.
- **왜 필요한가**: 모델은 스스로 외부 DB·인터넷에 붙지 못한다. 클라이언트가 서버에 "어떤 기능이 있는지" 묻고, 모델이 고른 도구를 대신 실행해 결과를 컨텍스트로 되먹인다.
- **핵심 직관**: 본체의 "포트 하나". 노트북 본체(호스트)에 여러 포트(클라이언트)가 있고, 포트마다 주변장치(서버) 하나가 물린다. 서버가 여럿이면 클라이언트도 여럿이다.

## 핵심 용어 정리 (내부에 등장하는 것들)
답안 본문에 등장하는 용어를 처음 보는 사람도 이해하도록 비유와 함께 먼저 정리한다.

| 용어/표기 | 의미 | 비유·예 |
|:---|:---|:---|
| MCP 클라이언트(핵심) | 호스트 안에서 서버 1개와 1:1 연결·중계하는 커넥터 | 본체의 "포트 하나" |
| 호스트(Host) | 사용자를 마주하는 LLM 앱, 여러 클라이언트를 조율 | 노트북 "본체" |
| 1:1 연결 | 클라이언트 1개가 서버 1개에만 대응하는 관계 | 포트-장치 1대1 |
| 프로토콜 협상 | 연결 초기 지원 기능·버전을 교환·합의 | 첫 만남 "가능한 일 확인" |
| Discovery | 서버가 노출한 툴·리소스 목록을 조회 | 메뉴판 받아오기 |
| Tool Call | 모델이 "이 도구가 필요"라며 실행을 요청하는 행위 | 주문서 전달 |
| 요청 중계 | 모델↔서버 사이 메시지를 변환·전달 | 통역·심부름 |
| Context Window | 모델이 한 번에 읽는 입력 공간, 결과 주입 대상 | 사장님 "책상 위" |
| HITL(User-in-the-loop) | 고위험 실행 전 사용자 승인 절차 | 결재 사인 |
| Aggregator | 여러 서버 연결을 한 호스트에서 묶는 방식 | 멀티포트 허브 |

## 깊이 이해
- **배경·문제의식**: MCP 전체 목적·N×M 해소는 006에서 다룬다. 클라이언트 관점의 문제는 "모델의 추론(무엇을 할지)과 서버의 실행(실제로 함)을 어떻게 안전하게 잇는가"이다. 예전엔 앱마다 도구 실행 코드를 하드코딩해, 모델·도구가 바뀔 때마다 앱을 고쳐야 했다.
- **작동 원리(어떻게+왜)**: 클라이언트는 ① 서버에 연결해 capability를 협상하고 ② 목록을 받아온다(List). 사용자 질문에 모델이 Tool Call로 응답하면 ③ 클라이언트가 서버에 실행을 요청하고 ④ 결과를 모델 컨텍스트에 되먹여 최종 답을 만든다. 즉 모델↔서버 메시지 루프의 관리자이다.
- **비유**: 웹 브라우저. 브라우저(클라이언트)가 웹 서버에 접속해 HTML을 받아 사용자에게 보여주듯, MCP 클라이언트는 서버에서 도구·데이터를 받아 모델에게 보여준다.
- **구체 예시(실제 사례)**: Claude Desktop이 대표 클라이언트이다. 사용자가 설치한 로컬 서버들과 통신해 파일 수정·터미널 실행 기능을 Claude 모델에 공급한다. LangChain 등 프레임워크도 클라이언트 역할을 한다.
- **흔한 오해·주의점**: 클라이언트가 도구를 마음대로 실행하는 게 아니다. 모델이 "실행 필요"로 판단할 때만 대행하며, 고위험 도구는 사용자 승인(HITL)을 거친다. 또한 서버 결과가 길면 토큰이 폭증하므로 요약·청킹으로 컨텍스트를 관리해야 한다.

## 연결 개념
- MCP(006) — 클라이언트가 속한 전체 프로토콜·아키텍처
- MCP 서버(007) — 클라이언트가 1:1로 연결해 기능을 소비하는 상대
- Tool Call·Context Window — 모델의 실행 요청과 결과 주입 공간

# 📝 【답안용】 시험 답안 템플릿

## 핵심 인사이트 (3줄 요약)

> 1. **본질**: MCP 클라이언트는 호스트 안에서 서버와 1:1 연결·프로토콜 협상·요청 중계를 맡는 연동 주체임.
> 2. **가치**: 모델의 추론과 서버의 실행을 표준 루프로 이어, 도구 추가를 앱 수정 없이 흡수하고 사용자 통제를 표준화함.
> 3. **판단 포인트**: 다중 서버 연결·토큰 최적화·고위험 도구 승인(HITL) 설계가 필수적임.

## 출제 의도 및 답안 포인트

| 출제 의도 | 반드시 짚을 핵심 | 감점 회피 포인트 |
|:---|:---|:---|
| 중계 프로세스 이해 | Discovery -> 추론 -> 실행 -> 통합 루프, 1:1 연결 | 단순 UI 계층으로 축소 기술 시 감점 |
| 토큰·비용 통제 역량 | 결과 요약, 토큰 관리, 컨텍스트 주입 전략 | 서버 기능만 나열·클라이언트 최적화 부재 시 감점 |
| 사용자 보안·세션 | 권한 필터링, HITL 승인 | 모든 도구 무조건 실행 강조 시 감점 |

> 요약: 모델 추론과 서버 실행을 유기적으로 결합하고 사용자 통제권을 확보하는 중계 역할을 확인하려는 문제임.

---

## Ⅰ. 개요 및 필요성

- 개요: 호스트 안에서 서버와 1:1 연결해 도구·자원을 모델 추론에 통합하는 중계 인터페이스 모듈임
- 배경: 모델별 독자 Tool Use 규격을 탈피하고 다종 외부 소스를 동적으로 결합해야 하는 환경이 도래함 (전체 배경은 006 참조)
- 필요성: 연동 인터페이스 표준화로 생산성을 높이고, 세션 기반 도구 가시성·실행 승인을 통제해야 함
- 위치: 호스트-클라이언트-서버 3계층(006) 중 모델과 서버를 잇는 중계 계층임

---

## Ⅱ. 구조 및 구성요소

- 선형 구조도

```text
LLM(추론 엔진) -> MCP 클라이언트 코어 -> 전송 관리자 -> MCP 서버들
  클라이언트 코어 분기: Discovery / 툴 핸들러 / 컨텍스트 관리자 / 승인(HITL)
  전송 관리자 분기: stdio / SSE
```

| 구성요소 | 역할 | 특이사항 |
|:---|:---|:---|
| Discovery | 서버 기능 목록 수집·관리 | List Tools/Resources, 캐싱 |
| 툴 핸들러 | 모델 호출 요청 처리·중계 | 인자 스키마 확인, 실행 요청 |
| 컨텍스트 관리자 | 결과의 모델 주입 최적화 | 요약, 토큰 제한, 히스토리 |
| 전송 관리자 | 서버 연결 세션 유지 | stdio 프로세스·SSE HTTP |
| 승인(HITL) | 실행 최종 승인 | User-in-the-loop, 결과 시각화 |

> 요약: 모델 추론을 서버 메시지로, 서버 결과를 모델 컨텍스트로 변환하는 이중 중계 구조를 가짐.

---

## Ⅲ. 동작원리 및 흐름도

- 선형 흐름도

```text
연결·협상 -> 목록 스캔 -> 사용자 질문 -> 모델 추론(Tool Call) -> 서버 실행 -> 결과 통합 -> 최종 응답
```

1. 연결·스캔: 클라이언트가 서버와 연결·협상 후 모든 서버의 툴·리소스 명세를 획득함
2. 추론·선택: 사용자 질문에 대해 모델이 필요한 도구와 인자를 결정함
3. 실행 중계: 클라이언트가 인자를 서버에 전송하되, 고위험 도구는 사용자 승인을 대기함
4. 통합: 클라이언트가 실행 결과를 모델에 재주입해 사용자 답변을 생성하게 함

> 요약: 연결-스캔-추론-실행-통합 루프를 돌며 모델과 서버 사이 메시지를 클라이언트가 관리함.

---

## Ⅳ. 특징

- 1:1 연결: 클라이언트 1개가 서버 1개를 담당하고, 호스트가 여러 클라이언트를 조율함
- 중계 이중성: 모델 언어를 서버 메시지로, 서버 결과를 모델 컨텍스트로 양방향 변환함
- 모델 독립: 표준 규격이라 여러 LLM에 공통 적용되어 멀티 모델 전략이 쉬워짐
- 사용자 통제: 실행 전 승인(HITL)을 표준 단계로 두어 무단 실행을 차단함
- 토큰 관리: 서버 결과를 요약·청킹해 컨텍스트 오버플로우와 비용을 제어함

---

## Ⅴ. 심화 비교 및 적용 판단

- 같은 "클라이언트"라도 일반 API 클라이언트와 대비하면 성격이 드러남

| 구분 | MCP 클라이언트 | 일반 API 클라이언트 |
|:---|:---|:---|
| 호출 결정 | 모델 추론이 도구·인자 결정 | 개발자 코드가 사전 결정 |
| 연결 수명 | 세션 내내 유지되는 1:1 연결 | 요청 단위 무상태 호출 |
| 기능 발견 | 런타임 List로 동적 발견 | 문서 보고 코드에 고정 |
| 실행 통제 | HITL 사용자 승인 개입 | 자동 실행(사람 개입 없음) |
| 결과 처리 | 요약·주입해 모델 컨텍스트로 | 앱 로직이 파싱·사용 |

> 요약: 호출을 모델이 결정하고 연결을 세션으로 유지하며 실행에 사용자를 개입시킴이 일반 API 클라이언트와의 차이임.

- 데스크톱 vs 프레임워크 클라이언트 선택
  - 데스크톱(Claude 등) — 일반 사용자, 설정 기반 간편 연결, 개인 생산성
  - 프레임워크(LangChain 등) — 개발자, 코드 기반 정밀 제어, 전사 에이전트 구축

- 주요 리스크와 대응(불릿)
  - 컨텍스트 오버플로우 — 서버 결과가 길어 토큰 초과가 원인 → 요약·청킹 적용
  - 무단 도구 실행 — 모델 환각 호출이 원인 → 고위험 도구 명시적 승인 필수
  - 서버 연결 지연 — 다수 서버 동시 연결이 원인 → 비동기 호출·Circuit Breaker

- 운영 지표(불릿)
  - 도구 선택 정확도 — 95% 이상 목표 — Replay 테스트·Human Eval
  - 무승인 고위험 실행 — 0건 목표 — 보안 감사 로그
  - 컨텍스트 내 결과 비중 — 40% 이내 목표 — 토큰 분석·비용 대시보드

---

## Ⅵ. 실무 적용 및 결론

- 적용 방안
  1. 하이브리드 연결: 민감 로컬 파일은 stdio 서버로, 전사 DB는 SSE 서버로 붙여 클라이언트에서 통합 관리
  2. 조건부 승인: 쓰기(Write) 권한 도구 호출 시에만 확인 버튼을 노출하는 HITL 워크플로우 적용
  3. 동적 컨텍스트 최적화: 서버 응답이 2,000토큰 초과 시 자동 요약해 모델에 전달하는 필터 구현
- 결론
  - 기술사 판단: 개인 도구는 완제품 데스크톱 클라이언트를, 복합 워크플로우는 프레임워크 커스텀 클라이언트를 적용함
  - 향후 방향: 다중 에이전트가 리소스를 공유·협업하는 에이전트 간 통신(A2A) 클라이언트로 진화함
