# 📖 【암기용】 개념 완전 이해

## 한눈에
- **개요**: **MCP 클라이언트**는 AI 애플리케이션(Host) 내부에서 MCP 서버와 통신하며, 서버가 제공하는 리소스와 도구를 모델(LLM)이 사용할 수 있도록 중계하는 **연결 엔진**이다.
- **필요성**: 모델은 스스로 인터넷을 하거나 파일을 읽는 능력이 없다. 클라이언트가 서버로부터 도구 목록을 가져와 모델에게 "이런 연장들이 있어"라고 알려주고, 모델이 연장을 고르면 대신 실행해주는 역할을 한다.
- **핵심 직관**: **"AI 모델의 손발을 관리하는 컨트롤러"**. 모델의 의도(Intent)를 서버의 규격(Protocol)에 맞춰 전달하고 결과를 받아 모델에게 다시 먹여주는 주체다.

## 깊이 이해
- **배경 (Standardizing the Consumption Layer)**: 다양한 모델(GPT, Claude, Llama)이 각기 다른 환경에서 동작할 때, 동일한 도구 세트를 사용하려면 모델 쪽에서도 공통된 통신 계층이 필요하다. MCP 클라이언트는 이 소비(Consumption) 방식을 표준화한다.
- **작동 원리 (The Client Logic)**:
    - **Connection Management**: 하나 이상의 MCP 서버에 연결하고 상태를 유지.
    - **Capability Negotiation**: 서버가 어떤 기능(Resource, Tool 등)을 지원하는지 확인.
    - **Orchestration**: 모델의 응답에서 도구 호출 요청을 감지하면 서버에 실행 명령을 내리고 결과를 모델 컨텍스트에 삽입.
- **비유**: 여행객(AI 모델)이 묵는 호텔의 **컨시어지(MCP 클라이언트)**와 같다. 여행객이 "주변 맛집을 알고 싶어"라고 하면 컨시어지가 외부 업체(MCP 서버)에 물어 정보를 가져다주고, 예약을 원하면 대신 처리해주는 것과 같다.
- **구체 예시**: `Claude Desktop` 앱 자체가 대표적인 MCP 클라이언트다. 설정 파일에 MCP 서버 주소만 적으면 앱 내의 클라이언트가 자동으로 연결을 수행한다.
- **주의점**: 클라이언트는 서버의 기능을 무조건 신뢰하지 말고, 사용자에게 실행 여부를 묻거나(User Approval) 결과물의 안전성을 검사하는 **보안 중계자** 역할을 병행해야 한다.

## 연결 개념
- **MCP Host**: 클라이언트를 포함하고 있는 최종 애플리케이션 (예: IDE, 챗봇 앱).
- **MCP Server (007)**: 클라이언트가 연결하여 서비스를 요청하는 대상.
- **Resource/Tool Discovery**: 클라이언트가 서버에 어떤 기능이 있는지 묻는 과정.

# 📝 【답안용】 시험 답안 템플릿

## 핵심 인사이트 (3줄 요약)
> 1. **본질**: AI 호스트 애플리케이션 내에서 MCP 서버와의 세션을 관리하고, 모델의 요구사항을 서버 명령으로 변환하는 **중계 인터페이스**.
> 2. **가치**: 모델 중심의 도구 활용 구조를 탈피하여, 다수의 독립적 도구 서버를 통합 관리할 수 있는 **유연한 확장성** 제공.
> 3. **판단 포인트**: 사용자의 명시적 승인(Consent) 절차와 도구 호출 결과의 컨텍스트 주입 로직을 얼마나 안전하고 효율적으로 처리하는지가 관건.

## 출제 의도 및 답안 포인트
- **출제 의도**: MCP 생태계에서 클라이언트의 역할과 모델과의 연동 방식, 세션 관리 메커니즘 이해 여부.
- **핵심 포인트**: 기능 협상(Negotiation), 상태 관리, 사용자 승인 중계, 컨텍스트 주입.

## Ⅰ. MCP 클라이언트(MCP Client)의 정의 및 핵심 역할
### 1. MCP 클라이언트의 정의
- AI 애플리케이션 내부에 위치하여 MCP 서버와 통신 프로토콜을 수행하고, 획득한 컨텍스트와 도구 역량을 모델(LLM)에게 전달하는 소프트웨어 모듈.
### 2. 핵심 역할
- **서버 생명주기 관리**: Stdio 프로세스 실행/종료 또는 원격 SSE 연결 및 재연결 관리.
- **역량 발견 (Discovery)**: 서버로부터 사용 가능한 Resource, Tool, Prompt 목록을 질의 및 캐싱.
- **도구 호출 중계**: 모델의 Function Call 의도를 수신하여 서버의 JSON-RPC 명령으로 변환 및 실행 요청.
- **결과 통합**: 서버의 응답 데이터를 모델의 컨텍스트 윈도우에 적절한 포맷으로 삽입.

---

## Ⅱ. MCP 클라이언트의 작동 메커니즘 및 데이터 흐름
- **모델과 서버 사이의 브릿지 프로세스**
```text
┌───────────┐          ┌──────────────┐          ┌────────────┐
│ AI Model  │ <──────> │  MCP Client  │ <──────> │ MCP Server │
│ (Claude)  │  Context │  (Session)   │ JSON-RPC │ (Tool/DB)  │
└───────────┘          └──────────────┘          └────────────┘
      ↑                       │                        ↑
      └───────────────────────┼────────────────────────┘
                       User Approval (HITL)
```

1. **Initialize**: 서버에 연결하고 프로토콜 버전 및 역량(Capabilities) 협상.
2. **Expose Tools**: 서버의 도구 명세를 모델의 시스템 프롬프트나 전용 도구 슬롯에 주입.
3. **Handle Call**: 모델이 특정 도구 호출을 시도하면, 클라이언트가 이를 가로채어 서버에 전달.
4. **Safety Check**: (선택 사항) 도구 실행 전 사용자에게 팝업 등을 통해 승인을 요청.
5. **Feed Result**: 실행 결과를 모델의 메시지 히스토리에 추가하여 다음 추론 유도.

## Ⅲ. MCP 클라이언트의 주요 기능 계층

| 기능 계층 | 주요 수행 내용 | 비고 |
|:---:|:---|:---|
| **Transport Layer** | Stdio 파이프 관리, SSE 메시지 파싱, 네트워크 재연결 | 로우레벨 통신 |
| **Protocol Layer** | JSON-RPC 요청/응답 처리, 에러 핸들링, 버전 호환성 체크 | MCP 표준 준수 |
| **Security Layer** | 사용자 승인 UI 제공, 실행 권한 필터링, 민감 데이터 마스킹 | 보안 및 HITL |
| **Model Adapter** | 모델별 상이한 도구 호출 포맷(OpenAI vs Anthropic)을 MCP 표준으로 매핑 | 상호운용성 지원 |

---

## Ⅳ. MCP 클라이언트 구현 시 고려사항
- **병렬 연결 (Multi-server Connection)**: 한 클라이언트가 여러 개의 독립적인 MCP 서버(예: GitHub 서버 + Slack 서버)에 동시 연결하여 기능을 통합 제공할 수 있어야 함.
- **지연 시간 (Latency)**: 클라이언트-서버 간 통신이 지연되면 모델의 추론 속도에 직접적인 영향을 주므로 최적화된 비동기 처리 필수.
- **에러 핸들링**: 서버에서 발생한 에러를 모델이 이해할 수 있는 자연어 형태로 변환하여 전달함으로써 모델이 스스로 복구(Self-correction)할 기회 제공.

## Ⅴ. 클라이언트 유형별 특징

| 유형 | 예시 | 특징 |
|:---:|:---|:---|
| **Integrated Client** | Claude Desktop, Cursor IDE | 특정 앱에 내장되어 별도 개발 없이 설정만으로 서버 연결. |
| **Custom Client** | 회사 내 전용 챗봇 앱 | SDK(TypeScript/Python)를 사용하여 특정 요구사항에 맞춰 직접 구현. |
| **Proxy Client** | MCP-to-OpenAI Bridge | MCP 서버를 기존의 다른 API 규격으로 변환하여 구형 모델에 연결. |

## Ⅵ. 실무 관점의 결론 및 제언
- **보안의 핵심 지점**: MCP 서버는 기능을 제공할 뿐이며, 실제 해당 기능을 실행할지 결정하고 통제하는 최종 책임은 클라이언트에 있음.
- **결론**: 기술사는 클라이언트 단에서 **"에이전트 거버넌스"**를 구현해야 하며, 도구 실행에 대한 명확한 로그 기록(Audit Log)과 사용자 승인 체계를 필수적으로 설계해야 함.

- **구현/전략형**: Ⅳ. 구현 시 고려사항 및 Ⅵ. 보안 거버넌스 제언 강조.
