# 📖 【암기용】 개념 완전 이해

> 목적: MCP 클라이언트(MCP Client)를 처음 봐도 완벽히 이해하게 만든다. 시험 답안 양식이 아니라, 이해를 위한 친절한 설명이다.

## 한눈에
- **개요**: LLM 애플리케이션 내에서 MCP 서버와 통신하며 도구와 데이터를 모델에게 전달하는 "사용 주체"
- **왜 필요한가**: 모델(AI)은 스스로 외부 인터넷이나 DB에 접속할 수 없다. 클라이언트가 중간에서 "모델이 필요로 하는 도구가 서버에 있는지" 물어보고, 있으면 실행해서 그 결과를 모델에게 읽어주는 역할을 한다.
- **핵심 직관**: AI의 "비서". 사장님(LLM)이 "최근 매출 보고서 가져와"라고 하면, 비서(Client)가 서류함(Server)에서 보고서(Resource)를 찾아 사장님 책상(Context Window)에 올려두는 구조이다.

## 깊이 이해
- **배경·문제의식**: 예전에는 AI 앱마다 도구 실행 코드를 직접 구현(Hard-coding)해야 했다. 이로 인해 모델이 바뀌거나 도구가 추가될 때마다 앱 전체를 고쳐야 하는 번거로움과 보안 설정의 중복이 발생했다.
- **작동 원리**: 클라이언트는 서버에 연결(Connect)한 뒤 사용 가능한 목록을 받아온다(List). 사용자가 질문을 하면, 모델이 "이 도구가 필요해"라고 응답(Tool Call)하고, 클라이언트는 서버에 실제 실행을 요청한 뒤 결과를 다시 모델에게 전달하여 최종 답변을 생성하게 돕는다.
- **비유**: 웹 브라우저. 브라우저(Client)가 웹 서버(Server)에 접속해 HTML(Resource)을 받아 사용자에게 보여주듯, MCP 클라이언트는 서버에서 도구를 받아 모델에게 보여준다.
- **구체 예시**: "Claude 데스크톱 앱"은 대표적인 MCP 클라이언트이다. 사용자가 설치한 로컬 MCP 서버들과 통신하여 파일 수정, 터미널 실행 등의 기능을 Claude 모델에게 제공한다.
- **흔한 오해·주의점**: 클라이언트가 도구를 마음대로 실행하는 것은 아니다. 모델이 "실행이 필요하다"고 판단한 경우에만 클라이언트가 대행한다. 즉, 모델의 판단력과 클라이언트의 실행력이 결합된 형태이다.

## 연결 개념
- MCP Server — 클라이언트에게 도구와 데이터를 제공하는 서버
- Tool Call (도구 호출) — 모델이 특정 도구 실행을 클라이언트에게 요청하는 행위
- Context Window (문맥 창) — 클라이언트가 서버에서 가져온 결과를 주입하는 공간

# 📝 【답안용】 시험 답안 템플릿

> 목적: 시험장에서 25분에 그대로 쓰는 답안 양식. 작성방식(추상표현 금지·수치·도식·문제유형 전환)을 엄격히 지킨다.
> 핵심: MCP 클라이언트는 모델의 추론(Reasoning)과 실제 실행(Action)을 연결하는 핵심 인터페이스이자, 사용자 세션 및 보안 정책의 집행 지점(PEP)이다.

## 핵심 인사이트 (3줄 요약)

> 1. **본질**: MCP 클라이언트는 LLM 애플리케이션 내부에서 MCP 서버의 리소스를 발견(Discovery)하고 도구 호출(Tool Call)을 중계하는 연동 주체이다.
> 2. **가치**: 모델 중심의 아키텍처에서 외부 연동 로직을 표준화하여 개발 복잡도를 낮추고, 사용자 컨텍스트에 따른 동적 도구 할당을 가능케 한다.
> 3. **판단 포인트**: 클라이언트 설계 시 서버 라이프사이클 관리, 다중 서버 연결(Aggregator), 모델의 토큰 소모 최적화 및 결과 요약 전략이 중요하다.

## 출제 의도 및 답안 포인트

| 출제 의도 | 반드시 짚을 핵심 | 감점 회피 포인트 |
|:---|:---|:---|
| MCP 클라이언트의 연동 프로세스 이해 | Discovery -> Reasoning -> Execution -> Integration 흐름 | 클라이언트를 단순 UI 계층으로만 기술(로직 중계 역할 누락) |
| 모델 효율성 및 비용 통제 역량 | 결과 요약(Summarization), 토큰 관리, 컨텍스트 주입 전략 | 서버의 기능만 나열하고 클라이언트 측 최적화 방안 부재 |
| 사용자 보안 및 세션 관리 | 클라이언트 측 권한 필터링, User-in-the-loop(승인) | 모든 도구의 무조건적 실행 강조(보안 위험 방치) |

> 요약: 모델의 추론 결과와 서버의 실행 결과를 유기적으로 결합하고, 사용자 통제권을 확보하는 클라이언트의 중계 역할을 기술한다.

## Ⅰ. 개요 및 필요성

- 정의: LLM 애플리케이션 내에 구현되어 MCP 서버와 통신하며 도구·자원을 모델의 추론 과정에 통합하는 인터페이스 모듈
- 배경: 모델별 독자적 Tool Use 규격 탈피 및 다종의 외부 데이터 소스를 동적으로 결합해야 하는 멀티 에이전트 환경 도래
- 필요성: 연동 인터페이스 표준화를 통한 개발 생산성 향상, 사용자 세션 기반의 도구 가시성(Visibility) 및 실행 승인 통제 확보

---

## Ⅱ. 구조 및 구성요소

```text
[MCP 클라이언트 내부 구성도]
[ LLM (Reasoning Engine) ] <-> [ MCP Client Core ] <-> [ Transport Manager ] <-> MCP Servers
                                      |                       |
                         +------------+------------+     +----+----+
                         |            |            |     |         |
                  [ Discovery ] [ Tool Handler ] [ Context ] [ Stdio ] [ SSE ]
```

| 구성요소 | 역할 | 주요 사양 |
|:---|:---|:---|
| Discovery Engine | 서버 기능 목록 수집 및 관리 | List Tools/Resources, 기능 캐싱 |
| Tool Handler | 모델의 호출 요청 처리 | 인자 스키마 체크, 실행 요청 중계 |
| Context Manager | 실행 결과의 모델 주입 최적화 | 결과 요약, 토큰 제한 적용, 히스토리 관리 |
| Transport Mgr | 서버와의 연결 세션 유지 | Stdio 기반 프로세스 제어, SSE 기반 HTTP 관리 |
| UI/Approval | 사용자의 실행 최종 승인 | User-in-the-loop 인터페이스, 실행 결과 시각화 |

> 요약: 모델의 추론 결과를 서버가 이해하는 메시지로 변환하고, 반대로 실행 결과를 모델이 이해하는 컨텍스트로 변환하는 이중 중계 구조를 갖는다.

---

## Ⅲ. 동작원리 및 흐름도

```text
[MCP 클라이언트 연동 시퀀스]
Connect -> List -> User Query -> LLM Inference -> Tool Call -> Server Execution -> Result -> Final Response
(Setup)  (Scan)    (Input)      (Decision)    (Dispatch)     (Action)      (Merge)     (Answer)
```

| 단계 | 처리 내용 | 주요 제어 지점 |
|:---:|:---|:---|
| 1 | 서버 연결 및 기능 스캔 | 사용 가능한 모든 MCP 서버로부터 도구 및 리소스 명세 획득 |
| 2 | 모델 추론 및 도구 선택 | 사용자 질문에 대해 모델이 필요한 도구와 인자(Argument) 결정 |
| 3 | 도구 호출 실행 (중계) | 결정된 인자를 서버에 전송, 실행 전 사용자 승인(고위험 도구 시) 대기 |
| 4 | 결과 통합 및 최종 추론 | 실행 결과(텍스트/이미지)를 모델에 재주입하여 사용자 답변 생성 |

> 요약: 연결-스캔-추론-실행-통합의 5단계를 거치며, 모델과 서버 사이의 메시지 루프(Message Loop)를 관리한다.

## Ⅴ. 심화 비교 및 적용 판단

| 구분 | 데스크톱 클라이언트 (Claude 등) | 프레임워크 클라이언트 (LangChain 등) | 선택 기준 |
|:---|:---|:---|:---|
| 사용 주체 | 일반 사용자 (End-user) | 개발자/시스템 (Developer) | 서비스 제공 대상 |
| 구현 복잡도 | 설정 기반 간편 연결 | 코드 기반 정밀 제어 | 비즈니스 로직의 복잡도 |
| 주요 용도 | 개인 생산성 도구 강화 | 엔터프라이즈 에이전트 시스템 구축 | 대규모 워크플로우 자동화 여부 |

> 요약: 개인 도구에는 완제품 클라이언트를, 복합 업무 프로세스에는 프레임워크 기반 커스텀 클라이언트를 적용한다.

| 리스크 | 원인 | 대응 방안 | 확인 지표 |
|:---|:---|:---|:---|
| 컨텍스트 오버플로우 | 서버 결과가 너무 길어 토큰 초과 | 결과 요약(Summarization), 청킹 적용 | 모델 입력 토큰 소모량(Avg/Max) |
| 무단 도구 실행 | 모델의 할루시네이션(환각) 호출 | 고위험 도구 사용자 명시적 승인 필수 | 무승인 고위험 도구 실행 건수 (0건) |
| 서버 연결 지연 | 다수 서버 연결 시 타임아웃 발생 | 비동기 호출(Parallel), Circuit Breaker 적용 | 클라이언트 측 p99 지연 시간 |

> 요약: 토큰 최적화, 사용자 승인, 비동기 처리를 통해 클라이언트 운영의 안정성과 비용 효율을 확보한다.

| 점검 항목 | 목표 기준 | 측정 방법 |
|:---|:---|:---|
| 도구 호출 정확도 | 모델의 도구 선택 정확도 95% 이상 | Replay 테스트, 인간 평가(Human Eval) |
| 사용자 인터랙션 | 고위험 도구 승인 팝업 노출 100% | UI 단위 테스트, 보안 감사 로그 |
| 자원 효율성 | 컨텍스트 내 도구 결과 비중 40% 이내 | 토큰 분석 도구, 비용 대시보드 |

> 요약: 호출 정확도, 사용자 통제 준수율, 토큰 효율성을 지표로 클라이언트 성능을 관리한다.

## Ⅵ. 실무 적용 및 결론

**적용 방안 3개:**
1. 하이브리드 연결: 보안이 중요한 로컬 파일은 Stdio 서버로, 전사 DB는 SSE 서버로 연결하여 클라이언트에서 통합 관리
2. 승인 워크플로우: 쓰기(Write) 권한이 있는 도구 호출 시에만 사용자에게 확인 버튼을 노출하는 조건부 승인제 실시
3. 동적 컨텍스트 최적화: 서버 응답이 2,000토큰 초과 시 자동으로 핵심 내용만 요약하여 모델에 전달하는 필터 구현

**결론 (2줄):**
- 기술사 판단: MCP 클라이언트는 에이전트 운영의 "두뇌(LLM)"와 "손(Server)"을 잇는 신경계이며, 토큰 비용과 보안 승인 설계가 핵심이다.
- 향후 방향: 다중 에이전트 간 MCP 리소스를 공유하고 협업하는 에이전트 간 통신(Agent-to-Agent) 클라이언트로 진화할 전망이다.
