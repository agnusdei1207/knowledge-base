## Ⅰ. 개요
- **정의**: 에이전트의 추론 궤적·도구 호출·토큰 소비·지연 시간을 Trace/Span 구조로 수집·시각화하여 디버깅과 비용 최적화를 수행하는 LLMOps 체계
- **배경/필요성**: 에이전트가 멀티 턴으로 30초 이상 자율 실행되면 내부 의사결정 과정이 블랙박스화되어, 오답 원인 파악·병목 구간 식별·API 과금 추적이 불가하며, 감각적 프롬프트 튜닝에서 데이터 기반 엔지니어링으로의 전환이 필수임
- **비유**: 자동차 블랙박스가 사고 원인을 초 단위로 재현하듯, 에이전트의 모든 추론·행동을 녹화하는 것과 유사

| 출제 의도 | 반드시 짚을 핵심 | 감점 회피 포인트 |
|:---|:---|:---|
| 전통 APM과 에이전트 관측성의 차이 | Trace/Span + LLM 특화 메타데이터(프롬프트·토큰·모델명) | OpenTelemetry 표준 준수 및 개인정보 마스킹 아키텍처 누락 시 감점 |

> 요약: 에이전트 관측성은 블랙박스 LLM의 추론 과정을 투명하게 만들어 데이터 기반 디버깅·비용 관리를 가능케 하는 체계임

## Ⅱ. 구성요소
```text
+------------------------------------------------------------------+
|                  Observability Pipeline                           |
|  +-------------+    +-----------+    +-----------+    +--------+ |
|  | Instrumentor|--->| Collector |--->| Dashboard |--->| Action | |
|  | (SDK/Hook)  |    | (OTel)   |    | (LangSmith|    | (Debug/| |
|  |             |    |          |    |  Phoenix) |    |  Tune) | |
|  +-------------+    +-----------+    +-----------+    +--------+ |
|   계측 삽입          수집·전송       시각화·분석      피드백·최적화 |
+------------------------------------------------------------------+
```

| 구성요소 | 설명 | 비유 |
|:---|:---|:---|
| Instrumentor | SDK 데코레이터·콜백으로 LLM 호출·도구 호출마다 Span 생성 및 메타데이터 부착 | CCTV 설치 |
| Collector | OpenTelemetry(OTel) 프로토콜로 비동기 백그라운드 전송, PII 마스킹 필터 적용 | 녹화 영상 전송·저장 |
| Dashboard | Trace 트리 시각화, 토큰 비용 집계, Latency 히트맵, 프롬프트 원문 열람 제공 | 관제 센터 모니터 |
| Action Layer | 오류 Trace의 프롬프트를 Playground로 복사하여 즉시 수정·재실행하는 디버깅 루프 | 현장 정비 |

> 요약: 계측→수집→시각화→피드백의 4단계로 에이전트 내부를 완전 투명화

## Ⅲ. 절차
```text
+----------+     +-----------+     +-----------+     +----------+
| Span     |---->| 비동기    |---->| 대시보드  |---->| 프롬프트 |
| 생성     |     | 전송      |     | 시각화    |     | 튜닝     |
| (Hook)   |     | (OTel)    |     | (분석)    |     | (수정)   |
+----------+     +-----------+     +-----------+     +----------+
```

1. **Trace/Span 수집(Instrumentation)** — 사용자 요청 1건을 Trace ID로 생성, 하위 LLM 호출·도구 호출·서브 에이전트 호출을 각각 Span으로 트리 구조 기록(프롬프트 원문, 토큰 수, 모델명, 응답 시간 포함)
2. **LLM 특화 메타데이터 포획** — 입력 프롬프트 전문, 출력 텍스트, Prompt Token·Completion Token 개수, 사용 모델(GPT-4o 등), Temperature 파라미터를 Span 속성에 부착
3. **비동기 전송 및 저장** — 서비스 성능 영향 최소화를 위해 백그라운드 스레드로 OTel 표준 프로토콜 전송, 전송 전 PII 마스킹 필터 적용
4. **분석 및 디버깅** — 대시보드에서 Latency 병목 Span 식별, 토큰 비용 이상치 탐지, 오류 Trace의 프롬프트를 Playground로 즉시 복제하여 수정·재실행

> 요약: Span 수집→메타데이터 부착→비동기 전송→대시보드 디버깅으로 데이터 기반 최적화 수행

## Ⅳ. 문제점
- **개인정보 유출**: 프롬프트 원문(고객명·주민번호 포함)이 SaaS 관측 플랫폼에 평문 저장 — 개인정보보호법 위반 리스크
- **데이터 폭증**: 에이전트 세션당 수십 개 Span × 일일 수만 건 → 스토리지·검색 비용 기하급수적 증가 — 보존 정책 부재
- **관측 오버헤드**: 과도한 계측으로 에이전트 응답 시간 10~15% 증가 — 계측 범위·샘플링 미설정

> 요약: 개인정보 유출, 스토리지 폭증, 성능 오버헤드가 관측성의 3대 과제임

## Ⅴ. 개선방안
1. 단기: OTel Collector 단에서 PII 정규식 마스킹 필터 필수 적용 + 관측 플랫폼 VPC 내 자체 호스팅(Self-hosting)
2. 중기: Trace 보존 기간(30일) + 샘플링률(정상 10%, 에러 100%) 정책 수립으로 스토리지 비용 70% 절감
3. 장기: 관측 데이터 이상 탐지 시 자동으로 프롬프트 최적화 모델(Tuner AI)을 트리거하는 Self-Healing 파이프라인 구축

- **개인정보 유출**: 전송 전 마스킹 + 자체 호스팅 + 접근 제어(RBAC) (지표: PII 노출 건수 0건)
- **데이터 폭증**: TTL 30일 + Head-based Sampling + 에러 Trace 전수 보존 (지표: 월간 스토리지 비용 예산 ±15% 이내)
- **관측 오버헤드**: 비동기 전송 + 경량 SDK + 샘플링 적용 (지표: 관측으로 인한 Latency 증가 < 5%)

> 요약: 마스킹·샘플링·비동기화로 보안·비용·성능 트레이드오프 최적화

## Ⅵ. 전망
- 향후 발전 방향: 단순 시각화를 넘어 관측 데이터 기반 자동 프롬프트 최적화(Self-Healing), 이상 탐지 시 가드레일·정책 엔진 규칙 자동 업데이트로 폐쇄 루프(Closed-Loop) LLMOps 실현
- 기술사적 판단: 관측성은 평가(025번 참조)와 한 쌍으로 동작하며, 평가가 '점수'를 매기면 관측성이 '원인'을 찾는 역할 분담 구조임. 관측 없는 평가는 블라인드 테스트에 불과함
- 기술사 제언: OpenTelemetry 표준을 준수하여 벤더 종속을 회피하고, 관측 데이터 파이프라인에 PII 마스킹을 아키텍처 레벨(Collector 단)에서 강제 적용할 것. SaaS 플랫폼 사용 시 반드시 데이터 상주 지역(Residency) 요건을 사전 검토할 것
