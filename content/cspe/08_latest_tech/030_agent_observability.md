# 📖 【암기용】 개념 완전 이해

> 목적: 에이전트 관측성을 처음 봐도 완벽히 이해하게 만든다.

## 한눈에
- **정의**: AI 에이전트의 추론·도구 호출·비용·성능을 실시간으로 추적·분석하는 체계
- **왜 필요한가**: 에이전트는 내부 추론이 블랙박스이고 다단계 도구를 호출하므로, 실패 원인·비용·품질을 파악하려면 전 과정이 가시화돼야 함
- **핵심 직관**: 자동차 블랙박스+대시보드처럼 에이전트의 모든 사고·행동·결과를 실시간으로 기록하고 시각화하는 것

## 깊이 이해
- **배경·문제의식**: 기존 APM은 HTTP 요청·응답 중심인데, 에이전트는 LLM 호출·프롬프트·도구 체인·토큰 비용 등 새로운 관측 차원이 필요함
- **작동 원리**: ① 트레이싱: 요청→계획→도구호출→응답을 단일 Trace ID로 연결 ② 메트릭: 토큰 사용량·비용·지연·성공률 수집 ③ 로깅: 프롬프트·응답·판정 이유 기록 ④ 평가: LLM-as-Judge로 응답 품질 자동 채점
- **비유**: 병원 환자 모니터가 심박·혈압·산소포화도를 동시에 보여주듯, 에이전트의 추론·비용·성능을 한 대시보드에서 보는 것
- **구체 예시**: LangSmith가 에이전트 체인의 각 단계를 트레이스로 기록하고, 토큰 비용 $0.03/요청, p95 지연 2.1s, 성공률 94%를 대시보드에 표시
- **흔한 오해·주의점**: 프롬프트·응답 전문을 저장하면 PII가 포함될 수 있으므로 마스킹 정책이 필수

## 연결 개념
- OpenTelemetry — 트레이스·메트릭·로그 수집 표준
- LLMOps — 관측성을 포함한 LLM 운영 전체 체계
- 에이전트 실패복구 — 관측성 데이터로 실패 원인을 분석·복구


# 📝 【답안용】 시험 답안 템플릿

> 목적: 시험장에서 25분에 그대로 쓰는 답안 양식.

## 핵심 인사이트 (3줄 요약)

> 1. **본질**: 에이전트 관측성은 추론·도구호출·비용·품질을 트레이스·메트릭·로그·평가로 가시화하는 체계임.
> 2. **가치**: 실패 원인 파악 MTTR 60분→10분, 비용 이상 탐지, 응답 품질 자동 채점 적용.
> 3. **판단 포인트**: 기존 APM에 LLM 전용 차원(토큰·프롬프트·체인 트레이스)을 추가 설계해야 함.


## Ⅰ. 개요 및 필요성

에이전트 관측성은 AI 에이전트 실행의 가시화 체계임. 에이전트의 다단계 추론·도구 호출은 기존 APM으로 추적이 불가능하며, 토큰 비용·프롬프트 품질·체인 트레이스 등 LLM 전용 관측 차원이 필요함.


## Ⅱ. 구조 및 구성요소

```text
Agent Execution → OTel Collector → Storage
                       │
           ┌───────────┼───────────┐
        Traces      Metrics      Logs
           │           │           │
        Dashboard + Alert + Evaluation
```

| 구성요소 | 역할 | 특이사항 |
|:---|:---|:---|
| Trace Collector | 요청→계획→도구→응답 체인 기록 | OpenTelemetry, Span 단위 |
| Metrics Store | 토큰·비용·지연·성공률 집계 | Prometheus, 15s 간격 |
| Log Store | 프롬프트·응답·판정 사유 저장 | PII 마스킹 필수, 보관 90일 |
| Evaluator | LLM-as-Judge 응답 품질 채점 | 정확도·완전성·안전성 3축 |

> 요약: 트레이스·메트릭·로그·평가 4축으로 에이전트 실행 전 과정을 가시화함.


## Ⅲ. 동작원리 및 흐름도

```text
에이전트 실행 → Span 생성(Trace ID) → 도구 호출 Span 연결
→ 메트릭 수집(토큰·비용·지연) → 로그 저장(프롬프트·응답)
→ 평가(LLM-as-Judge) → 대시보드·알림
```

| 단계 | 처리 내용 | 검증 기준 |
|:---:|:---|:---|
| 1 | 요청 수신·Trace ID 발급 | UUID v4, 전 단계 전파 |
| 2 | 각 도구 호출을 Child Span으로 기록 | 도구명·입출력·지연·상태 코드 |
| 3 | 토큰·비용·지연 메트릭 집계 | p95 지연 <3s, 비용 $0.05/요청 |
| 4 | 품질 평가·이상 알림 | 품질 <0.7 시 알림, MTTR <10분 |

> 요약: 단일 Trace ID로 전 단계를 연결하고, 메트릭·평가 기반으로 이상을 자동 탐지함.


## Ⅳ. 특징

| 구분 | 기존 APM | 에이전트 관측성 | 수치·판단 포인트 |
|:---|:---|:---|:---|
| 추적 단위 | HTTP 요청 | 추론+도구 체인 Span | Span 깊이 평균 5단계 |
| 비용 가시성 | 인프라 비용만 | 토큰·API 호출 비용 | 요청당 $0.03~0.10 |
| 품질 평가 | 없음 | LLM-as-Judge 자동 채점 | 정확도·완전성·안전성 3축 |

> 요약: 기존 APM 대비 LLM 추론 체인·토큰 비용·품질 평가 차원이 추가됨.


## Ⅴ. 실무 적용 및 결론

**적용 방안 3개:**
1. OpenTelemetry SDK로 에이전트 체인을 Span 단위로 계측하고 Jaeger에서 트레이스 시각화
2. Prometheus에 토큰 사용량·요청당 비용·p95 지연·성공률 메트릭을 15s 간격으로 수집
3. LLM-as-Judge로 응답 품질을 자동 채점(정확도·완전성·안전성)하고 0.7 미만 시 PagerDuty 알림

**결론 (2줄):**
- 기술사 판단: 기존 APM에 LLM Span·토큰 메트릭·품질 평가를 추가하여 에이전트 전용 관측 체계 구축
- 향후 방향: 관측 데이터 기반 자동 프롬프트 최적화·비용 예측 모델로 LLMOps 자동화 발전
