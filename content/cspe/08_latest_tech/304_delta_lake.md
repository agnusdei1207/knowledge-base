# 📖 【암기용】 개념 완전 이해

> 목적: Delta Lake를 처음 봐도 완벽히 이해하게 만든다. 시험 답안 양식이 아니라, 이해를 위한 친절한 설명이다.

## 한눈에
- **개요**: 데이터 레이크 위에 ACID 트랜잭션을 구현한 오픈소스 스토리지 레이어
- **왜 필요한가**: 기존 데이터 레이크는 쓰기 도중에 장애가 나면 데이터가 깨지거나, 읽는 도중에 데이터가 바뀌어 결과가 틀어지는 문제가 있었다. 이를 해결하기 위해 '거래 장부(Transaction Log)'를 도입한 것이다.
- **핵심 직관**: "데이터 파일(Parquet) 옆에 믿을 수 있는 기록장(JSON Log)을 두어 데이터의 안전을 책임진다."

## 깊이 이해
- **배경·문제의식**: 하둡(HDFS)이나 S3 같은 저장소는 파일 단위로 관리됨. 수천 개 파일 중 일부만 업데이트(UPSERT)하거나 삭제하는 게 매우 어렵고, 작업 중에 누군가 읽으면 불완전한 데이터를 보게 됨(신뢰성 문제).
- **작동 원리**: 데이터를 저장할 때 실제 데이터 파일(Parquet)과 함께 '델타 로그(_delta_log)'라는 폴더에 작업 내역을 JSON으로 기록함. 읽기 요청이 오면 로그를 먼저 보고 '가장 최신의 유효한 파일들'이 무엇인지 확인한 뒤 읽음. 이를 통해 낙관적 동시성 제어(OCC)를 수행함.
- **비유**: 은행 거래와 같음. 통장 잔액(데이터 파일)만 있는 게 아니라 거래 내역(로그)이 함께 있어서, 입금 도중에 끊겨도 로그를 보고 복구하거나 이전 상태로 되돌릴 수 있음.
- **구체 예시**: `UPDATE` 명령을 내리면 Delta Lake는 수정된 행을 포함한 새로운 파일을 쓰고, 로그에 "이제 구버전 파일 대신 이 신버전 파일을 보세요"라고 적음. 사용자는 끊김 없이 일관된 데이터를 보게 됨.
- **흔한 오해·주의점**: 별도의 데이터베이스 엔진이 아님. Spark, Flink, Trino 등이 데이터를 읽고 쓸 때 사용하는 '포맷 규칙'이자 '라이브러리'임.

## 연결 개념
- Apache Spark - Delta Lake를 탄생시킨 핵심 연산 엔진
- ACID 트랜잭션 - 데이터 신뢰의 4요소 (원자성, 일관성, 격리성, 지속성)
- Medallion Architecture - Delta Lake를 활용한 데이터 정제 단계

# 📝 【답안용】 시험 답안 템플릿

> 목적: 시험장에서 25분에 그대로 쓰는 답안 양식. 작성방식(추상표현 금지·수치·도식·문제유형 전환)을 엄격히 지킨다.
> 핵심: Delta Lake의 핵심 메커니즘인 트랜잭션 로그(_delta_log)와 이를 통한 Time Travel, Schema Enforcement 기능을 기술적으로 명시한다.

## 핵심 인사이트 (3줄 요약)

> 1. **본질**: Delta Lake는 클라우드 오브젝트 스토리지에서 ACID 트랜잭션을 보장하고 대규모 데이터를 관리하기 위한 오픈 표준 테이블 포맷이다.
> 2. **가치**: 스키마 강제(Enforcement)와 버전 관리(Time Travel)를 통해 데이터 품질을 DW 수준으로 유지하며, 스트리밍과 배치를 단일 테이블에서 처리한다.
> 3. **판단 포인트**: 트랜잭션 로그 기반의 스냅샷 격리(Snapshot Isolation) 메커니즘을 통해 데이터 일관성과 쿼리 성능을 동시에 확보한다.

| 출제 의도 | 반드시 짚을 핵심 | 감점 회피 포인트 |

> 요약: Delta Lake는 로그 기반 거버넌스를 통해 데이터 레이크를 신뢰할 수 있는 분석 플랫폼으로 변모시킨다.

## Ⅰ. 개요 및 필요성

- 정의: Apache Spark 기반으로 데이터 레이크의 안정성과 성능을 높이기 위해 설계된 오픈소스 스토리지 계층
- 배경: 기존 데이터 레이크(HDFS/S3)의 원자성(Atomicity) 부재로 인한 데이터 오염 및 동시 읽기/쓰기 충돌
- 필요성: 실시간 데이터 업데이트(Upsert) 요구 증가, 데이터 오염 방지를 위한 스키마 거버넌스, 과거 데이터 복구(Time Travel) 필요성

---

## Ⅱ. 구조 및 구성요소

```text
[ Delta Table Structure ]
  / _delta_log/ (JSON/CheckPoint) -> 트랜잭션 이력 및 스냅샷 관리
  / part-0001.parquet -> 실제 데이터 (Columnar Storage)
  / part-0002.parquet -> 추가/수정된 데이터
Metadata Layer -> Schema, Statistics, Version -> ACID 보장
```

| 구성요소 | 역할 | 특이사항 |
|:---|:---|:---|
| Transaction Log | 모든 변경 사항을 순차적으로 기록 (_delta_log) | JSON 포맷, 주기적 체크포인트 |
| Parquet Files | 실제 데이터가 저장되는 고성능 열 지향 포맷 | 압축 및 컬럼 기반 스캔 최적화 |
| Snapshot | 특정 시점의 유효한 파일 목록 정의 | 버전 관리 및 Time Travel의 근거 |

> 요약: JSON 형태의 트랜잭션 로그와 Parquet 형태의 데이터 파일을 결합하여 상태를 관리하는 구조이다.

## Ⅲ. 동작원리 및 흐름도 (Optimistic Concurrency Control)

```text
Write 요청 -> [ 1. Begin ] -> [ 2. Read ] -> [ 3. Write ] -> [ 4. Commit ]
                 |              |              |                |
              버전 확인      최신 상태 스캔    새 파일 생성     로그 기록 및 확정
```

| 단계 | 처리 내용 | 검증 기준 |
|:---:|:---|:---|
| 1 | 트랜잭션 시작 | 현재 테이블의 최신 버전(Version N) 확인 | - |
| 2 | 데이터 기록 | 수정/추가된 내용을 새로운 Parquet 파일로 저장 | - |
| 3 | 로그 기록 | _delta_log에 작업 내용(Add/Remove 파일) 기록 | 원자적(Atomic) 기록 |
| 4 | 충돌 확인 | 기록 도중 다른 트랜잭션이 성공했는지 확인 | 낙관적 동시성 제어 (OCC) |
| 5 | 체크포인트 | 로그가 많아지면 Parquet 형태의 스냅샷으로 병합 | 읽기 성능 최적화 |

> 요약: 데이터 파일을 먼저 쓰고 마지막에 로그를 원자적으로 확정하여 트랜잭션을 완성한다.

## Ⅳ. 특징

| 구분 | 주요 특징 | 상세 내용 |
|:---|:---|:---|
| 데이터 신뢰성 | ACID 트랜잭션 | 다수 작업자의 동시 접근에도 데이터 일관성 보장 |
| 품질 관리 | Schema Enforcement | 스키마에 맞지 않는 데이터 유입을 원천 차단 |
| 유연성 | Schema Evolution | 비즈니스 변화에 맞춰 스키마를 안전하게 변경 |
| 버전 관리 | Time Travel | 과거 버전 데이터 조회 및 Rollback (최대 30일 등 설정) |
| 성능 최적화 | Z-Ordering | 관련 데이터를 물리적으로 가깝게 배치하여 쿼리 속도 향상 |

> 요약: DW 수준의 기능(ACID, Schema)을 데이터 레이크에 구현하여 분석 신뢰도를 극대화한다.

## Ⅴ. 심화 비교 및 적용 판단

| 구분 | 기존 Parquet (Data Lake) | Delta Lake | 선택 기준 |
|:---|:---|:---|:---|
| 업데이트 | 전체 재작성 필요 | MERGE INTO (Upsert) 지원 | 데이터 수정 빈도 |
| 트랜잭션 | 없음 (Partial Write 위험) | 있음 (ACID 보장) | 데이터 무결성 중요도 |
| 동시성 | 읽기 중 쓰기 시 에러/오류 | 스냅샷 격리로 동시 처리 가능 | 동시 사용자 수 |
| 버전 관리 | 수동 백업 필요 | 자동 (Time Travel) | 감사(Audit) 요건 |

> 요약: 단순 보관은 Parquet로 충분하나, 잦은 변경과 동시 분석이 필요하면 Delta Lake가 필수적이다.

| 리스크 | 원인 | 대응 방안 | 확인 지표 |
|:---|:---|:---|:---|
| 로그 파편화 | 잦은 작은 트랜잭션 발생 | 주기적 VACUUM 및 CHECKPOINT 수행 | _delta_log 폴더 크기 |
| 성능 저하 | 많은 수의 작은 파일 (Small Files) | OPTIMIZE 명령을 통한 파일 병합(Compaction) | 파일 개수 대비 평균 크기 |
| 스토리지 비용 | 과거 버전 데이터 누적 | 데이터 보관 주기(Retention) 설정 및 VACUUM | 삭제 대기 파일 용량 |

> 요약: 성능 유지를 위해 주기적인 OPTIMIZE와 VACUUM 관리가 운영의 핵심이다.

| 점검 항목 | 목표 기준 | 측정 방법 |
|:---|:---|:---|
| 쓰기 성공률 | 트랜잭션 충돌로 인한 실패율 1% 미만 | 오류 로그 분석 및 재시도 횟수 |
| 쿼리 응답 시간 | 일반 Parquet 대비 동일 또는 우위 | TPC-DS 벤치마크 수행 |
| 데이터 복구 시간 | 특정 시점 복구(Rollback) 10분 이내 | Time Travel 기능 테스트 |

> 요약: 트랜잭션 안정성과 쿼리 성능, 그리고 복구 용이성을 도입 평가지표로 활용한다.

## Ⅵ. 실무 적용 및 결론

**적용 방안 3개:**
1. **메달리온 아키텍처(Medallion)**: Raw(Bronze) -> Filtered(Silver) -> Aggregated(Gold) 흐름을 Delta Table로 구축하여 데이터 품질 단계별 관리
2. **실시간 CDC 반영**: 운영 DB의 변경분을 Spark Structured Streaming과 Delta Lake의 MERGE를 사용하여 실시간 분석 테이블 유지
3. **규제 대응(GDPR/잊혀질 권리)**: 특정 사용자의 데이터를 삭제(DELETE)할 때 Delta Lake의 ACID 기능을 사용하여 운영 중단 없이 안전하게 처리

**결론 (2줄):**
- 기술사 판단: Delta Lake는 데이터 레이크의 고질적 문제인 '데이터 신뢰성'을 소프트웨어 계층에서 해결한 혁신이며, 레이크하우스 구현의 실질적 표준이다.
- 향후 방향: Hudi, Iceberg와의 상호운용성(UniForm) 확대를 통해 개방형 데이터 생태계의 중심 역할을 지속할 전망이다.
