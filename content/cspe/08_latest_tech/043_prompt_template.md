## 미리 알고가기

- 프롬프트 템플릿 ($Prompt$ $Template$): 공통 지시문과 변수 슬롯($Variable$ $Slot$)이 사전 정의된 재사용 가능하고 버전 관리가 가능한 텍스트 뼈대임
- 슬롯 바인딩 ($Binding$): 런타임 시점에 데이터베이스 조회 값이나 사용자 입력을 템플릿 내의 변수 공간에 동적으로 채워 넣는 작업임
- 구조적 형상 ($Schema$): 출력물의 데이터 객체 키 이름과 변수 타입을 엄밀히 정의하여 기계적 후처리를 보장하는 틀임
- 디리미터 ($Delimiter$): 시스템 지시문과 주입 데이터의 경계를 획정하여 탈옥을 방지하는 구분 문자열(예: `###`, `---` 등)임

## Ⅰ. 개요

- **정의/개념**: Prompt Template은 모델에게 하달할 기본 역할과 업무 규칙 및 출력 스키마를 텍스트 뼈대로 고정하고, 런타임에 유동적으로 변경되는 사용자 질의나 사내 문서 정보만 변수 슬롯($Variable$ $Slot$)에 주입하여 호출하는 파라미터화된 지시문 템플릿임
- **배경/필요성**: 기업형 상용 서비스에서는 하루에도 수만 건의 정형화된 과업이 발생하므로, 자연어 질문의 무작위 변동성을 억제하고 소프트웨어 코드처럼 프롬프트를 배포·갱신·테스트하기 위해 추상화된 제어 레이어가 필요함

## Ⅱ. 특징

- 입출력의 형식을 고정하므로 API 응답값의 포맷 깨짐($JSON$ 파싱 에러)을 미연에 방지하여 하위 시스템과의 결합 안정성을 대폭 개선함
- 프롬프트를 자연어 스트링이 아닌 독립적인 형상 관리 자산(예: Git 버전 관리)으로 취급할 수 있게 하여, 품질 배포 파이프라인($CI/CD$)과 연계할 수 있음
- 템플릿 엔진(Jinja2 등)을 사용해 조건부 분기(If-Else)나 반복문(For)을 동적으로 주입하여 상황 맞춤형 거대 문맥을 조립해 내는 유연함을 가짐

## Ⅲ. 종류 및 비교

| 판단 기준 | 정적 텍스트 프롬프트 | 동적 프롬프트 템플릿 (Prompt Template) |
|:---|:---|:---|
| **동적 데이터 바인딩** | 불가능함 (수동으로 문장을 고쳐 써야 함) | 가능함 (런타임에 슬롯 단위 자동 치환) |
| **소프트웨어 제어력** | 매우 낮음 (애플리케이션과 독립적 작동) | 매우 높음 (코드 단에서 템플릿 변수 조작) |
| **형상 버전 관리** | 어려움 | 쉬움 (독립된 파일로 관리 및 $CI/CD$ 통합) |
| **데이터 누수 방지** | 취약함 (입력과 지시문의 모호한 경계) | 우수함 (구분자($Delimiter$) 설계를 통해 격리) |

> 요약: 정적 프롬프트는 단발성 테스트에, 동적 템플릿은 자동화 시스템 통합 및 품질 통제에 최적임.

## Ⅳ. 구성요소 및 구조

| 구성요소 | 설명 |
|:---|:---|
| 골격 텍스트 | 역할 정의, 지시 사항, 절대적 정책이 정의되어 변하지 않는 상수 텍스트 영역임 |
| 변수 슬롯 | 중괄호(`{{var}}` 등) 형식을 취하며, 런타임에 실제 정보가 주입되는 변수 바인딩 영역임 |
| 구분자 명세 | 주입되는 텍스트가 명령어로 돌변하는 것을 막기 위해 입력 값을 감싸 격리하는 표식임 |
| 포맷 가이드라인 | 답변 스키마 양식(예: `$JSON_SCHEMA`)을 지정하여 일관된 텍스트 출력을 보증하는 가이드부임 |

```text
[ 프롬프트 템플릿 렌더링 예시 ]
[Template String: "분석할 텍스트: ###{{text}}###"] 
                     ↓ (Runtime binding: text = "안녕하세요")
[Rendered String: "분석할 텍스트: ###안녕하세요###"]
```

## Ⅴ. 원리 및 절차 흐름도

```text
+-------------+     +--------------+     +-------------+     +-------------+
| 템플릿 설계  | --> | 실시간 바인딩| --> | 구분자 이중격| --> | 파서 유효검증|
+-------------+     +--------------+     +-------------+     +-------------+
```

1. **골격 정의** — 서비스 성격에 맞게 시스템 지시어와 필수 퓨샷 및 출력 스키마를 담은 템플릿 파일을 작성하여 형상 저장소에 등록함
2. **슬롯 매핑** — 사용자가 요청을 보내면, RAG 엔진이 관련 문서 조각을 찾아내어 템플릿 내 지정된 변수 슬롯에 동적으로 매핑함
3. **구분자 적용** — 외부 입력값이 템플릿 골격 내부 지시를 무시하게 하는 인젝션을 방지하기 위해 이중 구분자(Delimiter)로 입력을 격리 렌더링함
4. **전송 및 정밀화** — 렌더링 완료된 텍스트를 LLM에 전송하고, 도출된 출력이 템플릿에서 선언한 JSON 구조에 부합하는지 정밀 스키마 파싱을 수행함

## Ⅵ. 실무 적용 및 유의점

1. 외부 데이터가 템플릿 슬롯에 그대로 채워질 때, 해당 데이터 안에 탈옥용 우회 명령이 포함되면 템플릿 전체 통제권이 무력화되므로, 변수 대입 시 악성 키워드와 시스템 구분자 기호를 강제로 정화하는 '슬롯 새니타이제이션'을 장착하고 스키마 유효 검증 통과율로 이를 확인함
2. 서비스 템플릿의 내용이 수정되어 배포될 때 기존과 다른 무작위 답변이나 품질 하락이 생길 수 있으므로, 배포 전 모의 평가셋을 통해 테스트를 돌리는 '회귀 테스트($Regression$ $Test$)' 프로세스를 필수 가동하고 배포 성공률과 응답 편집 거리($Edit$ $Distance$) 지표로 안정성을 보장해야 함

## Ⅶ. 결론

- 프롬프트 템플릿은 확률적 언어 지능을 신뢰성 있는 정형화 소프트웨어로 통합시키는 문맥 조립 프레임워크이며, 설계자는 주입 변수의 입력 정화와 배포 전 품질 평가 체계를 상시 가동하여 서빙 안전성을 구축해야 함
