## 미리 알고가기

- Prompt Template은 고정 지시문에 변수 슬롯을 결합한 재사용 가능한 프롬프트 골격임
- Variable Slot은 사용자 입력, 검색 결과, 규칙 문서 같은 동적 값을 주입하는 자리임
- Output Schema는 템플릿이 생성해야 할 형식을 고정해 시스템 연동을 쉽게 만드는 제약임

## Ⅰ. 개요

- **정의/개념**: Prompt Template은 역할 지시와 업무 규칙과 출력 형식을 고정하고 사용자 입력이나 검색 결과만 변수로 주입해 일관된 품질을 내도록 만든 파라미터화 프롬프트 구조임
- **배경/필요성**: 운영 시스템에서는 같은 업무를 수천 번 반복 처리하므로 매 요청마다 사람이 프롬프트를 다시 작성할 수 없으며, 재사용 가능하고 테스트 가능한 템플릿 계층이 필요함

## Ⅱ. 특징

- 프롬프트를 코드처럼 재사용하고 버전 관리할 수 있어 운영 안정성이 높음
- 동일 업무에 대해 형식 편차를 줄여 후처리와 API 연동을 단순화함
- RAG, Agent, Workflow에서 문맥 주입 위치와 출력 계약을 명시적으로 통제할 수 있음
- 잘못 설계하면 변수 오염과 슬롯 누락이 반복적으로 발생하므로 검증 체계가 필수임

## Ⅲ. 종류 및 비교

| 판단 기준 | 자유 입력 프롬프트 | Prompt Template | Workflow Template |
|:---|:---|:---|:---|
| 재사용성 | 낮음 | 높음 | 매우 높음 |
| 변수 관리 | 수동 | 슬롯 기반 | 단계별 슬롯 기반 |
| 출력 일관성 | 낮음 | 높음 | 매우 높음 |
| 적합 업무 | 실험성 질의 | 반복 업무 자동화 | 다단계 에이전트 파이프라인 |

## Ⅳ. 구성요소 및 구조

| 구성요소 | 설명 |
|:---|:---|
| Base Instruction | 역할, 목표, 금지사항을 고정해 모든 요청에서 유지할 공통 규칙을 정의함 |
| Variable Slot | 질문, 문서 조각, 정책 규칙처럼 요청마다 달라지는 값을 안전하게 주입하는 자리임 |
| Example Block | 원하는 응답 패턴을 고정해 형식 드리프트를 줄이고 결과 예측 가능성을 높임 |
| Output Schema | JSON 필드, 표 컬럼, 마크다운 구조를 명시해 시스템 후처리를 안정화함 |

```text
+------------------+     +------------------+     +------------------+     +------------------+
| Base Instruction | --> | Variable Slot    | --> | Example Block    | --> | Output Schema    |
+------------------+     +------------------+     +------------------+     +------------------+
```

## Ⅴ. 원리 및 절차 흐름도

```text
+-------------+     +-------------+     +---------------+     +-------------+
| 템플릿 정의  | --> | 변수 채움    | --> | 렌더링, 호출   | --> | 결과 검증    |
+-------------+     +-------------+     +---------------+     +-------------+
```

1. **템플릿 정의**: 역할, 규칙, 예시, 출력 형식을 공통 골격으로 설계함
2. **변수 채움**: 사용자 질의와 검색 문맥과 도메인 파라미터를 슬롯에 바인딩함
3. **렌더링 및 호출**: 완성된 프롬프트를 모델에 전송해 응답을 생성함
4. **결과 검증**: 스키마 준수 여부와 품질 평가 결과를 확인해 템플릿을 수정함

## Ⅵ. 문제점 및 해결 방안

1. 문제: 사용자 입력이나 검색 문맥이 슬롯을 통해 그대로 들어오면 템플릿 구조를 깨거나 injection을 유발할 수 있음
   - 해결방안: 변수 escaping과 delimiter 분리를 적용하고 schema validation 실패율과 injection success rate로 안정성을 검증함
2. 문제: 템플릿 버전이 늘어나면 어떤 규칙이 어느 서비스에 적용되는지 추적이 어려워 운영 혼선이 발생할 수 있음
   - 해결방안: 템플릿 버전 관리와 배포 이력을 분리 운영하고 release별 task success rate와 rollback 빈도로 품질을 검증함
3. 문제: 검색 문맥과 예시를 과도하게 넣으면 템플릿이 비대해져 context budget을 낭비하고 핵심 지시가 묻힐 수 있음
   - 해결방안: 슬롯별 토큰 상한과 우선순위를 설정하고 rendered prompt token 수와 answer accuracy 대비 cost로 효율을 검증함

## Ⅶ. 적용 사례

- RAG 답변 시스템: 질문, 검색 문맥, 답변 형식을 슬롯으로 분리해 일관된 근거 답변을 생성함, 확인 지표는 faithfulness와 schema pass rate임
- 고객지원 분류기: 문의 유형과 제품군을 변수로 넣어 동일 포맷의 분류 결과를 반환함, 확인 지표는 routing accuracy와 automation rate임
- 보고서 자동화: 기간, 지표, 강조 포인트를 슬롯화해 반복 보고서를 생성함, 확인 지표는 template reuse rate와 edit distance임

## Ⅷ. 결론

프롬프트 템플릿은 말을 재사용하는 편의 기능이 아니라 프롬프트를 테스트 가능하고 배포 가능한 운영 자산으로 바꾸는 구조화 계층임.
