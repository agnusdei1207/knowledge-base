# 📖 【암기용】 개념 완전 이해

> 목적: 프롬프트 템플릿을 처음 봐도 완벽히 이해하게 만든다.

## 한눈에
- **개요**: 변수 슬롯을 포함한 재사용 가능한 프롬프트 구조체
- **왜 필요한가**: 매번 프롬프트를 수동 작성하면 품질 편차가 크고, 버전 관리·테스트가 불가능함.
- **핵심 직관**: 프롬프트의 "양식지"로, 빈칸만 채우면 일관된 품질의 입력이 생성됨.

## 깊이 이해
- **배경·문제의식**: 프롬프트 엔지니어링이 성숙하면서, 검증된 프롬프트를 팀 단위로 공유·재사용·버전 관리할 필요가 생김. 하드코딩된 문자열은 유지보수·A/B 테스트가 어려움.
- **작동 원리**: 템플릿 문자열에 `{variable}` 슬롯을 두고, 런타임에 사용자 입력·DB 결과·검색 결과를 삽입함. LangChain PromptTemplate, Jinja2 등으로 구현.
- **비유**: 계약서 표준 양식에 당사자명·금액·날짜만 채워 넣는 것과 동일.
- **구체 예시**: `"다음 {language} 코드를 리뷰하시오: {code}"` -> language="Python", code=실제 코드 삽입.
- **흔한 오해·주의점**: 변수 삽입 시 프롬프트 인젝션 위험이 있음. 사용자 입력을 그대로 삽입하면 시스템 프롬프트 우회 가능.

## 연결 개념
- Prompt Engineering — 템플릿 설계의 상위 프레임워크
- System Prompt — 템플릿 내 역할 고정 계층
- RAG — 검색 결과를 템플릿 변수에 삽입하는 패턴

# 📝 【답안용】 시험 답안 템플릿

> 목적: 시험장에서 25분에 그대로 쓰는 답안 양식.

## 핵심 인사이트 (3줄 요약)

> 1. **본질**: 프롬프트 템플릿은 변수 슬롯 기반의 재사용 가능한 프롬프트 구조체임.
> 2. **가치**: 팀 공유·버전 관리·A/B 테스트를 가능하게 하여 프롬프트 품질 편차를 제거함.
> 3. **판단 포인트**: 변수 삽입 시 프롬프트 인젝션 방어와 토큰 예산 관리를 함께 설계해야 함.

---

## Ⅰ. 개요 및 필요성

- 개요: 변수화된 프롬프트 양식
- 배경: 프롬프트 엔지니어링이 팀 단위로 확산되면 하드코딩 문자열은 재현성·변경 이력·승인 절차를 남기기 어려움.
- 필요성: variable slot, version, test case, approval workflow로 템플릿 변경과 출력 품질을 관리해야 함.

---

## Ⅱ. 구조 및 구성요소

```text
  Static Section ->  Variable Slot ->  Output Format
  (역할·제약)         ({input})          (JSON·표)
```

| 구성요소 | 역할 | 특이사항 |
|:---|:---|:---|
| Static Section | 역할·톤·규칙 고정 | System Prompt와 통합 |
| Variable Slot | 런타임 입력 삽입 지점 | Jinja2·f-string·Mustache |
| Output Format | 출력 형식 지정 | JSON Schema·Markdown 표 |
| Guard Rail | 입력 검증·인젝션 방어 | 길이 제한·특수문자 이스케이프 |

> 요약: 템플릿은 고정 영역(역할·제약)과 변수 영역(입력·출력 포맷)을 분리하여 재사용성을 확보함.

---

## Ⅲ. 동작원리 및 흐름도

```text
템플릿 로드 -> 변수 바인딩 -> 입력 검증(Guard)
    -> 프롬프트 조립 -> LLM 호출 -> 출력 파싱
```

| 단계 | 처리 내용 | 검증 기준 |
|:---:|:---|:---|
| 1 | 템플릿 저장소에서 버전 로드 | 템플릿 ID·버전 해시 |
| 2 | 변수 바인딩·입력 검증 | 토큰 수 ≤ 예산, 인젝션 패턴 차단 |
| 3 | 프롬프트 조립·LLM 호출 | 총 토큰 수, 응답 시간 p95 |
| 4 | 출력 파싱·스키마 검증 | JSON Schema 적합률 98%+ |

> 요약: 템플릿 로드->변수 바인딩->검증->호출->파싱의 파이프라인으로 일관된 품질을 보장함.

---

## Ⅳ. 특징

| 구분 | 하드코딩 프롬프트 | 프롬프트 템플릿 | 판단 포인트 |
|:---|:---|:---|:---|
| 재사용성 | 복붙, 편차 발생 | 변수 치환, 일관성 유지 | 팀 3인 이상이면 템플릿 필수 |
| 버전 관리 | 불가능 | Git·레지스트리 관리 | A/B 테스트·롤백 가능 |
| 보안 | 인젝션 취약 | Guard Rail 내장 | 사용자 입력 직접 삽입 금지 |

> 요약: 템플릿은 재사용·버전관리·보안 세 축에서 하드코딩 대비 운영 성숙도를 높임.

---

## Ⅴ. 실무 적용 및 결론

**적용 방안 3개:**
1. LangChain PromptTemplate + Git 기반 레지스트리로 팀 공유, 버전 해시로 배포 추적
2. 변수 삽입 전 입력 길이 제한(4K 토큰)·특수문자 이스케이프·인젝션 패턴 필터 적용
3. 템플릿별 A/B 테스트 파이프라인 구축, F1·응답 시간·비용을 자동 비교 후 승격

**결론 (2줄):**
- 기술사 판단: 프롬프트 3개 이상 운영 시 템플릿 레지스트리 도입, 단일 용도면 인라인 유지
- 향후 방향: DSPy·Promptflow 등 자동 최적화 프레임워크와 통합되어 템플릿이 자동 진화하는 방향
