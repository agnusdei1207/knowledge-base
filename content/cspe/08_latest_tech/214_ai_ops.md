# 📖 【암기용】 개념 완전 이해

> 목적: AIOps를 처음 봐도 완벽히 이해하게 만든다. 시험 답안 양식이 아니라, 이해를 위한 친절한 설명이다.

## 한눈에
- **개요**: 빅데이터와 AI를 활용하여 IT 운영 프로세스(모니터링, 장애 탐지, 해결)를 자동화하고 지능화하는 체계
- **왜 필요한가**: 클라우드와 마이크로서비스(MSA) 도입으로 인프라가 너무 복잡해져서, 사람이 수천 개의 알람을 일일이 확인하고 원인을 찾는 것이 불가능해졌기 때문
- **핵심 직관**: 수많은 로그와 지표 속에서 "진짜 문제(원인)"를 AI가 대신 찾아주고, 나아가 장애가 터지기 전에 미리 예측하는 "똑똑한 관제 센터"

## 깊이 이해
- **배경·문제의식**: 고전적인 모니터링은 임계치(예: CPU > 90%)를 넘으면 알람을 보낸다. 하지만 수천 개의 서버에서 알람이 쏟아지면(Alert Fatigue), 정작 중요한 장애 원인을 놓치게 된다. 또한, 서비스 간 복잡한 의존성 때문에 어디가 문제인지 파악하는 데 많은 시간이 소요된다.
- **작동 원리**: 다양한 소스(로그, 메트릭, 트레이스)에서 데이터를 수집한 뒤, AI가 데이터 간 상관관계를 분석한다. 비슷한 알람들을 하나로 묶고(Event Correlation), 평소와 다른 패턴(Anomaly Detection)을 감지하며, 장애의 근본 원인(Root Cause)을 도출한다.
- **비유**: 병원에서 수많은 모니터 장비가 삐삐 소리를 낼 때, 숙련된 의사가 "이건 장비 오류고, 진짜 문제는 심장 박동이야"라고 짚어주는 과정을 AI가 수행하는 것과 같다.
- **구체 예시**: 웹 서비스 지연이 발생했을 때, AIOps 시스템이 "로그 분석 결과 DB 쿼리 속도는 정상이지만, 네트워크 패킷 손실이 급증했으므로 네트워크 장비를 점검하라"고 가이드를 제시한다.
- **흔한 오해·주의점**: AIOps는 단순한 자동화 스크립트가 아니다. 머신러닝 모델이 지속적으로 데이터를 학습하여 운영 환경의 변화에 적응하는 동적인 시스템이다.

## 연결 개념
- SRE (Site Reliability Engineering) — AIOps의 실행 주체이자 방법론
- Observability (관측성) — AIOps를 위한 고품질 데이터 공급원
- Self-Healing — AIOps의 최종 단계인 장애 자동 복구

# 📝 【답안용】 시험 답안 템플릿

> 목적: 시험장에서 25분에 그대로 쓰는 답안 양식. 작성방식(추상표현 금지·수치·도식·문제유형 전환)을 엄격히 지킨다.

## 핵심 인사이트 (3줄 요약)

> 1. **본질**: AIOps는 IT 운영 데이터(Log, Metric, Event)를 AI로 분석하여 장애 탐지·상관관계 분석·원인 파악을 자동화하는 지능형 운영 체계이다.
> 2. **가치**: 알람 피로도(Alert Fatigue) 해소, 장애 조치 시간(MTTR) 단축, 선제적 장애 예방을 통한 서비스 가용성을 극대화한다.
> 3. **판단 포인트**: 단순 임계치 관제에서 벗어나 동적 임계치(Dynamic Threshold)와 이벤트 상관분석 기반의 정밀 관제로 전환해야 한다.

## 출제 의도 및 답안 포인트

| 출제 의도 | 반드시 짚을 핵심 | 감점 회피 포인트 |
|:---|:---|:---|
| IT 운영 복잡도 해결 역량 확인 | 상관관계 분석(Correlation), 원인 분석(RCA), 이상 탐지 | 단순히 "AI로 운영 자동화"라고 추상적으로 기술 |
| AIOps 구성 요소 및 기술 이해 확인 | 데이터 수집(Log/Metric), 분석(ML), 시각화, 대응 | 데이터 소스 종류와 ML 모델 역할을 분리하지 못함 |
| 운영 지표 개선 효과 제시 확인 | MTTR 감소, Noise 제거율, 예측 정확도 | "성능이 좋아짐"과 같은 모호한 효과 서술 |

> 요약: 복잡한 인프라 환경에서 AI를 활용해 소음(Noise)을 줄이고 핵심 장애 신호를 식별하는 메커니즘 제시가 핵심이다.

## Ⅰ. 개요 및 필요성

- 정의: 머신러닝과 빅데이터 분석을 통해 IT 서비스 운영 프로세스를 지능화하고 자동화하는 프레임워크
- 배경: 클라우드·MSA 전환으로 인한 데이터 폭증, 사람이 수동으로 관제하기 불가능한 운영 복잡성 임계치 도달
- 필요성: 장애 대응 시간(MTTR) 단축, 불필요한 알람 억제(Noise Reduction), 선제적 장애 예측을 통한 무중단 서비스 구현

---

## Ⅱ. 구조 및 구성요소

```text
Data Sources (Log/Metric/Trace) -> Data Ingestion & Preprocessing
                                           |
               Remediation (Auto-recovery) <- ML Analytics (Anomaly/Correlation/RCA)
                                           |
                              Dashboards & Alerting (Visibility)
```

| 구성요소 | 역할 | 특이사항 |
|:---|:---|:---|
| Data Ingestion | 다양한 소스의 비정형 데이터 수집 | Kafka, Elastic Stack 연동 |
| Anomaly Detection | 과거 데이터를 학습하여 이상 패턴 감지 | Unsupervised Learning 기반 |
| Event Correlation | 연관된 중복 알람을 그룹화하여 소음 제거 | Clustering, Graph Analysis |
| RCA Engine | 장애의 근본 원인 분석 및 추천 | 결정 트리, 인과 분석 모델 |

> 요약: 데이터 수집부터 AI 기반 상관 분석 및 원인 도출을 거쳐 자동 복구까지 연결되는 선순환 구조임.

---

## Ⅲ. 동작원리 및 흐름도

```text
실시간 지표 수집 -> 동적 임계치 비교 -> 이상 징후 포착 -> 연관 이벤트 그룹화 -> 근본 원인(RCA) 도출 -> 조치 권고/자동 복구
      |                 |                |                 |                   |                   |
      +-----------------+----------------+-----------------+-------------------+-------------------+-----> 학습 데이터 축적
```

| 단계 | 처리 내용 | 검증 기준 |
|:---:|:---|:---|
| 1 | 메트릭/로그 실시간 수집 및 파싱 | 수집 지연 10초 이내 |
| 2 | ML 기반 동적 임계치 적용 | 계절성(Seasonality) 반영 여부 |
| 3 | 알람 소음 제거 및 상관 분석 | 중복 알람 90% 이상 억제 |
| 4 | 장애 원인 진단 및 조치 실행 | RCA 정확도 85% 이상 |

> 요약: 정적인 규칙 대신 데이터 기반의 동적 패턴을 분석하여 장애 전조를 포착하고 원인을 정밀 진단함.

## Ⅳ. 특징

| 구분 | 고전적 모니터링 | AIOps | 판단 포인트 |
|:---|:---|:---|:---|
| 분석 방식 | Rule/Threshold 기반 | ML/Pattern 기반 | 정적 vs 동적 |
| 대응 시점 | 장애 발생 후 (Reactive) | 장애 발생 전 (Proactive) | 사전 예측 가능성 |
| 데이터 활용 | 단일 지표 중심 (Silo) | 상관 지표 통합 (Holistic) | 데이터 연계성 |
| 운영 부하 | 수동 확인 및 조치 | 자동 분류 및 조치 추천 | 사람의 개입 정도 |

> 요약: AIOps는 전방위적 데이터 통합 분석을 통해 장애 대응의 패러다임을 사후 조치에서 사전 예방으로 전환함.

## Ⅴ. 심화 비교 및 적용 판단

| 비교 축 | Domain-Agnostic (범용) | Domain-Specific (전용) | 선택 기준 |
|:---|:---|:---|:---|
| 적용 범위 | IT 전반 인프라 통합 | 특정 벤더 장비/DB 집중 | 통합 관제 vs 심층 관제 |
| 구축 비용 | 높음 (데이터 정제 필수) | 낮음 (빌트인 모델 제공) | 가용 예산 및 인력 |
| 유연성 | 높음 (커스텀 모델 가능) | 낮음 (종속성 높음) | 인프라 이질성 정도 |

> 요약: 전사 통합 관제가 목표면 범용 AIOps를, 핵심 자산(예: DB)의 집중 관리가 필요하면 전용 툴을 선택함.

| 리스크 | 원인 | 대응 방안 | 확인 지표 |
|:---|:---|:---|:---|
| 데이터 품질 저하 | 부정확한 로그 및 누락 지표 | 데이터 파이프라인 정제 강화 | 데이터 정합성 99% 이상 |
| False Positive | 과도하게 민감한 ML 모델 | 피드백 기반 모델 재학습(RL) | 오탐률(False Alarm Rate) |
| 자동화 오류 | 검증되지 않은 복구 스크립트 | 단계적 자동화(Human-in-the-loop) | 자동 복구 성공률 |

> 요약: 데이터 품질은 정제로, 오탐은 피드백 학습으로, 자동화 리스크는 단계적 도입으로 해결함.

| 점검 항목 | 목표 기준 | 측정 방법 |
|:---|:---|:---|
| 알람 노이즈 제거율 | 중복/불필요 알람 90% 감소 | 도입 전후 알람 발생 수 대조 |
| MTTR 단축 | 평균 복구 시간 50% 단축 | 장애 발생~종료 로그 분석 |
| 장애 예측 정확도 | 주요 장애 80% 사전 예측 | 실제 장애 대비 사전 알람 일치율 |

> 요약: 도입 효과는 알람 노이즈 감소, 복구 시간(MTTR) 단축, 사전 예측 적중률로 측정함.

## Ⅵ. 실무 적용 및 결론

**적용 방안 3개:**
1. 알람 피로도 개선: Clustering 알고리즘을 적용하여 초당 수천 개의 중복 이벤트를 단일 장애 인시던트로 그룹화하여 Noise 95% 제거
2. 지능형 RCA 구축: 서비스 토폴로지(Topology) 맵과 연동된 인과 분석 모델을 활용하여 장애 원인 파악 시간을 30분에서 3분으로 단축
3. 선제적 용량 관리: 시계열 예측(LSTM 등) 모델을 통해 트래픽 급증을 사전 감지하고 클라우드 오토스케일링과 연동하여 서비스 중단 방지

**결론 (2줄):**
- 기술사 판단: AIOps는 단순히 사람을 대체하는 것이 아니라, 사람이 더 복잡한 아키텍처를 안정적으로 운영하게 돕는 "운영의 증강"임
- 향후 방향: 생성형 AI와 결합하여 장애 로그를 자연어로 요약하고 해결 가이드를 자동 생성하는 "ChatOps" 형태로 고도화될 것임
