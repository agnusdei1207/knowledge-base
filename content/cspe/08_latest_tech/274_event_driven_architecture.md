# 📖 【암기용】 개념 완전 이해

> 목적: EDA를 처음 봐도 완벽히 이해하게 만든다. 시험 답안 양식이 아니라, 이해를 위한 친절한 설명이다.

## 한눈에
- **개요**: 시스템의 상태 변화(이벤트)를 감지하고, 이를 비동기적으로 전달하여 다른 서비스들이 반응하게 만드는 아키텍처 스타일
- **왜 필요한가**: 서비스들이 서로를 직접 부르는 방식(Request-Response)은 한 곳이 죽으면 줄줄이 죽는 "강한 결합" 문제를 일으킨다. 이를 끊어내고 유연한 시스템을 만들기 위해 이벤트가 필요하다.
- **핵심 직관**: "주문이 완료되었습니다"라는 사실(이벤트)을 방송국(메시지 브로커)에 알리면, 필요한 사람(결제, 배송, 알림 서비스)들이 각자 알아서 듣고 자기 할 일을 하는 방식이다.

## 깊이 이해
- **배경·문제의식**: MSA 환경에서 서비스 간 의존성이 복잡해지면 성능 저하와 장애 전파가 심각해진다. 또한 실시간 데이터 처리 요구가 늘어나면서 데이터를 쌓아두고 한꺼번에 처리(Batch)하는 대신, 발생하는 즉시 처리(Stream)하는 방식이 중요해졌다.
- **작동 원리**: **생성자(Producer)**는 이벤트를 발행만 하고 누가 읽을지 신경 쓰지 않는다. **브로커(Broker)**는 이벤트를 저장하고 전달한다. **소비자(Consumer)**는 관심 있는 이벤트만 골라서 처리한다. 이 과정은 모두 비동기(Asynchronous)로 이루어진다.
- **비유**: 트위터(X)나 유튜브 구독과 같다. 내가 글을 쓰거나 영상을 올리면(이벤트 발생), 팔로워나 구독자(소비자)들은 각자 알림을 받고 내용을 확인한다. 나는 누가 내 글을 보는지 일일이 확인하지 않아도 된다.
- **구체 예시**: 쇼핑몰 결제 완료 시 -> [포인트 적립] 서비스와 [카카오톡 알림] 서비스가 동시에 각자 동작.
- **흔한 오해·주의점**: "메시지 기반 아키텍처"와 비슷해 보이지만, 메시지는 특정 대상을 향한 '명령'인 경우가 많고, 이벤트는 이미 벌어진 '사실'의 기록이라는 점이 다르다.

## 연결 개념
- Message Broker (Kafka, RabbitMQ) — 이벤트 전달의 핵심 인프라
- Event Sourcing — 데이터의 현재 상태가 아닌 모든 변경 이력을 저장하는 방식
- CQRS — 명령(쓰기)과 조회(읽기)의 책임을 분리하여 성능을 높이는 패턴
- Serverless (FaaS) — 이벤트 발생 시에만 함수를 실행하는 EDA의 극단적 형태

# 📝 【답안용】 시험 답안 템플릿

> 목적: 시험장에서 25분에 그대로 쓰는 답안 양식. 작성방식(추상표현 금지·수치·도식·문제유형 전환)을 엄격히 지킨다.
> 핵심: 이벤트 기반 아키텍처의 비동기적 느슨한 결합(Loose Coupling)과 실시간 스트리밍 처리 관점을 기술한다.

## 핵심 인사이트 (3줄 요약)

> 1. **본질**: EDA는 시스템 상태의 유의미한 변화인 '이벤트'를 생성, 감지, 소비하여 컴포넌트 간 비동기적 통신을 수행하는 분산 아키텍처이다.
> 2. **가치**: 서비스 간 강한 결합(Strong Coupling)을 제거하여 장애 격리와 독립적 확장을 가능케 하며, 실시간 데이터 스트리밍 처리에 최적화되어 있다.
> 3. **판단 포인트**: 데이터 정합성을 보장하기 위한 최종 일관성(Eventual Consistency) 관리와 이벤트 스키마 거버넌스가 성공의 핵심이다.

## 출제 의도 및 답안 포인트

| 출제 의도 | 반드시 짚을 핵심 | 감점 회피 포인트 |
|:---|:---|:---|
| 서비스 간 결합도 제어 능력 확인 | 느슨한 결합(Loose Coupling), 비동기성, 브로커의 역할 | 단순히 "비동기 통신"으로만 뭉뚱그려 서술 |
| 데이터 정합성 유지 전략 확인 | 최종 일관성, Saga 패턴, Idempotency(멱등성) | 정합성 문제에 대한 구체적 대안 누락 |
| 실시간 처리 및 확장성 이해 확인 | Fan-out 구조, 오토스케일링, 배압 제어 | 전통적 Batch 방식과의 차별점 부각 미흡 |

> 요약: 장애 전이를 차단하고 유연한 확장을 제공하는 비동기 이벤트 흐름 설계 능력을 중점적으로 서술한다.

## Ⅰ. 개요 및 필요성

- 정의: 시스템 내외의 상태 변화를 '이벤트'로 정의하고, 이를 비동기 메시지 형태로 교환하여 분산된 구성요소들이 협력하는 아키텍처
- 배경: 동기식 호출(REST/gRPC) 기반 MSA의 서비스 체인(Service Chain) 심화로 인한 Latency 누적 및 장애 전파 리스크 급증
- 필요성: 실시간 비즈니스 인텔리전스 요구 증가와 고가용성·고확장성 클라우드 네이티브 환경으로의 전환 가속화

---

## Ⅱ. 구조 및 구성요소

```text
Event Producer -> Event Channel (Topic) -> Event Consumer A (Update DB)
     |                 | (Pub/Sub)      -> Event Consumer B (Send SMS)
     +-> State Change  +-> Persistence  -> Event Consumer C (Analyze)

[핵심 컴포넌트: Producer, Broker, Consumer, Event Store]
```

| 구성요소 | 역할 | 특이사항 |
|:---|:---|:---|
| Event Producer | 상태 변화 감지 및 이벤트 발행 | 소비자의 존재를 알 필요 없음 |
| Event Broker | 이벤트를 수집, 보관, 라우팅 | Kafka, RabbitMQ, EventBridge 등 |
| Event Consumer | 관심 있는 이벤트를 구독하여 로직 수행 | 자신의 속도에 맞춰 메시지 처리 |
| Event Schema | 이벤트 데이터의 구조와 규격 정의 | Avro, JSON Schema, Protobuf |

> 요약: 발행자와 구독자가 브로커를 통해 철저히 분리(Decoupling)된 형태를 띤다.

---

## Ⅲ. 동작원리 및 흐름도

```text
[동작 흐름: 발생 -> 저장 -> 전달 -> 처리]
Capture Event -> Append to Log (Broker) -> Push/Pull to Consumer
      |                |                       |
   Validation       Durability            Processing & Ack
```

| 단계 | 처리 내용 | 검증 기준 |
|:---:|:---|:---|
| 1 | 이벤트 생성 | 비즈니스 트랜잭션 성공 시 관련 사실을 이벤트로 캡처 |
| 2 | 이벤트 중계 | 브로커가 순서를 보장하여 이벤트를 저장하고 구독자에게 노출 |
| 3 | 이벤트 소비 | 소비자가 이벤트를 읽어 로직을 수행하고 완료 처리(Ack) |
| 4 | 결과 수렴 | 각 서비스의 처리가 완료되어 시스템이 최종 일관성 상태에 도달 |

> 요약: '사실의 기록'인 이벤트를 중심에 두고 비동기적으로 상태를 전파하고 동기화한다.

## Ⅳ. 특징

| 구분 | 내용 | 판단 포인트 |
|:---|:---|:---|
| 유연성 | 새로운 소비자(서비스) 추가 시 기존 시스템 수정 불필요 | 플러그인 스타일 확장성 |
| 가용성 | 소비자가 일시 정지되어도 브로커에 메시지 보관되어 유실 방지 | 장애 복원력(Resilience) |
| 성능 | 요청-응답 대기 시간이 없어 사용자 체감 응답 속도 향상 | 비동기 논블로킹 효과 |
| 복잡성 | 분산 트랜잭션 관리 및 흐름 추적의 어려움 | 분산 추적(Tracing) 도구 필수 |

> 요약: 시스템의 '반응성'과 '확장성'을 극대화하는 대신 '추적성'과 '일관성' 관리 비용을 지불한다.

## Ⅴ. 심화 비교 및 적용 판단

| 구분 | Request-Response (REST) | Event-Driven (Pub/Sub) | 선택 기준 |
|:---|:---|:---|:---|
| 결합도 | 강함 (주소, 인터페이스 의존) | 느슨함 (이벤트 규격에만 의존) | 시스템 변경 빈도 |
| 응답성 | 동기적 (결과 즉시 확인) | 비동기적 (결과 지연 확인) | 즉시 응답 필요성 |
| 장애 영향 | 전이됨 (Cascading Failure) | 차단됨 (Isolation) | 무중단 서비스 목표 |

> 요약: 즉각적인 결과 확인이 필요한 조회는 REST, 후속 처리가 많은 변경은 EDA가 유리하다.

| 리스크 | 원인 | 대응 방안 | 확인 지표 |
|:---|:---|:---|:---|
| 메시지 중복 처리 | 네트워크 오류로 인한 재전송 | 멱등성(Idempotency) 보장 설계 | 중복 처리 오류 발생 건수 |
| 이벤트 순서 뒤바뀜 | 분산 파티션 처리 시 순서 역전 | 시퀀스 번호 또는 파티션 키 활용 | 데이터 선후 관계 정합성 |
| 추적의 난해함 | 이벤트 흐름이 눈에 보이지 않음 | Correlation ID 및 분기별 로깅 | End-to-End 지연 시간 |

> 요약: 중복 방지와 순서 보장, 그리고 통합 모니터링 체계 구축이 실무 적용의 핵심이다.

| 점검 항목 | 목표 기준 | 측정 방법 |
|:---|:---|:---|
| 소비자 지연 (Lag) | 메시지 생성 대비 소비 지연 1초 미만 | 브로커 모니터링 (Kafka Lag 등) |
| 처리량 (Throughput) | 초당 10만 건 이상의 이벤트 처리 | 부하 테스트 결과 수치 |
| 정합성 복구 시간 | 최종 일관성 도달 시간 5초 이내 | 서비스 간 데이터 동기화 확인 |

> 요약: 처리량과 함께 지연 시간(Lag)을 핵심 지표로 관리해야 한다.

## Ⅵ. 실무 적용 및 결론

**적용 방안 3개:**
1. Transactional Outbox 패턴: DB 업데이트와 이벤트 발행을 하나의 트랜잭션으로 묶어 메시지 유실 방지
2. Saga 패턴 연계: 분산 트랜잭션 대신 이벤트를 주고받으며 실패 시 보상 트랜잭션(Compensating Transaction) 실행
3. 데이터 스트리밍 분석: 사용자 행동 이벤트를 실시간으로 분석 시스템(Flink 등)에 전달하여 개인화 추천 제공

**결론 (2줄):**
- 기술사 판단: EDA는 MSA의 복잡성을 해결하고 '실시간성'이라는 비즈니스 가치를 창출하는 현대 아키텍처의 중추(Backbone)이다.
- 향후 방향: 클라우드 네이티브를 넘어 엣지 컴퓨팅까지 이벤트를 확장하는 Event Mesh 기술이 주목받을 것이다.
