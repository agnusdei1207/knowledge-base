# 📖 【암기용】 개념 완전 이해

> 목적: 마이크로서비스들이 서로 직접 호출(API)하며 거대한 스파게티 덩어리가 되는 것을 막기 위해, '이벤트(사건)'를 중앙에 던지고 각자 알아서 주워가는 극단적인 결합도 분리(Decoupling) 패턴을 이해한다.

## 한눈에
- **정의**: 시스템의 상태 변화(Event)가 발생하면, 이를 메시지 형태로 발행(Publish)하고 관심 있는 다른 시스템이 이를 구독(Subscribe)하여 후속 작업을 처리하는 **비동기 분산 아키텍처 패턴**
- **필요성**: 주문 서비스가 결제, 재고, 배송 API를 직접 호출하면(동기 방식), 배송 서버가 죽었을 때 주문 서버까지 같이 죽어버리는 도미노 현상(장애 전파)이 발생하기 때문
- **핵심 직관**: "동기 API 통신이 '전화'라면(안 받으면 꼼짝없이 기다려야 함), EDA는 '사내 게시판'이다. 주문팀이 게시판에 '주문 들어옴!'이라고 붙여놓고 퇴근하면, 배송팀과 결제팀이 나중에 출근해서 그 메모를 보고 각자 할 일을 하는 것."

## 깊이 이해
- **배경(왜 등장했나?)**: 마이크로서비스(MSA)를 도입했더니 100개의 서비스가 서로 거미줄처럼 REST API를 쏘며 얽혔다(API Sprawl). 서비스 A가 B를 부르고 B가 C를 부르는데 C가 10초 걸리면, A도 10초 동안 멈춰 있어야 했다. 이런 지옥을 벗어나기 위해 넷플릭스, 우버 등은 시스템 중간에 거대한 메시지 큐(Kafka)를 놓고, 모든 통신을 비동기 이벤트로 바꿨다.
- **작동 원리(어떻게 달성했나?)**: 
  1. **Event Producer (생산자)**: 고객이 결제 버튼을 누르면, 주문 서비스는 Kafka(이벤트 브로커)에 `{"이벤트명": "OrderCreated", "금액": 5000}`이라는 쪽지를 던지고 즉시 "주문 완료!" 응답을 반환한다. (자신의 역할 끝)
  2. **Event Broker (브로커)**: 이 쪽지(이벤트)를 안전하게 보관한다. (Kafka, RabbitMQ)
  3. **Event Consumer (소비자)**: 결제 서버, 재고 서버, 배송 서버는 Kafka를 계속 쳐다보다가 `OrderCreated` 쪽지가 올라오면, 각자 자기가 할 일(결제 승인, 재고 차감, 송장 출력)을 비동기적으로 처리한다.
- **일상 비유**: 유튜버(Producer)가 영상을 올릴 때마다 구독자 100만 명(Consumer)에게 일일이 카톡을 보내는 게 아니다. 그냥 유튜브 서버(Broker)에 올리면(Publish), 알림 설정을 해둔 구독자들이 알아서 각자의 시간에 영상을 시청한다(Subscribe).
- **구체 예시**: 배달의민족 앱에서 주문을 하면 즉시 '주문 접수 대기 중' 화면이 뜬다. 백단에서는 이벤트가 발행되어 식당 포스기 알림, 라이더 배차 시스템 등에 비동기로 쫙 뿌려지고 있는 것이다.
- **흔한 오해/주의점**: "EDA는 무조건 빠르고 좋은가?" → 아니다! 사용자가 결제 버튼을 눌렀는데 잔액 부족으로 결제가 실패했다면? 이미 주문 서버는 "주문 성공"을 띄운 상태다. 이처럼 데이터 상태를 되돌리는 것(Saga 패턴, 보상 트랜잭션)이 엄청나게 복잡해지는 치명적인 단점이 있다.

## 연결 개념
- **Apache Kafka**: 이벤트 기반 아키텍처를 구현하기 위한 전 세계 1위의 이벤트 브로커 플랫폼.
- **MSA (Microservices Architecture)**: EDA가 필수적으로 요구되는 분산 시스템. MSA의 완성은 EDA다.
- **CQRS (Command and Query Responsibility Segregation)**: EDA와 찰떡궁합인 패턴. 데이터 변경(Command)은 이벤트를 쏴서 처리하고, 조회(Query)는 별도의 DB에서 읽어오는 아키텍처.

# 📝 【답안용】 시험 답안 템플릿

## 핵심 인사이트 (3줄 요약)
> 1. **본질**: 이벤트 기반 아키텍처(EDA)는 시스템 간의 상태 변경(Event)을 비동기적 Pub/Sub 모델로 전달하여, 마이크로서비스 간의 시공간적 결합도를 극단적으로 낮추는(Decoupling) 아키텍처 패턴이다.
> 2. **가치**: 특정 컴포넌트의 장애가 전체 시스템으로 전파되지 않게 격리(Resilient)하며, 이벤트 브로커를 통한 버퍼링으로 대규모 트래픽 스파이크(Spike) 상황에서도 백엔드 시스템을 보호한다.
> 3. **판단 포인트**: 도입 시 데이터의 최종적 일관성(Eventual Consistency) 모델을 반드시 수용해야 하며, 2PC(2-Phase Commit)의 대안인 Saga 패턴 적용 및 메시지 순서 보장 전략이 핵심 아키텍처 과제가 된다.

## Ⅰ. 개요 및 필요성
- **정의**: 비즈니스 상태의 유의미한 변화(Event)를 생성, 라우팅, 소비하는 흐름을 중심으로 시스템을 구성하는 비동기 통신 기반의 소프트웨어 아키텍처
- **배경**: MSA 환경에서 Point-to-Point(REST API, gRPC) 동기식 통신이 유발하는 장애 결합(Cascading Failure) 및 응답 지연 누적(Latency Accumulation) 문제 심화
- **필요성**: 서비스 확장의 유연성(Plug & Play) 확보, 대용량 트래픽 처리 시 논블로킹(Non-blocking)을 통한 시스템 응답성 극대화, 데이터 분석을 위한 실시간 스트리밍 기반 마련

## Ⅱ. EDA의 3대 핵심 구성요소 및 동작 방식
```text
┌──────────────┐         ┌────────────────────────┐         ┌──────────────┐
│  Event       │ (발행)  │      Event Broker      │ (구독)  │  Event       │
│  Producer    ├────────▶│    (Kafka, RabbitMQ)   ├────────▶│  Consumer    │
│  (주문 MS)    │         │ (메시지 큐 / 이벤트 로그)│         │  (결제 MS)    │
└──────────────┘         └──────────┬─────────────┘         └──────────────┘
                                    │
                                    └─────────▶ ┌──────────────┐
                                       (구독)   │  Event       │
                                                │  Consumer    │
                                                │  (배송 MS)    │
                                                └──────────────┘
```
1. **Event Producer (생산자)**: 상태 변화를 감지하고 이벤트를 발행. 컨슈머가 누군지, 몇 명인지 전혀 모름(완벽한 결합도 분리).
2. **Event Broker (브로커)**: 이벤트를 수신하여 안전하게 영속화(Persistence)하고, 구독자에게 라우팅하거나 스트림을 제공함.
3. **Event Consumer (소비자)**: 브로커를 구독(Subscribe)하며 이벤트를 수신하고 자신의 도메인 로직을 비동기적으로 수행.

## Ⅲ. 기존 동기식 아키텍처(REST) vs 이벤트 기반 아키텍처(EDA) 비교
| 비교 지표 | Request/Response (REST API) | Event-Driven (Pub/Sub) |
|:---|:---|:---|
| **통신 방식** | 동기식(Synchronous), Point-to-Point | **비동기식(Asynchronous), 1:N / N:M 통신** |
| **결합도** | 높음 (타겟 IP/도메인을 알아야 함) | **매우 낮음 (브로커만 알면 됨, Decoupling)** |
| **장애 영향** | B 서버 장애 시 A 서버도 응답 대기로 마비 | **B 서버가 죽어도 브로커에 메시지 대기(격리)** |
| **트랜잭션** | ACID 트랜잭션, 2PC 가능 (RDBMS) | **BASE 기반, Eventual Consistency 보장** |

## Ⅳ. EDA 구현을 위한 주요 토폴로지 (Topology)
이벤트 브로커가 메시지를 어떻게 다루느냐에 따라 2가지로 나뉜다.
1. **브로커 토폴로지 (Broker Topology)**
   - 중앙의 컨트롤러(오케스트레이터) 없이, 각 서비스가 이벤트를 릴레이(Relay) 방식으로 연쇄적으로 발행하는 체인(Chain) 형태. (구현이 쉽지만 전체 흐름(Workflow) 추적이 어려움)
2. **미디에이터 토폴로지 (Mediator Topology)**
   - 중앙에 '이벤트 중재자(Mediator)'가 존재하여, 여러 단계로 이루어진 복잡한 이벤트(예: 결제 ➔ 재고 ➔ 배송 완료)의 오케스트레이션과 상태를 멱등성 있게 통제함.

## Ⅴ. 기술적 한계(리스크) 및 데이터 일관성 해결 전략
EDA는 통신이 분리되는 만큼 '데이터 정합성 보장'이 가장 큰 리스크다.

| 리스크 요인 | 현상 및 문제점 | 해결 패턴 및 가이드 |
|:---|:---|:---|
| **분산 트랜잭션 불가** | 결제는 성공했는데 재고 차감 이벤트가 실패한 경우, DB 롤백이 불가능함 | **Saga Pattern (보상 트랜잭션)**: 재고 차감 실패 시 역으로 '결제 취소 이벤트'를 발행하여 논리적 롤백 수행 |
| **메시지 유실 및 중복**| 네트워크 단절로 이벤트가 증발하거나, 브로커 재시도로 동일 이벤트가 2번 들어옴 | **Outbox Pattern**으로 DB와 이벤트를 원자적으로 저장하고, 컨슈머는 **멱등성(Idempotency)** 기반으로 코딩 |
| **이벤트 순서 꼬임** | '생성' 이벤트보다 '수정' 이벤트가 브로커 지연으로 먼저 도착하여 데이터 오염 | **Kafka Partition Key**를 주문ID 등으로 고정하여 동일 엔티티의 순서를 엄격히 보장 |

## Ⅵ. 실무 적용 및 결론
**적용 방안 및 실무 가이드:**
1. **CQRS 패턴과의 결합**: 데이터 쓰기(Command) 로직에서 이벤트를 발행하면, 여러 개의 읽기(Query) 전용 DB들이 이벤트를 구독하여 데이터를 자신들의 입맛에 맞게(ElasticSearch, Redis) 동기화하는 아키텍처로 확장해야 한다.
2. **Dead Letter Queue (DLQ) 구성**: 소비자가 처리에 실패한 이벤트를 영원히 재시도하면 큐가 막혀버린다. 실패 횟수가 초과한 이벤트는 별도의 에러 보관함(DLQ)으로 빼내어 관리자가 수동으로 재처리하도록 구성해야 한다.

**결론:**
- 이벤트 기반 아키텍처는 MSA의 단점(통신 복잡성, 장애 전파)을 해결하고 대규모 클라우드 시스템에 '탄력성'과 '회복성'을 불어넣는 **사실상의 표준(De-facto Standard)**이다.
- 완벽한 실시간(Real-time) 일관성을 포기하고 **최종적 일관성(Eventual Consistency)**을 받아들이는 비즈니스적 타협이 선행될 때, EDA는 그 어떤 시스템보다 유연하고 견고한 위력을 발휘한다.
