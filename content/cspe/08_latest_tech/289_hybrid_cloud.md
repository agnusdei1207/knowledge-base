# 📖 【암기용】 개념 완전 이해

> 목적: 하이브리드 클라우드를 온프레미스와 퍼블릭 클라우드를 섞어 쓰는 단순 조합이 아니라, 워크로드와 데이터를 이동 가능하게 묶는 배치 전략으로 이해하게 만든다.

## 한눈에
- **개요**: 서로 다른 클라우드와 온프레미스를 연결해 워크로드를 배치·이동하는 운영 모델
- **왜 필요한가**: 규제 데이터, 기존 시스템, 급증 트래픽, 비용 구조가 서로 달라 모든 업무를 한 클라우드에 둘 수 없다.
- **핵심 직관**: 사내 금고, 외부 창고, 임시 행사장을 연결하고 물건 성격에 따라 보관 위치를 바꾸는 방식이다.

## 깊이 이해
- **배경·문제의식**: 핵심 업무는 전용망·레거시 DB·규제 통제가 필요하고, 웹·분석·AI 업무는 퍼블릭 클라우드 자원 탄력성이 필요하다.
- **작동 원리**: 네트워크 연결, 통합 IAM, 데이터 동기화, 공통 운영도구를 통해 온프레미스·프라이빗·퍼블릭 클라우드를 하나의 배치 풀처럼 운영한다.
- **비유**: 병원이 중환자실은 자체 시설에 두고, 대량 검사는 외부 전문기관에 보내며, 예약 시스템은 클라우드로 운영하는 것과 같다.
- **구체 예시**: 개인정보 원천 DB는 사내망에 두고, 비식별 로그 분석은 퍼블릭 클라우드 Spark·Object Storage에서 수행한다.
- **흔한 오해·주의점**: 하이브리드는 두 환경을 동시에 쓰는 상태만 뜻하지 않는다. 표준화된 연결과 운영 통제가 없으면 단순 이중 운영이 된다.

## 연결 개념
- Multi Cloud — 여러 퍼블릭 클라우드 조합 중심
- Cloud Migration 6R — 워크로드별 이전 방식 판단
- Sovereign Cloud — 데이터 주권 요구가 강한 하이브리드 배치 축

# 📝 【답안용】 시험 답안 템플릿

> 목적: 시험장에서 25분에 그대로 쓰는 답안 양식.
> 핵심: 하이브리드 클라우드는 배치 위치가 아니라 워크로드 적합성, 연결 구조, 운영 통제 기준으로 설명해야 함.

## 핵심 인사이트 (3줄 요약)

> 1. **본질**: Hybrid Cloud는 프라이빗·퍼블릭·온프레미스 환경을 연결해 데이터와 애플리케이션 이동성을 확보하는 배치 모델임.
> 2. **가치**: 규제·지연시간·비용·탄력성 조건이 다른 워크로드를 단일 기준이 아니라 위치별 최적 배치로 처리함.
> 3. **판단 포인트**: 네트워크 지연, 데이터 동기화, IAM 일관성, 운영도구 표준화가 설계 성패를 결정함.

## 출제 의도 및 답안 포인트

| 출제 의도 | 반드시 짚을 핵심 | 감점 회피 포인트 |
|:---|:---|:---|
| 클라우드 배치 모델 이해 확인 | NIST 배치 모델, 온프레미스·프라이빗·퍼블릭 결합 | 단순 이중 운영으로 설명 |
| 워크로드 배치 판단 확인 | 규제, 지연시간, 데이터 중력, 비용 예측성 | 모든 업무의 클라우드 이전으로 단정 |
| 운영 리스크 인식 확인 | 네트워크, IAM, 데이터 동기화, 관측성 | 연결망만 쓰고 운영 통제 누락 |

> 요약: 이 문제는 배치 모델 정의보다 워크로드별 위치 선택과 통합 운영 기준을 요구한다.

---

## Ⅰ. 개요 및 필요성

- 개요: 이기종 클라우드 결합 운영
- 배경: 레거시 핵심 시스템, 규제 데이터, 클라우드 탄력 업무가 한 배치 모델 안에 공존함.
- 필요성: 업무별 RTO/RPO, 데이터 위치, p95 지연시간, 월간 비용 예측성을 기준으로 실행 위치를 나눠야 함.

---

## Ⅱ. 구조 및 구성요소

```text
On-Prem / Private Cloud / Public Cloud
  +-> Network Interconnect -> Common IAM -> Policy / Monitoring
  +-> Data Sync -> Workload Placement -> Service Delivery
```

| 구성요소 | 역할 | 특이사항 |
|:---|:---|:---|
| 연결망 | 전용회선·VPN으로 환경 간 통신 제공 | 지연시간과 대역폭이 배치 기준 |
| 통합 IAM | 사용자·서비스 계정 인증과 권한 연계 | SSO, federation, RBAC |
| 데이터 계층 | 복제·동기화·백업 정책 수행 | RPO와 데이터 위치 기준 필요 |
| 운영 계층 | 모니터링·배포·정책을 공통 적용 | IaC, 로그, CMDB 연계 |

> 요약: 하이브리드 클라우드는 연결망, IAM, 데이터, 운영 계층을 묶어 워크로드를 위치별로 제어한다.

---

## Ⅲ. 동작원리 및 흐름도

```text
업무 요구 식별 -> 데이터 등급 분류 -> 실행 위치 결정
-> 네트워크 / IAM 연결 -> 데이터 동기화 -> 운영 지표 측정
```

| 단계 | 처리 내용 | 검증 기준 |
|:---:|:---|:---|
| 1 | 업무 중요도, 규제, 지연시간 요구 식별 | 업무 등급표 |
| 2 | 데이터 위치와 전송 가능 범위 결정 | 개인정보·기밀 등급 |
| 3 | 온프레미스·프라이빗·퍼블릭 실행 위치 선택 | 비용, p95 지연, RTO/RPO |
| 4 | 연결·인증·관측성 통합 적용 | 장애 추적, 권한 감사 |

> 요약: 하이브리드 운영은 업무 요구와 데이터 등급을 먼저 정하고 연결·인증·관측 기준을 맞추는 순서로 동작한다.

---

## Ⅳ. 특징

| 구분 | 단일 클라우드 | Hybrid Cloud | 판단 기준 |
|:---|:---|:---|:---|
| 배치 | 한 공급자 중심 | 업무별 위치 분산 | 규제·지연시간 |
| 데이터 | 이동 경로 단순 | 동기화·복제 설계 필요 | RPO·전송 비용 |
| 운영 | 도구 일원화 용이 | 공통 운영 표준 필요 | IaC·관측성 범위 |
| 위험 | 공급자 종속 | 운영 복잡도 증가 | 책임 경계 문서화 |

> 요약: 하이브리드는 배치 유연성을 주지만 데이터 동기화와 운영 표준을 별도로 설계해야 한다.

---

## Ⅴ. 심화 비교 및 적용 판단

| 비교 축 | 기존/대안 | 본 키워드 | 선택 기준 |
|:---|:---|:---|:---|
| 구조 | 온프레미스 단독 | 온프레미스+클라우드 결합 | 기존 DB 의존도와 탄력 수요 |
| 비용 | 고정 투자 중심 | 고정+사용량 과금 혼합 | 기준 부하와 피크 부하 차이 |
| 운영 | 내부 표준 단일 | 공급자별 API와 정책 병행 | 운영 자동화 수준 |

> 요약: 기준 부하는 내부에 두고 피크·분석·개발 업무는 퍼블릭 클라우드에 둘 때 하이브리드 가치가 명확하다.

| 리스크 | 원인 | 대응 방안 | 확인 지표 |
|:---|:---|:---|:---|
| 데이터 불일치 | 양방향 복제 충돌 | master source 지정 | sync lag |
| 지연시간 초과 | 클라우드 간 왕복 통신 | 서비스 근접 배치 | p95 latency |
| 권한 불일치 | IAM 정책 중복 관리 | federation·권한 리뷰 | orphan account |

> 요약: 주요 리스크는 데이터, 지연시간, 권한 경계에서 발생하며 단일 원천과 지표 기반 점검으로 통제한다.

| 점검 항목 | 목표 기준 | 측정 방법 |
|:---|:---|:---|
| 가용성 | 업무별 RTO/RPO 충족 | DR 리허설 |
| 비용 | 월 예산 대비 편차 추적 | FinOps 태그 리포트 |
| 운영 | 변경 실패율과 MTTR 관리 | 배포·장애 기록 |

> 요약: 도입 효과는 배치 유연성보다 RTO/RPO, 비용 편차, 장애 복구 지표로 판단한다.

## Ⅵ. 실무 적용 및 결론

**적용 방안 3개:**
1. 워크로드를 규제형, 저지연형, 탄력형, 분석형으로 분류하고 실행 위치와 데이터 이동 허용 범위를 문서화함.
2. 전용회선·VPN, SSO federation, IaC 모듈을 표준 구성으로 지정해 환경별 운영 편차를 줄임.
3. 비용 태그, p95 지연시간, RTO/RPO, sync lag를 공통 대시보드에서 측정해 배치 변경 근거로 사용함.

**결론 (2줄):**
- 기술사 판단: 규제 데이터와 레거시 결합도가 높으면 하이브리드, 신규 디지털 채널 중심이면 퍼블릭 우선 배치가 타당함.
- 향후 방향: 하이브리드는 Kubernetes, service mesh, 정책형 보안과 결합해 위치보다 정책 중심 운영으로 발전함.
