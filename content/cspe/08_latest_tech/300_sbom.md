# 📖 【암기용】 개념 완전 이해

> 목적: SBOM을 처음 봐도 완벽히 이해하게 만든다. 시험 답안 양식이 아니라, 이해를 위한 친절한 설명이다.

## 한눈에
- **개요**: 소프트웨어를 구성하는 모든 부품(오픈소스, 라이브러리, 모듈 등)의 목록과 이들의 관계, 버전 정보를 담은 명세서
- **왜 필요한가**: 우리가 쓰는 소프트웨어의 90% 이상이 오픈소스를 가져다 쓴다. 만약 특정 오픈소스에서 보안 문제가 터지면, 우리 소프트웨어의 어디에 그게 들어있는지 빨리 찾아야 대응할 수 있기 때문이다.
- **핵심 직관**: "소프트웨어를 위한 전 성분 표시제 (식품의 원재료 함량 표시와 동일)"

## 깊이 이해
- **배경·문제의식**: Log4j 사태처럼 널리 쓰이는 라이브러리에서 치명적인 취약점이 발견되었을 때, 기업들은 자사 서비스 중 무엇이 위험한지 파악하는 데만 수주가 걸렸다. 또한 소프트웨어 공급망 공격(Supply Chain Attack)이 늘어나면서 투명한 관리가 필수적이 되었다.
- **작동 원리**: **Generation -> Sharing -> Analysis**. ① Generation: 빌드 단계에서 자동으로 구성 요소 추출. ② Sharing: 표준 형식(SPDX, CycloneDX)으로 만들어 파트너사에 전달. ③ Analysis: 새로운 취약점(CVE)이 발표되면 SBOM과 대조하여 즉시 영향도 파악.
- **비유**: 편의점에서 파는 샌드위치에 식중독을 일으킨 'A 농장 토마토'가 들어갔는지 확인하려면, 샌드위치 포장지에 적힌 원재료 목록(SBOM)을 보면 바로 알 수 있는 것과 같다.
- **구체 예시**: 미국 바이든 대통령의 행정명령(EO 14028)으로 연방 정부에 납품하는 소프트웨어는 SBOM 제출이 의무화되었다. 구글, 마이크로소프트 등도 오픈소스 보안을 위해 SBOM을 적극 도입 중이다.
- **흔한 오해·주의점**: "한 번 만들면 끝"이 아니다. 소프트웨어가 업데이트될 때마다 SBOM도 새로 갱신되어야 하며, 전체 공급망(Supplier -> Developer -> Consumer)에서 끊임없이 유통되어야 가치가 있다.

## 연결 개념
- Software Supply Chain Security — 소프트웨어의 제작부터 배포까지 전 과정의 보안
- SPDX / CycloneDX — SBOM을 작성하는 대표적인 국제 표준 포맷
- VEX (Vulnerability Exploitability eXchange) — SBOM 내 취약점이 실제로 실행 가능한지 알려주는 보충 정보

# 📝 【답안용】 시험 답안 템플릿

> 목적: 시험장에서 25분에 그대로 쓰는 답안 양식. 작성방식(추상표현 금지·수치·도식·문제유형 전환)을 엄격히 지킨다.
> 핵심: 소프트웨어 공급망 보안의 가시성 확보와 신속한 취약점 대응(Incident Response) 체계로서의 SBOM의 역할과 표준 형식을 중심으로 서술한다.

## 핵심 인사이트 (3줄 요약)

> 1. **본질**: SBOM(Software Bill of Materials)은 소프트웨어 제품을 구성하는 모든 오픈소스 및 상용 컴포넌트의 상세 정보를 포함한 기계 판독 가능한 목록(Inventory)이다.
> 2. **가치**: 복잡한 소프트웨어 공급망 내의 구성 요소를 투명화하여 취약점 발생 시 영향도 분석(Impact Analysis) 시간을 단축하고 라이선스 리스크를 관리한다.
> 3. **판단 포인트**: SPDX, CycloneDX와 같은 표준 포맷 준수와 빌드 파이프라인(CI/CD) 내의 자동화된 생성·검증 체계 구축이 핵심이다.

## 출제 의도 및 답안 포인트

| 출제 의도 | 반드시 짚을 핵심 | 감점 회피 포인트 |
|:---|:---|:---|
| SBOM 정의 및 도입 배경 이해 | 소프트웨어 공급망 보안, Log4j 사태 대응, 가시성 확보 | 단순히 '라이브러리 목록' 수준으로 서술 금지 |
| SBOM 주요 표준 포맷 숙지 여부 | SPDX, CycloneDX, SWID | 표준 명칭 혼동 및 특징 누락 시 감점 |
| SBOM 기반의 취약점 대응 프로세스 파악 | CVE 매핑, VEX 연동, 라이선스 검등 | 생성 단계만 강조하고 유통/활용 단계 간과 경계 |

> 요약: 소프트웨어 투명성 확보를 통한 공급망 보안 강화 전략으로서의 SBOM의 기술적 사양과 운영 방안을 평가한다.

## Ⅰ. 개요 및 필요성

- 정의: 소프트웨어 패키지 내의 모든 구성 요소, 버전, 라이선스 및 종속 관계를 명시한 기계 판독 가능한 명세서
- 배경: 오픈소스 사용량 급증(전체 코드의 70~90%) 및 소프트웨어 공급망을 타깃으로 한 사이버 공격 증가
- 필요성: 신속한 취약점 영향도 파악(MTTI 단축), 오픈소스 라이선스 위반 리스크 방지, 소프트웨어 품질 및 무결성 보장

## Ⅱ. 구조 및 구성요소

```text
[ Software Product ]
      | (Analyze / Extract)
[ SBOM Document ]
  / Component Name & Version (무엇인가)
  / Supplier Name (누가 만들었나)
  / Dependency Relationship (어떻게 연결됐나)
  / License Info (권리는 어떠한가)
  / Hash / Digital Signature (변조되지 않았나)
```

| 구성요소 | 역할 | 필수 데이터 항목 (NTIA 기준) |
|:---|:---|:---|
| 컴포넌트 정보 | 구성 요소 식별 | 제작자 이름, 컴포넌트 이름, 버전 값 |
| 관계 정보 | 종속성 및 포함 관계 명시 | 상위/하위 컴포넌트 간 관계 (Depends on) |
| 고유 식별자 | 컴포넌트의 유일성 보장 | PURL (Package URL), CPE (Common Platform Enumeration) |
| 무결성 정보 | 위변조 방지 및 신뢰 보장 | 체크섬(Hash), 디지털 서명, 인증서 정보 |
| 라이선스 정보 | 법적 분쟁 방지 및 규제 준수 | 라이선스 타입 (MIT, Apache, GPL 등) |

> 요약: 부품의 이름, 출처, 버전, 관계를 명확히 하여 소프트웨어 내부를 '가시화'하는 것이 목적이다.

---

## Ⅲ. 동작원리 및 흐름도

```text
코드 분석(CI/CD) -> SBOM 생성(SPDX/CycloneDX) -> 취약점 DB(CVE/NVD) 매핑 -> 위협 평가 -> 배포 및 공유
```

| 단계 | 처리 내용 | 검증 기준 |
|:---:|:---|:---|
| 1 | 자동 생성 (Generation) | 빌드 시점에 SCA(Software Composition Analysis) 도구로 SBOM 생성 |
| 2 | 표준 변환 (Standardization) | SPDX 또는 CycloneDX 등 상호운용 가능한 포맷으로 변환 |
| 3 | 취약점 매핑 (Matching) | NVD, OSV 등 글로벌 취약점 DB와 SBOM 구성 요소 실시간 대조 |
| 4 | 정보 유통 (Distribution) | 하위 공급자로부터 상위 소비자까지 신뢰할 수 있는 방식으로 전달 |

> 요약: 개발 단계에서 자동으로 생성된 명세서를 글로벌 취약점 정보와 결합하여 상시 모니터링 체계를 가동한다.

## Ⅳ. 특징 (표준 포맷 비교)

| 구분 | SPDX (ISO/IEC 5962) | CycloneDX (OWASP) |
|:---|:---|:---|
| 주도 기관 | Linux Foundation (ISO 표준) | OWASP Foundation |
| 주요 강점 | 방대한 데이터 표현, 라이선스 관리 특화 | 가볍고 자동화 용이, 보안(Vulnerability) 특화 |
| 파일 형식 | JSON, YAML, RDF, Tag:Value | JSON, XML |
| 활용 분야 | 소프트웨어 라이선스 컴플라이언스 | 보안 취약점 관리, 공급망 가시성 |

> 요약: 범용적인 SPDX와 보안에 민감한 CycloneDX가 시장을 양분하고 있으며, 상호 호환성을 갖추는 방향으로 발전 중이다.

## Ⅴ. 심화 비교 및 적용 판단

| 구분 | SCA (Software Composition Analysis) | SBOM (Bill of Materials) | 선택 기준 |
|:---|:---|:---|:---|
| 성격 | 보안 분석 행위/도구 | 분석의 결과물 (산출물/데이터) | 분석 도구 도입 여부 vs 데이터 공유 여부 |
| 범위 | 현재 프로젝트 내 분석 | 공급망 전체에 걸친 데이터 유통 | 외부 파트너와의 협업 필요성 |
| 가치 | 취약점 발견 및 조치 | 투명성 확보 및 장기적 추적성 | 소프트웨어 공급망의 복잡도 |

> 요약: SCA 도구를 통해 SBOM을 생성하며, 생성된 SBOM은 SCA 도구가 없는 외부 조직에서도 활용 가능하다.

| 리스크 | 원인 | 대응 방안 | 확인 지표 |
|:---|:---|:---|:---|
| 정보의 부정확성 | 동적 종속성(Dynamic) 반영 누락 | 런타임 분석 결합, 정기적 SBOM 갱신 | SBOM 정확도 (Precision), 업데이트 주기 |
| 관리 오버헤드 | 수많은 마이크로서비스별 SBOM 관리 부담 | 중앙 집중식 SBOM 저장소(Repository) 구축 | 프로젝트당 SBOM 관리 성공률 |
| 기밀 유출 우려 | 상세 구조 노출로 인한 역공학 위험 | 민감 정보 필터링, 신뢰 기반 공유 체계 | 데이터 유출 사고 건수 |

> 요약: SBOM의 정확도 유지가 가장 큰 과제이며, 빌드 파이프라인 자동화를 통해 해결해야 한다.

| 점검 항목 | 목표 기준 | 측정 방법 |
|:---|:---|:---|
| 취약점 대응 시간 | 신규 CVE 발표 후 영향도 분석 < 1시간 | 사고 발생 시 영향 파악 완료 시간 측정 |
| 컴포넌트 식별률 | 전체 종속성 중 식별된 비율 100% | 빌드 로그와 SBOM 리스트 대조 분석 |
| 표준 준수 여부 | 국제 표준 포맷(SPDX 등) 준수율 100% | 표준 검증 도구(Validator) 통과 여부 |

> 요약: 도입 효과는 취약점 분석 속도 향상과 전체 부품에 대한 완벽한 식별 여부로 평가한다.

## Ⅵ. 실무 적용 및 결론

**적용 방안 3개:**
1. **취약점 조기 대응**: Log4j와 같은 치명적 취약점 발견 시, 전사 SBOM 저장소를 검색하여 5분 이내에 영향받는 시스템 리스트 추출
2. **라이선스 거버넌스**: 배포 전 SBOM을 스캔하여 GPL 등 비즈니스에 위험한 오픈소스 라이선스 포함 여부를 자동으로 검증
3. **공급망 보안 검수**: 외부 업체로부터 소프트웨어 납품 시 SBOM 제출을 의무화하고, 알려진 취약점이 없는지 사전 검증 후 승인

**결론 (2줄):**
- 기술사 판단: SBOM은 '보안의 투명성'을 확보하는 기초 자산이며, 단순한 파일 생성을 넘어 VEX(취약점 실행 가능 정보)와 연계된 실질적 대응 체계로 고도화되어야 한다.
- 향후 방향: 하드웨어 정보를 포함한 HBOM, AI 모델 정보를 포함한 AI-BOM으로 확장되어 '토탈 가시성' 확보의 핵심 수단이 될 전망이다.
