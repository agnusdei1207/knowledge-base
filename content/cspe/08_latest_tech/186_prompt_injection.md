## 미리 알고가기

- 프롬프트 인젝션은 LLM이 지시와 데이터를 같은 텍스트 컨텍스트에서 해석하는 구조적 한계를 악용함
- 단순 욕설 출력 문제가 아니라 에이전트 권한과 결합되면 데이터 유출과 잘못된 외부 작업으로 이어질 수 있음
- 방어 핵심은 입력 필터보다 권한 최소화와 instruction-data 분리 설계에 가까움

## Ⅰ. 개요

- **정의/개념**: 프롬프트 인젝션은 공격자가 사용자 입력이나 외부 문맥에 악성 지시를 삽입해 시스템 프롬프트와 안전 정책을 무력화하고 모델 동작을 바꾸는 자연어 기반 공격임
- **배경/필요성**: LLM은 전통적 프로그램처럼 명령과 데이터를 엄격히 분리하지 못하므로, 적대적 입력이 정책 우회와 비즈니스 로직 교란으로 이어질 수 있어 구조적 대응이 필요해짐

## Ⅱ. 특징

- SQL injection처럼 구문 오류를 찌르는 공격이 아니라 의미와 문맥 해석을 교란하는 공격임
- 직접 입력뿐 아니라 검색 결과와 문서와 툴 응답까지 공격 매개체가 될 수 있음
- 에이전트와 결합되면 읽기 전용 오류를 넘어 송금과 메일 발송과 파일 삭제 같은 실제 행위 오남용으로 확대됨
- 금지어 필터만으로는 변형 표현과 다단계 우회를 막기 어려움

## Ⅲ. 종류 및 비교

| 판단 기준 | Direct Prompt Injection | Indirect Prompt Injection | Jailbreak |
|:---|:---|:---|:---|
| 주입 위치 | 사용자 입력 | 외부 문서와 웹 콘텐츠 | 대화 맥락과 역할 부여 |
| 핵심 목적 | 시스템 지시 오버라이드 | 신뢰하지 않는 콘텐츠 경유 오염 | 안전 필터 우회 |
| 위험 확대 경로 | 잘못된 답변, 도구 오남용 | 대규모 공급망식 오염 | 유해 콘텐츠 생성 |
| 방어 중점 | 입력 검증, 권한 분리 | 문서 정화, RAG 격리 | 안전 정책 강화 |

## Ⅳ. 구성요소 및 구조

| 구성요소 | 설명 |
|:---|:---|
| System Prompt | 모델 역할과 정책과 제약을 담고 있으나 후속 문맥에 의해 흔들릴 수 있는 제어층임 |
| User Input, External Context | 공격자가 명령을 숨기는 주요 주입 경로로 모델이 지시와 데이터로 동시에 해석할 수 있음 |
| Policy, Guardrail Layer | 위험 의도와 금지 작업을 감지해 모델 응답이나 도구 실행을 차단하는 통제 계층임 |
| Tool, Action Interface | DB 조회와 메일 발송처럼 프롬프트 오염이 실제 행동으로 전이되는 가장 위험한 경계임 |
| Logging, Review | 공격 시도와 차단 결과를 남겨 정책 개선과 레드팀 피드백으로 연결함 |

```text
+-------------------+      +-------------------+      +-------------------+
| System Prompt     | ---> | User / Ext Context| ---> | Policy Guardrail  |
+-------------------+      +-------------------+      +-------------------+
                                                           |
                                                           v
                                                   +-------------------+
                                                   | Tool / Action     |
                                                   +-------------------+
```

## Ⅴ. 원리 및 절차 흐름도

```text
+-------------+     +-------------+     +-------------+     +-------------+
| 악성 지시 주입   | --> | 문맥 하이재킹   | --> | 정책 우회 시도  | --> | 응답/행동 오염  |
+-------------+     +-------------+     +-------------+     +-------------+
```

1. **악성 지시 주입**: 입력이나 문서에 우회 명령을 숨김
2. **문맥 하이재킹**: 모델이 이를 새 지시로 해석하도록 유도함
3. **정책 우회 시도**: 시스템 프롬프트와 안전 규칙을 약화시킴
4. **응답 또는 행동 오염**: 잘못된 답변이나 외부 행위를 유발함

## Ⅵ. 문제점 및 해결 방안

1. 문제: 시스템 프롬프트와 사용자 입력이 같은 컨텍스트 창에 섞이면 우선순위 충돌로 정책이 쉽게 흔들릴 수 있음
   - 해결방안: instruction-data separation과 structured prompt boundary를 적용하고 prompt override rate와 policy adherence rate로 검증함
2. 문제: 모델이 과도한 도구 권한을 가지면 단순 인젝션이 실제 시스템 변경과 데이터 유출로 이어질 수 있음
   - 해결방안: least privilege tool design과 step-up approval을 적용하고 unauthorized tool execution rate와 high-risk action block rate로 검증함
3. 문제: 금지어 필터 위주의 방어는 인코딩과 역할극과 다단계 변형 프롬프트를 충분히 막지 못할 수 있음
   - 해결방안: intent classifier와 continuous red teaming을 병행하고 attack success rate와 false positive rate로 검증함

## Ⅶ. 적용 사례

- 고객지원 에이전트가 환불 규정 우회 프롬프트를 차단하도록 운영되며 확인 지표는 prompt override rate와 refund abuse incident rate임
- 사내 업무 자동화 봇이 메일 발송 권한을 최소화한 채 인젝션 방어를 적용하며 확인 지표는 unauthorized send attempt rate와 human approval coverage임
- RAG 기반 상담 서비스가 외부 문서를 신뢰하지 않는 컨텍스트로 격리하고 운영되며 확인 지표는 indirect injection block rate와 grounded answer rate임

## Ⅷ. 결론

프롬프트 인젝션은 LLM 구조의 본질적 위험이므로 입력 차단보다 권한 축소와 문맥 경계 설계와 지속적 레드팀 운영이 핵심 대응 전략임.
