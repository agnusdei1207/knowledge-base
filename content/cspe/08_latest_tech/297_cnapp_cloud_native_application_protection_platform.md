# 📖 【암기용】 개념 완전 이해

> 목적: CNAPP를 CSPM·CWPP·CIEM·IaC 스캔 등을 하나로 묶어 클라우드 네이티브 애플리케이션의 개발부터 운영까지 위험을 관리하는 플랫폼으로 이해하게 만든다.

## 한눈에
- **개요**: 클라우드 인프라, 워크로드, 권한, 코드 구성을 통합 분석해 위험을 우선순위화하는 보호 플랫폼
- **왜 필요한가**: Kubernetes, serverless, IaC, 멀티클라우드는 설정 오류·취약점·권한 과다·런타임 위협이 서로 연결되어 발생한다.
- **핵심 직관**: 건물 안전 점검, 출입 권한, 공사 도면 검토, 실시간 CCTV를 따로 보지 않고 하나의 위험 상황판으로 보는 방식이다.

## 깊이 이해
- **배경·문제의식**: CSPM은 설정을 보고, CWPP는 워크로드를 보며, CIEM은 권한을 본다. 그러나 실제 침해 경로는 잘못 열린 스토리지, 과다 권한, 취약 컨테이너가 연결될 때 발생한다.
- **작동 원리**: 클라우드 API, IaC 저장소, 이미지 레지스트리, Kubernetes, 런타임 telemetry를 수집하고 공격 경로와 비즈니스 중요도를 기준으로 조치 순위를 정한다.
- **비유**: 병원에서 혈액검사, 영상검사, 진료기록을 따로 보지 않고 환자 한 명의 위험도를 종합 판정하는 것과 같다.
- **구체 예시**: 인터넷에 노출된 Kubernetes Service, critical CVE가 있는 컨테이너, 관리자 권한 서비스 계정을 하나의 공격 경로로 묶어 우선 조치한다.
- **흔한 오해·주의점**: CNAPP는 단순 통합 대시보드가 아니다. 코드·클라우드·런타임 데이터를 연결해 실제 악용 가능성을 기준으로 우선순위를 산정해야 한다.

## 연결 개념
- CSPM — 클라우드 설정·컴플라이언스 점검
- CWPP — 워크로드 런타임 보호
- DevSecOps — 개발 파이프라인에서 보안 검사를 자동화

# 📝 【답안용】 시험 답안 템플릿

> 목적: 시험장에서 25분에 그대로 쓰는 답안 양식.
> 핵심: CNAPP는 CSPM과 CWPP를 합친 명칭이 아니라 코드부터 런타임까지 클라우드 위험을 상관분석하는 통합 플랫폼이다.

## 핵심 인사이트 (3줄 요약)

> 1. **본질**: CNAPP는 클라우드 네이티브 애플리케이션 보호를 위해 CSPM, CWPP, CIEM, IaC, KSPM 등을 통합한 보안 플랫폼임.
> 2. **가치**: 설정 오류, 취약 이미지, 과다 권한, 런타임 위협을 공격 경로 기준으로 연결해 조치 우선순위를 제시함.
> 3. **판단 포인트**: 자산 가시성, 위험 상관분석, shift-left 검사, 런타임 탐지, 티켓·CI/CD 연계가 평가 기준임.

## 출제 의도 및 답안 포인트

| 출제 의도 | 반드시 짚을 핵심 | 감점 회피 포인트 |
|:---|:---|:---|
| 클라우드 보안 통합 이해 확인 | CSPM·CWPP·CIEM·IaC·런타임 연계 | 단순 취약점 스캐너로 설명 |
| 위험 우선순위 판단 확인 | attack path, exposure, exploitability | 발견 건수 나열 |
| DevSecOps 연결 확인 | 코드 저장소부터 운영까지 검사 | 운영 단계 보안만 작성 |

> 요약: 이 문제는 클라우드 보안 항목을 많이 나열하는 것이 아니라 위험 상관분석 구조를 쓰는 것이 핵심이다.

---

## Ⅰ. 개요 및 필요성

- 개요: 클라우드 통합 보호 플랫폼
- 배경: 클라우드 네이티브 환경은 IaC, 컨테이너, Kubernetes, 권한, 런타임 이벤트가 하나의 공격 경로로 연결됨.
- 필요성: 설정 오류와 취약점 발견 건수보다 실제 노출·권한·중요 자산 연결 여부를 기준으로 조치해야 함.

---

## Ⅱ. 구조 및 구성요소

```text
Cloud API / IaC Repo / Image Registry / Kubernetes / Runtime
  +-> CNAPP Data Lake -> Risk Correlation -> Prioritized Finding
  +-> Ticket / CI-CD / SIEM / SOAR
```

| 구성요소 | 역할 | 특이사항 |
|:---|:---|:---|
| CSPM | 클라우드 설정과 컴플라이언스 점검 | 공개 스토리지, 보안그룹 |
| CWPP | VM·컨테이너·serverless 보호 | 취약점, runtime detection |
| CIEM | 권한과 identity 위험 분석 | 과다 권한, unused permission |
| IaC/KSPM | 코드와 Kubernetes 설정 검사 | misconfiguration 사전 차단 |

> 요약: CNAPP는 클라우드 설정, 워크로드, 권한, 코드 구성을 연결해 위험을 통합 판단한다.

---

## Ⅲ. 동작원리 및 흐름도

```text
자산 수집 -> 구성 / 취약점 / 권한 / 런타임 데이터 정규화
-> 공격 경로 분석 -> 위험 점수 산정 -> 조치 티켓 발행 -> 재검증
```

| 단계 | 처리 내용 | 검증 기준 |
|:---:|:---|:---|
| 1 | 멀티클라우드 자산과 워크로드 식별 | asset coverage |
| 2 | 설정 오류, CVE, 권한, 노출도 수집 | finding freshness |
| 3 | 공격 경로와 중요 자산 연결 분석 | reachable risk |
| 4 | CI/CD·티켓·SIEM으로 조치 연계 | remediation SLA |

> 요약: CNAPP는 자산 데이터를 모은 뒤 공격 경로와 업무 중요도를 반영해 조치 순서를 정한다.

| 우선순위 | 심각도 점수 중심 | 노출·권한·자산 중요도 결합 | 조치 backlog |

> 요약: CNAPP는 분리된 보안 결과를 공격 경로 기준으로 묶어 조치 가능한 위험으로 전환한다.

## Ⅴ. 심화 비교 및 적용 판단

| 구분 | 기존/대안 | 본 키워드 | 선택 기준 |
|:---|:---|:---|:---|
| 구조 | CSPM·CWPP 개별 도입 | 통합 CNAPP | 멀티클라우드·Kubernetes 사용 |
| 비용 | 도구별 라이선스 | 플랫폼 통합 구독 | 중복 기능과 운영 인력 |
| 운영 | 알림 과다 | 위험 우선순위 기반 조치 | critical backlog |

> 요약: 클라우드 네이티브 자산이 많고 보안 알림이 누적되면 CNAPP 통합 가치가 커진다.

| 리스크 | 원인 | 대응 방안 | 확인 지표 |
|:---|:---|:---|:---|
| 알림 과다 | 상관분석 없는 탐지 | attack path 기반 필터 | actionable finding ratio |
| 권한 사각지대 | CIEM 연계 부족 | identity graph 통합 | excessive permission |
| 운영 미연계 | 티켓·CI/CD 분리 | Jira, Git, pipeline 연동 | remediation lead time |

> 요약: CNAPP 리스크는 탐지보다 조치 연결 실패이며, 실행 가능한 finding 비율과 조치 시간을 봐야 한다.

| 점검 항목 | 목표 기준 | 측정 방법 |
|:---|:---|:---|
| 자산 가시성 | 클라우드 계정·클러스터 누락 없음 | inventory 대조 |
| 위험 우선순위 | 중요 자산 연결 finding 우선 처리 | attack path report |
| 조치 | SLA 내 remediation | 티켓 상태 추적 |

> 요약: CNAPP 성공은 탐지 건수보다 자산 누락, 우선순위 정확도, 조치 SLA로 판단한다.

## Ⅵ. 실무 적용 및 결론

**적용 방안 3개:**
1. 클라우드 계정, Kubernetes 클러스터, 이미지 레지스트리, IaC 저장소를 CNAPP 수집 범위에 먼저 포함함.
2. 인터넷 노출, critical CVE, 과다 권한, 중요 데이터 접근을 조합한 attack path 우선순위 규칙을 정의함.
3. CI/CD 차단 기준과 운영 티켓 SLA를 나눠 개발 단계와 운영 단계 조치 흐름을 분리함.

**결론 (2줄):**
- 기술사 판단: 단일 클라우드·소수 VM은 CSPM/CWPP 개별 도구로 충분하나, Kubernetes·IaC·멀티클라우드는 CNAPP가 타당함.
- 향후 방향: CNAPP는 ASPM, DSPM, exposure management와 결합해 애플리케이션·데이터 중심 위험 관리로 발전함.
