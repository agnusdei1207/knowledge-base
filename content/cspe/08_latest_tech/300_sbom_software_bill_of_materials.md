# 📖 【암기용】 개념 완전 이해

> 목적: SBOM을 소프트웨어에 들어간 구성요소와 의존 관계를 기록한 명세서로 이해하고, 공급망 취약점 대응에서 왜 필요한지 설명하게 만든다.

## 한눈에
- **개요**: 소프트웨어 구성요소, 버전, 공급자, 의존 관계를 기록한 자재명세서
- **왜 필요한가**: Log4j 같은 취약점이 공개되면 어떤 제품과 서비스가 해당 라이브러리를 포함하는지 즉시 찾아야 한다.
- **핵심 직관**: 식품 알레르기 사고 때 원재료 표시가 있어야 어떤 제품에 문제가 있는지 추적할 수 있는 것과 같다.

## 깊이 이해
- **배경·문제의식**: 현대 소프트웨어는 오픈소스, 상용 라이브러리, 컨테이너 이미지, 빌드 도구가 복잡하게 연결되어 직접 작성 코드만 관리해서는 공급망 위험을 알 수 없다.
- **작동 원리**: 빌드·패키징 단계에서 구성요소와 의존 관계를 수집하고 SPDX, CycloneDX 같은 표준 형식으로 생성해 취약점 DB와 대조한다.
- **비유**: 자동차 정비사가 부품번호와 제조사를 알아야 리콜 대상 차량을 찾듯, 보안팀은 컴포넌트 이름과 버전을 알아야 영향을 판단한다.
- **구체 예시**: 특정 CVE가 `openssl 3.0.x`에 공개되면 SBOM에서 해당 버전을 포함한 컨테이너 이미지와 서비스를 조회해 패치 대상을 확정한다.
- **흔한 오해·주의점**: SBOM은 문서 한 번 제출로 끝나지 않는다. 릴리스마다 생성하고, 취약점·라이선스·무결성 관리와 연결해야 가치가 있다.

## 연결 개념
- SCA — 오픈소스 구성요소와 취약점 분석
- SSDF — 보안 소프트웨어 개발 프레임워크
- DevSecOps — CI/CD에서 SBOM 생성·검증 자동화

# 📝 【답안용】 시험 답안 템플릿

> 목적: 시험장에서 25분에 그대로 쓰는 답안 양식.
> 핵심: SBOM은 공급망 투명성을 위한 구성요소 명세이며, 생성·배포·검증·취약점 매핑까지 운영해야 한다.

## 핵심 인사이트 (3줄 요약)

> 1. **본질**: SBOM은 소프트웨어를 구성하는 컴포넌트와 의존 관계, 버전, 공급자, 식별자를 기록한 공식 명세임.
> 2. **가치**: 신규 CVE, 라이선스 위반, 위조 패키지 발생 시 영향 제품과 서비스를 대응 SLA 안에서 식별함.
> 3. **판단 포인트**: SPDX/CycloneDX 형식, 생성 시점, 최소 데이터 필드, 취약점 DB 매핑, 무결성 검증이 핵심임.

## 출제 의도 및 답안 포인트

| 출제 의도 | 반드시 짚을 핵심 | 감점 회피 포인트 |
|:---|:---|:---|
| 공급망 보안 이해 확인 | 구성요소, 버전, 의존 관계, 식별자 | 라이브러리 목록으로만 축소 |
| 운영 절차 판단 확인 | CI/CD 생성, 저장, 공유, 취약점 매핑 | 수동 엑셀 문서로 설명 |
| 표준 형식 확인 | SPDX, CycloneDX, package URL, hash | 자체 양식만 제시 |

> 요약: 이 문제는 SBOM을 생성 문서가 아니라 취약점 영향 분석과 공급망 감사의 운영 데이터로 설명해야 한다.

---

## Ⅰ. 개요 및 필요성

- 개요: 소프트웨어 구성요소 명세
- 배경: 오픈소스·컨테이너·외부 패키지 의존이 커져 제품 내부 구성요소를 모르면 취약점 영향 범위를 알 수 없음.
- 필요성: 신규 CVE 공개 시 SBOM 기반으로 영향 서비스, 패치 우선순위, 공급업체 책임을 추적해야 함.

---

## Ⅱ. 구조 및 구성요소

```text
Source / Dependency / Container Image -> SBOM Generator
  +-> Component Inventory -> Dependency Graph -> SPDX / CycloneDX
  +-> Vulnerability DB / License DB / Artifact Repository
```

| 구성요소 | 역할 | 특이사항 |
|:---|:---|:---|
| 컴포넌트 식별 | 패키지명·버전·공급자 기록 | purl, CPE, hash |
| 의존 관계 | 직접·전이 의존성 연결 | dependency graph |
| 표준 형식 | SBOM 교환과 자동 분석 지원 | SPDX, CycloneDX |
| 검증 연계 | 취약점·라이선스·무결성 점검 | CVE, license, signature |

> 요약: SBOM은 컴포넌트 식별, 의존 관계, 표준 형식, 검증 연계를 갖춰야 자동 분석 데이터가 된다.

---

## Ⅲ. 동작원리 및 흐름도

```text
빌드 시작 -> 의존성 해석 -> SBOM 생성 -> 서명 / 저장
-> 취약점 DB 매핑 -> 영향 서비스 식별 -> 패치 / 예외 승인
```

| 단계 | 처리 내용 | 검증 기준 |
|:---:|:---|:---|
| 1 | 소스·패키지·이미지에서 구성요소 수집 | component coverage |
| 2 | SPDX 또는 CycloneDX 형식으로 SBOM 생성 | schema validation |
| 3 | CVE·라이선스 DB와 매핑 | match accuracy |
| 4 | 영향 서비스와 패치 상태 추적 | remediation SLA |

> 요약: SBOM은 빌드 산출물과 함께 생성되어 취약점 DB와 연결되고 패치 추적 데이터로 사용된다.

> 요약: 공급망 감사와 외부 제출 요구가 있으면 SCA 결과를 SBOM 표준 산출물로 관리해야 한다.

| 리스크 | 원인 | 대응 방안 | 확인 지표 |
|:---|:---|:---|:---|
| 누락 | 전이 의존성·컨테이너 계층 미수집 | 빌드 단계 자동 생성 | component coverage |
| 오래된 SBOM | 릴리스 후 변경 미반영 | artifact와 SBOM 버전 결합 | freshness |

> 요약: SBOM 리스크는 누락, 최신성, 공개 범위이며 빌드 자동화와 접근통제로 관리한다.

| 점검 항목 | 목표 기준 | 측정 방법 |
|:---|:---|:---|
| 완전성 | 주요 산출물 SBOM 생성 | artifact 대조 |
| 표준성 | SPDX/CycloneDX schema 통과 | validator |
| 대응성 | critical CVE 영향 분석 SLA 충족 | incident 기록 |

> 요약: SBOM 성과는 생성 여부보다 완전성, 표준성, CVE 영향 분석 시간으로 판단한다.

## Ⅵ. 실무 적용 및 결론

**적용 방안 3개:**
1. CI/CD에서 소스, 패키지, 컨테이너 이미지별 SBOM을 SPDX 또는 CycloneDX로 자동 생성하고 artifact와 함께 저장함.
2. SBOM을 SCA, 취약점 DB, 라이선스 정책, 서명 검증과 연결해 릴리스 게이트로 사용함.
3. 공급업체 계약에 SBOM 제출 형식, 갱신 주기, 취약점 통보 SLA, 공유 범위를 명시함.

**결론 (2줄):**
- 기술사 판단: 오픈소스와 외부 패키지 의존이 큰 제품은 SBOM을 릴리스 산출물로 관리해야 하며, 단독 문서 제출은 운영 가치가 낮음.
- 향후 방향: SBOM은 VEX, SLSA, Sigstore와 결합해 취약점 영향성과 빌드 무결성을 함께 증명하는 공급망 보안 데이터로 발전함.
