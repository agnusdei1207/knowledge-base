## 핵심 인사이트 (3줄 요약)
> 1. **본질**: 거대 언어 모델(LLM)이 당장 눈앞의 한 걸음만 보고 행동하는 근시안적 한계를 벗어나, "최종 목표를 달성하려면 전체 과정을 1단계, 2단계, 3단계로 어떻게 쪼개고 접근해야 할까?"를 먼저 설계하는 **인지적 로드맵(Cognitive Roadmap) 그리기 기술**이다.
> 2. **가치**: "파이썬으로 웹 서버 짜줘" 같은 큰 목표를 주면 예전 AI는 중간에 길을 잃고 포기했다. 하지만 플래닝 능력이 결합되면 스스로 작업을 잘게 부수고(Task Decomposition), 끝낸 일과 남은 일을 체크하며 끝까지 과업을 완수해 내는 미친 지구력을 보여준다.
> 3. **판단 포인트**: 실행하면서 생각하는 방식(ReAct)과 실행 전에 전체 계획부터 완벽히 짜놓는 방식(Plan-and-Solve)의 트레이드오프를 이해하고, 중간에 계획이 틀어졌을 때 스스로 계획을 수정하는 재계획(Re-planning) 메커니즘을 서술해야 한다.

## Ⅰ. 개요 및 필요성
- **개요**: 에이전트 플래닝(Agent Planning)은 복잡하고 모호한 고수준(High-level)의 목표가 주어졌을 때, 에이전트가 이를 실행 가능한 수준의 하위 작업(Sub-tasks)들로 분해하고 순서를 배치하여 실행 전략을 수립하는 사전 추론 과정이다.
- **배경**: ReAct(생각$\to$행동$\to$관찰) 패턴은 훌륭했지만, 장기적인 전략이 없이 매 순간 "다음엔 뭐 하지?"만 고민하는 탐욕적(Greedy) 방식이었다. 이로 인해 작업이 10단계를 넘어가면 자기가 원래 뭘 하려고 했는지 까먹고 삼천포로 빠지는 현상(Goal Forgetting)이 빈번했다.
- **필요성**: 집을 지을 때 벽돌부터 쌓는 게 아니라 전체 설계도(Blueprint)부터 그려야 하듯, AI 에이전트도 거대 과업을 수행하기 전 '전체 작업 지시서'를 먼저 작성하고, 이를 하나씩 지워나가는(Check-off) 체계적 공정 관리가 필수적이었다.

## Ⅱ. 아키텍처 및 핵심 원리

```text
       [ 사용자 ] ── "지난 5년간의 서울 아파트 가격 동향을 리포트로 만들어줘" ──┐
                                                                           │
  ┌───────────────────────────── [ Agent Planning 시스템 ] ──────────────────▼──────┐
  │                                                                               │
  │  1. [ 작업 분해 (Task Decomposition) ] - "Plan-and-Solve 전략 발동!"               │
  │    - Sub-Task 1: "지난 5년 아파트 가격 데이터 검색하기"                             │
  │    - Sub-Task 2: "검색된 데이터로 연도별 평균 가격 통계 내기"                        │
  │    - Sub-Task 3: "통계 기반으로 마크다운 리포트 작성하기"                             │
  │                                                                               │
  │  2. [ 실행 및 궤도 추적 (Execution & Tracking) ]                                  │
  │     ▶ (Sub-Task 1 수행 중) ... 검색 완료! [체크 ✔️]                              │
  │     ▶ (Sub-Task 2 수행 중) ... 어라? 2022년 데이터가 누락됐네? (오류 발생)           │
  │                                                                               │
  │  3. [ 재계획 (Re-planning / Self-Correction) ]                                │
  │    - "아, 계획을 수정하자! 2022년 데이터만 특정 사이트에서 다시 검색하는 태스크 추가!"  │
  │    - Sub-Task 2-1: "2022년 국토부 실거래가 검색" (새로 추가됨)                     │
  │                                                                               │
  │  4. [ 최종 완료 ] ──▶ 남은 태스크 모두 소거 후 최종 결과 생성                           │
  └───────────────────────────────────────────────────────────────────────────────┘
```

- **1단계 [목표 분해 (Task Decomposition)]**: 가장 핵심적인 단계. 거대한 목표를 LLM의 추론 능력(CoT, Tree of Thoughts)을 활용해 "지금 당장 실행할 수 있는 가장 작은 크기의 행동 단위"로 잘게 쪼갠다.
- **2단계 [DAG 기반 순서도 작성]**: 쪼개진 태스크들 사이에 선후 관계를 설정한다. "데이터 수집이 안 끝나면 통계 분석은 시작할 수 없다"는 식의 의존성 그래프(DAG)를 메모리에 구성한다.
- **3단계 [순차 실행 (Sequential Execution)]**: 플래너가 짠 계획표를 들고 '실행(Worker) 에이전트'가 1번 작업부터 순서대로 도구를 써서 처리하며 결과를 쌓아나간다.
- **4단계 [성찰 및 재계획 (Reflection & Re-planning)]**: 현실 세계는 계획대로 되지 않는다. 실행 도중 에러가 나거나 예상치 못한 결과가 나오면, 플래너 에이전트가 다시 등판하여 "계획 전면 수정!"을 외치고 남은 작업의 순서나 목표를 동적으로 갈아엎는다.

## Ⅲ. 비교 및 연결

| 비교 축 | ReAct 패턴 (생각+행동 핑퐁) | Plan-and-Solve (플래닝 중심) |
|:---:|:---|:---|
| **행동 방식** | 일단 들이받고 보면서 생각함 (Agile) | **전체 계획을 완벽히 다 짜놓고 시작함 (Waterfall)** |
| **적합한 과업** | 2~3단계의 짧고 빠른 검색/조회 | **10단계 이상의 장기적이고 복잡한 거대 과업** |
| **환각(에러) 대처** | 그때그때 임기응변이 빠름 | **플랜을 중간에 수정(Re-planning)하는 메커니즘 필수** |
| **속도 (Latency)**| 바로 첫 번째 행동 돌입 | 계획 짜느라 초반에 시간 좀 걸림 (Delay 발생) |

> ※ **연결 포인트**: 플래닝 능력을 극대화하기 위해, 최근 연구자들은 LLM에게 단순히 글을 쓰게 하는 걸 넘어 'Tree of Thoughts(생각의 나무)'나 'Graph of Thoughts' 같은 고도의 프롬프팅 기법을 써서 여러 갈래의 미래를 시뮬레이션(Look-ahead)하게 만든 뒤 가장 좋은 계획을 선택하게 한다.

## Ⅳ. 실무 적용 및 기술사 판단

- **적용 사례 1 (HuggingGPT의 모델 플래닝)**: "이 사진 속 여자가 읽고 있는 책의 내용을 음성으로 읽어줘"라는 미친 복합 지시를 내리면, 플래닝 에이전트가 1) 이미지에서 사람을 자르고(탐지 모델), 2) 손에 든 책 표지 글씨를 읽고(OCR 모델), 3) 책 제목으로 인터넷을 검색하고(LLM), 4) 그걸 음성으로 바꾼다(TTS 모델)라는 4단계 계획을 완벽히 세운 뒤 허깅페이스의 모델들을 순서대로 호출해 결과를 낸다.
- **적용 사례 2 (데이터 분석 에이전트의 Plan-and-Execute)**: 유저가 복잡한 CSV 파일을 던지면, 랭체인(LangChain)의 `Plan-and-Execute Agent`가 먼저 전체 데이터 정제, 그룹핑, 시각화 순서로 계획을 짠다. 이후 작업자 에이전트가 하나씩 파이썬 코드를 샌드박스에서 돌리며 계획표에 줄(Strike-through)을 긋고, 막히면 플랜을 수정하는 식으로 훌륭한 엑셀 보고서를 뽑아낸다.
- **기술사 판단**: 플래닝 시스템 설계 시 가장 유의할 점은 **'과도한 플래닝(Over-planning)에 의한 무한 루프'**다. AI가 계획을 짜다가 "완벽하지 않아"라며 계획만 무한정 쪼개고 수정하느라 정작 실행은 1비트도 안 하는 마비 상태(Analysis Paralysis)가 올 수 있다. 아키텍트는 플래닝 단계에서 최대 생성 가능한 하위 작업의 수(예: Max Tasks = 5)를 하드코딩으로 제한하여 시스템의 실용성을 강제해야 한다.

## Ⅴ. 기대효과 및 결론

- **기대효과**: LLM의 단기 기억 상실과 문맥 이탈(Context Loss) 문제를 해결하여, 수 시간~며칠이 걸리는 장기(Long-horizon) 과업도 끝까지 추적하고 완수해 내는 진정한 비즈니스 자율 에이전트 시대를 연다.
- **향후 발전 방향**: 최근 OpenAI의 o3(Strawberry) 같은 추론 특화(Reasoning) 모델들은 프롬프트로 억지로 계획을 짜게 할 필요 없이, 모델 자체가 내재적(Native)으로 수만 번의 플래닝 시뮬레이션을 돌린 후 정답을 내놓는 '강화학습 기반 플래닝'의 경지로 진화하고 있다.

### 📌 관련 개념 맵
- **재계획 (Re-planning)**: 복싱에서 "누구나 그럴싸한 계획을 가지고 있다. 쳐맞기 전까지는"이라는 명언처럼, 에이전트가 도구를 쓰다 에러를 쳐맞았을 때 당황하지 않고 남은 태스크 계획표를 동적으로 수정하는 필수 복원력(Resilience) 메커니즘.
- **BabyAGI**: 아주 초창기에 나온 플래닝 에이전트의 조상님. 목표를 주면 무한 루프를 돌면서 스스로 할 일 목록(To-Do List)을 만들고 하나씩 해치우며 다시 목록을 업데이트하는 기발한 아이디어로 업계에 충격을 주었다.

### 📈 관련 키워드 및 발전 흐름도
`단순 질의응답 (Zero-shot)` $\to$ `ReAct (단기적 생각+행동)` $\to$ `Plan-and-Solve (사전 계획 수립 구조)` $\to$ `Re-planning (동적 계획 수정 능력 추가)` $\to$ `Test-Time Compute (모델 자체의 내재적 플래닝 시뮬레이션)`

### 👶 어린이를 위한 3줄 비유 설명
1. 장난감 조립을 할 때, 설명서도 안 보고 손에 잡히는 부품부터 무작정 끼우면 나중에 다 부수고 다시 해야 하죠? (예전 AI)
2. '플래닝(Planning)'은 조립하기 전에 설명서를 쭉 읽어보고, "1번 몸통 조립 $\to$ 2번 팔 조립 $\to$ 3번 다리 조립"이라고 나만의 계획표를 먼저 짜는 거예요.
3. 이렇게 꼼꼼하게 계획을 짜고 하나씩 체크(✔️) 하면서 조립하니까, 아무리 크고 복잡한 레고 성도 실수 없이 끝까지 멋지게 완성할 수 있답니다!
