# 📖 【암기용】 개념 완전 이해

## 한눈에
- **개요**: **에이전트 플래닝**은 에이전트(001 참조)가 **큰 목표를 실행 가능한 하위 작업으로 분해하고 순서·의존관계를 설계하는 계획 수립 과정**이다(HTN·Plan-and-Execute·ReWOO 등).
- **왜 필요한가**: ReAct(003)처럼 한 스텝씩 즉흥 판단만 하면 장기 목표에서 길을 잃고 도구 호출이 낭비된다. 먼저 전체 계획을 세우면 방향성·병렬화·비용 예측이 가능해진다.
- **핵심 직관**: 요리 전 레시피를 짜는 것이다. 재료 손질→끓이기→플레이팅 순서를 미리 정하면 중간에 헤매지 않는다. "무엇을 어떤 순서로 할지"를 실행 전에 먼저 구조화하는 것이 플래닝의 본질이다.

## 핵심 용어 정리 (내부에 등장하는 것들)
답안 본문에 등장하는 용어를 처음 보는 사람도 이해하도록 비유와 함께 먼저 정리한다.

| 용어/표기 | 의미 | 비유·예 |
|:---|:---|:---|
| 에이전트 플래닝(핵심) | 목표를 하위 작업으로 분해·순서화하는 계획 수립 | 실행 전 "레시피 짜기" |
| 작업 분해(Decomposition) | 큰 목표를 작은 실행 단위로 쪼갬 | 프로젝트를 "WBS로 분할" |
| 하위 목표(Subgoal)/스텝 | 분해된 개별 실행 단위 | 체크리스트 "항목" |
| HTN(계층적 작업망) | 상위 작업을 하위 작업으로 재귀 분해하는 기법 | 큰 일을 "가지치기" 분해 |
| Plan-and-Execute | 계획을 먼저 세운 뒤 순차 실행·필요 시 재계획 | 계획표 짜고 "따라 실행" |
| ReWOO | 도구 호출 없이 추론만으로 전체 계획을 먼저 수립 | 관찰 전 "설계도 완성" |
| ReAct(003 참조) | 한 스텝씩 추론-행동을 번갈아 진행 | 한 발씩 "즉흥 대응" |
| 재계획(Replanning) | 실행 결과가 어긋나면 계획을 갱신 | 상황 변화에 "일정 수정" |
| 의존관계(DAG) | 작업 간 선후·병렬 관계를 그린 그래프 | 공정 "선후 관계도" |
| 계획 검증(Plan Validation) | 실행 전 계획의 타당성·제약 충족 확인 | 착공 전 "설계 검토" |

## 깊이 이해
- **배경·문제의식**: ReAct(003)는 매 스텝 "생각→행동→관찰"을 반복하는데, 장기·다단계 목표에서는 근시안적 판단으로 경로를 이탈하거나 같은 도구를 반복 호출한다. 계획을 실행과 분리해 먼저 전체 그림을 세우면, 병렬 가능한 작업을 식별하고 도구 호출 수를 줄이며 진행 상황을 목표 대비 추적할 수 있다.
- **작동 원리(어떻게+왜)**: Planner LLM이 목표를 하위 작업 목록과 의존관계(DAG)로 분해한다. Plan-and-Execute는 계획을 세운 뒤 Executor가 순차 수행하고, 스텝 실패·환경 변화 시 재계획한다. ReWOO는 관찰(도구 결과) 없이 추론만으로 전체 계획·변수 참조를 먼저 만들어 도구를 한 번에 호출함으로써 LLM 호출 수를 크게 줄인다. HTN은 상위 작업을 사전 정의된 방법으로 하위 작업까지 재귀 분해해 도메인 지식을 계획에 주입한다.
- **비유**: 여행 계획. 즉흥 여행(ReAct)은 그때그때 다음 목적지를 정해 헤매기 쉽고, 사전 일정표(Plan-and-Execute)는 동선을 최적화하되 변수 발생 시 일정을 수정한다. 패키지 상품(HTN)은 검증된 코스를 그대로 따른다.
- **구체 예시(실제 사례)**: LangChain의 Plan-and-Execute 에이전트는 Planner가 스텝 리스트를 만들고 Executor가 하나씩 수행한다. ReWOO 논문은 관찰 의존을 제거해 토큰·호출을 절감했고, BabyAUI/AutoGPT는 목표를 태스크 큐로 분해·재우선순위화한다. HTN은 고전 자동계획(로봇·게임 AI)에서 온 기법으로 LLM 에이전트의 구조적 분해에 접목된다.
- **흔한 오해·주의점**: "계획을 미리 다 세우는 것이 항상 낫다"가 아니다. 환경이 자주 바뀌면 초기 계획이 금세 낡아 재계획 비용이 커진다. 반대로 불확실성이 낮은 정형 과제는 사전 계획(ReWOO)이 효율적이다. 계획 품질은 Planner LLM 추론력에 좌우되므로 계획 검증 단계가 필요하다.

## 연결 개념
- ReAct(003) — 계획 없이 스텝별 추론-행동을 엮는 대비 기법
- 멀티 에이전트 협업(013) — 분해된 하위 작업을 역할별 에이전트에 배분
- 에이전트 오케스트레이션(014) — 수립된 계획을 그래프·상태로 구동·라우팅

# 📝 【답안용】 시험 답안 템플릿

## 핵심 인사이트 (3줄 요약)

> 1. **본질**: 에이전트 플래닝은 목표를 하위 작업·의존관계로 분해해 실행 전 계획을 수립하는 과정(HTN·Plan-and-Execute·ReWOO)임.
> 2. **가치**: 스텝별 즉흥 판단(ReAct)의 근시안·도구 낭비를 줄이고 병렬화·비용 예측·진척 추적을 가능케 함.
> 3. **판단 포인트**: 환경 불확실성에 따라 사전 계획과 재계획 비중을 조절하고 계획 검증을 삽입해야 함.

## 출제 의도 및 답안 포인트

| 출제 의도 | 반드시 짚을 핵심 | 감점 회피 포인트 |
|:---|:---|:---|
| 목표 분해·계획 수립 구조 이해 | 작업 분해, DAG, Plan-and-Execute·ReWOO·HTN | ReAct(003)와 개념 미구분 감점 |
| 사전계획 vs 즉흥의 트레이드오프 인식 | 도구 호출 절감 vs 재계획 비용 | 사전 계획만 우월 단정 감점 |
| 계획 신뢰성 설계 역량 | 계획 검증, 재계획 조건, 종료 판정 | 검증·재계획 누락 시 실무 이해 부족 감점 |

> 요약: 목표를 어떻게 분해하고 사전계획·재계획을 어떤 기준으로 선택하는지 확인하려는 문제임.

## Ⅰ. 개요 및 필요성

- 개요: 목표를 실행 가능한 하위 작업·의존관계로 분해해 계획을 세우는 과정임
- 배경: ReAct(003) 스텝별 즉흥 판단은 장기 목표에서 근시안·도구 반복 호출을 유발함
- 필요성: 실행 전 전체 계획으로 병렬화·비용 예측·진척 추적을 확보해야 함
- 위치: 협업(013)·오케스트레이션(014)이 구동할 작업 구조를 산출하는 계획 단계임

---

## Ⅱ. 구조 및 구성요소

- 선형 구조도

```text
목표 -> Planner(작업 분해) -> 하위 작업 목록 + 의존관계(DAG)
  -> 계획 검증 -> Executor(스텝 실행) -> 결과 평가
    / 계획 이탈 -> Replanner(재계획) -> Executor 복귀
  -> 목표 달성 판정 -> 종료
```

| 구성요소 | 역할 | 특이사항 |
|:---|:---|:---|
| Planner | 목표를 하위 작업·순서로 분해 | 계획 품질이 LLM 추론력에 의존 |
| 작업 그래프(DAG) | 스텝 선후·병렬 관계 표현 | 병렬 가능 작업 식별 |
| 계획 검증기 | 제약·타당성 사전 확인 | 실행 전 오류 차단 |
| Executor | 스텝을 순차·병렬 실행 | 도구 호출·관찰 수행 |
| Replanner | 이탈 시 계획 갱신 | 재계획 트리거 조건 정의 |

> 요약: Planner가 목표를 DAG로 분해·검증하고 Executor가 실행하며 이탈 시 Replanner가 갱신함.

---

## Ⅲ. 동작원리 및 흐름도

- 선형 흐름도

```text
목표 입력 -> 작업 분해 -> 계획 검증 -> 스텝 실행·관찰 -> 목표 대비 평가 -> (이탈 시 재계획) -> 종료 판정
```

1. 분해: Planner가 목표를 하위 작업과 의존관계로 나눠 실행 계획을 생성함
2. 검증: 계획 검증기가 제약·자원·순서 타당성을 실행 전에 확인함
3. 실행: Executor가 스텝을 순서·병렬로 수행하고 도구 결과를 관찰함
4. 재계획·종료: 결과가 계획과 어긋나면 Replanner가 계획을 갱신하고 목표 달성 시 종료함

> 요약: 목표를 분해·검증한 뒤 실행하고 이탈 시 재계획하며 목표 달성으로 완결함.

---

## Ⅳ. 특징

- 목표 분해: 큰 목표를 하위 작업·의존관계로 구조화해 진척을 추적 가능하게 함
- 실행 분리: 계획과 실행을 나눠 근시안적 판단과 도구 낭비를 줄임
- 병렬화 식별: DAG로 독립 작업을 찾아 동시 실행·지연 단축을 가능케 함
- 호출 효율(ReWOO): 관찰 의존을 제거해 LLM·도구 호출 수를 절감함
- 재계획 비용: 환경 변동이 잦으면 계획 갱신 오버헤드가 커져 트리거 설계가 필요함

---

## Ⅴ. 심화 비교 및 적용 판단

- 플래닝 기법 선택은 계획 시점·재계획 방식으로 갈리며 세 기법과 ReAct를 대비함

| 구분 | ReAct(003) | Plan-and-Execute | ReWOO | HTN |
|:---|:---|:---|:---|:---|
| 계획 시점 | 스텝마다 즉흥 | 사전 계획 후 실행 | 관찰 전 전체 계획 | 재귀 분해 사전 계획 |
| 도구 호출 | 매 스텝 관찰 의존 | 스텝별 관찰 | 일괄 호출로 절감 | 방법 정의에 따름 |
| 재계획 | 매 스텝 자동 | 이탈 시 재계획 | 계획 실패 시 | 하위 재분해 |
| 강점 | 변화 대응 유연 | 방향성·추적성 | 호출·토큰 효율 | 도메인 지식 주입 |
| 적합 상황 | 불확실·탐색적 | 다단계 정형 | 관찰 무관 정형 | 규칙 명확 도메인 |

> 요약: 불확실하면 ReAct·재계획 중심, 정형·다단계면 Plan-and-Execute, 호출 효율이 중요하면 ReWOO, 규칙이 명확하면 HTN이 적합함.

- 주요 리스크와 대응(불릿)
  - 계획 오류 — Planner 추론 한계가 원인 → 계획 검증기·소수 예시·제약 명시
  - 계획 노후화 — 환경 변동으로 계획이 낡음이 원인 → 재계획 트리거·부분 재분해
  - 과도 재계획 — 잦은 갱신으로 비용 폭증이 원인 → 재계획 임계값·최대 횟수 제한
- 운영 지표(불릿)
  - 계획 성공률 — 재계획 없이 완료한 비율 목표 — 실행 로그 집계
  - 도구 호출 수 — ReWOO 적용 절감폭 목표 — 호출 카운터 측정
  - 재계획 빈도 — 목표 상한 이내 — 재계획 트리거 로그 분석

---

## Ⅵ. 실무 적용 및 결론

- 적용 방안
  1. LangChain Plan-and-Execute로 Planner-Executor를 분리하고 스텝 실패 시 재계획을 트리거
  2. 관찰 의존이 낮은 정형 과제는 ReWOO로 계획·변수 참조를 일괄 수립해 LLM 호출을 절감
  3. 규칙이 명확한 도메인은 HTN으로 상위 작업을 재귀 분해하고 실행 전 계획 검증기를 필수화
- 결론
  - 기술사 판단: 환경이 불확실하면 재계획 중심 Plan-and-Execute, 정형·호출 효율 우선이면 ReWOO로 이원화함
  - 향후 방향: 플래닝은 협업(013)·오케스트레이션(014)과 결합해 목표 분해-배분-구동의 자율 실행 파이프라인으로 확장됨
