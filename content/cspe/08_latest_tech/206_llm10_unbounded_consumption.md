# 📖 【암기용】 개념 완전 이해

## 한눈에
- **정의**: OWASP LLM Top 10의 취약점으로, 사용자가 AI 모델에 **아주 복잡하고 긴 질문을 던지거나 무한 루프 작업을 지시하여, 서버의 값비싼 GPU 자원을 고갈시키고 막대한 클라우드 요금 폭탄을 유발하는 AI 맞춤형 자원 고갈 공격(Model DoS)**.
- **필요성**: 기존의 디도스(DDoS)는 수만 대의 좀비 PC로 깡통 요청을 쏘는 거지만, AI 시대에는 해커 1명이 똑똑한 질문("파이 값을 무한대로 계산해") 하나만 던져도 백엔드의 최신 엔비디아 GPU 하나가 통째로 묶여버림. 다른 정상 고객들은 서비스 지연을 겪고, 회사는 하룻밤 새 수천만 원의 클라우드 토큰(Token) 청구서를 받게 됨.
- **핵심 직관**: 레스토랑 주방장 혹사시키기. 일반적인 디도스는 식당 문 앞에 알바생 1만 명을 세워 진짜 손님을 막는 것임. 반면 **무제한 소비(LLM10)**는 손님 1명이 식당에 들어와서, 주방장(GPU)에게 "메뉴판에 있는 요리 1,000개를 쌀알 1개 단위로 다져서 내와"라고 주문하는 것. 주방장은 이 한 주문을 치르느라 쓰러지고 다른 테이블은 모두 굶게 됨.

## 깊이 이해
- **배경**: LLM API(오픈AI 등)는 글자 수(Token) 단위로 과금됨. 또한 트랜스포머 아키텍처의 셀프 어텐션(Self-Attention) 특성상 입력이 길어질수록 연산량은 $O(N^2)$로 기하급수적으로 폭증함. 이 비대칭성(Asymmetry)을 노린 경제적 공격(Economic Denial of Sustainability, EDoS)이 부상함.
- **작동 원리 (자원 고갈의 3대 매커니즘)**:
  1. **긴 컨텍스트 공격 (Long Context)**: 허용된 최대 텍스트 길이(예: 128K 토큰)를 꽉 채운 무의미한 문서를 던지고 "이걸 한 줄로 요약해"라고 시킴. VRAM(GPU 메모리)이 오버플로우됨.
  2. **장문 출력 유도 (Unbounded Output)**: "지금부터 1부터 10억까지 숫자를 소리 내어 세어줘"라고 프롬프트 입력. LLM은 한 단어 생성 시마다 이전 맥락을 전부 다시 읽어야(Autoregressive) 하므로, 출력이 길어질수록 연산이 극단적으로 느려지고 비싸짐.
  3. **에이전트 무한 루프 (Tool Loop)**: 자율 에이전트에게 모순된 지시("A가 맞는지 웹 검색해보고, 틀리면 B를 검색하고, 둘 다 아니면 다시 A를 검색해")를 내려, 모델 스스로 무한히 외부 API를 호출하며 핑퐁을 치게 만듦.
- **구체 예시**: 2023년 발생한 특정 번역 AI 서비스 마비 사건. 공격자가 정상 문장이 아닌 "!!!???..." 처럼 반복되는 특수기호를 입력함 (이른바 Sponge Example 공격). AI 모델의 내부 연산 복잡도가 급상승하여 0.1초 만에 끝나야 할 번역이 20초 이상 걸렸고, 이런 쿼리 100개만으로 서비스 전체가 다운됨.
- **흔한 오해/주의점**: "AWS WAF(웹 방화벽)로 IP당 접속 횟수 제한(Rate Limit)하면 되지 않나요?" $\rightarrow$ 못 막음. WAF는 네트워크 트래픽(초당 10번 접속 금지)만 통제할 뿐, 1시간에 1번 접속해서 "10시간짜리 연산"을 던지는 공격은 그냥 통과시켜버림. 방어는 반드시 애플리케이션 '토큰(Token)' 단위에서 이루어져야 함.

## 연결 개념
- **FinOps (클라우드 재무 관리)**: IT 인프라 비용을 통제하는 개념. LLM10 취약점은 보안 사고일 뿐만 아니라 기업의 재무 상태를 파괴하는 FinOps 리스크임.
- **Token Bucket / Rate Limiting**: 전통적 API 호출 수(RPM) 제한을 넘어, 이제는 "분당 소모 토큰 수(TPM)" 제한을 적용해야 함.
- **Circuit Breaker (서킷 브레이커)**: 과부하가 걸렸을 때 시스템 전체가 죽기 전, 알아서 연결을 끊어버리는 최후의 차단 스위치.

# 📝 【답안용】 시험 답안 템플릿
## 핵심 인사이트 (3줄 요약)
- **본질**: 거대 언어 모델(LLM)의 생성적 특성(Autoregressive)과 비대칭적인 연산 비용($O(N^2)$ 복잡도)을 악용하여, 공격자가 극소수의 요청만으로 백엔드 GPU 자원을 고갈시키거나 막대한 API 과금을 유발하는 애플리케이션 계층 서비스 거부(Model DoS) 취약점.
- **가치**: 기존의 볼류메트릭(Volumetric) 네트워크 DDoS 방어 솔루션(WAF, L4스위치)을 무력화하며, 서비스 가용성(Availability) 파괴와 함께 종량제(Pay-as-you-go) 환경에서 막대한 경제적 타격(EDoS)을 동반하는 AI 생태계의 고질적 위협임.
- **판단 포인트**: 네트워크 계층의 방어만으로는 대응이 불가능하므로, AI API Gateway를 도입하여 입력/출력 토큰의 강제 제한(Hard Capping), TPM(Tokens Per Minute) 기반의 할당량(Quota) 제어, 장기 실행 트랜잭션의 서킷 브레이커(Circuit Breaker) 아키텍처를 적용해야 함.

## Ⅰ. 개요 및 필요성
- **정의**: 시스템이 사용자의 입력 크기, 출력 생성 길이, 에이전트의 도구 호출 횟수를 엄격히 제한하지 않아, 악의적이거나 잘못된 쿼리에 의해 메모리(VRAM)와 연산 자원(Compute)이 무제한으로 소비되는 결함.
- **배경**: 최신 LLM이 컨텍스트 윈도우(Context Window)를 1M 토큰 이상 확장하고 무한한 출력을 지원함에 따라, 사용자 1명이 소모할 수 있는 최대 자원의 한계선(Ceiling)이 통제 불능 상태에 도달함.
- **필요성**: OWASP LLM Top 10에 규정된 필수 대응 항목으로, AI 서비스의 경제적 지속 가능성을 확보하고 타 정상 사용자에 대한 서비스 품질(SLA) 저하를 방지하기 위함.

## Ⅱ. 무제한 소비(LLM10) 공격의 3대 발생 벡터
LLM의 아킬레스건(자원 병목)을 찌르는 패턴.
| 공격 벡터 (Vectors) | 메커니즘 및 징후 (Mechanism) | 피해 임팩트 |
|:---:|:---|:---|
| **입력 플러딩 (Input DoS)** | 허용 한계에 가까운 방대한 텍스트나 복잡도 높은 특수 문자열(Sponge Example)을 주입하여 어텐션(Attention) 연산을 포화시킴. | VRAM 오버플로우로 인한 컨테이너 OOM(Out of Memory) 크래시. |
| **출력 극대화 (Output DoS)** | "반복문 작성해", "무한대의 자리수 소수 출력해" 등 모델 스스로 계속 토큰을 생성하게 유도하는 프롬프팅. | 스레드(Thread)를 장기 점유하여 타 요청 큐잉 지연 (가용성 장애). |
| **도구/에이전트 무한 루프** | 자율 에이전트에게 핑퐁을 치는 모순된 룰을 지시하여, 자체 검색 API나 서드파티 플러그인을 무한 호출하게 만듦. | 서드파티 API(구글 맵 등) 호출 과금 폭탄 및 계정 락다운(Lock-down). |

## Ⅲ. 기존 네트워크 DDoS와 Model DoS(LLM10)의 비교
| 구분 | 기존 DDoS 공격 | Model DoS (LLM10) |
|:---:|:---|:---|
| **공격 매개체** | 봇넷(Botnet)을 통한 대규모 트래픽 발생 | **소수 계정에서 발송된 정교한 무거운 프롬프트** |
| **타겟 레이어** | L3/L4 (네트워크 대역폭), L7(세션) | **L7 이상 (AI 모델 추론 엔진 및 GPU 연산)** |
| **탐지 지표** | BPS (Bits Per Second), QPS (Queries) | **TPM (Tokens Per Minute), GPU 활용률, 큐 지연(Queue Delay)** |
| **방어 솔루션** | Cloudflare, CDN, L4 방화벽 | **AI Gateway, 토큰 쿼터(Quota) 제한, FinOps 모니터링** |

## Ⅳ. LLM10 방어 아키텍처 (Resilience Design)
가용성과 지갑을 동시에 방어하는 다층 통제망.
1. **입/출력 길이의 하드 캡(Hard Capping) 강제**:
   - 백엔드 모델로 쿼리를 넘기기 전, API 게이트웨이에서 입력 텍스트의 바이트(Byte) 및 토큰 사이즈를 검증.
   - LLM 호출 파라미터에 `max_tokens` (최대 생성 토큰 수)를 반드시 명시적으로 설정하여 무한 생성 방지.
2. **토큰 단위 할당량(Quota) 및 쓰로틀링(Throttling)**:
   - 사용자 계정(API Key) 또는 IP별로 RPM(분당 요청 수)뿐만 아니라 **TPM(분당 생성 토큰 수)** 할당량을 적용. 쿼터 초과 시 HTTP 429(Too Many Requests) 반환.
3. **타임아웃(Timeout) 및 서킷 브레이커 (Circuit Breaker)**:
   - 단일 추론(Inference) 요청이 지정된 시간(예: 30초)을 초과하거나 GPU 점유율이 90% 이상으로 치솟을 경우, 백그라운드 프로세스를 강제 종료(Kill)하는 타임아웃 룰 적용.
4. **시맨틱 캐싱 (Semantic Caching)**:
   - 반복적인 헤비 쿼리(Heavy Query) 공격 시, 매번 GPU를 깨우지 않도록 Redis 기반의 시맨틱 캐시(비슷한 질문은 이전 답변 반환)를 구축하여 연산 자원 보호.

## Ⅴ. 실무 적용 및 결론
- **판단 지표**: AI 서버의 P99 응답 지연(Latency) 안정성, 사용자당 일일 최대 소모 토큰 비율(FinOps 모니터링), OOM(Out of Memory)으로 인한 런타임 재시작 빈도수.
- **실무 설계**: IT 플랫폼 G사의 'AI 기반 로그 분석 어시스턴트' 사내 도입. 오픈 첫 주, 특정 부서에서 테라바이트급 에러 로그를 한 번에 챗봇에 밀어 넣고 분석을 지시하여 GPU 서버가 다운되고 클라우드 빌링(Billing) 알럿이 울리는 LLM10 사고 발생. 조치 방안: 1) Kong API Gateway를 도입하여 AI 엔드포인트 앞단에 '유저당 최대 16K 토큰 컨텍스트 제한' 및 `max_output_tokens=2048` 강제 세팅. 2) 프롬프트 텍스트의 압축(Prompt Compression) 알고리즘 적용으로 불필요 공백 및 특수문자 제거. 3) 클라우드 과금 한도 80% 도달 시 해당 API 키를 자동 정지시키는 웹훅(Webhook) 연동. 서비스 안정화 달성.
- **결론**: 무제한 소비 취약점(LLM10)은 개발자의 실수라기보다는 딥러닝 트랜스포머 아키텍처의 태생적 비용 구조가 낳은 필연적 위협이다. "트래픽이 적다고 안전한 것이 아니다"라는 AI 시대의 새로운 가용성 패러다임을 인지하고, 모든 AI 서비스의 설계 초기(Shift-left) 단계부터 토큰 예산(Token Budget) 통제와 에이전트 자율성 제한을 최우선으로 아키텍처에 내재화해야 한다.

### 🔀 문제 유형별 목차 전환
- **Ⅱ·Ⅲ 강조 (개념/원리형)**: 모델 병목을 유발하는 트랜스포머의 '어텐션 메커니즘'의 연산 텐서 사이즈 증가(Quadratic Complexity) 원리와 KV-Cache(Key-Value Cache) 메모리 고갈 메커니즘 구조화.
- **Ⅴ·Ⅵ 강조 (실무/설계형)**: 트래픽 스파이크(Model DoS) 발생 시 쏟아지는 동시 요청을 다운타임 없이 방어하기 위해 vLLM의 'Continuous Batching(연속 배치)'과 'PagedAttention(페이징 어텐션)' 기술을 결합한 고가용성 추론 서버 아키텍처 설계 방안.
