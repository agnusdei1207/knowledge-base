# 📖 【암기용】 개념 완전 이해

## 한눈에
- **개요**: **Tool Use**는 LLM이 과업을 수행하는 과정에서 자신의 지식 범위를 벗어나는 작업을 외부 시스템(API, 데이터베이스, 코드 실행기 등)에 위임하여 처리하는 기술이다.
- **필요성**: LLM은 학습 데이터 시점 이후의 실시간 정보가 없고(Knowledge Cutoff), 복잡한 수치 계산이나 파일 조작에 취약하다. Tool Use를 통해 이러한 물리적/논리적 한계를 극복한다.
- **핵심 직관**: **"LLM에게 전용 장비와 연장통을 쥐여주는 것"**. 필요할 때 망치(계산기)를 꺼내 쓰고 돋보기(검색)를 쓰는 능력이다.

## 깊이 이해
- **배경 (Extending LLM Capabilities)**: 단순한 텍스트 생성을 넘어 "실행"의 영역으로 확장하려는 시도다. 초기에는 프롬프트에 "계산기를 써"라고 지시하는 수준이었으나, 현재는 모델 아키텍처 수준에서 정형화된 호출 규격을 지원한다.
- **작동 원리 (The Tool Use Flow)**:
    1. **Tool Definition**: 사용 가능한 도구들의 이름, 기능 설명, 입력 파라미터 규격을 **JSON Schema** 형태로 모델에게 제공.
    2. **Tool Selection**: LLM이 사용자의 요청을 분석하고, 도구 목록 중 가장 적합한 것을 선택.
    3. **Parameter Generation**: 선택한 도구의 규격에 맞는 인자(Arguments)를 생성. (예: `get_weather(city="Seoul")`)
    4. **Execution & Feedback**: 외부 시스템이 실제 실행하고 그 결과를 모델에게 다시 전달.
- **비유**: 실력은 좋지만 손이 없는 기술자(LLM)에게 조수(Tool Executor)가 연장(Tool)을 대신 써주고 그 결과를 말해주는 시스템과 같다.
- **구체 예시**: `Claude 3.5 Sonnet`의 Tool Use 기능, `OpenAI`의 Tools API 등.
- **주의점**: **보안(Security)**이 가장 중요하다. 에이전트에게 파일 삭제나 전금법 위반 소지가 있는 API 권한을 무분별하게 주면 안 된다.

## 연결 개념
- **Function Calling (005)**: Tool Use를 구현하는 구체적인 프로그래밍 방식.
- **MCP (006)**: 도구와 에이전트를 연결하는 최신 표준 규격.
- **ReAct 패턴 (003)**: 도구를 언제, 왜 쓸지 결정하는 사고 루프.

# 📝 【답안용】 시험 답안 템플릿

## 핵심 인사이트 (3줄 요약)
> 1. **본질**: LLM이 텍스트 생성을 넘어 외부 API, 데이터베이스, 소프트웨어 기능과 상호작용하도록 하는 역량 확장 기술.
> 2. **가치**: 실시간 정보 접근, 정확한 연산, 파일 시스템 제어 등 LLM의 태생적 한계(Cutoff, Hallucination)를 물리적 실행으로 해결.
> 3. **판단 포인트**: 정확한 파라미터 추출을 위한 **JSON Schema 기반의 강제된 구조화 출력(Structured Output)** 기술이 핵심.

## 출제 의도 및 답안 포인트
- **출제 의도**: 에이전트 시스템의 필수 구성 요소인 '도구 활용'의 원리와 보안적 고려사항 이해 여부.
- **핵심 포인트**: JSON Schema, 파라미터 추출, Grounding, 보안 가드레일.

---

## Ⅰ. Tool Use(도구 호출)의 정의 및 기술적 필요성
### 1. Tool Use의 정의
- LLM이 자율적으로 외부 인터페이스(API, SDK, CLI 등)를 식별하고, 해당 기능을 실행하기 위한 구조화된 인자(Arguments)를 생성하여 작업을 위임하는 프로세스.
### 2. 기술적 필요성
- **최신성 결여 해결**: 학습 데이터 컷오프(Cutoff) 이후의 실시간 정보(뉴스, 주가 등) 획득.
- **정확도 향상**: 복잡한 수학 연산이나 코드 실행을 전용 엔진에 위임하여 환각(Hallucination) 제거.
- **실제 영향력 행사**: 이메일 발송, DB 업데이트, 클라우드 리소스 생성 등 실제 시스템 변경 수행.

---

## Ⅱ. Tool Use의 작동 프로세스 및 핵심 기술
- **JSON Schema 기반의 정교한 연동 구조**
1. **Tool Specification (명세)**:
   - 도구의 기능과 파라미터 타입을 정의. (예: `type: object`, `properties: { location: { type: string } }`)
2. **Context Injection (주입)**:
   - 시스템 프롬프트에 사용 가능한 도구 목록과 사용 지침을 주입.
3. **Structured Output (구조화 출력)**:
   - LLM이 자유 양식이 아닌 정해진 JSON 포맷으로 응답하도록 강제.
4. **Execution & Observation**:
   - 에이전트 런타임이 JSON을 파싱하여 실제 호출을 수행하고 결과를 수집.

---

## Ⅲ. 주요 도구(Tool)의 유형 및 활용 사례

| 도구 유형 | 주요 기능 | 활용 사례 |
|:---:|:---|:---|
| **Information Retrieval** | 웹 검색, 기업 내부 DB 조회 | 실시간 뉴스 요약, 사내 규정 검색 |
| **Computational Tools** | 계산기, Wolfram Alpha, Python 인터프리터 | 정밀한 재무 분석, 데이터 시각화 코드 실행 |
| **Action Tools** | Slack API, Jira API, 이메일 시스템 | 장애 티켓 생성, 팀원에게 업무 자동 공유 |
| **Data Processing** | SQL 클라이언트, 벡터 검색 | 거대 데이터셋 통계 산출, 의미 기반 문서 추출 |

---

## Ⅳ. Tool Use 구현 시 보안 및 운영 고려사항
- **보안 가드레일 (Security Guardrails)**:
    - **RBAC**: 에이전트에게 최소 권한(Least Privilege)만 부여.
    - **Sandboxing**: 코드 실행 도구는 반드시 격리된 컨테이너 환경에서 운영.
    - **HITL (Human-in-the-Loop)**: 승인이 필요한 도구(예: 결제, 삭제)는 실행 전 사람의 컨펌 절차 설계.
- **운영 최적화**:
    - **Token Management**: 도구 명세가 너무 많으면 컨텍스트 비용이 증가하므로 필요 시점에만 관련 도구 노출.
    - **Retry Logic**: 외부 API 장애 시 재시도 또는 대체 도구 선택 로직 필요.

---

## Ⅴ. Tool Use vs RAG(검색증강생성) 비교

| 비교 항목 | RAG (Retrieval-Augmented) | Tool Use (Agentic) |
|:---:|:---|:---|
| **주요 목적** | 정적인 지식 보강 및 답변 보조 | 능동적 과업 수행 및 환경 변화 |
| **동작 방식** | 질문과 유사한 문서를 '참조' | 특정 기능을 '실행' |
| **결과 형태** | 보강된 텍스트 응답 | 시스템 상태 변화 또는 실행 결과 |
| **상호작용** | 단회성 (One-off) | 다회성 (Iterative loop 내 포함 가능) |

---

## Ⅵ. 미래 전망: 자율적 도구 생태계
- **Autonomous Tool Creation**: 에이전트가 스스로 필요한 도구(스크립트)를 작성하고 등록하여 사용하는 수준으로 진화.
- **결론**: Tool Use는 LLM을 단순한 '말동무'에서 '유능한 일꾼'으로 바꾸는 기술적 변곡점이며, 이를 위해 표준화된 도구 연결 규격(MCP 등)의 도입이 가속화될 것임.

### 🔀 문제 유형별 목차 전환
- **기술형**: Ⅱ. 작동 프로세스(JSON Schema)와 Ⅳ. 보안(Sandboxing) 강조.
- **활용/설계형**: Ⅲ. 도구 유형과 Ⅴ. RAG 비교를 통한 에이전트 도입 타당성 강조.
