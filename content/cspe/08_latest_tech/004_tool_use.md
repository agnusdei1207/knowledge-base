# 📖 【암기용】 개념 완전 이해

## 한눈에
- **개요**: **Tool Use**(도구 호출)는 **LLM**이 스스로 못 하는 일(최신 검색·정확한 계산·DB 조회·시스템 조작)을 **외부 도구**(API·함수·검색엔진·코드 실행기)에 위임해 처리하는 **LLM 확장 패턴**이다.
- **왜 필요한가**: LLM은 학습 시점에 고정된 지식을 확률적으로 생성할 뿐, 오늘 날씨·정확한 사칙연산·실시간 재고를 알지 못한다. 모르는 것은 도구에게 물어 사실로 채워야 환각이 줄고 실제 행동이 가능해진다.
- **핵심 직관**: LLM은 "무엇을 모르는지 알고, 어떤 연장을 쓸지 판단하는 두뇌"다. Tool Use는 그 두뇌가 연장(도구)을 집어 드는 **개념·패턴**이고, 그 연장을 실제로 부르는 구체 기법이 Function Calling(005), 도구 연결을 표준화한 규격이 MCP(006)다.

## 핵심 용어 정리 (내부에 등장하는 것들)
답안 본문에 등장하는 용어를 처음 보는 사람도 이해하도록 비유와 함께 먼저 정리한다.

| 용어/표기 | 의미 | 비유·예 |
|:---|:---|:---|
| Tool Use(핵심) | LLM이 외부 도구에 작업을 위임해 능력을 확장하는 패턴 | 사람이 "계산기·검색을 쓰는" 것 |
| LLM(대형 언어모델) | 학습된 텍스트로 언어를 이해·생성하는 신경망. 도구를 부를지 판단하는 주체 | 판단하는 "두뇌" |
| 도구(Tool) | 검색·계산·DB·코드 실행 등 외부 기능. 이름·설명·입력형식을 가짐 | 두뇌가 쓰는 "연장" |
| 파라메트릭 지식 | 모델 가중치에 담긴 학습 시점 고정 지식 | 머릿속 "암기한 내용" |
| 그라운딩(Grounding) | 도구가 준 실제 사실에 답을 근거 짓는 것 | 소문 대신 "출처 확인" |
| 도구 명세(Tool Spec) | 도구 이름·용도·입력 인자를 기술한 설명서 | 연장에 붙은 "사용 설명서" |
| 라우팅(도구 선택) | 여러 도구 중 지금 상황에 맞는 것을 고르는 판단 | 상황 맞는 "연장 고르기" |
| Function Calling | 도구 명세를 받아 호출용 JSON 인자를 생성하는 구체 구현 기법(005) | 연장을 실제로 "집어 드는 손동작" |
| MCP | 도구 연결을 표준화한 개방 프로토콜(006) | 연장용 "USB-C 표준" |
| 실행 루프(Agent Loop) | 도구 호출→결과 관찰→재판단을 반복하는 구조(003 ReAct) | "생각-확인-생각" 반복 |
| 환각(Hallucination) | 모델이 사실이 아닌 내용을 그럴듯하게 지어내는 것 | 모르면서 "지어낸 답" |

## 깊이 이해
- **배경·문제의식**: 초기 LLM 활용은 프롬프트만으로 답을 짜내는 방식이라 두 한계가 있었다. ① 학습 이후의 사실(오늘 환율, 방금 배포)을 모른다. ② 확률적 생성이라 15자리 곱셈 같은 정밀 계산에 약하다. 이 둘을 모델 재학습으로 해결하려면 비용·시간이 크고 실시간성도 없다. 그래서 "모델을 더 키우지 말고, 모르는 것은 도구에게 물어보자"는 발상이 Tool Use다.
- **작동 원리(어떻게+왜)**: 모델에 사용 가능한 도구의 이름·용도·입력형식(명세)을 알려주면, 모델은 사용자 요청을 보고 "이건 내 지식으로 답할지, 도구를 부를지"를 먼저 판단(라우팅)한다. 도구가 필요하면 어떤 도구를 어떤 입력으로 부를지 결정하고, 도구가 돌려준 실제 결과를 근거(그라운딩)로 최종 답을 만든다. 핵심은 **모델이 직접 실행하지 않고 "호출 의도"만 만들며, 실제 실행은 외부 런타임이 맡는다**는 점이다. 이 분리 덕분에 권한·비용·감사를 실행 계층에서 통제할 수 있다.
- **비유**: 유능한 상담원이 모든 걸 외우지 않고, 재고는 창고 시스템에, 배송은 물류 API에 조회해 답하는 것과 같다. 상담원(LLM)의 역할은 "무엇을 어디에 물을지" 판단이고, 실제 데이터는 각 시스템(도구)이 준다.
- **구체 예시(실제 프레임워크·표준)**: OpenAI Function Calling, Anthropic Claude tool use, LangChain Tools, Google Gemini function calling이 모두 이 패턴을 구현한다. 예: "서울 오늘 미세먼지 알려줘"에서 모델이 대기질 API를 도구로 선택→호출→응답 수치를 근거로 답한다. 계산·코드 실행은 Code Interpreter류 도구에 위임한다.
- **흔한 오해·주의점**: Tool Use는 특정 API 문법이 아니라 "외부 능력에 위임한다"는 **상위 개념·패턴**이다. 이를 실제로 구현하는 방법이 Function Calling(005)이고, 도구를 표준 규격으로 연결하는 것이 MCP(006)다. 또한 도구를 붙였다고 안전한 게 아니라, 잘못된 도구 선택·악의적 도구 결과(간접 프롬프트 인젝션)·과도한 권한이 새 위험이 되므로 도구 권한 격리가 필수다.

## 연결 개념
- Function Calling(005) — Tool Use를 실제로 구현하는 인자 생성·호출 기법
- MCP(006) — 도구 연결을 표준화한 개방 프로토콜
- ReAct(003)·에이전트 시스템(001) — Tool Use가 반복 실행되는 상위 루프·아키텍처

# 📝 【답안용】 시험 답안 템플릿

## 핵심 인사이트 (3줄 요약)

> 1. **본질**: Tool Use는 LLM이 못 하는 작업을 외부 도구에 위임해 능력을 확장하는 패턴임.
> 2. **가치**: 재학습 없이 최신성·정확성·실행력을 확보해 환각을 줄이고 실제 행동을 가능케 함.
> 3. **판단 포인트**: 도구 선택 정확도·결과 그라운딩·도구 권한 격리를 함께 설계해야 함.

## 출제 의도 및 답안 포인트

| 출제 의도 | 반드시 짚을 핵심 | 감점 회피 포인트 |
|:---|:---|:---|
| LLM 능력 확장 원리 이해 | 위임·라우팅·그라운딩, 호출 의도와 실행의 분리 | Function Calling 구현 문법으로 축소 서술 시 감점 |
| 도구 연동 시 위험·통제 인식 | 도구 권한 격리, 결과 검증, 인젝션 대응 | 도구만 붙이면 된다는 식의 통제 누락 시 감점 |

> 요약: 왜 도구가 필요하고 어떻게 위임·근거화하며 무엇을 통제하는지를 함께 확인하려는 문제임.

---

## Ⅰ. 개요 및 필요성

- 개요: LLM이 외부 도구에 작업을 위임해 능력을 확장하는 패턴임
- 배경: LLM은 학습 시점 고정 지식·확률적 생성이라 최신 사실·정밀 계산·시스템 조작에 취약함
- 필요성: 재학습 대신 도구 결과로 답을 근거 지어 환각을 줄이고 실제 행동을 수행해야 함
- 위치: 구현 기법은 Function Calling(005), 연결 표준은 MCP(006)로 위임되는 상위 개념임

---

## Ⅱ. 구조 및 구성요소

- 선형 구조도

```text
사용자 요청 -> LLM(도구 필요 판단·도구 선택) -> 도구 명세 조회
  -> 호출 의도 생성 -> 실행 런타임(권한 검사 후 도구 실행) -> 결과 관찰
  -> LLM(결과 근거로 최종 답 생성)
```

| 구성요소 | 역할 | 특이사항 |
|:---|:---|:---|
| LLM | 도구 필요성·도구 선택·최종 응답 판단 | 실행은 하지 않고 의도만 생성 |
| 도구 명세 | 이름·용도·입력형식 기술 | 설명 품질이 선택 정확도 좌우 |
| 실행 런타임 | 도구를 실제 호출·결과 반환 | RBAC·allowlist·비용 한도 적용 |
| 결과 관찰 | 도구 응답을 답의 근거로 반영 | 출처·응답코드·신뢰도 확인 |

> 요약: 모델은 호출 의도만 만들고 실행·통제는 외부 런타임이 맡는 분리 구조임.

---

## Ⅲ. 동작원리 및 흐름도

- 선형 흐름도

```text
요청 수신 -> 도구 필요 판단 -> 도구 선택·입력 결정 -> 실행·결과 수신 -> 근거화 -> 최종 답변
```

1. 필요성 판단: 내부 지식으로 답할지, 도구가 필요한지 라우팅 결정
2. 도구 선택: 명세를 근거로 적합한 도구와 입력 인자 결정
3. 실행·관찰: 런타임이 권한 검사 후 호출, 결과·오류·출처 수신
4. 근거화 응답: 도구 결과를 근거로 최종 답 생성, 실패 시 대체 도구·재시도

> 요약: 도구 선택의 정확성과 결과 근거화가 최종 답 품질을 좌우함.

---

## Ⅳ. 특징

- 능력 확장: 재학습 없이 검색·계산·조회·실행 능력을 모델 밖에서 붙임
- 최신성 확보: 학습 이후 사실도 도구 조회로 실시간 반영함
- 그라운딩: 도구가 준 실제 데이터에 답을 근거 지어 환각을 줄임
- 실행·판단 분리: 모델은 의도만 만들고 실행·권한 통제는 런타임이 담당함
- 신규 위험: 잘못된 도구 선택·악의적 결과·과도한 권한이 새 공격면이 됨

---

## Ⅴ. 심화 비교 및 적용 판단

- 모델에 새 능력·지식을 주는 방식 관점에서 파인튜닝과 대비함

| 구분 | 파인튜닝 | Tool Use |
|:---|:---|:---|
| 지식 반영 | 가중치에 학습해 내재화 | 호출 시점에 외부에서 조달 |
| 최신성 | 재학습 전까지 고정 | 실시간 최신 데이터 반영 |
| 정밀 연산 | 여전히 확률적 근사 | 계산 도구로 정확히 처리 |
| 비용·주기 | 데이터·GPU·재학습 필요 | 도구 연결만으로 즉시 적용 |
| 근거 추적 | 출처 불명확 | 도구 응답·출처로 검증 가능 |

> 요약: 실시간성·정확성·행동이 필요하면 Tool Use, 고유 문체·도메인 내재화가 필요하면 파인튜닝이 적합하며 둘은 상호보완임.

- 주요 리스크와 대응(불릿)
  - 도구 오선택: 명세 설명 부실이 원인 → 용도·예시 포함한 명세 개선, 선택 로그 평가
  - 결과 오염: 도구 응답에 악성 지시 삽입(간접 인젝션) → 결과를 데이터로만 처리·필터링
  - 권한 남용: 도구 권한 미격리가 원인 → RBAC·allowlist·고위험 작업 HITL 승인

- 도입 효과 지표(불릿)
  - 도구 선택 정확도 90% 이상(정답 도구 대비 선택 로그 평가)
  - 근거 포함 응답률 95% 이상(출처 첨부 비율)
  - 환각 응답률 5% 이하(사실성 평가 샘플링)

---

## Ⅵ. 실무 적용 및 결론

- 적용 방안
  1. LangChain Tools·Claude tool use로 도구를 명세와 함께 등록하되 용도·입력 예시를 상세화해 선택 정확도 확보
  2. 실행 런타임에 RBAC·allowlist·비용 한도를 두고 고위험 도구는 HITL 승인으로 분리
  3. 도구 응답을 출처·응답코드·Timestamp와 함께 로그로 남겨 근거 추적과 감사 가능화
- 결론
  - 기술사 판단: 최신 조회·정밀 계산·시스템 조작 업무는 Tool Use, 도메인 문체 내재화는 파인튜닝을 적용함
  - 향후 방향: Tool Use는 Function Calling 표준화(005)와 MCP 상호운용(006)을 통해 에이전트 능력 확장의 기본 축으로 정착됨
