# 📖 【암기용】 개념 완전 이해

> 목적: Tool Use를 처음 봐도 완벽히 이해하게 만든다.

## 한눈에
- **개요**: LLM이 외부 API·검색·DB·코드 실행기를 선택해 호출하는 기능
- **왜 필요한가**: LLM 내부 지식은 최신 업무 데이터, 사내 권한, 계산 결과를 직접 보장하지 못함.
- **핵심 직관**: 모델이 모르는 것은 도구에 물어보고, 할 수 없는 일은 도구로 실행함.

## 깊이 이해
- **배경·문제의식**: LLM 단독 답변은 학습시점 이후 데이터와 조직 내부 상태를 반영하지 못함.
- **작동 원리**: 모델이 도구 설명과 입력 스키마를 보고 호출 여부를 결정하며, 결과를 다시 프롬프트 컨텍스트에 넣어 답변함.
- **비유**: 의사가 진단 중 혈액검사·영상검사 결과를 호출해 판단을 보정하는 구조.
- **구체 예시**: 재고 문의에서 LLM이 ERP API를 호출해 현재 수량 42개, 입고 예정 2026-07-03을 응답에 반영함.
- **흔한 오해·주의점**: 도구 호출은 자동화 권한을 의미하므로 읽기·쓰기·삭제 권한을 분리해야 함.

## 연결 개념
- Function Calling — 구조화된 함수 호출 방식
- MCP — 도구와 자원을 연결하는 프로토콜
- Prompt Injection — 도구 결과를 통한 명령 오염 위험

# 📝 【답안용】 시험 답안 템플릿

> 목적: 시험장에서 25분에 그대로 쓰는 답안 양식.

## 핵심 인사이트 (3줄 요약)

> 1. **본질**: Tool Use는 LLM이 외부 시스템 기능을 구조화된 입력으로 호출하는 실행 메커니즘임.
> 2. **가치**: 최신 데이터 조회, 정확 계산, 업무 시스템 조작을 LLM 응답 흐름에 결합함.
> 3. **판단 포인트**: 도구 스키마, 권한 분리, 입력 검증, 호출 로그가 설계 핵심임.

## 출제 의도 및 답안 포인트

| 출제 의도 | 반드시 짚을 핵심 | 감점 회피 포인트 |
|:---|:---|:---|
| LLM 외부 도구 호출 구조와 실행 제어 이해 | 도구 선택·스키마 검증·권한 분리·결과 정제 | "도구 사용" 단순 서술 — 권한·감사·비용 통제 누락 시 감점 |
| 업무 자동화 시 보안·운영 설계 역량 확인 | 읽기/쓰기 권한 분리, rate limit, 프롬프트 인젝션 방어 | Function Calling과 혼동 금지 — Tool Use는 상위 개념 |

> 요약: 출제자는 도구 호출 실행 구조와 권한·검증·감사 설계를 함께 확인하려 함.

---

## Ⅰ. 개요 및 필요성

- 정의: LLM이 외부 API·검색·DB를 선택해 호출하는 실행 기능
- 배경: LLM 내부 지식은 학습 시점 이후 데이터와 조직 내부 상태를 반영하지 못함
- 필요성: 실시간 데이터 조회·업무 시스템 조작을 LLM 응답 흐름에 결합해야 함

---

## Ⅱ. 구조 및 구성요소

```text
LLM -> Tool Selector -> Schema Validator -> Tool/API
  -> Result Formatter -> LLM 응답 생성
```

| 구성요소 | 역할 | 특이사항 |
|:---|:---|:---|
| Tool Selector | 호출할 도구 선택 | 도구 설명 품질 필요 |
| Schema Validator | 입력 형식 검증 | JSON Schema 적용 |
| Tool/API | 검색·DB·업무 실행 | 읽기/쓰기 권한 분리 |
| Result Formatter | 결과를 답변 컨텍스트로 변환 | 민감정보 마스킹 |

> 요약: Tool Use는 도구 선택, 입력 검증, 실행, 결과 정제의 제어 경로로 구성됨.

---

## Ⅲ. 동작원리 및 흐름도

```text
질의 입력 -> 도구 필요성 판단 -> 파라미터 생성
        -> 스키마 검증 -> 도구 실행 -> 결과 반영
```

| 단계 | 처리 내용 | 검증 기준 |
|:---:|:---|:---|
| 1 | 질의와 도구 후보 매핑 | 도구명, 설명 일치율 |
| 2 | 입력 파라미터 생성 | 필수값, 타입, 범위 |
| 3 | 도구 실행 | 응답코드, p95 지연, 오류율 |
| 4 | 결과 반영·로그 | Trace ID, 마스킹, 출처 |

> 요약: 도구 호출 품질은 모델보다 도구 설명, 스키마 검증, 결과 정제 체계에 좌우됨.

---

## Ⅳ. 특징

| 구분 | LLM 단독 | Tool Use | 수치·판단 포인트 |
|:---|:---|:---|:---|
| 데이터 | 학습 지식 | 실시간 API·DB | 최신 시각, 출처 |
| 실행 | 텍스트 생성 | 시스템 조작 가능 | 쓰기 권한 승인 |
| 위험 | 환각 | 권한 오남용·비용 | 호출 한도, 감사로그 |

> 요약: Tool Use는 실행 범위를 확장하지만, 호출 권한과 입력 검증이 통제되지 않으면 업무 사고로 이어짐.

---

## Ⅴ. 심화 비교 및 적용 판단

| 구분 | LLM 단독 | Tool Use 적용 | 선택 기준 |
|:---|:---|:---|:---|
| 데이터 | 학습 시점 지식만 | 실시간 API·DB 조회 | 최신 데이터 필요 여부 |
| 실행 | 텍스트 생성 | 시스템 조작·트랜잭션 | 변경 작업 수행 여부 |
| 위험 | 환각 | 권한 오남용·비용 초과 | 쓰기 권한 필요 여부 |

> 요약: 실시간 조회·변경 작업이 필요하면 Tool Use, 단순 생성이면 LLM 단독을 선택함.

| 리스크 | 원인 | 대응 방안 | 확인 지표 |
|:---|:---|:---|:---|
| 권한 오남용 | 쓰기/삭제 권한 미분리 | 읽기/쓰기/삭제 RBAC 분리, 변경형 승인 필수 | 권한별 호출 비율 |
| 비용 폭주 | rate limit 미설정·반복 호출 | 도구당 분당 10회, 작업당 비용 한도 1.0 | 분당 호출 수, 누적 비용 |
| 프롬프트 인젝션 | 도구 결과에 악의적 명령 삽입 | 결과를 데이터로 처리, HTML·URL 필터 | 필터 우회율 0% |

> 요약: 권한 오남용·비용 폭주·인젝션이 주요 리스크이며, RBAC·rate limit·입력 필터로 통제함.

| 점검 항목 | 목표 기준 | 측정 방법 |
|:---|:---|:---|
| 도구 호출 성공률 | API 응답 200 비율 95% 이상 | Trace ID별 응답코드 집계 |
| 권한 위반 건수 | 월간 0건 | RBAC 로그 감사 |
| 호출 비용 | 작업당 1.0 이내 | 비용 대시보드 모니터링 |

> 요약: 호출 성공률·권한 위반·비용으로 Tool Use 도입 효과를 정량 평가함.

---

## Ⅵ. 실무 적용 및 결론

**적용 방안 3개:**
1. 도구별 JSON Schema, allowlist, rate limit, 읽기/쓰기 권한 분리를 적용
2. 외부 입력은 명령어가 아닌 데이터로 처리하고 URL·HTML·문서 결과는 프롬프트 인젝션 필터 적용
3. 모든 호출에 사용자ID, 도구명, 파라미터 해시, 응답코드, 비용을 Trace ID로 기록

**결론 (2줄):**
- 기술사 판단: 조회형 도구는 자동화하고 변경형 도구는 승인·롤백·감사 요건을 붙여야 함.
- 향후 방향: Tool Use는 MCP 기반 표준 연결과 결합해 기업 AI 실행 계층으로 정착함.
