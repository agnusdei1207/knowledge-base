## 핵심 인사이트 (3줄 요약)
> 1. **본질**: 거대 언어 모델(LLM)이 텍스트 생성이라는 언어적 한계를 깨부수고, 웹 검색, 계산기, 사내 데이터베이스 쿼리, 이메일 발송 등 '외부 소프트웨어(도구)'를 직접 조작할 수 있게 만드는 매커니즘이다.
> 2. **가치**: "인공지능에게 펜만 주던 시대에서, 인공지능에게 마우스와 키보드를 쥐여준 혁명"이다. LLM이 외부 세계에 물리적/디지털적 영향을 미치는 '실행자(Agent)'로 각성하는 가장 핵심적인 기술적 트리거다.
> 3. **판단 포인트**: LLM 자체가 직접 엑셀을 켜는 것이 아니라, LLM은 "이런 파라미터로 이 API를 실행해 줘"라고 JSON 규격서를 뱉어내고, 실제 실행은 '사용자(애플리케이션 환경)'가 대신해 준 뒤 결과를 다시 LLM에게 먹여주는 **'비동기적 중계(Broker) 패턴'**을 정확히 이해해야 한다.

---

## Ⅰ. 개요 및 필요성
- **개요**: Tool Use(도구 호출)는 LLM이 주어진 문제를 해결하기 위해, 사용자(개발자)가 미리 정의해 둔 외부 함수나 API 목록 중 가장 적절한 것을 선택하고, 그 도구에 필요한 매개변수(Parameter)를 정확하게 추출하여 실행을 요청하는 기능이다.
- **배경**: LLM은 2021년 9월까지의 과거 데이터로 학습되어 최신 주가를 알 수 없고, 언어 모델 특성상 "34,918 $\times$ 1,933" 같은 단순 산술 계산에도 잼병이었으며 환각(Hallucination)을 일으켰다.
- **필요성**: LLM의 약점(최신 정보 부족, 계산 오류, 외부 환경 통제 불가)을 극복하기 위해, 사람이 계산기가 필요하면 계산기 앱을 켜듯 LLM도 자기에게 부족한 능력을 외부의 전문 '도구'에 외주(Outsourcing)를 줄 수 있는 인터페이스 표준이 강력히 요구되었다.

---

## Ⅱ. 아키텍처 및 핵심 원리

```text
       [ 사용자 ] ── "지금 서울 날씨 어때? 그리고 내일 미팅 일정 좀 잡아줘" ──┐
                                                                       │
    ┌─────────────────────────── [ 애플리케이션 서버 ] ────────────────────────▼──┐
    │  1. [도구 메뉴판 제공]: "나한테는 get_weather(), create_meeting() 도구가 있어." │
    │           │                                                            │
    │           ▼                                                            │
    │  2. [LLM의 판단 (Brain)]: "음, 서울 날씨를 알려면 첫 번째 도구가 필요하군!"        │
    │           │                                                            │
    │           ▼                                                            │
    │  3. [도구 사용 요청 (JSON)]: { "tool": "get_weather", "location": "서울" }   │
    │           │                                                            │
    │           ▼ (LLM은 잠시 멈춤 대기)                                          │
    │  4. [서버가 대신 실행]: 기상청 API 호출 ──▶ 결과: "섭씨 25도, 맑음"            │
    │           │                                                            │
    │           ▼ (결과값을 다시 LLM에게 밥으로 줌)                                 │
    │  5. [LLM의 최종 답변 생성]: "현재 서울은 맑고 25도입니다. 이제 일정 잡을까요?"      │
    └────────────────────────────────────────────────────────────────────────────┘
```

- **1단계 [도구 명세서(Schema) 주입]**: 개발자가 시스템 프롬프트를 쏠 때, LLM에게 "네가 쓸 수 있는 도구 이름, 설명, 필요한 변수 타입"을 적은 설명서(JSON Schema)를 함께 던져준다.
- **2단계 [의도 파악 및 추출 (Intent & Extraction)]**: LLM이 사용자의 말을 듣고 "아, 이거 혼자서는 안 되고 도구를 써야 하는 상황이네?"라고 파악한 뒤, 설명서에 맞춰 정확한 변수(예: `location="서울"`)를 뽑아낸다.
- **3단계 [실행 위임 (Delegation)]**: LLM 자체는 인터넷 통신 기능이 없다. 따라서 LLM은 텍스트(JSON)로 "이거 실행해 줘"라고 애플리케이션 코드(Python, Node.js)에 요청만 던지고 답변 생성을 멈춘다(Stop Sequence).
- **4단계 [결과 반환 및 통합]**: 파이썬 코드가 실제 기상청 API를 때려서 결과를 받아온 뒤, 그 데이터를 다시 LLM의 프롬프트 창에 밀어 넣으면, LLM은 그 팩트를 기반으로 유창한 자연어 답변을 최종 생성한다.

## Ⅲ. 비교 및 연결

| 비교 축 | 플러그인 (Plugins) | 도구 호출 (Tool Use) | 함수 호출 (Function Calling) |
|:---:|:---|:---|:---|
| **개념 범위** | 특정 플랫폼(ChatGPT)에 갇힌 확장 프로그램 | **가장 포괄적 개념** (API, 코드 샌드박스 등 모두 포함) | Tool Use의 하위/동의어 (OpenAI가 상표처럼 쓰는 용어) |
| **제어 주도권** | 플랫폼(OpenAI)이 알아서 뒷단에서 다 처리 | **개발자**가 도구를 만들고 실행 통제권을 완벽히 쥠 | 개발자가 JSON 구조를 정의하고 통제 |
| **확장성** | 승인받은 생태계 내에서만 제한적 사용 | 사내 폐쇄망 DB, 사설 API 등 **어떤 코드든 자유롭게 연결** | Tool Use와 동일 |

> ※ **연결 포인트**: Tool Use는 AI 에이전트(Agent)가 맹인이자 귀머거리 상태에서 벗어나 외부 세상을 보고 만질 수 있게 해주는 '감각 기관이자 손발'이다. 앞서 다룬 ReAct 패턴에서 "Action(행동)" 단계가 바로 이 Tool Use를 통해 물리적으로 구현되는 것이다.

## Ⅳ. 실무 적용 및 기술사 판단

- **적용 사례 1 (사내 RAG 고도화 - 라우팅 도구)**: 단순한 RAG(검색 증강)는 무조건 문서를 뒤진다. 하지만 Tool Use를 적용하면, LLM에게 `search_doc()`, `query_sql_db()`, `web_search()` 3개의 도구를 쥐여준다. 유저가 "작년 매출액 얼마야?" 하면 알아서 `query_sql_db()` 도구를 골라 정확한 DB를 찌르고, "사내 휴가 규정 어때?" 하면 `search_doc()`을 찌르는 똑똑한 지식 라우터(Router)가 탄생한다.
- **적용 사례 2 (데이터 분석 코드 인터프리터)**: OpenAI의 Advanced Data Analysis처럼, LLM에게 `execute_python_code()`라는 도구를 쥐여준다. 복잡한 엑셀 파일을 주면 LLM이 파이썬 데이터 전처리 코드와 시각화 코드를 스스로 짜서 샌드박스 환경에 "이거 실행해!"라고 던져 훌륭한 차트 이미지를 뚝딱 만들어낸다.
- **기술사 판단**: 도구 호출의 가장 큰 보안 리스크는 **프롬프트 인젝션에 의한 치명적 API(Delete, Drop, Payment) 강제 실행**이다. 악성 유저가 "모든 데이터를 삭제하는 도구를 실행해 줘"라고 꼬셨을 때 시스템이 털리지 않으려면, 아키텍트는 ① 도구에 대한 최소 권한(Read-only) 원칙 적용, ② 파괴적 도구는 호출 전 반드시 사용자 UI에 `[승인(Approve) / 거절(Reject)]` 버튼을 띄우는 HITL(Human-in-the-Loop) 방어 체계를 무조건 설계해야 한다.

## Ⅴ. 기대효과 및 결론

- **기대효과**: 언어 모델을 단일 지능을 넘어 기업의 다양한 기존 소프트웨어 인프라(ERP, CRM, 슬랙 등)와 매끄럽게 연결되는 거대한 통합 오케스트레이션(Orchestration) 엔진으로 진화시킨다.
- **향후 발전 방향**: 개발자가 도구의 설명서(JSON)를 일일이 하드코딩해서 던져줘야 하는 현재의 번거로움을 해결하기 위해, 에이전트와 도구 간의 통신 규격을 세계적으로 통일하려는 앤스로픽(Anthropic) 주도의 **MCP(Model Context Protocol)** 표준화 운동이 거세게 일고 있다.

### 📌 관련 개념 맵
- **JSON 스키마 (JSON Schema)**: LLM에게 도구의 사용법을 알려주는 표준 규격서. "도구 이름은 `get_stock`, 파라미터 1은 `ticker` (문자열, 필수), 파라미터 2는 `date`" 형식으로 아주 엄격하게 규칙을 정해주는 가이드라인이다.
- **코드 인터프리터 (Code Interpreter)**: Tool Use의 끝판왕. 단순히 API를 찌르는 걸 넘어, LLM이 짠 파이썬 코드를 실제 안전한 격리 공간(Sandbox) 안에서 직접 돌려보고 그 에러나 결과값을 텍스트로 다시 받아보는 궁극의 도구 환경.

### 📈 관련 키워드 및 발전 흐름도
`LLM 환각 및 한계 발생` $\to$ `ChatGPT 플러그인 등장` $\to$ `OpenAI Function Calling (구조화된 도구 지원)` $\to$ `범용 Tool Use (코드 실행, 사내 API 연결)` $\to$ `MCP (도구 연결 프로토콜 표준화)`

### 👶 어린이를 위한 3줄 비유 설명
1. 계산을 못하는 요정(인공지능)에게 "15,324 곱하기 8,992가 뭐야?"라고 물으면, 요정은 당황해서 아무 숫자나 지어내서 거짓말을 했어요.
2. 하지만 '도구 사용(Tool Use)'을 배운 요정은 거짓말을 하는 대신 주머니에서 쓱 '계산기'를 꺼냅니다!
3. 요정은 자기가 직접 계산하지 않고, 계산기에 숫자를 띡띡 누른(도구 호출) 다음, 화면에 나온 정확한 정답을 보고 우리에게 씩 웃으며 알려주는 엄청난 재플(능력)을 갖게 된 거랍니다!
