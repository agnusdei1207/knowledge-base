## 미리 알고가기

- OCR+LLM은 문자 인식과 문맥 추론을 분리한 하이브리드 문서 이해 방식임
- OCR은 텍스트를 꺼내고 LLM은 구조화와 의미 해석을 담당함
- schema validation과 grounding이 없으면 환각 리스크가 커짐

## Ⅰ. 개요

- **정의/개념**: OCR+LLM 문서 이해는 OCR 엔진이 추출한 텍스트와 좌표 정보를 바탕으로, LLM이 문맥 추론과 오류 보정과 스키마 기반 구조화를 수행해 최종 업무 데이터를 생성하는 2단계 문서 파이프라인임
- **배경/필요성**: 기존 KIE 모델은 양식 추가마다 재학습 부담이 컸으므로, 프롬프트와 스키마 변경만으로 새로운 문서 유형에 대응할 수 있는 유연한 구조가 필요함

## Ⅱ. 특징

- OCR과 LLM 역할이 분리돼 기존 OCR 자산을 재사용하기 쉬움
- 프롬프트만으로 다양한 문서 필드 추출 요구를 빠르게 바꿀 수 있음
- OCR 오타를 문맥으로 보정할 수 있지만 없는 정보를 지어낼 위험도 함께 생김
- 긴 문서는 토큰 비용과 위치 정보 손실을 함께 관리해야 함

## Ⅲ. 종류 및 비교

| 판단 기준 | OCR만 사용 | OCR+LLM | VLM 직접 이해 |
|:---|:---|:---|:---|
| 구조화 유연성 | 낮음 | 높음 | 높음 |
| 위치 정보 활용 | 높음 | 중간 | 높음 |
| 비용 효율 | 높음 | 중간 | 낮음 |
| 환각 리스크 | 낮음 | 높음 | 중간 |

## Ⅳ. 구성요소 및 구조

| 구성요소 | 설명 |
|:---|:---|
| OCR Engine | 문서에서 텍스트와 bbox와 읽기 순서를 추출해 후속 추론의 원재료를 제공함 |
| Serialization Layer | OCR 결과를 표와 문단 구조가 유지되도록 markdown이나 JSON으로 정리해 LLM 입력 효율을 높임 |
| Schema Prompt, LLM | 추출 필드와 제약 조건을 주고 문맥 기반 보정과 구조화 출력을 생성함 |
| Validator, Grounding Layer | 출력 형식과 값 출처와 타입을 검증해 환각과 파싱 오류를 차단함 |

```text
+-------------------+      +-------------------+      +-------------------+
| OCR Engine        | ---> | Serialization     | ---> | Schema Prompt LLM |
+-------------------+      +-------------------+      +-------------------+
                                                           |
                                                           v
                                                   +-------------------+
                                                   | Validator / GND   |
                                                   +-------------------+
```

## Ⅴ. 원리 및 절차 흐름도

```text
+-------------+     +-------------+     +-------------+     +-------------+
| OCR 추출 수행   | --> | 구조화 입력 생성 | --> | 스키마 기반 추론 | --> | 검증/출력 저장  |
+-------------+     +-------------+     +-------------+     +-------------+
```

1. **OCR 추출 수행**: 문서에서 텍스트와 좌표를 뽑아냄
2. **구조화 입력 생성**: 표와 문단 구조가 유지되도록 입력을 직렬화함
3. **스키마 기반 추론**: LLM이 필요한 필드를 추출하고 보정함
4. **검증 및 출력 저장**: 형식과 근거를 확인한 뒤 결과를 저장함

## Ⅵ. 문제점 및 해결 방안

1. 문제: OCR이 읽지 못한 값을 LLM이 문맥상 그럴듯하게 채워 넣으면 자동화는 성공해 보여도 사실성은 무너질 수 있음
   - 해결방안: null-first policy와 evidence citation을 적용하고 hallucination rate와 citation coverage로 검증함
2. 문제: 긴 문서 전체를 LLM에 넣으면 비용이 커지고 핵심 필드보다 주변 문맥이 더 많은 토큰을 차지할 수 있음
   - 해결방안: field-aware chunking과 retrieval prompting을 적용하고 token cost와 extraction F1으로 검증함
3. 문제: OCR 결과에서 좌표나 표 구조가 사라지면 LLM이 값은 읽어도 어떤 헤더에 속하는지 헷갈릴 수 있음
   - 해결방안: bbox grounding과 table serialization을 적용하고 cell-header linking accuracy와 schema validity로 검증함

## Ⅶ. 적용 사례

- 무역 문서 심사가 계약 조건과 금액과 날짜를 빠르게 구조화하도록 OCR+LLM을 적용하며 확인 지표는 extraction F1과 review time reduction임
- 병원 접수가 스캔 진단서에서 환자명과 질환과 발급일을 추출하도록 OCR+LLM을 운영하며 확인 지표는 field accuracy와 hallucination rate임
- 법무 검토가 계약서 조항을 JSON 스키마로 정리하도록 OCR+LLM을 활용하며 확인 지표는 schema validity와 analyst productivity임

## Ⅷ. 결론

OCR+LLM은 문서 이해 유연성을 크게 높이는 구조이지만, 실무에서는 환각 방지와 좌표 기반 검증을 넣어야만 자동화 품질이 유지됨.
