# 📖 【암기용】 개념 완전 이해

> 목적: 스마트 계약을 블록체인에 배포되어 조건 충족 시 상태 변경을 실행하는 프로그램으로 이해하게 만든다.

## 한눈에
- **개요**: 블록체인 주소에 배포되어 거래 입력에 따라 실행되는 코드와 상태
- **왜 필요한가**: 중앙 운영자 없이도 자산 이전, 권한 부여, 규칙 집행을 공개 검증 가능한 방식으로 처리할 수 있다.
- **핵심 직관**: 계약서를 서버에 맡기는 대신, 규칙을 코드로 공개하고 네트워크가 같은 결과를 검증한다.

## 깊이 이해
- **배경·문제의식**: 전통 시스템은 중앙 DB와 운영자가 상태를 변경한다. 스마트 계약은 코드, 상태, 실행 결과가 체인 합의에 포함되어 임의 변경을 어렵게 만든다.
- **작동 원리**: 사용자가 트랜잭션을 보내면 EVM 같은 실행환경이 함수를 실행하고, gas를 소모하며 상태 변경 결과를 블록에 기록한다.
- **비유**: 자동판매기는 동전을 넣고 버튼을 누르면 정해진 규칙대로 상품을 낸다. 스마트 계약은 이 규칙과 결과를 다수 노드가 같이 검증하는 자동판매기다.
- **구체 예시**: ERC-20 토큰 계약은 `transfer()` 호출 시 잔액 조건을 확인하고 sender와 receiver의 balance 상태를 갱신한다.
- **흔한 오해·주의점**: 스마트 계약은 법률 계약 전체가 아니다. 코드가 표현한 규칙만 자동 실행하며, 법적 효력과 분쟁 해결은 별도 제도와 연결해야 한다.

## 연결 개념
- Ethereum Virtual Machine — 스마트 계약 실행환경
- Oracle — 외부 데이터를 온체인으로 제공
- Reentrancy — 대표 스마트 계약 취약점

# 📝 【답안용】 시험 답안 템플릿

> 목적: 시험장에서 25분에 그대로 쓰는 답안 양식.
> 핵심: 스마트 계약은 온체인 프로그램이며, 자동 실행보다 검증 가능성, 불변성, 취약점 대응, 오라클 신뢰 모델이 답안 포인트다.

## 핵심 인사이트 (3줄 요약)

> 1. **본질**: 스마트 계약은 블록체인에 배포된 코드와 상태가 트랜잭션 입력에 따라 결정적으로 실행되는 프로그램이다.
> 2. **가치**: 중앙 운영자 없이 자산·권한·규칙 변경을 공개 검증 가능한 상태 전이로 처리한다.
> 3. **판단 포인트**: gas 비용, 업그레이드 방식, oracle 신뢰, reentrancy·overflow·권한 취약점을 검증한다.

## 출제 의도 및 답안 포인트

| 출제 의도 | 반드시 짚을 핵심 | 감점 회피 포인트 |
|:---|:---|:---|
| 온체인 실행 원리 확인 | code, state, transaction, gas | 단순 전자계약으로 설명 |
| 보안 취약점 인식 확인 | reentrancy, access control, oracle manipulation | 배포 후 수정 가능으로 단정 |
| 실무 적용 판단 확인 | 감사, upgrade proxy, key management | 자동화 장점만 나열 |

> 요약: 이 문제는 코드 자동 실행보다 상태 전이의 검증 가능성과 취약점 통제를 묻는다.

---

## Ⅰ. 개요 및 필요성

- 개요: 온체인 실행 계약
- 배경: 중앙 서버 기반 거래는 운영자 권한, 감사 추적, 상호 신뢰 문제를 별도 통제로 해결해야 함.
- 필요성: 토큰, DeFi, DID, NFT 업무에서 규칙을 코드화하고 실행 결과를 합의 로그로 검증해야 함.

---

## Ⅱ. 구조 및 구성요소

```text
User Wallet -> Transaction -> Smart Contract Code
             -> EVM/Runtime -> State Update -> Event Log
             +-> Oracle / Token / Governance Contract
```

| 구성요소 | 역할 | 특이사항 |
|:---|:---|:---|
| 계약 코드 | 함수와 조건 정의 | Solidity, Vyper |
| 상태 저장소 | 잔액·권한·설정값 보관 | on-chain storage |
| 실행환경 | 결정적 실행과 gas 계산 | EVM, WASM VM |
| 외부 연계 | 현실 데이터·다른 계약 호출 | oracle, composability |

> 요약: 스마트 계약은 지갑 입력, 코드 실행, 상태 저장, 이벤트 로그, 외부 연계로 구성된다.

---

## Ⅲ. 동작원리 및 흐름도

```text
계약 작성 -> 컴파일/배포 -> 트랜잭션 호출
-> 조건 검증 -> 상태 변경 -> 이벤트 기록 -> 블록 확정
```

| 단계 | 처리 내용 | 검증 기준 |
|:---:|:---|:---|
| 1 | 계약 코드를 작성하고 bytecode로 컴파일함 | compiler version |
| 2 | 배포 트랜잭션으로 계약 주소를 생성함 | contract address |
| 3 | 사용자가 함수 호출 트랜잭션을 제출함 | gas limit |
| 4 | 노드가 동일 실행 결과와 상태 루트를 검증함 | state root |

> 요약: 스마트 계약은 모든 검증 노드가 같은 입력으로 같은 상태 변경 결과를 재현해야 합의에 포함된다.

## Ⅳ. 특징

| 구분 | 전통 애플리케이션 | 스마트 계약 | 판단 기준 |
|:---|:---|:---|:---|
| 실행 주체 | 중앙 서버 | 분산 노드 | 신뢰 모델 |
| 상태 변경 | DB 트랜잭션 | 온체인 상태 전이 | 공개 검증 필요 |
| 수정 방식 | 배포·패치 | 불변 또는 proxy upgrade | 변경 거버넌스 |
| 비용 | 인프라 비용 | gas 비용 | 호출 빈도 |

> 요약: 스마트 계약은 공개 검증성을 얻는 대신 gas 비용, 코드 불변성, 키 관리 부담을 가진다.

## Ⅴ. 심화 비교 및 적용 판단

| 비교 축 | 기존/대안 | 본 키워드 | 선택 기준 |
|:---|:---|:---|:---|
| 업무 규칙 | 서버 코드 | 온체인 코드 | 외부 감사 필요 |
| 데이터 | 중앙 DB | 체인 상태 | 개인정보 저장 제한 |
| 외부 정보 | API 직접 호출 | oracle 사용 | 데이터 조작 위험 |

> 요약: 스마트 계약은 공개 검증이 필요한 최소 상태만 온체인에 두고 개인정보와 대용량 데이터는 오프체인으로 분리한다.

| 리스크 | 원인 | 대응 방안 | 확인 지표 |
|:---|:---|:---|:---|
| 재진입 공격 | 외부 호출 후 상태 갱신 | checks-effects-interactions, guard | reentrancy test |
| 권한 오남용 | owner key 집중 | multisig, timelock, RBAC | privileged call log |
| 오라클 조작 | 단일 가격 소스 | TWAP, 다중 oracle | price deviation |

> 요약: 스마트 계약 리스크는 코드 결함, 관리자 키, 외부 데이터 신뢰 지점에서 집중적으로 발생한다.

| 점검 항목 | 목표 기준 | 측정 방법 |
|:---|:---|:---|
| 보안 | 감사 지적 high 0건 | audit report |
| 비용 | 함수별 gas 상한 관리 | gas snapshot |
| 운영 | 업그레이드·긴급정지 절차 문서화 | governance log |

> 요약: 배포 전 감사와 gas 측정, 배포 후 권한 호출 감시가 스마트 계약 운영의 핵심 지표다.

## Ⅵ. 실무 적용 및 결론

**적용 방안 3개:**
1. 온체인에 둘 상태를 자산 소유권, 권한, 해시 증명으로 제한하고 개인정보와 원문 데이터는 오프체인 저장소에 둠.
2. 정적 분석, fuzzing, unit test, 외부 audit로 reentrancy, access control, oracle manipulation을 검증함.
3. multisig, timelock, pause, upgrade proxy 정책을 문서화하고 관리자 키 분실·탈취 시나리오를 훈련함.

**결론 (2줄):**
- 기술사 판단: 공개 검증과 자동 정산이 필요한 업무는 스마트 계약을 적용하고, 빈번한 변경과 개인정보 처리가 큰 업무는 중앙 시스템을 선택함.
- 향후 방향: 스마트 계약은 account abstraction, formal verification, ZK proof와 결합해 사용성·검증성을 개선하는 방향으로 진화함.
