# 📖 【암기용】 개념 완전 이해

> 목적: Ontology를 처음 봐도 완벽히 이해하게 만든다.

## 한눈에
- **개요**: 특정 도메인의 개념, 관계, 속성, 제약을 명시적으로 정의한 지식 모델
- **왜 필요한가**: 지식그래프에 같은 개념이 여러 이름으로 들어가거나 잘못된 관계가 만들어지면 추론 결과가 흔들림.
- **핵심 직관**: 그래프를 그리기 전에 "어떤 종류의 노드와 관계를 허용할 것인가"를 정하는 설계도임.

## 깊이 이해
- **배경·문제의식**: 사내 문서에서 "고객", "사용자", "계약자"가 섞이면 같은 개념인지 다른 개념인지 판단 기준이 필요하다.
- **작동 원리**: 클래스, 인스턴스, 속성, 관계, 제약 조건을 정의하고 RDF/OWL 또는 도메인 스키마로 표현하여 그래프 생성·검증·추론에 사용함.
- **비유**: 건물을 짓기 전 설계도와 건축 규칙을 정해, 아무 벽이나 아무 곳에 세우지 못하게 하는 기준임.
- **구체 예시**: 의료 온톨로지에서 `질병-증상-치료제` 관계를 정의하면, "감기 증상에 항생제" 같은 잘못된 관계를 검증 규칙으로 탐지할 수 있음.
- **흔한 오해·주의점**: 온톨로지는 문서가 아니라 운영되는 스키마임. 도메인 변화에 맞춰 버전 관리와 변경 영향 분석이 필요함.

## 연결 개념
- Knowledge Graph — 온톨로지를 기반으로 인스턴스 지식을 저장
- RDF/OWL — 온톨로지 표현 표준
- Reasoning — 온톨로지 제약과 관계를 이용한 추론

# 📝 【답안용】 시험 답안 템플릿

> 목적: 시험장에서 25분에 그대로 쓰는 답안 양식.

## 핵심 인사이트 (3줄 요약)

> 1. **본질**: Ontology는 도메인 개념·관계·제약을 정의해 지식그래프의 의미 일관성을 보장하는 모델임.
> 2. **가치**: 엔티티 중복·관계 오류를 줄이고, 규칙 기반 검증과 추론으로 Graph RAG 근거 품질을 높임.
> 3. **판단 포인트**: 과도하게 복잡한 온톨로지는 구축·변경 비용을 높이므로 핵심 관계부터 점진 확장함.

## 출제 의도 및 답안 포인트

| 출제 의도 | 반드시 짚을 핵심 | 감점 회피 포인트 |
|:---|:---|:---|
| 지식그래프의 의미 일관성 확보 방법론 이해 확인 | 클래스·속성·제약 구조, RDF/OWL/SHACL 표준, 검증·추론 과정 | 단순 "스키마 정의" 서술 금지, 구축 합의 비용·버전 관리 누락 |

> 요약: Ontology의 구조 요소와 그래프 검증·추론 역할을 표준명 기반으로 제시해야 함.

---

## Ⅰ. 개요 및 필요성

- 정의: 도메인 개념·관계·제약을 명시 정의한 지식 모델
- 배경: 지식그래프에 개념 정의와 제약이 없으면 엔티티 중복률 15% 이상, 관계 오류 발생
- 필요성: RDF/OWL 기반 제약 검증과 추론으로 그래프 의미 일관성을 보장하고 Graph RAG 근거 품질을 높임

## Ⅱ. 구조 및 구성요소

```text
Domain Concept → Class/Property/Constraint
  → RDF/OWL Schema → Knowledge Graph Validation → Reasoning
```

| 구성요소 | 역할 | 특이사항 |
|:---|:---|:---|
| Class | 도메인 개념 유형 정의 | 고객, 계약, 서비스, 장애 |
| Property | 속성·관계 정의 | hasOwner, dependsOn, violates |
| Constraint | 허용 관계·카디널리티 제약 | domain/range, cardinality |
| Reasoner | 규칙 기반 검증·추론 | OWL reasoner, SHACL validation |

> 요약: Ontology는 클래스·속성·제약·추론 규칙으로 그래프 데이터의 의미 구조를 정의함.

## Ⅲ. 동작원리 및 흐름도

```text
도메인 분석 → 개념/관계 도출 → 온톨로지 모델링
  → 그래프 적재 검증 → 추론/질의 → 버전 관리
```

| 단계 | 처리 내용 | 검증 기준 |
|:---:|:---|:---|
| 1 | 도메인 용어와 핵심 관계 수집 | 핵심 개념 커버리지 ≥90% |
| 2 | 클래스·속성·제약 모델링 | 중복 개념률 <5% |
| 3 | SHACL/OWL 규칙으로 그래프 검증 | 제약 위반 탐지율 100% |
| 4 | 추론 결과와 변경 버전 관리 | 변경 영향 문서화율 100% |

> 요약: 도메인 개념을 모델링하고 제약 기반 검증·추론을 적용해 그래프 품질을 유지함.

## Ⅳ. 특징

| 구분 | 단순 스키마 | Ontology | 판단 포인트 |
|:---|:---|:---|:---|
| 표현 범위 | 테이블·필드 | 개념·관계·제약·추론 | 의미 일관성 필요 시 Ontology |
| 검증 | 타입·필수값 | domain/range·카디널리티 | 관계 오류 탐지 가능 |
| 유연성 | 구현 중심 | 도메인 의미 중심 | 변경 거버넌스 필요 |
| 비용 | 낮음 | 모델링·합의 비용 | 핵심 도메인부터 적용 |

> 요약: Ontology는 단순 스키마보다 의미 표현과 추론이 풍부하지만 도메인 합의와 버전 관리 비용이 발생함.

## Ⅴ. 심화 비교 및 적용 판단

| 비교 축 | 단순 DB 스키마 | Ontology | 선택 기준 |
|:---|:---|:---|:---|
| 표현 범위 | 테이블·필드·타입 | 개념·관계·제약·추론 규칙 | 관계 의미 검증 필요 시 Ontology |
| 검증 수준 | NOT NULL, FK 제약 | domain/range, 카디널리티, SHACL | 관계 오류 자동 탐지 기준 |
| 변경 비용 | 마이그레이션 1~2일 | 도메인 합의·영향 분석 1~2주 | 핵심 도메인부터 점진 확장 |

> 요약: 관계 의미 검증이 필요한 영역은 Ontology, 단순 데이터 저장은 DB 스키마로 선택함.

| 리스크 | 원인 | 대응 방안 | 확인 지표 |
|:---|:---|:---|:---|
| 과도 복잡성 | 모든 관계를 모델링 시도 | 핵심 클래스 20개 이내로 시작, 분기별 확장 | 클래스 수 대비 활용률 |
| 합의 지연 | 도메인 전문가 간 용어 불일치 | 용어 사전 사전 구축, 워크숍 2~3회 | 합의 완료 개념 비율 ≥90% |
| 버전 충돌 | 스키마 변경 시 기존 그래프 불일치 | v1/v2 분리 운영, 마이그레이션 스크립트 | 변경 영향 문서화율 100% |

> 요약: 과도 복잡성·합의 지연·버전 충돌을 점진 확장·워크숍·분리 운영으로 통제함.

| 점검 항목 | 목표 기준 | 측정 방법 |
|:---|:---|:---|
| 개념 커버리지 | 핵심 도메인 개념 ≥90% 반영 | 도메인 용어 사전 대비 클래스 매핑률 |
| 제약 위반 탐지 | SHACL 검증 위반 탐지율 100% | 그래프 적재 시 SHACL 검증 로그 |
| 추론 정확도 | 추론 결과 정확률 ≥95% | 수동 검수 표본 200건 |

> 요약: 개념 커버리지·제약 위반 탐지·추론 정확도를 정기 검수로 관리함.

## Ⅵ. 실무 적용 및 결론

**적용 방안 3개:**
1. Graph RAG 도메인 모델: 서비스, API, DB, 장애, 조치 클래스를 정의하고 dependsOn·causedBy 관계 제약 설정
2. 품질 검증: SHACL로 "장애는 최소 1개 영향 서비스 보유" 같은 규칙 검증, 위반 건은 데이터 정제 큐로 전송
3. 버전 관리: ontology v1/v2를 분리하고 변경된 관계 타입의 Graph RAG 답변 영향 샘플 1천 건 평가

**결론 (2줄):**
- 기술사 판단: 규정·의료·장애 분석처럼 관계 의미가 중요한 영역은 Ontology 기반 KG, 단순 검색은 스키마 최소화
- 향후 방향: LLM이 후보 온톨로지를 생성하고 전문가가 검증하는 human-in-the-loop 방식으로 구축 비용 절감
