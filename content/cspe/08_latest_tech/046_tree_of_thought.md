## 미리 알고가기

- Thought는 문제 해결 중간 단계에서 생성되는 후보 추론 상태임
- Search는 여러 후보 상태를 탐색하며 유망한 경로를 선택하는 절차임
- Pruning은 가능성이 낮은 후보를 조기에 제거해 비용을 줄이는 전략임

## Ⅰ. 개요

- **정의/개념**: Tree-of-Thought는 LLM이 단일 선형 추론 대신 여러 중간 생각 후보를 트리 형태로 생성하고 평가하고 가지치기하며 정답 경로를 탐색하도록 만드는 다경로 reasoning 프레임워크임
- **배경/필요성**: Chain-of-Thought는 한 번 잘못 든 추론 경로를 끝까지 따라가기 쉬우므로, 조합 탐색이나 계획 수립이나 복합 논리 문제에서는 여러 대안을 비교하며 되돌아갈 수 있는 탐색 구조가 필요함

## Ⅱ. 특징

- 선형 추론이 아닌 분기형 탐색으로 복수의 해결 경로를 동시에 검토할 수 있음
- 후보 경로를 자체 평가해 유망한 가지에만 연산을 집중하므로 brute force보다 효율적임
- BFS, DFS, beam search 등 탐색 정책에 따라 성능과 비용 특성이 달라짐
- 문제 난도가 높을수록 정답률 이점이 커지지만 비용과 latency도 크게 증가함

## Ⅲ. 종류 및 비교

| 판단 기준 | Chain-of-Thought | Tree-of-Thought | Graph-of-Thought |
|:---|:---|:---|:---|
| 추론 구조 | 선형 | 트리형 분기 | 그래프형 병합, 재참조 |
| 오류 복구 | 약함 | 중간 상태에서 백트래킹 가능 | 병합과 재사용까지 가능 |
| 비용 | 낮음 | 높음 | 매우 높음 |
| 적합 업무 | 일반 추론 | 탐색형 문제 해결 | 복합 워크플로우 설계 |

## Ⅳ. 구성요소 및 구조

| 구성요소 | 설명 |
|:---|:---|
| Thought Generator | 현재 상태에서 다음 후보 추론 단계를 여러 개 생성해 탐색 가지를 형성함 |
| State Evaluator | 각 후보가 정답에 얼마나 가까운지 점수화해 생존시킬 경로를 결정함 |
| Search Controller | BFS, DFS, beam search 중 어떤 방식으로 다음 상태를 확장할지 통제함 |
| Pruner | 불가능하거나 비효율적인 경로를 제거해 토큰 비용과 지연을 억제함 |

```text
+------------------+     +------------------+     +------------------+     +------------------+
| Thought Generate | --> | State Evaluate   | --> | Search Control   | --> | Prune / Expand   |
+------------------+     +------------------+     +------------------+     +------------------+
```

## Ⅴ. 원리 및 절차 흐름도

```text
+-------------+     +-------------+     +-------------+     +-------------+
| 후보 생성    | --> | 상태 평가    | --> | 경로 선택    | --> | 확장/가지치기 |
+-------------+     +-------------+     +-------------+     +-------------+
```

1. **후보 생성**: 현재 추론 상태에서 다음에 시도할 수 있는 여러 생각 후보를 생성함
2. **상태 평가**: 각 후보가 정답 가능성이 높은지 혹은 모순이 있는지 점수화함
3. **경로 선택**: 점수가 높은 후보만 남기고 탐색 정책에 맞춰 다음 단계로 전달함
4. **확장 및 가지치기**: 선택된 경로를 다시 확장하고 불필요한 가지는 제거하며 종료 조건까지 반복함

## Ⅵ. 문제점 및 해결 방안

1. 문제: 분기 수와 깊이가 커지면 탐색 공간이 급격히 팽창해 추론 비용과 지연이 통제 불가능해질 수 있음
   - 해결방안: beam width와 max depth를 명시적으로 제한하고 task success rate 대비 token cost로 탐색 효율을 검증함
2. 문제: 후보 평가가 부정확하면 유망한 경로를 조기에 제거하거나 비효율 경로를 끝까지 살려 정답률이 흔들릴 수 있음
   - 해결방안: verifier나 self-consistency 평가를 병행하고 pruning 후 final answer accuracy로 평가 품질을 검증함
3. 문제: 매 단계마다 프롬프트를 반복 호출하면 실시간 서비스에서 TTFT와 운영 비용이 과도하게 증가할 수 있음
   - 해결방안: 고난도 과제에만 ToT를 라우팅하고 latency budget과 요청당 비용으로 적용 범위를 검증함

## Ⅶ. 적용 사례

- 수학, 퍼즐 풀이: 여러 해법을 동시에 탐색해 오답 경로를 줄임, 확인 지표는 final answer accuracy와 pass@k임
- 에이전트 계획 수립: 도구 사용 순서를 여러 안으로 비교함, 확인 지표는 task completion rate와 retry count임
- 설계안 생성: 다수 대안을 만든 뒤 유망한 안만 심화함, 확인 지표는 accepted plan rate와 latency임

## Ⅷ. 결론

Tree-of-Thought의 핵심은 더 많이 생각하는 데 있지 않고 유망한 경로만 남기는 탐색 제어를 통해 고난도 추론 정답률을 비용 안에서 끌어올리는 데 있음.
