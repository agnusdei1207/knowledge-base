# 📖 【암기용】 개념 완전 이해

> 목적: 실리움을 처음 봐도 완벽히 이해하게 만든다. 시험 답안 양식이 아니라, 이해를 위한 친절한 설명이다.

## 한눈에
- **개요**: eBPF 기술을 기반으로 쿠버네티스 서비스 간의 네트워킹, 보안, 관측성을 제공하는 차세대 클라우드 네이티브 솔루션(CNI)
- **왜 필요한가**: 기존 쿠버네티스 네트워크(iptables 방식)는 서비스가 많아지면 속도가 급격히 느려지고 보안 설정이 복잡했다. 실리움은 커널 수준(eBPF)에서 직접 데이터를 처리해 이 문제를 해결한다.
- **핵심 직관**: "쿠버네티스라는 거대 도시의 낡은 신호등과 교차로(iptables)를 철거하고, 자율주행 전용 초고속 지하 터널(eBPF)을 뚫어 교통과 보안을 동시에 해결하는 시스템"

## 깊이 이해
- **배경·문제의식**: 쿠버네티스는 기본적으로 `iptables`를 써서 트래픽을 전달한다. 하지만 서비스가 수천 개가 되면 `iptables` 규칙도 수만 개로 늘어나고, 패킷 하나가 들어올 때마다 수만 개의 규칙을 순차적으로 대조하느라 CPU가 비명을 지른다. 또한 IP 주소 기반의 보안은 컨테이너가 수시로 바뀌는 환경에서 관리하기 매우 어렵다.
- **작동 원리**:
  1. **eBPF 활용**: 패킷이 커널에 들어오는 순간 eBPF 프로그램이 가로채서 즉시 목적지로 보낸다(Short-cut). 복잡한 IP 스택이나 규칙 대조 과정을 생략한다.
  2. **아이덴티티 기반 보안**: IP 주소 대신 서비스의 '이름(Identity)'을 기준으로 보안 정책을 세운다. 컨테이너 IP가 바뀌어도 보안 정책은 그대로 유지된다.
  3. **투명한 관측성(Hubble)**: 커널에서 직접 패킷을 보므로, 애플리케이션 수정 없이도 모든 통신 흐름을 시각화하고 추적할 수 있다.
- **비유**: 모든 방문객의 신분증을 입구에서 일일이 장부(iptables)와 대조하는 대신, 방문객의 옷에 달린 스마트 태그(Identity)를 센서(eBPF)가 순식간에 인식해서 전용 통로로 안내하는 것과 같다.
- **구체 예시**: Istio 같은 서비스 메시를 쓸 때, 실리움을 함께 쓰면 사이드카 프록시를 거치지 않고 커널에서 바로 통신을 처리하는 '사이드카리스(Sidecar-less)' 아키텍처를 구현할 수 있다.
- **흔한 오해·주의점**: "실리움은 그냥 네트워크 도구다"라고 생각하면 오산이다. 최근에는 런타임 보안(Tetragon), 멀티 클러스터 연결(Cluster Mesh) 등 플랫폼 전체의 보안과 운영을 책임지는 거대 에코시스템으로 성장했다.

## 연결 개념
- eBPF — 실리움을 지탱하는 핵심 커널 기술
- CNI (Container Network Interface) — 쿠버네티스 네트워크 표준 인터페이스
- Hubble — 실리움의 데이터를 시각화해주는 관측성 도구

# 📝 【답안용】 시험 답안 템플릿

> 목적: 시험장에서 25분에 그대로 쓰는 답안 양식. 작성방식(추상표현 금지·수치·도식·문제유형 전환)을 엄격히 지킨다.
> 핵심: 실리움은 eBPF 기반의 성능 혁신(iptables 탈피)과 아이덴티티 기반 보안을 중심으로 기술한다.

## 핵심 인사이트 (3줄 요약)

> 1. **본질**: 실리움(Cilium)은 리눅스 커널의 eBPF 기술을 활용하여 쿠버네티스 환경에 최적화된 고성능 네트워킹, 서비스 메시, 런타임 보안을 제공하는 CNI 솔루션이다.
> 2. **가치**: 기존 iptables 기반의 오버헤드를 제거하여 패킷 처리 성능을 극대화하고, IP가 아닌 서비스 식별자(Identity) 중심의 보안 체계를 구축한다.
> 3. **판단 포인트**: 대규모 마이크로서비스 운영 시 네트워크 복잡도 해결 및 사이드카 오버헤드 절감이 필요할 때 차세대 표준 CNI로 채택한다.

## 출제 의도 및 답안 포인트

| 출제 의도 | 반드시 짚을 핵심 | 감점 회피 포인트 |
|:---|:---|:---|
| 차세대 CNI 기술 동향 파악 | eBPF 기반 데이터패브릭, iptables 우회 | 단순히 "네트워크 드라이버"로만 설명 |
| 클라우드 네이티브 보안 전략 이해 | Identity-based Security, L7 필터링 | IP/Port 기반의 전통적 방화벽 개념에 고착 |
| 아키텍처 효율화 역량 확인 | Sidecar-less Service Mesh, Hubble 관측성 | 개별 기능의 기술적 연계성 누락 |

> 요약: eBPF를 통한 데이터 플레인 가속 원리와 논리적 보안 계층(Identity)을 중심으로 기술한다.

## Ⅰ. 개요 및 필요성

- 정의: 리눅스 커널의 eBPF를 사용하여 API 수준의 보안, 가용성 및 성능 가시성을 제공하는 클라우드 네이티브 네트워킹 플랫폼
- 배경: 서비스 규모 확장에 따른 전통적인 iptables/IPVS 방식의 성능 선형성 하락 및 관리 복잡성 증가
- 필요성: 컨테이너의 동적 IP 환경에 대응하는 식별자 중심 보안 체계 마련 및 네트워크 가시성(L3-L7) 확보

---

## Ⅱ. 구조 및 구성요소

```text
[Cilium 아키텍처 및 데이터 패스]
App Pod A <------------------------------> App Pod B
      |                                       |
[Cilium Agent] (eBPF Program) <---> [Cilium Agent]
      |          (Kernel Space)               |
      +---- Hubble (Observability) -----------+
      +---- Tetragon (Security) --------------+
```

| 구성요소 | 역할 | 특이사항 |
|:---|:---|:---|
| Cilium Agent | 각 노드에서 eBPF 프로그램을 관리 및 배치 | 쿠버네티스 API와 통신 |
| eBPF Data Path | 실제 패킷의 필터링, 포워딩, 로드밸런싱 수행 | 커널 레벨에서 동작, iptables 우회 |
| Hubble | 흐름 로깅 및 서비스 의존성 시각화 | Prometheus/Grafana 연동 지원 |
| Tetragon | 실시간 런타임 보안 및 권한 감시 | eBPF 기반의 시스템 콜 추적 |
| Cluster Mesh | 여러 쿠버네티스 클러스터 간 네트워크 통합 | 멀티 클라우드/하이브리드 지원 |

> 요약: 노드마다 배치된 에이전트가 커널에 eBPF 코드를 심어 패킷을 초고속으로 처리하고 관리하는 구조다.

---

## Ⅲ. 동작원리 및 흐름도

```text
[eBPF 기반 패킷 처리 흐름]
Packet In -> NIC Driver (XDP) -> eBPF Hook -> Identity Lookup -> Policy Check -> Local Pod Delivery
```

| 단계 | 처리 내용 | 검증 기준 |
|:---:|:---|:---|
| 1 | 패킷이 네트워크 카드(NIC)에 도착하자마자 eBPF(XDP)가 가로챔 | 커널 IP 스택 진입 전 단계 |
| 2 | 패킷 헤더에서 소스/목적지의 Identity(식별자) 확인 | IP 매핑 테이블 조회 (Hash Map) |
| 3 | 사전 정의된 보안 정책(L3-L7)을 커널 내에서 즉시 검사 | 정책 위반 시 즉시 폐기(Drop) |
| 4 | 정상 패킷을 대상 Pod의 가상 인터페이스로 직접 전달 | 컨텍스트 스위칭 최소화 |

> 요약: 패킷이 커널 깊숙이 들어가기 전에 eBPF가 미리 기다리고 있다가, 신분증(Identity)만 확인하고 바로 전달하는 방식이다.

## Ⅳ. 특징

| 구분 | 내용 | 판단 포인트 |
|:---|:---|:---|
| 성능 혁신 | iptables O(N) 탐색을 eBPF O(1) 해시 매핑으로 대체 | 대규모 클러스터(Pod 1만개 이상) 성능 |
| 보안 고도화 | DNS 인지(DNS-aware) 및 L7(HTTP/gRPC) 필터링 | API 수준의 세밀한 접근 제어 |
| 사이드카리스 | 사이드카 없이 서비스 메시 기능 구현 (Ambient) | 프록시 리소스 오버헤드 절감 효과 |

> 요약: 검색 알고리즘의 효율화(Hash)와 커널 수준의 직접 제어를 통해 성능과 보안을 동시에 잡았다.

## Ⅴ. 심화 비교 및 적용 판단

| 비교 축 | Calico (기본 CNI) | Cilium (eBPF CNI) | 선택 기준 |
|:---|:---|:---|:---|
| 데이터 처리 | iptables / IPVS / BGP | eBPF (Direct Data Path) | 대규모 트래픽 처리 성능 |
| 보안 정책 | IP / CIDR 기반 | Identity / Label / DNS 기반 | 동적 환경의 정책 관리 편의성 |
| 관측성 | 로그 기반 (제한적) | Hubble 기반 실시간 시각화 | 네트워크 트러블슈팅 깊이 |

> 요약: 일반적인 중소규모 환경은 Calico를, 고성능과 깊은 가시성이 필요한 MSA 환경은 Cilium을 선택한다.

| 리스크 | 원인 | 대응 방안 | 확인 지표 |
|:---|:---|:---|:---|
| 커널 버전 의존성 | 최신 eBPF 기능을 위해 5.x 이상 커널 필수 | 운영체제 업그레이드 또는 호환성 모드 사용 | 리눅스 커널 버전 및 기능 지원 표 |
| 운영 복잡도 | eBPF 프로그램 디버깅 및 관리 난이도 | Cilium CLI(cilium-dbg) 및 Hubble 활용 | 네트워크 장애 원인 분석 시간 |
| 자원 오버헤드 | BPF Maps 관리를 위한 일부 메모리 소비 | 맵 크기 최적화 및 불필요한 기능 비활성화 | 노드당 실리움 에이전트 자원 사용량 |

> 요약: 커널 제약 사항은 최신 OS 도입으로, 디버깅 어려움은 전용 시각화 도구(Hubble)로 해결한다.

| 점검 항목 | 목표 기준 | 측정 방법 |
|:---|:---|:---|
| 네트워크 지연 | iptables 방식 대비 30% 이상 단축 | `netperf` Latency 측정 |
| 보안 정책 적용 | Pod 생성/삭제와 동시 정책 적용 | Identity 업데이트 지연 시간 측정 |
| 서비스 맵 정확도 | 100% 서비스 간 호출 관계 시각화 | Hubble UI 연계 분석 |

> 요약: 패킷 지연 시간 단축 수치와 서비스 식별자 기반의 보안 무결성을 통해 도입 성과를 측정한다.

## Ⅵ. 실무 적용 및 결론

**적용 방안 3개:**
1. 대규모 MSA 성능 최적화: 수천 개의 서비스가 복잡하게 얽힌 클러스터에서 iptables를 제거하고 실리움을 도입하여 네트워크 지연 50% 절감
2. 제로 트러스트 API 보안: DNS 기반의 화이트리스트 정책을 수립하여, 승인되지 않은 외부 API 호출이나 내부 횡적 이동(Lateral Movement)을 차단
3. 멀티 클러스터 통합: Cluster Mesh 기능을 활용하여 서로 다른 리전이나 클라우드에 흩어진 쿠버네티스 노드들을 하나의 가상 네트워크로 통합

**결론 (2줄):**
- 기술사 판단: 실리움은 eBPF라는 '커널의 힘'을 빌려 쿠버네티스의 숙원 과제인 성능과 가시성을 해결한 독보적인 솔루션이며, 차세대 플랫폼의 표준이다
- 향후 방향: 사이드카 없는 서비스 메시와 통합 런타임 보안(Tetragon)을 통해, 네트워크 레이어를 넘어 '보안 및 관측 통합 플랫폼'으로 진화할 것이다
