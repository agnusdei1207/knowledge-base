# 📖 【암기용】 개념 완전 이해

> 목적: DataOps를 처음 봐도 완벽히 이해하게 만든다. 시험 답안 양식이 아니라, 이해를 위한 친절한 설명이다.

## 한눈에
- **개요**: 데이터 생명주기 전반(수집, 가공, 배포)에 걸쳐 민첩성, 품질, 보안을 확보하기 위해 DevOps 원칙을 데이터에 적용한 운영 체계
- **왜 필요한가**: 데이터 분석가가 데이터를 요청하면 몇 주씩 걸리고, 막상 받은 데이터의 품질이 낮아 분석 결과가 틀리는 "데이터 병목"과 "신뢰성 문제"를 해결하기 위함
- **핵심 직관**: 데이터를 단순히 "보관"하는 대상이 아니라, 지속적으로 흐르고 가공되는 "제품(Data Product)"으로 보고 그 생산 라인을 자동화하는 것

## 깊이 이해
- **배경·문제의식**: 예전에는 데이터를 DB에 쌓아두고 필요할 때 쿼리만 던졌다. 하지만 지금은 실시간 로그, 센서 데이터, 외부 API 등 소스가 너무 다양해졌고 사용자(분석가, AI 모델)도 급증했다. 수동으로 ETL(추출·변환·적재)을 관리하다 보니 데이터가 누락되거나 형식이 바뀌어 하위 시스템이 뻗는 사고가 잦아졌다.
- **작동 원리**: 애자일 방법론으로 요구사항을 수렴하고, DevOps 기술(CI/CD, 버전 관리)로 데이터 파이프라인을 구축하며, 린(Lean) 통계적 기법으로 품질을 상시 감시한다. 데이터가 어디서 왔는지(Lineage)를 추적하여 문제 발생 시 즉시 원인을 파악한다.
- **비유**: 예전에는 물이 필요하면 우물에서 직접 길어다 썼다면(Manual Data), DataOps는 정수장과 수도관을 만들고 수질 센서를 달아 집집마다 깨끗한 물을 실시간으로 공급하는 수도망 시스템과 같다.
- **구체 예시**: 개발자가 DB 스키마를 바꾸면, DataOps 시스템이 이를 감지하여 영향받는 하위 리포트와 AI 모델에 알람을 주고, 데이터 정합성 테스트를 자동으로 돌려 문제가 있으면 파이프라인 배포를 중단시킨다.
- **흔한 오해·주의점**: "DataOps는 단순히 ETL 도구를 쓰는 것이다"라고 생각할 수 있으나, 기술보다 "데이터를 사용하는 부서 간의 협업 문화"와 "품질에 대한 신뢰 보장"이 더 중요한 본질이다.

## 연결 개념
- Data Lineage — 데이터 흐름과 변경 이력 추적
- Data Quality (DQ) — 데이터의 정확성·완결성 지표
- Data Mesh — 중앙 집중형이 아닌 분산화된 데이터 운영 아키텍처

# 📝 【답안용】 시험 답안 템플릿

> 목적: 시험장에서 25분에 그대로 쓰는 답안 양식. 작성방식(추상표현 금지·수치·도식·문제유형 전환)을 엄격히 지킨다.

## 핵심 인사이트 (3줄 요약)

> 1. **본질**: DataOps는 협업·자동화·모니터링을 통해 고품질의 데이터를 신속하고 안정적으로 전달하는 데이터 관리 프레임워크이다.
> 2. **가치**: 데이터 분석 대기 시간(Cycle Time) 단축, 데이터 품질 사고 방지, 데이터 거버넌스 준수성 확보를 실현한다.
> 3. **판단 포인트**: 데이터 파이프라인의 자동화(CI/CD)와 통계적 품질 관리(SPC)를 결합하여 데이터 신뢰성(Data Observability)을 확보해야 한다.

## 출제 의도 및 답안 포인트

| 출제 의도 | 반드시 짚을 핵심 | 감점 회피 포인트 |
|:---|:---|:---|
| 데이터 생명주기 관리 역량 확인 | 데이터 파이프라인 자동화, 테스트 자동화, Lineage | 단순히 "데이터 운영 잘하기"와 같은 모호한 서술 |
| DataOps와 DevOps의 차별점 이해 확인 | 데이터의 가변성, 품질 테스트 중요성, 복잡한 의존성 | DevOps와 똑같은 개념으로만 기술 |
| 데이터 품질 및 거버넌스 전략 확인 | DQ 지표, 데이터 카탈로그, SLA/SLO 관리 | 기술적 도구 나열에만 치중 |

> 요약: 데이터 파이프라인을 하나의 소프트웨어처럼 관리(Data-as-Code)하고 지속적으로 품질을 검증하는 체계 제시가 핵심이다.

## Ⅰ. 개요 및 필요성

- 정의: 데이터 개발자와 사용자 간의 협업을 촉진하고 데이터 파이프라인 전체를 자동화하여 데이터 가치를 극대화하는 운영 체계
- 배경: 데이터 소스 및 소비자의 다변화로 인한 운영 복잡성 증가, 낮은 데이터 품질로 인한 비즈니스 의사결정 리스크 발생
- 필요성: 데이터 제품의 배포 속도 향상, 데이터 흐름 가시성 확보(Lineage), 데이터 거버넌스 및 보안 규제 자동 준수

---

## Ⅱ. 구조 및 구성요소

```text
Requirement -> Data Dev (Code) -> Pipeline CI/CD -> Data Ingestion & Transformation
                                          |                     |
                Data Catalog/Lineage <- DQ Testing <- Monitoring & Alerting
```

| 구성요소 | 역할 | 특이사항 |
|:---|:---|:---|
| Pipeline Orchestration | 데이터 흐름 자동 제어 및 스케줄링 | Airflow, Dagster 등 |
| Data Quality Testing | 데이터 유효성·정확성 자동 검증 | Great Expectations, dbt |
| Data Catalog | 데이터 자산 메타데이터 관리 및 탐색 | 데이터 검색성(Discoverability) |
| Data Lineage | 데이터 생성부터 소비까지의 경로 추적 | 장애 영향도 분석(Impact Analysis) |

> 요약: 오케스트레이션을 통한 자동화와 DQ 테스트를 통한 신뢰성 확보가 DataOps 구조의 핵심임.

---

## Ⅲ. 동작원리 및 흐름도

```text
개발: 파이프라인 코드 작성 -> 버전 관리 -> 유닛 테스트 -> 코드 리뷰
운영: 데이터 수집 -> 스키마 검증 -> 변환 -> 품질 테스트 -> 가공 데이터 배포 -> 성능 모니터링
      |               |              |               |               |
      +---------------+--------------+---------------+---------------+-----> 지속적 피드백
```

| 단계 | 처리 내용 | 검증 기준 |
|:---:|:---|:---|
| 1 | 데이터 수집 및 유효성 검사 | Null 비율, 데이터 타입 일치 |
| 2 | 데이터 변환 및 적재 (ETL/ELT) | 변환 로직 정합성, 처리 시간 |
| 3 | 상시 품질 및 프로파일링 테스트 | 비즈니스 룰 준수 여부 |
| 4 | 거버넌스 업데이트 및 가용화 | 카탈로그 동기화, 권한 제어 |

> 요약: 파이프라인 자체의 코드 품질(DevOps)과 흐르는 데이터의 품질(Lean)을 동시에 관리함.

## Ⅳ. 특징

| 구분 | 고전적 데이터 관리 | DataOps | 판단 포인트 |
|:---|:---|:---|:---|
| 운영 방식 | 수동 ETL 및 사후 정제 | 자동 파이프라인 및 상시 검증 | 자동화 수준 |
| 개발 주기 | 폭포수형 (수개월) | 애자일/반복형 (수일) | 대응 속도 |
| 품질 보증 | 샘플링 기반 수동 검사 | 전수 자동 테스트 및 SPC 적용 | 신뢰성 확보 방식 |
| 인프라 | 온프레미스/고정형 | 클라우드/탄력적 서버리스 | 확장성 및 유연성 |

> 요약: DataOps는 데이터 관리를 수동 작업에서 자동화된 지속적 전달(Continuous Delivery) 체계로 전환함.

## Ⅴ. 심화 비교 및 적용 판단

| 비교 축 | ETL (기존) | ELT (최신) | 선택 기준 |
|:---|:---|:---|:---|
| 처리 위치 | 별도 스테이징 서버 | 목적지(Data Warehouse) 내부 | 인프라 성능 및 비용 |
| 유연성 | 낮음 (변환 로직 고정) | 높음 (원천 데이터 보존) | 분석 요구사항 변경 빈도 |
| 데이터 보안 | 변환 후 적재 (유리) | 선 적재 후 변환 (관리 필요) | 보안 규제 강도 |

> 요약: 데이터 양이 방대하고 분석 요구가 빈번하면 ELT 기반 DataOps를, 엄격한 보안이 필요하면 ETL을 고려함.

| 리스크 | 원인 | 대응 방안 | 확인 지표 |
|:---|:---|:---|:---|
| Pipeline Break | 상위 시스템 스키마 변경 | 스키마 레지스트리 및 계약 테스트 | 파이프라인 가동률(Uptime) |
| 데이터 침해 | 관리되지 않은 데이터 접근 | 권한 제어 자동화 및 마스킹 적용 | 개인정보 노출 사고 건수 |
| 비용 폭증 | 비효율적인 쿼리 및 중복 처리 | 쿼리 최적화 및 비용 모니터링 | 데이터 처리당 단가 |

> 요약: 스키마 변경은 계약 테스트로, 보안은 자동화된 권한 통제로, 비용은 최적화로 대응함.

| 점검 항목 | 목표 기준 | 측정 방법 |
|:---|:---|:---|
| 데이터 가용성 | SLA 준수율 99.9% 이상 | 데이터 적시 도착 여부 체크 |
| 품질 사고율 | 월간 주요 DQ 사고 1건 이하 | 장애 보고서(Incident Report) 분석 |
| 파이프라인 반영 속도 | 요구사항~배포 48시간 이내 | 사이클 타임(Cycle Time) 측정 |

> 요약: 도입 효과는 데이터의 적시 가용성, 품질 무결성, 운영 민첩성 지표로 판정함.

## Ⅵ. 실무 적용 및 결론

**적용 방안 3개:**
1. 데이터 신뢰성 확보: Great Expectations를 활용하여 데이터 수집 단계에서 비즈니스 룰(예: 가격 > 0)을 100% 자동 검증하고 오류 시 격리
2. 파이프라인 가시성 강화: OpenLineage 표준을 도입하여 데이터의 소스부터 최종 대시보드까지의 흐름을 시각화하고 장애 영향 분석 시간 70% 단축
3. 셀프 서비스 데이터 제공: 데이터 카탈로그(Amundsen 등)와 연동된 자동 권한 승인 워크플로우를 구축하여 분석가의 데이터 획득 대기 시간을 2주에서 1시간으로 단축

**결론 (2줄):**
- 기술사 판단: DataOps는 단순 기술 도입을 넘어 데이터 품질에 대한 조직 내 상호 신뢰 계약을 기술로 강제하는 체계임
- 향후 방향: AI 모델의 원재료인 데이터의 신뢰성을 보장하기 위해 MLOps와 긴밀히 통합된 "DataOps for AI"로 진화할 것임
