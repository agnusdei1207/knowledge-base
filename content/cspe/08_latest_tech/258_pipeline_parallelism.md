# 📖 【암기용】 개념 완전 이해

> 목적: 모델 병렬화의 치명적 단점인 'GPU 노는 시간(Bubble)'을 마이크로 배치(Micro-batch)라는 기발한 아이디어로 어떻게 극복했는지 완벽히 이해한다.

## 한눈에
- **정의**: 모델의 층(Layer)을 여러 GPU에 분할해 둔 상태에서, 입력 데이터를 아주 잘게 쪼갠 **'마이크로 배치(Micro-batch)'** 단위로 파이프라인처럼 끊임없이 흘려보내어 모든 GPU가 쉬지 않고 일하게 만드는 분산 학습 기법
- **필요성**: 단순한 모델 병렬화(Naive MP)에서는 앞의 GPU가 계산을 끝내고 데이터를 넘겨줄 때까지 뒤의 GPU들이 손가락만 빨고 기다려야(Idle) 하는 치명적인 비효율성을 타파하기 위함
- **핵심 직관**: "세탁-건조-다림질 공정에서 세탁기가 옷 100벌을 다 빨 때까지 건조기가 노는 게 아니라(Naive MP), 옷을 1벌씩(Micro-batch) 빨아서 바로 건조기로 넘겨주면 세탁기와 건조기가 동시에 돌아가는 원리"

## 깊이 이해
- **배경(왜 등장했나?)**: 거대 모델을 1~50층은 GPU 0에, 51~100층은 GPU 1에 올렸다. 데이터를 한 덩어리(Batch)로 GPU 0에 넣었더니, GPU 1은 GPU 0이 50층까지 다 계산할 때까지 마냥 기다려야 했다. 이 '유휴 시간(Bubble)' 때문에 GPU 효율이 50% 밑으로 떨어지자, 구글(GPipe 연구진)이 "배치를 잘게 쪼개서 연속으로 넘기자!"고 제안한 것이 파이프라인 병렬화다.
- **작동 원리(어떻게 달성했나?)**: 
  1. 전체 미니 배치 데이터를 4개의 **마이크로 배치(M1, M2, M3, M4)**로 쪼갠다.
  2. GPU 0이 M1을 계산해서 GPU 1로 넘긴다.
  3. **(핵심!)** 그 즉시 GPU 0은 M2 계산을 시작하고, 동시에 GPU 1은 넘어온 M1 계산을 시작한다.
  4. 이렇게 파이프라인에 물이 차오르듯 데이터가 꽉 차면(Steady State), 모든 GPU가 100% 가동률로 돌아가게 된다.
- **일상 비유**: 서브웨이 샌드위치를 만들 때, 빵 굽는 사람, 야채 넣는 사람, 소스 뿌리는 사람이 있다. 빵을 10개 다 굽고 나서야 다음 사람에게 넘기는 게 아니라, 빵 1개 굽자마자 넘겨주면 3명이 동시에 일할 수 있다.
- **구체 예시**: 구글의 GPipe(가장 기본적 형태), 마이크로소프트의 PipeDream(파이프라인 속도를 더 높이기 위해 비동기식 업데이트 도입) 등이 대표적인 알고리즘 프레임워크다.
- **흔한 오해/주의점**: "파이프라인 병렬화(PP)를 쓰면 버블(Bubble)이 0%가 되나?" → 아니다. 처음에 파이프라인이 채워지는 시간(Fill)과 마지막에 비워지는 시간(Drain)에는 필연적으로 일부 GPU가 쉴 수밖에 없다. 하지만 마이크로 배치의 개수를 늘릴수록 이 버블의 비율은 0에 수렴하게 된다.

## 연결 개념
- **Micro-batch (마이크로 배치)**: 파이프라인 병렬화의 핵심. 미니 배치를 더 잘게 쪼개어 유휴 시간을 줄이는 데이터 단위
- **Bubble (버블)**: GPU가 연산할 데이터가 없어서 멍하니 놀고 있는 유휴 시간(Idle time)
- **Model Parallelism (모델 병렬화)**: PP가 해결하고자 하는 근본적인 아키텍처. (PP는 MP의 발전된 세부 형태 중 하나임)

# 📝 【답안용】 시험 답안 템플릿

## 핵심 인사이트 (3줄 요약)
> 1. **본질**: 파이프라인 병렬화(Pipeline Parallelism, PP)는 분할된 모델 레이어(Layer)를 거치는 입력 데이터를 마이크로 배치(Micro-batch) 단위로 파이프라이닝하여 가속기 간의 동시 처리(Concurrency)를 구현하는 학습 기법이다.
> 2. **가치**: 순진한 모델 병렬화(Naive MP)의 치명적 단점인 GPU 유휴 시간(Pipeline Bubble)을 최소화하여, 메모리 제약을 극복함과 동시에 훈련 처리량(Throughput)을 선형적으로 향상시킨다.
> 3. **판단 포인트**: 마이크로 배치 수($M$)와 파이프라인 스테이지 수($P$)의 비율 최적화, 그리고 1F1B(One Forward One Backward) 스케줄링을 통한 VRAM 메모리 사용량(Peak Memory) 절감이 프레임워크 설계의 핵심이다.

## Ⅰ. 개요 및 필요성
- **정의**: 모델 레이어 단위로 워커(GPU)를 할당한 구조에서, 글로벌 배치를 더 작은 마이크로 배치로 분할한 뒤, 각 워커가 순차적/연속적으로 순전파(Forward) 및 역전파(Backward)를 오버래핑(Overlapping)하여 처리하는 기법
- **배경**: Naive MP(단순 모델 병렬화)는 이전 GPU의 연산이 끝날 때까지 다음 GPU가 대기하는 종속성(Dependency)으로 인해 극심한 자원 낭비(Idle) 초래
- **필요성**: 모델 병렬화의 장점(OOM 방지)을 유지하면서도 데이터 병렬화 수준의 높은 연산 효율(Hardware Utilization) 확보 필요

## Ⅱ. Naive MP vs Pipeline Parallelism 버블(Bubble) 메커니즘 비교
```text
[ Naive Model Parallelism - 막대한 Bubble ]
GPU 0: [Fwd_Batch]-------------------------[Bwd_Batch]
GPU 1: -----------[Fwd_Batch]----[Bwd_Batch]-----------
          ↑ 대기(Bubble) ↑          ↑ 대기(Bubble) ↑

[ Pipeline Parallelism (GPipe 예시) - Micro-batch로 Bubble 축소 ]
GPU 0: [F1][F2][F3][F4]------------------------[B1][B2][B3][B4]
GPU 1: ----[F1][F2][F3][F4]------------[B1][B2][B3][B4]--------
            ↑ (동시 연산 구간 확대로 Bubble 최소화) ↑
```

| 구분 | Naive Model Parallelism | Pipeline Parallelism (PP) |
|:---|:---|:---|
| **입력 단위** | 전체 글로벌 배치 (Global Batch) | **잘게 쪼갠 마이크로 배치 (Micro-batch)** |
| **동시성(Concurrency)**| 1번에 1대의 GPU만 동작 | **파이프라인 충진 시 모든 GPU가 동시 동작** |
| **Bubble 비율** | 압도적으로 높음 (비효율의 극치) | **마이크로 배치가 많을수록 0에 수렴** |

## Ⅲ. 파이프라인 병렬화의 핵심 프레임워크 동향
단순히 마이크로 배치로 쪼개는 방식(GPipe)은 역전파를 위해 모든 활성화 값(Activation)을 메모리에 들고 있어야 하는 단점이 있어, 다양한 스케줄링 방식으로 발전했다.

1. **GPipe (Google 제안)**
   - **방식**: 모든 마이크로 배치의 순전파(Forward)를 끝낸 뒤, 한꺼번에 역전파(Backward)를 수행하는 일괄 처리 방식.
   - **한계**: 역전파가 시작될 때까지 모든 중간 결과물(Activation)을 VRAM에 보관해야 하므로 메모리 압박(Peak Memory)이 큼.
2. **PipeDream (1F1B 스케줄링)**
   - **방식**: One Forward One Backward (1F1B). 한 마이크로 배치의 순전파가 끝나는 즉시 해당 역전파를 이어서 수행하는 스케줄링.
   - **효과**: 순전파/역전파가 촘촘히 엮여 메모리에 쌓이는 활성화 값(Activation)을 바로바로 삭제할 수 있어 **메모리 요구량이 GPipe 대비 획기적으로 감소**함.
3. **Interleaved Pipeline (Megatron-LM)**
   - **방식**: GPU마다 연속된 층을 주지 않고 띄엄띄엄(예: GPU 0에 1층과 5층, GPU 1에 2층과 6층) 할당하는 방식.
   - **효과**: 파이프라인의 시작과 끝에서 필연적으로 발생하는 Bubble 크기를 하드웨어적으로 더욱 줄여줌.

## Ⅳ. 수식으로 보는 Bubble의 최소화 원리
버블(유휴 시간)이 차지하는 비율은 **마이크로 배치 수($m$)**와 **파이프라인 스테이지(GPU) 수($p$)**에 의해 결정된다.
- 파이프라인을 채우고 비우는 데 걸리는 시간 때문에, 총 연산 단계는 $(m + p - 1)$이 된다.
- **이상적인 연산 시간 비율**: $m / (m + p - 1)$
- **결론**: 파이프라인 스테이지 수($p$)가 고정되어 있을 때, **마이크로 배치의 개수($m$)를 무한히 늘리면 버블의 비율은 0%에 수렴한다.** (단, $m$이 너무 커지면 활성화 메모리 한계에 부딪히므로 트레이드오프 계산 필수)

## Ⅴ. 기술적 한계(리스크) 및 대응 방안
| 리스크 요인 | 발생 원인 | 대응 방안 (엔지니어링/최적화 관점) |
|:---|:---|:---|
| **Pipeline Flush (버블 잔존)**| 배치(Batch)가 끝날 때마다 가중치를 동기화하기 위해 파이프라인을 다 비워야(Flush) 하는 시간 발생 | 버블 오버헤드를 상쇄할 수 있도록 충분히 큰 $m$(마이크로 배치 수) 설정 및 Interleaved 스케줄링 |
| **Load Imbalance (불균형)** | 각 GPU(스테이지)에 할당된 레이어들의 연산 시간이 다르면, 가장 느린 GPU 속도에 전체 파이프라인 병목 발생 | 트랜스포머(Transformer) 블록 등 연산량이 균일한 모듈 단위로 정교하게 파티셔닝(Partitioning) |
| **활성화 메모리 압박** | 역전파를 위해 Forward 시점의 Activation을 계속 들고 있어야 함 | **Activation Checkpointing (재계산)** 기법을 도입하여, 메모리에 저장하지 않고 역전파 시점에 다시 계산함 |

## Ⅵ. 실무 적용 및 결론
**적용 방안 및 실무 가이드:**
1. **LLM 3D 병렬화 토폴로지 매핑**: 파이프라인 병렬화(PP)는 노드(Server) 간 통신에 적합하다. 텐서 병렬화(TP)는 통신량이 너무 많아 서버 내부(NVLink)로 묶고, 파이프라인 병렬화는 상대적으로 통신량이 적으므로(레이어 경계의 Activation만 전송) 랙(Rack) 간의 인피니밴드나 RoCE 스위치 홉(Hop)을 넘나드는 스케일 아웃(Scale-out) 아키텍처에 배치한다.
2. **DeepSpeed 프레임워크 활용**: 마이크로소프트의 DeepSpeed나 Megatron-LM 라이브러리를 사용하면, 사용자가 직접 1F1B 스케줄링 코드를 짜지 않고도 Config 설정만으로 최적화된 파이프라인 병렬화를 적용할 수 있다.

**결론:**
- 파이프라인 병렬화(PP)는 모델 병렬화가 가진 태생적 비효율을 '시분할(Micro-batch)'이라는 운영체제적 발상으로 극복한 우아한 아키텍처이다.
- 수백 노드 단위의 LLM 클러스터에서 텐서 병렬화(TP)만으로는 노드 간 통신 병목을 감당할 수 없으므로, **PP를 통한 계층적 횡단 배치**가 거대 AI 인프라 확장의 필수 불가결한 생존 스킬이 되었다.
