# 📖 【암기용】 개념 완전 이해

## 한눈에
- **정의**: 사용자의 질문이 들어올 때 질의의 난이도, 의도, 필요 리소스를 사전에 평가(분류)하여, 가장 적절한 RAG 파이프라인(경로)으로 동적 할당(Routing)하는 스마트한 RAG 아키텍처.
- **필요성**: 모든 질문에 무거운 고급 RAG(리랭킹, 멀티홉)를 쓰면 돈과 시간이 낭비되고, 단순 RAG만 쓰면 복잡한 질문에 엉뚱한 답을 함. "닭 잡는 데 소 잡는 칼을 쓸 필요 없다"는 비용-효율(FinOps) 철학.
- **핵심 직관**: 병원의 응급실 접수처(Triage). 찰과상 환자는 간호사(단순 FAQ)에게 보내고, 가벼운 감기 환자는 동네 의원(Naive RAG)으로, 중증 외상 환자는 대형 수술실(Agentic RAG)로 분배하는 교통정리 시스템.

## 깊이 이해
- **배경**: AI 서비스가 상용화되면서 LLM API 토큰 비용과 클라우드 DB 호출 비용이 천문학적으로 치솟음. 지연 시간(Latency)과 비용(Cost)을 최적화하기 위한 라우팅(Routing) 설계가 핵심 화두로 떠오름.
- **작동 원리 (Classify $\rightarrow$ Route $\rightarrow$ Execute)**:
  1. (분류기): 질문이 들어오면 LLM 기반 Classifier(혹은 경량 머신러닝 모델)가 질의의 난이도를 판별.
  2. (라우터 분기):
     - 난이도 하 (일반 대화): 아예 RAG 검색을 건너뛰고 내부 파라미터로 즉시 답변 (No Retrieval).
     - 난이도 중 (단일 정보): 기본 단일 벡터 검색으로 처리 (Naive/Single-hop RAG).
     - 난이도 상 (복합 추론): 웹 검색 결합, 리랭킹, 멀티홉 적용 (Advanced/Agentic RAG).
- **구체 예시**: 사내 봇. "안녕? 오늘 날씨 어때?" $\rightarrow$ 검색 없이(No RAG) 바로 100ms 만에 답변. "규정집 어딨어?" $\rightarrow$ 단순 벡터 검색 500ms 만에 답변. "작년 A부서 예산 대비 올해 집행률 분석해" $\rightarrow$ 5초 걸리는 멀티홉 검색/계산 파이프라인으로 라우팅.
- **흔한 오해/주의점**: 접수처 직원이 오진하면 끔찍한 결과가 발생함. 암 환자를 감기로 잘못 분류해 단순 RAG로 보내면 환각(Hallucination)이 발생하고, 감기 환자를 수술실로 보내면 비용이 낭비됨. 라우터(Router) 모델의 분류 정확도(Accuracy 90% 이상)가 시스템 전체의 생명줄임.

## 연결 개념
- **Query Routing (질의 라우팅)**: 질문의 성격에 따라 적절한 데이터 소스나 RAG 모델을 선택해주는 핵심 컴포넌트.
- **Self-RAG (자기검색 RAG)**: Self-RAG가 답변을 만들어 나가며 '생성 중에' 검색 여부를 동적으로 결정한다면, Adaptive RAG는 '질문이 들어온 직후'에 파이프라인 자체를 미리 결정함.
- **FinOps (비용 최적화)**: 클라우드와 AI 자원을 낭비 없이 쓰기 위한 재무적/기술적 접근법 (Adaptive RAG의 핵심 목적).

# 📝 【답안용】 시험 답안 템플릿
## 핵심 인사이트 (3줄 요약)
- **본질**: 질의(Query)의 복잡도, 도메인, 보안 민감도를 사전 분석하는 라우터(Router)를 앞단에 배치하여, 여러 단계의 RAG 처리 경로(Path) 중 최적의 비용-성능 구간을 동적으로 선택하는 트래픽 제어 아키텍처.
- **가치**: 일률적인 헤비(Heavy) 파이프라인 구동 시 발생하는 API 과금 폭발과 응답 지연(Latency)을 해결. 단순 질의의 40% 이상을 경량 파이프라인으로 우회시켜 전체 시스템 운영 비용을 획기적으로 절감.
- **판단 포인트**: Classifier(분류기)의 추론 오버헤드 최소화, 라우팅 오분류 시 상위 경로로 재진입하는 Fallback(오류 복구) 메커니즘, 경로별 상이한 SLA(응답 시간) 관리 역량.

## Ⅰ. 개요 및 필요성
- **정의**: 사용자 질의의 복잡성과 리소스 요구량을 평가하여, 검색 생략(No-RAG), 기본 검색(Naive RAG), 고도화 검색(Multi-hop/Agentic RAG) 등 적절한 워크플로를 동적으로 할당하는 맥락 인지형 검색증강생성 구조.
- **배경**: 엔터프라이즈 환경의 질의 중 30~50%는 단순 인사말이나 캐싱된 빈출 질문(FAQ)임에도, 고정된 Advanced RAG 파이프라인을 통과하며 불필요한 벡터 연산과 Cross-encoder 리랭킹 비용을 낭비함.
- **필요성**: 품질(Quality), 비용(Cost), 속도(Latency)의 3중 제약(Trilemma) 속에서 질의의 가치에 비례하여 컴퓨팅 자원을 차등 배분(Cost-aware Serving)하기 위함.

## Ⅱ. Adaptive RAG 핵심 아키텍처
```text
[ User Query ]
      |
[ Query Classifier & Router ] (분류기 / 라우터) ---> [ 비용/난이도 판별 ]
      |
      +-- (단순 대화 / 캐시 힛) --> [ No Retrieval ] -> 즉시 응답 (100ms)
      |
      +-- (단일 팩트 검색)     --> [ Naive RAG (Vector Only) ] -> 응답 (500ms)
      |
      +-- (모호/심화 질의)     --> [ Advanced RAG (Hybrid+Rerank) ] -> 응답 (1.5s)
      |
      +-- (비교/인과 복합 질의) --> [ Agentic / Multi-hop RAG ] -> 응답 (5s+)
      |
[ Fallback Guardrail ] (저신뢰도 도출 시 상위 RAG로 Re-route)
```

## Ⅲ. 라우터(Router)의 3대 분류 전략
| 라우팅 기준 | 판별 요소 및 기술 | 적용 시나리오 |
|:---:|:---|:---|
| **복잡도 라우팅 (Complexity)** | 토큰 길이, 엔티티 개수, 문장 구조 분석 (경량 머신러닝/LLM 적용) | 단순 질의 vs 다중 홉(Multi-hop) 필요 질의 분리 |
| **도메인 라우팅 (Domain)** | 키워드 매칭, 의도 분류 (Intent Classification) | 법무 DB vs HR DB vs 외부 웹 검색 분기 |
| **보안/위험 라우팅 (Risk)** | 유해어 필터, 권한 검증, PII(개인정보) 탐지 | VIP 고객 질문은 인간 검토(Human-in-the-loop)로 포워딩 |

## Ⅳ. 심화: Fallback 메커니즘 (라우팅 실패 대응)
- 라우터가 질의를 '단순'으로 오판하여 Naive RAG로 보냈으나, 검색 결과가 형편없을 수 있음.
- **해결 로직**: RAG 각 경로의 마지막에 응답 신뢰도(Confidence Score) 측정 봇을 둠. "답변이 질문을 완전히 해결하지 못했다(Score < 0.7)"고 판정되면, 답변을 내보내지 않고 즉시 상위 경로(예: Advanced RAG)로 에스컬레이션(Escalation)하여 재실행(Fallback)함.

## Ⅴ. 고정 RAG 대비 가치 비교 (Trade-off)
| 평가 지표 | 고정형 Advanced RAG | Adaptive RAG |
|:---:|:---|:---|
| **운영 비용 (FinOps)**| 매우 높음 (모든 질문에 Reranker 호출) | **낮음 ~ 중간** (단순 질문 처리 비용 절감) |
| **평균 응답 지연 (Avg Latency)**| 균일하게 느림 (예: 1.5초 고정) | 질의별 상이 (단순 질의는 즉각 반응) |
| **아키텍처 복잡도** | 단일 파이프라인 (유지보수 용이) | **매우 복잡** (분류기 및 분기별 코드 유지보수) |
| **비즈니스 효과** | 안정적인 일관성 보장 | SLA 최적화, 대규모 트래픽(B2C) 수용 용이 |

## Ⅵ. 실무 적용 및 결론
- **판단 지표**: 라우팅 정확도(Accuracy of Classifier $\ge$ 90%), 경로별 트래픽 분산율, 월간 전체 벡터DB 및 LLM 토큰 API 호출 비용 절감률.
- **실무 설계**: 대국민 공공서비스 민원 챗봇 구축 시. 하루 100만 건의 쿼리 발생. 이 중 40%는 단순 FAQ("여권 발급 위치")이므로 Semantic Cache + No RAG 경로로 라우팅. 50%는 단일 규정 확인 질의로 Naive RAG(Vector Search)로 처리. 오직 10%의 예외적 분쟁성 복합 질의("A 상황인데 B법령과 C조례 중 무엇이 우선인가요?")에 대해서만 Multi-hop RAG + Web Search 경로를 태워 1건당 5초의 리소스를 태움. 결과적으로 전체 운영 예산을 40% 절감하면서도 체감 성능 저하를 방어함.
- **결론**: Adaptive RAG는 RAG 시스템이 실험실을 벗어나 경제성이 담보된 상용 서비스(Production)로 정착하기 위한 필수 아키텍처이며, 비용과 성능 사이의 딜레마를 해결하는 지능형 스위치보드(Switchboard) 역할을 수행함.

### 🔀 문제 유형별 목차 전환
- **Ⅱ·Ⅲ 강조 (개념/원리형)**: 질의 분류기(Classifier)의 구현 방식(Rule-based, Small LLM, Prompt-based), 도메인/메타데이터 라우팅 알고리즘의 동작 구조 중심 서술.
- **Ⅴ·Ⅵ 강조 (실무/설계형)**: FinOps(클라우드 비용 최적화) 관점의 정량적 절감 효과, 라우터 오분류 시의 에스컬레이션(Fallback) 복구 아키텍처 설계, 경로별 SLA 차등 설정 전략 작성.
