# 📖 【암기용】 개념 완전 이해

> 목적: 멀티 에이전트 협업을 처음 봐도 완벽히 이해하게 만든다.

## 한눈에
- **개요**: 여러 에이전트가 역할을 나누어 공동 목표를 해결하는 구조
- **왜 필요한가**: 복잡 업무는 검색, 분석, 실행, 검증이 동시에 필요해 단일 모델 프롬프트로 한계가 있음.
- **핵심 직관**: 한 명의 만능 담당자보다 역할이 다른 팀이 검토하고 실행하는 방식임.

## 깊이 이해
- **배경·문제의식**: LLM 에이전트가 고위험 업무까지 다루면 권한 집중, 환각 전파, 검증 부재 문제가 발생함.
- **작동 원리**: Planner, Executor, Critic, Domain Agent가 각자 산출물을 만들고 상호 검토 후 결과를 확정함.
- **비유**: 개발 프로젝트에서 기획자, 개발자, 보안담당자, QA가 같은 목표를 역할별로 처리하는 구조.
- **구체 예시**: 코드 수정 협업에서 분석 Agent가 원인 파악, 코딩 Agent가 패치, 테스트 Agent가 회귀 테스트를 수행함.
- **흔한 오해·주의점**: Agent 수를 늘리면 품질이 항상 오르는 것이 아니며 지연, 비용, 충돌 조정 부담이 증가함.

## 연결 개념
- A2A — Agent 간 통신 방식
- Critic Agent — 결과 검토 역할
- Agent Observability — Agent별 판단 추적

# 📝 【답안용】 시험 답안 템플릿

> 목적: 시험장에서 25분에 그대로 쓰는 답안 양식.

## 핵심 인사이트 (3줄 요약)

> 1. **본질**: 멀티 에이전트 협업은 역할별 에이전트가 계획·실행·검토·통합을 분담하는 구조임.
> 2. **가치**: 전문성 분리와 상호 검증으로 복합 업무 처리의 오류 전파를 줄임.
> 3. **판단 포인트**: Agent 수, 역할 경계, 충돌 해결, 비용 한도, 감사 추적을 설계해야 함.

## 출제 의도 및 답안 포인트

| 출제 의도 | 반드시 짚을 핵심 | 감점 회피 포인트 |
|:---|:---|:---|
| 복합 업무에서 에이전트 분업 설계 역량 확인 | Planner-Executor-Critic 역할 분리, 충돌 해결, Trace ID 기반 감사 | Agent 수 증가를 품질 향상과 동일시, 비용·지연 미고려 |
| 상호 검증과 결과 통합 방식 이해 | Critic 검토 단계, Aggregator 통합, 고위험 결정 시 Human Approval | 단일 Agent 자기검토와 Critic 검토 차이 미구분 |

> 요약: 멀티 에이전트는 역할 분리·상호 검증·비용 통제를 함께 설계해야 함을 확인하는 문제임.

---

## Ⅰ. 개요 및 필요성

- 정의: 다중 Agent가 역할을 분담해 공동 목표를 처리하는 분업 구조
- 배경: 단일 Agent는 권한 집중, 환각 전파, 검증 부재로 고위험 업무에 부적합
- 필요성: 역할 분리와 상호 검증으로 오류 탐지율 80% 이상, 환각 전파 차단

---

## Ⅱ. 구조 및 구성요소

```text
User Goal -> Planner -> Executor -> Critic -> Aggregator
               |           |          |           |
               +-> Domain Agents / Tools ---------+
```

| 구성요소 | 역할 | 특이사항 |
|:---|:---|:---|
| Planner | 작업 분해·순서 결정 | 목표·제약 반영 |
| Executor | 도구 호출·작업 수행 | 권한 등급 제한 |
| Critic | 산출물 검토 | 오류·근거·정책 점검 |
| Aggregator | 결과 통합 | 충돌 해결·최종 응답 |

> 요약: 멀티 에이전트는 계획, 실행, 검토, 통합 역할을 분리해 협업 흐름을 구성함.

---

## Ⅲ. 동작원리 및 흐름도

```text
목표 수신 -> 역할 할당 -> 병렬/순차 실행 -> 상호 검토
        -> 충돌 조정 -> 최종 결과 -> 로그 저장
```

| 단계 | 처리 내용 | 검증 기준 |
|:---:|:---|:---|
| 1 | 목표와 역할 정의 | Agent별 책임·권한 |
| 2 | 작업 실행 | 성공률, p95 지연, 비용 |
| 3 | 상호 검토 | 근거, 정책, 테스트 결과 |
| 4 | 통합·감사 | 충돌률, Trace ID, 승인 |

> 요약: 멀티 에이전트 협업은 역할별 산출물을 검토·통합해 최종 결과를 만든다.

---

## Ⅳ. 특징

| 구분 | 단일 Agent | 멀티 Agent | 수치·판단 포인트 |
|:---|:---|:---|:---|
| 처리 방식 | 한 흐름에서 수행 | 역할별 병렬·순차 수행 | Agent 수, 단계 수 |
| 검증 | 자기검토 의존 | Critic·QA Agent 활용 | 오류 탐지율 |
| 비용 | 상대적으로 낮음 | 호출·조정 비용 증가 | 작업당 토큰, p95 지연 |

> 요약: 멀티 에이전트는 검증력을 얻는 대신 지연과 비용을 관리해야 함.

---

## Ⅴ. 심화 비교 및 적용 판단

| 구분 | 단일 Agent | 멀티 Agent 협업 | 선택 기준 |
|:---|:---|:---|:---|
| 구조 | 단일 컨텍스트 처리 | Planner-Executor-Critic 분업 | 검증 필요 단계 2개 이상이면 멀티 Agent |
| 비용/성능 | 1회 호출, 토큰 절약 | Agent당 호출, 조정 비용 발생 | 작업당 총 토큰 50,000 이내 통제 |
| 운영/위험 | 자기검토 의존 | Critic 검토, 충돌 조정 필요 | 오류 탐지율 80% 이상 목표 |

> 요약: 검증이 필요한 고위험 업무에 멀티 Agent를 적용하고 단순 조회는 단일 Agent로 처리함.

| 리스크 | 원인 | 대응 방안 | 확인 지표 |
|:---|:---|:---|:---|
| Agent 간 결과 충돌 | 동일 질문에 상이한 판단 반환 | Aggregator에서 근거 수·신뢰도 비교, 상충 시 사람 승인 | 충돌 발생률, 사람 승인 비율 |
| 비용·지연 초과 | Agent 수·루프 증가 | 작업당 최대 Agent 수 5개, 최대 루프 3회, 토큰 예산 설정 | 작업당 토큰, p95 지연 |
| 환각 전파 | 한 Agent 오류가 후속 Agent 입력에 포함 | Critic Agent 검토 의무화, 근거 링크 필수, 무근거 결과 차단 | 환각 탐지 건수, 근거 누락률 |

> 요약: 충돌·비용·환각을 Aggregator 정책, 예산 한도, Critic 검토로 통제함.

| 점검 항목 | 목표 기준 | 측정 방법 |
|:---|:---|:---|
| 성능/효율 | p95 지연 5초 이내, 작업당 토큰 50,000 이내 | APM 대시보드, 토큰 사용 로그 |
| 품질/정확도 | 오류 탐지율 80% 이상, 근거 누락 0건 | Critic 검토 로그, 근거 검증 보고 |
| 운영/보안 | Agent별 Trace ID 연결률 100%, 권한 위반 0건 | 감사 로그, RBAC 점검 보고 |

> 요약: 지연·토큰·오류탐지율·Trace 연결률로 멀티 에이전트 운영 성과를 판단함.

---

## Ⅵ. 실무 적용 및 결론

**적용 방안 3개:**
1. Planner, Executor, Critic, Auditor 역할을 분리하고 Agent별 도구 권한을 최소화
2. 작업당 최대 Agent 수, 최대 루프, 토큰 예산, p95 지연 목표를 정책으로 설정
3. Agent별 입력·출력·도구 호출·판단 근거를 Trace ID로 연결해 사후 재현성 확보

**결론 (2줄):**
- 기술사 판단: 고위험·복합 업무는 멀티 에이전트, 단순 질의는 단일 Agent 구조가 적합함.
- 향후 방향: 멀티 에이전트 협업은 A2A, MCP, Agent Observability와 결합해 운영체계가 표준화됨.

| 요구사항 명시형 | 설계하시오, 방안을 제시하시오 | Agent별 권한·비용 통제 | 지연·충돌·감사 대책 |
