# 📖 【암기용】 개념 완전 이해

## 한눈에
- **개요**: **멀티 에이전트 협업**은 **역할이 다른 여러 자율 에이전트**(001 참조)가 하나의 목표를 나눠 맡아 **상호작용 패턴**(역할 분담·순차 전달·토론)으로 결과를 합쳐 완성하는 구조다.
- **왜 필요한가**: 단일 에이전트에 모든 도구·지식·판단을 몰아넣으면 프롬프트가 비대해지고 전문성이 흐려진다. 문제를 전문가별로 쪼개 각자 잘하는 부분만 맡기면 정확도·재사용성이 오른다.
- **핵심 직관**: 만능 1인 대신 "TF 팀"이다. 기획·개발·검수를 각 담당자가 맡고, 서로 결과물을 주고받거나 토론해 최종안을 만든다. 이 "누가·어떻게 상호작용하는가(토폴로지)"가 협업의 본질이다.

## 핵심 용어 정리 (내부에 등장하는 것들)
답안 본문에 등장하는 용어를 처음 보는 사람도 이해하도록 비유와 함께 먼저 정리한다.

| 용어/표기 | 의미 | 비유·예 |
|:---|:---|:---|
| 멀티 에이전트 협업(핵심) | 역할이 다른 여러 에이전트가 상호작용으로 목표를 완성하는 구조 | 여러 담당자로 구성된 "TF 팀" |
| 역할 분담(Role Specialization) | 에이전트마다 전담 기능·도구·페르소나를 부여 | 기획·개발·QA "직무 배정" |
| 협업 토폴로지 | 에이전트 간 연결·상호작용 형태(계층/수평/토론) | 팀 조직도의 "보고 라인" |
| 계층형(Hierarchical) | 상위가 하위에 지시·통합하는 위계 구조 | 팀장-팀원 "지휘 체계" |
| 수평형(Peer/파이프라인) | 대등 에이전트가 순차로 산출물을 전달·정제 | 컨베이어 "조립 라인" |
| 토론형(Debate) | 여러 에이전트가 상반된 답을 내고 비판·수렴 | 찬반 "패널 토론" |
| 비평가(Critic)·검증 에이전트 | 다른 에이전트 출력을 검토·반박하는 역할 | 원고를 보는 "교정 담당" |
| 공유 상태/블랙보드 | 에이전트들이 함께 읽고 쓰는 작업 공간 | 팀 공용 "화이트보드" |
| A2A(012 참조) | 에이전트 간 발견·위임·협업 통신 표준 | 담당자 간 "업무 의뢰 규약" |
| 합의(Consensus)·투표 | 여러 답을 다수결·가중치로 종합 | 회의 "표결" |

## 깊이 이해
- **배경·문제의식**: 단일 에이전트(001)는 도구 수십 개와 복합 규칙을 한 컨텍스트에 담을수록 판단이 흐려지고(컨텍스트 희석), 한 번 틀리면 교정할 관점이 없다. 사람 조직이 분업·상호검토로 품질을 올리듯, 문제를 전문 역할로 나누고 상호작용시키면 각 에이전트의 프롬프트가 좁아져 정확도가 오르고 상호 검증이 가능해진다.
- **작동 원리(어떻게+왜)**: ① 목표를 역할 단위(예: 조사→작성→검수)로 분해하고 ② 각 역할에 전용 도구·시스템 프롬프트를 부여하며 ③ 토폴로지(계층·수평·토론)에 따라 결과물을 전달·병합한다. 계층형은 상위 에이전트가 하위 산출물을 통합해 일관성을 확보하고, 토론형은 상반된 답을 부딪혀 오류를 걸러낸다. 상호작용은 공유 상태(블랙보드)나 A2A(012) 메시지로 오간다.
- **비유**: 신문사. 취재기자(조사)가 초고를 쓰면 데스크(작성)가 다듬고, 교열기자(비평가)가 사실·문법을 검증한다. 사안이 민감하면 여러 기자가 서로 반박하며(토론) 최종 논조를 정한다.
- **구체 예시(실제 프레임워크·사례)**: Microsoft AutoGen은 대화형 다중 에이전트(작성자-비평가)로 코드 생성·검증을 반복하고, CrewAI는 역할·목표·도구를 가진 Crew를 구성한다. MetaGPT는 PM·아키텍트·개발자 역할로 SW 개발 파이프라인을 모사한다. 토론형은 여러 LLM이 답을 내고 서로 반박해 정답률을 높인 Multi-Agent Debate 연구가 대표적이다.
- **흔한 오해·주의점**: "에이전트를 많이 붙일수록 좋다"가 아니다. 에이전트가 늘면 통신 비용·지연·오류 전파(한 에이전트의 환각이 다음으로 전이)가 커진다. 협업이 실효를 내려면 역할 경계·종료 조건·합의 규칙이 명확해야 한다.

## 연결 개념
- 에이전트 오케스트레이션(014) — 협업을 중앙 조정자가 제어·라우팅하는 상위 관점
- A2A(012) — 이기종 에이전트 협업의 통신·위임 표준
- 에이전트 플래닝(015) — 협업 전 목표를 역할·하위작업으로 분해하는 계획 단계

# 📝 【답안용】 시험 답안 템플릿

## 핵심 인사이트 (3줄 요약)

> 1. **본질**: 멀티 에이전트 협업은 역할이 다른 다수 에이전트를 계층·수평·토론 토폴로지로 상호작용시켜 목표를 완성하는 구조임.
> 2. **가치**: 문제를 전문 역할로 분업하고 상호 검증해 단일 에이전트의 컨텍스트 희석·오류 무교정 한계를 보완함.
> 3. **판단 포인트**: 에이전트 수 확대보다 역할 경계·종료 조건·합의 규칙과 오류 전파 통제를 먼저 설계해야 함.

## Ⅰ. 개요 및 필요성

- 개요: 역할이 다른 여러 자율 에이전트가 상호작용해 하나의 목표를 완성하는 협업 구조임
- 배경: 단일 에이전트는 도구·규칙 과다 시 컨텍스트가 희석되고 자기 오류를 교정할 관점이 없음
- 필요성: 문제를 전문 역할로 분업하고 상호 검증해 정확도·재사용성을 높여야 함
- 위치: A2A(012) 통신 위에서 역할 분담·상호작용 패턴을 정의하는 협업 계층임

---

## Ⅱ. 구조 및 구성요소

- 선형 구조도

```text
목표 -> 역할 분해(조사/작성/검수) -> 역할별 에이전트(전용 도구·시스템 프롬프트)
  상호작용: 계층형(상위가 통합) / 수평형(순차 전달) / 토론형(상호 반박)
  -> 공유 상태·A2A 메시지 교환 -> 합의·투표 -> 통합 결과
```

| 구성요소 | 역할 | 특이사항 |
|:---|:---|:---|
| 역할 에이전트 | 전담 기능·도구·페르소나 수행 | 좁은 프롬프트로 전문성 확보 |
| 비평가·검증 에이전트 | 타 에이전트 출력 검토·반박 | 오류·환각 필터 |
| 협업 토폴로지 | 계층·수평·토론 상호작용 형태 | 문제 성격에 맞춰 선택 |
| 공유 상태·블랙보드 | 공동 읽기·쓰기 작업 공간 | 상태 일관성·락 필요 |
| 합의·통합기 | 다수 결과를 투표·병합 | 종료 조건·충돌 해소 |

> 요약: 역할 에이전트를 토폴로지로 상호작용시키고 공유 상태·합의로 결과를 통합함.

---

## Ⅲ. 동작원리 및 흐름도

- 선형 흐름도

```text
목표 입력 -> 역할 분해 -> 역할별 에이전트 실행 -> 상호작용(전달·반박·검증) -> 합의·투표 -> 통합 결과 반환
```

1. 역할 분해: 조정자가 목표를 역할 단위로 나누고 각 에이전트에 전용 도구·프롬프트를 배정함
2. 역할 실행: 각 에이전트가 자기 하위 작업을 수행해 산출물을 공유 상태에 기록함
3. 상호작용: 토폴로지에 따라 상위가 통합하거나 대등 에이전트가 순차 전달·상호 반박함
4. 합의·종료: 비평가 검증·투표로 결과를 수렴하고 종료 조건 충족 시 통합 결과를 반환함

> 요약: 역할 분해 후 각자 수행하고 토폴로지에 따라 상호작용·검증해 합의로 완결함.

---

## Ⅳ. 특징

- 역할 전문화: 에이전트별로 도구·페르소나를 좁혀 프롬프트 희석 없이 전문성을 확보함
- 상호 검증: 비평가·토론으로 단일 에이전트가 못하는 자기 오류 교정을 수행함
- 토폴로지 가변성: 계층·수평·토론을 문제 성격에 맞춰 조합·전환함
- 오류 전파 취약성: 한 에이전트의 환각이 다음 에이전트로 전이될 수 있어 검증 지점이 필수임
- 비용·지연 증가: 에이전트·왕복 수에 비례해 토큰 비용과 응답 지연이 늘어남

## Ⅴ. 심화 비교 및 적용 판단

- 협업의 핵심 선택은 어떤 토폴로지로 상호작용시키느냐이며 세 유형을 대비함

| 구분 | 계층형(Hierarchical) | 수평형(Pipeline/Peer) | 토론형(Debate) |
|:---|:---|:---|:---|
| 상호작용 | 상위가 지시·통합 | 순차로 산출물 전달 | 상반 답 상호 반박 |
| 일관성 확보 | 상위 통합으로 강함 | 단계 정의에 의존 | 수렴 규칙에 의존 |
| 오류 교정 | 상위 검토에 의존 | 다음 단계가 정제 | 상호 반박으로 강함 |
| 적합 문제 | 복합 통합 과제 | 정형 다단계 처리 | 정답 불확실·고난도 판단 |
| 비용 특성 | 통합 병목 | 단계 수 비례 | 라운드 수만큼 급증 |

> 요약: 통합 일관성이 중요하면 계층형, 정형 파이프는 수평형, 오답 위험이 큰 판단은 토론형이 적합함.

- 주요 리스크와 대응(불릿)
  - 오류 전파 — 상류 환각의 하류 전이가 원인 → 단계별 비평가 검증·출력 스키마 강제
  - 무한 상호작용 — 토론·재작업 미종료가 원인 → 최대 라운드 제한·수렴 임계값 설정
  - 비용 폭증 — 에이전트·왕복 급증이 원인 → 역할 수 최소화·병렬 상한·토큰 예산 배정
- 운영 지표(불릿)
  - 협업 정답률 — 단일 에이전트 대비 향상폭 목표 — 벤치마크 A/B 측정
  - 수렴 라운드 — 평균 3회 이내 목표 — 상호작용 로그 집계
  - 에이전트당 비용 — 목표 토큰 예산 이내 — 역할별 사용량 계측

## Ⅵ. 실무 적용 및 결론

- 적용 방안
  1. AutoGen·CrewAI로 작성자-비평가 역할을 구성해 코드·문서 생성 후 검증 루프를 강제
  2. 고난도 판단은 3개 LLM 토론형으로 상반 답을 반박·투표하고 최대 라운드를 3회로 제한
  3. 이기종 에이전트 협업은 A2A(012)로 위임·통신하고 공유 상태는 블랙보드로 일관성 관리
- 결론
  - 기술사 판단: 통합 일관성이 핵심이면 계층형, 오답 위험이 큰 판단이면 토론형으로 토폴로지를 이원화함
  - 향후 방향: 협업은 오케스트레이션(014)·플래닝(015)과 결합해 자기조직화 에이전트 팀으로 발전됨
