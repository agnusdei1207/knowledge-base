# 📖 【암기용】 개념 완전 이해

> 목적: 100개로 쪼개진 마이크로서비스들이 서로 통신할 때 발생하는 지옥 같은 '네트워크 복잡성'을, 개발자 몰래 인프라 단에서 어떻게 깔끔하게 해결했는지 이해한다.

## 한눈에
- **정의**: 마이크로서비스(MSA) 환경에서 수많은 컨테이너(서비스) 간의 **통신(라우팅, 보안, 모니터링)을 비즈니스 로직(코드)과 완전히 분리하여 인프라 계층에서 전담 처리하는 아키텍처 패턴**
- **필요성**: MSA로 넘어가면서 서비스끼리 API를 수만 번씩 호출하게 되자, "타임아웃 처리, 재시도(Retry), 암호화(mTLS), 로깅" 같은 통신 제어 코드를 모든 서비스마다 일일이 짜넣어야 하는 '중복의 늪'에 빠졌기 때문
- **핵심 직관**: "모든 사무실(서비스)에 '비서(Sidecar Proxy)'를 한 명씩 붙여주고, 사장(개발자)은 비서에게 '영업팀에 서류 좀 전해줘'라고만 하면, 비서가 알아서 암호화하고 영수증(로그)을 챙겨서 전달하는 시스템"

## 깊이 이해
- **배경(왜 등장했나?)**: 과거엔 넷플릭스 OSS 같은 '라이브러리'를 각 서비스(Java, Node.js) 코드 안에 직접 심어서 통신을 제어했다. 그런데 언어마다 라이브러리를 다 따로 만들어야 하고, 업데이트할 때마다 모든 서비스를 다시 배포해야 했다. 그래서 "차라리 컨테이너 옆에 '통신 전용 프록시(대리인)'를 하나씩 붙여서 통신을 싹 다 가로채자!"라는 기발한 아이디어가 나왔고, 이것이 서비스 메시다.
- **작동 원리(어떻게 달성했나?)**: 
  1. **Sidecar Pattern**: K8s의 Pod 안에 실제 앱 컨테이너 옆에 'Envoy(엔보이)'라는 고성능 프록시 컨테이너를 몰래 하나 더 띄운다(사이드카).
  2. **Data Plane**: 앱이 다른 서비스로 API를 쏘면, 앱 몰래 사이드카가 그걸 가로채서(Intercept) 암호화하고 상대방 사이드카로 전달한다.
  3. **Control Plane**: 관리자(Istio)가 중앙에서 "앞으로 결제팀 트래픽의 10%만 신규 버전으로 보내(카나리 배포)"라고 설정하면, 수백 개의 사이드카들에게 한 번에 룰(Rule)을 쫙 뿌려준다.
- **일상 비유**: 회사에서 부서 간 전화를 할 때, 직원(앱)이 직접 다이얼을 돌리는 게 아니라 무조건 '각 부서 전담 교환수(사이드카)'를 거쳐야 한다. 중앙 통제실(컨트롤 플레인)에서 "오늘부터 A부서 전화는 도청 방지(암호화)하고, B부서로 가는 전화는 3번 울려도 안 받으면 끊어(Timeout)"라고 지시하면 모든 교환수가 알아서 처리한다.
- **구체 예시**: 구글/IBM/Lyft가 주도하여 만든 **Istio(이스티오)**가 컨트롤 플레인 역할을 하고, Lyft가 만든 **Envoy(엔보이)**가 사이드카(데이터 플레인) 역할을 하는 조합이 시장의 절대 표준이다.
- **흔한 오해/주의점**: "API Gateway와 Service Mesh는 같은 것 아닌가?" → 다르다! API Gateway는 **'외부'**에서 클러스터 내부로 들어오는 남북(North-South) 트래픽을 통제하는 '정문 수위 아저씨'이고, Service Mesh는 클러스터 **'내부'** 서비스들끼리 통신하는 동서(East-West) 트래픽을 통제하는 '사내 우편집배원'이다.

## 연결 개념
- **Sidecar Proxy**: 메인 애플리케이션 옆에 보조용으로 붙어서 통신을 대리하는 프록시. (Envoy가 대표적)
- **MSA (Microservices Architecture)**: 서비스 메시가 존재해야만 하는 근본적인 이유. (서비스가 몇 개 없으면 서비스 메시는 오버헤드일 뿐이다.)
- **mTLS (Mutual TLS)**: 서비스 메시가 켜져 있으면, 서비스 간의 모든 통신을 '서로' 인증하고 암호화하는 가장 완벽한 내부 보안.

# 📝 【답안용】 시험 답안 템플릿

## 핵심 인사이트 (3줄 요약)
> 1. **본질**: 서비스 메시(Service Mesh)는 MSA 환경에서 서비스 간 통신(East-West Traffic)을 비즈니스 로직과 분리하여, 인프라 계층(사이드카 프록시)에서 트래픽 제어, 보안, 관측성을 일괄 제공하는 아키텍처 패턴이다.
> 2. **가치**: 개발자는 언어(Language)나 프레임워크에 구속되지 않고 순수 비즈니스 로직 개발에만 집중할 수 있으며, 인프라 운영자는 코드를 건드리지 않고도 클러스터 전체의 네트워크 정책을 중앙 통제할 수 있다.
> 3. **판단 포인트**: Istio + Envoy 조합의 Control/Data Plane 아키텍처를 이해하고, API Gateway(North-South)와의 역할 분담, 그리고 사이드카로 인한 자원 오버헤드(Latency/Memory)를 고려한 아키텍처 최적화가 필수적이다.

## Ⅰ. 개요 및 필요성
- **정의**: 마이크로서비스 간의 복잡한 통신 네트워크를 안전하고, 빠르고, 신뢰할 수 있게 만들기 위해 인프라스트럭처 레벨에 삽입된 전용 통신 계층(Layer)
- **배경**: MSA 전환 후, 서비스 간 호출 실패, 네트워크 지연, 병목 지점 파악 불가 등 '분산 시스템의 오류(Fallacies of Distributed Computing)' 문제 직면. 기존 Fat-Client 라이브러리(Spring Cloud 등) 방식은 다국어(Polyglot) 지원이 어렵고 침투적(Invasive)임
- **필요성**: 비즈니스 로직과 네트워크 제어 로직의 완벽한 분리(Decoupling), 투명한 트래픽 제어(Traffic Management), 내부 서비스 간 제로 트러스트(Zero Trust) 보안 구현

## Ⅱ. 서비스 메시 아키텍처: Control Plane과 Data Plane
서비스 메시는 논리적으로 두 개의 플레인으로 명확히 나뉜다. (Istio + Envoy 기준)

```text
[ 관리자 (YAML 정책 설정) ]
           │
┌──────────▼──────────────────────────┐
│        Control Plane (Istio)        │
│ - Pilot   : 프록시 라우팅 룰 배포       │
│ - Citadel : 인증서(mTLS) 발급 및 관리  │
│ - Galley  : 설정 검증 및 변환         │
└──────────┬──────────────────────────┘
 (정책 및 인증서 셋업) ▼  (Telemetry 수집) ▲
┌──────────┴──────────────────────────┐
│           Data Plane                │
│  [ Pod A ]             [ Pod B ]    │
│ ┌───────┐ ◀ 통신 가로채기 ┌───────┐    │
│ │ App A │             │ App B │    │
│ └───────┘             └───────┘    │
│ ┌───────┐   (mTLS)    ┌───────┐    │
│ │ Envoy │ ◀─────────▶ │ Envoy │    │
│ └───────┘  (통신 수행)  └───────┘    │
└─────────────────────────────────────┘
```

## Ⅲ. 서비스 메시 3대 핵심 기능
1. **Traffic Management (트래픽 제어)**
   - **기능**: 서비스 디스커버리, 로드 밸런싱, A/B 테스트 및 카나리(Canary) 배포 (ex. 신규 버전으로 5% 트래픽만 전송).
   - **안정성**: Circuit Breaker(장애 전파 차단), Retry(재시도), Timeout, Fault Injection(결함 주입 테스트) 지원.
2. **Security (보안 및 인증)**
   - **기능**: 모든 사이드카 프록시 간의 통신을 상호 인증 및 암호화하는 **mTLS(Mutual TLS)**를 코드 수정 없이 자동 적용하여 사내망 도청 원천 차단.
3. **Observability (관측성)**
   - **기능**: 서비스 간 통신의 메트릭(지연시간, 에러율), 분산 추적 로그(Distributed Tracing, 예: Jaeger 연동), 트래픽 흐름도를 자동으로 수집 및 시각화.

## Ⅳ. API Gateway vs Service Mesh 역할 비교
마이크로서비스 네트워크 아키텍처에서 두 요소는 대체재가 아닌 보완재이다.

| 구분 | API Gateway | Service Mesh |
|:---|:---|:---|
| **트래픽 방향** | North-South (외부 클라이언트 ➔ 내부) | **East-West (내부 서비스 ➔ 내부 서비스)** |
| **주요 역할** | 라우팅, 외부 인증(OAuth), 속도 제한(Rate Limit), 과금 | **내부 mTLS, 카나리 배포, 서킷 브레이커, 분산 추적** |
| **배치 위치** | 클러스터 진입점 (Edge) | **클러스터 내부 각 Pod (Sidecar)** |
| **적용 단위** | 비즈니스 도메인 / 시스템 전체 | **개별 컨테이너 / 마이크로서비스** |

## Ⅴ. 기술적 한계(리스크) 및 최신 발전 동향 (Sidecarless)
| 리스크 요인 | 원인 분석 | 최신 트렌드: Sidecarless Mesh (eBPF) |
|:---|:---|:---|
| **자원 오버헤드 (Cost)** | 수백 개의 Pod마다 Envoy 컨테이너가 하나씩 더 떠야 하므로, 메모리 및 CPU 자원 낭비 심각 | **Cilium (eBPF 기반)**: 리눅스 커널 레벨에서 네트워크를 통제하여 사이드카 없이 서비스 메시 구현 |
| **지연 시간 (Latency)** | `App ➔ Envoy ➔ Envoy ➔ App` 구조로 인해 네트워크 홉(Hop)이 추가되어 지연 시간 발생 | **Istio Ambient Mesh**: 사이드카 패턴을 버리고 노드 단위의 공유 프록시(ztunnel) 계층으로 레이어 통합 전환 중 |
| **운영 복잡성 극상** | Istio 자체의 학습 곡선이 K8s만큼 높음 | 클라우드 관리형(AWS App Mesh, GCP Anthos Service Mesh) 도입 |

## Ⅵ. 실무 적용 및 결론
**적용 방안 및 실무 가이드:**
1. **점진적 도입(Phased Adoption)**: 처음부터 모든 기능을 켜지 않는다. 1단계로 mTLS(보안)만 활성화하고, 2단계로 Observability(추적)를 켜서 모니터링 체계를 잡은 뒤, 마지막에 무중단 배포(카나리) 라우팅을 적용하는 순차적 전략이 안전하다.
2. **K8s Network Policy와 병행**: 서비스 메시는 L7(애플리케이션 계층) 통제를 담당하므로, L3/L4(IP/Port) 통제는 쿠버네티스의 네이티브 Network Policy(Calico 등)와 결합하여 다층 심층 방어(Defense in Depth)를 구성해야 한다.

**결론:**
- 서비스 메시는 복잡한 분산 환경에서 **"네트워크는 절대 신뢰할 수 없다"**는 대전제를 인프라 차원에서 해결해 준 클라우드 네이티브의 마스터키이다.
- 무분별한 도입은 독이 되지만, 서비스 개수가 수십 개를 넘어가고 다국어(Polyglot) 환경이 혼재된 거대 엔터프라이즈 환경에서는 선택이 아닌 생존을 위한 필수 아키텍처이다.

### 🔀 문제 유형별 목차 전환
| 문제 유형 | 문제 신호어 | Ⅱ·Ⅲ 강조 (기능/아키텍처) | Ⅳ·Ⅴ 강조 (비교/최신동향) |
|:---|:---|:---|:---|
| **클라우드 네이티브 아키텍처형**| "Istio", "Sidecar Pattern" | Control/Data Plane 분리 도식화 및 트래픽/보안/관측성 3대 기능 중심 서술 | API Gateway와의 역할 분담(North-South vs East-West) 명확화 |
| **차세대 네트워크 기술형** | "MSA 통신 병목", "eBPF" | mTLS를 통한 제로 트러스트 보안 및 Circuit Breaker 메커니즘 | Ⅴ 사이드카 오버헤드의 한계 지적 및 eBPF 기반의 Sidecarless Mesh(Ambient Mesh) 진화 방향 전면 배치 |
