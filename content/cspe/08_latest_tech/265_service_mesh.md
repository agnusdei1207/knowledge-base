# 📖 【암기용】 개념 완전 이해

> 목적: 서비스 메시를 처음 봐도 완벽히 이해하게 만든다. 시험 답안 양식이 아니라, 이해를 위한 친절한 설명이다.

## 한눈에
- **개요**: 마이크로서비스(MSA) 환경에서 서비스들 사이의 통신(네트워킹)을 안전하고 신뢰성 있게 관리하기 위한 인프라 계층
- **왜 필요한가**: 서비스가 수백 개로 늘어나면 "누가 누구와 통신하는지", "어디서 에러가 나는지", "보안은 잘 지켜지는지" 일일이 코드에 넣기 힘들기 때문이다. 이를 서비스 밖(인프라)에서 대신 처리해준다.
- **핵심 직관**: "각 서비스 옆에 전담 비서(사이드카 프록시)를 하나씩 붙여서, 전화 걸기(통신), 녹음하기(로깅), 보안 검사하기(인증)를 비서들끼리 알아서 하게 만드는 시스템"

## 깊이 이해
- **배경·문제의식**: 예전에는 재시도(Retry), 타임아웃(Timeout), 서킷 브레이커(Circuit Breaker) 같은 통신 로직을 애플리케이션 코드 안에 직접 짰다. 서비스마다 언어가 다르면 라이브러리를 다 따로 관리해야 했고, 인프라 변경 시 코드를 다 고쳐야 하는 불편함이 있었다.
- **작동 원리**:
  1. **사이드카(Sidecar) 패턴**: 서비스 바로 옆에 가벼운 프록시(Envoy 등)를 배치한다. 모든 데이터는 이 프록시를 거친다.
  2. **컨트롤 플레인(Control Plane)**: 중앙 지휘부에서 각 프록시에게 "너는 저 서비스랑 통신할 때 암호화해" 같은 정책을 내린다.
  3. **데이터 플레인(Data Plane)**: 실제 데이터가 오가는 경로로, 프록시들이 정책에 따라 트래픽을 제어한다.
- **비유**: 모든 외교관(서비스)이 외국어를 배울 필요 없이, 각자 전담 통역사(프록시)를 데리고 다니며 통역사들끼리 약속된 프로토콜로 대화하게 하는 것과 같다.
- **구체 예시**: Istio, Linkerd 등이 대표적이다. "사용자 트래픽의 10%만 신규 버전(v2)으로 보내"라는 명령을 내리면 서비스 메시가 알아서 트래픽을 가른다.
- **흔한 오해·주의점**: 서비스 메시는 만능이 아니다. 프록시를 거치기 때문에 약간의 지연 시간(Latency)이 발생하고, 시스템 구조가 더 복잡해진다. 서비스가 몇 개 안 될 때는 도입하지 않는 것이 낫다.

## 연결 개념
- Sidecar Proxy (Envoy) — 서비스 메시의 실제 일꾼 (데이터 플레인)
- Control Plane (Istiod) — 서비스 메시의 두뇌 (정책 설정)
- Observability (관측성) — 서비스 메시 도입으로 얻는 핵심 이득 (Tracing, Metrics)

# 📝 【답안용】 시험 답안 템플릿

> 목적: 시험장에서 25분에 그대로 쓰는 답안 양식. 작성방식(추상표현 금지·수치·도식·문제유형 전환)을 엄격히 지킨다.
> 핵심: 서비스 메시의 3대 핵심 기능(트래픽 관리, 보안, 관측성)과 아키텍처 구조(Control/Data Plane)를 중심으로 기술한다.

## 핵심 인사이트 (3줄 요약)

> 1. **본질**: 서비스 메시(Service Mesh)는 서비스 간 통신(East-West Traffic)을 제어하기 위해 사이드카 프록시를 활용하여 구현한 전용 인프라 계층이다.
> 2. **가치**: 애플리케이션 코드 변경 없이 트래픽 제어, mTLS 보안, 분산 추적(Tracing) 등의 공통 기능을 제공하여 MSA 운영 복잡도를 해소한다.
> 3. **판단 포인트**: 서비스 간 호출 관계가 복잡한 대규모 MSA 환경에서 필수적이나, 추가적인 지연 시간(Latency)과 자원 소모 비용을 고려해야 한다.

## 출제 의도 및 답안 포인트

| 출제 의도 | 반드시 짚을 핵심 | 감점 회피 포인트 |
|:---|:---|:---|
| MSA 통신 복잡도 해결 역량 확인 | 사이드카 패턴, Control/Data Plane 구조 | 단순히 "네트워크 관리 도구"로만 서술 |
| 서비스 메시 핵심 기능 이해도 | 트래픽 시프팅, mTLS 인증, 서킷 브레이커 | 기능 나열 시 구체적 메커니즘 누락 |
| 도입 시 트레이드오프 판단 능력 | 지연 시간 증가, 운영 복잡도, 자원 오버헤드 | 장점만 기술하고 부작용(Penalty) 간과 |

> 요약: 서비스 간 통신의 추상화를 통한 운영 효율화 방안과 기술적 실체(Proxy 기반 제어)를 중심으로 기술한다.

---

## Ⅰ. 개요 및 필요성

- 정의: 마이크로서비스 간 통신을 관리하기 위해 애플리케이션 옆에 배치된 사이드카 프록시 네트워크
- 배경: 서비스 수 증가에 따른 통신 로직(Retry, Timeout 등)의 파편화 및 관리 한계 직면
- 필요성: 비즈니스 로직과 통신 로직의 완전한 분리(Decoupling)를 통한 폴리그랏(Polyglot) 환경 지원 및 가시성 확보

---

## Ⅱ. 구조 및 구성요소

```text
[서비스 메시 아키텍처: Control/Data Plane]
        [Control Plane] (Pilot, Citadel, Galley)
               | (Policy, Config, Certs)
        +------+------+-----------------+
        |             |                 |
[Service A] -- [Envoy Proxy] <--- mTLS ---> [Envoy Proxy] -- [Service B]
 [Data Plane]  (Sidecar)                     (Sidecar)    [Data Plane]
```

| 구성요소 | 역할 | 특이사항 |
|:---|:---|:---|
| Data Plane | 실제 서비스 트래픽을 가로채고 전달 | Envoy, Linkerd-proxy 등 고성능 프록시 |
| Control Plane | 프록시들에게 정책과 설정을 배포 | Istiod 등 중앙 관리 서버 |
| Sidecar Proxy | 서비스 포드(Pod) 내에 함께 배포되는 프록시 | 로컬호스트 통신으로 오버헤드 최소화 |
| Ingress/Egress Gateway | 클러스터 외부와의 통신 통로 | 트래픽 진입/진출 지점 제어 |

> 요약: 각 서비스 옆에 붙은 일꾼(Proxy)들과 이들을 중앙에서 지휘하는 지휘부(Control Plane)의 이층 구조다.

---

## Ⅲ. 동작원리 및 흐름도

```text
[트래픽 제어 흐름도]
Request -> Ingress GW -> Sidecar A (Outbound) -> [mTLS] -> Sidecar B (Inbound) -> Service B
             | (Policy Check)                           | (Auth/Rate Limit)
```

| 단계 | 처리 내용 | 검증 기준 |
|:---:|:---|:---|
| 1 | 애플리케이션의 모든 네트워크 요청을 사이드카 프록시가 가로챔(Interception) | iptables 또는 eBPF 기반 리다이렉션 |
| 2 | 프록시가 컨트롤 플레인으로부터 받은 최신 정책 확인 | 로드 밸런싱 알고리즘, 타임아웃 설정 등 |
| 3 | 상호 TLS(mTLS)를 통해 통신 채널 암호화 및 신원 확인 | 인증서(Certificate) 유효성 검사 |
| 4 | 호출 결과 및 메트릭을 수집하여 중앙 관측 도구로 전송 | 분산 추적(Tracing) ID 주입 |

> 요약: 서비스가 직접 전화를 거는 대신, 비서(Proxy)가 정책을 확인하고 암호화된 채널로 대신 전화를 걸어주는 방식이다.

---

## Ⅳ. 특징

| 구분 | 내용 | 판단 포인트 |
|:---|:---|:---|
| 트래픽 관리 | 카나리 배포, 블루/그린 배포, 트래픽 분할 | 신규 기능 배포 리스크 관리 |
| 보안 강화 | 서비스 간 mTLS 자동 적용, 인증/인가(RBAC) | 제로 트러스트(Zero Trust) 아키텍처 구현 |
| 관측성 | 서비스 맵(Topology), 골든 시그널 수집 | 장애 전파 경로 시각화 및 원인 분석 |

> 요약: 코드 수정 없이 인프라 계층에서 보안, 통신 제어, 모니터링을 한 번에 해결하는 것이 핵심이다.

## Ⅴ. 심화 비교 및 적용 판단

| 비교 축 | API Gateway | Service Mesh | 선택 기준 |
|:---|:---|:---|:---|
| 관리 범위 | 외부 -> 내부 통신 (North-South) | 내부 -> 내부 통신 (East-West) | 통신의 방향 및 목적 |
| 주요 기능 | 인증, 과금, API 노출, 포털 | 재시도, 서킷브레이커, mTLS | 제어의 세밀함(Granularity) |
| 배치 위치 | 네트워크 경계 (Edge) | 각 서비스 옆 (Sidecar) | 도입 범위 및 복잡도 |

> 요약: 외부 진입점 관리는 API Gateway가, 내부 서비스 간 복잡한 얽힘은 Service Mesh가 담당한다.

| 리스크 | 원인 | 대응 방안 | 확인 지표 |
|:---|:---|:---|:---|
| 지연 시간 증가 | 프록시 경유에 따른 추가 네트워크 홉(Hop) | 사이드카 없는 메시(Proxyless) 또는 eBPF 활용 | P99 Latency (1~5ms 추가 발생) |
| 리소스 소모 | 수많은 프록시 작동에 따른 CPU/Mem 소비 | 사이드카 리소스 제한(Limit) 및 경량 프록시 선정 | 클러스터 전체 오버헤드 비율 |
| 운영 복잡도 | 복잡한 설정 및 트러블슈팅 난이도 상승 | Kiali 등 가시화 도구 및 표준 프로파일 활용 | 운영 인력의 기술 숙련도 |

> 요약: 지연 시간과 자원 낭비 리스크는 eBPF 기술과 정교한 리소스 튜닝을 통해 관리해야 한다.

| 점검 항목 | 목표 기준 | 측정 방법 |
|:---|:---|:---|
| 프록시 지연 오버헤드 | 서비스 단독 호출 대비 10% 이내 | 사이드카 On/Off 벤치마크 비교 |
| mTLS 적용률 | 클러스터 내 전체 통신의 100% 암호화 | 보안 감사 도구 및 대시보드 |
| 장애 감지 속도 | 비정상 응답 발생 시 1초 내 서킷 오픈 | Fault Injection 테스트 |

> 요약: 통신 지연 오버헤드와 보안 적용 수준을 통해 서비스 메시의 효율성을 정량적으로 평가한다.

## Ⅵ. 실무 적용 및 결론

**적용 방안 3개:**
1. 제로 트러스트 보안 구현: 서비스 간 통신 시 mTLS를 강제하고, 사이드카를 통한 세밀한 접근 제어(Authorization Policy)를 적용하여 내부 침투 차단
2. 지능형 트래픽 라우팅: 헤더 기반의 카나리 배포를 수행하여 특정 사용자군에게만 신규 기능을 노출하고 단계적으로 배포 범위 확대
3. 분산 시스템 가시성 확보: Jaeger/Zipkin 등과 연동하여 서비스 간 호출 지연의 병목 구간을 시각적으로 파악하고 성능 최적화 수행

**결론 (2줄):**
- 기술사 판단: 서비스 메시는 MSA의 '완성'을 위한 인프라 계층이나, 성능 저하와 복잡성을 정당화할 만큼의 규모(Scale)가 확보되었을 때 도입해야 한다
- 향후 방향: 사이드카의 오버헤드를 줄이기 위해 커널 수준에서 트래픽을 제어하는 Sidecar-less(Ambient Mesh) 기술이 주류로 부상할 것이다
