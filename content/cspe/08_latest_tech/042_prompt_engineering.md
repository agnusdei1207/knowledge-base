## 미리 알고가기

- 프롬프트 ($Prompt$): 생성형 AI 모델이 맥락을 이해하고 다음 단어를 유추하도록 주입하는 명령과 질문의 결합체임
- 퓨샷 러닝 ($Few-shot$): 원하는 출력 형식과 의사결정의 중간 논리가 담긴 예시 몇 쌍을 프롬프트에 직접 동반하여 모델을 학습시키는 방식임
- 프롬프트 인젝션 ($Injection$): 사용자 입력 영역을 통해 악의적인 명령어(예: "이전 명령어를 모두 무시하고...")를 주입해 모델을 제어권을 뺏는 해킹 기법임
- 정형 출력 ($Structured$ $Output$): 모델의 무작위 텍스트 대신, $JSON$ 스키마 규칙을 강제하여 후속 외부 API 파이프라인과의 연동을 안정화하는 기술임

## Ⅰ. 개요

- **정의/개념**: Prompt Engineering은 대형 언어 모델($LLM$)의 가중치($Weights$)를 직접 업데이트하지 않고, 주입하는 지시문, 상황 맥락, 입출력 퓨샷 예시를 기하학적으로 최적 구조화하여 모델의 응답 정밀도와 일관성을 극대화하는 인공지능 제어 기술임
- **배경/필요성**: 생성형 AI는 동일한 모델도 질문의 수식어나 배치 순서에 따라 확률적 예측 성능이 널뛰는 불안정성을 가지므로, 비즈니스 수준의 일관된 성능과 연동 규격을 상용 서비스 환경에서 담보하기 위해 고안됨

## Ⅱ. 특징

- 파라미터를 수정하는 미세 조정($Fine-tuning$)에 비해 학습 인프라 구축과 데이터 라벨링에 드는 시간과 비용을 수백 분의 일 수준으로 아끼는 실시간 PoC 가속 효과를 제공함
- 시스템 프롬프트(규칙)와 사용자 입력(데이터)의 물리적 경계를 모호하게 결합하여 작동하므로, 외부 위협 데이터가 침투할 시 지시문 왜곡이나 프라이버시 오염이 발생하기 쉬움
- 최근에는 단순 요령식 기법을 넘어, 템플릿화와 버전 관리 및 프롬프트 최적화용 에이전트($DSPy$ 등)를 활용한 체계적 전산 아키텍처화로 진화하고 있음

## Ⅲ. 종류 및 비교

| 판단 기준 | 애드혹 프롬프트 (Ad-hoc) | 엔지니어링 프롬프트 (Systematic) | 미세 조정 (Fine-tuning) |
|:---|:---|:---|:---|
| **준비 비용** | 없음 (단발성 입력) | 낮음 ~ 중간 (템플릿 설계) | 매우 높음 (인프라 및 학습 비용) |
| **반응 속도** | 즉시 생성 | 즉시 적용 가능 | 훈련 및 검증에 최소 수시간 소요 |
| **보안/안정성** | 오작동에 무방비함 | 필터링 및 탈옥 방지 설계 가능 | 모델 내재적 가이드라인 탑재 가능 |
| **적합한 타깃** | 일회성 번역, 단순 질의 | 챗봇 시나리오, 자동화 파이프라인 | 도메인 고유 언어 체계 학습, 법률용 |

> 요약: 애드혹은 개인 실험에, 엔지니어링은 상용 소프트웨어 통합에, 파인튜닝은 도메인 언어 내재화에 최적임.

## Ⅳ. 구성요소 및 구조

| 구성요소 | 설명 |
|:---|:---|
| 시스템 지시문 | 모델의 아바타 정체성과 권한 한계, 답변 규칙, 절대 금지 사항을 명시하는 통제부임 |
| 상황 맥락 ($Context$) | $RAG$를 통해 얻은 관련 사내 규정이나 데이터베이스 정보 등 판단의 준거가 되는 팩트 원본임 |
| 퓨샷 템플릿 | 질문과 희망하는 정답 형식의 예시 쌍으로, 특히 정형 구조 유도에 핵심적인 역할을 함 |
| 제약/정합 옵션 | $JSON$ 스키마 명세나 마크다운 변환 등 외부 서버가 받아들일 출력 틀을 강제하는 인터페이스임 |

```text
[ 프롬프트 구조 템플릿 ]
--------------------------------------------------
System: 너는 사내 규정 답변 챗봇이다. 모르면 솔직히 모른다고 답해라. (1. 지시문)
Context: [규정 14조: 연차는 입사...] (2. 상황 맥락)
User: 입사 6개월 차 연차 개수가 어떻게 돼? (3. 사용자 질의)
--------------------------------------------------
```

## Ⅴ. 원리 및 절차 흐름도

```text
+-------------+     +--------------+     +-------------+     +-------------+
| 과업 분석   | --> | 템플릿/Fewshot| --> | 스키마 제약 | --> | 자동 검증   |
| 및 조건 수립|     | 맥락 조립설계|     | 출력 포맷팅 |     | 및 튜닝 피드백|
+-------------+     +--------------+     +-------------+     +-------------+
```

1. **경계 획정** — 인공지능이 완수할 구체적 업무(예: 메일 분류)를 분석하여 필요한 입력 포맷과 예상 출력을 정의하고, 불필요한 행동 반경을 금지함
2. **지식/예시 융합** — 기저 시스템 프롬프트를 작성하고, 이해를 도울 몇 쌍의 예시(Few-shot)와 외부 조회 데이터셋($Context$)을 동적으로 병합함
3. **포맷팅 제약** — 응답 파서($Parser$)가 오동작하지 않도록 `JSON` 구조 및 특정 스키마를 강제하는 장치와 누출 보안 필터를 주입함
4. **회귀 평가** — 작성된 프롬프트를 대상으로 가상의 평가용 테스트 케이스를 가동하여, 정답률과 출력 구조 준수 여부(JSON 깨짐 등)를 자동 측정함

## Ⅵ. 실무 적용 및 유의점

1. 운영 환경에서 사용자 입력에 악성 코드가 섞여 들어와 시스템 프롬프트 보안 가이드라인이 해제되는 '프롬프트 인젝션/탈옥'을 막기 위해, 시스템 지시 영역과 사용자 입력 영역을 명확히 구분하고 사용자 입력 데이터의 특수 문자 소독($Sanitization$) 및 LLM 기반의 중간 검증기($Guardrail$) 장치를 장착해야 함
2. 프롬프트를 작성할 때 무작정 좋은 미사여구와 너무 많은 퓨샷을 넣으면 프롬프트 토큰 크기가 비대해져 첫 토큰 지연($TTFT$)과 과금 비용이 급증하므로, 템플릿을 최소화하는 '프롬프트 압축' 기법을 적용하고 정확도 대비 토큰 가성비 지표로 튜닝해야 함

## Ⅶ. 결론

- 프롬프트 엔지니어링은 인공지능의 확률적 무질서를 통제된 비즈니스 가치로 변환하는 조향 장치이며, 설계자는 프롬프트 해킹 취약성과 토큰 서빙 비용을 체계적으로 억제하는 아키텍처 관점으로 접근해야 함
