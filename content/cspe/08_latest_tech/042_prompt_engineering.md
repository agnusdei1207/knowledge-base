# 📖 【암기용】 개념 완전 이해

> 목적: 프롬프트 엔지니어링을 처음 봐도 완벽히 이해하게 만든다.

## 한눈에
- **개요**: LLM의 입력 텍스트(프롬프트)를 체계적으로 설계하여 원하는 출력 품질을 확보하는 기법
- **왜 필요한가**: 같은 모델이라도 프롬프트에 따라 정확도 차이가 20~40%p 발생하므로, 모델 재학습 없이 성능을 끌어올리는 가장 저비용 방법임.
- **핵심 직관**: 모델에게 역할·문맥·출력 형식·제약조건을 명시하는 입력 설계 기술임.

## 깊이 이해
- **배경·문제의식**: LLM은 학습 데이터 패턴을 따르므로 모호한 지시에는 모호한 답을 낸다. Fine-tuning은 GPU·데이터 비용이 크고, 프롬프트 조정만으로 동일 효과를 내는 경우가 많음.
- **작동 원리**: 역할 지정(System Prompt) -> 맥락 제공(Few-shot 예시) -> 제약 조건 명시(출력 포맷·길이) -> 추론 유도(CoT) 순서로 프롬프트를 구성함.
- **비유**: 신입사원에게 업무를 시킬 때, 목표·배경·예시·출력 양식을 구체적으로 줄수록 결과가 정확해지는 것과 동일.
- **구체 예시**: "요약해줘" -> F1 0.52, "아래 기사를 3문장으로 요약하시오. 핵심 수치를 포함하시오." -> F1 0.78.
- **흔한 오해·주의점**: 긴 프롬프트가 항상 정답률을 높이지는 않음. 불필요한 지시는 토큰 비용을 늘리고 요구사항 충돌을 만들어 정확도를 낮출 수 있음.

## 연결 개념
- Chain-of-Thought — 단계적 추론 유도 기법
- Few-shot Learning — 예시 기반 학습
- System Prompt — 역할·제약 설정 계층

# 📝 【답안용】 시험 답안 템플릿

> 목적: 시험장에서 25분에 그대로 쓰는 답안 양식.

## 핵심 인사이트 (3줄 요약)

> 1. **본질**: 프롬프트 엔지니어링은 모델 재학습 없이 입력 설계만으로 출력 품질을 제어하는 기법임.
> 2. **가치**: Fine-tuning 대비 GPU 비용 0원, 반복 실험 사이클 수분 단위로 단축.
> 3. **판단 포인트**: 역할·맥락·예시·제약·추론유도 5요소를 구조화하고, 평가 메트릭(F1·BLEU)으로 검증해야 함.

## 출제 의도 및 답안 포인트

| 출제 의도 | 반드시 짚을 핵심 | 감점 회피 포인트 |
|:---|:---|:---|
| PE의 체계적 설계 프로세스와 Fine-tuning 대비 위치를 이해하는지 확인 | 5계층(역할·맥락·예시·제약·추론유도), F1 0.52→0.78 수치, A/B 테스트·메트릭 검증 | "프롬프트만 잘 쓰면 된다"는 서술 금지, 정확도 gap 5%p+ 시 Fine-tuning 병행 필요 명시 |

> 요약: 출제자는 PE를 단순 팁이 아닌 체계적 설계·검증 프로세스로 이해하고 있는지를 봄.

---

## Ⅰ. 개요 및 필요성

- 정의: LLM 입력을 체계적으로 설계하여 출력 품질을 제어하는 기법
- 배경: 동일 모델에서 프롬프트 차이만으로 정확도 20~40%p 변동이 발생함
- 필요성: Fine-tuning 없이 GPU 비용 0원으로 품질을 확보하는 최저비용 접근법

---

## Ⅱ. 구조 및 구성요소

```text
System Prompt(역할·제약) -> User Prompt(맥락·예시) -> Output Parser(포맷 검증)
```

| 구성요소 | 역할 | 특이사항 |
|:---|:---|:---|
| System Prompt | 역할·톤·출력 포맷 지정 | 모델 API별 위치 상이 |
| Few-shot 예시 | 입출력 패턴 시연 | 3~5개가 정확도-비용 최적 |
| 제약 조건 | 길이·언어·금지어 명시 | JSON Schema 강제 가능 |
| 추론 유도 (CoT) | 단계적 사고 과정 요구 | "Let's think step by step" |

> 요약: 프롬프트는 역할->맥락->예시->제약->추론유도 5계층으로 구성됨.

---

## Ⅲ. 동작원리 및 흐름도

```text
과제 식별 -> 역할 지정 -> 맥락·예시 삽입 -> 제약 명시
    -> LLM 추론 -> 출력 검증 -> 프롬프트 반복 개선
```

| 단계 | 처리 내용 | 검증 기준 |
|:---:|:---|:---|
| 1 | 과제 정의·평가 메트릭 선정 | F1·BLEU·정확도 목표치 |
| 2 | System Prompt + Few-shot 설계 | 예시 3~5개, 토큰 수 제한 |
| 3 | LLM 추론·출력 수집 | 응답 시간 p95, 토큰 소비량 |
| 4 | 평가·프롬프트 반복 개선 | A/B 테스트, 메트릭 비교 |

> 요약: 프롬프트 설계->추론->평가->개선의 반복 루프로 품질을 수렴시킴.

---

## Ⅳ. 특징

| 구분 | Fine-tuning | Prompt Engineering | 판단 포인트 |
|:---|:---|:---|:---|
| 비용 | GPU 수백~수천 달러 | API 호출 비용만 | 데이터 1K건 이하면 PE 우선 |
| 소요 시간 | 수시간~수일 | 수분~수시간 | 실험 사이클 속도 |
| 정확도 상한 | 도메인 특화 시 최고 | 모델 기본 능력 범위 내 | 정확도 gap 5%p 이상이면 FT |

> 요약: PE는 저비용·빠른 반복이 장점이나, 도메인 특화 정확도 한계 시 Fine-tuning과 병행함.

---

## Ⅴ. 심화 비교 및 적용 판단

| 비교 축 | Fine-tuning | Prompt Engineering | 선택 기준 |
|:---|:---|:---|:---|
| 구조 | 모델 가중치 업데이트 | 입력 텍스트 설계만 | 모델 수정 권한·데이터 유무 |
| 비용/성능 | GPU 수백~수천 달러, 정확도 상한 높음 | GPU 비용 0원, F1 0.52→0.78 | 데이터 1K건 이하면 PE, 이상이면 FT |
| 운영/위험 | 모델 배포·버전 관리 필요 | 프롬프트 버전 관리(Git)만 필요 | 운영 복잡도 vs 정확도 트레이드오프 |

> 요약: 데이터 1K건·정확도 gap 5%p를 기준으로 PE 단독과 FT 병행을 판단함.

| 리스크 | 원인 | 대응 방안 | 확인 지표 |
|:---|:---|:---|:---|
| 프롬프트 드리프트 | 모델 업데이트 시 기존 프롬프트 성능 변동 | 프롬프트 버전별 A/B 테스트·회귀 검증 파이프라인 | F1 변동 2%p 이내 |
| 출력 품질 편차 | Temperature·샘플링 설정에 따른 비결정적 출력 | Temperature 0.0~0.3 고정, 출력 스키마 검증 | JSON Schema 적합률 98%+ |
| 프롬프트 인젝션 | 사용자 입력이 시스템 프롬프트를 우회 | 입력 필터링·Guard Model(Llama Guard) 적용 | 인젝션 탐지율 95%+ |

> 요약: 프롬프트 드리프트·품질 편차·인젝션 3대 리스크를 회귀 테스트·스키마 검증·Guard로 통제함.

| 점검 항목 | 목표 기준 | 측정 방법 |
|:---|:---|:---|
| 성능/효율 | p95 응답 2초 이내, 토큰 소비 입력 대비 30% 이하 | API 로그·APM 모니터링 |
| 품질/정확도 | F1 0.75+, BLEU 0.60+ | 테스트셋 500건 자동 평가 |
| 운영/보안 | 프롬프트 버전 롤백 30초 이내, 인젝션 탐지율 95%+ | Git 태그·Guard Model 로그 |

> 요약: F1·응답 시간·인젝션 탐지율 3지표로 PE 파이프라인의 운영 안정성을 판단함.

---

## Ⅵ. 실무 적용 및 결론

**적용 방안 3개:**
1. 역할·포맷·금지어를 System Prompt에 고정하고, Few-shot 3~5개로 정확도 F1 0.75+ 확보
2. 프롬프트 버전 관리(Git)·A/B 테스트 파이프라인 구축, 배포 전 메트릭 회귀 검증
3. LangSmith·Phoenix 등 프롬프트 관찰 도구로 토큰 소비·응답 시간·실패율 모니터링

**결론 (2줄):**
- 기술사 판단: 데이터 1K건 이하·빠른 실험이면 PE, 도메인 정확도 gap 5%p+이면 Fine-tuning 병행
- 향후 방향: 자동 프롬프트 최적화(DSPy·OPRO)와 결합해 수동 설계 의존도를 낮추는 방향으로 발전
