## 미리 알고가기

- $TensorRT-LLM$: NVIDIA가 자사의 GPU(Hopper, Ada Lovelace 등) 하드웨어 아키텍처에 완벽 동기화되도록 설계한 텐서 컴파일 및 초고속 LLM 추론 라이브러리임
- 엔진 빌드 ($Engine$ $Build$): PyTorch 기반의 범용 가중치를 특정 NVIDIA GPU 칩셋의 하드웨어 특성에 부합하도록 컴파일 및 정렬하여 바이너리 런타임을 만드는 과정임
- 커널 융합 ($Kernel$ $Fusion$): 연산 오버헤드 단축을 위해 곱셈, 활성화 함수, 어텐션을 하나의 연산 커널로 묶어 동작 성능을 가속하는 컴파일러 기법임
- $NIM$ ($NVIDIA$ $Inference$ $Microservice$): TensorRT-LLM 엔진을 도커 컨테이너로 래핑하여 쿠버네티스 환경에 신속 배포하도록 규격화한 클라우드 네이티브 솔루션임

## Ⅰ. 개요

- **정의/개념**: TensorRT-LLM은 PyTorch 등으로 학습 완료된 언어 모델의 순방향 연산 그래프를 분석하여, 특정 NVIDIA GPU의 물리 칩셋 레지스터 및 메모리 대역 구조에 밀착 컴파일한 후, 초고속 연산 바이너리 형태(TRT Engine)로 가동하는 하드웨어 친화적 LLM 추론 프레임워크임
- **배경/필요성**: 범용 서빙 프레임워크는 이기종 하드웨어 이식성은 좋으나 실시간 대화 서비스에서 NVIDIA GPU의 최대 성능(FLOPs)을 극한으로 뽑아내지 못하는 아쉬움이 있어, 인프라 비용 절감과 초저지연 배포를 실현할 장치로 대두됨

## Ⅱ. 특징

- 기저 신경망의 추론 실행 경로 상에 존재하는 불필요한 레이어를 축소하고 커널 융합($Kernel$ $Fusion$)을 얹어, 런타임 상의 자원 대기 지연을 최대로 억제함
- 수평 병렬화인 텐서 병렬화($TP$) 및 가상 페이지 메모리(PagedAttention), 그리고 연속 배칭($Continuous$ $Batching$) 기술이 칩셋 레벨 커널 단에 구현되어 있음
- FP8 및 INT4/INT8 등 최신 양자화 포맷을 기본 해석 및 연산 지원하여, VRAM 용량 압박 해소와 연산 가속을 동시에 달성함

## Ⅲ. 종류 및 비교

| 판단 기준 | 기본 HuggingFace 추론 | vLLM (범용 오픈소스 가속) | TensorRT-LLM (엔비디아 특화 가속) |
|:---|:---|:---|:---|
| **최적화 기법** | 없음 (정적 실행) | 가상 메모리 및 실시간 배칭 제어 | 하드웨어 칩 컴파일 및 전용 최적 커널 빌드 |
| **추론 속도 지표** | 보통 | 매우 우수함 | 극대화 (동일 하드웨어 기준 최상의 성능) |
| **이식 유연성** | 매우 높음 (모든 가속기 구동) | 높음 (다양한 드라이버 호환) | 낮음 (NVIDIA 특정 세대 GPU 및 TRT 전용) |
| **사전 준비 과정** | 즉시 구동 가능 | 즉시 구동 가능 | 복잡함 (가중치를 엔진 파일로 사전 빌드 필요) |

> 요약: HuggingFace는 연구 개발 단계에, vLLM은 높은 확장성을 띈 상용화에, TensorRT-LLM은 고정 NVIDIA 인프라 기반의 엔터프라이즈 극대 가속에 최적임.

## Ⅳ. 구성요소 및 구조

| 구성요소 | 설명 |
|:---|:---|
| 가중치 파서 | HuggingFace 모델 가중치를 수집하여 TensorRT 호환 텐서 형태로 파싱하는 모듈임 |
| 컴파일러 빌더 | 특정 GPU 아키텍처(예: H100)의 스키마와 양자화 타깃을 읽고 TRT 가속 엔진 파일을 추출하는 컴파일기임 |
| C++ 런타임 스케줄러 | 빌드된 엔진 위에서 인플라이트 배칭($In-flight$ $Batching$) 및 $KV$ 캐싱 주소를 초고속 처리하는 C++ 런타임부임 |
| NIM 마이크로서비스 | 완성된 바이너리 추론 엔진을 Docker 기반 컨테이너 API 서비스로 패키징해 주는 마이크로서비스 계층임 |

```text
[ TensorRT-LLM 빌드 및 배포 파이프라인 ]
PyTorch Weights -> [Model Converter] -> [Engine Builder (Target: H100)] -> TRT Engine -> [C++ Runtime Serving]
- 타겟 GPU 사양에 딱 맞추어 최적 컴파일 과정을 거쳐 바이너리 엔진을 생성 및 실무 가동함
```

## Ⅴ. 원리 및 절차 흐름도

```text
+-------------+     +--------------+     +-------------+     +-------------+
| 모델 가중치 | --> | 타겟 GPU 전용| --> | TRT 엔진    | --> | 인플라이트  |
| 및 토큰 분석|     | 컴파일 및 빌드|     | 바이너리적재|     | 배칭 가동/QA|
+-------------+     +--------------+     +-------------+     +-------------+
```

1. **포맷 변환** — 기존 가중치 텐서를 TensorRT-LLM이 즉시 판독할 수 있는 전용 체크포인트 포맷으로 정돈함
2. **최적화 컴파일** — 타겟 장비(예: H100 8장) 옵션을 지정하고 빌더를 작동시켜, 커널 융합이 끝난 바이너리 아티팩트(TRT Engine)를 출력함
3. **메모리 적재** — 생성된 바이너리를 C++ 초고속 런타임 메모리에 바로 올린 뒤, PagedAttention 가상 메모리 공간을 세팅함
4. **고속 가속 추론** — 동시다발적으로 들어오는 세션에 대해, CPU-GPU 통신 오버헤드를 건너뛰는 온칩 가속 연산을 실행하고 응답을 출력함

## Ⅵ. 실무 적용 및 유의점

1. TensorRT-LLM 엔진 빌드는 컴파일 시간이 매우 길고 대상 GPU 하드웨어 사양(예: A100에서 빌드한 엔진은 H100에서 동작 불가)이 1픽셀만 어긋나도 실행이 불가능하므로, 반드시 개발-운영 서버 간의 GPU 칩셋 규격을 완벽 동기화하고 CI/CD 빌드 배포 자동화 파이프라인을 구축해 검증해야 함
2. 특정 그래픽 벤더(NVIDIA) 종속성으로 인해, 타사 가속기(AMD Instinct, Google TPU)나 멀티클라우드 하이브리드 아키텍처로의 즉시 전환이 불가능해지는 락인($Lock-in$) 우려가 있으므로, 호환 스택인 vLLM을 백업용 대체 수단으로 설정하는 재해 복구(DR) 시나리오를 구비해야 함

## Ⅶ. 결론

- TensorRT-LLM은 NVIDIA 장비의 물리 지능 효율을 극한의 수준으로 정화해 내는 최고의 인프라 성능 가속 기법이며, 설계자는 컴파일러의 하드웨어 종속적 특성을 정밀하게 통제하기 위해 일관된 GPU 환경 통제와 락인 위험 완화책을 동시에 병행 수립해야 함
