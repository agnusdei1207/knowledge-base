## 미리 알고가기

- TensorRT는 NVIDIA GPU용 추론 그래프 최적화와 엔진 생성을 담당하는 런타임 계열 기술임
- LLM 서빙 성능은 첫 토큰 지연 시간과 초당 토큰 처리량으로 주로 평가함
- 엔진 빌드 방식은 대상 GPU 아키텍처가 바뀌면 재빌드가 필요한 경우가 많음

## Ⅰ. 개요

- **정의/개념**: TensorRT-LLM은 LLM을 NVIDIA GPU 구조에 맞게 컴파일하고 전용 커널로 실행하여 지연 시간과 처리량을 극대화하는 고성능 추론 프레임워크임
- **배경/필요성**: 범용 서빙 엔진은 호환성은 높지만 고정된 NVIDIA GPU 클러스터에서 얻을 수 있는 극한 성능을 모두 끌어내지 못하므로, 대규모 상용 서비스에는 하드웨어 밀착형 최적화 계층이 필요함

## Ⅱ. 특징

- 모델 그래프를 사전 엔진으로 빌드해 런타임 오버헤드를 줄이고 GPU별 최적 경로를 확보함
- fused kernel, tensor parallelism, quantization을 결합해 높은 처리량과 낮은 응답 지연을 제공함
- Triton, NIM 같은 배포 계층과 쉽게 결합되어 엔터프라이즈 추론 파이프라인으로 연결됨
- 성능 이점이 큰 대신 GPU 세대와 소프트웨어 버전에 따른 종속성이 높아 운영 유연성은 낮아질 수 있음

## Ⅲ. 종류 및 비교

| 판단 기준 | 일반 Transformers 서빙 | vLLM | TensorRT-LLM |
|:---|:---|:---|:---|
| 최적화 방식 | 범용 런타임 중심임 | 메모리 관리와 배치 최적화 중심임 | GPU 아키텍처 맞춤 컴파일 중심임 |
| 처리량/지연 | 기본 수준임 | 높음 | 매우 높음 |
| 하드웨어 종속성 | 낮음 | 중간 | 높음 |
| 대표 활용 | 연구, 검증 | 범용 상용 서빙 | 고정 GPU 기반 대규모 상용 서비스 |

## Ⅳ. 구성요소 및 구조

| 구성요소 | 설명 |
|:---|:---|
| Model Converter | PyTorch나 HuggingFace 모델을 TensorRT-LLM 형식으로 변환해 엔진 생성의 입력으로 사용함 |
| Engine Builder | 대상 GPU, 정밀도, 병렬화 정책에 맞춰 최적화된 실행 엔진을 생성해 성능 상한을 결정함 |
| Runtime Scheduler | 요청 배치, KV cache, 병렬 실행을 조정해 실제 서빙 처리량과 지연 시간을 통제함 |
| Deployment Layer | Triton, NIM, Kubernetes 같은 배포 환경과 연결되어 운영 표준화와 확장을 담당함 |

## Ⅴ. 원리 및 절차 흐름도

```text
+-------------+     +-------------+     +-------------+     +-------------+
| 모델/옵션 입력 | --> | 엔진 빌드 수행 | --> | 요청 배치/실행 | --> | 토큰 응답 반환 |
+-------------+     +-------------+     +-------------+     +-------------+
```

1. **모델 및 옵션 입력**: 대상 모델과 GPU 종류, 정밀도, 병렬화 정책을 정의함
2. **엔진 빌드 수행**: 최적화된 연산 그래프와 전용 커널을 생성하여 실행 엔진을 만듦
3. **요청 배치 및 실행**: 런타임이 배치와 캐시를 관리하며 GPU에서 추론을 수행함
4. **토큰 응답 반환**: 스트리밍 응답과 모니터링 지표를 함께 수집해 운영 상태를 확인함

## Ⅵ. 문제점 및 해결 방안

1. 문제: GPU 세대나 드라이버 조건이 바뀌면 기존 엔진이 바로 재사용되지 않아 운영 유연성이 떨어질 수 있음
   - 해결방안: 표준 GPU 프로파일별 엔진 아티팩트를 관리하고 재빌드 시간과 benchmark 대비 tokens/sec 편차로 호환성을 검증함
2. 문제: 빌드 옵션과 병렬화 조합이 복잡하여 잘못 설정하면 기대한 성능 대신 OOM이나 성능 저하가 발생할 수 있음
   - 해결방안: 모델별 golden config와 자동 벤치마크 파이프라인을 운영하고 build success rate와 p95 latency로 설정 품질을 검증함
3. 문제: 특정 벤더 최적화에 의존하면 멀티클라우드나 이기종 가속기 전략과 충돌할 수 있음
   - 해결방안: 범용 엔진과 TensorRT-LLM을 역할별로 분리하고 workload별 cost per token과 failover 성공률로 배치 전략을 검증함

## Ⅶ. 적용 사례

- 초대형 고객센터 챗봇: 고정된 H100 클러스터에서 초저지연 응답을 제공함, 확인 지표는 p95 TTFT와 tokens/sec임
- 사내 프라이빗 RAG 서비스: NIM 기반으로 표준 배포를 구성함, 확인 지표는 deployment time과 GPU utilization임
- 대규모 생성형 API 사업자: 동일 GPU군에서 처리량을 극대화함, 확인 지표는 request concurrency와 cost per token임

## Ⅷ. 결론

TensorRT-LLM은 고정된 NVIDIA 인프라에서 LLM 추론 성능을 극대화해야 할 때 가장 강력한 선택지이지만, 그 대가로 빌드 복잡성과 하드웨어 종속성을 함께 관리해야 하는 기술임.
