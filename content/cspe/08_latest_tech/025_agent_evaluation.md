# 📖 【암기용】 개념 완전 이해

## 한눈에
- **개요**: 에이전트 평가는 AI 에이전트의 **업무 성공·도구 사용·안전성·비용·지연**을 종합 측정하는 **다차원 품질 평가** 체계다. 기존 LLM 평가가 "답변이 정확한가"를 보는 반면, 에이전트 평가는 "업무를 안전하게 끝냈는가"를 본다.
- **왜 필요한가**: 에이전트는 답변이 아니라 실제 도구 호출·시스템 변경·결제 등 **행동**을 수행하므로, 모델 정답률(accuracy)이 높아도 도구 오류율·정책 위반율이 높으면 운영 배포가 불가능하다. 단일 지표가 아닌 다차원 지표로 배포 여부를 결정해야 한다.
- **핵심 직관**: 운전면허 시험과 같다. 필기(답변 품질)만 통과해도 실기(경로 준수·안전 운전·주차)를 통과하지 못하면 면허를 발급하지 않는다.

## 핵심 용어 정리 (내부에 등장하는 것들)

| 용어/표기 | 의미 | 비유·예 |
|:---|:---|:---|
| Task Success Rate | 전체 테스트 태스크 중 성공적으로 완료한 비율 | 주문 100건 중 92건 정상 처리 = 92% |
| Policy Violation Rate | 정책(권한·안전·윤리) 위반이 발생한 태스크 비율 | 100건 중 2건 비인가 API 호출 = 2% |
| Tool Error Rate | 도구 호출 실패(5xx·타임아웃·잘못된 파라미터) 비율 | 도구 200회 호출 중 8회 실패 = 4% |
| Cost/Task | 태스크 1건당 총 비용(토큰+도구+외부 API) | 1건당 평균 $0.35 |
| p95 Latency | 전체 태스크의 95번째 백분위 지연 시간 | 95%의 태스크가 12초 이내 완료 |
| LLM-as-a-Judge | LLM을 평가자로 사용해 출력 품질을 자동 채점하는 기법 | AI가 AI를 평가 |
| 회귀 테스트(Regression Test) | 변경 후 기존 기능이 깨지지 않았는지 재확인하는 테스트 | 업그레이드 후 기존 시나리오 재실행 |
| 배포 게이트(Deploy Gate) | 지표가 기준을 충족해야만 배포를 허용하는 관문 | 품질 검사 합격 도장 |

## 깊이 이해
- **배경·문제의식**: 에이전트 워크플로우(024)가 "어떤 절차로 실행하는가"를 정의하고, 실패복구(026)가 "실패 시 어떻게 재개하는가"를 다룬다면, 평가는 "이 에이전트가 운영에 투입해도 되는 수준인가"를 판단한다. LLM 벤치마크(MMLU, HumanEval 등)는 지식·코딩 능력만 측정하고, 도구 선택·정책 준수·비용 효율·실패 대응은 측정하지 못한다.
- **작동 원리(어떻게+왜)**: ① 평가 시나리오를 정상(60%)·예외(25%)·보안/권한(15%) 비율로 구성한다. 예외 케이스가 빠지면 정상 경로에서만 성공하는 과적합 에이전트를 걸러내지 못한다. ② 에이전트를 테스트 환경에서 실행하고, Trace를 수집한다. ③ Task Success Rate, Tool Error Rate, Policy Violation Rate, Cost/Task, p95 Latency를 산출한다. ④ 자동 평가(규칙 기반·LLM-as-a-Judge)와 사람 평가(샘플링)를 결합해 최종 점수를 부여한다. ⑤ 배포 게이트에서 기준 미달 시 배포를 차단하고, 운영 중에는 1일 단위 샘플링 평가+주간 회귀 테스트를 수행한다.
- **비유**: 자동차 출하 전 품질 검사와 같다. 직진 속도(정답률)만 빠르면 안 되고, 코너링(예외 처리)·브레이크(안전 정지)·연비(비용)·내구성(지속 성능)을 모두 통과해야 출하한다.
- **구체 예시**: 고객 티켓 처리 에이전트를 100개 시나리오(정상 60건, 예외 25건, 보안 15건)로 평가한다. 결과: Task Success 92%, Tool Error 3%, Policy Violation 0.5%, Cost/Task $0.28, p95 Latency 8초. Policy Violation이 기준(1% 이내)을 충족하므로 배포 승인한다.
- **흔한 오해·주의점**: "모델을 업그레이드하면 에이전트도 자동으로 좋아진다"는 오해가 있다. 모델 변경 시 도구 호출 패턴이 바뀌어 Tool Error가 증가하거나, 프롬프트 해석이 달라져 Policy Violation이 발생할 수 있으므로, 모델 변경 시 반드시 전체 회귀 평가를 실시해야 한다.

## 연결 개념
- LLM Judge(231) — 에이전트 출력의 자동 품질 평가에 활용
- 에이전트 관측성(030) — 평가 데이터(Trace·메트릭) 수집의 기반
- 에이전트 워크플로우(024) — 평가 대상이 되는 표준 절차

# 📝 【답안용】 시험 답안 템플릿

## 핵심 인사이트 (3줄 요약)

> 1. **본질**: 에이전트 평가는 업무 성공·도구 사용·안전성·비용·지연을 다차원으로 측정하는 품질 평가 체계임.
> 2. **가치**: 배포 전 결함 차단, 배포 후 성능 저하·정책 위반 조기 탐지로 운영 신뢰성을 확보함.
> 3. **판단 포인트**: Task Success·Tool Error·Policy Violation·Cost/Task·p95 Latency 5대 지표로 배포 게이트를 설계해야 함.

## 출제 의도 및 답안 포인트

| 출제 의도 | 반드시 짚을 핵심 | 감점 회피 포인트 |
|:---|:---|:---|
| AI 에이전트 품질 평가 설계 | 5대 지표, 평가셋 비율(정상/예외/보안), 배포 게이트 | 정답률(accuracy)만 언급, 행동·안전·비용 지표 누락 |
| 배포 판단 기준 설계 역량 | 기준 미달 시 차단, 운영 중 샘플링·회귀 테스트 | 모델 점수가 높으면 배포 가능 단정 |

> 요약: 정답률이 아닌 5대 다차원 지표로 배포 게이트를 설계하는 역량을 증명해야 함.

---

## Ⅰ. 개요 및 필요성

- 개요: AI 에이전트의 업무 성공·도구 사용·안전성·비용·지연을 다차원 측정하는 품질 평가 체계임
- 배경: 에이전트는 답변이 아닌 행동(도구 호출·시스템 변경)을 수행하므로 LLM 정답률만으로 판단 불가함
- 필요성: 배포 전 결함 차단과 배포 후 성능 저하·정책 위반 조기 탐지에 다차원 평가가 필수임

---

## Ⅱ. 구조 및 구성요소

```text
평가 시나리오(정상/예외/보안) -> 에이전트 실행 -> Trace 수집
  -> 지표 산출(5대 지표) -> 자동·사람 평가 -> 배포 게이트 판정
```

| 구성요소 | 역할 | 특이사항 |
|:---|:---|:---|
| Test Set | 평가 시나리오 집합 | 정상 60%·예외 25%·보안 15% |
| Trace Collector | 실행 경로·도구·비용 기록 | Trace ID 기반 |
| Metric Engine | 5대 지표 자동 산출 | 배포 기준 자동 비교 |
| Judge | 자동(규칙/LLM)+사람(샘플링) 평가 | 기준표 기반 채점 |

> 요약: 테스트셋→실행→Trace→지표→판정 파이프라인으로 배포 여부를 결정함.

---

## Ⅲ. 동작원리 및 흐름도

```text
시나리오 준비 -> 에이전트 실행 -> Trace 수집 -> 지표 산출
  -> 배포 기준 비교 -> 합격/차단 -> 운영 중 샘플링·회귀 테스트
```

1. 시나리오 구성: 정상 60%·예외 25%·보안/권한 15% 비율로 테스트셋을 구성함
2. 실행·수집: 테스트 환경에서 에이전트를 실행하고 Trace(단계·도구·비용·시간)를 수집함
3. 지표 산출: Task Success Rate, Tool Error Rate, Policy Violation Rate, Cost/Task, p95 Latency를 자동 산출함
4. 판정·운영: 배포 게이트에서 기준 미달 시 차단하고, 운영 중 1일 샘플링+주간 회귀 테스트를 수행함

> 요약: 시나리오 구성→실행·Trace→지표 산출→배포 판정→운영 모니터링의 반복 사이클임.

---

## Ⅳ. 특징

- 다차원 평가: 정답률 단일 지표가 아닌 성공·안전·비용·지연의 5대 지표로 판단함
- 예외 포함: 정상 경로만이 아닌 예외·보안 시나리오를 포함해 과적합을 방지함
- 자동+사람: 규칙/LLM 자동 평가와 사람 샘플링을 결합해 평가 비용과 정확도를 균형 맞춤
- 배포 게이트: 기준 미달 시 자동 차단하여 불완전한 에이전트의 운영 투입을 방지함
- 지속 평가: 배포 후에도 샘플링·회귀 테스트로 모델·데이터 변화에 의한 성능 저하를 탐지함

---

## Ⅴ. 심화 비교 및 적용 판단

| 구분 | LLM 벤치마크 평가 | 에이전트 평가 | 선택 기준 |
|:---|:---|:---|:---|
| 평가 대상 | 답변 유창성·정확성 | 업무 완료·도구 실행·정책 준수 | 도구 호출·시스템 변경 여부 |
| 위험 차원 | 환각·편향 | 환각+권한 위반·오작동·과다 비용 | 실행 영향 범위 |
| 비용 지표 | 토큰 비용 중심 | 토큰+도구+외부 API+지연 통합 | 태스크당 총 비용(Cost/Task) |

> 요약: 도구 호출·시스템 변경이 있으면 LLM 벤치마크가 아닌 에이전트 다차원 평가를 적용함.

**리스크·대응:**
- 평가셋 편향: 정상 케이스만 구성 → 정상 60%·예외 25%·보안 15% 비율 유지 (지표: 케이스 유형별 커버리지)
- 운영 성능 저하: 모델·데이터 변화 → 1일 샘플링 평가+주간 회귀 테스트 자동화 (지표: 주간 성공률 추이)
- 평가셋 과적합: 에이전트가 고정 평가셋에 최적화 → 평가셋 주기적 갱신, 운영 로그 기반 신규 케이스 추가 (지표: 갱신 주기 월 1회)

**도입 후 점검 지표:**
- Task Success Rate: 배포 기준 90% 이상 — 평가셋 실행 결과 자동 산출
- Policy Violation Rate: 허용 기준 1% 이내 — Trace 기반 정책 위반 탐지

---

## Ⅵ. 실무 적용 및 결론

**적용 방안 3개:**
1. 정상 60%·예외 25%·보안 15% 비율로 평가 시나리오를 구성하고 월 1회 갱신함
2. Task Success·Tool Error·Policy Violation·Cost/Task·p95 Latency 5대 지표를 배포 게이트 기준으로 운영함
3. 배포 전 기준 미달 시 차단하고, 운영 중 1일 샘플링+주간 회귀 테스트로 지속 평가함

**결론:**
- 기술사 판단: 에이전트는 정답률만 높아도 Policy Violation Rate가 허용 기준을 넘으면 배포하지 않음
- 향후 방향: 에이전트 평가는 LLMOps(212)와 결합해 자동 회귀 평가·지속 모니터링 체계로 발전함
