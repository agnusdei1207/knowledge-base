## Ⅰ. 개요
- **정의**: 에이전트의 행동 궤적(Trajectory)과 최종 결과를 다차원으로 정량 채점하는 품질 보증(QA) 체계
- **배경/필요성**: 기존 LLM 평가(BLEU, ROUGE)는 텍스트 유사도만 측정하나, 에이전트는 "도구를 올바른 순서로 호출했는가", "목표를 실제로 달성했는가"라는 행동 품질이 핵심임. 프롬프트·모델 변경 시 성능 회귀(Regression)를 수치로 검증하지 않으면 프로덕션 배포 불가
- **비유**: 자동차 충돌 테스트 — 결과(생존)뿐 아니라 과정(충격 흡수 궤적)까지 다차원 계측

| 출제 의도 | 반드시 짚을 핵심 | 감점 회피 포인트 |
|:---|:---|:---|
| 기존 LLM 평가와 에이전트 평가의 차이 | Trajectory 평가, Task Success Rate, LLM-as-a-Judge | 텍스트 매칭(Exact Match)만 쓰면 안 됨. 행동 궤적·효율성·안전성 3축 채점 필수 |

> 요약: 에이전트의 궤적·결과·안전성을 정량 채점하여 프로덕션 배포 여부를 수치로 판단하는 QA 체계

## Ⅱ. 구성요소
```text
+---------------------------+
|  Test Dataset (Gold Set)  |
|  - 시나리오 + 모범 궤적   |
+-----------+---------------+
            |
            v
+-----------+---------------+
|  Sandbox Test Runner      |
|  - 모의 API 환경에서      |
|    에이전트 자동 실행      |
+-----------+---------------+
            |
            v
+-----------+---------------+
|  Multi-Axis Evaluator     |
|  +-----+  +-----+ +----+ |
|  |Task |  |Traj.| |Safe| |
|  |Score|  |Score| |Score| |
|  +-----+  +-----+ +----+ |
+-----------+---------------+
            |
            v
+-----------+---------------+
|  CI/CD Gate               |
|  - 점수 임계치 Pass/Fail  |
+---------------------------+
```

| 구성요소 | 설명 | 비유 |
|:---|:---|:---|
| Test Dataset | 에이전트가 풀어야 할 시나리오 + 모범 행동 궤적(Golden Trajectory) + 기대 결과를 100~1,000건 규모로 구축한 기준 데이터셋 | 모의고사 문제집 |
| Sandbox Test Runner | 모의 API 환경(Mock)에서 에이전트를 자동 실행하고 전체 행동 로그를 수집하는 테스트 하네스 | 시험 감독관 |
| Multi-Axis Evaluator | Task 달성도·궤적 효율성·안전성을 LLM-as-a-Judge + 결정론적 코드로 다차원 채점 | 채점 위원단 |
| CI/CD Gate | 종합 점수가 임계치를 통과해야 배포를 승인하는 자동화 관문 | 합격선 커트라인 |

> 요약: 테스트셋→샌드박스 실행→다축 채점→CI/CD 게이트의 4계층 평가 파이프라인

## Ⅲ. 절차
```text
+----------------+    +----------------+    +----------------+    +----------------+
| 1. 테스트셋    | -> | 2. 자동 실행   | -> | 3. 다축 채점   | -> | 4. 배포 판정   |
| (Gold Set)     |    | (Auto Run)     |    | (Multi-Eval)   |    | (CI/CD Gate)   |
+----------------+    +----------------+    +----------------+    +----------------+
```

1. **테스트셋 구축(Gold Set)** — 복합 미션(프롬프트), 모범 도구 호출 순서(Golden Trajectory), 기대 최종 결과를 DB에 100~1,000건 수록
2. **자동 실행(Auto Run)** — CI/CD 파이프라인에서 에이전트를 모의 API 환경(Sandbox)에 투입하여 전 시나리오를 자동 실행, 행동 로그(Trace) 전량 수집
3. **다축 채점(Multi-Axis Evaluation)** — Task Success(목표 달성 여부), Trajectory Efficiency(도구 호출 횟수·순서 적정성), Safety(PII 미노출·금지 API 미호출)를 LLM-as-a-Judge + 결정론적 코드로 채점
4. **배포 판정(CI/CD Gate)** — 종합 점수가 이전 버전 대비 동등 이상이면 Deploy 승인, 미만이면 프롬프트 롤백 또는 튜닝 루프(DSPy) 진입

> 요약: 테스트셋 구축→자동 실행→다축 채점→배포 판정의 4단계 품질 보증 프로세스

## Ⅳ. 문제점
- [심판 편향(Judge Bias)]: LLM-as-a-Judge 사용 시 심판 모델이 자사 모델 계열에 높은 점수를 부여하는 자기 편향 존재
- [테스트셋 고착화]: 고정된 시나리오만 반복하면 에이전트가 테스트셋에 과적합(Overfitting)되어 실 환경 대응력 저하
- [비결정적 채점]: 동일 로그에 대해 LLM Judge가 실행마다 다른 점수를 반환하여 평가 재현성 훼손

> 요약: 심판 편향, 테스트셋 과적합, 채점 비결정성이 에이전트 평가의 3대 신뢰성 위협

## Ⅴ. 개선방안
1. 단기: Ensemble Judge 도입 — 이종 모델(GPT, Claude, Llama) 3종 다수결로 단일 모델 편향 완화
2. 중기: 테스트셋 자동 증강 — LLM이 기존 시나리오를 변형하여 신규 엣지 케이스를 주기적으로 추가, 과적합 방지
3. 장기: 평가 결과를 DSPy 등 자동 프롬프트 최적화 프레임워크에 피드백하여 에이전트가 스스로 프롬프트를 개선하는 자율 진화 루프 구축

- [비결정적 채점]: [LLM 확률적 출력] → 결정론적 코드 채점(API 응답 코드 검증 등)을 LLM Judge와 5:5 하이브리드 (지표: 채점 재현율 ≥ 95%)

> 요약: 다수결 심판으로 편향 제거, 테스트셋 자동 증강으로 과적합 방지, 하이브리드 채점으로 재현성 확보

## Ⅵ. 전망
- 향후 발전 방향: 평가-최적화 통합 루프(DSPy) 보편화 — 채점 결과가 프롬프트 자동 수정으로 직결되는 자율 진화형 MLOps 체계
- 기술사적 판단: 에이전트 평가는 "감에 의존한 프롬프트 엔지니어링"을 "데이터 기반 과학"으로 격상시키는 전환점. 평가 체계 없는 에이전트 배포는 무검증 소프트웨어 출시와 동일
- 기술사 제언: LLM-as-a-Judge 단독 의존을 지양하고, 결정론적 코드 검증을 필수 병행할 것. 감사 로그(021 참조) 인프라와 평가 파이프라인을 연동하여 채점 근거의 추적성을 확보할 것
