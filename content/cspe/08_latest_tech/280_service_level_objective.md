# 📖 【암기용】 개념 완전 이해

> 목적: SLO를 막연한 품질 목표가 아니라 사용자가 체감하는 서비스 수준을 수치로 합의하고 운영 의사결정에 쓰는 기준으로 이해하게 만든다.

## 한눈에
- **개요**: SLI로 측정한 사용자 경험에 대해 특정 기간 동안 달성해야 하는 목표 값
- **왜 필요한가**: "장애가 없어야 한다"는 말은 배포, 비용, 대응 우선순위를 정하지 못한다.
- **핵심 직관**: 시험 합격 기준처럼 100점이 아니라 합격선과 평가 항목을 정해야 학습 전략을 세울 수 있다.

## 깊이 이해
- **배경·문제의식**: 시스템 내부 CPU나 서버 up/down 지표만으로는 사용자가 결제 실패, 검색 지연, 로그인 오류를 겪는지 알기 어렵다.
- **작동 원리**: 사용자 여정에서 SLI를 고르고 목표 기간과 목표 값을 정해 SLO를 만들며, 위반률은 error budget 소진으로 해석한다.
- **비유**: 택배 서비스가 "대부분 제때 배송"이 아니라 "수도권 익일 도착 98%"처럼 측정 가능한 약속을 정하는 것과 같다.
- **구체 예시**: checkout API의 30일 SLO를 "정상 요청의 99.9%가 500ms 이하로 완료"로 두면 위반 요청 0.1%가 오류 예산이 된다.
- **흔한 오해·주의점**: SLO는 SLA와 다르다. SLA는 고객 계약과 보상 조항을 포함할 수 있고, SLO는 내부 운영 목표로 더 세밀하게 둘 수 있다.

## 연결 개념
- SLI — SLO의 측정 대상 지표
- Error Budget — SLO 미달 허용량
- SRE — SLO를 운영 정책의 기준으로 사용

# 📝 【답안용】 시험 답안 템플릿

> 목적: 시험장에서 25분에 그대로 쓰는 답안 양식.
> 핵심: SLO는 품질 선언이 아니라 사용자 영향, 측정식, 기간, 제외 조건까지 명시하는 운영 계약이다.

## 핵심 인사이트 (3줄 요약)

> 1. **본질**: SLO는 SLI에 대해 일정 기간 달성해야 할 목표 수준을 정의한 내부 운영 기준임.
> 2. **가치**: 배포 허용, 장애 우선순위, error budget 정책을 사용자 영향 기준으로 조정함.
> 3. **판단 포인트**: 사용자 여정, 측정식, 기간, 목표값, 제외 조건, alert 기준을 함께 설계해야 함.

## 출제 의도 및 답안 포인트

| 출제 의도 | 반드시 짚을 핵심 | 감점 회피 포인트 |
|:---|:---|:---|
| SRE 핵심 개념 확인 | SLI, SLO, SLA, error budget 관계 | SLO와 SLA 혼동 |
| 목표 설정 역량 확인 | 사용자 경험 기반 지표와 기간 | CPU 사용률만 목표로 제시 |
| 운영 정책 연결 확인 | burn rate alert, release gate | 100% 목표를 무비판적으로 제시 |

> 요약: 이 문제는 서비스 목표를 사용자 체감 지표와 운영 정책으로 연결하는 능력을 평가한다.

---

## Ⅰ. 개요 및 필요성

- 개요: 서비스 수준 목표값
- 배경: 내부 시스템 지표만으로는 사용자가 경험하는 실패율과 지연을 판단하기 어려움.
- 필요성: SLO를 통해 장애 대응, 배포 통제, 신뢰성 투자를 같은 사용자 영향 지표로 판단해야 함.

---

## Ⅱ. 구조 및 구성요소

```text
User Journey -> SLI Definition -> SLO Target / Window
SLO -> Error Budget -> Burn Rate Alert / Release Policy
SLO Document -> Owner / Exclusion / Review Cycle
```

| 구성요소 | 역할 | 특이사항 |
|:---|:---|:---|
| User Journey | 측정 대상 서비스 흐름 | 로그인, 결제, 검색 등 |
| SLI | 측정 가능한 지표 | latency, availability, correctness |
| Target Window | 목표값과 평가 기간 | 99.9%, 30일 등 |
| Policy | 위반 시 조치 기준 | alert, 배포 중단 |

> 요약: SLO는 사용자 여정에서 SLI를 선택하고 목표값·기간·정책을 문서화한 운영 기준이다.

---

## Ⅲ. 동작원리 및 흐름도

```text
사용자 여정 선정 -> SLI 측정식 정의 -> 목표값 / 기간 설정
-> error budget 산정 -> burn rate 감시
-> alert / release gate 실행 -> SLO review
```

| 단계 | 처리 내용 | 검증 기준 |
|:---:|:---|:---|
| 1 | 핵심 사용자 기능과 실패 조건 정의 | business criticality |
| 2 | valid request, success event, latency threshold 정의 | 측정 재현성 |
| 3 | SLO 목표값과 rolling window 설정 | budget 계산 가능 |
| 4 | 위반률과 burn rate로 alert·배포 정책 실행 | false alert ratio |

> 요약: SLO는 지표 선택부터 정책 실행까지 측정식이 명확해야 운영 판단에 사용할 수 있다.

---

## Ⅳ. 특징

| 구분 | SLI | SLO | SLA |
|:---|:---|:---|:---|
| 의미 | 측정 지표 | 내부 목표 | 외부 계약 |
| 예시 | 성공 요청 비율 | 30일 99.9% | 미달 시 보상 조항 |
| 주체 | 운영·개발 | 제품·SRE 합의 | 고객·법무·영업 |
| 판단 기준 | 측정 가능성 | 사용자 영향과 비용 균형 | 계약 리스크 |

> 요약: SLI는 측정값, SLO는 내부 목표, SLA는 대외 약속이므로 범위와 책임을 구분해야 한다.

---

## Ⅴ. 심화 비교 및 적용 판단

| 비교 축 | 내부 지표 중심 | SLO 중심 | 선택 기준 |
|:---|:---|:---|:---|
| 목표 | 서버 정상 여부 | 사용자 경험 달성 | 고객 영향 측정 |
| 알림 | CPU, memory 임계치 | burn rate alert | 대응 필요성 |
| 배포 | 일정 중심 | budget 잔여율 반영 | 변경 위험 |

> 요약: SLO 중심 운영은 시스템 상태가 아니라 사용자가 체감하는 성공률과 지연을 기준으로 판단한다.

| 리스크 | 원인 | 대응 방안 | 확인 지표 |
|:---|:---|:---|:---|
| 목표 과도 | 100%에 가까운 목표 | 비용·사용자 기대 기반 조정 | budget exhaustion frequency |
| 측정 왜곡 | synthetic만 측정 | real user와 server-side 지표 병행 | SLI mismatch count |
| 제외 조건 남용 | maintenance 제외 과다 | exclusion 승인 정책 | excluded minutes |

> 요약: SLO 리스크는 목표값, 측정 방식, 제외 조건에서 발생하며 정기 review로 보정해야 한다.

| 점검 항목 | 목표 기준 | 측정 방법 |
|:---|:---|:---|
| 명확성 | 측정식·기간·소유자 문서화 | SLO document review |
| 운영성 | alert와 release policy 연결 | incident record |
| 적합성 | 사용자 불만과 SLO 위반 상관 | support ticket 분석 |

> 요약: SLO 품질은 문서 명확성, 정책 연결성, 실제 사용자 영향과의 상관으로 검증한다.

---

## Ⅵ. 실무 적용 및 결론

**적용 방안 3개:**
1. 핵심 사용자 여정별로 valid request, successful response, latency threshold를 명시해 SLI 측정식을 정의함.
2. 30일 rolling window와 목표값을 설정하고 SLO 미달 허용량을 error budget으로 계산함.
3. burn rate alert와 release gate를 연결해 예산 소진 시 신규 배포보다 장애 원인 제거를 우선함.

**결론 (2줄):**
- 기술사 판단: SLO는 기술 지표가 아니라 제품·개발·운영이 합의한 사용자 영향 기준으로 설정해야 함.
- 향후 방향: SLO는 platform engineering과 progressive delivery에 연결되어 자동 rollback과 배포 승인 정책의 기준이 됨.
