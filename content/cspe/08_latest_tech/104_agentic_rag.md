# 📖 【암기용】 개념 완전 이해

> 목적: Agentic RAG를 처음 봐도 완벽히 이해하게 만든다.

## 한눈에
- **정의**: LLM 에이전트가 계획을 세우고 여러 검색·도구를 호출하며 중간 결과를 반영해 답변하는 RAG 구조
- **왜 필요한가**: 단일 검색으로 답하기 어려운 복합 질문은 질의 분해, 추가 검색, 계산, 검증이 반복되어야 함.
- **핵심 직관**: 한 번 검색하고 끝내는 것이 아니라, 조사관처럼 "다음에 무엇을 더 찾아야 하는가"를 판단하며 근거를 모음.

## 깊이 이해
- **배경·문제의식**: 기업 질의는 "A 규정과 B 계약을 비교해 리스크를 계산"처럼 여러 문서·도구·단계를 요구한다. Naive RAG는 한 번의 Top-K 검색으로 이런 질문을 처리하기 어렵다.
- **작동 원리**: Planner가 하위 질문을 생성하고, Router가 벡터DB·SQL·웹·계산기 도구를 선택하며, Agent가 관찰 결과에 따라 다음 행동을 반복한 뒤 Synthesizer가 최종 답변을 생성함.
- **비유**: 변호사가 판례 검색, 계약서 검토, 법령 확인, 계산표 작성 순서로 조사 계획을 세우고 결론을 쓰는 과정임.
- **구체 예시**: 장애 RCA에서 로그 검색, 메트릭 조회, 배포 이력 확인을 3회 도구 호출로 수행해 원인 후보를 7개→2개로 축소.
- **흔한 오해·주의점**: 자율성이 높아질수록 도구 오용과 루프 위험이 커진다. 최대 반복 횟수, 허용 도구, 비용 한도를 정책으로 제한해야 함.

## 연결 개념
- AI Agent — 계획·도구 호출·관찰 기반 실행 주체
- Tool Calling — 외부 API·DB·검색기를 호출하는 LLM 인터페이스
- Multi-hop RAG — 여러 근거를 연결하는 다단계 검색 문제

# 📝 【답안용】 시험 답안 템플릿

> 목적: 시험장에서 25분에 그대로 쓰는 답안 양식.

## 핵심 인사이트 (3줄 요약)

> 1. **본질**: Agentic RAG는 에이전트가 계획·검색·도구 호출·검증을 반복하는 다단계 RAG임.
> 2. **가치**: 복합 질의에서 근거 탐색 범위를 동적으로 조정해 단일 Top-K 검색의 한계를 보완함.
> 3. **판단 포인트**: 반복 횟수·도구 권한·비용 한도·감사로그를 통제하지 않으면 운영 리스크가 증가함.

## Ⅰ. 개요 및 필요성

Agentic RAG는 에이전트 기반 검색증강생성 구조임. 복합 질의는 단일 검색 결과만으로 답하기 어려워 계획 수립, 도구 선택, 추가 검색, 검증이 필요하다. LLM 에이전트가 관찰 결과에 따라 다음 검색 행동을 결정한다.

## Ⅱ. 구조 및 구성요소

```text
User Query → Planner → Tool Router → Retriever/API/DB
                  ▲          │              │
                  └── Memory/Observation ◀──┘ → Synthesizer
```

| 구성요소 | 역할 | 특이사항 |
|:---|:---|:---|
| Planner | 질의 분해·실행 계획 생성 | ReAct, Plan-and-Execute 패턴 |
| Tool Router | 검색기·SQL·API·계산기 선택 | 허용 도구 ACL 적용 |
| Memory | 중간 관찰·근거 저장 | 세션 메모리 TTL 30~60분 |
| Synthesizer | 근거 통합·최종 답변 생성 | 출처·도구 호출 이력 첨부 |

> 요약: Agentic RAG는 Planner와 Tool Router가 반복적으로 도구를 호출하고, Memory의 관찰 결과를 모아 최종 답변을 생성함.

## Ⅲ. 동작원리 및 흐름도

```text
복합 질의 → 하위 질문 분해 → 도구 선택
  → 검색/API 호출 → 관찰 저장 → 추가 필요성 판단
  ├─ 필요 → 다음 도구 호출 반복
  └─ 충분 → 근거 통합 답변 생성
```

| 단계 | 처리 내용 | 검증 기준 |
|:---:|:---|:---|
| 1 | Planner가 하위 질문 2~5개 생성 | 분해 누락률 < 10% |
| 2 | Router가 도구 선택 및 파라미터 구성 | 허용 도구 위반 0건 |
| 3 | 검색·DB·API 결과 관찰 및 반복 판단 | 최대 반복 5회, 호출 비용 $0.05/질의 이하 |
| 4 | 근거 통합 후 답변·출처·호출 로그 출력 | 출처 표시율 100%, 감사로그 90일 보관 |

> 요약: 질의를 분해하고 도구 호출 결과를 관찰하며 필요한 만큼 검색을 반복한 뒤, 근거와 호출 로그를 포함해 답변함.

## Ⅳ. 특징

| 구분 | Advanced RAG | Agentic RAG | 판단 포인트 |
|:---|:---|:---|:---|
| 실행 방식 | 고정 파이프라인 | 계획 기반 반복 실행 | 질의 복잡도 편차가 크면 Agentic |
| 도구 범위 | 벡터DB·리랭커 중심 | 검색·SQL·API·계산기 | 도구 ACL·감사로그 필수 |
| 지연 | 1~2초 목표 | 반복 호출로 3~10초 | 실시간 채팅은 반복 3회 이하 |
| 리스크 | 검색 품질 오류 | 도구 오용·무한 루프 | max_step, budget, timeout 설정 |

> 요약: Agentic RAG는 복합 추론 범위가 넓지만, 지연·비용·도구 권한을 정책으로 제한해야 운영 가능함.

## Ⅴ. 실무 적용 및 결론

**적용 방안 3개:**
1. 장애 분석: 로그 검색, Prometheus 쿼리, 배포 이력 API를 도구로 등록하고 max_step=5, timeout=10초 설정
2. 권한 통제: Tool Router에 RBAC 적용, PII 조회 도구는 승인된 역할만 호출, 감사로그 90일 저장
3. 비용 관리: 질의당 호출 예산 $0.05, 반복 5회 초과 시 근거 부족 응답, 캐시 적중 질의는 도구 호출 생략

**결론 (2줄):**
- 기술사 판단: 다중 문서·도구·계산이 필요한 업무는 Agentic RAG, 단일 문서 QA는 Advanced RAG 적용
- 향후 방향: MCP 기반 표준 도구 연결과 정책 기반 Agent Guardrail로 기업 적용 범위 확대
