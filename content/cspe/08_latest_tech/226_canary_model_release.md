# 📖 【암기용】 개념 완전 이해

> 목적: 카나리 모델 배포를 신규 모델을 전체 사용자에게 한 번에 공개하지 않고 제한된 트래픽으로 검증하는 운영 전략으로 이해하게 만든다.

## 한눈에
- **개요**: 신규 모델을 1~10% 트래픽에 먼저 적용해 품질·지연·오류를 확인한 뒤 점진 확대하는 배포 방식
- **왜 필요한가**: ML 모델은 오프라인 AUC가 높아도 실제 사용자 분포, feature skew, latency 조건에서 실패할 수 있다.
- **핵심 직관**: 새 메뉴를 전 매장에 내기 전에 일부 매장에서 판매량과 불만 건수를 측정하는 방식이다.

## 깊이 이해
- **배경·문제의식**: 모델 v2를 전체 트래픽에 즉시 적용하면 예측 오류, 지연 초과, 수익 지표 하락이 전 사용자에게 전파된다.
- **작동 원리**: 라우터가 사용자 또는 요청 일부를 v2로 보내고, v1과 v2의 error rate, p95 latency, CTR, conversion을 비교한다.
- **비유**: 항공사가 새 탑승 절차를 특정 노선에서 먼저 운영해 지연과 민원 지표를 본 뒤 전 노선으로 확대하는 것과 같다.
- **구체 예시**: 추천 모델 v2를 트래픽 5%에 배포하고 1시간 동안 error rate 0.1% 이하, CTR 하락 2% 이내, p95 latency 150ms 이하일 때 25%로 확대한다.
- **흔한 오해·주의점**: 카나리 배포는 A/B 테스트와 다르다. 카나리는 운영 위험 통제가 목적이고, A/B 테스트는 통계적 효과 검증이 목적이다.

## 연결 개념
- Model Serving — 카나리 라우팅과 롤백이 실행되는 추론 제공 계층
- Online Evaluation — 실제 트래픽 기반 품질 검증
- Shadow Deployment — 사용자 영향 없이 신규 모델을 병렬 실행하는 방식

# 📝 【답안용】 시험 답안 템플릿

> 목적: 시험장에서 25분에 그대로 쓰는 답안 양식.
> 핵심: 카나리 모델 배포는 신규 모델 위험을 트래픽 비율, 품질 지표, 자동 롤백 기준으로 통제한다.

## 핵심 인사이트 (3줄 요약)

> 1. **본질**: Canary Model Release는 신규 모델을 제한 트래픽에 먼저 적용해 운영 지표를 확인한 뒤 점진 확대하는 배포 전략임.
> 2. **가치**: error rate, p95 latency, CTR, rollback time을 기준으로 전체 장애 전파를 차단함.
> 3. **판단 포인트**: 통계 검증 목적이면 A/B 테스트, 장애 반경 축소 목적이면 카나리 배포를 선택함.

## 출제 의도 및 답안 포인트

| 출제 의도 | 반드시 짚을 핵심 | 감점 회피 포인트 |
|:---|:---|:---|
| ML 배포 리스크 통제 이해 확인 | traffic split, metric gate, rollback | 모델 정확도만 쓰고 운영 지표 누락 |
| 운영 배포 전략 비교 확인 | canary, blue-green, shadow, A/B 차이 | 카나리와 A/B 테스트 혼동 |
| 자동화 판단 확인 | 배포 단계, 임계치, rollback trigger | 수동 승인만으로 배포 통제 서술 |

> 요약: 이 문제는 신규 모델을 제한된 영향 범위에서 검증하고 자동 롤백하는 운영 판단을 요구한다.

---

## Ⅰ. 개요 및 필요성

- 개요: 제한 트래픽 기반 점진 모델 배포
- 배경: 신규 모델은 오프라인 지표가 충족되어도 실제 사용자 분포와 서비스 지연 조건에서 실패할 수 있음.
- 필요성: 트래픽 5% 단위 확대, error rate 0.1% 이하, rollback 5분 이내 기준으로 장애 반경을 제한해야 함.

---

## Ⅱ. 구조 및 구성요소

```text
Client -> Traffic Router -> Model v1 / Model v2 Canary -> Metric Collector -> Policy Gate -> Rollback / Ramp-up
```

| 구성요소 | 역할 | 특이사항 |
|:---|:---|:---|
| Traffic Router | 사용자·요청 비율을 v1/v2로 분기 | sticky routing, feature flag |
| Canary Model | 신규 모델을 제한 트래픽에 적용 | 1%, 5%, 25%, 50% 단계 |
| Metric Collector | 지연·오류·품질·사업 지표 수집 | model_id별 로그 분리 |
| Policy Gate | 확대·중지·롤백 판단 | 임계치 기반 자동화 |

> 요약: 카나리 배포는 라우팅, 지표 수집, 정책 게이트, 롤백 경로가 함께 있어야 장애 반경을 제한한다.

---

## Ⅲ. 동작원리 및 흐름도

```text
모델 v2 승인 -> 1~5% 트래픽 분기 -> 지표 비교 -> 임계치 판정 -> 확대 또는 롤백
```

| 단계 | 처리 내용 | 검증 기준 |
|:---:|:---|:---|
| 1 | registry 승인 모델을 canary slot에 배포 | 승인 이력 존재 |
| 2 | 트래픽 1~5%를 신규 모델로 분기 | 분기 비율 오차 1% 이내 |
| 3 | v1/v2 지표를 model_id별 비교 | p95 latency, error rate, CTR |
| 4 | 정책 게이트가 확대 또는 롤백 수행 | rollback 5분 이내 |

> 요약: 카나리 배포는 작은 트래픽에서 지표를 확인하고 임계치에 따라 확대 또는 롤백하는 폐루프로 동작한다.

---

## Ⅳ. 특징

| 구분 | 전체 배포 | 카나리 모델 배포 | 수치 기준 |
|:---|:---|:---|:---|
| 영향 범위 | 전체 사용자 | 1~10% 초기 노출 | 장애 반경 10% 이하 |
| 검증 방식 | 배포 후 장애 확인 | 배포 중 지표 게이트 | p95, error, CTR |
| 롤백 | 전체 버전 되돌림 | canary slot 차단 | rollback 5분 이내 |

> 요약: 카나리 배포는 전체 배포 대비 초기 영향 범위를 줄이고 지표 기반 확대 결정을 가능하게 한다.

---

## Ⅴ. 심화 비교 및 적용 판단

| 비교 축 | 기존/대안 | 본 키워드 | 선택 기준 |
|:---|:---|:---|:---|
| 목적 | A/B 테스트는 효과 검증 | 카나리는 운영 위험 통제 | 장애 반경 축소 우선 시 카나리 |
| 구조 | blue-green은 환경 전환 | 트래픽 비율 단계 확대 | gradual ramp 필요 시 카나리 |
| 운영/위험 | 전체 배포는 rollback 부담 | metric gate로 자동 차단 | 롤백 자동화 가능 여부 |

> 요약: 카나리는 효과 검증보다 운영 위험 축소에 초점을 둔 점진 배포 전략이다.

| 리스크 | 원인 | 대응 방안 | 확인 지표 |
|:---|:---|:---|:---|
| 표본 편향 | 특정 사용자군만 canary 포함 | random bucket과 segment별 지표 분리 | segment별 CTR 차이 |
| 늦은 장애 탐지 | delayed label 업무 | proxy metric과 delayed label 병행 | label 도착 지연 |
| 롤백 실패 | 모델·feature schema 동시 변경 | backward compatible schema 유지 | rollback 성공률 |

> 요약: 카나리 리스크는 표본 편향, 지연 라벨, 롤백 불일치이며 bucket·proxy metric·schema 호환성으로 통제한다.

| 점검 항목 | 목표 기준 | 측정 방법 |
|:---|:---|:---|
| 서비스 품질 | p95 latency 150ms 이하 | APM, inference log |
| 오류율 | error rate 0.1% 이하 | model_id별 로그 |
| 사업 지표 | CTR 하락 2% 이내 | 실험 대시보드 |

> 요약: 카나리 성공 여부는 지연·오류·사업 지표가 모두 기준 안에 있을 때 판단한다.

---

## Ⅵ. 실무 적용 및 결론

**적용 방안 3개:**
1. 배포 단계는 1% -> 5% -> 25% -> 50% -> 100%로 설정하고 각 단계마다 최소 30분 관측 시간을 둠.
2. error rate 0.1% 초과, p95 latency 150ms 초과, CTR 2% 하락 중 하나가 발생하면 자동 rollback을 실행함.
3. model_id, feature_version, route_bucket을 로그에 남겨 canary 장애의 원인을 1시간 이내 추적함.

**결론 (2줄):**
- 기술사 판단: 신규 모델의 사용자 영향이 크면 카나리 배포를 기본값으로 선택하고, 통계적 효과 검증은 별도 A/B 테스트로 분리함.
- 향후 방향: 카나리 배포는 continuous evaluation, feature flag, automated rollback과 결합된 LLMOps 배포 표준으로 확장됨.
