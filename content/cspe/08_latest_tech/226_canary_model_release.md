# 📖 【암기용】 개념 완전 이해

## 한눈에
- **정의**: 새로 학습시킨 머신러닝 모델을 상용 서버에 배포할 때, 전체 사용자에게 100% 한 번에 오픈하지 않고 **극소수(예: 5%)의 실 사용자 트래픽만 떼어내서 신규 모델에 흘려보내며 안정성을 간 보는 '소프트 랜딩' 배포 전략**.
- **필요성**: 개발 환경에서 아무리 테스트를 거쳐도, 실제 운영 환경의 '야생 데이터'를 만나면 모델이 뻗거나 엉뚱한 예측을 할 수 있음. 한 번에 100% 배포(빅뱅 배포)했다가 장애가 나면 롤백하는 동안 고객 수만 명이 떨어져 나감. 대형 사고(Blast Radius)를 미연에 방지하기 위해 필수적임.
- **핵심 직관**: 광산의 '카나리아(Canary) 새'. 옛날 광부들은 유독 가스가 있는지 확인하기 위해, 사람보다 가스에 민감한 카나리아 새를 새장에 넣어 먼저 동굴에 밀어 넣었음. 카나리아가 죽으면 즉시 대피함. 마찬가지로 5%의 트래픽(새)을 새 모델(동굴)에 보내서 에러율이 치솟으면, 배포를 즉각 중단하고 구버전 모델로 롤백함.

## 깊이 이해
- **배경**: AI 모델은 소프트웨어 코드와 달리, 데이터의 분포가 조금만 틀어져도 성능이 나락으로 감. "데이터가 깨끗한 연구실(Offline)"에서는 천재였던 모델이 "더티한 현실(Online)"에서는 바보가 되는 일이 다반사. 따라서 반드시 '실제 트래픽'으로 검증해야 하는데, 그 위험을 최소화하기 위해 고안됨.
- **작동 원리 (점진적 롤아웃)**:
  1. 기존 모델(v1)이 100% 트래픽을 처리 중. 신규 모델(v2)을 컨테이너로 띄움.
  2. API 게이트웨이/로드밸런서 설정을 통해 전체 요청 중 무작위 5%만 v2로 보냄.
  3. 실시간 모니터링: v1과 v2의 에러율, 응답 지연(Latency), 고객 클릭률(CTR)을 10분간 비교함.
  4. v2가 멀쩡하다면 비율을 20% $\rightarrow$ 50% $\rightarrow$ 100%로 서서히 늘려가며 v1을 최종 소멸시킴.
- **구체 예시**: 넷플릭스 영화 추천 엔진. 새로운 '개인화 추천 딥러닝 모델'을 만들었음. 아시아 지역 고객 중 무작위 1%에게만 이 새 모델이 추천하는 목록을 띄워줌. 실시간으로 감시해 보니 이 1% 고객의 '시청 이탈률'이 기존보다 심각하게 높게 나옴. 즉시 1% 고객을 다시 구버전 엔진으로 돌리고, 새 모델은 폐기 후 재학습시킴. 피해 최소화 성공.
- **흔한 오해/주의점**: "Canary 배포는 A/B 테스트랑 똑같은 거 아님?" $\rightarrow$ 헷갈리기 쉽지만 다름. A/B 테스트는 "둘 중에 어느 모델의 성능/매출이 더 좋은가?"를 찾기 위한 '비즈니스 실험'이고, 카나리 배포는 "이 모델을 배포해도 서버가 안 터지고 안전한가?"를 확인하는 '안전/인프라 전략'임.

## 연결 개념
- **Shadow Deployment (섀도 배포)**: 카나리 배포의 전 단계. 카나리는 5%의 고객이라도 '실제 영향'을 받지만, 섀도 배포는 사용자는 모르게 뒤에서 결과만 대조해 보는 0% 리스크 배포 방식.
- **Blue-Green Deployment (블루-그린 배포)**: 카나리처럼 5%, 10% 찔끔찔끔 넘기는 게 아니라, 신버전(Green)을 완벽히 띄워놓고 트래픽 라우팅을 0%에서 100%로 한 방에 스위칭하는 배포 방식. 롤백이 빠름.
- **Circuit Breaker (서킷 브레이커)**: 카나리 배포 중 에러가 임계치를 넘으면(카나리아가 죽으면) 사람이 개입하지 않아도 시스템이 자동으로 배포를 중단하고 롤백하는 안전장치.

# 📝 【답안용】 시험 답안 템플릿
## 핵심 인사이트 (3줄 요약)
- **본질**: 운영 환경(Production)에서 신규 머신러닝 모델을 배포할 때, 전체 트래픽 중 극히 소수(예: 1~5%)의 트래픽만 라우팅하여 안정성과 성능을 검증한 후 점진적으로 가중치를 높이는 리스크 최소화 배포 전략.
- **가치**: 학습 환경과 운영 데이터 간의 편차(Training-Serving Skew)로 인한 예측 불가능한 런타임 오류(OOM, Latency 증가)가 전체 서비스에 미치는 폭발 반경(Blast Radius)을 물리적으로 격리 통제함.
- **판단 포인트**: 카나리 배포의 핵심 성공 요인은 로드밸런서의 정교한 트래픽 분할(Routing) 능력과 더불어, 구 모델(Baseline)과 신규 모델(Canary) 간의 성능 지표를 실시간으로 비교하여 이상 시 자동 롤백하는 관측성(Observability) 체계의 구축임.

## Ⅰ. 개요 및 필요성
- **정의**: 새로운 버전의 모델(v2)을 별도의 인프라에 프로비저닝한 뒤, 로드밸런서 규칙을 조작하여 전체 사용자 트래픽의 일부만 단계적(Progressive)으로 인입시켜 시스템의 안전성을 검증하는 배포 파이프라인.
- **배경**: AI 모델은 소프트웨어 로직(Logic) 결함보다 데이터 분포 변화에 기인한 조용한 실패(Silent Failure)가 잦아, 기존 CI/CD의 단위 테스트(Unit Test)만으로는 운영 환경에서의 안전을 담보할 수 없음.
- **필요성**: 장애 발생 시 전체 비즈니스 KPI 폭락 방지, 실제 유저 피드백 기반의 무중단 검증, 신속한 롤백(Rollback)을 통한 고가용성(99.99%) 유지.

## Ⅱ. Canary Release 아키텍처 및 핵심 구성요소
트래픽 스플리팅과 관측의 결합.
| 컴포넌트 | 메커니즘 (Mechanism) 및 상세 역할 | 주요 기술 스택 |
|:---:|:---|:---|
| **Traffic Router**<br>(라우터/게이트웨이) | API 요청을 받아 헤더(Header) 정보나 무작위 확률 분산 알고리즘을 통해 95:5 비율로 트래픽을 두 클러스터로 분리. | Nginx, Istio, AWS ALB |
| **Stable Model**<br>(기존 모델) | 현재 프로덕션에서 안정성이 검증되어 95%의 주력 트래픽을 처리하는 대조군(Control Group). | KServe, Triton Server |
| **Canary Model**<br>(신규 모델) | 검증 대상 모델로 5%의 실험군(Treatment Group) 트래픽을 수용하여 실제 추론을 수행. | Kubernetes Pod |
| **Comparison Engine**<br>(비교 엔진) | 두 모델의 시스템 지표(지연/에러율)와 비즈니스 지표를 시계열로 수집해 임계치 초과 여부 감시. | Prometheus, Grafana |

## Ⅲ. 단계적 배포 (Progressive Rollout) 흐름도
5%에서 100%로 가는 험난한 여정.
1. **배포 및 트래픽 분할 (Initial Routing)**: 신규 모델 Pod 활성화 후 API Gateway에서 가중치를 `Stable 95% : Canary 5%`로 설정.
2. **실시간 모니터링 (Observability)**: 30분간 Canary 모델의 HTTP 5xx 에러율, P99 Latency, 추론 응답의 널(Null) 반환 비율 모니터링.
3. **오류 시 자동 롤백 (Circuit Break)**: 에러율이 1%를 초과할 경우 즉각 Canary 배포를 취소하고 트래픽을 Stable 100%로 원복 (MTTR 최소화).
4. **단계적 확대 (Scaling Up)**: 지표가 안정적이면 트래픽 비율을 20% $\rightarrow$ 50% $\rightarrow$ 100%로 점진 상향. (Kubernetes HPA와 연동해 Canary 파드 증설).
5. **구 버전 일몰 (Decommissioning)**: 100% 전환 완료 시 기존 Stable 모델 자원 회수.

## Ⅳ. Canary 배포 vs 기타 배포 전략 비교
| 구분 | Canary Deployment | Blue-Green Deployment | Shadow Deployment |
|:---:|:---|:---|:---|
| **트래픽 전환 방식** | **점진적 가중치 기반 분할** (5% $\rightarrow$ 100%) | 0%에서 100%로 **일시(스위칭) 전환** | 트래픽을 100% **비동기 복제(Mirroring)** |
| **인프라 자원 요구** | 낮음 (트래픽 비율만큼만 인스턴스 증설) | 매우 높음 (기존과 동일한 크기의 전체 자원 2배수 필요) | 중간 (가상 추론용 자원만 필요) |
| **사용자 리스크** | **국소적 노출** (5% 고객만 장애 경험) | 100% 전체 고객 노출 리스크 (롤백은 빠름) | **제로 리스크** (사용자 응답에 전혀 반영 안 됨) |

## Ⅴ. 실무 적용 및 결론
- **판단 지표**: 치명적 장애 발생 시 평균 롤백 소요 시간(MTTR < 1분 이내), 자동화된 트래픽 전환 성공률, 사용자 세션 연속성(Sticky Session 유지율).
- **실무 설계**: 금융권 B사의 'AI 이상거래탐지(FDS) 모델 업그레이드'. FDS는 0.1초의 지연도 용납되지 않으므로 빅뱅 배포 불가. 조치 방안: 서비스 메시(Istio) 기반의 Canary 파이프라인 구축. 1) Istio VirtualService 설정을 통해 전체 결제 트래픽의 1%만 신규 모델(v2)로 라우팅 (헤더 기반 타겟팅 적용해 특정 사내 테스트망부터 인입). 2) Argo Rollouts 도구를 결합하여, v2 모델의 추론 응답 속도가 200ms를 초과하거나 HTTP 4xx/5xx 응답이 발생하면 Istio 라우팅을 즉각 v1으로 100% 롤백하는 자동화 파이프라인 구축. 3) 24시간 후 지표 안정성 확인 시 10%씩 매시간 트래픽을 늘리며 무중단 릴리스 성공.
- **결론**: Canary 배포는 실험실의 온실 속 화초(모델)를 거친 프로덕션의 야생에 조심스럽게 적응시키는 MLOps의 최전선 안전망이다. 불확실성이 극대화된 AI 시스템 환경에서 기업은 "완벽한 테스트를 거친 완벽한 모델"이라는 환상을 버려야 한다. 대신 "언제든 실패할 수 있음을 인정하고, 그 실패의 충격을 최소화하며 유연하게 후퇴할 수 있는 배포 아키텍처"를 갖추는 것이 진정한 엔지니어링 역량이다.

### 🔀 문제 유형별 목차 전환
- **Ⅱ·Ⅲ 강조 (개념/원리형)**: MLOps A/B 테스트와의 아키텍처 및 철학적 차이. A/B 테스트는 비즈니스 최적화(매출 증대)를 위해 두 모델의 트래픽을 장기간 고정(예: 50:50)하여 통계적 유의성(P-value)을 검증하는 반면, Canary 배포는 IT 리스크 관리(가용성)를 위해 트래픽을 단기간 내 동적으로 변경(Scale-up)하는 차이점 분석.
- **Ⅴ·Ⅵ 강조 (실무/설계형)**: 상태 저장(Stateful) 모델 및 데이터 편향(Data Skew) 대응 설계. 캐시(Redis)를 공유하는 환경에서 Canary 배포 시 신규 모델이 기존 캐시 스키마를 오염시키는 문제를 막기 위한 네임스페이스 분리 아키텍처 및 'Sticky Session(동일 유저는 계속 같은 모델로 라우팅)' 구현 방안.
