# 📖 【암기용】 개념 완전 이해

> 목적: Canary Model Release를 처음 봐도 완벽히 이해하게 만든다. 시험 답안 양식이 아니라, 이해를 위한 친절한 설명이다.

## 한눈에
- **개요**: 새로운 머신러닝 모델을 배포할 때, 전체 사용자에게 한꺼번에 공개하지 않고 소수의 사용자(예: 5%)에게만 먼저 노출하여 안정성을 검증한 뒤 점진적으로 확대하는 방식
- **왜 필요한가**: 모델은 학습 환경과 실제 운영 환경의 데이터가 다를 수 있어, 바로 전체 배포했다가 예측 오류가 대량 발생하면 비즈니스에 치명적인 타격을 주기 때문
- **핵심 직관**: 광부들이 유독가스 유무를 확인하기 위해 카나리아 새를 광산에 먼저 보냈던 것처럼, 소수의 사용자에게 모델을 먼저 보내 안전을 확인하는 전략

## 깊이 이해
- **배경·문제의식**: ML 모델은 코드가 정상이라도 데이터가 조금만 이상하면 엉뚱한 답을 낸다. 모든 테스트를 통과해도 실제 운영 환경의 '살아있는 데이터' 앞에서는 예상치 못한 성능 저하가 발생할 수 있다. 한 번에 100% 배포(Big Bang)했다가 오류가 나면 롤백하는 동안 이미 많은 고객이 이탈할 수 있다.
- **작동 원리**: 로드 밸런서나 API 게이트웨이에서 트래픽의 일부를 떼어내 신규 모델(Canary)로 보내고, 나머지는 기존 모델(Stable)로 보낸다. 실시간으로 두 모델의 성능(정확도, 응답 속도, 비즈니스 KPI)을 비교하여 문제가 없으면 신규 모델의 트래픽 비중을 5% -> 20% -> 50% -> 100%로 서서히 높인다.
- **비유**: 새로운 요리 레시피를 전 지점에 출시하기 전에, 특정 한 지점에서만 먼저 팔아보고 손님 반응이 좋으면 전국으로 확대하는 것과 같다.
- **구체 예시**: 넷플릭스에서 새로운 추천 알고리즘을 배포할 때, 전 세계 사용자가 아니라 특정 지역의 1% 사용자에게만 먼저 적용해보고 '시청 시간'이 늘어나는지 확인한 뒤 전 세계로 배포한다.
- **흔한 오해·주의점**: "Canary 배포는 단순한 A/B 테스트다"라고 생각할 수 있으나, A/B 테스트는 '어떤 게 더 좋은가'를 찾는 실험 목적이 강하고, Canary는 '새로운 게 안전한가'를 확인하며 위험을 분산하는 배포 전략의 성격이 강하다.

## 연결 개념
- Shadow Deployment — 실제 사용자에게 노출하지 않고 백그라운드에서만 검증하는 방식
- Blue-Green Deployment — 구/신 버전을 완전히 교체하는 방식
- Progressive Delivery — 점진적으로 가치를 전달하는 현대적 배포 방법론

# 📝 【답안용】 시험 답안 템플릿

> 목적: 시험장에서 25분에 그대로 쓰는 답안 양식. 작성방식(추상표현 금지·수치·도식·문제유형 전환)을 엄격히 지킨다.

## 핵심 인사이트 (3줄 요약)

> 1. **본질**: Canary Release는 신규 모델을 소수 트래픽에 먼저 노출하여 위험을 최소화하며 배포하는 점진적 배포 전략이다.
> 2. **가치**: 운영 환경의 실제 데이터를 기반으로 모델 안정성을 실시간 검증하며, 오류 발생 시 영향 범위를 최소화한다.
> 3. **판단 포인트**: 트래픽 분할 비율의 정교한 제어와 함께, 신/구 모델의 성능 지표를 즉각 비교할 수 있는 실시간 모니터링 체계가 필수적이다.

## 출제 의도 및 답안 포인트

| 출제 의도 | 반드시 짚을 핵심 | 감점 회피 포인트 |
|:---|:---|:---|
| 리스크 관리 기반 배포 전략 이해 확인 | 점진적 트래픽 전이, 폭폭도(Blast Radius) 최소화 | 단순히 "조금씩 배포"라고 추상적으로 기술 |
| 모델 성능 비교 및 의사결정 역량 확인 | 신/구 모델 비교 지표, 자동 롤백 기준 | 기술적 구성 요소(로드 밸런서 등) 누락 |
| MLOps 배포 자동화 성숙도 확인 | 가중치 기반 라우팅, 실시간 관측성 연계 | 수동 배포와 같은 낮은 수준의 공정 기술 |

> 요약: 신규 모델 배포 시 실제 운영 데이터의 불확실성에 대응하기 위해 영향 범위를 단계적으로 확장하는 안전 중심 배포 체계 제시가 핵심이다.

---

## Ⅰ. 개요 및 필요성

- 정의: 신규 모델(Canary)을 전체 트래픽의 소량에만 우선 적용하여 안정성을 확인한 후, 단계적으로 적용 범위를 넓혀가는 배포 방식
- 배경: 학습 데이터와 실제 데이터의 괴리(Skew) 위험, 대규모 배포 시 장애 발생에 따른 비즈니스 임팩트 최소화 필요
- 필요성: 배포 초기 단계에서의 오류 조기 발견, 롤백(Rollback) 비용 절감, 실제 사용자 반응 기반의 신속한 품질 검증

---

## Ⅱ. 구조 및 구성요소

```text
User Request -> Traffic Router (Load Balancer/API Gateway)
                        |
            +-----------+-----------+
            | (95%)                 | (5%)
      Stable Model (v1)      Canary Model (v2)
            |                       |
            +-----------+-----------+
                        |
              Monitoring & Comparison Engine -> Decision (Rollout/Rollback)
```

| 구성요소 | 역할 | 특이사항 |
|:---|:---|:---|
| Traffic Router | 사용자 요청을 비율에 따라 신/구 모델로 분산 | Nginx, Istio, AWS ALB 등 |
| Control Group | 기존의 검증된 안정적인 모델 (v1) | Baseline 역할 |
| Canary Group | 신규로 배포하여 검증할 모델 (v2) | 소수 트래픽 할당 |
| Analysis Engine | 두 모델의 성능 및 비즈니스 KPI 실시간 비교 | Prometheus, Grafana 연동 |

> 요약: 라우터를 통한 트래픽 분할과 엔진을 통한 실시간 지표 대조를 통해 배포 지속 여부를 결정함.

---

## Ⅲ. 동작원리 및 흐름도

```text
신규 모델 배포 -> 트래픽 5% 할당 -> 지표 감시 (30분) -> 정상 시 20% 확대 -> 지표 감시 -> 100% 전환 -> 구 모델 제거
      |               |                 |                 |                 |                |                |
      +---------------+-----------------+-----------------+-----------------+----------------+----------------+-----> 완료
      (이상 발생 시) -> 즉시 0% 축소 (Rollback)
```

| 단계 | 처리 내용 | 검증 기준 |
|:---:|:---|:---|
| 1 | 초기 트래픽 유입 (v2) | 가용 인스턴스 정상 동작 확인 |
| 2 | 실시간 성능 모니터링 | 정확도 하락 < 1%, 에러율 < 0.1% |
| 3 | 비즈니스 KPI 대조 | 클릭률(CTR), 구매전환율 등 유지/상승 |
| 4 | 단계적 롤아웃 (Rollout) | 트래픽 가중치 순차 상향 |

> 요약: 소수 트래픽에서 안정성이 입증될 때만 다음 단계로 트래픽을 확대하여 리스크를 원천 차단함.

---

## Ⅳ. 특징

| 구분 | Canary Deployment | Blue-Green Deployment | Shadow Deployment |
|:---|:---|:---|:---|
| 트래픽 전이 | 점진적 (5% -> 100%) | 일시적 (0% -> 100%) | 중복 (동시 전송) |
| 위험 노출 | 소수 사용자 노출 | 전체 사용자 노출 | 노출 없음 (안전함) |
| 자원 효율 | 높음 (점진적 확장) | 낮음 (2배 자원 필요) | 낮음 (2배 자원 필요) |
| 주 목적 | 안정성 및 성능 검증 | 신속한 교체 및 롤백 | 운영 데이터 무위험 검증 |

> 요약: Canary는 자원 효율과 안전성을 동시에 추구하며 실제 사용자 피드백을 단계적으로 수용하는 방식임.

## Ⅴ. 심화 비교 및 적용 판단

| 구분 | 사용자 그룹 기반 (Targeted) | 가중치 기반 (Weighted) | 선택 기준 |
|:---|:---|:---|:---|
| 분할 방식 | 특정 ID, 지역, 디바이스 기준 | 단순 트래픽 비율 (Round Robin) | 테스트 대상의 특수성 |
| 장점 | 특정 계층 영향도 정밀 파악 | 구현이 단순하고 부하 분산 용이 | 인프라 제어 편의성 |
| 단점 | 세션 관리 및 라우팅 복잡 | 특정 세그먼트 편향 발생 가능성 | 분석의 정밀도 요구사항 |

> 요약: 특정 기능의 타겟 테스트가 중요하면 그룹 기반을, 전반적인 인프라 안정성 확인이 목적이면 가중치 기반을 선택함.

| 리스크 | 원인 | 대응 방안 | 확인 지표 |
|:---|:---|:---|:---|
| Sticky Session 오류 | 신/구 모델 간 세션 불일치 | 세션 지속성(Sticky) 설정 강화 | 세션 끊김 발생률 |
| 모니터링 지연 | 성능 지표 집계 및 분석 지체 | 실시간 스트리밍 분석 도구 도입 | 지표 가시화 지연 시간 |
| 데이터 편향 | 소수 트래픽의 비대표성 | 무작위 샘플링 검증 및 기간 연장 | 샘플 데이터 통계적 유의성 |

> 요약: 세션 문제는 인프라 설정으로, 지연은 실시간 도구로, 편향은 통계 검정으로 대응함.

| 점검 항목 | 목표 기준 | 측정 방법 |
|:---|:---|:---|
| 장애 영향 범위 | 장애 시 영향 사용자 5% 미만 | 트래픽 분할 비율 모니터링 |
| 자동 롤백 시간 | 이상 감지 후 롤백 1분 이내 | 자동화 스크립트 실행 로그 |
| 검증 신뢰도 | 신/구 모델 지표 오차 1% 이내 | 통계적 가설 검정 (T-test 등) |

> 요약: 도입 효과는 장애 발생 시 폭폭도(Blast Radius) 통제력과 자동 대응 속도로 판정함.

## Ⅵ. 실무 적용 및 결론

**적용 방안 3개:**
1. 리스크 최소화 배포: 신규 대출 승인 모델 배포 시, 1단계로 내부 직원(5%)에게만 1시간 동안 노출하여 기술적 오류 점검 후 단계적 확대
2. 자동화된 롤백(Circuit Breaker): 서비스 에러율이 1%를 초과하거나 응답 지연이 200ms 이상 발생할 경우, 사람의 개입 없이 즉시 Canary 트래픽을 0%로 자동 복구
3. 지표 기반 의사결정: Prometheus와 연동된 배포 도구(Argo Rollouts 등)를 사용하여 정확도 및 비즈니스 KPI가 Baseline 대비 우수할 때만 자동으로 다음 단계 롤아웃

**결론 (2줄):**
- 기술사 판단: Canary 배포는 불확실성이 높은 ML 모델을 운영 환경에 안전하게 착륙시키기 위한 "소프트 랜딩" 전략임
- 향후 방향: 트래픽 분할뿐만 아니라 모델의 결과값을 실시간으로 비교하여 이상치를 차단하는 "인텔리전트 가드레일"과 결합될 전망
