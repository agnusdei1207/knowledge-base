# 📖 【암기용】 개념 완전 이해

> 목적: OTA를 차량·단말·장비 소프트웨어를 원격으로 배포·검증·회수하는 수명주기 관리로 이해하게 만든다.

## 한눈에
- **개요**: 네트워크를 통해 소프트웨어 패키지를 원격 배포하고 적용하는 업데이트 방식
- **왜 필요한가**: 차량과 IoT 장비는 출고 후에도 보안 취약점, 결함, 기능 요구가 계속 발생한다.
- **핵심 직관**: 정비소 방문 없이 검증된 패키지를 내려받아 적용하고, 문제가 생기면 이전 상태로 되돌리는 배포 체계다.

## 깊이 이해
- **배경·문제의식**: 차량 기능이 소프트웨어화되면서 업데이트 대상은 인포테인먼트뿐 아니라 제어기, ADAS, 배터리 관리까지 확대되었다.
- **작동 원리**: 서버가 대상 차량과 버전을 식별하고, 서명된 패키지를 전송하며, 차량은 무결성·호환성·전원 상태를 확인한 뒤 설치한다.
- **비유**: OTA는 집으로 배송되는 약과 같다. 처방전 확인, 포장 봉인, 복용 조건, 부작용 시 중단 절차가 모두 필요하다.
- **구체 예시**: UNECE R156은 소프트웨어 업데이트 관리체계(SUMS)와 소프트웨어 식별번호(SWIN) 기반 이력 관리를 요구한다.
- **흔한 오해·주의점**: OTA는 단순 다운로드가 아니다. 업데이트 실패가 차량 기능 제한으로 이어질 수 있으므로 A/B 파티션, 전원 조건, 롤백, 승인 이력이 필요하다.

## 연결 개념
- UNECE R156 — 차량 소프트웨어 업데이트 관리 규정
- SDV — OTA를 전제로 한 차량 SW 플랫폼
- SBOM — 업데이트 패키지 구성요소와 취약점 추적

# 📝 【답안용】 시험 답안 템플릿

> 목적: 시험장에서 25분에 그대로 쓰는 답안 양식.
> 핵심: OTA는 원격 배포가 아니라 식별·서명·무결성 검증·설치·롤백·감사를 포함하는 SW 업데이트 관리체계다.

## 핵심 인사이트 (3줄 요약)

> 1. **본질**: OTA Update는 네트워크를 통해 SW를 배포하고 장치가 검증 후 설치하는 원격 업데이트 체계다.
> 2. **가치**: 보안 패치, 결함 수정, 기능 변경을 장치 수명주기 동안 수행하고 현장 방문 비용과 리콜 부담을 줄인다.
> 3. **판단 포인트**: 서명 검증, 대상 식별, 안전 상태 확인, 롤백, 업데이트 이력, 규제 대응이 핵심이다.

## 출제 의도 및 답안 포인트

| 출제 의도 | 반드시 짚을 핵심 | 감점 회피 포인트 |
|:---|:---|:---|
| OTA 구조 이해 확인 | 패키징·배포·검증·설치·롤백 | 다운로드 방식만 설명 |
| 보안 통제 판단 확인 | 코드 서명, TLS, 무결성, 권한 | 암호화만 쓰고 서명 검증 누락 |
| 차량 규제 인식 확인 | UNECE R156 SUMS, SWIN, 이력 관리 | R155와 R156 목적 혼동 |

> 요약: 이 문제는 원격 업데이트 편의보다 실패·위변조·승인 이력 통제 능력을 확인한다.

---

## Ⅰ. 개요 및 필요성

- 개요: 원격 SW 업데이트
- 배경: 연결 장치와 차량은 출고 이후에도 취약점 패치와 결함 수정이 필요하다.
- 필요성: OTA는 대상 식별, 서명 검증, 설치 조건 확인, 롤백으로 원격 배포 리스크를 통제한다.

---

## Ⅱ. 구조 및 구성요소

```text
Update Server -> Campaign Manager -> Secure Channel -> Device Agent
      +-> Package Signing / Manifest
      +-> Install Engine -> A/B Slot / Rollback -> Audit Log
```

| 구성요소 | 역할 | 특이사항 |
|:---|:---|:---|
| Campaign Manager | 대상 장치·버전·일정 정의 | staged rollout |
| Package/Manifest | 바이너리, 버전, 의존성, 서명 포함 | hash, signature |
| Device Agent | 다운로드·검증·설치 수행 | 전원·상태 조건 확인 |
| Rollback/Audit | 실패 복구와 업데이트 이력 보관 | UNECE R156 대응 |

> 요약: OTA는 서버 캠페인, 서명 패키지, 장치 에이전트, 롤백·감사 로그가 결합된 배포 구조다.

---

## Ⅲ. 동작원리 및 흐름도

```text
대상 식별 -> 패키지 서명 -> 다운로드
-> 무결성·호환성 검증 -> 설치 -> 재시작 / 활성화 -> 성공 확인 / 롤백
```

| 단계 | 처리 내용 | 검증 기준 |
|:---:|:---|:---|
| 1 | 장치 모델, SW 버전, 배터리·전원 상태를 확인함 | eligibility rule |
| 2 | 패키지와 manifest를 다운로드함 | TLS, resume support |
| 3 | 해시·서명·버전 의존성을 검증함 | signature verification |
| 4 | A/B slot 또는 delta 방식으로 설치함 | install result, rollback log |

> 요약: OTA는 설치 전 검증과 설치 후 확인을 분리해 위변조와 배포 실패를 통제한다.

## Ⅳ. 특징

| 구분 | 로컬 업데이트 | OTA Update | 판단 기준 |
|:---|:---|:---|:---|
| 배포 방식 | 정비소·USB | 네트워크 캠페인 | 대상 수와 긴급도 |
| 보안 통제 | 물리 접근 통제 | 서명·TLS·권한 검증 | key protection |
| 실패 대응 | 현장 복구 | 원격 롤백·재시도 | A/B slot 여부 |
| 규제 대응 | 정비 기록 중심 | 업데이트 이력·SWIN | UNECE R156 |

> 요약: OTA는 현장 방문을 줄이는 대신 위변조 방지와 실패 복구 설계를 배포 전제조건으로 둔다.

## Ⅴ. 심화 비교 및 적용 판단

| 비교 축 | 기존/대안 | 본 키워드 | 선택 기준 |
|:---|:---|:---|:---|
| 배포 범위 | 수동 정비 | 원격 대규모 배포 | 긴급 패치 필요 |
| 패키지 | 전체 이미지 | delta·container·A/B | 대역폭과 복구 요구 |
| 운영 | 일괄 배포 | canary·staged rollout | 실패 영향 범위 |

> 요약: OTA는 대규모 장치와 긴급 패치가 필요한 환경에서 단계 배포와 롤백 설계를 전제로 선택한다.

| 리스크 | 원인 | 대응 방안 | 확인 지표 |
|:---|:---|:---|:---|
| 패키지 위변조 | 서명 키 유출·검증 누락 | HSM, code signing, manifest hash | invalid package block |
| 업데이트 중단 | 전원 차단·통신 단절 | A/B partition, resume download | interrupted update rate |
| 기능 장애 | 버전 의존성 충돌 | dependency check, rollback gate | post-update DTC |

> 요약: OTA 리스크는 위변조, 중단, 호환성 오류이며 서명·A/B·의존성 검증으로 통제한다.

| 점검 항목 | 목표 기준 | 측정 방법 |
|:---|:---|:---|
| 배포 성공 | 성공률·롤백률·재시도율 추적 | campaign dashboard |
| 보안 | 서명 검증 실패와 키 접근 기록 | PKI log, HSM audit |
| 규제 | SWIN·버전·대상·승인 이력 보관 | SUMS audit trail |

> 요약: OTA 품질은 성공률 하나가 아니라 롤백률, 서명 실패, 승인 이력을 함께 봐야 한다.

---

## Ⅵ. 실무 적용 및 결론

**적용 방안 3개:**
1. ECU·장치별 criticality를 분류하고 safety-critical 업데이트에는 전원 조건, 정차 조건, 사용자 승인 조건을 분리 적용함.
2. 코드 서명 키를 HSM/KMS로 보호하고 manifest hash, TLS, secure boot 연계를 통해 설치 전 무결성을 검증함.
3. canary 1% -> staged rollout -> 전체 배포 순서로 캠페인을 구성하고 failure threshold 초과 시 자동 중단과 롤백을 실행함.

**결론 (2줄):**
- 기술사 판단: OTA는 원격 배포 대상이 많고 패치 긴급도가 높을수록 필요하나, 서명·롤백·감사 체계 없이는 적용 범위를 제한해야 함.
- 향후 방향: OTA는 SDV, SBOM, 취약점 관리, 기능 구독과 결합해 차량·IoT 운영의 기본 배포 체계가 됨.
