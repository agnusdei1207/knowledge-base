# 📖 【암기용】 개념 완전 이해

## 한눈에
- **개요**: 에이전트 샌드박스는 AI 에이전트의 **코드 실행·파일 접근·네트워크 호출**을 호스트 시스템으로부터 **격리**하는 제한된 실행 환경이다. 권한통제(020)가 "이 도구를 호출할 자격이 있는가"를 판단한다면, 샌드박스는 "호출이 허용되더라도 실행 결과가 호스트에 피해를 주지 않도록 물리적으로 격리"하는 역할이다.
- **왜 필요한가**: 에이전트가 코드 실행기(REPL)·셸·브라우저·외부 API를 사용하면, 프롬프트 인젝션(186 참조)으로 주입된 악성 코드가 실제 명령으로 실행될 수 있다. 호스트와 동일 권한으로 실행하면 파일 삭제·데이터 유출·자원 고갈(무한루프)이 직접 발생하므로, 격리된 환경에서 실행하고 결과만 추출해야 한다.
- **핵심 직관**: 신약 실험을 일반 병동이 아니라 밀폐된 실험실에서 하는 것과 같다. 실험 중 사고가 나도 병동 환자에게 영향이 없고, 실험이 끝나면 실험실을 폐기한다.

## 핵심 용어 정리 (내부에 등장하는 것들)

| 용어/표기 | 의미 | 비유·예 |
|:---|:---|:---|
| 샌드박스(상위 키워드) | 프로그램 실행을 격리해 호스트 피해를 방지하는 보안 메커니즘 | 놀이터의 모래 상자 — 모래가 밖으로 안 나감 |
| 컨테이너(Container) | OS 커널을 공유하되 네임스페이스·cgroup으로 프로세스를 격리 | 칸막이 사무실 — 벽은 있지만 건물은 공유 |
| gVisor | 사용자 공간 커널로 시스템 콜을 중계해 컨테이너 탈출을 방지 | 실제 커널과 컨테이너 사이의 "방탄 유리" |
| Firecracker | 경량 microVM으로 커널 수준 격리 제공(Lambda·Fargate 기반) | 진짜 별도 건물에서 실험 |
| seccomp | 프로세스가 사용할 수 있는 시스템 콜을 제한하는 리눅스 기능 | "이 도구만 사용 가능" 목록 |
| AppArmor/SELinux | 프로세스의 파일·네트워크 접근을 프로파일로 제한하는 MAC | 방마다 출입 허가증이 다른 보안 시스템 |
| egress 차단 | 컨테이너에서 외부 네트워크로 나가는 트래픽을 차단 | 실험실에서 외부로 전화 금지 |
| read-only FS | 파일시스템을 읽기 전용으로 마운트해 변경을 원천 차단 | 열람만 가능한 자료실 |
| SBOM(Software Bill of Materials) | 소프트웨어 구성 요소 목록. 이미지 취약점(CVE) 스캔의 입력 | 식품의 원재료 표시 |

## 깊이 이해
- **배경·문제의식**: HITL(022)이 "사람이 승인하는가"를 다루고, 권한통제(020)가 "호출 자격이 있는가"를 다룬다면, 샌드박스는 "실행 자체의 물리적 피해를 어떻게 제한하는가"를 다룬다. 특히 코드 생성 에이전트(코드 인터프리터·Jupyter 실행)나 브라우저 에이전트는 임의 코드를 직접 실행하므로, 격리 없이는 호스트 전체가 공격 표면이 된다.
- **작동 원리(어떻게+왜)**: ① 작업 요청이 들어오면 서명 검증·CVE 스캔을 통과한 이미지로 격리 환경(컨테이너 or microVM)을 생성한다. ② read-only FS, 비특권 UID(예: 65534), seccomp/AppArmor 프로파일, egress allowlist, CPU 2코어/메모리 4GB/timeout 300초 제한을 설정한다. ③ 에이전트 코드·도구가 격리 환경 내에서 실행되고, 모니터가 시스템 콜·네트워크·자원 사용을 실시간 감시한다. ④ 실행 완료 후 결과만 마스킹 처리해 반환하고, 격리 환경 전체를 폐기(ephemeral)한다.
- **비유**: 폭발물 처리반이 작업할 때 방폭 챔버 안에서 해체하는 것과 같다. 성공하면 결과(해체 완료)만 꺼내고, 실패(폭발)해도 챔버 밖은 안전하다. 작업 후 챔버를 청소(폐기)한다.
- **구체 예시**: 코드 분석 에이전트가 Pull Request의 보안 취약점을 점검할 때, 해당 레포를 read-only로 마운트한 gVisor 컨테이너(CPU 2코어, 메모리 4GB, timeout 300초, 외부망 차단)에서 정적 분석 도구를 실행한다. 분석 결과 JSON만 반환하고 컨테이너는 즉시 삭제한다.
- **흔한 오해·주의점**: "샌드박스는 완전한 보안이다"는 오해다. 컨테이너는 커널을 공유하므로 커널 취약점으로 탈출(container escape)이 가능하다. gVisor·Firecracker로 커널 격리를 강화하고, 이미지 자체의 CVE를 SBOM 기반으로 주기적으로 스캔해야 한다. 샌드박스는 "피해 범위 제한"이지 "침투 불가"가 아니다.

## 연결 개념
- 에이전트 권한통제(020) — 도구 호출 자격. 샌드박스는 호출 허용 후 실행 격리를 담당
- 에이전트 가드레일(029) — 출력 안전성 제어. 샌드박스와 계층적으로 결합
- 기밀 컴퓨팅(184) — TEE 기반 실행 격리. 샌드박스보다 하드웨어 수준의 격리

# 📝 【답안용】 시험 답안 템플릿

## 핵심 인사이트 (3줄 요약)

> 1. **본질**: 에이전트 샌드박스는 코드·도구 실행을 컨테이너/microVM으로 격리해 호스트 피해를 제한하는 실행 환경임.
> 2. **가치**: 악성 코드 실행·데이터 유출·자원 고갈을 격리 경계 안에 가두고, 실행 후 환경을 폐기함.
> 3. **판단 포인트**: 커널 격리 수준(gVisor/Firecracker), egress 차단, 자원 한도, 이미지 CVE 스캔을 함께 설계해야 함.

## 출제 의도 및 답안 포인트

| 출제 의도 | 반드시 짚을 핵심 | 감점 회피 포인트 |
|:---|:---|:---|
| AI 실행 격리 설계 역량 | 컨테이너/VM, seccomp, egress 차단, 자원 한도 | 샌드박스를 완전 보안으로 서술(피해 범위 제한임) |
| 잔여 리스크 인식 | 컨테이너 탈출, 이미지 CVE, 자원 고갈 | 격리만으로 충분 단정, 탈출 방어(gVisor) 누락 |

> 요약: AI 실행 격리 설계와 잔여 리스크(탈출·이미지 취약점) 인식을 증명해야 함.

---

## Ⅰ. 개요 및 필요성

- 개요: AI 에이전트의 코드·도구 실행을 컨테이너/microVM으로 격리하는 제한된 실행 환경임
- 배경: 에이전트가 REPL·셸·브라우저를 사용하면 인젝션 코드가 호스트에서 직접 실행될 수 있음
- 필요성: 파일 삭제·데이터 유출·자원 고갈 방지를 위해 격리·권한·자원 제한 후 결과만 추출이 필수임

---

## Ⅱ. 구조 및 구성요소

```text
에이전트 작업 -> 이미지 검증(서명/CVE) -> 격리 환경 생성
  -> 권한 설정(read-only/seccomp/egress) -> 실행·감시
     -> 결과 추출(마스킹) -> 환경 폐기
```

| 구성요소 | 역할 | 특이사항 |
|:---|:---|:---|
| Runtime | 격리 실행 환경 제공 | Container, gVisor, Firecracker |
| Policy Guard | 파일·네트워크·시스템콜 통제 | seccomp, AppArmor, egress allowlist |
| Resource Limiter | CPU·메모리·시간·PID 제한 | cgroup v2, timeout 자동 종료 |
| Monitor | 실행 감시·이상 탐지·중단 | syscall 추적, 자원 모니터링 |

> 요약: 검증된 이미지로 격리 환경을 생성하고, 정책·자원·감시로 실행을 통제한 뒤 환경을 폐기함.

---

## Ⅲ. 동작원리 및 흐름도

```text
작업 수신 -> 이미지 서명·CVE 검증 -> 격리 환경 생성
  -> 권한·자원 제한 설정 -> 작업 실행·감시 -> 결과 추출 -> 환경 폐기
```

1. 이미지 검증: 실행 이미지의 서명을 확인하고 SBOM 기반 CVE 스캔을 통과해야 환경 생성을 허용함
2. 환경 설정: read-only FS, 비특권 UID, seccomp/AppArmor 프로파일, egress allowlist, CPU/메모리/timeout 한도를 적용함
3. 실행·감시: 격리 환경 내에서 코드·도구를 실행하고, 시스템 콜·네트워크·자원 사용을 실시간 모니터링함
4. 결과·폐기: 실행 결과만 마스킹 처리해 반환하고, 격리 환경 전체를 즉시 삭제(ephemeral)함

> 요약: 이미지 검증→격리 설정→실행 감시→결과 추출→환경 폐기로 잔류 위험을 최소화함.

---

## Ⅳ. 특징

- 일회성(Ephemeral): 작업 완료 후 환경을 폐기해 잔류 데이터·프로세스를 원천 제거함
- 다층 격리: seccomp(시스템 콜)+AppArmor(파일·네트워크)+gVisor(커널)로 격리 수준을 조합함
- egress 차단: 기본 외부망 차단, allowlist에 등록된 API만 호출 가능해 데이터 유출을 방지함
- 자원 한도: CPU/메모리/PID/timeout 제한으로 무한루프·fork bomb에 의한 자원 고갈을 차단함
- 피해 범위 제한: 샌드박스는 "침투 불가"가 아니라 "피해를 격리 경계 안에 가둠"이므로 탈출 방어도 병행 필수임

---

## Ⅴ. 심화 비교 및 적용 판단

| 구분 | 호스트 직접 실행 | 에이전트 샌드박스 | 선택 기준 |
|:---|:---|:---|:---|
| 권한 범위 | 호스트 전체 파일·프로세스 접근 | read-only FS, 비특권 UID | 코드 실행·파일 처리 시 샌드박스 필수 |
| 네트워크 | 외부망 자유 접근 | egress allowlist, 내부망 제한 | 외부 API 호출 여부에 따라 allowlist 설정 |
| 장애 영향 | 호스트 전체에 파급 | 격리 환경 내 한정, 폐기로 잔류 제거 | 실행 실패 시 호스트 영향도 |

> 요약: 코드 실행·파일 처리 에이전트는 호스트 직접 실행 대신 샌드박스 격리를 기본으로 설계함.

**리스크·대응:**
- 컨테이너 탈출: 커널 취약점·권한 상승 → gVisor/Firecracker로 커널 격리, 비특권 UID, seccomp 적용 (지표: CVE 패치 적용률 100%)
- 데이터 유출: 네트워크·볼륨 마운트 경유 → egress 차단, 임시 볼륨 사용, 결과 마스킹 (지표: 외부 전송 차단 건수)
- 자원 고갈: 무한루프·fork bomb → CPU/메모리/PID 제한, timeout 자동 종료 (지표: OOM kill·timeout 건수 월 5건 이내)

**도입 후 점검 지표:**
- 이미지 취약점: Critical/High CVE 0건 — SBOM 기반 주간 스캔
- 격리 정책 적용률: seccomp·AppArmor 100% 적용 — 런타임 정책 감사

---

## Ⅵ. 실무 적용 및 결론

**적용 방안 3개:**
1. 코드 실행 에이전트는 기본값으로 read-only FS·비특권 UID·seccomp·AppArmor·egress 차단을 적용함
2. 작업별 CPU 2코어·메모리 4GB·timeout 300초·PID 100 한도를 설정하고 초과 시 자동 종료함
3. 실행 이미지는 서명 검증+SBOM 기반 CVE 스캔을 CI/CD에서 강제하고, 실행 로그를 SIEM으로 전송함

**결론:**
- 기술사 판단: 코드 실행·브라우징·파일 처리 에이전트는 샌드박스 없이 운영 환경 접근을 허용하지 않음
- 향후 방향: 에이전트 샌드박스는 기밀 컴퓨팅(184)·AI Gateway·Policy Engine과 결합한 다층 실행 보안으로 발전함
