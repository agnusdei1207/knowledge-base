## Ⅰ. 개요
- **정의**: 에이전트가 생성한 신뢰 불가 코드를 호스트로부터 커널 수준으로 격리하여 실행하는 일회용 보안 환경
- **배경/필요성**: 에이전트에 코드 실행(Code Interpreter) 능력이 부여되면서, 프롬프트 인젝션에 의한 원격 코드 실행(RCE) 공격으로 호스트 시스템 전체가 탈취될 위험이 현실화됨. 에이전트의 행동을 제한(020 참조)하는 것과 별개로, 코드 실행 자체를 물리적으로 격리하는 환경이 필수
- **비유**: 폭발물 처리반의 방폭 컨테이너 — 폭발이 일어나도 컨테이너 밖은 무사

| 출제 의도 | 반드시 짚을 핵심 | 감점 회피 포인트 |
|:---|:---|:---|
| 컨테이너 vs 마이크로VM 격리 수준 차이 | 커널 격리, 네트워크 차단, cgroups 자원 제한, Ephemeral 생명주기 | Docker만 쓰면 커널 공유로 탈출 가능. MicroVM(Firecracker)의 커널 독립 격리를 구분 |

> 요약: 에이전트 생성 코드를 커널 격리된 일회용 환경에서 실행하여 호스트 보안을 보장하는 체계

## Ⅱ. 구성요소
```text
+---------------------------+
|  Agent Runtime            |
|  "이 Python 코드 실행해"  |
+-----------+---------------+
            | 코드 전달
            v
+-----------+---------------+
|  Sandbox Orchestrator     |
|  - 환경 프로비저닝        |
|  - 자원 할당(cgroups)     |
+-----------+---------------+
            |
            v
+-----------+---------------+
|  Isolated Runtime         |
|  +---------------------+ |
|  | MicroVM / Container | |
|  | - 네트워크 차단      | |
|  | - 읽기전용 마운트    | |
|  | - CPU 0.5c, RAM 512M| |
|  +---------------------+ |
+-----------+---------------+
            | stdout/stderr만 반환
            v
+-----------+---------------+
|  Result Extractor         |
|  + 환경 즉시 폐기         |
+---------------------------+
```

| 구성요소 | 설명 | 비유 |
|:---|:---|:---|
| Sandbox Orchestrator | 코드 실행 요청마다 격리 환경을 100ms 이내 프로비저닝하고 자원 한도를 설정 | 실험실 안전관리자 |
| Isolated Runtime | 독립 커널(MicroVM) 또는 네임스페이스 격리(Container) 기반 실행 공간. 네트워크·파일시스템·시스템콜 제한 적용 | 방폭 챔버 |
| cgroups/seccomp | CPU·메모리 상한 설정(cgroups), 위험 시스템콜 차단(seccomp/AppArmor) | 전력 차단기 |
| Result Extractor | 실행 결과(stdout, stderr)만 호스트로 추출 후 환경 전체를 즉시 삭제(Tear-down) | 검체 추출 후 폐기 |

> 요약: 오케스트레이터가 일회용 격리 환경을 생성하고, 결과만 추출 후 환경을 폐기하는 4계층 구조

## Ⅲ. 절차
```text
+----------------+    +----------------+    +----------------+    +----------------+
| 1. 환경 생성   | -> | 2. 격리 실행   | -> | 3. 결과 추출   | -> | 4. 환경 폐기   |
| (Spin-up)      |    | (Isolated Run) |    | (Extract)      |    | (Tear-down)    |
+----------------+    +----------------+    +----------------+    +----------------+
```

1. **환경 생성(Ephemeral Spin-up)** — 에이전트의 코드 실행 요청 시 Firecracker MicroVM 또는 Docker 컨테이너를 100ms 이내에 프로비저닝. 재사용 없이 매 요청마다 신규 생성
2. **격리 실행(Isolated Run)** — 아웃바운드 네트워크 100% 차단, 파일시스템 읽기 전용 마운트, seccomp으로 위험 시스템콜 필터링. cgroups로 CPU 0.5코어·RAM 512MB·실행 시간 10초 제한 적용
3. **결과 추출(Extract)** — 실행 완료 후 stdout/stderr 텍스트만 호스트로 전달. 생성된 파일·바이너리는 반환하지 않음
4. **환경 폐기(Tear-down)** — 실행 환경(파일시스템·프로세스·네트워크 네임스페이스)을 흔적 없이 강제 삭제. 악성 코드가 잔류할 여지 제거

> 요약: 일회용 생성→격리 실행→결과만 추출→즉시 폐기의 무상태(Stateless) 생명주기

## Ⅳ. 문제점
- [컨테이너 탈출(Container Breakout)]: Docker는 호스트와 커널을 공유하므로, 커널 취약점 악용 시 호스트 Root 권한 탈취 가능
- [Cold Start 지연]: MicroVM의 경우에도 동시 수백 요청 시 프로비저닝 지연(수초)으로 처리량 병목 발생
- [데이터 탈취(Exfiltration)]: 네트워크 차단에도 DNS 터널링 등 우회 경로를 통한 사내 데이터 유출 가능성 존재

> 요약: 커널 공유 탈출, 프로비저닝 병목, DNS 터널링 기반 데이터 탈취가 3대 위협

## Ⅴ. 개선방안
1. 단기: Docker → MicroVM(Firecracker) 전환으로 커널 독립 격리 달성, 컨테이너 탈출 경로 원천 차단
2. 중기: Warm Pool(사전 생성 대기 VM 풀) 운영으로 Cold Start를 50ms 이내로 단축
3. 장기: WebAssembly(WASM) 기반 브라우저 샌드박스 도입으로 서버리스·엣지 환경까지 격리 범위 확장

- [DNS 탈취]: [우회 경로 존재] → 아웃바운드 DNS 쿼리 포함 전 네트워크 스택 완전 비활성화(Air-gap) (지표: 아웃바운드 패킷 0건)

> 요약: MicroVM으로 격리 강화, Warm Pool로 지연 해소, WASM으로 엣지 보안까지 확장

## Ⅵ. 전망
- 향후 발전 방향: 코드 실행을 넘어 브라우저 렌더링·GUI 조작까지 포함하는 Full-OS 클라우드 샌드박스(E2B, Daytona)로 확장 중
- 기술사적 판단: 에이전트에 코드 실행 능력을 부여하는 전제 조건이 샌드박스임. 샌드박스 없는 Code Interpreter는 프로덕션 투입 불가
- 기술사 제언: MicroVM + Air-gap 네트워크를 기본 설계로 채택하고, 격리 수준을 SLA로 명시(탈출 확률 0, 아웃바운드 트래픽 0)하여 보안 감사를 통과할 것
