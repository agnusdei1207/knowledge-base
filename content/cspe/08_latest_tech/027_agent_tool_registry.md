## Ⅰ. 개요
- **정의**: 에이전트가 사용 가능한 도구(API·함수)의 명세·권한·엔드포인트를 중앙 등록·검색·배급하는 카탈로그 플랫폼
- **배경/필요성**: 엔터프라이즈 환경에서 도구가 수백~수천 개로 증가하면 전체 명세를 프롬프트에 주입 시 토큰 한도 초과 및 할루시네이션이 발생하며, 권한 없는 도구 호출을 막을 중앙 통제가 필수임
- **비유**: 수천 권의 책이 꽂힌 도서관에서 사서가 요청 주제에 맞는 3권만 골라 건네주는 것과 유사

| 출제 의도 | 반드시 짚을 핵심 | 감점 회피 포인트 |
|:---|:---|:---|
| 하드코딩 도구 주입의 한계와 동적 레지스트리의 필요성 | Tool-RAG(의미 검색 기반 동적 주입) + RBAC 권한 필터링 | MCP 생태계와의 관계, 도구 설명(Description) 품질 거버넌스 누락 시 감점 |

> 요약: 도구 레지스트리는 수천 개 도구를 중앙 관리하고 필요한 것만 동적 주입하는 에이전트 전용 카탈로그임

## Ⅱ. 구성요소
```text
+------------------------------------------------------------------+
|                     Tool Registry Platform                        |
|  +------------+    +-----------+    +----------+    +----------+  |
|  | Schema     |--->| Semantic  |--->| RBAC     |--->| Prompt   |  |
|  | Store      |    | Retriever |    | Filter   |    | Injector |  |
|  +------------+    +-----------+    +----------+    +----------+  |
|   도구 명세 저장     의미 검색        권한 필터링     프롬프트 주입  |
+------------------------------------------------------------------+
```

| 구성요소 | 설명 | 비유 |
|:---|:---|:---|
| Schema Store | 도구명·Description·JSON Schema·엔드포인트·버전을 벡터 DB에 등록·저장 | 도서관 서지 목록 |
| Semantic Retriever | 사용자 입력과 도구 설명 간 임베딩 유사도로 상위 N개 도구 검색(Tool-RAG) | 사서의 주제별 검색 |
| RBAC Filter | 검색된 도구 중 사용자·에이전트의 역할(Role)에 부적합한 도구 제거 | 열람 제한 도서 필터 |
| Prompt Injector | 최종 선별된 도구의 JSON Schema만 시스템 프롬프트에 동적 삽입 | 필요한 책만 책상에 배치 |

> 요약: 저장→검색→필터→주입의 4단계로 토큰 비용 절감과 권한 통제를 동시 달성

## Ⅲ. 절차
```text
+----------+     +----------+     +----------+     +----------+
| 도구 등록 |---->| 의미 검색 |---->| 권한 검증 |---->| 동적 주입 |
| (Schema) |     | (Vector) |     | (RBAC)   |     | (Prompt) |
+----------+     +----------+     +----------+     +----------+
```

1. **도구 등록(Registration)** — 개발자가 도구명, 상세 자연어 설명, 파라미터 JSON Schema, 사용 조건(When-to-use / When-not-to-use)을 레지스트리에 등록
2. **동적 도구 검색(Retrieval)** — 사용자 입력을 임베딩하여 벡터 DB에서 코사인 유사도 기준 상위 Top-K 도구를 1차 추출
3. **권한 필터링(Authorization)** — 추출된 도구 중 현재 세션의 사용자 Role·에이전트 등급에 부적합한 도구를 RBAC 정책으로 제거
4. **프롬프트 렌더링(Injection)** — 최종 도구(3~5개)의 JSON Schema만 시스템 프롬프트에 삽입, 토큰 소비를 도구당 평균 200토큰 이내로 제한

> 요약: 등록→검색→필터→주입 파이프라인으로 수천 개 도구를 3~5개로 압축 제공

## Ⅳ. 문제점
- **설명 모호성**: 유사 이름 도구(search_db vs query_db) 간 Description 부실로 LLM이 잘못된 도구 선택 — 도구 거버넌스 부재
- **벡터 검색 오탐**: 임베딩 유사도만 의존 시 의미는 유사하나 기능이 다른 도구가 주입되어 할루시네이션 유발 — 단일 검색 전략 한계
- **레지스트리 비대화**: 미사용·폐기 도구가 축적되어 검색 정확도 저하 및 관리 오버헤드 증가 — 라이프사이클 관리 부재

> 요약: 설명 품질, 검색 정확도, 도구 수명 관리가 레지스트리의 3대 과제임

## Ⅴ. 개선방안
1. 단기: 도구 등록 시 When-to-use / When-not-to-use(Negative Prompt) 기입을 필수 심사 항목으로 제도화
2. 중기: 벡터 검색 + 키워드 매칭 + 카테고리 태그를 결합한 Hybrid Retrieval로 검색 정밀도 향상
3. 장기: 도구별 호출 빈도·성공률 메트릭 수집 → 6개월 미사용 도구 자동 비활성화(Deprecation) 파이프라인 구축

- **설명 모호성**: 등록 심사 시 Description 품질 점수(LLM 자동 채점) 70점 미만 반려 → 도구 구분 정확도 95% 이상 유지 (지표: 도구 선택 오류율 < 3%)
- **벡터 검색 오탐**: Hybrid Retrieval + Re-ranker 모델 2단계 적용 → 의미·기능 일치도 동시 검증 (지표: Top-3 적중률 > 90%)
- **레지스트리 비대화**: 분기별 호출 통계 기반 자동 정리 + 버전 관리(Semantic Versioning) 적용 (지표: 활성 도구 비율 > 80%)

> 요약: 거버넌스 강화·하이브리드 검색·라이프사이클 자동화로 레지스트리 품질 확보

## Ⅵ. 전망
- 향후 발전 방향: MCP(Model Context Protocol) 생태계와 결합하여 외부 MCP Server의 도구를 자동 발견·등록하는 분산 레지스트리로 확장, 나아가 에이전트가 도구를 직접 코딩하여 자가 등록하는 Self-Evolution 단계로 진화
- 기술사적 판단: 레지스트리의 핵심 가치는 '도구 수 확장성'이 아니라 '도구 설명 품질'에 있으며, Description 거버넌스 없는 레지스트리는 할루시네이션 증폭기로 전락함
- 기술사 제언: 정책 엔진(028번 참조)과 연동하여 도구 주입 단계에서 권한을, 도구 실행 단계에서 파라미터 검증을 이중으로 수행하는 계층형 보안 설계를 권고함
