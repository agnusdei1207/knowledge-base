# 📖 【암기용】 개념 완전 이해

> 목적: 에이전트 도구 레지스트리를 처음 봐도 완벽히 이해하게 만든다.

## 한눈에
- **개요**: AI 에이전트가 호출 가능한 도구(API·함수·서비스)의 메타데이터를 중앙 관리하는 카탈로그
- **왜 필요한가**: 에이전트가 수십~수백 개 도구 중 적합한 것을 선택하려면 이름·스키마·권한·버전이 검색 가능해야 함
- **핵심 직관**: 앱스토어처럼 도구를 등록·검색·버전관리하고, 에이전트가 필요할 때 골라 쓰는 구조

## 깊이 이해
- **배경·문제의식**: 도구를 하드코딩하면 새 도구 추가마다 에이전트 재배포가 필요하고, 권한 없는 도구 호출 위험이 생김
- **작동 원리**: ① 도구 제공자가 OpenAPI/MCP 스키마로 등록 ② 레지스트리가 이름·설명·입출력·권한을 색인 ③ 에이전트가 의미 검색으로 도구 후보를 조회 ④ 정책 엔진이 호출 권한 검증
- **비유**: 회사 내부 포털에서 사내 시스템 목록을 검색하고, 권한 신청 후 접근하는 것과 같음
- **구체 예시**: MCP 서버가 도구 50개를 JSON Schema로 등록하면, 에이전트가 "매출 조회"를 의미 검색해 `sales_api.get_revenue` 도구를 선택함
- **흔한 오해·주의점**: 도구 수가 많을수록 LLM 컨텍스트를 소모하므로, 전체 목록이 아닌 상위 K개만 주입해야 함

## 연결 개념
- MCP (Model Context Protocol) — 도구 등록·호출의 표준 프로토콜
- 에이전트 정책 엔진 — 도구 호출 권한·비용 통제
- Function Calling — LLM이 도구를 선택·호출하는 인터페이스

# 📝 【답안용】 시험 답안 템플릿

> 목적: 시험장에서 25분에 그대로 쓰는 답안 양식.

## 핵심 인사이트 (3줄 요약)

> 1. **본질**: 도구 레지스트리는 에이전트가 사용할 도구의 스키마·권한·버전을 중앙 관리하는 카탈로그임.
> 2. **가치**: 도구 추가·변경 시 에이전트 재배포 없이 동적 바인딩 가능, 도구 검색 정확도 90% 이상 확보.
> 3. **판단 포인트**: 도구 수 50개 이하는 전체 주입, 50개 초과는 의미 검색+Top-K 필터링으로 설계.

---

## Ⅰ. 개요 및 필요성

도구 레지스트리는 에이전트용 도구 카탈로그임. 에이전트 도구가 증가할수록 하드코딩 방식은 재배포 비용과 권한 관리 부재 문제를 유발하며, 중앙화된 등록·검색·버전관리·권한 검증 체계가 필수적임.

---

## Ⅱ. 구조 및 구성요소

```text
Tool Provider → Registry API → Metadata Store
                                     │
                    ┌────────────────┼────────────────┐
               Semantic Index    Version Manager    ACL Store
                    │                                   │
               Agent Query ──────────────────── Policy Check
```

| 구성요소 | 역할 | 특이사항 |
|:---|:---|:---|
| Metadata Store | 도구 이름·스키마·설명 저장 | OpenAPI 3.0 / MCP JSON Schema |
| Semantic Index | 도구 설명 임베딩 벡터 검색 | 코사인 유사도 Top-5 반환 |
| Version Manager | 도구 버전·호환성 관리 | SemVer, 하위 호환 검증 |
| ACL Store | 도구별 호출 권한·역할 매핑 | RBAC, 도구당 허용 에이전트 목록 |

> 요약: 메타데이터 저장 → 의미 검색 → 버전 관리 → 권한 검증의 4계층 구조로 도구를 관리함.

---

## Ⅲ. 동작원리 및 흐름도

```text
도구 등록(스키마) → 임베딩 색인 → 에이전트 쿼리
→ Top-K 후보 반환 → 권한 검증 → 도구 바인딩·호출
```

| 단계 | 처리 내용 | 검증 기준 |
|:---:|:---|:---|
| 1 | 도구 제공자가 스키마(OpenAPI/MCP) 등록 | 스키마 유효성, 필수 필드 검증 |
| 2 | 설명 텍스트 임베딩·벡터 색인 | 임베딩 차원 768, 색인 지연 <500ms |
| 3 | 에이전트가 자연어로 도구 검색 | Top-5 후보, 유사도 >0.8 필터 |
| 4 | ACL 검증 후 도구 바인딩 | RBAC 통과, 버전 호환 확인 |

> 요약: 스키마 등록 → 벡터 색인 → 의미 검색 → 권한 검증 순서로 도구를 동적 바인딩함.

---

## Ⅳ. 특징

| 구분 | 하드코딩 방식 | 도구 레지스트리 | 수치·판단 포인트 |
|:---|:---|:---|:---|
| 도구 추가 | 코드 수정·재배포 | API 등록만으로 반영 | 배포 시간 30분→0분 |
| 검색 정확도 | 이름 매칭만 | 의미 검색(코사인 유사도) | 검색 정확도 60%→92% |
| 권한 관리 | 없음 | RBAC·ACL 기반 | 비인가 호출률 0% 목표 |

> 요약: 하드코딩 대비 배포 없는 도구 추가·의미 검색·RBAC 권한 관리를 제공함.

---

## Ⅴ. 실무 적용 및 결론

**적용 방안 3개:**
1. MCP 서버에 OpenAPI 3.0 스키마 기반 도구 등록 API를 구축하고 SemVer로 버전 관리
2. 도구 설명을 text-embedding-3-small(768차원)로 임베딩하여 Qdrant 벡터 DB에 색인
3. 도구별 RBAC ACL을 적용하고 호출 로그를 OpenTelemetry Trace에 기록

**결론 (2줄):**
- 기술사 판단: 도구 50개 이하는 전체 목록 주입, 초과 시 의미 검색+Top-K 필터링으로 설계
- 향후 방향: A2A 프로토콜과 연동하여 조직 간 도구 페더레이션 레지스트리로 확장됨
