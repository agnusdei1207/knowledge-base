# 📖 【암기용】 개념 완전 이해

## 한눈에
- **개요**: 에이전트 도구 레지스트리는 AI 에이전트가 호출 가능한 **도구(API·함수·서비스)**의 **스키마·권한·버전·설명**을 중앙에서 관리하는 **카탈로그** 시스템이다. MCP(006 참조)가 도구 호출의 통신 프로토콜이라면, 레지스트리는 "어떤 도구가 있고 어떻게 쓰는가"를 등록·검색·관리하는 저장소다.
- **왜 필요한가**: 에이전트가 수십~수백 개 도구를 사용할 때, 도구를 코드에 하드코딩하면 새 도구 추가마다 에이전트를 재배포해야 하고, 폐기된 도구 호출·권한 없는 도구 호출 위험이 생긴다. 또한 도구 수가 50개를 넘으면 전체 목록을 LLM 컨텍스트에 넣기 어려워, 의미 검색으로 관련 도구만 선별해야 한다.
- **핵심 직관**: 앱스토어와 같다. 개발자가 앱(도구)을 등록하고, 사용자(에이전트)가 검색해서 설치(바인딩)하며, 앱스토어(레지스트리)가 권한·버전·호환성을 관리한다.

## 핵심 용어 정리 (내부에 등장하는 것들)

| 용어/표기 | 의미 | 비유·예 |
|:---|:---|:---|
| 도구 레지스트리(상위 키워드) | 도구의 메타데이터를 중앙 관리하는 카탈로그 | 앱스토어 |
| 스키마(Schema) | 도구의 입력·출력 형식을 정의한 구조 명세(OpenAPI 3.0, MCP JSON Schema) | 주문서 양식 |
| 의미 검색(Semantic Search) | 도구 설명 텍스트를 임베딩 벡터로 변환해 유사도로 검색 | "매출 조회"로 검색하면 `sales_api.get_revenue` 발견 |
| Top-K 필터링 | 유사도 상위 K개만 반환해 컨텍스트 소모를 줄이는 전략 | 검색 결과 상위 5개만 표시 |
| SemVer(Semantic Versioning) | Major.Minor.Patch 버전 체계. Major 변경은 하위 비호환 | v2.0.0은 v1.x와 호환 안 됨 |
| ACL(Access Control List) | 도구별 호출 허용 에이전트·역할 목록 | "결제 API는 결제 에이전트만 허용" |
| 동적 바인딩(Dynamic Binding) | 런타임에 레지스트리에서 도구를 조회해 호출하는 방식(재배포 불필요) | 플러그인 설치 후 재시작 없이 사용 |

## 깊이 이해
- **배경·문제의식**: 에이전트 실패복구(026)가 "도구 호출 실패를 어떻게 복구하는가"를 다루고, 정책 엔진(028)이 "도구 호출을 허용할 것인가"를 판단한다면, 도구 레지스트리는 그 앞 단계인 "어떤 도구를 선택할 것인가"를 관리한다. Function Calling(005)은 LLM이 도구를 호출하는 인터페이스이고, 레지스트리는 그 인터페이스에 바인딩될 도구의 목록·메타데이터를 관리하는 백엔드다.
- **작동 원리(어떻게+왜)**: ① 도구 제공자가 OpenAPI 3.0 또는 MCP JSON Schema로 도구를 등록한다. 이름·설명·입출력 스키마·권한·버전이 메타데이터 저장소에 기록된다. ② 도구 설명 텍스트를 임베딩 모델(예: text-embedding-3-small, 768차원)로 벡터화해 Semantic Index에 색인한다. ③ 에이전트가 자연어로 "매출 데이터 조회"를 요청하면, 코사인 유사도 Top-5를 반환한다. ④ ACL에서 해당 에이전트의 호출 권한을 검증하고, SemVer 호환성을 확인한 뒤 도구를 동적 바인딩한다.
- **비유**: 도서관 목록(OPAC) 시스템과 같다. 책(도구)을 ISBN·제목·저자(스키마)로 등록하고, 대출 가능 여부(ACL)를 확인하며, 개정판(버전)을 관리한다. 도서관이 없으면 서가를 다 돌아다녀야 한다(하드코딩).
- **구체 예시**: MCP 서버에 도구 50개가 등록되어 있다. 에이전트가 "이번 달 매출 조회"를 요청하면, Semantic Index가 `sales_api.get_revenue`(유사도 0.94), `sales_api.get_trend`(0.87), `finance.monthly_report`(0.82)를 Top-3으로 반환한다. ACL 검증에서 에이전트의 역할이 "영업팀 에이전트"로 확인되어 `sales_api.get_revenue`가 허용·바인딩된다.
- **흔한 오해·주의점**: "도구를 많이 등록할수록 에이전트가 똑똑해진다"는 오해다. 도구 수가 많으면 LLM 컨텍스트를 소모해 추론 품질이 떨어지고, 잘못된 도구를 선택할 확률이 높아진다. 전체 목록 주입(50개 이하)과 의미 검색+Top-K(50개 초과)를 규모에 따라 분기해야 한다.

## 연결 개념
- MCP(006) — 도구 등록·호출의 표준 프로토콜. 레지스트리가 관리하는 도구의 통신 규격
- 에이전트 정책 엔진(028) — 레지스트리에서 선택된 도구의 호출 권한·비용을 판정
- Function Calling(005) — LLM이 레지스트리에서 바인딩된 도구를 호출하는 인터페이스

# 📝 【답안용】 시험 답안 템플릿

## Ⅰ. 개요 및 필요성

- 개요: 에이전트용 도구의 스키마·권한·버전을 중앙 관리하는 카탈로그 시스템임
- 배경: 하드코딩 시 도구 추가마다 재배포 필요, 폐기 도구 호출·권한 관리 부재
- 필요성: 도구 50개 이상 운영 시 등록·검색·버전·권한 체계 없이는 검색 정확도 60% 수준에 머묾

---

## Ⅱ. 구조 및 구성요소

```text
도구 제공자 -> Registry API -> Metadata Store(스키마·설명·버전)
                                   |
              Semantic Index(임베딩) / Version Manager(SemVer) / ACL Store(RBAC)
                                   |
              에이전트 쿼리 -> Top-K 반환 -> ACL 검증 -> 동적 바인딩
```

| 구성요소 | 역할 | 특이사항 |
|:---|:---|:---|
| Metadata Store | 도구 이름·스키마·설명 저장 | OpenAPI 3.0 / MCP JSON Schema |
| Semantic Index | 도구 설명 임베딩 벡터 검색 | 코사인 유사도 Top-5 반환 |
| Version Manager | 도구 버전·호환성 관리 | SemVer, Major 변경 시 하위 호환 검증 |
| ACL Store | 도구별 호출 권한·역할 매핑 | RBAC, 에이전트별 허용 도구 목록 |

> 요약: 메타데이터→의미 검색→버전 관리→권한 검증 4계층으로 도구를 중앙 관리함.

---

## Ⅲ. 동작원리 및 흐름도

```text
도구 등록(스키마) -> 임베딩 색인 -> 에이전트 자연어 쿼리
  -> Top-K 후보 반환 -> ACL 권한 검증 -> SemVer 호환 확인 -> 동적 바인딩·호출
```

1. 도구 등록: 제공자가 OpenAPI/MCP 스키마로 도구를 등록하고, 스키마 유효성·필수 필드를 검증함
2. 벡터 색인: 도구 설명 텍스트를 임베딩 모델(768차원)로 벡터화해 Semantic Index에 색인함
3. 의미 검색: 에이전트가 자연어로 도구를 검색하면 코사인 유사도 Top-5를 반환함(유사도 >0.8 필터)
4. 바인딩: ACL에서 에이전트 역할을 확인하고, SemVer 호환성을 검증한 뒤 도구를 동적 바인딩함

> 요약: 스키마 등록→벡터 색인→의미 검색→권한·버전 검증→동적 바인딩 순서로 도구를 연결함.

---

## Ⅳ. 특징

- 동적 바인딩: 도구 추가·변경 시 코드 수정·재배포 없이 API 등록만으로 즉시 반영함
- 의미 검색: 이름 매칭이 아닌 임베딩 유사도로 검색해 검색 정확도가 60%→92%로 향상됨
- RBAC 권한: 도구별 호출 허용 역할을 ACL로 관리해 비인가 호출을 차단함
- SemVer 호환: Major 변경 시 하위 호환 검증을 자동화해 스키마 깨짐을 방지함
- Top-K 제어: 도구 50개 초과 시 전체 목록이 아닌 상위 K개만 컨텍스트에 주입해 토큰을 절약함

## Ⅴ. 심화 비교 및 적용 판단

| 구분 | 하드코딩 방식 | 도구 레지스트리 | 선택 기준 |
|:---|:---|:---|:---|
| 도구 추가 | 코드 수정+재배포(30분) | API 등록 즉시 반영(0분) | 변경 월 5회 이상 시 레지스트리 필수 |
| 검색 정확도 | 이름 매칭(60%) | 의미 검색 Top-5(92%) | 도구 50개 초과 시 의미 검색 필수 |
| 권한 관리 | 전체 허용 | RBAC ACL 도구별 제어 | 민감 API·멀티테넌트 시 필수 |

> 요약: 도구 50개 초과·월 5회 이상 변경·민감 API 포함 시 레지스트리 도입이 필수임.

**리스크·대응:**
- 검색 정확도 저하: 도구 설명 품질 불균일 → 설명 템플릿 표준화+임베딩 정기 재색인 (지표: Top-5 정확도 >90%)
- 스키마 호환 깨짐: Major Breaking Change → SemVer 변경 시 하위 호환 검증 자동화 (지표: 스키마 검증 실패율 <1%)
- 비인가 호출: ACL 미설정·역할 매핑 오류 → 등록 시 RBAC 필수 입력, 주간 권한 감사 (지표: 비인가 호출률 0%)

**도입 후 점검 지표:**
- 도구 검색 정확도: Top-5 정확도 >90% — 테스트 쿼리셋 대비 적중률
- 재배포 없는 추가율: 100% — 도구 추가 시 에이전트 재배포 0회

## Ⅵ. 실무 적용 및 결론

**적용 방안 3개:**
1. MCP 서버에 OpenAPI 3.0 스키마 기반 등록 API를 구축하고 SemVer로 도구 버전을 관리함
2. 도구 설명을 text-embedding-3-small(768차원)로 벡터화해 Qdrant에 색인하고, Top-5 의미 검색을 적용함
3. 도구별 RBAC ACL을 설정하고, 호출 로그를 OpenTelemetry Trace ID로 감사 기록에 연동함

**결론:**
- 기술사 판단: 도구 50개 이하는 전체 목록 주입, 초과 시 의미 검색+Top-K 필터링으로 설계함
- 향후 방향: A2A(012) 프로토콜과 연동해 조직 간 도구 페더레이션 레지스트리로 확장됨
