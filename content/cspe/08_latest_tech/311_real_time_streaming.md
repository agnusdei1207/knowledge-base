# 📖 【암기용】 개념 완전 이해

> 목적: 실시간 스트리밍을 처음 봐도 완벽히 이해하게 만든다. 시험 답안 양식이 아니라, 이해를 위한 친절한 설명이다.

## 한눈에
- **개요**: 데이터가 발생하는 즉시 중단 없이 흐르듯 처리하여 결과를 만들어내는 데이터 처리 방식
- **왜 필요한가**: 과거에는 데이터를 모아서 한꺼번에 처리하는 '배치(Batch)' 방식이었지만, 이제는 사기 결제 탐지나 실시간 내비게이션처럼 1초만 늦어도 가치가 떨어지는 일이 많아졌기 때문이다.
- **핵심 직관**: "데이터를 '저수지'에 모아두고 나중에 푸는 게 아니라, '흐르는 강물'에서 물고기를 낚듯 데이터가 흐를 때 즉시 처리하는 것."

## 깊이 이해
- **배경·문제의식**: 배치는 하루 한 번, 혹은 몇 시간마다 처리하므로 '현재 상태'를 알기 어려움. 또한 데이터 양이 너무 많아지면 배치 작업 시간이 너무 길어져 다음 작업에 영향을 줌.
- **작동 원리**: 데이터가 생성되는 시점(Event Time)과 시스템에 들어오는 시점(Processing Time)을 구분함. 끊임없이 들어오는 무한한 데이터(Unbounded Data)를 '윈도우(Window)'라는 개념으로 잘라서 계산하거나, 상태(State)를 유지하며 누적 계산함.
- **비유**: 편지(배치)와 전화(스트리밍)의 차이. 편지는 다 쓰고 우체통에 넣어 며칠 뒤에 확인하지만, 전화는 상대방의 말이 들리는 즉시 대답하고 반응하는 것과 같음.
- **구체 예시**: 신용카드 결제가 일어나는 순간(스트리밍), 평소 패턴과 다른지 즉시 분석하여 승인 거절을 결정함. 결제 데이터를 모아서 다음 날 분석하면 이미 사고가 터진 뒤임.
- **흔한 오해·주의점**: 무조건 '빠른 것'만은 아님. 스트리밍의 핵심은 '데이터가 끊임없이 들어온다'는 전제로 시스템을 설계하는 것이며, 지연(Latency)과 처리량(Throughput) 사이의 균형이 중요함.

## 연결 개념
- Batch Processing - 데이터를 일정량 모아서 한 번에 처리하는 방식
- Micro-batch - 스트리밍을 구현하기 위해 아주 짧은 주기로 배치를 돌리는 방식 (Spark Streaming)
- Event-Driven Architecture (EDA) - 이벤트(스트리밍 데이터)를 중심으로 시스템이 동작하는 아키텍처

# 📝 【답안용】 시험 답안 템플릿

> 목적: 시험장에서 25분에 그대로 쓰는 답안 양식. 작성방식(추상표현 금지·수치·도식·문제유형 전환)을 엄격히 지킨다.
> 핵심: 무한 데이터(Unbounded Data) 처리 기법, 시간 개념(Event vs Processing Time), 상태 관리(State Management) 및 장애 복원 메커니즘을 강조한다.

## 핵심 인사이트 (3줄 요약)

> 1. **본질**: 실시간 스트리밍은 연속적으로 발생하는 무한한 데이터 흐름(Data Stream)을 지연 없이 즉각적으로 처리하여 비즈니스 가치를 창출하는 데이터 처리 패러다임이다.
> 2. **가치**: 데이터 발생 시점과 처리 시점 사이의 지연(Latency)을 최소화하여 실시간 의사결정(FDS, 이상 탐지 등)과 비즈니스 민첩성을 확보한다.
> 3. **판단 포인트**: 낮은 지연 시간(Latency), 높은 처리량(Throughput), 그리고 데이터 유실 없는 정확한 처리(Exactly-once)를 동시에 달성하는 것이 핵심 기술적 도전 과제이다.

## 출제 의도 및 답안 포인트

| 출제 의도 | 반드시 짚을 핵심 | 감점 회피 포인트 |
|:---|:---|:---|
| 배치 vs 스트리밍 차이점 이해 확인 | Unbounded Data, 시간 개념(Event/Processing Time), 윈도우 | 단순히 "속도가 빠르다"는 식의 결과만 서술 |
| 스트리밍 처리 핵심 기술 및 아키텍처 | 윈도잉(Tumbling/Sliding), 상태 관리, 워터마크 | 구체적인 처리 기법(워터마크 등) 설명 누락 |
| 장애 복구 및 정합성 보장 역량 | Checkpointing, Exactly-once Semantics | 유실 가능성에 대한 대책 언급 미흡 |

> 요약: 실시간 스트리밍은 시간의 흐름에 따라 끊임없이 유입되는 데이터를 상태 기반으로 자율 처리하는 시스템이다.

## Ⅰ. 개요 및 필요성

- 정의: 연속적으로 생성되는 데이터(Stream)를 수집하는 즉시 가공, 분석하여 결과를 산출하는 처리 방식
- 배경: 실시간 반응형 서비스 요구 증대, 데이터 폭증으로 인한 배치 처리 윈도우(Batch Window) 부족 현상
- 필요성: 즉각적 이상 징후 탐지(FDS), 실시간 추천을 통한 매출 증대, 로그/지표 모니터링을 통한 가용성 확보

---

## Ⅱ. 구조 및 구성요소 (스트림 처리 파이프라인)

```text
[ Producer ] ----> [ Stream Storage ] ----> [ Stream Processor ] ----> [ Consumer ]
     |                  |                       |                      |
  로그, IoT          Kafka, Pulsar           Flink, Spark, Storm      DB, App, UI
  (Event 발생)       (버퍼링/저장)            (연산/상태관리)           (결과 소비)
```

| 구성요소 | 역할 | 특이사항 |
|:---|:---|:---|
| Stream Source | 이벤트 데이터를 생성하고 송신 | 센서, 웹 로그, DB 변경(CDC) |
| Message Broker | 데이터 유입 속도와 처리 속도의 차이를 완충 | 분산 메시지 큐 (Kafka 등) |
| Stream Engine | 데이터 필터링, 집계, 조인 등 연산 수행 | 상태(State)를 유지하며 연산 |
| Windowing | 무한한 데이터를 시간/개수 단위로 분할 처리 | Tumbling, Sliding, Session |

> 요약: 발생(Source) -> 완충(Broker) -> 처리(Engine) -> 소비(Sink)의 단계를 거치며 파이프라인이 구성된다.

## Ⅲ. 동작원리 및 흐름도 (시간과 워터마크)

```text
Event 발생 (t1) -> [ Network Delay ] -> [ Ingestion (t2) ] -> [ Processing ]
       |                                       |
  (Event Time)                           (Processing Time)
       |
  [ Watermark (t1-delta) ] -> "이 시간 이전 데이터는 더 이상 안 옴" -> Window 닫기
```

| 단계 | 처리 내용 | 검증 기준 |
|:---:|:---|:---|
| 1 | 이벤트 생성 | 실제 사건이 발생한 시각(Event Time)을 태깅 | - |
| 2 | 데이터 인입 | 네트워크를 거쳐 시스템에 도착한 시각(Processing Time) 기록 | 지연(Skew) 발생 가능 |
| 3 | 워터마크 생성 | 늦게 도착하는 데이터(Lateness)를 기다려주는 기준 시점 설정 | 지연과 정확도의 트레이드오프 |
| 4 | 윈도우 연산 | 지정된 시간 범위 내 데이터 집계 (예: 최근 5분간 평균) | 상태 관리 (State) |
| 5 | 결과 출력 | Exactly-once 보장을 위해 싱크(Sink)와 협업하여 출력 | 정합성 보장 |

> 요약: 이벤트 시각과 시스템 시각의 간극을 워터마크로 관리하며, 무한 데이터를 윈도우 단위로 연산한다.

## Ⅳ. 특징 (처리 기법 및 보장 수준)

| 구분 | 주요 특징 | 상세 내용 |
|:---|:---|:---|
| 시간 개념 | Event Time 처리 | 데이터 발생 순서에 따른 정확한 분석 (순서 뒤바뀜 해결) |
| 윈도잉 기법 | Sliding Window | 겹치는 시간 범위를 지속적으로 업데이트하며 계산 |
| 정합성 보장 | Exactly-once | 장애 발생 시에도 중복이나 누락 없이 정확히 한 번 처리 |
| 상태 관리 | Stateful Processing | 이전 데이터를 기억하여 누적 집계나 패턴 탐색 수행 |

> 요약: 순서 보장(Event Time), 누적 계산(State), 중복 방지(Exactly-once)가 기술적 핵심이다.

## Ⅴ. 심화 비교 및 적용 판단

| 구분 | 배치 처리 (Batch) | 실시간 스트리밍 (Streaming) | 선택 기준 |
|:---|:---|:---|:---|
| 데이터 범위 | 유한함 (Bounded) | 무한함 (Unbounded) | 데이터 발생 형태 |
| 처리 지연 | 수분 ~ 수시간 (High) | 수밀리초 ~ 수초 (Low) | 요구 반응 속도 |
| 처리량 | 매우 높음 (Throughput) | 상대적 낮음 (Latency 중심) | 데이터 부하 및 비용 |
| 복잡도 | 낮음 | 높음 (상태 관리, 장애 복구 필요) | 운영 난이도 |

> 요약: 분석의 '깊이'와 '대량 처리'가 중요하면 배치, '즉시성'과 '흐름'이 중요하면 스트리밍을 선택한다.

| 리스크 | 원인 | 대응 방안 | 확인 지표 |
|:---|:---|:---|:---|
| Backpressure | 처리 속도가 유입 속도를 못 따라감 | 오토스케일링, 브로커 버퍼링, 샘플링 | Consumer Lag, CPU 사용률 |
| Data Skew | 특정 키에 데이터가 몰려 병목 발생 | 솔트(Salt) 추가를 통한 데이터 분산 | 노드별 처리량 편차 |
| Late Data | 네트워크 지연으로 윈도우 마감 후 도착 | 허용 지연 시간(Allowed Lateness) 설정 | 유실된 데이터 비율 |

> 요약: 처리량 한계(Backpressure)와 데이터 편향(Skew)을 제어하는 것이 안정적 운영의 관건이다.

| 점검 항목 | 목표 기준 | 측정 방법 |
|:---|:---|:---|
| End-to-End Latency | 발생부터 결과 도출까지 1초 이내 | 타임스탬프 기반 지연 측정 |
| 가용성 | 99.9% 이상의 무중단 처리 | 장애 복구 시간(MTTR) 측정 |
| 처리 정합성 | 중복/누락 발생 0건 | 데이터 검증(Check-sum) 및 감사 |

> 요약: 도입 효과는 비즈니스 반응 속도의 단축과 데이터 처리의 신뢰성 지표로 평가한다.

## Ⅵ. 실무 적용 및 결론

**적용 방안 3개:**
1. **람다/카파 아키텍처(Lambda/Kappa)**: 배치의 정확성과 스트리밍의 신속성을 보완하거나, 스트리밍만으로 전체를 처리하는 구조로 설계
2. **실시간 이상 탐지(FDS)**: 유입되는 로그를 복잡한 이벤트 처리(CEP) 엔진으로 실시간 패턴 매칭하여 보안 사고 즉시 차단
3. **실시간 대시보드 구현**: WebSocket이나 서버 푸시 기술과 연계하여 사용자에게 지연 없는 데이터 시각화 서비스 제공

**결론 (2줄):**
- 기술사 판단: 실시간 스트리밍은 단순한 '빠른 처리'를 넘어 데이터의 시공간적 맥락을 실시간으로 포착하는 기술이며, 미래 비즈니스의 핵심 경쟁력이다.
- 향후 방향: AI 모델의 실시간 추론(Inference)과 결합하여 데이터 유입 즉시 예측 결과를 반환하는 '지능형 실시간 스트리밍'으로 진화할 전망이다.
