# 📖 【암기용】 개념 완전 이해

> 목적: 가상 스레드를 처음 봐도 완벽히 이해하게 만든다. 시험 답안 양식이 아니라, 이해를 위한 친절한 설명이다.

## 한눈에
- **개요**: OS 스레드와 1:1로 매칭되지 않고, 수백만 개를 동시에 띄울 수 있는 매우 가벼운 사용자 수준 스레드 (Java 21 Project Loom의 결과물)
- **왜 필요한가**: 기존의 OS 스레드(Platform Thread)는 생성 비용이 비싸고 개수 제한이 있다. 서버가 수만 개의 요청을 받으려면 복잡한 비동기 프로그래밍(Reactive)을 해야 했는데, 가상 스레드는 쉬운 동기식 코드로도 고성능을 낼 수 있게 해준다.
- **핵심 직관**: 실제 일꾼(OS 스레드)은 소수지만, 예약용 번호표(가상 스레드)를 수만 개 발행해두고 일꾼이 노는 시간 없이 계속 번호표를 바꿔가며 처리하는 방식이다.

## 깊이 이해
- **배경·문제의식**: Thread-per-request 모델은 직관적이지만 OS 스레드 부족으로 확장성에 한계가 있다. 이를 극복하려고 나온 리액티브 프로그래밍은 코드가 복잡하고 디버깅이 어렵다(Stack trace 추적 곤란).
- **작동 원리**: **M:N 스케줄링**을 사용한다. 수많은 가상 스레드(M)가 소수의 캐리어 스레드(N, OS 스레드) 위에서 실행된다. 가상 스레드가 I/O 작업 등으로 대기(Blocking) 상태가 되면, 런타임이 이를 캐리어 스레드에서 떼어내고(Unmount) 다른 가상 스레드를 올린다(Mount).
- **비유**: 은행 창구(캐리어 스레드)는 4개뿐인데, 손님(가상 스레드)은 1,000명이다. 손님이 서류 작성을 하는 동안(I/O 대기) 창구 직원은 다음 손님을 본다. 손님이 서류를 다 쓰면 다시 비어있는 창구로 가서 업무를 마저 본다.
- **구체 예시**: Java 21에서 `Thread.ofVirtual().start(() -> { ... })`로 생성. 기존 `Thread.sleep()`이나 Blocking I/O를 호출해도 실제 OS 스레드는 멈추지 않고 다른 가상 스레드를 처리한다.
- **흔한 오해·주의점**: CPU 연산 위주의 작업(CPU Bound)에서는 성능 이득이 거의 없다. 오히려 컨텍스트 스위칭 오버헤드만 생길 수 있다. I/O Bound 작업에 최적이다.

## 연결 개념
- Platform Thread — 전통적인 OS 커널 스레드
- Coroutine (Kotlin/Go) — 유사한 경량 스레드 개념 (단, 가상 스레드는 기존 라이브러리 호환성이 높음)
- Project Loom — Java의 가상 스레드 도입 프로젝트 명칭
- Reactive Programming — 비동기 논블로킹 방식 (가상 스레드의 강력한 대안/비교 대상)

# 📝 【답안용】 시험 답안 템플릿

> 목적: 시험장에서 25분에 그대로 쓰는 답안 양식. 작성방식(추상표현 금지·수치·도식·문제유형 전환)을 엄격히 지킨다.
> 핵심: 가상 스레드의 기술적 메커니즘(Mount/Unmount)과 리액티브 프로그래밍 대비 생산성/확장성 우위를 논리적으로 서술한다.

## 핵심 인사이트 (3줄 요약)

> 1. **본질**: 가상 스레드 (Virtual Thread)는 OS 커널 스레드와 분리되어 JVM 내부 스케줄러에 의해 관리되는 수백만 개 생성이 가능한 초경량 실행 단위이다.
> 2. **가치**: Blocking I/O 발생 시 캐리어 스레드를 반납하는 메커니즘을 통해, 코드의 직관성(동기식)과 서버의 고처리량(High Throughput)을 동시에 달성한다.
> 3. **판단 포인트**: Thread-per-request 모델의 확장성 한계와 Reactive 프로그래밍의 복잡성(Callback Hell)을 모두 해결하는 차세대 서버 아키텍처의 핵심이다.

## 출제 의도 및 답안 포인트

| 출제 의도 | 반드시 짚을 핵심 | 감점 회피 포인트 |
|:---|:---|:---|
| 기존 스레드 모델의 한계점 인식 확인 | Thread-per-request의 확장성 한계 (메모리, 생성 비용) | 단순히 "스레드가 많아진다"고만 서술 |
| 가상 스레드 작동 메커니즘 이해 확인 | Carrier Thread, Mount/Unmount, Continuation | JVM 내부 동작 원리 누락 |
| 기술적 트레이드오프 판단 능력 확인 | CPU Bound 작업 시 역효과, ThreadLocal 사용 주의 | 모든 상황에서 빠르다고 주장 (CPU Bound 한계 명시 필요) |

> 요약: I/O 집약적 서버 환경에서 동기식 코드의 생산성과 비동기식 코드의 성능을 결합한 기술이다.

## Ⅰ. 개요 및 필요성

- 정의: 운영체제 스레드와 독립적으로 JVM 수준에서 수천 수만 개를 동시에 실행할 수 있도록 설계된 경량 스레드
- 배경: 기존 플랫폼 스레드는 1개당 1MB~2MB 메모리를 점유하여 동시 접속자 수 증가 시 OOM(Out Of Memory) 리스크 발생
- 필요성: 비동기/리액티브 코드의 높은 학습 곡선 및 디버깅 난해함을 해결하고, 기존 동기식 라이브러리를 그대로 쓰면서 확장성 확보

---

## Ⅱ. 구조 및 구성요소

```text
Virtual Thread 1  Virtual Thread 2  ...  Virtual Thread M
       |                 | (Mount/Unmount)
       +-----------------+-----------------+
                JVM Scheduler (ForkJoinPool)
                         |
           Carrier Thread 1 (OS Thread 1)
           Carrier Thread 2 (OS Thread 2)
```

| 구성요소 | 역할 | 특이사항 |
|:---|:---|:---|
| 가상 스레드 | 실제 로직을 수행하는 경량 단위 | 힙 메모리에 저장, 수백 바이트 수준 점유 |
| 캐리어 스레드 | 가상 스레드를 실제로 실행하는 OS 스레드 | JVM이 관리하는 ForkJoinPool 기반 |
| JVM 스케줄러 | 가상 스레드를 캐리어 스레드에 할당/해제 | FIFO 또는 Work-Stealing 방식 사용 |
| Continuation | 실행 상태(Stack, PC)를 보관하는 객체 | Blocking 시 상태 저장 및 복구의 핵심 |

> 요약: 가상 스레드(M)를 소수의 캐리어 스레드(N)에 매핑하여 실행하는 M:N 구조를 가진다.

---

## Ⅲ. 동작원리 및 흐름도

```text
[동작 흐름: 실행 -> I/O 대기 -> Unmount -> Re-mount -> 완료]
Start -> Mount(to Carrier) -> Execute -> Blocking I/O -> Unmount(Save Stack)
                                               |
Wait(Kernel) <- Event Polling <- Continuation Object (Heap)
                                               |
Wake up -> Ready Queue -> Mount(to any Carrier) -> Resume -> End
```

| 단계 | 처리 내용 | 검증 기준 |
|:---:|:---|:---|
| 1 | 실행(Mount) | 스케줄러가 가상 스레드를 비어있는 캐리어 스레드에 할당 |
| 2 | 차단(Blocking) | `Thread.sleep()`이나 I/O 요청 시 Continuation 저장 |
| 3 | 분리(Unmount) | 캐리어 스레드를 해제하여 다른 가상 스레드가 쓸 수 있게 함 |
| 4 | 복귀(Resume) | I/O 완료 이벤트 수신 시 힙의 데이터를 다시 스택으로 복사 |

> 요약: I/O 대기 시 일꾼(OS 스레드)을 쉬게 하지 않고 즉시 다른 일로 전환하는 것이 핵심이다.

## Ⅳ. 특징

| 구분 | 내용 | 판단 포인트 |
|:---|:---|:---|
| 확장성 | 수백만 개의 동시 실행 가능 (100만 개 이상) | 힙 메모리 크기에만 의존 |
| 생산성 | 기존 명령형(Imperative) 코드 스타일 유지 | `try-catch`, 디버거, 프로파일러 활용 용이 |
| 호환성 | 기존 `java.lang.Thread` API와 완벽 호환 | 기존 라이브러리 수정 없이 성능 향상 |
| 효율성 | I/O Bound 작업에서 처리량(Throughput) 극대화 | Blocking 시 발생하는 OS 컨텍스트 스위칭 제거 |

> 요약: 리액티브 프로그래밍의 대안으로, "동기식 코드로 작성하고 비동기식으로 실행"하는 패러다임을 제공한다.

## Ⅴ. 심화 비교 및 적용 판단

| 비교 축 | Platform Thread (OS) | Reactive (WebFlux) | Virtual Thread |
|:---|:---|:---|:---|
| 프로그래밍 모델 | 동기(Synchronous) | 비동기(Asynchronous) | 동기(Synchronous) |
| 확장성 | 낮음 (스레드 수 제한) | 높음 (이벤트 루프) | 매우 높음 (경량 스레드) |
| 디버깅/유지보수 | 용이 | 매우 어려움 (Stack Trace 소실) | 용이 (기존 툴 사용) |
| 적용 권장 | CPU 집중 작업 | 복잡한 이벤트 체인 | 일반적인 웹/API 서버 |

> 요약: 대규모 I/O 처리가 필요한 웹 애플리케이션에서 생산성과 성능의 최적 균형점이다.

| 리스크 | 원인 | 대응 방안 | 확인 지표 |
|:---|:---|:---|:---|
| Pinning (고정) | `synchronized` 블록 내 Blocking | `ReentrantLock`으로 교체 | JFR(Java Flight Recorder) 피닝 이벤트 |
| CPU Starvation | CPU Bound 작업 과다 점유 | 가상 스레드 대신 플랫폼 스레드 사용 | 캐리어 스레드 CPU 사용률 |
| ThreadLocal 오용 | 무거운 객체 저장 시 메모리 급증 | ThreadLocal 대신 Scoped Value 검토 | Heap 메모리 분석 (MAT) |

> 요약: Pinning 현상 방지를 위해 락 사용 방식을 검토하고, CPU 밀집 작업과의 혼용을 주의해야 한다.

| 점검 항목 | 목표 기준 | 측정 방법 |
|:---|:---|:---|
| 처리량 (TPS) | 기존 모델 대비 2~3배 이상 향상 | JMeter, k6 부하 테스트 |
| 응답 시간 (p99) | Tail Latency 안정화 | APM 모니터링 |
| GC 오버헤드 | 가상 스레드 생성/소멸로 인한 GC 부하 5% 미만 | GC 로그 분석 (G1GC, ZGC) |

> 요약: 처리량 개선 수치와 함께 짧게 자주 발생하는 GC의 영향을 모니터링해야 한다.

## Ⅵ. 실무 적용 및 결론

**적용 방안 3개:**
1. Spring Boot 3.2+ 도입: `spring.threads.virtual.enabled=true` 설정을 통해 톰캣 스레드 풀을 가상 스레드로 전환
2. DB 접근 최적화: Blocking JDBC 드라이버를 쓰더라도 가상 스레드 환경에서 처리량을 극대화하여 RDBMS 효율 향상
3. 마이크로서비스(MSA): 수많은 외부 API 호출이 발생하는 Gateway나 Aggregator 서비스에 적용하여 동시성 처리 능력 강화

**결론 (2줄):**
- 기술사 판단: 가상 스레드는 Java 생태계에서 리액티브 프로그래밍의 복잡성을 제거하고 '단순함의 미학'으로 성능을 잡은 혁신적 모델이다.
- 향후 방향: 가상 스레드와 어울리는 Scoped Value, Structured Concurrency가 안착되면 더 안전하고 효율적인 병렬 프로그래밍이 가능해질 것이다.
