# 📖 【암기용】 개념 완전 이해

> 목적: 스프링(Spring) 백엔드 생태계를 뒤흔든 Java 21의 가장 위대한 혁명. "스레드 고갈"이라는 고질적 병폐를 OS가 아닌 JVM 레벨에서 완벽히 해결한 가상 스레드의 원리를 이해한다.

## 한눈에
- **정의**: 기존의 무거운 운영체제(OS) 스레드에 1:1로 매핑되지 않고, 자바 가상 머신(JVM)이 자체적으로 관리하여 수백만 개를 띄워도 메모리가 터지지 않는 **초경량 사용자 스레드(User-mode Thread)**
- **필요성**: 기존에는 DB나 외부 API의 응답을 기다릴 때(Blocking I/O) 비싼 OS 스레드가 그냥 멍때리며 낭비되었다. 트래픽이 몰리면 스레드가 모자라 서버가 터졌는데, 이를 해결하려면 코드가 지저분해지는 '비동기(Reactive)' 프로그래밍을 해야만 했기 때문
- **핵심 직관**: "창구 직원(OS 스레드)은 10명뿐인데, 손님(요청)이 서류를 작성하는(I/O 대기) 동안 직원이 멍하니 기다리는 게 아니라, 그 손님을 잠시 옆(메모리)으로 밀어두고 즉시 다음 손님의 업무를 처리하게 만드는 마법"

## 깊이 이해
- **배경(왜 등장했나?)**: 백엔드 서버(Tomcat)는 요청 1개당 스레드 1개를 쓴다(Thread-per-request 모델). 근데 OS 스레드는 1개당 메모리를 1MB나 먹고, 1만 개만 만들어도 서버가 뻗는다. 그래서 WebFlux 같은 리액티브(Reactive) 프로그래밍이 유행했지만, "코드가 너무 읽기 어렵고 디버깅은 지옥 같다"며 개발자들이 고통받았다. 이에 Java 진영(Project Loom)이 "그냥 예전처럼 쉽게(동기식으로) 코드 짜! 스레드 관리는 JVM이 알아서 해줄게!"라며 낸 해답이 가상 스레드다.
- **작동 원리(어떻게 달성했나?)**: 
  1. 가상 스레드는 OS 스레드(Carrier Thread) 위에서 실행된다. (M:N 매핑)
  2. 코드 실행 중 DB 응답을 기다려야 하는 `Thread.sleep()`이나 I/O 작업을 만난다.
  3. 옛날 같으면 OS 스레드 통째로 블로킹(대기) 상태에 빠졌겠지만, 가상 스레드는 **자신의 상태(스택)를 JVM 힙(Heap) 메모리에 싹 저장(Unmount)하고 OS 스레드를 놔준다.**
  4. 해방된 OS 스레드는 즉시 다른 가상 스레드를 올려서(Mount) 일한다.
  5. DB 응답이 오면, 힙에 뒀던 가상 스레드를 다시 OS 스레드에 얹어서 남은 코드를 마저 실행한다.
- **일상 비유**: 식당 종업원(OS 스레드)이 고기(CPU 연산)를 구워주다가, 손님이 "화장실 좀 다녀올게요(DB 대기)" 하면 종업원이 그 자리에서 가만히 서서 기다리는 게 아니라(전통적 스레드), 즉시 옆 테이블로 가서 고기를 구워주고(가상 스레드 언마운트), 손님이 돌아오면 다시 구워주는 것이다. 종업원 10명이 테이블 10,000개를 커버할 수 있게 된다.
- **구체 예시**: Spring Boot 3.2부터 `spring.threads.virtual.enabled=true` 옵션 하나만 켜면 톰캣 서버가 가상 스레드로 동작한다. 100명이 한계이던 서버가 코드 수정 1줄도 없이 10,000명의 동시 접속을 버텨낸다.
- **흔한 오해/주의점**: "가상 스레드가 연산 속도(CPU)를 빠르게 해주나?" → 절대 아니다! 가상 스레드는 CPU 연산(수학 계산, 암호화)이 빡센 작업에는 아무 도움이 안 된다. 오직 네트워크나 DB 응답을 '기다리는 시간(I/O Blocking)'이 많을 때 극적인 동시성 향상을 가져온다.

## 연결 개념
- **Project Loom (프로젝트 룸)**: 가상 스레드를 탄생시킨 자바 생태계의 거대한 혁신 프로젝트 이름.
- **Reactive Programming (WebFlux)**: 가상 스레드 등장 이전, 스레드 블로킹 문제를 해결하기 위해 쓰던 비동기 패러다임. (이제 가상 스레드 때문에 입지가 흔들리고 있다.)
- **Goroutine (고루틴)**: Go 언어에서 가상 스레드와 똑같은 개념으로 이미 오래전부터 쓰고 있던 경량 스레드. (드디어 자바가 Go의 장점을 흡수했다.)

# 📝 【답안용】 시험 답안 템플릿

## 핵심 인사이트 (3줄 요약)
> 1. **본질**: 가상 스레드(Virtual Thread)는 Java 21(Project Loom)에 공식 도입된 초경량 User-mode 스레드로, JVM이 OS 스레드(Carrier)와 가상 스레드를 M:N으로 스케줄링하여 관리한다.
> 2. **가치**: 기존 Thread-per-request 모델의 직관적이고 쉬운(동기적) 코딩 방식을 그대로 유지하면서도, 수백만 개의 동시 I/O 처리(높은 처리량, Throughput)를 가능하게 하여 Reactive 프로그래밍의 복잡성을 제거한다.
> 3. **판단 포인트**: Continuation 매커니즘(Mount/Unmount)을 통한 I/O 논블로킹(Non-blocking) 원리를 이해하고, CPU Bound 작업이 아닌 I/O Bound 작업에 적용해야 한다는 아키텍처적 제약을 명확히 인지해야 한다.

## Ⅰ. 개요 및 필요성
- **정의**: 운영체제(OS) 스레드에 1:1로 매핑되지 않고, JVM 레벨에서 자체적으로 스케줄링 및 상태(Context)를 관리하는 매우 가벼운(수십 바이트 수준) 논리적 스레드
- **배경**: 플랫폼 스레드(OS 스레드)는 생성 비용이 비싸고 메모리 점유(통상 1MB 스택)가 커서, 서버 트래픽이 증가할 때 하드웨어 자원이 아닌 '스레드 개수 부족'으로 인한 병목(Thread Exhaustion)이 먼저 발생
- **필요성**: 비동기/리액티브(Reactive) 프로그래밍이 초래한 콜백 지옥(Callback Hell) 및 디버깅/로깅의 어려움을 타파하고, 고전적인 동기(Synchronous) 코드 구조를 유지하며 하드웨어 한계까지 동시성 극대화

## Ⅱ. 가상 스레드의 핵심 동작 메커니즘 (Continuation)
가상 스레드는 I/O 대기(Blocking)가 발생하는 순간, OS 스레드를 점유하지 않고 자신의 스택 정보를 Heap 메모리로 옮긴다(Unmount).

```text
[ JVM Heap Memory ]
  ┌─────────────────┐       ┌─────────────────┐
  │ Virtual Thread A│       │ Virtual Thread B│ (대기 중인 수만 개의 가상 스레드)
  │ (상태: I/O 대기) │       │ (상태: Runnable) │
  └─────────────────┘       └────────┬────────┘
        ▲ (Unmount 시 상태 저장)        │ (Mount 시 상태 복원 및 실행)
────────┼────────────────────────────┼─────────────────────────
        │  [ Carrier Thread (OS Thread 1) ]  ◀ JVM ForkJoinPool 관리
        ▼
   (A가 DB 응답을 기다릴 때, OS Thread는 즉시 B를 할당받아 연산 수행)
```

1. **Carrier Thread**: 가상 스레드를 싣고 달리는 실제 플랫폼(OS) 스레드.
2. **Mount**: 가상 스레드가 Carrier Thread에 적재되어 CPU 연산을 수행하는 상태.
3. **Unmount (Continuation)**: I/O Blocking이 호출되면(예: DB 조회), 가상 스레드는 스택 프레임을 Heap에 복사(저장)하고 Carrier Thread를 양보(Yield)함.

## Ⅲ. 기존 방식과의 동시성 처리 모델 비교
| 구분 | Thread-per-request (전통적 방식) | Reactive (비동기 콜백/WebFlux) | Virtual Thread (Java 21) |
|:---|:---|:---|:---|
| **코드 스타일** | 동기식 (작성/읽기 쉬움) | 비동기 함수형 (작성/디버깅 지옥) | **동기식 (작성/읽기 쉬움)** |
| **I/O 대기 시** | OS 스레드 멈춤 (블로킹) | OS 스레드 반환 (논블로킹) | **OS 스레드 반환 (JVM 레벨 논블로킹)** |
| **스레드 개수** | 최대 수천 개 한계 | 소수의 스레드만 사용 | **수백만 개 무제한 생성 가능** |
| **메모리 점유** | 스레드당 1MB 스택 강제 할당 | 적음 | **동적 스택 할당 (수백 바이트 가능)** |

## Ⅳ. 기술적 한계 (Pinning 현상) 및 주의사항
가상 스레드가 만능은 아니며, 특정 상황에서는 기존 OS 스레드처럼 꼼짝없이 블로킹되는 **Pinning(고정)** 현상이 발생할 수 있다.

| 리스크 요인 | 현상 및 문제점 | 대응 방안 (엔지니어링 가이드) |
|:---|:---|:---|
| **`synchronized` 블록 사용** | `synchronized` 내부에서 I/O가 발생하면, 가상 스레드가 Carrier Thread에서 Unmount 되지 못하고 OS 스레드를 통째로 블로킹해 버림 | `synchronized` 대신 **`ReentrantLock`**을 사용하도록 레거시 코드를 전면 리팩토링 |
| **CPU Bound 작업** | 암호화 연산, 동영상 인코딩 등 CPU를 100% 쓰는 작업은 I/O 대기가 없어 Unmount가 발생하지 않음 | 가상 스레드는 **I/O Bound 작업에만 사용**하고, 연산 집약적 작업은 별도의 전통적 플랫폼 스레드 풀에 위임 |

## Ⅴ. 클라우드 네이티브 아키텍처에 미치는 영향
- **마이크로서비스(MSA)의 효율 극대화**: MSA 환경에서는 서비스 간 REST API 통신(네트워크 I/O)이 극심하게 발생한다. 가상 스레드는 이러한 '연쇄적인 네트워크 대기' 상황에서 서버의 리소스 낭비를 제로(0)에 가깝게 만든다.
- **Spring Boot 3.x의 패러다임 시프트**: 비동기 처리를 위해 억지로 도입했던 Spring WebFlux 인프라가 다시 Spring MVC(동기) 기반의 가상 스레드 아키텍처로 대거 회귀(Migration)하는 현상이 엔터프라이즈 시장에서 나타나고 있다.

## Ⅵ. 실무 적용 및 결론
**적용 방안 및 실무 가이드:**
1. **Thread Pool의 폐기**: 가상 스레드는 생성 비용이 0에 가깝기 때문에, 스레드를 미리 만들어두는 '스레드 풀(Thread Pool)' 패턴을 사용하면 안 된다. 요청이 올 때마다 새로 만들고(`Executors.newVirtualThreadPerTaskExecutor()`) 버리는 것이 올바른 사용법이다.
2. **ThreadLocal 남용 금지**: 가상 스레드를 100만 개 띄울 때 무거운 `ThreadLocal` 객체를 담아두면 Heap 메모리가 폭발할 수 있으므로, Java 21에 함께 도입된 **Scoped Values** 메커니즘으로 대체해야 한다.

**결론:**
- 가상 스레드는 자바 역사상 가장 위대한 "동기식 코드의 우아함과 비동기식 처리의 성능"을 동시에 달성한 패러다임 시프트이다.
- I/O 기반의 현대 웹 애플리케이션에서 서버의 하드웨어 리소스를 한계치까지 착취할 수 있게 해주며, 리액티브 프로그래밍의 복잡성이라는 무거운 짐을 개발자의 어깨에서 덜어주었다.
