# 📖 【암기용】 개념 완전 이해

> 목적: DevSecOps를 처음 봐도 완벽히 이해하게 만든다. 시험 답안 양식이 아니라, 이해를 위한 친절한 설명이다.

## 한눈에
- **개요**: 소프트웨어 개발(Dev)과 운영(Ops)에 보안(Sec)을 **처음부터(Shift-Left)** 결합하여, 개발 전 과정에 보안이 자동으로 녹아들게 만드는 문화와 기술
- **왜 필요한가**: 예전에는 개발 다 끝나고 배포 직전에 보안 검사를 했다. 그러면 뒤늦게 발견된 보안 취약점 때문에 출시가 늦어지거나, 아예 처음부터 다시 만들어야 하는 비효율이 발생했다. 보안을 '나중에 하는 숙제'가 아니라 '매일 하는 루틴'으로 만들어야 한다.
- **핵심 직관**: 보안의 **좌측 이동 (Shift-Left Security)**과 **자동화된 가드레일**이다.

## 깊이 이해
- **배경·문제의식**: 배포 속도가 하루에도 수십 번씩 일어나는 현대적 환경에서 수동 보안 점검은 병목(Bottleneck)이 된다. 보안 팀이 "안 돼요"라고만 하는 방해꾼이 아니라, 개발자가 스스로 보안을 지킬 수 있게 돕는 조력자가 되어야 한다.
- **작동 원리**: CI/CD 파이프라인 곳곳에 보안 검사 도구를 심는다. 코드를 짤 때(SAST), 라이브러리를 가져올 때(SCA), 빌드할 때, 실행할 때(DAST) 각각 자동으로 검사해서 문제가 있으면 바로 개발자에게 알린다.
- **비유**: 자동차 공장과 같다.
    - 예전 방식: 차를 다 만든 후 마지막에 브레이크가 잘 듣는지 검사함. 안 들으면 차를 다 뜯어내야 함.
    - DevSecOps 방식: 부품을 가져올 때부터 검사하고, 조립할 때마다 센서가 제대로 달렸는지 실시간으로 확인하며 차를 만듦. 마지막엔 가볍게 최종 확인만 하면 됨.
- **구체 예시**: 개발자가 코드를 Push하면 GitHub Actions에서 SonarQube(코드 분석)와 Snyk(라이브러리 분석)가 자동으로 돌아가서 보안 취약점이 있으면 Merge를 막는 환경.
- **흔한 오해·주의점**: 단순히 "보안 툴을 많이 쓰는 것"이 아니다. 보안이 개발의 흐름을 방해하지 않고 **자연스럽게 스며들도록 하는 문화**와 **자동화**가 핵심이다.

## 연결 개념
- Shift-Left Security — 보안 검사 시점을 개발 초기(왼쪽)로 당기는 것
- SAST / DAST — 정적/동적 애플리케이션 보안 테스트
- SCA (Software Composition Analysis) — 오픈소스 라이브러리 취약점 분석
- IaC Security — 인프라 설정 코드(Terraform 등)의 보안성 검사

# 📝 【답안용】 시험 답안 템플릿

> 목적: 시험장에서 25분에 그대로 쓰는 답안 양식. 작성방식(추상표현 금지·수치·도식·문제유형 전환)을 엄격히 지킨다.
> 핵심: 보안의 좌측 이동(Shift-Left)과 CI/CD 파이프라인 내의 자동화된 보안 도구 체계(Toolchain)를 중심으로 서술한다.

## 핵심 인사이트 (3줄 요약)

> 1. **본질**: DevSecOps는 소프트웨어 개발 생명주기(SDLC) 전 과정에 보안을 통합하여 '보안이 곧 품질'이라는 인식을 실천하는 문화이자 자동화된 운영 체계이다.
> 2. **가치**: 보안 점검의 좌측 이동(Shift-Left)을 통해 취약점 발견 및 조치 비용을 획기적으로 절감하고, 출시 속도(Velocity)와 안전성(Security)을 동시에 확보한다.
> 3. **판단 포인트**: 보안 전문가의 수동 점검 대신, CI/CD 파이프라인 내에 자동화된 보안 가드레일을 구축하여 개발자 스스로 보안을 통제하게 하는 것이 핵심이다.

## 출제 의도 및 답안 포인트

| 출제 의도 | 반드시 짚을 핵심 | 감점 회피 포인트 |
|:---|:---|:---|
| DevSecOps의 핵심 철학 이해 확인 | Shift-Left, 가드레일, 공유된 책임 (Shared Responsibility) | 단순히 "보안 자동화"로만 서술 |
| 단계별 보안 도구 체계(Toolchain) 확인 | SAST, DAST, SCA, IAST, RASP | 도구의 명칭만 나열하고 역할 누락 |
| 도입 효과 및 거버넌스 관점 확인 | 출시 속도 향상, 보안 사고 비용 절감, 컴플라이언스 준수 | 기술적 측면만 강조 (비즈니스 가치 누락) |

> 요약: 개발-보안-운영 간의 장벽을 허물고 전체 프로세스에 보안을 내재화하는 기술적/문화적 방안을 기술한다.

---

## Ⅰ. 개요 및 필요성

- 정의: 개발(Development), 보안(Security), 운영(Operations)을 통합하여 SDLC 전 단계에 걸쳐 보안 활동을 자동화하고 내재화하는 방법론
- 배경: 고속 배포 환경에서 전통적인 사후 보안 점검 방식의 병목 현상 심화 및 오픈소스 활용 증가에 따른 공급망 보안 리스크 급증
- 필요성: 취약점 조기 발견을 통한 비용 절감, 보안 거버넌스 자동화, 지속적인 보안 태세(Continuous Security Posture) 유지

---

## Ⅱ. 구조 및 구성요소

```text
[ SDLC & DevSecOps Toolchain ]
  - Plan: 보안 위협 모델링 (Threat Modeling)
  - Code: 정적 분석 (SAST), 라이브러리 분석 (SCA)
  - Build: 컨테이너 이미지 스캔, IaC 보안 검사
  - Test: 동적 분석 (DAST), 대화형 분석 (IAST)
  - Release/Operate: 런타임 보호 (RASP), 보안 모니터링
```

| 구성요소 | 역할 | 특이사항 |
|:---|:---|:---|
| SAST | 소스 코드 수준의 보안 약점 분석 (정적) | 개발 초기 단계 적용 |
| SCA | 오픈소스 라이브러리의 취약점 및 라이선스 검사 | 공급망 보안의 핵심 |
| DAST | 실행 중인 앱의 취약점 분석 (동적/블랙박스) | 런타임 취약점(SQLi, XSS 등) 탐지 |
| RASP | 앱 내부에서 실시간 공격을 탐지 및 차단 | 자체 방어 메커니즘 |

> 요약: 개발 계획부터 운영 모니터링까지 전 단계에 걸쳐 특화된 보안 도구가 배치된 구조다.

---

## Ⅲ. 동작원리 및 흐름도

```text
[동작 흐름: 코드 커밋 -> 자동 검사 -> 피드백 -> 배포 승인]
IDE (Lint) -> Commit -> CI Pipeline (SAST/SCA) -> Artifact (Image Scan)
                                |                      |
      (Fail: 배포 차단) <--- [취약점 발견] ---------- [취약점 없음] ---> Deploy
```

| 단계 | 처리 내용 | 검증 기준 |
|:---:|:---|:---|
| 1 | 코딩 단계 | IDE 내 보안 플러그인을 통해 실시간으로 보안 가이드를 개발자에게 제시 |
| 2 | 파이프라인 검사 | 소스 코드 푸시 시 SAST와 SCA가 자동 실행되어 CVE 취약점 유무 판단 |
| 3 | 이미지 검사 | 빌드된 컨테이너 이미지 내의 OS 및 미들웨어 취약점을 스캔하여 저장소 등록 전 차단 |
| 4 | 배포 및 감시 | 운영 환경 배포 후 DAST 및 실시간 모니터링을 통해 미탐된 위협 상시 감시 |

> 요약: 보안 검사를 '게이트(Gate)'로 활용하여 기준 미달 시 자동으로 배포를 차단하는 원리다.

## Ⅳ. 특징

| 구분 | 내용 | 판단 포인트 |
|:---|:---|:---|
| 좌측 이동 (Shift-Left) | 보안 활동을 개발 초기 단계로 전진 배치 | 수정 비용의 기하급수적 절감 |
| 자동화 (Automation) | 수동 점검을 배제하고 CI/CD 파이프라인에 통합 | 휴먼 에러 제거 및 속도 확보 |
| 공유된 책임 | 보안은 보안팀만의 업무가 아닌 전 조직의 공동 책임 | 문화적 혁신 |
| 지속적 모니터링 | 배포 후에도 실시간 위협을 탐지하고 즉각 대응 | 피드백 루프 완성 |

> 요약: 보안의 '민첩성'과 '정확성'을 확보하여 보안이 비즈니스의 조력자가 되게 하는 특징을 가진다.

## Ⅴ. 심화 비교 및 적용 판단

| 비교 축 | 전통적 보안 (Water-fall) | DevSecOps (Agile) |
|:---|:---|:---|
| 점검 시점 | 개발 완료 후 배포 직전 | 개발 전 과정 (Continuous) |
| 점검 방식 | 보안 팀에 의한 수동 전수 검사 | 툴에 의한 자동화된 가드레일 |
| 개발 영향 | 출시 지연 및 병목 발생 | 자연스러운 흐름 내 보안 확보 |
| 주안점 | 컴플라이언스 충족 (Check-list) | 실질적 리스크 대응 및 신속한 조치 |

> 요약: 속도가 생명인 클라우드 네이티브 환경에서는 DevSecOps 외에는 대안이 없다.

| 리스크 | 원인 | 대응 방안 | 확인 지표 |
|:---|:---|:---|:---|
| False Positive | 오탐으로 인한 개발 흐름 방해 및 피로도 증가 | 룰셋 최적화 및 예외 처리 정책 수립 | 오탐률(False Positive Rate) |
| 개발 속도 저하 | 무거운 보안 툴 실행으로 파이프라인 지연 | 증분 스캔 및 비동기 스캔 방식 도입 | 파이프라인 소요 시간 |
| 도구 사일로 | 보안 툴의 파편화로 통합 관리 어려움 | ASOC(Application Security Orchestration) 도입 | 취약점 통합 관리 및 조치율 |

> 요약: '오탐 관리'와 '파이프라인 속도 유지'가 개발자의 수용성을 결정하는 핵심 요인이다.

| 점검 항목 | 목표 기준 | 측정 방법 |
|:---|:---|:---|
| 취약점 조치 시간 | 발견 후 24시간 이내 (Critical 기준) | 티켓 생성~완료 시간 측정 |
| 보안 게이트 통과율 | 전체 빌드 중 보안 기준 미달로 차단된 비율 | CI/CD 성공/실패 로그 분석 |
| 평균 조치 비용 | 사후 발견 시 대비 사전 조치 시 비용 절감률 | 수정 공수 데이터 비교 |

> 요약: 단순히 '검사'하는 것보다 '얼마나 빨리 고치는가'를 핵심 지표로 관리해야 한다.

## Ⅵ. 실무 적용 및 결론

**적용 방안 3개:**
1. 보안 가드레일 설정: 고위험 취약점(CVSS 7.0 이상) 발견 시 빌드를 자동 실패 처리하는 규정 적용
2. SBOM(Software Bill of Materials) 연계: SCA 도구를 통해 소프트웨어 자재 명세서를 자동 생성하여 공급망 투명성 확보
3. 보안 챔피언 제도: 개발팀 내에 보안 지식을 갖춘 '챔피언'을 육성하여 실시간 보안 가이드 및 소통 강화

**결론 (2줄):**
- 기술사 판단: DevSecOps는 보안을 '통제'가 아닌 '자동화된 서비스'로 전환하여 비즈니스의 안전한 성장을 지원하는 필수 전략이다.
- 향후 방향: AI를 활용하여 오탐을 줄이고 자동으로 코드를 수정해주는 'AI 기반 자동 치료(Self-healing)' 보안으로 진화할 것이다.
