# 📖 【암기용】 개념 완전 이해

> 목적: "출시 하루 전날, 보안팀이 빠꾸를 놨다!"라는 개발자의 가장 큰 악몽을 피하기 위해, 보안 검사를 파이프라인 극초반(왼쪽)으로 확 당겨버리는 'Shift-Left' 보안 철학을 이해한다.

## 한눈에
- **정의**: 소프트웨어 개발(Dev)과 운영(Ops)의 전체 라이프사이클에 **보안(Sec)을 내재화(Built-in)**하여, 안전한 소프트웨어를 빠르고 지속적으로 배포하는 문화이자 프랙티스
- **필요성**: DevOps로 하루에 10번씩 배포하는데, 옛날처럼 한 달짜리 코드를 다 짜놓고 마지막에 보안팀이 수동으로 엑셀 파일 들고 와서 점검하면 배포 속도가 박살나기 때문
- **핵심 직관**: "공항 출국심사. 예전엔 비행기 타기 직전(배포 직전)에만 짐 검사를 해서 걸리면 집으로 쫓겨났다. DevSecOps는 공항 입구(코딩), 티켓 발권(빌드), 면세점(테스트) 곳곳에 자동 엑스레이를 설치해서 폭발물이 애초에 비행기 근처에도 못 오게 막는 것."

## 깊이 이해
- **배경(왜 등장했나?)**: 클라우드 시대에는 오픈소스 라이브러리(npm, maven)를 엄청나게 가져다 쓴다. (최근 Log4j 사태 등). 이런 상황에서 전통적인 '출시 직전 모의해킹' 방식은 이미 늦다. "보안은 보안팀의 전유물이 아니라, 코드를 짜는 개발자부터 책임져야 한다!"라는 움직임이 시작되었고, 이를 자동화로 풀어낸 것이 DevSecOps다.
- **작동 원리 (Shift-Left 철학)**: 개발 파이프라인(왼쪽 ➔ 오른쪽)에서 보안 검사를 최대한 '왼쪽(초기)'으로 이동시킨다.
  1. **코딩(IDE)**: 개발자가 코드를 치는 순간 플러그인이 "이거 SQL 인젝션 취약점 있음!" 하고 빨간 줄을 긋는다.
  2. **빌드(CI)**: Git에 코드를 올리면 파이프라인이 돌면서 오픈소스 라이브러리의 해킹 취약점 유무를 자동 스캔한다(SCA).
  3. **테스트**: 앱을 띄워놓고 자동화된 해킹 툴이 무차별 공격을 날려본다(DAST).
  4. **운영(CD)**: 컨테이너 이미지에 악성코드가 없는지 검사하고(Image Scan), 런타임 방화벽(WAF)이 작동한다.
- **일상 비유**: 자동차 공장. 옛날에는 차를 다 조립하고 나서 마지막에 브레이크가 안 듣는 걸 발견했다(전부 다 뜯고 재조립). 지금은 나사를 조일 때마다 로봇이 브레이크 센서를 스캔한다. 불량품은 다음 라인으로 아예 넘어가지 못한다.
- **구체 예시**: GitHub에 AWS 접속 비밀번호가 적힌 코드를 실수로 Commit & Push 하려 하면, 사전에 설치된 'git-secrets' 같은 도구가 이를 감지하고 "이봐! 비밀번호가 들어있어!"라며 Push 자체를 강제로 막아버린다.
- **흔한 오해/주의점**: "보안 검사를 많이 넣으면 배포가 느려지지 않나?" → 오히려 그 반대다! 마지막에 발견해서 아키텍처를 뒤엎는 비용보다, 코딩 단계에서 발견해서 1분 만에 수정하는 것이 전체 출시 기간(Time-to-Market)을 훨씬 단축시킨다.

## 연결 개념
- **Shift-Left (시프트 레프트)**: DevSecOps를 관통하는 단 하나의 핵심 철학. 보안의 위치를 파이프라인 '왼쪽(초기)'으로 옮겨라.
- **SAST (정적 분석) / DAST (동적 분석)**: 파이프라인에서 코드를 분석(SAST)하거나 실제 실행된 앱을 공격(DAST)하는 자동화 보안 스캐너 기술.
- **SCA (소프트웨어 구성 분석)**: "내가 가져다 쓴 오픈소스에 해커가 백도어를 심어놨는가?"를 검사하는 도구. 현대 보안의 가장 중요한 영역.

# 📝 【답안용】 시험 답안 템플릿

## 핵심 인사이트 (3줄 요약)
> 1. **본질**: DevSecOps는 DevOps 파이프라인의 전 주기에 걸쳐 보안(Security)을 내재화(Built-in)하여, 개발의 민첩성(Agility)을 훼손하지 않으면서 보안성을 극대화하는 문화와 기술의 결합이다.
> 2. **가치**: 보안 검사를 소프트웨어 생명주기(SDLC)의 극초반으로 당기는 'Shift-Left' 전략을 통해, 보안 취약점의 발견 및 조치 비용을 기하급수적으로 절감한다.
> 3. **판단 포인트**: 기존 '경계형 보안(Perimeter Security)'의 한계를 지적하고, CI/CD 파이프라인 각 단계(Plan-Code-Build-Test-Release)에 매핑되는 자동화 보안 기술(SAST, DAST, SCA)을 체계적으로 제시해야 한다.

## Ⅰ. 개요 및 필요성
- **정의**: 애플리케이션 보안 원칙과 프랙티스를 개발(Dev)과 운영(Ops)의 전체 가치 사슬(Value Chain)에 매끄럽게 통합하는 파이프라인 아키텍처
- **배경**: 클라우드 인프라(IaC), 컨테이너, 오픈소스 사용의 폭발적 증가. 출시 마지막 단계(Post-development)에 수행되는 전통적 보안 감사의 병목 현상 발생
- **필요성**: 제로 트러스트(Zero Trust) 기반의 보안 강화, 오픈소스 공급망 공격(Supply Chain Attack) 선제 대응, 보안 결함 수정 비용(Rework Cost)의 최소화

## Ⅱ. DevSecOps의 핵심 철학: Shift-Left 전략
소프트웨어 결함은 늦게 발견될수록 수정 비용이 기하급수적으로 증가한다(Boehm의 법칙).
- **개념**: 개발 프로세스의 오른쪽(배포/운영)에 집중되어 있던 보안 검사(Security Testing)를 왼쪽(기획/코딩/빌드) 단계로 이동시키는 전략.
- **효과**: 개발자는 자신이 작성한 코드의 보안 결함을 즉각적으로 인지하고(피드백 루프 단축), 보안팀은 병목 지시자가 아닌 '자동화 도구 및 정책 제공자'로 역할이 전환된다.

## Ⅲ. CI/CD 파이프라인 단계별 보안 통합 기술 요소
DevSecOps는 파이프라인이 다음 단계로 넘어가는 'Gate' 역할을 수행한다.

| 개발 수명주기(SDLC) | 보안 활동 및 기술 요소 | 주요 점검 내용 |
|:---|:---|:---|
| **1. Code (코딩)** | **IDE Plug-in, Pre-commit Hook** | 하드코딩된 Secret(비밀번호, 토큰) 차단, 시큐어 코딩 규칙 실시간 검사 |
| **2. Build (빌드)** | **SAST** (정적 코드 분석)<br>**SCA** (소프트웨어 구성 분석) | 소스 코드 내부의 문법적 취약점(SQLi 등) 검출<br>오픈소스 라이브러리의 알려진 취약점(CVE) 스캔 |
| **3. Test (테스트)**| **DAST** (동적 애플리케이션 분석)<br>**IAST** (대화형 애플리케이션 분석) | 컴파일되어 실행 중인 웹 애플리케이션에 외부에서 모의 공격을 주입하여 런타임 취약점 점검 |
| **4. Deploy (배포)**| **Container Image Scan**<br>**IaC Scan** (Terraform 등) | 도커 이미지 내부의 악성코드 검사<br>인프라 코드의 보안 설정(예: S3 Public 오픈) 오류 검증 |
| **5. Run (운영)** | **CSPM** (클라우드 보안 형상 관리)<br>**RASP** (런타임 자가 방어) | 클라우드 환경의 컴플라이언스 모니터링 및 애플리케이션 내부에서 발생하는 비정상 공격 실시간 차단 |

## Ⅳ. DevSecOps 구축을 위한 핵심 프랙티스
1. **Policy as Code (코드로 관리되는 정책)**
   - 보안 규정 문서화(Excel)를 폐기하고, OPA(Open Policy Agent) 등을 활용하여 보안 정책을 '코드화'한다. 인프라 배포 시 이 코드가 자동으로 위반 사항을 차단한다.
2. **소프트웨어 자재 명세서 (SBOM - Software Bill of Materials)**
   - 앱을 만들 때 사용된 수백 개의 오픈소스 라이브러리 목록, 버전, 라이선스를 문서화한 파일. Log4j 같은 제로데이 취약점 터졌을 때 "우리 시스템 어디에 Log4j가 쓰이고 있나?"를 1초 만에 파악하는 근간이 된다.

## Ⅴ. 기술적 한계(리스크) 및 해결 방안
| 리스크 요인 | 현상 및 문제점 | 대응 방안 (엔지니어링 가이드) |
|:---|:---|:---|
| **과도한 오탐(False Positive)** | SAST 스캐너가 문제없는 코드까지 취약점으로 잡아내어 CI 파이프라인이 계속 실패하고 개발자들의 피로도(Alert Fatigue) 극심화 | **보안 게이트의 점진적 강화**: 초기에는 Critical 등급에만 파이프라인 차단(Break)을 걸고, 점진적으로 임계치를 조정하며 예외(Ignore) 룰을 정교화 |
| **개발팀의 보안 거부감**| "개발 일정도 바쁜데 보안까지 책임지라고?"라는 개발자와 보안 조직 간의 사일로(Silo) 발생 | 각 개발팀 내에 보안에 관심 있는 엔지니어를 **'Security Champion'**으로 지정하여, 보안팀과 개발팀 간의 가교 및 멘토 역할 수행 |

## Ⅵ. 실무 적용 및 결론
**적용 방안 및 실무 가이드:**
1. **CI/CD 파이프라인 통합 보드 구축**: Jenkins나 GitLab CI 파이프라인 결과에 SonarQube(SAST) 및 Trivy(Image Scan) 결과를 연동시켜, 보안 결함 통과 여부를 PR(Pull Request) Merge의 필수 조건으로 설정한다.
2. **보안 지표의 가시화**: 해결된 취약점 수, 평균 조치 시간(MTTR)을 대시보드로 만들어 개발 조직의 보안 기여도를 정량적으로 평가할 수 있게 한다.

**결론:**
- DevSecOps는 단순히 툴을 사는 것이 아니라, **"보안은 나중에 누군가 해주는 것이 아니라 모두의 책임(Security is Everyone's Job)"**이라는 조직 문화의 근본적 변화다.
- 클라우드 네이티브의 속도(Speed)라는 무기가 스스로의 발등을 찍지 않도록, 파이프라인 자체를 견고한 보안의 요새로 만드는 현대 IT 환경의 가장 필수적인 생존 전략이다.

### 🔀 문제 유형별 목차 전환
| 문제 유형 | 문제 신호어 | Ⅱ·Ⅲ 강조 (Shift-Left/파이프라인) | Ⅳ·Ⅴ 강조 (실천/오탐 관리) |
|:---|:---|:---|:---|
| **보안 아키텍처/프로세스형**| "보안 내재화", "Shift-Left" | Shift-Left의 비용 절감 곡선 논리 및 파이프라인 단계별 보안 솔루션(SAST, DAST, SCA) 1:1 매핑 표 전면 배치 | 오탐(False Positive)으로 인한 파이프라인 지연(Bottleneck) 해결 전략 부각 |
| **소프트웨어 공급망 보안형**| "오픈소스 보안", "Log4j" | SCA(Software Composition Analysis) 도구의 원리 중심 서술 | Ⅳ SBOM의 필수성과 Policy as Code를 통한 인프라(IaC) 보안 통제 아키텍처 집중 조명 |
