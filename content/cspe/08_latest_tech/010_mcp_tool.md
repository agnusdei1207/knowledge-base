# 📖 【암기용】 개념 완전 이해

## 한눈에
- **개요**: **MCP 툴**(MCP Tool)은 MCP 서버가 노출하는 3대 프리미티브 중 **모델이 호출해 실제 동작을 일으키는 실행 가능 함수**이다(파일 쓰기·API 호출·DB 갱신 등 부작용 동반).
- **왜 필요한가**: 모델이 세상을 읽기만 해서는 일을 끝낼 수 없다. 툴은 "읽기"에 그치는 리소스(009)와 달리 상태를 바꾸는 행위를 표준 규격으로 안전하게 노출한다.
- **핵심 직관**: 도서관에서 책을 읽는 것이 리소스라면, 툴은 "책을 새로 쓰거나 대출 기록을 바꾸는" 행위 버튼이다. 결과가 남으므로 함부로 눌러선 안 되고 승인·권한이 따른다.

## 핵심 용어 정리 (내부에 등장하는 것들)
답안 본문에 등장하는 용어를 처음 보는 사람도 이해하도록 비유와 함께 먼저 정리한다.

| 용어/표기 | 의미 | 비유·예 |
|:---|:---|:---|
| MCP 툴(핵심) | 서버가 노출하는 실행 가능 함수(부작용 있음) | 누르면 일이 벌어지는 "기능 버튼" |
| 3대 프리미티브 | 툴(실행)·리소스(읽기)·프롬프트(템플릿) | 기능 버튼/자료/서식 (006·009 참조) |
| 부작용(Side Effect) | 외부 상태를 실제로 바꾸는 성질 | 송금·삭제처럼 되돌리기 어려운 행위 |
| Input Schema | 툴 인자 구조·타입을 규정한 JSON Schema | 버튼의 "입력 양식" |
| tools/list · tools/call | 툴 목록 조회 / 툴 실행 두 요청 | 메뉴판 보기 / 주문하기 |
| 모델 제어(Model-controlled) | 툴 호출 여부를 모델이 판단 | AI가 "이 버튼을 누를지" 결정 |
| annotations | readOnly·destructive 등 툴 위험 힌트 | 버튼에 붙은 "위험" 라벨 |
| HITL | 고위험 실행 전 사람이 승인 (Human-in-the-Loop) | 결재 승인 단계 |
| 멱등성(Idempotency) | 같은 호출을 반복해도 결과가 같은 성질 | 여러 번 눌러도 한 번만 반영 |
| isError | 툴 실행 결과의 오류 여부 플래그 | "실패" 표시등 |

## 깊이 이해
- **배경·문제의식**: MCP 전체 구조·프리미티브 개념은 006, 읽기 전용 리소스는 009에서 다룬다. 툴 관점의 문제는 "모델이 외부에 실제 영향을 주려면(메일 발송·결제) 실행 권한이 필요한데, 이 위험 동작을 어떻게 표준화하고 통제하는가"이다.
- **작동 원리(어떻게+왜)**: 서버는 각 툴을 이름·설명·Input Schema(JSON Schema)로 선언한다. 모델이 `tools/list`로 목록을 발견하고, 인자를 채워 `tools/call`로 실행을 요청하면, 서버가 인자를 검증·실행하고 결과(콘텐츠+isError)를 반환한다. 호출 여부를 모델이 판단(Model-controlled)하므로 위험 툴에는 annotations·HITL 승인을 결합한다.
- **비유**: 리소스가 "읽기 전용 열람실"이라면 툴은 "실행 버튼이 달린 조작 패널"이다. 송금 버튼은 누르는 순간 되돌리기 어려우므로 확인 팝업(승인)과 권한 검사가 필수다.
- **구체 예시(실제 사례)**: GitHub MCP 서버의 `create_issue` 툴은 `{title, body}`를 받아 실제 이슈를 생성한다. 모델이 자연어 요청을 이 툴 호출로 변환하면 서버가 GitHub API를 호출해 상태를 바꾼다. Slack `post_message`, DB `run_query`도 같은 실행 계열이다.
- **흔한 오해·주의점**: 툴은 부작용을 전제한다. 단순 데이터 조회는 툴이 아니라 리소스(009)로 노출해야 프리미티브 오용이 아니다. 또한 툴 설명(description)에 숨긴 악성 지시(툴 인젝션)가 모델을 오도할 수 있어 설명 정제·권한 최소화·샌드박스가 필요하다.

## 연결 개념
- MCP 리소스(009) — 부작용 없는 읽기 계열, 툴과 대비되는 프리미티브
- Function Calling(005) — 툴 호출의 기반 개념(모델이 함수 인자를 생성)
- HITL(022)·에이전트 가드레일 — 고위험 툴 실행을 통제하는 상위 안전장치

# 📝 【답안용】 시험 답안 템플릿

## 핵심 인사이트 (3줄 요약)

> 1. **본질**: MCP 툴은 모델이 호출해 외부 상태를 바꾸는, 부작용을 전제한 실행 가능 함수임.
> 2. **가치**: 위험한 실행 동작을 이름·스키마로 표준 선언해 안전한 발견·호출·통제를 가능하게 함.
> 3. **판단 포인트**: 부작용 크기에 따라 승인(HITL)·권한 최소화·멱등성·감사를 차등 설계해야 함.

## 출제 의도 및 답안 포인트

| 출제 의도 | 반드시 짚을 핵심 | 감점 회피 포인트 |
|:---|:---|:---|
| 실행 프리미티브 구조 이해 | Input Schema, tools/list·call, 모델 제어 | 읽기 리소스(009)와 혼동 기술 시 감점 |
| 부작용·위험 통제 인식 | annotations, HITL 승인, 권한 최소화 | 승인·권한 통제 누락 시 감점 |
| Function Calling과의 관계 | 표준 규격으로 여러 호스트 재사용 | 단일 앱 함수 호출로 축소 시 감점 |

> 요약: 부작용 있는 실행을 무엇으로 선언하고 어떤 승인·권한으로 통제하는지 확인하려는 문제임.

---

## Ⅰ. 개요 및 필요성

- 개요: 서버가 이름·스키마로 선언하고 모델이 호출해 외부 상태를 바꾸는 실행 가능 함수임
- 배경: 리소스(009)는 읽기만 가능해 메일 발송·결제 같은 실제 행위를 처리하지 못함
- 필요성: 위험한 실행 동작을 표준 규격으로 노출·검증해야 에이전트가 작업을 완결함 (전체 구조는 006 참조)
- 위치: 서버가 노출하는 3대 프리미티브 중 부작용을 동반하는 실행 계열임

---

## Ⅱ. 구조 및 구성요소

- 선형 구조도

```text
서버 툴 선언(name / description / inputSchema)
  모델이 발견 tools/list -> 인자 생성(JSON Schema 준수)
    -> tools/call 실행 요청 -> 서버 인자 검증·권한 확인
    -> 실제 동작 수행(API·DB) -> 결과 반환(content + isError)
  고위험 툴 -> annotations 표시 -> HITL 승인 게이트
```

| 구성요소 | 역할 | 특이사항 |
|:---|:---|:---|
| 이름·설명 | 툴 식별·용도 안내 | 설명 인젝션 검증 필요 |
| Input Schema | 인자 구조·타입 규정 | JSON Schema로 검증 |
| 실행 로직 | 실제 외부 동작 수행 | 부작용 발생 지점 |
| annotations | 위험도 힌트(readOnly·destructive) | 승인 정책 근거 |
| 결과(Result) | 콘텐츠·isError 반환 | 성공·실패 구분 |

> 요약: 툴은 이름·스키마로 선언되고, 검증·권한 확인 후 실행돼 결과와 오류 여부를 반환함.

---

## Ⅲ. 동작원리 및 흐름도

- 선형 흐름도

```text
tools/list 발견 -> 모델이 실행 필요 판단 -> 인자 생성 -> (고위험 시 사용자 승인) -> tools/call -> 서버 검증·실행 -> 결과·isError 반환 -> 모델 반영
```

1. 발견: 클라이언트가 서버의 툴 목록과 각 Input Schema를 획득함
2. 결정: 모델이 목표 달성에 특정 툴 실행이 필요함을 판단하고 인자를 생성함
3. 실행: 고위험 툴은 사용자 승인을 거친 뒤 서버가 인자를 검증·권한 확인 후 동작을 수행함
4. 반영: 서버가 결과·오류 여부를 반환하고 모델이 다음 행동 또는 최종 답을 결정함

> 요약: 모델이 툴을 선택·호출하되, 서버가 인자·권한을 검증하고 고위험 실행은 승인 게이트를 통과함.

---

## Ⅳ. 특징

- 부작용 전제: 리소스와 달리 외부 상태를 실제로 변경하는 실행 동작임
- 모델 제어: 어떤 툴을 언제 호출할지 모델이 판단해 자율적 작업 수행이 가능함
- 스키마 계약: Input Schema로 인자를 강제 검증해 잘못된 호출을 사전 차단함
- 위험 차등: annotations로 파괴적·읽기 전용 여부를 표시해 승인 정책을 차등 적용함
- 표준 재사용: 한 번 만든 툴을 MCP 지원 호스트 전체가 동일 규격으로 호출함

---

## Ⅴ. 심화 비교 및 적용 판단

- 툴의 성격은 같은 서버가 노출하는 읽기 프리미티브(리소스)와 대비할 때 가장 분명함

| 구분 | 툴(Tool) | 리소스(Resource) |
|:---|:---|:---|
| 목적 | 실행·상태 변경 | 읽기 전용 데이터 참조 |
| 부작용 | 있음(외부 상태 변경) | 없음(상태 불변) |
| 식별·계약 | 이름·Input Schema(JSON Schema) | URI·MIME 타입 |
| 호출 요청 | tools/call | resources/read |
| 승인 필요 | 높음(고위험 시 HITL) | 낮음(단순 읽기) |
| 반복 안전성 | 멱등성 설계 필요 | 반복 읽기 안전 |

> 요약: 부작용 유무가 핵심 축으로, 조회는 리소스로 노출하고 상태 변경은 반드시 툴로 분리해야 함.

- 툴 위험도별 승인 설계(불릿)
  - 읽기성 툴(readOnly) — 상태 불변 계산·조회, 자동 실행 허용
  - 변경성 툴 — 생성·수정, 로그·롤백 준비 후 실행
  - 파괴성 툴(destructive) — 삭제·송금, HITL 필수 승인 게이트

- 주요 리스크와 대응(불릿)
  - 툴 설명 인젝션 — 설명에 숨긴 지시가 모델을 오도함이 원인 → 설명 정제·서명·허용 목록
  - 과도 권한 실행 — 넓은 시스템 접근 부여가 원인 → 최소 권한·샌드박스·범위 토큰
  - 중복 실행 부작용 — 재시도 시 이중 처리가 원인 → 멱등성 키·요청 중복 제거

- 운영 지표(불릿)
  - 승인 준수율 — 고위험 툴 100% 승인 경유 목표 — 승인 로그 대조
  - 실행 성공률 — isError 비율 1% 이하 목표 — 호출 결과 집계
  - 권한 위반 — 0건/주 목표 — 접근 감사로그 분석

---

## Ⅵ. 실무 적용 및 결론

- 적용 방안
  1. 위험 등급화: 툴에 annotations(readOnly·destructive)를 부여하고 파괴적 툴은 HITL 승인 게이트로 강제
  2. 스키마 강제: Input Schema로 인자 타입·범위를 검증하고 실패 시 isError로 회수해 오작동 차단
  3. 격리·추적: 서버를 샌드박스·최소 권한 토큰으로 격리하고 tools/call을 감사로그로 남겨 추적성 확보
- 결론
  - 기술사 판단: 단순 조회는 리소스로, 상태를 바꾸는 동작은 툴로 분리하고 위험도에 따라 승인을 차등 적용함
  - 향후 방향: 툴 레지스트리·정책 엔진과 결합해 위험 기반 자동 승인이 이뤄지는 통제형 에이전트로 진화함
