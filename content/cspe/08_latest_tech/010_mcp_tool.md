# 📖 【암기용】 개념 완전 이해

## 한눈에
- **개요**: **MCP 툴**은 AI 모델이 외부 세계에 물리적인 변화를 일으키거나(Side Effects), 특정 연산을 수행하기 위해 호출할 수 있는 **실행 가능한 함수**이다.
- **필요성**: 리소스가 단순 '읽기'라면, 툴은 '쓰기'와 '실행'이다. 파일을 생성하거나, 코드를 실행하거나, API를 통해 이메일을 보내는 등 모델이 실질적인 작업을 완수하게 해준다.
- **핵심 직관**: **"에이전트가 쥐고 흔드는 도구"**. 모델의 의사결정을 실체적인 결과물로 바꿔주는 실무적 수단이다.

## 깊이 이해
- **배경 (Action-oriented Intelligence)**: 모델이 정보를 아는 것(Knowing)에 그치지 않고 행동하는 것(Doing)으로 나아가기 위해 등장했다. 기존의 Function Calling 개념을 MCP라는 표준 프로토콜 내에서 구현한 것이다.
- **작동 원리 (The Tool Schema)**:
    - **Name**: 툴의 고유 이름 (예: `write_file`).
    - **Description**: 툴이 무슨 일을 하는지, 언제 써야 하는지에 대한 상세 설명. 모델은 이 설명을 보고 툴을 고른다.
    - **Input Schema**: 툴이 받아들이는 인자들의 규격 (JSON Schema 형식).
    - **Execution Result**: 실행 후 텍스트, 이미지, 또는 다른 리소스 형태의 결과를 반환.
- **비유**: 리소스가 "요리 책"이라면, 툴은 "가스레인지"나 "칼"과 같다. 요리 책의 정보를 바탕으로 실제 재료를 변형시키고 완성된 요리(결과물)를 만들어내는 장비다.
- **구체 예시**: `Google Maps MCP Server`는 `get_directions`라는 툴을 제공할 수 있다. 에이전트는 출발지와 목적지를 인자로 넣어 경로 데이터를 얻어온다.
- **주의점**: 툴은 시스템의 상태를 바꿀 수 있으므로(State Change), 실행 전 반드시 보안 검증과 사용자 승인(HITL)이 수반되어야 한다.

## 연결 개념
- **MCP Resource (009)**: 툴의 입력값이 되거나 결과값이 저장되는 데이터 개체.
- **Function Calling (005)**: 툴 사용을 가능하게 하는 기술적 메커니즘.
- **Side Effect (부작용/영향)**: 툴 실행으로 인해 시스템 외부 환경이 변하는 현상.

# 📝 【답안용】 시험 답안 템플릿

## 핵심 인사이트 (3줄 요약)
> 1. **본질**: MCP 서버가 정의한 기능을 모델이 특정 파라미터와 함께 실행할 수 있도록 설계된 **자율적 행동 유닛**.
> 2. **가치**: 읽기 전용 데이터를 넘어 실질적인 시스템 제어, 데이터 생성, 외부 상호작용을 가능케 하여 에이전트의 실무 완결성 확보.
> 3. **판단 포인트**: 모델이 툴의 용도와 제약을 명확히 이해할 수 있도록 **자연어 기반의 정교한 기능 설명(Semantic Description)** 작성이 필수.

## 출제 의도 및 답안 포인트
- **출제 의도**: MCP 툴의 구조, 실행 메커니즘, 그리고 리소스와의 차별점 이해 여부 파악.
- **핵심 포인트**: 실행 가능성(Executable), 입력 스키마(JSON Schema), Side Effect, 사용자 승인(Consent).

---

## Ⅰ. MCP 툴(MCP Tool)의 정의 및 핵심 특징
### 1. MCP 툴의 정의
- AI 모델의 요청에 따라 특정 비즈니스 로직이나 시스템 명령을 수행하고 그 결과를 반환하는 MCP 규격의 실행 가능 컴포넌트.
### 2. 핵심 특징
- **Executable**: 데이터 참조가 아닌, 실제 코드나 API의 실행을 수반함.
- **State Change (Side Effect)**: 파일 생성, 데이터 수정, 메시지 발송 등 외부 시스템 상태에 변화를 줄 수 있음.
- **Structured Interaction**: JSON Schema 기반의 엄격한 입력 규격 준수.

---

## Ⅱ. 툴의 기술적 명세 및 구성 요소
- **모델의 도구 선택을 돕는 메타데이터 구조**
| 구성 요소 | 상세 설명 | 중요도 |
|:---:|:---|:---:|
| **Name** | 툴의 고유 식별자 (예: `search_database`) | 필수 |
| **Description** | 툴의 기능, 사용 시점, 주의사항을 자연어로 기술 | **최상** |
| **Input Schema** | 호출에 필요한 파라미터 명세 (JSON Schema) | 필수 |
| **Result Type** | 결과의 형태 (Text, Image, Binary 등) | 권장 |

---

## Ⅲ. MCP 툴의 작동 및 실행 시퀀스
1. **Tool Discovery**: 클라이언트가 서버에 연결 시 사용 가능한 툴 목록과 설명을 수집.
2. **Intent Matching**: 모델이 사용자의 질문을 분석하고, 툴 설명과 대조하여 필요한 툴을 선정.
3. **Param Generation**: 모델이 입력 스키마에 맞춰 실제 인자값(Arguments)을 생성.
4. **Execution Request**: 클라이언트가 서버에 해당 인자와 함께 실행 요청 전송.
5. **Side Effect Guard**: (선택적) 클라이언트가 위험 여부 판단 후 사용자 승인 획득.
6. **Result Feedback**: 서버의 실행 결과가 모델에게 전달되어 최종 답변에 활용.

---

## Ⅳ. MCP 툴 vs MCP 리소스 비교

| 비교 항목 | MCP 리소스 (Resource) | MCP 툴 (Tool) |
|:---:|:---:|:---:|
| **주요 동사** | 읽기 (Read) | 실행하기 (Execute / Write) |
| **상태 변화** | 없음 (Side-effect free) | 존재함 (Side effects possible) |
| **식별 방식** | URI 주소 체계 | 함수 이름 체계 |
| **모델 활용** | 배경 지식으로 참조 | 과업 수행의 수단으로 활용 |
| **비유** | 도서관의 책 | 공구함의 망치 |

---

## Ⅴ. 툴 설계 및 운영의 핵심 고려사항
- **Semantic Clarity**: 툴 이름과 설명을 명확히 하여 모델이 툴을 오용(Misuse)하거나 누락하지 않도록 최적화.
- **Sandboxing**: 임의의 코드 실행이나 시스템 명령을 포함하는 툴은 반드시 격리된 환경에서 실행하여 보안 사고 방지.
- **Idempotency (멱등성)**: 가능한 경우 툴을 여러 번 실행해도 시스템 상태가 동일하게 유지되도록 설계하여 모델의 재시도 로직 지원.
- **Observability**: 어떤 툴이 어떤 인자로 호출되었고 결과가 무엇이었는지에 대한 상세 Trace 로그를 남겨 사후 분석 가능케 함.

---

## Ⅵ. 실무 관점의 결론 및 제언
- **에이전틱 워크플로우의 완성**: 툴은 단순 기능 연동을 넘어 복잡한 비즈니스 프로세스(예: 결제 -> 배송 요청 -> 알림 발송)를 자율적으로 엮는 핵심 동력임.
- **결론**: 기술사는 툴의 자율 실행 권한을 정의하는 **"도구 정책 엔진(Policy Engine)"**을 함께 설계하여, 에이전트의 활동 범위와 안전성을 동시에 확보해야 함.

### 🔀 문제 유형별 목차 전환
- **비교형**: Ⅳ. 리소스 vs 툴 비교를 통해 상황별 적정 컴포넌트 선택 전략 강조.
- **설계/보안형**: Ⅲ. 실행 시퀀스의 승인 단계와 Ⅴ. 설계 고려사항(Sandboxing) 중심으로 기술.
