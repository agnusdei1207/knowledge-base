# 📖 【암기용】 개념 완전 이해

> 목적: MCP 도구(MCP Tool)를 처음 봐도 완벽히 이해하게 만든다. 시험 답안 양식이 아니라, 이해를 위한 친절한 설명이다.

## 한눈에
- **개요**: AI 에이전트가 외부 시스템에 물리적인 변화를 주거나 연산을 수행할 때 사용하는 "실행 버튼"
- **왜 필요한가**: AI가 단순히 말만 하는 것이 아니라, 실제로 메일을 보내고 코드를 실행하고 데이터를 수정하려면 안전한 "실행 통로"가 필요하다.
- **핵심 직관**: AI의 "손". AI(Client)가 손(Tool)을 뻗어 외부 세상(Backend)의 물건을 옮기거나 기기를 조작하는 동작이다.

## 깊이 이해
- **배경·문제의식**: 예전에는 AI에게 도구를 줄 때마다 복잡한 API 스펙을 프롬프트에 구구절절 적어줘야 했다. 이 방식은 토큰을 많이 쓰고, 모델이 입력 형식을 틀리기 쉬우며(Hallucination), 보안 통제가 어렵다는 단점이 있었다.
- **작동 원리**: 서버는 도구의 이름, 설명, 그리고 입력해야 할 값들의 규격(JSON Schema)을 제공한다. 모델이 "이 도구가 필요해"라고 하면, 클라이언트가 정해진 스키마에 맞춰 인자(Arguments)를 채워 서버에 보내고, 서버는 이를 검증한 뒤 실행한다.
- **비유**: 자동판매기. 각 버튼(Tool)마다 가격과 선택 옵션(Argument)이 정해져 있고, 사용자가 버튼을 누르면 내부 메커니즘이 동작하여 상품을 내놓는 것과 같다.
- **구체 예시**: `fetch_website` 도구는 URL을 입력받아 웹페이지 내용을 긁어오고, `sql_query` 도구는 쿼리문을 입력받아 DB 결과를 가져온다.
- **흔한 오해·주의점**: 도구는 리소스(Resource)와 다르다. 리소스는 읽기만 하는 것이고, 도구는 서버에 어떤 동작을 시키거나 새로운 결과를 "생성"해내는 실행력을 갖는다. 따라서 실행 전 "정말 실행하시겠습니까?"라는 승인이 매우 중요하다.

## 연결 개념
- Function Calling — 모델이 도구의 입력값을 구조화된 형태로 생성하는 기술
- JSON Schema — 도구의 입력 인자 타입을 정의하는 표준 규격
- User-in-the-Loop — 고위험 도구 실행 전 사용자의 최종 승인을 받는 절차

# 📝 【답안용】 시험 답안 템플릿

> 목적: 시험장에서 25분에 그대로 쓰는 답안 양식. 작성방식(추상표현 금지·수치·도식·문제유형 전환)을 엄격히 지킨다.
> 핵심: MCP 도구는 AI의 실행력(Agency)을 실현하는 핵심 자산이며, 스키마 기반의 엄격한 입력 제어와 사용자 승인 체계를 통한 리스크 관리가 설계의 본질이다.

## 핵심 인사이트 (3줄 요약)

> 1. **본질**: MCP 도구는 MCP 서버가 JSON Schema 기반의 표준 규격으로 노출하여 모델이 호출할 수 있도록 정의된 실행 가능한 기능 단위이다.
> 2. **가치**: 모델의 도구 사용(Tool Use) 프로세스를 표준화하여 모델 교체 시의 재사용성을 확보하고, 실행 전후의 강력한 보안 정책 집행 지점을 제공한다.
> 3. **판단 포인트**: 도구 설계 시 설명(Description)의 명확성, 입력 유효성 검증(Validation), 실행 결과의 에러 처리 및 멱등성(Idempotency) 보장이 핵심이다.

## 출제 의도 및 답안 포인트

| 출제 의도 | 반드시 짚을 핵심 | 감점 회피 포인트 |
|:---|:---|:---|
| MCP 도구의 라이프사이클 및 실행 원리 | Discovery -> Reasoning -> Argument Generation -> Call -> Result | 도구 명세(Description)의 중요성(모델 선택 성능 직결) 누락 |
| 실행 리스크 통제 및 보안 역량 | 입력 스키마 검증, 사용자 승인(HITL), 롤백/멱등성 설계 | 무조건적인 자동 실행 강조(안전한 에이전시 구현 실패) |
| 기술적 세부 사양 인지 | JSON Schema 7.0+, 에러 코드 처리, 타임아웃 관리 | 추상적인 "기능이 다양하다"는 표현 사용 |

> 요약: 스키마 기반의 실행 통제와 모델의 정확한 선택을 유도하는 메타데이터 설계, 보안 거버넌스 확보 방안을 연계하여 기술한다.

## Ⅰ. 개요 및 필요성

- 정의: LLM이 외부 시스템과 상호작용하기 위해 MCP 서버가 노출하는 스키마 기반의 실행 가능한 함수 인터페이스
- 배경: 모델별 상이한 도구 호출 방식에 따른 앱 복잡도 증가 및 모델의 잘못된 인자 생성으로 인한 시스템 오류 위험 증대
- 필요성: 도구 호출 규격의 표준화를 통한 범용 에이전트 구현, 실행 전 승인 및 실행 후 결과 정제를 통한 안전한 업무 자동화

---

## Ⅱ. 구조 및 구성요소

```text
[MCP 도구 명세 및 실행 구조]
Name: [도구명]
Description: [모델용 설명 - 호출 시점 판단 근거]
Input Schema: { "type": "object", "properties": { ... }, "required": [...] }
        |
[ Execution Logic ] -> Input Validation (Server-side)
                    -> Action (API/DB/Script)
                    -> Output Formatting (Result to LLM)
```

| 구성요소 | 역할 | 주요 사양 |
|:---|:---|:---|
| Name / Description | 도구 식별 및 선택 가이드 | 모델의 Semantic 매칭용 메타데이터 |
| Input Schema | 입력 인자의 구조 및 타입 정의 | JSON Schema 규격 적용 |
| Handler / Executor | 실제 비즈니스 로직 수행 | 서버 측 실행 코드, 타임아웃 관리 |
| Result Object | 실행 결과 데이터 | 텍스트, 이미지, 또는 에러 메시지 반환 |
| Capabilities | 도구별 특수 기능 정의 | 실행 전 승인 필요 여부, 멱등성 보장 등 |

> 요약: 명확한 설명과 엄격한 스키마 정의를 통해 모델의 정확한 선택과 안전한 실행을 보장하는 구조를 갖는다.

## Ⅲ. 동작원리 및 흐름도

```text
[MCP 도구 실행 워크플로우]
Discovery -> LLM Reasoning -> Argument Gen -> Client Dispatch -> Server Validation -> Backend Execution -> Result
 (List)     (Tool Selection)   (Schema Match)     (Request)         (Security)          (Real Action)    (Feed)
```

| 단계 | 처리 내용 | 주요 검증/제어 기준 |
|:---:|:---|:---|
| 1 | 도구 카탈로그 획득 | 서버에 연결하여 사용 가능한 도구 명세(이름, 설명, 스키마) 수집 |
| 2 | 도구 선택 및 인자 생성 | 질문 맥락에 맞는 도구 선정 후 모델이 JSON 형식으로 인자 생성 |
| 3 | 요청 전송 및 서버 검증 | 클라이언트가 서버로 요청 발송, 서버 측에서 스키마 유효성 및 권한 체크 |
| 4 | 실행 및 결과 피드백 | 실제 기능 수행 후 성공/실패 결과를 텍스트화하여 모델 컨텍스트에 주입 |

> 요약: 발견-선택-생성-검증-실행의 순환 구조를 통해 모델의 지능과 시스템의 실행력을 결합한다.

## Ⅳ. 특징

| 구분 | MCP 도구 방식 | 일반적인 API 래핑 방식 | 기술사 판단 포인트 |
|:---|:---|:---|:---|
| 선택 정확도 | 설명(Description) 기반 최적화 | 프롬프트 내 API 가이드 의존 | 모델의 도구 오선택율(Hallucination) 감소 |
| 입력 유효성 | 서버 측 스키마 강제 검증 | 앱 레벨의 개별 검증 로직 | 비정상 호출에 의한 시스템 영향 차단 |
| 보안 승인 | 표준화된 승인 인터페이스 | 앱마다 승인 UI/로직 상이 | 일관된 보안 거버넌스(HITL) 적용 |
| 유지보수 | 서버 명세 수정 시 즉시 반영 | 앱-모델 간 연동 코드 수정 필요 | 민첩한 기능 확장(Time-to-Market) |

> 요약: MCP 도구는 표준화된 명세와 검증 체계를 통해 에이전트의 실행 안정성과 보안성을 획기적으로 향상시킨다.

## Ⅴ. 심화 비교 및 적용 판단

| 비교 축 | 조회형 도구 (Read-only) | 변경형 도구 (State-changing) | 설계 고려 사항 |
|:---|:---|:---|:---|
| 위험도 | 낮음 (정보 유출 위주) | 높음 (데이터 파손, 오작동 위주) | 리스크 기반 등급 분류 |
| 승인 정책 | 자동 실행 가능 (Auto-exec) | 명시적 사용자 승인 (Manual) | User-in-the-loop 적용 범위 |
| 기술적 요건 | 데이터 정제 및 요약 | 멱등성 보장, 롤백 시나리오 | 실행 결과의 원자성(Atomicity) |

> 요약: 부작용이 없는 조회형은 자동화 효율을, 상태를 변화시키는 변경형은 보안 통제와 안정성을 우선한다.

| 리스크 | 원인 | 대응 방안 | 확인 지표 |
|:---|:---|:---|:---|
| 환각 호출 (Hallucination) | 설명 부족으로 잘못된 도구 선택 | 도구 설명 구체화, Few-shot 제공, 네이밍 개선 | 도구 선택 오류율 (Target < 3%) |
| 과다 리소스 소모 | 무한 루프 호출 또는 대량 데이터 요청 | 호출 횟수 제한(Rate Limit), 결과 크기 제한 | API 호출 비용 및 서버 CPU 사용률 |
| 부정 실행 (Unauthorized) | 사용자 권한을 넘어서는 호출 | 세션 기반 권한 검증, 서버 측 RBAC 적용 | 권한 위반 차단 건수 |

> 요약: 환각, 자원 남용, 권한 오남용을 설명 최적화와 서버 측 통제 정책으로 방어한다.

| 점검 항목 | 목표 기준 | 측정 방법 |
|:---|:---|:---|
| 정확성 (Hit Rate) | 도구 선택 및 인자 생성 성공률 97% | 골든 데이터셋 기반 리그레션 테스트 |
| 가용성 (Success Rate) | 실제 백엔드 실행 성공률 99.9% | 에러 코드(5xx) 및 타임아웃 빈도 분석 |
| 보안성 (Audit) | 실행 전 승인 프로세스 준수율 100% | 보안 감사 로그 및 UI 인터랙션 추적 |

> 요약: 호출 정확성, 실행 가용성, 보안 준수율을 도구 운영의 핵심 KPI로 관리한다.

## Ⅵ. 실무 적용 및 결론

**적용 방안 3개:**
1. 등급별 보안 차등: 도구 성격에 따라 'Public/Internal/High-Risk'로 등급을 나누고, High-Risk 도구는 2단계 인증(2FA) 연동
2. 멱등성 인터페이스: `create_user`와 같은 도구에 중복 호출 방지를 위한 `client_token` 필드를 스키마에 필수 포함
3. 지능형 오류 복구: 실행 실패 시 에러 원인을 모델이 이해하기 쉬운 텍스트로 변환하여 반환, 모델이 스스로 수정 호출하도록 유도

**결론 (2줄):**
- 기술사 판단: MCP 도구는 AI가 수동적 관찰자에서 능동적 행위자로 진화하는 변곡점이며, 도입 시 기능의 양보다 "통제 가능한 Agency" 확보가 우선이다.
- 향후 방향: 도구 간의 의존성을 모델이 스스로 파악하여 복합 워크플로우를 자동 생성하는 '자율형 도구 체이닝' 기술이 고도화될 전망이다.
