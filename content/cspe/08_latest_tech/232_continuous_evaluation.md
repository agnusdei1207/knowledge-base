# 📖 【암기용】 개념 완전 이해

> 목적: 지속 평가(Continuous Evaluation) 개념을 처음 보는 사람도 완벽히 이해하게 만든다. 시험 답안 양식이 아니라, 이해를 위한 친절한 설명이다.

## 한눈에
- **개요**: AI 모델의 개발부터 배포, 운영 전 과정에서 성능과 품질을 멈추지 않고 실시간 또는 주기적으로 측정하는 체계
- **왜 필요한가**: 모델은 학습 데이터와 실제 환경 데이터의 차이(Data Drift) 때문에 시간이 지나면 성능이 떨어지기 때문(Model Decay). 특히 RAG는 외부 데이터가 변하면 답변 품질이 즉시 변함
- **핵심 직관**: "출시 전 한 번 보는 기말고사 대신, 매일 보는 형성평가와 실시간 모니터링"

## 깊이 이해
- **배경·문제의식**: 전통적인 소프트웨어는 로직이 고정되어 있어 테스트를 통과하면 안전함. 하지만 AI는 입력 데이터의 분포가 변하면 갑자기 엉뚱한 답을 함. 이를 '드리프트'라고 하며, 배포 후에 발견하면 이미 늦음
- **작동 원리**: CI/CD 파이프라인에 CE(Continuous Evaluation)를 통합함. ① 개발 단계에서는 벤치마크 테스트, ② 배포 단계에서는 카나리/섀도 테스트, ③ 운영 단계에서는 실제 사용자 피드백(Thumbs up/down)과 LLM Judge 기반 자동 평가 수행
- **비유**: 정수기 필터를 한 번 끼우고 끝내는 것이 아니라, 수질 측정기(CE)를 달아 물의 오염도(성능)를 실시간 감시하며 교체 시기를 정하는 것
- **구체 예시**: 고객 센터 챗봇 배포 후, 사용자의 질문 유형이 "상품 문의"에서 "반품 불만"으로 바뀌면 정확도가 떨어짐. CE 체계는 이를 감지하여 재학습이나 프롬프트 수정을 트리거함
- **흔한 오해·주의점**: 운영 중인 모든 데이터를 평가하는 것은 불가능함(비용 이슈). 중요한 샘플을 추출(Sampling)하거나, 저비용 모델로 1차 필터링하는 전략이 필요함

## 연결 개념
- **LLMOps**: 지속 평가가 핵심 프로세스로 포함되는 운영 체계
- **Data/Concept Drift**: 지속 평가가 감지해야 하는 핵심 위험 요소
- **Feedback Loop**: 평가 결과를 다시 학습 데이터로 넣는 선순환 구조

# 📝 【답안용】 시험 답안 템플릿

> 목적: 시험장에서 25분에 그대로 쓰는 답안 양식. 작성방식(추상표현 금지·수치·도식·문제유형 전환)을 엄격히 지킨다.
> 핵심: CI/CD/CT(Continuous Training)를 넘어 **CE(Continuous Evaluation)**의 독자적 영역과 지표 관리 체계를 강조한다.

## 핵심 인사이트 (3줄 요약)

> 1. **본질**: 지속 평가(Continuous Evaluation)는 AI 모델 라이프사이클 전반에 걸쳐 모델의 정확성, 안전성, 드리프트를 자동화된 파이프라인으로 상시 모니터링하는 체계이다.
> 2. **가치**: 모델 노후화(Model Decay) 및 환경 변화에 따른 성능 하락 리스크를 조기 발견하여 서비스 신뢰성(Reliability)을 유지하고 운영 비용을 최적화한다.
> 3. **판단 포인트**: 정적 벤치마크(Offline)와 실시간 피드백(Online) 지표를 통합 관리하며, 드리프트 발생 시 재학습(CT) 트리거링 기준을 명확히 정의해야 한다.

## 출제 의도 및 답안 포인트

| 출제 의도 | 반드시 짚을 핵심 | 감점 회피 포인트 |
|:---|:---|:---|
| AI 서비스의 신뢰성 유지 역량 확인 | CI/CD/CE 통합, 드리프트(Drift) 감지, Feedback Loop | 배포 전 테스트만 언급하는 수준에 그침 |
| LLMOps/MLOps 실무 이해도 측정 | Offline vs Online 평가, LLM Judge 활용, 비용 최적화 전략 | 단순 정확도(Accuracy) 지표만 나열 |

> 요약: 출시 이후의 품질 저하를 방어하기 위한 '상시 평가 체계' 구축 전략을 제시한다.

## Ⅰ. 개요 및 필요성

- 정의: AI 모델의 개발, 배포, 운영 단계에서 성능 지표와 데이터 분포 변화를 자동화 도구로 상시 측정하는 품질 관리 체계
- 배경: 학습 데이터 편향, 외부 환경 변화(Concept Drift), 모델 노후화로 인해 고정된 테스트셋(Static Testset)만으로는 품질 보증 불가
- 필요성: 성능 저하로 인한 비즈니스 손실 방지, 사용자 신뢰 회복, 재학습 시점 판단의 객관적 근거 확보

## Ⅱ. 구조 및 구성요소

```text
Dataset -> [CI/CD Pipeline] -> Deployment -> [Real-time Monitoring]
              |                   |                  |
              +--> Offline CE <---+--- Feedback <----+-- Online CE
              (Benchmarking)        (Human/LLM)         (Drift Detection)
```

| 구성요소 | 역할 | 특이사항 |
|:---|:---|:---|
| Offline CE | 배포 전 황금 데이터셋(Golden Dataset) 기반 평가 | 회귀 테스트(Regression Test) 수행 |
| Online CE | 실시간 운영 데이터 스트림 감시 | PSI(Population Stability Index) 측정 |
| Feedback Loop | 사용자 피드백 및 LLM Judge 평가 취합 | 정답지(Ground Truth) 자동 생성 및 축적 |

> 요약: 오프라인(배포 전)과 온라인(배포 후) 평가가 상호 보완하며 모델의 건강 상태를 360도 감시하는 구조이다.

---

## Ⅲ. 동작원리 및 흐름도

```text
Data Ingestion -> Model Inference -> Metric Collection -> Drift Detection -> Alert/Retrain
(실제 운영 데이터)  (답변 생성 및 저장)   (성능/통계 지표 수집)  (임계값 기반 판단)   (자동 트리거링)
```

| 단계 | 처리 내용 | 검증 기준 |
|:---:|:---|:---|
| 1 | 운영 로그 및 메트릭 수집 | 추론 결과, 지연시간(Latency), 비용 수집 |
| 2 | 지표 분석 및 드리프트 체크 | PSI > 0.2 또는 정확도 5% 이상 하락 |
| 3 | LLM Judge 기반 품질 검사 | Faithfulness(RAG), Toxicity(Safety) 검증 |
| 4 | 재학습 또는 롤백 실행 | 성능 개선 확인 후 최종 배포 결정 |

> 요약: 수집-분석-감지-대응의 루프를 통해 데이터 분포 변화와 모델 성능 하락에 능동적으로 대처한다.

## Ⅳ. 특징

| 구분 | 일반 테스트 (Unit Test) | 지속 평가 (Continuous Eval) | 판단 포인트 |
|:---|:---|:---|:---|
| 평가 대상 | 코드 로직, 함수 | 데이터 분포, 모델 확률적 결과 | 비결정성(Non-deterministic) 관리 |
| 수행 시점 | 빌드 및 배포 단계 | 배포 후 전 기간 (상시) | 운영 중 성능 가시성 확보 |
| 주요 지표 | 통과/실패 (Pass/Fail) | 드리프트(Drift), 정확도 추이, 비용 | 통계적 유의성(Significance) |
| 수치 사례 | Coverage 80% 이상 | Precision @k, MTTR(복구시간) 1시간 이내 | 가용성 및 품질 지표 결합 |

> 요약: 결정론적 코드 테스트와 달리, 확률적 결과물의 통계적 변화를 장기적으로 추적하는 것이 핵심이다.

## Ⅴ. 심화 비교 및 적용 판단

| 비교 축 | Offline Evaluation | Online Evaluation | 선택 기준 |
|:---|:---|:---|:---|
| 데이터셋 | 고정된 골든 데이터셋 | 실제 유입되는 라이브 데이터 | 데이터 확보 가능 여부 |
| 평가 모델 | 전문가 검수 답변 | 사용자 피드백, LLM Judge | 비용 및 실시간성 요구도 |
| 주요 용도 | 배포 승인 (Gate) | 드리프트 감지 및 경고 | 파이프라인 위치 |

> 요약: 신뢰성 확보를 위해 배포 전 Offline 검증을 수행하고, 운영 중에는 Online 감지로 보완한다.

| 리스크 | 원인 | 대응 방안 | 확인 지표 |
|:---|:---|:---|:---|
| Evaluation Cost | LLM Judge 호출 비용 과다 | 경량 모델(SLM) 활용, 샘플링 평가 | 1K 토큰당 평가 비용 |
| Labeling Delay | 정답지(Label) 확보 지체 | Active Learning, Weak Supervision | 데이터 라벨링 소요 시간 |
| Concept Drift | 데이터 의미 관계의 급격한 변화 | 적응형 재학습(Adaptive Retraining) | KL Divergence(데이터 분포 차이) |

> 요약: 평가 비용과 라벨링 지연 리스크를 줄이기 위해 샘플링 및 자동화 라벨링 기술을 병행한다.

| 점검 항목 | 목표 기준 | 측정 방법 |
|:---|:---|:---|
| 탐지 지연 (Detection Lag) | 드리프트 발생 5분 이내 감지 | 모니터링 시스템 알람 로그 분석 |
| 평가 정합성 | LLM Judge와 인간 평가 일치도 85% | Kappa 통계량 측정 |
| 가용성 영향 | 평가 프로세스로 인한 지연 10ms 이하 | 추론 파이프라인 비동기 처리 확인 |

> 요약: 평가 체계가 서비스 가용성을 해치지 않으면서도 신속하고 정확하게 이상을 감지해야 한다.

## Ⅵ. 실무 적용 및 결론

**적용 방안 3개:**
1. **RAG 파이프라인 통합**: Arize Phoenix 등을 활용하여 문맥 정밀도(Context Precision)와 답변 관련성을 상시 측정하고, 특정 수치 하락 시 임베딩 인덱스 업데이트 트리거
2. **A/B 테스트 자동화**: 신규 프롬프트/모델 적용 시 기존 모델(Champion)과 신규 모델(Challenger)의 실시간 지표를 비교하여 승자 모델 자동 승격
3. **가드레일 모니터링**: 유해물 생성 방지 가드레일 통과율을 실시간 대시보드화하여 보안 사고 및 컴플라이언스 대응

**결론 (2줄):**
- 기술사 판단: 지속 평가는 AI 운영의 '가시성'을 확보하는 필수 장치이며, 단순 지표 측정을 넘어 자동 재학습(CT)으로 이어지는 선순환 구조 설계가 핵심이다
- 향후 방향: 사람이 직접 개입하지 않아도 평가-학습-배포가 자율적으로 일어나는 Self-improving AI 시스템으로 발전할 전망이다
