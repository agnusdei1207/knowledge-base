# 📖 【암기용】 개념 완전 이해

> 목적: 지속 평가를 모델·프롬프트·데이터가 바뀔 때마다 품질과 안전성을 자동으로 다시 검증하는 운영 체계로 이해하게 만든다.

## 한눈에
- **개요**: 모델 변경, 프롬프트 변경, 데이터 drift, 배포 이후 로그를 트리거로 평가를 반복 실행하는 체계
- **왜 필요한가**: AI 서비스는 모델, 검색 인덱스, 프롬프트, 사용자 분포가 계속 바뀌어 초기 평가 결과가 오래 유지되지 않는다.
- **핵심 직관**: 건강검진을 한 번 받는 것이 아니라 매일 체온과 혈압을 확인해 이상 징후를 조기에 잡는 방식이다.

## 깊이 이해
- **배경·문제의식**: 모델 릴리스 후에도 데이터 분포 변화, 신규 공격 프롬프트, 지식베이스 갱신, 프롬프트 수정으로 품질 회귀가 발생한다.
- **작동 원리**: CI/CD와 모니터링 이벤트가 평가 파이프라인을 호출하고 offline set, shadow log, online metric, LLM judge, human review를 연결한다.
- **비유**: 생산 라인의 최종 검사뿐 아니라 공정 중 센서와 샘플 검사를 계속 수행하는 품질관리 체계와 같다.
- **구체 예시**: RAG 시스템은 매일 500개 regression set으로 groundedness 4/5 이상, citation error 1% 이하, p95 latency 2초 이하를 확인한다.
- **흔한 오해·주의점**: 지속 평가는 모니터링만이 아니다. 평가 데이터, 지표, 기준선, 승인 게이트, 롤백 절차까지 포함한다.

## 연결 개념
- MLOps/LLMOps — 지속 평가가 포함되는 운영 자동화 체계
- Model Monitoring — drift와 운영 이상을 평가 트리거로 제공
- LLM Judge — 대량 회귀 평가 자동화 수단

# 📝 【답안용】 시험 답안 템플릿

> 목적: 시험장에서 25분에 그대로 쓰는 답안 양식.
> 핵심: 지속 평가는 배포 전·후 품질 게이트를 자동화해 모델 회귀와 drift를 조기에 차단한다.

## 핵심 인사이트 (3줄 요약)

> 1. **본질**: Continuous Evaluation은 모델, 데이터, 프롬프트, 운영 로그 변화마다 평가를 반복 실행하는 AI 품질관리 체계임.
> 2. **가치**: regression test, drift trigger, online metric, LLM judge, human review를 연결해 품질 회귀를 배포 전에 차단함.
> 3. **판단 포인트**: 평가 자동화는 기준선, 임계치, 승인 게이트, 롤백 정책이 함께 있어야 운영 통제가 가능함.

## 출제 의도 및 답안 포인트

| 출제 의도 | 반드시 짚을 핵심 | 감점 회피 포인트 |
|:---|:---|:---|
| AI 운영 품질관리 이해 확인 | CI/CD 평가, drift trigger, regression set | 단순 monitoring으로만 서술 |
| LLMOps 연결 판단 확인 | prompt, retrieval, model 변경 평가 | 모델 파일 변경만 평가 |
| 통제 체계 확인 | quality gate, rollback, human review | 지표만 있고 의사결정 기준 누락 |

> 요약: 이 문제는 AI 서비스의 변경과 운영 분포 변화를 지속 평가로 통제하는 구조를 요구한다.

---

## Ⅰ. 개요 및 필요성

- 개요: 변경·운영 이벤트 기반 반복 평가
- 배경: 모델, 프롬프트, 검색 인덱스, 사용자 분포는 배포 이후에도 계속 변함.
- 필요성: groundedness 4/5 이상, citation error 1% 이하, p95 latency 2초 이하 같은 기준을 지속 확인해야 함.

---

## Ⅱ. 구조 및 구성요소

```text
Change/Event Trigger -> Evaluation Dataset -> Metric Runner/LLM Judge -> Quality Gate -> Deploy/Rollback/Human Review
```

| 구성요소 | 역할 | 특이사항 |
|:---|:---|:---|
| Trigger | 코드·모델·프롬프트·drift 이벤트 감지 | CI/CD, monitoring 연동 |
| Evaluation Dataset | regression, red-team, shadow 샘플 제공 | 주기적 갱신 필요 |
| Metric Runner | 자동 지표와 LLM judge 실행 | 품질·안전·비용 지표 |
| Quality Gate | 배포 승인·차단·롤백 판단 | 임계치 기반 정책 |

> 요약: 지속 평가는 변경 이벤트를 평가 파이프라인으로 연결하고 품질 게이트로 배포 여부를 결정한다.

---

## Ⅲ. 동작원리 및 흐름도

```text
변경 감지 -> 평가셋 선택 -> 자동 평가 실행 -> 기준선 비교 -> 승인/차단 -> 운영 로그로 평가셋 갱신
```

| 단계 | 처리 내용 | 검증 기준 |
|:---:|:---|:---|
| 1 | 변경 또는 drift 이벤트 감지 | trigger 누락 0건 |
| 2 | 업무별 평가셋과 red-team set 선택 | 커버리지 |
| 3 | 자동 지표와 LLM judge 평가 실행 | schema 준수 |
| 4 | quality gate가 승인·차단·롤백 결정 | 기준 위반 자동 차단 |

> 요약: 지속 평가는 변경 감지부터 평가셋 갱신까지 폐루프로 동작해 품질 회귀를 반복 차단한다.

---

## Ⅳ. 특징

| 구분 | 일회성 평가 | Continuous Evaluation | 수치 기준 |
|:---|:---|:---|:---|
| 실행 시점 | 배포 전 1회 | 변경·주기·drift 이벤트마다 실행 | daily, per release |
| 평가 범위 | 고정 테스트셋 | regression, red-team, online log | 커버리지 추적 |
| 의사결정 | 수동 판단 | quality gate 자동화 | 기준 위반 배포 차단 |

> 요약: 지속 평가는 일회성 검증을 변경 기반 품질 게이트로 확장한다.

---

## Ⅴ. 심화 비교 및 적용 판단

| 비교 축 | 기존/대안 | 본 키워드 | 선택 기준 |
|:---|:---|:---|:---|
| 구조 | 수동 QA | 자동 평가 파이프라인 | 릴리스 빈도 높으면 continuous |
| 비용/성능 | 평가 비용 낮으나 회귀 탐지 지연 | 평가 비용 발생, 회귀 조기 탐지 | 장애 비용과 평가 비용 비교 |
| 운영/위험 | 변경 누락 가능 | trigger와 gate로 통제 | CI/CD 연동 성숙도 |

> 요약: 배포 빈도와 drift 위험이 큰 AI 서비스는 지속 평가를 품질 게이트로 적용한다.

| 리스크 | 원인 | 대응 방안 | 확인 지표 |
|:---|:---|:---|:---|
| 평가셋 오염 | 모델이 평가셋에 과적합 | holdout rotation, hidden set 운영 | score jump 이상치 |
| 비용 증가 | LLM judge 대량 호출 | 샘플링, 캐시, risk-based eval | cost/run |
| 경보 피로 | 임계치 과민 | severity 등급, SLO 기반 threshold | false alarm rate |

> 요약: 지속 평가 리스크는 평가셋 오염, 비용 증가, 경보 피로이며 hidden set과 위험 기반 샘플링으로 통제한다.

| 점검 항목 | 목표 기준 | 측정 방법 |
|:---|:---|:---|
| 품질 회귀 | baseline 대비 2% 초과 하락 차단 | eval report |
| 안전 | red-team fail 0건 | safety test |
| 운영 | p95 latency 2초 이하 | APM, replay test |

> 요약: 지속 평가 성공 여부는 품질 회귀 차단, 안전 위반 0건, 운영 SLA 준수로 판단한다.

---

## Ⅵ. 실무 적용 및 결론

**적용 방안 3개:**
1. 모델·프롬프트·retrieval index 변경 시 regression set과 red-team set을 CI 단계에서 자동 실행함.
2. 운영 로그에서 실패 샘플을 매주 100건 이상 추출해 evaluation dataset에 추가함.
3. quality score 2% 하락, safety fail 1건 이상, p95 latency 2초 초과 시 배포를 차단함.

**결론 (2줄):**
- 기술사 판단: AI 서비스는 배포 1회 평가가 아니라 변경·drift 이벤트마다 품질 게이트를 통과해야 운영 가능함.
- 향후 방향: 지속 평가는 LLMOps 플랫폼의 기본 기능으로 통합되어 자동 평가, 사람 검토, 롤백을 연결함.
