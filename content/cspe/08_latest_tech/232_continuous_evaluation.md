# 📖 【암기용】 개념 완전 이해

## 한눈에
- **정의**: AI 모델을 상용 환경에 배포해 놓고 "이제 끝!" 하는 게 아니라, **운영되는 365일 24시간 내내 모델의 응답 퀄리티, 정확도, 비정상 답변 비율을 끊임없이 감시하고 평가하는 자동화 체계**.
- **필요성**: 세상(데이터)은 변함. 코로나 이전의 소비 패턴으로 학습된 AI가 코로나 터진 직후에 엉뚱한 물건을 추천함(Data Drift). 특히 RAG 같은 LLM 챗봇은 법규가 바뀌거나 매뉴얼이 수정되면 바로 오답(환각)을 내뱉음. 이렇게 **'모델이 늙어가는 현상(Model Decay)'을 실시간으로 감지하고 즉시 알람을 울리기 위해** 필수적임.
- **핵심 직관**: 건강 검진(오프라인 평가) vs 스마트워치 심박수 감시(지속 평가). 배포 전에 하는 평가는 1년에 한 번 병원 가서 받는 건강검진임. 하지만 환자가 일상생활(운영 환경)에서 심정지가 오는 걸 막으려면 24시간 손목에 스마트워치를 채워놓고(CE 파이프라인), 심박수가 이상하면 즉시 119(재학습 트리거)를 부르게 해야 함.

## 깊이 이해
- **배경**: 전통적인 SW(예: 로그인 기능)는 한 번 코드를 짜고 테스트를 통과하면 10년이 지나도 에러가 안 남. 하지만 머신러닝 시스템은 코드가 멀쩡해도 '입력 데이터의 분포'가 달라지면 조용히(Error log 없이) 미쳐버림. "어? 에러 안 났는데요? 근데 왜 매출은 반토막이 났죠?"라는 기괴한 사태(Silent Failure)를 막기 위해 MLOps/LLMOps의 최종 진화 단계로 등장함.
- **작동 원리 (데이터 가로채기와 LLM Judge)**:
  1. **로그 수집(Telemetry)**: 유저가 챗봇에 질문하고 받은 답변, 그리고 "좋아요/싫어요" 클릭 이력을 비동기로 빼돌려 DB(옵저버빌리티 플랫폼)에 모음.
  2. **샘플링 평가**: 모든 걸 다 평가하면 API 비용이 폭발하므로, 하루 1천 개만 무작위 추출.
  3. **자동 채점(LLM Judge)**: GPT-4를 심판으로 띄워놓고, 오늘 유저가 받은 1천 개의 답변 중 '환각'이나 '동문서답'이 몇 개인지 채점함.
  4. **트리거(Trigger)**: 환각 비율이 기준치(예: 5%)를 넘거나, 검색 정확도가 폭락하면 관리자 슬랙(Slack)으로 알람을 보내거나 **재학습(Retraining) 파이프라인을 자동 가동**함.
- **구체 예시**: e커머스의 최저가 예측 AI. 매일 들어오는 경쟁사의 가격 변동 폭이 어느 날 미친 듯이 커짐(Data Drift). CE 시스템이 "입력 데이터 분포가 학습 때와 너무 다릅니다(PSI 지표 이상)"라고 경고를 띄움. 엔지니어가 즉시 최근 1주일치 데이터를 넣어 모델을 파인튜닝(Fine-Tuning)하여 손실을 막음.
- **흔한 오해/주의점**: "모니터링 대시보드(Grafana) 띄워놓는 게 CE 아님?" $\rightarrow$ 아님. 단순히 CPU 사용량이나 API Latency를 보는 건 '인프라 모니터링'임. CE는 **데이터의 통계적 분포(수학)와 AI의 답변 퀄리티(의미) 자체를 수치화하여 모니터링**하는 고차원적 행위임.

## 연결 개념
- **Data Drift / Concept Drift**: 학습 당시의 세계와 현재 운영 중인 세계의 규칙이나 데이터 텐션이 달라지는 현상. CE가 잡아내야 할 1순위 타깃.
- **LLM Judge**: 지속 평가를 '자동화'하기 위한 핵심 무기. 사람이 24시간 모니터링할 수 없으므로 AI가 AI를 감시하게 함.
- **Continuous Training (CT, 지속 학습)**: CE 파이프라인에서 "모델 썩었음!" 알람이 울리면 자동으로 실행되어 새 모델을 찍어내는 재학습 파이프라인.

# 📝 【답안용】 시험 답안 템플릿
## 핵심 인사이트 (3줄 요약)
- **본질**: AI/ML 시스템이 프로덕션 환경에 배포된 이후, 라이브 스트리밍 데이터의 통계적 편향성(Drift)과 모델 추론 퀄리티(Metric) 하락을 실시간(또는 주기적)으로 측정·감시하는 자동화 파이프라인.
- **가치**: 시간 경과 및 환경 변화에 따른 조용한 실패(Silent Failure)와 모델 노후화(Model Decay) 리스크를 조기 탐지하여, 시스템 가용성 유지 및 재학습(CT, Continuous Training)의 정확한 트리거 시점을 통계적으로 결정함.
- **판단 포인트**: 이상적인 CE 아키텍처는 인프라 지표(Latency, OOM) 모니터링을 넘어, 데이터-개념 드리프트(PSI, KL-Divergence) 지표와 LLM Judge 기반의 정성적 퀄리티 메트릭을 통합 관제(Observability)할 수 있어야 함.

## Ⅰ. 개요 및 필요성
- **정의**: MLOps/LLMOps의 운영 주기(Operation Lifecycle) 내에서, 추론 로그(Inference Log)와 그라운드 트루스(Ground Truth) 간의 오차, 데이터 분포의 변화를 상시 추적(Tracking)하는 퀄리티 보증 체계.
- **배경**: AI 모델은 소프트웨어 로직 부패가 아닌 '데이터의 부패(Data Rot)'로 인해 성능이 하락함. 오프라인 평가(Offline Eval) 시점의 성능이 온라인 상용 환경에서 영구적으로 보장되지 않음.
- **필요성**: 비즈니스 KPI 폭락 전 선제적 리스크 방어, 고비용의 무의미한 주기적 재학습(Cron-based Retraining) 방지, RAG 시스템 내 외부 지식 베이스 아웃데이트 현상 감지.

## Ⅱ. Continuous Evaluation의 3대 핵심 모니터링 지표 (Metrics)
무엇을 24시간 감시할 것인가?
| 감시 대상 | 측정 목적 및 리스크 정의 | 주요 적용 통계량 및 지표 (Algorithm) |
|:---:|:---|:---|
| **Data Drift**<br>(데이터 드리프트) | **입력 피처(Input Feature)**의 통계적 분포가 학습 당시(Train Set)와 확연히 달라졌는지 감시. | **PSI**(Population Stability Index), **KL Divergence**, Wasserstein Distance. |
| **Concept Drift**<br>(개념 드리프트) | 독립변수(X)와 종속변수(Y) 간의 **패턴(맵핑 관계) 자체가 변질**되었는지 감시. (예: 인플레이션으로 10만 원의 가치 변화) | 타깃 변수(Y)의 분포 변화율, 시간 윈도우 기반 실시간 예측 오차율(Loss). |
| **Model Quality**<br>(LLM 품질 저하) | 생성된 답변 자체의 윤리성, 할루시네이션, RAG 문서 참조 정확도의 저하 여부 감시. | **LLM-as-a-Judge** 5점 척도, 유저 피드백(Thumbs up/down) 비율, RAGAS 메트릭(Faithfulness). |

## Ⅲ. CE (Continuous Evaluation) 자동화 아키텍처 흐름도
감지부터 피드백까지의 폐쇄 루프(Closed-loop).
1. **Shadow Logging (비동기 로깅)**: 실시간 추론 트래픽에서 User Prompt, Model Response, Context(참조문서)를 서비스 지연(Latency) 없이 메시지 큐(Kafka)로 비동기 수집.
2. **Sampling & Auto-Labeling**: 운영 비용 최적화를 위해 전체 로그 중 특정 기준(예: 토큰 수가 비정상적으로 긴 것, 유저 체류시간이 짧은 것) 위주로 일일 1,000건 샘플링.
3. **Metric Calculation (배치 평가)**: Airflow 등의 스케줄러를 통해 자정마다 LLM Judge API를 호출하여 샘플링된 로그의 할루시네이션 여부 채점 및 PSI 지표 산출.
4. **Alert & Trigger (의사결정)**: 측정된 지표가 Threshold(예: 환각률 3% 초과)를 이탈할 경우, Grafana 대시보드 경고 발송 및 **CT(Continuous Training) 파이프라인 웹훅(Webhook) 자동 트리거**.

## Ⅳ. 기존 CI/CD 파이프라인과 CE의 패러다임 비교
소프트웨어 엔지니어링을 넘어서는 AI옵스의 영역.
| 비교 항목 | CI / CD (지속적 통합/배포) | CE (지속적 평가) |
|:---:|:---|:---|
| **실행 주체 및 시점** | 개발자 및 빌드 서버 / 배포 **'전'** 1회성 | MLOps 엔지니어 및 옵저버빌리티 도구 / 배포 **'후'** 상시 |
| **입력 데이터의 성격** | 개발 환경의 **정적(Static)** 테스트 코퍼스 | 상용 환경의 **동적(Dynamic) 라이브 트래픽** 스트림 |
| **성공/실패 판단 기준**| 코드 컴파일 에러 유무, Test Case 통과 여부 (결정론적) | 데이터 분포의 통계적 유의성(P-value), 모델 응답 선호도 (확률론적) |
| **실패 시 후속 액션** | 빌드 중단 (Rollback) | **재학습(Retraining) 트리거 또는 프롬프트 튜닝 지시** |

## Ⅴ. 실무 적용 및 결론
- **판단 지표**: 드리프트 발생 후 감지까지의 소요 시간(MTTD), 오탐률(False Alarm Rate) 최소화, CE 파이프라인 자체의 클라우드 API 호출 비용 최적화.
- **실무 설계**: 통신사 B사의 'AICC(AI 콜센터) 상담 어시스턴트' 운영 환경. 최근 요금제 개편(환경 변화) 이후 챗봇이 과거 요금제를 추천하는 심각한 할루시네이션(Concept Drift) 발생. 조치 방안: Arize AI 기반의 CE 체계 전면 도입. 1) 고객 질의와 챗봇 답변을 벡터DB로 실시간 임베딩하여 로깅. 2) 학습 데이터 벡터 공간과 현재 운영 데이터 벡터 공간의 거리 차이(Cosine Distance)를 10분 단위로 모니터링하는 Drift Detection 설정. 3) 요금제 관련 키워드가 들어온 로그만 필터링하여 LLM Judge로 '응답 정확도' 2차 평가. 4) 정확도가 90% 밑으로 떨어지면 슬랙(Slack) 알람 송출 및 최신 요금제 PDF 매뉴얼을 벡터DB에 자동 재-인덱싱(Re-indexing)하는 복구 루프 완성.
- **결론**: 머신러닝 시스템은 배포되는 그 순간부터 부패하기 시작하는 '생물'과 같다. Continuous Evaluation은 이 생물이 야생(운영 환경)에서 썩어가지 않도록 체온과 맥박을 재는 생명 유지 장치다. 완벽한 모델을 한 번에 배포하려는 망상(Big Bang Release)에서 벗어나, 불완전함을 인정하고 빠르게 붕괴를 감지하여 진화시키는 "상시 관측(Observability)과 자가 치유(Self-Healing)" 아키텍처를 구현하는 것이 AI 서비스 생존의 필수 조건이다.

### 🔀 문제 유형별 목차 전환
- **Ⅱ·Ⅲ 강조 (개념/원리형)**: 드리프트(Drift)의 수학적 탐지 원리 심화 분석. 데이터 분포 차이를 구하기 위한 PSI(Population Stability Index)의 `Sum((Actual% - Expected%) * ln(Actual%/Expected))` 수식 원리와, Kullback-Leibler Divergence를 활용한 통계적 거리 측정 기법 도해.
- **Ⅴ·Ⅵ 강조 (실무/설계형)**: CE 구축 시 폭발하는 LLM API 요금(Evaluation Cost) 방어 아키텍처. 모든 100% 트래픽을 GPT-4(거대 모델)로 평가하는 대신, 싸고 빠른 7B 크기의 SLM(소형 모델)을 1차 라우터로 배치하여 의심스러운 답변(Confidence Score가 낮은 응답)만 샘플링하여 GPT-4로 2차 검증하는 'Tiered Evaluation Routing' 설계 방안.
