# 📖 【암기용】 개념 완전 이해

> 목적: 쿠버네티스를 처음 봐도 완벽히 이해하게 만든다. 시험 답안 양식이 아니라, 이해를 위한 친절한 설명이다.

## 한눈에
- **개요**: 컨테이너화된 애플리케이션의 배포, 확장 및 관리를 자동화해주는 오픈소스 오케스트레이션(Orchestration) 플랫폼
- **왜 필요한가**: 컨테이너가 10개면 사람이 관리할 수 있지만, 1,000개면 어떤 게 죽었는지, 어디에 배포해야 할지 일일이 챙기기 불가능하다. 쿠버네티스는 이를 '알아서' 해준다.
- **핵심 직관**: "수많은 악기(컨테이너)들이 제때 소리를 내고 조화를 이루도록 지휘하는 '오케스트라 지휘자'" 또는 "거대한 선박의 수천 개 컨테이너를 적재적소에 배치하고 관리하는 '항만 터미널 관리 시스템'"

## 깊이 이해
- **배경·문제의식**: 마이크로서비스(MSA)가 확산되면서 관리해야 할 서비스 조각(컨테이너)이 너무 많아졌다. 서버 한 대가 고장 나면 그 안의 서비스들을 다른 서버로 옮겨야 하고(Failover), 사용자가 몰리면 늘려야 한다(Scaling). 이 수동 작업을 자동화하려는 니즈에서 탄생했다.
- **작동 원리**: **선언적 구성(Declarative Configuration)**이 핵심이다. 사용자가 "나는 웹 서버 컨테이너 3개가 항상 떠 있길 원해"라고 '바라는 상태(Desired State)'를 정의하면, 쿠버네티스는 '현재 상태(Current State)'를 계속 감시하며 바라는 상태와 맞추려고 노력(Reconciliation Loop)한다.
- **비유**: 온도 조절기(Thermostat)와 같다. 내가 24도로 설정해두면, 현재 온도가 낮으면 히터를 틀고 높으면 에어컨을 켜서 '항상 24도'를 유지하는 것과 같다.
- **구체 예시**: 서버 10대로 구성된 클러스터에서 컨테이너 배포 명령을 내리면, 쿠버네티스(Scheduler)가 CPU/메모리 여유가 가장 많은 서버를 골라 자동으로 컨테이너를 실행시킨다.
- **흔한 오해·주의점**: "쿠버네티스가 모든 문제를 해결해주는 마법의 도구"는 아니다. 설정이 매우 복잡하고 운영 오버헤드가 크기 때문에, 단순한 웹사이트 하나 운영할 때는 오히려 과한 도구(Overkill)가 될 수 있다.

## 연결 개념
- Docker — 쿠버네티스가 관리하는 대표적인 컨테이너 런타임
- Helm — 쿠버네티스용 패키지 매니저 (복잡한 설정을 템플릿화)
- Service Mesh (Istio) — 쿠버네티스 내부 서비스 간 통신을 더 정교하게 관리

# 📝 【답안용】 시험 답안 템플릿

> 목적: 시험장에서 25분에 그대로 쓰는 답안 양식. 작성방식(추상표현 금지·수치·도식·문제유형 전환)을 엄격히 지킨다.
> 핵심: 쿠버네티스는 선언적 모델(Declarative Model)과 제어 루프(Control Loop), 그리고 핵심 아키텍처(Control Plane vs Worker Node)를 중심으로 기술한다.

## 핵심 인사이트 (3줄 요약)

> 1. **본질**: 쿠버네티스(Kubernetes)는 컨테이너화된 애플리케이션의 라이프사이클 전반(배포, 스케줄링, 자가치유)을 선언적 명세 기반으로 자동화하는 오케스트레이션 플랫폼이다.
> 2. **가치**: 인프라 추상화를 통해 하드웨어 활용률을 극대화하고, 서비스 가용성 보장 및 무중단 배포(Blue-Green, Canary)를 손쉽게 구현한다.
> 3. **판단 포인트**: 복잡한 분산 시스템 운영 효율을 위해 도입하되, 관리형 서비스(EKS, GKE, AKS) 활용 여부와 운영 역량(Ops) 성숙도를 함께 고려해야 한다.

## 출제 의도 및 답안 포인트

| 출제 의도 | 반드시 짚을 핵심 | 감점 회피 포인트 |
|:---|:---|:---|
| 컨테이너 에코시스템 이해도 확인 | Pod, Service, Deployment 등 핵심 오브젝트 | 단순히 "컨테이너 관리 툴"로만 서술 |
| 아키텍처 설계 역량 검증 | Control Plane(API Server, etcd, Scheduler) 구성 요소 | 마스터-노드 구조 및 통신 흐름 누락 |
| 자동화 메커니즘 파악 여부 | 선언적 API, Reconciliation Loop (자가치유) | 수동 조작 중심의 관리 방식으로 오해 |

> 요약: 쿠버네티스의 아키텍처적 구성 요소와 '바라는 상태'를 유지하기 위한 제어 메커니즘을 중심으로 기술한다.

## Ⅰ. 개요 및 필요성

- 정의: 컨테이너화된 애플리케이션의 대규모 클러스터 운영을 자동화하는 구글(Borg) 기반 오픈소스 플랫폼
- 배경: 클라우드 네이티브 환경의 확산으로 수천 개의 컨테이너를 관리하기 위한 자동화된 운영체제(Cloud OS) 필요성 증대
- 필요성: 자가치유(Self-healing), 자동 확장(Auto-scaling), 로드 밸런싱을 통한 시스템 안정성 및 운영 효율성 확보

---

## Ⅱ. 구조 및 구성요소

```text
[쿠버네티스 아키텍처 도식]
User (kubectl) -> [Control Plane] (API Server, Scheduler, CM, etcd)
                      |
        +-------------+-------------+
        |             |             |
[Worker Node 1] [Worker Node 2] [Worker Node 3]
(Kubelet, Proxy)(Kubelet, Proxy)(Kubelet, Proxy)
     [Pod]           [Pod]           [Pod]
```

| 구성요소 | 역할 | 특이사항 |
|:---|:---|:---|
| API Server | 모든 요청의 관문이자 상태값의 입출력 담당 | REST API 제공, etcd와 통신 |
| etcd | 클러스터의 모든 상태를 저장하는 분산 Key-Value DB | 고가용성(HA) 필수, 일관성 중시 |
| Scheduler | 가용 자원 및 제약 사항을 고려하여 Pod 배치 결정 | 노드 필터링 및 점수화(Scoring) |
| Kubelet | 각 노드에서 컨테이너 실행 및 상태 감시 | 파드(Pod)의 라이프사이클 관리 |
| Pod | 쿠버네티스의 최소 배포 단위 | 하나 이상의 컨테이너가 네트워크/볼륨 공유 |

> 요약: 명령을 내리고 상태를 관리하는 컨트롤 플레인과 실제 일을 하는 워커 노드로 구성된 마스터-슬레이브 구조다.

---

## Ⅲ. 동작원리 및 흐름도

```text
[선언적 제어 루프 (Reconciliation Loop) 흐름]
Observe (현재 상태 관찰) -> Diff (바라는 상태와 비교) -> Act (상태 일치를 위한 작업 수행) -> Repeat
```

| 단계 | 처리 내용 | 검증 기준 |
|:---:|:---|:---|
| 1 | 사용자 정의(YAML) 파일 제출 (Deployment 등) | API Server 스키마 유효성 검사 |
| 2 | Scheduler가 적절한 워커 노드 선정 및 바인딩 | 노드 자원(CPU/Mem) 및 어피니티 조건 |
| 3 | 해당 노드의 Kubelet이 컨테이너 런타임에 실행 명령 | 이미지 풀링(Pulling) 및 네트워크 설정 |
| 4 | Controller Manager가 실행 중인 파드 수를 상시 감시 | 장애 발생 시 즉시 재시작(Self-healing) |

> 요약: 사용자가 정의한 '상태'를 etcd에 저장하고, 각 컨트롤러들이 실제 상태를 그에 맞추기 위해 끊임없이 움직인다.

## Ⅳ. 특징

| 구분 | 내용 | 판단 포인트 |
|:---|:---|:---|
| 자가 치유 | 컨테이너 장애 시 자동 재시작 및 노드 이동 | 서비스 중단 시간(Downtime) 최소화 |
| 자동 확장 | 부하에 따른 HPA(Pod), CA(Node) 확장 | 자원 사용 최적화 및 비용 절감 |
| 서비스 디스커버리 | 이름 기반의 부하 분산 및 로드 밸런싱 | Pod IP 변경 시에도 안정적 연결 보장 |

> 요약: 복잡한 분산 시스템의 운영 작업을 표준화된 API로 자동화하여 신뢰성을 높인다.

## Ⅴ. 심화 비교 및 적용 판단

| 구분 | 가상 머신 (VM) | 쿠버네티스 (Container) | 선택 기준 |
|:---|:---|:---|:---|
| 격리 수준 | HW 수준 (Hypervisor) | OS 수준 (Namespace/Cgroup) | 보안 및 격리 요구 사항 |
| 시작 속도 | 분 단위 (OS 부팅 포함) | 초 단위 (프로세스 실행 수준) | 오토스케일링 민첩성 |
| 자원 효율 | 높음 (게스트 OS 오버헤드) | 매우 높음 (커널 공유) | 인프라 비용 및 밀적도 |

> 요약: 레거시 앱은 VM을, 탄력성과 빠른 배포가 중요한 신규 서비스는 쿠버네티스를 선택한다.

| 리스크 | 원인 | 대응 방안 | 확인 지표 |
|:---|:---|:---|:---|
| 보안 위협 | 컨테이너 간 권한 탈취 및 이미지 오염 | RBAC 설정, 이미지 스캔, Network Policy | CVE 점수 및 비인가 접근 로그 |
| 운영 복잡도 | 가파른 학습 곡선 및 관리 오버헤드 | 관리형 서비스(EKS 등) 도입, GitOps 적용 | 리소스 배포 시간 및 오류 발생률 |
| 네트워크 지연 | 복잡한 계층(Service, Ingress)에 따른 Hop 증가 | eBPF 기반 CNI(Cilium) 도입 및 최적화 | P99 Latency 및 패킷 오버헤드 |

> 요약: 보안은 강화된 정책으로, 복잡도는 관리형 서비스로, 성능은 고성능 CNI 도입으로 해결한다.

| 점검 항목 | 목표 기준 | 측정 방법 |
|:---|:---|:---|
| 클러스터 가용성 | 컨트롤 플레인 가용성 99.95% 이상 | 가동 시간 및 API 응답 속도 모니터링 |
| 자원 활용률 | CPU/Mem 할당 대비 실제 사용률 60% 이상 | Prometheus/Grafana 지표 분석 |
| 배포 성공률 | 롤백 발생률 5% 미만 | CI/CD 파이프라인 통계 분석 |

> 요약: 시스템 가용성과 자원 활용 효율성, 그리고 배포 안정성을 통해 도입 성과를 측정한다.

## Ⅵ. 실무 적용 및 결론

**적용 방안 3개:**
1. 하이브리드/멀티 클라우드 구축: 벤더 종속성 없는 쿠버네티스 표준 API를 활용하여 온프레미스와 퍼블릭 클라우드 간의 유연한 워크로드 이동성 확보
2. AI/ML 파이프라인 자동화: Kubeflow를 통해 모델 학습부터 서빙까지의 전 과정을 컨테이너 기반으로 오케스트레이션하여 MLOps 구현
3. GitOps 기반 지속적 배포: ArgoCD를 사용하여 Git 저장소의 명세와 클러스터 상태를 자동으로 동기화함으로써 휴먼 에러 방지 및 추적성 강화

**결론 (2줄):**
- 기술사 판단: 쿠버네티스는 단순한 관리 도구가 아니라 '현대적 데이터센터의 운영체제'로 자리 잡았으며, 효율적인 자원 할당과 보안 격리 설계가 도입의 핵심이다
- 향후 방향: 서버리스(Serverless)와의 경계가 허물어지고(Knative), eBPF 등 커널 기술과 결합하여 관측성과 보안이 내재된 지능형 플랫폼으로 진화할 것이다
