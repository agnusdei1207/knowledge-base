# 📖 【암기용】 개념 완전 이해

> 목적: 구글이 15년간 자사 컨테이너들을 통제하던 극비 기술(Borg)을 세상에 풀어버린, '클라우드 운영체제' 쿠버네티스의 본질을 이해한다.

## 한눈에
- **정의**: 수많은 컨테이너(도커 등)를 여러 대의 서버(Node)에 자동으로 배포하고, 스케일링하며, 장애가 나면 스스로 복구(Auto-healing)하는 **오픈소스 컨테이너 오케스트레이션 플랫폼**
- **필요성**: MSA(마이크로서비스) 시대로 넘어오면서 관리해야 할 컨테이너가 수백~수천 개로 폭증하자, 사람이 일일이 서버에 접속해서 도커를 띄우고 모니터링하는 것이 물리적으로 불가능해졌기 때문
- **핵심 직관**: "도커(Docker)가 '컨테이너(화물)'라면, 쿠버네티스(K8s)는 수천 개의 화물을 전 세계 항구(서버)에 언제, 어떻게 내리고 실을지 통제하는 '항만 컨트롤 타워'"

## 깊이 이해
- **배경(왜 등장했나?)**: 도커(Docker)의 등장으로 "내 PC에선 되는데 서버에선 안 돼"라는 문제는 해결되었다. 하지만 서버가 100대로 늘어나면 "어느 서버에 여유가 있지? 3번 서버가 죽으면 거기 있던 컨테이너는 누가 다시 살리지?"라는 문제가 생겼다. 이를 해결하기 위해 구글이 자사의 천문학적인 컨테이너 관리 시스템 노하우를 바탕으로 만든 K8s가 시장을 완전히 평정했다.
- **작동 원리(어떻게 달성했나?)**: 
  1. **선언적(Declarative) 상태 유지**: 쿠버네티스의 가장 위대한 원리다. "웹 서버 3개를 띄워줘"라고 **'원하는 상태(Desired State)'**를 선언해 두면, K8s는 **'현재 상태(Current State)'**를 계속 감시한다.
  2. **Control Loop**: 만약 서버 하나가 불타서 웹 서버가 2개가 되면, K8s는 "어? 원하는 건 3개인데 지금 2개네?" 하고 즉시 다른 서버에 빈 공간을 찾아 1개를 새로 띄워버린다(Auto-healing).
  3. **추상화된 컴포넌트**: 최소 배포 단위인 **Pod**, 네트워크를 연결하는 **Service**, 무중단 배포를 돕는 **Deployment** 등 인프라를 레고 블록처럼 추상화했다.
- **일상 비유**: 식당 매니저(K8s Master)에게 "항상 요리사(Pod) 5명이 주방(Node)에 있게 해줘"라고 지시서(YAML)를 준다. 매니저는 계속 주방을 쳐다보다가 1명이 화장실에 가면(장애), 즉시 대기실에서 1명을 새로 주방에 밀어 넣어 무조건 '5명'이라는 상태를 유지한다.
- **구체 예시**: 블랙프라이데이 때 쇼핑몰 트래픽이 폭주하면, K8s의 HPA(Horizontal Pod Autoscaler)가 CPU 사용량을 감지하여 결제 컨테이너를 10개에서 100개로 1분 만에 자동으로 늘려준다.
- **흔한 오해/주의점**: "쿠버네티스는 도커를 대체하는 것인가?" → 아니다. 도커는 컨테이너를 '만들고 실행'하는 엔진이고, K8s는 그 컨테이너들을 '지휘'하는 지휘자(Orchestrator)다. (다만 K8s는 최근 도커 엔진 지원을 중단하고 containerd 같은 표준 런타임으로 갈아탔다.)

## 연결 개념
- **Container Orchestration**: K8s가 속해 있는 상위 기술 범주 (Docker Swarm, Mesos 등을 K8s가 다 죽이고 천하 통일함)
- **Microservices Architecture (MSA)**: K8s가 없으면 사실상 운영이 불가능한 현대의 소프트웨어 아키텍처
- **Service Mesh (Istio)**: K8s 안에 떠 있는 수많은 마이크로서비스 간의 복잡한 통신과 보안을 관리해 주는 K8s의 단짝 친구

# 📝 【답안용】 시험 답안 템플릿

## 핵심 인사이트 (3줄 요약)
> 1. **본질**: 쿠버네티스(K8s)는 '선언적 API(Declarative API)'와 '제어 루프(Control Loop)'를 기반으로 수많은 컨테이너의 라이프사이클(배포, 스케일링, 복구)을 자동화하는 컨테이너 오케스트레이션의 사실상 표준(De-facto)이다.
> 2. **가치**: 인프라 환경(온프레미스, 멀티 클라우드)에 종속되지 않는 일관된 운영 환경을 제공하여, 기업의 클라우드 네이티브 전환(Cloud Native Transformation)과 애자일(Agile) 딜리버리를 촉진한다.
> 3. **판단 포인트**: K8s의 3대 핵심 메커니즘(Auto-healing, Auto-scaling, Rolling-update)과 Master-Worker 노드 간의 아키텍처적 상호작용을 완벽히 이해하는 것이 MSA 인프라 설계의 핵심이다.

## Ⅰ. 개요 및 필요성
- **정의**: 호스트 클러스터(다수의 노드) 전체를 논리적인 하나의 서버처럼 다루며, 컨테이너화된 애플리케이션의 배포(Deployment), 확장(Scaling), 관리를 자동화하는 오픈소스 플랫폼 (CNCF 졸업 프로젝트)
- **배경**: Monolithic에서 MSA로의 진화에 따라 수십~수백 개의 컨테이너가 배포되면서, 노드 자원 할당, 컨테이너 간 네트워킹, 로드 밸런싱을 수동으로 관리하는 것이 불가능(Operation Nightmare)해짐
- **필요성**: 인프라 불변성(Immutable Infrastructure) 확보, 선언적 설정을 통한 상태 유지, 높은 가용성(High Availability)의 자동 보장

## Ⅱ. 쿠버네티스 아키텍처 (Master - Worker Node 구조)
쿠버네티스는 중앙에서 통제하는 Control Plane(Master)과 실제 컨테이너가 도는 Worker Node로 구성된다.

```text
[ Control Plane (Master Node) ] ──────────────┐
  │ 1. API Server  : 모든 명령의 진입점 (REST)   │
  │ 2. etcd        : 클러스터 모든 상태(Data) 저장 │
  │ 3. Scheduler   : Pod를 어느 Node에 넣을지 결정 │
  │ 4. Controller  : Desired State 유지 감시    │
  └─────────────────┬─────────────────────────┘
          (명령 하달 및 상태 보고) ▼ 
  ┌─────────────────┴─────────────────────────┐
[ Worker Node 1 ]       [ Worker Node 2 ]
  ├ Kubelet               ├ Kubelet (상태보고/명령수행)
  ├ Kube-proxy (NW)       ├ Kube-proxy
  └ Pod (Container)       └ Pod, Pod ...
```

| 주요 컴포넌트 | 핵심 역할 및 기능 |
|:---|:---|
| **API Server** | `kubectl` 명령어를 받아들이는 중앙 출입구. 모든 컴포넌트는 API Server와만 통신함 |
| **etcd** | 분산 Key-Value 저장소. "현재 어떤 Pod가 떠 있는지, 원하는 상태는 무엇인지"에 대한 단일 진실 공급원(SSOT) |
| **Kubelet** | 각 Worker Node의 선장. Master의 명령을 받아 컨테이너 런타임(containerd)에 컨테이너 생성을 지시 |
| **Kube-proxy**| 노드로 들어오는 네트워크 트래픽을 적절한 Pod로 라우팅하는 네트워크 프록시 (iptables/IPVS) |

## Ⅲ. 논리적 핵심 오브젝트 (K8s Resources)
K8s는 인프라를 추상화된 오브젝트로 다루며, 이를 YAML 파일로 정의(선언)한다.

1. **Pod (파드)**
   - K8s가 생성하고 관리하는 **가장 작은 배포 단위**. 1개 이상의 컨테이너 모음.
   - Pod 내의 컨테이너들은 IP 주소와 스토리지 볼륨을 공유함. (고래 떼를 뜻하는 영어 단어에서 유래)
2. **ReplicaSet (레플리카셋)**
   - "항상 N개의 동일한 Pod가 실행되도록" 유지하는 컨트롤러. (Auto-healing 담당)
3. **Deployment (디플로이먼트)**
   - ReplicaSet을 관리하는 상위 개념. 무중단 배포(Rolling Update, Rollback)의 기준이 됨.
4. **Service (서비스)**
   - 생성/삭제되며 IP가 계속 바뀌는 Pod들에게 **변하지 않는 단일 고정 진입점(IP/DNS)**을 제공하고 로드 밸런싱 수행.

## Ⅳ. 쿠버네티스의 3대 마법 (자동화 메커니즘)
| 메커니즘 | 원리 및 기대 효과 |
|:---|:---|
| **Auto Healing (자가 치유)** | 노드 장애나 컨테이너 크래시로 Pod가 죽으면, Controller Manager가 즉시 이를 감지하고 다른 건강한 노드에 새 Pod를 띄워 **서비스 다운타임 제로(0)** 달성 |
| **Auto Scaling (자동 확장)** | **HPA(Horizontal Pod Autoscaler)**를 통해 CPU/Memory 임계치 초과 시 Pod 개수를 자동으로 늘리고(Scale-out), 트래픽이 줄면 다시 줄임(Scale-in) |
| **Rolling Update (무중단 배포)**| V1을 V2로 업데이트할 때, V2 Pod를 하나 띄우고 V1 Pod를 하나 죽이는 과정을 반복하여, **사용자가 업데이트를 전혀 눈치채지 못하게 배포** 완료 |

## Ⅴ. 기술적 한계 및 운영 리스크 (Day 2 Operations)
| 리스크 요인 | 분석 | 대응 방안 |
|:---|:---|:---|
| **초기 학습 곡선(Learning Curve)** | 오브젝트가 너무 방대하고 러닝 커브가 수직 절벽 수준으로 높아 전담 엔지니어 부족 현상 | 퍼블릭 클라우드의 K8s 관리형 서비스(**EKS, AKS, GKE**)를 도입하여 Master Node 관리 부담 전가 |
| **스토리지 영속성(Stateful)** | Pod는 죽으면 데이터가 날아가는(Stateless) 구조라 DB 등을 K8s에 올리기 까다로움 | **Persistent Volume (PV)**와 StatefulSet을 활용한 스토리지 아키텍처 정밀 설계 |
| **보안 및 접근 통제 복잡성** | 수천 개의 Pod 간 통신이 발생하여 기존 방화벽(IP) 체계 무력화 | **Service Mesh (Istio)** 도입 및 mTLS를 통한 Pod 간 암호화, RBAC 기반의 철저한 권한 제어 |

## Ⅵ. 실무 적용 및 결론
**적용 방안 및 실무 가이드:**
1. **클라우드 네이티브 락인(Lock-in) 방지 전략**: K8s 표준 API를 사용하면 AWS(EKS)에서 작성한 YAML 파일을 그대로 GCP(GKE)나 온프레미스로 들고 가서 배포할 수 있다. 이는 기업의 진정한 하이브리드/멀티 클라우드 전략의 근간이 된다.
2. **GitOps 파이프라인 구축**: ArgoCD 같은 도구를 사용하여, Git 저장소에 K8s YAML 파일이 커밋되면 K8s가 이를 감지하고 자동으로 운영 서버의 상태를 일치시키는(Sync) 모던 CI/CD 파이프라인을 구축한다.

**결론:**
- 쿠버네티스는 단순한 오케스트레이션 도구를 넘어, 전 세계 모든 인프라를 동일한 방식으로 제어할 수 있게 만든 **"현대 클라우드의 운영체제(OS)"**이다.
- AI, 데이터 분석, 백엔드 등 모든 워크로드가 K8s 위로 모여들고 있으며, IT 엔지니어에게 K8s 이해도는 과거 리눅스(Linux)를 다룰 줄 아는 것과 동일한 수준의 필수 역량이 되었다.

### 🔀 문제 유형별 목차 전환
| 문제 유형 | 문제 신호어 | Ⅱ·Ⅲ 강조 (아키텍처/오브젝트) | Ⅳ·Ⅴ 강조 (자동화/운영) |
|:---|:---|:---|:---|
| **인프라 아키텍처형** | "Control Plane", "API Server, Kubelet" | Master-Worker 노드 간의 통신 구조와 etcd의 SSOT(단일 진실 공급원) 역할 도식화 중심 | K8s의 학습 곡선 리스크 및 관리형 서비스(EKS) 도입 당위성 |
| **배포/운영 기술형** | "무중단 배포", "HPA, 자가 치유" | Pod, Deployment, Service 3대 핵심 오브젝트의 상호 연관성 (Label Selector) 설명 | Ⅳ 자동 스케일링 및 Rolling Update의 내부 제어 루프(Control Loop) 메커니즘 전면 배치 |
