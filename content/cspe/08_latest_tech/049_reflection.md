# 📖 【암기용】 개념 완전 이해

> 목적: Reflection을 처음 봐도 완벽히 이해하게 만든다.

## 한눈에
- **개요**: LLM이 자신의 출력을 스스로 검토·비판하고, 피드백을 반영하여 답을 반복 개선하는 자기 수정 추론 패턴
- **왜 필요한가**: 1회 생성(one-shot)은 논리 오류·사실 오류를 포함해도 수정 기회가 없어 답변 품질 한계
- **핵심 직관**: "초안을 쓰고, 스스로 빨간펜으로 고치기를 반복한다"

## 깊이 이해
- **배경·문제의식**: LLM은 autoregressive 특성상 한 번 생성한 토큰을 되돌릴 수 없음. 사람은 글을 쓴 뒤 퇴고하지만, 기본 LLM은 퇴고 없이 제출. Reflexion(Shinn et al., 2023)에서 체계화
- **작동 원리**: ① Actor가 초기 답변 생성 -> ② Evaluator가 답변을 평가(정확성·논리·완성도 점수) -> ③ Self-Reflection이 실패 원인을 자연어로 분석 -> ④ 피드백을 프롬프트에 추가하여 Actor가 재생성 -> ⑤ 평가 통과 또는 최대 반복 횟수(3~5회)까지 반복
- **비유**: 논문을 제출하기 전에 자기 자신이 심사위원이 되어 리뷰하고, 수정본을 다시 제출하는 것
- **구체 예시**: HumanEval 코드 생성에서 1회 생성 pass@1 67% -> Reflexion 3회 반복 시 91%(Shinn et al., 2023). AlfWorld 작업 성공률 75%->97%
- **흔한 오해·주의점**: Reflection은 외부 ground truth 없이 LLM 자체 판단에 의존 -> 모델이 자기 오류를 인식하지 못하면 개선 불가(blind spot). 외부 검증기(테스트 케이스, 도구)와 병행이 효과적

## 연결 개념
- Chain-of-Thought(CoT): Reflection의 내부 추론 단위
- Self-Consistency: 다수결 기반 검증, Reflection의 자기 비판과 상호보완
- Test-Time Compute: Reflection은 TTC를 활용하는 대표 기법


# 📝 【답안용】 시험 답안 템플릿

> 목적: 시험장에서 25분에 그대로 쓰는 답안 양식.

## 핵심 인사이트 (3줄 요약)

> 1. **본질**: LLM이 자기 출력을 평가·비판하고 피드백을 반영해 반복 개선하는 자기 수정 추론 패턴
> 2. **가치**: HumanEval pass@1 67%->91%, 추가 학습 없이 프롬프팅+반복으로 달성
> 3. **판단 포인트**: 검증 가능한 과제(코드·수학)에 효과적, 자기 판단 한계 시 외부 검증기 필수


## Ⅰ. 개요 및 필요성

- 개요: 자기 출력 검토·수정 패턴
- 배경: 1회 생성은 논리·사실 오류를 포함해도 수정 기회가 없고, autoregressive 생성은 이전 토큰을 되돌리지 못함.
- 필요성: critique, revise, verifier, stop condition으로 오류 수정 횟수와 비용 상한을 통제해야 함.


## Ⅱ. 구조 및 구성요소

```text
Actor(생성) -> Evaluator(평가/점수) -> Self-Reflect(원인 분석)
Self-Reflect -> Feedback -> Actor
```

| 구성요소 | 역할 | 특이사항 |
|:---|:---|:---|
| Actor | 프롬프트+피드백 기반으로 답변 생성 | 매 반복마다 이전 피드백 컨텍스트 추가 |
| Evaluator | 답변의 정확성·논리·완성도 점수 산출 | 외부 도구(테스트·검색) 연동 가능 |
| Self-Reflection | 실패 원인을 자연어로 분석·요약 | "왜 틀렸는지"를 명시적으로 서술 |
| Memory | 이전 시도와 피드백을 누적 저장 | 슬라이딩 윈도우 3~5회분 |

> 요약: Actor가 생성, Evaluator가 평가, Self-Reflection이 원인 분석하여 피드백 루프를 형성


## Ⅲ. 동작원리 및 흐름도

```text
문제 입력 -> Actor 초기 답변 -> Evaluator 평가
-> 통과? -Yes-> 최종 답 출력
        -No-> Self-Reflection(원인 분석)
             -> 피드백 추가 -> Actor 재생성 (최대 3~5회)
```

| 단계 | 처리 내용 | 검증 기준 |
|:---:|:---|:---|
| 1 | Actor가 초기 답변 생성 | 프롬프트 포맷 준수 |
| 2 | Evaluator가 점수 산출(0~10) | 임계값 8점 이상 시 통과 |
| 3 | Self-Reflection이 실패 원인 자연어 분석 | 구체적 오류 지점 명시 |
| 4 | 피드백 반영 후 Actor 재생성(최대 3~5회) | 점수 단조증가 여부 확인 |

> 요약: 생성->평가->원인 분석->피드백 반영->재생성의 반복 루프, 최대 3~5회


## Ⅳ. 특징

| 구분 | 내용 | 판단 포인트 |
|:---|:---|:---|
| 1회 생성 대비 | 반복 자기 수정으로 품질 향상 | HumanEval +24%p, AlfWorld +22%p |
| Self-Consistency 대비 | 경로 평가·원인 분석 포함 | 오류 원인 파악 가능, 단순 다수결 아님 |
| 한계 | 모델 blind spot은 자기 검토로 발견 불가 | 외부 검증기(테스트 케이스) 병행 필요 |

> 요약: 검증 가능 과제에서 +22~24%p 향상, blind spot 한계는 외부 검증기로 보완


## Ⅴ. 실무 적용 및 결론

**적용 방안 3개:**
1. CI/CD 파이프라인에 Reflection 코드 리뷰 에이전트 도입, 자동 생성 코드의 테스트 통과율 67%->91%
2. 보고서 자동 생성에 Evaluator로 사실 검증(RAG 교차 확인) 적용, 환각률 18%->5%
3. SQL 쿼리 생성에 실행 결과를 Evaluator로 활용, 쿼리 정확도 72%->93%

**결론 (2줄):**
- 기술사 판단: 검증 수단이 있는 과제(코드 테스트·SQL 실행·사실 검증)면 Reflection, 검증 수단 없으면 Self-Consistency 우선
- 향후 방향: 멀티 에이전트 Reflection(Critic 에이전트 분리)으로 blind spot 완화 진행 중

| 유형 | 문제 신호어 | Ⅲ 강조 | Ⅳ 강조 |
