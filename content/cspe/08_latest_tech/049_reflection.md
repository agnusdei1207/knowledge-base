## 미리 알고가기

- 자기 검토 ($Reflection$): 생성형 AI가 산출한 초안 결과물을 스스로 비판적으로 평가하고 오류를 수정하여 최종 품질을 점진적으로 높여나가는 순환 루프형 추론 기법임
- 크리틱 ($Critic$): 초안 모델이 도출해 낸 결과물에 대해 요구사항 충족 여부, 오류, 문법, 보안 규정 위반을 매의 눈으로 심사하는 평가자 역할임
- 루프 제어기 ($Stop$ $Controller$): 자기 검토 연산이 무한 궤도에 빠지는 것을 방지하기 위해 종료 조건(점수 임계값, 컴파일 통과 여부 등)을 판정하는 모듈임
- 에이전트 워크플로우: LLM을 단순 단답형 질의 응답이 아닌, 계획$\rightarrow$실행$\rightarrow$검토의 프로세스로 묶어 스스로 작동하게 만드는 응용 설계 구조임

## Ⅰ. 개요

- **정의/개념**: Reflection은 모델이 1차 결과(초안)를 빠르게 작성해낸 뒤, 이에 대해 자가 비판(Critic)을 수행하고 그 수정 피드백을 반영해 2차 개정안을 재도출해 내는 에이전틱($Agentic$) 자가 교정 및 반복 생성 디자인 패턴임
- **배경/필요성**: 단 한 번의 단발성 출력($Zero-shot$)으로 복잡한 파이썬 스크립트 작성이나 보고서 검토를 마스터하려 하면 연산 오점과 논리 누락을 필연적으로 동반하므로, 인간 개발자가 코드 리뷰 후 리팩터링하는 구조를 모사하여 정확도를 올리고자 제안됨

## Ⅱ. 특징

- 한 번에 완전한 최적 답을 내야 하는 모델의 가중치적 부담을 덜어주며, 일단 작동하는 초안을 낸 뒤 점진적으로 버그를 소거해 나가는 융통성을 발휘함
- 생성하는 모델(Generator)과 비판하는 모델(Critic)을 각기 다른 페르소나나 프롬프트 템플릿으로 분리 구성함으로써, 오류 검출력을 훨씬 높일 수 있음
- 1차 코드 생성 후 외부 인터프리터(컴파일러)에 올려 돌린 뒤 에러 로그를 직접 분석해 자가 수정하는 도구 피드백($Tool$ $Feedback$) 구조와 유연하게 결합함

## Ⅲ. 종류 및 비교

| 판단 기준 | 단발성 생성 (Zero-shot) | 자기 일관성 (Self-Consistency) | 자기 검토 (Reflection) |
|:---|:---|:---|:---|
| **작동 원리** | 1회성 완성 출력 | 동일 질문의 $K$개 다수결 | 초안 $\rightarrow$ 비판 $\rightarrow$ 수정 루프 순환 |
| **에러 소거 메커니즘** | 운에 의존 (가중치 확률) | 다수결 합의에 의한 오류 상쇄 | 구체적인 피드백 기반의 자가 수정 |
| **적합한 타깃 과제** | 가벼운 일상 질문, 요약 | 단순 수학 문제, 정형화된 분류 | 복잡한 코딩, 수필 작성, 설계안 보완 |
| **추론 지연 시간** | 극도로 낮음 | 낮음 ~ 보통 (병렬 처리 지원) | 다소 높음 (루프 완료 시까지 대기) |

> 요약: 제로샷은 가벼운 소통에, 자기 일관성은 논리 합의에, 자기 검토는 완벽함이 요구되는 실무 텍스트/코드 교정에 특화됨.

## Ⅳ. 구성요소 및 구조

| 구성요소 | 설명 |
|:---|:---|
| 초안 생성기 | 최초의 기획안, 코드 템플릿을 빠르게 배출하는 1차 신경망 층임 |
| 크리틱 ($Critic$) | 작성된 결과물을 룰북에 대조하여 논리적 오점이나 규정 누락을 집어 피드백 텍스트를 적는 감사 층임 |
| 개정 엔진 ($Refiner$) | "이전 결과물 + 크리틱 피드백"을 결합 입력으로 주입받아 수정본을 렌더링하는 재생성 모듈임 |
| 루프 통제 밸브 | 스코어 임계치 돌파나 단위 테스트 통과 시 루프를 차단하고 최종 확정안을 릴리즈하는 조타수임 |

```text
[ Reflection 루프 구조 ]
Input -> [Generator] -> Draft -> [Critic] -> Critique -> [Refiner] -> Revised Draft --\
            ^                                                                          | (Loop check)
            |----------------------------- (If fails Stop Condition) ------------------/
```

## Ⅴ. 원리 및 절차 흐름도

```text
+-------------+     +--------------+     +-------------+     +-------------+
| 초안 릴리즈 | --> | 피드백 생성  | --> | 지시반영 수정| --> | 기준 통과   |
| (1차 생성)  |     | (자가/타 비판) |     | (개정본 배출) |     | 최종안 확정 |
+-------------+     +--------------+     +-------------+     +-------------+
```

1. **초안 출력** — 사용자 요구사항을 바탕으로 완성도와 무관하게 동작 원칙에만 부합하는 1차 답변이나 스크립트를 신속히 인출함
2. **비판 가동** — 크리틱 프롬프트(또는 외부 테스트 실행기)를 돌려, "에러 메시지: SyntaxError" 혹은 "조항 누락"과 같은 정밀 피드백을 기재함
3. **개정 재생성** — 개정 엔진이 바인딩되어 이전 버전의 코드와 실패 보고서를 한눈에 비교 검토하며 수치나 조항을 뜯어고침
4. **루프 차단** — 단위 테스트 결과가 모두 성공 상태(Pass)로 확인되거나 루프 상한선(예: 3회)에 걸리면, 최종본을 확정 릴리즈하고 연산을 해제함

## Ⅵ. 실무 적용 및 유의점

1. 자기 검토 루프 작성 시 평가 기준이 불명확하면 모델이 이전 답변의 장점까지 깎아내려 성능이 오히려 역행하는 '퇴보($Regression$)' 현상이 발생하므로, 반드시 명확한 채점 규칙($Rubric$)을 수립하고, 버전별 평가지 변화 폭 지표를 추적해야 함
2. 종료 조건이 정합적이지 못하면 두 상태 간의 모순을 유발하며 무한 뱅글뱅글 루프를 돌며 서빙 토큰 요금을 기하급수적으로 폭증시키므로, 최대 순환 횟수($Max$ $Iteration$)와 타임아웃 코드를 상태 테이블에 의무 지정하고, 평균 연산 순환 수 지표로 안정성을 모니터링해야 함

## Ⅶ. 결론

- Reflection은 단번에 과업을 완수하려는 과욕 대신 차분한 리뷰와 순차 리팩터링으로 완벽함을 빚어내는 에이전트의 완성식이며, 설계자는 정확한 자가 감정 규칙과 무한 루프 탈출 안전망을 확보하여 상용 서비스의 정확도 신뢰성을 확보해야 함
