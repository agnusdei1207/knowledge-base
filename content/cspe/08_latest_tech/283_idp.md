# 📖 【암기용】 개념 완전 이해

> 목적: IDP를 처음 봐도 완벽히 이해하게 만든다. 시험 답안 양식이 아니라, 이해를 위한 친절한 설명이다.

## 한눈에
- **개요**: 개발자가 애플리케이션의 개발부터 배포, 운영까지 필요한 모든 도구와 인프라 자원을 스스로(Self-service) 사용할 수 있게 해주는 사내 전용 소프트웨어 플랫폼
- **왜 필요한가**: 클라우드 네이티브 환경이 너무 복잡해서, 개발자가 코딩보다 인프라 설정(YAML, 테라폼 등)에 더 많은 시간을 쓰는 문제를 해결하기 위해 필요하다.
- **핵심 직관**: 개발자를 위한 사내용 **'원스톱 서비스 센터'**이자 **'App Store'**다.

## 깊이 이해
- **배경·문제의식**: "DevOps는 좋은데, 내가 왜 네트워크와 보안까지 다 알아야 하지?"라는 개발자의 불만이 커졌다. 인지적 부하(Cognitive Load)가 임계점을 넘은 것이다. 인프라 팀은 매번 반복되는 생성 요청 티켓을 처리하느라 정작 중요한 일(플랫폼 고도화)을 못 한다.
- **작동 원리**: 인프라 전문가가 보안과 표준이 적용된 **'황금 경로(Golden Path)'** 템플릿을 미리 만들어 IDP에 등록한다. 개발자는 이 템플릿을 골라 필요한 정보를 입력하고 '생성' 버튼만 누르면, 뒤에서 자동화 도구들이 서버, DB, CI/CD 라인을 알아서 깔아준다.
- **비유**: 호텔 뷔페와 같다.
    - 예전(티켓 방식): 요리사(인프라 팀)에게 일일이 메뉴를 말하고 만들어 줄 때까지 기다려야 함.
    - IDP: 요리사가 이미 완벽하게 준비해 놓은 **뷔페(IDP)**에서 개발자가 원하는 음식(자원)을 담아오기만 하면 됨. 요리사는 음식이 떨어지지 않게(플랫폼 유지)만 신경 쓰면 됨.
- **구체 예시**: Spotify에서 만든 **Backstage**가 가장 유명한 IDP 구축 프레임워크다.
- **흔한 오해·주의점**: IDP는 단순히 'UI 화면'이 아니다. 그 뒤에 숨겨진 복잡한 인프라를 연결하고 자동화하는 '오케스트레이션 계층'이 핵심이다.

## 연결 개념
- Platform Engineering — IDP를 만드는 행위/학문
- Golden Path — IDP가 제공하는 최적의 표준화된 경로
- Backstage — 대표적인 IDP 오픈소스 포털
- Humanitec — IDP를 비즈니스화한 대표적인 플랫폼 오케스트레이터

# 📝 【답안용】 시험 답안 템플릿

> 목적: 시험장에서 25분에 그대로 쓰는 답안 양식. 작성방식(추상표현 금지·수치·도식·문제유형 전환)을 엄격히 지킨다.
> 핵심: 셀프 서비스 역량과 인프라 추상화를 통한 개발자 인지 부하 감소를 중심으로 IDP의 기술 구조를 서술한다.

## 핵심 인사이트 (3줄 요약)

> 1. **본질**: IDP는 개발자가 인프라의 복잡성을 직접 관리하지 않고도 애플리케이션의 전체 생명주기를 스스로 운영할 수 있도록 인프라 기능을 제품화한 셀프 서비스 플랫폼이다.
> 2. **가치**: 인프라 표준화(Golden Path)를 통한 거버넌스 강화와 개발자의 인지적 부하 감소를 통해 기업의 소프트웨어 딜리버리 성능(DORA metrics)을 극대화한다.
> 3. **판단 포인트**: 단순한 도구의 나열이 아니라, '워크로드 사양'과 '인프라 구성'을 분리하여 추상화하는 플랫폼 오케스트레이션 능력이 핵심이다.

## 출제 의도 및 답안 포인트

| 출제 의도 | 반드시 짚을 핵심 | 감점 회피 포인트 |
|:---|:---|:---|
| IDP의 정의 및 필요성 이해 확인 | 셀프 서비스, 인지 부하(Cognitive Load) 감소 | 단순히 "사내 포털"로만 서술 |
| 핵심 구성요소 및 아키텍처 확인 | 서비스 카탈로그, 스코어카드, 소프트웨어 템플릿 | UI 기능에만 집중 (백엔드 오케스트레이션 누락) |
| 플랫폼 엔지니어링과의 연관성 확인 | Platform as a Product, Golden Path | 두 개념을 별개의 기술로 설명 |

> 요약: 복잡한 인프라를 추상화하여 개발자 생산성을 높이는 내부 플랫폼의 구조와 운영 철학을 중심으로 기술한다.

## Ⅰ. 개요 및 필요성

- 정의: 개발자가 클라우드 네이티브 애플리케이션을 배포 및 운영하는 데 필요한 자원을 스스로 확보하고 관리할 수 있게 해주는 내부용 제품 플랫폼
- 배경: 쿠버네티스 등 현대적 인프라의 복잡성 증가로 개발자의 인지적 부하가 임계치에 도달하여 실제 코드 작성 시간 감소
- 필요성: 인프라 요청 대기 시간(Ticket Wait Time) 제거, 인프라 구성 표준화 및 보안 가드레일 적용, 개발자 경험(DX) 향상

## Ⅱ. 구조 및 구성요소

```text
[ Developer UI / CLI ]
         |
+-------------------------------------------------------+
|        Internal Developer Platform (IDP)              |
|  - Service Catalog (가시성)                            |
|  - Software Templates (Golden Path 제공)              |
|  - TechDocs (중앙 집중식 문서화)                       |
|  - Platform Orchestrator (자원 제어 및 배포)            |
+-------------------------------------------------------+
         |
[ IaC: Terraform / Pulumi ] [ CI/CD: ArgoCD / GitHub Actions ]
         |
[ Cloud Resources / Kubernetes / Security Policy ]
```

| 구성요소 | 역할 | 특이사항 |
|:---|:---|:---|
| Service Catalog | 모든 마이크로서비스와 인프라의 메타데이터 관리 | 소유권, 의존성 가시화 |
| Software Templates | 표준화된 프로젝트/인프라 생성 스크립트 | 황금 경로(Golden Path) 구현체 |
| Scorecards | 서비스의 품질(보안, 가용성 등) 지표 측정 및 시각화 | 모범 사례 준수 유도 |
| Orchestrator | 개발자의 의도를 실제 인프라 명령으로 변환 | 인프라 추상화의 핵심 |

> 요약: 개발자에게는 단순한 입력을 받고, 뒤에서는 복잡한 인프라 도구들을 조율하여 결과를 내놓는 구조다.

## Ⅲ. 동작원리 및 흐름도

```text
[동작 흐름: 템플릿 선택 -> 환경 정의 -> 프로비저닝 -> 등록]
Select Template -> Input Vars -> Trigger Orchestrator -> Result
       |               |               |                 |
(Go API App) ---- (DB Req: Yes) --- (IaC Exec) ---- (Catalog Update)
```

| 단계 | 처리 내용 | 검증 기준 |
|:---:|:---|:---|
| 1 | 템플릿 선택 | 보안팀과 인프라팀이 사전에 검증한 '황금 경로' 템플릿 중 하나를 선택 |
| 2 | 의도 정의 | 개발자가 필요한 추상화된 요구사항(메모리, 저장소, 도메인 등)만 입력 |
| 3 | 오케스트레이션 | IDP가 배경에서 Terraform, ArgoCD 등을 호출하여 실제 인프라 및 앱 배포 수행 |
| 4 | 서비스 등록 | 생성된 서비스의 API 문서와 모니터링 링크를 카탈로그에 자동 업데이트 |

> 요약: 개발자는 '인프라 언어'를 배우지 않고도 '비즈니스 언어'로 필요한 자원을 얻을 수 있게 한다.

## Ⅳ. 특징

| 구분 | 내용 | 판단 포인트 |
|:---|:---|:---|
| 셀프 서비스 | 중앙 부서의 개입 없이 개발자가 즉시 자원 확보 가능 | 대기 시간(Lead Time) 단축 |
| 인지 부하 감소 | YAML이나 인프라 API의 세부 사항을 몰라도 운영 가능 | 추상화 수준(Abstraction) |
| 표준화 및 거버넌스 | 템플릿을 통해 전사 보안 정책 및 인프라 표준 강제 적용 | 가드레일(Guardrail) |
| 제품 중심 사고 | 플랫폼을 하나의 제품으로 보고 지속적 개선 수행 | 피드백 루프 구축 |

> 요약: 개발자에게는 '편의'를, 기업에는 '통제'와 '속도'를 동시에 제공하는 특징을 가진다.

## Ⅴ. 심화 비교 및 적용 판단

| 구분 | 전통적 티켓 방식 | 순수 DevOps 방식 | IDP 기반 방식 |
|:---|:---|:---|:---|
| 요청 처리 | 운영팀에 메일/지라 요청 | 개발자가 YAML 직접 작성 | IDP 포털에서 클릭/입력 |
| 지식 요구 | 낮음 (요청만 하면 됨) | 매우 높음 (인프라 전문가 수준) | 적정 수준 (비즈니스 요구 중심) |
| 응답 속도 | 며칠~몇 주 소요 | 빠름 (직접 하니까) | 매우 빠름 (자동화된 표준) |
| 거버넌스 | 수동 검토 (병목 발생) | 관리 부재 위험 | 자동 검토 (가드레일 적용) |

> 요약: 숙련된 개발자가 부족한 대규모 조직일수록 IDP의 도입 효과가 극대화된다.

| 리스크 | 원인 | 대응 방안 | 확인 지표 |
|:---|:---|:---|:---|
| 섀도우 IT | IDP가 불편하여 개발자가 직접 클라우드 사용 | 개발자 경험(DX) 연구 및 편의성 강화 | IDP 템플릿 사용 비율 |
| 플랫폼 종속성 | 특정 IDP 도구에 인프라 로직이 종속됨 | 표준 IaC(Terraform 등) 기반 플러그인화 | 플랫폼 교체 시 비용 및 시간 |
| 유지보수 부하 | 다양한 팀의 요구사항으로 템플릿 과다 생성 | 템플릿 범용화 및 라이프사이클 관리 | 생성된 템플릿 수 및 활성 사용률 |

> 요약: '사용하고 싶은 플랫폼'을 만드는 것과 템플릿 파편화를 막는 것이 실무의 관건이다.

| 점검 항목 | 목표 기준 | 측정 방법 |
|:---|:---|:---|
| 신규 서비스 배포 시간 | 기존 대비 80% 이상 단축 | 개발 시작~첫 배포 시점 측정 |
| 개발자 행복도 | NPS(Net Promoter Score) 7.0 이상 | 사내 정기 설문 조사 |
| 보안 취약점 발견율 | 표준 템플릿 사용 시 0건 지향 | 정기 보안 스캔 결과 분석 |

> 요약: 개발 효율성 지표와 함께 플랫폼을 통한 보안/표준 준수율을 핵심 성과 지표(KPI)로 관리해야 한다.

## Ⅵ. 실무 적용 및 결론

**적용 방안 3개:**
1. Backstage 도입: 오픈소스 기반의 포털을 구축하여 파편화된 문서와 자원을 하나로 통합 가시화
2. Golden Path 수립: 가장 빈번한 프로젝트 유형(예: Java Spring Microservice)부터 표준 템플릿화하여 보급
3. 가드레일 자동화: OPA(Open Policy Agent) 등을 IDP와 연동하여 부적절한 자원 요청을 실시간 차단

**결론 (2줄):**
- 기술사 판단: IDP는 DevOps의 성숙도를 한 단계 높여 조직 전체의 인지 부하를 최적화하는 핵심 인프라 전략이다.
- 향후 방향: 단순 자동화를 넘어 AI가 개발자의 의도를 읽고 인프라를 최적 설계해주는 지능형 IDP로 발전할 것이다.
