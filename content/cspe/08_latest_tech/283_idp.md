## 미리 알고가기

- IDP는 Platform Engineering의 대표 구현 산출물로 개발자가 셀프서비스로 공통 기능을 이용하게 하는 내부 플랫폼임
- 포털만 뜻하는 것이 아니라 API와 자동화와 템플릿까지 포함한 서비스 묶음임
- golden path와 개발자 경험 지표를 중심으로 이해하는 것이 적절함

## Ⅰ. 개요

- **정의/개념**: Internal Developer Platform은 개발팀이 배포와 환경 생성과 보안 설정과 관측 연결 같은 공통 운영 기능을 셀프서비스로 사용할 수 있게 제공하는 내부 플랫폼 제품임
- **배경/필요성**: 개발팀마다 인프라와 배포 구성을 개별 관리하면 속도와 품질과 보안 수준이 불균형해져 내부 개발자 플랫폼을 통한 표준화가 요구됨

## Ⅱ. 특징

- 개발자 입장에서 복잡한 인프라를 추상화해 사용성을 높임
- 템플릿과 자동화로 서비스 생성 시간을 줄임
- 표준 보안과 관측 구성을 기본값으로 제공할 수 있음
- 지나친 추상화는 예외 요구를 숨겨 우회 경로를 만들 수 있음

## Ⅲ. 종류 및 비교

| 판단 기준 | IDP | Self Service Portal | Shared Scripts Repo |
|:---|:---|:---|:---|
| 범위 | 포털, API, 템플릿, 자동화 | UI 중심 | 스크립트 제공 중심 |
| 표준화 강도 | 높음 | 중간 | 낮음 |
| 개발자 경험 | 높음 | 중간 | 낮음 |
| 거버넌스 연계 | 강함 | 중간 | 약함 |

## Ⅳ. 구성요소 및 구조

| 구성요소 | 설명 |
|:---|:---|
| Developer Portal | 서비스 생성과 배포와 운영 기능을 노출하는 사용자 인터페이스이자 진입점임 |
| Platform API | 포털과 외부 도구가 동일한 기능을 사용할 수 있게 하는 자동화 인터페이스 계층임 |
| Golden Path Template | 서비스 종류별 권장 구성과 보안과 관측 설정을 기본값으로 제공하는 표준 템플릿임 |
| Workflow Automation | 환경 생성과 CI CD 연결과 정책 검증을 자동 수행해 수작업을 제거하는 실행 계층임 |
| Governance Control | 권한과 정책과 감사 기록을 연결해 셀프서비스 속도와 통제를 함께 유지하는 관리 계층임 |

```text
+----------------+    +----------------+    +----------------+
| Developer      | -> | Portal / API   | -> | Automation     |
+----------------+    +----------------+    +----------------+
                                  |
                                  v
                           Golden Path / Governance
```

## Ⅴ. 원리 및 절차 흐름도

```text
+-------------+    +-------------+    +-------------+    +-------------+    +-------------+
| 서비스 요청   | -> | 템플릿 선택  | -> | 자동 생성    | -> | 정책 검증    | -> | 배포 및 운영  |
+-------------+    +-------------+    +-------------+    +-------------+    +-------------+
```

1. **서비스 요청**: 개발자가 새 서비스나 환경 생성을 요청함
2. **템플릿 선택**: 용도에 맞는 golden path를 선택함
3. **자동 생성**: 리포지터리와 파이프라인과 인프라를 자동 구성함
4. **정책 검증**: 보안과 권한과 태깅 규칙을 검증함
5. **배포 및 운영**: 생성된 서비스가 표준 운영 흐름으로 연결됨

## Ⅵ. 문제점 및 해결 방안

1. 문제: 포털 중심으로만 설계하면 API 자동화 수요를 충족하지 못해 플랫폼 활용 범위가 제한될 수 있음
   - 해결방안: API first IDP design을 적용하고 API usage ratio와 manual portal dependency rate로 검증함
2. 문제: 템플릿이 실제 팀 요구를 반영하지 못하면 개발자가 표준 경로를 버리고 개별 도구를 우회 사용하게 될 수 있음
   - 해결방안: template evolution process와 developer feedback backlog를 적용하고 golden path adoption rate와 bypass configuration count로 검증함
3. 문제: 셀프서비스 속도만 강조하면 권한과 감사 추적이 약해져 운영 통제가 흔들릴 수 있음
   - 해결방안: policy as code와 audit trail integration을 적용하고 non compliant provision rate와 audit trace completeness로 검증함

## Ⅶ. 적용 사례

- 플랫폼 팀이 API 우선 구조를 채택하며 확인 지표는 API usage ratio와 manual portal dependency rate임
- 개발자 플랫폼이 템플릿 개선 루프를 운영하며 확인 지표는 golden path adoption rate와 bypass configuration count임
- 엔터프라이즈 IDP가 정책형 거버넌스를 적용하며 확인 지표는 non compliant provision rate와 audit trace completeness임

## Ⅷ. 결론

IDP는 개발자 생산성을 높이는 도구가 아니라 표준화와 셀프서비스와 거버넌스를 함께 구현하는 내부 플랫폼 제품으로 설계되어야 함.
