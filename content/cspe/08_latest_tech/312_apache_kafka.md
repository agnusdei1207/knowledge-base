# 📖 【암기용】 개념 완전 이해

> 목적: Apache Kafka를 처음 봐도 완벽히 이해하게 만든다. 시험 답안 양식이 아니라, 이해를 위한 친절한 설명이다.

## 한눈에
- **개요**: 대규모 데이터를 실시간으로 주고받기 위해 설계된 고성능 분산 이벤트 스트리밍 플랫폼 (메시지 브로커)
- **왜 필요한가**: 수많은 서버(소스)와 시스템(타겟)이 직접 연결되면 관리가 안 되고 복잡해지는데(Spaghetti), 중간에서 이들을 깔끔하게 중계하고 데이터를 안전하게 보관해주는 '중앙 터미널'이 필요했기 때문이다.
- **핵심 직관**: "데이터의 홍수를 받아내어 안전하게 저장하고, 필요한 곳에 필요한 만큼 나누어주는 거대한 '데이터 파이프라인'이자 '중앙 저장소'."

## 깊이 이해
- **배경·문제의식**: 링크드인(LinkedIn)에서 데이터가 급증하자 기존의 메시징 시스템(RabbitMQ 등)으로는 처리량과 저장 용량을 감당할 수 없었음. 데이터를 디스크에 순차적으로 기록하여 성능을 높이고, 여러 대의 서버로 확장 가능한 시스템이 필요했음.
- **작동 원리**: 발행-구독(Pub-Sub) 모델임. 생산자(Producer)가 데이터(Event)를 토픽(Topic)에 던지면, 소비자(Consumer)가 원하는 만큼 가져감. 데이터를 메모리가 아닌 디스크에 순차적(Append-only)으로 저장하여 성능을 뽑아내고, 유실되지 않게 복제(Replication)함.
- **비유**: 신문사와 구독자 시스템과 같음. 신문사(Producer)는 신문(Data)을 발행해서 지점(Topic)에 쌓아둠. 구독자(Consumer)는 자기가 원할 때 신문을 가져가서 읽음. 신문이 이미 배달되었어도 지점에는 일정 기간 신문이 남아있어서(Retention), 나중에 다시 읽거나 새로 온 구독자가 예전 신문을 볼 수도 있음.
- **구체 예시**: 넷플릭스가 사용자의 모든 클릭 로그를 카프카로 모음. 이 데이터는 동시에 실시간 추천 엔진, 로그 저장소, 결제 정산 시스템으로 각각 전달되어 활용됨.
- **흔한 오해·주의점**: 단순한 '전달자'가 아님. 데이터를 일정 기간 '저장'하는 기능이 강력하여, 소비자가 장애가 나도 나중에 복구해서 읽을 수 있는 '버퍼' 역할을 훌륭히 수행함.

## 연결 개념
- Pub-Sub Model - 카프카의 기본 통신 방식
- Zookeeper / KRaft - 카프카 클러스터를 관리하는 코디네이터
- Kafka Connect / Streams - 카프카 주변 생태계 (연결 및 실시간 처리)

# 📝 【답안용】 시험 답안 템플릿

> 목적: 시험장에서 25분에 그대로 쓰는 답안 양식. 작성방식(추상표현 금지·수치·도식·문제유형 전환)을 엄격히 지킨다.
> 핵심: 분산 아키텍처(Broker, Partition, Replication), 고성능 비결(Zero Copy, Page Cache), 소비자 그룹(Consumer Group)의 동작 원리를 기술적으로 명시한다.

## 핵심 인사이트 (3줄 요약)

> 1. **본질**: Apache Kafka는 고성능, 확장성, 가용성을 갖춘 분산 메시지 브로커이자 분산 커밋 로그(Distributed Commit Log) 기반의 이벤트 스트리밍 플랫폼이다.
> 2. **가치**: 시스템 간 결합도(Decoupling)를 낮추고, 초당 수백만 건의 이벤트를 유실 없이 수용하여 실시간 분석과 배치를 위한 통합 데이터 허브 역할을 수행한다.
> 3. **판단 포인트**: 파티셔닝(Partitioning)을 통한 병렬 처리와 복제(Replication)를 통한 장애 내결함성 확보가 대규모 아키텍처 설계의 핵심이다.

## 출제 의도 및 답안 포인트

| 출제 의도 | 반드시 짚을 핵심 | 감점 회피 포인트 |
|:---|:---|:---|
| 카프카 핵심 아키텍처 이해 확인 | Topic, Partition, Offset, Broker, Replication | 용어의 혼용(Topic vs Partition) 주의 |
| 고성능 실현 기술 파악 능력 | Zero Copy, Sequential I/O, Page Cache | 단순히 "속도가 빠르다"는 서술 지양 |
| 분산 시스템의 특징 및 운영 역량 | ISR(In-Sync Replicas), Consumer Group, Rebalancing | 장애 복구 메커니즘 설명 누락 |

> 요약: 카프카는 디스크 기반의 순차 로그 기록 방식을 통해 처리량과 신뢰성을 동시에 극대화한 분산 메시징 시스템이다.

---

## Ⅰ. 개요 및 필요성

- 정의: 실시간 스트리밍 데이터를 처리하기 위해 설계된 분산 커밋 로그 기반의 발행-구독(Pub-Sub) 모델 메시징 플랫폼
- 배경: 데이터 소스와 타겟 시스템 간의 복잡한 연결(Spaghetti Architecture), 기존 메시지 큐의 성능 및 확장성 한계
- 필요성: 시스템 간 비동기 통합(Decoupling), 실시간 이벤트 가공, 대규모 로그 수집 및 버퍼링

---

## Ⅱ. 구조 및 구성요소

```text
[ Producer ] --(Send)--> [ Topic (Partition 0, 1, 2...) ] --(Poll)--> [ Consumer Group ]
                               |
                   [ Broker 1 (Leader/Follower) ]
                   [ Broker 2 (Leader/Follower) ]
                   [ Broker 3 (Leader/Follower) ]
```

| 구성요소 | 역할 | 특이사항 |
|:---|:---|:---|
| Broker | 카프카 서버 인스턴스, 데이터 저장 및 중계 | 클러스터로 구성 |
| Topic | 메시지를 구분하는 논리적 단위 | 디렉터리와 유사 |
| Partition | 토픽을 분할하여 병렬 처리를 가능하게 하는 물리적 단위 | 순서 보장 단위 |
| Producer/Consumer | 이벤트를 생성하여 보내는 주체 / 가져가서 처리하는 주체 | Push/Pull 모델 기반 |
| Zookeeper/KRaft | 클러스터 메타데이터 관리 및 컨트롤러 선출 | 카프카의 두뇌 역할 |

> 요약: 토픽을 파티션으로 쪼개어 여러 브로커에 분산 저장함으로써 병렬 처리와 고가용성을 달성한다.

---

## Ⅲ. 동작원리 및 흐름도 (고성능 및 신뢰성 메커니즘)

```text
Write: Producer -> Broker (Leader) -> Sequential I/O (Disk) -> Replicas (ISR)
Read: Consumer (Pull) -> Page Cache -> Zero Copy -> Network Card -> Consumer
```

| 단계 | 처리 내용 | 검증 기준 |
|:---:|:---|:---|
| 1 | 메시지 발행 | 프로듀서가 키(Key)를 기반으로 특정 파티션에 전송 | - |
| 2 | 데이터 기록 | 브로커가 OS 페이지 캐시를 거쳐 디스크에 순차 기록 | Sequential I/O 성능 활용 |
| 3 | 데이터 복제 | 팔로워 브로커들이 리더로부터 데이터를 복제 | ISR(In-Sync Replicas) 유지 |
| 4 | 메시지 소비 | 컨슈머가 오프셋(Offset)을 관리하며 필요한 만큼 폴링 | Zero Copy를 통한 커널-유저 공간 복사 생략 |

> 요약: 페이지 캐시와 Zero Copy 기술로 CPU/메모리 부하를 줄이고, ISR 구조로 데이터 유실을 방지한다.

## Ⅳ. 특징

| 구분 | 주요 특징 | 상세 내용 |
|:---|:---|:---|
| 고성능 | Throughput 최적화 | 초당 수백만 건 처리, 배치 전송 및 압축 지원 |
| 확장성 | Scale-out | 브로커 및 파티션 추가를 통한 선형적 성능 확장 |
| 영속성 | Disk Persistence | 메시지를 디스크에 저장하여 일정 기간 보관 (Retention) |
| 고가용성 | Replication & Failover | 복제본을 통한 데이터 안전 보장 및 리더 자동 선출 |
| 병렬성 | Consumer Group | 파티션과 컨슈머를 1:1 매핑하여 대량의 데이터 병렬 처리 |

> 요약: 성능(Speed), 확장성(Scale), 안전성(Durability) 삼박자를 고루 갖춘 분산 아키텍처이다.

## Ⅴ. 심화 비교 및 적용 판단

| 구분 | RabbitMQ (전통적 MQ) | Apache Kafka | 선택 기준 |
|:---|:---|:---|:---|
| 데이터 처리 | 전달 후 즉시 삭제 (Queue) | 보관 기간 동안 유지 (Log) | 데이터 재처리 필요성 |
| 통신 모델 | Smart Broker (복잡한 라우팅) | Dumb Broker / Smart Consumer | 라우팅 복잡도 vs 처리량 |
| 처리량 | 낮음 (수천~수만 TPS) | 매우 높음 (수백만 TPS) | 데이터 부하 규모 |
| 우선순위 | 메시지 개별 확인(ACK) 및 우선순위 | 순차적 처리 및 처리량 중심 | 순밀성 vs 처리량 |

> 요약: 복잡한 비즈니스 로직과 즉각적 전달은 RabbitMQ, 대규모 데이터 스트리밍과 로그 통합은 Kafka가 적합하다.

| 리스크 | 원인 | 대응 방안 | 확인 지표 |
|:---|:---|:---|:---|
| Consumer Lag | 컨슈머 처리 속도 저하 | 파티션 및 컨슈머 증설, 로직 최적화 | Lag (Current - Log End Offset) |
| Data Loss | 비정상 종료 및 복제 미완료 | acks=all 설정, min.insync.replicas 상향 | Unclean Leader Election 발생 건수 |
| Rebalancing 부하 | 컨슈머 추가/제거 시 일시 중단 | 컨슈머 그룹 관리 최적화, 정적 그룹 설정 | Rebalance 소요 시간 |

> 요약: 컨슈머 지연(Lag)과 데이터 유실(Loss) 방지를 위한 튜닝이 운영의 핵심이다.

| 점검 항목 | 목표 기준 | 측정 방법 |
|:---|:---|:---|
| 처리량 (TPS) | 설계 목표(예: 100만 TPS) 달성 | Producer/Consumer Throughput 측정 |
| 가용성 (SLA) | 연간 99.99% 가용성 유지 | 브로커 장애 시 리더 전환 시간 측정 |
| 정합성 보장 | 중복/유실 발생 0건 | 감사 로그 및 멱등성(Idempotent) 설정 확인 |

> 요약: 도입 효과는 초당 처리량, 장애 복구 시간, 그리고 데이터 유실 유무로 검증한다.

## Ⅵ. 실무 적용 및 결론

**적용 방안 3개:**
1. **중앙 로그 수집 허브**: 전사 마이크로서비스(MSA)의 로그를 카프카로 집결시켜 ELK나 S3로 분산 전달하는 파이프라인 구축
2. **실시간 이벤트 처리(CEP)**: 카프카 스트림즈(Kafka Streams)를 활용해 윈도우 기반 집계나 이종 데이터 조인을 수행하여 실시간 지표 산출
3. **데이터베이스 동기화(CDC)**: DB의 변경분을 카프카로 추출(Debezium 등 활용)하여 타 DB나 검색 엔진(ES)에 실시간 반영

**결론 (2줄):**
- 기술사 판단: 카프카는 현대 데이터 아키텍처의 신경계이며, 시스템 간 느슨한 결합과 실시간 가용성을 보장하는 가장 강력한 표준이다.
- 향후 방향: KRaft 도입을 통한 관리 간소화, 서버리스 카프카(Confluent 등) 확대, 그리고 AI 에이전트의 데이터 피딩(Feeding) 채널로서 역할이 증대될 것이다.
