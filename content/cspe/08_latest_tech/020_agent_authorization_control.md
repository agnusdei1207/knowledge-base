# 📖 【암기용】 개념 완전 이해

## 한눈에
- **개요**: 에이전트 권한통제는 **AI 에이전트**가 호출할 수 있는 **도구·데이터·행동 범위**를 서버 측 정책으로 제한하는 **접근제어** 체계다. 사람 계정에 RBAC/ABAC를 적용하듯 에이전트에도 최소 권한 원칙을 적용하되, 프롬프트가 아닌 서버 게이트웨이에서 집행한다.
- **왜 필요한가**: 에이전트는 자연어 명령을 해석해 실제 시스템을 조회·변경·삭제할 수 있으며, 프롬프트 인젝션(186 참조)으로 의도하지 않은 도구 호출이 유도될 수 있다. 프롬프트에 "~하지 마"라고 써도 모델이 이를 준수한다는 보장이 없으므로, 서버 측에서 호출 자체를 차단하는 권한 통제가 필수다.
- **핵심 직관**: 사원에게 열쇠를 줄 때 건물 마스터키를 주는 것이 아니라 자기 사무실 키만 주고, 서버실은 관리자 승인 후에만 출입하게 하는 것이다. 에이전트에도 똑같이 직무에 필요한 최소 도구만 열어주고 고위험 행동은 사람 승인을 거치게 한다.

## 핵심 용어 정리 (내부에 등장하는 것들)

| 용어/표기 | 의미 | 비유·예 |
|:---|:---|:---|
| 접근제어(상위 키워드) | 주체가 객체에 접근할 수 있는 범위를 제한하는 보안 메커니즘 | 건물 출입 통제 시스템 |
| RBAC(Role-Based) | 역할(관리자·운영자·조회자)에 권한을 묶어 부여하는 방식 | "운영팀"이면 배포 가능, "개발팀"이면 조회만 |
| ABAC(Attribute-Based) | 속성(시간·위치·데이터 민감도)을 조합해 판단하는 방식 | 근무시간+사내 IP면 허용, 외부 IP면 차단 |
| 최소 권한 원칙(PoLP) | 업무에 필요한 최소한의 권한만 부여하는 원칙 | 택배기사에게 대문 열쇠만 주고 금고 열쇠는 안 줌 |
| Policy Decision Point(PDP) | 허용·거부를 판단하는 논리 엔진 | 출입 심사관 |
| Policy Enforcement Point(PEP) | PDP 판단을 실제 집행하는 지점(게이트웨이) | 출입문 잠금장치 |
| Tool Gateway | 에이전트 도구 호출을 중개하며 allowlist·rate limit을 적용하는 프록시 | API 게이트웨이의 에이전트 전용 버전 |
| Human-in-the-Loop Approval | 고위험 행동 실행 전 사람의 명시적 승인을 요구하는 절차 | 은행 대출 최종 승인은 사람이 함 |
| 위험등급(Risk Level) | 도구 호출의 영향도를 분류한 등급(조회/변경/관리) | 화재 위험도에 따라 소화기 배치가 다른 것 |

## 깊이 이해
- **배경·문제의식**: 에이전트 상태관리(019)가 "작업을 어디까지 했는가"를 추적한다면, 권한통제는 "이 작업을 할 자격이 있는가"를 판단한다. 기존 시스템의 RBAC을 그대로 쓰면 에이전트가 사용자 전체 권한을 상속해 과다 권한이 되고, 프롬프트에 금지사항을 쓰면 인젝션이나 모델 오해석으로 우회된다.
- **작동 원리(어떻게+왜)**: ① 사용자가 에이전트에 작업을 요청하면 사용자 토큰(OAuth)과 에이전트 서비스 계정(workload identity)을 분리 인증한다. ② 에이전트가 도구를 호출하려 할 때 Tool Gateway의 PDP가 {사용자 역할, 에이전트 역할, 도구 위험등급, 시간·위치 속성}을 평가한다. ③ 조회(Low)는 자동 허용, 변경(Medium)은 율제한+로깅, 관리·삭제(High)는 Human Approval을 요구한다. ④ 허용·거부·승인 이벤트 전부를 감사로그(021)로 기록한다.
- **비유**: 회사 문서 시스템에서 일반 직원(에이전트)은 문서 "읽기"는 자유지만, "편집"은 팀장 승인이 필요하고, "삭제"는 관리자만 가능하다. 에이전트가 "이 문서를 삭제해줘"라고 요청해도, 서버가 권한 없음으로 거부하고 로그를 남긴다.
- **구체 예시**: 장애 대응 에이전트가 로그 조회(Low — 자동 허용)는 즉시 실행하지만, 방화벽 규칙 변경(High)은 보안 담당자에게 Slack 승인 요청을 보내고 10분 내 승인되면 실행, 미승인이면 거부하고 Trace ID와 거부 사유를 기록한다.
- **흔한 오해·주의점**: "시스템 프롬프트에 '결제 API를 호출하지 마'라고 쓰면 충분하다"는 위험한 오해다. 프롬프트 지침은 모델 내부에서 처리되어 우회가 가능하며(인젝션), 감사 증거로도 부적합하다. 권한통제는 반드시 서버 측 PDP/PEP에서 정형 정책으로 집행해야 한다.

## 연결 개념
- 에이전트 상태관리(019) — 권한통제를 통과한 도구 호출의 진행 상태를 추적하는 체계
- 에이전트 감사로그(021) — 허용·거부·승인 이벤트의 감사 기록 측면
- 에이전트 가드레일(029) — 권한통제와 별도로 출력·행동의 안전성을 제어하는 보완 계층

# 📝 【답안용】 시험 답안 템플릿

## 핵심 인사이트 (3줄 요약)

> 1. **본질**: 에이전트 권한통제는 도구·데이터·행동 범위를 서버 측 정책(PDP/PEP)으로 제한하는 접근제어 체계임.
> 2. **가치**: 프롬프트 인젝션·과다 권한·오작동에 의한 비인가 시스템 변경 사고를 차단함.
> 3. **판단 포인트**: 사용자-에이전트 위임 분리, RBAC/ABAC, 도구 위험등급, Human Approval, 감사 연동을 함께 설계해야 함.

## 출제 의도 및 답안 포인트

| 출제 의도 | 반드시 짚을 핵심 | 감점 회피 포인트 |
|:---|:---|:---|
| AI 에이전트 실행 권한 제한 설계 | 사용자-에이전트 위임 분리, PDP/PEP, 도구 위험등급 | 프롬프트 지침을 권한통제로 오해, 서버 측 집행 누락 |
| 고위험 행동 승인·감사 체계 | Human Approval, Tool Gateway allowlist, SIEM 감사 | 조회·변경 권한 미분리, 승인 절차 없이 자동 실행 |

> 요약: 프롬프트가 아닌 서버 측 정형 정책 집행과 위험등급별 승인·감사를 설계해야 감점을 피함.

---

## Ⅰ. 개요 및 필요성

- 개요: AI 에이전트의 도구·데이터 접근을 서버 측 정책(PDP/PEP)으로 제한하는 접근제어 체계임
- 배경: 프롬프트 지침은 모델 내부 처리로 인젝션 우회가 가능하며 감사 증거로 부적합함
- 필요성: 최소 권한 원칙과 위험등급별 승인 정책을 서버 게이트웨이에서 집행해야 비인가 변경을 차단함

---

## Ⅱ. 구조 및 구성요소

```text
사용자 토큰 + Agent 서비스 계정 -> PDP(정책 판단) -> Tool Gateway(PEP, 집행)
                                      |                     |
                                      +-> RBAC/ABAC 평가    +-> allowlist/rate limit
                                      |
                                      +-> Audit Log -> SIEM 연동
```

| 구성요소 | 역할 | 특이사항 |
|:---|:---|:---|
| Identity Layer | 사용자·에이전트 신원 분리 인증 | OAuth 위임 토큰, workload ID |
| PDP(Policy Decision) | 역할·속성·위험등급 기반 허용·거부 판단 | RBAC+ABAC+risk score 조합 |
| Tool Gateway(PEP) | 도구 호출 집행·차단 | allowlist, rate limit, 스키마 검증 |
| Audit Log | 허용·거부·승인 이벤트 기록 | Trace ID, 입력 해시, 거부 사유 |

> 요약: 사용자-에이전트 위임을 분리 인증하고, PDP가 판단·Tool Gateway가 집행·감사 로그가 기록함.

---

## Ⅲ. 동작원리 및 흐름도

```text
요청 수신 -> 사용자·에이전트 인증 -> 도구 위험등급 판정
  -> PDP 정책 평가 -> 자동허용/Human Approval 요구/거부 -> 실행·감사 기록
```

1. 인증: 사용자 OAuth 토큰과 에이전트 workload ID를 분리 검증하고 권한 범위를 확인함
2. 위험등급 판정: 호출 대상 도구를 조회(Low)·변경(Medium)·관리/삭제(High)로 분류함
3. 정책 평가: PDP가 {사용자 역할, 에이전트 역할, 도구 등급, 시간·위치}를 평가해 허용·승인·거부를 결정함
4. 집행·감사: Tool Gateway가 결정을 집행하고, 허용·거부·승인 이벤트를 Trace ID와 함께 감사 로그에 기록함

> 요약: 인증→위험등급 분류→정책 평가→집행·감사 순서로 도구 호출 전 권한을 검증함.

---

## Ⅳ. 특징

- 서버 측 집행: 프롬프트 지침과 달리 PDP/PEP에서 정형 정책으로 집행하므로 인젝션 우회가 불가함
- 위험등급 분리: 조회·변경·관리를 구분해 등급별로 자동허용·율제한·사람 승인을 차등 적용함
- 위임 분리: 사용자 전체 권한을 에이전트에 상속하지 않고, 직무별 최소 권한만 위임함
- 감사 연동: 모든 허용·거부·승인 이벤트가 Trace ID로 감사 로그(021)에 기록됨
- 동적 정책: ABAC 속성(시간·위치·데이터 민감도)으로 런타임 조건에 따라 권한을 조정함

---

## Ⅴ. 심화 비교 및 적용 판단

| 구분 | 프롬프트 지침 | 서버 측 권한통제 | 선택 기준 |
|:---|:---|:---|:---|
| 집행 위치 | 모델 내부(우회 가능) | PDP/PEP 서버(우회 불가) | 변경·삭제 작업은 서버 측 필수 |
| 통제 정밀도 | 자연어 규칙(해석 오차) | RBAC/ABAC 정형 정책 | 정형 정책이 감사·규제 요건 충족 |
| 감사 증거 | 대화 로그(비정형) | 허용·거부·승인 이벤트(정형) | 규제 대상 업무는 SIEM 연동 필수 |

> 요약: 프롬프트 지침은 보조 수단이고, 변경·삭제·규제 대상 업무는 서버 측 정형 정책이 필수임.

**리스크·대응:**
- 과다 권한: 에이전트에 관리자 권한 부여 → 직무별 최소 권한, 조회/변경/관리 등급 분리 (지표: Agent당 평균 권한 수 5개 이내)
- 프롬프트 인젝션: 악의적 입력으로 비인가 도구 호출 유도 → 입력 스키마 검증, allowlist, 위험등급별 차단 (지표: 비허용 호출 차단율 99.9%)
- 승인 우회: 고위험 작업 자동 실행 → 변경·삭제는 Human Approval 필수, 승인 SLA 10분 (지표: 미승인 실행 건수 월 0건)

**도입 후 점검 지표:**
- 권한 최소화: Agent당 평균 권한 수 — IAM 정책 리뷰로 분기별 확인
- 차단 정확도: 비허용 호출 차단율 99.9% — Tool Gateway 로그 분석

---

## Ⅵ. 실무 적용 및 결론

**적용 방안 3개:**
1. 사용자 OAuth 토큰과 에이전트 workload ID를 분리하고, 도구별 조회/변경/관리 위험등급을 정의함
2. Tool Gateway에서 allowlist·rate limit·입력 스키마 검증을 적용하고, High 등급은 Human Approval을 필수로 설정함
3. 모든 허용·거부·승인 이벤트를 SIEM으로 전송하고, 이상 호출 패턴은 SOAR 자동 대응과 연계함

**결론:**
- 기술사 판단: AI 에이전트에는 사람 계정보다 좁은 최소 권한을 부여하고 변경형 작업은 반드시 사람 승인을 거치게 설계함
- 향후 방향: 에이전트 권한통제는 Zero Trust·IAM·AI Gateway가 결합된 실행 보안 계층으로 발전함
