## Ⅰ. 개요
- **정의**: AI 에이전트의 도구(Tool) 사용 범위와 리소스 접근 권한을 역할 기반으로 제한하고, 위험 행위 시 인간 승인을 강제하는 보안 통제 체계
- **배경/필요성**: 에이전트가 이메일 발송·결제·DB 삭제 등 비가역적 도구를 직접 실행하게 되면서, 프롬프트 인젝션이나 환각에 의한 자산 훼손 리스크가 부상함. 최소 권한 원칙(PoLP) 적용과 HITL 방어선이 실무 도입의 전제 조건임
- **비유**: 신입 사원에게 전체 서버 root 권한 대신 읽기 전용 계정만 부여하는 것과 동일한 원리

| 출제 의도 | 반드시 짚을 핵심 | 감점 회피 포인트 |
|:---|:---|:---|
| AI 보안 거버넌스 설계 | PoLP → Sanitizing → HITL → Audit의 4단계 방어 계층 | 기존 IT 보안(방화벽)과 에이전트 보안(행위 통제)의 차이를 명확히 구분 |
| 프롬프트 인젝션 대응 | 직접/간접 인젝션 공격 벡터와 방어 아키텍처 | 감사 로그(→021 참조)와의 연계: 권한 통제 실패 시 사후 추적 메커니즘 포함 |

> 요약: 에이전트 도구 실행 권한을 RBAC·Sandbox·HITL·Audit 4계층으로 통제하여 비가역적 사고를 원천 차단하는 보안 프레임워크

## Ⅱ. 구성요소
```text
+------------------------------------------------------+
|          Agent Authorization Architecture            |
|  +-----------+                                       |
|  | Request   | -- 에이전트의 도구 호출 요청              |
|  +-----+-----+                                       |
|        |                                             |
|        v                                             |
|  +-----+------------+                                |
|  | 1. RBAC Layer     | -- 역할별 허용 도구 목록 검증     |
|  | (PoLP 적용)        |    Agent A: Read-only          |
|  +-----+-------------+    Agent B: Read/Write         |
|        |                                             |
|        v                                             |
|  +-----+-------------+                               |
|  | 2. Sanitizer      | -- 파라미터 악성코드 검사         |
|  | (입력 검증)         |    DROP TABLE, rm -rf 차단     |
|  +-----+-------------+                               |
|        |                                             |
|        v                                             |
|  +-----+-------------+                               |
|  | 3. HITL Gate      | -- 비가역적 행위 시 인간 승인     |
|  | (승인 대기)         |    requires_approval=True     |
|  +-----+-------------+                               |
|        |                                             |
|        v                                             |
|  +-----+-------------+                               |
|  | 4. Sandbox        | -- 격리 환경에서 실행            |
|  | (Docker 컨테이너)   |    네트워크 차단, TTL 5분       |
|  +-----+-------------+                               |
|        |                                             |
|        v                                             |
|  +-----+-------------+                               |
|  | Audit Log         | -- 실행 이력 불변 기록           |
|  +-------------------+                               |
+------------------------------------------------------+
```

| 구성요소 | 설명 | 비유 |
|:---|:---|:---|
| RBAC Layer | 에이전트 역할별 허용 도구 목록을 정의하고, 미허가 도구 호출을 사전 차단 | 출입증 — 층별 접근 권한이 다름 |
| Sanitizer | 도구 호출 파라미터에서 SQL Injection·시스템 명령어 등 악성 패턴을 정규식·보안 필터로 검출 | 공항 보안 검색대 |
| HITL Gate | 결제·삭제·이메일 발송 등 비가역적 도구에 requires_approval 태그를 부여하여 인간 승인 전까지 실행 보류 | 결재 라인 — 팀장 서명 필요 |
| Execution Sandbox | 코드 실행을 네트워크 격리된 일회용 컨테이너에서 수행하여 호스트 시스템 보호 | 방폭 실험실 — 사고가 나도 외부 무영향 |

> 요약: RBAC 사전 차단 + 파라미터 검증 + 인간 승인 + 격리 실행의 4중 방어 계층

## Ⅲ. 절차
```text
+------------------+     +------------------+     +------------------+     +------------------+
| 1. AuthZ Check   | --> | 2. Sanitize      | --> | 3. HITL Approval | --> | 4. Sandboxed     |
| (권한 검증)       |     | (파라미터 검사)   |     | (인간 승인)       |     |    Execution     |
+------------------+     +------------------+     +------------------+     +------------------+
```

1. **AuthZ Check(권한 검증)** — 에이전트 ID와 요청 도구를 RBAC 정책 테이블에 대조하여 허가/차단을 판정함
2. **Sanitize(파라미터 검사)** — 도구 호출 JSON 인자에 포함된 악성 패턴(DROP, DELETE, rm -rf 등)을 정규식·WAF로 탐지 및 차단함
3. **HITL Approval(인간 승인)** — 비가역적 도구(결제, 삭제) 호출 시 State를 동결(Sleep)하고 관리자에게 승인/거절 알림을 전송함
4. **Sandboxed Execution(격리 실행)** — 승인된 도구를 네트워크 격리 컨테이너 내에서 실행하고, TTL 초과 시 자동 폐기함

> 요약: 권한 대조 → 입력 검증 → 인간 승인 → 격리 실행의 순차 방어 절차

## Ⅳ. 문제점
- **데이터 무결성 훼손**: 삭제·결제는 HITL로 차단 가능하나, "고객명 철자를 미묘하게 변경"하는 소량 수정이 대량 반복되면 탐지 불가 — 비파괴적 변조에 대한 감시 로직 부재가 원인
- **HITL 병목**: 모든 위험 도구에 인간 승인을 요구하면 처리 속도가 급감하여 자동화 이점이 상쇄됨 — 위험도 분류 기준의 부재가 원인
- **간접 프롬프트 인젝션**: 에이전트가 읽는 외부 문서(PDF, 웹페이지)에 은닉된 악성 명령어를 RBAC만으로는 차단 불가 — 입력 소스 신뢰도 검증 미적용이 원인

> 요약: 비파괴적 변조, HITL 병목, 간접 인젝션이 권한 통제의 3대 난제

## Ⅴ. 개선방안
1. 단기: 비동기 이중화 버퍼 — 에이전트가 DB를 직접 변경하지 못하게 하고, Diff 테이블에 수정 제안서를 적재한 후 배치 검증 프로그램이 본 테이블에 반영
2. 중기: 위험도 티어링 — 도구별 Risk Score(Low/Medium/High)를 산정하여 Low는 자동 승인, Medium은 AI 가드레일 검증, High만 HITL 적용
3. 장기: Guardrail Agent — 전담 보안 AI가 0.01초 내에 요청의 악성 여부를 판별하여 인간 HITL을 대체하는 AI-to-AI 방어 체계 구축

- **간접 인젝션**: 외부 문서 내 은닉 명령 → 입력 소스별 신뢰도 태깅 + 비신뢰 소스의 도구 호출 권한 자동 박탈 (지표: 인젝션 성공률 < 0.1%)

> 요약: Diff 버퍼 → 위험도 티어링 → AI 가드레일로 무결성·속도·보안 동시 확보

## Ⅵ. 전망
- **향후 발전 방향**: MCP(Model Context Protocol) 서버가 도구별 권한 프록시 역할을 수행하여, 에이전트-도구 간 표준화된 인가 인터페이스로 발전할 전망
- **기술사적 판단**: 에이전트 권한 통제는 기존 IT 보안의 경계 방어(Perimeter)에서 행위 기반 통제(Behavioral Control)로의 패러다임 전환을 의미함. RBAC+HITL+Sandbox 3중 방어가 최소 기준임
- **기술사 제언**: 에이전트 도입 초기에는 모든 도구에 HITL을 적용하고, 운영 데이터 축적 후 점진적으로 위험도 티어링을 확대하는 점진적 자율성 확장(Gradual Autonomy) 전략을 권고함
