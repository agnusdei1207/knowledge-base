# 📖 【암기용】 개념 완전 이해

> 목적: 관측성을 처음 봐도 완벽히 이해하게 만든다. 시험 답안 양식이 아니라, 이해를 위한 친절한 설명이다.

## 한눈에
- **개요**: 시스템 내부에서 무슨 일이 벌어지고 있는지 외부 데이터(로그, 메트릭, 트레이스)를 통해 깊이 있게 이해할 수 있는 상태나 능력
- **왜 필요한가**: 예전에는 서버 1대를 모니터링하면 끝이었다. 하지만 수백 개의 컨테이너가 떴다 죽는 클라우드 환경에서는 "서버가 살아있나?"라는 질문보다 "사용자가 왜 느리다고 하지?"에 대한 답을 찾는 게 훨씬 어려워졌기 때문이다.
- **핵심 직관**: 단순히 '아픈지' 아는 것(모니터링)을 넘어, 어디가 왜 아픈지 '진단'할 수 있는 수준(관측성)을 갖추는 것이다.

## 깊이 이해
- **배경·문제의식**: 마이크로서비스(MSA)는 요청 하나가 여러 서비스를 거친다. 특정 구간에서 에러가 나거나 느려지면 어디가 원인인지 찾기 힘들다. 기존의 단순 모니터링(CPU 80% 등)만으로는 서비스 간의 복잡한 연관 관계를 설명할 수 없다.
- **작동 원리**: **3대 기둥(Three Pillars)**인 메트릭(숫자), 로그(텍스트), 분산 추적(흐름)을 결합한다. 메트릭으로 이상을 감지하고, 분산 추적으로 어느 서비스가 문제인지 특정하며, 로그로 구체적인 원인을 파악한다. 최근에는 eBPF 기술을 써서 소스 수정 없이 데이터를 수집하기도 한다.
- **비유**: 모니터링이 자동차 계기판(속도, 연료)이라면, 관측성은 블랙박스 영상과 차량 진단 컴퓨터(ECU 데이터)를 합친 것이다. 사고가 났을 때 계기판만 봐서는 원인을 모르지만, 블랙박스와 진단 데이터를 보면 정확한 사고 경위를 알 수 있는 것과 같다.
- **구체 예시**: OpenTelemetry 표준을 사용하여 수집된 데이터를 Prometheus(메트릭), Grafana(시각화), Jaeger(추적) 등에서 통합 분석하는 환경.
- **흔한 오해·주의점**: "모니터링이랑 똑같은 거 아냐?"라고 생각할 수 있지만, 모니터링은 '알고 있는 문제(Known-Unknowns)'를 감시하는 것이고, 관측성은 '예상치 못한 문제(Unknown-Unknowns)'를 탐탐하는 능력을 말한다.

## 연결 개념
- Three Pillars (Metrics, Logs, Traces) — 관측성의 기초 데이터
- OpenTelemetry (OTel) — 데이터 수집의 글로벌 표준 규격
- Distributed Tracing — 서비스 간 호출 경로 추적 기술
- SRE (Site Reliability Engineering) — 관측성을 활용해 시스템 신뢰도를 관리하는 철학

# 📝 【답안용】 시험 답안 템플릿

> 목적: 시험장에서 25분에 그대로 쓰는 답안 양식. 작성방식(추상표현 금지·수치·도식·문제유형 전환)을 엄격히 지킨다.
> 핵심: 모니터링과 관측성의 차이를 명확히 하고, 3대 기둥(Metrics, Logs, Traces)과 OpenTelemetry 중심의 기술 체계를 서술한다.

## 핵심 인사이트 (3줄 요약)

> 1. **본질**: 클라우드 네이티브 관측성은 분산 시스템의 외부 출력 데이터(Metrics, Logs, Traces)를 통해 내부 상태를 추론하고 미지의 문제(Unknown-Unknowns)를 디버깅하는 능력이다.
> 2. **가치**: 마이크로서비스(MSA)의 복잡한 상관관계를 가시화하여 MTTR(평균 복구 시간)을 단축하고 서비스 신뢰성(SLO)을 지표 기반으로 관리하게 해준다.
> 3. **판단 포인트**: 벤더 종속성을 탈피한 OpenTelemetry 표준 채택과 eBPF 기반의 무중단 수집 기술이 현대적 관측성의 핵심 트렌드이다.

## 출제 의도 및 답안 포인트

| 출제 의도 | 반드시 짚을 핵심 | 감점 회피 포인트 |
|:---|:---|:---|
| 모니터링과 관측성의 개념적 차이 확인 | 사후 분석(Debugging), 미지의 문제 탐색능력 | 단순히 "성능 측정"으로만 기술 |
| 관측성의 3대 핵심 요소 이해 확인 | 메트릭(Metrics), 로그(Logs), 트레이스(Traces) | 3요소 중 일부 누락 |
| 표준화 및 최신 수집 기술 인지 확인 | OpenTelemetry(OTel), eBPF, 분산 추적 | 특정 벤더(Datadog 등) 솔루션에만 국한된 설명 |

> 요약: 복잡한 분산 시스템의 가시성 확보를 위한 데이터 통합과 분석 역량을 중심으로 서술한다.

## Ⅰ. 개요 및 필요성

- 정의: 로그, 메트릭, 분산 추적 데이터를 통합하여 복잡한 분산 환경의 내부 상태를 깊이 있게 파악하고 문제를 진단할 수 있는 능력
- 배경: 마이크로서비스 확산으로 인해 요청 경로가 파편화되어 기존 서버 단위 모니터링으로는 병목 구간 및 장애 원인 파악 불가능
- 필요성: 시스템 가용성 유지, 성능 최적화, 비즈니스 영향도 분석을 위해 '살아있는가'를 넘어 '왜 그런가'에 대한 해답 제시 필요

## Ⅱ. 구조 및 구성요소

```text
       [ 관측성 (Observability) ]
             /        |        \
    +----------+ +----------+ +----------+
    | Metrics  | |   Logs   | |  Traces  | <--- 3 Pillars
    +----------+ +----------+ +----------+
         |            |            |
    [ OpenTelemetry Collector (Unified) ]
         |            |            |
    [ Prometheus ] [ Loki/ELK ] [ Jaeger ] <--- Backend Storage
```

| 구성요소 | 역할 | 특이사항 |
|:---|:---|:---|
| 메트릭 (Metrics) | 시계열 수치 데이터 (CPU, 에러율, TPS) | 이상 징후 감지 및 대시보드 |
| 로그 (Logs) | 특정 시점의 불연속적 텍스트 기록 | 상세 원인 분석 및 이벤트 기록 |
| 트레이스 (Traces) | 요청의 엔드투엔드 이동 경로 및 시간 | 분산 환경의 병목 구간 특정 |
| 콜렉터 (Collector) | 다양한 포맷의 데이터를 수집/처리/전달 | 벤더 독립적 데이터 파이프라인 |

> 요약: 3대 핵심 데이터(Pillars)를 통합 수집하여 상관관계(Correlation)를 분석하는 구조를 가진다.

---

## Ⅲ. 동작원리 및 흐름도

```text
[동작 흐름: 생성 -> 수집 -> 가공 -> 분석/시각화]
Application -> OTel SDK -> OTel Collector -> Backend (Storage) -> Grafana
      |           |              |               |                 |
(Context) -- (Export) ---- (Transform) ---- (Index/Query) ---- (Dashboard)
```

| 단계 | 처리 내용 | 검증 기준 |
|:---:|:---|:---|
| 1 | 컨텍스트 전파 | 요청 시 Trace ID를 생성하여 모든 서비스 호출에 포함 (Propagation) |
| 2 | 데이터 수출 | SDK나 Agent가 메트릭/로그/트레이스를 표준 규격으로 전송 |
| 3 | 데이터 가공 | 수집기에서 태그 추가, 샘플링, 불필요 데이터 필터링 수행 |
| 4 | 상관 분석 | Trace ID를 기반으로 로그와 메트릭을 연결하여 문제 시점의 전후 맥락 파악 |

> 요약: 고유 식별자(Trace ID)를 통해 서로 다른 유형의 데이터를 하나로 엮어 분석하는 것이 핵심이다.

## Ⅳ. 특징

| 구분 | 내용 | 판단 포인트 |
|:---|:---|:---|
| 탐험적 분석 | 정의되지 않은 문제의 원인을 사후에 찾아낼 수 있음 | Unknown-Unknowns 대응 |
| 상관관계 | 트레이스 ID를 매개로 로그와 메트릭을 연결 분석 | 데이터 간 사일로(Silo) 제거 |
| 표준화 | OpenTelemetry를 통한 데이터 형식 및 프로토콜 단일화 | 벤더 종속성(Lock-in) 해제 |
| 자동화 | eBPF 등을 활용하여 코드 수정 없는(Zero-code) 수집 가능 | 운영 부하 최소화 |

> 요약: 단순한 '지표 감시'가 아니라 데이터 간의 '연결'을 통해 시스템의 인과 관계를 밝히는 특징을 가진다.

## Ⅴ. 심화 비교 및 적용 판단

| 비교 축 | 모니터링 (Monitoring) | 관측성 (Observability) | 선택 기준 |
|:---|:---|:---|:---|
| 주요 질문 | 시스템이 정상인가? (Is it up?) | 왜 문제가 발생했는가? (Why?) | 분석의 깊이 |
| 대응 대상 | 알고 있는 문제 (Known-Unknowns) | 예기치 못한 문제 (Unknown-Unknowns) | 장애 예측 가능성 |
| 핵심 도구 | 대시보드, 알람 | 분산 추적, 상관 분석, 프로파일링 | 시스템 복잡도 |

> 요약: 단일 서버나 단순 구조는 모니터링으로 충분하나, 복잡한 MSA 환경은 관측성 체계가 필수적이다.

| 리스크 | 원인 | 대응 방안 | 확인 지표 |
|:---|:---|:---|:---|
| 데이터 폭증 | 모든 호출을 수집할 경우 비용/성능 오버헤드 | 헤드/테일 샘플링(Sampling) 적용 | 데이터 전송량 및 저장 비용 |
| 성능 저하 | 수집 라이브러리의 CPU/메모리 추가 점유 | eBPF 기반 에이전트리스 수집 검토 | 수집 전후 애플리케이션 Latency |
| 데이터 분절 | 서로 다른 도구 사용으로 인한 연결성 부족 | OpenTelemetry 표준으로 통합 | Trace-to-Log 연결 성공률 |

> 요약: 과도한 수집 비용을 통제하기 위한 샘플링 전략과 성능 오버헤드 관리가 실무의 관건이다.

| 점검 항목 | 목표 기준 | 측정 방법 |
|:---|:---|:---|
| MTTR 개선율 | 도입 전 대비 장애 복구 시간 30% 이상 단축 | 장애 관리 대장 분석 |
| 추적 성공률 | 전체 요청 중 Trace ID가 완결된 비율 95% 이상 | 추적 시스템 통계 |
| 성능 오버헤드 | 관측성 수집으로 인한 지연 증가 5ms 이하 | 벤치마크 테스트 |

> 요약: 복구 시간 단축이라는 실질적 가치와 수집 효율성을 동시에 측정해야 한다.

## Ⅵ. 실무 적용 및 결론

**적용 방안 3개:**
1. OpenTelemetry 표준 도입: 모든 서비스에 OTel SDK를 적용하여 벤더에 무관한 통합 데이터 수집 파이프라인 구축
2. 분산 추적 강화: 서비스 간 지연 시간(Latency)이 높은 구간을 Jaeger를 통해 시각화하고 병목 DB 쿼리나 API 호출 특정
3. 비즈니스 관측성 연계: 기술 지표와 함께 주문량, 매출 등 비즈니스 지표를 결합하여 시스템 장애의 실질적 영향도 분석

**결론 (2줄):**
- 기술사 판단: 클라우드 네이티브 환경에서 관측성은 단순한 운영 도구가 아니라 시스템의 신뢰성을 보장하는 핵심 아키텍처 요소이다.
- 향후 방향: AI를 결합한 AIOps와 결합하여, 방대한 데이터 속에서 자동으로 이상 징후를 찾고 원인을 제시하는 지능형 관측성으로 발전할 것이다.
