# 📖 【암기용】 개념 완전 이해

> 목적: 모놀리식 시절의 단순한 '모니터링(Monitoring)'을 넘어, 수백 개로 쪼개진 MSA 환경에서 "도대체 어디서 왜 터졌는지"를 파악하기 위한 3대 기둥(Metrics, Logs, Traces)과 관측성 사상을 이해한다.

## 한눈에
- **정의**: 시스템의 외부로 출력되는 데이터(Logs, Metrics, Traces)를 바탕으로, **시스템 내부 상태와 장애의 근본 원인(Root Cause)을 정확히 추론하고 이해할 수 있는 능력**
- **필요성**: MSA로 넘어가면서 "사용자 결제 실패!"라는 에러가 발생했을 때, 이것이 앞단 API 게이트웨이 때문인지, 중간의 인증 서버 때문인지, 끝단의 DB 타임아웃 때문인지 기존의 단순한 CPU 모니터링으로는 도저히 찾을 수 없게 되었기 때문
- **핵심 직관**: "모니터링이 '환자의 체온이 39도라는 걸 알려주는 온도계'라면, 관측성은 '혈액검사, X-ray, MRI 데이터를 다 모아서 환자가 왜 열이 나는지 정확히 진단해 내는 종합 병원 시스템'이다."

## 깊이 이해
- **배경(왜 등장했나?)**: 옛날에는 서버가 1대여서 죽으면 그냥 그 서버 로그만 까보면 됐다(모니터링). 근데 클라우드 네이티브 환경에서는 사용자 요청 1개가 20개의 컨테이너를 거쳐 간다. 컨테이너는 떴다가 금방 죽어버리고 IP도 계속 바뀐다. 장애가 났을 때 "이게 도대체 어느 컨테이너의 무슨 코드에서 터진 거야?"라는 아비규환이 벌어졌고, 이를 해결하기 위해 Observability(관측성)라는 개념이 급부상했다.
- **작동 원리(어떻게 달성했나?) - 3대 기둥(Three Pillars)**:
  1. **Metrics (메트릭)**: '무엇(What)이 문제인가?' (예: 결제 서버 CPU가 99%다, HTTP 500 에러가 1초에 100개 발생한다.) → 주로 Prometheus가 수집.
  2. **Traces (분산 추적)**: '어디(Where)가 문제인가?' (예: 사용자의 요청이 A ➔ B ➔ C 서버로 갔는데, C 서버에서 10초나 걸렸네?) → 서로 다른 서버 간의 호출 흐름을 연결(Trace ID)해서 보여줌. (Jaeger, Zipkin)
  3. **Logs (로그)**: '왜(Why) 문제인가?' (예: C 서버 로그를 까보니 "NullPointerException"이 발생했네.) → Fluentd, ElasticSearch 등이 수집.
- **일상 비유**: 범죄(장애) 수사와 같다. 메트릭은 "어제 강남역에 강도 사건 3건 발생(통계)"이라는 경찰청 보고서다. 트레이스는 "범인이 강남역에서 택시를 타고 이태원으로 도망갔다(동선 추적)"는 CCTV 기록이다. 로그는 "범인이 도망가다 흘린 지갑 속 신분증(구체적 증거)"이다. 이 3가지가 다 있어야 범인을 잡는다.
- **구체 예시**: 개발자가 OpenTelemetry 표준 라이브러리를 앱에 추가하면, 코드가 실행될 때마다 메트릭/로그/트레이스 데이터가 자동으로 뿜어져 나와 중앙의 Datadog이나 Grafana 같은 대시보드에 예쁘게(상관관계가 묶여서) 그려진다.
- **흔한 오해/주의점**: "관측성 도구(Datadog 등)만 비싼 돈 주고 사면 관측성이 생기나?" → 절대 아니다! 개발자가 애초에 에러 로그를 제대로 남기지 않고, 서비스 간에 Trace ID를 넘겨주도록 코딩하지 않으면 비싼 툴을 사도 아무것도 볼 수 없다.

## 연결 개념
- **Monitoring (모니터링)**: 시스템이 멈췄는지 안 멈췄는지 대시보드로 보는 행위. 관측성의 부분집합이다.
- **OpenTelemetry (OTel)**: 관측성 데이터(메트릭, 로그, 트레이스)를 수집하는 방식을 하나로 통일한 CNCF의 거대한 오픈소스 표준 (De-facto).
- **Service Mesh (Istio)**: 개발자가 코드에 추적 로직을 심지 않아도, 인프라 단에서 강제로 관측성 데이터를 뽑아내주는(Zero-instrumentation) 고마운 기술.

# 📝 【답안용】 시험 답안 템플릿

## 핵심 인사이트 (3줄 요약)
> 1. **본질**: 클라우드 네이티브 관측성(Observability)은 분산 시스템이 뿜어내는 원격 측정 데이터(Telemetry)를 수집 및 연관 분석하여, 사전에 예측하지 못한 장애의 근본 원인(Root Cause)을 동적으로 파악하는 시스템의 속성이자 역량이다.
> 2. **가치**: 마이크로서비스(MSA), 서버리스, 컨테이너 등 추상화되고 동적인 인프라 환경에서 블랙박스화된 시스템의 가시성을 확보하고, MTTR(평균 복구 시간)을 획기적으로 단축한다.
> 3. **판단 포인트**: 모니터링(단순 상태 감시)과의 차별성을 강조하고, 관측성의 3대 기둥(Metrics, Traces, Logs)과 이를 통합 수집하는 OpenTelemetry 생태계 표준을 반드시 제시해야 한다.

## Ⅰ. 개요 및 필요성
- **정의**: 제어 이론(Control Theory)에서 유래된 용어로, 시스템의 외부 출력 데이터를 통해 내부 상태를 얼마나 잘 추론할 수 있는지를 나타내는 척도
- **배경**: 모놀리식 아키텍처와 달리 MSA 환경에서는 1개의 사용자 요청이 수십 개의 서비스를 횡단함. 예측 가능한 대시보드 기반의 '모니터링(Monitoring)'만으로는 "Unknown-Unknowns(알려지지 않은 알 수 없는 오류)"에 대응 불가
- **필요성**: 분산 환경에서의 장애 지점 파악(Isolating), 성능 병목(Bottleneck) 구간 추적, 데이터 기반의 시스템 용량 산정 및 SRE(Site Reliability Engineering) 프랙티스 실현

## Ⅱ. Monitoring vs Observability 비교
| 구분 | Monitoring (모니터링) | Observability (관측성) |
|:---|:---|:---|
| **목적** | 시스템이 잘 동작하고 있는가? (상태 확인) | **시스템이 왜 동작하지 않는가? (원인 분석)** |
| **대응 영역** | **Known-Unknowns** (예상 가능한 에러 모니터링) | **Unknown-Unknowns** (예측 불가능한 장애 원인 탐색) |
| **방향성** | 수동적 반응 (알람 발생 시 확인) | **능동적 탐색 (디버깅 및 쿼링을 통한 추론)** |
| **데이터 결합** | CPU, Memory 등 개별 지표 중심 | **Metrics, Traces, Logs의 상관관계(Correlation) 결합** |

## Ⅲ. 관측성의 3대 기둥 (The Three Pillars)
관측성은 다음 세 가지 데이터를 상호 연관 지어(Contextualized) 분석할 때 완성된다.

1. **Metrics (메트릭)**
   - **정의**: 시간에 따른 시스템의 수치화된 측정값 (예: CPU 사용률, HTTP 500 에러율, QPS).
   - **역할**: "어디에 문제가 발생했는가?"를 가장 먼저 알려주는 알람(Alerting)의 기준 데이터. (대표 도구: **Prometheus**)
2. **Traces (분산 추적)**
   - **정의**: 단일 사용자 요청이 여러 마이크로서비스를 거쳐 가는 전체 생명주기와 호출 경로.
   - **역할**: "어느 구간(Service Hop)에서 지연(Latency)되거나 끊겼는가?"를 파악. Trace ID와 Span ID를 통해 흐름을 이어줌. (대표 도구: **Jaeger, Zipkin**)
3. **Logs (로그)**
   - **정의**: 특정 시간(Timestamp)에 발생한 이벤트를 기록한 불변의 텍스트 레코드.
   - **역할**: "정확히 코드의 어느 줄에서 무슨 에러(예: NullPointer)가 발생했는가?" 즉, 최종 근본 원인(Root Cause) 제공. (대표 도구: **ELK Stack / Fluentd**)

## Ⅳ. OpenTelemetry (OTel): 관측성의 사실상 표준
과거에는 Datadog, New Relic 등 각 벤더별로 데이터를 수집하는 방식(Agent)이 달라 종속성(Lock-in) 문제가 심각했다. 이를 해결하기 위해 CNCF가 만든 글로벌 표준이 OpenTelemetry다.

- **단일 파이프라인**: 벤더 중립적인 단일 API, SDK, Collector를 제공하여 메트릭, 로그, 트레이스를 통일된 포맷으로 한 번에 수집.
- **효과**: 개발자는 OTel 표준 코드로만 관측성을 계측(Instrumentation)하고, 나중에 데이터를 보낼 백엔드(Datadog, Grafana 등)는 언제든 설정 파일 하나로 쉽게 바꿀 수 있음.

## Ⅴ. 기술적 한계(리스크) 및 해결 방안
| 리스크 요인 | 현상 및 문제점 | 대응 방안 (엔지니어링 가이드) |
|:---|:---|:---|
| **데이터 폭증 (Cost Overrun)** | 수십 개의 서비스가 뿜어내는 로그와 트레이스 데이터 보관 비용이 실제 서비스 인프라 비용을 역전하는 현상 발생 | **샘플링(Sampling) 기법** 적용 (예: 정상 트래픽은 1%만 트레이스 수집, 에러 발생 시에만 100% 수집하는 Tail-based Sampling) |
| **개발자 계측(Instrumentation) 부담** | 추적을 위해 비즈니스 로직마다 Trace ID를 파싱하고 전달하는 코드를 강제로 넣어야 함 | **Service Mesh (Istio)**나 **eBPF (Cilium)** 등 인프라 레이어에서 앱 코드 수정 없이 자동으로 수집(Zero-instrumentation)하는 기술 도입 |

## Ⅵ. 실무 적용 및 결론
**적용 방안 및 실무 가이드:**
1. **Correlation(상관관계) ID 표준화**: 3대 기둥을 따로 보면 의미가 없다. 사용자 요청이 들어올 때 API Gateway에서 고유한 `TraceID`를 발급하여, 이후 발생되는 모든 로그와 메트릭에 이 ID를 태깅하도록 사내 로깅 표준 프레임워크를 강제해야 한다.
2. **RED 메트릭 대시보드 구축**: 마이크로서비스 모니터링의 기본인 RED(Rate-요청량, Errors-에러율, Duration-응답속도) 대시보드를 Grafana로 구성하여 관측성의 엔트리 포인트(진입점)로 삼는다.

**결론:**
- 클라우드 네이티브 환경에서 관측성(Observability)은 단순한 운영 도구가 아니라, 복잡한 분산 시스템을 지속 가능하게 유지보수하기 위한 **소프트웨어 아키텍처의 필수 요구사항(NFR)**이다.
- OpenTelemetry라는 통일된 생태계를 바탕으로, AI/ML을 접목하여 장애를 예측하고 자동 복구하는 AIOps로 대전환하는 것이 현재 관측성 시장의 최종 목적지이다.
