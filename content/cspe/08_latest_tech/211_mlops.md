# 📖 【암기용】 개념 완전 이해

## 한눈에
- **정의**: 머신러닝(ML) 모델의 **데이터 수집 $\rightarrow$ 모델 학습 $\rightarrow$ 배포 $\rightarrow$ 모니터링 $\rightarrow$ 재학습**에 이르는 전체 생애주기(Lifecycle)를 끊김 없이 자동화하고, 소프트웨어 공학의 'DevOps' 철학을 ML 영역에 이식한 통합 운영 체계.
- **필요성**: 데이터 사이언티스트가 본인 노트북(주피터)에서 기가 막힌 모델을 만들어도, 이걸 실제 서비스 서버에 올리고 1년 내내 장애 없이 돌리는 건 전혀 다른 차원의 문제임. 과거엔 "모델 만들었으니 개발팀이 알아서 서비스해 줘"라고 던졌다가 잦은 장애와 성능 저하(Drift)가 터짐. 이 간극을 메우는 자동화 컨베이어 벨트가 필요함.
- **핵심 직관**: 자동차 공장 시스템. 천재 엔지니어가 수제작으로 람보르기니 1대를 만들 수는 있음(주피터 노트북). 하지만 이걸 하루 1,000대씩 불량 없이 똑같이 찍어내고(재현성), 고장 나면 바로 AS를 하며(모니터링), 새 부품이 나오면 즉시 생산 라인을 업그레이드(지속적 학습, CT)하는 '공장 운영 자동화 시스템'이 바로 MLOps임.

## 깊이 이해
- **배경**: 전통적인 소프트웨어는 '코드(Code)'만 배포하면 끝이었음. 하지만 ML 시스템은 **'코드 + 데이터 + 모델'**이라는 3차원 방정식임. 데이터가 매일 변하므로 모델도 매일 썩어감(Model Decay). 이를 해결하기 위해 DevOps의 CI/CD에 '지속적 학습(Continuous Training, CT)' 개념을 추가함.
- **작동 원리 (파이프라인 아키텍처)**:
  1. **Feature Store (데이터/특성 저장소)**: 데이터 엔지니어가 정제한 데이터를 저장해두고 재사용.
  2. **CI (Continuous Integration)**: 모델 학습 코드나 하이퍼파라미터가 깃허브에 올라오면, 자동으로 빌드 및 테스트(유닛/통합) 수행.
  3. **CT (Continuous Training)**: CI 통과 시, 최신 데이터를 가져와 자동으로 모델을 재학습(Retraining)시킴.
  4. **Model Registry (모델 저장소)**: 학습을 마친 모델 버전들(v1.0, v1.1) 중 테스트셋 정확도를 넘긴 승인된 놈만 보관하는 창고.
  5. **CD (Continuous Deployment)**: 창고에 있는 모델을 API 컨테이너(Docker)로 말아서 쿠버네티스(K8s) 등 상용 서버에 무중단 배포(섀도우/카나리 배포).
  6. **Monitoring (관측)**: 배포된 모델이 실시간으로 뱉는 결과를 감시. 정답률이 떨어지거나(Concept Drift), 입력 데이터 분포가 확 바뀌면(Data Drift) 알람을 울려 다시 CT(재학습) 단계로 돌려보냄(피드백 루프).
- **구체 예시**: 넷플릭스 추천 시스템. 사용자의 어제 시청 기록(새 데이터)이 쌓이면, 밤사이 MLOps 파이프라인이 자동으로 최신 추천 모델을 재학습(CT)하고, 아침에 수백 대의 서버에 무중단으로 새 모델을 배포(CD)함. 사람(엔지니어)의 개입은 0임.
- **흔한 오해/주의점**: "MLOps는 KubeFlow나 MLflow 같은 툴을 까는 건가요?" $\rightarrow$ 아님. 도구는 수단일 뿐, 본질은 팀(Data, Dev, Ops) 간의 사일로(장벽)를 허물고 '재현성(Reproducibility)'과 '추적성(Lineage)'을 보장하는 조직적 문화이자 프로세스임.

## 연결 개념
- **DevOps**: MLOps의 아버지. 개발(Dev)과 운영(Ops)을 통합해 코드 배포를 자동화하는 철학.
- **Data Drift (데이터 표류)**: MLOps 모니터링의 가장 핵심 타겟. 코로나19가 터지자 과거 데이터로 학습한 마스크 수요 예측 모델이 바보가 된 현상이 바로 드리프트임. 이를 감지하면 즉시 재학습(CT)을 돌려야 함.
- **LLMOps**: MLOps의 자식. 거대 언어 모델(LLM)에 맞게 프롬프트 엔지니어링과 RAG 파이프라인 관리를 추가한 최신 운영 체계.

# 📝 【답안용】 시험 답안 템플릿
## 핵심 인사이트 (3줄 요약)
- **본질**: 머신러닝 시스템의 개발(Dev)과 운영(Ops) 프로세스를 결합하여, **코드(Code), 데이터(Data), 모델(Model)**의 버전 관리를 통합하고 모델의 지속적 통합/배포/학습(CI/CD/CT)을 자동화하는 엔지니어링 문화 및 실천 방법론.
- **가치**: 데이터 사이언티스트의 실험 환경(Research)과 IT 엔지니어의 상용 환경(Production) 간의 간극을 해소하여 타임투마켓(Time-to-Market)을 단축하고, 모델 성능 저하(Drift) 리스크를 실시간 피드백 루프로 통제함.
- **판단 포인트**: 기존 DevOps 프랙티스에 머물지 않고, ML 파이프라인의 핵심인 Feature Store 구축, Model Registry(모델 버저닝 및 승인 게이트) 도입, 그리고 데이터/컨셉 드리프트를 탐지하여 자동 재학습(CT)을 격발시키는 폐루프(Closed-loop) 모니터링 설계가 필수적임.

## Ⅰ. 개요 및 필요성
- **정의**: 기계학습 모델의 설계, 학습, 검증, 배포, 모니터링에 이르는 전 생애주기(End-to-End Lifecycle)를 대규모 시스템에서 안정적이고 재현 가능하게(Reproducible) 관리하는 운영 체계.
- **배경**: ML 모델은 정적인 소스코드와 달리 입력 데이터의 확률적 분포 변화에 따라 시간이 지날수록 성능이 퇴화(Model Decay)하는 특성이 있어, 1회성 배포가 아닌 '지속적 진화'의 메커니즘이 요구됨.
- **필요성**: 모델 서빙 인프라의 장애 대응(Resilience), AI 규제 감사(Audit)를 위한 데이터-모델 간 계보(Lineage) 추적, 그리고 데이터 과학자(탐색)와 엔지니어(운영) 간의 R&R 충돌 해결.

## Ⅱ. MLOps 아키텍처 및 구성요소
모델을 찍어내고 관리하는 공장 라인.
| 주요 컴포넌트 | 역할 및 메커니즘 (Mechanism) | 대표 오픈소스/솔루션 |
|:---:|:---|:---|
| **Feature Store** | 모델 학습 및 추론에 사용되는 정제된 특징(Feature) 변수들을 일관되게 제공하여 학습-서빙 간 불일치(Skew) 방지. | Feast, Hopsworks |
| **Exp. Tracking**<br>(실험 추적) | 데이터 사이언티스트가 변경하는 하이퍼파라미터, 학습 데이터 해시, 평가 지표(Accuracy 등)를 기록. | MLflow, W&B |
| **Model Registry**<br>(모델 저장소) | 검증을 통과한 모델 아티팩트(Artifact)를 버전별로 저장하고 배포 상태(Staging/Prod)와 롤백을 관리. | MLflow Model Registry |
| **CI / CD / CT** | 코드 푸시 $\rightarrow$ 파이프라인 단위 테스트(CI) $\rightarrow$ 자동 재학습(CT) $\rightarrow$ 컨테이너 기반 API 서빙 배포(CD). | Kubeflow, ArgoCD |
| **Monitoring** | 배포된 모델의 지연 시간(Latency) 및 Drift(데이터 분포 변화)를 실시간 관측하여 CT 트리거. | Prometheus, Grafana |

## Ⅲ. 기존 DevOps vs MLOps 패러다임 비교
| 구분 | DevOps | MLOps |
|:---:|:---|:---|
| **관리의 주체** | 소스 코드 (Source Code) | **코드(Code) + 데이터(Data) + 모델(Model)** |
| **자동화 파이프라인**| CI (통합) / CD (배포) | **CI / CD + CT (지속적 학습, Continuous Training)** |
| **성능 저하 원인** | 소프트웨어 버그, 하드웨어 장애 | **Data Drift, Concept Drift (환경 변화에 따른 퇴화)** |
| **모니터링 지표** | CPU/RAM 사용량, 에러 율(5xx) | **모델 정확도 하락, 예측값의 통계적 분포 변화(PSI)** |

## Ⅳ. 모델 성능 하락(Drift) 메커니즘 및 방어 아키텍처
MLOps가 막아야 하는 가장 큰 적.
1. **성능 하락의 원인 (Drift 유형)**:
   - **Data Drift (데이터 표류)**: 입력 데이터의 통계적 분포가 바뀜 (예: 20대만 오던 쇼핑몰에 갑자기 60대가 유입됨. $P(X)$의 변화).
   - **Concept Drift (컨셉 표류)**: 정답(Label)의 기준 자체가 바뀜 (예: 인플레이션으로 1만 원의 가치가 하락해 고객 구매 패턴 공식이 깨짐. $P(Y|X)$의 변화).
2. **방어 아키텍처 (Continuous Training Loop)**:
   - **탐지 (Detection)**: 배포 모델의 예측값(Output)과 실시간 입력값(Input)의 분포를 기준선(Baseline)과 비교(예: PSI 지표 활용). 오차 임계치 초과 시 알람(Alert).
   - **재학습 격발 (Trigger)**: 알람이 울리면, 최신 1개월 치 데이터를 Feature Store에서 끌어와 자동 재학습(CT) 파이프라인을 실행.
   - **챔피언-챌린저 (A/B Test)**: 새로 학습된 챌린저 모델을 기존 챔피언 모델과 섀도우 모드(Shadow Mode)로 동시 실행하여 성능 우위 입증 시 자동 스위칭(CD).

## Ⅴ. 실무 적용 및 결론
- **판단 지표**: 모델 배포 리드타임(수개월 $\rightarrow$ 수 시간), 재현 성공률(Reproducibility Rate 100%), 모델 성능 저하 발생 후 자동 복구(재학습 배포)까지 걸리는 시간(MTTR).
- **실무 설계**: 금융권 S은행의 '대출 심사 이탈 예측 모델' 운영 환경. 초기엔 분석가가 로컬에서 모델을 픽클(Pickle) 파일로 구워 운영팀에 USB로 전달함(재현 불가, 장애 빈발). 조치 방안: Level 2 수준의 MLOps 도입. 1) 소스코드 Git 푸시 시, Jenkins가 Kubeflow 파이프라인을 자동 컴파일(CI). 2) Kubeflow 파이프라인이 Airflow 스케줄링에 의해 매주 1회 최신 DB 데이터로 모델을 재학습(CT). 3) 평가 검증기(Evaluator)가 모델 정확도(AUC) 80% 이상일 때만 MLflow Registry에 '운영(Prod)' 태그를 부여. 4) ArgoCD가 해당 태그를 감지해 K8s 클러스터에 무중단 롤링 배포(CD). 배포 주기 단축 및 운영 안정성 확보.
- **결론**: MLOps는 AI를 '연구소의 실험'에서 '비즈니스의 심장'으로 이식하는 인프라 수술이다. 단기적인 모델 정확도(Accuracy)에만 집착하던 과거를 버리고, 수천 번의 재학습과 배포를 견뎌내는 '파이프라인의 견고함'에 투자할 때 비로소 진정한 AI 트랜스포메이션(AX)이 완성된다.

### 🔀 문제 유형별 목차 전환
- **Ⅱ·Ⅲ 강조 (개념/원리형)**: MLOps 성숙도 모델(Maturity Model). 구글(Google)이 정의한 Level 0 (수동 스크립트) $\rightarrow$ Level 1 (ML 파이프라인 자동화/CT) $\rightarrow$ Level 2 (CI/CD 파이프라인 자동화)의 단계별 진화 과정 및 구조적 차이점.
- **Ⅴ·Ⅵ 강조 (실무/설계형)**: 운영 중인 상용 서버에 리스크 없이 새 모델을 배포하기 위한 카나리 배포(Canary), 블루-그린(Blue-Green), 섀도우 배포(Shadow Deployment)의 트래픽 라우팅 아키텍처 및 롤백(Rollback) 전략 설계.
