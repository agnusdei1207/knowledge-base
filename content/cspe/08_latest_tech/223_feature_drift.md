# 📖 【암기용】 개념 완전 이해

## 한눈에
- **정의**: 머신러닝 모델의 입력 데이터 전체가 아니라, **특정 '개별 특징(변수, Feature)' 1개의 통계적 분포 값이나 의미가 학습 시점과 확연히 다르게 오염되거나 변하는 현상**.
- **필요성**: 모델 성능이 떨어졌을 때(Model Drift), 수백 개의 변수 뭉텅이(Data Drift)를 그냥 쳐다본다고 원인이 나오지 않음. "도대체 어떤 변수가 미쳐 날뛰어서 모델이 망가졌는가?" 범인을 정확히 색출해 내야(RCA) 데이터 파이프라인 버그를 고치거나 모델을 치료할 수 있음.
- **핵심 직관**: 건강검진 피검사. "이 사람 몸 상태(Data)가 전반적으로 안 좋다"가 아니라, 백혈구 수치(피처 A), 간수치(피처 B) 등 수십 개의 개별 항목을 검사해서 "간수치(Feature Drift)가 비정상적으로 높다!"라고 정확한 병의 원인을 콕 집어내는 과정.

## 깊이 이해
- **배경**: 현업의 ML 모델은 수십~수백 개의 피처(나이, 구매액, 클릭 수, 위도 등)를 사용함. 데이터 파이프라인(ETL) 어딘가에서 버그가 나면 '나이' 컬럼에 갑자기 '999'라는 결측치 대체값이 쏟아지거나 단위가 바뀌어버림. 이 '하나의 고장 난 피처'가 모델 전체의 예측값을 쓰레기로 만듦.
- **작동 원리 (변수 단위 쪼개기 감시)**:
  1. **개별 피처 감시**: 100개의 피처 각각에 대해 히스토그램을 그리고 학습 때와 똑같은지 감시함 (PSI, 평균, 분산 관측).
  2. **우선순위(Feature Importance)**: 100개 다 변했다고 알람을 울리면 피곤함(Alert Fatigue). 모델 성능에 제일 영향을 많이 주는 핵심 피처(Top 10)가 변했을 때만 강력한 알람을 띄움.
  3. **격리 조치**: 문제가 된 피처를 발견하면, 재학습 전까지 해당 피처의 가중치를 죽이거나 이전 평균값으로 강제 보정해 줌.
- **구체 예시**: 집값 예측 모델. 학습할 땐 집 크기(Feature) 단위가 '평(Pyung)'이었는데, 운영 파이프라인 담당자가 바뀌면서 단위가 몰래 '제곱미터(m²)'로 수집되기 시작함. 숫자 스케일이 3.3배 커져버림(Feature Drift). 모델은 모든 집이 엄청나게 큰 대저택이라고 착각해 집값을 수백억으로 예측하는 참사 발생.
- **흔한 오해/주의점**: "Data Drift = Feature Drift 똑같은 말 아님?" $\rightarrow$ 헷갈리기 쉬움. Data Drift는 숲(전체 데이터)이 변하는 뭉뚱그린 현상이고, Feature Drift는 그 숲 안의 '소나무(특정 피처)'가 썩고 있다는 매우 구체적인 핀셋 진단명임.

## 연결 개념
- **Data Drift**: 전체 데이터 세트의 분포 변화. Feature Drift 여러 개가 모이면 Data Drift가 됨.
- **Feature Importance (피처 중요도)**: 의사결정 트리나 SHAP 값에서 뽑아내는 '어떤 변수가 제일 일 잘하나'의 척도. 알람의 우선순위를 정하는 핵심 도구.
- **Data Quality Monitoring (데이터 품질 감시)**: Null 값, 단위 오류 등 Feature Drift를 유발하는 가장 1차원적인 원인을 막는 앞단의 방어벽.

# 📝 【답안용】 시험 답안 템플릿
## 핵심 인사이트 (3줄 요약)
- **본질**: Data Drift의 미시적(Micro) 관점으로, 모델을 구성하는 독립 변수 집합($X$) 중 특정 개별 특징 변수($x_i$)의 통계적 분포, 스케일, 또는 범주형 비율이 학습 시점(Baseline)과 확연히 이탈하는 현상.
- **가치**: 전체 데이터 세트 수준의 모호한 이상 탐지를 넘어, 모델 성능 퇴화의 직접적인 근본 원인(RCA, Root Cause Analysis)을 변수 단위로 핀셋 식별하여 파이프라인 버그 패치 및 변수 제거의 근거를 제공함.
- **판단 포인트**: 현업의 모델은 수천 개의 피처를 사용하므로 모든 피처의 변화에 알람을 울리면 알람 피로(Alert Fatigue)가 발생함. 반드시 모델 내 **피처 중요도(Feature Importance)** 및 **SHAP 가중치**와 결합하여 핵심 기여 변수 위주로 임계치(Threshold)를 차등 설정하는 지능형 모니터링이 필수적임.

## Ⅰ. 개요 및 필요성
- **정의**: 운영 환경의 머신러닝 파이프라인에서 추출되는 개별 피처(Feature) 데이터가, 외부 트렌드 변화나 내부 시스템 오류로 인해 기준점(학습 데이터)의 통계적 특성(Mean, Variance, Skewness)에서 벗어나는 현상.
- **배경**: 복잡한 MSA 아키텍처 환경에서 상위 소스 데이터베이스의 스키마 변경, 단위 환산(Unit) 오류, 센서 교체 등의 이슈가 조용히 하위 ML 피처 스토어로 전파(Cascade)되는 사고의 빈발.
- **필요성**: 모델 전체 재학습(Retraining) 결정 전 데이터 파이프라인(ETL) 자체의 오류 가능성 우선 배제, 치명적 버그 데이터 유입의 런타임 차단, 디버깅 공수(MTTR)의 획기적 단축.

## Ⅱ. Feature Drift의 발생 유형 및 메커니즘
무엇이 피처를 오염시키는가.
| 발생 유형 (Type) | 상세 메커니즘 및 증상 | 실무 예시 |
|:---:|:---|:---|
| **통계적 분포 이동**<br>(Distribution Shift) | 값의 범위는 정상이나 통계적 쏠림 발생 (평균 이동, 분산 팽창). | 특정 시간대(심야) 결제 비율이 평소 10% $\rightarrow$ 60%로 급증 (사용자 패턴 변화). |
| **스케일 및 단위 파괴**<br>(Scale/Unit Error) | 피처의 스케일 자릿수 자체가 변경됨. (가장 흔한 인프라 오류). | API 변경으로 온도 피처가 섭씨(C) $\rightarrow$ 화씨(F)로 수집됨. |
| **범주형 신규 값 출현**<br>(New Categories) | 학습 당시에 존재하지 않던 전혀 새로운 카테고리(Label) 인입. | OS 버전 피처에 학습 땐 없던 `iOS 18` 이라는 텍스트가 들어와 원핫 인코딩 에러 발생. |
| **결측치 폭증**<br>(Null/NaN Surge) | 파이프라인 장애로 특정 피처의 데이터 채워짐이 실패함. | 로그 수집기 장애로 유저 체류시간 피처의 99%가 Null로 채워짐. |

## Ⅲ. 중요도 기반 지능형 드리프트 관제 (Weighted Monitoring)
모든 피처가 평등한 것은 아니다.
1. **Feature Importance 결합**: Random Forest, XGBoost 등에서 모델 성능에 80%를 기여하는 상위 10%의 핵심 피처(Core Feature)를 식별.
2. **차등적 임계치(Threshold) 적용**:
   - **핵심 피처**: PSI > 0.1만 되어도 즉각 P1(Critical) 장애 알람 발생 및 서빙 차단.
   - **비핵심/노이즈 피처**: PSI > 0.25여도 대시보드상 단순 경고(Warning)만 띄우고 무시 (알람 피로 최소화).
3. **Drift Score 산출**: 개별 피처의 $\text{PSI} \times \text{Feature Importance}$ 값을 모두 더한 통합 'Feature Drift Score'를 생성하여 전체 파이프라인 건강도(Health) 모니터링.

## Ⅳ. 드리프트 탐지 알고리즘 (통계적 검정의 분리)
자료형에 따른 무기 선택.
| 검정 지표 | 적용 데이터 타입 | 알고리즘 특징 및 장단점 |
|:---:|:---|:---|
| **PSI** (Population Stability Index) | 범주형, 이산화된 수치형 | 현업/금융권 표준. 두 분포의 구간별 밀도 차이의 정보량 계산. 직관적 수치(0.1, 0.2) 제공. |
| **KS Test** (Kolmogorov-Smirnov) | 연속형 수치 (Numerical) | 누적분포함수(CDF) 간 최대 거리 계산. 평균/분산 변화를 매우 민감하게 잡아냄(비모수 검정). |
| **Chi-Square Test** (카이제곱) | 순수 범주형 (Categorical) | 각 카테고리의 빈도수 차이가 통계적으로 유의미한지 P-value로 도출. |

## Ⅴ. 실무 적용 및 결론
- **판단 지표**: 드리프트 원인 변수(Feature) 특정까지 걸리는 소요 시간(RCA Time < 10분), Feature Importance 상위 10개 피처의 모니터링 커버리지 100%, 오탐(False Positive) 알람 억제율.
- **실무 설계**: 통신사 K사의 '가입자 이탈(Churn) 예측 모델' 고도화 프로젝트. 기존엔 이탈 예측률이 20% 급락하면 무작정 모델 전체를 재학습시켰으나 성능이 복구되지 않음. 조치 방안: Feature 단위 모니터링(Evidently AI) 도입. 1) 수백 개 피처 중 모델 기여도 상위 5개인 `최근_통화_실패율`, `멤버십_포인트` 등에 개별 KS-test 가드레일 설치. 2) 며칠 뒤 `최근_통화_실패율` 피처의 분포가 0에서 갑자기 99(에러 코드)로 쏠리는 Feature Drift 알람 발생. 3) 분석 결과 통신사 내부 콜센터 DB의 API 규격 변경 버그(결측치)로 판명. 모델 재학습이 아닌 DB 파이프라인 버그를 패치(ETL 수정)하여 즉시 성능 100% 원상 복구.
- **결론**: Feature Drift 감시 체계는 머신러닝 시스템의 '면역 체계(Immune System)'다. 성능 하락이라는 질병이 발현되기 전에 파이프라인 내부의 독성 변수를 찾아내 격리함으로써, "모델이 망가진 건지 데이터가 썩은 건지"를 명확히 구분하는 MLOps 디버깅의 가장 날카로운 메스로 작용한다.

### 🔀 문제 유형별 목차 전환
- **Ⅱ·Ⅲ 강조 (개념/원리형)**: SHAP(SHapley Additive exPlanations) 값 기반의 드리프트 해석 원리. 통계적 PSI 지표만으로는 "이 드리프트가 모델에 얼마나 악영향을 미치는가"를 알 수 없으므로, Explainable AI(XAI) 기법인 SHAP 값을 연동하여 드리프트의 비즈니스 임팩트(Impact) 손실액을 역산출해 내는 수리적 매커니즘.
- **Ⅴ·Ⅵ 강조 (실무/설계형)**: 장애 발생 시 모델 가용성(High Availability) 확보 아키텍처. 핵심 피처에 치명적 드리프트(예: Null 값 폭증) 발생 시 런타임 에러를 뿜으며 모델 서빙이 죽어버리는 것을 막기 위해, Feature Store의 대체 로직(Imputation, 직전 정상 스냅샷 값 사용)을 구동하는 서킷 브레이커(Circuit Breaker) 아키텍처 설계.
