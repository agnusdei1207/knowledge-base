# 📖 【암기용】 개념 완전 이해

> 목적: 데이터 메시를 처음 봐도 완벽히 이해하게 만든다. 시험 답안 양식이 아니라, 이해를 위한 친절한 설명이다.

## 한눈에
- **개요**: 중앙 집중식 데이터 관리에서 벗어나, 데이터를 생성하는 각 부서(도메인)가 자신의 데이터를 책임지고 관리하며 서비스하는 분산형 데이터 아키텍처
- **왜 필요한가**: 회사가 커지면 중앙 데이터 팀이 모든 부서의 요구를 들어주지 못하는 '병목 현상'이 발생한다. 데이터를 제일 잘 아는 부서가 직접 데이터를 관리하게 하여 이 문제를 해결하려는 것이다.
- **핵심 직관**: "데이터 관리를 '중앙 도서관' 방식에서 '각 부서별 전문 서점' 방식으로 바꾸고, 이들을 네트워크로 연결하는 것."

## 깊이 이해
- **배경·문제의식**: 데이터 레이크나 DW를 아무리 크게 지어도, 데이터를 중앙 팀이 모르면 품질이 떨어지고 분석 요청 처리가 늦어짐. 도메인 전문가(현업 부서)는 데이터가 어디에 어떻게 쓰이는지 제일 잘 알지만 관리 권한이 없어서 소통 비용만 증가함.
- **작동 원리**: 4대 핵심 원칙을 따름. ① **도메인 소유권**: 각 부서가 데이터 관리. ② **데이터 제품**: 데이터를 내부 전용이 아닌 외부에도 파는 '상품'처럼 관리. ③ **셀프 서비스 플랫폼**: 각 부서가 쉽게 데이터를 다룰 수 있는 공통 인프라 제공. ④ **연합 거버넌스**: 전사 표준(보안, 포맷)을 준수하면서 분산 관리.
- **비유**: 마이크로서비스(MSA) 아키텍처의 데이터 버전임. 하나의 거대한 모놀리식 DB가 아니라, 각 서비스가 자기 DB를 가지고 API로 통신하듯, 각 도메인이 데이터를 API처럼 제공하는 것.
- **구체 예시**: 인사팀은 사원 정보 데이터를, 영업팀은 매출 데이터를 각각 '데이터 제품'으로 만들어 사내 마켓에 올림. 마케팅팀은 이 두 제품을 조합해 마케팅 분석을 수행함. 중앙 팀은 이들이 쓸 인프라만 깔아줌.
- **흔한 오해·주의점**: 특정 기술(소프트웨어)이 아님. 조직 문화, 프로세스, 아키텍처가 결합된 '패러다임'임. 소규모 조직에는 오히려 관리 부하만 늘릴 수 있음.

## 연결 개념
- Microservices Architecture (MSA) - 데이터 메시의 사상적 기반
- Data Product - 데이터 메시의 핵심 제공 단위
- Data Fabric - 데이터 메시와 유사하지만 '기술적 자동화'에 더 집중한 개념

# 📝 【답안용】 시험 답안 템플릿

> 목적: 시험장에서 25분에 그대로 쓰는 답안 양식. 작성방식(추상표현 금지·수치·도식·문제유형 전환)을 엄격히 지킨다.
> 핵심: 데이터 메시의 4대 핵심 원칙(Domain Ownership, Data as a Product, Self-serve Platform, Federated Governance)을 명확히 제시하고, 중앙 집중식의 한계를 어떻게 극복하는지 논한다.

## 핵심 인사이트 (3줄 요약)

> 1. **본질**: 데이터 메시는 중앙 집중식 데이터 아키텍처의 병목 문제를 해결하기 위해 데이터 소유권을 도메인별로 분산하고 '데이터 제품'화하는 탈중앙화 거버넌스 패러다임이다.
> 2. **가치**: 데이터를 가장 잘 아는 도메인 전문가가 품질을 책임지게 함으로써 데이터 가용성을 극대화하고, 전사적 데이터 확장성(Scalability) 문제를 해결한다.
> 3. **판단 포인트**: 기술적 구현보다 조직 구조의 변화와 셀프 서비스 인프라의 성숙도가 데이터 메시 성공의 결정적 요인이다.

## 출제 의도 및 답안 포인트

| 출제 의도 | 반드시 짚을 핵심 | 감점 회피 포인트 |
|:---|:---|:---|
| 데이터 아키텍처 패러다임 변화 이해 확인 | 중앙 집중(Lake/DW) vs 분산(Mesh)의 철학적 차이 | 단순히 "데이터 분산 저장"으로 오해하지 말 것 |
| 4대 핵심 원칙 서술 능력 | 도메인 소유권, 제품화, 플랫폼화, 연합 거버넌스 | 원칙 중 일부를 누락하거나 모호하게 서술 |
| 실무적 적용 및 한계 인식 확인 | 조직 문화, 거버넌스 복잡도, 데이터 메시 vs 데이터 패브릭 | 무조건 "데이터 메시가 좋다"는 식의 결론 지양 |

> 요약: 데이터 메시는 데이터 관리의 책임을 도메인으로 전이시켜 비즈니스 민첩성을 확보하는 데이터 거버넌스 혁신이다.

## Ⅰ. 개요 및 필요성

- 정의: 데이터의 소유권을 중앙 팀에서 비즈니스 도메인 팀으로 분산하고, 데이터를 서비스 형태로 제공하는 탈중앙화 데이터 아키텍처
- 배경: 중앙 집중형 데이터 레이크의 확장성 한계(Data Monolith), 도메인 지식 부족으로 인한 데이터 품질 저하
- 필요성: 분석 요구사항의 폭발적 증가 대응(Agility), 데이터 사일로 제거, 도메인 주도 설계(DDD)의 데이터 영역 확장

---

## Ⅱ. 구조 및 구성요소 (4대 핵심 원칙)

```text
[ Federated Computational Governance ] -> 전사 표준/정책 수립
             |
[ Domain Team A ]   [ Domain Team B ]   [ Domain Team C ]
  - Data Product      - Data Product      - Data Product
             |              |                  |
-------------------------------------------------------
[ Self-Serve Data Infrastructure Platform ] -> 공통 인프라 제공
```

| 원칙 | 상세 내용 | 핵심 가치 |
|:---|:---|:---|
| Domain Ownership | 데이터를 생성하는 도메인이 직접 관리 및 책임 | 도메인 전문성 기반의 고품질 데이터 |
| Data as a Product | 데이터를 외부 사용자가 쓰기 편한 '제품'으로 제공 | 발견 가능성, 신뢰성, 상호운용성 |
| Self-serve Platform | 도메인 팀이 인프라 걱정 없이 데이터를 다루는 환경 | 기술 장벽 완화 및 중복 투자 방지 |
| Federated Governance | 분산된 환경에서도 최소한의 전사 표준을 준수 | 데이터 보안, 컴플라이언스 유지 |

> 요약: 자율성(도메인)과 통제(거버넌스)의 균형을 맞추며 인프라를 서비스화하는 구조이다.

---

## Ⅲ. 동작원리 및 흐름도 (Data Product Lifecycle)

```text
Domain Source -> [ Ingest & Clean ] -> [ Data Product Publishing ] -> Consumer
                     |                          |
               (도메인 내 가공)             (카탈로그 등록/공유)
                     ^                          ^
                     |                          |
               [ Self-Serve Platform: Storage, Compute, Security ]
```

| 단계 | 처리 내용 | 검증 기준 |
|:---:|:---|:---|
| 1 | 도메인 소유권 확립 | 데이터를 생산하는 부서가 관리 주체로 지정됨 | 데이터 책임 소재 명확화 |
| 2 | 데이터 제품 개발 | 도메인 내부 데이터를 정제하여 표준 API/테이블로 노출 | 발견성, 주소 지정성(Addressability) |
| 3 | 카탈로그 등록 | 중앙 카탈로그에 데이터 제품 명세, 품질 지표, 권한 정보 등록 | 메타데이터 기반 가시성 |
| 4 | 연합 거버넌스 적용 | 공통 보안 정책(PII 마스킹 등)이 자동으로 적용됨 | 전사 보안 가이드라인 준수 |

> 요약: 각 도메인이 생산한 '데이터 제품'을 전사 플랫폼을 통해 안전하게 발견하고 활용하는 흐름이다.

---

## Ⅳ. 특징

| 구분 | 중앙 집중형 (Lake/DW) | 데이터 메시 (Mesh) |
|:---|:---|:---|:---|
| 조직 구조 | 중앙 집중 데이터 팀 | 분산된 도메인 팀 (Cross-functional) |
| 관리 철학 | 데이터 보관 및 통합 (Storage) | 데이터 가치 및 서비스 (Product) |
| 아키텍처 | 모놀리식 (Monolithic) | 분산 네트워크 (Distributed) |
| 성공 지표 | 저장된 데이터 용량, 쿼리 수 | 데이터 제품 수, 사용자 만족도, MTTI |

> 요약: 데이터 메시는 '저장'이 아닌 '소비와 가치' 중심의 분산 네트워크 시스템이다.

---

## Ⅴ. 심화 비교 및 적용 판단

| 구분 | 데이터 메시 (Data Mesh) | 데이터 패브릭 (Data Fabric) | 선택 기준 |
|:---|:---|:---|:---|
| 핵심 접근 | 조직 및 아키텍처의 분산 (Organizational) | 메타데이터 기반 기술적 자동화 (Technological) | 조직 변경 가능 여부 |
| 주요 동력 | 사람과 도메인 (Social) | AI 및 메타데이터 엔진 (AI-driven) | 기술 자동화 성숙도 |
| 관리 방식 | 수동적인 도메인 책임 부여 | 자동화된 데이터 가상화/통합 | 관리 인력 및 예산 |
| 목표 | 비즈니스 민첩성, 확장성 | 데이터 관리 자동화, 통합 가시성 | 해결 목표의 우선순위 |

> 요약: 메시는 '조직의 변화'를, 패브릭은 '기술의 자동화'를 통해 데이터 문제를 해결한다.

| 리스크 | 원인 | 대응 방안 | 확인 지표 |
|:---|:---|:---|:---|
| 거버넌스 파편화 | 도메인별 제각각의 관리 방식 | 연합 거버넌스 자동화(Guardrail) 적용 | 표준 준수율, 보안 사고 건수 |
| 도메인 역량 부족 | 현업 부서의 데이터 기술력 한계 | 셀프 서비스 플랫폼의 추상화 수준 고도화 | 도메인 팀의 데이터 제품 생성 주기 |
| 중복 투자 | 도메인별 중복된 도구/인프라 사용 | 강력한 중앙 플랫폼 팀의 표준 인프라 제공 | 전사 데이터 관련 TCO 변화율 |

> 요약: 자율성에 따른 무질서를 방지하기 위해 '자동화된 가드레일'과 '강력한 공통 플랫폼'이 필수적이다.

| 점검 항목 | 목표 기준 | 측정 방법 |
|:---|:---|:---|
| 데이터 제품 신뢰도 | 데이터 품질 지표(SLA) 준수율 99% 이상 | 도메인별 품질 대시보드 |
| 데이터 발견 시간 | 신규 데이터 검색 및 승인까지 1시간 이내 | 가탈로그 검색 및 권한 승인 로그 |
| 비즈니스 만족도 | 현업 부서의 데이터 활용 자급률 70% 이상 | 중앙 팀 의존도 설문 및 분석 티켓 수 |

> 요약: 도입 효과는 중앙 팀의 병목 해소와 도메인 팀의 데이터 활용 생산성으로 측정한다.

## Ⅵ. 실무 적용 및 결론

**적용 방안 3개:**
1. **도메인 데이터 스튜어드 지정**: 각 현업 부서에 데이터 품질과 제품화를 책임질 '데이터 스튜어드'를 배치하여 소유권 실현
2. **데이터 제품 카탈로그 구축**: 전사 데이터가 어디에 있고 누가 관리하는지 한눈에 볼 수 있는 마켓플레이스 형태의 카탈로그 운영
3. **Infrastructure as Code (IaC)**: 도메인 팀이 버튼 클릭만으로 보안이 설정된 데이터 저장소를 할당받을 수 있는 자동화 플랫폼 구축

**결론 (2줄):**
- 기술사 판단: 데이터 메시는 기술의 변화가 아닌 '데이터의 민주화'와 '책임의 분산'을 통한 조직적 성숙의 결과이며, 대규모 기업의 필수 생존 전략이다.
- 향후 방향: AI 에이전트가 데이터 제품을 자동으로 검색하고 조합하는 '에이전틱 데이터 메시'로 진화하여 분석 자동화가 가속화될 전망이다.
