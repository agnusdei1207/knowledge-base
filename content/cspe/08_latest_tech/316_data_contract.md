# 📖 【암기용】 개념 완전 이해

> 목적: Data Contract를 데이터 생산자와 소비자가 합의한 스키마·품질·SLA 약속으로 이해하게 만든다.

## 한눈에
- **개요**: 데이터셋의 구조, 의미, 품질, 변경 규칙을 코드처럼 관리하는 계약
- **왜 필요한가**: 컬럼명 변경, 타입 변경, 지연 적재가 사전 통보 없이 발생하면 분석 대시보드·ML 파이프라인·정산 로직이 동시에 깨진다.
- **핵심 직관**: API에 OpenAPI 명세가 있듯, 데이터 테이블에도 깨면 안 되는 입력·출력 명세가 필요하다.

## 깊이 이해
- **배경·문제의식**: 데이터 레이크와 스트리밍 플랫폼은 생산 팀과 소비 팀이 분리되어 있어 스키마 변경 책임이 불명확해지기 쉽다.
- **작동 원리**: YAML/JSON 계약에 필드명, 타입, 의미, null 허용, 품질 규칙, 갱신 주기, 소유자, 변경 정책을 기록하고 CI/CD에서 실제 데이터와 대조한다.
- **비유**: 납품 계약서에 품목, 규격, 납기, 검수 기준을 쓰듯 데이터 계약은 테이블의 규격과 납기, 검수 기준을 명시한다.
- **구체 예시**: `orders.amount`를 decimal(18,2)로 계약하고 null 비율 0.1% 이하를 검증하면, 문자열 적재나 대량 null 유입을 배포 전에 차단할 수 있다.
- **흔한 오해·주의점**: Data Contract는 문서가 아니라 테스트 가능한 운영 자산이다. 계약만 저장하고 파이프라인 검증에 연결하지 않으면 장애 예방 효과가 없다.

## 연결 개념
- Data Product — 데이터 계약을 포함해 소유권·SLA·사용 경험을 묶은 제품 단위
- Schema Registry — 이벤트 스키마 버전과 호환성을 검증하는 저장소
- Data Quality — 계약의 품질 규칙을 실제 데이터로 검증하는 활동

# 📝 【답안용】 시험 답안 템플릿

> 목적: 시험장에서 25분에 그대로 쓰는 답안 양식.
> 핵심: Data Contract는 데이터 생산자와 소비자의 책임을 스키마·품질·SLA·변경관리로 고정하는 운영 통제 수단임.

## 핵심 인사이트 (3줄 요약)

> 1. **본질**: Data Contract는 데이터셋의 스키마, 의미, 품질 규칙, SLA, 소유자를 기계 판독 가능한 형식으로 정의한 합의임.
> 2. **가치**: 스키마 드리프트와 품질 저하를 CI/CD·오케스트레이션 단계에서 탐지해 downstream 장애를 줄임.
> 3. **판단 포인트**: 계약 형식, 호환성 정책, 품질 테스트, 소유자 승인, 변경 통보 절차를 함께 설계해야 함.

## 출제 의도 및 답안 포인트

| 출제 의도 | 반드시 짚을 핵심 | 감점 회피 포인트 |
|:---|:---|:---|
| 데이터 거버넌스 운영 이해 확인 | 생산자·소비자 계약, 스키마, 품질, SLA | 컬럼 설명서로만 축소 |
| 데이터 파이프라인 장애 예방 판단 확인 | CI 검증, schema compatibility, 품질 게이트 | 사후 모니터링만 제시 |
| Data Mesh 연계 이해 확인 | 도메인 소유권, 데이터 제품, 계약 기반 변경관리 | 중앙 데이터팀 책임으로만 설명 |

> 요약: 이 문제는 데이터 설명이 아니라 변경 가능한 데이터 인터페이스를 계약으로 통제하는 능력을 요구한다.

---

## Ⅰ. 개요 및 필요성

- 개요: 데이터 인터페이스 계약
- 배경: 생산자 시스템의 컬럼·타입·코드값 변경이 소비자 파이프라인 장애로 전파됨.
- 필요성: 스키마, 품질, SLA, 변경 승인 기준을 배포 전 검증해 데이터 장애를 계약 위반으로 식별해야 함.

---

## Ⅱ. 구조 및 구성요소

```text
Producer System -> Data Contract -> Validation Gate -> Dataset / Event
                        +-> Owner / SLA / Change Policy
                        +-> Consumer Approval / Lineage
```

| 구성요소 | 역할 | 특이사항 |
|:---|:---|:---|
| 스키마 명세 | 필드명·타입·nullable·키 정의 | backward/forward compatibility |
| 의미 명세 | 컬럼 의미·단위·코드값 정의 | business glossary 연결 |
| 품질 규칙 | null 비율·범위·유일성 검증 | Great Expectations, dbt tests |
| 운영 조건 | 소유자·SLA·변경 정책 기록 | 승인·통보·버전관리 |

> 요약: Data Contract는 스키마와 품질 규칙에 소유자·SLA·변경 정책을 붙여 데이터 인터페이스를 검증 가능하게 만든다.

---

## Ⅲ. 동작원리 및 흐름도

```text
계약 작성 -> Git Review -> 파이프라인 배포 전 검증
-> 실제 데이터 대조 -> 위반 차단 / 승인 -> 소비자 알림
```

| 단계 | 처리 내용 | 검증 기준 |
|:---:|:---|:---|
| 1 | 생산자와 소비자가 필드·의미·SLA를 합의함 | owner와 consumer 명시 |
| 2 | 계약 파일을 저장소에 버전관리함 | YAML/JSON schema validation |
| 3 | CI/CD에서 실제 테이블·이벤트와 계약을 대조함 | type, null, range, freshness |
| 4 | 호환성 위반 시 배포 차단 또는 승인 절차 실행 | breaking change 승인 기록 |

> 요약: Data Contract는 합의, 버전관리, 자동 검증, 변경 승인 흐름으로 데이터 변경의 책임 소재를 남긴다.

---

## Ⅳ. 특징

| 구분 | 기존 데이터 명세 | Data Contract | 판단 기준 |
|:---|:---|:---|:---|
| 형식 | 문서·위키 | YAML/JSON 등 기계 판독 | 자동 검증 필요성 |
| 책임 | 데이터팀 중심 | 생산자·소비자 공동 승인 | 도메인 소유권 |
| 검증 | 사후 장애 확인 | 배포 전 계약 테스트 | pipeline gate |
| 변경 | 이메일 통보 | 버전·호환성 정책 | breaking change 여부 |

> 요약: Data Contract는 정적 문서를 배포 파이프라인의 검증 조건으로 바꾸는 데이터 운영 방식이다.

---

## Ⅴ. 심화 비교 및 적용 판단

| 비교 축 | 기존/대안 | 본 키워드 | 선택 기준 |
|:---|:---|:---|:---|
| 구조 | Data Catalog 메타데이터 | 계약 기반 인터페이스 | 변경 차단 필요 시 |
| 품질 | 별도 품질 점검 | 계약 내 품질 규칙 | SLA 대상 데이터셋 |
| 운영 | 사후 장애 대응 | CI/CD 게이트 | 소비자 영향 큰 데이터 |

> 요약: 설명 목적은 카탈로그, 변경 통제 목적은 Data Contract를 우선 적용한다.

| 리스크 | 원인 | 대응 방안 | 확인 지표 |
|:---|:---|:---|:---|
| 과도한 계약 | 모든 컬럼에 규칙 부여 | 핵심 소비 필드부터 적용 | 계약 위반 대비 실제 장애 |
| 계약 미준수 | 검증이 배포와 분리 | CI/CD·Airflow·dbt 게이트 연결 | gate pass/fail 기록 |
| 승인 지연 | 소비자 승인 절차 과다 | breaking change만 승인 대상화 | change lead time |

> 요약: Data Contract는 핵심 데이터셋부터 자동 게이트로 연결하고, 승인 범위를 breaking change로 좁혀야 운영 가능하다.

| 점검 항목 | 목표 기준 | 측정 방법 |
|:---|:---|:---|
| 계약 커버리지 | 핵심 데이터셋 계약 등록 | catalog 대조 |
| 검증 실행 | 배포·적재마다 계약 테스트 | CI 로그, orchestration log |
| 변경 통제 | breaking change 승인 추적 | PR·ticket 감사 |

> 요약: 도입 성과는 계약 수가 아니라 핵심 데이터셋의 자동 검증률과 breaking change 추적성으로 판단한다.

---

## Ⅵ. 실무 적용 및 결론

**적용 방안 3개:**
1. 핵심 테이블과 Kafka topic부터 필드·타입·품질·freshness·owner를 Data Contract YAML로 정의함.
2. dbt tests, Great Expectations, Schema Registry를 CI/CD와 오케스트레이션에 연결해 계약 위반 배포를 차단함.
3. 컬럼 삭제·타입 변경·의미 변경은 breaking change로 분류하고 소비자 승인, deprecation 기간, lineage 영향 분석을 의무화함.

**결론 (2줄):**
- 기술사 판단: 소비자가 많은 공유 데이터는 Data Contract를 우선 적용하고, 단일 팀 내부 임시 데이터는 카탈로그 수준으로 관리함.
- 향후 방향: Data Contract는 Data Product, Data Mesh, AI 학습 데이터 거버넌스의 인터페이스 통제 단위로 확대됨.
