# 📖 【암기용】 개념 완전 이해

> 목적: 데이터 계약을 처음 봐도 완벽히 이해하게 만든다. 시험 답안 양식이 아니라, 이해를 위한 친절한 설명이다.

## 한눈에
- **개요**: 데이터를 주는 쪽(생산자)과 받는 쪽(소비자)이 데이터의 형식, 품질, 보안 정책 등을 미리 약속하고 문서화한 기술적 협약
- **왜 필요한가**: 개발자가 DB 구조를 바꿨는데, 이를 모르던 분석팀의 대시보드가 깨지는 사고가 빈번하기 때문이다. 미리 '계약'을 맺어두면 구조를 바꿀 때 자동으로 경고를 주거나 차단할 수 있다.
- **핵심 직관**: "데이터 세계의 'API 명세서'이자 '품질 보증 서약서'."

## 깊이 이해
- **배경·문제의식**: 데이터는 생산자와 소비자가 다를 때가 많음. 생산자(개발자)는 앱 기능 구현이 우선이라 DB를 자주 바꾸지만, 소비자(분석가)는 그 결과물에 의존함. 이 소통의 부재가 '데이터 품질 저하'와 '파이프라인 장애'의 80%를 차지함.
- **작동 원리**: 데이터의 스키마(컬럼명, 타입), 데이터 품질(결측치 허용 범위), 보안(PII 포함 여부), SLA(제공 주기) 등을 YAML이나 JSON 형태의 '계약서'로 정의함. CI/CD 파이프라인에서 이 계약을 위반하는 변경이 발생하면 배포를 중단하거나 담당자에게 알림을 보냄.
- **비유**: 아파트 층간 소음 협약과 같음. 위층(생산자)이 인테리어 공사를 하거나 큰 소리를 낼 때(데이터 구조 변경), 아래층(소비자)과 맺은 협약 범위 내에서만 하거나 미리 알리기로 약속하여 갈등을 예방하는 것.
- **구체 예시**: "고객 ID는 항상 필수(NOT NULL)여야 하며, 숫자로만 구성되어야 한다"는 계약을 맺음. 만약 개발자가 실수로 문자열을 넣으려 하면, 시스템이 이를 감지해 데이터 레이크에 쌓이기 전에 차단함.
- **흔한 오해·주의점**: 단순한 '문서'가 아님. 실제 시스템(CI/CD, 거버넌스 도구)에 연동되어 자동으로 검증되고 강제되는 '코드 형태의 협약(Contract as Code)'이어야 의미가 있음.

## 연결 개념
- Data Mesh - 도메인 팀 간 협업을 위해 데이터 계약이 필수적임
- Schema Registry - 데이터 계약 중 '형식' 부분을 관리하는 저장소
- SLO (Service Level Objective) - 데이터 계약에 포함되는 성능/품질 목표

# 📝 【답안용】 시험 답안 템플릿

> 목적: 시험장에서 25분에 그대로 쓰는 답안 양식. 작성방식(추상표현 금지·수치·도식·문제유형 전환)을 엄격히 지킨다.
> 핵심: 데이터 계약의 구성 요소(Schema, Quality, SLA)를 명시하고, 생산자와 소비자 간의 결합도를 낮추면서 품질을 보장하는 '인터페이스'로서의 역할을 강조한다.

## 핵심 인사이트 (3줄 요약)

> 1. **본질**: 데이터 계약은 데이터 생산자와 소비자 간에 체결된 데이터 인터페이스, 품질 표준 및 서비스 수준에 대한 명시적이고 기계 읽기 가능한 기술적 협약이다.
> 2. **가치**: 상류(Upstream) 시스템의 변경이 하류(Downstream) 분석 환경에 미치는 영향을 차단하여 데이터 파이프라인의 안정성과 품질 신뢰도를 확보한다.
> 3. **판단 포인트**: 단순한 문서화를 넘어 CI/CD 파이프라인과 연동된 자동 검증 및 강제(Enforcement) 메커니즘 구축이 핵심이다.

## 출제 의도 및 답안 포인트

| 출제 의도 | 반드시 짚을 핵심 | 감점 회피 포인트 |
|:---|:---|:---|
| 데이터 품질 사고 원인 분석 능력 | 생산자-소비자 간 소통 부재 및 결합도 문제 | 단순히 "데이터가 깨진다"는 현상만 서술 |
| 데이터 계약 구성 요소 및 원리 | Schema, Metadata, Quality, SLA, YAML/JSON 정의 | 기술적 명세(계약서 포맷 등) 누락 |
| 현대적 데이터 거버넌스(Mesh) 연계 | 도메인 간 협업, Contract-first 개발, 자동화 검증 | "서로 잘 협의하자"는 식의 관념적 서술 지양 |

> 요약: 데이터 계약은 데이터를 '부산물'이 아닌 '정의된 인터페이스'로 취급하여 공급망 신뢰를 구축하는 도구이다.

## Ⅰ. 개요 및 필요성

- 정의: 데이터 생산자와 소비자 간의 상호 운용성을 보장하기 위해 데이터 스키마, 품질, 보안, 가용성 정책을 명시한 기술적 규약
- 배경: 애플리케이션 변경에 따른 데이터 파이프라인의 잦은 장애(Silent Failure), 부서 간 데이터 의미 해석 차이 발생
- 필요성: 데이터 품질 관리의 시점 이동(Shift-left), 생산자의 책임 의식 고취(Ownership), 자동화된 거버넌스 실현

---

## Ⅱ. 구조 및 구성요소 (Data Contract Architecture)

```text
[ Producer System ] <--- [ Data Contract ] ---> [ Consumer System ]
      |                         |                        |
      +--> (1) API/CI-CD        |           (2) Discovery/Monitor <--+
                                |
[ Contract Definition (YAML/JSON) ]
  - Schema: Column, Type, Constraint
  - Metadata: Description, Owner, Tag
  - Quality: Nullable, Uniqueness, Latency
  - Security: PII Masking, Access Policy
```

| 구성요소 | 역할 | 특이사항 |
|:---|:---|:---|
| Schema Definition | 데이터의 물리적 구조(이름, 타입, 필수 여부) 정의 | Protobuf, Avro, JSON Schema |
| Quality Constraints | 데이터가 충족해야 할 통계적 기준(값의 범위 등) | Great Expectations 등과 연계 |
| Service Level (SLA) | 데이터 제공 주기, 신선도, 가동률 약속 | 데이터 제공의 비즈니스 가동률 |
| Governance Policy | 개인정보 취급 및 접근 권한 정책 명시 | 컴플라이언스 대응의 근거 |

> 요약: 데이터의 형상(Schema)과 내실(Quality), 그리고 제공 약속(SLA)을 하나의 코드로 묶어 관리한다.

---

## Ⅲ. 동작원리 및 흐름도 (Contract-first Workflow)

```text
1. 계약 정의 -> 2. CI/CD 검증 -> 3. 데이터 생산 -> 4. 런타임 감시 -> 5. 위반 조치
      |               |                |               |                |
(생산/소비 합의)  (스키마 변경 체크)   (계약 준수 기록)  (품질 지표 측정)  (경고/차단)
```

| 단계 | 처리 내용 | 검증 기준 |
|:---:|:---|:---|
| 1 | 계약 수립 | 소비자의 요구사항을 반영하여 생산자가 계약 명세서 작성 | 버전 관리 (Git) |
| 2 | 배포 전 검증 | 생산자의 소스 변경(DDL 등)이 계약을 위반하는지 체크 | Breaking Change 감지 |
| 3 | 데이터 발행 | 계약된 형식과 품질에 맞는 데이터만 게이트웨이 통과 | Schema Registry 연동 |
| 4 | 품질 모니터링 | 운영 중 데이터가 계약된 품질/SLA를 유지하는지 감시 | 실시간 대시보드 |
| 5 | 위반 대응 | 위반 발생 시 생산자에게 티켓 자동 발행 또는 데이터 차단 | 피드백 루프 형성 |

> 요약: 설계 단계에서 계약을 맺고, 배포와 운영 전 과정에서 이를 자동 검증하여 장애를 사전에 방지한다.

## Ⅳ. 특징

| 구분 | 주요 특징 | 상세 내용 |
|:---|:---|:---|
| Shift-left | 사전 방지 | 문제가 발생한 후(하류)가 아니라 발생 전(상류)에 통제 |
| Decoupling | 시스템 결합도 완화 | 내부 DB 구조를 숨기고 계약된 '인터페이스'만 노출 |
| 가시성 | 명시적 정의 | 데이터가 무엇을 의미하고 어떤 품질인지 누구나 파악 가능 |
| 신뢰성 | 품질 보증 | 약속된 품질을 기반으로 소비자가 안심하고 분석 수행 |

> 요약: 데이터 계약은 '소통의 기술화'를 통해 데이터 파이프라인의 불확실성을 제거한다.

## Ⅴ. 심화 비교 및 적용 판단

| 비교 축 | 데이터 카탈로그 | 데이터 계약 (Data Contract) | 선택 기준 |
|:---|:---|:---|:---|
| 목적 | 데이터 탐색 및 이해 (Passive) | 데이터 무결성 강제 및 협업 (Active) | 관리의 강제성 필요도 |
| 시점 | 데이터 생성 후 (Post-generation) | 데이터 설계 및 생성 전 (Pre-generation) | 거버넌스 적용 시점 |
| 관계 | 소비자 중심의 정보 포털 | 생산자-소비자 간의 양방향 약속 | 협업 주체 간의 역학 |
| 주요 도구 | Amundsen, DataHub | OpenDataContract, dbt, CI/CD 도구 | 인프라 자동화 수준 |

> 요약: 카탈로그가 '무엇이 있는지' 보여준다면, 계약은 '무엇을 지킬지' 강제한다.

| 리스크 | 원인 | 대응 방안 | 확인 지표 |
|:---|:---|:---|:---|
| 개발 민첩성 저하 | 엄격한 계약 검증으로 배포 지연 | 비파괴적 변경(Non-breaking) 자동 승인 룰 적용 | 배포 성공률 및 소요 시간 |
| 관리 오버헤드 | 수많은 데이터 소스별 계약 관리 부담 | 핵심 데이터(Tier-1) 위주 우선 적용, 자동 생성 도구 활용 | 계약 적용 대상 비중 |
| 계약의 노후화 | 비즈니스 변화를 따라가지 못하는 계약 | 계약의 진화(Evolution) 프로세스 및 버전 관리 체계 수립 | 계약 갱신 주기 및 오류 건수 |

> 요약: '유연한 버전 관리'와 '중요도 기반의 선별적 적용'이 운영 부하를 줄이는 핵심이다.

| 점검 항목 | 목표 기준 | 측정 방법 |
|:---|:---|:---|
| 파이프라인 가동률 | 스키마 변경에 의한 장애 90% 이상 감소 | 장애 원인 분석 보고서 |
| 데이터 품질 지표 | 계약 준수율(SLA/Quality) 99% 달성 | 품질 모니터링 시스템 로그 |
| 사용자 만족도 | 소비자(분석가)의 데이터 신뢰도 점수 향상 | 정기 만족도 설문 조사 |

> 요약: 도입 효과는 파이프라인의 안정성 지표와 데이터 소비자의 신뢰도 변화로 평가한다.

## Ⅵ. 실무 적용 및 결론

**적용 방안 3개:**
1. **CI/CD 파이프라인 연계**: GitHub Actions 등에 데이터 계약 검증 스텝을 추가하여 스키마 파괴 변경 시 빌드 실패 처리
2. **도메인 데이터 공유 플랫폼**: 데이터 메시 아키텍처에서 도메인 간 데이터를 주고받을 때 '데이터 계약서' 첨부를 의무화하여 책임 명확화
3. **데이터 품질 자동 감시**: 계약에 정의된 규칙(예: 유저 ID 10자리)을 기반으로 스트리밍 데이터에 대한 실시간 유효성 체크 수행

**결론 (2줄):**
- 기술사 판단: 데이터 계약은 데이터를 단순히 '저장된 상태'가 아닌 '살아있는 서비스'로 취급하는 인식의 전환이며, 고도의 데이터 성숙도를 위한 필수 관문이다.
- 향후 방향: AI가 비즈니스 로직을 분석하여 데이터 계약을 초안을 제안하고, 분산된 시스템 간 계약 이행을 자동 중계하는 '지능형 계약 플랫폼'으로 진화할 것이다.
