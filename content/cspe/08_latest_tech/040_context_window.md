## 미리 알고가기

- Context Window는 모델이 한 번의 추론에서 참조할 수 있는 전체 토큰 예산임
- KV Cache는 이미 처리한 토큰의 Key, Value를 저장해 다음 토큰 생성 속도를 높이는 메모리 구조임
- TTFT는 요청 후 첫 토큰이 반환될 때까지의 지연 시간으로 긴 컨텍스트에서 급격히 늘어날 수 있음

## Ⅰ. 개요

- **정의/개념**: Context Window는 LLM이 한 번의 입력과 생성 과정에서 동시에 참조할 수 있는 최대 토큰 범위로서 프롬프트 길이와 대화 기억 범위와 문서 처리 상한을 규정하는 모델 제약임
- **배경/필요성**: 문서 검색, 코드 분석, 장기 대화처럼 서로 멀리 떨어진 정보를 한 번에 참조해야 하는 작업이 늘어나면서, 단순 모델 크기보다 긴 문맥을 얼마만큼 안정적으로 유지하는지가 실무 성능의 핵심 기준이 됨

## Ⅱ. 특징

- 입력 가능 문서량과 대화 기억량을 직접 제한하므로 사용자 경험과 활용 범위를 즉시 결정함
- 단순 UI 제한이 아니라 attention 연산량과 KV cache 메모리 사용량에 의해 물리적으로 제약됨
- 컨텍스트가 커질수록 교차 참조 능력은 좋아지지만 TTFT와 비용도 함께 증가함
- Long Context 모델, prompt caching, RAG 전략과 결합해 실무적으로 운용해야 효과가 남

## Ⅲ. 종류 및 비교

| 판단 기준 | 짧은 컨텍스트 | 긴 컨텍스트 | RAG 기반 보완 |
|:---|:---|:---|:---|
| 직접 참조 범위 | 제한적임 | 넓음 | 검색된 일부만 주입 |
| 추론 지연 | 낮음 | 높음 | 중간 |
| 비용 | 낮음 | 높음 | 검색 비용 추가이나 제어 가능 |
| 적합 업무 | 짧은 질의응답 | 장문 분석, 다문서 비교 | 대규모 지식 질의응답 |

## Ⅳ. 구성요소 및 구조

| 구성요소 | 설명 |
|:---|:---|
| Token Budget | 시스템 프롬프트, 사용자 입력, 검색 문맥, 생성 답변이 함께 소비하는 전체 토큰 한도임 |
| Attention Memory | 현재 컨텍스트 전체를 상호 참조하는 연산 영역으로 길이가 늘수록 비용이 빠르게 증가함 |
| KV Cache | 이미 처리한 문맥을 저장해 생성 효율을 높이지만 긴 대화에서는 메모리 점유가 커짐 |
| Context Manager | 어떤 문서를 넣고 무엇을 요약하거나 제거할지 결정해 실제 컨텍스트 사용 효율을 통제하는 계층임 |

## Ⅴ. 원리 및 절차 흐름도

```text
+-------------+     +-------------+     +--------------+     +-----------+
| 토큰 예산 계산 | --> | 문맥 적재    | --> | Attention/KV | --> | 응답 생성  |
+-------------+     +-------------+     +--------------+     +-----------+
```

1. **토큰 예산 계산**: 시스템 지시, 사용자 입력, 검색 결과, 예상 출력 길이를 합산해 허용 범위를 산정함
2. **문맥 적재**: 우선순위가 높은 정보부터 컨텍스트에 배치하고 초과분은 요약하거나 제거함
3. **Attention, KV 처리**: 모델이 적재된 문맥을 상호 참조하고 생성 단계에서는 KV cache를 활용함
4. **응답 생성**: 제한된 문맥 안에서 답변을 생성하고 다음 턴에는 일부 문맥을 재사용하거나 축약함

## Ⅵ. 문제점 및 해결 방안

1. 문제: 컨텍스트가 길어질수록 attention과 KV cache 비용이 커져 추론 지연과 인프라 비용이 급격히 증가함
   - 해결방안: prompt caching과 token budget 정책을 적용하고 TTFT와 요청당 비용으로 최적 구성을 검증함
2. 문제: 긴 문서를 모두 넣어도 중간 구간 정보가 묻혀 핵심 근거를 놓치는 lost-in-the-middle 현상이 발생할 수 있음
   - 해결방안: 중요 정보 재배치와 요약 앵커를 적용하고 needle-in-a-haystack 정확도와 answer faithfulness로 효과를 검증함
3. 문제: 필요 이상으로 긴 문맥을 매 턴 전송하면 실제 정답률 향상보다 비용 증가와 사용자 대기시간만 커질 수 있음
   - 해결방안: RAG와 요약 기반 라우팅으로 필요한 문맥만 선별하고 answer accuracy 대비 token cost 비율로 효율을 검증함

## Ⅶ. 적용 사례

- 코드베이스 분석: 다수 파일을 한 번에 넣어 구조적 의존성을 파악함, 확인 지표는 버그 탐지율과 TTFT임
- 장기 대화형 상담: 이전 대화 이력을 유지해 맥락 일관성을 높임, 확인 지표는 context retention rate와 user satisfaction임
- 계약서 검토: 긴 법률 문서를 교차 참조해 충돌 조항을 찾음, 확인 지표는 clause recall과 review time임

## Ⅷ. 결론

컨텍스트 윈도우는 단순히 클수록 좋은 수치가 아니라 비용과 지연을 감당 가능한 수준으로 유지하면서 필요한 근거를 얼마나 효율적으로 남기느냐를 판단하는 운영 설계 변수임.
