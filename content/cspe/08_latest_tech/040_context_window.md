## 미리 알고가기

- 컨텍스트 창 ($Context$ $Window$): 모델이 한 번의 요청과 생성 과정에서 동시에 연산 테이블에 올릴 수 있는 최대 토큰 범위임
- $KV$ 캐시 ($KV$ $Cache$): 대화 중 이미 처리된 단어들의 Key, Value 연산 값을 메모리에 고정하여 재연산을 방지하는 메모리 영역임
- $TTFT$ ($Time$ $To$ $First$ $Token$): 사용자가 프롬프트를 전송한 후 첫 번째 답변 글자가 출력되기까지 소요되는 지연 시간임
- 로스트 인 더 미들 ($Lost-in-the-Middle$): 입력된 긴 문서의 앞부분과 뒷부분은 잘 기억하지만, 중간 영역의 정보는 참조하지 못하고 유실하는 현상임

## Ⅰ. 개요

- **정의/개념**: Context Window는 대형 언어 모델($LLM$)이 한 번의 추론 주기에서 물리적으로 동시 참조하여 연산할 수 있는 프롬프트와 생성 토큰의 최대 결합 한계선이며, 인공지능이 유지할 수 있는 단기 기억의 크기를 규정하는 물리적 스펙임
- **배경/필요성**: 책 한 권 분량의 보고서 분석, 대규모 코드베이스 디버깅, 장기 상담 기록 추적 등 긴 시퀀스를 한 번에 입력해야 할 실제 비즈니스 사용성이 급증함에 따라, 단순 파라미터 크기 경쟁을 넘어 단기 정보 가용 공간의 크기가 핵심 경쟁력으로 부상함

## Ⅱ. 특징

- 사용자가 입력할 수 있는 파일의 개수와 이전 대화 문맥의 저장 한계선을 즉각 규정하므로, 애플리케이션의 사용자 시나리오 설계 영역을 한정함
- 단순히 소프트웨어적인 입력 제한이 아니라, 어텐션 연산 시 발생하는 $O(N^2)$ 복잡도의 VRAM 점유량과 물리적인 $KV$ 캐시 메모리 가용성에 의해 상한선이 결정됨
- 컨텍스트 창의 용량이 커질수록 여러 문서를 대조하는 교차 참조 성능은 비약하지만, 입력 검토에 드는 초기 추론 지연($TTFT$)과 토큰당 API 과금 비용이 비례하여 상승함

## Ⅲ. 종류 및 비교

| 판단 기준 | 단기 컨텍스트 모델 | 초장기 컨텍스트 모델 (Long Context) | 검색 증강 생성 ($RAG$) 보완 |
|:---|:---|:---|:---|
| **가용 토큰 크기** | 보통 4K ~ 8K 토큰 내외 | 128K ~ 1M 이상 (책 수십 권) | 무제한 지식 소스 (필요만 선별 주입) |
| **추론 지연 (TTFT)** | 매우 낮음 (밀리초 단위) | 매우 높음 (입력 비례 지연) | 중간 (검색에 소요되는 시간 발생) |
| **메모리(VRAM) 점유** | 안정적이고 경제적임 | 기하급수적으로 폭증 (서빙 부담) | 일정 수준 이하로 통제 가능 |
| **적합 업무 시나리오** | 단순 번역, 일상 대화 | 논문 교차 검토, 전체 소스코드 분석 | 대규모 사내 문서 지식 검색 QA |

> 요약: 단기는 빠른 속도에, 장기는 종합적 문맥 분석에, RAG는 제약 조건 제어 하의 대규모 외부 지식 활용에 특화됨.

## Ⅳ. 구성요소 및 구조

| 구성요소 | 설명 |
|:---|:---|
| 시스템 예산 가이드 | 프롬프트 입력과 최장 출력의 합이 최대 한도를 넘지 않도록 제한하는 쿼타 매니저임 |
| $KV$ 캐시 매니저 | 기연산된 문맥 정보($K, V$)를 VRAM에 파티셔닝하여 적재해 두고, 다음 단어 생성 시의 재연산 속도를 단축함 |
| 프롬프트 캐싱 | 동일하게 반복되는 시스템 메시지나 대화 역사를 임시 메모리에 박제해 두어 요금을 깎아주는 장치임 |
| 바운딩 마이너 | 창 영역을 벗어나는 오래된 대화 기록을 자동 요약하거나 망각 처리하여 창 크기를 보존하는 정책임 |

```text
[ 컨텍스트 윈도우 구성 배분 예시 (128K 한도 내) ]
[ System Prompt (2K) ] + [ Retrieval Context (100K) ] + [ User Query (2K) ] + [ Reserve for Output (24K) ]
- 합산 토큰이 물리 한계 128K를 넘지 않도록 토큰 예산을 정교하게 배분하여 가동함
```

## Ⅴ. 원리 및 절차 흐름도

```text
+-------------+     +--------------+     +-------------+     +-------------+
| 예산 쿼타책정| --> | 문맥 압축/적재| --> | KV캐시 활성화| --> | 순환생성/망각|
+-------------+     +--------------+     +-------------+     +-------------+
```

1. **예산 조율** — 사용자 질문과 함께 주입할 외부 문서들의 토큰 크기를 합산하고, 모델의 최대 창 크기를 넘지 않는지 검사함
2. **문맥 필터링** — 중요도가 낮은 대화 내역이나 공백을 전처리로 줄여, 한계 메모리 안에 가장 알짜배기 지식만 우선 적재함
3. **가속 연산** — 입력된 프롬프트를 한꺼번에 인코딩하며 발생한 $K, V$ 연산 값을 캐시에 보관하고, 쿼리와의 어텐션 가중치를 산출함
4. **기억 순환** — 답변 생성이 지속되면서 창의 끝부분이 차오르면, 가장 우선순위가 떨어지는 오래된 대역을 망각($Trimming$) 처리하여 안정적인 창 상태를 유지함

## Ⅵ. 실무 적용 및 유의점

1. 초장기 컨텍스트(예: 128K) 모델에 방대한 양의 규정집을 다 집어넣더라도 정답이 문서 중간 부분에 위치하면 모델이 이를 간과하고 오답을 내는 '로스트 인 더 미들' 현상이 발생하므로, 질문의 실마리가 되는 키워드 정보는 반드시 프롬프트의 최상단이나 최하단 영역에 전략적으로 배치하고 바늘찾기 성능($NIAH$) 평가를 통해 정밀도를 검증해야 함
2. 대화 세션이 길어져 이전 턴의 전체 대화를 매번 서버로 다시 보내면 중복 입력 비용과 $TTFT$가 선형적으로 증가하여 서비스 수지가 악화되므로, 중복 전송 구역의 연산 요금을 대폭 깎아주는 '프롬프트 캐싱($Prompt$ $Caching$)' 옵션을 API 게이트웨이에 적용하고 평균 응답 지연 단축 시간과 청구 요금 절감률을 정기 모니터링해야 함

## Ⅶ. 결론

- 컨텍스트 윈도우는 인공지능이 일관성 있게 집중할 수 있는 지식의 물리적 사정거리이며, 설계자는 무작정 창을 넓히는 장비 증설에 의존하지 말고 프롬프트 캐싱과 lost-in-the-middle 완화 배치를 설계하여 가성비 높고 강건한 서빙 인프라를 구현해야 함
