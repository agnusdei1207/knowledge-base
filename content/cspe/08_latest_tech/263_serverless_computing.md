# 📖 【암기용】 개념 완전 이해

> 목적: 개발자가 "서버(Server)를 신경 쓸(Less) 필요 없이" 오직 비즈니스 로직(코드)에만 집중할 수 있게 해주는 클라우드 컴퓨팅의 진화형을 이해한다.

## 한눈에
- **정의**: 클라우드 제공자(AWS, GCP 등)가 서버 등 인프라의 프로비저닝, 스케일링, 유지보수를 완전히 숨기고, 개발자는 코드만 올리면 실행된 시간만큼만 비용을 내는 **클라우드 실행 모델**
- **필요성**: 기존에는 이벤트를 대비해 트래픽이 없어도 하루 24시간 서버를 켜두고 돈을 내야 했으며, OS 업데이트나 해킹 방어 등 개발 외적인 서버 관리(Ops)에 너무 많은 시간을 뺏겼기 때문
- **핵심 직관**: "자동차를 직접 사서 주유, 세차, 정비를 다 하는 것(IaaS)이 아니라, 택시를 불러서 내가 '탄 거리만큼만' 돈을 내고 내리는 것(Serverless)"

## 깊이 이해
- **배경(왜 등장했나?)**: 클라우드(IaaS)가 유행하면서 물리 서버를 살 필요는 없어졌지만, 여전히 가상 머신(EC2)을 켜고 리눅스를 깔고 웹서버를 세팅해야 했다. "아니, 나는 그냥 이 함수(코드) 하나만 실행하고 싶은데 왜 OS부터 다 세팅해야 해?"라는 개발자들의 불만에서 AWS Lambda가 탄생하며 서버리스 시대가 열렸다.
- **작동 원리(어떻게 달성했나?)**: 
  1. **Event-driven (이벤트 기반)**: 평소에는 서버가 죽어 있다(비용 0원). 누군가 웹페이지 버튼을 누르거나(API 호출), 파일이 업로드되는 등 '이벤트'가 발생하면,
  2. **Auto-scaling (자동 확장)**: 클라우드 벤더가 0.1초 만에 컨테이너를 띄워 내 코드를 실행한다. 트래픽이 만 배로 뛰면 컨테이너 만 개를 알아서 띄운다.
  3. **Pay-as-you-go (종량제)**: 코드가 실행된 딱 '밀리초(ms)' 단위의 시간과 메모리 사용량만큼만 돈을 낸다.
- **일상 비유**: 수도꼭지와 같다. 평소에는 물(돈)이 전혀 안 새다가, 내가 밸브를 틀었을 때(이벤트 발생)만 물이 콸콸 나오고 딱 쓴 만큼만 수도 요금을 낸다.
- **구체 예시**: 서버리스는 크게 두 가지로 나뉜다.
  1. **FaaS (Function as a Service)**: 내가 직접 짠 백엔드 코드를 올리는 것 (AWS Lambda)
  2. **BaaS (Backend as a Service)**: 인증, DB, 스토리지 같은 공통 백엔드 기능을 빌려 쓰는 것 (Firebase, AWS DynamoDB, S3)
- **흔한 오해/주의점**: "서버리스는 진짜 서버가 없는 건가?" → 아니다! 물리적 서버는 당연히 구글이나 아마존 데이터센터에 존재한다. 단지 '사용자(개발자) 입장'에서 서버가 보이지 않고 관리할 필요가 없다(Less)는 뜻이다.

## 연결 개념
- **FaaS (Function as a Service)**: 서버리스 컴퓨팅의 핵심 구현체. 코드를 '함수' 단위로 쪼개어 배포함.
- **Microservices Architecture (MSA)**: 서버리스 함수들이 모여서 하나의 거대한 앱을 구성하는 아키텍처.
- **Cold Start (콜드 스타트)**: 서버리스의 치명적 단점. 코드가 너무 오랫동안 안 불리면 클라우드가 컨테이너를 죽여버리는데, 이때 다시 부르면 초기 구동(수 초)이 걸리는 현상.

# 📝 【답안용】 시험 답안 템플릿

## 핵심 인사이트 (3줄 요약)
> 1. **본질**: 서버리스 컴퓨팅(Serverless Computing)은 클라우드 프로바이더가 인프라의 관리 및 할당을 동적으로 처리하여, 개발자가 서버 프로비저닝 없이 애플리케이션 로직(Code)에만 집중할 수 있게 하는 클라우드 실행 모델이다.
> 2. **가치**: 이벤트 주도(Event-driven) 방식과 밀리초 단위의 종량제 과금(Pay-as-you-go)을 통해 유휴 자원(Idle Resource) 비용을 0원으로 만들고, 무한대의 오토 스케일링을 제공한다.
> 3. **판단 포인트**: FaaS와 BaaS의 결합으로 NoOps 시대를 열었으나, Cold Start 문제와 Vendor Lock-in(종속성), 그리고 복잡한 마이크로서비스 간의 디버깅 난이도(Observability)를 해결하는 아키텍처 설계가 필수적이다.

## Ⅰ. 개요 및 필요성
- **정의**: 인프라에 대한 용량 계획, 패치, 유지보수 없이 개발자가 코드나 비즈니스 로직을 배포하면, 실행 횟수와 시간에 비례하여 과금되는 클라우드 컴퓨팅 모델
- **배경**: IaaS/PaaS 환경에서도 여전히 OS 업데이트, 보안 패치, 로드 밸런서 설정 등 운영(Ops) 오버헤드가 존재. 항시 구동(Always-on)으로 인한 클라우드 비용 낭비 발생
- **필요성**: TTM(Time-to-Market)의 극단적 단축, 완벽한 NoOps(운영 제로) 실현, 트래픽 폭증(Spike)에 대한 유연한 대응

## Ⅱ. 클라우드 서비스 모델의 진화와 Serverless의 위치
| 구분 | IaaS (Infra) | PaaS (Platform) | Serverless (FaaS/BaaS) |
|:---|:---|:---|:---|
| **관리 주체** | OS, 미들웨어, 런타임, 데이터, 앱 | 데이터, 애플리케이션 | **오직 애플리케이션(함수 단위 코드)** |
| **스케일링 단위** | VM (가상 머신) | Instance / Container | **Request (요청/이벤트) 단위** |
| **과금 방식** | 켜둔 시간(Hour) 당 | 켜둔 시간(Hour) 당 | **실행된 시간(Millisecond) 당** |
| **유휴 상태 비용** | 트래픽 없어도 요금 발생 | 트래픽 없어도 요금 발생 | **트래픽 없으면 요금 0원 (Scale to Zero)** |

## Ⅲ. 서버리스 생태계 구성요소: FaaS와 BaaS
서버리스 애플리케이션은 사용자가 작성한 커스텀 코드(FaaS)와 클라우드 벤더가 제공하는 관리형 서비스(BaaS)의 결합으로 완성된다.

1. **FaaS (Function as a Service)**
   - **개념**: 개발자가 작성한 비즈니스 로직(함수)을 클라우드에 업로드하고, 특정 이벤트(HTTP 요청, 파일 업로드 등)가 발생할 때만 짧게 실행되는 컴퓨팅 환경.
   - **대표 서비스**: AWS Lambda, Google Cloud Functions, Azure Functions.
2. **BaaS (Backend as a Service)**
   - **개념**: 모바일/웹 앱 개발 시 공통으로 필요한 백엔드 기능(데이터베이스, 사용자 인증, 스토리지, 푸시 알림)을 API 형태로 빌려 쓰는 서비스.
   - **대표 서비스**: Firebase, AWS DynamoDB, Amazon Cognito, Amazon S3.

## Ⅳ. 서버리스 아키텍처 작동 메커니즘 (Event-Driven)
```text
[ Trigger (이벤트 발생) ] ──────> [ API Gateway ]
  - 사용자 스마트폰 앱 클릭          (요청 라우팅)
  - S3에 이미지 파일 업로드               │
  - DB에 데이터 추가                      ▼ 
                               [ FaaS (AWS Lambda) ] ◀── (트래픽에 맞춰 0개에서 1만 개로 즉시 확장)
                                 - 비즈니스 로직 연산
                                 - 이미지 리사이징 등
                                      │
                                      ▼ 
                               [ BaaS (데이터 저장) ]
                                 - DynamoDB (NoSQL)
```

## Ⅴ. 기술적 한계(리스크) 및 해결 방안
| 리스크 요인 | 현상 및 원인 | 기술적 대응 방안 |
|:---|:---|:---|
| **Cold Start (콜드 스타트)** | 함수가 일정 시간 호출되지 않으면 컨테이너를 내림. 다시 호출될 때 컨테이너/런타임을 적재하느라 수 초의 지연(Latency) 발생 | **Provisioned Concurrency**(미리 웜업된 상태 유지 설정) 적용 또는 C/Go/Rust 등 가벼운 언어 사용 |
| **Vendor Lock-in (벤더 종속)**| 각 클라우드 제공자마다 FaaS API, 트리거 구조, BaaS 연동 방식이 완전히 달라 다른 클라우드로의 이주가 거의 불가능함 | **Serverless Framework** 사용, 혹은 쿠버네티스 위에서 돌아가는 오픈소스 FaaS(**Knative, OpenFaaS**) 구축 |
| **상태 비저장 (Stateless)** | 함수는 실행이 끝나면 죽으므로 내부 메모리나 디스크에 데이터를 영구 저장할 수 없음 | 세션 상태 및 지속적 데이터는 반드시 외부의 초고속 BaaS(Redis, DynamoDB)에 저장하도록 아키텍처 설계 |
| **디버깅 및 추적의 어려움** | 거대한 앱이 수백 개의 함수로 잘게 쪼개져 얽혀 있어, 에러 발생 시 원인 추적이 지옥과 같음 | AWS X-Ray, Datadog 등 분산 추적(Distributed Tracing) 및 Observability 툴 도입 필수 |

## Ⅵ. 실무 적용 및 결론
**적용 방안 및 실무 가이드:**
1. **마이크로서비스 극단화 (Nano-services)**: 웹 애플리케이션의 API 하나하나를 전부 독립된 람다(Lambda) 함수로 쪼개어 배포한다. 이를 통해 특정 API(예: 결제)에 트래픽이 몰려도 다른 기능(예: 상품 검색)은 전혀 영향을 받지 않는 극강의 고가용성을 확보한다.
2. **배치/비동기 작업 최적화**: 사용자가 영상을 업로드하면 썸네일을 생성하고 인코딩하는 무거운 백그라운드 작업을 서버리스로 넘기면, 별도의 인코딩 서버를 24시간 켜둘 필요 없이 엄청난 비용을 절감할 수 있다.

**결론:**
- 서버리스 컴퓨팅은 단순히 '서버 관리의 회피'를 넘어, 코드를 비즈니스 가치로 변환하는 시간을 최소화하는 **애자일(Agile) 혁신의 최종 진화 형태**이다.
- 콜드 스타트와 벤더 종속이라는 리스크가 존재하지만, 초기 스타트업부터 엔터프라이즈의 비동기 마이크로서비스 확장에 이르기까지 "가장 빠르고 경제적으로 시스템을 구축하는" 표준 아키텍처로 자리 잡았다.
