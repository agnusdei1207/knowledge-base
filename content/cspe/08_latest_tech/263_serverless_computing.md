## 미리 알고가기

- 서버리스는 서버가 없다는 뜻이 아니라 인프라 운영 책임이 플랫폼 제공자로 크게 이동한 실행 모델임
- 자동 확장과 사용량 기반 과금이 핵심 가치임
- 상태 관리와 콜드스타트와 벤더 종속성이 대표 운영 이슈임

## Ⅰ. 개요

- **정의/개념**: Serverless Computing은 개발자가 서버 프로비저닝과 운영을 직접 관리하지 않고 코드나 서비스를 배포하면 플랫폼이 자동으로 실행과 확장과 과금을 처리하는 클라우드 실행 모델임
- **배경/필요성**: 이벤트 기반 서비스와 불규칙한 트래픽 환경에서 고정 서버 운영은 비용과 운영 부담이 커 사용량 기반 자동 실행 모델이 각광받게 됨

## Ⅱ. 특징

- 인프라 운영 책임이 감소해 개발 생산성을 높임
- 요청 기반 자동 확장으로 유휴 자원 비용을 줄일 수 있음
- 사용량 기반 과금으로 소규모 이벤트 처리에 유리함
- 상태 유지와 지연 민감 워크로드에는 제약이 존재함

## Ⅲ. 종류 및 비교

| 판단 기준 | Serverless | Container Service | VM 기반 서비스 |
|:---|:---|:---|:---|
| 운영 책임 | 낮음 | 중간 | 높음 |
| 확장 자동화 | 매우 높음 | 높음 | 제한적 |
| 지연 제어 | 상대적으로 약함 | 중간 | 높음 |
| 적합 워크로드 | 이벤트성, 간헐성 | 지속 서비스 | 장기 실행과 특수 환경 |

## Ⅳ. 구성요소 및 구조

| 구성요소 | 설명 |
|:---|:---|
| Event Source | HTTP 요청과 메시지 큐와 스토리지 이벤트처럼 함수 실행을 트리거하는 입력 원천임 |
| Serverless Runtime | 코드를 격리된 실행 환경에서 기동하고 요청마다 필요한 자원을 할당하는 실행 계층임 |
| Autoscaling Engine | 요청량에 따라 인스턴스를 자동 증감해 사용량 변화에 즉시 대응하는 확장 계층임 |
| Billing Meter | 실행 시간과 호출 수와 자원 사용량을 계량해 종량 과금을 수행하는 측정 계층임 |
| Managed Integration | 인증과 로깅과 메시징과 데이터 저장소 같은 주변 기능을 통합 제공해 운영 부담을 줄이는 서비스 계층임 |

```text
+-------------+    +----------------+    +----------------+    +--------------+
| Event Source| -> | Serverless RT  | -> | Managed Service| -> | Billing Meter|
+-------------+    +----------------+    +----------------+    +--------------+
```

## Ⅴ. 원리 및 절차 흐름도

```text
+-------------+    +-------------+    +-------------+    +-------------+    +-------------+
| 이벤트 수신  | -> | 실행 환경 준비 | -> | 코드 실행    | -> | 결과 반환    | -> | 자원 회수    |
+-------------+    +-------------+    +-------------+    +-------------+    +-------------+
```

1. **이벤트 수신**: 플랫폼이 트리거 이벤트를 받음
2. **실행 환경 준비**: 필요한 실행 컨테이너나 샌드박스를 기동함
3. **코드 실행**: 지정된 함수나 서비스를 수행함
4. **결과 반환**: 응답이나 후속 이벤트를 생성함
5. **자원 회수**: 사용하지 않는 실행 환경을 줄여 비용을 절감함

## Ⅵ. 문제점 및 해결 방안

1. 문제: 요청이 드문 서비스는 콜드스타트로 인해 첫 응답 지연이 커져 사용자 경험이 저하될 수 있음
   - 해결방안: provisioned concurrency와 warm up strategy를 적용하고 cold start latency와 p95 response time으로 검증함
2. 문제: 플랫폼 종속 서비스에 깊게 묶이면 이식성과 장기 비용 통제가 어려워질 수 있음
   - 해결방안: abstraction layer와 portability aware architecture를 적용하고 migration effort index와 managed service dependency ratio로 검증함
3. 문제: 무상태 실행 모델에 맞지 않는 세션과 장기 작업을 직접 올리면 운영 복잡도와 실패율이 커질 수 있음
   - 해결방안: external state store와 async workflow design을 적용하고 state consistency error rate와 long running failure rate로 검증함

## Ⅶ. 적용 사례

- 간헐적 이벤트 처리 시스템이 provisioned concurrency를 운영하며 확인 지표는 cold start latency와 p95 response time임
- 멀티클라우드 아키텍처가 이식성 계층을 적용하며 확인 지표는 migration effort index와 managed service dependency ratio임
- 백오피스 비동기 처리 플랫폼이 외부 상태 저장을 사용하며 확인 지표는 state consistency error rate와 long running failure rate임

## Ⅷ. 결론

서버리스는 운영 부담을 크게 줄이지만 콜드스타트와 상태 관리와 종속성 문제를 함께 설계해야 비용 효율과 민첩성이 유지됨.
