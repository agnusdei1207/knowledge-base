# 📖 【암기용】 개념 완전 이해

> 목적: 서버리스를 처음 봐도 완벽히 이해하게 만든다. 시험 답안 양식이 아니라, 이해를 위한 친절한 설명이다.

## 한눈에
- **개요**: 개발자가 서버의 사양, 개수, 설치 등을 신경 쓰지 않고 코드만 짜서 올리면, 실행될 때만 자원을 할당받아 동작하는 컴퓨팅 방식
- **왜 필요한가**: 서버를 24시간 켜두면 사용자가 없을 때도 돈이 나가고 관리가 귀찮기 때문이다. 서버리스는 '쓴 만큼만' 돈을 내고 관리는 클라우드 업체가 다 해준다.
- **핵심 직관**: "내가 직접 차를 사서 관리(서버 운영)하지 않고, 필요할 때만 불러서 타고 내리는 '택시(Uber)' 같은 서비스"

## 깊이 이해
- **배경·문제의식**: 클라우드가 보급되었지만 여전히 개발자는 OS 패치, 서버 용량 증설(Scaling), 보안 설정을 고민해야 했다. 이를 **NoOps(No Operations)**로 전환하여 개발자가 '비즈니스 로직'에만 집중하게 하려는 시도다.
- **작동 원리**:
  1. **이벤트 기반(Event-driven)**: 어떤 사건(이미지 업로드, API 호출, DB 변경 등)이 발생하면 코드가 트리거된다.
  2. **즉시 실행 및 자동 확장**: 요청이 들어오는 순간 컨테이너가 순식간에 떴다가 연산이 끝나면 사라진다. 요청이 1,000개면 1,000개의 복사본이 동시에 뜬다.
  3. **사용량 과금**: 코드가 실행된 시간(밀리초 단위)과 메모리 사용량만큼만 비용이 청구된다.
- **비유**: 집의 전등과 같다. 스위치를 켜면(이벤트) 불이 들어오고(실행), 끄면 나간다. 전등을 어떻게 관리하는지는 한전(클라우드 업체)이 책임지고, 나는 쓴 전력량만큼만 요금을 낸다.
- **구체 예시**: AWS Lambda, Google Cloud Functions가 대표적이다. 사진을 올리면 자동으로 썸네일을 만드는 기능을 서버리스로 만들면, 사진이 올라올 때만 잠깐 서버가 돌아가고 평소엔 0원이다.
- **흔한 오해·주의점**: "서버가 아예 없는 것"은 아니다. 어딘가에 서버는 있지만 **내가 관리하지 않을 뿐**이다. 또한, 처음 실행할 때 약간의 지연 시간(**Cold Start**)이 발생할 수 있어, 극도로 빠른 응답이 필요한 서비스는 주의해야 한다.

## 연결 개념
- FaaS (Function as a Service) — 서버리스의 핵심 실행 형태 (함수 단위 실행)
- BaaS (Backend as a Service) — 인증, DB 등 백엔드 기능을 API로 빌려 쓰는 서버리스의 한 축
- Cold Start — 서버리스의 가장 큰 기술적 단점 (초기 기동 지연)

# 📝 【답안용】 시험 답안 템플릿

> 목적: 시험장에서 25분에 그대로 쓰는 답안 양식. 작성방식(추상표현 금지·수치·도식·문제유형 전환)을 엄격히 지킨다.
> 핵심: 서버리스는 추상화 수준(NoOps)과 과금 모델(Pay-as-you-go), 이벤트 기반 아키텍처를 중심으로 기술한다.

## 핵심 인사이트 (3줄 요약)

> 1. **본질**: 서버리스 컴퓨팅(Serverless Computing)은 클라우드 제공업체가 서버 자원을 동적으로 관리하며, 개발자는 인프라 관리 없이 코드(함수)만 배포하는 서비스 모델이다.
> 2. **가치**: 인프라 운영 부담(NoOps)을 제거하고, 실제 사용량 기반의 과금 방식을 통해 가동 비용을 최적화하며 무한한 확장성(Scalability)을 제공한다.
> 3. **판단 포인트**: 실행 지연(Cold Start) 및 실행 시간 제한(Timeout) 등의 제약 사항을 고려하여 상태가 없는(Stateless) 단기 실행 워크로드에 우선 적용한다.

## 출제 의도 및 답안 포인트

| 출제 의도 | 반드시 짚을 핵심 | 감점 회피 포인트 |
|:---|:---|:---|
| 클라우드 서비스 모델 이해도 확인 | FaaS vs BaaS, 추상화 계층 | 단순히 "서버가 없는 것"으로 오해 |
| 기술적 특징 및 제약 사항 파악 | 이벤트 기반, Cold Start, Stateless | 장점만 나열하고 한계점(지연 시간 등) 누락 |
| 경제성 및 운영 효율성 분석 | Pay-as-you-go 과금, 관리 오버헤드 제거 | 비용이 항상 저렴하다고 단정(고부하 시 역전 가능) |

> 요약: 서버리스의 구성 요소인 FaaS와 BaaS, 그리고 작동 메커니즘인 이벤트 기반 트리거와 자동 확장을 기술한다.

## Ⅰ. 개요 및 필요성

- 정의: 서버 인프라의 가상화와 관리를 클라우드 사업자가 전담하고, 사용자는 코드 실행과 이벤트 처리에만 집중하는 컴퓨팅 모델
- 배경: 인프라 관리 비용(TCO) 절감 및 개발 속도(Agility) 향상을 위한 추상화된 컴퓨팅 환경 수요 증대
- 필요성: 불규칙한 트래픽 패턴 대응을 위한 자동 확장(Auto-scaling) 및 비사용 시 유휴 비용 0원 실현

---

## Ⅱ. 구조 및 구성요소

```text
[서버리스 컴퓨팅 구성도]
Event Source (S3, DB, API Gateway) -> [Trigger] -> [FaaS (Logic)] <-> [BaaS (Service)]
    (이미지 업로드, HTTP 요청 등)          |      (Lambda, Functions)      (Auth, DB, Log)
                                     [Ephemeral Container]
```

| 구성요소 | 역할 | 특이사항 |
|:---|:---|:---|
| FaaS (Function as a Service) | 애플리케이션 로직(함수) 실행 환경 | 무상태성(Stateless), 짧은 수명 |
| BaaS (Backend as a Service) | 인증, 데이터베이스, 스토리지 등 부가 기능 | API/SDK 기반 호출, 관리형 서비스 |
| Event Trigger | 함수를 실행시키는 특정 사건 | 스케줄러, HTTP 요청, 파일 생성 등 |
| API Gateway | 외부 요청과 서버리스 함수를 연결하는 관문 | 라우팅, 인증, 속도 제한(Throttling) |

> 요약: 이벤트가 발생하면 함수(FaaS)가 실행되고, 필요한 백엔드 기능은 관리형 서비스(BaaS)를 빌려 쓰는 구조다.

---

## Ⅲ. 동작원리 및 흐름도

```text
[서버리스 실행 라이프사이클]
Event Detect -> Instance Provisioning (Cold Start) -> Code Execution -> Result Return -> Instance Destruction
```

| 단계 | 처리 내용 | 검증 기준 |
|:---:|:---|:---|
| 1 | 구성된 이벤트 소스에서 특정 사건 발생 감지 | 트리거 설정 및 권한 확인 |
| 2 | 실행 환경(Container/MicroVM) 즉시 생성 | Cold Start 시간 (보통 수백 ms ~ 초 단위) |
| 3 | 업로드된 소스 코드 로드 및 핸들러 함수 실행 | 실행 시간(Timeout) 및 메모리 제한 |
| 4 | 연산 완료 후 결과 반환 및 실행 환경 회수 | 유휴 자원 즉시 반납 및 사용량 집계 |

> 요약: 요청이 올 때만 즉각적으로 전용 실행 환경을 만들고(Cold Start), 일이 끝나면 바로 부수는 방식으로 동작한다.

## Ⅳ. 특징

| 구분 | 내용 | 판단 포인트 |
|:---|:---|:---|
| 관리 오버헤드 | NoOps (서버 패치, 업데이트 없음) | 개발 집중도 및 운영 인력 효율 |
| 확장성 | 요청 수에 비례한 자동적 무한 확장 | 동시성 제한(Concurrency Limit) 점검 |
| 비용 모델 | Pay-as-you-go (1ms 단위 과금 가능) | 월간 호출 횟수 및 평균 실행 시간 |
| 상태 관리 | 무상태성 (Stateless) | 외부 저장소(Redis, DB) 연동 필수 |

> 요약: 인프라 관리 부담을 없애고 확장성을 얻는 대신, 무상태성과 초기 지연이라는 제약이 따른다.

## Ⅴ. 심화 비교 및 적용 판단

| 구분 | 서버 기반 (IaaS/PaaS) | 서버리스 (FaaS) | 선택 기준 |
|:---|:---|:---|:---|
| 제어권 | 높음 (OS, 네트워크 설정 가능) | 낮음 (런타임만 선택 가능) | 커스텀 환경 필요성 |
| 비용 구조 | 고정 비용 + 사용료 | 순수 사용량 기반 | 트래픽의 예측 가능성 및 불규칙성 |
| 실행 시간 | 제한 없음 (상시 가동) | 제한 있음 (보통 15분 이내) | 장기 실행(Long-running) 작업 여부 |

> 요약: 예측 가능하고 지속적인 부하는 서버 기반이, 불규칙하고 간헐적인 부하는 서버리스가 유리하다.

| 리스크 | 원인 | 대응 방안 | 확인 지표 |
|:---|:---|:---|:---|
| Cold Start | 초기 기동 시 런타임 준비 지연 | Provisioned Concurrency, 워밍업(Warm-up) | P99 Response Latency |
| Vendor Lock-in | 특정 클라우드사의 독자 API/기능 의존 | 오픈소스 서버리스(Knative) 활용 | 플랫폼 이전 시 코드 수정 범위 |
| 디버깅 어려움 | 로컬 환경과 클라우드 환경의 차이 | 서버리스 전용 모니터링/로깅 도구 도입 | 평균 장애 복구 시간 (MTTR) |

> 요약: 지연 시간은 워밍업 기법으로, 종속성은 표준 프레임워크 활용으로 리스크를 관리한다.

| 점검 항목 | 목표 기준 | 측정 방법 |
|:---|:---|:---|
| 성공 실행률 | 99.9% 이상 (에러율 0.1% 미만) | CloudWatch/Stackdriver 에러 로그 |
| 평균 응답 시간 | Cold Start 제외 시 100ms 이내 | API Gateway 지연 시간 메트릭 |
| 비용 절감 효과 | 기존 대비 30% 이상 (유휴 시간 고려) | 인프라 청구서 비교 분석 |

> 요약: 실행 안정성, 응답 속도, 비용 절감 수치를 통해 서버리스 도입의 실효성을 평가한다.

## Ⅵ. 실무 적용 및 결론

**적용 방안 3개:**
1. 이벤트 기반 데이터 처리: 이미지/영상 업로드 시 즉시 썸네일 생성, 트랜스코딩 등을 수행하는 비동기 파이프라인 구축
2. 챗봇 및 Webhook 처리: 불규칙하게 들어오는 외부 API 요청이나 메신저 알림을 최소 비용으로 안정적으로 수용
3. 클라우드 자동화 스케줄러: 정기적인 DB 백업, 리소스 정리, 보안 점검 스크립트를 서버 관리 없이 정기적으로 실행

**결론 (2줄):**
- 기술사 판단: 서버리스는 '경제적 유연성'과 '운영 단순성'의 결합이며, 단순 유행이 아닌 엔터프라이즈 아키텍처의 필수 구성 요소로 정착 중이다
- 향후 방향: GPU 서버리스, WebAssembly(Wasm) 기반의 초고속 서버리스 등 지연 시간을 획기적으로 줄인 기술로 진화할 것이다
