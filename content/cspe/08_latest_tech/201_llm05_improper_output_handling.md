# 📖 【암기용】 개념 완전 이해

> 목적: LLM05 Improper Output Handling을 처음 봐도 완벽히 이해하게 만든다.

## 한눈에
- **개요**: LLM 출력을 검증 없이 후속 시스템에 전달해 XSS·SSRF·RCE가 발생하는 취약점
- **왜 필요한가**: LLM 응답은 사용자 입력과 동일하게 신뢰할 수 없는 데이터이므로, 브라우저·DB·API에 그대로 전달하면 코드 실행 경로가 열린다.
- **핵심 직관**: LLM을 "신뢰할 수 없는 외부 입력원"으로 간주하고, 출력도 반드시 이스케이프·검증해야 한다.

## 깊이 이해
- **배경·문제의식**: 기존 웹 보안은 사용자 입력만 검증했지만, LLM 출력이 HTML·SQL·Shell에 삽입되면서 새로운 주입 경로가 생김.
- **작동 원리**: 공격자가 프롬프트에 악성 페이로드를 삽입 -> LLM이 그대로 출력 -> 후속 시스템이 코드로 해석 -> XSS·SSRF·RCE 실행.
- **비유**: 통역사(LLM)가 외국인의 말을 그대로 전달하는데, 말 속에 "금고를 열어라"가 숨어 있으면 수행자가 실행해버리는 구조.
- **구체 예시**: LLM 챗봇이 `<script>document.cookie</script>`를 응답에 포함 -> 브라우저가 실행 -> 세션 쿠키 탈취.
- **흔한 오해·주의점**: "LLM이 생성한 것이니 안전하다"는 틀림. 프롬프트 인젝션과 결합하면 임의 페이로드 생성 가능.

## 연결 개념
- LLM01 Prompt Injection — 입력 측 공격이 출력 측 취약점으로 연결
- XSS/SSRF — 전통 웹 취약점이 LLM 출력 경로로 재현
- Output Encoding — OWASP 권장 대응 기법

# 📝 【답안용】 시험 답안 템플릿

> 목적: 시험장에서 25분에 그대로 쓰는 답안 양식.

## 핵심 인사이트 (3줄 요약)

> 1. **본질**: LLM 출력을 신뢰 데이터로 취급해 후속 시스템에 무검증 전달 시 XSS·SSRF·RCE가 발생하는 OWASP LLM Top 10 취약점.
> 2. **가치**: LLM 출력 경로를 기존 웹 입력 검증과 동일 수준으로 통제해야 공격 표면 확장을 차단함.
> 3. **판단 포인트**: 출력 인코딩·CSP 헤더·샌드박스 실행 여부를 체크해야 함.

---

## Ⅰ. 개요 및 필요성

LLM 출력 무검증 전달로 발생하는 주입 취약점. LLM 응답이 HTML·SQL·Shell에 삽입되면서 기존 입력 검증만으로는 새로운 주입 경로를 차단할 수 없어 출력 측 검증이 필수.

---

## Ⅱ. 구조 및 구성요소

```text
사용자 입력 -> LLM 추론 -> [출력 검증 누락] -> 후속 시스템
                          브라우저(XSS)    API(SSRF)    Shell(RCE)
```

| 구성요소 | 역할 | 취약 지점 |
|:---|:---|:---|
| LLM 출력 | 자연어+코드 혼합 응답 생성 | 악성 페이로드 포함 가능 |
| 출력 파서 | 응답을 구조화·렌더링 | 이스케이프 누락 시 코드 실행 |
| 후속 시스템 | 브라우저·DB·API·Shell | 신뢰 경계 없이 실행 |

> 요약: LLM 출력이 후속 시스템에 무검증 전달되면 브라우저·API·Shell 각각에서 주입 공격이 발생함.

---

## Ⅲ. 동작원리 및 흐름도

```text
악성 프롬프트 -> LLM 응답(페이로드 포함) -> 출력 검증 부재
-> 후속 시스템 실행 -> XSS/SSRF/RCE 발현
```

| 단계 | 처리 내용 | 검증 기준 |
|:---:|:---|:---|
| 1 | 공격자가 프롬프트에 페이로드 삽입 | 입력 필터링·프롬프트 분리 |
| 2 | LLM이 페이로드를 포함한 응답 생성 | 출력 토큰 패턴 탐지 |
| 3 | 후속 시스템이 출력을 코드로 해석 | Output Encoding(HTML Entity·SQL Param) |
| 4 | XSS·SSRF·RCE 실행, 데이터 유출 | CSP 헤더, 샌드박스, WAF 차단 |

> 요약: 프롬프트 인젝션이 출력 경로를 타고 후속 시스템에서 코드로 실행되는 공격 체인임.

---

## Ⅳ. 특징

| 구분 | 기존 XSS/주입 | LLM05 출력 주입 | 수치·판단 포인트 |
|:---|:---|:---|:---|
| 입력원 | 사용자 폼·URL | LLM 생성 응답 | 출력도 Untrusted Input 간주 |
| 탐지 | WAF 시그니처 | LLM 출력 패턴 분석 필요 | 정규식+ML 하이브리드 탐지율 92%증가 |
| 대응 | 입력 검증 단일 | 입력+출력 이중 검증 | CSP strict-dynamic, sandbox 적용 |

> 요약: LLM 출력은 기존 입력 검증 범위 밖이므로 출력 인코딩·CSP·샌드박스를 추가 적용해야 함.

---

## Ⅴ. 실무 적용 및 결론

**적용 방안 3개:**
1. LLM 응답을 HTML 렌더링 전 Output Encoding(HTML Entity) 적용, CSP `script-src 'strict-dynamic'` 설정
2. DB·API 전달 시 Parameterized Query·allowlist URL 필터 적용, SSRF 차단율 99%증가 목표
3. Shell 실행 경로에 컨테이너 샌드박스(gVisor) + seccomp 프로파일 적용, RCE 격리

**결론 (2줄):**
- 기술사 판단: LLM 출력은 사용자 입력과 동등한 Untrusted Source로 분류하고 출력 인코딩을 필수 적용
- 향후 방향: OWASP LLM Top 10 v2.0 기반 출력 검증 자동화 파이프라인이 CI/CD에 통합되는 방향
