# 📖 【암기용】 개념 완전 이해

> 목적: Semantic Chunking을 처음 봐도 완벽히 이해하게 만든다.

## 한눈에
- **개요**: 토큰 수가 아니라 의미 경계와 주제 전환점을 기준으로 문서를 분할하는 청킹 기법
- **왜 필요한가**: 고정 길이 분할은 문장·조항·표를 중간에서 자를 수 있어 검색 근거의 의미가 깨짐.
- **핵심 직관**: 일정한 자로 자르는 것이 아니라, 문단의 주제가 바뀌는 지점에서 끊는 방식임.

## 깊이 이해
- **배경·문제의식**: RAG 검색은 청크 하나가 독립 근거로 쓰인다. 의미가 끊긴 청크는 검색에는 잡혀도 답변 근거로 부적합하다.
- **작동 원리**: 문장 단위 임베딩을 계산하고 인접 문장 간 cosine distance가 임계값을 넘는 지점을 경계로 삼거나, 제목·조항·표 구조를 함께 반영함.
- **비유**: 책을 2쪽마다 기계적으로 자르지 않고, 한 절이나 한 주제가 끝나는 곳에서 책갈피를 꽂는 방식임.
- **구체 예시**: 고정 512토큰 분할 대비 Semantic Chunking 적용 시 근거 문장 완전성 78%->92%, 평균 청크 길이는 430~700토큰으로 가변.
- **흔한 오해·주의점**: 의미 청킹은 전처리 비용이 더 든다. 문서 100만 건 이상이면 배치 임베딩 비용과 재색인 시간을 고려해야 함.

## 연결 개념
- Chunking — 고정 길이·문단 기준 기본 분할
- Embedding — 문장 간 의미 변화 감지에 사용
- Parent-Child Chunking — 작은 청크 검색 후 큰 문맥을 제공하는 계층형 방식

> 1. **본질**: Semantic Chunking은 의미 경계와 문서 구조를 기준으로 가변 길이 청크를 생성함.
> 2. **가치**: 근거 문장 완전성 78%->92%로 개선해 RAG 답변의 출처 품질을 높임.

## Ⅰ. 개요 및 필요성

- 정의: 의미 경계 기반 가변 길이 문서 분할 기법
- 배경: 고정 토큰 분할은 문장·조항을 중간에서 잘라 근거 의미를 훼손함
- 필요성: RAG 답변의 출처 완전성 확보를 위해 의미 변화점과 문서 구조 기준 분할이 필요함

## Ⅱ. 구조 및 구성요소

```text
Document -> Sentence Split -> Sentence Embedding
  -> Boundary Detection -> Variable Chunk -> Metadata/Index
```

| 구성요소 | 역할 | 특이사항 |
|:---|:---|:---|
| Sentence Splitter | 문장·조항 단위 분리 | 한국어 종결어미·조항 번호 처리 |
| Sentence Embedding | 문장 의미 벡터 생성 | cosine distance 계산 |
| Boundary Detector | 주제 전환점 탐지 | distance threshold 0.25~0.4 |
| Chunk Assembler | 최소·최대 길이 제약 적용 | 256~1,024토큰 범위 |

> 요약: Semantic Chunking은 문장 임베딩 간 의미 변화와 문서 구조를 결합해 완결된 가변 청크를 생성함.

## Ⅲ. 동작원리 및 흐름도

```text
문서 입력 -> 문장 분리 -> 문장별 임베딩
  -> 인접 문장 거리 계산 -> 경계 후보 선정
  -> 길이 제약 보정 -> 청크 생성
```

| 단계 | 처리 내용 | 검증 기준 |
|:---:|:---|:---|
| 1 | 문장·조항 단위로 문서 분해 | 문장 절단 오류 <3% |
| 2 | 문장 임베딩 및 인접 거리 계산 | 배치 처리 5천 문장/분 |
| 3 | 의미 거리 임계값으로 경계 탐지 | 근거 완전성 ≥90% |
| 4 | 최소·최대 토큰 제약으로 청크 보정 | 평균 청크 430~700토큰 |

> 요약: 문장 간 의미 거리로 주제 전환점을 찾고 길이 제약을 적용해 검색에 적합한 청크를 생성함.

## Ⅳ. 특징

| 구분 | Fixed Chunking | Semantic Chunking | 판단 포인트 |
|:---|:---|:---|:---|
| 분할 기준 | 토큰 수 | 의미 경계·문서 구조 | 규정·보고서에 적합 |
| 청크 길이 | 고정 256~512 | 가변 256~1,024 | Top-K 입력 비용 관리 |
| 품질 | 문맥 절단 가능 | 근거 완전성 90% 이상 | 출처 신뢰도 필요 시 선택 |
| 비용 | 전처리 낮음 | 문장 임베딩 비용 추가 | 대량 문서 재색인 비용 검토 |

> 요약: Semantic Chunking은 근거 완전성을 높이지만, 전처리 비용과 가변 길이 컨텍스트 관리를 함께 고려해야 함.

## Ⅴ. 심화 비교 및 적용 판단

| 비교 축 | Fixed Chunking | Semantic Chunking | 선택 기준 |
|:---|:---|:---|:---|
| 분할 정밀도 | 토큰 수 고정, 문장 절단 발생 | 의미 경계 기반, 근거 완전성 92% | 규정·보고서 등 구조화 문서 여부 |
| 전처리 비용 | 단순 분할, GPU 불필요 | 문장 임베딩 계산, GPU 배치 필요 | 문서 100만 건 이상 시 비용 대비 효과 산정 |
| 운영 복잡도 | 고정 파라미터(512토큰) | 임계값·최소/최대 길이 튜닝 필요 | 재색인 주기와 파이프라인 관리 역량 |

> 요약: 구조화 문서이고 근거 품질이 중요하면 Semantic Chunking, 단순 FAQ·대량 문서는 Fixed Chunking 적용

| 리스크 | 원인 | 대응 방안 | 확인 지표 |
|:---|:---|:---|:---|
| 경계 오탐 | 임계값 부적절, 도메인 불일치 | 도메인별 threshold 0.25~0.4 튜닝, 검증셋 평가 | 근거 완전성 ≥90% |
| 전처리 지연 | 대량 문서 임베딩 배치 부하 | GPU 병렬 배치, 증분 인덱싱 적용 | 100만 문서 처리 시간 ≤4시간 |
| 청크 길이 편차 | 주제 전환 빈도 차이 | min 256·max 1,024토큰 제약 적용 | 청크 길이 표준편차 ≤200토큰 |

> 요약: 임계값 튜닝과 길이 제약으로 경계 오탐과 길이 편차를 통제함

| 점검 항목 | 목표 기준 | 측정 방법 |
|:---|:---|:---|
| 근거 완전성 | 문장 절단율 ≤3%, 완전성 ≥90% | 검증셋 대비 자동 평가 |
| 검색 품질 | Recall@10 ≥85%, faithfulness ≥80% | RAG 평가 파이프라인 |
| 전처리 비용 | 100만 문서 재색인 ≤4시간 | GPU 배치 처리 로그 |

> 요약: 근거 완전성·검색 품질·전처리 비용 3개 축으로 도입 효과를 정량 판단함

## Ⅵ. 실무 적용 및 결론

**적용 방안 3개:**
1. 규정 RAG: 조항 번호와 제목을 hard boundary로 두고, 본문은 문장 임베딩 거리 0.3 이상에서 분할
2. 기술문서 RAG: 코드 블록·표는 단일 청크로 보존, 1,024토큰 초과 시 parent-child chunking 적용
3. 운영 검증: fixed 512 vs semantic 가변 청크의 Recall@10·faithfulness·평균 입력 토큰을 주 단위 비교

**결론 (2줄):**
- 기술사 판단: 구조화 문서·규정·보고서는 Semantic Chunking, 단순 FAQ는 Fixed Chunking 적용
- 향후 방향: LLM 기반 document parser와 계층형 청킹을 결합해 표·그림·코드 문맥을 보존하는 방향으로 발전
