# 📖 【암기용】 개념 완전 이해

## 한눈에
- **정의**: 글로벌 보안 가이드라인의 바이블인 OWASP(웹 애플리케이션 보안 프로젝트)에서 발표한, **거대 언어 모델(LLM)을 활용한 애플리케이션을 개발하고 배포할 때 반드시 막아야 하는 10가지 최우선 보안 취약점 리스트**.
- **필요성**: 기존의 웹 보안(SQL 인젝션, XSS 등) 기준만으로는 "명령어와 데이터가 구분되지 않는" 생성형 AI 특유의 취약점(환각, 프롬프트 해킹, RAG 오염 등)을 방어할 수 없음. 기업이 안전하게 AI 챗봇이나 에이전트를 도입하기 위한 필수 체크리스트가 필요함.
- **핵심 직관**: AI 서비스의 십계명. 웹사이트 만들 때 "비밀번호는 암호화해라, 입력창에 특수문자 막아라(OWASP Web Top 10)"가 법칙인 것처럼, AI 챗봇을 만들 때 "사용자의 프롬프트(명령어)를 너무 믿지 마라, AI가 외부 데이터 읽을 때 감시해라"라는 10가지의 새로운 법칙을 세운 것.

## 깊이 이해
- **배경**: ChatGPT의 등장 이후 기업들이 앞다투어 사내 AI 시스템을 도입했으나, 삼성전자의 소스코드 유출 사건 등 보안 사고가 속출함. 이에 2023년 OWASP 산하의 AI 전문가 그룹이 초안을 발표하고, 전 세계 피드백을 수렴하여 LLM 시대의 글로벌 보안 표준으로 정립함.
- **Top 10의 구성 철학**:
  - LLM 모델 자체의 결함보다는, **"LLM을 가져다 쓰는 애플리케이션(플러그인, API, RAG) 파이프라인의 취약성"**에 집중함.
  - 입력(프롬프트) $\rightarrow$ 처리(모델, 외부 API) $\rightarrow$ 출력(결과물)의 전체 생애주기(Lifecycle)에서 발생하는 위협을 망라함.
- **가장 중요한 상위 취약점**:
  - **LLM01 (프롬프트 인젝션)**: 시스템 지시를 무시하고 해커의 명령을 따르게 함.
  - **LLM02 (민감 정보 노출)**: AI가 응답 중에 개인정보나 사내 기밀을 뱉어냄.
  - **LLM03 (공급망 취약점)**: 오염된 오픈소스 모델이나 플러그인을 가져다 써서 시스템이 감염됨.
- **흔한 오해/주의점**: "이 10개만 막으면 완벽한가?" $\rightarrow$ 아님. OWASP Web Top 10이 웹 보안의 전부가 아니듯, LLM Top 10도 가장 빈번하고 치명적인 공격을 모아둔 '최소한의 가이드라인'일 뿐임. 기존 클라우드 보안과 결합해야 함.

## 연결 개념
- **OWASP Web Top 10**: 웹 애플리케이션 보안의 표준. LLM 시스템 역시 웹 인터페이스를 가지므로 두 가이드라인을 교차(Mapping)하여 적용해야 함.
- **AI RMF (AI Risk Management Framework)**: 미국 NIST가 발표한 거시적인 AI 위험 관리 프레임워크. OWASP LLM Top 10은 이 중 보안/기술 영역을 실무적으로 구체화한 지침.
- **AI Red Teaming (AI 레드티밍)**: 이 Top 10 리스트에 있는 기법들을 동원하여 자사 AI 서비스를 실제로 모의 해킹(스트레스 테스트)해보는 검증 활동.

# 📝 【답안용】 시험 답안 템플릿
## 핵심 인사이트 (3줄 요약)
- **본질**: 거대 언어 모델(LLM) 기반의 애플리케이션, 플러그인, 에이전트(Agents)를 설계하고 배포하는 과정에서 발생하는 가장 위협적이고 빈번한 10대 보안 취약점 및 대응 가이드라인(Defacto Standard).
- **가치**: 기존 결정론적(Deterministic) 소프트웨어 취약점(CWE) 체계로는 포섭할 수 없는 비결정론적(Probabilistic) 언어 모델 특유의 취약성(프롬프트 주입, 환각, RAG 데이터 오염)에 대한 구체적인 방어 아키텍처 수립의 기준을 제공함.
- **판단 포인트**: 기업은 LLM 애플리케이션 도입 시 OWASP LLM Top 10을 보안성 검토(Security Review) 체크리스트로 의무화하고, MLOps 파이프라인 전 구간에 걸친 다층 방어(Defense in Depth) 및 제로 트러스트(Zero Trust) 체계를 적용해야 함.

## Ⅰ. 개요 및 필요성
- **정의**: 비영리 보안 단체 OWASP에서 발표한 LLM 도입 환경에서의 상위 10가지 보안 위협 목록으로, 프롬프트, 데이터, 모델, 애플리케이션 계층(Layer)의 취약점을 종합한 프레임워크.
- **배경**: LLM이 단순 챗봇을 넘어 서드파티 API, 데이터베이스, 검색 엔진과 결합된 자율형 에이전트(Autonomous Agent)로 진화하면서, AI의 오작동이 실제 물리적/데이터적 침해 사고로 직결됨.
- **필요성**: AI 개발자, 데이터 과학자, 보안 엔지니어 간의 공통된 위협 인식(Shared Vocabulary)을 마련하고, 컴플라이언스 준수 및 안전한 LLM 서비스 런칭을 위한 최소한의 보안 통제 기준 제시.

## Ⅱ. OWASP LLM Top 10 핵심 항목 요약 (V1.1 기준)
가장 빈번하고 치명적인 취약점 1~5위.
| 식별자 | 취약점 명칭 (Kor) | 취약점 개념 (Mechanism) | 대응 방안 (Mitigation) |
|:---:|:---|:---|:---|
| **LLM01** | **프롬프트 인젝션**<br>(Prompt Injection) | 악의적 입력으로 모델의 시스템 프롬프트를 오버라이딩하여 의도치 않은 동작 유발. (직접/간접 주입) | 입력-명령어 구조적 분리, 권한 최소화, 사람 승인(HITL) 도입. |
| **LLM02** | **안전하지 않은 출력 처리**<br>(Insecure Output Handling) | 플러그인이나 백엔드가 LLM의 출력값을 검증 없이(XSS, RCE 등) 그대로 실행해버리는 취약점. | 출력 결과물에 대한 엄격한 인코딩/이스케이프(Escape), 제로 트러스트 적용. |
| **LLM03** | **훈련 데이터 오염**<br>(Training Data Poisoning) | 학습/미세조정 단계에서 악성 데이터나 편향된 데이터를 주입해 모델 성능과 윤리를 파괴함. | 데이터 출처 무결성 검증, 통계적 이상치(Outlier) 필터링 적용. |
| **LLM04** | **모델 서비스 거부**<br>(Model DoS) | LLM의 과도한 리소스를 소모시키는 쿼리(컨텍스트 최대화 등)를 날려 서버를 다운시키거나 요금 폭탄 유발. | 사용자/IP 단위 엄격한 토큰(Token) 사용량 쓰로틀링(Throttling) 및 제한. |
| **LLM05** | **공급망 취약점**<br>(Supply Chain Vulnerabilities)| 오염된 외부 오픈소스 모델, 라이브러리, 크라우드소싱 데이터를 무분별하게 결합하여 전체 시스템 감염. | AI-SBOM 구축, 외부 모델 MLOps 내 자체 검증 격리 환경 운영. |

## Ⅲ. OWASP LLM Top 10 핵심 항목 요약 (6~10위)
아키텍처 및 데이터 보호 관점의 취약점.
| 식별자 | 취약점 명칭 (Kor) | 취약점 개념 (Mechanism) | 대응 방안 (Mitigation) |
|:---:|:---|:---|:---|
| **LLM06** | **민감 정보 노출**<br>(Sensitive Info Disclosure) | 사용자 질의에 모델이 암기하고 있던 민감 정보(PII, 영업비밀)나 내부 구조를 뱉어내는 사고. | 학습 전 PII 데이터 정제(Sanitization), RAG 검색 접근 제어 강제. |
| **LLM07** | **안전하지 않은 플러그인 설계** | 모델과 연결된 외부 플러그인(API)이 입력값을 검증하지 않거나 과도한 권한을 가지는 경우. | 플러그인 권한의 최소화(Least Privilege), 명시적 API 계약 검증. |
| **LLM08** | **과도한 권한 위임**<br>(Excessive Agency) | LLM 에이전트에게 너무 많은 자율권(권한, 판단력)을 주어 오작동 시 재앙적 피해 발생. | 고위험 작업(송금, 삭제 등)은 반드시 인간(HITL)이 개입/승인. |
| **LLM09** | **과도한 의존성**<br>(Overreliance) | 사용자가 AI의 환각(Hallucination)이나 오류를 비판 없이 맹신하여 치명적 의사결정을 내리는 위험. | "AI의 답변은 부정확할 수 있음" 명시, 교차 검증 도구 및 출처 제공. |
| **LLM10** | **모델 탈취**<br>(Model Theft) | API 질의 반복(Model Extraction)이나 섀도우 IT를 통해 회사의 핵심 AI 모델 아키텍처/가중치를 복제당함. | API 쿼리 이상 탐지, MLOps 접근 제어, 모델 가중치에 워터마크 삽입. |
*(※ 참고: OWASP 버전 업데이트에 따라 항목 순서나 명칭이 미세하게 병합/조정될 수 있으나 핵심 위협 벡터는 동일함)*

## Ⅳ. 기존 웹 취약점과 LLM 취약점의 보안 패러다임 비교
| 구분 | 기존 웹(Web) 보안 (OWASP Top 10) | LLM 애플리케이션 보안 |
|:---:|:---|:---|
| **입력 (Input)** | 정형화된 파라미터 제어 (SQL, XSS) | **비정형/무한한 자연어 컨텍스트 (프롬프트)** |
| **실행 (Execution)** | 코드 기반의 결정론적 분기 처리 | **확률 기반의 비결정론적(Probabilistic) 생성** |
| **보안 경계** | 프론트엔드 $\leftrightarrow$ 백엔드 $\leftrightarrow$ DB | **사용자 $\leftrightarrow$ LLM $\leftrightarrow$ 플러그인/에이전트 (경계 모호)** |
| **대응 철학** | 방화벽(WAF), 필터링, 패치(Patch) | **다층 가드레일, 정렬(Alignment), 권한 격리** |

## Ⅴ. 실무 적용 및 결론
- **판단 지표**: 사내 AI 서비스 기획 시 OWASP LLM Top 10 항목별 Threat Modeling 수행 여부, 프롬프트 인젝션 방어율, 외부 모델/라이브러리에 대한 AI-SBOM 보유율.
- **실무 설계**: 금융사의 임직원용 '사내 업무 규정 RAG 챗봇' 도입 프로젝트. OWASP 가이드 기반 보안 검토 수행. **[LLM02 민감정보 노출 방어]**: 인사 등급에 따른 RAG 벡터 DB 접근 제어(RBAC) 구현 및 출력단 DLP 필터링 적용. **[LLM06 안전하지 않은 플러그인 방어]**: 챗봇이 사내 시스템 API를 호출할 때 Read-Only 권한만 부여하고 Write 권한 완전 박탈. **[LLM01 프롬프트 인젝션 방어]**: NeMo Guardrails를 도입하여 악의적 지시어 우회 차단. 종합 보안성 검토 통과 후 안전하게 사내 서비스 런칭.
- **결론**: OWASP LLM Top 10은 AI가 "신기한 장난감"에서 "엔터프라이즈의 핵심 인프라"로 넘어가는 관문에서 반드시 숙지해야 할 생존 교본이다. 기업은 완벽한 보안 모델이 존재하지 않음을 인정하고, LLM의 오작동과 해킹을 기본값(Assume Breach)으로 상정한 채 피해 반경(Blast Radius)을 최소화하는 제로 트러스트(Zero Trust) 아키텍처로 AI 서비스를 설계해야 한다.

### 🔀 문제 유형별 목차 전환
- **Ⅱ·Ⅲ 강조 (개념/원리형)**: LLM01(프롬프트 인젝션)과 LLM08(과도한 권한 위임)이 결합될 때 발생하는 '자율 에이전트 탈취(Agentic Hijacking)'의 체인 리스크 매커니즘 구조화.
- **Ⅴ·Ⅵ 강조 (실무/설계형)**: 데브섹옵스(DevSecOps) 파이프라인 내에 OWASP LLM Top 10 취약점을 스캐닝하는 자동화 도구(예: Garak, LLM-as-a-Judge)를 CI/CD 단계별로 어떻게 통합하고 모니터링할 것인지에 대한 MLOps 보안 아키텍처.
