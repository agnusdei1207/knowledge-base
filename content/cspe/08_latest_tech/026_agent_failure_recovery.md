# 📖 【암기용】 개념 완전 이해

## 한눈에
- **개요**: 에이전트 실패복구는 다단계 작업 중 **도구 호출·LLM 추론 실패** 시 **체크포인트 기반으로 마지막 성공 지점부터 재개**하는 회복력(Resilience) 메커니즘이다. 에이전트 상태관리(019)가 "진행 상태를 어디에 기록하는가"를 다룬다면, 실패복구는 "그 기록을 어떻게 활용해 복구하는가"의 전략을 다룬다.
- **왜 필요한가**: 에이전트가 5단계 API 호출 체인의 3단계에서 타임아웃되면, 1~2단계를 다시 실행하면 중복 비용(토큰+API 과금)과 부작용(중복 결제·중복 주문)이 발생한다. 체크포인트+멱등키+보상 트랜잭션 없이는 작업 완료율 99.5% 확보가 불가능하다.
- **핵심 직관**: 게임 세이브 포인트와 같다. 보스전에서 지면 세이브 지점(체크포인트)에서 재시작하지, 게임 처음부터 다시 하지 않는다. 단, 보스에게 지기 전에 사용한 아이템(부작용)은 보상 처리로 되돌려야 한다.

## 핵심 용어 정리 (내부에 등장하는 것들)

| 용어/표기 | 의미 | 비유·예 |
|:---|:---|:---|
| 회복력(Resilience, 상위 키워드) | 장애 발생 시 서비스를 정상 상태로 복원하는 능력 | 스프링이 눌렸다가 되돌아오는 탄성 |
| 체크포인트(Checkpoint) | 각 단계 완료 시 입력·출력·상태를 저장한 복구 지점 | 게임 세이브 포인트 |
| 지수 백오프(Exponential Backoff) | 재시도 간격을 1s→2s→4s로 배수 증가시키는 전략 | 전화 안 받으면 2분 후, 5분 후, 10분 후 재시도 |
| 멱등키(Idempotency Key) | 같은 요청을 여러 번 보내도 1회와 동일 결과를 보장하는 고유 ID | 택배 송장번호 — 같은 번호로 두 번 접수해도 1건 |
| Saga 패턴 | 분산 트랜잭션을 단계별 로컬 트랜잭션+보상 액션으로 분리 | 호텔·항공 각각 예약, 항공 실패 시 호텔만 취소 |
| 보상 트랜잭션(Compensation) | 이미 완료된 단계의 변경을 역방향으로 되돌리는 액션 | 결제 취소, 배포 롤백 |
| 일시적 오류(Transient) | 네트워크 타임아웃·5xx 등 재시도하면 해소될 수 있는 오류 | 전화 잠깐 끊김 — 다시 걸면 연결 |
| 영구적 오류(Permanent) | 인증 실패·404·4xx 등 재시도해도 해소 불가한 오류 | 번호 자체가 없음 — 다시 걸어도 안 됨 |
| DLQ(Dead Letter Queue) | 처리 불가 메시지를 별도 적재해 수동 검토하는 큐 | 반송 우편함 |
| Circuit Breaker | 연속 실패 시 호출을 일시 차단해 장애 전파를 방지 | 과부하 시 차단기 작동 |

## 깊이 이해
- **배경·문제의식**: 에이전트 워크플로우(024)가 "어떤 절차로 실행하는가"를 정의하지만, 실제 운영에서는 외부 API 5xx, LLM 타임아웃, DB 연결 실패 등 부분 장애가 불가피하다. 상태관리(019)가 "어디까지 했는가"를 기록하고, 실패복구는 그 기록을 활용해 "어디서부터 어떻게 이어갈 것인가"를 결정한다.
- **작동 원리(어떻게+왜)**: ① Failure Detector가 실패를 감지하고 일시적(5xx·타임아웃) vs 영구적(4xx·인증 실패)으로 분류한다. ② 일시적 오류는 지수 백오프(1s→2s→4s)로 최대 3회 재시도한다. 멱등키를 포함해 재시도 시 중복 실행을 방지한다. ③ 재시도 3회 실패 또는 영구적 오류는 Saga 보상 트랜잭션을 실행해 이미 완료된 단계의 변경을 롤백한다. ④ 보상 실패 시 DLQ에 적재하고 Human Escalation(PagerDuty 알림 <30초)으로 전달한다. ⑤ Circuit Breaker가 연속 실패(5회/분)를 감지하면 해당 도구 호출을 일시 차단해 장애 전파를 방지한다.
- **비유**: 등산 중 폭우가 오면 가장 가까운 대피소(체크포인트)로 돌아가서, 날씨가 개면(일시적) 대피소에서 다시 출발한다. 산이 통째로 막히면(영구적) 우회 경로(보상)를 찾거나 구조대(에스컬레이션)를 부른다.
- **구체 예시**: 주문 처리 에이전트가 ① 재고 확인(성공)→② 결제 API 호출(5xx 타임아웃)에서 실패한다. 멱등키 `order-2026-0705-001`로 결제 API를 2초 후 재시도하면 성공한다. 만약 3회 모두 실패하면 ①의 재고 예약을 보상 트랜잭션으로 해제하고, Slack 알림으로 운영자에게 에스컬레이션한다.
- **흔한 오해·주의점**: "모든 실패를 재시도하면 된다"는 위험한 단순화다. 비멱등 API(결제·삭제)를 멱등키 없이 재시도하면 중복 결제·이중 삭제가 발생한다. 또한 영구적 오류(4xx)를 재시도하면 자원만 낭비하므로, 실패 유형 분류가 복구 전략의 첫 단계다.

## 연결 개념
- 에이전트 상태관리(019) — 체크포인트를 저장하는 인프라. 실패복구의 데이터 기반
- 에이전트 관측성(030) — 실패 감지·원인 분석의 모니터링 기반
- 에이전트 워크플로우(024) — 복구 대상이 되는 작업 절차

> 2. **가치**: 멱등키로 중복 실행을 방지하고, Saga 보상으로 부분 실패를 롤백해 완료율 99.5%를 확보함.
> 3. **판단 포인트**: 일시적 vs 영구적 오류 분류, 멱등키 적용, Saga 보상, Circuit Breaker, Human Escalation을 함께 설계해야 함.

## Ⅰ. 개요 및 필요성

- 개요: 다단계 에이전트 작업 중단을 체크포인트 기반으로 재개하는 회복력 메커니즘임
- 배경: 외부 API 5xx·LLM 타임아웃·DB 장애 등 부분 실패가 다단계 워크플로우에서 불가피함
- 필요성: 재시도·보상·에스컬레이션 전략 없이는 완료율 99.5% 확보와 중복 실행 방지가 불가능함

---

## Ⅱ. 구조 및 구성요소

```text
단계 실행 -> Checkpoint Store(상태 저장) -> Failure Detector(감지)
                                                |
                         일시적(5xx) ---------> Retry Engine(지수 백오프+멱등키)
                         영구적(4xx) ---------> Compensation(Saga 보상) -> Escalation
                                                |
                         연속 실패 -----------> Circuit Breaker(호출 차단)
```

| 구성요소 | 역할 | 특이사항 |
|:---|:---|:---|
| Checkpoint Store | 단계별 입력·출력·상태 저장 | Redis Cluster, TTL 24h |
| Failure Detector | 실패 감지·분류(일시적/영구적) | HTTP 코드, 타임아웃 기준 |
| Retry Engine | 지수 백오프 재시도(최대 3회) | 멱등키 기반 중복 방지 |
| Compensation | 비멱등 작업 보상 트랜잭션 | Saga 패턴, 실패 시 DLQ |

> 요약: 체크포인트 저장→실패 감지→오류 분류→재시도/보상→에스컬레이션의 복구 파이프라인임.

---

## Ⅲ. 동작원리 및 흐름도

```text
단계 실행 -> 성공? -> Yes -> 체크포인트 저장 -> 다음 단계
              No -> 오류 분류(일시적/영구적)
              -> 일시적 -> 지수 백오프 재시도(1s->2s->4s, 최대 3회)
              -> 영구적 or 재시도 실패 -> Saga 보상 -> Human Escalation
```

1. 실행·감지: 단계를 실행하고 응답 코드·타임아웃으로 성공/실패를 판정함
2. 오류 분류: 5xx·타임아웃은 일시적(재시도 가능), 4xx·인증 실패는 영구적(재시도 불가)으로 분류함
3. 재시도: 일시적 오류는 지수 백오프(1s→2s→4s)로 최대 3회 재시도하며, 멱등키를 포함해 중복 실행을 방지함
4. 보상·에스컬레이션: 재시도 실패 또는 영구적 오류 시 Saga 보상 트랜잭션으로 완료 단계를 롤백하고, 보상 실패 시 DLQ+Human Escalation으로 전달함

> 요약: 실패 감지→오류 분류→재시도/보상→에스컬레이션 순서로 부분 장애를 처리함.

---

## Ⅳ. 특징

- 부분 재개: 체크포인트에서 마지막 성공 지점부터 재개해 전체 재실행 비용을 제거함
- 오류 분류: 일시적 vs 영구적을 구분해 재시도 가능 여부를 자동 판정함
- 멱등 보장: 멱등키+결과 캐시로 재시도 시 중복 실행(중복 결제 등)을 차단함
- 비용 통제: 재시도 최대 3회+일일 토큰 한도로 무한 재시도에 의한 비용 폭주를 방지함
- 장애 전파 차단: Circuit Breaker로 연속 실패 시 해당 도구 호출을 일시 차단함

## Ⅴ. 심화 비교 및 적용 판단

| 구분 | 단순 재시도 | 에이전트 실패복구 | 선택 기준 |
|:---|:---|:---|:---|
| 상태 보존 | 없음(처음부터 재실행) | 체크포인트 기반 부분 재개 | 단계 3개 이상 시 체크포인트 필수 |
| 부작용 방지 | 미보장(중복 실행) | 멱등키+Saga 보상 | 결제·삭제 등 비멱등 API 포함 시 필수 |
| 비용 통제 | 무한 재시도 위험 | 최대 3회+일일 한도 | 일일 비용 $50 이상 워크플로우 |

> 요약: 3단계 이상 워크플로우에서 비멱등 API가 포함되면 체크포인트+보상 설계가 필수임.

**리스크·대응:**
- 체크포인트 유실: Redis 장애·TTL 만료 → Redis Cluster+TTL 24h+디스크 백업 (지표: 체크포인트 복구율 99.9%)
- 중복 실행: 멱등키 미적용 → 모든 외부 API에 UUID v4 멱등키 부여 (지표: 중복 실행률 0%)
- 무한 재시도: 영구 오류를 일시 오류로 오분류 → 4xx 즉시 보상, 5xx만 재시도(최대 3회) (지표: 평균 재시도 횟수 <1.5회)

**도입 후 점검 지표:**
- 작업 완료율: 99.5% 이상 — 완료/전체 워크플로우 비율
- 평균 복구 시간: MTTR <5분 — PagerDuty 알림→해결 시간

---

## Ⅵ. 실무 적용 및 결론

**적용 방안 3개:**
1. 각 도구 호출 전후 상태를 Redis Cluster 체크포인트에 저장하고 TTL 24h로 자동 만료를 설정함
2. 멱등키(UUID v4)를 모든 외부 API 호출에 부여하고, 지수 백오프(1s→2s→4s) 최대 3회 재시도를 적용함
3. 재시도 3회 실패 시 Saga 보상 트랜잭션을 실행하고, 보상 실패 시 DLQ 적재+PagerDuty 알림(MTTA <5분)으로 에스컬레이션함

**결론:**
- 기술사 판단: 멱등 API는 자동 재시도, 비멱등 작업은 Saga 보상+Human Escalation으로 설계함
- 향후 방향: LLM이 실패 원인을 자체 분류하고 대안 도구를 선택하는 자율 복구로 발전함
