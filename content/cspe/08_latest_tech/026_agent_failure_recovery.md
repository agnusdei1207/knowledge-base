# 📖 【암기용】 개념 완전 이해

> 목적: 에이전트 실패복구를 처음 봐도 완벽히 이해하게 만든다.

## 한눈에
- **개요**: AI 에이전트 실행 중 도구 호출·LLM 추론 실패 시 작업을 재개하는 메커니즘
- **왜 필요한가**: 에이전트는 다단계 작업을 수행하므로 중간 실패가 전체 워크플로우를 무효화할 수 있음
- **핵심 직관**: 게임 세이브포인트처럼 각 단계 상태를 저장하고, 실패 시 마지막 성공 지점부터 재시작함

## 깊이 이해
- **배경·문제의식**: 에이전트가 API 호출 5단계 중 3단계에서 타임아웃되면, 1~2단계를 다시 실행하면 중복 비용(토큰·API 과금)과 부작용(중복 주문) 발생
- **작동 원리**: ① 각 단계 결과를 체크포인트로 저장 ② 실패 감지(HTTP 5xx·타임아웃·LLM 거부) ③ 재시도 정책(지수 백오프, 최대 3회) ④ 복구 불가 시 Human Escalation
- **비유**: 등산 중 폭우가 오면 가장 가까운 대피소(체크포인트)로 돌아가 날씨가 개면 거기서 다시 출발하는 것
- **구체 예시**: 주문 처리 에이전트가 결제 API 타임아웃 시, 멱등키(Idempotency Key)로 중복 결제를 방지하며 최대 3회 재시도 후 실패 시 Slack 알림
- **흔한 오해·주의점**: 단순 재시도만으로는 부족함. 비멱등 API는 재시도 시 부작용이 발생하므로 멱등성 보장이 선행돼야 함

## 연결 개념
- 에이전트 관측성(Observability) — 실패 감지·원인 분석의 기반
- 에이전트 가드레일(Guardrail) — 재시도 한도·비용 제한 정책
- Saga 패턴 — 분산 트랜잭션 보상 처리와 유사한 구조


# 📝 【답안용】 시험 답안 템플릿

> 목적: 시험장에서 25분에 그대로 쓰는 답안 양식.

## 핵심 인사이트 (3줄 요약)

> 1. **본질**: 에이전트 실패복구는 다단계 작업의 중간 실패를 체크포인트 기반으로 재개하는 회복력 메커니즘임.
> 2. **가치**: 중복 실행 방지(멱등키)와 비용 통제(재시도 한도)를 결합해 작업 완료율 99.5% 이상 확보.
> 3. **판단 포인트**: 멱등 API는 자동 재시도, 비멱등 작업은 보상 트랜잭션 또는 Human Escalation으로 분기 설계.

## 출제 의도 및 답안 포인트

| 출제 의도 | 반드시 짚을 핵심 | 감점 회피 포인트 |
|:---|:---|:---|
| 에이전트 자율 실행의 회복력 설계 역량 확인 | 체크포인트·멱등키·Saga 보상·에스컬레이션 4요소 | 단순 재시도만 쓰면 부작용(중복 결제) 미언급으로 감점 |
| 실패 유형별 복구 전략 분기 능력 | 일시적(5xx) vs 영구적(4xx) 분류 + 비멱등 보상 설계 | 모든 실패를 동일 재시도로 처리하면 설계 미흡 |

> 요약: 실패 유형 분류 → 멱등/비멱등 분기 → 보상·에스컬레이션 설계가 핵심 채점 축임.

## Ⅰ. 개요 및 필요성

- 정의: 에이전트 작업 중단을 체크포인트 기반으로 재개하는 회복력 구조
- 배경: 다단계 워크플로우에서 외부 API·LLM·DB 호출 시 부분 실패가 불가피함
- 필요성: 재시도·보상·에스컬레이션 전략 없이는 작업 완료율 99.5% 확보와 비용 통제가 불가능함


## Ⅱ. 구조 및 구성요소

```text
Task Step -> Checkpoint Store -> Failure Detector
               |                       |
          Retry Engine           Compensation
               |                       |
        Success / Escalate      Rollback / Alert
```

| 구성요소 | 역할 | 특이사항 |
|:---|:---|:---|
| Checkpoint Store | 단계별 입력·출력·상태 저장 | Redis TTL 24h, 암호화 저장 |
| Failure Detector | HTTP 5xx·타임아웃·LLM 거부 감지 | p99 응답 >5s 시 타임아웃 판정 |
| Retry Engine | 지수 백오프 재시도(최대 3회) | 멱등키 기반 중복 방지 |
| Compensation | 비멱등 작업 보상 트랜잭션 실행 | Saga 패턴 적용 |

> 요약: 체크포인트 저장 -> 실패 감지 -> 재시도/보상 -> 에스컬레이션의 4단계 복구 구조임.


## Ⅲ. 동작원리 및 흐름도

```text
단계 실행 -> 성공? -> Yes -> 체크포인트 저장 -> 다음 단계
              No -> 재시도 가능? -> Yes -> 지수 백오프 재시도
                                  No -> 보상 트랜잭션 -> Human Escalation
```

| 단계 | 처리 내용 | 검증 기준 |
|:---:|:---|:---|
| 1 | 단계 실행·결과 수신 | HTTP 200, 응답 p95 <3s |
| 2 | 실패 감지·분류 | 일시적(5xx) vs 영구적(4xx) |
| 3 | 재시도(지수 백오프 1s->2s->4s) | 최대 3회, 멱등키 필수 |
| 4 | 복구 불가 시 보상·에스컬레이션 | Slack 알림 <30s, 보상 완료 확인 |

> 요약: 일시적 실패는 지수 백오프로 자동 복구하고, 영구적 실패는 보상 트랜잭션 후 사람에게 넘김.


## Ⅳ. 특징

| 구분 | 단순 재시도 | 에이전트 실패복구 | 수치·판단 포인트 |
|:---|:---|:---|:---|
| 상태 관리 | 없음 | 체크포인트 기반 | 재시작 시간 0s vs 전체 재실행 |
| 중복 방지 | 미보장 | 멱등키·Saga 보상 | 중복 실행률 0% 목표 |
| 비용 통제 | 무한 재시도 위험 | 최대 3회+비용 한도 | 일일 토큰 한도 100K |

> 요약: 단순 재시도 대비 체크포인트·멱등키·비용 한도를 결합해 안전한 복구를 보장함.


## Ⅴ. 심화 비교 및 적용 판단

| 비교 축 | 단순 재시도 | 에이전트 실패복구 | 선택 기준 |
|:---|:---|:---|:---|
| 상태 보존 | 없음(처음부터 재실행) | 체크포인트 기반 부분 재개 | 단계 수 3개 이상 시 체크포인트 필수 |
| 부작용 방지 | 미보장(중복 실행) | 멱등키+Saga 보상 | 결제·주문 등 비멱등 API 포함 시 필수 |
| 비용 통제 | 무한 재시도 위험 | 최대 3회+일일 한도 100K 토큰 | 일일 비용 $50 이상 워크플로우 |

> 요약: 3단계 이상 워크플로우에서 비멱등 API가 포함되면 체크포인트+보상 설계가 필수임.

| 리스크 | 원인 | 대응 방안 | 확인 지표 |
|:---|:---|:---|:---|
| 체크포인트 유실 | Redis 장애·TTL 만료 | Redis Cluster + TTL 24h + 디스크 백업 | 체크포인트 복구율 99.9% |
| 중복 실행 | 멱등키 미적용 | 모든 외부 API에 UUID v4 멱등키 부여 | 중복 실행률 0% |
| 무한 재시도 | 영구 오류를 일시 오류로 오분류 | 4xx는 즉시 보상, 5xx만 재시도(최대 3회) | 평균 재시도 횟수 <1.5회 |

> 요약: 체크포인트 유실·중복 실행·무한 재시도가 주요 리스크이며, 클러스터·멱등키·오류 분류로 통제함.

| 점검 항목 | 목표 기준 | 측정 방법 |
|:---|:---|:---|
| 작업 완료율 | 99.5% 이상 | 완료/전체 워크플로우 비율, APM 대시보드 |
| 평균 복구 시간 | MTTR <5분 | PagerDuty 알림→해결 시간 |
| 중복 실행률 | 0% | 멱등키 충돌 로그 모니터링 |

> 요약: 작업 완료율 99.5%, MTTR 5분 이내, 중복 실행 0%로 복구 체계 효과를 판단함.

## Ⅵ. 실무 적용 및 결론

**적용 방안 3개:**
1. 각 도구 호출 전후 상태를 Redis 체크포인트에 저장하고 TTL 24h로 자동 만료 설정
2. 멱등키(UUID v4)를 모든 외부 API 호출에 부여하여 재시도 시 중복 실행 방지
3. 재시도 3회 실패 시 Saga 보상 트랜잭션 실행 후 PagerDuty 알림(MTTA <5분)

**결론 (2줄):**
- 기술사 판단: 멱등 API는 자동 재시도, 비멱등 작업은 Saga 보상+Human Approval로 설계함
- 향후 방향: LLM 자체 판단으로 실패 원인을 분류하고 대안 도구를 선택하는 자율 복구로 발전함
