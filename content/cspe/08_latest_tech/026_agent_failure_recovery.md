## Ⅰ. 개요
- **정의**: 에이전트 실행 중 발생하는 예외를 자율적으로 인지·분석·우회하여 목표를 완수하는 동적 복원 메커니즘
- **배경/필요성**: 외부 API 타임아웃, 환각 기반 파라미터 오류 등 현실 환경의 불확실성으로 인해 에이전트 중단율이 30% 이상 발생하며, 인간 개입 없는 자율 복구 체계가 필수임
- **비유**: 내비게이션이 막힌 도로를 감지해 자동으로 우회 경로를 재탐색하는 것과 유사

| 출제 의도 | 반드시 짚을 핵심 | 감점 회피 포인트 |
|:---|:---|:---|
| 전통 예외처리와 에이전트 복구의 차이 | Self-Correction(LLM 추론) vs Time-Travel(상태 롤백) 이중 구조 | 무한 루프 방지를 위한 Max Retries + HITL 에스컬레이션 누락 시 감점 |

> 요약: 에이전트 장애 복구는 에러를 '실패'가 아닌 '단서'로 활용하여 재계획·우회하는 자율 복원력임

## Ⅱ. 구성요소
```text
+------------------------------------------------------------------+
|                  Failure Recovery Pipeline                        |
|  +------------+    +-----------+    +----------+    +----------+  |
|  | Exception  |--->| Reflector |--->| Recovery |---> | Circuit  |  |
|  | Catcher    |    | (LLM)    |    | Selector |    | Breaker  |  |
|  +------------+    +-----------+    +----------+    +----------+  |
|       |                 |               |               |        |
|   에러 포획         원인 분석        전략 선택        루프 차단    |
+------------------------------------------------------------------+
```

| 구성요소 | 설명 | 비유 |
|:---|:---|:---|
| Exception Catcher | 도구 반환값의 HTTP 상태·Stack Trace를 포획하여 정상/이상 분류 | 자동차 충격 센서 |
| Reflector | LLM이 에러 로그를 읽고 파라미터 오류·서버 장애·권한 부족 등 원인 진단 | 정비사의 고장 진단 |
| Recovery Selector | Retry(재시도), Fallback(대체 도구), Rollback(체크포인트 복원) 중 전략 선택 | 우회도로 선택 |
| Circuit Breaker | 동일 에러 3회 초과 시 루프 강제 중단 후 HITL 에스컬레이션 | 과전류 차단기 |

> 요약: 에러 포획→원인 진단→전략 선택→루프 차단의 4계층 파이프라인으로 구성

## Ⅲ. 절차
```text
+----------+     +----------+     +------------+     +----------+
| 도구 실행 |---->| 에러 감지 |---->| 원인 분석   |---->| 복구 실행 |
| (Action) |     | (Catch)  |     | (Reflect)  |     | (Retry/  |
|          |     |          |     |            |     |  Fallback)|
+----------+     +----------+     +------------+     +----------+
     ^                                                     |
     +------- 성공 시 다음 단계 / 실패 시 Circuit Break ------+
```

1. **도구 실행 및 예외 포획** — 오케스트레이터가 도구 호출 결과를 정상 JSON과 에러 로그로 분류하여 에이전트 컨텍스트에 주입
2. **메타 인지(Self-Reflection)** — LLM이 Stack Trace를 파싱하여 "날짜 파라미터 형식 불일치", "API 503 서버 다운" 등 원인을 자연어로 진단
3. **복구 전략 선택** — 파라미터 오류 시 Retry(수정 후 재호출), 서버 장애 시 Fallback(대체 도구 전환), 상태 오염 시 Rollback(체크포인트 복원)
4. **무한 루프 차단** — Max Retries(3회) 초과 시 Circuit Breaker 발동, 인간 승인(HITL) 요청 또는 Graceful Degradation 수행

> 요약: 실행→감지→분석→복구의 피드백 루프를 Max Retries로 제한하여 무한 루프 방지

## Ⅳ. 문제점
- **환각 기반 거짓 복구**: 도구 호출 실패 시 LLM이 결과를 지어내어 사용자에게 전달 — 검증 없는 Final Answer 생성
- **무한 재시도 과금**: 동일 에러에 대해 Retry를 반복하며 토큰·API 비용이 기하급수적 증가 — Circuit Breaker 미설정
- **상태 오염 전파**: Retry 과정에서 변경된 외부 상태(DB 레코드 수정 등)가 롤백되지 않아 데이터 불일치 발생

> 요약: 거짓 복구, 과금 폭주, 상태 오염이 에이전트 장애 복구의 3대 리스크임

## Ⅴ. 개선방안
1. 단기: 도구 호출의 확정적 결과(JSON 응답코드 200)가 없으면 Final Answer 노드 진입을 State Machine 레벨에서 차단
2. 중기: Exponential Backoff(1s→2s→4s) + Max Retries(3회) + 월별 토큰 예산 임계치 알림 설정
3. 장기: 에이전트 실행 전 체크포인트(Snapshot) 저장 → 실패 시 Time-Travel로 정합성 있는 상태로 원자적 롤백

- **거짓 복구**: LLM 추론 결과와 도구 응답 간 Cross-Validation 필수화 → Fact-Check 통과율 95% 이상 시에만 전달 (지표: 거짓 복구율 < 2%)
- **과금 폭주**: 세션당 토큰 상한(Budget Cap) 설정 → 초과 시 자동 중단 (지표: 월별 API 비용 편차 ±10% 이내)
- **상태 오염**: 외부 부수효과 발생 도구는 트랜잭션 래핑 후 Compensating Action 등록 (지표: 롤백 성공률 99.9%)

> 요약: 검증 강제·예산 제한·트랜잭션 롤백으로 3대 리스크 각각에 대응

## Ⅵ. 전망
- 향후 발전 방향: 에러 극복 궤적을 장기 메모리(Vector DB)에 축적하여 동일 유형 에러 발생 시 즉시 최적 복구 전략을 검색·적용하는 메타 학습(Meta-Learning) 기반 복구로 진화
- 기술사적 판단: Self-Correction은 LLM 추론 능력에 의존하므로 100% 보장 불가하며, 미션 크리티컬 시스템에서는 반드시 결정론적 State Machine + 체크포인트 롤백을 병행 설계해야 함
- 기술사 제언: 샌드박스(023번 참조) 내에서 실패-복구를 반복할 수 있는 안전한 실행 환경과, 복구 실패 시 인간 에스컬레이션 경로를 아키텍처 설계 초기부터 확보할 것
