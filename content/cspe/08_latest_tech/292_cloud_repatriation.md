# 📖 【암기용】 개념 완전 이해

> 목적: 클라우드 회귀를 처음 봐도 완벽히 이해하게 만든다. 시험 답안 양식이 아니라, 이해를 위한 친절한 설명이다.

## 한눈에
- **개요**: 퍼블릭 클라우드에 올렸던 시스템이나 데이터를 다시 온프레미스(사내 서버)나 프라이빗 클라우드로 되돌리는 현상
- **왜 필요한가**: 클라우드가 무조건 저렴할 줄 알았는데 써보니 비용이 너무 많이 나오거나, 보안/성능 면에서 사내 서버가 더 유리한 경우가 생기기 때문이다.
- **핵심 직관**: "월세(클라우드)가 너무 비싸져서 다시 내 집(온프레미스)으로 들어가는 것"

## 깊이 이해
- **배경·문제의식**: 'Cloud First' 전략에 따라 무작정 클라우드로 옮겼던 기업들이 비용 폭탄(Bill Shock), 성능 저하, 관리 복잡성에 직면했다. 특히 24시간 내내 일정한 트래픽이 발생하는 서비스는 클라우드보다 직접 서버를 사는 게 장기적으로 훨씬 싸다.
- **작동 원리**: 모든 것을 다 가져오는 것이 아니라 '선별적'으로 가져온다. ① **비용 최적화**: 사용량이 꾸준한 워크로드. ② **보안/규제**: 민감 데이터. ③ **성능**: 네트워크 지연에 민감한 고성능 연산. 이를 위해 컨테이너(Kubernetes) 기술을 써서 클라우드에서 온프레미스로 쉽게 옮길 수 있게 만든다.
- **비유**: 매일 외식을 하다가 식비가 너무 많이 나오자, 자주 먹는 밥과 국은 집에서 해 먹고(회귀), 가끔 먹는 특식만 외식(클라우드)하는 식으로 바꾸는 전략이다.
- **구체 예시**: 37signals(Basecamp)가 클라우드에서 온프레미스로 전환해 5년간 700만 달러를 절감한 사례. 드롭박스(Dropbox)가 자체 인프라로 회귀한 사례.
- **흔한 오해·주의점**: "클라우드 실패"를 의미하는 게 아니다. 클라우드가 적합한 곳(가변적 트래픽)과 온프레미스가 적합한 곳(고정적 트래픽)을 구분해 '하이브리드'로 가는 과정 중 하나다.

## 연결 개념
- TCO (Total Cost of Ownership) — 하드웨어 구매부터 운영까지의 총 비용
- Cloud Sprawl — 클라우드 자원을 무분별하게 사용하여 관리가 안 되고 비용이 급증하는 현상
- Cloud Native — 환경에 구애받지 않고 어디서든 구동되게 하여 회귀를 용이하게 함

# 📝 【답안용】 시험 답안 템플릿

> 목적: 시험장에서 25분에 그대로 쓰는 답안 양식. 작성방식(추상표현 금지·수치·도식·문제유형 전환)을 엄격히 지킨다.
> 핵심: 비용 효율성과 데이터 주권이라는 실무적 관점에서 클라우드 회귀의 판단 기준과 이행 전략을 서술한다.

## 핵심 인사이트 (3줄 요약)

> 1. **본질**: Cloud Repatriation은 퍼블릭 클라우드의 비용(OpEx) 부담, 성능 병목, 보안 규제를 해결하기 위해 워크로드를 온프레미스나 프라이빗 환경으로 재이전하는 전략이다.
> 2. **가치**: 예측 가능한 워크로드의 TCO를 최대 50% 이상 절감하고, 물리적 인프라에 대한 직접적인 통제권과 보안 컴플라이언스를 강화한다.
> 3. **판단 포인트**: 트래픽 가변성, 데이터 전송량(Egress), 인프라 관리 역량(OpEx vs CapEx)을 종합 분석하여 회귀 대상을 선별해야 한다.

## 출제 의도 및 답안 포인트

| 출제 의도 | 반드시 짚을 핵심 | 감점 회피 포인트 |
|:---|:---|:---|
| 클라우드 회귀의 등장 배경 분석 | 비용(Bill Shock), 보안, 성능, 기술 종속성 | 단순히 '클라우드를 포기하는 것'으로 오해 금지 |
| 회귀 의사결정 기준(Matrix) 파악 | 워크로드 특성(고정 vs 가변), 데이터 밀집도 | 감성적 판단이 아닌 정량적 TCO 분석 기반 서술 |
| 하이브리드 클라우드 전략과의 연계 | 선별적 회귀를 통한 최적의 인프라 믹스 | 무조건적인 온프레미스 회귀 예찬 경계 |

> 요약: 무분별한 클라우드 도입의 부작용을 극복하고, 비즈니스 가치에 최적화된 인프라 재배치 능력을 평가한다.

## Ⅰ. 개요 및 필요성

- 정의: 퍼블릭 클라우드에서 운영 중인 애플리케이션, 데이터, 서비스를 온프레미스나 프라이빗 클라우드로 되돌리는 전략적 이동
- 배경: 클라우드 운영 비용의 급격한 상승(연평균 20~30% 증가), 클라우드 벤더 종속성 심화, 특정 워크로드의 성능 한계
- 필요성: 고정형 워크로드의 비용 효율화, 데이터 주권 및 보안 통제권 회복, 인프라 아키텍처의 유연성 확보

## Ⅱ. 구조 및 구성요소

```text
[ 분석 ] -> [ 대상 선정 ] -> [ 재이전 (Repatriation) ] -> [ 최적화 운영 ]
  |            |               |                         |
  |      +-----+-----+   +-----+-----+             +-----+-----+
  |      | 고정 워크로드 |   | 컨테이너 이관 |             | 하이브리드  |
  +----->| 데이터 밀집형 |-->| 데이터 마이그 |------------>| 거버넌스    |
         | 보안 민감형  |   | 네트워크 재구성 |             | 통합 관리    |
         +-----------+   +-----------+             +-----------+
```

| 구성요소 | 역할 | 핵심 기술/도구 |
|:---|:---|:---|
| TCO 분석 모델 | 회귀 전후의 비용 편익 정량적 비교 | FinOps 도구, ROI 계산기 |
| 워크로드 이동성 | 환경 간 앱 이전을 용이하게 함 | Docker, Kubernetes, IaC (Terraform) |
| 데이터 마이그레이션 | 대규모 클라우드 데이터의 안전한 회수 | Snowball, 전용선(Direct Connect), CDC |
| 현대화 인프라 | 온프레미스에서도 클라우드 경험 제공 | HCI (Hyper-Converged Infrastructure), SDDC |

> 요약: 정밀한 비용 분석을 바탕으로 컨테이너 기술을 활용해 워크로드의 이동성을 확보하는 것이 핵심이다.

## Ⅲ. 동작원리 및 흐름도

```text
클라우드 비용/성능 모니터링 -> 회귀 타당성 검토 -> 아키텍처 설계 -> 데이터/앱 재배포 -> 검증 및 최적화
```

| 단계 | 처리 내용 | 검증 기준 |
|:---:|:---|:---|
| 1 | 워크로드 프로파일링 | CPU/MEM 사용 패턴(Flat vs Spiky) 분석 |
| 2 | 회귀 가치 산정 | 3~5년 기준 CapEx(구매) vs OpEx(구독) 비교 |
| 3 | 인프라 준비 | SDDC 기반의 프라이빗 클라우드 또는 HCI 구축 |
| 4 | 단계적 이전 | 비핵심 업무부터 시범 이전 및 성능/비용 검증 |

> 요약: 사용 패턴이 일정한 워크로드를 선별하여 하드웨어 자산화(CapEx)를 통해 장기적 비용 구조를 개선한다.

## Ⅳ. 특징

| 구분 | 퍼블릭 클라우드 유지 | 온프레미스 회귀 (Repatriation) |
|:---|:---|:---|
| 비용 구조 | 변동 비용 (Pay-as-you-go) | 고정 비용 (CapEx + 유지보수비) |
| 자원 확장성 | 즉각적, 무한대 (Elasticity) | 물리적 증설 필요 (제한적) |
| 관리 책임 | CSP 분담 (Shared Responsibility) | 기업 자체 책임 (Full Control) |
| 최적 워크로드 | 트래픽 변동이 심한 신규 서비스 | 트래픽이 일정한 대규모 서비스 |

> 요약: 클라우드의 유연성을 포기하는 대신, 운영의 안정성과 비용 예측 가능성을 얻는 트레이드오프 관계이다.

## Ⅴ. 심화 비교 및 적용 판단

| 구분 | 클라우드 유지 (Maintain) | 클라우드 회귀 (Repatriate) | 선택 기준 |
|:---|:---|:---|:---|
| 비용 (Cost) | 데이터 전송(Egress) 비중 높음 | 초기 도입비 높음, 운영비 낮음 | 데이터 통신량 및 스토리지 규모 |
| 성능 (Performance) | 공유 자원 간섭 가능성 | 전용 하드웨어 성능 독점 | 지연시간(Latency) 민감도 |
| 보안 (Security) | 논리적 격리, 규제 대응 복잡 | 물리적 격리, 직접 통제 가능 | 데이터 보안 등급 및 규제 강도 |

> 요약: 데이터 전송량이 많고 보안 등급이 높으며 사용량이 일정한 워크로드는 회귀를 우선 검토한다.

| 리스크 | 원인 | 대응 방안 | 확인 지표 |
|:---|:---|:---|:---|
| 초기 비용 부담 | 대규모 하드웨어 구매 비용 발생 | 리스/렌탈 모델 활용, 단계적 전환 | 투자 회수 기간 (Payback Period) |
| 관리 역량 부족 | 클라우드에 의존하던 운영 기술 공백 | 인프라 자동화 도구 도입, 전문 인력 확보 | 시스템 가동률, 장애 복구 시간 |
| 확장성 제한 | 갑작스러운 수요 증가 대응 불가 | 클라우드와의 하이브리드 연결 유지 | 자원 사용률(Utilization) 여유분 |

> 요약: CapEx 부담과 운영 역량 저하가 리스크이며, 하이브리드 전략으로 보완해야 한다.

| 점검 항목 | 목표 기준 | 측정 방법 |
|:---|:---|:---|
| 비용 절감액 | 회귀 후 TCO 30% 이상 감소 | 이전 전/후 월평균 운영비 비교 |
| 서비스 응답 속도 | 네트워크 지연 50% 이상 개선 | APM(Application Performance Monitoring) |
| 데이터 전송비 | 클라우드 Egress 비용 90% 제거 | 클라우드 빌링 리포트 분석 |

> 요약: 도입 효과는 비용 절감률, 성능 향상 폭, 그리고 데이터 전송 비용 제거 수준으로 평가한다.

## Ⅵ. 실무 적용 및 결론

**적용 방안 3개:**
1. **데이터 집약형**: 데이터 분석 워크로드 등 매월 수 PB의 데이터를 처리하여 클라우드 Egress 비용이 과다한 시스템 회귀
2. **고정 워크로드**: 24/7 가동되는 핵심 뱅킹 서비스나 ERP 등 트래픽 변화가 거의 없는 안정적 시스템의 하드웨어 자산화
3. **규제 대응**: 국가 안보나 개인정보보호 강화로 인해 반드시 사내 전산실에 위치해야 하는 필수 데이터 서버 회귀

**결론 (2줄):**
- 기술사 판단: 클라우드 회귀는 클라우드의 실패가 아니라 인프라 전략의 고도화 과정이며, '어디서든 돌아가는(Cloud Native)' 기술력이 회귀의 전제 조건이다.
- 향후 방향: 퍼블릭 클라우드-프라이빗 클라우드-엣지 컴퓨팅을 유기적으로 배치하는 '인프라 최적 재배치(Right-placing)'가 기업 IT의 핵심 역량이 될 것이다.
