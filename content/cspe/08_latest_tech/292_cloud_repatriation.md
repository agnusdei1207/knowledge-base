# 📖 【암기용】 개념 완전 이해

> 목적: 클라우드 회귀를 클라우드 실패가 아니라 워크로드 특성 변화와 비용·통제 요구에 따라 실행 위치를 다시 조정하는 전략으로 이해하게 만든다.

## 한눈에
- **개요**: 퍼블릭 클라우드의 일부 워크로드를 온프레미스·프라이빗 클라우드·코로케이션으로 되돌리는 이전
- **왜 필요한가**: 예측 가능한 고정 부하, 대용량 데이터 전송, 규제 데이터, 특수 하드웨어 업무는 퍼블릭 클라우드 과금 구조와 맞지 않을 수 있다.
- **핵심 직관**: 단기 렌터카가 편해도 매일 같은 구간을 오래 달리면 차량 구매가 더 맞을 수 있다.

## 깊이 이해
- **배경·문제의식**: 초기 클라우드 전환은 속도와 유연성을 우선하지만, 운영이 성숙하면 월 과금, egress 비용, 라이선스, 지연시간, 데이터 통제가 재검토 대상이 된다.
- **작동 원리**: 비용·성능·규제·운영 데이터를 분석해 회귀 후보를 정하고, 데이터 이전·플랫폼 재구성·운영 전환을 단계적으로 수행한다.
- **비유**: 임시 사무실에서 시작한 회사가 인원과 업무가 고정되면 장기 임대 사무실로 옮기는 것과 같다.
- **구체 예시**: 24시간 일정 부하의 분석 DB가 월 클라우드 비용 대부분을 차지하면, 스토리지·네트워크 비용을 포함해 프라이빗 클라우드 이전을 검토한다.
- **흔한 오해·주의점**: 회귀는 전체 클라우드 철수가 아니다. 워크로드별로 퍼블릭, 프라이빗, 온프레미스의 경제성과 통제 요건을 재배치하는 과정이다.

## 연결 개념
- FinOps — 회귀 후보를 비용 데이터로 식별
- Hybrid Cloud — 회귀 후 운영 모델
- Cloud Migration 6R — Rehost, Replatform, Retire 판단과 연결

# 📝 【답안용】 시험 답안 템플릿

> 목적: 시험장에서 25분에 그대로 쓰는 답안 양식.
> 핵심: 클라우드 회귀는 비용 절감 구호가 아니라 워크로드별 TCO, 데이터 이동, 운영 역량을 검증한 배치 재설계다.

## 핵심 인사이트 (3줄 요약)

> 1. **본질**: Cloud Repatriation은 퍼블릭 클라우드 워크로드를 내부 인프라나 프라이빗 클라우드로 이전하는 배치 재조정임.
> 2. **가치**: 예측 가능한 고정 부하, 높은 egress 비용, 규제 통제, 특수 하드웨어 요구를 위치 재배치로 처리함.
> 3. **판단 포인트**: 회귀 전후 TCO, 데이터 이전 비용, 운영 인력, RTO/RPO, 보안 책임 경계를 비교해야 함.

## 출제 의도 및 답안 포인트

| 출제 의도 | 반드시 짚을 핵심 | 감점 회피 포인트 |
|:---|:---|:---|
| 클라우드 비용 구조 이해 확인 | compute, storage, egress, license, 운영비 | 클라우드가 비싸다는 일반론 |
| 배치 재설계 판단 확인 | 후보 선정, 이전 방식, 운영 전환 | 전체 철수로 단정 |
| 리스크 관리 확인 | 데이터 이전, 서비스 중단, 역량 부족 | 이전 비용과 장애 위험 누락 |

> 요약: 이 문제는 클라우드 회귀의 타당성을 TCO와 운영 전환 리스크로 판단하라는 요구다.

---

## Ⅰ. 개요 및 필요성

- 개요: 워크로드 내부 회귀 이전
- 배경: 클라우드 사용량이 커지면 상시 부하, 데이터 전송, 라이선스 비용이 초기 예상과 달라질 수 있음.
- 필요성: 월별 TCO, egress, p95 지연시간, RTO/RPO를 기준으로 퍼블릭 유지와 내부 회귀를 비교해야 함.

---

## Ⅱ. 구조 및 구성요소

```text
Cloud Workload Inventory -> Cost / Risk Analysis -> Repatriation Candidate
  +-> Target Platform -> Data Migration -> Cutover
  +-> Monitoring / Backup / Security Operation
```

| 구성요소 | 역할 | 특이사항 |
|:---|:---|:---|
| 비용 분석 | 과금 항목과 사용 패턴 식별 | compute, storage, egress |
| 후보 선정 | 회귀 대상 워크로드 분류 | 고정 부하·규제·지연시간 |
| 목표 플랫폼 | 온프레미스·프라이빗·코로케이션 선택 | 용량·운영 인력 필요 |
| 전환 운영 | 데이터 이전과 cutover 수행 | rollback, backup, DR |

> 요약: 회귀 구조는 비용 분석에서 시작해 후보, 목표 플랫폼, 데이터 이전, 운영 전환으로 이어진다.

---

## Ⅲ. 동작원리 및 흐름도

```text
사용량 수집 -> TCO 비교 -> 회귀 후보 확정
-> 데이터 / 의존성 분석 -> 목표 환경 구축 -> 이전 / 검증 -> 운영 전환
```

| 단계 | 처리 내용 | 검증 기준 |
|:---:|:---|:---|
| 1 | 리소스 사용량과 과금 항목 수집 | 월별 단가·egress |
| 2 | 퍼블릭 유지와 내부 운영 TCO 비교 | 3년 TCO, 감가상각 |
| 3 | 의존 서비스와 데이터 이동 계획 수립 | downtime, RPO |
| 4 | 성능·보안·백업 검증 후 전환 | p95 latency, DR test |

> 요약: 클라우드 회귀는 비용 후보를 찾은 뒤 의존성·데이터·운영 검증을 통과한 업무만 이전한다.

---

## Ⅳ. 특징

| 구분 | 클라우드 유지 | Cloud Repatriation | 판단 기준 |
|:---|:---|:---|:---|
| 비용 | 사용량 과금 | 설비·운영비 전환 | 고정 부하 비율 |
| 통제 | 공급자 책임 모델 | 조직 책임 증가 | 보안 운영 역량 |
| 데이터 | 리전 내 저장 | 내부 위치 통제 | 규제·egress |
| 민첩성 | 서비스 조달 용이 | 용량 증설 시간 필요 | 수요 변동성 |

> 요약: 회귀는 비용과 통제권을 얻는 대신 용량 계획과 내부 운영 책임을 다시 부담한다.

---

## Ⅴ. 심화 비교 및 적용 판단

| 비교 축 | 기존/대안 | 본 키워드 | 선택 기준 |
|:---|:---|:---|:---|
| 구조 | 퍼블릭 클라우드 상시 운영 | 프라이빗·온프레미스 재배치 | 부하 예측 가능성 |
| 비용 | OPEX 사용량 과금 | CAPEX+운영비 혼합 | 3년 TCO |
| 운영 | Managed service 의존 | 내부 SRE·보안 운영 필요 | 운영 인력과 자동화 |

> 요약: 회귀는 워크로드가 고정 부하이고 내부 운영 역량이 있을 때 검토 가치가 있다.

| 리스크 | 원인 | 대응 방안 | 확인 지표 |
|:---|:---|:---|:---|
| 이전 중단 | 데이터 크기와 의존성 복잡 | phased cutover, rollback | downtime |
| 비용 역전 | 숨은 운영비 누락 | 인력·전력·상면 포함 TCO | cost variance |
| 운영 공백 | managed service 대체 실패 | runbook, on-call 체계 | incident MTTR |

> 요약: 회귀 리스크는 이전 중단, 비용 역전, 운영 공백이며 TCO와 운영 지표로 검증해야 한다.

| 점검 항목 | 목표 기준 | 측정 방법 |
|:---|:---|:---|
| 경제성 | 3년 TCO 기준 우위 | 비용 모델 검토 |
| 서비스 품질 | SLA와 p95 지연시간 충족 | 부하 테스트 |
| 복구 | RTO/RPO 기준 충족 | 백업·DR 리허설 |

> 요약: 회귀 성공은 이전 완료가 아니라 경제성, 서비스 품질, 복구 기준을 동시에 만족하는지로 판단한다.

---

## Ⅵ. 실무 적용 및 결론

**적용 방안 3개:**
1. FinOps 리포트로 상시 부하, egress 상위, 라이선스 비용 상위 워크로드를 회귀 후보로 선정함.
2. 3년 TCO에 서버, 스토리지, 전력, 상면, 인력, 백업, DR 비용을 포함해 퍼블릭 유지안과 비교함.
3. 데이터 동기화, 병행 운영, rollback, cutover 리허설을 수행하고 전환 후 30일 비용·성능 지표를 검토함.

**결론 (2줄):**
- 기술사 판단: 수요 변동이 크면 퍼블릭 유지, 고정 부하와 규제 통제가 크면 선택적 회귀가 타당함.
- 향후 방향: 회귀는 클라우드 철수가 아니라 FinOps 기반 하이브리드 배치 최적화로 자리 잡음.
