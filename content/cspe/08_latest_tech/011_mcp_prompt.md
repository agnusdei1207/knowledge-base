# 📖 【암기용】 개념 완전 이해

## 한눈에
- **개요**: **MCP 프롬프트**(MCP Prompt)는 MCP 서버가 노출하는 3대 프리미티브 중 **인자를 받아 완성된 대화 메시지로 펼쳐지는 재사용 프롬프트 템플릿**이다(사용자가 슬래시 명령 등으로 골라 실행).
- **왜 필요한가**: 좋은 프롬프트를 매번 손으로 다시 쓰는 것은 낭비다. 서버가 검증된 작업 서식을 템플릿으로 배포하면, 사용자가 인자만 채워 일관된 워크플로를 반복 실행할 수 있다.
- **핵심 직관**: "빈칸 채우는 결재 서식". 코드 리뷰·회의록 요약 같은 반복 작업의 지시문을 서버가 서식으로 미리 만들어두고, 사용자는 대상만 넣어 제출한다.

## 핵심 용어 정리 (내부에 등장하는 것들)
답안 본문에 등장하는 용어를 처음 보는 사람도 이해하도록 비유와 함께 먼저 정리한다.

| 용어/표기 | 의미 | 비유·예 |
|:---|:---|:---|
| MCP 프롬프트(핵심) | 인자로 완성되는 재사용 프롬프트 템플릿 | 빈칸 채우는 "작업 서식" |
| 3대 프리미티브 | 툴(실행)·리소스(읽기)·프롬프트(템플릿) | 기능 버튼/자료/서식 (006·009 참조) |
| arguments | 템플릿에 주입하는 변수 목록 | 서식의 "빈칸 필드" |
| prompts/list · prompts/get | 프롬프트 목록 조회 / 완성본 요청 | 서식철 보기 / 작성본 받기 |
| 사용자 제어(User-controlled) | 어떤 프롬프트를 쓸지 사용자가 선택 | 사람이 서식을 "고름" |
| 슬래시 명령 | UI에서 프롬프트를 부르는 진입점 `/review` | 서식 바로가기 메뉴 |
| PromptMessage | 완성돼 돌아오는 role·content 메시지열 | 작성 완료된 서식지 |
| 임베디드 리소스 | 프롬프트에 끼워 넣는 리소스 참조 | 서식에 첨부된 자료 |
| 프롬프트 인젝션 | 프롬프트에 숨긴 악성 지시 | 서식에 몰래 적은 지시문 |

## 깊이 이해
- **배경·문제의식**: MCP 전체 구조·프리미티브 개념은 006, 리소스는 009에서 다룬다. 프롬프트 관점의 문제는 "숙련자가 만든 좋은 지시문(코드 리뷰 체크리스트 등)이 개인 노트에 흩어져 재사용되지 못한다"는 것이다. 서버가 이를 표준 템플릿으로 배포해 팀 전체가 공유하게 한다.
- **작동 원리(어떻게+왜)**: 서버는 프롬프트를 이름·설명·arguments(변수 목록)로 선언한다. 사용자가 `prompts/list`로 목록을 보고 슬래시 명령 등으로 선택하면, 클라이언트가 인자를 채워 `prompts/get`을 호출하고, 서버가 변수를 치환한 완성 메시지열(PromptMessage)을 반환한다. 호출 여부를 사용자가 정하므로(User-controlled) 툴(모델 제어)·리소스와 제어 주체가 다르다.
- **비유**: 워드의 "문서 서식"과 같다. 이력서 서식을 골라 이름·경력 칸만 채우면 완성 문서가 나오듯, 프롬프트 서식을 골라 대상만 넣으면 완성된 지시 메시지가 만들어진다.
- **구체 예시(실제 사례)**: Git MCP 서버가 `/git-commit` 프롬프트를 제공하면, 사용자가 변경 diff를 인자로 넣어 "이 diff로 커밋 메시지를 작성하라"는 완성 프롬프트를 받는다. 코드 리뷰·PR 요약·번역 서식도 같은 방식으로 팀이 공유한다.
- **흔한 오해·주의점**: MCP 프롬프트는 앱에 하드코딩된 일반 프롬프트 문자열이 아니라, 서버가 배포하고 사용자가 선택하는 표준화·재사용 템플릿이다. 또한 프롬프트 본문·임베디드 리소스에 숨긴 지시(프롬프트 인젝션)가 위험이므로 출처 신뢰·검증이 필요하다.

## 연결 개념
- MCP 툴(010)·리소스(009) — 프롬프트와 대비되는 나머지 두 프리미티브(제어 주체가 다름)
- 프롬프트 템플릿(043)·시스템 프롬프트(044) — 프롬프트 설계의 기반 개념
- 프롬프트 엔지니어링(042) — 템플릿에 담기는 지시 설계 기법

# 📝 【답안용】 시험 답안 템플릿

## 핵심 인사이트 (3줄 요약)

> 1. **본질**: MCP 프롬프트는 서버가 배포하고 사용자가 선택하는, 인자로 완성되는 재사용 프롬프트 템플릿임.
> 2. **가치**: 검증된 작업 지시문을 표준 서식으로 공유해 반복 워크플로의 일관성·재사용을 확보함.
> 3. **판단 포인트**: 사용자 제어 특성상 슬래시 명령 UX와 함께 프롬프트 인젝션·출처 검증을 설계해야 함.

## 출제 의도 및 답안 포인트

| 출제 의도 | 반드시 짚을 핵심 | 감점 회피 포인트 |
|:---|:---|:---|
| 템플릿 프리미티브 구조 이해 | arguments, prompts/list·get, 사용자 제어 | 툴·리소스와 제어 주체 혼동 시 감점 |
| 재사용 가치 인식 | 표준 서식 배포·팀 공유, 일관성 | 단순 문자열 저장으로 축소 시 감점 |
| 보안 인식 | 프롬프트 인젝션·임베디드 리소스 검증 | 출처 신뢰 통제 누락 시 감점 |

> 요약: 프롬프트를 무엇으로 선언·완성하고 누가 제어하며 어떤 위협을 통제하는지 확인하려는 문제임.

---

## Ⅰ. 개요 및 필요성

- 개요: 서버가 이름·인자로 선언하고 사용자가 선택해 완성 메시지로 펼치는 재사용 프롬프트 템플릿임
- 배경: 숙련자의 좋은 지시문이 개인 노트에 흩어져 재사용·공유되지 못함
- 필요성: 검증된 작업 서식을 표준 배포해 반복 워크플로의 일관성을 확보해야 함 (전체 구조는 006 참조)
- 위치: 서버가 노출하는 3대 프리미티브 중 사용자가 주도해 선택하는 템플릿 계열임

---

## Ⅱ. 구조 및 구성요소

- 선형 구조도

```text
서버 프롬프트 선언(name / description / arguments)
  사용자가 발견 prompts/list -> 슬래시 명령 등으로 선택
    -> 인자 입력 -> prompts/get 요청
    -> 서버가 변수 치환·리소스 임베드 -> PromptMessage(role·content) 반환
    -> 대화 컨텍스트에 삽입 -> 모델 처리
```

| 구성요소 | 역할 | 특이사항 |
|:---|:---|:---|
| 이름·설명 | 프롬프트 식별·용도 안내 | 슬래시 명령명과 연결 |
| arguments | 주입 변수 정의 | required·description 포함 |
| 템플릿 본문 | 변수 자리표시자 포함 지시문 | 치환 대상 |
| 임베디드 리소스 | 프롬프트에 끼운 데이터 참조 | 출처 검증 필요 |
| PromptMessage | 완성된 role·content 메시지열 | 대화에 그대로 삽입 |

> 요약: 프롬프트는 이름·인자로 선언되고, 사용자가 선택·입력하면 서버가 완성 메시지열로 펼쳐 반환함.

---

## Ⅲ. 동작원리 및 흐름도

- 선형 흐름도

```text
prompts/list 발견 -> 사용자가 프롬프트 선택 -> 인자 입력 -> prompts/get 요청 -> 서버 변수 치환·리소스 임베드 -> PromptMessage 반환 -> 대화 삽입 -> 모델 처리
```

1. 발견: 클라이언트가 서버의 프롬프트 목록과 각 arguments 정의를 획득함
2. 선택: 사용자가 슬래시 명령 등으로 프롬프트를 고르고 인자 값을 입력함
3. 완성: 클라이언트가 prompts/get을 호출하고 서버가 변수 치환·리소스 임베드로 메시지열을 생성함
4. 처리: 반환된 PromptMessage를 대화 컨텍스트에 삽입해 모델이 지시를 수행함

> 요약: 사용자가 프롬프트를 주도 선택하고, 서버가 인자를 치환한 완성 메시지열을 대화에 제공함.

---

## Ⅳ. 특징

- 사용자 제어: 모델이 아니라 사용자가 어떤 프롬프트를 쓸지 선택해 실행함
- 재사용성: 검증된 작업 지시문을 표준 서식으로 배포·공유해 반복 사용함
- 매개변수화: arguments로 변수를 주입해 하나의 서식으로 다양한 대상을 처리함
- 리소스 결합: 임베디드 리소스로 데이터를 프롬프트에 끼워 맥락을 함께 전달함
- 부작용 없음: 실행 동작이 아니라 메시지 생성이므로 상태를 바꾸지 않음

---

## Ⅴ. 심화 비교 및 적용 판단

- MCP 프롬프트는 앱에 하드코딩된 일반 프롬프트 문자열과 대비할 때 그 표준화 가치가 분명함

| 구분 | MCP 프롬프트 | 일반 프롬프트(하드코딩) |
|:---|:---|:---|
| 출처·배포 | 서버가 표준 선언·배포 | 앱 코드·개인 노트에 내장 |
| 매개변수 | arguments로 구조화 주입 | 문자열 직접 조립 |
| 발견·선택 | prompts/list로 동적 발견 | 사전 고정, 발견 불가 |
| 재사용 범위 | MCP 호스트 전체 공유 | 해당 앱·개인 한정 |
| 호출 방식 | prompts/get 표준 요청 | 코드 내부 문자열 결합 |

> 요약: 팀·호스트 간 공유와 동적 발견이 필요하면 MCP 프롬프트, 단일 앱 전용 고정 지시는 하드코딩도 충분함.

- 프롬프트 성격별 활용(불릿)
  - 워크플로형 — 코드 리뷰·릴리스 노트, 팀 표준 절차 서식화
  - 변환형 — 번역·요약·포맷 변경, 대상만 인자로 교체
  - 컨텍스트 주입형 — 임베디드 리소스로 근거 데이터 동봉

- 주요 리스크와 대응(불릿)
  - 프롬프트 인젝션 — 템플릿·임베디드 리소스에 숨긴 지시가 원인 → 출처 신뢰·본문 검증·서명
  - 인자 오남용 — 미검증 사용자 입력이 지시를 왜곡함이 원인 → arguments 스키마·값 검증
  - 버전 불일치 — 서식 갱신이 전파 안 됨이 원인 → 프롬프트 버전 표기·호환 관리

- 운영 지표(불릿)
  - 재사용률 — 공용 프롬프트 채택 수/팀 목표 — 사용 로그 집계
  - 완성 일관성 — 동일 인자 재현율 100% 목표 — 출력 회귀 검증
  - 인젝션 차단 — 미검증 서버 프롬프트 0건 목표 — 출처 감사

---

## Ⅵ. 실무 적용 및 결론

- 적용 방안
  1. 표준 서식화: 코드 리뷰·회의록 요약 등 반복 작업을 arguments 기반 프롬프트로 배포해 팀이 슬래시 명령으로 재사용
  2. 근거 동봉: 임베디드 리소스로 대상 문서·diff를 프롬프트에 끼워 맥락과 지시를 한 번에 전달
  3. 신뢰 통제: 서버 출처를 서명·허용 목록으로 검증하고 프롬프트 본문·인자를 정제해 인젝션 차단
- 결론
  - 기술사 판단: 팀 공유·동적 발견이 필요한 반복 워크플로는 MCP 프롬프트로 표준화하고, 단일 앱 전용 고정 지시는 하드코딩을 유지함
  - 향후 방향: 프롬프트 레지스트리·버전 관리와 결합해 조직 지식이 표준 서식으로 축적·공유되는 방향으로 진화함
