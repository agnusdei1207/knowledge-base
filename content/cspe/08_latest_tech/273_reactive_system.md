# 📖 【암기용】 개념 완전 이해

> 목적: 리액티브 시스템을 처음 봐도 완벽히 이해하게 만든다. 시험 답안 양식이 아니라, 이해를 위한 친절한 설명이다.

## 한눈에
- **개요**: 변화에 민감하게 반응(Reactive)하며, 부하가 늘어도 죽지 않고 일정한 응답 속도를 유지하도록 설계된 시스템 아키텍처
- **왜 필요한가**: 현대의 웹 서비스는 수천만 명의 사용자가 접속하고 데이터량이 폭증한다. 기존의 동기식 방식으로는 서버가 금방 마비되기 때문에, 어떤 상황에서도 "살아있고(Available) 빠른(Responsive)" 시스템이 필요하게 되었다.
- **핵심 직관**: **리액티브 선언문(Reactive Manifesto)**에서 정의한 4가지 핵심 가치(응답성, 회복성, 탄력성, 메시지 기반)를 갖춘 시스템이다.

## 깊이 이해
- **배경·문제의식**: 예전에는 서버 성능이 부족하면 기다리게 했다(Blocking). 하지만 클라우드 환경에서는 기다리는 동안 비용이 나가고 시스템 전체가 도미노처럼 무너진다. 이를 막기 위해 "비동기 논블로킹(Asynchronous Non-blocking)" 방식이 필수적이 되었다.
- **작동 원리**: **메시지 기반(Message-driven)** 통신을 기초로 한다. 구성요소들이 서로를 직접 부르는 게 아니라 메시지를 주고받으며 독립적으로 동작한다. 덕분에 에러가 나도 격리(회복성)할 수 있고, 부하가 오면 서버를 늘리기(탄력성) 쉽다. 결국 사용자에게 항상 빠른 응답(응답성)을 준다.
- **비유**: 푸드코트와 같다. 주문(메시지)을 하면 벨을 주고 기다린다. 주방은 주문 순서대로 요리하고 벨을 울린다. 한 주방이 불이 나도(에러) 다른 코너는 멀쩡하며, 손님이 많으면 요리사를 더 투입하면 된다. 손님은 계속 줄 서지 않고 다른 일을 하며 기다릴 수 있다.
- **구체 예시**: Netflix의 API Gateway, Akka 프레임워크 기반 시스템, Spring WebFlux를 사용한 마이크로서비스 등.
- **흔한 오해·주의점**: "리액티브 프로그래밍(RxJava, Project Reactor)"과 혼동하기 쉽다. 프로그래밍은 구현 도구일 뿐이고, 시스템은 그 도구를 포함해 인프라와 설계 전체가 추구하는 "지향점"이다.

## 연결 개념
- Reactive Manifesto — 리액티브 시스템의 성전
- Backpressure (역압) — 데이터 폭주 시 수신자가 공급량을 조절하는 메커니즘
- Circuit Breaker — 시스템 장애 확산을 막는 차단기
- Microservices — 리액티브 시스템을 구현하기 가장 적합한 단위

# 📝 【답안용】 시험 답안 템플릿

> 목적: 시험장에서 25분에 그대로 쓰는 답안 양식. 작성방식(추상표현 금지·수치·도식·문제유형 전환)을 엄격히 지킨다.
> 핵심: 리액티브 선언문의 4대 원칙(응답성, 회복성, 탄력성, 메시지 기반)을 논리 구조의 중심에 두고 서술한다.

## 핵심 인사이트 (3줄 요약)

> 1. **본질**: 리액티브 시스템은 비동기 메시지 기반 통신을 통해 높은 응답성(Responsive), 회복성(Resilient), 탄력성(Elastic)을 달성하는 현대적 분산 아키텍처이다.
> 2. **가치**: 장애가 전체로 확산되는 것을 방지(격리)하고, 부하 변화에 유연하게 대응하여 사용자 경험 유지와 인프라 비용 효율성을 동시에 확보한다.
> 3. **판단 포인트**: 단순한 비동기 라이브러리 사용을 넘어, 시스템 전반의 느슨한 결합(Loose Coupling)과 위치 투명성(Location Transparency) 확보가 핵심이다.

## 출제 의도 및 답안 포인트

| 출제 의도 | 반드시 짚을 핵심 | 감점 회피 포인트 |
|:---|:---|:---|
| 리액티브 선언문(Manifesto) 이해 확인 | 4대 원칙 (응답성, 회복성, 탄력성, 메시지 기반) | 4대 원칙 중 일부 누락 |
| 구현 메커니즘 및 기술 요소 확인 | 역압(Backpressure), 비동기 논블로킹, 서킷 브레이커 | 단순 이론만 서술하고 기술 요소(Backpressure 등) 누락 |
| 실무 적용 및 설계 역량 확인 | 클라우드 네이티브, MSA와의 연관성 | 전통적 아키텍처와의 차이점 불분명 |

> 요약: 변화와 장애에 유연하게 대응하는 시스템의 4대 속성을 명확히 정의하고 상호 관계를 도식화한다.

## Ⅰ. 개요 및 필요성

- 정의: 리액티브 선언문(2014)에 따라 응답성, 회복성, 탄력성, 메시지 기반 통신을 갖춘 분산 시스템 아키텍처
- 배경: 분산 컴퓨팅 환경에서 데이터 폭증 및 사용자 요구 고도화로 인해 기존 동기식 차단(Blocking) 아키텍처의 한계 도래
- 필요성: 시스템의 가용성(Availability) 극대화, 지연 시간(Latency) 최소화, 자원 활용 효율 증대를 통한 클라우드 비용 최적화

---

## Ⅱ. 구조 및 구성요소

```text
       +----------------------------+
       |       응답성 (Responsive)   | <--- 최종 목표
       +----------------------------+
                ^          ^
       +--------+----------+--------+
       | 회복성(Resilient) | 탄력성(Elastic) | <--- 수단
       +--------+----------+--------+
                ^          ^
       +----------------------------+
       |    메시지 기반 (Message-driven)  | <--- 토대
       +----------------------------+
```

| 구성요소 | 역할 | 특이사항 |
|:---|:---|:---|
| 응답성 | 어떤 상황에서도 신속하고 일정한 응답 시간 제공 | 사용자 경험의 핵심 |
| 회복성 | 장애 발생 시 부분적 장애로 격리 및 자가 복구 | 복제, 봉쇄(Containment), 격리 |
| 탄력성 | 부하 변화에 따라 자원을 동적으로 늘리거나 줄임 | 오토스케일링, 위치 투명성 |
| 메시지 기반 | 비동기 메시지 교환으로 컴포넌트 간 결합도 최소화 | 역압(Backpressure) 통제 가능 |

> 요약: 메시지 기반 통신을 토대로 회복성과 탄력성을 확보하여 궁극적인 응답성을 지향하는 구조다.

---

## Ⅲ. 동작원리 및 흐름도

```text
[동작 흐름: 요청 -> 메시지 큐 -> 비동기 처리 -> 결과 알림]
Request -> Message Broker (Queue) -> Subscriber 1 (Processing)
                                 -> Subscriber 2 (Logging)
   ^                                     |
   |----------- Backpressure (Slow down) <--- 부하 감지
```

| 단계 | 처리 내용 | 검증 기준 |
|:---:|:---|:---|
| 1 | 비동기 요청 | 요청자는 결과를 기다리지 않고 메시지 큐에 위임 후 다른 작업 수행 |
| 2 | 위치 투명성 | 메시지 수신자의 실제 위치를 몰라도 주소(ID)만으로 통신 |
| 3 | 역압 제어 | 수신측 처리가 늦어지면 송신측에 데이터 전송 속도 조절 요청 |
| 4 | 장애 격리 | 특정 서비스 장애 시 서킷 브레이커가 작동하여 전체 시스템 보호 |

> 요약: 비동기 메시지 전송과 역압 제어를 통해 하위 구성요소의 상태가 상위로 전이되는 것을 차단한다.

## Ⅳ. 특징

| 구분 | 내용 | 판단 포인트 |
|:---|:---|:---|
| 비동기성 | 논블로킹 I/O를 통한 스레드 효율성 극대화 | 적은 스레드로 많은 요청 처리 |
| 자가 복구 | 장애 시 상위 컴포넌트가 하위 상태를 감시하고 재시작 | Supervision 전략 |
| 유연성 | 특정 벤더나 하드웨어에 종속되지 않는 소프트웨어 설계 | 클라우드 네이티브 적합성 |
| 일관된 지연 | 예측 가능한 응답 시간 유지 (Tail Latency 관리) | 고가용성 서비스의 필수 요건 |

> 요약: '결합도'를 낮추고 '반응성'을 높여서 대규모 분산 환경의 불확실성을 통제하는 아키텍처적 특징을 가진다.

## Ⅴ. 심화 비교 및 적용 판단

| 구분 | 전통적 시스템 (Imperative) | 리액티브 시스템 (Reactive) | 선택 기준 |
|:---|:---|:---|:---|
| 통신 방식 | 동기식 RPC / HTTP (Blocking) | 비동기 메시지 (Non-blocking) | 응답 지연 민감도 |
| 장애 대응 | 전체 장애 전이 위험 (Cascade) | 장애 격리 및 자가 복구 | 시스템 신뢰도 목표 |
| 스케일링 | 서버 단위 수직 확장 (Scale-up) | 컴포넌트 단위 수평 확장 (Scale-out) | 트래픽 가변성 |

> 요약: 단순 CRUD 시스템은 전통적 방식이 생산적이나, 대규모 MSA나 실시간 데이터 처리에는 리액티브가 필수적이다.

| 리스크 | 원인 | 대응 방안 | 확인 지표 |
|:---|:---|:---|:---|
| 구현 복잡성 | 비동기 흐름 제어의 난해함 | 가상 스레드(Java) 또는 표준 라이브러리 사용 | 개발 및 유지보수 비용 |
| 데이터 일관성 | 최종 일관성(Eventual Consistency) 문제 | Saga 패턴, 이벤트 소싱 도입 | 데이터 정합성 오류율 |
| 운영 오버헤드 | 분산 메시지 큐 관리 부담 | 관리형 서비스(Managed Service) 활용 | 인프라 운영 공수 |

> 요약: 기술적 복잡도를 보완하기 위해 명확한 상태 관리 패턴과 운영 자동화 도구가 병행되어야 한다.

| 점검 항목 | 목표 기준 | 측정 방법 |
|:---|:---|:---|
| 가용성 | 99.99% (Four Nines) 이상 | 장애 시간(Downtime) 측정 |
| 자원 효율성 | CPU 사용률 대비 처리량 30% 향상 | 단위 자원당 TPS 측정 |
| 장애 복구 시간 | MTTR(평균 복구 시간) 1분 이내 | 장애 시뮬레이션 및 복구 테스트 |

> 요약: 도입 효과는 가동률 향상과 단위 비용당 처리량 개선으로 입증한다.

## Ⅵ. 실무 적용 및 결론

**적용 방안 3개:**
1. 스트리밍 서비스: Kafka와 연동하여 실시간 사용자 로그를 처리하고 역압(Backpressure)으로 시스템 다운 방지
2. 전자상거래(e-Commerce): 결제, 재고, 주문 시스템을 메시지 기반으로 분리하여 특정 서비스 장애 시에도 주문 접수 유지
3. API Gateway: 입구 단계에서 비동기 논블로킹을 적용하여 수만 개의 동시 접속을 최소 자원으로 수용

**결론 (2줄):**
- 기술사 판단: 리액티브 시스템은 이제 선택이 아닌 대규모 분산 시스템과 클라우드 네이티브 환경의 기본 소양(Baseline)이다.
- 향후 방향: 최근에는 가상 스레드(Java 21) 등 구현 난이도를 낮추는 기술이 등장하여 리액티브 철학이 더욱 널리 확산될 전망이다.
