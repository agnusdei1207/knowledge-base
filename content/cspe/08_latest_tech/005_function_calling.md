# 📖 【암기용】 개념 완전 이해

## 한눈에
- **개요**: **Function Calling**(함수 호출)은 개발자가 준 **함수 스키마**(이름·설명·JSON Schema 인자)를 LLM이 읽고, 호출에 필요한 **구조화된 JSON 인자**를 생성해 반환하는 **Tool Use 구현 기법**이다.
- **왜 필요한가**: 도구를 실제로 부르려면 자유 문장이 아니라 파싱 가능한 정확한 인자(예: `{"city":"Seoul","unit":"C"}`)가 필요하다. 모델이 규격에 맞는 JSON을 직접 뽑아 주면, 취약한 정규식·문자열 파싱 없이 함수를 안정적으로 호출할 수 있다.
- **핵심 직관**: "무엇을 도구에 위임할지"라는 개념은 Tool Use(004)에 두고, 여기서는 "모델이 스키마를 받아 호출용 JSON을 어떻게 만들고, 그 결과를 어떻게 되먹여 실행 루프를 도는가"라는 **구체 메커니즘**에 집중한다.

## 핵심 용어 정리 (내부에 등장하는 것들)
답안 본문에 등장하는 용어를 처음 보는 사람도 이해하도록 비유와 함께 먼저 정리한다.

| 용어/표기 | 의미 | 비유·예 |
|:---|:---|:---|
| Function Calling(핵심) | 스키마를 받아 호출용 JSON 인자를 생성하는 Tool Use 구현 기법 | 서식에 맞춰 "신청서 자동 작성" |
| 함수 스키마(Tool Schema) | 함수 이름·용도·인자 구조를 기술한 정의 | 신청서의 "빈칸 양식" |
| JSON Schema | 인자의 타입·필수여부·범위를 규정하는 표준 스펙 | 양식의 "기입 규칙" |
| 구조화 인자(Arguments) | 모델이 만든 `{키:값}` 형태 호출 파라미터 | 다 채운 "신청서 내용" |
| 파서(Parser)/검증기 | 모델이 낸 JSON을 스키마에 맞는지 검사·변환 | 접수처의 "서식 검사원" |
| 함수 실행기(Executor) | 검증된 인자로 실제 함수·API를 호출 | 접수 후 "실제 처리 부서" |
| 실행 루프(Loop) | 인자 생성→실행→결과 반환→재호출 판단 반복 | "채우고 처리하고 다시" 반복 |
| tool_calls / 함수 결과 반환 | 모델 응답의 호출 요청, 실행 결과를 다음 입력으로 되먹임 | 처리 결과를 "회신"해 다음 판단 |
| 병렬 함수 호출 | 한 턴에 여러 함수를 동시에 호출 요청 | 여러 부서에 "동시 신청" |
| 프롬프트 파싱 | JSON 규격 없이 자유 텍스트를 정규식으로 뜯어 인자 추출하던 옛 방식 | 자유 편지에서 "손으로 항목 발췌" |
| 스키마 강제(Constrained Decoding) | 출력이 스키마를 벗어나지 않게 디코딩을 제약 | 양식 밖 기입을 "원천 차단" |

## 깊이 이해
- **배경·문제의식**: Tool Use(004) 초창기에는 모델에게 "도구를 쓰려면 `TOOL: search(query=...)`처럼 써라"고 프롬프트로 지시하고, 그 출력을 정규식으로 뜯어 파라미터를 뽑았다. 그러나 모델이 형식을 조금만 어겨도(따옴표 누락, 설명 문장 혼입) 파싱이 깨졌다. 이 취약함을 없애려고, 모델 자체가 정해진 스키마에 맞는 JSON을 1급 출력으로 내도록 한 것이 Function Calling이다.
- **작동 원리(어떻게+왜)**: ① 개발자가 함수 스키마(이름·설명·JSON Schema 인자)를 요청에 함께 전달한다. ② 모델은 사용자 의도와 스키마를 대조해 어떤 함수를 부를지 정하고, 인자를 스키마 타입에 맞춰 JSON으로 생성한다(모델은 실행하지 않고 호출 요청만 낸다). ③ 애플리케이션이 그 JSON을 스키마로 검증(파싱)한 뒤 실제 함수를 실행한다. ④ 실행 결과를 다시 모델 입력으로 되먹여 최종 답 또는 다음 함수 호출을 판단한다. 이 왕복이 실행 루프이며, JSON을 표준 출력으로 삼기에 정규식 파싱보다 안정적이다.
- **비유**: 민원인이 자유롭게 쓴 편지에서 항목을 손으로 발췌하던 방식(프롬프트 파싱) 대신, 아예 표준 신청서 양식(스키마)을 주고 빈칸을 채우게 하는 것이다. 접수처(파서)는 서식만 검사하면 되고, 실제 처리 부서(실행기)는 채워진 값으로 바로 일한다.
- **구체 예시(실제 프레임워크·표준)**: OpenAI `tools`/`tool_calls`, Anthropic `tools` 블록, Google Gemini function calling이 대표 구현이다. 예: `get_weather(city, unit)` 스키마를 주면 모델이 `{"city":"Seoul","unit":"C"}`를 생성하고, 앱이 검증 후 실제 날씨 API를 호출한다. 최근 구현은 여러 함수를 한 번에 요청하는 병렬 함수 호출과, 출력이 스키마를 벗어나지 못하게 하는 스키마 강제 디코딩을 지원한다.
- **흔한 오해·주의점**: Function Calling은 모델이 함수를 직접 "실행"하는 게 아니라, 실행에 필요한 인자를 "생성"할 뿐이다. 실행·권한·검증은 애플리케이션 몫이다. 또한 모델이 스키마에 없는 필드나 잘못된 타입을 낼 수 있으므로 실행 전 스키마 검증은 필수이며, 생성된 인자를 검증 없이 SQL·셸에 넘기면 인젝션 위험이 생긴다.

## 연결 개념
- Tool Use(004) — Function Calling이 구현하는 상위 개념·패턴
- MCP(006) — 함수 스키마·호출을 여러 앱·서버 간 표준으로 확장한 프로토콜
- ReAct(003)·JSON Schema — 호출 결과를 되먹이는 실행 루프와 인자 규격 표준

## Ⅰ. 개요 및 필요성

- 개요: LLM이 함수 스키마를 읽고 호출용 JSON 인자를 생성하는 Tool Use 구현 기법임
- 배경: 초기 프롬프트 파싱은 형식 이탈에 취약해 정규식 추출이 자주 깨짐
- 필요성: 모델이 스키마에 맞는 JSON을 1급 출력으로 내야 안정적으로 함수를 호출함
- 위치: Tool Use(004) 개념을 구현하는 하위 기법이며 연결 표준은 MCP(006)로 확장됨

---

## Ⅱ. 구조 및 구성요소

- 선형 구조도

```text
함수 스키마 등록 -> LLM(의도·스키마 대조·JSON 인자 생성) -> 파서·검증기(스키마 대조)
  -> 함수 실행기(실제 API·함수 호출) -> 결과 반환 -> LLM(최종 답 또는 다음 호출 판단)
```

| 구성요소 | 역할 | 특이사항 |
|:---|:---|:---|
| 함수 스키마 | 이름·용도·인자 구조 정의 | JSON Schema로 타입·필수 규정 |
| LLM 인자 생성 | 의도에 맞는 함수·JSON 인자 산출 | 실행 아닌 호출 요청만 생성 |
| 파서·검증기 | 인자를 스키마로 검증·정제 | 타입·범위·누락 필드 차단 |
| 함수 실행기 | 검증된 인자로 실제 호출 | RBAC·권한 분리·입력 이스케이프 |

> 요약: 모델은 JSON 인자를 생성하고, 검증기와 실행기가 정합성·실행·권한을 책임지는 분업 구조임.

---

## Ⅲ. 동작원리 및 흐름도

- 선형 흐름도

```text
스키마 전달 -> 함수·인자 결정 -> JSON 인자 생성 -> 스키마 검증 -> 실행 -> 결과 반환·재판단
```

1. 스키마 제공: 호출 가능한 함수 이름·용도·인자 구조를 요청에 포함
2. 인자 생성: 모델이 사용자 의도와 스키마를 대조해 함수·JSON 인자 산출
3. 검증·실행: 파서가 스키마로 검증 후 실행기가 실제 함수 호출
4. 결과 반환: 실행 결과를 모델에 되먹여 최종 답 또는 다음 함수 호출 판단

> 요약: 실행 전 스키마 검증이 인젝션·타입 오류를 막는 정합성의 핵심 단계임.

---

## Ⅳ. 특징

- 구조화 출력: 자유 문장이 아닌 스키마 준수 JSON을 생성해 파싱을 표준화함
- 파싱 안정성: 정규식·문자열 추출을 제거해 형식 이탈로 인한 실패를 줄임
- 실행·생성 분리: 모델은 인자만 만들고 실행·검증·권한은 애플리케이션이 담당함
- 병렬 호출: 한 턴에 여러 함수를 동시에 요청해 다단계 작업을 압축함
- 검증 의존: 스키마 검증이 없으면 잘못된 타입·인젝션이 그대로 실행될 수 있음

## Ⅴ. 심화 비교 및 적용 판단

- 도구 인자를 확보하는 방식 관점에서 옛 프롬프트 파싱과 대비함

| 구분 | 프롬프트 파싱(정규식) | Function Calling |
|:---|:---|:---|
| 인자 형식 | 자유 텍스트에서 발췌 | 스키마 준수 JSON 직접 생성 |
| 안정성 | 형식 이탈 시 파싱 실패 | 스키마 검증으로 정합성 확보 |
| 유지보수 | 프롬프트·정규식 개별 관리 | 스키마 선언으로 일원화 |
| 다중 호출 | 수동 파싱·순차 처리 | 병렬 함수 호출 지원 |
| 오류 처리 | 실패 원인 추적 난이 | 스키마 위반 지점 명확 |

> 요약: 안정적 도구 연동에는 Function Calling이 표준이며, 프롬프트 파싱은 스키마 미지원 모델의 예외적 대체책임.

- 주요 리스크와 대응(불릿)
  - 인자 인젝션: 생성 인자를 무검증으로 SQL·셸 전달이 원인 → 스키마 검증·파라미터 바인딩·이스케이프
  - 스키마 이탈: 없는 필드·잘못된 타입 생성 → JSON Schema 검증·스키마 강제 디코딩
  - 과잉 호출: 병렬·반복 호출 폭주 → 호출 수 상한·비용 한도·타임아웃

- 도입 효과 지표(불릿)
  - 인자 검증 통과율 99% 이상(스키마 검증 성공 비율)
  - 함수 호출 성공률 95% 이상(실행 응답코드 집계)
  - 파싱 실패율 1% 이하(형식 오류 로그 비율)

## Ⅵ. 실무 적용 및 결론

- 적용 방안
  1. OpenAI `tools`·Anthropic tools 블록으로 함수 스키마를 선언하고 JSON Schema로 타입·필수 인자를 강제
  2. 생성된 인자는 실행 전 스키마 검증기를 통과시키고 파라미터 바인딩으로 SQL·셸 인젝션 차단
  3. 함수 실행기에 RBAC·호출 수 상한·타임아웃을 두고 tool_call ID로 요청~결과를 감사 추적
- 결론
  - 기술사 판단: 도구 인자가 정형·검증 대상이면 Function Calling, 스키마 미지원 환경만 프롬프트 파싱을 예외 적용함
  - 향후 방향: Function Calling은 스키마 강제 디코딩과 MCP(006) 표준을 통해 앱·서버 간 상호운용으로 확장됨
