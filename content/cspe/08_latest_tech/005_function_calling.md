# 📖 【암기용】 개념 완전 이해

> 목적: Function Calling을 처음 봐도 완벽히 이해하게 만든다.

## 한눈에
- **개요**: LLM이 정해진 함수명과 인자를 구조화된 형식으로 생성하는 방식
- **왜 필요한가**: 자연어 답변만으로는 API 실행에 필요한 타입·필수값·범위를 일관되게 보장하기 어려움.
- **핵심 직관**: 모델이 “문장” 대신 “실행 가능한 함수 호출 요청서”를 작성함.

## 깊이 이해
- **배경·문제의식**: 도구 호출에서 파라미터 누락, 타입 오류, 임의 텍스트 혼입은 업무 API 장애와 잘못된 실행을 유발함.
- **작동 원리**: 개발자가 함수명·설명·JSON Schema를 제공하고, LLM은 사용자 의도에 맞는 함수와 인자를 생성함.
- **비유**: 콜센터 상담원이 자유문장 메모가 아니라 정해진 신청서 양식에 값을 채워 후속 시스템에 넘기는 구조.
- **구체 예시**: `create_ticket(severity="P1", system="payment", summary="timeout")`처럼 구조화된 호출을 생성함.
- **흔한 오해·주의점**: Function Calling은 실행 자체가 아니라 호출 요청 생성이며, 실제 실행 전 서버 측 검증과 권한 확인이 필요함.

## 연결 개념
- Tool Use — 함수 호출을 포함하는 넓은 개념
- JSON Schema — 인자 검증 형식
- API Gateway — 실제 실행과 인증·인가 담당

# 📝 【답안용】 시험 답안 템플릿

> 목적: 시험장에서 25분에 그대로 쓰는 답안 양식.

## 핵심 인사이트 (3줄 요약)

> 1. **본질**: Function Calling은 LLM 출력값을 함수명·인자·스키마 기반 호출 형식으로 제한하는 기법임.
> 2. **가치**: 자연어 출력을 API 실행 가능한 구조로 바꿔 파라미터 누락과 형식 오류를 줄임.
> 3. **판단 포인트**: 스키마 검증, 서버 측 재검증, 권한 확인, 실패 재시도 정책을 함께 둬야 함.

## 출제 의도 및 답안 포인트

| 출제 의도 | 반드시 짚을 핵심 | 감점 회피 포인트 |
|:---|:---|:---|
| LLM 출력을 구조화된 함수 호출로 제한하는 원리 이해 | JSON Schema, 함수명·인자·타입 정의, 서버 측 재검증 | "함수 호출" 단순 서술 — 스키마 검증·서버 검증 누락 시 감점 |
| 실행 전 검증·권한 확인 설계 역량 확인 | RBAC, 멱등성 키, 트랜잭션 로그, 롤백 절차 | Tool Use와 혼동 금지 — Function Calling은 구조화된 호출 생성 단계 |

> 요약: 출제자는 구조화 호출 원리와 서버 측 검증·권한 설계를 함께 확인하려 함.

---

## Ⅰ. 개요 및 필요성

- 정의: LLM이 함수명과 인자를 구조화된 형식으로 생성하는 방식
- 배경: 자연어 출력만으로는 API 실행에 필요한 타입·필수값·범위를 일관되게 보장하기 어려움
- 필요성: 업무 자동화에서 파라미터 누락·타입 오류·임의 텍스트 혼입을 방지하려면 스키마 기반 검증이 필수임

---

## Ⅱ. 구조 및 구성요소

```text
User Intent -> LLM -> Function Schema -> Function Call JSON
  -> Server Validation -> API 실행 -> 결과 반환
```

| 구성요소 | 역할 | 특이사항 |
|:---|:---|:---|
| Function Schema | 함수명·인자·타입 정의 | JSON Schema, enum 사용 |
| LLM Mapper | 의도를 함수 호출로 변환 | 모호한 값은 재질문 |
| Validator | 필수값·범위·권한 검증 | 서버 측 검증 필수 |
| API Executor | 실제 업무 처리 | 트랜잭션·롤백 필요 |

> 요약: Function Calling은 모델 출력 제어와 서버 검증을 결합해야 실행 가능한 구조가 됨.

---

## Ⅲ. 동작원리 및 흐름도

```text
사용자 요청 → 함수 후보 선택 → 인자 생성 → 스키마 검증
        → 권한 확인 → API 실행 → 결과 반환
```

| 단계 | 처리 내용 | 검증 기준 |
|:---:|:---|:---|
| 1 | 사용자 의도 분석 | 함수 후보, 필수 파라미터 |
| 2 | 구조화 인자 생성 | 타입, enum, 길이 제한 |
| 3 | 서버 측 검증 | RBAC, 입력 범위, 정책 |
| 4 | 실행·결과 처리 | 응답코드, 롤백, 감사로그 |

> 요약: 함수 호출은 LLM 생성 후 서버 검증을 통과해야 실제 API 실행으로 이어짐.

## Ⅳ. 특징

| 구분 | 자연어 출력 | Function Calling | 수치·판단 포인트 |

| 형식 | 자유 텍스트 | JSON 인자 | 스키마 오류율 |

> 요약: Function Calling은 자연어를 실행 형식으로 제한하지만 최종 보안은 서버 검증이 담당함.

## Ⅴ. 심화 비교 및 적용 판단

| 비교 축 | 자연어 출력 | Function Calling | 선택 기준 |
|:---|:---|:---|:---|
| 형식 | 자유 텍스트 | JSON 인자 (함수명·타입·enum) | API 연계 필요 여부 |
| 검증 | 프롬프트 의존 | 스키마+서버 재검증 | 입력 오류 허용 범위 |
| 통제 | 출력 후처리 필요 | RBAC·멱등성·트랜잭션 | 변경형 API 존재 여부 |

> 요약: API 연계와 입력 검증이 필요하면 Function Calling, 단순 텍스트면 자연어 출력을 선택함.

| 리스크 | 원인 | 대응 방안 | 확인 지표 |
|:---|:---|:---|:---|
| 스키마 오류 | 필수값 누락·타입 불일치 | JSON Schema 필수값·enum·min/max 명시 | 스키마 검증 통과율 98% 이상 |
| 무단 실행 | 모델 출력을 검증 없이 실행 | 서버 측 RBAC·업무 규칙 재검증 필수 | 서버 검증 건너뛴 건수 0건 |
| 장애 확산 | 변경형 함수 실패 시 롤백 부재 | idempotency key·트랜잭션 로그·롤백 절차 | 롤백 성공률 99% 이상 |

> 요약: 스키마 오류·무단 실행·장애 확산이 주요 리스크이며, 스키마 검증·서버 재검증·롤백으로 통제함.

| 점검 항목 | 목표 기준 | 측정 방법 |
|:---|:---|:---|
| 스키마 검증 통과율 | 98% 이상 | 검증 성공/실패 로그 집계 |
| 서버 측 검증 건너뛴 | 월간 0건 | RBAC 감사 로그 |
| 변경형 함수 롤백 성공률 | 99% 이상 | 트랜잭션 로그 분석 |

> 요약: 스키마 통과율·검증 건너뛴·롤백 성공률으로 Function Calling 도입 효과를 정량 평가함.

---

## Ⅵ. 실무 적용 및 결론

**적용 방안 3개:**
1. 모든 함수 인자에 JSON Schema, enum, min/max, nullable 정책을 명시
2. 모델 출력은 신뢰하지 않고 API 서버에서 RBAC, 업무 규칙, 중복 요청 방지를 재검증
3. 변경형 함수는 idempotency key, 트랜잭션 로그, 롤백 절차를 포함해 장애 영향을 제한

**결론 (2줄):**
- 기술사 판단: 조회형 함수는 자동 실행, 변경형 함수는 승인·멱등성·롤백 조건 충족 시 적용함.
- 향후 방향: Function Calling은 MCP와 결합해 모델-도구 간 표준 실행 인터페이스로 확장됨.
