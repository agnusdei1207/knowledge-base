## 미리 알고가기

- 토큰 처리량 ($Token$ $Throughput$): 단위 시간(보통 1초) 동안 LLM 서빙 시스템이 전체 사용자 세션을 대상으로 연산해 낸 입력(프리필) 및 출력(디코드) 토큰의 총합 수량 지표임
- 동접 배치 관리 ($Concurrency$): GPU 장치 내부에서 여러 명의 사용자 요청을 동시 병렬 배칭하여 연산 장치 활용도를 극대화하는 멀티 세션 가동 상태임
- 혼합 워크로드 ($Request$ $Mix$): 입력이 극도로 길고 출력이 짧은 RAG 요청과, 입력은 짧지만 출력이 긴 추론(CoT) 요청 등이 서버에 불규칙하게 뒤섞여 들어오는 부하 양상임
- 용량 산정 ($Capacity$ $Planning$): 예상 동시 접속자 수와 사용량 패턴을 바탕으로 인프라(GPU 서버 대수) 및 가용 서빙 스펙을 통계 계산하여 구축 예산을 확보하는 장기 인프라 기획임

## Ⅰ. 개요

- **정의/개념**: Token Throughput은 대형 언어 모델 서빙 시스템이 초당($1$ $Second$) 인코딩 및 디코딩하여 배출해 내는 총 토큰 수($Tokens/Sec$)이며, 서버의 하드웨어 자원 효율성과 최대 동접 처리 용량을 입증하는 가장 객관적인 시스템적 생산성 지표임
- **배경/필요성**: 서비스 운영자 관점에서는 개별 요청의 처리 속도($TTFT$, $TPOT$)만 측정하면 서버 1대가 감당할 수 있는 전체적인 사용량과 인프라 가성비를 알 수 없으므로, 하드웨어 투자대비 수익성($ROI$)과 서비스의 동시 스케일 아웃 한계를 규명하기 위해 필수 관리됨

## Ⅱ. 특징

- 스케줄러의 동적 배칭 효율, GPU 텐서 코어의 실질 가동률, PagedAttention의 메모리 블록 재사용율에 따라 수치가 정비례하여 결정됨
- 개별 사용자 반응 지연 시간($Latency$)과는 반비례하는 트레이드오프가 존재하므로, 처리량을 무한정 높이면 개별 서비스 응답성이 오히려 손상될 수 있음
- 학습용 코퍼스 훈련과 추론($Inference$) 서비스 양단에서 하드웨어 서버의 절대 가성비를 대변하는 벤치마킹 표준 잣대로 사용됨

## Ⅲ. 종류 및 비교

| 판단 기준 | 최초 토큰 지연 (TTFT) | 토큰당 출력 지연 (TPOT) | 토큰 처리량 (Token Throughput) |
|:---|:---|:---|:---|
| **지표의 물리 단위** | 밀리초 ($ms$) | 밀리초/토큰 ($ms/token$) | 초당 처리 토큰수 ($tokens/sec$) |
| **측정 대상 범위** | 1개 세션의 초기 대기 | 1개 세션의 단어 생성 속도 | 서버 전체 세션의 총 생산량 합계 |
| **인프라 관측 의의** | 사용자 첫인상 및 이탈 감사 | 스트리밍 끊김 및 UX 적합성 | GPU 장비 자원 포화도 및 가성비 판정 |
| **가장 민감한 요인** | 스케줄 큐 대기 시간 | 물리 메모리 반도체 대역폭 | 병렬 배치 크기, 가상 페이지 할당력 |

> 요약: TTFT와 TPOT은 고객 친화적 반응성이고, Token Throughput은 기업 친화적 인프라 수지 효율 지표임.

## Ⅳ. 구성요소 및 구조

| 구성요소 | 설명 |
|:---|:---|
| 혼합 요청 큐 | 실시간으로 흘러 들어오는 가변 입력/출력 쿼리들을 모으는 부하 수집 통로임 |
| 동적 배칭 스케줄러 | GPU 가동율을 $95\%$ 이상으로 묶어 두기 위해 매 토큰 스텝마다 배치를 재결합하는 분배기임 |
| 가중치/캐시 I/O 엔진 | HBM 메모리 병목을 극복하며 가중치 행렬을 온칩 코어에 실어나르는 가속 엔진임 |
| 처리량 계측 모니터 | 시간 틱($Tick$) 단위로 처리 완료된 토큰 누적 합을 계산해 릴리즈하는 관측 데몬임 |

```text
[ LLM 서빙 시스템 생산성 측정 영역 ]
Incoming Queries ---> [Dynamic Scheduler] ---> GPU [Inference Engine] ---> [Output Tokens] -> Monitor (Total Tokens / Sec)
                      |<------------- VRAM & Tensor Cores Maximize ------------>|
```

## Ⅴ. 원리 및 절차 흐름도

```text
+-------------+     +--------------+     +-------------+     +-------------+
| 다중 질의   | --> | 토큰 스텝별  | --> | 병렬 연산 및| --> | 시간단위    |
| 큐 적재     |     | 동적 배칭조립|     | 토큰 배출   |     | 처리합산 산출|
+-------------+     +--------------+     +-------------+     +-------------+
```

1. **작업 큐 대기** — 사용자들이 보낸 수많은 질문들이 큐에 쌓이면, 각 프롬프트의 토큰 크기를 실시간 분석하여 배치 우선순위를 잡음
2. **배치 압축 적재** — 연속 배칭 스케줄러를 구동하여 GPU 연산 텐서 크기에 밀착하도록 활성 세션들을 하나의 대형 배치 행렬로 병합함
3. **병렬 연산 구동** — FlashAttention과 PagedAttention 커널을 구동해, 묶인 세션들의 프리필과 디코드 과정을 한 번에 동시 다발 처리함
4. **통계 합산** — 매 초마다 서버 인터페이스를 통과한 인코딩/디코딩 토큰 갯수를 합산하여 최종 토큰 처리량($Throughput$)을 콘솔에 보고함

## Ⅵ. 실무 적용 및 유의점

1. 토큰 처리량 수치만을 억지로 극대화하기 위해 배치 크기 상한을 지나치게 높게 설정하면, GPU 램 버스 대역폭 초과로 개별 사용자들의 TPOT 지연이 $100$ms 이상으로 늘어나 실시간 스트리밍이 멈추므로, 반드시 '처리량-지연 한계 분석 곡선'을 측정하고 p95 TPOT이 마지노선 내로 방어되는 sweet-spot 배치 크기로 제어해야 함
2. 입력 프롬프트가 거대한 RAG 요청(Prefill-heavy)과 답변이 장황한 요약 요청(Decode-heavy)은 동일한 토큰 처리량 수치를 보이더라도 GPU의 전력 소모와 병목 성격이 완전히 다르므로, 반드시 프리필과 디코드의 처리량을 이원화하여 분리 측정하고 '용량 산정($Capacity$ $Planning$)' 모델에 개별 반영해야 함

## Ⅶ. 결론

- 토큰 처리량은 인공지능 서비스 인프라의 단위 요금당 수용율을 나타내는 최고 경제적 지표이며, 설계자는 단독 수치의 눈속임에 속아 개별 고객 지연($Latency$)이 파괴되지 않도록 QoS 정책 수립과 프리필/디코드 분리 계측 체계를 수립해 가성비 높고 쾌적한 추론 플랫폼을 서빙해야 함
