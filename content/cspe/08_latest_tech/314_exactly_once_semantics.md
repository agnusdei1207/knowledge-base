# 📖 【암기용】 개념 완전 이해

> 목적: Exactly-Once를 처음 봐도 완벽히 이해하게 만든다. 시험 답안 양식이 아니라, 이해를 위한 친절한 설명이다.

## 한눈에
- **개요**: 시스템에 장애가 발생하더라도 데이터가 '중복'되거나 '유실'되지 않고, 결과적으로 '정확히 한 번'만 처리된 것과 같은 상태를 보장하는 기술
- **왜 필요한가**: 금융 결제나 포인트 적립 같은 시스템에서 네트워크 장애로 재전송이 일어날 때, 돈이 두 번 빠져나가거나 아예 안 빠져나가는 일이 없어야 하기 때문이다.
- **핵심 직관**: "장애가 몇 번이 나든, 최종 결과는 아무 일 없었던 것처럼 완벽하게 하나만 기록되는 마법 같은 정합성."

## 깊이 이해
- **배경·문제의식**: 분산 시스템에서는 '메시지 전송 성공' 여부를 확신하기 어려움. 보냈는데 응답이 없으면, 안 간 건지(Lost) 갔는데 응답만 안 온 건지 알 수 없음. 이때 다시 보내면 중복(At-least-once), 안 보내면 유실(At-most-once)의 위험이 있음.
- **작동 원리**: 단순히 한 번 보낸다는 뜻이 아니라, '결과가 한 번만 반영된다'는 뜻임. 이를 위해 ① **멱등성(Idempotence)**: 여러 번 수행해도 결과가 같은 작업 구조, ② **2단계 커밋(2PC)**: 준비와 확정 단계 분리, ③ **체크포인팅**: 상태를 주기적으로 백업하여 장애 시 해당 시점부터 재개하는 기술 등을 복합적으로 사용함.
- **비유**: 은행 ATM 입금과 같음. 돈을 넣다가 기계가 꺼져도, 다시 켰을 때 내 통장에 돈이 두 번 찍히거나 안 찍히는 일 없이, 정확히 넣은 금액만큼만 기록되도록 설계된 시스템.
- **구체 예시**: 카프카(Kafka)에서 `enable.idempotence=true` 설정을 하면, 네트워크 오류로 같은 메시지가 여러 번 가도 카프카 브로커가 "이미 받은 거네" 하고 중복을 제거함.
- **흔한 오해·주의점**: 물리적으로 '딱 한 번만 전송'하는 것은 네트워크 세상에서 불가능에 가까움. "여러 번 전송될 수는 있지만, 최종 상태 변화는 한 번만 일어난 것처럼 만든다"는 것이 실질적인 의미임.

## 연결 개념
- At-Least-Once - 최소 한 번 (중복 허용, 유실 불가)
- At-Most-Once - 최대 한 번 (유실 허용, 중복 불가)
- Idempotence (멱등성) - Exactly-Once를 구현하는 핵심 속성

# 📝 【답안용】 시험 답안 템플릿

> 목적: 시험장에서 25분에 그대로 쓰는 답안 양식. 작성방식(추상표현 금지·수치·도식·문제유형 전환)을 엄격히 지킨다.
> 핵심: 3가지 메시징 전달 보장 수준(At-most, At-least, Exactly)을 비교하고, 구현 기술인 Idempotent Producer, Two-phase Commit(2PC), Checkpointing 메커니즘을 상세히 논한다.

## 핵심 인사이트 (3줄 요약)

> 1. **본질**: Exactly-Once Semantics는 분산 처리 환경에서 발생할 수 있는 장애 상황에도 불구하고 모든 데이터가 중복이나 누락 없이 결과에 반영됨을 보장하는 최상위 신뢰성 수준이다.
> 2. **가치**: 중복 처리로 인한 데이터 오염과 유실로 인한 비즈니스 손실을 방지하여 금융, 결제, 정산 등 고정밀 데이터 처리를 가능하게 한다.
> 3. **판단 포인트**: 메시지 생성자(Producer), 브로커(Broker), 소비자(Consumer) 전 구간에 걸친 협력적 트랜잭션 메커니즘 구현 여부가 핵심이다.

## 출제 의도 및 답안 포인트

| 출제 의도 | 반드시 짚을 핵심 | 감점 회피 포인트 |
|:---|:---|:---|
| 데이터 전달 보장 수준(Delivery Guarantees) 비교 | At-most, At-least, Exactly-once 정의 및 차이 | 단순히 용어 정의에만 그침 |
| Exactly-once 구현 기술 메커니즘 파악 | 멱등성(Idempotence), 2단계 커밋(2PC), 체크포인팅 | 구현 기술 간의 유기적 관계 설명 누락 |
| 실무적 트레이드오프 인식 확인 | 성능 저하(오버헤드)와 신뢰성 사이의 선택 기준 | 무조건 "Exactly-once가 필수"라고 서술 지양 |

> 요약: Exactly-Once는 멱등적 처리와 트랜잭션 관리를 통해 장애 시에도 논리적 일관성을 유지하는 기술적 약속이다.

## Ⅰ. 개요 및 필요성

- 정의: 데이터 처리 중 장애가 발생하더라도 결과 시스템에 데이터가 중복되거나 유실되지 않고 단 한 번만 반영되는 보장 수준
- 배경: 분산 시스템의 비결정론적 네트워크 장애, 재전송 메커니즘으로 인한 데이터 중복 발생 가능성
- 필요성: 금융 거래 및 정산의 정확성 확보, 중복 데이터 제거를 위한 사후 처리 비용 절감, 데이터 신뢰도 향상

---

## Ⅱ. 구조 및 구성요소 (전 구간 보장 체계)

```text
[ Producer ] ----> [ Messaging Broker ] ----> [ Consumer / Sink ]
      |                    |                         |
 (1) Idempotence      (2) Transaction Log       (3) Atomic Commit
 - 시퀀스 번호 부여    - 상태 관리 및 복제        - 쓰기 작업과 오프셋 갱신 결합
```

| 구성요소 | 역할 | 특이사항 |
|:---|:---|:---|
| Idempotent Producer | 동일 메시지 재전송 시 브로커에서 중복 제거 | 시퀀스 번호(PID + Seq) 활용 |
| Transaction Manager | 여러 파티션/토픽에 대한 쓰기를 원자적으로 관리 | 트랜잭션 코디네이터 역할 |
| Two-phase Commit | 준비(Prepare)와 확정(Commit)의 2단계 제어 | 분산 시스템 간 상태 동기화 |
| State Snapshot | 장애 시 복구할 마지막 성공 시점의 상태 저장 | Flink의 체크포인트 등 |

> 요약: 메시지의 고유 식별과 처리 상태의 원자적 기록을 통해 전 구간 무결성을 확보한다.

## Ⅲ. 동작원리 및 흐름도 (Kafka Transaction 예시)

```text
Begin Trans -> [ 1. Write Data ] -> [ 2. Offset Commit ] -> [ 3. End Trans ]
                     |                       |                     |
              (데이터 미노출)          (준비 상태 기록)        (모두가 보게 함)
                     |                       |                     |
        [ 5. Rollback ] <- [ 4. 장애 발생 시 지점 복구 ] <----------+
```

| 단계 | 처리 내용 | 검증 기준 |
|:---:|:---|:---|
| 1 | 트랜잭션 시작 | 고유한 Transactional ID를 할당받고 시작 알림 | - |
| 2 | 메시지 전송 | 데이터를 보내되, '커밋 전' 상태로 마킹하여 읽기 제한 | Isolation Level 설정 |
| 3 | 오프셋 기록 | 소비한 위치(Offset)를 트랜잭션 범위 내에서 기록 | 데이터와 위치 정보의 동기화 |
| 4 | 트랜잭션 커밋 | 모든 작업이 성공하면 '커밋' 마커를 기록하여 가시화 | 원자성(Atomicity) 완성 |
| 5 | 장애 복구 | 커밋되지 않은 메시지는 무시하고 마지막 커밋 시점부터 재개 | 중복/유실 방지 |

> 요약: 데이터 쓰기와 읽은 위치 기록을 하나의 트랜잭션으로 묶어 '모두 성공' 아니면 '모두 실패'로 처리한다.

## Ⅳ. 특징 (보장 수준별 비교)

| 구분 | At-Most-Once (최대 한 번) | At-Least-Once (최소 한 번) | Exactly-Once (정확히 한 번) |
|:---|:---|:---|:---|
| 유실 가능성 | 있음 (장애 시 유실) | 없음 | 없음 |
| 중복 가능성 | 없음 | 있음 (장애 시 중복) | 없음 |
| 성능 (처리량) | 매우 높음 | 높음 | 상대적 낮음 (오버헤드 발생) |
| 구현 복잡도 | 낮음 | 중간 | 높음 |
| 주요 용도 | 단순 로그, 센서 데이터 | 일반적인 메시지 처리 | 금융, 결제, 정산 |

> 요약: 신뢰성이 높아질수록 시스템 복잡도와 성능 비용이 증가하는 트레이드오프 관계가 존재한다.

## Ⅴ. 심화 비교 및 적용 판단

| 구분 | 멱등성 (Idempotence) | Exactly-Once Semantics | 선택 기준 |
|:---|:---|:---|:---|
| 범위 | 단일 쓰기 작업 | 전 주기 파이프라인 (End-to-End) | 시스템 전체 무결성 요건 |
| 구현 방식 | 시퀀스 번호 중복 체크 | 트랜잭션, 2PC, 스냅샷 결합 | 처리 로직의 복잡성 |
| 실패 대응 | 단순 재전송 및 무시 | 롤백 및 상태 복구 | 데이터 유실/중복 민감도 |
| 성능 영향 | 미미함 | 상대적으로 큼 (Commit 대기) | 허용 가능한 지연 시간 |

> 요약: 멱등성은 Exactly-Once를 구현하기 위한 '수단'이며, Exactly-Once는 시스템의 '목표 상태'이다.

| 리스크 | 원인 | 대응 방안 | 확인 지표 |
|:---|:---|:---|:---|
| 지연 시간 증가 | 트랜잭션 커밋 대기 및 오버헤드 | 트랜잭션 범위 최적화, 배치 크기 조정 | End-to-End Latency |
| 처리량 감소 | 분산 환경의 코디네이션 비용 | 멱등성 위주의 설계(Idempotent Sink)로 대체 | Throughput (TPS) |
| 좀비 인스턴스 | 죽은 프로듀서의 뒤늦은 쓰기 시도 | 에포크(Epoch) 번호를 통한 구버전 차단 | Zombie Fencing 발생 빈도 |

> 요약: 성능 저하를 최소화하기 위해 '트랜잭션 크기'와 '팬싱(Fencing) 메커니즘' 튜닝이 중요하다.

| 점검 항목 | 목표 기준 | 측정 방법 |
|:---|:---|:---|
| 데이터 정합성 | 중복 및 누락 건수 0건 | 데이터 검수 및 중복 체크 쿼리 |
| 장애 복구 성공률 | 자동 복구 후 정합성 유지 100% | 카오스 엔지니어링(장애 주입) 테스트 |
| 성능 유지율 | 일반 처리 대비 성능 하락 20% 이내 | 벤치마크 (TPS 비교) |

> 요약: 도입 효과는 데이터의 무결성 수치와 비즈니스 신뢰도로 평가한다.

## Ⅵ. 실무 적용 및 결론

**적용 방안 3개:**
1. **멱등적 싱크(Idempotent Sink) 활용**: 대상 DB(예: HBase, Cassandra)의 Upsert 기능을 활용하여 자연스럽게 중복을 제거하는 Exactly-once 구현
2. **카프카-플링크 통합**: 카프카의 트랜잭션과 플링크의 체크포인트를 연동하여 소스부터 싱크까지 전체 구간 Exactly-once 달성
3. **분산 트랜잭션 최소화**: 가급적 도메인을 분리하여 분산 트랜잭션 범위를 좁히고, 비즈니스 로직 자체를 멱등하게 설계하여 기술적 부하 경감

**결론 (2줄):**
- 기술사 판단: Exactly-Once는 기술적 완결성을 넘어 비즈니스의 법적/재무적 리스크를 통제하는 핵심 장치이며, 시스템 설계 단계부터 내재화되어야 한다.
- 향후 방향: 하드웨어 가속 및 합의 알고리즘 개선으로 Exactly-Once의 성능 오버헤드가 감소함에 따라, 고신뢰 시스템의 기본 사양(Default)으로 자리 잡을 것이다.
