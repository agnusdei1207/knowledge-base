# 📖 【암기용】 개념 완전 이해

## 한눈에
- **개요**: **ReAct**(Reasoning and Acting)는 **LLM**이 한 번의 추론으로 끝내지 않고, **Thought(추론)-Action(도구 실행)-Observation(결과 관찰)**을 번갈아 반복해 문제를 푸는 **프롬프팅·추론 패턴**이다.
- **왜 필요한가**: LLM의 내부 지식만으로 하는 추론(CoT)은 최신 데이터·계산·시스템 상태를 모른다. 실제 결과를 관찰해 다음 추론에 반영해야 환각이 줄고 다단계 문제가 풀린다.
- **핵심 직관**: "생각 → 도구로 확인 → 결과 보고 → 다시 생각"의 짧은 루프다. 에이전트 시스템(001)·에이전틱 패러다임(002)이 큰 그림이라면, ReAct는 그 안에서 LLM이 실제로 도는 최소 실행 단위다.

## 핵심 용어 정리 (내부에 등장하는 것들)
답안 본문에 나오는 용어를 먼저 비유와 함께 정리한다.

| 용어/표기 | 의미 | 비유·예 |
|:---|:---|:---|
| ReAct(핵심) | Thought-Action-Observation을 반복해 추론과 도구 실행을 엮는 패턴 | "생각하고, 확인하고, 다시 생각하는" 탐정 |
| LLM | 언어를 이해·생성하는 신경망. ReAct에서 Thought를 생성하는 주체 | 추리를 하는 "두뇌" |
| Thought(추론) | 다음에 무엇을 할지 언어로 판단하는 단계 | 탐정의 "혼잣말 추리" |
| Action(행동) | 정해진 형식으로 도구·API를 호출하는 단계 | 현장에 나가 "증거 수집" |
| Observation(관찰) | 도구가 돌려준 결과(데이터·오류)를 받는 단계 | 수집한 "증거 확인" |
| Tool Use(도구 호출) | 검색·계산·DB·API 등 외부 기능을 부르는 것. Action의 실체 | 두뇌가 쓰는 "연장" |
| CoT(Chain-of-Thought) | 도구 없이 추론 과정만 단계적으로 전개하는 기법 | 머릿속으로만 "암산 풀이" |
| Plan-and-Execute | 먼저 전체 계획을 세우고 그 뒤 순차 실행하는 패턴 | 여행 일정 다 짜고 "그대로 실행" |
| Reflexion | 실패 결과를 언어 피드백으로 남겨 다음 시도를 개선하는 확장 | 경기 후 "리뷰 노트" |
| 종료조건(Stop condition) | 답 도출·최대 반복·비용 한도 등 루프를 멈추는 규칙 | "N번까지만 시도" |
| allowlist/JSON Schema | 호출 가능한 도구·입력 형식을 사전 제한하는 안전장치 | 정해진 "양식·허가 목록" |
| Prompt Injection | Observation에 악성 지시를 넣어 다음 Thought를 오염시키는 공격 | 위조 증거로 "수사 오도" |

## 깊이 이해
- **배경·문제의식**: CoT는 "단계적으로 생각하자"고 유도해 추론 정확도를 높였지만, 어디까지나 모델이 학습한 지식 안에서만 논리를 전개한다. 오늘 환율, 방금 배포 이력, 특정 계정 잔액 같은 외부 사실은 알 수 없어 그럴듯한 환각을 만든다. 그래서 "생각"과 "실제 확인(도구 실행)"을 한 루프에 엮자는 발상이 ReAct다(2022년, Yao 등).
- **작동 원리(어떻게+왜)**: LLM이 Thought에서 "무엇을 모르는지, 무슨 도구가 필요한지"를 판단하고, Action에서 그 도구를 호출한다. 도구가 돌려준 Observation을 다음 프롬프트에 이어 붙여 다시 Thought를 생성한다. 관찰된 사실이 추론의 근거가 되므로, 매 루프마다 모델의 판단이 실제 데이터로 교정된다. 이 인터리빙(교차 반복)이 순수 추론 대비 환각을 줄이고, 순수 도구 호출 대비 "왜 그 도구를 부르는지" 판단 근거를 남긴다.
- **비유**: 장애 대응자가 "원인이 배포일 것 같다(Thought)" → 배포 로그를 조회(Action) → "3시간 전 배포 확인(Observation)" → "그럼 롤백 이력을 보자(Thought)"로 이어가는 방식이다. 머릿속 추측만 하지도, 무작정 명령만 치지도 않는다.
- **구체 예시(실제 프레임워크·사례)**: LangChain의 ReAct Agent, LlamaIndex의 ReActAgent가 이 패턴을 프롬프트 템플릿으로 구현한다. 예: "매출 급감 원인 분석"에서 매출 DB 조회 → 배포 이력 확인 → 결제 오류 로그 확인을 Thought-Action-Observation으로 순차 수행한다.
- **흔한 오해·주의점**: ReAct는 시스템 아키텍처(001)나 자율성 패러다임(002)이 아니라, 그 안에서 도는 "프롬프트 수준 추론-행동 루프"다. 또한 Thought(내부 추론)를 사용자에게 그대로 노출하면 내부 정책·프롬프트가 유출되므로, 사용자 출력과 감사 로그를 분리해야 한다. Observation에 악성 지시가 섞이는 간접 프롬프트 인젝션도 주의한다.

## 연결 개념
- AI 에이전트 시스템(001)·에이전틱 AI(002) — ReAct 루프가 실제로 동작하는 상위 시스템·패러다임
- CoT·Reflexion — ReAct의 선행 추론 기법과 자기개선 확장
- Prompt Injection·Tool Use — Observation 오염 위협과 Action의 실행 수단

# 📝 【답안용】 시험 답안 템플릿

## 핵심 인사이트 (3줄 요약)

> 1. **본질**: ReAct는 Thought-Action-Observation 루프로 LLM 추론과 외부 도구 실행을 인터리빙하는 프롬프팅 패턴임.
> 2. **가치**: 순수 추론(CoT)의 환각과 순수 도구 호출의 근거 부재를 동시에 보완함.
> 3. **판단 포인트**: 도구 결과 신뢰성·루프 종료조건·내부 추론 노출 통제를 함께 설계해야 함.

## 출제 의도 및 답안 포인트

## Ⅰ. 개요 및 필요성

- 개요: LLM이 추론과 도구 실행을 번갈아 반복하는 프롬프팅·추론 패턴임
- 배경: CoT는 학습 지식 내 추론만 가능해 외부 사실·시스템 상태를 반영 못함
- 필요성: 관찰된 실제 데이터를 추론에 되먹여야 환각이 줄고 다단계 정확도가 향상됨
- 위치: 에이전트 시스템(001)·에이전틱(002) 안에서 LLM이 도는 최소 실행 루프임

---

## Ⅱ. 구조 및 구성요소

- 선형 구조도

```text
User Goal -> Thought(다음 행동 판단) -> Action(도구 호출) -> Observation(결과 수신)
  -> 종료조건 검사 -> 미충족 시 Thought로 반복 / 충족 시 최종 답변
```

| 구성요소 | 역할 | 특이사항 |
|:---|:---|:---|
| Thought | 다음 행동·필요 도구를 언어로 판단 | 내부 로그와 사용자 출력 분리 |
| Action | 검색·계산·API 등 도구 호출 | allowlist·JSON Schema로 제한 |
| Observation | 도구 결과·오류 수신 | 출처·응답코드·신뢰도 확인 |
| Stop Rule | 종료 판단 | 최대 반복·비용 한도 설정 |

> 요약: 관찰 결과가 다음 Thought의 입력이 되는 인터리빙 폐루프임.

---

## Ⅲ. 동작원리 및 흐름도

- 선형 흐름도

```text
질문 수신 -> Thought 생성 -> Action 선택·실행 -> Observation 반영 -> 종료 판단 -> 답변 또는 다음 루프
```

1. 문제 해석: 요구사항·금지 행동·필요 정보 식별
2. 추론·행동 선택: Thought로 도구명·입력 파라미터 결정(JSON Schema 검증)
3. 실행·관찰: 도구 호출 후 응답코드·출처·지연·신뢰도 확인
4. 종료 판단: 답 도출·최대 반복·비용 한도 도달 시 종료, 아니면 재추론

> 요약: 관찰 결과가 다음 추론의 근거이므로 Observation 검증이 최종 품질을 좌우함.

---

## Ⅳ. 특징

- 인터리빙: 추론과 도구 실행을 교차 반복해 판단을 실제 데이터로 교정함
- 환각 저감: Observation의 사실을 근거로 삼아 CoT 대비 환각을 줄임
- 근거 추적: Thought가 "왜 그 도구를 불렀는지" 판단 이유를 로그로 남김
- 통제 필요: 실행 능력이 생기는 대신 종료조건·도구 권한 설계가 필수가 됨
- 노출 위험: Thought를 그대로 출력하면 내부 정책·프롬프트가 유출될 수 있음

## Ⅴ. 심화 비교 및 적용 판단

- 추론 패턴 관점에서 CoT·Plan-and-Execute와 대비함

| 구분 | CoT | Plan-and-Execute | ReAct |
|:---|:---|:---|:---|
| 도구 사용 | 없음(내부 추론만) | 계획 후 일괄 실행 | 매 단계 추론 직후 호출 |
| 적응성 | 고정 추론 체인 | 계획 확정 후 경직 | 관찰마다 경로 재조정 |
| 외부 사실 | 반영 불가 | 실행 단계에서 반영 | 매 루프 즉시 반영 |
| 오버헤드 | 최저 | 계획 1회+실행 | 루프마다 LLM 호출 다수 |

> 요약: 실시간 관찰·재조정이 필요하면 ReAct, 단순 추론은 CoT, 안정된 다단계 절차는 Plan-and-Execute가 적합함.

- 주요 리스크와 대응(불릿)
  - 루프 폭주: 종료조건 미설정·도구 반복 실패가 원인 → 최대 반복 5회·작업당 비용 한도
  - Thought 유출: 내부 추론을 사용자에 그대로 출력이 원인 → 감사 로그와 사용자 출력 분리
  - Observation 오염: 도구 결과에 악성 지시 삽입(간접 인젝션) → 결과를 데이터로만 처리·인젝션 필터

- 도입 효과 지표(불릿)
  - 작업 완료율 90% 이상(종료 사유별 로그 분석)
  - 도구 호출 성공률 95% 이상(Trace ID별 응답코드 집계)
  - 평균 루프 3회 이내(작업별 루프 카운트)

---

## Ⅵ. 실무 적용 및 결론

- 적용 방안
  1. LangChain ReAct Agent로 구현하되 Thought는 내부 감사 저장소에만 보관하고 사용자에겐 근거·결과·출처만 출력
  2. Action은 allowlist·JSON Schema·최대 5회 루프·작업당 비용 한도로 제한
  3. Observation은 출처 URL·API 응답코드·Timestamp를 포함해 재현 가능한 로그로 저장
- 결론
  - 기술사 판단: 외부 검증·실시간 조회가 필요한 업무는 ReAct, 단순 요약·추론은 CoT를 적용함
  - 향후 방향: ReAct는 MCP 도구 표준화·Reflexion 자기개선과 결합해 에이전트 실행 패턴의 기본 구조가 됨
