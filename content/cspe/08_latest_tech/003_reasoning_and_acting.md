# 📖 【암기용】 개념 완전 이해

> 목적: ReAct 패턴을 처음 봐도 완벽히 이해하게 만든다.

## 한눈에
- **개요**: LLM이 추론(Reasoning)과 행동(Acting)을 번갈아 수행하는 에이전트 패턴
- **왜 필요한가**: 복잡한 문제는 내부 추론만으로 부족하며, 검색·계산·시스템 조회 결과를 반영해야 함.
- **핵심 직관**: 생각하고, 도구를 쓰고, 결과를 보고, 다시 생각하는 반복 구조임.

## 깊이 이해
- **배경·문제의식**: Chain-of-Thought는 추론 흔적을 만들지만 외부 사실 확인과 시스템 실행이 없음.
- **작동 원리**: Thought로 다음 행동을 정하고, Action으로 도구를 호출하며, Observation으로 결과를 받아 다음 Thought에 반영함.
- **비유**: 장애 대응자가 원인을 추정하고 로그를 조회한 뒤 결과를 보고 다음 점검 항목을 고르는 방식.
- **구체 예시**: “매출 급감 원인 분석”에서 DB 조회, 배포 이력 확인, 결제 오류 로그 확인을 순차 수행함.
- **흔한 오해·주의점**: Thought를 그대로 노출하면 내부 정책·프롬프트가 유출될 수 있어 사용자 출력과 감사 로그를 분리해야 함.

## 연결 개념
- Tool Use — Action 단계의 실행 수단
- RAG — Observation을 지식 검색으로 보강
- Prompt Injection — 도구 결과가 다음 추론을 오염시키는 공격

# 📝 【답안용】 시험 답안 템플릿

> 목적: 시험장에서 25분에 그대로 쓰는 답안 양식.

## 핵심 인사이트 (3줄 요약)

> 1. **본질**: ReAct는 Thought-Action-Observation 루프로 LLM 추론과 외부 도구 실행을 결합하는 패턴임.
> 2. **가치**: 정적 답변이 아니라 조회·검증·수정이 필요한 다단계 문제 해결에 적합함.
> 3. **판단 포인트**: 도구 결과 신뢰성, 루프 종료조건, 내부 추론 노출 통제를 함께 설계해야 함.

## 출제 의도 및 답안 포인트

| 출제 의도 | 반드시 짚을 핵심 | 감점 회피 포인트 |
|:---|:---|:---|
| LLM 에이전트의 추론-실행 결합 구조 이해 확인 | Thought-Action-Observation 루프, 도구 호출 통제, 종료 조건 | CoT와 혼동 금지, 루프 폭주 통제 누락 시 감점 |
| 도구 연동 시 안전성 설계 역량 확인 | allowlist, JSON Schema, 최대 반복 횟수, RBAC | 단순 "도구 사용" 서술 — 권한·비용·감사 미언급 시 감점 |

> 요약: 출제자는 ReAct 루프 원리와 도구 호출 통제 설계를 함께 확인하려 함.

---

## Ⅰ. 개요 및 필요성

- 정의: LLM이 추론과 도구 실행을 반복하는 에이전트 패턴
- 배경: Chain-of-Thought는 추론만 가능하고 외부 데이터 조회·시스템 실행을 수행하지 못함
- 필요성: 다단계 업무에서 검색·계산·DB 조회 결과를 추론에 반영해야 정확도가 향상됨

---

## Ⅱ. 구조 및 구성요소

```text
User Goal -> Thought -> Action(Tool) -> Observation
  -> Replan or Finish (루프 반복 / 종료 판단)
```

| 구성요소 | 역할 | 특이사항 |
|:---|:---|:---|
| Thought | 다음 행동 판단 | 내부 로그와 사용자 출력 분리 |
| Action | 검색·계산·API 호출 | 허용 도구와 파라미터 제한 |
| Observation | 도구 결과 수신 | 신뢰도·출처·오류코드 확인 |
| Stop Rule | 종료 판단 | 최대 루프·비용 한도 설정 |

> 요약: ReAct는 추론과 도구 실행을 관찰 결과로 연결하는 폐루프 패턴임.

---

## Ⅲ. 동작원리 및 흐름도

```text
질문 수신 -> Thought 생성 -> Action 선택 -> Tool 실행
       -> Observation 반영 -> 답변 생성 or 다음 루프
```

| 단계 | 처리 내용 | 검증 기준 |
|:---:|:---|:---|
| 1 | 문제와 목표 해석 | 요구사항, 금지 행동 |
| 2 | 추론으로 행동 선택 | 도구명, 입력 파라미터 |
| 3 | 도구 실행 후 관찰 | 응답코드, 출처, 지연시간 |
| 4 | 종료 또는 재시도 | 최대 반복 수, 정확도 평가 |

> 요약: ReAct는 관찰 결과가 다음 추론의 입력이 되므로 도구 결과 검증이 품질을 좌우함.

---

## Ⅳ. 특징

| 구분 | CoT | ReAct | 수치·판단 포인트 |
|:---|:---|:---|:---|
| 외부 정보 | 없음 | 검색·API·DB 사용 | 출처 신뢰도, 응답코드 |
| 실행 능력 | 추론 텍스트 | 실제 도구 호출 | 호출 성공률, 비용 |
| 위험 | 추론 오류 | 도구 오남용·루프 폭주 | 최대 반복, RBAC |

> 요약: ReAct는 CoT보다 실행 능력이 크지만 도구 권한과 종료조건 설계가 필수임.

---

## Ⅴ. 심화 비교 및 적용 판단

| 비교 축 | CoT (추론 전용) | ReAct (추론+실행) | 선택 기준 |
|:---|:---|:---|:---|
| 외부 데이터 | 없음 (학습 지식만) | 검색·API·DB 호출 | 실시간 데이터 필요 여부 |
| 실행 능력 | 텍스트 출력만 | 시스템 조작 가능 | 업무 자동화 요구 여부 |
| 복잡도 | 단일 추론 체인 | 루프 제어·종료조건 필요 | 단순 질의 vs 다단계 업무 |

> 요약: 실시간 조회·시스템 실행이 필요하면 ReAct, 단순 추론이면 CoT를 선택함.

| 리스크 | 원인 | 대응 방안 | 확인 지표 |
|:---|:---|:---|:---|
| 루프 폭주 | 종료조건 미설정·도구 반복 실패 | 최대 반복 5회, 작업당 비용 한도 $0.5 | 루프 횟수, 총 비용 |
| Thought 유출 | 내부 추론을 사용자에게 그대로 출력 | 감사 로그와 사용자 출력 분리 | 출력 필터 적용률 |
| 도구 결과 오염 | Observation에 악의적 명령 삽입 | 도구 결과를 데이터로 처리, 인젝션 필터 | 필터 우회율 0% |

> 요약: 루프 폭주·추론 유출·결과 오염이 주요 리스크이며, 반복 한도·출력 분리·입력 필터로 통제함.

| 점검 항목 | 목표 기준 | 측정 방법 |
|:---|:---|:---|
| 작업 완료율 | 목표 대비 완료율 90% 이상 | 종료 사유별 로그 분석 |
| 도구 호출 성공률 | API 응답 200 비율 95% 이상 | Trace ID별 응답코드 집계 |
| 평균 루프 횟수 | 작업당 3회 이내 | 작업별 루프 카운트 통계 |

> 요약: 완료율·호출 성공률·루프 횟수로 ReAct 도입 효과를 정량 평가함.

---

## Ⅵ. 실무 적용 및 결론

**적용 방안 3개:**
1. Thought는 내부 감사 저장소에 보관하고 사용자에게는 근거·결과·출처만 출력
2. 도구 호출은 allowlist, JSON Schema, 최대 5회 루프, 작업당 비용 한도로 제한
3. Observation은 출처 URL, API 응답코드, Timestamp를 포함해 재현 가능한 로그로 저장

**결론 (2줄):**
- 기술사 판단: 외부 검증이 필요한 업무는 ReAct, 단순 요약은 일반 프롬프트 체인을 적용함.
- 향후 방향: ReAct는 MCP 기반 도구 표준화와 결합해 에이전트 실행 패턴의 기본 구조가 됨.
