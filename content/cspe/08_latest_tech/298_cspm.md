# 📖 【암기용】 개념 완전 이해

> 목적: 클라우드 해킹 사고의 99%가 해커의 천재적인 기술 때문이 아니라, 개발자의 어처구니없는 '설정 실수'에서 비롯됨을 깨닫고 이를 자동 탐지/수정하는 CSPM의 원리를 이해한다.

## 한눈에
- **정의**: 클라우드 인프라(IaaS, PaaS)의 설정(Configuration) 상태를 지속적으로 모니터링하여, **보안 위협 및 규정(Compliance) 위반 사항을 식별하고 자동으로 조치하는 보안 솔루션**
- **필요성**: 개발자가 야근하다가 실수로 클릭 한 번 잘못해서 S3(AWS 저장소)를 '전체 공개(Public)'로 열어버리면, 그 안에 있던 수백만 명의 개인정보가 다음 날 인터넷에 뿌려진다. 이런 휴먼 에러(Misconfiguration)를 막기 위함
- **핵심 직관**: "스마트홈의 가스 밸브 점검 로봇. 주인이 외출할 때 깜빡하고 가스 밸브를 열어두거나 창문을 열어두면(설정 오류), 로봇(CSPM)이 집안을 빙빙 돌며 '어? 가스 열렸네?' 하고 알람을 울린 뒤 알아서 밸브를 잠가(자동 복구) 버리는 것."

## 깊이 이해
- **배경(왜 등장했나?)**: 온프레미스 시절에는 전산실에 서버를 한 대 넣으려면 수십 명의 결재를 받아야 했다(안전함). 하지만 클라우드 시대에는 신입 개발자도 API 호출 한 번에 서버 100대를 띄울 수 있다. 속도는 빨라졌지만, 보안팀이 모르는 사이에 '방화벽이 뻥 뚫린 서버'가 무수히 생성되는 치명적인 부작용이 생겼다. 가트너는 "2025년까지 클라우드 침해 사고의 99%는 고객의 설정 실수 때문일 것"이라고 경고했고, 이를 막기 위해 CSPM이 탄생했다.
- **작동 원리 (CSPM의 3단계)**:
  1. **가시성 확보(Discovery)**: 클라우드 계정에 연동하여, 현재 떠 있는 모든 서버, DB, 스토리지의 목록과 설정 상태를 API로 쫙 긁어온다.
  2. **위협 탐지(Assessment)**: 긁어온 설정이 'Best Practice(모범 사례)'나 'ISMS-P(보안 인증)' 규정에 맞는지 비교한다. "S3 버킷이 Public인가?", "DB가 암호화되지 않았는가?", "MFA(다중 인증)를 안 켰는가?"
  3. **자동 복구(Remediation)**: 위험한 설정이 발견되면 슬랙으로 알람을 보내고, 심각한 경우 CSPM이 직접 클라우드 API를 쏴서 설정을 안전하게 강제 변경(예: S3 Public ➔ Private)해버린다.
- **일상 비유**: 맞춤법 검사기. 내가 글(클라우드 인프라)을 막 쓰면, 옆에서 맞춤법 검사기(CSPM)가 실시간으로 빨간 줄(위협 탐지)을 긋고, 버튼 하나 누르면 올바른 단어로 고쳐주는(자동 복구) 것.
- **구체 예시**: 2019년 미국의 대형 은행 캐피탈원(Capital One) 해킹 사건. AWS에 올려둔 방화벽(WAF)에 과도한 권한(설정 실수)이 부여되어 있었고, 이 틈을 타 해커가 1억 명의 개인정보를 빼갔다. 만약 CSPM이 있었다면 "방화벽 권한이 비정상적으로 높습니다!"라고 사전에 경고했을 것이다.
- **흔한 오해/주의점**: "CSPM은 해커의 악성코드를 막아주나요?" → 아니다! CSPM은 서버 '내부'의 악성코드를 잡는 백신(CWPP)이 아니라, 서버의 '외부 껍데기(인프라 설정)'가 단단히 잠겨있는지를 확인하는 자물쇠 점검 도구다.

## 연결 개념
- **Misconfiguration (설정 오류)**: CSPM이 존재하는 유일한 이유. 개발자의 실수로 보안의 문이 열려 있는 상태.
- **CWPP (클라우드 워크로드 보호 플랫폼)**: CSPM이 인프라(껍데기)를 검사한다면, CWPP는 그 안에 돌아가는 앱(알맹이/컨테이너)의 악성코드를 검사한다.
- **CNAPP (클라우드 네이티브 보호 플랫폼)**: CSPM과 CWPP 등을 하나로 묶어놓은 클라우드 보안의 완전체. (요즘엔 CSPM 단독으로 안 팔고 CNAPP로 합쳐서 판다.)

# 📝 【답안용】 시험 답안 템플릿

## 핵심 인사이트 (3줄 요약)
> 1. **본질**: CSPM(Cloud Security Posture Management)은 IaaS/PaaS 환경의 인프라 설정 오류(Misconfiguration)를 지속적으로 탐지하고, 규제 컴플라이언스(ISMS-P, GDPR 등) 준수 여부를 평가하는 클라우드 보안 솔루션이다.
> 2. **가치**: 클라우드 민첩성(Agility)으로 인해 발생하는 섀도우 IT(Shadow IT)와 개발자의 휴먼 에러를 통제하고, 자동화된 복구(Auto-Remediation)를 통해 보안 사고를 선제적으로 예방한다.
> 3. **판단 포인트**: 기존 온프레미스의 정적인 취약점 점검(Vulnerability Scan)과의 차이점을 명시하고, CSPM의 핵심 기능인 '가시성 확보 ➔ 형상 평가 ➔ 자동 조치' 프로세스와 IaC(Terraform) 연동을 통한 Shift-Left 전략을 제시해야 한다.

## Ⅰ. 개요 및 필요성
- **정의**: 클라우드 인프라 자산의 설정 상태(Posture)를 가시화하고, 보안 정책 및 규정 위반(Compliance Violation)을 자동으로 식별, 알림, 복구하는 보안 형상 관리 플랫폼
- **배경**: 클라우드 자원의 동적 프로비저닝 증가 및 관리자 권한 분산. 가트너 예측 클라우드 침해 사고의 99%가 사용자의 설정 실수(Misconfiguration)에 기인
- **필요성**: 멀티 클라우드 환경의 자산 가시성(Visibility) 일원화, 지속적 컴플라이언스(Continuous Compliance) 모니터링, 데이터 유출 방지 및 보안 감사의 자동화

## Ⅱ. CSPM의 핵심 기능 및 작동 프로세스
CSPM은 클라우드 제공자(CSP)의 API를 호출하여 상태를 점검하는 Agentless(에이전트리스) 방식으로 동작한다.

| 단계 | 핵심 기능 | 세부 수행 활동 및 예시 |
|:---|:---|:---|
| **1. 식별** (Discovery) | **멀티 클라우드 자산 가시화** | - AWS, Azure 등 여러 클라우드에 흩어진 EC2, S3, RDS 자산 목록을 실시간 수집 |
| **2. 평가** (Assessment) | **설정 오류 및 규정 위반 스캔** | - **보안 정책**: S3 Public 노출, 디폴트 패스워드 사용, 암호화 미적용 탐지<br>- **컴플라이언스**: ISMS-P, ISO27001, CIS Benchmarks 기준 충족 여부 맵핑 |
| **3. 조치** (Remediation)| **자동 복구 및 알림** | - 경고: 심각도에 따라 Slack, Jira, SIEM으로 알람 전송<br>- **Auto-Remediation**: 람다(Lambda) 함수를 트리거하여 퍼블릭 S3를 프라이빗으로 강제 전환 |

## Ⅲ. CSPM과 기존 취약점 점검 체계(CVE)의 비교
| 구분 | 기존 취약점 스캐너 (Vulnerability Scanner) | CSPM (Cloud Security Posture Mgmt) |
|:---|:---|:---|
| **점검 대상** | OS 및 애플리케이션 내부 (OS 버전, 라이브러리) | **클라우드 인프라 설정 (IAM, S3, 네트워크 등)** |
| **작동 방식** | 에이전트(Agent) 설치 또는 네트워크 포트 스캐닝 | **CSP 제공 API 연동 (에이전트 불필요)** |
| **발생 원인** | 소프트웨어 자체의 버그 (Zero-day 등) | **관리자(사용자)의 휴먼 에러 (설정 실수)** |
| **점검 주기** | 주기적 (월 1회, 분기 1회) | **실시간 / 지속적 (Continuous)** |

## Ⅳ. 최신 진화 방향: Shift-Left를 통한 예방적 CSPM
기존 CSPM은 서버가 생성된 '이후'에 오류를 잡았다. 최근에는 '생성되기 전(IaC)'에 오류를 차단한다.

- **IaC(Infrastructure as Code) 보안 검사**: Terraform, CloudFormation 등의 코드가 CI/CD 파이프라인(GitHub Actions)을 통해 배포되기 전, 코드를 정적 분석하여 "이 코드로 배포하면 보안 설정에 위배됩니다!"라고 파이프라인 자체를 차단(Break)하는 기능.

## Ⅴ. 기술적 한계(리스크) 및 해결 방안
| 리스크 요인 | 현상 및 문제점 | 대응 방안 (엔지니어링 가이드) |
|:---|:---|:---|
| **과도한 오탐 (False Positive)** | 사내 테스트용으로 의도적으로 열어둔 서버까지 CSPM이 규정 위반으로 간주하여 수천 개의 알림 융단폭격 | **태깅(Tagging) 및 예외 처리 고도화**: 자원 생성 시 환경(Dev, Prod) 태그를 강제화하고, Dev 환경에는 느슨한 룰을 적용하는 컨텍스트 기반 정책(Context-aware Policy) 수립 |
| **Auto-Remediation의 부작용** | CSPM이 위험을 감지하고 개발팀 모르게 설정을 닫아버려, 서비스 장애(Downtime)가 발생 | 시스템 차단(Fix) 권한은 매우 보수적으로 적용(예: S3 Public 차단만 허용)하고, 원칙적으로는 개발팀 스스로 코드를 수정하게 하는 **가드레일(Guardrail)** 접근법 채택 |

## Ⅵ. 실무 적용 및 결론
**적용 방안 및 실무 가이드:**
1. **클라우드 보안 거버넌스 수립**: CSPM 도구를 구매하기 전, 전사적으로 통용되는 "우리 회사의 최소 보안 베이스라인(Baseline)"을 명문화해야 한다. 이 기준표가 없으면 CSPM의 수많은 알람 중 무엇을 고쳐야 할지 기준을 잡을 수 없다.
2. **CNAPP으로의 로드맵**: CSPM 단독 운영 시 컨테이너(CWPP)나 권한(CIEM)과의 연관 분석이 불가능하므로, 장기적으로는 이 모든 가시성이 통합된 CNAPP 아키텍처로 진화해야 한다.

**결론:**
- CSPM은 속도가 생명인 클라우드 네이티브 환경에서, 무분별하게 생성되는 인프라 자산의 통제권을 되찾아주는 **'안전벨트이자 나침반'**이다.
- 클라우드 보안의 가장 큰 적은 해커가 아니라 '우리의 실수(Misconfiguration)'임을 인지하고, CSPM을 통해 규정 준수 검사를 일회성 이벤트가 아닌 '지속 가능한 파이프라인'으로 내재화해야 한다.
