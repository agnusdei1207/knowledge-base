# 📖 【암기용】 개념 완전 이해

> 목적: 블록체인 트릴레마를 확장성, 보안성, 탈중앙성 사이의 설계 균형 문제로 이해하게 만든다.

## 한눈에
- **개요**: 블록체인이 확장성·보안성·탈중앙성을 동시에 극대화하기 어려운 설계 제약
- **왜 필요한가**: 처리량만 늘리면 검증 노드 요구사항이 커지고, 탈중앙성을 낮추면 운영 주체 신뢰 문제가 생긴다.
- **핵심 직관**: 모두가 모든 거래를 직접 확인하면 믿을 수 있지만 느리고, 소수에게 맡기면 처리량은 늘지만 신뢰 모델이 바뀐다.

## 깊이 이해
- **배경·문제의식**: 퍼블릭 블록체인은 누구나 검증에 참여하는 구조를 목표로 한다. 그러나 블록 크기, 합의 주기, 노드 요구사항을 키우면 검증 비용이 증가한다.
- **작동 원리**: 확장성은 TPS와 지연, 보안성은 공격 비용과 합의 안전성, 탈중앙성은 검증 참여자 수와 권한 분산으로 평가한다.
- **비유**: 모든 주민이 회의록을 직접 검토하면 조작은 어렵지만 결재가 늦다. 대표 몇 명에게 맡기면 의사결정은 빨라지지만 대표 선출과 감시가 필요하다.
- **구체 예시**: Layer 2 rollup은 실행을 오프체인에서 처리하고 증명 또는 사기 검증을 Layer 1에 제출해 확장성과 보안 상속을 절충한다.
- **흔한 오해·주의점**: 트릴레마는 "셋 중 하나만 가능"이라는 법칙이 아니다. 설계가 어느 축을 희생하고 어떤 보완 장치를 두는지 설명하는 분석 틀이다.

## 연결 개념
- Layer 2 Rollup — 확장성 보완 구조
- PoS Consensus — 보안성과 탈중앙성의 경제적 설계
- Data Availability — 롤업 검증 가능성의 핵심 조건

# 📝 【답안용】 시험 답안 템플릿

> 목적: 시험장에서 25분에 그대로 쓰는 답안 양식.
> 핵심: 블록체인 트릴레마는 확장성·보안성·탈중앙성의 균형 문제이며, Layer 2, 샤딩, 합의 알고리즘은 세 축의 배분 방식으로 설명해야 한다.

## 핵심 인사이트 (3줄 요약)

> 1. **본질**: 블록체인 트릴레마는 처리량 확대, 공격 저항, 검증 권한 분산을 동시에 만족시키기 어려운 구조적 제약이다.
> 2. **가치**: 블록체인 설계안을 TPS 홍보가 아니라 신뢰 모델과 검증 비용 관점에서 평가하게 한다.
> 3. **판단 포인트**: 합의 방식, 노드 요구사항, 데이터 가용성, Layer 2 보안 상속, 거버넌스 집중도를 함께 본다.

## 출제 의도 및 답안 포인트

| 출제 의도 | 반드시 짚을 핵심 | 감점 회피 포인트 |
|:---|:---|:---|
| 블록체인 성능 한계 이해 확인 | 확장성·보안성·탈중앙성 3축 | TPS만으로 평가 |
| 대안 기술 판단 확인 | Rollup, sharding, sidechain, PoS | 특정 체인을 만능으로 설명 |
| 운영 리스크 인식 확인 | 검증자 집중, bridge 위험, DA 실패 | 탈중앙성을 슬로건으로 처리 |

> 요약: 이 문제는 블록체인 설계를 세 축의 트레이드오프와 보완장치로 설명하는 능력을 요구한다.

---

## Ⅰ. 개요 및 필요성

- 개요: 블록체인 3축 균형
- 배경: 퍼블릭 블록체인은 누구나 검증 가능해야 하지만 모든 노드가 모든 거래를 처리하면 처리량과 지연에 한계가 생김.
- 필요성: 서비스 도입 전 TPS, finality, 검증자 분산, 공격 비용을 함께 평가해야 함.

---

## Ⅱ. 구조 및 구성요소

```text
Blockchain Design
  / Scalability: TPS, latency, block size
  / Security: consensus safety, attack cost, finality
  / Decentralization: validator count, node cost, governance
Trade-off Analysis -> Layer 1 / Layer 2 / Sidechain Selection
```

| 구성요소 | 역할 | 특이사항 |
|:---|:---|:---|
| 확장성 | 거래 처리량과 지연 결정 | TPS, finality time |
| 보안성 | 이중지불·검열·재구성 공격 저항 | 합의 알고리즘 |
| 탈중앙성 | 검증 참여와 의사결정 분산 | 노드 비용, 지분 집중 |
| 보완기술 | 한 축 희생을 줄이는 구조 | rollup, sharding, DA |

> 요약: 트릴레마는 성능 수치가 아니라 신뢰 모델과 검증 비용까지 포함한 설계 평가 틀이다.

---

## Ⅲ. 동작원리 및 흐름도

```text
요구사항 정의 -> 3축 지표 산정 -> 병목 축 식별
-> L1/L2/Sidechain 후보 비교 -> 신뢰 모델 검증 -> 운영 지표 측정
```

| 단계 | 처리 내용 | 검증 기준 |
|:---:|:---|:---|
| 1 | 업무의 TPS, finality, 데이터 공개 범위를 정의함 | workload profile |
| 2 | 합의 방식과 노드 요구사항을 확인함 | validator/node count |
| 3 | Layer 2 또는 샤딩 적용 시 보안 상속 방식을 검토함 | proof/DA model |
| 4 | 운영 중 bridge, sequencer, governance 위험을 측정함 | incident metric |

> 요약: 트릴레마 분석은 요구 성능에서 시작해 합의·검증·운영 리스크로 내려가는 절차다.

---

## Ⅳ. 특징

| 구분 | 확장성 우선 | 보안성 우선 | 탈중앙성 우선 |
|:---|:---|:---|:---|
| 대표 방식 | 큰 블록, 고성능 노드, L2 | 강한 합의, 긴 finality | 낮은 노드 요구사항 |
| 얻는 효과 | 처리량 확대 | 공격 비용 증가 | 검증 참여 확대 |
| 비용 | 노드 집중 | 지연 증가 | TPS 제약 |
| 점검 지표 | TPS, p95 latency | reorg, slashing | validator concentration |

> 요약: 세 축은 독립 KPI가 아니라 하나를 조정하면 다른 축의 비용이 발생하는 연동 지표다.

## Ⅴ. 심화 비교 및 적용 판단

| 비교 축 | 기존/대안 | 본 키워드 | 선택 기준 |
|:---|:---|:---|:---|
| 확장 해법 | L1 블록 크기 확대 | Rollup/Shard 절충 | 노드 비용 허용 범위 |
| 신뢰 모델 | 중앙 DB | 퍼블릭 검증 | 감사 가능성 필요 |
| 운영 구조 | 단일 운영자 | 검증자·sequencer·bridge | 장애 책임 구분 |

> 요약: 블록체인 선택은 탈중앙 검증이 필요한 업무에서만 의미가 있으며, 내부 업무는 중앙 DB가 더 단순할 수 있다.

| 리스크 | 원인 | 대응 방안 | 확인 지표 |
|:---|:---|:---|:---|
| 검증자 집중 | 지분·인프라 편중 | 분산 validator 정책 | top-N stake ratio |
| 브리지 손실 | 외부 체인 자산 잠금 | audited bridge, limit cap | bridge TVL exposure |
| 데이터 가용성 실패 | 거래 데이터 미공개 | DA layer, fraud/validity proof | DA sampling result |

> 요약: 확장성 보완 기술은 bridge, sequencer, DA 같은 새 신뢰 지점을 만든다.

| 점검 항목 | 목표 기준 | 측정 방법 |
|:---|:---|:---|
| 성능 | 업무 TPS와 finality 충족 | chain explorer, load test |
| 보안 | reorg·slashing·bridge 사고 이력 | incident review |
| 분산성 | 검증자와 클라이언트 다양성 | validator dashboard |

> 요약: 트릴레마 평가는 TPS, finality, 사고 이력, 검증자 집중도를 함께 봐야 한다.

---

## Ⅵ. 실무 적용 및 결론

**적용 방안 3개:**
1. 업무가 탈중앙 검증을 요구하는지 먼저 판단하고, 단순 감사로그는 append-only log나 중앙 DB 대안을 비교함.
2. L1, rollup, sidechain 후보별 TPS, finality, 검증자 집중도, bridge 노출액을 표로 비교함.
3. sequencer 장애, bridge 제한, 데이터 가용성 실패 시나리오를 운영 플레이북과 모니터링 지표에 반영함.

**결론 (2줄):**
- 기술사 판단: 공공 검증성과 검열 저항이 요구되면 블록체인을 선택하고, 내부 처리량만 필요한 경우 중앙 시스템을 선택함.
- 향후 방향: Rollup, DA sampling, ZK proof가 트릴레마의 비용을 낮추지만 신뢰 지점 제거 여부는 별도 검증해야 함.
