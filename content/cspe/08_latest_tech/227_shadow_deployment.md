# 📖 【암기용】 개념 완전 이해

> 목적: Shadow Deployment를 처음 봐도 완벽히 이해하게 만든다. 시험 답안 양식이 아니라, 이해를 위한 친절한 설명이다.

## 한눈에
- **개요**: 운영 환경의 실제 트래픽을 복사하여 기존 모델(Production)과 신규 모델(Shadow)에 동시에 보내되, 신규 모델의 결과값은 실제 서비스에 반영하지 않고 성능 검증용으로만 기록하는 배포 방식
- **왜 필요한가**: 신규 모델이 실제 사용자에게 어떤 영향을 줄지 전혀 모르는 상태에서, 아무리 적은 비율(Canary)이라도 사용자에게 노출하는 것조차 위험한 '초고위험 서비스'의 안정성을 확보하기 위함
- **핵심 직관**: 실제 경기(운영)를 뛰는 선수(기존 모델) 옆에서, 신입 선수(신규 모델)가 벤치에 앉아 "나라면 이렇게 했을 거야"라고 가상으로 경기를 치러보며 실력을 점검하는 것

## 깊이 이해
- **배경·문제의식**: 카나리(Canary) 배포도 결국 소수의 사용자에게는 잠재적 오류를 노출한다. 금융 결제나 자율주행처럼 한 번의 실수가 치명적인 분야에서는 0%의 위험도 용납되지 않는다. 따라서 사용자는 모르게 뒤편(Shadow)에서만 조용히 성능을 확인하고, 기존 모델과 답변이 얼마나 다른지 비교하는 과정이 필요하다.
- **작동 원리**: 요청이 들어오면 트래픽 복제기(Traffic Mirroring/Tee)가 요청을 복사한다. 하나는 기존 모델로 보내 실시간 응답을 주고, 다른 하나는 신규 모델로 보낸다. 신규 모델의 응답은 로그로만 남기고 사용자에게는 보내지 않는다. 이후 로그를 분석하여 신규 모델이 기존보다 얼마나 더 정확했는지, 혹은 이상한 답을 내지 않았는지 평가한다.
- **비유**: 시험을 치는 학생 뒤에 다른 학생이 서서, 시험지에 답을 쓰지는 않고 자기 연습장에만 답을 적어본 뒤 나중에 실제 정답지와 대조해보는 것과 같다.
- **구체 예시**: 이상 거래 탐지(FDS) 모델을 교체할 때, 한 달 동안 실제 거래 데이터를 섀도 모델에 흘려보낸다. 실제로는 기존 모델이 거래를 승인/거절하지만, 섀도 모델의 판단 결과를 사후에 대조하여 오탐(False Positive)이 줄었는지 최종 확인 후 배포한다.
- **흔한 오해·주의점**: "섀도 배포는 부하 테스트와 같다"는 오해다. 부하 테스트는 '서버가 버티는가'를 보는 것이고, 섀도 배포는 '실제 데이터에서 모델이 올바른 답을 내는가'를 보는 기능적·통계적 검증 목적이 크다.

## 연결 개념
- Traffic Mirroring — 트래픽을 복제하여 다른 곳으로 보내는 핵심 기술
- Canary Release — 섀도 배포 이후, 안전이 확인된 뒤 소수 사용자에게 노출하는 다음 단계
- Champion-Challenger — 신/구 모델의 성과를 실시간으로 비교하는 테스트 전략

# 📝 【답안용】 시험 답안 템플릿

> 목적: 시험장에서 25분에 그대로 쓰는 답안 양식. 작성방식(추상표현 금지·수치·도식·문제유형 전환)을 엄격히 지킨다.

## 핵심 인사이트 (3줄 요약)

> 1. **본질**: Shadow Deployment는 운영 트래픽을 복제(Mirroring)하여 신규 모델에 전달하되, 그 결과는 비즈니스에 반영하지 않고 백그라운드에서 검증하는 무위험 배포 전략이다.
> 2. **가치**: 실제 운영 환경의 데이터 분포(Live Distribution)에서 모델의 안정성과 정확도를 사용자 영향 없이 100% 검증할 수 있다.
> 3. **판단 포인트**: 서비스 지연(Latency)에 영향을 주지 않는 비동기 트래픽 복제와, 두 모델의 결과를 대조 분석하는 'Dark Launch' 모니터링 체계가 핵심이다.

## 출제 의도 및 답안 포인트

| 출제 의도 | 반드시 짚을 핵심 | 감점 회피 포인트 |
|:---|:---|:---|
| 제로 리스크 배포 전략 이해 확인 | 트래픽 복제(Mirroring), 사용자 노출 없음(Zero Impact) | 단순히 "테스트용 배포"라고 모호하게 서술 |
| 실무적 검증 체계 설계 능력 확인 | 신/구 모델 결과 대조 분석, 성능 및 리소스 비교 | 사용자 응답에 포함된다고 오해하여 서술 |
| 인프라 구현 기술 이해 확인 | 사이드카 프록시(Envoy/Istio), 비동기 처리 | 트래픽 복제 방식(Mirroring) 언급 누락 |

> 요약: 실제 운영 트래픽을 활용하되 사용자 경험에는 0%의 영향도 주지 않는 궁극의 안전 검증 체계 제시가 핵심이다.

## Ⅰ. 개요 및 필요성

- 정의: 운영 환경의 실제 요청(Live Traffic)을 복제하여 신규 모델에 전달하고, 그 결과는 저장/분석만 수행하며 사용자에게는 기존 모델의 결과만 응답하는 배포 방식
- 배경: 신규 모델의 예측 오류가 비즈니스에 치명적인 영향을 줄 수 있는 고위험 서비스(금융, 의료 등)의 안정성 확보 요구
- 필요성: 운영 데이터 기반의 무위험 성능 검증, 인프라 부하 처리 능력 확인, 신/구 모델 간의 예측값 편차(Discrepancy) 사전 파악

---

## Ⅱ. 구조 및 구성요소

```text
User Request -> Traffic Mirroring (Tee / Proxy)
                        |
            +-----------+-----------+
            | (Production)          | (Shadow - 복제)
      Current Model (v1)      New Model (v2)
            |                       |
      Real Response         Shadow Log (Discarded)
            |                       |
            +-----------+-----------+
                        |
              Comparison & Analysis Engine (Offline/Real-time)
```

| 구성요소 | 역할 | 특이사항 |
|:---|:---|:---|
| Traffic Mirroring | 실제 요청을 복사하여 두 경로로 동시 전달 | 비동기 처리 필수 (Latency 보호) |
| Production Model | 실제 사용자에게 응답을 주는 현재 가동 모델 | 주 모델 (Champion) |
| Shadow Model | 복제된 트래픽을 받아 가상 추론을 수행하는 모델 | 부 모델 (Challenger) |
| Analysis Engine | 두 모델의 출력값 및 성능 지표를 대조 분석 | 예측값 편차 및 정확도 비교 |

> 요약: 트래픽 복제를 통해 기존 서비스 흐름을 방해하지 않으면서 신규 모델의 성능을 병렬로 검증함.

---

## Ⅲ. 동작원리 및 흐름도

```text
요청 인입 -> 트래픽 복제 -> (A) 운영 모델 처리 및 응답 -> (B) 섀도 모델 가상 추론 -> 결과 로그 적재 -> 주기적 성능 대조 분석
      |               |                 |                       |                       |                      |
      +---------------+-----------------+-----------------------+-----------------------+----------------------+-----> 승인 여부 결정
```

| 단계 | 처리 내용 | 검증 기준 |
|:---:|:---|:---|
| 1 | 비동기 트래픽 미러링 | 운영 모델 응답 지연 발생 여부 체크 |
| 2 | 섀도 모델 추론 및 결과 로깅 | 섀도 결과는 사용자 응답에서 제외 |
| 3 | 신/구 모델 결과 비교 분석 | 예측값 일치율, 정답 기준 정확도 |
| 4 | 리소스 및 안정성 평가 | 메모리/GPU 점유율, 에러 발생 빈도 |

> 요약: 운영 서비스의 가용성(A)을 보장하면서, 신규 모델(B)의 지능과 성능을 그림자처럼 따라가며 평가함.

---

## Ⅳ. 특징

| 구분 | Canary Deployment | Shadow Deployment | 판단 포인트 |
|:---|:---|:---|:---|
| 사용자 노출 | 소수 사용자 (5% 등) | 없음 (0%) | 리스크 허용도 |
| 응답 반영 | 실제 응답으로 사용 | 응답에 반영 안 됨 (Discarded) | 실무 적용 여부 |
| 데이터 활용 | 실제 트래픽의 일부 | 실제 트래픽 전체 (또는 일부 복제) | 데이터 대표성 |
| 주 용도 | 위험 분산 및 점진적 배포 | 고위험 모델의 완벽한 사전 검증 | 도입 목적 |

> 요약: Shadow Deployment는 Canary보다 안전하며, 실제 배포 전 "최종 리허설"의 성격이 강함.

## Ⅴ. 심화 비교 및 적용 판단

| 비교 축 | Proxy 기반 (Istio/Envoy) | Application 기반 (Async Call) | 선택 기준 |
|:---|:---|:---|:---|
| 구현 위치 | 인프라 레이어 (네트워크) | 애플리케이션 레이어 (코드) | 개발 및 운영 환경 |
| 구현 난이도 | 중간 (설정 기반) | 높음 (비동기 로직 구현) | 인프라 제어 권한 |
| 서비스 영향 | 거의 없음 (투명함) | 약간의 오버헤드 발생 가능 | 성능 민감도 |

> 요약: 인프라가 서비스 메시(Service Mesh) 환경이면 프록시 기반을, 그렇지 않으면 애플리케이션 단의 비동기 호출을 선택함.

| 리스크 | 원인 | 대응 방안 | 확인 지표 |
|:---|:---|:---|:---|
| 부하 증가 | 두 배의 모델 연산으로 인한 자원 고갈 | 섀도 전용 인프라 분리 및 샘플링 복제 | GPU/CPU 사용률 |
| 응답 지연 (Tee 지연) | 트래픽 복제 과정에서의 병목 | 비동기 복제 및 Fire-and-forget 방식 적용 | 운영 모델 Latency 증가폭 |
| 데이터 일관성 | 섀도 모델의 쓰기 작업(DB 등) 오염 | 섀도 모델의 외부 쓰기 작업 금지 (Read-only) | 운영 데이터 무결성 |

> 요약: 부하는 자원 분리로, 지연은 비동기 처리로, 데이터 오염은 읽기 전용 설정으로 대응함.

| 점검 항목 | 목표 기준 | 측정 방법 |
|:---|:---|:---|
| 예측 일치율 | 기존 모델과 90% 이상 유사성 확보 | 두 모델의 출력값 분포 대조 |
| 섀도 모델 에러율 | 운영 환경 내 에러 발생 0.1% 이하 | 섀도 모델 전용 로그 분석 |
| 서비스 영향도 | 운영 모델 지연 시간 증가 5ms 이내 | 섀도 활성화 전후 Latency 대조 |

> 요약: 도입 효과는 모델 간 예측 일관성, 섀도 환경의 안정성, 운영 서비스의 무영향성 지표로 판정함.

## Ⅵ. 실무 적용 및 결론

**적용 방안 3개:**
1. 제로 리스크 검증: 신규 부정 거래 탐지(FDS) 모델을 2주간 섀도 배포하여, 실제 정지(Block) 처리는 기존 모델이 하되 신규 모델의 오탐률을 사후 분석하여 안정성 확인
2. 실환경 부하 테스트: 신규 거대 모델(LLM) 배포 전, 실제 운영 트래픽을 100% 복제하여 섀도 모델에 보내며 피크 타임의 자원 점유율과 연산 속도를 실전 검증
3. 비즈니스 임팩트 분석: 추천 알고리즘 변경 시, 섀도 모델이 추천했을 결과와 실제 클릭된 아이템을 대조하여 가상의 CTR(클릭률) 개선 폭을 선제적으로 파악

**결론 (2줄):**
- 기술사 판단: 섀도 배포는 사용자 경험을 해치지 않으면서 운영 데이터의 불확실성을 극복하는 MLOps의 가장 강력한 안전장치임
- 향후 방향: 트래픽 복제를 넘어, 섀도 모델의 결과를 실시간으로 비교하여 이상 징후 발생 시 배포 파이프라인을 자동 차단하는 "인텔리전트 가드레일"로 발전할 것임
