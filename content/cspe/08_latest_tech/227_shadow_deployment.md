# 📖 【암기용】 개념 완전 이해

> 목적: 섀도 배포를 실제 사용자 응답에는 영향을 주지 않고 신규 모델을 실트래픽 복제본으로 검증하는 방식으로 이해하게 만든다.

## 한눈에
- **개요**: 운영 요청을 기존 모델과 신규 모델에 동시에 보내되 사용자 응답은 기존 모델 결과만 사용하는 배포 검증 방식
- **왜 필요한가**: 신규 모델의 지연, 오류, 비용, 출력 형식을 실트래픽에서 확인하면서 사용자 경험을 바꾸지 않아야 한다.
- **핵심 직관**: 시험 방송을 실제 송출망 뒤에서 몰래 병렬 실행하되 시청자에게는 기존 방송만 보여주는 방식이다.

## 깊이 이해
- **배경·문제의식**: 오프라인 테스트 데이터는 운영 트래픽의 장문 입력, 이상 요청, 피크 QPS, 권한 조건을 충분히 담지 못한다.
- **작동 원리**: request mirror가 운영 요청을 복제해 shadow model에 보내고, 응답은 폐기하거나 로그로 저장해 기존 모델과 비교한다.
- **비유**: 신규 계산원이 실제 주문을 따라 계산 연습을 하지만 영수증은 기존 계산원이 발행하는 상황과 같다.
- **구체 예시**: LLM 답변 모델 v2를 shadow로 실행해 p95 latency 2초 이하, timeout 0.5% 이하, token cost/request 20% 이하 증가 조건을 확인한다.
- **흔한 오해·주의점**: 섀도 배포는 사용자 반응 지표를 직접 측정하지 못한다. CTR, conversion 같은 행동 지표는 카나리나 A/B 테스트가 필요하다.

## 연결 개념
- Canary Model Release — 검증 후 제한 사용자에게 실제 응답을 제공하는 단계
- Online Evaluation — shadow 로그를 실트래픽 품질 평가에 활용
- Model Monitoring — shadow와 production 지표를 model_id별로 비교

# 📝 【답안용】 시험 답안 템플릿

> 목적: 시험장에서 25분에 그대로 쓰는 답안 양식.
> 핵심: 섀도 배포는 사용자 영향 없이 실트래픽 재현성, 지연, 오류, 비용을 검증한다.

## 핵심 인사이트 (3줄 요약)

> 1. **본질**: Shadow Deployment는 운영 요청을 신규 모델에도 복제해 실행하되 사용자 응답에는 기존 모델 결과만 반영하는 검증 방식임.
> 2. **가치**: 실트래픽 분포에서 latency, timeout, cost, schema compatibility를 사용자 영향 없이 확인함.
> 3. **판단 포인트**: 사용자 행동 지표가 필요하면 카나리·A/B, 실행 적합성 검증이면 섀도 배포를 선택함.

## 출제 의도 및 답안 포인트

| 출제 의도 | 반드시 짚을 핵심 | 감점 회피 포인트 |
|:---|:---|:---|
| 무영향 검증 구조 이해 확인 | request mirroring, response discard, metric compare | 사용자에게 신규 결과를 노출한다고 서술 |
| 배포 전략 차이 판단 확인 | shadow vs canary vs A/B | 실트래픽 검증과 사용자 반응 검증 혼동 |
| 운영 비용 인식 확인 | 중복 추론 비용과 개인정보 복제 통제 | 비용·권한·마스킹 누락 |

> 요약: 이 문제는 신규 모델을 사용자에게 노출하지 않고 운영 적합성을 검증하는 구조를 요구한다.

---

## Ⅰ. 개요 및 필요성

- 개요: 사용자 무영향 실트래픽 병렬 검증
- 배경: 테스트 데이터는 운영 요청의 피크 QPS, 이상 입력, 권한 조건을 충분히 재현하지 못함.
- 필요성: 신규 모델을 실제 응답에 쓰기 전 p95 latency, timeout, cost/request, schema error를 실트래픽에서 확인해야 함.

---

## Ⅱ. 구조 및 구성요소

```text
Client -> Production Model -> User Response
       +-> Request Mirror -> Shadow Model -> Shadow Log -> Metric Compare
```

| 구성요소 | 역할 | 특이사항 |
|:---|:---|:---|
| Production Model | 사용자 응답 생성 | 기준 모델 |
| Request Mirror | 운영 요청 복제 | 개인정보 마스킹 필요 |
| Shadow Model | 신규 모델 병렬 실행 | 응답은 사용자에게 미노출 |
| Metric Compare | 지연·오류·비용·출력 차이 비교 | model_id별 로그 저장 |

> 요약: 섀도 배포는 실제 응답 경로와 shadow 검증 경로를 분리해 사용자 영향 없이 신규 모델을 실행한다.

---

## Ⅲ. 동작원리 및 흐름도

```text
운영 요청 수신 -> 기존 모델 응답 반환 -> 요청 복제 -> 신규 모델 병렬 실행 -> shadow 지표 비교
```

| 단계 | 처리 내용 | 검증 기준 |
|:---:|:---|:---|
| 1 | 운영 요청을 기존 모델이 처리 | production SLA 충족 |
| 2 | request mirror가 요청을 shadow 경로로 복제 | 복제율 1~100% |
| 3 | 신규 모델이 병렬 추론 수행 | timeout 0.5% 이하 |
| 4 | shadow 결과를 로그로 저장하고 비교 | schema error 0건 |

> 요약: 섀도 배포는 기존 응답을 유지한 채 신규 모델의 실행 결과를 로그로만 평가한다.

---

## Ⅳ. 특징

| 구분 | Canary | Shadow Deployment | 수치 기준 |
|:---|:---|:---|:---|
| 사용자 노출 | 일부 사용자에게 신규 결과 노출 | 신규 결과 미노출 | 영향 사용자 0명 |
| 검증 지표 | 오류·지연·행동 지표 | 오류·지연·비용·출력 차이 | p95, timeout, cost |
| 비용 구조 | 단일 응답 경로 중심 | 중복 추론 비용 발생 | GPU 사용량 2배 가능 |

> 요약: 섀도 배포는 사용자 영향이 없지만 중복 추론 비용과 행동 지표 부재를 감수한다.

---

## Ⅴ. 심화 비교 및 적용 판단

| 비교 축 | 기존/대안 | 본 키워드 | 선택 기준 |
|:---|:---|:---|:---|
| 검증 목적 | 오프라인 평가는 고정 데이터 | shadow는 실트래픽 실행 검증 | 운영 분포 재현 필요 시 shadow |
| 사용자 영향 | canary는 실제 노출 | shadow는 미노출 | 민감 서비스는 shadow 우선 |
| 비용/성능 | 단일 추론 비용 | 중복 추론 비용 | GPU budget과 샘플링 비율 판단 |

> 요약: 섀도 배포는 민감 서비스에서 운영 적합성을 먼저 검증할 때 선택한다.

| 리스크 | 원인 | 대응 방안 | 확인 지표 |
|:---|:---|:---|:---|
| 비용 증가 | production과 shadow 중복 추론 | 샘플링 1~10%, 비피크 시간 실행 | GPU 사용률, cost/request |
| 개인정보 노출 | 실요청 복제 | PII 마스킹, 접근통제, 로그 보존기간 설정 | 마스킹 실패 0건 |
| 행동 지표 부재 | shadow 응답 미노출 | 이후 canary/A/B 단계 연결 | canary 전환 여부 |

> 요약: 섀도 배포 리스크는 중복 비용, 개인정보 복제, 행동 지표 부재이며 샘플링과 단계 전환으로 통제한다.

| 점검 항목 | 목표 기준 | 측정 방법 |
|:---|:---|:---|
| 지연시간 | p95 2초 이하 | shadow inference log |
| 오류율 | timeout 0.5% 이하 | model runtime metric |
| 비용 | token cost/request 20% 이하 증가 | billing tag, GPU metric |

> 요약: 섀도 배포 성공 여부는 지연·오류·비용이 production 허용 범위 안에 있는지로 판단한다.

---

## Ⅵ. 실무 적용 및 결론

**적용 방안 3개:**
1. 민감 업무는 shadow 10% 샘플링으로 24시간 운영 분포를 검증한 뒤 canary 1%로 전환함.
2. shadow 요청에는 PII 마스킹, tenant_id 접근통제, 30일 로그 보존 정책을 적용함.
3. 기존 모델과 신규 모델의 output schema, refusal rate, cost/request를 model_id별로 비교함.

**결론 (2줄):**
- 기술사 판단: 사용자 영향 0명이 요구되는 금융·의료·공공 업무는 섀도 배포 후 카나리 배포 순서로 전환함.
- 향후 방향: 섀도 배포는 LLM judge, continuous evaluation, prompt regression test와 결합된 사전 운영 검증 체계로 확장됨.
