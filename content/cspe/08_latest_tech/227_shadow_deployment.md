# 📖 【암기용】 개념 완전 이해

## 한눈에
- **정의**: 신규 머신러닝 모델을 상용 서버에 배포할 때, **실제 사용자들의 요청(트래픽)을 '복제(Mirroring)'해서 기존 모델과 신규 모델에 동시에 쏘되, 신규 모델의 결과값은 고객에게 안 보여주고 뒤(Shadow)에 조용히 저장만 해서 성능을 비교 검증**하는 무위험 배포 방식.
- **필요성**: 카나리 배포로 단 1%의 고객에게만 모델을 노출해도, 그 서비스가 '자율주행'이거나 '주식 자동매매'라면 단 한 번의 오류가 사람 목숨을 앗아가거나 수억 원의 소송으로 이어짐. 즉, 사용자 노출 리스크가 '0%'여야만 하는 초고위험 AI 서비스 검증에 필수적임.
- **핵심 직관**: 실제 축구 경기 중에 몰래 뛰는 '그림자(투명 인간) 선수'. 경기장에 투명 인간(신규 모델)을 투입해 실제 패스(트래픽)를 줌. 투명 인간이 혼자 슛을 쏘고 결과를 내지만, 전광판(고객 응답) 점수로는 인정 안 됨. 경기 끝난 뒤 감독(엔지니어)이 비디오를 돌려보며 "저 투명 인간이 기존 공격수보다 골을 더 잘 넣었네?" 판단이 서면 다음 경기에 진짜로 투입함.

## 깊이 이해
- **배경**: 오프라인 과거 데이터로 아무리 테스트해도, 오늘 지금 이 순간 유입되는 쌩 리얼 데이터(Live Traffic) 앞에서는 모델이 어떻게 반응할지 알 수 없음. 그래서 '살아있는 데이터'로 테스트는 하고 싶은데, '장애 리스크'는 절대 지고 싶지 않다는 극단적 딜레마에서 탄생한 궁극의 방어적 배포 기법.
- **작동 원리 (비동기 트래픽 미러링)**:
  1. 고객이 결제 버튼을 누름. API 게이트웨이가 이 요청을 받음.
  2. 게이트웨이는 메인 요청을 기존 모델(Champion)에 보내고 즉시 결과를 고객에게 리턴함 (정상 서비스).
  3. 이와 **동시에(비동기적으로)** 똑같은 요청을 복제(Mirror)해서 뒤에 숨어있는 신규 모델(Challenger)로 보냄.
  4. 신규 모델이 혼자 고민해서 뱉어낸 예측값은 고객에게 안 가고 별도의 로그 DB에 얌전히 저장됨 (Dark Launch).
  5. 데이터 사이언티스트가 양쪽 모델의 예측 정확도 차이와 응답 속도(Latency)를 비교 분석함.
- **구체 예시**: 신용카드사의 새로운 딥러닝 사기 탐지(FDS) 모델. 이 모델을 즉시 배포하면 정상 고객의 카드를 막아버릴 위험이 있음. 1주일간 섀도우 배포를 함. 실제 카드를 정지시키는 건 옛날 모델이 수행함. 1주일 뒤 DB를 까보니, 새 모델은 옛날 모델이 놓친 사기범 100명을 더 찾아냈고 정상 결제는 한 건도 막지 않았음이 수학적으로 증명됨. 이제 안심하고 새 모델을 정식 배포(스위칭)함.
- **흔한 오해/주의점**: "그냥 테스트서버에 부하 테스트하는 거랑 뭐가 다름?" $\rightarrow$ 부하 테스트는 '가짜 더미 데이터(Dummy)'를 쏴서 서버가 안 터지나 보는 거고, 섀도우 배포는 **진짜 사용자의 오늘 자 최신 리얼 데이터**를 넣어 모델의 '예측 지능(정확도)'을 평가하는 데 초점이 맞춰져 있음. 인프라 자원(서버 비용)이 2배로 든다는 게 최대 단점.

## 연결 개념
- **Traffic Mirroring (트래픽 미러링)**: 섀도우 배포의 핵심 네트워크 기술. 원본 트래픽에 성능 부하를 주지 않고 트래픽을 100% 똑같이 복사해 다른 곳으로 쏴주는 기능 (Istio/Envoy Proxy 등이 지원).
- **Dark Launch (다크 론치)**: 섀도우 배포와 거의 비슷한 개념. 기능은 배포되었으나 사용자 UI에는 보이지 않게 숨겨놓고 백그라운드에서만 돌리는 기법.
- **Canary Release (카나리 배포)**: 섀도우 배포로 안전성이 100% 검증되면, 비로소 실제 사용자에게 5%, 10%씩 릴리스를 시작하는 다음 타자 배포 전략.

# 📝 【답안용】 시험 답안 템플릿
## 핵심 인사이트 (3줄 요약)
- **본질**: 운영 환경의 라이브 트래픽(Live Traffic)을 비동기적으로 복제(Mirroring)하여 신규 모델에 주입하되, 그 추론 결과는 사용자에게 노출하지 않고 백그라운드 로깅을 통해 기존 모델(Champion)과 성능을 대조 평가(Challenger)하는 제로 리스크 배포 전략.
- **가치**: 예측 오류 발생 시 치명적인 비즈니스 손실(금융, 자율주행, 헬스케어)을 초래하는 도메인에서, 사용자 경험(UX)과 서비스 가용성에 0%의 영향도 주지 않은 채 "오프라인-온라인 데이터 괴리"를 완벽하게 검증할 수 있음.
- **판단 포인트**: 섀도우 배포 아키텍처의 성패는 원본 트래픽의 응답 지연(Latency)에 페널티를 주지 않는 논블로킹(Non-blocking) 네트워크 미러링 기술(Istio/Envoy) 적용 여부와, 두 모델의 출력 편차(Discrepancy)를 시계열로 비교 분석하는 관측성 파이프라인의 완성도에 달림.

## Ⅰ. 개요 및 필요성
- **정의**: 실제 서비스 환경에서 기존 프로덕션 모델(Primary)의 정상 응답 흐름을 유지하면서, 신규 후보 모델(Shadow)에 동일한 입력 데이터를 흘려보내 성능과 안정성을 은밀하게(Dark Launch) 테스트하는 배포 방법론.
- **배경**: 과거 데이터 기반의 오프라인 평가(Offline Evaluation)로는 실시간 트렌드 변화와 예외 케이스(Edge case)를 검증하기 불가능하며, A/B 테스트나 카나리 배포조차 고객 이탈 리스크를 내포함.
- **필요성**: 제로 리스크(Zero Risk) 모델 인텔리전스 검증, 신규 딥러닝 아키텍처 도입 시 OOM(Out of Memory) 등 인프라 부하 내성(Stress) 사전 확인, 데이터 입력 스키마 오류 선제 탐지.

## Ⅱ. Shadow Deployment 아키텍처 및 메커니즘
트래픽 복제와 격리된 추론 루프.
| 핵심 컴포넌트 | 메커니즘 (Mechanism) 및 아키텍처 역할 | 비고 (요구 사항) |
|:---:|:---|:---|
| **Traffic Splitter / Proxy** | 클라이언트 API 요청을 수신 후, 원본은 기존 모델로 라우팅하고 패킷을 100% 복제(Tee/Mirroring)하여 섀도우 모델로 비동기 전송함. | Fire-and-Forget (응답 대기 안 함). |
| **Primary Model (v1)** | 사용자 요청을 처리하고 **직접 응답(Response)**을 클라이언트로 반환함. | 서비스 주체 (Champion) |
| **Shadow Model (v2)** | 복제된 트래픽을 처리하나, **응답을 버리거나(Discard) 메트릭 DB에만 적재함.** | 서비스 비노출 (Challenger) |
| **Data Comparator** | ELK 스택 등을 이용해 동일한 Request ID를 가진 v1, v2의 예측값과 연산 속도를 대조 분석함. | 오프라인 사후 평가 수행. |

## Ⅲ. 주요 배포 전략 비교 (MLOps 관점)
위험도와 리소스의 트레이드오프.
| 구분 | Shadow Deployment | Canary Release | Blue-Green Deployment |
|:---:|:---|:---|:---|
| **사용자 응답 노출**| **전혀 없음 (0%)** | 극소수 노출 (예: 5%) | 100% 한 번에 전체 노출 |
| **인프라 자원 비용**| **매우 높음 (2배의 연산 파워 상시 대기)** | 보통 (확장되는 비율만큼 증설) | 높음 (동일 복제 환경 구축) |
| **트래픽 분할 방식**| 100% 복제 (Mirroring) | 비율 기반 할당 (예: 95:5) | 라우팅 일괄 스위칭 (100:0) |
| **최적 도입 환경** | 절대 무결성이 요구되는 금융/보안 도메인 | 에러 발생 시 부분 롤백이 허용되는 커머스 | 서버 다운타임 최소화가 중요한 프론트엔드 |

## Ⅳ. 섀도우 배포 구축 시 3대 기술적 리스크 및 방어 기법
단순 복제가 야기하는 인프라 파국 방지.
1. **Network Latency Penalty (원본 응답 지연)**:
   - *문제*: 미러링 시스템이 섀도우 모델의 추론이 끝날 때까지 기다리느라 원본 응답이 지연됨.
   - *대응*: Istio의 `mirror` 정책을 활용하여, 비동기 스레드 풀(Thread Pool) 기반의 **논블로킹(Non-blocking) 파이어 앤 포겟(Fire-and-forget)** 아키텍처 적용.
2. **Side-effect (상태 변이 오염)**:
   - *문제*: 섀도우 모델이 추론 로직 내에서 외부 DB에 값을 쓰거나(Write) 포인트 차감 API를 호출하여 고객 데이터가 오염됨.
   - *대응*: 섀도우 컨테이너 환경의 **외부 쓰기(Outbound Write) 권한을 IAM 레벨에서 차단(Read-Only)** 하거나, 더미(Mock) DB로 연결을 우회(Stubbing).
3. **Resource Starvation (자원 고갈)**:
   - *문제*: 트래픽을 100% 복제하므로 GPU 비용이 2배로 폭증함.
   - *대응*: 전체 트래픽 중 무작위 10%만 샘플링하여 복제(Sampled Mirroring)하는 방식으로 비용 최적화.

## Ⅴ. 실무 적용 및 결론
- **판단 지표**: 모델 예측 일치율(Discrepancy Rate), 섀도우 환경 OOM 발생 횟수, 운영 모델(Primary)의 P99 응답 지연 증가율(0% 목표).
- **실무 설계**: 자율주행 모빌리티 V사의 '보행자 인식 비전 AI 업그레이드'. 신규 딥러닝 모델 적용 시 오인식으로 인한 급브레이크(생명 직결) 리스크 존재. 조치 방안: 차량 내 NPU 엣지(Edge) 환경 섀도우 배포. 1) 차량 카메라 트래픽을 분기하여, 조향 제어는 기존 모델(v1)이 수행하고 신규 모델(v2)은 백그라운드 연산만 수행. 2) v2가 "보행자 감지"라고 가상 예측(Shadow Prediction)한 이벤트와 실제 레이더 센서 값을 대조하는 로그를 중앙 클라우드로 비동기 전송. 3) 1달간 주행 로그 분석 결과, v2의 눈/비 환경 인식률이 15% 향상되었고 조향 충돌 로직이 없음을 증명한 후 OTA(무선 업데이트)로 전면 배포 승인.
- **결론**: Shadow Deployment는 실패 비용(Cost of Failure)이 천문학적인 엔터프라이즈 AI 환경에서 채택할 수 있는 유일한 '불패의 검증 전략'이다. 서버 비용을 2배로 지불하더라도 비즈니스의 심장을 멈추지 않고 신형 엔진의 출력을 테스트할 수 있다면 그것은 낭비가 아니라 가장 훌륭한 보험이다. MLOps 성숙도는 장애가 터진 후 얼마나 빨리 롤백하는가(Canary)를 넘어, 장애가 사용자에게 도달하기 전 어둠 속에서 미리 소멸시킬 수 있는가(Shadow)에 달려 있다.

### 🔀 문제 유형별 목차 전환
- **Ⅱ·Ⅲ 강조 (개념/원리형)**: 클라우드 네이티브 환경의 트래픽 미러링 기술 원리. Kubernetes 환경에서 서비스 메시(Istio/Envoy) 프록시 계층을 활용하여 애플리케이션 코드 수정(Zero Code Change) 없이 라우팅 룰 설정만으로 L7 계층(HTTP/gRPC) 패킷을 100% 복제하는 아키텍처 도식화.
- **Ⅴ·Ⅵ 강조 (실무/설계형)**: 거대 언어 모델(LLM) 환경에서의 섀도우 배포 한계점 및 해결책 설계. LLM은 생성(Generation) 모델이므로 기존 모델과 신규 모델의 답변 텍스트가 100% 일치할 수 없음. 따라서 단순 텍스트 비교가 아닌, "답변의 유해성(Toxicity), 할루시네이션 지수"를 제3의 평가 모델(LLM-as-a-Judge)을 통해 정량 점수화하여 두 섀도우 답변의 우위를 비교하는 자동 평가 파이프라인 연계 방안.
