# 📖 【암기용】 개념 완전 이해

> 목적: Vector Database를 처음 봐도 완벽히 이해하게 만든다.

## 한눈에
- **개요**: 임베딩 벡터를 저장·색인·검색하고 메타데이터 필터와 함께 관리하는 데이터베이스
- **왜 필요한가**: RAG는 수십만~수억 개 문서 벡터에서 유사한 근거를 100ms 이내에 찾아야 함.
- **핵심 직관**: 문서 의미 좌표를 저장해두고, 질문 좌표와 가까운 점을 ANN 인덱스로 찾아주는 지도 인덱스임.

## 깊이 이해
- **배경·문제의식**: 일반 RDB는 벡터 거리 계산과 ANN 인덱스에 최적화되어 있지 않아 대규모 임베딩 검색 지연이 커진다.
- **작동 원리**: 벡터와 문서 ID, 출처, 권한 메타데이터를 함께 저장하고 HNSW·IVF-PQ 같은 ANN 인덱스로 Top-K 유사 벡터를 반환함.
- **비유**: 모든 문서를 의미 좌표가 찍힌 지도에 올려두고, 질문 위치에서 반경이 가까운 문서를 찾는 공간 검색 엔진임.
- **구체 예시**: 1,536차원 float32 벡터 1억 건은 원시 벡터만 약 614GB가 필요하며, PQ 압축과 샤딩 설계가 필요함.
- **흔한 오해·주의점**: 벡터DB는 정답을 만드는 모델이 아님. 임베딩 품질과 청킹 품질이 낮으면 ANN 검색이 잘못된 문서를 반환함.

## 연결 개념
- ANN Search — 근사 최근접 이웃 검색 알고리즘
- Embedding — 벡터DB에 저장되는 의미 표현
- RAG — 벡터DB를 외부 지식 검색 계층으로 활용

# 📝 【답안용】 시험 답안 템플릿

> 목적: 시험장에서 25분에 그대로 쓰는 답안 양식.

## 핵심 인사이트 (3줄 요약)

> 1. **본질**: Vector Database는 임베딩 벡터를 ANN 인덱스로 저장·검색하는 RAG 검색 인프라임.
> 2. **가치**: 수백만~수억 벡터에서 Recall@10 95%, p95 100ms 이하 검색을 목표로 함.
> 3. **판단 포인트**: 인덱스 방식, 메타데이터 필터, 샤딩, 권한 통제가 운영 품질을 결정함.

## Ⅰ. 개요 및 필요성

- 개요: 벡터 검색 전용 데이터 저장소
- 배경: LLM 서비스는 문서 임베딩을 저장하고 질의와 가까운 근거를 실시간으로 찾기 위한 ANN 검색 계층이 필요함.
- 필요성: HNSW·IVF-PQ, metadata filter, ACL, sharding/replication으로 Recall@K·p95 latency·권한 필터 정확도를 관리해야 함.

## Ⅱ. 구조 및 구성요소

```text
Embedding -> Vector Store -> ANN Index(HNSW/IVF-PQ)
Metadata/ACL -> Filter -> Top-K Search -> Document ID
```

| 구성요소 | 역할 | 특이사항 |
|:---|:---|:---|
| Vector Store | 벡터와 문서 ID 저장 | 384~1,536차원 float/quantized |
| ANN Index | 유사 벡터 Top-K 검색 | HNSW, IVF, PQ, ScaNN |
| Metadata Filter | 출처·날짜·권한 조건 필터링 | tenant_id, ACL, version |
| Sharding/Replication | 대용량·가용성 구성 | 샤드별 1천만~5천만 벡터 기준 |

> 요약: 벡터DB는 벡터 저장, ANN 인덱스, 메타데이터 필터, 샤딩 구성을 결합한 검색 인프라임.

## Ⅲ. 동작원리 및 흐름도

```text
문서 임베딩 -> 벡터 저장/색인 -> 질의 임베딩
  -> 메타데이터 필터 적용 -> ANN Top-K 검색 -> 원문 조회
```

| 단계 | 처리 내용 | 검증 기준 |
|:---:|:---|:---|
| 1 | 문서 벡터와 메타데이터 적재 | upsert 지연 < 1초/1천 건 |
| 2 | HNSW·IVF-PQ 인덱스 생성 | Recall@10 ≥95% |
| 3 | 질의 벡터와 ACL 필터로 Top-K 검색 | p95 <100ms, 권한 위반 0건 |
| 4 | 문서 ID로 원문 조회 후 RAG 전달 | 출처 매핑 성공률 100% |

> 요약: 벡터DB는 색인된 벡터를 권한 조건으로 필터링한 뒤 유사도 Top-K와 원문 식별자를 반환함.

## Ⅳ. 특징

| 구분 | RDB 확장 | 전용 Vector DB | 판단 포인트 |
|:---|:---|:---|:---|
| 검색 규모 | 수십만~수백만 벡터 | 수천만~수억 벡터 | 대규모 RAG는 전용 DB |
| 인덱스 | pgvector HNSW | HNSW, IVF-PQ, 분산 샤딩 | 압축·샤딩 필요성 판단 |
| 운영 기능 | SQL·트랜잭션 강점 | ANN·메타데이터 필터 강점 | 기존 DB 연계 vs 검색 처리량 |
| 비용 | 단일 DB 운영 | 별도 클러스터 비용 | 월 질의·벡터 수로 산정 |

> 요약: 소규모는 pgvector로 충분하지만 대규모 RAG는 전용 Vector DB의 샤딩·압축·검색 처리량이 필요함.

## Ⅴ. 실무 적용 및 결론

**적용 방안 3개:**
1. 사내 RAG: 512토큰 청크, BGE-M3 1,024차원 벡터, Milvus HNSW, tenant_id·ACL 필터 적용
2. 대규모 검색: 1억 벡터는 IVF-PQ 압축과 샤드 4개 구성, p95 100ms·Recall@10 95% 목표
3. 운영 관리: 색인 버전 관리, blue-green index 교체, 검색 실패율 1% 초과 시 자동 롤백

**결론 (2줄):**
- 기술사 판단: 100만 벡터 이하는 pgvector, 1천만 이상 또는 다중 테넌트는 Milvus·Pinecone·Weaviate 검토
- 향후 방향: 벡터 검색은 BM25·Graph DB와 결합된 멀티 인덱스 검색 계층으로 발전
