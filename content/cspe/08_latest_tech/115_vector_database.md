# 📖 【암기용】 개념 완전 이해

## 한눈에
- **정의**: 비정형 데이터(텍스트, 이미지 등)를 머신러닝 모델이 변환한 고차원 숫자 배열(Embedding Vector)로 저장하고, 벡터 간의 유사도(거리)를 빛의 속도로 연산하여 검색해 주는 특수 목적 데이터베이스.
- **필요성**: 기존 RDB(관계형 DB)는 "나이가 30 이상인 사람" 같이 정확한 조건(SQL)으로 찾는 덴 천재지만, "이 문장과 '가장 느낌이 비슷한' 문장 찾아줘"라는 유사도 계산(수백만 번의 실수 내적 연산)을 시키면 서버가 터지거나 수 분이 걸림.
- **핵심 직관**: 모든 데이터를 1,536차원의 광활한 우주 공간에 떠 있는 수많은 별(점)들로 찍어놓음. 새로운 질문 별이 하나 나타났을 때, 우주 전체를 다 뒤지지 않고(Exact Search), 똑똑한 우주 지도(ANN 인덱스)를 이용해 가장 가까운 이웃 별 5개만 0.01초 만에 싹 잡아오는 전용 내비게이션.

## 깊이 이해
- **배경**: 생성형 AI와 RAG 아키텍처가 대유행하면서, LLM이 문서를 참고하게 하려면 방대한 사내 문서를 '벡터화'해 놓고 초고속으로 검색할 인프라가 필요해짐. Milvus, Pinecone, Qdrant 등이 1조 원 단위 투자를 받으며 급부상.
- **작동 원리 (데이터 저장과 ANN 검색)**:
  1. (저장): 원본 텍스트 + 임베딩 벡터값(예: [0.1, -0.23, ...]) + 메타데이터(저자, 날짜 등)를 함께 저장.
  2. (인덱싱): 수백만 개의 벡터를 찾기 쉽게 군집으로 묶거나(IVF) 다층 그래프(HNSW)로 엮어놓음. (여기서 100% 완벽한 정답은 포기하되 99% 근사치를 100배 빨리 찾는 ANN 기술 적용).
  3. (검색/유사도 연산): 코사인 유사도(방향성)나 L2 거리(유클리디안 물리적 거리)를 연산하여 Top-K 추출.
- **비유**: 한남동에서 가장 맛있는 카페를 찾을 때, 대한민국 모든 건물을 다 조사(RDB 방식)하는 게 아니라, 일단 용산구로 좁히고(IVF), 길을 따라가면서(HNSW) 가까운 3곳만 추천받는 것.
- **흔한 오해/주의점**: 벡터 DB 자체는 AI 모델이 아님! 텍스트를 이해하거나 추론하는 능력은 1도 없고, 그냥 '숫자 배열의 거리'를 빠르게 계산해 주는 엑셀(DB)일 뿐임. 임베딩 모델(OpenAI 등)이 쓰레기 벡터를 만들어 넣으면 벡터 DB는 0.01초 만에 가장 비슷한 쓰레기를 찾아줌 (Garbage in, Garbage out).

## 연결 개념
- **Embedding (임베딩)**: 벡터 DB에 저장되는 본체. 비정형 데이터를 숫자로 압축한 엑기스.
- **ANN (Approximate Nearest Neighbor)**: 수백만 건의 벡터를 실시간 연산하기 위해 정확도를 아주 조금 포기하고 속도를 극한으로 끌어올리는 벡터 DB의 심장 알고리즘. (HNSW가 대세).
- **pgvector**: 기존 PostgreSQL 같은 전통 RDB에 플러그인을 붙여 벡터 DB처럼 쓰게 해주는 기술. (초기 도입 시 가성비 좋음).

# 📝 【답안용】 시험 답안 템플릿
## 핵심 인사이트 (3줄 요약)
- **본질**: 고차원 공간의 임베딩 벡터(Embedding Vector) 저장과 근사 최근접 이웃(ANN: Approximate Nearest Neighbor) 기반의 유사도 검색에 최적화된 비정형 데이터 전용 인프라스트럭처.
- **가치**: 기존 DBMS가 처리할 수 없는 초거대 차원(768~1536) 행렬의 실시간 내적/코사인 거리를 밀리초(ms) 단위로 연산하여, RAG 등 엔터프라이즈 AI 서비스의 검색 지연 병목(Latency Bottleneck)을 해소.
- **판단 포인트**: 데이터 규모 및 갱신 빈도에 따른 인덱싱 알고리즘(HNSW vs IVF-PQ) 취사선택, 벡터 전용 DB(Milvus)와 RDB 확장형(pgvector) 간의 트레이드오프(아키텍처 복잡성 vs 유지보수성) 판단.

## Ⅰ. 개요 및 필요성
- **정의**: 비정형 데이터(문서, 이미지, 오디오)의 의미론적 특성(Semantics)을 추출한 다차원 실수 배열(벡터)과 그 메타데이터를 저장, 관리하고 대규모 유사도 연산을 가속화하는 시스템.
- **배경**: 기존 관계형 DB 구조로는 벡터 간의 기하학적 거리 연산(KNN: K-Nearest Neighbor) 수행 시 데이터 수 증가에 따라 연산량이 선형 비례하여 $O(N)$의 치명적 성능 저하(Full Scan)가 발생.
- **필요성**: 생성형 AI 워크로드에서 파생되는 수억 건의 벡터를 메모리 상에서 고압축/고속 탐색하여, RAG 파이프라인의 실시간 추론 품질과 처리량(Throughput)을 보장하기 위함.

## Ⅱ. Vector DB 핵심 아키텍처 구성 요소
```text
[ Embedding Model ] -> (생성된 고차원 벡터)
                           |
+--------------------[ Vector Database ]--------------------+
| 1. Storage Engine    : 벡터 데이터 + 스칼라 메타데이터 병합 보관 |
| 2. ANN Indexing      : HNSW, IVF-PQ 등 고속 탐색 트리/그래프 구축|
| 3. Query Processing  : 거리 산출 (Cosine, L2/Euclidean, Dot)     |
| 4. Filtering (ACL)   : 메타데이터 기반 조건부 사전/사후 필터링   |
+---------------------------------------------------------+
                           | (Top-K 반환)
                     [ LLM Generator ]
```

## Ⅲ. 심화: 고속 탐색을 위한 핵심 ANN 알고리즘 비교
모든 데이터를 다 뒤지는 완전 탐색(KNN) 대신 속도를 택하는 근사 탐색(ANN) 적용.
| 인덱스 알고리즘 | 동작 메커니즘 | 장점 | 단점 (Trade-off) |
|:---:|:---|:---|:---|
| **IVF (Inverted File)** | 벡터 공간을 여러 개의 군집(Voronoi Cell)으로 쪼개고, 질의가 속한 군집 내에서만 검색. | 대규모 데이터 압축 효율, 빠른 훈련 속도. | 엣지 케이스에서 정확도(Recall)가 다소 떨어짐. |
| **PQ (Product Quantization)** | 고차원 벡터를 짧은 서브 벡터로 쪼개고 양자화(근사치 압축)하여 저장. | 메모리 사용량 획기적 감소 (비용 최적화). | 압축 손실 발생. (IVF-PQ 형태로 주로 결합 사용). |
| **HNSW (Hierarchical Navigable Small World)** | 다층 노드 그래프를 구축하여 상층부(듬성듬성)에서 하층부(조밀)로 고속 점프 탐색. | **압도적인 검색 속도와 매우 높은 재현율(Recall). 현재 업계 표준.** | 메모리를 엄청나게 소모함, 인덱스 구축 시간 오래 걸림. |

## Ⅳ. 도입 및 선택 전략 (Native vs Plugin)
| 구분 | Native Vector DB (전용) | RDB/NoSQL Plugin (확장) |
|:---:|:---|:---|
| **대표 솔루션** | Milvus, Pinecone, Qdrant, Chroma | PostgreSQL (pgvector), Elasticsearch |
| **설계 사상** | 오직 벡터 연산과 분산 처리를 위해 밑바닥부터 C++/Rust로 설계. | 기존 데이터베이스 엔진에 거리 연산 함수와 ANN 인덱스 기능 덧붙임. |
| **확장성/성능** | 수십억 건 벡터 클러스터링(분산 아키텍처)에 탁월, 밀리초 단위 응답. | 기존 RDB의 확장 한계를 따름. 수천만 건 이상 시 병목. |
| **도입 판단** | **엔터프라이즈급 대규모 RAG**, 독립적인 초고속 AI 검색 레이어 필요 시. | **초기 PoC, 중소규모 RAG**, 기존 DB 연동성 및 트랜잭션(ACID) 일관성 중요 시. |

## Ⅴ. 운영 고려사항 (리스크 및 튜닝 전략)
- **리스크 1: 메타데이터 필터링 병목 (Pre/Post-Filtering 딜레마)**:
  - "특정 권한(ACL)을 가진 부서 문서 중 관련 문서"를 찾을 때, ANN 검색을 먼저 하고 권한을 나중에 필터링(Post-filtering)하면 결과값이 빈 깡통이 될 수 있음. 권한 필터링 먼저(Pre-filtering)하면 ANN 그래프 구조가 망가짐.
  - **대응 방안**: 메타데이터 조건과 ANN 트리를 결합하는 Single-stage Filtering(또는 인-메모리 비트맵 필터 혼합 방식)을 지원하는 최신 Vector DB(Milvus 등) 엔진 적용.
- **리스크 2: 메모리(FinOps) 폭발적 증가**:
  - HNSW 방식은 모든 인덱스를 RAM(메모리)에 올려야 하므로 클라우드 인프라 비용이 급증.
  - **대응 방안**: 스토리지 계층화(Tiering). 자주 찾는 핫(Hot) 데이터는 RAM에 올리고, 콜드 데이터는 NVMe/SSD 기반의 디스크 인덱스(DiskANN 등)로 내리는 하이브리드 스토리지 구성 설계.

## Ⅵ. 실무 적용 및 결론
- **판단 지표**: QPS(초당 쿼리 처리량), Latency(지연 시간), Recall@K(ANN 도입에 따른 정확도 손실률).
- **실무 설계**: 대형 법무법인의 1억 건 판례 검색 RAG 시스템 구축 시. 초기 PostgreSQL(pgvector)로 PoC를 하였으나 데이터 1,000만 건 초과 시 쿼리 지연이 2초 이상 발생. 이에 분산 아키텍처 전용인 Milvus DB로 마이그레이션 단행. 인덱싱은 IVF-PQ 기반으로 메모리 자원을 70% 절약하면서도, QPS를 10배 향상시키고 P95 응답 속도 50ms 미만을 달성함.
- **결론**: Vector DB는 단순히 데이터를 저장하는 그릇이 아니라 고차원 수학 연산을 실시간으로 소화하는 'AI 연산 엔진'이며, 엔터프라이즈 환경에서 지식 검색의 물리적 한계를 돌파하는 인프라의 최종 퍼즐 조각임.

### 🔀 문제 유형별 목차 전환
- **Ⅱ·Ⅲ 강조 (개념/원리형)**: HNSW의 스킵 리스트(Skip-list) 유사 층별 그래프 구조 원리, 코사인 유사도와 내적(Dot Product)의 수학적 차이 및 임베딩 정규화(Normalization) 중심 서술.
- **Ⅴ·Ⅵ 강조 (실무/설계형)**: 하이브리드 서치(Hybrid Search) 지원 여부, RBAC(접근 통제) 연계 필터링 아키텍처, Native와 Plugin 형태 간의 TCO(총소유비용) 비교 분석 작성.
