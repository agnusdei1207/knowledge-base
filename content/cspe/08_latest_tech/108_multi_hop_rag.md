# 📖 【암기용】 개념 완전 이해

## 한눈에
- **정의**: 한 번의 검색(Single-hop)으로 정답을 찾을 수 없는 복잡한 질문에 대해, 이전 검색 결과를 단서 삼아 다음 검색을 이어나가며(여러 단계의 홉) 파편화된 근거들을 연결해 답변하는 RAG 기법.
- **필요성**: "A회사의 CEO가 졸업한 대학의 설립 연도는?"이라는 질문은 한 문서에 없을 가능성이 큼. "A회사 CEO 검색 $\rightarrow$ 일론 머스크 확인 $\rightarrow$ 일론 머스크 졸업 대학 검색 $\rightarrow$ 펜실베니아 대학 확인 $\rightarrow$ 설립 연도 검색"처럼 논리적 사슬이 필요함.
- **핵심 직관**: 탐정이 살인 사건을 수사할 때 한 번의 탐문으로 범인을 잡는 게 아니라, 용의자 A의 알리바이를 조사하고, 그 결과에서 B의 이름을 알아내어, 다시 B를 추궁하며 진실의 퍼즐을 맞춰 나가는(Multi-hop) 과정.

## 깊이 이해
- **배경**: 지식 기반이 방대해지고 질문이 고도화(원인-결과, 교차 비교 등)되면서, 단순 벡터 검색(Top-K)이 가진 구조적 한계(문맥 단절)를 극복하기 위해 등장함.
- **작동 원리 (Chain of Retrievals)**:
  1. 복잡한 원본 질문을 분해(Decomposition)하거나, 첫 번째 키워드로 1차 검색(Hop-1).
  2. 1차 검색 결과에서 새로운 단서(Entity)나 조건을 추출.
  3. 추출된 단서를 바탕으로 2차 검색(Hop-2)을 수행.
  4. 이를 N번 반복(N-Hop)하여 충분한 근거(Supporting Facts)가 모이면 이를 통합(Synthesize)하여 최종 답변을 생성.
- **구체 예시**: 사내 IT 헬프데스크. 질문: "어제 서버 다운된 거, 원인 제공한 배포 건의 담당자 연락처 줘." $\rightarrow$ (Hop 1): 장애 보고서 검색해 원인 서비스 '결제 API v2' 확인 $\rightarrow$ (Hop 2): 배포 이력 검색해 결제 API v2 배포자 '김철수' 확인 $\rightarrow$ (Hop 3): 사내 조직도 검색해 김철수 연락처 확인.
- **흔한 오해/주의점**: 검색(Hop) 횟수가 늘어난다고 무조건 좋은 게 아님. 1차 검색에서 엉뚱한 사람을 찾아오면 2차, 3차 검색은 완전히 산으로 감(오류 전파, Error Propagation). Hop별 엄격한 검증 로직이 필수임.

## 연결 개념
- **Agentic RAG**: LLM 비서가 Multi-hop 검색의 횟수와 계획을 스스로 판단하여 동적으로 수행하는 상위 호환 프레임워크.
- **Graph RAG**: 여러 홉(Hop)을 건너야 하는 관계 검색을 가장 효율적으로 수행하기 위해 아예 데이터 자체를 그래프(지식 구조도)로 만들어 놓는 아키텍처.
- **Query Decomposition (질의 분해)**: Multi-hop 수행 전에 복잡한 쿼리를 여러 개의 단순한 서브 쿼리로 쪼개는 전처리 기술.

# 📝 【답안용】 시험 답안 템플릿
## 핵심 인사이트 (3줄 요약)
- **본질**: 파편화된 다중 문서 간의 인과관계, 종속성, 교차 비교 등을 처리하기 위해, 선행 검색 결과를 후행 검색의 입력(단서)으로 사용하여 근거 체인(Evidence Chain)을 구성하는 반복 검색 파이프라인.
- **가치**: 단일 벡터 검색으로는 도저히 매칭할 수 없는 고난도 추론(Complex Reasoning) 질의에 대한 정보 접근성(Supporting Fact Recall)을 획기적으로 향상시켜 엔터프라이즈 AI의 활용 범위를 대폭 확장.
- **판단 포인트**: 단계적 오류 누적(Error Propagation)을 차단하기 위한 홉(Hop)별 신뢰도 검증 메커니즘, 적정 최대 반복 횟수(Max Hops) 제약, 그리고 응답 지연(Latency) 증가에 대한 SLA 관리.

## Ⅰ. 개요 및 필요성
- **정의**: 단일 문서에 명시되지 않은 복합적 정보 요구를 충족하기 위해, 질의를 분해하고 중간 추출된 엔티티(Entity)를 징검다리 삼아 복수의 검색-탐색 주기를 순차적으로 수행하는 검색 증강 기법.
- **배경**: "A 시스템 장애가 B 부서의 이번 달 KPI에 미친 영향은?"과 같은 비즈니스 핵심 질의는 원인(장애 로그) $\rightarrow$ 영향(의존성) $\rightarrow$ 결과(매출/KPI)의 연결고리가 분산되어 있어 기본 RAG로는 답변 불가함.
- **필요성**: 이종 데이터 사일로(Data Silo)에 흩어진 정보 조각들을 엮어(Connecting the dots) 인간 수준의 논리적 조사(Investigation) 역량을 AI에 부여하기 위함.

## Ⅱ. Multi-hop RAG 아키텍처 및 메커니즘
```text
[ User Query (복잡 질의) ]
        |
        v
[ Query Decomposer (질의 분해기) ] -> Sub-Query 1, 2 생성
        |
+-------+-- (Hop 1) -------------------------------+
| [ Retriever ] -> 1차 문서 검색                   |
| [ Evidence Extractor ] -> 중간 단서(Entity) 추출 |
+-------+------------------------------------------+
        | (단서를 바탕으로 다음 질의 생성)
+-------+-- (Hop 2) -------------------------------+
| [ Retriever ] -> 2차 문서 검색 (단서 연계)       |
| [ Validator ] -> 근거 충분성 검증                |
+-------+------------------------------------------+
        | (충분한 근거 체인 확보)
        v
[ Synthesizer (통합 생성기) ] -> 최종 응답 및 다중 출처 생성
```

## Ⅲ. 핵심 해결 과제 (구현 패턴)
1. **질의 분해 기반 패턴 (Query Decomposition)**:
   - 복합 질의를 독립적인 하위 질의로 병렬화. "A와 B의 차이는?" $\rightarrow$ "A 검색", "B 검색" 동시 수행 후 병합.
2. **순차적 추론 패턴 (Sequential Reasoning)**:
   - 이전 검색 결과가 없으면 다음 검색이 불가능한 직렬화. (CEO 검색 $\rightarrow$ 출신 학교 검색).
3. **지식 그래프 연계 (Graph-based)**:
   - 여러 문서를 점프(Hop)하는 대신, 문서들의 연관 관계를 미리 지식 그래프(Knowledge Graph)로 구축해 두고 그래프 순회 알고리즘으로 경로(Path)를 탐색.

## Ⅳ. Single-hop vs Multi-hop RAG 비교
| 구분 | Single-hop RAG (기본) | Multi-hop RAG |
|:---:|:---|:---|
| **검색 횟수** | 1회 (Top-K 추출 후 종료) | **N회 (조건 충족 시까지 반복)** |
| **적합한 질의**| 단순 팩트 확인, 단일 정책 조회 | 인과관계 분석, 다자간 비교, 장애 원인 추적 |
| **추론 방식** | 단문서 요약 (Shallow) | **다문서 연쇄 추론 (Deep)** |
| **지연 시간** | 짧음 (1~2초 이내) | 김 (반복 횟수에 비례하여 N초 소요) |
| **취약점** | 맥락 분절 시 오답 반환 | **오류 전파(Error Propagation)** |

## Ⅴ. 한계점(운영 리스크) 및 통제 전략
- **리스크 1: 오류 전파 (Error Propagation)**:
  - 1-hop 단계에서 일론 머스크 대신 빌 게이츠를 찾아오면, 2-hop, 3-hop 검색은 모두 쓰레기 정보를 양산함(전체 체인 붕괴).
  - **대응 방안**: 각 Hop이 끝날 때마다 '신뢰도(Confidence Score)'를 측정하는 게이트(Gate) 설치. 신뢰도가 0.7 이하일 경우 다음 Hop으로 넘어가지 않고 1-hop 검색의 키워드를 수정하여 재검색(Self-correction).
- **리스크 2: 무한 루프 및 과도한 지연 (Latency Blow-up)**:
  - 계속해서 새로운 단서가 나오면 검색을 멈추지 않아 타임아웃(Time-out) 발생.
  - **대응 방안**: Max-Hops를 3~4회로 하드 코딩(Hard-limit)하고, 캐싱(Caching) 레이어를 두어 반복되는 중간 질의는 벡터 DB를 타지 않고 즉시 반환하도록 최적화.

## Ⅵ. 실무 적용 및 결론
- **판단 지표**: Supporting Fact Recall(정답 도출에 필요한 모든 징검다리 근거 문서를 수집했는가), End-to-End Latency, 복합 질의 정확도.
- **실무 설계**: 클라우드 인프라 장애 원인 분석(RCA) 시스템. 엔지니어가 "주문 API 타임아웃의 근본 원인을 찾아라"라고 질문. 시스템은 (Hop-1) 주문 API 서버 로그 분석 $\rightarrow$ (Hop-2) 연관된 DB 락(Lock) 이벤트 검색 $\rightarrow$ (Hop-3) 해당 시간에 배포된 DB 스키마 변경 문서 검색. 세 단계의 근거 체인을 종합하여 "DB 스키마 변경으로 인한 락 발생이 원인"임을 다중 출처(Log, Metric, Doc)와 함께 제시.
- **결론**: Multi-hop RAG는 파편화된 엔터프라이즈 데이터의 사일로를 허물고, 단순 지식 검색을 넘어선 인과적/분석적 AI 에이전트로 나아가기 위한 핵심 브리지(Bridge) 기술임.

### 🔀 문제 유형별 목차 전환
- **Ⅱ·Ⅲ 강조 (개념/원리형)**: 질의 분해(Decomposition) 알고리즘, 순차적 홉(Hop) 간의 엔티티 치환(Entity Substitution) 로직 등 다단계 검색 메커니즘 중심 서술.
- **Ⅴ·Ⅵ 강조 (실무/설계형)**: 오류 전파(Cascading Errors) 방지를 위한 검증 로직 구현, HotpotQA 등 다중 홉 벤치마크 지표, Graph RAG와의 아키텍처 비교 우위(Trade-off) 관점 작성.
