## 미리 알고가기

- TEE는 CPU나 SoC 내부의 격리된 실행 구역에서 코드와 데이터를 보호하는 하드웨어 보안 기술임
- 운영체제나 하이퍼바이저가 침해되어도 enclave 내부 자산을 분리하는 것이 핵심 목표임
- 원격 증명이 실제 배포에서 키 제공과 신뢰 연결의 기준점이 됨

## Ⅰ. 개요

- **정의/개념**: 신뢰실행환경은 일반 실행 영역과 분리된 하드웨어 기반 격리 구역에서 민감한 코드와 데이터를 실행해 기밀성과 무결성을 보호하는 보안 실행 기술임
- **배경/필요성**: 저장 데이터와 전송 데이터가 암호화되어도 연산 중 메모리에 평문이 노출되면 내부자와 메모리 덤프 공격에 취약하므로, 실행 중 데이터 보호를 위한 격리 구조가 필요해짐

## Ⅱ. 특징

- OS나 하이퍼바이저보다 작은 신뢰 경계를 만들어 공격 표면을 줄임
- 메모리 격리와 코드 무결성과 원격 증명을 함께 제공해 클라우드 신뢰 문제를 완화함
- enclave 전환과 제한된 시스템 인터페이스로 인해 개발과 디버깅 복잡도가 증가할 수 있음
- 부채널 공격과 마이크로아키텍처 취약점에 대한 지속적 패치가 필요함

## Ⅲ. 종류 및 비교

| 판단 기준 | ARM TrustZone | Intel SGX | AMD SEV |
|:---|:---|:---|:---|
| 보호 단위 | secure world | 애플리케이션 enclave | VM 메모리 |
| 장점 | 모바일·임베디드 적합 | 세밀한 격리 | 레거시 VM 호환성 높음 |
| 한계 | OS 분리 의존 | 개발 복잡도 큼 | 세밀한 앱 단위 통제는 약함 |
| 대표 활용 | 결제, 생체인증 | 기밀 앱, 증명형 서비스 | confidential VM |

## Ⅳ. 구성요소 및 구조

| 구성요소 | 설명 |
|:---|:---|
| Enclave, Secure World | 민감 코드와 데이터를 일반 실행 영역과 분리해 접근을 제한하는 격리 공간임 |
| Memory Protection | 하드웨어 암호화와 접근 제어로 외부 메모리 읽기와 변조를 방지함 |
| Attestation | 현재 실행 중인 코드와 환경이 신뢰 가능한지 외부 검증자에게 증명함 |
| Secure Key Release | 증명 성공 시에만 비밀키나 민감 설정을 enclave에 제공해 신뢰 사슬을 완성함 |
| Trusted Interface | 외부와 최소한의 입출력 인터페이스만 허용해 공격면을 줄임 |

```text
+-------------------+      +-------------------+      +-------------------+
| Normal World      | ---> | Enclave / TEE     | ---> | Attestation       |
+-------------------+      +-------------------+      +-------------------+
                                                           |
                                                           v
                                                   +-------------------+
                                                   | Key Release       |
                                                   +-------------------+
```

## Ⅴ. 원리 및 절차 흐름도

```text
+-------------+     +-------------+     +-------------+     +-------------+
| 격리 영역 생성   | --> | 코드/데이터 적재 | --> | 원격 증명 수행  | --> | 키 수신 후 실행  |
+-------------+     +-------------+     +-------------+     +-------------+
```

1. **격리 영역 생성**: 하드웨어가 enclave나 secure world를 준비함
2. **코드 및 데이터 적재**: 승인된 코드와 입력이 격리 구역에 로드됨
3. **원격 증명 수행**: 외부 검증자가 실행 무결성을 확인함
4. **키 수신 후 실행**: 신뢰가 검증된 경우에만 비밀키와 민감 연산을 허용함

## Ⅵ. 문제점 및 해결 방안

1. 문제: enclave 경계 밖과의 상호작용이 많아질수록 TCB가 커지고 기대한 격리 효과가 약해질 수 있음
   - 해결방안: minimal TCB와 narrow interface를 설계하고 TCB size와 interface exposure count로 검증함
2. 문제: 부채널 공격이나 마이크로코드 취약점이 존재하면 하드웨어 격리만 믿고 운영한 시스템이 무력화될 수 있음
   - 해결방안: microcode patch와 side-channel hardening을 적용하고 vulnerability remediation time과 leakage test result로 검증함
3. 문제: enclave I/O와 디버깅 제약이 커서 기존 애플리케이션 포팅 비용이 예상보다 커질 수 있음
   - 해결방안: library OS와 staged porting을 적용하고 porting effort와 runtime overhead로 검증함

## Ⅶ. 적용 사례

- 모바일 결제 서비스가 생체인증 비밀을 TEE 내부에서만 처리하며 확인 지표는 attestation success rate와 credential leakage rate임
- 퍼블릭 클라우드의 기밀 워크로드가 TEE 기반으로 민감 연산을 수행하며 확인 지표는 in-use data exposure rate와 enclave overhead임
- 기업 AI 서비스가 원격 증명 후에만 모델 키를 수령해 추론을 시작하며 확인 지표는 key release policy compliance와 startup latency임

## Ⅷ. 결론

TEE는 실행 중 데이터 보호를 하드웨어 수준으로 끌어올리는 현실적 수단이므로 원격 증명과 최소 신뢰 경계 설계가 실효성을 좌우함.
