## Ⅰ. 개요
- **정의**: 대화 세션 종료 후에도 사용자 팩트·선호를 외부 DB에 영구 보존하고 유사도 기반으로 인출하는 기억 저장소
- **배경/필요성**: 에이전트 메모리의 이원 구조 중(→016 참조) 장기 기억은 세션 간 연속성을 담당함. 매 세션마다 사용자 정보를 재입력하는 UX 피로를 제거하고 시간 축적형 개인화를 실현하기 위해 필수적임
- **비유**: 서랍 깊숙이 보관하는 비밀 노트 — 몇 달 뒤에도 꺼내 읽을 수 있음

| 출제 의도 | 반드시 짚을 핵심 | 감점 회피 포인트 |
|:---|:---|:---|
| Vector DB vs Knowledge Graph 구현 비교 | 임베딩 기반 의미 검색과 트리플 기반 관계 추론 | 단순 "DB에 저장"이 아닌 Extraction→Encoding→Storage→Retrieval→Update 생애주기 설명 |
| 개인정보보호 아키텍처 설계 | PII 스크러빙, GDPR 삭제권 대응 | 기억 충돌(Conflict) 해소 로직과 망각(Forget) 메커니즘 포함 필요 |

> 요약: 세션 간 연속성과 개인화를 위해 Vector DB·Knowledge Graph에 팩트를 영구 저장하고 유사도 기반으로 인출하는 아키텍처

## Ⅱ. 구성요소
```text
+--------------------------------------------------+
|          Long-term Memory Pipeline               |
|  +------------------+                            |
|  | Extraction       | -- LLM으로 핵심 팩트 추출    |
|  +--------+---------+                            |
|           |                                      |
|           v                                      |
|  +------------------+    +-------------------+   |
|  | Vector Store     |    | Knowledge Graph   |   |
|  | (Embedding 저장)  |    | (Triple 관계 저장)  |   |
|  | Pinecone/Milvus  |    | Neo4j/NebulaGraph |   |
|  +--------+---------+    +---------+---------+   |
|           |                        |             |
|           +----------+-------------+             |
|                      v                           |
|           +---------------------+                |
|           | Retrieval Engine    |                |
|           | (Hybrid Search)     |                |
|           +----------+----------+                |
|                      |                           |
|                      v                           |
|           +---------------------+                |
|           | Update / Forget     |                |
|           | (생애주기 관리)       |                |
|           +---------------------+                |
+--------------------------------------------------+
```

| 구성요소 | 설명 | 비유 |
|:---|:---|:---|
| Extraction & Reflection | 잡담 속에서 장기 보존 가치가 있는 팩트·선호·이벤트를 LLM으로 선별 추출 | 일기 쓸 때 중요한 것만 골라 적음 |
| Vector Store | 텍스트를 고차원 벡터(1536d)로 변환하여 의미 유사도 검색 가능하게 저장 | 도서관 색인 카드 — 의미로 분류 |
| Knowledge Graph | 주어-술어-목적어 트리플로 개체 간 관계를 그래프 구조로 저장 | 인물 관계도 — 논리 추론에 강점 |
| Update & Forget | 신규 팩트와 기존 기억 충돌 시 최신 정보로 갱신하거나 폐기하는 생애주기 관리 | 주소 변경 시 옛 주소를 덮어씀 |

> 요약: 추출→벡터/그래프 이중 저장→하이브리드 검색→갱신/망각의 생애주기 파이프라인

## Ⅲ. 절차
```text
+----------------+     +----------------+     +------------------+     +----------------+
| 1. Extraction  | --> | 2. Encoding    | --> | 3. Retrieval     | --> | 4. Update      |
| (팩트 추출)     |     | (임베딩/트리플) |     | (유사도 검색)     |     | (갱신/망각)     |
+----------------+     +----------------+     +------------------+     +----------------+
```

1. **Extraction(팩트 추출)** — 대화 스트림에서 LLM이 "이 유저는 해산물 알레르기 있음" 등 장기 보존 팩트를 자동 식별·요약함
2. **Encoding(임베딩/트리플 변환)** — Vector DB 방식은 텍스트를 1536차원 벡터로 변환, Graph DB 방식은 [User]--(allergy)-->[Seafood] 트리플로 구조화함
3. **Retrieval(유사도 검색)** — 새 입력이 들어오면 Cosine Similarity + Time Decay 가중치를 결합한 하이브리드 스코어로 관련 기억을 인출함
4. **Update & Forget(갱신/망각)** — "강아지를 다른 집에 보냄" 등 신규 팩트가 기존 기억과 충돌하면 Recency 우선으로 갱신하거나 아카이브함

> 요약: 팩트 추출 → 이중 인코딩 → 시간 가중 검색 → 충돌 해소의 4단계

## Ⅳ. 문제점
- **기억 오염(Memory Contamination)**: 환각으로 생성된 잘못된 팩트가 장기 기억에 고착화됨 — LLM 추출 단계의 정확도 한계가 원인
- **프라이버시 침해**: 사용자가 무심코 입력한 주민번호·비밀번호가 벡터로 영구 저장됨 — 입력 시점 PII 필터링 부재가 원인
- **검색 지연(Retrieval Latency)**: 기억 누적량 증가 시 벡터 인덱스 검색 시간이 선형 증가함 — 인덱스 파티셔닝 미적용이 원인

> 요약: 오염 고착화, 개인정보 영구저장 위험, 검색 성능 저하가 장기 기억의 3대 난제

## Ⅴ. 개선방안
1. 단기: PII 스크러빙 전처리 — 기억 Insert 직전 정규식+NER 모델로 민감 정보를 마스킹 처리
2. 중기: 팩트 검증 체인 — 추출된 팩트를 별도 LLM이 교차 검증한 후에만 DB에 커밋하는 이중 확인 파이프라인 적용
3. 장기: GraphRAG 하이브리드 — Vector DB의 의미 검색 + Knowledge Graph의 관계 추론을 결합하여 검색 정확도와 추론 깊이를 동시 확보

- **검색 지연**: 기억량 증가에 따른 인덱스 비대화 → ANN 인덱스(HNSW) + 시간 기반 파티셔닝 적용 (지표: p99 검색 지연 < 100ms)

> 요약: PII 마스킹 → 팩트 이중 검증 → GraphRAG 하이브리드로 보안·정합성·성능 확보

## Ⅵ. 전망
- **향후 발전 방향**: Microsoft GraphRAG처럼 사용자 주변 인물·관심사를 그래프로 연결하는 관계형 장기 기억이 단순 벡터 검색을 대체하며 추론 깊이를 확장할 전망
- **기술사적 판단**: 거대 Context Window가 장기 기억을 완전 대체하기는 어려움. 수년간 누적된 팩트를 매 호출마다 전송하는 것은 비용·지연 측면에서 비현실적이며, 영구 저장소 기반 장기 기억은 지속적 필요성을 가짐
- **기술사 제언**: GDPR 삭제권(Right to Erasure) 대응을 위해 기억 단위별 삭제 API와 벡터 인덱스 재구축 파이프라인을 아키텍처 설계 초기에 포함할 것을 권고함
