# 📖 【암기용】 개념 완전 이해

> 목적: CDC를 처음 봐도 완벽히 이해하게 만든다. 시험 답안 양식이 아니라, 이해를 위한 친절한 설명이다.

## 한눈에
- **개요**: 데이터베이스(DB)에 데이터가 추가, 수정, 삭제될 때 그 '변경 사항'만 즉시 감지하여 다른 시스템으로 전달하는 기술
- **왜 필요한가**: 과거에는 매일 밤 DB 전체를 복사(Full Load)했지만, 데이터가 너무 많아지면 시간이 너무 오래 걸리고 DB에 부하를 준다. 변경된 것만 골라 보내면 훨씬 빠르고 가볍게 동기화할 수 있기 때문이다.
- **핵심 직관**: "DB의 모든 이력을 실시간으로 중계하는 'CCTV'이자 '중계 방송'."

## 깊이 이해
- **배경·문제의식**: 서비스용 DB와 분석용 DB(DW)를 따로 두는 경우가 많음. 두 DB를 동기화할 때 '업데이트된 날짜' 컬럼이 없으면 무엇이 변했는지 알 수 없고, 삭제된 데이터는 추적하기 힘듦. 또한 운영 중인 DB에 조회 쿼리를 세게 날리면 서비스가 느려짐.
- **작동 원리**: 대부분의 DB는 장애 복구를 위해 모든 변경 이력을 '로그(Redo Log, Binlog 등)'에 기록함. CDC는 이 로그를 직접 읽어서(Log-based) 서비스에 영향을 주지 않고 변경 내용만 가로챔.
- **비유**: 은행 거래 내역 알림 서비스와 같음. 내 통장 잔액을 매번 확인하는 게 아니라, 입출금이 일어나는 '사건(Event)'이 발생할 때마다 은행이 내 폰으로 푸시 알림을 보내주는 것.
- **구체 예시**: 고객이 쇼핑몰에서 주소를 바꾸면(Update), CDC 도구(Debezium 등)가 DB 로그에서 이를 포착해 카프카(Kafka)로 보냄. 카프카는 이를 검색 엔진(Elasticsearch)과 물류 시스템에 전달해 즉시 반영함.
- **흔한 오해·주의점**: 쿼리 기반(Query-based) CDC도 있지만, 이는 삭제된 데이터를 알기 어렵고 DB 부하가 있어 최근에는 로그 기반(Log-based) CDC를 주로 의미함.

## 연결 개념
- Transaction Log - CDC가 데이터를 추출하는 원천 (Redo, Binlog 등)
- Debezium - 가장 널리 쓰이는 오픈소스 CDC 도구
- Real-time ETL - CDC를 활용한 지연 없는 데이터 통합 방식

# 📝 【답안용】 시험 답안 템플릿

> 목적: 시험장에서 25분에 그대로 쓰는 답안 양식. 작성방식(추상표현 금지·수치·도식·문제유형 전환)을 엄격히 지킨다.
> 핵심: 로그 기반 CDC(Log-based CDC)의 비침해적(Non-intrusive) 특성과 실시간성, 그리고 데이터 일관성 유지 메커니즘을 강조한다.

## 핵심 인사이트 (3줄 요약)

> 1. **본질**: CDC는 원천 데이터베이스에서 발생하는 삽입(Insert), 수정(Update), 삭제(Delete) 이벤트를 실시간으로 식별하고 추출하여 타겟 시스템에 전달하는 기술이다.
> 2. **가치**: 운영 DB에 부하를 주지 않는 비침해적 동기화를 실현하며, 데이터 레이크와 검색 엔진의 실시간성을 확보하여 '단일 진실 공급원(SSOT)'을 유지한다.
> 3. **판단 포인트**: 쿼리 방식의 한계를 극복하기 위해 DB 엔진의 트랜잭션 로그를 직접 파싱하는 로그 기반 방식의 구현이 기술적 핵심이다.

## 출제 의도 및 답안 포인트

| 출제 의도 | 반드시 짚을 핵심 | 감점 회피 포인트 |
|:---|:---|:---|
| 데이터 동기화 기법 이해 확인 | 변경분 추출(Incremental), 실시간 전송, 타겟 반영 | 단순히 "데이터 복사"로만 서술 지양 |
| 로그 기반 CDC의 기술적 우위 파악 | Non-intrusive, 삭제 데이터 추적, 트랜잭션 로그 활용 | 운영 DB 부하 문제에 대한 언급 누락 |
| 실시간 아키텍처 활용 역량 | Kafka 연계, 이벤트 주도 아키텍처(EDA), MLOps 활용 | 기술적 정의에만 치중하여 활용 사례 간과 |

> 요약: CDC는 트랜잭션 로그를 이벤트 스트림으로 전환하여 데이터 사일로를 실시간으로 해소하는 가교이다.

---

## Ⅰ. 개요 및 필요성

- 정의: 데이터베이스 내 데이터 상태 변화(Insert/Update/Delete)를 실시간으로 감지하고 추출하여 이종 시스템 간 동기화를 구현하는 기술
- 배경: 대용량 데이터 환경에서 배치 ETL의 시간적 한계와 운영 DB 부하 문제, 실시간 분석 수요 증대
- 필요성: 시스템 간 데이터 일관성 유지, 운영 DB와 분석 환경의 분리(Decoupling), 실시간 추천/이상탐지 서비스 구현

---

## Ⅱ. 구조 및 구성요소 (Log-based CDC 아키텍처)

```text
[ Source DB ] ----> [ Log Reader / CDC Agent ] ----> [ Message Broker ] ----> [ Target ]
      |                      |                          |                    |
  Redo/Binlog           Event Extraction             Kafka, Pulsar       DW, ES, App
  (변경 이력)            (파싱 및 직렬화)             (버퍼링/전송)        (반영/소비)
```

| 구성요소 | 역할 | 특이사항 |
|:---|:---|:---|
| Source Log | 트랜잭션의 모든 변경 내용이 기록된 물리적 파일 | Oracle Redo, MySQL Binlog 등 |
| Capture Agent | 로그 파일을 읽어 변경된 행(Row) 정보를 추출 | Debezium, Oracle GoldenGate |
| Transformation | 캡처된 데이터를 표준 포맷(JSON, Avro)으로 변환 | 스키마 정보 포함 |
| Target / Sink | 변환된 데이터를 최종 반영하는 시스템 | 데이터 레이크, 검색 엔진, 캐시 |

> 요약: DB 로그를 직접 읽어 변경분을 추출하고, 메시지 브로커를 통해 타겟 시스템에 실시간으로 전달하는 구조이다.

---

## Ⅲ. 동작원리 및 흐름도 (Log-based vs Query-based)

```text
[ Log-based ]
Transaction -> Log Write -> [ CDC Agent Scan ] -> Event Capture -> Target
(비침해적, 삭제 감지 가능, 실시간)

[ Query-based ]
Transaction -> DB Table -> [ Batch Query Scan ] -> Filter -> Target
(부하 발생, 삭제 감지 불가, 주기적)
```

| 단계 | 처리 내용 | 검증 기준 |
|:---:|:---|:---|
| 1 | 트랜잭션 발생 | 사용자가 DB에서 데이터를 변경하면 로그에 먼저 기록됨 | 원자적 기록 |
| 2 | 로그 스캔 | CDC 에이전트가 오프셋(Offset)을 관리하며 로그를 추적 | DB 부하 최소화 |
| 3 | 스키마 해석 | 캡처된 바이너리 데이터를 테이블 구조에 맞춰 해석 | 스키마 레지스트리 연계 |
| 4 | 이벤트 발행 | 변경된 전/후(Before/After) 값을 포함하여 이벤트 생성 | 멱등성 보장 정보 포함 |
| 5 | 타겟 반영 | 대상 시스템의 특성(Idempotent Write 등)에 맞춰 반영 | 최종 일관성 (Eventual Consistency) |

> 요약: DB 엔진 내부의 로그를 활용하여 서비스에 영향을 주지 않으면서도 모든 변화를 정밀하게 추적한다.

---

## Ⅳ. 특징

| 구분 | 주요 특징 | 상세 내용 |
|:---|:---|:---|
| 비침해성 | Low Intrusiveness | 운영 쿼리 성능에 영향을 주지 않고 독립적으로 동작 |
| 무결성 | Integrity | 트랜잭션 순서를 보장하며, 물리적 삭제(Hard Delete)도 감지 |
| 실시간성 | Real-time | 변경 발생 즉시 타겟 시스템에 전파 (초 단위 미만 지연) |
| 효율성 | Efficient | 전체 데이터가 아닌 변경된 델타(Delta)만 전송하여 대역폭 절감 |

> 요약: 운영 환경의 안정성을 해치지 않으면서도 데이터의 최신성을 보장하는 고효율 동기화 방식이다.

## Ⅴ. 심화 비교 및 적용 판단

| 구분 | 쿼리 방식 (Query-based) | 로그 방식 (Log-based) | 선택 기준 |
|:---|:---|:---|:---|
| 추출 대상 | DB 테이블 (Select 쿼리) | 트랜잭션 로그 파일 | DB 부하 허용 수준 |
| 삭제 데이터 감지 | 불가능 (Trigger 필요) | 가능 | 비즈니스 로직 요건 |
| 구현 난이도 | 낮음 (SQL만 필요) | 높음 (DB별 로그 포맷 상이) | 개발 및 운영 역량 |
| 데이터 타입 | 정형 데이터 중심 | 모든 데이터 변화 추적 가능 | 데이터 다양성 |

> 요약: 단순한 주석이나 상태 변경 확인은 쿼리 방식, 정밀한 실시간 동기화는 로그 방식이 필수적이다.

| 리스크 | 원인 | 대응 방안 | 확인 지표 |
|:---|:---|:---|:---|
| 로그 유실 | DB 로그 보관 주기(Retention) 부족 | 로그 보관 기간 확대 및 에이전트 가용성 확보 | Log Sequence Gap 건수 |
| 스키마 변경 | 소스 DB 테이블 구조 변경(DDL) | Schema Evolution 지원 CDC 툴 사용 | 스키마 불일치 에러 발생률 |
| 타겟 병목 | 소스 발생 속도보다 반영 속도가 느림 | 브로커를 통한 완충 및 타겟 쓰기 병렬화 | Consumer Lag (Backlog) |

> 요약: '로그 보관 관리'와 '스키마 변화 대응'이 CDC 운영의 핵심 성공 요인이다.

| 점검 항목 | 목표 기준 | 측정 방법 |
|:---|:---|:---|
| 동기화 지연 시간 | 발생부터 반영까지 5초 이내 (P99) | 소스-타겟 타임스탬프 차이 분석 |
| 데이터 일치율 | 소스-타겟 레코드 수 및 값 일치 100% | 정기적 데이터 검증(Reconciliation) |
| 운영 DB 영향도 | CPU/IO 증가량 5% 미만 유지 | 시스템 모니터링 지표 분석 |

> 요약: 도입 효과는 데이터의 신선도(Freshness)와 운영 시스템의 안정성 지표로 평가한다.

## Ⅵ. 실무 적용 및 결론

**적용 방안 3개:**
1. **CQRS 아키텍처 구현**: 쓰기용 DB(RDBMS)와 읽기용 DB(Elasticsearch/Redis)를 CDC로 연결하여 성능과 확장성 동시 확보
2. **실시간 데이터 레이크 구축**: 온프레미스 DB의 데이터를 클라우드 S3/Iceberg로 실시간 전송하여 최신 데이터 기반 ML 모델 학습
3. **Legacy 시스템 현대화**: 오래된 메인프레임이나 DB를 교체할 때 CDC를 활용하여 신구 시스템 간 데이터를 무중단 실시간 동기화

**결론 (2줄):**
- 기술사 판단: CDC는 데이터 아키텍처를 '정적 상태'에서 '동적 흐름'으로 전환하는 핵심 엔진이며, 실시간 기업(Real-time Enterprise)의 기반 기술이다.
- 향후 방향: 서버리스 CDC 서비스의 확대와 AI를 통한 변경 패턴 분석 기반의 자동 스키마 대응 기술이 더욱 중요해질 것이다.
