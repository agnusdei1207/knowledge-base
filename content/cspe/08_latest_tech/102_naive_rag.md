# 📖 【암기용】 개념 완전 이해

> 목적: Naive RAG를 처음 봐도 완벽히 이해하게 만든다.

## 한눈에
- **정의**: 질의 임베딩으로 Top-K 문서를 검색한 뒤 그대로 LLM 컨텍스트에 넣는 기본 RAG 구조
- **왜 필요한가**: 파인튜닝 없이 외부 문서를 참조하여 최신 정보와 사내 지식을 답변에 반영함.
- **핵심 직관**: 검색 결과 상위 5개를 그대로 참고자료로 붙여 답안을 쓰는 가장 단순한 오픈북 방식임.

## 깊이 이해
- **배경·문제의식**: LLM은 학습 컷오프 이후 정보와 사내 규정을 알 수 없으므로, 별도 학습 없이 문서를 붙여 답하게 하는 방식이 필요함.
- **작동 원리**: 문서를 256~512토큰 청크로 분할→임베딩 생성→벡터DB 저장→질의 임베딩→Top-K 검색→프롬프트 삽입→LLM 생성 순서임.
- **비유**: 시험장에서 색인표로 관련 페이지 5장을 찾아 책상 위에 놓고 답안을 쓰는 방식임.
- **구체 예시**: 사내 FAQ 10만 청크를 HNSW 인덱스로 검색하고 Top-5를 GPT-4o 컨텍스트에 넣어 평균 응답 지연 1.2초로 답변 제공.
- **흔한 오해·주의점**: 검색된 문서가 모두 정답 근거라는 보장이 없음. 무관 문서 1개가 포함되면 LLM이 그 내용을 근거처럼 서술할 수 있음.

## 연결 개념
- RAG — Naive RAG를 포함하는 검색증강생성 전체 개념
- Advanced RAG — Naive RAG에 쿼리 변환·리랭킹·후처리를 추가한 방식
- Hybrid Search — BM25와 Dense 검색을 결합하여 Top-K 후보 품질을 높이는 기법

# 📝 【답안용】 시험 답안 템플릿

> 목적: 시험장에서 25분에 그대로 쓰는 답안 양식.

## 핵심 인사이트 (3줄 요약)

> 1. **본질**: Naive RAG는 검색 Top-K 문서를 별도 검증 없이 LLM 컨텍스트로 주입하는 기본 구조임.
> 2. **가치**: 문서 색인만 갱신해 파인튜닝 없이 사내 지식·최신 정보를 반영함.
> 3. **판단 포인트**: Precision@K가 낮으면 환각이 증가하므로, 기준선 구축 후 Advanced RAG로 확장 판단 필요.

## Ⅰ. 개요 및 필요성

Naive RAG는 기본 검색증강생성 구조임. LLM의 학습 컷오프와 도메인 지식 부재를 보완하기 위해, 검색 문서를 프롬프트에 직접 주입한다. 초기 PoC와 기준선 측정에 적합하나 검색 오류가 생성 오류로 전파된다.

## Ⅱ. 구조 및 구성요소

```text
문서 → Chunking → Embedding → Vector DB
질의 → Embedding → Top-K 검색 → Prompt 조합 → LLM 응답
```

| 구성요소 | 역할 | 특이사항 |
|:---|:---|:---|
| Chunker | 문서를 256~512토큰 단위로 분할 | overlap 10~20% 적용 |
| Embedding | 질의·문서 벡터 변환 | 768~1,536차원 모델 사용 |
| Vector DB | ANN 기반 Top-K 검색 | HNSW, IVF, PQ 중 선택 |
| Prompt Builder | 검색 문서와 질의 결합 | 컨텍스트 4K~32K 토큰 제한 관리 |

> 요약: Naive RAG는 문서 전처리·임베딩·Top-K 검색·프롬프트 결합만으로 구성되는 RAG 기준선임.

## Ⅲ. 동작원리 및 흐름도

```text
사용자 질의 → 질의 임베딩 → 유사도 검색 Top-K
  → 검색 청크 삽입 → LLM 생성 → 답변 출력
```

| 단계 | 처리 내용 | 검증 기준 |
|:---:|:---|:---|
| 1 | 문서 청킹 및 임베딩 색인 | 청크 누락률 0%, 색인 갱신 10분 이내 |
| 2 | 질의 임베딩 생성 | 임베딩 지연 < 50ms |
| 3 | Top-K 유사도 검색 | Recall@10 ≥ 85%, 검색 지연 < 100ms |
| 4 | 컨텍스트 삽입 후 LLM 생성 | 출처 표시율 100%, 환각률 < 15% |

> 요약: 질의를 벡터로 바꿔 유사 청크를 찾고, 별도 판정 없이 LLM 컨텍스트에 넣어 응답을 생성함.

## Ⅳ. 특징

| 구분 | Naive RAG | Advanced RAG | 판단 포인트 |
|:---|:---|:---|:---|
| 구현 범위 | Top-K 검색+생성 | 쿼리 변환·리랭킹·평가 포함 | PoC 2주 이내면 Naive 우선 |
| 품질 통제 | 검색 결과 무검증 | Cross-Encoder, LLM-as-Judge 적용 | Precision@3 < 70%면 고도화 필요 |
| 비용 | 벡터DB+LLM 호출 | 리랭커·평가 호출 추가 | 월 질의 100만 건 이상이면 호출비 산정 |

> 요약: Naive RAG는 구축 속도와 구조 단순성이 장점이나, 검색 품질 통제가 없어 운영 전 리랭킹·평가 보강이 필요함.

## Ⅴ. 실무 적용 및 결론

**적용 방안 3개:**
1. PoC 기준선: 512토큰 청크, Top-5 검색, BGE-M3 임베딩으로 Precision@3·Recall@10 측정
2. 운영 전 보완: Precision@3 70% 미만이면 Hybrid Search와 Cross-Encoder 리랭킹 추가
3. 품질 모니터링: Ragas faithfulness·answer relevancy를 일 단위 측정, 환각률 15% 초과 시 색인 재구성

**결론 (2줄):**
- 기술사 판단: 초기 검증·저위험 FAQ는 Naive RAG, 규정·금융·의료 답변은 Advanced RAG 이상 적용
- 향후 방향: 기준선 RAG에서 평가 기반 CRAG·Self-RAG·Graph RAG로 단계 확장
