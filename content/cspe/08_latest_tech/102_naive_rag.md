# 📖 【암기용】 개념 완전 이해

## 한눈에
- **정의**: 질의를 임베딩(벡터화)하여 가장 유사한 상위 K개의 문서를 단순 검색한 뒤, 별도의 가공 없이 그대로 LLM의 프롬프트에 던져 답변을 생성하는 초기 형태의 기본 RAG 구조.
- **필요성**: 기업 문서 기반의 QA 시스템을 구축할 때, 복잡한 파이프라인 없이 가장 빠르고 저렴하게 "오픈북 챗봇"의 프로토타입(PoC)을 완성하기 위함.
- **핵심 직관**: 질문이 들어오면 무조건 키워드로 검색해서 상위 5개 문서를 복사해 그대로 LLM에게 "이것만 보고 답해!"라고 시키는 직관적이고 단순무식한 구조.

## 깊이 이해
- **배경**: 2020년 랭체인(LangChain) 등 프레임워크가 보급되면서 누구나 쉽게 RAG를 구축할 수 있게 되었을 때 기본으로 제공된 `VectorStoreRetriever` 형태의 아키텍처.
- **작동 원리 (Index -> Retrieve -> Generate)**:
  1. **Index**: 문서를 일정한 길이(예: 500자)로 뭉툭하게 자른 뒤(Chunking) 벡터 DB에 넣음.
  2. **Retrieve**: 사용자가 질문하면 벡터로 바꿔서 코사인 유사도 기준 가장 가까운(Dense Search) 문서 조각 N개를 찾음.
  3. **Generate**: 찾은 N개 조각을 프롬프트에 이어 붙여 LLM에 전송.
- **비유**: 초보 조사관. "상법 제3조 찾아와" 하면 그냥 도서관 검색기로 상법 3조가 들어간 책 3권을 무작위로 복사해다 책상에 던져놓고(Naive RAG), 그걸 보고 보고서를 쓰는 것.
- **흔한 오해/주의점**: Naive RAG는 구축은 쉽지만 실제 현장에 배포하면 "바보 같다"는 소리를 듣기 십상. 사용자가 "작년 3분기랑 올해 3분기 매출 비교해줘"라고 하면, '매출'이라는 단어만 보고 엉뚱한 년도의 매출 문서를 가져와서 환각(Hallucination)을 일으킴.

## 연결 개념
- **Advanced RAG**: Naive RAG의 한계를 극복하기 위해 질문을 보정하고(Query Rewrite), 검색 결과를 깐깐하게 재평가(Reranking)하는 고도화 기법.
- **Cosine Similarity (코사인 유사도)**: Naive RAG가 문서를 찾을 때 유일하게 의존하는 1차원적인 방향성 비교 지표.
- **Chunking (청킹)**: 문서를 잘게 쪼개는 작업. Naive RAG에서는 주로 글자 수 기반(Fixed-size chunking)으로 단순하게 자름.

# 📝 【답안용】 시험 답안 템플릿
## 핵심 인사이트 (3줄 요약)
- **본질**: 문서를 고정 크기로 분할하여 임베딩하고, 사용자 질의와 벡터 유사도(Dense Retrieval)만으로 Top-K 문서를 추출하여 LLM에 직접 주입하는 'Index-Retrieve-Generate'의 선형적 구조.
- **가치**: 랭체인(LangChain) 등의 도구를 활용해 며칠 내로 파이프라인을 구축할 수 있어, 사내 지식 기반 QA 시스템의 기준선(Baseline) 및 PoC 모델로 활용됨.
- **판단 포인트**: 낮은 검색 정밀도(Precision)로 인한 무관 문서 주입 위험, "Lost in the Middle" 현상, 복합 추론 질의 대응 한계를 명확히 인식하고 Advanced RAG로 고도화할 시점(Trigger)을 판단하는 것.

## Ⅰ. 개요 및 필요성
- **정의**: 질의 임베딩을 통한 단순 단일 벡터 검색(Single-Dense Retrieval) 결과물(Top-K)을 어떠한 재가공이나 품질 검증 없이 LLM의 컨텍스트 윈도우에 주입하는 1세대 RAG 아키텍처.
- **배경**: LLM의 지식 한계(Knowledge Cut-off)와 환각(Hallucination)을 막기 위해 외부 데이터를 참조하는 RAG 개념이 등장하며, 가장 직관적이고 구현이 쉬운 형태로 정립됨.
- **필요성**: 엔터프라이즈 환경에서 지식 베이스 연동 시스템 도입 여부를 결정하기 위한 타당성 검증(PoC)과 시스템의 기본 성능 기준점(Baseline) 확보를 위해 필수적으로 구축됨.

## Ⅱ. Naive RAG의 기본 파이프라인
```text
[ 1. Indexing (색인 단계) ]
- Document -> Fixed-size Chunking (단순 글자수 분할) -> Embedding -> Vector DB

[ 2. Retrieval (검색 단계) ]
- User Query -> Query Embedding -> ANN Similarity Search -> Top-K Chunks

[ 3. Generation (생성 단계) ]
- Prompt: "Context: [Top-K Chunks] / Query: [User Query] / Answer:"
- LLM -> Final Response
```

## Ⅲ. Naive RAG의 핵심 컴포넌트 한계
| 컴포넌트 | Naive 방식의 특징 | 발생하는 문제점 (Pain Points) |
|:---|:---|:---|
| **Chunking** | 고정 토큰 길이(예: 512)로 기계적 분할 | 문맥이 중간에 잘려나가 의미 소실 (Semantic Loss) |
| **Retrieval** | 단일 임베딩 모델 기반 Dense 검색 (의미 유사도) | 고유명사, 약어, 품번 등 정확한 키워드 매칭 실패 |
| **Top-K 선정** | 유사도 점수와 무관하게 무조건 상위 5개 등 고정 추출 | 무관한 문서(Noise)가 섞여 들어가 할루시네이션 유발 |
| **Generation** | 랭킹 고려 없이 프롬프트에 일렬로 단순 병합 | LLM이 앞뒤 정보만 기억하는 Lost in the Middle 현상 발생 |

## Ⅳ. 주요 장애(Failure) 유형
1. **검색 실패 (Retrieval Failure)**:
   - 질의의 의도를 담지 못하는 임베딩 모델의 한계로 인해 정답이 들어있는 청크가 Top-K 안에 들지 못함 (낮은 Recall).
2. **응답 실패 (Generation Failure)**:
   - 정답 문서가 Top-K에 포함되어 프롬프트로 넘어갔음에도 불구하고, 무관한 문서(노이즈)들의 간섭으로 인해 LLM이 정답을 제대로 추출/요약하지 못함 (낮은 Precision).
3. **토큰 한도 초과 및 비용 비효율성**:
   - 무조건 긴 문서를 다 던져 넣으므로, API 호출 비용(Token cost)이 상승하고 응답 지연(Latency)이 발생함.

## Ⅴ. 심화: Naive RAG vs Advanced RAG 전환의 임계점 판단
| 판단 지표 | Naive RAG 유지 | Advanced RAG로 전환 (Scale-up) |
|:---|:---|:---|
| **질의의 성격** | "OO 정책이 뭐야?" (단순 정보 탐색) | "A제품과 B제품의 장단점을 비교해" (복합 추론/비교) |
| **문서의 형태** | 순수 텍스트 위주의 단순 매뉴얼 | 도표, 표, 전문용어, 고유명사가 섞인 복합 PDF |
| **성능 지표** | Precision@3 $\ge$ 80% 달성 시 | Recall은 높으나 노이즈로 인해 환각률 15% 이상 시 |
| **개발 목표** | 2주 내 PoC(개념 증명) 구현 | 프로덕션 수준의 대고객 상용 서비스 (SLA 보장) |

## Ⅵ. 실무 적용 및 결론
- **판단 지표**: Ragas 프레임워크 기준의 Context Precision(검색된 문서 중 정답 비율) 및 Context Recall(정답을 찾았는지 여부) 측정.
- **실무 설계**: 사내 IT 헬프데스크 챗봇 초기 구축 시. 10만 건의 과거 Q&A 데이터를 512토큰 단위로 자르고(Naive), OpenAI `ada-002` 모델로 임베딩하여 Vector DB에 저장함. 평가 결과 "비밀번호 초기화" 같은 단순 질문은 잘 답하나, "VPN 접속 불가 시 에러코드 500과 501의 차이" 같은 복잡한 질문에서 오류를 보임. 이를 기준선(Baseline) 성능으로 삼고 하이브리드 검색 도입 등 고도화 예산 타당성을 입증함.
- **결론**: Naive RAG는 RAG 여정의 '출발점'일 뿐 '도착점'이 될 수 없음. 기업은 Naive RAG로 데이터 파이프라인의 뼈대를 빠르게 세운 뒤, 질의 로그를 분석하여 자사 도메인에 맞는 쿼리 재작성(Query Rewrite)과 리랭킹(Reranking) 모듈을 조립해 나가는 점진적 고도화 전략을 취해야 함.

### 🔀 문제 유형별 목차 전환
- **Ⅱ·Ⅲ 강조 (개념/원리형)**: Indexing, Retrieval, Generation의 선형적 워크플로와 Dense Vector의 유클리디안 거리/코사인 유사도 등 수학적/구조적 메커니즘을 상세히 설명.
- **Ⅴ·Ⅵ 강조 (실무/설계형)**: Naive 구조가 초래하는 7가지 실패 지점(Seven Failure Points of RAG)을 분석하고, 이를 타개하기 위해 실무 현장에서 어떤 정량적 지표(Ragas)를 기준으로 아키텍처를 진화시키는지 전략 제시.
