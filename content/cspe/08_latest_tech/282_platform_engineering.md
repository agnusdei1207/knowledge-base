# 📖 【암기용】 개념 완전 이해

> 목적: "너희가 짠 코드니까 인프라도 직접 올려!"라는 잔혹한 DevOps 시대에 지쳐버린 개발자들을 구원하기 위해 등장한 넥스트 데브옵스, 플랫폼 엔지니어링의 철학을 이해한다.

## 한눈에
- **정의**: 개발자가 인프라(K8s, DB, CI/CD)에 대한 깊은 지식 없이도 스스로 코드를 배포하고 운영할 수 있도록, **'내부 개발자 플랫폼(IDP)'을 구축하고 제공하는 소프트웨어 엔지니어링의 한 분야**
- **필요성**: DevOps의 모토인 "You build it, you run it(네가 만들고 네가 운영해라)"를 시켰더니, 개발자들이 코드는 안 짜고 쿠버네티스 YAML 파일 쓰다가 하루가 다 가는 비효율성(인지 부하 폭발)이 발생했기 때문
- **핵심 직관**: "요리사(개발자)에게 맛있는 요리를 하라면서 가스레인지 조립과 수도관 연결(인프라 세팅)까지 시키는 게 DevOps였다면, 플랫폼 엔지니어링은 요리사 전용 풀옵션 주방(IDP)을 렌탈해주고 '당신은 버튼(Self-service)만 누르고 요리만 해!'라고 하는 것."

## 깊이 이해
- **배경(왜 등장했나?)**: 클라우드 네이티브 시대가 오면서 K8s, Istio, Terraform, Argocd 등 툴이 수십 개로 늘어났다. 개발자에게 이 모든 툴을 배워서 직접 배포하라고 했더니 개발 속도가 처참하게 떨어졌다(인지 부하 증가). 이에 가트너(Gartner)는 2026년까지 대기업의 80%가 소프트웨어 개발을 위해 **'플랫폼 엔지니어링 팀'**을 구성할 것이라고 예측했다.
- **작동 원리(어떻게 달성했나?)**: 
  1. 조직 내에 최고 수준의 인프라/SRE 전문가들로 '플랫폼 팀'을 만든다.
  2. 플랫폼 팀은 사내 개발자들(고객)을 위한 웹 포털이나 CLI 도구인 **IDP(Internal Developer Platform)**를 개발한다. (마치 사내용 AWS를 만드는 것과 같다.)
  3. 일반 개발자는 IDP 포털에 접속해서 "스프링부트 템플릿, K8s 배포, DB는 MySQL" 옵션을 클릭 한 번(Self-service)으로 생성한다. 뒤에서 복잡한 Terraform 인프라 세팅은 플랫폼이 다 알아서 해준다.
- **일상 비유**: 식당에서 손님(개발자)이 콜라를 먹고 싶을 때 직원을 불러서 달라고 하는 건 옛날(Ops팀) 방식이다. 직원이 바쁘면 한참을 기다려야 한다. 그래서 손님이 직접 주방에 가서 콜라 기계를 조립해서 뽑아 먹게 했더니 손님이 화를 낸다(DevOps의 부작용). 결국 식당 한가운데에 **'셀프 자판기(IDP)'**를 놔두는 것이 플랫폼 엔지니어링이다.
- **구체 예시**: 스포티파이(Spotify)는 이 분야의 선구자다. 그들은 사내 개발자들이 수많은 툴을 한곳에서 쓸 수 있도록 'Backstage'라는 개발자 포털을 만들었고, 이를 오픈소스로 풀어 전 세계 기업들의 플랫폼 엔지니어링 표준 뼈대가 되었다.
- **흔한 오해/주의점**: "플랫폼 팀은 옛날의 '운영팀(Ops)'으로 돌아간 거 아닌가?" → 절대 아니다! 옛날 운영팀은 티켓(결재)을 받아서 대신 서버를 띄워주는 **'병목(Bottleneck)'**이었다. 플랫폼 팀은 셀프 서비스 도구를 만들어 주는 **'제품 개발팀'**이며, 그들의 고객이 바로 '사내 개발자'다.

## 연결 개념
- **IDP (Internal Developer Platform)**: 플랫폼 엔지니어링의 최종 산출물이자 제품. 개발자를 위한 사내 전용 PaaS/포털.
- **Cognitive Load (인지 부하)**: 인간의 뇌가 한 번에 처리할 수 있는 정보의 한계치. 플랫폼 엔지니어링의 제1 목표는 '개발자의 인지 부하 감소'다.
- **Backstage**: 스포티파이가 만든 대표적인 IDP 구축용 오픈소스 프레임워크 (CNCF 인큐베이팅 프로젝트).

# 📝 【답안용】 시험 답안 템플릿

## 핵심 인사이트 (3줄 요약)
> 1. **본질**: 플랫폼 엔지니어링(Platform Engineering)은 클라우드 네이티브 생태계의 복잡성(Tool Sprawl)을 추상화하여, 개발자 경험(DevEx)을 최적화하는 내부 개발자 플랫폼(IDP)을 구축하는 엔지니어링 원칙이다.
> 2. **가치**: "You build it, you run it"이라는 DevOps의 이상이 초래한 개발자의 '인지 부하(Cognitive Load)'를 해소하고, 셀프 서비스(Self-service) 기반의 표준화된 인프라 배포를 통해 조직 전체의 제품 출시 속도(Time-to-Market)를 극대화한다.
> 3. **판단 포인트**: 플랫폼 팀(Platform Team)을 과거의 운영(Ops) 부서가 아닌 '사내 개발자를 고객으로 삼는 제품(Product) 팀'으로 명확히 규정하고, IDP 아키텍처와 Backstage 같은 도구를 제시해야 한다.

## Ⅰ. 개요 및 필요성
- **정의**: 소프트웨어 배포의 전체 수명주기를 포괄하는 재사용 가능한 도구와 자동화된 셀프 서비스(Self-service) 기반의 내부 플랫폼(IDP)을 설계/구축하는 접근법
- **배경**: K8s, Service Mesh, CI/CD 등 클라우드 기술 스택의 급격한 파편화 및 복잡도 증가. 개발자가 비즈니스 로직(Code)보다 인프라 설정(YAML/HCL)에 더 많은 시간을 쏟는 주객전도 발생
- **필요성**: 개발자의 인지 부하(Cognitive Load) 감소, 섀도우 IT(Shadow IT) 및 비표준 인프라 생성 방지, 엔터프라이즈 전사 차원의 거버넌스 및 보안 준수(Golden Path 제공)

## Ⅱ. DevOps 진화의 역사 (플랫폼 엔지니어링의 등장)
플랫폼 엔지니어링은 DevOps를 버리는 것이 아니라, DevOps의 부작용을 극복하는 'Next DevOps' 모델이다.

| 단계 | 아키텍처/문화 | 특징 및 문제점 |
|:---|:---|:---|
| **Siloed Ops (과거)** | 개발(Dev)과 운영(Ops)의 분리 | 개발자가 서버 요청 티켓을 발행하면 운영팀이 세팅 (극심한 병목 발생, 릴리즈 수개월 소요) |
| **DevOps (현재)** | "네가 만들고 네가 운영해라" | 개발팀이 인프라까지 전담. 자율성은 높아졌으나 **인지 부하(Cognitive Load) 폭발**로 번아웃 발생 |
| **Platform Eng. (미래)**| **"셀프 서비스(Self-Service) 플랫폼"** | 플랫폼 팀이 '황금 경로(Golden Path)'가 깔린 IDP를 제공하고, 개발자는 버튼만 눌러 인프라를 프로비저닝함 |

## Ⅲ. 플랫폼 엔지니어링의 핵심 산출물: IDP (내부 개발자 플랫폼)
IDP(Internal Developer Platform)는 개발자에게 필요한 모든 도구와 프로세스를 추상화한 API/웹 UI 포털이다.

```text
┌─────────────────────────────────────────────────────────────┐
│ 1. Developer Portal (UI / CLI) - ex: Spotify Backstage      │
│  [ 신규 서비스 생성 ]  [ 인프라 모니터링 ]  [ API 카탈로그 ]    │
└───────────────────────┬─────────────────────────────────────┘
        (Self-Service)  │ (Platform API / GitOps)
┌───────────────────────▼─────────────────────────────────────┐
│ 2. Platform Orchestrator (황금 경로/Golden Path 템플릿)       │
│  - 표준화된 CI/CD 파이프라인, RBAC 거버넌스, 보안 정책 강제 주입 │
└───────────────────────┬─────────────────────────────────────┘
                        │ (Terraform / Crossplane)
┌───────────────────────▼─────────────────────────────────────┐
│ 3. Infrastructure & Services (인프라 계층)                   │
│  [ Kubernetes ]  [ AWS/GCP ]  [ Kafka ]  [ PostgreSQL ]     │
└─────────────────────────────────────────────────────────────┘
```

## Ⅳ. 플랫폼 팀(Platform Team)의 역할과 제품 마인드셋
플랫폼 엔지니어링의 성패는 플랫폼 팀의 철학에 달려 있다. (Team Topologies 이론 기반)
1. **Product as a Platform (플랫폼은 제품이다)**
   - IDP를 단순히 '운영 스크립트 모음'이 아니라, 사내 개발자를 '고객(Customer)'으로 생각하고 피드백을 받아 개선하는 하나의 상용 '프로덕트'로 취급해야 한다.
2. **Golden Path (황금 경로) 제공**
   - 회사의 보안 규정과 아키텍처 표준을 만족하는 "가장 빠르고 안전한 기본 템플릿(Golden Path)"을 제공하여, 이 길을 따라가면 인프라/보안 팀의 복잡한 결재 없이 즉시 배포되게 한다.
3. **자율성 보장 (No Lock-in)**
   - 개발자가 황금 경로를 벗어나 새로운 기술(예: 새로운 NoSQL)을 써야 한다면, 강제로 막지 않고 스스로 구축할 수 있는 자율성(Escape Hatch)을 열어둔다.

## Ⅴ. 기술적 한계(리스크) 및 해결 방안
| 리스크 요인 | 현상 및 문제점 | 대응 방안 (엔지니어링 가이드) |
|:---|:---|:---|
| **과도한 추상화의 덫** | IDP가 쿠버네티스의 세세한 기능을 너무 숨기면, 예외적인 튜닝이 필요할 때 개발자가 아무것도 할 수 없는 블랙박스가 됨 | IDP는 강제적인 추상화가 아닌 '선택 가능한 추상화'를 제공하고, 필요시 원본 K8s 리소스에 접근 가능한 권한(Escape Hatch) 부여 |
| **Top-Down 식 플랫폼 강요**| 경영진 주도로 개발자의 의견 없이 플랫폼을 만들면 '비싸고 아무도 안 쓰는 쓰레기 시스템'으로 전락함 | 사내 개발자를 대상으로 주기적인 **NPS(순수 고객 추천 지수)** 설문을 진행하고 철저한 Agile 방식으로 IDP 점진적 개발 |

## Ⅵ. 실무 적용 및 결론
**적용 방안 및 실무 가이드:**
1. **Backstage 기반 포털 구축**: 사내 수백 개의 마이크로서비스 카탈로그, API 문서, CI/CD 대시보드를 통합하는 시작점으로 Spotify의 Backstage를 도입하여 플랫폼의 프론트엔드를 구성한다.
2. **Crossplane(크로스플레인) 도입**: 인프라 프로비저닝 시 기존의 Terraform(IaaC) 방식을 넘어, K8s의 CRD(Custom Resource Definition)를 활용하여 클라우드 자원을 K8s 네이티브하게 관리하는 Crossplane 생태계를 구성한다.

**결론:**
- 플랫폼 엔지니어링은 무너져가는 DevOps의 한계를 극복하고 클라우드 네이티브 생태계를 다음 단계로 견인하는 **가장 강력한 조직론적 해답**이다.
- 훌륭한 플랫폼(IDP)은 개발자의 인지 부하를 최소화하여 그들이 진정으로 사랑하는 일(비즈니스 로직 작성)에만 집중하게 만들고, 결과적으로 기업의 비즈니스 민첩성(Agility)을 극대화한다.
