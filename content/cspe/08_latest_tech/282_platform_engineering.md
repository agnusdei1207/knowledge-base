# 📖 【암기용】 개념 완전 이해

> 목적: 플랫폼 엔지니어링을 처음 봐도 완벽히 이해하게 만든다. 시험 답안 양식이 아니라, 이해를 위한 친절한 설명이다.

## 한눈에
- **개요**: 개발자가 인프라나 복잡한 설정 신경 안 쓰고 개발에만 집중할 수 있게, 모든 도구와 기능을 한데 모아 '셀프 서비스 플랫폼(IDP)'을 만들어 제공하는 기술 및 문화
- **왜 필요한가**: 클라우드 네이티브 환경(쿠버네티스, 클라우드 서비스 등)이 너무 복잡해졌다. 개발자가 코딩보다 인프라 설정에 시간을 더 쓰는 문제를 해결하기 위해, 인프라 전문가들이 "쓰기 편한 도구 상자"를 대신 만들어주는 것이다.
- **핵심 직관**: **개발자 경험(Developer Experience, DX)**을 극대화하여 제품 출시 속도를 높이는 "내부 서비스 플랫폼" 구축이다.

## 깊이 이해
- **배경·문제의식**: "You build it, you run it" (DevOps) 정신은 좋았으나, 개발자에게 가해지는 인지적 부하(Cognitive Load)가 너무 컸다. 개발자가 네트워크, 보안, 배포 설정을 다 공부하기엔 시간이 부족하다.
- **작동 원리**: **IDP (Internal Developer Platform)**라는 것을 만든다. 개발자는 IDP 화면이나 명령어를 통해 "서버 1대 띄워줘", "DB 연결해줘"라고 요청하면, 플랫폼이 미리 설정된 표준(Golden Path)에 따라 자동으로 처리해준다.
- **비유**: 레스토랑과 밀키트의 차이다.
    - 기존 DevOps: 식재료부터 조리 기구까지 다 챙겨서 직접 요리해야 함. (인지 부하 높음)
    - 플랫폼 엔지니어링: 손질된 재료와 레시피가 담긴 **밀키트(IDP)**를 제공. 개발자는 끓이기만 하면 일정한 품질의 요리가 나옴.
- **구체 예시**: Backstage(Spotify 오픈소스)를 활용한 사내 개발자 포털, 인프라 자동화 도구(Terraform, Crossplane)와 연동된 셀프 서비스 UI.
- **흔한 오해·주의점**: "인프라 팀의 이름만 바꾼 거 아냐?"라고 할 수 있지만, 플랫폼 엔지니어링의 핵심은 인프라를 '요청받아 처리해주는 것'이 아니라, 개발자가 스스로 할 수 있는 '제품(Product)'으로서 플랫폼을 만드는 것이다.

## 연결 개념
- IDP (Internal Developer Platform) — 플랫폼 엔지니어링의 결과물
- Cognitive Load (인지적 부하) — 줄여야 할 대상
- Golden Path (황금 경로) — 플랫폼이 권장하는 표준화된 개발/배포 경로
- Developer Experience (DX) — 핵심 목표 지표

# 📝 【답안용】 시험 답안 템플릿

> 목적: 시험장에서 25분에 그대로 쓰는 답안 양식. 작성방식(추상표현 금지·수치·도식·문제유형 전환)을 엄격히 지킨다.
> 핵심: 개발자 인지 부하 감소와 셀프 서비스(Self-Service) 역량을 중심으로 내부 개발자 플랫폼(IDP)의 구조를 서술한다.

## 핵심 인사이트 (3줄 요약)

> 1. **본질**: 플랫폼 엔지니어링은 개발자가 소프트웨어 전달 과정에서 겪는 인지적 부하를 최소화하기 위해 공통 도구와 인프라 기능을 '내부 개발자 플랫폼(IDP)'으로 제품화하여 제공하는 규율이다.
> 2. **가치**: 셀프 서비스(Self-Service)와 표준화된 황금 경로(Golden Path)를 통해 개발팀의 자율성을 보장하고, 기업 전체의 소프트웨어 출시 속도(Time-to-Market)를 가속화한다.
> 3. **판단 포인트**: 단순한 도구 집합이 아니라 플랫폼을 '하나의 제품(Platform as a Product)'으로 간주하고 개발자의 피드백을 지속적으로 반영하는 운영 방식이 핵심이다.

## 출제 의도 및 답안 포인트

| 출제 의도 | 반드시 짚을 핵심 | 감점 회피 포인트 |
|:---|:---|:---|
| 플랫폼 엔지니어링의 등장 배경 이해 확인 | 개발자 인지 부하(Cognitive Load) 감소, DevOps의 한계 보완 | 단순히 "인프라 자동화"로만 서술 |
| 핵심 구성요소 및 IDP 구조 확인 | IDP, Golden Path, 셀프 서비스 UI, API | 특정 클라우드 서비스(AWS 등) 소개에 그침 |
| 개발자 경험(DX) 향상 전략 확인 | 가시성, 표준화, 자동화, 제품 관리 관점 | 기술적 기능 나열만 하고 '사용성' 관점 누락 |

> 요약: 복잡한 현대 인프라를 추상화하여 개발 생산성을 높이는 내부 플랫폼 구축 역량을 중심으로 기술한다.

## Ⅰ. 개요 및 필요성

- 정의: 애플리케이션의 생명주기 전반에 필요한 인프라, 보안, 도구들을 통합하여 개발자가 스스로 사용할 수 있게 만든 내부용 제품 플랫폼 개발 규율
- 배경: 클라우드 네이티브 기술 스택의 파편화 및 복잡도 증가로 인해 개발자가 인프라 설정에 과도한 시간 소모(Cognitive Load 발생)
- 필요성: 개발 생산성(Developer Velocity) 극대화, 인프라 거버넌스 및 표준 준수 강화, 인프라 전문가 부족 문제 해결

## Ⅱ. 구조 및 구성요소

```text
[ Developer / User ]
         | (Self-Service Interface: UI / CLI / API)
+-------------------------------------------------------+
|        Internal Developer Platform (IDP)              |
|  - Developer Portal (e.g. Backstage)                  |
|  - Service Catalog & Golden Paths                     |
|  - Infrastructure Orchestration (IaC)                 |
+-------------------------------------------------------+
         | (Provisioning / Management)
[ K8s / Cloud / Database / Security / Observability ]
```

| 구성요소 | 역할 | 특이사항 |
|:---|:---|:---|
| Developer Portal | 플랫폼의 단일 진입점 (Single Pane of Glass) | Backstage 등 활용 |
| Golden Paths | 권장되는 표준 배포 및 개발 워크플로우 | 가이드라인 및 템플릿화 |
| Infrastructure Orchestration | 인프라 생성 및 관리 자동화 엔진 | Terraform, Crossplane 등 |
| Service Catalog | 사용 가능한 서비스 및 인프라 목록 관리 | 권한 및 소유권 명시 |

> 요약: 하위의 복잡한 인프라를 추상화하여 상위의 개발자에게 단일 인터페이스로 노출하는 계층 구조다.

## Ⅲ. 동작원리 및 흐름도

```text
[동작 흐름: 템플릿 선택 -> 변수 입력 -> 자동 생성 -> 가시성 확보]
Select Template (Golden Path) -> Fill Requirements -> Auto Provisioning
          |                         |                    |
(New Microservice) -------- (Name, DB Size) ---- (K8s, CI/CD, DB)
          |                         |                    |
          +-------------------------+--------------------+
                                    |
                          Update Service Catalog (Visibility)
```

| 단계 | 처리 내용 | 검증 기준 |
|:---:|:---|:---|
| 1 | 셀프 서비스 요청 | 개발자가 플랫폼 포털에서 필요한 자원(서버, DB 등)을 정의된 템플릿으로 요청 |
| 2 | 거버넌스 체크 | 플랫폼이 요청 내용이 회사 보안 및 표준(Golden Path)에 부합하는지 자동 검증 |
| 3 | 인프라 프로비저닝 | IaC 도구를 통해 실제 인프라를 생성하고 관련 권한 및 모니터링 연동 |
| 4 | 서비스 등록 | 생성된 자원을 카탈로그에 자동 등록하여 가시성 및 소유권 관리 보장 |

> 요약: 개발자가 '어떻게(How)'가 아닌 '무엇(What)'을 원하는지에 집중하도록 추상화된 워크플로우를 제공한다.

## Ⅳ. 특징

| 구분 | 내용 | 판단 포인트 |
|:---|:---|:---|
| 인지 부하 감소 | 복잡한 인프라 지식 없이도 배포 및 운영 가능 | 개발자 경험(DX) 중심 |
| 황금 경로 (Golden Path) | 베스트 프랙티스가 적용된 표준 템플릿 제공 | '자유'보다 '가이드' 제공 |
| 셀프 서비스 | 티켓 기반 요청 대기 시간 제거, 즉시 생성 | 민첩성(Agility) 확보 |
| 플랫폼의 제품화 | 개발자를 고객으로 간주하고 피드백 기반 진화 | 제품 관리(Product Management) |

> 요약: 인프라를 '기술'이 아닌 '서비스 제품'으로 제공하여 조직의 속도를 높이는 특징을 가진다.

## Ⅴ. 심화 비교 및 적용 판단

| 비교 축 | 전통적 IT 운영 | DevOps | 플랫폼 엔지니어링 |
|:---|:---|:---|:---|
| 인프라 관리 | 운영팀이 수동 처리 | 개발자가 직접 관리 (YAML 등) | 플랫폼을 통해 셀프 서비스 |
| 개발자 역할 | 코드 작성만 수행 | 빌드/배포/운영 전체 책임 | 비즈니스 로직에만 집중 |
| 주안점 | 안정성 및 통제 | 자율성 및 속도 | 생산성 및 추상화 |

> 요약: DevOps의 자율성은 유지하되, 개발자의 인드라 부담을 플랫폼으로 흡수하여 효율을 극대화한다.

| 리스크 | 원인 | 대응 방안 | 확인 지표 |
|:---|:---|:---|:---|
| 플랫폼 비대화 | 과도한 기능 추가로 플랫폼 자체가 복잡해짐 | 필수 기능(MVP) 위주 개발 및 모듈화 | 플랫폼 학습 곡선(Onboarding 시간) |
| 창의성 저해 | 정해진 경로(Golden Path) 외 시도 차단 | 황금 경로는 권장하되 탈출 경로(Exit) 보장 | 표준 템플릿 사용 비율 |
| 투자 비용 | 플랫폼 구축 및 유지를 위한 전담 팀 필요 | 기성 오픈소스(Backstage 등) 적극 활용 | 개발자당 생산성 향상 수치 |

> 요약: 표준화를 통한 효율과 자율성 보장 사이의 균형을 맞추는 것이 실무의 난제다.

| 점검 항목 | 목표 기준 | 측정 방법 |
|:---|:---|:---|
| Onboarding 시간 | 신규 개발자가 첫 배포까지 걸리는 시간 50% 단축 | 데이터 트래킹 |
| 셀프 서비스율 | 인프라 요청 중 자동 처리 비중 90% 이상 | 티켓 분석 |
| 개발자 만족도 (Net Promoter Score) | 플랫폼 사용 편의성 평가 8점 이상 | 사내 설문 조사 |

> 요약: 기술적 성능보다 '개발자가 얼마나 편하게 일하게 되었는가'를 핵심 지표로 관리해야 한다.

## Ⅵ. 실무 적용 및 결론

**적용 방안 3개:**
1. Backstage 기반 포털 구축: 서비스 카탈로그, 문서화, 템플릿 기능을 한데 모아 개발자 가시성 확보
2. Golden Path 템플릿화: 보안과 가용성이 검증된 표준 MSA 템플릿을 제공하여 보안 사고 사전 예방
3. GitOps 연계: 플랫폼에서 생성된 설정이 Git 저장소를 통해 자동 반영되도록 설계하여 형상 관리 일관성 유지

**결론 (2줄):**
- 기술사 판단: 플랫폼 엔지니어링은 'You build it, you run it'의 고통을 덜어주고, 조직의 규모를 확장 가능하게(Scalable) 만드는 현대적 운영의 종착지이다.
- 향후 방향: AI를 결합하여 개발자의 의도만으로 인프라를 구성하는 'AI 기반 플랫폼 엔지니어링'으로 진화할 전망이다.
