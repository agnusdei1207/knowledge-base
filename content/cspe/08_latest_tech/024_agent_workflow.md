## Ⅰ. 개요
- **정의**: 복수의 LLM 호출·도구 실행을 결정론적 흐름 제어(순차·분기·반복)로 엮어 예측 가능한 결과를 생산하는 파이프라인 설계 패턴
- **배경/필요성**: 에이전트에 자율성을 부여하면 무한 검색·환각·비용 폭주가 발생함. 엔터프라이즈 환경은 일관성·재현성이 필수이므로 "모델 크기 확장보다 워크플로우 구조화가 성능 향상에 유리하다"는 실증 결과(Andrew Ng)가 워크플로우 설계 패턴의 필요성을 뒷받침
- **비유**: 공장 조립 라인 — 각 공정(에이전트)이 정해진 순서와 품질 검사 게이트를 통과해야만 다음 공정으로 이동

| 출제 의도 | 반드시 짚을 핵심 | 감점 회피 포인트 |
|:---|:---|:---|
| 자율 에이전트 vs 워크플로우의 설계 철학 차이 | 체이닝·라우팅·병렬화·평가-수정자 4대 패턴 | 자율 에이전트(ReAct)와 혼동 금지. 워크플로우는 코드로 하드코딩된 상태 기계 |

> 요약: LLM 호출을 결정론적 파이프라인으로 구조화하여 일관성·재현성·비용 효율을 확보하는 설계 체계

## Ⅱ. 구성요소
```text
+--------------------------------------------------+
|  Workflow Engine (LangGraph / Prefect 등)         |
|                                                   |
|  +-------+   +--------+   +--------+   +------+  |
|  | Chain | ->| Router | ->| Parallel| ->| Eval |  |
|  | Node  |   | Node   |   | Node   |   | Node |  |
|  +-------+   +--------+   +--------+   +------+  |
|       |           |            |           |      |
|       v           v            v           v      |
|   순차 전달    의도 분기    동시 실행    반복 검증  |
+--------------------------------------------------+
```

| 구성요소 | 설명 | 비유 |
|:---|:---|:---|
| Prompt Chaining | 태스크를 소단계로 분할하여 앞 단계 출력을 다음 단계 입력으로 순차 전달 | 릴레이 바톤 |
| Routing | 입력의 의도·유형을 분류하여 전문 에이전트로 트래픽을 분기하는 게이트웨이 | 우체국 분류기 |
| Parallelization | 독립 작업을 복수 에이전트에 동시 분배하거나 동일 작업을 다수결(Ensemble)로 검증 | 병렬 조립 라인 |
| Evaluator-Optimizer | 비판 에이전트(Critic)가 산출물을 채점하고 미달 시 수정 에이전트에 반환하는 반복 루프 | 원고 교열-재작성 |

> 요약: 체이닝·라우팅·병렬화·평가-수정자 4대 패턴을 Workflow Engine이 상태 기계로 오케스트레이션

## Ⅲ. 절차
```text
+----------------+    +----------------+    +----------------+    +----------------+
| 1. 태스크 분해 | -> | 2. 패턴 선택   | -> | 3. 노드 실행   | -> | 4. 품질 게이트 |
| (Decompose)    |    | (Pattern)      |    | (Execute)      |    | (Quality Gate) |
+----------------+    +----------------+    +----------------+    +----------------+
```

1. **태스크 분해(Decompose)** — 복합 업무를 독립 실행 가능한 소단위(요약·번역·검증 등)로 분할하여 각 노드에 할당
2. **패턴 선택(Pattern Selection)** — 업무 특성에 따라 순차(Chaining), 분기(Routing), 동시(Parallel), 반복(Eval-Opt) 패턴을 조합
3. **노드 실행(Execute)** — 각 노드가 LLM 호출 또는 도구 실행을 수행하고, 결과를 다음 노드의 입력 State로 전달
4. **품질 게이트(Quality Gate)** — Evaluator 노드 또는 결정론적 검증(정규식·JSON 스키마 등)을 통해 산출물 품질 미달 시 이전 노드로 반환

> 요약: 분해→패턴 조합→노드 실행→품질 게이트 통과의 4단계 파이프라인

## Ⅳ. 문제점
- [과도한 설계 복잡도]: 그래프 노드·엣지 수가 증가하면 디버깅 및 유지보수 비용이 기하급수적으로 상승
- [반복 루프 비용 폭주]: Evaluator-Optimizer 패턴에서 반복 횟수 제한 없이 운영 시 토큰 소비 및 지연이 무한 증가
- [결정론적 경직성]: 하드코딩된 분기 로직이 예상 외 입력을 처리하지 못하여 전체 파이프라인 실패로 이어짐

> 요약: 그래프 복잡도, 반복 비용 폭주, 예외 입력 대응 불가가 워크플로우의 3대 한계

## Ⅴ. 개선방안
1. 단기: Max Iteration 상한(3~5회) 강제 설정으로 반복 루프 비용을 토큰 예산 이내로 제한
2. 중기: Evaluator 노드에 LLM 채점과 결정론적 코드 검증(정규식·스키마)을 5:5 하이브리드로 구성하여 환각 기반 오판 차단
3. 장기: 워크플로우 템플릿 라이브러리(법무 검토, 보안 점검 등)를 전사 자산으로 표준화하여 부서별 재사용·조합 가능하게 함

- [경직성]: [예외 미처리] → Fallback 노드를 그래프 말단에 배치, 미분류 입력을 자율 에이전트(ReAct)로 위임 (지표: Fallback 발동률 ≤ 5%)

> 요약: 반복 상한 제한, 하이브리드 검증, 템플릿 표준화로 비용·품질·재사용성 동시 확보

## Ⅵ. 전망
- 향후 발전 방향: 워크플로우 패턴과 자율 에이전트의 하이브리드 — 정형 업무는 워크플로우, 예외·창의 업무는 자율 에이전트로 동적 전환하는 적응형 아키텍처
- 기술사적 판단: LLM 성능의 천장을 구조적 엔지니어링으로 돌파하는 실용적 방법론. 프롬프트 1-turn 대비 정답률 30%+ 향상 실증
- 기술사 제언: 모든 Evaluator 노드에 결정론적 검증 코드를 반드시 1개 이상 삽입하여 "AI 출력을 100% 신뢰하지 않는" 설계 원칙을 견지할 것
