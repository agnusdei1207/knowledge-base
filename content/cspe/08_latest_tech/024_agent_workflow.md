# 📖 【암기용】 개념 완전 이해

## 한눈에
- **개요**: 에이전트 워크플로우는 AI **에이전트**(001 참조)의 업무를 **단계·조건 분기·도구 호출·승인·출력 형식**으로 정의한 재현 가능한 실행 절차다. 오케스트레이션(014)이 "누가 무엇을 호출하는가"의 실행 제어라면, 워크플로우는 "어떤 순서·조건·형식으로 진행하는가"의 업무 프로세스 정의에 해당한다.
- **왜 필요한가**: 프롬프트만으로 업무를 맡기면 에이전트가 매번 다른 순서로 단계를 밟거나 단계를 누락하고, 결과 형식도 일관되지 않는다. 반복 업무(장애 대응·보안 점검·고객 응대 등)에서 품질 편차·승인 누락·감사 공백이 발생하므로, 표준화된 절차가 필요하다.
- **핵심 직관**: 제조 공정표와 같다. 원재료 투입(입력)→가공(단계)→품질 검사(분기)→포장(출력)까지 순서와 기준이 정해져 있어, 누가 작업하든 동일한 품질의 제품이 나온다.

## 핵심 용어 정리 (내부에 등장하는 것들)

| 용어/표기 | 의미 | 비유·예 |
|:---|:---|:---|
| 워크플로우(상위 키워드) | 업무를 단계·조건·도구·승인으로 정의한 재현 가능한 절차 | 제조 공정표 |
| Step(단계) | 워크플로우의 개별 처리 단위. Agent·Tool·Human Task 중 하나를 실행 | 공정의 각 "공정" |
| Condition(조건 분기) | 이전 단계 결과에 따라 다음 경로를 선택하는 논리(if/switch) | 품질 검사 합격/불합격 |
| Input/Output Schema | 각 단계의 입력·출력 형식을 JSON Schema 등으로 정의 | 주문서 양식, 보고서 템플릿 |
| Fallback | 단계 실패 시 대체 경로(재시도·에스컬레이션·중단) | 비상 대피 경로 |
| Workflow 버전 관리 | 워크플로우 정의를 Git으로 관리하고, 변경 시 승인 후 배포 | 공정 변경 시 품질팀 승인 |
| DAG(Directed Acyclic Graph) | 단계 간 의존 관계를 방향 있는 비순환 그래프로 표현 | 공정 순서도 |
| Runbook | 운영 절차를 문서화한 것. 워크플로우는 Runbook의 자동화 버전 | 매뉴얼 → 자동화 스크립트 |

## 깊이 이해
- **배경·문제의식**: 에이전트 오케스트레이션(014)이 "에이전트들을 어떻게 조율하는가"의 런타임 제어를 다룬다면, 워크플로우는 "어떤 업무 절차를 따르는가"의 프로세스 설계를 다룬다. 프롬프트에 "1번 하고 2번 하고 3번 해줘"라고 써도, 모델이 순서를 바꾸거나 중간 단계를 건너뛸 수 있고, 승인 없이 실행할 수 있다. 워크플로우는 이를 DAG·조건·스키마로 강제한다.
- **작동 원리(어떻게+왜)**: ① 업무 유형(장애 대응, 보안 점검 등)별로 워크플로우를 DAG로 정의한다. 각 Step에 {실행 주체(Agent/Tool/Human), Input Schema, Output Schema, 성공 조건, 실패 시 Fallback}을 명시한다. ② 요청이 들어오면 오케스트레이터가 해당 워크플로우를 로드하고, Step 순서대로 실행한다. 조건 분기 노드에서 이전 Step 결과를 평가해 경로를 선택한다. ③ 고위험 Step은 HITL(022) 승인을 요구하고, 실패 시 retry/fallback/에스컬레이션을 수행한다. ④ 최종 출력은 Output Schema에 맞춰 생성하고, 전체 실행 이력을 Trace ID로 감사 로그(021)에 기록한다.
- **비유**: 응급실 프로토콜과 같다. 환자 접수→활력징후 측정→중증도 분류(triage)→처치→입원/퇴원 분기까지 표준 절차가 있어, 어느 응급실이든 동일한 품질로 환자를 처리한다. 프로토콜 없이 의사 재량에만 맡기면 처치 누락·순서 오류가 발생한다.
- **구체 예시**: 장애 대응 워크플로우: ① 감지(알림 수신)→② 로그 수집(로그 에이전트 호출)→③ 원인 분석(분석 에이전트)→④ 조치 제안(Proposal 생성)→⑤ 승인(HITL, SLA 10분)→⑥ 실행(변경 에이전트, 멱등성 키)→⑦ 사후 보고(보고서 에이전트, Output Schema: Markdown). 3단계에서 원인 미식별이면 Fallback으로 온콜 엔지니어에게 에스컬레이션한다.
- **흔한 오해·주의점**: "워크플로우는 에이전트의 자유도를 없애는 것"이라는 오해가 있다. 실제로는 각 Step 내에서 에이전트가 자유롭게 추론하되, Step 간 순서·조건·형식만 강제한다. 자유형 에이전트와 워크플로우 에이전트는 양자택일이 아니라, 반복·고위험 업무에 워크플로우를, 탐색·창작 업무에 자유형을 적용하는 것이다.

## 연결 개념
- 에이전트 오케스트레이션(014) — 워크플로우를 실행하는 런타임 제어 계층
- HITL 에이전트(022) — 워크플로우 내 고위험 Step에 삽입되는 승인 게이트
- 에이전트 상태관리(019) — 워크플로우 실행 상태의 영속 추적

## Ⅰ. 개요 및 필요성

- 개요: AI 업무를 단계·분기·도구·승인·출력 형식으로 정의한 재현 가능한 실행 절차임
- 배경: 프롬프트만으로 업무를 맡기면 단계 순서 변동·누락·결과 형식 불일치가 발생함
- 필요성: 반복 업무의 품질 편차·감사 공백을 줄이려면 DAG 기반 표준 절차 정의가 필수임

---

## Ⅱ. 구조 및 구성요소

```text
요청 -> Workflow 선택 -> Step 1(Agent/Tool) -> Condition(분기)
  -> Step 2(승인/Human) -> Step 3(실행) -> Output Schema -> 감사 기록
```

| 구성요소 | 역할 | 특이사항 |
|:---|:---|:---|
| Workflow Definition | DAG 기반 단계·분기·조건 정의 | YAML/JSON, Git 버전 관리 |
| Step | Agent·Tool·Human Task 실행 단위 | Input/Output Schema, 성공 조건 |
| Condition | 이전 결과 기반 경로 선택 | 위험도·점수·오류 코드 |
| Fallback Handler | 실패 시 retry·에스컬레이션·중단 | 재시도 횟수·대기 시간 |

> 요약: 워크플로우는 DAG 정의·Step·조건 분기·Fallback으로 AI 업무를 표준 절차화함.

---

## Ⅲ. 동작원리 및 흐름도

```text
요청 접수 -> 업무 유형별 Workflow 로드 -> Step 순차/병렬 실행
  -> 조건 분기(성공/실패/위험) -> 승인/재시도/Fallback -> 출력 생성 -> 이력 저장
```

1. Workflow 로드: 요청의 업무 유형·위험등급에 맞는 워크플로우를 오케스트레이터가 로드함
2. Step 실행: 각 Step의 Input Schema를 검증하고, Agent·Tool·Human Task를 실행한 뒤 Output Schema를 확인함
3. 분기·예외: 조건 노드에서 결과를 평가해 다음 경로를 선택하고, 실패 시 retry/fallback/에스컬레이션을 수행함
4. 출력·기록: 최종 결과를 Output Schema에 맞춰 생성하고, 전체 실행 이력을 Trace ID로 감사 로그에 기록함

> 요약: Workflow 로드→Step 실행→분기/Fallback→출력·감사로 반복 업무의 재현성을 보장함.

---

## Ⅳ. 특징

- 재현성: 동일 업무 유형에 동일 절차를 적용해 결과 편차를 제거함
- Schema 강제: 각 Step의 입출력을 JSON Schema로 정의해 형식 불일치를 차단함
- 분기 내재화: 조건 분기·Fallback·에스컬레이션이 워크플로우에 명시되어 예외 미처리를 방지함
- 버전 관리: Git 기반으로 변경 이력을 추적하고 승인 후 배포해 무관리 수정을 차단함
- Step 내 자유도: 각 Step 안에서 에이전트는 자유 추론이 가능하며, Step 간 순서·형식만 강제함

## Ⅴ. 심화 비교 및 적용 판단

| 구분 | 자유형 에이전트 | 워크플로우 에이전트 | 선택 기준 |
|:---|:---|:---|:---|
| 절차 통제 | 모델 자율 판단(순서 변동) | DAG·조건·승인 명시(순서 고정) | 업무 반복성과 위험도 |
| 품질 편차 | 실행마다 결과 상이 가능 | Output Schema 표준화 | Schema 통과율 95% 이상 |
| 변경 관리 | 프롬프트 수정 즉시 반영 | 버전 관리+승인 후 배포 | 변경 영향 범위와 규제 요건 |

> 요약: 반복·고위험 업무는 워크플로우, 탐색·창작 업무는 자유형 에이전트로 분기함.

**리스크·대응:**
- 단계 누락: 워크플로우 정의 불완전 → Step별 Input/Output 검증, 필수 단계 체크 (지표: 단계 누락률 0%)
- 예외 미처리: 분기 조건 미정의 → timeout·retry·fallback·에스컬레이션 명시 (지표: 예외 미처리 건수 월 0건)
- 버전 충돌: 무관리 수정 배포 → Git 기반 버전 관리, 변경 시 승인 후 배포 (지표: 무승인 변경 건수 0건)

**도입 후 점검 지표:**
- 성공률: task success rate 90% 이상 — 워크플로우 실행 이력 대시보드
- 실패 단계 분포: 특정 Step 집중 실패 식별 — 실패 Step 히트맵 주간 분석

## Ⅵ. 실무 적용 및 결론

**적용 방안 3개:**
1. 장애 대응·보안 점검·고객 응대 등 업무 유형별 워크플로우를 DAG로 정의하고 Git 버전 관리를 적용함
2. Step별 Input/Output Schema·timeout·retry·approval·rollback 조건을 명시하고 Fallback 경로를 설계함
3. 워크플로우 버전·실행 이력·성공률·실패 단계 분포·p95 처리 시간을 지표로 관리함

**결론:**
- 기술사 판단: 반복 가능한 업무는 워크플로우로 표준화하고, 탐색적 판단 업무는 자유형 에이전트+HITL(022) 승인으로 분기함
- 향후 방향: 에이전트 워크플로우는 BPM·Runbook Automation·LLMOps(212)가 결합된 AI 업무 운영 표준으로 발전함
