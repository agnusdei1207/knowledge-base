# 📖 【암기용】 개념 완전 이해

## 한눈에
- **정의**: 문서와 검색어를 모두 수백 차원(예: 768차원)의 꽉 찬 실수 배열(Dense Vector)로 변환한 뒤, 두 벡터 사이의 '방향과 거리(유사도)'를 계산하여 연관 문서를 찾아내는 검색 기술.
- **필요성**: 기존의 키워드 검색(Sparse)은 "사과"라는 단어가 문서에 없으면 절대 찾지 못함. "Apple"이든 "아이폰"이든 의미적으로 연결된 문맥을 이해하고 찾아주는 지능형 검색이 필요함.
- **핵심 직관**: 사람의 성격을 [외향성, 창의성, 논리성] 3차원 점수로 표현하듯, 문장의 의미를 [정치적 느낌, 경제적 느낌, 긍정적 느낌...] 등 768개의 속성 점수로 수치화함. 내 질문의 점수와 가장 비슷한 점수 조합을 가진 문서를 찾아내는 것.

## 깊이 이해
- **배경**: BERT 같은 사전학습 언어모델(PLM)이 등장하면서, 문장의 문맥(Context)을 깊이 있게 이해하는 워드 임베딩 기술이 폭발적으로 발전함. 이를 검색에 응용하여 2020년경 DPR(Dense Passage Retrieval) 논문이 나오며 오픈 도메인 QA의 패러다임이 바뀜.
- **작동 원리 (Bi-Encoder 구조)**:
  1. (문서 변환): 위키백과 등 수백만 개 문서를 Document Encoder에 넣어 벡터 뭉치로 만들어 벡터 DB에 저장.
  2. (질의 변환): 사용자가 질문하면 Query Encoder에 넣어 똑같이 벡터로 만듦.
  3. (거리 계산): 질문 벡터와 가장 코사인 유사도(Cosine Similarity)가 높은 방향의 문서 벡터 Top-K를 벡터 DB(ANN 알고리즘 적용)에서 뽑아옴.
- **비유**: 키워드 검색이 "옷에 '빨간색' 태그 붙은 것만 찾아와"라면, 밀집 검색은 "태그 상관없이 내 빨간 셔츠랑 '가장 어울리는 분위기'의 바지를 찾아와"라고 하는 스타일 코디네이터.
- **흔한 오해/주의점**: 벡터가 모든 걸 해결해 주진 않음. 임베딩 모델(Encoder)이 학습하지 않은 낯선 단어(신제품 이름, 특수 오류 코드)가 들어오면 무작위로 엉뚱한 벡터 공간에 던져버려서 완전히 헛소리 문서를 가져옴(환각 유발). 따라서 도메인 데이터로 파인튜닝하거나, 키워드 검색과 병행해야 함.

## 연결 개념
- **Semantic Search (의미 검색)**: 밀집 검색을 통해 달성하고자 하는 궁극적인 목적/서비스 형태.
- **Bi-Encoder vs Cross-Encoder**: 밀집 검색은 속도를 위해 문서를 미리 각자 변환해 두는 Bi-Encoder 방식을 씀. Cross-Encoder는 정확하지만 너무 느려서 최종 리랭킹(재채점)에만 씀.
- **Vector Database**: 만들어진 빽빽한 실수 배열(Dense Vector)들을 저장하고 빛의 속도로 거리를 계산해 주는 전용 데이터베이스(Milvus, Pinecone 등).

# 📝 【답안용】 시험 답안 템플릿
## 핵심 인사이트 (3줄 요약)
- **본질**: 질의(Query)와 코퍼스(Document)를 사전학습 딥러닝 모델(Bi-Encoder)을 이용해 저차원(수백~수천)의 조밀한 실수 벡터(Dense Vector) 공간에 매핑하고 코사인 유사도를 연산하는 기법.
- **가치**: 형태소가 달라도 문맥적 의미가 유사하면 높은 스코어를 부여하여, 어휘 불일치(Vocabulary Mismatch) 문제를 해결하고 RAG 환경에서의 재현율(Recall@K)을 비약적으로 상승시킴.
- **판단 포인트**: 연산 복잡도 $O(N)$의 병목을 해결하기 위한 근사 최근접 이웃(ANN) 인덱스 아키텍처 필수 도입, OOV(Out-of-Vocabulary) 취약점을 극복하기 위한 도메인 파인튜닝(Contrastive Learning) 및 Hybrid Search 결합 역량.

## Ⅰ. 개요 및 필요성
- **정의**: 자연어를 딥러닝 기반 임베딩 모델을 통해 의미론적(Semantic) 정보를 압축한 Dense Vector로 변환하고, 벡터 공간 상의 기하학적 거리(유사도)를 측정하여 최적의 연관 문서를 검색하는 아키텍처.
- **배경**: 기존 Sparse Retrieval(BM25 등) 방식은 다의어(Polysemy), 동의어(Synonym) 등 자연어의 의미적 풍부함을 반영하지 못하여, 사용자가 정확한 키워드를 모르면 검색에 실패함.
- **필요성**: 자연어 질문으로 대화하는 생성형 AI(LLM) 환경에서, 질문의 숨은 의도와 맥락을 파악하여 관련성 높은 지식 컨텍스트를 제공(RAG)하기 위한 필수 엔진임.

## Ⅱ. Dense Retrieval 아키텍처 (Bi-Encoder 기반)
```text
[ Offline Phase ]
Document 1 -> [ Document Encoder (BERT 등) ] -> Vector [0.1, -0.4, 0.9, ...]
Document 2 -> [ Document Encoder (BERT 등) ] -> Vector [0.2, 0.5, -0.1, ...]
  => [ Vector Database ] 에 색인 (HNSW, IVF-PQ 알고리즘)

[ Online Phase ]
User Query -> [ Query Encoder ] -> Query Vector [-0.3, 0.8, 0.1, ...]
                                         |
                            (ANN: Approximate Nearest Neighbor)
                                         v
                            [ Top-K 유사 문서 추출 및 반환 ]
```

## Ⅲ. 성능 최적화를 위한 핵심 메커니즘
1. **분리형 인코더 (Bi-Encoder/Dual Encoder)**:
   - 질의와 문서를 개별적으로 임베딩하여 연산. 오프라인에서 전체 문서를 미리 임베딩(Pre-compute)해 둘 수 있어 실시간 검색 속도(Latency)가 매우 빠름.
2. **ANN (Approximate Nearest Neighbor) Search**:
   - 밀집 벡터 수백만 개를 일일이 내적 연산(Exhaustive Search)하면 타임아웃 발생. 공간을 군집화(IVF)하거나 그래프(HNSW)로 연결하여 정확도를 조금(1~2%) 포기하고 속도를 1,000배 올림.
3. **Contrastive Learning (대조 학습)**:
   - 인코더를 훈련할 때, 관련 있는(Positive) 문서 쌍의 거리는 좁히고, 헷갈리기 쉬운 관련 없는(Hard Negative) 문서 쌍의 거리는 멀어지도록 가중치를 업데이트함.

## Ⅳ. Sparse vs Dense 비교
| 비교 지표 | Sparse Retrieval (BM25) | Dense Retrieval (Bi-Encoder) |
|:---:|:---|:---|
| **표현 방식** | 어휘 사전 크기의 희소 배열 (대부분 0) | 수백~천 차원의 밀집 실수 배열 (0 없음) |
| **장점** | 정확한 키워드 매칭, 인덱싱 속도 및 비용 저렴 | **의미론적/문맥적 유사도 매칭, 동의어 처리** |
| **단점** | 어휘 불일치 시 검색 실패 (Zero Recall) | **OOV(신조어/코드) 검색 취약, 높은 인프라 비용** |
| **DB 인프라** | Inverted Index (Elasticsearch 등) | **Vector DB (Milvus, Pinecone 등)** |

## Ⅴ. 한계점 및 도메인 최적화 전략
- **리스크 1: OOD (Out-of-Domain) 성능 저하 및 고유명사 한계**:
  - 사전 학습된 범용 모델(OpenAI ada-002 등)은 인터넷 지식 기반이므로 사내 특수 프로젝트명이나 오류 코드를 구별하지 못함.
  - **대응 방안**: In-domain(사내) 질의-문서(QA) 쌍 데이터셋을 수천 건 구축하여, 오픈소스 인코더 모델(BGE-M3, E5)을 파인튜닝. 범용 인코더의 약점을 극복하고 Recall을 대폭 상승시킴.
- **리스크 2: Cross-Encoder 대비 낮은 정밀도(Precision)**:
  - 독립 인코딩(Bi-Encoder) 방식은 질의와 문서 간의 세밀한 상호작용(Attention)을 계산하지 못해 최종 순위 정확도가 떨어짐.
  - **대응 방안**: Bi-Encoder로 빠르게 100개를 추려온 뒤, 매우 정밀한 **Cross-Encoder 리랭커(Reranker)** 모델에 태워 Top-5의 순위를 재정렬하는 2-Stage Pipeline 아키텍처 도입.

## Ⅵ. 실무 적용 및 결론
- **판단 지표**: Recall@20 (검색 파이프라인의 수용력), nDCG@10 (순위의 품질), 질의당 벡터 연산 지연 시간(p95 Latency).
- **실무 설계**: 금융권 약관 분석 시스템 구축 시. 기존 키워드 검색은 "휴대폰 파손 보상" 질의에 "스마트폰 액정 파손" 약관을 매칭하지 못함(어휘 불일치). Dense Retrieval을 전면 도입하되, 금융 특화 용어 사전을 기반으로 Hard Negative 샘플을 추출해 모델을 파인튜닝함. 추가로 약관 번호("제4조 2항") 등 정확 매칭을 위해 BM25를 결합(Hybrid Search)하여 검색 재현율을 98%까지 확보함.
- **결론**: Dense Retrieval은 단순한 텍스트 비교를 넘어 기계가 언어의 '의미(Semantics)' 공간을 유영하게 만든 딥러닝 검색 혁명이며, RAG 시대에 가장 중요한 핵심(Backbone) 정보 추출 엔진임.

### 🔀 문제 유형별 목차 전환
- **Ⅱ·Ⅲ 강조 (개념/원리형)**: In-batch Negatives 및 Hard Negatives 등 대조 학습(Contrastive Learning)의 손실 함수(InfoNCE Loss) 구조, HNSW를 활용한 ANN 매커니즘 상세화.
- **Ⅴ·Ⅵ 강조 (실무/설계형)**: Vector DB 인프라 운영 관점에서의 임베딩 차원 축소(Quantization, PQ/SQ)를 통한 메모리(FinOps) 최적화 방안, 도메인 파인튜닝 아키텍처 전략 작성.
