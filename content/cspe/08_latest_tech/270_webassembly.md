# 📖 【암기용】 개념 완전 이해

> 목적: 웹어셈블리를 처음 봐도 완벽히 이해하게 만든다. 시험 답안 양식이 아니라, 이해를 위한 친절한 설명이다.

## 한눈에
- **개요**: 웹 브라우저에서 실행 가능한 새로운 형태의 저수준(low-level) 이진 형식 코드. 자바스크립트보다 훨씬 빠르며, C/C++/Rust 등 다양한 언어로 짠 코드를 웹에서 돌릴 수 있게 해준다.
- **왜 필요한가**: 자바스크립트는 배우기 쉽지만 복잡한 연산(3D 게임, 영상 편집 등)을 하기엔 느리다. 네이티브 앱만큼 빠른 성능을 웹에서도 누리기 위해 탄생했다.
- **핵심 직관**: "웹 브라우저라는 가상 환경에서 돌아가는 '초소형·초고속 CPU 명령어 세트'"

## 깊이 이해
- **배경·문제의식**: 웹의 역할이 단순히 정보를 보여주는 것에서 포토샵, 동영상 편집기 같은 '애플리케이션'으로 진화했다. 하지만 자바스크립트는 텍스트 기반이라 브라우저가 읽고 실행하는 데 시간이 걸리고 성능 최적화에 한계가 있었다.
- **작동 원리**:
  1. **이진 포맷(Binary Format)**: 텍스트가 아닌 컴팩트한 이진 데이터라 다운로드 속도가 빠르고 브라우저가 바로 이해할 수 있다.
  2. **샌드박스 실행**: 브라우저의 안전한 격리 공간(Sandbox)에서 돌아가므로 보안 걱정이 없다.
  3. **WASI (WebAssembly System Interface)**: 최근에는 웹 브라우저를 넘어, 서버(클라우드)에서도 실행할 수 있게 파일 시스템/네트워크 접근 인터페이스가 표준화되었다.
- **비유**: 외국인(브라우저)에게 한국어(자바스크립트)를 가르쳐서 일을 시키는 대신, 그가 이미 알고 있는 수학 기호(WebAssembly 이진 코드)로 업무 지시서를 주는 것과 같다. 훨씬 빠르고 정확하게 소통할 수 있다.
- **구체 예시**: Figma(디자인 도구), Google Earth, AutoCAD 웹 버전은 모두 웹어셈블리를 사용하여 복잡한 그래픽 연산을 부드럽게 처리한다.
- **흔한 오해·주의점**: "웹어셈블리가 자바스크립트를 대체한다"는 오해다. 둘은 라이벌이 아니라 콤비다. 복잡한 계산은 웹어셈블리가, 화면 UI 조작은 자바스크립트가 맡아 협력한다.

## 연결 개념
- WASI — 웹어셈블리를 서버/임베디드에서 돌리게 해주는 표준
- Rust — 웹어셈블리로 컴파일할 때 가장 궁합이 좋은 현대적 언어
- Serverless Wasm — 도커(Docker)보다 가볍고 빠른 차세대 서버리스 기술

# 📝 【답안용】 시험 답안 템플릿

> 목적: 시험장에서 25분에 그대로 쓰는 답안 양식. 작성방식(추상표현 금지·수치·도식·문제유형 전환)을 엄격히 지킨다.
> 핵심: 웹어셈블리는 이진 포맷의 성능 우위와 샌드박스 기반 보안, 그리고 WASI를 통한 클라우드 확장성을 중심으로 기술한다.

## 핵심 인사이트 (3줄 요약)

> 1. **본질**: 웹어셈블리(Wasm)는 현대 웹 브라우저에서 네이티브에 가까운 속도로 실행될 수 있는 효율적인 스택 기반 가상 머신용 이진 명령어 포맷이다.
> 2. **가치**: C/C++, Rust 등 고성능 언어로 작성된 코드를 웹 환경에서 구동 가능하게 하여 브라우저의 연산 한계를 돌파하고, 서버리스 환경에서 컨테이너의 대안으로 부상하고 있다.
> 3. **판단 포인트**: 실행 지연(Cold Start)에 민감한 엣지 컴퓨팅이나 고성능 연산이 필요한 웹 앱 아키텍처 설계 시 최우선적으로 고려한다.

## 출제 의도 및 답안 포인트

| 출제 의도 | 반드시 짚을 핵심 | 감점 회피 포인트 |
|:---|:---|:---|
| 차세대 웹 및 런타임 기술 이해도 | 이진 포맷(Binary), 스택 기반 VM, 다국어 컴파일 | 단순히 "빠른 자바스크립트"로 오해 |
| 보안 및 격리 매커니즘 파악 | Sandbox, Linear Memory, 메모리 안전성 | 네이티브 코드 실행에 따른 보안 위협 간과 |
| 클라우드/서버 확장성 인지 여부 | WASI (System Interface), Docker와의 비교 | 브라우저 내 실행에만 국한하여 서술 |

> 요약: 성능적 이점(Binary Format)과 범용적 실행 환경(WASI)이라는 두 가지 축을 중심으로 기술한다.

## Ⅰ. 개요 및 필요성

- 정의: 웹 브라우저 및 다양한 런타임에서 실행 가능한 개방형 표준 이진 명령어 포맷
- 배경: 자바스크립트의 동적 타입 분석 및 컴파일 오버헤드로 인한 고성능 연산 처리의 한계 직면
- 필요성: 네이티브 앱 수준의 성능(Near-native speed) 확보와 언어 독립적 실행 환경 구현을 통한 웹 플랫폼 확장

---

## Ⅱ. 구조 및 구성요소

```text
[WebAssembly 실행 및 컴파일 구조]
C/C++/Rust Source -> [LLVM/Wasm Compiler] -> .wasm (Binary)
                                                 |
[JS Engine] <-> [Wasm Runtime (VM)] <---> [Memory/Table]
                   (Sandbox)               (Linear Memory)
```

| 구성요소 | 역할 | 특이사항 |
|:---|:---|:---|
| Binary Format (.wasm) | 컴파일된 실행 코드 | 압축률이 높고 파싱 속도가 빠름 |
| Text Format (.wat) | 사람이 읽을 수 있는 어셈블리 표현 | 디버깅 및 분석용으로 사용 |
| Linear Memory | 연속적인 가변 바이트 배열 | 직접적인 메모리 접근 격리 및 보안 확보 |
| Host Environment | Wasm이 실행되는 브라우저나 서버 런타임 | JS 또는 WASI와 통신 |
| WASI | 파일 시스템, 네트워크 등 OS 자원 접근 표준 | 서버측 Wasm(Server-side)의 핵심 인터페이스 |

> 요약: 컴파일된 이진 코드가 격리된 메모리 공간(Linear Memory)을 가진 전용 가상 머신에서 실행되는 구조다.

---

## Ⅲ. 동작원리 및 흐름도

```text
[웹 브라우저 내 Wasm 실행 흐름]
Fetch .wasm -> Compile (Streaming) -> Instantiate -> Invoke (via JS) -> Execute (Native Speed)
```

| 단계 | 처리 내용 | 검증 기준 |
|:---:|:---|:---|
| 1 | 서버로부터 .wasm 바이너리 파일을 비동기로 다운로드 | 스트리밍 컴파일(Streaming Compilation) |
| 2 | 바이너리 유효성 검사 및 하드웨어 기계어로 변환 | 모듈 캐싱 및 최적화 |
| 3 | 메모리, 테이블 등 필요한 자원 할당 및 인스턴스화 | 격리된 샌드박스 환경 구축 |
| 4 | 자바스크립트에서 Wasm 함수 호출 및 연산 수행 | JS-Wasm 간 데이터 교환(Glue code) |

> 요약: 다운로드와 동시에 컴파일을 수행하며, 자바스크립트와 데이터를 주고받으며 고속 연산을 처리한다.

## Ⅳ. 특징

| 구분 | 내용 | 판단 포인트 |
|:---|:---|:---|
| 성능 | 네이티브 코드 대비 10~20% 내외의 차이 | 자바스크립트 대비 2~10배 가속 |
| 보안 | 강제된 샌드박스 및 메모리 안전성(Memory Safety) | 비인가 시스템 접근 차단 |
| 이식성 | CPU나 OS에 관계없이 동일한 바이너리 실행 | 웹, 클라우드, 임베디드 등 범용성 |

> 요약: 속도, 보안, 이식성이라는 3대 강점을 통해 자바스크립트의 한계를 보완하고 플랫폼을 확장한다.

## Ⅴ. 심화 비교 및 적용 판단

| 구분 | JavaScript | WebAssembly | 선택 기준 |
|:---|:---|:---|:---|
| 실행 방식 | 인터프리터 / JIT (텍스트) | 가상 머신 (이진 포맷) | 연산 복잡도 |
| 타입 시스템 | 동적 타입 (Weak) | 정적 타입 (Strong) | 코드 안정성 및 최적화 |
| 강점 영역 | UI 조작, 비동기 통신, 유연성 | 복잡한 수치 계산, 3D 그래픽, 영상 처리 | 워크로드의 성격 |

> 요약: 사용자 인터렉션은 자바스크립트를, 무거운 연산 로직은 웹어셈블리를 사용하여 하이브리드 구성을 지향한다.

| 리스크 | 원인 | 대응 방안 | 확인 지표 |
|:---|:---|:---|:---|
| 초기 로딩 지연 | 대용량 바이너리 다운로드 및 컴파일 오버헤드 | 스트리밍 컴파일 및 다단 캐싱 적용 | FCP (First Contentful Paint) |
| 개발 복잡도 | C/Rust 언어 숙련도 및 인터페이스 설계 필요 | 표준 프레임워크(Emscripten, Wasm-bindgen) 활용 | 개발 및 유지보수 생산성 |
| 보안 취약점 | 선형 메모리 내의 버퍼 오버플로우 가능성 | 컴파일 타임의 보안 옵션 및 샌드박스 강화 | 메모리 보호 정책 준수 여부 |

> 요약: 성능과 생산성의 트레이드오프를 고려하여 연산 집약적인 핵심 모듈에만 선택적으로 적용한다.

| 점검 항목 | 목표 기준 | 측정 방법 |
|:---|:---|:---|
| 실행 시간 | 기존 JS 대비 50% 이상 단축 | 브라우저 성능 프로파일링 도구 |
| 바이너리 크기 | 동일 기능 JS 대비 30% 이하 압축 | 네트워크 탭 전송 용량 비교 |
| 기동 속도 (Server) | 컨테이너 대비 100배 빠른 기동 (10ms 이하) | 서버리스 콜드 스타트 지연 시간 측정 |

> 요약: 브라우저 내 연산 가속 효과와 서버 환경에서의 빠른 기동 속도를 통해 도입 성과를 측정한다.

## Ⅵ. 실무 적용 및 결론

**적용 방안 3개:**
1. 웹 기반 고성능 도구 개발: 브라우저상에서 구동되는 영상 편집기(Clipchamp), 디자인 도구(Figma) 등에 적용하여 데스크톱 앱 수준의 사용자 경험 제공
2. 서버리스 에지 컴퓨팅: Cloudflare Workers 등 에지 환경에서 컨테이너 대신 Wasm을 사용하여 초저지연 서버리스 함수 실행
3. 게임 엔진 웹 이식: Unity, Unreal 엔진으로 제작된 고사양 게임을 별도 설치 없이 웹 브라우저에서 즉시 실행 가능하도록 배포

**결론 (2줄):**
- 기술사 판단: 웹어셈블리는 '웹의 성능 장벽'을 허문 기술이며, 이제는 브라우저를 넘어 클라우드 네이티브의 새로운 런타임으로 자리매김하고 있다
- 향후 방향: 가비지 컬렉션(GC) 지원, 멀티 스레딩 강화 등을 통해 더 많은 언어와 복잡한 앱을 수용하며 '만능 실행 포맷'으로 진화할 것이다
