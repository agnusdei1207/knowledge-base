# 📖 【암기용】 개념 완전 이해

> 목적: 웹 브라우저 안에서 자바스크립트의 성능 한계를 극복하기 위해 등장했다가, 이제는 도커(Docker) 컨테이너의 자리까지 위협하고 있는 초경량 실행 포맷 'Wasm'의 본질을 이해한다.

## 한눈에
- **정의**: C, C++, Rust, Go 같은 다양한 언어로 짠 코드를 웹 브라우저나 서버(Edge)에서 네이티브(Native) 속도에 가깝게 실행할 수 있도록 컴파일해 주는 **이진(Binary) 명령어 포맷**
- **필요성**: 웹에서 포토샵, 3D 게임, 영상 편집기를 돌리고 싶은데 자바스크립트는 태생적(인터프리터)으로 너무 느리다. 그래서 '미리 컴파일된 가벼운 기계어'를 던져서 브라우저가 바로 씹어먹게 하기 위함
- **핵심 직관**: "자바스크립트가 브라우저에게 한 줄 한 줄 설명해 주는 '통역사'라면, 웹어셈블리는 브라우저의 뇌에 칩을 바로 꽂아서 빛의 속도로 동작하게 만드는 '매트릭스 칩'"

## 깊이 이해
- **배경(왜 등장했나?)**: 구글, 모질라, 애플, 마이크로소프트 4대장이 뭉쳤다. "우리가 맨날 JS 속도 경쟁만 할 게 아니라, 아예 C/C++ 코드를 브라우저에서 돌릴 수 있는 공통 표준을 만들자!" 그렇게 탄생한 WebAssembly는 브라우저 내 샌드박스에서 돌아가는 엄청나게 빠른 바이너리 코드가 되었다. 
- **작동 원리(어떻게 달성했나?)**: 
  1. 개발자가 Rust나 C++로 코드를 짠다.
  2. 컴파일러가 이를 `.wasm` 이라는 아주 작은 바이너리 파일로 바꾼다.
  3. 브라우저 엔진(V8 등)이 이 `.wasm` 파일을 받자마자 내부의 'Wasm 가상머신'에서 네이티브 CPU 속도로 즉시 실행한다.
- **일상 비유**: 미국인(브라우저)에게 한국어 책(코드)을 주면 번역기(JS 엔진)를 돌리느라 10시간이 걸린다. 그래서 아예 '그림책(Wasm)'으로 만들어서 줬더니, 미국인이든 일본인이든 보자마자 1초 만에 내용을 이해하고 웃는 것과 같다.
- **구체 예시 (서버/엣지로의 확장)**: 원래 웹용이었으나, 사람들이 "어? 이거 크기도 1MB밖에 안 되고 켜지는데 0.001초밖에 안 걸리잖아? 도커(Docker) 대신 서버나 IoT 기기에 배포하면 대박이겠는데?"라고 깨달았다. 그래서 브라우저 밖에서도 Wasm을 돌릴 수 있는 **WASI(WebAssembly System Interface)** 표준이 나오며 서버리스/엣지 컴퓨팅의 넥스트 빅 띵(Next Big Thing)이 되었다. 도커 창시자인 솔로몬 하익스가 "2008년에 Wasm/WASI가 있었다면 도커는 만들 필요도 없었다"라고 말했을 정도다.
- **흔한 오해/주의점**: "Wasm이 자바스크립트를 대체(Kill)하는가?" → 아니다. DOM 조작이나 UI 이벤트 처리는 여전히 JS가 잘한다. Wasm은 복잡한 수학 연산, 영상 인코딩, 3D 렌더링 같은 '무거운 일'만 뒤에서 몰래 대신해 주는 훌륭한 조수다.

## 연결 개념
- **WASI (Wasm System Interface)**: Wasm이 브라우저 밖으로 나와서 OS의 파일 시스템, 네트워크에 접근할 수 있게 해주는 표준 인터페이스.
- **Docker (Container)**: Wasm이 가장 위협하고 있는 기술. 컨테이너보다 Wasm이 100배 가볍고 빠르다.
- **Serverless (Edge Computing)**: Wasm의 밀리초(ms) 단위 부팅 속도가 빛을 발하는 분야 (Cloudflare Workers 등).

# 📝 【답안용】 시험 답안 템플릿

## 핵심 인사이트 (3줄 요약)
> 1. **본질**: 웹어셈블리(WebAssembly, Wasm)는 다양한 프로그래밍 언어를 스택 기반의 가상 머신에서 실행 가능한 안전하고 이식성(Portability) 높은 이진(Binary) 포맷으로 컴파일하는 개방형 웹 표준이다.
> 2. **가치**: 브라우저 내에서 네이티브 수준의 성능을 제공하여 웹의 한계를 돌파했으며, 최근 WASI 인터페이스를 통해 클라우드 엣지(Edge)와 서버리스 영역에서 도커 컨테이너의 대안으로 급부상하고 있다.
> 3. **판단 포인트**: 기존 JavaScript와의 보완적 관계, Docker 대비 극단적인 경량성/초고속 콜드 스타트의 장점을 이해하고, OCI(Open Container Initiative) 생태계와의 통합 트렌드를 제시해야 한다.

## Ⅰ. 개요 및 필요성
- **정의**: 웹 브라우저 및 브라우저 외부 환경에서 C/C++, Rust, Go 등의 언어로 작성된 코드를 네이티브에 가까운 속도로 안전하게 실행할 수 있는 바이너리 명령어 형식 (W3C 표준)
- **배경**: JavaScript의 JIT 컴파일 성능이 한계에 도달하여 웹 기반의 고성능 애플리케이션(3D 게임, 영상 편집, CAD 등) 구동에 제약이 컸음
- **필요성**: CPU 아키텍처나 OS에 종속되지 않는 크로스 플랫폼 실행 환경 보장, 다운로드 크기 최소화(바이너리), 격리된 샌드박스를 통한 보안성(Security) 확보

## Ⅱ. WebAssembly의 작동 원리
Wasm은 텍스트 포맷과 바이너리 포맷을 가지며, 스택 기반 가상 머신(Stack-based VM)에서 동작한다.

```text
[ 소스 코드 ] C++, Rust, Go 
     │
     ▼  (LLVM / Emscripten 컴파일러)
[ .wasm 파일 ] 이진 포맷 (극도로 작은 용량, 빠른 디코딩)
     │
     ▼  (HTTP 전송)
[ 호스트 환경 ] 브라우저(V8 엔진) OR 서버/엣지 런타임(Wasmtime)
     │
     ▼  (단 1회의 빠른 컴파일/검증)
[ Native Machine Code ] ➔ OS 샌드박스 내에서 초고속 실행
```

## Ⅲ. WebAssembly 확장의 핵심: WASI (WebAssembly System Interface)
Wasm은 브라우저 내의 샌드박스에서만 돌았기 때문에 파일이나 네트워크에 접근할 수 없었다. 이를 브라우저 밖(Server/OS)으로 꺼낸 것이 WASI다.

1. **WASI 개념**: Wasm 모듈이 운영체제의 기능(파일 시스템, 소켓, 시계 등)을 안전하게 사용할 수 있도록 표준화한 API. (POSIX와 유사한 개념)
2. **보안성(Capability-based Security)**: Wasm 모듈은 실행될 때 명시적으로 허락받은 폴더(예: `/tmp`)에만 접근할 수 있어, 해킹당해도 시스템 전체가 털리지 않는 극강의 샌드박스 보안을 제공.
3. **Write Once, Run Anywhere**: WASI 규격만 맞추면, x86 리눅스 서버에서 돌던 Wasm 파일을 그대로 ARM 맥북이나 IoT 기기로 가져가서 수정 없이 실행할 수 있음.

## Ⅳ. Docker Container vs WebAssembly (Wasm) 비교
서버 환경에서 Wasm은 컨테이너 아키텍처의 강력한 보완재이자 대체재로 평가받고 있다.

| 비교 지표 | Docker Container | WebAssembly (Wasm) + WASI |
|:---|:---|:---|
| **포함 내용물** | App 코드 + 리눅스 OS 배포판 전체 | **오직 컴파일된 App 코드 (OS 없음)** |
| **파일 크기** | 수십 ~ 수백 MB | **수십 ~ 수백 KB (극단적 경량)** |
| **부팅 속도** | 수 초 (초기 세팅 필요) | **1 밀리초(ms) 이하 (즉시 실행)** |
| **보안 모델** | 네임스페이스/cgroups 격리 (OS 커널 공유) | **메모리 보호된 자체 Wasm 가상 머신 샌드박스** |
| **이식성** | x86 컨테이너는 ARM에서 안 돌아감 | **CPU 아키텍처 무관 (Write Once, Run Anywhere)** |

## Ⅴ. 기술적 한계(리스크) 및 해결 방안
| 리스크 요인 | 분석 | 대응 방안 (생태계 동향) |
|:---|:---|:---|
| **언어 제약** | C, Rust 등 컴파일 언어는 완벽 지원하나, Python, Java 등 런타임/GC가 필요한 언어는 Wasm 변환 효율이 떨어짐 | 언어별 컴파일러 고도화 및 Wasm 런타임 내에 가비지 컬렉터(GC) 기능을 내장하는 표준 제정 진행 중 |
| **디버깅 어려움** | 바이너리 형태이므로 브라우저나 서버에서 에러 발생 시 원천 소스코드 추적이 어려움 | Source Map(소스 맵) 지원을 통해 브라우저 개발자 도구에서 원본 Rust/C 코드로 브레이크포인트 디버깅 환경 제공 |

## Ⅵ. 실무 적용 및 결론
**적용 방안 및 실무 가이드:**
1. **Edge Computing 최적화**: Cloudflare Workers, Fastly Compute@Edge 같은 엣지 서버리스 플랫폼에 Wasm 모듈을 배포하면, 전 세계 사용자와 가장 가까운 CDN 노드에서 콜드 스타트 제로(Zero Cold Start)로 백엔드 로직이 수행된다.
2. **K8s + Wasm 하이브리드 배포**: 도커를 전부 버리는 것이 아니라, Docker 이미지 규격(OCI)에 Wasm 모듈을 패키징하고 K8s의 `RuntimeClass`를 활용하여 무거운 기존 컨테이너와 가벼운 Wasm을 한 클러스터 내에서 혼합하여 운영(Krustlet 등)한다.

**결론:**
- WebAssembly는 "브라우저 안의 미니 OS"로 시작하여, 이제는 **"서버 인프라를 가장 가볍고 안전하게 실행하는 보편적 런타임"**으로 진화하고 있다.
- 자바스크립트를 죽이려는 기술이 아니며, 도커를 완전히 멸종시킬 기술도 아니다. 다만, 마이크로서비스보다 더 작은 단위의 '서버리스 함수'나 '엣지 컴퓨팅' 영역에서는 Wasm이 차세대 인프라의 절대 표준으로 자리 잡을 것이다.
