# 📖 【암기용】 개념 완전 이해

> 목적: Model Serving을 처음 봐도 완벽히 이해하게 만든다. 시험 답안 양식이 아니라, 이해를 위한 친절한 설명이다.

## 한눈에
- **개요**: 학습된 머신러닝 모델을 실제 서비스 환경에 배포하여 사용자나 시스템의 요청에 대해 실시간 혹은 배치로 예측 결과(Inference)를 제공하는 체계
- **왜 필요한가**: 모델이 아무리 정확해도 사용자가 쓸 수 있는 형태(API, 앱 등)로 안정적이고 빠르게 제공되지 않으면 아무런 가치를 창출할 수 없기 때문
- **핵심 직관**: 레시피(Model)가 완성된 후, 실제 손님(User)에게 음식을 빠르고 맛있게 대접하는 "주방 서비스 시스템"과 같음

## 깊이 이해
- **배경·문제의식**: 연구용 노트북에서 모델을 실행하는 것과 수천 명의 동시 접속자를 처리하는 것은 완전히 다른 문제다. 모델은 연산량이 많아 일반적인 웹 서버보다 훨씬 느리고 자원을 많이 먹는다. 또한 모델 파일 크기가 수 GB에 달하기도 하여 효율적인 메모리 관리와 지연 시간(Latency) 단축이 핵심 과제가 된다.
- **작동 원리**: 모델을 특정 형식(ONNX, SavedModel, TensorRT 등)으로 변환한 뒤, 이를 실행할 수 있는 서버 환경을 구축한다. 요청이 오면 데이터를 전처리하고, 모델에 통과시켜 결과를 얻은 뒤, 다시 후처리하여 응답한다. 실시간성 요구에 따라 **Online Serving**, **Batch Serving**, **Edge Serving** 등으로 나뉜다.
- **비유**: 오프라인 서점(Batch)은 책을 미리 쌓아두고 한꺼번에 팔지만, 온라인 서점(Online)은 주문이 들어올 때마다 한 권씩 배송한다. 만약 스마트폰 앱에서 바로 검색(Edge)한다면 서점에 갈 필요도 없는 것과 같다.
- **구체 예시**: 유튜브 추천 시스템에서 내가 영상을 클릭하는 순간(Online) 관련 영상을 즉시 추천해주거나, 은행에서 어제 가입한 수만 명의 고객에 대해 밤사이(Batch) 대출 승인 점수를 미리 계산해두는 것 등이다.
- **흔한 오해·주의점**: "Flask나 FastAPI로 감싸기만 하면 서빙이다"라고 생각할 수 있으나, 실제 운영 환경에서는 Auto-scaling, 로드 밸런싱, 버전 관리, A/B 테스팅, GPU 가속 등이 결합된 복잡한 아키텍처가 요구된다.

## 연결 개념
- Latency & Throughput — 모델 서빙의 핵심 성능 지표
- Model Compression — 서빙 속도를 높이기 위한 모델 압축 기술 (Quantization 등)
- ONNX (Open Neural Network Exchange) — 서로 다른 프레임워크 간 모델 교환 표준

# 📝 【답안용】 시험 답안 템플릿

> 목적: 시험장에서 25분에 그대로 쓰는 답안 양식. 작성방식(추상표현 금지·수치·도식·문제유형 전환)을 엄격히 지킨다.

## 핵심 인사이트 (3줄 요약)

> 1. **본질**: Model Serving은 학습된 모델을 API, Batch, Edge 형태로 가용화하여 실시간 또는 주기적 추론(Inference) 서비스를 제공하는 기술적 인프라이다.
> 2. **가치**: 모델의 비즈니스 접점을 생성하며, 낮은 지연 시간(Low Latency)과 높은 처리량(High Throughput)을 통해 서비스 가용성을 확보한다.
> 3. **판단 포인트**: 서비스 요구사항(실시간성, 비용, 자원 제약)에 맞춰 온라인, 배치, 스트리밍, 온디바이스 방식 중 최적의 서빙 아키텍처를 선택해야 한다.

## 출제 의도 및 답안 포인트

| 출제 의도 | 반드시 짚을 핵심 | 감점 회피 포인트 |
|:---|:---|:---|
| 추론(Inference) 방식별 특징 이해 확인 | Online vs Batch vs Stream vs Edge 서빙 비교 | 단순히 "API 배포"라고 단편적으로 서술 |
| 서빙 성능 최적화 역량 확인 | 모델 경량화, 가속기(GPU/NPU) 활용, 캐싱 | 성능 향상을 단순 "속도 개선"으로 추상화 |
| 고가용성 및 확장성 설계 능력 확인 | Auto-scaling, 로드 밸런싱, 모델 버전 관리 | 인프라 운영 관점의 관리 요소 누락 |

> 요약: 서비스 지연 시간(Latency)을 최소화하고 자원 효율을 극대화하는 서빙 전략과 아키텍처 제시가 핵심이다.

## Ⅰ. 개요 및 필요성

- 정의: 학습이 완료된 머신러닝 모델을 프로덕션 환경에 배포하여 입력 데이터에 대한 예측값(Inference)을 산출하고 전달하는 체계
- 배경: 연구 환경 대비 높은 동적 트래픽 처리 필요, 복잡한 연산에 따른 응답 지연 해결 및 하드웨어 자원 효율화 요구
- 필요성: 실시간 의사결정 지원, 대규모 데이터의 효율적 배치 처리, 오프라인 환경에서의 모델 가용성 확보(Edge)

---

## Ⅱ. 구조 및 구성요소

```text
Request (REST/gRPC) -> Load Balancer -> Model Serving Instance (Docker/K8s)
                                              |
                   +--------------------------+--------------------------+
                   |                          |                          |
             Preprocessor              Inference Engine            Postprocessor
             (Data Normalization)      (TensorRT/ONNX Runtime)     (Ranking/Threshold)
```

| 구성요소 | 역할 | 특이사항 |
|:---|:---|:---|
| Model Server | 모델 실행 및 API 엔드포인트 제공 | TensorFlow Serving, TorchServe |
| Inference Engine | 하드웨어 가속 및 연산 최적화 실행 | TensorRT, OpenVINO, ONNX |
| Pre/Post Processor | 데이터 입력 전처리 및 출력 가공 | 도메인 로직 포함 |
| Model Repository | 버전별 모델 아티팩트 저장 및 로딩 | S3, Model Registry 연동 |

> 요약: 로드 밸런싱을 통한 요청 분산과 전용 엔진을 통한 추론 가속화를 통해 고성능 서빙을 구현함.

---

## Ⅲ. 동작원리 및 흐름도 (Online Serving 기준)

```text
요청 수신 -> 전처리(데이터 변환) -> 모델 로딩/추론(Compute) -> 결과 후처리 -> 응답 반환 -> 모니터링(Logging)
      |               |                    |                    |               |               |
      +---------------+--------------------+--------------------+---------------+---------------+-----> 성능 통계 축적
```

| 단계 | 처리 내용 | 검증 기준 |
|:---:|:---|:---|
| 1 | API 요청 수신 및 인증 | 요청 유효성 및 권한 확인 |
| 2 | 특징 인출 (Feature Lookup) | Feature Store 연동, 지연 < 10ms |
| 3 | 추론 연산 (Inference) | P95 Latency < 200ms |
| 4 | 결과 검증 및 응답 | 가드레일(Guardrails) 적용 |

> 요약: 요청마다 실시간으로 특징을 찾아 추론을 수행하며, 낮은 지연 시간(Latency) 확보를 최우선으로 함.

---

## Ⅳ. 특징 (서빙 방식 비교)

| 구분 | Online Serving | Batch Serving | Edge Serving |
|:---|:---|:---|:---|
| 데이터 유입 | 실시간 요청 (REST/gRPC) | 대량 데이터 (DB/S3) | 로컬 센서/사용자 기기 |
| 지연 시간 | 매우 낮음 (ms 단위) | 높음 (분/시간 단위) | 거의 없음 (Zero Latency) |
| 처리량 | 낮음~중간 | 매우 높음 | 개별 기기 한정 |
| 주요 용도 | 추천, 챗봇, 사기 탐지 | 타겟 마케팅, 점수 산출 | 자율주행, 모바일 AI |

> 요약: 즉각적 응답이 필요하면 Online을, 대규모 처리가 필요하면 Batch를, 오프라인 및 프라이버시가 중요하면 Edge를 선택함.

## Ⅴ. 심화 비교 및 적용 판단

| 비교 축 | CPU 서빙 | GPU 서빙 | 선택 기준 |
|:---|:---|:---|:---|
| 처리 속도 | 느림 (복잡한 모델 부적합) | 매우 빠름 (병렬 연산) | 모델 복잡도 및 파라미터 수 |
| 운영 비용 | 낮음 (저렴한 인스턴스) | 높음 (고가 비용) | 예산 및 트래픽 규모 |
| 유연성 | 높음 (일반 서버 활용) | 낮음 (전용 드라이버 필요) | 인프라 운영 난이도 |

> 요약: 정형 데이터 기반의 가벼운 모델은 CPU로, 딥러닝(이미지/LLM) 기반의 무거운 모델은 GPU/NPU를 선택함.

| 리스크 | 원인 | 대응 방안 | 확인 지표 |
|:---|:---|:---|:---|
| Cold Start | 모델 초기 로딩 지연 | Pre-loading 및 Warming-up | 최초 요청 응답 시간 |
| Out of Memory | 모델 크기 대비 부족한 자원 | 모델 경량화(Pruning) 및 분산 서빙 | GPU/RAM 점유율 |
| Serving Skew | 학습-서빙 데이터 불일치 | Feature Store 및 동일 전처리 로직 공유 | 학습 vs 운영 성능 편차 |

> 요약: 초기 지연은 워밍업으로, 자원 부족은 경량화로, 데이터 불일치는 공유 인프라로 대응함.

| 점검 항목 | 목표 기준 | 측정 방법 |
|:---|:---|:---|
| 추론 지연 시간 | P99 Latency 300ms 이내 | 엔드투엔드 API 시간 측정 |
| 처리량 (Throughput) | 초당 1,000 TPS 이상 처리 | 부하 테스트 도구 (Locust 등) |
| 가용성 | 서비스 업타임 99.99% 이상 | 상태 체크(Health Check) 모니터링 |

> 요약: 도입 효과는 추론 속도(Latency), 처리량(Throughput), 시스템 가용성 지표로 판정함.

## Ⅵ. 실무 적용 및 결론

**적용 방안 3개:**
1. 하드웨어 가속 최적화: NVIDIA TensorRT를 적용하여 딥러닝 모델의 부동소수점 연산(FP32)을 정수형(INT8)으로 양자화하고 추론 속도 4배 향상
2. 탄력적 인프라 구성: Kubernetes 상에서 요청 수에 따라 서빙 인스턴스를 자동 조절(HPA)하여 트래픽 급증 시에도 안정적인 서비스 유지
3. 모델 서비스 분리: 전처리 로직은 가벼운 CPU 노드에서, 모델 추론은 전용 GPU 노드에서 수행하는 다단계 파이프라인으로 자원 효율 극대화

**결론 (2줄):**
- 기술사 판단: Model Serving은 ML 모델이 가치를 창출하는 최종 관문이며, 단순 배포를 넘어 성능·비용·안정성의 최적점을 찾는 엔지니어링의 정수임
- 향후 방향: LLM의 거대화에 따라 수천억 개의 파라미터를 효율적으로 서빙하기 위한 모델 병렬화 및 추측 디코딩(Speculative Decoding) 기술이 필수화될 것임
