# 📖 【암기용】 개념 완전 이해

## 한눈에
- **정의**: 데이터 과학자가 힘들게 학습시킨 **인공지능 모델을 상용 서버에 배포하여, 사용자나 다른 애플리케이션의 요청에 맞춰 '실시간(API)' 또는 '주기적(배치)'으로 예측값(추론, Inference)을 뱉어내게 만드는 시스템 및 아키텍처**.
- **필요성**: 주피터 노트북에서 정확도 99%짜리 모델을 만들었어도, 그걸 고객 스마트폰 앱에서 쓸 수 없게 만들면 그냥 비싼 연구 과제에 불과함. 모델 파일(Pickle, pt)은 그 자체로 프로그램이 아님. 이걸 감싸서 수만 명의 동시 접속을 버텨내고, GPU를 쪽쪽 빨아먹으며 0.1초 만에 응답을 쏴주는 "포장 및 서빙(배달)" 인프라가 반드시 필요함.
- **핵심 직관**: 레스토랑의 서빙 시스템. 요리사(데이터 과학자)가 레시피와 특제 소스(모델 가중치)를 만들었음. 하지만 이 소스통을 손님 테이블에 그냥 던져줄 순 없음. 손님이 "스테이크 하나요!"라고 주문(API 요청)하면, 주방(서버)에서 소스를 뿌리고(추론) 접시에 예쁘게 담아 서빙(응답)하는 매끄럽고 빠른 컨베이어 벨트가 있어야 장사가 됨.

## 깊이 이해
- **배경**: AI 모델은 무거움. 일반적인 웹 서버(Spring, Node.js)처럼 가볍게 동작하지 않고 수 기가바이트의 메모리와 GPU 자원을 갉아먹음. 게다가 파이썬(Python)은 실시간 대규모 트래픽 처리(동시성)에 취약함. 그래서 쌩 파이썬으로 띄우지 않고, C++ 기반의 엔진(TensorRT, ONNX 등)으로 포장한 전용 모델 서버(Triton, KServe)가 필요해짐.
- **작동 원리 (서빙의 3대 방식)**:
  1. **Online (실시간 서빙)**: 유저가 넷플릭스에 접속하자마자 즉시 "추천 영화 10개"를 쏴줌. 초저지연(Low Latency)과 트래픽 자동 확장(Auto-scaling)이 생명. (보통 REST API나 gRPC 통신).
  2. **Batch (일괄 배치 서빙)**: 은행에서 밤 12시에 오늘 신규 가입한 10만 명의 대출 한도를 한꺼번에 왕창 예측해서 DB에 밀어 넣음. 속도(Latency)보단 엄청난 양을 한 번에 처리하는 처리량(Throughput)이 중요.
  3. **Edge (온디바이스 서빙)**: 스마트폰 안면인식 잠금해제. 서버로 통신하지 않고 기기 자체에 모델을 욱여넣어 인터넷 없이도 즉시 추론. 압축(경량화) 기술이 핵심.
- **구체 예시**: 번역 앱 파파고. 사용자가 "Hello"를 입력하고 번역 버튼을 누름 $\rightarrow$ 클라우드의 Model Serving API로 텍스트 날아감 $\rightarrow$ 로드밸런서가 여유 있는 GPU 서버 컨테이너로 토스 $\rightarrow$ 거대 번역 모델이 "안녕"이라고 추론 $\rightarrow$ 100ms(0.1초) 만에 스마트폰에 응답값 도착.
- **흔한 오해/주의점**: "Flask나 FastAPI로 감싸서 `app.run()` 하면 끝 아님?" $\rightarrow$ 대학생 수준의 착각. 상용 트래픽이 초당 1,000건(TPS)씩 쏟아지면 파이썬 프로세스는 GIL(전역 인터프리터 락) 때문에 뻗어버림. 진정한 서빙은 입력 데이터를 묶어서 한 번에 GPU로 밀어 넣는 '다이나믹 배칭(Dynamic Batching)'과 C++ 런타임 기반의 병렬 처리를 필수로 써야 함.

## 연결 개념
- **Inference (추론)**: 이미 학습된 모델에 새 데이터를 집어넣어 결과(예측)를 뽑아내는 행위. 서빙 서버의 유일한 존재 목적.
- **Model Registry (모델 레지스트리)**: 서빙 서버가 최신 버전의 모델 파일을 다운로드 받기 위해 쳐다보는 중앙 저장고(창고).
- **A/B Test / Canary Deployment**: 서빙할 때 갑자기 새 모델 100%로 갈아치우면 위험하니까, 기존 모델(A) 90%, 새 모델(B) 10% 비율로 트래픽을 나눠서 서빙하며 성능을 간 보는 배포 전략.

# 📝 【답안용】 시험 답안 템플릿
## 핵심 인사이트 (3줄 요약)
- **본질**: 데이터 사이언티스트가 개발 및 훈련을 완료한 머신러닝/딥러닝 모델(Artifact)을 프로덕션 환경에 배포하여, 다운스트림 애플리케이션이나 엔드 유저에게 빠르고 안정적으로 추론(Inference) 결과를 제공하는 아키텍처.
- **가치**: 모델의 비즈니스 가치 창출을 위한 최종 인터페이스(관문) 역할을 하며, 대규모 동시 요청 환경에서 하드웨어 연산 자원(GPU/CPU) 활용 효율을 극대화하여 서비스 가용성과 응답 지연(Latency)의 SLA를 준수함.
- **판단 포인트**: 서비스의 요구사항에 맞춰 실시간 응답이 필수적인지(Online API), 대용량 데이터의 주기적 예측인지(Batch), 보안 및 네트워크 단절에 대비해야 하는지(Edge)를 선별하여 아키텍처를 취사선택하고, 하드웨어 가속(TensorRT, ONNX)을 통한 추론 최적화를 동반해야 함.

## Ⅰ. 개요 및 필요성
- **정의**: 이종 프레임워크(PyTorch, TensorFlow 등)로 개발된 모델을 규격화하여 컨테이너 환경에 로드하고, REST API/gRPC 통신 기반의 추론 엔드포인트를 프로비저닝(Provisioning)하는 일련의 기술 프랙티스.
- **배경**: AI 서비스의 스케일 아웃. 딥러닝 모델 파라미터 수의 폭발적 증가(LLM 시대)로 인해 단순 웹 프레임워크 기반 배포로는 OOM(Out of Memory) 크래시 및 심각한 지연(Latency) 발생.
- **필요성**: 비즈니스 실시간성 보장, 트래픽 스파이크에 대응하는 탄력적 확장(Auto-scaling), 모델 버전 무중단 교체(Zero-Downtime Deployment), 섀도우 배포/A-B 테스트 등 운영 통제권 확보.

| 계층 (Layer) | 핵심 구성 요소 | 메커니즘 및 주요 기술 (Tools) |
|:---:|:---|:---|
| **Interface Layer** | API 엔드포인트 / 로드밸런서 | REST, gRPC 프로토콜을 통해 클라이언트의 요청을 로드밸런싱하여 뒷단 워커로 라우팅. |
| **Model Server** | 서빙 프레임워크 | NVIDIA Triton, KServe, Seldon Core. 다중 모델 로드, 다이나믹 배칭(Dynamic Batching) 큐잉 지원. |

## Ⅲ. 서빙 패턴 (Serving Patterns) 비교 분석
어떻게 배달할 것인가.
| 서빙 방식 | 아키텍처 특징 | 핵심 최적화 목표 | 적용 비즈니스 유스케이스 |
|:---:|:---|:---|:---|
| **Online (실시간 API)** | 유저 요청 시 즉시(On-demand) 추론 연산 후 반환. | **Low Latency** (초저지연, ms 단위). 트래픽 확장에 따른 자동 스케일링. | 실시간 추천, 챗봇, 사기 결제 차단(FDS). |
| **Batch (비동기 일괄)** | 스케줄러(Airflow)에 의해 대규모 데이터 셋을 야간에 긁어와 한 번에 예측해 DB에 적재. | **High Throughput** (처리량 극대화). GPU 100% 점유 사용. | 다음 날 타겟 마케팅 리스트 추출, 대규모 신용 등급 재산정. |
| **Edge / On-Device** | 클라우드가 아닌 사용자 스마트폰, IoT, 차량 내부 NPU 칩셋에 모델을 경량화하여 탑재. | **네트워크 독립성**, 데이터 프라이버시, 메모리/배터리 소모 최소화. | 모바일 안면/지문 인식, 자율주행, 스마트 팩토리 불량 판독. |

## Ⅳ. 고성능 추론을 위한 서빙 최적화(Optimization) 기법
파이썬의 한계를 극복하는 하드웨어 튜닝.
1. **모델 컴파일 및 포맷 변환 (ONNX)**: PyTorch 등으로 짠 무거운 구조를, 프레임워크 종속성 없는 개방형 규격(ONNX)으로 변환해 불필요한 연산 노드를 가지치기(Pruning)함.
2. **양자화 (Quantization)**: GPU 메모리를 먹는 주범인 32비트 부동소수점(FP32) 가중치를 16비트(FP16)나 8비트 정수형(INT8)으로 압축. 정확도는 1% 손해 보면서 추론 속도는 2~4배 폭등시킴.
3. **다이나믹 배칭 (Dynamic Batching)**: 서빙 서버 큐(Queue)에 유저 요청이 동시다발적으로 들어올 때, 1개씩 GPU로 넘기지 않고 5ms 대기 후 요청 32개를 모아서 GPU의 병렬 코어로 한 방에 처리(Throughput 극대화).

## Ⅴ. 실무 적용 및 결론
- **판단 지표**: 서빙 P99 Latency(99%의 요청이 N 밀리초 내에 응답), 초당 처리 가능한 요청 수(TPS / Throughput), 무중단 배포 스위칭 성공률, 모델 단위 서빙 인프라 운영 비용(FinOps).
- **실무 설계**: e-커머스 K사의 '초개인화 홈 화면 상품 추천 API' 아키텍처. 초기엔 Spring 서버 안에 파이썬 스크립트를 내장해 서빙했으나, 트래픽 피크 시 JVM 메모리 초과 및 2초 이상 렌더링 지연 발생. 조치 방안: Kubernetes 기반 KServe 전용 아키텍처 분리. 1) 추천 딥러닝 모델을 TensorRT 포맷으로 변환해 GPU 추론 최적화. 2) NVIDIA Triton Inference Server를 도입해 다이나믹 배칭 켜기. 3) KServe의 Serverless 아키텍처를 적용해, 평시엔 파드를 최소 유지하다 이벤트 트래픽 폭증 시 10초 만에 파드 100개로 Auto-scaling(Scale-to-Zero 지원). 지연시간 100ms 이내로 단축 및 서버 비용 40% 절감.
- **결론**: 연구실의 모델은 코스트(Cost) 부채이지만, 서빙 환경의 모델은 레비뉴(Revenue) 자산이다. AI 트랜스포메이션의 진짜 결승선은 훌륭한 논문을 쓰는 것이 아니라, 무자비한 트래픽 환경 속에서도 묵묵히 0.1초 만에 예측값을 뱉어내는 탄탄한 '서빙 아키텍처'를 구축하는 데 있다. 향후 LLM 시대를 맞아 vLLM, PagedAttention과 같은 거대 언어 모델 특화 메모리 서빙 기술이 인프라 엔지니어링의 새로운 격전지가 될 것이다.

### 🔀 문제 유형별 목차 전환
- **Ⅱ·Ⅲ 강조 (개념/원리형)**: 무중단 모델 배포(Zero-Downtime Deployment) 전략 비교. 단일 진입점(Gateway) 라우팅을 이용해 90%의 트래픽은 기존 A모델에, 10%는 신규 B모델에 태워 위험을 분산하는 카나리(Canary) 배포와 100% 트래픽을 동시에 쏴서 결과만 비교하는 섀도우(Shadow) 배포의 아키텍처 차이.
- **Ⅴ·Ⅵ 강조 (실무/설계형)**: LLM(거대 언어 모델) 전용 서빙 최적화 방안 설계. 수백 기가의 가중치와 엄청난 컨텍스트 창을 가진 LLM을 실시간 서빙하기 위해, GPU 메모리의 파편화를 막고 KV 캐시(Key-Value Cache)를 블록 단위로 할당하여 메모리 효율을 극대화하는 PagedAttention (vLLM 프레임워크) 기술 적용 방안.
