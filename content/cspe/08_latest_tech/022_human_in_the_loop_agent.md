# 📖 【암기용】 개념 완전 이해

## 한눈에
- **개요**: Human-in-the-Loop(HITL) 에이전트는 AI **에이전트**(001 참조) 실행 흐름의 특정 지점에 **사람의 검토·승인·수정** 단계를 삽입해, 고위험 행동이 사람 확인 없이 실행되지 않도록 하는 통제 패턴이다. 에이전트 권한통제(020)가 "도구를 호출할 자격"을 판단한다면, HITL은 "자격이 있더라도 사람이 최종 확인하는가"를 결정한다.
- **왜 필요한가**: 결제·권한 변경·보안 정책 수정처럼 오실행 시 피해가 큰 작업에서, AI의 환각·프롬프트 인젝션·과다 권한으로 인한 변경 사고를 승인 게이트로 차단해야 한다. 전건 자동 실행은 사고 시 책임 소재가 불분명하고, 전건 수동 승인은 처리 지연만 유발하므로 위험등급별 분기가 필요하다.
- **핵심 직관**: 신용카드 고액 결제에서 "정말 결제하시겠습니까? OTP를 입력하세요"라고 묻는 것과 같다. 소액은 자동, 고액은 추가 인증, 초고액은 은행 직원 승인이 필요한 구조다.

## 핵심 용어 정리 (내부에 등장하는 것들)

| 용어/표기 | 의미 | 비유·예 |
|:---|:---|:---|
| HITL(상위 패턴) | 자동화 프로세스에 사람 판단 단계를 삽입하는 설계 패턴 | 자동 번역 후 사람이 교정 |
| 위험등급(Risk Level) | 도구 호출의 영향도를 분류한 등급. Low(조회)·Medium(변경)·High(관리·삭제) | 화재 위험도에 따른 소화기 배치 |
| 승인 SLA | 승인 요청 접수 후 처리 완료까지의 목표 시간 | "30분 내 응답" 약속 |
| 에스컬레이션(Escalation) | 승인자 부재·SLA 초과 시 상위 승인자에게 자동 전달 | 팀장 부재 시 부서장에게 올라감 |
| Proposal(제안서) | 에이전트가 실행 전 생성하는 행동 계획(근거·영향·롤백 포함) | 결재 상신서 |
| 2인 승인(Dual Control) | 고위험 작업에 2명 이상의 독립 승인을 요구하는 원칙 | 금고 열쇠를 2명이 동시에 돌림 |
| 긴급 승인(Break-the-Glass) | 긴급 상황에서 사후 검토 조건부로 즉시 실행을 허용 | 비상시 유리 깨고 소화기 사용 |

## 깊이 이해
- **배경·문제의식**: 에이전트 권한통제(020)는 PDP/PEP로 "호출 가능 여부"를 판단하지만, 허용된 도구라도 실행 결과의 영향도가 클 수 있다(예: 정상 권한으로 방화벽 전체 규칙 삭제). HITL은 이 "허용되었지만 위험한" 영역을 사람 승인으로 보호한다. 반면 모든 작업을 사람이 확인하면 에이전트를 쓰는 의미가 없으므로, 위험등급에 따라 자동화 수준을 분기하는 것이 핵심 설계다.
- **작동 원리(어떻게+왜)**: ① 에이전트가 도구 호출 전에 Proposal(실행 계획)을 생성한다. Proposal에는 실행 근거·대상 시스템·변경 전후 값·영향 범위·롤백 방안이 포함된다. ② Risk Scoring 모듈이 {도구 위험등급, 변경 범위, 금액, 데이터 민감도}를 평가해 Low(자동 실행)·Medium(1인 승인)·High(2인 승인)로 분기한다. ③ 승인이 필요하면 승인자에게 Proposal을 전달하고 SLA 타이머를 시작한다. 승인자 화면에 근거·영향·변경 전후 diff·롤백 버튼이 표시된다. ④ 승인되면 실행, 거부되면 차단하고, 승인자·사유·결과를 감사로그(021)에 기록한다. SLA 초과 시 상위자에게 에스컬레이션한다.
- **비유**: 병원 처방 시스템과 같다. 일반 처방(Low)은 의사가 바로 내리지만, 고위험 약물(High)은 약사 검증+팀장 승인을 거친다. 긴급 상황에서는 Break-the-Glass로 즉시 투약하되, 24시간 내 사후 검토를 반드시 실시한다.
- **구체 예시**: 보안 에이전트가 DDoS 공격 탐지 후 특정 IP 대역 차단을 제안한다. Proposal: "203.0.113.0/24 차단, 영향: 외부 파트너 3사 접속 불가, 롤백: 차단 해제 명령 fw-unblock-0715". 보안 담당자가 영향 범위를 확인하고 10분 내 승인하면 실행된다. 미승인 시 에스컬레이션되고, 긴급 시 Break-the-Glass로 즉시 차단 후 24시간 내 사후 검토를 진행한다.
- **흔한 오해·주의점**: "사람을 넣으면 통제가 완성된다"는 오해가 있다. 승인 화면에 근거·영향·롤백이 표시되지 않으면 승인자가 내용을 확인하지 않고 "승인"만 누르는 형식적 승인(rubber-stamping)이 발생한다. 또한 승인 피로(alert fatigue)를 줄이려면 Low 등급은 반드시 자동 실행하고, 진짜 위험한 것만 사람에게 올려야 한다.

## 연결 개념
- 에이전트 권한통제(020) — 도구 호출 "자격"을 판단하는 서버 측 통제. HITL과 보완 관계
- 에이전트 감사로그(021) — 승인·거부 이벤트의 감사 기록
- 에이전트 가드레일(029) — 출력·행동의 안전성 제어. HITL과 계층적으로 결합

## Ⅰ. 개요 및 필요성

- 개요: AI 에이전트 실행 흐름에 위험등급별 사람 승인 게이트를 삽입한 통제 패턴임
- 배경: 에이전트 자율 실행 시 환각·인젝션·과다 권한으로 고위험 변경 사고가 발생할 수 있음
- 필요성: 고위험 업무(결제·삭제·보안 정책)에서 위험등급별 승인 분기와 감사 기록이 필수임

---

## Ⅱ. 구조 및 구성요소

```text
에이전트 Proposal 생성 -> Risk Scoring(위험등급 판정)
  -> Low: 자동 실행 / Medium: 1인 승인 / High: 2인 승인
     -> 승인 화면(근거/영향/롤백) -> Execute/Reject -> Audit Log
```

| 구성요소 | 역할 | 특이사항 |
|:---|:---|:---|
| Proposal Generator | 실행 근거·영향·롤백을 포함한 제안서 생성 | 승인자 판단의 기반 |
| Risk Scoring | 도구 위험등급·변경 범위·민감도 평가 | Low/Medium/High 3단계 |
| Approval Gateway | 승인 요청·SLA 타이머·에스컬레이션 관리 | SLA 초과 시 상위 전달 |
| Execution Gate | 승인 결과에 따른 실행·차단·롤백 집행 | 감사 로그 연동 |

> 요약: Proposal 생성→위험등급 평가→승인 게이트→실행·감사로 사람 통제를 구조화함.

---

## Ⅲ. 동작원리 및 흐름도

```text
실행 제안 생성 -> 위험등급 산정 -> 자동/1인/2인 승인 분기
  -> 승인 화면 표시 -> 승인/거부/수정 -> 실행·감사 기록
```

1. Proposal 생성: 에이전트가 도구 호출 전에 근거·대상·변경 전후·영향 범위·롤백 방안을 포함한 제안서를 작성함
2. 위험등급 판정: Risk Scoring이 {도구 등급, 변경 범위, 금액, 민감도}를 평가해 Low(자동)/Medium(1인)/High(2인) 승인으로 분기함
3. 승인 처리: 승인자에게 Proposal을 전달하고, 근거·영향·diff·롤백 버튼을 승인 화면에 표시하며 SLA 타이머를 기동함
4. 실행·감사: 승인되면 실행, 거부되면 차단하고, 승인자·사유·결과를 Trace ID와 함께 감사 로그(021)에 기록함

> 요약: Proposal→위험등급→승인 분기→실행·감사 순서로 고위험 행동에 사람 게이트를 적용함.

---

## Ⅳ. 특징

- 위험등급 분기: Low는 자동, Medium은 1인, High는 2인 승인으로 자동화 수준을 차등 적용함
- 근거 가시성: 승인 화면에 실행 근거·영향 시스템·변경 diff·롤백 방안이 표시되어 형식적 승인을 방지함
- 책임 명확화: 승인자 개인이 승인 사유와 함께 기록되어 사고 시 책임 소재가 명확함
- SLA 기반: 승인 대기 시간에 SLA(예: 30분)를 설정하고 초과 시 에스컬레이션으로 병목을 방지함
- 긴급 모드: Break-the-Glass로 즉시 실행을 허용하되 24시간 내 사후 검토를 강제함

## Ⅴ. 심화 비교 및 적용 판단

| 구분 | 완전 자동 에이전트 | HITL 에이전트 | 선택 기준 |
|:---|:---|:---|:---|
| 실행 속도 | 즉시(ms 단위) | 승인 SLA 의존(분~시간) | 업무 긴급도와 위험도 |
| 오류 통제 | 정책 엔진 자동 판단 | 사람 검토로 환각·오작동 차단 | 오실행 영향도 |
| 책임 소재 | 시스템·운영팀 | 승인자 개인 책임 포함 | 규제·감사 요구 수준 |

> 요약: 조회형은 자동, 변경형은 1인, 관리자 권한은 2인 승인으로 분기하는 것이 기본 설계임.

**리스크·대응:**
- 승인 지연 병목: 승인자 부재·과다 요청 → 대리 승인 체계+SLA 30분+에스컬레이션 (지표: 평균 승인 대기 시간)
- 형식적 승인: 근거 미표시로 확인 없이 승인 → Proposal에 근거·영향·diff·롤백을 필수 표시 (지표: 근거 확인 클릭률)
- 긴급 승인 남용: Break-the-Glass를 일상적으로 사용 → 긴급 승인 비율 5% 이내 제한, 24시간 사후 검토 (지표: 긴급 승인 비율)

**도입 후 점검 지표:**
- 승인 SLA 준수율: 요청 후 30분 내 처리 95% — 승인 큐 모니터링
- 감사 완전성: 승인자·사유·결과 100% 기록 — 로그 누락 건수 주간 점검

---

## Ⅵ. 실무 적용 및 결론

**적용 방안 3개:**
1. 도구별 위험등급(Low/Medium/High)을 정의하고 조회형 자동·변경형 1인·관리 권한 2인 승인으로 분류함
2. 승인 화면에 실행 근거·영향 시스템·변경 전후 diff·롤백 버튼·만료 타이머를 표시해 형식적 승인을 방지함
3. 승인자·사유·실행 결과를 Trace ID로 감사 로그에 기록하고, 긴급 승인은 24시간 내 사후 검토를 강제함

**결론:**
- 기술사 판단: 고위험 업무에서는 자동화율보다 승인 근거의 가시성과 롤백 가능성이 우선 설계 항목임
- 향후 방향: HITL은 AI 거버넌스(161)와 결합해 위험 기반 자동화 수준을 결정하는 표준 패턴으로 발전함
