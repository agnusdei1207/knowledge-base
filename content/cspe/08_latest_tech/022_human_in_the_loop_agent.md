## Ⅰ. 개요
- **정의**: 비가역적 액션 직전에 에이전트를 일시 정지시켜 인간의 승인·반려·수정을 강제하는 안전 브레이크 체계
- **배경/필요성**: 에이전트가 결제·삭제·발송 등 되돌릴 수 없는 행위를 자율 수행하면서 환각·프롬프트 인젝션에 의한 대형 사고 리스크가 부상함. 최종 법적 책임이 인간에게 귀속되므로 치명적 분기점에서 인간 통제권 확보가 필수
- **비유**: 자율주행 차량의 보조석 브레이크 — 평소에는 AI가 운전하되 위험 순간에만 인간이 개입

| 출제 의도 | 반드시 짚을 핵심 | 감점 회피 포인트 |
|:---|:---|:---|
| 완전 자율과 HITL의 아키텍처 차이 | 체크포인팅(State Snapshot), 비동기 승인 루프, Dynamic HITL | 단순 승인 UI가 아닌 상태 직렬화·복원 메커니즘을 서술해야 함 |

> 요약: 비가역 액션 직전 체크포인트를 찍고 인간 승인을 대기하는 비동기 안전 아키텍처

## Ⅱ. 구성요소
```text
+--------------------+
|  Agent Runtime     |
|  (자율 실행 구간)  |
+---------+----------+
          | Tool 호출 요청
          v
+---------+----------+
|  Risk Classifier   |
|  (위험도 분류기)   |
+---------+----------+
     |           |
     | 안전      | 위험(requires_approval)
     v           v
+----+----+ +----+-----------+
| 즉시    | | Checkpoint     |
| 실행    | | (State 직렬화) |
+---------+ +----+-----------+
                 |
                 v
          +------+-------+
          | Human Review |
          | (Slack/Web)  |
          +------+-------+
                 | 승인/반려/수정
                 v
          +------+-------+
          | State Resume |
          | (상태 복원)  |
          +--------------+
```

| 구성요소 | 설명 | 비유 |
|:---|:---|:---|
| Risk Classifier | 도구 호출의 위험도를 태그(requires_approval) 기반으로 분류하는 게이트 | 공항 보안 검색대 |
| Checkpoint Engine | 에이전트의 전체 상태(변수·대화 이력·중간 결과)를 DB에 직렬화하여 스냅샷 저장 | 게임 세이브 포인트 |
| Human Review UI | Slack·웹 대시보드를 통해 승인(Approve)·반려(Reject)·수정(Override) 인터페이스 제공 | 결재 시스템 |
| State Resume | 인간 응답 수신 후 DB에서 스냅샷을 복원하여 중단 지점부터 실행 재개 | 게임 로드 |

> 요약: 위험도 분류→체크포인트→인간 리뷰→상태 복원의 4요소로 비동기 승인 루프 구성

## Ⅲ. 절차
```text
+----------------+    +----------------+    +----------------+    +----------------+
| 1. 트리거 분류 | -> | 2. 상태 동결   | -> | 3. 인간 승인   | -> | 4. 실행 재개   |
| (Risk Gate)    |    | (Checkpoint)   |    | (Async Review) |    | (Resume)       |
+----------------+    +----------------+    +----------------+    +----------------+
```

1. **트리거 분류(Risk Gate)** — 도구별 위험 태그를 검사하여 안전 도구는 즉시 실행, 비가역 도구(Send_Email, Drop_Table 등)는 승인 루프로 분기
2. **상태 동결(Checkpoint)** — 에이전트의 전체 컨텍스트(프롬프트 히스토리, 중간 변수, 실행 위치)를 DB에 직렬화하여 서버 메모리 의존성 제거
3. **인간 승인(Async Review)** — Slack/웹 대시보드로 알림 발송, 인간이 내용 확인 후 승인·반려·파라미터 수정(Override) 중 택 1
4. **실행 재개(Resume)** — 승인 수신 시 DB에서 스냅샷을 복원하여 중단 시점의 정확한 코드 라인부터 실행 속개. 반려 시 사유를 State에 기록하고 종료

> 요약: 위험 도구 감지→상태 스냅샷→비동기 인간 승인→스냅샷 복원 실행의 4단계 루프

## Ⅳ. 문제점
- [승인 병목(Approval Bottleneck)]: 에이전트는 초당 수백 건 처리 가능하나, 인간 승인 처리량은 하루 수십 건 수준 — 자동화 효과 상쇄
- [알림 피로(Alert Fatigue)]: 과도한 승인 요청으로 인간이 내용 미확인 후 맹목적 승인 — HITL 방어선 무력화
- [상태 복원 비용]: 대규모 컨텍스트(128k 토큰) 직렬화/역직렬화 시 지연 및 스토리지 부하 발생

> 요약: 승인 병목, 알림 피로에 의한 방어선 무력화, 상태 직렬화 오버헤드가 3대 과제

## Ⅴ. 개선방안
1. 단기: Dynamic HITL 도입 — 금액·감정 분석 등 위험 지표 기반으로 임계치 이하(예: 5만 원 미만 환불)는 자율 실행 허용
2. 중기: 에이전트 Confidence Score 기반 자율성 점진 확대 — 누적 승인율 95% 이상 도메인부터 HITL 해제, 사후 감사 로그(021 참조)로 전환
3. 장기: AI-in-the-Loop — 가드레일 전문 에이전트(AI Judge)가 1차 승인 수행, 인간은 정책(Policy) 설정·예외 케이스만 관여

- [알림 피로]: [과도한 승인 빈도] → 위험도 3등급(High/Medium/Low) 분류 체계 적용, High만 인간 알림 (지표: 일일 승인 요청 ≤ 20건)

> 요약: Dynamic HITL로 병목 완화, Confidence 기반 자율성 확대, AI-in-the-Loop로 인간 부담 최소화

## Ⅵ. 전망
- 향후 발전 방향: HITL 승인 이력이 학습 데이터로 축적되어 가드레일 에이전트의 자율 승인 정확도가 향상되는 자기강화 루프 형성
- 기술사적 판단: 완전 자율과 완전 수동 사이의 현실적 타협점으로서, 엔터프라이즈 AI 도입의 필수 관문임
- 기술사 제언: 초기 100% HITL에서 시작하여 도메인별 신뢰도 축적에 따라 단계적으로 자율성을 확대하는 로드맵을 배포 전 수립할 것
