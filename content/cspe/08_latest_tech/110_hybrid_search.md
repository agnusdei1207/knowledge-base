# 📖 【암기용】 개념 완전 이해

## 한눈에
- **정의**: 키워드 기반의 전통적인 희소 검색(Sparse Search, 예: BM25)과, 딥러닝 임베딩 기반의 밀집 검색(Dense Search, 의미 검색)을 동시에 실행한 뒤, 두 결과를 합쳐 최적의 정답 문서를 찾아내는 검색 방식.
- **필요성**: 벡터(Dense) 검색은 '문맥'은 잘 파악하지만, 고유명사, 품번(예: "TX-9980"), 제품명 등 정확히 그 단어가 들어가야만 하는 검색에는 젬병임. 반대로 키워드(Sparse) 검색은 동의어("사과" vs "Apple")를 못 알아먹음.
- **핵심 직관**: 형사 두 명이 수사하는 것과 같음. A형사(Sparse)는 범인이 남긴 "지문과 족적(정확한 키워드)"만 철저히 대조하고, B형사(Dense)는 "범행 동기와 수법(전체적인 의미와 맥락)"을 추론함. 둘의 수첩을 합쳐 공통으로 지목된 놈을 범인(정답)으로 확정하는 것.

## 깊이 이해
- **배경**: RAG 시스템의 초기 열풍 땐 "벡터 DB(Dense)가 만능"이라는 환상이 있었으나, 기업 실무에 적용해 보니 특정 법 조항 번호나 제품 코드를 자꾸 못 찾는 치명적 한계(Recall 저하)가 발견됨. 이를 보완하기 위한 필수 아키텍처로 하이브리드 검색이 자리 잡음.
- **작동 원리 (Sparse + Dense $\rightarrow$ Fusion)**:
  1. 문서가 들어오면, 역색인(Inverted Index)과 벡터 임베딩을 모두 만들어 둠.
  2. 질의가 들어오면, BM25(키워드 빈도) 엔진과 Vector DB를 병렬로 동시 호출함.
  3. 두 쪽에서 상위 K개(예: 50개씩)의 후보를 뽑아옴.
  4. (결합 로직): 점수의 스케일이 다르므로 1/(순위+K) 공식을 쓰는 RRF(Reciprocal Rank Fusion)나 가중합(Weighted Sum) 알고리즘으로 문서들의 최종 등수를 매겨 Top-5를 뽑아 LLM에 넘김.
- **구체 예시**: Q: "V100 GPU 발열 이슈 트러블슈팅". $\rightarrow$ Dense 검색기는 'GPU 과열 문제'라는 맥락은 이해하지만 'V100'이라는 고유 모델명을 엉뚱한(A100 등) 문서로 착각함. $\rightarrow$ Sparse 검색기(BM25)는 정확히 문서 내에 'V100'이 박혀있는 문서만 싹 쓸어옴. $\rightarrow$ 둘을 합치면 V100 모델이면서 발열과 관련된 완벽한 문서를 찾아냄.
- **흔한 오해/주의점**: 엔진을 두 개 돌려야 하므로 검색 인프라 유지보수 비용과 스토리지 비용이 두 배로 듦. 점수 합산 시 정규화(Normalization)를 제대로 안 하면, 한쪽 엔진의 결과가 다른 쪽을 압도해 버려 하이브리드의 의미가 사라짐.

## 연결 개념
- **BM25 (Best Matching 25)**: 전통적인 검색 엔진(Elasticsearch 등)의 표준 키워드 매칭 알고리즘. 단어의 출현 빈도와 문서 길이를 고려함 (Sparse).
- **RRF (Reciprocal Rank Fusion)**: 점수(Score)가 아니라 각 검색기의 '순위(Rank)'를 기반으로 공평하게 결과를 합치는 마법의 결합 수식.
- **Cross-Encoder Reranker**: 하이브리드 검색으로 가져온 약간 넉넉한 문서 풀(Pool)을 가장 정밀하게 다시 채점하는 최종 보스 모델. Advanced RAG 구성의 핵심.

# 📝 【답안용】 시험 답안 템플릿
## 핵심 인사이트 (3줄 요약)
- **본질**: 어휘적 일치(Lexical Match)에 강한 Sparse 검색과 의미적 일치(Semantic Match)에 강한 Dense 검색을 병렬 수행하고, 결과를 융합(Fusion)하는 상호 보완적 검색 아키텍처.
- **가치**: 약어, 고유명사, 일련번호 등 정확한 키워드 매칭이 필수적인 엔터프라이즈 도메인에서 벡터 검색 단독 수행 시 발생하는 재현율(Recall) 저하 현상을 근본적으로 해결.
- **판단 포인트**: 이기종 검색 엔진 동시 운영에 따른 인프라 비용/복잡도 증가 감수, 점수 스케일이 다른 두 결과를 융합하기 위한 RRF 파라미터 튜닝 및 정규화(Normalization) 전략 수립.

## Ⅰ. 개요 및 필요성
- **정의**: BM25, TF-IDF 기반의 희소 검색(Sparse Retrieval)과 임베딩 모델 기반의 밀집 검색(Dense Retrieval)을 결합하여, 어휘적(Lexical) 특성과 의미적(Semantic) 특성을 동시에 캡처하는 RAG 검색 기법.
- **배경**: 순수 Dense 검색(Vector)은 동의어 및 문맥 파악에 탁월하나, 아웃라이어 단어(특수 품번, 코드, 법령 등 OOV: Out Of Vocabulary) 검색에 극도로 취약함.
- **필요성**: 도메인 특화 용어가 난무하는 기업 환경에서 검색의 사각지대(False Negative)를 없애고, RAG 파이프라인의 핵심인 검색 품질(Recall@K)을 한계점 이상으로 끌어올리기 위함.

## Ⅱ. Hybrid Search 아키텍처 흐름도
```text
[ User Query ]
       |
       +-----------------------------------+
       | (동시 병렬 검색)                  |
[ BM25/SPLADE Engine ]            [ Embedding Model & Vector DB ]
 (Exact Keyword 매칭)               (Contextual/Semantic 매칭)
       |                                   |
   Top-50 후보 문서                     Top-50 후보 문서
       |                                   |
       +------------> [ Fusion Engine ] <--+
                    (결과 병합 및 점수 산출)
                           |
                     [ Reranker ] (선택적 최종 재정렬)
                           |
                [ Top-K 최우수 문서 반환 ]
```

## Ⅲ. Sparse vs Dense 비교 및 보완 관계
| 구분 | Sparse Retrieval (BM25 등) | Dense Retrieval (Vector 임베딩) |
|:---:|:---|:---|
| **매칭 원리** | 단어의 표면적 형태와 빈도수 | 단어의 주변 문맥과 내포된 의미 |
| **강점 (Sweet Spot)**| 고유명사, 특수 기호, 품번, 에러코드 | 동의어, 유사 표현, 뉘앙스 파악 |
| **약점 (취약점)** | "사과" $\neq$ "Apple" (어휘 불일치 시 0점) | 희귀 단어(Rare words) 매칭 무시 현상 |
| **차원 수** | 수십만 차원 (대부분 0인 희소 벡터) | 768~1536 차원 (값이 꽉 찬 밀집 벡터) |

## Ⅳ. 핵심 알고리즘: Fusion (융합) 메커니즘
서로 점수 체계가 다른 두 결과를 공정하게 합치는 방법.
1. **RRF (Reciprocal Rank Fusion)**:
   - 점수(Score)를 무시하고 오직 '순위(Rank)'만으로 계산하여 절대적 점수 편향을 막는 업계 표준.
   - $RRF Score = \frac{1}{k + Rank_{sparse}} + \frac{1}{k + Rank_{dense}}$ (보통 $k=60$ 사용).
   - 두 검색 결과 모두에서 상위권에 포진한 문서에 강력한 가중치가 부여됨.
2. **가중치 합산 (Weighted Sum / Convex Combination)**:
   - 각 엔진의 점수를 $0 \sim 1$로 정규화(Min-Max Normalization 등)한 뒤, 도메인 특성에 맞춰 가중치($\alpha$)를 부여.
   - $Final Score = \alpha \times Score_{dense} + (1-\alpha) \times Score_{sparse}$
   - 전문 용어가 많은 문서는 BM25 비중 상향 조정.

## Ⅴ. 한계점(운영 리스크) 및 통제 가이드
- **리스크 1: 인프라 파편화 및 동기화(Sync) 이슈**:
  - BM25를 위한 RDBMS(Elasticsearch 등)와 임베딩을 위한 Vector DB(Milvus 등) 두벌의 인프라를 유지해야 함. 문서 업데이트 시 양쪽 DB를 동시에 갱신(Two-phase commit)해야 하는 트랜잭션 복잡도 발생.
  - **대응 방안**: 최근 BM25와 Vector Index를 자체적으로 동시 지원하는 통합형 벡터 데이터베이스(예: Qdrant, Pinecone 하이브리드 인덱스, Elasticsearch 8.x)를 도입하여 단일 파이프라인으로 구조 단순화.
- **리스크 2: 검색 지연 시간 (Latency Overhead)**:
  - 두 검색 엔진의 I/O 병목이 발생하고 Fusion 연산 시간이 추가됨.
  - **대응 방안**: 검색 API를 엄격히 비동기(Asynchronous) 병렬 호출로 설계하고, 검색 엔진 간의 타임아웃(Timeout)을 설정해 지연 현상 전파를 방어.

## Ⅵ. 실무 적용 및 결론
- **판단 지표**: 단독 검색 대비 nDCG@10 (랭킹 품질), Recall@50 상승분, 시스템 전체 장애/지연 시간 증분.
- **실무 설계**: 엔터프라이즈 사내 규정 Q&A 시스템. RAG 파이프라인 구축 시 "특정 법령 4조 2항"과 같은 핀포인트 쿼리가 Dense 검색에서 번번이 누락(Recall 실패)되는 현상 발생. Elasticsearch 기반의 BM25 엔진과 BGE-M3 임베딩 기반의 벡터 검색을 병렬화하는 Hybrid 파이프라인 도입. RRF(k=60)로 두 후보군 100개를 병합한 후 Cross-encoder로 Top-5를 리랭킹하여, 오검색으로 인한 환각(Hallucination) 발생률을 0%에 가깝게 억제함.
- **결론**: 하이브리드 검색은 '문맥 이해'라는 AI의 장점과 '정확도'라는 전통 IT의 장점을 결합한 실용적 타협점이며, 환각이 허용되지 않는 엔터프라이즈 환경에서 RAG를 상용화하기 위한 최소한의 방어선이자 디팩토(De Facto) 표준 설계 방식임.

### 🔀 문제 유형별 목차 전환
- **Ⅱ·Ⅲ 강조 (개념/원리형)**: Sparse/Dense 벡터가 생성되는 수학적 원리(TF-IDF와 신경망 임베딩), RRF 수식 및 점수 정규화 메커니즘 중심 서술.
- **Ⅴ·Ⅵ 강조 (실무/설계형)**: 이중 색인(Dual Indexing) 유지보수 비용과 검색 정밀도의 Trade-off 분석, SPLADE 기반 신경망 Sparse 등 최신 통합 아키텍처 진화 방향성 작성.
