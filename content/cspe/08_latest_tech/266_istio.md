# 📖 【암기용】 개념 완전 이해

> 목적: 구글이 K8s로 컨테이너 배포를 천하 통일한 뒤, '네트워크 통신'까지 통일하기 위해 만든 서비스 메시의 절대 강자 'Istio'의 구조를 이해한다.

## 한눈에
- **정의**: 마이크로서비스 간의 트래픽 라우팅, 보안(mTLS), 정책 적용, 모니터링 원격 측정(Telemetry)을 중앙에서 쉽게 제어할 수 있게 해주는 **오픈소스 서비스 메시(Service Mesh) 플랫폼**
- **필요성**: 수백 개의 사이드카 프록시(Envoy)들을 수동으로 설정하는 것은 불가능하므로, 이들에게 한 번에 정책을 쏴주고 관리할 '중앙 통제실(Control Plane)'이 필요했기 때문
- **핵심 직관**: "각 부서의 교환수(Envoy Proxy)들에게 매일 아침 '오늘의 전화 규칙'을 방송하고, 누가 누구에게 전화했는지 통화 기록(로그)을 모조리 수집하는 사내 네트워크 총괄 지휘 통제실"

## 깊이 이해
- **배경(왜 등장했나?)**: 구글, IBM, Lyft가 모였다. Lyft가 이미 'Envoy'라는 엄청나게 빠르고 훌륭한 C++ 기반 사이드카 프록시를 만들어 쓰고 있었다. 하지만 Envoy 수천 개를 관리할 두뇌가 없었다. 그래서 구글과 IBM이 "Envoy들을 조종하는 뇌(Control Plane)를 만들자"라고 합의하여 탄생시킨 것이 Istio다. (그래서 Istio의 기본 데이터 플레인은 언제나 Envoy다.)
- **작동 원리(어떻게 달성했나?)**: 
  1. Istio의 뇌인 **`istiod` (Control Plane)**가 뜬다.
  2. 개발자가 "오늘부터 결제 서비스는 V2 버전으로 트래픽 10%만 보내(Canary)"라고 쿠버네티스 YAML에 적는다.
  3. `istiod`가 이 YAML을 분석해서, 클러스터에 깔린 수많은 Envoy 프록시들에게 룰을 쫙 뿌린다(Pilot 역할).
  4. 동시에 `istiod`는 모든 Envoy들에게 서로를 믿고 암호화 통신(mTLS)을 할 수 있도록 인증서를 발급해 준다(Citadel 역할).
- **일상 비유**: 각 사거리마다 교통경찰(Envoy)이 서 있다. 이들은 도로 상황을 잘 통제하지만 전체 도시의 그림은 모른다. 시청 교통통제센터(Istio)가 무전기로 "지금 강남역 막히니까 10% 차량만 신논현으로 우회시켜"라고 지시를 내리면 모든 경찰이 동시에 그 지시를 따르는 것이다.
- **구체 예시**: Istio를 설치하면 K8s 네임스페이스에 `istio-injection=enabled` 라벨만 붙여주면 끝이다. 그러면 그 안에 뜨는 모든 Pod에는 내가 묻지도 따지지도 않아도 자동으로 Envoy 프록시 컨테이너가 찰싹 달라붙는다(Auto Injection).
- **흔한 오해/주의점**: "Istio가 데이터(트래픽)를 직접 나르나?" → 절대 아니다. Istio 본체(`istiod`)는 설정(Rule)만 전달할 뿐, 실제 트래픽 짐짝은 언제나 Envoy 프록시들끼리만 주고받는다. 그래서 Istio가 잠깐 죽어도 현재 통신은 끊기지 않는다.

## 연결 개념
- **Service Mesh**: Istio가 속한 아키텍처 패턴이자 개념 그 자체
- **Envoy Proxy**: Istio의 손발이 되어 실제 트래픽을 가로채고 전달하는 Data Plane 프록시
- **Kubernetes**: Istio가 기생하여(밀접하게 통합되어) 동작하는 모(母) 플랫폼. K8s 없는 Istio는 상상하기 힘들다.

# 📝 【답안용】 시험 답안 템플릿

## 핵심 인사이트 (3줄 요약)
> 1. **본질**: Istio는 마이크로서비스 간의 트래픽 라우팅, 로드 밸런싱, 보안(mTLS), 정책 강제 및 텔레메트리(Telemetry) 수집을 중앙에서 관리하는 Control Plane 소프트웨어이다.
> 2. **가치**: 애플리케이션 코드의 수정 없이 서비스 메시(Service Mesh)를 완벽하게 구현하며, 개발자와 인프라 운영자의 책임을 완전히 분리(Decoupling)하는 클라우드 네이티브의 핵심 인프라이다.
> 3. **판단 포인트**: 기존의 복잡했던 다중 컴포넌트(Pilot, Citadel, Galley)를 통합한 단일 바이너리 `istiod`의 최신 아키텍처를 이해하고, Ambient Mesh(Sidecarless)로 진화하는 동향을 파악해야 한다.

## Ⅰ. 개요 및 필요성
- **정의**: 분산 마이크로서비스 아키텍처 환경에서 애플리케이션을 연결, 보호, 관리, 모니터링하기 위한 개방형(Open Source) 서비스 메시 플랫폼
- **배경**: MSA로 인해 폭증하는 네트워크 홉(Hop) 간의 지연 타임아웃, 재시도, 보안 암호화 등의 공통 네트워크 요구사항을 수많은 Polyglot(다국어) 앱마다 개별 구현하는 것이 불가능해짐
- **필요성**: 투명한(Transparent) 트래픽 제어, 제로 트러스트(Zero Trust) 기반의 서비스 간 상호 인증(mTLS), 클러스터 전반의 통합된 관측성(Observability) 확보

## Ⅱ. Istio 핵심 아키텍처 구조 (istiod + Envoy)
과거에는 Control Plane이 여러 모듈로 쪼개져 있었으나, 복잡성 문제로 현재는 `istiod`라는 단일 프로세스로 통합되었다.

```text
[ Administrator (kubectl / YAML) ]
                │
┌───────────────▼─────────────────────────────────┐
│           Control Plane ( istiod )              │
│ ┌────────┐ ┌─────────┐ ┌────────┐ ┌─────────┐   │
│ │ Pilot  │ │ Citadel │ │ Galley │ │ Mixer*  │   │
│ └────────┘ └─────────┘ └────────┘ └─────────┘   │
└───────┬────────────┬────────────────┬───────────┘
        │ (라우팅)    │ (인증서 발급)  │ (메트릭 수집)
┌───────▼────────────▼────────────────▼───────────┐
│                   Data Plane                    │
│ ┌────────────────┐         ┌────────────────┐   │
│ │ [ Pod A ]      │         │ [ Pod B ]      │   │
│ │ ┌────────────┐ │ (mTLS)  │ ┌────────────┐ │   │
│ │ │ Envoy Proxy│◀┼────────▶│ │ Envoy Proxy│ │   │
│ │ └─────▲──────┘ │         │ └─────▲──────┘ │   │
│ │       │(Local) │         │       │        │   │
│ │ ┌─────▼──────┐ │         │ ┌─────▼──────┐ │   │
│ │ │   App A    │ │         │ │   App B    │ │   │
│ │ └────────────┘ │         │ └────────────┘ │   │
│ └────────────────┘         └────────────────┘   │
└─────────────────────────────────────────────────┘
```

## Ⅲ. Control Plane 주요 내부 컴포넌트 역할
1. **Pilot (트래픽 관리자)**
   - K8s의 API Server로부터 서비스 디스커버리 정보를 읽어들여, 각 Envoy가 트래픽을 어떻게 라우팅(A/B 테스트, 카나리)해야 할지 설정(Config)을 동적으로 배포함.
2. **Citadel (보안 및 인증 관리자)**
   - 클러스터 내의 자체 인증기관(CA) 역할을 수행. 각 Pod의 Envoy에게 암호화 통신용 X.509 인증서를 발급하고 주기적으로 갱신(Rotation)하여 **mTLS**를 강제함.
3. **Galley (설정 검증자)**
   - 사용자가 작성한 Istio CRD(Custom Resource Definition) YAML 파일의 문법과 유효성을 검증하고, Pilot이 이해할 수 있는 형식으로 변환함.
4. *참고: 과거의 Mixer는 성능 병목 원인으로 지목되어 아키텍처에서 삭제되고 그 기능(텔레메트리 수집)이 Envoy Proxy 자체 플러그인(Wasm 등)으로 이관됨.*

## Ⅳ. Istio의 3대 커스텀 리소스(CRD)
Istio를 제어하기 위해 개발자가 작성하는 핵심 YAML 오브젝트들이다.

1. **VirtualService (가상 서비스)**: 클라이언트로 들어온 요청을 '어디로(Which Service)' 보낼지 라우팅 룰을 정의. (예: URI가 `/v2`면 버전 2로 가라)
2. **DestinationRule (도착지 규칙)**: 트래픽이 목적지에 도착한 후 '어떻게(How)' 처리할지 정의. (예: 로드 밸런싱 방식은 Round-robin으로, 서킷 브레이커 설정 등)
3. **Gateway (게이트웨이)**: 클러스터 외부에서 내부로 들어오는 Ingress 트래픽이나, 밖으로 나가는 Egress 트래픽의 열려 있는 포트와 프로토콜(HTTP/HTTPS)을 제어.

## Ⅴ. 기술적 한계 및 최신 혁신 (Istio Ambient Mesh)
| 리스크 요인 | 현상 및 문제점 | 대응 혁신: Ambient Mesh (Sidecarless) |
|:---|:---|:---|
| **Sidecar Resource Overhead** | 수만 개의 Pod에 Envoy가 1:1로 붙으면서 전체 클러스터 CPU/메모리의 30% 이상을 인프라가 낭비함 | **사이드카 패턴 폐기**. L4(보안/라우팅) 처리를 위한 **ztunnel**을 노드(Node)당 1개만 띄우는 공유형 방식으로 진화 |
| **L7 통제 비용 (Latency)** | 단순 라우팅만 필요한데도 무거운 L7 프록시 연산을 거쳐 레이턴시 급증 | L7(HTTP) 제어가 필요한 트래픽만 별도의 **Waypoint Proxy**로 우회시켜 비용과 지연시간을 획기적으로 줄임 |

## Ⅵ. 실무 적용 및 결론
**적용 방안 및 실무 가이드:**
1. **Canary Deployment 파이프라인 자동화**: Argo Rollouts와 Istio를 결합하면, 새 버전 배포 시 1% ➔ 5% ➔ 10%로 점진적으로 트래픽을 늘리며 에러율(500 에러 등)을 분석하여 자동으로 롤백하는 완전 자동화 파이프라인 구축이 가능하다.
2. **Kiali 및 Jaeger 연동**: Istio가 쏟아내는 엄청난 텔레메트리 데이터를 시각화하기 위해 Kiali(서비스 토폴로지 맵 시각화)와 Jaeger(분산 추적 시스템)를 반드시 1세트로 구축하여 운영 가시성을 확보해야 한다.

**결론:**
- Istio는 서비스 간의 네트워크 제어를 애플리케이션 계층에서 떼어내 인프라 계층으로 완전히 내린 **클라우드 네이티브 네트워크의 완성형**이다.
- 최근 Ambient Mesh(사이드카 없는 메시) 구조로 대격변을 겪으면서, 그동안 발목을 잡았던 무거운 오버헤드라는 단점마저 극복하고 차세대 인프라 표준으로 확고히 자리 잡고 있다.
