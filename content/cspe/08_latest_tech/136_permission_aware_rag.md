# 📖 【암기용】 개념 완전 이해

> 목적: Permission-aware RAG를 처음 봐도 완벽히 이해하게 만든다.

## 한눈에
- **개요**: 사용자 권한을 검색·컨텍스트 구성·답변 생성 전 과정에 반영하는 RAG 구조
- **왜 필요한가**: RAG가 사용자가 볼 수 없는 문서를 검색해 답변하면 정보 유출이 발생함.
- **핵심 직관**: 사내 검색 챗봇도 사용자 권한에 따라 볼 수 있는 문서만 참고해야 함.

## 깊이 이해
- **배경·문제의식**: 벡터DB는 의미가 가까운 문서를 찾지만, 권한이 없는 문서인지 자동으로 알지 못한다. 사내 문서는 부서·직급·프로젝트별 접근 통제가 필요함.
- **작동 원리**: 문서 청킹 시 ACL·tenant_id·security_label을 메타데이터로 저장하고, 검색 요청 시 사용자 권한 토큰을 필터로 적용함.
- **비유**: 도서관 사서가 질문에 맞는 책을 찾기 전에, 사용자가 열람 가능한 서가인지 먼저 확인하는 방식임.
- **구체 예시**: HR 문서 RAG에서 employee_role=HR 조건을 벡터DB와 Elasticsearch 양쪽 필터에 적용해 미권한 문서 반환 0건 목표.
- **흔한 오해·주의점**: 답변 후 마스킹만으로 충분하지 않음. 검색 단계에서 미권한 컨텍스트가 LLM에 들어가지 않아야 함.

## 연결 개념
- Enterprise RAG — 기업 운영형 RAG의 상위 아키텍처
- RBAC/ABAC — 역할·속성 기반 접근제어
- Private RAG — 사내망·폐쇄망 RAG 운영 방식

# 📝 【답안용】 시험 답안 템플릿

> 목적: 시험장에서 25분에 그대로 쓰는 답안 양식.

## 핵심 인사이트 (3줄 요약)

> 1. **본질**: Permission-aware RAG는 권한 메타데이터와 사용자 ACL을 검색 단계에 적용하는 보안형 RAG임.
> 2. **가치**: LLM 컨텍스트에 미권한 문서가 유입되는 것을 차단해 정보 유출을 방지함.
> 3. **판단 포인트**: 검색 전 필터링, 메타데이터 동기화, 감사로그, 권한 회귀 테스트가 필수임.

## 출제 의도 및 답안 포인트

| 출제 의도 | 반드시 짚을 핵심 | 감점 회피 포인트 |
|:---|:---|:---|
| 검색 단계 보안 통제 이해 확인 | 사전 필터로 미권한 컨텍스트의 LLM 유입 원천 차단 | 답변 후 마스킹을 충분한 통제로 단정 |
| 권한 모델 연동 설계 역량 확인 | RBAC/ABAC, 청크별 ACL 메타데이터, 정책 엔진(OPA) | 원천 시스템 ACL과 색인 메타데이터 동기화 누락 |
| 보안 검증 체계 판단 확인 | 역할별 권한 회귀 테스트, 접근 결정 감사로그 | 검색 품질 지표와 권한 위반 지표 혼동 |

> 요약: 이 문제는 RAG 검색 흐름 설명이 아니라 권한 위반 0건을 보장하는 필터 위치와 검증 체계 판단을 묻는다.

## Ⅰ. 개요 및 필요성

- 개요: 권한 통제형 RAG 구조
- 배경: 기업 문서는 사용자별 접근 권한이 달라 RAG 검색 결과에도 원천 시스템의 ACL 정책이 적용되어야 한다.
- 필요성: pre-filtering·post-filtering·row-level security로 미권한 문서 노출 0건과 감사 로그 추적성을 확보한다.

## Ⅱ. 구조 및 구성요소

```text
User Query + Auth Token -> Policy Engine -> ACL Filter
  -> Vector/BM25 Search -> Allowed Context -> LLM Answer
```

| 구성요소 | 역할 | 특이사항 |
|:---|:---|:---|
| Auth Context | 사용자·역할·부서·프로젝트 식별 | SSO, JWT, group claims |
| Metadata ACL | 문서별 접근 정책 저장 | tenant_id, role, label |
| Policy Engine | RBAC/ABAC 조건 평가 | OPA, IAM 연동 |
| Audit Log | 검색·답변 권한 기록 | user_id, doc_id, decision |

> 요약: 권한인지 RAG는 사용자 인증 정보와 문서 ACL을 검색 필터로 결합해 허용 컨텍스트만 LLM에 전달함.

## Ⅲ. 동작원리 및 흐름도

```text
문서 수집 -> ACL 메타데이터 부여 -> 색인
사용자 질의 -> 권한 토큰 확인 -> ACL 필터 검색
  -> 허용 문서만 컨텍스트 구성 -> 답변/감사로그
```

| 단계 | 처리 내용 | 검증 기준 |
|:---:|:---|:---|
| 1 | 문서별 ACL·보안등급 메타데이터 저장 | ACL 누락률 0% |
| 2 | 사용자 인증·권한 속성 확인 | SSO 연동 실패율 <1% |
| 3 | 벡터DB·BM25 양쪽에 ACL 필터 적용 | 미권한 문서 반환 0건 |
| 4 | 검색·답변·근거 로그 저장 | 감사로그 90일 이상 |

> 요약: 문서 색인부터 사용자 질의까지 동일 권한 정책을 적용하고 모든 접근 결정을 로그로 남김.

## Ⅳ. 특징

| 구분 | 일반 RAG | Permission-aware RAG | 판단 포인트 |
|:---|:---|:---|:---|
| 검색 기준 | 의미·키워드 | 의미·키워드+권한 | 기업 RAG 필수 |
| 보안 통제 | 답변 후 필터 가능 | 검색 전 ACL 필터 | 컨텍스트 유입 차단 |
| 운영 부담 | 낮음 | ACL 동기화·테스트 필요 | 권한 변경 지연 관리 |
| 검증 | 품질 지표 | 품질+권한 위반 0건 | 보안 회귀 테스트 |

> 요약: Permission-aware RAG는 검색 품질보다 먼저 권한 위반 0건을 보장해야 하는 기업 보안 구조임.

## Ⅴ. 심화 비교 및 적용 판단

| 비교 축 | 사후 필터 (Post-filtering) | 사전 필터 (Pre-filtering) | 선택 기준 |
|:---|:---|:---|:---|
| 유출 경로 | 미권한 문서가 검색 결과·컨텍스트에 유입 가능 | 검색 시점 metadata filter로 유입 원천 차단 | 보안 요구 수준, 규제 대상 여부 |
| 결과 품질 | top-k 필터 후 잔여 결과 부족 발생 | 허용 문서 집합 내 top-k 보장 | recall 안정성 요구 |
| 구현 위치 | 애플리케이션 후처리 로직 | 벡터DB·검색엔진 필터 조건 | 검색엔진의 필터 기능 지원 여부 |

> 요약: 기업 환경은 사전 필터를 기본으로 하고, 사후 필터는 보조 방어선으로만 사용함.

| 리스크 | 원인 | 대응 방안 | 확인 지표 |
|:---|:---|:---|:---|
| 권한 변경 지연 유출 | 원천 ACL과 색인 메타데이터 동기화 지연 | 이벤트 기반 ACL 동기화, 캐시 TTL 단축 | ACL 동기화 지연 시간 |
| 필터 우회 경로 | 캐시·요약 인덱스 등 필터 미적용 경로 | 전 검색 경로 필터 강제, 경로 인벤토리 점검 | 미권한 문서 반환 0건 |
| 과도 차단 | ACL 메타데이터 오부여 | 역할별 golden query 회귀 테스트 | 정당 접근 실패율 |

> 요약: 핵심 위험은 ACL 동기화 지연과 필터 우회 경로이며, 이벤트 동기화와 회귀 테스트로 통제함.

## Ⅵ. 실무 적용 및 결론

**적용 방안 3개:**
1. 메타데이터 표준화: 모든 청크에 tenant_id, owner_group, security_label, doc_version 필수 저장
2. 이중 필터: Elasticsearch와 Vector DB 검색 양쪽에 동일 ACL 필터 적용, 후처리 필터만 사용하는 구조 금지
3. 보안 테스트: 사용자 역할별 golden query 500건으로 미권한 문서 반환 0건을 CI에서 검증

**결론 (2줄):**
- 기술사 판단: 기업 RAG는 Permission-aware 구조를 기본값으로 두고, 권한 없는 컨텍스트는 LLM에 전달하지 않음
- 향후 방향: ABAC, DLP, 정책 엔진을 결합한 Zero Trust RAG 아키텍처로 발전
