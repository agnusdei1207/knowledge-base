## 미리 알고가기

- 권한인지 RAG는 검색 단계에서 사용자 권한을 반영해 허용된 문서만 검색하는 구조임
- post-filtering보다 pre-filtering이 원칙이며 보안 사고 방지의 핵심임
- IAM과 메타데이터 동기화 품질이 실제 보안 수준을 좌우함

## Ⅰ. 개요

- **정의/개념**: 권한인지 RAG는 사용자 역할과 부서와 프로젝트 권한을 검색 쿼리에 결합해, 인가된 문서와 청크만 LLM의 문맥으로 승급시키는 보안형 RAG 아키텍처임
- **배경/필요성**: 시맨틱 검색은 의미 유사도만 보면 민감 문서도 쉽게 끌어올릴 수 있으므로, 기업 환경에서는 의미보다 보안이 먼저 반영되는 검색 구조가 필요함

## Ⅱ. 특징

- 검색 단계에서 ACL과 RBAC와 ABAC를 반영해 미인가 문서 노출을 원천 차단함
- 사용자별로 같은 질문에도 서로 다른 문맥과 답변이 반환될 수 있음
- 사후 마스킹보다 사전 필터링이 보안성과 운영 단순성 모두에서 유리함
- 권한 메타데이터가 늦게 동기화되면 보안성과 최신성이 함께 흔들릴 수 있음

## Ⅲ. 종류 및 비교

| 판단 기준 | 일반 RAG | 권한인지 RAG | Private RAG |
|:---|:---|:---|:---|
| 검색 기준 | 관련성 중심 | 관련성+권한 | 폐쇄망+권한 |
| 문서 노출 위험 | 높음 | 낮음 | 매우 낮음 |
| 운영 난도 | 중간 | 높음 | 매우 높음 |
| 대표 환경 | 공개 지식서비스 | 엔터프라이즈 검색 | 금융, 국방, 공공 |

## Ⅳ. 구성요소 및 구조

| 구성요소 | 설명 |
|:---|:---|
| ACL Metadata | 문서와 청크에 역할과 부서와 소유 범위를 메타데이터로 저장해 필터링 기준을 제공함 |
| Identity, Token Context | 로그인 토큰과 IAM 정보에서 현재 사용자 권한 속성을 추출함 |
| Permission Filtered Retriever | 벡터 검색과 키워드 검색 전에 허용된 범위만 남겨 검색 대상을 축소함 |
| Audit, Sync Layer | 권한 변경 이벤트와 검색 로그를 동기화하고 감사해 누락과 우회 시도를 추적함 |

```text
+-------------------+      +-------------------+      +-------------------+
| ACL Metadata      | ---> | Perm Filtered RT  | ---> | Safe Context      |
+-------------------+      +-------------------+      +-------------------+
             ^                        ^
             |                        |
+-------------------+      +-------------------+
| Identity / Token  |      | Audit / Sync      |
+-------------------+      +-------------------+
```

## Ⅴ. 원리 및 절차 흐름도

```text
+-------------+     +-------------+     +-------------+     +-------------+
| 권한 속성 추출   | --> | ACL 필터 적용  | --> | 허용 문서 검색 | --> | 안전 답변 생성 |
+-------------+     +-------------+     +-------------+     +-------------+
```

1. **권한 속성 추출**: 세션 토큰과 IAM에서 현재 사용자 속성을 읽음
2. **ACL 필터 적용**: 문서와 청크 메타데이터에서 허용 범위만 남김
3. **허용 문서 검색**: 남은 집합 안에서 의미 검색과 리랭킹을 수행함
4. **안전 답변 생성**: 인가된 문맥만 사용해 답변과 citation을 생성함

## Ⅵ. 문제점 및 해결 방안

1. 문제: 권한 필터가 검색 이후에 적용되면 LLM이 이미 민감 문맥을 읽어 유출 위험이 남을 수 있음
   - 해결방안: pre-filtering 구조를 고정하고 unauthorized retrieval rate와 audit issue count로 검증함
2. 문제: IAM과 문서 ACL 동기화가 늦으면 퇴사자나 이동자의 권한이 검색에 계속 반영되어 보안 공백이 생길 수 있음
   - 해결방안: CDC 기반 권한 동기화를 적용하고 permission sync lag와 stale ACL rate로 검증함
3. 문제: 세밀한 청크 단위 권한을 과도하게 적용하면 검색 recall이 낮아져 답변 품질이 불안정해질 수 있음
   - 해결방안: 문서와 청크 단위 정책을 혼합하고 authorized recall과 answer completeness로 균형을 검증함

## Ⅶ. 적용 사례

- 병원 의료 기록 RAG가 간호사와 의사 권한에 따라 다른 문맥만 검색하도록 권한인지 RAG를 적용하며 확인 지표는 unauthorized retrieval rate와 audit pass rate임
- 금융사 정책 챗봇이 부서별 규정만 조회되도록 권한인지 RAG를 운영하며 확인 지표는 permission sync lag와 hallucination rate임
- 기업 지식검색 포털이 프로젝트별 비밀 문서를 분리하도록 권한인지 RAG를 활용하며 확인 지표는 tenant isolation과 answer completeness임

## Ⅷ. 결론

권한인지 RAG는 검색 품질보다 먼저 보안 경계를 문맥 생성 단계 앞에 세우는 구조이므로, pre-filtering과 ACL 동기화와 감사 체계가 본질적 설계 포인트임.
