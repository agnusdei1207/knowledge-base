# 📖 【암기용】 개념 완전 이해

> 목적: 데이터 드리프트를 처음 봐도 모델 품질 저하 원인으로 이해하게 만든다.

## 한눈에
- **개요**: 운영 입력 데이터의 통계 분포가 학습 데이터 분포와 달라지는 현상
- **왜 필요한가**: 모델은 학습 당시 데이터 분포를 기준으로 패턴을 배웠기 때문에 입력 분포가 바뀌면 예측 오차가 증가할 수 있다.
- **핵심 직관**: 시험 범위로 공부했는데 실제 시험 문제가 다른 범위에서 나오는 상황과 같다.

## 깊이 이해
- **배경·문제의식**: 계절, 고객군, 캠페인, 센서 교체, 정책 변경은 입력 feature의 평균, 분산, 범주 비율을 바꾼다.
- **작동 원리**: 학습 데이터와 운영 데이터의 feature별 분포를 비교하고 PSI, KS-test, Jensen-Shannon divergence 같은 통계량으로 변화 정도를 수치화한다.
- **비유**: 내비게이션이 작년 도로 통행 패턴으로 학습했는데 올해 공사와 교통 정책이 바뀌면 예상 시간이 빗나가는 상황이다.
- **구체 예시**: 대출 신청자의 소득 구간 비율이 학습 시점 3천만~5천만 원 45%에서 운영 시점 25%로 감소하면 해당 feature의 PSI가 0.2를 넘을 수 있다.
- **흔한 오해·주의점**: 데이터 드리프트가 항상 모델 성능 하락을 뜻하지는 않으며, label 기반 성능 지표와 함께 해석해야 한다.

## 연결 개념
- Model Monitoring — drift와 품질 지표를 운영 대시보드에서 관측
- Concept Drift — 입력과 정답 관계 자체의 변화
- Feature Drift — 특정 feature 단위의 분포 변화

# 📝 【답안용】 시험 답안 템플릿

> 목적: 시험장에서 25분에 그대로 쓰는 답안 양식.
> 핵심: 데이터 분포 변화와 모델 성능 하락을 구분하고, 감지 지표와 재학습 기준을 연결한다.

## 핵심 인사이트 (3줄 요약)

> 1. **본질**: Data Drift는 운영 입력 데이터 분포가 학습 데이터 분포에서 벗어나는 현상임.
> 2. **가치**: PSI 0.2 초과, KS-test p-value 0.05 미만 같은 지표로 품질 하락의 선행 신호를 감지함.
> 3. **판단 포인트**: drift 크기와 실제 AUC·F1 하락을 함께 보아 재학습, 임계값 조정, 데이터 수집 개선을 결정해야 함.

## 출제 의도 및 답안 포인트

| 출제 의도 | 반드시 짚을 핵심 | 감점 회피 포인트 |
|:---|:---|:---|
| ML 품질 저하 원인 분류 확인 | 학습 분포와 운영 분포 비교, PSI·KS-test 지표 | 개념 드리프트와 혼동 |
| MLOps 대응 역량 확인 | drift detection -> 영향 평가 -> 재학습 승인 | 감지 지표만 쓰고 조치 누락 |
| 데이터 거버넌스 관점 확인 | schema, 결측률, 범주 비율, 데이터 lineage | 데이터 품질 오류와 drift를 같은 원인으로 단정 |

> 요약: 이 문제는 입력 데이터 분포 변화가 모델 운영에 미치는 영향을 수치와 대응 절차로 설명해야 한다.

---

## Ⅰ. 개요 및 필요성

- 개요: 운영 입력 분포 변화
- 배경: 고객군, 계절, 정책, 센서 변경은 학습 데이터와 다른 입력 패턴을 만든다.
- 필요성: PSI 0.2 초과 또는 주요 feature KS-test p-value 0.05 미만이면 모델 성능 재평가가 필요함.

---

## Ⅱ. 구조 및 구성요소

```text
Training Data Profile -> Baseline Distribution
Production Feature Log -> Current Distribution -> Drift Metric -> Alert / Analysis
```

| 구성요소 | 역할 | 특이사항 |
|:---|:---|:---|
| Baseline Profile | 학습 데이터 feature별 분포 저장 | 평균, 분위수, 범주 비율 |
| Current Profile | 운영 데이터 분포 계산 | sliding window 1일/7일 |
| Drift Metric | 두 분포 차이 수치화 | PSI, KS-test, JS divergence |
| Impact Analyzer | drift와 성능 하락 연결 | AUC, F1, business KPI |

> 요약: 데이터 드리프트 관리는 기준 분포와 운영 분포를 같은 feature 단위로 비교해 변화량을 계량화한다.

---

## Ⅲ. 동작원리 및 흐름도

```text
기준 분포 생성 -> 운영 로그 수집 -> 분포 비교 -> 임계값 판정 -> 영향 평가 -> 재학습 판단
```

| 단계 | 처리 내용 | 검증 기준 |
|:---:|:---|:---|
| 1 | 학습 데이터의 기준 통계 저장 | feature coverage 100% |
| 2 | 운영 데이터 window별 통계 계산 | 로그 누락 1% 이하 |
| 3 | PSI·KS-test로 분포 차이 계산 | PSI 0.1 주의, 0.2 경고 |
| 4 | 성능 지표와 업무 지표 영향 분석 | AUC 5%p 하락, 매출 KPI 변동 |

> 요약: 데이터 드리프트는 통계적 차이만으로 끝내지 않고 모델 품질과 업무 지표 영향으로 후속 조치를 결정한다.

---

## Ⅳ. 특징

| 구분 | 데이터 품질 오류 | 데이터 드리프트 | 수치 기준 |
|:---|:---|:---|:---|
| 원인 | 결측, 중복, schema 위반 | 정상 데이터의 분포 변화 | 결측률 vs PSI |
| 탐지 시점 | 수집·적재 단계 | 운영 window 비교 단계 | 1일/7일 이동분포 |
| 대응 | 파이프라인 수정 | 재학습, segment 모델, threshold 조정 | PSI 0.2 이상 경고 |

> 요약: 데이터 드리프트는 데이터가 틀린 문제가 아니라 정상 데이터의 분포가 기준과 달라진 문제다.

## Ⅴ. 심화 비교 및 적용 판단

| 비교 축 | 기존/대안 | 본 키워드 | 선택 기준 |
|:---|:---|:---|:---|
| 감지 방식 | 단순 평균 비교 | PSI, KS-test, JS divergence | 수치형·범주형 feature 혼합 여부 |
| 대응 방식 | 주기적 재학습 | 임계값 기반 재평가 | label 확보 주기와 drift 빈도 |
| 운영 범위 | 전체 데이터만 비교 | segment별 분포 비교 | 고객군·지역별 모델 편차 존재 |

> 요약: drift가 특정 segment에 집중되면 전체 평균 지표보다 segment별 PSI와 성능 지표를 우선 확인한다.

| 리스크 | 원인 | 대응 방안 | 확인 지표 |
|:---|:---|:---|:---|
| 허위 알람 | 표본 수 부족 | 최소 표본 n 1000 이상 window 적용 | alert precision 80% 이상 |
| 성능 영향 오판 | label 지연 | proxy KPI와 delayed label 결합 | label delay days |
| 원인 미분류 | feature lineage 누락 | feature store와 데이터 카탈로그 연결 | lineage coverage 100% |

> 요약: 데이터 드리프트 운영은 표본 수, label 지연, feature lineage를 통제해야 해석 오류를 줄인다.

| 점검 항목 | 목표 기준 | 측정 방법 |
|:---|:---|:---|
| 분포 변화 | 주요 feature PSI 0.2 이하 | baseline/current histogram 비교 |
| 품질 영향 | AUC·F1 5%p 이내 하락 | label 기반 batch evaluation |
| 업무 영향 | KPI 변동 10% 이내 | segment별 리포트 |

> 요약: 성공 여부는 drift 지표 단독이 아니라 모델 품질과 업무 KPI의 동시 관측으로 판단한다.

---

## Ⅵ. 실무 적용 및 결론

**적용 방안 3개:**
1. 기준선 수립: 학습 데이터 feature별 평균, 분위수, 범주 비율, 결측률을 model_version별 baseline profile로 저장함.
2. 감지 체계: 운영 데이터 1일/7일 window에 PSI 0.1 주의, 0.2 경고 기준을 적용하고 segment별 결과를 분리 표시함.
3. 대응 절차: PSI 0.2 초과 feature가 3개 이상이면 성능 재평가, 원인 분석, 재학습 후보 생성, 승인 배포 순서로 처리함.

**결론 (2줄):**
- 기술사 판단: Data Drift는 재학습의 충분조건이 아니며, 성능 하락과 업무 영향이 확인될 때 배포 조치를 실행해야 함.
- 향후 방향: drift detection은 feature store, model monitoring, automated retraining과 결합된 MLOps 품질 게이트로 발전함.
