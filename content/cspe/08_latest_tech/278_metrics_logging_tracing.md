# 📖 【암기용】 개념 완전 이해

> 목적: 관측 3요소를 처음 봐도 완벽히 이해하게 만든다. 시험 답안 양식이 아니라, 이해를 위한 친절한 설명이다.

## 한눈에
- **개요**: 시스템의 내부 상태를 파악하기 위해 수집하는 세 가지 핵심 데이터 유형 (메트릭, 로그, 트레이스)
- **왜 필요한가**: 시스템 장애는 한 가지 데이터만 봐서는 알 수 없다. 숫자로 이상을 느끼고(메트릭), 흐름으로 위치를 찾고(트레이스), 글자로 원인을 확정하는(로그) 입체적인 분석이 필요하기 때문이다.
- **핵심 직관**: 관측성(Observability)이라는 건물을 지탱하는 **세 개의 기둥(Three Pillars)**이다.

## 깊이 이해
- **배경·문제의식**: 마이크로서비스 환경에서 데이터가 너무 많아지니, 효율적으로 관리하기 위해 데이터의 성격에 따라 3가지로 분류하게 되었다. 각각의 장단점이 뚜렷하여 상호 보완적으로 사용된다.
- **작동 원리**:
    - **메트릭(Metrics)**: 특정 시간 동안의 수치(CPU, 메모리, 요청 수). 저장 용량이 적고 통계 계산이 빠르다. "문제가 생겼다!"는 신호를 준다.
    - **로그(Logging)**: 발생한 개별 이벤트의 텍스트 기록. 내용이 상세하지만 용량이 크고 검색이 느리다. "왜 생겼다!"는 이유를 알려준다.
    - **트레이스(Tracing)**: 요청의 엔드투엔드 이동 경로. 서비스 간의 관계를 보여준다. "어디서 생겼다!"는 위치를 특정한다.
- **비유**: 몸이 아플 때와 같다.
    - 메트릭: 체온계(숫자). "체온 39도, 열나네!"
    - 트레이스: 엑스레이/MRI(경로). "폐에서 염증 반응이 보이네!"
    - 로그: 정밀 혈액 검사 결과(상세 정보). "폐렴구균이 발견되었습니다."
- **구체 예시**: Prometheus(메트릭) + ELK(로그) + Jaeger(트레이스)를 조합한 통합 모니터링 시스템.
- **흔한 오해·주의점**: 셋 중 하나만 잘하면 된다고 생각할 수 있지만, 셋이 'Trace ID' 같은 식별자로 서로 연결(Correlation)되어야 진정한 효과가 난다.

## 연결 개념
- Observability (관측성) — 3요소를 통해 도달하려는 목표 상태
- Correlation ID — 3요소를 하나로 묶어주는 열쇠 (식별자)
- OpenTelemetry — 3요소를 통합 수집하기 위한 표준 프레임워크
- Cardinality — 메트릭 데이터의 복잡도를 나타내는 척도

# 📝 【답안용】 시험 답안 템플릿

> 목적: 시험장에서 25분에 그대로 쓰는 답안 양식. 작성방식(추상표현 금지·수치·도식·문제유형 전환)을 엄격히 지킨다.
> 핵심: 3요소 각각의 정의와 장단점, 그리고 이들 간의 상관관계(Correlation)를 통한 입체적 분석 관점을 서술한다.

## 핵심 인사이트 (3줄 요약)

> 1. **본질**: 관측 3요소는 분산 시스템의 가시성 확보를 위한 세 가지 핵심 데이터 원천인 메트릭(Metrics), 로깅(Logging), 분산 추적(Tracing)을 의미한다.
> 2. **가치**: 데이터의 성격(수치, 텍스트, 관계)에 따라 분석 단계를 계층화하여, 대규모 분산 환경에서의 장애 탐지 및 원인 분석 시간을 획기적으로 단축한다.
> 3. **판단 포인트**: 각 요소의 사일로(Silo)를 제거하기 위해 Trace ID 등을 매개로 한 데이터 간의 상관관계(Correlation) 확보가 관측성 체계의 성패를 결정한다.

## 출제 의도 및 답안 포인트

| 출제 의도 | 반드시 짚을 핵심 | 감점 회피 포인트 |
|:---|:---|:---|
| 관측성의 3대 핵심 요소 정의 및 차이 확인 | 메트릭(숫자), 로그(텍스트), 트레이스(관계) | 요소를 나열만 하고 차이점 기술 누락 |
| 요소별 장단점 및 상호 보완 관계 확인 | 저장 효율성, 분석 상세도, 인과 관계 파악 | 특정 요소가 만능이라고 서술 |
| 통합 관측 체계 구축 전략 확인 | Correlation (상관관계), Trace ID, 통합 대시보드 | 개별 도구 소개에만 그침 |

> 요약: 3대 데이터의 특징을 비교 분석하고, 이를 통합하여 장애를 해결하는 논리적 흐름을 기술한다.

---

## Ⅰ. 개요 및 필요성

- 정의: 시스템 내부 상태를 측정하고 이해하기 위해 수집하는 세 가지 유형의 기초 데이터(Metrics, Logging, Tracing)
- 배경: 마이크로서비스(MSA)의 복잡성 증가로 인해 단일 유형의 데이터만으로는 장애의 위치와 원인을 동시에 파악하기 불가능
- 필요성: 신속한 장애 탐지(MTTD) 및 복구(MTTR), 시스템 성능 최적화, 비즈니스 영향도 분석을 위한 입체적 데이터 체계 구축

---

## Ⅱ. 구조 및 구성요소

```text
[ Observability Pillars ]
      |
      +-- Metrics: 수치 데이터 (What: 상태 변화 감지)
      |
      +-- Tracing: 흐름 데이터 (Where: 구간/위치 특정)
      |
      +-- Logging: 텍스트 데이터 (Why: 상세 원인 확정)

* Key: Correlation (Trace ID / Context) 를 통한 데이터 연결
```

| 구성요소 | 역할 | 특이사항 |
|:---|:---|:---|
| 메트릭 (Metrics) | 시스템 리소스 및 비즈니스 지표 수치화 | 저장 효율 높음, 실시간 알람에 최적 |
| 로깅 (Logging) | 개별 이벤트에 대한 상세 기록 | 가장 상세하나 비용/검색 부하 높음 |
| 트레이스 (Tracing) | 요청 단위의 엔드투엔드 호출 경로 시각화 | 병목 구간 및 서비스 간 관계 파악 |

> 요약: 상태(Metrics) -> 위치(Tracing) -> 원인(Logging)으로 이어지는 분석 깔때기 구조를 형성한다.

---

## Ⅲ. 동작원리 및 흐름도

```text
[분석 흐름: Alert -> Trace -> Log]
1. Metrics Alert: "에러율 5% 초과!" (Prometheus)
      |
2. Distributed Tracing: "서비스 B의 DB 쿼리가 느림!" (Jaeger)
      |
3. Error Logging: "DB Connection Timeout 발생!" (ELK)
```

| 단계 | 처리 내용 | 검증 기준 |
|:---:|:---|:---|
| 1 | 이상 감지 | 메트릭 기반 임계치(Threshold) 체크를 통해 장애 상황 실시간 전파 |
| 2 | 위치 특정 | 트레이스 정보를 조회하여 전체 호출 체인 중 지연/에러가 발생한 지점 확인 |
| 3 | 원인 분석 | 특정된 구간/시간대의 상세 로그를 검색하여 코드 레벨의 오류 원인 파악 |
| 4 | 상관 관계 | Trace ID를 검색어로 활용하여 세 가지 데이터를 한 화면에 통합 분석 |

> 요약: 메트릭으로 '발견'하고, 트레이스로 '추적'하며, 로그로 '진단'하는 유기적 협력 체계다.

---

## Ⅳ. 특징

| 구분 | 메트릭 (Metrics) | 로깅 (Logging) | 트레이스 (Tracing) |
|:---|:---|:---|:---|
| 데이터 형태 | 시계열 수치 (Key-Value) | 비정형/반정형 텍스트 | 트리/그래프 구조 (Span) |
| 장점 | 경제적, 빠른 통계 분석 | 가장 상세한 컨텍스트 | 서비스 간 인과관계 가시화 |
| 단점 | 상세 원인 파악 불가 | 저장 비용 및 검색 부하 | 구현 및 운영 복잡도 |
| 핵심 도구 | Prometheus, Datadog | Elasticsearch, Splunk | Jaeger, Zipkin |

> 요약: 각 요소는 성능, 비용, 분석 깊이 측면에서 서로 다른 트레이드오프(Trade-off)를 가진다.

## Ⅴ. 심화 비교 및 적용 판단

| 비교 축 | 메트릭 중심 운영 | 로그 중심 운영 | 통합 관측 (3요소) |
|:---|:---|:---|:---|
| 장애 탐지 | 빠름 (임계치 기반) | 보통 (키워드 매칭) | 매우 빠르고 정확함 |
| 원인 분석 | 불가능 (유추만 가능) | 가능 (단편적) | 매우 용이 (입체적 분석) |
| 운영 비용 | 낮음 | 매우 높음 (용량 비례) | 적정 (샘플링 전략 적용) |

> 요약: 서비스 규모가 커질수록 3요소의 균형 있는 수집과 연결(Correlation)이 운영 효율을 결정한다.

| 리스크 | 원인 | 대응 방안 | 확인 지표 |
|:---|:---|:---|:---|
| 데이터 사일로 | 요소별 서로 다른 도구 사용 | OpenTelemetry 표준으로 수집 단일화 | 데이터 간 이동 편의성 |
| 수집 비용 폭증 | 무분별한 로그/트레이스 수집 | 샘플링 및 로그 레벨/보관 주기 최적화 | 인프라 비용 대비 관측 비용 비중 |
| 분석 피로도 | 너무 많은 지표와 알람 발생 | 핵심 지표(Golden Signals) 위주 관리 | 알람 정확도 (False Positive 비율) |

> 요약: '무엇을 버릴 것인가'에 대한 전략(샘플링, 필터링)이 관측 체계의 지속 가능성을 좌우한다.

| 점검 항목 | 목표 기준 | 측정 방법 |
|:---|:---|:---|
| MTTR (평균 복구 시간) | 도입 전 대비 50% 이상 단축 | 장애 보고서 분석 |
| 상관관계 연결률 | 트레이스에서 로그로 바로 이동 가능한 비율 95% 이상 | 관리 도구 기능 테스트 |
| 데이터 샘플링 비율 | 성능/비용 고려하여 1~10% 수준 유지 | 트래픽 대비 수집량 모니터링 |

> 요약: 지표의 수집량보다는 지표 간의 연결성과 이를 통한 복구 시간 단축 성과를 측정해야 한다.

## Ⅵ. 실무 적용 및 결론

**적용 방안 3개:**
1. 골든 시그널(Golden Signals) 정의: 레이턴시, 트래픽, 에러, 포화도 4대 지표를 메트릭의 핵심으로 관리
2. 구조화된 로깅(Structured Logging): 로그를 JSON 포맷으로 남기고 Trace ID를 필수로 포함하여 검색 효율 극대화
3. 적응형 샘플링(Adaptive Sampling): 정상 요청은 1%만, 에러 요청은 100% 추적하도록 설정하여 비용과 가시성 동시 확보

**결론 (2줄):**
- 기술사 판단: 관측 3요소는 독립된 데이터가 아니며, 이를 하나의 '맥락'으로 엮어내는 것이 진정한 클라우드 네이티브 운영 역량이다.
- 향후 방향: 최근에는 eBPF를 활용한 무중단 수집과 AI를 통한 자동 상관관계 분석(AIOps)으로 진화하고 있다.
