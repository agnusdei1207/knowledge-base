# 📖 【암기용】 개념 완전 이해

> 목적: 클라우드 네이티브 시스템의 건강을 진단하는 3가지 필수 검사 도구(메트릭, 로그, 트레이스)의 명확한 역할 분담과 그들이 어떻게 서로 시너지를 내는지 이해한다.

## 한눈에
- **정의**: 복잡한 분산 시스템(MSA)의 내부 상태를 외부에서 파악하기 위해 수집하는 3가지 핵심 원격 측정 데이터. 흔히 **관측성(Observability)의 3대 기둥(Three Pillars)**이라 부름.
- **필요성**: 장애가 발생했을 때, 알람만 울리고(메트릭) 어디서 막혔는지(트레이스) 모르거나, 어디서 막혔는지는 아는데 왜 막혔는지(로그) 모르면 문제를 해결할 수 없기 때문
- **핵심 직관**: "메트릭은 '비상벨(어, 불났다!)', 트레이스는 'CCTV(불길이 2층에서 3층으로 번지고 있네?)', 로그는 '화재 조사 보고서(누군가 2층 쓰레기통에 담배꽁초를 버렸음)'"

## 깊이 이해
- **1. Metrics (수치/통계) - "문제가 생겼음을 가장 먼저 아는 방법"**
  - **특징**: "현재 CPU 90%", "1초당 에러 50개"처럼 집계된 숫자의 연속이다. 데이터 크기가 매우 작아서 오랫동안 보관하기 좋고, 1초마다 수집해도 서버에 무리가 없다.
  - **용도**: 주로 **대시보드(Grafana)**에 그래프를 그리고, 숫자가 임계치를 넘으면 개발자에게 카톡이나 슬랙으로 **알람(Alerting)**을 보내는 데 쓴다. (도구: Prometheus)
- **2. Traces (분산 추적) - "요청이 어디서 길을 잃었는지 찾는 방법"**
  - **특징**: 단일 사용자의 요청이 A ➔ B ➔ C 서버를 거쳐 가는 전체 생명주기다.
  - **용도**: 메트릭 알람을 받고 출근한 개발자가 가장 먼저 보는 화면이다. "아, 전체 응답이 10초 걸렸는데, C 서버의 DB 쿼리에서 9초를 까먹었구나!" 하고 **병목 구간(Bottleneck)**을 1초 만에 찾게 해준다. (도구: Jaeger)
- **3. Logs (상세 텍스트) - "도대체 왜 에러가 났는지 확인하는 방법"**
  - **특징**: "2026-07-05 10:00:00 [ERROR] NullPointerException at line 45" 같은 구체적인 텍스트다. 크기가 무지막지하게 크다.
  - **용도**: 트레이스를 통해 C 서버가 문제라는 걸 알았으면, 해당 시간대의 C 서버 로그를 검색해서 **최종 원인(Root Cause)**을 파악하고 코드를 고친다. (도구: ELK 스택)
- **흔한 오해/주의점**: "로그만 다 모아놓으면 최고 아닌가?" → 옛날엔 그랬다. 하지만 MSA 환경에서는 하루에 로그가 수 테라바이트(TB)씩 쌓인다. 여기서 텍스트 검색(grep)만으로 에러를 찾는 건 모래사장에서 바늘 찾기다. 그래서 반드시 메트릭으로 알람을 받고, 트레이스로 범위를 좁힌 다음, 마지막에 로그를 까보는 순서가 지켜져야 한다.

## 연결 개념
- **Observability (관측성)**: 이 3가지 데이터를 합쳐서 시스템을 꿰뚫어 보는 능력.
- **Correlation (상관관계)**: 3대 기둥의 핵심. 로그 데이터 안에 Trace ID를 넣어두어야, 트레이스 화면에서 버튼 하나로 해당 로그로 넘어갈 수 있다. (안 묶여있으면 3개 다 무용지물이다.)

# 📝 【답안용】 시험 답안 템플릿

## 핵심 인사이트 (3줄 요약)
> 1. **본질**: 관측성(Observability)의 3대 기둥은 시스템의 거시적 건강 상태를 보여주는 메트릭(Metrics), 요청의 흐름을 보여주는 트레이싱(Tracing), 미시적 이벤트를 기록하는 로깅(Logging)으로 구성된다.
> 2. **가치**: 이 세 가지 데이터가 단일 파이프라인(예: OpenTelemetry)을 통해 상호 연관성(Correlation)을 가질 때, SRE 엔지니어는 '알람 발생 ➔ 병목 구간 식별 ➔ 근본 원인 파악'의 디버깅 파이프라인을 자동화할 수 있다.
> 3. **판단 포인트**: 각 요소의 데이터 구조적 특징(비용, 볼륨)을 비교하고, 최근 트렌드인 이벤트를 포함한 MELT(Metrics, Events, Logs, Traces) 모델로의 확장성을 제시해야 한다.

## Ⅰ. 개요 및 필요성
- **정의**: 분산 시스템의 내부 상태를 유추하고 장애를 디버깅하기 위해 필수적으로 수집해야 하는 3가지 형태의 원격 측정(Telemetry) 데이터 세트
- **배경**: 클라우드 인프라의 동적 특성(Auto-scaling, Container)으로 인해, 컨테이너가 삭제되면 내부 로그도 증발함. 또한 마이크로서비스 간의 복잡한 의존성으로 인해 기존의 단일 머신 로깅 전략이 실패함
- **필요성**: 시스템 성능 저하의 빠른 인지(MTTD 단축), 복잡한 마이크로서비스 호출 체인의 가시화, 애플리케이션의 상세 오류 원인 분석(MTTR 단축)

## Ⅱ. 관측 3요소의 상세 비교 분석 (Metrics, Traces, Logs)
| 특성 | Metrics (메트릭) | Traces (트레이스) | Logs (로그) |
|:---|:---|:---|:---|
| **데이터 형태** | 수치화된 시계열 데이터 (숫자) | 계층 구조화된 데이터 (Tree/Span) | 타임스탬프가 있는 텍스트/JSON |
| **주요 목적** | **Alerting (알람) 및 대시보드** | **Profiling 및 병목 지점 추적** | **Debugging 및 근본 원인(Root Cause) 분석** |
| **응답성/비용** | 용량이 작아 수집/쿼리 비용 매우 저렴 | 헤더 전파 비용 발생, 샘플링 필요 | **용량이 가장 커서 저장/검색 비용이 압도적으로 높음** |
| **대표 도구** | Prometheus, InfluxDB | Jaeger, Zipkin | ElasticSearch, Fluentd, Loki |
| **디버깅 순서** | 1단계 (시스템에 문제 발생 인지) | 2단계 (어느 서비스가 문제인지 범위 축소)| 3단계 (해당 서비스의 특정 코드 에러 확인) |

## Ⅲ. 3요소 간의 시너지 메커니즘 (Correlation)
이 세 가지 데이터는 독립적으로 존재할 때보다 **상관관계(Correlation)**로 묶일 때 진정한 관측성이 완성된다.

```text
 [ 알람 발생 ] ──▶  [ 병목 구간 확인 ] ──▶  [ 상세 에러 분석 ]
   (Metrics)           (Traces)               (Logs)
       │                   │                     ▲
       │                   ▼                     │
       └─────▶ 특정 시간대의 Trace ID 추출 ────────┘
               (Trace ID로 Log 필터링)
```
- **Exemplar (메트릭 ➔ 트레이스)**: 메트릭의 P99(상위 1% 지연 시간) 그래프를 클릭하면, 그 지연을 유발한 대표적인 Trace ID로 즉시 연결되게 하는 최신 기술.
- **Log Injection (트레이스 ➔ 로그)**: 로깅 프레임워크(MDC)를 설정하여 모든 로그 텍스트의 앞에 `[TraceID-1234]`를 강제 삽입. 특정 트레이스의 에러 로그만 즉시 검색 가능.

## Ⅳ. 3대 기둥의 발전 한계와 MELT 모델로의 진화
최근 관측성 진영에서는 3대 기둥만으로는 부족하다며 **Events(이벤트)**를 추가한 **MELT** 개념을 도입하고 있다.

- **Metrics**: 요약된 수치
- **Events (추가됨)**: K8s OOMKill(메모리 부족 종료), 신규 배포(Deployment), 설정 변경 등 인프라의 중대한 상태 변화를 알리는 불연속적인 사건. (장애의 가장 큰 원인은 '최근 배포'이기 때문에 이벤트 트래킹이 필수적임)
- **Logs**: 상세 텍스트 기록
- **Traces**: 요청 흐름

## Ⅴ. 기술적 한계 및 SRE 최적화 전략
| 리스크 요인 | 현상 및 문제점 | SRE 관점의 최적화 가이드 |
|:---|:---|:---|
| **저장소 비용 폭발** | 로그와 트레이스를 100% 수집하면 AWS S3 비용이 기하급수적으로 증가함 | **Tail-based Sampling**(트레이스) 적용 및 ELK 대신 S3 기반의 비용 효율적 로그 저장소(Grafana Loki 등)로 이관 |
| **개발자 계측 파편화** | 서비스마다 도구(Agent)가 달라 3가지 데이터가 하나로 엮이지 않음(Correlation 실패) | CNCF 표준인 **OpenTelemetry(OTel)**로 수집 파이프라인을 단일화하여 벤더 종속성 제거 및 ID 연동 강제화 |

## Ⅵ. 실무 적용 및 결론
**적용 방안 및 실무 가이드:**
1. **관측성 파이프라인 통합**: 개발자는 비즈니스 로직에만 집중하게 하고, K8s 노드에 Fluent Bit나 OpenTelemetry Collector를 DaemonSet으로 띄워 메트릭/로그/트레이스를 일괄 수집하는 구조를 강제한다.
2. **RED 메트릭 표준화**: 모든 서비스는 반드시 RED(Rate, Errors, Duration) 메트릭을 기본적으로 노출하도록 설계하여, SRE 팀이 단일 대시보드에서 시스템 전체의 건강을 한눈에 파악할 수 있게 한다.

**결론:**
- Metrics, Logs, Traces는 클라우드 네이티브라는 복잡한 거대 생명체의 혈압, 심전도, MRI 데이터와 같다.
- 이 세 가지 원격 측정 데이터를 OpenTelemetry로 통합하고 서로 유기적으로 연관시키는(Contextualized) 기업만이, 장애를 두려워하지 않고 하루에 수십 번씩 릴리즈(CI/CD)할 수 있는 진정한 애자일 조직으로 거듭날 수 있다.
