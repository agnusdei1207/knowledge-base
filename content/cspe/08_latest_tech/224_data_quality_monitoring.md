# 📖 【암기용】 개념 완전 이해

## 한눈에
- **정의**: 데이터가 원천(Source)에서 생성되어 데이터 웨어하우스(DW)나 머신러닝 파이프라인으로 흘러가는 전 과정에서, **"데이터에 빵꾸(결측치)가 나진 않았는지, 형식이 깨지진 않았는지, 엉뚱한 값이 들어오진 않는지"를 24시간 감시하고 불량품을 걸러내는 자동화 체계**.
- **필요성**: IT의 진리 "Garbage In, Garbage Out(쓰레기가 들어가면 쓰레기가 나온다)". 천문학적인 돈을 들여 초거대 AI와 화려한 대시보드를 만들어 놔도, 파이프라인 어딘가에서 '유저 나이: 999살', '결제금액: -5만 원' 같은 오염된 데이터가 들어가는 순간 모든 분석 결과는 개그가 됨.
- **핵심 직관**: 정수장의 '자동 수질 검사기'. 흙탕물(원천 데이터)을 퍼 와서 수돗물(분석용 데이터)로 만들 때, 파이프 중간중간에 센서를 달아둠. "탁도(스키마 형식이 맞는가?) 통과! 중금속(이상치/Null 값) 통과!" 만약 중금속 수치가 치솟으면 즉시 밸브를 잠그고(파이프라인 중단) 경고음을 울려 가비지 데이터가 우리 집(AI 모델)으로 배달되는 걸 막음.

## 깊이 이해
- **배경**: MSA 환경이 되면서 데이터 소스가 수십 개로 쪼개짐. 백엔드 개발자가 DB 컬럼명 하나 바꿨는데(예: `user_name` $\rightarrow$ `name`), 하위 데이터 엔지니어는 그걸 모르고 있다가 다음 날 1억 건의 데이터가 싹 다 에러(Null) 처리되며 데이터 레이크가 '데이터 늪(Data Swamp)'으로 변하는 참사가 빈발함. 수동 검증의 한계 도달.
- **작동 원리 (데이터 계약과 룰 엔진)**:
  1. **Rule 정의 (Data Contract)**: "고객 ID는 무조건 10자리 숫자여야 해", "가입일은 오늘보다 클 수 없어", "NULL 값은 1% 미만이어야 해" 등의 룰을 코드(YAML 등)로 미리 다 적어둠.
  2. **CI/CD 테스트**: 새 데이터가 DB에 쌓일 때마다, Great Expectations 같은 룰 엔진 툴이 저 룰을 바탕으로 데이터를 스캔함.
  3. **서킷 브레이커 (격리)**: 불량률이 5%를 넘으면 심각한 에러로 판단해, 그 데이터를 하위 마트나 ML 모델로 못 넘어가게 파이프라인을 멈춰 세움(Quarantine, 격리).
- **구체 예시**: 병원의 환자 예측 모델. 새벽 배치 작업 중 병원 EMR 시스템 연동 오류로 환자 체온 데이터가 전부 '0도'로 수집됨. 이대로 ML 모델에 들어가면 '시체'로 판단해 모델이 붕괴함. Data Quality Monitoring 시스템이 "정상 범위(35~40도) 이탈 데이터 100% 발생!"을 감지, 즉시 배치를 멈추고 데이터 엔지니어를 깨움.
- **흔한 오해/주의점**: "그냥 DB 테이블 생성할 때 `NOT NULL`, `VARCHAR(10)` 같은 제약 조건(Constraint) 걸면 되는 거 아님?" $\rightarrow$ 그것만으론 택도 없음. "어제 대비 주문량이 반 토막이 났는가?", "환불 일자가 결제 일자보다 앞서는가?" 같은 논리적, 통계적 오류는 DB 차원에서 못 잡고 반드시 외부 모니터링 엔진이 필요함.

## 연결 개념
- **DataOps**: 데이터 엔지니어링에 DevOps의 CI/CD와 테스트 자동화를 가져온 철학. Data Quality Monitoring은 이 DataOps를 실현하는 가장 핵심 무기임.
- **Data Contract (데이터 계약)**: 백엔드 개발자(데이터 생성자)와 데이터 엔지니어(소비자) 간에 "이 컬럼은 이런 형식을 유지하겠다"고 맺는 문서화/코드화된 약속.
- **Data Observability (데이터 관측성)**: 데이터 품질 룰 검사(Testing)를 포함하여, 메타데이터와 리니지(Lineage)까지 시각화해서 파이프라인의 전반적인 건강을 보는 상위 호환 개념.

# 📝 【답안용】 시험 답안 템플릿
## 핵심 인사이트 (3줄 요약)
- **본질**: 엔터프라이즈 데이터 파이프라인을 흐르는 데이터의 상태를 6대 품질 지표(정확성, 완전성, 일관성 등)와 비즈니스 룰 기반으로 24시간 실시간/배치 스캔하여 결함을 색출하는 통제 프로세스.
- **가치**: "Garbage In, Garbage Out(GIGO)" 리스크를 원천 차단하여 후속 AI 모델 예측이나 BI 대시보드 지표의 신뢰성을 보장하고, 사후에 엉망이 된 데이터를 수습하는 막대한 엔지니어링 기술 부채(Tech Debt)를 절감함.
- **판단 포인트**: 현대적인 Data Quality Monitoring의 핵심은 사람이 룰을 수동으로 입력하는 것을 넘어, 머신러닝 프로파일링(Profiling)을 통해 데이터의 통계적 베이스라인을 스스로 학습하고 이상치(Anomaly)를 잡아내는 자동화된 관측성(Data Observability) 아키텍처로 진화하는 데 있음.

## Ⅰ. 개요 및 필요성
- **정의**: 데이터 소스로부터 데이터 웨어하우스(DW)/레이크(Lake)를 거쳐 소비자(ML/BI)에게 전달되는 전 생애주기 동안 데이터의 무결성(Integrity)과 품질 메트릭을 측정, 감시, 제어하는 DataOps 기반 퀄리티 게이트웨이.
- **배경**: 마이크로서비스(MSA)와 외부 서드파티 API 연동 확대로 데이터 소스 스키마의 무단 변경(Schema Drift)이 빈발. 백엔드 배포 하나가 하위 DW 파이프라인 수백 개를 연쇄 붕괴시키는 파급 효과 발생.
- **필요성**: 데이터 신뢰 부족으로 인한 현업 부서의 의사결정 혼란 방지, 컴플라이언스(개인정보 결함 등) 리스크 조기 식별, 장애 인지 시간(MTTD)과 복구 시간(MTTR)의 획기적 단축.

## Ⅱ. 핵심 측정 지표: 데이터 품질 6대 차원 (DAMA DMBOK 기준)
무엇을 '좋은 데이터'라고 부르는가?
| 품질 지표 (Dimension) | 핵심 의미 | 실제 모니터링 체크 룰 (Assertion Rule) 예시 |
|:---:|:---|:---|
| **완전성 (Completeness)** | 필수 값이 누락되지 않았는가? | `user_email` 컬럼의 Null(결측치) 비율이 1% 미만일 것. |
| **정확성 (Accuracy)** | 현실 세계의 실제 사실과 일치하는가? | `age` 컬럼 값은 현실적인 범위인 0 ~ 120 사이일 것. |
| **일관성 (Consistency)** | 여러 시스템 간 포맷과 내용이 동일한가? | 고객 CRM DB와 결제 DB의 `고객 상태` 코드가 동일할 것. |
| **유일성 (Uniqueness)** | 레코드가 불필요하게 중복되지 않는가? | `transaction_id` 컬럼에 중복(Duplicate) 레코드가 0건일 것. |
| **유효성 (Validity)** | 사전에 약속된 데이터 도메인/포맷 준수 | `phone_number` 값이 정규식 `010-\d{4}-\d{4}` 포맷을 맞출 것. |
| **적시성 (Timeliness)** | 데이터가 필요한 시간에 제때 도착했는가? | 최신 파티션 데이터 스탬프가 현재 시점 기준 2시간 이내일 것. |

## Ⅲ. Data Quality Monitoring 아키텍처 및 파이프라인
검문소(Quality Gate)를 통과한 물만 마신다.
```text
Source DB -> [ETL Extraction] -> Quarantine Area (격리 구역) 
                                      |
                       [Data Quality Engine (ex. Great Expectations)]
                        /                     \
            (Fail: Rule 위반)               (Pass: Rule 통과)
                  /                             \
        Alert (Slack/Pager)             Data Lake / Data Warehouse
        Data Engineer 디버깅               ML Model / BI Dashboard
```
- **격리 및 검문 (Quarantine)**: 로드된 원시 데이터는 즉시 메인 DW에 합쳐지지 않고 대기(Staging) 구역에 머무름. 엔진이 YAML(또는 파이썬) 코드로 정의된 수백 개의 테스트 슈트(Test Suite)를 실행함.
- **서킷 브레이커 (Circuit Breaker)**: 치명적(Critical) 품질 룰 위반 시 파이프라인을 즉시 강제 중단시킴. 오염된 데이터가 하위로 흘러가는 것을 방벽처럼 막아냄.

## Ⅳ. 기존 방식과 DataOps 방식의 품질 관리 비교
| 구분 | 전통적 ETL 품질 관리 | DataOps 기반 자동 모니터링 |
|:---:|:---|:---|
| **테스트 시점** | 데이터가 적재된 후(Post-load) 사후 수동 검사 | **CI/CD 파이프라인 단계 (Pre-load) 자동 검증** |
| **룰 관리 주체**| DB 관리자의 머릿속 또는 워드/엑셀 명세서 | **Git 기반의 형상 관리를 통한 Data-as-Code** |
| **이상 탐지** | 하드코딩된 임계치(Threshold) | **ML 기반 과거 통계 프로파일링 (자동 이상 탐지)** |
| **장애 대응** | 현업이 대시보드 붕괴를 보고 IT에 항의 | **엔지니어가 파이프라인 알람을 받고 선제적 패치** |

## Ⅴ. 실무 적용 및 결론
- **판단 지표**: 주요 테이블(Core Entity) 대상 품질 룰 커버리지 100%, 파이프라인 장애 조기 탐지율(MTTD < 10분), 가비지 데이터 인입으로 인한 후속 장애 및 재처리 비용 단축률.
- **실무 설계**: 모빌리티 서비스 S사의 '주행 로그 데이터 신뢰도 확보' 프로젝트. 기존엔 앱 업데이트 후 위경도 좌표 체계가 몰래 바뀌어 수집되면, 며칠 뒤 요금 산정 로직이 박살 난 뒤에야 IT팀이 인지함. 조치 방안: Data Build Tool(dbt) 및 dbt-tests 연동. 1) `latitude(-90~90)`, `longitude(-180~180)` 범위 및 Null 비율 검증 룰을 dbt `.yml` 파일에 선언. 2) 매시간 동작하는 Airflow DAG에 `dbt test` 태스크를 삽입. 3) 좌표가 범위를 벗어난 이상(Anomaly) 데이터가 0.1%를 초과 감지 시, `dbt run` 태스크를 스킵(Skip)하여 DW 적재를 중단시키고, Slack으로 "GPS 스키마 위반 발생" 알람 발송. 4) 배포 팀이 프론트 앱 버그를 롤백하여 정상화.
- **결론**: 데이터의 양(Volume)보다 무서운 것은 데이터의 불확실성이다. Data Quality Monitoring은 더 이상 데이터 팀만의 뒷바라지 작업이 아니다. "테스트 코드가 없는 소프트웨어는 레거시"이듯, "품질 모니터링 게이트가 없는 데이터 파이프라인은 시한폭탄"이다. 강력한 품질 관제탑을 세울 때 비로소 기업은 '데이터를 감으로 찍어 맞추는 조직'에서 '데이터를 100% 신뢰하는 조직'으로 진화한다.

### 🔀 문제 유형별 목차 전환
- **Ⅱ·Ⅲ 강조 (개념/원리형)**: 데이터 관측성(Data Observability)의 5대 기둥(Pillars). 기존의 단순 규칙 검사(Quality)를 넘어, 머신러닝을 활용해 데이터의 신선도(Freshness), 볼륨(Volume), 스키마 변화(Schema), 데이터 분포(Distribution), 계보(Lineage)를 종합적으로 프로파일링하고 시계열로 이상 탐지하는 차세대 모니터링 프레임워크 아키텍처.
- **Ⅴ·Ⅵ 강조 (실무/설계형)**: 마이크로서비스(MSA) 환경에서의 '데이터 계약(Data Contract)' 아키텍처 설계. 백엔드 개발자(생성자)가 API 스키마를 변경할 때, CI(Continuous Integration) 파이프라인에서 데이터 계약 저장소(Schema Registry)를 조회하여 하위 데이터 팀(소비자)의 규격을 깨뜨리는(Breaking Change) 배포를 런타임 이전에 강제 차단하는 Shift-Left 거버넌스 구현 방안.
