# 📖 【암기용】 개념 완전 이해

> 목적: Data Quality Monitoring을 처음 봐도 완벽히 이해하게 만든다. 시험 답안 양식이 아니라, 이해를 위한 친절한 설명이다.

## 한눈에
- **개요**: 머신러닝이나 데이터 분석에 사용되는 데이터가 정확하고, 완전하며, 일관성 있는지 실시간으로 감시하고 관리하는 체계
- **왜 필요한가**: "쓰레기가 들어가면 쓰레기가 나온다(GIGO, Garbage In Garbage Out)"는 원칙에 따라, 아무리 좋은 모델이라도 데이터 품질이 나쁘면 분석 결과가 엉터리가 되기 때문
- **핵심 직관**: 정수장에 들어오는 원수를 상시 검사하여 오염된 물이 가정(모델)으로 들어가지 않게 하는 수질 검사 시스템

## 깊이 이해
- **배경·문제의식**: 현대 기업의 데이터는 수많은 소스(DB, 로그, 센서, 외부 API)에서 쏟아진다. 이 과정에서 데이터 누락(Null), 형식 불일치, 중복, 비현실적인 값(예: 나이 200세) 등이 수시로 발생한다. 특히 ML 모델은 데이터의 작은 결함에도 크게 왜곡된 예측을 할 수 있어, 단순한 소프트웨어 버그보다 더 찾아내기 힘든 "조용한 실패"를 야기한다.
- **작동 원리**: 데이터 파이프라인의 각 단계(수집-저장-가공)에서 사전에 정의된 품질 규칙(Data Quality Rules)을 자동으로 체크한다. 규칙에는 스키마 일치 여부, 필수 값 존재 여부, 값의 허용 범위, 통계적 분포의 안정성 등이 포함된다.
- **비유**: 공장 생산 라인 중간중간에 설치된 카메라와 센서가 부품의 치수가 맞는지, 흠집은 없는지 자동으로 선별하여 불량품이 조립 라인으로 넘어가지 않게 하는 것과 같다.
- **구체 예시**: 고객 주소 데이터가 들어올 때, 우편번호 자릿수가 맞는지, 주소 필드가 비어있지 않은지 Great Expectations 같은 도구로 자동 검증하고, 오류율이 5%를 넘으면 데이터 로딩 작업을 즉시 중단한다.
- **흔한 오해·주의점**: "데이터 품질 관리는 DB의 제약 조건(Primary Key 등)만으로 충분하다"고 생각할 수 있으나, 비즈니스 맥락에서의 논리적 결함(예: 주문 취소일이 주문일보다 빠른 경우)까지 잡아내야 진정한 품질 모니터링이다.

## 연결 개념
- Data Observability — 시스템 지표와 데이터 품질을 통합 관측하는 확장된 개념
- Data Contract — 데이터 생산자와 소비자 간의 품질 약속
- GIGO (Garbage In, Garbage Out) — 데이터 품질의 중요성을 나타내는 핵심 격언

# 📝 【답안용】 시험 답안 템플릿

> 목적: 시험장에서 25분에 그대로 쓰는 답안 양식. 작성방식(추상표현 금지·수치·도식·문제유형 전환)을 엄격히 지킨다.

## 핵심 인사이트 (3줄 요약)

> 1. **본질**: 데이터 품질 모니터링은 데이터의 6대 품질 지표(정확성·완전성·일관성·최신성·유효성·유일성)를 자동화된 규칙으로 상시 검증하는 프로세스이다.
> 2. **가치**: 데이터 오염에 의한 의사결정 오류를 방지하고, 데이터 파이프라인 장애 조치 시간(MTTR)을 단축하며 분석 신뢰도를 확보한다.
> 3. **판단 포인트**: 정적 스키마 검증을 넘어 비즈니스 로직 기반의 프로파일링과 통계적 이상 탐지(Anomaly Detection)를 결합해야 한다.

## 출제 의도 및 답안 포인트

| 출제 의도 | 반드시 짚을 핵심 | 감점 회피 포인트 |
|:---|:---|:---|
| 데이터 거버넌스 및 품질 관리 역량 확인 | 품질 6대 지표, 자동화 규칙, 데이터 프로파일링 | 단순히 "데이터 깨끗하게 관리"라고 서술 |
| 데이터 생명주기 내 품질 게이트 이해 확인 | Ingestion/Transformation 단계별 검증 기술 | 특정 DB 기능(Constraint)에만 국한하여 기술 |
| 실무적 모니터링 체계 설계 능력 확인 | SLA/SLO 설정, 실시간 알람, 장애 격리(Isolation) | "품질이 좋아짐"과 같은 추상적 효과 서술 |

> 요약: 데이터 파이프라인 전 과정에 걸쳐 품질 검증 코드(Data Testing)를 이식하고 상시 감시하는 체계 제시가 핵심이다.

---

## Ⅰ. 개요 및 필요성

- 정의: 데이터의 생성, 전송, 저장 과정에서 데이터가 사전에 정의된 비즈니스 규칙과 기술적 표준을 충족하는지 실시간으로 관측하고 제어하는 활동
- 배경: 데이터 소스의 파편화로 인한 오염 위험 증가, 수동 품질 관리의 한계로 인한 분석 신뢰도 저하 및 재작업 비용 발생
- 필요성: 신뢰할 수 있는 AI/BI 결과 보장, 데이터 사고의 조기 발견 및 확산 방지, 컴플라이언스(GDPR 등) 준수를 위한 데이터 무결성 확보

## Ⅱ. 구조 및 구성요소

```text
Data Source -> Data Collector -> Data Quality Engine (Testing) -> Quality Dashboard
                                         |                         |
                    +--------------------+-------------------------+
                    |                    |                         |
              Rule Repository      Profiling Tool            Alerting System
              (YAML/Code)          (Statistical Stats)       (Slack/Email/Pager)
```

| 구성요소 | 역할 | 특이사항 |
|:---|:---|:---|
| Rule Repository | 품질 검증 규칙(Schema, Logic) 저장 및 버전 관리 | Data-as-Code 기반 |
| Profiling Tool | 데이터 분포, 평균, 결측률 등 통계 정보 추출 | 자동 스키마 추론 |
| Testing Engine | 실시간/배치 데이터에 규칙 적용 및 통과 여부 판단 | Great Expectations, dbt 등 |
| Incident Manager | 품질 위반 시 장애 전파 및 격리(Circuit Breaker) | 데이터 파이프라인 차단 |

> 요약: 정의된 규칙(Rule)과 통계 분석(Profiling)을 기반으로 테스트를 수행하고 이상 시 즉각 대응함.

## Ⅲ. 동작원리 및 흐름도

```text
데이터 유입 -> 스키마 검증 -> 형식/타입 체크 -> 비즈니스 로직 테스트 -> 통계적 이상 탐지 -> 결과 로깅 및 리포팅 -> (실패 시) 격리/알람
      |               |               |                |                   |                   |                      |
      +---------------+---------------+----------------+-------------------+-------------------+----------------------+-----> 품질 개선 피드백
```

| 단계 | 처리 내용 | 검증 기준 |
|:---:|:---|:---|
| 1 | 기술적 품질 검증 | 컬럼명 일치, Null 허용 여부, 데이터 타입 |
| 2 | 논리적 품질 검증 | 값의 범위(Range), 참조 무결성, 날짜 순서 |
| 3 | 통계적 품질 검증 | 평소 대비 레코드 수 급증/감소, 분포 편차 |
| 4 | 품질 지표 산출 및 대응 | DQ Score 계산, Critical 실패 시 파이프라인 중단 |

> 요약: 단순 스키마 체크부터 고도화된 통계적 이상 탐지까지 다단계로 품질을 검증함.

## Ⅳ. 특징 (품질 6대 지표 중심)

| 지표 | 의미 | 점검 사례 | 판단 포인트 |
|:---|:---|:---|:---|
| 완전성 (Completeness) | 필수 항목의 누락 여부 | 고객 연락처 Null 비율 < 1% | 필수 값 존재 |
| 정확성 (Accuracy) | 실제 값과의 일치 여부 | 우편번호-주소 일치, 비현실적 수치 | 데이터의 진위 |
| 일관성 (Consistency) | 시스템 간 데이터 일치 여부 | 주문 정보와 배송 정보의 상태값 일치 | 데이터 간 정합성 |
| 최신성 (Timeliness) | 필요한 시점의 데이터 가용 여부 | 데이터 업데이트 지연 시간 < 1시간 | 데이터 적시성 |
| 유효성 (Validity) | 형식 및 도메인 규칙 준수 | 이메일 정규식 준수, 날짜 형식 | 형식의 적합성 |
| 유일성 (Uniqueness) | 데이터의 중복 존재 여부 | PK 중복 건수 0건 | 데이터 유일 식별 |

> 요약: 데이터 품질 6대 지표를 기반으로 서비스 목적에 맞는 가중치를 설정하여 관리함.

## Ⅴ. 심화 비교 및 적용 판단

| 비교 축 | 수동 품질 관리 | 자동 품질 모니터링 (DataOps) | 선택 기준 |
|:---|:---|:---|:---|
| 점검 빈도 | 필요 시 수시 (Silo 단위) | 실시간/배치 상시 감시 (End-to-End) | 데이터 가변성 정도 |
| 확장성 | 낮음 (사람의 수동 쿼리) | 높음 (자동화된 테스트 스크립트) | 데이터 소스 및 양 |
| 대응 속도 | 느림 (사후 인지 및 보고) | 빠름 (사전 탐지 및 즉각 대응) | 비즈니스 긴급도 |
| 신뢰도 | 주관적 판단에 의존 | 객관적 지표 및 대시보드 기반 | 의사결정 크리티컬도 |

> 요약: 데이터가 방대하고 실시간성이 중요해질수록 자동화된 데이터 품질 모니터링 체계가 필수적임.

| 리스크 | 원인 | 대응 방안 | 확인 지표 |
|:---|:---|:---|:---|
| Alert Fatigue | 너무 잦고 사소한 품질 알람 | 중요도 분류 및 알람 단계(Severity) 세분화 | 유효 알람률 |
| 검증 오버헤드 | 전수 조사로 인한 파이프라인 지연 | 샘플링 검증 및 핵심 지표 위주 점검 | 처리 시간 지연 최소화 |
| 규칙 관리 부재 | 비즈니스 로직 변경 미반영 | 데이터 계약(Data Contract) 정례화 | 규칙 현행화율 |

> 요약: 알람 소음은 등급화로, 부하는 샘플링으로, 규칙 노후화는 협업 체계로 해결함.

| 점검 항목 | 목표 기준 | 측정 방법 |
|:---|:---|:---|
| 데이터 무결성 | 주요 품질 규칙 통과율 99.9% | 대시보드상 DQ Score 추이 |
| 사고 탐지 신속성 | 품질 사고 발생 후 5분 내 감지 | 사고 발생~알람 시점 대조 |
| 데이터 가동률 | 품질 문제로 인한 중단 시간 최소화 | 월간 가동 시간 / 전체 시간 |

> 요약: 도입 효과는 데이터의 무결성 점수, 탐지 속도, 시스템 가동률 지표로 판정함.

## Ⅵ. 실무 적용 및 결론

**적용 방안 3개:**
1. 품질 가드레일 구축: Ingestion 단계에 Great Expectations를 도입하여 원천 데이터 스키마가 틀어질 경우 하위 DW로 오염이 확산되지 않도록 즉시 차단
2. 비즈니스 로직 검증: dbt tests를 활용하여 "취소된 주문의 결제 금액은 0원이어야 한다"는 등의 비즈니스 정합성을 배치마다 100% 자동 확인
3. 지능형 이상 탐지: 과거 데이터 유입량을 학습하여, 평소 대비 데이터 건수가 30% 이상 급증하거나 급감할 경우 상위 시스템 장애를 예측하고 선제 알람

**결론 (2줄):**
- 기술사 판단: 데이터 품질 모니터링은 "데이터의 생명 보험"과 같으며, 분석 결과에 대한 신뢰를 기술적으로 보증하는 최후의 보루임
- 향후 방향: AI가 데이터의 문맥을 이해하여 스스로 품질 규칙을 생성하고 제안하는 "Self-Healing Data Governance" 형태로 진화할 것임
