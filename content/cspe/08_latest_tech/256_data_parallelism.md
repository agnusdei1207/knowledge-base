# 📖 【암기용】 개념 완전 이해

> 목적: 데이터 병렬화를 처음 봐도 완벽히 이해하게 만든다. 시험 답안 양식이 아니라, 이해를 위한 친절한 설명이다.

## 한눈에
- **개요**: 거대한 학습 데이터를 여러 조각으로 나누어 여러 대의 GPU가 동시에 처리하게 함으로써 학습 속도를 높이는 기술
- **왜 필요한가**: 혼자서 100만 장의 사진을 공부하려면 100일이 걸리지만, 10명이 10만 장씩 나눠서 공부하면 훨씬 빨리 끝낼 수 있기 때문이다.
- **핵심 직관**: "똑같은 교과서(모델)를 여러 학생(GPU)에게 나눠주고, 각자 다른 연습문제(데이터)를 풀게 한 뒤 나중에 정답(기울기)을 맞춰보는 방식"

## 깊이 이해
- **배경·문제의식**: 딥러닝 모델 학습에는 수조 개의 토큰이 필요하다. 단일 GPU로는 학습에 수십 년이 걸릴 수 있다. 연산 자원을 수천 개로 늘려 병렬 처리해야 하는데, 가장 직관적이고 구현하기 쉬운 방법이 바로 데이터 병렬화다.
- **작동 원리**:
  1. 모든 GPU에 **동일한 모델 가중치**를 복사한다(Replication).
  2. 전체 데이터를 GPU 개수만큼 쪼개어(Sharding) 각 GPU에 전달한다.
  3. 각 GPU는 자기가 받은 데이터로 오차를 계산(Forward/Backward)한다.
  4. 계산된 오차값(Gradient)을 모든 GPU가 공유(All-Reduce)하여 평균을 낸다.
  5. 모든 GPU가 동일한 평균값으로 모델 가중치를 업데이트한다.
- **비유**: 셰프 10명이 똑같은 레시피로 요리하는데, 각자 다른 손님의 주문을 받아 요리한 뒤, 마지막에 "간이 좀 짜네?"라는 의견을 모아 모두가 레시피를 조금씩 수정하는 것과 같다.
- **구체 예시**: PyTorch의 DDP(Distributed Data Parallel)가 대표적이다. 8장의 GPU를 쓰면 이론상 1장의 GPU보다 약 8배 빠른 학습이 가능하다(통신 오버헤드 제외 시).
- **흔한 오해·주의점**: "데이터 병렬화를 쓰면 무조건 빨라진다"는 틀렸다. GPU가 너무 많아지면 서로 오차값을 공유하는 통신 시간(Communication Overhead)이 실제 계산 시간보다 길어져서 오히려 느려질 수 있다. 이를 해결하기 위해 고속 인터커넥트(NVLink)가 중요하다.

## 연결 개념
- All-Reduce — 데이터 병렬화에서 오차값을 공유하는 핵심 통신 방식
- Model Parallelism (모델 병렬화) — 모델이 너무 커서 GPU 한 대에 안 담길 때 쓰는 보완 기술
- Distributed Data Parallel (DDP) — PyTorch의 표준 데이터 병렬화 라이브러리

> 핵심: 데이터 병렬화는 모델 복제와 데이터 분할, 그리고 동기화(Sync) 과정을 중심으로 기술한다.

## 핵심 인사이트 (3줄 요약)

> 1. **본질**: 데이터 병렬화(Data Parallelism)는 전체 데이터셋을 분할하여 다수의 연산 노드에 할당하고, 동일한 모델을 병렬로 학습시킨 후 가중치를 동기화하는 기법이다.
> 2. **가치**: 구현 복잡도가 낮고 연산 효율이 높아 대규모 클러스터에서 학습 처리량(Throughput)을 선형적으로 확장하는 핵심 수단이다.
> 3. **판단 포인트**: 모델 크기가 단일 GPU 메모리 용량을 초과하는 경우에는 단독 사용이 불가능하며, 모델 병렬화(Model Parallelism)와 혼합하여 사용해야 한다.

## 출제 의도 및 답안 포인트

| 출제 의도 | 반드시 짚을 핵심 | 감점 회피 포인트 |
|:---|:---|:---|
| 분산 학습 아키텍처 이해도 | 데이터 Sharding, 모델 Replication, Gradient All-Reduce | 단순 데이터 분할로만 설명(가중치 동기화 누락) |
| 통신 효율화 및 병목 지점 파악 | 통신 오버헤드, NCCL 라이브러리, 고속 인터커넥트 활용 | GPU 개수 증가와 성능 향상을 비례관계로만 단정 |
| 현대적 구현 방식(DDP) 인지 | PyTorch DDP의 버킷(Bucket) 기반 통신 최적화 원리 | 구형 DataParallel(DP) 방식과의 차이점 누락 |

> 요약: 모델 복제 기반의 병렬 연산 구조와 통신 병목을 해결하기 위한 동기화 기법을 중심으로 답안을 구성한다.

## Ⅰ. 개요 및 필요성

- 정의: 대규모 데이터셋을 여러 조각으로 나누어 다수의 GPU 노드에서 동일한 모델로 동시 학습시키는 분산 처리 기법
- 배경: 단일 GPU 성능 한계를 초과하는 거대 데이터셋 학습 수요 증가 및 학습 기간 단축 필요성 대두
- 필요성: 학습 처리량(Throughput) 극대화를 통한 AI 개발 사이클 가속화 및 리소스 활용 최적화

---

## Ⅱ. 구조 및 구성요소

```text
[데이터 병렬화 구조도]
Full Data -> [Split/Sharding] -> Batch 1, Batch 2, Batch 3
                                     |        |        |
GPU 0 (Model Copy) <-----------------+        |        |
GPU 1 (Model Copy) <--------------------------+        |
GPU 2 (Model Copy) <-----------------------------------+
      |
[All-Reduce Sync] -> Shared Gradients -> All Models Update
```

| 구성요소 | 역할 | 특이사항 |
|:---|:---|:---|
| Master/Rank 0 | 학습 프로세스 제어 및 초기 모델 배포 | DDP에서는 특정 마스터 없이 협력 |
| Replica | 각 노드에 복제된 동일한 모델 가중치 | 메모리 점유율이 모델 크기에 비례 |
| Data Sampler | 중복 없는 데이터 분할 공급 | DistributedSampler 등을 활용 |
| All-Reduce Engine | 노드 간 기울기 동기화 및 평균 산출 | NCCL 등 고속 통신 라이브러리 사용 |

> 요약: 모든 GPU가 동일한 모델을 가진 상태에서 서로 다른 데이터를 학습하고 결과를 합산하는 구조다.

---

## Ⅲ. 동작원리 및 흐름도

```text
[학습 스텝별 동작 흐름]
Data Sharding -> Forward Pass -> Backward Pass (Local Grad) -> All-Reduce (Global Grad) -> Optimizer Step (Update)
```

| 단계 | 처리 내용 | 검증 기준 |
|:---:|:---|:---|
| 1 | 전체 배치 사이즈를 GPU 수(N)로 나눈 마이크로 배치 할당 | 각 GPU의 메모리 할당량 균형 |
| 2 | 각 GPU가 독립적으로 순전파/역전파 수행 | 연산량(FLOPs)의 균등 분포 |
| 3 | 발생한 기울기(Gradient)를 노드 간 교환 및 평균 | 통신 대역폭 활용률 및 지연 시간 |
| 4 | 산출된 평균 기울기로 로컬 모델 가중치 갱신 | 모든 GPU의 가중치 일치 여부 |

> 요약: 각자 공부하고(Backward), 답을 맞춘 뒤(All-Reduce), 모두가 똑같이 수정하는(Update) 과정을 반복한다.

## Ⅳ. 특징

| 구분 | 내용 | 판단 포인트 |
|:---|:---|:---|
| 확장성 | 노드 수 증가에 따른 선형적 성능 향상 | 통신 오버헤드 비율(전체 시간의 20% 미만 권장) |
| 메모리 | 모델 가중치가 모든 GPU에 중복 저장됨 | 모델 크기 > GPU 메모리 시 적용 불가 |
| 구현 난이도 | 표준 라이브러리(DDP)로 쉽게 구현 가능 | 코드 수정 최소화 (수 줄 이내) |

> 요약: 모델이 GPU 한 장에 들어가는 한 가장 효율적인 병렬화 방식이나, 대형 모델에서는 메모리 중복이 한계로 작용한다.

## Ⅴ. 심화 비교 및 적용 판단

| 비교 축 | Data Parallel (DP) | Distributed Data Parallel (DDP) | 선택 기준 |
|:---|:---|:---|:---|
| 구현 방식 | Single-Process, Multi-Thread | Multi-Process (노드당 프로세스) | 확장성 요구 수준 |
| 통신 효율 | 마스터 GPU 병목 발생 | 링 알리듀스(Ring All-Reduce)로 병목 제거 | GPU 수 (4개 이상은 DDP 필수) |
| 파이썬 GIL | GIL 영향으로 성능 제한 | GIL 영향 없음 | 실제 성능 가속비 (Speed-up Ratio) |

> 요약: 현대적 환경에서는 멀티 프로세스 기반의 DDP가 표준이며, DP는 단일 노드 간이 테스트용으로만 쓰인다.

| 리스크 | 원인 | 대응 방안 | 확인 지표 |
|:---|:---|:---|:---|
| 통신 병목 | GPU 간 대역폭 부족 (특히 이더넷 사용 시) | NVLink, InfiniBand 도입 및 버켓팅 튜닝 | Communication vs Computation Ratio |
| 메모리 부족 | 모델 자체가 너무 커서 복제가 불가능 | FSDP(Fully Sharded DP) 또는 ZeRO 적용 | Peak Memory Usage per GPU |
| 수렴 불안정 | 배치 사이즈 급증에 따른 학습 성능 저하 | 학습률(Learning Rate) 스케일링 기술 적용 | 최종 검증 정확도 (Accuracy/Loss) |

> 요약: 통신 병목은 고속 링크로, 메모리 한계는 파라미터 샤딩(ZeRO)으로, 학습 불안정은 하이퍼파라미터 튜닝으로 대응한다.

| 점검 항목 | 목표 기준 | 측정 방법 |
|:---|:---|:---|
| 가속 효율 | 8개 GPU 사용 시 7.2배 이상 (90%) | Scaling Efficiency (T1 / (N * TN)) |
| 통신 시간 | Step당 통신 비중 15% 이하 | PyTorch Profiler, Nsight Systems |
| 데이터 로딩 | I/O 병목에 의한 GPU 유휴 시간 0 | Data Loader Worker 수 및 캐싱 점검 |

> 요약: Scaling Efficiency와 통신 시간 비중을 통해 분산 학습의 건강도를 체크한다.

## Ⅵ. 실무 적용 및 결론

**적용 방안 3개:**
1. PyTorch DDP 도입: 단일 프로세스 기반의 구형 DP 대신 멀티 프로세스 기반의 DDP를 표준으로 채택하여 학습 성능 30% 이상 향상
2. FSDP (Fully Sharded Data Parallel) 적용: 모델 가중치, 기울기, 옵티마이저 상태를 모두 샤딩하여 데이터 병렬화의 메모리 중복 문제 해결
3. 그라디언트 축적 (Gradient Accumulation): 실제 배치 사이즈가 너무 클 경우 여러 스텝의 기울기를 모아 한 번에 동기화하여 통신 횟수 절감

**결론 (2줄):**
- 기술사 판단: 데이터 병렬화는 모든 분산 학습의 기저 기술이며, 단순 복제를 넘어 ZeRO/FSDP와 같은 샤딩 기반 데이터 병렬화로 진화하고 있다
- 향후 방향: 통신 오버헤드를 숨기기 위한 연산-통신 오버랩 기술과 압축 통신(Gradient Compression) 기술이 더욱 중요해질 전망이다
