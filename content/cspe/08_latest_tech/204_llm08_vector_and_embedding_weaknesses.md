# 📖 【암기용】 개념 완전 이해

## 한눈에
- **정의**: 최신 AI의 핵심인 RAG(검색 증강 생성) 시스템에서, 문서를 숫자로 바꾼 **'벡터(Vector)' 데이터베이스나 그 변환 과정(임베딩)을 조작하여, AI가 엉뚱한 문서를 참고하게 하거나 권한 없는 기밀문서를 읽어오게 만드는 취약점**.
- **필요성**: 기업이 챗봇에게 사내 수만 장의 PDF를 읽게 하려면(RAG), 이 문서를 수많은 숫자(임베딩 벡터)로 변환해 벡터 DB에 저장함. 이 벡터 DB의 관리가 허술하면 해커가 몰래 쓰레기 숫자(악성 문서)를 밀어 넣거나, 평사원 질문에 사장님 연봉 문서를 매칭시키는 대형 보안 사고가 터지므로 철저히 방어해야 함.
- **핵심 직관**: 도서관 청구기호 조작 사건. 학생(AI)이 질문하면, 사서(벡터 검색기)가 책의 '청구기호(벡터값)'가 비슷한 책을 쏙 빼서 줌. 악당이 몰래 도서관에 잠입해 기밀문서의 청구기호를 일반 문서와 똑같이 바꿔치기하거나, 쓰레기 정보가 담긴 책을 엄청 많이 꽂아둠. 학생은 사서가 건네주는 이상한/기밀 책들을 보고 그대로 답변해 버림.

## 깊이 이해
- **배경**: AI 서비스가 고도화되면서 단순 질의응답을 넘어 RAG(Retrieval-Augmented Generation) 아키텍처가 사실상 표준이 됨. 이에 따라 Pinecone, Milvus 같은 벡터 데이터베이스(Vector DB)가 인프라의 핵심으로 부상했는데, 전통적인 SQL DB에 비해 보안 검증(접근 통제, 입력 필터링) 체계가 성숙하지 않아 공격의 새로운 타겟이 됨.
- **작동 원리 (벡터 계층이 뚫리는 방식)**:
  1. **임베딩 오염 (Embedding/Vector Poisoning)**: 해커가 사내 위키에 악성 문서("환불은 무조건 해준다")를 올림. 이 문서가 벡터로 변환되어 DB에 저장됨. 누군가 '환불'을 물어보면, 벡터 유사도(코사인 거리)가 높아 이 악성 문서가 1순위로 검색되어 LLM의 답변 근거로 쓰임.
  2. **벡터 검색 권한 우회 (Broken ACL)**: 사장이 쓴 기밀문서도 벡터 DB에 저장됨. 벡터 검색은 "의미가 얼마나 비슷한가"만 따지고 "질문자가 이 문서를 볼 권한이 있는가"를 검사하지 않는 경우가 많음. 평사원이 교묘하게 기밀문서와 관련된 단어로 질문하면, 벡터 유사도가 높아 기밀문서가 컨텍스트로 끌려와 노출됨.
  3. **임베딩 전이 공격 (Embedding Inversion)**: 벡터 DB의 숫자(임베딩 값) 자체를 훔쳐낸 뒤, 이를 역연산(Inversion Attack)하여 원래 어떤 문장이었는지 원본 기밀을 복원해 내는 고도화된 해킹 기법.
- **구체 예시**: 인사팀 RAG 챗봇 사고. 직원이 "동료 직원의 고과 평가 점수가 궁금해"라고 묻자, 챗봇이 "검색 결과, 김철수의 평가는 C입니다"라고 답함. 벡터 DB에 인사팀의 기밀문서가 임베딩되어 있었으나 검색 시점(Retrieval)에 쿼리를 날린 사용자의 부서(ACL)를 필터링하는 로직이 빠져있어 그대로 유출됨.
- **흔한 오해/주의점**: "임베딩된 데이터는 그냥 알 수 없는 숫자 배열이니까 털려도 안전하지 않음?" $\rightarrow$ 절대 아님. 수학적 모델을 이용하면 벡터값에서 원래 단어와 문장의 맥락(원본)을 상당 수준 복원할 수 있음. 벡터 데이터도 암호화와 접근 제어가 필요한 1급 기밀 데이터임.

## 연결 개념
- **RAG (검색 증강 생성)**: 벡터 DB와 임베딩 기술이 사용되는 가장 대표적인 AI 아키텍처. 이 기술의 핵심 부품이 취약점의 무대가 됨.
- **LLM04 (데이터 오염)**: 악의적인 문서를 벡터 DB에 밀어넣는(Ingestion) 행위 자체가 데이터 오염 공격의 일환임.
- **Metadata Filtering (메타데이터 필터링)**: 벡터 검색을 할 때 숫자 유사도만 보지 않고, 문서에 꼬리표(권한, 작성자 등 메타데이터)를 달아 SQL의 WHERE 문처럼 필터링하여 보안성을 높이는 방어 기술.

# 📝 【답안용】 시험 답안 템플릿
## 핵심 인사이트 (3줄 요약)
- **본질**: RAG(Retrieval-Augmented Generation) 아키텍처를 지탱하는 벡터 데이터베이스(Vector DB)와 임베딩(Embedding) 모델 계층에서 발생하는 인증/인가 누락, 데이터 오염(Poisoning), 임베딩 역전 공격을 포괄하는 인프라 보안 취약점.
- **가치**: 대다수 기업의 AI 챗봇이 사내 기밀 문서를 벡터화하여 활용하는 상황에서, 이 계층의 보안이 뚫리면 간접 프롬프트 인젝션(Indirect Injection), 권한 우회 정보 유출(LLM02), 지식 기반 오염이 연쇄적으로 폭발하는 SPoF(단일 장애점)가 됨.
- **판단 포인트**: 벡터 유사도(Cosine Similarity)는 '의미의 근접성'을 찾을 뿐 '열람 권한'을 검사하지 않으므로, 검색 시점(Retrieval)에 사용자 IAM 권한과 문서 메타데이터를 매핑하는 벡터 필터링(Metadata ACL) 로직 및 무결성 검증 체계 구축이 필수적임.

## Ⅰ. 개요 및 필요성
- **정의**: 비정형 데이터를 다차원 벡터로 변환하는 임베딩 과정이나 저장 및 검색을 담당하는 벡터 DB(Pinecone, Milvus 등)가 부적절한 접근 제어, 무결성 훼손, 정보 유출 공격에 노출되는 아키텍처 상의 맹점.
- **배경**: LLM의 환각(Hallucination)을 줄이기 위해 외부 지식을 주입하는 RAG 모델이 대세가 되었으나, RAG의 심장부인 벡터 데이터 파이프라인(Ingestion $\rightarrow$ Embedding $\rightarrow$ Retrieval)에 대한 기존 DevSecOps 통제가 부재함.
- **필요성**: OWASP LLM08에 해당하는 이 위협은, LLM이 신뢰할 수 없는 쓰레기 데이터를 근거로 답변을 생성하게 만들거나 타인의 문서를 탈취하는 직접적 원인이 되므로, MLOps의 데이터 엔지니어링 단계에서부터 통제해야 함.

## Ⅱ. 벡터 및 임베딩 계층의 3대 취약 벡터 (Vectors)
RAG 파이프라인을 붕괴시키는 위협 요소.
| 취약 지점 | 위협 메커니즘 (Mechanism) | 피해 사례 |
|:---:|:---|:---|
| **검색 권한 누락**<br>(Broken Access Control) | 벡터 DB가 유사도 쿼리 결과 반환 시 사용자별 접근 권한(RBAC)을 검증하지 않고 Top-K 문서를 무조건 반환. | 일반 사용자가 타 부서의 재무제표나 기밀문서 기반 요약을 제공받음 (정보 노출). |
| **벡터 인덱스 오염**<br>(Index Poisoning) | 임베딩 인제스천(Ingestion) 파이프라인에 악성 문서가 삽입되어 오염된 벡터가 DB에 저장됨. | 프롬프트 인젝션 코드가 담긴 문서를 검색해 LLM이 읽고 감염됨 (간접 인젝션). |
| **임베딩 역추론**<br>(Embedding Inversion) | 해커가 탈취한 타겟 임베딩 벡터값($k$-차원 부동소수점 배열)을 수치 해석 모델에 넣어 원문을 복구해냄. | 벡터 DB만 해킹당했음에도 원본 기밀문서(텍스트)가 그대로 유출되는 효과 발생. |

## Ⅲ. 기존 RDB(관계형 DB) vs Vector DB 보안의 패러다임 비교
| 구분 | 관계형 데이터베이스 (RDB / SQL) | 벡터 데이터베이스 (Vector DB) |
|:---:|:---|:---|
| **검색 기준** | 명시적 조건 매칭 (`WHERE id=1`) | **확률적/의미론적 근접성 매칭 (Cosine Similarity)** |
| **권한 통제 (ACL)** | 테이블/로우(Row) 레벨의 세밀한 권한 제어 성숙 | **유사도 연산 자체에는 권한 개념이 없어 개발자가 구현 필요** |
| **보안 위협** | SQL Injection, DB Dump | **문서 오염(Poisoning), 임베딩 역전(Inversion) 공격** |
| **방어 메커니즘** | Parameterized Query, DB 암호화 | **메타데이터 기반 하이브리드 필터링, RAG RBAC** |

## Ⅳ. LLM08 방어 아키텍처 (Secure RAG Pipeline)
벡터 공간의 지식 무결성과 기밀성 보호.
1. **메타데이터 필터링 및 RAG RBAC (Metadata-based ACL)**:
   - 문서를 청킹(Chunking)하고 벡터로 저장할 때, 단순 숫자만 넣지 말고 문서의 '보안 등급(Level)', '작성 부서(Dept)'를 메타데이터(Metadata) 딕셔너리로 함께 저장함.
   - 검색(Retrieval) 시, 쿼리를 날린 사용자의 세션 정보(IAM)와 메타데이터가 일치(Match)하는 벡터들 풀(Pool) 내에서만 코사인 유사도 검색을 수행하도록 하이브리드 검색 강제.
2. **인제스천 파이프라인 무결성 확보 (Data Sanitization)**:
   - 문서를 벡터 DB에 넣기 전, 문서 내에 숨겨진 프롬프트 인젝션 코드나 비정상적 형식(HTML 태그 등)을 스크러빙(Scrubbing)하는 전처리 게이트웨이 구축. 인가된 사용자만 DB를 업데이트할 수 있도록 IAM 통제.
3. **임베딩 암호화 및 역전 방어 (Encryption at Rest)**:
   - 벡터 DB에 저장되는 임베딩 데이터는 스토리지 레벨 암호화(KMS)를 적용하고, 인터넷망에 DB 포트를 직접 노출하지 않는 프라이빗 서브넷 격리(Network Isolation).

## Ⅴ. 실무 적용 및 결론
- **판단 지표**: 벡터 DB 내 전체 도큐먼트 대비 메타데이터(권한 식별자) 태깅 비율, 인가되지 않은 권한으로 우회 검색 시 벡터 DB의 차단율, 문서 인제스천(입력) 시 악성코드 스캐닝 및 서명 검증 수행률.
- **실무 설계**: IT 플랫폼 E사의 사내 통합 지식 검색 RAG 챗봇 구축. Milvus 벡터 DB 사용. 모의 해킹 결과, 개발팀 인턴이 챗봇에게 "임원진 연봉 협상 가이드"와 의미상 유사한 문장("핵심 인사 평가 보상 기준")을 지속해서 질의하자, 벡터 유사도 연산에 의해 인사팀 기밀문서 청크가 LLM 컨텍스트로 빨려 들어가 요약 노출되는 결함 식별. 조치 방안: 1) 데이터 엔지니어링 개선: 모든 벡터 삽입 시 `{"allowed_roles": ["HR", "Executive"]}` 메타데이터 필수화. 2) API 게이트웨이 개선: 인턴의 API 호출 시 벡터 쿼리 파라미터에 `filter: "Intern" in allowed_roles`를 강제로 추가(Pre-filtering)하여, 임원 문서는 유사도 계산 대상에서 아예 배제되도록 수정. 정보 유출 100% 차단.
- **결론**: RAG 아키텍처의 도입으로 벡터 DB는 기업의 모든 기밀이 모이는 새로운 "단일 실패 지점(SPoF)"이 되었다. 수많은 소수점 배열 뒤에 숨겨진 데이터의 본질을 망각하면 안 된다. "의미의 유사성이 곧 접근의 허가를 의미하지 않는다"는 대원칙 아래, 벡터 검색 메커니즘 설계 시 인프라스트럭처 레벨의 엄격한 역할 기반 접근 통제(RBAC) 체계가 반드시 선행되어야 한다.

### 🔀 문제 유형별 목차 전환
- **Ⅱ·Ⅲ 강조 (개념/원리형)**: 임베딩 역전 공격(Embedding Inversion Attack)의 기술적 원리. 공격자가 다층 퍼셉트론(MLP) 등을 훈련하여 768차원의 벡터값에서 텍스트의 구문 구조와 민감 정보를 점진적으로 복원해 내는 수치해석적 위협 모델 분석.
- **Ⅴ·Ⅵ 강조 (실무/설계형)**: 거대 RAG 시스템을 안전하게 운영하기 위해, LangChain이나 LlamaIndex 프레임워크 상에서 **사전 필터링(Pre-filtering)**과 **사후 검증(Post-retrieval reranking)**을 혼합하여 속도와 보안(접근 제어)을 동시에 잡는 하이브리드 RAG 데이터 파이프라인 설계 방안.
