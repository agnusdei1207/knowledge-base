# 📖 【암기용】 개념 완전 이해

> 목적: Chunking을 처음 봐도 완벽히 이해하게 만든다.

## 한눈에
- **개요**: 긴 문서를 RAG 검색과 LLM 입력에 적합한 작은 단위로 나누는 전처리 기법
- **왜 필요한가**: 문서 전체를 한 번에 임베딩하면 핵심 근거가 희석되고, LLM 컨텍스트 비용도 증가함.
- **핵심 직관**: 두꺼운 책을 검색 가능한 쪽지 묶음으로 잘라 필요한 쪽지만 찾아 쓰는 방식임.

## 깊이 이해
- **배경·문제의식**: PDF·위키·규정 문서는 수천~수만 토큰으로 길다. 너무 큰 청크는 검색 정확도를 낮추고, 너무 작은 청크는 문맥을 잃는다.
- **작동 원리**: 문단·제목·토큰 수 기준으로 256~512토큰 단위로 분할하고, 인접 청크 간 10~20% overlap을 둬 문맥 단절을 줄임.
- **비유**: 교재를 장 전체가 아니라 핵심 문단 단위 카드로 만들어, 질문과 관련된 카드만 꺼내는 방식임.
- **구체 예시**: 512토큰 청크와 64토큰 overlap을 적용하면 규정 문서 RAG에서 Recall@10 82%->91%, 입력 토큰은 원문 대비 85% 절감.
- **흔한 오해·주의점**: 청크 크기 하나로 모든 문서를 처리하면 표·코드·조항 구조가 깨질 수 있음. 문서 유형별 전략이 필요함.

## 연결 개념
- Semantic Chunking — 의미 경계 기준으로 청크를 나누는 고도화 방식
- Embedding — 청크를 벡터로 변환하는 단계
- RAG — 검색 대상의 기본 단위로 청크를 사용

# 📝 【답안용】 시험 답안 템플릿

> 목적: 시험장에서 25분에 그대로 쓰는 답안 양식.

## 핵심 인사이트 (3줄 요약)

> 1. **본질**: Chunking은 긴 문서를 검색 가능한 근거 단위로 분할하는 RAG 전처리임.
> 2. **가치**: 512토큰+overlap 10~20% 적용 시 Recall@10 82%->91%, 입력 토큰 85% 절감 가능.
> 3. **판단 포인트**: 청크 크기, overlap, 문서 구조 보존이 검색 품질과 비용을 좌우함.

## 출제 의도 및 답안 포인트

| 출제 의도 | 반드시 짚을 핵심 | 감점 회피 포인트 |
|:---|:---|:---|
| 검색 단위 설계 이해 확인 | 256~512토큰 분할, overlap 10~20%, 크기-문맥 트레이드오프 | 단일 청크 크기를 만능 정답으로 단정 |
| 문서 구조 보존 인식 확인 | 표·코드·조항 구조와 문서 유형별 분할 전략 | 문서 유형 구분 없는 일괄 분할 서술 |
| 품질-비용 판단 확인 | Recall@10 82%->91%, 입력 토큰 85% 절감 근거 | 청크 크기와 Top-K의 상호 영향 누락 |

> 요약: 이 문제는 분할 방법 나열이 아니라 문서 유형별 크기·overlap·구조 보존의 설계 판단을 묻는다.

## Ⅰ. 개요 및 필요성

- 개요: 문서 검색 단위 분할 전처리 기법
- 배경: 긴 문서를 그대로 임베딩하면 여러 주제가 한 벡터에 섞여 검색 근거가 희석되고 LLM 컨텍스트 비용이 증가함.
- 필요성: 256~512토큰 chunk, 10~20% overlap, metadata/ACL 부여로 검색 품질과 인용 단위·입력 토큰 비용을 관리해야 함.

## Ⅱ. 구조 및 구성요소

```text
Raw Document -> Parser -> Splitter -> Overlap Handler
  -> Metadata Attach -> Embedding -> Vector DB
```

| 구성요소 | 역할 | 특이사항 |
|:---|:---|:---|
| Parser | PDF·HTML·Markdown 구조 추출 | 제목·표·코드 블록 보존 |
| Splitter | 토큰·문단·제목 기준 분할 | 256~512토큰 권장 |
| Overlap Handler | 인접 청크 문맥 연결 | 10~20% overlap |
| Metadata Attach | 출처·페이지·권한 부여 | source_id, page, ACL |

> 요약: Chunking은 원문 구조를 파싱하고 적정 크기로 나눈 뒤 출처·권한 메타데이터와 함께 색인함.

## Ⅲ. 동작원리 및 흐름도

```text
문서 입력 -> 구조 파싱 -> 토큰 수 계산
  -> 청크 분할 -> overlap 부여 -> 메타데이터 연결 -> 임베딩
```

| 단계 | 처리 내용 | 검증 기준 |
|:---:|:---|:---|
| 1 | 문서 구조 파싱 및 텍스트 추출 | 파싱 실패율 <1% |
| 2 | 256~512토큰 기준 청크 분할 | 평균 청크 길이 편차 ±20% |
| 3 | 10~20% overlap으로 문맥 연결 | 문장 절단률 <5% |
| 4 | 출처·권한 메타데이터 부여 후 임베딩 | source 매핑 성공률 100% |

> 요약: 문서 구조를 보존하면서 일정 토큰 단위로 분할하고 overlap과 메타데이터로 검색·출처 추적성을 확보함.

## Ⅳ. 특징

| 구분 | 큰 청크 | 작은 청크 | 판단 포인트 |
|:---|:---|:---|:---|
| 검색 정밀도 | 관련 없는 내용 혼입 | 근거 문장 집중 | FAQ는 256~384토큰 |
| 문맥 보존 | 문맥 충분 | 문맥 단절 위험 | 규정·계약은 512~1,024토큰 |
| 비용 | 입력 토큰 증가 | 검색 후보 증가 | Top-K와 함께 조정 |
| 운영 리스크 | 답변 산만 | 근거 부족 | overlap과 parent 문서 보완 |

> 요약: 청크 크기는 정밀도와 문맥 보존의 트레이드오프이며, 문서 유형별로 다르게 설정해야 함.

## Ⅴ. 심화 비교 및 적용 판단

| 비교 축 | 고정 토큰 분할 | 의미·구조 기반 분할(Semantic/계층형) | 선택 기준 |
|:---|:---|:---|:---|
| 구현 난이도 | 토큰 수 규칙만으로 즉시 적용 | 의미 경계 탐지·구조 파서 개발 필요 | 신속 구축·균질 문서면 고정 분할 |
| 경계 품질 | 문장·조항 중간 절단 발생 | 제목·의미 경계 보존으로 절단 감소 | 규정·계약 등 구조 문서면 의미·구조 기반 |
| 전처리 비용 | 저비용, 색인 속도 빠름 | 경계 탐지용 임베딩 연산 추가 | 재색인 빈도 높으면 비용 검토 후 결정 |

> 요약: 균질한 단문 코퍼스는 고정 분할, 조항·표가 많은 구조 문서는 의미·구조 기반 분할을 선택함.

| 리스크 | 원인 | 대응 방안 | 확인 지표 |
|:---|:---|:---|:---|
| 문맥 단절 | overlap 부족, 경계 절단 | overlap 10~20%, parent-child 청크 병행 | 문장 절단률, Recall@10 |
| 표·코드 구조 파손 | 평문화 파싱으로 구조 손실 | 구조 인식 파서, 표 단위 분리 색인 | 파싱 실패율, 표 질의 정답률 |
| 출처 추적 실패 | 청크 메타데이터 누락 | source_id·page·heading path 필수 부여 | source 매핑 성공률 100% |

> 요약: 주요 위험은 경계 절단과 구조 손실이며, overlap·구조 파서·메타데이터 표준으로 통제함.

## Ⅵ. 실무 적용 및 결론

**적용 방안 3개:**
1. 사내 위키: Markdown 제목 계층 기준 512토큰 분할, 64토큰 overlap, heading path 메타데이터 저장
2. 규정 문서: 조항 단위 우선 분할, 조항이 1,024토큰 초과 시 하위 항 단위 재분할
3. 품질 평가: chunk size 256/512/1,024 A/B 테스트, Recall@10·faithfulness·입력 토큰 비용 비교

**결론 (2줄):**
- 기술사 판단: 단문 FAQ는 작은 청크, 규정·계약은 구조 보존 청크와 overlap 적용
- 향후 방향: 고정 토큰 분할에서 의미 경계·계층형 parent-child chunking으로 발전
