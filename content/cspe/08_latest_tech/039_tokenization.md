# 📖 【암기용】 개념 완전 이해

> 목적: 토큰화를 처음 봐도 완벽히 이해하게 만든다.

## 한눈에
- **개요**: 자연어 텍스트를 모델이 처리할 수 있는 토큰 ID 시퀀스로 변환하는 전처리
- **왜 필요한가**: 신경망은 문자열을 직접 계산하지 못하므로, 단어·부분단어·문자를 숫자 ID로 바꿔야 함.
- **핵심 직관**: 긴 문장을 레고 블록처럼 잘라 번호표를 붙이고, 모델은 번호표 배열을 입력으로 받음.

## 깊이 이해
- **배경·문제의식**: 단어 단위 토큰화는 미등록어(OOV)에 취약하고, 문자 단위는 시퀀스가 길어짐. BPE·WordPiece·SentencePiece는 빈도 높은 부분문자열을 토큰으로 묶어 균형점을 찾음.
- **작동 원리**: 학습 말뭉치에서 빈번한 문자쌍을 병합해 Vocabulary를 만들고, 입력 텍스트를 해당 Vocabulary의 토큰 ID로 변환함. LLM은 이 ID를 임베딩 테이블에서 벡터로 조회함.
- **비유**: 사전을 만들 때 자주 나오는 "정보", "처리", "tion" 조각을 미리 등록해 낱글자보다 짧고 단어보다 유연하게 표현하는 방식임.
- **구체 예시**: "unbelievable"은 `un`, `believ`, `able`처럼 부분단어로 분해될 수 있으며, 어휘 크기는 32K~128K 범위가 일반적임.
- **흔한 오해·주의점**: 토큰 수는 글자 수와 다름. 한글·코드·특수문자는 모델별 토크나이저에 따라 비용과 컨텍스트 점유율이 달라짐.

## 연결 개념
- Embedding — 토큰 ID를 벡터로 변환
- Context Window — 입력 가능한 최대 토큰 수
- BPE/SentencePiece — 대표 토큰화 알고리즘

# 📝 【답안용】 시험 답안 템플릿

> 목적: 시험장에서 25분에 그대로 쓰는 답안 양식.

## 핵심 인사이트 (3줄 요약)

> 1. **본질**: 토큰화는 텍스트를 Vocabulary 기반 토큰 ID로 변환해 LLM 입력 단위로 만드는 과정임.
> 2. **가치**: OOV 문제와 시퀀스 길이 증가를 부분단어 방식으로 절충하여 학습·추론 비용을 통제함.
> 3. **판단 포인트**: 어휘 크기, 언어별 토큰 효율, 특수 토큰, 컨텍스트 비용을 함께 검토해야 함.

## 출제 의도 및 답안 포인트

| 출제 의도 | 반드시 짚을 핵심 | 감점 회피 포인트 |
|:---|:---|:---|
| 토큰화 알고리즘 원리와 비교 확인 | BPE 문자쌍 병합, WordPiece 가능도 기반, SentencePiece Unigram 모델 | 알고리즘 나열만 하고 병합 기준 차이 미설명 |
| 실무 비용·운영 판단력 확인 | 어휘 크기 32K~128K 선정 근거, 한글 tokens/char 비교, API 과금=토큰 수 | 언어별 토큰 효율 차이 미언급, OOV 대응 누락 |

> 요약: 토큰화 알고리즘 원리 차이와 어휘 크기·언어별 비용 설계 판단력을 동시에 평가하는 문제임.

---

## Ⅰ. 개요 및 필요성

- 정의: 텍스트를 Vocabulary 기반 토큰 ID로 변환하는 LLM 입력 전처리
- 배경: LLM은 문자열을 직접 연산하지 못하므로 부분단어 ID로 변환 필요
- 필요성: BPE·WordPiece·SentencePiece로 OOV를 해소하고, 어휘 크기 32K~128K 범위에서 토큰 효율과 임베딩 비용을 균형

---

## Ⅱ. 구조 및 구성요소

```text
Raw Text → Normalizer → Pre-tokenizer → Subword Tokenizer
    → Token IDs → Embedding Lookup → Model Input
```

| 구성요소 | 역할 | 특이사항 |
|:---|:---|:---|
| Normalizer | 대소문자·공백·Unicode 정규화 | NFC/NFKC 정책 |
| Vocabulary | 토큰 문자열과 ID 매핑 | 32K~128K 규모 |
| Subword Algorithm | BPE·WordPiece·SentencePiece 분할 | OOV 완화 |
| Special Token | BOS/EOS/PAD/UNK 등 제어 | 채팅 템플릿 포함 |

> 요약: 토큰화는 정규화→부분단어 분할→ID 변환→임베딩 조회의 입력 파이프라인을 구성함.

---

## Ⅲ. 동작원리 및 흐름도

```text
학습 코퍼스 → 빈도 기반 병합(BPE) → Vocabulary 생성
    → 입력 문장 분할 → Token ID 변환 → 임베딩 조회
```

| 단계 | 처리 내용 | 검증 기준 |
|:---:|:---|:---|
| 1 | 코퍼스 정규화·빈도 집계 | Unicode 정책, 언어 커버리지 |
| 2 | 문자쌍 병합 또는 Unigram 학습 | Vocabulary 32K/50K/128K |
| 3 | 입력 텍스트를 토큰 ID로 변환 | OOV율, tokens/char |
| 4 | 특수 토큰 삽입 후 모델 입력 | BOS/EOS, max token 초과 여부 |

> 요약: 토크나이저는 말뭉치 통계로 Vocabulary를 만들고, 입력을 토큰 ID 시퀀스로 변환해 모델 계산 단위로 제공함.

---

## Ⅳ. 특징

| 구분 | 단어 단위 | 부분단어 토큰화 | 수치·판단 포인트 |
|:---|:---|:---|:---|
| OOV 대응 | 미등록어 취약 | 미등록어를 조각으로 표현 | UNK율 0% 근접 |
| 시퀀스 길이 | 짧으나 어휘 폭증 | 중간 수준 | 한글 tokens/char 모델별 차이 |
| 어휘 크기 | 수백K 이상 | 32K~128K | 임베딩 파라미터 비용 |
| 운영 영향 | 언어별 편차 큼 | 다국어 대응 가능 | API 과금=토큰 수 |

> 요약: 부분단어 토큰화는 OOV와 시퀀스 길이의 균형점이며, 실제 비용은 언어별 토큰 효율에 좌우됨.

---

## Ⅴ. 심화 비교 및 적용 판단

| 비교 축 | 단어 단위 토큰화 | 부분단어 토큰화(BPE/SentencePiece) | 선택 기준 |
|:---|:---|:---|:---|
| OOV 대응 | 미등록어 UNK 처리 | 부분문자열로 분해, UNK율 0% 근접 | 전문 용어·신조어 빈도 |
| 어휘 크기 | 수백K 이상, 임베딩 파라미터 비용 증가 | 32K~128K 범위 | 모델 파라미터 예산 |
| 언어 효율 | 영어 중심, 한글·코드 비효율 | 다국어 대응 가능, 언어별 tokens/char 차이 | 한글 tokens/char 2~3x 증가 시 비용 산정 |

> 요약: 부분단어 방식은 OOV와 어휘 크기의 균형점이며, 언어별 토큰 효율 차이가 운영 비용을 좌우함.

| 리스크 | 원인 | 대응 방안 | 확인 지표 |
|:---|:---|:---|:---|
| 한글 토큰 비효율 | 영어 중심 Vocabulary 학습 | 한국어 코퍼스 포함 토크나이저 재학습 또는 모델 선택 시 tokens/char 비교 | 한글 tokens/char 비율 |
| 도메인 용어 분절 | 전문 약어가 낱글자로 분해 | 도메인 코퍼스 추가 학습, 용어 사전 기반 전처리 | 도메인 문서 토큰 수 변화율 |
| 컨텍스트 초과 | 특수 토큰·템플릿이 윈도우를 예상 이상 점유 | system/user/assistant 토큰 포함 예산표 적용 | 실제 입력 토큰 수 vs 예산 |

> 요약: 언어·도메인·특수 토큰에 의한 토큰 비용 증가를 사전 측정과 예산표로 통제함.

| 점검 항목 | 목표 기준 | 측정 방법 |
|:---|:---|:---|
| OOV율 | UNK 0%~0.1% | 도메인 테스트 문서 토큰화 후 UNK 비율 |
| 토큰 효율 | 한글 tokens/char 1.5 이하(목표) | 후보 모델별 동일 문서 토큰 수 비교 |
| API 비용 | 월 예산 대비 토큰 비용 10% 이내 | tokens/request × 요청수 × 단가 |

> 요약: OOV율·토큰 효율·월 비용을 정량 측정해 토크나이저와 모델을 선택함.

---

## Ⅵ. 실무 적용 및 결론

**적용 방안 3개:**
1. 한국어·코드 업무는 후보 모델별 `tokens/char`, `tokens/request`를 측정해 월 API 비용 산정
2. 사내 특수 용어가 많으면 도메인 코퍼스로 토크나이저 추가 학습 또는 용어 사전 전처리 적용
3. 채팅 모델은 system/user/assistant 특수 토큰과 템플릿 삽입으로 실제 컨텍스트 사용량을 계산

**결론 (2줄):**
- 기술사 판단: 일반 업무는 범용 BPE/SentencePiece, 전문 약어·코드 도메인은 토큰 효율 측정 후 모델 선택함.
- 향후 방향: 멀티모달 모델은 텍스트 토큰과 이미지·오디오 토큰을 통합 Vocabulary 또는 별도 Encoder로 처리함.
