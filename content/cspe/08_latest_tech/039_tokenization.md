## 미리 알고가기

- Token은 모델이 한 번에 처리하는 최소 언어 단위로 단어, 서브워드, 기호 조각일 수 있음
- Vocabulary는 토큰과 정수 ID를 매핑한 사전으로 크기가 비용과 표현력을 함께 좌우함
- BPE, WordPiece, SentencePiece는 최신 LLM에서 널리 쓰이는 서브워드 기반 토큰화 방식임

## Ⅰ. 개요

- **정의/개념**: Tokenization은 원문 텍스트를 모델이 처리할 수 있는 토큰 시퀀스로 분해하고 이를 정수 ID로 변환하는 입력 전처리이자 출력 복원 인터페이스임
- **배경/필요성**: 모델은 문자를 그대로 이해하지 못하므로, 다국어 문장과 코드와 기호를 일관된 단위로 분절해 비용과 표현력과 OOV 대응력을 동시에 확보하는 토큰화 계층이 필요함

## Ⅱ. 특징

- 모델 입출력의 가장 앞단에서 비용과 latency와 context 사용량을 직접 결정함
- 서브워드 기반 방식은 미등록 단어를 쪼개 처리해 OOV 문제를 완화함
- 언어별 토큰 길이 차이가 커서 동일 글자 수라도 과금과 처리 효율이 달라질 수 있음
- RAG 청킹, context budget, JSON 출력 안정성까지 후속 파이프라인 전반에 영향을 미침

## Ⅲ. 종류 및 비교

| 판단 기준 | Word-level | Character-level | Subword-level |
|:---|:---|:---|:---|
| 사전 크기 | 큼 | 작음 | 중간 |
| OOV 대응 | 취약함 | 강함 | 강함 |
| 시퀀스 길이 | 짧음 | 매우 김 | 균형적임 |
| 대표 활용 | 초기 NLP | 특수 문자 중심 작업 | 최신 LLM 표준 |

## Ⅳ. 구성요소 및 구조

| 구성요소 | 설명 |
|:---|:---|
| Normalizer | 대소문자, 공백, 유니코드 형태를 정리해 동일 표현이 같은 토큰으로 분해되도록 맞춤 |
| Pre-tokenizer | 공백, 구두점, 숫자, 코드 기호를 기준으로 1차 분절해 서브워드 병합의 입력 단위를 만듦 |
| Vocabulary, Merge Rule | 자주 등장하는 조각을 토큰으로 채택하고 병합 규칙을 저장해 압축률과 일반화 성능을 좌우함 |
| Encoder, Decoder | 원문을 토큰 ID 시퀀스로 바꾸고 생성된 ID를 다시 사람이 읽는 문자열로 복원함 |

## Ⅴ. 원리 및 절차 흐름도

```text
+-----------+     +-------------+     +---------------+     +-----------+
| 정규화    | --> | 1차 분절    | --> | 서브워드 병합 | --> | ID 매핑   |
+-----------+     +-------------+     +---------------+     +-----------+
```

1. **정규화**: 공백과 대소문자와 유니코드 형태를 정리해 입력 편차를 줄임
2. **1차 분절**: 문장을 공백, 구두점, 숫자, 기호 기준으로 대략적인 조각으로 나눔
3. **서브워드 병합**: 학습된 규칙에 따라 자주 함께 등장하는 조각을 토큰으로 합침
4. **ID 매핑**: 최종 토큰을 vocabulary ID로 치환해 모델 입력으로 전달하고 출력 시 역변환함

## Ⅵ. 문제점 및 해결 방안

1. 문제: 한국어와 코드처럼 분절이 복잡한 입력은 토큰 수가 과도하게 늘어나 context 낭비와 비용 증가를 유발함
   - 해결방안: 언어와 도메인에 맞는 tokenizer를 선택하고 문자당 토큰 수와 API 비용으로 효율을 검증함
2. 문제: 토큰 경계를 무시한 청킹은 문서 의미를 중간에서 잘라 RAG 검색 품질과 답변 근거성을 떨어뜨림
   - 해결방안: token-aware chunking과 semantic chunking을 병행하고 context recall과 faithfulness로 품질을 검증함
3. 문제: 신규 도메인 용어가 지나치게 잘게 쪼개지면 의미 표현이 불안정해져 검색과 추론 성능이 저하될 수 있음
   - 해결방안: 도메인 말뭉치 기반 vocabulary 평가나 tokenizer 교체를 검토하고 rare-term retrieval accuracy로 적합성을 검증함

## Ⅶ. 적용 사례

- LLM API 과금 관리: 프롬프트 전송 전 실제 토큰 수를 계산해 비용 상한을 제어함, 확인 지표는 요청당 token 수와 비용임
- RAG 파이프라인: tokenizer 기준 청킹으로 문맥 손실을 줄임, 확인 지표는 context precision과 answer relevancy임
- 온디바이스 LLM: 작은 vocabulary와 효율적 분절로 메모리 사용량을 제어함, 확인 지표는 model size와 latency임

## Ⅷ. 결론

토큰화는 단순 전처리가 아니라 모델 비용과 문맥 효율과 검색 품질을 결정하는 입력 인터페이스이므로, 언어 특성과 도메인 특성에 맞는 tokenizer 선택이 서빙 아키텍처 성패를 좌우함.
