## 핵심 인사이트 (3줄 요약)
> 1. **본질**: 인간이 쓰는 자연어(문장)를 컴퓨터(LLM)가 이해하고 계산할 수 있도록, **의미를 가진 가장 작은 단위 조각(Token)들로 잘게 쪼개고 각각에 고유 번호(ID)를 부여하는 데이터 전처리(사전 번역) 과정**이다.
> 2. **가치**: "사과가"를 단어 단위로 쪼개면 너무 사투리가 많아 사서 고생하고, 글자(알파벳) 단위로 쪼개면 문맥을 잃는다. 현대의 토큰화(BPE 등)는 "자주 쓰는 덩어리(Subword)" 단위로 영리하게 쪼개어, 세상의 모든 신조어와 오타까지 에러 없이 처리하는 무한의 어휘력(Vocabulary)을 LLM에게 선물했다.
> 3. **판단 포인트**: 이 과정이 LLM의 API '과금(Cost)' 기준이자 '컨텍스트 길이'를 결정짓는 핵심 단위임을 인지하고, 한글이 영어보다 토큰을 2~3배 더 잡아먹는 '토큰 비효율성(Token Inefficiency)' 문제와 토크나이저 압축 알고리즘(BPE, Tiktoken)의 작동 원리를 서술해야 한다.

---

## Ⅰ. 개요 및 필요성
- **개요**: 토큰화(Tokenization)는 원시 텍스트(Raw Text) 스트링을 머신러닝 모델이 섭취할 수 있는 수치화된 배열(Token IDs)로 변환하는 첫 번째 파이프라인으로, 모델의 성능, 속도, 비용을 좌우하는 가장 기저의 아키텍처다.
- **배경**: AI에게 "Unbelievable(믿을 수 없는)" 이라는 단어를 가르쳐야 했다. 단어 단위(Word-level)로 쪼개면 사전에 세상 모든 단어(수백만 개)를 다 저장해야 해서 메모리가 터졌다. 알파벳 단위(Char-level)로 'U', 'n', 'b'로 쪼개면 메모리는 적게 들지만 AI가 "이게 뭔 뜻이야?"라며 의미를 파악하지 못해 바보가 됐다.
- **필요성**: 너무 크지도 않고, 너무 작지도 않은 '적절한 의미 덩어리(Subword)'로 쪼개야 했다. "Un + believ + able" 처럼 자주 쓰이는 접두사나 어근 덩어리로 잘라내어, 처음 보는 신조어나 오타가 나와도 조립해서 유추(OOV, Out-of-Vocabulary 문제 해결)할 수 있는 똑똑한 믹서기가 필요했다.

## Ⅱ. 아키텍처 및 핵심 원리

```text
  [ 원본 문장 ]: "ChatGPT is incredible!"

  ┌──────────────────────── [ BPE (Byte-Pair Encoding) 토큰화 흐름 ] ────────────────────────┐
  │                                                                                      │
  │ 1. [ 글자 단위 쪼개기 ] : C, h, a, t, G, P, T, _, i, s, _, i, n, c, r, e, d, i, b, l, e, ! │
  │                                                                                      │
  │ 2. [ 빈도수 병합 (Merge) 무한 반복 - 학습 과정 ]                                            │
  │    - "데이터를 보니 'i'와 'n'이 맨날 같이 붙어 다니네? 합쳐!" ──▶ 'in' 토큰 탄생             │
  │    - "'Chat'이라는 덩어리가 자주 나오네? 합쳐!"          ──▶ 'Chat' 토큰 탄생           │
  │                                                                                      │
  │ 3. [ 서브워드(Subword) 분해 - 추론 과정 ]                                                 │
  │    문장을 학습된 토큰 사전(Vocabulary, 약 10만 개)에 맞춰 잘라냄.                           │
  │    - "Chat" / "G" / "PT" / " is" / " in" / "cred" / "ible" / "!"                     │
  │                                                                                      │
  │ 4. [ 정수 매핑 (ID 부여) ]                                                              │
  │    - 14352  /  42 / 9912 /   345 /   222 /   8921 /   1104 / 0 (총 8개 토큰)          │
  └──────────────────────────────────────────────────────────────────────────────────────┘
           ▼
  [ LLM 입력 ] : [ 14352, 42, 9912, 345, 222, 8921, 1104, 0 ] 이라는 숫자 배열이 신경망에 꽂힘!
```

- **1단계 [전처리 (Pre-tokenization)]**: 텍스트를 공백(Space)이나 구두점 기준으로 대략 쪼갠다. (영어는 쉽지만, 띄어쓰기가 엉망인 한국어나 공백이 없는 중국어는 여기서부터 난관이다).
- **2단계 [BPE 알고리즘 병합 (Byte-Pair Encoding)]**: 훈련 데이터를 쫙 훑어보고, 가장 많이 같이 등장하는 글자 쌍(Byte pair)을 묶어서 새로운 토큰 사전에 추가한다. 이 짓을 사전에 10만 개(Vocab Size)가 찰 때까지 반복한다.
- **3단계 [OOM (Out-of-Vocabulary) 방지]**: "민트초코치킨"이라는 생전 처음 보는 단어가 들어와도 에러를 뱉지 않는다. "민트", "초코", "치킨" 혹은 "민", "트", "초" 등 자기가 아는 가장 큰 조각(Subword)들로 어떻게든 쪼개서 숫자로 바꿔낸다.
- **4단계 [디토큰화 (Detokenization)]**: LLM이 `[ 8921, 1104 ]` 라는 결과 숫자를 뱉어내면, 토크나이저가 사전을 보고 다시 "cred" + "ible" = "credible" 이라는 인간의 언어로 조립해서 화면에 띄워준다.

## Ⅲ. 비교 및 연결

| 비교 축 | Word-level (단어 단위) | Char-level (글자 단위) | Subword-level (BPE, WordPiece) |
|:---:|:---|:---|:---|
| **쪼개는 방식** | "I", "love", "apple" | "I", "l", "o", "v", "e" | **"I", "lo", "ve", "app", "le"** |
| **사전 크기** | 수백만 개 (메모리 폭발) | 26개 알파벳 (매우 작음) | **보통 3만 ~ 10만 개 (적절함)** |
| **신조어/오타 처리**| "스마트폰" 모르면 에러 뻗음 | 조립 가능하지만 뜻을 모름 | **"스마트" + "폰" 으로 잘라서 유추 가능** |
| **적용 모델** | 옛날 RNN 챗봇 | 거의 안 씀 | **GPT, BERT, Llama (현재 천하통일)** |

> ※ **연결 포인트**: OpenAI가 공개한 토크나이저 알고리즘인 **'Tiktoken'**은 현재 세계에서 가장 빠르고 효율적인 토크나이저 중 하나다. 토크나이저를 어떻게 깎느냐에 따라 동일한 "안녕하세요"라는 문장도 A모델은 3토큰으로, B모델은 6토큰으로 인식하게 되며, 이는 곧 기업의 API 요금(Cost)과 직결된다.

## Ⅳ. 실무 적용 및 기술사 판단

- **적용 사례 1 (한국어 토큰 비효율성 문제 - Token Tax)**: GPT-3 시절, "사과"라는 영어 "Apple"은 1토큰(1달러)인데, 한국어 "사과"는 토크나이저가 한글을 학습하지 못해 "ㅅ", "ㅏ", "ㄱ", "ㅘ" 바이트 단위로 쪼개버려 무려 4토큰(4달러)을 갉아먹었다. 이를 해결하기 위해 최근 네이버 HyperCLOVA나 한국어 특화 Llama-3-ko 같은 로컬 모델들은, 아예 한글 덩어리("습니다", "그래서")를 꽉꽉 채워 넣은 '한국어 전용 토크나이저 사전(Vocab)'을 새로 만들어 한국어 처리 비용을 1/4로 후려쳤다.
- **적용 사례 2 (프롬프트 최대치 꽉꽉 채우기)**: 개발자가 LLM에 책 한 권을 RAG로 밀어 넣을 때 글자 수(Max Length) 10만 자를 넣었다고 안심하면 안 된다. 토크나이저를 거치면 영문은 1단어가 약 1.3토큰이지만, 한글이나 코드는 기호 때문에 1단어가 3~4토큰으로 뻥튀기된다. 서버가 뻗는 걸 막으려면 텍스트 글자 수가 아니라 반드시 사전에 `tiktoken.encode()` 함수를 돌려서 나온 정확한 '토큰 수' 기준으로 문서를 자르는(Chunking) 로직을 짜야 한다.
- **기술사 판단**: 아키텍트는 **'토크나이저의 어휘 사전(Vocabulary Size)'** 크기가 모델의 인지 능력과 추론 속도에 미치는 트레이드오프를 파악해야 한다. 사전을 20만 개로 늘리면 "슈퍼마켓"을 1토큰으로 한 방에 처리해 압축률이 좋아지고 문맥 윈도우를 아낄 수 있다. 하지만 출력층(Softmax)에서 20만 개의 단어 확률을 매번 계산해야 하므로 GPU 연산 딜레이(Latency)가 폭증한다. 최신 AI 설계의 화두는 이 토크나이저 사전을 얼마나 아름답고 효율적으로 설계하느냐에 달려 있다.

## Ⅴ. 기대효과 및 결론

- **기대효과**: OOV(미등록 단어) 에러라는 자연어 처리의 오랜 숙적을 완벽히 박살 냈으며, 기계가 세계의 모든 언어, 이모티콘(👍), 심지어 파이썬 코드 블록까지 차별 없이 일관된 숫자로 씹어먹을 수 있는 보편적 인터페이스를 완성했다.
- **향후 발전 방향**: 최근에는 텍스트를 토큰화하는 것에 그치지 않고, 이미지 픽셀, 오디오 파형, 비디오 프레임까지 모조리 잘게 쪼개어 동일한 '멀티모달 토큰(Multimodal Token)'으로 묶어버림으로써 진정한 의미의 '통합 인공지능 두뇌'로 발전하는 초석이 되고 있다.

### 📌 관련 개념 맵
- **BPE (Byte-Pair Encoding)**: 원래는 데이터를 쫙 압축하는 알고리즘이었다. 자주 나오는 "AA"를 "Z"로 치환해서 용량을 줄이던 기법인데, 이걸 자연어 처리에 가져와 자주 쓰이는 단어 덩어리(Subword)를 묶는 데 썼더니 초대박이 터져버린 AI의 근본 알고리즘.
- **토큰(Token) 과금 구조**: OpenAI API는 글자 수가 아니라 '토큰 수'로 과금한다. 한글 1글자 = 대략 2~3토큰, 영어 1단어 = 대략 1.3토큰이다. 한국인이 챗GPT를 쓰면 미국인보다 서버 비용을 2배 넘게 내는 셈인데, 이를 '토큰 세금(Token Tax)'이라고 부르며, 각국이 자국어 전용 소버린(Sovereign) AI를 굳이 만들려는 이유 중 하나다.

### 📈 관련 키워드 및 발전 흐름도
`Word2Vec (단어 1:1 매칭, OOV 문제)` $\to$ `BPE / WordPiece (서브워드 쪼개기 도입)` $\to$ `SentencePiece (공백 무시 통합 토크나이저)` $\to$ `Tiktoken (GPT-4 고속 토크나이저)` $\to$ `Multimodal Tokenizer (텍스트, 이미지, 소리 통합 쪼개기)`

### 👶 어린이를 위한 3줄 비유 설명
1. 외국인 친구(AI)에게 한국말 "엄마가 방에 들어가신다"를 가르쳐주려는데, 한국말을 통째로 주면 너무 어려워서 울어버려요.
2. 그래서 **'토큰화'**라는 가위로 "엄마+가 / 방+에 / 들어+가신다" 처럼 외국인 친구가 소화하기 딱 좋은 **'한 입 크기 덩어리(블록)'**로 예쁘게 잘라주는 거예요.
3. 이렇게 잘라준 블록들을 하나씩 번호(ID)를 매겨서 입에 쏙쏙 넣어주면, 낯선 단어가 나와도 레고 조립하듯이 완벽하게 뜻을 알아맞힐 수 있답니다!
