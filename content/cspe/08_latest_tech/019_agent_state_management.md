# 📖 【암기용】 개념 완전 이해

## 한눈에
- **개요**: 에이전트 상태관리는 **AI 에이전트**(001 참조)가 다단계 작업을 수행할 때 각 **단계·변수·도구 결과·승인 여부**를 외부 저장소에 기록·추적하는 체계다. 에이전트 메모리(016)가 대화 맥락을 다룬다면, 상태관리는 **작업 진행 현황과 제어 흐름** 자체를 다룬다.
- **왜 필요한가**: 에이전트가 5단계 이상의 도구 호출 체인을 실행하다가 중간에 장애·세션 만료가 발생하면, LLM 컨텍스트에만 상태를 둔 경우 이전까지의 진행분이 유실되어 처음부터 재실행해야 한다. 변경형 작업(결제·배포·삭제 등)에서 이 재실행은 중복 처리 사고로 이어진다.
- **핵심 직관**: 택배 추적 시스템과 같다. 접수→집하→이동→배달완료 각 단계를 DB에 기록해 두면 중간에 차량 고장이 나도 "이동 중" 상태에서 이어서 처리할 수 있다. 에이전트 상태관리도 똑같이 작업 단계를 영속 저장해 중단 복구를 가능하게 한다.

## 핵심 용어 정리 (내부에 등장하는 것들)

| 용어/표기 | 의미 | 비유·예 |
|:---|:---|:---|
| 상태 전이표(State Transition) | 허용된 단계 간 이동 규칙(예: 접수→검증은 가능, 접수→완료는 불가) | 지하철 노선도의 "갈 수 있는 다음 역" |
| 체크포인트(Checkpoint) | 특정 단계까지의 작업 스냅샷을 저장한 복구 지점 | 게임의 세이브 포인트 |
| 멱등성 키(Idempotency Key) | 같은 요청을 여러 번 보내도 결과가 1회와 동일하게 하는 고유 식별자 | 택배 송장번호 — 같은 번호로 두 번 접수해도 1건만 처리됨 |
| Saga 패턴 | 분산 트랜잭션을 단계별 로컬 트랜잭션+보상 액션으로 분리하는 패턴 | 호텔·항공·렌터카 각각 예약 후, 항공 실패 시 호텔만 취소 |
| 보상 트랜잭션(Compensation) | 이전 단계의 변경을 되돌리는 역방향 액션 | 결제 취소, 배포 롤백 |
| Optimistic Lock | 읽을 때 버전을 기록하고, 쓸 때 버전이 바뀌었으면 충돌로 거부하는 동시성 제어 | "내가 읽은 v3인데 이미 v4면 다시 읽어라" |
| DLQ(Dead Letter Queue) | 처리 실패한 메시지를 별도로 적재해 수동 검토하는 큐 | 반송 우편함 |
| Trace ID | 요청의 전체 호출 경로를 추적하는 고유 식별자 | 택배 송장의 바코드 — 전 구간 추적 가능 |

## 깊이 이해
- **배경·문제의식**: 에이전트 오케스트레이션(014)이 "무엇을 어떤 순서로 하는가"를 정의한다면, 상태관리는 "지금 어디까지 했고, 실패하면 어디서 이어갈 것인가"를 영속 기록하는 역할이다. LLM 컨텍스트에만 상태를 두면 세션 만료·OOM·네트워크 장애 시 복구가 불가능하고, 변경형 호출이 재시도되면 이중 결제·이중 삭제 사고가 발생한다.
- **작동 원리(어떻게+왜)**: 작업이 시작되면 고유 ID와 초기 상태(CREATED)를 State Store에 생성한다. 각 단계가 완료될 때마다 상태를 전이(예: CREATED→VALIDATED→APPROVED→EXECUTED→COMPLETED)하고, 입력·출력·타임스탬프를 함께 기록한다. 장애 시 Recovery Manager가 마지막 체크포인트의 상태를 읽어 해당 단계부터 재시도하거나, 변경이 이미 적용된 단계는 보상 트랜잭션으로 롤백한다. 동시에 같은 상태를 갱신하는 충돌은 Optimistic Lock(버전 비교)으로 방지한다.
- **비유**: 병원 수술 기록과 같다. 마취→절개→처치→봉합→회복 각 단계를 차트에 기록하므로, 수술 중 담당의가 교체되어도 "절개 완료, 처치 진행 중" 상태에서 이어받을 수 있다. 기록 없이 진행하면 어디까지 했는지 알 수 없어 처음부터 다시 해야 한다.
- **구체 예시**: 비용 정산 에이전트가 영수증 수집(OCR)→금액 검증→관리자 승인→회계 시스템 등록 4단계를 수행한다. 3단계(승인 대기)에서 세션이 끊겨도 State Store에 `status=PENDING_APPROVAL, step=3, receipt_id=R-2026-0715`가 남아 있어, 승인 후 4단계(회계 등록)부터 재개한다. 회계 등록 API에는 `idempotency_key=R-2026-0715`를 포함해 동일 등록이 두 번 처리되지 않게 한다.
- **흔한 오해·주의점**: "상태를 저장하면 복구가 자동으로 된다"는 오해가 있다. 상태 저장은 "어디까지 했는지"만 알려주고, 실제 복구는 재시도 로직·보상 트랜잭션·멱등성 키가 함께 설계되어야 한다. 또한 상태 저장소 자체의 가용성(Redis Cluster, RDB 이중화 등)도 설계 대상이다.

## 연결 개념
- 에이전트 오케스트레이션(014) — 상태관리의 대상이 되는 워크플로우 실행 체계
- 에이전트 실패복구(026) — 상태 기반 복구의 구체 전략(재시도·보상·폴백)
- 에이전트 감사로그(021) — 상태 변경 이력의 감사·규제 대응 측면

## Ⅰ. 개요 및 필요성

- 개요: 에이전트 작업의 단계·변수·결과를 외부 저장소에 영속 기록하는 상태 추적 체계임
- 배경: LLM 컨텍스트에만 상태를 두면 장애·세션 만료 시 진행분이 유실되고 변경형 재실행이 사고로 이어짐
- 필요성: 체크포인트 복구(RTO 수 초), 멱등성 기반 중복 방지, 상태 전이 감사 추적이 필수임

---

## Ⅱ. 구조 및 구성요소

```text
작업 요청 -> State Model(전이표) -> State Store(영속 저장) -> Recovery Manager(복구)
                                        |                          |
                                        +-> 버전/락                +-> 재시도/보상
                                        |
                                        +-> Audit Trail -> 변경 이력/Trace ID
```

| 구성요소 | 역할 | 특이사항 |
|:---|:---|:---|
| State Model | 단계·변수·전이 규칙 정의 | 허용 전이만 열거(whitelist) |
| State Store | 상태 영속 저장·버전 관리 | Redis Cluster, RDB 이중화 |
| Recovery Manager | 장애 시 체크포인트 기반 복구 | 재시도 + Saga 보상 연동 |
| Audit Trail | 상태 변경 이력 기록 | 변경자·Trace ID·입력 해시 |

> 요약: 전이표로 허용 상태를 정의하고, 영속 저장소·복구 관리자·감사 이력이 함께 동작함.

---

## Ⅲ. 동작원리 및 흐름도

```text
작업 시작 -> 상태 생성(CREATED) -> 단계 실행 -> 상태 전이(버전 갱신)
  -> 실패 감지 -> 체크포인트 복구/보상 트랜잭션 -> 완료 기록(COMPLETED)
```

1. 상태 생성: 작업 ID·사용자 ID·버전 1로 State Store에 초기 레코드를 생성함
2. 단계별 전이: 각 단계 완료 시 상태를 전이하고 입력·출력·타임스탬프를 Optimistic Lock으로 갱신함
3. 장애 복구: 실패 시 마지막 체크포인트를 읽어 재시도하고, 변경 완료된 단계는 보상 트랜잭션(Saga)으로 롤백함
4. 완료·감사: 전체 완료 시 COMPLETED로 전이하고, 전 과정의 Trace ID·승인자·결과를 감사 로그에 기록함

> 요약: 상태 생성→단계별 전이→장애 복구→완료 감사의 순환으로 작업 연속성과 책임 추적을 보장함.

---

## Ⅳ. 특징

- 영속성: 외부 저장소에 기록하므로 세션 장애·재시작에도 진행분이 유지됨
- 멱등 보장: 멱등성 키+결과 캐시로 재시도 시 중복 실행을 차단함(TTL 24시간)
- 전이 제약: 상태 전이표로 허용되지 않은 단계 이동(예: 접수→완료 건너뛰기)을 차단함
- 동시성 안전: Optimistic Lock으로 동시 갱신 충돌을 감지하고 재시도로 해소함
- 감사 연동: 상태 변경마다 Trace ID·변경자·입력 해시가 기록되어 규제 감사에 대응함

## Ⅴ. 심화 비교 및 적용 판단

| 구분 | 컨텍스트 기반 상태 | 외부 상태관리 | 선택 기준 |
|:---|:---|:---|:---|
| 저장 위치 | LLM 컨텍스트 윈도우 내 | Redis/RDB 외부 저장소 | 5분 이상 또는 변경형 작업은 외부 필수 |
| 복구 | 세션 소멸 시 전량 유실 | 체크포인트 기반 복구(RTO 수 초) | 장애 후 재개가 필요하면 외부 저장 |
| 중복 방지 | 재시도 시 중복 실행 위험 | 멱등성 키+Optimistic Lock | 결제·삭제 등 변경 API 포함 시 필수 |
| 감사 | 대화 로그만 존재(비정형) | 상태 전이·승인·Trace ID(정형) | 규제·내부통제 업무는 감사 로그 필수 |

> 요약: 장시간·변경형 작업이면 외부 상태관리를 적용하고, 조회 전용 단기 작업은 컨텍스트 기반으로 충분함.

**리스크·대응:**
- 상태 불일치: 동시 갱신 시 락 미적용 → Optimistic Lock+버전 관리, 충돌 시 재시도 (지표: 충돌 발생 건수/월)
- 중복 실행: 멱등성 키 미적용 → idempotency key+결과 캐시(TTL 24시간) 적용 (지표: 중복 실행 건수 월 0건)
- 보상 실패: Saga 보상 미구현 → 단계별 보상 액션 정의, 실패 시 DLQ 적재 후 수동 처리 (지표: DLQ 적체 건수)

**도입 후 점검 지표:**
- 복구 성공률: 장애 주입 테스트 시 체크포인트 복구 성공률 99% 이상
- 감사 완전성: 상태 전이 100% 감사 로그 기록(Trace ID 커버리지 확인)

## Ⅵ. 실무 적용 및 결론

**적용 방안 3개:**
1. 상태 전이표를 정의하고 허용되지 않은 전이·권한 없는 변경을 State Model에서 차단함
2. 변경형 작업에 idempotency key+Optimistic Lock을 적용하고, 부분 실패 시 Saga 보상 트랜잭션으로 롤백함
3. 상태 변경마다 AgentID·Tool명·입력 해시·Trace ID를 감사 로그에 기록하고 SIEM으로 연동함

**결론:**
- 기술사 판단: 조회형 단기 작업은 컨텍스트 경량 상태, 변경형 장시간 작업은 외부 영속 상태관리를 적용함
- 향후 방향: 에이전트 오케스트레이션(014)과 결합해 상태 기반 자동 복구·감사가 AI 업무 신뢰성의 기반이 됨
