# 📖 【암기용】 개념 완전 이해

## 한눈에
- **정의**: 머신러닝 모델을 **실제 상용 서비스(Online)에 배포한 뒤, 실제 사용자들의 클릭률, 구매율 같은 '비즈니스 실 데이터'를 바탕으로 모델이 돈을 잘 벌어다 주는지(진짜 성능)를 통계적으로 평가**하는 과정.
- **필요성**: 연구실(Offline)에서 과거 데이터로 잰 '정확도 99%'는 반쪽짜리 진실임. 아무리 정확한 추천 모델이어도 응답이 1초나 걸려서 고객이 앱을 꺼버리거나, 디자인이 구려서 클릭을 안 하면 비즈니스 가치는 0임. "그래서 이 모델이 실제 세상에서 가치가 있는가?"를 최종적으로 증명하는 도장 찍기 과정임.
- **핵심 직관**: 백종원의 골목식당. 식당 주방(Offline)에서 셰프들끼리 새 메뉴를 만들어보고 "맛있다(정확도 99%)"고 평가함. 하지만 그게 진짜 맛집 메뉴인지는 실제 매장 문을 열고(Online) 진짜 손님들이 돈을 내고 사 먹은 뒤 "재방문율, 하루 매출(비즈니스 KPI)"을 까봐야 결판이 남. 이 실제 장사 성적표를 매기는 게 온라인 평가.

## 깊이 이해
- **배경**: 오프라인 평가는 '과거에 벌어진 일(데이터)'을 잘 맞히는가만 봄. 하지만 실제 세상에는 '인과 관계'와 '사용자 상호작용(UX)'이 얽혀 있음. 오프라인에선 최고의 성적을 거둔 딥러닝 추천 알고리즘이, 실제 서비스에 배포했더니 연산량이 너무 무거워 로딩이 길어지는 바람에 매출이 폭락하는 현상(Offline-Online Gap)이 터지며, 결국 실전 평가의 중요성이 대두됨.
- **작동 원리 (대표적 기법)**:
  1. **A/B Testing (표준)**: 고객을 딱 반으로 쪼갬(50:50). A그룹엔 기존 모델, B그룹엔 새 모델을 노출함. 2주 뒤 어느 그룹이 물건을 더 많이 샀는지(매출 증가율)를 T-검정 등 통계로 엄밀하게 판정해 새 모델의 승리를 선언함.
  2. **Multi-Armed Bandit (MAB)**: A/B 테스트의 단점(2주 동안 못난이 모델을 보는 B그룹 고객은 피해를 봄)을 개선. 실시간으로 성적을 봐서 "오, B모델이 클릭을 잘 받네?" 싶으면 똑똑하게 B모델 쪽으로 트래픽을 60%, 70% 동적으로 몰아주는 강화학습 기반 평가.
  3. **Interleaving**: 네이버/구글 검색창에서 많이 씀. 화면을 반으로 나누는 게 아니라, A모델이 찾은 결과 1위와 B모델이 찾은 결과 1위를 섞어서(지퍼처럼 교차 배열) 화면에 뿌림. 고객이 뭘 클릭하는지 눈치채지 못하게 실시간 경쟁을 붙임.
- **구체 예시**: 유튜브 썸네일 추천 알고리즘 평가. 새로 만든 모델(v2)을 온라인 평가(A/B 테스트)에 올림. 평가 지표는 단순 정확도가 아니라 '유저 체류 시간(Watch Time)'. 1주일 뒤, v2를 적용받은 유저들의 체류 시간이 v1 대비 3% 증가했다는 결과가 나옴(P-value < 0.05). 즉시 100% 전면 도입 결정.
- **흔한 오해/주의점**: "그냥 모델 배포하고 어제보다 매출 올랐으면 좋은 거 아님?" $\rightarrow$ 최악의 오류(통계적 착각). 매출이 오른 게 모델 때문인지, 어제 비가 와서 배달 앱 주문이 늘어난 건지(외부 요인) 알 수 없음. 그래서 반드시 똑같은 시간에, 무작위로 나눈 두 그룹(A/B)을 동시 비교 통제해야 함.

## 연결 개념
- **Offline Evaluation (오프라인 평가)**: 온라인 평가 전에 반드시 거쳐야 하는 예선전. 훈련용/테스트용 과거 데이터로 모델의 수학적 오류(Loss, F1)를 잼.
- **Selection Bias (선택 편향)**: A/B 테스트 짤 때 그룹을 잘못 나누면 생기는 오류. (A그룹엔 20대만, B그룹엔 50대만 몰림). 이를 막기 위해 철저한 무작위 해싱(Random Hashing) 분배가 필수.
- **P-value (유의확률)**: 우연히 이 결과가 나왔을 확률. "B모델이 A모델보다 수익이 높은 게 우연일 확률이 5% 미만이다(P < 0.05)"라는 통계적 도장이 찍혀야 비로소 승리가 확정됨.

# 📝 【답안용】 시험 답안 템플릿
## 핵심 인사이트 (3줄 요약)
- **본질**: 머신러닝 모델을 상용 환경(Production)에 배포한 후, 실제 유저의 상호작용(Live Traffic)을 기반으로 비즈니스 KPI(클릭률, 전환율, 체류시간) 향상 여부를 통계적 가설 검정을 통해 증명하는 최종 평가 체계.
- **가치**: 오프라인 과거 데이터(Hold-out) 평가만으로는 알 수 없는 사용자 경험(UX), 응답 지연(Latency), 네트워크 효과 등의 변수를 통제된 환경에서 실측하여 "오프라인-온라인 성능 괴리(Gap)" 리스크를 원천 차단함.
- **판단 포인트**: 정확하고 신뢰성 있는 온라인 평가를 위해서는 완벽한 사용자 무작위 분할(Random Hashing) 인프라가 전제되어야 하며, 장기 A/B 테스트로 인한 기회비용(Regret)을 최소화하기 위해 강화학습 기반의 다중 슬롯머신 알고리즘(MAB: Multi-Armed Bandit) 도입을 전략적으로 고려해야 함.

## Ⅰ. 개요 및 필요성
- **정의**: 두 개 이상의 서로 다른 머신러닝 모델(버전)을 운영 환경에 동시 서비스하며, 사용자 그룹별 행동 로그와 비즈니스 피드백을 실시간 수집해 상대적 성능 우위를 판별하는 MLOps 방법론.
- **배경**: AI 서비스의 주안점이 기술적 정확도(Accuracy)에서 비즈니스 지표(ROI, 전환율)로 전환됨. 아무리 모델의 수학적 오차가 적어도, 응답이 느리거나 사용자의 실시간 컨텍스트를 반영하지 못하면 외면받는 시장 환경.
- **필요성**: 데이터 과학과 비즈니스 목표의 정렬(Alignment), 외부 노이즈(계절성, 이벤트)가 통제된 상태에서의 순수 알고리즘 효과(Causal Impact) 증명, 무위험 릴리스 프로세스 확립.

## Ⅱ. 온라인 평가의 3대 핵심 방법론 (A/B Test, MAB, Interleaving)
어떻게 트래픽을 다루고 평가할 것인가?
| 평가 기법 | 아키텍처 원리 및 트래픽 분할 방식 | 장단점 및 적용 시나리오 |
|:---:|:---|:---|
| **A/B Testing**<br>(무작위 대조 실험) | 트래픽을 A(대조군, 기존 모델)와 B(실험군, 신규 모델)로 N:N 분할하여 고정 배포 후, 일정 기간(예: 2주) 뒤 지표를 통계 검정함. | [장] 결과를 가장 엄밀하게 통계 검정 가능.<br>[단] 실험 기간 동안 나쁜 모델을 보는 그룹은 손해(기회비용 발생). |
| **MAB**<br>(Multi-Armed Bandit) | A, B 모델 중 실시간 클릭(Reward)이 더 잘 나오는 승자 모델 쪽에 트래픽 노출 비중(Exploitation)을 동적, 자동적으로 높여가는 알고리즘. | [장] 실험 중 발생하는 비즈니스 손실(Regret) 최소화.<br>[단] 인프라 구현이 매우 복잡함. (뉴스 기사 추천 등 트렌드 급변 시 유리). |
| **Interleaving**<br>(교차 배치) | 유저 1명의 화면에 A모델의 추천 결과(홀수열)와 B모델의 추천 결과(짝수열)를 교차(지퍼 풀링)로 섞어 뿌린 뒤, 무엇을 더 클릭하는지 대결시킴. | [장] 화면 UI 위치에 따른 편향(Bias) 제거, 매우 적은 샘플로도 승자 판별 가능.<br>[단] 두 모델 간 응답 지연 시간 동기화 어려움. |

## Ⅲ. 온라인 평가 파이프라인 흐름도 (A/B Test 기준)
가설에서 검정까지의 라이프사이클.
1. **가설 수립 및 실험 설계 (Design)**: "신규 협업 필터링 모델(v2) 도입 시 사용자당 구매 전환율(CVR)이 v1 대비 3% 포인트 향상될 것이다." 목표 지표 및 필요 샘플 수(Sample Size) 산출.
2. **해싱 기반 트래픽 분할 (Routing)**: User_ID를 시드(Seed)로 하는 해시 함수를 적용해 50:50으로 그룹 할당. (실험 기간 중 동일 유저는 항상 동일 모델에 연결되는 Sticky Session 보장 필수).
3. **지표 수집 (Telemetry)**: Kafka 등 이벤트 스트림을 통해 실험 그룹 태그(A/B)가 매핑된 클릭/구매 로그 수집. 시스템 지표(OOM, Latency) 동시 관측.
4. **통계적 유의성 검정 (Stat-Test)**: 최소 샘플 수가 채워지면 카이제곱 검정(범주형 비율) 또는 T-test(연속형 매출) 수행. P-value < 0.05 만족 여부 확인.
5. **승자 독식 배포 (Roll-out)**: 통계적으로 의미 있는 승리가 입증되면 라우팅 룰을 조정하여 신규 모델을 100% 전면 롤아웃.

## Ⅳ. Offline 평가 vs Online 평가 심화 대조
상호 보완적인 두 개의 거울.
| 구분 | Offline Evaluation (오프라인) | Online Evaluation (온라인) |
|:---:|:---|:---|
| **검증 환경** | 정적(Static), 통제된 과거 데이터 세트 | 동적(Dynamic), 변동하는 라이브 상용 트래픽 |
| **최우선 지표**| Accuracy, F1-Score, RMSE, AUC-ROC | CTR(클릭률), CVR(전환율), ARPU(유저당 매출), Latency |
| **평가 대상** | 모델의 수학적 추론력 및 일반화 성능 한계치 | UX/UI 요소가 결합된 최종 서비스의 비즈니스 임팩트 |
| **소요 시간** | 즉각적 산출 가능 (시간~일 단위) | 통계적 유의성 달성을 위해 수주~수개월의 관찰 기간 필요 |

## Ⅴ. 실무 적용 및 결론
- **판단 지표**: 통계적 유의성(Stat-sig) 달성에 소요되는 MDE(Minimum Detectable Effect) 최적화, 샘플 비율 불일치(SRM) 오류 발생 0건, A/B 테스트 파이프라인 처리량 증대.
- **실무 설계**: 대형 이커머스 C사의 '검색 랭킹 최적화 모델' 평가 체계 설계. 기존 오프라인 테스트에서 최강이던 딥러닝 검색 모델이 운영에선 2초 이상의 로딩 지연을 발생시켜 사용자 이탈을 유발함. 조치 방안: AWS 기반의 A/B 테스트 중앙 통제 플랫폼 구축. 1) 유저 해시 링(Hash Ring)을 구성해 트래픽을 90(기존):10(신규)으로 분할 배포. 2) 1주일간 메트릭 수집. CVR(전환율) 지표 자체는 올랐으나, 지연 시간(P95 Latency)이 1초 이상 튀는 빈도가 15% 증가함을 데이터 대시보드(Tableau)로 동시 확인. 3) 종합 비즈니스 로직에 의거하여 "성능 향상분보다 지연으로 인한 이탈 페널티가 더 크다"고 판정. 배포 기각 및 모델 경량화 파이프라인으로 롤백 지시.
- **결론**: 오프라인 평가는 AI 모델의 '출전 자격'을 심사하는 신체검사일 뿐이다. 모델이 비즈니스라는 실제 전장에 나갔을 때, 고객의 지갑을 열고 기업의 매출을 올리는 '진짜 성적'은 오직 온라인 평가(A/B Test)를 통해서만 증명된다. 기술 부서의 자기만족(Accuracy 99%)을 넘어, 경영진과 시장이 납득할 수 있는 데이터 기반 의사결정(Data-driven Decision)을 내리게 하는 것, 그것이 Online Evaluation 파이프라인의 궁극적 존재 이유다.

### 🔀 문제 유형별 목차 전환
- **Ⅱ·Ⅲ 강조 (개념/원리형)**: A/B 테스트에서 흔히 발생하는 통계적 함정 3대장 분석. 1) 충분한 기간을 안 지키고 중간에 훔쳐봐서 승리를 선언하는 'Peeking Problem', 2) 초기 신규 기능에 대한 호기심으로 트래픽이 일시 반짝하는 '신기 효과(Novelty Effect)', 3) 주말/평일 편향을 걸러내기 위한 'Seasonality 통제 방안' 원리.
- **Ⅴ·Ⅵ 강조 (실무/설계형)**: 트렌드가 분 단위로 변하는 숏폼 비디오(TikTok 등) 환경에서의 탐색-활용 최적화 설계. 느린 A/B 테스트로는 유행을 못 따라가므로, 추천 알고리즘 평가 체계에 Contextual Bandit 강화학습을 도입하여. 사용자 피드백(Watch Time)을 초 단위로 스코어링하여 실시간으로 모델 노출 확률을 튜닝하는 동적 앙상블 시스템(Dynamic Routing) 구현 방안.
