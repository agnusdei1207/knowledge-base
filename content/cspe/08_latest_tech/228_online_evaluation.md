# 📖 【암기용】 개념 완전 이해

> 목적: Online Evaluation을 처음 봐도 완벽히 이해하게 만든다. 시험 답안 양식이 아니라, 이해를 위한 친절한 설명이다.

## 한눈에
- **개요**: 머신러닝 모델을 실제 운영 환경에 배포한 후, 실제 사용자의 반응과 비즈니스 지표를 기반으로 모델의 성능을 실시간으로 평가하는 과정
- **왜 필요한가**: 과거 데이터(Offline)로 아무리 성적이 좋아도, 실제 사용자들의 마음은 다를 수 있으며 비즈니스 가치(매출, 클릭률)는 운영 환경에서만 최종적으로 확인 가능하기 때문
- **핵심 직관**: 연습 경기(Offline) 기록이 아무리 좋아도, 실제 본선 경기(Online)에서 관중들의 반응과 최종 승부 결과를 보고 실력을 판가름하는 것

## 깊이 이해
- **배경·문제의식**: 오프라인 평가는 과거의 데이터 셋을 사용한다. 하지만 실제 서비스에서는 '시간적 순서', '사용자 간의 상호작용', '외부 환경 변화' 등 수많은 변수가 작용한다. 오프라인에서 정확도가 높았던 추천 모델이 정작 실제 서비스에선 사용자의 외면을 받는 '오프라인-온라인 괴리(Gap)' 현상을 극복하기 위해 온라인 평가가 필수적이다.
- **작동 원리**: 실제 유입되는 트래픽을 대상으로 평가를 수행한다. 가장 대표적인 방식이 **A/B Testing**(트래픽을 나누어 대조)과 **Multi-Armed Bandit (MAB)**(성능이 좋은 모델에 트래픽을 동적으로 몰아줌)이다. 주요 지표로는 CTR(클릭률), CVR(전환율), ARPU(사용자당 평균 매출) 등 비즈니스 KPI를 사용한다.
- **비유**: 새로운 메뉴(모델)를 개발했을 때, 내부 시식회(Offline) 점수만 믿지 않고 실제 매장에서 손님들에게 팔아보며 얼마나 많이 팔리는지(Online)를 직접 확인하는 과정이다.
- **구체 예시**: 전자상거래 앱에서 기존 추천 엔진(v1)과 개선된 엔진(v2)을 사용자 50:50으로 나누어 적용한다. 1주일간 운영한 결과 v2의 구매 전환율이 5% 더 높다면, 최종적으로 v2를 전면 도입하기로 결정한다.
- **흔한 오해·주의점**: "온라인 평가는 정확도(Accuracy)만 보면 된다"는 오해다. 정확도는 높지만 시스템 응답이 너무 느려(Latency) 사용자가 이탈한다면 비즈니스 관점에서는 '실패한 모델'이다. 따라서 기술 지표와 비즈니스 지표를 함께 봐야 한다.

## 연결 개념
- A/B Testing — 온라인 평가의 가장 표준적인 방법
- Multi-Armed Bandit (MAB) — 탐색과 활용의 균형을 맞추는 동적 평가 기법
- Business KPI — 모델의 가치를 최종적으로 증명하는 지표들

# 📝 【답안용】 시험 답안 템플릿

> 목적: 시험장에서 25분에 그대로 쓰는 답안 양식. 작성방식(추상표현 금지·수치·도식·문제유형 전환)을 엄격히 지킨다.

## 핵심 인사이트 (3줄 요약)

> 1. **본질**: 온라인 평가는 운영 환경에서 실제 사용자 트래픽을 대상으로 비즈니스 KPI와 사용자 피드백을 통해 모델의 실질적 가치를 검증하는 과정이다.
> 2. **가치**: 오프라인 성능과 실제 서비스 성과 간의 괴리를 해소하고, 데이터 편향(Selection Bias)이 배제된 환경에서 모델의 유효성을 확정한다.
> 3. **판단 포인트**: 통계적 유의성(P-value) 확보를 위한 충분한 샘플 수와 기간, 그리고 시스템 성능(Latency)과 비즈니스 성과의 트레이드오프 분석이 핵심이다.

## 출제 의도 및 답안 포인트

| 출제 의도 | 반드시 짚을 핵심 | 감점 회피 포인트 |
|:---|:---|:---|
| 운영 환경의 모델 검증 역량 확인 | A/B Testing, MAB, 비즈니스 KPI 연계 | 단순히 "운영 중 테스트"라고 모호하게 서술 |
| 오프라인-온라인 괴리 현상 이해 확인 | 과거 데이터의 한계, 사용자 피드백 루프 | 오프라인 정확도만 강조하여 서술 |
| 통계적 의사결정 능력 확인 | 유의 수준(P-value), 탐색(Exploration) vs 활용(Exploitation) | 주관적인 판단에 의한 배포 결정 기술 |

> 요약: 모델의 기술적 정확도를 넘어 실제 서비스에서 창출되는 비즈니스 임팩트를 정량적으로 측정하고 환류하는 체계 제시가 핵심이다.

## Ⅰ. 개요 및 필요성

- 정의: 배포된 모델이 실제 사용자 상호작용 과정에서 생성하는 클릭, 구매, 잔류 등의 행동 지표를 기반으로 모델의 성과를 직접 측정하는 활동
- 배경: 오프라인 평가 지표(Accuracy 등)와 비즈니스 목표(매출 등) 간의 불일치 발생, 동적인 운영 환경에서의 모델 안정성 확인 필요
- 필요성: 모델 도입에 따른 실제 ROI(투자 대비 수익) 산출, 최적의 모델 버전 선정을 위한 객관적 근거 확보, 지속적 개선을 위한 피드백 루프 구축

## Ⅱ. 구조 및 구성요소

```text
User Request -> Traffic Splitter (Experiment Engine)
                        |
            +-----------+-----------+
            | (Group A)             | (Group B)
      Control Model (v1)      Treatment Model (v2)
            |                       |
      User Action (Click/Buy) -> Event Collector
                                    |
                          Statistical Analysis Engine (P-value/KPI)
```

| 구성요소 | 역할 | 특이사항 |
|:---|:---|:---|
| Experiment Engine | 사용자별 일관된 그룹 할당(Bucketizing) | 세션 유지 필수 (Hashing) |
| Event Collector | 사용자의 행동(클릭, 스크롤, 전환) 수집 | 실시간 로그 파이프라인 |
| Metric Builder | 원천 로그를 비즈니스 KPI로 가공 | CTR, CVR, ARPU 등 산출 |
| Analysis Engine | 두 그룹 간의 통계적 차이 분석 및 검정 | T-test, Chi-square, Z-test |

> 요약: 실험 엔진을 통한 사용자 분할과 행동 로그 분석을 통해 두 모델 간의 성과 우위를 통계적으로 판정함.

## Ⅲ. 동작원리 및 흐름도

```text
실험 설계(가설 수립) -> 샘플 크기 및 기간 결정 -> 트래픽 할당 및 배포 -> 로그 수집 -> 지표 계산 -> 통계 검정 -> 최종 의사결정
      |                     |                   |               |            |            |                  |
      +---------------------+-------------------+---------------+------------+------------+------------------+-----> 전면 롤아웃
```

| 단계 | 처리 내용 | 검증 기준 |
|:---:|:---|:---|
| 1 | 실험 그룹(A/B) 할당 및 모델 서빙 | 사용자 ID 기반 해싱(Hashing) 적용 |
| 2 | 사용자 행동 데이터 실시간 로깅 | 누락 없는 데이터 수집 보장 |
| 3 | 주요 KPI 산출 및 통계적 유의성 확인 | P-value < 0.05, 신뢰수준 95% |
| 4 | 비즈니스 영향도 종합 판단 | 수익성 상승 및 인프라 비용 대조 |

> 요약: 가설 검정 기반의 통계적 방법론을 적용하여 모델 교체에 따른 리스크를 관리하고 가치를 증명함.

## Ⅳ. 특징 (평가 방식 비교)

| 구분 | A/B Testing | Multi-Armed Bandit (MAB) | Interleaving |
|:---|:---|:---|:---|
| 평가 방식 | 정적 트래픽 분할 (50:50) | 성능 기반 동적 비중 조정 | 두 모델 결과를 섞어서 제공 |
| 최적화 목표 | 가설 검정 및 성과 확정 | 탐색과 활용의 조화 (기회비용 최소화) | 사용자 선호도 신속 비교 |
| 단점 | 실험 기간 중 하위 모델 비용 발생 | 통계적 분석이 복잡함 | UI/UX 구성의 제약 |
| 주요 용도 | 신규 모델의 확정적 검증 | 광고 배너, 뉴스 추천 등 급변 환경 | 검색 순위, 추천 리스트 평가 |

> 요약: 실험의 정확한 검증이 목적이면 A/B Test를, 실험 중 손실을 줄이려면 MAB를, 선호도 확인이 목적이면 Interleaving을 선택함.

## Ⅴ. 심화 비교 및 적용 판단

| 비교 축 | 오프라인 평가 (Offline) | 온라인 평가 (Online) | 선택 기준 |
|:---|:---|:---|:---|
| 데이터 특성 | 과거 고정 데이터 (Historical) | 현재 실시간 데이터 (Live) | 데이터의 시의성 |
| 평가 지표 | Accuracy, F1, RMSE | CTR, CVR, 매출, Latency | 비즈니스 가치 직결 여부 |
| 실행 속도 | 빠름 (분/시간 단위) | 느림 (수일/수주 단위) | 의사결정의 긴급도 |
| 환경 제약 | 낮음 (서버 내 계산) | 높음 (사용자 노출 리스크) | 실패 시 위험 비용 |

> 요약: 오프라인 평가는 모델의 '기술적 가능성'을, 온라인 평가는 '비즈니스 실효성'을 검증하는 필수 병행 단계임.

| 리스크 | 원인 | 대응 방안 | 확인 지표 |
|:---|:---|:---|:---|
| Selection Bias | 실험 그룹 간 사용자 특성 불균형 | 무작위 할당(Randomization) 검증 | 그룹 간 인구통계학적 동질성 |
| Novelty Effect | 신규 기능에 대한 일시적 호기심 | 실험 기간 연장 및 안정기 관찰 | 기간별 성과 추세선(Trend) |
| Interference | 그룹 간 상호 간섭 (네트워크 효과) | 클러스터 기반 분할 (Cluster Randomization) | 그룹 간 독립성 점검 |

> 요약: 선택 편향은 무작위화로, 신기 효과는 기간 연장으로, 간섭 효과는 클러스터 분할로 대응함.

| 점검 항목 | 목표 기준 | 측정 방법 |
|:---|:---|:---|
| 통계적 유의성 | P-value 0.05 미만 | 가설 검정 도구 활용 |
| 샘플 대표성 | 전체 트래픽의 유의미한 비율 확보 | Sample Size Calculator 활용 |
| 시스템 가용성 | 실험 중 서비스 장애 0건 | 시스템 헬스 체크 모니터링 |

> 요약: 도입 효과는 비즈니스 KPI의 유의미한 개선, 통계적 신뢰도 확보, 사용자 경험 안정성으로 판정함.

## Ⅵ. 실무 적용 및 결론

**적용 방안 3개:**
1. 신규 알고리즘 검증: 추천 모델 v2 배포 시, 2주간 A/B 테스트를 실시하여 기존 대비 구매 전환율(CVR) 7% 상승 및 통계적 유의성(P<0.01) 확보 후 전면 도입
2. 기회비용 최소화: 트렌드 변화가 심한 패션 상품 추천 시, MAB(Thompson Sampling)를 적용하여 실시간으로 반응이 좋은 모델에 노출 비중을 높여 매출 극대화
3. 기술/비즈니스 통합 평가: 모델의 정확도는 높으나 API 지연 시간(Latency)이 500ms를 초과하여 사용자 이탈이 발생하는지 '응답 속도별 전환율' 상관관계 분석

**결론 (2줄):**
- 기술사 판단: 온라인 평가는 데이터 과학의 가설을 비즈니스의 수익으로 전환시키는 최종 검증 관문이며, MLOps의 ROI를 증명하는 핵심 도구임
- 향후 방향: 사용자 개개인의 맥락에 맞춘 실시간 개인화 평가와, LLM의 정성적 답변을 온라인에서 평가하는 "Reward Model" 기반 환류 체계로 고도화될 것임
