# 📖 【암기용】 개념 완전 이해

> 목적: SDV를 차량 기능이 기계 부품보다 소프트웨어와 데이터로 정의되는 구조로 이해하게 만든다.

## 한눈에
- **개요**: 차량 기능을 소프트웨어, 중앙 컴퓨팅, OTA로 지속 변경하는 차량 아키텍처
- **왜 필요한가**: 전통 차량은 ECU별 기능이 고정되어 출고 후 기능 변경과 결함 수정이 제한된다.
- **핵심 직관**: 자동차가 스마트폰처럼 하드웨어 플랫폼 위에서 앱과 운영체제로 진화하는 구조다.

## 깊이 이해
- **배경·문제의식**: 차량에는 수십~100개 이상 ECU가 분산 배치되어 배선, 버전 관리, 기능 중복, 사이버보안 관리가 복잡해졌다.
- **작동 원리**: 도메인/존 제어기와 HPC가 센서·액추에이터를 통합하고, 차량 OS·미들웨어·서비스 API가 기능을 소프트웨어 서비스로 제공한다.
- **비유**: 예전 차량이 기능별 전용 리모컨 묶음이라면, SDV는 하나의 운영체제에서 앱이 권한을 받아 하드웨어를 사용하는 태블릿에 가깝다.
- **구체 예시**: 주행 보조 기능 개선, 배터리 관리 로직 수정, 인포테인먼트 기능 추가를 OTA로 배포하고 UNECE R156 기준에 따라 업데이트 이력을 관리한다.
- **흔한 오해·주의점**: SDV는 단순히 차량에 앱을 올리는 개념이 아니다. ISO 26262 기능안전, ISO/SAE 21434 사이버보안, UNECE R155/R156 승인 체계를 함께 만족해야 한다.

## 연결 개념
- OTA Update — 차량 소프트웨어 배포와 회수 체계
- AUTOSAR Adaptive — HPC 기반 차량 애플리케이션 플랫폼
- ISO/SAE 21434 — 차량 사이버보안 엔지니어링

# 📝 【답안용】 시험 답안 템플릿

> 목적: 시험장에서 25분에 그대로 쓰는 답안 양식.
> 핵심: SDV는 차량 기능을 ECU 하드웨어가 아니라 차량 OS, 중앙 컴퓨팅, 데이터, OTA로 정의·갱신하는 자동차 SW 플랫폼 전환이다.

## 핵심 인사이트 (3줄 요약)

> 1. **본질**: SDV는 차량 기능과 사용자 경험을 소프트웨어 서비스로 구현하고 OTA로 수명주기 동안 변경하는 구조다.
> 2. **가치**: 기능 출시 주기를 양산 이후까지 확장하고, 결함 수정·보안 패치·데이터 기반 기능 개선을 차량 수명주기에 포함한다.
> 3. **판단 포인트**: 중앙 컴퓨팅, 차량 OS, OTA, 안전·보안 승인, 데이터 거버넌스를 함께 설계해야 한다.

## 출제 의도 및 답안 포인트

| 출제 의도 | 반드시 짚을 핵심 | 감점 회피 포인트 |
|:---|:---|:---|
| 자동차 아키텍처 전환 이해 확인 | 분산 ECU -> 도메인/존 -> 중앙 컴퓨팅 | 인포테인먼트 앱 수준으로 축소 |
| SW 수명주기 판단 확인 | OTA, DevSecOps, 형상·버전 관리 | 출고 후 운영·회수 절차 누락 |
| 안전·보안 규제 인식 확인 | ISO 26262, ISO/SAE 21434, UNECE R155/R156 | 기능 추가만 쓰고 승인 체계 누락 |

> 요약: 이 문제는 자동차를 SW 플랫폼으로 보는 관점과 안전·보안 승인 체계를 함께 묻는다.

---

## Ⅰ. 개요 및 필요성

- 개요: 차량 기능 SW 플랫폼
- 배경: ECU별 폐쇄 구조는 기능 변경, 보안 패치, 데이터 활용을 차량 출고 이후에 확장하기 어렵다.
- 필요성: SDV는 OTA와 중앙 컴퓨팅으로 결함 수정, 기능 구독, 주행 데이터 기반 개선을 차량 수명주기에 반영한다.

---

## Ⅱ. 구조 및 구성요소

```text
Sensor / Actuator -> Zone Controller -> Vehicle HPC
      +-> Vehicle OS / Middleware -> Service API -> App / ADAS / Infotainment
      +-> OTA / Security / Data Platform
```

| 구성요소 | 역할 | 특이사항 |
|:---|:---|:---|
| Zone Controller | 물리 위치별 센서·액추에이터 집선 | 배선 길이와 ECU 수 감소 |
| Vehicle HPC | ADAS, 인포테인먼트, 바디 제어 연산 통합 | SoC, GPU, NPU 사용 |
| Vehicle OS/Middleware | 서비스 API, 통신, 자원 관리 제공 | AUTOSAR Adaptive, POSIX |
| OTA/Data Platform | 배포, 로그, 진단, 기능 활성화 관리 | UNECE R156 이력 관리 |

> 요약: SDV는 차량 하드웨어를 zone과 HPC로 묶고, 기능은 OS·미들웨어·서비스 API 위에서 실행한다.

---

## Ⅲ. 동작원리 및 흐름도

```text
요구 기능 정의 -> SW 개발·검증 -> OTA 패키징
-> 차량 배포 -> 안전 상태 확인 -> 기능 활성화 / 롤백
```

| 단계 | 처리 내용 | 검증 기준 |
|:---:|:---|:---|
| 1 | 기능 요구와 안전 목표를 정의함 | HARA, safety goal |
| 2 | 차량 OS와 API 위에 애플리케이션을 구현함 | API contract, integration test |
| 3 | OTA 패키지와 서명을 생성함 | signature, SBOM |
| 4 | 차량 상태 확인 후 배포·활성화·롤백을 수행함 | update success rate, rollback log |

> 요약: SDV 기능은 개발·검증·서명·배포·운영 관측이 연결된 차량 SW 수명주기로 동작한다.

## Ⅳ. 특징

| 구분 | 기존 차량 | SDV | 판단 기준 |
|:---|:---|:---|:---|
| 기능 정의 | ECU 하드웨어 중심 | SW 서비스 중심 | API·OTA 가능 여부 |
| 아키텍처 | 분산 ECU | 도메인/존/HPC | ECU 수, 배선 복잡도 |
| 수명주기 | 출고 전 기능 확정 | 출고 후 기능 변경 | 형상·승인 이력 |
| 규제 | 부품 인증 중심 | SW 업데이트 승인 포함 | UNECE R155/R156 |

> 요약: SDV는 기능 구현 위치가 부품에서 소프트웨어 플랫폼으로 이동하므로 배포·보안·안전 책임이 OEM 운영 영역으로 확장된다.

## Ⅴ. 심화 비교 및 적용 판단

| 비교 축 | 기존/대안 | 본 키워드 | 선택 기준 |
|:---|:---|:---|:---|
| 구조 | 기능별 ECU | 중앙 컴퓨팅+zone | 배선·기능 중복 비용 |
| 배포 | 정비소 업데이트 | OTA 배포·롤백 | 결함 수정 리드타임 |
| 운영 | 출고 후 제한 관리 | 데이터 기반 수명주기 관리 | 로그·진단·동의 체계 |

> 요약: SDV는 기능 변경 빈도와 차량 데이터 활용 가치가 큰 차종에서 중앙 컴퓨팅 전환 효과가 크다.

| 리스크 | 원인 | 대응 방안 | 확인 지표 |
|:---|:---|:---|:---|
| 안전 오동작 | SW 결함이 제동·조향에 영향 | ISO 26262 안전 목표와 ASIL 분해 | safety case 승인 |
| 사이버 침해 | 외부 연결·OTA 채널 확대 | ISO/SAE 21434 TARA, mTLS, 서명 검증 | 취약점 조치 SLA |
| 배포 실패 | 전원·통신·버전 충돌 | A/B partition, delta update, rollback | update failure rate |

> 요약: SDV 리스크는 기능안전, 사이버보안, OTA 회수 가능성으로 구분해 통제해야 한다.

| 점검 항목 | 목표 기준 | 측정 방법 |
|:---|:---|:---|
| 배포 품질 | OTA 성공·롤백·중단률 관리 | fleet update telemetry |
| 안전·보안 | ISO 26262, ISO/SAE 21434 산출물 추적 | safety/security case review |
| 운영 가치 | 결함 수정 리드타임·기능 활성화율 | issue tracker, vehicle log |

> 요약: SDV 성과는 기능 수보다 배포 품질, 안전·보안 승인, 결함 수정 리드타임으로 판단한다.

## Ⅵ. 실무 적용 및 결론

**적용 방안 3개:**
1. 차종별 ECU 기능을 도메인·존·HPC로 재배치하고 safety-critical 기능과 infotainment 기능의 실행 격리를 정의함.
2. OTA는 UNECE R156 기준으로 SWIN, 서명 검증, 배포 대상 식별, 롤백 절차, 업데이트 이력 보관을 구현함.
3. 개발 단계에서 ISO 26262 HARA, ISO/SAE 21434 TARA, SBOM, 취약점 대응 프로세스를 동일 릴리스 게이트에 연결함.

**결론 (2줄):**
- 기술사 판단: SDV는 기능 변경 가치가 큰 차량에 우선 적용하되 안전·보안 승인과 OTA 회수 절차가 준비된 범위부터 배포해야 함.
- 향후 방향: SDV는 AUTOSAR Adaptive, V2X, AI 기반 ADAS/ADS, 차량 데이터 플랫폼과 결합해 서비스형 모빌리티 기반으로 확장됨.
