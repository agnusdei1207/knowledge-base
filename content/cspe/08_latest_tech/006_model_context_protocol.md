# 📖 【암기용】 개념 완전 이해

> 목적: MCP(Model Context Protocol)를 처음 봐도 완벽히 이해하게 만든다. 시험 답안 양식이 아니라, 이해를 위한 친절한 설명이다.

## 한눈에
- **개요**: LLM 애플리케이션과 외부 데이터·도구를 연결하는 개방형 표준 프로토콜
- **왜 필요한가**: AI 에이전트마다 서로 다른 API 연동 코드를 작성하면 유지보수와 보안 통제가 불가능해진다. 이를 해결하기 위해 "한 번의 서버 구축으로 모든 모델 연결"을 목표로 한다.
- **핵심 직관**: AI계의 USB-C 규격. 노트북(LLM 앱)에 USB 허브(MCP Server)를 꽂아 마우스(Tool), 외장하드(Resource)를 표준 방식으로 쓰는 것과 같다.

## 깊이 이해
- **배경·문제의식**: 기존에는 Anthropic, OpenAI 등 모델 제조사마다 도구 사용(Tool Use) 방식이 달랐고, 각 앱마다 DB·SaaS 연동 로직을 개별 구현하여 데이터 파편화와 보안 사각지대가 발생했다.
- **작동 원리**: JSON-RPC 2.0 기반으로 동작하며, 클라이언트와 서버가 `Tools`(실행), `Resources`(읽기), `Prompts`(템플릿)라는 3가지 핵심 자원을 주고받는다. 전송 계층은 `Stdio`(로컬)나 `SSE`(원격)를 사용한다.
- **비유**: 해외 여행 시 가전제품마다 어댑터를 챙기는 대신, 전 세계 공통 콘센트(MCP)를 설치하여 어떤 기기든 바로 꽂아 쓰는 방식이다.
- **구체 예시**: 개발자가 Git MCP 서버 하나만 띄워두면, Claude 데스크톱 앱에서도, 커스텀 AI 에이전트에서도 동일하게 "커밋 조회", "PR 생성" 기능을 즉시 사용할 수 있다.
- **흔한 오해·주의점**: MCP는 데이터 전송 규약일 뿐, 그 자체로 권한을 부여하지 않는다. 서버 측에서 누가 어떤 도구를 호출할지 결정하는 RBAC(역할 기반 접근 제어) 설계가 반드시 병행되어야 한다.

## 연결 개념
- Tool Use (도구 사용) — MCP를 통해 실행되는 구체적 기능
- JSON-RPC 2.0 — MCP 메시지 교환의 기반 규격
- SSE (Server-Sent Events) — MCP의 원격 전송 프로토콜

# 📝 【답안용】 시험 답안 템플릿

> 목적: 시험장에서 25분에 그대로 쓰는 답안 양식. 작성방식(추상표현 금지·수치·도식·문제유형 전환)을 엄격히 지킨다.
> 핵심: MCP는 단순 연동 기술이 아니라, 기업 내 AI 에이전트의 보안 경계(Trust Boundary)를 설정하고 데이터 거버넌스를 확보하는 아키텍처이다.

## 핵심 인사이트 (3줄 요약)

> 1. **본질**: MCP(Model Context Protocol)는 LLM 기반 애플리케이션이 외부 데이터(Resource)와 도구(Tool)를 일관되게 사용하도록 규정한 JSON-RPC 기반 개방형 표준이다.
> 2. **가치**: 에이전트별 파편화된 커넥터를 MCP Server로 통합하여 재사용성을 극대화하고 보안 감사(Audit) 지점을 단일화한다.
> 3. **판단 포인트**: 도입 시 전송 계층(Stdio vs SSE) 선택, 도구별 권한 등급화, 민감 데이터 DLP(Data Loss Prevention) 필터링 설계가 핵심이다.

## 출제 의도 및 답안 포인트

| 출제 의도 | 반드시 짚을 핵심 | 감점 회피 포인트 |
|:---|:---|:---|
| AI 에이전트 연동 표준화 역량 확인 | Client-Server 구조, Tool·Resource·Prompt 3요소, JSON-RPC 2.0 | MCP를 보안 솔루션으로 오해(전송 규약임), 인증·인가 별도 설계 누락 |
| 엔터프라이즈 AI 거버넌스 이해 | 중앙 집중형 감사로그, 도구 발견(Discovery) 자동화 | 모든 API의 MCP 전환 강조(비용 대비 효율성 판단 필요) |
| 기술적 세부 사양 인지 | Transport 계층(Stdio, SSE), 메시지 스키마 검증 | 추상적인 "연동이 쉽다"는 표현 사용 |

> 요약: MCP의 표준화된 연동 아키텍처와 이를 통한 엔터프라이즈 보안 거버넌스 확보 방안을 연결하여 기술한다.

---

## Ⅰ. 개요 및 필요성

- 정의: LLM 애플리케이션-외부 시스템 간 도구·자원 공유를 위한 JSON-RPC 기반 표준 프로토콜
- 배경: AI 에이전트 확산에 따른 개별 API 연동 파편화로 유지보수 비용 급증 및 보안 통제력 약화
- 필요성: 단일 인터페이스를 통한 도구 재사용성 확보, 데이터 접근 권한 및 감사로그 일원화(Single Point of Control)

---

## Ⅱ. 구조 및 구성요소

```text
[MCP 아키텍처 구조도]
LLM Application -> MCP Client <-> Transport (Stdio/SSE) <-> MCP Server -> Tools
                      |                                       |       -> Resources
                      +-> Context Window                      +-> Prompts
```

| 구성요소 | 역할 | 특이사항 |
|:---|:---|:---|
| MCP Client | 모델과 서버 간 중계 | 도구 발견(List Tools), 호출 요청, 결과 컨텍스트 반영 |
| MCP Server | 도구 및 데이터 노출 | 로컬/원격 실행 환경 제공, 백엔드 시스템(DB, SaaS) 연동 |
| Transport | 메시지 전송 계층 | Stdio(로컬 프로세스 간), SSE(HTTP 기반 원격 통신) 지원 |
| 3대 리소스 | 제공 기능의 단위 | Tools(실행), Resources(데이터), Prompts(템플릿) |

> 요약: Client-Server 구조에서 Transport 계층을 통해 3대 핵심 리소스를 표준 메시지로 교환하여 연동을 수행한다.

---

## Ⅲ. 동작원리 및 흐름도

```text
[MCP 메시지 교환 흐름]
Initialize -> List Tools/Resources -> Tool Call -> Input Validation -> Backend Execution -> Result
(Capabilities)   (Discovery)       (Request)      (Security)         (Processing)        (Context)
```

| 단계 | 처리 내용 | 검증/보안 기준 |
|:---:|:---|:---|
| 1 | 세션 초기화(Initialize) | Client-Server 간 프로토콜 버전 및 기능(Capabilities) 협상 |
| 2 | 리소스 발견(Discovery) | 사용 가능한 Tool 목록 및 JSON 스키마 기반 입력 규격 획득 |
| 3 | 도구 호출 및 실행 | JSON-RPC 기반 메시지 전달, 서버 측에서 입력 인자 및 권한 검증 |
| 4 | 결과 반환 및 컨텍스트 반영 | 실행 결과를 텍스트/이미지 형태로 반환, 모델의 컨텍스트 윈도우에 주입 |

> 요약: 초기 협상 후 표준 스키마에 따라 도구를 호출하며, 모든 과정은 서버 측 보안 검증을 거쳐 수행된다.

---

## Ⅳ. 특징

| 구분 | 개별 API 연동 (기존) | MCP 표준 연동 (개선) | 기술사 판단 포인트 |
|:---|:---|:---|:---|
| 연동 복잡도 | N:M (앱 x 시스템) | 1:N (표준 Client x 서버) | 커넥터 개발 공수 70% 이상 절감 |
| 도구 관리 | 소스코드 내 하드코딩 | 동적 발견(Discovery) 기반 | 도구 추가 시 앱 재배포 불필요 |
| 보안 감사 | 앱별 로그 분산 | 서버 단위 중앙 집중 감사 | SIEM/SOAR 연동 용이성 확보 |
| 메시지 규격 | 커스텀 API (REST/gRPC) | 표준 JSON-RPC 2.0 | 인터페이스 일관성 및 검증 자동화 |

> 요약: MCP는 연동의 복잡도를 단일 표준으로 압축하여 운영 효율성과 보안 통제력을 동시 확보한다.

## Ⅴ. 심화 비교 및 적용 판단

| 구분 | 로컬 Transport (Stdio) | 원격 Transport (SSE) | 선택 기준 |
|:---|:---|:---|:---|
| 구현 방식 | 표준 입출력 스트림 기반 | HTTP 기반 SSE (Server-Sent Events) | 네트워크 경계 존재 여부 |
| 보안성 | 프로세스 격리 환경 | TLS 기반 암호화 통신 필요 | 데이터 민감도 및 격리 요건 |
| 확장성 | 단일 머신 내 제한 | 네트워크 기반 다수 앱 연결 | 중앙 집중형 MCP 서버 운영 시 |

> 요약: 개발/보안 환경에서는 Stdio를, 전사 공유 도구 서버 운영 시에는 SSE 기반 원격 연결을 선택한다.

| 리스크 | 원인 | 대응 방안 | 확인 지표 |
|:---|:---|:---|:---|
| 과잉 권한 실행 | Tool 권한 범위 미설계 | 조회/변경/관리 권한 분리(RBAC), 고위험 Tool 승인 | 변경형 Tool 무승인 실행 0건 |
| 데이터 유출 | 리소스 응답 내 민감정보 포함 | 서버 측 DLP(Regex/NLP) 필터링, 마스킹 적용 | 개인정보 노출 차단율 99.9% |
| 서버 신뢰성 위험 | 미검증 외부 MCP 서버 사용 | 서명 검증, 내부 Proxy 운영, 허용 서버 List 관리 | 미승인 서버 호출 차단 건수 |

> 요약: 권한 분리, 데이터 필터링, 서버 신뢰 검증을 통해 MCP 연동의 보안 리스크를 통제한다.

| 점검 항목 | 목표 기준 | 측정 방법 |
|:---|:---|:---|
| 성능 (Latency) | p99 200ms 이내 (Transport 오버헤드 제외) | MCP Inspector, APM 호출 추적 |
| 정확도 (Accuracy) | 도구 선택 오류율(Model Side) 5% 이하 | 골든 데이터셋 기반 평가(Evaluation) |
| 보안 (Audit) | 호출자-도구-파라미터-결과 전체 로그 보존 | SIEM 대시보드 및 감사 로그 정합성 |

> 요약: 응답 속도, 모델의 도구 선택 정확도, 감사 로그 무결성을 지표로 도입 효과를 검증한다.

## Ⅵ. 실무 적용 및 결론

**적용 방안 3개:**
1. 엔터프라이즈 게이트웨이: 전사 공용 MCP 서버를 구축하여 DB·SaaS 접근 권한을 중앙에서 RBAC로 통제
2. 보안 필터 레이어: MCP 서버 응답 단계에서 주민번호, API 키 등 민감정보를 정규식 기반으로 자동 마스킹 처리
3. 옵저버빌리티 통합: Trace ID를 MCP 메시지에 포함하여 모델의 추론부터 실제 도구 실행까지 전체 흐름을 가시화

**결론 (2줄):**
- 기술사 판단: MCP는 AI 에이전트의 "Plug-and-Play"를 실현하는 핵심 규격이며, 도입 시 기능 구현보다 보안 경계 설정이 우선되어야 한다.
- 향후 방향: 모델별 독자 규격에서 MCP 중심의 생태계로 통합될 것이며, 향후 인증(Auth) 레이어가 강화된 MCP 2.0으로 진화할 전망이다.
