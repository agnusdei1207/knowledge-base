# 📖 【암기용】 개념 완전 이해

## 한눈에
- **개요**: **MCP**(Model Context Protocol)는 LLM 애플리케이션(호스트)과 도구·데이터 제공자(서버)를 **JSON-RPC** 기반의 표준 규격으로 잇는 **개방형 상호운용 프로토콜**이다.
- **왜 필요한가**: Tool Use(004)·Function Calling(005)은 "도구를 부르는 법"을 풀었지만, 도구마다 연동 방식이 제각각이라 앱마다 개별 통합(N×M 배선)을 반복해야 했다. MCP는 이 연결 방식을 한 규격으로 표준화해 재사용을 만든다.
- **핵심 직관**: USB-C가 기기·주변장치 연결을 한 규격으로 통일했듯, MCP는 "어떤 LLM 앱이든 어떤 도구·데이터든" 같은 규격으로 꽂아 쓰게 한다. Anthropic이 2024년 공개한 뒤 사실상 개방 표준으로 확산됐다.

## 핵심 용어 정리 (내부에 등장하는 것들)
답안 본문에 등장하는 용어를 처음 보는 사람도 이해하도록 비유와 함께 먼저 정리한다.

| 용어/표기 | 의미 | 비유·예 |
|:---|:---|:---|
| MCP(핵심) | LLM 앱과 도구·데이터를 표준 규격으로 잇는 개방 프로토콜 | 도구 연결의 "USB-C 표준" |
| 호스트(Host) | 사용자를 마주하는 LLM 애플리케이션(IDE·챗 앱) | 여러 주변장치를 꽂는 "노트북 본체" |
| 클라이언트(Client) | 호스트 안에서 서버 1개와 1:1 연결을 맡는 커넥터 | 본체의 "포트 하나" |
| 서버(Server) | 도구·데이터·프롬프트를 규격대로 제공하는 프로세스 | 꽂는 "주변장치" |
| 리소스(Resource) | 서버가 읽기용으로 노출하는 데이터·파일·문서 | 읽어 오는 "자료" |
| 툴(Tool) | 서버가 실행용으로 노출하는 함수·동작 | 실행하는 "기능 버튼" |
| 프롬프트(Prompt) | 서버가 제공하는 재사용 프롬프트·작업 템플릿 | 준비된 "작업 서식" |
| JSON-RPC 2.0 | 요청·응답·알림을 규정한 경량 원격호출 표준 | 표준화된 "대화 규약" |
| stdio / SSE·HTTP | 로컬 표준입출력, 원격 스트리밍 전송 방식 | 유선 케이블 / 무선 연결 |
| capability negotiation | 연결 초기 서로 지원 기능을 교환·합의 | 첫 만남에 "가능한 일 확인" |
| 커스텀 통합(N×M) | 앱·도구 조합마다 개별 연동 코드를 만드는 방식 | 기기마다 "전용 어댑터 제작" |

## 깊이 이해
- **배경·문제의식**: Function Calling(005)으로 한 앱 안에서 도구 부르는 법은 표준화됐지만, 도구 자체의 연결은 벤더·앱마다 달랐다. 앱 M개와 도구 N개를 붙이려면 M×N개의 개별 통합을 만들어야 했고, 도구가 바뀌면 앱마다 다시 손봐야 했다. MCP는 이 "연결 규격"을 프로토콜로 못 박아, 서버 1개를 만들면 MCP를 지원하는 모든 호스트가 재사용하게 한다.
- **작동 원리(어떻게+왜)**: 호스트 안의 클라이언트가 서버와 1:1로 연결되고, 초기 핸드셰이크에서 서로의 기능을 교환·합의(capability negotiation)한다. 이후 JSON-RPC 2.0 메시지로 서버가 노출한 세 가지 원시요소를 다룬다. ① 리소스(읽기용 데이터), ② 툴(실행용 함수), ③ 프롬프트(재사용 작업 템플릿). 전송은 로컬이면 stdio, 원격이면 SSE·HTTP를 쓴다. 규격을 고정했기에 어떤 호스트든 같은 방식으로 서버를 발견·호출할 수 있고, 이것이 상호운용의 핵심이다.
- **비유**: 예전엔 프린터·마우스마다 전용 단자가 달라 기기마다 어댑터가 필요했다. USB-C 표준 이후엔 케이블 하나로 다 꽂힌다. MCP 서버는 USB-C 주변장치, 호스트는 본체, 클라이언트는 포트에 해당한다.
- **구체 예시(실제 프레임워크·표준)**: Anthropic이 2024년 공개한 MCP는 Claude Desktop·여러 IDE·에이전트 프레임워크가 채택했다. 파일시스템·GitHub·DB·Slack용 공식/커뮤니티 MCP 서버가 있어, 하나의 GitHub MCP 서버를 여러 호스트가 그대로 재사용한다.
- **흔한 오해·주의점**: MCP는 새로운 도구 호출 "방법"을 만든 게 아니라, 기존 Tool Use(004)·Function Calling(005)을 여러 앱·도구가 공유하도록 "연결을 표준화"한 것이다. 또한 서버는 외부 코드·데이터에 접근하므로, 신뢰되지 않은 서버 연결·악의적 툴 설명(도구 설명에 숨긴 지시)·과도한 권한이 위험이 된다. 서버 출처 검증·권한 최소화·사용자 승인이 필요하다.

## 연결 개념
- Tool Use(004)·Function Calling(005) — MCP가 표준으로 감싸는 도구 호출 개념·구현
- 에이전트 시스템(001)·Tool Registry — MCP 서버를 런타임에 발견·연결하는 상위 구조
- MCP 서버·클라이언트·리소스·툴·프롬프트(007~011) — MCP 구성요소별 상세

> 2. **가치**: 앱·도구별 N×M 개별 통합을 표준 규격 재사용으로 전환해 연동 비용을 줄임.
> 3. **판단 포인트**: 상호운용 이득과 함께 서버 신뢰·권한 최소화·사용자 승인을 설계해야 함.

## Ⅰ. 개요 및 필요성

- 개요: LLM 앱과 도구·데이터를 JSON-RPC 규격으로 잇는 개방형 상호운용 프로토콜임
- 배경: Tool Use(004)·Function Calling(005)은 호출법을 풀었으나 도구 연결이 앱마다 제각각임
- 필요성: 앱 M개×도구 N개의 개별 통합을 표준 규격 재사용으로 줄여야 확장이 가능함
- 위치: 도구 호출 개념·구현(004·005)을 여러 앱이 공유하도록 표준화한 상위 연결 계층임

---

## Ⅱ. 구조 및 구성요소

- 선형 구조도

```text
호스트(LLM 앱) -> 클라이언트(서버당 1:1 커넥터) -> [전송: stdio 또는 SSE·HTTP]
  -> 서버(도구·데이터 제공) -> 리소스(읽기 데이터) / 툴(실행 함수) / 프롬프트(작업 템플릿)
```

| 구성요소 | 역할 | 특이사항 |
|:---|:---|:---|
| 호스트 | 사용자 대면 LLM 앱, 서버 조율 | 여러 클라이언트 관리 |
| 클라이언트 | 서버 1개와 1:1 연결·중계 | 초기 capability 협상 |
| 서버 | 리소스·툴·프롬프트 제공 | 외부 접근 권한 최소화 |
| 리소스/툴/프롬프트 | 읽기 데이터/실행 함수/재사용 템플릿 | 툴 설명에 숨은 지시 검증 |

> 요약: 호스트-클라이언트-서버 3계층이 JSON-RPC로 리소스·툴·프롬프트를 표준 교환함.

---

## Ⅲ. 동작원리 및 흐름도

- 선형 흐름도

```text
연결 개시 -> capability 협상 -> 서버 리소스·툴 발견 -> 툴 호출·리소스 조회 -> 결과 반환 -> LLM 반영
```

1. 연결·협상: 클라이언트가 서버와 연결 후 지원 기능·버전을 교환·합의
2. 발견: 서버가 노출한 리소스·툴·프롬프트 목록을 조회
3. 호출: 사용자 승인 하에 JSON-RPC로 툴 실행·리소스 읽기 요청
4. 반영: 결과를 호스트가 LLM 컨텍스트에 넣어 최종 답 또는 다음 호출 판단

> 요약: 초기 capability 협상이 상호운용을 보장하고, 툴 호출은 사용자 승인·권한 통제를 거침.

---

## Ⅳ. 특징

- 상호운용: 표준 규격이라 한 서버를 MCP 지원 호스트 전체가 재사용함
- 개방 표준: 특정 벤더·모델에 종속되지 않는 공개 프로토콜임
- 원시요소 분리: 읽기(리소스)·실행(툴)·재사용(프롬프트)을 명확히 구분함
- 전송 유연성: 로컬 stdio와 원격 SSE·HTTP를 동일 규격으로 지원함
- 신뢰 경계: 서버가 외부 데이터·코드에 접근하므로 출처·권한 검증이 필수축이 됨

## Ⅴ. 심화 비교 및 적용 판단

- 도구 연동 방식 관점에서 앱마다 만드는 커스텀 통합과 대비함

| 구분 | 커스텀 통합(N×M) | MCP |
|:---|:---|:---|
| 연결 방식 | 앱·도구 조합마다 개별 코드 | 표준 규격 1회 구현·재사용 |
| 확장 비용 | 도구·앱 늘수록 통합 폭증 | 서버 1개로 다수 호스트 지원 |
| 유지보수 | 도구 변경 시 앱마다 수정 | 서버만 갱신하면 전파 |
| 벤더 종속 | 앱·벤더별 전용 방식 | 개방 표준으로 종속 완화 |
| 발견성 | 사전 하드코딩 | capability 협상·동적 발견 |

> 요약: 도구·앱이 많고 재사용이 필요하면 MCP, 단일 앱의 소수 전용 도구만이면 커스텀 통합도 충분함.

- 주요 리스크와 대응(불릿)
  - 악성 서버: 신뢰 안 된 서버 연결이 원인 → 서버 출처 검증·서명·허용 목록 관리
  - 툴 설명 인젝션: 툴 설명에 숨긴 지시가 모델을 오도 → 설명 정제·사용자 승인·권한 최소화
  - 과도 권한: 서버가 넓은 시스템 접근 → 최소 권한·샌드박스·감사로그

- 도입 효과 지표(불릿)
  - 도구 통합 공수 절감(신규 도구 연동 시간 단축률)
  - 서버 재사용률(호스트당 공용 서버 채택 수)
  - 권한 위반 0건/주(서버 접근 감사로그)

## Ⅵ. 실무 적용 및 결론

- 적용 방안
  1. 파일시스템·GitHub·DB 등 공용 기능은 MCP 서버로 구현해 여러 호스트가 재사용하도록 표준화
  2. 서버 연결은 출처 서명·허용 목록으로 제한하고 툴 호출은 사용자 승인·최소 권한·샌드박스로 격리
  3. JSON-RPC 요청·응답과 툴 호출을 감사로그로 남겨 상호운용 구간의 추적성 확보
- 결론
  - 기술사 판단: 도구·앱이 많은 전사 환경은 MCP 표준화, 단일 앱 전용 소수 도구는 커스텀 통합을 적용함
  - 향후 방향: MCP는 서버 레지스트리·원격 인증 표준과 결합해 에이전트 도구 생태계의 개방 상호운용 기반으로 정착됨
