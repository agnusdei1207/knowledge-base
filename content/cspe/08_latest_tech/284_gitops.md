# 📖 【암기용】 개념 완전 이해

> 목적: "누가 언제 서버 설정을 바꿨어?!"라는 절망적인 외침을 끝내기 위해, 인프라의 모든 상태를 오직 'Git'이라는 하나의 진실의 원천(SSOT)에 박제해버리는 배포 패러다임을 이해한다.

## 한눈에
- **정의**: 애플리케이션 코드뿐만 아니라 인프라 설정(YAML, Terraform)까지 모두 Git 저장소에 선언적으로(Declarative) 저장하고, Git의 변경 사항을 시스템에 자동으로 동기화하는 **클라우드 네이티브 배포 및 운영 방법론**
- **필요성**: 기존에는 개발자가 Jenkins 파이프라인(Push 방식)으로 K8s에 직접 배포했다. 그런데 누군가 수동으로 K8s 설정을 바꿔버리면, 소스코드(Git)와 실제 서버 상태가 달라져서 장애가 났을 때 원인을 찾을 수도, 이전 상태로 롤백할 수도 없었기 때문
- **핵심 직관**: "Git이 '법전(진실)'이고, ArgoCD가 '경찰'이다. 경찰은 매일 K8s 서버를 순찰하며, 법전(Git)에 적힌 내용과 실제 서버 상태가 다르면 가차 없이 서버를 법전과 똑같이 뜯어고친다."

## 깊이 이해
- **배경(왜 등장했나?)**: 2017년 Weaveworks라는 회사에서 처음 주창했다. 쿠버네티스(K8s)가 천하통일을 하면서 "어차피 K8s 설정도 다 YAML(텍스트)인데, 이것도 앱 소스코드처럼 Git에 올리면 안 되나?"라는 아이디어가 나왔다. Git에 올리면 누가 결재했는지(PR), 누가 수정했는지(Commit History)가 완벽하게 추적되므로 보안과 감사(Audit)에 완벽했기 때문이다.
- **작동 원리 (Push vs Pull)**:
  - **과거 (Push 방식 - CIOps)**: Jenkins가 코드를 빌드하고, 그 Jenkins가 `kubectl apply` 명령어로 K8s의 문을 따고 들어가서 파일을 집어넣었다. (보안 구멍 발생, K8s 밖에서 안으로 밀어 넣음)
  - **현재 (Pull 방식 - GitOps)**: Jenkins는 그냥 Docker 이미지만 만들고 끝난다. 대신 K8s 내부에 살고 있는 'GitOps 에이전트(ArgoCD)'가 주기적으로 밖의 Git을 쳐다보다가(Pull), "어? Git 내용이 바뀌었네?" 하면 자기가 스스로 K8s 내부 상태를 변경한다.
- **일상 비유**: 옛날엔 사장님(Jenkins)이 매장(K8s)에 직접 찾아와서 진열대를 바꿨다(Push). GitOps는 매장에 '본사 지침서(Git)'와 '매니저(ArgoCD)'를 둔다. 사장님은 본사 지침서만 수정하고 퇴근한다. 매니저는 지침서를 보고 알아서 진열대를 바꾼다(Pull).
- **구체 예시**: 서버가 랜섬웨어에 걸려 완전히 박살이 났다. 옛날 같으면 백업 서버를 찾느라 난리가 나겠지만, GitOps 환경에서는 빈 K8s 클러스터 하나 띄우고 "저 Git 주소 보고 똑같이 만들어"라고 명령어 한 줄 치면 5분 만에 완벽히 복구(Disaster Recovery)된다. 모든 진실이 Git에 있기 때문이다.
- **흔한 오해/주의점**: "GitOps는 CI/CD를 대체하는 건가?" → 아니다! CI(Continuous Integration)는 여전히 Jenkins나 GitHub Actions가 코드를 빌드하고 테스트하는 데 쓰인다. GitOps는 오직 **CD(Continuous Delivery, 배포)** 영역을 가져와서 혁신한 것이다.

## 연결 개념
- **Declarative (선언적 인프라)**: "서버 3대 띄워줘!"라고 결과만 말하는 방식. K8s의 핵심 사상이자 GitOps가 가능하게 된 전제 조건.
- **ArgoCD, Flux**: GitOps를 구현하기 위해 K8s 내부에서 24시간 Git을 감시하고 동기화(Sync)하는 양대 산맥 오픈소스 에이전트.
- **SSOT (Single Source of Truth, 단일 진실 원천)**: "시스템의 진짜 상태는 오직 Git만이 알고 있다." GitOps의 가장 중요한 철학.

# 📝 【답안용】 시험 답안 템플릿

## 핵심 인사이트 (3줄 요약)
> 1. **본질**: GitOps는 클라우드 네이티브 인프라 및 애플리케이션 설정을 선언적(Declarative) 코드로 작성하여 Git에 저장하고, 이를 단일 진실 원천(SSOT)으로 삼아 시스템 상태를 자동 동기화하는 운영 패러다임이다.
> 2. **가치**: 기존의 Push 기반 배포가 가진 보안 취약점(외부 스크립트의 클러스터 접근 권한)을 K8s 내부의 Pull 기반 에이전트 모델로 극복하여, 보안(Zero-Trust)과 감사(Audit) 트레일을 완벽히 보장한다.
> 3. **판단 포인트**: 기존 CI/CD 파이프라인과의 구조적 차이점(Push vs Pull)을 명확히 대조하고, 구성 편차(Configuration Drift)를 스스로 치유(Self-Healing)하는 ArgoCD 등의 오퍼레이터(Operator) 역할을 강조해야 한다.

## Ⅰ. 개요 및 필요성
- **정의**: Git 저장소를 시스템 구성 및 인프라의 단일 진실 원천(SSOT)으로 사용하여 배포, 모니터링, 관리 프로세스를 자동화하는 방법론 (Weaveworks 제창)
- **배경**: 인프라가 코드로 관리되는 IaC(Infrastructure as Code) 시대가 도래했음에도, 배포는 여전히 외부 스크립트 기반(Jenkins 등)으로 수행되어 K8s 클러스터의 권한 탈취 리스크가 존재함
- **필요성**: 수동 조작으로 인한 시스템 구성 편차(Drift) 방지, 즉각적인 재해 복구(Disaster Recovery) 및 롤백(Rollback) 능력 확보, 개발자의 익숙한 도구(Git PR)를 통한 인프라 거버넌스 구현

## Ⅱ. GitOps 아키텍처 (Pull-based 모델)
GitOps 아키텍처는 코드 빌드(CI)와 인프라 동기화(CD)를 물리적/논리적으로 분리한다.

```text
 [ 개발자 ] ──(Commit)──▶ [ App 소스코드 Git ] ──▶ [ CI 도구 (Jenkins/GitHub Action) ]
                                                            │ (Build & Test)
                                                            ▼
                                                     [ Image Registry (Docker Hub) ]
                                                            │ (이미지 태그 업데이트 Push)
 [ 운영자 ] ──(PR/Merge)─▶ [ Infra 설정 Git (YAML) ] ◀──────┘
                                  ▲ (감시 & 동기화)
 ─────────────────────────────────┼─────────────────────────────────
 [ K8s Cluster ]                  │
   ┌──────────────────────────────┼───┐
   │ ┌───────────────┐ (Pull)     │   │
   │ │ GitOps Agent  │ ◀──────────┘   │ ◀─ K8s 내부에 설치되어 외부의 Git을 주기적으로 폴링(Polling)
   │ │ (ArgoCD/Flux) │                │
   │ └───────┬───────┘                │
   │         │ (Apply)                │
   │         ▼                        │
   │ [ App Pods / Services ]          │
   └──────────────────────────────────┘
```

## Ⅲ. 기존 Push 방식 (CIOps) vs GitOps (Pull 방식) 비교
| 비교 지표 | 기존 Push 기반 (Jenkins 중심) | GitOps (Pull 기반, ArgoCD 중심) |
|:---|:---|:---|
| **배포 주체** | 클러스터 외부의 CI/CD 서버 | **클러스터 내부의 GitOps 에이전트** |
| **보안 (크레덴셜)**| CI 서버가 K8s 최고 권한(Kubeconfig)을 가짐 (탈취 위험) | **K8s 내부에서 밖으로 나가서 가져오므로 외부 권한 노출 없음** |
| **상태 관리** | CI 파이프라인이 멈추면 서버 상태 알 수 없음 | **GitOps 에이전트가 24시간 모니터링 및 상태 보장** |
| **구성 편차 해결**| 누군가 `kubectl`로 수정하면 다음 배포 전까지 방치됨 | **에이전트가 Git과 다름을 감지(Out of Sync)하고 즉시 원복(Self-Heal)** |

## Ⅳ. GitOps의 4대 핵심 원칙 (OpenGitOps 표준)
CNCF 산하의 OpenGitOps 워킹 그룹이 정의한 4가지 원칙이다.
1. **선언적 (Declarative)**: "어떻게" 할지가 아니라 "무엇을" 원하는지 최종 상태를 정의한다. (명령형 스크립트 지양)
2. **버전 관리 및 불변성 (Versioned and Immutable)**: 원하는 상태는 수정 불가능하고(Immutable) 버전이 관리되는 저장소(Git)에 저장되어야 한다.
3. **자동화된 가져오기 (Pulled Automatically)**: 소프트웨어 에이전트가 선언된 상태를 저장소에서 자동으로 가져와야(Pull) 한다.
4. **지속적인 조정 (Continuously Reconciled)**: 시스템은 실제 상태와 선언된 상태의 차이(Drift)를 지속적으로 감지하고 동일하게 맞추려(Reconciliation) 노력해야 한다.

## Ⅴ. 기술적 한계(리스크) 및 해결 방안
| 리스크 요인 | 현상 및 문제점 | 대응 방안 (엔지니어링 가이드) |
|:---|:---|:---|
| **Secret(비밀번호) 관리의 어려움** | DB 패스워드나 인증 키 등을 텍스트 형태인 Git에 그대로 올리면 대형 보안 사고 발생 | **Sealed Secrets, External Secrets Operator** 등을 활용하여 암호화된 형태로 Git에 올리거나 K8s 내부에서 키 관리 시스템(Vault)과 동기화 |
| **저장소 구조의 파편화** | App 코드와 Infra 코드를 하나의 Git에 넣으면, 개발 코드가 바뀔 때마다 무한 루프 배포가 일어날 수 있음 | App Repository와 인프라 설정 전용(Config) Repository를 **물리적으로 분리(Separation of Concerns)** |

## Ⅵ. 실무 적용 및 결론
**적용 방안 및 실무 가이드:**
1. **Infrastructure as Code (IaC) 통합**: K8s 리소스뿐만 아니라, AWS/GCP의 컴퓨팅 자원이나 데이터베이스 프로비저닝도 Crossplane 같은 도구를 이용해 YAML로 선언하여 GitOps의 통제 하에 둔다.
2. **Auditing (감사) 프로세스 확립**: 상용 환경(Production)의 Git 브랜치에는 개발자가 직접 Commit 할 수 없도록 막고, 반드시 Pull Request(PR)와 시니어 엔지니어의 Approve(승인)를 통해서만 Merge 되도록 정책을 강제한다.

**결론:**
- GitOps는 단순한 배포 도구의 변경이 아니라, "개발과 운영의 진실을 오직 Git이라는 하나의 성소(Sanctuary)에 보관하겠다"는 클라우드 네이티브의 **궁극적인 철학적 선언**이다.
- 장애 복구를 위해 SSH로 서버에 접속하던 시대를 종식시키고, 모든 변경 이력을 Git 커밋으로 투명하게 남겨 시스템 운영의 예측 가능성과 안정성을 극대화한 최고의 배포 패러다임이다.
