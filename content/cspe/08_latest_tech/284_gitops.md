# 📖 【암기용】 개념 완전 이해

> 목적: GitOps를 처음 봐도 완벽히 이해하게 만든다. 시험 답안 양식이 아니라, 이해를 위한 친절한 설명이다.

## 한눈에
- **개요**: 시스템의 설정 정보(인프라, 앱 설정)를 Git 저장소에 넣어두고, Git에 저장된 상태가 실제 시스템에 자동으로 반영되게 만드는 운영 방식
- **왜 필요한가**: 예전에는 서버 설정을 수동으로 하거나 복잡한 배포 스크립트를 썼다. 그러다 보니 "현재 서버 설정이 어떻게 되어 있지?"라는 질문에 답하기 힘들었다. GitOps는 Git만 보면 현재 상태를 알 수 있고, 되돌리기도 쉽다.
- **핵심 직관**: **Git을 '단일 진실 공급원(Single Source of Truth)'**으로 삼는 운영 자동화다.

## 깊이 이해
- **배경·문제의식**: 쿠버네티스 같은 복잡한 인프라는 설정 파일(YAML)이 매우 많다. 이를 수동으로 적용(kubectl apply)하다 보면 실수하기 쉽고, 누가 언제 바꿨는지 알기 어렵다. 또한 배포 권한을 많은 사람에게 주면 보안상 위험하다.
- **작동 원리**: **선언적(Declarative)** 방식을 쓴다. "서버 3대 띄워줘"라고 Git에 적어두면, 시스템 내부에 있는 **에이전트(Operator)**가 Git과 실제 서버 상태를 계속 비교한다. 만약 다르면(Drift 발생), 에이전트가 알아서 실제 서버를 Git 상태와 똑같이 맞춰버린다(Reconciliation).
- **비유**: 인테리어 설계도와 같다.
    - 예전 방식: 인테리어 업자에게 매번 "이 의자 옮겨주세요"라고 전화함. (수동 명령)
    - GitOps 방식: 거실 설계도(Git)를 수정해서 게시판에 붙여둠. 인테리어 로봇(에이전트)이 수시로 설계도를 보고 실제 거실을 설계도와 똑같이 배치함. 누군가 몰래 의자를 옮겨도 로봇이 다시 제자리로 갖다 놓음.
- **구체 예시**: ArgoCD나 FluxCD 같은 도구를 쿠버네티스에 설치하고, YAML 파일을 관리하는 Git 주소를 연결.
- **흔한 오해·주의점**: "CI/CD랑 똑같은 거 아냐?"라고 할 수 있지만, CI는 코드 빌드에 집중하고, GitOps는 주로 **CD(지속적 배포)와 인프라 운영**의 '상태 유지'에 집중한다.

## 연결 개념
- Single Source of Truth (SSOT) — 모든 정보는 Git에 있다는 원칙
- Declarative Infrastructure — 결과 상태만 기술하는 방식
- Drift (드리프트) — Git 상태와 실제 상태의 차이
- ArgoCD, FluxCD — 대표적인 GitOps 구현 도구

# 📝 【답안용】 시험 답안 템플릿

> 목적: 시험장에서 25분에 그대로 쓰는 답안 양식. 작성방식(추상표현 금지·수치·도식·문제유형 전환)을 엄격히 지킨다.
> 핵심: 선언적 인프라와 재조합(Reconciliation) 루프를 통한 자동 동기화 메커니즘을 중심으로 서술한다.

## 핵심 인사이트 (3줄 요약)

> 1. **본질**: GitOps는 Git 저장소를 시스템의 원하는 상태(Desired State)에 대한 단일 진실 공급원(SSOT)으로 삼아, 실제 상태(Actual State)와 자동으로 동기화하는 운영 방법론이다.
> 2. **가치**: 인프라와 애플리케이션 설정을 코드로 관리(IaC)하여 변경 이력의 투명성을 확보하고, 장애 시 신속한 롤백(Rollback)과 구성의 일관성을 보장한다.
> 3. **판단 포인트**: 푸시(Push) 기반의 기존 CD 방식과 달리, 시스템 내부 에러전트가 상태를 감시하는 풀(Pull) 기반의 재조합(Reconciliation) 메커니즘이 핵심이다.

## 출제 의도 및 답안 포인트

| 출제 의도 | 반드시 짚을 핵심 | 감점 회피 포인트 |
|:---|:---|:---|
| GitOps의 핵심 원칙 이해 확인 | 선언적(Declarative), 버전 관리, 자동 동기화 | 단순히 "Git으로 배포한다"고만 서술 |
| Push 기반 vs Pull 기반 방식 비교 확인 | 에이전트 기반의 Pull 방식 이점 (보안, Drift 방지) | 두 방식의 기술적 차이 누락 |
| 쿠버네티스 환경에서의 작동 원리 확인 | Reconciliation Loop, Controller/Operator | 특정 도구(ArgoCD)의 기능 나열에 그침 |

> 요약: Git을 중심으로 시스템의 형상을 정의하고 자동 동기화하는 메커니즘과 그로 인한 안정성/투명성 효과를 기술한다.

---

## Ⅰ. 개요 및 필요성

- 정의: 애플리케이션 배포 및 인프라 구성을 Git 저장소에 선언적으로 정의하고, 실제 환경과 항상 일치하도록 자동화하는 운영 모델
- 배경: 쿠버네티스 등 복잡한 인프라 설정의 파편화(Config Drift) 발생 및 배포 프로세스의 가시성 결여 문제 해결 필요
- 필요성: 운영의 투명성 및 추적성 확보, 배포 승인 절차의 단순화(PR/Merge 기반), 장애 시 즉각적인 형상 복구 역량 강화

---

## Ⅱ. 구조 및 구성요소

```text
[ Developer ] --(Commit/PR)--> [ Git Repository (SSOT) ]
                                      | (Declarative Manifests)
                                      V
[ Target Env ] <--(Sync/Apply)-- [ GitOps Agent ]
  (K8s 등)                          (ArgoCD/Flux)
       |                              |
       +------(Detect Drift: 비교)-----+
```

| 구성요소 | 역할 | 특이사항 |
|:---|:---|:---|
| Git Repository | 시스템의 모든 설정(YAML 등)을 저장 | 단일 진실 공급원(SSOT) |
| GitOps Agent | Git과 실제 환경의 상태를 비교/동기화 | Pull 기반 메커니즘의 핵심 |
| Declarative Config | 원하는 결과 상태(State)만 기술한 파일 | "어떻게"가 아닌 "무엇"을 정의 |
| Reconciliation Loop | 상태 차이를 감지하고 자동으로 보정하는 루프 | Drift 발생 시 자동 복구 실행 |

> 요약: Git(원하는 상태)과 실제 환경(현재 상태) 사이에서 에이전트가 끊임없이 동기화를 수행하는 구조다.

---

## Ⅲ. 동작원리 및 흐름도

```text
[동작 흐름: Git 변경 -> 감지 -> 비교 -> 반영]
Git Commit -> Sync Event -> Compare (Desired vs Actual) -> Apply Diff
      |            |                |                      |
(YAML 수정) -- (Polling) ------ (Out-of-sync?) --------- (Self-healing)
```

| 단계 | 처리 내용 | 검증 기준 |
|:---:|:---|:---|
| 1 | 설정 변경 | 개발자가 Git 저장소의 매니페스트(YAML)를 수정하고 승인(Merge) |
| 2 | 차이 감지 | 에이전트가 Git의 새로운 상태와 클러스터의 현재 상태를 비교(Diff) |
| 3 | 재조합 실행 | 차이가 발견되면 에이전트가 클러스터에 설정을 적용하여 상태를 일치시킴 |
| 4 | 자가 복구 | 누군가 수동으로 설정을 바꾸면 에이전트가 다시 Git 상태로 원복(Self-healing) |

> 요약: 'Pull 기반' 방식을 통해 외부에서의 인프라 접근 권한을 최소화하고 상태 일관성을 유지한다.

## Ⅳ. 특징

| 구분 | 내용 | 판단 포인트 |
|:---|:---|:---|
| 가시성 | Git 로그가 곧 인프라 변경 이력이 됨 | "누가, 왜" 바꿨는지 확인 가능 |
| 보안성 | 클러스터 외부로 배포 권한(Kubeconfig 등)을 유출할 필요 없음 | Pull 기반 보안 모델 |
| 신뢰성 | 실수로 잘못 배포해도 `git revert` 한 번으로 즉시 복구 | 빠른 롤백(Mean Time to Recover) |
| 자동화 | 인프라 관리에 수동 개입을 배제하여 인적 오류 방지 | Drift 감지 및 자동 보정 |

> 요약: Git의 버전 관리 능력과 에이전트의 자동 동기화 능력을 결합하여 운영 안정성을 극대화한다.

## Ⅴ. 심화 비교 및 적용 판단

| 구분 | Push 기반 CD (Jenkins, GitLab CI) | Pull 기반 CD (GitOps - ArgoCD) |
|:---|:---|:---|
| 실행 주체 | 외부 CI 도구가 명령을 보냄 | 내부 에이전트가 Git을 읽어옴 |
| 보안 | 배포 대상의 자격증명이 CI 도구에 필요 | 자격증명이 내부에서만 관리됨 |
| Drift 대응 | 배포 시점에만 확인 가능 | 상시 감지 및 자동 복구 가능 |
| 적합 환경 | 전통적 서버, 단순 배포 | 쿠버네티스, 복잡한 선언적 환경 |

> 요약: 보안과 형상 일관성이 중요한 엔터프라이즈 클라우드 환경에서는 Pull 기반의 GitOps가 필수적이다.

| 리스크 | 원인 | 대응 방안 | 확인 지표 |
|:---|:---|:---|:---|
| 보안 사고 | Git 저장소 접근 권한 탈취 시 전체 인프라 위협 | Git 권한 관리 강화(RBAC), 2FA 필수 | Git 비인가 접근 시도 횟수 |
| 민감 정보 노출 | 비밀번호, API 키가 Git에 평문으로 저장됨 | Sealed Secrets, Vault 등 비밀번호 관리 도구 연동 | 보안 스캔 시 노출된 시크릿 건수 |
| 동기화 지연 | 대규모 환경에서 Git Polling 부하 및 지연 발생 | Webhook 활용 및 에이전트 분산 배치 | Git-to-Cluster 동기화 지연 시간 |

> 요약: Git 자체의 보안과 시크릿(Secret) 관리 체계 마련이 도입 전제 조건이다.

| 점검 항목 | 목표 기준 | 측정 방법 |
|:---|:---|:---|
| 배포 성공률 | 99% 이상 (자동 동기화 성공률) | ArgoCD 동기화 통계 |
| 롤백 시간 | 1분 이내 (revert 후 즉시 반영) | 장애 발생 시 복구 시간 측정 |
| Drift 발생률 | 수동 조작으로 인한 상태 불일치 0건 지향 | Out-of-sync 발생 로그 분석 |

> 요약: 배포 속도보다는 형상의 일관성(Consistency)과 복구 속도를 핵심 지표로 관리해야 한다.

## Ⅵ. 실무 적용 및 결론

**적용 방안 3개:**
1. 환경별 Git 레포 분리: 개발, 검증, 운영 환경을 디렉토리나 레포로 분리하여 환경 간 간섭 최소화
2. 시크릿 관리 통합: HashiCorp Vault와 연동하여 Git에는 참조 값만 넣고 실제 값은 런타임에 주입
3. 승인 워크플로우: Git의 Pull Request와 Code Review 기능을 인프라 변경 승인 절차로 활용

**결론 (2줄):**
- 기술사 판단: GitOps는 단순한 배포 도구를 넘어 인프라를 '코드'로 다루는 문화를 정착시키는 신뢰성 운영의 핵심 프레임워크이다.
- 향후 방향: 인프라를 넘어 보안 정책(Policy-as-Code)과 애플리케이션 코드까지 통합 관리하는 'Everything-as-Code'로 진화할 것이다.
