## Ⅰ. 개요
- **정의**: 현재 세션 내 대화·작업 맥락을 LLM의 Context Window에 유지하는 휘발성 임시 기억 장치
- **배경/필요성**: 에이전트 메모리 이원 구조 중(→016 참조) 단기 기억은 세션 내 연속성을 담당함. Stateless API 구조에서 대명사("그거") 해석과 작업 흐름 유지를 위해 매 호출 시 대화 이력을 프롬프트에 재주입해야 함
- **비유**: 수학 시간 칠판 — 꽉 차면 오래된 풀이를 지우고 새로 씀

| 출제 의도 | 반드시 짚을 핵심 | 감점 회피 포인트 |
|:---|:---|:---|
| Context Window 관리 전략 비교 | Buffer vs Sliding Window vs Summary Buffer 3가지 전략 | 단순 "대화 저장"이 아닌 토큰 한계 도달 시 Pruning 전략 설명 |
| 비용 최적화 설계 역량 | Prompt Caching을 통한 과금 절감 | 장기 기억(017)과의 연계: 단기 기억 폐기 직전 핵심 팩트를 장기 기억에 이관하는 구조 |

> 요약: Stateless LLM API에서 세션 내 맥락을 유지하기 위해 Message History를 관리하고, 토큰 한계 도달 시 Pruning 전략을 적용하는 메커니즘

## Ⅱ. 구성요소
```text
+---------------------------------------------------+
|           Short-term Memory Manager               |
|  +---------------------+                         |
|  | Message History     |                         |
|  | [System, User, Asst]|                         |
|  | (Array 누적)         |                         |
|  +----------+----------+                         |
|             |                                    |
|             v                                    |
|  +---------------------+                         |
|  | Token Counter       |                         |
|  | (한계치 감시)         |                         |
|  +----------+----------+                         |
|             |                                    |
|      +------+------+                             |
|      v              v                            |
|  +----------+  +-------------+                    |
|  | Sliding  |  | Summary     |                    |
|  | Window   |  | Buffer      |                    |
|  | (절삭)    |  | (요약 압축)  |                    |
|  +----------+  +-------------+                    |
|             |                                    |
|             v                                    |
|  +---------------------+                         |
|  | Prompt Assembler    |                         |
|  | (최종 페이로드 구성)  |                         |
|  +---------------------+                         |
+---------------------------------------------------+
```

| 구성요소 | 설명 | 비유 |
|:---|:---|:---|
| Message History | System/User/Assistant 역할별 대화 텍스트를 배열로 순차 누적하는 버퍼 | 회의록 — 발언순으로 기록 |
| Token Counter | 현재 누적 토큰 수를 실시간 계산하여 Context Window 한계 도달 여부를 감시 | 칠판 여백 측정기 |
| Pruning Strategy | 한계 도달 시 Sliding Window(오래된 턴 삭제) 또는 Summary Buffer(LLM 요약 압축) 적용 | 가지치기 — 오래된 가지를 정리 |
| Prompt Assembler | Pruning 후 남은 기억 + 새 입력을 최종 API 페이로드로 조립하여 LLM에 전송 | 서류 봉투 포장 |

> 요약: 대화 누적 → 토큰 감시 → Pruning(절삭/요약) → 페이로드 조립의 4계층 구조

## Ⅲ. 절차
```text
+------------------+     +------------------+     +------------------+     +------------------+
| 1. History       | --> | 2. Injection     | --> | 3. Limit Check   | --> | 4. Pruning       |
|    Accumulation  |     |    (프롬프트 주입) |     |    (토큰 감시)    |     |    (메모리 정리)  |
+------------------+     +------------------+     +------------------+     +------------------+
```

1. **History Accumulation(이력 누적)** — 사용자·어시스턴트 메시지를 Role 태그와 함께 시간순 배열에 추가함
2. **Prompt Injection(프롬프트 주입)** — 새 사용자 입력 시 누적 배열 전체를 API 페이로드에 포함하여 LLM에 전송함
3. **Limit Check(토큰 한계 감시)** — 누적 토큰 수가 모델 한계(예: 128K)의 80%에 도달하면 Pruning 트리거를 발동함
4. **Pruning(메모리 정리)** — Sliding Window(최고령 턴 삭제) 또는 Summary Buffer(과거 대화를 LLM으로 1줄 요약 압축)를 실행함

> 요약: 누적 → 주입 → 한계 감시 → Pruning의 순환 사이클

## Ⅳ. 문제점
- **토큰 비용 선형 증가**: 대화가 길어질수록 매 호출 시 전체 이력을 재전송하여 과금이 누적됨 — Stateless API 구조의 근본 원인
- **맥락 유실(Context Loss)**: Sliding Window 적용 시 오래된 턴이 삭제되어 초반 핵심 정보("사용자는 서울 거주")가 소실됨 — FIFO 삭제 정책의 한계
- **Scratchpad 과부하**: 에이전트 작업 중간 결과가 Scratchpad에 과도하게 누적되어 정작 추론에 필요한 토큰 공간이 부족해짐 — 작업 궤적 정리 로직 부재가 원인

> 요약: 과금 누적, 초반 맥락 소실, 작업 궤적 과부하가 단기 기억의 3대 난제

## Ⅴ. 개선방안
1. 단기: Prompt Caching 활용 — 변경되지 않는 Prefix(시스템 프롬프트+초기 이력)를 GPU VRAM에 캐싱하여 재과금 90% 절감(Anthropic, Google 등 지원)
2. 중기: Summary Buffer 고도화 — 단순 요약 대신 Named Entity·팩트만 추출하여 구조화 요약으로 정보 보존율 향상
3. 장기: 단기→장기 자동 이관 — Pruning 직전 핵심 팩트를 장기 기억(→017 참조) Vector DB에 자동 이관하는 파이프라인 구축

- **Scratchpad 과부하**: 중간 결과 무제한 누적 → 단계별 결과 요약 후 최종 결론만 유지하는 자동 정리 로직 적용 (지표: Scratchpad 토큰 < 전체의 20%)

> 요약: 캐싱 과금 절감 → 구조화 요약 → 장기 기억 자동 이관으로 비용·보존·성능 최적화

## Ⅵ. 전망
- **향후 발전 방향**: Gemini 1.5 Pro(200만 토큰) 등 거대 Context Window 모델 등장으로 Pruning 필요성이 감소하나, 비용 측면에서 무제한 투입은 비현실적이며 Pruning+Caching 병행이 주류로 유지될 전망
- **기술사적 판단**: 단기 기억은 장기 기억의 전처리(Staging) 역할을 겸함. 단기→장기 이관 파이프라인의 품질이 전체 메모리 아키텍처의 개인화 수준을 결정함
- **기술사 제언**: Prompt Caching 히트율 극대화를 위해 프롬프트 구조를 [불변 Prefix | 가변 Suffix]로 분리 설계할 것을 권고함
