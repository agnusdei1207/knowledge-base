## 미리 알고가기

- SRE는 운영을 소프트웨어 공학으로 다루는 접근으로 자동화와 신뢰성 목표를 중심에 둠
- DevOps와 겹치지만 SLO와 error budget으로 운영 의사결정을 정량화한다는 점이 특징임
- 단순 운영팀이 아니라 신뢰성 엔지니어링 역할과 프로세스를 포함한 체계로 이해해야 함

## Ⅰ. 개요

- **정의/개념**: SRE는 서비스 신뢰성과 운영 효율을 소프트웨어 공학 방식으로 관리하기 위해 자동화와 SLO와 장애 대응 원칙을 체계화한 운영 공학 접근임
- **배경/필요성**: 대규모 온라인 서비스는 수동 운영만으로 가용성과 변경 속도를 동시에 만족하기 어려워 운영 자체를 코드와 지표와 정책으로 다루는 모델이 필요해짐

## Ⅱ. 특징

- 운영 업무를 자동화해 toil을 줄이고 엔지니어링 비중을 높임
- SLO와 error budget을 기준으로 안정성과 출시 속도를 균형화함
- 장애 대응과 사후 분석을 학습 루프로 연결함
- 관측성과 런북과 자동복구 체계가 운영 기반이 됨

## Ⅲ. 종류 및 비교

| 판단 기준 | SRE | Traditional Ops | DevOps |
|:---|:---|:---|:---|
| 운영 방식 | 지표와 자동화 중심 | 수동 운영 중심 | 개발과 운영 협업 중심 |
| 핵심 기준 | SLO, error budget | SLA 준수 | 배포 속도와 협업 |
| toil 관리 | 적극적 감축 | 반복 업무 수용 | 자동화 지향 |
| 장애 학습 루프 | 강함 | 약함 | 중간 |

## Ⅳ. 구성요소 및 구조

| 구성요소 | 설명 |
|:---|:---|
| SLO and Error Budget | 신뢰성 목표와 허용 가능한 실패 범위를 정의해 운영과 배포 의사결정의 기준점을 만드는 계층임 |
| Observability Stack | 메트릭과 로그와 추적을 통해 실제 서비스 신뢰성 상태를 계량하는 관측 계층임 |
| Incident Response Flow | 탐지와 대응과 커뮤니케이션과 복구를 표준화해 장애 처리 속도와 일관성을 높이는 절차 계층임 |
| Automation and Runbook | 반복 운영 작업과 복구 절차를 자동화해 toil을 줄이는 실행 계층임 |
| Postmortem and Improvement Loop | 장애 원인과 개선 과제를 학습해 시스템 구조와 프로세스를 발전시키는 회고 계층임 |

## Ⅴ. 원리 및 절차 흐름도

```text
+-------------+    +-------------+    +-------------+    +-------------+    +-------------+
| 신뢰성 목표 정의 | -> | 상태 관측    | -> | 장애 대응    | -> | 사후 분석    | -> | 자동화와 개선  |
+-------------+    +-------------+    +-------------+    +-------------+    +-------------+
```

1. **신뢰성 목표 정의**: SLO와 error budget을 수립함
2. **상태 관측**: 서비스 신호를 지속적으로 측정함
3. **장애 대응**: 경보 발생 시 복구 절차를 수행함
4. **사후 분석**: 원인과 영향과 교훈을 정리함
5. **자동화와 개선**: 반복 문제를 코드와 프로세스로 제거함

## Ⅵ. 문제점 및 해결 방안

1. 문제: SLO 없이 가용성만 추상적으로 관리하면 배포 속도와 안정성 사이 판단 기준이 흔들릴 수 있음
   - 해결방안: user centric SLO와 error budget governance를 적용하고 release decision consistency와 budget burn visibility로 검증함
2. 문제: 반복 운영 업무가 자동화되지 않으면 SRE가 엔지니어링보다 수동 대응 조직으로 변질될 수 있음
   - 해결방안: toil budget policy와 runbook automation을 적용하고 toil ratio와 automated remediation coverage로 검증함
3. 문제: 장애 사후 분석이 비난 문화로 흐르면 학습과 구조 개선이 멈출 수 있음
   - 해결방안: blameless postmortem과 action tracking loop를 적용하고 postmortem completion rate와 recurring incident reduction rate로 검증함

## Ⅶ. 적용 사례

- 대형 서비스 조직이 사용자 중심 SLO를 운영하며 확인 지표는 release decision consistency와 budget burn visibility임
- 플랫폼 팀이 toil 예산과 자동화 정책을 적용하며 확인 지표는 toil ratio와 automated remediation coverage임
- 운영 조직이 비난 없는 회고 문화를 유지하며 확인 지표는 postmortem completion rate와 recurring incident reduction rate임

## Ⅷ. 결론

SRE는 운영을 지표와 자동화와 학습 루프로 바꾸는 체계이므로 SLO 중심 판단과 toil 감축과 회고 문화가 함께 성숙해야 함.
