# 📖 【암기용】 개념 완전 이해

> 목적: SRE를 처음 봐도 완벽히 이해하게 만든다. 시험 답안 양식이 아니라, 이해를 위한 친절한 설명이다.

## 한눈에
- **개요**: 구글이 제안한 운영 철학으로, "소프트웨어 엔지니어가 운영 작업을 맡으면 어떻게 할까?"에 대한 해답 (운영을 코딩처럼!)
- **왜 필요한가**: 개발팀은 새 기능을 빨리 만들고 싶어 하고(속도), 운영팀은 시스템이 안 깨지길 원한다(안정). 이 둘의 싸움을 끝내고 "얼마큼의 장애는 허용하자"라는 합의점을 찾기 위해 SRE가 필요하다.
- **핵심 직관**: **에러 예산(Error Budget)**이라는 개념을 도입해, 속도와 안정성 사이의 트레이드오프를 데이터(지표) 기반으로 결정하는 문화이자 실무 지침이다.

## 깊이 이해
- **배경·문제의식**: 서비스 규모가 커지면 수작업 운영은 한계에 부딪힌다. 장애가 나면 누군가를 비난(Blame)하게 되고, 반복적인 노가다 작업(Toil)에 엔지니어가 지친다. 이를 해결하기 위해 자동화와 블레임리스(Blameless) 문화가 등장했다.
- **작동 원리**:
    - **SLI (지표)**: 무엇을 측정할 것인가? (예: 응답 시간)
    - **SLO (목표)**: 어느 정도를 지킬 것인가? (예: 99.9% 성공)
    - **에러 예산**: SLO를 지키고 남은 여유분. 이 예산이 남아있으면 공격적으로 업데이트하고, 다 썼으면 모든 배포를 멈추고 안정화에 집중한다.
- **비유**: 다이어트와 같다.
    - SLI: 몸무게 숫자
    - SLO: 70kg 유지 목표
    - 에러 예산: 이번 달에 먹어도 되는 '치킨 횟수'. 살이 빠졌으면 치킨을 먹고(새 기능 배포), 살이 쪘으면 치킨을 끊고 운동(시스템 안정화)만 해야 한다.
- **구체 예시**: 구글의 SRE 팀은 운영 업무의 50% 이상을 자동화 코드 작성에 할당하도록 강제한다.
- **흔한 오해·주의점**: "DevOps와 다른 건가요?"라고 묻는다면, DevOps가 추상적인 '이념'이라면 SRE는 그 이념을 실천하기 위한 구체적인 '구현 방법론'이라고 보면 된다. (class SRE implements DevOps)

## 연결 개념
- DevOps — SRE의 상위 철학
- Error Budget — 속도와 안정을 조절하는 핵심 장치
- Toil (노가다) — 자동화해야 할 단순 반복 작업
- Post-mortem (사후 검토) — 비난 없이 원인을 분석하는 보고서

# 📝 【답안용】 시험 답안 템플릿

> 목적: 시험장에서 25분에 그대로 쓰는 답안 양식. 작성방식(추상표현 금지·수치·도식·문제유형 전환)을 엄격히 지킨다.
> 핵심: SRE의 7대 원칙과 SLI/SLO/Error Budget의 연계 구조, Toil 자동화 관점을 중점적으로 서술한다.

## 핵심 인사이트 (3줄 요약)

> 1. **본질**: SRE는 운영을 소프트웨어 엔지니어링 관점에서 접근하여 자동화, 지표 기반 의사결정, 속도와 안정성의 조화를 추구하는 실천적 운영 체계이다.
> 2. **가치**: 에러 예산(Error Budget)을 통해 개발과 운영 간의 이해충돌을 계량적으로 해결하고, 반복적 수작업(Toil)을 제거하여 시스템 확장성을 확보한다.
> 3. **판단 포인트**: 단순히 도구를 도입하는 것이 아니라, 비난 없는 사후 검토(Blameless Post-mortem)와 같은 문화적 변화와 데이터 중심의 목표 관리가 병행되어야 한다.

## 출제 의도 및 답안 포인트

| 출제 의도 | 반드시 짚을 핵심 | 감점 회피 포인트 |
|:---|:---|:---|
| SRE와 DevOps의 관계 이해 확인 | "class SRE implements interface DevOps" | 두 개념을 서로 배타적인 기술로 서술 |
| 핵심 지표 체계 및 관리 메커니즘 확인 | SLI, SLO, SLA, Error Budget | 지표 간의 정의 혼동 및 관계 설정 누락 |
| SRE 실천 원칙 및 가치 인지 확인 | Toil 제거, 자동화, 비난 없는 문화, 가시성 | 기술적인 자동화만 강조하고 문화적 측면 누락 |

> 요약: 데이터(SLO)에 기반하여 시스템의 신뢰성과 혁신 속도를 동시에 관리하는 엔지니어링 기법임을 강조한다.

## Ⅰ. 개요 및 필요성

- 정의: 소프트웨어 공학의 관점에서 운영(Operations)에 접근하여 서비스의 안정성, 신뢰성, 효율성을 극대화하는 방법론
- 배경: 서비스 규모의 기하급수적 팽창으로 인한 수작업 운영의 한계와 개발(Velocity)과 운영(Stability) 간의 이해 상충 심화
- 필요성: 장애 복구 시간(MTTR) 단축, 운영 비용(OPEX) 절감, 지표 기반의 투명한 의사결정 체계 구축

---

## Ⅱ. 구조 및 구성요소

```text
[ SRE 핵심 지표 체계 ]
  / SLI (Indicator): 성능 척도 (성공률, 지연시간 등)
  / SLO (Objective): 서비스 목표 수준 (SLI >= 99.9%)
  / SLA (Agreement): 고객과의 약속 (SLO 미달 시 보상)
  / Error Budget: 허용 가능한 장애 범위 (1.0 - SLO)

* Mechanism: Error Budget 소진 시 신규 배포 중단 및 안정화 집중
```

| 구성요소 | 역할 | 특이사항 |
|:---|:---|:---|
| SLI | 실제 측정되는 서비스 수준 지표 | 정량적 수치 (가용성, 지연 등) |
| SLO | 내부적으로 달성하고자 하는 목표치 | 개발/운영 합의의 기준점 |
| Error Budget | 속도와 안정성을 조절하는 안전장치 | (100% - SLO)에 해당하는 시간/횟수 |
| Toil (노역) | 사람이 반복적으로 수행하는 저부가가치 작업 | 50% 미만 유지가 SRE 권고 사항 |

> 요약: SLI/SLO로 목표를 정하고, 에러 예산으로 실행 속도를 조절하며, Toil 제거로 효율성을 높이는 구조다.

---

## Ⅲ. 동작원리 및 흐름도

```text
[동작 흐름: 측정 -> 평가 -> 결정 -> 조치]
Monitor SLI -> Compare with SLO -> Calculate Error Budget
      |               |                     |
      +--- [충분함] ---+---> New Feature Release (Velocity)
      |               |                     |
      +--- [부족함] ---+---> Stabilization & Bug Fix (Stability)
```

| 단계 | 처리 내용 | 검증 기준 |
|:---:|:---|:---|
| 1 | 지표 수집 | Golden Signals(지연, 트래픽, 오류, 포화도)를 실시간 모니터링 |
| 2 | 예산 산정 | 현재까지 발생한 장애 시간을 계산하여 남은 에러 예산 확인 |
| 3 | 우선순위 결정 | 예산 고갈 시 개발팀은 기능을 멈추고 운영팀과 함께 신뢰성 확보 작업 수행 |
| 4 | 사후 복기 | 장애 발생 시 비난 없이 원인을 분석하고 자동화 방안 도출 (Post-mortem) |

> 요약: 데이터(예산)가 허락하는 범위 내에서만 속도를 내고, 장애를 학습의 기회로 삼아 자동화에 재투자한다.

## Ⅳ. 특징 (7대 원칙)

| 원칙 | 내용 | 판단 포인트 |
|:---|:---|:---|
| 운영은 소프트웨어 문제 | 운영을 코드로 관리 (IaC, 자동화) | 엔지니어링 역량 강조 |
| 지표 기반 SLO 관리 | 주관적 판단 배제, 데이터 중심 결정 | Error Budget 활용 |
| Toil 제거에 집중 | 반복 업무 자동화로 창의적 업무 시간 확보 | 업무 비중 50% 룰 |
| 장애 허용 및 예산 | 100% 가용성은 불가능함을 인정 | 완벽주의 지양 |
| 자동화 추구 | 사람의 개입 없이 시스템이 자가 복구되도록 설계 | 확장성(Scalability) 확보 |
| 변경 사항 소규모화 | 큰 배포보다 작은 배포를 자주 하여 리스크 분산 | 릴리즈 안정성 |
| 단순화 유지 | 시스템 복잡도를 낮추어 관리 가능성 향상 | 미니멀리즘 설계 |

> 요약: '운영의 자동화'와 '장애의 수용'을 통해 지속 가능한 시스템을 만드는 원칙을 가진다.

## Ⅴ. 심화 비교 및 적용 판단

| 비교 축 | 전통적 운영 (SysAdmin) | 사이트 신뢰성 공학 (SRE) | 선택 기준 |
|:---|:---|:---|:---|
| 핵심 역량 | 하드웨어/OS 설정 및 수동 조치 | 프로그래밍 기반 자동화 도구 개발 | 자동화 비중 목표 |
| 장애 대응 | 장애 제로 지향 (보수적) | 허용 범위 내 혁신 (진보적) | 비즈니스 성장 속도 |
| 도구 활용 | CLI, 스크립트 위주 | API 기반 오케스트레이션, IaC | 인프라 규모 및 복잡도 |

> 요약: 안정성이 최우선인 금융권 코어 시스템은 보수적 접근이, 빠른 혁신이 필요한 클라우드 서비스는 SRE가 유리하다.

| 리스크 | 원인 | 대응 방안 | 확인 지표 |
|:---|:---|:---|:---|
| SLO 과잉 설정 | 무리한 가용성 목표 설정으로 개발 속도 저하 | 비즈니스 가치에 맞는 적정 SLO 재협상 | 에러 예산 소진 주기 |
| Toil 자동화 실패 | 자동화 코드 자체의 버그로 인한 2차 장애 | 점진적 자동화 및 철저한 테스트 | 수작업 비중 및 자동화 성공률 |
| 문화적 거부감 | 장애를 숨기거나 서로 비난하는 관성 | 경영진의 지지와 심리적 안전감 확보 | 사후 검토서(Post-mortem) 품질 |

> 요약: 기술적 자동화보다 '실패를 용인하고 학습하는 문화' 정착이 실무의 가장 큰 난제다.

| 점검 항목 | 목표 기준 | 측정 방법 |
|:---|:---|:---|
| 가용성 (Uptime) | SLO 정의 수준 (예: 99.99%) | 가동 시간 / 전체 시간 |
| MTTR (평균 복구 시간) | 목표 시간 이내 (예: 15분 이내) | 장애 발생~종료 시각 차이 |
| 자동화율 | 전체 운영 업무 중 자동화된 비중 70% 이상 | JIRA 티켓 처리 데이터 분석 |

> 요약: 시스템의 신뢰도 지표와 엔지니어의 생산성 지표를 동시에 관리해야 한다.

## Ⅵ. 실무 적용 및 결론

**적용 방안 3개:**
1. 골든 시그널 기반 모니터링: 지연 시간, 트래픽, 에러, 포화도를 통합 대시보드화하여 시스템 건전성 상시 파악
2. 카나리 배포(Canary Release): 신규 기능을 일부 사용자에게만 노출하고 SLI를 모니터링하여 에러 예산 소진 시 즉시 롤백
3. 카오스 엔지니어링 연계: 시스템에 의도적인 장애를 주입하여 SRE의 대응 절차와 자동 복구 메커니즘을 상시 검증

**결론 (2줄):**
- 기술사 판단: SRE는 단순한 직무 명칭이 아니라, 데이터 기반으로 개발과 운영의 합의를 이끌어내는 고도의 공학적 의사결정 체계이다.
- 향후 방향: 인프라가 더욱 파편화됨에 따라 AIOps와 결합하여 지능형 자동 복구(Self-healing) 시스템으로 진화할 것이다.
