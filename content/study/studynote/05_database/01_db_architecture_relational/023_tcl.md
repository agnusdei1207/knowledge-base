## 핵심 인사이트 (3줄 요약)
> 1. **본질**: TCL ([[191_transaction_concept_states|Transaction]] Control Language, [[191_transaction_concept_states|트랜잭션]] 제어 언어)은 [[002_database_definition|데이터베이스]]에서 [[369_logic_bomb|논리]]적 작업 단위인 [[191_transaction_concept_states|트랜잭션]]의 완료(COMMIT), 취소([[313_rollback|ROLLBACK]]), 부분 [[658_ir_recovery|복구]]([[200_savepoint_partial_rollback|SAVEPOINT]])를 제어하는 [[158_instruction|명령어]] 집합이다.
> 2. **가치**: 시스템 장애나 [[369_logic_bomb|논리]] 오류 발생 시 [[002_database_definition|데이터베이스]]를 일관된 상태(Consistent [[272_state_pattern|State]])로 유지하며, ACID ([[193_atomicity_all_or_nothing|Atomicity]]·[[194_consistency_database_integrity|Consistency]]·[[195_isolation_concurrency_control|Isolation]]·[[196_durability_permanent_storage|Durability]]) 특성 중 [[193_atomicity_all_or_nothing|원자성]]과 [[196_durability_permanent_storage|영속성]]을 보장하는 핵심 인터페이스다.
> 3. **판단 포인트**: [[191_transaction_concept_states|트랜잭션]] 경계 안에 외부 [[014_api_posix|API]] 호출이나 [[020_ddl|DDL]] ([[020_ddl|Data Definition Language]])을 혼용하면 의도치 않은 Auto-Commit이 발생해 [[001_dikw_pyramid|데이터]] 정합성이 붕괴되므로, [[191_transaction_concept_states|트랜잭션]]을 최대한 짧고 순수하게 유지해야 한다.

---

## Ⅰ. 개요 및 필요성

TCL은 [[002_database_definition|데이터베이스]] 시스템에서 [[083_dml|DML]] ([[021_dml|Data Manipulation Language]], [[001_dikw_pyramid|데이터]] 조작 언어) 연산들을 하나의 [[369_logic_bomb|논리]]적 단위로 묶어 "전부 아니면 전무(All or Nothing)"의 [[193_atomicity_all_or_nothing|원자성]]을 보장하는 제어 메커니즘이다.

### 등장 배경: TCL이 없으면 무슨 일이 생기는가?

계좌 이체 시나리오를 생각해보자. A 계좌에서 100만 원을 출금(UPDATE)한 직후, 서버 전원이 차단된다면 B 계좌는 돈을 받지 못한 채 A만 돈을 잃게 된다.

```text
  [TCL이 없는 경우 — 재난 발생]

  UPDATE A SET balance = balance - 1000000;  ← 물리 디스크 즉시 반영
         ↓ 전원 차단
  UPDATE B SET balance = balance + 1000000;  ← 미실행 → 돈 증발


  [TCL로 트랜잭션 경계 설정 — 복구 가능]

  BEGIN TRANSACTION
    ├─ UPDATE A (-1,000,000)  → 메모리 버퍼 반영 + Undo 로그 기록
    ├─ ⚡ 전원 차단 발생
    └─ UPDATE B (+1,000,000)  → 미실행
  ──────────────────────────────────────────
  엔진 재시작 후: Undo 로그 읽어 A를 원래 잔고로 자동 복원
  (트랜잭션 전체가 없었던 일로 처리됨)
```

핵심은 TCL이 개별 [[083_dml|DML]] 연산들을 하나의 **안전한 실행 캡슐(Begin ~ End)**로 묶어, 중간 장애가 발생해도 [[002_database_definition|데이터베이스]] 엔진이 내부 [[568_logs_distributed_logging_elk_fluentd|로그]]를 이용해 언제든 [[459_quic_fec_forward_error_correction|초기]] 상태로 되돌릴 수 있게 한다는 점이다.

> 📢 **섹션 요약 비유**: 은행 창구 직원이 서류를 작성하다 실수하면, 지우개로 지우는 대신 **"작성 취소([[313_rollback|ROLLBACK]])" 버튼**을 눌러 새 종이를 꺼내는 것과 같습니다.

## Ⅱ. 아키텍처 및 핵심 원리

### [[197_transaction_state_transition|트랜잭션 상태 전이]] ([[272_state_pattern|State]] Machine)

[[191_transaction_concept_states|트랜잭션]]은 시작부터 종료까지 엄격한 상태 머신을 따른다. 모든 TCL [[158_instruction|명령어]]는 이 상태를 전이시키는 [[507_acid_properties|트리거]]다.

```text
  ┌─────────────────────────────────────────────────────────────┐
  │                  트랜잭션 상태 전이도                         │
  │                                                             │
  │  [Active] ──DML 완료──▶ [Partially Committed]               │
  │     │                         │                            │
  │     │ (오류 발생)              │ COMMIT                     │
  │     ▼                         ▼                            │
  │  [Failed] ──ROLLBACK──▶ [Aborted] ──── (재시작/종료)         │
  │                                                             │
  │                  [Partially Committed]                      │
  │                         │ COMMIT (Redo 로그 Flush 완료)      │
  │                         ▼                                  │
  │                    [Committed] ──── (종료, 영구 반영)         │
  └─────────────────────────────────────────────────────────────┘
```

**핵심 포인트**: "Partially Committed"와 "Committed"의 분리가 핵심이다. [[083_dml|DML]] 연산이 [[369_logic_bomb|논리]]적으로 완료되었다고 해서 디스크에 영구 기록된 것이 아니다. 명시적 COMMIT 호출 시에만 WAL ([[236_wal_write_ahead_logging_protocol|Write-Ahead Logging]]) [[295_protocol_field_tcp_udp_icmp|프로토콜]]에 따라 [[234_redo_roll_forward_durability_recovery|Redo]] [[568_logs_distributed_logging_elk_fluentd|로그]]가 디스크에 [[212_synchronization_mechanisms|동기화]](Flush)된다.

### TCL 핵심 [[158_instruction|명령어]]와 내부 동작

| [[158_instruction|명령어]] | 역할 | 내부 동작 메커니즘 | 실무 비유 |
|:-------|:-----|:-----------------|:---------|
| **COMMIT** | [[191_transaction_concept_states|트랜잭션]] 확정 | [[234_redo_roll_forward_durability_recovery|Redo]] [[568_logs_distributed_logging_elk_fluentd|로그]] 버퍼 → 디스크 Flush, 락([[510_lock|Lock]]) 해제, [[393_undo|Undo]] 세그먼트 상태 변경 | 계약서에 최종 도장 찍기 |
| **[[313_rollback|ROLLBACK]]** | [[191_transaction_concept_states|트랜잭션]] 전체 취소 | [[393_undo|Undo]] 세그먼트 이전 [[001_dikw_pyramid|데이터]]로 버퍼 복원, 락 해제 | 작성 중이던 계약서 파기 |
| **[[200_savepoint_partial_rollback|SAVEPOINT]]** | 부분 [[658_ir_recovery|복구]] 지점 [[009_config|설정]] | 현재 SCN (System Change Number) 마킹, [[369_logic_bomb|논리]]적 [[022_snapshot_backup_architecture|스냅샷]] [[087_process_state_transition|생성]] | 게임 중간 세이브 포인트 |

### [[200_savepoint_partial_rollback|SAVEPOINT]] 내부 구조

```text
  [시간 흐름] ─────────────────────────────────────────▶

  BEGIN
    │
    ├─ INSERT 1 (row_id=1)
    │
  SAVEPOINT A ───────────── [Undo Pointer 1 기억]
    │
    ├─ INSERT 2 (row_id=2)
    │
  SAVEPOINT B ───────────── [Undo Pointer 2 기억]
    │
    ├─ INSERT 3 (row_id=3)
    │
  ROLLBACK TO SAVEPOINT A ─ INSERT 3 취소 + INSERT 2 취소
    │                        SAVEPOINT B 자동 파기됨
    │                        INSERT 1 은 유지됨
    ▼
  COMMIT ─────────────────── INSERT 1 만 영구 반영
```

SAVEPOINT는 대규모 배치(Batch) 작업에서 일부 레코드 삽입 실패 시 전체 [[098_rollback_strategy_pipeline_error_threshold|롤백]] 대신 실패 구간만 취소해 [[658_ir_recovery|복구]] 비용을 최소화하는 데 활용된다.

> 📢 **섹션 요약 비유**: 미로 [[315_exploration_exploitation|탐험]] 시 갈림길마다 분필로 화살표([[200_savepoint_partial_rollback|SAVEPOINT]])를 그려두어, 막다른 길을 만나면 미로 입구([[313_rollback|ROLLBACK]] 전체)가 아닌 **마지막 갈림길까지만** 되돌아갈 수 있는 생존 기법입니다.

## Ⅲ. 비교 및 연결

### 갱신 방식 비교: [[239_immediate_update_recovery_redo_undo|즉시 갱신]] vs [[238_deferred_update_recovery_no_undo|지연 갱신]]

```text
  ┌────────────────┬────────────────────────┬────────────────────────┐
  │    항목        │   즉시 갱신(Immediate)  │   지연 갱신(Deferred)   │
  ├────────────────┼────────────────────────┼────────────────────────┤
  │  반영 시점     │ DML 실행 즉시 버퍼 반영 │ COMMIT 호출 시까지 대기 │
  │  COMMIT 부하   │ 작음 (이미 반영됨)      │ 큼 (이때 모두 반영)     │
  │  ROLLBACK 방식 │ Undo 로그로 물리 복원   │ 버퍼·로그 폐기          │
  │  주류 DBMS     │ Oracle, MySQL, PostgreSQL│ 일부 경량 DBMS          │
  └────────────────┴────────────────────────┴────────────────────────┘
```

### [[020_ddl|DDL]] Auto-Commit 충돌: 가장 위험한 [[128_water_scrum_fall_anti_pattern|안티패턴]]

```text
  BEGIN TRANSACTION
    │
    ├─ UPDATE Emp SET salary = 0;    ← 상태: Uncommitted (롤백 가능)
    │
    ├─ CREATE TABLE temp (id INT);   ← ⚠️ DDL: 암묵적 Auto-Commit 발생!
    │                                   UPDATE는 이미 Committed → 취소 불가
    │
    └─ ROLLBACK;                     ← ❌ CREATE만 롤백, UPDATE는 이미 확정됨
```

[[188_pl_sql_t_sql_procedural|Oracle]], MySQL에서 [[020_ddl|DDL]](`CREATE`, `DROP`, `ALTER`)이 실행되면 엔진은 [[216_progress_in_synchronization|진행]] 중인 [[191_transaction_concept_states|트랜잭션]]을 강제 COMMIT한다. 비즈니스 [[083_dml|DML]] 중간에 임시 테이블을 [[087_process_state_transition|생성]]하면 의도치 않은 중간 커밋으로 [[001_dikw_pyramid|데이터]] 정합성이 완전히 붕괴된다.

> 📢 **섹션 요약 비유**: 물건을 바구니에 담다가([[083_dml|DML]]), 갑자기 바구니 자체를 새로 만들려 하면([[020_ddl|DDL]]), 계산원이 바구니 속 물건을 **강제로 결제(Auto-Commit)** 해버리는 상황과 같습니다.

## Ⅳ. 실무 적용 및 기술사 판단

### 실무 시나리오: 커밋 [[015_지연_데이터_관점|지연]]이 유발한 [[275_lock_contention_monitoring|락 경합]] 장애

이벤트 기간 동시 접속자 급증으로 전체 시스템이 멈추는 현상이 발생했다.

```text
  [장애 원인 분석]

  클라이언트 요청
       │
       ▼
  BEGIN TRANSACTION ─────────────────────────────────────────┐
    │                                                         │ 10초간
    ├─ UPDATE Order SET status = 'processing'  ← DB 락 보유  │ 락 유지
    │                                                         │
    ├─ 외부 결제 API 호출 (응답 시간: 10초)     ← 락 유지 중  │
    │                                                         │
    └─ COMMIT ──────────────────────────────────────────────┘
               락 해제

  결과: DB 커넥션 풀 고갈, 다른 요청 전원 대기 상태
```

**해결책**: 외부 [[014_api_posix|API]] 호출을 [[191_transaction_concept_states|트랜잭션]] 경계 바깥으로 이동, DB 변경 구간만 BEGIN~COMMIT으로 감싸 락 보유 시간을 ms 단위로 축소.

### [[228_batch_processing_hadoop_spark|배치 처리]] 커밋 주기 최적화

```text
  ┌─────────────────────────────────────────────────────────┐
  │  배치 100만 건 업데이트 커밋 전략 비교                   │
  ├─────────────────┬───────────────────────────────────────┤
  │  1건마다 COMMIT  │ 디스크 I/O 100만 회 → 극심한 성능 저하 │
  │  100만 건 한번에 │ Undo 테이블스페이스 고갈 → ORA-30036   │
  │  1만~5만 건 단위 │ 권장: I/O 비용과 Undo 균형점           │
  └─────────────────┴───────────────────────────────────────┘
```

### 데드락([[281_deadlock_definition|Deadlock]])과 TCL 개입

```text
  Tx A: Lock(X) 보유 ────▶ Lock(Y) 대기
                                          ← 교착 상태
  Tx B: Lock(Y) 보유 ────▶ Lock(X) 대기

  ──────────────────────────────────────────────────────
  엔진 데드락 탐지기 (Wait-For Graph 분석)
       ↓ 사이클 발견
  희생자(Victim) 선정: Tx B 강제 ROLLBACK
       ↓ 락 해제
  Tx A 정상 진행
  ──────────────────────────────────────────────────────
  ORA-00060 에러 반환 → 애플리케이션에서 Retry 로직 필수
```

> 📢 **섹션 요약 비유**: 좁은 외나무다리에서 두 차가 마주쳐 오도가도 못 할 때(데드락), 경찰(엔진)이 와서 한 대를 **강제로 후진([[313_rollback|ROLLBACK]])** 시켜 길을 뚫어주는 것과 같습니다.

### 미래 전망: [[248_distributed_transaction_multiple_nodes|분산 트랜잭션]]으로의 진화

클라우드·[[619_msa_traffic_hardware|MSA]] ([[122_msa_microservices_architecture|Microservices Architecture]]) 확산으로 단일 DB TCL 제어를 넘어선 [[248_distributed_transaction_multiple_nodes|분산 트랜잭션]] 관리가 필수화되었다.

- **[[549_2pc_two_phase_commit_limitations_msa|2PC]] ([[549_2pc_two_phase_commit_limitations_msa|Two-Phase Commit]])**: [[136_variance|분산]] 노드 전체가 COMMIT에 합의하는 고전 [[295_protocol_field_tcp_udp_icmp|프로토콜]]. 코디네이터 장애 시 블로킹 문제 존재
- **[[305_saga|Saga]] 패턴**: [[548_local_vs_distributed_transactions|로컬 트랜잭션]] + 실패 시 [[551_compensating_transaction_logical_rollback|보상 트랜잭션]]([[369_logic_bomb|논리]]적 [[313_rollback|ROLLBACK]])으로 [[136_variance|분산]] [[194_consistency_database_integrity|일관성]] 유지. 이벤트 기반 MSA에 적합

[[001_dikw_pyramid|데이터]] 엔지니어는 단일 DB의 TCL 메커니즘을 완벽히 이해하고, [[136_variance|분산]] 시스템의 [[194_consistency_database_integrity|일관성]] 유지 [[268_strategy_pattern|전략]]으로 시야를 확장해야 한다.

> 📢 **섹션 요약 비유**: TCL은 [[001_dikw_pyramid|데이터]]의 과거와 현재를 안전하게 이어주는 **마법의 타임머신**이자, 신뢰받는 디지털 거래의 든든한 보증수표입니다.

[ACID 이론 정립 (1970s)]
