## 핵심 인사이트 (3줄 요약)

> 1. **본질**: 동기식 [[344_bus|버스]] ([[010_동기식_비동기식_전송|Synchronous]] [[344_bus|Bus]])는 모든 참여 장치가 하나의 공통 클럭 ([[045_clock|Clock]])을 기준으로 같은 시점에 주소, 제어, [[001_dikw_pyramid|데이터]]를 주고받는 시간 합의형 [[344_bus|버스]] 구조다.
> 2. **가치**: 별도의 복잡한 [[396_validation|확인]]-응답 없이 정해진 [[344_bus|버스]] 사이클 ([[344_bus|Bus]] Cycle)만 맞추면 되므로 제어가 단순하고, 짧은 거리에서는 높은 [[139_throughput|처리량]]과 예측 가능한 [[015_지연_데이터_관점|지연]]시간을 얻기 쉽다.
> 3. **판단 포인트**: [[282_performance_tactics|성능]]의 핵심은 클럭을 높이는 것이 아니라, 가장 느린 장치의 [[138_response_time|응답 시간]]·클럭 스큐 ([[388_spanner_truetime_clock_skew|Clock Skew]])·배선 길이를 모두 감당할 수 있는 범위 안에서 동기성을 유지하는 데 있다.

---

## Ⅰ. 개요 및 필요성

동기식 [[344_bus|버스]] ([[010_동기식_비동기식_전송|Synchronous]] [[344_bus|Bus]])는 [[344_bus|버스]]에 연결된 장치들이 **언제 [[130_signal|신호]]를 내보내고 언제 읽을지**를 공통 클럭으로 합의한 [[344_bus|버스]] 방식이다. 즉, 중앙처리장치 (Central Processing Unit, CPU), 메모리, 주변 장치가 제각각 "준비됐나?"를 계속 묻는 대신, 클럭 에지 ([[045_clock|Clock]] Edge)가 오면 미리 약속된 동작을 수행한다.

이 방식이 필요해진 이유는 고속 장치 사이 통신에서 제어 오버헤드가 [[282_performance_tactics|성능]]을 갉아먹기 때문이다. CPU와 주기억장치가 나노초 (ns) 단위로 동작하는 환경에서는 매 전송마다 [[396_validation|확인]] [[130_signal|신호]]를 주고받는 것보다, 1사이클에는 주소를 놓고 2사이클 뒤에는 [[001_dikw_pyramid|데이터]]를 읽는 식으로 타이밍을 고정하는 편이 훨씬 효율적이다. 그래서 동기식 [[344_bus|버스]]는 특히 메인보드 내부의 짧고 빠른 경로, 예를 들어 과거의 [[365_fsb|프론트 사이드 버스]] (Front Side [[344_bus|Bus]], [[365_fsb|FSB]])나 동기식 메모리 인터페이스에서 강점을 보였다.

하지만 전제도 분명하다. 동기식 [[344_bus|버스]]는 연결된 장치들이 정해진 시간 안에 응답할 수 있어야 한다. 이 약속이 깨지면 빠른 장치는 아직 준비되지 않은 [[001_dikw_pyramid|데이터]]를 읽고, 시스템 전체는 오류나 대기 상태에 빠진다. 결국 동기식 [[344_bus|버스]]는 "빠른 [[344_bus|버스]]"이기 전에 "시간 약속이 지켜지는 [[344_bus|버스]]"다.

- **📢 섹션 요약 비유**: 동기식 [[344_bus|버스]]는 모두가 종소리에 맞춰 움직이는 단체 줄넘기와 같다. 종이 울리는 순간에 맞춰 뛰면 빠르고 질서정연하지만, 한 사람이라도 박자를 놓치면 전체 흐름이 꼬인다.

## Ⅱ. 아키텍처 및 핵심 원리

동기식 [[344_bus|버스]]의 핵심은 [[344_bus|버스]] 사이클을 미리 정의하는 것이다. 보통 마스터 장치가 주소와 읽기/[[289_cqrs_db|쓰기]] 제어를 먼저 내보내고, 슬레이브 장치는 정해진 클럭 수 안에 [[001_dikw_pyramid|데이터]]를 실어 보낸다. 따라서 제어 [[369_logic_bomb|논리]]는 단순하지만, 타이밍 예산은 더 엄격해진다.

| 구성 요소 | 역할 | 설계 포인트 |
| :-- | :-- | :-- |
| 클럭 ([[045_clock|Clock]]) | 모든 전송의 기준 시점 제공 | 주기, 지터 (Jitter), 스큐 관리 |
| 주소선 (Address Lines) | 접근 대상 지정 | 클럭 에지 전 안정화 필요 |
| 제어선 (Control Lines) | 읽기/[[289_cqrs_db|쓰기]], 유효 구간 지시 | 사이클 정의가 명확해야 함 |
| [[001_dikw_pyramid|데이터]]선 ([[001_dikw_pyramid|Data]] Lines) | 실제 [[001_dikw_pyramid|데이터]] 전달 | 셋업/홀드 시간 충족 필요 |
| 대기 상태 (Wait [[272_state_pattern|State]]) | 느린 장치 대응용 완충 | [[282_performance_tactics|성능]] 저하와 [[344_compatibility_usability|호환성]]의 절충 |

아래 그림은 동기식 [[344_bus|버스]]가 "정해진 클럭 수 뒤에 [[001_dikw_pyramid|데이터]]를 읽는다"는 사실을 보여준다.

```text
┌──────────────────────────────────────────────────────────────────────┐
│            Synchronous Bus Cycle : fixed timing contract            │
├──────────────┬──────────────┬──────────────┬──────────────┬──────────┤
│ Clock        │      C1      │      C2      │      C3      │    C4    │
├──────────────┼──────────────┼──────────────┼──────────────┼──────────┤
│ Master       │ Addr + Read  │ Hold control │ Sample data  │ Finish   │
│ Slave        │ Decode addr  │ Access data  │ Drive bus    │ Release  │
│ Data bus     │    ----      │    ----      │  VALID DATA  │   ----   │
├──────────────┴──────────────┴──────────────┴──────────────┴──────────┤
│ Rule: data must become valid by the agreed sampling edge.           │
└──────────────────────────────────────────────────────────────────────┘
```

이 구조에서 가장 중요한 식은 간단하다. **[[133_clock_cycle_time|클럭 주기]] ≥ 주소 해석 시간 + 장치 [[138_response_time|응답 시간]] + 배선 [[016_전파_지연|전파 지연]] + 안전 마진**이어야 한다. 메모리가 이 시간 안에 [[001_dikw_pyramid|데이터]]를 올리지 못하면, 마스터는 잘못된 값을 읽게 된다. 그래서 실제 시스템은 느린 장치를 위해 대기 상태를 삽입하거나, 아예 빠른 [[344_bus|버스]]와 느린 [[344_bus|버스]]를 분리한다.

또 하나의 핵심은 물리 한계다. 클럭이 빨라질수록 배선 길이 차이에서 생기는 클럭 스큐가 더 치명적이 된다. 인쇄회로기판 (Printed Circuit Board, PCB) 위에서 몇 밀리미터 차이도 고속 인터페이스에서는 무시하기 어렵기 때문에, 동기식 [[344_bus|버스]]는 [[369_logic_bomb|논리]] 설계만이 아니라 배선 정합까지 포함한 타이밍 공학이다.

- **📢 섹션 요약 비유**: 동기식 [[344_bus|버스]]는 벨트 속도가 정해진 공장 컨베이어와 같다. 작업자들이 벨트 박자를 정확히 알고 있으면 빠르게 물건을 넘길 수 있지만, 누군가 제시간에 올려놓지 못하면 다음 공정이 빈손으로 지나가 버린다.

## Ⅲ. 비교 및 연결

동기식 [[344_bus|버스]]의 경계는 [[349_asynchronous_bus|비동기식 버스]] ([[349_asynchronous_bus|Asynchronous Bus]])와 비교할 때 가장 또렷해진다. 동기식은 공통 시간축이 있는 대신 거리와 속도 차이에 약하고, 비동기식은 [[396_validation|확인]]-응답 기반이라 유연하지만 제어 오버헤드가 크다.

| 항목 | 동기식 [[344_bus|버스]] | [[349_asynchronous_bus|비동기식 버스]] |
| :-- | :-- | :-- |
| 시간 기준 | 공통 클럭 | 요청-응답 핸드셰이크 |
| 장점 | 높은 [[139_throughput|처리량]], 단순한 제어, 예측 가능한 사이클 | 이기종 장치 수용, 거리 확장, 유연한 응답 |
| 약점 | 가장 느린 장치에 영향, 클럭 스큐 민감 | 오버헤드 증가, [[015_지연_데이터_관점|지연]]시간 변동 큼 |
| 적합 환경 | 칩 내부, 메모리 [[344_bus|버스]], 짧은 보드 레벨 연결 | 외부 장치, 장거리 링크, 저속 혼재 환경 |

이 비교는 다른 컴퓨터구조 개념과도 바로 이어진다. 동기식 [[344_bus|버스]]는 동기식 동적 램 ([[010_동기식_비동기식_전송|Synchronous]] Dynamic Random Access Memory, [[252_sdram|SDRAM]])과 이중 [[001_dikw_pyramid|데이터]] 전송률 ([[253_ddr_sdram|Double Data Rate]], DDR) 계열 메모리의 기반 철학이며, 동시에 멀티클럭 [[064_relation_domain|도메인]]과 [[344_bus|버스]] [[260_bridge_pattern_abstraction_implementation|브리지]] 설계의 출발점이기도 하다. 반대로 [[349_asynchronous_bus|비동기식 버스]]는 [[344_compatibility_usability|호환성]] 중심의 입출력 (Input/Output, I/O) 인터페이스 사고방식과 닿아 있다.

즉, 동기식 [[344_bus|버스]]를 이해한다는 것은 단순히 "클럭이 있다"를 외우는 것이 아니라, **공통 시간축이 [[282_performance_tactics|성능]]을 올리는 대신 시스템 경계를 더 엄격하게 만든다**는 점을 이해하는 것이다. 그래서 현대 시스템은 빠른 구간은 동기식으로 묶고, 경계에서는 [[260_bridge_pattern_abstraction_implementation|브리지]]와 버퍼로 비동기성을 흡수하는 계층형 구조를 선택한다.

- **📢 섹션 요약 비유**: 동기식은 군악대 행진처럼 모두가 같은 박자로 움직이는 방식이고, 비동기식은 서로 눈짓을 하며 합을 맞추는 소규모 합주와 같다. 전자는 웅장하고 빠르지만 규율이 필요하고, 후자는 유연하지만 템포가 흔들리기 쉽다.

## Ⅳ. 실무 적용 및 기술사 판단

실무에서 동기식 [[344_bus|버스]]를 쓸지 판단할 때는 "클럭 공유가 가능한가"를 먼저 본다. 장치 간 거리가 짧고, [[138_response_time|응답 시간]] 편차가 작고, 높은 대역폭이 우선이라면 동기식이 유리하다. 반대로 장치 속도가 제각각이거나 배선 거리가 길다면, 클럭 분배 비용과 타이밍 [[395_verification_process_review|검증]] 비용이 급격히 커진다.

### 실무 판단 체크포인트

1. **[[138_response_time|응답 시간]] 상한**: 가장 느린 장치도 정해진 사이클 안에 응답할 수 있는가?
2. **배선 길이 제어**: 보드 배선 길이와 스큐를 관리할 수 있는가?
3. **대기 상태 허용도**: 느린 장치를 위해 wait state를 넣어도 전체 [[282_performance_tactics|성능]] 목표를 만족하는가?
4. **[[064_relation_domain|도메인]] 분리 필요성**: 고속 [[344_bus|버스]]와 저속 [[344_bus|버스]]를 [[260_bridge_pattern_abstraction_implementation|브리지]]로 분리해야 하는가?

대표 사례는 [[252_sdram|SDRAM]] 계열 메모리다. 메모리 컨트롤러와 메모리는 같은 클럭 기준으로 명령과 [[001_dikw_pyramid|데이터]]를 주고받기 때문에 연속 [[344_bus|버스]]트 전송에서 높은 효율을 낸다. 다만 속도가 올라갈수록 배선 정합, 타이밍 캘리브레이션, [[130_signal|신호]] [[003_integrity|무결성]] 관리가 필수이며, 이 부담을 감당하지 못하면 이론 대역폭은 실제 [[282_performance_tactics|성능]]으로 이어지지 않는다.

안티패턴도 분명하다. 첫째, 느린 장치를 고속 동기식 [[344_bus|버스]]에 무리하게 직접 매다는 설계다. 이 경우 wait state가 반복되어 빠른 [[344_bus|버스]]의 장점이 사라진다. 둘째, 클럭 주파수만 높이고 보드 레이아웃과 타이밍 폐쇄를 가볍게 보는 접근이다. 이런 설계는 벤치마크보다 현장 장애를 먼저 만든다.

- **📢 섹션 요약 비유**: 동기식 [[344_bus|버스]] 설계는 고속도로 제한속도 표지판만 세우는 일이 아니다. 노면 상태, 차 간격, 진입로 길이까지 맞아야 진짜로 그 속도를 안전하게 낼 수 있다.

## Ⅴ. 기대효과 및 결론

동기식 [[344_bus|버스]]의 가장 큰 효과는 예측 가능성이다. [[344_bus|버스]] 사이클이 고정되면 [[282_performance_tactics|성능]] 분석, [[395_verification_process_review|검증]], 파이프라인 설계가 쉬워지고, 짧은 구간에서는 매우 높은 [[139_throughput|처리량]]을 안정적으로 낼 수 있다. 그래서 프로세서 내부 인터커넥트와 메모리 인터페이스는 오랫동안 동기식 철학을 중심으로 발전해 왔다.

하지만 한계도 분명하다. 클럭을 공유해야 하므로 물리적 거리 확장에 불리하고, 서로 다른 속도의 장치를 자연스럽게 수용하기 어렵다. 결국 현대 아키텍처는 "모든 곳을 동기식으로 통일"하지 않고, 고속 핵심 구간에서만 동기식을 강하게 적용한 뒤 경계에서는 [[260_bridge_pattern_abstraction_implementation|브리지]], 버퍼, 패킷 기반 인터커넥트로 문제를 푼다.

따라서 동기식 [[344_bus|버스]]는 "무조건 빠른 [[344_bus|버스]]"로 기억하기보다, **공통 시간 기준을 무기로 단순성과 고속성을 얻는 대신, 물리 제약과 [[344_compatibility_usability|호환성]] 비용을 떠안는 구조**로 기억하는 것이 정확하다. 기술사 관점에서도 핵심은 장점 암기가 아니라, 어디까지 동기성을 유지하고 어디서 경계를 끊을지 판단하는 데 있다.

- **📢 섹션 요약 비유**: 좋은 지휘자는 무조건 빠른 템포만 고집하지 않는다. 모든 연주자가 정확히 맞출 수 있는 범위 안에서 템포를 정해야 합주가 아름답게 완성된다.

### 👶 어린이를 위한 3줄 비유 설명

1. 동기식 [[344_bus|버스]]는 친구들이 모두 같은 북소리를 듣고 동시에 움직이는 놀이예요.
2. 북소리에 맞추면 아주 빨리 물건을 주고받을 수 있지만, 느린 친구가 있으면 모두 그 친구 속도에 맞춰야 해요.
3. 그래서 가까이 있는 빠른 친구들끼리는 이 방법이 좋고, 멀리 있거나 느린 친구와는 다른 방법이 더 잘 맞아요.
