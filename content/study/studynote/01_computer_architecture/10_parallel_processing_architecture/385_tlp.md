## 핵심 인사이트 (3줄 요약)

> 1. **본질**: [[092_thread_lwp|스레드]] 레벨 [[430_index_fast_full_scan|병렬]]성 (TLP, Thread-Level Parallelism)은 하나의 큰 프로그램을 여러 실행 흐름으로 나누어, 여러 코어 또는 여러 하드웨어 [[092_thread_lwp|스레드]]가 동시에 처리하게 만드는 [[430_index_fast_full_scan|병렬]]성이다.
> 2. **가치**: [[158_instruction|명령어]] 레벨 [[430_index_fast_full_scan|병렬]]성 (ILP, Instruction-Level Parallelism)이 [[001_dikw_pyramid|데이터]] 의존성과 [[231_branch_prediction|분기 예측]] 한계에 막힐 때, TLP는 "다른 일을 동시에 돌리는 방식"으로 처리량을 계속 확장한다.
> 3. **판단 포인트**: TLP의 성패는 코어 수가 아니라 작업 분해, [[212_synchronization_mechanisms|동기화]] 비용, 메모리 경합, [[001_operating_system_purpose|운영체제]] 스케줄링 정책을 함께 제어할 수 있느냐에 달려 있다.

## Ⅰ. 개요 및 필요성

[[092_thread_lwp|스레드]] 레벨 [[430_index_fast_full_scan|병렬]]성 (TLP, Thread-Level Parallelism)은 여러 [[092_thread_lwp|스레드]]가 서로 다른 실행 문맥을 유지한 채 동시에 진행되도록 만드는 [[430_index_fast_full_scan|병렬]] 처리 방식이다. 핵심은 한 [[092_thread_lwp|스레드]] 안에서 [[158_instruction|명령어]] 순서를 더 공격적으로 재배치하는 것이 아니라, **독립성이 있는 실행 흐름 자체를 여러 개 준비해 하드웨어의 빈 시간을 메우는 것**이다.

이 개념이 중요해진 이유는 단일 코어의 클럭 상승과 ILP만으로는 [[282_performance_tactics|성능]] 향상을 계속 끌어내기 어려워졌기 때문이다. 한 [[092_thread_lwp|스레드]]는 메모리 접근 [[015_지연_데이터_관점|지연]], 분기 실패, 잠금 대기 때문에 자주 멈추는데, 그 순간 연산 장치가 놀게 된다. TLP는 바로 그 빈틈에 다른 [[092_thread_lwp|스레드]]를 투입해 프로세서 활용률을 높인다.

특히 웹 서버, [[002_database_definition|데이터베이스]], 렌더링, 과학 계산처럼 독립 요청이나 작업 조각이 많이 존재하는 환경에서는 "한 일을 빨리 끝내는 능력"보다 "여러 일을 동시에 처리하는 능력"이 더 중요해진다. TLP가 없으면 멀티코어 프로세서의 물리적 자원은 충분해도, 실제 시스템 처리량은 단일 [[092_thread_lwp|스레드]] 수준에 머무르게 된다.

```text
┌──────────────────────────────────────────────────────────────────────┐
│                 TLP가 필요한 이유: 유휴 시간 메우기                 │
├──────────────────────────────────────────────────────────────────────┤
│ 스레드 A만 실행할 때                                                 │
│ [계산] ─ [계산] ─ [메모리 대기] ─ [계산] ─ [분기 실패 복구]          │
│                      ▲                    ▲                          │
│                      │                    │                          │
│                 코어 일부 유휴        파이프라인 일부 유휴           │
├──────────────────────────────────────────────────────────────────────┤
│ 스레드 A, B를 함께 실행할 때                                         │
│ A가 대기하면 ───────────────▶ B를 실행                               │
│ B가 대기하면 ───────────────▶ A 또는 C를 실행                        │
│ 결과: 같은 하드웨어로 더 높은 처리량 확보                            │
└──────────────────────────────────────────────────────────────────────┘
```

이 그림의 핵심은 TLP가 "모든 [[092_thread_lwp|스레드]]를 항상 완전히 동시에 끝내는 기술"이 아니라, **한 [[092_thread_lwp|스레드]]의 정지 시간을 다른 [[092_thread_lwp|스레드]]의 진행으로 덮어 처리량을 올리는 기술**이라는 점이다.

- **📢 섹션 요약 비유**: 한 명이 계산하다가 자료를 찾느라 멈추면 교실이 조용해지지만, 여러 학생이 각자 숙제를 하면 누군가 멈춘 순간에도 다른 학생은 계속 풀 수 있다. TLP는 교실 전체가 쉬지 않게 만드는 운영 방식이다.

## Ⅱ. 아키텍처 및 핵심 원리

TLP는 소프트웨어의 [[092_thread_lwp|스레드]]와 하드웨어의 실행 자원이 만나는 지점에서 구현된다. [[001_operating_system_purpose|운영체제]] (OS, [[001_operating_system_purpose|Operating System]])는 실행 가능한 [[092_thread_lwp|스레드]]를 준비하고, 프로세서는 이를 코어와 하드웨어 [[092_thread_lwp|스레드]] 문맥에 배치한다. 이때 중요한 것은 **문맥은 분리하되, 연산 장치와 캐시는 어느 수준까지 공유할지**를 정하는 일이다.

대표 구현 방식은 굵게 보면 세 가지다. 첫째, 여러 코어를 두는 멀티코어 구조는 가장 직관적인 TLP 구현이다. 둘째, 미세 또는 조밀한 [[397_multithreading|멀티스레딩]]은 클록마다 다른 [[092_thread_lwp|스레드]]를 번갈아 투입해 메모리 [[015_지연_데이터_관점|지연]]을 숨긴다. 셋째, [[400_smt|동시 멀티스레딩]] ([[400_smt|SMT]], Simultaneous [[095_multithreading_benefits|Multithreading]])은 하나의 코어 안에서 같은 사이클에 여러 [[092_thread_lwp|스레드]]의 [[158_instruction|명령어]]를 함께 발행해 유휴 실행 슬롯을 채운다.

| 구현 방식 | 핵심 원리 | 강점 | 한계 |
| :-- | :-- | :-- | :-- |
| 멀티코어 (Multicore) | 독립 코어에 서로 다른 [[092_thread_lwp|스레드]] 배치 | 확실한 [[430_index_fast_full_scan|병렬]] 실행, 예측 용이 | 면적·전력 증가, [[402_cache_coherence|캐시 일관성]] 비용 |
| [[399_fine_grained_multithreading|세밀한 멀티스레딩]] ([[399_fine_grained_multithreading|Fine-Grained]] [[095_multithreading_benefits|Multithreading]]) | 짧은 주기로 [[092_thread_lwp|스레드]] 전환 | 메모리 [[015_지연_데이터_관점|지연]] 은닉에 강함 | 단일 [[092_thread_lwp|스레드]] 체감 [[282_performance_tactics|성능]] 저하 가능 |
| [[400_smt|동시 멀티스레딩]] ([[400_smt|SMT]], Simultaneous [[095_multithreading_benefits|Multithreading]]) | 한 코어의 남는 발행 슬롯을 다른 [[092_thread_lwp|스레드]]로 채움 | 하드웨어 활용률 향상 | 캐시·실행 유닛 경합, 보안 이슈 |

아래 그림은 멀티코어와 SMT가 어떻게 다른 수준에서 TLP를 만드는지 보여준다. 중요한 차이는 **멀티코어는 물리 자원을 늘리는 방식**이고, **SMT는 같은 물리 자원의 빈틈을 재활용하는 방식**이라는 점이다.

```text
┌──────────────────────────────────────────────────────────────────────┐
│                    TLP의 하드웨어 수용 구조                          │
├──────────────────────────────────────────────────────────────────────┤
│ 소프트웨어 스레드                                                    │
│   T0        T1        T2        T3        T4        T5               │
│    │         │         │         │         │         │               │
│    └────┬────┴────┬────┘         └────┬────┴────┬────┘               │
│         ▼         ▼                    ▼         ▼                    │
│   ┌───────────┐ ┌───────────┐   ┌───────────┐ ┌───────────┐          │
│   │ Core 0    │ │ Core 1    │   │ Core 0    │ │ Core 1    │          │
│   │ 1 thread  │ │ 1 thread  │   │ SMT x2    │ │ SMT x2    │          │
│   └───────────┘ └───────────┘   └───────────┘ └───────────┘          │
│      멀티코어 구조                  멀티코어 + SMT 구조               │
├──────────────────────────────────────────────────────────────────────┤
│ 왼쪽: 코어 수만큼 병렬성 확보                                         │
│ 오른쪽: 코어 수 + 코어 내부 빈 슬롯 활용                              │
└──────────────────────────────────────────────────────────────────────┘
```

하지만 [[092_thread_lwp|스레드]] 수를 늘린다고 무조건 [[282_performance_tactics|성능]]이 오르지는 않는다. [[092_thread_lwp|스레드]]가 공유 [[001_dikw_pyramid|데이터]]에 자주 접근하면 [[402_cache_coherence|캐시 일관성]] ([[402_cache_coherence|Cache Coherence]]) 비용이 커지고, 잠금이 많으면 대기 시간이 [[430_index_fast_full_scan|병렬]]성을 잠식한다. 결국 TLP의 핵심 원리는 "[[092_thread_lwp|스레드]]를 많이 만드는 것"이 아니라, **충분히 독립적인 [[092_thread_lwp|스레드]]를 적절한 하드웨어 자원에 매핑하는 것**이다.

- **📢 섹션 요약 비유**: 멀티코어는 주방을 여러 개 만드는 방식이고, SMT는 한 주방의 빈 화구를 다른 요리사가 같이 쓰게 하는 방식이다. 요리사는 늘어도 냄비와 조리대가 자꾸 겹치면 오히려 엉키기 쉽다.

## Ⅲ. 비교 및 연결

TLP를 제대로 이해하려면 다른 [[430_index_fast_full_scan|병렬]]성과의 경계를 분명히 봐야 한다. ILP가 **한 [[092_thread_lwp|스레드]] 내부**에서 [[158_instruction|명령어]] 겹침을 늘리는 기술이라면, TLP는 **여러 [[092_thread_lwp|스레드]] 사이**의 동시 실행을 다룬다. 또 [[386_dlp|데이터 레벨 병렬성]] ([[386_dlp|DLP]], Data-Level Parallelism)은 같은 명령을 많은 [[001_dikw_pyramid|데이터]]에 반복 적용하는 방식이므로, "서로 다른 일감"을 나누는 TLP와 출발점이 다르다.

| 구분 | ILP | TLP | [[386_dlp|DLP]] |
| :-- | :-- | :-- | :-- |
| [[430_index_fast_full_scan|병렬]]화 대상 | 한 [[092_thread_lwp|스레드]] 내부 [[158_instruction|명령어]] | 여러 [[092_thread_lwp|스레드]]/작업 | 동일 연산의 다수 [[001_dikw_pyramid|데이터]] |
| 대표 하드웨어 | 파이프라인, 슈퍼스칼라 | 멀티코어, [[400_smt|SMT]] | [[370_simd|SIMD]], [[418_gpu|GPU]] |
| 병목 | [[001_dikw_pyramid|데이터]] 의존성, 분기 | [[212_synchronization_mechanisms|동기화]], 스케줄링, 캐시 경합 | 메모리 정렬, 분기 발산 |
| 잘 맞는 문제 | 순차 코드 가속 | 다중 요청·다중 작업 | 벡터·행렬 연산 |

또한 TLP는 [[001_operating_system_purpose|운영체제]]와 메모리 구조의 영향을 강하게 받는다. OS 스케줄러가 [[092_thread_lwp|스레드]]를 자주 다른 코어로 옮기면 캐시 지역성 (Locality)이 깨지고, [[377_numa_allocation|NUMA]] ([[377_numa_allocation|Non-Uniform Memory Access]]) 구조에서는 같은 [[092_thread_lwp|스레드]]라도 어느 메모리를 참조하느냐에 따라 [[015_지연_데이터_관점|지연]]이 달라진다. 즉, TLP는 단순히 CPU 코어 수의 문제가 아니라 스케줄링과 메모리 배치 전략까지 포함하는 시스템 문제다.

[[430_index_fast_full_scan|병렬]]성의 상한을 설명하는 데는 암달의 법칙 (Amdahl's Law)도 중요하다. 전체 작업 중 [[149_serial_communication_rs232_rs485|직렬]] 구간이 [[489_raid_10_hybrid|10]]% 남아 있다면, 코어를 무한히 늘려도 속도 향상은 10배를 넘기 어렵다. 따라서 TLP는 "[[430_index_fast_full_scan|병렬]] 실행 가능 부분을 얼마나 크게 만들 수 있는가"와 "[[149_serial_communication_rs232_rs485|직렬]]·공유 구간을 얼마나 줄일 수 있는가"를 함께 봐야 한다.

- **📢 섹션 요약 비유**: ILP가 한 사람이 손발을 더 바쁘게 쓰는 기술이라면, TLP는 사람 수를 늘리는 기술이고, DLP는 같은 동작을 여러 물건에 한꺼번에 적용하는 기계다. 사람을 많이 모아도 출입문 하나에 모두 걸리면 줄은 그대로 길다.

## Ⅳ. 실무 적용 및 기술사 판단

실무에서 TLP를 설계할 때 가장 먼저 해야 할 질문은 "이 작업이 정말 [[092_thread_lwp|스레드]]로 나뉠 수 있는가"다. CPU 바운드 (CPU-bound) 작업은 보통 코어 수에 가까운 [[092_thread_lwp|스레드]] 수가 유리하고, 입출력 바운드 (I/O-bound) 작업은 대기 시간이 많아 더 많은 [[092_thread_lwp|스레드]]를 허용할 수 있다. 하지만 이것도 단순 공식이 아니라, 락 경합과 큐 대기 시간을 측정해 조정해야 한다.

예를 들어 웹 서버는 요청 단위 [[430_index_fast_full_scan|병렬]]성이 풍부해 TLP의 효과를 크게 본다. 반면 공유 [[059_counter|카운터]], 전역 캐시, 단일 [[002_database_definition|데이터베이스]] 잠금에 지나치게 의존하면 [[092_thread_lwp|스레드]] 수를 늘릴수록 경쟁만 심해지고 처리량은 정체된다. 이때는 [[092_thread_lwp|스레드]] 추가보다 작업 큐 분리, 락 세분화, 불변 [[001_dikw_pyramid|데이터]] 활용, [[280_sharding|샤딩]] 같은 구조 개선이 더 큰 효과를 낸다.

### 적용 판단 [[435_checklist_based_testing|체크리스트]]

1. 작업이 독립 [[092_thread_lwp|스레드]]로 분해 가능한가?
2. 공유 자원 접근 빈도가 높지 않은가?
3. [[211_context_switch|문맥 교환]] ([[211_context_switch|Context Switch]]) 비용이 실제 작업 시간보다 커지지 않는가?
4. [[377_numa_allocation|NUMA]] 환경이라면 [[092_thread_lwp|스레드]]와 메모리 배치를 함께 묶었는가?
5. [[400_smt|SMT]] 사용 시 [[282_performance_tactics|성능]] 이득이 캐시 경합·보안 리스크보다 큰가?

### 대표 [[128_water_scrum_fall_anti_pattern|안티패턴]]

- 코어 8개 시스템에서 CPU 바운드 작업에 [[092_thread_lwp|스레드]] 200개를 두는 설계
- 작은 임계 구역을 넘어 큰 비즈니스 로직 전체를 하나의 락으로 감싸는 설계
- [[430_index_fast_full_scan|병렬]]화 비용 측정 없이 "멀티스레드면 무조건 빠르다"고 가정하는 설계

```text
┌──────────────────────────────────────────────────────────────┐
│                 TLP 도입 판단 흐름                           │
├──────────────────────────────────────────────────────────────┤
│ 작업 분해 가능?                                               │
│   ├─ 아니오 ──▶ 단일 스레드 최적화 또는 알고리즘 개선        │
│   └─ 예                                                       │
│        │                                                      │
│        ▼                                                      │
│ 공유 자원 경합 큼?                                            │
│   ├─ 예 ──────▶ 락 축소, 큐 분리, 데이터 분할 우선            │
│   └─ 아니오                                                   │
│        │                                                      │
│        ▼                                                      │
│ 대기 시간이 큼?                                               │
│   ├─ 예 ──────▶ I/O 중심 TLP, 비동기 모델 검토               │
│   └─ 아니오 ──▶ 코어 수 기반 CPU 중심 TLP 적용               │
└──────────────────────────────────────────────────────────────┘
```

기술사 답안에서는 "멀티코어라서 TLP를 쓴다"보다, **어떤 워크로드에서 어떤 병목을 숨기기 위해 TLP를 쓰는지**를 말해야 한다. [[282_performance_tactics|성능]] 향상보다 먼저 [[430_index_fast_full_scan|병렬]]화 가능한 범위, [[212_synchronization_mechanisms|동기화]] 비용, 메모리 계층 영향까지 함께 제시해야 높은 완성도의 답안이 된다.

- **📢 섹션 요약 비유**: 점원이 적어서 줄이 길면 사람을 더 세우는 게 맞지만, 계산대 하나 때문에 막히는 상황이면 점원을 늘려도 소용없다. TLP 튜닝은 "사람 수"보다 "어디서 줄이 막히는지"를 먼저 보는 일이다.

---

## Ⅴ. 기대효과 및 결론

TLP의 가장 큰 효과는 프로세서의 유휴 시간을 줄여 시스템 처리량을 높인다는 데 있다. 멀티코어 서버가 많은 요청을 동시에 처리하고, 과학 계산이 큰 문제를 여러 조각으로 나눠 수행하며, 사용자 환경에서 여러 애플리케이션이 동시에 반응할 수 있는 기반도 여기에 있다. 즉, TLP는 현대 컴퓨터가 "한 번에 한 일만 하는 기계"에서 "여러 일을 꾸준히 처리하는 시스템"으로 넘어가게 만든 핵심 축이다.

그러나 TLP는 만능이 아니다. [[430_index_fast_full_scan|병렬]]화 자체가 오버헤드이며, 공유 자원이 많거나 [[149_serial_communication_rs232_rs485|직렬]] 구간이 크면 기대 효과가 급격히 줄어든다. 또한 [[092_thread_lwp|스레드]] 안전성, 메모리 [[194_consistency_database_integrity|일관성]], 디버깅 난이도, 재현 어려운 경쟁 조건까지 함께 따라온다.

앞으로도 TLP는 멀티코어 확장, 경량 [[092_thread_lwp|스레드]], 비동기 런타임, 이종 프로세서와 결합하며 계속 중요해질 것이다. 다만 기억해야 할 핵심은 하나다. **TLP는 [[092_thread_lwp|스레드]]를 많이 만드는 기술이 아니라, 독립 작업을 하드웨어가 쉬지 않도록 배치하는 설계 기술**이다.

- **📢 섹션 요약 비유**: TLP는 운동장에 사람만 많이 세우는 일이 아니라, 서로 부딪히지 않게 코스를 나눠 달리게 만드는 운영이다. 코스가 잘 나뉘면 모두가 빨라지고, 얽히면 사람만 많아진다.

### 📈 관련 키워드 및 발전 흐름도

```text
단일 코어 성능 향상 중심
        │
        ▼
명령어 레벨 병렬성 (ILP, Instruction-Level Parallelism)
        │
        ▼
스레드 레벨 병렬성 (TLP, Thread-Level Parallelism)
        │
        ├─▶ 멀티코어 (Multicore)
        │
        ├─▶ 동시 멀티스레딩 (SMT, Simultaneous Multithreading)
        │
        ▼
NUMA 기반 대규모 병렬 시스템
        │
        ▼
경량 스레드 · 비동기 런타임 · 이종 병렬 처리
```

이 흐름은 "단일 [[092_thread_lwp|스레드]] 내부 최적화 → 여러 [[092_thread_lwp|스레드]] 동시 실행 → 코어·메모리 구조 확장 → 소프트웨어 런타임 진화"로 이어지는 발전 방향을 보여준다.

### 👶 어린이를 위한 3줄 비유 설명

1. TLP는 숙제를 혼자 다 하는 대신, 여러 친구가 다른 문제를 나눠 동시에 푸는 방법이에요.
2. 어떤 친구가 잠깐 멈춰도 다른 친구가 계속 풀기 때문에 전체 숙제가 더 빨리 끝나요.
3. 하지만 모두가 지우개 하나만 같이 쓰면 싸우느라 느려지니, 나눌 수 있는 일을 잘 고르는 게 중요해요.
