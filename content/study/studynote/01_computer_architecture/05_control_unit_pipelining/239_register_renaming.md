## 핵심 인사이트 (3줄 요약)

> 1. **본질**: [[057_register|레지스터]] 리네이밍 ([[175_register_addressing|Register]] Renaming)은 프로그램이 보는 적은 수의 [[369_logic_bomb|논리]] [[057_register|레지스터]] 이름을, 하드웨어 내부의 더 많은 물리 [[057_register|레지스터]] 번호로 동적으로 치환해 **이름 충돌과 실제 [[001_dikw_pyramid|데이터]] 저장 공간을 분리**하는 기술이다.
> 2. **가치**: 이 분리 덕분에 [[238_out_of_order_execution|비순차 실행]] (Out-of-Order Execution, OoO) 코어는 읽기 후 [[289_cqrs_db|쓰기]] ([[226_war|Write After Read]], [[226_war|WAR]]), [[289_cqrs_db|쓰기]] 후 [[289_cqrs_db|쓰기]] ([[227_waw|Write After Write]], [[227_waw|WAW]]) 같은 가짜 의존성을 제거하고 [[158_instruction|명령어]] 수준 [[430_index_fast_full_scan|병렬]]성 ([[158_instruction|Instruction]]-Level Parallelism, ILP)을 크게 늘린다.
> 3. **판단 포인트**: 리네이밍은 [[282_performance_tactics|성능]]을 높이지만, 물리 [[057_register|레지스터]] 수·[[658_ir_recovery|복구]] 방식·전력 비용이 함께 따라오므로 "얼마나 넓게 추측하고 얼마나 빨리 되돌릴 것인가"가 설계의 핵심이다.

---

## Ⅰ. 개요 및 필요성

[[057_register|레지스터]] 리네이밍은 **같은 이름을 쓰더라도 서로 다른 저장 공간을 배정해 의존성을 다시 정의하는 기법**이다. 프로그램은 여전히 `R1`, `R2` 같은 소수의 아키텍처 [[057_register|레지스터]]만 본다. 하지만 CPU (Central Processing Unit) 내부는 이 이름을 그대로 믿지 않고, [[158_instruction|명령어]]가 들어올 때마다 더 넓은 물리 [[057_register|레지스터]] 풀에서 실제 저장 위치를 새로 배정한다.

이 기술이 필요한 이유는 파이프라인 병목의 상당수가 "계산이 아직 안 끝났다"가 아니라 "이름이 겹친다"에서 생기기 때문이다. 예를 들어 앞 [[158_instruction|명령어]]가 `R1`을 읽는 동안 뒤 [[158_instruction|명령어]]가 새로운 값을 다시 `R1`에 쓰려 하면, 순차 파이프라인은 둘을 충돌로 본다. 그러나 실제로는 앞 [[158_instruction|명령어]]가 과거의 `R1`만 읽으면 되고, 뒤 [[158_instruction|명령어]]는 미래의 `R1`을 만들면 되므로 저장 공간만 분리하면 동시에 진행할 수 있다.

특히 가시 [[057_register|레지스터]] 수가 적은 [[158_instruction|명령어]] 집합 구조 ([[157_isa|Instruction Set Architecture]], [[157_isa|ISA]])에서는 리네이밍의 효과가 더 크다. x86처럼 프로그램이 볼 수 있는 [[057_register|레지스터]] 수가 제한된 환경에서는 컴파일러만으로 가짜 의존성을 충분히 없애기 어렵다. 그래서 현대 고성능 코어는 프런트엔드에서 이름을 다시 붙여, 겉으로는 오래된 ISA를 유지하면서 내부에서는 훨씬 넓은 실행 창을 확보한다.

- **📢 섹션 요약 비유**: 같은 사번을 가진 직원이 한 명뿐이면 업무가 겹칠 때마다 줄을 서야 한다. 리네이밍은 인사팀이 내부적으로 임시 사번을 새로 발급해, 겉보기 직함은 같아도 실제 업무는 동시에 처리하게 만드는 방식이다.

## Ⅱ. 아키텍처 및 핵심 원리

리네이밍은 보통 디코드 이후, 발행 이전 단계에서 수행된다. 이때 핵심 구성요소는 아키텍처 [[057_register|레지스터]] [[501_file_definition_logical_record|파일]] (Architectural [[175_register_addressing|Register]] [[501_file_definition_logical_record|File]], ARF), 물리 [[057_register|레지스터]] [[501_file_definition_logical_record|파일]] (Physical [[175_register_addressing|Register]] [[501_file_definition_logical_record|File]], PRF), [[057_register|레지스터]] 별칭 테이블 ([[175_register_addressing|Register]] Alias Table, RAT), 프리 리스트 (Free List), [[240_reorder_buffer|재주문 버퍼]] ([[240_reorder_buffer|Reorder Buffer]], ROB)다. ARF는 프로그램이 약속한 이름의 집합이고, PRF는 실제 값이 저장되는 공간이며, RAT는 "현재 `R1`의 최신 값은 `P37`에 있다" 같은 매핑 정보를 유지한다.

아래 그림은 새 목적 [[057_register|레지스터]]가 등장할 때 매핑이 어떻게 바뀌고, 언제 이전 물리 [[057_register|레지스터]]가 해제되는지를 보여준다.

```text
┌──────────────────────────────────────────────────────────────────────────────┐
│               리네이밍의 핵심 흐름: 이름은 유지, 저장 위치만 교체            │
├──────────────────────────────────────────────────────────────────────────────┤
│ 명령어: ADD R1, R2, R3                                                      │
│          │                                                                   │
│          ▼                                                                   │
│ RAT 조회: R2 -> P08, R3 -> P11, 기존 R1 -> P05                              │
│          │                                                                   │
│          ▼                                                                   │
│ Free List에서 새 PRF 할당: P19                                               │
│          │                                                                   │
│          ▼                                                                   │
│ 리네임 결과: ADD P19, P08, P11                                               │
│          │                                                                   │
│          ├─ RAT 갱신: R1 -> P19                                               │
│          └─ ROB 기록: "이전 R1 = P05, 새 R1 = P19"                          │
│                                                                              │
│ Commit 시점: 명령어가 안전하게 완료되면 P05 반환 -> Free List 복귀           │
└──────────────────────────────────────────────────────────────────────────────┘
```

이 구조에서 중요한 것은 **소스는 현재 매핑을 읽고, 목적지는 새 물리 [[057_register|레지스터]]를 받는다는 점**이다. 그래서 읽기 후 [[289_cqrs_db|쓰기]] ([[226_war|WAR]])와 [[289_cqrs_db|쓰기]] 후 [[289_cqrs_db|쓰기]] ([[227_waw|WAW]])는 이름 수준에서만 존재하던 충돌로 바뀌고, 실제 저장 위치가 달라지면서 사라진다. 반면 읽기 후 [[289_cqrs_db|쓰기]] ([[225_raw|Read After Write]], [[225_raw|RAW]])는 앞선 연산 결과 자체가 필요하므로 여전히 남는다. 즉 리네이밍은 모든 의존성을 없애는 기술이 아니라, **가짜 의존성만 정밀하게 제거하는 기술**이다.

실제 구현에서는 [[231_branch_prediction|분기 예측]] 실패나 예외 상황에 대비한 [[658_ir_recovery|복구]]도 중요하다. 이를 위해 리네이밍 시점의 RAT [[022_snapshot_backup_architecture|스냅샷]]을 저장하거나, ROB에 이전 매핑을 기록해 롤백한다. [[282_performance_tactics|성능]] 좋은 코어일수록 "빨리 이름을 붙이는 속도"만큼 "빨리 옛 상태로 되돌리는 속도"도 중요하다.

| 구성 요소 | 역할 | 설계에서 보는 포인트 |
| :--- | :--- | :--- |
| RAT | [[369_logic_bomb|논리]] [[057_register|레지스터]]와 최신 PRF 매핑 유지 | 다중 [[446_port_and_bus|포트]] 접근 [[015_지연_데이터_관점|지연]], 분기 [[658_ir_recovery|복구]] 속도 |
| PRF | 실제 연산 결과 저장 | 개수 부족 시 rename stall 발생 |
| Free List | 비어 있는 PRF 번호 관리 | 할당/반납 충돌 최소화 |
| ROB | 순차 커밋과 예외 [[658_ir_recovery|복구]] 지원 | 이전 매핑 추적, precise exception 보장 |

- **📢 섹션 요약 비유**: 호텔 프런트가 손님 이름표는 그대로 두고 실제 객실 번호만 매번 새로 배정하는 것과 같다. 중요한 것은 체크인 속도도 빠르지만, 예약 취소가 나왔을 때 어떤 방을 다시 비울지 정확히 기억하는 운영 장부다.

## Ⅲ. 비교 및 연결

리네이밍을 제대로 이해하려면 "무엇을 해결하고 무엇은 못 푸는가"를 구분해야 한다. 아래 표는 대표 의존성과 리네이밍의 경계를 보여준다.

| 의존성 유형 | 의미 | 리네이밍 효과 | 남는 문제 |
| :--- | :--- | :--- | :--- |
| [[225_raw|RAW]] ([[225_raw|Read After Write]]) | 앞 결과를 뒤 [[158_instruction|명령어]]가 읽어야 함 | 제거 불가 | 값 생산 [[015_지연_데이터_관점|지연]], 캐시 미스 |
| [[226_war|WAR]] ([[226_war|Write After Read]]) | 앞 [[158_instruction|명령어]]가 읽기 전 뒤 [[158_instruction|명령어]]가 덮어씀 | 제거 가능 | 없음 |
| [[227_waw|WAW]] ([[227_waw|Write After Write]]) | 두 [[158_instruction|명령어]]가 같은 목적지에 기록 | 제거 가능 | 커밋 순서 보장 필요 |

이 차이가 중요한 이유는 OoO 코어의 [[282_performance_tactics|성능]] 상한이 결국 RAW에 의해 정해지기 때문이다. 리네이밍이 없으면 [[226_war|WAR]], WAW까지 모두 벽이 되어 실행 창이 급격히 좁아진다. 반대로 리네이밍이 있으면 하드웨어는 "진짜로 기다려야 하는 [[158_instruction|명령어]]"만 남겨두고, 나머지는 [[241_reservation_station|예약역]] ([[241_reservation_station|Reservation Station]], RS)에서 자유롭게 재배치할 수 있다.

또한 리네이밍은 스코어보딩 (Scoreboarding)보다 더 공격적인 동적 스케줄링과 잘 맞는다. 스코어보딩은 충돌을 감시해 멈추는 데 강하지만, 이름 자체를 바꾸지 못하므로 가짜 의존성 제거에 한계가 있다. 토마술로 [[001_algorithm_definition|알고리즘]] (Tomasulo's [[001_algorithm_definition|Algorithm]]) 계열이 현대 [[236_superscalar|수퍼스칼라]] 코어의 표준이 된 이유도, 태그 기반 값 전달과 리네이밍이 결합되면 넓은 실행 창을 훨씬 유연하게 운영할 수 있기 때문이다.

결국 리네이밍은 [[236_superscalar|수퍼스칼라]], [[231_branch_prediction|분기 예측]], OoO, 정밀 예외 처리와 따로 존재하지 않는다. [[236_superscalar|수퍼스칼라]]가 한 사이클에 여러 [[158_instruction|명령어]]를 들여보내면, 리네이밍은 그 [[158_instruction|명령어]]들이 서로 이름 때문에 막히지 않게 길을 닦아 준다. 그리고 ROB는 그렇게 뒤섞인 실행 결과를 다시 프로그램 순서로 정렬해 소프트웨어에 일관된 세계를 보여 준다.

- **📢 섹션 요약 비유**: 리네이밍은 교차로에서 번호판이 같은 차들 때문에 생기는 혼잡을 없애 주는 임시 번호판 시스템이다. 하지만 앞차가 실제로 길을 막고 있으면 번호판을 바꿔도 못 지나가듯, 진짜 [[001_dikw_pyramid|데이터]] 의존성은 끝까지 남는다.

## Ⅳ. 실무 적용 및 기술사 판단

실무 설계에서 리네이밍은 "넣을까 말까"보다 "어느 정도까지 넣을까"가 핵심이다. 고성능 서버용 코어는 높은 [[158_instruction|명령어]] 창과 깊은 추측 실행이 필요하므로 PRF와 RAT를 크게 설계한다. 반면 모바일·임베디드 코어는 전력과 면적 제약이 크기 때문에, 제한된 폭의 리네이밍이나 단순한 in-order 구조를 택하기도 한다.

### 설계 판단 체크포인트

1. **PRF 개수**: 너무 적으면 rename stall이 자주 발생해 OoO의 이점이 줄어든다. 너무 많으면 PRF 접근 [[015_지연_데이터_관점|지연]]과 누설 전력이 증가해 클럭과 전성비가 악화된다.
2. **[[658_ir_recovery|복구]] 방식**: [[231_branch_prediction|분기 예측]] 실패 시 RAT 전체 [[022_snapshot_backup_architecture|스냅샷]] 복원은 빠르지만 저장 비용이 크다. 이전 매핑을 ROB에 기록하는 방식은 저장 효율이 좋지만 [[658_ir_recovery|복구]] 경로가 길어질 수 있다.
3. **[[446_port_and_bus|포트]] 수와 폭**: 4-way, 6-way [[236_superscalar|수퍼스칼라]] 코어는 한 사이클에 여러 소스·목적지 [[057_register|레지스터]]를 동시에 읽고 갱신해야 하므로 RAT 다중 [[446_port_and_bus|포트]] 비용이 급격히 커진다.
4. **[[157_isa|ISA]] 특성**: x86처럼 가시 [[057_register|레지스터]]가 적고 [[158_instruction|명령어]] 형식이 복잡한 ISA는 리네이밍의 체감 이득이 크다. 반대로 비교적 단순한 [[195_risc|RISC]] (Reduced [[158_instruction|Instruction]] Set Computer) 계열은 컴파일러 최적화와 함께 더 균형 있게 설계할 수 있다.

### 실무 [[128_water_scrum_fall_anti_pattern|안티패턴]]

- 분기 추측은 공격적으로 하면서 리네임 [[658_ir_recovery|복구]] 경로를 약하게 두는 설계
- PRF 고갈 경보 없이 창 크기만 키우는 설계
- 벡터 [[057_register|레지스터]]와 정수 [[057_register|레지스터]]의 특성을 무시하고 동일한 비용 구조로 취급하는 설계

기술사 관점에서는 "리네이밍 = [[282_performance_tactics|성능]] 향상"으로만 쓰면 부족하다. 반드시 **[[282_performance_tactics|성능]] 증가와 함께 복잡도, 소비전력, [[395_verification_process_review|검증]] 난이도도 함께 증가한다**는 점을 적어야 한다. 특히 멀티이슈 폭이 커질수록 리네임 로직이 프런트엔드 임계 경로에 가까워지므로, 좋은 설계는 더 많은 [[057_register|레지스터]]를 주는 것이 아니라 "가장 비싼 충돌을 가장 효율적으로 없애는 수준"을 찾는 것이다.

- **📢 섹션 요약 비유**: 창고에 상자를 많이 쌓아 두는 것만으로 물류가 빨라지지는 않는다. 바코드 시스템, 반품 처리, 출고선 정리가 함께 갖춰져야 진짜로 빠른 창고가 되듯, 리네이밍도 저장 공간보다 운영 정책이 더 중요하다.

## Ⅴ. 기대효과 및 결론

[[057_register|레지스터]] 리네이밍의 가장 큰 효과는 **프로그래머에게는 단순한 [[057_register|레지스터]] 모델을 유지하면서, 하드웨어 내부에서는 훨씬 넓은 [[430_index_fast_full_scan|병렬]] 실행 공간을 만드는 것**이다. 이 덕분에 현대 CPU는 오래된 ISA를 버리지 않고도 높은 [[117_ipc|IPC]] ([[135_ipc|Instructions Per Cycle]])를 달성할 수 있었다. 다시 말해 리네이밍은 호환성과 [[282_performance_tactics|성능]]을 동시에 지키게 해 준 핵심 완충 장치다.

다만 이 기술은 공짜가 아니다. PRF, RAT, ROB, [[658_ir_recovery|복구]] 로직이 커질수록 면적과 전력, [[395_verification_process_review|검증]] 비용이 함께 증가한다. 또한 보안 관점에서는 추측 실행 상태가 [[204_microarchitecture|마이크로아키텍처]] 흔적을 남길 수 있어, 리네이밍을 포함한 내부 상태 관리가 사이드채널 분석 대상이 되기도 한다.

앞으로의 방향은 단순히 PRF를 더 늘리는 것이 아니라, 워크로드별로 리네이밍 자원을 더 영리하게 배분하는 쪽에 가깝다. 예를 들어 정수·벡터·메모리 의존성을 분리해 관리하거나, 저전력 구간에서는 리네임 폭을 동적으로 줄이는 방식이 중요해진다. 따라서 리네이밍은 "[[057_register|레지스터]]를 많이 숨겨 둔 기술"이 아니라, **거짓 병목만 걷어내고 진짜 병목에 자원을 집중하게 만드는 질서 재편 기술**로 기억하는 것이 정확하다.

- **📢 섹션 요약 비유**: 좋은 무대 감독은 배우 이름표를 바꾸려는 사람이 아니라, 무대 뒤 대기실과 출연 순서를 정리해 공연이 끊기지 않게 만드는 사람이다. 리네이밍도 바로 그런 보이지 않는 무대 운영 기술이다.

### 📈 관련 키워드 및 발전 흐름도

```text
가시 레지스터 부족
    │
    ▼
가짜 의존성 식별
(WAR, WAW)
    │
    ▼
레지스터 리네이밍
(RAT + PRF + Free List)
    │
    ├──▶ 비순차 실행 (OoO)
    │        │
    │        ▼
    │    예약역 · 다중 발행
    │
    ▼
재주문 버퍼 (ROB)
기반 순차 커밋
    │
    ▼
넓은 수퍼스칼라 · 추측 실행 · 전성비 최적화
```

이 흐름은 "[[057_register|레지스터]] 부족 인식 → 가짜 의존성 제거 → 동적 실행 확대 → 정확한 커밋 보장 → 고성능 코어 최적화"로 이어지는 발전 방향을 보여준다.
