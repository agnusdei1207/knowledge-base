## 핵심 인사이트 (3줄 요약)

> 1. **본질**: 메인 메모리 [[347_compaction|압축]] (Main Memory [[159_compression|Compression]])은 CPU (Central Processing Unit)와 [[251_dram|DRAM]] (Dynamic Random Access Memory) 사이에서 [[001_dikw_pyramid|데이터]]를 투명하게 [[347_compaction|압축]] 저장해, 물리 메모리를 늘리지 않고도 더 큰 작업 집합을 주기억장치 안에 붙잡아 두는 기술이다.
> 2. **가치**: [[347_compaction|압축]]이 잘 맞는 워크로드에서는 스왑, 원격 메모리, 불필요한 [[251_dram|DRAM]] 왕복을 줄여 유효 용량과 유효 [[140_bandwidth|대역폭]]을 동시에 늘릴 수 있다.
> 3. **판단 포인트**: 실제 효과는 [[347_compaction|압축]]률 자체보다도 [[012_metadata|메타데이터]] 조회, 재배치, [[347_compaction|압축]] 해제 [[015_지연_데이터_관점|지연]]을 모두 합친 비용이 [[286_page_frame|페이지]] 폴트나 [[441_cxl|CXL]] ([[441_cxl|Compute Express Link]]) 원격 접근 비용보다 충분히 작은가에 달려 있다.

## Ⅰ. 개요 및 필요성

메인 메모리 [[347_compaction|압축]]은 [[001_operating_system_purpose|운영체제]]나 메모리 컨트롤러가 주기억장치의 일부 [[001_dikw_pyramid|데이터]]를 [[347_compaction|압축]]된 형태로 저장하고, CPU에는 원래 크기 그대로 보이게 만드는 투명한 용량 확장 기법이다. 핵심은 "메모리가 부족해졌다고 바로 디스크로 내보내기 전에, 같은 [[251_dram|DRAM]] 안에서 먼저 더 작게 접어 넣는다"는 데 있다. [[251_dram|DRAM]] 가격과 전력 소모는 여전히 크고, [[139_inmemory_db|인메모리 데이터베이스]]·가상 머신 밀집 배치·통합 메모리 기반 [[190_ai_llm_requirements_specification|AI]] ([[001_artificial_intelligence|Artificial Intelligence]]) 워크로드는 작업 집합을 계속 키우기 때문에 물리 증설만으로는 비용을 감당하기 어렵다.

[[347_compaction|압축]]이 필요한 이유는 메모리 부족 이후의 비용이 너무 가파르기 때문이다. 캐시를 벗어난 뒤에도 [[001_dikw_pyramid|데이터]]가 로컬 DRAM에 남아 있으면 [[015_지연_데이터_관점|지연]]은 수십 ns 수준이지만, [[347_compaction|압축]] 없이 넘쳐난 [[286_page_frame|페이지]]가 스왑이나 원격 메모리로 밀리면 비용은 수백 ns에서 수 ms까지 커질 수 있다. 즉 메인 메모리 [[347_compaction|압축]]은 단순한 저장 공간 절약이 아니라, **비싼 계층 이동을 늦추는 [[015_지연_데이터_관점|지연]]시간 방어선**이다.

이 그림은 왜 "조금의 [[347_compaction|압축]] 오버헤드"가 "큰 계층 이동 비용"보다 유리할 수 있는지를 보여준다.

```text
┌────────────────────────────────────────────────────────────────────────────┐
│            압축이 필요한 이유: 로컬 DRAM을 넘기면 비용이 급증              │
├────────────────────────────────────────────────────────────────────────────┤
│ Working Set = 96 GB, Physical DRAM = 64 GB                                │
│                                                                            │
│ [비압축] 64 GB DRAM ── 초과 32 GB ──▶ swap / 원격 메모리                   │
│                                  │                                         │
│                                  └─ page fault, I/O, 수백 ns ~ ms 비용     │
│                                                                            │
│ [압축]   64 GB DRAM × 1.5 압축률 ≈ 논리 96 GB 수용                         │
│                                  │                                         │
│                                  └─ 메타데이터 조회 + 해제 지연 수십 ns     │
└────────────────────────────────────────────────────────────────────────────┘
```

물론 모든 [[001_dikw_pyramid|데이터]]가 1.5배로 잘 접히는 것은 아니다. 그러나 0 값이 많은 [[286_page_frame|페이지]], 유사한 [[423_non_clustered_index|포인터 배열]], 희소 행렬처럼 규칙성이 높은 [[001_dikw_pyramid|데이터]]는 [[347_compaction|압축]] 효과가 커서 로컬 메모리에 더 오래 남을 수 있다. 반대로 이미 암호화되었거나 [[347_compaction|압축]]된 [[001_dikw_pyramid|데이터]]는 효과가 작으므로, 결국 메인 메모리 [[347_compaction|압축]]의 핵심은 "무엇을 [[347_compaction|압축]]할지"를 똑똑하게 고르는 일이다.

- **📢 섹션 요약 비유**: 메인 메모리 [[347_compaction|압축]]은 여행 가방에 진공 [[347_compaction|압축]]팩을 넣는 것과 같다. 가방을 새로 사지 않아도 더 많은 옷을 넣을 수 있지만, 꺼낼 때 조금의 수고가 추가된다는 점까지 함께 봐야 한다.

## Ⅱ. 아키텍처 및 핵심 원리

메인 메모리 [[347_compaction|압축]]의 핵심 경로는 `분류 → 압축 → 배치 → 메타데이터 기록 → 필요 시 해제`로 정리된다. 구현 위치는 크게 두 가지다. 하나는 [[001_operating_system_purpose|운영체제]]가 [[286_page_frame|페이지]] 단위로 [[347_compaction|압축]] 풀을 관리하는 방식이고, 다른 하나는 메모리 컨트롤러나 [[744_load_line_calibration|LLC]] (Last-Level Cache) 하단에서 캐시라인 단위로 [[347_compaction|압축]]하는 방식이다. 후자가 더 빠르지만 하드웨어 복잡도가 높고, 전자가 더 유연하지만 소프트웨어 개입 [[015_지연_데이터_관점|지연]]이 크다.

| 구성 요소 | 역할 | 설계 포인트 |
| :--- | :--- | :--- |
| [[347_compaction|압축]] 판별기 | [[001_dikw_pyramid|데이터]]가 [[347_compaction|압축]] 가치가 있는지 판단 | [[151_entropy|엔트로피]] 높은 [[001_dikw_pyramid|데이터]]는 즉시 우회 |
| [[347_compaction|압축]] 엔진 | 짧은 [[015_지연_데이터_관점|지연]]으로 [[073_bit|비트]] 수 축소 | 저지연 [[001_algorithm_definition|알고리즘]] 선택이 핵심 |
| [[012_metadata|메타데이터]] 테이블 | 크기, 위치, 포맷 기록 | 조회 [[015_지연_데이터_관점|지연]]과 저장 오버헤드 최소화 |
| 배치/재배치기 | 가변 길이 블록을 물리 공간에 정렬 | 단편화와 [[347_compaction|compaction]] 비용 관리 |
| 해제기 | 읽기 시 원래 크기로 복원 | 파이프라인 병렬화로 [[015_지연_데이터_관점|지연]] 숨김 |

실제로 많이 언급되는 방식은 BDI (Base-Delta-Immediate), FPC (Frequent Pattern [[159_compression|Compression]]), [[225_lcp_link_control_protocol|LCP]] (Linearly Compressed Pages)다. BDI는 서로 비슷한 값이 많은 [[055_array|배열]]에 강하고, FPC는 0이나 작은 정수처럼 자주 나오는 패턴에 강하다. LCP는 [[001_algorithm_definition|알고리즘]] 그 자체라기보다 "같은 [[286_page_frame|페이지]] 안의 캐시라인을 비슷한 크기로 맞춰 빠르게 주소 계산을 하자"는 배치 프레임워크에 가깝다.

| 기법 | 핵심 아이디어 | 강점 | 약점 |
| :--- | :--- | :--- | :--- |
| BDI | 기준값 하나와 작은 차이만 저장 | [[423_non_clustered_index|포인터 배열]]·연속 값에 강함 | 무작위 바이트에는 약함 |
| FPC | 자주 등장하는 패턴을 짧은 코드로 치환 | [[001_operating_system_purpose|운영체제]] [[001_dikw_pyramid|데이터]] 구조에 잘 맞음 | 패턴 탐지 회로가 필요 |
| [[225_lcp_link_control_protocol|LCP]] | [[286_page_frame|페이지]] 내부 슬롯 크기를 제한해 주소 계산 단순화 | [[012_metadata|메타데이터]] 조회가 빠름 | 내부 단편화가 생길 수 있음 |

이 그림은 [[289_cqrs_db|쓰기]] 경로와 읽기 경로가 어디서 추가 비용을 내는지 보여준다.

```text
┌────────────────────────────────────────────────────────────────────────────┐
│                메인 메모리 압축 경로: 빠른 경로와 느린 경로                │
├────────────────────────────────────────────────────────────────────────────┤
│ LLC Miss / Writeback                                                      │
│        │                                                                  │
│        ▼                                                                  │
│ [Compression Engine] ── 압축 가능? ──┬─ Yes ─▶ [Metadata: size / slot]    │
│        │                             │                    │                │
│        └────────────── No ───────────┘                    ▼                │
│                                                  [Compressed DRAM Region]  │
│                                                                            │
│ Read Request ──────────────────────────────────────────────────────────────│
│        │                                                                   │
│        ▼                                                                   │
│ [Metadata Lookup] → [Fetch 16/32/48/64B] → [Decompress] → [64B Line 반환]  │
└────────────────────────────────────────────────────────────────────────────┘
```

여기서 어려운 지점은 가변 길이 [[001_dikw_pyramid|데이터]] 관리다. 64B 캐시라인이 어떤 것은 16B로 줄고 어떤 것은 64B 그대로 남으면, 단순한 `주소 = base + offset` 계산이 깨진다. 그래서 메인 메모리 [[347_compaction|압축]]은 [[347_compaction|압축]]률만 보는 기술이 아니라, **빠른 위치 결정과 낮은 단편화를 함께 달성하는 주소 관리 기술**이기도 하다. 일반적으로 유효 용량은 `물리 용량 × 평균 압축률 - 메타데이터 및 여유 공간`으로 생각할 수 있다.

- **📢 섹션 요약 비유**: 이 기술은 옷을 접는 법만 좋은 것이 아니라, 접은 옷이 서랍 어디에 들어갔는지 빨리 찾는 수납 시스템까지 함께 좋아야 하는 정리술과 같다.

## Ⅲ. 비교 및 연결

메인 메모리 [[347_compaction|압축]]을 이해하려면 저장장치 [[347_compaction|압축]], 중복 제거, 메모리 계층 확장과 구분해서 봐야 한다. 저장장치 [[347_compaction|압축]]은 높은 [[347_compaction|압축]]률을 노려도 되지만, 메인 메모리 [[347_compaction|압축]]은 ns 단위 [[015_지연_데이터_관점|지연]]시간 때문에 매우 단순한 [[001_algorithm_definition|알고리즘]]만 허용된다. 또한 중복 제거는 "같은 [[286_page_frame|페이지]]를 하나로 합치자"는 접근이고, 메모리 [[347_compaction|압축]]은 "같지 않아도 더 작게 담자"는 접근이라서 서로 보완재에 가깝다.

| 구분 | 메인 메모리 [[347_compaction|압축]] | zswap / zram 기반 [[286_page_frame|페이지]] [[347_compaction|압축]] | 중복 제거 (Deduplication) |
| :--- | :--- | :--- | :--- |
| 주 대상 | 캐시라인 또는 [[286_page_frame|페이지]] | [[286_page_frame|페이지]] | 동일 [[286_page_frame|페이지]] |
| 목표 | 로컬 [[251_dram|DRAM]] 체류 시간 증가 | 스왑 [[015_지연_데이터_관점|지연]] 완화 | 동일 [[546_data_deduplication|데이터 중복 제거]] |
| 장점 | 빠른 계층 유지, 투명성 높음 | 구현 유연성, [[001_operating_system_purpose|운영체제]] 제어 용이 | 중복이 큰 [[598_vm_migration_nic|VM]] 이미지에 강함 |
| 약점 | [[012_metadata|메타데이터]]·재배치 복잡도 | CPU 오버헤드 존재 | 동일성 없으면 효과 없음 |

또한 메인 메모리 [[347_compaction|압축]]은 [[517_huge_page|Huge Page]], [[377_numa_allocation|NUMA]] ([[377_numa_allocation|Non-Uniform Memory Access]]), [[441_cxl|CXL]] 메모리 확장과도 연결된다. 거대 [[286_page_frame|페이지]]는 [[357_tlb|TLB]] ([[291_tlb|Translation Lookaside Buffer]]) 적중률을 높이지만, 한 [[286_page_frame|페이지]] 안에 비압축 [[001_dikw_pyramid|데이터]]가 섞이면 [[347_compaction|압축]] 관리가 까다로워질 수 있다. [[377_numa_allocation|NUMA]] 환경에서는 [[347_compaction|압축]]으로 로컬 노드에 더 오래 머무르게 하는 것이 중요하고, [[441_cxl|CXL]] 확장 메모리가 붙은 시스템에서는 원격 메모리로 밀어내기 전에 먼저 [[347_compaction|압축]]해 로컬 수용량을 늘리는 [[268_strategy_pattern|전략]]이 특히 유효하다.

즉 메인 메모리 [[347_compaction|압축]]은 독립 기술이 아니라, 메모리 벽 ([[433_memory_wall|Memory Wall]]), 원격 메모리, [[260_page_replacement|페이지 교체]] [[164_policy|정책]] 사이에 놓인 연결점이다. [[347_compaction|압축]]만으로 모든 문제를 해결하지는 못하지만, 잘 맞는 워크로드에서는 스왑보다 훨씬 싼 비용으로 병목을 완화한다.

- **📢 섹션 요약 비유**: 중복 제거가 같은 책 두 권을 한 권만 남기는 일이라면, 메인 메모리 [[347_compaction|압축]]은 책의 여백을 줄여 같은 책장을 더 촘촘하게 쓰는 일이다. 둘 다 공간을 아끼지만 방법과 효과가 다르다.

## Ⅳ. 실무 적용 및 기술사 판단

실무에서 메인 메모리 [[347_compaction|압축]]이 잘 맞는 대표 사례는 가상 머신 밀도 향상, 인메모리 분석, 모바일 통합 메모리, [[441_cxl|CXL]] 메모리 티어링 전단이다. [[001_operating_system_purpose|운영체제]] [[286_page_frame|페이지]]나 객체 힙처럼 0 값과 반복 패턴이 많은 [[001_dikw_pyramid|데이터]]는 효과가 좋다. 반대로 암호화 버퍼, 이미 [[347_compaction|압축]]된 미디어, 난수성 높은 체크포인트는 [[347_compaction|압축]]률이 낮아 오히려 [[015_지연_데이터_관점|지연]]만 늘릴 수 있다.

기술사 관점에서는 "[[347_compaction|압축]] 가능성"과 "[[015_지연_데이터_관점|지연]] 예산"을 함께 말해야 답안이 깊어진다. 예를 들어 [[347_compaction|압축]] 해제 추가 비용이 20~40ns인데, 이를 통해 수백 ns의 원격 메모리 접근이나 수 μs 이상의 [[286_page_frame|페이지]] 폴트를 줄일 수 있다면 채택 명분이 분명하다. 하지만 tail latency가 매우 엄격한 실시간 시스템이라면, 평균 [[347_compaction|압축]]률이 높아도 해제 [[015_지연_데이터_관점|지연]]의 [[136_variance|분산]] 자체가 위험 요인이 될 수 있다.

### 적용 [[435_checklist_based_testing|체크리스트]]

1. [[001_dikw_pyramid|데이터]]가 0 값, 작은 정수, 유사 포인터처럼 규칙성을 가지는가?
2. [[347_compaction|압축]] 해제 [[015_지연_데이터_관점|지연]]이 서비스의 99번째 백분위수 (P99) [[015_지연_데이터_관점|지연]] 목표 안에 들어오는가?
3. [[012_metadata|메타데이터]] 테이블이 캐시에 잘 머물러 추가 미스를 만들지 않는가?
4. compaction과 재배치가 [[377_numa_allocation|NUMA]] 로컬리티를 깨지 않는가?
5. [[347_compaction|압축]] 실패 [[286_page_frame|페이지]]를 바로 우회하는 bypass 경로가 준비되어 있는가?

### 피해야 할 [[128_water_scrum_fall_anti_pattern|안티패턴]]

- [[347_compaction|압축]]률만 보고 모든 [[286_page_frame|페이지]]에 강제 적용하는 설계
- [[012_metadata|메타데이터]] 오버헤드를 무시한 용량 계산
- [[347_compaction|압축]]으로 생긴 tail latency를 측정하지 않고 "평균 메모리 사용률"만 보는 운영

결국 메인 메모리 [[347_compaction|압축]]은 DRAM을 공짜로 늘리는 마법이 아니다. 더 정확하게는 **비싼 계층 이동을 피하기 위해, 싸게 감당 가능한 정도의 [[347_compaction|압축]] 오버헤드를 미리 지불하는 [[268_strategy_pattern|전략]]**이다.

- **📢 섹션 요약 비유**: 매일 쓰는 옷은 옷장 안에서 [[347_compaction|압축]]팩으로 정리하면 편하지만, 당장 입어야 하는 공연 의상을 너무 꽉 [[347_compaction|압축]]해 두면 꺼내는 시간이 더 큰 문제가 되는 것과 같다.

## Ⅴ. 기대효과 및 결론

메인 메모리 [[347_compaction|압축]]의 가장 큰 효과는 유효 용량 증가, 스왑 감소, 로컬 [[140_bandwidth|대역폭]] 활용 개선이다. 특히 물리 메모리 증설이 비싸거나 전력 한계가 빡빡한 시스템에서는 같은 하드웨어로 더 큰 작업 집합을 처리하게 해 준다. 또한 원격 메모리나 보조 저장장치로 밀려나는 빈도를 낮추므로, 평균 성능뿐 아니라 장애 [[233_recovery_database_restoration_overview|회복]] 시의 예측 가능성까지 좋아질 수 있다.

하지만 한계도 분명하다. [[347_compaction|압축]]률은 워크로드 의존적이고, [[012_metadata|메타데이터]] 관리와 재배치 복잡도는 하드웨어 면적과 전력을 증가시킨다. 또한 [[347_compaction|압축]] 여부에 따라 접근 시간이 달라지면 보안 측면의 타이밍 부채널을 점검해야 하며, 이미 [[347_compaction|압축]]된 [[001_dikw_pyramid|데이터]] 비중이 큰 환경에서는 투자 대비 효과가 작다.

앞으로는 [[441_cxl|CXL]] 기반 메모리 풀과 연계한 [[164_policy|정책]]형 [[347_compaction|압축]], 테넌트별 메모리 품질 [[164_policy|정책]], [[190_ai_llm_requirements_specification|AI]] 가속기 통합 메모리용 [[347_compaction|압축]]이 더 중요해질 가능성이 크다. 결론적으로 메인 메모리 [[347_compaction|압축]]은 "DRAM을 더 크게 만드는 기술"이라기보다, **작업 집합을 더 오래 로컬에 붙잡아 두는 계층 제어 기술**로 기억하는 것이 정확하다.

- **📢 섹션 요약 비유**: 결국 이 기술은 작은 냉장고를 조금 더 크게 쓰는 방법이다. 냉장고 문을 자주 열어 멀리 창고까지 가지 않게 해 주지만, 정리 방식이 엉망이면 오히려 필요한 반찬을 찾는 데 시간이 더 걸린다.

### 📈 관련 키워드 및 발전 흐름도

```text
DRAM 증설 중심 메모리 운영
        │
        ▼
메모리 벽 (Memory Wall) · 스왑 병목
        │
        ▼
운영체제 기반 페이지 압축
        │
        ▼
저지연 캐시라인 압축 (BDI · FPC)
        │
        ▼
LCP · 메타데이터 최적화 · compaction 제어
        │
        ▼
NUMA / CXL 연계 정책형 메인 메모리 압축
```

이 흐름은 "부족하면 내보내는 메모리 관리"에서 출발해, "먼저 로컬에서 더 작게 담아 보자"는 방향으로 진화한 과정을 보여 준다.

### 👶 어린이를 위한 3줄 비유 설명

1. 메인 메모리 [[347_compaction|압축]]은 장난감 상자 안의 공기를 꾹 빼서 더 많은 장난감을 넣는 방법이에요.
2. 덕분에 장난감을 창고로 옮기지 않아도 돼서 더 빨리 꺼내 놀 수 있어요.
3. 하지만 꺼낼 때는 다시 모양을 펴야 하니까, 너무 아무 장난감이나 꾹 누르면 오히려 찾기 불편해질 수 있어요.
