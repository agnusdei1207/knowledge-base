> **핵심 인사이트 3줄**
> 1. [[217_cdc_binlog_change_capture_debezium|CDC]]([[217_cdc_binlog_change_capture_debezium|Change Data Capture]])는 소스 DB의 INSERT·UPDATE·DELETE 변경 이벤트를 실시간으로 캡처해 다운스트림 시스템에 전파하는 [[001_dikw_pyramid|데이터]] 통합 기법이다.
> 2. [[568_logs_distributed_logging_elk_fluentd|로그]] 기반 [[217_cdc_binlog_change_capture_debezium|CDC]](Debezium + [[179_kafka_flink_watermark_time_window|Kafka]])는 소스 DB 부하 없이 WAL/Binlog를 읽어 서브밀리초 [[015_지연_데이터_관점|지연]]으로 변경을 스트리밍하는 현대 표준이다.
> 3. CDC는 실시간 [[209_data_warehouse_schema_on_write|데이터 웨어하우스]]·[[532_microservices_decomposition_patterns|마이크로서비스]] [[214_eda_event_driven_architecture_async|이벤트 드리븐 아키텍처]]·[[110_zero_downtime_db_schema_rollout|Zero-downtime]] 마이그레이션의 핵심 인프라로 사용된다.

---

## Ⅰ. CDC의 정의와 필요성

[[217_cdc_binlog_change_capture_debezium|CDC]]([[217_cdc_binlog_change_capture_debezium|Change Data Capture]], [[218_cdc_change_data_capture|변경 데이터 캡처]])는 **[[001_dikw_pyramid|데이터]]베이스의 모든 변경 사항을 감지·캡처·전달하는 기술**이다.

### [[217_cdc_binlog_change_capture_debezium|CDC]] vs 배치 [[215_etl_vs_elt_pipeline|ETL]] 비교

| 항목          | 배치 [[215_etl_vs_elt_pipeline|ETL]]              | [[217_cdc_binlog_change_capture_debezium|CDC]] (실시간)           |
|-------------|----------------------|----------------------|
| 처리 방식    | 주기적 (야간 배치)    | 이벤트 기반 실시간     |
| [[001_dikw_pyramid|데이터]] 신선도 | 시간~일 단위          | 밀리초~초 단위         |
| 소스 DB 부하 | [[298_qkv_attention|쿼리]] 부하 높음        | [[568_logs_distributed_logging_elk_fluentd|로그]] 기반 시 낮음      |
| 복잡도       | 단순                  | 높음 ([[005_schema|스키마]] [[079_change_enablement|변경 관리]]) |
| 사용 사례    | 보고서·분석           | 실시간 대시보드·[[212_synchronization_mechanisms|동기화]]  |

📢 **섹션 요약 비유**: CDC는 우체통을 주기적으로 확인하는 것(배치 [[215_etl_vs_elt_pipeline|ETL]]) 대신, 편지가 도착하는 순간 알림을 받는 것([[217_cdc_binlog_change_capture_debezium|CDC]])과 같다.

## Ⅱ. [[217_cdc_binlog_change_capture_debezium|CDC]] 구현 방식 3가지

### 1. [[298_qkv_attention|쿼리]] 기반 [[217_cdc_binlog_change_capture_debezium|CDC]] (Query-Based)

```sql
-- 마지막 추출 시각 이후 변경된 행 조회
SELECT * FROM orders
WHERE updated_at > :last_extract_time
ORDER BY updated_at;
```
- 장점: 구현 간단, 기존 DB 변경 불필요
- 단점: 삭제 감지 불가, DB 부하, 밀리초 [[015_지연_데이터_관점|지연]] 불가

### 2. [[507_acid_properties|트리거]] 기반 [[217_cdc_binlog_change_capture_debezium|CDC]] (Trigger-Based)

```sql
CREATE TRIGGER orders_cdc
AFTER INSERT OR UPDATE OR DELETE ON orders
FOR EACH ROW
INSERT INTO cdc_log VALUES (NOW(), TG_OP, OLD/NEW데이터);
```
- 장점: 삭제 감지 가능
- 단점: DB [[282_performance_tactics|성능]] 저하, [[005_schema|스키마]] 변경 시 [[507_acid_properties|트리거]] 관리 복잡

### 3. [[568_logs_distributed_logging_elk_fluentd|로그]] 기반 [[217_cdc_binlog_change_capture_debezium|CDC]] (Log-Based) — 현대 표준

```
PostgreSQL WAL / MySQL Binlog
         ↓
     Debezium (오픈소스 CDC)
         ↓
     Apache Kafka (이벤트 스트림)
         ↓
  다운스트림: DWH / 검색 / 캐시
```
- 장점: 소스 DB 부하 없음, 모든 변경 캡처, 서브밀리초
- 단점: DB [[568_logs_distributed_logging_elk_fluentd|로그]] [[009_config|설정]] 필요, 복잡한 운영

📢 **섹션 요약 비유**: [[568_logs_distributed_logging_elk_fluentd|로그]] 기반 CDC는 [[933_cctv|CCTV]] 녹화본을 분석하는 방식이다 — 직접 현장(DB)에 탐정([[298_qkv_attention|쿼리]]/[[507_acid_properties|트리거]])을 배치하지 않고 기존 보안 카메라([[191_transaction_concept_states|트랜잭션]] [[568_logs_distributed_logging_elk_fluentd|로그]])를 활용한다.

## Ⅲ. Debezium + [[179_kafka_flink_watermark_time_window|Kafka]] [[217_cdc_binlog_change_capture_debezium|CDC]] 아키텍처

```
┌──────────────────────────────────────────────────────────────┐
│                   CDC 데이터 파이프라인                        │
│                                                              │
│  PostgreSQL ──→ Debezium ──→ Kafka Topic ──→ Flink/Spark    │
│    (WAL)       Connector    (변경 이벤트)    (스트림 처리)    │
│                                  │                          │
│                            Kafka Connect │                  │
│                            Sink Connector│                  │
│                                  ↓                          │
│                    Elasticsearch / Snowflake / Redis        │
└──────────────────────────────────────────────────────────────┘
```

### Debezium 이벤트 메시지 구조

```json
{
  "op": "u",          // c=create, u=update, d=delete
  "before": { "id": 1, "status": "pending" },
  "after":  { "id": 1, "status": "shipped" },
  "source": {
    "table": "orders",
    "ts_ms": 1700000000000,
    "lsn": 12345678
  }
}
```

📢 **섹션 요약 비유**: Debezium 이벤트는 신문 사회면 기사다 — "어떤 사건(op)이, 이전엔(before) 어땠고, 지금은(after) 어떻게 됐다"를 정확히 기록한다.

## Ⅳ. [[217_cdc_binlog_change_capture_debezium|CDC]] 활용 패턴

| 패턴              | 설명                               |
|-----------------|-----------------------------------|
| [[001_dikw_pyramid|데이터]] [[212_synchronization_mechanisms|동기화]]    | RDBMS → DWH 실시간 [[016_replication_factor|복제]]            |
| 이벤트 발행      | DB 변경 → [[532_microservices_decomposition_patterns|마이크로서비스]] 이벤트    |
| 캐시 무효화      | DB 업데이트 → [[542_redis|Redis]] 캐시 갱신      |
| 검색 [[154_database_index_b_tree_search_optimization|인덱스]] 갱신 | DB 변경 → [[302_cdc|Elasticsearch]] [[212_synchronization_mechanisms|동기화]]     |
| [[606_auditing_linux_auditd|감사]] 로깅        | 모든 변경 이력 중앙 저장            |
| 마이그레이션     | 무중단 DB 마이그레이션 (이중 기록)  |

### [[110_zero_downtime_db_schema_rollout|Zero-downtime]] 마이그레이션 패턴

```
Phase 1: CDC로 구 DB → 신 DB 동기화
Phase 2: 읽기 트래픽 신 DB로 전환 (테스트)
Phase 3: 쓰기 트래픽도 신 DB로 완전 전환
Phase 4: CDC 중단, 구 DB 폐기
```

📢 **섹션 요약 비유**: [[110_zero_downtime_db_schema_rollout|Zero-downtime]] 마이그레이션은 달리는 기차의 선로를 교체하는 것과 같다 — CDC가 두 선로 사이의 전환 [[238_switch_operation_principles|스위치]] 역할을 한다.

## Ⅴ. [[217_cdc_binlog_change_capture_debezium|CDC]] 운영 고려사항

### [[005_schema|스키마]] 변화 처리 ([[505_schema|Schema]] Evolution)

```
소스 DB 컬럼 추가 시:
  Debezium → Kafka Schema Registry (Avro/Protobuf)
  → 컨슈머는 새 필드를 Optional로 처리 (하위 호환)
```

### At-Least-Once / Exactly-Once 보장

| 보장 수준         | 방법                          |
|-----------------|-------------------------------|
| At-Least-Once   | [[179_kafka_flink_watermark_time_window|Kafka]] + [[171_idempotency_iac_terraform|멱등성]] 소비자          |
| Exactly-Once    | [[179_kafka_flink_watermark_time_window|Kafka]] Transactions + [[549_2pc_two_phase_commit_limitations_msa|2PC]]      |

📢 **섹션 요약 비유**: [[505_schema|Schema]] Evolution 처리는 회사 양식 변경과 같다 — 새 칸이 추가되어도 예전 양식으로 작성한 서류가 거부되지 않도록 하위 호환을 유지해야 한다.

## 👶 어린이를 위한 3줄 비유 설명

1. CDC는 일기 복사기다 — 내가 일기를 쓰는 순간 친구에게도 똑같이 전달되어 항상 최신 내용을 볼 수 있다.
2. [[568_logs_distributed_logging_elk_fluentd|로그]] 기반 CDC는 [[933_cctv|CCTV]] 영상 분석이다 — 직접 물어보지 않아도 기록만 보면 무슨 일이 있었는지 알 수 있다.
3. Debezium은 번역가다 — DB 언어(WAL/Binlog)를 모두가 이해하는 [[179_kafka_flink_watermark_time_window|Kafka]] 이벤트 언어로 실시간 번역해준다.
