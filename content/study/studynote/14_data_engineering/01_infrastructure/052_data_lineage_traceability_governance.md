## 핵심 인사이트 (3줄 요약)

> 1. **본질**: [[214_data_lineage_tracking|데이터 리니지]] ([[214_data_lineage_tracking|Data Lineage]])는 [[001_dikw_pyramid|데이터]]가 어디서 왔고, 어떤 변환을 거쳐 어디로 갔는지 추적하는 족보 지도다.
> 2. **가치**: 오류 원인 분석과 영향도 분석을 빠르게 해 주어, [[005_schema|스키마]] 변경이나 [[215_etl_vs_elt_pipeline|ETL]] 오류의 파급 범위를 즉시 파악하게 한다.
> 3. **판단 포인트**: [[012_metadata|메타데이터]], SQL 파서, [[215_etl_vs_elt_pipeline|ETL]] [[568_logs_distributed_logging_elk_fluentd|로그]], [[213_data_catalog_metadata|데이터 카탈로그]]가 함께 있어야 자동 리니지가 실용적이다.

---

## Ⅰ. 개요 및 필요성

[[001_dikw_pyramid|데이터]]가 여러 시스템을 거치면 숫자의 출처를 사람이 기억하기 어렵다. 리니지가 없으면 대시보드 숫자가 왜 바뀌었는지, 어떤 스크립트가 잘못됐는지, 어떤 다운스트림이 영향을 받는지 추적하기 힘들다.

그래서 [[214_data_lineage_tracking|데이터 리니지]]는 [[001_dikw_pyramid|데이터]] 신뢰성과 운영 안정성의 핵심이 된다. 특히 [[001_dikw_pyramid|데이터]] 플랫폼이 커질수록 "이 숫자는 어디서 왔나"를 설명할 수 있어야 한다.

- **📢 섹션 요약 비유**: [[214_data_lineage_tracking|데이터 리니지]]는 물이 어느 샘에서 시작해 어느 관을 지나 수도꼭지로 왔는지 알려주는 수질 지도와 같다.

---

## Ⅱ. 아키텍처 및 핵심 원리

리니지는 [[001_dikw_pyramid|데이터]] 흐름을 [[401_bayesian_network_dag_causality|DAG]] ([[255_apache_airflow_dag|Directed Acyclic Graph]])로 본다. 소스 테이블, 변환 로직, 타깃 테이블의 연결을 추적하면 역방향으로 원인을 찾고, 순방향으로 영향 범위를 찾을 수 있다.

```text
┌──────────────────────────────────────────────────────────────┐
│                    Data Lineage Flow                        │
├──────────────────────────────────────────────────────────────┤
│ Source DB → ETL/ELT → Staging → Mart → Dashboard            │
│     ▲                                         │             │
│     └──────────── Backward / Forward Trace ───┘             │
└──────────────────────────────────────────────────────────────┘
```

| 구성 요소 | 역할 | 포인트 |
| :--- | :--- | :--- |
| Source | 원천 [[001_dikw_pyramid|데이터]] | 출발점 |
| Transformation | 변환 로직 | SQL, 파이프라인, 스크립트 |
| Target | 소비 [[001_dikw_pyramid|데이터]] | 대시보드, 마트 |
| [[012_metadata|Metadata]] | 설명 [[001_dikw_pyramid|데이터]] | [[005_schema|스키마]], 소유자, 태그 |
| [[394_catalog_metadata|Catalog]] | 탐색 인터페이스 | 검색과 영향도 분석 |

리니지는 단순 기록이 아니라 운영 도구다. 컬럼 타입을 바꾸거나 테이블을 삭제하기 전에 downstream을 확인해야 하고, 이상한 숫자가 보이면 upstream을 따라가 원인을 찾아야 한다.

- **📢 섹션 요약 비유**: 리니지는 강의 노트의 목차다. 끝에서 문제를 발견하면 앞쪽으로 거슬러 올라가 어디서 잘못됐는지 바로 찾을 수 있다.

---

## Ⅲ. 비교 및 연결

리니지는 [[213_data_catalog_metadata|데이터 카탈로그]], [[203_metadata_management|메타데이터 관리]], [[001_dikw_pyramid|데이터]] 품질, [[001_dikw_pyramid|데이터]] 오브저버빌리티와 연결된다. [[394_catalog_metadata|카탈로그]]가 "무엇이 있는가"를 보여준다면, 리니지는 "어디서 왔는가"를 보여준다.

| 항목 | [[213_data_catalog_metadata|데이터 카탈로그]] | [[012_metadata|메타데이터]] | [[214_data_lineage_tracking|데이터 리니지]] |
| :--- | :--- | :--- | :--- |
| 질문 | 무엇이 있는가 | 무슨 의미인가 | 어디서 왔고 어디로 가는가 |
| 목적 | 탐색 | 이해 | 추적 |
| 가치 | 발견성 | 해석력 | 원인/영향 분석 |

또한 리니지는 규제 대응과 직결된다. 금융, 의료, 공공 영역에서는 민감 [[001_dikw_pyramid|데이터]]가 어디로 퍼지는지 설명해야 하므로, 리니지 그래프가 사실상 필수다.

- **📢 섹션 요약 비유**: [[394_catalog_metadata|카탈로그]]는 도서관 책 목록, 리니지는 그 책이 어느 서고에서 어떤 경로로 내 손에 왔는지 적은 운송장이다.

---

## Ⅳ. 실무 적용 및 기술사 판단

실무에서는 SQL 파싱, [[215_etl_vs_elt_pipeline|ETL]] 도구, 워크플로 엔진, [[213_data_catalog_metadata|데이터 카탈로그]]를 연결해 리니지를 자동 수집한다. 그리고 [[005_schema|스키마]] 변경 전에 영향도를 확인하고, 장애가 나면 역추적을 통해 원인을 찾는다.

### [[435_checklist_based_testing|체크리스트]]

1. 소스-변환-타깃 관계가 자동 수집되는가?
2. [[005_schema|스키마]] 변경 영향도를 미리 볼 수 있는가?
3. 민감 [[001_dikw_pyramid|데이터]] 태그와 접근 경로가 연결되는가?
4. 비즈니스 사용자가 읽을 수 있는 형태로 제공되는가?

### [[128_water_scrum_fall_anti_pattern|안티패턴]]

- 문서만 있고 자동 추적이 없는 경우
- SQL [[568_logs_distributed_logging_elk_fluentd|로그]]를 못 읽어 리니지가 끊기는 경우
- 기술팀만 보고 비즈니스 사용자는 못 보는 경우

기술사 관점에서는 리니지를 "[[001_dikw_pyramid|데이터]] 거버넌스의 관측성"으로 설명하면 좋다. [[001_dikw_pyramid|데이터]]가 왜 틀렸는지, 어디가 영향을 받는지, 누가 책임지는지를 한눈에 보여주는 체계다.

- **📢 섹션 요약 비유**: [[214_data_lineage_tracking|데이터 리니지]]는 택배 추적 번호와 같다. 어디서 출발했고 어디를 거쳤는지 알 수 있어야 분실도 빨리 찾는다.

---

## Ⅴ. 기대효과 및 결론

[[214_data_lineage_tracking|데이터 리니지]]가 있으면 원인 분석과 영향도 분석이 빨라지고, 규제 대응과 변경 관리가 쉬워진다. [[001_dikw_pyramid|데이터]] 품질과 신뢰성이 높아져 결국 분석과 AI의 결과도 좋아진다.

즉 리니지는 [[001_dikw_pyramid|데이터]] 플랫폼의 안전벨트다. 보이지 않지만 장애와 오해를 줄여 준다.

- **📢 섹션 요약 비유**: [[214_data_lineage_tracking|데이터 리니지]]는 족보 책이다. 누가 누구에게서 왔는지 알아야 책임도 추적할 수 있다.
