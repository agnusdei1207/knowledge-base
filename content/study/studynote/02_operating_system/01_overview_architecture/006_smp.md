## 핵심 인사이트 (3줄 요약)
> 1. **본질**: [[195_real_time_scheduling|대칭 다중 처리]] ([[195_real_time_scheduling|SMP]], Symmetric Multiprocessing)는 2개 이상의 동일한 프로세서가 하나의 [[118_shared_memory|공유 메모리]]를 공유하며, [[001_operating_system_purpose|운영체제]]가 모든 프로세서를 동등하게 관리하여 [[430_index_fast_full_scan|병렬]] 처리를 극대화하는 아키텍처이다.
> 2. **가치**: 마스터-슬레이브 구조의 병목을 제거하여 시스템 [[139_throughput|처리량]]([[139_throughput|Throughput]])을 높이지만, 프로세서 증가에 따른 [[344_bus|버스]] 경합([[344_bus|Bus]] Contention)과 [[402_cache_coherence|캐시 일관성]]([[402_cache_coherence|Cache Coherence]]) 유지 비용이 확장성의 임계점을 결정한다.
> 3. **융합**: 멀티코어 프로세서의 기반 기술로서 [[054_hypervisor|하이퍼바이저]]([[054_hypervisor|Hypervisor]])의 [[041_resource_allocation|자원 할당]], 고성능 컴퓨팅([[548_automotive_hpc|HPC]]), [[002_database_definition|데이터베이스]] 서버의 [[430_index_fast_full_scan|병렬]] [[298_qkv_attention|쿼리]] 수행 등 현대 컴퓨팅 전반의 하드웨어 운영 표준으로 자리 잡았다.

---

## Ⅰ. 개요 및 필요성 ([[033_context|Context]] & Necessity)

- **개념**: [[195_real_time_scheduling|대칭 다중 처리]] ([[195_real_time_scheduling|SMP]], Symmetric Multiprocessing)는 여러 개의 프로세서가 단일 [[118_shared_memory|공유 메모리]] ([[118_shared_memory|Shared Memory]])와 I/O 장치에 연결되어 있으며, 단일 [[001_operating_system_purpose|운영체제]] (OS, [[001_operating_system_purpose|Operating System]]) 인스턴스에 의해 모든 프로세서가 대칭적으로 제어되는 [[430_index_fast_full_scan|병렬]] 컴퓨팅 방식이다. 모든 프로세서가 메모리의 모든 영역에 동일한 접근 권한을 가지며, 특정 프로세서가 제어를 전담하지 않는 것이 특징이다.

- **필요성**: 단일 프로세서의 클럭 속도 향상이 물리적 한계(발열, [[466_power_consumption|전력 소모]])에 직면하면서, 시스템 [[282_performance_tactics|성능]]을 높이기 위해 프로세서의 수를 늘리는 수평적 확장([[202_scale_out_distributed_horizontal_expansion|Scale-out]] within a box)이 필연적이 되었다. SMP는 작업을 여러 프로세서에 [[136_variance|분산]]시켜 응답 시간을 단축하고, 특정 프로세서 장애 시에도 다른 프로세서가 업무를 대행하는 고가용성(High [[452_availability|Availability]])을 제공하기 위해 도입되었다.

- **💡 비유**: SMP는 "모든 요리사가 동일한 조리대와 냉장고를 공유하는 주방"과 같다. 주방장(마스터)이 따로 지시하지 않아도 모든 요리사가 빈 화구를 찾아 요리를 시작하며, 재료(메모리)를 자유롭게 꺼내 쓸 수 있는 구조다.

- **등장 배경**: [[459_quic_fec_forward_error_correction|초기]] 다중 처리 시스템은 특정 프로세서가 [[001_operating_system_purpose|운영체제]]를 전담하고 나머지는 연산만 수행하는 [[194_numa_scheduling|비대칭 다중 처리]] ([[194_numa_scheduling|ASMP]], Asymmetric Multiprocessing) 방식이었다. 하지만 ASMP는 마스터 프로세서에 부하가 집중되는 병목 현상이 심화되었고, 이를 해결하기 위해 모든 프로세서가 [[001_operating_system_purpose|운영체제]] [[022_kernel_role|커널]]을 실행할 수 있는 [[195_real_time_scheduling|SMP]] 구조가 탄생했다.

```text
  ┌─────────────────────────────────────────────────────────────┐
  │           ASMP (비대칭) vs SMP (대칭) 구조 비교             │
  ├─────────────────────────────────────────────────────────────┤
  │                                                             │
  │  [ASMP: Master-Slave]          [SMP: Peer-to-Peer]          │
  │                                                             │
  │    ┌──────────┐                  ┌──────────┐  ┌──────────┐ │
  │    │ Master P │ (OS 전담)        │ Processor│  │ Processor│ │
  │    └────┬─────┘                  └────┬─────┘  └────┬─────┘ │
  │         │      (명령 하달)             │            │       │
  │    ┌────▼─────┐  ┌────▼─────┐    ┌────┴────────────┴────┐   │
  │    │ Slave P  │  │ Slave P  │    │     Shared Bus       │   │
  │    └──────────┘  └──────────┘    └────┬────────────┬────┘   │
  │                                       │            │        │
  │  [한계] 마스터 장애 시 붕괴      [특징] 모든 CPU 동등 권한  │
  │         마스터 병목 발생                부하 분산 최적화    │
  └─────────────────────────────────────────────────────────────┘
```

**[다이어그램 해설]** 위 도식은 다중 처리 시스템의 진화 과정을 보여준다. 왼쪽의 [[194_numa_scheduling|ASMP]] (Asymmetric Multiprocessing)는 마스터 프로세서가 I/O와 OS 스케줄링을 독점하므로 구조는 단순하지만 확장성이 낮다. 반면 오른쪽의 [[195_real_time_scheduling|SMP]] (Symmetric Multiprocessing)는 공유 [[344_bus|버스]]를 통해 모든 프로세서가 동등하게 자원에 접근한다. 이는 프로세서 하나가 죽어도 시스템 전체가 멈추지 않는 [[296_fault_tolerance_architecture|결함 허용]]([[800_system_architecture_fault_tolerance_dual|Fault Tolerance]]) 능력을 제공하며, [[022_kernel_role|커널]] 코드를 여러 CPU에서 동시에 실행할 수 있게 하여 시스템 효율을 극대화한다. 다만, 모든 CPU가 하나의 통로(Shared [[344_bus|Bus]])를 사용하므로 CPU 수가 늘어날수록 통로를 차지하려는 싸움(Contention)이 치열해지는 트레이드오프가 존재한다.

- **📢 섹션 요약 비유**: 독재자가 지시하는 사회([[194_numa_scheduling|ASMP]])에서 모든 시민이 자유롭게 생산 활동에 참여하는 민주 사회([[195_real_time_scheduling|SMP]])로 발전하여 전체 생산성을 높인 것과 같습니다.

### [[195_real_time_scheduling|SMP]] 시스템 아키텍처 및 [[001_dikw_pyramid|데이터]] 흐름

[[195_real_time_scheduling|SMP]] 아키텍처의 핵심은 모든 프로세서가 단일 [[127_system_bus|시스템 버스]]를 통해 [[118_shared_memory|공유 메모리]]에 접근하는 물리적 연결 구조와, 각 프로세서가 가진 지역 캐시(Local Cache)의 [[001_dikw_pyramid|데이터]]를 일관되게 유지하는 논리적 메커니즘의 결합이다.

```text
 ┌───────────────────────────────────────────────────────────────┐
 │                  SMP 하드웨어 상세 구조도                     │
 ├───────────────────────────────────────────────────────────────┤
 │                                                               │
 │  ┌──────────┐      ┌──────────┐      ┌──────────┐             │
 │  │ CPU #1   │      │ CPU #2   │      │ CPU #n   │             │
 │  ├──────────┤      ├──────────┤      ├──────────┤             │
 │  │ L1 Cache │      │ L1 Cache │      │ L1 Cache │             │
 │  └────┬─────┘      └────┬─────┘      └────┬─────┘             │
 │       │                 │                 │                   │
 │  ┌────┴─────────────────┴─────────────────┴────┐              │
 │  │           System Bus (Data / Addr / Control)│              │
 │  └────┬───────────────────────────────────┬────┘              │
 │       │                                   │                   │
 │  ┌────┴─────┐                       ┌─────┴────┐              │
 │  │ Shared   │                       │   I/O    │              │
 │  │ Memory   │                       │ Controller│             │
 │  └──────────┘                       └──────────┘              │
 │                                                               │
 │  [동작] CPU #1이 메모리 수정 시, 버스를 통해 타 CPU에 알림    │
 │  [병목] CPU 증가 -> Bus Contention -> 성능 포화 (Saturation)  │
 └───────────────────────────────────────────────────────────────┘
```

**[다이어그램 해설]** 이 구조도는 SMP의 물리적 연결 방식을 나타낸다. 모든 프로세서(CPU #1~n)는 독립적인 L1/L2 캐시를 가지고 있지만, 메인 메모리는 하나를 공유한다. 프로세서가 늘어날수록 [[127_system_bus|시스템 버스]]에 대한 접근 요청이 기하급수적으로 증가하며, 특정 시점이 지나면 CPU를 추가해도 [[344_bus|버스]] 대기 시간 때문에 전체 [[282_performance_tactics|성능]]이 더 이상 늘어나지 않는 포화 지점(Saturation Point)에 도달한다. 실무적으로 SMP는 보통 8~32개 정도의 프로세서까지만 효율적이며, 그 이상의 확장을 위해서는 [[377_numa_allocation|NUMA]] ([[377_numa_allocation|Non-Uniform Memory Access]]) 아키텍처로의 전환이 필요하다. 또한, 한 CPU가 캐시의 [[001_dikw_pyramid|데이터]]를 변경했을 때 다른 CPU가 그 변경 사실을 즉시 알 수 있도록 [[344_bus|버스]]에서 [[130_signal|신호]]를 감시하는 '스누핑(Snooping)' 메커니즘이 여기서 작동한다.

### [[402_cache_coherence|캐시 일관성]] ([[402_cache_coherence|Cache Coherence]]) 문제와 해결

SMP에서 가장 치명적인 문제는 각 CPU가 동일한 메모리 번지의 [[001_dikw_pyramid|데이터]]를 자신의 캐시에 복사해 두었을 때, 한 CPU가 이를 수정해도 다른 CPU는 옛날 [[001_dikw_pyramid|데이터]]를 계속 보고 있을 수 있다는 점이다. 이를 해결하기 위해 MESI [[295_protocol_field_tcp_udp_icmp|프로토콜]]이 널리 사용된다.

```text
  [CPU 1] 수정 요청 (Write)
     ↓
  [MESI Protocol] 상태 전이
     ↓
  Modified (M) : 나만 가짐, 수정됨
  Exclusive (E): 나만 가짐, 원본과 동일
  Shared (S)   : 여러 명이 가짐, 원본과 동일
  Invalid (I)  : 내 데이터는 쓰레기 (무효화됨)
     ↓
  [Bus] 무효화 신호 (Invalidation) 송출
     ↓
  [CPU 2, 3] 자신의 캐시 상태를 'I'로 변경
```

**[다이어그램 해설]** 위 흐름은 [[402_cache_coherence|캐시 일관성]]을 유지하는 MESI (Modified, Exclusive, Shared, Invalid) [[295_protocol_field_tcp_udp_icmp|프로토콜]]의 작동 원리이다. CPU 1이 [[001_dikw_pyramid|데이터]]를 수정하려 할 때, 해당 [[001_dikw_pyramid|데이터]]가 'Shared' 상태라면 [[344_bus|버스]]에 무효화(Invalidate) [[130_signal|신호]]를 보내 다른 모든 CPU의 해당 캐시 라인을 'Invalid' 상태로 강제 전환시킨다. 이후 CPU 1은 상태를 'Modified'로 바꾸고 [[001_dikw_pyramid|데이터]]를 수정한다. 이 과정에서 발생하는 [[344_bus|버스]] 트래픽을 '[[402_cache_coherence|캐시 일관성]] 오버헤드'라고 하며, [[001_dikw_pyramid|데이터]] 공유가 잦은 멀티스레드 프로그램일수록 이 비용이 급증하여 [[282_performance_tactics|성능]]을 저하시킨다. 실무에서는 이러한 오버헤드를 줄이기 위해 [[019_data_locality|데이터 지역성]](Locality)을 고려한 프로그래밍과 락 프리([[256_lock_free_data_structures|Lock-free]]) [[001_algorithm_definition|알고리즘]] 사용이 권장된다.

- **📢 섹션 요약 비유**: 회의실 칠판([[118_shared_memory|공유 메모리]])의 내용을 각자 수첩(캐시)에 적어갔을 때, 누군가 칠판 내용을 고치면 큰 소리로 "수첩 내용 다 지워!"라고 외쳐서 정보를 맞추는 것과 같습니다.

## Ⅲ. 융합 비교 및 다각도 분석

### [[195_real_time_scheduling|SMP]] vs [[194_numa_scheduling|ASMP]] vs [[377_numa_allocation|NUMA]] vs MPP

| 비교 항목 | [[195_real_time_scheduling|SMP]] ([[195_real_time_scheduling|대칭 다중 처리]]) | [[194_numa_scheduling|ASMP]] ([[194_numa_scheduling|비대칭 다중 처리]]) | [[377_numa_allocation|NUMA]] (비균등 메모리) | MPP (대량 [[430_index_fast_full_scan|병렬]] 처리) |
|:---|:---|:---|:---|:---|
| **메모리 구조** | [[118_shared_memory|공유 메모리]] ([[379_uma|UMA]]) | [[118_shared_memory|공유 메모리]] | [[136_variance|분산]] [[118_shared_memory|공유 메모리]] | 독립 메모리 ([[306_embedding_model|Shared Nothing]]) |
| **[[001_operating_system_purpose|운영체제]]** | 단일 OS 인스턴스 | 단일 OS (Master 전담) | 단일 OS (하이브리드) | 개별 OS (노드별) |
| **확장성** | 낮음 ([[344_bus|버스]] 병목) | 매우 낮음 | 높음 | 매우 높음 |
| **통신 비용** | 낮음 ([[344_bus|Bus]]) | 낮음 | 중간 (Interconnect) | 높음 (Network) |
| **프로그래밍** | 쉬움 ([[092_thread_lwp|스레드]] 기반) | 보통 | 중간 | 어려움 (메시지 패싱) |

SMP는 개발자 입장에서 메모리가 하나인 것처럼 보이므로 멀티스레드 프로그래밍이 매우 직관적이다. 하지만 물리적으로 [[344_bus|버스]] 하나에 매달려야 하므로 확장성에 명확한 한계가 있다. 반면 MPP (Massively Parallel Processing)는 수천 대의 컴퓨터를 묶을 수 있지만, [[001_dikw_pyramid|데이터]]를 주고받는 비용이 크고 프로그래밍이 복잡하다. 현대의 하이엔드 서버는 SMP의 편의성과 MPP의 확장성을 절충한 [[377_numa_allocation|NUMA]] ([[377_numa_allocation|Non-Uniform Memory Access]]) 방식을 주로 채택한다.

- **📢 섹션 요약 비유**: SMP가 한 집에서 화장실을 공유하는 가족이라면, NUMA는 각 방에 화장실이 있지만 필요할 때 옆 방 화장실도 쓸 수 있는 고급 저택과 같고, MPP는 각자 집에서 사는 이웃 사촌들 사이의 [[083_relationship_in_er_model|관계]]와 같습니다.

## Ⅳ. 실무 적용 및 기술사적 판단

### 실무 시나리오

1. **DB 서버의 [[282_performance_tactics|성능]] 포화**: CPU 점유율은 높지 않은데 [[298_qkv_attention|쿼리]] 응답 시간이 급격히 느려지는 현상이 발생한다. 분석 결과, 수많은 CPU가 공유 자원([[048_latch|Latch]]/[[223_mutex|Mutex]])을 획득하기 위해 경합하며 [[344_bus|버스]] 트래픽을 유발하고 있었다. 이 경우 CPU를 추가하기보다 애플리케이션 레벨에서 [[001_dikw_pyramid|데이터]] 파티셔닝을 통해 CPU 간 간섭을 줄이거나, 하드웨어를 [[377_numa_allocation|NUMA]] 구조로 전환하여 메모리 [[140_bandwidth|대역폭]]을 [[136_variance|분산]]시켜야 한다.

2. **[[015_virtualization|가상화]] 환경의 [[041_resource_allocation|자원 할당]]**: [[054_hypervisor|하이퍼바이저]] 위에서 여러 개의 가상 머신([[598_vm_migration_nic|VM]])을 돌릴 때, 특정 VM에 과도한 vCPU를 할당하면 [[195_real_time_scheduling|SMP]] 구조의 오버헤드 때문에 오히려 전체 시스템의 스케줄링 효율이 떨어진다. 실무에서는 물리 CPU(pCPU)의 코어 수와 [[377_numa_allocation|NUMA]] 노드 경계를 고려하여 vCPU를 할당하는 '[[144_cpu_affinity|CPU Affinity]]' 설정이 필수적이다.

### 도입 [[435_checklist_based_testing|체크리스트]]
- **[[344_bus|버스]] [[140_bandwidth|대역폭]] [[396_validation|확인]]**: CPU 증가에 따른 메모리 [[140_bandwidth|대역폭]] 점유율이 70%를 넘지 않는가?
- **캐시 미스율 모니터링**: '[[409_false_sharing|False Sharing]]' (서로 다른 [[001_dikw_pyramid|데이터]]가 같은 캐시 라인에 있어 불필요한 [[194_consistency_database_integrity|일관성]] 오버헤드 발생) 현상이 심하지 않은가?
- **[[022_kernel_role|커널]] 락([[022_kernel_role|Kernel]] [[510_lock|Lock]]) 분석**: `Spinlock` 대기 시간이 전체 CPU 시간의 [[489_raid_10_hybrid|10]]%를 초과하는가?

### [[128_water_scrum_fall_anti_pattern|안티패턴]]
- **과도한 CPU 할당**: 워크로드가 [[430_index_fast_full_scan|병렬]]화되지 않는데 CPU 수만 늘리면, 락 경합과 캐시 무효화 비용 때문에 단일 CPU보다 [[282_performance_tactics|성능]]이 떨어지는 'Negative Scaling'이 발생할 수 있다.
- **지역성 무시**: 메모리 접근 패턴이 무작위(Random)라면 캐시 적중률이 급감하여 SMP의 [[282_performance_tactics|성능]] 이점이 사라진다.

- **📢 섹션 요약 비유**: 도로가 막히는데([[344_bus|버스]] 병목) 차만 계속 늘리면(CPU 추가) 전체 도착 시간은 오히려 늦어지는 교통 체증 현상과 같습니다.

### 미래 전망
현대 컴퓨팅은 단일 칩 안에 수십 개의 코어가 들어가는 'Many-core' 시대로 진입했다. 이에 따라 전통적인 공유 [[344_bus|버스]] 기반 SMP는 한계에 도달했으며, 칩 내부에서 네트워크 방식으로 [[001_dikw_pyramid|데이터]]를 주고받는 **[[367_noc|NoC]] ([[367_noc|Network on Chip]])** 기술과 결합하고 있다. 또한, [[231_ai_turing_test|인공지능]]([[190_ai_llm_requirements_specification|AI]]) 연산을 위해 GPU나 [[424_npu|NPU]] 같은 이기종 프로세서를 [[195_real_time_scheduling|SMP]] 구조에 통합하려는 **[[439_heterogeneous_computing|이기종 컴퓨팅]] ([[439_heterogeneous_computing|Heterogeneous Computing]])** 연구가 활발히 [[216_progress_in_synchronization|진행]] 중이다.

- **📢 섹션 요약 비유**: 주방 통로를 넓히는 데 한계가 오자, 이제는 주방 안에 작은 컨베이어 벨트([[367_noc|NoC]])를 설치하여 요리사들이 부딪히지 않고 음식을 나르는 시대로 가고 있는 것과 같습니다.

### 📈 관련 키워드 및 발전 흐름도

```text
[단일 코어 (Single Core)]
    │
    ▼
[비대칭 다중처리 (ASMP, Asymmetric Multiprocessing)]
    │
    ▼
[대칭 다중처리 (SMP, Symmetric Multiprocessing)]
    │
    ▼
[NUMA (Non-Uniform Memory Access)]
```

이 흐름도는 단일 코어에서 시작해 대칭 다중처리와 NUMA로 발전하는 구조 변화를 보여준다.
### 👶 어린이를 위한 3줄 비유 설명
1. SMP는 **"여러 명의 요리사가 하나의 큰 냉장고를 같이 쓰는 주방"**과 같아요. 
2. 모든 요리사가 똑같은 힘을 가지고 있어서, 냉장고에서 재료를 꺼내 각자의 프라이팬에서 요리를 동시에 할 수 있어요.
3. 요리사가 너무 많아지면 냉장고 문 앞에서 서로 부딪히기도 하지만, 한 명이 아파서 쉬더라도 다른 요리사들이 요리를 계속 완성할 수 있어 아주 든든하답니다!
