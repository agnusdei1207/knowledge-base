## 1. 처음 문제 정의

우리가 풀고 싶었던 문제는 단순히 "문서를 저장할 장소"가 아니었습니다.

- 사람마다 메모 위치가 달라서 정보가 흩어짐
- 기술 검토, 사업 아이디어, R&D 메모가 서로 연결되지 않음
- AI 에이전트가 읽고 정리할 수 있는 공통 포맷이 필요함
- 특정 SaaS에 종속되지 않는 자산 축적 구조가 필요함
- 웹에서 보기 쉬우면서도 원본은 단순해야 함

결론적으로 목표는 다음과 같이 정리되었습니다.

1. 원본 데이터는 단순해야 한다
2. 사람과 AI가 같이 편집할 수 있어야 한다
3. Git 기반 이력 관리가 가능해야 한다
4. 배포는 자동이어야 한다
5. 나중에 구조를 바꾸더라도 데이터는 살아남아야 한다

## 2. 검토했던 대안

### A. Notion / Confluence 계열

장점:
- 시작이 빠름
- 웹 편집이 쉬움
- 비개발자 친화적

단점:
- 데이터 포맷이 플랫폼에 종속됨
- AI 에이전트가 대량 수정하거나 구조적으로 링크 정리하기 불편함
- Git 기반 버전 관리와 자동 배포 흐름이 약함
- 장기적으로 사내 자산이 SaaS 안에 갇히기 쉬움

판단:
- 협업은 쉽지만 "AI와 함께 운영되는 내부 지식 자산"으로는 한계가 있다고 판단

### B. Obsidian 전용 운영

장점:
- 링크 기반 문서 작성이 매우 편함
- 로컬 파일 기반이라 데이터 소유권이 명확함
- 그래프 탐색 경험이 좋음

단점:
- 웹 공유와 조직 단위 열람 체계가 약함
- 여러 사용자가 공용 뷰를 보는 운영 모델로 확장하기엔 추가 작업이 필요함

판단:
- 작성 경험은 좋지만, 전 직원이 브라우저에서 보는 포털까지 연결하려면 별도 퍼블리싱 계층이 필요함

### C. 그래프 DB / 전용 지식그래프 시스템

장점:
- 관계 모델링이 강력함
- 질의와 시각화 확장성이 높음

단점:
- 초기에 운영 복잡도가 높음
- 문서 작성보다 시스템 운영 자체가 일이 되기 쉬움
- 직원들이 진입하기 어렵고 AI에게도 원문 단위 편집이 번거로움

판단:
- 현재 단계에는 과한 선택이었다고 봄

### D. MkDocs / Docusaurus 계열

장점:
- 정적 사이트 배포가 단순함
- 문서 사이트로는 안정적

단점:
- 우리가 원한 "문서 간 관계 탐색"과 그래프 경험이 약함
- 위키식 상호 링크 탐색의 체감이 Quartz보다 덜함

판단:
- 안정적 대안이지만, 이번 목적에는 Quartz 쪽이 더 적합

## 3. 최종 선택

최종적으로 채택한 구조는 아래와 같습니다.

- 작성 원본: Markdown
- 작성 공간: `content/`
- 링크 방식: 위키링크(`[[문서명]]`)
- 형상관리: GitHub
- 웹 퍼블리싱: Quartz
- 자동 배포: GitHub Actions
- 로컬/사내 미리보기: Docker Compose

이 구조는 작성, 버전관리, 퍼블리싱을 분리합니다.

- 사람과 AI는 `content/*.md`만 다룬다
- Quartz는 배포 시점에만 동작한다
- 웹 뷰는 파생 산출물이지 원본이 아니다

이 분리가 가장 중요했습니다.

---

## 4. 이 구조를 선택한 핵심 이유

### 4-1. 원본이 단순하다

원본은 결국 마크다운 파일입니다.

- 텍스트 편집기로 열 수 있음
- Git diff가 잘 보임
- 백업이 쉽고 이식성이 좋음
- AI가 읽고 수정하기 쉬움

문서 시스템이 바뀌어도 `content/`는 남습니다.

### 4-2. 사람과 AI가 같은 포맷을 공유한다

사람은 VS Code, GitHub, 에디터로 수정할 수 있고 AI는 같은 파일을 직접 읽고 링크를 정리할 수 있습니다.

이 점에서 Markdown은 협업용 공용 언어 역할을 합니다.

### 4-3. 배포 구조가 분리된다

우리가 원하는 것은 저장소 안을 빌드 파일로 더럽히지 않는 것이었습니다.

그래서 운영 원칙을 다음처럼 잡았습니다.

- 저장소에는 문서와 설정만 둔다
- Quartz 엔진은 배포 시점에만 불러온다
- `node_modules`, `package.json`, Quartz 소스는 상주시키지 않는다

이 덕분에 작성자 입장에서는 단순한 문서 저장소로 보입니다.

### 4-4. 그래프 탐색이 살아 있다

이번 선택에서 Quartz를 끝까지 유지한 이유는 단순 사이트 생성이 아니라 "관계 탐색 경험" 때문입니다.

- 문서 간 링크를 시각적으로 볼 수 있음
- 프로젝트, 사업, 기술, 메모가 서로 연결됨
- 개별 문서보다 지식망 전체를 보게 됨

이건 일반 문서 사이트와 차별화되는 지점입니다.

### 4-5. Git 기반 운영이 가능하다

누가 무엇을 바꿨는지 남고, AI 에이전트가 정리한 흔적도 추적할 수 있습니다.

또한 다음 같은 운영이 가능합니다.

- 문서 히스토리 추적
- 실수 복구
- 브랜치/PR 검토
- 자동 배포 연계

## 5. 운영하면서 확정한 원칙

### 원칙 1. 저장소는 문서 중심이어야 한다

문서 작성자가 봤을 때 저장소가 복잡해지면 안 됩니다.

- 핵심 관심사는 `content/`
- 설정은 최소화
- 빌드 파일은 저장소에 상주시지 않음

### 원칙 2. 공용 PC 단일 작업본 운영은 피한다

여러 사람이 하나의 작업 디렉터리를 번갈아 쓰는 구조는 충돌과 덮어쓰기 위험이 큽니다.

권장 방식:
- 각자 작업본 보유
- 작업 시작 전 pull
- 수정 후 commit / push

### 원칙 3. AI는 Quartz가 아니라 Markdown을 다룬다

AI 에이전트는 Quartz 엔진을 수정하는 존재가 아닙니다.

- AI의 역할: `content/*.md` 편집, 링크 정리, 요약, 구조화
- Quartz의 역할: 웹사이트 렌더링

이 역할 분리가 깨지면 운영이 금방 복잡해집니다.

### 원칙 4. 웹은 조회, 원본은 Git

사이트는 읽기 좋은 포털입니다.
원본 편집과 승인 흐름은 Git/GitHub를 중심으로 둡니다.

## 6. 지금 시점의 평가

현재 구조는 다음 조건을 만족합니다.

- 원본 데이터가 단순함
- GitHub Actions로 자동 배포 가능
- Quartz 그래프 뷰 제공
- AI 협업이 쉬움
- 저장소 오염을 최소화함

아직 남아 있는 과제도 있습니다.

- 웹에서 바로 수정하는 진짜 CMS형 편집 경험은 없음
- 비개발자 대상 편집 UX는 GitHub 또는 로컬 에디터 학습이 필요함
- 문서 수가 늘어나면 분류 규칙과 운영 규칙이 더 중요해짐

하지만 지금 단계에서는 "가볍고 오래 가는 구조"라는 점에서 가장 균형이 좋습니다.

---

## 7. 그래서 왜 이걸 선택했는가

한 문장으로 정리하면:

**가장 단순한 원본 포맷으로, 사람과 AI가 함께 문서를 쌓고, Git으로 관리하고, Quartz로 시각화할 수 있는 구조였기 때문입니다.**

좀 더 실무적으로 정리하면:

- 문서는 마크다운으로 남는다
- AI가 이해하고 수정하기 쉽다
- Git으로 검토와 복구가 가능하다
- 웹 포털로 조직 전체에 공유할 수 있다
- 기술적 유연성을 잃지 않는다

이게 현재 시점에서 가장 실용적인 선택이었습니다.

## 8. 다음 단계에서 무엇을 붙일 것인가

현재 구조는 "원본 Markdown + Git + Quartz"까지만 확정되어 있습니다.

하지만 직원 수가 늘고, 비개발자 편집 비중이 높아지고, 에이전트 접속 방식까지 표준화하려면 다음 계층이 추가로 필요합니다.

- 웹 편집 계층: [[decap-cms]]
- 검색/인덱싱 파생 계층: [[knowledge-pipeline]]

중요한 원칙은 하나입니다.

**원본은 계속 Markdown과 Git에 두고, 검색 인덱스와 AI 연결 계층은 모두 파생 계층으로 붙인다.**

이 원칙을 지키면 기능을 고도화해도 원본 자산과 운영 복잡도를 방어할 수 있습니다.
