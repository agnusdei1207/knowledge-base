## 1. 설계 원칙

먼저 원칙을 고정해야 합니다.

1. 원본은 항상 Markdown과 Git에 둔다
2. 검색 인덱스와 벡터 인덱스는 파생 데이터로만 둔다
3. 첨부파일과 비정형 자료도 원본 보존과 검색용 가공을 분리한다
4. 장애가 나도 최악의 경우 `content/`만 있으면 복구 가능해야 한다

이 원칙을 지키면 기능을 늘려도 복잡도가 폭증하지 않습니다.

## 2. 권장 데이터 흐름

### 입력 계층

입력 소스는 다양할 수 있습니다.

- 직원이 직접 작성한 Markdown
- 회의록
- PDF, PPT, DOCX
- 정책 문서
- 메신저 로그 요약본
- 영업 제안서 초안

### 정규화 계층

모든 입력은 아래 두 갈래로 나눕니다.

- 원본 보존본
- 검색/추론용 정규화본

권장 방식:
- 사람 문서는 `content/*.md`에 정리
- 첨부 원본은 별도 자산 경로에 저장
- PDF/DOCX 등은 텍스트 추출 후 Markdown 또는 텍스트 조각으로 변환

### 퍼블리싱 계층

- Quartz가 Markdown을 정적 포털로 빌드
- 직원은 브라우저에서 읽고 그래프로 탐색

### 인덱싱 계층

Git push 또는 PR merge를 계기로 비동기 인덱싱 수행

- OpenSearch: 키워드/BM25/필터 검색
- pgvector: 의미 검색
- 링크 그래프 메타데이터: related docs, backlink, 허브 중심성

### 에이전트 계층

MCP 기반 도구가 아래를 조합해 응답

- 원본 문서 조회
- 키워드 검색
- 의미 검색
- 링크 기반 후보 확장
- 승인 가능한 초안 작성

## 3. 검색은 어떻게 구성하는가

좋은 검색은 한 가지 엔진으로 끝나지 않습니다.

권장 조합:

### 1차 검색

- OpenSearch로 제목, 본문, 태그, 부서, 날짜 기준 검색

### 2차 의미 검색

- pgvector로 사용자 질의와 유사한 문서 조각 검색

### 3차 재정렬

다음 신호를 함께 사용해 재정렬합니다.

- 최근성
- 문서 허브 연결 수
- 제목 일치도
- 태그 일치도
- 수동 중요도
- 링크 거리

이렇게 하면 "정확한 단어를 모를 때"와 "정확한 문서를 다시 찾을 때"를 둘 다 커버하기 쉽습니다.

---

## 4. 비정형 자료는 어떻게 커버하는가

비정형 자료를 억지로 전부 Markdown으로만 맞추면 오히려 운영이 망가집니다.

권장 방식은 분리입니다.

### 원본 보존

- PDF, PPT, 이미지, 스캔본은 그대로 저장

### 추출/정규화

- OCR 또는 텍스트 추출
- 문단 단위 분해
- 제목, 작성자, 날짜, 부서 같은 메타데이터 추출

### 연결 문서 생성

- 사람과 AI가 읽을 요약본은 Markdown으로 생성
- 원본 파일 링크를 함께 남김

즉:

- 원본은 원본대로 남기고
- 사람이 읽을 표준 문서는 Markdown으로 만들고
- 검색용 인덱스는 별도로 만든다

이 3단 분리가 핵심입니다.

## 5. 휴먼 리더블과 검색 성능을 같이 잡는 법

둘을 같은 저장 구조에서 해결하려고 하면 문서가 금방 난잡해집니다.

그래서 아래처럼 역할을 분리합니다.

### 사람을 위한 문서

- 짧은 제목
- 명확한 문단
- 허브 문서 연결
- 위키 링크 사용

### 기계를 위한 메타데이터

- 태그
- 부서
- 문서 유형
- 작성/개정일
- 관련 프로젝트

### 검색엔진을 위한 인덱스

- 토큰화 결과
- 벡터 임베딩
- 링크 그래프 특징량

사람이 보는 Markdown에 검색용 내부 구조를 과도하게 박아 넣지 않는 것이 중요합니다.

## 6. 운영 복잡도를 낮추는 실전 규칙

복잡도를 낮추려면 기능보다 경계를 먼저 정해야 합니다.

### 소스 오브 트루스

- 오직 Git의 Markdown만 진짜 원본으로 간주

### 인덱스 재생성 가능성

- OpenSearch와 pgvector는 언제든 다시 만들 수 있어야 함

### 비동기 처리

- 업로드 시 즉시 완벽 인덱싱하려 하지 말고 큐 기반 비동기 처리

### 승인 흐름

- 대규모 수정은 PR 또는 CMS 승인 흐름으로 통제

### 문서 템플릿

- 사업, 운영, 개발, 영업 문서는 공통 템플릿 유지

## 7. 추천 파이프라인 구성

### 최소 구성

- GitHub
- Markdown
- Quartz
- GitHub Actions

장점:
- 가장 단순

한계:
- 검색 고도화와 웹 편집은 부족

### 권장 구성

- GitHub 또는 Forgejo/Gitea
- Markdown
- Quartz
- Decap CMS
- OpenSearch
- PostgreSQL + pgvector
- MCP

장점:
- 사람, 웹, AI, 검색을 균형 있게 커버

복잡도:
- 중간

### 과한 구성

- 초기에 그래프 DB, 별도 CMS DB, 커스텀 백오피스를 한 번에 붙이는 방식

문제:
- 운영 인력과 유지보수 비용이 너무 빨리 커짐

## 8. 최종 판단

현재 단계에서는 아래가 가장 균형이 좋습니다.

**Markdown을 원본으로 유지하고, Quartz는 조회 포털로 두고, Decap CMS는 편집용으로 붙이고, 검색은 OpenSearch와 pgvector를 파생 인덱스로 운용하고, 에이전트는 MCP를 통해 접근하게 한다.**

이 구조면:

- 직원은 읽고 쓸 수 있고
- AI는 공통 인터페이스로 붙을 수 있고
- 검색 품질을 계속 높일 수 있고
- 원본 자산은 끝까지 단순하게 유지됩니다
