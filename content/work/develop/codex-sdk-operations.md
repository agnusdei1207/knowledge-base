## 1. 전제

우리 조직은 개발자, 디자이너, 기획자, R&D, 마케팅까지 전부 AI 코딩 에이전트를 사용합니다.

이 환경에서는 역할을 이렇게 나누는 것이 가장 안정적입니다.

- 직원 개인 작업: Codex CLI 또는 에이전트 클라이언트 사용
- 공용 검색/문맥: `knowledgebase-mcp`
- 내부 문서 자동화: Python Codex SDK 서비스
- 최종 반영: Git 브랜치와 PR

중요한 점은 <strong>직원용 대화형 사용과 내부 자동화 백엔드를 분리하는 것</strong>입니다.

---

## 2. 왜 Codex SDK를 따로 쓰는가

직원이 각자 Codex를 쓰는 것만으로도 문서는 작성할 수 있습니다.

하지만 조직 운영 관점에서는 아래 같은 반복 작업이 남습니다.

- 회의록을 문서 템플릿에 맞게 정리
- 코드 변경 후 관련 운영 문서 갱신
- 중복 문서 탐지
- 링크 누락 문서 탐지
- 문서 초안 생성 후 PR 생성
- 오래된 문서 검토 배치 실행

이런 일은 사람마다 수동으로 시키기보다, <strong>내부 Python 서비스가 Codex SDK로 일괄 처리</strong>하는 편이 낫습니다.

---

## 3. 공식 SDK 상태

현재 Codex는 Python SDK를 제공합니다.

- 패키지명: `openai-codex`
- 설치: `pip install openai-codex`
- 기본 개념: `Codex` 인스턴스를 만들고, thread/turn 단위로 실행

이 SDK는 문서 자동화 워커를 만들기에 적합합니다.

실무적으로는:

- 직원용 인터랙티브 도구가 아니라
- 서버 내부 배치/자동화 런타임으로 쓰는 것이 더 적합합니다

## 4. 권장 아키텍처

### 직원 사용 계층

- Codex CLI
- Claude Code
- 기타 MCP 지원 클라이언트

### 공용 지식 계층

- Git + Markdown
- Quartz
- `knowledgebase-mcp`

### 내부 자동화 계층

- Python 서비스
- `openai-codex`
- GitHub API 또는 로컬 Git

흐름은 아래처럼 가져가는 것이 좋습니다.

1. 직원이 에이전트에 업무 요청
2. 에이전트가 `knowledgebase-mcp`로 관련 문서 검색
3. 내부 서비스가 Codex SDK로 초안 생성 또는 수정안 생성
4. 서비스가 브랜치 생성
5. PR 생성
6. 검토 후 머지

---

## 5. 직군별 활용 방식

### 개발자

- 코드 변경 후 README, 운영 문서, 배포 가이드 갱신 초안 생성
- 아키텍처 문서와 실제 구현 차이 점검
- 릴리스 노트 초안 생성

### 디자이너

- 디자인 변경사항을 제품 문서와 온보딩 문서에 반영
- 화면 흐름 설명 문서 초안 생성
- 브랜드/톤앤매너 변경이 반영되지 않은 문서 탐지

### 기획자

- 회의 메모를 요구사항 문서 형식으로 정리
- 정책 변경사항을 여러 문서에 반영할 초안 생성
- 고객 요구와 내부 기능 문서 연결

### R&D

- 실험 노트를 표준 템플릿으로 정리
- 연구 결과를 사업/개발 문서와 연결
- 기술 검토 메모에서 중복/충돌되는 가설 탐지

### 마케팅

- 제품 변경사항을 영업/마케팅 문서에 반영
- 캠페인 회고를 템플릿화
- FAQ, 제안 메시지, 포지셔닝 문서 초안 생성

핵심은 직군별로 도구를 나누는 게 아니라, <strong>같은 지식 원본 위에서 역할만 다르게 쓰는 것</strong>입니다.

---

## 6. 먼저 만들 가치가 큰 자동화 작업

처음부터 큰 시스템을 만들 필요는 없습니다.

우선순위가 높은 작업은 아래 세 가지입니다.

### A. 회의록 -> 문서 초안 생성

- 입력: 메모, 채팅 로그, 회의록
- 출력: `content/*.md` 초안
- 후속: 자동 PR 생성

### B. 코드 변경 -> 문서 수정 제안

- 입력: Git diff, 관련 디렉터리, 릴리스 범위
- 출력: 수정 대상 문서 목록과 패치 초안
- 후속: 자동 PR 생성

### C. 문서 상태 점검

- 오래된 문서 찾기
- 고아 문서 찾기
- 링크 누락 찾기
- 중복 문서 후보 찾기

이 세 가지가 가장 빨리 체감 가치를 줍니다.

---

## 7. 권장 실행 규칙

Codex SDK를 내부 서비스로 쓸 때는 아래 규칙이 중요합니다.

### 직접 main 수정 금지

- 항상 브랜치 생성
- 항상 PR로 반영

### 먼저 검색 후 생성

- 바로 쓰지 말고 `knowledgebase-mcp`로 관련 문서부터 찾기

### 대상 파일 범위 제한

- 한 번의 작업에서 수정 가능한 파일 수를 제한
- 관련 허브 문서 중심으로 범위를 좁히기

### 템플릿 강제

- 사업, 운영, 개발, 영업 문서는 미리 정한 섹션 구조를 유지

### 인간 승인 유지

- 자동 생성은 초안까지만
- 승인과 머지는 사람이 담당

## 8. 최소 구현 예시

개념적으로는 이런 흐름입니다.

```python
from openai_codex import Codex

prompt = """
knowledgebase 검색 결과를 참고해 content/operations.md 업데이트 초안을 작성해라.
직접 main에 반영하지 말고 PR용 수정안만 반환해라.
"""

with Codex() as codex:
    codex.login_api_key("sk-...")
    thread = codex.thread_start()
    result = thread.run(prompt)
    print(result.final_response)
```

이 코드는 완성품이 아니라, 내부 문서 워커가 가져야 할 기본 구조를 보여주는 예시입니다.

---

## 9. 추천 운영 모델

가장 균형이 좋은 구조는 아래입니다.

- 직원은 Codex를 직접 사용
- 공용 문맥은 MCP로 통일
- 반복 문서 업무는 Codex SDK 백엔드가 수행
- 결과는 PR로만 반영

이렇게 해야:

- 직군이 달라도 같은 지식 원본을 공유하고
- 검색 문맥이 통일되고
- 반복 문서 업무가 자동화되며
- 운영 통제가 무너지지 않습니다

---

## 10. 최종 판단

Codex SDK는 직원 개인이 직접 만지는 도구라기보다, <strong>회사 내부 문서 자동화 엔진</strong>으로 보는 편이 맞습니다.

정리하면:

- 사람은 Codex로 요청한다
- 내부 서비스는 Codex SDK로 처리한다
- 지식 검색은 MCP가 맡는다
- 반영은 Git PR이 맡는다

이 구조가 전 직군 사용 환경에서 가장 실용적입니다.
