# 21. [[001_dikw_pyramid|데이터]] 조작 언어 ([[083_dml|DML]]: [[001_dikw_pyramid|Data]] Manipulation Language)

#### 핵심 인사이트 (3줄 요약)
> 1. **본질**: DDL이 [[002_database_definition|데이터베이스]]의 뼈대와 규칙을 세운다면, DML은 그 구조 안에 실제 비즈니스 가치를 지닌 [[001_dikw_pyramid|데이터]]를 [[087_process_state_transition|생성]], 수정, 삭제, 조회(CRUD)하는 생명선 역할을 한다.
> 2. **가치**: [[038_relational_algebra|관계 대수]]([[038_relational_algebra|Relational Algebra]]) 기반의 선언적 문법을 통해 수천만 건의 [[001_dikw_pyramid|데이터]]를 루프(Loop) 없이 단 한 줄의 질의어로 고속 조작할 수 있는 극강의 [[298_qkv_attention|쿼리]] 생산성을 제공한다.
> 3. **융합**: DML은 [[001_dikw_pyramid|데이터]] 버퍼 갱신, 행 잠금(Row-level [[510_lock|Lock]]), [[393_undo|Undo]]/[[234_redo_roll_forward_durability_recovery|Redo]] 로깅을 동반하는 [[191_transaction_concept_states|트랜잭션]]의 실체적 [[507_acid_properties|트리거]]이며, [[163_optimizer_sql_execution_plan_generator|옵티마이저]]의 [[282_performance_tactics|성능]] 튜닝 대상이 되는 핵심 워크로드다.

---

### Ⅰ. 개요 및 필요성 ([[033_context|Context]] & Necessity)
[[002_database_definition|데이터베이스]]의 존재 이유는 결국 '[[001_dikw_pyramid|데이터]]를 활용'하기 위함이다. 아무리 견고한 [[005_schema|스키마]]([[020_ddl|DDL]])가 준비되어 있더라도, 사용자와 애플리케이션이 원하는 시점에 정확한 [[001_dikw_pyramid|데이터]]를 밀어 넣고, 뽑아보고, 수정하지 못한다면 의미가 없다. 이 실제적인 [[001_dikw_pyramid|데이터]] 조작 요구를 해결하기 위해 설계된 것이 [[083_dml|DML]]([[001_dikw_pyramid|Data]] Manipulation Language)이다.

과거 [[501_file_definition_logical_record|파일]] 시스템이나 [[459_quic_fec_forward_error_correction|초기]] 네트워크 DB 시절에는 [[001_dikw_pyramid|데이터]]를 검색([[520_select|SELECT]])하거나 변경(UPDATE)하려면 개발자가 직접 물리적인 디스크 블록 주소를 따라가는 절차적 코드를 작성해야 했다. 이로 인해 [[001_dikw_pyramid|데이터]]가 조금만 커져도 애플리케이션 코드가 스파게티처럼 엉키고 시스템 메모 시 스파게티처럼 엉키고 시스템 메모리가 마비되었다. 그러나 SQL 표준의 DML은 [[001_dikw_pyramid|데이터]]를 철저히 '수학적 집합(Set)'으로 대우한다. 사용자가 "연봉이 5000 이상인 영업부 직원의 이름을 가져와([[520_select|SELECT]])"라고 집합적 요구사항만 던지면, 내부의 [[163_optimizer_sql_execution_plan_generator|옵티마이저]]가 가장 빠른 물리적 디스크 접근 [[001_algorithm_definition|알고리즘]]을 찾아내 대신 수행해주는 패러다임의 혁명이 일어났다.

오늘날 전 세계 수조 건의 전자상거래, 금융 결제, 물류 시스템 백엔드는 바로 이 DML의 `INSERT`, `UPDATE`, `DELETE`, `SELECT` 네 가지 기본 동사에 의해 실시간으로 통제되고 있으며, 이 [[158_instruction|명령어]]들의 실행 최적화 여부가 전체 [[090_service_kubernetes_network_load_balancing|서비스]]의 응답 [[015_지연_데이터_관점|지연]]([[141_latency|Latency]])을 결정짓는 척도가 된다.

아래 다이어그램은 애플리케이션의 [[083_dml|DML]] [[298_qkv_attention|쿼리]]가 어떻게 디스크 I/O를 우회하여 메모리(버퍼 풀) 공간에서 [[148_5g_embb_urllc_mmtc|초고속]]으로 처리되는지, 현대 [[502_dbms|DBMS]] 아키텍처의 [[017_hardware_interrupt|비동기적]] [[289_cqrs_db|쓰기]](Write-behind) 구조를 보여준다.

```text
[DML 실행에 따른 메모리 및 디스크 상태 전이]

 App ──"UPDATE 급여 SET 5000"──▶ (DBMS 엔진 진입)
                                         ↓
┌───────────────── Memory (Buffer Pool) ──────────────────┐
│ 1. 해당 데이터 블록이 메모리에 없으면 디스크에서 적재 │
│ 2. Row Lock 획득 후 데이터 값 변경 (Dirty Block 발생) │
│ 3. 이전 값(Old)은 Undo 버퍼에, 새 값(New)은 Redo 버퍼에 기록 │
└─────────────────────────┬───────────────────────────────┘
  (비동기 I/O 대기)       │ (Commit 시점 또는 체크포인트 시점에 내려씀)
┌─────────────────────────▼───────────────────────────────┐
│ ┌───────────────┐ ┌──────────────┐ ┌────────────────┐ │
│ │ Data File(DB) │ │ Undo Segments│ │ Redo Log Files │ │
│ └───────────────┘ └──────────────┘ └────────────────┘ │
└────────────────────── Physical Disk ────────────────────┘
```

이 구조도의 핵심은 [[083_dml|DML]] 작업(갱신/삽입/삭제)이 **디스크([[001_dikw_pyramid|Data]] [[501_file_definition_logical_record|File]])에 즉시 기록되지 않고 메모리(버퍼 풀) 위에서 [[369_logic_bomb|논리]]적으로 먼저 수행된다는 점**이다. 만약 수천 건의 `UPDATE`를 할 때마다 디스크 헤더를 움직여 기록한다면, 물리적 I/O 병목으로 인해 [[191_transaction_concept_states|트랜잭션]] [[282_performance_tactics|성능]]은 바닥으로 곤두박질칠 것이다. DBMS는 메모리의 블록만 수정한 상태(Dirty Block)로 애플리케이션에 완료 [[130_signal|신호]]를 보낸 뒤, 변경 내역만 시퀀셜(Sequential)하게 [[234_redo_roll_forward_durability_recovery|Redo]] [[568_logs_distributed_logging_elk_fluentd|로그]]에 남겨 [[196_durability_permanent_storage|영속성]]을 보장하고, 실제 [[001_dikw_pyramid|데이터]] [[501_file_definition_logical_record|파일]] 반영은 백그라운드 프로세스가 여유 있을 때 몰아서(Batch) 처리하는 [[015_지연_데이터_관점|지연]] [[289_cqrs_db|쓰기]](Deferred Write) 기법을 사용한다. 따라서 개발자는 DML이 단순히 텍스트 명령이 아니라, 메모리 [[335_swapping|스와핑]]과 [[191_transaction_concept_states|트랜잭션]] [[568_logs_distributed_logging_elk_fluentd|로그]]를 대량 생산하는 무거운 시스템 콜임을 인지해야 한다.

📢 **섹션 요약 비유**: 마치 결제 내역([[083_dml|DML]])을 발생할 때마다 은행 금고(디스크)까지 뛰어가서 기록하는 대신, 빠른 장부(메모리 버퍼)에 우선 적어두고 나중에 퇴근할 때 한 번에 금고 장부를 정리하여 속도를 극대화하는 것과 같습니다.

### Ⅱ. 아키텍처 및 핵심 원리 (Deep Dive)
DML의 핵심 [[158_instruction|명령어]] 4가지는 [[001_dikw_pyramid|데이터]]를 조작하지만, 시스템 내부에서 발생시키는 '락([[510_lock|Lock]])'의 수준과 장애 발생 시나리오의 성격이 각기 다르다.

| [[083_dml|DML]] [[158_instruction|명령어]] | 핵심 동작 및 용도 | 내부 시스템 오버헤드 ([[510_lock|Lock]] 및 병목 요소) | 비유 |
|:---|:---|:---|:---|
| **[[520_select|SELECT]]** | 조건에 맞는 [[001_dikw_pyramid|데이터]] 집합 필터링 조회 | **Shared [[510_lock|Lock]] (읽기 락)**: 타 [[160_session_controlling_terminal|세션]] 읽기는 허용하나 X-[[510_lock|Lock]] 획득은 차단. [[428_table_full_scan|테이블 풀 스캔]] 시 메모리([[526_first_normal_form|PGA]])와 I/O 부하 심각 | 도서관에서 책 찾아 읽기 |
| **INSERT** | 새로운 [[001_dikw_pyramid|데이터]] [[063_relation_tuple_cardinality|튜플]](행) 삽입 | **고유성 체크 병목**: PK 중복 여부를 찾기 위해 [[154_database_index_b_tree_search_optimization|인덱스]] 리프 노드 분할([[154_database_index_b_tree_search_optimization|Index]] Split) 유발 빈번 | 도서관 서가에 새 책 꽂기 |
| **UPDATE** | 기존 [[001_dikw_pyramid|데이터]] 행의 [[082_attribute_types_er_model|속성]]값 갱신 | **Row Exclusive [[510_lock|Lock]]**: 타 [[160_session_controlling_terminal|세션]] 동시 갱신 차단. 이전 값 보존을 위해 대량의 [[393_undo|Undo]] 세그먼트 [[087_process_state_transition|생성]] 유발 | 책의 특정 [[286_page_frame|페이지]] 내용 고쳐쓰기 |
| **DELETE** | 조건에 맞는 [[063_relation_tuple_cardinality|튜플]]을 개별 삭제 | **가장 무거운 부하**: 행 단위 지움 + 삭제 [[658_ir_recovery|복구]]를 위한 전체 [[393_undo|Undo]] 로깅 + [[154_database_index_b_tree_search_optimization|인덱스]] 트리 재정렬 | 책을 한 권씩 폐기하고 기록 남기기 |

이 중에서도 [[001_dikw_pyramid|데이터]]를 조회하는 `SELECT` 구문은 가장 복잡한 파싱 구조를 지닌다. RDBMS는 [[520_select|SELECT]] [[298_qkv_attention|쿼리]] 내의 `FROM → WHERE → GROUP BY → HAVING → SELECT → ORDER BY` 순서로 [[369_logic_bomb|논리]]적 실행 단계를 거치며, 집합을 축소(Filter)하고 결합([[521_join|Join]])한다. 

다음 다이어그램은 가장 심각한 [[083_dml|DML]] [[282_performance_tactics|성능]] 저하 원인 중 하나인 `인덱스 스플릿(Index Split)`이 대량 `INSERT` [[083_dml|DML]] 환경에서 어떻게 일어나는지 구조적으로 설명한다.

```text
[B-Tree 인덱스 구조의 잦은 INSERT 병목 현상]

        [ Root Node (10~50) ]
             ↙      ↘
  [ Leaf (10, 20) ]  [ Leaf (30, 40, 50) ] ◀ (빈 공간 없음)
                               ▲
                 (새로운 DML) INSERT VALUES (35) 발생

       (결과: 블록 분할 및 트리 재구성 오버헤드 발생)
        [ Root Node (10~50) ]
             ↙       ↓      ↘
[ Leaf (10, 20) ] [Leaf(30, 35)] [Leaf(40, 50)] => 구조 변경을 위한 심각한 I/O 블로킹 유발
```

이 도식의 핵심은 테이블에 [[001_dikw_pyramid|데이터]]를 밀어 넣는(INSERT, [[083_dml|DML]]) 행위가 단일 동작으로 끝나지 않고, 테이블에 연결된 **모든 [[154_database_index_b_tree_search_optimization|인덱스]] 자료구조([[064_b_tree|B-Tree]])의 연쇄적인 수정**을 강제한다는 점이다. 특히 [[154_database_index_b_tree_search_optimization|인덱스]]의 특정 리프 블록이 가득 찬 상태에서 중간 값(예: 35)이 인서트되면, DBMS는 블록을 반으로 쪼개고(Split) 부모 노드의 포인터를 갱신하는 무거운 물리적 작업을 수행한다. 이 짧은 순간 동안 해당 [[154_database_index_b_tree_search_optimization|인덱스]] 구간은 배타적 잠금 상태가 되어 후속 DML들이 모두 대기(Wait)하게 된다. 초당 만 건씩 인서트되는 대규모 로깅 시스템에서 [[154_database_index_b_tree_search_optimization|인덱스]]를 5개씩 걸어두면 디스크 I/O가 마비되는 이유가 바로 이 아키텍처 원리 때문이다. 

📢 **섹션 요약 비유**: 책꽂이([[154_database_index_b_tree_search_optimization|인덱스]] 블록)가 가득 찼는데 억지로 중간에 새 책(INSERT [[083_dml|DML]])을 꽂으려면, 책꽂이를 통째로 분해해서 칸을 늘리는 대공사([[154_database_index_b_tree_search_optimization|인덱스]] 스플릿)를 치러야 하므로 삽입 속도가 느려지는 것과 같습니다.

### Ⅲ. 융합 비교 및 다각도 분석 (Comparison & Synergy)
DML을 사용할 때 가장 크게 부딪히는 실무적 트레이드오프는 "단건 처리(Row-by-Row)"와 "집합적 처리(Set-based/Bulk)" 패러다임 간의 [[282_performance_tactics|성능]] 및 자원 소모 비교다.

| 비교 요소 | 단건 루프 [[083_dml|DML]] (Procedural / Row-by-Row) | 집합적 Bulk [[083_dml|DML]] (Set-based) | 판단 포인트 |
|:---|:---|:---|:---|
| **처리 방식** | 애플리케이션 FOR 루프 내에서 1건씩 INSERT/UPDATE | `INSERT INTO .. SELECT` 등 하나의 SQL로 수만 건 갱신 | 네트워크 비용 및 파싱 |
| **네트워크 I/O**| 10만 건 처리 시 10만 번의 DB 왕복 트래픽 | 1번의 [[298_qkv_attention|쿼리]] 전송으로 엔진 내부 연산 | I/O [[015_지연_데이터_관점|지연]]([[141_latency|Latency]]) 압도적 |
| **[[191_transaction_concept_states|트랜잭션]]/[[568_logs_distributed_logging_elk_fluentd|로그]]**| 1건마다 자동 커밋 시 과도한 [[234_redo_roll_forward_durability_recovery|Redo]]/[[393_undo|Undo]] 플러시 부하 | 한 번의 거대한 [[191_transaction_concept_states|트랜잭션]] 묶음 | [[658_ir_recovery|복구]] 안정성 vs [[510_lock|Lock]] 점유 시간 |
| **적용 시나리오**| 복잡한 외부 [[014_api_posix|API]] 결합 등 분기 로직이 섞인 작업 | 단순 대용량 [[001_dikw_pyramid|데이터]] 마이그레이션, 집계 갱신 | [[282_performance_tactics|성능]] 튜닝의 최우선순위 |

초보 개발자들은 객체지향적 사고에 익숙해진 나머지 대용량 [[001_dikw_pyramid|데이터]]를 처리할 때 [[055_array|배열]] 리스트를 가져와서 반복문(Loop)을 돌리며 건건이 `UPDATE` 구문을 날린다. 이는 [[002_database_definition|데이터베이스]] [[282_performance_tactics|성능]]을 갉아먹는 최악의 [[128_water_scrum_fall_anti_pattern|안티패턴]]([[161_anti_pattern|Anti-pattern]])이다.

아래는 단건 [[083_dml|DML]] 처리 방식과 다중버전 [[014_concurrency|동시성]] 제어([[449_mvcc|MVCC]]) 하에서의 읽기/[[289_cqrs_db|쓰기]] 충돌 회피 메커니즘을 비교한 [[065_state_diagram|상태도]]이다.

```text
┌────────────────── [동시성 모델 (MVCC 지원)] ─────────────────┐
│ TX 1 (DML 쓰기): UPDATE 계좌 SET 잔액=0 WHERE ID=A             │
│   └─ [레코드 A에 X-Lock 획득, 버퍼 갱신, 이전 값은 Undo에 저장]│
├──────────────────────────────────────────────────────────────┤
│ TX 2 (DML 읽기): SELECT 잔액 FROM 계좌 WHERE ID=A              │
│   └─ 💥 충돌 회피: TX 1의 X-Lock 대기 없이, Undo 영역에        │
│                    저장된 '이전 값(원래 잔액)'을 읽어옴(CR Read)│
└──────────────────────────────────────────────────────────────┘
```

이 [[014_concurrency|동시성]] 흐름도의 핵심은 DML의 읽기([[520_select|SELECT]])와 [[289_cqrs_db|쓰기]](UPDATE) 간의 블로킹([[122_sync_async_communication|Blocking]]) 한계를 혁신적으로 풀어낸 [[449_mvcc|MVCC]](Multi-Version [[508_concurrency_control|Concurrency Control]]) 아키텍처다. 과거 시스템은 누군가 [[001_dikw_pyramid|데이터]]를 갱신(UPDATE)하고 있으면 커밋 전까지 아무도 그 [[001_dikw_pyramid|데이터]]를 읽을 수 없어 시스템 대기 시간이 길었다. 하지만 현대 DBMS는 [[083_dml|DML]] 갱신 시 발생하는 '[[393_undo|Undo]] 세그먼트([[098_rollback_strategy_pipeline_error_threshold|롤백]] 용도)'를 재활용하여, [[289_cqrs_db|쓰기]] [[191_transaction_concept_states|트랜잭션]]이 끝나지 않았더라도 다른 사용자가 과거 시점의 [[022_snapshot_backup_architecture|스냅샷]] [[288_version_ihl_tos_total_length|버전]]을 막힘없이 읽게 해준다. 따라서 실무에서 수백만 건의 집계 [[083_dml|DML]] [[298_qkv_attention|쿼리]]가 돌고 있는 도중에도 사용자들은 [[090_service_kubernetes_network_load_balancing|서비스]] 중단 없이 실시간 조회가 가능한 시너지를 얻게 된다. 

📢 **섹션 요약 비유**: 문서([[001_dikw_pyramid|데이터]]) 원본을 동료가 수정(UPDATE)하고 있을 때, 밖에서 기다리는 대신 수정 전 복사본([[393_undo|Undo]] [[022_snapshot_backup_architecture|스냅샷]])을 미리 받아 읽어봄으로써 업무([[520_select|SELECT]])가 정체되지 않고 돌아가게 하는 것과 같습니다.

### Ⅳ. 실무 적용 및 기술사적 판단 ([[268_strategy_pattern|Strategy]] & Decision)
운영 환경에서 잘못 작성된 1줄의 [[083_dml|DML]] [[298_qkv_attention|쿼리]]는 [[163_optimizer_sql_execution_plan_generator|옵티마이저]]를 속여 전체 DB 서버의 CPU를 100%로 솟구치게 만드는 시한폭탄이다. [[083_dml|DML]] 작성 시의 [[154_database_index_b_tree_search_optimization|인덱스]] 설계와 [[191_transaction_concept_states|트랜잭션]] 분할 [[268_strategy_pattern|전략]]이 필수적이다.

1. **실무 시나리오: 풀 테이블 스캔(Full Table Scan)을 유발하는 [[083_dml|DML]] 실수**
   - **상황**: 수억 건의 결제 테이블에서 `SELECT * FROM PAY WHERE TO_CHAR(pay_date, 'YYYY') = '2023'` 형태의 조회를 실행하여 DB 서버가 뻗음.
   - **원인 및 판단**: 좌변 가공 금지 원칙([[154_database_index_b_tree_search_optimization|인덱스]] 무효화)을 위반. 컬럼(`pay_date`) 자체를 함수로 가공하면 [[163_optimizer_sql_execution_plan_generator|옵티마이저]]는 해당 컬럼의 [[064_b_tree|B-Tree]] [[154_database_index_b_tree_search_optimization|인덱스]]를 타지 못하고 테이블 전체 블록을 뒤지는 풀 스캔(FTS)을 강행한다.
   - **개선 로직**: 질의 조건을 `WHERE pay_date >= '2023-01-01' AND pay_date < '2024-01-01'` 형태로 수정(범위 검색)하여 [[154_database_index_b_tree_search_optimization|인덱스]] 스캔을 강제 유도([[429_index_range_scan|Index Range Scan]])한다.
2. **도입 [[435_checklist_based_testing|체크리스트]]: 대용량 [[001_dikw_pyramid|데이터]] 일괄 삭제/갱신 (Chunk [[083_dml|DML]])**
   - 1억 건의 오래된 이력 [[001_dikw_pyramid|데이터]]를 삭제(`DELETE`)해야 한다. 한 번의 [[298_qkv_attention|쿼리]]로 실행하면?
   - [[191_transaction_concept_states|트랜잭션]] [[568_logs_distributed_logging_elk_fluentd|로그]] 버퍼 및 [[393_undo|Undo]] 테이블스페이스가 터져(ORA-01555 [[637_zfs_snapshot_cow_architecture|Snapshot]] Too Old 등) [[298_qkv_attention|쿼리]]가 강제 취소되고 [[098_rollback_strategy_pipeline_error_threshold|롤백]]되는 대형 장애 발생. 또한 대량의 [[215_exclusive_lock_write_concurrency|배타 락]](X-[[510_lock|Lock]])을 장시간 점유하여 [[014_concurrency|동시성]] 마비.
   - **기술사적 결단**: 대용량 DML은 절대 한 [[191_transaction_concept_states|트랜잭션]]에 담지 마라. `LIMIT 10000`이나 일자별/PK 범위별로 쪼개어(Chunking) 여러 번의 작고 짧은 [[191_transaction_concept_states|트랜잭션]]으로 커밋하면서 삭제 루프를 돌리는 '배치 분할 처리 아키텍처'를 반드시 구성해야 한다.

아래 [[124_decision_tree|의사결정 트리]]는 애플리케이션에서 대량의 [[001_dikw_pyramid|데이터]]를 삽입(Insert)해야 할 때 발생하는 오버헤드를 제어하기 위한 [[282_performance_tactics|성능]] 분기 플로우이다.

```text
[대규모 데이터 INSERT DML 발생]
   ↓
(Q1. 건수가 수백만 건 이상이며, 일회성 마이그레이션 성격인가?)
   ├─ 예 ────> [DB Native 벌크 로더 사용 (SQL*Loader, COPY 명령어)] => 파싱 우회 초고속 적재
   └─ 아니오 ──> (Q2. 실시간 트랜잭션이며 테이블에 인덱스가 많은가?)
                   ├─ 아니오 ──> [일반 INSERT 구문 실행]
                   └─ 예 ─────> [비동기 메시지 큐(Kafka) + 버퍼링 기반 배치 인서트(Batch Insert) 튜닝]
```

이 의사결정 흐름의 핵심은 DML의 파싱 비용(Parsing Cost)과 I/O 충돌 병목을 우회하는 설계 지혜다. 한 건씩 `INSERT`를 날리면 [[1002_network_delay_rtt_oneway_delay_components|네트워크 지연]]과 SQL 파싱 오버헤드가 건건이 누적된다. 따라서 개발자는 JDBC의 `executeBatch()` 같은 벌크 인서트(Batch [[083_dml|DML]]) 기능을 활용하여 수천 건의 페이로드를 단 한 번의 네트워크 호출로 밀어 넣거나, 초고부하 상태에서는 [[179_kafka_flink_watermark_time_window|Kafka]] 같은 [[389_mesh_topology|메시]]지 큐를 앞에 두어 [[083_dml|DML]] 트래픽을 완충([[454_buffering|Buffering]])하는 방어막을 구축해야 [[002_database_definition|데이터베이스]] 다운을 막을 수 있다.

📢 **섹션 요약 비유**: 수만 명의 관객(대량 INSERT [[001_dikw_pyramid|데이터]])을 경기장에 입장시킬 때, 1명씩 신분증 검사를 하면 입구가 마비됩니다. 100명 단위 단체 티켓(Batch [[083_dml|DML]])으로 묶거나, 대기열 공간([[389_mesh_topology|메시]]지 큐)을 만들어 입장 속도를 부하에 맞게 조절해야 하는 것과 같습니다.

### Ⅴ. 기대효과 및 결론 (Future & Standard)
DML은 [[001_dikw_pyramid|데이터]]라는 자산을 가공하고 추출하여 비즈니스 통찰력과 [[090_service_kubernetes_network_load_balancing|서비스]] 가치로 변환시키는 엔진의 피스톤 운동이다. SQL이라는 세계 공통의 비절차적 질의어를 통해 개발자는 더 이상 복잡한 자료구조 [[001_algorithm_definition|알고리즘]]을 고민하지 않아도 되게 되었다.

| 구분 | 비즈니스/기술적 파급 효과 | 최적화 결과 지표 |
|:---|:---|:---|
| **[[001_dikw_pyramid|데이터]] 활용성 극대화** | 조인([[521_join|Join]])과 [[147_aggregate_function_group_by|집계 함수]]([[522_group_by|Group By]])를 통한 다차원 분석 실시간 추출 | 의사결정 정보 도출(BI/[[209_data_warehouse_schema_on_write|DW]]) 시간 극단적 단축 |
| **안전한 동시 작업** | 락([[510_lock|Lock]]) 및 격리 수준([[227_transaction_isolation_levels_ansi_sql_standard|Isolation Level]])을 통한 [[014_concurrency|동시성]] 보장 | [[001_dikw_pyramid|데이터]] 손실([[203_lost_update_concurrency_problem|Lost Update]]) 무결점 [[191_transaction_concept_states|트랜잭션]] 유지 |
| **아키텍처 확장** | [[083_dml|DML]] 튜닝, [[154_database_index_b_tree_search_optimization|인덱스]] 효율화에 따른 디스크 I/O 절감 | 동일 DB 서버 스펙으로 TPS 수십 배 방어 가능 |

미래의 [[001_dikw_pyramid|데이터]] 조작 트렌드는 인간이 직접 복잡한 SQL DML을 짜는 단계에서, [[263_llm_large_language_model|LLM]] 기반의 Text-to-SQL 기술이나 AI가 [[298_qkv_attention|쿼리]] [[166_execution_plan_optimizer_navigation_tree|실행 계획]]을 스스로 교정하는 자율주행 [[002_database_definition|데이터베이스]](Autonomous [[501_database|Database]])로 넘어가고 있다. 그러나 도구가 발전할수록 [[163_optimizer_sql_execution_plan_generator|옵티마이저]]가 잘못된 [[166_execution_plan_optimizer_navigation_tree|실행 계획]]을 선택하여 발생하는 악성 [[298_qkv_attention|쿼리]]의 폐해는 숨겨지기 더 쉽다. 결국 [[083_relationship_in_er_model|관계]]형 대수에 입각해 [[369_logic_bomb|논리]]적 집합을 필터링하고 물리적인 조인 메커니즘([[431_nested_loop_join|Nested Loop]], [[174_hash_join|Hash Join]])을 꿰뚫어 보는 [[083_dml|DML]] 최적화 역량은 수석 백엔드/[[001_dikw_pyramid|데이터]] 엔지니어를 가르는 가장 중요한 기준점이 될 것이다.

📢 **섹션 요약 비유**: 엔진([[502_dbms|DBMS]])이 아무리 거대해도, 실제로 바퀴를 돌려 차를 앞으로 나가게 만드는 것은 정교하게 분사되는 연료([[083_dml|DML]])의 효율성에 달린 것과 같습니다. 좋은 연비([[163_optimizer_sql_execution_plan_generator|옵티마이저]] 튜닝)를 얻으려면 엔진의 폭발 방식([[038_relational_algebra|관계 대수]])을 정확히 이해해야 합니다.

* **[[449_mvcc|MVCC]] (Multi-Version [[508_concurrency_control|Concurrency Control]])** | [[001_dikw_pyramid|데이터]]를 갱신([[083_dml|DML]])하는 도중에도 과거의 [[022_snapshot_backup_architecture|스냅샷]] [[001_dikw_pyramid|데이터]]를 읽을 수 있게 하여 읽기와 [[289_cqrs_db|쓰기]] 작업 간의 충돌 블로킹을 회피하는 아키텍처 기술
* **[[191_transaction_concept_states|트랜잭션]] ([[191_transaction_concept_states|Transaction]])** | [[193_atomicity_all_or_nothing|원자성]]을 보장하기 위해 한 개 이상의 [[083_dml|DML]](삽입, 갱신, 삭제) 문장들을 [[369_logic_bomb|논리]]적으로 하나로 묶어 커밋(Commit)하거나 [[098_rollback_strategy_pipeline_error_threshold|롤백]]([[313_rollback|Rollback]])하는 단위

### 📈 관련 키워드 및 발전 흐름도

```text
[DDL (Data Definition Language) — 스키마·테이블 구조 정의]
    │
    ▼
[DML (Data Manipulation Language) — SELECT/INSERT/UPDATE/DELETE]
    │
    ▼
[옵티마이저 (Query Optimizer) — 실행 계획(Execution Plan) 수립]
    │
    ▼
[트랜잭션 (Transaction) / MVCC — 원자성·격리성 보장]
    │
    ▼
[Text-to-SQL / 자율주행 DB (Autonomous Database) — 차세대]
```
DDL이 테이블 구조를 정의하고 나면 DML이 실질적인 [[001_dikw_pyramid|데이터]] 가치를 생산하며, [[163_optimizer_sql_execution_plan_generator|옵티마이저]]와 [[191_transaction_concept_states|트랜잭션]]이 DML의 [[282_performance_tactics|성능]]과 안전성을 함께 보장한다.

### 👶 어린이를 위한 3줄 비유 설명
1. 완성된 장난감 성([[002_database_definition|데이터베이스]]) 안에서 "파란색 인형 3개만 찾아줘([[520_select|SELECT]])" 하거나 "인형을 더 넣어줘(INSERT)"라고 부탁하는 마법 주문이 DML이에요.
2. 이 마법 주문은 아주 똑똑해서, 우리가 굳이 성 안을 일일이 돌아다니지 않아도 가장 빠른 길을 알아서 찾아([[163_optimizer_sql_execution_plan_generator|옵티마이저]]) 장난감을 가져온답니다.
3. 하지만 한 번에 너무 많은 장난감을 꺼내달라고 떼쓰거나 길을 꼬이게 잘못 주문하면, 마법사(서버)가 지쳐 쓰러질 수 있으니 예쁘게 잘 말해야 해요!
