## 핵심 인사이트 (3줄 요약)

> 1. **본질**: RPC (Remote Procedure [Call](/knowledge-base/studynote/01_computer_architecture/04_instruction_set_architecture/189_subroutine_call_return/), 원격 프로시저 호출)는 네트워크로 연결된 원격 서버의 함수(프로시저)를 마치 로컬 함수인 것처럼 호출할 수 있게 해주는 [분산](/knowledge-base/studynote/08_algorithm_stats/08_stats/136_variance/) 시스템용 통신 [추상화](/knowledge-base/studynote/04_software_engineering/04_testing_quality/198_abstraction_control_data_process/) 프레임워크다.
> 2. **가치**: IDL (Interface Definition Language)로 인터페이스를 명세하고 스터브([Stub](/knowledge-base/studynote/04_software_engineering/11_testing_validation/852_stub_test_double/)) 코드를 자동 [생성](/knowledge-base/studynote/02_operating_system/02_process_thread/087_process_state_transition/)하여, [소켓](/knowledge-base/studynote/02_operating_system/02_process_thread/125_socket/)([Socket](/knowledge-base/studynote/02_operating_system/02_process_thread/125_socket/)) 기반의 하위 네트워크 프로그래밍 복잡성([마샬링](/knowledge-base/studynote/02_operating_system/02_process_thread/128_marshalling_unmarshalling/), 연결 관리, 에러 처리)을 개발자에게 완전히 은닉한다.
> 3. **융합**: 1980년대 Sun Microsystems의 ONC RPC에서 시작하여 [gRPC](/knowledge-base/studynote/03_network/09_application_layer_web_email/479_grpc_protobuf_http2/) ([gRPC](/knowledge-base/studynote/03_network/09_application_layer_web_email/479_grpc_protobuf_http2/) Remote Procedure Calls), Apache Thrift 등 현대 [마이크로서비스 아키텍처](/knowledge-base/studynote/04_software_engineering/04_testing_quality/213_msa_microservices_architecture/)([MSA](/knowledge-base/studynote/01_computer_architecture/15_advanced_topics/619_msa_traffic_hardware/))의 핵심 내부 통신 표준으로 발전하였으며, [마샬링](/knowledge-base/studynote/02_operating_system/02_process_thread/128_marshalling_unmarshalling/)([Marshalling](/knowledge-base/studynote/02_operating_system/02_process_thread/128_marshalling_unmarshalling/)), [XDR](/knowledge-base/studynote/02_operating_system/02_process_thread/127_xdr_external_data_representation/) ([External Data Representation](/knowledge-base/studynote/02_operating_system/02_process_thread/127_xdr_external_data_representation/)), IDL 등 다양한 기술을 융합한 [분산](/knowledge-base/studynote/08_algorithm_stats/08_stats/136_variance/) 컴퓨팅의 근간 기술이다.

## Ⅰ. 개요 및 필요성

- **개념**: RPC는 [분산](/knowledge-base/studynote/08_algorithm_stats/08_stats/136_variance/) 시스템에서 클라이언트 프로세스가 네트워크 상의 서버 프로세스가 제공하는 함수([서비스](/knowledge-base/studynote/13_cloud_architecture/02_iaas_paas_saas/090_service_kubernetes_network_load_balancing/))를 로컬 [함수 호출](/knowledge-base/studynote/06_ict_convergence/04_ai_llm/294_function_calling_tool_use/)과 동일한 구문으로 호출할 수 있도록, 네트워크 통신의 모든 복잡성을 스터브([Stub](/knowledge-base/studynote/04_software_engineering/11_testing_validation/852_stub_test_double/))라는 [프록시](/knowledge-base/studynote/04_software_engineering/04_testing_quality/264_proxy_pattern_surrogate_access_control/)([Proxy](/knowledge-base/studynote/04_software_engineering/04_testing_quality/264_proxy_pattern_surrogate_access_control/)) 계층으로 캡슐화하는 통신 프레임워크다.
- **필요성**: [소켓](/knowledge-base/studynote/02_operating_system/02_process_thread/125_socket/)([Socket](/knowledge-base/studynote/02_operating_system/02_process_thread/125_socket/)) 기반의 네트워크 프로그래밍은 [데이터](/knowledge-base/studynote/05_database/01_db_architecture_relational/001_dikw_pyramid/) 직렬화(Serialization), 엔디안(Endian) 변환, [TCP](/knowledge-base/studynote/03_network/08_transport_layer/405_tcp_transmission_control_protocol_connection_oriented/) 연결 관리, [타임아웃](/knowledge-base/studynote/04_software_engineering/09_cloud_native_ai_architecture/573_timeout_retry_backoff_strategy/)([Timeout](/knowledge-base/studynote/02_operating_system/05_deadlock/319_timeout_prevention/)) 처리, 재시도(Retry) 로직 등 비즈니스 로직과 무관한 하위 계층 코드를 반복적으로 작성해야 한다. [서비스](/knowledge-base/studynote/13_cloud_architecture/02_iaas_paas_saas/090_service_kubernetes_network_load_balancing/)가 수십 개로 [분산](/knowledge-base/studynote/08_algorithm_stats/08_stats/136_variance/)되는 [마이크로서비스](/knowledge-base/studynote/04_software_engineering/09_cloud_native_ai_architecture/532_microservices_decomposition_patterns/) 환경에서는 이러한 통신 보일러플레이트(Boilerplate) 코드가 프로젝트의 상당 부분을 차지하여 유지보수성을 심각하게 저하시킨다. RPC는 이 모든 네트워크 장벽을 '[함수 호출](/knowledge-base/studynote/06_ict_convergence/04_ai_llm/294_function_calling_tool_use/)'이라는 직관적인 패러다임 뒤로 감추어, 개발자가 [분산](/knowledge-base/studynote/08_algorithm_stats/08_stats/136_variance/) 시스템의 비즈니스 로직 구현에만 집중할 수 있도록 한다.

- **등장 배경**: 1984년 Andrew Birrell과 Bruce Nelson이 Xerox PARC에서 RPC 개념을 학술적으로 정립하였고, 1980년대 후반 Sun Microsystems의 ONC RPC (Open Network Computing RPC)가 상용화의 표준이 되었다. 이후 DCE RPC, CORBA, Java RMI를 거쳐, 2015년 Google이 [HTTP](/knowledge-base/studynote/03_network/09_application_layer_web_email/461_http_stateless_connection_oriented/)/2와 [Protocol](/knowledge-base/studynote/03_network/06_network_layer_ip/295_protocol_field_tcp_udp_icmp/) Buffers를 결합한 gRPC를 공개하면서 [클라우드 네이티브](/knowledge-base/studynote/04_software_engineering/11_testing_validation/923_cloud_native_architecture/) [마이크로서비스](/knowledge-base/studynote/04_software_engineering/09_cloud_native_ai_architecture/532_microservices_decomposition_patterns/) 시대의 사실상(De-facto) 표준으로 부활하였다.

```text
  +---------------------------------------------------------------------+
  |              RPC의 핵심 가치: 네트워크 은닉(Transparency)           |
  +---------------------------------------------------------------------+
  |                                                                     |
  |  [소켓 기반 통신 (개발자가 직접 구현)]                              |
  |                                                                     |
  |  sock = socket(AF_INET, SOCK_STREAM, 0);                            |
  |  connect(sock, "192.168.1.10", 8080);                               |
  |  // 개발자가 직접 직렬화                                            |
  |  msg = pack("order_id=%d,user_id=%d", 1001, 555);                   |
  |  send(sock, msg, strlen(msg), 0);                                   |
  |  resp = recv(sock, buf, 4096, 0);                                   |
  |  // 개발자가 직접 역직렬화                                          |
  |  result = parse_response(resp);                                     |
  |  close(sock);                                                       |
  |                                                                     |
  |  -------------------------------------------------------------      |
  |                                                                     |
  |  [RPC 기반 통신 (프레임워크가 자동 처리)]                           |
  |                                                                     |
  |  result = orderService.GetOrderStatus(order_id=1001, user_id=555);  |
  |                                                                     |
  |  내부적으로 스터브(Stub)이 자동 수행:                               |
  |  +----------------------------------------------------------+       |
  |  | 1. 파라미터 마샬링 (pack to binary)                       |      |
  |  | 2. 네트워크 전송 (TCP send)                                |     |
  |  | 3. 응답 대기 (블로킹)                                     |      |
  |  | 4. 응답 언마샬링 (unpack from binary)                     |      |
  |  | 5. 결과 반환                                                |    |
  |  +----------------------------------------------------------+       |
  |                                                                     |
  |  개발자 코드: 1줄 vs 소켓 코드: 7줄 (복잡도 85% 감소)               |
  +---------------------------------------------------------------------+
```

**[다이어그램 해설]** 이 비교는 RPC가 왜 [분산](/knowledge-base/studynote/08_algorithm_stats/08_stats/136_variance/) 시스템에서 필수적인지를 극명하게 보여준다. [소켓](/knowledge-base/studynote/02_operating_system/02_process_thread/125_socket/) 기반 코드에서 개발자는 비즈니스 로직과 무관한 직렬화, 연결 [설정](/knowledge-base/studynote/15_devops_sre/01_culture_methodology/009_config/), 송수신, 역직렬화 코드를 매 호출마다 반복 작성해야 한다. 반면 RPC에서는 로컬 [함수 호출](/knowledge-base/studynote/06_ict_convergence/04_ai_llm/294_function_calling_tool_use/)처럼 한 줄의 코드로 동일한 작업을 수행하며, 모든 네트워크 통신 로직은 IDL 컴파일러가 자동 [생성](/knowledge-base/studynote/02_operating_system/02_process_thread/087_process_state_transition/)한 스터브([Stub](/knowledge-base/studynote/04_software_engineering/11_testing_validation/852_stub_test_double/))가 대행한다. 이러한 [추상화](/knowledge-base/studynote/04_software_engineering/04_testing_quality/198_abstraction_control_data_process/)([Abstraction](/knowledge-base/studynote/04_software_engineering/04_testing_quality/198_abstraction_control_data_process/))는 단순히 코드 라인 수를 줄이는 것을 넘어, 네트워크 프로그래밍의 실수(엔디안 변환 누락, [버퍼 오버플로우](/knowledge-base/studynote/02_operating_system/10_security/591_buffer_overflow/) 등)를 원천적으로 방지하여 시스템의 신뢰성을 획기적으로 높인다.

- **📢 섹션 요약 비유**: 원격 리모컨의 버튼 하나만 누르면 저 멀리 있는 TV의 채널이 바뀌듯이, 내부의 전파 송수신 과정(네트워크)을 알 필요 없이 버튼 누르기([함수 호출](/knowledge-base/studynote/06_ict_convergence/04_ai_llm/294_function_calling_tool_use/))라는 직관적 행위만으로 원격 작업을 수행하는 것이 RPC의 핵심 가치입니다.

### RPC 호출의 전체 실행 시퀀스

```text
  +---------------------------------------------------------------------+
  |                 RPC 호출의 전체 실행 시퀀스 (8단계)                 |
  +---------------------------------------------------------------------+
  |                                                                     |
  |  [Client Machine]                  [Server Machine]                 |
  |                                                                     |
  |  1. Client Code                   8. Server Function                |
  |     result = func(a, b)          +---> getStockPrice("AAPL")         |
  |       |                          |       |                          |
  |       v                          |       v                          |
  |  2. Client Stub                  |  7. Server Skeleton              |
  |     마샬링(a,b -> binary)         |     언마샬링(binary -> args)      |
  |       |                          |       |                          |
  |       v                          |       v                          |
  |  3. RPC Runtime (Client)         |  6. RPC Runtime (Server)         |
  |     전송 계층 (TCP/UDP)          |     수신 큐에서 꺼내기           |
  |       |                          |       |                          |
  |       |    +----------------+     |       |                         |
  |       +---->|   Network     |-----+       |                          |
  |            |  (TCP/IP 등)   |             |                         |
  |            +----------------+             |                         |
  |       4. Request Message                5. Response Message         |
  |          [func_id|arg_bytes] <----------- [result_bytes|status]      |
  |                                                                     |
  |  [역순 반환]                                                        |
  |  9. Client Stub 언마샬링(result_bytes -> result)                     |
  |  10. Client Code가 result 사용                                      |
  +---------------------------------------------------------------------+
```

**[다이어그램 해설]** RPC의 8단계 실행 시퀀스에서 가장 중요한 설계 원칙은 대칭성(Symmetry)이다. 클라이언트 측의 [마샬링](/knowledge-base/studynote/02_operating_system/02_process_thread/128_marshalling_unmarshalling/)(단계 2)과 서버 측의 언마샬링(단계 7)은 정확히 역연산 관계에 있으며, 이 역연산의 정확성을 IDL이 보장한다. 단계 3~6에서 RPC 런타임이 실제 네트워크를 통해 메시지를 전송한다. 이때 메시지에는 함수 [식별자](/knowledge-base/studynote/03_network/06_network_layer_ip/289_identification_flags_fragmentation_offset/)(func_id), [마샬링](/knowledge-base/studynote/02_operating_system/02_process_thread/128_marshalling_unmarshalling/)된 인자(arg_bytes), 그리고 부가 정보(메시지 유형, [트랜잭션](/knowledge-base/studynote/05_database/04_transactions_concurrency/191_transaction_concept_states/) ID 등)가 포함된다. 클라이언트는 단계 3에서 메시지를 전송한 후 결과를 기다리며 블로킹([Blocking](/knowledge-base/studynote/02_operating_system/02_process_thread/122_sync_async_communication/))되며, 서버의 응답 메시지가 도달하면 블로킹이 해제되고 역순으로 결과가 복원된다. 이 과정에서 개발자는 네트워크 경계(Network Boundary)의 존재를 전혀 인식하지 못한다.

### RPC 의미론(Semantics)의 세 가지 유형

| 의미론 유형 | 설명 | 장점 | 단점 | 구현 예시 |
|:---|:---|:---|:---|:---|
| <strong><a href="/knowledge-base/studynote/12_it_management/02_itsm_itil/083_cross_validation/">정확히 한 번</a> (Exactly-Once)</strong> | 호출이 [정확히 한 번](/knowledge-base/studynote/12_it_management/02_itsm_itil/083_cross_validation/)만 실행됨을 보장 | 가장 안전, [데이터](/knowledge-base/studynote/05_database/01_db_architecture_relational/001_dikw_pyramid/) [일관성](/knowledge-base/studynote/05_database/04_transactions_concurrency/194_consistency_database_integrity/) 보장 | 구현 복잡, 중복 제거 메커니즘 필요 | [TCP](/knowledge-base/studynote/03_network/08_transport_layer/405_tcp_transmission_control_protocol_connection_oriented/) 기반 [gRPC](/knowledge-base/studynote/03_network/09_application_layer_web_email/479_grpc_protobuf_http2/) + 멱등 키 |
| **최대 한 번 (At-Most-Once)** | 호출이 한 번 이상 수행되지 않음을 보장 | 중복 실행 없음, 구현 비교적 단순 | 서버 처리 후 응답 유실 시 결과 누락 | [UDP](/knowledge-base/studynote/03_network/08_transport_layer/406_udp_user_datagram_protocol_connectionless_fast/) 기반 RPC |
| **최소 한 번 (At-Least-Once)** | 호출이 적어도 한 번은 수행됨을 보장 | 결과 누락 방지 | 중복 실행 가능 (재시도 시) | [멱등성](/knowledge-base/studynote/13_cloud_architecture/04_devops_observability/171_idempotency_iac_terraform/)이 보장된 연산 + 재시도 |

- **📢 섹션 요약 비유**: '[정확히 한 번](/knowledge-base/studynote/12_it_management/02_itsm_itil/083_cross_validation/)'은 등기 우편으로 확실하게 한 번 배달하는 것이고, '최대 한 번'은 일반 우편으로 분실되면 다시 보내지 않는 것이며, '최소 한 번'은 분실되면 재발송하여 여러 번 도착할 수 있더라도 반드시 도착시키는 것과 같습니다.

## Ⅲ. 비교 및 연결

### RPC vs [REST](/knowledge-base/studynote/07_enterprise_systems/03_eai_esb_msa/156_rest_representational_state_transfer/) 다차원 비교

| 평가 기준 | RPC ([gRPC](/knowledge-base/studynote/03_network/09_application_layer_web_email/479_grpc_protobuf_http2/)) | [REST](/knowledge-base/studynote/07_enterprise_systems/03_eai_esb_msa/156_rest_representational_state_transfer/) ([HTTP](/knowledge-base/studynote/03_network/09_application_layer_web_email/461_http_stateless_connection_oriented/)/[JSON](/knowledge-base/studynote/11_design_supervision/06_exam_summary/343_json/)) | 판단 기준 |
|:---|:---|:---|:---|
| **설계 철학** | 동사(Action) 중심 | 명사(Resource) 중심 | 행위 vs 자원 중심 |
| **페이로드** | 이진 포맷(Protobuf) | 텍스트 포맷([JSON](/knowledge-base/studynote/11_design_supervision/06_exam_summary/343_json/)) | [대역폭](/knowledge-base/studynote/01_computer_architecture/03_architecture_basics_performance/140_bandwidth/) 효율 |
| **타입 안정성** | IDL 기반 강한 타입 | [JSON](/knowledge-base/studynote/11_design_supervision/06_exam_summary/343_json/) [스키마](/knowledge-base/studynote/05_database/01_db_architecture_relational/005_schema/)(선택적) | 인터페이스 계약 엄격성 |
| **스트리밍** | 양방향 스트리밍 기본 지원 | [HTTP](/knowledge-base/studynote/03_network/09_application_layer_web_email/461_http_stateless_connection_oriented/)/2 SSE만 [단방향](/knowledge-base/studynote/03_network/01_data_communication/008_단방향_반이중_전이중/) | 실시간 [데이터](/knowledge-base/studynote/05_database/01_db_architecture_relational/001_dikw_pyramid/) 처리 |
| **오버헤드** | [HTTP](/knowledge-base/studynote/03_network/09_application_layer_web_email/461_http_stateless_connection_oriented/)/2 멀티플렉싱 | [HTTP](/knowledge-base/studynote/03_network/09_application_layer_web_email/461_http_stateless_connection_oriented/)/1.1 헤더 중복 | 내부 통신 효율 |
| **사용처** | [마이크로서비스](/knowledge-base/studynote/04_software_engineering/09_cloud_native_ai_architecture/532_microservices_decomposition_patterns/) 간(S2S) 통신 | 외부 Public [API](/knowledge-base/studynote/02_operating_system/01_overview_architecture/014_api_posix/), 프론트엔드 | 내부 vs 외부 |

- **📢 섹션 요약 비유**: REST가 누구나 읽을 수 있는 표준 편지(사람 친화적)라면, RPC는 훈련된 요원들끼리 암호화된 모스 부호(기계 친화적)로 통신하는 방식으로, 외부 고객에게는 REST를, 내부 [서비스](/knowledge-base/studynote/13_cloud_architecture/02_iaas_paas_saas/090_service_kubernetes_network_load_balancing/) 간에는 RPC를 사용하는 하이브리드 전략이 실무의 표준입니다.

## Ⅳ. 실무 적용 및 기술사 판단

### 실무 시나리오

1. <strong>시나리오 -- RPC <a href="/knowledge-base/studynote/04_software_engineering/09_cloud_native_ai_architecture/573_timeout_retry_backoff_strategy/">타임아웃</a>과 <a href="/knowledge-base/studynote/04_software_engineering/05_devops_ci_cd/307_circuit_breaker_pattern/">서킷 브레이커</a></strong>: [MSA](/knowledge-base/studynote/01_computer_architecture/15_advanced_topics/619_msa_traffic_hardware/) 환경에서 주문 [서비스](/knowledge-base/studynote/13_cloud_architecture/02_iaas_paas_saas/090_service_kubernetes_network_load_balancing/)가 결제 [서비스](/knowledge-base/studynote/13_cloud_architecture/02_iaas_paas_saas/090_service_kubernetes_network_load_balancing/)를 gRPC로 호출했으나, 네트워크 [스위치](/knowledge-base/studynote/03_network/05_lan_wan_l2_devices/238_switch_operation_principles/) 장애로 응답이 유실된 상황. 주문 [서비스](/knowledge-base/studynote/13_cloud_architecture/02_iaas_paas_saas/090_service_kubernetes_network_load_balancing/)가 [타임아웃](/knowledge-base/studynote/04_software_engineering/09_cloud_native_ai_architecture/573_timeout_retry_backoff_strategy/)([Timeout](/knowledge-base/studynote/02_operating_system/05_deadlock/319_timeout_prevention/)) [설정](/knowledge-base/studynote/15_devops_sre/01_culture_methodology/009_config/) 없이 무한 대기하면 전체 시스템이 마비되는 캐스케이딩(Cascading) 장애가 발생한다. 아키텍트는 반드시 RPC 호출에 명시적 [타임아웃](/knowledge-base/studynote/04_software_engineering/09_cloud_native_ai_architecture/573_timeout_retry_backoff_strategy/)을 [설정](/knowledge-base/studynote/15_devops_sre/01_culture_methodology/009_config/)하고, 실패 누적 시 [서킷 브레이커](/knowledge-base/studynote/04_software_engineering/05_devops_ci_cd/307_circuit_breaker_pattern/)([Circuit Breaker](/knowledge-base/studynote/12_it_management/05_security_compliance/304_circuit_breaker/))를 트리거하여 장애 전파를 차단해야 한다.

2. <strong>시나리오 -- <a href="/knowledge-base/studynote/13_cloud_architecture/04_devops_observability/171_idempotency_iac_terraform/">멱등성</a>(<a href="/knowledge-base/studynote/15_devops_sre/04_iac_cloud_native/194_idempotency/">Idempotency</a>) 보장과 재시도 폭풍(Retry Storm)</strong>: [타임아웃](/knowledge-base/studynote/04_software_engineering/09_cloud_native_ai_architecture/573_timeout_retry_backoff_strategy/)으로 RPC 호출이 실패했을 때, 사실 서버에서는 이미 요청을 처리했으나 응답만 유실된 상태일 수 있다. 무조건 재시도하면 결제 중복 승인 같은 치명적 오류가 발생한다. 백엔드 엔지니어는 모든 상태 변경 RPC에 멱등 키([Idempotency](/knowledge-base/studynote/15_devops_sre/04_iac_cloud_native/194_idempotency/) [Key](/knowledge-base/studynote/05_database/02_modeling_normalization/067_db_key_uniqueness_minimality/))를 IDL에 포함시켜, 중복 호출 시 서버가 이전 결과를 반환하도록 설계해야 한다.

### 도입 [체크리스트](/knowledge-base/studynote/04_software_engineering/11_testing_validation/435_checklist_based_testing/)
- **기술적**: IDL 파일의 하위 [호환성](/knowledge-base/studynote/04_software_engineering/06_software_architecture/344_compatibility_usability/)(Backward [Compatibility](/knowledge-base/studynote/04_software_engineering/06_software_architecture/344_compatibility_usability/))을 위해 필드 번호와 타입 변경 정책을 수립하였는가? RPC 호출에 적절한 [타임아웃](/knowledge-base/studynote/04_software_engineering/09_cloud_native_ai_architecture/573_timeout_retry_backoff_strategy/)([Timeout](/knowledge-base/studynote/02_operating_system/05_deadlock/319_timeout_prevention/))과 재시도(Retry) 정책을 [설정](/knowledge-base/studynote/15_devops_sre/01_culture_methodology/009_config/)하였는가?
- **운영 보안적**: RPC 통신 채널에 [TLS](/knowledge-base/studynote/02_operating_system/11_exam_summary/694_thread_local_storage_tls/) 암호화를 적용하였으며, [mTLS](/knowledge-base/studynote/03_network/16_data_center_cloud/831_mtls_mutual_tls_microservices_zero_trust/) ([Mutual TLS](/knowledge-base/studynote/09_security/04_endpoint_security/187_mtls_mutual_tls_authentication/))로 [서비스](/knowledge-base/studynote/13_cloud_architecture/02_iaas_paas_saas/090_service_kubernetes_network_load_balancing/) 간 상호 인증을 구현하였는가? RPC 트래픽의 [지연](/knowledge-base/studynote/03_network/01_data_communication/015_지연_데이터_관점/)([Latency](/knowledge-base/studynote/01_computer_architecture/03_architecture_basics_performance/141_latency/))과 에러율(Error Rate)을 APM으로 모니터링하고 있는가?

### [안티패턴](/knowledge-base/studynote/04_software_engineering/02_requirements_analysis/128_water_scrum_fall_anti_pattern/)
- **RPC 남용에 의한 채티 I/O (Chatty I/O)**: 로컬 객체를 다루듯 루프 안에서 수천 번의 RPC 호출을 수행하는 [안티패턴](/knowledge-base/studynote/04_software_engineering/02_requirements_analysis/128_water_scrum_fall_anti_pattern/). 1회 호출에 10ms가 걸리면 1,000회 호출 시 10초의 [지연](/knowledge-base/studynote/03_network/01_data_communication/015_지연_데이터_관점/)이 발생한다. 반드시 배치(Batch) 처리가 가능한 굵직한([Coarse-grained](/knowledge-base/studynote/01_computer_architecture/11_multicore_synchronization/398_coarse_grained_multithreading/)) 인터페이스를 IDL에 정의해야 한다.

- **📢 섹션 요약 비약 비유**: 로컬 함수는 내가 직접 주방에서 요리하는 것이지만, RPC는 원격 요리사에게 주문하는 것이라 전화가 끊기면 요리를 안 한 건지, 다 해놓고 배달만 못 한 건지 알 수 없으므로 반드시 주문 번호(멱등 키)와 대기 시간([타임아웃](/knowledge-base/studynote/04_software_engineering/09_cloud_native_ai_architecture/573_timeout_retry_backoff_strategy/))을 [설정](/knowledge-base/studynote/15_devops_sre/01_culture_methodology/009_config/)해야 합니다.

- **📢 섹션 요약 비유**: 운전자가 도로 상황에 따라 기어와 브레이크를 다르게 선택하는 것처럼 조건별 판단이 중요하다.

- **📢 섹션 요약 비유**: 수동 기어 조작으로 엔진 회전수를 맞춰야 했던 과거의 운전([소켓](/knowledge-base/studynote/02_operating_system/02_process_thread/125_socket/) 프로그래밍)이 자동 변속기(RPC)의 도입으로 엑셀과 브레이크만 밟으면 되는 시대로 변모하여, 개발자가 오직 목적지(비즈니스 로직)에만 집중할 수 있게 된 것과 같습니다.

### 📈 관련 키워드 및 발전 흐름도

```text
[소켓 (Socket) 통신]
    |
    v
[RPC (Remote Procedure Call)]
    |
    +---> [XDR (External Data Representation)]
    +---> [마샬링 (Marshalling) / 언마샬링 (Unmarshalling)]
```

이 흐름도는 선행 개념에서 현재 개념으로 넘어온 뒤, 구현 세분화와 후속 확장으로 이어지는 학습 순서를 압축해 보여준다.

### 👶 어린이를 위한 3줄 비유 설명

1. RPC는 다른 나라에 있는 요리사에게 내가 원하는 요리를 만들어 달라고 부탁하는 "만능 통역 스마트폰"이에요.
2. 내가 한국어로 "피자 만들어줘"라고 버튼을 누르면, 스마트폰 안의 똑똑한 비서([Stub](/knowledge-base/studynote/04_software_engineering/11_testing_validation/852_stub_test_double/))가 알아서 상대방 언어로 번역해서 이메일로 보내주고, 응답이 오면 다시 내 식탁에 올려줘요.
3. 요리사가 멀리 있어도 내 눈앞에서 요리하는 것처럼 느껴지지만, 사실은 중간에 통역([마샬링](/knowledge-base/studynote/02_operating_system/02_process_thread/128_marshalling_unmarshalling/))과 배달(네트워크)이라는 복잡한 과정이 숨어 있답니다!
