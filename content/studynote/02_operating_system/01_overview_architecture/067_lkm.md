## 핵심 인사이트 (3줄 요약)

> 1. **본질**: LKM(Loadable [Kernel](/knowledge-base/studynote/02_operating_system/01_overview_architecture/022_kernel_role/) Modules)은 [커널](/knowledge-base/studynote/02_operating_system/01_overview_architecture/022_kernel_role/)을 재부팅하지 않고 기능을 추가/제거할 수 있게 하는 [모듈](/knowledge-base/studynote/04_software_engineering/04_testing_quality/192_module_independence/) 방식이다.
> 2. **가치**: 드라이버, [파일](/knowledge-base/studynote/02_operating_system/09_file_system/501_file_definition_logical_record/) 시스템, 네트워크 기능을 동적으로 확장할 수 있어 유지보수와 유연성이 높다.
> 3. **판단**: [커널](/knowledge-base/studynote/02_operating_system/01_overview_architecture/022_kernel_role/) 내부이므로 안정성과 보안이 중요하며, [모듈](/knowledge-base/studynote/04_software_engineering/04_testing_quality/192_module_independence/) 서명과 의존성 관리가 필요하다.

## Ⅰ. 개요 및 필요성

모든 기능을 [커널](/knowledge-base/studynote/02_operating_system/01_overview_architecture/022_kernel_role/)에 기본 탑재(built-in)하면 [커널](/knowledge-base/studynote/02_operating_system/01_overview_architecture/022_kernel_role/) 이미지가 거대해지고, 불필요한 드라이버까지 메모리에 항상 올라가게 된다. 이는 메모리 낭비이자 부팅 시간 증가로 이어진다. 초기 리눅스는 모놀리식 커널 구조였으나, 시스템이 복잡해지고 지원해야 할 하드웨어 종류가 폭발적으로 증가하면서 동적 확장의 필요성이 대두되었다.

LKM(Loadable Kernel Modules)은 이러한 문제를 해결하기 위해 등장한 메커니즘이다. 운영 중인 시스템에서 [커널](/knowledge-base/studynote/02_operating_system/01_overview_architecture/022_kernel_role/)을 재컴파일하거나 재부팅하지 않고도 새로운 기능을 동적으로 적재(load)하거나 제거(unload)할 수 있다. 장치 드라이버, 파일시스템, 네트워크 프로토콜, 시스템 콜 등 다양한 기능을 LKM 형태로 제공한다.

리눅스 2.6 커널부터 본격적으로 안정화된 LKM 프레임워크는 현재 대부분의 리눅스 배포판에서 핵심 확장 메커니즘으로 사용된다. `lsmod`, `modprobe`, `modinfo` 등의 도구로 관리되며, `/lib/modules/$(uname -r)/` 디렉터리에 모듈 파일(.ko)이 저장된다. 기술사 시험에서는 LKM을 "커널 런타임 확장"의 대표 사례로 다루며, 모놀리식 커널과 마이크로커널의 장점을 혼합한 구조로 설명할 수 있어야 한다.

- **📢 섹션 요약 비유**: 벽을 뜯지 않고 필요한 부품만 끼워 넣는 조립식 가구처럼, 시스템을 멈추지 않고도 기능 블록을 삽입하거나 뽑아낼 수 있다.

### 핵심 구성 요소

| 구성 요소 | 설명 | 비고 |
| :--- | :--- | :--- |
| `.ko` 파일 | 커널 오브젝트(ELF 형식 공유 객체) | Kernel Object |
| `insmod` | 모듈을 직접 적재하는 명령 | 의존성 미처리 |
| `modprobe` | 의존성 포함 자동 적재 명령 | `/etc/modprobe.d` 참조 |
| `rmmod` | 모듈 제거 명령 | 참조 중이면 실패 |
| `lsmod` | 현재 적재된 모듈 목록 출력 | `/proc/modules` 읽기 |
| `modinfo` | 모듈 메타데이터 조회 | 버전, 작성자, 파라미터 |
| `depmod` | 모듈 의존성 데이터베이스 생성 | `modules.dep` 파일 |
| Symbol Table | 커널-모듈 간 함수/변수 연결 | `EXPORT_SYMBOL` 매크로 |

### LKM 라이프사이클

| 단계 | 설명 |
| :--- | :--- |
| 컴파일(Compile) | `.c` 소스를 `.ko`로 빌드 |
| 적재(Load) | `insmod` 또는 `modprobe`로 커널 공간 진입 |
| 초기화(Init) | `module_init()` 함수 실행, 서브시스템 등록 |
| 동작(Running) | 커널의 일부로 동작, 심볼 공유 |
| 제거(Unload) | `rmmod` 호출, `module_exit()` 실행, 메모리 해제 |

### 커널 모듈 기본 구조 (코드 예시)

```c
#include <linux/init.h>
#include <linux/module.h>
#include <linux/kernel.h>

MODULE_LICENSE("GPL");
MODULE_AUTHOR("Example");
MODULE_DESCRIPTION("A simple LKM example");

static int __init hello_init(void)
{
    printk(KERN_INFO "LKM: Hello, Kernel!\n");
    return 0;
}

static void __exit hello_exit(void)
{
    printk(KERN_INFO "LKM: Goodbye, Kernel!\n");
}

module_init(hello_init);
module_exit(hello_exit);
```

### 심볼 해석과 의존성

LKM은 커널이 제공하는 심볼(`EXPORT_SYMBOL`로 공개된 함수/변수)을 참조하여 동작한다. `modprobe`는 `/lib/modules/$(uname -r)/modules.dep` 파일을 읽어 필요한 모듈을 자동으로 먼저 적재한 후 목적 모듈을 올린다. 서명(Module Signing) 기능이 활성화된 경우, 서명되지 않은 모듈은 SecureBoot 환경에서 거부된다.

- **📢 섹션 요약 비유**: 장난감에 맞는 연결핀(심볼)을 꽂아 기능을 확장하되, 먼저 호환 여부(의존성)를 검사하는 느낌이다.

## Ⅲ. 비교 및 연결

### LKM vs Built-in 커널 비교

| 항목 | Built-in 커널 | LKM |
| :--- | :--- | :--- |
| 적재 시점 | 부팅 시 고정 탑재 | 런타임 동적 적재 |
| 유연성 | 낮음 | 높음 |
| 메모리 효율 | 낮음(항상 메모리 점유) | 높음(필요 시만 점유) |
| 안정성 | 상대적으로 높음 | 모듈 품질에 의존 |
| 재부팅 필요 | 기능 추가 시 필요 | 불필요 |
| 보안 | 일체형으로 견고 | 모듈 서명 정책 필요 |
| 용도 | 핵심 필수 기능 | 드라이버, 확장 기능 |

### LKM vs eBPF 비교

| 항목 | LKM | eBPF |
| :--- | :--- | :--- |
| 실행 공간 | 커널 공간(Ring 0) | 커널 내 샌드박스 |
| 안전성 | 버그 시 커널 패닉 가능 | 검증기(Verifier)가 보장 |
| 유연성 | 매우 높음 | 제한적(루프 횟수 제한 등) |
| 주요 용도 | 드라이버, 파일시스템 | 관측성, 보안, 네트워킹 |
| 재부팅 | 불필요 | 불필요 |

### LKM이 지원하는 주요 기능 분류

| 카테고리 | 예시 |
| :--- | :--- |
| 장치 드라이버 | 네트워크 카드(e1000), GPU(nvidia), USB 드라이버 |
| 파일시스템 | ext4, xfs, btrfs, NFS, FUSE |
| 네트워크 | Netfilter/iptables, tc, 터널링 드라이버 |
| 보안 | SELinux, AppArmor (일부 모듈) |
| 기타 | 암호화 모듈, 가상화(KVM), 시스템 콜 확장 |

LKM은 필요할 때만 넣는 방식이라 효율적이지만, 커널 내부 코드인 만큼 버그가 커널 패닉(Kernel Panic)으로 이어질 수 있다. 따라서 품질 관리가 매우 중요하다.

- **📢 섹션 요약 비유**: 필요할 때만 붙였다 떼는 도구지만, 잘못 끼우면 전체 시스템이 흔들리는 정밀 부품이다.

## Ⅳ. 실무 적용 및 기술사 판단

### 설계 판단 체크리스트

1. 모듈의 의존성 관계가 명확하게 정의되어 있는가?
2. 모듈 서명(Signing) 정책이 적용되어 있는가? (SecureBoot 환경에서 필수)
3. `insmod`와 `modprobe`의 차이를 이해하고 적절히 사용하는가?
4. 런타임 적재/제거 시 영향 범위(롤백 계획)를 분석했는가?
5. 커널 심볼 충돌(Symbol Conflict)이나 버전 불일치(ABI 문제) 위험은 없는가?
6. 모듈 파라미터(`module_param`)를 통해 동작을 외부에서 제어할 수 있는가?
7. 모듈 제거(unload) 시 메모리 및 자원 해제가 완전히 이루어지는가?
8. 커널 버전 업그레이드 시 모듈 재컴파일이 필요한 시나리오를 고려했는가?

### 안티패턴

- **무서명 모듈 무분별 적재**: 검증되지 않은 서드파티 모듈을 운영 환경에 바로 적재하면 커널 안정성이 위협받는다. 반드시 GPG 서명과 테스트를 거쳐야 한다.
- **의존성 무시 insmod**: `insmod`로 의존성이 해결되지 않은 상태에서 모듈을 올리면 심볼 해석 실패로 오류가 발생한다. `modprobe`를 기본으로 사용해야 한다.
- **메모리 해제 미완료**: `module_exit()` 함수에서 할당한 메모리나 등록한 핸들러를 해제하지 않으면 메모리 누수(leak)나 댕글링 포인터(dangling pointer)가 발생한다.
- **커널 버전 고정 미확인**: 특정 커널 버전에 맞춰 컴파일된 모듈은 다른 버전에서 동작하지 않는다(KABI 불일치). 버전 관리 없는 배포는 운영 장애를 유발한다.

기술사 관점에서는 LKM을 "커널 확장 메커니즘"으로 보되, 안정성과 보안을 반드시 함께 언급해야 한다. 특히 모듈 서명, DKMS(Dynamic Kernel Module Support)를 통한 자동 재컴파일 관리, ABI 안정성 등이 엔터프라이즈 운영의 핵심이다.

- **📢 섹션 요약 비유**: 새 부품을 넣을 때는 설명서와 안전장치(서명, 테스트)가 꼭 필요하다. 아무 부품이나 끼우면 전체가 망가질 수 있다.

## Ⅴ. 기대효과 및 결론

LKM은 커널 재컴파일 없이 기능을 확장하게 해 운영 효율이 크게 향상된다. 특히 장치 드라이버 중심의 임베디드 시스템이나 서버 환경에서 하드웨어 추가/변경 시 무중단으로 대응할 수 있다는 것이 핵심 가치다.

DKMS(Dynamic Kernel Module Support)와 결합하면 커널 버전 업그레이드 시에도 모듈을 자동으로 재컴파일하여 적재할 수 있어, 운영 부담이 대폭 줄어든다. 클라우드 환경에서는 가상화 드라이버(virtio, KVM 모듈 등)가 LKM으로 제공되어 하이퍼바이저와의 연결이 유연하게 이루어진다.

보안 측면에서는 IMA(Integrity Measurement Architecture) 및 모듈 서명 검증 기능이 강화되고 있어, 신뢰할 수 없는 모듈의 실행을 차단하는 방향으로 발전하고 있다. 결론적으로 LKM은 모놀리식 커널의 성능 이점과 마이크로커널의 모듈화 유연성을 모두 취하는 실용적 설계다.

- **📢 섹션 요약 비유**: 필요한 기능만 나중에 끼워 넣을 수 있는 커다란 레고 세트다. 덕분에 항상 완성된 모습을 유지하면서도 언제든 새 블록을 추가할 수 있다.

### 👶 어린이를 위한 3줄 비유 설명

1. 레고 집을 짓다가 새 창문 부품이 생기면, 집을 부수지 않고 그냥 끼워 넣을 수 있어요.
