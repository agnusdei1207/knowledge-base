> **핵심 인사이트 3줄**
> 1. ELT(Extract·Load·Transform)는 원시 [데이터](/knowledge-base/studynote/05_database/01_db_architecture_relational/001_dikw_pyramid/)를 먼저 클라우드 DWH에 적재한 뒤 강력한 컴퓨팅 파워로 변환을 수행하는 현대 [데이터 파이프라인](/knowledge-base/studynote/01_computer_architecture/15_advanced_topics/645_data_pipeline_acceleration/) 패턴으로, ETL의 중간 변환 서버 병목을 제거했다.
> 2. 현대 [데이터](/knowledge-base/studynote/05_database/01_db_architecture_relational/001_dikw_pyramid/) [스택](/knowledge-base/studynote/08_algorithm_stats/04_datastructure/057_stack/)([Modern Data Stack](/knowledge-base/studynote/16_bigdata/09_platform/178_modern_data_stack/))은 Fivetran/Airbyte(EL)·[Snowflake](/knowledge-base/studynote/05_database/04_transactions_concurrency/541_cassandra/)/[BigQuery](/knowledge-base/studynote/13_cloud_architecture/05_data_engineering/263_storage_compute_separation_bigquery/)(DWH)·dbt(T)·[Looker](/knowledge-base/studynote/16_bigdata/08_visualization/166_looker/)/[Tableau](/knowledge-base/studynote/16_bigdata/08_visualization/164_tableau/)(BI)의 레이어로 구성되며, 각 레이어의 [SaaS](/knowledge-base/studynote/12_it_management/05_security_compliance/309_saas/) 전문화가 팀 생산성을 극적으로 높인다.
> 3. [데이터 레이크하우스](/knowledge-base/studynote/12_it_management/05_security_compliance/210_data_lakehouse_delta_lake/)([Lakehouse](/knowledge-base/studynote/16_bigdata/07_data_lake/146_lakehouse/))는 [데이터 레이크](/knowledge-base/studynote/12_it_management/05_security_compliance/208_data_lake_schema_on_read/)의 유연성과 DWH의 ACID [트랜잭션](/knowledge-base/studynote/05_database/04_transactions_concurrency/191_transaction_concept_states/)·[쿼리](/knowledge-base/studynote/10_ai/04_ai_ops_ethics/298_qkv_attention/) [성능](/knowledge-base/studynote/04_software_engineering/05_devops_ci_cd/282_performance_tactics/)을 결합한 통합 아키텍처로, [Delta Lake](/knowledge-base/studynote/16_bigdata/07_data_lake/147_delta_lake/)·Iceberg·Hudi가 오픈 포맷 표준 경쟁 중이다.

## Ⅰ. [ELT vs ETL](/knowledge-base/studynote/16_bigdata/07_data_lake/155_elt_vs_etl/) — 패러다임 전환



<div class="kb-diagram" data-diagram="ascii-converted">
<div class="kb-diagram-flow">
<div class="kb-diagram-note">ETL (전통):</div>
<div class="kb-diagram-note">원본 → ETL 서버 (변환) → DWH</div>
<div class="kb-diagram-note">↑ 병목: 서버 용량 한계</div>
<div class="kb-diagram-note">↑ 원시 데이터 보존 안 됨</div>
<div class="kb-diagram-note">ELT (현대):</div>
<div class="kb-diagram-note">원본 → EL 도구 → DWH (원시 레이어) → dbt 변환 → 마트</div>
<div class="kb-diagram-note">(Fivetran) (Snowflake) (SQL 모델)</div>
<div class="kb-diagram-note">↑ DWH 컴퓨팅 파워 활용</div>
<div class="kb-diagram-note">↑ 원시 데이터 항상 보존 → 재처리 가능</div>
</div>
</div>



📢 **섹션 요약 비유**: ETL은 음식을 조리해서 냉장고에 넣는 것이고, ELT는 재료째 냉장고에 넣고 먹기 전에 조리하는 것이다 — 재료가 항상 보존되고, 냉장고(클라우드 DWH)가 강력하면 ELT가 더 유연하다.

## Ⅲ. [데이터 레이크하우스](/knowledge-base/studynote/12_it_management/05_security_compliance/210_data_lakehouse_delta_lake/) ([Lakehouse](/knowledge-base/studynote/16_bigdata/07_data_lake/146_lakehouse/))

```
데이터 레이크 한계: 스키마 없음, ACID 트랜잭션 불가, 성능 낮음
데이터 DWH 한계: 비정형·반정형 데이터 불가, 비싼 저장 비용

레이크하우스 = 레이크 + 웨어하우스:
```

| 기능              | [데이터 레이크](/knowledge-base/studynote/12_it_management/05_security_compliance/208_data_lake_schema_on_read/)  | [데이터](/knowledge-base/studynote/05_database/01_db_architecture_relational/001_dikw_pyramid/) DWH  | [레이크하우스](/knowledge-base/studynote/16_bigdata/07_data_lake/146_lakehouse/)  |
|-----------------|-------------|------------|------------|
| [비정형 데이터](/knowledge-base/studynote/14_data_engineering/01_infrastructure/004_unstructured_data/)     | ✅          | ❌          | ✅          |
| ACID [트랜잭션](/knowledge-base/studynote/05_database/04_transactions_concurrency/191_transaction_concept_states/)    | ❌          | ✅          | ✅          |
| SQL [쿼리](/knowledge-base/studynote/10_ai/04_ai_ops_ethics/298_qkv_attention/) [성능](/knowledge-base/studynote/04_software_engineering/05_devops_ci_cd/282_performance_tactics/)    | 낮음         | 높음         | 높음         |
| 저장 비용        | 낮음         | 높음         | 낮음         |
| 스트리밍         | ✅          | 제한         | ✅          |

📢 **섹션 요약 비유**: [레이크하우스](/knowledge-base/studynote/16_bigdata/07_data_lake/146_lakehouse/)는 스마트 창고다 — 모든 종류의 물건(레이크: 비정형 포함)을 보관하면서도, 어떤 물건이 어디 있는지 정확히 관리(DWH: ACID·SQL)한다.

## Ⅳ. [오픈 테이블 포맷](/knowledge-base/studynote/14_data_engineering/01_infrastructure/054_open_table_format_iceberg_delta_hudi/) — [Delta Lake](/knowledge-base/studynote/16_bigdata/07_data_lake/147_delta_lake/)·Iceberg·Hudi

| 포맷         | 주도           | 핵심 특성                      |
|-----------|-------------|-------------------------------|
| [Delta Lake](/knowledge-base/studynote/16_bigdata/07_data_lake/147_delta_lake/) | [Databricks](/knowledge-base/studynote/16_bigdata/03_spark/074_photon_engine/)  | 타임 트래블, ACID, Z-Order     |
| [Apache Iceberg](/knowledge-base/studynote/16_bigdata/07_data_lake/148_apache_iceberg/) | Netflix  | [스키마](/knowledge-base/studynote/05_database/01_db_architecture_relational/005_schema/) 진화, 시간 여행, 멀티클라우드|
| [Apache Hudi](/knowledge-base/studynote/16_bigdata/07_data_lake/149_apache_hudi/) | Uber       | 증분 처리, [CDC](/knowledge-base/studynote/14_data_engineering/05_exam_keywords/217_cdc_binlog_change_capture_debezium/) 최적화           |

```
타임 트래블 예시 (Delta Lake):
  SELECT * FROM orders TIMESTAMP AS OF '2024-01-01'
  -- 과거 시점 데이터 조회 가능 (실수 복구·감사)

스키마 진화 (Iceberg):
  ALTER TABLE orders ADD COLUMN promo_code STRING
  -- 기존 파티션과 하위 호환 유지
```

📢 **섹션 요약 비유**: 타임 트래블은 [데이터](/knowledge-base/studynote/05_database/01_db_architecture_relational/001_dikw_pyramid/)의 되감기 버튼이다 — 실수로 [데이터](/knowledge-base/studynote/05_database/01_db_architecture_relational/001_dikw_pyramid/)를 삭제해도 "어제 [버전](/knowledge-base/studynote/03_network/06_network_layer_ip/288_version_ihl_tos_total_length/) 보여줘"라고 하면 과거 상태로 돌아갈 수 있다.

## Ⅴ. 역방향 [ETL](/knowledge-base/studynote/12_it_management/05_security_compliance/215_etl_vs_elt_pipeline/) ([Reverse ETL](/knowledge-base/studynote/13_cloud_architecture/05_data_engineering/278_reverse_etl_operational_analytics/))

역방향 [ETL](/knowledge-base/studynote/12_it_management/05_security_compliance/215_etl_vs_elt_pipeline/)([Reverse ETL](/knowledge-base/studynote/13_cloud_architecture/05_data_engineering/278_reverse_etl_operational_analytics/))은 <strong>DWH에 정제된 <a href="/knowledge-base/studynote/05_database/01_db_architecture_relational/001_dikw_pyramid/">데이터</a>를 운영 시스템(<a href="/knowledge-base/studynote/07_enterprise_systems/02_erp_systems/107_crm_customer_relationship_management/">CRM</a>·광고·Slack)으로 역전송</strong>하는 패턴이다.



<div class="kb-diagram" data-diagram="ascii-converted">
<div class="kb-diagram-flow">
<div class="kb-diagram-note">일반 흐름: 소스 → DWH → BI (분석)</div>
<div class="kb-diagram-note">역방향 ETL: DWH → CRM (Salesforce) / 광고 (Facebook Ads)</div>
<div class="kb-diagram-note">→ 이메일 (Mailchimp) / Slack 알림</div>
<div class="kb-diagram-note">예시: BigQuery의 "고가치 고객 세그먼트" → Salesforce 영업팀 자동 배정</div>
</div>
</div>



**도구**: Hightouch, Census, dbt + Airflow 커스텀

📢 **섹션 요약 비유**: 역방향 ETL은 분석 보고서를 현장 직원 메신저로 보내는 것이다 — "분석 결과를 보고서로만 보는 것"이 아니라, 영업팀 CRM에 자동으로 넣어서 바로 행동하게 한다.

## 👶 어린이를 위한 3줄 비유 설명

1. ELT는 재료째 냉장고에 넣고 먹기 전에 요리하는 것이다 — 원재료를 보존하고 강력한 주방(클라우드 DWH)에서 바로 요리한다.
2. [레이크하우스](/knowledge-base/studynote/16_bigdata/07_data_lake/146_lakehouse/)는 만능 스마트 창고다 — 어떤 물건이든(비정형 포함) 저장하면서도, RFID 태그(ACID [메타데이터](/knowledge-base/studynote/05_database/01_db_architecture_relational/012_metadata/))로 정확히 관리한다.
3. 타임 트래블은 [데이터](/knowledge-base/studynote/05_database/01_db_architecture_relational/001_dikw_pyramid/) 되감기 버튼이다 — 실수로 삭제한 [데이터](/knowledge-base/studynote/05_database/01_db_architecture_relational/001_dikw_pyramid/)도 "어제 오전 10시 [버전](/knowledge-base/studynote/03_network/06_network_layer_ip/288_version_ihl_tos_total_length/)"으로 되돌릴 수 있다.
