> **핵심 인사이트 3줄**
> 1. [CDC](/studynote/14_data_engineering/05_exam_keywords/217_cdc_binlog_change_capture_debezium/)([Change Data Capture](/studynote/14_data_engineering/05_exam_keywords/217_cdc_binlog_change_capture_debezium/))는 소스 DB의 INSERT·UPDATE·DELETE 변경 이벤트를 실시간으로 캡처해 다운스트림 시스템에 전파하는 [데이터](/studynote/05_database/01_db_architecture_relational/001_dikw_pyramid/) 통합 기법이다.
> 2. [로그](/studynote/04_software_engineering/09_cloud_native_ai_architecture/568_logs_distributed_logging_elk_fluentd/) 기반 [CDC](/studynote/14_data_engineering/05_exam_keywords/217_cdc_binlog_change_capture_debezium/)(Debezium + [Kafka](/studynote/14_data_engineering/04_mlops/179_kafka_flink_watermark_time_window/))는 소스 DB 부하 없이 WAL/Binlog를 읽어 서브밀리초 [지연](/studynote/03_network/01_data_communication/015_지연_데이터_관점/)으로 변경을 스트리밍하는 현대 표준이다.
> 3. CDC는 실시간 [데이터 웨어하우스](/studynote/12_it_management/05_security_compliance/209_data_warehouse_schema_on_write/)·[마이크로서비스](/studynote/04_software_engineering/09_cloud_native_ai_architecture/532_microservices_decomposition_patterns/) [이벤트 드리븐 아키텍처](/studynote/04_software_engineering/04_testing_quality/214_eda_event_driven_architecture_async/)·[Zero-downtime](/studynote/15_devops_sre/02_cicd_gitops/110_zero_downtime_db_schema_rollout/) 마이그레이션의 핵심 인프라로 사용된다.

## Ⅰ. CDC의 정의와 필요성

[CDC](/studynote/14_data_engineering/05_exam_keywords/217_cdc_binlog_change_capture_debezium/)([Change Data Capture](/studynote/14_data_engineering/05_exam_keywords/217_cdc_binlog_change_capture_debezium/), [변경 데이터 캡처](/studynote/12_it_management/05_security_compliance/218_cdc_change_data_capture/))는 <strong><a href="/studynote/05_database/01_db_architecture_relational/001_dikw_pyramid/">데이터</a>베이스의 모든 변경 사항을 감지·캡처·전달하는 기술</strong>이다.

### [CDC](/studynote/14_data_engineering/05_exam_keywords/217_cdc_binlog_change_capture_debezium/) vs 배치 [ETL](/studynote/12_it_management/05_security_compliance/215_etl_vs_elt_pipeline/) 비교

| 항목          | 배치 [ETL](/studynote/12_it_management/05_security_compliance/215_etl_vs_elt_pipeline/)              | [CDC](/studynote/14_data_engineering/05_exam_keywords/217_cdc_binlog_change_capture_debezium/) (실시간)           |
|-------------|----------------------|----------------------|
| 처리 방식    | 주기적 (야간 배치)    | 이벤트 기반 실시간     |
| [데이터](/studynote/05_database/01_db_architecture_relational/001_dikw_pyramid/) 신선도 | 시간~일 단위          | 밀리초~초 단위         |
| 소스 DB 부하 | [쿼리](/studynote/10_ai/04_ai_ops_ethics/298_qkv_attention/) 부하 높음        | [로그](/studynote/04_software_engineering/09_cloud_native_ai_architecture/568_logs_distributed_logging_elk_fluentd/) 기반 시 낮음      |
| 복잡도       | 단순                  | 높음 ([스키마](/studynote/05_database/01_db_architecture_relational/005_schema/) [변경 관리](/studynote/12_it_management/02_itsm_itil/079_change_enablement/)) |
| 사용 사례    | 보고서·분석           | 실시간 대시보드·[동기화](/studynote/02_operating_system/03_cpu_scheduling/212_synchronization_mechanisms/)  |

📢 **섹션 요약 비유**: CDC는 우체통을 주기적으로 확인하는 것(배치 [ETL](/studynote/12_it_management/05_security_compliance/215_etl_vs_elt_pipeline/)) 대신, 편지가 도착하는 순간 알림을 받는 것([CDC](/studynote/14_data_engineering/05_exam_keywords/217_cdc_binlog_change_capture_debezium/))과 같다.

## Ⅱ. [CDC](/studynote/14_data_engineering/05_exam_keywords/217_cdc_binlog_change_capture_debezium/) 구현 방식 3가지

### 1. [쿼리](/studynote/10_ai/04_ai_ops_ethics/298_qkv_attention/) 기반 [CDC](/studynote/14_data_engineering/05_exam_keywords/217_cdc_binlog_change_capture_debezium/) (Query-Based)

```sql
-- 마지막 추출 시각 이후 변경된 행 조회
SELECT * FROM orders
WHERE updated_at > :last_extract_time
ORDER BY updated_at;
```
- 장점: 구현 간단, 기존 DB 변경 불필요
- 단점: 삭제 감지 불가, DB 부하, 밀리초 [지연](/studynote/03_network/01_data_communication/015_지연_데이터_관점/) 불가

### 2. [트리거](/studynote/05_database/04_transactions_concurrency/507_acid_properties/) 기반 [CDC](/studynote/14_data_engineering/05_exam_keywords/217_cdc_binlog_change_capture_debezium/) (Trigger-Based)

```sql
CREATE TRIGGER orders_cdc
AFTER INSERT OR UPDATE OR DELETE ON orders
FOR EACH ROW
INSERT INTO cdc_log VALUES (NOW(), TG_OP, OLD/NEW데이터);
```
- 장점: 삭제 감지 가능
- 단점: DB [성능](/studynote/04_software_engineering/05_devops_ci_cd/282_performance_tactics/) 저하, [스키마](/studynote/05_database/01_db_architecture_relational/005_schema/) 변경 시 [트리거](/studynote/05_database/04_transactions_concurrency/507_acid_properties/) 관리 복잡

### 3. [로그](/studynote/04_software_engineering/09_cloud_native_ai_architecture/568_logs_distributed_logging_elk_fluentd/) 기반 [CDC](/studynote/14_data_engineering/05_exam_keywords/217_cdc_binlog_change_capture_debezium/) (Log-Based) — 현대 표준

```
PostgreSQL WAL / MySQL Binlog
         v
     Debezium (오픈소스 CDC)
         v
     Apache Kafka (이벤트 스트림)
         v
  다운스트림: DWH / 검색 / 캐시
```
- 장점: 소스 DB 부하 없음, 모든 변경 캡처, 서브밀리초
- 단점: DB [로그](/studynote/04_software_engineering/09_cloud_native_ai_architecture/568_logs_distributed_logging_elk_fluentd/) [설정](/studynote/15_devops_sre/01_culture_methodology/009_config/) 필요, 복잡한 운영

📢 **섹션 요약 비유**: [로그](/studynote/04_software_engineering/09_cloud_native_ai_architecture/568_logs_distributed_logging_elk_fluentd/) 기반 CDC는 [CCTV](/studynote/09_security/18_iot_ot_physical/933_cctv/) 녹화본을 분석하는 방식이다 — 직접 현장(DB)에 탐정([쿼리](/studynote/10_ai/04_ai_ops_ethics/298_qkv_attention/)/[트리거](/studynote/05_database/04_transactions_concurrency/507_acid_properties/))을 배치하지 않고 기존 보안 카메라([트랜잭션](/studynote/05_database/04_transactions_concurrency/191_transaction_concept_states/) [로그](/studynote/04_software_engineering/09_cloud_native_ai_architecture/568_logs_distributed_logging_elk_fluentd/))를 활용한다.

## Ⅲ. Debezium + [Kafka](/studynote/14_data_engineering/04_mlops/179_kafka_flink_watermark_time_window/) [CDC](/studynote/14_data_engineering/05_exam_keywords/217_cdc_binlog_change_capture_debezium/) 아키텍처

```
+--------------------------------------------------------------+
|                   CDC 데이터 파이프라인                        |
|                                                              |
|  PostgreSQL ---> Debezium ---> Kafka Topic ---> Flink/Spark    |
|    (WAL)       Connector    (변경 이벤트)    (스트림 처리)    |
|                                  |                          |
|                            Kafka Connect |                  |
|                            Sink Connector|                  |
|                                  v                          |
|                    Elasticsearch / Snowflake / Redis        |
+--------------------------------------------------------------+
```

### Debezium 이벤트 메시지 구조

```json
{
  "op": "u",          // c=create, u=update, d=delete
  "before": { "id": 1, "status": "pending" },
  "after":  { "id": 1, "status": "shipped" },
  "source": {
    "table": "orders",
    "ts_ms": 1700000000000,
    "lsn": 12345678
  }
}
```

📢 **섹션 요약 비유**: Debezium 이벤트는 신문 사회면 기사다 — "어떤 사건(op)이, 이전엔(before) 어땠고, 지금은(after) 어떻게 됐다"를 정확히 기록한다.

### [Zero-downtime](/studynote/15_devops_sre/02_cicd_gitops/110_zero_downtime_db_schema_rollout/) 마이그레이션 패턴

```
Phase 1: CDC로 구 DB -> 신 DB 동기화
Phase 2: 읽기 트래픽 신 DB로 전환 (테스트)
Phase 3: 쓰기 트래픽도 신 DB로 완전 전환
Phase 4: CDC 중단, 구 DB 폐기
```

📢 **섹션 요약 비유**: [Zero-downtime](/studynote/15_devops_sre/02_cicd_gitops/110_zero_downtime_db_schema_rollout/) 마이그레이션은 달리는 기차의 선로를 교체하는 것과 같다 — CDC가 두 선로 사이의 전환 [스위치](/studynote/03_network/05_lan_wan_l2_devices/238_switch_operation_principles/) 역할을 한다.

## Ⅴ. [CDC](/studynote/14_data_engineering/05_exam_keywords/217_cdc_binlog_change_capture_debezium/) 운영 고려사항

### [스키마](/studynote/05_database/01_db_architecture_relational/005_schema/) 변화 처리 ([Schema](/studynote/05_database/04_transactions_concurrency/505_schema/) Evolution)

```
소스 DB 컬럼 추가 시:
  Debezium -> Kafka Schema Registry (Avro/Protobuf)
  -> 컨슈머는 새 필드를 Optional로 처리 (하위 호환)
```

### At-Least-Once / Exactly-Once 보장

| 보장 수준         | 방법                          |
|-----------------|-------------------------------|
| At-Least-Once   | [Kafka](/studynote/14_data_engineering/04_mlops/179_kafka_flink_watermark_time_window/) + [멱등성](/studynote/13_cloud_architecture/04_devops_observability/171_idempotency_iac_terraform/) 소비자          |
| Exactly-Once    | [Kafka](/studynote/14_data_engineering/04_mlops/179_kafka_flink_watermark_time_window/) Transactions + [2PC](/studynote/04_software_engineering/09_cloud_native_ai_architecture/549_2pc_two_phase_commit_limitations_msa/)      |

📢 **섹션 요약 비유**: [Schema](/studynote/05_database/04_transactions_concurrency/505_schema/) Evolution 처리는 회사 양식 변경과 같다 — 새 칸이 추가되어도 예전 양식으로 작성한 서류가 거부되지 않도록 하위 호환을 유지해야 한다.

## 📌 관련 개념 맵

```
CDC (Change Data Capture)
+-- 구현 방식
|   +-- 쿼리 기반 (Timestamp Poll)
|   +-- 트리거 기반 (DB Trigger)
|   +-- 로그 기반 (WAL/Binlog) <- 현대 표준
+-- 핵심 도구
|   +-- Debezium (오픈소스 CDC)
|   +-- Apache Kafka (스트리밍)
|   +-- AWS DMS (관리형 CDC)
+-- 활용 패턴
|   +-- 실시간 DWH 동기화
|   +-- 이벤트 드리븐 MSA
|   +-- Zero-downtime 마이그레이션
+-- 관련 개념
    +-- WAL (Write-Ahead Log)
    +-- Binlog (MySQL)
    +-- Schema Registry (Avro)
```

## 👶 어린이를 위한 3줄 비유 설명

1. CDC는 일기 복사기다 — 내가 일기를 쓰는 순간 친구에게도 똑같이 전달되어 항상 최신 내용을 볼 수 있다.
2. [로그](/studynote/04_software_engineering/09_cloud_native_ai_architecture/568_logs_distributed_logging_elk_fluentd/) 기반 CDC는 [CCTV](/studynote/09_security/18_iot_ot_physical/933_cctv/) 영상 분석이다 — 직접 물어보지 않아도 기록만 보면 무슨 일이 있었는지 알 수 있다.
3. Debezium은 번역가다 — DB 언어(WAL/Binlog)를 모두가 이해하는 [Kafka](/studynote/14_data_engineering/04_mlops/179_kafka_flink_watermark_time_window/) 이벤트 언어로 실시간 번역해준다.
