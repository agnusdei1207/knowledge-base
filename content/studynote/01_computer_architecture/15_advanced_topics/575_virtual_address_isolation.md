## 핵심 인사이트 (3줄 요약)

> 1. **본질**: [[382_virtual_address_space|가상 주소 공간]] 분리는 각 프로세스가 자신만의 주소 지도를 갖도록 하고, [[328_mmu|MMU]] ([[284_mmu|Memory Management Unit]])가 그 지도와 권한 [[073_bit|비트]]를 기준으로 접근을 번역·차단함으로써 같은 시스템 안에서도 서로 다른 메모리 세계를 보게 만드는 기술이다.
> 2. **가치**: 같은 가상 주소를 여러 프로세스가 동시에 사용해도 충돌하지 않게 만들고, 한 프로세스의 버그나 침해가 다른 프로세스나 [[022_kernel_role|커널]]로 즉시 번지지 않도록 막아 안정성과 보안을 함께 높인다.
> 3. **판단 포인트**: 진짜 격리는 [[353_page_table|페이지 테이블]] 분리만으로 끝나지 않으며, 특권 [[073_bit|비트]], [[357_tlb|TLB]] ([[291_tlb|Translation Lookaside Buffer]]) 태깅, [[118_shared_memory|공유 메모리]] [[164_policy|정책]], [[746_io_direct_memory_access_dma|DMA]] ([[318_dma|Direct Memory Access]]) 차단, [[578_kpti|KPTI]] ([[022_kernel_role|Kernel]] [[286_page_frame|Page]]-Table [[195_isolation_concurrency_control|Isolation]]) 같은 보강 요소까지 함께 맞아야 완성된다.

## Ⅰ. 개요 및 필요성

[[382_virtual_address_space|가상 주소 공간]] 분리는 "프로세스마다 자기만의 주소 우주를 준다"는 아이디어다. 프로그램은 자신이 `0x400000` 같은 주소를 사용한다고 생각하지만, 실제로는 현재 프로세스에 연결된 [[353_page_table|페이지 테이블]]을 통해 전혀 다른 물리 프레임으로 번역된다. 그래서 서로 다른 두 프로세스가 같은 가상 주소를 써도 충돌하지 않으며, 상대방 메모리를 직접 들여다볼 수도 없다.

이 기술이 필요한 이유는 멀티프로그래밍 환경에서 오류 전파를 막기 위해서다. 격리가 없다면 잘못된 포인터 하나가 다른 프로세스의 [[001_dikw_pyramid|데이터]]나 [[001_operating_system_purpose|운영체제]] 핵심 구조를 덮어쓸 수 있다. 보안 관점에서도 마찬가지다. 악성 코드가 같은 기계에 올라와 있더라도, 하드웨어가 주소 번역 단계에서 남의 [[286_page_frame|페이지]]를 원천 차단해야 비밀번호, [[140_session_key|세션 키]], 업무 [[001_dikw_pyramid|데이터]] 같은 민감 정보가 직접 노출되지 않는다.

즉 [[382_virtual_address_space|가상 주소 공간]] 분리는 메모리를 "공유 자원"으로 쓰면서도, 사용자에게는 "개인 공간"처럼 보이게 하는 핵심 장치다. 이 분리가 무너지면 현대 [[001_operating_system_purpose|운영체제]]의 프로세스 모델, 브라우저 샌드박스, 클라우드 멀티테넌시는 모두 성립하기 어렵다.

- **📢 섹션 요약 비유**: [[382_virtual_address_space|가상 주소 공간]] 분리는 같은 건물 안에 살아도 각자 다른 열쇠와 다른 집 구조를 갖는 아파트와 같다. 집 번호가 비슷해 보여도 문을 열 수 있는 권한과 내부 배치는 사람마다 완전히 다르다.

## Ⅱ. 아키텍처 및 핵심 원리

이 격리는 [[353_page_table|페이지 테이블]]과 권한 [[073_bit|비트]]만으로 끝나지 않는다. 현재 어떤 주소 공간이 활성 상태인지, 캐시에 남은 주소 번역 정보가 다른 프로세스와 섞이지 않는지, [[022_kernel_role|커널]] [[286_page_frame|페이지]]가 사용자 모드에서 보이지 않는지까지 함께 관리해야 한다. 그래서 [[382_virtual_address_space|가상 주소 공간]] 분리는 사실상 주소 번역기, 권한 검사기, 문맥 전환 [[164_policy|정책]]이 한 덩어리로 움직이는 구조다.

| 구성 요소 | 역할 | 핵심 포인트 |
| :-- | :-- | :-- |
| [[353_page_table|페이지 테이블]] 루트 | 현재 프로세스의 주소 지도를 지정 | 문맥 전환 시 어떤 주소 공간을 볼지 결정한다 |
| [[353_page_table|페이지 테이블]] 엔트리 ([[353_page_table|Page Table]] Entry, PTE) | 가상 [[286_page_frame|페이지]]의 물리 프레임과 권한 저장 | User/Supervisor, Read/Write/Execute [[073_bit|비트]]가 직접 격리를 집행한다 |
| [[357_tlb|TLB]] | 최근 주소 번역 결과 캐시 | Address Space [[088_identifier_in_er_model|Identifier]] ([[360_asid|ASID]]) 또는 Process-Context [[088_identifier_in_er_model|Identifier]] (PCID)로 다른 주소 공간을 구분한다 |
| [[022_kernel_role|커널]] 분리 [[164_policy|정책]] | 사용자와 [[022_kernel_role|커널]]의 가시 범위를 조정 | KPTI로 사용자 모드에서 [[022_kernel_role|커널]] 매핑 노출을 최소화할 수 있다 |

아래 그림은 같은 가상 주소가 서로 다른 물리 프레임으로 번역되는 모습을 보여 준다.

```text
┌────────────────────────────────────────────────────────────────────────────┐
│ Same virtual address, different physical destination                      │
├────────────────────────────────────────────────────────────────────────────┤
│ Process A              Process B                 Kernel                    │
│ VA 0x400000            VA 0x400000               VA high region            │
│     │                      │                         │                      │
│     ▼                      ▼                         ▼                      │
│  PT root A              PT root B                PT root K                 │
│     │                      │                         │                      │
│     ▼                      ▼                         ▼                      │
│ PFN 0x1234              PFN 0x8A20               PFN 0x0010                │
│                                                                            │
│ User-mode access to kernel-only page ───────────────────────────▶ blocked  │
└────────────────────────────────────────────────────────────────────────────┘
```

문맥 전환이 일어나면 [[001_operating_system_purpose|운영체제]]는 현재 주소 공간의 루트를 바꾸고, TLB가 잘못된 이전 번역을 재사용하지 않도록 ASID나 PCID 같은 태그를 활용한다. 또한 [[286_page_frame|페이지]]마다 사용자 접근 허용 여부, 읽기/[[289_cqrs_db|쓰기]] 가능 여부, 실행 가능 여부를 따로 지정해 "보이기만 하고 못 만지는 [[286_page_frame|페이지]]", "읽을 수는 있지만 실행할 수는 없는 [[286_page_frame|페이지]]" 같은 세밀한 경계를 만든다. [[482_meltdown|멜트다운]] 이후에는 사용자 모드에서 [[022_kernel_role|커널]] [[286_page_frame|페이지]] 자체를 거의 숨기는 KPTI가 중요한 보강책이 되었다.

결국 핵심은 단순 번역이 아니라, 번역 순간마다 "이 프로세스가 이 주소를 지금 이 권한으로 접근할 자격이 있는가"를 하드웨어가 즉시 판정한다는 데 있다.

- **📢 섹션 요약 비유**: 이 구조는 건물 경비실이 손님마다 다른 출입 카드와 출입 층을 확인하는 시스템과 같다. 같은 엘리베이터 버튼을 눌러도 누구의 카드인지에 따라 도착 가능한 층이 달라진다.

## Ⅲ. 비교 및 연결

[[382_virtual_address_space|가상 주소 공간]] 분리를 더 잘 이해하려면 과거의 [[364_segmentation|세그멘테이션]] ([[364_segmentation|Segmentation]]), 현대의 [[259_paging|페이징]], 그리고 그 위에 놓인 [[015_virtualization|가상화]] 계층을 함께 봐야 한다. 모두 "남의 메모리에 함부로 못 가게 하자"는 목표는 같지만, 얼마나 잘게 나누고 얼마나 유연하게 [[571_protection_vs_security|보호]]하느냐가 다르다.

| 방식 | [[571_protection_vs_security|보호]] 단위 | 강점 | 한계 |
| :-- | :-- | :-- | :-- |
| [[364_segmentation|세그멘테이션]] | 큰 연속 구간 | 개념 단순, [[459_quic_fec_forward_error_correction|초기]] [[571_protection_vs_security|보호]]에 유용 | 세밀한 공유·[[571_protection_vs_security|보호]]가 어렵고 [[291_fragmentation_and_reassembly_process|단편화]] 문제가 크다 |
| [[286_page_frame|페이지]] 기반 주소 공간 분리 | 고정 크기 [[286_page_frame|페이지]] | 현대 [[001_operating_system_purpose|운영체제]]의 표준, 세밀한 권한 제어 가능 | [[357_tlb|TLB]], [[353_page_table|페이지 테이블]] 관리 비용이 따른다 |
| 가상 머신 격리 | 게스트 전체 주소 공간 | [[001_operating_system_purpose|운영체제]] 간 강한 경계 형성 | 중첩 [[286_page_frame|페이지]] 변환과 I/O [[015_virtualization|가상화]] 비용이 추가된다 |

또한 주소 공간 분리는 [[374_aslr|ASLR]] (Address Space Layout Randomization)과도 연결된다. 주소 공간 분리가 "남의 집에 못 들어가게 하는 벽"이라면, ASLR은 "내 집 안 구조도 쉽게 모르게 하는 장치"에 가깝다. 즉 분리는 직접 접근을 막고, 무작위화는 공격 준비 자체를 어렵게 만든다. 둘은 경쟁 관계가 아니라 겹쳐야 강해지는 보안 층이다.

[[118_shared_memory|공유 메모리]]는 예외도 보여 준다. 두 프로세스가 같은 물리 프레임을 일부러 함께 매핑하면 빠른 통신이 가능하지만, 그만큼 격리 경계가 얇아진다. 따라서 공유는 [[282_performance_tactics|성능]]을 위한 허용된 틈이지, 격리가 약하다는 반례가 아니다.

- **📢 섹션 요약 비유**: 주소 공간 분리는 콘크리트 벽으로 나뉜 집이고, [[118_shared_memory|공유 메모리]]는 그 벽에 의도적으로 낸 작은 창구다. 창구가 있으면 물건을 빨리 주고받을 수 있지만, 그만큼 출입 규칙을 더 엄격히 정해야 한다.

## Ⅳ. 실무 적용 및 기술사 판단

실무에서는 "프로세스가 나뉘어 있다"는 사실만으로 충분하지 않다. 브라우저 렌더러, [[002_database_definition|데이터베이스]] 워커, 클라우드 [[561_container_based_deployment|컨테이너]], 가상 머신은 모두 서로 다른 수준의 격리를 요구한다. [[353_page_table|페이지 테이블]] 경계는 기본이지만, 장치가 DMA로 메모리를 직접 만질 수 있다면 [[627_iommu_dma_isolation|IOMMU]] (Input/Output [[284_mmu|Memory Management Unit]])까지 있어야 진짜 격리가 완성된다.

### 판단 [[435_checklist_based_testing|체크리스트]]

1. 사용자 프로세스와 [[022_kernel_role|커널]]이 [[353_page_table|페이지 테이블]]과 권한 [[073_bit|비트]] 수준에서 명확히 분리되어 있는가?
2. [[289_cqrs_db|쓰기]]와 실행 분리 (Write XOR Execute, W^X) [[164_policy|정책]]으로 코드 [[286_page_frame|페이지]]와 [[001_dikw_pyramid|데이터]] [[286_page_frame|페이지]]의 역할을 나누고 있는가?
3. ASID나 PCID를 활용해 [[282_performance_tactics|성능]] 비용을 줄이되, 격리 경계 자체는 생략하지 않고 있는가?
4. [[118_shared_memory|공유 메모리]], [[418_memory_mapped_file_mmap|메모리 매핑 파일]], `/dev/mem` 유사 경로처럼 예외적 공유 지점을 최소화했는가?
5. 장치 접근이 많은 시스템이라면 DMA를 IOMMU로 제한해 프로세스 밖 메모리 침범을 막고 있는가?
6. KPTI를 포함한 [[022_kernel_role|커널]] 격리 보강책을 위협 모델에 맞게 유지하고 있는가?

### 피해야 할 [[128_water_scrum_fall_anti_pattern|안티패턴]]

- 디버깅 편의를 이유로 광범위한 [[022_kernel_role|커널]] 매핑이나 물리 메모리 접근 경로를 사용자 공간에 열어 두는 설계
- [[561_container_based_deployment|컨테이너]] 분리를 곧바로 하드웨어 주소 공간 분리와 동일시해, 장치나 [[022_kernel_role|커널]] 공유 위험을 과소평가하는 판단
- [[282_performance_tactics|성능]] 수치만 보고 KPTI나 권한 검사를 무턱대고 약화시키는 운영

기술사 답안에서는 "프로세스마다 주소 공간이 다르다"에서 멈추지 말고, 그 경계를 누가 강제하는지, 어떤 예외가 경계를 약하게 만드는지, 장치와 [[022_kernel_role|커널]]까지 포함하면 무엇이 더 필요해지는지까지 써야 설계 답안이 된다.

- **📢 섹션 요약 비유**: 주소 공간 분리 운영은 큰 사무실에 보안 구역을 나누는 일과 같다. 일반 사원, 서버실, 금고실을 같은 열쇠로 열게 하면 편해 보일 수는 있지만, 사고가 나면 피해는 순식간에 건물 전체로 번진다.

## Ⅴ. 기대효과 및 결론

[[382_virtual_address_space|가상 주소 공간]] 분리가 잘 작동하면 프로그램 하나의 버그가 시스템 전체 장애로 번지는 가능성이 크게 줄어든다. 또한 프로세스별 주소 독립성 덕분에 프로그램은 메모리 배치를 단순하게 생각할 수 있고, [[001_operating_system_purpose|운영체제]]는 물리 메모리를 더 유연하게 재배치할 수 있다. 안정성, [[283_security_tactics|보안성]], 프로그래밍 편의성이 동시에 얻어지는 이유가 여기에 있다.

하지만 이 기술도 만능은 아니다. [[118_shared_memory|공유 메모리]]와 [[022_kernel_role|커널]] 버그, 사이드 채널, 장치의 무단 [[746_io_direct_memory_access_dma|DMA]], 투기 실행 기반 정보 유출은 직접적인 [[286_page_frame|페이지]] [[571_protection_vs_security|보호]]만으로 다 막기 어렵다. 그래서 현대 시스템은 주소 공간 분리 위에 [[374_aslr|ASLR]], [[578_kpti|KPTI]], [[627_iommu_dma_isolation|IOMMU]], [[796_memory_encryption|메모리 암호화]], [[795_confidential_computing|기밀 컴퓨팅]] 같은 층을 계속 쌓고 있다.

결론적으로 [[382_virtual_address_space|가상 주소 공간]] 분리는 현대 컴퓨팅의 기본 신뢰 경계다. 같은 컴퓨터를 함께 쓰더라도 각자 다른 세계를 보게 만든다는 점, 그리고 그 경계를 MMU와 권한 [[073_bit|비트]]가 하드웨어로 집행한다는 점을 기억하면 핵심을 놓치지 않는다.

- **📢 섹션 요약 비유**: 이 기술은 한 동네 안에서도 집집마다 담장과 주소, 자물쇠가 따로 있는 질서와 같다. 모두 같은 땅 위에 서 있지만, 누구나 아무 집에나 들어갈 수는 없기에 마을이 평화롭게 유지된다.

| PTE ([[353_page_table|Page Table]] Entry) | 개별 [[286_page_frame|페이지]]의 물리 위치와 권한 [[073_bit|비트]]를 저장한다. |
| [[357_tlb|TLB]] | 번역 결과를 캐시하므로 [[282_performance_tactics|성능]] 핵심이지만, 주소 공간 태깅이 없으면 격리 오류 위험이 커진다. |
| [[360_asid|ASID]] / PCID | 서로 다른 주소 공간의 번역 정보를 안전하게 구분하는 태그다. |
| [[578_kpti|KPTI]] | 사용자 모드에서 [[022_kernel_role|커널]] 매핑 노출을 줄여 격리 경계를 강화한다. |
| [[627_iommu_dma_isolation|IOMMU]] | 장치의 DMA까지 주소 공간 규칙 안에 넣어 프로세스 밖 메모리 침범을 막는다. |
