## 핵심 인사이트 (3줄 요약)

> 1. **본질**: 인라인 [[347_compaction|압축]]은 [[001_dikw_pyramid|데이터]]가 저장 매체에 기록되기 직전에 즉시 [[347_compaction|압축]]해, [[369_logic_bomb|논리]] 용량과 물리 사용량을 다르게 만드는 투명한 저장 최적화 기술이다.
> 2. **가치**: 디스크 공간뿐 아니라 백엔드 기록량과 플래시 마모까지 줄여, 같은 [[327_ssd|SSD]] ([[327_ssd|Solid State Drive]]) 용량으로 더 많은 [[001_dikw_pyramid|데이터]]를 더 오래 운영하게 해 준다.
> 3. **판단 포인트**: [[347_compaction|압축]]률 자체보다 중요한 것은 [[347_compaction|압축]] [[001_algorithm_definition|알고리즘]]의 [[141_latency|지연 시간]], 비압축 [[001_dikw_pyramid|데이터]] 우회 [[164_policy|정책]], [[012_metadata|메타데이터]] 관리가 [[090_service_kubernetes_network_load_balancing|서비스]] 응답 시간을 얼마나 흔들지 여부다.

---

## Ⅰ. 개요 및 필요성

인라인 [[347_compaction|압축]]은 [[001_dikw_pyramid|데이터]]가 미디어에 닿기 전에 [[347_compaction|압축]]을 수행하는 방식이다. 전통적인 사후 [[347_compaction|압축]]은 일단 원본을 저장한 뒤 나중에 다시 읽어서 줄였기 때문에, 처음 쓸 때는 원본 크기만큼 공간이 필요했고 한 번 더 쓰고 지우는 비용도 발생했다. 반면 인라인 [[347_compaction|압축]]은 저장 직전에 물리 크기를 줄여 버리므로, 같은 순간에 필요한 실제 용량 자체를 낮춘다.

이 차이는 플래시 스토리지에서 특히 중요하다. 예를 들어 4 킬로바이트(KB) [[369_logic_bomb|논리]] 블록이 평균 1.5 KB로 줄어든다면, 같은 [[001_dikw_pyramid|데이터]]셋을 훨씬 적은 [[289_cqrs_db|쓰기]] 횟수로 저장할 수 있다. 이는 단순 공간 절약을 넘어 [[696_waf_web_application_firewall|WAF]] ([[480_write_amplification|Write Amplification]] Factor)를 낮추고, 결과적으로 [[327_ssd|SSD]] ([[327_ssd|Solid State Drive]])의 수명과 백엔드 대역폭에 직접 영향을 준다.

물론 모든 [[001_dikw_pyramid|데이터]]가 잘 [[347_compaction|압축]]되는 것은 아니다. [[568_logs_distributed_logging_elk_fluentd|로그]], 텍스트, 0으로 채워진 [[286_page_frame|페이지]]는 잘 줄어들지만, 이미 [[347_compaction|압축]]된 영상이나 암호화된 블록은 거의 줄지 않는다. 따라서 인라인 [[347_compaction|압축]]은 “무조건 [[347_compaction|압축]]”보다 “[[347_compaction|압축]] 가치가 있는 [[001_dikw_pyramid|데이터]]만 빠르게 고르기”가 더 중요한 기술이다.

- **📢 섹션 요약 비유**: 큰 이불을 장롱에 넣기 전에 문 앞에서 바로 [[347_compaction|압축]]팩에 넣는 것이 인라인 [[347_compaction|압축]]이다. 장롱 안에 들어간 뒤 다시 꺼내 [[347_compaction|압축]]하는 것보다 훨씬 덜 힘들고 공간도 즉시 아낄 수 있다.

## Ⅱ. 아키텍처 및 핵심 원리

인라인 [[347_compaction|압축]]의 핵심 경로는 입력 [[001_dikw_pyramid|데이터]] 검사, [[347_compaction|압축]] 가능성 판단, 실제 [[347_compaction|압축]], [[012_metadata|메타데이터]] 기록, 읽기 시 복원으로 이어진다. 컨트롤러는 먼저 블록의 반복 패턴과 엔트로피를 살펴 [[347_compaction|압축]] 이득이 있는지 추정한다. 이득이 충분하면 LZ4 (Lempel-Ziv 4)나 Zstd (Zstandard) 같은 [[001_algorithm_definition|알고리즘]]으로 [[001_dikw_pyramid|데이터]]를 줄이고, 그렇지 않으면 그대로 통과시킨다.

아래 그림은 인라인 [[347_compaction|압축]]의 [[289_cqrs_db|쓰기]] 분기와 읽기 복원 경로를 보여준다.

```text
┌──────────────────────────────────────────────────────────────────┐
│ Inline compression path                                         │
├──────────────────────────────────────────────────────────────────┤
│ Logical block                                                   │
│     │                                                           │
│     ├-> [Compressibility Test] -> low  -> [Bypass]             │
│     │                                                           │
│     └-> [Compressibility Test] -> high -> [Compressor]         │
│                                           │                    │
│                                           ├-> data shrinks      │
│                                           └-> map metadata      │
│                                                                   │
│ Read path: media block + metadata -> [Decompressor] -> host      │
└──────────────────────────────────────────────────────────────────┘
```

이때 [[012_metadata|메타데이터]]가 매우 중요하다. [[347_compaction|압축]] 후에는 물리 블록 길이가 가변적이므로, [[369_logic_bomb|논리]] 주소와 실제 저장 위치를 정확히 매핑해야 한다. 읽기 시에는 이 정보를 바탕으로 필요한 [[347_compaction|압축]] 블록만 가져와 복원해야 하므로, [[347_compaction|압축]] 엔진뿐 아니라 주소 변환 테이블의 설계가 함께 좋아야 한다.

| 구성 요소 | 역할 | 설계상 주의점 |
| :--- | :--- | :--- |
| [[347_compaction|압축]] 가능성 판단기 | [[347_compaction|압축]] 가치가 있는 블록 선별 | 잘못 판단하면 [[015_지연_데이터_관점|지연]]만 증가 |
| [[347_compaction|압축]] 엔진 | 실제 [[001_dikw_pyramid|데이터]] 축소 | CPU (Central Processing Unit) 부하 또는 가속기 필요 |
| [[012_metadata|메타데이터]] 맵 | [[369_logic_bomb|논리]] 주소와 [[347_compaction|압축]] 블록 위치 연결 | 손상 시 복원 전체가 어려움 |
| 복원 경로 | 읽기 요청 시 원본 재구성 | 읽기 [[015_지연_데이터_관점|지연]]의 꼬리값 관리 필요 |

그래서 고성능 스토리지는 [[347_compaction|압축]]률보다 [[015_지연_데이터_관점|지연]] 안정성을 더 중시한다. [[347_compaction|압축]]률이 조금 낮더라도 빠른 [[001_algorithm_definition|알고리즘]]을 택하거나, 일정 비율 이하로만 줄어드는 [[001_dikw_pyramid|데이터]]는 바로 우회시키는 이유가 여기에 있다.

- **📢 섹션 요약 비유**: 짐을 트럭에 싣기 전에 먼저 진공 포장할지, 그냥 실을지 문 앞에서 바로 판단하는 과정과 같다. 포장은 공간을 아끼지만, 포장지 정보와 위치표를 잘못 적으면 나중에 꺼낼 때 더 헷갈린다.

## Ⅲ. 비교 및 연결

인라인 [[347_compaction|압축]]은 [[347_compaction|압축]]을 “언제” 하느냐와 “무엇을” 줄이느냐 관점에서 다른 기술과 구분된다. 사후 [[347_compaction|압축]]은 저장 후 나중에 정리하고, [[501_file_definition_logical_record|파일]] [[347_compaction|압축]]은 사용자가 직접 `zip` 같은 형식으로 다루며, 중복 제거는 서로 다른 블록 사이의 반복을 없앤다. 인라인 [[347_compaction|압축]]은 이들 중에서도 저장 경로 안에서 자동으로, 사용자 개입 없이, [[289_cqrs_db|쓰기]] 직전에 수행된다는 점이 핵심이다.

| 기술 | 동작 시점 | 줄이는 대상 | 장점 | 주의점 |
| :--- | :--- | :--- | :--- | :--- |
| 인라인 [[347_compaction|압축]] | [[289_cqrs_db|쓰기]] 직전 | 블록 내부 반복 패턴 | 즉시 공간 절감, [[289_cqrs_db|쓰기]]량 감소 | [[141_latency|지연 시간]]과 [[012_metadata|메타데이터]] 부담 |
| 사후 [[347_compaction|압축]] | 저장 후 [[228_batch_processing_hadoop_spark|배치 처리]] | 블록 내부 반복 패턴 | 실시간 경로 부담이 적음 | 최초 저장 공간 필요 |
| [[501_file_definition_logical_record|파일]] [[347_compaction|압축]] | 사용자 또는 애플리케이션 단계 | [[501_file_definition_logical_record|파일]] 자체 | 이동·보관 편의 | 투명성 부족 |
| 중복 제거 | 저장 전/후 | 블록 간 동일성 | 반복 [[501_file_definition_logical_record|파일]]에 매우 강함 | [[154_database_index_b_tree_search_optimization|인덱스]] 비용 큼 |

실무에서는 인라인 [[347_compaction|압축]]과 중복 제거를 함께 쓰는 경우가 많다. 먼저 동일한 블록을 하나로 줄이고, 남은 블록 내부 패턴까지 [[347_compaction|압축]]하면 절감률이 커지기 때문이다. 다만 두 기술 모두 [[012_metadata|메타데이터]]를 많이 요구하므로, 읽기 경로가 복잡해지는 비용도 같이 고려해야 한다.

- **📢 섹션 요약 비유**: 인라인 [[347_compaction|압축]]은 짐을 실기 전에 상자 크기를 줄이는 일이고, 중복 제거는 똑같은 상자를 하나만 싣는 일이다. 둘 다 창고를 넓게 쓰게 해 주지만, 상자 목록 관리가 더 중요해진다.

## Ⅳ. 실무 적용 및 기술사 판단

인라인 [[347_compaction|압축]]은 [[568_logs_distributed_logging_elk_fluentd|로그]] 저장소, 가상 머신 이미지, 분석 [[001_dikw_pyramid|데이터]], [[555_backup_and_restore_strategy|백업]] 저장소처럼 반복 패턴이 많은 워크로드에서 특히 유효하다. 반면 이미 [[347_compaction|압축]]된 미디어 [[501_file_definition_logical_record|파일]], [[365_tde|데이터베이스 암호화]] [[286_page_frame|페이지]], 고속 저지연 거래 [[568_logs_distributed_logging_elk_fluentd|로그]]처럼 [[347_compaction|압축]] 이득이 작거나 [[015_지연_데이터_관점|지연]] 예산이 매우 짧은 환경에서는 신중해야 한다. 이런 구간에서는 빠른 [[001_algorithm_definition|알고리즘]]을 쓰거나, [[347_compaction|압축]]률 임계값을 두어 이득이 작으면 바로 우회시키는 [[164_policy|정책]]이 필요하다.

기술사 관점에서는 세 가지를 같이 본다. 첫째, [[347_compaction|압축]]률보다 평균 [[015_지연_데이터_관점|지연]]과 꼬리 [[015_지연_데이터_관점|지연]]이 [[090_service_kubernetes_network_load_balancing|서비스]] 수준을 만족하는가. 둘째, 읽기 시 복원 부하가 피크 시간대에 병목이 되지 않는가. 셋째, 삭제와 덮어쓰기가 잦을 때 가변 길이 블록 관리가 조각화를 유발하지 않는가. 특히 컨트롤러 캐시가 작거나 CPU 여유가 부족한 장비에서 공격적으로 인라인 [[347_compaction|압축]]을 걸면, 용량은 아껴도 응답 시간은 오히려 불안정해질 수 있다.

안티패턴도 분명하다. [[347_compaction|압축]]이 거의 안 되는 [[001_dikw_pyramid|데이터]]에 무조건 동일 [[164_policy|정책]]을 적용하는 것, [[012_metadata|메타데이터]] [[571_protection_vs_security|보호]] 없이 [[347_compaction|압축]]만 강조하는 것, 읽기 [[282_performance_tactics|성능]] 요구가 높은 시스템에서 복원 비용을 과소평가하는 것은 대표적인 실패 사례다. 결국 인라인 [[347_compaction|압축]]은 “[[347_compaction|압축]]률 최고치”보다 “예측 가능한 [[015_지연_데이터_관점|지연]]”을 기준으로 설계해야 한다.

- **📢 섹션 요약 비유**: 옷을 여행 가방에 최대한 눌러 담으면 많이 들어가지만, 공항에서 급히 꺼낼 때 시간이 더 걸릴 수 있다. 그래서 비행시간이 촉박하면 조금 덜 눌러 담더라도 빨리 꺼낼 수 있게 정리하는 것이 더 현명하다.

## Ⅴ. 기대효과 및 결론

인라인 [[347_compaction|압축]]은 유효 용량 확대, 기록량 감소, 플래시 마모 완화라는 세 가지 효과를 동시에 만든다. 같은 장비로 더 많은 [[001_dikw_pyramid|데이터]]를 운영할 수 있고, 백엔드 [[289_cqrs_db|쓰기]]량이 줄어 [[282_performance_tactics|성능]]과 수명 모두에 긍정적인 영향을 줄 수 있다. 특히 올플래시 환경에서는 이 차이가 총소유비용에 직접 반영된다.

반면 이 모든 이점은 [[347_compaction|압축]] 엔진과 [[012_metadata|메타데이터]] 계층이 안정적으로 동작할 때만 성립한다. 앞으로는 스토리지 컨트롤러 내부 가속기, 메모리 계층 [[347_compaction|압축]], 계산 스토리지 형태의 오프로딩이 더 확대될 가능성이 크다. 즉 인라인 [[347_compaction|압축]]은 단순 기능이 아니라, 저장 경로 전체를 더 적은 바이트로 운영하려는 아키텍처 전략으로 봐야 한다.

결론적으로 인라인 [[347_compaction|압축]]은 “저장 후 정리”가 아니라 “들어오는 순간 최적화”다. 물리 매체에 [[289_cqrs_db|쓰기]] 전에 얼마나 똑똑하게 줄이고 우회하느냐가 [[282_performance_tactics|성능]]과 비용을 함께 결정한다.

- **📢 섹션 요약 비유**: 좋은 인라인 [[347_compaction|압축]]은 현관에서 신발을 가지런히 정리하고 들어오는 습관과 같다. 집 안이 늘 넓게 유지되지만, 정리 동선이 복잡하면 오히려 들어오는 시간이 느려질 수 있다.
