## 핵심 인사이트 (3줄 요약)

> 1. **본질**: 암달의 법칙 (Amdahl's Law)은 시스템의 한 부분만 빨라져도 전체 [[282_performance_tactics|성능]] 향상은 그 부분이 원래 차지하던 실행 시간 비중에 의해 제한된다는 법칙이다.
> 2. **가치**: 이 법칙은 "코어를 더 넣으면 얼마나 빨라질까"를 감이 아니라 수식으로 판단하게 해 주며, [[430_index_fast_full_scan|병렬]]화보다 먼저 순차 병목을 찾아야 하는 이유를 설명한다.
> 3. **판단 포인트**: [[430_index_fast_full_scan|병렬]] 처리 자원을 늘릴수록 중요한 것은 총 코어 수가 아니라, [[430_index_fast_full_scan|병렬]]화 불가능한 구간과 [[212_synchronization_mechanisms|동기화]] 오버헤드가 전체 시간에서 몇 퍼센트를 차지하는가이다.

---

## Ⅰ. 개요 및 필요성

암달의 법칙 (Amdahl's Law)은 **전체 작업 중 개선 가능한 부분의 비율이 전체 [[282_performance_tactics|성능]] 향상의 상한선을 결정한다**는 [[282_performance_tactics|성능]] 분석 원리다. 이 법칙이 중요한 이유는 컴퓨터 시스템의 병목이 보통 가장 느린 부분에 숨어 있기 때문이다. 중앙처리장치 (Central Processing Unit, CPU) 코어를 늘리거나 그래픽처리장치 ([[418_gpu|Graphics Processing Unit]], [[418_gpu|GPU]])를 붙여도, 초기화·[[149_serial_communication_rs232_rs485|직렬]] 계산·입출력·락 대기처럼 동시에 처리할 수 없는 구간이 남아 있으면 전체 시간은 그 구간 때문에 멈춘다.

즉 암달의 법칙은 "[[430_index_fast_full_scan|병렬]] 자원 증설" 자체를 부정하는 것이 아니라, **[[430_index_fast_full_scan|병렬]]화 가능한 비율과 순차 구간의 잔존량을 먼저 측정하라**고 요구한다. 그래서 이 법칙은 멀티코어 설계, [[430_index_fast_full_scan|병렬]] 프로그램 튜닝, 가속기 도입, 클라우드 [[202_scale_out_distributed_horizontal_expansion|스케일 아웃]] 판단의 공통 기준으로 쓰인다.

- **📢 섹션 요약 비유**: 주방에 요리사 10명을 더 넣어도 마지막 plating을 셰프 1명이 해야 한다면, 식당 전체 주문 속도는 그 마지막 한 사람의 손속도에 묶인다.

## Ⅱ. 아키텍처 및 핵심 원리

암달의 법칙의 핵심은 전체 실행 시간을 **순차 구간**과 **[[430_index_fast_full_scan|병렬]]화 가능한 구간**으로 나누는 데 있다. [[430_index_fast_full_scan|병렬]]화 가능한 비율을 `P`, 사용한 프로세서 수를 `N`이라고 하면 전체 [[144_speedup|속도 향상도]]는 다음처럼 표현된다.

\[
[[144_speedup|Speedup]] = \frac{1}{(1-P) + \frac{P}{N}}
\]

여기서 `(1 - P)`는 아무리 자원을 추가해도 남는 순차 비율이다. 따라서 `N`이 무한히 커져도 최대 [[144_speedup|속도 향상도]]는 아래 한계를 넘지 못한다.

\[
Max\ [[144_speedup|Speedup]] = \frac{1}{1-P}
\]

예를 들어 전체 작업의 90%만 [[430_index_fast_full_scan|병렬]]화 가능하다면, 코어를 아무리 많이 추가해도 최대 속도 향상은 10배다. 95% [[430_index_fast_full_scan|병렬]]화라면 상한은 20배다. 이 계산은 [[430_index_fast_full_scan|병렬]] 하드웨어의 가치를 평가할 때 "몇 개 넣을 수 있느냐"보다 "얼마나 순차 비율을 줄였느냐"가 더 중요함을 보여 준다.

```text
┌──────────────────────────────────────────────────────────────────────┐
│                  암달의 법칙이 보여주는 병렬화의 한계               │
├──────────────────────────────────────────────────────────────────────┤
│ 전체 실행 시간 = 순차 구간 + 병렬 구간                              │
│                                                                      │
│ 1코어 실행:   [ 순차 10% ][                병렬 90%                ] │
│ 4코어 실행:   [ 순차 10% ][      병렬 90% / 4로 분할 처리         ] │
│ 64코어 실행:  [ 순차 10% ][ 병렬 90% / 64로 더 작아짐             ] │
│                                                                      │
│ 그런데도 남는 것                                                     │
│                └──────────── 순차 10%는 끝까지 그대로 ────────────┘ │
│                                                                      │
│ N → ∞ 여도 전체 속도 향상 상한 = 1 / 0.10 = 10배                    │
└──────────────────────────────────────────────────────────────────────┘
```

이 그림의 요점은 [[430_index_fast_full_scan|병렬]] 구간은 계속 쪼갤 수 있어도, 순차 구간은 전체 시간의 바닥처럼 남는다는 점이다. 실제 시스템에서는 여기에 [[402_cache_coherence|캐시 일관성]], [[092_thread_lwp|스레드]] [[087_process_state_transition|생성]], [[212_synchronization_mechanisms|동기화]], [[001_dikw_pyramid|데이터]] 이동 비용까지 추가되므로 체감 [[282_performance_tactics|성능]]은 이론치보다 더 낮아지는 경우가 많다.

| [[430_index_fast_full_scan|병렬]]화 가능 비율 `P` | 이론적 최대 [[144_speedup|속도 향상도]] | 의미 |
| :--- | :---: | :--- |
| 0.50 | 2배 | 절반만 [[430_index_fast_full_scan|병렬]]화되면 자원 증설 효과가 매우 빨리 포화된다. |
| 0.80 | 5배 | [[430_index_fast_full_scan|병렬]]화가 커 보여도 순차 20%가 큰 벽으로 남는다. |
| 0.90 | 10배 | 고성능 서버에서도 순차 구간 제거가 계속 중요하다. |
| 0.99 | 100배 | 거의 완벽한 [[430_index_fast_full_scan|병렬]]화가 되어야 대규모 확장이 의미를 가진다. |

- **📢 섹션 요약 비유**: 큰 물탱크를 아무리 넓혀도 배수구가 좁으면 전체 배수 속도는 결국 그 배수구 굵기에 의해 정해진다.

## Ⅲ. 비교 및 연결

암달의 법칙을 제대로 이해하려면 **[[144_speedup|속도 향상도]] ([[144_speedup|Speedup]])**, **[[142_performance_equation|컴퓨터 성능 방정식]] ([[142_performance_equation|Performance Equation]])**, **구스타프슨의 법칙 (Gustafson's Law)**과 함께 봐야 한다. 암달의 법칙은 고정된 문제 크기에서 "얼마나 더 빨라질 수 있는가"를 묻는 반면, 구스타프슨의 법칙은 자원이 늘 때 "더 큰 문제를 같은 시간 안에 처리할 수 있는가"를 본다.

| 비교 항목 | 암달의 법칙 (Amdahl's Law) | 구스타프슨의 법칙 (Gustafson's Law) |
| :--- | :--- | :--- |
| 문제 크기 가정 | 고정된 작업량 | 프로세서 수에 따라 작업량 확대 가능 |
| 핵심 질문 | 한 작업을 얼마나 더 빨리 끝낼 수 있는가 | 더 큰 작업을 얼마나 효율적으로 처리할 수 있는가 |
| 강조점 | 순차 병목의 제거 | 확장 가능한 [[430_index_fast_full_scan|병렬]] 작업의 확대 |
| 잘 맞는 관점 | 지연시간 ([[141_latency|Latency]]) 중심 [[090_service_kubernetes_network_load_balancing|서비스]] | [[139_throughput|처리량]] ([[139_throughput|Throughput]]) 중심 대규모 연산 |

이 차이는 설계 의사결정을 바꾼다. 예를 들어 사용자 [[138_response_time|응답 시간]]을 줄여야 하는 온라인 [[191_transaction_concept_states|트랜잭션]] 처리 (Online [[191_transaction_concept_states|Transaction]] Processing, [[327_hint_handoff|OLTP]]) [[090_service_kubernetes_network_load_balancing|서비스]]는 암달의 법칙 관점이 더 중요하다. 반대로 과학 계산이나 [[231_ai_turing_test|인공지능]] 학습처럼 [[001_dikw_pyramid|데이터]] 크기를 키우며 많은 자원을 계속 활용하는 환경은 구스타프슨의 법칙 설명력이 더 크다. 즉 둘은 서로 반박하는 법칙이라기보다, **문제의 크기를 고정해서 볼 것인가 확장해서 볼 것인가**의 차이다.

- **📢 섹션 요약 비유**: 암달은 "피자 1판을 더 빨리 굽는 법"을 묻고, 구스타프슨은 "오븐이 많아졌으니 피자 100판 주문을 동시에 받을 수 있는가"를 묻는다.

## Ⅳ. 실무 적용 및 기술사 판단

실무에서 암달의 법칙은 단순 수식 암기가 아니라 **투자 우선순위를 정하는 기준**으로 써야 한다. 핵심은 [[430_index_fast_full_scan|병렬]] 자원 추가 전에 순차 병목을 계측하고, [[430_index_fast_full_scan|병렬]]화 이후에는 오버헤드가 새 병목이 되는지 확인하는 것이다.

### [[435_checklist_based_testing|체크리스트]]

1. 전체 실행 시간 중 [[430_index_fast_full_scan|병렬]]화 가능한 비율 `P`를 실제 측정으로 구했는가?
2. 순차 구간의 실체가 초기화, 입출력, 락, 단일 [[092_thread_lwp|스레드]] [[001_algorithm_definition|알고리즘]] 중 무엇인지 분해했는가?
3. 코어 수 증가에 따라 [[212_synchronization_mechanisms|동기화]] 비용과 메모리 [[140_bandwidth|대역폭]] 병목이 새로 생기지 않는가?
4. 목표가 [[138_response_time|응답 시간]] 개선인지, [[139_throughput|처리량]] 확대인지 먼저 구분했는가?

### 실무 판단 예시

- 웹 서버에서 요청 처리의 15%가 [[002_database_definition|데이터베이스]] [[149_serial_communication_rs232_rs485|직렬]] 구간이라면, 애플리케이션 서버 코어만 늘려서는 기대한 [[282_performance_tactics|성능]]이 나오지 않는다. 이때는 코어 증설보다 질의 구조 개선, 캐시 도입, 락 범위 축소가 먼저다.
- [[430_index_fast_full_scan|병렬]] 연산 가속기를 붙이는 경우에도 호스트 중앙처리장치 (Central Processing Unit, CPU)와 장치 사이 [[001_dikw_pyramid|데이터]] 복사 시간이 크면 전체 향상은 제한된다. 따라서 가속기 자체 [[282_performance_tactics|성능]]보다 [[001_dikw_pyramid|데이터]] 이동 구조를 함께 설계해야 한다.

### [[128_water_scrum_fall_anti_pattern|안티패턴]]

- **측정 없이 코어만 늘리는 설계**: [[430_index_fast_full_scan|병렬]]화 비율을 모르는 상태에서 인프라만 키우면 비용은 선형으로 증가하지만 [[282_performance_tactics|성능]]은 빠르게 포화된다.
- **락 경합을 숨긴 채 멀티스레드화하는 설계**: 코드 겉모습은 [[430_index_fast_full_scan|병렬]]이지만 [[214_critical_section|임계 구역]] ([[214_critical_section|Critical Section]])이 크면 실제로는 대부분 줄 서는 구조가 된다.

- **📢 섹션 요약 비유**: 차가 막히는 원인이 톨게이트인데 도로 차선만 늘리는 것은, 병목 위치를 잘못 본 대표적인 예다.

## Ⅴ. 기대효과 및 결론

암달의 법칙을 이해하면 [[282_performance_tactics|성능]] 개선을 더 냉정하게 볼 수 있다. 이 법칙은 "[[430_index_fast_full_scan|병렬]]화는 중요하지만 만능은 아니다"라는 사실을 분명히 보여 주며, 병목 제거와 구조 개선이 왜 하드웨어 증설보다 먼저 검토되어야 하는지 설명한다. 특히 멀티코어, [[136_variance|분산]] 처리, 가속기 활용이 일반화된 지금도 이 법칙은 여전히 유효하다.

다만 암달의 법칙은 **문제 크기가 고정되어 있다는 전제** 위에서 가장 강하게 작동한다. 그래서 대규모 [[001_dikw_pyramid|데이터]] 분석이나 [[231_ai_turing_test|인공지능]] 학습처럼 문제 자체가 커지는 환경에서는 구스타프슨의 법칙과 함께 봐야 균형 잡힌 판단이 가능하다. 결국 이 개념은 "코어를 몇 개 더 살까"보다 **"전체 시간에서 끝까지 남는 비병렬 구간을 얼마나 줄일 수 있는가"**로 기억하는 것이 맞다.

- **📢 섹션 요약 비유**: 줄다리기에서 힘센 사람을 더 데려오는 것보다, 묶인 매듭 하나를 먼저 풀어 주는 편이 전체 움직임을 더 크게 바꾼다.

### 👶 어린이를 위한 3줄 비유 설명

1. 친구들이 숙제를 같이 해도, 마지막에 선생님께 제출하는 일은 한 명이 해야 하면 그 시간이 꼭 남아요.
2. 그래서 친구를 계속 더 데려와도 숙제가 무한히 빨라지지는 않아요.
3. 진짜로 빨라지려면 친구 수를 늘리기 전에, 혼자 해야 하는 마지막 일을 줄이는 방법부터 찾아야 해요.
