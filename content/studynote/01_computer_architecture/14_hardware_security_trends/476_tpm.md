## 핵심 인사이트 (3줄 요약)

> 1. **본질**: TPM (Trusted Platform [Module](/knowledge-base/studynote/04_software_engineering/04_testing_quality/192_module_independence/))은 플랫폼에 붙은 하드웨어 루트 오브 트러스트로서, 부팅 측정값과 장치 바인딩 키를 [보호](/knowledge-base/studynote/02_operating_system/10_security/571_protection_vs_security/)해 "이 장치가 어떤 상태에서 켜졌는가"를 증명하게 만든다.
> 2. **가치**: 비트로커 ([BitLocker](/knowledge-base/studynote/09_security/04_endpoint_security/397_bitlocker_windows_fde/)), [Measured Boot](/knowledge-base/studynote/09_security/18_iot_ot_physical/919_measured_boot/), 원격 증명 ([Remote Attestation](/knowledge-base/studynote/09_security/04_endpoint_security/396_remote_attestation/)), 장치 신원 확인은 TPM 덕분에 [운영체제](/knowledge-base/studynote/02_operating_system/01_overview_architecture/001_operating_system_purpose/) 바깥의 신뢰 출발점을 확보할 수 있다.
> 3. **판단 포인트**: TPM은 HSM처럼 대량 암호 연산을 처리하는 장치가 아니라, [부팅 무결성](/knowledge-base/studynote/09_security/18_iot_ot_physical/916_secure_boot/) 측정·키 실링 (Sealing)·장치 신뢰 증명을 담당하는 보드 수준 신뢰 앵커로 이해해야 한다.

---

## Ⅰ. 개요 및 필요성

TPM (Trusted Platform [Module](/knowledge-base/studynote/04_software_engineering/04_testing_quality/192_module_independence/))은 메인보드나 프로세서 보안 블록 안에 탑재되는 신뢰 칩으로, 장치 고유 키와 부팅 측정값을 [보호](/knowledge-base/studynote/02_operating_system/10_security/571_protection_vs_security/)하는 하드웨어 [모듈](/knowledge-base/studynote/04_software_engineering/04_testing_quality/192_module_independence/)이다. 핵심 목적은 [운영체제](/knowledge-base/studynote/02_operating_system/01_overview_architecture/001_operating_system_purpose/)가 자기 자신을 믿는 순환 논리를 끊는 데 있다. BIOS나 [부트로더](/knowledge-base/studynote/02_operating_system/01_overview_architecture/029_bootloader/)가 이미 변조된 상태라면, 그 위에 올라온 [운영체제](/knowledge-base/studynote/02_operating_system/01_overview_architecture/001_operating_system_purpose/)는 아무리 "정상"이라고 말해도 스스로를 충분히 증명할 수 없기 때문이다.

그래서 TPM은 부팅 과정 바깥에 있는 작은 증인 역할을 맡는다. [펌웨어](/knowledge-base/studynote/02_operating_system/01_overview_architecture/032_firmware/), [부트로더](/knowledge-base/studynote/02_operating_system/01_overview_architecture/029_bootloader/), [커널](/knowledge-base/studynote/02_operating_system/01_overview_architecture/022_kernel_role/), [초기](/knowledge-base/studynote/03_network/08_transport_layer/459_quic_fec_forward_error_correction/) 드라이버가 차례로 로드될 때 각 단계의 해시를 PCR (Platform Configuration [Register](/knowledge-base/studynote/01_computer_architecture/04_instruction_set_architecture/175_register_addressing/))에 누적 기록하고, 특정 상태에서만 키를 꺼내 주거나 원격 서비스에 현재 플랫폼 상태를 증명한다. 이 덕분에 장치 보안은 단순 패스워드 [보호](/knowledge-base/studynote/02_operating_system/10_security/571_protection_vs_security/)에서 "정상 상태에서만 비밀을 제공하는 구조"로 발전했다.

아래 그림은 TPM이 왜 필요한지 보여 준다.

```text
+----------------------------------------------------------------------------+
|            TPM의 필요성: 운영체제가 손상될 수 있으니, 외부 증인이 필요하다   |
+----------------------------------------------------------------------------+
| 전원 인가                                                                   |
|    |                                                                        |
|    v                                                                        |
| 펌웨어 / 부트로더 / 커널 순차 로드                                           |
|    |                                                                        |
|    +- 각 단계가 스스로 "정상"이라 말할 수는 있음                            |
|    |                                                                        |
|    +- 하지만 이미 손상되었다면 그 말도 믿기 어려움                           |
|                                                                             |
| TPM은 별도 하드웨어에서 각 단계 해시를 기록하고,                            |
| 정상 측정값일 때만 키 제공 또는 원격 증명을 수행한다.                        |
+----------------------------------------------------------------------------+
```

즉 TPM의 강점은 "모든 공격을 막는다"가 아니라 "플랫폼 상태를 신뢰 가능한 방식으로 재는 기준점을 준다"에 있다. Secure Boot가 실행을 막는 문지기라면, TPM은 무엇이 실제로 올라왔는지 기록하고 증명하는 기록 장치에 가깝다.

- **📢 섹션 요약 비유**: TPM은 시험장 CCTV와 같다. 시험지를 누가 어떻게 바꿨는지 기록이 남아 있어야, 나중에 "정상 진행이었다"는 말을 믿을 수 있다.

## Ⅱ. 아키텍처 및 핵심 원리

TPM 2.0의 핵심 요소는 PCR, EK (Endorsement [Key](/knowledge-base/studynote/05_database/02_modeling_normalization/067_db_key_uniqueness_minimality/)), 저장 계층 키, Attestation [Key](/knowledge-base/studynote/05_database/02_modeling_normalization/067_db_key_uniqueness_minimality/), Sealed Object다. EK는 칩의 신원 뿌리 역할을 하고, PCR은 부팅과 런타임 이벤트의 측정값을 누적하며, Attestation Key는 현재 플랫폼 상태에 대한 서명을 담당한다. Sealing은 비밀 값을 특정 PCR 조합에 묶어, 기대한 부팅 상태가 아닐 때는 그 비밀을 풀지 못하게 만드는 기능이다.

중요한 점은 PCR이 단순 덮어쓰기가 아니라 Extend 연산으로 누적된다는 것이다. 보통 `PCR[n] = Hash(PCR[n] || 새 측정값)` 형태를 쓰므로, 중간 단계 하나라도 바뀌면 최종 PCR 값이 완전히 달라진다. 이 구조 덕분에 공격자가 "정상 부팅처럼 보이게" 일부만 슬쩍 바꾸는 일이 어려워진다.

| 구성 요소 | 역할 | 설계·운영 포인트 |
| :-- | :-- | :-- |
| PCR (Platform Configuration [Register](/knowledge-base/studynote/01_computer_architecture/04_instruction_set_architecture/175_register_addressing/)) | 부팅 측정값 누적 저장 | 어떤 단계가 어떤 PCR에 들어가는지 [정책](/knowledge-base/studynote/10_ai/02_dl_architecture_new/164_policy/) 관리 |
| EK (Endorsement [Key](/knowledge-base/studynote/05_database/02_modeling_normalization/067_db_key_uniqueness_minimality/)) | TPM 고유 신원 뿌리 | 제조 신뢰 체계와 프라이버시 고려 |
| Attestation [Key](/knowledge-base/studynote/05_database/02_modeling_normalization/067_db_key_uniqueness_minimality/) | [현재 상태](/knowledge-base/studynote/04_software_engineering/03_design_architecture/178_as_is_to_be_analysis/) 증명용 서명 키 | 원격 [검증](/knowledge-base/studynote/04_software_engineering/07_object_oriented/395_verification_process_review/) [정책](/knowledge-base/studynote/10_ai/02_dl_architecture_new/164_policy/)과 연동 필요 |
| Sealed [Secret](/knowledge-base/studynote/04_software_engineering/08_security_compliance_devsecops/514_secret_management_vault_kms/) | 특정 PCR 조합에 묶인 비밀 | [BitLocker](/knowledge-base/studynote/09_security/04_endpoint_security/397_bitlocker_windows_fde/), 장치 비밀 [보호](/knowledge-base/studynote/02_operating_system/10_security/571_protection_vs_security/)에 활용 |
| NV Storage | 영속 보안 [데이터](/knowledge-base/studynote/05_database/01_db_architecture_relational/001_dikw_pyramid/) 저장 | [초기](/knowledge-base/studynote/03_network/08_transport_layer/459_quic_fec_forward_error_correction/)화 [정책](/knowledge-base/studynote/10_ai/02_dl_architecture_new/164_policy/), 장치 교체 시 영향 고려 |

아래 그림은 TPM이 측정과 실링을 어떻게 결합하는지 보여 준다.

```text
+----------------------------------------------------------------------------+
|              TPM 동작 개요: 측정값을 쌓고, 맞는 상태에서만 비밀을 푼다        |
+----------------------------------------------------------------------------+
| [CRTM / 펌웨어] -- 측정값 ---> PCR[0] Extend                                 |
| [부트로더]     -- 측정값 ---> PCR[1] Extend                                 |
| [커널/드라이버] -- 측정값 ---> PCR[7] Extend                                 |
|                                                                            |
| Sealed Secret                                                               |
|   +- "PCR[0], PCR[1], PCR[7]이 기대값과 같을 때만 복호화 허용"              |
|                                                                            |
| Remote Attestation                                                          |
|   +- Attestation Key로 PCR 요약값 서명 ---> 원격 검증 서버                   |
|                                                                            |
| 결과: 정상 부팅이면 키 사용 가능, 상태가 달라지면 비밀 해제 거부             |
+----------------------------------------------------------------------------+
```

이 구조 때문에 TPM은 [성능](/knowledge-base/studynote/04_software_engineering/05_devops_ci_cd/282_performance_tactics/) 장치가 아니라 [정책](/knowledge-base/studynote/10_ai/02_dl_architecture_new/164_policy/) 장치에 가깝다. 암호 연산량 자체는 HSM보다 작지만, "이 장치가 신뢰 가능한 상태인가"를 장치 스스로 증명하게 한다는 점에서 매우 독특하다. 또 구현 방식도 dTPM (Discrete TPM), fTPM ([Firmware](/knowledge-base/studynote/02_operating_system/01_overview_architecture/032_firmware/) TPM), Pluton 같은 통합형으로 나뉘며, 보안 경계와 운영 편의성 사이에서 각각 trade-off가 있다.

- **📢 섹션 요약 비유**: TPM은 금고 비밀번호를 기억하는 장치가 아니라, 집 안이 정상 상태인지 확인해야만 비밀번호를 알려 주는 경비원과 같다.

## Ⅲ. 비교 및 연결

TPM을 제대로 이해하려면 Secure Boot와 구분해야 한다. Secure Boot는 서명되지 않은 코드를 실행하지 못하게 하는 예방 통제이고, TPM 기반 Measured Boot는 실제로 무엇이 실행되었는지를 기록하고 증명하는 탐지·증명 통제다. 둘은 경쟁 관계가 아니라 보완 관계다. Secure Boot만 있으면 "차단"은 되지만 상태 증명이 약하고, TPM만 있으면 기록은 남지만 악성 코드 실행을 즉시 막지는 못할 수 있다.

| 구분 | TPM [Measured Boot](/knowledge-base/studynote/09_security/18_iot_ot_physical/919_measured_boot/) | [Secure Boot](/knowledge-base/studynote/02_operating_system/10_security/608_secure_boot/) | [HSM](/knowledge-base/studynote/01_computer_architecture/14_hardware_security_trends/475_hsm/) |
| :-- | :-- | :-- | :-- |
| 핵심 역할 | 부팅 상태 측정·증명 | 서명 [검증](/knowledge-base/studynote/04_software_engineering/07_object_oriented/395_verification_process_review/)으로 실행 차단 | 중앙 키 [보호](/knowledge-base/studynote/02_operating_system/10_security/571_protection_vs_security/)와 암호 연산 |
| 배치 위치 | 플랫폼 보안 [모듈](/knowledge-base/studynote/04_software_engineering/04_testing_quality/192_module_independence/) | [펌웨어](/knowledge-base/studynote/02_operating_system/01_overview_architecture/032_firmware/) [검증](/knowledge-base/studynote/04_software_engineering/07_object_oriented/395_verification_process_review/) 체계 | 별도 장치/어플라이언스 |
| 대표 사용처 | [BitLocker](/knowledge-base/studynote/09_security/04_endpoint_security/397_bitlocker_windows_fde/), 장치 증명 | [부트킷](/knowledge-base/studynote/09_security/04_endpoint_security/362_bootkit/) 방지 | Root [CA](/knowledge-base/studynote/06_ict_convergence/01_blockchain/089_contract_account_smart_contract/), 결제, [KMS](/knowledge-base/studynote/07_enterprise_systems/02_erp_systems/127_kms_knowledge_management_system/) |
| 주요 질문 | 지금 상태가 정상인가 | 실행 전 허용 가능한가 | 키를 밖으로 내보내지 않는가 |

TPM은 [운영체제](/knowledge-base/studynote/02_operating_system/01_overview_architecture/001_operating_system_purpose/), [제로 트러스트](/knowledge-base/studynote/02_operating_system/10_security/667_zero_trust_runtime_integrity_measurement/), 엔드포인트 관리와도 깊게 연결된다. 기업은 원격 증명으로 "패치된 [펌웨어](/knowledge-base/studynote/02_operating_system/01_overview_architecture/032_firmware/)와 정상 부팅 상태의 장치만 VPN에 접속 허용" 같은 [정책](/knowledge-base/studynote/10_ai/02_dl_architecture_new/164_policy/)을 만들 수 있고, 디스크 암호화는 특정 장치·특정 부팅 상태에 바인딩할 수 있다. 즉 TPM은 장치 신뢰의 출발점이지, 단독 보안 완성품은 아니다.

또한 TPM은 TEE나 HSM과 계층적으로 결합될 수 있다. TPM이 부팅 신뢰를 제공하고, TEE가 런타임 민감 연산을 [보호](/knowledge-base/studynote/02_operating_system/10_security/571_protection_vs_security/)하며, HSM이 조직 최고가치 키를 맡는 구조가 흔하다. 이 연결을 봐야 TPM의 위치가 선명해진다.

- **📢 섹션 요약 비유**: Secure Boot가 입구의 문지기라면, TPM은 출입 기록부이고, HSM은 중앙 금고다. 셋 다 필요할 수 있지만 하는 일은 서로 다르다.

## Ⅳ. 실무 적용 및 기술사 판단

실무에서 TPM은 가장 자주 디스크 암호화와 장치 신뢰 증명에 쓰인다. Windows에서는 BitLocker가 TPM과 결합해 정상 부팅일 때만 볼륨 키를 자동 해제할 수 있고, 서버·엣지 장치에서는 원격 증명으로 "허용된 [펌웨어](/knowledge-base/studynote/02_operating_system/01_overview_architecture/032_firmware/) 상태의 장치만 서비스망에 붙인다"는 [정책](/knowledge-base/studynote/10_ai/02_dl_architecture_new/164_policy/)을 구성할 수 있다. 특히 사람이 직접 비밀번호를 입력하지 않는 무인 장비일수록 TPM의 장치 바인딩이 의미를 가진다.

### 적용 판단 [체크리스트](/knowledge-base/studynote/04_software_engineering/11_testing_validation/435_checklist_based_testing/)

1. <strong><a href="/knowledge-base/studynote/09_security/13_secops_ir_forensics/658_ir_recovery/">복구</a> <a href="/knowledge-base/studynote/04_software_engineering/04_testing_quality/268_strategy_pattern/">전략</a></strong>: TPM 상태가 바뀌거나 보드가 교체될 때 [복구](/knowledge-base/studynote/09_security/13_secops_ir_forensics/658_ir_recovery/) 키와 운영 절차가 준비되어 있는가?
2. <strong>PCR <a href="/knowledge-base/studynote/10_ai/02_dl_architecture_new/164_policy/">정책</a></strong>: 어떤 [펌웨어](/knowledge-base/studynote/02_operating_system/01_overview_architecture/032_firmware/)·부트 단계 변화를 정상으로 볼지 명확히 정의했는가?
3. <strong>증명 <a href="/knowledge-base/studynote/10_ai/02_dl_architecture_new/164_policy/">정책</a></strong>: 원격 증명 결과를 실제 접근 제어에 반영하는가?
4. **구현 방식 선택**: dTPM, fTPM, 통합형 중 위협 모델에 맞는 선택을 했는가?
5. **업데이트 관리**: BIOS/[UEFI](/knowledge-base/studynote/01_computer_architecture/15_advanced_topics/706_uefi/) 업데이트가 실링된 비밀 해제 [정책](/knowledge-base/studynote/10_ai/02_dl_architecture_new/164_policy/)에 어떤 영향을 주는지 파악했는가?

### 피해야 할 [안티패턴](/knowledge-base/studynote/04_software_engineering/02_requirements_analysis/128_water_scrum_fall_anti_pattern/)

- TPM만 있으면 [부트킷](/knowledge-base/studynote/09_security/04_endpoint_security/362_bootkit/) 방지까지 자동 해결된다고 오해하는 것
- [BitLocker](/knowledge-base/studynote/09_security/04_endpoint_security/397_bitlocker_windows_fde/) [복구](/knowledge-base/studynote/09_security/13_secops_ir_forensics/658_ir_recovery/) 키를 안전하게 보관하지 않아 보드 교체 후 [데이터](/knowledge-base/studynote/05_database/01_db_architecture_relational/001_dikw_pyramid/)에 접근하지 못하는 것
- PCR 변화 원인을 분석하지 않고 무조건 TPM [초기](/knowledge-base/studynote/03_network/08_transport_layer/459_quic_fec_forward_error_correction/)화를 반복하는 것
- 원격 증명 [데이터](/knowledge-base/studynote/05_database/01_db_architecture_relational/001_dikw_pyramid/)를 수집만 하고 실제 [정책](/knowledge-base/studynote/10_ai/02_dl_architecture_new/164_policy/) 결정에는 쓰지 않는 것

기술사 답안에서는 TPM을 "작은 [HSM](/knowledge-base/studynote/01_computer_architecture/14_hardware_security_trends/475_hsm/)"이라고 쓰면 부정확하다. TPM의 본질은 처리량이 아니라 신뢰 상태 측정과 장치 바인딩이다. 따라서 답안에서는 [Measured Boot](/knowledge-base/studynote/09_security/18_iot_ot_physical/919_measured_boot/), Sealing, [Remote Attestation](/knowledge-base/studynote/09_security/04_endpoint_security/396_remote_attestation/), Secure Boot와의 관계까지 함께 설명해야 한다.

- **📢 섹션 요약 비유**: TPM 운영은 자물쇠를 하나 더 다는 일이 아니라, 집 상태가 정상일 때만 열쇠를 주는 관리 규칙을 만드는 일과 같다.

## Ⅴ. 기대효과 및 결론

TPM을 잘 활용하면 장치 신뢰를 사람의 기억이나 소프트웨어 설정에만 맡기지 않아도 된다. 부팅 상태 측정, 디스크 키 실링, 원격 증명 덕분에 엔드포인트 보안은 "설치되어 있다"가 아니라 "지금도 정상 상태다"를 기준으로 판단할 수 있다. 이는 [제로 트러스트](/knowledge-base/studynote/02_operating_system/10_security/667_zero_trust_runtime_integrity_measurement/) 단말 관리, 무인 장비 운영, 기업 [PC](/knowledge-base/studynote/01_computer_architecture/04_instruction_set_architecture/164_pc/) [보호](/knowledge-base/studynote/02_operating_system/10_security/571_protection_vs_security/)에서 큰 장점이다.

하지만 TPM은 만능이 아니다. 런타임 메모리 전체를 [보호](/knowledge-base/studynote/02_operating_system/10_security/571_protection_vs_security/)하지도 않고, 고성능 암호 연산 장치도 아니다. 또한 부팅 이후 애플리케이션 침해, 사용자 계정 탈취, 네트워크 공격까지 단독으로 막아 주지 않는다. 그래서 TPM은 [Secure Boot](/knowledge-base/studynote/02_operating_system/10_security/608_secure_boot/), OS 하드닝, [EDR](/knowledge-base/studynote/09_security/04_endpoint_security/325_edr/) (Endpoint [Detection](/knowledge-base/studynote/09_security/19_ai_advanced_security/961_deepfake_detection/) and Response), [TEE](/knowledge-base/studynote/01_computer_architecture/14_hardware_security_trends/478_tee/) 같은 다른 계층과 결합해야 효과가 커진다.

앞으로는 Microsoft Pluton, DICE (Device [Identifier](/knowledge-base/studynote/05_database/02_modeling_normalization/088_identifier_in_er_model/) Composition 엔진), [공급망](/knowledge-base/studynote/04_software_engineering/08_security_compliance_devsecops/520_supply_chain_attack_and_ci_cd_security/) 증명처럼 장치 신뢰 체계를 더 세밀하게 묶는 흐름이 강해질 것이다. 그래도 TPM의 핵심은 분명하다. **장치가 어떤 상태에서 켜졌는지를 하드웨어가 증명하게 만든다**, 이것이 TPM을 기억하는 가장 좋은 문장이다.

- **📢 섹션 요약 비유**: TPM은 컴퓨터의 출생 기록부와 같다. 기록이 맞아야만 중요한 서랍을 열 수 있고, 기록이 달라지면 먼저 이유를 확인해야 한다.

### 👶 어린이를 위한 3줄 비유 설명

1. TPM은 컴퓨터 안에 있는 작은 기록 상자예요.
2. 컴퓨터가 켜질 때마다 "누가 먼저 들어왔는지"를 차곡차곡 적어 두고, 기록이 맞을 때만 중요한 열쇠를 꺼내 줘요.
3. 그래서 누군가 몰래 부팅 길을 바꾸면, 컴퓨터는 바로 예전과 다르다는 걸 알아차릴 수 있어요.
