## 핵심 인사이트 (3줄 요약)

> 1. **본질**: SLO(Service Level Objective)는 **신뢰성을 "허용 가능한 실패량"이라는 수학적 약속**으로 재정의하며, SLI(Service Level Indicator)는 이를 측정하는 **원시 신호(원자 지표)**, 에러 버짓(Error Budget)은 `(1 - SLO) × 측정 기간`으로 산출되는 **신뢰성 화폐(currency of reliability)**다. 이는 Google SRE Workbook이 정의한 **"100% 신뢰성은 비싸고 비현실적이며 잘못된 목표"** 라는 패러다임에서 출발한다.
> 2. **가치**: 99% vs 99.9% vs 99.99%의 차이는 **월 7.3시간 vs 43.8분 vs 4.38분 다운타임**이며, 마지막 0.09%를 개선하는 비용은 기하급수적으로 증가(추가 인프라 10배~)한다. SLO는 주관적인 "안정성" 논쟁을 제거하고 **데이터 기반 출시(Deployment)/투자/리스크 의사결정**을 가능케 한다.
> 3. **판단 포인트**: 핵심 트레이드오프는 **(a) SLO 목표치의 보수성**(너무 높으면 비용 폭증, 너무 낮으면 사용자 이탈) **(b) 측정 방식의 정확도**(서버측 vs 클라이언트측 synthetic vs RUM) **(c) 에러 버짓 소진 시 정책**(Feature freeze? 사고 사후 분석? 인프라 투자?) **(d) Multi-Window Multi-Burn-Rate Alert 파라미터 튜닝**이다.

## Ⅰ. 개요 및 필요성

### 1.1 패러다임 전환의 배경

전통적인 IT 운영 환경에서는 **"가용성(Availability) 99.999%(Five Nines)"**가 미덕처럼 여겨졌으며, 장애는 **반드시 숨겨야 할 실패**로 인식되었다. 그러나 Google SRE팀이 2016년 『Site Reliability Engineering』을 통해 제시한 핵심 교훈은 **"완벽한 신뢰성은 비싸고, 비현실적이며, 사용자에게는 오히려 해롭다"**는 것이다. 0.001%의 추가 가용성을 확보하기 위한 비용이 그 비즈니스 가치보다 커지기 때문이다. 이러한 인식 전환에서 출발한 것이 **SLO 기반 신뢰성 엔지니어링**이다.

기존의 SLA(Service Level Agreement)는 **공급자와 고객 간의 사후적 계약**으로, 위반 시 크레딧 환불이나 페널티를 동반하는 **외부적·법적 문서**다. 반면 SLO는 **내부 개발팀·운영팀·사업팀이 함께 사용하는 운영 목표**로서, 페널티보다 **"신뢰성이라는 희소 자원을 어디에 쓸 것인가"**에 대한 **선제적 의사결정 도구**다. SLO의 핵심 가치인 **에러 버짓**은 단순한 지표가 아니라 **"이번 분기 얼마나 혁신(배포)을 할 수 있는가"**를 결정하는 **재화(currency)**다.

### 1.2 가용성 비용의 기하급수적 증가

```text
        신뢰성 목표 vs 상대적 인프라 비용
   99.999% ▓▓▓▓▓▓▓▓▓▓▓▓▓▓▓▓▓▓▓▓▓▓▓▓▓▓▓▓▓▓▓▓▓▓▓▓▓▓  <- 100% 대비 약 100x 비용
   99.99%  ▓▓▓▓▓▓▓▓▓▓▓▓▓▓▓▓▓▓▓▓▓▓▓▓▓▓▓▓▓▓▓          <- 99.9% 대비 약 10x 비용
   99.9%   ▓▓▓▓▓▓▓▓▓▓▓▓▓▓▓▓▓▓▓▓                        <- 99% 대비 약 10x 비용
   99%     ▓▓▓▓▓▓▓▓▓▓▓▓▓▓                              <- Baseline
   95%     ▓▓▓▓▓▓▓▓▓▓                                 <- 1/5 비용
   90%     ▓▓▓▓▓▓                                     <- 1/10 비용

   [비용 곡선: Diminishing Returns of Nines - 마지막 9% 개선에 가장 큰 비용]
```

### 1.3 SLO가 해결하는 엔지니어링 문제

| 문제 | SLO 도입 전 | SLO 도입 후 |
| :--- | :--- | :--- |
| 안정성 수준 결정 | "최대한 안정적으로" (주관적) | "p99 latency 300ms 이하" (객관적) |
| 장애 대응 | 모든 장애가 동일 심각도 | Burn rate 기반 차등 대응 |
| 신규 기능 배포 | 운영팀이 무조건 차단 | Error budget 잔여량 기준 자율 결정 |
| 인프라 투자 정당화 | 경영진 설득에 의존 | ROI = (SLO 회복 비용 / 매출 영향)으로 산출 |
| 인시던트 후 행동 | "왜 또 터졌어?" (비난) | "이번 분기 budget 0 -> 1주 freeze" (절차) |

### 1.4 SLO 구성의 수학적 기초

```text
        시간축 기준 SLO 99.9%의 Error Budget 계산

  <----------- 30일 (1개월) ----------->
  |              |                |
  |  100% 가용   |  0.1% 허용실패  |  --- 월간 허용 downtime
  |   43,200분   |    43.8분      |
  |              |                |
  |  ████████████████|██|            |
  |  성공(Success) |실패(Errors)  |
  |              |                |
  +--------------+----------------+

  계산식: Error Budget = (1 - SLO) × 측정 기간
         = (1 - 0.999) × 30일 × 24h × 60분
         = 0.001 × 43,200분
         = 43.2분 (해당 월에 허용된 "실패 시간")

  만약 SLO를 99.95%로 올리면?
         = 0.0005 × 43,200분 = 21.6분 (절반으로 줄어듦)
         -> 거의 2배 정밀한 운영 요구
```

- **📢 섹션 요약 비유**: SLO는 **"은행의 신용 한도(credit limit)"**와 같다. 99.9% SLO는 **월 43.8분짜리 신용카드**를 발급해주는 것이고, 우리는 그 안에서 **자유롭게 지출(배포/리팩토링)**할 수 있다. 한도를 다 쓰면(0.1% 소진) 카드 사용이 정지(freeze)되어 우선 더 안전한 시스템에 **투자(상환)**해야 한다.

### 2.3 Burn Rate와 Multi-Window Alerting 수학

#### 2.3.1 기본 공식

```
SLI(t)         = 1 - (에러 이벤트 수 / 전체 이벤트 수)
Error Budget   = 1 - SLO        (예: 99.9% SLO -> 0.001 budget)
Burn Rate(θ)   = 현재 에러율 / 허용 에러율 = error_rate / (1 - SLO)
                예: error_rate 0.1% / 0.1% = 1.0 (정상 속도 소진)
                    error_rate 1.0% / 0.1% = 10.0 (10배 빨리 소진 중!)
```

#### 2.3.2 Multi-Window Multi-Burn-Rate Alert 조합 (Google SRE Ch.5 권장)

```text
  +--------------------------------------------------------------+
  |       Multi-Window Multi-Burn-Rate Alert Matrix              |
  +------------------+-----------------+----------+--------------+
  | Window(과거)     | Burn Rate 임계값| 소진시간 | 심각도      |
  +------------------+-----------------+----------+--------------+
  |  1 hour /  5 min |       14.4x     |  ~ 2h    | [Page]      |
  |  6 hour / 30 min |        6x       |  ~ 1일   | [Page]      |
  |  3 day  /  6 h   |        1x       |  ~ 1월   | [Ticket]    |
  |  7 day  /  6 h   |        3x       |  ~ 1주   | [Ticket]    |
  +------------------+-----------------+----------+--------------+

  <------ 빠른 탐지(Severe Incidents) ------>|<---- 느린 탐지(Slow Burn) --->

  근거: 1% SLO budget을 1시간 내 소진 -> 2h 안에 budget 고갈 = 즉시 대응
        5% budget을 6h 내 소진 -> 1일 안에 budget 고갈 = 즉시 대응
        2% budget을 3일 내 소진 -> 약 1개월 = 1개월 budget 위협 -> 티켓
```

#### 2.3.3 Burn Rate 임계값 도출 공식

```
Wanted exhaustion time(τ) = τ_hours × 60 분
Burn rate(θ) = (1 - SLO) × 1h / τ_hours
              = 0.001 / τ_h (SLO 99.9% 기준)

예) 1h 안에 budget 다 쓰려면:  θ = 0.001 / 1 = 0.001 (1x)  -> 1% rate
    6h 안에 1% 쓰려면:        θ = 0.001 / 6 = 0.000167      -> 0.1% rate
