## 핵심 인사이트 (3줄 요약)

> 1. **본질**: 성능 감리 벤치마크 기준은 정보시스템의 응답시간(화면/트랜잭션/배치), 처리량(TPS·동시사용자), 가용성(99.9% SLA), 자원 활용률(CPU·Memory·Disk·Network)을 정량 KPI로 정의하고, TPC/SPEC/TTA 표준·유사 시스템 실적·계약 SLA의 3축을 기준으로 **측정 가능·비교 가능·재현 가능**한 기준선(Baseline)을 설정하는 절차다.
> 2. **가치**: 정량적 기준을 사전에 못 박으면 감리 결과의 적부 판단이 "주관적 견해"로 변질된다. 기준을 표준화하면 구축-이행-운영 3단계 전 구간에서 결함 누락 30~50% 감소, 장애 재현율 70% 이상 확보, 수용 협의(인수인계) 분쟁 비용을 대폭 절감할 수 있다.
> 3. **판단 포인트**: 절대 기준(예: "응답시간 3초 이내")만으로는 업무별·피크별·데이터량별 편차를 반영하지 못하므로, **상대 기준(유사 시스템 대비 110% 이내) + 절대 기준(이상치 제거 후 95 percentile) + SLA 기준(계약 문서 우선)**의 3중 계층 구조로 설계해야 한다. 또한 클라우드/오토스케일 환경에서는 동적 부하 모델링과 시나리오 기반 합성 트래픽(Synthetic Transaction) 설계가 핵심 변별점이 된다.

---

## Ⅰ. 개요 및 필요성

성능 감리는 **「정보시스템의 효율적 도입 및 운영에 관한 지침」(대통령령, 행정안전부 소관)**과 **「정보시스템 감리 수행 안내서」**에 따라, 사업자가 구축·이행한 시스템이 사용자의 요구사항과 계약상 성능 조건을 충족하는지를 독립적으로 검증하는 감리 활동이다. 여기서 벤치마크 기준 설정은 감리 전체의 "자(ruler)" 역할을 한다.

예전(2000년대 초반)에는 벤치마크가 **"체감 응답속도"**나 **"현장 담당자 인터뷰"** 같은 주관적 요소에 의존했다. 이 경우, 발주청과 사업자 간에 "성능이 좋다/나쁘다"는 공방이 반복되어 감리 보완 요청, 재감리, 계약금 지급 보류 등의 분쟁이 빈번했다. 2010년대 이후 행정안전부 고시 "성능측정 항목 및 기준"이 정비되고, TTA(한국정보통신기술협회)의 성능 측정 방법 표준(TTAK.KO-10.0800 시리즈)이 제정되면서, **표준화된 합성 부하(Synthetic Load) 기반의 재현 가능한 정량 측정**으로 패러다임이 전환되었다.

특히 공공정보화 사업의 경우 발주청이 감리를 통해 성능 적부를 확인하지 않으면 **준공 검사** 단계에서 성능 부적격 판정을 받아 사업비 회수 및 추가 이행 청구로 이어지므로, 벤치마크 기준은 단순한 품질 체크리스트가 아니라 **법적·재무적 리스크를 통제하는 핵심 통제 장치**다.

```text
+----------------------------------------------------------------------+
|          성능 감리 벤치마크 기준 설정의 위치와 흐름                    |
+----------------------------------------------------------------------+
|                                                                      |
|   [사업 발주]      [성능 기준 협의]    [구축·이행]      [성능 감리]   |
|   요구사항 정의  -+                 +-- 개발·테스트  --+              |
|   (RFP, SLA)     |                 |  부하 테스트      |              |
|                  v                 |  파일럿 검증      |              |
|           +--------------+         |                   |              |
|           |  기준 설정   |<---------+                   |              |
|           |  Benchmark   |                             |              |
|           |  Setting     |                             |              |
|           +------+-------+                             |              |
|                  |                                     v              |
|   +--------------v----------------------------------------------+   |
|   |   3축 기준선 (Baseline Triangulation)                       |   |
|   |  +----------+  +----------+  +----------+                   |   |
|   |  | 절대기준 |  | 상대기준 |  | SLA 기준 |                   |   |
|   |  | Absolute |  | Relative |  | Contract |                   |   |
|   |  | (표준)   |  | (유사)   |  | (계약)   |                   |   |
|   |  +----+-----+  +----+-----+  +----+-----+                   |   |
|   |       |             |             |                          |   |
|   |       +-------------+-------------+                          |   |
|   |                     v                                        |   |
|   |          [성능 지표 측정 및 비교]                              |   |
|   |          Throughput / Latency / Availability                  |   |
|   +--------------------------------------------------------------+   |
|                  |                                                  |
|                  v                                                  |
|   [적합]                  [부적합]                                   |
```

**왜 이게 필요한가?**

- **법적 근거**: 「정보시스템의 효율적 도입 및 운영에 관한 지침」 제49조(감리), 행정안전부 고시 "성능측정 항목 및 기준"
- **기술적 근거**: 동일 HW·SW 자원에서 시스템별 성능 편차가 수십 배까지 발생(예: SQL 튜닝 한 번에 응답시간 50% 감소)
- **재현 가능성**: "이번 주에는 빨랐다"는 식의 일회성 측정을 배제하고, **합성 부하 시나리오**로 언제든 재현
- **이해관계자 합의**: 발주청·사업자·감리원이 **동일한 잣대**로 측정

- **📢 섹션 요약 비유**: 벤치마크 기준은 마치 **경찰 단속기(camera)**와 같다. 기준선(limit)을 미리 정해두지 않으면 "너무 빨랐다느니, 너무 늦었다느니" 하는 헛소리만 오가고, 정작 사고(장애·분쟁)가 나도 책임 소재를 가를 수 없다.

## Ⅱ. 아키텍처 및 핵심 원리

성능 감리 벤치마크 기준은 크게 **(1) 지표 정의 계층**, **(2) 측정·도구 계층**, **(3) 시나리오·부하 모델 계층**, **(4) 비교·판정 계층**의 4-계층으로 구성된다.

```text
+------------------------------------------------------------------------+
|      성능 감리 벤치마크 4-계층 아키텍처 (4-Layer Benchmark Stack)      |
+------------------------------------------------------------------------+
|                                                                        |
|  +----------------------------------------------------------------+   |
|  |  L1. 지표 정의 계층 (Metric Definition Layer)                  |   |
|  |  +-------------+  +-------------+  +--------------+            |   |
|  |  | 응답시간     |  | 처리량      |  | 가용성/안정성 |            |   |
|  |  | Latency     |  | Throughput  |  | Availability  |            |   |
|  |  | - 화면응답   |  | - TPS       |  | - Uptime      |            |   |
|  |  | - TX응답     |  | - 동시사용자|  | - MTBF/MTTR   |            |   |
|  |  | - 배치응답   |  | - 데이터처리|  | - Error Rate  |            |   |
|  |  +------+------+  +------+------+  +------+-------+            |   |
|  +---------+----------------+----------------+--------------------+   |
|            |                |                |                        |
|  +---------v----------------v----------------v--------------------+   |
|  |  L2. 측정·도구 계층 (Measurement & Tooling Layer)              |   |
|  |  +--------------+  +--------------+  +----------------------+  |   |
|  |  | 부하 생성기   |  | APM 에이전트 |  | 리소스 모니터        |  |   |
|  |  | JMeter       |  | Dynatrace    |  | Prometheus+Grafana   |  |   |
|  |  | Gatling       |  | New Relic    |  | nmon, iostat, vmstat |  |   |
|  |  | k6, Locust   |  | Pinpoint     |  | Telegraf, collectd   |  |   |
|  |  +------+-------+  +------+-------+  +----------+-----------+  |   |
|  +---------+----------------+----------------------+--------------+   |
|            |                |                      |                  |
|  +---------v----------------v----------------------v--------------+   |
|  |  L3. 시나리오·부하 모델 계층 (Workload Modeling Layer)          |   |
|  |  +----------------------------------------------------------+  |   |
|  |  |  업무 시나리오 (Use Case)                                |  |   |
|  |  |  - 로그인 (5%)  - 조회 (60%)  - 등록/수정 (20%)  - 보고(15%) |   |
|  |  +----------------------------------------------------------+  |   |
|  |  +----------------------------------------------------------+  |   |
|  |  |  부하 프로파일 (Load Profile)                             |  |   |
|  |  |  Ramp-up (점진 증가) -> Peak (1.5×예상 동시자)             |  |   |
|  |  |  -> Soak (8h 지속) -> Spike (급증) -> Ramp-down             |  |   |
|  |  +----------------------------------------------------------+  |   |
|  |  +----------------------------------------------------------+  |   |
|  |  |  데이터 셋 (Test Data)                                    |  |   |
|  |  |  - 운영 데이터 10% 마스킹 / 합성 데이터 1:1 매핑           |  |   |
|  |  |  - 마스터 10만 / 트랜잭션 1,000만 레코드                  |  |   |
|  |  +----------------------------------------------------------+  |   |
|  +----------------------------+-----------------------------------+   |
|                               |                                       |
|  +----------------------------v-----------------------------------+   |
|  |  L4. 비교·판정 계층 (Comparison & Judgment Layer)              |   |
|  |  +-------------+  +-------------+  +-------------+             |   |
|  |  | 절대 기준   |  | 상대 기준   |  | SLA 기준    |             |   |
|  |  | 표준/법령   |  | 유사 시스템 |  | 계약 문서   |             |   |
|  |  | 예: 3초이내 |  | 예: ±10%   |  | 예: 99.9%   |             |   |
|  |  +-------------+  +-------------+  +-------------+             |   |
|  |  -> 종합 판정: 적합 / 조건부적합 / 부적합                        |   |
|  +----------------------------------------------------------------+   |
+------------------------------------------------------------------------+
```
