## 핵심 인사이트 (3줄 요약)

> 1. **본질**: ISO/IEC 20000은 IT 서비스 관리 시스템(SMS)에 대한 국제 표준으로, ISO/IEC 20000-1:2018은 인증 가능한 요구사항(Requirements), -2:2019는 적용 지침(Guidance)을 제공하며, 10개 서비스 관리 프로세스군을 중심으로 서비스 라이프사이클 전 과정을 통제 가능한 형태로 정의한다.
> 2. **가치**: 인증 취득을 통해 고객·규제기관에 IT 운영 성숙도를 객관적으로 입증할 수 있으며, ITIL과 달리 인증·감사 체계가 존재하므로 BS 15000의 후속 표준으로서 IT 거버넌스 RFP/SLA 계약의 사실상 디팩토 기준이 된다.
> 3. **판단 포인트**: ISO 20000과 ITIL 4의 적용 범위(프로세스 프레임워크 vs 실무 지침서), ISO 27001(보안)·ISO 9001(품질)·CMMI(성숙도)·COBIT(거버넌스)과의 통합(ISMS·QMS·SMS Integrated Management System) 구축 여부, 그리고 조직의 IT 성숙도에 따라 Part 1(전사 SMS) vs 일부 프로세스(Part 1 Annex A/B scope) 적용 범위 결정이 핵심 판단 포인트이다.

## Ⅰ. 개요 및 필요성

### 1.1 표준의 탄생 배경

ISO/IEC 20000은 2002년 영국표준협회(BSI)의 BS 15000을 모태로, 2005년 12월 ISO/IEC JTC 1/SC 7에서 ISO/IEC 20000-1(요구사항)과 -2(적용지침)로 국제 표준화되었다. 2011년 1차 개정(Part 1~5), 2018년 9월 2차 개정(Part 1, 2)을 거쳐 현재는 **ISO High-Level Structure(HLS)**에 맞춰 10개 절(Clause)로 재구성되었으며, 2019년에는 Part 2 개정판이, 2024년 Part 1 개정(ISO/IEC 20000-1:2024)까지 진행되었다.

배경에는 다음과 같은 IT 산업 패러다임 변화가 있다.

- **1990년대 말~2000년대 초**: 메인프레임에서 클라이언트/서버, 그리고 ASP(Application Service Provider)·SaaS 모델로 전환되며, IT 부서가 "비용 센터"에서 "서비스 제공자(Internal/External Service Provider)"로 역할이 변화
- **BS 15000 -> ISO 20000**: 영국 정부 조달청(GCHQ/CCTA)이 보유하던 ITIL(IT Infrastructure Library)이 운영 가이드로 방대하게 활용되었으나, 인증 가능한 객관적 표준 부재로 품질 보증에 한계 -> BSI가 ITIL v2를 기반으로 검증 가능한 표준 제정 착수
- **2011 개정**: PDCA(Plan-Do-Check-Act) 기반 구조 채택
- **2018 개정**: ISO 9001·27001과 동일한 10개 HLS 조항 구조로 변경, '서비스 요구사항(Clause 6.2) -> 서비스 카탈로그(Clause 8.5) -> 인시던트/서비스 요청(Clause 8.6) -> 문제(Clause 8.7) -> 변경(Clause 8.5.6) -> 릴리스(Clause 8.5.7)' 등 프로세스 절을 8장 운영(Operation)에 통합

### 1.2 기존 패러다임 vs ISO 20000 도입 후

| 구분 | 표준 도입 이전 (Ad-hoc ITSM) | ISO 20000 도입 이후 (Systematic SMS) |
| :--- | :--- | :--- |
| 서비스 정의 | 부서별/시스템별 암묵적 정의, KB·Confluence 산재 | 서비스 카탈로그(Clause 8.5.1)에 표준화된 서비스 항목·SLA·가격 명세 |
| 변경 관리 | 시스템 관리자 임의 판단, 야간 작업 통보 부재 | RFC(Request for Change) -> CAB(Change Advisory Board) 승인 -> 변경 일정·롤백 계획 의무화 (Clause 8.5.6) |
| 인시던트 대응 | 전화·메신저 기반 핫픽스, 우선순위 부재 | 인시던트 분류(P1~P4), SLA 응답/복구 시간 정의, Major Incident Procedure 별도 운영 (Clause 8.6) |
| 공급자 관리 | 단가표 기반 일회성 계약, 성능 측정 없음 | 공급자 평가·재검토(Clause 8.4) 및 외부 공급자 SLA 연동 |
| 지속적 개선 | 장애 후 일회성 사후 분석(RCA) | 서비스 수준 보고서(SLR), 내부감사(Clause 9.2), 경영검토(Clause 9.3) 통한 PDCA 순환 |
| 대외 신뢰 | 자체 발표·레퍼런스 | 제3자 인증서(UKAS 인정 KAB·ANAB 등) 통한 객관적 증명 |

### 1.3 왜 필요한가 (기술사적 관점)

- **규제 요구 충족**: 공공·금융·통신 부문(예: 한국 정보통신공사업법, 전자금융거래법, 클라우드컴퓨팅법) 입찰 자격으로 인증 요구 빈번
- **계약 조건 충족**: 글로벌 클라이언트(특히 EU, 일본)의 SOC 2·ISO 27001·ISO 20000 통합 요구 — 단일 표준 취득으로 다수 RFP 응답력 확보
- **내부 거버넌스 강화**: IT 부서가 1) 서비스 카탈로그, 2) SLA/OLA/UC(Service Level Agreement/Operational Level Agreement/Underpinning Contract), 3) CMDB(Configuration Management Database) — AWS Config·ServiceNow CMDB·BMC Atrium 등 — 를 체계적으로 운영하도록 강제
- **위험 관리**: ISO 31000 리스크 관리 원칙과 연계하여 서비스 연속성(Clause 8.5.8)·가용성·容量 관리(Clause 8.5.9)를 통합 관리

```text
       [ISO 20000 인증 도입 전후 변화 — 지식·프로세스·조직 성숙도 측면]

   도입 전 (Pre-ISO 20000)               도입 후 (Post-ISO 20000)
   ---------------------                ---------------------
   +------------------+                +--------------------------+
   | IT 운영팀         |                | IT 서비스 관리 시스템(SMS) |
   | - 경험·감 위주    |                | - 정책/절차 문서화         |
   | - 부서별 은어     |   ---->   | - 표준화된 용어·절차       |

   +------------------+                +--------------------------+
```

- **📢 섹션 요약 비유**: ISO 20000은 마치 식당에서 **"위생등급제 + HACCP 인증 마크"** 와 같다. 주방장이 아무리 잘해도 외부인에게 그 역량을 증명하려면 객관적인 기준과 인증서가 필요하고, ISO 20000이 바로 IT 서비스 주방의 "위생 마크" 역할을 한다.

## Ⅱ. 아키텍처 및 핵심 원리

### 2.1 ISO 20000 Family 구성 (2024 기준)

| Part | 명칭 | 주요 내용 | 비고 |
| :--- | :--- | :--- | :--- |
| Part 1:2018 (2024) | 요구사항(Requirements) | SMS 수립·운영·유지·개선 의무 요구사항, 인증 가능 | **핵심 인증 기준** |
| Part 2:2019 | 적용 지침(Guidance) | Part 1 각 요구사항별 권고 사례, 예시 프로세스·문서 | 비인증, 자가진단 활용 |
| Part 3:2009 (폐지) | 용어·정의(Scope & Applicability) | 2018 개정으로 본문 통합 | 2018 개정 시 삭제 |
| Part 4:2010 (폐지) | 프로세스 참조 모델(Process Reference Model) | 2018 개정으로 본문 통합 | 2018 개정 시 삭제 |
| Part 5:2010 (폐지) | 구현 지침 | Part 2에 통합 | 2018 개정 시 삭제 |
| Part 6:2017 | ISO/IEC 20000-1 Part 1 적용 범위·적용성 지침 | 인증 시 제외·포함 범위 결정 절차 | 신규 |
| Part 7:2018 | ISO/IEC 20000의 거버넌스 적용 통합 지침 | 거버넌스 시스템 연계 | 신규 |
| Part 8:2018 | ISO/IEC 20000-1 Part 1을 위한 적합성 평가 | 자체 적합성 평가 방법 | 신규 |
| Part 9:2018 | ISO/IEC 20000-5 적용 지침 | 서비스 제공자 거버넌스 평가 | 일부 폐지 후 Part 7로 |
| Part 10:2018 | ISO/IEC 20000-1 Part 1 적합성 평가 | 인증기관·심사원 지침 | Part 6·8과 연계 |
| Part 11:2021 | ISO/IEC 20000-1 Part 1의 클라우드 서비스 확장 | IaaS/PaaS/SaaS 서비스 별도 지침 | 신규 |
| Part 12:2023 | ISO/IEC 20000-1의 AI 서비스 확장 | AI/ML 워크로드 별도 지침 | 신규 |

> ※ 2018 개정의 핵심 변화: ISO HLS(High-Level Structure) 채택, PDCA 모델 내재화, Annex A(서비스 제공자 의무 8개), Annex B(추가 요구사항·기대사항) 분리, 문서 요구사항을 7.5 "문서화된 정보"로 통합.

```text
        |     8.4 공급자 관리                                    |
        |     8.5 서비스 구축·전환·제어(CMDB/릴리즈/변경)          |
        |     8.6 인시던트·서비스 요청                            |
        |     8.7 문제 관리                                      |
        |     8.8 인시던트·문제 종결                              |

        +------------------------------------------------------+
        |  9. 성과 평가(Performance Evaluation)                   |

        |     9.3 경영검토                                       |
        |     --->  [Check: 정량·정성 평가]                        |
        +------------------------------------------------------+
        |  10. 개선(Improvement)                                  |
        |     10.1 일반, 10.2 부적합·시정 조치, 10.3 지속 개선     |
        |     --->  [Act: 시정·예방·혁신]                           |
        +------------------------------------------------------+
```

### 2.3 핵심 운영 프로세스 (Clause 8) 상세

| 구성 요소 | 역할 | 핵심 기술 및 동작 방식 |
| :--- | :--- | :--- |
| 8.2.2 서비스 포트폴리오 | 서비스 투자 포트폴리오 정의·승인·갱신 | BCG/GE Matrix 방식의 서비스 분류(Star·Cash Cow·Question Mark·Dog), 신규 서비스 Go-To-Market 전 단계 거버넌스 |
| 8.3 서비스 요구사항 | 서비스 수준 요구사항 수집·검토·정의 | 비즈니스 요구사항 -> 기술·운영 요구사항 변환, SLA(SLO/SLI)·OLA·UC 3계층 협상 프레임 |
| 8.4 공급자 관리 | 외부 공급자 평가·선정·모니터링·재평가 | 가중치 평가표(품질 30%·비용 25%·납기 20%·보안 15%·ESG 10%), 분기별 성과 미팅, Exit Plan |
| 8.5.1 서비스 카탈로그 | 고객·사용자가 보는 서비스 메뉴 | ServiceNow CMDB·BMC Helix·Jira Service Management의 Service Catalog 모듈, SSO 연동, 가격·요청 워크플로우 포함 |
| 8.5.2 구성 관리(CMDB) | CI(Configuration Item) 식별·제어·상태 추적 | 자동 발견(Discovery): AWS Config, Azure Resource Graph, Qualys, Tanium, SCCM -> CMDB 동기화, Relationship(논리/물리/서비스) 모델링 |
| 8.5.6 변경 관리 | 표준·긴급·비상 변경 절차 | **ECAB(Emergency CAB)**: P1/Major 변경 1시간 이내 소집, **CAB(Change Advisory Board)**: 주 1회 정례, **Pre-approval**: 저위험 변경 자동 승인 룰 |
