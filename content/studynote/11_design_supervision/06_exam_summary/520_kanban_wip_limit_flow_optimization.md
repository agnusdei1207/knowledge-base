## 핵심 인사이트 (3줄 요약)

> 1. **본질**: 칸반의 WIP(Work In Progress) 제한은 리틀의 법칙(L = λW)에 기반하여 시스템 내 동시 진행 작업 수를 임계치 이하로 묶어두어, 변동성(Variability)과 대기 시간(WIP Queue)을 기하급수적으로 억제하는 **풀(Pull) 기반 흐름 제어 메커니즘**이다.
> 2. **가치**: WIP를 50% 축소할 경우 평균 리드타임은 약 75% 감소(DevOps Research Report, DORA)되며, 컨텍스트 스위칭 비용과 멀티태스킹 오버헤드를 제거하여 자원 활용률(순환 효율 20%->80%+ 향상)과 예측 가능성(P95 리드타임 안정화)을 동시에 달성한다.
> 3. **판단 포인트**: WIP 한도 설정 시 단순히 "팀원 수 × 1.5" 같은 경험칙이 아닌, **클래스 오브 서비스(CoS) 가중치, 병목 단계 식별(ToC), 변동성 계수(CV) 분석, 그리고 시스템 유형(I-타입/M-타입)**에 따라 동적으로 산정해야 하며, 지나치게 낮은 한도는 스타베이션(Starvation)을, 높은 한도는 멀티태스킹 병목(DTW: Dark Waiting Time 증가)을 유발한다.

## Ⅰ. 개요 및 필요성

소프트웨어 개발 조직은 본질적으로 **지식 작업(Knowledge Work)**이며, 전통적인 제조업의 푸시(Push) 방식 계획(전월 말 다음달 스프린트 100% 백로그 잠금)은 **린(Lean) 사고**에 부합하지 않는다. 데보캣스(David J. Anderson)가 2007년 마이크로소프트의 XIT(R) 팀에서 도입한 **칸반(Kanban)**은 JIT(Just-In-Time) 생산의 핵심 개념을 지식 작업에 적용한 **에반스-리 시스템(Conwip/D-Brane 변형)**으로, 토요타 생산방식(TPS)의 *Heijunka(평준화)*, *Mura(불균일 제거)*, *Muda(낭비 제거)* 3무를 소프트웨어 흐름에 그대로 이식한다.

문제의 본질은 **리틀의 법칙(L = λW, Lead Time = WIP / Throughput)**에서 명확해진다. 처리량(Throughput)을 무리하게 끌어올리기 위해 WIP를 무제한 허용하면, WIP의 n차 누적으로 **리드타임이 폭증**한다(체감 리드타임 ≈ WIP² / (2 × Throughput) — 변동성 포함 모델). 이로 인해 ① 컨텍스트 스위칭 비용(공식: 23분 집중 후 10분 회복, UC Irvine 연구), ② 결함 전파 효과(Defect Amplification, IBM Systems Sciences Institute: 후반부 결함 1건 수정 비용 = 초기 100배), ③ 예측 불가능성(P95/P99 SLA 미달), ④ 번아웃(과부하)이라는 4중 악순환이 발생한다.

```text
   [기존: WIP 무제한 푸시 시스템]                [목표: WIP 제한 풀 시스템]
   +--------------+                              +--------------+
   | Product Owner|                              | Product Owner|
   | (수요 폭주)  |                              | (우선순위 큐)|
   +------+-------+                              +------+--------+
          | 무제한 푸시                                  | 풀 시그널
          v                                              v
   +------------------------------+             +------------------+
   |  [To Do]   ████████████ 무한 |             | [To Do]  [FIFO]  |
   +------------------------------+             +------------------+
   |  [Doing1]  ███  ██  ████  █ | <- 컨텍스트  | [Doing]  [WIP=3] | <- 집중
   +------------------------------+   스위칭    +------------------+
   |  [Doing2]  ██  █████  ██  ██|   비용^^   | [Test]   [WIP=2] |
   +------------------------------+             +------------------+
   |  [Done]    ▓▓▓▓▓▓▓▓▓▓▓▓▓▓▓▓ |             | [Done]   [SSOT]  |
   +------------------------------+             +------------------+
   평균 리드타임: 14일 / 변동성 ^^                  평균 리드타임: 3.5일 / 변동성 v
   자원 활용률: 100%(겉보기) / 20%(실제)            자원 활용률: 80%(실질 순환)
```

- **📢 섹션 요약 비유**: 모든 차선이 꽉 찬 고속도로가 오히려 평균 통행속도를 떨어뜨리는 "브라ess 효과(역설)"처럼, 동시에 많은 일을 시키면 전체는 더 느려진다.

## Ⅱ. 아키텍처 및 핵심 원리

칸반 시스템의 **물리적/논리적 아키텍처**는 5가지 핵심 메커니즘 — ① 시각화 보드(Virtual Board), ② WIP 제한(Constraint), ③ 풀 시그널(Pull Signal), ④ 흐름 정책(Flow Policy), ⑤ 명시적 클래스 오브 서비스(CoS) — 으로 구성된다. 기술사 관점에서 이는 **운영체제(OS)의 세마포어/뮤텍스 기반 동시성 제어 모델**과 등가이다.

```text
                    +-------------------------------------+
                    |   칸반 흐름 제어 아키텍처 (Kanban Flow)|
                    +-------------------------------------+

  +--------+    Pull     +-------------+   Token     +-------------+
  | Backlog| -----------> |  Ready Queue| -----------> |  In-Progress|
  |  (입력)|   (우선순위  |  (WIP_R)    |   (WIP 한도 |  (WIP_IP)   |
  |        |    기반)    |  Limit=N_R  |    체크)    |  Limit=N_IP |
  +--------+             +-------------+             +--------+---+
                                                              |
                                                  Done 시그널 v
                                                     +----------------+
                                                     |   Validation  |
                                                     |   (WIP_V)      |
                                                     +--------+-------+
                                                              v
                                                     +----------------+
                                                     |      Done      |
                                                     |   (배포/출하)   |
                                                     +----------------+

  [병렬 모니터링 채널]
   +--------------+  +--------------+  +--------------+
   | CFD 차트     |  | 버닝 차트    |  | 히스토그램   |
   | (누적흐름도)  |  | (리드타임추세)|  | (사이클타임) |
   +--------------+  +--------------+  +--------------+
```

| 구성 요소 | 역할 | 핵심 기술 및 동작 방식 |
| :--- | :--- | :--- |
| **시각화 보드 (Kanban Board)** | 작업 흐름의 SSOT(Single Source of Truth) 제공 | JIRA/Jira Align, Leankit, Azure DevOps Boards, GitHub Projects, Trello + Power Automate. 컬럼별 **입퇴장 SLA(Service Level Expectation)** 명시 (예: "In-Progress 3일 내 진행") |
| **WIP 제한 (WIP Limit)** | 동시 진행 작업 수의 상한 결정 | 컬럼 단위 또는 클래스 오브 서비스별 차등 적용. `WIP = ceil(리드타임 목표 × 처리량) × 안전계수(1.2~1.5)` 공식 또는 `WIP = 인원수 × c(Kanban 계수, 통상 1.0~1.5)` 휴리스틱 |
| **풀 시그널 (Pull Signal)** | 후방 단계가 여유 슬롯 발생 시 전방에 작업 인출 요청 | FIFO, LIFO, SLOB(Shortest Lead-time On Board) 정책. 비동기 메시지 큐(Kafka/RabbitMQ) 패턴으로 구현 시 **이벤트 기반 트리거** 활용 |
| **클래스 오브 서비스 (CoS)** | 작업 우선순위 및 정책 차별화 | Expedite(긴급, WIP=1), Fixed Delivery Date(계약 마감), Standard(일반), Intangible(내부 부채). WIP 비율 가중치(예: Std 70%, FDD 25%, Exp 5%) |
| **흐름 메트릭 (Flow Metrics)** | 시스템 동작의 관측 가능성 확보 | **리드타임(Lead Time)**, **사이클 타임(Cycle Time)**, **처리량(Throughput)**, **WIP**, **블로커 비율(%)** 5대 핵심 지표 + CFD/Cycle Time Histogram/Scatter Plot |

핵심 수학적 모델은 **리틀의 법칙(Little's Law: L = λW)**과 **컨웨이-맥스웰-마르코프 모델(Kingman의 대기시간 근사: Wq ≈ (CVa² + CVp²)/2 × ρ/(1-ρ) × 평균서비스시간)**이다. 여기서 CVa는 도착 변동 계수, CVp는 서비스 변동 계수, ρ는 이용률(ρ = λ/μ)이다. ρ가 0.8을 넘어가면 평균 대기시간이 **기하급수적으로 폭증**하므로, WIP를 제한하여 ρ를 통제하는 것이 곧 흐름 최적화의 본질이다. 추가로 **검정 시간(Black Time) = 활동 시간(Activity Time) + 대기 시간(Waiting Time) + 컨텍스트 시간(Context Time) + 전환 시간(Transition Time)** 4-T 모델을 적용한다.

- **📢 섹션 요약 비유**: 레스토랑 주방의 1인 1요리 원칙(개인 WIP=1)과 같다. 셰프 한 명에게 5개 주문을 동시에 시키면 모든 손님의 음식이 늦어지지만, 한 번에 1~2개씩만 받으면 **흐름 속도(Flow Velocity)**가 오히려 빨라진다.

## Ⅲ. 비교 및 연결

| 구분 | 스크럼(Scrum) | 칸반(Kanban) | 린 소프트웨어 개발(LSD) | XP(Extreme Programming) |
| :--- | :--- | :--- | :--- | :--- |
| **반복 주기** | 고정 스프린트(1~4주) | 연속 흐름(Continuous Flow) | 지속적 개선(PDCA) | 1~2주 짧은 반복 |
| **계획 주체** | 팀 자체 (Sprint Planning) | 수요 측 (Prioritization만) | 가치 흐름 분석(VSM) | 사용자 스토리 단위 |
| **WIP 제어** | 스프린트 백로그 잠금(간접) | 명시적 컬럼별 한도(직접) | 가치 흐름별 최적화 | 페어 프로그래밍/이야기 카드 |
| **역할** | PO/SM/Developer 고정 | 기존 역할 유지 + 서비스 인도 책임자(SDE) | 없음(전원 참여) | 코치/트래커 |
| **변경 수용** | 스프린트 내 변경 불가 (바위) | 언제든 변경 가능 (유동성) | Pull 기반 무제한 | 우선순위 즉시 반영 |
| **핵심 지표** | 벨로시티, 번 다운 차트 | 리드타임, CFD, 히스토그램 | Muda/Mura/Muri 카운트 | 코드 커버리지, 페어 시간 |
| **적합 조직** | 그린필드, 단일팀 | 레거시 유지보수, 운영팀 | 전체 가치 흐름 | R&D, 신기술 도입팀 |

칸반은 **데브옵스 파이프라인(CI/CD)과 깊은 결합**을 가진다. GitHub Actions/Argo CD 이벤트가 **풀 시그널**로 작용하고, Feature Flag(LaunchDarkly/Unleash)가 WIP 단위의 점진적 출하(Progressive Delivery)를 가능케 한다. 또한 SRE의 **SLO 기반 에러 예산(Error Budget) 정책**은 칸반의 클래스 오브 서비스 중 *Fixed Delivery Date*와 직접 매핑된다. 그리고 **ToC(Theory of Constraints, 골드라트의 5단계 집중 프로세스)** — 식별(Identify) -> 활용(Exploit) -> 단계적 통제(Subordinate) -> 끌어올림(Elevate) -> 반복 — 은 칸반의 병목 컬럼(WIP 초과 지속 컬럼) 해소에 직접 활용된다.

- **📢 섹션 요약 비유**: 스크럼은 "정해진 시간에 정해진 코스를 뛰는 마라톤"이고, 칸반은 "엘리베이터에 사람이 너무 많으면 자동 정지하는 최대 탑승 인원 제한 장치"와 같다.

## Ⅳ. 실무 적용 및 기술사 판단

### 기술사형 판단 체크리스트

1. **리틀의 법칙 검증**: 시스템의 *현재* WIP(예: 18), 처리량(예: 6건/주), 평균 리드타임(예: 4주)이 L=λW를 만족하는지 산술 검증. 불일치 시 측정 오류 또는 숨은 WIP(브랜치/PR/QA 대기) 존재.
2. **병목 단계 식별**: CFD(Cumulative Flow Diagram)에서 가장 가파른 수직 라인 또는 사이클 타임 히스토그램의 **장 꼬리(Long Tail)** 발견 시 ToC 5단계 적용. 처리 시간이 80/20을 벗어나는지(파레토) 확인.
3. **WIP 한도의 정당화**: 단순 경험칙이 아닌 *가설(Hypothesis)* 로 설정. "한도 5에서 평균 사이클 타임을 5일 -> 3일로 단축" 같은 **SMART 목표 + 실험 설계(A/B 또는 시간 분할)** 필요.
4. **클래스 오브 서비스(CoS) 비율**: Expedite는 전체 WIP의 5~10% 이내로 엄격 제한(쿨다운 정책: 동일 긴급 작업 후 24시간 쿨다운). FDD는 계약 SLA에 맞춰 25~30%. 표준은 잔여 WIP.
5. **예측 가능성 검증**: **사이클 타임 히스토그램 + 누적 분포 함수(CDF)** 에서 85th percentile이 SLA 이내인지 확인. 히스토그램이 *로그 정규 분포(Log-Normal)* 를 따르므로 평균이 아닌 백분위(Percentile)로 판단.

### 피해야 할 안티패턴

- **유령 작업(Ghost Work)**: 보드에는 없지만 개인 머릿속/이메일/로컬 브랜치에 남아있는 작업. WIP는 줄었으나 **숨은 대기열(Hidden Queue)** 형성. -> **Git Worktree/Feature Branch 정책 강제 + 일일 Standup**으로 가시화.
- **WIP 한도 = 팀원 수**: 인원 수와 무관하게 *시스템 흐름 능력*에 맞춰야 함. 5명 팀이라 WIP=5가 아니라, 처리량과 리드타임 목표에서 역산. **"한 사람이 2개 작업"보다 "5명이 3개 작업"이 더 빠름**이 다수 연구에서 입증(MIT, T. DeMarco).
- **병목을 강화(WIP+1)하는 함정**: 병목 단계의 WIP를 더 늘려 해결하려는 시도. -> **리틀의 법칙상 불가**, 반드시 *활용(Exploit)* -> *단계적 통제(Subordinate)* -> *끌어올림(Elevate)* 순서로.
- **칸반 = 스크럼 대체** 오해: 칸반은 **스크럼과 병행 가능(Scrumban)**하며, 단독으로 도입 시 거버넌스/백로그 정제 회의 부재로 운영 악화. **반드시 서비스 인도 책임자(SDE) 역할**과 주기적 리트리뷰트(Replenishment Meeting) 필요.

- **📢 섹션 요약 비유**: 다이어트(WIP 축소)를 시도하면서도 냉장고(WIP 풀)에 매일 보충(푸시)하는 것은 의미가 없다. **"들어오는 양(인입량) ≤ 나가는 양(처리량)"** 의 평형이 핵심이다.
