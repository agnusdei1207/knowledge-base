## 핵심 인사이트 (3줄 요약)

> 1. **본질**: WBS (Work Breakdown Structure, 작업 분해 구조)는 프로젝트 전체 범위를 계층적으로 분해하여 관리 가능한 작업 패키지(Work Package) 단위로 정의하는 범위 관리의 핵심 도구로, 모든 프로젝트 계획(일정·비용·자원)의 출발점이다.
> 2. **가치**: WBS의 '100% 규칙'에 따라 프로젝트 전체 범위를 빠짐없이 포함함으로써, 범위 누락(Scope Creep)과 원가 초과의 근본 원인을 방지한다.
> 3. **판단 포인트**: WBS는 무엇(What)을 만들지 정의하고, 일정 도구(CPM, PERT, 간트 차트)는 언제(When)/어떤 순서(Order)로 만들지를 정의한다. WBS 없이는 일정·원가 계획이 원천적으로 불가능하다.

## Ⅰ. 개요 및 필요성

대형 소프트웨어 프로젝트나 시스템 통합(SI) 프로젝트에서 가장 많이 실패하는 원인 중 하나가 범위 관리 실패다. 처음에 명확히 정의하지 않은 작업이 나중에 추가되거나, 정의했다고 생각했는데 빠진 작업이 발견되는 현상(Scope Creep)이 반복된다. WBS는 이 문제를 근본에서 해결한다.

WBS의 역사는 1960년대 미국 국방부(DoD)의 방위산업 프로젝트 관리로 거슬러 올라간다. MIL-STD-881에서 처음 공식화되었고, 이후 PMBOK (Project Management Body of Knowledge)의 범위 관리 지식 영역의 핵심 산출물로 표준화되었다. 소프트웨어 분야에서는 애자일의 Product Backlog가 WBS 계층 개념을 계승한 형태다.

WBS를 작성함으로써 얻는 핵심 이점은 다음과 같다. 첫째, 범위의 가시화 — 프로젝트가 무엇을 만들어야 하는지 모든 이해관계자가 동일하게 이해할 수 있다. 둘째, 원가·일정 추정의 기초 — 작업 패키지 단위로 기간과 비용을 추정할 수 있다. 셋째, 책임 배정의 기준 — 각 작업 패키지에 담당 팀이나 개인을 배정할 수 있다. 넷째, 진도 측정의 기준 — 작업 패키지 완료 여부로 프로젝트 진행률을 객관적으로 측정할 수 있다.

- **📢 섹션 요약 비유**: 대형 건물을 짓기 전에 도면을 그리고 모든 부품 목록(자재 명세서)을 작성하는 것과 같다. 도면 없이 시작하면 반드시 빠진 자재가 나오고, 공사가 늦어지며, 비용이 초과된다.

### WBS 구성 요소 상세

| 구성 요소 | 정의 | 기준 |
|:---|:---|:---|
| Level 0 | 전체 프로젝트 (단일 요소) | 프로젝트 목표 |
| Level 1 | 주요 단계 또는 인도물 그룹 | 3~8개 권장 |
| Level 2~N | 단계적 세분화 | 추정 가능한 수준까지 |
| Work Package (WP) | 최하위 분해 단위 | 80시간 원칙 참고 |
| WBS 사전 | WP별 상세 기술서 | ID, 담당자, 기간, 원가, 인도물, 품질 기준 |

### 80시간 규칙 (80-Hour Rule)

작업 패키지의 크기에 대한 실용적 가이드라인:
- **최대 80시간(2주)**: 이 이상이면 더 분해한다. 너무 크면 진도 파악이 어렵다.
- **최소 8시간(1일)**: 이 미만이면 관리 오버헤드가 너무 크다.

- **📢 섹션 요약 비유**: 이삿짐 목록을 작성할 때 "나머지"로 뭉뚱그리면 반드시 빠진 물건이 생긴다. WBS의 100% 규칙은 모든 이삿짐이 목록에 있어야 한다는 원칙이다.

### WBS vs 유사 개념 비교

| 비교 항목 | WBS | Product Backlog (애자일) | OBS |
|:---|:---|:---|:---|
| 중심 개념 | 산출물 중심 분해 | 기능(User Story) 중심 | 조직 단위 분해 |
| 계층 구조 | 엄격한 트리 | 우선순위 목록 | 조직도 |
| 변경 관리 | 변경 요청(CR) 필수 | 백로그 정제(Grooming) | 조직 변경 시 |
| 적합한 방법론 | 폭포수, 하이브리드 | 애자일(스크럼) | 모든 방법론 |
| 주요 도구 | MS Project, Jira (Epic) | Jira, Trello | OrgChart 도구 |

### 범위 기준선 (Scope Baseline)

PMBOK에서 범위 기준선은 3가지 구성 요소의 결합이다:
- **범위 기술서 (Scope Statement)**: 프로젝트가 만들 것과 만들지 않을 것
- **WBS**: 범위의 계층적 분해
- **WBS 사전**: 각 WP의 상세 정의

이 세 가지가 함께 있어야 범위 관리의 기준이 된다.

- **📢 섹션 요약 비유**: WBS는 레고 부품 목록, 간트 차트는 조립 순서, RACI는 누가 어떤 부품을 담당하는지다. 세 가지가 함께 있어야 프로젝트가 완성된다.

## Ⅳ. 실무 적용 및 기술사 판단

### 설계 판단 체크리스트

1. **모든 인도물(Deliverable)이 WBS에 포함되었는가?**: 문서, 소프트웨어, 하드웨어, 서비스 등 모든 산출물이 WBS에 있어야 한다.
2. **관리 업무(Management Activities)가 포함되었는가?**: 주간 회의, 보고서, 품질 검토, 교육 등 관리 활동도 WP로 정의해야 한다. 보통 프로젝트 공수의 15~25%를 차지한다.
3. **각 WP의 크기가 추정 가능한가?**: 80시간(2주) 이하로 분해되어 담당자, 기간, 원가를 추정할 수 있어야 한다.
4. **WBS 사전이 작성되었는가?**: WP별로 담당자, 인도물, 완료 기준(Done의 정의), 품질 기준이 명시되어야 한다.
5. **이해관계자와 WBS를 공유하고 확인을 받았는가?**: WBS는 범위의 기준이므로, 주요 이해관계자의 검토와 승인이 필요하다.

### 공공 SI 프로젝트 WBS 예시

```text
공공 SI 프로젝트 WBS (행정업무 전산화):

1. 프로젝트 관리
   1.1 착수·계획 수립
   1.2 주간/월간 보고
   1.3 품질 관리 (QA)
   1.4 위험 관리

2. 분석
   2.1 현행 업무 분석
   2.2 요구사항 정의 (RFP 기반)
   2.3 사용자 요구사항 검증

3. 설계
   3.1 아키텍처 설계
   3.2 데이터베이스 설계 (ERD)
   3.3 화면 설계 (UI/UX)
   3.4 인터페이스 설계

4. 구현
   4.1 공통 기반 개발 (인증, 권한)
   4.2 핵심 업무 모듈 개발
   4.3 연계 시스템 개발
   4.4 배치 프로그램 개발

5. 시험
   5.1 단위 시험 (Unit Test)
   5.2 통합 시험 (Integration Test)
   5.3 성능 시험 (Performance Test)
   5.4 사용자 인수 시험 (UAT)

6. 전개 및 교육
   6.1 이행 계획 수립
   6.2 데이터 이행
   6.3 사용자 교육
   6.4 운영 이관
```

### WBS 작성 도구

| 도구 | 특징 | 적합한 상황 |
|:---|:---|:---|
| MS Project | WBS + 간트 자동 연동, 자원 관리 | 대형 전통 프로젝트 |
| Jira / Confluence | Epic > Story > Task 계층 | 애자일 프로젝트 |
| Miro / Lucidchart | 시각적 트리 다이어그램 | 워크숍, 브레인스토밍 |
| WBS Chart Pro | WBS 전용, 시각화 강점 | WBS 작성 특화 |
| Excel | 단순하고 범용적 | 소규모 프로젝트 |

### 안티패턴

- **기능이 아닌 조직 중심 WBS**: WBS는 산출물(What)을 중심으로 작성해야 한다. "개발팀 업무", "QA팀 업무"처럼 조직 단위로 나누면 범위 누락을 찾기 어렵다.
- **WBS 사전 없는 WBS**: 항목만 나열하고 완료 기준, 담당자, 원가 추정이 없으면 WBS가 종이 호랑이가 된다.
- **범위 변경 후 WBS 미갱신**: 변경 요청으로 범위가 추가/삭제되었을 때 WBS를 갱신하지 않으면 기준이 흔들린다.
- **너무 세밀한 분해**: 1~2시간 단위까지 분해하면 WBS 관리 자체가 프로젝트가 된다. 적절한 수준(80시간 이하 WP)을 유지한다.

- **📢 섹션 요약 비유**: WBS 없이 프로젝트를 시작하는 것은 설계도 없이 건물을 짓는 것이다. 나중에 "이 방은 어디 있나요?"라고 물었을 때 "설계도에 없는데요"라는 대답을 듣게 된다.

## Ⅴ. 기대효과 및 결론

WBS는 소프트웨어 프로젝트 관리에서 가장 기초적이면서도 가장 중요한 산출물 중 하나다. 프로젝트 규모와 복잡도가 증가할수록 WBS의 가치는 더욱 커진다.

정량적 효과로는 범위 변경 요청(CR) 감소 (명확한 범위 정의로 모호함 제거), 원가 추정 정확도 향상 (WP 단위 상향식 추정), 진도 측정의 객관성 확보 (WP 완료 여부 기반)를 들 수 있다. 연구에 따르면 WBS를 제대로 작성한 프로젝트가 그렇지 않은 프로젝트보다 일정 준수율이 20~30% 높다.

애자일 시대에도 WBS는 사라지지 않는다. 스크럼의 Product Backlog는 WBS의 계층 개념(Epic > Feature > Story > Task)을 계승한 것이며, 하이브리드 PM에서는 릴리스 레벨에서 WBS를 사용하고 스프린트 레벨에서 백로그를 사용하는 방식이 일반적이다.

기술사 답안에서는 "100% 규칙으로 범위 완전성 보장, WP 단위의 원가·일정 추정 가능, CPM/PERT/간트 차트의 입력 데이터, 범위 기준선의 핵심 구성 요소"를 핵심 키워드로 설명한다.

- **📢 섹션 요약 비유**: WBS는 프로젝트의 유전자 지도(DNA)다. 모든 작업의 구조와 관계가 담겨 있어, 이것만 제대로 완성되면 나머지 모든 계획(일정, 비용, 자원)을 자동으로 도출할 수 있다.

| :--- | :--- |

| 간트 차트 | WBS + 기간 + 자원을 시간축으로 표현 |

### 👶 어린이를 위한 3줄 비유 설명

1. WBS는 레고 세트를 조립하기 전에 부품 목록을 다 적어두는 것이에요. 모든 조각이 목록에 있어야 나중에 빠진 조각이 없어요.
2. 큰 작업(레고 세트)을 작은 작업(개별 부품)으로 계속 나눠서, 각 부품마다 "누가, 언제, 얼마에" 만들지 정해요.
3. WBS가 없으면 반드시 빠진 작업이 나오고, 프로젝트가 늦어지거나 돈이 더 들어요!
